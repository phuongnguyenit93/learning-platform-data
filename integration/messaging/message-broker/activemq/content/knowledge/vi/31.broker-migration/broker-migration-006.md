# Xử lý namespace javax/jakarta và các tính năng chưa tương đương

## 1. Migration không dừng ở việc thay import

Khi chuyển ứng dụng giữa **ActiveMQ Classic** và **ActiveMQ Artemis**, hoặc nâng dòng Classic 5.x lên 6.x, nhóm phát triển thường gặp hai lớp thay đổi khác nhau:

1. **Java API namespace và binary compatibility**: các kiểu JMS nằm trong package **javax.jms** hoặc **jakarta.jms**. Dù tên lớp như ConnectionFactory, Session, Message và Queue giống nhau, hai kiểu này là hai class identity khác nhau đối với compiler, JVM, framework và classloader.
2. **Broker/provider feature parity**: cùng một API JMS không có nghĩa mọi tính năng riêng của broker, semantics vận hành, destination model, retry policy, scheduler, management và HA đều tương đương.

Một phép thay hàng loạt:

~~~java
import javax.jms.*;
~~~

thành:

~~~java
import jakarta.jms.*;
~~~

chỉ thay tên package trong source. Nó **không tự chuyển dependency, Spring Framework, JNDI binding, JCA resource adapter, generated bytecode, provider-specific options hoặc broker configuration**. Nó cũng không chuyển message store, wire protocol hay chính sách retry sang broker mới.

~~~mermaid
flowchart TD
    A["Ứng dụng JMS hiện tại"] --> B["Kiểm kê API và dependency"]
    B --> C["Chọn namespace mục tiêu"]
    C --> D["Biên dịch lại + kiểm tra classloader"]
    D --> E["Đối chiếu protocol và provider features"]
    E --> F["Mapping destination / retry / scheduler / XA"]
    F --> G["Contract tests và dữ liệu migration"]
    G --> H["Canary, cutover, reconcile"]
~~~

Trong module **INTEGRATION_MESSAGING_MESSAGE_BROKER_ACTIVEMQ**, ActiveMQ Classic và Artemis đều cung cấp messaging qua queue/topic, producer/consumer, transaction, acknowledgment, redelivery và vận hành broker. Bài này tập trung vào ranh giới migration: **javax/jakarta là ranh giới API Java**, còn tính năng broker cần được đối chiếu theo **provider + version + protocol + configuration**.

## 2. javax.jms và jakarta.jms là hai API khác nhau

### 2.1. Khác namespace, không phải chỉ khác cách viết

| API | Package chính | Nguồn chuẩn | Ví dụ kiểu |
| --- | --- | --- | --- |
| JMS 1.1 / JMS 2.0 | javax.jms | Java EE / Jakarta EE trước namespace change | javax.jms.ConnectionFactory |
| Jakarta Messaging 3.x | jakarta.jms | Jakarta EE 9+ | jakarta.jms.ConnectionFactory |

Các lớp có tên giống nhau nhưng không cùng kiểu:

~~~java
javax.jms.ConnectionFactory legacyFactory = ...;
jakarta.jms.ConnectionFactory modernFactory = ...;
~~~

Không thể truyền trực tiếp biến thứ nhất vào method nhận biến thứ hai. JVM lưu tên lớp đầy đủ trong bytecode descriptor, nên một thư viện biên dịch với **javax.jms.ConnectionFactory** không tự tương thích với API **jakarta.jms.ConnectionFactory**.

Lỗi thường gặp khi migration:

| Dấu hiệu | Nguyên nhân thường gặp |
| --- | --- |
| package javax.jms does not exist | Dependency JMS javax đã bị loại hoặc scope không đúng |
| package jakarta.jms does not exist | Chưa thêm Jakarta Messaging API/client tương thích |
| incompatible types: javax.jms... cannot be converted to jakarta.jms... | Hai namespace cùng xuất hiện ở ranh giới method/bean |
| ClassNotFoundException / NoClassDefFoundError | Runtime thiếu API package mà bytecode đã tham chiếu |
| ClassCastException | Cùng tên lớp đơn giản nhưng class identity khác namespace/classloader |
| NoSuchMethodError / AbstractMethodError | Binary được biên dịch với API/provider version khác runtime |
| Bean type mismatch khi khởi động Spring | Framework và JMS ConnectionFactory dùng namespace khác nhau |

**Không chữa lỗi bằng cách thêm cả hai JMS API vào classpath** nếu provider/framework không hỗ trợ mô hình đó. Cần xác định một namespace cho mỗi ứng dụng/deployment boundary, hoặc tách adapter sang process/classloader riêng khi thật sự phải duy trì hai thế hệ client.

### 2.2. Phân biệt broker version và client artifact

Các dòng ActiveMQ có lịch sử chuyển đổi khác nhau:

| Dòng | API phía broker | Client/API thường gặp | Lưu ý migration |
| --- | --- | --- | --- |
| Classic 5.x cũ | javax.jms | activemq-client với javax.jms | Phù hợp ứng dụng Java EE/Spring cũ |
| Classic 5.18.x | javax.jms ở broker | activemq-client javax; có module chuyển tiếp activemq-client-jakarta cho client từ xa | Jakarta transitional client không dùng chung JVM với broker/client javax; không dùng embedded VM transport trong mô hình này |
| Classic 6.x | Jakarta namespace | activemq-client Jakarta | Cần JDK/framework tương thích Jakarta; một số JMS 2.0/3.1 API vẫn có mức hỗ trợ theo release |
| Artemis | Broker protocol/core độc lập với JMS namespace | artemis-jms-client cho JMS javax; artemis-jakarta-client cho Jakarta Messaging | Chọn đúng artifact theo namespace của ứng dụng |

Bảng này là định hướng theo các dòng phát hành, **không thay thế release notes của đúng patch version**. Ví dụ Classic 5.18.x có artifact chuyển tiếp Jakarta chỉ cho client kết nối remote; không nhúng broker javax vào cùng JVM. Classic 6.x dùng Jakarta namespace ở cả client và broker. Artemis cung cấp hai client artifact cho hai API namespace, trong khi server vẫn có thể phục vụ các protocol được cấu hình.

### 2.3. JMS namespace không phải wire protocol

JMS/Jakarta Messaging định nghĩa **API lập trình**, không định nghĩa một wire protocol bắt buộc. Ví dụ:

- Classic JMS client native thường dùng **OpenWire**.
- Artemis JMS/Jakarta client native thường dùng **Artemis Core protocol**.
- Artemis có thể cấu hình OpenWire protocol support để một số Classic client kết nối; mức tương thích tính năng cần được kiểm tra.
- Cả hai broker có thể hỗ trợ thêm AMQP, MQTT hoặc STOMP theo module/acceptor và version.

Do đó:

- Đổi import javax → jakarta không đổi protocol trên dây.
- Đổi ActiveMQConnectionFactory sang Artemis ActiveMQConnectionFactory có thể đồng thời đổi client artifact, native protocol, reconnect/failover options và semantics riêng.
- Dùng OpenWire client kết nối Artemis không đồng nghĩa mọi tính năng Classic đều có mặt trên Artemis.
- Đổi protocol không làm message store KahaDB trở thành Artemis journal.

## 3. Chọn dependency và namespace đúng

### 3.1. ActiveMQ Classic client

Classic 5.x với ứng dụng javax thường dùng dependency:

~~~xml
<dependency>
    <groupId>org.apache.activemq</groupId>
    <artifactId>activemq-client</artifactId>
    <version>5.18.7</version>
</dependency>
~~~

Với **Classic 5.18.x** và ứng dụng Jakarta cần client kết nối remote, có module chuyển tiếp:

~~~xml
<dependency>
    <groupId>org.apache.activemq</groupId>
    <artifactId>activemq-client-jakarta</artifactId>
    <version>5.18.7</version>
</dependency>
~~~

Module chuyển tiếp này có giới hạn quan trọng: không dùng chung trong một JVM với broker/client Classic sử dụng javax.jms và không hỗ trợ embedded VM transport. Nếu cần embedded broker hoặc nâng cả broker, đánh giá dòng Classic 6.x thay vì coi module chuyển tiếp là một broker Jakarta đầy đủ.

Classic 6.x sử dụng artifact client Jakarta:

~~~xml
<dependency>
    <groupId>org.apache.activemq</groupId>
    <artifactId>activemq-client</artifactId>
    <version>6.4.0</version>
</dependency>
~~~

Các version ở đây minh họa cách chọn artifact, không phải khuyến nghị cố định. Pin broker/client theo release được hỗ trợ và kiểm tra Java/Spring compatibility trước khi nâng.

### 3.2. Artemis client

Ứng dụng dùng JMS 2.0 với javax namespace:

~~~xml
<dependency>
    <groupId>org.apache.activemq</groupId>
    <artifactId>artemis-jms-client</artifactId>
    <version>2.42.0</version>
</dependency>
~~~

Ứng dụng dùng Jakarta Messaging:

~~~xml
<dependency>
    <groupId>org.apache.activemq</groupId>
    <artifactId>artemis-jakarta-client</artifactId>
    <version>2.42.0</version>
</dependency>
~~~

Chọn **một** trong hai artifact cho một module. Không thêm cả hai để “hỗ trợ mọi broker”. Client version phải tương thích với broker release; tránh tự ghép jar nội bộ Artemis khác version vì dễ tạo lỗi linkage khó chẩn đoán.

### 3.3. Dependency convergence và kiểm tra classpath

Maven:

~~~bash
mvn dependency:tree -Dverbose
~~~

Tìm đồng thời các artifact:

- javax.jms API (ví dụ javax.jms-api hoặc geronimo-jms spec).
- jakarta.jms-api.
- activemq-client / activemq-client-jakarta.
- artemis-jms-client / artemis-jakarta-client.
- Spring JMS, Spring Boot starter, JCA adapter và connection pool.

Nếu ứng dụng chỉ chuyển sang Jakarta, phải loại dependency javax cũ khỏi **runtime path** của module tương ứng, trừ khi một thư viện độc lập cần namespace cũ và được cô lập an toàn. Kiểm tra dependency tree cả compile, runtime, test và packaged artifact; dependency bị đánh dấu provided có thể vẫn xuất hiện trong container application server.

Có thể dùng jdeps để phát hiện bytecode tham chiếu namespace cũ:

~~~bash
jdeps --multi-release 17 --recursive --class-path "lib/*" target/classes
~~~

Kết quả jdeps hỗ trợ tìm dependency package, nhưng không phát hiện mọi truy cập qua reflection, string class name, XML bean definition hoặc JNDI runtime binding. Phải tìm source/config bổ sung.

## 4. Phân định ranh giới source code và provider adapter

### 4.1. Giữ namespace ở lớp adapter

Nếu domain service gọi trực tiếp JMS API khắp codebase, migration buộc phải sửa nhiều module và khó chạy song song hai provider. Tách logic nghiệp vụ khỏi JMS type bằng một interface nội bộ:

~~~java
public interface OrderEventPublisher {
    void publish(String eventId, String orderId, String eventType);
}
~~~

Domain service chỉ phụ thuộc interface:

~~~java
public final class OrderApplicationService {
    private final OrderEventPublisher publisher;

    public OrderApplicationService(OrderEventPublisher publisher) {
        this.publisher = publisher;
    }

    public void orderPaid(String orderId) {
        String eventId = java.util.UUID.randomUUID().toString();
        publisher.publish(eventId, orderId, "OrderPaid");
    }
}
~~~

Mỗi build profile/module cung cấp một adapter cụ thể. **Không đưa javax.jms hoặc jakarta.jms vào chữ ký interface domain**; nếu không, abstraction vẫn mang namespace của provider cũ.

### 4.2. Adapter javax.jms cho Classic 5.x

~~~java
import javax.jms.Connection;
import javax.jms.ConnectionFactory;
import javax.jms.JMSException;
import javax.jms.MessageProducer;
import javax.jms.Queue;
import javax.jms.Session;
import javax.jms.TextMessage;

public final class ClassicOrderPublisher implements OrderEventPublisher {
    private final ConnectionFactory connectionFactory;
    private final String destinationName;

    public ClassicOrderPublisher(
            ConnectionFactory connectionFactory,
            String destinationName) {
        this.connectionFactory = connectionFactory;
        this.destinationName = destinationName;
    }

    @Override
    public void publish(
            String eventId, String orderId, String eventType) {
        try (Connection connection =
                     connectionFactory.createConnection()) {
            Session session = connection.createSession(
                    true, Session.SESSION_TRANSACTED);
            try {
                Queue queue = session.createQueue(destinationName);
                MessageProducer producer = session.createProducer(queue);
                try {
                    TextMessage message = session.createTextMessage(eventType);
                    message.setStringProperty("eventId", eventId);
                    message.setStringProperty("orderId", orderId);
                    message.setStringProperty("eventType", eventType);
                    producer.send(message);
                    session.commit();
                } catch (JMSException failure) {
                    session.rollback();
                    throw failure;
                } finally {
                    producer.close();
                }
            } finally {
                session.close();
            }
        } catch (JMSException failure) {
            throw new IllegalStateException(
                    "Classic publish failed", failure);
        }
    }
}
~~~

Đoạn minh họa dùng transacted session để làm rõ commit boundary; eventId/orderId/eventType được đặt thành properties để ví dụ không phụ thuộc một serializer cụ thể. Trong ứng dụng thật, connection/session nên được quản lý bởi Spring/JMS pool hoặc producer lifecycle thích hợp, không tạo một connection mới cho mỗi event nếu throughput yêu cầu cao.

### 4.3. Adapter jakarta.jms cho Artemis hoặc Classic 6.x

~~~java
import jakarta.jms.ConnectionFactory;
import jakarta.jms.JMSContext;
import jakarta.jms.JMSProducer;
import jakarta.jms.Queue;

public final class JakartaOrderPublisher implements OrderEventPublisher {
    private final ConnectionFactory connectionFactory;
    private final String destinationName;

    public JakartaOrderPublisher(
            ConnectionFactory connectionFactory,
            String destinationName) {
        this.connectionFactory = connectionFactory;
        this.destinationName = destinationName;
    }

    @Override
    public void publish(
            String eventId, String orderId, String eventType) {
        try (JMSContext context = connectionFactory.createContext(
                JMSContext.SESSION_TRANSACTED)) {
            Queue queue = context.createQueue(destinationName);
            JMSProducer producer = context.createProducer();
            producer.setProperty("eventId", eventId);
            producer.setProperty("orderId", orderId);
            producer.setProperty("eventType", eventType);
            producer.send(queue, context.createTextMessage(eventType));
            context.commit();
        }
    }
}
~~~

Đoạn code dùng API Jakarta Messaging 3.x/JMS 2.0 style. Cách tạo JMSContext transacted không thay thế XA khi cùng transaction còn ghi database. Với XA/JTA, cần XAConnectionFactory, transaction manager và adapter/provider phù hợp; không tự gọi context.commit() bên trong một transaction được quản lý bởi container.

### 4.4. Không dùng reflection để “ép” hai namespace thành một

Không tạo utility nhận Object rồi reflection gọi createProducer/createSession nhằm dùng một class cho cả javax và jakarta. Cách đó:

- Mất kiểm tra kiểu ở compile time.
- Lỗi method signature chỉ xuất hiện lúc runtime.
- Che khác biệt transaction/exception types.
- Làm logging và tracing khó phân loại.
- Không xử lý được provider-specific features hoặc classloader boundary.

Dùng source set/module riêng và interface domain trung lập dễ kiểm thử hơn. Nếu bắt buộc có một artifact hỗ trợ hai namespace, tạo hai adapter module độc lập với dependency rõ ràng và test cả hai pipeline build.

## 5. Spring Framework, Spring Boot và JNDI cũng phải cùng namespace

### 5.1. Ranh giới Spring 5 và Spring 6

| Nền tảng | Namespace JMS thường dùng | Hệ quả |
| --- | --- | --- |
| Spring Framework 5.x / Spring Boot 2.x | javax.jms | Dùng JMS provider client javax và starter tương thích |
| Spring Framework 6.x / Spring Boot 3.x | jakarta.jms | Dùng provider client Jakarta; listener/factory/adapter phải cùng namespace |
| Spring Framework 7.x / Spring Boot 4.x | Jakarta namespace | Kiểm tra compatibility matrix theo release cụ thể |

Không thể chỉ nâng ActiveMQ client sang Jakarta rồi giữ nguyên Spring 5.x JMS classes. Ngược lại, Spring Boot 3.x không thể inject một javax.jms.ConnectionFactory vào bean mong đợi jakarta.jms.ConnectionFactory.

### 5.2. Spring Boot Artemis Jakarta

Ví dụ cấu hình kết nối native:

~~~yaml
spring:
  artemis:
    mode: native
    broker-url: tcp://broker.example.internal:61616
    user: ${ARTEMIS_USER}
    password: ${ARTEMIS_PASSWORD}
~~~

Code listener trong ứng dụng Jakarta:

~~~java
import jakarta.jms.Message;
import jakarta.jms.JMSException;
import org.springframework.jms.annotation.JmsListener;
import org.springframework.stereotype.Component;

@Component
public class OrderEventListener {
    @JmsListener(destination = "orders.events")
    public void onMessage(Message message) throws JMSException {
        String eventId = message.getStringProperty("eventId");
        // Delegate to application service with idempotency.
    }
}
~~~

Starter và auto-configuration phải tạo Jakarta-compatible ConnectionFactory. Kiểm tra dependency tree để chắc rằng không có một starter javax cũ kéo Spring JMS type cũ vào cùng application context.

### 5.3. Spring Boot Classic 5.x và 6.x

Classic 5.x với Spring 5/Boot 2 thường dùng javax-compatible client/starter. Classic 6.x dùng Jakarta namespace và phù hợp với Spring 6/Boot 3+ theo ma trận release.

~~~yaml
spring:
  activemq:
    broker-url: tcp://classic-broker.internal:61616
    user: ${ACTIVEMQ_USER}
    password: ${ACTIVEMQ_PASSWORD}
~~~

Hai ví dụ thuộc **hai starter khác nhau**. Không giữ đồng thời cả starter Artemis và Classic rồi suy rằng Spring tự chọn đúng broker. Kiểm tra dependency, auto-configuration report và bean ConnectionFactory thực tế được inject vào JmsTemplate/listener.

### 5.4. JNDI binding và application server

JNDI name như **java:/JmsXA** hoặc **jms/OrdersConnectionFactory** không mang namespace JMS trong chuỗi tên. Nhưng object được bind dưới tên đó vẫn có kiểu Java cụ thể. Khi đổi javax → jakarta:

- Cập nhật provider resource adapter và JNDI object factory tương thích.
- Cập nhật application server/Jakarta EE runtime.
- Kiểm tra resource-ref và injection type.
- Cập nhật deployment descriptor, annotation và server module dependencies.
- Không bind một javax ConnectionFactory rồi inject vào jakarta JMS resource.
- Kiểm tra pooling/transaction manager có nhận đúng XAConnectionFactory hay không.

Trong container/application server, thư viện có thể được nạp bởi parent classloader. Đặt thêm JMS API vào WAR/EAR có thể tạo duplicate classes và class-cast failure. Ưu tiên dùng namespace do server cung cấp và resource adapter đúng version; không đóng gói tùy tiện API/provider jars khi server đã quản lý chúng.

### 5.5. XA/JTA không phải đổi import là xong

Khi ứng dụng sử dụng XA, cần kiểm tra cả:

- XAConnectionFactory/XAConnection và XAResource đúng provider.
- JTA transaction manager, enlist/delist, recovery log và resource name.
- Recovery credentials và quyền truy cập broker sau restart.
- Transaction timeout, heuristic outcome và xử lý in-doubt transaction.
- Spring JtaTransactionManager hoặc application-server transaction integration.
- Khả năng provider/client version hỗ trợ API XA đang dùng.

Một code path transacted Session không tương đương XA. Nếu DB và broker phải cùng commit trong JTA, không thay XA bằng JMSContext local transaction chỉ vì code mới compile được.

## 6. Wire protocol: API namespace không quyết định giao thức trên mạng

### 6.1. Native protocol và client provider

| Broker | Native Java client thường dùng | Wire protocol native |
| --- | --- | --- |
| ActiveMQ Classic | activemq-client | OpenWire |
| ActiveMQ Artemis | artemis-jms-client hoặc artemis-jakarta-client | Artemis Core |

JMS không quy định hai broker phải sử dụng cùng wire protocol. Classic client native dùng OpenWire; Artemis native client dùng Core protocol. Artemis có protocol module **OpenWire** để tiếp nhận một số Classic clients khi acceptor bật protocol đó. Tuy nhiên, OpenWire interoperability không chứng minh mọi vendor-specific destination option, advisory, scheduler, management operation hoặc failure behavior được bảo toàn.

### 6.2. Artemis OpenWire acceptor là compatibility bridge

Ví dụ Artemis acceptor có thể bật OpenWire:

~~~xml
<acceptor name="legacy-openwire">
    tcp://0.0.0.0:61616?protocols=OPENWIRE
</acceptor>
~~~

Đây là ví dụ acceptor đặt trong phần **acceptors** của broker.xml; port và TLS/auth phải khớp môi trường. Classic client có thể tiếp tục kết nối qua OpenWire trong giai đoạn chuyển tiếp, nhưng phải kiểm thử từng tính năng đang dùng. Native Artemis Jakarta client sẽ dùng Core protocol, dù source code có import jakarta.jms.

**Không nhầm hai kiểu compatibility:**

- OpenWire bridge giúp một client Classic nói chuyện với Artemis qua protocol được hỗ trợ.
- Jakarta client đổi API Java sang jakarta.jms.
- Hai việc có thể diễn ra độc lập: có thể dùng Classic client OpenWire trên Artemis, hoặc dùng Artemis Jakarta client native Core.
- Không thể dùng một artifact javax chỉ bằng cách đổi broker URL sang Artemis Core; wire protocol và JMS API đều phải tương thích.

### 6.3. Chọn protocol theo giai đoạn

| Giai đoạn | Client | Broker | Mục tiêu |
| --- | --- | --- | --- |
| Legacy baseline | Classic javax/OpenWire | Classic 5.x | Đo và lưu hành vi hiện tại |
| Compatibility phase | Classic client/OpenWire | Artemis OpenWire acceptor | Tách thay broker khỏi thay source namespace, nếu feature set đủ |
| Jakarta client phase | Artemis Jakarta/Core hoặc Classic 6.x Jakarta | Broker tương ứng | Chuyển API namespace và provider |
| Multi-protocol integration | AMQP/JMS/other clients | Artemis/Classic acceptor phù hợp | Tích hợp client khác ngôn ngữ; kiểm tra mapping semantics |

Compatibility phase chỉ nên là **cầu nối có thời hạn**. Ghi ngày loại bỏ OpenWire legacy client, đo feature gap và không coi nó là đích kiến trúc mặc định nếu ứng dụng cần native Artemis functionality.

## 7. Feature parity: phân loại tính năng trước khi viết lại

### 7.1. Ba mức parity

Dùng ba mức khi lập danh mục:

- **Tương đương chuẩn**: hành vi được định nghĩa bởi JMS/Jakarta Messaging, hai provider đều có hỗ trợ phù hợp; vẫn cần contract test vì cấu hình và edge cases khác nhau.
- **Có cơ chế tương tự nhưng không tương đương**: đạt cùng mục tiêu nghiệp vụ nhưng cấu hình, semantics, failure mode hoặc management khác.
- **Không có parity trực tiếp / phải thay thế**: cần adapter, application logic, bridge, route hoặc thay đổi kiến trúc.

Không gắn nhãn “supported” chỉ vì broker có một tính năng tên gần giống. Cần ghi **phiên bản broker, client, protocol, cấu hình, test evidence**.

### 7.2. Ma trận tính năng cần đối chiếu

| Nhóm | ActiveMQ Classic | Artemis | Cách xử lý migration |
| --- | --- | --- | --- |
| Queue/topic cơ bản | JMS Queue/Topic | JMS Queue/Topic trên address/queue routing | Thường tương đương ở API; xác minh durable/temporary và auto-create |

| Durable subscription | Classic durable topic subscription | Durable subscription queue/address mapping | Kiểm tra clientID/subscriptionName, offline backlog và unsubscribe |
| Shared durable subscription | Phụ thuộc Classic release/client feature support | Hỗ trợ theo JMS/Jakarta client version và cấu hình | Không giả định parity; test multi-consumer, distribution, close/reconnect |
| Async send CompletionListener | Hỗ trợ theo release; có API method chưa triển khai ở một số dòng | Hỗ trợ theo API/client release | Kiểm tra callback completion/error và ordering |

| Persistence files | KahaDB/JDBC store tùy cấu hình | Artemis journal/paging/bindings | Không dùng chung hoặc copy trực tiếp data directory |

### 7.4. Ví dụ feature gap phải kiểm tra theo release

Tài liệu hỗ trợ JMS 2.0/Jakarta Messaging của ActiveMQ Classic ghi rõ đây là **partial support** và một số method có thể ném **UnsupportedOperationException** thay vì thực thi. Trong bảng implementation progress hiện hành tại thời điểm đối chiếu **17-11-2026**, các ví dụ đáng chú ý gồm:

- **JMSContext, JMSConsumer, JMSProducer và JMSRuntimeException** đã được triển khai từ dòng 5.18.0.
- Các XA Connection methods được ghi nhận hoàn tất ở 5.18.3 và 6.0.0.
- **CompletionListener async send** đang có tiến độ triển khai với target 6.5.0; không mặc định có trong dòng Classic 6.4.x.
- **Shared topic consumer** và **JMS DeliveryDelay** được ghi target 7.0.0 trong bảng tiến độ này; kiểm tra lại release notes trước khi dùng.
- Tính năng tùy chọn **JMSProducer.disableMessageID** được ghi là không hỗ trợ trong feature notes.

Các mốc trên là trạng thái của bảng hỗ trợ tại thời điểm viết, không phải cam kết rằng mọi build/vendor distribution đều giống nhau. Với API chuẩn, hãy viết test khởi tạo và gọi method thực tế trên client version đã pin; không chỉ kiểm tra method có tồn tại lúc compile. Đối với provider-specific behavior, ghi fallback/adapter hoặc quyết định bỏ tính năng.

## 8. Mapping những tính năng dễ mất khi chuyển broker

### 8.1. Virtual topics và durable subscriptions

Classic Virtual Topic thường dùng một topic nguồn và các queue theo consumer group, ví dụ:

~~~text
Topic: VirtualTopic.Orders
Queue: Consumer.Inventory.VirtualTopic.Orders
Queue: Consumer.Billing.VirtualTopic.Orders
~~~

Mỗi logical consumer group có queue riêng; nhiều worker trong cùng group chia sẻ queue đó. Khi chuyển sang Artemis, mô hình thường được biểu diễn bằng **MULTICAST address** và một queue riêng cho từng consumer group:

~~~xml
<address name="orders.events">
    <multicast>
        <queue name="orders.inventory"/>
        <queue name="orders.billing"/>
    </multicast>
</address>
~~~

Producer publish tới address **orders.events**; queue inventory và billing nhận bản phân phối riêng. Nhiều Inventory workers cùng consume queue **orders.inventory** để chia việc trong nhóm. Đây là mapping mục tiêu, không tự chuyển được tất cả tên destination, selector, durable subscription và wildcard của Classic. Cần tạo queue, kiểm tra routing type và test offline consumer backlog trước cutover.

Với durable topic subscription, lập danh sách **clientID + subscriptionName**, selector và **noLocal** nếu dùng. Không đổi tên subscription tùy tiện: broker có thể coi đó là subscription mới, để backlog cũ ở subscription cũ hoặc tạo hai luồng nhận trùng.

### 8.2. Composite destinations và fan-out

Classic có thể cấu hình composite destination để một send được route tới nhiều destination. Artemis có **divert**, MULTICAST address hoặc application fan-out để đạt một số mục tiêu tương tự, nhưng không mặc định cùng semantics:

- Một send tới nhiều đích có thể có thứ tự và failure behavior khác.
- Divert là routing ở broker; không phải JMS transaction phân tán giữa nhiều broker.
- Nếu yêu cầu một business event được ghi đồng bộ vào nhiều hệ thống, cần xác định atomicity và reconciliation.
- Nếu không có cơ chế atomic fan-out phù hợp, cân nhắc outbox + event relay và idempotent consumers.

Không chuyển một chuỗi composite destination URI thành một divert XML bằng phép thay tên. Hãy viết test cho từng destination: message có xuất hiện, persistence, duplicate, rollback, expiry và thứ tự.

### 8.3. Scheduled delivery và delivery delay

Classic scheduler có thể dùng property riêng như **AMQ_SCHEDULED_DELAY** khi scheduler được bật. Jakarta Messaging/JMS 2 cung cấp API **JMSProducer.setDeliveryDelay**, nhưng mức hỗ trợ phụ thuộc client/provider release. Artemis có cơ chế scheduled delivery riêng và hỗ trợ API theo release.

Classic vendor-specific example:

~~~java
TextMessage message = session.createTextMessage("invoice-reminder");
message.setLongProperty("AMQ_SCHEDULED_DELAY", 30_000L);
producer.send(message);
~~~

Artemis/Jakarta API example:

~~~java
context.createProducer()
       .setDeliveryDelay(30_000L)
       .send(queue, "invoice-reminder");
~~~

Không xem hai đoạn code là bảo đảm tương đương trước khi kiểm thử. Cần đối chiếu:

- Delay tính từ lúc broker nhận hay lúc client gọi send.
- Độ chính xác thời gian và clock source.
- Persistent scheduled message qua restart.
- TTL/expiration tương tác với delivery time.
- Retry, redelivery và dead-letter sau thời điểm scheduled.
- Hành vi nếu client timeout và gửi lại event.

Với cron, repeat/periodic scheduling hoặc job scheduler stateful, có thể cần một scheduler service/application riêng thay vì cố ép mọi job thành delayed message một lần.

### 8.4. Redelivery, DLQ và poison message

Classic và Artemis đều có retry/redelivery và dead-letter capability, nhưng cấu hình đặt ở các lớp khác nhau. Classic có thể dùng **RedeliveryPolicy** phía client và **individualDeadLetterStrategy** ở broker; Artemis dùng **address-settings** với redelivery delay, max-delivery-attempts và dead-letter address.

Migration cần so sánh **kết quả quan sát**, không chỉ so số cấu hình:

| Thuộc tính | Cần ghi nhận |
| --- | --- |
| Initial redelivery delay | Lần retry đầu sau bao lâu |
| Backoff | Fixed hay exponential; multiplier và maximum delay |
| Maximum attempts | Số lần delivery tổng cộng hay số lần redelivery sau lần đầu |
| Rollback | Có trả message ngay hay theo delay |
| Consumer crash | Message đang in-flight được xử lý thế nào |
| Expiration | Message hết TTL trước retry được xử lý ra sao |
| DLQ routing | Tên DLQ, preserve headers/properties, queue durability |
| Poison message | Có thể retry vô hạn hay được quarantine |
| Ordering | Một message đang retry có chặn message sau trong cùng queue/group không |

Chạy test có chủ đích: consumer rollback N lần, sau đó ACK; một test khác luôn rollback đến khi message vào DLQ. So số lần delivery, JMSXDeliveryCount/Redelivered, timestamp và destination cuối cùng.

### 8.5. Message grouping và ordering

Nếu ứng dụng dựa vào **JMSXGroupID**, phải test:

- Cùng group được xử lý tuần tự theo mong đợi.
- Nhiều group có thể được phân phối song song.
- Consumer đóng hoặc mất kết nối thì ownership group chuyển ra sao.
- Failover/rebalance có thể giao lại message và làm side effect lặp không.
- **JMSXGroupFirstForConsumer** hoặc provider-specific group hints có mapping hay không.

Không suy rằng hai broker hỗ trợ JMSXGroupID thì ordering/fairness/failover behavior giống hệt. Ghi test theo **business aggregate ID và sequence**, không chỉ quan sát thứ tự trên console.

### 8.6. Advisory và management notifications

Classic advisory topics có thể được ứng dụng dùng như event stream để biết consumer/producer/destination lifecycle. Artemis có management notifications và management API, nhưng tên event, payload, security và subscription mechanism không giống advisory topic mặc định.

Nếu ứng dụng đang subscribe advisory:

1. Liệt kê advisory topic và message property mà code đọc.
2. Phân biệt advisory dùng cho **business logic** hay chỉ monitoring.
3. Business logic nên chuyển sang event/domain API ổn định thay vì phụ thuộc notification nội bộ broker.
4. Monitoring chuyển sang Artemis management/JMX/metrics exporter hoặc adapter riêng.
5. Test mất notification, reconnect, duplicate và quyền management.

Không xóa advisory listener trước khi chứng minh consumer nghiệp vụ không còn phụ thuộc.

### 8.7. ObjectMessage và payload compatibility

ObjectMessage có thể phụ thuộc Java class name, serialVersionUID, classloader và serialization policy. Đổi broker hoặc namespace không giải quyết các vấn đề này. Khi có thể, chuyển payload giữa các service sang schema rõ ràng như JSON/Avro/Protobuf với **schema version** và event contract.

Nếu vẫn phải hỗ trợ ObjectMessage:

- Kiểm tra allowlist/trust policy của broker/client.
- Đảm bảo class có mặt ở cả hai runtime và tương thích serialVersionUID.
- Test rolling upgrade khi producer và consumer chạy hai version khác nhau.
- Không deserialize object không tin cậy.
- Đặt lộ trình loại bỏ payload gắn chặt Java class khỏi contract liên dịch vụ.

## 9. Destination, URI và configuration không thể copy nguyên trạng

### 9.1. Destination naming và routing model

Classic thường phân biệt queue/topic theo JMS Destination. Artemis biểu diễn address và queue với routing type **ANYCAST/MULTICAST**. Một address có thể có một hoặc nhiều queue; tên JMS queue/topic không nhất thiết phản ánh đầy đủ topology thực.

| Classic concept | Artemis concept có thể dùng | Cần kiểm chứng |
| --- | --- | --- |
| Queue | Address + ANYCAST queue | Auto-create, queue durability, routing |
| Topic | Address + MULTICAST | Subscription queues, durable subscription |
| Virtual topic | MULTICAST address + queue theo group | Fan-out và consumer-group semantics |
| Wildcard destination | Address/queue wildcard match | Syntax, separator và phạm vi match |
| Composite destination | Divert/multicast/application fan-out | Atomicity, order, duplicate |
| Temporary queue/topic | Temporary queue/address semantics | Ownership, lifetime và reconnect |
| Destination options trong URI | Artemis address settings/consumer options | Không copy query option provider-specific |

Một queue có thể tồn tại trên Artemis nhưng consumer không nhận message nếu routing type hoặc binding không khớp. Khi tạo destination, xác minh **address, queue, routing type, durable flag, filter/selector và permissions**.

### 9.2. URI options và connection factory

Classic client URI có thể chứa transport options như failover, prefetch, redelivery, compression và OpenWire wire format. Artemis client dùng connector/factory options và Core protocol parameters. Cùng một tên option không bảo đảm cùng semantics hoặc cùng đơn vị.

Tạo một bảng mapping cho mỗi option:

~~~text
Option:
Classic URI/property:
Artemis URI/property:
Default Classic:
Default Artemis:
Unit:
When applied:
Behavior under reconnect:
Behavior under transaction rollback:
Load/security impact:
Test evidence:
Decision:
~~~

Không copy **failover:(...)** sang Artemis hoặc copy **consumerWindowSize** sang Classic. Viết lại connection factory config theo provider đích, sau đó test broker restart, network loss, reconnect, credential rotation và TLS hostname validation.

### 9.3. Persistence store không tương thích

Classic KahaDB/JDBC store và Artemis journal/bindings/paging có định dạng và metadata khác nhau. **Không copy thư mục data của Classic sang Artemis**, không đổi tên file journal để ép broker đọc. Broker đích phải được khởi tạo storage riêng.

Di chuyển dữ liệu cần một trong các cách được thiết kế rõ:

- Drain queue bằng consumer bridge/relay có ACK và retry.
- Export/import theo công cụ được hỗ trợ cho đúng broker release.
- Chuyển tiếp message qua protocol/bridge trong cửa sổ migration.
- Replay từ source of truth/outbox/event log nếu có.

Với mọi cách, cần xác định message headers/properties, delivery mode, expiration, priority, timestamp, correlation ID, reply-to, group ID, scheduled time, redelivery count và original destination nào được bảo toàn. Không phải mọi metadata provider-specific đều chuyển được.


## 10. Kế hoạch migration theo giai đoạn

### Giai đoạn 1 — Inventory hiện trạng

Thu thập từ source code, runtime và broker configuration:

- Maven/Gradle dependencies, JMS API namespace, provider client và Java version.
- Spring Framework/Boot, JCA resource adapter, JNDI, XA transaction manager, connection pool.
- Destination thực tế: queue/topic, durable subscription, virtual topic, composite destination, wildcard.
- URI options: failover, prefetch, redelivery, compression, TLS, clientID và reconnect.
- Broker policies: DLQ, expiry, scheduler, paging/flow control, authorization, advisories, persistence, HA.
- Payload contract: TextMessage/BytesMessage/MapMessage/ObjectMessage, property type, schema version.
- SLO: throughput, p95/p99 latency, RPO/RTO, backlog age và downtime window.

Không chỉ tìm chuỗi **javax.jms** bằng grep. Dùng dependency tree, jdeps, reflection/config search, application server descriptor và broker management để tìm cả phụ thuộc gián tiếp.

### Giai đoạn 2 — Chọn namespace và runtime đích

Chốt:

1. Broker đích là Classic 6.x hay Artemis, đúng release cụ thể.
2. Client artifact và namespace javax/jakarta.
3. JDK và Spring Boot/Framework tương thích.
4. Native protocol hay compatibility protocol trong giai đoạn chuyển.
5. Ứng dụng standalone hay chạy trong application server/JCA.
6. Có XA/JTA hay local JMS transaction.
7. Những tính năng chưa parity cần thay thế hoặc loại bỏ.

Viết quyết định kiến trúc trước khi thay code. Nếu cần chuyển namespace nhưng chưa thể chuyển broker, có thể chọn một client Jakarta tương thích remote với broker cũ trong giai đoạn chuyển tiếp **nếu đúng artifact/release hỗ trợ**. Đây là giải pháp tạm có giới hạn, không phải bảo đảm broker đã chuyển sang Jakarta.

### Giai đoạn 3 — Cô lập provider adapter

- Tạo module Classic javax hoặc Classic Jakarta/Artemis Jakarta riêng.
- Domain/service layer chỉ phụ thuộc interface nội bộ.
- Chuyển cấu hình ConnectionFactory, pool, JNDI và Spring listener.
- Loại duplicate JMS API/provider jar khỏi runtime classpath.
- Biên dịch và chạy unit tests từng module.
- Kiểm tra exception translation, transaction boundary và resource lifecycle.

Không chuyển đồng thời mọi service nếu một nhóm có thể chuyển độc lập qua contract ổn định. Nhưng phải có kế hoạch rõ về destination ownership và consumer concurrency khi nhiều broker cùng hoạt động.

### Giai đoạn 4 — Mapping broker features

Với từng feature register, quyết định một trong bốn hướng:

| Quyết định | Khi dùng |
| --- | --- |
| **Keep** | Có parity đủ và test chứng minh |
| **Replace** | Có cơ chế khác đạt cùng mục tiêu nghiệp vụ |
| **Redesign** | Semantics cũ gắn quá chặt provider hoặc không có parity trực tiếp |
| **Remove** | Feature không còn cần thiết; có owner xác nhận |

Ví dụ: advisory chỉ dùng monitoring có thể chuyển sang metrics/notifications; virtual topic có thể map sang multicast address và consumer queues; scheduled cron job có thể chuyển sang scheduler service; retry/DLQ phải cấu hình lại theo address policy và test poison message.

### Giai đoạn 5 — Data migration và coexistence

Chọn cách chuyển message theo yêu cầu downtime và khả năng đối soát:

- **Drain and switch**: dừng producer, để consumer cũ xử lý hết backlog, sau đó chuyển client sang broker mới.
- **Bridge/relay**: chuyển message từ broker cũ sang broker mới trong thời gian coexistence; phải xử lý duplicate, ACK và loop.
- **Export/import**: chỉ dùng công cụ hỗ trợ đúng phiên bản và kiểm tra metadata được giữ.
- **Replay from source of truth**: phát lại event từ outbox/event log có eventId ổn định.

Không dual-write đồng thời vào hai broker bằng hai JMS send độc lập nếu chưa có outbox/idempotency. Nếu send thứ nhất thành công và send thứ hai timeout, hai broker có trạng thái khác nhau; retry có thể tạo duplicate.

### Giai đoạn 6 — Canary và cutover

- Chọn một producer/consumer group hoặc tenant ít rủi ro.
- Dùng destination test riêng và eventId duy nhất.
- Chạy contract tests, security tests và performance baseline.
- So backlog, enqueue/dequeue, ACK, DLQ, latency và business side effects.
- Mở rộng theo từng nhóm, theo dõi trong cửa sổ đã định.
- Chuyển writer ownership theo từng destination; tránh hai broker cùng nhận writes cho cùng business stream nếu không có cơ chế reconciliation.

### Giai đoạn 7 — Rollback và kết thúc

Rollback không chỉ là đổi URL trở lại broker cũ. Cần xác định message đã được consume/ACK ở broker mới sẽ được phục hồi ra sao:

- Giữ broker cũ ở trạng thái read-only hoặc không cho nhận producer mới sau cutover.
- Ghi eventId/sequence để xác định phần dữ liệu đã đi qua broker mới.
- Nếu rollback, replay có kiểm soát các event chưa được xử lý ở hệ thống đích.
- Không copy data directory giữa hai broker.
- Chỉ gỡ bridge/client cũ sau khi backlog, durable subscriptions, DLQ và audit đã được đối soát.
- Giữ khả năng rollback trong thời hạn đã thống nhất; sau đó archive cấu hình và bằng chứng nghiệm thu.

## 11. Contract test: chứng minh semantics trước khi cutover

Mỗi test phải chạy trên **broker version + client version + protocol + configuration** thực tế dự kiến production. Một test in-memory hoặc embedded broker không chứng minh được TLS, reconnect, persistence hay wire interoperability.

### 11.1. API và classpath

| Test | Kỳ vọng |
| --- | --- |
| Compile domain module | Không tham chiếu javax/jakarta trực tiếp |
| Compile provider adapter | Chỉ một JMS namespace trong module |
| Runtime dependency tree | Không có provider/API conflict |
| Spring context startup | ConnectionFactory đúng namespace được inject |
| JNDI lookup | Object type tương thích resource-ref |
| JCA/XA startup | Resource adapter và transaction manager đúng namespace |

### 11.2. Messaging semantics

| Test case | Điều cần xác minh |
| --- | --- |
| Queue send/receive | Message đến đúng queue, đúng routing |
| Topic multicast | Mỗi subscriber có bản phân phối theo policy |
| Durable subscription | Offline backlog, reconnect, unsubscribe |
| Selector | Property type, null, numeric/string comparison |
| Persistent + transacted send | Commit/rollback và restart |
| Consumer ACK/rollback | Redelivery count, duplicate, DLQ |
| TTL/expiration | Expiry timestamp và dead-letter/expiry address |
| Priority | Dispatch behavior trong điều kiện backlog |
| Delivery delay | Scheduled time, restart và expiration |
| Message group | Ordering trong group, ownership sau consumer loss |
| XA/JTA | Enlist, rollback, recovery sau broker restart |
| Temporary destination | Lifetime, owner connection và reconnect |
| ObjectMessage | Serialization allowlist, class compatibility |
| Correlation/reply-to | Correlation ID, reply destination và request timeout |

### 11.3. Network, security và recovery

- DNS đổi IP và broker restart.
- TCP timeout, connection reset và reconnect backoff.
- TLS CA sai, SAN sai, certificate hết hạn.
- mTLS thiếu client certificate.
- Credentials sai, role thiếu send/consume.
- HA failover và transaction outcome UNKNOWN.
- Mirror/bridge lag nếu dùng coexistence.
- Connection leak, consumer leak và pool exhaustion.

Một test được coi là PASS khi xác minh được **cả kết quả mong đợi lẫn trạng thái broker**. Ví dụ, producer nhận exception sau commit timeout không đủ để kết luận message chưa được lưu; cần tra eventId ở broker và consumer side effect để phân loại outcome UNKNOWN.

### 11.4. Test không mất/không lặp nghiệp vụ

Mỗi message migration nên có **eventId ổn định** và sequence/aggregate key. Consumer dùng inbox table hoặc unique constraint để ngăn side effect lặp:

~~~sql
CREATE TABLE processed_events (
    consumer_name VARCHAR(100) NOT NULL,
    event_id VARCHAR(160) NOT NULL,
    processed_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (consumer_name, event_id)
);
~~~

Trong cùng DB transaction, insert eventId nếu chưa có, thực hiện side effect, rồi commit DB; ACK JMS sau khi transaction nghiệp vụ thành công. Nếu process crash giữa DB commit và JMS ACK, message redeliver nhưng inbox ngăn xử lý side effect lần hai.

Không dùng JMSMessageID làm business key duy nhất: khi message được re-send/bridge qua broker khác, broker đích có thể tạo JMSMessageID mới. Giữ eventId trong property/body và đối soát theo key này.

## 12. Các sai lầm thường làm migration thất bại

| Sai lầm | Hậu quả | Cách tránh |
| --- | --- | --- |
| Thay import nhưng giữ dependency javax | Compile/runtime linkage error | Chọn artifact đúng namespace, dependency convergence |
| Thêm cả javax và jakarta API vào mọi module | Classloader/type mismatch | Tách module/process boundary |
| Cho rằng Jakarta API làm đổi wire protocol | Client và acceptor nói khác protocol | Chọn protocol và provider rõ ràng |
| Dùng Classic OpenWire client trên Artemis rồi tuyên bố parity | Vendor features có thể thiếu/khác | Feature register và contract test |
| Copy broker XML | Destination/URI/policy semantics khác | Map từng policy theo mục tiêu |
| Copy KahaDB vào Artemis | Broker không đọc được store, có thể hỏng dữ liệu | Export/bridge/drain/replay |
| Đổi VirtualTopic thành topic đơn giản | Mất queue-per-consumer-group semantics | Address MULTICAST + queue theo group |
| Đổi scheduler property thành delivery delay mà không test | Delay/expiry/restart khác | Kiểm thử timeline và persistence |
| Chỉ test send success | Consumer/ACK/selector có thể sai | End-to-end send, receive, commit và đối soát |
| Bỏ qua durable subscription | Backlog hoặc subscription cũ bị bỏ lại | Inventory clientID/subscriptionName |
| Dùng admin để smoke test | Che thiếu quyền service account | Test đúng principal production |
| Dual-write không idempotency | Một broker nhận, broker kia timeout; duplicate khi retry | Outbox/event relay và reconciliation |
| Rollback chỉ bằng đổi URL | Message đã ACK ở broker mới không có ở broker cũ | Event ledger, replay và cutover ownership |
| Không kiểm tra XA recovery | In-doubt transaction sau migration | Test transaction manager/recovery log thực tế |

## 13. Checklist quyết định và nghiệm thu

| Câu hỏi | Bằng chứng cần có |
| --- | --- |
| Đã chốt namespace mục tiêu? | Dependency matrix và runtime classpath |
| Framework/application server tương thích? | Spring/Jakarta EE/JCA compatibility test |
| Client artifact đúng broker release? | Version matrix, pinned dependencies |
| Wire protocol đã chốt? | URI, acceptor, protocol compatibility test |
| Destination topology đã mapping? | Queue/topic/address/ANYCAST/MULTICAST inventory |
| Vendor features đã đối chiếu? | Feature register với parity level và owner |
| Retry/DLQ/scheduler/order đã test? | Contract tests và broker metrics |
| XA/JTA có recovery? | Fail/restart recovery evidence |
| Message store migration có kế hoạch? | Drain/bridge/export/replay plan; không copy journal |
| Duplicate/loss có kiểm soát? | Stable eventId, inbox, reconciliation |
| Security đã chuyển? | TLS/mTLS, principal, least-privilege authorization |
| Cutover có rollback? | Writer ownership, RPO/RTO, rollback runbook |
| Observability đã đổi? | Dashboard, alerts, advisory/notification mapping |
| Legacy client có ngày loại bỏ? | Milestone và owner rõ ràng |

**Kết luận:** Migration giữa ActiveMQ Classic và Artemis có hai bài toán độc lập nhưng liên quan: chuyển API Java từ **javax.jms** sang **jakarta.jms** và chuyển semantics/configuration từ một provider sang provider khác. Namespace migration đòi hỏi dependency, framework, classloader và resource adapter đồng bộ; feature migration đòi hỏi mapping destination, scheduler, redelivery/DLQ, virtual topic, advisory, XA, persistence và management. Giữ API khác namespace ở adapter riêng, kiểm tra protocol độc lập, lập feature register và chứng minh bằng contract tests trước khi cutover. Đừng coi source compile thành công là bằng chứng hệ thống đã migration đúng.
