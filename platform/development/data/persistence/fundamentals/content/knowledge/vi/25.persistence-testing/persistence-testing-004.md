# Kiểm thử ràng buộc, giá trị biên và dữ liệu không hợp lệ

## Mục tiêu học tập

Sau bài học này, người học có thể:

1. Phân biệt kiểm thử validation ở Java, kiểm thử repository/JDBC và kiểm thử **ràng buộc thực thi trong database**.
2. Thiết kế ca kiểm thử cho khóa chính, UNIQUE, khóa ngoại, NOT NULL, CHECK, kiểu dữ liệu, giới hạn độ dài, độ chính xác số và quan hệ giữa nhiều cột.
3. Tìm đúng **điểm biên**: ngay dưới ngưỡng, tại ngưỡng, ngay trên ngưỡng; phân biệt giá trị NULL với chuỗi rỗng, số không và giá trị không tồn tại.
4. Kiểm tra SQLSTATE, trạng thái transaction và dữ liệu sau rollback thay vì chỉ khẳng định “có exception”.
5. Sử dụng Java 17, JDBC, JUnit 5 và một PostgreSQL Testcontainers dành riêng cho integration test.
6. Phát hiện những lỗi khó thấy khi nhiều transaction đồng thời ghi cùng khóa, sử dụng lại request key hoặc truy cập chéo tenant.
7. Đưa bộ kiểm thử vào migration/CI mà không rò dữ liệu thật hoặc phụ thuộc kết quả tình cờ từ một DBMS khác.

Bài nằm trong chương **Kiểm thử lưu trữ** của module **DATA_PERSISTENCE_FUNDAMENTALS**. Module đề cập toàn bộ vòng đời persistence của Java: mô hình dữ liệu, schema, truy vấn, chỉ mục, transaction, isolation, kiểm soát đồng thời, lỗi kết nối, tiến hóa schema, bảo mật, sao lưu và hiệu năng. Ở đây mục tiêu là chứng minh **dữ liệu hợp lệ được chấp nhận, dữ liệu không hợp lệ bị từ chối và trạng thái bền vững không bị phá vỡ khi một thao tác thất bại**.

## 1. Kiểm thử persistence khác gì kiểm thử một hàm Java?

Giả sử service tạo đơn hàng có điều kiện:

~~~java
if (quantity <= 0) {
    throw new IllegalArgumentException("Invalid quantity");
}
~~~

Một unit test có thể chứng minh Java không gọi repository nếu `quantity = 0`. Nhưng điều đó **không chứng minh** database chặn được một script SQL, batch job, phiên bản ứng dụng cũ hoặc một đường ghi khác bỏ qua validation này.

Ngược lại, một database có `CHECK (quantity > 0)` có thể bảo vệ hàng dữ liệu, nhưng không tự đưa ra phản hồi API thân thiện hoặc kiểm tra quyền người dùng trước khi truy vấn.

| Tầng kiểm thử | Điều cần bảo đảm | Điều không tự chứng minh |
| --- | --- | --- |
| Unit test domain/service | Quy tắc nghiệp vụ và ánh xạ kết quả lỗi ở Java | PostgreSQL constraint có tồn tại/thực thi đúng |
| Test repository với mock | Service gọi repository đúng nhánh | JDBC SQL, constraint, transaction, isolation thực |
| Integration test với DB thật | SQL thực, kiểu dữ liệu, SQLSTATE, FK/UNIQUE/CHECK và rollback | Toàn bộ đường HTTP, xác thực, queue hoặc cache |
| API/component test | Validation, authorization, response 4xx/5xx, transaction orchestration | Khả năng khôi phục sau mất điện hoặc lỗi toàn vùng |
| Concurrency/fault test | Race, deadlock, kết quả commit không rõ, retry/idempotency | Mọi lịch thực thi và mọi sự cố ngoài mô hình test |

**Nguyên tắc:** kiểm tra cùng một bất biến ở các lớp cần thiết, nhưng không xem một lớp là vật thay thế cho lớp còn lại. Ví dụ “không cho đặt quantity âm” nên có validation ở API **và** ràng buộc ở DB nếu đó là bất biến lưu trữ bắt buộc.

### 1.1. Điều cần xác nhận trong một test âm tính

Một test tốt cho input không hợp lệ không chỉ cần “có lỗi”:

1. Lỗi phát sinh **ở tầng mong đợi**: validation, DB constraint hay authorization.
2. Có **loại lỗi ổn định** để định danh, ví dụ SQLSTATE và constraint name khi thích hợp.
3. **Không có hàng sai** được commit.
4. Các thay đổi trước đó trong cùng transaction **không bị commit một phần** khi nghiệp vụ yêu cầu nguyên tử.
5. Connection/transaction được rollback, đóng hoặc trả pool đúng cách.
6. API không làm lộ SQL, dữ liệu tenant khác, stack trace, secret hay thông tin nhạy cảm.
7. Retry không biến một lỗi dữ liệu xác định thành vòng lặp hoặc tạo side effect trùng.

Kiểm thử phải nói rõ dữ liệu đầu vào, hành động, kết quả mong đợi và bằng chứng trạng thái DB cuối cùng.

## 2. Lược đồ ví dụ: đơn hàng nhiều tenant

Dùng PostgreSQL để kiểm chứng nhất quán một mô hình cụ thể. Ví dụ bên dưới chỉ dành cho **database test độc lập**:

~~~sql
CREATE TABLE tenants (
    tenant_id BIGINT PRIMARY KEY,
    name TEXT NOT NULL
);

CREATE TABLE customers (
    tenant_id   BIGINT NOT NULL REFERENCES tenants (tenant_id),
    customer_id BIGINT NOT NULL,
    email       TEXT NOT NULL,
    PRIMARY KEY (tenant_id, customer_id)
);

CREATE TABLE orders (
    tenant_id    BIGINT NOT NULL REFERENCES tenants (tenant_id),
    order_id     BIGINT GENERATED BY DEFAULT AS IDENTITY,
    request_key  VARCHAR(64) NOT NULL,
    customer_id  BIGINT NOT NULL,
    quantity     INTEGER NOT NULL CHECK (quantity BETWEEN 1 AND 1000),
    unit_price   NUMERIC(12, 2) NOT NULL CHECK (unit_price >= 0),
    status       TEXT NOT NULL CHECK (status IN ('NEW', 'PAID')),
    paid_at      TIMESTAMPTZ,
    delivery_note TEXT,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (tenant_id, order_id),
    UNIQUE (tenant_id, request_key),
    FOREIGN KEY (tenant_id, customer_id)
        REFERENCES customers (tenant_id, customer_id),
    CONSTRAINT paid_requires_time
        CHECK (status <> 'PAID' OR paid_at IS NOT NULL)
);

CREATE TABLE order_items (
    tenant_id BIGINT NOT NULL,
    order_id  BIGINT NOT NULL,
    line_no   INTEGER NOT NULL CHECK (line_no > 0),
    PRIMARY KEY (tenant_id, order_id, line_no),
    FOREIGN KEY (tenant_id, order_id)
        REFERENCES orders (tenant_id, order_id)
);
~~~

Lược đồ này cố ý chứa nhiều kiểu ràng buộc:

- `PRIMARY KEY (tenant_id, order_id)` nhận diện đơn trong phạm vi tenant.
- `UNIQUE (tenant_id, request_key)` chống tạo trùng yêu cầu **trong cùng tenant**.
- `FOREIGN KEY (tenant_id, customer_id)` yêu cầu khách hàng và đơn cùng tenant.
- `quantity BETWEEN 1 AND 1000` cho phép hai đầu biên, loại ngoài biên.
- `NUMERIC(12,2)` giới hạn độ chính xác và scale của giá.
- `status IN ('NEW','PAID')` giới hạn tập trạng thái.
- `paid_requires_time` áp dụng quy tắc liên cột: đơn PAID phải có `paid_at`.
- `delivery_note` được phép NULL nên test không được đồng nhất NULL với chuỗi rỗng.
- `created_at` có DEFAULT tại DB khi omitted; gửi NULL một cách tường minh vẫn không phải “dùng DEFAULT”.

Dữ liệu fixture:

~~~sql
INSERT INTO tenants (tenant_id, name)
VALUES (42, 'Tenant A'), (77, 'Tenant B');

INSERT INTO customers (tenant_id, customer_id, email)
VALUES
    (42, 10, 'a@example.invalid'),
    (77, 10, 'b@example.invalid');
~~~

Hai tenant có **cùng `customer_id = 10`** có chủ đích. Test phải chứng minh khóa ghép ngăn gán nhầm khách giữa các tenant; dùng một bộ dữ liệu luôn có ID toàn cục khác nhau có thể bỏ lỡ lỗi join/FK thiếu tenant.

## 3. Bảng quyết định kiểm thử theo ràng buộc

| Bất biến | Hợp lệ điển hình | Không hợp lệ hoặc giá trị biên | Kỳ vọng |
| --- | --- | --- | --- |
| PK đơn hàng | `(42, 1)` khác `(77, 1)` | Hai hàng trùng `(42, 1)` | SQLSTATE `23505` |
| Unique request | Tenant A/B cùng `req-1` | Tenant A gửi `req-1` lần hai | `23505` hoặc xử lý idempotent ở service |
| Customer FK | Order tenant 42, customer 10 của tenant 42 | Order tenant 42, customer 99 không có | `23503` |
| Item FK ghép | Item (42, order của 42) | Item tenant 77 trỏ order chỉ có ở 42 | `23503` |
| Quantity | 1 và 1000 | 0, −1, 1001 | `23514` |
| Giá | 0.00 và số dương hợp lệ | −0.01 | `23514` |
| Phạm vi NUMERIC(12,2) | 9999999999.99 | 10000000000.00 | `22003` |
| Trường NOT NULL | `request_key='r1'` | `request_key=NULL` | `23502` |
| Độ dài VARCHAR(64) | 64 ký tự | 65 ký tự khác khoảng trắng | `22001` |
| Status | `NEW`, `PAID` | `DELETED` | `23514` |
| Điều kiện liên cột | `PAID + paid_at` | `PAID + paid_at=NULL` | `23514` |
| Note nullable | NULL hoặc chuỗi rỗng | Không mặc nhiên coi chúng giống nhau | Cả hai hợp lệ nhưng khác nghĩa |
| Default timestamp | Không truyền created_at | Truyền created_at=NULL | Default **không** thay NULL tường minh; `23502` |
| Kiểu dữ liệu | BIGINT hợp lệ | `'abc'::BIGINT` | Thường `22P02` |

Các mã SQLSTATE trên là hướng dẫn cho **PostgreSQL với lược đồ đã nêu**. Mã ở API hoặc exception subclass JDBC có thể khác theo driver, ORM và nơi lỗi được phát hiện.

### 3.1. Tránh test chỉ có một giá trị “sai hiển nhiên”

Ví dụ quantity:

~~~text
Phân vùng không hợp lệ dưới:  ... -1, 0
Biên dưới hợp lệ:                     1
Bên trong hợp lệ:                  2..999
Biên trên hợp lệ:                   1000
Phân vùng không hợp lệ trên:        1001, 2000, ...
~~~

Một test chỉ dùng `quantity = -999` chứng minh quá ít: lỗi off-by-one thường xuất hiện ở `0, 1, 1000, 1001`. Tương tự, test độ dài nên dùng `63, 64, 65` ký tự, không chỉ một chuỗi 10.000 ký tự.

## 4. Kiểm thử NULL, CHECK và ba giá trị logic

Trong SQL, `NULL` không đồng nghĩa với 0, chuỗi rỗng hay false. Kết quả của biểu thức liên quan NULL có thể là **UNKNOWN**.

Ở PostgreSQL, một `CHECK` thất bại khi biểu thức đánh giá thành **FALSE**, còn TRUE hoặc UNKNOWN không bị CHECK từ chối. Vì vậy:

~~~sql
CREATE TABLE price_example (
    amount NUMERIC(12, 2) CHECK (amount >= 0)
);
~~~

Lệnh `INSERT INTO price_example(amount) VALUES (NULL)` có thể được chấp nhận dù có CHECK. Nếu nghiệp vụ bắt buộc giá, cần:

~~~sql
CREATE TABLE price_example_strict (
    amount NUMERIC(12, 2) NOT NULL CHECK (amount >= 0)
);
~~~

**Bộ test cần tách hai trường hợp:** giá âm bị CHECK từ chối; NULL bị NOT NULL từ chối. Không nói “CHECK amount >= 0 đã bảo vệ không-null”.

### 4.1. NULL và chuỗi rỗng

~~~sql
SELECT NULL IS NULL;     -- TRUE
SELECT '' IS NULL;       -- FALSE
SELECT NULL = NULL;      -- UNKNOWN, không phải TRUE
~~~

Với `delivery_note TEXT`, NULL có thể nghĩa “chưa cung cấp”, còn chuỗi rỗng nghĩa “đã cung cấp nhưng không có nội dung”. Nếu nghiệp vụ coi chúng tương đương, hãy chuẩn hóa ở ranh giới được xác định và kiểm thử việc chuẩn hóa. Đừng tình cờ thay đổi ngữ nghĩa khi migration Java/JPA.

### 4.2. UNIQUE và NULL

PostgreSQL mặc định cho phép **nhiều giá trị NULL** trong một cột có UNIQUE vì các NULL được xem là khác nhau theo ngữ nghĩa ràng buộc mặc định.

~~~sql
CREATE TABLE optional_codes (
    id BIGINT PRIMARY KEY,
    code TEXT UNIQUE
);

INSERT INTO optional_codes (id, code)
VALUES (1, NULL), (2, NULL); -- Thường hợp lệ trên PostgreSQL
~~~

Từ PostgreSQL 15 có hỗ trợ khai báo unique với `NULLS NOT DISTINCT` khi muốn đối xử NULL như không phân biệt. Đây là lựa chọn schema có chủ đích; đừng áp dụng mặc định từ một DBMS sang DBMS khác.

### 4.3. Quy tắc nhiều cột và các tổ hợp

Với `paid_requires_time`, nên thử ma trận:

| status | paid_at | Kỳ vọng |
| --- | --- | --- |
| NEW | NULL | Hợp lệ |
| NEW | Giá trị thời điểm hợp lệ | Hợp lệ theo CHECK hiện tại, dù nghiệp vụ có thể muốn cấm |
| PAID | NULL | `23514` |
| PAID | Thời điểm hợp lệ | Hợp lệ |
| NULL | Bất kỳ | `23502` vì status NOT NULL |
| UNKNOWN | Bất kỳ | `23514` vì status CHECK |

Nếu nghiệp vụ muốn “NEW phải có paid_at NULL”, schema hiện tại **chưa áp quy tắc đó**. Test nên làm lộ khoảng trống và dẫn đến quyết định sửa constraint, không viết assertion theo điều hệ thống *đáng lẽ* làm rồi giả vờ đã có ràng buộc.

## 5. Biên số: INTEGER, BIGINT, NUMERIC và làm tròn

Một kiểu dữ liệu có hai loại giới hạn: **phạm vi biểu diễn** và **phạm vi nghiệp vụ**.

- `INTEGER` PostgreSQL lưu số nguyên 32-bit có dấu. Một giá trị ngoài phạm vi có thể gây `22003` trước khi tới CHECK.
- `BIGINT` lưu số nguyên 64-bit có dấu; Java `long` khớp về phạm vi số nguyên, nhưng vẫn cần kiểm tra parse, overflow khi tính và giá trị âm không hợp lệ.
- `NUMERIC(12,2)` có tối đa 12 chữ số tổng cộng, trong đó 2 chữ số sau dấu thập phân; giá trị tối đa dương nằm dưới 10^10.
- `CHECK (quantity BETWEEN 1 AND 1000)` hẹp hơn miền kiểu INTEGER.

### 5.1. Độ chính xác tiền và phép làm tròn

~~~sql
SELECT 0.001::NUMERIC(12, 2); -- Có thể thành 0.00
SELECT 1.235::NUMERIC(12, 2); -- Làm tròn theo quy tắc NUMERIC
~~~

Với PostgreSQL, ép `NUMERIC` về scale nhỏ hơn có thể làm tròn; **không mặc nhiên ném lỗi vì người gọi gửi quá hai chữ số thập phân**. Do vậy, nếu hợp đồng API muốn **từ chối** giá `1.234` thay vì âm thầm làm tròn, cần validation ở Java hoặc constraint kiểm tra độ chính xác đầu vào trước khi ép vào cột mất thông tin.

Java nên dùng `BigDecimal` cho giá tiền, kiểm tra scale theo nghiệp vụ:

~~~java
import java.math.BigDecimal;
import java.math.RoundingMode;

public final class MoneyValidation {
    public static BigDecimal requireExactTwoDecimals(
            BigDecimal input) {
        if (input == null) {
            throw new IllegalArgumentException("Amount is required");
        }
        if (input.signum() < 0) {
            throw new IllegalArgumentException("Amount is negative");
        }

        // UNNECESSARY từ chối nếu cần thay đổi giá trị để đạt scale 2.
        return input.setScale(2, RoundingMode.UNNECESSARY);
    }
}
~~~

`new BigDecimal("1.230")` được chấp nhận vì có thể biểu diễn chính xác thành 1.23; `new BigDecimal("1.234")` bị từ chối. Không tạo `BigDecimal` từ số thực nhị phân `double` để biểu diễn số tiền nhập văn bản.

### 5.2. Biên ngày giờ

Với `TIMESTAMPTZ`, kiểm thử:

- Thời điểm có offset khác nhau nhưng cùng instant có được lưu/truy vấn nhất quán không?
- UTC và múi giờ hiển thị có bị nhầm, nhất là quanh đổi giờ mùa hè ở hệ thống có DST?
- Giá trị thiếu timezone khi chuyển từ `LocalDateTime` sang `Instant` được diễn dịch theo timezone nào?
- Giá trị quá xa, định dạng sai hoặc NULL có bị xử lý theo hợp đồng đúng không?
- Giá trị `created_at` mặc định chỉ được tạo khi **omitted** chứ không phải khi client truyền NULL.
- `paid_at` có phải sau `created_at` không? Schema hiện tại **chưa kiểm tra** quan hệ này.

Ở Java, `Instant` hoặc `OffsetDateTime` thường phù hợp với các mốc thời gian tuyệt đối. Dùng dữ liệu giờ giả lập rõ ràng thay vì `LocalDateTime.now()` không được kiểm soát trong unit test.

### 5.3. Unicode, VARCHAR và số ký tự

`VARCHAR(64)` trong PostgreSQL giới hạn theo **ký tự**, không đơn giản là số byte UTF-8. Java `String.length()` trả độ dài theo **UTF-16 code unit**, nên một emoji có thể chiếm hai code unit dù ứng dụng người dùng nhìn một ký tự.

Các ca nên có:

- 64 ký tự ASCII và 65 ký tự ASCII.
- Dữ liệu tiếng Việt có dấu và Unicode tổ hợp.
- Emoji và ký tự nằm ngoài Basic Multilingual Plane.
- Chuỗi rỗng, khoảng trắng đầu/cuối, tab và ký tự xuống dòng.
- Chuỗi rất dài để kiểm tra từ chối có kiểm soát, không gây phình bộ nhớ/log.

**Không suy rằng số byte, Java `length()`, số code point và số grapheme hiển thị là một đại lượng.** Hợp đồng nghiệp vụ nên chọn rõ cách đo, rồi kiểm tra cả validation Java và giới hạn thực của DB.

## 6. Khóa ngoại, composite key và bất biến nhiều bảng

Một lỗi phổ biến trong SaaS là các bảng đều có `tenant_id` nhưng khóa ngoại lại chỉ dựa trên một ID không mang tenant.

Ví dụ không an toàn nếu `order_id` chỉ duy nhất **trong từng tenant**:

~~~sql
-- Không đủ để bảo vệ quan hệ theo tenant:
FOREIGN KEY (order_id) REFERENCES orders (order_id)
~~~

Ngoài việc có thể không tạo được nếu `orders(order_id)` không có unique key phù hợp, ý tưởng này bỏ qua ranh giới tenant. Trong lược đồ ví dụ:

~~~sql
FOREIGN KEY (tenant_id, order_id)
REFERENCES orders (tenant_id, order_id)
~~~

Test âm tính cần thực sự tạo hai tenant có các ID trùng nhau; nếu mọi fixture ID đều khác nhau, test có thể không phát hiện sự nhầm phạm vi.

### 6.1. Dữ liệu fixture phải tạo điều kiện kích hoạt lỗi

Giả sử chỉ có order `(tenant_id=42, order_id=101)`. Hãy cố tạo:

~~~sql
INSERT INTO order_items (tenant_id, order_id, line_no)
VALUES (77, 101, 1);
~~~

Nếu Tenant B **không** có order 101, FK ghép phải báo `23503`. Nếu cả hai tenant đều có order 101, câu INSERT đó là quan hệ hợp lệ tới order B; test không được suy rằng “cùng order_id với A là lỗi” khi B có hàng cha tương ứng.

### 6.2. Kiểm thử FK chưa đủ cho authorization

Ràng buộc FK ngăn quan hệ dữ liệu không hợp lệ, **không tự ngăn SELECT hoặc UPDATE chéo tenant** bởi một role có quyền toàn bảng. Một test bảo mật cần:

- Dùng database role runtime giống production.
- Kiểm tra RLS nếu có, với tenant context đã đặt đúng.
- Xác minh query JOIN mang đủ tenant scope.
- Dùng request/token thuộc Tenant A cố đọc/sửa tài nguyên B.
- Kiểm tra cache, export và queue cũng phân vùng theo tenant.

Test constraint và test authorization có mục tiêu khác nhau; một bài test có `23503` không thể đại diện cho tất cả bảo đảm multi-tenancy.

## 7. SQLSTATE: khẳng định đúng loại lỗi thay vì dựa vào thông báo

Với PostgreSQL/JDBC:

| SQLSTATE | Ý nghĩa | Trường hợp điển hình |
| --- | --- | --- |
| `23505` | unique_violation | Trùng PK hoặc UNIQUE |
| `23503` | foreign_key_violation | Tham chiếu hàng cha không tồn tại |
| `23502` | not_null_violation | NULL cho cột NOT NULL |
| `23514` | check_violation | Quantity âm, status sai, PAID thiếu paid_at |
| `22001` | string_data_right_truncation | Chuỗi vượt giới hạn VARCHAR |
| `22003` | numeric_value_out_of_range | Số vượt phạm vi NUMERIC/INTEGER |
| `22P02` | invalid_text_representation | Chuỗi không chuyển được sang kiểu mục tiêu |
| `25P02` | in_failed_sql_transaction | Transaction đã lỗi nhưng vẫn cố chạy SQL |
| `40001` | serialization_failure | Xung đột isolation SERIALIZABLE |
| `40P01` | deadlock_detected | Deadlock giữa các transaction |

Ở Java:

~~~java
try {
    // Gửi lệnh SQL có thể vi phạm constraint.
} catch (java.sql.SQLException error) {
    String sqlState = error.getSQLState();
    int vendorCode = error.getErrorCode();

    // Assertion test có thể dùng SQLSTATE và kiểm tra trạng thái DB.
    // Không phân loại bằng việc chứa một chuỗi tiếng Anh trong message.
    throw error;
}
~~~

**Vì sao không assert message?** Thông báo có thể thay đổi theo driver, DBMS, phiên bản hoặc localization. SQLSTATE ổn định hơn với PostgreSQL, nhưng vẫn cần hiểu **ngữ cảnh operation**: một `23505` ở idempotency key có thể nghĩa yêu cầu đã xử lý, không phải luôn là lỗi 500.

Lỗi có thể xuất hiện ở `executeUpdate()`, `flush()` hoặc **`COMMIT`**, nhất là constraint được cấu hình deferrable. Test cần xét đúng thời điểm mà database thật thực thi ràng buộc.

## 8. Integration test thực với JUnit 5, Testcontainers và JDBC

Đối với constraint PostgreSQL, một database nhúng khác SQL dialect có thể cho kết quả không tương đương. Dùng một **PostgreSQL riêng cho test**, ví dụ Testcontainers, giúp chạy đúng cú pháp và SQLSTATE. Ví dụ dưới đây giả định project đã cấu hình JUnit Jupiter, Testcontainers PostgreSQL module và driver JDBC PostgreSQL tương thích với Java 17.

**Không chạy bộ fixture này trên database production hoặc database có dữ liệu cần giữ**: `TRUNCATE ... CASCADE` cố ý xóa dữ liệu của container thử nghiệm.

### 8.1. Bộ test cơ bản

Ví dụ Java dưới đây thiết lập database riêng, mỗi test reset dữ liệu, và luôn kiểm tra SQLSTATE **với kết nối thật**:

~~~java
import static org.junit.jupiter.api.Assertions.*;

import java.math.BigDecimal;
import java.sql.Connection;
import java.sql.DriverManager;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;
import java.sql.Statement;
import java.sql.Types;
import java.time.OffsetDateTime;

import org.junit.jupiter.api.BeforeAll;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.testcontainers.containers.PostgreSQLContainer;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;

@Testcontainers
class OrderConstraintIntegrationTest {
    @Container
    static final PostgreSQLContainer<?> POSTGRES =
            new PostgreSQLContainer<>("postgres:16-alpine");

    static Connection open() throws SQLException {
        return DriverManager.getConnection(
                POSTGRES.getJdbcUrl(),
                POSTGRES.getUsername(),
                POSTGRES.getPassword());
    }

    @BeforeAll
    static void createSchema() throws SQLException {
        // Ví dụ rút gọn từ schema ở phần 2; giữ cùng constraints.
        try (Connection c = open();
             Statement s = c.createStatement()) {
            s.executeUpdate("""
                CREATE TABLE tenants (
                    tenant_id BIGINT PRIMARY KEY
                )
                """);
            s.executeUpdate("""
                CREATE TABLE customers (
                    tenant_id BIGINT NOT NULL
                        REFERENCES tenants(tenant_id),
                    customer_id BIGINT NOT NULL,
                    PRIMARY KEY (tenant_id, customer_id)
                )
                """);
            s.executeUpdate("""
                CREATE TABLE orders (
                    tenant_id BIGINT NOT NULL
                        REFERENCES tenants(tenant_id),
                    order_id BIGINT GENERATED BY DEFAULT AS IDENTITY,
                    request_key VARCHAR(64) NOT NULL,
                    customer_id BIGINT NOT NULL,
                    quantity INTEGER NOT NULL
                        CHECK (quantity BETWEEN 1 AND 1000),
                    unit_price NUMERIC(12, 2) NOT NULL
                        CHECK (unit_price >= 0),
                    status TEXT NOT NULL
                        CHECK (status IN ('NEW', 'PAID')),
                    paid_at TIMESTAMPTZ,
                    PRIMARY KEY (tenant_id, order_id),
                    UNIQUE (tenant_id, request_key),
                    FOREIGN KEY (tenant_id, customer_id)
                        REFERENCES customers(tenant_id, customer_id),
                    CONSTRAINT paid_requires_time
                        CHECK (status <> 'PAID' OR paid_at IS NOT NULL)
                )
                """);
        }
    }

    @BeforeEach
    void seed() throws SQLException {
        // Chỉ sử dụng trong container test dành riêng cho class này.
        try (Connection c = open();
             Statement s = c.createStatement()) {
            s.executeUpdate(
                "TRUNCATE TABLE tenants RESTART IDENTITY CASCADE");
            s.executeUpdate(
                "INSERT INTO tenants(tenant_id) VALUES (42), (77)");
            s.executeUpdate("""
                INSERT INTO customers(tenant_id, customer_id)
                VALUES (42, 10), (77, 10)
                """);
        }
    }

    private static void insertOrder(
            Connection c,
            long tenantId,
            long customerId,
            String requestKey,
            int quantity,
            BigDecimal price,
            String status,
            OffsetDateTime paidAt) throws SQLException {
        String sql = """
            INSERT INTO orders
                (tenant_id, customer_id, request_key,
                 quantity, unit_price, status, paid_at)
            VALUES (?, ?, ?, ?, ?, ?, ?)
            """;
        try (PreparedStatement p = c.prepareStatement(sql)) {
            p.setLong(1, tenantId);
            p.setLong(2, customerId);
            p.setString(3, requestKey);
            p.setInt(4, quantity);
            p.setBigDecimal(5, price);
            p.setString(6, status);
            if (paidAt == null) {
                p.setNull(7, Types.TIMESTAMP_WITH_TIMEZONE);
            } else {
                p.setObject(7, paidAt);
            }
            p.executeUpdate();
        }
    }

    @FunctionalInterface
    interface SqlAction {
        void run(Connection c) throws SQLException;
    }

    static void assertSqlState(
            String expected, SqlAction action) {
        SQLException failure = assertThrows(
            SQLException.class,
            () -> {
                try (Connection c = open()) {
                    action.run(c);
                }
            });
        assertEquals(expected, failure.getSQLState());
    }

    @Test
    void quantityBoundary() throws SQLException {
        try (Connection c = open()) {
            insertOrder(c, 42, 10, "min", 1,
                    new BigDecimal("0.00"), "NEW", null);
            insertOrder(c, 42, 10, "max", 1000,
                    new BigDecimal("100.00"), "NEW", null);
        }
        assertSqlState("23514", c ->
            insertOrder(c, 42, 10, "zero", 0,
                new BigDecimal("1.00"), "NEW", null));
        assertSqlState("23514", c ->
            insertOrder(c, 42, 10, "over", 1001,
                new BigDecimal("1.00"), "NEW", null));
    }

    @Test
    void requestKeyUniqueOnlyWithinTenant() throws SQLException {
        try (Connection c = open()) {
            insertOrder(c, 42, 10, "same", 1,
                    BigDecimal.ONE, "NEW", null);
            insertOrder(c, 77, 10, "same", 1,
                    BigDecimal.ONE, "NEW", null);
        }
        assertSqlState("23505", c ->
            insertOrder(c, 42, 10, "same", 1,
                BigDecimal.ONE, "NEW", null));
    }

    @Test
    void foreignKeyAndPaidConstraint() {
        assertSqlState("23503", c ->
            insertOrder(c, 42, 999, "missing-parent", 1,
                BigDecimal.ONE, "NEW", null));
        assertSqlState("23514", c ->
            insertOrder(c, 42, 10, "paid-no-time", 1,
                BigDecimal.ONE, "PAID", null));
    }

    @Test
    void negativePriceAndNumericOverflow() {
        assertSqlState("23514", c ->
            insertOrder(c, 42, 10, "negative", 1,
                new BigDecimal("-0.01"), "NEW", null));
        assertSqlState("22003", c ->
            insertOrder(c, 42, 10, "too-large", 1,
                new BigDecimal("10000000000.00"),
                "NEW", null));
    }

    @Test
    void lengthBoundary() throws SQLException {
        try (Connection c = open()) {
            insertOrder(c, 42, 10, "a".repeat(64), 1,
                    BigDecimal.ONE, "NEW", null);
        }
        assertSqlState("22001", c ->
            insertOrder(c, 42, 10, "a".repeat(65), 1,
                BigDecimal.ONE, "NEW", null));
    }

    @Test
    void errorAbortsTransactionUntilRollback() throws SQLException {
        try (Connection c = open()) {
            c.setAutoCommit(false);
            try {
                insertOrder(c, 42, 10, "duplicate", 1,
                        BigDecimal.ONE, "NEW", null);

                SQLException duplicate = assertThrows(
                    SQLException.class,
                    () -> insertOrder(c, 42, 10, "duplicate", 1,
                        BigDecimal.ONE, "NEW", null));
                assertEquals("23505", duplicate.getSQLState());

                SQLException aborted = assertThrows(
                    SQLException.class,
                    () -> {
                        try (Statement s = c.createStatement();
                             ResultSet rs =
                                 s.executeQuery("SELECT COUNT(*) FROM orders")) {
                            rs.next();
                        }
                    });
                assertEquals("25P02", aborted.getSQLState());
            } finally {
                c.rollback();
            }
        }

        try (Connection check = open();
             Statement s = check.createStatement();
             ResultSet rs =
                 s.executeQuery("SELECT COUNT(*) FROM orders")) {
            assertTrue(rs.next());
            assertEquals(0, rs.getLong(1));
        }
    }
}
~~~

Bộ test trên **minh họa các ca tiêu biểu**, không phải toàn bộ ma trận. Nó không kiểm tra `order_items`, `created_at` hoặc `delivery_note` vì schema class được rút gọn; hãy mở rộng fixture theo schema production hoặc chạy migration thật của ứng dụng khi phát triển bộ test đầy đủ.

Lưu ý về Testcontainers: image PostgreSQL, tên package và cấu hình phụ thuộc các phiên bản dependency thực tế. Không cần bắt chước nguyên xi hình thức tích hợp Docker nếu CI đã có một PostgreSQL cô lập tương đương. Điều không được đánh đổi là **test trên engine và phiên bản tương thích production** đối với những semantics đang kiểm chứng.

### 8.2. Tránh chạy test phá dữ liệu lên DB không dành cho test

Có thể áp các nguyên tắc:

- Không cho test reset schema khi database URL trỏ tới môi trường không được phê duyệt.
- Dùng database/user riêng, quyền tối thiểu và tên schema riêng cho test.
- Không cần mang dữ liệu khách hàng production vào container.
- Không sử dụng secret production trong CI test.
- Không chạy các test dùng chung fixture và `TRUNCATE` song song nếu không có isolation test phù hợp.

Test rollback được diễn ra trên transaction thật; bản thân test framework có thể cũng mở transaction rồi rollback sau mỗi test. Cần phân biệt việc framework cleanup với **rollback do ràng buộc bị từ chối**.

## 9. Kiểm thử transaction: sau lỗi database ở trạng thái gì?

PostgreSQL có hành vi quan trọng: khi một statement trong transaction gặp lỗi, transaction thường chuyển sang trạng thái **aborted**. Các câu SQL sau bị trả `25P02` cho đến khi `ROLLBACK` hoặc rollback tới savepoint thích hợp.

Ví dụ:

~~~sql
BEGIN;

INSERT INTO orders
    (tenant_id, customer_id, request_key,
     quantity, unit_price, status)
VALUES (42, 10, 'req-1', 1, 10.00, 'NEW');

-- Trùng UNIQUE (tenant_id, request_key), sẽ lỗi:
INSERT INTO orders
    (tenant_id, customer_id, request_key,
     quantity, unit_price, status)
VALUES (42, 10, 'req-1', 1, 10.00, 'NEW');

-- Nếu vẫn ở transaction aborted, SELECT sau cũng có thể lỗi 25P02.
ROLLBACK;
~~~

Test phải kiểm tra cả **không có hàng `req-1` đã commit** sau rollback, không chỉ exception của INSERT thứ hai. Một thiết kế “catch SQLException rồi vẫn commit phần đầu” có thể phá tính nguyên tử nếu không tuân thủ transaction boundary.

### 9.1. Savepoint là công cụ có điều kiện

Một transaction có thể tạo savepoint, thử một statement rồi rollback tới savepoint khi lỗi để tiếp tục phần hợp lệ:

~~~sql
BEGIN;
SAVEPOINT before_optional_insert;

-- Thử INSERT có thể vi phạm UNIQUE.
-- Nếu thất bại:
ROLLBACK TO SAVEPOINT before_optional_insert;

-- Tiếp tục transaction nếu nghiệp vụ cho phép.
COMMIT;
~~~

Đây là cơ chế transaction, **không phải lý do bỏ qua lỗi dữ liệu**. Phải xác định một bước thất bại có thực sự là tùy chọn hay toàn nghiệp vụ phải rollback. Trong Java/JDBC, có API `Connection.setSavepoint()` và `rollback(savepoint)` khi driver hỗ trợ.

### 9.2. Constraint DEFERRABLE có thể lỗi ở COMMIT

Một số ràng buộc như foreign key và unique hỗ trợ kiểm tra deferred trong PostgreSQL nếu được khai báo thích hợp; không phải mọi loại CHECK/NOT NULL đều defer theo cùng cách.

~~~sql
CREATE TABLE parent_deferred (
    id BIGINT PRIMARY KEY
);

CREATE TABLE child_deferred (
    id BIGINT PRIMARY KEY,
    parent_id BIGINT NOT NULL,
    FOREIGN KEY (parent_id)
        REFERENCES parent_deferred(id)
        DEFERRABLE INITIALLY DEFERRED
);
~~~

Hai transaction case đáng thử:

**Case hợp lệ:** trong một transaction, INSERT child tham chiếu parent chưa có, sau đó INSERT parent trước COMMIT. Kết quả cuối hợp lệ nên commit có thể thành công.

**Case không hợp lệ:** chỉ INSERT child thiếu parent rồi COMMIT; lỗi FK có thể xuất hiện tại **COMMIT**, không phải khi INSERT ban đầu được gửi.

Một test chỉ gọi `entityManager.flush()` hoặc `executeUpdate()` rồi không bao giờ commit có thể bỏ sót lỗi deferred. Test phải thực sự commit trong môi trường cô lập và kiểm tra trạng thái sau thất bại.

## 10. Dữ liệu bị từ chối có thể ảnh hưởng sequence và audit không?

Đừng kỳ vọng một INSERT lỗi sẽ không tạo ra **bất kỳ side effect kỹ thuật** nào:

- PostgreSQL sequence/identity thường **không rollback giá trị đã cấp** khi transaction rollback hoặc INSERT thất bại.
- Do đó khóa sinh tự động có thể có **khoảng trống**; test không được khẳng định IDs luôn liên tục.
- Một trigger nằm trong transaction có thể bị rollback cùng hàng nếu nó ghi DB trong cùng transaction, nhưng một tác dụng phụ bên ngoài DB (email, HTTP call) không tự rollback.
- Log hệ thống có thể ghi nhận lệnh thử không hợp lệ ngay cả khi database từ chối.
- Thông báo lỗi có thể chứa giá trị constraint hoặc thông tin schema; không gửi nguyên văn cho API client.

**Tiêu chí đúng:** các bất biến nghiệp vụ và trạng thái commit phải được giữ, không phải “không có một byte nào đổi trên hệ thống”.

## 11. Concurrency: UNIQUE phải thắng cả khi hai request đến đồng thời

Hai request cùng tạo order với `tenant_id=42, request_key='checkout-17'`:

~~~text
Request A                  PostgreSQL                 Request B
    |                          |                         |
    | INSERT cùng key          |             INSERT key  |
    |------------------------->|<------------------------|
    |                          |                         |
    |   Một transaction có thể commit thành công          |
    |   Transaction còn lại phải chờ/conflict/được        |
    |   xử lý theo cơ chế UNIQUE và isolation             |
    |                          |                         |
~~~

Một test “đã SELECT không tồn tại rồi INSERT” chạy tuần tự **không phát hiện** race:

~~~java
// Không an toàn nếu thiếu constraint ở DB.
if (!repository.existsByRequestKey(tenantId, requestKey)) {
    repository.insertOrder(...);
}
~~~

Hai request có thể cùng thấy `false` trước khi bất kỳ bên nào INSERT. Cần UNIQUE ở DB hoặc một cơ chế tương đương giữ invariant, và xử lý idempotency ở tầng service.

### 11.1. Cách tổ chức concurrency test

1. Hai connection/transaction **độc lập**, mỗi cái có một request dùng cùng tenant và key.
2. Dùng `CountDownLatch` hoặc barrier để cho cả hai bắt đầu gần nhau.
3. Không giả định thread A thắng; kết quả hợp lệ là **chính xác một yêu cầu logic được tạo thành công**.
4. Khi cạnh tranh, một phía có thể chờ rồi nhận `23505`, hoặc service có thể dùng `ON CONFLICT` và trả kết quả cũ theo hợp đồng.
5. Đọc database bằng connection thứ ba và xác nhận chỉ có **một hàng** với khóa đó.
6. Kiểm tra mọi side effect ngoài DB được deduplicate nếu tồn tại.
7. Ghi nhận timeout/deadlock hoặc retry nếu test có thêm thao tác nhiều bảng; không chấp nhận mất bất biến chỉ vì kết quả race khó dự đoán.

Đừng cố dùng `Thread.sleep(20)` thay cho barrier và tuyên bố test chứng minh lịch đồng thời cần thiết. Với những transaction có thay đổi nhiều bảng, nên kiểm tra tính nguyên tử dưới deadlock và serialization failure.

### 11.2. Idempotency key trùng nhưng payload khác

Một constraint UNIQUE trên `(tenant_id, request_key)` không tự xác định người gọi đã gửi **cùng nội dung**:

~~~text
Lần 1: key=checkout-17, quantity=1 -> tạo đơn thành công
Lần 2: key=checkout-17, quantity=9 -> trùng key
~~~

Service phải kiểm tra định danh và fingerprint/payload của yêu cầu đã lưu rồi **từ chối xung đột** khi nội dung khác; không được trả kết quả cũ như thể hai yêu cầu tương đương. Thử lại một giao dịch mất ACK/COMMIT phải dùng cùng key, có đối soát và giới hạn phạm vi tenant.

## 12. Validation và cách ánh xạ lỗi tại API

Một lỗi SQLSTATE không phải một HTTP status mặc định:

| Tình huống | Kiểm tra ở đâu | Kết quả API có thể phù hợp |
| --- | --- | --- |
| quantity ngoài miền | Java Bean Validation/domain + CHECK DB | 400/422 theo hợp đồng |
| request key trùng cùng payload | UNIQUE DB + tra cứu kết quả cũ | Trả lại kết quả logic đã có |
| request key trùng khác payload | UNIQUE DB + so khớp request | 409 Conflict |
| FK customer không tồn tại | Service kiểm tra quyền/quan hệ + FK DB | 400/404/409 tùy nghiệp vụ |
| Thao tác tới tài nguyên tenant khác | Authorization + tenant-aware query/RLS | 403/404 theo chính sách chống lộ tồn tại |
| DB schema chưa tương thích | Migration/deploy issue | Lỗi hệ thống, không đổ cho input client |
| Serialization failure/deadlock | Transaction boundary và classifier | Retry toàn transaction nếu an toàn, có budget |
| Mất phản hồi COMMIT | Idempotency và đối soát | Trạng thái chưa xác định/tra cứu, không tạo yêu cầu mới |

Trên JPA/Spring, exception có thể được wrap vào `PersistenceException` hoặc `DataIntegrityViolationException`. Chỉ assert subclass framework nếu đó là hợp đồng test cần kiểm chứng; integration test DB nên giữ khả năng tìm nguyên nhân SQLSTATE theo provider/driver.

**Không gửi SQL, stack trace, tham số nhạy cảm hay constraint chứa PII trong body lỗi công khai.** Logging cũng cần cẩn trọng với request_key, email và nội dung ghi chú.

## 13. Property-based testing và tạo dữ liệu biên

Các ca ví dụ thủ công vẫn có thể bỏ sót tổ hợp hiếm. Có thể bổ sung property-based testing với generator tạo dữ liệu hợp lệ/không hợp lệ.

### 13.1. Property thay vì chỉ ví dụ

Một số property đáng kiểm chứng:

- Với mọi `quantity` trong [1, 1000], nếu các trường còn lại hợp lệ và key mới, INSERT không vi phạm quantity CHECK.
- Với mọi `quantity <= 0` hoặc `quantity > 1000` trong phạm vi INTEGER, INSERT bị từ chối bằng ràng buộc quantity.
- Hai lần INSERT có cùng `tenant_id + request_key` không thể cùng tạo hai hàng đã commit.
- Không có `order_items` đã commit tham chiếu `orders` ở tenant khác.
- Mọi hàng `status='PAID'` đã commit đều có `paid_at IS NOT NULL`.
- Sau rollback transaction thất bại, không còn những hàng chỉ được tạo trong transaction đó.
- Không có request thuộc Tenant A đọc được dữ liệu của Tenant B khi dùng runtime role/policy.

Cần **sinh đủ các trường hợp có ý nghĩa**. Generator hoàn toàn ngẫu nhiên có thể hầu như không chạm tới 0, 1, 1000 và 1001; nên dùng bias vào biên, giá trị đặc biệt và chuỗi dài.

### 13.2. Co giãn, thu nhỏ và tái hiện lỗi

Nếu dùng property-based library như jqwik, cần lưu **seed** khi test thất bại để chạy lại, và ưu tiên shrinking nhằm tìm input nhỏ nhất gây lỗi. Ví dụ một chuỗi Unicode dài bất thường có thể được thu nhỏ về tổ hợp ký tự gây sai lệch giữa Java length và PostgreSQL length.

Giữ test **deterministic trong khả năng có thể**: container DB version cố định, timezone rõ, cấu hình collation được biết, seed được ghi lại và database được dọn bằng fixture phù hợp.

## 14. Migration có thể khiến constraint đang được tin tưởng thay đổi

Một release mới có thể:

- Thêm cột NOT NULL khi hàng cũ còn NULL.
- Đổi `VARCHAR(64)` thành `VARCHAR(32)` khi dữ liệu hiện có dài hơn.
- Thêm UNIQUE trong khi dữ liệu đã trùng.
- Thêm FOREIGN KEY nhưng các hàng con có tham chiếu mồ côi.
- Thay CHECK cho `status` nhưng ứng dụng cũ vẫn ghi trạng thái cũ.
- Tách tenant từ khóa ID cũ khiến composite FK bị sai.

### 14.1. Test schema evolution bằng ma trận

| Pha schema | Code cũ | Code mới | Điều cần kiểm |
| --- | --- | --- | --- |
| Trước expand | Hoạt động | Chưa chắc hoạt động | Baseline bất biến |
| Sau expand | Vẫn hoạt động | Có thể dùng trường mới | Không phá INSERT/SELECT cũ |
| Trong backfill | Cùng chạy được theo protocol | Cùng chạy được | Không ghi đè cập nhật mới |
| Read/write cutover | Cần kiểm tra trạng thái tương thích | Hoạt động | Cả dữ liệu cũ lẫn mới đúng |
| Sau contract | Có thể không tương thích | Hoạt động | Không còn consumer hoặc rollback cũ |

Không chỉ test “migration script trả exit 0”. Sau migration, dùng **ứng dụng thật hoặc repository thật** chạy bộ test constraint trên schema đã được migration tạo ra. Nếu migration được chạy trong transaction test rồi rollback tự động, cần bảo đảm test đã thực sự quan sát trạng thái schema sau commit theo quy trình production.

### 14.2. Constraint chưa VALIDATE không phải toàn bộ bằng chứng

PostgreSQL hỗ trợ thêm một số FOREIGN KEY/CHECK constraint dưới dạng `NOT VALID` rồi `VALIDATE CONSTRAINT` sau đó. Constraint mới có thể được áp dụng cho thay đổi mới, nhưng hàng lịch sử có thể chưa được xác minh khi validation chưa chạy.

Test cần phân biệt:

1. Dữ liệu mới không hợp lệ bị từ chối.
2. Dữ liệu cũ đã qua kiểm tra/clean-up.
3. Bước validate được thực thi thành công.
4. Không có phiên bản ứng dụng cũ tiếp tục tạo dữ liệu vi phạm sau cutover.

Không phải mọi loại constraint đều hỗ trợ `NOT VALID` giống nhau; không suy rộng sang UNIQUE hay NOT NULL mà chưa kiểm tra engine/version.

## 15. Hiệu năng và an toàn khi chạy bộ test âm tính

Một test constraint có thể rất nhẹ, nhưng test concurrency và bộ dữ liệu lớn có thể tăng CPU, WAL, lock contention và ảnh hưởng pool. Trong CI:

- Dùng PostgreSQL có phiên bản/extension/collation đủ gần production.
- Cô lập database mỗi suite hoặc có chiến lược reset tránh test ảnh hưởng nhau.
- Kiểm soát thread, connection count và timeout; dừng khi test treo.
- Không làm fault injection hay gọi `TRUNCATE CASCADE` trên môi trường có dữ liệu cần giữ.
- Dùng fixture tổng hợp không chứa PII khách hàng.
- Kiểm tra rollback và dọn container/connection ngay cả khi assertion thất bại.
- Chạy test race nhiều lịch có chủ đích, không chỉ tăng vòng lặp mù.
- Lưu SQLSTATE, test case ID và SQL operation, nhưng lọc tham số nhạy cảm.
- Với những index hoặc constraint mới, đo cả thời gian ghi và tác động đến insert/update thay vì chỉ đo read query.

**Test pass không có nghĩa schema sẽ tự bảo vệ mọi đường bên ngoài phạm vi được mô phỏng.** Cần kết hợp review migration, authorization, quan sát production và kế hoạch phục hồi dữ liệu.

## 16. Bộ ca kiểm thử tối thiểu để đưa vào CI

Có thể dùng checklist sau như definition of done cho một bảng mới:

| Nhóm | Những ca bắt buộc |
| --- | --- |
| PK/UNIQUE | Thêm hợp lệ, trùng khóa, trùng request cùng tenant, cùng key khác tenant |
| FK | Cha tồn tại, cha thiếu, tham chiếu chéo tenant, thao tác xóa/sửa cha có con |
| NOT NULL/DEFAULT | Omitted, explicit NULL, chuỗi rỗng và giá trị mặc định |
| CHECK | Biên dưới/trên, vượt biên, tổ hợp nhiều cột, NULL/UNKNOWN |
| Type/precision | INTEGER overflow, NUMERIC overflow, fractional scale, invalid cast |
| String/Unicode | 63/64/65 ký tự, emoji, tiếng Việt, khoảng trắng và chuỗi dài |
| Date/time | UTC, offset, DST khi phù hợp, missing timestamp, ranh giới nghiệp vụ |
| Transaction | Lỗi trong transaction, rollback toàn bộ, savepoint và commit-deferred |
| Concurrency | Hai INSERT cùng unique key, optimistic version, deadlock/serialization nếu có |
| Multi-tenant | Query/JOIN/FK đúng scope, quyền và connection context được reset |
| Recovery | Timeout/commit chưa rõ, idempotency, retry không tạo hàng/side effect trùng |
| Migration | Schema trước/sau migration, dữ liệu cũ, rolling compatibility, validation |
| Security | SQL injection bị ngăn bằng bind, không rò dữ liệu qua lỗi/log |
| Observability | SQLSTATE phân loại đúng, không retry lỗi dữ liệu, cleanup tài nguyên |

Một test suite tốt còn kiểm tra **đường thành công**, không chỉ đường lỗi. Nếu tất cả INSERT đều thất bại nhưng bộ test chỉ đo rằng input sai bị chặn, schema có thể đang chặn luôn dữ liệu hợp lệ.

## 17. Những sai lầm thường gặp

**“Đã có `@NotNull` trong DTO nên DB không cần NOT NULL.”** Validation có thể bị bypass bởi batch, script, job hoặc phiên bản cũ.

**“Mock repository ném `DataIntegrityViolationException` đủ để test DB.”** Mock không chứng minh constraint và SQLSTATE thực.

**“CHECK amount >= 0 ngăn cả NULL.”** SQL CHECK cho UNKNOWN đi qua; phải có NOT NULL khi nghiệp vụ bắt buộc.

**“UNIQUE luôn coi hai NULL là trùng nhau.”** PostgreSQL mặc định cho phép nhiều NULL; có cú pháp khác khi cần NULLS NOT DISTINCT.

**“`NUMERIC(12,2)` sẽ tự từ chối mọi input có ba chữ số thập phân.”** PostgreSQL có thể làm tròn; nếu cần reject, validation phải diễn đạt rõ.

**“Chỉ cần test giá trị −100 và 999999.”** Off-by-one ở đúng biên 0/1/1000/1001 dễ bị bỏ sót.

**“`String.length()` luôn bằng số ký tự mà PostgreSQL giới hạn.”** UTF-16 code unit, Unicode code point và grapheme khác nhau.

**“Foreign key bất kỳ đã đủ cho multi-tenant.”** FK không mang tenant có thể tham chiếu sai phạm vi.

**“Test SQL lỗi là đủ; không cần đọc DB sau rollback.”** Có thể có thay đổi commit một phần ở những transaction khác hoặc side effect ngoài DB.

**“Lỗi chỉ xuất hiện ở INSERT.”** DEFERRABLE constraint có thể phát hiện tại COMMIT.

**“Sequence bị nhảy số là lỗi transaction.”** Sequence không rollback theo cách thông thường; khoảng trống là hợp lệ.

**“Hai request cùng check exists trước INSERT sẽ không trùng.”** Race yêu cầu UNIQUE/transaction hoặc cơ chế authority phù hợp.

**“SQLSTATE 23505 lúc nào cũng là HTTP 409.”** Trùng idempotency key cùng payload có thể trả kết quả cũ thay vì lỗi.

**“`@Transactional` test rollback sau mỗi method đã chứng minh commit thực.”** Test rollback tự động có thể bỏ qua lỗi deferred tại commit; cần test commit ở DB cô lập.

**“Testcontainers pass thì mọi database đều hành xử giống vậy.”** Cú pháp và semantics khác theo DBMS/version; bài này chủ động kiểm PostgreSQL.

## 18. Bài tập vận dụng

**Bài 1 — ma trận giá trị biên.** Với `quantity BETWEEN 1 AND 1000`, viết ca ở −1, 0, 1, 2, 999, 1000, 1001; phân loại hợp lệ/không hợp lệ, SQLSTATE, trạng thái DB cuối.

**Bài 2 — NULL và CHECK.** Tạo hai bảng, một có `CHECK (amount >= 0)`, bảng còn lại thêm `NOT NULL`. Thử NULL, −0.01, 0, 1.00. Giải thích vì sao câu trả lời khác nhau.

**Bài 3 — tiền và rounding.** Gửi `BigDecimal("1.235")` và `BigDecimal("1.234")` vào `NUMERIC(12,2)`; so sánh kết quả DB với validation Java dùng `RoundingMode.UNNECESSARY`. Viết hợp đồng API nếu muốn từ chối giá có độ chính xác quá hai chữ số.

**Bài 4 — ràng buộc tenant.** Hai tenant đều có `customer_id=10`. Hãy chứng minh một FK chỉ dùng ID không đảm bảo ownership và viết composite FK đúng. Tạo test âm tính khi Tenant B tham chiếu order chỉ có ở Tenant A.

**Bài 5 — deferred FK.** Tạo constraint `DEFERRABLE INITIALLY DEFERRED`. Chạy một transaction INSERT child trước parent rồi COMMIT; chạy transaction chỉ INSERT child rồi COMMIT. Lỗi xuất hiện ở bước nào và vì sao?

**Bài 6 — transaction rollback.** Trong một transaction, INSERT order hợp lệ rồi INSERT trùng request key. Sau khi bắt `23505`, thử SELECT trong cùng transaction rồi rollback. Xác nhận `25P02` và không có hàng mới commit.

**Bài 7 — concurrency.** Hai connection cùng INSERT `(tenant_id=42, request_key='same')`. Dùng latch và thời hạn chờ, kiểm tra chỉ một hàng được commit. Nếu tầng service bắt lỗi duplicate để trả kết quả cũ, cần kiểm tra điều kiện payload gì?

**Bài 8 — Unicode.** Tạo các chuỗi 64/65 ASCII, chữ tiếng Việt tổ hợp và emoji. So sánh Java `String.length()`, số code point và PostgreSQL `char_length()`; giải thích cách chọn giới hạn phù hợp UI/API/DB.

**Bài 9 — schema migration.** Một migration cần siết status từ ba giá trị xuống hai giá trị khi code cũ vẫn ghi giá trị thứ ba. Đề xuất expand–contract và bộ test tương thích V1/V2 trước, trong và sau rollout.

**Bài 10 — thiết kế lỗi API.** Với các lỗi `23502`, `23503`, `23505`, `23514`, `40001` và timeout khi COMMIT, hãy lập bảng cách phân loại, retry, rollback, idempotency và HTTP response mà không làm lộ cấu trúc DB.

## Ghi nhớ

**Kiểm thử ràng buộc phải chứng minh database thực sự bảo vệ bất biến, không chỉ chứng minh Java đã gọi đúng nhánh.** Dùng dữ liệu hợp lệ và không hợp lệ sát biên, kiểm tra NULL/UNKNOWN, khóa ghép theo tenant, phạm vi NUMERIC/VARCHAR, quy tắc liên cột và SQLSTATE thực từ PostgreSQL. Sau lỗi, phải xác minh transaction rollback/commit và trạng thái dữ liệu đã lưu.

Đối với ứng dụng Java, JUnit 5/Testcontainers/JDBC giúp kiểm tra lược đồ thật trong môi trường cô lập; concurrency test phát hiện race mà test tuần tự bỏ sót; migration test bảo đảm constraint mới không phá phiên bản ứng dụng cũ. Một bộ test persistence đáng tin phải kết hợp **tính đúng đắn, an toàn dữ liệu, thông tin lỗi và khả năng phục hồi**, thay vì chỉ khẳng định exception được ném ra.
