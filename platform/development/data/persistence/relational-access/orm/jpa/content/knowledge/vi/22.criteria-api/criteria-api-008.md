# Nhóm, lọc nhóm và sắp xếp kết quả

## 1. Từ danh sách entity đến báo cáo tổng hợp

Trong Jakarta Persistence (JPA), **Criteria API** cho phép xây dựng truy vấn bằng các đối tượng Java thay vì ghép chuỗi JPQL. Khi làm báo cáo, ba thao tác quan trọng là:

- **Nhóm (`GROUP BY`):** gom nhiều hàng có chung giá trị khóa nhóm thành một nhóm logic.
- **Lọc nhóm (`HAVING`):** giữ hoặc loại **cả nhóm** sau khi tính các biểu thức tổng hợp như `COUNT`, `SUM` hoặc `AVG`.
- **Sắp xếp (`ORDER BY`):** xác định thứ tự kết quả, bao gồm thứ tự theo khóa nhóm và theo giá trị tổng hợp.

Ví dụ, một hệ thống bán hàng muốn biết:

> Với từng vùng kinh doanh, có bao nhiêu đơn hàng đã thanh toán, tổng số tiền là bao nhiêu; chỉ hiển thị vùng có từ hai đơn đã thanh toán trở lên, xếp theo doanh thu giảm dần.

JPQL tương ứng có thể là:

```jpql
SELECT c.regionCode, COUNT(o.id), SUM(o.totalAmount)
FROM PurchaseOrder o
JOIN o.customer c
WHERE o.status = :paid
GROUP BY c.regionCode
HAVING COUNT(o.id) >= :minimumCount
ORDER BY SUM(o.totalAmount) DESC, c.regionCode ASC
```

Trong Criteria API, cùng ý định được xây bằng các phương thức:

```java
query.groupBy(region);
query.having(cb.ge(orderCount, minimumCount));
query.orderBy(cb.desc(revenue), cb.asc(region));
```

Điểm quan trọng là **`WHERE` lọc hàng trước khi nhóm**, còn **`HAVING` lọc nhóm sau khi tính aggregate**. `ORDER BY` chỉ quyết định thứ tự những hàng kết quả đã còn lại.

Bài học này xây một mô hình dữ liệu, thực hiện truy vấn bằng Criteria API từ cơ bản đến động, giải thích những bẫy về join, nhóm rỗng, dữ liệu `NULL`, kiểu kết quả, phân trang và hiệu năng.

## 2. Mô hình entity và dữ liệu giả định

### 2.1. Hai entity làm nền

Giả sử mỗi `PurchaseOrder` thuộc một `Customer`. Khách hàng có mã vùng `regionCode`, đơn hàng có trạng thái, thời điểm và tổng tiền.

**`OrderStatus.java`**

```java
package com.example.shop.domain;

public enum OrderStatus {
    NEW,
    PAID,
    CANCELLED
}
```

**`Customer.java`**

```java
package com.example.shop.domain;

import jakarta.persistence.*;
import java.util.ArrayList;
import java.util.List;

@Entity
@Table(name = "customers")
public class Customer {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "full_name", nullable = false, length = 120)
    private String fullName;

    @Column(name = "region_code", nullable = false, length = 24)
    private String regionCode;

    @OneToMany(mappedBy = "customer")
    private List<PurchaseOrder> orders = new ArrayList<>();

    protected Customer() {}

    public Long getId() {
        return id;
    }

    public String getFullName() {
        return fullName;
    }

    public String getRegionCode() {
        return regionCode;
    }
}
```

**`PurchaseOrder.java`**

```java
package com.example.shop.domain;

import jakarta.persistence.*;
import java.math.BigDecimal;
import java.time.Instant;

@Entity
@Table(name = "purchase_orders")
public class PurchaseOrder {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "customer_id", nullable = false)
    private Customer customer;

    @Enumerated(EnumType.STRING)
    @Column(name = "status", nullable = false, length = 24)
    private OrderStatus status;

    @Column(name = "total_amount", nullable = false,
            precision = 14, scale = 2)
    private BigDecimal totalAmount;

    @Column(name = "placed_at", nullable = false)
    private Instant placedAt;

    protected PurchaseOrder() {}

    public Long getId() {
        return id;
    }

    public OrderStatus getStatus() {
        return status;
    }

    public BigDecimal getTotalAmount() {
        return totalAmount;
    }
}
```

### 2.2. Lược đồ SQL minh họa

Ví dụ PostgreSQL:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    full_name VARCHAR(120) NOT NULL,
    region_code VARCHAR(24) NOT NULL
);

CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL REFERENCES customers(id),
    status VARCHAR(24) NOT NULL,
    total_amount NUMERIC(14, 2) NOT NULL,
    placed_at TIMESTAMP WITH TIME ZONE NOT NULL
);

CREATE INDEX ix_orders_customer_id
    ON purchase_orders(customer_id);
```

Trong Criteria API, dùng các **thuộc tính Java** như `totalAmount` và `regionCode`, không phải các tên cột vật lý `total_amount` hay `region_code`.

### 2.3. Dữ liệu mẫu

Giả sử dữ liệu Customers:

| ID | Họ tên | Vùng |
|---:|---|---|
| 1 | An | HCM |
| 2 | Bình | HCM |
| 3 | Chi | HN |
| 4 | Dũng | DN |
| 5 | Em | HN |

Các PurchaseOrder:

| Order ID | Customer | Status | Total amount |
|---:|---|---|---:|
| 101 | An | PAID | 400000 |
| 102 | An | CANCELLED | 100000 |
| 103 | Bình | PAID | 800000 |
| 104 | Bình | PAID | 900000 |
| 105 | Dũng | NEW | 300000 |

Chi chưa có đơn hàng. Dữ liệu được chọn để giúp kiểm tra bằng suy luận:

Những số liệu này dùng để giải thích truy vấn, không phải kết quả đọc từ cơ sở dữ liệu thực tế.

## 3. Các lớp Criteria API cần biết

Các kiểu thường gặp nằm trong package `jakarta.persistence.criteria`:

| Kiểu | Vai trò |
|---|---|
| `CriteriaBuilder` | Tạo biểu thức, aggregate, predicate, sắp xếp |
| `CriteriaQuery<T>` | Đối tượng mô tả truy vấn với kiểu kết quả `T` |
| `Root<T>` | Entity nguồn của mệnh đề `FROM` |
| `Join<X,Y>` | Association join từ entity/nguồn `X` sang `Y` |
| `Path<T>` | Đường dẫn đến thuộc tính Java có kiểu `T` |
| `Expression<T>` | Biểu thức có thể được tính trong truy vấn |
| `Predicate` | Điều kiện boolean dùng trong `WHERE`/`HAVING` |
| `Order` | Cấu trúc sắp xếp do `cb.asc` hoặc `cb.desc` tạo |
| `Tuple` | Một hàng kết quả chứa nhiều cột được chọn |
| `TypedQuery<T>` | Truy vấn đã được tạo từ `CriteriaQuery<T>` để bind tham số, phân trang và lấy dữ liệu |

Đoạn khởi đầu:

```java
import jakarta.persistence.EntityManager;
import jakarta.persistence.Tuple;
import jakarta.persistence.criteria.*;

CriteriaBuilder cb = em.getCriteriaBuilder();

CriteriaQuery<Tuple> cq = cb.createTupleQuery();

Root<PurchaseOrder> order = cq.from(PurchaseOrder.class);
Join<PurchaseOrder, Customer> customer = order.join("customer");
```

Ở đây:

- `em` là `EntityManager` còn hoạt động.
- `cq` sẽ trả các hàng `Tuple` thay vì toàn bộ entity.
- `order` trỏ tới `PurchaseOrder` trong `FROM`.
- `customer` đi qua association Java `PurchaseOrder.customer`.

Một cách viết Criteria API có thể hơi dài hơn JPQL dạng chuỗi, nhưng đặc biệt hữu ích khi cần **tạo điều kiện động** hoặc **tái sử dụng các Expression** trong `SELECT`, `HAVING` và `ORDER BY`.

## 4. `groupBy()`: tạo nhóm theo một thuộc tính

### 4.1. Ví dụ: đếm số đơn của từng vùng

Với dữ liệu trên, nhóm mọi Order theo mã vùng của Customer:

```java
CriteriaBuilder cb = em.getCriteriaBuilder();
CriteriaQuery<Tuple> cq = cb.createTupleQuery();

Root<PurchaseOrder> o = cq.from(PurchaseOrder.class);
Join<PurchaseOrder, Customer> c = o.join("customer");

Path<String> region = c.get("regionCode");
Expression<Long> orderCount = cb.count(o.get("id"));

cq.multiselect(
        region.alias("region"),
        orderCount.alias("orderCount")
    )
    .groupBy(region)
    .orderBy(cb.asc(region));

List<Tuple> rows = em.createQuery(cq).getResultList();
```

Giải thích từng bước:

1. `cq.from(PurchaseOrder.class)` quyết định nguồn hàng được tính là **Order**.
2. `o.join("customer")` lấy vùng của Customer tương ứng.
3. `cb.count(o.get("id"))` tính số Order trong từng nhóm.
4. `groupBy(region)` gom các hàng có cùng `regionCode`.
5. `multiselect` trả một hàng cho mỗi vùng với mã vùng và số đơn.
6. `orderBy(cb.asc(region))` sắp theo mã vùng tăng dần.

Kết quả logic với dữ liệu mẫu:

| region | orderCount |
|---|---:|
| DN | 1 |
| HCM | 4 |
| HN | 1 |

### 4.2. `groupBy` và SELECT có quan hệ chặt chẽ

Khi một truy vấn có aggregate như `COUNT` và có `GROUP BY`, các biểu thức không được tổng hợp trong `SELECT` phải tương thích với các khóa nhóm theo quy tắc của JPQL và database.

Ví dụ hợp lý:

```java
cq.multiselect(
    c.get("regionCode"),
    cb.count(o.get("id"))
);
cq.groupBy(c.get("regionCode"));
```

Ví dụ không hợp lý về mặt ý định và có thể bị provider/database từ chối:

```java
cq.multiselect(
    c.get("regionCode"),
    c.get("fullName"),        // Không được nhóm hoặc aggregate.
    cb.count(o.get("id"))
);
cq.groupBy(c.get("regionCode"));
```

Trong một vùng có thể có nhiều Customer mang `fullName` khác nhau. Query không xác định nên chọn tên ai làm đại diện. Không dựa vào việc một database cụ thể chấp nhận một phép GROUP BY nới lỏng để coi truy vấn là portable.

### 4.3. `groupBy` không phải `DISTINCT`

Hai cách:

```java
cq.select(region).distinct(true);
```

và:

```java
cq.select(region).groupBy(region);
```

có thể cùng trả các vùng duy nhất trong một số tình huống, nhưng khác mục đích:

- `DISTINCT` loại các dòng kết quả bị lặp.
- `GROUP BY` tạo nhóm để tính aggregate và lọc theo điều kiện nhóm.
- Khi cần `COUNT` hoặc `SUM` theo vùng, nên dùng `GROUP BY`.
- Không thêm `distinct(true)` vào mọi grouped query theo thói quen; phải xem nó có thêm ý nghĩa gì với phần SELECT hay không.

## 5. Nhóm theo nhiều thuộc tính

### 5.1. Theo vùng và trạng thái đơn

Giả sử cần số Order cho từng cặp `(regionCode, status)`:

```java
CriteriaBuilder cb = em.getCriteriaBuilder();
CriteriaQuery<Tuple> cq = cb.createTupleQuery();

Root<PurchaseOrder> o = cq.from(PurchaseOrder.class);
Join<PurchaseOrder, Customer> c = o.join("customer");

Path<String> region = c.get("regionCode");
Path<OrderStatus> status = o.get("status");
Expression<Long> count = cb.count(o.get("id"));

cq.multiselect(
        region.alias("region"),
        status.alias("status"),
        count.alias("count")
    )
    .groupBy(region, status)
    .orderBy(
        cb.asc(region),
        cb.asc(status)
    );

List<Tuple> rows = em.createQuery(cq).getResultList();
```

Lúc này **một nhóm** là một cặp giá trị: cùng vùng nhưng khác trạng thái sẽ là hai nhóm khác nhau.

Ví dụ kết quả logic:

| region | status | count |
|---|---|---:|
| DN | NEW | 1 |
| HCM | CANCELLED | 1 |
| HCM | PAID | 3 |
| HN | PAID | 1 |

Không có nhóm `HN/CANCELLED` vì không có hàng Order nào thỏa cặp này. `GROUP BY` không tự tạo các tổ hợp thiếu; muốn hiển thị cả tổ hợp có số 0, cần mô hình dữ liệu/truy vấn ngoài để sinh đầy đủ các cặp hoặc ghép dữ liệu khi trình bày.

### 5.2. Các overload của `groupBy`

Criteria API cho phép:

```java
cq.groupBy(region);
cq.groupBy(region, status);
cq.groupBy(List.of(region, status));
```

Đây là các phương án **thay thế**, không phải ba lệnh cần gọi lần lượt. Lời gọi sau thiết lập danh sách nhóm cho truy vấn theo API tương ứng.

Nếu muốn nhóm theo nhiều cột, đưa tất cả biểu thức khóa nhóm vào **cùng một lệnh**, tránh vô tình ghi đè hoặc thay đổi cấu hình nhóm từ bước trước.

### 5.3. Nhóm theo tên hiển thị có thể gây gộp nhầm

Nếu nhóm Customer chỉ bằng `fullName`, hai khách hàng khác ID nhưng cùng tên có thể bị gộp vào một nhóm. Khi mục tiêu là “mỗi Customer”, nên nhóm theo **khóa định danh** và các thuộc tính không aggregate đang chọn:

```java
cq.groupBy(c.get("id"), c.get("fullName"));
```

Nếu mục tiêu là “mỗi tên khách”, nhóm chỉ theo tên có thể đúng, nhưng đó là một báo cáo khác. **Khóa nhóm phải phản ánh câu hỏi nghiệp vụ**.

## 6. Các hàm tổng hợp trong `CriteriaBuilder`

Các aggregate quyết định giá trị tính cho từng nhóm.

### 6.1. Những phương thức thường dùng

| Hàm Criteria | Ý nghĩa | Kiểu kết quả quan trọng |
|---|---|---|
| `cb.count(expression)` | Đếm biểu thức không null | `Expression<Long>` |
| `cb.countDistinct(expression)` | Đếm số giá trị khác nhau, không null | `Expression<Long>` |
| `cb.sum(numberExpression)` | Tính tổng | Phụ thuộc kiểu number expression |
| `cb.sumAsLong(integerExpression)` | Tổng các số nguyên kiểu Integer dưới dạng Long | `Expression<Long>` |
| `cb.sumAsDouble(floatExpression)` | Tổng các số Float dưới dạng Double | `Expression<Double>` |
| `cb.avg(numberExpression)` | Trung bình số học | `Expression<Double>` |
| `cb.min(numberExpression)` | Giá trị số nhỏ nhất | Phù hợp kiểu numeric expression |
| `cb.max(numberExpression)` | Giá trị số lớn nhất | Phù hợp kiểu numeric expression |
| `cb.greatest(expression)` | Giá trị lớn nhất của kiểu có thể so sánh | Ví dụ Date/String theo mapping |
| `cb.least(expression)` | Giá trị nhỏ nhất của kiểu có thể so sánh | Ví dụ Date/String theo mapping |

Với `BigDecimal totalAmount`:

```java
Path<BigDecimal> amount = o.get("totalAmount");

Expression<BigDecimal> totalRevenue = cb.sum(amount);
Expression<Double> averageAmount = cb.avg(amount);

Expression<BigDecimal> smallest = cb.min(amount);
Expression<BigDecimal> largest = cb.max(amount);
```

Ví dụ này dùng `java.math.BigDecimal`. `cb.avg` trả `Double` theo API, không giữ nguyên `BigDecimal`. Nếu ứng dụng cần chính xác thập phân tuyệt đối cho báo cáo tài chính, hãy xác định chính sách chuyển đổi/làm tròn hoặc cân nhắc tính từ `SUM` và `COUNT` bằng kiểu số phù hợp; không mặc định `Double` là biểu diễn tiền tệ chính xác.

### 6.2. `COUNT` và `COUNT DISTINCT`

Giả sử một Customer có ba Order và một truy vấn join thêm bảng OrderLine, mỗi Order có nhiều Line. Khi đó:

```java
cb.count(o.get("id"))
```

đếm số **dòng của kết quả join** có ID Order không null, không mặc định là số Order duy nhất.

Nếu mục tiêu là số Order riêng:

```java
cb.countDistinct(o.get("id"))
```

đếm mỗi ID Order không null một lần trong nhóm.

Đây là khác biệt quan trọng ở báo cáo có nhiều association `OneToMany` hoặc `ManyToMany`.

### 6.3. `SUM` và giá trị null

`SUM` bỏ qua các giá trị null trong tập nguồn; nếu tập không có giá trị số non-null, kết quả có thể là null. `COUNT` thì trả 0 trong trường hợp không có phần tử được đếm.

Vì vậy, với nhóm Customer không có Order khi dùng `LEFT JOIN`:

- `COUNT(o.id)` là **0**.
- `SUM(o.totalAmount)` có thể là **null**.
- `AVG(o.totalAmount)` có thể là **null**.

Muốn hiển thị số tiền 0, có thể dùng `COALESCE` như phần tiếp theo.

### 6.4. Tính tổng tiền theo vùng

```java
CriteriaBuilder cb = em.getCriteriaBuilder();
CriteriaQuery<Tuple> cq = cb.createTupleQuery();

Root<PurchaseOrder> o = cq.from(PurchaseOrder.class);
Join<PurchaseOrder, Customer> c = o.join("customer");

Path<String> region = c.get("regionCode");
Path<BigDecimal> amount = o.get("totalAmount");

Expression<Long> count = cb.count(o.get("id"));
Expression<BigDecimal> revenue = cb.sum(amount);

cq.multiselect(
        region.alias("region"),
        count.alias("orders"),
        revenue.alias("revenue")
    )
    .groupBy(region)
    .orderBy(cb.asc(region));

List<Tuple> results = em.createQuery(cq).getResultList();
```

Theo dữ liệu mẫu, tổng tiền **mọi Order**, kể cả CANCELLED và NEW, là:

| Region | Orders | Revenue |
|---|---:|---:|
| DN | 1 | 300000 |
| HCM | 4 | 2200000 |
| HN | 1 | 200000 |

Nếu doanh thu chỉ được ghi nhận từ Order PAID, **phải lọc trạng thái trước khi tính SUM**, không dùng tất cả Order như trên.

## 7. `WHERE` và `HAVING`: hai tầng lọc khác nhau

### 7.1. WHERE lọc hàng trước khi chia nhóm

Ví dụ đếm số đơn PAID trong từng vùng:

```java
cq.where(cb.equal(o.get("status"), OrderStatus.PAID));

cq.groupBy(region);
```

Hình dung:

```text
Tất cả Order
      |
      v
WHERE status = PAID
      |
      v
Chỉ các Order PAID
      |
      v
GROUP BY region
      |
      v
COUNT / SUM từng vùng
```

Kết quả trên dữ liệu mẫu:

| Vùng | Order PAID | Tổng tiền PAID |
|---|---:|---:|
| HCM | 3 | 2100000 |
| HN | 1 | 200000 |

Vùng DN không xuất hiện vì nguồn `FROM PurchaseOrder` không có Order PAID nào tại DN.

### 7.2. HAVING lọc nhóm sau aggregate

Giả sử chỉ muốn vùng có **ít nhất hai Order PAID**:

```java
Expression<Long> paidCount = cb.count(o.get("id"));

cq.where(cb.equal(o.get("status"), OrderStatus.PAID));
cq.groupBy(region);
cq.having(cb.ge(paidCount, 2L));
```

Chuỗi logic:

```text
PurchaseOrder rows
      |
WHERE status = PAID
      |
GROUP BY region
      |
COUNT mỗi region
      |
HAVING COUNT >= 2
      |
Kết quả: HCM
```

`cb.ge(paidCount, 2L)` là phép so sánh kiểu số: `paidCount` có kiểu `Expression<Long>` và cận 2L là `long`.

### 7.3. Đừng đặt aggregate vào WHERE

Không viết theo ý định:

```java
// Không đúng vai trò của WHERE khi dùng aggregate:
cq.where(cb.ge(cb.count(o.get("id")), 2L));
```

Trong ngữ nghĩa SQL/JPQL, `WHERE` được đánh giá trước bước grouping/aggregate; biểu thức `COUNT` của nhóm thuộc `HAVING`.

Cách đúng:

```java
cq.groupBy(region);
cq.having(cb.ge(cb.count(o.get("id")), 2L));
```

### 7.4. Không nhầm “đơn giá lớn” với “tổng doanh thu nhóm lớn”

Hai yêu cầu khác nhau:

- **Chỉ tính các đơn có số tiền ít nhất 500.000:** dùng `WHERE o.totalAmount >= 500000` trước nhóm.
- **Chỉ lấy những vùng có tổng tiền của mọi đơn ít nhất 500.000:** dùng `HAVING SUM(o.totalAmount) >= 500000` sau nhóm.

Ví dụ:

```java
// Lọc hàng trước:
cq.where(cb.ge(
    o.<BigDecimal>get("totalAmount"),
    new BigDecimal("500000.00")
));

// Lọc nhóm sau:
cq.having(cb.ge(
    cb.sum(o.<BigDecimal>get("totalAmount")),
    new BigDecimal("500000.00")
));
```

Đây là **hai cách đặt predicate khác nhau**, tùy mục tiêu. Không phải hai bước luôn phải thực hiện đồng thời.

## 8. Tạo truy vấn hoàn chỉnh: WHERE + GROUP BY + HAVING + ORDER BY

Ví dụ nhận hai tham số:

- `requiredStatus`: trạng thái cần thống kê.
- `minimumCount`: số Order tối thiểu của nhóm.

```java
import jakarta.persistence.EntityManager;
import jakarta.persistence.Tuple;
import jakarta.persistence.criteria.*;

import java.math.BigDecimal;
import java.util.List;

public List<Tuple> reportPaidRegions(
        EntityManager em,
        OrderStatus requiredStatus,
        long minimumCount) {

    CriteriaBuilder cb = em.getCriteriaBuilder();
    CriteriaQuery<Tuple> cq = cb.createTupleQuery();

    Root<PurchaseOrder> o =
        cq.from(PurchaseOrder.class);

    Join<PurchaseOrder, Customer> c =
        o.join("customer");

    Path<String> region = c.get("regionCode");

    Expression<Long> count =
        cb.count(o.get("id"));

    Expression<BigDecimal> revenue =
        cb.sum(o.<BigDecimal>get("totalAmount"));

    Predicate statusFilter =
        cb.equal(o.get("status"), requiredStatus);

    Predicate enoughOrders =
        cb.ge(count, minimumCount);

    cq.multiselect(
            region.alias("region"),
            count.alias("orderCount"),
            revenue.alias("revenue")
        )
        .where(statusFilter)
        .groupBy(region)
        .having(enoughOrders)
        .orderBy(
            cb.desc(revenue),
            cb.asc(region)
        );

    return em.createQuery(cq).getResultList();
}
```

Gọi:

```java
List<Tuple> rows = reportPaidRegions(
    em, OrderStatus.PAID, 2L
);
```

Trên dữ liệu mẫu chỉ vùng **HCM** có ít nhất hai Order PAID. Kết quả tương đương một JPQL:

```jpql
SELECT c.regionCode, COUNT(o.id), SUM(o.totalAmount)
FROM PurchaseOrder o
JOIN o.customer c
WHERE o.status = :requiredStatus
GROUP BY c.regionCode
HAVING COUNT(o.id) >= :minimumCount
ORDER BY SUM(o.totalAmount) DESC, c.regionCode ASC
```

Ví dụ dùng giá trị enum trực tiếp trong Criteria predicate. Nếu truy vấn cần tái sử dụng với nhiều giá trị, có thể dùng `ParameterExpression<OrderStatus>` và bind tham số qua `TypedQuery`; sẽ được trình bày sau.

## 9. `having()` với nhiều điều kiện

### 9.1. Kết hợp điều kiện bằng `cb.and`

Yêu cầu: chỉ lấy vùng vừa có **ít nhất hai Order PAID**, vừa đạt **doanh thu từ 1 triệu trở lên**:

```java
Expression<Long> count = cb.count(o.get("id"));

Expression<BigDecimal> sum =
    cb.sum(o.<BigDecimal>get("totalAmount"));

Predicate countEnough = cb.ge(count, 2L);

Predicate revenueEnough = cb.ge(
    sum, new BigDecimal("1000000.00")
);

cq.having(cb.and(countEnough, revenueEnough));
```

Hai điều kiện nằm trong **HAVING** vì cùng nói về kết quả aggregate của từng nhóm.

### 9.2. Nhiều điều kiện truyền trực tiếp

Có thể viết:

```java
cq.having(countEnough, revenueEnough);
```

Theo API, các hạn chế truyền ở varargs sẽ được kết hợp theo phép **AND**. Đây là phương án thay thế cho `cb.and(...)`.

Khi cần `OR`:

```java
cq.having(cb.or(countEnough, revenueEnough));
```

Điều này chọn nhóm đáp ứng ít nhất một tiêu chí. Dùng ngoặc thông qua `cb.and`/`cb.or` sẽ làm logic rõ hơn khi các điều kiện lồng nhau.

### 9.3. Phân biệt “vùng nhiều đơn” và “vùng nhiều khách”

`cb.count(o.get("id"))` đếm số Order. Nó **không** đếm Customer duy nhất, vì một Customer có thể đặt nhiều Order.

Nếu muốn vùng có ít nhất hai Customer khác nhau có Order PAID:

```java
Expression<Long> distinctCustomers =
    cb.countDistinct(c.get("id"));

cq.having(cb.ge(distinctCustomers, 2L));
```

Trên dữ liệu mẫu vùng HCM có An và Bình, nên đạt hai Customer. Nếu chỉ một khách đặt mười đơn, `COUNT(Order) = 10` nhưng `COUNT(DISTINCT Customer) = 1`. Hãy xác định đại lượng trước khi chọn aggregate.

## 10. `orderBy()`: sắp xếp khóa nhóm và aggregate

### 10.1. Theo khóa nhóm tăng dần

```java
cq.orderBy(cb.asc(region));
```

Thứ tự text phụ thuộc collation/cách sắp xếp của database, nhưng `ORDER BY` làm ý định rõ ràng hơn để trả dữ liệu ổn định.

### 10.2. Theo aggregate giảm dần

```java
Expression<BigDecimal> revenue =
    cb.sum(o.<BigDecimal>get("totalAmount"));

cq.orderBy(cb.desc(revenue));
```

Đây là sắp theo tổng doanh thu của nhóm, **không** sắp theo đơn giá của một Order tùy ý.

### 10.3. Nhiều khóa sắp xếp

```java
cq.orderBy(
    cb.desc(revenue),
    cb.desc(orderCount),
    cb.asc(region)
);
```

Ý nghĩa:

1. Vùng doanh thu cao hơn xuất hiện trước.
2. Nếu doanh thu bằng nhau, vùng có nhiều Order hơn xuất hiện trước.
3. Nếu cả hai bằng nhau, sắp theo mã vùng tăng dần.

Một tie-breaker rõ ràng giúp kết quả **dễ dự đoán khi phân trang**. Nếu các khóa nhóm không duy nhất trong những cột sắp xếp đã chọn, thêm khóa nhóm để tạo thứ tự tổng ổn định.

### 10.4. Sắp xếp theo trường không nhóm và không aggregate

Không nên viết:

```java
cq.groupBy(region);
cq.orderBy(cb.asc(o.get("placedAt")));
```

nếu đang trả **một hàng cho mỗi vùng**. Một vùng có nhiều Order với `placedAt` khác nhau; không có một giá trị đơn lẻ đại diện để sắp vùng, và query có thể không hợp lệ theo các quy tắc nhóm của JPQL/database.

Nếu muốn sắp vùng theo **thời điểm có Order mới nhất**, hãy tổng hợp thời gian:

```java
Expression<Instant> latestPlacedAt =
    cb.greatest(o.<Instant>get("placedAt"));

cq.orderBy(cb.desc(latestPlacedAt));
```

`Instant` là kiểu so sánh được trong mô hình Java; khả năng ánh xạ/aggregate trên timestamp phải được provider/database hỗ trợ. Với kiểu số tiền, dùng `cb.max`/`cb.min`; với giá trị so sánh khác kiểu số, `greatest`/`least` thể hiện mục đích tương ứng.

### 10.5. Varargs và List

```java
cq.orderBy(cb.desc(revenue), cb.asc(region));
```

hoặc:

```java
List<jakarta.persistence.criteria.Order> sorts = List.of(
    cb.desc(revenue),
    cb.asc(region)
);

cq.orderBy(sorts);
```

Hai cách này là lựa chọn thay thế. Lệnh `orderBy(...)` dùng để thiết lập thứ tự của truy vấn; nếu code động gọi lại sau đó, phải chú ý danh sách sort cuối cùng được áp dụng.

## 11. Đọc kết quả bằng `Tuple` và alias

### 11.1. Lấy giá trị từ Tuple

Khi dùng `CriteriaQuery<Tuple>` và `multiselect`:

```java
cq.multiselect(
    region.alias("region"),
    count.alias("orderCount"),
    revenue.alias("revenue")
);
```

có thể đọc:

```java
for (Tuple row : rows) {
    String regionCode = row.get("region", String.class);
    Long numberOfOrders = row.get("orderCount", Long.class);
    BigDecimal total = row.get("revenue", BigDecimal.class);

    System.out.printf(
        "Region=%s, orders=%d, revenue=%s%n",
        regionCode,
        numberOfOrders,
        total
    );
}
```

Các alias `"region"`, `"orderCount"` và `"revenue"` chỉ là **nhãn kết quả truy vấn**, không phải cột mới trong entity.

### 11.2. Vì sao nên đặt alias?

`Tuple` cũng có thể lấy theo vị trí:

```java
String code = row.get(0, String.class);
Long count = row.get(1, Long.class);
```

Nhưng khi thứ tự `multiselect` thay đổi, code dùng index dễ đọc sai cột mà vẫn compile. Alias giúp dễ bảo trì, nhất là query động có nhiều aggregate.

Cần tránh dùng một alias trùng cho nhiều selection trong cùng query. Mỗi phần dữ liệu dùng để đọc theo tên nên có một alias riêng, có ý nghĩa.

### 11.3. Kiểu số không nên ép đoán

`COUNT` trả `Long`, không phải `Integer`:

```java
Long count = row.get("orderCount", Long.class);
```

`AVG` trả `Double`, không phải `BigDecimal`:

```java
Double avg = row.get("averageAmount", Double.class);
```

`SUM` với `BigDecimal` thường trả `BigDecimal` theo mapping tương ứng:

```java
BigDecimal revenue = row.get("revenue", BigDecimal.class);
```

Không giả định mọi aggregate trả cùng kiểu Java với cột nguồn. Các aggregate khác nhau có quy tắc kiểu kết quả riêng theo chuẩn JPA.

## 12. DTO projection: trả kiểu báo cáo riêng

### 12.1. Vì sao DTO thích hợp cho GROUP BY?

Một hàng kết quả nhóm không phải một `Customer` hay `PurchaseOrder` đầy đủ. Nó có thể chỉ gồm mã vùng, số đơn và doanh thu. Dùng **DTO/record** giúp API không phải trả entity managed không đúng mục đích.

Ví dụ Java record:

```java
package com.example.shop.report;

import java.math.BigDecimal;

public record RegionReport(
    String region,
    Long orderCount,
    BigDecimal revenue
) {}
```

### 12.2. CriteriaQuery cho DTO

```java
CriteriaBuilder cb = em.getCriteriaBuilder();

CriteriaQuery<RegionReport> cq =
    cb.createQuery(RegionReport.class);

Root<PurchaseOrder> o =
    cq.from(PurchaseOrder.class);

Join<PurchaseOrder, Customer> c =
    o.join("customer");

Path<String> region = c.get("regionCode");
Expression<Long> count = cb.count(o.get("id"));
Expression<BigDecimal> revenue =
    cb.sum(o.<BigDecimal>get("totalAmount"));

cq.select(cb.construct(
        RegionReport.class,
        region,
        count,
        revenue
    ))
    .groupBy(region)
    .orderBy(cb.desc(revenue), cb.asc(region));

List<RegionReport> reports =
    em.createQuery(cq).getResultList();
```

`cb.construct(RegionReport.class, ...)` tạo kết quả qua constructor phù hợp với **thứ tự và kiểu** selection:

1. `String`
2. `Long`
3. `BigDecimal`

Java record có canonical constructor tương ứng. Đây là DTO read model, **không trở thành entity managed** sau truy vấn.

### 12.3. Sai thứ tự constructor

Nếu định nghĩa:

```java
public record RegionReport(
    Long orderCount,
    String region,
    BigDecimal revenue
) {}
```

nhưng giữ `cb.construct(RegionReport.class, region, count, revenue)`, thứ tự kiểu không khớp. Provider có thể báo lỗi lúc tạo hoặc thực thi query.

Khi thay đổi cấu trúc DTO, hãy đồng bộ các expression trong `construct`. Không nên để DTO tự suy ra tên property từ alias; `cb.construct` chủ yếu dựa trên thứ tự và kiểu đối số constructor.

## 13. `LEFT JOIN` và nhóm có số lượng bằng 0

### 13.1. Vì sao bắt đầu từ Order sẽ thiếu khách chưa đặt hàng?

Nếu nguồn là:

```java
Root<PurchaseOrder> o = cq.from(PurchaseOrder.class);
```

thì Customer **Chi** không có Order sẽ không xuất hiện, dù thêm `GROUP BY o.customer` như thế nào.

Nếu yêu cầu là **đếm Order của mọi Customer, kể cả khách có 0 Order**, cần bắt đầu từ Customer và dùng `LEFT JOIN` tới collection `orders`.

### 13.2. Đếm số Order theo từng Customer, gồm số 0

```java
CriteriaBuilder cb = em.getCriteriaBuilder();
CriteriaQuery<Tuple> cq = cb.createTupleQuery();

Root<Customer> c = cq.from(Customer.class);

Join<Customer, PurchaseOrder> o =
    c.join("orders", JoinType.LEFT);

Path<Long> id = c.get("id");
Path<String> name = c.get("fullName");

Expression<Long> count = cb.count(o.get("id"));

cq.multiselect(
        id.alias("customerId"),
        name.alias("customerName"),
        count.alias("orderCount")
    )
    .groupBy(id, name)
    .orderBy(cb.asc(id));

List<Tuple> rows = em.createQuery(cq).getResultList();
```

Ở đây `o` là join tới `PurchaseOrder`. Với Customer không có Order, `LEFT JOIN` tạo hàng có phía Order là null. `COUNT(o.id)` **không đếm null**, nên trả 0.

Với dữ liệu mẫu:

| Customer | Orders |
|---|---:|
| An | 2 |
| Bình | 2 |
| Chi | 0 |
| Dũng | 1 |
| Em | 1 |

### 13.3. `COUNT(*)` và `COUNT(o.id)` không giống nhau khi LEFT JOIN

Trong SQL, `COUNT(*)` đếm cả hàng do LEFT JOIN giữ lại cho Customer không có Order, nên có thể ra 1; `COUNT(o.id)` bỏ qua giá trị ID null, nên cho 0.

Trong Criteria API, `cb.count(o.get("id"))` thể hiện rõ cần đếm các Order tồn tại. Không dùng `cb.count(c.get("id"))` để đếm số Order sau LEFT JOIN, vì ID Customer không null và có một hàng đại diện cho Customer không có Order.

**Chọn expression cần đếm theo entity được đếm, không chỉ theo root của query.**

### 13.4. SUM với nhóm rỗng và `COALESCE`

Tổng tiền Order của Chi có thể là null vì không có Order:

```java
Expression<BigDecimal> rawSum =
    cb.sum(o.<BigDecimal>get("totalAmount"));
```

Nếu báo cáo cần giá trị số 0:

```java
Expression<BigDecimal> total =
    cb.coalesce(rawSum, BigDecimal.ZERO);
```

Lúc đó:

```java
cq.multiselect(
    c.get("id"),
    cb.count(o.get("id")),
    total
);
```

`COALESCE` lấy giá trị không null đầu tiên: nếu `SUM` null thì dùng `BigDecimal.ZERO`. Điều này phù hợp với một báo cáo doanh thu đặt **“không có Order = tổng 0”**. Nhưng với các đại lượng như average, null có thể mang ý nghĩa “chưa có dữ liệu” khác với số 0; không coalesce mọi aggregate theo thói quen.

## 14. Bẫy WHERE biến LEFT JOIN thành lọc mất nhóm rỗng

Giả sử cần **đếm số Order PAID của mọi Customer, kể cả người chưa có Order PAID**.

### 14.1. Cách viết có thể sai

```java
Root<Customer> c = cq.from(Customer.class);

Join<Customer, PurchaseOrder> o =
    c.join("orders", JoinType.LEFT);

cq.where(
    cb.equal(o.get("status"), OrderStatus.PAID)
);
```

Mặc dù join là `LEFT`, điều kiện trong `WHERE` yêu cầu `o.status = PAID`. Với Customer không có Order hoặc không có Order PAID, biểu thức có thể không TRUE. Họ bị loại khỏi kết quả, làm mất nhóm có số 0.

### 14.2. Đặt filter vào `JOIN ... ON`

Criteria API hỗ trợ `Join.on(...)` để hạn chế các hàng phía được join:

```java
Root<Customer> c = cq.from(Customer.class);

Join<Customer, PurchaseOrder> paidOrders =
    c.join("orders", JoinType.LEFT);

paidOrders.on(
    cb.equal(paidOrders.get("status"), OrderStatus.PAID)
);

Expression<Long> paidCount =
    cb.count(paidOrders.get("id"));

cq.multiselect(
        c.get("id"),
        c.get("fullName"),
        paidCount
    )
    .groupBy(c.get("id"), c.get("fullName"))
    .orderBy(cb.asc(c.get("id")));
```

Ngữ nghĩa tương ứng:

```sql
SELECT c.id, c.full_name, COUNT(o.id)
FROM customers c
LEFT JOIN purchase_orders o
       ON o.customer_id = c.id
      AND o.status = 'PAID'
GROUP BY c.id, c.full_name
ORDER BY c.id;
```

Dữ liệu mẫu:

| Customer | Order PAID |
|---|---:|
| An | 1 |
| Bình | 2 |
| Chi | 0 |
| Dũng | 0 |
| Em | 1 |

`Join.on` giữ được Customer ngay cả khi không có Order PAID thỏa phần ON. Đây là khác biệt giữa **lọc dòng join** và **lọc kết quả cuối**.

### 14.3. Phương án khác: CASE trong aggregate

Nếu dùng LEFT JOIN toàn bộ Order, có thể tính số Order PAID bằng biểu thức điều kiện:

```java
Expression<Long> paidFlag = cb.<Long>selectCase()
    .when(
        cb.equal(o.get("status"), OrderStatus.PAID),
        1L
    )
    .otherwise(0L);

Expression<Long> paidCount = cb.sum(paidFlag);
```

Mỗi Order PAID góp 1, Order khác góp 0. Với Customer không có Order, hàng giả của LEFT JOIN cũng góp 0 vì điều kiện status không TRUE.

Phương án này có thể hữu ích khi cần **nhiều loại đếm có điều kiện trong cùng báo cáo**, nhưng cần đánh giá kiểu/SQL sinh ra và tránh join đa collection làm nhân bản hàng.

Nếu chỉ cần số Order PAID, `LEFT JOIN ... ON` thường trực tiếp và ngắn gọn hơn.

## 15. `HAVING` khi có LEFT JOIN và nhóm không có dữ liệu

### 15.1. Chỉ lấy Customer chưa có Order PAID

Nếu đã tạo `paidOrders` bằng `LEFT JOIN ... ON`:

```java
Expression<Long> paidCount =
    cb.count(paidOrders.get("id"));

cq.having(cb.equal(paidCount, 0L));
```

Query trả những Customer có **0 Order PAID**: Chi và Dũng. Đây là một lựa chọn thay cho `NOT EXISTS`; với yêu cầu thuần “không tồn tại hàng thỏa”, correlated `NOT EXISTS` cũng thường dễ diễn đạt.

### 15.2. Giữ nhóm có 0 nhưng lọc theo tổng

Nếu dùng:

```java
Expression<BigDecimal> revenue =
    cb.sum(paidOrders.<BigDecimal>get("totalAmount"));

cq.having(cb.ge(revenue, BigDecimal.ZERO));
```

Customer không có Order PAID có `SUM = NULL`, nên `NULL >= 0` không TRUE. **HAVING đã loại nhóm có 0 dù LEFT JOIN ban đầu giữ nhóm**.

Nếu muốn coi tổng thiếu dữ liệu là 0:

```java
Expression<BigDecimal> revenue =
    cb.coalesce(
        cb.sum(paidOrders.<BigDecimal>get("totalAmount")),
        BigDecimal.ZERO
    );

cq.having(cb.ge(revenue, BigDecimal.ZERO));
```

Kết quả lúc này có thể giữ cả nhóm tổng 0.

Nguyên tắc: **LEFT JOIN chỉ giữ hàng phía trái trước bước GROUP BY; các predicate sau đó vẫn có thể loại nhóm**. Cần xét WHERE, HAVING và logic NULL theo thứ tự.

## 16. Dùng `ParameterExpression` cho truy vấn có tham số

### 16.1. Tham số trạng thái

Thay vì gắn trực tiếp hằng enum trong expression:

```java
Predicate paid = cb.equal(
    o.get("status"), OrderStatus.PAID
);
```

có thể định nghĩa:

```java
ParameterExpression<OrderStatus> statusParam =
    cb.parameter(OrderStatus.class, "status");

Predicate matchesStatus =
    cb.equal(o.get("status"), statusParam);
```

Sau khi hoàn thiện `CriteriaQuery`:

```java
TypedQuery<Tuple> typed = em.createQuery(cq);

typed.setParameter("status", OrderStatus.PAID);

List<Tuple> rows = typed.getResultList();
```

`ParameterExpression` giúp query giữ cấu trúc cố định và truyền giá trị riêng, tương tự named parameter trong JPQL.

### 16.2. Tham số ngưỡng HAVING

```java
ParameterExpression<Long> minCount =
    cb.parameter(Long.class, "minCount");

Expression<Long> count = cb.count(o.get("id"));

cq.having(cb.ge(count, minCount));
```

`TypedQuery`:

```java
typed.setParameter("minCount", 2L);
```

Khi bind count threshold, dùng `Long` phù hợp kiểu của `COUNT`. Tránh trộn kiểu `Integer`/`Long` không có chủ đích.

### 16.3. Tham số khoảng thời gian trước khi nhóm

```java
ParameterExpression<Instant> from =
    cb.parameter(Instant.class, "from");

ParameterExpression<Instant> toExclusive =
    cb.parameter(Instant.class, "toExclusive");

Predicate inRange = cb.and(
    cb.greaterThanOrEqualTo(o.<Instant>get("placedAt"), from),
    cb.lessThan(o.<Instant>get("placedAt"), toExclusive)
);

cq.where(inRange);
```

Dùng khoảng `[from, toExclusive)` giúp báo cáo theo ngày không phải đoán mili-giây cuối ngày. Nếu người dùng nhập ngày lịch, hãy quy đổi theo `ZoneId` nghiệp vụ trước khi truyền thành `Instant`.

## 17. Bộ lọc động khi xây báo cáo

### 17.1. Thiết kế input rõ nghĩa

Giả sử API nhận:

```java
public record RegionReportFilter(
    OrderStatus status,
    Instant fromInclusive,
    Instant toExclusive,
    Long minimumOrders,
    BigDecimal minimumRevenue
) {}
```

Quy ước ví dụ:

- `status == null`: không lọc trạng thái.
- `fromInclusive == null`: không có cận dưới thời gian.
- `toExclusive == null`: không có cận trên thời gian.
- `minimumOrders == null`: không áp dụng điều kiện HAVING theo số đơn.
- `minimumRevenue == null`: không áp dụng điều kiện HAVING theo tổng tiền.

Đây là **chính sách của API**, không phải việc JPA tự hiểu tham số null là “bỏ lọc”.

### 17.2. Tạo predicates riêng cho WHERE và HAVING

```java
CriteriaBuilder cb = em.getCriteriaBuilder();
CriteriaQuery<Tuple> cq = cb.createTupleQuery();

Root<PurchaseOrder> o = cq.from(PurchaseOrder.class);
Join<PurchaseOrder, Customer> c = o.join("customer");

Path<String> region = c.get("regionCode");
Expression<Long> orderCount = cb.count(o.get("id"));
Expression<BigDecimal> revenue =
    cb.sum(o.<BigDecimal>get("totalAmount"));

List<Predicate> rowPredicates = new ArrayList<>();

if (filter.status() != null) {
    rowPredicates.add(
        cb.equal(o.get("status"), filter.status())
    );
}

if (filter.fromInclusive() != null) {
    rowPredicates.add(
        cb.greaterThanOrEqualTo(
            o.<Instant>get("placedAt"),
            filter.fromInclusive()
        )
    );
}

if (filter.toExclusive() != null) {
    rowPredicates.add(
        cb.lessThan(
            o.<Instant>get("placedAt"),
            filter.toExclusive()
        )
    );
}

List<Predicate> groupPredicates = new ArrayList<>();

if (filter.minimumOrders() != null) {
    groupPredicates.add(
        cb.ge(orderCount, filter.minimumOrders())
    );
}

if (filter.minimumRevenue() != null) {
    groupPredicates.add(
        cb.ge(revenue, filter.minimumRevenue())
    );
}
```

Cần import `java.util.ArrayList`, `java.util.List`, `java.math.BigDecimal`, `java.time.Instant` và các lớp Criteria API tương ứng.

### 17.3. Áp dụng vào CriteriaQuery

```java
cq.multiselect(
        region.alias("region"),
        orderCount.alias("orders"),
        revenue.alias("revenue")
    )
    .groupBy(region);

if (!rowPredicates.isEmpty()) {
    cq.where(rowPredicates.toArray(new Predicate[0]));
}

if (!groupPredicates.isEmpty()) {
    cq.having(groupPredicates.toArray(new Predicate[0]));
}

cq.orderBy(
    cb.desc(revenue),
    cb.asc(region)
);

List<Tuple> reports = em.createQuery(cq).getResultList();
```

Ở đây:

- `rowPredicates` lọc Order **trước grouping**.
- `groupPredicates` lọc từng nhóm **sau aggregate**.
- `orderBy` sắp kết quả cuối cùng.

Phân tách hai danh sách giúp tránh tình trạng vô tình đưa `COUNT` vào WHERE hoặc lọc từng Order bằng ngưỡng doanh thu của cả vùng.

### 17.4. Điều kiện lọc có thể làm biến mất cả nhóm

Nếu nguồn là `PurchaseOrder` và filter theo trạng thái PAID, vùng không có Order PAID sẽ không xuất hiện. Đó là đúng với báo cáo “thống kê vùng có hoạt động PAID”.

Nếu yêu cầu là “liệt kê mọi vùng, kể cả số 0”, truy vấn phải bắt đầu từ một danh sách vùng/Customer phù hợp và dùng LEFT JOIN + ON/aggregate. **Không thể chỉ thay HAVING để tạo ra những nhóm vốn không có hàng ở nguồn truy vấn.**

## 18. Sắp xếp động nhưng không cho client tùy ý chọn biểu thức

API báo cáo có thể nhận:

```text
sortBy=revenue&direction=desc
```

Không ghép nguyên chuỗi `sortBy` từ request vào SQL hoặc JPQL. Với Criteria API, tạo **whitelist biểu thức được phép sort**:

```java
Expression<?> selectedSort;

switch (sortBy) {
    case "region":
        selectedSort = region;
        break;
    case "orders":
        selectedSort = orderCount;
        break;
    case "revenue":
        selectedSort = revenue;
        break;
    default:
        throw new IllegalArgumentException(
            "sortBy không được hỗ trợ");
}

jakarta.persistence.criteria.Order primary =
    ascending
        ? cb.asc(selectedSort)
        : cb.desc(selectedSort);

cq.orderBy(primary, cb.asc(region));
```

Ở đây `sortBy` và `ascending` là tham số ứng dụng đã validate. Chỉ cho phép chọn giữa **những Expression thực sự có ý nghĩa với kết quả nhóm**.

Không sort theo `o.placedAt` chưa aggregate khi report đang là một hàng mỗi vùng. Nếu muốn sort theo “lần mua gần nhất”, hãy bổ sung `MAX(placedAt)` và đưa expression đó vào nhóm lựa chọn.

### 18.1. Null sorting và tính portable

`cb.asc`/`cb.desc` xác định hướng tăng/giảm, nhưng thứ tự của giá trị `NULL` khi sắp xếp có thể phụ thuộc database hoặc tính năng JPA/provider. Nếu UI yêu cầu “NULL luôn cuối cùng”, có thể xây biểu thức CASE thành một khóa sort:

```java
Expression<Integer> missingRevenue =
    cb.<Integer>selectCase()
        .when(cb.isNull(revenue), 1)
        .otherwise(0);

cq.orderBy(
    cb.asc(missingRevenue),
    cb.desc(revenue),
    cb.asc(region)
);
```

Khi query có GROUP BY, CASE này xây từ **aggregate revenue** chứ không phải một cột ngoài nhóm. Có thể cần kiểm tra SQL và quy tắc HAVING/GROUP BY của database cụ thể khi dùng biểu thức phức tạp.

## 19. Phân trang báo cáo có GROUP BY

### 19.1. Phân trang kết quả nhóm

`setFirstResult` và `setMaxResults` áp dụng lên **các hàng kết quả cuối**, tức các nhóm sau HAVING:

```java
List<Tuple> page = em.createQuery(cq)
    .setFirstResult(0)
    .setMaxResults(20)
    .getResultList();
```

Nếu query trả một hàng cho mỗi vùng, page size 20 nghĩa là tối đa 20 **vùng**, không phải 20 Order.

Luôn đặt `ORDER BY` ổn định khi phân trang. Với số liệu doanh thu bằng nhau, thêm `region` làm tie-breaker.

### 19.2. Query đếm tổng số nhóm khác query đếm tổng số đơn

Giả sử UI hiển thị 10 vùng mỗi trang và muốn biết **có bao nhiêu vùng thỏa filter**. Không thể dùng một cách máy móc:

```java
cb.count(o.get("id"))
```

trong một query không nhóm rồi coi đó là tổng số vùng. Nó đếm **Order**, không đếm các nhóm.

Nếu chỉ nhóm theo một mã vùng **không null** và không có HAVING phức tạp, có thể dùng:

```java
CriteriaQuery<Long> countQuery =
    cb.createQuery(Long.class);

Root<PurchaseOrder> countRoot =
    countQuery.from(PurchaseOrder.class);

Join<PurchaseOrder, Customer> countCustomer =
    countRoot.join("customer");

countQuery.select(
    cb.countDistinct(countCustomer.get("regionCode"))
);
```

Cần áp dụng **cùng WHERE filter** như report chính. Đây chỉ là cách đếm **các mã vùng khác nhau** có ít nhất một hàng sau WHERE; nó không tự phản ánh HAVING như “COUNT(Order) >= 2”.

### 19.3. Khi HAVING phức tạp, không có phép đếm nhóm một dòng cho mọi trường hợp

Nếu report nhóm theo `region, status` và có:

```java
cq.having(cb.ge(cb.count(o.get("id")), 2L));
```

thì `COUNT(DISTINCT region)` **không tương đương** số cặp `(region, status)` thỏa HAVING.

Các hướng xử lý:

1. Thiết kế một query riêng trả khóa nhóm thỏa cùng `WHERE/GROUP BY/HAVING` rồi đếm hàng kết quả nếu số nhóm nhỏ và chi phí chấp nhận được.
2. Dùng **native SQL** với derived table hoặc CTE để đếm kết quả của grouped query khi hệ quản trị hỗ trợ.
3. Dùng một bảng read model/materialized aggregation nếu đây là báo cáo lớn được truy vấn thường xuyên.
4. Tận dụng API/phần mở rộng của provider khi đã chấp nhận phụ thuộc công nghệ.

JPQL portable không có cùng cú pháp derived table trong `FROM` như SQL, vì vậy **không thể giả định luôn có thể bọc mọi grouped CriteriaQuery trong một `FROM (subquery)`** rồi dùng `COUNT(*)`.

### 19.4. Khi dữ liệu thay đổi giữa các trang

Offset pagination trên báo cáo doanh thu đang thay đổi có thể làm một vùng chuyển sang trang khác khi thứ hạng thay đổi. `ORDER BY` chỉ tạo thứ tự theo snapshot hiện tại; nó không đảm bảo các trang được đọc ở những thời điểm khác nhau có dữ liệu bất biến.

Nếu cần ảnh chụp báo cáo nhất quán, cân nhắc một mốc thời gian dữ liệu, snapshot/isolation phù hợp hoặc bảng tổng hợp đóng sổ. Đây là yêu cầu nghiệp vụ/transaction, không phải một tùy chọn riêng của `groupBy`.

## 20. Grouping theo quan hệ và tránh nhân bản do JOIN

### 20.1. Từ Order tới Customer

```java
Root<PurchaseOrder> o = cq.from(PurchaseOrder.class);
Join<PurchaseOrder, Customer> c = o.join("customer");
```

Một Order có đúng một Customer, nên join many-to-one như trên thường không tự nhân bản Order. Nhóm theo `c.regionCode` và đếm `o.id` phản ánh số Order.

### 20.2. Join thêm hai collection có thể nhân bản hàng

Giả sử một Order có 3 OrderLine và 2 PaymentTransaction. Nếu join cả:

```java
Join<PurchaseOrder, OrderLine> lines =
    o.join("lines");

Join<PurchaseOrder, PaymentTransaction> payments =
    o.join("payments");
```

một Order có thể đóng góp **3 × 2 = 6 hàng** ở kết quả join. Điều này làm:

- `COUNT(o.id)` phình lên.
- `SUM(o.totalAmount)` bị tính lặp.
- `COUNT(DISTINCT o.id)` có thể sửa số Order nhưng **không tự sửa doanh thu** nếu SUM vẫn lặp.

Đây chỉ là sơ đồ minh họa: để chạy, entity `PurchaseOrder` phải có hai collection được mapping tới `OrderLine` và `PaymentTransaction`.

### 20.3. Cách sửa cần theo đại lượng cần thống kê

Một số hướng:

- Nếu chỉ cần số Order và tổng tiền Order, **không join các collection không cần thiết**.
- Nếu cần lọc Order có Line phù hợp, có thể dùng `EXISTS` subquery để tránh nhân bản root Order.
- Nếu thật sự cần tổng theo Line, tính trên bảng/association Line và dùng `SUM(line.quantity × line.unitPrice)` theo đúng đại lượng, không sum Order total lặp.
- Nếu báo cáo phức tạp nhiều nguồn 1-n, cân nhắc truy vấn con/CTE/native SQL hoặc bước tổng hợp trung gian thích hợp.

Không tự thay `SUM(totalAmount)` bằng `SUM(DISTINCT totalAmount)` chỉ để chữa join duplication. Hai Order **khác nhau nhưng trùng số tiền** sẽ bị gộp thành một giá trị trong SUM DISTINCT, làm doanh thu sai.

## 21. `HAVING` và nhóm theo thuộc tính có NULL

### 21.1. GROUP BY gom các giá trị NULL như thế nào?

Khi một thuộc tính khóa nhóm nullable, các hàng mang giá trị null có thể tạo một nhóm đại diện cho null theo semantics SQL grouping. Ví dụ Customer có `regionCode` null (nếu schema cho phép) sẽ thuộc nhóm mã vùng chưa biết.

Trong schema ví dụ, `region_code NOT NULL` nên không gặp tình huống này. Với dữ liệu legacy, cần quyết định rõ báo cáo sẽ:

- Giữ nhóm vùng null.
- Loại trước khi nhóm bằng `WHERE c.regionCode IS NOT NULL`.
- Gộp null vào tên nhóm như `"UNKNOWN"` bằng `COALESCE`.

### 21.2. Nhóm với COALESCE

```java
Expression<String> regionGroup =
    cb.coalesce(
        c.<String>get("regionCode"),
        "UNKNOWN"
    );

cq.multiselect(
        regionGroup.alias("region"),
        cb.count(o.get("id")).alias("orders")
    )
    .groupBy(regionGroup);
```

**Chọn cùng expression ở SELECT và GROUP BY.** Không chọn `COALESCE(region, "UNKNOWN")` nhưng chỉ group theo một field không tương thích nếu muốn bảo đảm ngữ nghĩa và portability.

Cần lưu ý một mã vùng thật sự tên `"UNKNOWN"` sẽ được gộp với các giá trị null sau COALESCE. Nếu muốn phân biệt “mã UNKNOWN thật” với “không có mã”, cần một thiết kế khóa nhóm khác.

### 21.3. HAVING với SUM NULL

```java
Expression<BigDecimal> total =
    cb.sum(o.<BigDecimal>get("totalAmount"));

cq.having(cb.ge(total, BigDecimal.ZERO));
```

Với nhóm không có Order do LEFT JOIN, `SUM` có thể null; điều kiện so sánh với 0 trả UNKNOWN và nhóm bị loại.

Nếu yêu cầu bao gồm nhóm không có doanh thu:

```java
Expression<BigDecimal> safeTotal =
    cb.coalesce(total, BigDecimal.ZERO);

cq.having(cb.ge(safeTotal, BigDecimal.ZERO));
```

Null là một phần của ngữ nghĩa báo cáo, không đơn thuần là “giá trị không đẹp để hiển thị”.

## 22. Nhóm theo ngày, tháng và timezone

### 22.1. Nhóm theo `LocalDate` đã lưu

Nếu entity có thuộc tính `businessDate` kiểu `LocalDate` (ngày nghiệp vụ đã xác định), nhóm theo ngày trực tiếp:

```java
Path<LocalDate> day = o.get("businessDate");

cq.multiselect(
        day.alias("day"),
        cb.count(o.get("id")).alias("orders")
    )
    .groupBy(day)
    .orderBy(cb.asc(day));
```

Cần import `java.time.LocalDate` và khai báo/mapping thuộc tính `businessDate` trên entity để chạy biến thể này. Đây là cách có semantics khá rõ ràng nếu nghiệp vụ đã quy định ngày theo múi giờ.

### 22.2. Không giả định `Instant` tự tương đương ngày lịch

Trong mô hình ban đầu, `placedAt` là `Instant`. Nhóm trực tiếp:

```java
cq.groupBy(o.get("placedAt"));
```

sẽ nhóm theo **từng thời điểm**, không phải theo ngày. Những đơn đặt cùng ngày nhưng khác giờ vẫn thuộc các nhóm khác nhau.

Để nhóm theo ngày/tháng nghiệp vụ, phải chuyển timestamp sang bucket đúng timezone. Có vài phương án:

- Lưu cột `businessDate` hoặc `yearMonth` theo quy tắc nghiệp vụ và nhóm trực tiếp.
- Dùng database function như `DATE_TRUNC` hoặc `DATE`, thông qua `cb.function(...)` có chủ đích.
- Dùng native SQL khi cần timezone conversion hay nhóm theo kỳ phức tạp.

### 22.3. Hàm database không hoàn toàn portable

Ví dụ minh họa về khả năng gọi function:

```java
Expression<String> dayBucket = cb.function(
    "to_char",
    String.class,
    o.get("placedAt"),
    cb.literal("YYYY-MM-DD")
);
```

Cách này phụ thuộc database dialect, timezone của session và khả năng provider chấp nhận/ánh xạ hàm. **Không coi ví dụ là lời hứa rằng mọi JPA provider/database hỗ trợ `to_char`**. Nếu dùng, xác minh chuyển đổi theo múi giờ nghiệp vụ và dùng cùng biểu thức `dayBucket` trong `SELECT`, `GROUP BY` và `ORDER BY`.

Nếu báo cáo tổng tiền theo “ngày Việt Nam” nhưng DB lưu UTC, việc chỉ cắt chuỗi timestamp theo ngày UTC có thể nhóm sai đơn phát sinh gần ranh giới ngày. Phải chọn một `ZoneId` nghiệp vụ hoặc lưu cột ngày đã tính theo quy tắc rõ ràng.

### 22.4. Lọc khoảng trước khi nhóm

Khi báo cáo tháng, có thể lọc `placedAt` theo khoảng nửa mở:

```java
Predicate timeWindow = cb.and(
    cb.greaterThanOrEqualTo(
        o.<Instant>get("placedAt"), startInclusive
    ),
    cb.lessThan(
        o.<Instant>get("placedAt"), endExclusive
    )
);

cq.where(timeWindow);
```

Thời điểm đầu/cuối được chuẩn bị ở Java theo timezone và kỳ báo cáo. Thao tác `WHERE` làm giảm số Order cần nhóm; `GROUP BY` sau đó xử lý số hàng đã lọc.

## 23. Dùng static metamodel để an toàn kiểu hơn

### 23.1. Rủi ro của string-based path

```java
c.get("regionCode");
o.get("totalAmount");
```

Nếu đổi tên field Java từ `regionCode` thành `salesRegion` mà quên sửa chuỗi, lỗi có thể chỉ xuất hiện khi chạy query.

### 23.2. Static metamodel

Với cấu hình JPA static metamodel generator, có thể có lớp:

```java
@StaticMetamodel(Customer.class)
public abstract class Customer_ {
    public static volatile SingularAttribute<Customer, Long> id;
    public static volatile SingularAttribute<Customer, String> regionCode;
}
```

và:

```java
@StaticMetamodel(PurchaseOrder.class)
public abstract class PurchaseOrder_ {
    public static volatile SingularAttribute<PurchaseOrder, Long> id;
    public static volatile SingularAttribute<PurchaseOrder, BigDecimal>
        totalAmount;
    public static volatile SingularAttribute<PurchaseOrder, OrderStatus>
        status;
}
```

Đây là cấu trúc minh họa do annotation processor tạo, không khuyến khích viết tay khi dự án có generator.

Sử dụng:

```java
Path<String> region = c.get(Customer_.regionCode);

Path<BigDecimal> amount =
    o.get(PurchaseOrder_.totalAmount);

Expression<BigDecimal> revenue = cb.sum(amount);
```

Metamodel cho khả năng kiểm tra tên và kiểu thuộc tính tốt hơn khi refactor. Tuy nhiên, nó không tự bảo đảm biểu thức GROUP BY/HAVING đúng nghiệp vụ; vẫn phải hiểu sự khác nhau giữa hàng và nhóm.

## 24. `CriteriaQuery` có thể bị thay đổi cấu hình khi dựng động

### 24.1. Không gọi `where`/`having` nhiều lần mà không quản lý kết quả

Ví dụ dễ bị bỏ sót điều kiện:

```java
cq.where(cb.equal(o.get("status"), OrderStatus.PAID));
cq.where(cb.ge(
    o.<BigDecimal>get("totalAmount"),
    new BigDecimal("500000.00")
));
```

Các lời gọi `where(...)` thiết lập restriction của query; gọi sau **thay restriction trước**, không có nghĩa tự append bằng AND.

Cách đúng:

```java
Predicate paid =
    cb.equal(o.get("status"), OrderStatus.PAID);

Predicate large =
    cb.ge(
        o.<BigDecimal>get("totalAmount"),
        new BigDecimal("500000.00")
    );

cq.where(cb.and(paid, large));
```

Tương tự với `having(...)`: nên tập hợp điều kiện nhóm rồi đặt một lần, hoặc chủ động kết hợp chúng trước khi gọi.

### 24.2. `groupBy`/`orderBy` cũng không phải “append mãi”

Khi code báo cáo động có nhiều bước, cách an toàn là:

1. Tạo `List<Expression<?>> groupKeys` cho các khóa nhóm.
2. Tạo `List<jakarta.persistence.criteria.Order> sorts`.
3. Gọi `cq.groupBy(groupKeys)` một lần sau khi xác định grouping.
4. Gọi `cq.orderBy(sorts)` một lần sau khi xác định sắp xếp.
5. Gọi `where` và `having` theo các danh sách Predicate đã gộp.

Nhờ đó, các module không vô tình ghi đè restriction của nhau khi cùng làm việc trên một `CriteriaQuery`.

### 24.3. Một query nên có mục tiêu output rõ ràng

Không nên vừa dùng `CriteriaQuery<Customer>` để muốn trả entity Customer, vừa `multiselect(region, count, revenue)` rồi kỳ vọng JPA vẫn xây entity đầy đủ. Với report tổng hợp, chọn:

- `CriteriaQuery<Tuple>` cho nhiều trường dữ liệu động.
- `CriteriaQuery<RegionReport>` với `cb.construct` cho DTO cố định.
- `CriteriaQuery<Long>` cho một aggregate scalar đơn.

Dạng SELECT phải nhất quán với kiểu kết quả được khai báo.

## 25. Khi nào dùng `GROUP BY`, khi nào dùng truy vấn con?

### 25.1. Chỉ cần báo cáo thống kê theo vùng

Dùng nhóm trực tiếp là tự nhiên:

```jpql
SELECT c.regionCode, COUNT(o.id)
FROM PurchaseOrder o JOIN o.customer c
GROUP BY c.regionCode
```

### 25.2. Cần lấy Customer có nhiều Order nhưng vẫn trả entity đầy đủ

Có thể dùng truy vấn con tương quan:

```jpql
SELECT c
FROM Customer c
WHERE (
    SELECT COUNT(o)
    FROM PurchaseOrder o
    WHERE o.customer = c
) >= :minimum
```

Ưu điểm về cấu trúc: query ngoài trả **Customer entity**, subquery chỉ dùng để lọc. Không cần GROUP BY tất cả các thuộc tính Customer được chọn; tuy vậy hiệu năng phụ thuộc DB và index.

### 25.3. Cần lấy từng vùng cùng thống kê

`GROUP BY` và DTO projection thường phù hợp hơn. Subquery tương quan có thể là lựa chọn nếu muốn tính nhiều thước đo khác nhau mà không tạo join nhân bản, nhưng query sẽ phức tạp và cần đo performance.

**Cách lựa chọn:** bắt đầu từ hình dạng kết quả mong muốn. Nếu kết quả là “một hàng mỗi nhóm”, dùng GROUP BY; nếu kết quả là “tập entity thỏa một điều kiện dựa trên aggregate liên quan”, correlated subquery có thể dễ hiểu hơn.

## 26. Hiệu năng và chỉ mục

### 26.1. GROUP BY có chi phí thực tế

Database có thể dùng hash aggregate, sort aggregate hoặc các chiến lược khác để nhóm. Chi phí phụ thuộc:

- Số hàng sau WHERE.
- Số lượng nhóm.
- Số biểu thức nhóm và aggregate.
- Kích thước dữ liệu mỗi hàng.
- Index, phân bố giá trị và thống kê.
- Mức độ sắp xếp ORDER BY.
- Có join làm tăng số dòng hay không.

Criteria API chỉ tạo biểu thức truy vấn; nó **không tự đảm bảo query tối ưu**. Provider chuyển cấu trúc query thành SQL, rồi optimizer database quyết định execution plan.

### 26.2. Lọc hàng sớm khi đúng nghiệp vụ

Nếu chỉ báo cáo các Order PAID trong ba tháng gần đây, nên đặt status và thời gian trong WHERE (hoặc ON đúng semantics) để database không cần nhóm các Order bị loại.

Không đưa điều kiện hàng thuần túy sang HAVING để “chạy sau” khi không cần thiết. WHERE thường tạo cơ hội giảm số hàng trước aggregate.

### 26.3. Index theo điều kiện lọc và nhóm

Một index cần cân nhắc cho các báo cáo lọc theo Customer, status, thời gian:

```sql
CREATE INDEX ix_orders_status_date_customer
    ON purchase_orders(status, placed_at, customer_id);
```

Đây chỉ là ví dụ. Có thể index `(customer_id, status)` phù hợp hơn với truy vấn “một Customer có bao nhiêu Order PAID” hoặc các join correlation. Thứ tự cột trong index phải dựa trên predicate, độ chọn lọc và execution plan của DB đang sử dụng.

### 26.4. Nhiều điều kiện HAVING có thể tốn kém

Điều kiện:

```java
cq.having(cb.ge(cb.count(o.get("id")), 2L));
```

chỉ được đánh giá sau khi dữ liệu hình thành nhóm. Nếu báo cáo rất lớn và được gọi liên tục, có thể cần:

- Pre-aggregated/read model table.
- Materialized view với refresh policy phù hợp.
- Báo cáo theo batch hay theo chu kỳ.
- Cache kết quả nhóm theo kỳ dữ liệu.
- Native SQL với window functions hoặc các khả năng đặc thù database khi phù hợp.

Đây là lựa chọn kiến trúc, không phải một tùy chọn kỳ diệu của `CriteriaBuilder`.

### 26.5. SQL logging và execution plan

Để đánh giá:

1. Ghi nhận Criteria query đang xây và các tham số.
2. Bật log SQL trong môi trường phát triển/kiểm thử phù hợp.
3. Chạy EXPLAIN/EXPLAIN ANALYZE trong database trên tập dữ liệu đại diện.
4. Quan sát số hàng trước/sau join, số nhóm, sort, hash aggregate, memory, index.
5. So sánh với JPQL tương đương hoặc native SQL nếu cần.
6. Kiểm tra số query phát sinh sau khi đọc DTO/entity.

Không đánh giá hiệu năng chỉ bằng việc code Criteria có ít hay nhiều dòng Java.

## 27. Transaction, flush và tính nhất quán của báo cáo

### 27.1. Aggregate đọc trạng thái của transaction/query

Một báo cáo nhóm chạy trong persistence context và transaction sẽ nhìn thấy dữ liệu theo quy tắc flush, isolation và cache liên quan. Nếu ứng dụng vừa tạo Order PAID nhưng chưa flush, kết quả truy vấn tổng hợp có thể khác tùy flush mode và cách provider đảm bảo semantics.

Khi muốn kiểm soát việc đồng bộ thay đổi trước báo cáo:

```java
em.persist(newOrder);
em.flush();

List<Tuple> report = em.createQuery(cq).getResultList();
```

`flush` yêu cầu đồng bộ pending SQL trong transaction, nhưng **không phải commit**. Nếu transaction rollback, dữ liệu đó không còn ở committed state.

### 27.2. Báo cáo trong cùng transaction chưa chứng minh người đọc khác thấy kết quả

Nếu cần kiểm chứng dữ liệu đã commit:

1. Hoàn thành transaction ghi thành công.
2. Mở context/transaction đọc phù hợp sau commit.
3. Chạy truy vấn báo cáo nhóm.
4. Xác nhận kết quả theo snapshot và database nguồn.

Một báo cáo trên read replica có thể chậm hơn primary vì replication lag. Tương tự, cache/read model được cập nhật bất đồng bộ có thể chưa chứa dữ liệu ngay sau commit.

### 27.3. COUNT và SUM không thay thế ràng buộc dữ liệu

Một query HAVING có thể cho biết “hiện chưa có đủ số Order”, nhưng nó không ngăn transaction khác chèn thêm Order ngay sau đó. Nếu kết quả quyết định một hành động ghi nhạy cảm, cần thiết kế concurrency control và constraint phù hợp.

Báo cáo là công cụ đọc và tổng hợp, không phải một khóa giao dịch vĩnh viễn.

## 28. Các lỗi thường gặp

| Lỗi/tình huống | Vì sao sai hoặc gây bất ngờ | Cách xử lý |
|---|---|---|
| Đưa `COUNT`/`SUM` vào `WHERE` | Aggregate của nhóm thuộc HAVING | Đặt trong `cq.having(...)` |
| Đặt điều kiện từng Order vào HAVING thay vì WHERE | Lọc sai tầng hoặc làm DB phải nhóm nhiều hơn | Dùng `cq.where(...)` cho row predicate |
| Chọn `fullName` nhưng chỉ nhóm `regionCode` | Một nhóm có nhiều tên, giá trị không xác định | Chọn group keys/aggregate nhất quán |
| Nhóm theo tên Customer thay vì ID | Nhiều Customer trùng tên bị gộp | Nhóm theo ID và field cần hiển thị |
| Đếm `c.id` trên LEFT JOIN để lấy số Order | Customer không có Order vẫn có c.id | Đếm `o.id` |
| WHERE `o.status=PAID` sau LEFT JOIN | Loại Customer không có Order PAID | Dùng `Join.on` hoặc CASE aggregate |
| Có LEFT JOIN nhưng SUM nhóm rỗng là null | SUM không trả 0 khi không có giá trị | `cb.coalesce(sum, zero)` khi đúng nghiệp vụ |
| Coi `AVG` là `BigDecimal` | Criteria AVG trả `Double` | DTO/Tuple dùng đúng kiểu, xét precision |
| Coi `COUNT` là `Integer` | COUNT trả `Long` | Dùng `Expression<Long>`/`Long` |
| Join hai collection rồi SUM Order total | Multiplicity làm nhân bản dòng | Đổi query shape/subquery, không SUM DISTINCT tùy tiện |
| Dùng `SUM(DISTINCT amount)` chữa duplicate join | Hai Order khác ID trùng amount bị gộp | Đếm/nhóm theo đúng entity identity |
| ORDER BY một thuộc tính Order bất kỳ khi nhóm theo region | Một nhóm có nhiều giá trị Order | Sắp theo group key hoặc aggregate |
| Không có tie-breaker khi phân trang | Các nhóm cùng tổng có thứ tự khó đoán | Thêm khóa nhóm ổn định |
| Tính tổng số trang bằng COUNT(Order) | Đếm hàng nguồn, không đếm số nhóm | Query count groups theo đúng semantics |
| Lấy `COUNT(DISTINCT region)` dù HAVING phức tạp | Không phản ánh số nhóm thỏa HAVING | Query đếm riêng hoặc native SQL phù hợp |
| Gọi `where` nhiều lần tưởng tự nối AND | Restriction cũ bị thay | Tập hợp Predicate rồi gọi một lần |
| Gọi `orderBy` nhiều lần tưởng tự append | Thứ tự có thể bị thay | Xây List<Order> cuối rồi gọi một lần |
| Truyền cột SQL như `"total_amount"` vào `get` | Criteria API dùng Java property | Dùng `"totalAmount"` hoặc metamodel |
| DTO constructor sai kiểu/thứ tự | Provider không tạo được đối tượng | Khớp `cb.construct` với constructor |
| Coi GROUP BY timestamp là nhóm theo ngày | Mỗi timestamp là một giá trị riêng | Nhóm theo businessDate/bucket đúng timezone |
| Cho client tùy tiện quyết định sort expression | Không kiểm soát cú pháp/semantics | Whitelist `region/orders/revenue` |
| Chỉ nhìn L1 context rồi tin báo cáo đã commit | Flush và commit khác nhau | Kiểm tra transaction/read boundary đúng |
| Thấy nhóm thiếu vùng có 0 Order | Root là Order hoặc WHERE loại hàng | Bắt đầu từ Customer/dimension và LEFT JOIN |
| Dùng `GROUP BY` để fetch collection đầy đủ | Aggregate query không phải fetch plan | Tách báo cáo DTO và truy vấn chi tiết |

## 29. Bài thực hành

### Bài 1 — Nhóm số Order theo vùng

Từ `PurchaseOrder` join `Customer`, dùng Criteria API để chọn `regionCode` và `COUNT(Order.id)`. Nhóm theo vùng và sắp tăng dần theo mã vùng.

Dự đoán kết quả DN=1, HCM=4, HN=1 với dữ liệu mẫu. Giải thích vì sao Chi không có Order nhưng vùng HN vẫn xuất hiện nhờ Order của Em.

### Bài 2 — Lọc trạng thái trước khi nhóm

Thêm `WHERE status = PAID` vào query trước. So sánh kết quả với query không lọc và xác định vì sao vùng DN biến mất.

Giải thích sự khác nhau giữa “đếm mọi Order” và “đếm Order PAID”.

### Bài 3 — HAVING theo số Order

Chỉ chọn các vùng có ít nhất hai Order PAID. Sử dụng `cb.ge(cb.count(o.get("id")), 2L)` trong `cq.having`.

Thử thay HAVING bằng WHERE dùng COUNT và tìm hiểu vì sao đây là ý định sai về tầng xử lý.

### Bài 4 — Nhiều điều kiện HAVING

Viết báo cáo chỉ giữ nhóm có ít nhất hai Order PAID **và** tổng doanh thu PAID từ một triệu trở lên.

Dùng `cb.and`, rồi thử `cb.or` để xác định logic khác nhau. Đặt predicate trước/sau grouping đúng theo đại lượng.

### Bài 5 — Nhóm theo vùng và status

Dùng `groupBy(region, status)` và `multiselect(region, status, count)` để trả mỗi cặp vùng/trạng thái.

Giải thích vì sao không có nhóm cho các cặp không có Order, ví dụ DN/PAID.

### Bài 6 — Đếm cả Customer không có Order

Bắt đầu từ `Root<Customer>`, dùng `JoinType.LEFT` tới `orders`. Nhóm theo `id` và `fullName`.

Đảm bảo Chi có `orderCount = 0`. So sánh `COUNT(c.id)` với `COUNT(o.id)` khi Customer không có Order.

### Bài 7 — Số đơn PAID bằng 0

Dùng `LEFT JOIN ... ON (status = PAID)` và `COUNT(o.id)`. Tìm Customer không có Order PAID bằng `HAVING COUNT = 0`.

Với dữ liệu mẫu, xác định Chi và Dũng. Thử chuyển predicate status từ `ON` sang `WHERE` và nhận xét vì sao hàng nhóm 0 biến mất.

### Bài 8 — COALESCE SUM

Với LEFT JOIN Customer–Order, tính `SUM(totalAmount)` theo Customer. Quan sát nhóm Chi không có Order; dùng `cb.coalesce(rawSum, BigDecimal.ZERO)` để hiển thị 0.

Giải thích vì sao `COUNT` trả 0 còn `SUM` có thể trả null.

### Bài 9 — Sắp xếp theo tổng doanh thu

Nhóm theo vùng, sắp theo `SUM(totalAmount) DESC`, sau đó `region ASC`.

Giải thích ý nghĩa tie-breaker khi phân trang. Thử yêu cầu “sắp theo Order mới nhất” và chọn `MAX(placedAt)` thay vì sắp theo `o.placedAt` không nhóm.

### Bài 10 — Tuple và record DTO

Thực hiện cùng báo cáo theo hai cách:

1. `CriteriaQuery<Tuple>` + alias `region`, `orderCount`, `revenue`.
2. `CriteriaQuery<RegionReport>` + `cb.construct(RegionReport.class, ...)`.

So sánh cách lấy kết quả, kiểu `Long`, `BigDecimal` và trường hợp constructor sai thứ tự.

### Bài 11 — Truy vấn động

Tạo `RegionReportFilter` gồm status, khoảng thời gian, minimumOrders và minimumRevenue. Dùng `List<Predicate>` riêng cho WHERE/HAVING; thêm predicate chỉ khi input có giá trị.

Giải thích vì sao không nên truyền null vào một phép so sánh rồi coi là bỏ filter.

### Bài 12 — Join nhân bản kết quả

Mở rộng mô hình để Order có nhiều Line và nhiều PaymentTransaction. Join cả hai collection, sau đó quan sát `COUNT(o.id)` và `SUM(o.totalAmount)`.

Giải thích tại sao `COUNT DISTINCT` có thể sửa số Order nhưng `SUM(DISTINCT totalAmount)` có thể vẫn sai. Đề xuất query shape khác.

### Bài 13 — Phân trang và đếm nhóm

Phân trang báo cáo một hàng mỗi vùng với `setFirstResult`/`setMaxResults`. Đếm tổng số vùng bằng `COUNT(DISTINCT region)` khi **không có HAVING** và region không null.

Sau đó thêm `HAVING COUNT >= 2` và phân tích vì sao tổng số nhóm cần một cơ chế đếm khác, không thể giữ nguyên count query cũ.

### Bài 14 — Nhóm theo ngày

Thêm field `businessDate` kiểu `LocalDate` và nhóm theo ngày. So với việc nhóm trực tiếp `placedAt` kiểu `Instant`.

Thảo luận cách tính ngày theo timezone của ứng dụng, và khi nào cần database function/native SQL.

### Bài 15 — Đọc execution plan

Tạo dữ liệu thử nghiệm có nhiều Order trên một Customer. So sánh grouped Criteria query với JPQL tương đương, xem SQL sinh ra và execution plan.

Đo tác động của index liên quan status, placedAt và customer_id. Không kết luận một index luôn tốt chỉ từ tên cột của query.

## 30. Ghi nhớ cốt lõi

**Criteria API nhóm, lọc nhóm và sắp xếp bằng ba thao tác chính: `CriteriaQuery.groupBy(...)`, `CriteriaQuery.having(...)` và `CriteriaQuery.orderBy(...)`.** `GROUP BY` xác định khóa nhóm; các hàm `CriteriaBuilder.count`, `sum`, `avg`, `min`, `max` tính đại lượng theo nhóm; `HAVING` lọc **cả nhóm**, còn `ORDER BY` sắp những nhóm đã chọn.

Hãy dùng **`WHERE` cho điều kiện từng hàng trước khi tổng hợp** và **`HAVING` cho điều kiện phụ thuộc aggregate**. Khi cần giữ Customer không có Order, dùng `LEFT JOIN` và đếm `Order.id`; nếu chỉ đếm Order PAID mà vẫn muốn giữ nhóm 0, đặt filter vào `Join.on(...)` hoặc dùng aggregate có điều kiện. Với `SUM` trên nhóm rỗng, xác định rõ khi nào cần `COALESCE` thay null bằng 0.

Kết quả nhóm thường phù hợp với **`Tuple` hoặc DTO projection**, không phải entity đầy đủ. Khi sắp xếp/phân trang, chọn khóa nhóm và aggregate có ý nghĩa, thêm tie-breaker ổn định, và nhớ rằng **đếm số nhóm khác đếm số hàng nguồn**. Cuối cùng, kiểm tra SQL và execution plan khi dữ liệu lớn hoặc nhiều join: **một báo cáo đúng bắt đầu từ việc chọn đúng nguồn hàng, khóa nhóm, điều kiện trước nhóm, điều kiện sau nhóm và đại lượng đang được đếm/tính tổng**.
