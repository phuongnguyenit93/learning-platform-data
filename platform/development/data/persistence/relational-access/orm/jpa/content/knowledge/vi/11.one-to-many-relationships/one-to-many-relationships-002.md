# Ánh xạ OneToMany hai hướng bằng mappedBy

> **Chủ đề:** Data Persistence – Relational Access, ORM, JPA  
> **Nhóm kiến thức:** Quan hệ một-nhiều

Trong một cơ sở dữ liệu quan hệ, **một phòng ban có nhiều nhân viên** thường được biểu diễn bằng khóa ngoại **employees.department_id**. Trong mô hình Java, ứng dụng lại muốn đi theo cả hai chiều: từ **Department** lấy danh sách **Employee**, và từ một **Employee** tìm **Department** của người đó. Đây là một **quan hệ một–nhiều hai hướng (bidirectional one-to-many)**.

JPA cung cấp hai annotation phối hợp với nhau:

- **@OneToMany(mappedBy = "department")** trên collection ở Department;
- **@ManyToOne** cùng **@JoinColumn(name = "department_id")** trên thuộc tính department ở Employee.

Điểm quan trọng nhất: **mappedBy trỏ tới tên thuộc tính Java ở phía sở hữu quan hệ**, không phải tên cột database. Trong ví dụ này, **Employee.department là owning side**, chịu trách nhiệm ánh xạ khóa ngoại; **Department.employees là inverse side**, biểu diễn chiều ngược lại để duyệt object graph.

Bài học hướng dẫn cách dựng đầy đủ mapping, dự đoán SQL, viết phương thức giữ hai phía Java nhất quán, chọn cascade/orphanRemoval đúng với vòng đời nghiệp vụ, truy vấn hiệu quả và xác minh dữ liệu đã được lưu. Sau khi học, bạn sẽ giải thích được vì sao chỉ thêm một phần tử vào collection có thể chưa cập nhật khóa ngoại và vì sao chỉ đổi phía sở hữu có thể khiến object graph đang ở trong bộ nhớ bị lệch.

## 1. Từ một khóa ngoại SQL đến hai hướng trong Java

Một thiết kế quan hệ cơ bản:

~~~sql
CREATE TABLE departments (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(120) NOT NULL
);

CREATE TABLE employees (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    full_name VARCHAR(120) NOT NULL,
    department_id BIGINT,
    CONSTRAINT fk_employees_department
        FOREIGN KEY (department_id) REFERENCES departments(id)
);

CREATE INDEX idx_employees_department_id
    ON employees(department_id);
~~~

Ví dụ dùng cú pháp PostgreSQL; cú pháp tạo khóa tăng tự động, kiểu dữ liệu và index có thể khác theo RDBMS.

~~~text
departments                           employees
-----------                           ------------------------------
id (PK)                               id (PK)
name                                  full_name
   10  ───────────────────────────►   department_id (FK) = 10
           một phòng ban               nhiều hàng nhân viên
~~~

Một phòng ban có thể có 0, 1 hoặc nhiều nhân viên. Với một hàng Employee, cột **department_id** chứa tối đa **một** khóa của phòng ban. Vì thế:

- Ở **Java**, một Department sở hữu một collection **employees** và mỗi Employee có một reference **department**.
- Ở **SQL**, khóa ngoại thường nằm ở **bảng phía nhiều**, tức **employees**.
- **Không cần bảng nối** chỉ để biểu diễn quan hệ hai hướng này.
- Hai chiều trong Java không tạo ra hai khóa ngoại độc lập. Chúng là **hai cách nhìn cùng một quan hệ**.

~~~mermaid
flowchart LR
    D["Department (1)"] -->|"employees: List"| E["Employee (N)"]
    E -->|"department: reference"| D
    DB[("employees.department_id")] -.->|"FK tham chiếu"| D
~~~

Nếu không cần duyệt từ Department sang Employee, có thể chỉ mapping **@ManyToOne** trên Employee; đó là quan hệ một hướng. Chỉ thêm **@OneToMany(mappedBy=...)** khi ứng dụng có nhu cầu thực sự duyệt hoặc quản lý từ phía Department.

## 2. Mapping đúng bằng @ManyToOne, @OneToMany và mappedBy

### 2.1. Phía nhiều: Employee quản lý khóa ngoại

~~~java
package com.example.company;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.FetchType;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.JoinColumn;
import jakarta.persistence.ManyToOne;
import jakarta.persistence.Table;

@Entity
@Table(name = "employees")
public class Employee {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "full_name", nullable = false, length = 120)
    private String fullName;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "department_id")
    private Department department;

    protected Employee() { }

    public Employee(String fullName) {
        if (fullName == null || fullName.isBlank()) {
            throw new IllegalArgumentException("Tên nhân viên không được trống");
        }
        this.fullName = fullName;
    }

    public Long getId() { return id; }
    public String getFullName() { return fullName; }
    public Department getDepartment() { return department; }

    // Phương thức chuyển quan hệ sẽ được hoàn thiện ở phần sau.
}
~~~

Trên **Employee**, **@ManyToOne** mô tả nhiều nhân viên cùng tham chiếu một phòng ban. **@JoinColumn(name = "department_id")** chỉ cột FK ở bảng **employees**. Giá trị của **Employee.department** là cơ sở để provider quyết định ghi **department_id** khi flush.

**fetch = FetchType.LAZY** chủ động yêu cầu tải quan hệ khi cần. Mặc định theo JPA, **@ManyToOne** có fetch EAGER; nhiều dự án chuyển sang LAZY để kiểm soát lượng dữ liệu truy vấn, nhưng hiệu quả lazy phụ thuộc provider và cách sử dụng.

### 2.2. Phía một: Department duyệt ngược bằng mappedBy

~~~java
package com.example.company;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.FetchType;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.OneToMany;
import jakarta.persistence.Table;
import java.util.ArrayList;
import java.util.List;

@Entity
@Table(name = "departments")
public class Department {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "name", nullable = false, length = 120)
    private String name;

    @OneToMany(mappedBy = "department", fetch = FetchType.LAZY)
    private List<Employee> employees = new ArrayList<>();

    protected Department() { }

    public Department(String name) {
        if (name == null || name.isBlank()) {
            throw new IllegalArgumentException("Tên phòng ban không được trống");
        }
        this.name = name;
    }

    public Long getId() { return id; }
    public String getName() { return name; }
    public List<Employee> getEmployees() { return employees; }
}
~~~

**@OneToMany(mappedBy = "department")** nói rằng collection này là **phía đối ứng** của quan hệ được khai báo tại **Employee.department**. Để diễn đạt đúng, chuỗi **department** phải trùng tên thuộc tính Java, phân biệt hoa/thường, trên class Employee.

| Thành phần | Nằm ở đâu? | Ý nghĩa |
|---|---|---|
| **@OneToMany** | Department.employees | Một Department liên quan nhiều Employee |
| **mappedBy = "department"** | Department.employees | Quan hệ đã được quản lý bởi thuộc tính Employee.department |
| **@ManyToOne** | Employee.department | Nhiều Employee tham chiếu một Department |
| **@JoinColumn(name = "department_id")** | Employee.department | Cột FK vật lý trong bảng employees |
| **FetchType.LAZY** | Cả hai mapping trong ví dụ | Trì hoãn tải dữ liệu quan hệ khi phù hợp |

**mappedBy không phải tên column, table, repository, getter hoặc collection**. Các ví dụ sai:

~~~java
@OneToMany(mappedBy = "department_id") // Sai: tên cột SQL.
private List<Employee> employees;

@OneToMany(mappedBy = "employees") // Sai: tên collection phía Department.
private List<Employee> employees;
~~~

Với class Employee ở trên, chỉ **mappedBy = "department"** là đường dẫn đúng.

### 2.3. Owner và inverse được xác định bởi mapping, không phải tên lớp

Trong quan hệ hai chiều **@OneToMany/@ManyToOne**, **many side** thường là owning side. Từ “owner” ở đây là **sở hữu mapping quan hệ**, tức phía provider dùng để ghi foreign key; nó **không** có nghĩa Employee sở hữu phòng ban về mặt nghiệp vụ.

Ví dụ nghiệp vụ có thể yêu cầu phải gọi **department.addEmployee(employee)** để phân công, dù bên trong helper vẫn gán **employee.department**. Chủ thể điều phối nghiệp vụ và owning side của JPA là hai khái niệm khác nhau.

### 2.4. Vì sao không đặt @JoinColumn cả hai phía?

Đối với cặp annotation này, **@JoinColumn** được đặt ở phía **Employee.department**, nơi bảng employees có khóa ngoại. Collection **Department.employees** chỉ cần **mappedBy**. Nếu đồng thời khai báo một mapping **@JoinColumn** độc lập ở phía Department thay vì **mappedBy**, provider có thể hiểu hai mapping quan hệ riêng hoặc báo lỗi cấu hình, dẫn tới SQL/bảng không như mong muốn.

Đúng:

~~~java
@OneToMany(mappedBy = "department")
private List<Employee> employees;

// Trong Employee:
@ManyToOne
@JoinColumn(name = "department_id")
private Department department;
~~~

Nếu muốn **@OneToMany một hướng** không có thuộc tính Employee.department, cơ chế mapping khác và không dùng **mappedBy**. Bài học này tập trung vào **hai hướng**.

## 3. Vì sao chỉ sửa một phía là sai?

Trong Java, hai tham chiếu không tự giữ cho nhau đồng bộ. JPA có thể dựa vào owning side để ghi SQL, nhưng không có một “đồng hồ hai chiều” tự động áp dụng mọi phép gán thuộc tính lên object graph.

Giả sử:

~~~java
Department tech = em.find(Department.class, 10L);
Employee an = em.find(Employee.class, 21L);
~~~

### 3.1. Chỉ thêm vào Department.employees

~~~java
tech.getEmployees().add(an);
~~~

Lúc này:

~~~text
tech.employees chứa an      : có thể đúng
an.department == tech       : chưa chắc, có thể null hoặc Department khác
employees.department_id     : chưa chắc đổi khi flush
~~~

Vì Department.employees là inverse side, chỉ thay đổi collection **không phải cách đáng tin cậy để ghi FK**. Đừng dựa vào “nó đang có trong list” để kết luận quan hệ đã được lưu.

### 3.2. Chỉ gán Employee.department

~~~java
an.setDepartment(tech);
~~~

Nếu Employee đang managed, JPA có thể ghi FK đúng ở lần flush:

~~~sql
UPDATE employees
SET department_id = 10
WHERE id = 21;
~~~

Nhưng collection **tech.employees** đã được load có thể vẫn không chứa **an**, khiến code trong cùng transaction hoặc DTO được dựng từ collection đọc sai trạng thái. **Flush** không phải lời hứa “sửa toàn bộ object graph” trong bộ nhớ.

### 3.3. Bất biến cần bảo vệ

Với các instance thuộc cùng graph đang thao tác:

~~~text
Nếu employee.department == department
thì department.employees phải chứa employee.

Nếu employee chuyển từ A sang B
thì A.employees không còn employee
và B.employees chứa employee đúng một lần.
~~~

Đó là lý do nên có **phương thức nghiệp vụ đồng bộ hai phía**, thay vì cho phép code tùy ý gọi setter và **List.add/remove**.

## 4. Helper methods giữ hai phía nhất quán

Một thiết kế thực tế cho quan hệ Department–Employee gồm:

- **Department.addEmployee(employee)** và **removeEmployee(employee)** là API công khai.
- **Employee.moveTo(department)** là nơi điều phối chuyển phòng ban; có thể được gọi trực tiếp nếu domain cho phép.
- Hai phương thức nội bộ trên Department chỉ sửa collection, **không gọi ngược lại moveTo**. Nhờ vậy không phát sinh vòng lặp đệ quy.
- Getter trả về view chỉ đọc để code bên ngoài không tự ý thêm/xóa.

### 4.1. Department hoàn chỉnh

~~~java
package com.example.company;

import jakarta.persistence.*;
import java.util.ArrayList;
import java.util.Collections;
import java.util.Iterator;
import java.util.List;
import java.util.Objects;

@Entity
@Table(name = "departments")
public class Department {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "name", nullable = false, length = 120)
    private String name;

    @OneToMany(mappedBy = "department", fetch = FetchType.LAZY)
    private List<Employee> employees = new ArrayList<>();

    protected Department() { }

    public Department(String name) {
        if (name == null || name.isBlank()) {
            throw new IllegalArgumentException("Tên phòng ban không được trống");
        }
        this.name = name;
    }

    public Long getId() { return id; }
    public String getName() { return name; }

    public List<Employee> getEmployees() {
        return Collections.unmodifiableList(employees);
    }

    public void addEmployee(Employee employee) {
        Objects.requireNonNull(employee, "employee");
        employee.moveTo(this);
    }

    public void removeEmployee(Employee employee) {
        Objects.requireNonNull(employee, "employee");
        if (employee.getDepartment() == this) {
            employee.moveTo(null);
        }
    }

    // Chỉ thao tác collection; không gọi lại Employee.moveTo().
    void addEmployeeInternal(Employee employee) {
        for (Employee existing : employees) {
            if (existing == employee) {
                return;
            }
        }
        employees.add(employee);
    }

    void removeEmployeeInternal(Employee employee) {
        for (Iterator<Employee> it = employees.iterator(); it.hasNext();) {
            if (it.next() == employee) {
                it.remove();
                return;
            }
        }
    }
}
~~~

### 4.2. Employee hoàn chỉnh

~~~java
package com.example.company;

import jakarta.persistence.*;

@Entity
@Table(name = "employees")
public class Employee {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "full_name", nullable = false, length = 120)
    private String fullName;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "department_id")
    private Department department;

    protected Employee() { }

    public Employee(String fullName) {
        if (fullName == null || fullName.isBlank()) {
            throw new IllegalArgumentException("Tên nhân viên không được trống");
        }
        this.fullName = fullName;
    }

    public Long getId() { return id; }
    public String getFullName() { return fullName; }
    public Department getDepartment() { return department; }

    public void moveTo(Department target) {
        if (department == target) {
            // Gọi lặp lại không thêm trùng vào collection.
            if (target != null) {
                target.addEmployeeInternal(this);
            }
            return;
        }

        Department oldDepartment = department;

        if (oldDepartment != null) {
            oldDepartment.removeEmployeeInternal(this);
        }

        // Đây là phía JPA sở hữu khóa ngoại department_id.
        department = target;

        if (target != null) {
            target.addEmployeeInternal(this);
        }
    }
}
~~~

Các method nội bộ chỉ được gọi từ những entity trong cùng package. Ở ví dụ này **department_id** được phép null; vì vậy **moveTo(null)** có nghĩa nhân viên chưa được phân công. Khi nghiệp vụ bắt buộc mọi nhân viên có phòng ban, API phải từ chối null và schema cần **NOT NULL**.

Phương thức này hoạt động dựa trên **cùng một object graph/persistence context**, nơi một entity có ID được quản lý như một instance Java. Nó không nhằm hợp nhất các instance detached hoặc proxy từ nhiều EntityManager khác nhau.

### 4.3. Tại sao so sánh bằng == trong helper?

Trong một persistence context, JPA bảo đảm identity: khi một entity đang managed được yêu cầu lại theo cùng loại và ID, provider sử dụng managed instance tương ứng. Vì thế so sánh reference **==** trong ví dụ là lựa chọn rõ ràng cho việc đồng bộ các collection đang thuộc cùng graph.

Nếu dùng **List.contains** hoặc **List.remove(Object)**, kết quả phụ thuộc vào **equals/hashCode** của entity. Với ID được sinh sau persist, proxy, detached instance hoặc Lombok sinh equality theo toàn bộ quan hệ, triển khai sai có thể dẫn đến hành vi bất ngờ. Helper dùng **==** ở đây không phải giải pháp chung cho graph gồm object từ nhiều context; nó là quy ước áp dụng khi transaction nạp/điều phối các managed instance một cách nhất quán.

### 4.4. Vì sao không gọi helper qua lại?

Một kiểu cài đặt dễ gây **StackOverflowError**:

~~~java
// Department:
public void addEmployee(Employee employee) {
    employees.add(employee);
    employee.setDepartment(this);
}

// Employee:
public void setDepartment(Department department) {
    this.department = department;
    department.addEmployee(this);
}
~~~

Mỗi method gọi lại method bên kia, không có điểm dừng. Cách an toàn là **một method điều phối toàn bộ**, method nội bộ còn lại chỉ cập nhật một collection hoặc reference và không gọi đệ quy.

## 5. Lưu một quan hệ hai chiều trong transaction

### 5.1. Lưu tường minh hai entity mới, không cascade

Với mapping Department–Employee đã khai báo, **chưa có cascade**. Trong ứng dụng JPA tự quản lý resource-local transaction:

~~~java
EntityTransaction tx = em.getTransaction();

try {
    tx.begin();

    Department engineering = new Department("Engineering");
    Employee an = new Employee("An");
    engineering.addEmployee(an);

    em.persist(engineering);
    em.persist(an);

    tx.commit();
} catch (RuntimeException ex) {
    if (tx.isActive()) {
        tx.rollback();
    }
    throw ex;
}
~~~

**EntityManager** được tạo và đóng trong lifecycle của caller; đoạn này chỉ minh họa một transaction trên EntityManager resource-local. Với EntityManager do container/JTA quản lý, không gọi **getTransaction()** để tự điều khiển.

Về mặt dữ liệu, provider sẽ lưu Department, lấy ID tương ứng rồi lưu Employee với **department_id** trỏ về Department:

~~~sql
INSERT INTO departments (name)
VALUES ('Engineering');

INSERT INTO employees (full_name, department_id)
VALUES ('An', 1);
~~~

Hai câu SQL là minh họa; thứ tự, cách lấy ID, số lần flush và cột được ghi có thể khác theo JPA provider, chiến lược tạo khóa và schema. Điều không đổi là **Employee.department** quyết định giá trị foreign key.

### 5.2. Vì sao em.persist(parent) không mặc định lưu child?

**@OneToMany** xác định quan hệ, không tự bao gồm **CascadeType.PERSIST**. Khi chỉ gọi:

~~~java
em.persist(engineering);
~~~

JPA sẽ persist Department. Một Employee transient nằm trong collection không mặc định tự được persist. Nếu muốn lan thao tác persist, cần cấu hình cascade phù hợp:

~~~java
@OneToMany(
    mappedBy = "department",
    cascade = CascadeType.PERSIST
)
private List<Employee> employees = new ArrayList<>();
~~~

Khi đó **em.persist(engineering)** có thể lan thao tác persist tới Employee nằm trong collection; tuy nhiên **cascade không thay thế việc gán owning side**. Cần gọi helper để Employee.department tham chiếu đúng parent.

Với Department–Employee, mỗi Employee thường có vòng đời độc lập, vì vậy nhiều dự án **không bật cascade REMOVE hoặc orphanRemoval** trên quan hệ này. Quyết định cascade phụ thuộc ownership nghiệp vụ, không chỉ cấu trúc SQL.

### 5.3. Thay đổi quan hệ khi entity đang managed

~~~java
Employee employee = em.find(Employee.class, 21L);
Department target = em.find(Department.class, 10L);

target.addEmployee(employee);
// Hai phía được đồng bộ trong RAM.
// Khi flush/commit, khóa ngoại được cập nhật từ Employee.department.
~~~

Nếu employee đang managed trong transaction, ORM có thể phát:

~~~sql
UPDATE employees
SET department_id = 10
WHERE id = 21;
~~~

Không nhất thiết gọi **em.merge(employee)** hoặc repository **save(employee)** lần nữa khi entity vẫn đang managed. JPA dùng **dirty checking** để phát hiện thay đổi và đồng bộ khi flush. Với detached entity, tình huống khác và cần transaction mới, load hoặc merge theo quy tắc thích hợp.

### 5.4. Flush không phải commit

**Flush** gửi SQL thay đổi đang chờ tới database trong transaction, trong khi **commit** kết thúc transaction thành công. Sau khi helper chạy, object graph đã đổi ngay trong Java; SQL có thể chưa được gửi, và thay đổi chưa chắc được commit. Rollback hủy thay đổi dữ liệu của transaction, nhưng không tự hoàn nguyên từng field Java trong object đang giữ.

~~~text
addEmployee()
    ↓
Employee.department + Department.employees thay đổi trong RAM
    ↓
flush() → SQL UPDATE/INSERT được gửi
    ↓
commit() → transaction hoàn tất thành công

rollback → DB không giữ thay đổi chưa commit
           object Java không tự được đặt về trạng thái cũ.
~~~

## 6. Trường hợp chuyển nhân viên từ A sang B

Nếu ban đầu:

~~~text
Employee 21.department -> Department A
Department A.employees chứa Employee 21
Department B.employees chưa chứa Employee 21
~~~

Khi gọi:

~~~java
departmentB.addEmployee(employee21);
~~~

Helper xử lý theo thứ tự:

1. Xác định department cũ là A.
2. Xóa Employee 21 khỏi collection của A.
3. Gán Employee 21.department = B; đây là phía sở hữu khóa ngoại.
4. Thêm Employee 21 vào collection của B, không để trùng reference.

Kết quả trong RAM:

~~~text
Employee 21.department -> Department B
Department A.employees không còn Employee 21
Department B.employees chứa Employee 21
~~~

SQL thông thường chỉ cần:

~~~sql
UPDATE employees
SET department_id = :department_b_id
WHERE id = :employee_id;
~~~

Không cần xóa rồi tạo lại Employee. Nếu đối tượng có các quan hệ khác hoặc lịch sử công tác, chúng vẫn được bảo toàn theo mô hình.

### 6.1. Trường hợp không còn phòng ban

~~~java
departmentB.removeEmployee(employee21);
~~~

Nếu **department_id** nullable và không có orphanRemoval, helper chuyển owning reference về null và xóa khỏi collection; Employee vẫn tồn tại:

~~~sql
UPDATE employees
SET department_id = NULL
WHERE id = :employee_id;
~~~

Nếu database dùng **department_id NOT NULL**, thao tác này sẽ vi phạm ràng buộc. Khi ấy không nên thiết kế **removeEmployee** như “bỏ phân công”; thay bằng **transferTo(requiredTarget)**, xóa nhân viên theo nghiệp vụ, hoặc cơ chế riêng phù hợp.

### 6.2. Trạng thái bên ngoài persistence context

Không nên lấy Employee từ EntityManager A và Department từ EntityManager B rồi mặc nhiên điều phối như một graph duy nhất:

~~~java
Employee employee = emA.find(Employee.class, employeeId);
Department target = emB.find(Department.class, departmentId);

// Đây là graph trộn hai persistence context, không phải mô hình khuyến nghị.
employee.moveTo(target);
~~~

Việc so sánh reference, proxy, trạng thái detached/managed và cascade có thể khó đoán. Đối với request chuyển phòng, nên để service nạp cả hai managed entity trong cùng transaction/persistence context rồi gọi helper.

## 7. mappedBy và cascade: hai khái niệm độc lập

**mappedBy** xác định phía nào sở hữu relationship mapping; **cascade** xác định thao tác persistence nào được lan theo association.

| Cấu hình | Chức năng | Không có nghĩa |
|---|---|---|
| **mappedBy = "department"** | Department.employees là phía đối ứng của Employee.department | Không tự quản lý FK từ collection |
| **CascadeType.PERSIST** | Khi persist parent, có thể lan persist tới child | Không tự sửa child.department nếu field này sai |
| **CascadeType.MERGE** | Lan merge theo association | Không tự bảo đảm API domain và graph nhất quán |
| **CascadeType.REMOVE** | Khi remove parent, lan remove tới child | Không đồng nghĩa mọi lần remove khỏi collection đều xóa child |
| **CascadeType.ALL** | Gộp các loại cascade của JPA | Không tự bật orphanRemoval |
| **orphanRemoval = true** | Xóa child khi rời association sở hữu vòng đời theo semantics phù hợp | Không an toàn mặc định cho child có thể chuyển sang parent khác |

Điều dễ nhầm: **dù Department.employees là inverse side**, khai báo cascade trên collection này vẫn có thể lan thao tác persist/merge/remove tới các entity thành viên theo quy tắc lifecycle. Inverse side chỉ nói về ownership của **quan hệ FK**, không phủ nhận khả năng cấu hình cascade operation.

### 7.1. Ví dụ aggregate: Order–OrderLine

Trong một đơn hàng, từng dòng hàng thường phụ thuộc vòng đời đơn. Cấu hình có thể là:

~~~java
@Entity
@Table(name = "purchase_orders")
public class PurchaseOrder {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @OneToMany(
        mappedBy = "order",
        cascade = CascadeType.ALL,
        orphanRemoval = true
    )
    private List<OrderLine> lines = new ArrayList<>();

    protected PurchaseOrder() { }

    public void addLine(OrderLine line) {
        Objects.requireNonNull(line);
        if (line.getOrder() != null && line.getOrder() != this) {
            throw new IllegalStateException("Line đã thuộc đơn hàng khác");
        }
        for (OrderLine existing : lines) {
            if (existing == line) {
                return;
            }
        }
        lines.add(line);
        line.setOrderInternal(this);
    }

    public void removeLine(OrderLine line) {
        Objects.requireNonNull(line);
        for (Iterator<OrderLine> it = lines.iterator(); it.hasNext();) {
            if (it.next() == line) {
                it.remove();
                line.setOrderInternal(null);
                return;
            }
        }
    }
}
~~~

~~~java
@Entity
@Table(name = "order_lines")
public class OrderLine {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "sku", nullable = false)
    private String sku;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "order_id", nullable = false)
    private PurchaseOrder order;

    protected OrderLine() { }

    public OrderLine(String sku) {
        this.sku = Objects.requireNonNull(sku);
    }

    public PurchaseOrder getOrder() { return order; }

    void setOrderInternal(PurchaseOrder order) {
        this.order = order;
    }
}
~~~

Các snippet minh họa dùng import **jakarta.persistence.***, **java.util.ArrayList**, **Iterator**, **List** và **Objects** phù hợp. Điểm chính là **PurchaseOrder.lines** dùng **mappedBy = "order"**, còn **OrderLine.order** là owning side lưu cột **order_id**. Khi **em.persist(order)**, cascade có thể persist các OrderLine đã được add qua helper; khi xóa line khỏi collection của order đang managed, **orphanRemoval=true** yêu cầu xóa line theo vòng đời.

Không xem **orphanRemoval** là cách bỏ phân công rồi chuyển child sang một parent khác. Nó phù hợp khi **child thực sự bị hủy khi rời owner**. Một entity đã trở thành orphan không nên được mặc nhiên “hồi sinh” bằng cách thêm sang parent khác trong cùng transaction; hãy thiết kế lại quan hệ hoặc tạo entity mới nếu nghiệp vụ đòi hỏi.

### 7.2. Xóa parent và ràng buộc FK

Với **Department–Employee** không có cascade REMOVE, xóa Department còn Employee tham chiếu có thể bị DB từ chối do FK. Ứng dụng cần quyết định rõ: không cho xóa phòng ban còn nhân viên, chuyển nhân viên sang nơi khác, hay xóa tất cả theo chính sách nghiệp vụ. Không thêm **CascadeType.REMOVE** tùy tiện để làm hết lỗi FK.

Với **Order–OrderLine**, xóa Order thường kéo theo xóa Lines theo vòng đời aggregate; **CascadeType.REMOVE** hoặc **CascadeType.ALL** có thể phù hợp. Cơ chế **ON DELETE CASCADE** ở database là một lựa chọn khác ở tầng SQL, không đồng nghĩa hoàn toàn với cascade của JPA và cần được thiết kế, migration, kiểm tra riêng.

## 8. FetchType và cách tải collection hai chiều

Theo mặc định JPA, **@OneToMany là LAZY**, còn **@ManyToOne là EAGER** trừ khi chỉ rõ. Trong mô hình hai hướng, nên chủ động quyết định chiến lược fetch cho mỗi use case:

~~~java
@OneToMany(mappedBy = "department", fetch = FetchType.LAZY)
private List<Employee> employees = new ArrayList<>();
~~~

Khi tìm Department:

~~~java
Department department = em.find(Department.class, 10L);
~~~

Provider có thể chỉ query bảng Department trước. Khi truy cập:

~~~java
int count = department.getEmployees().size();
~~~

một query khác có thể được thực thi để load collection (hoặc tối ưu riêng của provider). Không được kết luận chỉ dựa trên Java getter rằng truy cập collection hoàn toàn không tốn SQL.

### 8.1. N+1 query khi duyệt nhiều parent

~~~java
List<Department> departments = em.createQuery(
    "select d from Department d", Department.class
).getResultList();

for (Department d : departments) {
    System.out.println(d.getName() + ": " + d.getEmployees().size());
}
~~~

Nếu provider tải mỗi collection bằng query riêng, có thể phát sinh **1 query cho danh sách phòng ban + N query cho nhân viên**. Đây là vấn đề N+1. Số statement thực tế phụ thuộc provider, cache, batch fetch và dữ liệu.

Khi màn hình cần thông tin Department kèm Employee, có thể dùng fetch join theo trường hợp:

~~~java
List<Department> departments = em.createQuery(
    """
    select distinct d
    from Department d
    left join fetch d.employees
    where d.id in :ids
    """,
    Department.class
).setParameter("ids", departmentIds)
 .getResultList();
~~~

**LEFT JOIN FETCH** yêu cầu tải collection trong cùng truy vấn, và SQL có thể trả nhiều dòng cho cùng Department. **DISTINCT** trong JPQL giúp diễn đạt mục đích trả các parent duy nhất; cách loại trùng và việc truyền DISTINCT xuống SQL phụ thuộc provider/version. Không lạm dụng fetch join với nhiều collection lớn.

### 8.2. Vì sao fetch join collection và pagination khó kết hợp?

SQL join một Department với 100 Employee tạo 100 dòng trung gian. Nếu áp dụng **LIMIT 20** lên các dòng đã join, có thể lấy thiếu phần tử hoặc phân trang theo dòng thay vì theo Department. Một số provider cảnh báo hoặc phải phân trang trong bộ nhớ khi fetch join collection.

Khi cần phân trang parent, thường nên:

1. Query trang ID Department bằng thứ tự ổn định;
2. Query dữ liệu liên quan cho tập ID của trang, bằng fetch join có kiểm soát, entity graph hoặc batch fetch;
3. Giữ nguyên thứ tự trang ở tầng ứng dụng nếu cần.

Đối với màn hình chỉ cần **số nhân viên**, dùng **COUNT** trong SQL/JPQL projection thường rẻ hơn load tất cả Employee vào một List.

### 8.3. LazyInitializationException

Trong Hibernate, nếu collection vẫn lazy và persistence context đã đóng, truy cập ngoài transaction/session phù hợp có thể ném **LazyInitializationException**:

~~~java
Department department = repository.findById(id).orElseThrow();
// Sau khi transaction/persistence context cần thiết đã kết thúc:
department.getEmployees().size(); // Có thể lỗi lazy loading.
~~~

Giải pháp là quyết định dữ liệu cần trả ngay tại service/query, dùng DTO/projection hoặc fetch plan đúng use case. Không bật EAGER cho tất cả relation chỉ để né lỗi và tạo nhiều query không kiểm soát.

## 9. List, Set, thứ tự và equals/hashCode

### 9.1. Có thể dùng List hay Set?

JPA hỗ trợ mapping collection bằng **List**, **Set** và các kiểu collection phù hợp. Lựa chọn phụ thuộc nghiệp vụ:

| Collection | Phù hợp khi | Cần lưu ý |
|---|---|---|
| **List<Employee>** | Muốn biểu diễn danh sách, có thể xử lý thứ tự riêng | Dễ có phần tử trùng nếu helper không kiểm soát; thứ tự đọc từ DB không mặc định ổn định |
| **Set<Employee>** | Không muốn nhiều phần tử được xem là bằng nhau theo equality | Phụ thuộc equals/hashCode; generated ID dễ gây hashCode biến đổi |

Không nên dùng **Set** để che giấu việc thiếu helper. Định nghĩa bất biến và xử lý một nguồn ghi quan hệ rõ ràng vẫn quan trọng. Với entity mutable có ID sinh sau insert, dùng **HashSet** đòi hỏi chiến lược equality/hashCode phù hợp với vòng đời và proxy của ORM.

### 9.2. @OrderBy và @OrderColumn khác nhau

Nếu muốn đọc nhân viên theo tên:

~~~java
@OneToMany(mappedBy = "department")
@OrderBy("fullName ASC")
private List<Employee> employees = new ArrayList<>();
~~~

**@OrderBy** yêu cầu sắp xếp khi tải collection theo thuộc tính được mapping (ở đây **fullName**); nó không tự tạo cột thứ tự.

Nếu nghiệp vụ cần một thứ tự do người dùng kéo thả và lưu lại, **@OrderColumn** là một cơ chế lưu vị trí vào cột database. Việc dùng order column trong mapping hai chiều cần cấu hình đúng ownership và schema, đồng thời chấp nhận chi phí cập nhật index của phần tử khi reorder. Không kết luận rằng List theo thứ tự INSERT hoặc theo ID nếu không có cơ chế sắp xếp rõ ràng.

### 9.3. Không đưa relation vào equals/hashCode hoặc toString tùy tiện

Hai chiều làm object graph có chu kỳ:

~~~text
Department.toString()
    -> employees.toString()
         -> Employee.toString()
              -> department.toString()
                   -> ...
~~~

Sử dụng Lombok **@Data** hoặc sinh equals/hashCode dựa vào tất cả field của entity có thể tạo đệ quy vô hạn, truy cập lazy bất ngờ và gây lỗi với Set. Với entity, hãy thiết kế equality có chủ đích dựa trên ID đã ổn định hoặc business key thực sự bất biến, đồng thời tránh để relationship collection là một phần của equality.

## 10. mappedBy không quyết định ràng buộc dữ liệu

Một điều dễ nhầm:

~~~java
@OneToMany(mappedBy = "department")
private List<Employee> employees;
~~~

không bảo đảm Employee có department, không cấm hai Employee trỏ cùng department và không tạo uniqueness trên department_id. Cần hiểu bản chất **one-to-many** là **nhiều Employee được phép chia sẻ cùng một giá trị department_id**.

### 10.1. Quan hệ bắt buộc

Nếu mọi Employee phải thuộc một Department:

~~~java
@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "department_id", nullable = false)
private Department department;
~~~

Và schema:

~~~sql
ALTER TABLE employees
    ALTER COLUMN department_id SET NOT NULL;
~~~

Metadata JPA như **optional=false** và **nullable=false** có thể được sử dụng để mô tả model/sinh DDL, nhưng constraint thật ở database mới bảo vệ dữ liệu do mọi client ghi. API helper phải điều chỉnh: không cho chuyển thành null, chỉ chuyển sang Department khác hoặc xóa Employee theo nghiệp vụ.

### 10.2. Chỉ cần unique khi quan hệ không còn là 1–N

Nếu đặt **UNIQUE(employees.department_id)**, mỗi Department chỉ có thể được một Employee tham chiếu (tùy semantics null), tức không còn mô hình “nhiều nhân viên mỗi phòng ban”. Không thêm UNIQUE cho cột foreign key chỉ vì nghĩ rằng “FK nên unique”.

### 10.3. Index trên FK

Query “nhân viên thuộc phòng ban X” dùng:

~~~sql
SELECT id, full_name
FROM employees
WHERE department_id = 10;
~~~

Index trên **employees.department_id** có thể hữu ích khi bảng lớn và tần suất lọc/join đáng kể. Không phải hệ quản trị nào tự tạo index cho mọi FK, nên cần chủ động kiểm tra kế hoạch thực thi và metadata DB. Index có chi phí lưu trữ và cập nhật; cân nhắc theo workload thực tế.

## 11. JPQL và Criteria với quan hệ mappedBy

### 11.1. Từ phía nhiều tìm theo parent

~~~java
List<Employee> employees = em.createQuery(
    """
    select e
    from Employee e
    where e.department.id = :departmentId
    order by e.fullName asc
    """,
    Employee.class
).setParameter("departmentId", 10L)
 .getResultList();
~~~

JPQL dùng **thuộc tính Java** là **e.department**, không dùng **employees.department_id**. Provider chuyển biểu thức sang SQL phù hợp; tùy query, có thể tận dụng FK mà không cần join bảng Department chỉ để lọc theo ID.

### 11.2. Từ phía một duyệt sang phía nhiều

~~~java
List<Department> departments = em.createQuery(
    """
    select distinct d
    from Department d
    join d.employees e
    where e.fullName like :prefix
    """,
    Department.class
).setParameter("prefix", "An%")
 .getResultList();
~~~

**d.employees** là tên thuộc tính collection Java. JPA biết join đến bảng employees vì collection dùng mappedBy trỏ tới Employee.department.

### 11.3. Đếm thay vì tải toàn bộ collection

~~~java
Long employeeCount = em.createQuery(
    """
    select count(e)
    from Employee e
    where e.department.id = :departmentId
    """,
    Long.class
).setParameter("departmentId", 10L)
 .getSingleResult();
~~~

Số hàng này là dữ liệu quan sát theo transaction và isolation hiện tại. Nếu nghiệp vụ cần giới hạn sức chứa Department khi nhiều request cùng phân công, chỉ chạy COUNT trước rồi thêm Employee có thể gặp race condition; cần cơ chế transaction/khóa hoặc thao tác nguyên tử phù hợp.

### 11.4. Criteria API

~~~java
CriteriaBuilder cb = em.getCriteriaBuilder();
CriteriaQuery<Employee> cq = cb.createQuery(Employee.class);
Root<Employee> employee = cq.from(Employee.class);

cq.select(employee).where(
    cb.equal(employee.get("department").get("id"), 10L)
);

List<Employee> result = em.createQuery(cq).getResultList();
~~~

Các type cần import từ **jakarta.persistence.criteria**. Với static metamodel, có thể cải thiện khả năng kiểm tra kiểu khi refactor. Logic vẫn dựa vào đường dẫn thuộc tính JPA như trong JPQL.

## 12. So sánh ba cách biểu diễn one-to-many

Trong thiết kế JPA có nhiều lựa chọn cho quan hệ một–nhiều. Cần hiểu sự khác nhau để không ngộ nhận mappedBy:

| Kiểu mapping | Java | Nơi lưu liên kết | Điểm cần chú ý |
|---|---|---|---|
| **Chỉ @ManyToOne một hướng** | Employee.department | FK employees.department_id | Gọn nếu chỉ cần truy cập child → parent |
| **@OneToMany một hướng** | Department.employees, Employee không có department | Có thể dùng bảng nối mặc định, hoặc FK theo mapping rõ | Dễ khác schema/SQL so với dự kiến nếu không chỉ rõ |
| **Hai hướng @OneToMany(mappedBy)/@ManyToOne** | Department.employees và Employee.department | FK employees.department_id do Employee mapping | Truy cập hai chiều, cần đồng bộ object graph |

Với bidirectional mapping, **mappedBy** biểu thị cả hai thuộc tính trỏ tới **cùng một association**. Không phải hai mapping độc lập được tự “ghép” bằng tên cột tương tự.

### 12.1. Khi nào không nên khai báo hai hướng?

Không phải lúc nào có FK cũng cần Department.employees. Nếu phòng ban có hàng triệu nhân viên và nghiệp vụ chỉ truy vấn từng trang qua repository, collection hai chiều có thể tạo chi phí và rủi ro truy cập lazy không cần thiết.

Sử dụng:

~~~java
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "department_id")
private Department department;
~~~

và repository query theo department ID có thể đơn giản hơn. Một thiết kế Java không cần mô phỏng mọi chiều truy vấn có thể viết được trong SQL; chỉ mapping những hướng phục vụ use case thực tế.

## 13. Những bẫy khi tích hợp với Spring Data JPA

Spring Data JPA không thay đổi khái niệm owning side của JPA. Nếu một repository lưu Department, không có nghĩa mọi Employee trong collection được cập nhật FK khi phía Employee.department không đúng.

### 13.1. Ví dụ service chuyển phòng ban

~~~java
@Service
public class DepartmentAssignmentService {
    private final EmployeeRepository employees;
    private final DepartmentRepository departments;

    public DepartmentAssignmentService(
            EmployeeRepository employees,
            DepartmentRepository departments) {
        this.employees = employees;
        this.departments = departments;
    }

    @Transactional
    public void assign(long employeeId, long departmentId) {
        Employee employee = employees.findById(employeeId)
            .orElseThrow(() -> new IllegalArgumentException("Employee không tồn tại"));

        Department target = departments.findById(departmentId)
            .orElseThrow(() -> new IllegalArgumentException("Department không tồn tại"));

        // Kiểm tra quy tắc quyền hoặc sức chứa ở đây khi cần.
        target.addEmployee(employee);
    }
}
~~~

Ví dụ giả định hai repository kế thừa **JpaRepository** tương ứng; các annotation **@Service** và **@Transactional** thuộc Spring, không phải JPA chuẩn. Trong transaction, Employee managed được dirty checking; không cần gọi thêm save chỉ để ghi thay đổi FK.

### 13.2. Không bind trực tiếp JSON vào graph entity phức tạp

Ví dụ payload:

~~~json
{
  "departmentId": 10,
  "employeeId": 21
}
~~~

Service nên nhận DTO và nạp managed entities bằng ID rồi gọi helper. Trả entity có quan hệ hai chiều trực tiếp qua JSON serializer có thể gây:

- Chu kỳ lặp Department → employees → department → ...;
- Tải lazy collection ngoài ý muốn;
- Dữ liệu trả về quá lớn hoặc làm lộ các field không chủ định;
- Trạng thái detached bị merge từ toàn bộ payload mà thiếu kiểm soát, nhất là khi có cascade/orphanRemoval.

Sử dụng DTO/projection để thể hiện chính xác dữ liệu API cần trả, ví dụ **EmployeeResponse(id, fullName, departmentId)**.

### 13.3. Transactional self-invocation

Trong cấu hình Spring proxy thông dụng, gọi một method **@Transactional** từ method khác **trên chính cùng object** có thể không đi qua proxy, khiến advice không được áp dụng như mong đợi. Đặt transaction boundary tại public service được gọi qua Spring bean, hoặc sử dụng cơ chế transaction được cấu hình đúng theo framework.

Đừng đặt việc mở/commit transaction vào helper thuần domain trên entity; helper nên chỉ chịu trách nhiệm trạng thái và bất biến object graph.

## 14. Cạnh tranh cập nhật: helper không thay thế locking

Hai request có thể đồng thời đọc Employee 21 và chuyển tới hai phòng ban khác nhau:

~~~text
T1: đọc Employee 21 đang ở Department A
T2: đọc Employee 21 đang ở Department A
T1: moveTo(B), flush
T2: moveTo(C), flush
~~~

Nếu không có biện pháp phát hiện xung đột, dữ liệu commit cuối có thể ghi đè quyết định trước đó theo isolation và database. Cả hai request đều gọi helper đúng, nhưng helper không thể thấy thay đổi chưa commit của transaction khác.

### 14.1. Optimistic locking bằng @Version

~~~java
@Version
private Long version;
~~~

Thêm field version vào Employee và migration tạo cột version phù hợp. Provider sẽ dùng version để phát hiện việc hai transaction sửa cùng một entity từ cùng phiên bản:

~~~sql
UPDATE employees
SET department_id = ?, version = ?
WHERE id = ? AND version = ?;
~~~

Nếu update không ảnh hưởng hàng nào vì version đã đổi, JPA có thể ném **OptimisticLockException** (hoặc exception framework tương ứng) lúc flush/commit. Ứng dụng quyết định thông báo xung đột hay retry **toàn bộ nghiệp vụ trong transaction mới**. Không tự động gửi lại cùng detached object mà bỏ qua quy tắc kiểm tra.

### 14.2. Bất biến trên cả collection

Nếu Department chỉ chứa tối đa 20 nhân viên, hai transaction có thể cùng thấy 19 người rồi mỗi bên thêm một Employee khác nhau. Version chỉ trên từng Employee chưa đủ vì họ cập nhật **hai hàng khác nhau**.

Giới hạn sức chứa có thể đòi hỏi khóa Department, điều kiện cập nhật nguyên tử trên một bộ đếm, transaction isolation thích hợp hoặc cấu trúc ràng buộc nghiệp vụ khác. **mappedBy** chỉ là metadata association, không áp dụng concurrency control cho cả collection.

## 15. Integration test xác nhận cả object graph và khóa ngoại

Một test chỉ kiểm tra hai reference trong RAM chứng minh helper chạy đúng ở Java, chưa chứng minh mapping có đúng ở DB hay không. Một test chỉ query database cũng chưa chứng minh object graph đang được dùng trong cùng transaction đã được đồng bộ trước flush.

Nên kiểm tra hai giai đoạn:

1. **Trước flush:** owning reference và inverse collection đúng.
2. **Sau flush + clear:** nạp lại entity từ database; FK phản ánh quan hệ đã được lưu.

### 15.1. Persist và nạp lại

~~~java
@Test
void persistsBidirectionalOneToMany() {
    Department department = new Department("Engineering");
    Employee employee = new Employee("An");

    department.addEmployee(employee);

    assertSame(department, employee.getDepartment());
    assertTrue(department.getEmployees().contains(employee));

    em.persist(department);
    em.persist(employee);
    em.flush();

    Long employeeId = employee.getId();
    Long departmentId = department.getId();
    em.clear();

    Employee reloaded = em.find(Employee.class, employeeId);
    assertEquals(departmentId, reloaded.getDepartment().getId());
}
~~~

Đây là ví dụ JUnit chạy trong test transaction đã cấu hình đúng EntityManager và database. **flush** gửi SQL, **clear** loại các managed instances để **find** nạp lại từ DB. Nếu test muốn kiểm tra visibility ngoài transaction, cần commit và query từ transaction khác, thay vì chỉ flush.

### 15.2. Chuyển từ Department A sang B

~~~java
@Test
void transferUpdatesBothSides() {
    Department a = new Department("A");
    Department b = new Department("B");
    Employee employee = new Employee("Lan");

    a.addEmployee(employee);
    b.addEmployee(employee);

    assertSame(b, employee.getDepartment());
    assertFalse(a.getEmployees().contains(employee));
    assertTrue(b.getEmployees().contains(employee));
    assertEquals(1, b.getEmployees().size());
}
~~~

Đoạn này test helper thuần Java. Integration test tương ứng nên lưu cả A/B/Employee, flush/clear, nạp lại, chuyển và tiếp tục flush/clear để xác nhận **employees.department_id** trỏ sang B.

### 15.3. Test những trường hợp khác

| Trường hợp | Điều cần xác minh |
|---|---|
| Thêm Employee mới | Employee.department trỏ đúng, Department.employees có phần tử |
| Gọi addEmployee hai lần | Không trùng trong List |
| Chuyển A → B | A không còn Employee, B có Employee, FK trỏ B |
| Bỏ phân công khi FK nullable | Employee còn tồn tại, department_id thành NULL |
| Bỏ phân công khi FK NOT NULL | API chặn trước hoặc DB từ chối nhất quán |
| Dùng cascade PERSIST | Persist parent lan child nhưng owning side vẫn được gán đúng |
| Dùng orphanRemoval | Bỏ child khỏi aggregate làm child bị xóa theo lifecycle |
| Truy vấn JPQL từ cả hai hướng | Kết quả đúng theo các cột/FK vật lý |
| Lazy loading | Dữ liệu được fetch trong transaction và không phát N+1 ngoài dự kiến |
| Cập nhật đồng thời | Version/locking xử lý xung đột theo thiết kế |

Khi kiểm chứng mapping thật, nên sử dụng cùng JPA provider và loại database dự kiến ở môi trường ứng dụng, đặc biệt nếu phụ thuộc vào generated key, constraint và SQL ordering.

## 16. Những lỗi mappedBy phổ biến

| Dấu hiệu hoặc lỗi | Nguyên nhân | Hướng xử lý |
|---|---|---|
| **mappedBy references an unknown property** | Chuỗi mappedBy không khớp field/getter được JPA mapping ở Employee | Đổi thành đúng tên Java **department** |
| **mappedBy reference an entity type không phù hợp** | Field chỉ tới loại entity khác hoặc mapping không tương thích | Kiểm tra loại của Employee.department và generics collection |
| ORM tạo bảng nối không mong muốn | Đã cấu hình hai mapping một hướng hoặc bỏ mappedBy | Dùng đúng cặp @OneToMany(mappedBy)/@ManyToOne |
| Collection có employee nhưng FK NULL | Chỉ sửa inverse collection | Gán owning side qua helper |
| DB có FK mới nhưng collection loaded vẫn cũ | Chỉ sửa Employee.department | Cập nhật collection Java hoặc refresh/load lại theo use case |
| Employee xuất hiện trong hai phòng ban trong RAM | Khi chuyển đã không xóa khỏi collection cũ | Viết moveTo nhận biết old parent |
| addEmployee gọi lặp làm List có bản sao | Không kiểm tra phần tử đã có | Helper idempotent, một đường điều phối |
| StackOverflowError | Hai setter/add method gọi qua lại | Method nội bộ chỉ cập nhật một phía |
| Persist parent không lưu child | Không có cascade PERSIST và chưa persist child | Persist child rõ ràng hoặc cấu hình cascade phù hợp |
| Xóa khỏi collection mà child vẫn còn DB | Không có orphanRemoval; child có vòng đời độc lập | Xác định ý nghĩa remove, cập nhật FK hoặc dùng orphanRemoval khi thích hợp |
| Xóa parent làm xóa child không mong muốn | Cascade REMOVE/ALL không phù hợp | Điều chỉnh cascade theo ownership nghiệp vụ |
| LazyInitializationException | Duyệt collection sau khi context đóng | Fetch plan/DTO trong transaction thích hợp |
| N+1 query | Lặp trên nhiều parent rồi truy cập lazy collection | Batch fetch, join fetch có kiểm soát hoặc projection |
| Lazy collection cực lớn gây chậm | Helper bắt buộc load toàn bộ danh sách | Xem xét mapping một hướng và query theo FK |
| JSON trả dữ liệu lặp vô hạn | Serialization duyệt hai phía | Dùng DTO hoặc cơ chế serialize theo use case |
| Entity Set hoạt động sai sau persist | equals/hashCode phụ thuộc ID mới sinh | Thiết kế equality/hashCode ổn định |

### 16.1. Tại sao không nên “chữa” bằng cách chỉ đổi cascade?

Nếu code chỉ thực hiện:

~~~java
department.getEmployees().add(employee);
~~~

việc thêm **cascade = CascadeType.ALL** không phải câu trả lời cho lỗi đồng bộ quan hệ. Cascade có thể khiến Employee được persist, nhưng vẫn không biến Department.employees thành owning side của FK. Phải cập nhật **Employee.department** đúng.

### 16.2. Tại sao không nên “chữa” bằng fetch EAGER?

Nếu collection trong RAM thiếu một Employee vừa được gán owning side, bật EAGER chỉ làm thay đổi thời điểm tải dữ liệu. Nó không thiết kế bất biến object graph cho các thao tác đang thực hiện, và có thể tạo thêm truy vấn lớn. Helper method mới là cách duy trì state của hai phía khi code thao tác trong cùng graph.

## 17. Bài tập thực hành

### Bài 1: Xác định owning side

Cho:

~~~java
@Entity
class Category {
    @Id Long id;
    @OneToMany(mappedBy = "category")
    List<Product> products = new ArrayList<>();
}

@Entity
class Product {
    @Id Long id;
    @ManyToOne
    @JoinColumn(name = "category_id")
    Category category;
}
~~~

Hãy trả lời:

1. Thuộc tính nào là owning side?
2. Tên cột FK vật lý là gì và nằm ở bảng nào?
3. Trong **mappedBy = "category"**, category là tên column hay Java property?
4. Nếu chỉ gọi **category.products.add(product)** thì FK chắc chắn được đổi chưa?

**Định hướng:** owning side là **Product.category**, cột FK thường là **products.category_id**; chuỗi mappedBy là tên property. Chỉ sửa collection inverse không đủ để yêu cầu provider đổi FK.

### Bài 2: Sửa đoạn code chỉ thay đổi một phía

~~~java
public void addProduct(Product product) {
    products.add(product);
}
~~~

Hãy viết lại thành helper:

- Từ chối product null;
- Không thêm trùng khi gọi lặp;
- Nếu product ở Category cũ thì loại khỏi collection cũ;
- Gán product.category = this thông qua method điều phối;
- Không tạo vòng gọi đệ quy.

Có thể áp dụng mô hình **Product.moveTo(Category)** tương tự **Employee.moveTo(Department)** ở phần 4.

### Bài 3: Phân biệt cascade và mappedBy

Với:

~~~java
@OneToMany(mappedBy = "order", cascade = CascadeType.PERSIST)
private List<OrderLine> lines = new ArrayList<>();
~~~

Service chỉ gọi:

~~~java
order.getLines().add(new OrderLine("SKU-1"));
em.persist(order);
~~~

Hãy giải thích vì sao code vẫn có thể lỗi FK hoặc lưu quan hệ không đúng nếu **OrderLine.order** còn null. Sau đó bổ sung **order.addLine(line)** để đảm bảo owning side đúng trước khi persist.

### Bài 4: Remove trong hai domain khác nhau

So sánh:

1. Department–Employee: Employee tồn tại độc lập, có thể chưa được phân công, **orphanRemoval=false**.
2. PurchaseOrder–OrderLine: Line chỉ tồn tại trong Order, **orphanRemoval=true**.

Nếu người dùng bấm nút “Loại khỏi danh sách”, phải sinh SQL UPDATE FK về NULL hay DELETE child ở từng domain? Giải thích vì sao không thể áp dụng cùng một cấu hình chỉ vì cả hai đều là one-to-many.

### Bài 5: N+1 với một màn hình danh sách

Màn hình hiển thị 50 Department và chỉ cần cột **employeeCount**. Code hiện tại dùng:

~~~java
for (Department d : departments) {
    result.add(new Row(d.getName(), d.getEmployees().size()));
}
~~~

Hãy đề xuất JPQL dùng **COUNT** và GROUP BY hoặc các projection thích hợp, để tránh tải toàn bộ collection. Nêu tình huống bạn vẫn cần fetch Employees thực sự, và vì sao fetch join collection không nên kết hợp phân trang parent một cách tùy tiện.

### Bài 6: Tìm lỗi trong chuỗi mappedBy

Giả sử **Employee** đổi tên thuộc tính:

~~~java
@ManyToOne
private Department assignedDepartment;
~~~

trong khi Department vẫn ghi:

~~~java
@OneToMany(mappedBy = "department")
private List<Employee> employees;
~~~

Hãy sửa **mappedBy = "assignedDepartment"**. Giải thích vì sao tên FK SQL có thể vẫn là **department_id**, dù tên Java property đổi.

### Bài 7: Kiểm chứng bằng flush/clear

Viết integration test:

1. Persist Department A, Department B và Employee đang thuộc A.
2. Flush/clear để rời các managed instances ban đầu.
3. Load lại Employee và B trong cùng EntityManager.
4. Gọi **B.addEmployee(employee)**.
5. Kiểm tra reference và hai collection trong RAM.
6. Flush/clear rồi load Employee từ DB.
7. Khẳng định **employee.department.id** bằng ID B và Employee không bị xóa/tạo lại.

Tại sao chỉ **assertSame(B, employee.getDepartment())** trước flush chưa đủ xác nhận quan hệ đã được lưu?

### Bài 8: Quan hệ bắt buộc và chuyển parent

Hệ thống quy định mọi OrderLine luôn thuộc một PurchaseOrder; FK **order_id NOT NULL**. Nghiệp vụ không cho chuyển một OrderLine sang Order khác.

Hãy đề xuất API **addLine** và **removeLine**, cấu hình **orphanRemoval**, cách từ chối chuyển line đã có parent, và migration cần thiết. Phân biệt giữa “xóa line khỏi order” với “đặt order_id thành NULL”.

## 18. Trình tự áp dụng trong dự án

Khi cần ánh xạ một quan hệ một–nhiều hai chiều, hãy thực hiện theo thứ tự tư duy:

1. **Xác định mô hình dữ liệu:** bảng parent, bảng child, khóa chính và khóa ngoại; xem child có thể không có parent hay không.
2. **Xác định nhu cầu duyệt hai hướng:** nếu chỉ cần child → parent, một @ManyToOne có thể đủ.
3. **Mapping owning side:** khai báo @ManyToOne và @JoinColumn ở child; xác định nullability và fetch strategy.
4. **Mapping inverse side:** khai báo @OneToMany(mappedBy = "tênPropertyChild") ở parent; không tạo thêm FK hoặc bảng nối.
5. **Thiết kế helper:** một đường điều phối cập nhật child.parent và parent.children; xử lý chuyển từ parent cũ, null và gọi lặp.
6. **Xác định lifecycle:** child độc lập hay phụ thuộc parent? Chọn cascade và orphanRemoval theo nghiệp vụ.
7. **Thiết kế database constraints:** FK, NOT NULL, index và các quy tắc toàn vẹn thực tế phải được migration tạo ra.
8. **Đặt transaction boundary:** thao tác trên managed entities trong cùng persistence context; xem xét @Version/locking khi có cập nhật đồng thời.
9. **Thiết kế query:** JPQL dùng property paths, chủ động xử lý LAZY, N+1 và pagination.
10. **Kiểm chứng dữ liệu:** test cả object graph trước flush và FK được nạp lại sau flush/clear.

Ghi nhớ ngắn:

~~~text
Employee.department
    = @ManyToOne + @JoinColumn
    = owning side ghi khóa ngoại.

Department.employees
    = @OneToMany(mappedBy = "department")
    = inverse side để duyệt và quản lý object graph.

department.addEmployee(employee)
    = phải đồng bộ cả hai phía Java.

cascade / orphanRemoval
    = quy tắc lan thao tác persistence và vòng đời child,
      không thay cho owning side hoặc helper.
~~~

**Kết luận:** **@OneToMany(mappedBy = "...")** là cách diễn đạt một collection ở phía đối ứng của quan hệ đã được sở hữu bởi **@ManyToOne** bên child. Hiểu đúng **mappedBy là tên thuộc tính Java**, cập nhật **owning side để JPA ghi FK**, đồng bộ **inverse collection bằng phương thức nghiệp vụ**, rồi kết hợp cascade, transaction, constraints và fetch hợp lý sẽ giúp quan hệ hai hướng nhất quán, dễ bảo trì và tránh các lỗi dữ liệu khó thấy khi chỉ kiểm tra trạng thái trong bộ nhớ.
