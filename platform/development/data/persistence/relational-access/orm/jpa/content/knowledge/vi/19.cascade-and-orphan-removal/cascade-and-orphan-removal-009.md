# Phân biệt bỏ đối tượng con khỏi quan hệ và gọi remove() trong JPA

## 1. Một thao tác “xóa dòng” nhưng có ba ý nghĩa khác nhau

Trong hệ thống sử dụng Jakarta Persistence (JPA), giả sử một **đơn hàng** có nhiều **dòng hàng**:

~~~text
PurchaseOrder #100
  ├── OrderLine #501: Bàn phím
  └── OrderLine #502: Chuột
~~~

Người dùng nhấn nút “Xóa dòng chuột”. Câu hỏi quan trọng là: **hệ thống cần xóa hẳn OrderLine #502 khỏi database, hay chỉ ngắt quan hệ giữa nó và PurchaseOrder #100?** Hai hành vi này có thể giống nhau trên giao diện nhưng có ngữ nghĩa dữ liệu khác nhau.

Trong JPA, cần tách ba cơ chế:

1. **Gỡ liên kết (disassociate/unlink):** loại một entity con khỏi quan hệ với entity cha, chẳng hạn xóa khỏi collection của cha và cập nhật tham chiếu chủ sở hữu quan hệ. Entity con vẫn có thể tồn tại trong database.
2. **Gọi EntityManager.remove(child):** yêu cầu chuyển **entity con đang được quản lý** sang trạng thái **removed**, để provider xóa hàng dữ liệu của entity đó khi đồng bộ transaction.
3. **orphanRemoval = true:** khi một entity con được quản lý bị loại khỏi quan hệ riêng tư của cha, provider áp dụng hành vi xóa orphan theo vòng đời quan hệ, thường dẫn đến DELETE khi flush, **mà ứng dụng không cần gọi remove(child) trực tiếp**.

Một cơ chế khác là **CascadeType.REMOVE**: khi gọi **remove(parent)**, thao tác remove được lan truyền sang những entity con theo mapping. Cascade REMOVE và orphanRemoval giải quyết **hai tình huống kích hoạt khác nhau**.

> **Nguyên tắc:** loại một phần tử khỏi collection Java **không mặc nhiên có nghĩa** xóa entity con khỏi database. Kết quả phụ thuộc **phía sở hữu quan hệ**, **orphanRemoval**, **cascade**, **nullability**, trạng thái entity và thời điểm flush.

## 2. Mô hình dữ liệu minh họa

Ta dùng quan hệ **một-nhiều hai hướng**:

~~~text
Java object graph

PurchaseOrder
    id=100
    lines [OrderLine #501, OrderLine #502]
                   |               |
                   +--- order -----+----> PurchaseOrder #100

Database

purchase_orders                   purchase_order_lines
-----------------                 ---------------------
id (PK)       <------------------ order_id (FK)
order_number                      id (PK)
                                  sku
                                  quantity
~~~

Ở Java, hai phía cùng điều hướng tới nhau:

- **PurchaseOrder.lines:** danh sách con, ánh xạ bằng **@OneToMany(mappedBy = "order")**.
- **OrderLine.order:** tham chiếu từ con về cha, ánh xạ bằng **@ManyToOne** và thường là **phía sở hữu khóa ngoại**.
- **order_id:** cột vật lý nằm trong bảng con.

Sơ đồ SQL ban đầu cho phép dòng hàng tồn tại mà chưa thuộc đơn hàng:

~~~sql
-- Ví dụ cú pháp PostgreSQL.
CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_number VARCHAR(50) NOT NULL UNIQUE
);

CREATE TABLE purchase_order_lines (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    sku VARCHAR(80) NOT NULL,
    quantity INTEGER NOT NULL CHECK (quantity > 0),
    order_id BIGINT NULL,
    CONSTRAINT fk_order_line_order
        FOREIGN KEY (order_id) REFERENCES purchase_orders(id)
);
~~~

Vì **order_id cho phép NULL**, một OrderLine có thể tồn tại trong database dù không còn liên kết với PurchaseOrder. Điều này giúp minh họa sự khác biệt giữa **UPDATE order_id = NULL** và **DELETE hàng OrderLine**.

Nếu nghiệp vụ quy định một dòng hàng *không bao giờ* được tồn tại độc lập, có thể yêu cầu order_id NOT NULL và dùng **orphanRemoval** hoặc xóa con có chủ đích. Khi ấy, việc đơn thuần gỡ quan hệ mà giữ hàng con có thể vi phạm constraint.

## 3. Entity ví dụ với orphanRemoval = false

Trước tiên, xem trường hợp **gỡ quan hệ không tự xóa con**.

### 3.1. Entity PurchaseOrder

~~~java
package com.example.orders;

import jakarta.persistence.CascadeType;
import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.OneToMany;
import jakarta.persistence.Table;
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

@Entity
@Table(name = "purchase_orders")
public class PurchaseOrder {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "order_number", nullable = false, unique = true)
    private String orderNumber;

    @OneToMany(
        mappedBy = "order",
        cascade = {CascadeType.PERSIST, CascadeType.MERGE},
        orphanRemoval = false
    )
    private List<OrderLine> lines = new ArrayList<>();

    protected PurchaseOrder() {}

    public PurchaseOrder(String orderNumber) {
        this.orderNumber = orderNumber;
    }

    public Long getId() { return id; }

    public List<OrderLine> getLines() {
        return Collections.unmodifiableList(lines);
    }

    public void addLine(OrderLine line) {
        if (line == null) {
            throw new IllegalArgumentException("Line must not be null");
        }
        if (line.getOrder() != null && line.getOrder() != this) {
            throw new IllegalStateException("Line belongs to another order");
        }
        if (!lines.contains(line)) {
            lines.add(line);
        }
        line.assignTo(this);
    }

    public boolean unlinkLine(OrderLine line) {
        if (lines.remove(line)) {
            line.assignTo(null);
            return true;
        }
        return false;
    }
}
~~~

Ở đây:

- **mappedBy = "order"** nói rằng quan hệ do trường OrderLine.order sở hữu.
- **CascadeType.PERSIST** giúp tạo đơn và các dòng mới cùng lúc; **CascadeType.MERGE** có thể lan truyền merge khi cần.
- **Không có CascadeType.REMOVE**, và **orphanRemoval = false**: gỡ một dòng khỏi quan hệ **không tự yêu cầu xóa hàng con**.
- **getLines()** trả unmodifiable view để client dùng helper, tránh thao tác trực tiếp chỉ một phía.

### 3.2. Entity OrderLine

~~~java
package com.example.orders;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.FetchType;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.JoinColumn;
import jakarta.persistence.ManyToOne;
import jakarta.persistence.Table;

@Entity
@Table(name = "purchase_order_lines")
public class OrderLine {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "sku", nullable = false, length = 80)
    private String sku;

    @Column(name = "quantity", nullable = false)
    private int quantity;

    @ManyToOne(fetch = FetchType.LAZY, optional = true)
    @JoinColumn(name = "order_id", nullable = true)
    private PurchaseOrder order;

    protected OrderLine() {}

    public OrderLine(String sku, int quantity) {
        if (sku == null || sku.isBlank() || quantity <= 0) {
            throw new IllegalArgumentException("Invalid order line");
        }
        this.sku = sku;
        this.quantity = quantity;
    }

    public Long getId() { return id; }
    public String getSku() { return sku; }
    public int getQuantity() { return quantity; }
    public PurchaseOrder getOrder() { return order; }

    void assignTo(PurchaseOrder order) {
        this.order = order;
    }
}
~~~

Ví dụ dùng Java 11+ do có **String.isBlank()**. Hai class này minh họa một mapping nhất quán với DDL cho phép **order_id NULL**. Những phần sau có phương án **orphanRemoval=true** và **order_id NOT NULL** là **biến thể thay thế**, không cấu hình lẫn nhau trong cùng schema khi chưa điều chỉnh mapping.

### 3.3. Khởi tạo đối tượng với cả hai chiều nhất quán

~~~java
PurchaseOrder order = new PurchaseOrder("PO-2026-001");
OrderLine keyboard = new OrderLine("KB-01", 1);
OrderLine mouse = new OrderLine("MS-01", 2);

order.addLine(keyboard);
order.addLine(mouse);

System.out.println(order.getLines().size());    // 2
System.out.println(mouse.getOrder() == order);   // true
~~~

Một quan hệ hai hướng không tự đồng bộ mọi thao tác Java giữa hai field. Helper **addLine()** đặt cả dòng vào collection và cập nhật reference sở hữu FK. Tương tự, helper **unlinkLine()** phải cập nhật cả hai phía.

## 4. Chỉ bỏ khỏi List: chuyện gì xảy ra?

Giả sử sau khi đọc từ DB, PurchaseOrder và OrderLine đều là **managed entities** trong cùng persistence context:

~~~java
PurchaseOrder order = em.find(PurchaseOrder.class, 100L);
OrderLine mouse = em.find(OrderLine.class, 502L);

order.unlinkLine(mouse);
~~~

Kết quả ngay trong bộ nhớ:

~~~text
Trước:
  order.lines  = [#501, #502]
  mouse.order  = order #100

Sau unlinkLine(mouse):
  order.lines  = [#501]
  mouse.order  = null
~~~

Với mapping **orphanRemoval=false** và FK nullable, một provider có thể phát SQL tương đương khi flush:

~~~sql
UPDATE purchase_order_lines
SET order_id = NULL
WHERE id = 502;
~~~

Sau transaction commit, OrderLine #502 **vẫn tồn tại**, chỉ không còn thuộc PurchaseOrder #100.

**Không có** câu DELETE đối với OrderLine chỉ vì nó bị loại khỏi collection Java.

### 4.1. Cẩn thận với phía sở hữu quan hệ

Với mapping **@OneToMany(mappedBy = "order")**, collection ở cha là **phía nghịch đảo** (*inverse side*). **OrderLine.order** là phía sở hữu quan hệ và quyết định khóa ngoại.

Nếu chỉ làm:

~~~java
// Ví dụ sai về đồng bộ hai phía của object graph:
order.lines.remove(mouse); // Giả sử field có thể truy cập.
// mouse.order vẫn trỏ về order.
~~~

thì hai phía Java không nhất quán. Vì foreign key được ánh xạ qua OrderLine.order, ứng dụng **không nên kỳ vọng chỉ sửa collection nghịch đảo** sẽ khiến order_id được cập nhật như mong muốn. Tác động phụ thuộc mapping/provider; hãy cập nhật **phía sở hữu** qua helper.

Ngược lại, nếu chỉ làm:

~~~java
mouse.assignTo(null);
// Nhưng order.lines vẫn chứa mouse.
~~~

DB có thể cập nhật order_id theo phía sở hữu, song collection Java trong persistence context vẫn chứa một phần tử không còn thuộc cha. Các phép kiểm tra nghiệp vụ trước khi reload có thể sai.

**Thực hành nhất quán:** dùng helper thao tác cả collection và reference owning side trong một transaction.

### 4.2. Một câu hỏi về ý nghĩa domain

“Loại một học viên khỏi nhóm học” có thể nghĩa là học viên **vẫn tồn tại**, chỉ không còn thuộc nhóm đó. Khi ấy, **orphanRemoval=false** và FK nullable, hoặc mô hình quan hệ trung gian riêng, thường hợp lý hơn việc tự xóa Student khỏi database.

“Loại một dòng hàng khỏi đơn hàng” có thể nghĩa là dòng hàng **không còn danh tính hoặc giá trị độc lập** ngoài đơn hàng. Khi ấy, **orphanRemoval=true** thường hợp lý hơn.

Hai trường hợp cùng gọi một phép xóa phần tử trong collection Java nhưng có **semantics nghiệp vụ khác nhau**. Phải chọn mapping theo vòng đời thực thể con, không chỉ theo sự tiện lợi của code.

## 5. Gọi EntityManager.remove(child) khác gì?

**EntityManager.remove(entity)** là một thao tác **lifecycle** trên entity đang managed. Nó yêu cầu xóa chính entity đó khỏi cơ sở dữ liệu ở một điểm đồng bộ transaction.

~~~java
em.remove(mouse);
~~~

Khi flush, provider thường phát:

~~~sql
DELETE FROM purchase_order_lines
WHERE id = 502;
~~~

Đây là xóa **hàng dữ liệu OrderLine #502**, không chỉ đặt order_id về NULL. Các quan hệ tham chiếu, callback, FK, cascade và trạng thái managed khác đều có thể bị ảnh hưởng.

### 5.1. Điều kiện: đối tượng con phải đang managed

~~~java
OrderLine mouse = em.find(OrderLine.class, 502L);
em.remove(mouse);
~~~

**remove() yêu cầu entity đang managed.** Nếu mouse là detached entity được truyền từ request cũ, gọi **em.remove(mouse)** có thể ném **IllegalArgumentException**. Một hướng phổ biến là tìm entity managed bằng ID trong transaction rồi mới gọi remove:

~~~java
OrderLine managed = em.find(OrderLine.class, lineId);
if (managed != null) {
    em.remove(managed);
}
~~~

Không nên gọi merge(detached) chỉ với mục tiêu có thể remove mà không xem các field khác trên detached object: merge có thể sao chép trạng thái cũ hoặc không mong muốn sang entity managed. Đối với thao tác delete theo ID, thường an toàn hơn khi xác định đối tượng và quyền xóa ngay trong transaction hiện tại.

### 5.2. remove() chưa nhất thiết thực thi DELETE ngay

~~~java
tx.begin();

OrderLine line = em.find(OrderLine.class, 502L);
em.remove(line);

// Entity được chuyển sang trạng thái removed.
// DELETE có thể chưa chạy ở chính dòng em.remove().

em.flush();
// DELETE cần thiết đã được đồng bộ trong transaction.

tx.commit();
~~~

**remove() không phải commit()**. SQL DELETE có thể chạy ở flush hoặc trước commit, nhưng nếu transaction rollback thì hành vi xóa DML chưa commit được hoàn tác theo transaction semantics của DB.

### 5.3. remove() không tự sửa collection trong bộ nhớ

Nếu gọi **em.remove(mouse)** nhưng PurchaseOrder.lines vẫn chứa reference tới mouse, object graph Java có thể trở nên không nhất quán:

~~~text
order.lines = [#501, #502]   // collection vẫn chứa #502
mouse       = entity removed
~~~

Provider có thể phát DELETE đúng khi flush, nhưng code nghiệp vụ đang duyệt collection có thể vẫn thấy phần tử cũ. Vì thế khi child đang gắn với parent, nên cập nhật collection và hai phía association một cách nhất quán **ngoài việc** gọi remove().

Với mapping **orphanRemoval=false**, một service xóa riêng dòng hàng có thể:

~~~java
// Trong transaction; order và line đang managed:
PurchaseOrder order = line.getOrder();
if (order != null) {
    order.unlinkLine(line);
}
em.remove(line);
~~~

**Đừng hiểu thành hai lệnh SQL bắt buộc UPDATE order_id=NULL rồi DELETE.** Khi entity đã được đánh dấu removed, provider có thể tối ưu chỉ phát DELETE, tùy tình trạng flush và mapping. Nếu FK nullable=false hoặc có orphanRemoval=true, cần lựa chọn quy trình phù hợp thay vì sao chép công thức này vào mọi association.

### 5.4. remove() trên cha là một chuyện khác

~~~java
em.remove(order);
~~~

Lời gọi trên nhắm tới PurchaseOrder, không trực tiếp nhắm tới một dòng hàng cụ thể. Việc các OrderLine có bị xóa theo không phụ thuộc **cascade REMOVE**, **orphanRemoval**, FK database và mapping. Không nên cho rằng chỉ vì parent có collection thì xóa parent sẽ tự động xóa mọi child.

## 6. orphanRemoval = true: bỏ con khỏi quan hệ trở thành xóa con

Trong JPA, **orphanRemoval** được hỗ trợ trên **@OneToOne** và **@OneToMany**. Nó được thiết kế cho những target entity có vòng đời gắn với quan hệ sở hữu riêng tư (*privately owned*).

Thay đổi mapping ở PurchaseOrder thành:

~~~java
@OneToMany(
    mappedBy = "order",
    cascade = {CascadeType.PERSIST, CascadeType.MERGE},
    orphanRemoval = true
)
private List<OrderLine> lines = new ArrayList<>();
~~~

Giữ helper:

~~~java
public boolean removeLine(OrderLine line) {
    if (lines.remove(line)) {
        line.assignTo(null);
        return true;
    }
    return false;
}
~~~

Trong transaction:

~~~java
PurchaseOrder order = em.find(PurchaseOrder.class, orderId);
OrderLine line = em.find(OrderLine.class, lineId);

boolean removedFromOrder = order.removeLine(line);

// Không gọi em.remove(line) ở đây.
// Nếu line thực sự là target orphan được quản lý của quan hệ này,
// JPA sẽ xử lý xóa theo orphanRemoval tại flush.
~~~

Một SQL điển hình:

~~~sql
DELETE FROM purchase_order_lines
WHERE id = ?;
~~~

Chính **việc gỡ con khỏi quan hệ có orphanRemoval=true** là tác nhân kích hoạt xóa. Ứng dụng không cần thêm **em.remove(line)** để xóa cùng entity một lần nữa.

### 6.1. Bảng trạng thái trước và sau

| Bước | Collection của cha | Trạng thái database dự kiến sau commit |
|---|---|---|
| Ban đầu | [#501, #502] | Hai dòng còn tồn tại |
| Bỏ #502 khỏi quan hệ, orphanRemoval=false | [#501] | #502 vẫn tồn tại, có thể order_id=NULL |
| Bỏ #502 khỏi quan hệ, orphanRemoval=true | [#501] | #502 bị DELETE theo orphan-removal semantics |
| Gọi em.remove(#502) trực tiếp | Có thể vẫn chứa #502 nếu không cập nhật Java | #502 bị DELETE |
| Gọi em.remove(parent), cascade phù hợp | Parent được đánh dấu removed | Có thể DELETE cả parent và children |

**Lưu ý:** bảng trên mô tả các thay đổi được commit thành công với mapping/constraint thích hợp. Kết quả SQL và thứ tự statement không được JPA hứa hẹn giống nhau ở mọi provider.

### 6.2. Orphan removal xảy ra ở thời điểm nào?

Theo ngữ nghĩa JPA, thao tác remove trên orphan được áp dụng khi thực hiện **flush**. Không nên dựa vào việc gọi **order.removeLine(line)** để kết luận hàng đã biến mất ngay khỏi database hoặc EntityManager đã hoàn tất SQL DELETE.

~~~java
order.removeLine(line);
// Trạng thái Java đã đổi.

em.flush();
// Provider đồng bộ, có thể phát DELETE.

// Chưa commit: vẫn có thể rollback.
~~~

Provider có thể có cơ chế theo dõi collection riêng, sắp xếp DELETE và đồng bộ FK, nên không nên dựa vào số lượng câu SQL hay thứ tự cụ thể nếu chưa quan sát trên runtime thật.

### 6.3. Không cần CascadeType.REMOVE để xóa một orphan

Mapping này vẫn có khả năng xóa orphan:

~~~java
@OneToMany(mappedBy = "order", orphanRemoval = true)
private List<OrderLine> lines = new ArrayList<>();
~~~

**CascadeType.REMOVE không phải điều kiện để orphanRemoval hoạt động**. Orphan removal có quy tắc riêng khi child bị gỡ khỏi quan hệ. Ngoài ra, theo quy tắc JPA cho quan hệ orphanRemoval, khi remove được áp dụng lên source entity managed, thao tác remove cũng được lan truyền tới target phù hợp, nên không nhất thiết khai báo CascadeType.REMOVE riêng để xử lý vòng đời child cùng parent.

Điều này không có nghĩa nên bỏ mọi cascade khác. Nếu muốn persist một PurchaseOrder mới và các OrderLine mới bằng một lệnh persist(parent), có thể cần **CascadeType.PERSIST** hoặc thao tác persist riêng theo model. OrphanRemoval không thay thế CascadeType.PERSIST.

### 6.4. Tại sao thường dùng orphanRemoval với aggregate?

Một OrderLine đại diện **một dòng cụ thể của một đơn hàng**. Nếu xóa nó khỏi Order, thường không còn lý do giữ một bản ghi OrderLine “vô chủ”:

~~~text
PurchaseOrder (aggregate root)
  owns OrderLine #501
  owns OrderLine #502

removeLine(#502)
       |
       v
OrderLine #502 không còn thuộc aggregate
       |
       v
DELETE theo orphanRemoval
~~~

OrphanRemoval phù hợp khi mối quan hệ có **quyền sở hữu vòng đời độc quyền**. Nó không phù hợp nếu child là một entity được dùng chung, có thể chuyển giữa parent, hoặc cần giữ lâu dài dù rời khỏi parent.

## 7. CascadeType.REMOVE: kích hoạt từ việc remove(parent)

**CascadeType.REMOVE** có nghĩa thao tác remove được **lan truyền** qua association khi ứng dụng remove entity nguồn.

~~~java
@OneToMany(
    mappedBy = "order",
    cascade = CascadeType.REMOVE
)
private List<OrderLine> lines = new ArrayList<>();
~~~

Khi:

~~~java
em.remove(order);
~~~

provider có thể lan truyền remove tới OrderLine #501 và #502, rồi DELETE parent theo một thứ tự tương thích với các FK.

Nhưng nếu chỉ:

~~~java
order.unlinkLine(mouse);
// KHÔNG gọi em.remove(order).
~~~

**CascadeType.REMOVE không được kích hoạt chỉ vì gỡ mouse khỏi association.** Vì vậy một mapping chỉ có cascade=REMOVE, orphanRemoval=false **không tương đương** orphanRemoval=true.

### 7.1. CascadeType.ALL chứa REMOVE

~~~java
@OneToMany(
    mappedBy = "order",
    cascade = CascadeType.ALL,
    orphanRemoval = false
)
private List<OrderLine> lines = new ArrayList<>();
~~~

CascadeType.ALL bao gồm PERSIST, MERGE, REMOVE, REFRESH và DETACH. Với ví dụ này:

- **em.persist(order)** có thể cascade persist children.
- **em.remove(order)** có thể cascade remove children.
- **order.unlinkLine(mouse)** vẫn không tự xóa mouse, vì orphanRemoval=false.

Đây là chỗ nhiều lập trình viên nhầm: **CascadeType.ALL không có nghĩa mọi thao tác remove khỏi collection đều DELETE entity con.**

### 7.2. Ma trận kích hoạt

| Hành động | CascadeType.REMOVE | orphanRemoval=true |
|---|---|---|
| **remove(parent)** | Lan truyền remove sang child của quan hệ | Cũng hỗ trợ lan truyền remove target theo quy tắc orphan-removal |
| **Bỏ child khỏi quan hệ** | Không tự được kích hoạt | Xóa orphan khi flush nếu thỏa điều kiện |
| **persist(parent)** | Không cascade persist | Không tự thay thế cascade persist |
| **Đổi thuộc tính scalar của child** | Không tự xóa | Không tự xóa |
| **Đọc child qua find/query** | Không tự xóa | Không tự xóa |
| **Chuyển child sang parent khác** | Không mặc định xóa | Không nên dùng orphanRemoval cho reparenting |

### 7.3. Không tùy tiện đặt CascadeType.REMOVE lên @ManyToOne

Giả sử nhiều OrderLine cùng trỏ về PurchaseOrder:

~~~java
@ManyToOne(cascade = CascadeType.REMOVE)
private PurchaseOrder order;
~~~

Nếu xóa **một** OrderLine, REMOVE có thể lan tới **PurchaseOrder** mà những dòng hàng khác còn đang tham chiếu. Đây thường là điều không mong muốn và có thể bị FK chặn.

Đối với quan hệ parent–child, cascade vòng đời thông thường được đặt **từ cha xuống con** nếu cha sở hữu vòng đời con, không phải từ child lên parent chỉ vì có @ManyToOne.

## 8. Khóa ngoại NOT NULL làm sự khác biệt rõ hơn

Khi OrderLine bắt buộc thuộc một PurchaseOrder, schema thường:

~~~sql
CREATE TABLE purchase_order_lines (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    sku VARCHAR(80) NOT NULL,
    quantity INTEGER NOT NULL,
    order_id BIGINT NOT NULL REFERENCES purchase_orders(id)
);
~~~

Mapping child tương ứng:

~~~java
@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "order_id", nullable = false)
private PurchaseOrder order;
~~~

Nếu **orphanRemoval=false**, gỡ quan hệ bằng cách đặt **order=null** có thể khiến ORM thử:

~~~sql
UPDATE purchase_order_lines
SET order_id = NULL
WHERE id = ?;
~~~

và DB từ chối vì **NOT NULL constraint**. Trạng thái Java “không còn cha” không hợp lệ theo schema hiện tại.

Ba hướng xử lý tùy nghiệp vụ:

1. **Không cho phép gỡ độc lập:** chỉ cho phép child thuộc một parent, và khi bỏ khỏi parent thì xóa child bằng **orphanRemoval=true**.
2. **Xóa child tường minh:** nếu không dùng orphanRemoval, xác định entity managed rồi gọi **em.remove(child)** trong một transaction; đồng bộ collection trong bộ nhớ phù hợp.
3. **Chuyển child sang parent mới:** nếu business cho phép reparenting, cập nhật FK từ order cũ sang order mới mà không đi qua trạng thái NULL ở DB, với **orphanRemoval=false** và helper giữ hai phía nhất quán.

Nếu muốn child tồn tại độc lập, cần cho phép FK null hoặc thay đổi mô hình liên kết. **Không nên sửa constraint chỉ để làm một thao tác Java không có ý nghĩa domain trở nên hợp lệ.**

### 8.1. Có orphanRemoval=true thì xóa con có cần UPDATE NULL trước không?

Về **ngữ nghĩa**, child bị xóa khỏi database khi thành orphan. Provider có thể lập kế hoạch DELETE và xử lý association theo cách khác nhau. Không được khẳng định sẽ luôn thực hiện một UPDATE order_id=NULL trước rồi mới DELETE; SQL/statement ordering phụ thuộc mapping/provider.

Nếu gặp lỗi NOT NULL khi đã bật orphanRemoval, nên kiểm tra **cả hai phía quan hệ**, cách provider theo dõi collection và SQL thực tế. Không nên vội tắt FK constraint hoặc thêm thao tác SQL tùy tiện.

## 9. Mô hình nào phù hợp để chuyển con sang cha khác?

Một số entity con được phép đổi cha, ví dụ một **Ticket** chuyển từ một Project sang Project khác. Vòng đời Ticket độc lập: nó không bị xóa chỉ vì đổi Project.

Với **orphanRemoval=false**, thao tác reparent nên cập nhật:

~~~text
projectA.tickets: [ticketX]  -> []
projectB.tickets: []         -> [ticketX]
ticketX.project: projectA   -> projectB
~~~

Một helper minh họa:

~~~java
public void moveTicket(Ticket ticket, Project target) {
    Project source = ticket.getProject();
    if (source == target) {
        return;
    }
    if (source != null) {
        source.removeTicketReference(ticket);
    }
    target.addTicketReference(ticket);
    ticket.assignProject(target);
}
~~~

Các helper trong ví dụ chỉ minh họa domain API, không phải những method JPA tạo sẵn. Cần kiểm tra quyền chuyển, tính hợp lệ của Ticket/Project và trạng thái managed trong service thật.

Với FK NOT NULL, provider có thể thực hiện:

~~~sql
UPDATE tickets
SET project_id = :new_project
WHERE id = :ticket_id;
~~~

Không cần DELETE Ticket.

### 9.1. Vì sao reparenting với orphanRemoval=true nguy hiểm?

Khi orphanRemoval=true, việc gỡ child khỏi cha cũ biểu thị **child phải bị xóa**. Sau đó lại gắn child vào cha mới tạo ra hai ý nghĩa trái ngược: vừa yêu cầu xóa, vừa muốn giữ.

Jakarta Persistence nêu rõ ứng dụng **không nên phụ thuộc vào một thứ tự remove cụ thể và không nên tái gán entity vừa bị orphan cho quan hệ khác hoặc cố persist lại nó**. Hành vi reparenting kiểu này không được bảo đảm portable giữa các provider.

Nếu business cho phép chuyển cha, hãy xem **orphanRemoval=false** và một thao tác cập nhật quan hệ có kiểm soát. Nếu business thật sự muốn xóa child cũ và tạo child mới ở parent mới, hãy biểu diễn thành **hai entity có danh tính khác nhau** theo domain thay vì chuyển object đã orphan.

## 10. So sánh remove khỏi List và EntityManager.remove bằng timeline

### 10.1. Không bật orphan removal

~~~text
T0: DB có OrderLine #502 (order_id = 100)
T1: Transaction bắt đầu
T2: order.unlinkLine(line)
       order.lines bỏ #502
       line.order = null
T3: em.flush()
       UPDATE line.order_id = NULL (nếu schema cho phép)
T4: commit
       OrderLine #502 còn tồn tại
~~~

### 10.2. Có orphanRemoval=true

~~~text
T0: DB có OrderLine #502 (order_id = 100)
T1: Transaction bắt đầu
T2: order.removeLine(line)
       #502 bị gỡ khỏi quan hệ
T3: em.flush()
       DELETE OrderLine #502
T4: commit
       OrderLine #502 không còn tồn tại
~~~

### 10.3. Gọi remove trực tiếp

~~~text
T0: DB có OrderLine #502 (order_id = 100)
T1: Transaction bắt đầu
T2: em.remove(line)
       line được đánh dấu removed
       order.lines có thể chưa được sửa trong bộ nhớ
T3: em.flush()
       DELETE OrderLine #502
T4: commit
       OrderLine #502 không còn tồn tại
~~~

Ba đường đi đều có thể phát SQL **trước commit**, nhưng chỉ sau transaction commit thành công thì thay đổi mới trở thành committed theo cơ chế DB. **Flush không phải commit**; nếu rollback sau flush, DML giao dịch chưa commit có thể được hoàn tác.

## 11. Phân biệt EntityManager.remove() với EntityManager.detach()

Đây là lỗi thuật ngữ dễ gây nhầm khi nói “bỏ con khỏi quan hệ”:

~~~java
em.remove(line); // Yêu cầu xóa entity khỏi database.
em.detach(line); // Chỉ làm entity rời persistence context.
~~~

**detach() không xóa entity và không tự xóa liên kết database**. Nó khiến object không còn được quản lý trong persistence context hiện tại. Nếu có thay đổi chưa flush trên entity rồi detach, các thay đổi đó có thể không được ghi.

Ba khái niệm:

- **Disassociate:** gỡ quan hệ cha–con ở mô hình đối tượng và FK/join table.
- **Remove:** xóa entity như một bản ghi có vòng đời riêng.
- **Detach:** ngừng quản lý entity trong một persistence context.

Một entity detached vẫn có thể tồn tại ở DB và vẫn thuộc cha. Do đó đừng gọi em.detach(child) với kỳ vọng nó sẽ được xóa khỏi collection hoặc database.

## 12. @OneToMany một hướng: join table và @JoinColumn

Quan hệ một-nhiều không bắt buộc bidirectional. Một mô hình có thể chỉ giữ collection ở cha:

~~~java
@Entity
public class PurchaseOrder {

    @Id
    @GeneratedValue
    private Long id;

    @OneToMany(orphanRemoval = false)
    private List<OrderLine> lines = new ArrayList<>();
}
~~~

Trong ánh xạ mặc định, JPA thường dùng **join table**:

~~~text
purchase_orders(id)
purchase_order_lines(id)
purchase_orders_purchase_order_lines(purchase_order_id, lines_id)
~~~

Tên bảng/cột thực tế phụ thuộc mapping và naming strategy. Gỡ một OrderLine khỏi collection có thể khiến provider **xóa hàng trong join table**:

~~~sql
DELETE FROM purchase_orders_purchase_order_lines
WHERE purchase_order_id = ? AND lines_id = ?;
~~~

**OrderLine vẫn tồn tại** trong bảng purchase_order_lines khi orphanRemoval=false và không có remove(entity) riêng.

Nếu cùng association đặt **orphanRemoval=true**, entity con bị orphan có thể còn bị DELETE khỏi bảng OrderLine khi flush, ngoài việc dọn hàng liên kết.

### 12.1. @JoinColumn ở @OneToMany một hướng

Một quan hệ @OneToMany một hướng cũng có thể ánh xạ bằng **@JoinColumn**:

~~~java
@OneToMany(orphanRemoval = false)
@JoinColumn(name = "order_id")
private List<OrderLine> lines = new ArrayList<>();
~~~

Trong trường hợp này, provider dùng cột FK trong bảng child thay vì join table riêng. Gỡ liên kết với orphanRemoval=false có thể làm FK được đặt NULL nếu schema cho phép. **Ownership/mapping vật lý quyết định DML gỡ liên kết**, còn orphanRemoval quyết định có xóa orphan entity hay không.

### 12.2. Vì sao không thể suy ra SQL chỉ từ List.remove()?

Một lời gọi:

~~~java
order.getLines().remove(line);
~~~

có thể dẫn tới:

- DELETE **hàng join table** nhưng giữ entity con;
- UPDATE **FK của entity con** thành NULL;
- DELETE **hàng entity con** nếu orphanRemoval=true;
- Hoặc không thay đổi dữ liệu đúng ý nếu chỉ sửa phía nghịch đảo mà owning side vẫn mang quan hệ cũ.

Để biết kết quả, phải xem đầy đủ **@OneToMany, @ManyToOne, mappedBy, @JoinColumn, @JoinTable, orphanRemoval, nullability** và SQL do provider phát.

## 13. @OneToOne: xóa orphan khi thay object duy nhất

orphanRemoval cũng áp dụng cho quan hệ **@OneToOne**. Giả sử một User sở hữu một Profile có vòng đời phụ thuộc hoàn toàn vào User:

~~~java
@Entity
public class User {

    @Id
    @GeneratedValue
    private Long id;

    @OneToOne(
        cascade = {CascadeType.PERSIST, CascadeType.MERGE},
        orphanRemoval = true
    )
    @JoinColumn(name = "profile_id", unique = true)
    private Profile profile;

    public void replaceProfile(Profile replacement) {
        this.profile = replacement;
    }
}
~~~

Trong một transaction:

~~~java
User user = em.find(User.class, userId);
Profile oldProfile = user.getProfile(); // Giả định có getter.

user.replaceProfile(new Profile("New preferences"));
// Nếu oldProfile là managed target có quan hệ orphanRemoval,
// khi gỡ khỏi quan hệ, JPA có thể DELETE oldProfile tại flush.
~~~

**Điểm quan trọng:** thay giá trị field từ oldProfile sang replacement có thể làm oldProfile trở thành orphan và cần DELETE. Entity mới replacement vẫn cần được **persist** phù hợp: sử dụng cascade PERSIST khi semantics cho phép hoặc gọi persist riêng.

Đây là ví dụ logic rút gọn; một implementation cần constructor, ID, quyền sở hữu FK và unique constraint tương ứng. Thứ tự SQL INSERT replacement, UPDATE FK, DELETE oldProfile có thể chịu unique constraints/DDL, nên trường hợp thay thế profile cần được kiểm thử trên provider và DB thật.

### 13.1. Nếu Profile có thể dùng chung?

Khi nhiều User được phép dùng cùng Profile hoặc Profile có vòng đời độc lập, **không nên dùng orphanRemoval=true** để xóa Profile khi một User ngừng tham chiếu. Có thể chọn một entity Profile dùng chung, quan hệ thích hợp và quy trình xóa riêng khi không còn reference hoặc khi nghiệp vụ xác nhận.

**orphanRemoval không tự kiểm tra rằng một entity target có thật sự không được entity khác sử dụng hay không.** Khóa ngoại của entity khác có thể ngăn DELETE, nhưng nếu không có constraint, có thể xảy ra mất dữ liệu ngoài dự định.

## 14. @ManyToMany: bỏ liên kết không có nghĩa xóa entity bên kia

Giả sử nhiều Article có thể dùng chung nhiều Tag:

~~~text
Article #1 ---> Tag #5 ("jpa")
Article #2 ---> Tag #5 ("jpa")
~~~

Mapping:

~~~java
@ManyToMany
@JoinTable(
    name = "article_tags",
    joinColumns = @JoinColumn(name = "article_id"),
    inverseJoinColumns = @JoinColumn(name = "tag_id")
)
private Set<Tag> tags = new HashSet<>();
~~~

Khi:

~~~java
article.getTags().remove(tag);
~~~

provider thường loại **hàng liên kết** (article_id, tag_id) trong bảng article_tags. **Tag #5 vẫn tồn tại**, vì Article khác còn có thể dùng nó.

~~~sql
DELETE FROM article_tags
WHERE article_id = 1 AND tag_id = 5;
~~~

Không có orphanRemoval trên @ManyToMany theo JPA; attribute này chỉ dành cho @OneToMany và @OneToOne.

### 14.1. Vì sao cascade REMOVE trên @ManyToMany nguy hiểm?

~~~java
@ManyToMany(cascade = CascadeType.REMOVE)
private Set<Tag> tags;
~~~

Nếu gọi **em.remove(article)**, cascade REMOVE có thể lan đến Tag dùng chung, có nguy cơ xóa một Tag mà Article khác vẫn tham chiếu, hoặc gây lỗi FK. Với entity chia sẻ như Tag, Permission, Category, Product hoặc Role, thường **không cascade REMOVE** theo quan hệ dùng chung.

Nếu muốn xóa một Tag khỏi hệ thống, đó là một **nghiệp vụ riêng**, cần đánh giá các Article đang sử dụng, quyền xóa và cách dọn các hàng join table.

### 14.2. Bảng so sánh quan hệ

| Loại quan hệ | Gỡ liên kết mặc định | Hỗ trợ orphanRemoval? | Điểm cần chú ý |
|---|---|---|---|
| **@ManyToOne** | Thay FK ở entity chủ sở hữu | Không | Child có thể đổi parent nếu domain cho phép |
| **@OneToMany**, FK ở child | Bỏ child khỏi cha; owning side cập nhật FK | Có | Đồng bộ hai phía và xem FK nullable |
| **@OneToMany**, join table | Xóa liên kết ở join table | Có | DELETE link khác với DELETE child entity |
| **@OneToOne** | Đặt tham chiếu null hoặc thay target | Có | Old target có thể bị xóa nếu orphanRemoval=true |
| **@ManyToMany** | Xóa hàng join table | Không | Không xóa entity target dùng chung |
| **@ElementCollection** | Xóa hàng value trong collection table | Không có entity orphan | Các phần tử là value, không phải entity có @Id |

## 15. @ElementCollection: xóa giá trị, không gọi remove(entity)

Một entity có tập keyword:

~~~java
@ElementCollection
@CollectionTable(
    name = "article_keywords",
    joinColumns = @JoinColumn(name = "article_id")
)
@Column(name = "keyword")
private Set<String> keywords = new HashSet<>();
~~~

~~~java
article.getKeywords().remove("jpa");
~~~

String **không phải entity**, nên không có chuyện **em.remove("jpa")**. Provider đồng bộ collection table theo mapping, có thể xóa hàng lưu keyword hoặc thay đổi cách ghi collection.

Phân biệt:

- **Xóa phần tử giá trị:** thay đổi @ElementCollection, thường ảnh hưởng collection table.
- **Xóa entity con:** có thể cần em.remove(child) hoặc orphanRemoval=true.
- **Xóa liên kết dùng chung:** thay đổi join table của @ManyToMany.

Việc có lời gọi collection.remove() trong cả ba trường hợp không khiến chúng có cùng semantics ở database.

## 16. Orphan removal áp dụng cho entity ở trạng thái nào?

JPA quy định orphanRemoval xử lý những **target entity bị orphan** theo lifecycle. Với một entity target là **new, detached hoặc đã removed**, ngữ nghĩa orphanRemoval **không áp dụng theo cùng cách như một target managed**.

### 16.1. Entity mới chưa được lưu

~~~java
PurchaseOrder order = new PurchaseOrder("PO-NEW");
OrderLine line = new OrderLine("SKU-A", 1);

order.addLine(line);
order.removeLine(line);

em.persist(order);
~~~

Nếu line mới chỉ được thêm rồi gỡ khỏi collection trước khi có quan hệ managed thích hợp, thường không có một hàng DB đã lưu cần DELETE. Không viết test dựa vào việc provider phải phát SQL DELETE cho entity mới như thể nó là orphan đã tồn tại.

### 16.2. Entity detached

~~~java
OrderLine detached = loadLineInOldEntityManager();
// EntityManager cũ đã đóng.

// Không thể giả định gỡ detached object khỏi một List tùy ý
// sẽ tự làm provider xóa hàng trong transaction mới.
~~~

Phải xác định relation và entities đang được quản lý trong **persistence context hiện tại**. Khi xử lý request “xóa dòng theo ID”, có thể load parent và child managed rồi sửa association hoặc gọi remove trong transaction mới.

### 16.3. Entity đã removed

Nếu child đã được em.remove(child) đánh dấu removed, đừng cố gắn child vào parent khác hoặc persist lại object đó chỉ để “hủy xóa”. Nếu nghiệp vụ cần tạo thực thể mới, hãy tạo một entity mới với ID/lifecycle thích hợp. Việc thay đổi lifecycle qua nhiều trạng thái phải theo contract JPA; không coi removed như một entity managed bình thường để sử dụng tiếp.

### 16.4. Không tái gán orphan để tránh DELETE

Theo ngữ nghĩa orphanRemoval, một target đã bị orphan không nên được reassign tới quan hệ khác và không nên dựa vào thứ tự provider áp dụng DELETE. Nếu domain có chuyển parent hợp lệ, chọn mapping **orphanRemoval=false** và cập nhật phía sở hữu thay vì lợi dụng timing của flush.

## 17. List.remove(), Set.remove() và equals()/hashCode()

Xóa entity con khỏi collection còn phụ thuộc **quy tắc equality của Java**.

### 17.1. List.remove(Object)

~~~java
boolean removed = order.getLinesInternal().remove(targetLine);
~~~

Phương thức **List.remove(Object)** tìm một phần tử bằng **equals()**. Nếu List chứa hai instance Java khác nhau nhưng đại diện cùng hàng DB, kết quả có thể phụ thuộc cách equals() của entity được thiết kế. Nếu không tìm được phần tử, List không thay đổi nên **orphanRemoval không có lý do để hoạt động theo cách mong muốn**.

**List.remove(int index)** xóa theo vị trí, không theo equals(). Nhưng thứ tự collection có thể thay đổi; xóa theo chỉ số người dùng gửi từ request cũ có nguy cơ xóa nhầm dòng.

### 17.2. Set.remove(Object)

Với Set dựa trên hash:

~~~java
boolean removed = order.getLinesInternal().remove(targetLine);
~~~

**HashSet.remove()** phụ thuộc cả hashCode và equals. Nếu entity hashCode dựa vào ID được cấp sau khi phần tử đã add hoặc dựa vào business key mutable, phần tử có thể không còn tìm thấy trong bucket cũ. Khi đó lệnh remove trả false và child vẫn nằm trong Set.

Ví dụ lỗi:

~~~java
Set<OrderLine> lines = new HashSet<>();
OrderLine line = new OrderLine("SKU-A", 1);
lines.add(line);       // id có thể null.
em.persist(line);      // provider cấp id.

// Nếu hashCode() dựa trực tiếp vào id,
// hashCode trước và sau persist có thể khác nhau.
boolean removed = lines.remove(line); // Có thể false.
~~~

Do đó:

- Không dùng association hoặc collection hai hướng trong equals/hashCode của entity.
- Tránh hash dựa trên giá trị thay đổi trong khi object nằm trong HashSet/HashMap.
- Nếu dùng generated ID, thiết kế equality/hash theo vòng đời entity và proxy/provider phù hợp.
- Kiểm tra **kết quả boolean** của thao tác gỡ collection, không giả định remove luôn thành công.

### 17.3. Xóa theo ID nghiệp vụ rõ ràng

Một helper có thể nhận **lineId** rồi tìm managed child của parent:

~~~java
public boolean removeLineById(Long lineId) {
    for (int i = 0; i < lines.size(); i++) {
        OrderLine line = lines.get(i);
        if (java.util.Objects.equals(line.getId(), lineId)) {
            lines.remove(i);
            line.assignTo(null);
            return true;
        }
    }
    return false;
}
~~~

Helper này tránh phụ thuộc vào equals() giữa entity được gửi từ bên ngoài và entity managed. Khi dùng trong service, **phải kiểm tra lineId thuộc đúng order**, không chỉ dựa vào khả năng find global theo ID. Nếu ID null của entity mới, cần xác định quy tắc xóa object mới riêng.

Với collection rất lớn, duyệt mọi child có thể gây tải dữ liệu và N+1. Trong một API có nhiều nghìn dòng, nên cân nhắc truy vấn child theo **lineId + orderId** rồi thao tác đúng aggregate trong transaction; không chuyển sang bulk delete vô điều kiện nếu cần orphan/cascade callbacks.

### 17.4. Không thay cả collection managed bằng collection mới tùy tiện

~~~java
// Cách dễ gây khó khăn với dirty tracking/orphanRemoval:
order.lines = new ArrayList<>();
~~~

Một số provider dùng wrapper riêng để theo dõi collection managed. Thay reference collection bằng một List mới có thể khiến provider không theo dõi đúng thay đổi, gây exception hoặc SQL không mong muốn, đặc biệt với orphanRemoval. **Ưu tiên thao tác trên collection đang managed thông qua helper** hoặc method có kiểm soát.

Nếu muốn thay toàn bộ danh sách, so sánh ID hiện tại và ID mới rồi add/remove từng child theo domain thay vì gán đè field một cách thiếu kiểm soát.

### 17.5. clear() không vô hại khi orphanRemoval=true

~~~java
order.getLinesInternal().clear();
~~~

Nếu collection có **orphanRemoval=true**, clear() có thể đánh dấu **tất cả managed children** là orphan để xóa khi flush. Trên một đơn có hàng nghìn dòng, hậu quả có thể là hàng nghìn DELETE, callback, lock và audit events.

Nên yêu cầu xác nhận nghiệp vụ và kiểm soát phạm vi thao tác. Không dùng clear() chỉ để làm response JSON ngắn hơn hoặc tránh vòng tham chiếu.

## 18. Thao tác xóa trong service có transaction

Một service ứng dụng nên biểu đạt rõ **gỡ liên kết** hay **xóa entity**.

### 18.1. Chỉ gỡ liên kết, giữ child

Giả sử dùng mapping orphanRemoval=false và FK nullable:

~~~java
import jakarta.persistence.EntityManager;
import jakarta.persistence.PersistenceContext;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class OrderLineService {

    @PersistenceContext
    private EntityManager em;

    @Transactional
    public void unlinkLine(long orderId, long lineId) {
        PurchaseOrder order = em.find(PurchaseOrder.class, orderId);
        if (order == null) {
            throw new IllegalArgumentException("Order not found");
        }

        boolean changed = order.removeLineById(lineId);
        if (!changed) {
            throw new IllegalArgumentException("Line not in this order");
        }
        // Không gọi em.remove(line).
        // FK order_id có thể được đặt NULL khi flush/commit.
    }
}
~~~

Ví dụ dùng annotation transaction của Spring; trong Jakarta EE có thể dùng **jakarta.transaction.Transactional** hoặc EJB CMT. Cần cấu hình EntityManager/transaction manager tương ứng. Mã nguồn cho helper removeLineById được minh họa ở phần trước và cần tích hợp vào entity ở biến thể này.

### 18.2. Xóa child tường minh bằng EntityManager.remove

Nếu mapping không có orphanRemoval, nghiệp vụ muốn xóa dòng hàng hẳn:

~~~java
@Transactional
public void deleteLine(long orderId, long lineId) {
    PurchaseOrder order = em.find(PurchaseOrder.class, orderId);
    OrderLine line = em.find(OrderLine.class, lineId);

    if (order == null || line == null ||
        line.getOrder() == null ||
        !java.util.Objects.equals(line.getOrder().getId(), orderId)) {
        throw new IllegalArgumentException("Line not in order");
    }

    if (!order.unlinkLine(line)) {
        throw new IllegalStateException("Inconsistent order graph");
    }

    em.remove(line);
    // DELETE được đồng bộ theo transaction.
}
~~~

Đoạn này là method của một service có EntityManager, Order/Line managed và mapping orphanRemoval=false. Không thêm code đồng thời **orphanRemoval=true** rồi gọi remove một cách dư thừa. Với FK NOT NULL, cần kiểm tra SQL do provider phát và thao tác một cách nhất quán để không vô tình flush trạng thái “line.order=null” như một UPDATE trước DELETE.

### 18.3. Xóa bằng orphanRemoval=true

Với aggregate OrderLine sở hữu độc quyền:

~~~java
@Transactional
public void removeLineFromOrder(long orderId, long lineId) {
    PurchaseOrder order = em.find(PurchaseOrder.class, orderId);
    if (order == null) {
        throw new IllegalArgumentException("Order not found");
    }

    if (!order.removeLineById(lineId)) {
        throw new IllegalArgumentException("Line not in order");
    }

    // Không gọi em.remove(line).
    // orphanRemoval=true sẽ xóa managed orphan khi flush.
}
~~~

Ba service có tên gần giống nhưng **khác hành vi dữ liệu**. Trong API nên đặt tên phản ánh mục đích: **unlink**, **remove**, **delete**, **move** hoặc **archive** theo contract nghiệp vụ, không gom tất cả thành một method chung mơ hồ.

### 18.4. Xóa theo yêu cầu HTTP

Một endpoint:

~~~http
DELETE /orders/100/lines/502
~~~

có thể mang semantics “xóa dòng khỏi đơn hàng” nhưng không tự nói rõ **có giữ row lịch sử hay không**. Repository/service phải quyết định dựa vào domain. Nếu đơn hàng đã thanh toán, nghiệp vụ có thể cấm DELETE và thay bằng một dòng điều chỉnh/audit record. Không nên ánh xạ HTTP DELETE máy móc vào **em.remove()** nếu dữ liệu phải giữ vì kế toán hoặc pháp lý.

## 19. Xóa bằng JPQL bulk DML khác remove(entity)

Một API có thể chạy:

~~~java
int deleted = em.createQuery(
    "delete from OrderLine l where l.order.id = :orderId"
).setParameter("orderId", orderId)
 .executeUpdate();
~~~

Đây là **bulk JPQL DELETE**, không phải vòng lặp gọi **em.remove(line)** cho từng entity. Khác biệt:

- Bulk DML tác động trực tiếp vào DB trong transaction.
- Không đi qua toàn bộ entity lifecycle callback và cascade như khi remove từng managed entity.
- Không tự cập nhật tất cả managed OrderLine và PurchaseOrder.lines trong persistence context đang tồn tại.
- Có thể vi phạm FK nếu các bảng khác tham chiếu child.
- Trạng thái cache và collection có thể cần refresh/clear phù hợp sau bulk DML.

Nếu dùng bulk DELETE với một parent đang managed và collection đã load, code có thể tiếp tục nhìn thấy các dòng đã bị xóa ở DB. Sau bulk DML, nên xác định lại ranh giới persistence context, flush pending changes trước khi delete nếu cần, và clear/refresh theo chính sách của service.

### 19.1. Vì sao bulk delete không thay thế orphanRemoval?

orphanRemoval có ngữ nghĩa vòng đời: **bỏ đúng child khỏi quan hệ** rồi provider xử lý entity removal. Bulk DELETE thường chỉ dựa vào một predicate SQL/JPQL và **bỏ qua các thông báo lifecycle thông thường đối với từng entity**.

Với dữ liệu cần audit callback hoặc cascade xóa con của child, bulk DELETE có thể không phù hợp. Nếu cần xóa số lượng rất lớn, có thể chấp nhận bulk DML nhưng phải **thiết kế rõ cách xử lý FK, audit, cache và các dependent rows**, không giả định nó là bản sao tối ưu của em.remove().

### 19.2. Spring Data JPA deleteById khác bulk @Modifying

Tùy implementation, một phương thức repository như **deleteById()** có thể load entity rồi gọi remove, còn một query **@Modifying** dùng DELETE trực tiếp là bulk DML. Không nên suy diễn mọi phương thức tên “delete” trong framework có cùng callback/cascade semantics. Cần xem implementation và query thực sự được chạy.

## 20. ON DELETE CASCADE ở database là cơ chế khác

DDL có thể có:

~~~sql
ALTER TABLE purchase_order_lines
ADD CONSTRAINT fk_order_line_order
FOREIGN KEY (order_id) REFERENCES purchase_orders(id)
ON DELETE CASCADE;
~~~

SQL này là **minh họa cấu trúc FK**; nếu constraint cũ đã tồn tại, cần drop/replace đúng theo DBMS chứ không chạy ADD trùng tên một cách máy móc.

**ON DELETE CASCADE** nghĩa là khi **hàng parent thực sự bị DELETE ở database**, DB có thể xóa các hàng child tham chiếu tới nó. Nó **không áp dụng cho việc UPDATE order_id=NULL hoặc gỡ một collection element**, vì đó không phải thao tác DELETE hàng cha.

So sánh:

| Cơ chế | Tầng thực thi | Kích hoạt chính |
|---|---|---|
| **CascadeType.REMOVE** | JPA | em.remove(parent) lan remove tới target |
| **orphanRemoval=true** | JPA | Managed child bị loại khỏi quan hệ privately owned |
| **ON DELETE CASCADE** | Database | Hàng parent thực sự bị DELETE |
| **FK ON DELETE SET NULL** | Database | Parent DELETE, DB đặt FK child NULL nếu hỗ trợ/hợp lệ |
| **Xóa join row** | JPA hoặc SQL DB | Quan hệ bị gỡ, entity target có thể vẫn tồn tại |

Khi DB tự cascade xóa hàng, JPA provider **không mặc nhiên nhận callback @PreRemove/@PostRemove cho từng child bị database xóa** hoặc tự làm mới mọi managed entity/cache trong memory. Nếu ứng dụng dùng cả ORM cascade lẫn DB cascade, phải hiểu tương tác và không giả định sẽ luôn có đúng một đường xóa.

### 20.1. Không đồng nhất ON DELETE CASCADE với ON UPDATE CASCADE

- **ON DELETE CASCADE:** xử lý child khi parent row bị xóa.
- **ON UPDATE CASCADE:** xử lý khóa ngoại khi giá trị khóa tham chiếu của parent thay đổi, trên DBMS hỗ trợ.

Trong bài toán bỏ child khỏi quan hệ, thường chỉ có **UPDATE FK** hoặc **DELETE child**. Không nên tìm ON UPDATE CASCADE như một cách bật orphan removal.

## 21. Kiểm chứng bằng transaction và dữ liệu thực tế

Chỉ nhìn một List giảm từ hai phần tử xuống một **không đủ chứng minh entity con đã bị xóa khỏi database**. Cần kiểm tra kết quả sau khi persistence context được đồng bộ và tránh đọc lại chỉ từ managed instances có sẵn.

Những ví dụ này dùng **EntityManager RESOURCE_LOCAL** để minh họa transaction độc lập. Nếu dự án dùng JTA, phải chuyển sang cách quản lý transaction của JTA thay vì dùng EntityManager.getTransaction().

### 21.1. Tạo dữ liệu

Với mapping ban đầu có **CascadeType.PERSIST**, có thể tạo một đơn hàng và hai dòng trong một transaction:

~~~java
EntityManager em = emf.createEntityManager();
Long orderId;
Long lineId;

try {
    EntityTransaction tx = em.getTransaction();
    tx.begin();

    PurchaseOrder order = new PurchaseOrder("PO-TEST-235");
    OrderLine first = new OrderLine("KB-01", 1);
    OrderLine second = new OrderLine("MS-01", 2);

    order.addLine(first);
    order.addLine(second);
    em.persist(order);
    em.flush();

    orderId = order.getId();
    lineId = second.getId();
    tx.commit();
} finally {
    em.close();
}
~~~

Đoạn này giả định schema và generator đã được cấu hình phù hợp; trong một test production-quality cần rollback nếu lỗi và dọn dữ liệu test. **Từng tình huống bên dưới nên dùng một fixture độc lập** để phép thử trước không xóa mất dữ liệu cho phép thử sau.

### 21.2. Kiểm thử orphanRemoval=false

Giả định PurchaseOrder có helper removeLineById() ở mục 17.3, mapping **orphanRemoval=false** và FK order_id cho phép NULL:

~~~java
EntityManager em = emf.createEntityManager();
try {
    EntityTransaction tx = em.getTransaction();
    tx.begin();

    PurchaseOrder order = em.find(PurchaseOrder.class, orderId);
    if (!order.removeLineById(lineId)) {
        throw new AssertionError("Line not found");
    }

    em.flush();
    em.clear();

    OrderLine remaining = em.find(OrderLine.class, lineId);
    if (remaining == null) {
        throw new AssertionError("Unlink must keep child");
    }
    if (remaining.getOrder() != null) {
        throw new AssertionError("Expected null parent");
    }

    tx.commit();
} finally {
    em.close();
}
~~~

Kết quả mong muốn: **hàng OrderLine vẫn tồn tại**, nhưng khóa ngoại liên kết tới parent đã được gỡ. Để xác nhận kết quả committed, có thể mở EntityManager và transaction mới sau commit.

### 21.3. Kiểm thử orphanRemoval=true

Trong một cấu hình test **riêng** có **orphanRemoval=true** trên PurchaseOrder.lines, sau khi tạo dữ liệu mới:

~~~java
EntityManager em = emf.createEntityManager();
try {
    EntityTransaction tx = em.getTransaction();
    tx.begin();

    PurchaseOrder order = em.find(PurchaseOrder.class, orderId);
    if (!order.removeLineById(lineId)) {
        throw new AssertionError("Line not found");
    }

    // Không gọi EntityManager.remove(line).
    em.flush();
    em.clear();

    OrderLine removedLine = em.find(OrderLine.class, lineId);
    if (removedLine != null) {
        throw new AssertionError("Expected orphan to be deleted");
    }

    tx.commit();
} finally {
    em.close();
}
~~~

Phép thử này phân biệt **gỡ liên kết giữ child** với **gỡ liên kết khiến child bị xóa**. Với orphanRemoval=true, kiểm tra row thực sự biến mất thay vì chỉ kiểm tra collection Java còn bao nhiêu phần tử.

### 21.4. Kiểm thử EntityManager.remove() độc lập

Với mapping orphanRemoval=false và một child đang managed:

~~~java
EntityManager em = emf.createEntityManager();
try {
    EntityTransaction tx = em.getTransaction();
    tx.begin();

    OrderLine line = em.find(OrderLine.class, lineId);
    if (line == null) {
        throw new AssertionError("Child not found");
    }

    PurchaseOrder parent = line.getOrder();
    if (parent != null) {
        parent.unlinkLine(line);
    }

    em.remove(line);
    em.flush();
    em.clear();

    if (em.find(OrderLine.class, lineId) != null) {
        throw new AssertionError("Expected child to be deleted");
    }
    tx.commit();
} finally {
    em.close();
}
~~~

Lệnh **em.remove(line)** nhắm trực tiếp tới hàng child. Nó không bắt buộc mapping orphanRemoval=true. Cách provider chọn DELETE hay thêm UPDATE FK phụ thuộc mapping và thời điểm flush; FK NOT NULL cần được xử lý phù hợp.

### 21.5. Kiểm chứng rollback sau flush

~~~java
tx.begin();
PurchaseOrder order = em.find(PurchaseOrder.class, orderId);
order.removeLineById(lineId);
em.flush();   // Với orphanRemoval=true, DELETE có thể đã chạy.
tx.rollback();
~~~

Trong database có transaction phù hợp, rollback hoàn tác DELETE chưa commit. **Không dùng object Java sau rollback như bằng chứng dữ liệu còn hay mất**. Hãy xác nhận bằng một EntityManager mới.

### 21.6. Bật SQL logging khi kiểm thử

Những hình dạng SQL thường gặp:

~~~text
Gỡ child, orphanRemoval=false, FK nullable:
  UPDATE purchase_order_lines SET order_id = NULL WHERE id = ?

Gỡ child, orphanRemoval=true:
  DELETE FROM purchase_order_lines WHERE id = ?

EntityManager.remove(managed child):
  DELETE FROM purchase_order_lines WHERE id = ?

Gỡ Tag khỏi Article trong @ManyToMany:
  DELETE FROM article_tags WHERE article_id = ? AND tag_id = ?
~~~

Đây là **minh họa ngữ nghĩa**, không phải cam kết về số lượng và thứ tự câu SQL. Hibernate, EclipseLink và các cấu hình batching, cascades, collection mappings có thể phát SQL khác.

## 22. Các tình huống mở rộng

### 22.1. Child có khóa chính phụ thuộc cha bằng @MapsId

~~~java
@Entity
public class OrderDetail {

    @Id
    private Long orderId;

    @MapsId
    @OneToOne(optional = false)
    @JoinColumn(name = "order_id")
    private PurchaseOrder order;
}
~~~

Trong mô hình này, khóa ngoại order_id cũng là khóa chính của OrderDetail. **Gỡ quan hệ rồi giữ row bằng cách đặt order_id=NULL không có ý nghĩa**. Nếu OrderDetail sống cùng Order, có thể dùng ownership với orphanRemoval. Nếu phải giữ lịch sử độc lập, nên thiết kế một identity và vòng đời khác.

### 22.2. Child đang được bảng khác tham chiếu

~~~text
purchase_order_lines.id <---- shipment_items.order_line_id
~~~

Nếu orphanRemoval=true dẫn tới DELETE OrderLine nhưng shipment_items vẫn trỏ tới nó, DB có thể từ chối DELETE. Đó là dấu hiệu phải xem lại **vòng đời và quyền sở hữu dữ liệu**, không chỉ sửa annotation.

Các lựa chọn gồm: cấm xóa dòng đã giao hàng, lưu snapshot, thiết kế dependent rows thực sự thuộc vòng đời child, hoặc đổi yêu cầu thành **hủy trạng thái**. Không thêm ON DELETE CASCADE vào mọi FK chỉ để “xóa được”, vì có thể làm mất dữ liệu audit.

### 22.3. Soft delete khác xóa entity

Nếu pháp lý hoặc kế toán yêu cầu giữ bản ghi, một method có thể thay trạng thái:

~~~java
@Column(name = "cancelled", nullable = false)
private boolean cancelled;

public void cancel() {
    this.cancelled = true;
}
~~~

Soft delete là **một UPDATE theo nghiệp vụ**, không phải mặc định của orphanRemoval. Trong JPA chuẩn, orphan removal dẫn đến ngữ nghĩa xóa entity. Nếu dùng cơ chế soft delete riêng của Hibernate hoặc provider khác, cần thiết kế và kiểm chứng theo khả năng của runtime đó.

### 22.4. Xóa đồng thời và @Version

Giả sử hai transaction cùng thao tác một OrderLine:

~~~text
T1 tải line #502
T2 đổi trạng thái hoặc chuyển quan hệ line #502, rồi commit
T1 gỡ line #502 khỏi order và flush
~~~

T1 có thể dựa vào thông tin cũ. **@Version** và optimistic locking có thể giúp phát hiện xung đột trên entity được cập nhật/xóa; tuy nhiên **không mặc định mọi thay đổi collection đều tăng version của parent theo cùng cách trên mọi mapping/provider**.

Khi thực hiện DELETE theo orderId + lineId, service phải kiểm tra line thực sự còn thuộc đúng order và user có quyền xóa. Với dữ liệu quan trọng, cân nhắc transaction isolation, khóa hoặc optimistic locking thích hợp.

### 22.5. Collection rất lớn

~~~java
order.getLinesInternal().clear();
~~~

Khi orphanRemoval=true, một lệnh clear có thể khiến hàng nghìn child bị xóa, gây nhiều DELETE, lock và callback. Không nên tải toàn bộ collection chỉ để xóa một dòng theo ID nếu aggregate rất lớn. Có thể truy vấn child đích theo khóa phù hợp; nếu chọn bulk DELETE để tối ưu, phải xử lý sự khác biệt về entity lifecycle, FK và cache.

### 22.6. Không sửa quan hệ chỉ để tạo JSON

~~~java
for (OrderLine line : order.getLines()) {
    line.assignTo(null);
}
return order;
~~~

Đoạn code này nguy hiểm nếu order/lines đang managed: provider có thể UPDATE FK hoặc DELETE orphan ở flush. Nếu mục đích là tránh vòng tham chiếu khi serialize hai hướng, cần thiết kế **DTO** hoặc cấu hình serializer, **không thay đổi quan hệ thật**.

## 23. Ra quyết định theo vòng đời dữ liệu

Trước khi viết một method removeChild(), cần xác định:

1. **Child có thể tồn tại độc lập không?** Nếu có, unlink có thể phù hợp. Nếu không, cần xem orphanRemoval hoặc xóa tường minh.
2. **Child có thể đổi cha không?** Nếu có, tránh làm orphan tại cha cũ theo semantics xóa.
3. **Child có được chia sẻ không?** Nếu có, không cascade REMOVE bừa bãi.
4. **FK có nullable không?** Unlink bằng FK NULL chỉ hợp lệ khi schema cho phép.
5. **Có bảng khác đang tham chiếu child không?** DELETE có thể bị FK chặn hoặc cần quy trình đặc biệt.
6. **Có cần giữ lịch sử không?** Có thể chuyển sang soft delete hoặc lưu snapshot.
7. **Xóa được kích hoạt bởi gì?** Bỏ quan hệ, xóa cha, hay lệnh xóa riêng?
8. **Đã cập nhật đúng owning side chưa?** Với mappedBy, collection nghịch đảo không quyết định FK.
9. **Đã tính concurrency và kích thước collection chưa?** Xóa hàng loạt có thể giữ lock lâu.
10. **Đã kiểm tra DB sau flush/commit chưa?** Không chỉ dựa vào List.size().

### 23.1. Bảng lựa chọn nhanh

| Nghiệp vụ | Cách thường phù hợp |
|---|---|
| Employee rời Department nhưng vẫn tồn tại | orphanRemoval=false, unlink/đổi owning FK |
| OrderLine không còn giá trị ngoài Order | @OneToMany(orphanRemoval=true), gỡ child qua helper |
| Xóa Order và mọi OrderLine riêng tư | Cascade REMOVE từ parent hoặc semantics orphanRemoval |
| Xóa riêng một child trong mapping không orphan | em.remove(managed child), cập nhật collection nhất quán |
| Bỏ Tag khỏi Article | Xóa hàng liên kết @ManyToMany, không xóa Tag dùng chung |
| Bỏ keyword đơn giản | Thay đổi @ElementCollection, không gọi em.remove(value) |
| Thay Profile riêng của User | @OneToOne(orphanRemoval=true) nếu thật sự ownership riêng |
| Chuyển Ticket sang Project mới | orphanRemoval=false, chuyển owning FK |
| Hủy dòng đã phát sinh chứng từ | Update trạng thái/historical event thay vì DELETE vật lý |
| Xóa lượng lớn dữ liệu | Thiết kế riêng DML/batch, cân nhắc callback, FK và cache |

## 24. Những lỗi thường gặp

| Hiện tượng | Nguyên nhân có thể gặp | Hướng xử lý |
|---|---|---|
| Gỡ khỏi List mà order_id không thay đổi | Chỉ sửa inverse side của mappedBy | Cập nhật owning side bằng helper |
| Child còn trong DB dù đã gỡ khỏi collection | orphanRemoval=false | Xác định muốn unlink hay DELETE |
| Child bị DELETE ngoài mong muốn | orphanRemoval=true | Chỉ bật khi child có ownership riêng tư |
| UPDATE FK thành NULL bị lỗi | order_id NOT NULL | Xóa entity hoặc reparent đúng domain |
| em.remove(detached) báo IllegalArgumentException | Entity không managed | Load managed entity theo ID trong transaction |
| em.remove(parent) không xóa children | Chưa cascade theo mapping phù hợp | Xem CascadeType.REMOVE, orphanRemoval, FK |
| Xóa child khiến parent/shared entity bị xóa | Cascade REMOVE sai hướng | Tránh cascade REMOVE từ child tới shared parent |
| Remove khỏi HashSet trả false | equals/hashCode thay đổi | Dùng equality ổn định, tìm đúng entity theo ID |
| Gán collection mới rồi flush báo lỗi | Provider đang theo dõi wrapper persistent collection | Thao tác trên collection hiện tại |
| clear() làm mất nhiều child | orphanRemoval=true áp dụng cho mọi phần tử | Giới hạn phạm vi thao tác |
| Child mới không phát DELETE orphan | Chưa có managed persisted child cần xóa | Xem lifecycle: new/detached/removed |
| Chuyển parent nhưng child bị xóa | Reparent với orphanRemoval=true | Dùng orphanRemoval=false |
| Bulk DELETE không chạy @PreRemove | Bulk DML bỏ qua callback từng entity | Dùng em.remove khi callback cần thiết |
| ON DELETE CASCADE không chạy khi unlink | Không xóa hàng parent | Phân biệt DB cascade với gỡ association |
| em.remove(child) nhưng collection vẫn chứa child | Không sửa object graph | Đồng bộ collection cùng entity lifecycle |
| Sau rollback object vẫn có ID/trạng thái cũ | State Java không tự hồi phục | Đọc lại bằng EntityManager mới |
| Xóa child sai order của khách khác | Thiếu kiểm tra lineId thuộc orderId | Xác thực ownership và authorization |
| Dữ liệu lịch sử mất sau DELETE | Chọn sai ngữ nghĩa domain | Soft delete, audit hoặc snapshot |

Nếu Hibernate báo lỗi kiểu “deleted object would be re-saved by cascade”, một khả năng là entity đã bị remove nhưng một association vẫn chứa reference tới nó và cascade tiếp tục xử lý entity đó. Cần kiểm tra đồng bộ hai phía và lifecycle thay vì cố gọi remove thêm lần nữa.

## 25. Bài tập áp dụng

### Bài 1: Nhân viên chuyển phòng ban

Employee còn tồn tại sau khi rời Department; hai entity được ánh xạ @OneToMany/@ManyToOne.

**Câu hỏi:** orphanRemoval=true có phù hợp không?

**Gợi ý:** Không, vì Employee không có vòng đời phụ thuộc vào một Department. Cần unlink/reparent với orphanRemoval=false và cập nhật owning FK.

### Bài 2: Dòng đơn hàng thuộc riêng một đơn

OrderLine không được tồn tại nếu không có Order. Mapping @OneToMany(orphanRemoval=true). Service gỡ một managed line khỏi collection.

**Câu hỏi:** Có cần em.remove(line) nữa không?

**Gợi ý:** Không. Gỡ orphan khỏi quan hệ đủ để kích hoạt xóa khi flush theo mapping.

### Bài 3: CascadeType.ALL

Order có @OneToMany(cascade=ALL, orphanRemoval=false). Ứng dụng bỏ Line khỏi List mà không gọi em.remove(order).

**Câu hỏi:** Line có bị DELETE không?

**Gợi ý:** Không mặc định. CascadeType.ALL chứa REMOVE, nhưng cơ chế đó lan khi remove(parent) chứ không khi đơn thuần unlink.

### Bài 4: Khóa ngoại NOT NULL

OrderLine.order_id NOT NULL. Code đặt line.order=null khi orphanRemoval=false.

**Câu hỏi:** Điều gì xảy ra khi flush?

**Gợi ý:** UPDATE FK thành NULL có thể bị DB từ chối. Cần xóa child hoặc chuyển sang parent khác theo nghiệp vụ.

### Bài 5: Tag được dùng chung

Hai Article dùng chung Tag #5. Article #1 loại Tag #5 khỏi Set<Tag>.

**Câu hỏi:** Có nên xóa hàng tags.id=5?

**Gợi ý:** Không. Chỉ xóa liên kết trong article_tags; Tag phải còn cho Article #2. Tránh cascade REMOVE tới Tag dùng chung.

### Bài 6: Thay Profile

User.profile là @OneToOne(orphanRemoval=true). User thay Profile A bằng Profile B.

**Câu hỏi:** Profile A có thể bị xử lý thế nào?

**Gợi ý:** Khi bị gỡ khỏi quan hệ riêng tư, Profile A có thể trở thành orphan và bị DELETE. Profile B phải được persist đúng mapping; kiểm tra unique constraint và SQL.

### Bài 7: Child detached

Một OrderLine được tải trong request cũ; EntityManager cũ đã đóng. Request mới gọi em.remove(detachedLine).

**Câu hỏi:** Sửa thế nào?

**Gợi ý:** Tìm OrderLine managed bằng ID trong transaction mới, xác minh thuộc đúng Order và quyền xóa, sau đó remove hoặc gỡ quan hệ theo mapping.

### Bài 8: Chuyển Ticket sang Project khác

Team dùng orphanRemoval=true trên Project.tickets, sau đó gọi oldProject.remove(ticket) và newProject.add(ticket).

**Câu hỏi:** Có portable không?

**Gợi ý:** Không nên dựa vào cách này. Ticket có thể trở thành orphan cần DELETE; chọn orphanRemoval=false nếu Ticket có quyền đổi Project.

### Bài 9: Xóa dữ liệu để chuẩn bị JSON

Controller gọi order.getLines().clear() để không gửi lines trong JSON. Mapping có orphanRemoval=true.

**Câu hỏi:** Vì sao nguy hiểm?

**Gợi ý:** clear() có thể xóa tất cả managed child khi flush. Muốn JSON gọn, dùng DTO, không sửa entity managed.

### Bài 10: Bulk delete và callback

Repository dùng JPQL DELETE trực tiếp, nhưng ứng dụng kỳ vọng @PreRemove trên từng OrderLine được chạy.

**Câu hỏi:** Kỳ vọng đúng không?

**Gợi ý:** Không. Bulk DML bỏ qua lifecycle callback/cascade như xóa từng managed entity. Cần quy trình audit khác hoặc dùng em.remove khi yêu cầu callbacks.

### Bài 11: Soft delete

Một OrderLine đã có shipment và hóa đơn; người dùng yêu cầu hủy dòng nhưng pháp lý yêu cầu giữ lịch sử.

**Câu hỏi:** Nên dùng orphanRemoval=true không?

**Gợi ý:** Thường không. Dùng trạng thái hủy hoặc một nghiệp vụ điều chỉnh dữ liệu; không xóa vật lý bản ghi lịch sử.

### Bài 12: Rollback sau flush

Trong transaction, gỡ child bằng orphanRemoval=true, flush thực hiện DELETE, sau đó transaction rollback.

**Câu hỏi:** Hàng child có chắc đã bị xóa khỏi DB không?

**Gợi ý:** Không. DML chưa commit bị rollback. Mở EntityManager mới sau rollback để kiểm tra.

## 26. Bảng ghi nhớ

| Hành động | Bản chất | Hàng child có bị DELETE? |
|---|---|---|
| **List.remove(child)**, orphanRemoval=false | Gỡ quan hệ và cập nhật owning side | Không mặc định |
| **child.setParent(null)**, FK nullable | UPDATE khóa ngoại | Không mặc định |
| **List.remove(child)**, orphanRemoval=true | Managed child trở thành orphan | Có theo orphan-removal semantics |
| **em.remove(managedChild)** | Xóa entity theo lifecycle | Có, khi đồng bộ transaction |
| **em.remove(parent)**, cascade REMOVE | Lan remove xuống children | Có nếu đúng quan hệ cascade |
| **em.remove(parent)**, orphanRemoval=true | Xóa source và privately owned targets | Có theo quy tắc orphan removal |
| **em.detach(child)** | Dừng quản lý entity | Không |
| **@ManyToMany Set.remove(tag)** | Dọn hàng join table | Không mặc định xóa Tag |
| **@ElementCollection.remove(value)** | Dọn value khỏi collection table | Không có child entity riêng |
| **JPQL bulk DELETE** | DML trực tiếp, không đi qua lifecycle từng entity | Có, tùy WHERE |
| **ON DELETE CASCADE** | FK database cascade khi DELETE parent | Có thể |
| **cancelled=true** | Soft delete theo nghiệp vụ | Không |

## 27. Kết luận

Để phân biệt chính xác **bỏ đối tượng con khỏi quan hệ** và **gọi remove()**, hãy luôn hỏi: **“Ta đang xóa một liên kết hay xóa một thực thể?”**

Bỏ child khỏi List/Set là thay đổi **association**. Khi **orphanRemoval=false**, entity con thường vẫn tồn tại; database có thể cập nhật FK hoặc xóa hàng join table. Với **orphanRemoval=true** trên quan hệ **@OneToMany/@OneToOne** có quyền sở hữu vòng đời riêng tư, child bị gỡ sẽ được xử lý xóa như orphan ở bước flush. Ngược lại, **EntityManager.remove(managedChild)** là yêu cầu xóa trực tiếp entity, độc lập với việc child có bị gỡ khỏi collection hay không.

**CascadeType.REMOVE** giải quyết tình huống khác: **xóa parent và lan thao tác remove tới children**, không đồng nghĩa gỡ collection element. Khi triển khai, cần giữ **cả hai phía quan hệ nhất quán**, tôn trọng **FK/NOT NULL**, trạng thái managed/detached, transaction/rollback và yêu cầu dữ liệu lịch sử.

Thiết kế đúng không phải luôn gọi remove cho mọi nút “Xóa”, mà là **thể hiện chính xác vòng đời của child theo domain**, rồi chọn mapping JPA, thao tác service và ràng buộc database tương ứng. Hãy kiểm chứng bằng dữ liệu sau flush/commit, không chỉ bằng số phần tử còn lại trong collection Java.
