# Phân biệt tải dữ liệu quan hệ và lan truyền thao tác trong JPA

Khi ánh xạ quan hệ giữa các entity bằng **Jakarta Persistence (JPA)**, lập trình viên thường gặp hai nhóm cấu hình đặt gần nhau trên các annotation `@OneToMany`, `@ManyToOne`, `@OneToOne` hoặc `@ManyToMany`:

- **Tải dữ liệu quan hệ (*fetching*)**: khi cần một entity, JPA có tải ngay những entity liên quan hay chờ đến khi ứng dụng truy cập quan hệ đó? Thuộc tính quan trọng là `fetch`, với `FetchType.LAZY` và `FetchType.EAGER`.
- **Lan truyền thao tác (*cascading*)**: khi ứng dụng yêu cầu `persist`, `merge`, `remove`, `refresh` hoặc `detach` trên một entity, thao tác có được truyền tiếp đến các entity liên quan không? Thuộc tính quan trọng là `cascade`, với các giá trị trong `CascadeType`.

Hai cơ chế giải quyết **hai bài toán khác nhau**. Một cơ chế quyết định **khi nào dữ liệu liên quan cần được lấy từ database**, cơ chế kia quyết định **những entity nào cùng nhận một thao tác vòng đời**. Có thể cấu hình tải trì hoãn mà vẫn tự động lưu entity con; cũng có thể tải quan hệ ngay nhưng hoàn toàn không cho phép xóa lan truyền.

Ví dụ:

```java
@OneToMany(
    mappedBy = "order",
    fetch = FetchType.LAZY,
    cascade = CascadeType.PERSIST
)
private List<OrderLine> lines = new ArrayList<>();
```

Khai báo này có nghĩa:

- `LAZY`: danh sách dòng đơn hàng được **dự kiến tải khi cần**, thay vì bắt buộc phải lấy toàn bộ ngay khi nạp đơn hàng.
- `PERSIST`: khi gọi `entityManager.persist(order)`, JPA **lan truyền thao tác persist** đến các dòng đơn hàng trong quan hệ.
- **Không có ý nghĩa** rằng việc tải danh sách tự động lưu dữ liệu, hoặc việc lưu đơn hàng bắt buộc phải truy vấn danh sách bằng cách eager loading.

Nắm chắc ranh giới này giúp tránh hai nhóm lỗi lớn: truy vấn SQL không kiểm soát vì cấu hình tải dữ liệu sai, và dữ liệu bị lưu/xóa ngoài ý muốn vì cấu hình cascade sai.

## 1. Mô hình quan hệ minh họa: đơn hàng và dòng đơn hàng

Giả sử hệ thống bán hàng có một đơn hàng `PurchaseOrder` chứa nhiều dòng `OrderLine`. Mỗi dòng thuộc về đúng một đơn hàng:

```text
PurchaseOrder (1)  -------------------- (*) OrderLine
     id                                      id
     orderNumber                             productCode
     lines                                   quantity
                                             order
```

Trong cơ sở dữ liệu quan hệ, có thể biểu diễn:

```sql
CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_number VARCHAR(50) NOT NULL UNIQUE
);

CREATE TABLE order_lines (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL REFERENCES purchase_orders(id),
    product_code VARCHAR(50) NOT NULL,
    quantity INTEGER NOT NULL CHECK (quantity > 0)
);
```

**Bảng `purchase_orders`**

| id | order_number |
| ---: | --- |
| 100 | PO-100 |
| 101 | PO-101 |

**Bảng `order_lines`**

| id | order_id | product_code | quantity |
| ---: | ---: | --- | ---: |
| 1 | 100 | KEYBOARD | 2 |
| 2 | 100 | MOUSE | 1 |
| 3 | 101 | MONITOR | 1 |

Quan hệ thực tế nằm ở khóa ngoại `order_lines.order_id`. JPA ánh xạ liên kết giữa đối tượng `PurchaseOrder` và tập hợp `OrderLine` vào khóa ngoại đó. **Việc cấu hình `fetch` hoặc `cascade` không thay thế khóa ngoại**, cũng không tự động xác định được cột sở hữu quan hệ.

### 1.1. Entity cha: PurchaseOrder

```java
package com.example.orders;

import java.util.ArrayList;
import java.util.List;
import jakarta.persistence.CascadeType;
import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.FetchType;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.OneToMany;
import jakarta.persistence.Table;

@Entity
@Table(name = "purchase_orders")
public class PurchaseOrder {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "order_number", nullable = false, unique = true)
    private String orderNumber;

    @OneToMany(
        mappedBy = "order",
        fetch = FetchType.LAZY,
        cascade = {CascadeType.PERSIST, CascadeType.MERGE}
    )
    private List<OrderLine> lines = new ArrayList<>();

    protected PurchaseOrder() {
        // Constructor không tham số cho JPA.
    }

    public PurchaseOrder(String orderNumber) {
        this.orderNumber = orderNumber;
    }

    public void addLine(String productCode, int quantity) {
        OrderLine line = new OrderLine(productCode, quantity);
        line.setOrder(this);
        lines.add(line);
    }

    public Long getId() {
        return id;
    }

    public String getOrderNumber() {
        return orderNumber;
    }

    public List<OrderLine> getLines() {
        return lines;
    }
}
```

### 1.2. Entity con: OrderLine

```java
package com.example.orders;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.FetchType;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.JoinColumn;
import jakarta.persistence.ManyToOne;
import jakarta.persistence.Table;

@Entity
@Table(name = "order_lines")
public class OrderLine {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "order_id", nullable = false)
    private PurchaseOrder order;

    @Column(name = "product_code", nullable = false, length = 50)
    private String productCode;

    @Column(nullable = false)
    private int quantity;

    protected OrderLine() {
    }

    public OrderLine(String productCode, int quantity) {
        this.productCode = productCode;
        this.quantity = quantity;
    }

    public void setOrder(PurchaseOrder order) {
        this.order = order;
    }

    public PurchaseOrder getOrder() {
        return order;
    }

    public String getProductCode() {
        return productCode;
    }

    public int getQuantity() {
        return quantity;
    }
}
```

Trong mapping trên:

- `PurchaseOrder.lines` là phía **không sở hữu** (*inverse side*) vì có `mappedBy = "order"`.
- `OrderLine.order` là phía **sở hữu quan hệ** (*owning side*), khai báo khóa ngoại bằng `@JoinColumn(name = "order_id")`.
- Phương thức `addLine()` cập nhật **cả hai phía** của quan hệ hai chiều để mô hình đối tượng nhất quán.
- Cascade được đặt từ đơn hàng đến dòng đơn hàng, vì ví dụ xem các dòng thuộc vòng đời nghiệp vụ của một đơn hàng.
- `OrderLine.order` không khai báo cascade trở lại đơn hàng, vì lưu hoặc xóa một dòng không nên mặc nhiên lưu/xóa đơn hàng cha.

Hai lớp sẽ được tái sử dụng để giải thích rõ tác dụng của từng cơ chế.

## 2. Fetching là gì?

**Fetching** quyết định cách provider JPA lấy dữ liệu quan hệ khi một entity được tải hoặc khi ứng dụng truy cập association.

Ví dụ:

```java
PurchaseOrder order =
    entityManager.find(PurchaseOrder.class, 100L);
```

Lời gọi này yêu cầu một `PurchaseOrder` theo khóa chính. Vì `PurchaseOrder` có `List<OrderLine> lines`, provider phải quyết định **có nạp các dòng đơn hàng ngay hay chưa**.

### 2.1. FetchType.LAZY

`FetchType.LAZY` yêu cầu **ưu tiên trì hoãn** việc tải dữ liệu liên quan cho đến khi thật sự cần. Đây là một *hint* theo hợp đồng JPA: provider có thể được phép lấy dữ liệu sớm hơn trong một số hoàn cảnh, nên không phải cam kết “sẽ luôn có đúng một truy vấn sau khi truy cập”.

Ví dụ:

```java
PurchaseOrder order =
    entityManager.find(PurchaseOrder.class, 100L);

String number = order.getOrderNumber();

// Có thể kích hoạt tải collection nếu collection chưa được khởi tạo.
int lineCount = order.getLines().size();
```

Một luồng SQL có thể xảy ra:

```sql
SELECT id, order_number
FROM purchase_orders
WHERE id = ?;

-- Khi truy cập order.getLines().size():
SELECT id, order_id, product_code, quantity
FROM order_lines
WHERE order_id = ?;
```

Đây là SQL **minh họa ý nghĩa**, không phải số câu lệnh hay cú pháp được bảo đảm. Provider có thể sử dụng cache, batching, cơ chế lazy khác hoặc truy vấn tối ưu theo cấu hình.

Lợi ích của LAZY: nếu trang chỉ cần số đơn hàng và mã đơn hàng, ứng dụng không cần tải cả tập hợp dòng sản phẩm. Cái giá phải trả là nếu tầng nghiệp vụ sau đó truy cập quan hệ, provider có thể phát sinh truy vấn bổ sung.

### 2.2. FetchType.EAGER

`FetchType.EAGER` yêu cầu provider **lấy dữ liệu của association một cách chủ động** để association được tải theo hợp đồng fetching. Ví dụ:

```java
@OneToMany(
    mappedBy = "order",
    fetch = FetchType.EAGER
)
private List<OrderLine> lines = new ArrayList<>();
```

Khi tải `PurchaseOrder`, provider phải đáp ứng yêu cầu eager fetching của quan hệ. Tuy nhiên, **EAGER không đồng nghĩa SQL luôn dùng một `JOIN`**. Provider có thể chọn:

- Một câu `SELECT` với `JOIN`.
- Một truy vấn lấy đơn hàng rồi một hoặc nhiều truy vấn phụ lấy dòng đơn hàng.
- Phương án khác phù hợp với persistence context, cache và cấu hình.

EAGER chỉ nói về **thời điểm/ý định tải**, không mô tả chính xác kế hoạch SQL. Nếu một entity có nhiều collection EAGER, việc tải có thể rất tốn bộ nhớ, phát sinh dữ liệu lặp do join hoặc nhiều truy vấn bổ sung.

### 2.3. Giá trị mặc định của JPA

Khi không khai báo `fetch`, các quan hệ có giá trị mặc định khác nhau:

| Loại quan hệ | Giá trị `fetch` mặc định trong JPA |
| --- | --- |
| `@ManyToOne` | `EAGER` |
| `@OneToOne` | `EAGER` |
| `@OneToMany` | `LAZY` |
| `@ManyToMany` | `LAZY` |

Đây là những mặc định của đặc tả. Trong ứng dụng lớn, lập trình viên thường chủ động khai báo `fetch = FetchType.LAZY` cho association phù hợp nhằm kiểm soát khối lượng dữ liệu tải. Với một số loại quan hệ và provider, để hiện thực lazy loading thực sự có thể cần cơ chế proxy, bytecode enhancement hoặc ràng buộc mapping nhất định.

Không nên suy luận rằng `@ManyToOne` mặc định EAGER là lựa chọn hiệu quả cho mọi câu truy vấn. Đặc biệt khi lấy nhiều entity con, EAGER có thể khiến provider phải nạp nhiều entity cha liên quan dù luồng xử lý không dùng chúng.

## 3. Cascade là gì?

**Cascade** xác định thao tác vòng đời nào trên entity nguồn được **lan truyền** sang entity đích trong quan hệ.

Ví dụ:

```java
@OneToMany(
    mappedBy = "order",
    cascade = CascadeType.PERSIST
)
private List<OrderLine> lines = new ArrayList<>();
```

Khi gọi:

```java
entityManager.persist(order);
```

JPA sẽ lan truyền **thao tác `persist`** từ `order` sang các `OrderLine` được tham chiếu qua association đó. Điều này giúp mã nghiệp vụ tạo một aggregate mà không phải gọi `persist()` riêng cho từng dòng khi mapping và trạng thái object hợp lệ.

**Cascade không quyết định thời điểm tải dữ liệu**. Một quan hệ có `cascade = PERSIST` vẫn có thể `fetch = LAZY`. Ngược lại, quan hệ EAGER không tự lan truyền `persist` hoặc `remove` nếu không khai báo cascade phù hợp.

### 3.1. Các CascadeType phổ biến

| CascadeType | Thao tác trên entity nguồn | Hành vi lan truyền chủ yếu |
| --- | --- | --- |
| `PERSIST` | `entityManager.persist(parent)` | Làm các entity liên quan phù hợp trở thành managed và được persist theo quy tắc JPA. |
| `MERGE` | `entityManager.merge(parent)` | Sao chép/đồng bộ trạng thái của các entity liên quan theo quy tắc `merge`. |
| `REMOVE` | `entityManager.remove(parent)` | Lan truyền thao tác xóa đến các entity liên quan. |
| `REFRESH` | `entityManager.refresh(parent)` | Làm mới các entity liên quan từ dữ liệu database theo cơ chế refresh. |
| `DETACH` | `entityManager.detach(parent)` | Tách các entity liên quan khỏi persistence context. |
| `ALL` | Bao gồm tất cả các giá trị trên. | Lan truyền toàn bộ các loại thao tác đã liệt kê. |

Trong Jakarta Persistence, `CascadeType` là tập hợp các loại thao tác vòng đời. **Không có `CascadeType.SAVE` hoặc `CascadeType.UPDATE` trong API chuẩn JPA**. Một số thư viện hay API riêng của Hibernate có khái niệm cascade khác, nhưng khi viết JPA portable nên dùng `CascadeType` của `jakarta.persistence`.

### 3.2. Cascade mặc định là gì?

Nếu không khai báo `cascade`, các annotation quan hệ JPA có mặc định **không lan truyền thao tác**:

```java
@ManyToOne
private Customer customer;

// Tương đương về cascade với khai báo không chứa loại cascade nào.
```

Điều này khác mặc định của `fetch`. Chẳng hạn `@ManyToOne` mặc định **EAGER** nhưng mặc định **không cascade**. Nghĩa là việc tải entity có thể tự lấy thêm `Customer`, trong khi gọi `persist` hoặc `remove` trên entity con không tự áp dụng cho `Customer`.

## 4. Hai câu hỏi độc lập trên cùng một quan hệ

Có thể kết hợp fetch và cascade theo nhiều cách:

| Fetch | Cascade | Ý nghĩa khi sử dụng |
| --- | --- | --- |
| `LAZY` | Không có | Tải association khi cần; các thao tác vòng đời không tự lan truyền. |
| `LAZY` | `PERSIST` | Tải relation theo nhu cầu; khi persist entity nguồn thì persist entity đích phù hợp. |
| `LAZY` | `PERSIST, MERGE` | Tải theo nhu cầu; lan truyền tạo mới và merge đồ thị entity. |
| `EAGER` | Không có | Association được tải chủ động, nhưng các thao tác vòng đời không tự lan truyền. |
| `EAGER` | `REMOVE` | Association được tải chủ động; xóa nguồn còn lan truyền xóa đích. Đây có thể là thiết kế nguy hiểm nếu đích được chia sẻ. |
| `LAZY` | `ALL` | Tải theo nhu cầu nhưng lan truyền mọi loại thao tác. Không nên dùng theo thói quen, đặc biệt khi có xóa hoặc refresh. |

Ví dụ:

```java
@ManyToOne(fetch = FetchType.LAZY)
private Customer customer;
```

Có nghĩa: **không có cascade**, dù quan hệ có thể tải trì hoãn.

```java
@ManyToOne(
    fetch = FetchType.EAGER,
    cascade = CascadeType.PERSIST
)
private Customer customer;
```

Có nghĩa: provider cần tải customer chủ động khi association được fetch; đồng thời `persist` trên entity chứa quan hệ có thể lan truyền đến customer. Việc cascade PERSIST cho một `Customer` vốn thường được chia sẻ bởi nhiều đơn hàng cần cân nhắc kỹ, vì có thể làm quy trình lưu thay đổi ngoài ý muốn.

**Không có quan hệ kéo theo:** LAZY không đồng nghĩa không cascade; EAGER không đồng nghĩa cascade; cascade REMOVE không đồng nghĩa collection bị eager loading.

## 5. Ví dụ: Persist đơn hàng và tự động Persist các dòng hàng

Với mapping `PurchaseOrder.lines` có `cascade = {PERSIST, MERGE}` trong mục đầu, ứng dụng có thể tạo đơn hàng và các dòng:

```java
PurchaseOrder order = new PurchaseOrder("PO-200");
order.addLine("KEYBOARD", 2);
order.addLine("MOUSE", 1);

entityManager.persist(order);
```

Trong một transaction hợp lệ, JPA nhận được thao tác `persist(order)`, sau đó lan truyền `persist` đến các `OrderLine` được liên kết. Kết quả dữ liệu mong đợi:

```text
purchase_orders
  (id = 200, order_number = 'PO-200')

order_lines
  (id = ..., order_id = 200, product_code = 'KEYBOARD', quantity = 2)
  (id = ..., order_id = 200, product_code = 'MOUSE', quantity = 1)
```

Giá trị ID thực tế do generator/database cấp; các con số chỉ minh họa. Với `GenerationType.IDENTITY`, provider có thể cần chạy `INSERT` sớm để biết khóa của bản ghi cha rồi chèn các dòng con theo khóa ngoại.

### 5.1. Một transaction resource-local hoàn chỉnh

Ví dụ trong Java SE, giả định `EntityManagerFactory` đã được tạo cho một persistence unit sử dụng `RESOURCE_LOCAL`:

```java
import jakarta.persistence.EntityManager;
import jakarta.persistence.EntityManagerFactory;
import jakarta.persistence.EntityTransaction;

public final class OrderCreator {
    private final EntityManagerFactory factory;

    public OrderCreator(EntityManagerFactory factory) {
        this.factory = factory;
    }

    public Long createOrder() {
        EntityManager em = factory.createEntityManager();

        try {
            EntityTransaction tx = em.getTransaction();

            try {
                tx.begin();

                PurchaseOrder order = new PurchaseOrder("PO-200");
                order.addLine("KEYBOARD", 2);
                order.addLine("MOUSE", 1);

                em.persist(order); // Cascade PERSIST đến các OrderLine.
                tx.commit();

                return order.getId();
            } catch (RuntimeException ex) {
                if (tx.isActive()) {
                    tx.rollback();
                }
                throw ex;
            }
        } finally {
            em.close();
        }
    }
}
```

Điều quan trọng là **chỉ gọi một thao tác `persist` trên cha nhưng vẫn có thể ghi cả cha và con**, nhờ cấu hình cascade và quan hệ hai chiều đã được cập nhật đúng.

### 5.2. Nếu không có CascadeType.PERSIST thì sao?

Giả sử thay mapping thành:

```java
@OneToMany(mappedBy = "order", fetch = FetchType.LAZY)
private List<OrderLine> lines = new ArrayList<>();
```

Khi đó:

```java
entityManager.persist(order);
```

chỉ là yêu cầu persist entity `order`. JPA **không được yêu cầu** tự persist các `OrderLine` thông qua association này. Với mô hình đang xét, các dòng mới có thể vẫn transient và không được chèn nếu không có thao tác persist riêng.

Cách quản lý thủ công:

```java
entityManager.persist(order);

for (OrderLine line : order.getLines()) {
    entityManager.persist(line);
}
```

Đây là lựa chọn hợp lệ nếu ứng dụng muốn tự kiểm soát từng entity cần lưu. Lưu ý trong các mapping khác, một entity chứa tham chiếu tới entity transient chưa được persist có thể gây lỗi tại flush/commit; loại lỗi phụ thuộc cấu trúc và phía sở hữu quan hệ.

### 5.3. Cascade PERSIST không thay thế cập nhật hai phía quan hệ

Trong ví dụ hai chiều, `OrderLine.order` giữ khóa ngoại. Nếu chỉ làm:

```java
order.getLines().add(line);
```

mà không đặt:

```java
line.setOrder(order);
```

thì **phía sở hữu quan hệ chưa phản ánh đúng association**. JPA không có trách nhiệm suy đoán rằng thêm vào inverse collection tương đương đã sửa owning side. Khi cột `order_id` bắt buộc, việc persist có thể gặp lỗi ràng buộc hoặc tạo quan hệ sai kỳ vọng.

Đó là lý do helper như `order.addLine(...)` cập nhật cả danh sách và tham chiếu của con. **Cascade quyết định lan truyền thao tác lifecycle; owning side quyết định cập nhật khóa ngoại.**

## 6. Ví dụ: Tải một đơn hàng có LAZY không kích hoạt Cascade

Giả sử trong transaction mới:

```java
PurchaseOrder order =
    entityManager.find(PurchaseOrder.class, orderId);

System.out.println(order.getOrderNumber());
```

Với `fetch = LAZY` của `lines`, provider có thể chưa cần tải các dòng. Chỉ khi ứng dụng thực sự truy cập:

```java
for (OrderLine line : order.getLines()) {
    System.out.println(line.getProductCode());
}
```

thì provider có thể chạy truy vấn tải collection.

**Không có lệnh `persist`, `merge` hoặc `remove` nào được gọi chỉ bởi việc đọc quan hệ.** Việc lấy dữ liệu không tự động yêu cầu cascade. Dữ liệu vẫn được quản lý trong persistence context theo vòng đời JPA, nhưng cascade configuration không phải một trigger chạy theo mỗi câu `SELECT`.

Nếu entity được tìm thấy và đã được managed, thay đổi một thuộc tính persistent của nó trong transaction có thể được phát hiện qua dirty checking. **Dirty checking là cơ chế quản lý trạng thái entity**, khác với việc cascade một lời gọi `merge` hoặc `persist`.

### 6.1. Khi rời persistence context

Với quan hệ lazy chưa được tải:

```java
PurchaseOrder detachedOrder;

EntityManager em = factory.createEntityManager();
try {
    detachedOrder = em.find(PurchaseOrder.class, orderId);
} finally {
    em.close();
}

// Collection có thể chưa được khởi tạo.
int size = detachedOrder.getLines().size();
```

Sau khi manager đóng, entity và collection proxy không còn context để truy vấn dữ liệu cần thiết. Với Hibernate, tình huống này thường gây `LazyInitializationException`. Một danh sách đã được khởi tạo đầy đủ trước khi đóng có thể vẫn đọc được, nhưng không nên dựa vào lazy loading hoạt động sau ranh giới persistence.

**CascadeType.PERSIST hoặc CascadeType.ALL không giải quyết lỗi lazy loading**. Cascade không giữ EntityManager mở, không tự tạo transaction mới và không biến association thành eager loading. Cách xử lý là thiết kế ranh giới truy vấn và dữ liệu cần trả về, chẳng hạn fetch join, entity graph hoặc DTO projection.

## 7. LAZY và vấn đề N+1 truy vấn

Một ví dụ điển hình:

```java
List<PurchaseOrder> orders = entityManager.createQuery(
    "SELECT o FROM PurchaseOrder o",
    PurchaseOrder.class
).getResultList();

for (PurchaseOrder order : orders) {
    System.out.println(order.getLines().size());
}
```

Nếu có 100 đơn hàng và các collection chưa được tải, provider có thể thực hiện:

```text
1 truy vấn: lấy danh sách 100 đơn hàng
100 truy vấn bổ sung: tải lines cho từng đơn hàng
------------------------------------------------
Tổng: có thể 101 truy vấn
```

Đây là kiểu **N+1 query problem**. Con số chính xác phụ thuộc cache, batch fetching và cách thực thi của provider, nhưng ý chính là số lượt truy vấn có thể tăng theo số entity cha.

### 7.1. Giải pháp fetch join theo nhu cầu

Nếu chức năng thực sự phải hiển thị đơn hàng cùng toàn bộ dòng hàng, có thể fetch join trong JPQL:

```java
List<PurchaseOrder> orders = entityManager.createQuery(
        "SELECT DISTINCT o FROM PurchaseOrder o " +
        "LEFT JOIN FETCH o.lines " +
        "WHERE o.id IN :ids",
        PurchaseOrder.class
    )
    .setParameter("ids", List.of(100L, 101L))
    .getResultList();
```

`JOIN FETCH` là **lựa chọn chiến lược tải cho truy vấn này**. Nó không sửa vĩnh viễn `fetch` trên entity và **không bật cascade**. Vì mỗi đơn hàng có nhiều dòng, kết quả SQL join có thể có nhiều hàng cho cùng một đơn hàng; `DISTINCT` trong JPQL nhằm mô tả mong muốn loại trùng entity cha, còn cách SQL/provider xử lý thực tế phụ thuộc phiên bản.

Fetch join một collection có thể ảnh hưởng đến **phân trang**: giới hạn hàng SQL sau join không nhất thiết tương đương giới hạn số đơn hàng. Với danh sách có paging, thường cần lấy trang ID của entity cha trước, sau đó tải các collection cho những ID ấy bằng truy vấn riêng hoặc chiến lược phù hợp.

### 7.2. Entity graph cũng chỉ điều chỉnh tải dữ liệu

Một cách khác là tạo fetch graph cho truy vấn:

```java
import jakarta.persistence.EntityGraph;

EntityGraph<PurchaseOrder> graph =
        entityManager.createEntityGraph(PurchaseOrder.class);
graph.addAttributeNodes("lines");

List<PurchaseOrder> orders = entityManager.createQuery(
        "SELECT o FROM PurchaseOrder o WHERE o.id IN :ids",
        PurchaseOrder.class
    )
    .setParameter("ids", List.of(100L, 101L))
    .setHint("jakarta.persistence.fetchgraph", graph)
    .getResultList();
```

`"jakarta.persistence.fetchgraph"` là hint của Jakarta Persistence hiện đại; các dự án JPA dùng namespace `javax.persistence` cũ dùng tên hint tương ứng của phiên bản đó. Entity graph định nghĩa những association cần được tải theo kế hoạch truy vấn. Nó **không truyền `persist`/`remove`** và không thay thế cấu hình cascade.

Provider có thể chọn cách lấy dữ liệu khác nhau để đáp ứng graph. Dù dùng fetch join hay entity graph, hãy kiểm soát dữ liệu thực sự cần và tránh kéo quá nhiều collection trong một lần.

### 7.3. Lúc nào nên dùng DTO projection?

Nếu API chỉ cần:

```text
OrderSummary(
    orderId = 100,
    orderNumber = "PO-100",
    lineCount = 2
)
```

thì không nhất thiết phải nạp toàn bộ `OrderLine` dưới dạng managed entity. Một truy vấn aggregate hoặc DTO projection có thể trực tiếp lấy cột và số lượng cần thiết. Đây là quyết định **truy vấn/hiệu năng**, vẫn độc lập với cascade.

## 8. CascadeType.MERGE và trạng thái detached

Trong JPA, `merge` xử lý trạng thái của entity **detached** hoặc entity mới theo hợp đồng merge; nó trả về **một instance managed**, có thể khác đối tượng được truyền vào.

Ví dụ trong một hệ thống nhận dữ liệu chỉnh sửa từ tầng giao diện:

```java
PurchaseOrder detachedOrder = /* đơn hàng đã rời context */;

// Trong transaction và persistence context mới:
PurchaseOrder managedOrder =
    entityManager.merge(detachedOrder);
```

Nếu `PurchaseOrder.lines` có `cascade = MERGE`, thao tác merge có thể được truyền đến các dòng liên quan để trạng thái của chúng được sao chép vào những instance managed tương ứng.

Nếu **không** có cascade MERGE, không nên giả định toàn bộ đồ thị detached được merge cùng lúc chỉ vì entity cha có một collection. Các association của managed instance được xử lý theo quy tắc JPA, nhưng trạng thái sửa đổi trên từng entity con detached có thể không được cập nhật như mong đợi.

### 8.1. Cascade MERGE khác với FetchType.EAGER

- `MERGE` nói về **lan truyền yêu cầu sao chép trạng thái** khi gọi `entityManager.merge(...)`.
- `EAGER` nói về **tải dữ liệu quan hệ** trong lúc lấy entity.
- Một thao tác merge có thể khiến provider cần nạp/truy xuất thêm dữ liệu để giải quyết trạng thái, kể cả trên mapping LAZY. Đây là hệ quả thực thi của thao tác merge, **không có nghĩa cấu hình fetch đã bị đổi thành EAGER**.

Cẩn trọng với dữ liệu detached đã cũ: merge một đồ thị lớn không được kiểm soát có thể ghi đè thay đổi từ giao dịch khác hoặc gây xung đột version. Đối với API cập nhật, cách dễ kiểm soát thường là **tải entity managed trong transaction, kiểm tra quyền và quy tắc nghiệp vụ, rồi cập nhật những field được cho phép**. Dùng `@Version` khi cần optimistic locking.

### 8.2. Không nhầm merge với persist

`persist` đưa entity mới vào context và lên lịch chèn vào database. `merge` tạo/tìm bản managed để sao chép trạng thái của entity nguồn theo quy tắc JPA. Với entity mới, merge cũng có thể dẫn đến tạo bản ghi, nhưng **đối tượng nguồn truyền vào `merge` không tự trở thành instance managed được trả về**.

Do vậy, nếu cần tiếp tục thao tác trong transaction sau merge, sử dụng giá trị trả về:

```java
PurchaseOrder managed = entityManager.merge(detachedOrder);

// Tiếp tục thao tác với "managed" theo quy tắc nghiệp vụ.
```

Cascade MERGE chỉ làm việc trên các association được cấu hình lan truyền, không tự định nghĩa mối quan hệ sở hữu khóa ngoại hay thứ tự thao tác nghiệp vụ.

## 9. CascadeType.REMOVE: xóa lan truyền

`CascadeType.REMOVE` yêu cầu JPA truyền thao tác xóa sang các entity liên quan khi xóa entity nguồn.

Ví dụ một đơn hàng và các dòng của nó có **vòng đời sở hữu hoàn toàn**: khi đơn hàng bị xóa, các dòng không còn ý nghĩa độc lập. Có thể cấu hình:

```java
@OneToMany(
    mappedBy = "order",
    fetch = FetchType.LAZY,
    cascade = {
        CascadeType.PERSIST,
        CascadeType.MERGE,
        CascadeType.REMOVE
    }
)
private List<OrderLine> lines = new ArrayList<>();
```

Sau đó:

```java
PurchaseOrder order =
    entityManager.find(PurchaseOrder.class, orderId);

entityManager.remove(order);
```

Trong transaction hợp lệ, `REMOVE` lan truyền đến `OrderLine` phù hợp. Provider phải bảo đảm SQL cuối cùng tuân thủ khóa ngoại; nó có thể phải truy vấn dữ liệu liên quan hoặc xử lý các entity đang được quản lý trước khi phát lệnh `DELETE`.

**Việc xử lý xóa liên quan không có nghĩa bạn buộc phải khai báo `fetch = EAGER`.** Một mapping có thể vẫn LAZY, còn hoạt động remove sẽ truy cập dữ liệu cần thiết theo cơ chế provider để lan truyền thao tác.

### 9.1. Nguy cơ khi cascade REMOVE sang entity được chia sẻ

Giả sử nhiều đơn hàng cùng tham chiếu một khách hàng:

```java
@ManyToOne(fetch = FetchType.LAZY)
private Customer customer;
```

Nếu vô tình viết:

```java
@ManyToOne(
    fetch = FetchType.LAZY,
    cascade = CascadeType.REMOVE
)
private Customer customer;
```

thì `remove(order)` có thể **truyền xóa đến customer**. Điều này thường sai vì `Customer` có vòng đời riêng, có thể thuộc nhiều đơn hàng khác. Hệ thống có thể xóa nhầm dữ liệu hoặc gặp lỗi khóa ngoại.

Tương tự, `CascadeType.REMOVE` và `CascadeType.ALL` thường nguy hiểm trên `@ManyToMany`, vì hai bên có thể cùng được nhiều entity khác tham chiếu. Khi xóa một bên của quan hệ nhiều-nhiều, nghiệp vụ thường chỉ muốn xóa **bản ghi liên kết trong join table**, không muốn xóa entity chia sẻ ở phía đối diện.

Các quy tắc portable của JPA về cascade remove nhấn mạnh quan hệ sở hữu chặt như `@OneToOne` và `@OneToMany`; việc áp dụng cho các association chia sẻ như `@ManyToMany` không nên được coi là lựa chọn an toàn hoặc portable.

### 9.2. Cascade REMOVE khác với ON DELETE CASCADE ở database

`CascadeType.REMOVE` là cơ chế **JPA truyền thao tác lifecycle qua đồ thị entity**. Còn:

```sql
FOREIGN KEY (order_id)
    REFERENCES purchase_orders(id)
    ON DELETE CASCADE
```

là ràng buộc database, có thể tự xóa các dòng phụ thuộc khi SQL xóa đơn hàng được thực thi. Hai cơ chế hoạt động ở tầng khác nhau.

Một số provider có tính năng tối ưu sử dụng database cascade, nhưng **không nên coi `CascadeType.REMOVE` tự động thêm `ON DELETE CASCADE` vào schema**. Ngược lại, database cascade có thể xóa các hàng mà JPA persistence context đang giữ, nên cần hiểu ảnh hưởng đến entity state/cache khi kết hợp.

## 10. orphanRemoval: xóa phần tử bị tách khỏi quan hệ

Một vấn đề dễ nhầm khác: **xóa entity cha** khác với **xóa một phần tử khỏi danh sách con của entity cha**.

Ví dụ:

```java
PurchaseOrder order =
    entityManager.find(PurchaseOrder.class, orderId);

OrderLine line = order.getLines().get(0);
order.getLines().remove(line);
```

Nếu quan hệ chỉ có `cascade = REMOVE`, việc `remove(line)` **khỏi Java collection** không đồng nghĩa ứng dụng đã gọi `entityManager.remove(line)`. Cascade REMOVE áp dụng khi **entity nguồn bị remove**, không phải với mọi thao tác `Collection.remove()`.

Nếu nghiệp vụ quy định dòng hàng không thể tồn tại độc lập khi bị gỡ khỏi đơn, JPA có **`orphanRemoval = true`** trên `@OneToMany` hoặc `@OneToOne`:

```java
@OneToMany(
    mappedBy = "order",
    fetch = FetchType.LAZY,
    cascade = {CascadeType.PERSIST, CascadeType.MERGE},
    orphanRemoval = true
)
private List<OrderLine> lines = new ArrayList<>();
```

Khi một `OrderLine` đang được quản lý bị loại khỏi association phù hợp, provider có thể lên lịch xóa dòng đó trong quá trình flush theo quy tắc orphan removal.

### 10.1. Helper duy trì hai phía quan hệ

Trong entity `PurchaseOrder` có thể thêm:

```java
public void removeLine(OrderLine line) {
    if (lines.remove(line)) {
        line.setOrder(null);
    }
}
```

Phương thức giả định `lines` là collection được JPA quản lý và `line` là phần tử hiện có. Với `orphanRemoval = true`, JPA có thể xử lý xóa entity con khi quan hệ bị phá vỡ theo quy tắc của nó. Việc gỡ quan hệ phải diễn ra trong transaction và context thích hợp.

Trong schema có `order_id NOT NULL`, nếu **không có orphanRemoval**, chỉ đặt `line.order = null` có thể dẫn đến một `UPDATE` vi phạm `NOT NULL` ở database thay vì xóa dòng. Điều này minh họa vì sao quyết định “gỡ liên kết” hay “xóa dòng con” cần rõ ràng trong thiết kế.

### 10.2. So sánh ba tình huống

| Tình huống | Cascade REMOVE | orphanRemoval |
| --- | --- | --- |
| Gọi `entityManager.remove(order)` | Lan truyền xóa con nếu mapping có `REMOVE`. | Với quan hệ sở hữu con phù hợp, orphan removal cũng liên quan đến vòng đời xóa khi parent bị remove. |
| Gỡ một `line` khỏi `order.lines` nhưng vẫn giữ `order` | Không tự có nghĩa gọi `remove(line)`. | Có thể lên lịch xóa dòng con bị bỏ khỏi association. |
| Thay một entity con bằng entity khác | Không mặc nhiên xóa cái cũ chỉ vì thay tham chiếu. | Có thể xem cái cũ là orphan và xóa theo quy tắc JPA. |

`orphanRemoval` dành cho quan hệ **vòng đời phụ thuộc và sở hữu riêng**, điển hình aggregate parent-child. Không nên dùng nó như công cụ xóa một entity còn được chia sẻ bởi nhiều thành phần nghiệp vụ.

Cần chú ý với collection/association đến entity mới, detached hoặc bị chuyển chủ sở hữu: đặc tả có giới hạn và lưu ý riêng về orphan removal. Không nên tùy tiện chuyển một child đang managed từ một parent sang parent khác mà kỳ vọng mỗi provider đều tự hiểu đó là thao tác không xóa.

## 11. CascadeType.REFRESH, DETACH và ALL

Ngoài `PERSIST`, `MERGE`, `REMOVE`, các loại cascade còn lại cũng là **lan truyền hành động**, không phải chiến lược tải thường xuyên.

### 11.1. CascadeType.REFRESH

`entityManager.refresh(entity)` yêu cầu nạp lại trạng thái persistent của entity từ database để làm mới managed entity theo quy tắc refresh. Nếu association khai báo `CascadeType.REFRESH`, thao tác refresh có thể được truyền đến entity liên quan.

```java
@OneToMany(
    mappedBy = "order",
    cascade = CascadeType.REFRESH
)
private List<OrderLine> lines;
```

Khi gọi:

```java
entityManager.refresh(order);
```

provider có thể làm mới cả các dòng theo cascade. Việc này có thể khiến trạng thái thay đổi chưa flush trên những entity được refresh bị thay thế bởi dữ liệu database. **REFRESH không phải một cách cấu hình fetch EAGER**; nó chỉ tác động khi thao tác refresh xảy ra.

### 11.2. CascadeType.DETACH

`entityManager.detach(order)` tách `order` khỏi persistence context. Với `CascadeType.DETACH`, thao tác detach có thể được lan truyền đến các entity liên quan.

```java
@OneToMany(
    mappedBy = "order",
    cascade = CascadeType.DETACH
)
private List<OrderLine> lines;
```

`detach` khiến các entity bị tách không còn được tự động theo dõi thay đổi. Nó **không đóng EntityManager** và cũng không xóa các hàng database. Nếu dùng không chủ đích, phần code sau đó có thể hiểu sai rằng sửa field trên entity detached vẫn được JPA tự flush.

### 11.3. CascadeType.ALL

`CascadeType.ALL` tương đương việc bật mọi kiểu cascade tiêu chuẩn nói trên:

```java
@OneToMany(
    mappedBy = "order",
    cascade = CascadeType.ALL,
    orphanRemoval = true
)
private List<OrderLine> lines = new ArrayList<>();
```

Cấu hình này có thể hợp lý khi **toàn bộ vòng đời của các dòng hàng hoàn toàn phụ thuộc đơn hàng**. Nhưng `ALL` bao gồm cả `REMOVE`, `REFRESH` và `DETACH`, nên không dùng chỉ vì muốn tiện lợi khi persist.

Khi đọc một mapping có `ALL`, hãy đặt câu hỏi: “Nếu xóa, refresh hoặc detach entity nguồn, những entity đích nào cũng sẽ chịu tác động?” Nếu câu trả lời không phù hợp domain, liệt kê từng loại cascade cần dùng thay vì `ALL`.

## 12. Fetching và Cascade có thể tác động hiệu năng theo các cách khác nhau

Mặc dù độc lập về **ý nghĩa cấu hình**, hai cơ chế vẫn cùng chạy trên persistence context và có thể ảnh hưởng chi phí thực tế.

### 12.1. Fetching ảnh hưởng dữ liệu được đọc

- `EAGER` có thể kéo nhiều bảng/quan hệ vào bộ nhớ ngay khi nạp entity nguồn.
- `LAZY` tránh đọc dữ liệu khi chưa cần, nhưng truy cập lặp lại có thể gây N+1.
- `JOIN FETCH` hoặc entity graph có thể giúp lấy đúng dữ liệu cần cho một use case.
- Provider có thể có batch fetch, second-level cache hoặc các tối ưu khác; việc đo SQL thực tế thường quan trọng hơn giả định dựa trên annotation.

### 12.2. Cascade ảnh hưởng quy mô thao tác ghi/quản lý trạng thái

- `PERSIST` trên một collection lớn có thể tạo nhiều entity managed và nhiều lệnh `INSERT`.
- `MERGE` trên một đồ thị detached sâu có thể yêu cầu nhiều thao tác đọc/ghi để đồng bộ.
- `REMOVE` trên aggregate lớn có thể gây nhiều lệnh `DELETE` và truy vấn phục vụ cascade.
- `REFRESH` lan truyền có thể tải lại nhiều entity không cần thiết.

**Không thể dùng `fetch = LAZY` như công tắc chặn tác động của cascade REMOVE**. Nếu nghiệp vụ yêu cầu xóa tất cả con, provider vẫn phải xử lý vòng đời các con khi xóa cha, bằng chiến lược SQL phù hợp.

### 12.3. Tập hợp lớn: tránh nạp nguyên graph khi không cần

Giả sử một khách hàng có hàng chục nghìn đơn hàng. Nếu đặt:

```java
@OneToMany(
    mappedBy = "customer",
    fetch = FetchType.EAGER,
    cascade = CascadeType.ALL
)
private List<PurchaseOrder> orders;
```

thì hai quyết định rủi ro cùng tồn tại:

1. Nạp khách hàng có thể buộc hệ thống xử lý lượng lớn đơn hàng liên quan dù màn hình chỉ cần tên.
2. Xóa/merge/refresh khách hàng có thể truyền thao tác đến toàn bộ đơn hàng, một hành vi nghiệp vụ rất nguy hiểm nếu không dự kiến.

Thông thường, những đơn hàng đã hoàn tất có vòng đời độc lập về pháp lý/nghiệp vụ. Không nên mặc định rằng khách hàng “sở hữu” các đơn hàng theo nghĩa được phép cascade REMOVE. Tách quan hệ đọc/truy vấn khỏi quyết định lan truyền thao tác sẽ dẫn đến mapping dễ kiểm soát hơn.

## 13. Spring Data JPA: save, @Transactional và EntityGraph

Trong ứng dụng Spring Boot, những cơ chế JPA vẫn giữ nguyên nhưng một số lời gọi được bọc bởi framework.

Giả sử repository:

```java
import org.springframework.data.jpa.repository.JpaRepository;

public interface PurchaseOrderRepository
        extends JpaRepository<PurchaseOrder, Long> {
}
```

Khi service tạo một đơn hàng mới và gọi `save(order)`, Spring Data JPA thường quyết định gọi `persist` hoặc `merge` theo cơ chế nhận diện trạng thái entity mới/đã tồn tại. **Đó vẫn là các thao tác JPA**, nên cascade PERSIST/MERGE từ mapping vẫn có ý nghĩa tương ứng.

Ví dụ:

```java
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class OrderService {
    private final PurchaseOrderRepository orders;

    public OrderService(PurchaseOrderRepository orders) {
        this.orders = orders;
    }

    @Transactional
    public Long createOrder() {
        PurchaseOrder order = new PurchaseOrder("PO-300");
        order.addLine("KEYBOARD", 2);
        order.addLine("MOUSE", 1);

        PurchaseOrder saved = orders.save(order);
        return saved.getId();
    }
}
```

Ví dụ giả định ứng dụng đã cấu hình Spring Data JPA, entity và generator tương ứng. Gọi `save` **không tự gán thêm CascadeType** cho mapping quan hệ. Nếu `lines` không được cấu hình cascade PERSIST khi tạo entity mới, phải điều phối việc lưu child một cách thích hợp.

### 13.1. @Transactional giúp điều gì cho Lazy loading?

`@Transactional` thường giữ một persistence context gắn với transaction trong thời gian thực thi service qua Spring transaction interceptor. Việc truy cập collection LAZY **trong phạm vi context còn hoạt động** có thể kích hoạt truy vấn và lấy dữ liệu cần thiết.

```java
@Transactional(readOnly = true)
public OrderSummary loadSummary(Long id) {
    PurchaseOrder order = orders.findById(id)
        .orElseThrow();

    // Nếu cần, đọc lines khi context còn hoạt động.
    int count = order.getLines().size();

    return new OrderSummary(order.getId(), count);
}
```

Trong ví dụ, `OrderSummary` là DTO, chẳng hạn:

```java
public record OrderSummary(Long id, int lineCount) {}
```

Điều này giải quyết ranh giới tải dữ liệu nhưng không tự chữa N+1. Nếu màn hình cần danh sách nhiều đơn hàng cùng số lượng dòng, nên thiết kế truy vấn aggregate hoặc fetch plan phù hợp thay vì lặp tải collection.

### 13.2. @EntityGraph điều chỉnh fetch, không điều chỉnh cascade

Spring Data JPA hỗ trợ `@EntityGraph` cho một số phương thức repository:

```java
import java.util.Optional;
import org.springframework.data.jpa.repository.EntityGraph;
import org.springframework.data.jpa.repository.JpaRepository;

public interface PurchaseOrderRepository
        extends JpaRepository<PurchaseOrder, Long> {

    @EntityGraph(attributePaths = "lines")
    Optional<PurchaseOrder> findWithLinesById(Long id);
}
```

Annotation này yêu cầu một fetch plan có `lines` khi truy vấn qua phương thức. Nó **không tương đương `cascade = ALL`** và không khiến việc save/xóa lan truyền khác mapping ban đầu.

Một hệ thống cũng có thể dùng Open Session in View để giữ context qua phần xử lý web, nhưng điều đó không thay thế thiết kế transaction và dễ khiến truy vấn phát sinh ở tầng hiển thị. Cách kiểm soát rõ ràng thường là lấy dữ liệu đủ dùng ở service/repository và trả DTO.

## 14. Những hiểu lầm thường gặp

### “Đặt LAZY thì khi xóa cha, con sẽ không bị xóa”

Sai. Nếu association có cascade REMOVE, thao tác xóa vẫn phải được xử lý theo mapping. LAZY chỉ điều chỉnh fetching, không vô hiệu hóa cascade.

### “Đặt EAGER thì persist(order) cũng lưu tất cả lines”

Sai. EAGER nói về tải dữ liệu quan hệ, không cấp quyền lan truyền persist. Muốn lưu các line mới qua `persist(order)` cần cascade PERSIST hoặc thao tác persist rõ ràng cho line.

### “CascadeType.ALL nghĩa là tải tất cả quan hệ”

Sai. `ALL` là tất cả **loại cascade lifecycle**, không có nghĩa eager load toàn bộ association.

### “CascadeType.REMOVE nghĩa là remove khỏi collection thì row tự bị xóa”

Không nhất thiết. Cascade REMOVE lan truyền khi entity nguồn bị remove. Gỡ child khỏi association và xóa orphan là bài toán của `orphanRemoval` và quyền sở hữu quan hệ.

### “Chỉ cần sửa inverse collection thì khóa ngoại được cập nhật”

Không đúng trong quan hệ hai chiều thông thường. Với `@OneToMany(mappedBy = "order")`, `OrderLine.order` là owning side. Code nghiệp vụ nên giữ hai phía nhất quán.

### “@ManyToOne luôn LAZY giống @OneToMany”

Không đúng theo mặc định JPA. `@ManyToOne` và `@OneToOne` mặc định EAGER; `@OneToMany` và `@ManyToMany` mặc định LAZY.

### “EAGER chắc chắn tạo một JOIN, nên không có N+1”

Không. Provider có thể sử dụng truy vấn phụ để thỏa mãn eager fetching. Cần quan sát SQL thực tế và thiết kế fetch plan cho từng use case.

### “Cascade MERGE biến đối tượng detached ban đầu thành managed”

Không. `merge` trả về **managed instance**; đối tượng truyền vào vẫn có thể detached. Cascade MERGE yêu cầu provider xử lý các entity liên quan theo quy tắc merge, không thay đổi bản chất này.

### “Cấu hình cascade có thể thay thế transaction”

Không. Persist/merge/remove vẫn cần ranh giới transaction phù hợp để thay đổi được lưu bền vững. Cascade quyết định phạm vi entity chịu thao tác, không tạo đảm bảo commit riêng hay thay thế rollback.

### “Có CascadeType.REMOVE thì không cần khóa ngoại database”

Không. Constraint khóa ngoại tiếp tục bảo vệ tính toàn vẹn quan hệ. Cascade JPA có thể quyết định xóa con trước cha, nhưng dữ liệu vẫn phải tuân thủ schema và những nguồn ghi ngoài JPA.

## 15. Cách chọn fetch và cascade theo từng quan hệ

Các cấu hình sau minh họa tư duy thiết kế, không phải công thức bất biến.

| Quan hệ nghiệp vụ | Fetch thường cân nhắc | Cascade thường cân nhắc | Lý do |
| --- | --- | --- | --- |
| `OrderLine → PurchaseOrder` | `LAZY` | Không cascade | Đọc dòng không luôn cần toàn bộ đơn hàng; xóa dòng không được xóa cha. |
| `PurchaseOrder → OrderLine` | `LAZY` | `PERSIST, MERGE`; có thể `REMOVE`/`orphanRemoval` nếu vòng đời sở hữu chặt | Dòng là thành phần của đơn; tải theo nhu cầu, lan truyền thao tác phù hợp aggregate. |
| `PurchaseOrder → Customer` | `LAZY` | Thường không cascade | Khách hàng tồn tại độc lập với một đơn hàng. |
| `Student ↔ Course` qua `@ManyToMany` | `LAZY` | Thường không cascade REMOVE | Cả sinh viên và khóa học là đối tượng được chia sẻ. |
| `User → Profile` một-một sở hữu riêng | `LAZY` nếu provider hỗ trợ phù hợp | `PERSIST, MERGE`, có thể `REMOVE`/`orphanRemoval` | Profile có thể phụ thuộc vòng đời user; cần cân nhắc tải và xóa riêng. |
| `Catalog → Product` trong hệ thống sản phẩm lớn | `LAZY` | Không mặc định `ALL` | Xóa catalog chưa chắc được phép xóa sản phẩm đang dùng ở nơi khác. |

Để quyết định chính xác hơn, hãy tự hỏi theo **hai trục riêng**:

**Trục A — Truy cập dữ liệu:**

1. Màn hình hoặc tác vụ có luôn cần entity liên quan không?
2. Cần một entity, một collection nhỏ hay hàng nghìn bản ghi?
3. Truy vấn trả một entity hay danh sách có phân trang?
4. Có thể trả về DTO/projection không?
5. Nên dùng LAZY, query fetch join, entity graph hoặc truy vấn chuyên biệt nào?

**Trục B — Vòng đời nghiệp vụ:**

1. Entity đích có tồn tại độc lập với entity nguồn không?
2. Khi tạo cha, con có luôn phải được tạo theo không?
3. Khi sửa detached graph, có nên merge toàn bộ con không?
4. Khi xóa cha, con có được phép xóa theo không?
5. Khi gỡ con khỏi collection, con là orphan phải xóa hay chỉ được chuyển sang quan hệ khác?

Cấu hình `fetch` dựa trên **nhu cầu đọc và chi phí truy vấn**; cấu hình `cascade` dựa trên **ranh giới sở hữu và quy tắc vòng đời nghiệp vụ**.

## 16. Bài tập thực hành có hướng dẫn

### Bài tập 1: LAZY + PERSIST

Cho mapping:

```java
@OneToMany(
    mappedBy = "order",
    fetch = FetchType.LAZY,
    cascade = CascadeType.PERSIST
)
private List<OrderLine> lines;
```

**Câu hỏi:** Nếu gọi `persist(order)` với hai child mới đã được liên kết đúng, child có thể được lưu không? Khi gọi `find(order)` ở transaction sau, lines có chắc được tải ngay không?

**Giải thích:** PERSIST có thể lan truyền để lưu child mới. LAZY không bắt buộc tải lines ngay khi chỉ tìm order; provider có thể trì hoãn đến khi truy cập, trong giới hạn hợp đồng fetching và cấu hình.

### Bài tập 2: EAGER không có cascade

Cho mapping:

```java
@ManyToOne(fetch = FetchType.EAGER)
private Customer customer;
```

**Câu hỏi:** Khi tải OrderLine, customer có thể được provider lấy cùng lúc hoặc bằng truy vấn phụ không? Khi xóa OrderLine, customer có tự bị xóa không?

**Giải thích:** EAGER yêu cầu tải customer chủ động, nhưng không quyết định phải JOIN. Vì không có cascade REMOVE, xóa line không có yêu cầu lan truyền xóa customer.

### Bài tập 3: REMOVE và orphanRemoval

Cho hai hành động:

```java
entityManager.remove(order);
```

và:

```java
order.removeLine(line);
```

**Câu hỏi:** Cơ chế nào liên quan trực tiếp đến mỗi hành động?

**Giải thích:** Khi remove order, cascade REMOVE có thể lan truyền xóa child. Khi gỡ một line mà vẫn giữ order, orphanRemoval phù hợp nếu line không còn được phép tồn tại ngoài aggregate. Không nên coi hai thao tác là một.

### Bài tập 4: Xử lý N+1

Trang danh sách trả 50 đơn hàng, mỗi dòng hiển thị số lượng `OrderLine`. Đoạn code lặp `order.getLines().size()` tạo nhiều truy vấn.

**Hướng giải quyết:** Cân nhắc truy vấn tổng hợp đếm line theo order, DTO projection, batch fetching hoặc fetch plan phù hợp. Không đổi cascade thành `ALL` và không mặc định bật `EAGER` trên mọi collection. Nếu dùng fetch join collection, cần xử lý tác động tới phân trang và số hàng SQL.

### Bài tập 5: Quan hệ nhiều-nhiều

Một sản phẩm có thể nằm trong nhiều chương trình khuyến mãi; một chương trình chứa nhiều sản phẩm.

**Câu hỏi:** Có nên đặt `cascade = REMOVE` từ promotion sang product để khi kết thúc promotion sẽ tự xóa product không?

**Giải thích:** Thông thường không, vì product là entity được chia sẻ và có vòng đời riêng. Nên xử lý việc xóa liên kết ở join table hoặc thiết kế một entity liên kết nếu quan hệ có thuộc tính nghiệp vụ.

## 17. Ghi nhớ cốt lõi

**Fetching và cascading là hai quyết định độc lập khi ánh xạ quan hệ trong JPA.** Fetching với `LAZY`/`EAGER` kiểm soát nhu cầu và thời điểm tải dữ liệu liên quan; cascade với `PERSIST`, `MERGE`, `REMOVE`, `REFRESH`, `DETACH` hoặc `ALL` kiểm soát việc **lan truyền một thao tác vòng đời** trên đồ thị entity.

Một quan hệ **LAZY vẫn có thể cascade PERSIST, MERGE hoặc REMOVE**; một quan hệ **EAGER vẫn có thể không cascade thao tác nào**. `orphanRemoval` liên quan đến entity con bị gỡ khỏi quan hệ sở hữu chặt, khác với cascade REMOVE khi xóa entity cha. `JOIN FETCH` và entity graph giúp tối ưu truy vấn, không thay đổi quyền lan truyền thao tác.

Khi thiết kế quan hệ, hãy xác định độc lập **dữ liệu nào cần được tải cho từng use case** và **entity nào thực sự thuộc vòng đời của entity nào**. Từ đó chọn fetch plan để kiểm soát SQL, chọn cascade để bảo đảm tính đúng đắn nghiệp vụ, và giữ transaction cùng khóa ngoại database làm nền tảng toàn vẹn dữ liệu.
