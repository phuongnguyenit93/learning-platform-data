# Thực hiện phép nối tường minh và truy cập đường dẫn quan hệ trong JPQL

Trong **Jakarta Persistence (JPA)**, entity thường liên kết với nhau qua các annotation như `@ManyToOne`, `@OneToMany`, `@OneToOne` hoặc `@ManyToMany`. Khi cần lấy dữ liệu từ nhiều entity liên quan, **Java Persistence Query Language (JPQL)** cung cấp hai cách diễn đạt quan trọng:

- **Truy cập đường dẫn quan hệ** (*relationship path navigation*): đi từ một entity sang các thuộc tính qua dấu chấm, ví dụ `o.customer.name`.
- **Phép nối tường minh** (*explicit join*): dùng `JOIN` hoặc `LEFT JOIN` để đặt bí danh cho entity liên quan, ví dụ `JOIN o.customer c` hoặc `LEFT JOIN o.lines l`.

Ví dụ:

```jpql
SELECT o
FROM PurchaseOrder o
WHERE o.customer.name = :customerName
```

Và:

```jpql
SELECT o
FROM PurchaseOrder o
JOIN o.customer c
WHERE c.name = :customerName
```

Cả hai truy vấn đều có thể tìm đơn hàng theo tên khách hàng. Nhưng đường dẫn qua dấu chấm và phép nối tường minh **không hoàn toàn thay thế được nhau** trong mọi tình huống. Khi phải đi qua collection, giữ những entity không có quan hệ đích, điều kiện ở `ON`, truy vấn nhiều cấp hay lấy dữ liệu tránh N+1, cần chọn cú pháp chính xác.

Bài học này đi từ ví dụ thực tế tới cách JPQL biến **association trong mô hình entity** thành phép nối dữ liệu, đặc biệt tập trung vào **`JOIN`, `LEFT JOIN`, điều hướng qua quan hệ đơn trị/đa trị, sự khác biệt `ON` và `WHERE`, nhân bản kết quả, `DISTINCT`, `JOIN FETCH` và những giới hạn khi dùng chúng**.

> **Nguyên tắc cốt lõi:** JPQL thường nối các entity **theo thuộc tính quan hệ đã ánh xạ**, không phải bằng cách tự ghi tên bảng và cột khóa ngoại như SQL. `JOIN o.customer c` mô tả quan hệ từ đơn hàng tới khách hàng; provider dựa trên mapping để tạo SQL phù hợp.

## 1. Bài toán xuyên nhiều entity

Giả sử hệ thống bán hàng có bốn loại entity:

- `Customer`: khách hàng.
- `PurchaseOrder`: đơn hàng của khách hàng.
- `OrderLine`: dòng sản phẩm của một đơn hàng.
- `Product`: sản phẩm trong danh mục.

Sơ đồ quan hệ:

```text
     Customer
        |
        | 1
        |
        | *
   PurchaseOrder
        |
        | 1
        |
        | *
     OrderLine  * ------------ 1 Product

Customer.orders          @OneToMany
PurchaseOrder.customer   @ManyToOne

PurchaseOrder.lines      @OneToMany
OrderLine.order          @ManyToOne

OrderLine.product        @ManyToOne
```

Để trả lời các câu hỏi nghiệp vụ, ứng dụng phải đi qua các quan hệ:

1. Những đơn hàng nào thuộc về khách hàng tên “An”?
2. Đơn hàng nào có sản phẩm mang mã `KB-001`?
3. Liệt kê tất cả khách hàng, kể cả khách chưa đặt đơn nào.
4. Tìm các đơn đã xác nhận, đồng thời lấy tên khách và thông tin sản phẩm.
5. Đếm số đơn hàng của từng khách, kể cả người có 0 đơn.
6. Tải đơn cùng các dòng hàng mà không tạo N+1 truy vấn.
7. Tìm đơn có **ít nhất một** dòng thỏa điều kiện, nhưng không làm nhân bản đơn trong kết quả.

Mỗi câu hỏi thể hiện một dạng **truy cập đường dẫn hoặc phép nối** khác nhau trong JPQL.

## 2. Dữ liệu và schema minh họa

Mô hình database có thể được thiết kế như sau:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(120) NOT NULL,
    city VARCHAR(100),
    referrer_id BIGINT,
    CONSTRAINT fk_customer_referrer
        FOREIGN KEY (referrer_id) REFERENCES customers(id)
);

CREATE TABLE products (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    sku VARCHAR(60) NOT NULL UNIQUE,
    name VARCHAR(160) NOT NULL,
    category VARCHAR(80) NOT NULL
);

CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    ordered_at TIMESTAMP NOT NULL,
    status VARCHAR(30) NOT NULL,
    CONSTRAINT fk_orders_customer
        FOREIGN KEY (customer_id) REFERENCES customers(id)
);

CREATE TABLE order_lines (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL,
    product_id BIGINT NOT NULL,
    quantity INTEGER NOT NULL CHECK (quantity > 0),
    unit_price NUMERIC(15, 2) NOT NULL,
    CONSTRAINT fk_lines_order
        FOREIGN KEY (order_id) REFERENCES purchase_orders(id),
    CONSTRAINT fk_lines_product
        FOREIGN KEY (product_id) REFERENCES products(id)
);
```

Một tập dữ liệu giả định:

**Khách hàng**

| id | name | city | referrer_id |
| ---: | --- | --- | ---: |
| 1 | An | Hà Nội | NULL |
| 2 | Bình | Đà Nẵng | 1 |
| 3 | Chi | Huế | NULL |

**Đơn hàng**

| id | customer_id | status |
| ---: | ---: | --- |
| 101 | 1 | CONFIRMED |
| 102 | 1 | DRAFT |
| 103 | 2 | CONFIRMED |

**Sản phẩm**

| id | sku | name |
| ---: | --- | --- |
| 201 | KB-001 | Bàn phím |
| 202 | MS-002 | Chuột |

**Dòng hàng**

| id | order_id | product_id | quantity |
| ---: | ---: | ---: | ---: |
| 1001 | 101 | 201 | 2 |
| 1002 | 101 | 202 | 1 |
| 1003 | 102 | 201 | 1 |
| 1004 | 103 | 202 | 3 |

Vì `Customer#3` chưa có đơn hàng, khách này đặc biệt hữu ích để hiểu **LEFT JOIN**.

Lưu ý: Những bảng, ID và kết quả trong bài chỉ để minh họa. JPQL làm việc với **tên entity và tên thuộc tính Java**, không trực tiếp với tên `purchase_orders` hay `customer_id` trong DDL.

## 3. Ánh xạ các quan hệ JPA tương ứng

Để hiểu một câu `JOIN`, trước hết phải biết nó đang đi qua association nào. Các class dưới đây dùng `jakarta.persistence.*`; mỗi public class được đặt trong file riêng trong package `com.example.sales`.

### 3.1. Customer: danh sách đơn hàng và quan hệ giới thiệu

```java
package com.example.sales;

import java.util.ArrayList;
import java.util.List;
import jakarta.persistence.*;

@Entity
@Table(name = "customers")
public class Customer {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 120)
    private String name;

    @Column(length = 100)
    private String city;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "referrer_id")
    private Customer referrer;

    @OneToMany(mappedBy = "customer", fetch = FetchType.LAZY)
    private List<PurchaseOrder> orders = new ArrayList<>();

    protected Customer() {}

    public Customer(String name, String city) {
        this.name = name;
        this.city = city;
    }

    public Long getId() { return id; }
    public String getName() { return name; }
    public String getCity() { return city; }
    public Customer getReferrer() { return referrer; }
    public List<PurchaseOrder> getOrders() { return orders; }

    public void setReferrer(Customer referrer) {
        this.referrer = referrer;
    }
}
```

Điểm quan trọng:

- `orders` là một **collection-valued association**: từ một Customer có thể đi tới nhiều PurchaseOrder.
- `referrer` là một **single-valued association**: mỗi Customer có thể trỏ tới một Customer giới thiệu hoặc `null`.
- `@OneToMany(mappedBy = "customer")` cho biết phía `PurchaseOrder.customer` sở hữu foreign key, nhưng vẫn có thể dùng `JOIN c.orders o` trong JPQL.

### 3.2. PurchaseOrder: quan hệ đơn trị tới Customer

```java
package com.example.sales;

import java.time.LocalDateTime;
import java.util.ArrayList;
import java.util.List;
import jakarta.persistence.*;

@Entity
@Table(name = "purchase_orders")
public class PurchaseOrder {
    public enum Status {
        DRAFT, CONFIRMED, CANCELLED
    }

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "customer_id", nullable = false)
    private Customer customer;

    @Column(name = "ordered_at", nullable = false)
    private LocalDateTime orderedAt;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 30)
    private Status status = Status.DRAFT;

    @OneToMany(mappedBy = "order", fetch = FetchType.LAZY)
    private List<OrderLine> lines = new ArrayList<>();

    protected PurchaseOrder() {}

    public PurchaseOrder(Customer customer, LocalDateTime orderedAt) {
        this.customer = customer;
        this.orderedAt = orderedAt;
    }

    public Long getId() { return id; }
    public Customer getCustomer() { return customer; }
    public LocalDateTime getOrderedAt() { return orderedAt; }
    public Status getStatus() { return status; }
    public List<OrderLine> getLines() { return lines; }

    public void confirm() { this.status = Status.CONFIRMED; }
}
```

`PurchaseOrder.customer` là quan hệ đơn trị. Vì vậy JPQL có thể điều hướng bằng:

```jpql
o.customer.name
o.customer.city
o.customer.id
```

Ngược lại, `PurchaseOrder.lines` là collection; không được lấy thuộc tính của “một dòng” trực tiếp bằng `o.lines.product.name` vì `lines` không đại diện cho một `OrderLine` duy nhất.

### 3.3. OrderLine: nối đơn hàng với sản phẩm

```java
package com.example.sales;

import java.math.BigDecimal;
import jakarta.persistence.*;

@Entity
@Table(name = "order_lines")
public class OrderLine {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "order_id", nullable = false)
    private PurchaseOrder order;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "product_id", nullable = false)
    private Product product;

    @Column(nullable = false)
    private int quantity;

    @Column(name = "unit_price", nullable = false)
    private BigDecimal unitPrice;

    protected OrderLine() {}

    public Long getId() { return id; }
    public PurchaseOrder getOrder() { return order; }
    public Product getProduct() { return product; }
    public int getQuantity() { return quantity; }
    public BigDecimal getUnitPrice() { return unitPrice; }
}
```

Một `OrderLine` có một order và một product, nên từ bí danh `l` ta có thể viết:

```jpql
l.order.id
l.product.sku
l.product.name
```

### 3.4. Product: thuộc tính cơ bản

```java
package com.example.sales;

import jakarta.persistence.*;

@Entity
@Table(name = "products")
public class Product {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true, length = 60)
    private String sku;

    @Column(nullable = false, length = 160)
    private String name;

    @Column(nullable = false, length = 80)
    private String category;

    protected Product() {}

    public Long getId() { return id; }
    public String getSku() { return sku; }
    public String getName() { return name; }
    public String getCategory() { return category; }
}
```

Không phải mọi thuộc tính cuối đường dẫn đều là association. `p.sku` và `p.name` là **basic state fields**; chúng có thể xuất hiện trong `SELECT`/`WHERE`/`ORDER BY` nhưng không thể được dùng như đích của association join `JOIN p.sku x`.

## 4. JPQL nói về entity, không phải bảng SQL

Trong SQL thường viết:

```sql
SELECT o.*
FROM purchase_orders o
JOIN customers c
    ON c.id = o.customer_id
WHERE c.name = 'An';
```

Trong JPQL, cách biểu đạt tự nhiên là:

```jpql
SELECT o
FROM PurchaseOrder o
JOIN o.customer c
WHERE c.name = :name
```

So sánh:

| SQL | JPQL |
| --- | --- |
| `purchase_orders` | Entity `PurchaseOrder` |
| `customers` | Entity `Customer` |
| `customer_id` | Association `o.customer` |
| `c.name` | Thuộc tính `Customer.name` |
| `JOIN customers c ON c.id = o.customer_id` | `JOIN o.customer c` |
| `SELECT o.*` | `SELECT o` |

JPA provider sử dụng metadata `@ManyToOne`, `@JoinColumn` và các annotation khác để biết phải join bảng nào, qua những cột nào.

**Không cần viết điều kiện khóa ngoại thủ công** cho một association đã ánh xạ:

```jpql
JOIN o.customer c
```

Provider có thể tạo SQL tương đương:

```sql
JOIN customers c ON c.id = o.customer_id
```

Điều kiện trên là điều kiện join **do mapping quyết định**. Nếu muốn lọc bổ sung trên phép nối, có thể dùng `ON` theo cách sẽ trình bày sau.

### 4.1. Bí danh identification variable

Trong:

```jpql
FROM PurchaseOrder o
JOIN o.customer c
```

`o` và `c` là các **identification variables**. Chúng được dùng để tham chiếu tới đối tượng/giá trị tại những vị trí khác của truy vấn.

- `o` đại diện từng PurchaseOrder thuộc phạm vi truy vấn.
- `c` đại diện Customer được join từ `o.customer`.
- `c.name` và `o.status` là các path expressions bắt đầu từ bí danh.

Bí danh phải được đặt sao cho không mơ hồ. Dùng tên ngắn nhưng có nghĩa như `o`, `c`, `l`, `p` thường đủ cho ví dụ nhỏ; với truy vấn dài có thể dùng `ord`, `customer`, `line`, `product`.

### 4.2. Tên entity có thể được cấu hình lại

Nếu khai báo:

```java
@Entity(name = "SalesOrder")
@Table(name = "purchase_orders")
public class PurchaseOrder {
    // ...
}
```

thì tên entity trong JPQL là `SalesOrder`:

```jpql
SELECT o FROM SalesOrder o
```

Không được tự động dùng `PurchaseOrder` chỉ vì tên class Java như vậy, hoặc dùng `purchase_orders` chỉ vì đó là tên bảng SQL. Các ví dụ còn lại giả định entity dùng tên mặc định theo class.

## 5. Truy cập đường dẫn quan hệ bằng dấu chấm

Một **path expression** là biểu thức đi từ bí danh tới một thuộc tính hoặc association:

```jpql
o.id
o.status
o.customer
o.customer.name
o.customer.city
```

Ở đây:

- `o.id` và `o.status` là state-field paths.
- `o.customer` là một **single-valued association path** có kiểu Customer.
- `o.customer.name` đi qua association đến basic field `name`.

Ví dụ lọc đơn hàng theo thành phố của khách:

```jpql
SELECT o
FROM PurchaseOrder o
WHERE o.customer.city = :city
```

Dù không có chữ `JOIN`, provider cần xử lý đường dẫn `o.customer.city` để đọc dữ liệu khách hàng tương ứng. Đây thường được gọi là **implicit join** khi điều hướng qua association đơn trị.

SQL tương đương về mặt ý tưởng:

```sql
SELECT o.*
FROM purchase_orders o
JOIN customers c ON c.id = o.customer_id
WHERE c.city = ?;
```

### 5.1. Đường dẫn chỉ có một phần tử và đường dẫn đi qua collection

Một điểm phân biệt nền tảng:

| Loại path | Ví dụ | Có thể đi tiếp tới field của phần tử? |
| --- | --- | --- |
| Basic state field | `o.status` | Không điều hướng tiếp như một entity. |
| Embeddable field | `o.shippingAddress.city` nếu `shippingAddress` là `@Embedded` | Có thể đi qua thuộc tính embeddable theo mapping. |
| Single-valued association | `o.customer.name` | Có, vì `customer` xác định một Customer. |
| Collection-valued association | `o.lines` | **Không trực tiếp** bằng `o.lines.product.name`. |
| Sau khi join collection | `JOIN o.lines l` rồi `l.product.name` | Có, vì `l` đại diện một OrderLine. |

`o.lines` là một tập hợp nhiều OrderLine. JPQL không thể tự chọn phần tử nào để lấy `product`. Phải tạo bí danh cho **mỗi phần tử** bằng join, hoặc dùng toán tử collection/query khác phù hợp.

### 5.2. Truy cập nhiều cấp qua các quan hệ đơn trị

Ta có thể bắt đầu từ OrderLine:

```jpql
SELECT l
FROM OrderLine l
WHERE l.order.customer.city = :city
```

Đường dẫn gồm:

```text
OrderLine l
   |
   +-- l.order                 (PurchaseOrder)
             |
             +-- .customer     (Customer)
                     |
                     +-- .city (String)
```

Vì `order` và `customer` đều là association đơn trị, JPQL có thể điều hướng theo chuỗi qua cả hai.

Tuy nhiên, nếu truy vấn có nhiều điều kiện trên cùng các entity liên quan, dùng **JOIN tường minh** thường rõ ràng hơn:

```jpql
SELECT l
FROM OrderLine l
JOIN l.order o
JOIN o.customer c
WHERE c.city = :city
```

## 6. Implicit join: tiện lợi nhưng phải hiểu ngữ nghĩa

Khi dùng:

```jpql
SELECT o
FROM PurchaseOrder o
WHERE o.customer.name = :name
```

phần `o.customer.name` yêu cầu provider điều hướng qua association `customer`. Với path traversal qua association đơn trị, ngữ nghĩa tương ứng một **inner join ngầm định** ở đường dẫn ấy.

Điều này có hệ quả:

- Nếu association tại điểm trung gian là `null`, hàng nguồn có thể không xuất hiện trong kết quả.
- Provider có thể tái sử dụng join ngầm định khi cùng một path xuất hiện ở nhiều vị trí, nhưng hình dạng SQL cụ thể là chi tiết provider.
- Với truy vấn cần giữ hàng dù association rỗng, nên dùng **`LEFT JOIN` tường minh**, không dựa vào điều hướng ngầm.

### 6.1. Quan hệ tùy chọn: Customer.referrer

Trong entity mẫu, `Customer.referrer` có thể là `null`.

Truy vấn:

```jpql
SELECT c
FROM Customer c
WHERE c.referrer.name = :referrerName
```

đi qua `c.referrer` để lấy tên người giới thiệu. Khách không có referrer không thỏa đường dẫn này.

Nếu muốn **lấy mọi khách, kể cả người không có referrer**, và hiển thị tên referrer khi có, viết:

```jpql
SELECT c.name, r.name
FROM Customer c
LEFT JOIN c.referrer r
ORDER BY c.id
```

Dựa trên dữ liệu ví dụ, kết quả ý tưởng là:

| customerName | referrerName |
| --- | --- |
| An | NULL |
| Bình | An |
| Chi | NULL |

Nếu thay `LEFT JOIN` thành `JOIN`, các khách không có referrer sẽ không xuất hiện.

### 6.2. Kiểm tra null của association không nhất thiết phải điều hướng qua nó

Nếu chỉ muốn tìm khách **không có** người giới thiệu, có thể viết:

```jpql
SELECT c
FROM Customer c
WHERE c.referrer IS NULL
```

Điều kiện này kiểm tra association, khác với việc đi tiếp tới `c.referrer.name`. Provider có thể biểu diễn bằng khóa ngoại `referrer_id IS NULL` hoặc SQL tương đương; không cần yêu cầu một tên từ entity referrer.

Đây là lý do cần phân biệt:

- `c.referrer IS NULL`: kiểm tra quan hệ có tồn tại hay không.
- `c.referrer.name = :name`: điều hướng tới trường của entity liên quan, có semantics tương ứng inner join.
- `LEFT JOIN c.referrer r`: có thể giữ Customer dù quan hệ không tồn tại.

## 7. Explicit INNER JOIN: nối tường minh

Cú pháp cơ bản:

```jpql
SELECT o
FROM PurchaseOrder o
JOIN o.customer c
WHERE c.name = :name
```

`JOIN` không có từ khóa khác mặc định là **inner join**. Có thể viết `INNER JOIN` để nhấn mạnh:

```jpql
SELECT o
FROM PurchaseOrder o
INNER JOIN o.customer c
WHERE c.name = :name
```

Với `JOIN o.customer c`:

1. `o` là một PurchaseOrder.
2. `o.customer` là association từ order đến Customer.
3. `c` là bí danh của Customer đã join.
4. Các điều kiện có thể dùng `c.name`, `c.city`, `c.id`.

### 7.1. INNER JOIN chỉ giữ những hàng có liên kết phù hợp

Ví dụ:

```jpql
SELECT c.name, o.id
FROM Customer c
JOIN c.orders o
ORDER BY c.id, o.id
```

Dựa trên dữ liệu ở đầu bài:

| c.name | o.id |
| --- | ---: |
| An | 101 |
| An | 102 |
| Bình | 103 |

Khách Chi không có đơn nên **không xuất hiện** trong inner join.

Một phép nối từ cha tới collection tạo ra kết quả có **một dòng logic cho mỗi phần tử được nối**. Vì An có hai đơn, tên An xuất hiện hai lần. Đây là semantics của join, không phải bug.

### 7.2. Join từ bên giữ khóa ngoại hay từ collection?

Hai hướng đều có thể hợp lệ nếu mapping tương ứng tồn tại.

Từ đơn hàng đến khách:

```jpql
SELECT o
FROM PurchaseOrder o
JOIN o.customer c
WHERE c.city = :city
```

Từ khách tới đơn hàng:

```jpql
SELECT o
FROM Customer c
JOIN c.orders o
WHERE c.city = :city
```

Cả hai đều có thể trả danh sách PurchaseOrder của khách ở thành phố tương ứng. Nhưng cách biểu diễn trong `FROM` khác nhau và có thể ảnh hưởng số dòng/tập gốc của truy vấn khi mở rộng thêm joins.

**Owning side JPA không hạn chế hướng JPQL join.** `Customer.orders` là inverse side do `mappedBy`, nhưng vẫn có thể viết `JOIN c.orders o`.

## 8. Explicit LEFT JOIN: giữ entity bên trái khi không có liên kết

`LEFT JOIN` (hoặc `LEFT OUTER JOIN`) giữ các hàng ở phía trái của phép nối ngay cả khi không có entity liên quan khớp điều kiện.

```jpql
SELECT c.name, o.id
FROM Customer c
LEFT JOIN c.orders o
ORDER BY c.id, o.id
```

Với dữ liệu giả định:

| c.name | o.id |
| --- | ---: |
| An | 101 |
| An | 102 |
| Bình | 103 |
| Chi | NULL |

Khách Chi được giữ lại, còn giá trị từ phía đơn hàng là `null`.

SQL tư duy tương đương:

```sql
SELECT c.name, o.id
FROM customers c
LEFT JOIN purchase_orders o
    ON o.customer_id = c.id;
```

### 8.1. Khi nào nên chọn LEFT JOIN?

- Muốn hiển thị mọi khách hàng, cả khách chưa có đơn.
- Muốn trả một entity cha ngay cả khi collection con rỗng.
- Muốn thống kê số phần tử, bao gồm kết quả bằng 0.
- Muốn lấy thông tin thuộc một association tùy chọn nhưng không loại bỏ entity nguồn.
- Muốn áp điều kiện lên liên kết mà vẫn giữ những hàng không có liên kết phù hợp.

### 8.2. LEFT JOIN không luôn bảo đảm tất cả hàng nguồn trong kết quả cuối

Nếu sau left join, `WHERE` đặt điều kiện bắt buộc trên entity bên phải:

```jpql
SELECT c
FROM Customer c
LEFT JOIN c.orders o
WHERE o.status = :status
```

khách không có order sẽ có `o = null` và không thỏa `o.status = :status`. Điều kiện `WHERE` có thể làm kết quả **hành xử gần như inner join** cho những hàng mà cột bên phải phải có giá trị.

Đây là điểm thường gây lỗi khi muốn “giữ tất cả khách” nhưng lại lọc trạng thái order.

## 9. ON và WHERE: hai nơi đặt điều kiện có ý nghĩa khác nhau

JPQL hỗ trợ `ON` để bổ sung điều kiện vào phép nối association. Với JPA hiện đại, cú pháp cơ bản:

```jpql
SELECT c, o
FROM Customer c
LEFT JOIN c.orders o ON o.status = :status
```

Phân biệt:

- **`ON`**: điều kiện tham gia **ghép hàng của phép nối**.
- **`WHERE`**: điều kiện lọc **những hàng đã đi qua FROM/JOIN**.

### 9.1. LEFT JOIN + ON giữ khách không có đơn khớp

Muốn lấy **mọi Customer**, đồng thời ghép đơn có trạng thái `CONFIRMED` nếu có:

```jpql
SELECT c.name, o.id
FROM Customer c
LEFT JOIN c.orders o ON o.status = :status
ORDER BY c.id, o.id
```

Với `:status = CONFIRMED`, kết quả:

| c.name | o.id |
| --- | ---: |
| An | 101 |
| Bình | 103 |
| Chi | NULL |

Khách không có đơn xác nhận vẫn được giữ.

Lưu ý đối với khách có nhiều đơn: left join có thể trả nhiều hàng nếu **nhiều** order khớp `ON`. Một hàng khách nguồn có thể được lặp cho mỗi order phù hợp.

### 9.2. LEFT JOIN + WHERE loại khách không có đơn khớp

So sánh:

```jpql
SELECT c.name, o.id
FROM Customer c
LEFT JOIN c.orders o
WHERE o.status = :status
ORDER BY c.id, o.id
```

Kết quả với `CONFIRMED`:

| c.name | o.id |
| --- | ---: |
| An | 101 |
| Bình | 103 |

Chi bị loại vì không có order nào để thỏa `WHERE`.

Cần ghi nhớ:

```text
LEFT JOIN ... ON condition
    Giữ entity bên trái, nếu bên phải không khớp thì điền NULL.

LEFT JOIN ... WHERE right.condition
    Lọc toàn bộ kết quả sau join, nên hàng bên phải NULL
    thường không qua được điều kiện.
```

### 9.3. Vì sao thêm OR o IS NULL chưa chắc thay thế được ON?

Một phương án thường gặp:

```jpql
SELECT c
FROM Customer c
LEFT JOIN c.orders o
WHERE o.status = :status OR o IS NULL
```

Nó có thể giữ khách **hoàn toàn không có đơn**, nhưng không nhất thiết giữ khách **có đơn nhưng không đơn nào khớp trạng thái**.

Ví dụ khách D chỉ có một đơn `CANCELLED`:

- `LEFT JOIN ... ON o.status = CONFIRMED` cho một hàng khách D với `o = null`.
- `LEFT JOIN ... WHERE o.status = CONFIRMED OR o IS NULL`: phép JOIN đã ghép ra một đơn CANCELLED, nên `o` không null và điều kiện WHERE không đạt; khách D bị loại.

Vì vậy, **`ON` và `WHERE` không phải chỉ là hai cách viết thẩm mỹ**. Chúng khác semantics khi outer join.

### 9.4. ON không thay thế điều kiện khóa ngoại đã ánh xạ

```jpql
LEFT JOIN c.orders o ON o.status = :status
```

vẫn dùng liên kết `Customer.orders` được mô tả bởi JPA. `ON` chỉ thêm điều kiện về status, không thay thế phép nối chuẩn trên foreign key.

Ở tầng SQL, ý tưởng thường tương đương:

```sql
LEFT JOIN purchase_orders o
    ON o.customer_id = c.id
   AND o.status = ?
```

Dùng `ON` để diễn đạt điều kiện trên association; đừng tự viết lại join key nếu mapping đã có và bạn chỉ muốn lọc thêm.

### 9.5. ON với INNER JOIN

Với inner join, lọc bằng `ON` và bằng `WHERE` nhiều khi có kết quả tương đương đối với những điều kiện đơn giản:

```jpql
FROM Customer c
JOIN c.orders o ON o.status = :status
```

và:

```jpql
FROM Customer c
JOIN c.orders o
WHERE o.status = :status
```

Tuy nhiên, nếu một truy vấn còn có nhiều outer joins hoặc điều kiện tổ hợp, việc di chuyển điều kiện giữa `ON` và `WHERE` có thể thay đổi ý nghĩa toàn truy vấn. Nên đặt điều kiện ở vị trí phản ánh đúng mục tiêu thay vì chỉ dựa vào một quy tắc tối ưu SQL chung.

## 10. Join một collection-valued association

Để lọc đơn hàng theo sản phẩm trong các dòng hàng:

```jpql
SELECT o
FROM PurchaseOrder o
JOIN o.lines l
WHERE l.quantity >= :minimum
```

`JOIN o.lines l` biến collection `o.lines` thành từng phần tử `OrderLine` với bí danh `l`.

Từ `l` có thể đi tiếp qua các association đơn trị:

```jpql
SELECT o
FROM PurchaseOrder o
JOIN o.lines l
JOIN l.product p
WHERE p.sku = :sku
```

Các bước:

```text
PurchaseOrder o
       |
       | JOIN o.lines l
       v
   OrderLine l
       |
       | JOIN l.product p
       v
    Product p
       |
       +-- p.sku
```

Đây là **phép nối nhiều cấp tường minh**, phù hợp khi truy vấn cần đi qua một collection và sau đó đọc trường của entity con.

### 10.1. Cú pháp không hợp lệ thường gặp

```jpql
-- Sai: lines là collection, không thể đi trực tiếp
-- đến một OrderLine cụ thể theo kiểu dấu chấm.
SELECT o
FROM PurchaseOrder o
WHERE o.lines.product.sku = :sku
```

Cách đúng:

```jpql
SELECT o
FROM PurchaseOrder o
JOIN o.lines l
JOIN l.product p
WHERE p.sku = :sku
```

Nếu chỉ cần kiểm tra collection có rỗng không, có thể dùng `IS EMPTY` hoặc `SIZE`, không nhất thiết join:

```jpql
SELECT o
FROM PurchaseOrder o
WHERE o.lines IS EMPTY
```

Hoặc dùng `EXISTS`/subquery cho điều kiện tồn tại phức tạp. Lựa chọn phụ thuộc mục tiêu truy vấn.

### 10.2. Đường dẫn sau bí danh collection

Sau khi:

```jpql
JOIN o.lines l
```

`l` đại diện cho **một OrderLine**, vì vậy những path sau hợp lệ:

```jpql
l.quantity
l.product.sku
l.product.category
l.order.id
```

Điều này không có nghĩa `o.lines` biến thành một đối tượng đơn trị trên entity `PurchaseOrder`. Chỉ **bí danh của phần tử join** mới biểu diễn từng OrderLine.

## 11. Kết quả bị nhân bản khi join quan hệ một-nhiều

Đây là một hệ quả trực tiếp của relational join.

Đơn `PurchaseOrder#101` có hai dòng:

```text
Order#101
   |
   +-- Line#1001 -> Product#201
   +-- Line#1002 -> Product#202
```

Truy vấn:

```jpql
SELECT o
FROM PurchaseOrder o
JOIN o.lines l
WHERE o.id = :id
```

có thể tạo **hai phần tử biểu diễn cùng entity Order#101** trong result list theo semantics join/projection/provider, vì có hai hàng join. Persistence context vẫn duy trì **một managed identity** cho `PurchaseOrder#101`; điều đó không mặc định có nghĩa mọi result list luôn chỉ chứa một phần tử.

### 11.1. Dùng DISTINCT để chọn các order không lặp

```jpql
SELECT DISTINCT o
FROM PurchaseOrder o
JOIN o.lines l
WHERE l.product.category = :category
```

`DISTINCT` yêu cầu loại trùng trong kết quả truy vấn theo semantics JPQL. Với entity projection, ý định là **mỗi PurchaseOrder chỉ có một lần**, ngay cả khi nhiều dòng thỏa điều kiện.

Tùy provider và phiên bản, DISTINCT có thể được xử lý ở SQL, ở quá trình materialize entity hoặc kết hợp; không khẳng định SQL luôn có một `SELECT DISTINCT` với đúng cùng cấu trúc.

### 11.2. DISTINCT không phải giải pháp cho mọi hình dạng truy vấn

So sánh:

```jpql
SELECT DISTINCT o
FROM PurchaseOrder o
JOIN o.lines l
```

với:

```jpql
SELECT DISTINCT o.id, l.id
FROM PurchaseOrder o
JOIN o.lines l
```

Truy vấn thứ hai vẫn trả nhiều cặp `(orderId, lineId)` vì từng cặp khác nhau. `DISTINCT` tác động lên **toàn bộ biểu thức được SELECT**, không biến một truy vấn nhiều giá trị thành một truy vấn chỉ có một entity cha nếu projection đang bao gồm giá trị của child.

Muốn lấy đúng một hàng cho mỗi order và một giá trị aggregate, phải thiết kế `GROUP BY` hoặc subquery phù hợp.

## 12. SELECT quyết định loại kết quả trả về

Một phép join không mặc nhiên quyết định kết quả là Customer, Order hay Product. **Mệnh đề SELECT** mới nói truy vấn trả kiểu gì.

### 12.1. Chọn entity gốc

```jpql
SELECT o
FROM PurchaseOrder o
JOIN o.customer c
WHERE c.city = :city
```

Kết quả là các `PurchaseOrder`.

Java:

```java
List<PurchaseOrder> orders = em.createQuery(
        "SELECT o FROM PurchaseOrder o " +
        "JOIN o.customer c " +
        "WHERE c.city = :city",
        PurchaseOrder.class
    )
    .setParameter("city", "Hà Nội")
    .getResultList();
```

### 12.2. Chọn entity được join

```jpql
SELECT c
FROM PurchaseOrder o
JOIN o.customer c
WHERE o.status = :status
```

Kết quả là `Customer`. Nếu một Customer có nhiều order khớp, có thể cần `DISTINCT c`.

### 12.3. Chọn hai entity

```jpql
SELECT o, c
FROM PurchaseOrder o
JOIN o.customer c
```

Mỗi hàng kết quả là một cặp `(PurchaseOrder, Customer)`, thường nhận dưới dạng `Object[]`:

```java
List<Object[]> rows = em.createQuery(
        "SELECT o, c FROM PurchaseOrder o JOIN o.customer c",
        Object[].class
    )
    .getResultList();

for (Object[] row : rows) {
    PurchaseOrder order = (PurchaseOrder) row[0];
    Customer customer = (Customer) row[1];

    System.out.println(order.getId() + ": " + customer.getName());
}
```

Với ứng dụng lớn, projection kiểu `Object[]` dễ gây nhầm thứ tự và ép kiểu. DTO projection thường dễ sử dụng hơn.

### 12.4. Chọn trường scalar

```jpql
SELECT o.id, c.name
FROM PurchaseOrder o
JOIN o.customer c
```

Kết quả không nhất thiết là managed entity `PurchaseOrder` hay `Customer`; mỗi hàng chứa giá trị trường được chọn.

### 12.5. Constructor expression trả DTO

Giả sử DTO:

```java
package com.example.sales.dto;

public record OrderSummary(
    Long orderId,
    String customerName,
    PurchaseOrder.Status status
) {}
```

Với `record` này, cần import `com.example.sales.PurchaseOrder` trong file Java.

JPQL:

```jpql
SELECT new com.example.sales.dto.OrderSummary(
    o.id,
    c.name,
    o.status
)
FROM PurchaseOrder o
JOIN o.customer c
WHERE o.status = :status
```

Ví dụ gọi:

```java
List<OrderSummary> summaries = em.createQuery(
        "SELECT new com.example.sales.dto.OrderSummary(" +
        "o.id, c.name, o.status) " +
        "FROM PurchaseOrder o JOIN o.customer c " +
        "WHERE o.status = :status",
        OrderSummary.class
    )
    .setParameter("status", PurchaseOrder.Status.CONFIRMED)
    .getResultList();
```

Đây là một cách rõ ràng để **lấy đúng dữ liệu cần hiển thị** thay vì tải toàn bộ object graph. `new` ở đây là constructor expression của JPQL, không phải lệnh tạo entity managed.

Trong các dự án dùng Java chưa hỗ trợ record, có thể dùng một class DTO có constructor phù hợp.

## 13. Truy vấn nhiều cấp kết hợp điều kiện ở nhiều entity

Ví dụ tìm những đơn chứa sản phẩm danh mục “Phụ kiện” của khách ở “Hà Nội”, với số lượng dòng ít nhất 2:

```jpql
SELECT DISTINCT o
FROM PurchaseOrder o
JOIN o.customer c
JOIN o.lines l
JOIN l.product p
WHERE c.city = :city
  AND p.category = :category
  AND l.quantity >= :minimum
```

Cấu trúc:

```text
      o: PurchaseOrder
      |
      +-- JOIN o.customer c
      |          |
      |          +-- c.city
      |
      +-- JOIN o.lines l
                 |
                 +-- l.quantity
                 |
                 +-- JOIN l.product p
                            |
                            +-- p.category
```

Với `SELECT DISTINCT o`, nếu một order có nhiều lines cùng thỏa điều kiện, kết quả mong muốn chỉ chứa một `PurchaseOrder` duy nhất.

Java:

```java
List<PurchaseOrder> results = em.createQuery(
        "SELECT DISTINCT o " +
        "FROM PurchaseOrder o " +
        "JOIN o.customer c " +
        "JOIN o.lines l " +
        "JOIN l.product p " +
        "WHERE c.city = :city " +
        "AND p.category = :category " +
        "AND l.quantity >= :minimum",
        PurchaseOrder.class
    )
    .setParameter("city", "Hà Nội")
    .setParameter("category", "Phụ kiện")
    .setParameter("minimum", 2)
    .getResultList();
```

**Không ghép giá trị trực tiếp vào JPQL bằng nối chuỗi từ input người dùng.** Dùng named parameters như `:city` và `:minimum` để biểu diễn dữ liệu đầu vào.

### 13.1. Điều kiện trên nhiều quan hệ bắt buộc join mỗi quan hệ không?

Không. Đối với đường dẫn đơn trị, có thể viết:

```jpql
SELECT l
FROM OrderLine l
WHERE l.order.customer.city = :city
  AND l.product.category = :category
```

Provider xử lý các association đơn trị được truy cập ngầm.

Tuy nhiên, khi truy vấn dài:

```jpql
SELECT l
FROM OrderLine l
JOIN l.order o
JOIN o.customer c
JOIN l.product p
WHERE c.city = :city
  AND p.category = :category
```

thường dễ đọc và dễ đặt điều kiện `ON`/`LEFT JOIN` hơn. Tường minh cũng giúp người đọc xác định ngay nơi câu truy vấn có thể làm thay đổi số dòng.

## 14. Dùng EXISTS thay cho JOIN khi chỉ cần kiểm tra sự tồn tại

Nhiều lúc yêu cầu là: “Lấy mọi order **có ít nhất một** dòng sản phẩm mã `KB-001`.” Nếu JOIN rồi chọn order:

```jpql
SELECT DISTINCT o
FROM PurchaseOrder o
JOIN o.lines l
JOIN l.product p
WHERE p.sku = :sku
```

đó là một cách đúng.

Nhưng có thể dùng `EXISTS`:

```jpql
SELECT o
FROM PurchaseOrder o
WHERE EXISTS (
    SELECT l.id
    FROM OrderLine l
    WHERE l.order = o
      AND l.product.sku = :sku
)
```

Ý nghĩa:

- Với từng `PurchaseOrder o`, subquery tìm `OrderLine l` thuộc order ấy.
- Nếu có ít nhất một dòng khớp SKU, order được giữ.
- Query gốc không bị nhân hàng vì join collection trong mệnh đề FROM gốc.

### 14.1. Khi nào EXISTS hữu ích?

- Chỉ cần biết **có** child thỏa điều kiện hay không.
- Không cần đưa các trường của child vào kết quả.
- Tránh nhân bản root entity do join nhiều child.
- Truy vấn có nhiều điều kiện tồn tại/không tồn tại.

Đây không phải lời hứa EXISTS luôn nhanh hơn JOIN. Database optimizer có thể biến đổi các dạng truy vấn khác nhau thành kế hoạch tương đương. Nên xem SQL thực tế, chỉ số và `EXPLAIN` khi hiệu năng là yếu tố quyết định.

### 14.2. NOT EXISTS và không có phần tử thỏa

Tìm order **không có dòng nào** chứa SKU:

```jpql
SELECT o
FROM PurchaseOrder o
WHERE NOT EXISTS (
    SELECT l.id
    FROM OrderLine l
    WHERE l.order = o
      AND l.product.sku = :sku
)
```

Nếu chỉ muốn order hoàn toàn không có dòng, `o.lines IS EMPTY` có thể ngắn gọn hơn. Hai điều kiện có ý nghĩa khác nhau: “không có dòng nào” và “không có dòng mang SKU này”.

## 15. Phép nối và phép thống kê COUNT/GROUP BY

Một tình huống điển hình là **đếm số đơn của từng khách, kể cả khách có 0 đơn**.

```jpql
SELECT c.id, c.name, COUNT(o)
FROM Customer c
LEFT JOIN c.orders o
GROUP BY c.id, c.name
ORDER BY c.id
```

Với dữ liệu mẫu:

| c.id | c.name | COUNT(o) |
| ---: | --- | ---: |
| 1 | An | 2 |
| 2 | Bình | 1 |
| 3 | Chi | 0 |

**Vì sao COUNT(o) chứ không phải COUNT(*)?**

Trong LEFT JOIN, khách không có order vẫn có một hàng kết quả với phía `o` bằng null. `COUNT(o)` đếm các biểu thức `o` không null, nên Chi có giá trị 0.

JPQL hỗ trợ `COUNT(...)`, bao gồm `COUNT(o)` trong những trường hợp phù hợp. Đếm bằng `COUNT(c)` lại có thể tính cả hàng bên trái; đó không phải số order. Vì thế chọn biểu thức COUNT theo **đối tượng muốn đếm**, không chọn tùy tiện.

### 15.1. Đếm đơn xác nhận của mỗi khách, gồm người có 0

```jpql
SELECT c.id, c.name, COUNT(o)
FROM Customer c
LEFT JOIN c.orders o
    ON o.status = :status
GROUP BY c.id, c.name
ORDER BY c.id
```

`ON` giữ khách không có đơn xác nhận, nên kết quả vẫn có Chi với 0.

Nếu thay bằng:

```jpql
FROM Customer c
LEFT JOIN c.orders o
WHERE o.status = :status
```

thì khách không có đơn xác nhận có thể bị loại trước khi GROUP BY; không còn hàng để đếm bằng 0.

### 15.2. Nhân bản khi join nhiều collection ảnh hưởng COUNT

Nếu Customer có cả `orders` và một collection khác `addresses`, truy vấn join đồng thời hai collection có thể nhân số dòng theo tích số phần tử.

Ví dụ một khách có 2 orders và 3 addresses:

```text
2 orders × 3 addresses = 6 hàng join
```

Khi đó `COUNT(o)` có thể thành 6 chứ không phải 2. Một hướng là dùng `COUNT(DISTINCT o)` theo khả năng JPQL/provider, hoặc thiết kế subquery/aggregation riêng để tránh nhân tích.

**Khi kết quả thống kê sai lớn hơn thực tế, hãy kiểm tra số hàng do JOIN tạo ra trước khi nghi ngờ dữ liệu nguồn.**

## 16. JOIN không phải JOIN FETCH

Đây là điểm cực kỳ quan trọng với JPA ORM.

`JOIN` thông thường được dùng để **xác định tập kết quả, lọc, chọn trường hoặc tính toán**. Nó **không yêu cầu provider khởi tạo đầy đủ association** trên entity được trả về.

Ví dụ:

```jpql
SELECT o
FROM PurchaseOrder o
JOIN o.customer c
WHERE c.city = :city
```

Truy vấn dùng Customer để lọc đơn. Nhưng sau khi trả danh sách `PurchaseOrder`, việc gọi:

```java
order.getCustomer().getName()
```

vẫn có thể dẫn tới lazy loading tùy trạng thái persistence context, provider và fetch plan.

Ngược lại, **`JOIN FETCH`** là một *fetch join* yêu cầu nạp association như một phần truy vấn:

```jpql
SELECT o
FROM PurchaseOrder o
JOIN FETCH o.customer
WHERE o.status = :status
```

Mục tiêu là trả về các PurchaseOrder **cùng Customer association đã được fetch**.

### 16.1. So sánh

| Cấu trúc JPQL | Mục đích chính |
| --- | --- |
| `JOIN o.customer c` | Có bí danh `c` để lọc/chọn Customer liên quan. |
| `LEFT JOIN o.lines l` | Giữ order kể cả không có line, đặt bí danh `l`. |
| `JOIN FETCH o.customer` | Tải association Customer cùng Order. |
| `LEFT JOIN FETCH o.lines` | Tải collection lines, giữ Order kể cả collection rỗng. |
| `JOIN o.customer c WHERE c.name = ...` | Tìm Order theo thông tin Customer; không tự đồng nghĩa fetch Customer. |

`JOIN FETCH` là chủ đề fetching liên quan trực tiếp tới phép nối, nhưng cần phân biệt với **JOIN tường minh chỉ phục vụ truy vấn**.

### 16.2. Fetch join một quan hệ đơn trị

```java
List<PurchaseOrder> orders = em.createQuery(
        "SELECT o FROM PurchaseOrder o " +
        "JOIN FETCH o.customer " +
        "WHERE o.status = :status",
        PurchaseOrder.class
    )
    .setParameter("status", PurchaseOrder.Status.CONFIRMED)
    .getResultList();
```

Ứng dụng có thể truy cập `o.getCustomer().getName()` sau khi truy vấn trong phạm vi thích hợp mà không phải phát thêm SELECT chỉ vì association Customer chưa được khởi tạo.

Tuy nhiên, fetch join **không khởi tạo vô hạn mọi quan hệ con của Customer**. Nếu `Customer.orders` vẫn LAZY, việc đọc collection đó có thể tiếp tục tạo SQL.

### 16.3. Fetch join collection

```jpql
SELECT DISTINCT o
FROM PurchaseOrder o
LEFT JOIN FETCH o.lines
WHERE o.id = :orderId
```

Tư duy kết quả:

- Order được nạp.
- Các lines thuộc association được fetch.
- `LEFT JOIN` cho phép order xuất hiện ngay cả khi không có line.
- `DISTINCT` diễn đạt mong muốn chỉ có một Order trong kết quả entity, tránh nhân bản do nhiều lines theo các semantics/provider phù hợp.

Với một số phiên bản provider, các entity trùng sinh ra từ fetch join collection được tự động gộp khi materialize; vẫn nên hiểu rõ semantics JPQL và kiểm tra phiên bản dùng trong dự án thay vì xem `DISTINCT` như công tắc hiệu năng không có tác dụng phụ.

### 16.4. Fetch join không dùng bí danh trong JPQL portable

Trong JPQL theo cấu trúc fetch join chuẩn, phần tử đích của `JOIN FETCH` không được khai báo như một identification variable thông thường để các phần khác của truy vấn tự do dùng:

```jpql
-- Mẫu portable:
SELECT o
FROM PurchaseOrder o
JOIN FETCH o.customer
```

Không coi việc một provider cho phép:

```jpql
-- Một số provider chấp nhận kiểu mở rộng này;
-- không coi là JPQL portable.
SELECT o
FROM PurchaseOrder o
JOIN FETCH o.customer c
WHERE c.city = :city
```

là hợp đồng chuẩn cho mọi JPA provider.

Nếu cần lọc Customer bằng alias, có thể dùng một join tường minh bình thường, hoặc truy vấn `o.customer.city`, rồi chọn fetch plan phù hợp. Có những provider cho phép cấu trúc join bổ sung, nhưng SQL và chi phí cần được cân nhắc.

### 16.5. Không lọc một phần collection bằng fetch join một cách tùy tiện

`JOIN FETCH` có mục đích **tải association**. Nếu áp điều kiện làm collection chỉ còn các phần tử khớp một trạng thái, ứng dụng có nguy cơ nhận collection nhìn như đã được tải đầy đủ nhưng thực chất chỉ có **một phần** dữ liệu.

Ví dụ mục tiêu “lấy order và chỉ những lines quantity >= 2” khác với “nạp toàn bộ lines của order”. Với nhu cầu chỉ hiển thị những dòng phù hợp, thường nên **trả DTO từ một JOIN thường** hoặc truy vấn danh sách OrderLine riêng, thay vì biến một managed association thành danh sách tải một phần khó kiểm soát.

Ngoài ra, `ON` trên fetch join không phải cách portable để lọc tùy ý collection được fetch. Hãy tách **lọc kết quả nghiệp vụ** và **fetch graph entity** thành hai quyết định.

## 17. N+1 và vì sao JOIN thường không đủ

Giả sử cần danh sách 100 đơn cùng tên khách:

```java
List<PurchaseOrder> orders = em.createQuery(
        "SELECT o FROM PurchaseOrder o",
        PurchaseOrder.class
    )
    .getResultList();

for (PurchaseOrder o : orders) {
    System.out.println(o.getCustomer().getName());
}
```

Nếu Customer association LAZY và chưa có dữ liệu liên quan trong cache, ứng dụng có thể tạo:

```text
1 SELECT lấy danh sách PurchaseOrder
N SELECT bổ sung để lấy các Customer cần dùng
```

Số SELECT bổ sung thực tế có thể ít hơn số order nếu nhiều order cùng customer, nhờ identity map/cache/batching. Nhưng **mẫu truy cập trong vòng lặp** vẫn có nguy cơ N+1.

Một cách dùng fetch join:

```jpql
SELECT o
FROM PurchaseOrder o
JOIN FETCH o.customer
```

Tuy nhiên, không nên biến mọi query thành fetch join mọi association:

- Fetch nhiều collection có thể gây nhân tích số hàng.
- Fetch graph lớn tốn bộ nhớ.
- Fetch join collection có thể không tương thích với phân trang ở mức SQL như mong muốn.
- JOIN FETCH không giúp nhiều nếu endpoint chỉ cần vài trường scalar.

### 17.1. Projection thay cho fetch graph

Nếu màn hình chỉ cần ID order và tên Customer:

```jpql
SELECT o.id, c.name
FROM PurchaseOrder o
JOIN o.customer c
```

Đây là **JOIN thường với scalar projection**. Không cần fetch toàn bộ Customer entity hoặc toàn bộ order graph nếu không dùng chúng sau đó.

Khi tối ưu, hãy bắt đầu bằng câu hỏi: **Ta cần managed entity đầy đủ hay chỉ cần một bản ghi hiển thị?**

## 18. Phân trang và join collection

Một query tìm danh sách đơn hàng có phân trang:

```java
List<PurchaseOrder> page = em.createQuery(
        "SELECT o FROM PurchaseOrder o " +
        "ORDER BY o.orderedAt DESC, o.id DESC",
        PurchaseOrder.class
    )
    .setFirstResult(0)
    .setMaxResults(20)
    .getResultList();
```

Cách này có thể phân trang theo root orders.

Nếu thêm:

```jpql
SELECT o
FROM PurchaseOrder o
LEFT JOIN FETCH o.lines
ORDER BY o.orderedAt DESC, o.id DESC
```

rồi dùng `setMaxResults(20)`, mỗi Order có thể tạo nhiều hàng SQL do lines. Giới hạn 20 hàng SQL **không tương đương** lấy đầy đủ 20 Order. Provider có thể phải phân trang trong bộ nhớ, thay đổi kế hoạch truy vấn hoặc cảnh báo/không cho phép trong cấu hình nhất định.

### 18.1. Chiến lược hai bước

Khi cần page các Order và tải lines:

**Bước 1:** Lấy ID của root theo filter/sort:

```jpql
SELECT o.id
FROM PurchaseOrder o
WHERE o.status = :status
ORDER BY o.orderedAt DESC, o.id DESC
```

Áp `setFirstResult/setMaxResults` cho truy vấn ID.

**Bước 2:** Tải các order có ID thuộc page, kèm lines:

```jpql
SELECT DISTINCT o
FROM PurchaseOrder o
LEFT JOIN FETCH o.lines
WHERE o.id IN :ids
```

Các điểm cần lưu ý:

- Trật tự kết quả của bước 2 **không tự bảo đảm** trùng thứ tự ID của page. Có thể sắp xếp lại theo danh sách ID trong ứng dụng hoặc có logic `ORDER BY` phù hợp.
- Nếu `:ids` rỗng, nên trả kết quả rỗng trước thay vì tạo truy vấn IN rỗng có thể không portable.
- Hai bước là hai lần đọc; dưới concurrency cao, nếu cần snapshot nhất quán phải xét isolation/transaction.
- Với page lớn, có thể cần batch ID và xem giới hạn bind parameters của database.

Đây là mẫu thiết kế thực tế khi cần kết hợp **collection fetching** và **pagination** mà không phụ thuộc provider tự phân trang trong bộ nhớ.

## 19. JOIN và EntityGraph

`@EntityGraph` hoặc `EntityManager` entity graph là cách mô tả fetch plan mà không nhất thiết đặt mọi fetching trực tiếp trong câu JPQL.

Ví dụ truy vấn:

```jpql
SELECT o
FROM PurchaseOrder o
WHERE o.status = :status
```

và một fetch graph muốn tải `customer`. Với Spring Data JPA có thể viết:

```java
public interface PurchaseOrderRepository
        extends JpaRepository<PurchaseOrder, Long> {

    @EntityGraph(attributePaths = {"customer"})
    List<PurchaseOrder> findByStatus(
        PurchaseOrder.Status status
    );
}
```

Ví dụ cần import `org.springframework.data.jpa.repository.EntityGraph`, `JpaRepository` và `java.util.List`.

Entity graph thay đổi **cách tải association**, không tự đổi logic lọc của JPQL. Để lọc theo tên khách hoặc trạng thái child, vẫn phải dùng đúng đường dẫn/joins/conditions.

**Không nhầm:**

- `JOIN`: quy định cách ghép các đối tượng trong truy vấn.
- `JOIN FETCH` hoặc entity graph: quy định association nào cần được nạp khi trả entity.
- `cascade`: quy định thao tác vòng đời được lan truyền, không phải phép nối truy vấn.

## 20. Nối qua Map-valued association

JPQL không chỉ nối `List` và `Set`. Nếu entity có một `Map` được ánh xạ, JPQL có thể truy cập **key và value** của các phần tử Map.

Ví dụ một Product có thuộc tính mở rộng:

```java
@ElementCollection(fetch = FetchType.LAZY)
@CollectionTable(
    name = "product_attributes",
    joinColumns = @JoinColumn(name = "product_id")
)
@MapKeyColumn(name = "attribute_key")
@Column(name = "attribute_value")
private Map<String, String> attributes = new HashMap<>();
```

Khi đó:

```jpql
SELECT p.id, KEY(a), VALUE(a)
FROM Product p
JOIN p.attributes a
WHERE p.id = :productId
```

Ý nghĩa:

- `JOIN p.attributes a` nối vào các entry của Map.
- `KEY(a)` lấy key, ví dụ `"color"`.
- `VALUE(a)` lấy value, ví dụ `"black"`.

Có thể dùng:

```jpql
SELECT p
FROM Product p
JOIN p.attributes a
WHERE KEY(a) = :key
  AND VALUE(a) = :value
```

Những sản phẩm có key/value phù hợp được trả về.

### 20.1. Map của entity vẫn là entity association

Nếu mapping là:

```java
@OneToMany(mappedBy = "product")
@MapKey(name = "code")
private Map<String, ProductVariant> variantsByCode;
```

với `ProductVariant` là một `@Entity` có thuộc tính `code`, thì:

```jpql
SELECT v
FROM Product p
JOIN p.variantsByCode v
WHERE KEY(v) = :code
```

`v` đại diện một ProductVariant; `KEY(v)` là key tương ứng của Map. Các chi tiết như cascade, lifecycle của ProductVariant vẫn theo mapping entity, không biến Map thành value collection.

Đây là **một biến thể schema/mapping khác**, không phải field tự có trong class Product tối giản ở mục 3. Muốn chạy trong dự án thật cần định nghĩa `ProductVariant`, quan hệ ngược và collection tương ứng.

### 20.2. INDEX đối với List có @OrderColumn

Nếu một association `List` có `@OrderColumn` để lưu thứ tự, JPQL có thể dùng `INDEX` trên identification variable của phần tử trong những tình huống phù hợp:

```jpql
SELECT l, INDEX(l)
FROM PurchaseOrder o
JOIN o.lines l
WHERE o.id = :orderId
```

Ví dụ này giả định **một biến thể mapping** mà `PurchaseOrder.lines` được cấu hình `@OrderColumn` và provider hỗ trợ ordering theo đặc tả. Trong mô hình gốc không có `@OrderColumn`, không nên coi mọi `List` đều có vị trí được lưu bền vững để truy vấn bằng `INDEX`.

Điểm chung của Map và List là: muốn lấy key/index hoặc thuộc tính của từng phần tử, thường phải **join collection và dùng bí danh của phần tử**.

## 21. Join các quan hệ một-một và nhiều-nhiều

Nguyên tắc association join không chỉ áp dụng cho mô hình Customer–Order.

### 21.1. @OneToOne

Ví dụ `UserAccount` có `UserProfile`:

```java
@OneToOne(mappedBy = "account", fetch = FetchType.LAZY)
private UserProfile profile;
```

Có thể viết:

```jpql
SELECT u
FROM UserAccount u
JOIN u.profile p
WHERE p.displayName = :name
```

Hoặc:

```jpql
SELECT u, p
FROM UserAccount u
LEFT JOIN u.profile p
```

LEFT JOIN phù hợp nếu account có thể chưa tạo profile.

### 21.2. @ManyToMany

Ví dụ `Student` có `Set<Course> courses`:

```java
@ManyToMany
private Set<Course> courses = new HashSet<>();
```

JPQL:

```jpql
SELECT DISTINCT s
FROM Student s
JOIN s.courses c
WHERE c.code = :courseCode
```

Mỗi Student có thể học nhiều Course, nên join có thể nhân bản Student nếu nhiều course thỏa điều kiện. `DISTINCT` diễn đạt ý định lấy một Student duy nhất.

Đây là mẫu khái niệm riêng, giả định `Student` và `Course` đã được ánh xạ đầy đủ. **JOIN qua `@ManyToMany` không có nghĩa JPA phải xóa hoặc persist Course theo Student**; fetching, joining và cascading vẫn là các cơ chế độc lập.

## 22. Không nối entity không có association một cách tùy tiện

Với SQL, ta thường có thể viết:

```sql
FROM purchase_orders o
JOIN customers c ON c.id = o.customer_id
```

Trong JPQL portable quen thuộc, dạng **association join** dựa trên đường dẫn đã được mapping là:

```jpql
FROM PurchaseOrder o
JOIN o.customer c
```

Không được tự mặc định rằng mọi provider và mọi phiên bản Jakarta Persistence đều hỗ trợ cùng một cú pháp để join hai entity **không có association được ánh xạ**:

```jpql
-- Cú pháp entity join độc lập có thể là tính năng
-- của phiên bản/provider, cần kiểm chứng trước.
FROM PurchaseOrder o
JOIN Customer c ON c.id = o.customer.id
```

Một số provider/phiên bản có hỗ trợ mở rộng hoặc những hình thức range/entity join mới, nhưng **nội dung cốt lõi của JPQL cơ bản nên ưu tiên association join** khi quan hệ đã tồn tại.

Nếu hai entity thực sự không có association và cần so khớp theo trường nào đó, có thể dùng nhiều root trong FROM cùng điều kiện WHERE, nhưng phải hiểu semantics:

```jpql
SELECT o
FROM PurchaseOrder o, Customer c
WHERE o.customer = c
  AND c.city = :city
```

Cách viết này tạo nhiều range variables và điều kiện lọc tương ứng, có thể dẫn tới cross join ở SQL trước khi optimizer xử lý. Nó không phải thay thế tốt hơn cho `JOIN o.customer c` khi association đã có.

**Cần xác định rõ phiên bản Jakarta Persistence, provider và cú pháp được hỗ trợ** nếu muốn áp dụng entity joins ngoài association join chuẩn của tài liệu đang dùng.

## 23. JOIN cùng một association nhiều lần

Một truy vấn có thể cần so sánh nhiều tập phần tử với những điều kiện khác nhau. Ví dụ tìm order vừa có dòng sản phẩm danh mục A, vừa có dòng sản phẩm danh mục B.

Một cách dùng hai joins:

```jpql
SELECT DISTINCT o
FROM PurchaseOrder o
JOIN o.lines lineA
JOIN lineA.product productA
JOIN o.lines lineB
JOIN lineB.product productB
WHERE productA.category = :categoryA
  AND productB.category = :categoryB
```

Với mỗi order, số hàng trung gian có thể là **tích số cặp lineA × lineB**. Nếu một order có 4 dòng và 5 dòng thỏa các điều kiện tương ứng, kết quả trung gian có thể lớn.

Có thể cân nhắc hai điều kiện `EXISTS`:

```jpql
SELECT o
FROM PurchaseOrder o
WHERE EXISTS (
    SELECT l1.id
    FROM OrderLine l1
    WHERE l1.order = o
      AND l1.product.category = :categoryA
)
AND EXISTS (
    SELECT l2.id
    FROM OrderLine l2
    WHERE l2.order = o
      AND l2.product.category = :categoryB
)
```

Với một số dữ liệu và chỉ số, cách này dễ biểu đạt “có A” và “có B” mà không nhân toàn bộ cặp phần tử. Nhưng hiệu năng thực tế vẫn phải đo trên database.

### 23.1. Một dòng phải thỏa hai điều kiện hay hai dòng khác nhau?

Hai `EXISTS` có thể cùng tìm thấy **cùng một dòng** nếu `:categoryA` và `:categoryB` giống nhau. Nếu nghiệp vụ đòi hỏi **hai dòng khác nhau**, cần bổ sung điều kiện phân biệt ID hoặc mô hình subquery phù hợp.

Đây là ví dụ cho thấy kết quả không chỉ phụ thuộc annotation, mà còn phụ thuộc logic nghiệp vụ trong `WHERE` và cách đặt aliases.

## 24. JOIN, null và ba giá trị logic của SQL

Khi truy vấn có `LEFT JOIN`, các thuộc tính từ phía không khớp có thể có `null` trong kết quả.

Ví dụ:

```jpql
SELECT c.name, o.id
FROM Customer c
LEFT JOIN c.orders o
```

Với khách Chi, `o.id` là null.

Trong biểu thức điều kiện, SQL sử dụng logic ba giá trị (*TRUE, FALSE, UNKNOWN*) cho nhiều phép so sánh có null. Vì vậy:

```jpql
WHERE o.status <> :status
```

không phải phép kiểm tra “mọi khách không có đơn CONFIRMED” như một người mới có thể nghĩ. Với `o = null`, phép so sánh có thể cho UNKNOWN, khiến hàng không được giữ.

Nếu cần khách **không có bất kỳ order CONFIRMED nào**, cách rõ ràng là:

```jpql
SELECT c
FROM Customer c
WHERE NOT EXISTS (
    SELECT o.id
    FROM PurchaseOrder o
    WHERE o.customer = c
      AND o.status = :status
)
```

Nếu chỉ cần khách hoàn toàn không có đơn:

```jpql
SELECT c
FROM Customer c
WHERE c.orders IS EMPTY
```

**Không dùng `<>` trên alias bên phải left join để suy diễn “không tồn tại phần tử”.** So sánh từng dòng và kiểm tra không tồn tại cả tập là hai bài toán khác nhau.

## 25. Đặt điều kiện ở JOIN hay trên đường dẫn?

Cân nhắc ba truy vấn:

**A. Implicit inner join:**

```jpql
SELECT o
FROM PurchaseOrder o
WHERE o.customer.city = :city
```

**B. Explicit inner join:**

```jpql
SELECT o
FROM PurchaseOrder o
JOIN o.customer c
WHERE c.city = :city
```

**C. Explicit left join:**

```jpql
SELECT o
FROM PurchaseOrder o
LEFT JOIN o.customer c
WHERE c.city = :city
```

Với `PurchaseOrder.customer` bắt buộc và dữ liệu hợp lệ, các truy vấn có thể cho kết quả giống nhau khi city được cung cấp. Nhưng không nên kết luận rằng A, B và C tương đương trong mọi mapping:

- A điều hướng implicit với semantics inner join.
- B yêu cầu explicit inner join.
- C dùng left join nhưng `WHERE c.city = ...` vẫn loại hàng không có customer.
- Nếu yêu cầu giữ order không có customer, phải thay đổi cách đặt điều kiện và projection theo nghiệp vụ.

Đối với association tùy chọn, sự khác nhau rõ hơn. Vì thế khi viết query, cần xuất phát từ câu hỏi:

1. Có cần giữ root khi association null hoặc collection rỗng không?
2. Có cần điều kiện chỉ ảnh hưởng phép nối hay lọc toàn bộ root?
3. Có cần thuộc tính của từng phần tử collection không?
4. Có cần load association hay chỉ lọc/chọn dữ liệu?
5. Có nguy cơ một root xuất hiện nhiều lần sau join không?

Trả lời năm câu hỏi này thường đủ để chọn **path navigation, INNER JOIN, LEFT JOIN, ON, DISTINCT hay FETCH JOIN** phù hợp.

## 26. JPQL và SQL phát sinh: quan sát đúng tầng

Một câu JPQL:

```jpql
SELECT DISTINCT o
FROM PurchaseOrder o
JOIN o.lines l
JOIN l.product p
WHERE p.sku = :sku
```

có thể được provider biến thành SQL minh họa:

```sql
SELECT DISTINCT o.*
FROM purchase_orders o
JOIN order_lines l
    ON l.order_id = o.id
JOIN products p
    ON p.id = l.product_id
WHERE p.sku = ?;
```

Nhưng **không phải cam kết SQL chính xác**. Provider có thể thay đổi:

- Bí danh bảng và cột.
- Kiểu JOIN và vị trí xử lý DISTINCT.
- SQL dành cho fetch plan hoặc lazy associations.
- Việc sử dụng các bảng discriminator/inheritance.
- Batching, cache, parameter binding và giới hạn phân trang.
- Cách dựng entity results khi cùng một row root xuất hiện nhiều lần.

### 26.1. Hiệu năng phụ thuộc cả index

Với mô hình mẫu, index thường cần cân nhắc trên các khóa ngoại dùng để join:

```sql
CREATE INDEX idx_orders_customer
ON purchase_orders(customer_id);

CREATE INDEX idx_lines_order
ON order_lines(order_id);

CREATE INDEX idx_lines_product
ON order_lines(product_id);
```

Unique index trên `products.sku` phục vụ điều kiện lọc theo SKU. Tùy dữ liệu và truy vấn, có thể cân nhắc index ghép như `purchase_orders(customer_id, status)`.

Không nên thêm mọi index có thể nghĩ ra: index làm tăng chi phí INSERT/UPDATE/DELETE và sử dụng dung lượng. Các đề xuất chỉ mang tính định hướng; cần xem query plan và workload thật.

### 26.2. Nhiều JOIN không tự động là xấu

JOIN là công cụ tự nhiên của database quan hệ. Một query có ba joins theo PK/FK được index tốt có thể nhanh hơn việc ứng dụng gọi rất nhiều SELECT trong vòng lặp.

Điểm cần đo là **số dòng trung gian, số lần round-trip, cột được đọc, số entity được khởi tạo, phân trang và mức sử dụng index**, không phải chỉ đếm số chữ `JOIN` trong JPQL.

## 27. Lỗi thường gặp và cách sửa

### Lỗi 1 — Dùng tên bảng SQL trong JPQL

```jpql
-- Sai nếu purchase_orders là tên bảng SQL, không phải entity name.
SELECT o FROM purchase_orders o
```

Dùng tên entity:

```jpql
SELECT o FROM PurchaseOrder o
```

### Lỗi 2 — Viết JOIN trên khóa ngoại thay vì association

```jpql
-- Không phải cách association join thông thường:
JOIN customers c ON c.id = o.customer_id
```

Dùng:

```jpql
JOIN o.customer c
```

Vì `customer_id` là tên cột SQL, còn `o.customer` là thuộc tính quan hệ Java.

### Lỗi 3 — Điều hướng trực tiếp qua collection

```jpql
-- Sai về path navigation:
WHERE o.lines.product.sku = :sku
```

Dùng:

```jpql
JOIN o.lines l
JOIN l.product p
WHERE p.sku = :sku
```

### Lỗi 4 — Tưởng JOIN thường luôn tải association

`JOIN o.customer c` giúp lọc/chọn Customer, **không yêu cầu `o.customer` được fetch** cho mọi entity trả về. Nếu cần dữ liệu liên quan khi truy cập, cân nhắc fetch join, entity graph hoặc DTO.

### Lỗi 5 — Dùng LEFT JOIN rồi WHERE làm mất hàng không khớp

```jpql
LEFT JOIN c.orders o
WHERE o.status = :status
```

có thể loại khách không có đơn. Nếu cần giữ mọi khách, dùng:

```jpql
LEFT JOIN c.orders o ON o.status = :status
```

### Lỗi 6 — Quên DISTINCT khi chọn root qua collection

```jpql
SELECT o FROM PurchaseOrder o JOIN o.lines l
```

có thể có root lặp do nhiều lines. Nếu yêu cầu một order mỗi lần, dùng `SELECT DISTINCT o` hoặc EXISTS tùy mục tiêu.

### Lỗi 7 — Nghĩ DISTINCT luôn làm giảm số hàng SQL trung gian

DISTINCT có thể cần xử lý SQL/materialization và không luôn loại mọi chi phí join. Với projection chứa cả `o.id` và `l.id`, các cặp vẫn khác nhau.

### Lỗi 8 — Join hai collection rồi COUNT sai

Tích số hàng của hai collection khiến COUNT tăng ngoài dự kiến. Cân nhắc `COUNT(DISTINCT ...)`, subquery hoặc các truy vấn thống kê tách biệt.

### Lỗi 9 — Dùng FETCH JOIN collection trực tiếp với phân trang

Một root có nhiều lines làm SQL rows nhân bản, gây phân trang sai hoặc phân trang trong memory. Cân nhắc phân trang ID trước rồi tải các root tương ứng.

### Lỗi 10 — Gắn alias và điều kiện tùy tiện vào JOIN FETCH

Các mở rộng provider có thể không portable. Với JPQL tiêu chuẩn, fetch join không phải công cụ tạo alias để lọc child như JOIN thường.

### Lỗi 11 — Tưởng implicit join tương đương LEFT JOIN

Điều hướng `c.referrer.name` có inner-join semantics; khách không có referrer sẽ bị loại. Dùng explicit LEFT JOIN nếu cần giữ họ.

### Lỗi 12 — Dùng `<>` trên left-joined alias để biểu diễn NOT EXISTS

Điều kiện không bằng trên **một hàng** khác với điều kiện **không có hàng nào** thỏa. Dùng NOT EXISTS khi hỏi về sự vắng mặt của cả một tập liên quan.

### Lỗi 13 — Lạm dụng SELECT entity khi chỉ cần vài cột

`SELECT o` có thể khởi tạo entity và các association theo fetch plan. Với màn hình chỉ cần tên khách và ID đơn, DTO/scalar projection thường rõ và tiết kiệm hơn.

### Lỗi 14 — Cho rằng @ManyToOne LAZY đổi ngữ nghĩa của JOIN

`FetchType.LAZY` mô tả thời điểm tải association vào Java, không biến `JOIN o.customer` thành LEFT JOIN hay thay điều kiện khớp.

### Lỗi 15 — Nhầm owning side với hướng truy vấn

Dù `Customer.orders` là inverse side của mapping hai chiều, `JOIN c.orders o` vẫn hợp lệ. Owning side quyết định SQL UPDATE khóa ngoại, không giới hạn hướng JPQL query.

### Lỗi 16 — Nối input người dùng vào câu JPQL

`"WHERE c.name = '" + input + "'"` dễ lỗi escaping và injection. Sử dụng `:name` cùng `setParameter()`.

### Lỗi 17 — Dùng inner join khi cần dữ liệu cha không có con

`JOIN c.orders o` loại mọi Customer không có order. Dùng `LEFT JOIN` hoặc query chỉ từ Customer rồi chọn collection theo mục tiêu.

### Lỗi 18 — Nghĩ ON thay thế association mapping

`LEFT JOIN c.orders o ON ...` vẫn nối theo `c.orders`. `ON` bổ sung điều kiện tham gia join; không tạo quyền truy cập cột FK Java chưa ánh xạ.

## 28. Bài tập thực hành có hướng dẫn

### Bài 1 — Tìm đơn của khách “An”

Yêu cầu: trả PurchaseOrder của khách tên “An”.

**Cách dùng đường dẫn:**

```jpql
SELECT o
FROM PurchaseOrder o
WHERE o.customer.name = :name
```

**Cách dùng explicit join:**

```jpql
SELECT o
FROM PurchaseOrder o
JOIN o.customer c
WHERE c.name = :name
```

Cả hai phù hợp vì đi qua association đơn trị.

### Bài 2 — Lấy mọi khách cùng ID đơn, kể cả chưa đặt

```jpql
SELECT c.name, o.id
FROM Customer c
LEFT JOIN c.orders o
ORDER BY c.id, o.id
```

Kết quả mẫu chứa Chi với `o.id = null`. Dùng INNER JOIN sẽ loại Chi.

### Bài 3 — Lấy mọi khách cùng ID đơn CONFIRMED nếu có

```jpql
SELECT c.name, o.id
FROM Customer c
LEFT JOIN c.orders o
    ON o.status = :status
ORDER BY c.id, o.id
```

Không đặt điều kiện vào WHERE nếu mục tiêu là giữ cả khách không có đơn xác nhận.

### Bài 4 — Đơn có sản phẩm mã KB-001

```jpql
SELECT DISTINCT o
FROM PurchaseOrder o
JOIN o.lines l
JOIN l.product p
WHERE p.sku = :sku
```

Phải join collection `lines` để có bí danh cho từng `OrderLine`. `DISTINCT` đảm bảo một order không bị lặp theo mục tiêu.

### Bài 5 — Đếm tất cả đơn của mỗi khách

```jpql
SELECT c.name, COUNT(o)
FROM Customer c
LEFT JOIN c.orders o
GROUP BY c.id, c.name
ORDER BY c.id
```

Dùng LEFT JOIN để giữ khách không có order, và `COUNT(o)` để nhận số 0.

### Bài 6 — Đơn không có dòng hàng

```jpql
SELECT o
FROM PurchaseOrder o
WHERE o.lines IS EMPTY
```

Vì chỉ kiểm tra collection rỗng, không bắt buộc join tới từng OrderLine.

### Bài 7 — Đơn không chứa SKU đã chọn

```jpql
SELECT o
FROM PurchaseOrder o
WHERE NOT EXISTS (
    SELECT l.id
    FROM OrderLine l
    WHERE l.order = o AND l.product.sku = :sku
)
```

Đây là “không có bất kỳ dòng nào thuộc SKU đó”, khác với tìm một dòng có SKU khác.

### Bài 8 — Lấy Order kèm Customer để hiển thị

```jpql
SELECT o
FROM PurchaseOrder o
JOIN FETCH o.customer
WHERE o.status = :status
```

Đây là fetch join; nếu chỉ cần scalar, có thể chọn `o.id, c.name` qua JOIN thường để tránh tải entity không cần thiết.

### Bài 9 — Lấy Order kèm toàn bộ dòng hàng

```jpql
SELECT DISTINCT o
FROM PurchaseOrder o
LEFT JOIN FETCH o.lines
WHERE o.id = :orderId
```

LEFT JOIN giữ order nếu lines rỗng. Không dùng cấu trúc này để phân trang hàng loạt order mà chưa xét hiện tượng nhân bản SQL rows.

### Bài 10 — Tên khách và người giới thiệu

```jpql
SELECT c.name, r.name
FROM Customer c
LEFT JOIN c.referrer r
ORDER BY c.name
```

Khách không có referrer vẫn được trả về với tên referrer null.

### Bài 11 — Một order có dòng category A và category B

Dùng hai điều kiện EXISTS như mục 23. Giải thích tại sao hai lần JOIN cùng collection có thể tạo nhiều cặp lineA/lineB.

### Bài 12 — Vì sao query LEFT JOIN lại loại khách Chi?

```jpql
SELECT c
FROM Customer c
LEFT JOIN c.orders o
WHERE o.status = :status
```

Vì WHERE yêu cầu điều kiện ở phía right; hàng `o = null` không thỏa. Sửa bằng điều kiện `ON` nếu nghiệp vụ muốn giữ tất cả Customer.

## 29. Câu hỏi tự kiểm tra

**1. Trong JPQL, `JOIN o.customer c` dùng tên bảng hay tên thuộc tính Java?**

Dùng thuộc tính association `customer` của entity `PurchaseOrder`, không trực tiếp dùng tên bảng `customers` hoặc cột `customer_id`.

**2. `o.customer.name` có thể tạo implicit join không?**

Có. Điều hướng qua association đơn trị thường có semantics tương ứng inner join.

**3. Vì sao `o.lines.product.name` sai?**

`lines` là collection, không phải một OrderLine đơn trị. Phải `JOIN o.lines l` rồi đi tiếp từ `l.product.name` hoặc join Product tường minh.

**4. `JOIN` và `LEFT JOIN` khác nhau ở đâu?**

INNER JOIN chỉ giữ hàng có liên kết phù hợp; LEFT JOIN giữ hàng bên trái ngay cả khi không có liên kết khớp, với phía phải null.

**5. Vì sao `LEFT JOIN ... WHERE o.status = :status` có thể không giữ khách chưa có đơn?**

Vì WHERE lọc sau join; hàng bên phải null không thỏa điều kiện trên `o.status`.

**6. Khi nào dùng `ON` thay cho `WHERE`?**

Đặc biệt khi cần giới hạn phần tử tham gia outer join mà vẫn giữ các entity phía trái không có phần tử khớp.

**7. Một Customer có hai orders: `SELECT c FROM Customer c JOIN c.orders o` có thể tạo điều gì?**

Có thể tạo nhiều hàng/result occurrences tương ứng với cùng Customer do hai orders. Dùng `DISTINCT c` hoặc EXISTS nếu muốn kết quả Customer không lặp.

**8. `SELECT DISTINCT o.id, l.id` có buộc mỗi order chỉ có một hàng không?**

Không. Các cặp `(orderId, lineId)` khác nhau vẫn là các kết quả distinct.

**9. `JOIN o.customer c` có chắc tải đầy đủ `o.customer` không?**

Không. JOIN thường dùng cho điều kiện/projection; để yêu cầu tải association, dùng JOIN FETCH hoặc fetch plan phù hợp.

**10. Có thể dùng `JOIN FETCH` để tùy ý đặt alias và `ON` lọc một phần collection trong JPQL portable không?**

Không nên. Fetch join có quy tắc hạn chế về bí danh và không phải công cụ an toàn để tải một managed collection chỉ một phần.

**11. Tại sao phân trang root Order bằng collection fetch join có thể có vấn đề?**

Vì mỗi Order sinh nhiều SQL rows; áp LIMIT/OFFSET vào hàng join không tương đương page theo số root Order.

**12. Muốn đếm số đơn của mọi khách, kể cả khách có 0 đơn, dùng gì?**

`LEFT JOIN c.orders o` kết hợp `COUNT(o)` và `GROUP BY` theo Customer.

**13. Khi chỉ cần kiểm tra tồn tại child, tại sao EXISTS có thể hợp lý hơn JOIN?**

EXISTS kiểm tra có ít nhất một hàng phù hợp mà không cần nhân root rows trong FROM của truy vấn chính.

**14. `Customer.orders` ở inverse side có dùng được `JOIN c.orders o` không?**

Có. `mappedBy` liên quan tới owning side của mapping ghi dữ liệu, không ngăn JPQL join theo association từ phía cha.

**15. `FetchType.LAZY` có nghĩa câu `JOIN` sẽ trở thành `LEFT JOIN` không?**

Không. Fetch type và join type là hai quyết định khác nhau.

## 30. Ghi nhớ cốt lõi

**JPQL nối các entity dựa trên relationship mapping**, sử dụng những đường dẫn như `o.customer` hoặc `o.lines` thay vì viết trực tiếp tên bảng SQL và cột foreign key. Với **association đơn trị**, có thể truy cập qua dấu chấm như `o.customer.name`; việc điều hướng này có ngữ nghĩa implicit inner join. Với **collection-valued association**, muốn lấy field từng phần tử phải **JOIN tường minh** để tạo bí danh như `JOIN o.lines l`.

**`JOIN` (inner join)** chỉ giữ các quan hệ khớp; **`LEFT JOIN`** có thể giữ entity nguồn ngay cả khi thiếu association đích. Khi dùng outer join, **`ON` và `WHERE` khác nhau**: điều kiện ở ON lọc thành phần tham gia join, còn WHERE lọc kết quả sau khi join và có thể vô tình loại các hàng null từ bên phải.

Khi join collection, một entity cha có thể xuất hiện nhiều lần do nhiều con; cân nhắc **`DISTINCT`, `EXISTS`, `GROUP BY` hoặc DTO projection** theo mục tiêu. Đừng nhầm **JOIN thường** (lọc/chọn kết quả) với **JOIN FETCH** (nạp association). Fetch join có ích chống N+1 nhưng cần thận trọng với collection lớn, nhiều collection cùng lúc và phân trang.

Cuối cùng, hãy thiết kế truy vấn từ **ý nghĩa nghiệp vụ**: cần giữ những root nào, có cần phần tử con nào, điều kiện gắn với phép nối hay với toàn bộ kết quả, và có cần managed entity hay chỉ cần vài cột. Hiểu rõ các câu hỏi ấy sẽ giúp sử dụng **phép nối tường minh và truy cập đường dẫn quan hệ** đúng, dễ đọc, portable và hiệu quả trong JPA.
