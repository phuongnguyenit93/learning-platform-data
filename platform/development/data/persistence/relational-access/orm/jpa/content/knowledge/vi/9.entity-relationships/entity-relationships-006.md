# Đồng bộ hai phía quan hệ bằng phương thức nghiệp vụ

> **Chủ đề:** Data Persistence – Relational Access, ORM, JPA  
> **Nhóm kiến thức:** Quan hệ thực thể

Trong mô hình hướng đối tượng, một quan hệ hai chiều thường được biểu diễn bằng **hai tham chiếu Java**: một nhân viên có thuộc tính `department`, và một phòng ban có tập `employees`. Trong cơ sở dữ liệu quan hệ, quan hệ ấy có thể chỉ được lưu bằng **một khóa ngoại** `employees.department_id`. JPA biết cách ánh xạ hai phía vào cùng một quan hệ, nhưng **không tự duy trì hai tham chiếu Java cho mọi thao tác trên đối tượng**.

Nếu code chỉ gọi `department.getEmployees().add(employee)` mà không gán `employee.department`, bộ nhớ có thể hiển thị một nhân viên thuộc phòng ban, trong khi INSERT/UPDATE không lưu khóa ngoại như mong đợi. Ngược lại, nếu chỉ gọi `employee.setDepartment(department)`, database có thể nhận đúng FK nhưng collection `department.employees` đang ở trong bộ nhớ vẫn thiếu nhân viên đó.

Giải pháp là đặt những **phương thức nghiệp vụ điều phối quan hệ** như `addEmployee`, `removeEmployee`, `moveToDepartment`, `addComment`, `setProfile` hoặc `enroll`. Những phương thức này cập nhật **cả hai phía của mô hình đối tượng** theo một quy tắc thống nhất, đồng thời giữ đúng phía sở hữu quan hệ để JPA phát sinh SQL.

Bài học tập trung vào cách viết helper method an toàn cho **@OneToMany/@ManyToOne**, **@OneToOne** và **@ManyToMany**, đặc biệt với chuyển chủ sở hữu, xóa thành phần, `orphanRemoval`, `cascade`, lazy collection, tính nhất quán trong persistence context và kiểm thử sau khi flush/clear.

## 1. Một quan hệ có hai biểu diễn khác nhau

Giả sử database có hai bảng:

~~~sql
CREATE TABLE departments (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(120) NOT NULL
);

CREATE TABLE employees (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    full_name VARCHAR(120) NOT NULL,
    department_id BIGINT REFERENCES departments(id)
);
~~~

Một nhân viên có thể thuộc một phòng ban hoặc chưa được phân công. Cột `department_id` là **nguồn biểu diễn quan hệ ở database**. Trong Java, hai entity có thể ánh xạ như sau:

~~~java
@Entity
@Table(name = "departments")
public class Department {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String name;

    @OneToMany(mappedBy = "department")
    private List<Employee> employees = new ArrayList<>();

    // Constructor và phương thức nghiệp vụ...
}
~~~

~~~java
@Entity
@Table(name = "employees")
public class Employee {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "full_name", nullable = false)
    private String fullName;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "department_id")
    private Department department;

    // Constructor và phương thức nghiệp vụ...
}
~~~

Sơ đồ:

~~~text
                    Java object model

Department ── employees: List<Employee> ──► Employee
     ▲                                        │
     └────────────── department ◄─────────────┘

                    Database model

departments.id ◄──── employees.department_id (FK)
~~~

Quan hệ Java có thể đi cả hai hướng; database chỉ cần FK nằm ở bảng `employees`. Hai phía Java giúp duyệt object graph thuận tiện, nhưng phải được giữ nhất quán trong suốt thao tác nghiệp vụ.

### 1.1. Phía sở hữu và phía đối ứng

Với mapping ở trên:

- **Employee.department** là **owning side**: `@ManyToOne` ánh xạ trực tiếp cột `department_id`. Khi quan hệ thay đổi, JPA dùng trạng thái phía này để xác định FK cần ghi.
- **Department.employees** là **inverse side**: `@OneToMany(mappedBy = "department")` nói rằng quan hệ đã được ánh xạ ở thuộc tính `Employee.department`.
- Chuỗi **"department"** trong `mappedBy` là **tên thuộc tính Java trên Employee**, không phải tên cột `department_id`.
- **Owning side** không đồng nghĩa đối tượng nào có quyền nghiệp vụ quyết định. Domain có thể cho phép chỉ Department thực hiện thao tác chuyển nhân viên, dù FK vẫn được JPA ghi qua Employee.

**Quy tắc then chốt:** khi làm việc với quan hệ hai chiều, cập nhật cả hai phía ở **bộ nhớ Java**; riêng đối với SQL, phải cập nhật đúng **phía sở hữu quan hệ**.

## 2. Điều gì xảy ra khi chỉ cập nhật một phía?

### 2.1. Chỉ thêm vào collection phía inverse

~~~java
Department development = em.find(Department.class, 10L);
Employee lan = em.find(Employee.class, 50L);

development.getEmployees().add(lan);
// lan.getDepartment() vẫn có thể là null hoặc phòng ban cũ.
~~~

Vì `Department.employees` dùng `mappedBy`, việc sửa riêng collection không đảm bảo thay đổi `employees.department_id`. Trong persistence context, code vừa làm cho collection và đối tượng Employee mâu thuẫn với nhau:

~~~text
development.employees  chứa lan  ✓
lan.department         vẫn null ✗
employees.department_id vẫn NULL sau flush nếu không có đường ghi khác
~~~

Nếu collection phía inverse có cascade hoặc orphan removal, việc sửa collection còn có thể có ảnh hưởng vòng đời entity; càng cần tránh để hai phía lệch nhau.

### 2.2. Chỉ gán phía owning

~~~java
Employee lan = em.find(Employee.class, 50L);
Department development = em.find(Department.class, 10L);

lan.setDepartment(development);
// development.getEmployees() có thể chưa chứa lan.
~~~

Ở trường hợp này, **FK có thể được ghi đúng** khi transaction flush vì owning side đã đổi. Nhưng nếu `development.employees` đã được khởi tạo trong persistence context, service hoặc API đang đọc collection có thể thấy dữ liệu cũ.

Ví dụ điều kiện nghiệp vụ:

~~~java
if (development.getEmployees().size() < MAX_EMPLOYEES) {
    // Có thể quyết định sai nếu collection và owning side lệch nhau.
}
~~~

Việc gọi `em.flush()` không đồng nghĩa JPA sẽ tự xây lại toàn bộ quan hệ đối ứng trong các object đã load. `flush` đồng bộ SQL cần thiết với database; nó không phải một lệnh "sửa mọi liên kết trong object graph".

### 2.3. Ba loại nhất quán cần tách bạch

| Loại | Câu hỏi phải trả lời | Cơ chế |
|---|---|---|
| **Nhất quán object graph** | `employee.department == department` và collection chứa đúng nhân viên chưa? | Phương thức nghiệp vụ cập nhật cả hai phía |
| **Nhất quán persistence mapping** | Phía sở hữu được đổi đúng để ORM sinh FK/update join table chưa? | `mappedBy`, `@JoinColumn`, owning side |
| **Nhất quán dữ liệu đã commit** | SQL đã chạy, constraint có hợp lệ và transaction commit chưa? | Flush, transaction, FK, UNIQUE, khóa/version |

Helper method giải quyết chủ yếu vấn đề thứ nhất và hỗ trợ vấn đề thứ hai. Nó không thay thế transaction, ràng buộc database hoặc cơ chế xử lý xung đột khi nhiều request đồng thời.

## 3. Thiết kế API nghiệp vụ: không phơi bày collection để sửa tùy ý

Một thiết kế khó kiểm soát:

~~~java
public List<Employee> getEmployees() {
    return employees;
}

public void setDepartment(Department department) {
    this.department = department;
}
~~~

Khi mọi lớp đều có thể gọi setter hoặc `getEmployees().clear()`, rất khó bảo đảm hai phía được cập nhật đồng thời. Chỉ cần quên một dòng là object graph lệch nhau.

Thay vào đó, mô hình nên có các thao tác rõ ý nghĩa:

~~~java
department.addEmployee(employee);
department.removeEmployee(employee);
employee.moveTo(newDepartment);
~~~

Với mỗi lời gọi, code duy trì một **bất biến**:

> Nếu `employee.department` trỏ đến `department`, collection `department.employees` phải chứa employee; nếu employee chuyển đi, collection phòng ban cũ phải không còn chứa employee.

Ở đây "chứa" được hiểu trên cùng object graph/persistence context đang thao tác. Không được đánh đồng việc hai instance từ hai EntityManager khác nhau có cùng ID database với việc chúng là cùng reference Java.

### 3.1. Tách phương thức công khai và thao tác nội bộ

Một cách phổ biến là có một **đường điều phối duy nhất**:

- API công khai `Department.addEmployee` gọi `Employee.moveTo`.
- `Employee.moveTo` cập nhật owning side rồi thay đổi hai collection thông qua phương thức nội bộ.
- Các phương thức nội bộ chỉ thêm/xóa trong collection, **không gọi lại API công khai**; như vậy tránh vòng gọi đệ quy.

Phương thức `getEmployees` chỉ cho phép đọc hoặc trả một view không cho sửa trực tiếp. Code gọi phải dùng helper thay vì tự thay đổi collection.

## 4. Ví dụ hoàn chỉnh: Department–Employee có thể chuyển phòng ban

Ví dụ này minh họa quan hệ **nhiều–một**, cho phép nhân viên chưa được phân công (`department_id` nullable). Không bật `orphanRemoval`, vì nhân viên có vòng đời độc lập với phòng ban.

### 4.1. Entity Department

~~~java
package com.example.company;

import jakarta.persistence.*;
import java.util.ArrayList;
import java.util.Collections;
import java.util.Iterator;
import java.util.List;
import java.util.Objects;

@Entity
@Table(name = "departments")
public class Department {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "name", nullable = false, length = 120)
    private String name;

    @OneToMany(mappedBy = "department")
    private List<Employee> employees = new ArrayList<>();

    protected Department() {
        // Constructor cho JPA.
    }

    public Department(String name) {
        if (name == null || name.isBlank()) {
            throw new IllegalArgumentException("Tên phòng ban không được trống");
        }
        this.name = name;
    }

    public Long getId() {
        return id;
    }

    public String getName() {
        return name;
    }

    public List<Employee> getEmployees() {
        return Collections.unmodifiableList(employees);
    }

    public void addEmployee(Employee employee) {
        Objects.requireNonNull(employee, "employee");
        employee.moveTo(this);
    }

    public void removeEmployee(Employee employee) {
        Objects.requireNonNull(employee, "employee");
        if (employee.getDepartment() == this) {
            employee.moveTo(null);
        }
    }

    // Phương thức nội bộ: chỉ chỉnh collection, không gọi ngược moveTo().
    void addEmployeeInternal(Employee employee) {
        for (Employee current : employees) {
            if (current == employee) {
                return; // Idempotent trong cùng object graph.
            }
        }
        employees.add(employee);
    }

    void removeEmployeeInternal(Employee employee) {
        for (Iterator<Employee> it = employees.iterator(); it.hasNext(); ) {
            if (it.next() == employee) {
                it.remove();
                return;
            }
        }
    }
}
~~~

### 4.2. Entity Employee: một nơi điều phối việc chuyển quan hệ

~~~java
package com.example.company;

import jakarta.persistence.*;

@Entity
@Table(name = "employees")
public class Employee {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "full_name", nullable = false, length = 120)
    private String fullName;

    @ManyToOne(fetch = FetchType.LAZY, optional = true)
    @JoinColumn(name = "department_id", nullable = true)
    private Department department;

    protected Employee() {
    }

    public Employee(String fullName) {
        if (fullName == null || fullName.isBlank()) {
            throw new IllegalArgumentException("Tên nhân viên không được trống");
        }
        this.fullName = fullName;
    }

    public Long getId() {
        return id;
    }

    public String getFullName() {
        return fullName;
    }

    public Department getDepartment() {
        return department;
    }

    public void moveTo(Department newDepartment) {
        if (department == newDepartment) {
            // Nếu gọi lặp lại, bảo đảm collection bên kia vẫn có phần tử.
            if (newDepartment != null) {
                newDepartment.addEmployeeInternal(this);
            }
            return;
        }

        Department oldDepartment = department;

        if (oldDepartment != null) {
            oldDepartment.removeEmployeeInternal(this);
        }

        // Owning side: thuộc tính này quyết định department_id trong SQL.
        department = newDepartment;

        if (newDepartment != null) {
            newDepartment.addEmployeeInternal(this);
        }
    }
}
~~~

Đây là một lựa chọn thiết kế: **Employee.moveTo** điều phối hai phía, còn các method **addEmployeeInternal/removeEmployeeInternal** chỉ quản lý collection. Nhờ vậy, các lời gọi không đệ quy vô hạn.

### 4.3. Trường hợp tạo quan hệ mới

~~~java
Department engineering = new Department("Engineering");
Employee lan = new Employee("Lan");

engineering.addEmployee(lan);

assert lan.getDepartment() == engineering;
assert engineering.getEmployees().contains(lan);
~~~

Trên object graph đang dùng, bất biến đã đúng ngay sau `addEmployee`, trước khi gọi `persist` hoặc `flush`.

Nếu dùng JPA trực tiếp với resource-local transaction:

~~~java
EntityTransaction tx = em.getTransaction();
try {
    tx.begin();

    Department engineering = new Department("Engineering");
    Employee lan = new Employee("Lan");
    engineering.addEmployee(lan);

    em.persist(engineering);
    em.persist(lan); // Không có cascade trong mapping của ví dụ.

    tx.commit();
} catch (RuntimeException e) {
    if (tx.isActive()) {
        tx.rollback();
    }
    throw e;
}
~~~

Trong mô hình trên, thứ tự/chi tiết SQL phụ thuộc provider và chiến lược tạo khóa, nhưng về bản chất khi lưu nhân viên, FK lấy từ **lan.department**:

~~~sql
INSERT INTO departments (name) VALUES ('Engineering');
-- Lấy id đã sinh, ví dụ 10.

INSERT INTO employees (full_name, department_id)
VALUES ('Lan', 10);
~~~

Việc thêm nhân viên vào **engineering.employees** giúp code Java nhất quán; riêng FK được JPA xác định từ owning side **Employee.department**.

### 4.4. Trường hợp chuyển nhân viên sang phòng ban khác

~~~java
Department engineering = em.find(Department.class, 10L);
Department operations = em.find(Department.class, 20L);
Employee lan = em.find(Employee.class, 50L);

operations.addEmployee(lan);
~~~

Giả sử ban đầu `lan.department == engineering`. Phương thức `moveTo` sẽ:

1. Xóa `lan` khỏi collection `engineering.employees` nếu phần tử đang có trong collection được quản lý.
2. Gán `lan.department = operations`, tức đổi phía sở hữu.
3. Thêm `lan` vào `operations.employees` nếu chưa có.

Sau khi flush, ORM có thể phát:

~~~sql
UPDATE employees
SET department_id = 20
WHERE id = 50;
~~~

Trong database, một nhân viên không bị "chuyển" bằng cách xóa rồi insert lại nhân viên; chỉ có FK thay đổi. Khi hai collection đều được thao tác từ cùng persistence context, các reference Java cũng phản ánh việc chuyển phòng ngay lập tức.

### 4.5. Trường hợp bỏ phân công

~~~java
engineering.removeEmployee(lan);
~~~

Với schema `department_id` nullable và **không có orphanRemoval**, ý nghĩa là **nhân viên vẫn tồn tại nhưng không còn phòng ban**:

~~~sql
UPDATE employees
SET department_id = NULL
WHERE id = 50;
~~~

Nếu nghiệp vụ bắt buộc mọi nhân viên luôn thuộc phòng ban, thì không nên cho phép `moveTo(null)`; lúc đó cần thay đổi API và schema thành `nullable=false`. Phương thức `removeEmployee` sẽ phải mang ý nghĩa khác, ví dụ chuyển tới phòng mặc định, hoặc không hỗ trợ remove độc lập.

### 4.6. Tại sao ví dụ dùng so sánh reference?

Ví dụ dùng `current == employee` trong collection và `department == newDepartment` để điều phối các object đang thuộc **cùng persistence context**. JPA bảo đảm identity map trong một context: cùng entity type và database identity được quản lý như một managed instance.

Đừng lấy `Employee` từ EntityManager A rồi gán vào `Department` từ EntityManager B và giả định reference equality còn đúng. Khi làm việc với detached entity, proxy hoặc hai persistence context, có thể có nhiều object Java đại diện cùng một hàng; cần thiết kế rõ cách nạp và đối chiếu entity trong transaction hiện tại.

Trong ví dụ không dùng `List.contains` hoặc `List.remove(Object)` cho logic nội bộ để tránh phụ thuộc vào cách cài `equals/hashCode` của entity. Cách này vẫn có chi phí duyệt collection và có thể làm khởi tạo lazy collection; phần hiệu năng được thảo luận ở sau.

## 5. Những bất biến nên được duy trì trong mọi phương thức

Một helper method đáng tin cậy nên xử lý được những tình huống sau:

| Tình huống | Hành vi mong muốn |
|---|---|
| Thêm một employee chưa có department | Gán owning side và thêm vào collection mới |
| Thêm cùng employee vào cùng department lần nữa | Không tạo phần tử trùng và không làm hỏng trạng thái |
| Chuyển employee từ A sang B | Xóa khỏi A, đổi owning side sang B, thêm vào B |
| Bỏ phân công khi FK nullable | Xóa khỏi collection cũ, gán owning side thành null |
| Remove một employee không thuộc department này | Không ảnh hưởng quan hệ thực tế |
| Thêm employee null | Báo lỗi đầu vào rõ ràng |
| Employee và Department từ hai persistence context khác nhau | Tránh trộn graph; nạp đối tượng thích hợp trong cùng đơn vị công việc |

Khi triển khai domain có quy tắc riêng, còn cần kiểm tra:

- Phòng ban có đang hoạt động không?
- Nhân viên có được phép chuyển phòng lúc đang làm dự án không?
- Có giới hạn số nhân viên hay yêu cầu quyền phê duyệt không?
- Cần ghi lịch sử chuyển phòng hay thông báo cho hệ thống khác không?
- Việc chuyển có thể diễn ra đồng thời từ hai request không?

Những quy tắc đó nên sống trong service/aggregate phù hợp, bên cạnh phương thức đồng bộ quan hệ. Helper method giữ invariant của object graph; transaction và cơ chế khóa/version bảo vệ trạng thái khi có cạnh tranh.

## 6. Trường hợp sở hữu vòng đời: Post–Comment với orphanRemoval

Mô hình Department–Employee không xóa employee khi rời department. Nhưng có những quan hệ **thành phần**: một comment chỉ tồn tại như một phần của post trong mô hình nghiệp vụ, hoặc một dòng đơn hàng chỉ tồn tại trong đơn hàng.

Trong trường hợp đó có thể dùng:

~~~java
@OneToMany(
    mappedBy = "post",
    cascade = CascadeType.ALL,
    orphanRemoval = true
)
private List<Comment> comments = new ArrayList<>();
~~~

**orphanRemoval=true** có nghĩa khi một entity con đã được quản lý bị loại khỏi quan hệ sở hữu theo semantics của JPA, provider sẽ xóa nó khi đồng bộ theo lifecycle thích hợp. Đây là thao tác **xóa entity con**, không đơn thuần set FK về NULL.

### 6.1. Class Post với helper methods

~~~java
package com.example.blog;

import jakarta.persistence.*;
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;
import java.util.Objects;

@Entity
@Table(name = "posts")
public class Post {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "title", nullable = false)
    private String title;

    @OneToMany(
        mappedBy = "post",
        cascade = CascadeType.ALL,
        orphanRemoval = true
    )
    private List<Comment> comments = new ArrayList<>();

    protected Post() {}

    public Post(String title) {
        this.title = Objects.requireNonNull(title);
    }

    public List<Comment> getComments() {
        return Collections.unmodifiableList(comments);
    }

    public void addComment(Comment comment) {
        Objects.requireNonNull(comment, "comment");
        if (comment.getPost() != null && comment.getPost() != this) {
            throw new IllegalStateException(
                "Comment đã thuộc Post khác; không chuyển một orphan sang Post mới"
            );
        }

        for (Comment existing : comments) {
            if (existing == comment) {
                return;
            }
        }

        comments.add(comment);
        comment.attachTo(this);
    }

    public void removeComment(Comment comment) {
        Objects.requireNonNull(comment, "comment");
        for (int index = 0; index < comments.size(); index++) {
            if (comments.get(index) == comment) {
                comments.remove(index);
                comment.attachTo(null);
                return;
            }
        }
    }
}
~~~

### 6.2. Class Comment sở hữu khóa ngoại

~~~java
package com.example.blog;

import jakarta.persistence.*;
import java.util.Objects;

@Entity
@Table(name = "comments")
public class Comment {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "body", nullable = false, length = 2000)
    private String body;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "post_id", nullable = false)
    private Post post;

    protected Comment() {}

    public Comment(String body) {
        this.body = Objects.requireNonNull(body);
    }

    public Post getPost() {
        return post;
    }

    // Chỉ helper của Post trong cùng package được chủ động điều phối FK.
    void attachTo(Post post) {
        this.post = post;
    }
}
~~~

Với cách tổ chức này:

~~~java
Post post = new Post("JPA relationship helpers");
post.addComment(new Comment("Bài viết hữu ích"));
post.addComment(new Comment("Ví dụ rõ ràng"));

em.persist(post); // CascadeType.ALL chứa PERSIST => lưu cả comments.
~~~

Khi xóa comment:

~~~java
Post post = em.find(Post.class, postId);
Comment comment = post.getComments().get(0);
post.removeComment(comment);
// Khi flush, comment bị coi là orphan để xóa theo mapping.
~~~

Ở đây **@ManyToOne** trên Comment vẫn là owning side của FK `post_id`; helper cập nhật cả **post.comments** và **comment.post**. Sự khác biệt so với Department–Employee là **orphanRemoval** làm thay đổi vòng đời: comment bị tách khỏi Post sẽ được xóa.

### 6.3. Không dùng orphanRemoval cho quan hệ có nhu cầu chuyển chủ thường xuyên

Khi một entity con có thể được chuyển từ parent A sang B, cần thận trọng:

~~~java
oldPost.removeComment(comment); // Với orphanRemoval=true: có thể đánh dấu DELETE.
newPost.addComment(comment);    // Không được giả định "hủy orphan" sẽ an toàn.
~~~

JPA không định nghĩa việc chuyển một entity đã bị orphan sang parent khác trong cùng transaction là trường hợp nên phụ thuộc để khôi phục entity; các provider có thể xử lý khác nhau hoặc báo lỗi. Nếu nghiệp vụ cần chuyển parent, cân nhắc **không sử dụng orphanRemoval**, hoặc thiết kế quy trình tạo bản ghi mới/thay thế rõ ràng theo vòng đời thực tế.

Trong mẫu Post–Comment trên, `addComment` chủ động từ chối comment đã gắn với Post khác. Nếu yêu cầu thay thế comment, hãy định nghĩa thao tác riêng và xử lý rõ thực thể cũ có bị xóa không.

### 6.4. Cascade và đồng bộ hai phía là hai việc khác nhau

| Cơ chế | Ý nghĩa chính | Điều nó không tự làm |
|---|---|---|
| **Helper add/remove** | Giữ hai phía object graph nhất quán | Không tự mở transaction, không tự commit |
| **CascadeType.PERSIST** | Lan thao tác persist từ parent sang con | Không gán FK nếu owning side vẫn null |
| **CascadeType.MERGE** | Lan thao tác merge theo mapping | Không thay thế việc thiết kế invariant trên graph |
| **CascadeType.REMOVE** | Khi remove parent, lan remove sang con | Không đồng nghĩa loại con khỏi collection sẽ xóa con |
| **orphanRemoval=true** | Xóa con khi rời quan hệ sở hữu theo semantics thích hợp | Không phù hợp mặc định cho entity con có vòng đời độc lập |
| **Foreign key ở DB** | Chặn tham chiếu tới parent không tồn tại | Không cập nhật collection Java |

Đặc biệt không nên đặt **CascadeType.REMOVE** bừa bãi vào **@ManyToMany** giữa các entity độc lập. Xóa một Student không có nghĩa xóa luôn Course mà những Student khác đang học.

## 7. Quan hệ @OneToOne hai chiều: gắn và tháo đối tượng

Ví dụ một tài khoản có một hồ sơ riêng:

~~~text
UserAccount.profile  ─────────► UserProfile
UserAccount          ◄───────── UserProfile.account

Database: user_profiles.account_id
          FOREIGN KEY tới user_accounts.id
          UNIQUE để bảo đảm 1–1
~~~

Mapping:

~~~java
@Entity
@Table(name = "user_accounts")
public class UserAccount {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @OneToOne(mappedBy = "account", cascade = CascadeType.ALL,
              orphanRemoval = true)
    private UserProfile profile;

    protected UserAccount() {}

    public UserProfile getProfile() {
        return profile;
    }

    public void attachProfile(UserProfile newProfile) {
        if (profile == newProfile) {
            return;
        }
        if (newProfile != null
                && newProfile.getAccount() != null
                && newProfile.getAccount() != this) {
            throw new IllegalStateException("Profile đã thuộc tài khoản khác");
        }

        UserProfile oldProfile = profile;
        profile = newProfile;

        if (oldProfile != null) {
            oldProfile.attachTo(null);
        }
        if (newProfile != null) {
            newProfile.attachTo(this);
        }
    }
}
~~~

~~~java
@Entity
@Table(name = "user_profiles")
public class UserProfile {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @OneToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "account_id", nullable = false, unique = true)
    private UserAccount account;

    protected UserProfile() {}

    public UserAccount getAccount() {
        return account;
    }

    void attachTo(UserAccount account) {
        this.account = account;
    }
}
~~~

**UserProfile.account** là owning side và ghi `account_id`. **UserAccount.profile** dùng `mappedBy` và là phía đối ứng. Helper `attachProfile` cập nhật cả hai reference. Với `orphanRemoval=true`, việc thay profile cũ bằng profile mới có thể yêu cầu chú ý **thứ tự DELETE/INSERT và UNIQUE constraint** ở database; provider không nhất thiết phát SQL theo thứ tự mà ta mong đợi. Nếu cần thay thế profile trong production, hãy xác định lifecycle và kiểm tra thao tác thực tế trên database, hoặc cập nhật nội dung profile hiện có khi có thể.

Với shared primary key one-to-one, **@MapsId** có thể phù hợp hơn: profile dùng khóa chính bằng ID của account. Dù dùng @MapsId, helper vẫn phải điều phối hai reference Java nếu mapping là hai chiều.

## 8. Quan hệ @ManyToMany: đồng bộ hai collection

Mối quan hệ nhiều–nhiều giữa Student và Course thường dùng một bảng nối:

~~~sql
CREATE TABLE student_courses (
    student_id BIGINT NOT NULL REFERENCES students(id),
    course_id BIGINT NOT NULL REFERENCES courses(id),
    PRIMARY KEY (student_id, course_id)
);
~~~

Giả sử **Student.courses** là owning side với **@JoinTable**, còn **Course.students** là inverse side với `mappedBy="courses"`.

### 8.1. Student điều phối đăng ký/hủy đăng ký

~~~java
@Entity
@Table(name = "students")
public class Student {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToMany
    @JoinTable(
        name = "student_courses",
        joinColumns = @JoinColumn(name = "student_id"),
        inverseJoinColumns = @JoinColumn(name = "course_id")
    )
    private Set<Course> courses = new HashSet<>();

    protected Student() {}

    public Set<Course> getCourses() {
        return Collections.unmodifiableSet(courses);
    }

    public void enroll(Course course) {
        Objects.requireNonNull(course);
        if (courses.add(course)) {
            course.addStudentInternal(this);
        }
    }

    public void unenroll(Course course) {
        Objects.requireNonNull(course);
        if (courses.remove(course)) {
            course.removeStudentInternal(this);
        }
    }
}
~~~

### 8.2. Course giữ collection đối ứng

~~~java
@Entity
@Table(name = "courses")
public class Course {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToMany(mappedBy = "courses")
    private Set<Student> students = new HashSet<>();

    protected Course() {}

    public Set<Student> getStudents() {
        return Collections.unmodifiableSet(students);
    }

    void addStudentInternal(Student student) {
        students.add(student);
    }

    void removeStudentInternal(Student student) {
        students.remove(student);
    }
}
~~~

Các snippet giả định import `jakarta.persistence.*`, `java.util.*` tương ứng. Trong thiết kế này, gọi:

~~~java
student.enroll(course);
~~~

thì **hai collection cùng phản ánh đăng ký**, còn ORM ghi bảng nối dựa trên owning side **Student.courses**:

~~~sql
INSERT INTO student_courses (student_id, course_id)
VALUES (?, ?);
~~~

Khi `unenroll`, SQL có thể là DELETE một dòng ở bảng nối. Không vì vậy mà Student hoặc Course phải bị xóa.

### 8.3. Lưu ý với Set và equals/hashCode

`HashSet` dựa trên `equals/hashCode`. Với entity có ID được database cấp sau `persist`, cách cài `hashCode` sai có thể làm phần tử "mất tích" trong Set khi ID đổi từ null sang giá trị thật. Entity cũng có thể được đại diện bằng proxy. Vì thế:

- Không dùng Lombok `@Data` một cách máy móc trên entity để sinh equals/hashCode từ mọi field và quan hệ.
- Không đưa các collection quan hệ mutable vào equals/hashCode, vì có thể gây đệ quy vòng, lazy loading và thay đổi hash.
- Nếu dùng business key để so sánh, khóa ấy phải thật sự ổn định và duy nhất.
- Nếu dùng generated ID để định nghĩa equality, phải có chính sách cho ID null và hashCode ổn định trong suốt thời gian entity được đặt trong Set.

Các ví dụ dùng `Set` để thể hiện tính không trùng của cặp Student–Course, nhưng phải triển khai equality đúng cho mô hình thực tế. Unique/primary key trên bảng nối vẫn là lớp bảo vệ dữ liệu cuối cùng.

### 8.4. Khi quan hệ nhiều–nhiều có dữ liệu riêng

Nếu việc đăng ký khóa học có **registeredAt**, **status**, **grade**, bản ghi nối không còn là liên kết thuần túy:

~~~text
Student 1 ─── * Enrollment * ─── 1 Course
               ├── registeredAt
               ├── status
               └── grade
~~~

Thiết kế phù hợp thường là **Enrollment entity** với hai association `@ManyToOne` và có thể có unique constraint trên `(student_id, course_id)`. Khi đó hãy viết helper `student.addEnrollment(enrollment)`, `course.addEnrollment(enrollment)` hoặc method nghiệp vụ `enroll(student, course)` bảo đảm owning sides và collection đối ứng nhất quán.

Không cố nhét những trường nghiệp vụ của một quan hệ vào mapping `@ManyToMany` trực tiếp vì JPA không có chỗ quản lý trạng thái riêng của từng link trong mapping join table đơn giản.

## 9. API cho quan hệ bắt buộc và quan hệ tùy chọn

Phương thức nghiệp vụ phải phù hợp với ràng buộc thực tế của database.

### 9.1. Quan hệ tùy chọn

~~~java
@ManyToOne(fetch = FetchType.LAZY, optional = true)
@JoinColumn(name = "department_id", nullable = true)
private Department department;
~~~

API `employee.moveTo(null)` có ý nghĩa: nhân viên chưa được phân công. Database cho phép FK NULL.

### 9.2. Quan hệ bắt buộc

~~~java
@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "department_id", nullable = false)
private Department department;
~~~

Nếu dữ liệu yêu cầu nhân viên luôn thuộc phòng ban:

~~~java
public void transferTo(Department target) {
    Objects.requireNonNull(target, "Phòng ban đích là bắt buộc");
    // Đồng bộ collection cũ/mới và owning side.
}
~~~

Không cung cấp một thao tác "remove employee khỏi department" chỉ gán FK null rồi hy vọng database chấp nhận. Nếu muốn xóa hẳn nhân viên, hãy thực hiện hành vi xóa entity với lifecycle và quyền phù hợp. Nếu muốn chuyển, target phải được chỉ định.

Với thay đổi từ A sang B trong cùng transaction, ORM có thể UPDATE trực tiếp FK A → B, không cần NULL ở giữa. Tuy nhiên domain method phải tránh để trạng thái trung gian không hợp lệ bị flush trong khi còn thiếu target.

### 9.3. Ràng buộc ở hai nơi

`@ManyToOne(optional=false)` và `@JoinColumn(nullable=false)` mô tả tính bắt buộc ở tầng JPA/schema generation. **FOREIGN KEY NOT NULL trên database đang chạy** bảo vệ dữ liệu từ mọi client. Nếu schema hiện hữu chưa có constraint, chỉ sửa annotation không tự bảo đảm ràng buộc đã được áp dụng.

Quy tắc khác như "một phòng ban tối đa 20 người" thường không thể giải quyết bằng một FK đơn giản; cần phối hợp logic nghiệp vụ, transaction và chiến lược xử lý đồng thời.

## 10. Phương thức nghiệp vụ nào nên sở hữu hành vi đồng bộ?

Không có một tên method đúng cho mọi domain. Có ba lựa chọn thường gặp:

| Cách tổ chức | Ví dụ | Khi phù hợp |
|---|---|---|
| Parent điều phối | `order.addLine(item)` | Child phụ thuộc parent, có lifecycle thành phần |
| Child điều phối | `employee.moveTo(department)` | Child có identity độc lập, dễ chuyển parent |
| Domain service điều phối, gọi helper entity | `assignmentService.assign(employeeId, departmentId)` | Cần quyền, kiểm tra nhiều aggregate, transaction hoặc sự kiện |

Đối với một aggregate như Order–OrderLine, parent thường là điểm vào nghiệp vụ. Với Employee–Department, child có thể có method chuyển vì FK thuộc Employee, nhưng service vẫn cần kiểm tra điều kiện như quyền chuyển và capacity.

Ví dụ service:

~~~java
@Service
public class AssignmentService {
    private final EmployeeRepository employees;
    private final DepartmentRepository departments;

    public AssignmentService(
            EmployeeRepository employees,
            DepartmentRepository departments
    ) {
        this.employees = employees;
        this.departments = departments;
    }

    @Transactional
    public void transfer(long employeeId, long targetDepartmentId) {
        Employee employee = employees.findById(employeeId)
                .orElseThrow(() -> new IllegalArgumentException("Employee không tồn tại"));
        Department target = departments.findById(targetDepartmentId)
                .orElseThrow(() -> new IllegalArgumentException("Department không tồn tại"));

        // Các kiểm tra quyền và quy tắc nghiệp vụ đặt tại đây.
        employee.moveTo(target);
    }
}
~~~

Đoạn này giả định Spring Data JPA repositories và các import Spring tương ứng; nó minh họa ranh giới transaction. Vì Employee được nạp trong transaction và managed, JPA có thể dirty-check owning side ở flush/commit. Không nhất thiết phải gọi `save(employee)` chỉ để lưu thay đổi trên một managed entity; hành vi cụ thể khi dùng Spring Data cần xét entity state/transaction.

Nếu muốn domain không expose `moveTo` công khai, có thể để phương thức package-private và chỉ service/aggregate phù hợp gọi. Điều quan trọng là **mọi đường ghi quan hệ trong hệ thống đều đi qua cùng quy tắc**.

## 11. Getter, setter, constructor và Lombok

### 11.1. Tránh setter sinh tự động cho cả hai phía

Một entity như:

~~~java
@Setter
@Getter
@Entity
public class Employee { ... }
~~~

có thể vô tình cho phép bất cứ code nào gọi `setDepartment` trực tiếp, phá bất biến giữa hai phía. Tương tự, getter trả về collection mutable cho phép `add/remove/clear` không qua helper.

Giải pháp có thể là:

- Chỉ tạo getter cần thiết; không sinh public setter cho association.
- Trả collection dưới dạng unmodifiable view hoặc phương thức truy vấn có chủ đích.
- Cung cấp `add/remove/transfer/attach/detach` thực hiện đúng quan hệ hai chiều.
- Dùng method nội bộ (package-private) cho thao tác thực sự chỉ thay collection hoặc gán reference.
- Tránh cho `toString` hoặc `equals/hashCode` truy cập toàn bộ association, vì dễ đệ quy vòng hay vô tình kích hoạt lazy loading.

### 11.2. Constructor cũng phải giữ invariant

Một constructor như:

~~~java
public Employee(String fullName, Department department) {
    this.fullName = fullName;
    this.department = department;
}
~~~

chỉ gán owning side, khiến collection đối ứng bị thiếu employee. Có thể:

~~~java
public Employee(String fullName, Department department) {
    this(fullName);
    moveTo(department);
}
~~~

hoặc tạo entity với dữ liệu cơ bản trước, rồi gọi `department.addEmployee(employee)` từ factory/service. Chọn cách phù hợp để không gọi vào association chưa được khởi tạo trong constructor và không tạo dependency phức tạp.

JPA cần constructor không tham số public hoặc protected theo đặc tả cho entity thông thường. Các method nghiệp vụ không thay thế yêu cầu đó.

### 11.3. Không chỉ sửa inverse collection từ setter

Một setter naive:

~~~java
public void setDepartment(Department newDepartment) {
    department = newDepartment;
    newDepartment.getEmployees().add(this);
}
~~~

có ít nhất ba lỗi:

1. Không xóa employee khỏi collection của department cũ.
2. Gọi setter với null gây NullPointerException.
3. Gọi lặp lại có thể thêm trùng vào List.

Vì vậy helper nên xét **trạng thái cũ**, **trạng thái mới**, **trường hợp gọi lặp** và **trường hợp null hợp lệ**.

## 12. Lazy loading và chi phí của helper method

Một entity có:

~~~java
@OneToMany(mappedBy = "department", fetch = FetchType.LAZY)
private List<Employee> employees = new ArrayList<>();
~~~

Thông thường, truy cập vào collection có thể khiến provider chạy SQL để load phần tử. Helper gọi `employees.contains`, duyệt iterator hoặc `employees.add` có thể khởi tạo collection tùy provider/mapping/trạng thái.

Nếu Department có hàng trăm nghìn nhân viên, việc load toàn bộ danh sách chỉ để chuyển một nhân viên có thể tốn bộ nhớ, thời gian và tạo SQL không cần thiết.

### 12.1. Giữ model nhất quán nhưng biết giới hạn quy mô

Mẫu helper cập nhật cả hai phía đặc biệt hữu ích khi:

- Object graph đang được sử dụng trong transaction.
- Collection có kích thước vừa phải, thuộc aggregate nghiệp vụ.
- Logic sau đó sẽ đọc collection và yêu cầu thấy thay đổi ngay.

Nếu collection rất lớn và không bao giờ được thao tác như một aggregate trong bộ nhớ, hãy cân nhắc:

- Chọn **@ManyToOne** là đường ghi chủ đạo, và chỉ cung cấp query repository để lấy danh sách con theo parent ID.
- Không đặt bidirectional association nếu không có use case cần duyệt cả hai phía.
- Không tải collection lớn chỉ để đếm; dùng `SELECT COUNT`/repository query có điều kiện.
- Nếu cần thao tác theo batch hoặc bulk SQL, thiết kế transaction và vô hiệu/truy vấn lại trạng thái persistence context phù hợp.

Đây không phải lý do bỏ mặc hai phía không đồng bộ trong một graph đang được dùng. Đó là lý do chọn **mô hình chỉ một chiều** hoặc giới hạn aggregate khi việc đồng bộ hai chiều không phù hợp quy mô.

### 12.2. Getter unmodifiable không tránh được query

`Collections.unmodifiableList(employees)` ngăn code bên ngoài gọi `add/remove` trên view, nhưng việc duyệt view vẫn có thể làm lazy collection được load. Nó chỉ là biện pháp bảo vệ API, không phải tối ưu SQL.

### 12.3. Thứ tự collection không mặc định được đảm bảo

Với List, thứ tự phần tử lưu/đọc lại không được bảo đảm chỉ vì dùng `ArrayList`. Nếu nghiệp vụ phụ thuộc thứ tự, cần cấu hình như **@OrderBy** hoặc **@OrderColumn** và hiểu khác biệt: **@OrderBy** sắp xếp theo giá trị khi tải, **@OrderColumn** lưu vị trí thứ tự như dữ liệu quan hệ. Helper thay đổi vị trí có thể cần cập nhật order column, ngoài FK.

## 13. Không trộn entity từ nhiều persistence context

Giả sử:

~~~java
EntityManager em1 = emf.createEntityManager();
EntityManager em2 = emf.createEntityManager();

Employee e = em1.find(Employee.class, 50L);
Department d = em2.find(Department.class, 10L);

e.moveTo(d); // Hai instance được quản lý bởi hai context khác nhau.
~~~

Đây không phải cách làm nên dùng trong transaction nghiệp vụ bình thường. Bên cạnh khó khăn với so sánh reference, quan hệ có thể dẫn tới lỗi detached/managed state, proxy và thay đổi không được tracking trong đúng context.

Nên thực hiện:

~~~java
// Trong một transaction và EntityManager có phạm vi rõ ràng:
Employee e = em.find(Employee.class, employeeId);
Department d = em.find(Department.class, departmentId);
e.moveTo(d);
~~~

Với dữ liệu đầu vào chỉ chứa ID, service nên nạp/kiểm tra entity phù hợp trong context hiện tại rồi gọi helper. **`em.getReference`** cũng có thể lấy reference dựa trên ID khi thích hợp, nhưng một ID không tồn tại có thể chỉ gây lỗi khi truy cập hoặc khi FK được ghi; không nên xem getReference như kiểm tra tồn tại.

### 13.1. Detached entity và merge

Sau khi EntityManager đóng, entity trở thành detached. Sửa cả hai phía trên detached object không tự làm SQL được ghi. `merge(detached)` sao chép trạng thái vào managed instance được trả về, có thể làm việc với nhiều association và cascade tùy mapping.

Nếu mục tiêu là thay đổi một quan hệ từ HTTP request, đường đi rõ ràng thường là:

~~~text
HTTP DTO chứa employeeId và newDepartmentId
     ↓
Service mở transaction
     ↓
find/getReference các managed entity phù hợp
     ↓
Gọi domain helper trên managed graph
     ↓
Flush/commit; DB kiểm tra FK và ràng buộc
~~~

Tránh deserialize nguyên một entity graph có collection từ JSON rồi `merge` một cách không kiểm soát. Collection bị thiếu hoặc null trong payload có thể gây cập nhật/xóa ngoài ý muốn, nhất là khi `orphanRemoval=true`.

## 14. Helper và thao tác trực tiếp bằng JPQL/native SQL

Helper method chỉ được gọi khi code thao tác trên entity Java. Những câu lệnh như:

~~~java
em.createQuery(
        "update Employee e set e.department = :newDepartment where e.id = :id")
  .setParameter("newDepartment", target)
  .setParameter("id", employeeId)
  .executeUpdate();
~~~

hoặc:

~~~sql
UPDATE employees
SET department_id = 20
WHERE id = 50;
~~~

thay dữ liệu trực tiếp mà không chạy `Employee.moveTo`, và **không tự đồng bộ collection đang loaded trong persistence context**. JPQL bulk update thường bỏ qua dirty checking/callback thông thường của từng managed entity, nên graph có thể bị stale.

Nếu sử dụng bulk DML:

- Xác định transaction boundary và các constraint DB.
- Hiểu rằng dữ liệu managed trước đó có thể cũ.
- Cân nhắc `clear`, `refresh`, tạo persistence context mới hoặc tải lại đúng entity/collection, theo use case.
- Không vừa chỉnh graph bằng helper rồi thực hiện bulk update liên quan mà không xác định thứ tự flush và cách làm mới state.

Đối với import hàng loạt, việc không đi qua helper có thể có lý do hiệu năng, nhưng invariants của database và quy trình dữ liệu vẫn phải được bảo vệ.

## 15. Đồng bộ hai phía không thay thế transaction và concurrency control

Giả sử hai request cùng chuyển employee:

~~~text
Request A: Employee 50 chuyển sang Department 10
Request B: Employee 50 chuyển sang Department 20

Cả hai đều dùng moveTo() đúng, nhưng chạy trong hai transaction riêng.
~~~

Helper giúp **mỗi request** giữ hai reference Java nhất quán. Nó không quyết định request nào phải thắng khi commit đồng thời. Nếu business yêu cầu phát hiện xung đột, thêm **@Version** cho Employee:

~~~java
@Version
private Long version;
~~~

Provider có thể dùng version trong UPDATE để phát hiện một transaction ghi đè lên trạng thái đã thay đổi bởi transaction khác. Ứng dụng cần xử lý lỗi optimistic locking và quyết định retry hoặc báo người dùng.

Nếu bất biến liên quan đến **nhiều hàng**, ví dụ số lượng nhân viên không vượt một giới hạn, `@Version` trên Employee không tự bảo vệ việc hai request thêm hai nhân viên khác nhau vào cùng Department. Cần thiết kế kiểm soát concurrency phù hợp ở aggregate/Department, constraint, lock, transaction isolation hoặc thao tác database nguyên tử tùy use case.

Đồng bộ hai phía còn khác với **toàn vẹn tham chiếu**:

- **FK** chặn employee tham chiếu department không tồn tại.
- **NOT NULL** chặn employee không có department nếu nghiệp vụ yêu cầu.
- **UNIQUE** trên FK có thể giúp triển khai one-to-one.
- **PK/UNIQUE** trên bảng nối ngăn duplicate many-to-many link.
- **Helper** giữ state Java đúng trong object graph đang thao tác.

Đây là các lớp bảo vệ bổ sung cho nhau.

## 16. Kiểm thử đúng cả hai phía và dữ liệu được lưu

Một bài test chỉ gọi:

~~~java
department.addEmployee(employee);
assertSame(department, employee.getDepartment());
~~~

chưa đủ chứng minh FK đã được lưu đúng. Ngược lại, chỉ query SQL sau commit cũng chưa chứng minh collection Java được đồng bộ trước flush.

Nên kiểm tra **hai giai đoạn**:

1. **Trước flush:** hai reference trong cùng object graph đúng như business invariant.
2. **Sau flush + clear + load lại:** quan hệ được ghi đúng ở database qua owning side và có thể được dựng lại đúng ở persistence context mới.

### 16.1. Test tạo quan hệ mới

Ví dụ JUnit trong một test transaction phù hợp:

~~~java
@Test
void addEmployeeKeepsBothSidesAndPersistsFk() {
    Department department = new Department("QA");
    Employee employee = new Employee("Minh");

    department.addEmployee(employee);

    assertSame(department, employee.getDepartment());
    assertTrue(department.getEmployees().contains(employee));

    em.persist(department);
    em.persist(employee);
    em.flush();

    Long departmentId = department.getId();
    Long employeeId = employee.getId();
    em.clear();

    Employee loaded = em.find(Employee.class, employeeId);
    assertEquals(departmentId, loaded.getDepartment().getId());
}
~~~

Ví dụ giả định `EntityManager` và transaction test được cấu hình, cũng như các static imports JUnit. `flush` thực thi SQL trong transaction; `clear` buộc tìm lại entity từ database thay vì trả instance đang managed. Nếu transaction chưa commit, đây là cách kiểm chứng mapping trong cùng transaction, chưa phải kiểm chứng visibility từ transaction khác.

### 16.2. Test chuyển phòng

~~~java
@Test
void transferRemovesFromOldAndAddsToNew() {
    Department oldDepartment = new Department("Old");
    Department newDepartment = new Department("New");
    Employee employee = new Employee("Lan");

    oldDepartment.addEmployee(employee);
    newDepartment.addEmployee(employee);

    assertSame(newDepartment, employee.getDepartment());
    assertFalse(oldDepartment.getEmployees().contains(employee));
    assertTrue(newDepartment.getEmployees().contains(employee));
}
~~~

Test này bắt được hai lỗi phổ biến: quên xóa khỏi parent cũ và quên cập nhật owning side. Trong integration test, lưu hai Department và Employee, sau đó reload và kiểm tra `department_id` cuối cùng.

### 16.3. Test gọi lặp và bỏ phân công

~~~java
@Test
void addingTwiceDoesNotDuplicateEmployee() {
    Department department = new Department("Support");
    Employee employee = new Employee("An");

    department.addEmployee(employee);
    department.addEmployee(employee);

    assertEquals(1, department.getEmployees().size());
    assertSame(department, employee.getDepartment());

    department.removeEmployee(employee);
    assertNull(employee.getDepartment());
    assertFalse(department.getEmployees().contains(employee));
}
~~~

Vì ví dụ Department–Employee cho phép FK nullable và không bật orphanRemoval, bỏ phân công không xóa Employee. Đối với Post–Comment có orphanRemoval, test lại phải kiểm tra **Comment bị DELETE** ở database.

### 16.4. Các ca kiểm thử nên có

| Ca | Điều cần xác minh |
|---|---|
| Thêm child vào parent | Owning reference và inverse collection đều được cập nhật |
| Thêm lặp | Không nhân đôi phần tử/link |
| Chuyển child A → B | A không còn chứa child, B có chứa, FK ghi theo B |
| Remove khỏi quan hệ nullable | FK null; child còn tồn tại nếu không orphanRemoval |
| Remove khỏi quan hệ orphanRemoval | Child bị xóa theo lifecycle khi flush |
| Thay một one-to-one | Cả hai reference đúng; constraint UNIQUE và thứ tự SQL được xử lý |
| Enroll/unenroll many-to-many | Hai collection cùng đổi; bảng nối thêm/xóa, Student/Course không bị xóa |
| Entity detached hoặc graph trộn nhiều context | API/service không cho trạng thái không quản lý gây sai |
| Bulk DML can thiệp association | Managed state cũ được refresh/clear theo thiết kế |
| Hai request đồng thời thay quan hệ | Version, khóa hoặc quy tắc transaction xử lý đúng xung đột |

## 17. Các lỗi thiết kế thường gặp

| Lỗi | Hệ quả | Hướng khắc phục |
|---|---|---|
| Chỉ `parent.children.add(child)` với `mappedBy` | Owning side không đổi; FK có thể không được cập nhật | Helper gán `child.parent` và collection |
| Chỉ `child.parent = parent` | Collection đang loaded có thể cũ | Đồng bộ thêm vào parent collection |
| Quên remove khỏi parent cũ khi chuyển | Child xuất hiện ở cả hai collection Java | Lấy oldParent, remove cũ rồi add mới |
| Setter gọi qua lại không có guard | Đệ quy vô hạn/StackOverflowError | Có một method điều phối, các method nội bộ chỉ chỉnh một phía |
| Expose collection mutable công khai | Caller có thể sửa inverse mà không đổi owner | Getter read-only + helper có tên nghiệp vụ |
| Helper thêm trùng | List có nhiều reference cùng child | Kiểm tra trước khi thêm; DB constraint khi phù hợp |
| `orphanRemoval=true` trên child có thể chuyển parent | Child có thể bị DELETE ngoài ý muốn | Chỉ bật với quan hệ sở hữu vòng đời thực sự |
| Dùng CascadeType.ALL trên many-to-many shared entity | Có thể lan REMOVE sang entity dùng chung | Giới hạn cascade theo vòng đời |
| Dùng Set với hashCode thay đổi sau persist | Remove/contains sai | Cài equality ổn định hoặc đổi chiến lược collection |
| Dùng Lombok `@Data` với association hai chiều | equals/toString có thể gọi nhau và kích hoạt lazy loading | Viết phương thức có chủ đích, loại association khỏi equals/toString |
| Chuyển entity bằng graph detached | Thay đổi không được tracking, merge khó kiểm soát | Nạp managed entity trong transaction rồi gọi helper |
| Dựa vào flush để đồng bộ collection Java | Object graph vẫn có thể cũ | Helper đồng bộ trước flush; reload khi cần |
| Helper load collection khổng lồ | Truy vấn nhiều, tăng bộ nhớ và latency | Giảm bidirectional mapping, query theo ID hoặc điều chỉnh aggregate |
| Chỉ test reference trong RAM | FK sai vẫn qua test | Thêm integration test flush + clear + load lại |
| Nhầm `mappedBy` với quyền nghiệp vụ | API tổ chức theo mapping thay vì invariant | Tách lựa chọn ownership ORM và điểm điều phối domain |

## 18. Bài tập thực hành

### Bài 1: Tìm lỗi trong code một phía

Giả sử:

~~~java
@OneToMany(mappedBy = "order")
private List<OrderItem> items = new ArrayList<>();

public void addItem(OrderItem item) {
    items.add(item);
}
~~~

`OrderItem` có:

~~~java
@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "order_id", nullable = false)
private PurchaseOrder order;
~~~

Hãy xác định owning side và giải thích vì sao `addItem` chưa đủ. Viết lại helper sao cho:

- Không chấp nhận null.
- Không thêm cùng item hai lần.
- Gán `item.order = this` thông qua method nội bộ.
- Không tự chuyển một item đã thuộc đơn khác nếu nghiệp vụ không cho phép.

Gợi ý:

~~~java
public void addItem(OrderItem item) {
    Objects.requireNonNull(item);
    if (item.getOrder() != null && item.getOrder() != this) {
        throw new IllegalStateException("Item đã thuộc đơn khác");
    }
    if (!items.contains(item)) {
        items.add(item);
    }
    item.assignOrder(this);
}
~~~

Khi dùng `contains` phải hiểu `equals/hashCode` của entity; có thể đổi sang kiểm tra reference trong cùng context như ví dụ Department.

### Bài 2: Viết helper chuyển một người phụ trách

Mô hình:

~~~text
Team.members        @OneToMany(mappedBy = "team")
Member.team         @ManyToOne @JoinColumn(name = "team_id")
~~~

Hãy viết:

~~~java
teamA.addMember(member);
teamB.addMember(member);
~~~

với kết quả:

~~~text
member.team == teamB
teamA.members không còn member
teamB.members có member đúng một lần
~~~

Giải thích vì sao UPDATE FK cần lấy trạng thái từ Member.team và vì sao collection Team.members cần được đồng bộ dù nó không sở hữu FK.

### Bài 3: Phân biệt remove và orphanRemoval

Trong hai mô hình:

**A.** Department–Employee dùng `@OneToMany(mappedBy="department")`, FK nullable, **không có orphanRemoval**.  
**B.** PurchaseOrder–OrderItem dùng `@OneToMany(mappedBy="order", orphanRemoval=true)`, FK NOT NULL.

Nếu loại child khỏi collection và cập nhật owning side phù hợp, điều gì xảy ra sau flush trong mỗi mô hình? Vì sao **B** nên được thiết kế với API `removeItem` thể hiện ý nghĩa xóa một dòng hàng?

**Gợi ý:** A có thể UPDATE FK thành NULL; B có thể DELETE OrderItem do vòng đời phụ thuộc Order. Không áp dụng chính sách của B cho Employee nếu nhân viên phải còn tồn tại sau khi đổi phòng ban.

### Bài 4: Sửa vòng gọi đệ quy

~~~java
class Parent {
    void add(Child child) {
        children.add(child);
        child.setParent(this);
    }
}

class Child {
    void setParent(Parent parent) {
        this.parent = parent;
        parent.add(this);
    }
}
~~~

Hãy chỉ ra nguyên nhân StackOverflowError. Sau đó viết lại theo một trong hai phương án:

1. Parent điều phối toàn bộ, Child có method nội bộ chỉ gán reference; hoặc
2. Child điều phối toàn bộ, Parent có method nội bộ chỉ thêm/xóa collection.

Yêu cầu xử lý null (nếu nghiệp vụ cho phép), gọi lặp và chuyển từ parent cũ sang mới.

### Bài 5: Many-to-many có dữ liệu phụ

Quan hệ Student–Course cần lưu điểm số và thời điểm đăng ký. Vì sao một mapping `@ManyToMany` đơn giản không đủ? Hãy đề xuất **Enrollment** như entity chứa:

~~~text
id
student_id (FK)
course_id (FK)
registered_at
grade
UNIQUE(student_id, course_id)
~~~

Viết phác thảo service method `enroll(studentId, courseId)`, nêu nơi kiểm tra trùng và cách dùng helper để các association/collection đối ứng không lệch nhau. Đừng chỉ dựa vào `existsBy...` vì hai request có thể đồng thời đăng ký; unique constraint là lớp chống trùng cuối cùng.

### Bài 6: Quan hệ hai chiều và transaction

Hai request cùng chuyển Employee số 5 sang hai Department khác nhau. Cả hai đều gọi đúng `moveTo`. Câu hỏi:

1. Helper có đủ ngăn lost update không?
2. `@Version` trên Employee giúp phát hiện xung đột nào?
3. Nếu hai request cùng thêm hai Employee khác nhau vào Department còn đúng một chỗ trống, version trên từng Employee có đủ bảo vệ giới hạn số người không?

**Định hướng:** helper bảo vệ RAM trong từng transaction; optimistic locking trên Employee có thể phát hiện ghi đè cùng Employee; bất biến về sức chứa Department cần biện pháp đồng thời khác theo thiết kế domain/database.

### Bài 7: Thiết kế kiểm thử round-trip

Viết integration test cho chuyển Department A → B:

1. Persist hai Department và Employee thuộc A.
2. Flush/clear để chắc chắn bắt đầu từ trạng thái đã lưu.
3. Load lại cả ba entity trong cùng EntityManager.
4. Gọi `B.addEmployee(employee)`.
5. Kiểm tra cả hai collection và owning reference trước flush.
6. Flush/clear, load Employee từ DB và kiểm tra FK trỏ tới B.

Giải thích vì sao test chỉ `assertSame(B, employee.getDepartment())` không thể chứng minh mapping SQL đúng.

## 19. Quy trình lựa chọn helper method cho mỗi quan hệ

Khi thêm một association hai chiều vào entity model, hãy đi theo trình tự:

1. **Xác định ý nghĩa nghiệp vụ:** quan hệ có bắt buộc không? Child có vòng đời độc lập không? Có được chuyển parent không?
2. **Xác định owning side JPA:** FK nằm ở đâu? `mappedBy` trỏ đến field nào? Với many-to-many, bên nào sở hữu join table?
3. **Chọn API công khai:** `add/remove`, `moveTo`, `attach/detach`, `enroll/unenroll` theo ý nghĩa domain.
4. **Quy định bất biến hai phía:** sau thao tác, reference và collection phải phản ánh cùng một liên kết.
5. **Viết đường điều phối duy nhất:** phương thức nội bộ cập nhật một phía mà không gọi đệ quy; hỗ trợ gọi lặp và parent cũ.
6. **Chọn lifecycle:** cascade để lan operation khi phù hợp; orphanRemoval chỉ khi tách child nghĩa là xóa child.
7. **Thiết kế database constraint:** FK, NOT NULL, UNIQUE và các constraint phù hợp trên bảng nối/bảng con.
8. **Đặt transaction và concurrency control:** thao tác trên managed entity trong cùng persistence context; xét version, khóa và giới hạn liên hàng.
9. **Kiểm soát chi phí collection:** không bắt ứng dụng load toàn bộ tập quan hệ khổng lồ nếu mô hình chỉ cần truy vấn theo FK.
10. **Kiểm thử hai giai đoạn:** object graph trước flush và dữ liệu nạp lại sau flush/clear.

Ghi nhớ:

~~~text
Owning side      quyết định dữ liệu FK / join table được ORM ghi.
Inverse side     cho phép duyệt ngược nhưng không tự là nguồn ghi quan hệ.
Helper method    giữ cả hai phía Java nhất quán ngay sau một thao tác.
Cascade          điều khiển việc lan thao tác persistence.
orphanRemoval    điều khiển xóa child khi rời quan hệ sở hữu.
Transaction      điều khiển phạm vi commit / rollback.
DB constraint    bảo vệ dữ liệu thật ở mọi đường ghi.
~~~

**Kết luận:** đồng bộ hai phía quan hệ bằng phương thức nghiệp vụ giúp object graph Java phản ánh đúng các liên kết mà JPA sẽ lưu vào database. Việc chọn một đường điều phối, cập nhật cả owning side và inverse side, xử lý chuyển parent hoặc xóa child theo vòng đời, và tránh sửa collection tùy ý là nền tảng cho quan hệ JPA dễ hiểu và đáng tin cậy. Khi kết hợp với transaction, constraint, locking và kiểm thử persistence, mô hình hai chiều sẽ phục vụ nghiệp vụ thay vì trở thành nguồn lỗi khó phát hiện.
