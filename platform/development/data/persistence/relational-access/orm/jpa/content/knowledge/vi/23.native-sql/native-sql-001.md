# Khi nào cần truy vấn SQL trực tiếp qua JPA

## 1. Vì sao có Native SQL khi đã có JPQL?

Jakarta Persistence (JPA) cho phép truy vấn dữ liệu qua **JPQL** và **Criteria API**: chúng làm việc với tên entity, thuộc tính Java, quan hệ và kiểu dữ liệu trong mô hình ánh xạ. Provider, ví dụ Hibernate hoặc EclipseLink, dịch truy vấn đó sang SQL phù hợp với hệ quản trị cơ sở dữ liệu (DBMS).

Tuy nhiên, có những tình huống sử dụng trực tiếp **SQL của database** mang lại lợi ích rõ rệt: biểu thức phân tích phức tạp, recursive CTE, khả năng riêng của PostgreSQL/Oracle/SQL Server, truy vấn JSON, tìm kiếm toàn văn, gợi ý optimizer, báo cáo nhiều cấp tổng hợp, hoặc cập nhật hàng loạt tối ưu cho dữ liệu lớn.

JPA cung cấp **Native SQL Query** để vẫn dùng cơ sở hạ tầng EntityManager nhưng chủ động viết SQL:

~~~java
List<?> rows = em.createNativeQuery(
    "select id, sku, price from products where active = true"
).getResultList();
~~~

Điểm khác biệt:

- **JPQL** dùng tên entity và property, ví dụ **select p from Product p where p.status = :status**.
- **Native SQL** dùng **tên bảng, cột, biểu thức và cú pháp thật của DB**, ví dụ **select * from products where status = 'ACTIVE'**.
- **Native SQL vẫn chạy qua EntityManager**, có thể tham gia transaction JPA/JTA; nhưng provider không thể tự suy luận mọi đặc điểm của SQL thủ công như với JPQL.

> Nguyên tắc lựa chọn: **dùng JPQL/Criteria cho bài toán JPA diễn đạt tốt và đủ nhanh; chọn Native SQL khi có một yêu cầu cụ thể về ngữ nghĩa SQL, khả năng DBMS, tối ưu hóa hoặc tích hợp mà JPQL không thể diễn đạt một cách phù hợp, dễ bảo trì và đã được kiểm chứng.**

Không nên mặc định Native SQL luôn nhanh hơn JPQL. Một câu JPQL đơn giản có thể tạo SQL rất tốt, còn một native query viết kém có thể full table scan, sort hàng triệu bản ghi hoặc tạo N+1 ở tầng ứng dụng.

## 2. Ba tầng cần phân biệt

~~~text
Ứng dụng Java
    |
    +-- JPQL / Criteria API
    |       |
    |       +-- JPA provider dịch entity/attribute -> SQL
    |
    +-- Native SQL qua EntityManager
    |       |
    |       +-- Lập trình viên viết SQL bảng/cột trực tiếp
    |       +-- Provider bind parameters, chạy query, ánh xạ kết quả
    |
    +-- JDBC hoặc công cụ SQL chuyên dụng
            |
            +-- Lập trình viên điều khiển SQL/ResultSet sâu hơn
    |
    v
Database driver / connection / transaction
    |
    v
PostgreSQL / MySQL / Oracle / SQL Server / ...
~~~

**Native SQL qua JPA không phải là JDBC thuần.** EntityManager vẫn quản lý kết nối và transaction theo cấu hình persistence unit, cung cấp API query và có thể ánh xạ kết quả thành entity hoặc DTO. Nhưng vì SQL được viết bằng tay, **tính di động giữa DBMS giảm**, đặc biệt khi dùng cú pháp riêng như PostgreSQL JSONB, DISTINCT ON, INSERT ... ON CONFLICT hoặc SQL Server APPLY.

### 2.1. Không trộn tên entity với tên bảng

JPQL:

~~~jpql
select p
from Product p
where p.price >= :minimumPrice
~~~

Native SQL, giả định PostgreSQL:

~~~sql
select p.id, p.sku, p.name, p.price, p.status
from products p
where p.price >= ?
~~~

**Product** là tên entity; **products** là tên bảng. **p.price** trông giống nhau trong hai ngôn ngữ chỉ vì cách đặt tên trùng hợp. Nếu entity có **@Column(name = "unit_price")**, JPQL vẫn chọn **p.price**, còn SQL phải dùng **p.unit_price**.

## 3. Mô hình ví dụ

Giả sử hệ thống bán hàng có bảng **customers**, **orders** và **order_lines**. Một customer có nhiều order; một order có nhiều line.

~~~text
Customer                         PurchaseOrder
-------------------------------- --------------------------------------
id (PK)          <-------------  customer_id (FK)
name                            id (PK)
region                          order_number
                                placed_at
                                status
                                version
                                               |
                                               v
                                OrderLine
                                --------------------------------------
                                id (PK)
                                order_id (FK)
                                sku
                                quantity
                                line_amount
~~~

Schema PostgreSQL minh họa:

~~~sql
create table customers (
    id bigint generated by default as identity primary key,
    name varchar(150) not null,
    region varchar(60) not null
);

create table orders (
    id bigint generated by default as identity primary key,
    order_number varchar(50) not null unique,
    customer_id bigint not null references customers(id),
    placed_at timestamp with time zone not null,
    status varchar(20) not null,
    version bigint not null
);

create table order_lines (
    id bigint generated by default as identity primary key,
    order_id bigint not null references orders(id),
    sku varchar(50) not null,
    quantity integer not null check (quantity > 0),
    line_amount numeric(14, 2) not null
);

create index ix_orders_customer_date
    on orders (customer_id, placed_at desc, id desc);

create index ix_order_lines_order_id on order_lines(order_id);
~~~

Trong Java:

~~~java
package com.example.sales.model;

import jakarta.persistence.*;
import java.time.Instant;
import java.util.ArrayList;
import java.util.List;

@Entity
@Table(name = "orders")
public class PurchaseOrder {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "order_number", nullable = false)
    private String orderNumber;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "customer_id", nullable = false)
    private Customer customer;

    @Column(name = "placed_at", nullable = false)
    private Instant placedAt;

    @Enumerated(EnumType.STRING)
    @Column(name = "status", nullable = false)
    private OrderStatus status;

    @Version
    private long version;

    @OneToMany(mappedBy = "order")
    private List<OrderLine> lines = new ArrayList<>();

    protected PurchaseOrder() {}

    public Long getId() { return id; }
    public String getOrderNumber() { return orderNumber; }
    public Instant getPlacedAt() { return placedAt; }
    public OrderStatus getStatus() { return status; }
}
~~~

~~~java
package com.example.sales.model;

import jakarta.persistence.*;

@Entity
@Table(name = "customers")
public class Customer {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "name", nullable = false)
    private String name;

    @Column(name = "region", nullable = false)
    private String region;

    protected Customer() {}
    public Long getId() { return id; }
    public String getName() { return name; }
    public String getRegion() { return region; }
}
~~~

~~~java
package com.example.sales.model;

import jakarta.persistence.*;
import java.math.BigDecimal;

@Entity
@Table(name = "order_lines")
public class OrderLine {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "order_id", nullable = false)
    private PurchaseOrder order;

    @Column(name = "sku", nullable = false)
    private String sku;

    @Column(name = "quantity", nullable = false)
    private int quantity;

    @Column(name = "line_amount", nullable = false)
    private BigDecimal lineAmount;

    protected OrderLine() {}
}
~~~

~~~java
package com.example.sales.model;

public enum OrderStatus {
    DRAFT, PAID, CANCELLED
}
~~~

Các class dùng làm nền cho ví dụ truy vấn, không phải toàn bộ ứng dụng; constructor nghiệp vụ, validation, quyền truy cập và transaction service được bổ sung trong dự án thực tế. Với SQL native, tên bảng và cột ở DDL là **hợp đồng vật lý** mà câu truy vấn phụ thuộc.

## 4. Quy tắc ra quyết định: trước tiên thử JPQL

Một yêu cầu thường **không cần native SQL** nếu:

- Chỉ lấy entity theo ID, điều kiện field hoặc association.
- Cần JOIN giữa entity, lọc, sắp xếp, phân trang thông thường.
- Cần DTO constructor expression với những scalar có thể chọn bằng JPQL.
- Cần count/sum/avg hoặc GROUP BY đơn giản.
- Muốn tận dụng tính di động và tên property Java.
- Cần entity managed để sửa theo dirty checking, optimistic locking và cascade.
- Query có hiệu năng tốt sau khi chọn projection, fetch plan và index phù hợp.

Ví dụ báo cáo số order theo customer có thể viết JPQL:

~~~jpql
select new com.example.sales.dto.CustomerOrderCount(
    c.id, c.name, count(o)
)
from Customer c
left join c.orders o
group by c.id, c.name
~~~

Query này giả định Customer có mapping **@OneToMany(mappedBy="customer")** tên orders. Không cần SQL trực tiếp chỉ vì có JOIN và GROUP BY.

### 4.1. Dấu hiệu Native SQL có giá trị thực sự

Ngược lại, cân nhắc Native SQL khi:

1. **Ngữ nghĩa DBMS cần thiết nhưng JPQL chuẩn không biểu diễn đủ rõ**, ví dụ recursive hierarchy query, window function chuyên sâu, pivot, LATERAL join hoặc tập hợp từ JSON.
2. **Cần khai thác khả năng riêng của hệ quản trị**, như full-text search có ranking, PostGIS, JSONB, SQL Server temporal tables, optimizer hints hay toán tử đặc biệt.
3. **Đã đo được SQL provider sinh không phù hợp** với một hot path và có native query khác hiệu quả hơn mà vẫn giữ đúng kết quả.
4. **Có báo cáo nhiều tầng, aggregate phức tạp**, cần CTE, window, grouping sets hoặc cấu trúc khó viết bằng JPQL hiện có.
5. **Cần một thao tác DML theo lô hoặc upsert có tính nguyên tử của DBMS**, và chấp nhận tự quản lý khác biệt với JPA lifecycle.
6. **Cần tích hợp schema di sản**, view/materialized view hoặc một câu SQL có sẵn, đã được tối ưu và bảo trì bởi DBA.
7. **Yêu cầu đặc biệt về concurrency/locking**, ví dụ lấy task tiếp theo bằng cú pháp SKIP LOCKED được DB hỗ trợ.

Các khả năng JPQL/HQL thay đổi theo **phiên bản đặc tả và provider**. Có tính năng mà SQL cổ điển cần native nhưng Hibernate HQL phiên bản mới đã hỗ trợ phần nào. Vì vậy kết luận đúng là “**JPQL/provider hiện tại không đáp ứng phù hợp**”, không phải khẳng định mọi JPQL ở mọi phiên bản đều không làm được.

### 4.2. Bảng lựa chọn theo nhu cầu

| Nhu cầu | Lựa chọn ưu tiên | Khi nào chuyển sang Native SQL? |
|---|---|---|
| CRUD entity theo khóa | EntityManager / repository | Hầu như không cần |
| Danh sách có vài field | JPQL SELECT NEW DTO | Khi cần biểu thức/DB operator chưa hỗ trợ |
| JOIN quan hệ đơn giản | JPQL hoặc Criteria | Chỉ khi SQL thủ công đo tốt hơn rõ rệt |
| Thống kê count/sum/group by | JPQL | Khi cần CTE/window/rollup/pivot chuyên sâu |
| Tìm kiếm full-text | Tùy DB/search engine | Khi cần ranking/lexeme/index riêng DB |
| Truy vấn JSONB | Có thể dùng FUNCTION nếu phù hợp | Khi cần toán tử và index JSONB đặc thù |
| Báo cáo có nhiều cấp tổng hợp | JPQL nếu dễ diễn đạt | Native CTE/window khi hiệu quả hoặc rõ hơn |
| Cập nhật hàng loạt | JPQL bulk DML trước | Native UPDATE FROM, UPSERT, RETURNING... |
| Xử lý hàng đợi cạnh tranh | Transaction/locking API chuẩn nếu đủ | SKIP LOCKED, NOWAIT, RETURNING theo DB |
| SQL đã được DBA chuẩn hóa | JPQL nếu chuyển đổi hợp lý | Có thể giữ native để đúng execution plan |
| Thao tác SQL rất đặc biệt | JPA Native SQL/JDBC | JDBC hoặc jOOQ nếu truy vấn vượt khả năng JPA |

**Chi phí của Native SQL cần được tính cùng lợi ích**, không chỉ dựa trên số milliseconds của một lần chạy ở môi trường dev.

## 5. API Native SQL cơ bản của JPA

EntityManager có các API phổ biến:

~~~java
Query query = em.createNativeQuery(sql);
Query entityQuery = em.createNativeQuery(sql, PurchaseOrder.class);
Query mappedQuery = em.createNativeQuery(sql, "OrderSummaryMapping");
~~~

Trong đó:

- **createNativeQuery(String sql)**: thực thi SQL native, kết quả scalar hoặc mảng object khi SELECT nhiều cột, tùy metadata và JDBC/provider.
- **createNativeQuery(String sql, Class resultClass)**: cho phép ánh xạ result phù hợp với entity class hay dạng result class được provider hỗ trợ.
- **createNativeQuery(String sql, String resultSetMapping)**: dùng tên **@SqlResultSetMapping** đã khai báo để ánh xạ kết quả.
- **getResultList()**: lấy nhiều hàng.
- **getSingleResult()**: lấy một kết quả; xử lý trường hợp không có hoặc nhiều kết quả theo semantics JPA.
- **executeUpdate()**: chạy native DML phù hợp và trả số hàng bị ảnh hưởng khi có thể xác định.
- **setFirstResult()/setMaxResults()**: phân trang query, provider chuyển thành SQL theo dialect/capability.

### 5.1. Chọn một cột scalar

~~~java
Number count = (Number) em.createNativeQuery(
    "select count(*) from orders"
).getSingleResult();

long totalOrders = count.longValue();
~~~

Sử dụng **Number** thay vì ép trực tiếp thành Long là cách phòng thủ thực dụng với SQL native, vì kiểu Java JDBC trả về có thể là Long, BigInteger, BigDecimal hoặc kiểu số khác theo DBMS/provider. Với giá trị có thể quá lớn, cần kiểm tra overflow trước khi chuyển về long; **Number.longValue()** có thể mất thông tin nếu kết quả vượt miền biểu diễn.

Với JPQL **count(o)**, kết quả chuẩn là Long. **Đừng mặc định cùng quy tắc kiểu kết quả áp dụng cho mọi native SQL count(*)**.

### 5.2. Chọn nhiều cột scalar

~~~java
@SuppressWarnings("unchecked")
List<Object[]> rows = em.createNativeQuery(
    """
    select id, order_number, status
    from orders
    order by id
    """
).getResultList();

for (Object[] row : rows) {
    Number idNumber = (Number) row[0];
    String number = (String) row[1];
    String status = (String) row[2];

    Long id = idNumber.longValue();
    System.out.println(id + " " + number + " " + status);
}
~~~

Ví dụ dùng Java text blocks (Java 15+). Nếu chỉ SELECT đúng một cột, kết quả thường là danh sách các scalar chứ không phải Object[] một phần tử. Không viết code ép cứng Object[] cho mọi native query.

### 5.3. Param binding an toàn

Ví dụ với một tham số vị trí trong native SQL:

~~~java
Query q = em.createNativeQuery(
    "select id, order_number from orders where customer_id = ?"
);

q.setParameter(1, customerId);
List<?> rows = q.getResultList();
~~~

Điểm cần nhớ:

- Sử dụng **bind parameter**, không ghép trực tiếp dữ liệu của user vào SQL string.
- Khi cần tính portable cao cho native query, ưu tiên **positional parameters** theo cú pháp/provider được hỗ trợ; JPA không bảo đảm named parameters trong native SQL giống JPQL.
- Hỗ trợ placeholder và chi tiết binding (kể cả collection parameter, temporal types hoặc kiểu JSON) phụ thuộc provider/dialect.
- SQL identifier (tên bảng, cột, ORDER BY direction) **không thể thay thế bằng parameter bind thông thường**.

Ví dụ **không an toàn**:

~~~java
String sql =
    "select * from orders where order_number = '" +
    userInput + "'";
~~~

Đây là điểm mở ra SQL injection và còn có thể làm hỏng cú pháp với dấu nháy. Dùng bind values; riêng phần cấu trúc query động phải được whitelist.

### 5.4. Positional và named parameters: tính portable

JPQL chuẩn dùng **:name** hoặc **?1**. SQL native sử dụng cú pháp parameter do API JPA/provider xử lý và database có thể có toán tử đặc thù chứa dấu hỏi, ví dụ JSON trong PostgreSQL. Khi một provider hỗ trợ **:customerId** trong native SQL, đó là tiện ích đáng dùng trong project đã khóa provider, nhưng **không mặc định mọi JPA provider đều hỗ trợ cùng cách**.

Với các toán tử dùng dấu hỏi như PostgreSQL JSONB **?**, parser binding có thể nhận nhầm là placeholder. Có thể cần cú pháp thay thế như hàm DB tương đương, escape provider-specific hoặc một thư viện SQL có API bind riêng. Hãy kiểm thử câu SQL thật trên tổ hợp provider và dialect của dự án.

## 6. Khi cần ánh xạ kết quả thành managed entity

Một native query có thể trả về entity thay vì Object[]:

~~~java
List<PurchaseOrder> orders = em.createNativeQuery(
    """
    select o.*
    from orders o
    where o.status = ?
    order by o.placed_at desc, o.id desc
    """,
    PurchaseOrder.class
).setParameter(1, "PAID")
 .getResultList();
~~~

Ở đây **PurchaseOrder** là một entity đã ánh xạ tới bảng orders; provider dùng result set để dựng/truy xuất những entity tương ứng.

### 6.1. Entity result cần đủ dữ liệu ánh xạ

Nếu mapping của PurchaseOrder có **id**, **order_number**, **customer_id**, **placed_at**, **status** và **version**, hãy bảo đảm native SELECT trả các cột cần thiết để provider tạo một entity hợp lệ.

Ví dụ thiếu cột:

~~~sql
select id, order_number
from orders
~~~

không phải một result set đầy đủ cho entity PurchaseOrder có nhiều mapped columns. Provider có thể ném lỗi khi hydrate, hoặc đưa ra hành vi không portable. Đối với entity result, cách rõ ràng là chọn toàn bộ những cột được yêu cầu theo mapping, cùng column aliases phù hợp. **Không dùng native entity result như một cách ép partial entity mà vẫn mong nó hoạt động như fully managed entity.**

### 6.2. Tránh SELECT * khi JOIN nhiều bảng

Nếu:

~~~sql
select *
from orders o
join customers c on c.id = o.customer_id
~~~

result set có thể chứa hai cột tên **id**, nhiều cột trùng tên khác, khiến mapping dựa vào aliases bị mơ hồ. Với entity PurchaseOrder:

~~~sql
select o.*
from orders o
join customers c on c.id = o.customer_id
~~~

có thể giảm va chạm tên cột. Khi ánh xạ nhiều entities hoặc DTO phức tạp, đặt alias tường minh và dùng **@SqlResultSetMapping** khi cần.

### 6.3. Native entity result vẫn là entity managed

Nếu EntityManager đang mở và query trả PurchaseOrder dưới dạng entity:

~~~java
PurchaseOrder order = em.createNativeQuery(
    "select * from orders where id = ?",
    PurchaseOrder.class
).setParameter(1, orderId)
 .getSingleResult();
~~~

object **order** có thể được quản lý trong persistence context giống các entity được load bằng find/JPQL. Thay đổi trạng thái entity trong transaction hợp lệ có thể được dirty checking và flush. Native query **không tự biến entity thành DTO hoặc read-only snapshot**.

Điều này có hai hệ quả:

- Nếu ứng dụng chỉ cần số liệu báo cáo, một **scalar/DTO projection** thường thích hợp hơn tải managed entities hàng loạt.
- Nếu entity cùng ID đã được quản lý trong persistence context, query không nhất thiết overwrite mọi field của instance đó bằng dữ liệu DB mới; identity map và trạng thái managed vẫn có vai trò. Khi cần lấy lại dữ liệu từ DB, xem **refresh**, clear, hoặc lựa chọn projection phù hợp.

### 6.4. Kế thừa và discriminator

Nếu entity thuộc một hierarchy **SINGLE_TABLE/JOINED/TABLE_PER_CLASS**, native result có thể cần discriminator và những cột tương ứng để provider xác định subtype. Không mặc định **select base columns** là đủ để hydrate mọi subtype. Kiểm tra yêu cầu của JPA provider với strategy cụ thể.

Nếu báo cáo chỉ cần ID và status, scalar DTO dễ kiểm soát hơn ánh xạ cả một hierarchy entity qua SQL tùy chỉnh.

## 7. Ánh xạ Native SQL thành DTO bằng @SqlResultSetMapping

Phần lớn report native **không cần managed entity**. Khi cần kết quả có kiểu rõ, JPA cung cấp **@SqlResultSetMapping** và **@ConstructorResult**.

Định nghĩa DTO:

~~~java
package com.example.sales.dto;

import java.math.BigDecimal;
import java.time.Instant;

public record OrderListRow(
    Long id,
    String orderNumber,
    String customerName,
    Instant placedAt,
    BigDecimal totalAmount
) {}
~~~

Trong một entity thuộc persistence unit, khai báo mapping:

~~~java
import jakarta.persistence.ColumnResult;
import jakarta.persistence.ConstructorResult;
import jakarta.persistence.Entity;
import jakarta.persistence.SqlResultSetMapping;

@SqlResultSetMapping(
    name = "OrderListRowMapping",
    classes = @ConstructorResult(
        targetClass = com.example.sales.dto.OrderListRow.class,
        columns = {
            @ColumnResult(name = "order_id", type = Long.class),
            @ColumnResult(name = "order_no", type = String.class),
            @ColumnResult(name = "customer_name", type = String.class),
            @ColumnResult(name = "placed_at", type = java.time.Instant.class),
            @ColumnResult(name = "total_amount", type = java.math.BigDecimal.class)
        }
    )
)
@Entity
public class PurchaseOrder {
    // Các field JPA khác như mục 3.
}
~~~

Đây là **minh họa thêm annotation lên PurchaseOrder đã có**, không tạo thêm một entity trùng tên/package trong project thật. ConstructorResult có thể được khai báo tại class entity hoặc mapped superclass theo API/version phù hợp; mapping name phải duy nhất trong phạm vi persistence unit.

Query:

~~~java
String sql = """
    select
        o.id as order_id,
        o.order_number as order_no,
        c.name as customer_name,
        o.placed_at as placed_at,
        coalesce(sum(l.line_amount), 0) as total_amount
    from orders o
    join customers c on c.id = o.customer_id
    left join order_lines l on l.order_id = o.id
    group by o.id, o.order_number, c.name, o.placed_at
    order by o.placed_at desc, o.id desc
    """;

@SuppressWarnings("unchecked")
List<OrderListRow> result = em.createNativeQuery(
    sql, "OrderListRowMapping"
).getResultList();
~~~

**Cần đặc biệt chú ý kiểu timestamp:** JDBC driver và JPA provider có thể trả timestamp with time zone dưới dạng OffsetDateTime, Timestamp hoặc kiểu khác; việc yêu cầu Instant.class trong **@ColumnResult** không được mọi dialect/provider tự chuyển như nhau. Trong môi trường cần portability, có thể chọn một kiểu mà provider xác nhận hỗ trợ hoặc chuyển từ scalar/DTO trung gian. Không coi ví dụ type conversion này là hợp đồng chung cho mọi DBMS.

### 7.1. Vì sao alias phải khớp?

~~~sql
o.id as order_id,
o.order_number as order_no,
...
~~~

tương ứng:

~~~java
@ColumnResult(name = "order_id", type = Long.class)
@ColumnResult(name = "order_no", type = String.class)
~~~

Nếu đổi alias SQL nhưng không đổi @ColumnResult, provider không tìm đúng cột kết quả. Đổi thứ tự @ColumnResult cũng có thể làm constructor nhận sai dữ liệu, vì **constructor parameters được truyền theo thứ tự đã khai báo trong mapping**.

### 7.2. DTO constructor không phải entity lifecycle

Một **OrderListRow** được khởi tạo bởi ConstructorResult không tự trở thành managed entity. Thay đổi các property DTO (nếu là class mutable) không làm database được cập nhật qua dirty checking. Muốn sửa Order, load **PurchaseOrder managed** theo ID trong transaction rồi thực hiện nghiệp vụ.

### 7.3. @EntityResult và @FieldResult

JPA còn hỗ trợ **@EntityResult** để ánh xạ native result thành entity, và **@FieldResult** để xác định cột kết quả ứng với một property khi aliases phức tạp:

~~~java
@SqlResultSetMapping(
    name = "OrderEntityMapping",
    entities = @EntityResult(
        entityClass = PurchaseOrder.class,
        fields = {
            @FieldResult(name = "id", column = "order_id"),
            @FieldResult(name = "orderNumber", column = "order_no"),
            @FieldResult(name = "placedAt", column = "placed_at"),
            @FieldResult(name = "status", column = "status"),
            @FieldResult(name = "version", column = "version"),
            @FieldResult(name = "customer", column = "customer_id")
        }
    )
)
~~~

Ví dụ có ý định mô tả mapping aliases; ánh xạ association qua @FieldResult và mapping thừa kế có yêu cầu khác nhau giữa đặc tả/provider và trường hợp cụ thể, nên cần kiểm thử kết quả với metadata thực. Để giảm rủi ro, ưu tiên **entity mapping đơn giản với đầy đủ cột**, hoặc DTO/scalars cho report JOIN phức tạp.

### 7.4. NamedNativeQuery

SQL có thể được khai báo dưới dạng named query để tập trung định nghĩa:

~~~java
@NamedNativeQuery(
    name = "PurchaseOrder.findRecentPaid",
    query = """
        select o.*
        from orders o
        where o.status = 'PAID'
        order by o.placed_at desc, o.id desc
        """,
    resultClass = PurchaseOrder.class
)
@Entity
public class PurchaseOrder {
    // Mapping như mục 3.
}
~~~

và gọi:

~~~java
List<PurchaseOrder> orders = em.createNamedQuery(
    "PurchaseOrder.findRecentPaid",
    PurchaseOrder.class
).setMaxResults(50)
 .getResultList();
~~~

NamedNativeQuery hữu ích khi query dùng lại nhiều nơi hoặc cần khai báo mapping tập trung. Nó **không tự chuẩn hóa cú pháp SQL** để chạy trên nhiều DBMS.

## 8. Trường hợp 1: Recursive CTE để duyệt dữ liệu phân cấp

Một bảng category lưu cấu trúc cha–con:

~~~sql
create table categories_tree (
    id bigint primary key,
    parent_id bigint references categories_tree(id),
    name varchar(100) not null
);
~~~

Nhu cầu: lấy **toàn bộ descendants của một category**, bất kể cây sâu bao nhiêu cấp, kèm depth.

PostgreSQL hỗ trợ **WITH RECURSIVE**:

~~~sql
with recursive subtree as (
    select id, parent_id, name, 0 as depth
    from categories_tree
    where id = ?

    union all

    select child.id, child.parent_id, child.name,
           subtree.depth + 1
    from categories_tree child
    join subtree on child.parent_id = subtree.id
)
select id, name, depth
from subtree
order by depth, id;
~~~

Trong JPA:

~~~java
@SuppressWarnings("unchecked")
List<Object[]> rows = em.createNativeQuery(
    """
    with recursive subtree as (
        select id, parent_id, name, 0 as depth
        from categories_tree
        where id = ?

        union all

        select c.id, c.parent_id, c.name, s.depth + 1
        from categories_tree c
        join subtree s on c.parent_id = s.id
    )
    select id, name, depth
    from subtree
    order by depth, id
    """
).setParameter(1, rootId)
 .getResultList();
~~~

**Vì sao đáng cân nhắc Native SQL?** Ứng dụng có thể lấy toàn bộ subtree trong một câu SQL thay vì lặp qua nhiều cấp, mỗi cấp lại query DB. Những bản JPQL/provider không hỗ trợ recursive queries đầy đủ sẽ khó diễn đạt thuật toán tương đương.

### 8.1. Cẩn thận với chu trình

Nếu dữ liệu hỏng tạo chu trình A → B → C → A, truy vấn recursive UNION ALL có thể lặp vô hạn hoặc đạt giới hạn resource. Cần:

- Ràng buộc domain ngăn parent cycle ngay khi ghi.
- Có thể giới hạn depth khi phù hợp.
- Sử dụng cơ chế phát hiện cycle hoặc mảng path mà DBMS hỗ trợ.
- Giới hạn tài nguyên/query timeout và benchmark trên dữ liệu lớn.

Không copy recursive query vào production mà không xác định **điều kiện dừng**.

### 8.2. Trường hợp không nên dùng recursive CTE

Nếu Category chỉ có tối đa hai cấp và không cần truy vấn arbitrary depth, JPQL JOIN đơn giản hoặc một query ID danh mục theo schema cụ thể có thể dễ bảo trì hơn. Khả năng viết CTE không đồng nghĩa mọi truy vấn phân cấp đều cần CTE.

## 9. Trường hợp 2: Window function cho bảng xếp hạng

Nhu cầu: **lấy ba đơn hàng gần nhất của từng khách hàng**, không phải ba đơn hàng gần nhất của toàn hệ thống.

Nếu dùng:

~~~jpql
select o from PurchaseOrder o order by o.placedAt desc
~~~

rồi **setMaxResults(3)**, chỉ có ba Order của toàn tập, không phải ba Order cho mỗi Customer.

Trong PostgreSQL và nhiều DBMS hiện đại, dùng **ROW_NUMBER() OVER (PARTITION BY ... ORDER BY ...)**:

~~~sql
select *
from (
    select
        o.id,
        o.customer_id,
        o.order_number,
        o.placed_at,
        row_number() over (
            partition by o.customer_id
            order by o.placed_at desc, o.id desc
        ) as row_no
    from orders o
    where o.status = 'PAID'
) ranked
where ranked.row_no <= 3
order by ranked.customer_id, ranked.row_no;
~~~

Ý nghĩa:

- **PARTITION BY customer_id** chia thứ hạng theo khách hàng.
- **ORDER BY placed_at DESC, id DESC** xác định thứ tự mới nhất, dùng id làm khóa phụ khi cùng thời gian.
- **ROW_NUMBER()** đánh số từ 1 trong mỗi partition.
- Query ngoài lọc **row_no <= 3**.

Trong JPA:

~~~java
@SuppressWarnings("unchecked")
List<Object[]> rows = em.createNativeQuery(
    """
    select customer_id, id, order_number, placed_at, row_no
    from (
        select o.customer_id, o.id, o.order_number, o.placed_at,
               row_number() over (
                   partition by o.customer_id
                   order by o.placed_at desc, o.id desc
               ) as row_no
        from orders o
        where o.status = 'PAID'
    ) ranked
    where row_no <= ?
    order by customer_id, row_no
    """
).setParameter(1, limitPerCustomer)
 .getResultList();
~~~

**Khi cần native:** một số JPA provider hoặc phiên bản HQL có thể hỗ trợ window functions, nhưng nếu JPQL chuẩn hiện tại trong dự án không diễn đạt tốt yêu cầu hoặc SQL native đã được kiểm chứng, câu SQL trực tiếp là lựa chọn rõ ràng.

### 9.1. ROW_NUMBER, RANK và DENSE_RANK

| Hàm | Khi có hai hàng đồng hạng | Phù hợp |
|---|---|---|
| **ROW_NUMBER()** | Vẫn cho số thứ tự khác nhau | Top N hàng chính xác theo thứ tự ổn định |
| **RANK()** | Hai hàng cùng hạng; hạng sau có khoảng trống | Bảng xếp hạng cuộc thi có đồng hạng |
| **DENSE_RANK()** | Hai hàng cùng hạng; hạng sau liên tiếp | Tìm top N cấp độ giá trị |

Nếu yêu cầu top N **khách hàng theo tổng doanh thu**, cần tổng hợp doanh thu theo customer trước, rồi sử dụng RANK/ROW_NUMBER trên kết quả aggregate. Không dùng window function khi chỉ cần **order by ... limit** của toàn bảng.

### 9.2. Index hỗ trợ nhưng không thay thuật toán

Index trên **orders(customer_id, placed_at DESC, id DESC)** có thể hỗ trợ những kiểu truy cập và sort nhất định. Tuy vậy, window query vẫn có thể phải xử lý nhiều hàng trong từng partition. Hãy đo execution plan và số hàng thực, không cho rằng có index là query top N luôn O(N) nhỏ.

## 10. Trường hợp 3: Báo cáo nhiều bước với CTE

Giả sử cần **tổng doanh thu theo tháng và region**, rồi chỉ lấy các region đóng góp trên ngưỡng.

Một truy vấn PostgreSQL minh họa:

~~~sql
with paid_order_amount as (
    select
        o.id,
        c.region,
        date_trunc('month', o.placed_at) as month_start,
        sum(l.line_amount) as amount
    from orders o
    join customers c on c.id = o.customer_id
    join order_lines l on l.order_id = o.id
    where o.status = 'PAID'
    group by o.id, c.region, date_trunc('month', o.placed_at)
),
regional_monthly as (
    select region, month_start, sum(amount) as revenue
    from paid_order_amount
    group by region, month_start
)
select region, month_start, revenue
from regional_monthly
where revenue >= ?
order by month_start desc, revenue desc;
~~~

**Điểm quan trọng:** hai tầng CTE có ý nghĩa khi logic nghiệp vụ cần tách **amount per order** khỏi **aggregate per region/month**. Không nhất thiết mọi truy vấn SUM cần CTE; một GROUP BY đơn giản của JPQL cũng có thể đáp ứng nhiều báo cáo.

### 10.1. CTE làm SQL dễ đọc nhưng không luôn nhanh hơn

CTE là một công cụ cấu trúc query. Tùy PostgreSQL version, optimizer có thể inline hoặc materialize CTE theo điều kiện. Một CTE bị materialize không cần thiết có thể gây tốn bộ nhớ/IO. Hãy so sánh với query tương đương và đo:

~~~sql
explain (analyze, buffers)
with ...
select ...;
~~~

Trong môi trường production, không chạy EXPLAIN ANALYZE cho query nặng mà không có kiểm soát; bản thân câu SELECT sẽ thực thi.

### 10.2. Lựa chọn DTO cho báo cáo

Kết quả report có thể ánh xạ thành DTO:

~~~java
public record MonthlyRevenue(
    String region,
    java.time.LocalDate month,
    java.math.BigDecimal revenue
) {}
~~~

Trên PostgreSQL **date_trunc** trả timestamp/timestamptz, không nhất thiết map thẳng sang LocalDate. Nếu muốn LocalDate, có thể **cast sang date** trong SQL hoặc dùng type conversion được kiểm thử. Với native query, không tự giả định các JDBC driver trả cùng kiểu cho date/time.

Một DTO report thường hợp lý hơn EntityResult vì các hàng tổng hợp **không tương ứng một entity riêng có primary key**.

## 11. Trường hợp 4: JSON, tìm kiếm toàn văn và extension của DB

### 11.1. JSONB PostgreSQL

Giả sử bảng products có cột **attributes jsonb**:

~~~sql
create table products_json (
    id bigint primary key,
    name varchar(150) not null,
    attributes jsonb not null
);
~~~

Ví dụ attributes:

~~~json
{
  "color": "black",
  "switch": "red",
  "wireless": true
}
~~~

Truy vấn theo thuộc tính:

~~~sql
select id, name
from products_json
where attributes ->> 'color' = ?;
~~~

Hoặc dùng phép kiểm tra JSON containment:

~~~sql
select id, name
from products_json
where attributes @> cast(? as jsonb);
~~~

với parameter được bind là một chuỗi JSON hợp lệ như **{"wireless":true}**, không ghép trực tiếp input vào SQL.

Đây là trường hợp native có lợi khi ứng dụng cần tận dụng **toán tử JSONB, function và index GIN** riêng PostgreSQL. Nhưng nếu JPA provider đang dùng đã có mapping JSON và hỗ trợ truy vấn tương ứng qua function/JPQL extension, nên so sánh khả năng bảo trì trước khi chọn native.

Ví dụ index:

~~~sql
create index ix_products_json_attrs
on products_json using gin (attributes);
~~~

**Không có nghĩa mọi điều kiện JSONB sẽ dùng index GIN này.** Với điều kiện **attributes ->> 'color' = ?**, có thể cần expression index thích hợp; với containment **@>**, GIN thường có khả năng hỗ trợ tùy operator class và phân bố dữ liệu.

### 11.2. Full-text search với ranking

Ví dụ PostgreSQL:

~~~sql
select
    p.id,
    p.name,
    ts_rank(
        to_tsvector('simple', p.name),
        plainto_tsquery('simple', ?)
    ) as rank_score
from products_json p
where to_tsvector('simple', p.name)
      @@ plainto_tsquery('simple', ?)
order by rank_score desc, p.id;
~~~

Đây là một **use case khác với LIKE '%keyword%'**:

- Tìm từ/ngữ nghĩa lexeme theo cấu hình tokenizer.
- Có thể xếp hạng relevance.
- Có thể tận dụng index tương ứng trên tsvector.
- Có cú pháp và chiến lược riêng của DBMS.

Trong ví dụ dùng **hai dấu ?**, đặt cùng searchTerm ở parameter 1 và 2. **Không nối searchTerm trực tiếp vào chuỗi SQL**.

Lưu ý cấu hình **'simple'** không phải tokenizer tốt cho mọi ngôn ngữ, đặc biệt nội dung tiếng Việt; cần kiểm tra yêu cầu tìm kiếm, normalization, accents và công cụ search phù hợp. Với nhu cầu search lớn, một search engine chuyên dụng đôi khi phù hợp hơn SQL native.

### 11.3. Geospatial/PostGIS

Một hệ thống có tọa độ và vùng địa lý có thể cần PostGIS:

~~~sql
select store_id
from stores
where ST_DWithin(
    geography(location),
    ST_SetSRID(ST_MakePoint(?, ?), 4326)::geography,
    ?
);
~~~

Ví dụ là cú pháp đặc thù PostGIS; thứ tự kinh độ/vĩ độ, SRID, kiểu geography/geometry, đơn vị khoảng cách và spatial index phải được xác định đúng trong thiết kế thật.

**Khi SQL native hợp lý:** khi muốn dùng hàm và kiểu dữ liệu địa lý mà JPQL/provider không diễn đạt tiện hoặc portable. Tuy nhiên, nếu Hibernate Spatial hoặc thư viện ORM đang dùng hỗ trợ những hàm đó an toàn, có thể không cần tự viết native query.

## 12. Trường hợp 5: UPDATE, DELETE và UPSERT hàng loạt

JPA cho phép JPQL bulk UPDATE/DELETE:

~~~jpql
update PurchaseOrder o
set o.status = :newStatus
where o.status = :oldStatus
~~~

Vì vậy **bulk DML đơn giản không phải lý do bắt buộc dùng SQL native**. Native DML trở nên hữu ích nếu cần:

- **UPDATE ... FROM** với JOIN tới một bảng tổng hợp hoặc staging table.
- **INSERT ... SELECT** chuyển nhiều hàng giữa bảng.
- **UPSERT** theo unique key bằng cú pháp riêng DBMS.
- **RETURNING** để lấy giá trị đã thay đổi trong một statement, nếu provider/API xử lý phù hợp.
- **MERGE** theo semantics DBMS.
- Các hint, partition hoặc thao tác nạp dữ liệu đặc thù.

### 12.1. UPDATE ... FROM PostgreSQL

Ví dụ cần cập nhật trạng thái order dựa trên bảng import đã được xác nhận:

~~~sql
update orders o
set status = 'CANCELLED'
from cancellation_requests r
where r.order_id = o.id
  and r.approved = true
  and o.status = 'DRAFT';
~~~

Với JPA:

~~~java
int updated = em.createNativeQuery(
    """
    update orders o
    set status = 'CANCELLED'
    from cancellation_requests r
    where r.order_id = o.id
      and r.approved = true
      and o.status = 'DRAFT'
    """
).executeUpdate();
~~~

**Cần transaction đang hoạt động.** Trong RESOURCE_LOCAL có thể dùng EntityTransaction; trong JTA/Spring dùng transaction manager phù hợp. Không sử dụng native UPDATE như một phép “chỉ đọc”.

**Quan trọng:** câu native SQL trên không tự cập nhật **@Version** của các PurchaseOrder đã thay đổi và không gọi các entity lifecycle callback như @PreUpdate/@PostUpdate cho từng hàng. Nếu model dùng optimistic locking, query bulk phải chủ động xử lý version/condition hoặc được kiểm soát để tránh phá vỡ invariant.

### 12.2. UPSERT với PostgreSQL ON CONFLICT

Một bảng tổng hợp doanh thu có unique key:

~~~sql
create table customer_month_totals (
    customer_id bigint not null,
    month_start date not null,
    amount numeric(14,2) not null,
    primary key (customer_id, month_start)
);
~~~

Native SQL:

~~~sql
insert into customer_month_totals (
    customer_id, month_start, amount
)
values (?, ?, ?)
on conflict (customer_id, month_start)
do update set amount = excluded.amount;
~~~

Ứng dụng có thể gửi statement này trong transaction thông qua createNativeQuery(...).executeUpdate(). Câu lệnh có đặc tính “**insert hoặc update theo conflict key**” dưới một statement được database phối hợp về concurrency.

Nhưng phải phân biệt:

- **ON CONFLICT** là cú pháp PostgreSQL, không phải JPQL chuẩn.
- **MySQL** có ON DUPLICATE KEY UPDATE với semantics khác.
- **SQL Server/Oracle** có MERGE hoặc phương án riêng; behavior dưới concurrency cần kiểm chứng.
- Nếu nghiệp vụ là “cộng dồn amount” thay vì “ghi đè amount”, công thức DO UPDATE phải thay đổi và tính idempotency phù hợp.
- Việc nhận giá trị RETURNING qua JPA có thể phụ thuộc phương thức query và provider; không mặc định executeUpdate() luôn trả result set.

### 12.3. INSERT ... SELECT

Ví dụ chép dữ liệu đã hoàn tất từ staging sang bảng chính:

~~~sql
insert into archived_orders (order_id, order_number, archived_at)
select o.id, o.order_number, current_timestamp
from orders o
where o.status = 'CANCELLED'
  and o.placed_at < ?;
~~~

Native SQL hữu ích nếu cần **chuyển hàng loạt dữ liệu trong DB** mà không materialize từng entity trong JVM. Tuy nhiên cần xét trùng khóa, retry/idempotency, trigger, audit và ranh giới transaction.

### 12.4. Không lạm dụng bulk UPDATE khi domain có lifecycle

Nếu khi hủy Order ứng dụng cần:

- Kiểm tra quyền truy cập và trạng thái từng Order.
- Gọi domain method cancel() với invariants.
- Phát domain event/transactional outbox.
- Tăng version.
- Cascade tới dependent entities.

thì một native UPDATE tất cả hàng **không thay thế đầy đủ** quy trình JPA managed entity. Có thể dùng Native SQL trong một quy trình migration/batch được phê duyệt, nhưng phải thiết kế các hệ quả riêng thay vì bỏ qua chúng.

## 13. Trường hợp 6: lấy công việc bằng SKIP LOCKED

Một hệ thống có bảng background_jobs:

~~~sql
create table background_jobs (
    id bigint primary key,
    status varchar(20) not null,
    priority integer not null,
    available_at timestamp with time zone not null
);
~~~

Nhiều worker đồng thời muốn nhận job chưa xử lý. Nếu mọi worker SELECT cùng hàng rồi mới UPDATE, có thể xảy ra race condition.

PostgreSQL hỗ trợ:

~~~sql
select id
from background_jobs
where status = 'READY'
  and available_at <= current_timestamp
order by priority desc, id
for update skip locked
limit 10;
~~~

**FOR UPDATE SKIP LOCKED** có thể bỏ qua các hàng đang được transaction khác khóa, giúp nhiều worker lấy các nhóm hàng khác nhau mà ít chờ hơn.

### 13.1. Những điều kiện để đúng

- SELECT cần chạy trong transaction thật; lock chỉ hữu ích nếu được giữ qua bước đánh dấu nhận việc.
- Worker phải cập nhật job thành **CLAIMED/RUNNING** hoặc trạng thái phù hợp trước commit.
- Phải xử lý crash/retry/timeout và idempotency; job có thể được chạy lại do failure.
- SKIP LOCKED có semantics khác nhau giữa DBMS và có thể dẫn tới **starvation** của một số job.
- Không dùng query này như bảng xếp hạng nhất quán tuyệt đối vì tập hàng trả về cố ý bỏ qua những hàng bị lock.

### 13.2. Vì sao Native SQL?

JPA cung cấp lock modes như **PESSIMISTIC_WRITE** và timeout hints, nhưng khả năng thể hiện đúng **SKIP LOCKED + LIMIT + ORDER BY** theo DBMS/provider không luôn portable. Nếu hệ thống cần semantics DB cụ thể, một native query kiểm chứng được có thể rõ ràng hơn.

Nếu ứng dụng chỉ cần khóa một entity theo ID, **EntityManager.lock()** hoặc **find(..., LockModeType.PESSIMISTIC_WRITE)** thường đủ; không cần native SQL chỉ vì có concurrency.

## 14. Trường hợp 7: view, materialized view và schema legacy

Giả sử một hệ thống đã có view báo cáo:

~~~sql
create view sales_order_summary as
select
    o.id as order_id,
    o.order_number,
    c.region,
    coalesce(sum(l.line_amount), 0) as total_amount
from orders o
join customers c on c.id = o.customer_id
left join order_lines l on l.order_id = o.id
group by o.id, o.order_number, c.region;
~~~

Native SQL có thể:

~~~java
List<?> summaries = em.createNativeQuery(
    """
    select order_id, order_number, region, total_amount
    from sales_order_summary
    where region = ?
    order by order_id
    """
).setParameter(1, region)
 .getResultList();
~~~

Khi view có **khóa duy nhất ổn định** và semantics phù hợp, một số ứng dụng ánh xạ read-only entity lên view. Nhưng:

- JPA @Entity vẫn yêu cầu identity phù hợp, không dùng row_number thay đổi giữa các lần chạy như khóa nếu muốn entity identity ổn định.
- View tổng hợp có thể không cập nhật được; không nên thử persist/merge/remove như với bảng writable thông thường.
- Materialized view có thể có độ trễ refresh, nên dữ liệu không nhất thiết real-time.
- Quyền SELECT và plan trên view có thể khác query trực tiếp, tùy DBMS.

### 14.1. Khi nào dùng repository native SQL cho legacy?

Nếu schema di sản có tên cột đặc biệt, stored function hoặc chuỗi JOIN đã được DBA duy trì, đôi khi native SQL giúp tích hợp nhanh mà không buộc phải tạo một entity graph phức tạp. Nhưng không nên biến mọi truy vấn legacy thành chuỗi SQL lặp trong nhiều service. Hãy gom chúng trong repository/DAO có tên nghiệp vụ và kiểm thử contract riêng.

### 14.2. Stored procedure là lựa chọn khác

Nếu logic nằm trong stored procedure, JPA có API **createStoredProcedureQuery()**:

~~~java
StoredProcedureQuery proc =
    em.createStoredProcedureQuery("recalculate_monthly_sales");
~~~

Việc đăng ký tham số IN/OUT, REF_CURSOR và cách nhận result phụ thuộc procedure và DBMS. Không nhất thiết gọi **createNativeQuery("CALL ...")** cho mọi stored procedure; dùng API dành riêng khi nó hỗ trợ đúng use case.

## 15. Tại sao Native SQL không phải lựa chọn mặc định?

### 15.1. Giảm tính di động giữa database

| Cú pháp hoặc chức năng | Ví dụ DBMS | Rủi ro khi chuyển DB |
|---|---|---|
| **ON CONFLICT DO UPDATE** | PostgreSQL | Cần viết lại cho MySQL/Oracle/SQL Server |
| **DISTINCT ON** | PostgreSQL | Không portable như SELECT DISTINCT chuẩn |
| **JSONB @>** | PostgreSQL | Kiểu dữ liệu/toán tử khác ở DB khác |
| **ILIKE** | PostgreSQL | Phải thay đổi cách so khớp case-insensitive |
| **TOP** | SQL Server | Khác LIMIT/FETCH |
| **CONNECT BY** | Oracle | Khác WITH RECURSIVE |
| **SKIP LOCKED** | Có trên nhiều DB | Cú pháp và semantics chi tiết khác |
| **Optimizer hint** | Oracle/MySQL/SQL Server/... | Tính năng và hiệu lực phụ thuộc optimizer |

Ngay cả cú pháp trông tương tự nhau như **LIMIT/OFFSET**, **boolean**, **timestamp**, **upsert** và **quoted identifier** cũng có khác biệt giữa DBMS/dialect.

Nếu ứng dụng có yêu cầu bắt buộc chạy trên nhiều DBMS, cần xem:

- JPQL/Criteria có thể diễn đạt yêu cầu không?
- Có thể dùng FUNCTION portable/extension với dialected implementations không?
- Có đáng tạo một interface repository và nhiều SQL implementations theo dialect không?
- Chi phí kiểm thử chéo DBMS có chấp nhận được không?

### 15.2. Phụ thuộc tên bảng/cột vật lý

Nếu rename **orders.order_number** thành **orders.external_ref**, Native SQL dùng order_number phải được cập nhật. Với JPQL, có thể giữ tên Java **orderNumber** và chỉ đổi **@Column(name=...)**, nên các JPQL dựa trên property đó ít bị ảnh hưởng hơn.

Schema migration và code deploy phải được phối hợp, đặc biệt khi nhiều phiên bản ứng dụng chạy song song. Một native query cũ có thể thất bại ngay sau DDL rename.

### 15.3. Dễ bỏ qua entity lifecycle

Một Native SQL:

~~~sql
delete from orders where id = ?;
~~~

không giống:

~~~java
PurchaseOrder order = em.find(PurchaseOrder.class, id);
em.remove(order);
~~~

Native DELETE không tự thực hiện **CascadeType.REMOVE**, **orphanRemoval**, entity callbacks, Bean Validation hay optimistic-locking semantics giống xóa managed entity thông thường. DB constraints vẫn áp dụng, nhưng DB không biết mọi invariant Java.

Nếu cần xóa hàng loạt qua SQL, phải xác định cách xử lý các dependent tables, version, audit và cache. Không tắt constraint chỉ để statement chạy thành công.

### 15.4. Mã khó bảo trì nếu phân tán

Một anti-pattern là viết cùng một truy vấn 300 dòng rải rác ở controller, service, scheduled job và repository. Khi schema thay đổi, đội phát triển không biết có bao nhiêu bản cần sửa.

Ưu tiên:

~~~text
Controller
    |
    v
Application service
    |
    v
ReportingRepository
    |
    +-- Native SQL định nghĩa tập trung
    +-- DTO mapping tập trung
    +-- Integration tests theo report
~~~

Tách câu SQL theo use case, đặt tên method theo nghiệp vụ, lưu query trong một vị trí có thể kiểm soát và test. **Không nhất thiết giấu mọi SQL vào một abstraction phức tạp**, nhưng tránh để application layer phụ thuộc trực tiếp vào từng cột schema.

## 16. Flush, transaction và consistency khi kết hợp JPA + Native SQL

Native SQL đi qua EntityManager vẫn có thể chạy trong cùng transaction database của JPA, nhưng **không mặc định nó thấy tất cả thay đổi Java chưa được flush**.

### 16.1. Pending changes trong persistence context

Giả sử trong transaction:

~~~java
PurchaseOrder managed = em.find(PurchaseOrder.class, orderId);
managed.changeStatus(OrderStatus.PAID); // Giả định method nghiệp vụ.

Object count = em.createNativeQuery(
    "select count(*) from orders where status = 'PAID'"
).getSingleResult();
~~~

Provider có thể chưa phát UPDATE trước native SELECT, tùy flush mode, JPA API, khả năng nhận biết bảng truy vấn và implementation. Khi native query **phụ thuộc trực tiếp vào pending state**, một cách diễn đạt rõ là:

~~~java
managed.changeStatus(OrderStatus.PAID);
em.flush();

Number count = (Number) em.createNativeQuery(
    "select count(*) from orders where status = 'PAID'"
).getSingleResult();
~~~

**em.flush() không commit transaction**. Nó đồng bộ SQL thích hợp vào DB trong transaction hiện tại. Nếu transaction sau đó rollback, DML chưa commit được hoàn tác theo ngữ nghĩa DB.

### 16.2. Native SQL DML làm managed entities bị stale

Nếu ProductOrder #100 đã được load:

~~~java
PurchaseOrder order = em.find(PurchaseOrder.class, orderId);
~~~

rồi ứng dụng chạy:

~~~java
em.createNativeQuery(
    "update orders set status = 'CANCELLED' where id = ?"
).setParameter(1, orderId)
 .executeUpdate();
~~~

object **order** trong persistence context có thể vẫn mang **status cũ**. Provider không tự cập nhật mọi managed object chỉ vì một câu SQL thủ công vừa ghi vào bảng tương ứng.

Các lựa chọn:

- **em.refresh(order)** sau native DML để đọc lại dữ liệu DB nếu mapping và transaction cho phép.
- **em.clear()** để detach toàn bộ context rồi load lại khi cần; cẩn thận vì các thay đổi chưa flush sẽ không được tự bảo toàn.
- Tách một transaction/batch chỉ dùng native SQL và tránh giữ managed entities của những hàng bị thay đổi.
- Thiết kế query trực tiếp có version predicate và tăng version đúng nếu đang áp dụng optimistic locking.

**Đừng dùng clear() vô điều kiện sau native DML** nếu trong context còn thay đổi quan trọng chưa flush. Cần quyết định thứ tự explicit flush → native SQL → refresh/clear.

### 16.3. Một transaction không đồng nghĩa một EntityManager context

Trong ứng dụng JTA, hai EntityManager hoặc một JDBC connection riêng có thể tham gia transaction khác nhau nếu cấu hình không đúng. Một native query trên connection không enlisted vào cùng JTA transaction có thể không thấy các DML chưa commit do isolation.

Kiểm tra:

1. Native SQL có chạy qua **cùng EntityManager/transaction manager** với các thay đổi entity không?
2. Context có joined JTA nếu dùng **UNSYNCHRONIZED** không?
3. Có flush những thay đổi cần thiết không?
4. JDBC connection/datasource có enlisted vào đúng transaction không?
5. Isolation level là READ COMMITTED, REPEATABLE READ hay chế độ khác?

Flush không phải cách “công bố dữ liệu” cho mọi connection. Transaction khác thường không được thấy dữ liệu chưa commit trong READ COMMITTED.

### 16.4. TransactionRequiredException khi ghi

Native INSERT/UPDATE/DELETE phải được thực thi trong transaction phù hợp. Nếu ứng dụng gọi **executeUpdate()** cho thao tác ghi trong điều kiện không có transaction cần thiết, JPA có thể ném **TransactionRequiredException**.

Với RESOURCE_LOCAL:

~~~java
EntityTransaction tx = em.getTransaction();
try {
    tx.begin();
    int count = em.createNativeQuery(
        "update orders set status = 'CANCELLED' where status = 'DRAFT'"
    ).executeUpdate();
    tx.commit();
} catch (RuntimeException ex) {
    if (tx.isActive()) {
        tx.rollback();
    }
    throw ex;
}
~~~

Với JTA/Spring, để container hoặc framework quản lý begin/commit/rollback; không gọi em.getTransaction() trên một JTA EntityManager.

### 16.5. Lock được giữ sau SQL trước commit

Một UPDATE native phát trong transaction có thể lấy row lock rồi giữ đến commit. Nếu transaction còn gọi API mạng hoặc xử lý lâu, những transaction khác có thể chờ. Nên giữ transaction ngắn, xác định lượng row bị ghi, có điều kiện WHERE chọn lọc và kiểm tra transaction timeout/deadlock strategy.

## 17. Bảo toàn optimistic locking khi dùng native DML

Entity có **@Version**:

~~~java
@Version
private long version;
~~~

Khi cập nhật managed entity, provider có thể sinh SQL với điều kiện **version hiện tại** và tăng version phù hợp. Nhưng native SQL:

~~~sql
update orders set status = 'PAID' where id = ?;
~~~

thường **không tự giữ optimistic locking semantics** của JPA.

Một câu SQL có kiểm tra version thủ công:

~~~sql
update orders
set status = ?, version = version + 1
where id = ? and version = ?;
~~~

Trong Java:

~~~java
int updated = em.createNativeQuery(
    """
    update orders
    set status = ?, version = version + 1
    where id = ? and version = ?
    """
).setParameter(1, newStatus.name())
 .setParameter(2, orderId)
 .setParameter(3, expectedVersion)
 .executeUpdate();

if (updated != 1) {
    throw new IllegalStateException(
        "Order missing or version conflict"
    );
}
~~~

Đây là chiến lược **compare-and-set** theo version, không phải bản sao tự động đầy đủ của locking JPA. Vẫn cần xem:

- Có trigger hoặc các bảng phụ cần cập nhật không?
- Có cần phân biệt “not found” với “version conflict” không?
- Có managed entity nào của cùng order trong context đang stale không?
- Có cần @PreUpdate callbacks, audit hoặc domain events không?
- Có phiên bản version type khác long/integer không?
- Có đồng bộ second-level cache hoặc invalidation phù hợp không?

Khi logic cập nhật một entity phức tạp và phụ thuộc callbacks/cascade, **ưu tiên dùng managed entity** thay vì cố mô phỏng toàn bộ lifecycle bằng SQL thủ công.

## 18. SQL injection và an toàn khi cho phép lọc/sắp xếp động

Đây là rủi ro đặc biệt quan trọng khi viết SQL native bằng chuỗi Java.

### 18.1. Bind value, không nối input

Không làm:

~~~java
String sql = "select * from orders where order_number = '" +
             requestedNumber + "'";
~~~

Thay bằng:

~~~java
List<?> rows = em.createNativeQuery(
    "select id, order_number from orders where order_number = ?"
).setParameter(1, requestedNumber)
 .getResultList();
~~~

Bind parameters cho **giá trị**, bao gồm ID, trạng thái, ngày tháng, chuỗi tìm kiếm và ngưỡng số. Đừng tự escape dấu nháy rồi tin rằng đó là cơ chế an toàn đầy đủ.

### 18.2. ORDER BY là identifier, không phải value

Sai:

~~~java
String sql =
    "select id, order_number from orders order by " +
    clientSort;
~~~

Không thể đơn giản thay tên cột bằng:

~~~sql
order by ?
~~~

vì placeholder biểu thị **giá trị** được bind chứ không phải tên cột SQL. Hãy dùng allowlist:

~~~java
String sortColumn = switch (requestedSortField) {
    case "date" -> "placed_at";
    case "number" -> "order_number";
    default -> "id";
};

String sortDirection =
    "desc".equalsIgnoreCase(requestedDirection)
        ? "DESC" : "ASC";

String sql = "select id, order_number from orders " +
             "order by " + sortColumn + " " + sortDirection + ", id ASC";
~~~

Ở đây mọi SQL identifier được lấy từ **hằng số do developer kiểm soát**, không từ chuỗi tự do của client. Với ứng dụng đa tenant dùng schema/table động, không nhét tenant name vào SQL identifier trực tiếp; ưu tiên cấu hình multi-tenancy được kiểm soát hoặc whitelist/mapping chặt chẽ.

### 18.3. Tham số danh sách IN

Một số provider hỗ trợ bind **Collection** trong native SQL cho IN (:ids), nhưng đó không nhất thiết là cơ chế portable của JPA:

~~~sql
where id in (?)
~~~

Một placeholder JDBC đại diện **một parameter**, không mặc định là danh sách SQL nhiều phần tử. Nếu cần query IDs động:

- Dùng JPQL **IN :ids** khi truy vấn tương đương không cần native.
- Dùng API mở rộng của provider có hỗ trợ collection native parameters.
- Tạo đúng số placeholders bằng một **query builder có kiểm soát** và bind từng value.
- Dùng **array parameter / ANY / temporary table** khi DB và driver hỗ trợ.

Đặc biệt, danh sách rỗng cần xử lý riêng; **IN ()** có thể là SQL không hợp lệ. Với nhiều nghìn ID, một giant IN clause cũng có thể ảnh hưởng plan và giới hạn tham số DB.

### 18.4. Quyền truy cập dữ liệu không tự có nhờ query DTO

Một query trả **chỉ ID và số tiền** vẫn có thể vi phạm bảo mật nếu thiếu điều kiện tenant/user:

~~~sql
select id, order_number
from orders
where customer_id = ?;
~~~

Service phải xác định customerId thuộc phạm vi người dùng hiện tại hoặc ràng buộc thêm tenant/organization theo domain. Không xem việc trả ít cột là một cơ chế authorization.

### 18.5. Native SQL và SQL logging

Không ghi đầy đủ parameter nhạy cảm vào application log khi debug. Query có thể chứa thông tin cá nhân, mã token, giá trị tài chính hoặc dữ liệu nội bộ. Hãy dùng logging phù hợp cho môi trường và che thông tin theo chính sách.

## 19. Hiệu năng: khi nào Native SQL thực sự đáng giá?

Việc dùng SQL trực tiếp được biện minh tốt nhất bằng **một nhu cầu có thể đo được**, không phải cảm giác rằng “SQL tay chắc chắn nhanh hơn ORM”.

### 19.1. Benchmark hai truy vấn cùng ngữ nghĩa

Giả sử yêu cầu là lấy 50 đơn hàng mới nhất, có ID, số đơn, tên khách và tổng tiền. Nếu so sánh:

**Phiên bản A:**

~~~java
List<PurchaseOrder> orders = em.createQuery(
    "select o from PurchaseOrder o",
    PurchaseOrder.class
).getResultList();

// Sau đó truy cập customer và lines trong vòng lặp.
~~~

với **phiên bản B**:

~~~sql
select ...
from orders o
join customers c ...
left join order_lines l ...
group by ...
order by ...
limit 50;
~~~

thì B có thể nhanh hơn rất nhiều. Nhưng phép đo này **chưa chứng minh Native SQL tốt hơn JPQL**, vì A đang tải entity và có thể tạo N+1, không chọn lọc số cột hoặc phân trang.

Một phép so sánh công bằng cần có **phiên bản JPQL DTO/aggregate với kết quả tương đương**, có fetch plan và pagination hợp lý, rồi đo với native SQL tối ưu. Đôi khi JPQL mới là đủ, không cần giảm portability.

### 19.2. Các chỉ số nên thu thập

| Chỉ số | Ý nghĩa |
|---|---|
| **Latency p50/p95/p99** | Tốc độ phổ biến và các request chậm |
| **Số câu SQL** | Truy vấn gốc hay có N+1? |
| **Rows scanned / returned** | DB có đọc nhiều hàng hơn số trả về không? |
| **Buffers / physical reads** | I/O thực tế, cache hit và trang dữ liệu |
| **Sort/hash memory** | Query có tràn bộ nhớ tạm ra disk không? |
| **CPU DB** | Window/aggregation/function có quá tốn CPU không? |
| **Network bytes** | Truyền bao nhiêu dữ liệu giữa DB và ứng dụng? |
| **Entity/DTO allocations** | Heap, GC và chi phí materialization |
| **Lock waits** | Transaction có chờ khóa hoặc deadlock không? |
| **Write throughput** | Với UPDATE/UPSERT hàng loạt, số rows/s |
| **Plan stability** | Dữ liệu/parameter khác nhau có làm plan thay đổi mạnh? |

Đặc biệt, query báo cáo có thể chạy nhanh trên dữ liệu thử rất nhỏ nhưng chậm khi table lên hàng chục triệu rows. Cần dữ liệu có phân bố representative: customer lớn/nhỏ, order lines nhiều/ít, thời gian, trạng thái, region và giá trị NULL.

### 19.3. EXPLAIN / EXPLAIN ANALYZE

PostgreSQL:

~~~sql
explain (analyze, buffers)
select o.id, o.order_number
from orders o
where o.status = 'PAID'
order by o.placed_at desc, o.id desc
limit 50;
~~~

Quan sát:

- **Index Scan / Bitmap Scan / Sequential Scan:** DB chọn đường truy cập nào.
- **Rows (estimated vs actual):** optimizer có dự đoán đúng số hàng không.
- **Sort / WindowAgg / HashAggregate:** thao tác nào chiếm thời gian.
- **Nested Loop / Hash Join / Merge Join:** loại JOIN có hợp với cardinality không.
- **Buffers:** đã đọc/đụng bao nhiêu page.
- **Execution time:** thời gian server thực thi, không bao gồm toàn bộ chi phí mapping/HTTP của ứng dụng.

Không có toán tử nào luôn xấu. Ví dụ sequential scan là hợp lý khi cần phần lớn bảng, còn nested loop có thể rất hiệu quả khi chỉ lấy vài hàng bằng index.

**EXPLAIN ANALYZE có thực thi query**. Với UPDATE/DELETE, lệnh giải thích có thể thực sự thay đổi dữ liệu; dùng staging hoặc transaction rollback theo cơ chế DB và có kế hoạch bảo vệ dữ liệu.

### 19.4. Index phù hợp trước khi thay ngôn ngữ truy vấn

Nếu JPQL sinh SQL:

~~~sql
select ...
from orders
where customer_id = ?
order by placed_at desc, id desc
limit 20;
~~~

thì index **(customer_id, placed_at DESC, id DESC)** có thể giúp rõ rệt. Đổi SELECT đó sang native SQL mà không có index có thể không cải thiện gì.

Tương tự, với JSONB hoặc full-text, lợi ích thường đến từ **operator + index specialized**, không chỉ từ chữ Native SQL. Một câu query native dùng phép toán không có index thích hợp vẫn có thể quét cả bảng.

### 19.5. Cần chú ý caching và flush

Entity query có thể hưởng lợi từ persistence context và second-level cache tùy mapping/provider. DTO query có thể không được cache theo entity identity. Native query cũng có thể khiến provider phải đồng bộ pending changes trước SELECT hoặc chạy query trực tiếp; tùy API/provider mà flush behavior khác.

Khi đo, hãy ghi rõ:

- Query chạy lần đầu hay lặp lại trong cùng EntityManager?
- Có transaction đọc/ghi và pending changes không?
- Cache DB đang ấm hay lạnh?
- Có query cache hay second-level cache riêng?
- Native DML có cần clear/refresh và chi phí đó đã tính chưa?

Không so sánh một query đã cache với một query chưa cache rồi kết luận cú pháp SQL là nguyên nhân.

## 20. Lựa chọn kiến trúc: Native SQL trong repository

Một codebase ổn định thường che chi tiết SQL cụ thể sau một interface có ngữ nghĩa nghiệp vụ.

~~~java
package com.example.sales.repository;

import com.example.sales.dto.OrderListRow;
import java.time.Instant;
import java.util.List;

public interface SalesReportRepository {
    List<OrderListRow> findRecentOrders(
        Instant from,
        Instant to,
        int limit
    );
}
~~~

Implementation dùng EntityManager:

~~~java
package com.example.sales.repository;

import jakarta.persistence.EntityManager;
import jakarta.persistence.PersistenceContext;
import java.time.Instant;
import java.util.List;

public class NativeSalesReportRepository
        implements SalesReportRepository {

    @PersistenceContext
    private EntityManager em;

    @Override
    @SuppressWarnings("unchecked")
    public List<OrderListRow> findRecentOrders(
        Instant from, Instant to, int limit
    ) {
        if (limit < 1 || limit > 500) {
            throw new IllegalArgumentException("Invalid limit");
        }

        String sql = """
            select
                o.id as order_id,
                o.order_number as order_no,
                c.name as customer_name,
                o.placed_at as placed_at,
                coalesce(sum(l.line_amount), 0) as total_amount
            from orders o
            join customers c on c.id = o.customer_id
            left join order_lines l on l.order_id = o.id
            where o.placed_at >= ?
              and o.placed_at < ?
            group by o.id, o.order_number, c.name, o.placed_at
            order by o.placed_at desc, o.id desc
            """;

        return em.createNativeQuery(sql, "OrderListRowMapping")
            .setParameter(1, from)
            .setParameter(2, to)
            .setMaxResults(limit)
            .getResultList();
    }
}
~~~

Các chú ý:

- **Instant binding** và timestamp mapping cần được xác nhận theo provider/dialect; một số nơi cần OffsetDateTime/Timestamp hoặc chuyển kiểu được kiểm thử.
- Truy vấn chỉ trả DTO và không cần tất cả managed entity.
- Giới hạn số hàng được validate ở repository/service, tránh request yêu cầu hàng triệu kết quả.
- Query được tập trung ở một implementation, có thể đổi cách ánh xạ mà không sửa controller.
- Nếu service đang dùng tenant scope, phải bổ sung điều kiện tenant/authorization theo model thật.

Với Spring:

~~~java
@Repository
public class NativeSalesReportRepository implements SalesReportRepository {
    @PersistenceContext
    private EntityManager em;
    // Implementation ...
}
~~~

**@Repository** là annotation của Spring, không phải JPA. Với Jakarta EE có thể dùng CDI bean thích hợp. Trong dự án thực, tránh định nghĩa cùng class hai lần; đoạn cuối chỉ minh họa annotation cần bổ sung.

### 20.1. Đặt tên method theo kết quả, không theo công nghệ

Ưu tiên:

~~~text
findTopOrdersPerCustomer()
aggregateRevenueByMonth()
claimReadyJobs()
searchProductsByText()
~~~

thay vì:

~~~text
runNativeSql1()
querySqlSpecial()
executeSomething()
~~~

Tên nghiệp vụ làm rõ contract, còn việc dùng Native SQL là chi tiết implementation có thể thay đổi sau này.

### 20.2. Tách SQL theo DBMS nếu cần

Nếu sản phẩm hỗ trợ hai database:

~~~text
SalesReportRepository
  ├── PostgresSalesReportRepository
  └── SqlServerSalesReportRepository
~~~

Mỗi implementation có thể dùng cú pháp tối ưu riêng nhưng cùng trả một DTO contract. Như vậy sự không portable được **cô lập**, không lan khắp application code.

Nhưng nếu dự án đã xác định chỉ dùng PostgreSQL, không cần dựng abstraction phức tạp chỉ để phòng trường hợp tưởng tượng sẽ đổi DB. Nên có một chiến lược cân bằng giữa tính di động mong muốn và độ phức tạp hiện tại.

## 21. Native SQL hay JDBC, jOOQ, Spring JdbcTemplate?

Native SQL qua EntityManager không phải công cụ duy nhất cho SQL trực tiếp:

| Công cụ | Mạnh ở đâu | Giới hạn/cân nhắc |
|---|---|---|
| **JPQL / Criteria** | Entity-centric, portable, tận dụng mapping | Một số SQL features khó diễn đạt |
| **JPA Native SQL** | SQL DB-specific nhưng vẫn qua EntityManager/JPA transaction | Mapping result phức tạp, quản lý cache/context phải cẩn thận |
| **JDBC** | Kiểm soát PreparedStatement, ResultSet, batching/driver | Nhiều mã quản lý resource và mapping thủ công |
| **Spring JdbcTemplate** | Giảm boilerplate JDBC trong Spring | Không tự có entity lifecycle của JPA |
| **jOOQ** | DSL SQL có kiểu và nhiều khả năng DBMS | Thêm thư viện/cách quản lý schema, licensing/tính năng tùy edition |
| **Stored procedure** | Đặt logic gần database, có thể tối ưu nhiều bước | Khó chuyển DB, cần versioning và quan sát lỗi |
| **Search/analytics engine** | Full-text, ranking, phân tích dữ liệu lớn theo thiết kế chuyên dụng | Đồng bộ dữ liệu và vận hành hệ thống mới |

**JPA Native SQL hợp lý** khi ứng dụng đã dùng EntityManager và chỉ có một nhóm query cần SQL thủ công. Nếu phần lớn hệ thống là báo cáo và SQL phức tạp, một SQL-centric tool có thể dễ bảo trì hơn việc cố nhét toàn bộ logic vào JPA.

### 21.1. Không tự tạo JDBC connection ngoài transaction

Một native query qua EntityManager thường sử dụng resource/transaction do provider quản lý. Nếu chuyển sang JDBC trực tiếp, phải bảo đảm connection được lấy từ datasource và enlisted vào transaction thích hợp. Không tự mở một connection khác rồi giả định nó thấy mọi thay đổi chưa commit trong EntityManager.

### 21.2. Không cần dùng native cho mọi thao tác DML

Để cập nhật một Product có @Version, validation và domain events, **managed entity** thường phù hợp hơn. Chọn jOOQ/JdbcTemplate/Native SQL cho mọi update có thể khiến ứng dụng phải tự triển khai lại các quy tắc entity lifecycle và optimistic locking.

## 22. Kiểm thử Native SQL trên database thật

Native SQL bị ràng buộc với **schema vật lý, dialect, JDBC types, indexes và runtime behavior**, nên kiểm thử tích hợp là tối quan trọng.

### 22.1. Unit test không thay thế integration test

Một unit test mock EntityManager và verify createNativeQuery() đã được gọi có thể giúp kiểm tra flow service nhưng **không xác nhận SQL hợp lệ** trên database.

Integration test nên có:

1. DBMS/version tương đương production, ví dụ PostgreSQL test container nếu production là PostgreSQL.
2. Migration schema giống deploy thật.
3. Dữ liệu fixture gồm trường hợp thường gặp và edge cases.
4. Transaction setup/rollback/cleanup đúng.
5. Assertion về **giá trị và kiểu kết quả**, không chỉ query không ném exception.
6. Assertion về số hàng bị ảnh hưởng với native DML.
7. Trường hợp concurrency khi query dùng locking/upsert.

### 22.2. Ví dụ test scalar result

~~~java
@Test
void countOrdersReturnsExpectedNumber() {
    // Fixture đã có đúng ba orders trong database test.
    Number count = (Number) em.createNativeQuery(
        "select count(*) from orders"
    ).getSingleResult();

    assertEquals(3L, count.longValue());
}
~~~

Test giả định JUnit 5, EntityManager được test setup quản lý và database test đã được cô lập, không chứa dữ liệu của test khác.

### 22.3. Ví dụ test DTO mapping

~~~java
@Test
void orderReportHasCustomerAndAmount() {
    @SuppressWarnings("unchecked")
    List<OrderListRow> rows = em.createNativeQuery(
        """
        select
            o.id as order_id,
            o.order_number as order_no,
            c.name as customer_name,
            o.placed_at as placed_at,
            coalesce(sum(l.line_amount), 0) as total_amount
        from orders o
        join customers c on c.id = o.customer_id
        left join order_lines l on l.order_id = o.id
        where o.order_number = ?
        group by o.id, o.order_number, c.name, o.placed_at
        """,
        "OrderListRowMapping"
    ).setParameter(1, "PO-TEST-1")
     .getResultList();

    assertEquals(1, rows.size());
    assertEquals("PO-TEST-1", rows.get(0).orderNumber());
    assertEquals("Alice", rows.get(0).customerName());
}
~~~

Ở đây **@SuppressWarnings** gắn vào biến cục bộ là Java annotation hợp lệ với phạm vi phù hợp, nhưng cách provider trả kiểu danh sách từ createNativeQuery vẫn cần cast do API không luôn typed. Test thật nên assert thêm **BigDecimal total**, **Instant/date conversion** và trường hợp order không có lines.

### 22.4. Test Native DML và persistence context

Một test quan trọng:

~~~java
PurchaseOrder managed = em.find(PurchaseOrder.class, orderId);

em.createNativeQuery(
    "update orders set status = 'CANCELLED' where id = ?"
).setParameter(1, orderId)
 .executeUpdate();

// Không khẳng định managed.getStatus() đã là CANCELLED.
em.refresh(managed);
assertEquals(OrderStatus.CANCELLED, managed.getStatus());
~~~

Thực hiện trong transaction thích hợp. Trước native update, không nên có dirty state của cùng entity có nguy cơ ghi đè sau đó. Sau test, rollback/cleanup phù hợp để không ảnh hưởng các case tiếp theo.

### 22.5. Test cạnh tranh cho UPSERT/SKIP LOCKED

Một test chỉ dùng một EntityManager và một transaction **không chứng minh** UPSERT hay locking hoạt động an toàn dưới cạnh tranh.

Đối với query nhận job:

- Mở hai transactions trên hai connections độc lập.
- Transaction T1 khóa một nhóm job.
- T2 chạy SKIP LOCKED và xác nhận không nhận lại job đang bị khóa.
- Kiểm tra trạng thái sau commit/rollback.
- Thêm timeout để tránh test treo nếu behavior khác kỳ vọng.

Đối với UPSERT:

- Dùng nhiều transaction chèn/cập nhật cùng unique key.
- Xác nhận không tạo duplicate row.
- Kiểm tra semantics ghi đè hay cộng dồn có đúng yêu cầu khi concurrency.

Đừng chạy load test kiểu này trên production database với dữ liệu thật.

## 23. Những lỗi thường gặp khi chuyển từ JPQL sang Native SQL

### 23.1. Dùng tên entity thay cho tên bảng

~~~sql
select * from PurchaseOrder
~~~

Trong JPQL **PurchaseOrder** là entity; SQL thật ở ví dụ phải truy vấn **orders**. Không phải DB nào cũng có bảng tên PurchaseOrder.

### 23.2. Dùng tên property thay tên cột vật lý

~~~sql
select orderNumber from orders
~~~

Trong schema, cột là **order_number**, không phải orderNumber. Cần đối chiếu DDL và @Column/@JoinColumn.

### 23.3. Thiếu cột khi ánh xạ entity result

~~~sql
select id, order_number from orders
~~~

không đủ để provider hydrate entity PurchaseOrder đầy đủ theo mapping có status, version, customer_id và placed_at. Nếu chỉ cần hai trường, dùng scalar/DTO, đừng ánh xạ partial result vào managed entity.

### 23.4. SELECT * qua JOIN có tên cột trùng

SELECT * FROM orders JOIN customers tạo nhiều id, gây mapping ambiguity. Chỉ chọn cột cần thiết, alias tường minh, hoặc chọn o.* khi resultClass là PurchaseOrder.

### 23.5. Ép native COUNT trực tiếp về Long

~~~java
Long total = (Long) em.createNativeQuery(
    "select count(*) from orders"
).getSingleResult();
~~~

có thể gặp ClassCastException tùy JDBC type/provider. Nhận **Number** rồi chuyển có kiểm soát.

### 23.6. Dùng :name và tưởng mọi provider đều hỗ trợ

Named parameter rất phổ biến trong Hibernate native queries, nhưng tính portable của native SQL parameter binding không giống JPQL. Nếu dự án có nhiều provider, dùng hình thức đã được chuẩn và runtime xác nhận.

### 23.7. Ghép input vào WHERE hoặc ORDER BY

Value phải bind; identifier/sort direction phải chọn từ whitelist. Một query “chỉ SELECT” vẫn có thể bị SQL injection và gây lộ dữ liệu hoặc làm hệ thống tốn tài nguyên.

### 23.8. Native UPDATE mà quên EntityManager đang giữ entity cũ

Native DML không tự làm object managed đang có được refresh. Nếu không clear/refresh đúng lúc, code Java có thể đọc state cũ hoặc ghi đè bằng flush sau.

### 23.9. Native DML không tự gọi lifecycle callbacks

Không kỳ vọng @PreUpdate/@PostUpdate, @PreRemove/@PostRemove, cascade/orphanRemoval và Bean Validation được áp dụng giống khi thao tác từng entity. Database constraints vẫn bảo vệ dữ liệu nhưng không thay thế toàn bộ business invariants.

### 23.10. Quên @Version trong SQL bulk

Native UPDATE không tự tăng version theo JPA optimistic locking. Nếu không xử lý, transaction khác có thể không phát hiện một số xung đột. Sử dụng version predicate và increment khi phù hợp, hoặc quay lại managed entity.

### 23.11. Nhầm flush với commit

Gọi em.flush() trước native SQL giúp đồng bộ pending changes trong cùng transaction, **không xác nhận chúng đã commit**. Rollback vẫn có thể hoàn tác DML và transaction khác chưa chắc thấy thay đổi theo isolation.

### 23.12. SQL tốt trên H2 nhưng thất bại trên PostgreSQL

H2 có parser, types, optimizer và khả năng tương thích khác DBMS đích. Native CTE/window/JSON/upsert rất dễ phụ thuộc dialect. Test trên đúng DBMS/version production hoặc test container tương đương.

### 23.13. Sai kiểu timestamp, UUID, JSON hoặc array

JDBC driver có thể trả Timestamp, OffsetDateTime, PGobject hoặc dạng array khác mong đợi. **@ColumnResult(type=...) không làm mọi phép chuyển đổi tự động portable**. Kiểm tra mapping và converter theo provider/dialect.

### 23.14. JOIN nhiều collection làm tổng bị nhân đôi

Nếu join order_lines với promotions theo hai quan hệ một-nhiều, **sum(line_amount)** có thể bị nhân theo số promotions. Vấn đề nằm ở cardinality JOIN, không phải JPA hay Native SQL tự làm sai phép cộng. Cần aggregate trước hoặc tách query.

### 23.15. Recursive CTE chạy mãi khi dữ liệu có cycle

Nếu hierarchy parent_id có chu trình, UNION ALL recursion có thể không dừng đúng. Cần ràng buộc dữ liệu, cycle detection hoặc độ sâu tối đa phù hợp.

### 23.16. JOIN/CTE/window chạy chậm dù chỉ trả vài dòng

SQL có thể quét, sort và aggregate rất nhiều rows trước LIMIT. Hãy xem EXPLAIN, indexes và điều kiện pushdown, không chỉ nhìn result size.

### 23.17. Phân trang sau JOIN làm sai đơn vị page

Một order có 10 lines sẽ tạo 10 hàng khi JOIN. LIMIT 20 trên kết quả phẳng không có nghĩa lấy 20 orders. Nếu API phân trang Orders, cần page root IDs trước rồi lấy lines/aggregate phù hợp.

### 23.18. Native DELETE vướng FK

Một SQL DELETE parent có thể bị FK chặn vì provider không áp dụng cascade REMOVE của entity mapping. Cần chọn lộ trình xóa theo business lifecycle hoặc DB cascade được thiết kế rõ, không tắt constraint vô điều kiện.

### 23.19. ResultSet mapping bị sai alias

SQL đổi alias **total_amount** thành **amount**, nhưng @ColumnResult vẫn khai báo total_amount. Query có thể ném lỗi hoặc mapping sai. Test phải kiểm tra alias và chữ ký constructor.

### 23.20. Dùng native vì nghĩ nó luôn nhanh hơn

Nếu JPQL DTO sinh cùng hình dạng SQL và có index tốt, native query có thể không đem lại lợi ích. Đừng đánh đổi portability và vòng đời entity nếu không có yêu cầu hoặc phép đo thực.

## 24. Tình huống quyết định theo yêu cầu sản phẩm

### 24.1. Màn hình CRUD sản phẩm

Yêu cầu: hiển thị 20 Product có status ACTIVE, phân trang theo price và cho phép sửa Product đã chọn.

**Đề xuất:** dùng **JPQL DTO** cho danh sách và **managed Product** cho thao tác sửa. Native SQL chỉ có ích nếu SQL provider sinh có vấn đề cụ thể đã đo được hoặc cần operator DB riêng.

**Lý do:** filter, order, DTO và update entity đều nằm trong khả năng bình thường của JPA. Dùng SQL native từ đầu làm tăng phụ thuộc tên cột mà chưa giải quyết vấn đề đặc biệt nào.

### 24.2. Báo cáo ba đơn hàng gần nhất cho mỗi khách hàng

Yêu cầu: top 3 **theo từng Customer**, không phải top 3 toàn hệ.

**Đề xuất:** xem JPQL/HQL version hiện tại có hỗ trợ window function/subquery thích hợp không. Nếu không hoặc query trở nên phức tạp, dùng **Native SQL ROW_NUMBER() OVER (PARTITION BY customer_id ...)**.

**Lý do:** đây là một truy vấn phân tích theo partition, không thể giải quyết bằng setMaxResults(3) của toàn query.

### 24.3. Tìm descendants của một category sâu bất kỳ

Yêu cầu: cây danh mục có thể sâu 10–30 cấp, cần lấy tất cả descendants trong một request.

**Đề xuất:** **recursive CTE** là ứng viên mạnh nếu DB hỗ trợ. So sánh với phương án mô hình hóa closure table/materialized path khi truy vấn hierarchy có tần suất rất cao.

**Lý do:** lặp nhiều lần em.find()/JPQL theo từng cấp tạo nhiều round-trip và có thể gây N+1; recursive SQL diễn đạt trực tiếp quan hệ liên tiếp.

### 24.4. Tìm kiếm nội dung có relevance và ngôn ngữ

Yêu cầu: tìm kiếm 10.000.000 bài viết, ranking theo full-text và highlight.

**Đề xuất:** xem full-text capability của DB với index specialized, hoặc search engine độc lập nếu quy mô/chức năng yêu cầu. Native SQL giúp sử dụng các operator/function riêng DB khi phù hợp.

**Lý do:** LIKE trên tên bài viết không tương đương truy vấn full-text có stemming/ranking. Tuy nhiên cần cân nhắc đặc điểm ngôn ngữ tiếng Việt và indexing thực.

### 24.5. Cập nhật một Order có validation và event

Yêu cầu: Order chỉ được hủy khi chưa giao hàng, phải tăng @Version, ghi audit và phát event sau commit.

**Đề xuất:** ưu tiên **load managed Order rồi gọi domain method** trong transaction; không dùng Native UPDATE chỉ vì nó ít dòng Java.

**Lý do:** Native UPDATE bỏ qua nhiều lifecycle behaviors. Nếu dùng batch native cho yêu cầu lớn, phải thiết kế lại toàn bộ invariants/audit/version/outbox.

### 24.6. Import 2 triệu dòng từ staging

Yêu cầu: nạp hàng loạt vào bảng nghiệp vụ, deduplicate theo unique key, không cần materialize từng entity vào JVM.

**Đề xuất:** xem **INSERT ... SELECT**, MERGE/UPSERT hoặc cơ chế bulk load của DB, kết hợp transaction và kiểm soát idempotency.

**Lý do:** gọi em.persist cho hai triệu object có thể tốn memory và round-trip; database có những công cụ set-based hiệu quả hơn. Nhưng không bỏ qua validation, constraints và reconciliation.

### 24.7. Hai backend database khác nhau

Yêu cầu: sản phẩm buộc chạy trên PostgreSQL và Oracle mà không duy trì hai code paths.

**Đề xuất:** ưu tiên JPQL/Criteria hoặc những khả năng portable. Nếu buộc native, cô lập query vào một interface với implementation cho từng dialect và test chéo.

**Lý do:** câu native chỉ phụ thuộc SQL chuẩn ở mức đơn giản có thể chạy cả hai, nhưng recursive syntax, JSON, upsert, timestamp và pagination đều dễ khác nhau.

### 24.8. Claim job giữa nhiều worker

Yêu cầu: 10 worker lấy job sẵn sàng từ cùng một DB mà không cùng nhận một job.

**Đề xuất:** cân nhắc transaction + pessimistic lock của JPA nếu đủ. Khi cần semantics **SKIP LOCKED/RETURNING**, native SQL với retry/idempotency có thể phù hợp hơn.

**Lý do:** yêu cầu concurrency và lock semantics cụ thể; không chỉ là SELECT danh sách thông thường.

### 24.9. Lấy dữ liệu từ view của hệ thống cũ

Yêu cầu: legacy DB có view đã định nghĩa logic nhiều bảng và được dùng bởi nhiều ứng dụng.

**Đề xuất:** Native SQL từ view hoặc mapping read-only entity lên view khi có ID ổn định và được phép.

**Lý do:** giữ hợp đồng SQL đã được DBA quản trị có thể giảm duplication, nhưng vẫn cần quản lý schema migration, privileges và version của view.

### 24.10. Truy vấn entity theo primary key

Yêu cầu: lấy Order #100 và sửa status.

**Đề xuất:** **em.find(PurchaseOrder.class, 100L)** hoặc repository tương đương, không cần native.

**Lý do:** identity map, managed entity, optimistic locking và lifecycle đã được ORM giải quyết tốt. Dùng SQL native cho một lookup ID đơn giản thường chỉ tăng rủi ro.

## 25. Bài tập thực hành

### Bài 1: Chọn JPQL hay Native SQL

Yêu cầu: tìm tất cả Order có status PAID và placedAt trong một khoảng thời gian, sắp xếp theo thời gian mới nhất.

**Câu hỏi:** Có lý do bắt buộc Native SQL không?

**Gợi ý:** Không. Đây là lọc/sort thông thường:

~~~jpql
select o
from PurchaseOrder o
where o.status = :status
  and o.placedAt >= :start
  and o.placedAt < :end
order by o.placedAt desc, o.id desc
~~~

JPQL hoặc DTO projection là lựa chọn mặc định hợp lý.

### Bài 2: Top N cho mỗi khách hàng

Yêu cầu: mỗi customer chỉ lấy 2 đơn có placedAt mới nhất.

**Câu hỏi:** Vì sao **setMaxResults(2)** không đủ?

**Gợi ý:** Nó giới hạn **toàn tập kết quả** xuống hai hàng, không giới hạn **mỗi group customer**. Có thể dùng ROW_NUMBER() OVER(PARTITION BY customer_id ORDER BY placed_at DESC, id DESC) trong native SQL khi provider không hỗ trợ diễn đạt phù hợp.

### Bài 3: Scalar COUNT và Java type

~~~java
Long n = (Long) em.createNativeQuery(
    "select count(*) from orders"
).getSingleResult();
~~~

**Câu hỏi:** Có chắc code portable không?

**Gợi ý:** Không. JDBC/provider có thể trả một kiểu Number khác Long. Đọc Number rồi convert có kiểm soát; với count rất lớn cần kiểm tra overflow.

### Bài 4: Result entity thiếu cột

~~~java
em.createNativeQuery(
    "select id, order_number from orders",
    PurchaseOrder.class
);
~~~

**Câu hỏi:** Có nên dùng kiểu result này để lấy tóm tắt hai field không?

**Gợi ý:** Không. PurchaseOrder còn các mapped fields khác. Dùng DTO/scalar result, hoặc SELECT đầy đủ các cột cần cho entity result nếu thực sự cần managed entity.

### Bài 5: Native query JOIN và alias

~~~sql
select *
from orders o
join customers c on c.id = o.customer_id;
~~~

**Câu hỏi:** Rủi ro gì khi ánh xạ entity result?

**Gợi ý:** Hai bảng đều có **id** và những cột có tên trùng. Chọn o.* cho PurchaseOrder result, hoặc alias rõ rồi dùng SqlResultSetMapping.

### Bài 6: Query parameter an toàn

Code:

~~~java
String sql = "select * from orders where order_number = '" +
             input + "'";
~~~

**Yêu cầu:** sửa.

**Gợi ý:**

~~~java
Query q = em.createNativeQuery(
    "select * from orders where order_number = ?"
);
q.setParameter(1, input);
~~~

Bind values thay vì nối trực tiếp; kiểm tra quyền truy cập Order sau khi đọc.

### Bài 7: Dynamic ORDER BY

API nhận **sortField** từ client. Developer nối thẳng sortField vào ORDER BY SQL.

**Câu hỏi:** Vì sao không thể chỉ bind sortField như value?

**Gợi ý:** Identifier SQL không được thay bằng một bind value thông thường. Dùng allowlist **date → placed_at, number → order_number, default → id**, và allowlist direction ASC/DESC.

### Bài 8: SQL native cập nhật dữ liệu đang managed

~~~java
PurchaseOrder o = em.find(PurchaseOrder.class, id);
em.createNativeQuery(
    "update orders set status = 'PAID' where id = ?"
).setParameter(1, id)
 .executeUpdate();
~~~

**Câu hỏi:** Có chắc **o.getStatus() == PAID** ngay sau đó?

**Gợi ý:** Không. Native DML không tự đồng bộ managed entity. Cần quản lý pending state, refresh/clear phù hợp và tính đến version.

### Bài 9: Tăng version

Order có @Version long version=4. Native UPDATE chỉ set status.

**Câu hỏi:** Điều gì có thể bị phá vỡ?

**Gợi ý:** Optimistic locking có thể không phát hiện thay đổi vì version không tăng. Nếu buộc native, dùng WHERE version=? và SET version=version+1 theo semantics domain, đồng thời xử lý managed entity stale và audit.

### Bài 10: CTE recursive có cycle

Bảng category cha–con do dữ liệu lỗi tạo A→B→C→A.

**Câu hỏi:** Recursive UNION ALL có thể gặp vấn đề gì?

**Gợi ý:** Lặp lại cùng nhóm rows cho tới khi DB giới hạn hoặc quá tải. Cần ngăn cycle ở write path, kiểm tra visited path hoặc cơ chế CYCLE/độ sâu tùy DB.

### Bài 11: JSONB index

Native query lọc **attributes ->> 'color' = 'black'**, nhưng một GIN index chung trên attributes không được optimizer dùng.

**Câu hỏi:** Có phải native query sai?

**Gợi ý:** Không nhất thiết. Index phải phù hợp operator. Có thể cân nhắc expression index trên **(attributes ->> 'color')**, index operator class khác hoặc truy vấn theo containment @> khi semantics tương đương.

### Bài 12: Full-text search

Ứng dụng dùng LIKE '%java%' để tìm 10 triệu bài có ranking.

**Câu hỏi:** Những giới hạn của LIKE là gì?

**Gợi ý:** Không có ranking/lexical analysis đầy đủ, có thể khó dùng index B-tree cho leading wildcard. Native full-text DB operator hoặc search engine có thể phù hợp nếu requirement thực sự cần.

### Bài 13: UPSERT và duplicate retry

Một job gửi cùng kết quả doanh thu tháng hai lần do retry. Câu SQL dùng ON CONFLICT DO UPDATE nhưng UPDATE đặt amount = amount + excluded.amount.

**Câu hỏi:** Kết quả có còn idempotent không?

**Gợi ý:** Không; retry có thể cộng đôi. Cần thiết kế event/process ID deduplication, hoặc ghi đè snapshot total theo công thức nghiệp vụ phù hợp. Upsert chỉ giúp tránh trùng hàng theo unique key, không tự đảm bảo toàn bộ operation idempotent.

### Bài 14: Cascade

Order có nhiều OrderLine với CascadeType.REMOVE ở Java. Team chạy:

~~~sql
delete from orders where id = ?;
~~~

**Câu hỏi:** Các OrderLine có tự được JPA cascade REMOVE không?

**Gợi ý:** Không. Native DELETE không gọi em.remove(order), nên JPA lifecycle cascade không tự chạy. DB có thể từ chối vì FK hoặc xóa theo ON DELETE CASCADE nếu đã cấu hình; phải xác định cơ chế mong muốn.

### Bài 15: Flush trước native SELECT

Trong cùng transaction, code sửa Product.price của managed entity rồi chạy native SELECT tính SUM(price) từ bảng products.

**Câu hỏi:** Tại sao kết quả native có thể không như trạng thái Java?

**Gợi ý:** UPDATE có thể chưa được flush. Nếu SQL cần thấy pending changes, gọi em.flush() trong transaction đã tham gia trước SELECT; vẫn chưa có commit.

### Bài 16: Kiểm tra báo cáo GROUP BY

Một report JOIN OrderLine và Promotion vào cùng Order rồi SUM(lineAmount). Với 3 lines và 2 promotions, tổng gấp đôi.

**Câu hỏi:** Vấn đề do Native SQL hay do cardinality?

**Gợi ý:** Do quan hệ JOIN nhân số hàng. Aggregate lines trước khi join promotions hoặc tách hai query/CTE. SUM(DISTINCT lineAmount) không luôn đúng khi có hai line hợp lệ cùng giá.

### Bài 17: Chọn tool

Một ứng dụng có 90% workload là SQL analytics nhiều CTE/window, chỉ 10% CRUD entity.

**Câu hỏi:** Có nhất thiết dùng EntityManager Native SQL cho mọi truy vấn?

**Gợi ý:** Không. Cân nhắc một SQL-centric tool như jOOQ/JdbcTemplate/JDBC cho analytics, giữ JPA cho entity domain nếu vẫn có lợi. Chọn theo khả năng mapping, transaction và đội ngũ.

### Bài 18: Tính di động

Dự án viết ON CONFLICT cho PostgreSQL rồi chuyển sang SQL Server.

**Câu hỏi:** Có thể giữ nguyên query không?

**Gợi ý:** Không. Cần phương án upsert tương ứng với semantics và concurrency của SQL Server, cũng như integration tests riêng. Đặt query trong repository abstraction sẽ giúp cô lập khác biệt.

### Bài 19: Phân trang báo cáo

Một query SELECT Order JOIN OrderLine trả về hàng theo từng line. API dùng LIMIT 20 rồi group thành OrderDetail.

**Câu hỏi:** Vì sao trang có thể chỉ chứa 2 Order?

**Gợi ý:** 20 hàng JOIN có thể thuộc 2 Order, không phải 20 orders. Page root IDs/header trước, sau đó query lines của root IDs đã chọn.

### Bài 20: Test hiệu năng

Team thấy native query chạy 20 ms còn JPQL entity query chạy 150 ms trên một bộ dữ liệu.

**Câu hỏi:** Có thể kết luận native luôn tốt hơn?

**Gợi ý:** Chưa. Kiểm tra entity query có N+1, fetch nhiều cột, thiếu pagination hoặc không dùng DTO không. So sánh cùng dữ liệu, kết quả, index, cache, transaction và các chỉ số p95/p99.

## 26. Checklist trước khi quyết định triển khai Native SQL

1. **Yêu cầu thật sự là gì?** Lấy entity để ghi, lấy report scalar, top-N-per-group, hierarchy hay batch DML?
2. **Đã thử JPQL/Criteria/DTO projection chưa?** Có phiên bản tương đương dễ đọc và đủ nhanh không?
3. **Tính năng DBMS nào là bắt buộc?** CTE, window, JSON, full-text, spatial, hints, UPSERT hay locking?
4. **Production DBMS/dialect/version đã xác định chưa?** Query có phải chạy trên nhiều DB không?
5. **SQL có đúng schema vật lý không?** Tên bảng, tên cột, alias, join keys, NULL, index.
6. **Dữ liệu kết quả cần ánh xạ ra gì?** Entity đầy đủ, DTO, Object[], Number, @ConstructorResult?
7. **Có kiểm tra kiểu JDBC và nullability?** COUNT, timestamp, BigDecimal, JSON, UUID, enum.
8. **Có bind mọi giá trị input không?** Identifier/sort có whitelist?
9. **Có ràng buộc tenant/authorization không?** Native SQL không tự bảo vệ mọi row.
10. **Có transaction và flush đúng không?** Pending entity changes có phải được đồng bộ trước native read?
11. **Native DML có ảnh hưởng managed entities không?** Cần refresh/clear, version handling, callbacks, cascade?
12. **Kết quả có bị nhân hàng do JOIN không?** GROUP BY, DISTINCT, EXISTS và SUM đã đúng?
13. **Có kiểm soát pagination và giới hạn response không?** Phân trang root hay hàng join?
14. **Đã xem execution plan, index và workload thực tế chưa?** Không chỉ đo một lần trên dev.
15. **Đã có integration tests trên DB giống production chưa?** Query/DTO/transaction/concurrency.
16. **SQL đã được cô lập trong repository phù hợp chưa?** Tránh phân tán query phụ thuộc schema.
17. **Có kế hoạch migration và rollback không?** Native query có thể hỏng khi rename cột hoặc thay schema.
18. **Lợi ích có lớn hơn chi phí bảo trì không?** Nếu không, quay lại JPQL/Criteria.

## 27. Bảng ghi nhớ

| Tình huống | Có cần Native SQL? | Ghi chú |
|---|---|---|
| Tìm entity theo ID | Thường **không** | em.find/repository |
| Danh sách product có filter/sort/pagination | Thường **không** | JPQL DTO |
| Count/SUM/GROUP BY đơn giản | Thường **không** | JPQL aggregate |
| Recursive hierarchy sâu tùy ý | **Có thể** | Recursive CTE hoặc mô hình dữ liệu khác |
| Top N rows per group | **Có thể** | Window function |
| JSONB containment / PostGIS | **Thường hữu ích** | DB-specific operators/index |
| Full-text relevance score | **Có thể** | Chọn DB FTS hoặc search engine |
| UPSERT/UPDATE FROM/INSERT SELECT phức tạp | **Có thể** | Bảo vệ constraints, version, idempotency |
| Claim jobs với SKIP LOCKED | **Có thể** | Transaction và concurrency testing |
| Legacy/materialized view | **Có thể** | Quản lý schema và freshness |
| Sửa một managed Order với lifecycle | Thường **không** | Dùng domain method và JPA |
| SQL handwritten nhưng không có benchmark | **Chưa đủ lý do** | Đo JPQL tương đương |
| Ứng dụng bắt buộc multi-DB portable | **Cân nhắc kỹ** | Cô lập dialect-specific logic |

## 28. Kết luận

**Native SQL qua JPA là một công cụ có chủ đích, không phải lối đi mặc định cho mọi truy vấn.** Nó đặc biệt hữu ích khi ứng dụng cần khả năng SQL của DBMS mà JPQL/Criteria trong hệ thống hiện tại không diễn đạt tốt, hoặc khi một câu SQL trực tiếp đã được **chứng minh** đáp ứng đúng nghiệp vụ với hiệu năng hoặc tính đơn giản vận hành vượt trội.

Các lý do thuyết phục gồm **recursive CTE**, **window functions**, **JSON/full-text/spatial operators**, **upsert và set-based DML**, **locking đặc thù**, cùng các báo cáo nhiều tầng trên view hoặc schema legacy. Ngược lại, **CRUD entity**, lọc/sắp xếp cơ bản, DTO projection và aggregate thông thường vẫn nên bắt đầu từ JPQL/Criteria.

Khi quyết định dùng Native SQL:

- Dùng **createNativeQuery()** với tham số được bind; không nối dữ liệu user vào SQL.
- Chọn ánh xạ **scalar/DTO** cho report và **entity result đầy đủ** khi cần managed entity.
- Quản lý rõ **flush, transaction, optimistic locking, cascade, callbacks và persistence context**; native DML không tự đồng bộ entity đang managed.
- Cô lập SQL theo repository/use case, có **integration tests trên DBMS thực** và quan sát execution plan.
- Đo chi phí end-to-end và so sánh với **JPQL tương đương đã tối ưu**, không so với một truy vấn entity bị N+1 hoặc lấy thừa dữ liệu.

Quyết định đúng là quyết định cân bằng giữa **ngữ nghĩa dữ liệu**, **hiệu năng**, **bảo mật**, **tính di động** và **chi phí bảo trì**. Native SQL có giá trị khi nó giải quyết một giới hạn cụ thể mà các công cụ JPA mức cao hơn không xử lý đủ tốt trong bối cảnh hệ thống của bạn.
