# Nguồn sở hữu DDL giữa ánh xạ ORM với công cụ migration trong Hibernate ORM

## 1. Một thay đổi entity có tự thay đổi database production không?

Trong một ứng dụng Java dùng Hibernate ORM, lập trình viên thường bắt đầu bằng entity:

~~~java
@Entity
@Table(name = "customers")
public class Customer {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "email", nullable = false, length = 320)
    private String email;
}
~~~

Nhìn vào code, Hibernate có đủ thông tin để đề xuất một bảng customers, một cột email và một số ràng buộc. Điều đó dễ dẫn đến suy luận: **cứ sửa @Entity thì Hibernate sẽ sửa database tương ứng**.

Suy luận ấy nguy hiểm khi ứng dụng chạy production. Việc thêm field, đổi tên Java property hoặc cập nhật annotation **không đồng nghĩa** một database đã có dữ liệu sẽ được migration đúng và an toàn. Ví dụ:

- Đổi @Column(name = "email") thành @Column(name = "primary_email") có thể bị công cụ tự động hiểu là cột mới, không phải đổi tên cột cũ.
- Thêm @Column(nullable = false) có thể không chạy được nếu hàng hiện tại chứa NULL.
- Đổi độ dài VARCHAR hoặc độ chính xác NUMERIC có thể gây lỗi dữ liệu.
- Đổi quan hệ @ManyToOne làm thay đổi FK và thứ tự thao tác trên những bảng đang có dữ liệu.
- Một lệnh DROP/CREATE có thể xóa dữ liệu hiện có.
- Triển khai nhiều phiên bản ứng dụng cùng lúc đòi hỏi schema tương thích trong giai đoạn chuyển giao.

Vì vậy chương **Lược đồ và chuyển đổi** cần trả lời câu hỏi nền tảng:

> Ai là nguồn sở hữu DDL (Data Definition Language): ánh xạ ORM tự sinh schema hay các migration scripts có phiên bản do Flyway/Liquibase quản lý?

Trong đa số ứng dụng có dữ liệu bền vững và quy trình triển khai nghiêm túc, cách tổ chức dễ kiểm soát là:

**Migration đã được version-control là nguồn thay đổi schema chính thức; entity mapping là hợp đồng Java ↔ schema phải tương thích với những migration đó.**

Hibernate vẫn hữu ích trong thiết kế, thử nghiệm và phát hiện một phần sai lệch, nhưng không nên để nhiều cơ chế độc lập cùng tự ý sửa cấu trúc database production.

### Mục tiêu học tập

Sau bài này, bạn có thể:

1. Phân biệt DDL, DML, metadata ORM và migration history.
2. Giải thích vì sao phải có một nguồn sở hữu thay đổi schema rõ ràng.
3. Đánh giá các chế độ hbm2ddl.auto/ddl-auto và chọn chế độ theo môi trường.
4. Thiết lập Hibernate validate cùng Flyway hoặc Liquibase.
5. Viết migration SQL PostgreSQL tương thích entity mapping.
6. Hiểu giới hạn của schema validation: không thay thế kiểm tra index, constraint hay logic DDL khác.
7. Thiết kế thay đổi schema nhiều bước theo expand–migrate–contract.
8. Xử lý renames, NOT NULL, FK, index, enum và dữ liệu đang tồn tại.
9. Hiểu baseline, checksum, schema drift, migration locks, rollback và quy trình vận hành.
10. Kiểm thử bằng database thực, CI và migration từ schema cũ sang schema mới.

Ví dụ dùng Java 17+, Jakarta Persistence, Hibernate ORM 6.x, Spring Boot 3.x, PostgreSQL và Flyway/Liquibase. Chi tiết cấu hình hoặc dependency của từng công cụ cần căn đúng phiên bản trong dự án; các đoạn mã minh họa không thay thế quy trình phê duyệt migration production.

## 2. DDL, DML, ORM metadata và migration là những lớp khác nhau

### 2.1. DDL — định nghĩa cấu trúc

DDL gồm các thao tác như:

~~~sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email VARCHAR(320) NOT NULL
);

ALTER TABLE customers
ADD COLUMN display_name VARCHAR(200);

CREATE INDEX idx_customers_email
ON customers(email);
~~~

DDL thiết lập bảng, cột, khóa, index và các database objects khác. DDL có thể làm thay đổi hợp đồng lưu trữ và ảnh hưởng dữ liệu đã tồn tại.

### 2.2. DML — tác động đến nội dung dữ liệu

~~~sql
INSERT INTO customers(email) VALUES ('linh@example.com');

UPDATE customers
SET display_name = 'Linh'
WHERE email = 'linh@example.com';

DELETE FROM customers
WHERE id = 100;
~~~

DML thay đổi rows. Migration có thể chứa cả DDL lẫn data migrations/DML (ví dụ backfill một cột trước khi bật NOT NULL). Nhưng việc dữ liệu được sửa qua DML không làm Hibernate tự biết rằng schema hoặc cache cũng cần thay đổi.

### 2.3. ORM metadata — mô tả cách Java dùng schema

~~~java
@Column(name = "display_name", length = 200)
private String displayName;
~~~

Annotation nói cho Hibernate biết thuộc tính Java displayName được lưu ở cột display_name, với một số thông tin phục vụ SQL binding và schema generation/validation. Nó **không tự thực hiện** ALTER TABLE mỗi khi code thay đổi; điều đó phụ thuộc chế độ schema-management được cấu hình.

### 2.4. Migration — chuỗi thay đổi có thứ tự

Một migration tool lưu lịch sử thay đổi và thực thi các phiên bản chưa chạy theo thứ tự:

~~~text
V1__create_customers.sql
V2__create_purchase_orders.sql
V3__add_customer_display_name.sql
V4__backfill_customer_display_name.sql
V5__require_customer_display_name.sql
~~~

Tên trên minh họa Flyway versioned SQL migrations. Không phải mọi hệ thống cần chia mỗi thay đổi thành một migration riêng; việc chia phải phục vụ rollout, atomicity và review.

### 2.5. Sơ đồ trách nhiệm

~~~mermaid
flowchart TD
    A[Nhà phát triển đổi mô hình nghiệp vụ] --> B[Thiết kế thay đổi schema]
    B --> C[Viết migration có phiên bản]
    B --> D[Cập nhật JPA entity mapping]
    C --> E[CI chạy migration trên database test]
    D --> F[Hibernate kiểm tra mapping]
    E --> F
    F --> G[Deploy migration có kiểm soát]
    G --> H[Ứng dụng mới chạy trên schema phù hợp]
~~~

Mục tiêu là để DDL được quản lý bằng migration, còn ORM được xác minh phù hợp với kết quả DDL. Không để cả migration tool và Hibernate update schema cùng lúc trong một môi trường production.

## 3. “Nguồn sở hữu DDL” phải được định nghĩa rõ

Khi nói một thành phần **sở hữu DDL**, nghĩa là nó có thẩm quyền:

- Định nghĩa phiên bản schema mong muốn.
- Thực hiện CREATE/ALTER/DROP trong môi trường được phép.
- Ghi lại lịch sử thay đổi đã áp dụng.
- Phát hiện schema chưa được nâng cấp.
- Quy định khi nào thay đổi được triển khai và ai phê duyệt.
- Phối hợp thay đổi database với các phiên bản ứng dụng tương ứng.

Không nên có hai nguồn độc lập cùng quyết định ALTER TABLE theo hai phương pháp khác nhau.

### 3.1. Những mô hình thường gặp

| Mô hình | Ai tạo DDL? | Khi nào phù hợp? | Rủi ro |
|---|---|---|---|
| Hibernate schema generation | Hibernate từ entity metadata | Prototype, test database ngắn hạn | Không quản lý quá trình chuyển đổi dữ liệu production |
| Flyway/Liquibase migration | Migration scripts/changelog được review | Phần lớn ứng dụng có dữ liệu bền vững | Cần giữ mapping và SQL migration đồng bộ |
| DBA/database platform sở hữu DDL | Nhóm database triển khai scripts được phê duyệt | Hệ thống kiểm soát thay đổi chặt | Cần quy trình phối hợp release rõ |
| ORM đề xuất DDL, migration triển khai | Developer dùng DDL sinh ra làm bản nháp | Thiết kế ban đầu, giảm công viết SQL | Phải review và chuyển thành migration an toàn |
| Nhiều tool tự sửa schema | Không có chủ sở hữu duy nhất | **Không nên** | Drift, race, startup fail và dữ liệu bị sửa ngoài kiểm soát |

Không phải lúc nào Flyway hay Liquibase cũng chính là bên **vận hành production deployment**. Có tổ chức dùng SQL migration trong Git do kỹ sư viết, nhưng DBA hoặc pipeline đặc biệt mới có quyền chạy. Khi đó migration repository/changelog vẫn là **nguồn khai báo thay đổi**, còn quyền thực thi nằm ở quy trình DBA.

### 3.2. Quy tắc đơn giản theo môi trường

| Môi trường | Chính sách gợi ý |
|---|---|
| Unit test không cần DB thật | Không yêu cầu DDL production |
| Integration test DB tạm thời | Migration như production; hoặc ORM create-drop nếu test chuyên biệt |
| Prototype/demo có thể xóa dữ liệu | Hibernate create/create-drop có thể được chấp nhận |
| Development DB dùng chung | Migration có phiên bản; ORM validate |
| Staging | Migration theo quy trình triển khai; ORM validate |
| Production | Migration/review/deployment có kiểm soát; ORM validate hoặc none theo policy |

Trong một project trưởng thành, chạy chính các migration của production trên test database thường có giá trị lớn hơn việc chỉ dùng create-drop: nó kiểm tra cả scripts, thứ tự, constraint và compatibility của mapping.

## 4. Các chế độ Hibernate schema-management

Hibernate thường có property:

~~~properties
hibernate.hbm2ddl.auto=validate
~~~

Trong Spring Boot:

~~~properties
spring.jpa.hibernate.ddl-auto=validate
~~~

Những giá trị phổ biến:

| Giá trị | Tác dụng khái quát | Lưu ý |
|---|---|---|
| none | Không tự tạo/cập nhật/validate schema qua cơ chế này | Không chứng minh schema đúng |
| validate | Kiểm tra một phần mapping đối chiếu database; không sửa DDL | Phù hợp khi migration sở hữu DDL |
| update | Cố gắng điều chỉnh schema theo metadata | Không phải công cụ migration an toàn cho production |
| create | Tạo schema theo metadata, thường có thể drop/recreate objects tương ứng | Nguy cơ mất dữ liệu hiện có |
| create-drop | Tạo khi khởi động, xóa khi SessionFactory đóng theo lifecycle hỗ trợ | Chỉ phù hợp dữ liệu tạm/test |

Tên property và các giá trị cụ thể phụ thuộc Hibernate/Spring Boot version. Ngoài hbm2ddl.auto còn có cơ chế Jakarta Persistence schema-generation properties; không kết hợp nhiều chế độ tạo schema khi chưa hiểu mức ưu tiên.

### 4.1. validate giúp làm gì?

Hibernate đọc metadata của entity, lấy thông tin database từ JDBC metadata/dialect và so sánh những phần nó hỗ trợ, ví dụ:

- Bảng đã tồn tại hay chưa.
- Cột cần mapping có tồn tại hay không.
- Một số kiểu JDBC/SQL có tương thích với mapping không.

Nếu phát hiện vấn đề, ứng dụng có thể fail khi khởi động:

~~~text
Schema-validation: missing column [display_name]
in table [customers]
~~~

Đây là một **tín hiệu hữu ích**: code mới đang mong một cột mà migration chưa tạo. Tuy nhiên validate không phải một schema diff/compliance engine đầy đủ.

### 4.2. Những điều validate không bảo đảm

Không suy luận từ việc validate pass rằng tất cả đều giống DDL mong muốn. Tùy phiên bản/dialect, cơ chế validate có thể **không kiểm tra đầy đủ**:

- Index hoặc thứ tự cột trong index.
- Unique/check constraint và business invariant.
- ON DELETE CASCADE, DEFERRABLE hoặc chi tiết FK.
- Database default, generated columns, triggers và stored procedures.
- Row-level security policies, permissions và roles.
- Partitioning, tablespaces, collation, extensions.
- Mọi khác biệt về nullability, length, precision/scale.
- Dữ liệu đã được backfill đúng ngữ nghĩa.
- Thứ tự thực hiện một thay đổi schema không gây downtime.

Vì vậy validate là một lớp kiểm tra mapping runtime, không thay thế migration tests, database introspection và review SQL.

### 4.3. Vì sao update nguy hiểm cho schema đang có dữ liệu?

Giả sử entity được đổi:

~~~java
// Trước
@Column(name = "full_name")
private String fullName;

// Sau
@Column(name = "display_name")
private String displayName;
~~~

Hibernate không thể suy ra chắc chắn rằng developer muốn **rename** cột cũ, hay tạo cột hoàn toàn mới phục vụ nghiệp vụ khác. Một schema-update tự động có thể thêm display_name mà không chuyển dữ liệu từ full_name.

Những việc Hibernate update không thể tự quyết định an toàn:

- Chuyển dữ liệu theo quy tắc business.
- Chia một cột thành hai cột.
- Gộp hai bảng thành một.
- Chuyển VARCHAR thành một enum model khác.
- Lập kế hoạch giữa hai phiên bản ứng dụng đang chạy.
- Phối hợp backfill lớn, locks và thời gian triển khai.

**Không dùng update làm migration mechanism production.**

### 4.4. create và create-drop chỉ dùng khi chấp nhận xóa dữ liệu

Trong integration test cần database disposable, create-drop có thể tiện. Nhưng không được dùng chỉ vì muốn “ứng dụng tự chạy được” trên DB development có dữ liệu quan trọng. Nếu URL trỏ nhầm production hoặc staging, chế độ tạo lại schema có thể gây hậu quả nặng.

Khi kết nối tới môi trường dùng chung, hãy dùng migration và credentials không có quyền DROP ngoài phạm vi cho phép.

## 5. Một ví dụ đầy đủ: SQL migration sở hữu schema, entity sở hữu mapping

Xây dựng mini-domain:

~~~text
Customer 1 --- n PurchaseOrder
~~~

DB PostgreSQL có:

- customers(id, email, full_name)
- purchase_orders(id, customer_id, status, total_amount, created_at, version)

### 5.1. Migration V1 tạo bảng Customers

File:

~~~text
src/main/resources/db/migration/V1__create_customers.sql
~~~

Nội dung:

~~~sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email VARCHAR(320) NOT NULL,
    full_name VARCHAR(200) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT uk_customers_email UNIQUE (email)
);

CREATE INDEX idx_customers_created_at
    ON customers(created_at);
~~~

V1 làm rõ:

- Kiểu SQL và độ dài của các cột.
- NOT NULL của các thuộc tính bắt buộc.
- UNIQUE được enforce tại database.
- DEFAULT CURRENT_TIMESTAMP do database tạo khi INSERT không truyền created_at.
- Index phục vụ một loại truy vấn đã được cân nhắc.

### 5.2. Migration V2 tạo PurchaseOrder

File:

~~~text
src/main/resources/db/migration/V2__create_purchase_orders.sql
~~~

~~~sql
CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    status VARCHAR(24) NOT NULL,
    total_amount NUMERIC(19, 2) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    version BIGINT NOT NULL DEFAULT 0,

    CONSTRAINT fk_orders_customer
        FOREIGN KEY (customer_id) REFERENCES customers(id),
    CONSTRAINT ck_orders_amount
        CHECK (total_amount >= 0)
);

CREATE INDEX idx_orders_customer_created
    ON purchase_orders(customer_id, created_at DESC, id DESC);

CREATE INDEX idx_orders_status_created
    ON purchase_orders(status, created_at DESC, id DESC);
~~~

Không bắt buộc mọi bảng đều cần cả hai index minh họa; index phải được lựa chọn theo workload và plan. Việc thêm index có chi phí ghi và storage.

### 5.3. Entity tương thích với migration V1

~~~java
import jakarta.persistence.*;
import java.time.Instant;

@Entity
@Table(name = "customers")
public class Customer {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 320)
    private String email;

    @Column(name = "full_name", nullable = false, length = 200)
    private String fullName;

    @Column(name = "created_at", nullable = false,
            insertable = false, updatable = false)
    private Instant createdAt;

    protected Customer() {}

    public Long getId() { return id; }
    public String getEmail() { return email; }
    public String getFullName() { return fullName; }
}
~~~

Trong ví dụ, createdAt để database tự cấp khi INSERT bỏ qua cột. Việc đánh dấu insertable=false/updatable=false **không đảm bảo** một entity mới được Hibernate tự điền lại createdAt ngay sau persist/flush. Nếu cần nhận default-generated value trong cùng transaction, phải cấu hình cơ chế generated value được Hibernate hỗ trợ hoặc refresh/đọc lại theo workflow phù hợp. Tương tự, annotation @Column(nullable=false) không thay thế NOT NULL thật trong migration.

### 5.4. Entity tương thích với migration V2

~~~java
import jakarta.persistence.*;
import java.math.BigDecimal;
import java.time.Instant;

@Entity
@Table(name = "purchase_orders")
public class PurchaseOrder {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "customer_id", nullable = false,
                foreignKey = @ForeignKey(name = "fk_orders_customer"))
    private Customer customer;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 24)
    private OrderStatus status;

    @Column(name = "total_amount", nullable = false,
            precision = 19, scale = 2)
    private BigDecimal totalAmount;

    @Column(name = "created_at", nullable = false,
            insertable = false, updatable = false)
    private Instant createdAt;

    @Version
    @Column(nullable = false)
    private long version;

    protected PurchaseOrder() {}

    public Long getId() { return id; }
    public BigDecimal getTotalAmount() { return totalAmount; }
}

enum OrderStatus { DRAFT, PAID, CANCELLED }
~~~

Các class/enum public trong project thực tế nằm trong các file Java riêng; ví dụ rút gọn để minh họa mapping. Việc @JoinColumn(foreignKey=...) đặt tên FK phục vụ metadata và schema generation, **không tạo lại FK đã được migration tạo** khi Hibernate ở validate.

### 5.5. So sánh hợp đồng hai phía

| ORM metadata | DDL migration | Ghi chú |
|---|---|---|
| @Entity @Table(name="customers") | CREATE TABLE customers | Tên bảng |
| @GeneratedValue(IDENTITY) | BIGINT ... AS IDENTITY | Cơ chế cấp khóa cần tương thích DB |
| @Column(name="full_name", length=200) | full_name VARCHAR(200) | Tên và kiểu/độ dài |
| @ManyToOne + @JoinColumn("customer_id") | customer_id BIGINT + FK | Tham chiếu quan hệ |
| @Enumerated(STRING) | status VARCHAR(24) | Java enum và kiểu lưu trữ |
| BigDecimal precision=19 scale=2 | NUMERIC(19, 2) | Số tiền |
| @Version long | version BIGINT NOT NULL | Optimistic locking |
| Entity property createdAt | created_at TIMESTAMPTZ DEFAULT ... | Cần quy ước write/read/generated value |

Migration là nơi DDL được thực thi; mapping cho Hibernate biết cách đọc, ghi và kiểm tra runtime. Hai bên phải được thay đổi cùng một feature/release với khả năng tương thích rollout.

## 6. Tổ chức Flyway trong ứng dụng Spring Boot

Flyway dùng migrations có phiên bản và bảng lịch sử schema, thường có tên flyway_schema_history. Trong một Spring Boot app tiêu chuẩn, có thể cấu hình Flyway để chạy trước khi JPA EntityManagerFactory được khởi tạo; sau đó Hibernate validate schema cuối cùng.

### 6.1. Dependencies minh họa

Với Gradle Kotlin DSL:

~~~kotlin
dependencies {
    implementation("org.springframework.boot:spring-boot-starter-data-jpa")
    implementation("org.flywaydb:flyway-core")
    runtimeOnly("org.postgresql:postgresql")
}
~~~

Một số phiên bản Flyway cần thêm database-specific artifact như flyway-database-postgresql để nhận diện/hỗ trợ PostgreSQL. Kiểm tra version được Spring Boot BOM quản lý và tài liệu Flyway phiên bản đó; không tự chọn module từ một bài viết của version khác.

### 6.2. Cấu hình dùng Flyway và Hibernate validate

~~~yaml
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/shop
    username: shop_app
    password: ${DB_PASSWORD}

  flyway:
    enabled: true
    locations: classpath:db/migration

  jpa:
    hibernate:
      ddl-auto: validate
    properties:
      hibernate:
        format_sql: true
~~~

Giả định tài khoản kết nối có quyền phù hợp trên môi trường local. Trong production nên tách role chạy migration và role ứng dụng; không đặt password vào Git.

Ở đây:

1. Flyway xác định migrations chưa áp dụng và thực hiện DDL theo policy.
2. Hibernate bắt đầu với schema đã được migration chuẩn bị.
3. validate kiểm tra một phần mapping ↔ database.
4. Ứng dụng được đưa vào phục vụ request nếu startup thành công.

### 6.3. Không cho Hibernate và Flyway cùng “update” DDL

Sai về chủ sở hữu:

~~~yaml
spring:
  flyway:
    enabled: true
  jpa:
    hibernate:
      ddl-auto: update
~~~

Trong một deployment, Flyway chạy DDL có lịch sử; Hibernate lại cố thay đổi schema theo metadata mà không tạo migration script tương ứng. Điều đó có thể làm:

- Schema trên production khác schema dựng bằng migrations trong CI.
- Lịch sử Flyway không phản ánh mọi DDL đã xảy ra.
- Một instance có thể sửa schema trước instance khác.
- Thay đổi cột được tạo ngoài review.
- Lần migration tiếp theo gặp object đã có hoặc trạng thái bất ngờ.

Chọn validate hoặc none khi Flyway sở hữu thay đổi DDL.

### 6.4. Boot ordering và môi trường triển khai

Trong cấu hình Spring Boot chuẩn có Flyway auto-configuration, migration thường được chạy trước JPA initialization. Nhưng nếu dùng nhiều DataSource, custom EntityManagerFactory hoặc cấu hình Flyway riêng, **không được mặc định startup order vẫn đúng**.

Kiểm tra application log và integration test rằng:

~~~text
1. Kết nối database
2. Flyway migrate hoàn tất
3. Hibernate bootstrap + schema validation
4. Application readiness
~~~

Một chiến lược production khác là CI/CD migration job chạy **trước khi deploy app**, còn application chỉ validate và dùng DML role. Khi đó không bật Flyway migrate tự động trên mọi app instance nếu policy vận hành không cho phép.

## 7. Liquibase là lựa chọn thay thế, không phải công cụ chạy song song vô điều kiện

Liquibase quản lý thay đổi qua changeSet/changelog và bảng lịch sử, thường có DATABASECHANGELOG và bảng lock liên quan. Nó có thể sử dụng YAML, XML, JSON hoặc SQL-formatted changelog.

Ví dụ YAML:

~~~yaml
databaseChangeLog:
  - changeSet:
      id: 001-create-customers
      author: dev-team
      changes:
        - createTable:
            tableName: customers
            columns:
              - column:
                  name: id
                  type: BIGINT
                  constraints:
                    primaryKey: true
                    nullable: false
              - column:
                  name: email
                  type: VARCHAR(320)
                  constraints:
                    nullable: false
~~~

Đây là ví dụ changelog tối giản. Cách cấp identity/sequence, uniqueness và các DB-specific details cần bổ sung để tương đương entity thật; không copy đoạn này thay cho V1 PostgreSQL đầy đủ ở trên.

### 7.1. Cấu hình Spring Boot Liquibase

~~~yaml
spring:
  liquibase:
    enabled: true
    change-log: classpath:db/changelog/db.changelog-master.yaml
  jpa:
    hibernate:
      ddl-auto: validate
~~~

Chọn Flyway **hoặc** Liquibase làm công cụ sở hữu schema theo policy. Dùng cả hai chỉ khi đã có ranh giới sở hữu cực rõ (ví dụ hai database khác nhau), vì mỗi tool có migration history/locking riêng và có thể va chạm DDL.

### 7.2. So sánh Flyway và Liquibase theo mục tiêu

| Tiêu chí | Flyway | Liquibase |
|---|---|---|
| Mô hình phổ biến | SQL files có version; hỗ trợ thêm script kiểu khác tùy edition/version | ChangeSet/changelog có ID/author/path; hỗ trợ SQL |
| Lịch sử | Schema history table | DATABASECHANGELOG |
| Kiểm soát phiên bản | Versioned/repeatable migrations | ChangeSet, preconditions/labels/contexts |
| Review SQL vật lý | Rất trực diện với SQL migrations | Dùng SQL changeset hoặc xem SQL sinh ra |
| DB-specific operation | SQL phù hợp | Có thể dùng SQL trực tiếp |
| Lock/chống chạy trùng | Cơ chế Flyway theo DB/version | Lock quản lý qua Liquibase |
| Thích hợp | Đội thích SQL migration rõ ràng | Đội cần changelog abstraction/preconditions |

Không có “tool tốt nhất” cho mọi tổ chức. Tiêu chí chính là khả năng version-control, review, triển khai nhất quán, kiểm soát drift, transaction và sự phù hợp với database/version.

## 8. Chỉ một chủ sở hữu, nhưng ORM vẫn có thể sinh DDL nháp

Hibernate schema export hữu ích khi thử nhanh mô hình trong một database **không có dữ liệu cần giữ**. Developer có thể:

1. Tạo entity mẫu với @Column/@JoinColumn.
2. Dùng Hibernate schema generation trong sandbox để xem SQL đề xuất.
3. Review types, constraints, indexes và naming conventions.
4. Viết hoặc điều chỉnh migration file chính thức.
5. Chạy migration trên PostgreSQL mới.
6. Chạy Hibernate validate.

Ở đây DDL sinh ra chỉ là **đầu vào tham khảo**, không phải source of truth cho môi trường deployed.

### 8.1. Vì sao không copy nguyên xi mọi SQL Hibernate sinh?

Generated DDL có thể thiếu hoặc chưa phản ánh đúng:

- Partial indexes hoặc expression indexes.
- PostgreSQL-specific generated columns, trigger, policy, partition.
- Nhu cầu CREATE INDEX CONCURRENTLY.
- Backfill dữ liệu hàng triệu bản ghi.
- Online migration qua nhiều phiên bản ứng dụng.
- Điều kiện CHECK phức tạp và quy tắc domain.
- Tối ưu data type, collation, locking và storage.

Kỹ sư cần hiểu schema vật lý. ORM sinh DDL là một công cụ hỗ trợ, không phải thay thế review migration.

### 8.2. Tránh thay đổi schema gián tiếp qua annotation

Annotation như @Index, @UniqueConstraint, @ColumnDefault hoặc @Check có thể tác động DDL **khi Hibernate được phép tạo schema**. Ở validate, chúng không tự tạo index/constraint mới trên production.

Ví dụ:

~~~java
@Table(
    name = "customers",
    uniqueConstraints = @UniqueConstraint(
        name = "uk_customers_email",
        columnNames = "email"
    )
)
~~~

Nếu đang dùng Flyway, vẫn cần migration:

~~~sql
ALTER TABLE customers
ADD CONSTRAINT uk_customers_email UNIQUE (email);
~~~

Nếu constraint đã tồn tại từ V1 thì không chạy lại. Entity metadata và migration phải thống nhất; annotation không phải migration lịch sử.

## 9. Thay đổi schema đang có dữ liệu: expand–migrate–contract

Một kiểu thay đổi rủi ro cao là rename hoặc thay thế thuộc tính đang được nhiều phiên bản ứng dụng sử dụng.

Giả sử Customer.fullName đã lưu ở cột full_name. Tính năng mới muốn dùng display_name và thay đổi logic sinh tên hiển thị.

Nếu migration chỉ:

~~~sql
ALTER TABLE customers
RENAME COLUMN full_name TO display_name;
~~~

thì phiên bản ứng dụng **cũ** vẫn đang truy cập full_name có thể lỗi ngay sau DDL, nhất là trong rolling deployment.

### 9.1. Quy trình tương thích nhiều phiên bản

~~~mermaid
flowchart TD
    A[Schema cũ: full_name] --> B[Expand: thêm display_name nullable]
    B --> C[Deploy app tương thích cả hai cột]
    C --> D[Backfill dữ liệu cũ]
    D --> E[Chuyển read path sang display_name]
    E --> F[Theo dõi không còn app cũ]
    F --> G[Contract: NOT NULL rồi bỏ full_name]
~~~

Không phải mọi thay đổi đều cần từng bước như trên; quy trình tương thích phụ thuộc deployment strategy, dữ liệu và downtime chấp nhận. Với hệ thống rolling/blue-green và nhiều service, expand–contract thường an toàn hơn thay đổi phá vỡ hợp đồng cùng lúc.

### 9.2. Expand — thêm cột mới có tính tương thích

~~~sql
ALTER TABLE customers
ADD COLUMN display_name VARCHAR(200);
~~~

Không đặt NOT NULL ngay nếu hiện có rows chưa có giá trị. Database vẫn phục vụ phiên bản app cũ vì full_name chưa bị xóa.

### 9.3. Bridge — phiên bản ứng dụng tạm thời

Trong giai đoạn chuyển đổi, ứng dụng có thể:

- Đọc display_name nếu có, fallback full_name.
- Ghi cả full_name và display_name cho dữ liệu mới/sửa, nếu cần duy trì app cũ.
- Dùng trigger hoặc cơ chế đồng bộ được review khi writes đến từ nhiều nguồn.

Không được mặc định dual-write luôn an toàn. Nếu cả hai cột có thể được cập nhật độc lập, cần xác định **quy tắc nguồn ưu tiên, thứ tự ghi và xử lý conflict**. Dual-write thường chỉ là giai đoạn tạm thời có endpoint/telemetry rõ ràng.

### 9.4. Backfill dữ liệu cũ

~~~sql
UPDATE customers
SET display_name = full_name
WHERE display_name IS NULL;
~~~

Với bảng nhỏ, một UPDATE có thể chấp nhận. Với bảng hàng chục triệu rows, UPDATE toàn bảng có thể tạo WAL lớn, lock/bloat, long transaction và replication lag. Khi đó nên backfill theo batch:

~~~sql
UPDATE customers
SET display_name = full_name
WHERE id >= :from_id
  AND id < :to_id
  AND display_name IS NULL;
~~~

Các tham số :from_id/:to_id là ký hiệu minh họa cho một backfill job dùng parameter binding, không phải script Flyway SQL thuần sẽ tự bind. Nếu backfill chạy ngoài migration, cần cơ chế progress checkpoint, retry, idempotency và monitoring.

### 9.5. Contract — chỉ khi app cũ không còn dùng cột cũ

Sau khi dữ liệu được backfill và write path mới ổn định:

~~~sql
ALTER TABLE customers
ALTER COLUMN display_name SET NOT NULL;
~~~

Cuối cùng, trong release tách biệt và sau khi đã xác minh không còn reader/writer cũ:

~~~sql
ALTER TABLE customers
DROP COLUMN full_name;
~~~

Không gộp các bước phá vỡ hợp đồng vào một migration chạy trước khi phiên bản ứng dụng cũ được thay thế. Drop column thường khó rollback nếu không có bản sao/backup dữ liệu.

## 10. Thêm NOT NULL, default và constraint an toàn

Với một bảng đang có hàng, thêm cột bắt buộc không thể chỉ viết:

~~~sql
ALTER TABLE purchase_orders
ADD COLUMN source VARCHAR(32) NOT NULL;
~~~

Nếu bảng không rỗng và database không có giá trị cho rows hiện hữu, migration có thể lỗi.

### 10.1. Quy trình phổ biến

1. Thêm source dạng nullable.
2. Deploy code ghi source cho mọi order mới.
3. Backfill source cho orders cũ theo quy tắc nghiệp vụ.
4. Kiểm tra không còn NULL.
5. Đặt NOT NULL ở migration sau khi đã sẵn sàng.

Ví dụ:

~~~sql
ALTER TABLE purchase_orders
ADD COLUMN source VARCHAR(32);

UPDATE purchase_orders
SET source = 'LEGACY'
WHERE source IS NULL;

ALTER TABLE purchase_orders
ALTER COLUMN source SET NOT NULL;
~~~

Ba statement có thể được đặt trong các migration/release tách biệt nếu hệ thống có nhiều app versions. Với dữ liệu lớn, cần chia backfill batch và tránh khóa lâu.

### 10.2. Default ở database khác default trong Java

~~~sql
ALTER TABLE purchase_orders
ALTER COLUMN source SET DEFAULT 'WEB';
~~~

Database default áp dụng khi INSERT không cung cấp giá trị cột theo SQL semantics. Nó **không tự thay đổi** một Java field đang null trong entity object khi code chưa reload/generated-value synchronization.

~~~java
@Column(name = "source", nullable = false)
private String source = "WEB";
~~~

Đây là Java initializer cho instance được tạo qua constructor, nhưng không chứng minh mọi insert path (native/JDBC/ETL) cùng có default. Nên xác định default ở domain/app, DB, hoặc cả hai một cách có chủ đích; tránh những default mâu thuẫn nhau.

### 10.3. Constraint là trách nhiệm database

@Column(nullable=false) mô tả mapping và phục vụ schema generation; để đảm bảo DB từ chối NULL, cần NOT NULL thật trong DDL. Tương tự, @UniqueConstraint mô tả metadata, còn UNIQUE trong migration mới bảo vệ dữ liệu trước mọi writer.

Nếu dữ liệu cũ vi phạm constraint, migration thêm UNIQUE/CHECK sẽ thất bại. Phải **điều tra và sửa dữ liệu trước** khi đặt constraint mới.

## 11. Rename cột, rename bảng và thay đổi loại dữ liệu

Một thay đổi tên thuộc tính Java không nhất thiết là thay đổi schema.

### 11.1. Chỉ đổi tên Java property

Trước:

~~~java
@Column(name = "full_name")
private String fullName;
~~~

Sau:

~~~java
@Column(name = "full_name")
private String displayName;
~~~

Nếu cột vật lý vẫn full_name, database **không cần migration DDL**. Mapping Java đổi nhưng cùng đọc/ghi cột cũ. HQL/Criteria dùng attribute displayName sẽ cần cập nhật theo code.

### 11.2. Đổi tên cột vật lý

Nếu đổi từ full_name sang display_name trong DB, cần migration explicit, và nếu app cũ vẫn chạy thì phải xử lý compatibility như phần expand–contract. ORM không thể tự biết rename là ngữ nghĩa mong muốn hay cột hoàn toàn mới.

### 11.3. Chuyển kiểu dữ liệu

Ví dụ chuyển một amount VARCHAR sang NUMERIC:

~~~sql
ALTER TABLE purchase_orders
ALTER COLUMN amount_text TYPE NUMERIC(19, 2)
USING amount_text::NUMERIC(19, 2);
~~~

Không áp dụng trực tiếp nếu dữ liệu chứa các giá trị không parse được, có dấu phân tách locale, currency khác nhau hoặc precision vượt giới hạn. Cần kiểm tra dữ liệu, xác định cách chuyển đổi và chọn chiến lược online nếu bảng lớn.

Một cách an toàn hơn có thể là:

1. Thêm total_amount NUMERIC nullable.
2. Backfill bằng logic đã kiểm tra.
3. Chuyển app đọc/ghi total_amount.
4. Kiểm tra/đặt constraint.
5. Bỏ amount_text khi không còn writer.

### 11.4. Đổi precision và scale

~~~sql
ALTER TABLE purchase_orders
ALTER COLUMN total_amount TYPE NUMERIC(19, 4);
~~~

Tăng scale có thể có tác động khác giảm scale. Nếu giảm precision/scale, các giá trị hiện có có thể bị làm tròn hoặc thất bại. Đừng sửa @Column(precision=..., scale=...) rồi chỉ tin validate để bảo đảm dữ liệu đã chuyển đúng.

## 12. Enum mapping và thay đổi giá trị

Giả sử entity có:

~~~java
@Enumerated(EnumType.STRING)
@Column(name = "status", nullable = false, length = 24)
private OrderStatus status;
~~~

Và database lưu status VARCHAR(24) với CHECK:

~~~sql
ALTER TABLE purchase_orders
ADD CONSTRAINT ck_orders_status
CHECK (status IN ('DRAFT', 'PAID', 'CANCELLED'));
~~~

Nếu ứng dụng thêm REFUNDED, việc sửa enum Java **không tự sửa** CHECK constraint trong production. Migration có thể cần drop/recreate constraint hoặc điều chỉnh theo cú pháp/database hỗ trợ.

### 12.1. PostgreSQL native enum khác VARCHAR

Nếu schema dùng PostgreSQL CREATE TYPE order_status AS ENUM (...), thì migration thêm giá trị enum có cú pháp và giới hạn transaction/version riêng. Không mặc định @Enumerated(EnumType.STRING) luôn tương đương PostgreSQL native enum trong mọi Hibernate version/dialect/configuration.

### 12.2. Chuẩn bị compatibility

Nếu app mới ghi REFUNDED nhưng app cũ chưa nhận biết giá trị đó, app cũ có thể lỗi khi load enum. Migration DB cho phép giá trị mới **chưa đủ**; cần đảm bảo các phiên bản ứng dụng cùng tồn tại không bị phá vỡ.

Một chiến lược là:

1. Deploy reader hiểu giá trị mới nhưng chưa ghi giá trị mới.
2. Mở rộng database constraint/type.
3. Enable feature ghi giá trị mới.
4. Loại bỏ logic tương thích cũ khi an toàn.

Thứ tự chính xác phụ thuộc hệ thống và khả năng rollout.

## 13. Foreign key, index, sequence và các object ngoài mapping đơn giản

Hibernate mapping diễn đạt quan hệ:

~~~java
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "customer_id")
private Customer customer;
~~~

Nhưng một migration đầy đủ cần xem:

- FK có nullable hay không.
- Cách xử lý DELETE/UPDATE parent.
- Index trên FK và pattern JOIN.
- Deferrable constraint nếu workflow cần.
- Thứ tự tạo bảng/constraint khi có vòng quan hệ.
- Dữ liệu cũ có vi phạm FK hay không.

### 13.1. Foreign key không tạo index tự động ở mọi DB

Ví dụ PostgreSQL không mặc định tạo index ở cột **referencing FK** chỉ vì có FK constraint. Nếu truy vấn liên kết hoặc xóa parent dựa trên customer_id, có thể cần:

~~~sql
CREATE INDEX idx_orders_customer_id
ON purchase_orders(customer_id);
~~~

Hãy xác nhận index chưa được bao phủ bởi index phù hợp khác và đánh giá plan/chi phí ghi.

### 13.2. Sequence và identity phải đồng bộ

Nếu entity:

~~~java
@GeneratedValue(strategy = GenerationType.SEQUENCE,
                generator = "order_id_seq_gen")
@SequenceGenerator(
    name = "order_id_seq_gen",
    sequenceName = "purchase_order_id_seq",
    allocationSize = 50
)
private Long id;
~~~

thì database phải có sequence tương ứng và cấu hình phù hợp với cách Hibernate cấp ID. Allocation size/optimizer và sequence increment không nên được thay đổi tùy tiện: có thể gây vấn đề hiệu năng hoặc cấp ID khi nhiều writer/client đồng thời.

Với IDENTITY trong ví dụ trước, migration dùng BIGINT GENERATED ... AS IDENTITY. **Chọn một chiến lược ID consistent**, không coi @GeneratedValue tự tạo sequence/table khi production dùng validate.

### 13.3. ORM không mô tả hết cấu trúc PostgreSQL

Các object thường nên quản lý bằng migration có review:

- Partial/expression index.
- Materialized view và refresh policy.
- Functions/triggers/stored procedures.
- Extensions như pg_trgm.
- Check constraints nâng cao.
- Row-level security và GRANT.
- Partitioned table, partition maintenance.
- Custom type, domain và native enum.

Hibernate validate thường không kiểm tra đầy đủ những đối tượng này. Nếu chúng quan trọng cho correctness, cần migration/integration test riêng.

## 14. Migration phải được review như code

Một migration có thể hoạt động trên một database trống nhưng gây downtime trên database production đang chạy. Code review nên xem:

1. Kết quả DDL mong muốn có đúng không?
2. Migration có idempotent/được tracking đúng theo tool không?
3. Dữ liệu cũ có hợp lệ với constraint mới không?
4. Có table rewrite, full scan hoặc long lock không?
5. Ứng dụng cũ và mới có cùng hoạt động trên schema trung gian không?
6. Rollback/forward-fix là gì nếu deploy app thất bại?
7. Backfill cần batch hoặc job riêng không?
8. Index creation có nên chạy concurrent/online không?
9. Có đổi quyền/tenant/RLS không?
10. Có log/metrics nào để quan sát quá trình triển khai không?

### 14.1. DDL không phải lúc nào cũng rollback được

PostgreSQL hỗ trợ transactional DDL với nhiều lệnh, nhưng không phải tất cả. Ví dụ:

~~~sql
CREATE INDEX CONCURRENTLY idx_orders_created
ON purchase_orders(created_at);
~~~

CREATE INDEX CONCURRENTLY không được chạy trong transaction block thông thường. Migration tool cần cấu hình thực thi non-transactional cho migration phù hợp theo phiên bản, và phải có kế hoạch khi lệnh thất bại để lại index invalid hoặc trạng thái dở dang.

Đừng chỉ gắn một annotation @Index rồi mong Hibernate chọn online index creation phù hợp production.

### 14.2. Lock timeout và statement timeout

Một ALTER TABLE có thể cần lock loại mạnh và chờ các transaction đang mở. Trên database bận, việc chờ lock lâu có thể tạo hàng dài request bị chặn. Khi cần, cấu hình:

~~~sql
SET lock_timeout = '5s';
~~~

Hoặc statement timeout/trình tự retry theo quy trình DB. Con số 5 giây chỉ minh họa; giá trị phải dựa trên SLA và môi trường. Một migration bị timeout phải được phát hiện để pipeline dừng, không âm thầm tiếp tục deploy ứng dụng kỳ vọng cột mới.

### 14.3. DDL chạy trước hay sau ứng dụng mới?

Với các thay đổi **expand-compatible**, có thể chạy migration trước rồi deploy app. Với các thay đổi **contract**, cần đợi app cũ hoàn toàn rời khỏi production. Không có một câu trả lời “migration trước app” tuyệt đối đúng cho mọi thay đổi; đúng hơn là **migration và app phải được triển khai theo ma trận tương thích của từng giai đoạn**.

## 15. Migration history và checksum

Flyway thường lưu thông tin migrations đã áp dụng trong flyway_schema_history, gồm version, script, checksum, thời điểm và trạng thái (chi tiết cột phụ thuộc version).

### 15.1. Không sửa nội dung migration đã chạy

Giả sử V3__add_display_name.sql đã áp dụng lên staging và production. Nếu developer chỉnh sửa nội dung V3 trong Git, Flyway validate có thể phát hiện checksum không khớp. Lỗi đó có giá trị: lịch sử được áp dụng không còn giống lịch sử trong code.

**Quy tắc thực hành:** migration đã phát hành là immutable; nếu cần sửa schema tiếp, tạo migration mới V4/V5 với thay đổi bổ sung.

Không sửa migration cũ chỉ để “môi trường dev từ đầu nhìn đẹp hơn”, vì production đã có lịch sử V3 ban đầu.

### 15.2. Repeatable migrations

Flyway có cơ chế repeatable migrations cho đối tượng cần cập nhật lại khi nội dung thay đổi, ví dụ một view hoặc function. Chúng có semantics khác với versioned migrations.

Không dùng repeatable migration thay cho các thao tác ALTER TABLE có dữ liệu bền vững nếu mục tiêu là một chuỗi chuyển đổi có thứ tự, có thể audit. Chọn loại migration theo tính chất đối tượng.

### 15.3. Repair không phải cách sửa sai tùy tiện

Flyway repair có thể điều chỉnh metadata lịch sử hoặc xử lý một số trạng thái lỗi theo semantics/version. Không chạy repair để xóa bỏ checksum mismatch mà không hiểu:

- Schema thật đã ở trạng thái nào?
- SQL nào đã chạy và có commit không?
- Có migration bị áp dụng một phần không?
- Repo Git và lịch sử database khác nhau ở đâu?

Repair có thể làm mất tín hiệu drift nếu dùng như một nút “bỏ qua lỗi”. Cần lưu log, phê duyệt và ghi nhận incident khi sử dụng trên production.

## 16. Đưa database hiện có vào quản lý migration: baseline

Một ứng dụng cũ có thể đã chạy nhiều năm, schema được tạo thủ công hoặc qua Hibernate update, nhưng chưa có Flyway/Liquibase history.

Không thể chỉ thêm V1__create_everything.sql rồi chạy trên database đã có toàn bộ bảng: CREATE TABLE có thể lỗi vì objects tồn tại.

Một quy trình baseline có thể gồm:

1. Kiểm kê schema thực tế: tables, constraints, indexes, sequences, views, triggers.
2. Xác định **version baseline** và trạng thái DB tương ứng.
3. Tạo migrations đầy đủ để **database mới** có thể dựng đúng schema.
4. Gắn dấu baseline cho database hiện có sau khi đã xác minh nó khớp phiên bản đã chọn.
5. Mọi thay đổi sau baseline chạy qua migrations mới.
6. Kiểm thử cả đường dựng database mới lẫn nâng cấp database cũ.

### 16.1. Cẩn thận với baselineOnMigrate

Một số Flyway configuration cho phép baseline-on-migrate. Nếu bật không kiểm soát và trỏ nhầm database đã có schema khác, có nguy cơ đánh dấu baseline mà không chứng minh schema thật đúng.

Chỉ baseline khi đã xác thực đối tượng, version và trạng thái database. Không dùng baseline như một cách tự động bỏ qua lỗi “table already exists” trong production.

### 16.2. Baseline không thay thế schema diff

Một DB có đủ bảng nhưng thiếu FK, unique constraint hoặc index quan trọng vẫn có thể tương thích một phần với entity. Nếu baseline nó mà không kiểm kê, lịch sử migration về sau sẽ giả định những đối tượng đó tồn tại. Cần kiểm tra schema thực, không chỉ Hibernate validate pass.

## 17. Schema drift: database thật khác lịch sử được quản lý

Schema drift xảy ra khi:

- DBA sửa cấu trúc trực tiếp mà không tạo migration.
- Hibernate update chạy ở một môi trường nhưng không chạy ở môi trường khác.
- Một migration bị sửa sau khi đã áp dụng.
- Team chạy SQL thủ công rồi quên version-control.
- Test DB được tạo bằng hbm2ddl, production tạo bằng migration.
- Migration được đánh dấu đã chạy nhưng thực thi/rollback không như kỳ vọng.

### 17.1. Hai loại kiểm tra khác nhau

**Migration validation** kiểm tra lịch sử migration và những thay đổi đã/đang được tool quản lý.

**Hibernate schema validation** kiểm tra một phần tương thích giữa entity mapping và database hiện tại.

Chúng bổ sung, không thay thế nhau.

~~~text
Migration history đúng
    ≠ mọi constraint/index đang đúng

Hibernate validate pass
    ≠ schema không drift

Cả hai pass
    ≠ logic data migration đã đúng
~~~

### 17.2. Cần kiểm tra thêm gì?

Với những đối tượng trọng yếu, có thể kiểm tra PostgreSQL catalogs hoặc dùng schema diff tooling:

- Có UNIQUE(customer.email) không?
- Có index hỗ trợ tra cứu thường xuyên không?
- FK có ON DELETE policy đúng không?
- CHECK constraint có đúng tập enum/giới hạn tiền không?
- Có default, trigger, RLS policy và GRANT cần thiết không?
- Có extension/function/view đúng phiên bản không?

Một bài kiểm thử integration có thể cố INSERT dữ liệu vi phạm UNIQUE/CHECK và assert database từ chối, thay vì chỉ kiểm tra entity validation.

## 18. Quyền truy cập DB: tách migrator khỏi runtime application

Trong local development, dùng một tài khoản có quyền CREATE/ALTER có thể tiện. Trong production, một mô hình vận hành an toàn hơn:

~~~mermaid
flowchart LR
    A[CI/CD migration job] --> B[(PostgreSQL)]
    C[Runtime application] --> B
    D[Migration credential: DDL] --> A
    E[Application credential: DML] --> C
~~~

Ý tưởng:

- **Migration role:** có quyền CREATE/ALTER/DROP phù hợp trong schema được phép, chạy qua pipeline/DBA process.
- **Application role:** quyền SELECT/INSERT/UPDATE/DELETE cần cho nghiệp vụ, không có quyền DDL rộng.
- **Read-only/reporting role:** chỉ quyền đọc cần thiết khi phù hợp.

### 18.1. Vì sao tách quyền quan trọng?

Nếu runtime ứng dụng có quyền DROP toàn schema, một cấu hình nhầm ddl-auto=create-drop hoặc lỗi bảo mật có thể gây thiệt hại lớn. Role tối thiểu giới hạn blast radius.

Một kịch bản:

~~~text
Release job: Flyway migrate bằng credential DDL
    ↓
Hibernate validate và smoke test
    ↓
Ứng dụng chạy bằng credential DML
~~~

Nếu app chỉ có DML role thì đừng cấu hình Flyway auto-migrate trên mọi app startup dùng chính datasource credential đó; migration có thể thất bại vì thiếu quyền. Chọn một cơ chế triển khai nhất quán.

### 18.2. Tên schema và search_path

PostgreSQL có thể có nhiều schema, ví dụ public, sales, audit. @Table(schema="sales") và SQL migration CREATE TABLE sales.purchase_orders cần thống nhất. Search_path, default schema và Hibernate naming strategy có thể gây lỗi nếu DB tool tạo object ở một schema nhưng ORM tìm ở schema khác.

Khi có nhiều schema, cấu hình Flyway/Liquibase schema history location và target schemas có chủ đích; không dựa vào search_path mặc định khác nhau giữa local và production.

## 19. Nhiều service dùng cùng một database: ai sở hữu bảng?

Trong microservices, hai app có thể cùng kết nối một PostgreSQL instance, thậm chí cùng schema. Nếu mỗi service có Hibernate update hoặc Flyway migration riêng sửa cùng bảng, rất dễ xung đột.

### 19.1. Bảng sở hữu rõ

Ví dụ:

~~~text
Customer service sở hữu customers
Order service sở hữu purchase_orders, order_items
Reporting service chỉ đọc qua view/contract được công bố
~~~

Mỗi bảng/schema nên có một team hoặc dịch vụ chịu trách nhiệm thay đổi cấu trúc. Những consumer khác cần API, event, view hoặc read model phù hợp; không tự ALTER bảng thuộc service khác.

### 19.2. Shared database trong monolith

Nếu các module trong cùng một monolith chia sẻ schema, có thể có **một migration stream** có thứ tự toàn cục. Code owners/reviewers cho từng vùng bảng vẫn có thể phân chia trách nhiệm, nhưng migration ordering và lịch sử phải nhất quán.

### 19.3. Separate migration streams

Nếu nhiều services thật sự sở hữu nhiều schemas độc lập, mỗi service có thể có migration history, credentials và default schema riêng. Nhưng phải định nghĩa dependency và tránh hai streams thay đổi một object chung.

Đừng để Flyway của Service A tự làm V5 trên bảng Orders trong khi Liquibase của Service B cũng đang sửa bảng đó theo một lịch sử khác, trừ khi có một cơ chế phối hợp cực kỳ rõ ràng.

## 20. Multi-tenant database và migration

Hibernate hỗ trợ nhiều mô hình multi-tenancy: discriminator/tenant column, separate schema hoặc separate database. Cách sở hữu DDL khác nhau theo mô hình.

### 20.1. Shared schema, tenant_id

Tất cả tenant dùng cùng tables, ví dụ purchase_orders(tenant_id,...). Một migration stream tạo/sửa schema chung. Nhưng các migration phải cẩn thận với dữ liệu tenant và constraints:

~~~sql
CREATE UNIQUE INDEX uk_external_order_per_tenant
ON purchase_orders(tenant_id, external_order_number);
~~~

Không dùng UNIQUE(external_order_number) toàn hệ thống nếu business chỉ cần unique theo tenant.

### 20.2. Separate schema per tenant

Mỗi tenant có schema riêng. Một migration cần được thực hiện cho mọi schema tương ứng, hoặc theo quy trình onboarding tenant mới. Phải quản lý:

- Tenant schema nào đã ở migration version nào?
- Nếu tenant migration thứ 37 lỗi thì pipeline dừng ở đâu?
- Có nhiều app versions truy cập các schema khác version không?
- Làm thế nào retry không gây duplicate DDL?
- Schema history được lưu ở đâu cho từng tenant?

Hibernate validate trên một tenant schema không chứng minh **mọi tenant schemas** đã migrate đúng. Cần orchestration và monitoring riêng.

### 20.3. Separate database per tenant

Migration có thể cần chạy trên nhiều database độc lập. Cần credential, rate limit, batching và báo cáo version cho từng DB. Không khởi động hàng nghìn migrations không kiểm soát từ mọi app instance.

## 21. Lock, concurrency và nhiều app instances cùng migrate

Khi deploy 5 app replicas cùng lúc, nếu tất cả tự chạy migration khi startup, migration tool thường có cơ chế khóa/coordination để tránh thực thi cùng migration song song. Tuy nhiên điều đó không có nghĩa cách triển khai là tối ưu.

### 21.1. Kịch bản nhiều node

~~~text
Node A starts -> acquires migration lock -> runs V12
Node B starts -> waits for migration lock
Node C starts -> waits
V12 commits -> B/C validate history -> proceed
~~~

Hành vi cụ thể phụ thuộc Flyway/Liquibase/database/version. Nếu migration dài, các node có thể bị trì hoãn readiness hoặc timeout. Nếu một migration fail, deployment phải dừng chứ không để node khác tiếp tục chạy app mới với schema chưa đúng.

### 21.2. Tách migration job khỏi app rollout

Ở production nhiều node, thường cân nhắc:

1. Deploy một migration job có quyền DDL.
2. Chờ kết quả thành công và validate history.
3. Deploy app mới bằng role DML.
4. App bootstrap Hibernate validate.
5. Đánh giá readiness và rollout dần.

Nhưng **expand–contract vẫn phải được tuân thủ** nếu app cũ và mới cùng hoạt động. Một migration job chạy thành công không có nghĩa mọi thay đổi breaking được phép chạy trước app mới.

## 22. Kiểm thử migration và ORM mapping bằng PostgreSQL thật

Một lỗi thường gặp là unit/integration test dùng H2 với ddl-auto=create-drop, trong khi production dùng PostgreSQL và Flyway. Khi đó test bỏ qua chính đường triển khai quan trọng nhất.

### 22.1. Hướng kiểm thử nên ưu tiên

Testcontainer PostgreSQL tạm:

~~~text
PostgreSQL container trống
    ↓
Flyway chạy V1..Vn
    ↓
Hibernate ddl-auto=validate
    ↓
Tạo entity, persist, query, update
    ↓
Kiểm tra constraints/index/schema behavior quan trọng
~~~

Cách này xác minh migration scripts **có thể tự dựng một DB mới** và entity hiện tại tương thích DB đó.

### 22.2. Dependencies test minh họa

~~~kotlin
dependencies {
    testImplementation("org.springframework.boot:spring-boot-starter-test")
    testImplementation("org.testcontainers:junit-jupiter")
    testImplementation("org.testcontainers:postgresql")
}
~~~

Các phiên bản Testcontainers có thể chuyển artifact/naming conventions giữa các major versions. Cần dùng bộ dependency tương thích Spring Boot/Testcontainers của dự án.

### 22.3. Integration test skeleton

~~~java
import org.junit.jupiter.api.Test;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.test.context.DynamicPropertyRegistry;
import org.springframework.test.context.DynamicPropertySource;
import org.testcontainers.containers.PostgreSQLContainer;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;

@Testcontainers
@SpringBootTest
class MigrationAndHibernateMappingIT {
    @Container
    static PostgreSQLContainer<?> postgres =
        new PostgreSQLContainer<>("postgres:16")
            .withDatabaseName("shop_test")
            .withUsername("test")
            .withPassword("test");

    @DynamicPropertySource
    static void datasource(DynamicPropertyRegistry registry) {
        registry.add(
            "spring.datasource.url", postgres::getJdbcUrl);
        registry.add(
            "spring.datasource.username", postgres::getUsername);
        registry.add(
            "spring.datasource.password", postgres::getPassword);
        registry.add(
            "spring.jpa.hibernate.ddl-auto", () -> "validate");
        registry.add(
            "spring.flyway.enabled", () -> "true");
    }

    @Test
    void contextStartsWithMigratedSchema() {
        // Nếu Flyway migration hoặc Hibernate validate thất bại,
        // Spring context không khởi động thành công.
    }
}
~~~

Ví dụ chỉ kiểm tra bootstrap. Đối với migration quan trọng, cần thêm test persist/query, constraint violation và readback dữ liệu. Các image database và artifact version phải được quản lý theo môi trường CI; không mặc định một image PostgreSQL bất kỳ đại diện production.

### 22.4. Test database nâng cấp từ schema cũ

Test database trống **chưa đủ**. Cần cả:

~~~text
DB tại version Vn-1, có dữ liệu thật đại diện
    ↓
Chạy Vn và các data migrations
    ↓
Kiểm tra dữ liệu được bảo toàn/chuyển đổi đúng
    ↓
Chạy app mới với Hibernate validate
~~~

Một SQL CREATE TABLE chạy tốt trên DB trống không chứng minh ALTER TABLE trên bảng có 50 triệu rows an toàn. Với hệ thống lớn, test dataset đủ lớn để đo lock/scan/write amplification hoặc có staging rehearsal theo policy.

### 22.5. Test rollback của application, không chỉ DB transaction

Thử:

1. Migration expand chạy.
2. App mới deploy thất bại.
3. Roll back app về version cũ.
4. App cũ có còn chạy trên schema đã mở rộng không?

Đây thường là mục tiêu quan trọng hơn khả năng “UNDO mọi DDL” tức thời. Với DROP COLUMN phá hủy dữ liệu, không thể giả định rollback SQL đơn giản sẽ khôi phục được thông tin.

## 23. CI/CD workflow mẫu

Một pipeline cho code và schema:

~~~mermaid
flowchart TD
    A[Pull request: code + migration] --> B[Review entity và DDL]
    B --> C[Flyway/Liquibase validate history]
    C --> D[PostgreSQL test container mới]
    D --> E[Apply tất cả migrations]
    E --> F[Hibernate schema validate]
    F --> G[Integration tests và constraint tests]
    G --> H[Test upgrade từ DB version trước]
    H --> I[Phê duyệt rollout và backout plan]
    I --> J[Migration job production]
    J --> K[Deploy app tương thích]
    K --> L[Quan sát readiness và metrics]
~~~

### 23.1. Review pull request nên chứa gì?

Một PR thêm field Customer.displayName nên có:

- Entity/DTO/service change nếu cần.
- Migration mới thêm cột, không chỉnh migration đã áp dụng.
- Backfill nếu dữ liệu cũ cần giá trị.
- Constraints/index hợp lý với query mới.
- Test từ DB trống và upgrade từ DB cũ.
- Mô tả compatibility với phiên bản app trước.
- Phương án rollback/forward-fix.

Nếu chỉ có Java field mới mà thiếu migration, CI có thể phát hiện khi chạy validate trên DB dựng từ migrations.

### 23.2. Các chốt chặn deployment

Không tiếp tục deploy app kỳ vọng schema mới khi:

- Migration validation/checksum fail.
- Migration DDL fail giữa chừng.
- Hibernate validate fail.
- Constraint test thiết yếu fail.
- Migration còn pending do quyền hoặc lock.
- Schema thực tế khác giả định release.

Khi một bước fail, dừng rollout và điều tra, không tự đổi ddl-auto thành update để ứng dụng “chạy được”.

## 24. Khi migration thất bại: rollback hay forward-fix?

Không có một cơ chế rollback chung cho mọi DDL. Cần phân biệt:

### 24.1. Migration transaction chưa commit

Nếu database và migration tool chạy DDL trong transaction có thể rollback, một lỗi có thể làm toàn transaction rollback. Tuy nhiên một số DDL không transactional, hoặc migration có side effects ngoài DB; phải kiểm tra trạng thái thật sau lỗi.

### 24.2. Migration đã commit

Một migration đã thành công nhưng ứng dụng mới lỗi không có nghĩa bắt buộc phải DROP schema ngay. Nếu thay đổi expand backward-compatible, thường có thể rollback app và giữ schema mới. Đây là lý do expand–contract hữu ích.

### 24.3. DDL phá hủy dữ liệu

Nếu đã DROP COLUMN chứa dữ liệu và không có bản sao/backup, không có lệnh “undo” thần kỳ để khôi phục dữ liệu. Cần chiến lược backup/restore hoặc giữ cột cũ qua nhiều release. Production migrations nên ưu tiên **forward-fix** khi phù hợp, nhưng quyết định phải dựa trên mức độ sự cố, backup, thời gian downtime và yêu cầu consistency.

### 24.4. Backup và restore phải được thử

Có backup không đồng nghĩa restore luôn thành công trong thời gian SLA. Với migration rủi ro cao, kiểm tra khả năng restore, point-in-time recovery, dung lượng, thời gian và quy trình kiểm soát truy cập. Không tạo migration phá hủy dữ liệu dựa trên một câu “chúng ta có backup” mà chưa được chứng minh.

## 25. Dữ liệu seed, reference data và data migrations

Không phải mọi thay đổi dữ liệu cần được thực hiện qua ORM startup.

### 25.1. Reference data có phiên bản

Ví dụ hệ thống cần bảng payment_methods chứa các mã cố định. Nếu dữ liệu này là một phần hợp đồng DB, migration có thể seed:

~~~sql
INSERT INTO payment_methods(code, display_name)
VALUES
    ('CASH', 'Tiền mặt'),
    ('BANK', 'Chuyển khoản');
~~~

Với database đã có dữ liệu, cần biết seed có thể chạy lại không, làm gì khi row đã tồn tại và ai được quyền sửa display_name. Flyway versioned migration được theo dõi lịch sử nên thường chỉ chạy một lần; nó không phải job chạy mỗi startup một cách độc lập.

### 25.2. Không dùng CommandLineRunner thay migration một cách mơ hồ

Một runner Java tự tạo bảng/dữ liệu lúc app khởi động có thể race với các app replicas, bỏ qua migration history và chạy khi DB permission không phù hợp. Nếu thật sự cần bootstrap runtime data, phải phân biệt rõ với schema migration và đảm bảo idempotency, transaction, quyền và orchestration.

### 25.3. Data backfill có thể cần job riêng

Backfill 100 triệu rows bằng một migration transaction rất dài có thể gây lock, WAL/replication lag và quá tải. Một workflow an toàn có thể:

1. Migration expand thêm cột.
2. App dual-write.
3. Backfill job theo batch có checkpoint.
4. Kiểm tra tỷ lệ hoàn thành và consistency.
5. Migration contract đặt constraint/xóa cột cũ.

Lịch sử DB migrations phải ghi nhận chính xác giai đoạn schema, còn job backfill cần audit/monitoring riêng. Không coi migration “finished” là bằng chứng data backfill async đã xong.

## 26. SQL initialization của Spring Boot không thay thế Flyway/Liquibase

Spring Boot còn hỗ trợ schema.sql và data.sql thông qua SQL initialization. Đây là một cơ chế khác với Hibernate DDL và với Flyway/Liquibase.

Trong production, tránh để đồng thời:

~~~text
schema.sql tự tạo bảng
Hibernate ddl-auto=update tự sửa bảng
Flyway chạy versioned migrations
Liquibase chạy changeSets
~~~

Nếu cùng target database, các cơ chế có thể va chạm. Hãy chọn migration tool làm nơi quản lý schema và sử dụng data.sql/schema.sql chỉ khi có ranh giới sử dụng rõ, ví dụ test context đặc biệt.

### 26.1. defer-datasource-initialization không phải giải pháp tổng quát

Spring Boot có thuộc tính liên quan đến thứ tự chạy SQL initialization so với JPA, chẳng hạn defer-datasource-initialization. Nó phục vụ một số workflow dùng Hibernate tạo schema rồi data.sql nạp dữ liệu. Trong ứng dụng đã chọn Flyway/Liquibase sở hữu DDL, không bật thuộc tính này để “sửa thứ tự” một cách máy móc; hãy tổ chức initialization qua migration đúng cơ chế.

### 26.2. Một bộ cấu hình rõ ràng cho staging/prod

~~~yaml
spring:
  flyway:
    enabled: true
    locations: classpath:db/migration
  jpa:
    hibernate:
      ddl-auto: validate
  sql:
    init:
      mode: never
~~~

Ví dụ trên dùng Flyway migration trước khi Hibernate validate, không dùng schema.sql/data.sql tự chạy. Nếu production dùng migration job tách biệt, có thể tắt Flyway auto-migrate trong app production và để pipeline migrate trước; lúc đó giữ Hibernate validate.

## 27. Các lỗi thường gặp và cách nhận biết

| Triệu chứng | Nguyên nhân thường gặp | Cách xử lý |
|---|---|---|
| Startup báo missing table/column | Code mới chờ DDL chưa chạy | Kiểm tra migration history và thứ tự bootstrap |
| Schema trên dev khác staging | Dev dùng ddl-auto=update | Dựng lại DB dev từ migrations, bỏ auto-update |
| Flyway báo checksum mismatch | Đã chỉnh migration đã chạy | Không sửa lịch sử; điều tra rồi tạo migration mới |
| CREATE TABLE báo already exists | DB chưa baseline nhưng đã có schema | Kiểm kê schema và baseline có kiểm soát |
| Hibernate validate pass nhưng query chậm | Missing index không được validate đầy đủ | EXPLAIN/DB catalog/migration index |
| Thêm @UniqueConstraint nhưng DB vẫn có duplicate | Annotation không chạy DDL khi validate | Migration unique + làm sạch dữ liệu |
| Đổi @Column name làm ứng dụng lỗi | Chưa migrate hoặc app cũ chưa tương thích | Expand–contract hoặc đồng bộ rollout |
| Hibernate update thêm cột mới thay vì rename | Tool không suy luận được ý định đổi tên | Viết ALTER RENAME/backfill migration |
| Thêm NOT NULL thất bại | Dữ liệu cũ có NULL | Expand nullable, backfill, contract |
| App cũ lỗi trong rolling deployment | DDL breaking chạy quá sớm | Thiết kế compatibility window |
| Index creation gây timeout | Lock/scan trên bảng lớn | Đánh giá online/concurrent approach và scheduling |
| Multi-node startup bị kẹt migration | Nhiều replicas cùng migrate hoặc migration dài | Tách migration job, kiểm tra lock/timeout |
| App production không có quyền CREATE | Runtime dùng role DML như mong muốn nhưng còn auto-migrate | Chuyển DDL sang deploy role/job |
| SQL đổi cột nhưng entity vẫn tên cũ | Mapping chưa cập nhật | Cập nhật @Column/association theo schema mới |
| Native enum/CHECK từ chối giá trị mới | Migration constraint/type thiếu | Migration tương ứng trước khi ghi giá trị mới |
| DB được DBA sửa tay rồi migration lỗi | Schema drift | Audit và reconcile bằng migration có lịch sử |
| Test H2 pass nhưng Postgres fail | DDL/dialect/typing khác | Test migration với PostgreSQL Testcontainers |
| Bật schema.sql + Flyway gây duplicate objects | Hai nguồn tạo schema | Chọn một owner và tắt initialization thừa |
| “Rollback” không lấy lại dữ liệu đã drop | DDL phá hủy dữ liệu | Backup/restore/forward-fix và lộ trình contract an toàn |

## 28. Thực hành theo từng mức độ

### Bài A — Phân biệt owner và mapping

1. Tạo Customer entity trong một project Spring Boot.
2. Chạy thử ddl-auto=create-drop trên PostgreSQL **disposable**.
3. Quan sát SQL Hibernate sinh ra.
4. Chuyển DDL đó thành một Flyway V1 có PK/UNIQUE hợp lệ.
5. Đổi ddl-auto sang validate.
6. Chạy từ DB trống, xác nhận Flyway tạo schema và Hibernate validate.
7. Sửa @Column để mong một cột chưa có migration; xác nhận validate fail.

### Bài B — Thêm trường vào bảng có dữ liệu

1. Tạo V1 với Customer.full_name.
2. Insert vài hàng có dữ liệu.
3. Viết V2 thêm display_name nullable.
4. Viết backfill dữ liệu cũ.
5. Chỉnh app để đọc display_name/fallback hợp lý.
6. Chỉ đặt NOT NULL sau khi dữ liệu đã sẵn sàng.
7. Thử rollback app về version trước mà không rollback DDL expand.

### Bài C — NOT NULL và UNIQUE

1. Tạo vài Customer có email trùng để mô phỏng dữ liệu bẩn.
2. Viết migration thêm unique constraint.
3. Quan sát migration fail.
4. Viết kế hoạch deduplicate dữ liệu.
5. Chạy constraint migration khi dữ liệu hợp lệ.
6. Kiểm tra database từ chối INSERT trùng từ JDBC, không chỉ từ Hibernate.

### Bài D — Rename và rolling deploy

1. Giả lập app v1 đọc full_name.
2. Viết migration rename trực tiếp sang display_name.
3. Xác nhận v1 không còn tương thích.
4. Thiết kế expand–bridge–backfill–contract.
5. Test v1/v2 cùng hoạt động trên schema expand.
6. Chỉ DROP full_name sau khi không còn app cũ.

### Bài E — Migration history

1. Dùng Flyway V1/V2/V3 theo đúng tên.
2. Chạy migrations lần đầu, xem flyway_schema_history.
3. Khởi động lại, xác nhận không chạy lại V1/V2/V3.
4. Sửa thử một migration đã áp dụng trong nhánh test, quan sát validation checksum.
5. Khôi phục nội dung, tạo V4 thay đổi mới.
6. Giải thích vì sao không dùng repair để che mismatch.

### Bài F — PostgreSQL-specific schema

1. Tạo index trên customer_id và created_at phù hợp query.
2. Dùng EXPLAIN ANALYZE kiểm tra query trước/sau.
3. Thử partial index cho deleted_at IS NULL trên DB test.
4. Xem tác động tạo index trên bảng nhiều rows.
5. Phân biệt CREATE INDEX CONCURRENTLY với DDL chạy trong transaction.
6. Ghi rõ index không được Hibernate validate chứng minh đầy đủ.

### Bài G — CI, môi trường và quyền

1. Tạo role migration riêng, role app chỉ có DML tối thiểu.
2. Chạy migration job bằng role DDL.
3. Khởi động app bằng role DML với ddl-auto=validate.
4. Test thiếu migration làm app không khởi động.
5. Test chuyển từ DB Vn-1 có dữ liệu sang Vn.
6. Thử hai app instances khởi động đồng thời theo chiến lược deploy đã chọn.
7. Viết bản kế hoạch rollback/forward-fix cho một DDL thay đổi cột.

## 29. Checklist kỹ thuật cho một pull request thay đổi schema

Trước khi merge hoặc deploy:

1. **Ai sở hữu DDL của table/schema này?** Không có hai sources cùng ALTER tự động.
2. **Migration mới có được version-control không?** Không chỉnh scripts đã chạy production.
3. **ORM mapping có đồng bộ tên bảng/cột, type, id generation và association không?**
4. **Có dữ liệu cũ không?** Null, duplicate, invalid enum và precision được xử lý thế nào?
5. **Thay đổi có breaking với app đang chạy không?** Cần expand–contract không?
6. **Constraint và index có được tạo bằng migration thật không?**
7. **Có write path ngoài ORM không?** ETL/JDBC/native SQL có bị ảnh hưởng không?
8. **Có data backfill lớn không?** Nếu có, batch, checkpoint và rollback plan là gì?
9. **DDL có lấy lock mạnh hoặc cần CREATE INDEX CONCURRENTLY không?**
10. **Migration transaction/timeout/lock handling đã được xác định chưa?**
11. **Flyway/Liquibase history và checksum hợp lệ chưa?**
12. **Hibernate validate có pass sau khi migrate DB trống không?**
13. **Upgrade từ DB có dữ liệu version trước đã được test chưa?**
14. **Đã test constraints quan trọng trực tiếp ở database chưa?**
15. **Tên schema/search_path/multi-tenant configuration có nhất quán không?**
16. **Production app có DML-only credential khi cần không?**
17. **Migration triển khai trước/sau app theo compatibility matrix chưa?**
18. **Có monitoring, backup, forward-fix và phương án rollback app rõ ràng không?**

## 30. Tổng kết: một nguồn thay đổi schema, hai bên cùng chịu trách nhiệm

Sơ đồ tư duy:

~~~mermaid
flowchart LR
    A[Entity mapping: hợp đồng Java và DB] --> B{Có cần thay đổi schema?}
    B -->|Không| C[Chỉ refactor mapping/code]
    B -->|Có| D[Migration versioned DDL]
    D --> E[Apply DB test / staging]
    E --> F[Hibernate validate + integration tests]
    F --> G[Deploy migration và app tương thích]
~~~

Những nguyên tắc quan trọng nhất:

1. **Mapping không phải migration history.** Entity mô tả Java lưu/đọc dữ liệu thế nào; migration mô tả database chuyển từ version này sang version khác.
2. **Một nguồn sở hữu DDL rõ ràng.** Flyway/Liquibase hoặc quy trình DBA có thể là nơi duy nhất triển khai thay đổi schema production.
3. **Hibernate validate là lớp kiểm tra, không phải engine thay đổi schema.** Nó chỉ kiểm tra một phần sự tương thích và không chứng minh đủ indexes/constraints/triggers.
4. **Không dùng ddl-auto=update/create/create-drop trên database có dữ liệu quan trọng.** Những chế độ này không thay thế data migration và compatibility planning.
5. **Migration có phiên bản và không sửa lịch sử đã áp dụng.** Checksum/history là công cụ phát hiện drift, không phải trở ngại cần bỏ qua.
6. **Đổi schema có dữ liệu là bài toán thời gian.** Thêm cột, backfill, chuyển readers/writers và contract nên được sắp xếp theo phiên bản ứng dụng có thể cùng tồn tại.
7. **Database constraints là lớp bảo vệ cuối cùng.** Annotation ORM không thay thế UNIQUE, NOT NULL, CHECK hoặc FK thực.
8. **Kiểm thử cả DB trống và DB nâng cấp.** Test PostgreSQL thực tế với Flyway/Liquibase và Hibernate validate giảm chênh lệch giữa CI và production.
9. **Quyền DDL và DML nên tách ở production.** Runtime không cần quyền ALTER/DROP nếu migrations do release pipeline chạy.
10. **DDL production cần chiến lược vận hành.** Lock, backfill, index, schema drift, concurrency, rollback và backup đều là phần của thiết kế.

Điểm kết luận: **ORM và migration tool không phải hai đối thủ cùng sở hữu schema**. ORM xác định hợp đồng ánh xạ mà ứng dụng yêu cầu; migration tool hoặc quy trình database kiểm soát cách hợp đồng ấy được triển khai trên dữ liệu thực, theo thứ tự có lịch sử và tương thích với các phiên bản ứng dụng. Khi ranh giới này rõ ràng, đội phát triển có thể tiến hóa mô hình Hibernate mà không biến mỗi lần khởi động ứng dụng thành một lần sửa database không dự đoán được.
