# Tập hợp lớn và dấu hiệu cần mô hình hóa thành thực thể riêng

## 1. Vì sao một collection nhỏ có thể trở thành vấn đề kiến trúc?

Trong Hibernate ORM, một entity có thể chứa collection để biểu diễn các giá trị hoặc các entity liên quan. Ví dụ, `Customer` có vài số điện thoại, `Book` có một số thể loại, `Order` có nhiều dòng hàng và `Article` có các bình luận. Khi tập hợp chỉ gồm vài phần tử và thường được dùng cùng entity cha, việc truy cập qua `customer.getPhoneNumbers()` hoặc `order.getLines()` có vẻ tự nhiên.

Vấn đề xuất hiện khi collection tăng lên vài nghìn, vài trăm nghìn hoặc hàng triệu phần tử; nhất là khi nghiệp vụ chỉ cần **một phần rất nhỏ**:

- Màn hình cần hiển thị 20 bình luận mới nhất nhưng gọi `article.getComments()` để lấy tất cả rồi cắt trang trong Java.
- Chức năng chỉ cần kiểm tra “đơn hàng có dòng SKU X không?” nhưng tải toàn bộ `order.getLines()` vào persistence context.
- Sửa một phần tử của `@ElementCollection` gây SQL cập nhật/xóa và tạo lại nhiều hàng tùy kiểu collection và mapping.
- Một aggregate có hàng vạn phần tử được cascade khi persist/merge/remove, làm transaction dài và tốn bộ nhớ.
- Tầng JSON serialization vô tình duyệt một collection lazy và kích hoạt rất nhiều truy vấn hoặc `LazyInitializationException`.

**Câu hỏi chính của bài:** khi nào một collection vẫn nên là tập hợp các giá trị thuộc entity cha, và khi nào từng phần tử cần trở thành một entity có định danh, vòng đời và thao tác riêng?

Đây là quyết định mô hình hóa, không phải chỉ đổi annotation để tối ưu SQL. Số phần tử lớn là một tín hiệu, nhưng **không có ngưỡng cố định** như “trên 100 phần tử phải dùng entity”. Cần xem cả ngữ nghĩa nghiệp vụ, truy cập, cập nhật, tính nhất quán và cách dữ liệu tăng trưởng.

## 2. Ba cách biểu diễn thường gặp

| Mô hình | Hibernate/JPA mapping phổ biến | Danh tính của từng phần tử | Vòng đời và cập nhật |
|---|---|---|---|
| Tập hợp kiểu cơ bản | `@ElementCollection Set<String>`, `List<Integer>` | Phần tử là giá trị; không có entity ID riêng | Gắn chặt với entity sở hữu; Hibernate đồng bộ qua collection |
| Tập hợp value object | `@ElementCollection List<@Embeddable>` (chú thích trên kiểu phần tử tùy mapping) | Phân biệt bằng các thuộc tính giá trị/vị trí, không có identity của entity độc lập | Được sở hữu bởi entity cha; thường sửa hoặc thay giá trị trong tập |
| Quan hệ tới entity | `@OneToMany`, `@ManyToMany` hoặc chỉ `@ManyToOne` phía con | Mỗi entity có `@Id` hoặc composite ID | Có thể truy vấn, cập nhật, phân trang và kiểm soát trạng thái từng entity |

Ví dụ ở cấp mô hình:

```text
Customer
  └─ phoneNumbers: Set<String>        → giá trị thuộc Customer

Order
  └─ shippingAddresses: List<Address> → @Embeddable value objects

Order
  └─ OrderLine(id, orderId, sku, ...)  → entity riêng có identity

Article
  └─ Comment(id, articleId, ...)       → entity riêng, truy vấn theo articleId
```

Một bảng riêng trong database **không có nghĩa** từng hàng của bảng đó phải là entity. `@ElementCollection` cũng có thể dùng collection table. Khác biệt nằm ở việc hàng đó có **identity và lifecycle độc lập trong domain/ORM** hay chỉ là một giá trị thuộc entity khác.

## 3. Value collection: sở hữu bởi entity cha

Một tập hợp nhỏ các nhãn gắn với bài viết có thể biểu diễn đơn giản:

```java
import jakarta.persistence.CollectionTable;
import jakarta.persistence.Column;
import jakarta.persistence.ElementCollection;
import jakarta.persistence.Entity;
import jakarta.persistence.FetchType;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.JoinColumn;
import jakarta.persistence.Table;
import java.util.HashSet;
import java.util.Set;

@Entity
@Table(name = "articles")
public class Article {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String title;

    @ElementCollection(fetch = FetchType.LAZY)
    @CollectionTable(
            name = "article_labels",
            joinColumns = @JoinColumn(name = "article_id"))
    @Column(name = "label", nullable = false, length = 80)
    private Set<String> labels = new HashSet<>();

    protected Article() {}

    public Article(String title) {
        this.title = title;
    }

    public Long getId() { return id; }
    public String getTitle() { return title; }

    public void addLabel(String label) {
        if (label == null || label.isBlank()) {
            throw new IllegalArgumentException("Label không hợp lệ");
        }
        labels.add(label.trim());
    }

    public void removeLabel(String label) {
        labels.remove(label);
    }
}
```

DDL minh họa:

```sql
CREATE TABLE articles (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title VARCHAR(255) NOT NULL
);

CREATE TABLE article_labels (
    article_id BIGINT NOT NULL,
    label VARCHAR(80) NOT NULL,
    CONSTRAINT pk_article_labels PRIMARY KEY (article_id, label),
    CONSTRAINT fk_labels_article
        FOREIGN KEY (article_id) REFERENCES articles(id)
);
```

Từng `label` không có `@Id` riêng và không thể gọi `entityManager.find(String.class, labelId)`. Trong mô hình này, giá trị “Hibernate” thuộc bài viết số 10 khác với giá trị “Hibernate” thuộc bài viết số 20 dù chuỗi giống nhau.

`Set<String>` diễn đạt ý nghĩa không trùng giá trị trong collection Java, và composite primary key `(article_id, label)` bảo vệ uniqueness tương ứng ở database. Với kiểu dữ liệu có collation hoặc quy tắc chuẩn hóa khác nhau giữa Java và database, vẫn cần thiết kế normalization để tránh hai tầng có cách hiểu khác nhau về “trùng”.

Ở mức vài nhãn mỗi bài viết, `@ElementCollection` thường đủ. Nhưng nếu phần tử cần có tác giả thêm nhãn, thời điểm tạo, trạng thái duyệt, quyền sửa hoặc lịch sử riêng, nó đã có các đặc điểm của một entity/association entity.

### 3.1. Một value object nhúng trong collection

`@ElementCollection` cũng có thể chứa `@Embeddable`:

```java
import jakarta.persistence.Column;
import jakarta.persistence.Embeddable;

@Embeddable
public class ContactNumber {
    @Column(name = "country_code", length = 8)
    private String countryCode;

    @Column(name = "local_number", length = 32)
    private String localNumber;

    protected ContactNumber() {}

    public ContactNumber(String countryCode, String localNumber) {
        this.countryCode = countryCode;
        this.localNumber = localNumber;
    }

    public String getCountryCode() { return countryCode; }
    public String getLocalNumber() { return localNumber; }
}
```

```java
@ElementCollection(fetch = FetchType.LAZY)
@CollectionTable(
        name = "customer_contacts",
        joinColumns = @JoinColumn(name = "customer_id"))
private List<ContactNumber> contacts = new ArrayList<>();
```

Các trường của `ContactNumber` được lưu trong collection table; object đó không có ID entity. Khi thiết kế `Set<ContactNumber>`, cần cài `equals()/hashCode()` theo giá trị và bảo đảm những thành phần ảnh hưởng tới hash không bị thay đổi khi đang nằm trong Set. Với `List` không có index mapping rõ ràng, cũng phải hiểu semantics của bag/list trong Hibernate.

**Không bắt buộc biến mọi value object thành entity.** Địa chỉ giao hàng cố định tại thời điểm đặt hàng vẫn có thể là value object rất phù hợp, kể cả khi có vài bản ghi lịch sử. Điều cần quan sát là cách đọc/sửa/lọc từng phần tử và yêu cầu identity độc lập.

## 4. “Tập hợp lớn” có những loại chi phí nào?

Khi gọi `order.getLines().size()` hoặc duyệt `order.getLines()`, hành vi thực tế phụ thuộc trạng thái khởi tạo collection, mapping và Hibernate version. Với collection lazy thông thường chưa khởi tạo, Hibernate có thể phải tải nhiều hàng về memory trước khi thao tác Java hoàn thành. Một số cơ chế riêng như extra-lazy có thể tối ưu vài thao tác, nhưng **không nên dựa vào collection API chung để giả định chỉ phát một query `COUNT(*)`**.

Có thể nhóm chi phí thành năm loại:

| Loại chi phí | Triệu chứng | Vì sao tăng |
|---|---|---|
| Số hàng trả về | Query mất nhiều thời gian, truyền dữ liệu lớn | Collection tải hàng nghìn/hàng triệu row dù UI chỉ cần vài row |
| Bộ nhớ JVM | Heap/GC tăng; request chậm dần | Entity, wrapper collection, snapshot/tracking và giá trị được materialize |
| Dirty checking/flush | Commit chậm, SQL nhiều | Hibernate cần quản lý collection snapshot và thao tác thêm/xóa/thay đổi |
| Nhiều query nhỏ | N+1, round trip lớn | Truy cập lazy collection trên từng entity cha |
| Contention/transaction | Lock lâu, deadlock, stale update | Một transaction sửa quá nhiều phần tử hoặc nhiều worker cùng sửa một aggregate |

Ví dụ 100 đơn hàng, mỗi đơn có 2.000 dòng. Nếu fetch tất cả:

```text
100 orders × 2.000 lines = 200.000 OrderLine entities

Tầng UI chỉ cần: số lượng dòng và 10 dòng gần nhất của mỗi đơn
         ↓
Tải 200.000 entity để tính và cắt trang trong Java
         ↓
Lãng phí SQL traffic, heap và persistence context
```

Các con số trên chỉ minh họa quy mô; chi phí thực tế phụ thuộc số cột, kiểu dữ liệu, fetch plan, index, JDBC driver và heap. Vấn đề không phải là `List` hay `Set` “chậm” tự thân, mà là **biên dữ liệu của một aggregate đang lớn hơn biên dữ liệu mà use case cần**.

### 4.1. Lazy loading chỉ dời chi phí, không xóa chi phí

`fetch = LAZY` giúp trì hoãn việc tải collection đến khi có code cần. Nó không làm `order.getLines()` tự động trở thành collection phân trang. Khi code thực sự duyệt toàn bộ, số lượng row phải tải vẫn rất lớn.

```java
Order order = entityManager.find(Order.class, orderId);
// Chưa chắc collection đã được tải tại đây.

for (OrderLine line : order.getLines()) {
    // Có thể kích hoạt việc tải toàn bộ collection.
    process(line);
}
```

Không nên sửa bằng cách đổi hết collection sang `EAGER`. Eager fetching khiến những thao tác chỉ cần entity cha cũng có nguy cơ kéo theo tập dữ liệu lớn.

### 4.2. Join fetch cũng có giới hạn

`JOIN FETCH` có thể giải quyết N+1 cho quan hệ cần tải trọn, nhưng fetch collection lớn làm tăng số row của câu SQL và nhân bản các cột từ entity cha trên mỗi row. Nếu join fetch đồng thời nhiều collection, số row có thể tăng theo tích số phần tử của các collection; Hibernate cũng có những giới hạn như fetch nhiều bag.

Ví dụ hai collection mỗi collection 100 phần tử có thể tạo khoảng 10.000 tổ hợp row SQL cho một entity cha nếu join đồng thời, tùy join và dữ liệu. Dùng `distinct` không làm chi phí truyền/đọc hàng nghìn row thừa biến mất.

Đặc biệt thận trọng khi dùng `setMaxResults()` hoặc `Pageable` cùng collection fetch join: việc phân trang có thể phải thực hiện trong memory hoặc bị Hibernate cảnh báo/từ chối theo cấu hình, dẫn tới kết quả và hiệu năng không mong muốn. Với collection lớn, hãy phân trang **trực tiếp entity con** hoặc dùng truy vấn hai bước phù hợp.

## 5. Dấu hiệu cần tách phần tử thành entity riêng

Có thể đặt một chuỗi câu hỏi cho mỗi collection:

| Câu hỏi | Nếu câu trả lời là “có” | Hướng thiết kế nên xem xét |
|---|---|---|
| Một phần tử cần được truy cập/cập nhật/xóa theo ID riêng? | Có identity nghiệp vụ hoặc ID kỹ thuật ổn định | Entity riêng với `@Id` |
| UI/API cần lọc, sắp xếp, phân trang phần tử? | Không phù hợp tải tất cả qua cha | Query trực tiếp bảng/entity con |
| Số phần tử tăng không giới hạn theo thời gian? | Aggregate có thể phình lớn | Tách repository/query boundary của phần tử |
| Phần tử có trạng thái và chuyển trạng thái riêng? | Có vòng đời nghiệp vụ riêng | Entity có method và transaction phù hợp |
| Phần tử cần `createdAt`, `updatedBy`, moderation, soft delete? | Dữ liệu có lịch sử/metadata riêng | Entity hoặc association entity |
| Phần tử được tham chiếu bởi entity khác? | Cần identity ổn định và FK | Entity độc lập |
| Nhiều transaction cùng sửa các phần tử khác nhau? | Có nhu cầu giảm tranh chấp ở cha | Entity riêng, khóa/version theo phần tử |
| Phải query theo thuộc tính phần tử mà không cần cha? | Có use case độc lập | Entity con và index phù hợp |
| Xóa một phần tử cần audit/retry/quyền riêng? | Lifecycle độc lập | Entity/service riêng |
| Phần tử chỉ là vài giá trị nhỏ, thay trọn cùng cha? | Không nhất thiết có identity riêng | Giữ `@ElementCollection`/`@Embeddable` |

**Không nhất thiết phải có tất cả dấu hiệu.** Chỉ riêng việc phải phân trang hàng trăm nghìn bình luận và phân quyền xóa từng bình luận thường đã đủ lý do làm `Comment` thành entity. Ngược lại, vài mã vùng bất biến của một profile có thể là value collection dù được lưu trong bảng riêng.

### 5.1. Identity quan trọng hơn cú pháp annotation

Giả sử hai địa chỉ có nội dung giống hệt nhau:

```text
"12 Nguyen Hue, District 1"
"12 Nguyen Hue, District 1"
```

Nếu đây chỉ là **giá trị địa chỉ giao hàng**, hai giá trị có thể tương đương nhau theo dữ liệu. Nếu đây là **hai yêu cầu giao hàng** khác nhau, chúng có ID, trạng thái, thời gian và người nhận riêng; dù địa chỉ trùng, hai yêu cầu không phải một thực thể.

Tách entity vì “số phần tử lớn” có thể là quyết định hợp lý về hiệu năng, nhưng mô hình domain phải trả lời rõ: **điều gì làm một phần tử là chính nó, khác với các phần tử khác?**

## 6. Case study: đơn hàng có rất nhiều dòng

Một thiết kế ban đầu có thể trông như sau:

```java
@Entity
public class Order {
    @Id
    @GeneratedValue
    private Long id;

    @OneToMany(mappedBy = "order",
            cascade = CascadeType.ALL,
            orphanRemoval = true)
    private List<OrderLine> lines = new ArrayList<>();

    public List<OrderLine> getLines() {
        return lines;
    }
}
```

Đây **đã là quan hệ tới entity riêng** nếu `OrderLine` có `@Entity` và `@Id`. Tuy nhiên, việc giữ collection lớn trên entity cha và để mọi nghiệp vụ truy cập bằng `order.getLines()` vẫn tạo rủi ro load toàn bộ.

Vì thế có **hai quyết định tách biệt**:

1. **Value hay entity?** `OrderLine` có ID và vòng đời riêng hay chỉ là một value object thuộc `Order`?
2. **Có cần collection navigation từ cha không?** Ngay cả khi `OrderLine` là entity, `Order` không bắt buộc phải khai báo `List<OrderLine> lines`. Có thể chỉ ánh xạ `OrderLine.order` và truy vấn theo `orderId`.

Với đơn hàng có hàng chục nghìn dòng, hướng thiết kế thứ hai thường cho khả năng kiểm soát truy vấn tốt hơn.

### 6.1. Thiết kế bảng

Ví dụ PostgreSQL:

```sql
CREATE TABLE orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    status VARCHAR(32) NOT NULL,
    version BIGINT NOT NULL DEFAULT 0
);

CREATE TABLE order_lines (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL,
    line_number INTEGER NOT NULL,
    sku VARCHAR(64) NOT NULL,
    quantity INTEGER NOT NULL,
    unit_price NUMERIC(18, 2) NOT NULL,
    CONSTRAINT fk_order_lines_orders
        FOREIGN KEY (order_id) REFERENCES orders(id),
    CONSTRAINT uq_order_lines_number
        UNIQUE (order_id, line_number),
    CONSTRAINT ck_order_lines_quantity
        CHECK (quantity > 0)
);

CREATE INDEX idx_order_lines_order_id_id
    ON order_lines (order_id, id);

CREATE INDEX idx_order_lines_order_sku
    ON order_lines (order_id, sku);
```

Ở đây mỗi dòng có `id` riêng để tra cứu/cập nhật; `order_id` là FK; `(order_id, line_number)` là unique key bảo vệ số thứ tự dòng không trùng trong một đơn. Index `(order_id, id)` hỗ trợ liệt kê và phân trang theo ID của các dòng thuộc một đơn; index `(order_id, sku)` hỗ trợ tìm dòng theo mã sản phẩm. Có cần cả hai index hay không phụ thuộc tần suất truy vấn và workload ghi.

Nếu mỗi SKU chỉ được xuất hiện một lần trong một đơn, phải có thêm unique constraint phù hợp trên `(order_id, sku)`; index thường không mặc nhiên cưỡng chế uniqueness. Nếu một SKU có thể xuất hiện ở nhiều dòng với giá/khuyến mãi khác nhau thì không thêm constraint đó.

### 6.2. Entity cha gọn

```java
package com.example.orders.domain;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;
import jakarta.persistence.Version;

@Entity
@Table(name = "orders")
public class Order {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "customer_id", nullable = false)
    private Long customerId;

    @Column(nullable = false, length = 32)
    private String status;

    @Version
    private Long version;

    protected Order() {}

    public Order(Long customerId) {
        this.customerId = customerId;
        this.status = "DRAFT";
    }

    public Long getId() { return id; }
    public String getStatus() { return status; }
    public Long getVersion() { return version; }

    public void markSubmitted() {
        if (!"DRAFT".equals(status)) {
            throw new IllegalStateException(
                    "Chỉ đơn nháp mới được gửi");
        }
        status = "SUBMITTED";
    }
}
```

Entity `Order` **không khai báo `List<OrderLine>`**. Điều này hoàn toàn hợp lệ: JPA/Hibernate không bắt buộc quan hệ phải được ánh xạ hai chiều. Ứng dụng có thể tìm mọi dòng qua repository/query theo `order.id`.

### 6.3. Entity con có identity và hành vi riêng

```java
package com.example.orders.domain;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.FetchType;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.JoinColumn;
import jakarta.persistence.ManyToOne;
import jakarta.persistence.Table;
import java.math.BigDecimal;

@Entity
@Table(name = "order_lines")
public class OrderLine {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "order_id", nullable = false)
    private Order order;

    @Column(name = "line_number", nullable = false)
    private int lineNumber;

    @Column(nullable = false, length = 64)
    private String sku;

    @Column(nullable = false)
    private int quantity;

    @Column(name = "unit_price", nullable = false,
            precision = 18, scale = 2)
    private BigDecimal unitPrice;

    protected OrderLine() {}

    public OrderLine(Order order,
                     int lineNumber,
                     String sku,
                     int quantity,
                     BigDecimal unitPrice) {
        if (order == null || sku == null || sku.isBlank()
                || quantity <= 0 || unitPrice == null
                || unitPrice.signum() < 0) {
            throw new IllegalArgumentException("Dòng hàng không hợp lệ");
        }
        this.order = order;
        this.lineNumber = lineNumber;
        this.sku = sku;
        this.quantity = quantity;
        this.unitPrice = unitPrice;
    }

    public Long getId() { return id; }
    public Order getOrder() { return order; }
    public int getLineNumber() { return lineNumber; }
    public String getSku() { return sku; }
    public int getQuantity() { return quantity; }
    public BigDecimal getUnitPrice() { return unitPrice; }

    public void changeQuantity(int newQuantity) {
        if (newQuantity <= 0) {
            throw new IllegalArgumentException("Số lượng phải dương");
        }
        this.quantity = newQuantity;
    }
}
```

`OrderLine.order` là phía sở hữu FK. `@ManyToOne(fetch = LAZY)` tránh eager load cha mỗi lần tải một dòng nếu chưa cần; khi truy cập dữ liệu cha, Hibernate vẫn có thể query. ID của dòng cho phép cập nhật riêng trong transaction, không cần đọc và giữ toàn bộ `Order.lines`.

**Lưu ý về invariant:** mô hình trên cho phép lưu/cập nhật dòng độc lập ở cấp ORM nhưng nghiệp vụ vẫn có thể cấm sửa dòng nếu `Order.status != DRAFT`. Việc bỏ collection khỏi entity cha không tự loại bỏ quy tắc aggregate; tầng service phải kiểm tra trạng thái và dùng transaction/locking phù hợp.

## 7. Đọc tập hợp lớn bằng query có giới hạn

Một use case “xem 30 dòng của đơn hàng” cần truy vấn chính những dòng đó, sắp xếp ổn định và giới hạn số bản ghi. Không làm:

```java
// Không nên dùng cho collection không giới hạn:
List<OrderLine> firstPage = order.getLines().stream()
        .sorted(Comparator.comparing(OrderLine::getId))
        .limit(30)
        .toList();
```

Với collection Hibernate chưa được khởi tạo, dòng trên có thể khiến toàn bộ tập hợp phải được load về trước khi Java `stream()`, `sorted()` và `limit()` được áp dụng. Giới hạn trong Java không đồng nghĩa `LIMIT` trong SQL.

### 7.1. DTO projection cho trang danh sách

Nếu UI chỉ cần ID, vị trí, SKU, số lượng và đơn giá, không cần quản lý toàn bộ entity `OrderLine`:

```java
package com.example.orders.readmodel;

import java.math.BigDecimal;

public record OrderLineRow(
        Long id,
        int lineNumber,
        String sku,
        int quantity,
        BigDecimal unitPrice) {}
```

Truy vấn:

```java
import com.example.orders.readmodel.OrderLineRow;
import jakarta.persistence.EntityManager;
import java.util.List;

public List<OrderLineRow> readFirstPage(
        EntityManager em, Long orderId, int requestedSize) {
    int size = Math.max(1, Math.min(requestedSize, 100));

    return em.createQuery(
            "select new com.example.orders.readmodel.OrderLineRow(" +
            "  l.id, l.lineNumber, l.sku, l.quantity, l.unitPrice) " +
            "from OrderLine l " +
            "where l.order.id = :orderId " +
            "order by l.id",
            OrderLineRow.class)
            .setParameter("orderId", orderId)
            .setMaxResults(size)
            .getResultList();
}
```

Vì constructor projection chỉ chọn các scalar values, Hibernate không cần tạo managed entity `OrderLine` cho từng phần tử của kết quả, miễn query thật sự chọn các scalar expression đó. Pagination thực hiện ở database, kết quả đã là DTO sẵn sàng cho response.

### 7.2. Offset pagination

Với số trang nhỏ:

```java
List<OrderLineRow> page = em.createQuery(
        "select new com.example.orders.readmodel.OrderLineRow(" +
        "  l.id, l.lineNumber, l.sku, l.quantity, l.unitPrice) " +
        "from OrderLine l where l.order.id = :orderId " +
        "order by l.id",
        OrderLineRow.class)
        .setParameter("orderId", orderId)
        .setFirstResult(pageNumber * pageSize)
        .setMaxResults(pageSize)
        .getResultList();
```

Phải kiểm tra `pageNumber >= 0`, `pageSize` trong giới hạn cho phép và tránh tràn số nguyên khi tính offset. Với offset rất sâu, database có thể phải duyệt/bỏ qua nhiều row, nên độ trễ tăng dù chỉ trả một trang nhỏ. Khi dữ liệu thay đổi giữa các lần lấy trang, offset cũng có thể tạo trùng hoặc bỏ sót row nếu không có snapshot/điều kiện truy vấn thích hợp.

### 7.3. Keyset/cursor pagination

Nếu sắp xếp bằng ID tăng dần và client lưu ID cuối của trang trước:

```java
public List<OrderLineRow> readAfter(
        EntityManager em, Long orderId, Long afterId, int requestedSize) {
    int size = Math.max(1, Math.min(requestedSize, 100));
    return em.createQuery(
            "select new com.example.orders.readmodel.OrderLineRow(" +
            "  l.id, l.lineNumber, l.sku, l.quantity, l.unitPrice) " +
            "from OrderLine l " +
            "where l.order.id = :orderId " +
            "and (:afterId is null or l.id > :afterId) " +
            "order by l.id",
            OrderLineRow.class)
            .setParameter("orderId", orderId)
            .setParameter("afterId", afterId)
            .setMaxResults(size)
            .getResultList();
}
```

Ở ví dụ tổng quát này, `afterId == null` biểu diễn trang đầu; trên một số dialect, dùng một parameter `null` trong biểu thức `:afterId is null` có thể cần khai báo kiểu tường minh. Cách dễ kiểm soát hơn trong code thực tế là tạo **hai query tĩnh**: một query không có điều kiện cursor cho trang đầu, một query có `l.id > :afterId` cho các trang tiếp theo.

Keyset hỗ trợ index `(order_id, id)` và thường tốt hơn deep offset khi duyệt nhiều trang liên tiếp. Nhưng nó có điều kiện: phải có thứ tự ổn định, cursor mang đầy đủ khóa sắp xếp (nếu sort theo `createdAt` thì cần thêm `id` làm tie-breaker), và client chấp nhận semantics khi có row mới/chỉnh sửa/xóa giữa các trang.

**Không sort bằng thuộc tính không duy nhất mà thiếu tie-breaker.** Ví dụ chỉ `order by createdAt` có thể trả row cùng timestamp theo thứ tự thay đổi giữa các trang.

## 8. Truy vấn count, exists và aggregate mà không tải collection

Để hiển thị “đơn có 12.450 dòng” không cần nạp 12.450 `OrderLine`:

```java
Long count = em.createQuery(
        "select count(l) from OrderLine l " +
        "where l.order.id = :orderId",
        Long.class)
        .setParameter("orderId", orderId)
        .getSingleResult();
```

Để kiểm tra SKU đã có:

```java
Long matches = em.createQuery(
        "select count(l) from OrderLine l " +
        "where l.order.id = :orderId and l.sku = :sku",
        Long.class)
        .setParameter("orderId", orderId)
        .setParameter("sku", sku)
        .getSingleResult();

boolean exists = matches > 0;
```

Nếu chỉ cần biết có ít nhất một row, truy vấn giới hạn một ID hoặc database `EXISTS` có thể tối ưu hơn đếm hết tập hợp tùy database, index và optimizer. Ở Hibernate/JPA, cũng có thể dùng projection chỉ chọn ID và `setMaxResults(1)`:

```java
boolean hasSku = !em.createQuery(
        "select l.id from OrderLine l " +
        "where l.order.id = :orderId and l.sku = :sku",
        Long.class)
        .setParameter("orderId", orderId)
        .setParameter("sku", sku)
        .setMaxResults(1)
        .getResultList()
        .isEmpty();
```

Để tính tổng số lượng hoặc giá trị, có thể dùng `SUM` thay vì lấy từng dòng rồi lặp:

```java
Long totalQuantity = em.createQuery(
        "select coalesce(sum(l.quantity), 0L) " +
        "from OrderLine l where l.order.id = :orderId",
        Long.class)
        .setParameter("orderId", orderId)
        .getSingleResult();
```

Với giá trị tiền tệ, có thể dùng `BigDecimal` và biểu thức nhân ở tầng database theo mapping/dialect, đồng thời kiểm soát rounding/precision. Không chuyển `BigDecimal` sang `double` chỉ để tính nhanh tổng tiền. Aggregate SQL vẫn có chi phí quét/index tương ứng, nhưng thường tiết kiệm đáng kể network và memory so với materialize mọi entity.

### 8.1. Count có thể tốn chi phí ở quy mô cực lớn

Tách thành query `COUNT(*)` không có nghĩa truy vấn luôn O(1). Với điều kiện lọc phức tạp, isolation, phân vùng và dữ liệu lớn, database vẫn phải đọc nhiều index entry/row. Nếu UI cần số lượng hiển thị thường xuyên, có thể cân nhắc denormalized counter hoặc read model riêng, nhưng khi đó phải có chiến lược duy trì tính đúng đắn.

Ví dụ `orders.line_count` là counter được cập nhật trong cùng transaction với việc thêm/xóa dòng; dưới concurrent updates cần câu SQL cập nhật nguyên tử, optimistic/pessimistic locking hoặc cơ chế phù hợp. Một counter cache eventual consistency không nên dùng để cưỡng chế invariant tuyệt đối nếu chấp nhận dữ liệu trễ.

## 9. Ghi và xóa một phần tử mà không materialize toàn bộ tập hợp

Giả sử cần thay số lượng của dòng 9001:

```java
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import jakarta.persistence.EntityManager;
import jakarta.persistence.PersistenceContext;

@Service
public class OrderLineCommandService {
    @PersistenceContext
    private EntityManager em;

    @Transactional
    public void changeQuantity(
            Long orderId, Long lineId, int newQuantity) {
        OrderLine line = em.find(OrderLine.class, lineId);
        if (line == null
                || !line.getOrder().getId().equals(orderId)) {
            throw new IllegalArgumentException(
                    "Không tìm thấy dòng thuộc đơn hàng");
        }

        Order order = em.find(Order.class, orderId);
        if (!"DRAFT".equals(order.getStatus())) {
            throw new IllegalStateException(
                    "Không thể sửa đơn đã gửi");
        }
        line.changeQuantity(newQuantity);
        // Hibernate dirty checking và flush trong transaction.
    }
}
```

Ở đây chỉ cần tải **một OrderLine** và **một Order**, không tải `Order.lines`. Việc truy cập ID của proxy `line.getOrder()` thường không cần nạp đầy đủ cha với Hibernate; tuy nhiên không nên dựa vào chi tiết proxy này ở mọi provider/version. Có thể thay bằng query lọc trực tiếp `where l.id = :lineId and l.order.id = :orderId` nếu muốn ownership check được thực hiện ngay trong SQL.

**Cạnh tranh:** việc kiểm tra `Order.status == DRAFT` rồi sửa dòng chỉ đúng theo chính sách transaction/isolation/locking. Một transaction khác có thể chuyển Order sang SUBMITTED đồng thời. Nếu đó là invariant nghiêm ngặt, cần khóa Order bằng `PESSIMISTIC_WRITE`, dùng protocol optimistic version được áp dụng thống nhất hoặc câu cập nhật có điều kiện; không mặc định `@Version` trên Order sẽ tự tăng khi chỉ cập nhật một OrderLine.

### 9.1. Xóa entity con

```java
@Transactional
public void removeLine(Long orderId, Long lineId) {
    OrderLine line = em.createQuery(
            "select l from OrderLine l " +
            "where l.id = :lineId and l.order.id = :orderId",
            OrderLine.class)
            .setParameter("lineId", lineId)
            .setParameter("orderId", orderId)
            .getResultStream()
            .findFirst()
            .orElseThrow(() -> new IllegalArgumentException(
                    "Không tìm thấy dòng hàng"));

    // Kiểm tra invariant của Order và quyền thao tác ở đây.
    em.remove(line);
}
```

Khi dùng entity con độc lập, `remove(line)` chỉ đánh dấu xóa entity ấy trong persistence context; SQL `DELETE` được thực thi theo flush/transaction. Không cần đưa nó ra khỏi một `List<OrderLine>` lớn trên cha. Nếu vẫn giữ collection hai chiều đã được load trong cùng session, cần đồng bộ hai phía của quan hệ trong memory để tránh một aggregate object graph không nhất quán; đó là một lý do khác để cân nhắc không mapping collection không giới hạn ở phía cha.

### 9.2. Bulk update/delete có đánh đổi

JPQL bulk DML có thể sửa/xóa nhiều row mà không load entity:

```java
int updated = em.createQuery(
        "update OrderLine l set l.quantity = :quantity " +
        "where l.order.id = :orderId and l.sku = :sku")
        .setParameter("quantity", 5)
        .setParameter("orderId", orderId)
        .setParameter("sku", sku)
        .executeUpdate();
```

Bulk DML đi vòng qua lifecycle bình thường của managed entities: thường không chạy dirty checking trên từng entity, không gọi các entity callbacks theo cách `em.find()` rồi sửa field, không tự đồng bộ mọi object đã được load vào persistence context, và optimistic version cần được xử lý chủ động theo thiết kế.

Sau bulk DML, các managed entity tương ứng trong session có thể mang state cũ; có thể cần `clear()`, `refresh()` hoặc sử dụng persistence context khác phù hợp. Không chọn bulk update cho mọi thao tác chỉ để nhanh hơn, đặc biệt khi phần tử có domain rules, audit hoặc callbacks cần thực thi.

## 10. Tại sao @ElementCollection lớn khó cập nhật từng phần tử?

Với `@ElementCollection`, Hibernate quản lý các row như **giá trị thuộc entity sở hữu**, không có entity identity riêng. Cơ chế đồng bộ collection phụ thuộc loại collection và mapping:

- `Set` các giá trị có equality phù hợp và đủ cột phân biệt phần tử có thể cho phép SQL xóa/chèn từng phần tử khi Hibernate xác định được thay đổi.
- Một **bag** không có khóa hàng riêng có thể buộc Hibernate xóa nhiều row của owner rồi chèn lại những giá trị còn lại trong một số kịch bản cập nhật.
- `List` có `@OrderColumn` duy trì vị trí trong database; chèn hoặc xóa giữa danh sách có thể cập nhật index của nhiều row phía sau.
- `Map` cần hiểu khóa của phần tử và column mapping; key mutable hoặc không duy nhất dễ tạo vấn đề.

Không thể kết luận “Hibernate luôn xóa và insert lại toàn bộ `@ElementCollection`”; SQL thực tế thay đổi theo loại collection, collection identifier/index, version Hibernate và thao tác. Nhưng khi giá trị trong collection có **tần suất cập nhật cao hoặc cần sửa riêng từng hàng**, mô hình entity với PK rõ ràng thường dễ dự đoán và kiểm soát hơn.

### 10.1. Bag, Set và List không giống nhau

| Java collection / mapping | Đặc tính quan trọng | Rủi ro khi lớn |
|---|---|---|
| `Set<T>` | Không trùng theo `equals()/hashCode()` của phần tử | Hash không ổn định với mutable element; load quá nhiều khi duyệt |
| `List<T>` không `@OrderColumn` | Thường là bag semantics đối với nhiều mapping Hibernate | Thiếu định danh vị trí hàng, một số cập nhật/xóa khó xác định row |
| `List<T>` + `@OrderColumn` | Lưu thứ tự theo cột vị trí | Insert/remove giữa danh sách có thể phải đổi hàng loạt index |
| `Map<K,V>` | Truy cập theo key; ánh xạ `@MapKey...` tùy model | Key mutable, key uniqueness, load tất cả để dùng Java map |
| `@OneToMany Set<Child>` | Phần tử là entity có PK riêng | Vẫn có thể tốn heap khi fetch trọn; equality/entity proxy cần cẩn trọng |

Nếu yêu cầu “trang 20 bình luận tiếp theo”, `@OrderColumn` trên `List<Comment>` không tự cung cấp API database pagination. Hãy truy vấn `Comment` theo `postId` với `ORDER BY createdAt, id` và giới hạn.

## 11. Many-to-many lớn và association entity

Quan hệ nhiều-nhiều không có thuộc tính riêng thường được ánh xạ trực tiếp bằng `@ManyToMany`:

```java
@ManyToMany
@JoinTable(
        name = "article_tags",
        joinColumns = @JoinColumn(name = "article_id"),
        inverseJoinColumns = @JoinColumn(name = "tag_id"))
private Set<Tag> tags = new HashSet<>();
```

Nhưng khi một việc **gắn nhãn** cần thông tin riêng như `createdAt`, `assignedBy`, `source`, `rank`, `status` hoặc quyền duyệt, row trong join table đã có đời sống nghiệp vụ. Khi số lượng liên kết lớn, nhu cầu phân trang và xóa riêng từng liên kết càng rõ.

Thay vì xem join table là chi tiết ẩn, có thể tạo entity:

```text
Article (id)
   │
   └─ ArticleTagAssignment
         ├─ id
         ├─ article_id  → Article
         ├─ tag_id      → Tag
         ├─ assigned_at
         └─ assigned_by
```

DDL:

```sql
CREATE TABLE article_tag_assignments (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    article_id BIGINT NOT NULL REFERENCES articles(id),
    tag_id BIGINT NOT NULL REFERENCES tags(id),
    assigned_at TIMESTAMP WITH TIME ZONE NOT NULL,
    assigned_by BIGINT NOT NULL,
    CONSTRAINT uq_article_tag UNIQUE (article_id, tag_id)
);

CREATE INDEX idx_article_tag_assignments_article_id_id
    ON article_tag_assignments(article_id, id);
```

Entity association có `@ManyToOne(fetch = LAZY)` tới `Article` và `Tag`, các thuộc tính `assignedAt`/`assignedBy` cùng logic nghiệp vụ. Một liên kết được truy cập theo ID riêng; uniqueness của `(article_id, tag_id)` được ràng buộc ở database.

Không phải mọi many-to-many phải được thay bằng association entity. Nếu liên kết rất ít và không có thuộc tính riêng, `@ManyToMany` vẫn có thể phù hợp. Tín hiệu cần chuyển rõ nhất là **liên kết đã trở thành một thực thể nghiệp vụ** hoặc phải đọc/cập nhật từng liên kết với query riêng.

## 12. Cascade và orphanRemoval khi tập hợp tăng rất lớn

Trong một aggregate nhỏ, cascade giúp code tự nhiên:

```java
@OneToMany(mappedBy = "order",
        cascade = CascadeType.ALL,
        orphanRemoval = true)
private List<OrderLine> lines = new ArrayList<>();
```

Với mapping trên:

- `cascade = ALL` gồm các thao tác persist, merge, remove, refresh, detach. Nó không có nghĩa Hibernate “chỉ cascade khi user bấm lưu”.
- `orphanRemoval = true` nghĩa là khi entity con bị gỡ khỏi association thuộc owner theo mapping, nó có thể được xóa theo vòng đời ORM.
- Thao tác cascade qua một object graph lớn có thể duyệt và đồng bộ nhiều entity; xóa một Order với hàng trăm nghìn OrderLine có thể kéo theo rất nhiều thao tác.

Khi collection không bị giới hạn về kích thước, **không nhất thiết phải đặt `cascade = ALL` và `orphanRemoval = true` chỉ vì quan hệ là một-nhiều**. Có thể quản lý lifecycle của `OrderLine` bằng service riêng, query/command riêng và database FK. Nếu nghiệp vụ yêu cầu xóa tất cả khi xóa cha, cần chủ động lựa chọn:

1. Xóa con theo chunk/transaction phù hợp, rồi xóa cha.
2. Dùng database `ON DELETE CASCADE` khi chấp nhận semantics đó và đã kiểm soát side effect.
3. Thiết kế soft delete/archive/retention khi dữ liệu con có lịch sử hoặc audit bắt buộc.

Database cascade không thực thi entity callbacks của Hibernate cho từng child như đường xóa entity ORM. Ngoài ra, nếu trong persistence context đã có child được load, việc xóa bằng bulk SQL hoặc database cascade có thể để lại object state cũ đến khi clear/refresh. Cần quyết định ở cấp kiến trúc, không trộn tùy tiện nhiều cơ chế.

**Cảnh báo domain:** một Order đã gửi có thể không được phép xóa dòng dù Hibernate vẫn hỗ trợ `remove()`. Cách phân quyền/kiểm tra trạng thái tại service/transaction quan trọng hơn annotation cascade.

## 13. Ranh giới aggregate và ranh giới transaction

Trong Domain-Driven Design, một aggregate thường là biên bảo vệ các invariant cần nhất quán mạnh, với aggregate root làm điểm vào cho thay đổi. Nhưng **aggregate không đồng nghĩa một `@OneToMany` graph luôn được load hết vào memory**.

Ví dụ đơn hàng có 100.000 dòng:

- Invariant: “đơn đã SUBMITTED thì không được sửa dòng”.
- Invariant: “mỗi `lineNumber` chỉ xuất hiện một lần trong một Order”.
- Invariant: “tổng giá trị không vượt hạn mức tín dụng”.

Đối với invariant đầu tiên, cần một protocol transaction kiểm tra/khóa trạng thái `Order` khi sửa dòng. Đối với uniqueness, database unique constraint `(order_id, line_number)` rất hữu ích. Đối với tổng giá trị, có thể dùng aggregate SQL, maintained summary hoặc transaction update có điều kiện.

Những invariant đó **không bắt buộc** code phải tải đủ 100.000 `OrderLine` mới được phép thực hiện. Thậm chí việc load toàn bộ làm tăng thời gian giữ lock, khiến tính nhất quán khó đạt hơn trong hệ thống cạnh tranh cao.

Mô hình có thể được tách ở hai cấp:

1. **Mapping/navigation:** `OrderLine` là entity, nhưng `Order` không chứa collection lớn.
2. **Aggregate nghiệp vụ:** nếu một phần tử có vòng đời và invariant độc lập rõ ràng, có thể xem nó là aggregate riêng hoặc dùng service có ranh giới transaction riêng; quyết định này phụ thuộc domain, không chỉ mapping.

Tách entity không tự động cho phép cập nhật chúng độc lập mà không kiểm tra parent state. Cần quy tắc concurrency nhất quán nếu nhiều request thay đổi các phần tử của cùng một parent.

### 13.1. Khi optimistic locking ở cha không đủ

`Order` có `@Version`. Nếu transaction A chỉ sửa `OrderLine.quantity`, Hibernate thường cập nhật version của **OrderLine nếu có `@Version` trên OrderLine**, còn `Order.version` không nhất thiết tăng vì không có field của Order thay đổi.

Do đó, nếu một transaction B đang chuyển `Order.status` sang SUBMITTED, không nên cho rằng `@Version` ở cha sẽ tự phát hiện mọi sửa đổi của child. Có thể:

- Khóa cha `PESSIMISTIC_WRITE` trong cả thao tác sửa dòng và submit.
- Chủ động tăng version ở cha theo một protocol thống nhất (ví dụ explicit optimistic force increment khi thích hợp).
- Đưa một số invariant vào conditional SQL hoặc constraint/database lock.
- Thiết kế state transition có hàng đợi/serialization theo order ID nếu đặc thù workload cần.

Lựa chọn phụ thuộc tần suất cập nhật, isolation và mức tranh chấp, nhưng mọi đường ghi phải tuân theo cùng một protocol.

## 14. Batch xử lý tập hợp lớn: từng chunk, không giữ Session vô hạn

Trong chức năng import hoặc xử lý lại hàng triệu dòng, query phân trang và transaction theo chunk giúp giới hạn bộ nhớ:

```text
Đọc 500 IDs cần xử lý
      ↓
Mở transaction
      ↓
Tải/cập nhật 500 entity
      ↓
Flush, commit và đóng Session
      ↓
Chuyển sang chunk tiếp theo
```

Với code Hibernate tự quản lý:

```java
import org.hibernate.Session;
import org.hibernate.Transaction;

public void processLineIds(
        SessionFactory factory, List<Long> lineIds) {
    final int chunkSize = 100;

    for (int start = 0; start < lineIds.size(); start += chunkSize) {
        int end = Math.min(start + chunkSize, lineIds.size());

        try (Session session = factory.openSession()) {
            Transaction tx = session.beginTransaction();
            try {
                for (int i = start; i < end; i++) {
                    OrderLine line =
                            session.get(OrderLine.class, lineIds.get(i));
                    if (line != null) {
                        // Thực hiện domain operation được cho phép.
                        // Ví dụ chỉ đọc/đánh dấu xử lý theo nghiệp vụ.
                    }
                }
                tx.commit();
            } catch (RuntimeException | Error ex) {
                if (tx.isActive()) {
                    try {
                        tx.rollback();
                    } catch (RuntimeException rollbackEx) {
                        ex.addSuppressed(rollbackEx);
                    }
                }
                throw ex;
            }
        }
    }
}
```

Ví dụ chỉ minh họa cấu trúc transaction theo chunk; việc đọc trước `lineIds` thành một danh sách hàng triệu ID cũng có thể chiếm memory, vì thế hệ thống lớn nên lấy tiếp các ID theo trang/cursor hoặc stream phù hợp thay vì gom tất cả vào một `List<Long>`.

Mỗi chunk commit độc lập có nghĩa công việc có thể **thành công một phần** nếu chunk sau lỗi. Quy trình import phải định nghĩa retry/idempotency/checkpoint đúng để không tạo dữ liệu trùng. Nếu nghiệp vụ bắt buộc tất cả cùng commit/rollback, chia transaction thành nhiều chunk không còn tương đương; cần thiết kế lại hoặc giới hạn khối lượng trong một transaction.

### 14.1. Flush/clear trong một transaction lớn

Nếu một transaction buộc xử lý nhiều entity, có thể `session.flush()` và `session.clear()` sau một số lượng nhất định để tránh persistence context phình vô hạn:

```java
for (int i = 0; i < batch.size(); i++) {
    session.persist(batch.get(i));
    if ((i + 1) % 50 == 0) {
        session.flush();
        session.clear();
    }
}
```

`clear()` làm entity đã được quản lý trở thành detached; `flush()` chỉ đồng bộ SQL, **không commit**. Một transaction khổng lồ vẫn có thể giữ lock và gây rollback lớn dù thường xuyên clear memory. Với `IDENTITY` generator, JDBC insert batching có thể bị hạn chế; sequence/generator phù hợp giúp tối ưu một số trường hợp.

## 15. Index và database layout phải đi cùng mô hình truy vấn

Sau khi tách `Comment` hoặc `OrderLine` thành entity, index nên dựa trên query thực tế:

```sql
-- Duyệt dòng thuộc một Order theo ID:
CREATE INDEX idx_lines_order_id_id
    ON order_lines(order_id, id);

-- Nếu UI lọc theo SKU trong một Order:
CREATE INDEX idx_lines_order_sku
    ON order_lines(order_id, sku);
```

Đối với bình luận:

```sql
CREATE TABLE comments (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    article_id BIGINT NOT NULL REFERENCES articles(id),
    author_id BIGINT NOT NULL,
    body TEXT NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL
);

CREATE INDEX idx_comments_article_created_id
    ON comments(article_id, created_at DESC, id DESC);
```

Query liệt kê bình luận mới nhất:

```java
List<CommentPreview> rows = em.createQuery(
        "select new com.example.read.CommentPreview(" +
        "  c.id, c.authorId, c.createdAt, c.body) " +
        "from Comment c " +
        "where c.article.id = :articleId " +
        "order by c.createdAt desc, c.id desc",
        CommentPreview.class)
        .setParameter("articleId", articleId)
        .setMaxResults(25)
        .getResultList();
```

Ví dụ giả định entity `Comment` có mapping `article`, `authorId`, `createdAt`, `body` và record `com.example.read.CommentPreview` có constructor khớp. Cột `created_at` có thể trùng giữa các row, nên cần `id` làm tie-breaker để phân trang ổn định. Với cursor ghép `(createdAt, id)`, điều kiện trang kế tiếp phải tương ứng thứ tự DESC:

```sql
SELECT id, author_id, created_at, body
FROM comments
WHERE article_id = :article_id
  AND (
      created_at < :cursor_time
      OR (created_at = :cursor_time AND id < :cursor_id)
  )
ORDER BY created_at DESC, id DESC
LIMIT 25;
```

Một index có thể phù hợp query này nhưng cũng tăng chi phí insert/update và dung lượng lưu trữ. Không tạo mọi index có thể nghĩ ra; lựa chọn dựa trên truy vấn quan trọng, cardinality và kế hoạch thực thi của database.

### 15.1. Tách entity không tự giải quyết bài toán dữ liệu quá lớn

Nếu tất cả bình luận được lưu một bảng duy nhất lên hàng tỷ row, còn có thể cần retention, partitioning theo thời gian/tenant, archived tables, search index hoặc read model. Những quyết định đó nằm ở tầng storage/data architecture. Nhưng tách `Comment` thành entity giúp tạo một ranh giới rõ ràng để triển khai truy vấn, index và lifecycle mà không buộc `Article` chứa toàn bộ bình luận trong object graph.

## 16. Tránh N+1 khi đọc nhiều entity cha

Giả sử có 50 bài viết và cần số lượng bình luận mỗi bài. Cách sau thường không hợp lý:

```java
for (Article article : articles) {
    int numberOfComments = article.getComments().size();
    // Có thể kích hoạt một query (hoặc tải collection) cho mỗi article.
}
```

Thay bằng group aggregate:

```java
List<Object[]> counts = em.createQuery(
        "select c.article.id, count(c) " +
        "from Comment c " +
        "where c.article.id in :articleIds " +
        "group by c.article.id",
        Object[].class)
        .setParameter("articleIds", articleIds)
        .getResultList();
```

Code gọi cần chuyển kết quả thành map `articleId → count`; những bài không có comment sẽ không có row trong kết quả và nên nhận mặc định 0. Nếu cần một DTO typed, có thể dùng constructor projection:

```java
public record ArticleCommentCount(Long articleId, Long count) {}
```

```java
List<ArticleCommentCount> counts = em.createQuery(
        "select new com.example.read.ArticleCommentCount(" +
        "c.article.id, count(c)) " +
        "from Comment c " +
        "where c.article.id in :articleIds " +
        "group by c.article.id",
        ArticleCommentCount.class)
        .setParameter("articleIds", articleIds)
        .getResultList();
```

Các đoạn ví dụ giả định entity `Comment` tồn tại và tên package DTO đúng với project. Khi `articleIds` rỗng, nên xử lý bằng kết quả rỗng ở Java thay vì tạo câu `IN ()` có thể không portable. Với danh sách ID quá lớn, có thể chia batch theo giới hạn database/dialect.

`@BatchSize` hoặc `hibernate.default_batch_fetch_size` có thể giúp giảm số round trip khi nạp nhiều association lazy, nhưng không thay thế việc chọn đúng dữ liệu: nếu 50 cha có tổng 100.000 con thì batch loading vẫn có thể tải 100.000 đối tượng. Hãy tối ưu *kết quả cần lấy*, rồi mới tối ưu *cách fetch*.

## 17. API response không nên vô tình xuất toàn bộ graph

Nếu controller trả trực tiếp một entity:

```java
return article; // Nếu serializer truy cập comments, có thể load toàn bộ.
```

Hệ quả có thể là:

- Tải collection lớn ngoài dự kiến hoặc `LazyInitializationException` khi session đã đóng.
- N+1 query trong lúc serialize.
- Vòng tham chiếu `Article → Comment → Article` gây recursive serialization.
- Response quá lớn, lộ trường nội bộ và thay đổi API theo mapping persistence.

Thay vào đó, xác định DTO cho endpoint:

```java
public record ArticleDetails(
        Long id,
        String title,
        long commentCount) {}

public record CommentPage(
        Long articleId,
        List<CommentPreview> items,
        String nextCursor) {}
```

Endpoint chi tiết chỉ trả metadata/tổng số bình luận; endpoint bình luận riêng trả một trang có cursor. Không cần chuyển `List<Comment>` từ Hibernate thành JSON để client tự phân trang.

Việc dùng DTO/record làm response cũng giúp tách data model và public contract. Record chỉ giữ giá trị tại thời điểm query, không bị Hibernate quản lý như entity. Nếu response có field đòi hỏi tính nhất quán đặc biệt với nội dung trang, chọn transaction isolation/snapshot hoặc read model tương ứng.

## 18. Những cách tối ưu chưa giải quyết bản chất vấn đề

| Biện pháp | Có ích khi nào | Giới hạn quan trọng |
|---|---|---|
| Đổi `EAGER` thành `LAZY` | Không phải use case nào cũng cần collection | Khi truy cập, collection vẫn có thể tải toàn bộ |
| `JOIN FETCH` | Tải trọn một association nhỏ để tránh N+1 | Collection lớn, multiple collections và pagination có thể rất tốn |
| `@BatchSize` | Nhiều lazy association nhỏ/cỡ vừa cần load | Chỉ giảm round trip; không giảm tổng số entity cần materialize |
| `@Fetch(SUBSELECT)` | Một số trường hợp cần tải collections của tập cha | Có thể kéo quá nhiều hàng; semantics phụ thuộc Hibernate |
| Second-level cache | Dữ liệu ít đổi và nhiều lượt đọc lặp | Giữ cache entry lớn, invalidation khó, không thay paging |
| Extra-lazy collection | Một số thao tác collection được tối ưu theo provider/version | Không thay API query rõ ràng, không bảo đảm mọi method đều không load toàn bộ |
| `session.clear()` | Giảm footprint khi batch | Làm detached entity, không giảm dữ liệu đã truyền từ SQL hoặc commit sớm |
| Tăng heap | Giảm nguy cơ OOM tạm thời | Che khuất query/fetch plan không giới hạn |
| Stream kết quả JDBC/Hibernate | Xử lý tuần tự nhiều row không gom hết | Cần đóng resource đúng, cursor/transaction có thể mở lâu |
| Tách entity con và repository query | Cần thao tác/phân trang/tìm kiếm từng phần tử | Phải thiết kế FK, transaction và invariant rõ ràng |

Một hệ thống có thể dùng nhiều biện pháp cùng lúc. Nhưng thứ tự thường có ích là: **mô hình truy cập đúng → SQL trả vừa đủ → index phù hợp → batch/fetch/cache khi cần đo được hiệu quả**.

## 19. Di chuyển từ @ElementCollection sang entity riêng

Giả sử ứng dụng đang có:

```java
@ElementCollection
@CollectionTable(name = "article_labels",
        joinColumns = @JoinColumn(name = "article_id"))
@Column(name = "label")
private Set<String> labels;
```

Sau này mỗi lần gắn nhãn cần thời điểm, người tạo và trạng thái duyệt. Ta muốn chuyển thành entity `ArticleLabel`:

```text
TRƯỚC:
article_labels(article_id, label)

SAU:
article_labels(
    id PRIMARY KEY,
    article_id FOREIGN KEY,
    label,
    assigned_by,
    assigned_at,
    review_status
)
```

Một quá trình migration có kiểm soát:

1. **Chốt semantics:** mỗi cặp `article_id + label` có được trùng không, ID có ổn định không, ai có quyền sửa/xóa, soft delete hay hard delete?
2. **Thêm schema:** tạo PK hoặc một bảng mới, các cột metadata và unique/FK/index phù hợp. Dùng migration có phiên bản.
3. **Backfill:** chuyển mỗi giá trị cũ thành một hàng entity mới; quyết định giá trị mặc định cho metadata chưa từng tồn tại (không bịa người tạo lịch sử).
4. **Chuyển đường ghi:** code nghiệp vụ persist/update/remove `ArticleLabel` qua repository/EntityManager; cân nhắc thời gian chuyển đổi tương thích nếu rolling deployment.
5. **Chuyển đường đọc:** query/pagination trực tiếp `ArticleLabel`, sửa DTO/API và fetch plan.
6. **Kiểm tra điều kiện cutover:** đối chiếu số hàng, uniqueness, FK, logic ghi đồng thời và quyền truy cập trước khi bỏ mapping cũ.
7. **Dọn cấu hình cũ:** bỏ `@ElementCollection`/đường ghi cũ khi deployment đã chuyển hoàn toàn, tránh hai mapping cùng quản lý một bảng gây ghi đè bất ngờ.

Migration phải tính đến downtime/online schema changes, các instance phiên bản cũ còn chạy, dữ liệu lỗi có từ trước, backfill theo batch và cơ chế rollback. Nếu chỉ đổi annotation `@ElementCollection` thành `@OneToMany` trên cùng bảng mà không bổ sung ID và quan hệ đúng, Hibernate có thể không ánh xạ hoặc tạo SQL theo kỳ vọng.

### 19.1. Chuyển từ @OneToMany graph lớn sang query entity con

Nếu `OrderLine` vốn đã là entity có PK, migration có thể đơn giản hơn nhiều: **không cần di chuyển dữ liệu**. Có thể bỏ collection `Order.lines` khỏi mapping nếu ứng dụng không cần điều hướng hai chiều, rồi thêm query theo `order.id`, giới hạn page size và xây service command cho child.

Tuy nhiên phải rà soát những hành vi đang dựa vào `cascade=ALL`, `orphanRemoval` hoặc việc gọi `order.getLines().add(...)`. Khi bỏ collection, cần thay thế logic persist/xóa child và quy tắc transaction; nếu không, dữ liệu có thể không được ghi hoặc không được dọn khi xóa parent.

## 20. Bốn tình huống để lựa chọn thực tế

### Tình huống A: khách hàng có 2–5 số điện thoại

Số điện thoại chỉ là giá trị liên hệ, thường hiển thị/chỉnh sửa cùng customer. Nếu không cần lịch sử/xác thực từng số, `@ElementCollection Set<String>` hoặc collection embeddable có thể hợp lý. Không cần entity riêng chỉ vì ORM hỗ trợ.

Nếu từng số có xác minh OTP, thời gian hiệu lực, trạng thái chính/phụ, quyền sử dụng và kiểm toán, `CustomerPhone` entity trở nên hợp lý dù chỉ có vài phần tử. **Identity/lifecycle** có thể quan trọng hơn cardinality.

### Tình huống B: một bài viết có 300.000 bình luận

Mỗi bình luận có ID, tác giả, nội dung, thời điểm, duyệt/xóa riêng; API cần phân trang và tìm kiếm. Dùng `Comment @Entity` với `@ManyToOne(fetch = LAZY) Article article`, query trực tiếp theo `article.id`, index `(article_id, created_at, id)` phù hợp. Không duyệt `article.getComments()` để trả trang bình luận.

Có thể tránh khai báo collection `Article.comments`. Tổng bình luận nên lấy bằng aggregate hoặc read model/counter có chính sách nhất quán được xác định.

### Tình huống C: đơn hàng có 20 dòng, nhưng trạng thái phải nguyên tử

Với số dòng nhỏ, aggregate `Order` có `@OneToMany` và các domain method thêm/xóa dòng có thể thuận tiện để giữ invariant trong một transaction. Nếu mỗi Order thực tế chỉ có vài chục dòng và nghiệp vụ luôn cần tất cả, không phải tách navigation bằng mọi giá.

Tuy nhiên `OrderLine` vẫn có thể là entity riêng nếu dòng cần ID, version hoặc FK riêng. Phân biệt **entity riêng** và **bỏ collection khỏi cha** là hai quyết định độc lập.

### Tình huống D: một bài viết có hàng triệu reaction

Mỗi reaction có thể được xác định bằng `(articleId, userId, reactionType)` hoặc surrogate ID, tùy nghiệp vụ cho phép một người có bao nhiêu reaction. API cần kiểm tra user đã react chưa, thêm/xóa riêng và hiển thị aggregate count. Tải toàn bộ `article.reactions` vào Java là không phù hợp.

Thiết kế bảng `article_reactions` với unique constraint thích hợp, index lookup theo article/user, và query/count/tổng hợp độc lập. Nếu reaction chỉ là một relation membership không cần domain entity có ID riêng, cũng có thể thao tác qua bảng bằng SQL/DAO chuyên dụng; **không nhất thiết phải làm mọi hàng thành Hibernate entity**. Điều quan trọng là tránh collection không giới hạn và bảo vệ uniqueness/concurrency ở database.

## 21. Một quy trình đánh giá nhanh khi review mapping

Đặt câu hỏi theo thứ tự:

**Thứ nhất, phần tử là giá trị hay thực thể?** Nếu hai phần tử có thuộc tính giống nhau nhưng vẫn phải phân biệt theo identity, thường cần entity. Nếu giá trị chỉ có ý nghĩa trong phạm vi owner, `@ElementCollection` vẫn là ứng viên.

**Thứ hai, collection có tăng không giới hạn không?** Những thứ như lịch sử sự kiện, comments, notifications, audit entries, order operations thường tăng theo thời gian. Với collection loại này, tránh API bắt buộc materialize toàn bộ.

**Thứ ba, use case đọc dữ liệu như thế nào?** Nếu cần lọc/trang/tổng hợp từng phần tử, tạo query riêng trả về projection vừa đủ, có điều kiện và index phù hợp.

**Thứ tư, use case ghi có phải sửa một phần tử độc lập không?** Nếu có, thiết kế entity key, service/transaction, concurrency protocol và permissions. Không để việc sửa một dòng phải khởi tạo hàng vạn phần tử.

**Thứ năm, trạng thái của cha ràng buộc các con ra sao?** Tách entity không làm mất invariant của aggregate. Cần thiết kế cách khóa, version hoặc update có điều kiện để kiểm soát thay đổi đồng thời.

**Thứ sáu, lifecycle xóa/retention của dữ liệu con như thế nào?** Với dữ liệu lớn, cascade remove và orphan removal có thể tạo transaction nặng. Cần chọn xóa theo chunk, FK cascade hoặc archive/soft delete theo yêu cầu domain.

**Thứ bảy, dữ liệu đang có cần migration ra sao?** Nếu đã là child entity, có thể chỉ thay navigation/query. Nếu là `@ElementCollection`, cần thiết kế khóa, backfill metadata và chuyển đường ghi an toàn.

## 22. Sơ đồ lựa chọn

```text
                  Collection của entity cha
                              │
                Mỗi phần tử có identity riêng?
                       ┌──────┴──────┐
                       │             │
                      CÓ           KHÔNG
                       │             │
                       ▼             ▼
                  @Entity con    Value collection
                       │        @ElementCollection /
                       │        @Embeddable
                       │             │
                       │      Cần phân trang hoặc
                       │      thao tác từng hàng lớn?
                       │             │
                       │       ┌─────┴─────┐
                       │      CÓ          KHÔNG
                       │       │            │
                       │       ▼            ▼
                       │   Cân nhắc       Giữ value
                       │   entity hoặc    collection
                       │   DAO/query      nhỏ/gọn
                       │   chuyên dụng
                       ▼
          Collection navigation từ cha
               có thực sự cần không?
                  ┌──────┴──────┐
                 CÓ           KHÔNG
                  │             │
                  ▼             ▼
           @OneToMany nếu    Chỉ @ManyToOne
           tập hợp bounded   ở entity con,
           và dùng trọn      query theo FK
                  │             │
                  └──────┬──────┘
                         ▼
                Query, index, transaction,
                cascade và concurrency rõ ràng
```

Điểm quan trọng là **quan hệ một-nhiều trong database không bắt buộc được biểu diễn bằng một collection Java lớn trên entity cha**. Khi phần tử có ID, vòng đời hoặc hành vi độc lập, hãy cân nhắc entity riêng; khi tập hợp có cardinality lớn, hãy truy vấn, phân trang và cập nhật phần tử theo phạm vi thực sự cần. Cách mô hình hóa này giữ cho Hibernate persistence context nhỏ, SQL dễ dự đoán và các transaction phù hợp với nhu cầu nhất quán của nghiệp vụ.
