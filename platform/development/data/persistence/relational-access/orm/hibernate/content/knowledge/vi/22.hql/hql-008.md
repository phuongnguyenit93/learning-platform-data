# Truy vấn con, kiểm tra tồn tại và xử lý tập hợp

## 1. Vì sao HQL cần truy vấn con?

HQL (Hibernate Query Language) cho phép mô tả truy vấn trên entity, thuộc tính và association thay vì viết trực tiếp tên bảng/cột. Khi điều kiện của một entity phụ thuộc vào dữ liệu ở một tập hợp khác, truy vấn con (*subquery*) giúp diễn đạt điều kiện đó ngay trong một câu truy vấn.

Ví dụ, một cửa hàng muốn tìm:

- Những khách hàng đã từng đặt ít nhất một đơn hàng.
- Những cuốn sách chưa có đánh giá nào.
- Những sản phẩm có giá cao hơn giá trung bình trong cùng danh mục.
- Những đơn hàng có ít nhất một dòng hàng số lượng lớn.
- Những tác giả có tất cả sách đều đã xuất bản.
- Những khách hàng có tổng giá trị đơn hàng vượt một ngưỡng.

Các bài toán này thường cần một truy vấn phụ để kiểm tra một tập hợp hoặc tính một giá trị tổng hợp. HQL hỗ trợ các cấu trúc như `EXISTS`, `NOT EXISTS`, `IN`, `ALL`, `ANY`/`SOME`, truy vấn con tương quan và các biểu thức làm việc với collection.

Điều cần nhớ là subquery không chỉ là một câu SELECT lồng bên trong câu SELECT khác. Nó là một cách diễn đạt **điều kiện trên tập kết quả**. Chọn đúng cấu trúc có thể làm câu truy vấn dễ hiểu hơn và tránh lỗi khi dữ liệu có NULL, collection rỗng hoặc nhiều bản ghi trùng lặp.

## 2. HQL truy vấn entity, không truy vấn tên bảng

Giả sử mô hình cửa hàng có các entity:

```text
Customer
  └── orders: Set<Order>
          └── lines: List<OrderLine>
                    └── product: Product

Book
  ├── author: Author
  ├── category: Category
  └── reviews: List<Review>
```

HQL dùng tên entity và thuộc tính Java:

```hql
select c
from Customer c
where c.active = true
```

HQL không yêu cầu viết trực tiếp tên bảng và cột vật lý như SQL:

```sql
select *
from customers
where active = true
```

Hibernate phân tích HQL, ánh xạ path expression qua metadata entity và sinh SQL phù hợp với dialect. Vì vậy:

- Customer là entity name (mặc định thường là tên class đơn giản).
- c.orders là association được khai báo trong mapping.
- o.total là thuộc tính entity, không nhất thiết trùng tên cột vật lý.
- c.id là thuộc tính định danh của entity.

Các ví dụ dưới đây dùng cú pháp HQL tương thích với Hibernate hiện đại. Phần nào là khả năng mở rộng của HQL so với JPQL sẽ được ghi rõ; nếu cần tính portable giữa nhiều JPA provider, hãy dùng tập con JPQL được Jakarta Persistence hỗ trợ.

## 3. Cấu trúc tổng quát của subquery

Một truy vấn con thường nằm trong điều kiện WHERE hoặc HAVING:

```hql
select b
from Book b
where b.price > (
    select avg(b2.price)
    from Book b2
)
```

Truy vấn trong ngoặc được gọi là subquery. Nó tính giá trung bình của các sách; truy vấn ngoài lấy những sách có giá cao hơn kết quả đó.

Có thể hình dung:

```text
Outer query: mỗi Book b
        │
        ▼
Subquery: tính avg(price) trên Book b2
        │
        ▼
So sánh b.price với giá trị scalar
        │
        ▼
Giữ lại Book thỏa điều kiện
```

Subquery có thể trả về:

| Dạng kết quả | Ví dụ | Cách dùng thường gặp |
|---|---|---|
| Một giá trị scalar | select avg(b.price) | So sánh >, <, = |
| Một cột nhiều hàng | select o.customer.id | IN, ANY, ALL |
| Tập có/không có hàng | select 1 from Review r | EXISTS, NOT EXISTS |
| Một giá trị tổng hợp | select count(o) | So sánh số lượng |

Khi dùng subquery scalar trong phép so sánh, phải bảo đảm nó trả về tối đa một giá trị. Nếu subquery trả nhiều hàng ở vị trí chỉ nhận scalar, database sẽ báo lỗi. Nếu cần so sánh với nhiều giá trị, dùng IN, ANY hoặc ALL.

## 4. Subquery không tương quan

Subquery không tương quan (*uncorrelated subquery*) không tham chiếu alias của truy vấn bên ngoài:

```hql
select b
from Book b
where b.price > (
    select avg(b2.price)
    from Book b2
)
```

Subquery có thể được đánh giá độc lập với từng Book ở outer query. Trình tối ưu database có thể biến đổi hoặc tính lại theo kế hoạch thực thi; không nên suy luận rằng database bắt buộc chạy nguyên subquery một lần cho mỗi hàng.

Ví dụ lấy sản phẩm có giá cao nhất:

```hql
select p
from Product p
where p.price = (
    select max(p2.price)
    from Product p2
)
```

Subquery max() trả về một giá trị. Nếu bảng không có sản phẩm, max() trả về NULL; so sánh p.price = NULL không trở thành true. Trong trường hợp đó outer query cũng không trả sản phẩm nào, đúng với kết quả mong đợi.

## 5. Subquery tương quan

Subquery tương quan (*correlated subquery*) tham chiếu alias của truy vấn ngoài:

```hql
select b
from Book b
where b.price > (
    select avg(b2.price)
    from Book b2
    where b2.category = b.category
)
```

Ở đây b thuộc outer query; subquery dùng b.category để tính giá trung bình trong cùng danh mục. Mỗi Book được so sánh với nhóm sách cùng category.

```text
Outer row: Book b (category = "ORM")
                 │
                 ▼
Subquery:
  select avg(b2.price)
  from Book b2
  where b2.category = b.category
                 │
                 ▼
       Giá trung bình của nhóm ORM
                 │
                 ▼
       So sánh với b.price
                 │
                 ▼
       Xét Book tiếp theo ở outer query
```

Một ví dụ khác: tìm khách hàng có đơn hàng vượt 10 triệu:

```hql
select c
from Customer c
where exists (
    select o.id
    from Order o
    where o.customer = c
      and o.total > :minimum
)
```

Subquery tham chiếu c từ outer query. Câu điều kiện kiểm tra từng Customer có ít nhất một Order thỏa ngưỡng hay không.

Correlated subquery thường diễn đạt trực tiếp một quy tắc theo từng entity. Tuy nhiên, nó không có nghĩa database nhất thiết chạy một query riêng cho mỗi entity. Optimizer có thể decorrelate hoặc chuyển thành semi-join/anti-join tùy database và thống kê.

## 6. EXISTS: kiểm tra có ít nhất một hàng

EXISTS trả về true nếu subquery có ít nhất một hàng; nó không quan tâm giá trị cột được SELECT:

```hql
select c
from Customer c
where exists (
    select 1
    from Order o
    where o.customer = c
)
```

Kết quả là các Customer có ít nhất một Order.

select 1 là cách viết dễ đọc vì điều kiện chỉ cần biết có hàng hay không. Có thể SELECT identifier hoặc biểu thức khác, nhưng giá trị không được dùng để so sánh trong EXISTS.

### 6.1. EXISTS không nhân bản outer rows

Nếu một Customer có 20 Order, outer query trên vẫn trả một entity Customer cho hàng Customer đó. Subquery chỉ trả lời câu hỏi tồn tại; nó không join các Order vào outer result.

Điều này khác với:

```hql
select c
from Customer c
join c.orders o
```

Join có thể tạo nhiều result rows cho một Customer tùy số Order và có thể cần DISTINCT nếu muốn danh sách Customer duy nhất. Nếu mục tiêu chỉ là kiểm tra có đơn hàng, EXISTS thường thể hiện ý định rõ hơn.

### 6.2. EXISTS với điều kiện phức hợp

```hql
select c
from Customer c
where exists (
    select 1
    from Order o
    where o.customer = c
      and o.status = :status
      and o.total >= :minimum
)
```

Đặt mọi điều kiện liên quan tới bản ghi con trong subquery. Alias o chỉ có phạm vi trong subquery; alias c được tham chiếu từ outer query.

## 7. NOT EXISTS: tìm entity không có bản ghi liên quan

NOT EXISTS là cách tự nhiên để tìm entity chưa có dữ liệu liên quan:

```hql
select b
from Book b
where not exists (
    select 1
    from Review r
    where r.book = b
)
```

Truy vấn trả về những Book chưa có Review.

Một ví dụ khác: Customer chưa từng đặt đơn:

```hql
select c
from Customer c
where not exists (
    select 1
    from Order o
    where o.customer = c
)
```

Đây là dạng anti-semi-join về mặt ý nghĩa: outer row được giữ khi không tìm thấy row con tương ứng.

### 7.1. NOT EXISTS thường an toàn hơn NOT IN khi subquery có NULL

Giả sử muốn tìm Customer không xuất hiện trong danh sách customer ID của một tập dữ liệu. Cách viết:

```hql
select c
from Customer c
where c.id not in (
    select x.customerId
    from ImportedOrder x
)
```

có thể cho kết quả bất ngờ nếu subquery trả về NULL. Trong SQL, NOT IN được diễn giải tương tự phủ định của các phép so sánh; nếu tập bên phải có NULL, phép so sánh có thể thành UNKNOWN thay vì TRUE. Vì WHERE chỉ giữ điều kiện TRUE, nhiều hàng có thể bị loại.

Nếu dùng NOT EXISTS tương quan:

```hql
select c
from Customer c
where not exists (
    select 1
    from ImportedOrder x
    where x.customerId = c.id
)
```

thì mỗi Customer chỉ bị loại khi có một hàng thật sự thỏa phép bằng. Một giá trị NULL trong x.customerId không làm tất cả các Customer khác biến thành UNKNOWN.

Nếu vẫn dùng NOT IN, cần bảo đảm subquery loại bỏ NULL:

```hql
select c
from Customer c
where c.id not in (
    select x.customerId
    from ImportedOrder x
    where x.customerId is not null
)
```

Đối với truy vấn anti-join, NOT EXISTS thường dễ đọc và ít bất ngờ hơn.

## 8. IN với một subquery

IN kiểm tra giá trị có nằm trong tập kết quả hay không:

```hql
select c
from Customer c
where c.id in (
    select o.customer.id
    from Order o
    where o.status = :status
)
```

Kết quả là Customer có ID nằm trong tập khách hàng của những Order có trạng thái đã chọn.

Có thể so sánh entity expression với tập entity tương ứng:

```hql
select b
from Book b
where b.author in (
    select a
    from Author a
    where a.active = true
)
```

Trong trường hợp entity-valued path, kiểu kết quả của subquery phải tương thích với biểu thức bên trái. Khi cần đơn giản hóa, có thể so sánh identifier:

```hql
select b
from Book b
where b.author.id in (
    select a.id
    from Author a
    where a.active = true
)
```

### 8.1. IN với collection-valued parameter không phải subquery

Hai dạng sau khác nhau:

```hql
-- Một subquery trả về tập ID:
where c.id in (
    select o.customer.id
    from Order o
    where o.status = :status
)

-- Một parameter chứa collection ID từ application:
where c.id in :customerIds
```

Dạng thứ hai dùng collection parameter được bind từ Java:

```java
List<Long> ids = List.of(10L, 20L, 30L);

List<Customer> customers = session.createSelectionQuery(
        "from Customer c where c.id in :ids",
        Customer.class)
        .setParameter("ids", ids)
        .getResultList();
```

Với Hibernate API/version khác, cách tạo query có thể dùng createQuery() thay cho createSelectionQuery(). Parameter collection rỗng và cách provider sinh SQL có thể khác theo phiên bản/dialect; nếu danh sách có thể rỗng, hãy xử lý rõ ở application trước khi thực hiện query.

## 9. ALL, ANY và SOME: so sánh với mọi hoặc một phần tử trong tập

Khi cần so sánh một giá trị với tập kết quả của subquery, dùng lượng từ:

- ALL: phép so sánh phải đúng với mọi giá trị trong tập.
- ANY hoặc SOME: phép so sánh đúng với ít nhất một giá trị trong tập.

Ví dụ tìm sản phẩm có giá cao hơn **mọi** sản phẩm trong danh mục 5:

```hql
select p
from Product p
where p.price > all (
    select p2.price
    from Product p2
    where p2.category.id = :categoryId
)
```

Ví dụ tìm sản phẩm có giá cao hơn **ít nhất một** sản phẩm trong danh mục 5:

```hql
select p
from Product p
where p.price > any (
    select p2.price
    from Product p2
    where p2.category.id = :categoryId
)
```

SOME là từ đồng nghĩa với ANY trong biểu thức lượng từ:

```hql
where p.price > some (
    select p2.price
    from Product p2
    where p2.category.id = :categoryId
)
```

### 9.1. ALL và ANY trên tập rỗng

Theo logic lượng từ:

- x > ALL (empty set) là true vì không có phần tử nào vi phạm điều kiện.
- x > ANY (empty set) là false vì không có phần tử nào làm điều kiện đúng.

Điều này có thể gây ngạc nhiên nếu nghiệp vụ mong “không có sản phẩm trong danh mục thì không trả sản phẩm nào” cho điều kiện ALL. Khi tập rỗng phải có nghĩa nghiệp vụ riêng, hãy thêm EXISTS hoặc NOT EXISTS để diễn đạt rõ.

Ví dụ yêu cầu danh mục phải có ít nhất một sản phẩm và giá phải cao hơn mọi sản phẩm khác trong danh mục:

```hql
select p
from Product p
where exists (
    select 1
    from Product p2
    where p2.category = p.category
)
and p.price > all (
    select p3.price
    from Product p3
    where p3.category = p.category
      and p3.id <> p.id
)
```

Nếu danh mục chỉ có chính sản phẩm p, subquery so sánh sẽ rỗng và ALL đúng theo logic lượng từ. Nếu nghiệp vụ không chấp nhận trường hợp đó, bổ sung điều kiện đếm/EXISTS phù hợp.

### 9.2. NULL làm kết quả so sánh thành UNKNOWN

ALL và ANY chịu ảnh hưởng của SQL three-valued logic. Nếu tập con có NULL, một phép so sánh có thể là UNKNOWN. Ví dụ, x > ALL (1, NULL) không chắc là TRUE dù x > 1, bởi phần tử NULL không thể so sánh. Nếu cột có thể NULL và nghiệp vụ bỏ qua giá trị chưa biết, lọc IS NOT NULL trong subquery.

## 10. Scalar subquery với aggregate

Aggregate thường được dùng trong subquery để trả một giá trị:

```hql
select p
from Product p
where p.price > (
    select avg(p2.price)
    from Product p2
    where p2.category = p.category
)
```

Các aggregate thường gặp:

| Hàm | Kết quả |
|---|---|
| count(...) | Số hàng/giá trị được đếm; thường trả 0 khi không có hàng |
| sum(...) | Tổng; có thể trả NULL nếu không có giá trị |
| avg(...) | Trung bình; trả NULL nếu không có giá trị |
| min(...) | Giá trị nhỏ nhất; trả NULL nếu không có giá trị |
| max(...) | Giá trị lớn nhất; trả NULL nếu không có giá trị |

Ví dụ tìm Author có ít nhất năm Book:

```hql
select a
from Author a
where (
    select count(b)
    from Book b
    where b.author = a
) >= 5
```

Subquery tương quan đếm Book cho từng Author. Có thể viết lại bằng EXISTS với nhóm/HAVING tùy mục tiêu; dùng count khi thực sự cần so sánh số lượng cụ thể.

### 10.1. COUNT khác EXISTS

Nếu chỉ cần biết có ít nhất một hàng, dùng EXISTS:

```hql
where exists (
    select 1
    from Book b
    where b.author = a
)
```

Nếu cần biết số lượng lớn hơn 4, dùng count:

```hql
where (
    select count(b)
    from Book b
    where b.author = a
) > 4
```

Không nên dùng count(...) > 0 như phản xạ mặc định khi EXISTS diễn đạt mục tiêu trực tiếp hơn. Optimizer có thể tối ưu cả hai, nhưng EXISTS thể hiện rằng chỉ cần tìm thấy một hàng.

## 11. Subquery trong HAVING

HAVING lọc nhóm sau khi aggregate được tính. Có thể so sánh aggregate của nhóm với kết quả subquery:

```hql
select c.id, c.name, sum(o.total)
from Customer c
join c.orders o
group by c.id, c.name
having sum(o.total) > (
    select avg(o2.total)
    from Order o2
)
```

Truy vấn lấy các Customer có tổng giá trị Order lớn hơn giá trị trung bình của một Order trong toàn hệ thống. Chú ý hai đại lượng khác nhau: vế trái là tổng theo Customer; subquery là trung bình theo từng Order.

Một ví dụ dùng subquery trả tập ID:

```hql
select c.id, c.name, count(o)
from Customer c
join c.orders o
group by c.id, c.name
having c.id in (
    select o2.customer.id
    from Order o2
    group by o2.customer.id
    having sum(o2.total) >= :minimumTotal
)
```

GROUP BY và HAVING bên trong subquery được thực thi độc lập để xác định các Customer ID có tổng doanh số đạt ngưỡng. Outer query tiếp tục tính số Order để hiển thị.

## 12. Subquery trong SELECT và FROM: HQL mở rộng hơn JPQL

HQL hiện đại có một số khả năng biểu đạt rộng hơn tập con JPQL portable. Một khác biệt quan trọng là vị trí subquery.

### 12.1. Subquery trong SELECT

Hibernate HQL hiện đại hỗ trợ subquery scalar trong select list:

```hql
select
    b.id,
    b.title,
    (
        select count(r)
        from Review r
        where r.book = b
    )
from Book b
```

Kết quả là các tuple gồm Book ID, title và số Review. Đây là correlated subquery vì nó tham chiếu b.

Đây không phải cú pháp JPQL portable theo Jakarta Persistence 3.1, vốn giới hạn subquery ở WHERE và HAVING. Nếu cần query chạy trên nhiều JPA provider, hãy cân nhắc join/group by hoặc DTO query tương thích.

### 12.2. Derived root trong FROM

Hibernate HQL hiện đại hỗ trợ derived root: một subquery không tương quan trong FROM, được đặt tên như một nguồn dữ liệu tạm:

```hql
select d.categoryName, d.averagePrice
from (
    select
        b.category.name as categoryName,
        avg(b.price) as averagePrice
    from Book b
    group by b.category.name
) d
where d.averagePrice > :minimum
```

Subquery d tạo một tập kết quả dẫn xuất gồm tên category và giá trung bình. Query ngoài lọc tập kết quả ấy.

Derived root là khả năng HQL/Hibernate-specific, không phải cú pháp JPQL portable. Subquery ở đây phải đáp ứng quy tắc derived root của phiên bản Hibernate sử dụng; đặc biệt, derived root thông thường là subquery không tương quan. Muốn tham chiếu alias bên ngoài trong một subquery ở FROM, cần cú pháp lateral join được hỗ trợ ở phiên bản/dialect thích hợp.

### 12.3. Lateral join

Hibernate HQL hiện đại có thể biểu diễn lateral join cho subquery trong FROM cần tham chiếu nguồn dữ liệu đứng trước. Đây là khả năng phụ thuộc Hibernate version và database dialect; không phải mọi database đều hỗ trợ cùng cú pháp SQL.

Chỉ dùng lateral join khi bài toán cần một tập con phụ thuộc vào từng row bên ngoài và query thông thường/correlated subquery trong WHERE không đủ rõ. Kiểm tra HQL grammar, SQL được sinh và hỗ trợ của dialect trong phiên bản dự án.

## 13. Kiểm tra collection với IS EMPTY

JPA/HQL hỗ trợ IS EMPTY để kiểm tra collection không có phần tử:

```hql
select b
from Book b
where b.reviews is empty
```

Tìm sách chưa có Review. Ngược lại:

```hql
select b
from Book b
where b.reviews is not empty
```

lấy sách đã có ít nhất một Review.

Đây là biểu thức trên collection-valued path, không phải kiểm tra collection Java đã được initialize hay chưa. Database kiểm tra dữ liệu liên quan; query không cần tải toàn bộ collection vào memory.

### 13.1. IS EMPTY so với EXISTS

Hai cách sau có thể diễn đạt cùng ý nghĩa:

```hql
-- Kiểu collection:
select b
from Book b
where b.reviews is empty

-- Kiểu truy vấn con:
select b
from Book b
where not exists (
    select 1
    from Review r
    where r.book = b
)
```

IS EMPTY ngắn gọn khi mapping collection đã có sẵn. NOT EXISTS linh hoạt hơn khi cần thêm điều kiện, ví dụ chỉ xem Review đã được duyệt:

```hql
select b
from Book b
where not exists (
    select 1
    from Review r
    where r.book = b
      and r.approved = true
)
```

Ở đây Book vẫn có thể có Review chưa duyệt; điều kiện chỉ nói không có Review nào đã duyệt.

## 14. MEMBER OF: kiểm tra một phần tử có thuộc collection

MEMBER OF kiểm tra một giá trị/entity có là phần tử của collection:

```hql
select b
from Book b
where :tag member of b.tags
```

Nếu tags là collection entity Tag hoặc collection value phù hợp, truy vấn tìm Book chứa tag được truyền vào.

Phủ định:

```hql
select b
from Book b
where :tag not member of b.tags
```

Giá trị bên trái và phần tử collection phải tương thích kiểu. Nếu collection có thể null theo mapping/đặc điểm dữ liệu, cần hiểu semantics null của biểu thức và cách provider ánh xạ; collection association thông thường được quản lý như collection rỗng khi không có row liên quan.

### 14.1. MEMBER OF với entity reference

Ví dụ:

```hql
select c
from Course c
where :student member of c.students
```

student phải là một Student entity/reference hợp lệ theo kiểu mapping. Có thể bind một entity managed hoặc reference thích hợp. Nếu chỉ có ID, có thể dùng getReference() tại persistence boundary hoặc viết query so sánh ID bằng subquery/association path.

### 14.2. MEMBER OF và EXISTS

Một dạng tương đương thường có thể viết bằng correlated subquery:

```hql
select c
from Course c
where exists (
    select 1
    from Student s
    where s member of c.students
      and s.id = :studentId
)
```

Nếu mapping đã có collection và chỉ cần kiểm tra membership, biểu thức :student member of c.students thường dễ đọc hơn. Dùng EXISTS khi cần thêm điều kiện trên phần tử hoặc kết hợp với entity khác.

## 15. SIZE: lấy số phần tử trong collection

SIZE() trả số phần tử của collection:

```hql
select b
from Book b
where size(b.reviews) >= 10
```

Truy vấn tìm Book có ít nhất 10 Review. SIZE() là phép tính phía query/database; nó không yêu cầu ứng dụng gọi book.getReviews().size() trên từng entity.

So sánh:

```java
for (Book book : books) {
    if (book.getReviews().size() >= 10) {
        // Có thể khởi tạo collection cho từng Book.
    }
}
```

Nếu chỉ cần lọc ở database, đưa điều kiện vào HQL thường hiệu quả và rõ ràng hơn.

### 15.1. SIZE và COUNT

size(b.reviews) phù hợp khi đếm collection được mapping. Một subquery count(r) phù hợp khi cần đếm phần tử theo điều kiện:

```hql
select b
from Book b
where (
    select count(r)
    from Review r
    where r.book = b
      and r.approved = true
) >= 3
```

SIZE(b.reviews) đếm toàn bộ phần tử collection; không nhận predicate để chỉ đếm Review đã duyệt. Dùng count với subquery khi cần điều kiện cụ thể.

## 16. HQL elements() và indices() cho collection

HQL có các hàm collection như elements() và indices() để tham chiếu tập giá trị hoặc chỉ số của collection trong các biểu thức định lượng.

Giả sử một Product có collection giá niêm yết theo vùng:

```java
@ElementCollection
@CollectionTable(
        name = "product_prices",
        joinColumns = @JoinColumn(name = "product_id"))
@Column(name = "price")
private List<BigDecimal> prices = new ArrayList<>();
```

Có thể diễn đạt điều kiện với phần tử collection:

```hql
select p
from Product p
where :maximum >= all elements(p.prices)
```

Ý nghĩa: :maximum lớn hơn hoặc bằng mọi giá trị trong collection prices của Product.

Với một collection có chỉ số (ví dụ List), indices() biểu diễn tập index:

```hql
select b
from Book b
where 0 in indices(b.chapters)
```

Ví dụ này tìm Book có phần tử ở index 0, nếu mapping collection có index và provider hỗ trợ biểu thức đó. Không áp dụng indices() cho collection không có index semantics.

Các hàm elements() và indices() là HQL-specific, không phải lúc nào cũng portable qua JPQL provider khác. Khi dùng, kiểm tra phiên bản Hibernate và loại collection được mapping.

## 17. Collection function và map-valued association

HQL hỗ trợ các biểu thức cho map-valued association:

- key(alias) lấy key của entry trong map.
- value(alias) lấy value.
- entry(alias) biểu diễn entry (key/value pair) trong ngữ cảnh HQL hỗ trợ.

Ví dụ entity có map metadata:

```java
@ElementCollection
@CollectionTable(
        name = "book_attributes",
        joinColumns = @JoinColumn(name = "book_id"))
@MapKeyColumn(name = "attribute_name")
@Column(name = "attribute_value")
private Map<String, String> attributes = new HashMap<>();
```

Query join map:

```hql
select b, key(a), value(a)
from Book b
join b.attributes a
where key(a) = :attributeName
```

Query lấy Book có một key:

```hql
select b
from Book b
where exists (
    select 1
    from Book b2
    join b2.attributes a
    where b2 = b
      and key(a) = :attributeName
      and value(a) = :attributeValue
)
```

Với map join, alias a đại diện cho entry theo semantics HQL. key(a) và value(a) truy cập hai thành phần. entry(a) có thể dùng khi cần trả entry trong select list và được HQL/provider hỗ trợ.

Đừng nhầm key() với identifier của entity value; key có thể là String, enum hoặc kiểu basic tùy mapping.

## 18. Các collection aggregate function của HQL

Ngoài size(), HQL có các hàm dành cho collection được hỗ trợ theo kiểu collection:

| Hàm | Ý nghĩa |
|---|---|
| maxelement(collection) | Phần tử lớn nhất của collection có thứ tự so sánh phù hợp |
| minelement(collection) | Phần tử nhỏ nhất |
| maxindex(collection) | Index lớn nhất của indexed collection |
| minindex(collection) | Index nhỏ nhất |
| elements(collection) | Tập giá trị phần tử |
| indices(collection) | Tập chỉ số |

Ví dụ:

```hql
select b
from Book b
where maxindex(b.chapters) >= 5
```

Truy vấn tìm Book có chỉ số chương lớn nhất ít nhất bằng 5. Với List được index từ 0, điều này có thể tương ứng có một phần tử tại index 5 hoặc cao hơn; nếu collection có gap hoặc thứ tự index đặc biệt, không suy ra số phần tử chính xác từ max index.

Ví dụ với phần tử có thể so sánh:

```hql
select p
from Product p
where maxelement(p.prices) > :threshold
```

Hàm collection-specific phụ thuộc mapping và hỗ trợ HQL/dialect. Nếu cần portable hoặc muốn điều kiện phức tạp, correlated subquery với max()/min() trên entity/value collection table có thể rõ ràng hơn.

## 19. Subquery với điều kiện trên child collection

Giả sử cần tìm Order có ít nhất một dòng hàng số lượng từ 10 trở lên:

```hql
select o
from Order o
where exists (
    select 1
    from OrderLine l
    where l.order = o
      and l.quantity >= :minimumQuantity
)
```

Nếu cần Order mà **mọi** dòng đều có quantity lớn hơn 0:

```hql
select o
from Order o
where not exists (
    select 1
    from OrderLine l
    where l.order = o
      and l.quantity <= 0
)
```

Đây là cách diễn đạt “không tồn tại child vi phạm điều kiện”. Tuy nhiên, nếu Order không có dòng nào, điều kiện NOT EXISTS vẫn đúng. Nếu nghiệp vụ yêu cầu Order phải có ít nhất một dòng, kết hợp thêm:

```hql
and exists (
    select 1
    from OrderLine l2
    where l2.order = o
)
```

Đây là mẫu hữu ích cho nhiều quy tắc:

- Không có dòng hàng bị hủy.
- Không có payment thất bại.
- Không có review chưa kiểm duyệt.
- Không có item vi phạm giới hạn.

## 20. Phân biệt “có ít nhất một” và “tất cả”

Hai quy tắc nghe gần giống nhau nhưng biểu thức khác nhau:

| Yêu cầu | Mẫu HQL |
|---|---|
| Có ít nhất một child đạt điều kiện | EXISTS (select 1 ... where child.condition) |
| Không có child nào đạt điều kiện | NOT EXISTS (select 1 ... where child.condition) |
| Mọi child đều đạt điều kiện | NOT EXISTS (select 1 ... where not condition) |
| Có ít nhất một child và mọi child đạt điều kiện | EXISTS (...) and NOT EXISTS (... where not condition) |
| Số child đạt điều kiện ít nhất N | select count(child) ... >= :n |

Ví dụ “tất cả OrderLine đều đã được xử lý”:

```hql
select o
from Order o
where not exists (
    select 1
    from OrderLine l
    where l.order = o
      and l.processed = false
)
```

Nếu processed là nullable, biểu thức processed = false không bắt được giá trị NULL vì phép so sánh là UNKNOWN. Nếu NULL cũng có nghĩa chưa xử lý, viết:

```hql
and (l.processed = false or l.processed is null)
```

Hoặc thiết kế cột NOT NULL với default phù hợp để giảm sự mơ hồ của trạng thái.

## 21. NULL semantics trong IN, NOT IN và so sánh scalar

SQL dùng logic ba giá trị:

- TRUE
- FALSE
- UNKNOWN (thường phát sinh khi so sánh với NULL)

WHERE chỉ giữ hàng có điều kiện TRUE.

### 21.1. IN với NULL

Giả sử subquery trả tập {10, 20, NULL}:

```hql
where c.id in (
    select x.customerId
    from ImportedOrder x
)
```

- c.id = 10 cho kết quả TRUE.
- c.id = 30 có thể cho UNKNOWN vì không khớp 10/20 và tập có NULL.
- c.id IS NULL cũng không tạo phép so sánh bằng thông thường thành TRUE.

### 21.2. NOT IN với NULL

Nếu subquery trả {10, 20, NULL}, c.id NOT IN (...) có thể là UNKNOWN cho cả ID 30. Đây là lý do truy vấn loại trừ thường nên dùng NOT EXISTS hoặc lọc NULL rõ ràng.

### 21.3. Scalar subquery trả NULL

```hql
where b.price > (
    select avg(b2.price)
    from Book b2
    where b2.category = :category
)
```

Nếu category không có sách, avg() trả NULL. So sánh b.price > NULL là UNKNOWN, nên không trả Book. Nếu cần giá trị mặc định, có thể dùng coalesce():

```hql
where b.price > coalesce(
    (
        select avg(b2.price)
        from Book b2
        where b2.category = :category
    ),
    0
)
```

Chỉ dùng default 0 nếu đúng nghiệp vụ. COALESCE không phải cách chung để che dữ liệu thiếu; phải quyết định rõ “không có dữ liệu” có nghĩa gì.

## 22. EXISTS, JOIN và DISTINCT: chọn đúng cấu trúc

Tìm Customer có Order:

```hql
-- EXISTS:
select c
from Customer c
where exists (
    select 1
    from Order o
    where o.customer = c
)
```

Hoặc:

```hql
-- JOIN:
select distinct c
from Customer c
join c.orders o
```

| Tiêu chí | EXISTS | JOIN |
|---|---|---|
| Mục tiêu | Kiểm tra có ít nhất một hàng phù hợp | Kết hợp dữ liệu từ hai nguồn |
| Số outer rows | Không nhân bản outer entity chỉ vì nhiều hàng con | Có thể tạo nhiều row cho một entity cha |
| Cần lấy field child | Không trực tiếp trả child từ subquery | Có thể select child/field của child |
| Chỉ cần kiểm tra tồn tại | Thường biểu đạt ý định rõ | Có thể cần DISTINCT |
| Điều kiện trên tập con | Dễ dùng với correlated predicate | Có thể dùng ON/WHERE |

Không có quy tắc hiệu năng tuyệt đối rằng EXISTS luôn nhanh hơn JOIN hoặc ngược lại. Optimizer database có thể biến đổi hai cấu trúc. Chọn theo ý nghĩa, cardinality, index và execution plan.

## 23. Chuyển đổi một số bài toán sang subquery

### 23.1. Sách có giá cao hơn trung bình danh mục

```hql
select b
from Book b
where b.price > (
    select avg(b2.price)
    from Book b2
    where b2.category = b.category
)
```

### 23.2. Tác giả chưa có sách

```hql
select a
from Author a
where not exists (
    select 1
    from Book b
    where b.author = a
)
```

### 23.3. Sản phẩm có giá thấp nhất trong danh mục

```hql
select p
from Product p
where p.price = (
    select min(p2.price)
    from Product p2
    where p2.category = p.category
)
```

Nếu nhiều sản phẩm đồng giá thấp nhất, query trả tất cả sản phẩm đồng hạng. Nếu cần đúng một sản phẩm, phải định nghĩa tie-breaker bằng ID hoặc thứ tự khác.

### 23.4. Customer có ít nhất ba đơn đã thanh toán

```hql
select c
from Customer c
where (
    select count(o)
    from Order o
    where o.customer = c
      and o.status = :paidStatus

```

select o
from Order o

    select 1
    from OrderLine l
    where l.order = o
      and l.status = :cancelledStatus

```

select c

    from Product p

```

## 24. Subquery và parameter binding

Không ghép giá trị người dùng trực tiếp vào chuỗi HQL. Dùng named parameters:

```java
String hql = """
    select c
    from Customer c
    where exists (
        select 1
        from Order o
        where o.customer = c
          and o.total >= :minimum
          and o.status = :status
    )
    """;

List<Customer> customers = session.createSelectionQuery(
        hql, Customer.class)
        .setParameter("minimum", new BigDecimal("1000000"))
        .setParameter("status", OrderStatus.PAID)
        .getResultList();
```

Parameter binding giúp Hibernate chuyển đổi kiểu dữ liệu đúng và tránh HQL injection từ giá trị. Tên entity/field và cấu trúc query vẫn phải được kiểm soát ở code; parameter chỉ thay thế giá trị, không thay thế tên field, keyword hay đoạn HQL tùy ý.

### 24.1. Collection parameter

```java
List<Long> customerIds = List.of(1L, 2L, 3L);

List<Customer> result = session.createSelectionQuery(
        "select c from Customer c where c.id in :ids",
        Customer.class)
        .setParameter("ids", customerIds)
        .getResultList();
```

Nếu collection parameter có thể rỗng, xử lý trường hợp đó ở application hoặc dùng một predicate rõ ràng. SQL không thống nhất về cú pháp IN (); provider có thể xử lý collection rỗng khác nhau theo phiên bản.

## 25. HQL so với JPQL: ranh giới portable

HQL của Hibernate có quan hệ gần với JPQL nhưng không hoàn toàn giống. HQL hiện đại mở rộng một số cấu trúc và hàm.

| Tính năng | JPQL portable | HQL Hibernate |
|---|---|---|
| Subquery trong WHERE | Có | Có |
| Subquery trong HAVING | Có | Có |
| EXISTS, NOT EXISTS | Có | Có |
| IN với subquery | Có | Có |
| ALL, ANY, SOME | Có theo cú pháp JPQL | Có |
| IS EMPTY, MEMBER OF, SIZE | Có | Có |
| Subquery trong SELECT list | Không theo JPQL 3.1 | HQL hiện đại hỗ trợ |
| Derived root/subquery trong FROM | Không theo JPQL 3.1 | HQL hiện đại hỗ trợ |
| Lateral join | Không portable theo JPQL 3.1 | Có trong HQL hiện đại khi version/dialect hỗ trợ |
| elements(), indices() và một số collection functions | Không phải tập JPQL chuẩn | HQL-specific |
| Map functions key(), value(), entry() | Có trong JPQL cho map-valued path | Có trong HQL |

Nếu dự án dùng Hibernate làm provider duy nhất, HQL extension có thể giúp query ngắn gọn hơn. Nếu thư viện hoặc ứng dụng cần chuyển provider, giữ query trong tập JPQL chuẩn để giảm phụ thuộc.

## 26. Subquery không phải lúc nào cũng là lựa chọn tốt nhất

Subquery rất hữu ích, nhưng không phải cấu trúc duy nhất.

| Bài toán | Subquery | Cách khác có thể cân nhắc |
|---|---|---|
| Customer có Order | EXISTS | JOIN |
| Customer không có Order | NOT EXISTS | LEFT JOIN + IS NULL |
| Giá cao hơn trung bình nhóm | Correlated scalar subquery | Window function/native SQL hoặc derived table |
| Đếm child theo điều kiện | Correlated COUNT | GROUP BY/HAVING |
| Lấy dữ liệu child để hiển thị | Subquery chỉ kiểm tra điều kiện | JOIN/fetch/projection |
| Kiểm tra collection rỗng | IS EMPTY/NOT EXISTS | Collection join + group |

Ví dụ LEFT JOIN anti-join:

```hql
select c
from Customer c
left join c.orders o
where o.id is null
```

Có thể trả Customer không có Order. NOT EXISTS thường ít bị ảnh hưởng bởi việc chọn cột nullability và tránh row multiplication do nhiều child. Nhưng optimizer và execution plan mới quyết định chi phí thực tế.

### 26.1. Tránh subquery lồng quá sâu

Một query với nhiều tầng correlated subquery có thể khó đọc và khó tối ưu:

```hql
select c
from Customer c
where exists (
    select 1
    from Order o
    where o.customer = c
      and exists (
          select 1
          from OrderLine l
          where l.order = o
            and l.quantity > :quantity
      )
)
```

Có thể viết bằng một subquery với join:

```hql
select c
from Customer c
where exists (
    select 1
    from Order o
    join o.lines l
    where o.customer = c
      and l.quantity > :quantity
)
```

Dạng thứ hai thường dễ theo dõi hơn vì quan hệ giữa Order và OrderLine được thể hiện ngay trong subquery. Chọn cấu trúc đơn giản nhất diễn đạt đúng điều kiện.

## 27. Hiệu năng: index, cardinality và execution plan

Subquery không tự động chậm. EXISTS tương quan có thể được database tối ưu thành semi-join và dừng tìm khi gặp row phù hợp. IN có thể được tối ưu tương tự. Một subquery aggregate có thể cần scan/group dữ liệu đáng kể.

Với:

```hql
select c
from Customer c
where exists (
    select 1
    from Order o
    where o.customer = c
      and o.status = :status
)
```

Index có thể cần cân nhắc:

```sql
CREATE INDEX idx_orders_customer_status
    ON orders(customer_id, status);
```

Nếu query lọc theo customer và status, composite index phù hợp có thể giảm lượng row phải đọc. Thứ tự cột index còn phụ thuộc các query khác và selectivity.

Đối với:

```hql
select b
from Book b
where b.author.id in (
    select a.id
    from Author a
    where a.active = true
)
```

cần xem index trên các cột liên quan như authors.active, books.author_id theo schema thực tế.

Các bước đánh giá:

1. Bật SQL logging để biết HQL sinh SQL nào.
2. Chạy SQL với dữ liệu gần production.
3. Dùng EXPLAIN/execution plan của database.
4. Kiểm tra index, cardinality, row estimate và actual rows.
5. So sánh EXISTS, IN, JOIN hoặc aggregate rewrite bằng cùng điều kiện và dữ liệu.
6. Đo thời gian, logical reads và memory; không chọn chỉ dựa trên cảm giác cú pháp.

## 28. Subquery và pagination

Subquery trong điều kiện thường kết hợp được với pagination:

```java
List<Customer> page = session.createSelectionQuery(
        """
        select c
        from Customer c
        where exists (
            select 1
            from Order o
            where o.customer = c
        )
        order by c.id
        """,
        Customer.class)
        .setFirstResult(0)
        .setMaxResults(50)
        .getResultList();
```

Pagination cần thứ tự ổn định để không trùng/mất row giữa các trang khi dữ liệu thay đổi. Dùng ORDER BY có tie-breaker duy nhất (ví dụ ID). Với dữ liệu lớn, keyset pagination thường phù hợp hơn offset pagination.

Nếu subquery được dùng để tính một scalar cho mỗi row, hãy xem execution plan và chi phí của aggregate. Không dùng fetch join collection chỉ để lọc; subquery EXISTS thường giữ root result gọn hơn.

## 29. Subquery với update/delete HQL

Hibernate HQL hỗ trợ bulk mutation queries và một số điều kiện có subquery tùy grammar/version. Ví dụ xóa những Review thuộc Book đã bị archive:

```hql
delete from Review r
where exists (
    select 1
    from Book b
    where b = r.book
      and b.archived = true
)
```

Bulk mutation chạy trực tiếp trên database, không tải từng entity và không gọi đầy đủ lifecycle/cascade callbacks như thao tác entity-by-entity. Persistence context có thể còn giữ state cũ sau bulk DML; thường cần clear/refresh thích hợp.

Đối với bulk update/delete:

- Chạy trong transaction.
- Kiểm tra cú pháp và giới hạn subquery theo Hibernate version/dialect.
- Không kỳ vọng entity listener/cascade hoạt động giống remove() trên từng managed entity.
- Đồng bộ persistence context và cache sau mutation.
- Kiểm tra số row bị ảnh hưởng và ràng buộc FK.

Nếu cần lifecycle behavior đầy đủ hoặc cascade remove, tải các entity cần xử lý và dùng API entity, hoặc thiết kế quy trình phù hợp.

## 30. Những lỗi thường gặp

| Lỗi | Vì sao xảy ra | Cách xử lý |
|---|---|---|
| Scalar subquery trả nhiều hàng | Dùng phép so sánh scalar nhưng query không đảm bảo một giá trị | Dùng aggregate, giới hạn logic hoặc IN/ANY |
| NOT IN trả không có kết quả | Subquery chứa NULL | Dùng NOT EXISTS hoặc lọc NULL |
| ALL trả true khi subquery rỗng | Đây là semantics logic lượng từ | Thêm EXISTS nếu tập phải có phần tử |
| ANY không khớp khi subquery rỗng | Không có phần tử nào làm điều kiện đúng | Xử lý tập rỗng theo nghiệp vụ |
| So sánh scalar trả UNKNOWN | Aggregate/subquery trả NULL | Dùng IS NULL, COALESCE khi có default hợp lệ |
| Correlated subquery khó tối ưu | Thiếu index hoặc predicate phức tạp | Xem execution plan và cân nhắc join/group |
| SIZE gây SQL không mong đợi | Đang đánh giá collection trong query hoặc truy cập object khác | Kiểm tra SQL; dùng COUNT subquery khi cần predicate |
| MEMBER OF sai kiểu | Phần tử truyền vào không tương thích collection element | Bind đúng entity/value type |
| elements() không chạy trên provider khác | Đây là HQL extension | Dùng JPQL MEMBER OF/subquery hoặc query portable |
| Subquery trong SELECT/FROM không compile | Đang dùng JPQL hoặc Hibernate version không hỗ trợ | Dùng HQL đúng version hoặc rewrite portable |
| Derived root tham chiếu alias ngoài | Derived root thông thường không tương quan | Dùng correlated subquery ở WHERE hoặc lateral join được hỗ trợ |
| Collection parameter rỗng gây SQL lỗi | IN () không portable | Xử lý empty list trước query |
| HQL dùng tên bảng/cột vật lý | HQL truy vấn entity model | Dùng entity name và property path; dùng native SQL nếu cần |
| Query đúng nhưng rất chậm | Index/cardinality không phù hợp | EXPLAIN, kiểm tra index và dữ liệu thực |

## 31. Quy trình viết một subquery rõ ràng

Khi gặp bài toán cần tập hợp:

**Bước 1 — Xác định câu hỏi.** Cần biết có ít nhất một row, không có row, giá trị nằm trong tập, hay so sánh với mọi phần tử?

**Bước 2 — Chọn toán tử.**

- Có ít nhất một: EXISTS.
- Không có: NOT EXISTS.
- Nằm trong tập: IN.
- Lớn hơn mọi giá trị: > ALL.
- Lớn hơn ít nhất một giá trị: > ANY/SOME.
- Một giá trị aggregate: scalar subquery.

**Bước 3 — Xác định correlation.** Subquery có cần tham chiếu alias outer query hay không? Nếu có, alias đó phải nằm trong scope hợp lệ.

**Bước 4 — Xác định kiểu kết quả.** Scalar, một cột nhiều hàng, hay chỉ cần sự tồn tại? Đảm bảo kiểu so sánh tương thích.

**Bước 5 — Xử lý NULL và tập rỗng.** Đặc biệt với NOT IN, ALL, ANY, aggregate và nullable fields.

**Bước 6 — Kiểm tra mapping collection.** IS EMPTY, MEMBER OF, SIZE, elements() và indices() yêu cầu collection path đúng kiểu.

**Bước 7 — Xác định mức portable.** Query cần JPQL chuẩn hay được phép dùng HQL extension như subquery SELECT/FROM và collection functions?

**Bước 8 — Kiểm tra SQL và execution plan.** Đo trên database và dữ liệu thực tế.

## 32. Sơ đồ chọn toán tử

```text
                   Cần điều kiện trên một tập?
                              │
                    Câu hỏi nghiệp vụ là gì?
                              │
          ┌───────────────────┼──────────────────┐
          │                   │                  │
      Có phần tử?        Không có phần tử?    So sánh giá trị?
          │                   │                  │
          ▼                   ▼                  ▼
       EXISTS             NOT EXISTS       Tập có một giá trị?
                                                  │
                                          ┌───────┴───────┐
                                         CÓ             NHIỀU
                                          │               │
                                          ▼               ▼
                                    Scalar subquery   IN / ALL / ANY
                                          │
                                          ▼
                                  Aggregate hoặc query
                                  bảo đảm tối đa một row

       Collection mapping:
         rỗng?       → IS EMPTY
         có phần tử? → MEMBER OF
         đếm phần tử → SIZE / COUNT
         lượng từ    → elements() / indices() (HQL)
```

## 33. Tổng kết

Subquery giúp HQL biểu đạt điều kiện dựa trên dữ liệu của một tập khác. EXISTS và NOT EXISTS phù hợp khi chỉ cần biết có hay không có hàng liên quan. IN kiểm tra membership trong tập kết quả. ALL và ANY/SOME diễn đạt so sánh với mọi hoặc ít nhất một phần tử. Scalar subquery kết hợp với avg, min, max, sum và count để tạo giá trị so sánh.

Với collection, IS EMPTY, MEMBER OF và SIZE là các biểu thức chuẩn hữu ích; HQL còn có elements(), indices() và các hàm collection-specific. Correlated subquery tham chiếu alias ngoài, còn uncorrelated subquery có thể đánh giá độc lập. HQL hiện đại hỗ trợ một số vị trí và cấu trúc rộng hơn JPQL như subquery trong SELECT, derived root trong FROM và lateral join, nhưng các khả năng này phụ thuộc phiên bản và không portable.

Khi viết query, hãy xác định đúng câu hỏi trên tập hợp, chọn toán tử tương ứng, xử lý NULL/tập rỗng, bind parameter và kiểm tra SQL thực tế. Cú pháp subquery tốt nhất là cú pháp thể hiện đúng invariant nghiệp vụ và cho database một kế hoạch thực thi hiệu quả.
