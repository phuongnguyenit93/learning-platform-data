# Khóa thực thể, định danh Java và khóa chính trong cơ sở dữ liệu

## 1. Một thực thể có bao nhiêu loại “danh tính”?

Trong Hibernate ORM, từ **định danh** (*identity*) dễ được dùng cho ba khái niệm liên quan nhưng không trùng nhau:

1. **Định danh tham chiếu Java** (*object/reference identity*): hai biến có trỏ tới cùng một object trong JVM hay không, kiểm tra bằng `==`.
2. **Định danh của thực thể trong mô hình ORM** (*entity identity*): một entity thuộc loại nào, mang giá trị khóa định danh gì, và đang thuộc persistence context nào. Hibernate dùng định danh này để theo dõi entity trong `Session`.
3. **Khóa chính của hàng dữ liệu** (*relational primary key*): một hoặc nhiều cột mà database ràng buộc tính duy nhất và không nhận `NULL`, dùng để xác định một hàng trong bảng.

Một khái niệm thứ tư thường xuất hiện là **khóa nghiệp vụ** (*business key/natural key*), chẳng hạn mã ISBN, mã quốc gia hoặc số đơn hàng do hệ thống bên ngoài cấp. Khóa này có thể duy nhất theo yêu cầu nghiệp vụ nhưng không nhất thiết được chọn làm primary key.

Ví dụ bảng `books`:

```text
books
┌──────┬──────────────────────┬─────────────────────┐
│ id   │ title                │ isbn                │
├──────┼──────────────────────┼─────────────────────┤
│ 101  │ Hibernate căn bản    │ 9780000000101       │
│ 102  │ Java và dữ liệu      │ 9780000000102       │
└──────┴──────────────────────┴─────────────────────┘

                Database: id = 101 là PRIMARY KEY
                         │
                         ▼
             Hibernate Book entity, id = 101
                         │
          ┌──────────────┴─────────────┐
          │                            │
    Trong Session A              Trong Session B
    Book object A                Book object B
    (tham chiếu Java A)          (tham chiếu Java B)
          │                            │
       A != B                     A.id == B.id
          └──────────────┬─────────────┘
                         ▼
               Cùng một hàng database
```

Trong cùng một persistence context, Hibernate bảo đảm một entity theo một khóa ORM được biểu diễn bằng một managed instance thống nhất. Qua hai session khác nhau, hai object Java có thể có cùng `id` nhưng `a == b` là `false`.

Để thiết kế đúng entity, khóa chính và `equals()/hashCode()`, trước tiên cần biết đang nói đến loại danh tính nào.

## 2. Bảng so sánh các tầng định danh

| Cấp độ | Được xác định bằng | Phạm vi | Kiểm tra/biểu diễn phổ biến |
|---|---|---|---|
| Java reference identity | Vị trí object được tham chiếu trong JVM | Trong bộ nhớ process | `a == b` |
| Java logical equality | Hợp đồng `equals()` do class định nghĩa | Các object Java, có thể qua nhiều session | `a.equals(b)` |
| Hibernate entity identity | Entity type/role + identifier, kèm ngữ cảnh quản lý/tenant khi cần | Persistence context | `Session.get(Book.class, 101L)` |
| Database primary key | Giá trị một hoặc nhiều cột PK | Một bảng/không gian định danh database | `PRIMARY KEY (id)` |
| Natural/business key | Một hoặc nhiều thuộc tính có ý nghĩa nghiệp vụ | Theo quy tắc domain, đôi khi có scope | `UNIQUE (isbn)` |
| Foreign key | Một hoặc nhiều cột tham chiếu khóa ở bảng khác | Quan hệ ràng buộc giữa các bảng | `FOREIGN KEY (book_id) REFERENCES books(id)` |

**Khóa chính** và **khóa ngoại** có mục đích khác nhau. Khóa chính định danh hàng trong bảng của nó. Khóa ngoại biểu diễn liên kết và bảo vệ tính toàn vẹn tham chiếu. Một cột có thể vừa là thành phần PK vừa là FK trong những thiết kế như shared primary key one-to-one hoặc composite key, nhưng không phải mọi FK đều là PK.

## 3. Một entity mẫu: ánh xạ @Id tới PRIMARY KEY

Giả sử ứng dụng quản lý sách bằng Hibernate với Jakarta Persistence API. Schema PostgreSQL tối giản:

```sql
CREATE TABLE books (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title VARCHAR(255) NOT NULL,
    isbn VARCHAR(32) NOT NULL,
    version BIGINT NOT NULL DEFAULT 0,
    CONSTRAINT uq_books_isbn UNIQUE (isbn)
);
```

Ở đây:

- `id` là **surrogate key**: giá trị kỹ thuật không biểu đạt trực tiếp nghiệp vụ.
- `isbn` là **candidate/business key**: duy nhất theo ràng buộc của ứng dụng.
- `version` dùng cho optimistic locking, không phải một phần của primary key.
- Database chịu trách nhiệm thực thi `PRIMARY KEY` và `UNIQUE`; cấu hình Java phải khớp với schema thực tế.

Entity:

```java
package com.example.library.domain;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;
import jakarta.persistence.Version;
import org.hibernate.annotations.NaturalId;

@Entity
@Table(name = "books")
public class Book {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 255)
    private String title;

    @NaturalId(mutable = false)
    @Column(nullable = false, unique = true, length = 32)
    private String isbn;

    @Version
    private Long version;

    protected Book() {
        // Constructor cho JPA/Hibernate.
    }

    public Book(String isbn, String title) {
        if (isbn == null || isbn.isBlank()) {
            throw new IllegalArgumentException("ISBN không hợp lệ");
        }
        if (title == null || title.isBlank()) {
            throw new IllegalArgumentException("Tiêu đề không hợp lệ");
        }
        this.isbn = isbn;
        this.title = title;
    }

    public Long getId() { return id; }
    public String getIsbn() { return isbn; }
    public String getTitle() { return title; }
    public Long getVersion() { return version; }

    public void rename(String newTitle) {
        if (newTitle == null || newTitle.isBlank()) {
            throw new IllegalArgumentException("Tiêu đề không hợp lệ");
        }
        this.title = newTitle;
    }
}
```

`@Id` cho Hibernate biết trường nào là **identifier mapping** của entity. `@GeneratedValue` cho biết cách tạo giá trị định danh. `@NaturalId` là khả năng riêng của Hibernate, giúp khai báo một khóa tự nhiên và hỗ trợ truy xuất theo thuộc tính ấy. `@Version` dùng để phát hiện cập nhật cạnh tranh; bản thân nó không làm hàng có thêm định danh.

Vì `@Id` được đặt trên field, đây là **field access**. Hibernate đọc/ghi trạng thái được ánh xạ qua field theo cơ chế của ORM; việc không có public setter cho `id` giúp code nghiệp vụ tránh tự ý thay khóa chính.

Đối với hệ thống sử dụng migrations, schema được tạo bằng công cụ như Flyway/Liquibase và Hibernate có thể chạy ở chế độ `validate`. Đừng giả định `@Id` tự thêm primary-key constraint vào database đã tồn tại nếu Hibernate không quản lý việc tạo schema.

## 4. Hibernate dùng identifier trong persistence context như thế nào?

Mỗi `Session`/persistence context giữ một **identity map** cho các entity đang được quản lý. Hibernate không chỉ tra một con số ID thuần túy: danh tính cần phân biệt loại entity, identifier, và trong mô hình đa tenant còn có tenant/scope phù hợp.

Trong cùng session:

```java
import org.hibernate.Session;

try (Session session = sessionFactory.openSession()) {
    Book first = session.get(Book.class, 101L);
    Book second = session.get(Book.class, 101L);

    if (first != null) {
        System.out.println(first == second); // true
    }
}
```

Lệnh `get()` đầu tiên thường cần truy vấn database nếu entity chưa nằm trong persistence context. Lệnh tiếp theo với cùng entity type và ID có thể dùng managed instance sẵn có. Điều này không có nghĩa tất cả câu HQL sau đó đều bỏ qua database: truy vấn tìm kiếm vẫn có thể thực thi SQL để xác định tập kết quả.

Qua hai session độc lập:

```java
Book first;
Book second;

try (Session session1 = sessionFactory.openSession()) {
    first = session1.get(Book.class, 101L);
}
try (Session session2 = sessionFactory.openSession()) {
    second = session2.get(Book.class, 101L);
}

if (first != null && second != null) {
    System.out.println(first == second);            // false thường gặp
    System.out.println(first.getId().equals(
            second.getId()));                       // true
}
```

Đây là lý do không nên dùng `==` để quyết định liệu hai detached entity qua các request có đại diện cùng một hàng dữ liệu hay không. Cùng một entity key có thể có **nhiều biểu diễn object ở các session khác nhau**, nhưng chỉ một managed instance tương ứng trong mỗi persistence context.

### Hibernate có phải chỉ dựa vào @Id để quyết định UPDATE không?

Không. Hibernate còn quản lý trạng thái entity, snapshot phục vụ dirty checking, trạng thái lifecycle và transaction. `@Id` giúp xác định hàng nào cần thao tác; dirty checking quyết định **có thay đổi nào cần đồng bộ** hay không.

```text
Session / Persistence Context
  ├─ Identity key: (Book, id=101)
  │     └─ Managed Book instance
  ├─ Trạng thái hiện tại: title = "Hibernate 2"
  ├─ Trạng thái đã tải: title = "Hibernate 1"
  └─ flush:
         └─ UPDATE books SET title = ... WHERE id = 101
```

SQL thực tế có thể có thêm điều kiện optimistic locking trên `version`, và các cột được đưa vào `UPDATE` phụ thuộc mapping/cấu hình Hibernate. Nếu `@Version` được dùng, bản thân cặp `id + version` hỗ trợ phát hiện cập nhật trên phiên bản cũ, nhưng **primary key vẫn là `id`**.

## 5. ==, equals() và hashCode(): ba quy tắc cần phân biệt

Trong Java:

- `a == b` đối với object kiểm tra **cùng reference**.
- `a.equals(b)` kiểm tra **logical equality** theo hợp đồng do class định nghĩa. Nếu không override `Object.equals()` thì thường tương đương reference equality.
- `a.hashCode()` hỗ trợ các cấu trúc hash như `HashSet` và `HashMap`. Nếu `a.equals(b) == true`, hai object bắt buộc có cùng hash code; chiều ngược lại không bắt buộc.

Ví dụ hai record chứa cùng giá trị:

```java
record BookView(Long id, String title) {}

BookView a = new BookView(101L, "Hibernate");
BookView b = new BookView(101L, "Hibernate");

System.out.println(a == b);      // false
System.out.println(a.equals(b)); // true: record so sánh theo components
```

Record phù hợp với **value equality**. Entity có identity và lifecycle riêng; một entity giữ cùng `id` ngay cả khi `title` thay đổi. Vì vậy không nên dùng logic equality của record gồm mọi field mutable làm khuôn mặc định cho entity.

### 5.1. Có nhất thiết phải override equals/hashCode trên entity?

**Không phải lúc nào cũng cần.** Nếu thao tác với entity chỉ trong một persistence context, không cần so sánh detached instance giữa các session hay đưa entity vào Set/Map với ý nghĩa domain equality, giữ reference equality mặc định có thể đơn giản hơn.

Khi application cần so sánh cùng entity qua nhiều session, sử dụng Set chứa entity, hoặc thao tác detached/merged object, cần có **hợp đồng equality nhất quán**. Có hai nhóm lựa chọn:

1. Dựa trên identifier database khi identifier đã có giá trị ổn định.
2. Dựa trên một business key duy nhất, bất biến, được chuẩn hóa và được database ràng buộc.

Không có một đoạn `equals()/hashCode()` phù hợp mọi entity hierarchy, proxy và chiến lược ID.

### 5.2. Cạm bẫy: hashCode thay đổi sau khi persist

Một cách triển khai tưởng hợp lý nhưng dễ gây lỗi:

```java
// VÍ DỤ KHÔNG KHUYẾN NGHỊ với generated ID:
@Override
public int hashCode() {
    return java.util.Objects.hashCode(id);
}
```

Với entity mới, `id == null`. Sau khi Hibernate cấp ID, `hashCode()` đổi giá trị. Nếu object đã nằm trong `HashSet`, bucket hash ban đầu không còn tương ứng:

```java
Book book = new Book("9780000000101", "Hibernate");
Set<Book> books = new HashSet<>();
books.add(book);       // id thường đang null

session.persist(book); // Hibernate có thể cấp ID tại đây
// Nếu hashCode() phụ thuộc trực tiếp vào id thì books.contains(book)
// có thể trả false dù chính object đó đang nằm trong Set.
```

Thời điểm ID được cấp thay đổi theo generation strategy, nhưng lỗi logic vẫn giống nhau: **đổi thành phần quyết định hashCode của key sau khi đã chèn vào hash collection**.

### 5.3. Một mẫu equality dựa trên generated ID

Với entity đơn giản **không dùng kế thừa entity**, ID sinh bởi database và không thay đổi sau khi gắn vào entity, có thể dùng mẫu sau:

```java
import java.util.Objects;

@Override
public boolean equals(Object other) {
    if (this == other) {
        return true;
    }
    if (!(other instanceof Book that)) {
        return false;
    }
    // Hai transient entity có id=null không được coi là bằng nhau.
    return getId() != null
            && Objects.equals(getId(), that.getId());
}

@Override
public int hashCode() {
    // Không đổi khi null id được thay bằng generated id.
    return Book.class.hashCode();
}
```

Ví dụ trên là **phần method thêm vào entity `Book`**, không phải class đầy đủ độc lập. Nó cho phép cùng một book có ID 101 được xem là bằng nhau qua các session, trong khi hai book mới có `id == null` khác nhau trừ khi là cùng reference.

Một hash code hằng theo loại entity tuân thủ hợp đồng Set/Map và không đổi khi phát sinh ID, đổi lại phân bố bucket có thể kém đối với **rất nhiều entity trong một HashSet/HashMap**. Cần cân nhắc nhu cầu thực tế.

**Giới hạn quan trọng:** với entity có kế thừa, proxy/lazy loading hoặc equality giữa các subtype, mẫu `instanceof Book` có thể không biểu diễn đúng ngữ nghĩa domain. Khi cần so sánh “đúng concrete entity class”, hãy xử lý class qua cơ chế nhận diện proxy của Hibernate và thiết kế `equals()`/`hashCode()` tương thích; gọi thẳng `getClass()` trên proxy có thể nhận subclass proxy thay vì class thực. Cần thống nhất một chiến lược cho cả hierarchy.

### 5.4. Equality theo khóa nghiệp vụ

Với khóa nghiệp vụ **duy nhất và không thay đổi**, có thể có tình huống equality theo ISBN:

```java
// Chỉ minh họa cho domain thực sự coi ISBN là identity
// và yêu cầu ISBN không null, chuẩn hóa, không đổi.
@Override
public boolean equals(Object other) {
    if (this == other) return true;
    if (!(other instanceof Book that)) return false;
    return getIsbn().equals(that.getIsbn());
}

@Override
public int hashCode() {
    return getIsbn().hashCode();
}
```

Mẫu này chỉ an toàn nếu `isbn` đã được gán trước khi object đưa vào Set, không bị đổi, có uniqueness bảo đảm và mọi Book cùng ISBN được domain coi là cùng thực thể. Nếu một ấn bản/sách vật lý có nhiều bản sao dùng chung ISBN, thì ISBN **không** định danh duy nhất từng bản sao; dùng nó cho equality sẽ sai ngay cả khi SQL không báo lỗi.

Không nên tự động kết luận `@NaturalId` luôn phải là khóa của `equals()/hashCode()`. Natural ID trong Hibernate và Java equality là hai quyết định kiến trúc riêng.

## 6. Vòng đời entity và thời điểm ID xuất hiện

Một đối tượng Hibernate có thể đi qua các trạng thái:

```text
new Book(...)                  session.persist(book)
    │                                  │
    ▼                                  ▼
TRANSIENT ─────────────────────────► MANAGED
                                       │
                              flush / commit
                                       │
                     SQL INSERT và database xác nhận
                                       │
                        session.close / clear
                                       │
                                       ▼
                                    DETACHED
                                       │
                         session.merge(detached)
                                       │
                                       ▼
                               instance MANAGED mới
```

Trong trường hợp ID được sinh:

```java
Book book = new Book("9780000000101", "Hibernate");
System.out.println(book.getId()); // Thường null trước persist

session.persist(book);
System.out.println(book.getId()); // Có thể đã có ID tùy strategy

session.flush();
System.out.println(book.getId()); // Với mapping phù hợp, đã có ID

transaction.commit();
```

**Đừng đồng nhất “đã có ID” với “đã commit”.** Với `IDENTITY`, Hibernate thường phải gửi `INSERT` sớm để lấy ID từ database. Với sequence, Hibernate có thể lấy số sequence trước khi gửi `INSERT`. Dù ID đã được cấp, transaction vẫn có thể rollback và hàng chưa bao giờ được commit.

### Transient, managed và detached có nhất thiết khác ID?

Không. Một detached entity có thể mang `id=101`; trong session mới, `session.get(Book.class, 101L)` trả về một managed instance khác cùng database ID. Hibernate không bắt detached object cũ thành managed chỉ vì ID trùng.

`merge()` sao chép trạng thái detached sang managed instance rồi **trả về managed instance**:

```java
Book detached = /* entity từ session đã đóng */;

try (Session session = sessionFactory.openSession()) {
    Transaction tx = session.beginTransaction();
    try {
        Book managed = session.merge(detached);
        // managed có thể khác reference với detached.
        tx.commit();
    } catch (RuntimeException | Error ex) {
        if (tx.isActive()) tx.rollback();
        throw ex;
    }
}
```

Trước khi dùng `merge()` với entity detached, cần phân biệt trường hợp cập nhật hợp lệ và dữ liệu stale. Nếu entity có `@Version`, Hibernate có thể phát hiện xung đột optimistic locking. Không coi `merge()` là cách “upsert theo ID” vô điều kiện; hành vi với entity có/không có ID, bản ghi đã bị xóa, version và database state phụ thuộc mapping và Hibernate version.

## 7. Chọn kiểu dữ liệu cho khóa chính

Một số lựa chọn phổ biến:

| Kiểu Java | Cột database thường dùng | Ưu điểm | Đánh đổi |
|---|---|---|---|
| `Long` | `BIGINT` | Nhỏ, dễ index/join, thuận lợi khi dùng sequence/identity | Không sẵn duy nhất xuyên hệ thống nếu chưa có chiến lược cấp ID |
| `Integer` | `INTEGER` | Dễ hiểu, dung lượng nhỏ | Dải giá trị giới hạn hơn; có thể hết nếu dữ liệu tăng |
| `UUID` | `UUID` hoặc kiểu tương đương | Có thể sinh ID ở application; hữu ích khi cần nhiều node tạo dữ liệu | Kích thước lớn hơn số nguyên; độ phân tán ảnh hưởng storage/index tùy phiên bản UUID và database |
| `String` | `VARCHAR`/`CHAR` | Hợp với khóa mã ổn định từ domain/hệ ngoài | Index và collation có thể tốn hơn; nguy cơ key đổi theo nghiệp vụ |
| Composite ID class | Nhiều cột PK | Biểu diễn định danh phụ thuộc các thuộc tính khác | FK và join dài hơn; equality/mapping phức tạp |

Ưu tiên kiểu wrapper `Long` thay vì primitive `long` cho khóa sinh tự động vì `null` biểu diễn rõ “chưa được cấp định danh”. Với primitive có giá trị mặc định 0, code dễ nhầm trạng thái “chưa persist” với ID hợp lệ hoặc cơ chế unsaved-value. Dù có thể dùng primitive trong những mapping, wrapper thường dễ quản lý vòng đời hơn.

Khóa chính nên:

- **Duy nhất** trong phạm vi bảng/tenant được thiết kế.
- **Ổn định:** không đổi khi business field thay đổi.
- **Không null:** database cưỡng chế bằng `PRIMARY KEY`.
- **Tối giản:** tránh đưa thông tin có thể sửa vào composite PK nếu không cần.
- **Có kế hoạch sinh/cấp khóa:** không phụ thuộc vào việc “lấy MAX(id) + 1” trong ứng dụng nhiều luồng.

Nếu database hỗ trợ `BIGINT` và số lượng hàng vừa/lớn trong phạm vi một database, generated numeric key thường là lựa chọn thuận tiện. Nếu cần sinh ID trước khi nối database hoặc giữa nhiều service, UUID có thể phù hợp. Không có một kiểu dữ liệu tối ưu cho mọi hệ thống.

## 8. @GeneratedValue và các chiến lược sinh khóa

Jakarta Persistence cung cấp `@GeneratedValue` với nhiều chiến lược. Hibernate hiện đại bổ sung các generator và tối ưu riêng, nhưng chọn strategy phải tương thích database/dialect và cách vận hành.

### 8.1. IDENTITY: database sinh khóa khi INSERT

```java
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;
```

Ví dụ PostgreSQL:

```sql
CREATE TABLE books (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title VARCHAR(255) NOT NULL
);
```

Hibernate cần nhận giá trị khóa được database cấp (thường qua JDBC generated keys/RETURNING hoặc cơ chế tương ứng). Vì ID phụ thuộc `INSERT`, Hibernate có thể phải gửi insert sớm và **khả năng gom JDBC insert batch thường bị hạn chế** với mapping `IDENTITY`.

Số identity được sinh không nhất thiết liên tục, nhất là khi insert thất bại hoặc transaction rollback. Không nên dùng ID làm số thứ tự chứng từ phải liên tục không đứt quãng.

### 8.2. SEQUENCE: lấy khóa từ database sequence

```java
import jakarta.persistence.SequenceGenerator;

@Id
@GeneratedValue(
        strategy = GenerationType.SEQUENCE,
        generator = "book_id_seq_gen")
@SequenceGenerator(
        name = "book_id_seq_gen",
        sequenceName = "book_id_seq",
        allocationSize = 50)
private Long id;
```

Ví dụ schema:

```sql
CREATE SEQUENCE book_id_seq START WITH 1 INCREMENT BY 50;

CREATE TABLE books (
    id BIGINT PRIMARY KEY,
    title VARCHAR(255) NOT NULL
);
```

Ví dụ minh họa một cấu hình sequence tăng theo block 50, nhưng cách Hibernate phân bổ dải ID phụ thuộc **optimizer/phiên bản/cấu hình**. Hãy đồng bộ `allocationSize`, database sequence increment và chiến lược generator; không tự ý thay tham số của một bên khi ứng dụng đang chạy.

Với cơ chế cấp phát tối ưu, Hibernate có thể lấy một vùng ID cho nhiều entity, giúp giảm số lần truy vấn sequence và thuận lợi hơn cho batching so với `IDENTITY`. Hệ quả tự nhiên là ID có thể **nhảy số**, nhất là khi process restart hoặc giao dịch rollback.

### 8.3. TABLE: bảng riêng dùng để cấp định danh

`GenerationType.TABLE` dùng một bảng giữ trạng thái phân phối ID. Nó có thể dùng khi database hoặc môi trường không hỗ trợ chiến lược phù hợp khác, nhưng thường thêm round trip và nguy cơ tranh chấp trên bảng cấp số.

```java
@Id
@GeneratedValue(strategy = GenerationType.TABLE)
private Long id;
```

Trong ứng dụng cần hiệu năng, nên xem xét `SEQUENCE` hoặc `IDENTITY` nếu database hỗ trợ. Muốn dùng TABLE có kiểm soát, hãy cấu hình generator và schema rõ ràng thay vì phụ thuộc tên bảng được provider tự đặt.

### 8.4. AUTO: để provider chọn

```java
@Id
@GeneratedValue(strategy = GenerationType.AUTO)
private Long id;
```

`AUTO` không có nghĩa “mọi database đều cấp ID giống nhau”. Hibernate quyết định generator dựa trên loại identifier, dialect và cấu hình/provider version. Nếu chuyển database hoặc nâng cấp Hibernate, cần xem xét hệ quả đối với schema và dữ liệu đã có.

Trong hệ thống có migration được quản lý chặt, khai báo generator cụ thể giúp DBA và application thống nhất hơn về nguồn cấp ID.

### 8.5. UUID: identifier được biểu diễn bằng UUID

Với Jakarta Persistence 3.1 trở lên và Hibernate version hỗ trợ:

```java
import java.util.UUID;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;

@Id
@GeneratedValue(strategy = GenerationType.UUID)
private UUID id;
```

UUID có thể được tạo ở application trước khi `INSERT`, nhưng **thời điểm chính xác và phiên bản UUID được dùng** phụ thuộc provider/generator. Nếu cần UUIDv7 hoặc quy tắc định danh đặc thù, phải chọn generator phù hợp và xác nhận hỗ trợ trên stack đang dùng.

UUID đặc biệt hữu ích khi dữ liệu được tạo độc lập ở nhiều node, đồng bộ offline hoặc cần ID trước khi lưu. Nó không bảo đảm quyền truy cập: một UUID khó đoán **không thay cho kiểm tra authorization** khi API nhận ID từ client.

### 8.6. ID được ứng dụng cấp trước

Một số entity có khóa có ý nghĩa nghiệp vụ, chẳng hạn mã tiền tệ theo chuẩn nghiệp vụ:

```java
import jakarta.persistence.Entity;
import jakarta.persistence.Id;

@Entity
public class CurrencyCode {
    @Id
    private String code;

    private String displayName;

    protected CurrencyCode() {}

    public CurrencyCode(String code, String displayName) {
        this.code = code;
        this.displayName = displayName;
    }

    public String getCode() { return code; }
    public String getDisplayName() { return displayName; }
}
```

```java
session.persist(new CurrencyCode("VND", "Vietnamese dong"));
```

Ở đây không có `@GeneratedValue`: ứng dụng phải gán `code` hợp lệ trước khi persist. Database vẫn cần `PRIMARY KEY(code)`, và code nghiệp vụ phải bảo đảm mã không được sửa sau khi đã tham chiếu từ nơi khác. Nếu có người tạo trùng code, database là nơi cuối cùng phát hiện vi phạm uniqueness.

## 9. Primary key và natural key không phải một

Một hệ thống có thể chọn surrogate PK `id` đồng thời có business key `isbn` duy nhất:

```sql
CREATE TABLE books (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    isbn VARCHAR(32) NOT NULL,
    title VARCHAR(255) NOT NULL,
    CONSTRAINT uq_books_isbn UNIQUE (isbn)
);
```

Việc tách hai khóa mang lại các lợi ích:

- Quan hệ giữa bảng dùng một PK nhỏ, ổn định.
- Business key có thể có quy tắc chuẩn hóa/thay đổi mà không phải cập nhật mọi FK.
- Có thể tạo thêm unique key theo email, mã sản phẩm hoặc key thuộc scope cụ thể.
- Entity vẫn dùng `@Id` tương ứng `id`; lookup nghiệp vụ có thể theo `isbn`.

Hibernate cung cấp `@NaturalId`:

```java
@NaturalId(mutable = false)
@Column(nullable = false, unique = true)
private String isbn;
```

Và API lookup (với Hibernate `Session`):

```java
Book book = session.byNaturalId(Book.class)
        .using("isbn", "9780000000101")
        .load();
```

`@NaturalId` không thay thế `@Id`, và bản thân annotation không thể bảo đảm dữ liệu không trùng nếu database schema chưa có unique constraint phù hợp. Hibernate có cơ chế natural-id resolution/cache tùy cấu hình; cần hiểu chi phí đồng bộ khi natural ID mutable.

Một business key chỉ nên coi là natural ID bất biến nếu chính sách domain thực sự bảo đảm không đổi. Ví dụ email thường có thể sửa; mã số thuế hoặc mã sản phẩm đôi khi được hiệu chỉnh. Nếu các trường đó thay đổi, dùng chúng làm PK hoặc Java hash code sẽ gây nhiều hệ quả hơn việc giữ một surrogate key ổn định.

### Unique constraint trong database giải quyết điều gì?

Hai transaction có thể cùng đọc “chưa có ISBN X” rồi cùng cố gắng insert:

```text
Transaction A               Transaction B
     │                            │
Query ISBN X: không có      Query ISBN X: không có
     │                            │
INSERT ISBN X               INSERT ISBN X
     │                            │
COMMIT                      Có thể fail vì UNIQUE
```

Kiểm tra tồn tại ở application **không thay** unique constraint, vì có race condition. Cần dựa vào database constraint và xử lý exception phù hợp trong transaction. Với unique key nhiều cột hoặc có giá trị null, quy tắc uniqueness và nullability khác nhau theo database; thiết kế schema phải đúng domain.

## 10. Khóa chính đơn và khóa chính tổng hợp

### 10.1. Khóa chính đơn

```sql
CREATE TABLE customers (
    id BIGINT PRIMARY KEY,
    name VARCHAR(100) NOT NULL
);
```

```java
@Entity
public class Customer {
    @Id
    private Long id;
    // Các thuộc tính khác...
}
```

Một field `@Id` ánh xạ một giá trị định danh đơn. Đây thường là mô hình đơn giản nhất để thao tác với `EntityManager.find(Customer.class, id)` và liên kết FK.

### 10.2. Composite PK: khi một hàng cần nhiều cột để định danh

Ví dụ chi tiết đơn hàng được định danh bằng **mã đơn hàng và số thứ tự dòng**:

```sql
CREATE TABLE order_lines (
    order_id BIGINT NOT NULL,
    line_no INTEGER NOT NULL,
    sku VARCHAR(64) NOT NULL,
    quantity INTEGER NOT NULL,
    CONSTRAINT pk_order_lines PRIMARY KEY (order_id, line_no)
);
```

JPA thường dùng `@EmbeddedId` hoặc `@IdClass`. Với `@EmbeddedId`, định danh là một đối tượng giá trị:

```java
package com.example.shop.domain;

import jakarta.persistence.Embeddable;
import java.io.Serializable;
import java.util.Objects;

@Embeddable
public class OrderLineId implements Serializable {

    private Long orderId;
    private Integer lineNo;

    protected OrderLineId() {}

    public OrderLineId(Long orderId, Integer lineNo) {
        this.orderId = Objects.requireNonNull(orderId);
        this.lineNo = Objects.requireNonNull(lineNo);
    }

    public Long getOrderId() { return orderId; }
    public Integer getLineNo() { return lineNo; }

    @Override
    public boolean equals(Object other) {
        if (this == other) return true;
        if (!(other instanceof OrderLineId that)) return false;
        return Objects.equals(orderId, that.orderId)
                && Objects.equals(lineNo, that.lineNo);
    }

    @Override
    public int hashCode() {
        return Objects.hash(orderId, lineNo);
    }
}
```

Entity:

```java
package com.example.shop.domain;

import jakarta.persistence.Column;
import jakarta.persistence.EmbeddedId;
import jakarta.persistence.Entity;
import jakarta.persistence.Table;

@Entity
@Table(name = "order_lines")
public class OrderLine {

    @EmbeddedId
    private OrderLineId id;

    @Column(nullable = false, length = 64)
    private String sku;

    @Column(nullable = false)
    private int quantity;

    protected OrderLine() {}

    public OrderLine(OrderLineId id, String sku, int quantity) {
        this.id = id;
        this.sku = sku;
        this.quantity = quantity;
    }

    public OrderLineId getId() { return id; }
    public String getSku() { return sku; }
    public int getQuantity() { return quantity; }
}
```

Tra cứu bằng **toàn bộ** khóa:

```java
OrderLineId key = new OrderLineId(500L, 2);
OrderLine line = session.get(OrderLine.class, key);
```

`OrderLineId` phải có equality/hash code dựa trên các thành phần khóa. Với khóa đơn `Long`, class ID không cần thiết; với composite key, class giúp định danh trở thành một giá trị Java có cấu trúc và tránh nhầm thứ tự cột.

### 10.3. @IdClass là cách biểu diễn khác

Với `@IdClass`, entity khai báo nhiều field `@Id`, còn class ID mô tả cùng tên và kiểu thành phần:

```java
import jakarta.persistence.Entity;
import jakarta.persistence.Id;
import jakarta.persistence.IdClass;

@Entity
@IdClass(OrderLineKey.class)
public class OrderLineWithIdClass {
    @Id
    private Long orderId;

    @Id
    private Integer lineNo;

    private String sku;

    protected OrderLineWithIdClass() {}
}
```

```java
import java.io.Serializable;
import java.util.Objects;

public class OrderLineKey implements Serializable {
    public Long orderId;
    public Integer lineNo;

    public OrderLineKey() {}

    public OrderLineKey(Long orderId, Integer lineNo) {
        this.orderId = orderId;
        this.lineNo = lineNo;
    }

    @Override
    public boolean equals(Object other) {
        if (this == other) return true;
        if (!(other instanceof OrderLineKey that)) return false;
        return Objects.equals(orderId, that.orderId)
                && Objects.equals(lineNo, that.lineNo);
    }

    @Override
    public int hashCode() {
        return Objects.hash(orderId, lineNo);
    }
}
```

Ví dụ `@IdClass` mang tính minh họa về cú pháp; khi áp dụng cho bảng `order_lines` thực, cần thêm `@Table`, `@Column(name = "...")` và các mapping đúng tên cột. `@IdClass` và `@EmbeddedId` là hai lựa chọn; không nên khai báo cả hai cho cùng một entity.

### 10.4. Giá trị khóa tổng hợp phải ổn định

Không đổi `orderId` hoặc `lineNo` sau khi `OrderLine` trở thành managed. Thay đổi khóa trong persistence context có thể khiến identity map, FK và database constraints không còn phù hợp. Nếu nghiệp vụ thực sự cần “chuyển dòng sang đơn khác” hoặc đổi số thứ tự, thường cần mô hình lại identity, tạo/xóa bản ghi theo transaction hoặc cân nhắc surrogate PK riêng.

Composite PK đôi khi giúp phản ánh invariant tự nhiên của quan hệ, nhưng cũng khiến FK ở bảng con phải mang nhiều cột:

```sql
CREATE TABLE line_notes (
    note_id BIGINT PRIMARY KEY,
    order_id BIGINT NOT NULL,
    line_no INTEGER NOT NULL,
    note_text VARCHAR(255) NOT NULL,
    CONSTRAINT fk_line_notes_order_line
        FOREIGN KEY (order_id, line_no)
        REFERENCES order_lines (order_id, line_no)
);
```

Chọn composite key khi hai thành phần thực sự là identity bền vững; không đưa tùy tiện title, status hoặc timestamp có thể sửa vào primary key chỉ vì chúng “giúp hàng có vẻ duy nhất”.

## 11. Khi khóa ngoại dùng định danh thực thể khác

Trong mô hình quan hệ, mỗi quan hệ entity không nhất thiết cần một bảng trung gian; với `@ManyToOne`, cột FK thường nằm ở bảng con.

Ví dụ bảng tác giả và sách:

```sql
CREATE TABLE authors (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(255) NOT NULL
);

CREATE TABLE books (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    author_id BIGINT NOT NULL,
    title VARCHAR(255) NOT NULL,
    CONSTRAINT fk_books_author
        FOREIGN KEY (author_id) REFERENCES authors(id)
);
```

Ánh xạ:

```java
@Entity
@Table(name = "books")
public class Book {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "author_id", nullable = false)
    private Author author;

    private String title;

    protected Book() {}

    // Constructor/getter/domain methods...
}
```

`author_id` tham chiếu `authors.id`. Nó là **foreign key**, không phải ID của `Book`. Identifier của Book vẫn là `books.id`. Hibernate có thể giữ reference/proxy của `Author` và sử dụng identifier của author để xây SQL liên quan. FK constraint trong database bảo vệ việc sách không tham chiếu tác giả không tồn tại, nếu ứng dụng dùng schema có constraint ấy.

Một lỗi phổ biến là nhầm “entity có quan hệ tới Author” với “Book phải dùng authorId làm @Id”. Nhiều book có thể cùng một author, nên `author_id` không đủ để định danh book.

### Shared primary key và @MapsId

Trong quan hệ một-một phụ thuộc vòng đời, PK của entity con có thể đồng thời là FK tới entity cha. Ví dụ `UserProfile.user_id` vừa là PK của profile vừa tham chiếu `users.id`.

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    username VARCHAR(100) NOT NULL UNIQUE
);

CREATE TABLE user_profiles (
    user_id BIGINT PRIMARY KEY,
    bio VARCHAR(1000),
    CONSTRAINT fk_profiles_users
        FOREIGN KEY (user_id) REFERENCES users(id)
);
```

Mapping có thể dùng `@MapsId` để gắn identifier con vào quan hệ:

```java
@Entity
@Table(name = "user_profiles")
public class UserProfile {
    @Id
    private Long id;

    @OneToOne(optional = false, fetch = FetchType.LAZY)
    @MapsId
    @JoinColumn(name = "user_id")
    private User user;

    @Column(length = 1000)
    private String bio;

    protected UserProfile() {}

    public UserProfile(User user) {
        this.user = user;
    }

    public Long getId() { return id; }
}
```

`User` là entity có mapping `@Id Long id` tương ứng bảng `users`; lớp đó được giả định đã khai báo. `@MapsId` nói rằng ID của profile được suy ra từ ID của User gắn với quan hệ. Đây là ví dụ **derived identifier**, khác với hai bảng tự sinh ID độc lập.

Với composite key, `@MapsId("orderId")` có thể gắn một thành phần `@EmbeddedId` tới quan hệ `Order` tương ứng. Khi triển khai, tên thuộc tính phải khớp với class ID và mapping FK; cách dùng này giúp tránh giữ hai trường `orderId` độc lập không đồng bộ với `order`.

## 12. Primary key và identifier trong quá trình update/delete

Hibernate sử dụng giá trị identifier để định vị row. Với optimistic locking, Hibernate còn dùng `version` hoặc cơ chế lock tương ứng:

```sql
-- Minh họa với Book id = 101, version cũ = 3
UPDATE books
SET title = 'Hibernate nâng cao',
    version = 4
WHERE id = 101 AND version = 3;
```

Nếu transaction khác đã cập nhật version từ 3 lên 4, lệnh update trên có thể ảnh hưởng 0 hàng. Hibernate dùng kết quả đó để phát hiện optimistic lock conflict. **Identifier** xác định hàng; **version** kiểm soát xung đột giữa các lần chỉnh sửa.

Tương tự với `DELETE`, Hibernate dùng identifier và có thể đưa điều kiện version khi entity được versioned. Điều này khác với quy tắc `ON DELETE CASCADE` ở database hoặc cascade của ORM; các cơ chế cascade xác định quan hệ với những hàng khác, không thay đổi ý nghĩa định danh của hàng mục tiêu.

### Tại sao không sửa @Id sau khi persist?

Ví dụ sai:

```java
Book book = session.get(Book.class, 101L);
// Không cung cấp setter id để biến 101 thành 202.
```

Persistence context đã lập ánh xạ `(Book, 101) → object`. Việc cố thay ID thành 202 trái với ý nghĩa entity identity bất biến và có thể khiến Hibernate báo lỗi identifier bị thay đổi, làm hỏng tham chiếu FK hoặc gây khó khăn cho trạng thái cache. Nếu domain cần một mã “đổi được”, mã đó nên là business attribute riêng thay vì identifier kỹ thuật.

Với entity có composite PK, thay một thành phần khóa cũng là thay identity; cần thận trọng như thay toàn bộ PK.

## 13. Định danh có ý nghĩa gì khi dùng find(), getReference() và query?

### find/get: nạp dữ liệu theo ID

```java
Book book = entityManager.find(Book.class, 101L);
```

Trả về managed Book nếu có row, thường là `null` khi không tìm thấy; trước khi truy vấn database, provider có thể kiểm tra persistence context và cache theo mapping.

Trong Hibernate native:

```java
Book book = session.get(Book.class, 101L);
```

### getReference: nhận reference theo ID, có thể lazy

```java
Book reference = entityManager.getReference(Book.class, 101L);
```

Đây có thể là proxy hoặc đối tượng enhanced được biểu diễn bằng identifier mà chưa load tất cả field. Truy cập các thuộc tính khác có thể phát sinh SQL; nếu ID không tồn tại, lỗi có thể xuất hiện khi state cần tải, và một số provider có thể kiểm tra sớm. Không dùng `getReference()` như phép kiểm tra chắc chắn rằng bản ghi tồn tại.

Ví dụ khi cần đặt FK của một quan hệ mà không cần đọc nội dung của entity cha, reference theo ID có thể hữu ích; tuy nhiên database FK vẫn quyết định việc tham chiếu tới ID không tồn tại có hợp lệ không.

### Query theo business key là một việc khác

```java
Book book = entityManager.createQuery(
        "select b from Book b where b.isbn = :isbn",
        Book.class)
        .setParameter("isbn", "9780000000101")
        .getSingleResult();
```

Query này tra theo ISBN, rồi nếu trả về entity, Hibernate gắn entity vào persistence context theo **@Id** của hàng tìm được. Predicate `isbn` không khiến ISBN trở thành primary key. Cần ràng buộc uniqueness nếu method giả định kết quả tối đa một hàng.

## 14. SQL PRIMARY KEY và ràng buộc thực tế trong database

Annotation Hibernate định nghĩa mô hình ORM, còn database cưỡng chế toàn vẹn dữ liệu theo DDL và privileges. Sự khác nhau quan trọng:

```java
@Id
private Long id;
```

và:

```sql
CONSTRAINT pk_books PRIMARY KEY (id)
```

Lệnh Java nói Hibernate dùng `id` làm identifier. Constraint SQL bảo đảm hàng trong bảng thực sự không có `id` rỗng/trùng. Trong hệ thống đã có schema, việc thêm annotation **không tự sửa DDL** trừ khi cấu hình schema management được phép tạo/cập nhật.

**Các ràng buộc khác cũng không hoán đổi với PK:**

- `UNIQUE(isbn)` ngăn hai hàng trùng ISBN theo semantics của database, nhưng không tự chọn ISBN thành identifier của Hibernate.
- `FOREIGN KEY(author_id)` ngăn một số tham chiếu không hợp lệ, nhưng không làm `author_id` thành PK của `books`.
- `NOT NULL(title)` bảo vệ một invariant của cột, không liên quan trực tiếp đến identity.
- `@Version` bảo vệ các xung đột cập nhật, không tự tạo primary key tổng hợp `(id, version)`.

Khi Hibernate báo lỗi từ database như duplicate key, foreign-key violation hoặc not-null violation, nguyên nhân thuộc nhóm integrity constraint. Nên xử lý exception trong transaction, rollback khi cần và trả thông điệp nghiệp vụ thích hợp. Không dựa vào việc `HashSet` đã ngăn duplicate để loại bỏ unique constraint trên database.

## 15. Khóa chính trong hệ thống nhiều tenant hoặc nhiều database

Trong multi-tenancy, chỉ nhìn `id=101` có thể không đủ để mô tả bản ghi trên toàn hệ thống:

```text
Tenant A / database A: books.id = 101
Tenant B / database B: books.id = 101
```

Hai hàng này khác nhau về ý nghĩa dù cùng ID. Cơ chế multi-tenancy của Hibernate có thể đưa tenant identifier vào context định danh, cách chọn connection hoặc schema/database phụ thuộc chiến lược triển khai.

Nếu chia tenant trong **cùng một bảng**, có thể thiết kế PK ghép:

```sql
CREATE TABLE tenant_books (
    tenant_id UUID NOT NULL,
    book_id BIGINT NOT NULL,
    title VARCHAR(255) NOT NULL,
    PRIMARY KEY (tenant_id, book_id)
);
```

Nhưng cũng có hệ thống chọn ID toàn cục duy nhất và unique constraint riêng cho tenant. Cách chọn ảnh hưởng đến FK, index, phân quyền, API và cơ chế query. Không giả định Hibernate tự bảo vệ mọi truy vấn khỏi lộ dữ liệu khác tenant chỉ vì entity có field `tenantId`; chiến lược multi-tenancy và kiểm soát truy cập phải được cấu hình đúng.

Một identifier UUID toàn cục cũng không tự thay thế kiểm tra `tenant_id` khi nhận một request có ID từ client.

## 16. PK được sinh không phải số thứ tự nghiệp vụ

Với `IDENTITY` hoặc `SEQUENCE`, giá trị tăng dần thường có **khoảng trống**:

```text
Tx A lấy sequence 1001 → INSERT → COMMIT
Tx B lấy sequence 1002 → INSERT → ROLLBACK
Tx C lấy sequence 1003 → INSERT → COMMIT

Các row tồn tại: 1001, 1003
Không có row 1002
```

Các giá trị sequence đã cấp có thể không được hoàn lại sau rollback. Việc cache hoặc cấp phát trước một vùng ID cũng tạo bước nhảy. Vì vậy:

- Đừng dùng `id` như số thứ tự hóa đơn bắt buộc liên tiếp không gap.
- Đừng giả định ID lớn hơn luôn có `createdAt` muộn hơn trong mọi mô hình phân tán/transaction.
- Đừng dùng `MAX(id) + 1` để cấp khóa trong ứng dụng có nhiều transaction; có race condition.
- Đừng xuất dữ liệu nhạy cảm chỉ vì client đoán ra ID tuần tự; API vẫn cần kiểm tra authorization.

Nếu domain cần mã chứng từ theo quy định riêng, hãy thiết kế **document number** là trường có quy trình cấp số riêng, độc lập với PK kỹ thuật. Những yêu cầu “không trùng”, “theo năm” hoặc “không được có khoảng trống” cần phân tích transaction, lock và vận hành cụ thể; không thể đạt được chỉ bằng `GenerationType.IDENTITY`.

## 17. Hiệu năng và lựa chọn generator

Identifier đi vào PK index, foreign key và SQL join. Một vài tác động đáng chú ý:

| Quyết định | Tác động có thể có | Cách cân nhắc |
|---|---|---|
| `BIGINT` PK | Kích thước index nhỏ, dễ join | Hợp với hệ thống một DB hoặc generator tập trung |
| UUID PK | Dễ tạo ID ở nhiều node | Xem xét kiểu cột, thứ tự khóa, UUID version và index database |
| `IDENTITY` | DB cấp ID lúc insert | Có thể hạn chế JDBC insert batching |
| `SEQUENCE` với pool allocation | Ít round trip để cấp ID | Cần đồng bộ sequence increment, generator optimizer |
| Composite PK nhiều cột | FK/join dài hơn, index lớn hơn | Chỉ chọn khi các thành phần đúng là identity |
| Business key làm PK | Dễ đọc ở SQL, ít cột kỹ thuật | Thay đổi domain key ảnh hưởng FK, migration và equality |

Với hàng triệu bản ghi, lựa chọn PK có thể ảnh hưởng kích thước các index phụ và chi phí join. Không chỉ đo SQL insert; hãy xét cả số FK, mức độ update, cache, cách phân trang và yêu cầu phân phối ID.

Nếu dùng JDBC batching để chèn nhiều entity, việc chọn `SEQUENCE` với chiến lược phân bổ hợp lý có thể thuận lợi hơn `IDENTITY`. Tuy nhiên batching phụ thuộc nhiều điều kiện khác như `hibernate.jdbc.batch_size`, trật tự câu lệnh, driver và kiểu association. Chuyển generator trên database đang có dữ liệu phải thực hiện qua migration cẩn trọng, đặc biệt khi số sequence hiện tại cần vượt mọi ID đã lưu.

## 18. Những lỗi định danh thường gặp

| Hiện tượng | Nguyên nhân có thể | Hướng xử lý |
|---|---|---|
| Hai object cùng ID nhưng `==` false | Hai session tạo hai Java object | So sánh ID/equality phù hợp, phân biệt reference identity |
| `HashSet.contains(entity)` false sau persist | `hashCode()` đổi vì generated ID từ null thành giá trị | Dùng hash ổn định hoặc business key thật sự bất biến |
| Hai entity mới có `id=null` bị xem là bằng nhau | `equals()` chỉ so `Objects.equals(id, other.id)` | Với generated ID, hai transient entity khác reference không được mặc nhiên bằng nhau |
| Duplicate key violation ở insert | ID cấp trùng hoặc unique business key xung đột | Dựa vào constraint DB; sửa generator/migration, xử lý race |
| Hibernate không tạo ID | `@GeneratedValue` thiếu/sai hoặc schema chưa đúng generator | Kiểm tra strategy, type, dialect và DDL |
| Identifier changed exception | Code cố thay `@Id` của managed entity | Không sửa PK; tách business attribute có thể thay đổi |
| Query theo ISBN trả nhiều hàng | Thiếu unique constraint hoặc dữ liệu cũ bị trùng | Ràng buộc DB, chuẩn hóa dữ liệu và domain key |
| `getReference()` tạo object nhưng sau đó lỗi | Reference chưa xác minh bản ghi tồn tại | Dùng `find()/get()` khi cần kiểm tra tồn tại |
| Chuyển DB, ID bắt đầu lại từ 1 | Sequence/identity chưa đồng bộ với dữ liệu migrate | Cập nhật generator sequence start phù hợp trong migration |
| `merge()` gây cập nhật không mong muốn | Dùng detached object như payload và sao chép toàn bộ state | Tải managed entity rồi áp dụng những field được phép |
| FK trỏ sai hàng/tenant | ID không đủ scope hoặc thiếu tenant constraint | Thiết kế PK/FK và tenant isolation theo scope nhất quán |
| Composite ID truy vấn không khớp | Class ID thiếu equality, tên/kiểu cột sai | Mapping `@EmbeddedId`/`@IdClass` khớp PK thực tế |
| Dùng ID làm số chứng từ nhưng bị gap | Sequence/identity không gapless | Tách số chứng từ khỏi PK |
| Dùng record DTO như entity | Record là dữ liệu giá trị, không có managed lifecycle như entity thông thường | Mapping entity bằng class phù hợp; record cho projection |

## 19. Một ví dụ nghiệp vụ xuyên suốt: tạo và tra cứu sách

Giả sử `Book` có `id` sinh tự động, `isbn` duy nhất và `version` dùng optimistic locking. Tầng nghiệp vụ tạo sách:

```java
import org.hibernate.Session;
import org.hibernate.SessionFactory;
import org.hibernate.Transaction;

public final class BookService {
    private final SessionFactory factory;

    public BookService(SessionFactory factory) {
        this.factory = factory;
    }

    public Long createBook(String isbn, String title) {
        try (Session session = factory.openSession()) {
            Transaction tx = session.beginTransaction();
            try {
                Book book = new Book(isbn, title); // transient
                session.persist(book);            // managed

                tx.commit();                     // commit thành công
                return book.getId();
            } catch (RuntimeException | Error failure) {
                if (tx.isActive()) {
                    try {
                        tx.rollback();
                    } catch (RuntimeException rollbackError) {
                        failure.addSuppressed(rollbackError);
                    }
                }
                throw failure;
            }
        }
    }

    public String readTitleById(Long id) {
        try (Session session = factory.openSession()) {
            Transaction tx = session.beginTransaction();
            try {
                Book book = session.get(Book.class, id);
                String title = book == null ? null : book.getTitle();
                tx.commit();
                return title;
            } catch (RuntimeException | Error failure) {
                if (tx.isActive()) {
                    try {
                        tx.rollback();
                    } catch (RuntimeException rollbackError) {
                        failure.addSuppressed(rollbackError);
                    }
                }
                throw failure;
            }
        }
    }
}
```

Quá trình của `createBook()`:

```text
new Book(isbn, title)
    → Java object mới, id=null, trạng thái TRANSIENT
    → session.persist(book)
    → Hibernate quản lý Book trong persistence context
    → Generator cấp id (thời điểm tùy IDENTITY/SEQUENCE/...)
    → SQL INSERT + database kiểm tra PK, UNIQUE(isbn), NOT NULL
    → tx.commit()
    → row tồn tại sau khi commit thành công
    → session.close(), Book thành detached
    → trả về Long id để các nghiệp vụ khác truy xuất
```

Lưu ý thiết kế API: trả về ID sau khi commit thành công và xử lý trường hợp unique constraint/transaction commit lỗi. Nếu dùng `@Version`, Hibernate còn chịu trách nhiệm kiểm soát version trong các lần cập nhật sau đó. Không sử dụng `id` do client cung cấp để bỏ qua kiểm tra quyền truy cập bản ghi.

Trong tầng HTTP có thể trả về DTO thay vì entity:

```java
public record BookCreatedResponse(Long id, String isbn) {}
```

`BookCreatedResponse` có field tên `id` nhưng **không là Hibernate entity**. Nó chỉ là value object truyền kết quả. Hibernate quản lý `Book` nhờ mapping `@Entity + @Id`, không dựa vào sự tồn tại của thuộc tính trùng tên trong bất kỳ class Java nào.

## 20. Cách suy luận đúng khi thiết kế một khóa thực thể

Hãy trả lời theo thứ tự:

**Bước 1 — Định danh nghiệp vụ là gì?** Một cuốn sách, một bản sao vật lý, một đơn hàng, hay một dòng đơn hàng? Nếu ISBN xác định ấn bản nhưng nghiệp vụ quản lý nhiều bản sao, dùng ISBN làm PK của bản sao sẽ sai.

**Bước 2 — Có khóa tự nhiên thực sự duy nhất và bất biến không?** Nếu không, dùng surrogate key và bổ sung unique constraint cho những thuộc tính nghiệp vụ cần duy nhất. Nếu natural key thay đổi được, tránh biến nó thành PK hoặc cơ sở duy nhất của equality.

**Bước 3 — Database lưu PK kiểu nào?** `BIGINT`, `UUID`, chuỗi mã hay composite PK? Quyết định ảnh hưởng index, FK, migration và số lượng dữ liệu.

**Bước 4 — Ai cấp ID và khi nào?** `IDENTITY`, `SEQUENCE`, UUID generator hay external ID? Kiểm tra thời điểm phát sinh ID và nhu cầu JDBC batching.

**Bước 5 — Hibernate ánh xạ đúng khóa chưa?** `@Id` hoặc `@EmbeddedId`/`@IdClass`, getter/field access, loại dữ liệu và schema phải nhất quán.

**Bước 6 — Java equality cần mang nghĩa nào?** Chỉ làm việc trong một session có thể giữ reference equality. Nếu entity được so sánh qua session hoặc đặt trong hash collections, cần hợp đồng `equals()/hashCode()` ổn định, tương thích ID strategy và proxy.

**Bước 7 — Khóa có phải được bảo vệ trên mọi đường ghi?** Database phải có PK/FK/unique constraints và kiểm soát quyền; `@Id`, `@NaturalId` hoặc Java `equals()` không tự giải quyết race condition hay truy cập trái phép.

## 21. Sơ đồ kết nối toàn bộ kiến thức

```text
             MÔ HÌNH NGHIỆP VỤ
         "Một Book là thực thể nào?"
                      │
          ┌───────────┴───────────┐
          │                       │
       Key kỹ thuật         Business / natural key
       @Id Long id          @NaturalId String isbn
          │                       │
          ▼                       ▼
    DATABASE SCHEMA          UNIQUE(isbn)
    PRIMARY KEY(id)          (không thay PK)
          │
          ├──── FOREIGN KEY từ bảng khác
          │
          ▼
    HIBERNATE IDENTITY MAP
    (entity type, id, scope/tenant)
          │
          ├── một managed instance / key trong Session
          ├── dirty checking / SQL UPDATE/DELETE theo key
          └── @Version nếu cần kiểm soát xung đột
          │
          ▼
    JAVA OBJECTS
    ==             : cùng reference?
    equals()       : cùng thực thể theo quy tắc Java?
    hashCode()     : ổn định khi dùng Set/Map?
          │
          ▼
    DTO / PROJECTION
    có thể mang id, nhưng không thành managed entity
```

Điểm cốt lõi là **khóa chính ở database** cung cấp tính duy nhất cho hàng dữ liệu, **identifier mapping của Hibernate** nối hàng đó với lifecycle và identity map của ORM, còn **định danh/equality trong Java** xác định cách các object được so sánh trong bộ nhớ. Ba tầng này liên quan chặt chẽ nhưng mỗi tầng giải quyết một loại vấn đề riêng. Thiết kế đúng ranh giới giúp tránh lỗi duplicate key, sửa nhầm entity, hash collection sai sau `persist()` và các giả định không chính xác khi chuyển dữ liệu giữa nhiều session.
