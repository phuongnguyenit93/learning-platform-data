# An toàn khi ghép các thành phần truy vấn động

Ứng dụng thường cần tạo truy vấn theo lựa chọn của người dùng: lọc theo trạng thái, tìm kiếm theo từ khóa, sắp xếp theo cột, phân trang hoặc bật/tắt một số điều kiện. Trong Hibernate, những truy vấn này thường được viết bằng HQL/JPQL. Nếu ghép chuỗi tùy tiện, dữ liệu đầu vào có thể bị hiểu thành cú pháp truy vấn, gây **HQL/SQL injection**, làm sai logic lọc hoặc tạo truy vấn khó kiểm soát.

Nguyên tắc cốt lõi là: **dùng parameter binding cho giá trị dữ liệu; dùng allowlist hoặc Criteria API cho cấu trúc truy vấn**. Parameter binding không thể thay thế tên entity, tên thuộc tính, toán tử hay hướng sắp xếp. Những thành phần cấu trúc phải được chọn từ các lựa chọn cố định mà ứng dụng kiểm soát.

Bài này tập trung vào Hibernate ORM 6.x và Jakarta Persistence. Ví dụ dùng HQL/JPQL qua `EntityManager`; các nguyên tắc tương tự áp dụng cho Hibernate `Session` và native SQL. Ranh giới giữa **value** và **query syntax** luôn giữ nguyên.

## 1. Truy vấn động là gì?

Một truy vấn tĩnh có cấu trúc cố định:

~~~java
List<Book> books = entityManager.createQuery(
        "select b from Book b where b.status = :status",
        Book.class
    )
    .setParameter("status", BookStatus.PUBLISHED)
    .getResultList();
~~~

Truy vấn động thường cần thay đổi một phần điều kiện dựa trên request:

- Người dùng có thể lọc theo trạng thái hoặc không.
- Có thể tìm theo title, author hoặc category.
- Có thể chọn sắp xếp theo title, price hoặc ngày tạo.
- Có thể yêu cầu tăng dần hoặc giảm dần.
- Có thể truyền một danh sách ID.
- Có thể có nhiều điều kiện kết hợp AND/OR.

Việc thay đổi cấu trúc query là nhu cầu bình thường. Rủi ro xuất hiện khi ứng dụng đưa trực tiếp chuỗi không tin cậy vào HQL/SQL:

~~~java
// NGUY HIỂM: không nối trực tiếp input vào cú pháp query.
String hql =
        "from Book b where b.title = '" + request.title() + "'";
~~~

Nếu đầu vào chứa dấu nháy và biểu thức HQL hợp lệ, người dùng có thể thay đổi ý nghĩa của query. Lỗi không chỉ nằm ở ký tự đặc biệt; bất kỳ dữ liệu nào được diễn giải như cú pháp đều có thể mở đường cho injection.

## 2. Parameter binding bảo vệ giá trị dữ liệu

### 2.1. Named parameters

Dùng placeholder có tên trong HQL:

~~~java
String hql =
        "select b from Book b where b.title = :title";

List<Book> books = entityManager.createQuery(hql, Book.class)
        .setParameter("title", request.title())
        .getResultList();
~~~

Hibernate gửi query structure riêng với giá trị parameter được bind qua JDBC. Giá trị chứa dấu nháy, dấu chấm phẩy hoặc chuỗi giống cú pháp HQL vẫn được coi là **dữ liệu của parameter**, không được ghép vào query text.

Ví dụ người dùng nhập chuỗi:

~~~text
' or 1=1 or 'x'='x
~~~

Với parameter binding, chuỗi này được so sánh như một giá trị title. Nó không làm thay đổi phần WHERE thành biểu thức luôn đúng.

### 2.2. Nhiều parameters

~~~java
String hql =
        "select b from Book b " +
        "where b.status = :status " +
        "and b.price >= :minimumPrice " +
        "and b.price <= :maximumPrice";

List<Book> books = entityManager.createQuery(hql, Book.class)
        .setParameter("status", BookStatus.PUBLISHED)
        .setParameter("minimumPrice", minimumPrice)
        .setParameter("maximumPrice", maximumPrice)
        .getResultList();
~~~

Mỗi giá trị cần bind đúng kiểu Java tương ứng với mapping. Nếu price là BigDecimal, truyền BigDecimal; nếu status là enum, truyền enum đã map. Tránh chuyển mọi thứ thành String rồi trông chờ DB tự chuyển kiểu, vì điều đó có thể gây lỗi, làm mất khả năng dùng index hoặc tạo khác biệt theo dialect.

### 2.3. Positional parameters

JPA hỗ trợ positional parameters:

~~~java
List<Book> books = entityManager.createQuery(
        "select b from Book b where b.status = ?1 and b.price < ?2",
        Book.class
    )
    .setParameter(1, BookStatus.PUBLISHED)
    .setParameter(2, maximumPrice)
    .getResultList();
~~~

Named parameters thường dễ đọc và ít lỗi hơn khi query có nhiều điều kiện. Positional parameters cần giữ đúng thứ tự và vị trí; đừng trộn quy ước vị trí không nhất quán.

### 2.4. Parameter không phải chuỗi thay thế văn bản

~~~java
// Không phải parameter binding:
String hql = "select b from Book b where b.title = :title";
hql = hql.replace(":title", "'" + request.title() + "'");
~~~

Việc replace quay lại đúng rủi ro nối chuỗi ban đầu. Hãy để provider bind giá trị qua setParameter() hoặc API tương ứng.

## 3. Parameter không thể thay thế cấu trúc HQL

Một lỗi hiểu nhầm phổ biến là nghĩ rằng có thể bind bất kỳ phần nào của query.

### 3.1. Không thể bind tên thuộc tính

~~~java
// Không hoạt động như dynamic property selection:
String hql = "select b from Book b order by :field";
entityManager.createQuery(hql, Book.class)
        .setParameter("field", request.sortField())
        .getResultList();
~~~

:field là một **giá trị parameter**. Hibernate không diễn giải giá trị đó thành path b.title hay b.price; nó chỉ là một biểu thức giá trị cố định trong query. Kết quả không thực hiện sắp xếp theo cột người dùng chọn.

Không thể dùng parameter để thay thế:

- Tên entity hoặc alias.
- Tên thuộc tính/path.
- Tên bảng/cột trong native SQL.
- Từ khóa ASC/DESC.
- Toán tử như =, LIKE, IN, IS NULL.
- Một đoạn WHERE, JOIN, GROUP BY hoặc ORDER BY.
- Tên function hoặc kiểu dữ liệu trong cú pháp CAST.

Những thành phần này thuộc **cấu trúc query**, không phải giá trị.

### 3.2. Không thể bind hướng sắp xếp

~~~java
// :direction không trở thành từ khóa ASC hoặc DESC.
String hql = "select b from Book b order by b.title :direction";
~~~

Hãy ánh xạ request thành một lựa chọn cú pháp cố định:

~~~java
String direction = request.descending() ? "desc" : "asc";

String hql = "select b from Book b order by b.title " + direction;
~~~

Đoạn trên an toàn vì direction chỉ có thể là một trong hai literal do ứng dụng tạo. Tuy nhiên, nếu có nhiều field cần sắp xếp, nên dùng enum/allowlist thay vì nhận chuỗi tùy ý.

## 4. Allowlist cho tên field, toán tử và hướng sắp xếp

### 4.1. Chuyển request sang enum

~~~java
public enum BookSortField {
    TITLE,
    PRICE,
    CREATED_AT
}

public enum SortDirection {
    ASC,
    DESC
}
~~~

Parse input:

~~~java
BookSortField parseSortField(String raw) {
    if (raw == null) {
        return BookSortField.TITLE;
    }

    return switch (raw.toLowerCase(Locale.ROOT)) {
        case "title" -> BookSortField.TITLE;
        case "price" -> BookSortField.PRICE;
        case "createdat" -> BookSortField.CREATED_AT;
        default -> throw new IllegalArgumentException(
                "Unsupported sort field"
        );
    };
}

SortDirection parseDirection(String raw) {
    if (raw == null) {
        return SortDirection.ASC;
    }

    return switch (raw.toLowerCase(Locale.ROOT)) {
        case "asc" -> SortDirection.ASC;
        case "desc" -> SortDirection.DESC;
        default -> throw new IllegalArgumentException(
                "Unsupported sort direction"
        );
    };
}
~~~

Không dùng Enum.valueOf() trực tiếp với request nếu muốn chấp nhận chữ thường hoặc trả lỗi validation rõ ràng. Nếu dùng, vẫn phải bắt lỗi và từ chối giá trị không hợp lệ; tuyệt đối không đưa raw string vào query.

### 4.2. Allowlist với HQL fragment cố định

~~~java
String sortPath = switch (sortField) {
    case TITLE -> "b.title";
    case PRICE -> "b.price";
    case CREATED_AT -> "b.createdAt";
};

String sortDirection =
        direction == SortDirection.DESC ? "desc" : "asc";

String hql =
        "select b from Book b " +
        "where b.status = :status " +
        "order by " + sortPath + " " + sortDirection;

List<Book> books = entityManager.createQuery(hql, Book.class)
        .setParameter("status", BookStatus.PUBLISHED)
        .getResultList();
~~~

Đây là cách ghép query text có kiểm soát:

- sortPath chỉ nhận một trong ba HQL path cố định.
- sortDirection chỉ nhận asc hoặc desc do code tạo.
- status vẫn được bind vì đó là giá trị dữ liệu.
- Không có phần nào lấy nguyên chuỗi tùy ý từ request để ghép vào query.

Allowlist nên phản ánh các lựa chọn mà nghiệp vụ thực sự cho phép. Không nhất thiết phơi bày mọi field trong entity; có field nhạy cảm, field không có index hoặc field không phù hợp để sắp xếp.

### 4.3. Allowlist cho toán tử

Nếu API cho phép chọn kiểu so sánh, không nối operator thô:

~~~java
public enum PriceComparison {
    LESS_THAN,
    LESS_OR_EQUAL,
    EQUAL,
    GREATER_OR_EQUAL,
    GREATER_THAN
}

String operator = switch (comparison) {
    case LESS_THAN -> "<";
    case LESS_OR_EQUAL -> "<=";
    case EQUAL -> "=";
    case GREATER_OR_EQUAL -> ">=";
    case GREATER_THAN -> ">";
};

String hql =
        "select b from Book b where b.price " +
        operator + " :price";

List<Book> books = entityManager.createQuery(hql, Book.class)
        .setParameter("price", requestedPrice)
        .getResultList();
~~~

Operator chỉ được chọn từ enum nội bộ. Nếu điều kiện chỉ có vài nhánh, có thể viết các query riêng hoặc dùng Criteria API để tránh tự quản lý fragment.

## 5. Ghép WHERE động an toàn

Một truy vấn tìm kiếm thường có các filter tùy chọn. Có thể ghép những **mảnh HQL cố định** và bind từng giá trị:

~~~java
StringBuilder hql = new StringBuilder(
        "select b from Book b where 1 = 1"
);

Map<String, Object> parameters = new HashMap<>();

if (filter.status() != null) {
    hql.append(" and b.status = :status");
    parameters.put("status", filter.status());
}

if (filter.minimumPrice() != null) {
    hql.append(" and b.price >= :minimumPrice");
    parameters.put("minimumPrice", filter.minimumPrice());
}

if (filter.maximumPrice() != null) {
    hql.append(" and b.price <= :maximumPrice");
    parameters.put("maximumPrice", filter.maximumPrice());
}

TypedQuery<Book> query =
        entityManager.createQuery(hql.toString(), Book.class);

parameters.forEach(query::setParameter);

List<Book> result = query.getResultList();
~~~

Các fragment and b.status = :status, and b.price >= :minimumPrice là hằng do developer viết. Request chỉ cung cấp **giá trị parameter** và quyết định có bật filter hay không. Đây là cách ghép HQL text an toàn nếu mọi fragment đều cố định và không chứa raw input.

### 5.1. Tránh placeholder không cần thiết

Có thể viết một query cố định với điều kiện optional:

~~~java
String hql =
        "select b from Book b " +
        "where (:status is null or b.status = :status) " +
        "and (:minPrice is null or b.price >= :minPrice)";
~~~

Cách này giảm số biến thể HQL nhưng có thể ảnh hưởng query plan/index usage tùy DBMS. Nếu filter có nhiều tổ hợp, ghép các điều kiện cố định chỉ khi có filter thường giúp SQL rõ hơn. Hãy đo query plan thay vì mặc định một cách luôn nhanh hơn.

### 5.2. Không dùng chuỗi rỗng để thay cú pháp

Đừng nhận một đoạn whereClause từ client rồi nối vào query. Client nên gửi các trường có cấu trúc như status, minimumPrice, sortField, không gửi HQL/SQL. Server validate và chuyển request thành query structure được kiểm soát.

## 6. Criteria API: lựa chọn tốt cho query có nhiều nhánh

Khi query có nhiều filter tùy chọn, Criteria API cho phép xây dựng expression bằng object API thay vì nối chuỗi.

~~~java
CriteriaBuilder cb = entityManager.getCriteriaBuilder();
CriteriaQuery<Book> cq = cb.createQuery(Book.class);
Root<Book> book = cq.from(Book.class);

List<Predicate> predicates = new ArrayList<>();

if (filter.status() != null) {
    predicates.add(
        cb.equal(book.get("status"), filter.status())
    );
}

if (filter.minimumPrice() != null) {
    predicates.add(
        cb.greaterThanOrEqualTo(
            book.get("price"),
            filter.minimumPrice()
        )
    );
}

if (filter.maximumPrice() != null) {
    predicates.add(
        cb.lessThanOrEqualTo(
            book.get("price"),
            filter.maximumPrice()
        )
    );
}

cq.select(book);
cq.where(predicates.toArray(Predicate[]::new));

List<Book> result = entityManager.createQuery(cq).getResultList();
~~~

Criteria API tạo query từ metadata và expression, giảm nguy cơ lỗi cú pháp do nối fragment. Nhưng nó **không tự biến input thành an toàn** nếu code vẫn dùng tên path tùy tiện từ request.

### 6.1. Dynamic sorting bằng Criteria API

~~~java
Path<?> sortPath = switch (sortField) {
    case TITLE -> book.get("title");
    case PRICE -> book.get("price");
    case CREATED_AT -> book.get("createdAt");
};

Order order = direction == SortDirection.DESC
        ? cb.desc(sortPath)
        : cb.asc(sortPath);

cq.orderBy(order);
~~~

Field path vẫn đến từ allowlist. Không viết book.get(request.sortField()) nếu request có thể chứa bất kỳ chuỗi nào. JPA metamodel có thể cung cấp type-safe paths thay cho tên chuỗi, nhất là khi dự án dùng generated static metamodel.

### 6.2. Criteria không thay thế authorization

Một Criteria query hoàn toàn hợp lệ về cú pháp vẫn có thể trả dữ liệu người dùng không được phép xem. Thêm predicate tenant/owner/permission từ context server-side; không lấy tenant ID hoặc user ID nhạy cảm từ client rồi tin tưởng vô điều kiện.

## 7. Tìm kiếm LIKE và ký tự wildcard

Parameter binding ngăn chuỗi tìm kiếm trở thành HQL syntax, nhưng % và _ vẫn có ý nghĩa **wildcard của LIKE**. Đây là khác biệt giữa injection và semantics tìm kiếm.

~~~java
List<Book> books = entityManager.createQuery(
        "select b from Book b where b.title like :pattern",
        Book.class
    )
    .setParameter("pattern", "%" + userInput + "%")
    .getResultList();
~~~

Nếu người dùng nhập %, query có thể khớp rất nhiều dòng. Đây không phải HQL injection vì parameter vẫn là dữ liệu, nhưng có thể không đúng mong muốn “tìm chuỗi literal”.

### 7.1. Escape wildcard để tìm literal substring

Chọn một escape character, ví dụ !, rồi escape chính nó trước khi escape % và _:

~~~java
String escapeLike(String value) {
    return value
            .replace("!", "!!")
            .replace("%", "!%")
            .replace("_", "!_");
}

String pattern = "%" + escapeLike(userInput) + "%";

List<Book> books = entityManager.createQuery(
        "select b from Book b " +
        "where b.title like :pattern escape '!'",
        Book.class
    )
    .setParameter("pattern", pattern)
    .getResultList();
~~~

Thứ tự escape quan trọng: escape ký tự ! trước để những ký tự ! vừa được thêm không bị escape lần thứ hai. Cú pháp ESCAPE được hỗ trợ trong JPQL/HQL; vẫn cần kiểm tra dialect và query cụ thể trong hệ thống.

Nếu nghiệp vụ muốn người dùng nhập wildcard có chủ đích, không escape chúng; hãy mô tả rõ semantics tìm kiếm và giới hạn độ rộng/chi phí truy vấn.

## 8. IN và danh sách tham số

Không nối ID vào chuỗi:

~~~java
// NGUY HIỂM:
String hql = "from Book b where b.id in (" +
        ids.stream().map(String::valueOf)
           .collect(Collectors.joining(",")) + ")";
~~~

Bind collection parameter:

~~~java
List<Book> books = entityManager.createQuery(
        "select b from Book b where b.id in :ids",
        Book.class
    )
    .setParameter("ids", ids)
    .getResultList();
~~~

Hibernate hỗ trợ bind collection cho biểu thức IN trong HQL/JPQL. Không tự tạo danh sách placeholder bằng cách nối giá trị. Nếu API nhận hàng nghìn ID, cần chú ý:

- DBMS có giới hạn số bind parameters hoặc độ dài statement.
- Query plan và kích thước IN list có thể ảnh hưởng hiệu năng.
- Chia danh sách thành batch hợp lý hoặc dùng bảng tạm/array/table-valued parameter theo DBMS khi phù hợp.
- Đừng gửi danh sách vô hạn từ client; validate số phần tử tối đa.

### 8.1. Danh sách rỗng

Không nên dựa vào cách mọi provider/DBMS xử lý IN với danh sách rỗng. Hãy xử lý rõ trong ứng dụng:

~~~java
if (ids == null || ids.isEmpty()) {
    return List.of();
}

return entityManager.createQuery(
        "select b from Book b where b.id in :ids",
        Book.class
    )
    .setParameter("ids", ids)
    .getResultList();
~~~

Nếu semantics nghiệp vụ của danh sách rỗng là “không áp filter” thay vì “không trả kết quả”, xử lý theo hợp đồng API trước khi tạo query. Hai trường hợp đó khác nhau và không nên để query tự quyết định.

## 9. Dynamic JOIN, path và entity name

Nếu người dùng có thể chọn lọc theo tác giả hoặc nhà xuất bản, hãy chọn một trong các query path cố định:

~~~java
String hql = switch (filter.relatedField()) {
    case AUTHOR -> "select b from Book b join b.author a " +
                   "where a.name = :value";
    case PUBLISHER -> "select b from Book b join b.publisher p " +
                      "where p.name = :value";
};

List<Book> books = entityManager.createQuery(hql, Book.class)
        .setParameter("value", filter.value())
        .getResultList();
~~~

relatedField phải là enum/giá trị đã validate. filter.value() là dữ liệu nên được bind.

Không nhận joinPath, entity name hoặc alias trực tiếp từ request. Nếu cần nhiều cấu trúc query, định nghĩa enum/command rồi ánh xạ sang Criteria joins hoặc các HQL template cố định. Một allowlist có thể chứa cả template query hoàn chỉnh nếu số trường hợp ít và rõ ràng.

## 10. Native SQL cũng cần parameter binding

Native query không an toàn hơn HQL chỉ vì nó là SQL. Giá trị phải được bind:

~~~java
List<?> rows = entityManager.createNativeQuery(
        "select id, title from books where status = :status"
    )
    .setParameter("status", "PUBLISHED")
    .getResultList();
~~~

Hoặc Hibernate Session native query API với named/positional parameter theo API version. Không nối input vào SQL.

### 10.1. Identifier trong native SQL không bind được

Không thể dùng:

~~~sql
select * from :tableName
~~~

để bind tên bảng. Database parameter đại diện giá trị expression, không đại diện identifier. Nếu cần chọn bảng/column động, dùng allowlist tên identifier cố định, hoặc thiết kế lại query/schema để không cần dynamic identifier.

Ví dụ an toàn:

~~~java
String table = switch (reportType) {
    case SALES -> "sales_summary";
    case INVENTORY -> "inventory_summary";
};

String sql = "select * from " + table + " where tenant_id = :tenantId";

List<?> rows = entityManager.createNativeQuery(sql)
        .setParameter("tenantId", tenantId)
        .getResultList();
~~~

An toàn chỉ khi reportType được parse thành enum và table chỉ có thể là một trong hai literal nội bộ. Không dùng tên bảng do client tự gửi.

### 10.2. Native SQL dynamic ORDER BY

Giống HQL, ORDER BY column/direction không thể bind như giá trị. Ánh xạ sang identifier/keyword cố định. Nếu query native có nhiều DBMS dialect, cần quản lý identifier quoting và cú pháp riêng một cách rõ ràng; đừng viết một hàm quote tùy tiện rồi coi nó là giải pháp thay allowlist.

## 11. Parameter binding không phải kiểm tra quyền truy cập

Một query được bind an toàn vẫn có thể có lỗi authorization:

~~~java
// Query có parameter binding, nhưng thiếu tenant predicate.
List<Book> books = entityManager.createQuery(
        "select b from Book b where b.status = :status",
        Book.class
    )
    .setParameter("status", status)
    .getResultList();
~~~

Nếu ứng dụng multi-tenant, query có thể trả sách của mọi tenant. Binding bảo vệ **cấu trúc query** khỏi injection; nó không tự thêm giới hạn quyền.

Lấy tenant/user scope từ security context đáng tin cậy ở server:

~~~java
List<Book> books = entityManager.createQuery(
        "select b from Book b " +
        "where b.tenantId = :tenantId " +
        "and b.status = :status",
        Book.class
    )
    .setParameter("tenantId", currentTenant.id())
    .setParameter("status", status)
    .getResultList();
~~~

currentTenant.id() phải đến từ context đã xác thực và được kiểm tra quyền, không chỉ lấy từ query parameter hoặc request body. Với object-level authorization, còn phải kiểm tra người dùng có quyền thao tác trên từng resource cụ thể.

## 12. Tránh để client gửi HQL/SQL fragment

Không thiết kế API như:

~~~json
{
  "where": "b.status = 'PUBLISHED' or 1=1",
  "orderBy": "b.price desc"
}
~~~

Đây là cách trao quyền điều khiển cú pháp query cho client. Thay vào đó, API nhận dữ liệu có schema:

~~~json
{
  "status": "PUBLISHED",
  "minimumPrice": "10.00",
  "sortField": "price",
  "direction": "desc"
}
~~~

Server parse, validate và ánh xạ:

- status thành enum.
- minimumPrice thành BigDecimal với range phù hợp.
- sortField thành enum allowlist.
- direction thành ASC/DESC.
- Tenant/owner scope lấy từ security context.
- Các filter tùy chọn được chuyển thành parameterized predicates.

Không nên nhận một DSL query tùy biến do người dùng tự viết trừ khi hệ thống thực sự cần, có parser/grammar riêng, giới hạn function/path/operator và kiểm soát quyền ở từng biểu thức. Không đưa raw DSL trực tiếp vào HQL.

## 13. Query structure, plan cache và khả năng bảo trì

Parameter binding không chỉ giúp an toàn. Nó còn giữ query text ổn định khi giá trị thay đổi:

~~~java
String hql = "select b from Book b where b.status = :status";
~~~

Nhiều request với các status khác nhau dùng cùng một cấu trúc HQL. Hibernate có thể tái sử dụng query plan trong query plan cache theo cấu hình/version; JDBC/DBMS cũng có cơ hội dùng prepared statement/plan tương ứng. Chi tiết cache phụ thuộc provider, driver, DBMS và parameter behavior, nên không bảo đảm mọi giá trị luôn dùng cùng execution plan.

Nếu nối literal vào query text:

~~~java
String hql = "select b from Book b where b.status = '" + status + "'";
~~~

mỗi giá trị có thể tạo query string khác nhau, làm giảm khả năng reuse và tăng số biến thể query. Đặc biệt, không dùng string concatenation để thay parameter binding cho mục tiêu tối ưu hiệu năng.

Dynamic filters có nhiều tổ hợp vẫn có thể tạo nhiều query shapes. Hãy cân nhắc Criteria API, giới hạn số filter, và đo plan cache hit/miss nếu workload cần tối ưu.

## 14. Phân trang và tham số số học

Giá trị phân trang là dữ liệu số, nên validate range rồi truyền qua API phân trang thay vì ghép vào HQL:

~~~java
int page = Math.max(request.page(), 0);
int size = Math.min(Math.max(request.size(), 1), 100);

List<Book> books = entityManager.createQuery(
        "select b from Book b order by b.title, b.id",
        Book.class
    )
    .setFirstResult(page * size)
    .setMaxResults(size)
    .getResultList();
~~~

setFirstResult và setMaxResults nhận số nguyên; không nối chuỗi LIMIT/OFFSET từ request vào HQL. Kiểm tra overflow khi tính offset nếu page/size có thể rất lớn. Thêm tie-breaker ổn định như ID vào ORDER BY để kết quả giữa các trang dễ dự đoán hơn.

Với một số DBMS/native query, pagination syntax khác nhau; dùng API dialect-aware hoặc bind giá trị theo hỗ trợ của driver, và vẫn validate giới hạn.

## 15. Một ví dụ hoàn chỉnh: search service an toàn

Giả sử request hỗ trợ status, khoảng giá, từ khóa title và sorting:

~~~java
public record BookSearchRequest(
        BookStatus status,
        BigDecimal minPrice,
        BigDecimal maxPrice,
        String titleContains,
        String sortField,
        String direction
) {}

public enum BookSortField {
    TITLE, PRICE, CREATED_AT
}

public enum SortDirection {
    ASC, DESC
}
~~~

Service dùng HQL template với fragment cố định:

~~~java
public List<Book> search(BookSearchRequest request) {
    BookSortField sortField = parseSortField(request.sortField());
    SortDirection direction = parseDirection(request.direction());

    String sortPath = switch (sortField) {
        case TITLE -> "b.title";
        case PRICE -> "b.price";
        case CREATED_AT -> "b.createdAt";
    };

    String sortKeyword =
            direction == SortDirection.DESC ? "desc" : "asc";

    StringBuilder hql = new StringBuilder(
            "select b from Book b where b.tenantId = :tenantId"
    );

    Map<String, Object> params = new HashMap<>();
    params.put("tenantId", currentTenant.id());

    if (request.status() != null) {
        hql.append(" and b.status = :status");
        params.put("status", request.status());
    }

    if (request.minPrice() != null) {
        hql.append(" and b.price >= :minPrice");
        params.put("minPrice", request.minPrice());
    }

    if (request.maxPrice() != null) {
        hql.append(" and b.price <= :maxPrice");
        params.put("maxPrice", request.maxPrice());
    }

    if (request.titleContains() != null
            && !request.titleContains().isBlank()) {
        hql.append(" and lower(b.title) like :titlePattern escape '!'");
        String escaped = escapeLike(
                request.titleContains().toLowerCase(Locale.ROOT)
        );
        params.put("titlePattern", "%" + escaped + "%");
    }

    hql.append(" order by ")
       .append(sortPath)
       .append(" ")
       .append(sortKeyword)
       .append(", b.id asc");

    TypedQuery<Book> query =
            entityManager.createQuery(hql.toString(), Book.class);

    params.forEach(query::setParameter);

    return query.getResultList();
}
~~~

Các helper parseSortField, parseDirection, escapeLike cần triển khai theo ví dụ ở trên. Request cần được validate thêm:

- minPrice không âm nếu domain yêu cầu.
- maxPrice không nhỏ hơn minPrice.
- titleContains có giới hạn độ dài.
- sort field và direction chỉ thuộc allowlist.
- tenant ID lấy từ authenticated server context.
- Kết quả cần pagination/size limit để tránh truy vấn không giới hạn.

Ví dụ minh họa cách tách rõ **query syntax nội bộ** và **giá trị request được bind**. Trong ứng dụng lớn, Criteria API hoặc query specification có thể giúp tái sử dụng predicates và giảm code StringBuilder.

## 16. Các lỗi thường gặp

| Cách làm | Rủi ro | Cách thay thế |
| --- | --- | --- |
| Nối request value vào HQL | HQL/SQL injection | Named/positional parameter |
| Bind tên field như :sortField | Parameter chỉ là giá trị, không phải path | Allowlist hoặc Criteria path |
| Nối ASC/DESC từ request | Người dùng điều khiển cú pháp | Enum direction |
| Nhận raw WHERE/ORDER BY fragment | Client kiểm soát query grammar | Request DTO có schema |
| Nối ID vào IN (...) | Injection và lỗi quoting/type | Collection parameter |
| Dùng LIKE '%input%' mà không hiểu wildcard | % và _ có semantics wildcard | Escape nếu cần tìm literal |
| Dùng raw table name trong native SQL | Identifier injection | Allowlist identifier |
| Dùng bind parameter để chọn table/column | Không có semantics như identifier | Chọn fragment cố định |
| Query an toàn nhưng thiếu tenant filter | Data exposure/authorization bug | Predicate server-side từ security context |
| Cast kết quả động không kiểm soát | ClassCastException/runtime bug | Typed query/DTO projection |
| Pagination không giới hạn | Resource exhaustion | Validate page/size và giới hạn tối đa |
| Catch lỗi query rồi tiếp tục Session lỗi | Persistence context/transaction có thể không còn an toàn | Rollback, bỏ context và xử lý ở boundary |

## 17. Kiểm thử truy vấn động

Test nên bao phủ cả tính đúng đắn và khả năng chống injection:

1. **Giá trị chứa dấu nháy:** title như O'Reilly được tìm như dữ liệu bình thường.
2. **Chuỗi giống injection:** x' or 1=1 -- không làm trả thêm dữ liệu ngoài điều kiện.
3. **Sort field lạ:** price desc, id hoặc name) ... bị từ chối, không được nối vào query.
4. **Direction lạ:** chỉ asc/desc được chấp nhận.
5. **Wildcard LIKE:** kiểm tra %, _ và escape character theo semantics đã chọn.
6. **IN list rỗng/rất lớn:** xử lý rõ ràng và giới hạn kích thước.
7. **Filter null/thiếu:** query được tạo đúng khi từng filter không có.
8. **Tenant/owner scope:** user không thể đọc dữ liệu của tenant khác bằng cách sửa request.
9. **Pagination:** page/size âm, cực lớn và offset overflow được xử lý.
10. **Native query:** identifier chỉ lấy từ allowlist, mọi value vẫn được bind.

Không chỉ kiểm tra chuỗi HQL cuối cùng. Nên thực thi query trên DB test phù hợp, xác nhận tập kết quả và quyền truy cập. Với test bảo mật, kiểm tra rằng input độc hại được xử lý như một giá trị hoặc bị validation từ chối, không thay đổi cấu trúc query.

## 18. Quy trình xây dựng query động an toàn

1. **Thiết kế request theo dữ liệu, không theo cú pháp.** Client gửi status, khoảng giá, sort option; không gửi HQL/SQL.
2. **Validate kiểu và miền giá trị.** Enum, số, ngày giờ, độ dài chuỗi và số lượng phần tử.
3. **Bind mọi giá trị.** Named parameters là lựa chọn dễ đọc; collection parameter dùng cho IN.
4. **Chọn cấu trúc từ code tin cậy.** Allowlist field, operator, join path và direction.
5. **Dùng Criteria API khi tổ hợp điều kiện phức tạp.** Criteria giảm lỗi nối chuỗi nhưng vẫn cần allowlist path.
6. **Xử lý semantics đặc biệt.** LIKE wildcard, null, empty IN, collation và case normalization.
7. **Áp dụng authorization độc lập.** Tenant/owner scope lấy từ security context server-side.
8. **Giới hạn tài nguyên.** Page size, độ dài tìm kiếm, số ID và độ phức tạp filter.
9. **Giữ query shape ổn định khi phù hợp.** Parameter binding hỗ trợ readability và khả năng reuse plan.
10. **Test trên DBMS thật và theo dõi.** Xem SQL, bind parameters an toàn, query plan, latency và kết quả quyền truy cập.

## 19. Bài tập tự kiểm tra

1. Vì sao where b.title = :title an toàn hơn nối trực tiếp title vào HQL?
2. Có thể dùng parameter để thay tên thuộc tính trong ORDER BY không? Vì sao?
3. Một API cho phép sort theo title, price và createdAt. Hãy thiết kế enum/allowlist cho path và direction.
4. Vì sao parameter binding không ngăn % trong LIKE trở thành wildcard?
5. Làm thế nào bind một danh sách ID trong biểu thức IN? Cần xử lý danh sách rỗng ra sao?
6. Vì sao native SQL cũng phải dùng parameter binding?
7. Một query có bind tenant ID từ request body. Điều đó đã đủ để bảo vệ tenant isolation chưa?
8. Criteria API có tự làm root.get(request.field()) an toàn không?
9. Vì sao không nên nhận một chuỗi WHERE do client gửi?
10. Một query dùng setMaxResults nhưng không giới hạn page size có rủi ro gì?

**Gợi ý:** (1) giá trị được bind tách khỏi cú pháp; (2) không, parameter không phải identifier; (3) enum map sang path cố định và ASC/DESC; (4) wildcard là semantics của LIKE, không phải cú pháp injection; (5) bind collection, xử lý empty list theo hợp đồng; (6) native SQL vẫn diễn giải cú pháp; (7) không, tenant scope phải được xác thực ở server; (8) không, field name vẫn cần allowlist; (9) nó trao quyền điều khiển query grammar; (10) resource exhaustion và query quá lớn.
