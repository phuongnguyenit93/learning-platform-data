# Tải thực thể theo định danh và lấy tham chiếu trì hoãn

Trong JPA/Hibernate, hai thao tác dưới đây đều bắt đầu bằng **kiểu thực thể** và **giá trị khóa chính**, nhưng chúng không có cùng mục đích:

~~~java
Customer customer = em.find(Customer.class, 42L);
Customer reference = em.getReference(Customer.class, 42L);
~~~

`find()` được dùng khi ứng dụng cần **tìm thực thể theo định danh**, và nhận `null` nếu không tồn tại. `getReference()` được dùng khi ứng dụng cần **một tham chiếu đến thực thể mang định danh đó**, chưa chắc cần đọc ngay các cột của hàng SQL. Hibernate thường có thể trả về proxy chưa khởi tạo, trì hoãn việc tải dữ liệu cho đến khi truy cập trạng thái.

Điều quan trọng nhất trong chương **Vòng đời thực thể** là: **một đối tượng đang được Hibernate quản lý không nhất thiết đã được tải đầy đủ**, và **nhận được một reference không chứng minh hàng dữ liệu thực sự tồn tại**. Hiểu hai nguyên tắc này sẽ giúp tránh những lỗi phổ biến về lazy initialization, transaction, kiểm tra tồn tại và hiệu năng N+1.

Bài học sử dụng Jakarta Persistence (`jakarta.persistence.*`), Hibernate ORM và cú pháp SQL PostgreSQL cho ví dụ. Với dự án dùng namespace `javax.persistence.*` hoặc phiên bản Hibernate cũ, tên API có thể khác, nhưng mô hình nhận diện entity và persistence context vẫn là nền tảng.

## 1. Định danh, thực thể và persistence context

Một entity có định danh để Hibernate nhận biết nó đại diện cho hàng nào trong cơ sở dữ liệu:

~~~java
@Entity
@Table(name = "customers")
public class Customer {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "display_name", nullable = false)
    private String displayName;

    protected Customer() {}

    public Long getId() {
        return id;
    }

    public String getDisplayName() {
        return displayName;
    }
}
~~~

Giả sử bảng `customers` chứa:

| id | display_name |
| ---: | --- |
| 42 | Nguyễn An |
| 43 | Trần Bình |

Một lần gọi `find(Customer.class, 42L)` muốn lấy thực thể gắn với hàng `id = 42`. Trong `EntityManager` hiện tại, Hibernate sử dụng **persistence context** như một bản đồ nhận diện:

~~~text
Entity identity                    Managed Java instance
(Customer, 42)       ───────────► Customer object / reference A
(Customer, 43)       ───────────► Customer object / reference B
~~~

Trong cùng một persistence context, Hibernate/JPA giữ tính đồng nhất của managed entity: cùng kiểu entity và cùng định danh không tạo ra hai đối tượng managed độc lập cho cùng hàng. Đây là **first-level cache** và mô hình identity map của persistence context.

Chẳng hạn:

~~~java
Customer first = em.find(Customer.class, 42L);
Customer second = em.find(Customer.class, 42L);

System.out.println(first == second); // true nếu entity tồn tại
~~~

Lần gọi thứ hai thường không cần query SQL mới vì context đã biết entity.

Nhưng persistence context có thể biết **identity** trước khi biết **toàn bộ trạng thái**. Đó chính là điểm xuất phát của reference trì hoãn.

## 2. Mô hình ví dụ xuyên suốt

Ta có quan hệ một khách hàng có nhiều đơn hàng; mỗi đơn hàng tham chiếu một khách hàng.

~~~sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    display_name VARCHAR(160) NOT NULL,
    email VARCHAR(200) NOT NULL UNIQUE
);

CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_code VARCHAR(40) NOT NULL UNIQUE,
    customer_id BIGINT NOT NULL REFERENCES customers(id)
);
~~~

Định nghĩa entity:

**`Customer.java`**

~~~java
package com.example.shop.domain;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;
import java.util.Objects;

@Entity
@Table(name = "customers")
public class Customer {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "display_name", nullable = false, length = 160)
    private String displayName;

    @Column(nullable = false, unique = true, length = 200)
    private String email;

    protected Customer() {
    }

    public Customer(String displayName, String email) {
        this.displayName = Objects.requireNonNull(displayName);
        this.email = Objects.requireNonNull(email);
    }

    public Long getId() {
        return id;
    }

    public String getDisplayName() {
        return displayName;
    }

    public String getEmail() {
        return email;
    }

    public void rename(String newName) {
        this.displayName = Objects.requireNonNull(newName);
    }
}
~~~

**`PurchaseOrder.java`**

~~~java
package com.example.shop.domain;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.FetchType;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.JoinColumn;
import jakarta.persistence.ManyToOne;
import jakarta.persistence.Table;
import java.util.Objects;

@Entity
@Table(name = "purchase_orders")
public class PurchaseOrder {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "order_code", nullable = false, unique = true)
    private String orderCode;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "customer_id", nullable = false)
    private Customer customer;

    protected PurchaseOrder() {
    }

    public PurchaseOrder(String orderCode, Customer customer) {
        this.orderCode = Objects.requireNonNull(orderCode);
        this.customer = Objects.requireNonNull(customer);
    }

    public Long getId() {
        return id;
    }

    public String getOrderCode() {
        return orderCode;
    }

    public Customer getCustomer() {
        return customer;
    }

    public void changeCustomer(Customer newCustomer) {
        this.customer = Objects.requireNonNull(newCustomer);
    }
}
~~~

Cột `purchase_orders.customer_id` là khóa ngoại, còn field `PurchaseOrder.customer` là tham chiếu tới một entity. Hibernate dựa vào metadata `@ManyToOne` và `@JoinColumn` để chuyển một object reference thành giá trị khóa ngoại khi ghi.

`FetchType.LAZY` yêu cầu nạp association theo hướng trì hoãn. Điều này có liên quan tới proxy nhưng **không đồng nghĩa** mọi lời gọi `getReference` hoặc getter association luôn không phát SQL.

## 3. `EntityManager.find()`: lấy entity theo khóa chính

Cú pháp cơ bản:

~~~java
Customer customer = em.find(Customer.class, 42L);
~~~

Khi tìm thấy entity, `find` trả về một instance được quản lý bởi context hiện tại. Nếu không tìm thấy, trả về `null`.

~~~java
Customer customer = em.find(Customer.class, customerId);

if (customer == null) {
    throw new IllegalArgumentException(
        "Không tìm thấy khách hàng có ID: " + customerId
    );
}

System.out.println(customer.getDisplayName());
~~~

Trong tình huống context chưa có entity và cache không đáp ứng, Hibernate có thể sinh:

~~~sql
SELECT id, display_name, email
FROM customers
WHERE id = 42;
~~~

**Không khẳng định mỗi `find` đều tương ứng một `SELECT`.** Nếu entity đã được tải trong persistence context, `find` có thể trả ngay instance cũ. Nếu second-level cache được bật và có dữ liệu hợp lệ, Hibernate cũng có thể tải từ cache.

### Khi cần dùng `find`

`find` thích hợp khi ứng dụng phải:

- Hiển thị tên hoặc thuộc tính khác của khách hàng.
- Kiểm tra khách hàng tồn tại và xử lý nhánh không tồn tại.
- Kiểm tra trạng thái nghiệp vụ như hoạt động/tạm khóa.
- Sửa thuộc tính của một entity cụ thể.
- Lấy một managed entity đã được xác định trước khi thực hiện logic phức tạp.

Tuy nhiên, **find không tự tải toàn bộ object graph**. Nếu `Customer` có collection đơn hàng `@OneToMany(fetch=LAZY)`, collection đó vẫn có thể chưa được tải sau khi tìm khách hàng.

### Tìm theo ID khác tìm theo khóa nghiệp vụ

~~~java
em.find(Customer.class, 42L);
~~~

tìm bằng `@Id`. Nếu muốn tìm bằng email:

~~~java
List<Customer> customers = em.createQuery(
        "select c from Customer c where c.email = :email",
        Customer.class
    )
    .setParameter("email", "an@example.test")
    .getResultList();
~~~

Không thể dùng `find(Customer.class, "an@example.test")` trừ khi `email` thật sự là ID của entity, điều không đúng trong ví dụ.

## 4. `EntityManager.getReference()`: lấy tham chiếu nhưng chưa nhất thiết tải dữ liệu

Cú pháp:

~~~java
Customer ref = em.getReference(Customer.class, 42L);
~~~

Trong cấu hình Hibernate thông dụng, nếu entity chưa có trong persistence context, provider có thể tạo **proxy chưa khởi tạo** cho `Customer` có ID `42`. Proxy biết cách yêu cầu Hibernate nạp trạng thái khi cần.

~~~text
em.getReference(Customer.class, 42L)
          |
          v
   Customer reference
     id = 42
     displayName = chưa nạp
     email = chưa nạp
          |
          | getDisplayName()
          v
    Khởi tạo reference
          |
          v
 SELECT FROM customers WHERE id = 42
          |
          v
 Trả về "Nguyễn An" nếu tìm thấy
~~~

Nhờ vậy, nếu ứng dụng chỉ cần ID của khách hàng để ghi khóa ngoại, nó có thể **tránh đọc những cột không sử dụng**.

**Nhưng JPA không cam kết `getReference` luôn không truy cập database.** Provider có thể kiểm tra sự tồn tại ngay tại `getReference` hoặc cần tải sớm vì cấu hình/mapping cụ thể. Hibernate cũng có thể trả instance đã managed nếu context đang có nó.

### Không dùng reference để kiểm tra tồn tại

~~~java
Customer ref = em.getReference(Customer.class, 999999L);
~~~

Lời gọi trên **có thể trả về object** dù hàng `id = 999999` không tồn tại. Lỗi có thể chỉ xuất hiện khi:

- Một getter cần trạng thái khiến proxy phải khởi tạo.
- Hibernate phát SQL cần trạng thái đó.
- Một thao tác insert/update dùng FK không hợp lệ bị database từ chối.
- Hoặc ngay tại `getReference` nếu provider chọn kiểm tra tồn tại sớm.

Vì vậy, điều kiện `ref != null` không chứng minh khách hàng có thật. `getReference` là yêu cầu **tham chiếu identity**, không phải **existence check**.

## 5. So sánh `find` và `getReference`

| Khía cạnh | `find(Customer.class,id)` | `getReference(Customer.class,id)` |
| --- | --- | --- |
| Ý định | Tìm entity theo định danh và truy cập trạng thái | Lấy tham chiếu đến entity có ID đã biết |
| Khi không tồn tại | Thường trả `null` | Có thể trả proxy và báo lỗi khi dùng; có thể báo lỗi ngay |
| Truy vấn SQL lúc gọi | Có thể cần SQL; có thể được đáp ứng từ context/cache | Thường có thể tránh SQL khi tạo proxy; không bảo đảm |
| Trạng thái trả về | Entity managed nếu tồn tại | Reference do context quản lý; có thể chưa initialized |
| Khi đọc field khác ID | Trạng thái cơ bản thường đã có | Có thể kích hoạt khởi tạo proxy |
| Dùng để xác thực tồn tại | Phù hợp theo mapping và quyền truy cập | **Không phù hợp** |
| Dùng để gán FK mà không đọc thuộc tính | Hợp lệ nhưng có thể dư query | Thường hữu ích |
| Khả năng phát lỗi sau khi session đóng | Lazy association chưa tải vẫn có thể lỗi | Proxy chưa initialized đặc biệt dễ gặp lỗi |
| Gắn transaction lock | Có các overload với lock mode | Reference không tự mang DB lock |

Trong một persistence context đã có `Customer id=42`, cả hai phương thức có thể dùng cùng managed instance, nên không thể suy luận số SQL chỉ từ tên API.

## 6. Proxy Hibernate hoạt động ra sao?

Một **entity proxy** là đại diện có khả năng trì hoãn việc truy cập trạng thái. Hibernate có thể dùng subclass proxy, interceptor và cơ chế bytecode enhancement tùy kiểu entity/cấu hình.

Ví dụ:

~~~java
Customer ref = em.getReference(Customer.class, 42L);
~~~

Khi reference chưa khởi tạo:

- Hibernate biết identifier `42` và entity mapping cần thiết.
- Các cột cơ bản như `display_name` chưa chắc đã được đọc.
- Object có thể được theo dõi trong persistence context.
- Khi truy cập thuộc tính cần dữ liệu, Hibernate có thể nạp entity từ context/cache/database.
- Nếu hàng không còn tồn tại, việc khởi tạo có thể thất bại.

### Truy cập ID có khiến proxy khởi tạo?

Trong trường hợp Hibernate proxy phổ biến, getter đơn giản của ID thường có thể trả giá trị mà không cần `SELECT`:

~~~java
Long id = ref.getId();
~~~

Nhưng hành vi chính xác còn tùy cách ánh xạ identifier, field/property access, proxy, composite ID, bytecode enhancement và các phương thức tự định nghĩa. Đừng biến đây thành giả định tuyệt đối cho mọi entity. Nếu ứng dụng đã có `customerId` và chỉ cần giá trị khóa để ghi log, nó có thể dùng chính biến ID thay vì gọi getter của proxy.

### `getClass()` không luôn là `Customer.class`

Với proxy subclass:

~~~java
ref.getClass() == Customer.class
~~~

có thể là `false` dù reference đại diện `Customer`. Hibernate có API để xác định kiểu thực thể, nhưng việc xác định class thực tế có thể khởi tạo proxy trong một số cấu hình. Tránh dùng so sánh class runtime thô như quy tắc nhận diện nghiệp vụ khi có proxy hoặc inheritance.

### Proxy không phải Customer “rỗng”

Reference chưa khởi tạo không có nghĩa customer thật sự có `displayName = null`. Các cột chưa được đọc, và getter có thể nạp chúng. Nếu hàng thiếu, Hibernate báo lỗi thay vì coi proxy là một entity mới có giá trị mặc định.

## 7. Phân biệt managed, initialized và detached

Hai chiều trạng thái cần tách riêng.

**Vòng đời JPA:**

~~~text
new/transient --persist--> managed --detach/clear/close--> detached
managed --remove--> removed
~~~

**Trạng thái tải dữ liệu:**

~~~text
Reference/proxy chưa initialized --truy cập thuộc tính--> initialized
~~~

Một proxy có thể đồng thời là:

- **Managed** vì còn gắn với persistence context.
- **Chưa initialized** vì chưa cần đọc các thuộc tính.

Ngược lại, một entity đã tải đầy đủ có thể trở thành **detached** khi đóng context. “Managed” và “đã có dữ liệu” không phải hai từ đồng nghĩa.

Sơ đồ:

~~~mermaid
flowchart TD
    A["getReference(Customer, 42)"] --> B["Reference thuộc context"]
    B --> C{"Cần field khác ID?"}
    C -- "Không" --> D["Chưa nhất thiết phát SELECT"]
    C -- "Có" --> E{"Context còn khả năng tải?"}
    E -- "Có" --> F["Dùng context/cache hoặc SQL SELECT"]
    F --> G{"Hàng tồn tại và truy cập được?"}
    G -- "Có" --> H["Reference initialized"]
    G -- "Không" --> I["EntityNotFound / persistence error"]
    E -- "Không" --> J["Có thể LazyInitializationException"]
~~~

Một reference bị detach khi context đóng vẫn là Java object; nhưng nếu chưa initialized và cần SQL để đọc, nó không thể tự truy vấn database như thể context cũ vẫn còn hoạt động.

## 8. Khi ID không tồn tại: `null` và ngoại lệ xuất hiện ở thời điểm khác nhau

Với `find`:

~~~java
Customer customer = em.find(Customer.class, 999999L);

if (customer == null) {
    // Không có entity tương ứng theo điều kiện/mapping hiện hành.
}
~~~

Với `getReference`:

~~~java
Customer ref =
    em.getReference(Customer.class, 999999L);

// ref có thể chưa phát hiện ID thiếu.

String name = ref.getDisplayName();
// Có thể ném EntityNotFoundException khi cần tải.
~~~

JPA cho phép provider ném `EntityNotFoundException` ngay tại `getReference` nếu kiểm tra sớm, hoặc khi truy cập trạng thái. Hibernate native cũng có thể có các exception riêng được bọc lại tùy API.

Nếu reference được gán vào khóa ngoại và không bị dereference:

~~~java
Customer ref =
    em.getReference(Customer.class, 999999L);

PurchaseOrder order =
    new PurchaseOrder("ORD-NO-CUSTOMER", ref);

em.persist(order);
~~~

Khi phát `INSERT`, database có thể từ chối `customer_id=999999` do FK. Khi đó có thể gặp ngoại lệ ràng buộc database, không nhất thiết là `EntityNotFoundException`.

**Quy tắc:** Không dùng `try/catch` quanh `getReference` để triển khai `existsById`. Không nuốt tất cả `PersistenceException` rồi kết luận entity không tồn tại; chúng cũng có thể biểu thị lỗi mạng, SQL, mapping hoặc quyền.

## 9. Tạo đơn hàng: khi nào `getReference` tiết kiệm SQL?

Giả sử đã có `customerId = 42L` và nghiệp vụ **không cần đọc** tên hay email khách hàng khi lưu đơn.

Cách A, dùng `find`:

~~~java
Customer customer = em.find(Customer.class, customerId);
PurchaseOrder order = new PurchaseOrder("ORD-001", customer);
em.persist(order);
~~~

Nếu entity chưa nằm trong context/cache, SQL minh họa có thể là:

~~~sql
SELECT id, display_name, email
FROM customers
WHERE id = 42;

INSERT INTO purchase_orders (order_code, customer_id)
VALUES ('ORD-001', 42);
~~~

Cách B, dùng `getReference`:

~~~java
Customer customerRef =
    em.getReference(Customer.class, customerId);

PurchaseOrder order =
    new PurchaseOrder("ORD-002", customerRef);

em.persist(order);
~~~

Trong trường hợp Hibernate có thể dùng proxy, SQL có thể chỉ cần:

~~~sql
INSERT INTO purchase_orders (order_code, customer_id)
VALUES ('ORD-002', 42);
~~~

Hibernate biết `42` để ghi FK, không cần materialize `Customer` chỉ để lấy lại ID đã biết.

Đây là **SQL minh họa**, không phải cam kết số lượng lệnh. Generator, flush, cascades, entity listeners, caches, cách provider giải quyết proxy và cấu hình khác có thể khiến SQL thực tế thay đổi.

### Reference không bỏ qua quy tắc nghiệp vụ

Nếu phải xác minh khách hàng đang hoạt động, thuộc đúng tenant, có quyền tạo đơn hoặc không bị khóa, thì việc đọc dữ liệu/kiểm tra quyền là **điều kiện nghiệp vụ thật**.

~~~java
Customer customer = em.find(Customer.class, customerId);

if (customer == null) {
    throw new IllegalArgumentException("Khách hàng không tồn tại");
}

if (!authorization.canCreateOrderFor(customer)) {
    throw new SecurityException("Không có quyền tạo đơn");
}

PurchaseOrder order =
    new PurchaseOrder("ORD-003", customer);

em.persist(order);
~~~

Trong ví dụ, `authorization` đại diện cho thành phần kiểm tra quyền của ứng dụng, không phải API có sẵn của JPA. Không nên dùng `getReference` để lách xác thực tồn tại hoặc bảo mật chỉ vì có thể giảm một query.

## 10. Ví dụ transaction hoàn chỉnh

Trong ứng dụng Java SE dùng resource-local transaction:

~~~java
package com.example.shop.service;

import com.example.shop.domain.Customer;
import com.example.shop.domain.PurchaseOrder;
import jakarta.persistence.EntityManager;
import jakarta.persistence.EntityManagerFactory;
import jakarta.persistence.EntityTransaction;

public class OrderWriter {
    private final EntityManagerFactory emf;

    public OrderWriter(EntityManagerFactory emf) {
        this.emf = emf;
    }

    public Long createOrder(String code, Long customerId) {
        EntityManager em = emf.createEntityManager();
        EntityTransaction tx = em.getTransaction();

        try {
            tx.begin();

            // Chỉ khi customerId đã được kiểm tra ở tầng thích hợp.
            Customer customerRef =
                em.getReference(Customer.class, customerId);

            PurchaseOrder order =
                new PurchaseOrder(code, customerRef);

            em.persist(order);
            tx.commit();

            return order.getId();
        } catch (RuntimeException ex) {
            if (tx.isActive()) {
                tx.rollback();
            }
            throw ex;
        } finally {
            em.close();
        }
    }
}
~~~

Ví dụ giả định `emf` đã được cấu hình đúng, bảng và FK tồn tại, đồng thời ID khách hàng đã được kiểm tra theo yêu cầu nghiệp vụ.

Đặc điểm đáng chú ý:

1. `getReference` chỉ giúp tạo tham chiếu entity đã có identity.
2. `em.persist(order)` quản lý **đơn hàng mới**; nó không tự tạo khách hàng.
3. Khi dùng `GenerationType.IDENTITY`, Hibernate có thể cần insert để lấy ID của `PurchaseOrder`.
4. FK xác nhận `customer_id` tham chiếu hàng hợp lệ tại thời điểm ràng buộc được database kiểm tra.
5. Transaction thất bại phải rollback và đóng context; không tiếp tục dùng context đang lỗi.
6. `tx.commit()` xác nhận thay đổi; `flush` trước đó vẫn có thể rollback.

Với Spring, thông thường service khai báo `@Transactional` và repository/JPA được framework quản lý. Không nên tự gọi `em.getTransaction().begin()` bên trong một transaction JTA/Spring đã được quản lý.

## 11. Đang managed thì `find` và `getReference` dùng chung identity

Trong cùng persistence context:

~~~java
Customer a = em.find(Customer.class, 42L);
Customer b = em.find(Customer.class, 42L);

System.out.println(a == b); // true nếu cùng entity đã tìm thấy
~~~

Nếu gọi:

~~~java
Customer ref = em.getReference(Customer.class, 42L);
Customer loaded = em.find(Customer.class, 42L);
~~~

Hibernate vẫn duy trì một identity trong context. `find` có thể khởi tạo proxy hoặc sử dụng instance đã được quản lý theo cơ chế của provider. Không nên suy luận có hai entity khác nhau chỉ bởi biến Java khác tên hoặc phương thức khác nhau.

Ngược lại, hai `EntityManager` khác nhau có thể nạp hai instance Java khác nhau đại diện cùng hàng:

~~~java
Customer first = em1.find(Customer.class, 42L);
Customer second = em2.find(Customer.class, 42L);

System.out.println(first == second); // Thường false
~~~

Đây là hai persistence context khác nhau; identity map chỉ bảo toàn đồng nhất **bên trong từng context**.

### `find` đôi khi không phản ánh SQL vừa được chạy ngoài ORM

Nếu entity đã managed, `find` thường trả chính object trong context. Nếu một job khác sửa database, object hiện tại không tự được cập nhật. Khi cần trạng thái mới, dùng `refresh`, context mới hoặc chính sách nhất quán/khóa phù hợp. `getReference` cũng không tự làm dữ liệu “mới hơn” trong một context đang giữ state cũ.

## 12. Hibernate Session API tương đương

Nếu dùng Hibernate native:

~~~java
import org.hibernate.Session;

Session session = sessionFactory.openSession();

try {
    Customer byFind = session.find(Customer.class, 42L);
    Customer byGet = session.get(Customer.class, 42L);
    Customer lazyRef = session.getReference(Customer.class, 42L);
} finally {
    session.close();
}
~~~

Trong cách dùng thông thường, `session.find` và `session.get` tìm entity theo ID (có thể trả `null`). `session.getReference` yêu cầu reference có khả năng tải trì hoãn.

Hibernate còn cung cấp API:

~~~java
Customer loaded =
    session.byId(Customer.class).load(42L);

Customer reference =
    session.byId(Customer.class).getReference(42L);
~~~

Dạng `byId` cho phép lựa chọn một số tùy chọn load theo ID của Hibernate. Khi ứng dụng cần tính di động giữa provider, ưu tiên API `EntityManager`.

Có những tài liệu Hibernate cũ sử dụng:

~~~java
session.load(Customer.class, 42L);
~~~

Một số overload `Session.load` đã thay đổi/deprecated ở các phiên bản mới. Khi viết ứng dụng hiện đại, ưu tiên `Session.getReference` hoặc `session.byId(...).getReference(...)` theo phiên bản Hibernate được dùng; không sao chép API cũ chỉ vì nó có tên “load”.

| Mục tiêu | Jakarta Persistence | Hibernate native |
| --- | --- | --- |
| Tải entity theo ID | `EntityManager.find` | `Session.find`, `Session.get`, `byId.load` |
| Lấy reference | `EntityManager.getReference` | `Session.getReference`, `byId.getReference` |
| Kiểm tra object managed | `em.contains` | `session.contains` |
| Quan sát lazy state | `PersistenceUnitUtil.isLoaded` | `Hibernate.isInitialized` |
| Yêu cầu init proxy/collection | Truy cập dữ liệu trong context hoặc fetch plan | `Hibernate.initialize` khi session hợp lệ |

## 13. Spring Data JPA: `findById` và `getReferenceById`

Nếu repository khai báo:

~~~java
public interface CustomerRepository
        extends JpaRepository<Customer, Long> {
}
~~~

ta có:

~~~java
Optional<Customer> found =
    customerRepository.findById(42L);

Customer reference =
    customerRepository.getReferenceById(42L);
~~~

- `findById` mang ý nghĩa tìm kiếm và trả `Optional` để xử lý không tồn tại.
- `getReferenceById` dựa trên JPA `getReference`, có thể trả tham chiếu chưa tải.
- Không nên mặc định `getReferenceById` đã xác nhận ID có thật.

Ví dụ Spring service gán FK:

~~~java
@Service
public class OrderService {
    private final CustomerRepository customers;
    private final PurchaseOrderRepository orders;

    public OrderService(
        CustomerRepository customers,
        PurchaseOrderRepository orders
    ) {
        this.customers = customers;
        this.orders = orders;
    }

    @Transactional
    public PurchaseOrder create(String code, Long customerId) {
        // ID và quyền đã được kiểm tra ở tầng phù hợp.
        Customer ref = customers.getReferenceById(customerId);
        return orders.save(new PurchaseOrder(code, ref));
    }
}
~~~

Đoạn trên giả định `PurchaseOrderRepository` kế thừa `JpaRepository<PurchaseOrder, Long>` và có các import Spring phù hợp. Trong API thực tế, thường trả về DTO/ID thay vì trả entity trực tiếp cho client.

Trong Spring Data JPA cũ có thể gặp `getOne` hoặc `getById`, nhưng `getReferenceById` là tên rõ mục đích hơn trong các phiên bản hiện đại.

## 14. Quan sát reference đã initialized chưa

Hibernate có:

~~~java
import org.hibernate.Hibernate;

Customer ref = em.getReference(Customer.class, 42L);

boolean before = Hibernate.isInitialized(ref);

Hibernate.initialize(ref);

boolean after = Hibernate.isInitialized(ref);
~~~

`Hibernate.isInitialized(ref)` giúp quan sát trạng thái của proxy/collection. `Hibernate.initialize(ref)` yêu cầu tải dữ liệu nếu chưa có và session còn đủ khả năng phục vụ.

Trong trường hợp proxy trì hoãn thông dụng:

~~~text
before = false
after  = true
~~~

Nhưng nếu entity đã có trong context hoặc provider không dùng proxy chưa initialized, `before` có thể đã là `true`.

### `initialize` có giới hạn

- Có thể phát SQL hoặc dùng cache.
- Có thể ném ngoại lệ khi hàng thiếu.
- Có thể ném `LazyInitializationException` nếu session đã đóng.
- Khởi tạo entity proxy **không bảo đảm toàn bộ lazy collections bên trong đã tải**.

Ví dụ nếu `Customer` có field `orders` lazy, `Hibernate.initialize(customer)` chưa chắc khởi tạo `customer.getOrders()`. Muốn toàn bộ dữ liệu cần thiết để trả API, hãy thiết kế fetch plan/projection phù hợp.

### API chuẩn JPA để quan sát loaded state

~~~java
import jakarta.persistence.PersistenceUnitUtil;

PersistenceUnitUtil util = emf.getPersistenceUnitUtil();

boolean entityLoaded = util.isLoaded(ref);
boolean emailLoaded = util.isLoaded(ref, "email");
~~~

`isLoaded` chỉ trả về đánh giá trạng thái đã tải theo provider, không phải lệnh tự khởi tạo. Đây là lựa chọn khi không muốn phụ thuộc API riêng Hibernate để kiểm tra.

## 15. Khi context đóng: `LazyInitializationException`

Xem đoạn:

~~~java
Customer reference;

EntityManager em = emf.createEntityManager();
try {
    reference = em.getReference(Customer.class, 42L);
} finally {
    em.close();
}

String name = reference.getDisplayName();
~~~

Nếu `reference` chưa initialized, Hibernate có thể ném `LazyInitializationException`: không còn session thích hợp để nạp trạng thái. Object Java vẫn tồn tại nhưng đã **detached** khỏi context vừa đóng.

Nguyên tắc quan trọng: **đóng session không tự động tải những field chưa đọc**.

### Cách phù hợp: chuyển sang DTO khi context còn mở

~~~java
public record CustomerSummary(
    Long id,
    String displayName,
    String email
) {
}
~~~

Trong service có transaction:

~~~java
@Transactional(readOnly = true)
public CustomerSummary readSummary(Long id) {
    Customer c = customerRepository.findById(id)
        .orElseThrow(() -> new NoSuchElementException(
            "Không tìm thấy khách hàng " + id
        ));

    return new CustomerSummary(
        c.getId(),
        c.getDisplayName(),
        c.getEmail()
    );
}
~~~

Ví dụ dùng Spring và giả định import `NoSuchElementException` cùng các annotation/repository cần thiết. DTO không có proxy nên phù hợp để trả qua HTTP hoặc qua ranh giới process.

### Truy vấn projection trực tiếp

Nếu chỉ cần một số cột, JPA constructor expression:

~~~java
List<CustomerSummary> result = em.createQuery(
    "select new com.example.shop.api.CustomerSummary(" +
    "c.id, c.displayName, c.email) " +
    "from Customer c where c.id = :id",
    CustomerSummary.class
)
.setParameter("id", 42L)
.getResultList();
~~~

Đường dẫn class trong JPQL cần khớp đúng package thực của DTO. Dùng projection khi không cần entity managed và không muốn nạp những trường/association ngoài nhu cầu.

## 16. `@ManyToOne(fetch = LAZY)` cũng dựa vào reference

Khi tải đơn hàng:

~~~java
PurchaseOrder order = em.find(PurchaseOrder.class, orderId);
Customer customer = order.getCustomer();
~~~

Hibernate biết `customer_id` nhờ hàng đơn. Nó có thể đại diện `Customer` bằng reference chưa initialized và chỉ tải khách hàng khi gọi:

~~~java
String name = customer.getDisplayName();
~~~

Tuy nhiên, không phải mọi association đều có cùng default:

| Quan hệ JPA | Fetch mặc định |
| --- | --- |
| `@ManyToOne` | `EAGER` |
| `@OneToOne` | `EAGER` |
| `@OneToMany` | `LAZY` |
| `@ManyToMany` | `LAZY` |

Vì thế cần khai báo `@ManyToOne(fetch = FetchType.LAZY)` nếu muốn gợi ý nạp trì hoãn. Với một số cấu trúc `@OneToOne`, tính lazy còn phụ thuộc cách mapping và bytecode enhancement; chỉ thêm `LAZY` không nhất thiết làm mọi trường hợp tránh query.

**Lazy association** mô tả chiến lược tải liên kết của entity. **`getReference` tường minh** bắt đầu từ class và ID mà ứng dụng đã biết; chúng có thể dùng chung cơ chế reference nhưng khác điểm khởi đầu.

## 17. Gán lại FK bằng reference

Giả sử nghiệp vụ cho phép chuyển một đơn hàng sang khách hàng khác:

~~~java
PurchaseOrder order = em.find(PurchaseOrder.class, orderId);

Customer newCustomer =
    em.getReference(Customer.class, newCustomerId);

order.changeCustomer(newCustomer);
~~~

Trong transaction, Hibernate có thể dùng ID của reference để cập nhật `purchase_orders.customer_id` mà không cần nạp mọi thuộc tính của khách hàng mới.

Nhưng việc chuyển khách hàng có thể chịu các quy tắc: đơn đã thanh toán không được chuyển, quyền người dùng, hóa đơn đã phát hành, v.v. Các kiểm tra đó phải được thực thi trong service phù hợp. Reference chỉ giúp biểu diễn association theo ID.

Không sửa trực tiếp ID của một Customer managed để “đổi khách hàng”; cần thay **tham chiếu entity ở field `PurchaseOrder.customer`**. ID của entity phải ổn định trong suốt vòng đời persistent.

## 18. Transaction, khóa và cạnh tranh đồng thời

`getReference` không giữ khóa database và không bảo đảm hàng còn tồn tại tới cuối transaction.

Một tình huống:

~~~text
Transaction A: getReference(Customer, 42)
                    |
Transaction B: xóa hoặc sửa Customer 42 rồi COMMIT
                    |
Transaction A: reference.getDisplayName()
~~~

Nếu hệ thống cho phép B thay đổi hàng, A có thể đọc dữ liệu khác dự kiến hoặc phát hiện hàng đã biến mất. Hành vi cụ thể phụ thuộc isolation level, FK và transaction thực tế.

Ngay cả `find` cũng không tự đặt khóa mạnh để giữ hàng bất biến. Nếu cần locking:

~~~java
Customer customer = em.find(
    Customer.class,
    42L,
    LockModeType.PESSIMISTIC_WRITE
);
~~~

Cần import `jakarta.persistence.LockModeType`, transaction còn hoạt động và database hỗ trợ cơ chế khóa. Lời gọi có thể phát SQL để lấy khóa; đây là mục đích khác với tạo reference.

Nếu cần phát hiện xung đột khi cập nhật entity, dùng `@Version` với optimistic locking theo mô hình JPA. `getReference` tự nó không phải API concurrency control.

### Kiểm tra tồn tại rồi thao tác vẫn có race condition

~~~java
Customer customer = em.find(Customer.class, 42L);

if (customer != null) {
    // Transaction khác có thể xóa hàng sau lúc kiểm tra.
}
~~~

Vì vậy **ràng buộc FK/transaction và thiết kế concurrency** vẫn rất quan trọng. `find` giúp biết trạng thái tại thời điểm đọc, nhưng không tự bảo đảm tồn tại vĩnh viễn.

## 19. `find` với entity graph khi cần association

Thay vì tải một entity rồi truy cập nhiều reference lazy ngoài dự kiến, JPA hỗ trợ fetch plan rõ ràng. Ví dụ yêu cầu tải `PurchaseOrder` cùng khách hàng:

~~~java
import jakarta.persistence.EntityGraph;
import java.util.Map;

EntityGraph<PurchaseOrder> graph =
    em.createEntityGraph(PurchaseOrder.class);

graph.addAttributeNodes("customer");

Map<String, Object> hints =
    Map.of("jakarta.persistence.fetchgraph", graph);

PurchaseOrder order = em.find(
    PurchaseOrder.class,
    orderId,
    hints
);
~~~

`fetchgraph` chỉ định các thuộc tính cần eager fetch trong ngữ cảnh thao tác; provider có thể dùng JOIN hoặc query khác. `loadgraph` có ngữ nghĩa kết hợp fetch mặc định khác `fetchgraph`.

Fetch graph hữu ích khi ứng dụng biết dữ liệu nào cần dùng. Nó không xác thực quyền hoặc thay đổi identity của entity.

## 20. N+1: reference có thể trì hoãn query, không loại bỏ nhu cầu đọc

Một ví dụ:

~~~java
List<PurchaseOrder> orders = em.createQuery(
    "select o from PurchaseOrder o",
    PurchaseOrder.class
).getResultList();

for (PurchaseOrder o : orders) {
    System.out.println(o.getCustomer().getDisplayName());
}
~~~

Truy vấn ban đầu lấy danh sách đơn. Mỗi lần đọc `getDisplayName()` có thể khởi tạo tham chiếu khách hàng riêng bằng SQL bổ sung. Nếu có nhiều khách hàng khác nhau, chương trình có nguy cơ **N+1**.

Hibernate có thể giảm số query nhờ persistence context, cache hoặc batch fetching; không nhất thiết đúng một SELECT cho mỗi đơn. Nhưng vấn đề là **lazy access phát query không dự kiến khi lặp**.

Nếu trang cần customer name cho mọi đơn, có thể chủ động fetch:

~~~java
List<PurchaseOrder> orders = em.createQuery(
    "select o from PurchaseOrder o " +
    "join fetch o.customer",
    PurchaseOrder.class
).getResultList();
~~~

Với `@ManyToOne`, fetch join thường không nhân số hàng như khi join một collection nhiều phần tử, nhưng vẫn cần cân nhắc lọc, pagination, lock và index.

**Không dùng `getReference` để hứa hẹn chữa N+1**. Nó tiết kiệm query khi chỉ cần identity; nếu cuối cùng phải đọc trạng thái của hàng trăm reference, các query lazy có thể xuất hiện.

## 21. Reference, `equals` và serialization

Proxy có thể khiến những phương thức tưởng “rẻ” phát truy vấn hoặc lỗi.

Một `toString()` gồm toàn bộ thuộc tính:

~~~java
@Override
public String toString() {
    return "Customer{" + displayName + "," + email + "}";
}
~~~

có thể kích hoạt việc đọc trạng thái nếu được gọi trên reference chưa initialized. Nếu context đã đóng, logging đơn giản cũng có thể gặp lỗi.

Tương tự:

- `equals`/`hashCode` dựa trên association có thể gây truy vấn và đệ quy.
- `HashSet` có thể lỗi khi hash của entity thay đổi do ID mới được sinh.
- Serialize trực tiếp entity thành JSON có thể tự gọi getter và tải lazy association ở tầng web.
- Lombok `@Data` sinh các phương thức dựa trên nhiều field có thể không phù hợp với entity có quan hệ hai chiều và proxy.

Nên định nghĩa equality nhất quán theo identity/business key thực sự ổn định, tránh đưa toàn bộ object graph vào `toString` và dùng DTO cho API. Không coi reference chưa khởi tạo là một object truyền dữ liệu độc lập với persistence context.

## 22. Reference và trạng thái detached/merge

Sau khi đóng context:

~~~java
Customer detachedReference;

EntityManager em = emf.createEntityManager();
try {
    detachedReference =
        em.getReference(Customer.class, 42L);
} finally {
    em.close();
}
~~~

`detachedReference` không còn managed trong context cũ. Nếu chưa initialized, việc truy cập field cần tải có thể thất bại.

Trong context mới, khi chỉ cần ID để tạo quan hệ, thường đơn giản hơn lấy lại reference:

~~~java
EntityManager em2 = emf.createEntityManager();

try {
    Customer managedReference =
        em2.getReference(Customer.class, 42L);

    // Thực hiện thao tác trong context/transaction mới.
} finally {
    em2.close();
}
~~~

Nếu có entity detached chứa trạng thái đã sửa cần hợp nhất, dùng `merge`:

~~~java
Customer managedCopy = em.merge(detachedCustomer);
~~~

`merge` trả về managed instance tương ứng; nó không biến object detached ban đầu thành managed. `getReference` và `merge` không thay thế cho nhau: cái thứ nhất cung cấp tham chiếu identity, cái thứ hai hợp nhất trạng thái detached.

Không sửa `@Id` của reference để trỏ sang hàng khác. Muốn một entity liên kết với customer mới, lấy reference mới rồi thay association trên entity sở hữu quan hệ.

## 23. Dùng reference để xóa entity có luôn tránh SELECT?

Đoạn mã thường gặp:

~~~java
Customer ref = em.getReference(Customer.class, id);
em.remove(ref);
~~~

Trong một số mapping, Hibernate có thể dựa trên identity để xóa mà không nạp toàn bộ trạng thái trước. Tuy nhiên **không được bảo đảm**:

- Cascade, orphan removal hoặc entity listener có thể cần tải dữ liệu.
- `@Version`, soft delete và các quy tắc đặc thù có thể thay đổi SQL.
- Provider có thể chọn khởi tạo entity để xử lý remove.
- Nếu ID không tồn tại, thời điểm báo lỗi phụ thuộc mapping và provider.

Ngoài ra còn có FK `purchase_orders.customer_id`: không thể xóa khách hàng có đơn tồn tại nếu ràng buộc không cho phép. Không cố tối ưu một `SELECT` trước khi xác định đúng quy tắc xóa và hậu quả dữ liệu.

## 24. Ánh xạ kế thừa và kiểu proxy thực tế

Với entity kế thừa:

~~~java
ContentItem ref =
    em.getReference(ContentItem.class, id);
~~~

Nếu `ContentItem` là lớp cha của các subtype được phân biệt bằng discriminator, Hibernate có thể chưa biết subtype thực sự khi reference còn chưa tải. Proxy được tạo dựa trên kiểu yêu cầu có thể chưa phù hợp để ép trực tiếp sang mọi subtype.

Nếu cần một `ArticleContent` cụ thể:

~~~java
ArticleContent article =
    em.find(ArticleContent.class, id);
~~~

Truy vấn và metadata sẽ xác định entity có đúng subtype đó hay không. Không tự ép kiểu một root reference chỉ vì ứng dụng nghĩ ID “chắc” thuộc subtype nào.

Để kiểm tra kiểu trong JPQL, có thể dùng `TYPE` hoặc `TREAT` theo JPA. Đó là truy vấn dữ liệu/metadata đúng mục đích, không phải biến reference thành instance kiểu mới.

## 25. Quan sát SQL thực tế thay vì suy đoán

Trong môi trường phát triển, có thể bật SQL logging. Với Spring Boot và Hibernate 6:

~~~properties
logging.level.org.hibernate.SQL=DEBUG
logging.level.org.hibernate.orm.jdbc.bind=TRACE
~~~

Với Hibernate native:

~~~properties
hibernate.show_sql=true
hibernate.format_sql=true
~~~

Cần thận trọng khi log bind parameter vì có thể chứa PII hoặc dữ liệu nhạy cảm. Không bật TRACE trên production khi chưa có chính sách bảo vệ log.

Thí nghiệm:

~~~java
EntityManager em = emf.createEntityManager();

try {
    Customer ref = em.getReference(Customer.class, 42L);

    System.out.println(
        "Before = " + Hibernate.isInitialized(ref)
    );

    String name = ref.getDisplayName();
    System.out.println("Name = " + name);

    System.out.println(
        "After = " + Hibernate.isInitialized(ref)
    );
} finally {
    em.close();
}
~~~

Trong cấu hình proxy trì hoãn phổ biến, kết quả có thể là:

~~~text
Before = false
Name = Nguyễn An
After = true
~~~

Và `SELECT customers` có thể xuất hiện khi đọc `displayName`, không phải khi lấy reference. Nếu `Before = true`, có thể entity đã được tải, provider đã khởi tạo sớm hoặc mapping dùng cơ chế khác; không nên coi đó là lỗi của API.

## 26. Những lỗi thường gặp

| Hiện tượng | Nguyên nhân thường gặp | Cách xử lý |
| --- | --- | --- |
| `getReference` trả object nhưng không có hàng SQL | Provider chưa kiểm tra tồn tại | Không dùng reference làm existence check |
| `EntityNotFoundException` khi gọi getter | Reference không materialize được hàng | Kiểm tra ID, dữ liệu, filter và transaction |
| `LazyInitializationException` sau khi đóng session | Proxy/association chưa initialized | Tải trong context phù hợp hoặc trả DTO |
| Thêm đơn báo lỗi FK dù lấy được reference | Customer ID không tồn tại | Kiểm tra đầu vào; bảo vệ FK |
| Lặp danh sách và phát hàng trăm SELECT | Lazy references khởi tạo từng lượt | Fetch join, batch fetch hoặc projection |
| `find` không phát SQL như dự đoán | Entity đã managed hoặc cache hit | Hiểu first-level/second-level cache |
| `getClass() == Customer.class` sai | Runtime object có thể là proxy subclass | Không dùng so sánh class thô làm logic entity |
| JSON serialization chạy query bất ngờ | Serializer gọi getter trên proxy | Mapping DTO và fetch rõ ràng |
| `getReference` không tự khóa hàng | Không có lock mode | Dùng API locking khi nghiệp vụ cần |
| Entity đã managed nhưng field mới trên DB không hiện | Persistence context giữ trạng thái cũ | Refresh/context mới và chiến lược concurrency |
| `getReference + remove` vẫn phát SELECT | Mapping cần cascade/state/version | Không giả định xóa chỉ bằng ID luôn 0 SELECT |
| Mang proxy qua thread/request khác bị lỗi | Proxy detached, không còn session | Truyền ID/DTO và nạp trong context mới |

## 27. Bài tập tình huống

**Bài 1 — Đọc tên khách hàng.** UI cần `displayName` của `Customer id=42`. Nên dùng `find` hay `getReference`?

**Đáp án:** `find` diễn đạt mục tiêu rõ hơn và cho phép xử lý `null`. `getReference` rồi đọc `displayName` thường vẫn phải nạp dữ liệu, chỉ làm lỗi vắng mặt xuất hiện muộn.

**Bài 2 — Gán FK theo ID đã xác thực.** Service đã biết `customerId=42` và chỉ lưu đơn mới, không cần bất kỳ field customer nào.

**Đáp án:** Có thể dùng `getReference(Customer.class,42L)` để gắn association, nhờ đó tránh một SELECT dư thừa trong cấu hình Hibernate proxy thông dụng. FK vẫn bảo vệ tính toàn vẹn.

**Bài 3 — Reference cho hàng không tồn tại.** `em.getReference(Customer.class,999999L)` không ném ngoại lệ ngay. Có nghĩa `Customer 999999` tồn tại?

**Đáp án:** Không. Reference có thể được tạo mà không xác thực hàng. Khi nạp trạng thái hoặc insert FK, lỗi mới có thể xuất hiện.

**Bài 4 — Reference sau `em.close()`.** Một reference chưa initialized được đưa ra khỏi transaction rồi gọi getter.

**Đáp án:** Có thể gặp `LazyInitializationException`. Tải dữ liệu trước khi đóng context hoặc truyền DTO/ID thay vì proxy.

**Bài 5 — Hai lần `find` trong một context.** `Customer a = em.find(...42L)` và `b = em.find(...42L)` trả về gì?

**Đáp án:** Với entity tồn tại, trong cùng persistence context `a == b` theo quy tắc managed entity identity.

**Bài 6 — 100 đơn hàng cần hiển thị tên khách hàng.** Dùng `getReference` cho mỗi ID có loại N+1 không?

**Đáp án:** Không. Mỗi lần đọc tên có thể khởi tạo reference và gây query bổ sung. Nên dùng fetch join, batch fetching hoặc projection theo nhu cầu.

**Bài 7 — Kiểm tra proxy có nạp chưa.** Có thể dùng getter `getDisplayName()` để xem nó đã loaded hay chưa mà không thay trạng thái không?

**Đáp án:** Không, getter có thể tự kích hoạt tải. Dùng `Hibernate.isInitialized` hoặc `PersistenceUnitUtil.isLoaded`.

**Bài 8 — Client truyền ID khách hàng khác.** Có được phép tạo đơn cho ID đó chỉ vì `getReference` thành công không?

**Đáp án:** Không. Phải kiểm tra quyền và quy tắc nghiệp vụ tương ứng; reference không xác minh authorization.

**Bài 9 — Xóa entity qua reference.** Có thể khẳng định `em.remove(em.getReference(...))` luôn là một SQL `DELETE` không?

**Đáp án:** Không. Cascade, version, listener, FK và cách provider xử lý có thể yêu cầu thêm query hoặc làm thao tác thất bại.

**Bài 10 — Parent entity inheritance.** `getReference(BaseContent.class,id)` có luôn biết subtype cụ thể mà không đọc discriminator không?

**Đáp án:** Không. Với các chiến lược kế thừa, provider có thể phải đọc thêm metadata/dữ liệu để xác định subtype thực tế.

## 28. Bảng chọn API

| Nhiệm vụ | Khởi đầu phù hợp | Lý do |
| --- | --- | --- |
| Tìm entity, xử lý không tồn tại | `find` hoặc `findById` | Nhận kết quả có/không rõ ràng |
| Cần đọc trạng thái hiện tại | `find` hoặc query/projection | Lấy dữ liệu thay vì chỉ identity |
| Chỉ cần ID để gán FK | `getReference` hoặc `getReferenceById` | Có thể tránh đọc thừa |
| Muốn kiểm tra quyền theo dữ liệu | Query/validation nghiệp vụ | Reference không xác thực quyền |
| Cần lock row | `find` với LockMode/API lock | Reference không tự lock |
| Cần entity cùng association | Fetch graph/fetch join | Chủ động xác định dữ liệu cần nạp |
| Cần dữ liệu sau khi context đóng | DTO/projection | Không phụ thuộc lazy proxy |
| Cần xóa theo ID | Xem mapping và remove/reference thích hợp | Không bảo đảm chỉ có một SQL |
| Cần chỉ nhìn trạng thái lazy | `isLoaded` hoặc `isInitialized` | Không tự kích hoạt nạp field |
| Lặp trên nhiều association | Batch/fetch plan/projection | Tránh N+1 |

## 29. Tổng kết

**`find` và `getReference` là hai lựa chọn khác nhau trong quá trình làm việc với entity identity.**

- **`find`** tìm entity theo khóa chính và cho kết quả `null` khi không có hàng tương ứng.
- **`getReference`** cung cấp tham chiếu entity và thường cho phép Hibernate trì hoãn truy vấn trạng thái.
- **Lấy được reference không xác thực tồn tại, quyền truy cập hoặc transaction safety.**
- **Managed không đồng nghĩa initialized.** Proxy có thể thuộc persistence context nhưng chưa tải các cột.
- **Sau khi session/context đóng**, getter cần lazy load có thể phát sinh `LazyInitializationException`.
- **Gán FK bằng reference** là tình huống tối ưu phổ biến nếu nghiệp vụ đã xác minh ID và không cần đọc dữ liệu liên quan.
- **Khi thực sự cần dữ liệu**, hãy dùng `find`, entity graph, fetch join hoặc projection thay vì cố tránh mọi query.
- **Hiệu năng phải đo trên truy vấn thật** với cache, mapping, transaction và kích thước kết quả, không suy từ tên API.
- **Spring Data JPA và Hibernate Session** cung cấp các API tương đương, nhưng cần phân biệt “tải” với “lấy tham chiếu”.

Hiểu rõ thời điểm Hibernate nhận biết identity, thời điểm nó nạp trạng thái và thời điểm persistence context kết thúc giúp viết code JPA/Hibernate vừa đúng vòng đời entity, vừa giảm truy vấn thừa mà không đánh đổi tính toàn vẹn hay quyền truy cập.
