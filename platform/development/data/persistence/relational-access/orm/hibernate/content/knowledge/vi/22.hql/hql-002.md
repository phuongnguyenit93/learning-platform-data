# Quan hệ giữa JPQL chuẩn với các khả năng riêng của HQL

Khi làm việc với Hibernate ORM, lập trình viên thường viết truy vấn bằng một ngôn ngữ gần SQL nhưng thao tác trên entity và thuộc tính Java thay vì bảng, cột vật lý. Ngôn ngữ đó có hai tên thường gặp: **JPQL** và **HQL**.

- **JPQL (Jakarta Persistence Query Language)** là ngôn ngữ truy vấn được chuẩn hóa bởi Jakarta Persistence. Nó định nghĩa một tập cú pháp và ngữ nghĩa truy vấn mà các JPA provider tương thích phải hỗ trợ.
- **HQL (Hibernate Query Language)** là ngôn ngữ truy vấn của Hibernate ORM. HQL có nền tảng tương thích với JPQL và bổ sung nhiều khả năng riêng của Hibernate, đặc biệt ở các phiên bản mới.

Trong Hibernate, JPQL thường được phân tích và thực thi thông qua bộ máy HQL của provider. Vì vậy, một câu JPQL chuẩn thường chạy được trên Hibernate; ngược lại, **một câu HQL có extension riêng không nhất thiết chạy được trên EclipseLink hoặc provider JPA khác**.

Sự khác biệt này quan trọng khi lựa chọn cú pháp cho repository, thiết kế truy vấn phức tạp, nâng cấp Hibernate hoặc muốn giữ khả năng thay đổi JPA provider. Bài học giải thích phần giao nhau giữa hai ngôn ngữ, những khả năng HQL mở rộng, cách dùng an toàn và tiêu chí quyết định nên viết JPQL, HQL hay native SQL.

## 1. JPQL và HQL nằm ở đâu trong kiến trúc persistence?

JPQL không phải SQL viết với tên class thay cho tên bảng một cách đơn giản. Đây là ngôn ngữ truy vấn trên **mô hình entity** mà Jakarta Persistence quản lý.

Ví dụ entity:

```java
@Entity
@Table(name = "purchase_orders")
public class PurchaseOrder {

    @Id
    private UUID id;

    @Column(name = "order_status")
    private String status;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "customer_id")
    private Customer customer;
}
```

SQL làm việc trực tiếp với bảng/cột:

```sql
SELECT o.id, o.order_status, o.customer_id
FROM purchase_orders o
WHERE o.order_status = 'SUBMITTED';
```

JPQL/HQL làm việc với entity/thuộc tính:

```sql
select o
from PurchaseOrder o
where o.status = :status
```

Ở đây:

- `PurchaseOrder` là entity name (mặc định thường là tên class entity, trừ khi `@Entity(name = ...)` đặt tên khác).
- `o` là identification variable/alias.
- `o.status` là thuộc tính Java được mapping.
- `purchase_orders` và `order_status` là tên vật lý của database, không được dùng trong JPQL/HQL thông thường.
- `:status` là named parameter được bind riêng.

Sơ đồ:

```text
JPQL / HQL
    |
    | entity names, attributes, associations
    v
Hibernate query parser + semantic model
    |
    | hiểu mapping, type, association, inheritance
    v
SQL theo dialect và database
    |
    v
JDBC
    |
    v
Database tables / columns
```

Hibernate chuyển truy vấn trên mô hình entity thành SQL phù hợp với dialect. Vì vậy, cùng một JPQL/HQL có thể sinh SQL khác nhau trên PostgreSQL, MySQL, Oracle hoặc SQL Server.

## 2. JPQL là chuẩn, HQL là ngôn ngữ của Hibernate

### 2.1. JPQL thuộc Jakarta Persistence

JPQL được định nghĩa trong đặc tả Jakarta Persistence. Nó cung cấp cú pháp chuẩn cho:

- SELECT và truy vấn entity.
- JOIN association.
- WHERE, GROUP BY, HAVING, ORDER BY.
- Subquery.
- Constructor expression để trả DTO.
- Các biểu thức và hàm chuẩn.
- Bulk UPDATE và DELETE.
- Parameter binding.
- Một số biểu thức collection, inheritance và polymorphism.

Một query JPQL chuẩn có thể chạy trên các provider tương thích Jakarta Persistence mà không phụ thuộc Hibernate-specific extension, miễn mapping và kiểu dữ liệu được hỗ trợ tương ứng.

### 2.2. HQL là superset theo hướng Hibernate

HQL được Hibernate phát triển và tích hợp sâu với mapping/runtime của provider. Nó hỗ trợ phần lớn cú pháp JPQL và có các extension tùy phiên bản, chẳng hạn:

- CTE (`with`, kể cả recursive CTE trong các phiên bản hỗ trợ).
- Window functions và biểu thức `over`.
- Set operations như `union`, `intersect`, `except` theo khả năng phiên bản.
- Derived roots, subquery trong `from` và lateral joins ở các phiên bản hỗ trợ.
- Một số kiểu join và biểu thức không thuộc tập JPQL portable.
- Các hàm Hibernate được đăng ký qua dialect hoặc function registry.
- Một số dạng query/instantiation và tiện ích cú pháp riêng Hibernate.

Không phải extension nào cũng có mặt ở mọi phiên bản Hibernate. Khi dùng một cú pháp HQL mới, cần đối chiếu **User Guide của đúng nhánh Hibernate đang chạy** và dialect thực tế.

### 2.3. Quan hệ tương thích

Có thể hình dung:

```text
                  HQL của Hibernate
        +--------------------------------------+
        |                                      |
        |       JPQL chuẩn                     |
        |      +--------------------+          |
        |      | SELECT / JOIN      |          |
        |      | WHERE / GROUP BY   |          |
        |      | SUBQUERY / DTO     |          |
        |      | BULK UPDATE/DELETE |          |
        |      +--------------------+          |
        |                                      |
        |   HQL extensions: CTE, window,       |
        |   set operations, derived roots,     |
        |   Hibernate functions, ...           |
        +--------------------------------------+
```

Sơ đồ diễn tả quan hệ khái niệm, không phải cam kết rằng mọi phiên bản HQL hỗ trợ mọi mục trong danh sách. Tập JPQL cụ thể cũng thay đổi theo phiên bản đặc tả Jakarta Persistence.

### 2.4. Dùng API EntityManager không tự làm câu query trở thành portable

Ví dụ:

```java
em.createQuery("""
    select o
    from PurchaseOrder o
    where o.status = :status
    """, PurchaseOrder.class);
```

Nếu câu truy vấn nằm trong tập JPQL chuẩn, nó portable theo đặc tả. Nhưng nếu truyền một cú pháp chỉ Hibernate hiểu vào cùng `EntityManager.createQuery`, câu query vẫn là **Hibernate-specific**. API gọi không quyết định tính portable; **ngôn ngữ và tính năng được sử dụng** mới quyết định.

## 3. Ví dụ cơ bản: cùng một câu JPQL cũng là HQL

Entity:

```java
@Entity
public class Product {

    @Id
    private Long id;

    private String name;

    private BigDecimal price;

    private boolean active;
}
```

Truy vấn:

```java
List<Product> products = em.createQuery("""
    select p
    from Product p
    where p.active = true
      and p.price >= :minimumPrice
    order by p.price desc, p.name asc
    """, Product.class)
    .setParameter(
        "minimumPrice",
        new BigDecimal("100.00")
    )
    .getResultList();
```

Đây là cú pháp thuộc tập JPQL chuẩn và Hibernate cũng thực thi được như HQL.

Một số điểm:

- `Product` là entity name.
- `p.active`, `p.price` và `p.name` là thuộc tính entity.
- `:minimumPrice` là named parameter.
- `true` là boolean literal.
- `order by` sắp xếp kết quả theo biểu thức.
- Kết quả là các entity `Product` được quản lý trong persistence context khi query chạy trong context thích hợp.

Không có tên bảng `products` hoặc cột `is_active` trong query, dù mapping vật lý có thể dùng các tên ấy.

### 3.1. Entity name có thể khác class name

```java
@Entity(name = "CatalogItem")
@Table(name = "catalog_items")
public class Product {
    // ...
}
```

JPQL/HQL dùng:

```sql
select p from CatalogItem p
```

không dùng `Product` nếu entity name đã được đổi thành `CatalogItem`. Tên bảng vẫn là `catalog_items` và chỉ thuộc SQL/native query.

### 3.2. Tên thuộc tính là tên trong mô hình entity

Nếu mapping:

```java
@Column(name = "created_at")
private Instant createdAt;
```

thì JPQL/HQL dùng `o.createdAt`, không dùng `o.created_at`.

Đây là khác biệt nền tảng giữa truy vấn ORM và SQL trực tiếp.

## 4. Truy vấn trên entity model, không phải bảng vật lý

JPQL/HQL hiểu association đã được mapping. Ví dụ:

```java
List<PurchaseOrder> orders = em.createQuery("""
    select o
    from PurchaseOrder o
    join o.customer c
    where c.email = :email
    """, PurchaseOrder.class)
    .setParameter("email", email)
    .getResultList();
```

Hibernate dựa trên association `PurchaseOrder.customer` để xác định điều kiện join theo FK mapping.

SQL sinh ra có thể tương đương:

```sql
SELECT o.*
FROM purchase_orders o
JOIN customers c ON c.id = o.customer_id
WHERE c.email = ?;
```

Nhưng query ORM không cần biết `customer_id` nằm ở bảng nào hoặc tên vật lý của cột là gì.

### 4.1. Association path expression

JPQL/HQL cho phép điều hướng theo thuộc tính:

```sql
select o
from PurchaseOrder o
where o.customer.email = :email
```

Đường dẫn `o.customer.email` có thể tạo implicit join tới Customer. Với association optional, implicit path navigation thường mang semantics inner join; nếu muốn giữ root không có association phù hợp, hãy dùng explicit LEFT JOIN và điều kiện phù hợp.

### 4.2. Không thể dùng tên cột tùy ý trong HQL

Ví dụ sai:

```sql
select o
from PurchaseOrder o
where o.order_status = 'SUBMITTED'
```

`order_status` là cột vật lý. Trừ khi entity thực sự có thuộc tính Java mang tên ấy, query không hợp lệ theo mô hình entity.

Nếu cần viết trực tiếp theo bảng/cột, dùng native SQL có chủ đích.

## 5. SELECT, WHERE, GROUP BY và ORDER BY: phần giao nhau rộng

Các cấu trúc truy vấn phổ biến thường có cú pháp tương tự trong JPQL và HQL:

```sql
select ...
from ...
where ...
group by ...
having ...
order by ...
```

Ví dụ thống kê tổng giá trị order theo customer:

```java
List<Object[]> rows = em.createQuery("""
    select c.id, c.name, sum(o.totalAmount)
    from PurchaseOrder o
    join o.customer c
    where o.status = :status
    group by c.id, c.name
    having sum(o.totalAmount) >= :minimum
    order by sum(o.totalAmount) desc
    """, Object[].class)
    .setParameter("status", "PAID")
    .setParameter("minimum", new BigDecimal("1000.00"))
    .getResultList();
```

Câu query sử dụng entity, association, aggregate và group theo cú pháp JPQL thông dụng.

Nếu trả nhiều scalar như `Object[]`, code cần biết thứ tự và kiểu từng phần tử. Với read model rõ ràng, constructor projection thường dễ bảo trì hơn.

## 6. Constructor expression và DTO projection

JPQL chuẩn hỗ trợ constructor expression:

```java
public record ProductSummary(
    Long id,
    String name,
    BigDecimal price
) {}
```

Query:

```java
List<ProductSummary> summaries = em.createQuery("""
    select new com.example.catalog.ProductSummary(
        p.id,
        p.name,
        p.price
    )
    from Product p
    where p.active = true
    order by p.name
    """, ProductSummary.class)
    .getResultList();
```

Các điểm cần nhớ:

- JPQL `select new` dùng tên class fully qualified.
- Kiểu và thứ tự đối số phải phù hợp constructor.
- Kết quả DTO không phải entity managed để dirty checking.
- Projection phù hợp khi chỉ cần vài trường cho danh sách, báo cáo hoặc API.
- EntityGraph không thay thế DTO projection; graph tải entity association, còn projection định nghĩa dữ liệu trả về.

Hibernate cũng hỗ trợ constructor instantiation và có thêm một số dạng dynamic instantiation tùy phiên bản. Khi cần khả năng portable, dùng constructor expression JPQL chuẩn.

## 7. JOIN và JOIN FETCH: cú pháp chuẩn và khác biệt

JPQL hỗ trợ join association:

```sql
select o
from PurchaseOrder o
join o.customer c
where c.active = true
```

Có thể dùng LEFT JOIN:

```sql
select o
from PurchaseOrder o
left join o.customer c
where o.createdAt >= :from
```

Join association dựa trên mapping entity.

### 7.1. ON condition

Jakarta Persistence hỗ trợ điều kiện bổ sung trên join association qua `ON` trong các phiên bản đặc tả có tính năng này (JPA 2.1 trở lên):

```sql
select o
from PurchaseOrder o
left join o.payments p on p.status = 'SETTLED'
```

Điều kiện ON bổ sung điều kiện join; nó không thay thế điều kiện FK/mapping của association.

HQL hỗ trợ cú pháp điều kiện join của Hibernate; các phiên bản Hibernate còn có cú pháp `with` lịch sử như một cách viết điều kiện bổ sung. Với query portable, dùng cú pháp JPQL chuẩn được phiên bản Jakarta Persistence mục tiêu hỗ trợ.

### 7.2. Fetch join trong JPQL

JPQL chuẩn hỗ trợ `JOIN FETCH`:

```sql
select o
from PurchaseOrder o
join fetch o.customer
where o.id = :id
```

Fetch join yêu cầu association được tải cùng query. Một số giới hạn chuẩn cần nhớ:

- Fetch join gắn với association path của root/association đang truy vấn.
- Cú pháp JPQL chuẩn không cung cấp một alias fetch join tự do giống join thông thường.
- Không dùng điều kiện ON tùy ý trên fetch join portable.
- Fetch collection có thể nhân hàng SQL và ảnh hưởng pagination.
- Fetch join không phải DTO projection.

HQL có thể hỗ trợ một số cú pháp mở rộng như alias cho fetch join trong các tình huống nested fetch, nhưng đây là phần cần kiểm tra theo version và không nên đưa vào query cần portability.

### 7.3. Nhiều collection và Cartesian product

Nếu fetch đồng thời `lines`, `payments` và `shipments`, số hàng SQL có thể tăng theo tích số phần tử của từng collection. Hibernate có thể gặp `MultipleBagFetchException` trong trường hợp nhiều bag được fetch cùng lúc.

Dù dùng JPQL fetch join, entity graph hay fetch profile, vẫn phải kiểm soát cardinality. Tách query hoặc DTO projection có thể tốt hơn việc join toàn bộ graph.

## 8. Join giữa các entity không có association

JPQL truyền thống diễn đạt join chủ yếu qua association path đã mapping. Hibernate HQL hỗ trợ thêm một số dạng **entity/root join** giữa entity không có association trực tiếp, với cú pháp và khả năng phụ thuộc phiên bản.

Ví dụ minh họa HQL Hibernate:

```sql
select o, p
from PurchaseOrder o
left join Payment p on p.externalOrderReference = o.externalReference
```

Ở đây `Payment` không nhất thiết được nối qua association mapping `o.payments`; điều kiện join được nêu rõ trong query.

Đây là khả năng hữu ích khi:

- Hai entity có quan hệ logic nhưng mapping chưa khai báo association.
- Cần join theo business key.
- Không muốn tạo association chỉ phục vụ một báo cáo.
- Muốn truy vấn một read model kết hợp nhiều entity.

**Không nên mặc định cú pháp entity join của HQL là JPQL portable**. Nếu ứng dụng phải chạy trên nhiều JPA provider, hãy kiểm tra đúng đặc tả và provider mục tiêu. Có thể dùng native SQL hoặc thiết kế DTO/query khác nếu cần semantics không được JPQL hỗ trợ.

### 8.1. Join không thay thế thiết kế association

Nếu hai entity luôn có quan hệ domain quan trọng và cần điều hướng thường xuyên, mapping association có thể phù hợp hơn. Ngược lại, tạo association chỉ để hỗ trợ một báo cáo đôi khi làm domain model phụ thuộc vào một đường đọc đặc thù.

Chọn giữa association mapping, HQL entity join và native SQL theo semantics domain, portability và nhu cầu query.

## 9. Polymorphism, TYPE và TREAT

JPQL/HQL hỗ trợ truy vấn polymorphic trên entity hierarchy. Khi truy vấn entity base class, kết quả có thể bao gồm các subtype phù hợp.

Ví dụ:

```java
@Entity
@Inheritance(strategy = InheritanceType.SINGLE_TABLE)
public abstract class Payment {
    @Id
    private Long id;
}

@Entity
public class CardPayment extends Payment {
    private String lastFourDigits;
}

@Entity
public class BankTransfer extends Payment {
    private String bankReference;
}
```

Truy vấn:

```sql
select p
from Payment p
```

có thể trả các subtype thuộc hierarchy theo polymorphic query semantics.

### 9.1. TYPE

`TYPE` cho phép kiểm tra kiểu entity thực tế:

```sql
select p
from Payment p
where type(p) = CardPayment
```

Entity type literal dùng entity name tương ứng theo query language, không phải tên bảng.

### 9.2. TREAT

`TREAT` cho phép xem một expression có kiểu base như một subtype trong phạm vi biểu thức:

```sql
select treat(p as CardPayment).lastFourDigits
from Payment p
where type(p) = CardPayment
```

TREAT hữu ích khi chỉ một subtype có thuộc tính cần truy vấn. Cú pháp và hỗ trợ chi tiết phụ thuộc phiên bản Jakarta Persistence/Hibernate, nhưng đây là khả năng đã có trong JPQL hiện đại.

### 9.3. HQL mở rộng biểu thức polymorphic

HQL có thể hỗ trợ các cách xử lý subtype và type expression phong phú hơn tùy phiên bản. Khi query phụ thuộc vào inheritance mapping, hãy kiểm tra SQL được sinh ra với chiến lược `SINGLE_TABLE`, `JOINED` hoặc `TABLE_PER_CLASS`.

Đặc biệt, polymorphic query có thể tạo join nhiều bảng trong chiến lược JOINED; query đúng về cú pháp chưa chắc đã tối ưu.

## 10. Collection expressions và hàm chuẩn

JPQL định nghĩa các biểu thức làm việc với collection association như:

- `IS EMPTY`.
- `MEMBER OF`.
- `SIZE`.
- `KEY`, `VALUE` và `ENTRY` cho map association trong ngữ cảnh phù hợp.
- `INDEX` cho list association có index mapping trong ngữ cảnh phù hợp.

Ví dụ:

```sql
select o
from PurchaseOrder o
where o.lines is not empty
```

Hoặc:

```sql
select o
from PurchaseOrder o
where size(o.lines) >= 2
```

Kiểm tra một phần tử thuộc collection:

```sql
select o
from PurchaseOrder o
where :tag member of o.tags
```

Những biểu thức này làm việc trên mapping collection của entity. Chúng không yêu cầu biết tên join table.

### 10.1. SIZE có thể tạo SQL riêng

`SIZE(o.lines)` là biểu thức ngữ nghĩa collection; Hibernate có thể chuyển thành subquery/count hoặc SQL phù hợp. Không nên giả định nó luôn tải toàn bộ collection vào bộ nhớ Java.

Nếu chỉ cần đếm số phần tử, dùng query aggregate/collection function thường tốt hơn tải tất cả child rồi gọi `size()` trong Java.

## 11. Hàm chuẩn và hàm riêng của Hibernate/database

JPQL cung cấp một tập hàm chuẩn cho chuỗi, số, ngày giờ và collection. Ví dụ:

```sql
select lower(c.email)
from Customer c
where length(c.name) > 3
```

Một số hàm chuẩn quen thuộc gồm:

- `LOWER`, `UPPER`, `LENGTH`.
- `CONCAT`, `SUBSTRING`, `TRIM`, `LOCATE`.
- `ABS`, `MOD`, `SQRT`.
- `CURRENT_DATE`, `CURRENT_TIME`, `CURRENT_TIMESTAMP`.
- `SIZE` cho collection.

Tập hàm chuẩn có thể mở rộng theo phiên bản Jakarta Persistence. Hãy xem đặc tả mà ứng dụng khai báo, không chỉ dựa vào một ví dụ cũ.

### 11.1. FUNCTION để gọi database function

JPQL có cú pháp `FUNCTION` để gọi hàm database/provider:

```sql
select function('my_normalize', c.name)
from Customer c
```

Cú pháp gọi là một phần của JPQL, nhưng **tên hàm và semantics của hàm không tự portable**. Database khác có thể không có `my_normalize` hoặc dùng tên/kiểu đối số khác.

### 11.2. HQL có function registry

Hibernate biết các hàm theo dialect và có thể đăng ký thêm function thông qua cơ chế mở rộng như `FunctionContributor`. Query HQL có thể sử dụng các function được Hibernate nhận diện và kiểm tra kiểu.

Một hàm custom được đăng ký có thể giúp code HQL dễ đọc, nhưng vẫn cần biết database/dialect nào hỗ trợ cách render SQL tương ứng.

### 11.3. HQL function syntax phong phú hơn

HQL hỗ trợ một số hàm và biểu thức hiện đại hơn JPQL baseline, tùy phiên bản và dialect, chẳng hạn biểu thức trích xuất/truncate ngày giờ, format hoặc các hàm aggregate chuyên biệt.

Không nên lấy một hàm thấy trong ví dụ HQL mới rồi giả định mọi JPA provider hoặc mọi Hibernate version đều có. Kiểm tra:

1. Hàm có nằm trong Jakarta Persistence version mục tiêu không?
2. Hibernate version hiện tại có đăng ký function không?
3. Dialect render SQL như mong đợi không?
4. Database đích có hỗ trợ semantics tương ứng không?

## 12. CTE và recursive query trong HQL

Một khả năng đáng chú ý của HQL hiện đại là **Common Table Expression (CTE)** qua mệnh đề `with`. CTE đặt một query có tên ở đầu câu truy vấn, sau đó dùng như một nguồn dữ liệu trong query chính.

Ví dụ minh họa HQL:

```sql
with paidOrders as (
    select o
    from PurchaseOrder o
    where o.status = 'PAID'
)
select p
from paidOrders p
where p.totalAmount > :minimum
```

CTE giúp chia query phức tạp thành các phần có tên, dễ đọc và có thể tái sử dụng trong cùng statement.

### 12.1. Recursive CTE

Với dữ liệu dạng cây như category có parent, recursive CTE có thể duyệt nhiều cấp:

```sql
with recursive categoryTree(id, parentId, depth) as (
    select c.id, c.parent.id, 0
    from Category c
    where c.id = :rootId

    union all

    select child.id, child.parent.id, tree.depth + 1
    from Category child
    join categoryTree tree on child.parent.id = tree.id
)
select tree
from categoryTree tree
```

Đây là **ví dụ khái niệm** để minh họa cấu trúc đệ quy. Cú pháp CTE HQL, cách khai báo cột/alias, khả năng tham chiếu entity và hỗ trợ recursive query đã thay đổi theo phiên bản Hibernate; cần điều chỉnh theo HQL User Guide của version thực tế và database dialect.

### 12.2. CTE có phải JPQL chuẩn không?

Không nên coi CTE HQL là JPQL portable chỉ vì query được gửi qua `EntityManager.createQuery`. Các phiên bản Jakarta Persistence có thể bổ sung cú pháp qua thời gian, nhưng CTE và recursive CTE trong nhiều ứng dụng Jakarta Persistence 3.1/những phiên bản cũ là phần mở rộng Hibernate hoặc phải dùng native SQL.

Hãy kiểm tra chính xác version đặc tả và provider. Nếu query cần chạy trên nhiều provider, CTE native SQL hoặc query nhiều bước có thể là lựa chọn phù hợp hơn.

### 12.3. CTE không tự làm query nhanh hơn

CTE là cách cấu trúc query. Database có thể inline, materialize hoặc tối ưu theo chiến lược riêng. Một CTE phức tạp vẫn có thể chậm; cần xem execution plan, index và số hàng thực tế.

## 13. Window functions trong HQL

Window function tính giá trị trên một cửa sổ hàng liên quan mà không gộp các hàng thành một hàng như GROUP BY.

Ví dụ xếp hạng order theo tổng tiền trong từng customer:

```sql
select
    o.customer.id,
    o.id,
    o.totalAmount,
    row_number() over (
        partition by o.customer.id
        order by o.totalAmount desc
    )
from PurchaseOrder o
```

HQL hiện đại hỗ trợ cú pháp window function trong các phiên bản có tính năng này, và khả năng render còn phụ thuộc database/dialect. Đây là công cụ hữu ích cho:

- Xếp hạng theo nhóm.
- Running total.
- So sánh giá trị hiện tại với hàng trước/sau.
- Chọn top-N theo từng nhóm.
- Tính moving average.

### 13.1. JPQL baseline và window function

JPQL truyền thống không cung cấp đầy đủ cú pháp `over (partition by ... order by ...)` như HQL hiện đại hoặc SQL. Một số phiên bản đặc tả có thể bổ sung khả năng truy vấn mới; cần kiểm tra phiên bản mục tiêu thay vì gắn nhãn “JPQL luôn không hỗ trợ” cho mọi thế hệ.

Nếu ứng dụng cần portability rộng, cân nhắc native SQL hoặc xử lý bằng query portable nhiều bước nếu dữ liệu không quá lớn.

### 13.2. Window function không thay ORDER BY ngoài cùng

`ORDER BY` bên trong `OVER` quyết định thứ tự trong cửa sổ để tính function. Nó không nhất thiết sắp xếp thứ tự hàng cuối cùng trả về. Muốn kết quả có thứ tự, query ngoài cùng vẫn cần `order by`.

## 14. Set operations: UNION, INTERSECT và EXCEPT

HQL hiện đại hỗ trợ các phép hợp tập kết quả như `union`, `intersect` và `except` theo phiên bản.

Ví dụ khái niệm:

```sql
select c.id, c.name
from Customer c
where c.active = true

union

select s.id, s.name
from SupplierContact s
where s.active = true
```

Hai nhánh cần trả cấu trúc kết quả tương thích về số cột và kiểu dữ liệu. Cách Hibernate kiểm tra type và render SQL phụ thuộc phiên bản.

Set operations hữu ích khi dữ liệu đến từ nhiều entity type không có một association chung nhưng cần kết hợp thành một read result.

### 14.1. Phần portable cần xác minh

Không giả định mọi set operator HQL đều thuộc JPQL của phiên bản ứng dụng. Một số đặc tả Jakarta Persistence mới có thể hỗ trợ một phần set operations; nếu cần portable, đối chiếu đúng grammar của đặc tả đang dùng.

### 14.2. UNION và UNION ALL

`UNION` thường loại bỏ duplicate theo semantics SQL; `UNION ALL` giữ tất cả hàng và thường tránh bước loại trùng. Hỗ trợ cú pháp và cách biểu đạt trong HQL cần xem version.

Chọn theo semantics nghiệp vụ, không chỉ theo suy nghĩ “ALL nhanh hơn”. Duplicate có thể là dữ liệu hợp lệ hoặc lỗi tùy use case.

## 15. Derived roots, subquery trong FROM và lateral joins

HQL ở các phiên bản mới có thể hỗ trợ query phức tạp hơn với derived roots hoặc subquery trong `FROM`, và lateral joins trong những trường hợp phù hợp.

Ví dụ SQL khái niệm:

```sql
select recent.customer_id, recent.total
from (
    select o.customer_id, sum(o.total_amount) as total
    from purchase_orders o
    group by o.customer_id
) recent
where recent.total > 1000
```

Trong HQL, derived root thường được mô tả bằng một subquery có alias trong query source theo grammar của phiên bản. Một derived root có thể bị giới hạn về correlated reference; lateral join là công cụ cho một số subquery cần tham chiếu từ nguồn ở bên trái.

Các khả năng này rất hữu ích cho báo cáo, top-N per group hoặc query tổng hợp nhiều tầng, nhưng:

- Không phải JPQL portable baseline.
- Có thể phụ thuộc Hibernate version.
- Có thể phụ thuộc database dialect.
- Dễ tạo query khó tối ưu nếu không xem execution plan.
- Native SQL đôi khi diễn đạt rõ hơn nếu query gắn chặt với tính năng DB.

Đừng dùng cú pháp derived root/lateral chỉ vì nó ngắn hơn; hãy cân nhắc khả năng bảo trì và portability.

## 16. Bulk UPDATE và DELETE: JPQL cũng có, nhưng semantics khác entity update

JPQL chuẩn hỗ trợ bulk update:

```java
int updated = em.createQuery("""
    update Product p
    set p.active = false
    where p.discontinuedAt < :cutoff
    """)
    .setParameter("cutoff", cutoff)
    .executeUpdate();
```

Và bulk delete:

```java
int deleted = em.createQuery("""
    delete from ExpiredToken t
    where t.expiresAt < :now
    """)
    .setParameter("now", now)
    .executeUpdate();
```

Đây không phải thao tác tải từng entity rồi gọi setter/remove. Bulk DML thực hiện trực tiếp trên database.

Hệ quả:

- Entity đang managed có thể giữ state cũ.
- Entity lifecycle callbacks không chạy theo quy trình remove/update từng entity thông thường.
- Cascade và orphan removal không được thực thi như thao tác entity.
- Cần quản lý persistence context, thường flush trước khi bulk DML nếu có pending changes và clear/refresh sau khi phù hợp.
- Bulk update cần chú ý `@Version` vì không tự có cùng semantics optimistic locking như update managed entity.

Hibernate HQL cũng hỗ trợ bulk DML và có thể có một số extension riêng, nhưng các lưu ý về persistence context vẫn quan trọng.

### 16.1. Bulk DML và số hàng bị tác động

`executeUpdate()` trả số hàng bị ảnh hưởng theo semantics provider/database. Với entity dùng inheritance nhiều bảng, số lượng SQL statement/hàng vật lý có thể khác với số entity logic; đừng suy luận đơn giản rằng số trả về luôn là tổng số hàng mọi bảng con.

## 17. INSERT trong HQL và JPQL

JPQL chuẩn tập trung vào SELECT, UPDATE và DELETE; không có cú pháp portable tổng quát kiểu `insert into Entity ...` tương tự SQL.

Hibernate HQL có hỗ trợ một số dạng bulk insert, chẳng hạn insert-select trong các phiên bản phù hợp:

```sql
insert into ArchivedOrder (id, status)
select o.id, o.status
from PurchaseOrder o
where o.status = 'CANCELLED'
```

Đây là ví dụ minh họa cú pháp HQL; khả năng, yêu cầu ID và hỗ trợ mapping phụ thuộc Hibernate version. Khi cần portability hoặc kiểm soát chi tiết database, dùng API persist cho entity mới hoặc native SQL có chủ đích.

Đừng nhầm `em.persist(entity)` với câu lệnh insert HQL. `persist` đưa entity vào lifecycle quản lý; Hibernate quyết định SQL khi flush.

## 18. Parameter binding: phần nên dùng nhất quán

JPQL và HQL hỗ trợ named parameters:

```java
List<Product> products = em.createQuery("""
    select p from Product p
    where p.category.id = :categoryId
      and p.price <= :maximum
    """, Product.class)
    .setParameter("categoryId", categoryId)
    .setParameter("maximum", maximumPrice)
    .getResultList();
```

Có thể dùng positional parameters theo cú pháp chuẩn JPA:

```java
List<Product> products = em.createQuery("""
    select p from Product p where p.price >= ?1
    """, Product.class)
    .setParameter(1, minimumPrice)
    .getResultList();
```

Khuyến nghị:

- Ưu tiên named parameters khi query có nhiều điều kiện.
- Không nối chuỗi dữ liệu người dùng vào query.
- Bind giá trị thay vì ghép literal.
- Đảm bảo kiểu parameter tương thích với thuộc tính entity.
- Không kỳ vọng parameter có thể thay thế tên entity, tên thuộc tính, keyword hoặc tên bảng.

Sai:

```java
String hql = "from Product p where p.name = '" + userInput + "'";
```

Đúng:

```java
List<Product> result = em.createQuery("""
    select p from Product p where p.name = :name
    """, Product.class)
    .setParameter("name", userInput)
    .getResultList();
```

Bind parameter giúp chống query injection qua giá trị và hỗ trợ database/provider xử lý kiểu dữ liệu đúng. Nó không cho phép bind tên cột hoặc keyword động; phần cấu trúc động cần whitelist.

## 19. Pagination và locking qua API JPA

Một điểm hay là nhiều tính năng không cần extension HQL vì đã được cung cấp qua API JPA.

Pagination:

```java
List<Product> page = em.createQuery("""
    select p from Product p order by p.name
    """, Product.class)
    .setFirstResult(0)
    .setMaxResults(20)
    .getResultList();
```

Pessimistic lock:

```java
Product product = em.find(
    Product.class,
    productId,
    LockModeType.PESSIMISTIC_WRITE
);
```

Hoặc query lock mode:

```java
List<Product> products = em.createQuery("""
    select p from Product p where p.category.id = :id
    """, Product.class)
    .setParameter("id", categoryId)
    .setLockMode(LockModeType.PESSIMISTIC_READ)
    .getResultList();
```

Các API này portable ở mức Jakarta Persistence tương ứng, nhưng SQL lock cụ thể, timeout, skip-locked và semantics database có thể khác. Không cần dùng HQL extension chỉ để phân trang hoặc thiết lập lock mode cơ bản.

## 20. Strict JPQL compliance trong Hibernate

Hibernate có thể cung cấp chế độ tuân thủ query nghiêm ngặt thông qua cấu hình compliance tương ứng, thường được biết đến với property:

```properties
hibernate.jpa.compliance.query=true
```

Khi bật, Hibernate có thể từ chối các cú pháp HQL extension không thuộc JPQL theo chính sách của phiên bản.

Mục tiêu là giúp phát hiện query đang phụ thuộc vào Hibernate-specific syntax. Tuy nhiên:

- Tên property và hành vi chi tiết phải kiểm tra tài liệu Hibernate version đang dùng.
- Chế độ compliance không thay thế kiểm thử trên JPA provider khác.
- Một query có thể portable về grammar nhưng vẫn phụ thuộc mapping, function hoặc kiểu dữ liệu của provider/database.
- Không bật cấu hình trong production một cách đột ngột nếu codebase đang có nhiều HQL extension chưa được kiểm kê.

Một chiến lược tốt là dùng strict compliance trong test/CI hoặc một profile kiểm tra tương thích, nếu version và kiến trúc ứng dụng cho phép.

## 21. Spring Data JPA: @Query đang dùng JPQL hay HQL?

Ví dụ:

```java
public interface ProductRepository
        extends JpaRepository<Product, Long> {

    @Query("""
        select p from Product p
        where p.active = true
        order by p.name
        """)
    List<Product> findActiveProducts();
}
```

`@Query` của Spring Data JPA mặc định là query JPQL thông qua JPA provider. Khi provider là Hibernate, parser Hibernate có thể chấp nhận HQL extension. Nhưng nếu query dùng cú pháp riêng Hibernate, repository method **phụ thuộc Hibernate** dù annotation nằm trong Spring Data JPA.

Native SQL:

```java
@Query(
    value = "select * from products where active = true",
    nativeQuery = true
)
List<Product> findActiveNative();
```

`nativeQuery = true` chuyển sang SQL database thay vì JPQL/HQL.

### 21.1. Khi nào nên dùng JPQL trong repository?

- Dự án muốn giữ provider portability.
- Query CRUD/association thông thường.
- Query dễ biểu đạt bằng JPQL.
- Repository là tầng persistence abstraction dùng chung.

### 21.2. Khi nào chấp nhận HQL extension?

- Ứng dụng đã xác định Hibernate là provider.
- Query cần CTE, window function, set operation hoặc cú pháp Hibernate-specific.
- Chi phí chuyển provider không phải yêu cầu.
- Có test integration với đúng Hibernate version và database dialect.
- Extension được ghi nhận rõ để khi nâng cấp biết cần kiểm tra.

### 21.3. Khi nào nativeQuery phù hợp?

- Cần tính năng database-specific mà HQL không diễn đạt được.
- Dùng CTE/hint/index operator hoặc cú pháp SQL đặc thù DB.
- Query báo cáo phụ thuộc schema vật lý.
- Cần kiểm soát SQL và execution plan chính xác.
- Đã đo và chứng minh SQL ORM không phù hợp sau khi phân tích.

Native query tăng phụ thuộc database/schema, nên hãy giới hạn ở những nơi lợi ích rõ ràng.

## 22. Criteria API và quan hệ với JPQL/HQL

Jakarta Persistence có Criteria API chuẩn để xây dựng query động bằng Java:

```java
CriteriaBuilder cb = em.getCriteriaBuilder();

CriteriaQuery<Product> cq = cb.createQuery(Product.class);
Root<Product> product = cq.from(Product.class);

cq.select(product)
  .where(
      cb.and(
          cb.isTrue(product.get("active")),
          cb.ge(
              product.get("price"),
              minimumPrice
          )
      )
  );

List<Product> result = em.createQuery(cq).getResultList();
```

Criteria API là cách xây dựng query theo metamodel/criteria thay vì ghép chuỗi JPQL. Nó hữu ích khi predicate động và nhiều điều kiện tùy chọn.

Hibernate có thêm extension Criteria riêng ở một số phiên bản, nhưng nếu cần portability hãy dùng API Jakarta Persistence.

### 22.1. Criteria không tự làm query nhanh hơn

Criteria và JPQL thường biểu đạt cùng query semantics. Hiệu năng phụ thuộc SQL sinh ra, index, query plan và dữ liệu, không phải việc query được viết bằng builder hay string.

### 22.2. Criteria cũng có giới hạn chuẩn

Nếu query cần HQL-only CTE/window/derived root mà Criteria API chuẩn không biểu đạt được trong phiên bản đang dùng, có thể chọn HQL hoặc native SQL. Không nên ép một query phức tạp vào Criteria chỉ vì muốn “type-safe” nếu kết quả khó đọc và khó kiểm soát.

## 23. HQL extension có làm query không portable không?

Nếu ứng dụng sử dụng một cú pháp chỉ Hibernate hỗ trợ, query phụ thuộc Hibernate. Nhưng cần phân biệt ba lớp portability:

1. **Ngôn ngữ:** query có nằm trong JPQL grammar của Jakarta Persistence version mục tiêu không?
2. **Provider/mapping:** query có dựa vào Hibernate function, type, mapping hoặc behavior riêng không?
3. **Database/dialect:** function/operator/CTE/window/lock có được DB đích hỗ trợ với cùng semantics không?

Ví dụ:

- JPQL chuẩn dùng `lower(c.name)`: tương đối portable.
- JPQL `function('json_extract', ...)`: cú pháp gọi có chuẩn, nhưng function và semantics phụ thuộc database.
- HQL CTE: phụ thuộc Hibernate version và có thể cả dialect.
- Native SQL dùng `jsonb_path_query`: phụ thuộc PostgreSQL.
- HQL gọi một function Hibernate đã đăng ký: phụ thuộc provider và cấu hình function registry.

Vì vậy, “JPQL” không có nghĩa query chạy giống hệt về hiệu năng hoặc mọi kiểu dữ liệu trên tất cả database. Nó chỉ chuẩn hóa ngôn ngữ/semantics ở mức đặc tả.

## 24. Version discipline: kiểm tra phiên bản trước khi dùng extension

Khả năng HQL thay đổi đáng kể giữa các nhánh Hibernate. Khi viết query có cú pháp nâng cao, hãy xác định:

- Hibernate ORM version thực tế trong dependency tree.
- Jakarta Persistence API version được ứng dụng sử dụng.
- Database dialect và phiên bản database.
- Query chạy qua `EntityManager` hay Hibernate `Session`.
- Spring Data JPA version nếu dùng repository annotation.
- Tính năng có trong HQL User Guide của đúng version hay không.

Ví dụ về nguyên tắc:

| Tính năng | JPQL portable? | HQL |
|---|---|---|
| Entity SELECT/WHERE/JOIN cơ bản | Có | Có |
| Association JOIN FETCH | Có, theo grammar chuẩn | Có và có thể có extension |
| DTO constructor expression | Có | Có |
| Bulk UPDATE/DELETE | Có | Có |
| CTE/recursive CTE | Phụ thuộc phiên bản Jakarta Persistence; không có trong nhiều baseline cũ | Có trong các phiên bản Hibernate hỗ trợ |
| Window function | Không có trong JPQL baseline truyền thống; kiểm tra spec version | Có trong HQL hiện đại theo version/dialect |
| Set operations | Kiểm tra đặc tả mục tiêu; không giả định mọi version | Có theo phiên bản HQL hỗ trợ |
| Derived root/lateral join | Không nên mặc định portable | Có ở các phiên bản Hibernate hỗ trợ |
| Function custom | `FUNCTION` có thể chuẩn hóa cú pháp gọi; semantics vẫn phụ thuộc | Registry/dialect và extension Hibernate |
| Native SQL | Không phải JPQL | Không phải HQL |

Bảng là hướng dẫn định vị tính năng, không thay thế việc kiểm tra đặc tả cụ thể. Đặc tả Jakarta Persistence mới có thể mở rộng grammar so với các phiên bản trước.

## 25. Cách chọn JPQL, HQL hay native SQL

Một cách quyết định thực tế:

### Chọn JPQL khi

- Query có thể biểu đạt rõ bằng entity, association và biểu thức chuẩn.
- Dự án muốn giữ khả năng đổi provider.
- Query nằm trong repository dùng chung.
- Cần cú pháp ổn định và dễ onboarding.
- Không cần tính năng đặc thù của Hibernate hoặc database.

Ví dụ:

```sql
select o
from PurchaseOrder o
join o.customer c
where c.id = :customerId
  and o.status = :status
```

### Chọn HQL khi

- Dự án đã chọn Hibernate làm provider.
- Cần CTE, window function, set operations hoặc extension được Hibernate hỗ trợ.
- Muốn query trên entity model thay vì tự viết SQL vật lý.
- HQL giúp biểu đạt rõ hơn query phức tạp.
- Có test với đúng Hibernate version/dialect.

Ví dụ khái niệm:

```sql
select
    o.customer.id,
    o.id,
    row_number() over (
        partition by o.customer.id
        order by o.createdAt desc
    )
from PurchaseOrder o
```

### Chọn native SQL khi

- Query cần cú pháp/tính năng đặc thù database.
- HQL không hỗ trợ hoặc không render SQL mong muốn.
- Cần hint, operator, recursive query hoặc execution strategy cụ thể.
- Query chủ yếu phục vụ báo cáo/read model theo schema vật lý.
- Đã đo và chứng minh SQL ORM không phù hợp.

Ví dụ PostgreSQL-specific:

```sql
SELECT id, payload
FROM outbox_messages
WHERE published_at IS NULL
ORDER BY created_at
FOR UPDATE SKIP LOCKED
LIMIT 100;
```

Đây là SQL dựa vào khả năng PostgreSQL; không phải JPQL/HQL portable. Cần xử lý transaction/locking và mapping kết quả theo API phù hợp.

### Đừng chọn HQL chỉ vì nó “mạnh hơn”

Một query portable dễ hiểu thường có chi phí bảo trì thấp hơn một extension không thực sự cần. Ngược lại, nếu CTE hoặc window function làm query rõ và hiệu quả hơn đáng kể, không có lý do phải né HQL chỉ để giữ một tính di động mà dự án không yêu cầu.

## 26. Bẫy khi chuyển query từ JPQL sang HQL hoặc ngược lại

### 26.1. Đổi tên bảng thành tên entity nhưng quên thuộc tính

SQL:

```sql
SELECT * FROM purchase_orders WHERE order_status = ?
```

JPQL/HQL phải dùng entity/attribute:

```sql
select o from PurchaseOrder o where o.status = :status
```

### 26.2. Dùng alias fetch join theo cú pháp HQL trong query portable

HQL có thể chấp nhận một số alias fetch join trong nested path; grammar JPQL chuẩn hạn chế hơn. Nếu repository cần portable, viết fetch join theo cú pháp chuẩn hoặc dùng EntityGraph.

### 26.3. Dùng function của dialect rồi gọi là JPQL portable

`FUNCTION('json_extract', ...)` không khiến function JSON tự portable. Cần kiểm tra database function và kiểu trả về.

### 26.4. Giả định CTE/window có ở mọi HQL version

Một query chạy trên Hibernate mới có thể không compile trên Hibernate cũ. Kiểm tra dependency version trong ứng dụng, không dựa vào tài liệu phiên bản khác.

### 26.5. Nhầm HQL với native SQL

HQL dùng entity và thuộc tính; native SQL dùng bảng/cột. Dù cú pháp HQL gần SQL, nó vẫn được phân tích qua mapping Hibernate.

### 26.6. Bulk DML rồi đọc entity managed cũ

Bulk UPDATE/DELETE chạy trực tiếp ở DB; persistence context có thể stale. Flush/clear/refresh đúng thời điểm và hiểu lifecycle semantics.

### 26.7. Dùng positional parameter cũ

Ưu tiên named parameter hoặc vị trí chuẩn `?1`. Tránh cú pháp positional legacy không chuẩn/đã bị loại bỏ trong một số Hibernate version.

### 26.8. Nối chuỗi tên cột do client gửi

Parameter binding không thay thế identifier. Nếu cần sort field động, dùng whitelist map từ API field sang path đã biết, không nối trực tiếp input vào HQL.

## 27. Kiểm thử tính tương thích và tính đúng đắn của query

Một query có thể chạy thành công trên H2 nhưng thất bại hoặc cho semantics khác trên database production. Với query HQL nâng cao, nên kiểm thử trên database/dialect thực tế hoặc test container phù hợp.

Các loại kiểm tra:

1. **Parse/validation:** query có được Hibernate version hiện tại chấp nhận?
2. **Mapping:** entity name, attribute, association và type có đúng?
3. **Dialect:** function/CTE/window/set operation được render đúng?
4. **Semantics:** null, duplicate, ordering, grouping và polymorphism có kết quả đúng?
5. **Performance:** SQL có index phù hợp, không N+1 hoặc Cartesian product?
6. **Transaction:** bulk DML, flush, locking và persistence context có được xử lý đúng?
7. **Portability:** nếu yêu cầu nhiều provider, chạy integration tests với provider mục tiêu, không chỉ bật một property compliance.

### 27.1. Xem SQL Hibernate sinh ra

Bật SQL logging trong môi trường development/test để xác nhận:

- Bảng và cột vật lý.
- Join predicate.
- Kiểu bind parameter.
- Có subquery hoặc secondary select không.
- CTE/window được render theo dialect.
- Số lượng statement và execution plan.

SQL log là bằng chứng về câu lệnh thực tế, nhưng không thay thế `EXPLAIN`/execution plan khi đánh giá hiệu năng.

### 27.2. Test query portable bằng provider khác

Nếu portability là yêu cầu thật, test trên ít nhất một JPA provider khác có cấu hình mapping tương đương. Chỉ chạy trên Hibernate không chứng minh query là JPQL chuẩn, nhất là khi Hibernate chấp nhận HQL extensions.

## 28. Quy ước trong codebase để phân biệt JPQL và HQL

Một dự án có thể đặt quy ước rõ ràng:

- Repository CRUD thông thường ưu tiên JPQL chuẩn.
- HQL extension phải được ghi chú vì phụ thuộc Hibernate và version tối thiểu.
- Native SQL phải được đánh dấu rõ database/dialect mục tiêu.
- Query có CTE/window/set operation có integration test với DB thật.
- Không đặt tên method/query là “JPQL” nếu bên trong dùng HQL-only syntax.
- Không dùng native SQL chỉ vì chưa biết association path JPQL.
- Không dùng HQL extension để thay thế DTO projection khi query chỉ cần vài scalar.
- Khi nâng Hibernate, chạy test parse và integration cho tất cả HQL-specific query.

Ví dụ comment trong repository:

```java
// Hibernate HQL extension: requires the project's supported
// Hibernate version and database window-function support.
@Query("""
    select ...
    """)
List<SomeResult> findRankedResults();
```

Ghi chú như vậy giúp reviewer nhận ra phụ thuộc provider khi nâng cấp hoặc tách module.

## 29. Bài tập phân biệt JPQL, HQL và SQL

### Bài 1: Entity hay table?

```sql
select p from Product p where p.active = true
```

**Nhận định:** Đây là query JPQL cơ bản và cũng được HQL hỗ trợ. `Product` là entity name, `active` là thuộc tính entity.

### Bài 2: Cột vật lý

```sql
select p from Product p where p.is_active = true
```

**Nhận định:** Nếu entity không có thuộc tính `is_active`, query sai. `is_active` có thể là tên cột SQL; JPQL/HQL cần dùng tên thuộc tính Java.

### Bài 3: Constructor projection

```sql
select new com.example.ProductSummary(p.id, p.name)
from Product p
```

**Nhận định:** Constructor expression là khả năng JPQL chuẩn, miễn class/constructor phù hợp.

### Bài 4: Window function

```sql
select p.id,
       row_number() over (order by p.price desc)
from Product p
```

**Nhận định:** Đây là cú pháp HQL hiện đại ở các phiên bản hỗ trợ window functions, không phải JPQL baseline truyền thống. Cần kiểm tra version/dialect; nếu không được hỗ trợ, dùng native SQL hoặc giải pháp khác.

### Bài 5: Native SQL

```sql
select * from products where is_active = true
```

**Nhận định:** Đây là SQL trên bảng/cột vật lý. Không phải JPQL/HQL. Dùng native query API.

### Bài 6: FUNCTION

```sql
select function('my_normalize', p.name)
from Product p
```

**Nhận định:** Cú pháp FUNCTION có thể thuộc JPQL, nhưng function `my_normalize` và semantics của nó phụ thuộc provider/database. Cú pháp portable không đồng nghĩa function portable.

### Bài 7: Entity join không có association

```sql
select o, p
from PurchaseOrder o
left join Payment p on p.externalOrderReference = o.externalReference
```

**Nhận định:** Cần kiểm tra HQL entity-join support của Hibernate version; không mặc định đây là JPQL portable.

## 30. Ghi nhớ

- **JPQL** là ngôn ngữ truy vấn chuẩn của Jakarta Persistence; query viết trên entity name, thuộc tính Java và association.
- **HQL** là ngôn ngữ của Hibernate, hỗ trợ phần lớn JPQL và bổ sung extension theo từng phiên bản.
- Một câu JPQL chuẩn thường chạy được trên Hibernate; một câu HQL extension không nhất thiết chạy trên provider JPA khác.
- Dùng `EntityManager.createQuery` không tự làm query portable; tính portable phụ thuộc grammar và semantics được dùng.
- Entity name có thể được tùy chỉnh bằng `@Entity(name = ...)`; JPQL/HQL không dùng tên bảng/cột vật lý trong truy vấn thông thường.
- JPQL/HQL hỗ trợ SELECT, WHERE, JOIN, GROUP BY, HAVING, ORDER BY, constructor projection và bulk UPDATE/DELETE theo đặc tả/phiên bản.
- JPQL chuẩn có association join và fetch join; HQL có thể mở rộng cú pháp join trong một số phiên bản. Fetch collection vẫn có thể tạo Cartesian product hoặc vấn đề pagination.
- TYPE/TREAT hỗ trợ truy vấn polymorphic trong entity inheritance; SQL sinh ra phụ thuộc chiến lược inheritance.
- Hàm chuẩn JPQL có tính portable hơn; `FUNCTION` chỉ chuẩn hóa cách gọi, không làm function database trở nên portable.
- HQL hiện đại có thể hỗ trợ CTE/recursive CTE, window functions, set operations, derived roots và lateral joins theo version/dialect.
- Bulk DML chạy trực tiếp ở DB và có thể làm persistence context stale; cascade/lifecycle callbacks không chạy như thao tác entity từng hàng.
- Parameter binding bằng named parameters hoặc positional `?1`; không nối dữ liệu người dùng vào query.
- Spring Data JPA `@Query` mặc định là query qua JPA provider; nếu dùng HQL extension thì repository vẫn phụ thuộc Hibernate. `nativeQuery = true` dùng SQL database.
- Criteria API chuẩn phù hợp query động portable; HQL/native có thể cần thiết khi query dùng tính năng ngoài Criteria API.
- Khi dùng extension, kiểm tra Hibernate version, Jakarta Persistence version, dialect, SQL sinh ra và integration tests.
- Chọn JPQL cho portability và query ORM thông thường; HQL cho tính năng Hibernate-specific có chủ đích; native SQL cho tính năng/database semantics cần kiểm soát trực tiếp.

**Kết luận:** JPQL và HQL không phải hai ngôn ngữ hoàn toàn tách biệt: JPQL cung cấp nền tảng chuẩn, còn HQL mở rộng khả năng truy vấn của Hibernate. Hãy dùng phần JPQL chuẩn cho các query thông thường cần portability; dùng HQL extension khi tính năng đó mang lại lợi ích rõ và dự án chấp nhận phụ thuộc Hibernate; chọn native SQL khi cần kiểm soát trực tiếp database. Quyết định tốt không dựa trên ngôn ngữ nào có nhiều cú pháp hơn, mà dựa trên **mức portability cần thiết, khả năng của phiên bản đang chạy, semantics dữ liệu và SQL thực tế được sinh ra**.
