# HQL truy vấn theo thực thể và thuộc tính thay vì tên bảng hoặc cột

## 1. HQL nhìn vào mô hình đối tượng, không nhìn trực tiếp vào schema SQL

Khi làm việc với JDBC, ta thường viết SQL dựa trên tên bảng và tên cột:

~~~sql
SELECT id, full_name, email
FROM customers
WHERE email = 'linh@example.com';
~~~

Trong Hibernate ORM, ứng dụng thường thao tác với entity Java. HQL (Hibernate Query Language) cho phép truy vấn theo cùng mô hình đó. Thay vì chỉ định bảng customers và cột email, HQL sử dụng entity Customer và thuộc tính email:

~~~hql
select c
from Customer c
where c.email = :email
~~~

Hibernate đọc câu HQL, đối chiếu tên entity và thuộc tính với mapping, sau đó tạo SQL phù hợp với database dialect và schema. Vì vậy câu HQL có thể tiếp tục hoạt động khi tên bảng hoặc tên cột vật lý thay đổi, miễn mapping entity vẫn đúng.

Đây là khác biệt quan trọng:

- **Tên trong HQL:** entity name, persistent attribute, association và kiểu dữ liệu trong mô hình Java.
- **Tên trong SQL sinh ra:** table, column, join và cú pháp cụ thể của hệ quản trị cơ sở dữ liệu.

HQL không có nghĩa là truy vấn dữ liệu đang nằm trong bộ nhớ Java. Hibernate vẫn gửi SQL đến database; HQL chỉ mô tả truy vấn ở mức mô hình đối tượng.

### Mục tiêu học tập

Sau bài này, bạn có thể:

1. Phân biệt tên entity, tên bảng, tên thuộc tính Java và tên cột vật lý.
2. Viết HQL dựa trên entity và persistent attributes.
3. Hiểu tác dụng của @Entity(name), @Table(name), @Column(name) và access strategy.
4. Dùng alias, path expression, association join và embedded attribute.
5. Truy vấn entity, scalar, DTO, aggregate và quan hệ kế thừa.
6. Truyền tham số an toàn bằng named/positional parameters.
7. Phân trang và sắp xếp kết quả bằng HQL.
8. Nhận biết giới hạn của bulk update/delete và tác động lên persistence context.
9. Đọc SQL Hibernate sinh ra để kiểm chứng truy vấn.

Ví dụ dùng Java 17+, Jakarta Persistence, Hibernate ORM 6.x, Spring Data JPA và PostgreSQL. HQL là ngôn ngữ của Hibernate; cú pháp mở rộng có thể khác JPQL chuẩn và phụ thuộc phiên bản. Khi ứng dụng cần khả năng di chuyển giữa nhiều JPA provider, nên ưu tiên phần cú pháp JPQL chuẩn.

## 2. Entity name và table name là hai định danh khác nhau

Xét entity:

~~~java
import jakarta.persistence.*;

@Entity(name = "Customer")
@Table(name = "customers")
public class Customer {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "full_name", nullable = false)
    private String fullName;

    @Column(name = "email_address", nullable = false)
    private String email;
}
~~~

Ở đây có bốn tên:

| Khái niệm | Giá trị | Được dùng ở đâu? |
|---|---|---|
| Entity name | Customer | HQL/JPQL |
| Table name | customers | SQL/DDL |
| Persistent attribute | fullName | HQL/JPQL |
| Column name | full_name | SQL/DDL |

Tương tự, thuộc tính Java email được ánh xạ tới cột email_address. HQL viết:

~~~hql
from Customer c
where c.email = :email
~~~

SQL Hibernate có thể sinh ra sẽ tham chiếu bảng/cột vật lý:

~~~sql
SELECT c.id, c.full_name, c.email_address
FROM customers c
WHERE c.email_address = ?;
~~~

Tên alias và chi tiết SQL ở trên chỉ minh họa; Hibernate có thể sinh tên alias, thứ tự cột và cú pháp khác tùy dialect.

### 2.1. Tên entity mặc định

Nếu viết:

~~~java
@Entity
public class PurchaseOrder {
    // ...
}
~~~

entity name mặc định là tên entity class không kèm package: PurchaseOrder. HQL thông thường truy vấn:

~~~hql
from PurchaseOrder o
~~~

Nếu khai báo:

~~~java
@Entity(name = "SalesOrder")
@Table(name = "purchase_orders")
public class PurchaseOrder {
    // ...
}
~~~

thì tên entity trong HQL là SalesOrder:

~~~hql
from SalesOrder o
~~~

Không suy ra entity name từ @Table. Đổi tên bảng trong migration hoặc @Table không bắt buộc phải đổi câu HQL.

### 2.2. @Entity(name), @Table(name), @Column(name)

- **@Entity(name = ...)** đặt tên entity trong persistence model.
- **@Table(name = ...)** chỉ định bảng vật lý (và có thể schema/catalog) mà entity được ánh xạ tới.
- **@Column(name = ...)** chỉ định cột vật lý cho persistent attribute.
- **@JoinColumn(name = ...)** chỉ định cột FK vật lý của association.

Ví dụ:

~~~java
@Entity(name = "PurchaseOrder")
@Table(name = "purchase_orders", schema = "sales")
public class PurchaseOrder {
    @Id
    private Long id;

    @Column(name = "created_at")
    private Instant createdAt;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "customer_id")
    private Customer customer;
}
~~~

HQL vẫn sử dụng:

~~~hql
select o
from PurchaseOrder o
where o.createdAt >= :fromTime
~~~

Không viết purchase_orders, created_at hoặc customer_id trong HQL chỉ vì đó là tên vật lý trong database.

## 3. HQL truy vấn persistent attributes, không truy vấn mọi field Java

HQL chỉ có thể tham chiếu những thuộc tính thuộc persistent model của entity:

~~~java
@Entity
public class Customer {
    @Id
    private Long id;

    private String email;

    @Transient
    private String displayLabel;
}
~~~

id và email được ánh xạ persistence; displayLabel có @Transient nên không phải thuộc tính persistent để truy vấn bằng HQL:

~~~hql
from Customer c
where c.email = :email
~~~

Câu sau không hợp lệ nếu displayLabel thật sự không được map:

~~~hql
from Customer c
where c.displayLabel = :label
~~~

### 3.1. Field access và property access

Jakarta Persistence xác định access strategy theo vị trí annotation định danh như @Id, trừ khi được chỉ định rõ bằng @Access. Ví dụ field access:

~~~java
@Entity
@Access(AccessType.FIELD)
public class Customer {
    @Id
    private Long id;

    @Column(name = "full_name")
    private String fullName;

    public String getDisplayName() {
        return fullName.trim();
    }
}
~~~

Trong trường hợp này, thuộc tính persistent là field fullName. Method getDisplayName() chỉ là method tính toán, không tự trở thành thuộc tính HQL.

Với property access:

~~~java
@Entity
@Access(AccessType.PROPERTY)
public class Customer {
    private Long id;
    private String fullName;

    @Id
    public Long getId() {
        return id;
    }

    @Column(name = "full_name")
    public String getFullName() {
        return fullName;
    }

    public String getDisplayName() {
        return fullName.trim();
    }
}
~~~

Các getter được mapping mới là persistent properties. displayName không có mapping persistence nên không truy vấn được chỉ vì có getter.

**Quy tắc thực hành:** xem mapping/access strategy để biết tên thuộc tính HQL, không chỉ nhìn tên cột trong DDL hoặc mọi method Java.

### 3.2. Naming strategy không đổi tên thuộc tính HQL

Hibernate có thể dùng physical naming strategy để chuyển tên logical table/column sang dạng vật lý, ví dụ purchaseOrders thành purchase_orders. Quy tắc đó ảnh hưởng SQL được sinh ra, không biến HQL thành ngôn ngữ dùng tên cột.

HQL tiếp tục sử dụng tên entity và thuộc tính persistent theo mapping.

## 4. Cấu trúc cơ bản của HQL

Một truy vấn HQL thường có hình dạng:

~~~hql
select <selection>
from <entity> <alias>
where <predicate>
group by <expression>
having <predicate>
order by <expression>
~~~

Không phải câu query nào cũng cần tất cả các mệnh đề. HQL cũng hỗ trợ join, subquery, expression, function và các dạng truy vấn khác.

### 4.1. FROM và alias

~~~hql
from Customer c
~~~

Truy vấn tất cả Customer. Alias c đại diện cho entity trong phần còn lại của query.

Có thể lọc:

~~~hql
from Customer c
where c.active = true
~~~

Và chọn rõ entity:

~~~hql
select c
from Customer c
where c.active = true
~~~

Hibernate HQL cho phép bỏ SELECT trong một số dạng truy vấn entity đơn giản; JPQL chuẩn yêu cầu SELECT trong cú pháp SELECT query. Nếu muốn code tương thích JPA provider, viết đầy đủ select c.

### 4.2. Alias không phải tên bảng

~~~hql
select c.email
from Customer c
~~~

c là alias của entity Customer, không phải alias của bảng customers do lập trình viên khai báo. Hibernate tự tạo alias SQL phù hợp.

Alias giúp câu query rõ ràng:

~~~hql
select o
from PurchaseOrder o
where o.customer.email = :email
~~~

## 5. Truy vấn thuộc tính đơn giản

Giả sử Customer có:

~~~java
private String email;
private String fullName;
private boolean active;
private Instant createdAt;
private BigDecimal creditLimit;
~~~

HQL dùng thuộc tính Java:

~~~hql
from Customer c
where c.active = true
  and c.createdAt >= :fromTime
  and c.creditLimit >= :minimumCredit
order by c.createdAt desc
~~~

Các kiểu tham số nên tương thích với kiểu persistent attribute:

- boolean/Boolean cho active.
- Instant cho createdAt.
- BigDecimal cho creditLimit.
- String cho email/fullName.

Không cần biết cột created_at hay credit_limit có kiểu SQL cụ thể nào nếu mapping đã xác định đúng. Hibernate và JDBC binder chuyển giá trị theo mapping và dialect.

### 5.1. Embedded attributes

Một entity có embedded value:

~~~java
@Embeddable
public class Address {
    private String city;
    private String district;
    private String postalCode;
}

@Entity
public class Customer {
    @Id
    private Long id;

    @Embedded
    private Address address;
}
~~~

HQL có thể điều hướng theo thuộc tính:

~~~hql
select c
from Customer c
where c.address.city = :city
  and c.address.district = :district
~~~

HQL tham chiếu đường dẫn thuộc tính của mô hình object. Nó không cần biết các giá trị address được lưu ở các cột address_city, address_district hay được override bằng @AttributeOverride.

### 5.2. Giá trị null

Dùng:

~~~hql
from Customer c
where c.deletedAt is null
~~~

hoặc:

~~~hql
from Customer c
where c.deletedAt is not null
~~~

Không dùng so sánh = null theo cách SQL/JPQL thông thường. So sánh với NULL tuân theo logic ba giá trị của SQL; dùng IS NULL/IS NOT NULL để biểu đạt rõ.

## 6. Truy vấn theo association và path expression

Entity Order tham chiếu Customer:

~~~java
@Entity
public class PurchaseOrder {
    @Id
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)
    private Customer customer;
}
~~~

Có thể viết:

~~~hql
select o
from PurchaseOrder o
where o.customer.email = :email
~~~

Đây là path expression đi từ PurchaseOrder tới association customer rồi tới thuộc tính email.

Hibernate sẽ tạo join cần thiết để đánh giá đường dẫn. Vì vậy code HQL không phải tên bảng/cột, nhưng vẫn có thể sinh SQL JOIN.

### 6.1. Implicit join

~~~hql
from PurchaseOrder o
where o.customer.email = :email
~~~

Đường dẫn o.customer.email có thể khiến Hibernate tạo implicit join tới Customer. Với path điều hướng qua association to-one, semantics thường tương đương một inner join cho đường dẫn cần giá trị liên quan. Nếu customer có thể null và bạn muốn giữ cả đơn không có customer, cần viết left join rõ ràng.

Implicit join có thể tiện trong query ngắn, nhưng với query nhiều association nên dùng explicit join để thể hiện loại join và alias rõ ràng.

### 6.2. Explicit join

~~~hql
select o
from PurchaseOrder o
join o.customer c
where c.email = :email
~~~

Alias c đại diện cho Customer được nối qua association o.customer.

Có thể chọn LEFT JOIN:

~~~hql
select o
from PurchaseOrder o
left join o.customer c
where c is null
   or c.active = true
~~~

LEFT JOIN giữ các PurchaseOrder không có customer (nếu mapping cho phép) trong kết quả. Tuy nhiên nếu đưa điều kiện c.active = true vào WHERE, những hàng có c NULL sẽ bị loại, làm kết quả gần với inner join cho điều kiện đó.

### 6.3. ON condition

Có thể thêm điều kiện cho join:

~~~hql
select o
from PurchaseOrder o
left join o.payments p on p.status = :status
~~~

Điều kiện ON giới hạn các hàng Payment được nối mà vẫn giữ PurchaseOrder không có Payment phù hợp. Đây là khác biệt quan trọng so với đặt điều kiện p.status trong WHERE, vì WHERE có thể loại parent không có child phù hợp.

Hibernate HQL hỗ trợ các dạng join condition; cú pháp JPQL chuẩn cũng có ON cho association join trong các phiên bản JPA hiện đại. Dùng đúng cú pháp theo provider/API version mà dự án hỗ trợ.

### 6.4. Join qua nhiều cấp

~~~hql
select o
from PurchaseOrder o
join o.customer c
join c.address a
where a.city = :city
~~~

Đường dẫn association phải tồn tại trong persistent model. HQL không cho phép đi qua một tên cột vật lý chỉ vì cột đó có trong bảng.

## 7. Truy vấn collection và JOIN

Một PurchaseOrder có nhiều OrderItem:

~~~java
@OneToMany(mappedBy = "order")
private List<OrderItem> items;
~~~

Muốn tìm đơn có ít nhất một dòng hàng số lượng lớn:

~~~hql
select distinct o
from PurchaseOrder o
join o.items i
where i.quantity >= :minimumQuantity
~~~

Join tạo một row cho mỗi cặp Order/OrderItem phù hợp. Một order có thể xuất hiện nhiều lần ở kết quả quan hệ; DISTINCT yêu cầu kết quả entity gốc không bị lặp theo semantics của query.

### 7.1. Dùng EXISTS nếu chỉ cần kiểm tra có child

Nếu mục tiêu là tìm đơn có ít nhất một item phù hợp, EXISTS có thể diễn đạt rõ hơn:

~~~hql
select o
from PurchaseOrder o
where exists (
    select 1
    from OrderItem i
    where i.order = o
      and i.quantity >= :minimumQuantity
)
~~~

EXISTS không tạo một tập kết quả parent bị nhân bản bởi child. Database có thể thực thi bằng semi-join hoặc plan phù hợp. Không thể khẳng định EXISTS luôn nhanh hơn JOIN trong mọi schema; hãy kiểm tra execution plan.

### 7.2. Đếm phần tử collection

~~~hql
select o.id, size(o.items)
from PurchaseOrder o
where o.status = :status
~~~

size() là biểu thức HQL/JPQL cho số phần tử collection. Hibernate có thể dịch thành correlated subquery hoặc SQL tương đương tùy mapping/dialect. Nếu gọi cho nhiều parent, kiểm tra SQL và plan để tránh chi phí không mong muốn.

### 7.3. Kiểm tra collection rỗng

~~~hql
select o
from PurchaseOrder o
where o.items is empty
~~~

hoặc:

~~~hql
select o
from PurchaseOrder o
where o.items is not empty
~~~

Đây là cách diễn đạt theo collection trong mô hình entity thay vì tự viết tên bảng order_items.

## 8. SELECT entity, scalar và nhiều giá trị

### 8.1. Chọn entity

~~~hql
select c
from Customer c
where c.active = true
~~~

Kết quả là các Customer entity. Trong persistence context hiện tại, Hibernate quản lý các entity được nạp theo identity map; thay đổi thuộc tính managed có thể được dirty checking và flush.

### 8.2. Chọn một thuộc tính

~~~hql
select c.email
from Customer c
where c.active = true
~~~

Kết quả là danh sách String, không phải Customer entity. Projection scalar thường giảm lượng dữ liệu và tránh hydrate entity graph khi chỉ cần một vài giá trị.

### 8.3. Chọn nhiều biểu thức

~~~hql
select c.id, c.email, c.createdAt
from Customer c
where c.active = true
~~~

Kết quả thường là mỗi hàng dạng Object[] nếu dùng untyped query, hoặc tuple/result type thích hợp nếu dùng API hỗ trợ. Cách này tiện nhưng code phụ thuộc vị trí phần tử và dễ sai khi query đổi thứ tự cột.

### 8.4. Constructor projection sang DTO

~~~java
package com.example.shop.dto;

public record CustomerSummary(Long id, String email, String fullName) {}
~~~

~~~hql
select new com.example.shop.dto.CustomerSummary(
    c.id,
    c.email,
    c.fullName
)
from Customer c
where c.active = true
order by c.fullName
~~~

Constructor expression tạo DTO thay vì entity managed. Lớp DTO phải có constructor tương thích với thứ tự và kiểu các biểu thức; record Java có canonical constructor phù hợp.

Ưu điểm:

- Chỉ lấy cột cần dùng.
- Không đưa entity vào persistence context.
- API có thể trả DTO mà không vô tình kích hoạt lazy loading sau transaction.
- Không cần tải collection nếu chỉ hiển thị tổng hợp.

Tên class trong constructor expression là tên Java fully qualified của DTO, khác với entity name trong FROM.

## 9. Named parameter và positional parameter

Nên dùng named parameter để câu query dễ đọc:

~~~hql
select o
from PurchaseOrder o
where o.status = :status
  and o.createdAt >= :fromTime
  and o.totalAmount >= :minimumAmount
~~~

Bind bằng JPA:

~~~java
List<PurchaseOrder> result = entityManager.createQuery("""
    select o
    from PurchaseOrder o
    where o.status = :status
      and o.createdAt >= :fromTime
    """, PurchaseOrder.class)
    .setParameter("status", OrderStatus.CONFIRMED)
    .setParameter("fromTime", fromTime)
    .getResultList();
~~~

Spring Data:

~~~java
@Query("""
    select o from PurchaseOrder o
    where o.status = :status
      and o.createdAt >= :fromTime
    """)
List<PurchaseOrder> findRecent(
    @Param("status") OrderStatus status,
    @Param("fromTime") Instant fromTime
);
~~~

### 9.1. Positional parameter

JPA positional parameter dùng vị trí bắt đầu từ 1:

~~~hql
select c
from Customer c
where c.email = ?1
  and c.active = ?2
~~~

~~~java
query.setParameter(1, email);
query.setParameter(2, true);
~~~

Named parameter thường dễ bảo trì hơn khi query có nhiều điều kiện.

### 9.2. Không nối chuỗi input vào HQL

Không viết:

~~~java
String hql = "from Customer c where c.email = '" + userInput + "'";
~~~

Nối chuỗi input tạo nguy cơ HQL injection và lỗi escaping. Hãy bind:

~~~java
String hql = "from Customer c where c.email = :email";
entityManager.createQuery(hql, Customer.class)
    .setParameter("email", userInput)
    .getResultList();
~~~

Parameter bind được cho **giá trị**, không được dùng để thay tên entity, thuộc tính, keyword hoặc hướng ORDER BY. Nếu cần sort động, ánh xạ lựa chọn từ một danh sách thuộc tính được cho phép sang biểu thức query đã xác định; không ghép trực tiếp chuỗi người dùng.

### 9.3. IN với collection parameter

~~~hql
select o
from PurchaseOrder o
where o.id in :ids
~~~

~~~java
if (ids.isEmpty()) {
    return List.of();
}

return entityManager.createQuery("""
    select o from PurchaseOrder o
    where o.id in :ids
    """, PurchaseOrder.class)
    .setParameter("ids", ids)
    .getResultList();
~~~

Collection parameter giúp bind một tập giá trị. Hãy xử lý tập rỗng ở application layer để tránh phụ thuộc vào cách provider/dialect mở rộng IN rỗng. Với tập rất lớn, cần chia batch hoặc dùng bảng tạm/array/table-valued mechanism phù hợp database; một câu IN hàng chục nghìn ID có thể vượt giới hạn bind parameter hoặc làm query kém hiệu quả.

## 10. Điều kiện WHERE và biểu thức HQL

HQL hỗ trợ các biểu thức so sánh quen thuộc:

~~~hql
from Product p
where p.price >= :minimumPrice
  and p.active = true
  and p.sku like :pattern
~~~

Các toán tử thường dùng:

| Nhóm | Biểu thức |
|---|---|
| So sánh | =, <>, <, <=, >, >= |
| Logic | AND, OR, NOT |
| Tập giá trị | IN, NOT IN |
| Khoảng | BETWEEN ... AND ... |
| Chuỗi | LIKE, NOT LIKE |
| Null | IS NULL, IS NOT NULL |
| Collection | IS EMPTY, MEMBER OF |
| Kiểu | TYPE, TREAT trong ngữ cảnh phù hợp |

### 10.1. LIKE và wildcard

~~~hql
from Customer c
where lower(c.email) like lower(:pattern)
~~~

Bind pattern như %example.com. Nếu input người dùng chứa % hoặc _ mà nghiệp vụ coi đó là ký tự thường, cần escape theo cú pháp LIKE phù hợp và khai báo ESCAPE rõ ràng.

### 10.2. BETWEEN

~~~hql
from PurchaseOrder o
where o.createdAt between :start and :end
~~~

BETWEEN thường bao gồm cả hai đầu mút. Với khoảng thời gian theo ngày, hãy xác định timezone và cách tạo end boundary; nhiều hệ thống thích khoảng nửa mở [start, nextDay) để tránh sai số độ chính xác timestamp.

### 10.3. CASE

~~~hql
select
    case
        when o.status = :paid then 'PAID'
        when o.status = :cancelled then 'CANCELLED'
        else 'OTHER'
    end
from PurchaseOrder o
~~~

CASE cho phép tạo giá trị có điều kiện trong projection hoặc predicate. Các nhánh cần có kiểu kết quả tương thích.

### 10.4. COALESCE và NULLIF

~~~hql
select coalesce(c.displayName, c.email)
from Customer c
~~~

COALESCE trả biểu thức đầu tiên khác null. NULLIF(a, b) trả null nếu hai giá trị bằng nhau, nếu không trả a. Các function chuẩn giúp xử lý null mà không cần viết native SQL cho trường hợp thông thường.

## 11. Function và kiểu dữ liệu

Một số function thường gặp:

~~~hql
select lower(c.email), upper(c.fullName), length(c.fullName)
from Customer c
~~~

~~~hql
select concat(c.firstName, ' ', c.lastName)
from Customer c
~~~

~~~hql
select current_date
from Customer c
~~~

Các function phổ biến khác gồm abs, sqrt, mod, coalesce, nullif, substring, trim, locate, extract và các function thời gian tùy HQL/JPQL version.

### 11.1. Function phụ thuộc database

Nếu database có function riêng, Hibernate HQL có thể gọi function được đăng ký trong dialect/function registry. Cú pháp:

~~~hql
select function('jsonb_extract_path_text', e.payload, 'kind')
from OutboxEvent e
~~~

function() là cách gọi function database trong các query language/provider hỗ trợ. Tên function và kiểu trả về cần được hỗ trợ bởi dialect hoặc được đăng ký phù hợp; đây không phải cam kết portable giữa mọi database.

Nếu query phụ thuộc nhiều vào JSONB, full-text search hoặc cú pháp đặc thù, native SQL có thể rõ ràng hơn. Không cố ép mọi tính năng database vào HQL chỉ vì ứng dụng đang dùng Hibernate.

### 11.2. So sánh enum

Với:

~~~java
@Enumerated(EnumType.STRING)
private OrderStatus status;
~~~

HQL:

~~~hql
from PurchaseOrder o
where o.status = :status
~~~

Bind trực tiếp enum:

~~~java
.setParameter("status", OrderStatus.PAID)
~~~

Không cần nối chuỗi tên enum vào query. Mapping enum quyết định cách Hibernate lưu/đọc giá trị ở DB.

### 11.3. So sánh ngày giờ

~~~hql
from PurchaseOrder o
where o.createdAt >= :fromTime
  and o.createdAt < :toTime
~~~

Bind Java time type phù hợp với mapping. Hãy thống nhất timezone, precision và kiểu SQL (TIMESTAMP/TIMESTAMPTZ) ở schema. HQL tham chiếu thuộc tính createdAt; database thực thi theo kiểu cột vật lý được mapping.

## 12. Aggregate, GROUP BY và HAVING

Tìm số đơn theo trạng thái:

~~~hql
select o.status, count(o)
from PurchaseOrder o
group by o.status
~~~

Tìm trạng thái có ít nhất 100 đơn:

~~~hql
select o.status, count(o)
from PurchaseOrder o
group by o.status
having count(o) >= :minimumCount
~~~

Các aggregate phổ biến:

- COUNT
- COUNT(DISTINCT ...)
- SUM
- AVG
- MIN
- MAX

### 12.1. Tổng tiền theo khách

~~~hql
select c.id, c.email, count(o), sum(o.totalAmount)
from Customer c
join c.orders o
group by c.id, c.email
having count(o) > 0
order by sum(o.totalAmount) desc
~~~

Query dùng association c.orders, không dùng tên bảng purchase_orders hay customer_id. Các biểu thức không aggregate trong SELECT cần được xử lý theo quy tắc GROUP BY của query language/provider và database.

### 12.2. Đếm entity và đếm collection row

~~~hql
select count(o)
from PurchaseOrder o
~~~

đếm số entity gốc. Trong query có join collection:

~~~hql
select count(o)
from PurchaseOrder o
join o.items i
~~~

một order có nhiều item có thể làm số đếm bị nhân lên. Nếu muốn đếm đơn khác nhau:

~~~hql
select count(distinct o.id)
from PurchaseOrder o
join o.items i
~~~

Nếu chỉ cần biết đơn có item hay không, EXISTS có thể rõ hơn và tránh duplicate parent rows.

## 13. Subquery trong HQL

HQL hỗ trợ subquery trong các ngữ cảnh được ngôn ngữ cho phép, thường gặp trong WHERE/HAVING.

### 13.1. EXISTS

~~~hql
select c
from Customer c
where exists (
    select o.id
    from PurchaseOrder o
    where o.customer = c
      and o.status = :status
)
~~~

Tìm Customer có ít nhất một đơn ở trạng thái chỉ định.

### 13.2. NOT EXISTS

~~~hql
select c
from Customer c
where not exists (
    select o.id
    from PurchaseOrder o
    where o.customer = c
)
~~~

Tìm Customer chưa có đơn hàng.

### 13.3. Subquery với aggregate

~~~hql
select o
from PurchaseOrder o
where o.totalAmount > (
    select avg(other.totalAmount)
    from PurchaseOrder other
    where other.customer = o.customer
)
~~~

Tìm đơn có tổng tiền cao hơn mức trung bình của các đơn cùng khách. Query này minh họa correlated subquery; chi phí phụ thuộc số lượng dữ liệu, index và optimizer. Với báo cáo lớn, so sánh plan với window function/native query nếu cần.

## 14. Truy vấn polymorphic theo entity hierarchy

Giả sử có kế thừa:

~~~java
@Entity
@Inheritance(strategy = InheritanceType.SINGLE_TABLE)
@DiscriminatorColumn(name = "payment_type")
public abstract class Payment {
    @Id
    private Long id;

    private BigDecimal amount;
}

@Entity
@DiscriminatorValue("CARD")
public class CardPayment extends Payment {
    private String lastFourDigits;
}

@Entity
@DiscriminatorValue("BANK")
public class BankTransferPayment extends Payment {
    private String bankReference;
}
~~~

Query:

~~~hql
select p
from Payment p
~~~

thường là polymorphic: trả về các instance thuộc Payment và các subclass cụ thể được mapping trong hierarchy. Hibernate dùng mapping inheritance/discriminator để dựng đúng Java type.

Không cần truy vấn tên bảng con hoặc discriminator column trực tiếp. Với TABLE_PER_CLASS/JOINED, SQL sinh ra có thể phức tạp hơn (join/union), nhưng HQL vẫn truy vấn entity type.

### 14.1. TYPE()

~~~hql
select p
from Payment p
where type(p) = CardPayment
~~~

TYPE kiểm tra kiểu entity thực tế trong hierarchy. Cú pháp và khả năng biểu diễn subtype phụ thuộc HQL/JPQL version; Hibernate HQL hỗ trợ các biểu thức kiểu phong phú hơn trong một số trường hợp.

### 14.2. TREAT()

~~~hql
select p
from Payment p
where treat(p as CardPayment).lastFourDigits = :digits
~~~

TREAT cho phép downcast một expression sang subtype để truy cập thuộc tính riêng của subclass trong query. Nó hữu ích khi cần lọc hoặc điều hướng thuộc tính không có trên base entity. Hãy kiểm tra mapping inheritance và SQL sinh ra trên dialect đang dùng.

## 15. HQL fetch join và phân biệt với join thông thường

JOIN thông thường:

~~~hql
select o
from PurchaseOrder o
join o.customer c
where c.email = :email
~~~

được dùng để nối dữ liệu phục vụ điều kiện/projection. Association có thể vẫn chưa được khởi tạo theo fetch plan của entity.

FETCH JOIN:

~~~hql
select o
from PurchaseOrder o
join fetch o.customer
where o.id = :id
~~~

yêu cầu Hibernate tải association customer cùng với PurchaseOrder để tránh lazy query riêng sau đó.

### 15.1. Fetch join collection

~~~hql
select o
from PurchaseOrder o
left join fetch o.items
where o.id = :id
~~~

Có thể phù hợp khi lấy chi tiết một đơn có số item vừa phải. Tuy nhiên, collection fetch join làm nhân bản hàng SQL. Khi kết hợp pagination trên root entity, Hibernate có thể phải xử lý pagination trong bộ nhớ; cần tránh query dạng này trên tập dữ liệu lớn.

### 15.2. Fetch nhiều collection

Fetch đồng thời nhiều collection có thể tạo Cartesian multiplication hoặc MultipleBagFetchException nếu nhiều bag được fetch cùng lúc. Nên chia thành nhiều query, dùng batch fetching hoặc DTO projection tùy use case.

### 15.3. Không dùng FETCH chỉ để lọc

Nếu chỉ muốn lọc PurchaseOrder theo thuộc tính Customer, dùng join thường hoặc path expression. FETCH chỉ nên được dùng khi thực sự cần khởi tạo association trong kết quả entity. Fetch plan là quyết định tải dữ liệu, không phải cú pháp thay thế mọi JOIN.

## 16. ORDER BY và phân trang

~~~hql
select o
from PurchaseOrder o
where o.status = :status
order by o.createdAt desc, o.id desc
~~~

Thứ tự có thể dựa trên thuộc tính persistent, không phải tên cột. Thêm khóa duy nhất để tạo thứ tự ổn định khi phân trang.

JPA:

~~~java
TypedQuery<PurchaseOrder> query = entityManager.createQuery("""
    select o
    from PurchaseOrder o
    where o.status = :status
    order by o.createdAt desc, o.id desc
    """, PurchaseOrder.class);

List<PurchaseOrder> page = query
    .setParameter("status", OrderStatus.PAID)
    .setFirstResult(40)
    .setMaxResults(20)
    .getResultList();
~~~

Spring Data:

~~~java
Page<PurchaseOrder> page =
    repository.findByStatus(
        OrderStatus.PAID,
        PageRequest.of(
            2,
            20,
            Sort.by(Sort.Order.desc("createdAt"),
                    Sort.Order.desc("id"))
        )
    );
~~~

Spring Data Sort dùng thuộc tính domain, ở đây là createdAt và id, không phải tên cột created_at. Với HQL query phức tạp, hãy tránh cho phép client truyền tùy ý tên sort field vào query; dùng danh sách thuộc tính cho phép.

### 16.1. OFFSET lớn

Page sâu có thể tốn kém do database phải bỏ qua nhiều hàng. Keyset pagination có thể phù hợp hơn:

~~~hql
select o
from PurchaseOrder o
where o.status = :status
  and (
      o.createdAt < :lastCreatedAt
      or (
          o.createdAt = :lastCreatedAt
          and o.id < :lastId
      )
  )
order by o.createdAt desc, o.id desc
~~~

Bind cursor từ hàng cuối trang trước và giới hạn số kết quả. Đây là query theo thuộc tính entity, còn SQL sẽ dùng cột vật lý tương ứng.

## 17. Bulk UPDATE và DELETE bằng HQL

HQL hỗ trợ DML trên entity:

~~~hql
update Customer c
set c.active = false
where c.lastLoginAt < :cutoff
~~~

~~~hql
delete from PurchaseOrder o
where o.status = :status
  and o.createdAt < :cutoff
~~~

Không viết tên bảng/cột vật lý trong HQL; đó là SQL/native SQL. HQL DML sử dụng entity name và persistent attributes.

### 17.1. Thực thi update

~~~java
int updated = entityManager.createQuery("""
    update Customer c
    set c.active = false
    where c.lastLoginAt < :cutoff
    """)
    .setParameter("cutoff", cutoff)
    .executeUpdate();
~~~

executeUpdate() trả số hàng/entity bị ảnh hưởng theo semantics của provider/query. Bulk DML thường được thực thi trực tiếp ở database, không load từng entity.

### 17.2. Bulk DML bỏ qua entity lifecycle thông thường

Bulk update/delete:

- Không chạy dirty checking cho từng entity.
- Không tự cascade REMOVE theo entity graph như EntityManager.remove().
- Không gọi @PreRemove/@PostRemove cho từng entity bị xóa.
- Có thể để entity đang managed trong persistence context giữ state cũ.
- Không tự động thực hiện mọi quy tắc version/callback giống thao tác entity-managed.

Nếu trong cùng EntityManager đã load Customer, rồi bulk update active=false, object Customer trong memory có thể vẫn có active=true. Một pattern thường dùng khi thích hợp:

~~~java
entityManager.flush();
int updated = entityManager.createQuery("""
    update Customer c
    set c.active = false
    where c.lastLoginAt < :cutoff
    """)
    .setParameter("cutoff", cutoff)
    .executeUpdate();
entityManager.clear();
~~~

Flush đồng bộ thay đổi pending trước bulk DML; clear detach tất cả entity managed sau đó. Clear ảnh hưởng toàn persistence context, không chỉ Customer, nên không gọi máy móc nếu service còn entity khác cần dirty checking.

### 17.3. Xóa entity có liên quan

HQL bulk delete PurchaseOrder không tự xóa OrderItem chỉ vì mapping có cascade REMOVE/orphanRemoval. Nếu FK không có ON DELETE CASCADE, database có thể từ chối xóa parent. Phải:

- Xóa child bằng bulk query trước rồi mới xóa parent trong cùng transaction; hoặc
- Dùng database FK cascade đã được thiết kế/chứng minh phù hợp; hoặc
- Load entity và dùng EntityManager.remove() để đi qua lifecycle ORM.

Chọn theo số lượng dữ liệu, callback/audit requirement và chi phí tải entity.

### 17.4. Bulk update version

Bulk HQL update không đi qua cơ chế dirty checking/version thông thường của từng managed entity. Nếu cần optimistic concurrency, phải thiết kế điều kiện version và thao tác version tường minh phù hợp. Hibernate HQL có một số extension theo version, nhưng không nên giả định mọi bulk query tự bảo vệ bằng @Version như entity update thông thường.

## 18. HQL và JPQL khác nhau thế nào?

JPQL là ngôn ngữ query chuẩn của Jakarta Persistence. HQL là ngôn ngữ của Hibernate, có nền tảng tương tự JPQL nhưng có thêm một số tính năng mở rộng theo Hibernate version.

| Tiêu chí | JPQL | HQL |
|---|---|---|
| Đặc tả | Jakarta Persistence | Hibernate |
| Entity/attribute query | Có | Có |
| Association joins | Có | Có |
| Constructor DTO | Có | Có |
| Named parameters | Có | Có |
| Bulk update/delete | Có | Có |
| Tính năng mở rộng Hibernate | Không portable | Có, tùy version |
| Có thể dùng với JPA provider khác | Thường có nếu query tuân chuẩn | Không bảo đảm |

Ví dụ JPQL chuẩn:

~~~hql
select o
from PurchaseOrder o
where o.status = :status
~~~

HQL có thể hỗ trợ thêm các dạng cú pháp, function, collection operation, CTE/window function hoặc expression tùy phiên bản Hibernate. Không nên sao chép tính năng từ tài liệu Hibernate mới sang ứng dụng Hibernate cũ mà chưa xác nhận version.

### 18.1. Khi nào ưu tiên JPQL subset?

- Ứng dụng có khả năng đổi JPA provider.
- Query cần dễ hiểu với lập trình viên biết Jakarta Persistence.
- Không cần function/cú pháp đặc thù Hibernate.
- Muốn giới hạn phụ thuộc provider trong repository.

### 18.2. Khi nào dùng HQL extension?

- Ứng dụng đã xác định Hibernate là provider.
- Query cần tính năng HQL nâng cao có giá trị rõ ràng.
- Đã kiểm thử trên version/dialect mục tiêu.
- Đội phát triển chấp nhận phụ thuộc Hibernate và có tài liệu cho query.

### 18.3. Khi nào dùng native SQL?

- Cần CTE, recursive query, window function hoặc cú pháp DB đặc thù chưa được HQL version hiện tại hỗ trợ phù hợp.
- Cần hint/index/lock clause cụ thể của database.
- Cần thao tác bulk hoặc reporting có plan tốt hơn khi viết SQL trực tiếp.
- Cần tận dụng tính năng PostgreSQL như JSONB hoặc full-text search chuyên sâu.

Native SQL sử dụng table/column vật lý và không tự động có entity lifecycle semantics. Hãy dùng khi lợi ích đủ rõ, bind parameter an toàn và kiểm thử với schema thật.

## 19. Đặt tên thuộc tính và refactor mapping

Một lợi ích của HQL là tách query khỏi tên vật lý, nhưng nó vẫn phụ thuộc tên entity và persistent attribute.

Giả sử schema đổi:

~~~sql
ALTER TABLE customers RENAME COLUMN email_address TO contact_email;
~~~

Nếu mapping cập nhật:

~~~java
@Column(name = "contact_email")
private String email;
~~~

HQL:

~~~hql
from Customer c
where c.email = :email
~~~

không cần đổi vì persistent attribute vẫn tên email.

Ngược lại, nếu Java attribute đổi từ email sang primaryEmail, HQL cần cập nhật:

~~~hql
from Customer c
where c.primaryEmail = :email
~~~

HQL gắn với mô hình Java nên refactor entity attribute có thể làm query string không còn hợp lệ. Các query string không được compiler kiểm tra đầy đủ như Java method call, vì vậy cần integration tests hoặc kiểm tra query khi ứng dụng khởi động.

### 19.1. Static metamodel và Criteria API

Nếu cần giảm lỗi do tên thuộc tính dạng chuỗi, JPA Criteria API với static metamodel có thể hỗ trợ compile-time navigation:

~~~java
root.get(Customer_.email)
~~~

HQL vẫn phù hợp khi query dễ đọc và được kiểm thử. Với query được xây dựng động từ nhiều filter, Criteria API hoặc query builder có thể dễ bảo trì hơn so với nối chuỗi HQL.

## 20. HQL không thể dùng parameter thay cho tên entity hoặc attribute

Đoạn này không hoạt động theo ý định:

~~~hql
select e from :entityName e
~~~

Parameter là giá trị được bind khi thực thi, không phải một phần của grammar cần được phân tích trước. Tương tự:

~~~hql
select c from Customer c order by c.:sortField
~~~

không phải cách hợp lệ để truyền tên thuộc tính động.

Nếu cần query theo nhiều loại entity, có thể:

- Chọn query cụ thể theo một enum/whitelist ở service.
- Viết method repository riêng cho từng loại.
- Dùng Criteria API để xây path từ metamodel.
- Với dynamic sorting, map tên sort công khai sang một biểu thức thuộc tính được cho phép.

Không ghép trực tiếp tên entity/property do client gửi vào HQL. Dù không phải bind value injection theo cách truyền thống, nó vẫn có thể gây query manipulation hoặc truy cập ngoài phạm vi dự kiến.

## 21. Cách kiểm tra HQL được chuyển thành SQL nào

HQL mô tả mô hình entity; để hiểu chi phí thật cần xem SQL do Hibernate sinh.

### 21.1. Bật log SQL trong development

~~~yaml
spring:
  jpa:
    show-sql: false
    properties:
      hibernate:
        format_sql: true
        generate_statistics: true

logging:
  level:
    org.hibernate.SQL: DEBUG
    org.hibernate.orm.jdbc.bind: TRACE
~~~

org.hibernate.SQL giúp quan sát SQL. org.hibernate.orm.jdbc.bind có thể hiển thị giá trị bind; chỉ bật ở môi trường phù hợp vì dữ liệu có thể chứa email, token hoặc thông tin nhạy cảm.

### 21.2. Đối chiếu HQL với SQL

HQL:

~~~hql
select o
from PurchaseOrder o
join o.customer c
where c.email = :email
  and o.status = :status
order by o.createdAt desc
~~~

SQL minh họa:

~~~sql
SELECT o.id, o.customer_id, o.status, o.created_at, o.total_amount
FROM purchase_orders o
JOIN customers c ON c.id = o.customer_id
WHERE c.email_address = ?
  AND o.status = ?
ORDER BY o.created_at DESC;
~~~

Quan sát:

- HQL dùng PurchaseOrder, customer, email, status, createdAt.
- SQL dùng purchase_orders, customers, customer_id, email_address, created_at.
- Hibernate lấy metadata mapping để tạo join condition và cột vật lý.
- Tham số được bind riêng, không nối vào SQL string.

SQL thật có thể thêm cột discriminator, version, tenant predicate, schema qualifier hoặc join khác do mapping/filter.

### 21.3. Hibernate Statistics

~~~java
SessionFactory sessionFactory =
    entityManagerFactory.unwrap(SessionFactory.class);
Statistics statistics = sessionFactory.getStatistics();

long statementsBefore = statistics.getPrepareStatementCount();
long loadsBefore = statistics.getEntityLoadCount();

// Thực hiện một use case có HQL.

long statementDelta =
    statistics.getPrepareStatementCount() - statementsBefore;
long entityLoadDelta =
    statistics.getEntityLoadCount() - loadsBefore;
~~~

Các counter thuộc SessionFactory và cộng dồn toàn ứng dụng. Phép trừ trước/sau chỉ dễ diễn giải trong test cô lập; chúng không phải số liệu riêng cho một request khi nhiều thread chạy cùng lúc.

### 21.4. EXPLAIN ANALYZE

Lấy SQL thực tế từ log và chạy trên database test/staging:

~~~sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT o.id, o.status
FROM purchase_orders o
JOIN customers c ON c.id = o.customer_id
WHERE c.email_address = 'linh@example.com'
  AND o.status = 'PAID'
ORDER BY o.created_at DESC
LIMIT 20;
~~~

Đọc:

- Scan type và index được dùng.
- Estimated rows so với actual rows.
- Join method và số loops.
- Sort có tốn nhiều memory hoặc spill ra disk không.
- Buffer hit/read và execution time.

Không suy luận HQL tốt hay xấu chỉ từ số ký tự hoặc số JOIN. Hãy đánh giá SQL plan, cardinality, index và dữ liệu thực.

## 22. Các lỗi HQL thường gặp

| Triệu chứng | Nguyên nhân | Cách xử lý |
|---|---|---|
| Could not resolve root entity | Dùng table name thay entity name hoặc entity chưa được mapping | Kiểm tra @Entity(name) và persistence unit |
| Could not resolve attribute | Dùng column name thay persistent attribute hoặc gõ sai tên property | Kiểm tra field/property access và mapping |
| HQL chạy được trước khi đổi @Entity(name), sau đó lỗi | Entity name đã thay đổi | Cập nhật query và test |
| Dùng @Column(name = ...) nhưng HQL vẫn báo không có property | Nhầm tên cột vật lý với tên attribute | Dùng tên Java persistent attribute |
| Truy vấn thuộc tính @Transient | Thuộc tính không được persistence mapping | Query field mapped hoặc dùng projection/application logic |
| Path expression loại mất parent có association null | Implicit/inner join semantics | Viết LEFT JOIN nếu cần giữ parent |
| LEFT JOIN nhưng kết quả vẫn loại parent null | Predicate child đặt trong WHERE | Đặt điều kiện phù hợp ở ON hoặc viết EXISTS |
| Một parent lặp nhiều lần | Join collection tạo nhiều hàng | Dùng DISTINCT khi đúng semantics hoặc EXISTS |
| Count lớn hơn số entity gốc | Count trên join collection | COUNT DISTINCT hoặc EXISTS |
| Query chỉ cần vài cột nhưng load nhiều entity | SELECT entity thay vì projection | Chọn scalar/DTO |
| Collection chưa được khởi tạo như mong muốn | JOIN thường bị hiểu nhầm là FETCH JOIN | Dùng fetch plan phù hợp |
| Pagination xử lý trong memory | Collection fetch join kết hợp limit | Page ID trước rồi fetch collection theo ID |
| Bulk update xong entity trong memory vẫn cũ | Bulk DML không đồng bộ persistence context | Flush/clear hoặc refresh phù hợp |
| Bulk delete vi phạm FK | DML không cascade entity lifecycle | Xóa child trước hoặc thiết kế DB cascade |
| Parameter IN rỗng gây query lỗi/khác dialect | Provider/database xử lý tập rỗng khác nhau | Xử lý rỗng ở application layer |
| Dynamic ORDER BY không hoạt động với parameter | Parameter không thay identifier | Whitelist property hoặc Criteria API |
| Query phụ thuộc function chỉ chạy trên PostgreSQL | Function/dialect-specific | Đăng ký function hoặc dùng native query có chủ đích |

## 23. Bài thực hành tổng hợp

Xây dựng ứng dụng Spring Boot + Hibernate + PostgreSQL với Customer, PurchaseOrder, OrderItem và Product.

### Bài A — Phân biệt tên entity và tên bảng

1. Đặt @Entity(name = "SalesOrder") cho class PurchaseOrder.
2. Đặt @Table(name = "purchase_orders").
3. Map createdAt sang cột created_at.
4. Viết HQL dùng SalesOrder và createdAt.
5. Quan sát SQL dùng purchase_orders và created_at.
6. Đổi tên cột vật lý bằng migration và cập nhật mapping; xác nhận HQL không phải đổi nếu entity attribute giữ nguyên.

### Bài B — Truy vấn thuộc tính và association

1. Tìm Customer theo email.
2. Tìm đơn theo customer.email bằng path expression.
3. Viết explicit JOIN và LEFT JOIN.
4. Tìm đơn chưa có item bằng IS EMPTY hoặc NOT EXISTS.
5. Tìm đơn có ít nhất một item có quantity vượt ngưỡng bằng EXISTS.
6. So sánh SQL và kết quả parent trùng nhau.

### Bài C — Projection và aggregate

1. Truy vấn email scalar.
2. Tạo CustomerSummary DTO bằng constructor expression.
3. Đếm đơn theo status.
4. Tính tổng tiền theo khách với GROUP BY/HAVING.
5. So sánh entity load count và dữ liệu trả về giữa entity query và DTO query.

### Bài D — Parameter và bảo mật

1. Dùng named parameter cho email, status và thời gian.
2. Dùng collection parameter IN với danh sách ID.
3. Xử lý danh sách rỗng.
4. Viết test input chứa dấu nháy để chứng minh parameter binding.
5. Xây dynamic sort bằng whitelist; không nối identifier từ request vào HQL.

### Bài E — Inheritance và bulk DML

1. Tạo Payment hierarchy có CardPayment và BankTransferPayment.
2. Query base entity Payment và quan sát kết quả polymorphic.
3. Dùng TYPE/TREAT để lọc subtype.
4. Chạy bulk update rồi kiểm tra entity managed cũ.
5. Thử bulk delete Order và xác nhận FK/cascade không tự chạy như entity remove.

### Bài F — Fetch plan và SQL

1. So sánh JOIN và JOIN FETCH.
2. Bật SQL logging.
3. Kiểm tra pagination trên collection fetch join.
4. Thay bằng ID-first hoặc DTO projection.
5. Chạy EXPLAIN ANALYZE và ghi nhận actual rows, index, time.

Kết quả cần đạt là có thể nhìn một câu HQL và giải thích **entity/property nào được tham chiếu, association nào tạo join, SQL nào có thể được sinh và dữ liệu nào được hydrate vào persistence context**.

## 24. Quy trình viết một câu HQL rõ ràng

Khi xây query cho một use case:

1. Xác định entity root bằng tên @Entity, không dùng tên bảng.
2. Liệt kê persistent attributes cần lọc/sắp xếp/chọn.
3. Xác định association path và cardinality to-one/to-many.
4. Chọn implicit path hay explicit join; ưu tiên explicit khi query phức tạp.
5. Quyết định cần entity managed, scalar hay DTO projection.
6. Bind mọi giá trị qua named parameters.
7. Nếu có collection, cân nhắc duplicate rows, count và pagination.
8. Với bulk DML, đánh giá lifecycle, FK và persistence context stale.
9. Bật SQL log trong môi trường phù hợp để đối chiếu mapping với SQL.
10. Viết integration test trên database/dialect mục tiêu cho query quan trọng.

## 25. Nguyên tắc ghi nhớ

HQL truy vấn theo mô hình đối tượng mà Hibernate quản lý:

1. **Entity name** lấy từ @Entity(name) hoặc tên class mặc định; nó không phải @Table(name).
2. **Attribute name** là tên thuộc tính persistent theo access strategy; nó không phải @Column(name).
3. **Association path** như o.customer.email biểu diễn quan hệ object; Hibernate tạo join SQL tương ứng.
4. **HQL vẫn chạy trên database:** Hibernate parse HQL, dùng metadata mapping và dialect để sinh SQL.
5. **Named parameter** bind giá trị an toàn; không dùng parameter để thay tên entity/property.
6. **Projection/DTO** giúp lấy đúng dữ liệu cần mà không phải hydrate mọi entity.
7. **Collection join** có thể nhân bản hàng; count, DISTINCT và pagination phải được thiết kế cẩn thận.
8. **Bulk DML** tác động trực tiếp lên DB và bỏ qua nhiều hành vi entity lifecycle; cần đồng bộ persistence context.
9. **JPQL là phần chuẩn hóa; HQL có extension của Hibernate:** xác nhận version và mức độ portable.
10. **SQL log và execution plan** là cách xác nhận câu HQL thật sự hoạt động như mong muốn.

Khi viết HQL, hãy nghĩ bằng tên entity và thuộc tính trong domain model, rồi dùng SQL được Hibernate sinh ra để kiểm chứng cách database thực thi. Sự tách biệt này giúp query bám vào mô hình Java, giảm phụ thuộc tên bảng/cột vật lý và giữ cho mã truy vấn dễ đọc khi schema được ánh xạ qua Hibernate ORM.
