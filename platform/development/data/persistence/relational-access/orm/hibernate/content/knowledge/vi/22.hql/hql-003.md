# SelectionQuery, MutationQuery và các API truy vấn theo phiên bản

## 1. Vì sao cần phân biệt SelectionQuery và MutationQuery?

Hibernate ORM cung cấp nhiều API để tạo và thực thi truy vấn. Khi đọc tài liệu hoặc chuyển mã từ phiên bản cũ sang phiên bản mới, ta có thể gặp các tên:

- `Query`, `TypedQuery` và `NativeQuery`.
- `SelectionQuery` cho truy vấn trả về kết quả đọc.
- `MutationQuery` cho truy vấn thay đổi dữ liệu.
- `Session.createQuery()`, `Session.createSelectionQuery()` và `Session.createMutationQuery()`.
- `EntityManager.createQuery()` và `EntityManager.createNativeQuery()`.

Nếu chỉ nhìn thấy tất cả đều có chữ “query”, rất dễ dùng nhầm API hoặc gọi method không phù hợp. Một câu SELECT cần trả danh sách kết quả; một câu UPDATE/DELETE cần thực thi mutation và trả số lượng bị ảnh hưởng. Hai loại công việc có mục tiêu và contract khác nhau.

**SelectionQuery và MutationQuery là các API chuyên biệt của Hibernate, được giới thiệu trong thế hệ Hibernate 6.** Chúng làm rõ ngay từ lúc tạo query rằng câu HQL được dùng để đọc hay thay đổi dữ liệu. Jakarta Persistence có các interface chuẩn như `Query` và `TypedQuery`, nhưng không định nghĩa hai interface Hibernate-specific này.

Bài học giải thích HQL, JPQL và native SQL; hai loại query; cách tạo query qua Hibernate `Session` và JPA `EntityManager`; parameter binding; lấy kết quả; pagination; streaming; HQL UPDATE/DELETE/INSERT-SELECT; bulk mutation và persistence context; optimistic locking; cùng những thay đổi đáng chú ý từ Hibernate 5 sang Hibernate 6/7.

> Ví dụ dùng Hibernate ORM 6.x theo API chuyên biệt, Jakarta Persistence và một số ví dụ Spring Data/JPA. Hibernate 5.x có API và tên method khác ở một số chỗ; Hibernate 7.x tiếp tục phát triển trên nền API mới. Hãy đối chiếu Javadoc/User Guide đúng minor version mà dự án đang dùng.

## 2. HQL, JPQL và SQL: truy vấn đang nói bằng ngôn ngữ nào?

### 2.1. HQL truy vấn entity model

HQL (Hibernate Query Language) là ngôn ngữ truy vấn hướng đối tượng của Hibernate. Câu lệnh dùng **entity name** và **persistent attributes** trong Java mapping, không phải tên bảng/cột vật lý.

Ví dụ entity:

~~~java
@Entity
@Table(name = "products")
public class Product {
    @Id
    private Long id;

    private String name;
    private BigDecimal price;
    private boolean active;
}
~~~

HQL:

~~~sql
select p
from Product p
where p.active = true
order by p.name
~~~

Ở đây `Product` là entity name; `active` và `name` là thuộc tính Java. SQL được Hibernate sinh ra dựa trên mapping, dialect và cấu hình.

### 2.2. JPQL là ngôn ngữ chuẩn Jakarta Persistence

JPQL có nhiều cú pháp giống HQL và là ngôn ngữ truy vấn được định nghĩa bởi Jakarta Persistence. Khi cần tính portable giữa các JPA provider, ưu tiên cú pháp thuộc JPQL specification.

Hibernate HQL là một superset ở nhiều phiên bản: nó có thể hỗ trợ thêm các tính năng mà JPQL chuẩn chưa định nghĩa. Vì vậy, một câu HQL hợp lệ với Hibernate chưa chắc chạy được trên một provider JPA khác.

### 2.3. Native SQL dùng tên bảng và cột

~~~sql
select p.id, p.name, p.price
from products p
where p.active = true
order by p.name
~~~

Đây là SQL trực tiếp. Nó sử dụng schema thực tế, tên cột và tính năng của database. Native SQL hữu ích cho CTE, window functions, JSON operators, optimizer hints hoặc câu lệnh đặc thù DB, nhưng đổi lại tính portable thấp hơn và ứng dụng phải quan tâm mapping kết quả.

### 2.4. Nhìn nhanh sự khác biệt

| Ngôn ngữ | Đối tượng truy vấn | Tính portable | Ví dụ |
|---|---|---|---|
| JPQL | Entity và persistent attributes | Theo chuẩn Jakarta Persistence | `select p from Product p` |
| HQL | Entity model và các extension Hibernate | Phụ thuộc Hibernate version | `from Product p` |
| Native SQL | Table, column, function của DB | Phụ thuộc database | `select * from products` |

Một câu HQL/JPQL không nhất thiết ánh xạ một entity duy nhất. Nó có thể trả scalar, DTO constructor projection, tuple, aggregate hoặc entity. Loại kết quả được quyết định bởi SELECT clause và kiểu query được tạo.

## 3. Hai loại query theo mục đích

### 3.1. Selection query: đọc và trả kết quả

~~~sql
select p
from Product p
where p.active = true
~~~

Đây là truy vấn đọc. Ứng dụng có thể lấy danh sách Product, một kết quả đơn, scalar hoặc DTO tùy biểu thức SELECT.

Với Hibernate 6, `SelectionQuery<R>` biểu diễn một truy vấn HQL/Criteria dùng để chọn kết quả kiểu `R`. Nó cung cấp các thao tác như lấy danh sách, kết quả đơn, phân trang, bind parameter và cấu hình đọc.

### 3.2. Mutation query: thay đổi dữ liệu

~~~sql
update Product p
set p.active = false
where p.price > :threshold
~~~

Đây là bulk mutation. Nó không trả về danh sách Product đã được sửa; ứng dụng gọi `executeUpdate()` để thực thi và nhận số lượng entity/row bị ảnh hưởng theo contract của provider.

Trong Hibernate 6, `MutationQuery` biểu diễn một HQL mutation statement như UPDATE, DELETE hoặc INSERT-SELECT được hỗ trợ. Nó không có mục đích cung cấp danh sách kết quả SELECT thông thường.

### 3.3. Tại sao tách hai interface?

~~~text
HQL SELECT / Criteria SELECT
          |
          v
  Session.createSelectionQuery(...)
          |
          v
      SelectionQuery<R>
          |
          +-- getResultList()
          +-- getSingleResult()
          +-- setFirstResult()/setMaxResults()
          +-- bind parameters


HQL UPDATE / DELETE / INSERT-SELECT
          |
          v
  Session.createMutationQuery(...)
          |
          v
       MutationQuery
          |
          +-- bind parameters
          +-- executeUpdate()
~~~

Sự phân biệt này giúp người đọc code nhận ra một method đang đọc hay thay đổi dữ liệu ngay tại chỗ tạo query.

## 4. SelectionQuery trong Hibernate 6

### 4.1. Tạo SelectionQuery bằng Session

`Session` là API native của Hibernate:

~~~java
import org.hibernate.Session;
import org.hibernate.query.SelectionQuery;

List<Product> products;

try (Session session = sessionFactory.openSession()) {
    session.beginTransaction();

    SelectionQuery<Product> query = session.createSelectionQuery(
        "select p from Product p where p.active = true order by p.name",
        Product.class
    );

    products = query.getResultList();

    session.getTransaction().commit();
}
~~~

Ở đây:

- `sessionFactory.openSession()` mở một Hibernate Session.
- `createSelectionQuery(hql, Product.class)` tạo selection query có kiểu kết quả Product.
- `getResultList()` trả danh sách kết quả.
- Session/transaction được quản lý trong ví dụ Java SE; với Spring/Jakarta EE, transaction manager có thể quản lý vòng đời này.

Đừng đóng Session trước khi dùng kết quả entity nếu còn cần lazy association. Khi Session đóng, entity references có thể detached và lazy loading chưa khởi tạo có thể không truy cập được.

### 4.2. SelectionQuery trả DTO

~~~java
public record ProductRow(
    Long id,
    String name,
    BigDecimal price
) {}
~~~

~~~java
SelectionQuery<ProductRow> query = session.createSelectionQuery(
    "select new com.example.catalog.ProductRow(p.id, p.name, p.price) " +
    "from Product p where p.active = true",
    ProductRow.class
);

List<ProductRow> rows = query.getResultList();
~~~

DTO constructor projection không trả managed Product entity. Đây là cách phù hợp khi chỉ cần dữ liệu đọc cụ thể. Kiểu component và thứ tự tham số phải khớp constructor.

### 4.3. SelectionQuery trả scalar

~~~java
SelectionQuery<String> query = session.createSelectionQuery(
    "select p.name from Product p where p.active = true",
    String.class
);

List<String> names = query.getResultList();
~~~

Khi chỉ cần một cột, không cần tạo entity hoặc DTO riêng.

### 4.4. SelectionQuery qua Criteria

Hibernate Session có thể tạo selection query từ Criteria query theo API phiên bản tương ứng. Cách xây Criteria vẫn dùng Jakarta Persistence Criteria API:

~~~java
CriteriaBuilder cb = session.getCriteriaBuilder();
CriteriaQuery<Product> criteria = cb.createQuery(Product.class);
Root<Product> root = criteria.from(Product.class);

criteria.select(root)
        .where(cb.isTrue(root.get("active")))
        .orderBy(cb.asc(root.get("name")));

SelectionQuery<Product> query =
    session.createSelectionQuery(criteria);

List<Product> products = query.getResultList();
~~~

Cần đối chiếu method overload với Hibernate minor version đang sử dụng. Nếu không cần API Hibernate-specific, có thể thực thi bằng `EntityManager.createQuery(criteria)` để giữ mã nguồn theo Jakarta Persistence.

## 5. MutationQuery trong Hibernate 6

### 5.1. Tạo MutationQuery cho UPDATE

~~~java
import org.hibernate.query.MutationQuery;

int updated;

try (Session session = sessionFactory.openSession()) {
    session.beginTransaction();

    MutationQuery query = session.createMutationQuery(
        "update Product p " +
        "set p.active = false " +
        "where p.price > :threshold"
    );

    query.setParameter("threshold", new BigDecimal("1000.00"));

    updated = query.executeUpdate();

    session.getTransaction().commit();
}
~~~

`executeUpdate()` thực thi câu mutation. Giá trị trả về cho biết số lượng entity/row bị ảnh hưởng theo provider contract; với inheritance mapping nhiều bảng, không nên luôn đồng nhất con số này với số câu SQL hoặc số row vật lý đã ghi.

### 5.2. Tạo MutationQuery cho DELETE

~~~java
MutationQuery query = session.createMutationQuery(
    "delete from Product p where p.active = false"
);

int deleted = query.executeUpdate();
~~~

Đây là bulk delete theo điều kiện. Nó không tương đương với việc tải từng Product, gọi `session.remove(product)` và để Hibernate thực hiện đầy đủ entity lifecycle cho từng instance.

### 5.3. INSERT-SELECT trong HQL

Hibernate HQL hỗ trợ một số dạng insert-select:

~~~java
MutationQuery query = session.createMutationQuery(
    "insert into ArchivedProduct (id, name, price) " +
    "select p.id, p.name, p.price " +
    "from Product p " +
    "where p.active = false"
);

int inserted = query.executeUpdate();
~~~

Cú pháp và các giới hạn phụ thuộc Hibernate HQL version, entity mapping, identifier strategy và database. INSERT-SELECT này là extension HQL/provider-specific trong các phiên bản liên quan; không giả định nó là cú pháp JPQL portable.

Cũng cần xem schema archive có cho phép giữ nguyên ID hay không, có xung đột primary key không, và các cột bắt buộc khác có được chọn đủ không.

### 5.4. MutationQuery không dùng getResultList()

Một mutation query không có danh sách Product kết quả để đọc:

~~~java
MutationQuery query = session.createMutationQuery(
    "update Product p set p.active = false"
);

int affected = query.executeUpdate();
~~~

Nếu muốn hiển thị những sản phẩm vừa bị tắt, hãy chạy selection query riêng sau mutation trong transaction/context phù hợp, hoặc thiết kế native SQL/DB-specific returning nếu database và API hỗ trợ. Không gọi API đọc kết quả trên MutationQuery như thể nó là SELECT.

## 6. So sánh Hibernate API và JPA API

### 6.1. JPA EntityManager

Jakarta Persistence cung cấp:

~~~java
TypedQuery<Product> query = entityManager.createQuery(
    "select p from Product p where p.active = true",
    Product.class
);

List<Product> products = query.getResultList();
~~~

Với mutation:

~~~java
int updated = entityManager.createQuery(
    "update Product p set p.active = false where p.price > :price"
)
.setParameter("price", new BigDecimal("1000.00"))
.executeUpdate();
~~~

Các interface chuẩn:

- `TypedQuery<T>`: query có kiểu kết quả.
- `Query`: query tổng quát, hỗ trợ cả một số thao tác SELECT và bulk update/delete.
- `EntityManager`: tạo query, native query, Criteria query và quản lý entity.

Jakarta Persistence không định nghĩa `SelectionQuery` và `MutationQuery`. Nếu code chỉ cần API chuẩn, dùng EntityManager/TypedQuery/Query.

### 6.2. Hibernate Session

Hibernate 6 bổ sung các API rõ mục đích:

~~~java
SelectionQuery<Product> selection =
    session.createSelectionQuery(
        "select p from Product p",
        Product.class
    );

MutationQuery mutation =
    session.createMutationQuery(
        "update Product p set p.active = false"
    );
~~~

Các API này gắn với Hibernate và có thể cung cấp thêm các khả năng/cấu hình native ngoài chuẩn JPA.

### 6.3. Dùng Session từ EntityManager

Trong một ứng dụng đã dùng JPA nhưng cần API Hibernate-specific:

~~~java
Session session = entityManager.unwrap(Session.class);

SelectionQuery<Product> query = session.createSelectionQuery(
    "select p from Product p where p.active = true",
    Product.class
);
~~~

`unwrap(Session.class)` yêu cầu EntityManager thực tế được cung cấp bởi Hibernate. Nếu ứng dụng đổi provider sang implementation khác, đoạn code này không còn portable.

Không tạo một Session/EntityManager thứ hai độc lập cho cùng use case chỉ để gọi query nếu mục tiêu là tiếp tục dùng persistence context hiện tại. Unwrap giúp truy cập Session underlying của EntityManager.

### 6.4. Bảng lựa chọn

| Nhu cầu | JPA API | Hibernate 6 API |
|---|---|---|
| SELECT entity/DTO/scalar | `TypedQuery<T>` | `SelectionQuery<T>` |
| Bulk UPDATE/DELETE | `Query.executeUpdate()` | `MutationQuery.executeUpdate()` |
| Native SELECT | `EntityManager.createNativeQuery()` | `Session.createNativeQuery()`/API native phù hợp |
| Portable giữa JPA providers | Có | Không, phụ thuộc Hibernate |
| Hibernate-specific HQL features | Không bảo đảm | Có theo version |
| Criteria query | `EntityManager.createQuery(criteria)` | Session selection API phù hợp |

Dùng API theo mức abstraction của ứng dụng. Repository dùng JPA chuẩn thường không cần unwrap Session cho một câu SELECT đơn giản. Hibernate-specific API có ý nghĩa khi cần HQL extension hoặc muốn contract selection/mutation rõ ràng.

## 7. Parameter binding: không nối chuỗi dữ liệu vào HQL

### 7.1. Named parameters

~~~java
SelectionQuery<Product> query = session.createSelectionQuery(
    "select p from Product p " +
    "where p.active = :active and p.price <= :maxPrice",
    Product.class
);

query.setParameter("active", true);
query.setParameter("maxPrice", new BigDecimal("500.00"));

List<Product> products = query.getResultList();
~~~

Named parameters làm query dễ đọc và tránh ghép dữ liệu đầu vào trực tiếp vào câu HQL.

### 7.2. Positional parameters

~~~java
SelectionQuery<Product> query = session.createSelectionQuery(
    "select p from Product p where p.active = ?1 and p.price <= ?2",
    Product.class
);

query.setParameter(1, true);
query.setParameter(2, new BigDecimal("500.00"));
~~~

JPQL/HQL hiện đại hỗ trợ positional parameter theo cú pháp có chỉ số như ví dụ. Một số dạng positional parameter cũ không đánh số có thể còn gặp trong mã legacy; nên theo cú pháp được version hiện tại hỗ trợ.

### 7.3. Parameter cho collection trong IN

~~~java
SelectionQuery<Product> query = session.createSelectionQuery(
    "select p from Product p where p.id in :ids",
    Product.class
);

query.setParameterList("ids", productIds);
~~~

`setParameterList` là API Hibernate-specific phổ biến trên Query/SelectionQuery của Hibernate. Nếu dùng JPA portable, có thể bind collection bằng `TypedQuery.setParameter` theo contract provider/API.

Khi danh sách rỗng, hãy xử lý riêng ở tầng service hoặc tạo predicate luôn false; hành vi của `IN` với collection rỗng có thể khác theo provider/version. Không xây dựng câu query bằng cách nối chuỗi ID.

### 7.4. Parameter không thể thay thế tên entity, tên cột hay hướng sort

Không thể bind tên thuộc tính như một value parameter:

~~~java
// Không có ý nghĩa như parameter value:
"select p from Product p order by :sortField"
~~~

Parameter biểu diễn **giá trị**, không phải cú pháp query. Nếu client chọn sort field, hãy ánh xạ một danh sách tên thuộc tính được cho phép trong code:

~~~java
String orderBy = switch (requestedSort) {
    case "name" -> "p.name";
    case "price" -> "p.price";
    default -> "p.id";
};

String hql = "select p from Product p order by " + orderBy;
~~~

Chỉ ghép identifier/order expression từ allowlist do ứng dụng kiểm soát; không ghép trực tiếp text từ người dùng vào HQL.

## 8. Lấy kết quả của SelectionQuery

### 8.1. Danh sách

~~~java
List<Product> products = session.createSelectionQuery(
    "select p from Product p order by p.id",
    Product.class
).getResultList();
~~~

Danh sách rỗng khi không có hàng phù hợp.

### 8.2. Một kết quả bắt buộc

~~~java
Product product = session.createSelectionQuery(
    "select p from Product p where p.id = :id",
    Product.class
).setParameter("id", productId)
 .getSingleResult();
~~~

`getSingleResult()` yêu cầu đúng một kết quả. Theo semantics JPA, không có kết quả có thể ném `NoResultException`; nhiều hơn một kết quả có thể ném `NonUniqueResultException`. Với Hibernate API, hãy kiểm tra method cụ thể được dùng và contract của version, ví dụ `getSingleResult()`, `uniqueResult()` hoặc `uniqueResultOptional()`.

### 8.3. Một kết quả có thể không tồn tại

Với Hibernate SelectionQuery, các API như `uniqueResult()`/`uniqueResultOptional()` có thể phù hợp nếu ứng dụng chấp nhận không có hàng. Trong JPA, `getSingleResultOrNull()` có ở các version Jakarta Persistence mới; với version cũ thường dùng `getResultList()` rồi kiểm tra hoặc xử lý `NoResultException`.

Ví dụ JPA portable:

~~~java
List<Product> matches = entityManager.createQuery(
    "select p from Product p where p.sku = :sku",
    Product.class
).setParameter("sku", sku)
 .setMaxResults(2)
 .getResultList();

Product product = matches.isEmpty() ? null : matches.get(0);
~~~

Nếu SKU có unique constraint, kết quả nhiều hơn một là vi phạm schema/invariant và cần phát hiện thay vì âm thầm lấy phần tử đầu. Ví dụ giới hạn 2 giúp nhận ra lỗi duplicate mà không tải toàn bộ kết quả.

### 8.4. Scalar và DTO result

~~~java
SelectionQuery<Long> countQuery = session.createSelectionQuery(
    "select count(p) from Product p where p.active = true",
    Long.class
);

Long count = countQuery.getSingleResult();
~~~

~~~java
SelectionQuery<ProductSummary> summaryQuery = session.createSelectionQuery(
    "select new com.example.ProductSummary(p.id, p.name) " +
    "from Product p",
    ProductSummary.class
);
~~~

Result type phải tương thích với SELECT expression. Với `count`, kiểu kết quả là Long; với DTO constructor expression, constructor phải khớp thứ tự và kiểu tham số.

## 9. Pagination và giới hạn kết quả

### 9.1. setFirstResult và setMaxResults

~~~java
SelectionQuery<Product> query = session.createSelectionQuery(
    "select p from Product p where p.active = true " +
    "order by p.name, p.id",
    Product.class
);

List<Product> page = query
    .setFirstResult(offset)
    .setMaxResults(pageSize)
    .getResultList();
~~~

- `setFirstResult(offset)` xác định vị trí bắt đầu, thường tính từ 0.
- `setMaxResults(pageSize)` giới hạn số kết quả.
- Thứ tự cần ổn định; thêm khóa duy nhất làm tie-breaker nếu sort field có thể trùng.

Với dữ liệu lớn, OFFSET cao có thể tốn kém vì database có thể phải bỏ qua nhiều row trước khi trả page.

### 9.2. Keyset pagination

Nếu duyệt theo ID tăng dần:

~~~java
SelectionQuery<Product> query = session.createSelectionQuery(
    "select p from Product p " +
    "where p.id > :lastId " +
    "order by p.id",
    Product.class
);

List<Product> nextPage = query
    .setParameter("lastId", lastSeenId)
    .setMaxResults(pageSize)
    .getResultList();
~~~

Keyset pagination tránh OFFSET lớn khi có index và predicate phù hợp. Nếu sort theo nhiều cột, điều kiện cursor phải phản ánh đầy đủ thứ tự và tie-breaker. Ví dụ sort theo createdAt rồi id cần predicate thứ tự từ điển phù hợp, không chỉ so sánh createdAt.

Keyset không tự tạo snapshot bất biến: record có thể được thêm/sửa giữa các page. Nếu yêu cầu một tập dữ liệu cố định, cần cutoff/version/snapshot strategy riêng.

### 9.3. Count query là một SelectionQuery khác

~~~java
Long total = session.createSelectionQuery(
    "select count(p) from Product p where p.active = true",
    Long.class
).getSingleResult();
~~~

Không nên giả định việc lấy page tự cung cấp total count. Spring Data `Page` thường cần count query; nếu UI chỉ cần biết còn trang tiếp theo, `Slice` hoặc pageSize + 1 có thể tránh count toàn bộ.

## 10. Stream và scroll cho tập dữ liệu lớn

### 10.1. Stream phải được đóng

~~~java
try (Stream<Product> stream = session.createSelectionQuery(
        "select p from Product p order by p.id",
        Product.class
    ).stream()) {

    stream.forEach(this::process);
}
~~~

Một stream từ Hibernate query có thể sử dụng JDBC resources/cursor tùy provider, driver và cách thực thi. Phải đóng stream để giải phóng tài nguyên. Không giữ stream sau khi Session/transaction đóng.

JPA có `getResultStream()`. Theo contract mặc định của JPA, provider có thể triển khai bằng stream của list; Hibernate có thể cung cấp cơ chế streaming/cursor phù hợp hơn tùy version. **Tên method stream không bảo đảm dữ liệu được đọc từng row mà không materialize toàn bộ.**

### 10.2. Entity stream vẫn có thể làm persistence context phình to

Nếu stream trả Product entities, mỗi entity được nạp có thể trở thành managed trong Session. Duyệt cursor không đồng nghĩa Hibernate tự clear những entity đã đọc.

Với batch đọc rất lớn:
- Cân nhắc DTO/scalar projection để không quản lý entity không cần thiết.
- Nếu cần entity, có thể flush/clear theo chunk khi logic cho phép.
- Cân nhắc fetch size và cursor behavior của JDBC driver.
- Giữ transaction và connection mở trong thời gian hợp lý.
- Đóng stream và Session đúng cách.

### 10.3. ScrollableResults

Hibernate cung cấp API scroll/cursor ở những phiên bản cụ thể, ví dụ các overload `scroll()` với `ScrollMode`. API và generic signature thay đổi giữa Hibernate versions. Khi dùng, đọc Javadoc đúng version để xác định resource lifecycle, forward-only behavior và cách đóng cursor.

Không sao chép code `ScrollableResults` của Hibernate 5 sang Hibernate 6/7 mà không kiểm tra migration guide. Với nhiều batch job, keyset pagination hoặc framework reader có checkpoint có thể đơn giản hơn cursor dài.

## 11. MutationQuery và bulk HQL DML

Bulk mutation là cách thay đổi nhiều row theo một câu HQL mà không tải từng entity rồi gọi setter/remove.

### 11.1. UPDATE nhiều entity

~~~java
MutationQuery query = session.createMutationQuery(
    "update Product p " +
    "set p.price = p.price * :factor " +
    "where p.active = true"
);

query.setParameter("factor", new BigDecimal("1.05"));

int affected = query.executeUpdate();
~~~

DB thực hiện một phép cập nhật set-based. Đây thường là cách hiệu quả hơn khi thao tác là biểu thức đồng nhất trên nhiều row và không cần chạy domain method cho từng entity.

### 11.2. DELETE theo điều kiện

~~~java
int deleted = session.createMutationQuery(
    "delete from Product p where p.active = false"
).executeUpdate();
~~~

Không có entity Product nào được tải chỉ để gọi remove từng instance. Vì vậy bulk delete không có cùng lifecycle/cascade semantics với việc xóa từng managed entity.

### 11.3. INSERT-SELECT

~~~java
int copied = session.createMutationQuery(
    "insert into ArchivedProduct (id, name, price) " +
    "select p.id, p.name, p.price " +
    "from Product p where p.active = false"
).executeUpdate();
~~~

HQL insert-select phụ thuộc Hibernate và có giới hạn mapping/identifier cụ thể. Nếu cần sequence/generated ID hoặc default values, kiểm tra cú pháp và DB behavior của version đang dùng.

### 11.4. MutationQuery cần transaction

Bulk DML phải được thực thi trong transaction phù hợp. Ví dụ Java SE resource-local:

~~~java
try (Session session = sessionFactory.openSession()) {
    Transaction tx = session.beginTransaction();

    try {
        int updated = session.createMutationQuery(
            "update Product p set p.active = false where p.price > :price"
        ).setParameter("price", new BigDecimal("1000.00"))
         .executeUpdate();

        tx.commit();
    } catch (RuntimeException ex) {
        if (tx.isActive()) {
            tx.rollback();
        }
        throw ex;
    }
}
~~~

Với Spring, transaction manager có thể quản lý commit/rollback; không tự gọi `beginTransaction()` trên Session được Spring quản lý nếu không đúng cách tích hợp.

### 11.5. Số lượng trả về không phải danh sách entity đã thay đổi

`executeUpdate()` trả một số nguyên về số lượng entity/row bị ảnh hưởng theo provider. Nó không trả về entity đã cập nhật, không trả DTO mới và không cho biết mọi callback/domain rule đã chạy.

Nếu cần trả dữ liệu sau mutation:
- Chạy selection query sau đó trong transaction/context phù hợp.
- Hoặc dùng native SQL có `RETURNING` nếu DB hỗ trợ và mapping phù hợp.
- Hoặc xử lý từng managed entity khi cần lifecycle/domain behavior.

## 12. Bulk mutation khác entity-by-entity update

Giả sử có một managed Product:

~~~java
Product product = session.find(Product.class, productId);
product.changePrice(new BigDecimal("150.00"));
~~~

Đây là entity-level update: Hibernate theo dõi state và sẽ dirty-check khi flush.

Ngược lại:

~~~java
session.createMutationQuery(
    "update Product p set p.price = 200 where p.id = :id"
).setParameter("id", productId)
 .executeUpdate();
~~~

Đây là bulk update trực tiếp ở database. Persistence context không tự đồng bộ tất cả managed Product instances với kết quả của bulk DML.

### 12.1. Entity managed có thể stale sau bulk update

~~~java
Product product = session.find(Product.class, productId);
// product.price = 150

session.createMutationQuery(
    "update Product p set p.price = 200 where p.id = :id"
).setParameter("id", productId)
 .executeUpdate();

// product.getPrice() có thể vẫn trả 150 trong Java.
~~~

Bulk update đã tác động DB nhưng `product` đang được managed vẫn có thể giữ state cũ.

Sau bulk mutation, có thể:
- Gọi `refresh(product)` nếu cần cập nhật một entity cụ thể và không muốn giữ thay đổi local chưa flush.
- Gọi `clear()` khi có thể detach tất cả managed entities mà không làm mất pending changes cần giữ.
- Đóng context và bắt đầu use case với Session mới.
- Tách bulk DML thành một transaction/use case riêng để boundary rõ.

### 12.2. Cẩn trọng với pending changes trước bulk DML

Nếu context có các entity đã được sửa nhưng chưa flush, thứ tự flush và mutation ảnh hưởng kết quả cuối. Với flush mode AUTO, Hibernate có thể flush trước một số query/mutation theo query space và semantics phù hợp. Tuy nhiên, đừng dựa vào một giả định không kiểm chứng về thứ tự SQL.

Một quy trình rõ ràng có thể là:
1. Flush các thay đổi managed cần được lưu trước mutation.
2. Thực hiện bulk mutation.
3. Clear/refresh/context boundary để tránh state stale.
4. Tiếp tục thao tác trên managed state mới.

Không gọi `clear()` trước flush nếu những thay đổi pending phải được giữ.

### 12.3. Bulk DML bỏ qua cascade và lifecycle callback

Bulk DELETE:

~~~java
session.createMutationQuery(
    "delete from Product p where p.active = false"
).executeUpdate();
~~~

không tương đương:

~~~java
for (Product product : inactiveProducts) {
    session.remove(product);
}
~~~

Bulk DML không đi qua entity lifecycle cho từng object theo cách thao tác remove entity-by-entity. Cascade REMOVE, orphan removal, `@PreRemove`, `@PostRemove`, domain methods và các logic Java không tự được gọi cho mỗi row bị xóa.

Nếu FK constraint ngăn xóa, database vẫn có thể từ chối bulk DELETE. Nếu cần xóa graph và chạy lifecycle, dùng entity operations hoặc một quy trình SQL/DB cascade được thiết kế riêng.

### 12.4. Bulk update và optimistic locking

JPA bulk update/delete không tự áp dụng optimistic locking/version checking trên từng entity như dirty checking entity-by-entity. Nếu mapping có `@Version`, không được mặc định bulk DML tự kiểm tra version và tăng version tương ứng.

Hibernate HQL có extension theo phiên bản, ví dụ cú pháp `update versioned` trong những phiên bản hỗ trợ, để yêu cầu version được cập nhật khi bulk update. Đây là Hibernate-specific; không thay thế mọi kiểm tra version theo từng entity và cần xác nhận đúng cú pháp/version. Nếu nghiệp vụ cần conflict detection theo từng row, cân nhắc query có version predicate, entity-level update hoặc SQL rõ ràng.

## 13. Query cache, read-only và các option trên SelectionQuery

SelectionQuery có thể cung cấp các cấu hình đọc của Hibernate, ngoài parameter và pagination.

Các tùy chọn phổ biến theo version gồm:
- Query timeout.
- Fetch size.
- Read-only result hint cho entity.
- Cacheable/query cache settings.
- Comment hoặc query hints.
- Lock mode.
- Flush mode.
- Scroll/stream behavior.

Ví dụ khái niệm:

~~~java
SelectionQuery<Product> query = session.createSelectionQuery(
    "select p from Product p where p.active = true",
    Product.class
);

query.setReadOnly(true);
query.setFetchSize(100);
query.setTimeout(10);

List<Product> products = query.getResultList();
~~~

Các method và đơn vị timeout phải kiểm tra trong Javadoc của Hibernate version cụ thể. `setReadOnly(true)` là gợi ý Hibernate cho entity result/query và có thể ảnh hưởng dirty checking; nó không phải quyền read-only ở database và không biến entity thành DTO.

### 13.1. Read-only entity query khác DTO projection

Một SelectionQuery trả Product entity với read-only hint vẫn trả entity theo mapping. DTO projection trả object không phải entity. Hai lựa chọn khác nhau:

| Cách đọc | Entity managed? | Dirty checking |
|---|---|---|
| Entity query thông thường | Có | Có |
| Entity query read-only hint | Vẫn là entity, theo semantics Hibernate read-only | Có thể giảm/bỏ theo dõi thay đổi tùy provider |
| DTO constructor projection | Không | Không |
| Scalar projection | Không | Không |

Nếu use case chỉ cần ID, name và price, DTO projection thường diễn đạt mục tiêu tốt hơn việc tải entity rồi đặt read-only.

### 13.2. Query cache không phải persistence context

Query cache (nếu bật) cache kết quả query theo cơ chế Hibernate. First-level cache vẫn là context của Session hiện tại. Không nhầm:
- Query cache hit với một managed entity được refresh.
- Second-level cache với database transaction snapshot.
- Read-only query với isolation level.

Cache policy cần được xem xét riêng, nhất là khi dữ liệu có thể bị cập nhật ngoài Hibernate.

## 14. Native query và API truy vấn theo mục đích

### 14.1. JPA native SELECT

~~~java
List<Object[]> rows = entityManager.createNativeQuery(
    "select id, name, price from products where active = true"
).getResultList();
~~~

Native SELECT có thể trả scalar rows, entity mapping hoặc result mapping. Nếu chỉ cần DTO, dùng `@SqlResultSetMapping`/constructor mapping hoặc Spring Data projection phù hợp.

### 14.2. Hibernate native query

Hibernate Session có native query API. Tùy phiên bản, các method `createNativeQuery()` trả `NativeQuery` với khả năng mapping/type configuration riêng.

~~~java
NativeQuery<Object[]> query = session.createNativeQuery(
    "select id, name from products where active = :active",
    Object[].class
);

query.setParameter("active", true);
List<Object[]> rows = query.getResultList();
~~~

Chữ ký overload có thay đổi giữa các phiên bản; không chép nguyên type parameter/method overload từ Hibernate 5 mà chưa kiểm tra Javadoc Hibernate 6/7.

### 14.3. Native mutation

Nếu cần native SQL UPDATE/DELETE, JPA `Query.executeUpdate()` có thể thực thi:

~~~java
int updated = entityManager.createNativeQuery(
    "update products set active = false where price > :price"
).setParameter("price", new BigDecimal("1000.00"))
 .executeUpdate();
~~~

Hibernate có native query extensions theo version. Nếu sử dụng API riêng để tạo native mutation, hãy xác nhận method và return type trong Javadoc của phiên bản dự án. Dù qua API nào, native DML vẫn có thể làm first-level context stale và bỏ qua entity lifecycle.

## 15. Hibernate 5 và Hibernate 6/7: đọc API theo phiên bản

Đây là phần quan trọng khi nâng cấp dự án hoặc đọc code từ tutorial cũ.

### 15.1. Hibernate 5.x

Trong Hibernate 5, code phổ biến:

~~~java
Query<Product> query = session.createQuery(
    "from Product p where p.active = true",
    Product.class
);

List<Product> products = query.list();
~~~

`org.hibernate.query.Query` là interface trung tâm cho nhiều thao tác query. Các ví dụ cũ thường dùng `list()`, `uniqueResult()`, `executeUpdate()` và `createQuery()`.

Hibernate 5 cũng có TypedQuery chuẩn JPA nếu làm việc qua EntityManager. Một số method Hibernate-specific được dùng rộng rãi trong legacy code.

### 15.2. Hibernate 6.x

Hibernate 6 làm rõ mục đích bằng các interface:
- `org.hibernate.query.SelectionQuery<R>`
- `org.hibernate.query.MutationQuery`

Ví dụ:

~~~java
SelectionQuery<Product> selection = session.createSelectionQuery(
    "from Product p where p.active = true",
    Product.class
);

List<Product> products = selection.getResultList();

MutationQuery mutation = session.createMutationQuery(
    "update Product p set p.active = false where p.price > :price"
);

int affected = mutation
    .setParameter("price", new BigDecimal("1000.00"))
    .executeUpdate();
~~~

Các API `createSelectionQuery()` và `createMutationQuery()` thể hiện rõ loại query. `getResultList()` là cách lấy danh sách theo API selection; `executeUpdate()` là cách thực thi mutation.

### 15.3. Hibernate 7.x

Hibernate 7 tiếp tục API query hiện đại, nhưng các overload, deprecated methods, result handling và extension có thể thay đổi theo minor release. Không nên coi mọi method Hibernate 6 đều còn nguyên trạng ở mọi Hibernate 7 release.

Khi cập nhật dependency:
1. Kiểm tra Hibernate ORM migration guide cho từng major version.
2. Kiểm tra compile error và deprecation warnings.
3. Đối chiếu `Session`, `SelectionQuery`, `MutationQuery`, `Query`, `NativeQuery` Javadoc đúng version.
4. Kiểm tra query HQL có dùng extension không portable không.
5. Chạy integration tests trên DB mục tiêu.
6. Kiểm tra SQL generated, result mapping, flush timing và pagination behavior.

### 15.4. Bảng định hướng migration

| Nhu cầu | Code legacy thường gặp | API rõ mục đích trên Hibernate 6 |
|---|---|---|
| HQL SELECT | `session.createQuery(...).list()` | `session.createSelectionQuery(...).getResultList()` |
| HQL SELECT có kiểu | `Query<T>`/`createQuery(hql, T.class)` | `SelectionQuery<T>` qua selection API |
| HQL UPDATE | `session.createQuery(...).executeUpdate()` | `session.createMutationQuery(...).executeUpdate()` |
| HQL DELETE | `session.createQuery(...).executeUpdate()` | `session.createMutationQuery(...).executeUpdate()` |
| JPA SELECT | `EntityManager.createQuery(..., T.class)` | Vẫn dùng `TypedQuery<T>` nếu muốn portable |
| JPA bulk DML | `EntityManager.createQuery(...).executeUpdate()` | Vẫn dùng `Query.executeUpdate()` |
| Native SQL | `createSQLQuery()` trong legacy code | `createNativeQuery()`/native query API theo version |

`createSQLQuery()` là API cũ của Hibernate và đã được thay thế trong thế hệ Hibernate mới bằng native query API. Không nên sửa hàng loạt bằng thay tên cơ học: cần xác định result mapping, scalar types, entity mapping và parameter binding.

### 15.5. Không trộn javax.persistence và jakarta.persistence

Hibernate 5 thường được dùng với hệ sinh thái `javax.persistence` ở các phiên bản cũ. Hibernate 6 chuyển sang `jakarta.persistence` theo Jakarta EE namespace.

Không thể chỉ đổi Hibernate dependency mà giữ nguyên mọi import và kỳ vọng compile. Khi migration, kiểm tra:
- `javax.persistence.*` sang `jakarta.persistence.*`.
- Phiên bản Spring/Spring Data tương thích.
- JPA provider và API dependency.
- Mapping annotations và converters.
- HQL parsing/semantic changes.
- Native query type/mapping behavior.

## 16. HQL mutation và entity lifecycle: chọn đúng công cụ

### 16.1. Khi nào dùng bulk MutationQuery?

Ví dụ:
- Đóng hàng nghìn sản phẩm hết hạn theo một điều kiện.
- Cập nhật trạng thái đồng loạt theo cutoff.
- Archive dữ liệu cũ.
- Thực hiện phép biến đổi đơn giản có thể diễn đạt bằng SQL set-based.
- Insert-select dữ liệu sang bảng lịch sử theo mapping được hỗ trợ.

Ưu điểm:
- Ít phải materialize entities.
- Giảm vòng lặp Java và round-trip.
- Database tối ưu phép cập nhật tập hợp.
- Phù hợp với thao tác đồng nhất trên nhiều row.

### 16.2. Khi nào cần load entity và xử lý từng instance?

Ví dụ:
- Mỗi Product có domain rule khác nhau.
- Cần kiểm tra trạng thái hiện tại trước khi đổi.
- Cần gọi domain method hoặc validation.
- Cần cascade và orphan removal.
- Cần lifecycle callbacks.
- Cần optimistic locking theo từng entity.
- Cần phát domain event theo từng thay đổi.

~~~java
List<Product> products = session.createSelectionQuery(
    "select p from Product p where p.active = false",
    Product.class
).getResultList();

for (Product product : products) {
    product.reactivate();
}
~~~

Đây là entity-level operation. Tuy nhiên, nếu danh sách rất lớn, cần phân trang hoặc flush/clear theo chunk để giới hạn persistence context. Không tải toàn bộ bảng rồi giữ hàng triệu managed entities.

### 16.3. Không gọi cascade để kỳ vọng bulk mutation lan theo graph

~~~java
session.createMutationQuery(
    "delete from Department d where d.active = false"
).executeUpdate();
~~~

Câu lệnh không có nghĩa Hibernate sẽ lần lượt gọi `remove()` cho mỗi Department và cascade sang Employee. Nếu DB FK không cho xóa, câu lệnh có thể thất bại. Nếu muốn xóa graph, cần thiết kế cascade/entity operation hoặc FK action phù hợp.

## 17. HQL query với association và fetch plan

SelectionQuery có thể trả entity và điều hướng association. Cần hiểu query shape.

### 17.1. Join để lọc không đồng nghĩa fetch association

~~~sql
select p
from Product p
join p.category c
where c.name = :categoryName
~~~

Join được dùng để lọc sản phẩm theo category. Nó không nhất thiết yêu cầu association `p.category` được fetch đầy đủ theo cách `join fetch`.

### 17.2. Join fetch

~~~sql
select p
from Product p
left join fetch p.category
where p.active = true
~~~

`join fetch` yêu cầu fetch association trong entity query, giúp tránh lazy query cho category khi truy cập sau đó. Kết quả vẫn là Product entities được quản lý.

### 17.3. DTO projection

~~~sql
select new com.example.ProductCard(p.id, p.name, c.name)
from Product p
left join p.category c
where p.active = true
~~~

DTO chỉ lấy giá trị cần hiển thị. Nếu không cần domain behavior của Product, đây thường là read model rõ ràng hơn.

### 17.4. Collection fetch và pagination

Join fetch một collection to-many có thể nhân số row. Kết hợp với pagination có thể làm query tốn kém hoặc không cho kết quả page theo entity như mong muốn. Hãy page IDs/DTO của parent trước, rồi tải dữ liệu con cho page đó bằng query thứ hai nếu cần.

## 18. Locking và query options

SelectionQuery có thể cấu hình lock mode theo Hibernate API/version hoặc JPA `Query.setLockMode()` khi dùng EntityManager.

Ví dụ JPA:

~~~java
Account account = entityManager.createQuery(
    "select a from Account a where a.id = :id",
    Account.class
).setParameter("id", accountId)
 .setLockMode(LockModeType.PESSIMISTIC_WRITE)
 .getSingleResult();
~~~

Lock chỉ có ý nghĩa trong transaction và được database thực thi theo dialect. Nó không biến DTO thành managed entity và không tự bảo vệ các row ngoài phạm vi khóa.

MutationQuery không phải cách để lấy lock rồi giữ entity graph. Nếu cần đọc–kiểm tra–ghi dưới lock, selection query với lock trong transaction phù hợp hơn; sau đó thay đổi managed entity và commit.

## 19. Các lỗi thường gặp khi dùng SelectionQuery và MutationQuery

| Hiện tượng | Nguyên nhân có thể | Cách xử lý |
|---|---|---|
| Gọi `getResultList()` trên mutation | Nhầm query thay đổi với query đọc | Dùng `executeUpdate()` |
| Gọi `executeUpdate()` trên SELECT | Dùng sai loại query/contract | Dùng SelectionQuery và lấy result |
| Query không tìm thấy entity | HQL dùng tên table/cột thay vì entity/attribute | Dùng entity name và property path |
| Constructor projection báo lỗi | Constructor/kiểu/thứ tự không khớp | Kiểm tra DTO constructor |
| Kết quả query entity là stale | Persistence context đã có managed instance | Refresh/clear/context mới có chủ đích |
| Bulk update xong entity vẫn cũ | Bulk DML không đồng bộ first-level cache | Refresh/clear/context boundary |
| Bulk delete không chạy cascade | Bulk DML bỏ qua entity lifecycle | Xóa entity-by-entity hoặc DB FK action |
| Bulk update không phát hiện version conflict | Bulk DML không tự version-check như entity update | Thiết kế version predicate/increment hoặc entity operations |
| Query nhiều kết quả nhưng dùng single-result API | Query không đảm bảo duy nhất | Thêm unique predicate/constraint hoặc lấy list |
| Query rỗng ném exception | Dùng getSingleResult khi có thể không có row | Dùng optional/null API hoặc list |
| Pagination trả thứ tự không ổn định | Thiếu ORDER BY hoặc thiếu tie-breaker | Sort theo khóa ổn định |
| Stream giữ connection quá lâu | Không đóng stream hoặc transaction | try-with-resources và scope hợp lý |
| Stream entity làm memory tăng | Entity vẫn được quản lý trong Session | DTO/scalar, chunk, flush/clear |
| Native result cast sai | JDBC/DB trả type khác dự kiến | Khai báo mapping/type rõ |
| HQL hoạt động trên Hibernate nhưng không provider khác | Dùng extension HQL | Dùng JPQL portable hoặc chấp nhận phụ thuộc Hibernate |
| Hibernate 5 code không compile với 6 | Query API, namespace, native query API thay đổi | Migration guide và Javadoc đúng version |
| `@Transactional` không áp dụng như nghĩ | Self-invocation hoặc propagation ngoài | Kiểm tra proxy và transaction boundary |
| MutationQuery không có transaction | Bulk DML chạy ngoài transaction phù hợp | Mở/đảm bảo transaction trước executeUpdate |

## 20. Ví dụ service hoàn chỉnh: đọc SelectionQuery và cập nhật bằng MutationQuery

Ví dụ sau minh họa một service Hibernate-specific sử dụng Session trong transaction. Nó giả định `SessionFactory` được quản lý bởi ứng dụng và các class entity/DTO đã tồn tại.

~~~java
public class ProductQueryService {
    private final SessionFactory sessionFactory;

    public ProductQueryService(SessionFactory sessionFactory) {
        this.sessionFactory = sessionFactory;
    }

    public List<ProductSummary> findActiveProducts(int offset, int limit) {
        try (Session session = sessionFactory.openSession()) {
            SelectionQuery<ProductSummary> query =
                session.createSelectionQuery(
                    "select new com.example.ProductSummary(p.id, p.name, p.price) " +
                    "from Product p " +
                    "where p.active = true " +
                    "order by p.name, p.id",
                    ProductSummary.class
                );

            query.setFirstResult(offset);
            query.setMaxResults(limit);

            return query.getResultList();
        }
    }

    public int deactivateExpensiveProducts(BigDecimal threshold) {
        try (Session session = sessionFactory.openSession()) {
            Transaction tx = session.beginTransaction();

            try {
                MutationQuery query = session.createMutationQuery(
                    "update Product p " +
                    "set p.active = false " +
                    "where p.price > :threshold"
                );

                query.setParameter("threshold", threshold);
                int affected = query.executeUpdate();

                tx.commit();
                return affected;
            } catch (RuntimeException ex) {
                if (tx.isActive()) {
                    tx.rollback();
                }
                throw ex;
            }
        }
    }
}
~~~

Hai method có hai mục đích khác nhau:

- `findActiveProducts` trả DTO đọc, không cần transaction ghi.
- `deactivateExpensiveProducts` chạy bulk mutation trong transaction và trả số lượng bị ảnh hưởng.

Trong ứng dụng Spring, thường inject transaction-scoped EntityManager/Session và để framework quản lý transaction thay vì mở/đóng Session thủ công như Java SE. Không trộn hai mô hình quản lý transaction trong cùng một method.

## 21. Bài tập tự luyện

### Bài 1 — Chọn loại query

~~~sql
select p from Product p where p.active = true
~~~

**Câu hỏi:** dùng SelectionQuery hay MutationQuery?

**Đáp án:** SelectionQuery vì câu lệnh đọc và trả kết quả.

### Bài 2 — Cập nhật nhiều sản phẩm

~~~sql
update Product p set p.active = false where p.price > :price
~~~

**Câu hỏi:** gọi `getResultList()` hay `executeUpdate()`?

**Đáp án:** MutationQuery với `executeUpdate()`.

### Bài 3 — API portable

Ứng dụng phải có khả năng đổi từ Hibernate sang provider JPA khác.

**Câu hỏi:** có nên để toàn bộ repository phụ thuộc `org.hibernate.query.SelectionQuery` không?

**Định hướng:** Không cần thiết cho truy vấn chuẩn. Dùng EntityManager/TypedQuery; chỉ dùng Hibernate-specific API ở nơi thật sự cần extension.

### Bài 4 — DTO projection

Query chọn `p.id`, `p.name`, `p.price` vào ProductSummary.

**Câu hỏi:** DTO có managed trong persistence context không?

**Đáp án:** Không, nếu DTO chỉ chứa scalar/value fields. Nếu DTO component chứa entity, entity component vẫn có thể managed.

### Bài 5 — Query rỗng

Một query theo SKU có thể không tìm thấy sản phẩm.

**Câu hỏi:** dùng `getSingleResult()` có phù hợp không?

**Định hướng:** Chỉ khi absence được xử lý qua exception; nếu không, dùng optional/null/list API phù hợp với version.

### Bài 6 — Parameter binding

Người dùng gửi chuỗi tìm kiếm.

**Câu hỏi:** có nên nối chuỗi vào HQL?

**Đáp án:** Không. Dùng named parameter; chỉ identifier/sort field được ghép từ allowlist.

### Bài 7 — Bulk update và entity stale

Session đã load Product#10. MutationQuery đổi giá DB. Getter của Product#10 vẫn trả giá cũ.

**Câu hỏi:** tại sao?

**Đáp án:** Bulk DML không đồng bộ first-level persistence context. Refresh/clear/context mới có kiểm soát.

### Bài 8 — Cascade trong bulk delete

MutationQuery xóa tất cả Department inactive.

**Câu hỏi:** JPA cascade REMOVE tự xóa Employee liên quan không?

**Đáp án:** Không. Bulk DML bỏ qua entity lifecycle cascade. Phải dùng entity removal hoặc DB FK action theo thiết kế.

### Bài 9 — Version

Entity có `@Version`, sau đó chạy bulk HQL UPDATE.

**Câu hỏi:** có chắc Hibernate kiểm tra version của từng entity như entity-level update không?

**Đáp án:** Không. Bulk mutation cần cơ chế version riêng nếu nghiệp vụ yêu cầu.

### Bài 10 — Hibernate 5 sang 6

Code legacy dùng `session.createQuery(hql, Product.class).list()`.

**Câu hỏi:** có thể thay bằng `createSelectionQuery(...).getResultList()` không?

**Định hướng:** Đây là hướng API rõ mục đích trên Hibernate 6; kiểm tra exact overload/version, result type và các API deprecated trong migration guide.

### Bài 11 — Stream lớn

SelectionQuery stream hàng triệu Product entities, không đóng stream và không clear Session.

**Câu hỏi:** có bảo đảm memory không tăng không?

**Đáp án:** Không. Entity có thể vẫn managed và stream giữ JDBC resource. Dùng DTO/scalar, chunk/cursor đúng cách và đóng stream.

### Bài 12 — Native SQL

Báo cáo cần PostgreSQL window function.

**Câu hỏi:** có nhất thiết viết HQL MutationQuery/SelectionQuery không?

**Đáp án:** Không. Native SQL là lựa chọn hợp lý khi cần tính năng DB-specific, với result mapping và transaction được kiểm soát.

## 22. Ghi nhớ

Trong Hibernate 6+, hãy phân biệt rõ:

- **SelectionQuery**: biểu diễn truy vấn đọc, trả entity, DTO, scalar hoặc kết quả chọn khác.
- **MutationQuery**: biểu diễn HQL mutation như UPDATE, DELETE và INSERT-SELECT được hỗ trợ; thực thi bằng `executeUpdate()`.
- **EntityManager/TypedQuery/Query**: API Jakarta Persistence portable, không có interface Hibernate-specific SelectionQuery/MutationQuery.
- **Session**: API native Hibernate, cho phép dùng HQL extension và các API chuyên biệt theo version.
- **NativeQuery**: truy vấn SQL trực tiếp, cần quản lý tên bảng/cột, mapping và khả năng phụ thuộc database.

Một số quy tắc khi viết code:

1. Dùng SELECT/SelectionQuery khi cần dữ liệu; dùng MutationQuery cho bulk DML.
2. Bind mọi giá trị bằng parameter; không nối dữ liệu đầu vào vào HQL/SQL.
3. Chọn result type rõ: entity, DTO, scalar hoặc tuple.
4. Dùng single-result API chỉ khi điều kiện truy vấn thực sự duy nhất và có cách xử lý absence.
5. Dùng ORDER BY ổn định khi phân trang.
6. Đóng stream/cursor và kiểm soát persistence context khi đọc lớn.
7. Bulk mutation cần transaction và có thể làm managed entities stale.
8. Bulk DML không tự chạy cascade, callback, domain method và optimistic version checking theo từng entity như thao tác entity-by-entity.
9. Đọc migration guide/Javadoc đúng Hibernate major/minor; không áp dụng máy móc code Hibernate 5 cho Hibernate 6/7.
10. Chọn API JPA khi cần portability; dùng API Hibernate khi có lý do cụ thể.
