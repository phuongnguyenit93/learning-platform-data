# Luồng chuyển hướng đăng nhập và xác minh ticket qua kết nối máy chủ

> **Module:** Spring Security – federation · **Chủ đề cha:** Nền tảng CAS. Bài học giải thích luồng Single Sign-On của **Central Authentication Service (CAS)**: trình duyệt được chuyển hướng tới máy chủ CAS để xác thực, nhận một **service ticket (ST)** khi trở lại ứng dụng, và **server ứng dụng** xác minh ST với CAS qua HTTPS trước khi tạo phiên đăng nhập. Trọng tâm là ranh giới tin cậy, tính dùng một lần của ticket, tính chính xác của `service` và cách tích hợp Spring Security.

## 1. Mục tiêu học tập

Sau bài này, bạn có thể:

1. Giải thích vai trò **browser**, **CAS server**, **Service Provider/ứng dụng (service)**, **CAS client** và **Spring Security** trong một lần đăng nhập.
2. Phân biệt **Ticket-Granting Ticket (TGT)**, **ticket-granting cookie (TGC)**, **Service Ticket (ST)**, **Login Ticket (LT)** và **Proxy Ticket (PT)**; biết ticket nào xuất hiện ở URL ứng dụng.
3. Trình bày chính xác luồng: yêu cầu tài nguyên → HTTP 302 đến `/cas/login?service=...` → CAS xác thực → 302 về `service?ticket=ST-...` → ứng dụng gọi `/serviceValidate` server-to-server → tạo local security context/session.
4. Phân biệt kiểm tra ST bằng **máy chủ CAS tin cậy qua HTTPS** với việc chỉ thấy tham số `ticket` do browser gửi.
5. Nắm ý nghĩa `service` **phải khớp với service mà ticket được cấp cho**, ticket **chỉ dùng một lần**, thời gian tồn tại ngắn và failure phải **fail closed**.
6. Đọc XML `cas:serviceResponse` với `cas:authenticationSuccess/cas:user` hoặc `cas:authenticationFailure`, bao gồm namespace CAS thực tế.
7. Phân biệt CAS 1.0 `/validate`, CAS 2.0 `/serviceValidate`, CAS 3.0 `/p3/serviceValidate`, `/proxyValidate` và CAS SAML 1.1 `/samlValidate`; không nhầm với SAML2 Web SSO.
8. Hiểu `CasAuthenticationEntryPoint`, `CasAuthenticationFilter`, `CasAuthenticationProvider`, `ServiceProperties` và `Cas20ServiceTicketValidator` trong Spring Security.
9. Chạy ví dụ Java 17 mô phỏng service-ticket lifecycle có stdout xác định; xem thêm chương trình JDK 17 thực hiện HTTPS validation và parse XML an toàn.
10. Xác định rủi ro open redirect, ticket replay, service mismatch, rò ticket qua URL/log/Referer, TLS lỗi, CAS outage, user mapping và authorization.
11. Lập kế hoạch test đúng/sai ticket, sai service, timeout, CA trust, multi-tenant và local session fixation.

**Đối tượng:** Ứng dụng Java Servlet, Spring Boot/Spring Security dùng **giao thức CAS truyền thống**. CAS server còn có thể hỗ trợ SAML2/OIDC như các giao thức khác. **CAS service ticket không phải SAML2 Assertion hoặc OAuth2 access token.**

## 2. Toàn cảnh: vì sao phải có hai đoạn kết nối?

Ứng dụng Orders Portal cần đăng nhập nhân viên. Thay vì nhận mật khẩu, Portal nhờ CAS server xác thực. Nhưng browser có thể thay mọi query parameter nó gửi tới Portal, nên **ST được đưa về qua browser chưa đủ chứng minh danh tính**.

~~~text
             BROWSER / FRONT CHANNEL              SERVER / BACK CHANNEL

[Browser]   [Orders Portal / CAS client]          [CAS server]
    |                  |                                 |
    | GET /orders      |                                 |
    |----------------->|                                 |
    |    chưa có local Authentication                     |
    |<-- 302 ----------|                                 |
    |    Location: https://cas.example/cas/login         |
    |             ?service=https%3A%2F%2Fportal.example%2Flogin%2Fcas
    |--------------------------------------------------->|
    |                                                   | xác thực user
    |                                                   | tạo TGT/TGC
    |<------------------ 302 redirect ------------------|
    |    Location: https://portal.example/login/cas?ticket=ST-123
    |----------------->|                                 |
    |                  |-- HTTPS GET /cas/serviceValidate -->|
    |                  |   service=https://portal.example/login/cas
    |                  |   ticket=ST-123                  |
    |                  |<-- CAS XML Success / Failure ----|
    |                  |                                 |
    |                  | kiểm tra kết quả validation      |
    |                  | load local account + authorities |
    |                  | tạo SecurityContext/session      |
    |<-- 302 sạch URL -|                                 |
    | GET /orders      |                                 |
    |----------------->|                                 |
    |<-- 200 ----------|                                 |
~~~

Hai đoạn khác nhau:

- **Front channel (browser):** chuyển hướng tới CAS và quay về service URL kèm ST. Browser thấy `ticket`, nhưng chưa phải người xác minh nó.
- **Back channel (server-to-server):** ứng dụng dùng `TicketValidator` liên hệ **CAS server đã cấu hình và tin cậy** để hỏi ticket có hợp lệ **cho đúng service** không. Thông tin người dùng từ kết quả validation hợp lệ mới được dùng để đăng nhập.

Khi nhận callback, **không** viết:

~~~java
// SAI: ticket là input browser, không phải username được xác minh.
String user = request.getParameter("ticket");
session.setAttribute("user", user);
~~~

Một chuỗi `ST-...` chỉ có ý nghĩa sau khi CAS server xác thực và trả kết quả qua kênh tin cậy.

## 3. Từ điển những “ticket” dễ nhầm

| Thành phần | Ai tạo và giữ? | Mục đích | Có nên đưa tới Portal dưới dạng user ID? |
| --- | --- | --- | --- |
| **TGT** | CAS server quản lý; browser thường giữ TGC tham chiếu TGT. | Duy trì phiên SSO tại CAS, cho phép xin ST mới mà không nhập lại mật khẩu. | **Không**. |
| **TGC** | CAS server cấp cookie cho browser trên domain CAS. | Browser trình lại cookie CAS để xác định TGT/SSO session. | **Không**. Portal không có quyền đọc cookie domain CAS. |
| **ST** | CAS server cấp cho đúng `service`. | Chứng cứ tạm để **một service** gọi CAS xác minh. | **Không** dùng làm local user ID/session ID. |
| **LT** | CAS server có thể cấp cho form login. | Bảo vệ một lần gửi thông tin đăng nhập CAS. | Không phải ST và không phải cookie phiên Portal. |
| **PT** | CAS server cấp cho proxy theo profile. | Service ở tuyến sau xác minh proxy ticket theo chính sách. | Không tự chấp nhận ở endpoint chỉ dành cho ST. |
| **PGT / PGTIOU** | CAS server và service proxy trao đổi theo cơ chế riêng. | Giúp dịch vụ xin PT khi thực hiện proxying. | Không cần cho luồng web login cơ bản. |
| **JSESSIONID** | Servlet container của Portal (hoặc session store). | Duy trì phiên **riêng** của Portal sau khi ST đã xác minh. | Không phải CAS ST/TGT. |

**TGT vs ST:** Một người có thể có **một phiên CAS SSO** nhưng nhận **nhiều ST khác nhau** khi vào nhiều ứng dụng. ST được dùng một lần để tạo các phiên ứng dụng; TGT/TGC còn sống có thể giúp xin ST mới.

**LT vs ST:** Nếu thấy `LT-...` trên form đăng nhập của CAS, đó thường là login ticket phục vụ bước gửi credentials tới CAS, **không phải** ST mà Portal được phép dùng tại `/serviceValidate`.

**Không lưu ST dài hạn:** Một ST đã được xác minh nên bị CAS tiêu thụ. Ứng dụng sử dụng `Authentication` đã được thiết lập và session local theo chính sách, không cần “gia hạn” hoặc phát lại ST ở request nghiệp vụ tiếp theo.

## 4. Bước 1 — Người dùng yêu cầu trang cần bảo vệ

Giả sử Portal có:

~~~text
GET https://portal.example/orders
Cookie: JSESSIONID=... (chưa có Authentication hợp lệ)
~~~

Spring Security kiểm tra yêu cầu. Nếu tài nguyên cần xác thực nhưng người dùng chưa có `Authentication`, `ExceptionTranslationFilter` gọi `AuthenticationEntryPoint`. Trong tích hợp CAS, `CasAuthenticationEntryPoint` xây URL đăng nhập CAS, kèm một `service` đã được cấu hình.

Ví dụ:

~~~http
HTTP/1.1 302 Found
Location: https://cas.example/cas/login?service=https%3A%2F%2Fportal.example%2Flogin%2Fcas
Cache-Control: no-store
~~~

**Đọc URL:** Browser sẽ vào `https://cas.example/cas/login`. `service` là URL callback của Portal, ở đây chính xác:

~~~text
https://portal.example/login/cas
~~~

Nó **không phải** trang người dùng muốn xem `/orders`, trừ khi CAS client cố ý xử lý ticket tại URL đó. Sau khi xác minh, Portal có thể dùng SavedRequest của Spring Security để quay lại `/orders`.

### 4.1. Quy tắc an toàn cho `service`

- CAS server nên có **service registry/allowlist** những URL ứng dụng được phép sử dụng CAS; không phát ticket cho service URL tùy ý do attacker điều khiển.
- Ứng dụng dùng một **public canonical HTTPS service URL** từ cấu hình đáng tin: scheme, host, port, context path, path, query (nếu có).
- Giá trị dùng khi gọi `/serviceValidate` phải khớp với service mà CAS đã cấp ticket cho, theo quy tắc so khớp của server/registration.
- Không tự lấy `service` từ `request.getParameter("service")` của browser rồi mang đi xác minh; điều này làm mở rộng trust boundary và có thể gây open redirect/tenant confusion.
- Sau reverse proxy/load balancer, đảm bảo external HTTPS URL không bị thay bằng `http://internal-node:8080/login/cas`.
- Với multi-tenant, mỗi service/registration cần canonical URL và chính sách mapping rõ; không chọn tenant từ tham số chưa tin cậy.

**Nhớ:** Dù URL CAS và Portal đều có đoạn `/login`, chúng là **hai host và hai endpoint khác nhau**.

## 5. Bước 2 — CAS xác thực người dùng và phát ST

Khi browser đến `/cas/login?service=...`:

1. CAS kiểm tra ticket-granting cookie đã có hay chưa; nếu có TGT/SSO session hợp lệ, CAS có thể không hỏi mật khẩu.
2. Nếu không có phiên, CAS cho người dùng nhập thông tin xác thực hoặc dùng cơ chế đăng nhập được cấu hình (MFA, directory, external IdP...).
3. CAS server quyết định xác thực có đạt không và service có được phép tham gia federation không.
4. Khi đủ điều kiện, CAS tạo **một ST opaque** dành cho service đã chỉ định.
5. CAS gửi HTTP redirect về callback ứng dụng, kèm `ticket`.

Ví dụ:

~~~http
HTTP/1.1 302 Found
Location: https://portal.example/login/cas?ticket=ST-4e8c9a
Cache-Control: no-store
~~~

Browser sau đó yêu cầu:

~~~http
GET /login/cas?ticket=ST-4e8c9a HTTP/1.1
Host: portal.example
Cookie: JSESSIONID=...
~~~

Ticket có thể có prefix `ST-`, nhưng **không xác minh tính hợp lệ bằng regex, prefix hay độ dài**. Mọi chuỗi có thể tự được gắn nhãn ST; chỉ CAS server được tin mới quyết định nó có được phát và chưa bị tiêu thụ/hết hạn không.

### 5.1. ST là opaque credential

- Không giải mã ST thành username, role hoặc email.
- Không dùng ST làm khóa tài khoản hoặc cache quyền lâu dài.
- Không log nguyên văn ST ở access log, APM trace, exception message hoặc `Referer`.
- Không truyền lại ST cho API khác như bearer token.
- Không dùng một ST của tenant A để đăng nhập tenant B.
- Không cho một ST bị lỗi validation kích hoạt “tạo phiên tạm” với quyền mặc định.

### 5.2. Ticket có tuổi thọ và tính một lần

CAS protocol quy định ST:

1. **Chỉ hợp lệ cho service** đã được chỉ định lúc CAS cấp.
2. **Chỉ hợp lệ cho một lần xác minh**; CAS phải vô hiệu hóa ticket sau attempt validation, **dù validation thành công hay không**.
3. Nên hết hạn nhanh nếu không được xác minh.

Vì vậy nếu Portal gọi CAS xác minh với **sai service**, ticket có thể đã bị tiêu thụ; chỉnh lại service rồi **retry chính ticket đó** không được coi là phương án khôi phục an toàn. Cần cho người dùng bắt đầu một lần CAS login mới để nhận ST mới.

Nếu kết nối bị timeout sau khi gửi request, ứng dụng không thể biết CAS đã tiêu thụ ST hay chưa; không tự khẳng định ticket vẫn còn hợp lệ và không tự cấp Authentication.

## 6. Bước 3 — Callback nhận ST nhưng chưa xác thực thành công

`CasAuthenticationFilter` nghe URL callback, mặc định thường là `/login/cas`. Khi browser đưa ST qua tham số `ticket`, filter tạo một **authentication request** chứa credential dạng ST và chuyển cho `AuthenticationManager` / `CasAuthenticationProvider`.

~~~text
GET /login/cas?ticket=ST-4e8c9a
         |
         v
CasAuthenticationFilter
  -> CasServiceTicketAuthenticationToken (unauthenticated)
         |
         v
AuthenticationManager / ProviderManager
         |
         v
CasAuthenticationProvider
  -> TicketValidator (server-to-server)
         |
         v
CAS /serviceValidate
         |
         v
Validated Assertion + CAS username
         |
         v
Load local UserDetails / GrantedAuthority
         |
         v
CasAuthenticationToken (authenticated)
         |
         v
SecurityContextRepository + local session
~~~

**Trong Spring Security 6.3**, tên token được Javadoc dùng là `CasServiceTicketAuthenticationToken`. Khi đọc tài liệu cũ, có thể gặp các mô tả/đoạn XML cấu hình thuộc phiên bản trước; hãy đối chiếu source API với dependency tree đang chạy.

Chú ý: **Browser không trực tiếp gọi `/serviceValidate` để đăng nhập Portal**. Nếu để JavaScript/browser tự validate và gửi username về server, attacker có thể thay giá trị username hoặc giả response. Việc xác minh phải diễn ra ở phía server Portal, qua kết nối HTTPS tới CAS do Portal kiểm soát.

## 7. Bước 4 — Portal gọi CAS xác minh ticket bằng back channel

### 7.1. Endpoint CAS 2.0

~~~text
GET https://cas.example/cas/serviceValidate
    ?service=https%3A%2F%2Fportal.example%2Flogin%2Fcas
    &ticket=ST-4e8c9a
~~~

Hai tham số bắt buộc:

| Tham số | Ai cung cấp? | Kiểm tra quan trọng |
| --- | --- | --- |
| `service` | **Server Portal từ cấu hình tin cậy**. | Phải đúng service mà CAS đã cấp ST. |
| `ticket` | Browser đưa về, nhưng **chỉ được tin sau CAS validation**. | ST đúng service, chưa dùng, chưa hết hạn theo CAS. |

Tham số `renew=true` chỉ sử dụng khi service yêu cầu xác thực lại bằng credentials chính thay vì dựa vào phiên SSO. Nếu dùng ở login, cũng phải dùng ở validation theo hợp đồng, nếu không kỳ vọng bảo mật có thể sai.

**Kết nối này khác HTTP redirect trước đó:** CAS server không lấy username bằng cách browser gọi lại Portal với một chuỗi xác nhận tự khai; **Portal chủ động kết nối tới CAS** và kiểm tra kết quả từ endpoint được cấu hình cố định.

### 7.2. CAS trả XML thành công

~~~xml
<cas:serviceResponse xmlns:cas="http://www.yale.edu/tp/cas">
    <cas:authenticationSuccess>
        <cas:user>alice</cas:user>
    </cas:authenticationSuccess>
</cas:serviceResponse>
~~~

Các điểm cần nắm:

- Namespace XML **`http://www.yale.edu/tp/cas`**, không phải namespace SAML2.
- `cas:user` là username/subject do CAS báo cho **ST hợp lệ**.
- CAS 3.0 có thể bổ sung `cas:attributes` khi dùng `/p3/serviceValidate` và cấu hình release attributes. Đừng giả định mọi deployment CAS 2.0 luôn trả cùng một tập attributes.
- Thành công ở CAS mới là **authentication identity**; quyền đọc đơn hàng, tenant và local account là trách nhiệm Portal.
- Username không nhất thiết ổn định/toàn cục giữa nhiều CAS realms; với multi-CAS phải gắn issuer/source tin cậy vào khóa liên kết.

Ví dụ CAS 3.0 có attributes:

~~~xml
<cas:serviceResponse xmlns:cas="http://www.yale.edu/tp/cas">
    <cas:authenticationSuccess>
        <cas:user>alice</cas:user>
        <cas:attributes>
            <cas:displayName>Alice</cas:displayName>
            <cas:email>alice@example.org</cas:email>
            <cas:affiliation>staff</cas:affiliation>
        </cas:attributes>
    </cas:authenticationSuccess>
</cas:serviceResponse>
~~~

`email` hay `affiliation` là dữ liệu IdP công bố; không tự biến `affiliation=admin` thành `ROLE_ADMIN` nếu không có trust/policy mapping rõ.

### 7.3. CAS trả XML thất bại

~~~xml
<cas:serviceResponse xmlns:cas="http://www.yale.edu/tp/cas">
    <cas:authenticationFailure code="INVALID_TICKET">
        Ticket not recognized
    </cas:authenticationFailure>
</cas:serviceResponse>
~~~

Một số mã thường gặp theo CAS protocol:

| Failure code | Ý nghĩa tiêu biểu | Xử lý tại SP |
| --- | --- | --- |
| `INVALID_TICKET` | ST không tồn tại, đã dùng hoặc hết hạn. | Không authenticate; bắt đầu flow mới nếu người dùng chọn. |
| `INVALID_SERVICE` | Service xác minh không khớp hoặc service không được CAS chấp nhận. | Kiểm tra canonical service URL/registration, không nới whitelist. |
| `INVALID_REQUEST` | Thiếu tham số hoặc request không hợp lệ. | Sửa client/protocol configuration. |
| `UNAUTHORIZED_SERVICE_PROXY` | Proxy grant không được cho phép trong cấu hình liên quan. | Không chuyển sang proxy mode tùy tiện. |
| `INTERNAL_ERROR` | CAS server gặp lỗi nội bộ. | Fail closed, log loại lỗi, alert/điều tra. |

Không lưu một ticket validation failure như “anonymous session có quyền USER” để cứu UX. Hãy trả lỗi có thể hiểu, không tiết lộ ticket hoặc CAS XML raw cho browser.

### 7.4. CAS protocol versions

| Endpoint CAS | Protocol | Response | Khi dùng |
| --- | --- | --- | --- |
| `/validate` | CAS 1.0 | Plaintext `yes\\nusername\\n` hoặc `no\\n`. | Chỉ tương thích legacy; không có XML attributes. |
| `/serviceValidate` | CAS 2.0 | CAS XML success/failure. | Xác minh **service tickets**, không chấp nhận proxy ticket thành công. |
| `/p3/serviceValidate` | CAS 3.0 | CAS XML có thể có `attributes` hoặc format hỗ trợ khác. | Khi có nhu cầu thuộc tính được IdP release. |
| `/proxyValidate` | CAS 2.0/3.0 | Xác minh ST hoặc PT theo profile. | Chỉ khi ứng dụng thực sự hỗ trợ proxying. |
| `/proxy` | CAS 2.0/3.0 | Cấp proxy ticket khi có PGT hợp lệ. | Không cần cho direct browser SSO. |
| `/samlValidate` | CAS extension dùng SAML 1.1 | SAML 1.1 response bằng POST. | Khác hẳn SAML2 Web SSO Spring `saml2Login`. |

**Không nâng cấp sang `/proxyValidate` để “sửa” một ST bị từ chối**. Khi cho phép PT, cần xác minh chuỗi proxy và quy tắc `CasProxyDecider`; không bật `AcceptAnyCasProxy` mù quáng trong môi trường nhạy cảm.

## 8. Bước 5 — Portal tạo local Authentication và phiên

Khi CAS trả success và TicketValidator đã kiểm tra kết quả:

1. `CasAuthenticationProvider` nhận username và assertion/attributes từ CAS client.
2. Ứng dụng tra `UserDetails` hoặc identity link đã được duyệt.
3. Tính `GrantedAuthority` theo **quyền nội bộ** và nguồn tin cậy.
4. Tạo `CasAuthenticationToken` đã được authenticate.
5. `CasAuthenticationFilter` lưu `SecurityContext` qua repository/session theo cấu hình, áp session fixation protection.
6. Redirect khỏi callback URL chứa ticket đến trang sạch (thường là saved request ban đầu).
7. Các request nghiệp vụ sau sử dụng session local `JSESSIONID`, **không gọi CAS lại với ST đã tiêu thụ**.
8. Backend vẫn kiểm tra permission/tenant/resource ownership trên từng hành động.

~~~text
CAS trả: authenticated CAS username = alice
       |
       v
(local account link CAS source, username) -> local_user_id=104
       |
       v
Local account ACTIVE?
  no -> deny/approval
 yes -> local permissions {APP_ORDER_READ}
       |
       v
GET /orders/123
  require APP_ORDER_READ
  AND localUser.tenant == order.tenant
       |
       v
Allow / Deny
~~~

CAS xác thực danh tính **không tự chứng minh `alice` có quyền ADMIN** tại Portal. Không gán mặc định roles cao cho mọi principal CAS hoặc cấp quyền chỉ vì tên account có prefix đáng tin.

### 8.1. Local session khác CAS SSO session

Sau khi ST đã xác minh, Portal giữ session riêng. CAS vẫn có TGT/TGC; do đó:

- Portal logout local không tự hủy TGT của CAS.
- CAS logout có thể phát SLO notification tới các dịch vụ nếu được triển khai, nhưng đó là luồng riêng.
- Một session Portal bị revoke phải bị chặn kể cả CAS session vẫn còn.
- User có thể được SSO lại ngay nếu truy cập trang bảo vệ trong khi TGT CAS còn sống.

## 9. Ba failure mode quan trọng nhất

### 9.1. Ticket bị dùng lại — replay

~~~text
CAS phát ST-123 cho https://portal.example/login/cas
Portal lần 1: serviceValidate(ST-123, đúng service) -> Success alice
Portal lần 2: serviceValidate(ST-123, đúng service) -> INVALID_TICKET
~~~

Tính **one-time** thuộc CAS protocol. Không “cache” một response success rồi cho cùng ticket được dùng lại như bearer token. Nếu cần auth giữa nhiều API, dùng session/access token do ứng dụng tạo qua cơ chế riêng và có lifecycle riêng.

### 9.2. Sai service — service mismatch

~~~text
CAS phát ticket cho:
  https://portal.example/login/cas

Portal xác minh nhầm với:
  http://portal-internal:8080/login/cas
~~~

Kết quả có thể là `INVALID_SERVICE` hoặc validation failure. Trên cụm có reverse proxy, phải cấu hình **public service URL** để cả redirect và back-channel cùng dùng một giá trị. Không “sửa” bằng cách tắt kiểm tra service ở CAS hoặc whitelist vô hạn.

### 9.3. CAS không phản hồi — timeout/HTTPS failure

Nếu Portal gọi CAS và gặp timeout, chứng thư TLS không tin cậy hoặc HTTP 5xx:

- Không có `authenticationSuccess` đáng tin → **không tạo Authentication**.
- CAS có thể đã tiêu thụ ST dù Portal không nhận response; không tự lặp xác minh chính ST vô hạn.
- Ghi metric lỗi và hướng dẫn người dùng thử đăng nhập lại từ đầu khi hệ thống phục hồi.
- Đặt connect/read timeout và giới hạn response size; tránh làm cạn toàn bộ servlet threads khi CAS chậm.
- Không fallback sang `request.getParameter("username")` hoặc danh tính cũ trong session chưa có chứng minh.

## 10. Cấu hình mạng, TLS và service URL

### 10.1. Quy tắc HTTPS

- `CAS /login`: browser vào URL HTTPS chính thức, đã được quản trị tin cậy.
- `CAS /serviceValidate`: server Portal kết nối HTTPS, xác minh certificate chain và hostname bằng trust store phù hợp.
- `Portal service`: callback công khai HTTPS và khớp đăng ký CAS.
- Không tắt chứng thư bằng `TrustAll`, `HostnameVerifier(alwaysTrue)` hoặc cấu hình bỏ `SSLValidation` trong CAS client.
- Nếu có mTLS/CA nội bộ, khai báo CA certificate đúng trust store; **không bỏ TLS verification** để chạy qua lỗi.
- Không lấy CAS validation URL từ query parameter hoặc ticket content; nếu không sẽ tạo lỗ hổng SSRF/đổi danh tính.

### 10.2. Một bộ URL minh họa đúng

~~~text
CAS base URL:
  https://cas.example/cas

CAS login:
  https://cas.example/cas/login

CAS CAS2 validation:
  https://cas.example/cas/serviceValidate

Portal canonical service URL:
  https://portal.example/login/cas

Browser redirect:
  https://cas.example/cas/login
    ?service=https%3A%2F%2Fportal.example%2Flogin%2Fcas

Server validation:
  https://cas.example/cas/serviceValidate
    ?service=https%3A%2F%2Fportal.example%2Flogin%2Fcas
    &ticket=ST-4e8c9a
~~~

Tất cả URL trên là ví dụ theo domain `.example`, không phải endpoint đang hoạt động. Khi triển khai, phải đăng ký Portal service thật trên CAS và cung cấp certificate/CA hợp lệ.

### 10.3. Bảo vệ ticket trong URL

Dù ST ngắn hạn và dùng một lần, nó vẫn là credential nhạy cảm trước validation:

- HTTPS từ CAS tới Portal.
- `Referrer-Policy: no-referrer` hoặc policy nghiêm ngặt trên callback/response có ticket.
- Không tải third-party assets và không render script analytics trên URL callback còn chứa `ticket`.
- Sau validation, redirect tới trang **không còn ticket**.
- Cấu hình ingress/access logs không lưu query ticket hoặc masking token đúng loại.
- `Cache-Control: no-store` cho callback/status nhạy cảm.
- Không đưa ticket vào email, query của redirect bên thứ ba, metrics labels hoặc exception messages.
- Đừng chuyển ticket qua `window.location` sang trang HTML do user có thể thao tác.

**Cẩn thận:** Browser có thể có lịch sử điều hướng/referrer; tính “một lần” làm giảm cửa sổ lạm dụng nhưng không thay cho kiểm soát lộ credential.

## 11. Java 17 độc lập: mô phỏng ticket cấp cho service và tiêu thụ một lần

Ví dụ sau là chương trình **chạy offline hoàn toàn**, không có CAS server thật. Nó mô phỏng các quy tắc bắt buộc: ticket dành cho đúng service và bị tiêu thụ **kể cả khi validation thất bại**. Dùng nó để hiểu sequence, **không dùng mô phỏng làm bộ xác thực production**.

### 11.1. Tệp `CasTicketLifecycleDemo.java`

~~~java
import java.util.HashMap;
import java.util.HashSet;
import java.util.Map;
import java.util.Set;

public class CasTicketLifecycleDemo {

    private static final String PORTAL =
        "https://portal.example/login/cas";
    private static final String OTHER =
        "https://other.example/login/cas";

    record Ticket(String service, String username) { }

    private final Map<String, Ticket> issued = new HashMap<>();
    private final Set<String> consumed = new HashSet<>();

    void issue(String ticket, String service, String username) {
        issued.put(ticket, new Ticket(service, username));
    }

    String validate(String ticket, String presentedService) {
        Ticket expected = issued.get(ticket);
        if (expected == null || !consumed.add(ticket)) {
            return "INVALID_TICKET";
        }

        // Ticket bị tiêu thụ ngay tại validation attempt.
        if (!expected.service().equals(presentedService)) {
            return "INVALID_SERVICE";
        }
        return "SUCCESS:" + expected.username();
    }

    public static void main(String[] args) {
        CasTicketLifecycleDemo cas = new CasTicketLifecycleDemo();
        cas.issue("ST-A", PORTAL, "alice");
        cas.issue("ST-B", PORTAL, "bob");

        System.out.println("first=" +
            cas.validate("ST-A", PORTAL));
        System.out.println("replay=" +
            cas.validate("ST-A", PORTAL));
        System.out.println("wrongService=" +
            cas.validate("ST-B", OTHER));
        System.out.println("afterWrongService=" +
            cas.validate("ST-B", PORTAL));
        System.out.println("unknown=" +
            cas.validate("ST-NOT-ISSUED", PORTAL));
    }
}
~~~

### 11.2. Chạy và stdout

~~~bash

~~~

**Stdout chính xác:**

~~~text

replay=INVALID_TICKET
wrongService=INVALID_SERVICE
afterWrongService=INVALID_TICKET
unknown=INVALID_TICKET
~~~

Giải thích:

- `ST-A` lần đầu đúng service trả về user alice.
- Lần tiếp theo `ST-A` không còn hợp lệ.
- `ST-B` được cấp cho Portal nhưng validate bằng OTHER → sai service.
- `ST-B` vẫn không thể validate thành công trở lại sau lần sai đó, vì protocol đã tiêu thụ ticket.
- ST không được phát hành bị từ chối.

**Giới hạn:** mô phỏng lưu trong `HashMap`, không có mật mã, user database, TGC/TGT, thời hạn ticket hay HTTP. Không có khả năng chống attacker thật. Chương trình chỉ thể hiện **các quy tắc** để thiết kế bộ test.

## 12. Java 17 server-to-server: gọi `/serviceValidate` và parse CAS XML an toàn

Trong production, ưu tiên **CAS client library / Spring Security CAS** thay vì tự xây parser và bộ xác minh. Mẫu sau dùng **JDK 17 thuần** để minh họa chính xác nơi diễn ra cuộc gọi HTTPS và những kiểm tra XML tối thiểu. Nó chỉ nhận **CAS validation URL và service URL được cấu hình cố định**, tuyệt đối không nhận hai URL này từ browser.

### 12.1. Tệp `CasServiceValidateClient.java`

~~~java
import java.io.ByteArrayInputStream;
import java.io.InputStream;
import java.net.URI;
import java.net.URLEncoder;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.nio.charset.StandardCharsets;
import java.time.Duration;

import javax.xml.XMLConstants;
import javax.xml.parsers.DocumentBuilderFactory;

import org.w3c.dom.Document;
import org.w3c.dom.Element;
import org.w3c.dom.Node;
import org.w3c.dom.NodeList;

public final class CasServiceValidateClient {

    // Ví dụ: thay bằng URL HTTPS do ADMIN cấu hình.
    private static final String VALIDATION_ENDPOINT =
        "https://cas.example/cas/serviceValidate";
    private static final String SERVICE =
        "https://portal.example/login/cas";
    private static final String CAS_NS =
        "http://www.yale.edu/tp/cas";

    private CasServiceValidateClient() {
    }

    public static String verifyServiceTicket(String ticket)
            throws Exception {

        if (ticket == null || ticket.isBlank()
                || ticket.length() > 512
                || ticket.chars().anyMatch(Character::isISOControl)) {
            throw new IllegalArgumentException("Invalid ticket input");
        }

        // CAS URL và service là constants đáng tin; chỉ ticket
        // đến từ browser và phải được xác minh qua HTTPS CAS.
        String query = "service=" +
            URLEncoder.encode(SERVICE, StandardCharsets.UTF_8)
            + "&ticket=" +
            URLEncoder.encode(ticket, StandardCharsets.UTF_8);

        URI uri = URI.create(VALIDATION_ENDPOINT + "?" + query);
        if (!"https".equalsIgnoreCase(uri.getScheme())) {
            throw new SecurityException("CAS must use HTTPS");
        }

        HttpClient client = HttpClient.newBuilder()
            .connectTimeout(Duration.ofSeconds(3))
            .followRedirects(HttpClient.Redirect.NEVER)
            .build();

        HttpRequest request = HttpRequest.newBuilder(uri)
            .timeout(Duration.ofSeconds(5))
            .header("Accept", "application/xml")
            .GET()
            .build();

        HttpResponse<InputStream> response = client.send(
            request, HttpResponse.BodyHandlers.ofInputStream());

        // Giới hạn đọc response; không cấp memory vô hạn cho XML.
        try (InputStream body = response.body()) {
            if (response.statusCode() != 200) {
                throw new SecurityException(
                    "CAS validation HTTP status not 200");
            }

            byte[] xml = body.readNBytes(65_537);
            if (xml.length > 65_536) {
                throw new SecurityException("CAS XML too large");
            }

            return parseSuccess(xml);
        }
    }

    private static String parseSuccess(byte[] xml) throws Exception {
        DocumentBuilderFactory factory =
            DocumentBuilderFactory.newInstance();
        factory.setNamespaceAware(true);
        factory.setXIncludeAware(false);
        factory.setExpandEntityReferences(false);
        factory.setFeature(XMLConstants.FEATURE_SECURE_PROCESSING, true);
        factory.setFeature(
            "http://apache.org/xml/features/disallow-doctype-decl",
            true);
        factory.setFeature(
            "http://xml.org/sax/features/external-general-entities",
            false);
        factory.setFeature(
            "http://xml.org/sax/features/external-parameter-entities",
            false);
        factory.setAttribute(XMLConstants.ACCESS_EXTERNAL_DTD, "");
        factory.setAttribute(XMLConstants.ACCESS_EXTERNAL_SCHEMA, "");

        Document document = factory.newDocumentBuilder().parse(
            new ByteArrayInputStream(xml));
        Element root = document.getDocumentElement();
        if (!CAS_NS.equals(root.getNamespaceURI())
                || !"serviceResponse".equals(root.getLocalName())) {
            throw new SecurityException("Not CAS serviceResponse");
        }

        Element success = directChild(root, "authenticationSuccess");
        Element failure = directChild(root, "authenticationFailure");
        if ((success == null) == (failure == null)) {
            throw new SecurityException("Ambiguous CAS response");
        }
        if (failure != null) {
            // Không đưa chi tiết raw XML hoặc ticket ra browser/log.
            throw new SecurityException("CAS rejected service ticket");
        }

        Element user = directChild(success, "user");
        if (user == null || user.getTextContent().isBlank()) {
            throw new SecurityException("CAS response without user");
        }
        return user.getTextContent().trim();
    }

    private static Element directChild(Element parent, String name) {
        Element found = null;
        NodeList nodes = parent.getChildNodes();
        for (int i = 0; i < nodes.getLength(); i++) {
            Node node = nodes.item(i);
            if (node instanceof Element element
                    && CAS_NS.equals(element.getNamespaceURI())
                    && name.equals(element.getLocalName())) {
                if (found != null) {
                    throw new SecurityException("Duplicate CAS element");
                }
                found = element;
            }
        }
        return found;
    }

    public static void main(String[] args) throws Exception {
        if (args.length != 1) {
            System.err.println(
                "Usage: java CasServiceValidateClient <service-ticket>");
            System.exit(2);
        }
        String user = verifyServiceTicket(args[0]);
        System.out.println("validatedUser=" + user);
    }
}
~~~

### 12.2. Chạy

~~~bash
javac --release 17 CasServiceValidateClient.java
java CasServiceValidateClient ST-REAL-TICKET
~~~

Vì ví dụ dùng host `cas.example` và `portal.example` không có thật, lệnh trên chỉ chạy thành công **khi thay hai constants bằng môi trường CAS test thật và có ST chưa dùng**. Stdout khi hợp lệ phụ thuộc username từ CAS, ví dụ `validatedUser=alice`; không có stdout cố định khi CAS/TLS/ticket không được cung cấp.

**Những gì code có làm:**

- Fixed HTTPS validation endpoint, không follow redirect và có connect/request timeout.
- `service` được URL-encode và không thay đổi theo input browser.
- Ticket chỉ gửi tới CAS validation endpoint, không tự tin nội dung ticket.
- Giới hạn body size, HTTP status check.
- Parse namespace CAS, loại DTD/external entities để giảm XXE, nhận **một** success hoặc failure.
- Chỉ trả username từ `cas:authenticationSuccess` khi response đạt kiểm tra tối thiểu.

**Những gì code KHÔNG tự làm:**

- Không phải CAS client production đầy đủ: chưa hỗ trợ version-negotiation, login redirect, Spring session/authentication, proxy chains, SLO, response schemas mở rộng.
- Không tự kiểm tra ST có đúng service theo dữ liệu XML; **CAS server** kiểm tra qua `serviceValidate`. Điều đó đòi tin đúng server CAS và TLS certificate/hostname.
- Không thiết lập local user/permissions hoặc harden toàn bộ HTTP ingress/headers.
- Không thay CAS client có hardened timeouts, telemetry, schema handling và security updates.
- Không chấp nhận “có username là admin”; authorization bắt buộc tách riêng.

### 12.3. Không tin response XML nếu chỉ có HTTP status 200

CAS server có thể trả **HTTP 200 kèm `authenticationFailure`**. Vì vậy status 200 chỉ nói request HTTP hoàn thành, **không phải login thành công**. Phải parse CAS XML và chỉ chấp nhận `authenticationSuccess` đúng namespace/format. Nếu HTTP 302 tới trang login, HTML lỗi, XML sai, TLS lỗi hoặc không có user → không cấp Authentication.

### 12.4. Xử lý retry đúng với ticket một lần

Nếu ticket đã đi vào một request `serviceValidate` nhưng mất response, không thể chắc chắn CAS đã tiêu thụ ST. Đối với browser login, phương án đơn giản là yêu cầu người dùng **khởi tạo CAS login mới** và nhận ST mới. Đừng cache một username vừa nhận từ kết nối không đủ tin cậy để cho request sau đi qua mà không xác minh.

## 13. Spring Security CAS: các class và luồng cấu hình

Tài liệu Spring Security CAS mô tả các thành phần:

| Thành phần | Vai trò |
| --- | --- |
| `ServiceProperties` | Giữ URL `service` (callback Portal) và chính sách renew. |
| `CasAuthenticationEntryPoint` | Redirect browser tới `/cas/login?service=...`. |
| `CasAuthenticationFilter` | Nhận `ticket` tại callback `/login/cas`, tạo token chưa xác thực. |
| `CasServiceTicketAuthenticationToken` | Mang ST tới AuthenticationManager/Provider. |
| `CasAuthenticationProvider` | Gọi TicketValidator, nạp user/authorities, sinh token đã xác thực. |
| `Cas20ServiceTicketValidator` | CAS client gọi `/serviceValidate` của CAS bằng HTTPS, parse XML. |
| `UserDetailsService` | Tải local user, trạng thái và quyền đã được ứng dụng duyệt. |
| `CasAuthenticationToken` | Authentication đã hoàn tất từ CAS validation và local authorities. |
| `SecurityContextRepository` | Lưu Authentication vào phiên local sau khi thành công. |
| `LogoutFilter` / CAS Single Sign Out filters | Local logout/SLO là bài toán riêng, không xảy ra tự động chỉ vì đã login qua CAS. |

**Spring Security CAS không phải `.saml2Login()`.** Nếu CAS server phát SAML2 Web SSO, đó là một tích hợp khác; chọn đúng protocol và dependencies.

### 13.1. Gói dependency

Với Spring Boot 3.3.x (Spring Security 6.3.x) có module:

~~~groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
    implementation 'org.springframework.boot:spring-boot-starter-security'
    implementation 'org.springframework.security:spring-security-cas'
}
~~~

Module `spring-security-cas` tích hợp một CAS client library. **Không** phải `spring-security-saml2-service-provider`, và Boot **không tự bật CAS filter chỉ vì có dependency**. Cần khai báo EntryPoint, Provider, Filter và chính sách session.

Tài liệu CAS trong Spring Security chứa nhiều ví dụ XML legacy; đoạn Java DSL ở bài này minh họa cấu hình nhắm phiên bản Spring Security 6.3. Khi nâng sang bản khác, xem API và việc lưu SecurityContext thực tế; đừng copy đoạn cấu hình không khớp major version.

import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.core.userdetails.UsernameNotFoundException;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.web.SecurityFilterChain;
import org.springframework.security.web.context.HttpSessionSecurityContextRepository;

@Configuration
public class CasSecurityConfig {

    @Bean
    ServiceProperties serviceProperties(
            @Value("${app.cas.service-url}") String serviceUrl) {
        if (!serviceUrl.startsWith("https://")
                || !serviceUrl.endsWith("/login/cas")) {
            throw new IllegalArgumentException(
                "CAS service must be canonical HTTPS /login/cas");
        }
        ServiceProperties properties = new ServiceProperties();
        properties.setService(serviceUrl);
        properties.setSendRenew(false);
        return properties;
    }

    @Bean
    CasAuthenticationEntryPoint casEntryPoint(
            ServiceProperties properties,
            @Value("${app.cas.login-url}") String loginUrl) {
        if (!loginUrl.startsWith("https://")) {
            throw new IllegalArgumentException("CAS login requires HTTPS");
        }
        CasAuthenticationEntryPoint entryPoint =
            new CasAuthenticationEntryPoint();
        entryPoint.setLoginUrl(loginUrl);
        entryPoint.setServiceProperties(properties);
        return entryPoint;
    }

    @Bean
    UserDetailsService localUsers() {
        // Demo allowlist cố định. Production: database,
        // account status, tenant mapping và approval.
        UserDetails alice = User.withUsername("alice")
            .password("{noop}not-used-for-cas")
            .authorities("APP_ORDER_READ")
            .build();

        Map<String, UserDetails> allowed =
            Map.of("alice", alice);

        return username -> {
            UserDetails found = allowed.get(username);
            if (found == null) {
                throw new UsernameNotFoundException(
                    "CAS subject not linked to local account");
            }
            return found;
        };
    }

    @Bean
    CasAuthenticationProvider casProvider(
            ServiceProperties properties,
            UserDetailsService localUsers,
            @Value("${app.cas.base-url}") String baseUrl) {

        if (!baseUrl.startsWith("https://")) {
            throw new IllegalArgumentException("CAS requires HTTPS");
        }

        CasAuthenticationProvider provider =
            new CasAuthenticationProvider();
        provider.setServiceProperties(properties);
        provider.setTicketValidator(
            new Cas20ServiceTicketValidator(baseUrl));
        provider.setUserDetailsService(localUsers);

        // CAS provider-local identity, không phải private key.
        provider.setKey("orders-portal-cas-provider");
        return provider;
    }

    @Bean
    AuthenticationManager casAuthenticationManager(
            CasAuthenticationProvider provider) {
        return new ProviderManager(List.of(provider));
    }

    @Bean
    CasAuthenticationFilter casAuthenticationFilter(
            AuthenticationManager casAuthenticationManager,
            ServiceProperties properties) {

        CasAuthenticationFilter filter =
            new CasAuthenticationFilter();
        filter.setAuthenticationManager(casAuthenticationManager);
        filter.setServiceProperties(properties);
        filter.setFilterProcessesUrl("/login/cas");

        // Spring Security 6.x: lưu SecurityContext
        // sau CAS auth vào session theo chính sách.
        filter.setSecurityContextRepository(
            new HttpSessionSecurityContextRepository());
        return filter;
    }

    @Bean
    SecurityFilterChain securityFilterChain(
            HttpSecurity http,
            CasAuthenticationEntryPoint entryPoint,
            CasAuthenticationFilter casFilter) throws Exception {

        return http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/error").permitAll()
                .anyRequest().authenticated()
            )
            .exceptionHandling(ex -> ex
                .authenticationEntryPoint(entryPoint)
            )
            .addFilterAt(casFilter, CasAuthenticationFilter.class)
            .build();
    }
}
~~~

**Cách từng bean phối hợp:**

1. `ServiceProperties` giữ một service URL cố định. Giá trị này được dùng ở redirect tới CAS và ở validation; không thay đổi theo query `service` của browser.
2. `CasAuthenticationEntryPoint` được Spring Security gọi khi trang bảo vệ yêu cầu Authentication. Nó chuyển browser tới URL `CAS_LOGIN_URL`.
3. `CasAuthenticationFilter` xử lý `/login/cas` và lấy `ticket`. Callback này phải trùng path trong `CAS_SERVICE_URL`.
4. `CasAuthenticationProvider` tạo CAS authentication khi `Cas20ServiceTicketValidator` xác minh ST bằng kết nối HTTPS đến `CAS_SERVER_BASE_URL + /serviceValidate`.
5. `localUsers` giới hạn user được phép dùng Portal sau CAS login. Nó **không sử dụng mật khẩu local để kiểm tra CAS**, nhưng chỉ trả quyền `APP_ORDER_READ` cho `alice` trong demo.
6. `ProviderManager` chứa CAS provider. `HttpSessionSecurityContextRepository` giúp phiên Servlet ghi nhận Authentication sau khi filter xử lý thành công.
7. `.exceptionHandling(...authenticationEntryPoint(...))` bảo đảm yêu cầu chưa đăng nhập được redirect tới CAS.
8. `.addFilterAt(..., CasAuthenticationFilter.class)` đặt CAS filter trong vị trí chuyên dụng của Spring Security.
9. Cấu hình chưa có **multi-tenant identity mapping** hoặc CAS SLO. Nếu Portal phục vụ nhiều CAS servers, cần tách realm/issuer và policy, không chỉ so username.
10. `password("{noop}not-used-for-cas")` là dữ liệu giả dành cho local UserDetails; ví dụ **không** đề nghị sử dụng password dạng noop cho tài khoản đăng nhập local production. CAS provider không dùng password ấy để xác thực CAS.

**Không nên làm:** thay `Cas20ServiceTicketValidator` bằng một validator luôn trả “success” để bỏ qua lỗi CAS. Điều đó sẽ biến ST do browser tự tạo thành đăng nhập hợp lệ.

### 14.5. WhoAmIController.java

`src/main/java/com/example/casdemo/WhoAmIController.java`:

~~~java
package com.example.casdemo;

import java.util.Map;
import org.springframework.security.core.Authentication;
import org.springframework.security.core.GrantedAuthority;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class WhoAmIController {

    @GetMapping("/me")
    public Map<String, Object> me(Authentication authentication) {
        return Map.of(
            "principal", authentication.getName(),
            "authorities", authentication.getAuthorities().stream()
                .map(GrantedAuthority::getAuthority)
                .toList()
        );
    }
}
~~~

Vì `/me` yêu cầu Authentication, người dùng chưa đăng nhập sẽ được chuyển sang CAS. Khi CAS validation thành công cho local subject `alice`, JSON dự kiến:

~~~json
{
  "principal": "alice",
  "authorities": ["APP_ORDER_READ"]
}
~~~

**JSON này chỉ là ví dụ** khi CAS username đúng `alice` và local allowlist đúng. CAS không tự cấp mọi local role. Nếu CAS xác thực `bob` nhưng ứng dụng không có link, `localUsers` báo lỗi và Portal không được cấp Authentication.

### 14.6. Chạy và kiểm chứng tương tác

Với JDK 17, Gradle wrapper tương thích, CAS server/metadata (CAS service registry) được cấu hình thật:

~~~bash
./gradlew bootRun
~~~

Trên Windows PowerShell:

~~~powershell
.\gradlew.bat bootRun
~~~

Các bước:

1. CAS server công bố `/login` và `/serviceValidate` trên HTTPS, sử dụng certificate được Portal tin.
2. Đăng ký `https://portal.company.example/login/cas` trong service registry của CAS; đảm bảo đúng callback host/path.
3. Cài `CAS_SERVER_BASE_URL`, `CAS_LOGIN_URL` và `CAS_SERVICE_URL` từ nguồn cấu hình được quản trị.
4. Mở `https://portal.company.example/me`. Spring redirect tới CAS với `service` đúng.
5. Đăng nhập CAS bằng một user được phép (`alice` trong demo).
6. CAS trả browser tới `/login/cas?ticket=ST-...`.
7. Xem network **phía server Portal**: CAS client gọi `/serviceValidate` qua HTTPS với `service` và `ticket`. Không log ST nguyên văn.
8. Sau success, browser được redirect tới trang sạch và có phiên Portal. `/me` trả username và local authorities.
9. Logout local, mở lại `/me`: nếu TGC CAS còn hiệu lực, có thể SSO nhanh trở lại. Đây là trạng thái CAS session độc lập.
10. Thử ticket cũ/sai service/timeout và quan sát **không có authenticated session**.

**Giới hạn runnable:** Java/Spring source dựa API Spring Security 6.x và CAS client; nó cần CAS server thật để xác minh ST. Demo không khởi động được một CAS server giả chỉ bằng chạy Portal. Với production phải thêm logging có redaction, session policies, account lifecycle/tenant checks, health checks và bản vá cập nhật.

## 15. CAS `renew`, `gateway`, proxying: biết để không làm sai flow

### 15.1. Renew

`renew=true` ở CAS `/login` yêu cầu CAS bỏ qua SSO session và thực hiện primary authentication lại theo profile. Ở `/serviceValidate`, cùng option giới hạn chấp nhận ticket phát từ việc user trình credentials chính, không phải chỉ từ phiên SSO cũ.

Không bật `renew` chỉ ở một phía rồi cho rằng step-up đã được thực thi. Nếu dùng MFA/step-up, phải hiểu chính sách thực của CAS server và kiểm thử với người dùng đang có TGT.

### 15.2. Gateway

`gateway=true` ở `/login` cho phép thử đăng nhập **không làm gián đoạn**. Nếu browser không có phiên SSO, CAS có thể trả về `service` **không có ticket**. Đây là một kết quả hợp lệ theo mode gateway, **không phải một ST rỗng được phép coi là đã authenticate**.

Gateway và renew có ý nghĩa trái ngược; không gửi cả hai rồi dựa vào hành vi ngẫu nhiên. Một CAS client có gateway phải xử lý callback không ticket và tránh vòng lặp redirect vô hạn.

### 15.3. Proxying

Đối với ứng dụng gọi dịch vụ khác thay mặt user, CAS hỗ trợ PGT/PT và `/proxyValidate`. Proxy flow có trust chain riêng; không “mở” proxy chỉ để tăng khả năng nhận ticket. Khi nhận PT, phải kiểm tra proxy list theo policy và chỉ chấp nhận những proxies đáng tin; không bật `acceptAnyProxy` mặc định trong môi trường nhạy cảm.

Bài này **chỉ tập trung direct service-ticket login**; proxying là phạm vi bổ sung.

### 15.4. CAS SLO

CAS `/logout` kết thúc CAS session; CAS server có thể thông báo tới services để hủy session local khi hỗ trợ Single Sign Out. Cấu hình SLO dùng filter/session mapping riêng và phải được thử ở multi-node.

**Không nhầm** CAS Single Sign Out với SAML2 `LogoutRequest` và `LogoutResponse`. Các loại message, cookie, tickets và validators khác nhau. Local logout Portal không tự chắc chắn hủy TGT CAS.

## 16. Khi có nhiều CAS servers hoặc nhiều tenant

Một ứng dụng federation có thể kết nối:

~~~text
CAS realm A:
  CAS base URL = https://cas-a.partner.example/cas
  service URL = https://portal.example/a/login/cas
  tenant = A

CAS realm B:
  CAS base URL = https://cas-b.partner.example/cas
  service URL = https://portal.example/b/login/cas
  tenant = B
~~~

Nếu cả hai CAS servers trả username `alice`, không được tự coi đó là cùng người hoặc cùng local account.

Khóa liên kết tham khảo:

~~~text
ExternalIdentityKey =
    (approved_cas_realm_id,
     canonical_service_scope,
     validated_cas_username)
~~~

- `approved_cas_realm_id` lấy từ cấu hình server CAS được tin, **không lấy từ query ticket**.
- `canonical_service_scope` là service đã đăng ký; một CAS server có thể cấp các ST với phạm vi service khác nhau.
- `validated_cas_username` chỉ lấy từ kết quả validation thành công trên đúng endpoint CAS.
- Local tenant và permissions được map qua approval/nguồn danh tính đáng tin cậy, không mặc định từ username.
- Nếu service URL thay khi di chuyển host/reverse proxy, cần migration có kiểm thử; không đơn giản thay một URL rồi cho login với ticket cũ.
- Nếu dùng dynamic routing, phải khóa mapping realm/service **trước khi redirect**, không để browser callback tự chọn CAS server khác.

**Ví dụ tấn công mix-up:** browser gửi `ticket=ST-A-...&casServer=https://attacker.example`. Nếu Portal gọi validation URL do client chỉ định, attacker trả XML `authenticationSuccess` chứa username admin, ứng dụng sẽ cấp quyền sai. Cấu hình đúng **không bao giờ** tin server URL tùy ý từ HTTP request.

## 17. Những trạng thái lỗi phải tách biệt

| Lỗi / bối cảnh | Triệu chứng | Xử lý an toàn |
| --- | --- | --- |
| Không có ST ở callback | CAS gateway không có SSO hoặc request sai. | Không authenticate; xử lý gateway riêng nếu bật. |
| ST bị replay | CAS trả `INVALID_TICKET`. | Không dùng lại; khởi tạo CAS login mới. |
| Service mismatch | CAS trả `INVALID_SERVICE`/validation fail. | Sửa canonical service URL và service registry. |
| CAS server timeout | Portal không có CAS validation result. | Fail closed; cho người dùng retry flow mới. |
| TLS trust/hostname sai | SSLHandshakeException/HTTPS fail. | Sửa trust store/certificate, không tắt validation. |
| CAS HTTP 200 nhưng XML failure | HTTP thành công, auth thất bại. | Không tạo Authentication. |
| CAS HTTP 302/HTML login page | Sai validation URL hoặc proxy rule. | Không follow redirect như success; kiểm tra endpoint. |
| XML không hợp lệ/DOCTYPE/XXE | Parser từ chối. | Ghi loại lỗi và chặn; không fallback username từ request. |
| User CAS không có local link | CAS auth thành công nhưng Portal chưa provision. | Deny/approval; không tự cấp role admin. |
| ST bị lộ trong access log | Có thể bị chiếm trước khi Portal consume. | Mask query, HTTPS, No-Referrer, redirect sạch. |
| Reverse proxy đổi host/scheme | Service gửi CAS khác URL đã đăng ký. | Dùng canonical HTTPS service URL; cấu hình forwarded headers tin cậy. |
| Callback trên Node 2 | Session SavedRequest khác Node 1. | Session replication/sticky session/shared store theo kiến trúc. |
| CAS đang chạy nhưng service registry thiếu Portal | CAS chặn service hoặc không phát ST. | Đăng ký đúng service/tenant; không làm regex allow-all. |
| Username bị tái sử dụng | Local link trỏ sai user. | Chính sách identity lifecycle, immutable ID/approved mapping nếu CAS hỗ trợ. |
| Sau local logout SSO lại ngay | TGT/TGC CAS vẫn còn. | Tách local logout và CAS logout/SLO, giải thích UX. |

### 18.1. Định nghĩa “pass” của bộ test

- Có bằng chứng network **server Portal** gọi đúng CAS host/service.
- ST được CAS chấp nhận tối đa một lần, không cache kết quả auth theo ST để replay.
- Không có Authentication nếu CAS XML failure, lỗi mạng, XML không hợp lệ hoặc service mismatch.
- Local account và permissions được tải từ nguồn tin cậy, không tự tin username/roles từ HTTP query.
- Browser kết thúc ở URL sạch; không log ticket.
- Test multi-tenant không chuyển CAS realm/service/identity context vì tham số do browser đặt.
- Local logout, CAS logout, session timeout và SLO được mô tả/kiểm thử riêng.

**Giới hạn ví dụ:** Java offline mục 11 **chỉ mô phỏng** ticket policy; Java HTTPS mục 12 minh họa validation wire; project Spring mục 14 yêu cầu CAS server thật. Không lấy output mô phỏng làm bằng chứng SSO production đang an toàn.

## 19. Câu hỏi tự đánh giá

**1. Vì sao Portal không thể chỉ nhìn thấy `ticket=ST-...` rồi đăng nhập?**  
Vì browser kiểm soát query parameter. Portal phải xác minh với CAS server đáng tin bằng kết nối back-channel.

**2. `service` dùng để làm gì?**  
Ràng buộc ticket với đúng ứng dụng/callback đã được CAS cấp quyền, ngăn ST dành cho nơi khác bị dùng ở Portal.

**3. Ticket đã validate sai service có thể gửi lại với service đúng không?**  
Không được kỳ vọng; CAS protocol quy định ST chỉ cho một validation attempt, kể cả thất bại.

**4. CAS trả HTTP 200, có thể tin là user đã authenticate không?**  
Không. Phải đọc `cas:authenticationSuccess` và dữ liệu user trong XML hợp lệ.

**5. TGT khác ST thế nào?**  
TGT/TGC giữ phiên SSO ở CAS; ST dùng một lần cho một service để Portal xác minh.

**6. Trong Spring Security, class nào tạo redirect tới CAS?**  
`CasAuthenticationEntryPoint`, với `ServiceProperties` xác định service URL.

**7. Class nào xác minh ticket?**  
`CasAuthenticationProvider` gọi `TicketValidator`, ví dụ `Cas20ServiceTicketValidator`, kết nối CAS qua HTTPS.

**8. CAS success có tự cấp quyền đọc mọi đơn hàng không?**  
Không. Local account, tenant và resource authorization là trách nhiệm ứng dụng.

**9. `renew=true` khác `gateway=true` thế nào?**  
Renew yêu cầu primary credentials mới; gateway không làm gián đoạn và có thể quay về không ticket.

**10. Khi CAS outage, có nên chấp nhận ST vì nó “giống đúng mẫu”?**  
Không. Không có validation thành công thì không cấp Authentication.

**11. Có dùng `spring-security-saml2-service-provider` cho CAS service tickets không?**  
Không. CAS ticket protocol có flow/validator và dependency khác SAML2 Web SSO.

**12. Vì sao proxy/reverse proxy thường gây `INVALID_SERVICE`?**  
Ứng dụng gửi callback URL nội bộ hoặc scheme/port/path khác URL CAS đã dùng cấp ST.

**13. ST sau khi xác minh thành công dùng cho các request sau bằng cách nào?**  
Thông thường không dùng ST nữa; Spring lưu authenticated SecurityContext trong phiên local và dùng session cookie.

**14. CAS server phát username alice ở hai realm có chứng minh cùng một người không?**  
Không; phải có realm/source scope và account linking đã được phê duyệt.

## 20. Checklist production

- [ ] CAS server login URL, validation endpoint và service URL đều là HTTPS được quản trị.
- [ ] CAS service registry chỉ allowlist các service/callback hợp lệ, không dùng wildcard thiếu kiểm soát.
- [ ] Service URL canonical **giống nhau** giữa redirect và `/serviceValidate`.
- [ ] `CasAuthenticationFilter` xử lý đúng callback path, không bypass provider.
- [ ] `CasAuthenticationProvider` gọi TicketValidator thật, không fake success.
- [ ] Không tin `ticket`/`service`/`username`/`casServer` do browser gửi trước validation.
- [ ] ST không bị cache làm bearer token, không retry bừa sau validation/timeout.
- [ ] Parser xử lý CAS XML namespace đúng, chặn XXE/response không hợp lệ.
- [ ] CAS TLS certificate/hostname được xác minh; trust store nội bộ được cấu hình đúng.
- [ ] Có network connect/read timeout, giới hạn response size, backoff/alert khi CAS outage.
- [ ] Không log hoặc lộ ST trong URL Referer, metrics labels, analytics và access logs.
- [ ] Callback redirect tới URL sạch sau success, không load third-party resources trước cleanup.
- [ ] Local user active và authorities phải đến từ nguồn tin cậy, tenant isolation được bảo vệ.
- [ ] Session fixation protection, cookie Secure/HttpOnly/SameSite, CSRF và session timeout được test.
- [ ] Có phân biệt CAS TGT/TGC với local session và chính sách CAS Single Sign Out.
- [ ] Nếu dùng proxy tickets, cần proxy list validation và trust policy riêng.
- [ ] Nếu nhiều CAS realms/tenants, lưu source realm và service scope với username.
- [ ] Chạy test C01–C32 hoặc bộ tương đương trong staging với CAS server thật.
- [ ] Nâng Spring Security/CAS client theo security patches và đối chiếu APIs theo version.
- [ ] Không dùng mẫu code tự viết ở mục 12 thay cho CAS client được kiểm thử/hardened ở production.

## Ghi nhớ

> **Redirect mang ticket đến Portal chỉ là bước chuyển giao credential. Portal phải dùng kênh HTTPS server-to-server gọi CAS để xác minh ticket đúng service, chưa dùng và còn hạn.** Chỉ khi CAS trả kết quả authentication success được kiểm tra, ứng dụng mới ánh xạ sang local account, thiết lập session và cấp quyền phù hợp. **ST dùng một lần; `service` là một ràng buộc bảo mật; browser không phải nguồn chứng minh danh tính.**
