# Đọc tập định danh rồi truy vấn theo nhóm

Trong ứng dụng Spring Data R2DBC, một màn hình thường cần dữ liệu từ nhiều bảng. Ví dụ, trang danh sách đơn hàng cần đọc các đơn hàng trước, sau đó lấy các dòng hàng thuộc từng đơn. Nếu gọi repository một lần cho mỗi đơn hàng, số truy vấn tăng theo số lượng đơn và dễ tạo ra vấn đề N+1 query. Một cách tổ chức hiệu quả hơn là đọc tập định danh của nhóm dữ liệu cần hiển thị, truy vấn dữ liệu liên quan theo từng nhóm ID, rồi ghép kết quả trong bộ nhớ.

Mẫu xử lý này thường gồm hai lượt truy vấn:

1. Lấy danh sách bản ghi cha hoặc tập ID của chúng theo một điều kiện và giới hạn kết quả rõ ràng.
2. Dùng tập ID đó để lấy tất cả bản ghi liên quan trong một truy vấn `IN`, hoặc chia ID thành các lô nhỏ khi tập quá lớn.

Sau đó, ứng dụng nhóm các bản ghi con theo khóa ngoại và kết hợp chúng với bản ghi cha. Đây là cách tải dữ liệu có chủ đích trong mô hình relational; Spring Data R2DBC không tự lazy-load quan hệ như JPA/Hibernate.

## 1. Bài toán và lý do đọc theo nhóm

Giả sử database có hai bảng:

```sql
CREATE TABLE orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    order_code VARCHAR(32) NOT NULL,
    status VARCHAR(20) NOT NULL,
    created_at TIMESTAMP NOT NULL
);

CREATE TABLE order_lines (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL REFERENCES orders(id),
    product_code VARCHAR(40) NOT NULL,
    quantity INTEGER NOT NULL,
    unit_price DECIMAL(19, 2) NOT NULL
);

CREATE INDEX idx_order_lines_order_id ON order_lines(order_id);
```

Một đơn hàng có nhiều dòng hàng. Khi cần hiển thị 30 đơn hàng gần nhất cùng các dòng hàng, có một số cách tiếp cận:

- Đọc đơn hàng, sau đó gọi `findByOrderId(...)` riêng cho từng đơn.
- Join `orders` với `order_lines` trong một câu SQL.
- Đọc danh sách đơn hàng trước, lấy ID của chúng, rồi truy vấn tất cả dòng hàng theo tập ID.

Cách đầu tiên dễ viết nhưng tạo N+1 query: một truy vấn lấy đơn hàng và N truy vấn lấy dòng hàng. Với 30 đơn hàng, ứng dụng có thể thực hiện 31 lượt truy cập database. Độ trễ mạng và chi phí thực thi lặp lại tăng theo số đơn.

Cách đọc theo nhóm thường giảm số lượt truy cập xuống hai: một truy vấn lấy đơn hàng và một truy vấn lấy tất cả dòng hàng có `order_id` thuộc tập ID vừa đọc. Cách này giữ dữ liệu cha và con thành hai luồng kết quả dễ quản lý, đồng thời không làm nhân bản các cột của đơn hàng như join một-nhiều.

```text
N+1 query

Query 1: SELECT orders ...
    |
    +-- Query 2: SELECT order_lines WHERE order_id = 101
    +-- Query 3: SELECT order_lines WHERE order_id = 102
    +-- Query 4: SELECT order_lines WHERE order_id = 103
    `-- ... một query cho mỗi order

Đọc theo nhóm

Query 1: SELECT orders ...
    |
    v
IDs = [101, 102, 103, ...]
    |
    v
Query 2: SELECT order_lines WHERE order_id IN (101, 102, 103, ...)
    |
    v
Group các dòng hàng theo order_id rồi ghép với từng order
```

## 2. Thiết kế entity và repository

### 2.1. Entity biểu diễn khóa ngoại bằng ID

Trong Spring Data Relational, có thể biểu diễn quan hệ giữa hai aggregate bằng khóa ngoại scalar. Ví dụ:

```java
@Table("orders")
public record OrderEntity(
        @Id Long id,
        @Column("customer_id") Long customerId,
        @Column("order_code") String orderCode,
        String status,
        @Column("created_at") Instant createdAt
) {
}
```

```java
@Table("order_lines")
public record OrderLineEntity(
        @Id Long id,
        @Column("order_id") Long orderId,
        @Column("product_code") String productCode,
        Integer quantity,
        @Column("unit_price") BigDecimal unitPrice
) {
}
```

`OrderLineEntity.orderId` giữ ID của đơn hàng sở hữu dòng hàng. Đây là dữ liệu quan hệ trong schema; chỉ khai báo `orderId` không làm Spring Data tự tải `OrderEntity`. Khi cần dữ liệu của cả hai bảng, ứng dụng quyết định truy vấn và cách kết hợp.

### 2.2. Repository lấy nhóm bản ghi cha

```java
public interface OrderRepository
        extends ReactiveCrudRepository<OrderEntity, Long> {

    Flux<OrderEntity> findTop50ByCustomerIdOrderByCreatedAtDescIdDesc(
            Long customerId);
}
```

Ví dụ này giới hạn tập đơn hàng ở tối đa 50 bản ghi gần nhất của một khách hàng. Giới hạn tập cha ngay từ đầu giúp giới hạn số ID cần đưa vào truy vấn thứ hai và lượng dữ liệu phải giữ trong bộ nhớ.

Nếu ứng dụng cần một trang tùy chọn, có thể dùng `R2dbcEntityTemplate` với `Query`/`Criteria`, hoặc một query method/SQL có limit và offset. Cần có thứ tự ổn định, thường thêm khóa chính làm tiêu chí phụ khi trường sort có thể trùng nhau.

### 2.3. Repository lấy bản ghi con theo tập ID

```java
public interface OrderLineRepository
        extends ReactiveCrudRepository<OrderLineEntity, Long> {

    Flux<OrderLineEntity> findByOrderIdInOrderByOrderIdAscIdAsc(
            Collection<Long> orderIds);
}
```

Phần `In` trong derived query biểu diễn điều kiện thuộc tập giá trị, tương ứng với SQL có dạng `WHERE order_id IN (...)`. Repository trả về `Flux` vì một đơn hàng có thể có nhiều dòng hàng và toàn bộ nhóm ID cũng có thể trả về nhiều bản ghi.

Thêm `OrderByOrderIdAscIdAsc` để kết quả có thứ tự xác định theo khóa ngoại rồi theo ID. Việc sắp xếp này hữu ích nếu thứ tự dòng hàng có ý nghĩa hoặc cần kết quả ổn định giữa các lần chạy. Nếu nghiệp vụ có cột `line_number`, nên dùng cột đó thay cho `id` để phản ánh đúng thứ tự hiển thị.

## 3. Thực hiện hai lượt truy vấn và ghép kết quả

### 3.1. Kiểu kết quả cho màn hình

Có thể định nghĩa một DTO chứa đơn hàng cùng các dòng hàng:

```java
public record OrderWithLines(
        OrderEntity order,
        List<OrderLineEntity> lines
) {
}
```

Đây là mô hình kết quả đọc, không nhất thiết là entity được lưu trong database. DTO giúp tầng API hoặc service tiêu thụ một cấu trúc đã được ghép sẵn.

### 3.2. Luồng reactive cơ bản

```java
@Service
public class OrderQueryService {

    private final OrderRepository orderRepository;
    private final OrderLineRepository lineRepository;

    public OrderQueryService(
            OrderRepository orderRepository,
            OrderLineRepository lineRepository) {
        this.orderRepository = orderRepository;
        this.lineRepository = lineRepository;
    }

    public Mono<List<OrderWithLines>> findRecentOrders(Long customerId) {
        return orderRepository
                .findTop50ByCustomerIdOrderByCreatedAtDescIdDesc(customerId)
                .collectList()
                .flatMap(orders -> {
                    if (orders.isEmpty()) {
                        return Mono.just(List.of());
                    }

                    List<Long> orderIds = orders.stream()
                            .map(OrderEntity::id)
                            .distinct()
                            .toList();

                    return lineRepository
                            .findByOrderIdInOrderByOrderIdAscIdAsc(orderIds)
                            .collectMultimap(OrderLineEntity::orderId)
                            .map(linesByOrderId -> orders.stream()
                                    .map(order -> new OrderWithLines(
                                            order,
                                            List.copyOf(linesByOrderId.getOrDefault(
                                                    order.id(), List.of()))))
                                    .toList());
                });
    }
}
```

Luồng thực hiện:

1. Repository phát ra các đơn hàng dưới dạng `Flux<OrderEntity>`.
2. `collectList()` gom tối đa 50 đơn hàng thành một `List`, vì bước sau cần toàn bộ ID của trang hiện tại.
3. Nếu danh sách rỗng, trả về danh sách rỗng ngay và không gọi repository dòng hàng.
4. Lấy ID, loại bỏ trùng lặp và tạo tập tham số cho truy vấn `IN`.
5. `findByOrderIdIn...` lấy tất cả dòng hàng trong một lượt truy vấn nhóm.
6. `collectMultimap(OrderLineEntity::orderId)` nhóm mỗi dòng hàng theo `orderId`.
7. Duyệt danh sách đơn hàng ban đầu và ghép với nhóm dòng hàng tương ứng. Đơn hàng không có dòng hàng nhận một list rỗng.

`collectMultimap` tạo một `Mono` chứa map từ khóa tới collection các giá trị. Bước ghép duyệt lại `orders`, do đó giữ được thứ tự đơn hàng ban đầu. Không nên duyệt trực tiếp các key của map nếu thứ tự cha là một phần của kết quả mong muốn.

### 3.3. Vì sao dùng collectList rồi flatMap?

Truy vấn thứ hai phụ thuộc vào ID do truy vấn thứ nhất phát ra. `collectList()` tạo một publisher chỉ phát danh sách sau khi truy vấn cha hoàn tất. `flatMap` sau đó dùng danh sách này để khởi tạo truy vấn con và nối kết quả vào cùng pipeline.

Không gọi `subscribe()` bên trong service để khởi chạy truy vấn thứ hai. Nếu tự subscribe, service không còn trả về một publisher đại diện cho toàn bộ công việc; tầng gọi có thể nhận kết quả trước khi truy vấn con hoàn tất và khó xử lý lỗi của bước thứ hai.

Không dùng `map` để nối trực tiếp một phương thức repository trả về `Mono` hoặc `Flux`, vì sẽ tạo publisher lồng nhau như `Mono<Flux<OrderLineEntity>>`. `flatMap` hoặc `flatMapMany` mới là toán tử phù hợp khi bước tiếp theo trả về publisher.

## 4. Xử lý tập ID rỗng và dữ liệu không đầy đủ

### 4.1. Không gửi truy vấn IN với danh sách rỗng

Khi không có bản ghi cha, không có lý do truy vấn bản ghi con. Một số dialect/database không chấp nhận cú pháp `IN ()`; ngay cả khi framework xử lý trường hợp này, nhánh rỗng rõ ràng vẫn tránh một lượt truy cập thừa.

```java
if (orderIds.isEmpty()) {
    return Mono.just(List.of());
}
```

### 4.2. Bản ghi cha không có bản ghi con

Map kết quả chỉ có key cho những `orderId` có ít nhất một dòng hàng. Khi ghép, dùng `getOrDefault(order.id(), List.of())` để đơn hàng không có dòng hàng vẫn xuất hiện với danh sách rỗng.

Đây là hành vi khác với inner join: inner join có thể loại đơn hàng không có dòng hàng khỏi kết quả. Nếu yêu cầu nghiệp vụ cần giữ mọi đơn hàng cha, cách ghép trong bộ nhớ hoặc SQL `LEFT JOIN` phải thể hiện đúng điều đó.

### 4.3. ID null và bản ghi chưa được lưu

ID lấy từ entity đã đọc trong database thông thường phải có giá trị. Nếu nguồn ID đến từ object mới chưa lưu, cần xác định rõ có được đưa vào truy vấn nhóm hay không. Không âm thầm loại bỏ ID null nếu điều đó che giấu lỗi trong luồng nghiệp vụ; hãy bảo đảm tập ID đầu vào phản ánh đúng các bản ghi đã tồn tại.

### 4.4. ID trùng lặp

Một tập ID truy vấn thường nên loại trùng để giảm tham số và tránh công việc không cần thiết. Dùng `distinct()` khi tạo danh sách ID. Nếu ID là khóa chính và danh sách cha được truy vấn trực tiếp từ bảng, trùng lặp thường không xảy ra; bước loại trùng vẫn có ích khi ID được tổng hợp từ nhiều nguồn.

## 5. Chia tập ID thành các lô nhỏ

Truy vấn `IN` có giới hạn thực tế. Database hoặc driver có thể giới hạn số tham số bind trong một câu lệnh; tập ID rất lớn cũng làm câu SQL và kế hoạch thực thi nặng hơn. Với vài chục hoặc vài trăm ID, một truy vấn nhóm thường hợp lý. Với hàng nghìn hoặc hàng chục nghìn ID, hãy chia thành các batch.

### 5.1. Hàm chia danh sách

```java
private static <T> List<List<T>> partition(List<T> values, int batchSize) {
    if (batchSize <= 0) {
        throw new IllegalArgumentException("batchSize must be positive");
    }

    List<List<T>> batches = new ArrayList<>();
    for (int start = 0; start < values.size(); start += batchSize) {
        int end = Math.min(start + batchSize, values.size());
        batches.add(List.copyOf(values.subList(start, end)));
    }
    return batches;
}
```

Hàm này tạo các batch không vượt quá `batchSize`. `List.copyOf` tạo bản sao không thể sửa qua list trả về, giúp tránh việc một batch bị thay đổi trong khi query đang sử dụng nó.

### 5.2. Truy vấn từng batch theo thứ tự

```java
private Flux<OrderLineEntity> findLinesInBatches(List<Long> orderIds) {
    return Flux.fromIterable(partition(orderIds, 500))
            .concatMap(lineRepository::findByOrderIdInOrderByOrderIdAscIdAsc);
}
```

`concatMap` đợi batch hiện tại hoàn tất trước khi chuyển sang batch tiếp theo. Cách này giữ số truy vấn đang chạy ở mức thấp và dễ dự đoán tải database. Nếu các batch độc lập và database còn khả năng xử lý song song, có thể dùng `flatMap` với giới hạn concurrency rõ ràng:

```java
return Flux.fromIterable(partition(orderIds, 500))
        .flatMap(lineRepository::findByOrderIdInOrderByOrderIdAscIdAsc, 4);
```

Tham số `4` giới hạn số batch được xử lý đồng thời. Không dùng concurrency không giới hạn cho một tập ID lớn vì có thể làm cạn connection pool hoặc gây tải đột biến lên database.

### 5.3. Nhóm kết quả sau nhiều batch

Sau khi các batch hoàn tất, vẫn có thể gom tất cả dòng hàng và nhóm theo `orderId`:

```java
return findLinesInBatches(orderIds)
        .collectMultimap(OrderLineEntity::orderId);
```

Kết quả cuối cùng vẫn là một map dùng để ghép với danh sách cha. Thứ tự hoàn tất batch có thể khác nhau nếu dùng `flatMap` song song; nếu thứ tự dòng hàng quan trọng, hãy sort theo khóa trong repository, sắp xếp lại sau khi thu thập hoặc dùng `concatMap`.

### 5.4. Chọn batch size

Không có một con số phù hợp cho mọi database. Cần cân nhắc:

- Giới hạn số bind parameter của database/driver.
- Độ dài câu lệnh SQL được tạo ra.
- Kích thước dữ liệu mỗi hàng và tổng dữ liệu trả về.
- Connection pool và số truy vấn đồng thời.
- Độ trễ mạng và thời gian thực thi của mỗi batch.
- Khả năng tận dụng index trên cột khóa ngoại.

Hãy bắt đầu với một batch size thận trọng, đo thời gian và tải database, sau đó điều chỉnh bằng số liệu. Batch size chỉ kiểm soát số ID trong mỗi câu truy vấn; nó không thay thế giới hạn tổng số bản ghi mà use case được phép tải.

## 6. Dữ liệu rất lớn: phân trang cha thay vì thu thập tất cả ID

Không nên lấy hàng triệu ID vào một `List` chỉ để thực hiện một truy vấn `IN`. Khi dữ liệu lớn, chia công việc thành từng trang cha:

1. Đọc một trang đơn hàng có giới hạn.
2. Lấy ID của trang đó.
3. Truy vấn các dòng hàng theo ID của trang.
4. Ghép và xử lý hoặc phát kết quả của trang.
5. Chuyển sang trang kế tiếp.

Ví dụ dùng query method giới hạn số bản ghi:

```java
Flux<OrderEntity> findTop100ByStatusOrderByIdAsc(String status);
```

Với luồng xử lý dài, có thể dùng keyset pagination để lấy trang kế tiếp dựa trên khóa cuối của trang trước. Keyset thường ổn định và tránh chi phí offset lớn khi dữ liệu tăng.

Nếu chỉ cần xử lý dữ liệu chứ không cần giữ toàn bộ kết quả để trả HTTP, hãy xử lý từng trang trong pipeline và giải phóng bộ nhớ sau mỗi trang. Nếu cần trả về một response chứa tất cả dữ liệu, hãy xác định giới hạn tổng kết quả rõ ràng; không biến một endpoint danh sách thành thao tác tải không giới hạn.

## 7. Truy vấn theo nhóm bằng DatabaseClient

Derived query `findByOrderIdIn(...)` phù hợp với truy vấn một bảng đơn giản. Nếu cần SQL tùy chỉnh, có thể dùng `DatabaseClient` với tham số danh sách.

```java
Flux<OrderLineEntity> findByOrderIds(Collection<Long> orderIds) {
    if (orderIds.isEmpty()) {
        return Flux.empty();
    }

    return databaseClient.sql("""
            SELECT id, order_id, product_code, quantity, unit_price
            FROM order_lines
            WHERE order_id IN (:orderIds)
            ORDER BY order_id, id
            """)
            .bind("orderIds", orderIds)
            .map((row, metadata) -> new OrderLineEntity(
                    row.get("id", Long.class),
                    row.get("order_id", Long.class),
                    row.get("product_code", String.class),
                    row.get("quantity", Integer.class),
                    row.get("unit_price", BigDecimal.class)))
            .all();
}
```

Named parameter expansion của Spring R2DBC DatabaseClient có thể mở rộng một collection thành các bind marker tương ứng trong câu `IN`, tùy API và phiên bản đang dùng. Cần kiểm tra hỗ trợ của phiên bản Spring Framework/driver trong dự án. Không tự nối các ID thành chuỗi SQL để thay thế việc bind tham số.

Nếu dùng API bind thấp hơn hoặc driver không hỗ trợ cách mở rộng mong muốn, có thể tạo placeholder theo số lượng phần tử bằng cơ chế tham số an toàn của framework hoặc dùng derived query. Mọi giá trị ID vẫn phải được bind; không đưa dữ liệu đầu vào vào SQL bằng string concatenation.

## 8. Khi nào nên dùng JOIN thay vì đọc ID rồi truy vấn nhóm?

Đọc theo nhóm không phải lúc nào cũng tốt hơn join. Hai cách giải quyết cùng một nhu cầu nhưng có đặc tính khác nhau.

### 8.1. JOIN trong một câu truy vấn

```sql
SELECT o.id AS order_id,
       o.order_code,
       o.status,
       l.id AS line_id,
       l.product_code,
       l.quantity,
       l.unit_price
FROM orders o
LEFT JOIN order_lines l ON l.order_id = o.id
WHERE o.customer_id = :customerId
ORDER BY o.created_at DESC, o.id DESC, l.id ASC
```

Ưu điểm là database thực hiện join trong một câu lệnh và ứng dụng chỉ có một lượt truy cập. Nhược điểm là thông tin của đơn hàng bị lặp lại trên mỗi dòng hàng. Code cần gom các hàng join thành cấu trúc cha-con; nếu có nhiều quan hệ một-nhiều trong cùng truy vấn, số hàng có thể nhân lên đáng kể.

### 8.2. Hai lượt truy vấn theo ID

Truy vấn cha trả về một hàng cho mỗi đơn hàng. Truy vấn con trả về một hàng cho mỗi dòng hàng. Ứng dụng nhóm các dòng hàng theo `orderId` rồi ghép vào từng đơn.

Ưu điểm:

- Tránh lặp lại cột cha trên từng hàng con.
- Dễ kiểm soát giới hạn tập cha trước khi tải dữ liệu liên quan.
- Có thể tái sử dụng Repository riêng cho từng aggregate/bảng.
- Dễ xử lý các nhóm con độc lập và gắn nhiều tập kết quả vào cùng cha.

Nhược điểm:

- Có ít nhất hai lượt truy cập database.
- Ứng dụng phải giữ dữ liệu cha và nhóm con trong bộ nhớ để ghép.
- Hai truy vấn có thể quan sát trạng thái database khác nhau nếu không có transaction/isolation phù hợp.

### 8.3. Bảng lựa chọn

| Tình huống | Cách thường phù hợp |
|---|---|
| Một trang cha nhỏ, mỗi cha có một nhóm con | Đọc ID rồi query nhóm |
| Cần nhiều nhóm con độc lập cho cùng tập cha | Query từng nhóm theo ID rồi ghép |
| Cần lọc/sắp xếp theo cột của nhiều bảng | JOIN/SQL tùy chỉnh |
| Cần aggregate hoặc báo cáo trên nhiều bảng | JOIN, GROUP BY hoặc CTE |
| Tập cha rất lớn | Phân trang cha, xử lý từng batch |
| Chỉ cần một số cột và database có thể xử lý tốt | Projection hoặc SQL join |
| Cần giữ mọi cha kể cả khi không có con | LEFT JOIN hoặc ghép nhóm với list rỗng |

Không nên chọn dựa trên số câu SQL đơn thuần. Hãy xem lượng dữ liệu truyền về, số hàng trung gian, execution plan, index và độ phức tạp của việc ghép kết quả.

## 9. Đọc nhiều nhóm dữ liệu cho cùng một tập cha

Một màn hình có thể cần dòng hàng, lịch sử trạng thái và ghi chú cho cùng một danh sách đơn hàng. Có thể lấy ID cha một lần rồi chạy một truy vấn nhóm cho mỗi loại dữ liệu:

```java
return orderRepository.findTop50ByCustomerIdOrderByCreatedAtDescIdDesc(customerId)
        .collectList()
        .flatMap(orders -> {
            if (orders.isEmpty()) {
                return Mono.just(List.of());
            }

            List<Long> ids = orders.stream()
                    .map(OrderEntity::id)
                    .distinct()
                    .toList();

            Mono<Map<Long, Collection<OrderLineEntity>>> linesMono =
                    lineRepository.findByOrderIdIn(ids)
                            .collectMultimap(OrderLineEntity::orderId);

            Mono<Map<Long, Collection<OrderStatusHistory>>> historyMono =
                    historyRepository.findByOrderIdIn(ids)
                            .collectMultimap(OrderStatusHistory::orderId);

            return Mono.zip(linesMono, historyMono)
                    .map(data -> orders.stream()
                            .map(order -> new OrderDetailView(
                                    order,
                                    List.copyOf(data.getT1().getOrDefault(
                                            order.id(), List.of())),
                                    List.copyOf(data.getT2().getOrDefault(
                                            order.id(), List.of()))))
                            .toList());
        });
```

`Mono.zip` kết hợp kết quả của hai truy vấn độc lập. Chúng có thể được subscribe cùng lúc; số truy vấn song song cần phù hợp với connection pool và tải database. Nếu cần tuần tự, có thể nối bằng `flatMap` hoặc `then` theo cấu trúc phù hợp. Khi một truy vấn lỗi, lỗi truyền qua publisher tổng hợp; không nên nuốt lỗi rồi trả về dữ liệu thiếu mà không có quy tắc nghiệp vụ rõ ràng.

Đoạn code minh họa cần có các repository và DTO tương ứng. Nếu một trong các nhóm không có bản ghi, `collectMultimap` vẫn phát map rỗng, nên `getOrDefault` cung cấp list rỗng cho nhóm đó.

## 10. Transaction và tính nhất quán giữa các lượt đọc

Khi đọc cha rồi đọc con bằng hai truy vấn riêng, dữ liệu có thể thay đổi giữa hai lượt. Ví dụ, một dòng hàng bị xóa sau khi truy vấn đơn hàng nhưng trước khi truy vấn dòng hàng. Kết quả ghép khi đó phản ánh hai thời điểm khác nhau.

Nếu use case chấp nhận đọc dữ liệu gần thời điểm nhau, có thể không cần transaction dài. Nếu cần một snapshot nhất quán, hãy xem xét reactive transaction và isolation level phù hợp với database.

Ví dụ khai báo transaction ở Service:

```java
@Transactional(readOnly = true)
public Mono<List<OrderWithLines>> findRecentOrders(Long customerId) {
    // Pipeline truy vấn cha, lấy ID, truy vấn con và ghép kết quả.
}
```

Transaction reactive sử dụng Reactor Context để truyền transaction qua pipeline. Cần giữ các thao tác trong cùng pipeline, không tự gọi `subscribe()` hoặc tách công việc thành một luồng độc lập nếu nó cần tham gia transaction.

`readOnly = true` thể hiện ý định chỉ đọc và có thể được hỗ trợ tùy transaction manager/database; nó không tự bảo đảm snapshot isolation. Mức nhất quán thực tế phụ thuộc isolation level của transaction và hệ quản trị. Hãy chọn mức phù hợp với yêu cầu, vì isolation cao hơn có thể ảnh hưởng concurrency và thời gian giữ tài nguyên.

## 11. Index, dữ liệu và hiệu năng

Truy vấn nhóm thường có dạng:

```sql
SELECT ...
FROM order_lines
WHERE order_id IN (...)
ORDER BY order_id, id
```

Các yếu tố ảnh hưởng hiệu năng:

- **Index khóa ngoại:** index trên `order_lines(order_id)` giúp tìm các dòng hàng theo nhóm ID.
- **Số lượng ID:** tập ID càng lớn, câu lệnh và số bind marker càng lớn.
- **Số dòng con mỗi cha:** một trang 50 đơn có thể trả về hàng chục nghìn dòng nếu mỗi đơn có nhiều dòng.
- **Projection:** chỉ chọn các cột cần dùng để giảm dữ liệu truyền và materialize.
- **Sort:** index phù hợp có thể giúp truy vấn trả kết quả theo thứ tự cần thiết.
- **Batch concurrency:** chạy nhiều batch đồng thời có thể tăng thông lượng nhưng cũng có thể gây cạnh tranh connection.

Không nên chỉ giới hạn số đơn hàng cha mà bỏ qua khả năng mỗi đơn có số dòng con rất lớn. Có thể cần giới hạn hoặc phân trang riêng cho dòng hàng, hoặc cung cấp một endpoint chi tiết riêng khi người dùng mở một đơn hàng.

Hãy đo bằng dữ liệu có kích thước gần thực tế, xem execution plan và theo dõi số kết nối, thời gian truy vấn, số hàng trả về. Một query `IN` có index tốt thường hiệu quả, nhưng không có bảo đảm rằng một batch cực lớn luôn nhanh hơn nhiều batch nhỏ.

## 12. Các lỗi thường gặp

### Gọi repository một lần cho mỗi bản ghi cha

Đây là N+1 query. Gom ID của nhóm cha và lấy toàn bộ dữ liệu con trong một truy vấn hoặc một số batch có giới hạn.

### Truy vấn tập con khi danh sách ID rỗng

Không có ID thì không cần truy vấn. Trả kết quả rỗng ngay để tránh `IN ()` và một lượt database thừa.

### Không nhóm kết quả theo khóa ngoại

Sau khi lấy tất cả dòng con, cần tạo map theo `orderId` hoặc khóa tương ứng. Nếu chỉ trả một list phẳng, tầng gọi lại phải tự tìm kiếm và có thể tạo vòng lặp lồng nhau tốn kém.

### Làm mất thứ tự của danh sách cha

Map không phải cấu trúc dùng để đại diện thứ tự cha. Khi ghép, duyệt danh sách cha ban đầu và tra map theo ID. Nếu thứ tự con quan trọng, sắp xếp con theo cột nghiệp vụ.

### Đưa quá nhiều ID vào một câu IN

Database/driver có giới hạn tham số và câu SQL rất lớn có thể chậm. Chia thành batch, xử lý có giới hạn concurrency hoặc phân trang cha.

### Dùng flatMap không giới hạn cho nhiều batch

Điều này có thể mở quá nhiều truy vấn đồng thời và làm cạn connection pool. Dùng `concatMap` tuần tự hoặc `flatMap` với concurrency được đặt rõ ràng.

### Dùng block hoặc subscribe trong Service

Các thao tác cần được nối trong pipeline reactive bằng `flatMap`, `map`, `zip` và các toán tử phù hợp. `block()` có thể chặn luồng; `subscribe()` nội bộ làm tầng gọi mất quyền kiểm soát hoàn tất và lỗi.

### Không có index trên khóa ngoại

Truy vấn `IN` có thể quét toàn bảng nếu cột `order_id` không có index phù hợp. Kiểm tra execution plan và index trên cột dùng để nhóm.

### Nhầm đọc theo nhóm với SQL GROUP BY

Đọc theo nhóm ID là chiến lược lấy dữ liệu theo một tập khóa rồi nhóm kết quả trong ứng dụng. SQL `GROUP BY` là phép tổng hợp hàng trong database. Hai khái niệm có thể được kết hợp nhưng không phải một.

### Không xem xét tính nhất quán giữa hai truy vấn

Nếu dữ liệu thay đổi giữa lượt đọc cha và con, kết quả ghép có thể không phải snapshot đồng nhất. Dùng transaction/isolation phù hợp nếu nghiệp vụ yêu cầu.

## 13. Quy trình áp dụng

1. Xác định bản ghi cha và các tập dữ liệu con cần hiển thị.
2. Xác định khóa ngoại hoặc ID liên kết giữa các bảng.
3. Đọc tập cha có điều kiện lọc, sort và giới hạn rõ ràng.
4. Xử lý trường hợp tập cha rỗng trước khi gọi repository con.
5. Trích xuất ID, loại bỏ trùng và kiểm tra ID hợp lệ.
6. Truy vấn bản ghi con theo tập ID bằng derived query `In`, Template hoặc SQL có bind parameter.
7. Nếu tập ID lớn, chia batch và kiểm soát concurrency.
8. Nhóm kết quả con theo khóa ngoại bằng `collectMultimap` hoặc cấu trúc map phù hợp.
9. Ghép bằng cách duyệt danh sách cha ban đầu để giữ thứ tự và tạo collection rỗng cho cha không có con.
10. Cân nhắc transaction/isolation khi hai lượt đọc cần tính nhất quán.
11. Kiểm tra index, số hàng trả về, memory footprint và thời gian truy vấn.
12. Kiểm thử trường hợp rỗng, nhiều con, ID trùng, batch ranh giới và dữ liệu thay đổi đồng thời.
