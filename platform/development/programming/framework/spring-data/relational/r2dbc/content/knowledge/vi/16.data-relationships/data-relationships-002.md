# Đọc và ghi quan hệ một-nhiều một cách tường minh

## 1. Quan hệ một-nhiều trong Spring Data Relational R2DBC

Quan hệ một-nhiều (one-to-many) xuất hiện khi một đối tượng cha quản lý nhiều đối tượng con. Ví dụ, một đơn hàng có nhiều dòng hàng, một khách hàng có nhiều địa chỉ giao hàng hoặc một bài viết có nhiều bình luận.

Trong Spring Data Relational, quan hệ một-nhiều thường được mô hình hóa trong ranh giới một **aggregate**. Đối tượng cha là **aggregate root**; các đối tượng con thuộc về aggregate và được truy cập thông qua root. Annotation `@MappedCollection` mô tả collection được lưu ở một bảng riêng và liên kết với root bằng khóa ngoại.

Ví dụ:

- `PurchaseOrder` là aggregate root.
- `OrderLine` là đối tượng con thuộc đơn hàng.
- Một `PurchaseOrder` có thể có nhiều `OrderLine`.
- Mỗi `OrderLine` thuộc về đúng một `PurchaseOrder`.

Trong mô hình này, ứng dụng tải và lưu `PurchaseOrder` thông qua repository của root. Không cần tạo repository riêng cho `OrderLine` nếu dòng hàng không có vòng đời độc lập.

Spring Data Relational dùng mô hình ánh xạ aggregate, không phải mô hình persistence context của JPA. Không nên kỳ vọng các annotation `@OneToMany`, `@ManyToOne`, lazy loading hoặc cascade của JPA hoạt động trong Spring Data R2DBC. Quan hệ cần được khai báo theo mapping của Spring Data Relational và được đọc/ghi theo cách tường minh.

## 2. Thiết kế bảng cho quan hệ một-nhiều

Giả sử cần lưu đơn hàng và các dòng hàng. Schema PostgreSQL có thể được thiết kế như sau:

```sql
CREATE TABLE purchase_order (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_number VARCHAR(40) NOT NULL UNIQUE,
    status VARCHAR(20) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE order_line (
    order_id BIGINT NOT NULL,
    line_no INTEGER NOT NULL,
    product_id BIGINT NOT NULL,
    quantity INTEGER NOT NULL,
    unit_price NUMERIC(19, 2) NOT NULL,
    CONSTRAINT pk_order_line PRIMARY KEY (order_id, line_no),
    CONSTRAINT fk_order_line_order
        FOREIGN KEY (order_id) REFERENCES purchase_order(id)
);

CREATE INDEX ix_order_line_product_id ON order_line(product_id);
```

Trong schema này:

- `purchase_order.id` là khóa chính của aggregate root.
- `order_line.order_id` là khóa ngoại trỏ về đơn hàng.
- `line_no` lưu vị trí của dòng hàng trong danh sách của đơn hàng.
- Khóa chính kép `(order_id, line_no)` bảo đảm mỗi đơn hàng không có hai dòng ở cùng vị trí.
- `product_id` là định danh tham chiếu tới sản phẩm; ví dụ này không nhúng toàn bộ aggregate `Product` vào đơn hàng.

Khóa ngoại đảm bảo không thể có dòng hàng tham chiếu tới đơn hàng không tồn tại. Nếu cần xóa các dòng hàng tự động khi xóa đơn hàng, có thể cân nhắc `ON DELETE CASCADE`, nhưng cần chọn chính sách xóa phù hợp với yêu cầu lưu trữ lịch sử. Với dữ liệu đơn hàng, nhiều hệ thống không cho xóa vật lý đơn hàng đã phát sinh giao dịch.

## 3. Ánh xạ collection bằng @MappedCollection

Spring Data Relational cung cấp `@MappedCollection` để ánh xạ thuộc tính collection của aggregate root tới một bảng khác.

Ví dụ root:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

import java.util.ArrayList;
import java.util.List;

@Table("purchase_order")
public class PurchaseOrder {

    @Id
    private Long id;

    private String orderNumber;

    private String status;

    @MappedCollection(idColumn = "order_id", keyColumn = "line_no")
    private List<OrderLine> lines = new ArrayList<>();

    protected PurchaseOrder() {
    }

    public PurchaseOrder(String orderNumber) {
        this.orderNumber = orderNumber;
        this.status = "DRAFT";
    }

    public Long getId() {
        return id;
    }

    public List<OrderLine> getLines() {
        return List.copyOf(lines);
    }

    public void addLine(Long productId, int quantity, BigDecimal unitPrice) {
        if (!"DRAFT".equals(status)) {
            throw new IllegalStateException("Only draft orders can be changed");
        }
        if (quantity <= 0) {
            throw new IllegalArgumentException("Quantity must be positive");
        }
        if (unitPrice == null || unitPrice.signum() < 0) {
            throw new IllegalArgumentException("Unit price must not be negative");
        }

        lines.add(new OrderLine(productId, quantity, unitPrice));
    }

    public void removeLine(int lineIndex) {
        if (!"DRAFT".equals(status)) {
            throw new IllegalStateException("Only draft orders can be changed");
        }
        if (lineIndex < 0 || lineIndex >= lines.size()) {
            throw new IndexOutOfBoundsException("Invalid order line index");
        }

        lines.remove(lineIndex);
    }
}
```

Đối tượng con:

```java
import org.springframework.data.relational.core.mapping.Table;

import java.math.BigDecimal;

@Table("order_line")
public class OrderLine {

    private Long productId;
    private Integer quantity;
    private BigDecimal unitPrice;

    protected OrderLine() {
    }

    public OrderLine(Long productId, Integer quantity, BigDecimal unitPrice) {
        this.productId = productId;
        this.quantity = quantity;
        this.unitPrice = unitPrice;
    }

    public Long getProductId() {
        return productId;
    }

    public Integer getQuantity() {
        return quantity;
    }

    public BigDecimal getUnitPrice() {
        return unitPrice;
    }
}
```

Trong ví dụ, `OrderLine` không có ID độc lập. Khóa nhận diện dòng con được tạo từ khóa của root và key của collection. Nếu dùng `List`, `keyColumn = "line_no"` lưu vị trí phần tử trong danh sách. Tên cột trong annotation phải khớp schema thực tế.

`idColumn = "order_id"` chỉ định cột trong bảng con chứa ID của aggregate root. `keyColumn = "line_no"` chỉ định cột lưu khóa/vị trí của phần tử trong collection. Với `Map`, key column có thể lưu khóa của map; với collection không cần thứ tự, thiết kế khóa và mapping phải phù hợp kiểu collection.

### 3.1. Vì sao dùng List và keyColumn?

`List` có thứ tự. Nếu thứ tự dòng hàng có ý nghĩa, cột `line_no` cho phép lưu vị trí. Ví dụ:

| order_id | line_no | product_id | quantity |
| ---: | ---: | ---: | ---: |
| 1001 | 0 | 501 | 2 |
| 1001 | 1 | 502 | 1 |
| 1001 | 2 | 503 | 4 |

Khi aggregate được đọc lại, mapping sử dụng key column để khôi phục collection theo khóa/vị trí. Hãy kiểm tra câu SQL và quy tắc thứ tự của phiên bản Spring Data Relational đang dùng nếu ứng dụng phụ thuộc vào thứ tự ổn định. Nếu thứ tự là dữ liệu nghiệp vụ lâu dài, có thể lưu một thuộc tính `position` rõ ràng trong đối tượng con thay vì chỉ dựa vào index của `List`.

Nếu thứ tự không quan trọng, có thể cân nhắc `Set`. Tuy nhiên, phải chọn khóa cho các phần tử sao cho không có hai phần tử bị nhầm là một; không nên dựa vào thứ tự trả về mặc định của database.

### 3.2. Tên bảng và cột

`@Table("purchase_order")` và `@Table("order_line")` làm rõ tên bảng. `@Column` có thể dùng khi tên thuộc tính Java khác tên cột SQL:

```java
@Column("product_id")
private Long productId;

@Column("unit_price")
private BigDecimal unitPrice;
```

Tên cột trong `idColumn` và `keyColumn` cũng là tên vật lý ở bảng con. Cần thống nhất naming strategy, annotation và DDL; một lỗi sai tên cột có thể khiến truy vấn đọc/ghi thất bại khi runtime.

## 4. Khai báo repository cho aggregate root

Repository được tạo cho `PurchaseOrder`, không phải cho từng `OrderLine`:

```java
import org.springframework.data.repository.reactive.ReactiveCrudRepository;

public interface PurchaseOrderRepository
        extends ReactiveCrudRepository<PurchaseOrder, Long> {
}
```

Spring Data sử dụng mapping metadata của root để biết collection `lines` được lưu ở bảng `order_line` và liên kết bằng `order_id`. Repository root là cổng truy cập cho aggregate.

Không cần khai báo:

```java
// Không cần nếu OrderLine chỉ là thành phần của PurchaseOrder aggregate
public interface OrderLineRepository
        extends ReactiveCrudRepository<OrderLine, Long> {
}
```

Trong ví dụ `OrderLine` không có ID riêng, vì vậy một repository CRUD độc lập cho nó cũng không phản ánh đúng mô hình. Nếu dòng hàng cần được tìm, sửa, xóa và quản lý vòng đời độc lập, cần xem xét biến nó thành aggregate root riêng với ID riêng.

## 5. Đọc aggregate một-nhiều bằng repository

Khi đọc một aggregate root, Spring Data Relational ánh xạ các thành phần thuộc aggregate theo metadata. Ví dụ:

```java
public Mono<PurchaseOrder> getOrder(Long orderId) {
    return purchaseOrderRepository.findById(orderId);
}
```

Publisher trả về một `PurchaseOrder` nếu đơn hàng tồn tại. Collection `lines` được nạp như một phần của aggregate; nếu không có dòng hàng, collection sẽ rỗng theo cách khởi tạo/mapping của entity.

Sử dụng:

```java
public Mono<OrderDetails> getOrderDetails(Long orderId) {
    return purchaseOrderRepository.findById(orderId)
            .switchIfEmpty(Mono.error(new OrderNotFoundException(orderId)))
            .map(order -> new OrderDetails(
                    order.getId(),
                    order.getOrderNumber(),
                    order.getStatus(),
                    order.getLines()));
}
```

Điểm quan trọng là ứng dụng đọc root và nhận collection theo mapping. Không cần tự gọi một repository con cho từng dòng hàng nếu chúng thuộc cùng aggregate.

### 5.1. Không có lazy loading như JPA

Spring Data Relational không dùng persistence context và proxy lazy loading theo kiểu JPA. Khi aggregate được tải, các thành phần được ánh xạ của aggregate được tải theo cơ chế của Spring Data. Không nên viết code với kỳ vọng truy cập `order.getLines()` sẽ phát sinh truy vấn database bất đồng bộ ở thời điểm getter được gọi.

Do đó:

- Repository trả về publisher cho quá trình đọc aggregate.
- Getter của collection chỉ truy cập dữ liệu đã được ánh xạ trong object.
- Nếu cần một truy vấn chỉ lấy một phần collection hoặc một projection, hãy khai báo truy vấn đọc riêng.
- Không thể dựa vào `FetchType.LAZY` hoặc `FetchType.EAGER` của JPA trong Spring Data R2DBC.

### 5.2. Đọc nhiều aggregate và chi phí truy vấn

`findAll()` có thể trả nhiều root. Khi mỗi root có collection con, việc đọc nhiều aggregate có thể tạo thêm truy vấn để nạp các thành phần phụ thuộc. Chi phí cụ thể phụ thuộc implementation và phiên bản Spring Data Relational.

Với bảng lớn, hãy quan sát SQL thực tế và số lần truy vấn. Không nên giả định `findAll()` luôn chỉ tạo một câu SELECT JOIN duy nhất hoặc không có chi phí đọc collection. Nếu màn hình chỉ cần một số cột, dùng projection hoặc truy vấn JOIN riêng có thể hiệu quả hơn.

## 6. Ghi mới root cùng các phần tử con

Khi tạo một aggregate mới, hãy tạo root và thêm các phần tử con thông qua domain method:

```java
public Mono<PurchaseOrder> createOrder(
        PurchaseOrderRepository repository,
        String orderNumber) {

    PurchaseOrder order = new PurchaseOrder(orderNumber);
    order.addLine(501L, 2, new BigDecimal("125.00"));
    order.addLine(502L, 1, new BigDecimal("75.50"));

    return repository.save(order);
}
```

Spring Data thực hiện việc ghi root và các collection được ánh xạ theo aggregate mapping. Nếu ID của root do database sinh, framework cần lấy ID đó để ghi các hàng con với `order_id` tương ứng.

Kết quả `save` là publisher của aggregate đã lưu. Hãy dùng root được phát ra để lấy ID và trạng thái sau lưu:

```java
return repository.save(order)
        .map(saved -> saved.getId());
```

Không đọc `order.getId()` ngay sau khi gọi `save` rồi giả định ID đã được sinh; publisher cần được subscribe và hoàn tất thao tác ghi trước.

### 6.1. Câu lệnh SQL minh họa

Với schema đã nêu, thao tác lưu một đơn hàng mới về mặt logic cần:

1. Insert một hàng vào `purchase_order`.
2. Nhận ID của đơn hàng nếu database sinh ID.
3. Insert mỗi `OrderLine` vào `order_line` với `order_id` bằng ID root.
4. Ghi `line_no` theo vị trí phần tử trong collection.

SQL minh họa:

```sql
INSERT INTO purchase_order (order_number, status)
VALUES ('PO-2026-001', 'DRAFT')
RETURNING id;

INSERT INTO order_line (order_id, line_no, product_id, quantity, unit_price)
VALUES (1001, 0, 501, 2, 125.00);

INSERT INTO order_line (order_id, line_no, product_id, quantity, unit_price)
VALUES (1001, 1, 502, 1, 75.50);
```

Đây là minh họa cho ý nghĩa dữ liệu, không phải cam kết Spring Data sẽ phát chính xác chuỗi câu lệnh như trên. Câu lệnh thực tế, cách bind và thứ tự thực thi phụ thuộc mapping metadata, dialect, driver và phiên bản Spring Data R2DBC.

## 7. Cập nhật aggregate và collection

Giả sử cần thêm một dòng hàng vào đơn hàng đã tồn tại. Cách làm theo aggregate là tải root, gọi domain method, rồi lưu lại root:

```java
@Service
public class OrderService {

    private final PurchaseOrderRepository repository;

    public OrderService(PurchaseOrderRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public Mono<PurchaseOrder> addLine(
            Long orderId,
            Long productId,
            int quantity,
            BigDecimal unitPrice) {

        return repository.findById(orderId)
                .switchIfEmpty(Mono.error(new OrderNotFoundException(orderId)))
                .flatMap(order -> {
                    order.addLine(productId, quantity, unitPrice);
                    return repository.save(order);
                });
    }
}
```

`addLine` đặt quy tắc nghiệp vụ trong root. Service điều phối thao tác đọc và lưu. Transaction reactive giúp việc thay đổi root và collection tham gia cùng đơn vị commit/rollback nếu transaction manager và `ConnectionFactory` được cấu hình phù hợp.

### 7.1. Xóa một phần tử con

Tương tự, để bỏ một dòng hàng:

```java
@Transactional
public Mono<PurchaseOrder> removeLine(Long orderId, int lineIndex) {
    return repository.findById(orderId)
            .switchIfEmpty(Mono.error(new OrderNotFoundException(orderId)))
            .flatMap(order -> {
                order.removeLine(lineIndex);
                return repository.save(order);
            });
}
```

Khi collection được lưu lại, Spring Data Relational đồng bộ các hàng con theo chiến lược persistence của aggregate. Không nên giả định framework luôn phát hiện một diff nhỏ và chỉ chạy một DELETE cho đúng dòng bị bỏ. Với collection được quản lý như một phần của aggregate, việc lưu root có thể thay thế các hàng con hiện tại bằng tập hàng con mới; hãy xem SQL thực tế của phiên bản đang dùng.

Điều này có hệ quả về hiệu năng: nếu một aggregate có hàng nghìn phần tử con mà mỗi lần thay đổi một phần tử đều phải xử lý lại toàn bộ collection, mô hình có thể quá lớn. Hãy cân nhắc giới hạn kích thước aggregate hoặc tách phần tử con thành aggregate riêng khi chúng có vòng đời độc lập.

### 7.2. Cập nhật một thuộc tính của dòng hàng

Nếu `OrderLine` vẫn thuộc aggregate `PurchaseOrder`, hãy thay đổi qua root:

```java
public void changeLineQuantity(int lineIndex, int quantity) {
    if (!"DRAFT".equals(status)) {
        throw new IllegalStateException("Only draft orders can be changed");
    }
    if (quantity <= 0) {
        throw new IllegalArgumentException("Quantity must be positive");
    }

    OrderLine current = lines.get(lineIndex);
    lines.set(lineIndex, new OrderLine(
            current.getProductId(),
            quantity,
            current.getUnitPrice()));
}
```

Sau đó lưu root bằng repository. Ví dụ này minh họa cách thay thế phần tử trong collection; trong entity thực tế có thể dùng method trên `OrderLine` nếu object mutable, hoặc tạo bản sao mới nếu object immutable.

## 8. Transaction cho việc ghi root và child

Một aggregate có thể cần nhiều câu SQL: insert/update root, insert/update hàng con và xóa các hàng con đã bỏ. Nếu nghiệp vụ yêu cầu không để lại trạng thái một phần, hãy đặt transaction reactive ở application service.

Ví dụ:

```java
@Transactional
public Mono<PurchaseOrder> createAndSave(PurchaseOrder order) {
    return purchaseOrderRepository.save(order);
}
```

Transaction manager R2DBC quản lý connection và transaction context. Các thao tác persistence phải tham gia cùng reactive context để được commit hoặc rollback cùng nhau.

Không gọi `subscribe()` độc lập bên trong phương thức `@Transactional`. Hãy trả publisher để Spring quản lý vòng đời transaction. Nếu một bước ghi hàng con lỗi sau khi root đã được insert, transaction phù hợp sẽ giúp rollback toàn bộ thay đổi thay vì để lại root không có đủ collection theo nghiệp vụ.

Không nên giữ transaction mở trong khi chờ gọi HTTP hoặc một dịch vụ từ xa. Transaction R2DBC chỉ bảo đảm phạm vi database được quản lý; nó không tự tạo transaction phân tán qua mạng.

## 9. Khác biệt giữa child thuộc aggregate và aggregate tham chiếu nhau

Không phải mọi quan hệ một-nhiều ở database đều nên dùng `@MappedCollection`.

### 9.1. Child thuộc vòng đời của root

Dùng `@MappedCollection` khi:

- Child chỉ có ý nghĩa trong phạm vi root.
- Child không được quản lý độc lập.
- Các thay đổi child cần tuân theo invariant của root.
- Ứng dụng thường tải và lưu child cùng root.

Ví dụ `OrderLine` chỉ tồn tại trong `PurchaseOrder`. Khi xóa đơn hàng theo chính sách cho phép, các dòng hàng cũng phải được xử lý cùng aggregate.

### 9.2. Đối tượng con thực ra là aggregate độc lập

Giả sử `Customer` có nhiều `Address`, nhưng mỗi địa chỉ có thể được quản lý, chọn mặc định, xác minh và xóa độc lập. Nếu địa chỉ có vòng đời riêng, có thể mô hình hóa `Address` thành aggregate root riêng:

```java
@Table("customer_address")
public class CustomerAddress {

    @Id
    private Long id;

    @Column("customer_id")
    private Long customerId;

    private String street;
    private String city;
    private Boolean defaultAddress;
}
```

```java
public interface CustomerAddressRepository
        extends ReactiveCrudRepository<CustomerAddress, Long> {

    Flux<CustomerAddress> findByCustomerId(Long customerId);
}
```

Ở đây `CustomerAddress` có ID riêng và repository riêng. `Customer` có thể giữ ID hoặc không giữ collection địa chỉ trong object. Use case truy vấn địa chỉ qua `CustomerAddressRepository`.

Nếu một customer có nhiều address nhưng address là aggregate độc lập, việc dùng `@MappedCollection` trong `Customer` sẽ khiến vòng đời address bị gắn chặt vào việc tải/lưu customer. Hãy chọn mô hình dựa trên quy tắc nghiệp vụ, không chỉ dựa vào quan hệ khóa ngoại.

### 9.3. Tham chiếu aggregate khác bằng ID

Một `OrderLine` thường tham chiếu `Product` bằng `productId`:

```java
private Long productId;
```

Đây là tham chiếu logic. Khi đọc `PurchaseOrder`, Spring Data không tự động tải toàn bộ `Product` tương ứng chỉ vì có trường `productId`. Nếu cần tên sản phẩm hiện tại, hãy truy vấn product riêng hoặc dùng truy vấn JOIN/read model. Dữ liệu snapshot như tên sản phẩm và đơn giá tại thời điểm mua có thể được lưu trong dòng hàng nếu nghiệp vụ lịch sử yêu cầu.

## 10. Đọc dữ liệu quan hệ bằng JOIN khi cần read model

Repository aggregate phù hợp khi cần tải root và các thành phần thuộc aggregate. Nhưng màn hình báo cáo có thể cần dữ liệu kết hợp từ nhiều bảng hoặc chỉ một vài cột. Khi đó, `DatabaseClient` có thể thực hiện JOIN và ánh xạ projection.

Ví dụ DTO:

```java
public record OrderLineView(
        Long orderId,
        String orderNumber,
        String status,
        Integer lineNo,
        Long productId,
        Integer quantity,
        BigDecimal unitPrice) {
}
```

Truy vấn PostgreSQL:

```java
public Flux<OrderLineView> findOrderLines(
        DatabaseClient databaseClient,
        Long orderId) {

    return databaseClient.sql("""
            SELECT o.id AS order_id,
                   o.order_number,
                   o.status,
                   l.line_no,
                   l.product_id,
                   l.quantity,
                   l.unit_price
            FROM purchase_order o
            LEFT JOIN order_line l ON l.order_id = o.id
            WHERE o.id = :orderId
            ORDER BY l.line_no
            """)
            .bind("orderId", orderId)
            .map((row, metadata) -> new OrderLineView(
                    row.get("order_id", Long.class),
                    row.get("order_number", String.class),
                    row.get("status", String.class),
                    row.get("line_no", Integer.class),
                    row.get("product_id", Long.class),
                    row.get("quantity", Integer.class),
                    row.get("unit_price", BigDecimal.class)))
            .all();
}
```

Đây là read model phẳng: mỗi hàng kết quả tương ứng với một dòng hàng. Nếu đơn hàng không có dòng hàng, `LEFT JOIN` vẫn có thể trả một hàng với các cột phía `order_line` là NULL. DTO cần cho phép các trường line nullable hoặc truy vấn cần xử lý riêng trường hợp không có dòng.

Nếu cần gom kết quả JOIN thành một DTO có collection lồng nhau, ứng dụng phải nhóm các hàng theo `order_id` và tạo collection trong pipeline. Không nên giả định `DatabaseClient` tự tái tạo aggregate graph như repository mapping.

### 10.1. JOIN không thay đổi ranh giới aggregate

Một truy vấn đọc có thể JOIN nhiều bảng để hiển thị dữ liệu. Điều đó không có nghĩa các bảng được gộp thành một aggregate hoặc có thể sửa tất cả qua một object graph tùy ý.

Phân biệt:

- **Write model:** dùng aggregate root và repository để bảo vệ invariant khi thay đổi.
- **Read model:** dùng projection, JOIN hoặc `DatabaseClient` để lấy dữ liệu phù hợp cho màn hình/báo cáo.

Đây là cách tổ chức phổ biến khi mô hình ghi cần chặt chẽ nhưng màn hình cần dữ liệu tổng hợp.

## 11. Truy vấn child theo điều kiện

Nếu cần tìm các đơn hàng có dòng hàng của một sản phẩm, có thể dùng truy vấn SQL tường minh:

```java
@Query("""
    SELECT DISTINCT o.id, o.order_number, o.status
    FROM purchase_order o
    JOIN order_line l ON l.order_id = o.id
    WHERE l.product_id = :productId
    """)
Flux<PurchaseOrderSummary> findOrdersContainingProduct(
        @Param("productId") Long productId);
```

Ví dụ này trả projection `PurchaseOrderSummary`, không nhất thiết trả đầy đủ aggregate có collection `lines`. Đây thường là lựa chọn phù hợp khi chỉ cần danh sách đơn hàng tóm tắt.

Nếu nghiệp vụ cần tải aggregate root đầy đủ để thực hiện thay đổi, hãy lấy ID các root phù hợp rồi tải root qua repository theo chiến lược phù hợp. Tránh dùng một projection thiếu dữ liệu để thực hiện domain operation yêu cầu invariant trên toàn bộ aggregate.

## 12. Hiệu năng và kích thước collection

Một aggregate một-nhiều có thể trở nên rất lớn theo thời gian. Nếu một customer có hàng triệu event hoặc một đơn hàng có hàng chục nghìn phần tử, việc tải và lưu toàn bộ collection cùng root có thể không còn phù hợp.

Các dấu hiệu cần xem lại thiết kế:

- Mỗi lần đọc root phải tải một collection rất lớn dù caller chỉ cần một phần tử.
- Một thay đổi nhỏ khiến nhiều hàng con bị xử lý lại.
- Nhiều request cập nhật các child khác nhau nhưng liên tục xung đột trên cùng root.
- Transaction giữ connection lâu do phải ghi nhiều hàng.
- Không thể phân trang child mà không tải toàn bộ aggregate.

Hướng xử lý có thể gồm:

- Tách child thành aggregate riêng nếu có vòng đời độc lập.
- Truy vấn child theo điều kiện và phân trang bằng repository riêng.
- Dùng read model hoặc `DatabaseClient` cho màn hình chỉ cần một phần dữ liệu.
- Chia batch khi ghi dữ liệu lớn, đồng thời xác định rõ tính nguyên tử theo nghiệp vụ.
- Giữ collection trong aggregate ở kích thước có thể quản lý.

Không tách aggregate chỉ để tối ưu truy vấn nếu invariant yêu cầu các object phải thay đổi cùng nhau. Khi tách, cần thiết kế lại quy trình nhất quán và xử lý trạng thái trung gian.

## 13. Index cho quan hệ một-nhiều

Khóa ngoại ở bảng con thường là cột được dùng để tải collection:

```sql
SELECT order_id, line_no, product_id, quantity, unit_price
FROM order_line
WHERE order_id = 1001
ORDER BY line_no;
```

Khóa chính kép `(order_id, line_no)` đã có `order_id` ở đầu nên có thể hỗ trợ truy vấn theo `order_id` và thứ tự `line_no` trong nhiều hệ quản trị. Nếu schema dùng một khóa chính khác, có thể cần index riêng:

```sql
CREATE INDEX ix_order_line_order_id_line_no
    ON order_line(order_id, line_no);
```

Nếu truy vấn thường lọc theo `product_id`, index trên `product_id` có thể hữu ích:

```sql
CREATE INDEX ix_order_line_product_id
    ON order_line(product_id);
```

Index phải dựa trên query workload và execution plan. Mỗi index tăng chi phí ghi và dung lượng, vì vậy không nên tạo index cho mọi cột một cách máy móc.

## 14. Xử lý thứ tự và cập nhật collection

Với `List`, thứ tự có thể là một phần của dữ liệu. Nếu xóa phần tử ở giữa, index các phần tử sau có thể thay đổi. Khi Spring Data đồng bộ collection, giá trị key column có thể được ghi lại theo trạng thái danh sách mới.

Nếu thứ tự có ý nghĩa nghiệp vụ và phải ổn định qua nhiều lần chỉnh sửa, cân nhắc lưu `line_no` như một thuộc tính domain rõ ràng thay vì chỉ coi nó là vị trí trong collection. Ví dụ:

```java
public class OrderLine {
    private Integer position;
    private Long productId;
    private Integer quantity;
    private BigDecimal unitPrice;
}
```

Khi đó, cần thiết kế mapping sao cho không nhầm `position` của domain với key column nội bộ của collection. Có thể dùng `@MappedCollection` cho khóa collection và cột domain riêng nếu mô hình yêu cầu, hoặc dùng persistence adapter/SQL tường minh.

Đừng dựa vào thứ tự vật lý của hàng trong database. Nếu truy vấn trực tiếp bảng con, luôn dùng `ORDER BY` theo cột thứ tự đã định nghĩa.

## 15. Xử lý ID được sinh và tham chiếu khóa ngoại

Khi ID của root được sinh ở database, các hàng con phải tham chiếu đúng ID sau khi insert root. Spring Data Relational quản lý mapping của aggregate để sử dụng ID root trong các hàng con.

Với ID do ứng dụng gán trước, root có thể có ID ngay từ khi tạo. Tuy nhiên, cần cấu hình newness detection đúng để Spring Data biết đây là aggregate mới. Nếu Spring Data nhận nhầm là entity đã tồn tại, nó có thể chọn đường update thay vì insert.

Với ID gán trước, có thể sử dụng `Persistable<ID>` để cung cấp `isNew()` nếu phù hợp. Sau khi lưu, trạng thái mới cần được quản lý đúng để các lần save tiếp theo không tiếp tục bị xem là mới.

Không nên tự gán `order_id` vào từng `OrderLine` nếu collection mapping đã quản lý khóa ngoại. Việc lặp lại thông tin quan hệ trong cả child object lẫn `@MappedCollection` có thể gây nhầm lẫn về cột nào là nguồn mapping chính.

## 16. Optimistic locking cho aggregate có collection

Nếu root có thuộc tính `@Version`, Spring Data Relational có thể dùng version để phát hiện cập nhật đồng thời trên aggregate:

```java
@Version
private Long version;
```

Khi hai request cùng tải một `PurchaseOrder`, cả hai có thể sửa collection `lines`. Khi request đầu tiên lưu và tăng version, request thứ hai dùng version cũ có thể thất bại với optimistic locking exception.

Điều này giúp tránh ghi đè âm thầm toàn bộ trạng thái aggregate. Tuy nhiên, nếu collection lớn và nhiều thao tác độc lập thường xuyên thay đổi các dòng khác nhau, xung đột ở root có thể xảy ra thường xuyên. Đây có thể là dấu hiệu aggregate đang gom quá nhiều phần có vòng đời hoặc nhu cầu cập nhật độc lập.

Không tự retry bằng cách lưu lại object cũ. Cần tải aggregate mới, áp dụng lại ý định nghiệp vụ nếu còn hợp lệ và lưu với version mới.

## 17. Xóa root và các hàng con

Khi xóa aggregate root, cần quyết định số phận các hàng con. Có thể dùng:

- Xóa các hàng con trước rồi xóa root trong cùng transaction.
- Dùng foreign key `ON DELETE CASCADE` nếu chính sách dữ liệu cho phép.
- Không cho phép xóa root khi còn dữ liệu con và trả lỗi nghiệp vụ.
- Dùng soft delete để giữ lại lịch sử.

Không nên giả định `repository.deleteById(rootId)` sẽ tự động thực hiện cascade theo object graph giống JPA. Spring Data Relational làm việc với database relational; constraint và hành vi cascade ở schema có vai trò quyết định. Hãy kiểm tra DDL và SQL thực tế.

Nếu dùng `ON DELETE CASCADE`, database xóa child rows khi root bị xóa. Cần kiểm thử điều này trên database thực tế và xem xét yêu cầu audit, retention, pháp lý hoặc lịch sử giao dịch trước khi dùng.

## 18. Những lỗi thường gặp

| Triệu chứng | Nguyên nhân có thể có | Cách xử lý |
| --- | --- | --- |
| Collection đọc luôn rỗng | Sai `idColumn`, tên bảng con hoặc schema không có hàng tham chiếu đúng root | Kiểm tra DDL, mapping metadata và SQL thực tế |
| Ghi root thành công nhưng child lỗi | Sai FK, kiểu ID hoặc thiếu transaction bao trùm thao tác | Kiểm tra constraint, bind type và reactive transaction |
| Không khôi phục đúng thứ tự List | Thiếu/sai `keyColumn` hoặc truy vấn không có thứ tự rõ ràng | Khai báo key column và dùng cột position/ORDER BY phù hợp |
| Tạo repository cho child không có ID | Child thực chất là thành phần của aggregate | Thao tác qua repository root hoặc thiết kế child thành aggregate riêng có ID |
| Thay một child nhưng nhiều hàng bị ghi lại | Aggregate persistence có thể thay thế collection con khi save root | Đánh giá kích thước aggregate và SQL; tách child nếu có vòng đời độc lập |
| Tải root kéo theo dữ liệu quá nhiều | Collection lớn hoặc mô hình aggregate quá rộng | Dùng projection/query riêng hoặc tách aggregate theo domain |
| `@OneToMany` không hoạt động | Dùng annotation JPA trong Spring Data Relational | Dùng `@MappedCollection` cho collection thuộc aggregate |
| Thay đổi Product không xuất hiện trong OrderLine | Child chỉ lưu `productId`, không tự tải Product | Truy vấn Product riêng hoặc dùng JOIN/read model |
| Xóa root bị lỗi foreign key | Hàng con vẫn tham chiếu root | Xác định cascade hoặc xóa child trước theo transaction |
| Cập nhật collection bị optimistic locking | Request khác đã thay đổi cùng root | Tải lại aggregate và xử lý xung đột theo nghiệp vụ |

## 19. Kiểm thử quan hệ một-nhiều

Unit test domain nên kiểm tra invariant của root:

```java
@Test
void shouldAddLineToDraftOrder() {
    PurchaseOrder order = new PurchaseOrder("PO-TEST-1");

    order.addLine(501L, 2, new BigDecimal("10.00"));

    assertEquals(1, order.getLines().size());
    assertEquals(501L, order.getLines().get(0).getProductId());
}
```

Integration test repository cần xác nhận dữ liệu được lưu và đọc lại từ database:

```java
StepVerifier.create(purchaseOrderRepository.save(order)
        .flatMap(saved -> purchaseOrderRepository.findById(saved.getId())))
        .assertNext(loaded -> {
            assertEquals(2, loaded.getLines().size());
            assertEquals(501L, loaded.getLines().get(0).getProductId());
        })
        .verifyComplete();
```

Các ví dụ giả định fixture, constructor và test database đã được cấu hình. Integration test nên chạy với R2DBC driver và hệ quản trị tương ứng, vì hành vi generated ID, kiểu dữ liệu, transaction, constraint và SQL có thể khác giữa database.

Các trường hợp nên kiểm thử:

- Lưu root không có child và đọc lại collection rỗng.
- Lưu root có nhiều child và xác nhận FK cùng key column.
- Đọc lại root và khôi phục đúng thứ tự collection.
- Thêm, sửa và bỏ child rồi lưu root.
- Child insert lỗi thì transaction có rollback root hay không.
- Xóa root theo chính sách cascade/constraint đã chọn.
- Cập nhật đồng thời và optimistic locking.
- Đọc projection qua JOIN với root không có child.

## 20. Quy trình chọn cách đọc và ghi quan hệ một-nhiều

Khi thiết kế một quan hệ một-nhiều trong Spring Data R2DBC, có thể thực hiện theo trình tự:

1. Xác định đối tượng cha có phải aggregate root hay không.
2. Xác định đối tượng con có vòng đời phụ thuộc root hay cần trở thành aggregate riêng.
3. Nếu child thuộc aggregate, khai báo collection bằng `@MappedCollection`.
4. Thiết kế bảng con với khóa ngoại trỏ tới root và key column phù hợp với List/Map hoặc định danh phần tử.
5. Tạo repository cho aggregate root.
6. Đọc root bằng repository khi cần toàn bộ aggregate.
7. Ghi mới hoặc cập nhật collection qua domain method của root rồi gọi `save`.
8. Dùng transaction reactive nếu các thao tác root/child cần nguyên tử.
9. Dùng `DatabaseClient`/projection/JOIN khi chỉ cần một phần dữ liệu hoặc read model tổng hợp.
10. Kiểm thử mapping, thứ tự, FK, generated ID, transaction và optimistic locking trên database thực tế.

`@MappedCollection` giúp Spring Data Relational ánh xạ quan hệ một-nhiều nằm trong cùng aggregate. Repository của root là điểm đọc/ghi chính; các phần tử con được quản lý cùng root và tham chiếu tới root bằng khóa ngoại. Khi cần truy vấn tổng hợp hoặc chỉ đọc một phần dữ liệu, có thể dùng SQL JOIN và projection riêng. Chọn đúng ranh giới aggregate, khóa ngoại, key column và transaction giúp quan hệ một-nhiều rõ ràng, nhất quán và phù hợp với cách hoạt động của Spring Data R2DBC.
