# Vai trò của định danh trong insert, update và save

Trong Spring Data R2DBC, định danh (ID) giúp xác định một hàng dữ liệu và thường là căn cứ để Spring Data biết một entity đang được tạo mới hay đã tồn tại. Khi gọi `save(entity)` trên reactive repository, Spring Data sử dụng trạng thái mới/cũ của entity để chọn thao tác insert hoặc update. Vì vậy, giá trị ID có ảnh hưởng trực tiếp đến hành vi lưu dữ liệu.

Điểm quan trọng là `save` không mặc định truy vấn database để kiểm tra hàng có tồn tại hay không rồi mới quyết định. Theo cơ chế nhận diện entity mới, Spring Data thường dựa vào thuộc tính `@Version` nếu có, nếu không thì dựa vào thuộc tính `@Id`; entity cũng có thể tự định nghĩa trạng thái bằng `Persistable.isNew()`. Hiểu quy tắc này giúp tránh tình huống một entity có ID được gán sẵn nhưng lại bị xử lý như bản ghi cần update.

## 1. ID đại diện cho điều gì?

Trong database quan hệ, khóa chính định danh duy nhất một hàng trong bảng. Trong entity Spring Data R2DBC, thuộc tính được đánh dấu `@Id` ánh xạ với khóa chính đó.

Ví dụ bảng khách hàng:

```sql
CREATE TABLE customer (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(200) NOT NULL,
    email VARCHAR(255) NOT NULL UNIQUE
);
```

Entity tương ứng:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Table;

@Table("customer")
public record Customer(
        @Id Long id,
        String name,
        String email
) {}
```

`@Id` cho Spring Data biết thuộc tính nào là định danh của entity. Với khóa tự sinh ở database, ứng dụng có thể tạo entity mới với `id = null`; sau khi insert, database sinh khóa và Spring Data trả về entity đã có ID.

Định danh có thể là số tự tăng, UUID hoặc kiểu khác phù hợp với schema và driver. Điều quan trọng là quy tắc tạo ID phải nhất quán giữa ứng dụng và database.

## 2. Insert và update khác nhau thế nào?

**Insert** tạo một hàng mới trong bảng. Database có thể tự sinh ID nếu cột khóa chính được cấu hình identity/sequence hoặc cơ chế tương đương.

**Update** thay đổi một hàng đã được xác định, thường bằng điều kiện dựa trên khóa chính. ID được dùng để tìm hàng cần cập nhật.

Ví dụ SQL:

```sql
INSERT INTO customer (name, email)
VALUES ('An', 'an@example.com');

UPDATE customer
SET name = 'An Nguyen'
WHERE id = 42;
```

Insert tạo một bản ghi mới và có thể nhận ID được sinh. Update nhắm đến bản ghi đã có ID. Nếu điều kiện update không khớp hàng nào, dữ liệu không được tạo mới một cách tự động chỉ vì update không tìm thấy bản ghi.

Trong Spring Data R2DBC, `insert` và `update` là hai thao tác khác nhau. Phương thức `save` của repository chọn một trong hai dựa trên trạng thái entity.

## 3. Cách ReactiveCrudRepository.save() chọn insert hay update

Một repository thông thường:

```java
public interface CustomerRepository
        extends ReactiveCrudRepository<Customer, Long> {
}
```

`ReactiveCrudRepository` cung cấp phương thức:

```java
<S extends T> Mono<S> save(S entity);
```

Về mặt khái niệm, Spring Data thực hiện:

```text
save(entity)
    |
    v
Xác định entity có mới hay không
    |
    +---- entity mới ------> INSERT
    |
    +---- entity đã có ----> UPDATE
    |
    v
Trả publisher chứa entity đã lưu
```

Quy tắc mặc định để nhận diện entity mới:

1. Nếu entity có thuộc tính `@Version`, Spring Data dùng giá trị version để xác định trạng thái mới/cũ.
2. Nếu không có thuộc tính version, Spring Data kiểm tra thuộc tính ID.
3. Nếu cần quy tắc riêng, entity có thể triển khai `Persistable` và cung cấp `isNew()`.

Với thuộc tính ID dạng object như `Long`, giá trị `null` thường biểu thị entity mới; ID khác null biểu thị entity đã tồn tại. Với ID kiểu primitive, giá trị mặc định như `0` có thể được dùng để nhận diện entity mới. Dùng kiểu wrapper như `Long` thường giúp biểu diễn rõ ràng trạng thái chưa có ID.

Nếu entity có `@Version`, trạng thái version được ưu tiên trong cơ chế nhận diện. Với version dạng wrapper, giá trị null biểu thị entity mới; sau khi lưu, Spring Data quản lý version cho các lần cập nhật tiếp theo.

## 4. Insert khi ID chưa được gán

Với khóa chính do database tự sinh, entity mới thường có ID là null:

```java
Customer newCustomer = new Customer(
        null,
        "An",
        "an@example.com"
);

Mono<Customer> savedPublisher = customerRepository.save(newCustomer);
```

Vì ID chưa có, entity được nhận diện là mới và `save` đi theo nhánh insert. Khi publisher được subscribe và insert thành công, database sinh ID.

Hãy sử dụng entity được phát ra từ publisher:

```java
return customerRepository.save(newCustomer)
        .doOnNext(saved -> log.info(
                "Created customer with id {}", saved.id()
        ));
```

Với entity bất biến như Java record, Spring Data có thể tạo một instance mới chứa ID được sinh thay vì sửa instance ban đầu. Vì vậy, không nên bỏ qua giá trị được phát ra rồi tiếp tục dùng object đầu vào với giả định rằng ID đã được cập nhật.

Ví dụ đầy đủ trong service:

```java
public Mono<Customer> createCustomer(String name, String email) {
    Customer customer = new Customer(null, name, email);
    return customerRepository.save(customer);
}
```

Service trả `Mono<Customer>`; controller hoặc tầng gọi tiếp theo nhận entity đã lưu khi publisher hoàn tất.

## 5. Update khi ID đã có giá trị

Khi entity có ID khác null và không có quy tắc nhận diện khác, Spring Data thường xem entity là đã tồn tại:

```java
Customer changedCustomer = new Customer(
        42L,
        "An Nguyen",
        "an@example.com"
);

Mono<Customer> updatedPublisher =
        customerRepository.save(changedCustomer);
```

Trong trường hợp này, `save` đi theo nhánh update. ID `42` được dùng để xác định hàng cần cập nhật.

Điều đó có nghĩa là ID khác null chỉ cho Spring Data biết entity được xem là đã tồn tại theo quy tắc nhận diện; nó không chứng minh hàng tương ứng thực sự đang có trong database.

Nếu ID không khớp hàng nào, `save` không tự chuyển sang insert để tạo hàng mới. Hành vi cụ thể khi update không tác động hàng nào phụ thuộc vào thao tác, versioning và lớp truy cập đang dùng. Với entity có `@Version`, việc không cập nhật được hàng mong đợi thường được biểu diễn thành lỗi optimistic locking.

Vì thế, đừng dùng `save` như một lệnh SQL upsert có nghĩa “có thì update, không có thì insert”. Nó chọn insert/update dựa trên trạng thái entity ở phía ứng dụng.

## 6. Bảng tổng hợp quy tắc nhận diện

| Trạng thái entity | Quy tắc mặc định | Nhánh `save` |
| --- | --- | --- |
| Không có `@Version`, ID kiểu `Long` là null | Entity mới | Insert |
| Không có `@Version`, ID kiểu `Long` khác null | Entity đã tồn tại theo trạng thái ID | Update |
| Có `@Version Long`, version là null | Entity mới | Insert |
| Có `@Version Long`, version đã có giá trị | Entity đã tồn tại theo version | Update |
| Triển khai `Persistable` | Theo kết quả `isNew()` | Insert hoặc update theo quy tắc tùy chỉnh |

Bảng trên mô tả cách nhận diện thông thường. Khi dùng version hoặc `Persistable`, cần hiểu rõ trạng thái của thuộc tính đó và cập nhật đúng sau khi lưu.

## 7. Vai trò của @Version trong save

ID xác định hàng cần cập nhật, còn version hỗ trợ phát hiện cập nhật đồng thời. Đây là optimistic locking.

Ví dụ:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;
import org.springframework.data.relational.core.mapping.Table;

@Table("inventory_item")
public record InventoryItem(
        @Id Long id,
        String name,
        int quantity,
        @Version Long version
) {}
```

Với entity mới:

```java
InventoryItem item = new InventoryItem(
        null,
        "Keyboard",
        10,
        null
);

return inventoryRepository.save(item);
```

Version null biểu thị entity mới theo quy tắc version-based. Khi insert thành công, Spring Data khởi tạo version. Khi cập nhật, version được tăng và được dùng để bảo vệ thao tác khỏi ghi đè thay đổi của một transaction khác.

Một update có version thường có ý nghĩa tương đương:

```sql
UPDATE inventory_item
SET quantity = 9,
    version = 4
WHERE id = 10
  AND version = 3;
```

Điều kiện `version = 3` đảm bảo hàng vẫn ở phiên bản mà ứng dụng đã đọc. Nếu một transaction khác đã cập nhật hàng và version đổi thành 4 trước đó, update cũ không còn khớp. Spring Data phát hiện không có hàng được cập nhật như mong đợi và báo lỗi optimistic locking thay vì âm thầm ghi đè.

Các giá trị version cụ thể trong ví dụ chỉ để minh họa. Hãy dùng entity được trả về sau mỗi lần save vì Spring Data có thể trả instance chứa version mới, đặc biệt với entity bất biến.

### Không bỏ qua version trả về

Giả sử ứng dụng đọc entity với version 3, lưu thay đổi và nhận entity mới với version 4. Nếu lần cập nhật sau vẫn dùng object cũ có version 3, optimistic locking có thể từ chối thao tác. Vì vậy:

```java
return inventoryRepository.findById(id)
        .switchIfEmpty(Mono.error(new InventoryItemNotFoundException(id)))
        .map(item -> new InventoryItem(
                item.id(),
                item.name(),
                item.quantity() - 1,
                item.version()
        ))
        .flatMap(inventoryRepository::save);
```

Publisher của `save` trả entity chứa version mới. Tầng gọi cần giữ kết quả đó nếu còn thực hiện các thao tác tiếp theo dựa trên version.

## 8. ID được gán sẵn và vấn đề nhận diện entity mới

Không phải ứng dụng nào cũng dùng ID tự sinh. Nhiều hệ thống tạo UUID ở phía ứng dụng trước khi insert:

```java
UUID id = UUID.randomUUID();
Customer customer = new Customer(id, "An", "an@example.com");
return customerRepository.save(customer);
```

Nếu entity không có `@Version` và dùng quy tắc mặc định dựa trên ID, ID khác null khiến Spring Data xem entity là đã tồn tại. `save` có thể chọn update dù hàng UUID đó chưa từng được insert.

Đây là điểm cần lưu ý khi dùng assigned ID. Có một số cách giải quyết:

- Dùng `@Version` wrapper và để version null trên entity mới, nếu version phù hợp với mô hình dữ liệu.
- Triển khai `Persistable<ID>` để tự cung cấp trạng thái mới/cũ.
- Dùng thao tác insert tường minh qua `R2dbcEntityTemplate` khi nghiệp vụ chắc chắn đang tạo bản ghi mới.

Không nên đặt ID thành null chỉ để ép insert nếu ID là định danh nghiệp vụ bắt buộc và database không tự sinh nó.

## 9. Dùng Persistable để tự định nghĩa isNew()

`Persistable<ID>` cho phép entity cung cấp ID và trạng thái mới/cũ thông qua `getId()` và `isNew()`. Cách này hữu ích khi ID được gán trước insert nhưng ứng dụng vẫn cần `save` chọn nhánh insert.

Ví dụ entity có ID UUID được gán từ phía ứng dụng:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Transient;
import org.springframework.data.annotation.PersistenceCreator;
import org.springframework.data.domain.Persistable;
import org.springframework.data.relational.core.mapping.Table;

@Table("external_customer")
public class ExternalCustomer implements Persistable<UUID> {

    @Id
    private final UUID id;

    private final String name;

    @Transient
    private boolean newEntity;

    @PersistenceCreator
    public ExternalCustomer(UUID id, String name) {
        this.id = id;
        this.name = name;
        this.newEntity = false;
    }

    public static ExternalCustomer newCustomer(UUID id, String name) {
        ExternalCustomer customer = new ExternalCustomer(id, name);
        customer.newEntity = true;
        return customer;
    }

    @Override
    public UUID getId() {
        return id;
    }

    @Override
    public boolean isNew() {
        return newEntity;
    }

    public void markNotNew() {
        this.newEntity = false;
    }
}
```

Ở ví dụ này:

- ID được gán ngay khi tạo object qua factory `newCustomer(...)`.
- `isNew()` trả true để chỉ ra entity cần insert.
- `@Transient` ngăn trạng thái nội bộ `newEntity` trở thành cột database.
- Sau khi insert thành công, trạng thái cần chuyển sang false để các lần save tiếp theo được nhận diện là update.

Constructor được đánh dấu `@PersistenceCreator` đặt trạng thái mặc định là false khi Spring Data tái tạo entity từ hàng đã lưu. Factory `newCustomer(...)` chỉ bật trạng thái mới cho object được tạo để insert.

Ứng dụng phải quản lý thời điểm chuyển trạng thái một cách nhất quán. Với mô hình mutable đơn giản, có thể cập nhật sau khi save hoàn tất:

```java
return externalCustomerRepository.save(customer)
        .doOnNext(ExternalCustomer::markNotNew);
```

Đây là minh họa về cơ chế `Persistable`; trong dự án thực tế, cần đảm bảo trạng thái mới/cũ cũng được khôi phục đúng khi entity được tải lại từ database. Entity được đọc từ database phải được xem là entity đã tồn tại. Có thể dùng callback hoặc factory tạo entity để thiết lập trạng thái phù hợp theo vòng đời ứng dụng.

Không nên triển khai `isNew()` chỉ dựa trên một cờ luôn true mà không có cơ chế chuyển trạng thái sau insert. Nếu cờ không đổi, những lần save tiếp theo có thể tiếp tục đi theo nhánh insert và gây lỗi khóa chính trùng.

## 10. Chọn insert hoặc update tường minh bằng R2dbcEntityTemplate

Repository `save` tiện lợi khi muốn Spring Data quyết định insert/update theo trạng thái entity. Nếu nghiệp vụ đã biết rõ đang tạo mới hoặc cập nhật, có thể dùng `R2dbcEntityTemplate` để diễn đạt thao tác tường minh.

Ví dụ insert:

```java
public Mono<Customer> insertCustomer(Customer customer) {
    return template.insert(customer);
}
```

Ví dụ update:

```java
public Mono<Customer> updateCustomer(Customer customer) {
    return template.update(customer);
}
```

Insert tường minh biểu đạt ý định tạo hàng mới; update tường minh biểu đạt ý định cập nhật hàng đã có. Cần dùng đúng overload và mapping phù hợp với phiên bản Spring Data Relational trong dự án.

Khi cập nhật một vài trường theo điều kiện, có thể dùng API fluent của template hoặc `DatabaseClient` với câu SQL rõ ràng. Cách đó tránh việc ghi lại toàn bộ thuộc tính của entity nếu use case chỉ thay đổi một phần dữ liệu.

Ví dụ cập nhật bằng SQL:

```java
public Mono<Long> renameCustomer(Long id, String newName) {
    return databaseClient.sql("""
            UPDATE customer
            SET name = :name
            WHERE id = :id
            """)
            .bind("name", newName)
            .bind("id", id)
            .fetch()
            .rowsUpdated();
}
```

Ở ví dụ này, số hàng cập nhật được trả về để service có thể phân biệt hàng đã được cập nhật với trường hợp không có hàng khớp. `rowsUpdated()` trả về publisher số hàng bị ảnh hưởng; giữ nguyên kiểu mà phiên bản API đang dùng cung cấp.

## 11. Save không phải là upsert

Trong SQL, upsert thường có nghĩa là insert nếu chưa có hàng hoặc update nếu đã có hàng, dựa trên một khóa hoặc constraint xác định. Cú pháp cụ thể tùy database, ví dụ PostgreSQL có `INSERT ... ON CONFLICT ... DO UPDATE`.

`repository.save(entity)` không mặc định thực hiện thao tác đó. Nó chọn insert hoặc update dựa trên trạng thái mới/cũ do Spring Data xác định.

Ví dụ với entity có ID 42:

- Nếu entity được nhận diện là mới, Spring Data thực hiện insert. Nếu khóa 42 đã tồn tại, database có thể báo lỗi vi phạm khóa chính.
- Nếu entity được nhận diện là đã tồn tại, Spring Data thực hiện update. Nếu không có hàng ID 42, nó không tự động insert một hàng mới.

Nếu nghiệp vụ thực sự cần upsert theo một khóa duy nhất, hãy sử dụng cơ chế native của database, constraint phù hợp và SQL tường minh qua `DatabaseClient` hoặc một phương thức truy vấn riêng. Cần kiểm tra kỹ hành vi với database và driver mục tiêu.

## 12. SaveAll và trạng thái của từng entity

`ReactiveCrudRepository.saveAll(...)` nhận một tập entity và trả về publisher của các entity đã lưu:

```java
Flux<Customer> saveAllCustomers(List<Customer> customers) {
    return customerRepository.saveAll(customers);
}
```

Mỗi entity cần có trạng thái mới/cũ phù hợp. Một danh sách có thể chứa cả entity mới với ID null và entity đã tồn tại với ID khác null; Spring Data xác định thao tác lưu theo trạng thái từng entity.

Không nên mặc định `saveAll` luôn tương đương một câu SQL bulk insert duy nhất. Việc thực thi và tối ưu phụ thuộc vào implementation, driver và database. Nếu cần bulk insert với hiệu năng cụ thể, hãy xem xét API batch hoặc SQL phù hợp và kiểm thử trên database mục tiêu.

Với các entity có version, cần sử dụng giá trị version được trả về sau khi lưu. Nếu tái sử dụng object cũ có version lỗi thời, thao tác cập nhật sau có thể thất bại do optimistic locking.

## 13. ID và version trong quá trình cập nhật đồng thời

ID xác định bản ghi, nhưng tự nó không ngăn hai request ghi đè dữ liệu của nhau.

Ví dụ:

1. Request A đọc hàng ID 42.
2. Request B cũng đọc hàng ID 42.
3. Request A cập nhật tên và commit.
4. Request B cập nhật email dựa trên bản dữ liệu cũ.

Nếu không có optimistic locking hoặc chiến lược đồng bộ phù hợp, request B có thể ghi lại các giá trị cũ ngoài ý muốn tùy cách update được tạo.

Với `@Version`, update có thể chỉ thành công nếu version trong database vẫn bằng version mà request đã đọc. Request đến sau nhận lỗi optimistic locking và có thể tải lại dữ liệu, kiểm tra xung đột rồi yêu cầu người dùng xử lý.

Optimistic locking phù hợp khi xung đột không quá thường xuyên và muốn tránh khóa pessimistic kéo dài. Nó không thay thế validation nghiệp vụ hoặc transaction; nó chỉ phát hiện một số trường hợp bản ghi đã thay đổi kể từ lúc được đọc.

## 14. Kiểm thử insert, update và save

Một bộ integration test nên xác nhận các nhánh trạng thái:

### Insert và ID được sinh

```java
StepVerifier.create(customerRepository.save(
                new Customer(null, "An", "an@example.com")
        ))
        .assertNext(saved -> {
            assertNotNull(saved.id());
            assertEquals("An", saved.name());
        })
        .verifyComplete();
```

Kiểm thử xác nhận publisher phát entity sau insert và entity trả về có ID.

### Update theo ID

```java
StepVerifier.create(
        customerRepository.save(
                new Customer(existingId, "An Nguyen", "an@example.com")
        )
)
        .assertNext(saved -> {
            assertEquals(existingId, saved.id());
            assertEquals("An Nguyen", saved.name());
        })
        .verifyComplete();
```

Test này giả định `existingId` đã được tạo trước đó và hàng tương ứng tồn tại.

### Assigned ID

Nếu dùng ID được gán trước, hãy kiểm tra `save` chọn insert theo `Persistable.isNew()` hoặc version null. Sau insert, xác nhận entity được chuyển sang trạng thái đã tồn tại và lần save tiếp theo đi theo nhánh update.

### Optimistic locking

Với entity có `@Version`, đọc cùng một bản ghi hai lần, lưu một bản thay đổi trước rồi thử lưu bản còn lại với version cũ. Xác nhận thao tác sau nhận lỗi optimistic locking. Test cần database thật hoặc database test có hỗ trợ hành vi versioning của Spring Data R2DBC.

## 15. Những nhầm lẫn thường gặp

1. **Nghĩ save luôn kiểm tra hàng tồn tại trước.** Spring Data xác định trạng thái entity từ version, ID hoặc `Persistable`; không nên coi save là truy vấn kiểm tra tồn tại rồi upsert.
2. **Gán UUID trước khi gọi save và mong insert tự động.** Với quy tắc mặc định dựa trên ID, ID khác null có thể làm entity được xem là đã tồn tại.
3. **Bỏ qua entity trả về từ save.** ID sinh tự động hoặc version mới có thể nằm trên instance được trả về.
4. **Dùng ID để chống cập nhật đồng thời.** ID xác định hàng; `@Version` hỗ trợ optimistic locking.
5. **Dùng primitive ID mà không hiểu giá trị mặc định.** Kiểu wrapper như `Long` giúp phân biệt rõ null với ID đã có.
6. **Đặt `isNew()` luôn true.** Sau insert cần chuyển trạng thái để các lần lưu tiếp theo không tiếp tục insert.
7. **Cho rằng update không tìm thấy hàng sẽ tự insert.** Update không phải upsert.
8. **Dùng save để cập nhật một vài trường nhưng không cân nhắc dữ liệu cũ.** Hãy chọn API update hoặc SQL tường minh khi cần thay đổi có kiểm soát.
9. **Cho rằng saveAll luôn là bulk SQL.** Nó là API lưu nhiều entity; chiến lược thực thi phụ thuộc implementation.
10. **Dùng version cũ sau lần save.** Hãy giữ entity được trả về để tránh optimistic locking với version lỗi thời.

## Quy tắc lựa chọn nhanh

- Với ID do database sinh, khởi tạo entity mới với ID null và dùng `save` để insert.
- Với entity có ID đã tồn tại, dùng `save` để update theo trạng thái nhận diện.
- Với ID gán sẵn, cấu hình trạng thái mới bằng `@Version`, `Persistable.isNew()` hoặc dùng insert tường minh.
- Dùng `@Version` khi cần phát hiện cập nhật đồng thời.
- Dùng `R2dbcEntityTemplate.insert` hoặc SQL tường minh khi muốn thể hiện rõ thao tác insert.
- Dùng update tường minh khi nghiệp vụ chắc chắn đang sửa một hàng đã tồn tại.
- Dùng native SQL upsert khi yêu cầu thực sự là insert-or-update theo constraint của database.
- Luôn sử dụng entity được phát ra từ publisher save để giữ ID hoặc version mới.

Trong Spring Data R2DBC, ID là một phần quan trọng của trạng thái persistence: nó xác định hàng và tham gia quyết định entity mới hay đã tồn tại. `save` dùng trạng thái entity để chọn insert hoặc update; version và `Persistable` có thể thay đổi cách nhận diện mặc định. Nắm rõ các quy tắc này giúp ứng dụng xử lý chính xác ID tự sinh, ID gán sẵn, cập nhật đồng thời và những tình huống cần insert/update tường minh.
