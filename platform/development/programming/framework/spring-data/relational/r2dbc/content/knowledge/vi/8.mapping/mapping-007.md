# Ánh xạ thuộc tính bất biến và cập nhật bản sao thực thể

Spring Data R2DBC có thể ánh xạ dữ liệu vào những thực thể không có setter và không cho phép thay đổi thuộc tính sau khi khởi tạo. Với kiểu dữ liệu bất biến, Spring Data tạo đối tượng thông qua constructor hoặc factory method phù hợp, sau đó sử dụng cơ chế tạo bản sao khi cần gán những giá trị được sinh trong quá trình lưu trữ. Khi cập nhật nghiệp vụ, ứng dụng tạo một instance mới chứa trạng thái mong muốn rồi truyền instance đó cho Repository.

Cách làm này phù hợp với Java record, các class có trường `final` và Kotlin data class. Nó giúp trạng thái entity dễ dự đoán, giảm thay đổi ngoài ý muốn và làm rõ sự khác nhau giữa đối tượng hiện tại với phiên bản tiếp theo của nó. Để sử dụng hiệu quả, cần hiểu constructor mapping, `@PersistenceCreator`, wither method, `@Id`, `@Version` và giá trị mà `save` trả về.

## 1. Đối tượng bất biến trong mô hình lưu trữ

Một đối tượng bất biến (*immutable object*) là đối tượng không cho phép thay đổi trạng thái quan sát được sau khi được tạo. Thay vì có setter như `setDisplayName(...)`, nó cung cấp các giá trị ban đầu qua constructor và giữ chúng trong những thuộc tính không thể gán lại.

Ví dụ class mutable:

```java
public class Customer {
    private Long id;
    private String email;
    private String displayName;

    public void setDisplayName(String displayName) {
        this.displayName = displayName;
    }
}
```

Sau khi được tạo, đối tượng trên có thể bị thay đổi bởi bất kỳ thành phần nào giữ tham chiếu và gọi setter. Một entity bất biến biểu diễn cùng dữ liệu bằng constructor:

```java
public record Customer(
        Long id,
        String email,
        String displayName
) {
}
```

Record không cung cấp setter. Muốn có tên hiển thị khác, chương trình tạo một `Customer` mới với ID và email được giữ lại.

### 1.1. Vì sao dùng entity bất biến?

- **Trạng thái rõ ràng:** sau khi khởi tạo, giá trị của từng thuộc tính không bị thay đổi âm thầm ở nơi khác.
- **Dễ suy luận:** mỗi instance đại diện cho một trạng thái cụ thể; thao tác cập nhật tạo ra trạng thái tiếp theo.
- **Giảm side effect:** nhiều thành phần có thể đọc cùng một instance mà không lo một thành phần khác sửa dữ liệu bên trong.
- **Hỗ trợ thiết kế theo giá trị:** có thể so sánh, truyền và kiểm thử các trạng thái mà không cần theo dõi chuỗi setter đã được gọi.
- **Phù hợp với constructor mapping:** Spring Data có thể tạo đối tượng từ các giá trị đọc được từ hàng database.

Tính bất biến không tự bảo đảm dữ liệu hợp lệ. Constructor, factory hoặc tầng nghiệp vụ vẫn cần kiểm tra các điều kiện cần thiết. Ngoài ra, một đối tượng có trường tham chiếu tới collection mutable vẫn có thể bị thay đổi gián tiếp; bất biến của entity nên được xem xét cả ở các đối tượng lồng bên trong.

### 1.2. Bất biến của Java object và cập nhật của database

Entity bất biến không có nghĩa là hàng database không thể cập nhật. Database vẫn có thể thực hiện `UPDATE`; ứng dụng chỉ biểu diễn trạng thái trước và sau bằng hai object riêng biệt.

```text
Customer cũ                    Customer mới
id = 12                         id = 12
email = a@example.com           email = a@example.com
displayName = "An"              displayName = "Anh An"
version = 3                     version = 3 (trước khi save)
       |                               |
       | tạo bản sao có tên mới        |
       +------------------------------>
                                       |
                                       v
                                Repository.save(...)
                                       |
                                       v
                              Database UPDATE
                                       |
                                       v
                                Customer đã lưu
                                version = 4
```

Instance cũ không bị sửa tại chỗ. Kết quả trả về từ thao tác lưu có thể là instance mới chứa version đã tăng hoặc giá trị được database sinh ra.

## 2. Cách Spring Data ánh xạ entity bất biến

Spring Data Relational sử dụng metadata của entity để đọc các cột trong hàng kết quả và chuyển chúng thành thuộc tính Java. Với entity mutable, framework có thể tạo đối tượng rồi gán thuộc tính qua cơ chế truy cập phù hợp. Với entity bất biến, framework cần biết constructor hoặc factory method nào tạo ra đối tượng từ các giá trị đã đọc.

Quá trình khái quát:

1. Driver R2DBC trả về các cột của hàng database.
2. Spring Data R2DBC đọc metadata mapping của entity, gồm tên bảng, cột và kiểu thuộc tính.
3. Giá trị cột được chuyển đổi sang kiểu Java tương ứng.
4. Spring Data chọn persistence constructor hoặc factory method.
5. Các giá trị được truyền vào tham số theo tên thuộc tính và metadata mapping.
6. Instance entity được tạo và trả về qua `Mono` hoặc `Flux`.

Ví dụ bảng:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email VARCHAR(254) NOT NULL,
    display_name VARCHAR(120) NOT NULL,
    version BIGINT
);
```

Entity bất biến tương ứng:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("customers")
public record Customer(
        @Id Long id,
        String email,
        @Column("display_name") String displayName,
        @Version Long version
) {
}
```

Spring Data ánh xạ cột `display_name` vào thuộc tính `displayName`. Tên tham số constructor của record tương ứng với tên thuộc tính Java (`displayName`), còn `@Column` chỉ định tên cột trong database. Không đổi tên tham số constructor thành `display_name` chỉ vì tên cột sử dụng snake_case.

### 2.1. Constructor mapping

Constructor dùng để materialize entity cần nhận được các giá trị cần thiết để tạo một instance hợp lệ. Với Java record, canonical constructor là lựa chọn tự nhiên vì record component định nghĩa rõ tên và kiểu thuộc tính.

Với class thông thường, constructor mapping cũng có thể dùng constructor có tham số. Tên tham số cần tương ứng với tên thuộc tính. Bảo đảm build cung cấp metadata tên tham số Java theo cấu hình phù hợp, thường là tùy chọn compiler `-parameters`; kiểm tra cấu hình build nếu Spring Data không thể xác định tên tham số. Không dùng tên cột SQL thay cho tên thuộc tính Java.

Ví dụ class bất biến:

```java
@Table("customers")
public final class Customer {

    @Id
    private final Long id;

    private final String email;

    @Column("display_name")
    private final String displayName;

    @Version
    private final Long version;

    public Customer(
            Long id,
            String email,
            String displayName,
            Long version) {
        this.id = id;
        this.email = email;
        this.displayName = displayName;
        this.version = version;
    }

    public Long getId() { return id; }
    public String getEmail() { return email; }
    public String getDisplayName() { return displayName; }
    public Long getVersion() { return version; }
}
```

Các trường `final` không có setter. Constructor nhận đủ giá trị và khởi tạo trạng thái của entity một lần. Getter chỉ cho phép đọc dữ liệu.

### 2.2. Chọn constructor bằng @PersistenceCreator

Một class có thể có nhiều constructor vì lý do tương thích, tạo mới trong ứng dụng hoặc phục vụ framework khác. Spring Data cần biết constructor nào được dùng để đọc dữ liệu từ database. Có thể đánh dấu constructor phù hợp bằng `@PersistenceCreator`.

```java
import org.springframework.data.annotation.PersistenceCreator;
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Table;

@Table("customers")
public final class Customer {

    @Id
    private final Long id;
    private final String email;
    private final String displayName;

    @PersistenceCreator
    public Customer(Long id, String email, String displayName) {
        this.id = id;
        this.email = email;
        this.displayName = displayName;
    }

    public Customer(String email, String displayName) {
        this(null, email, displayName);
    }

    public Long getId() { return id; }
    public String getEmail() { return email; }
    public String getDisplayName() { return displayName; }
}
```

Constructor có đủ `id`, `email` và `displayName` được dùng để materialize entity. Constructor tiện ích còn lại phục vụ việc tạo mới từ code ứng dụng. Khi chỉ có một constructor phù hợp, annotation có thể không cần thiết; hãy dùng nó khi cần loại bỏ sự mơ hồ về constructor được chọn.

Spring Data cũng hỗ trợ persistence factory method trong những trường hợp phù hợp. Nếu dùng factory, cần bảo đảm phương thức được đánh dấu đúng và trả về kiểu entity cần ánh xạ.

### 2.3. Tham số constructor và quy tắc mapping

Một số quy tắc nên tuân theo:

- Tên tham số constructor phản ánh tên thuộc tính trong entity.
- Kiểu tham số tương thích với kiểu thuộc tính sau khi chuyển đổi từ database.
- Tham số phải đủ để tạo một trạng thái hợp lệ của entity.
- `@Column` dùng để ánh xạ thuộc tính Java với cột database; nó không thay thế tên thuộc tính trong constructor.
- Khi có nhiều constructor, đánh dấu rõ persistence constructor thay vì trông chờ framework đoán theo thứ tự khai báo.
- Không thêm tham số constructor chỉ để nhận một cột không thuộc entity; nếu cần dữ liệu tổng hợp, hãy dùng projection hoặc kiểu kết quả truy vấn riêng.

Nếu entity có một trường được tính toán từ các trường khác, cân nhắc không đưa nó vào persistence constructor hoặc đánh dấu thuộc tính không lưu trữ bằng `@Transient` nếu phù hợp. Với dữ liệu truy vấn tổng hợp, projection thường thể hiện mục đích rõ hơn.

## 3. Record và các kiểu bất biến khác

### 3.1. Java record

Java record là lựa chọn gọn cho entity có dữ liệu chủ yếu được mô tả bằng các thành phần cố định. Canonical constructor nhận toàn bộ record component, getter có tên chính component và không có setter.

```java
@Table("products")
public record Product(
        @Id Long id,
        String sku,
        String name,
        BigDecimal price,
        @Version Long version
) {
}
```

Record giúp tránh boilerplate getter, constructor và `equals`/`hashCode`. Tuy nhiên, `equals`/`hashCode` do record sinh dựa trên các component; hãy cân nhắc ý nghĩa so sánh của entity trong domain. Record không tự cung cấp quy tắc identity theo khóa chính của database.

### 3.2. Class có trường final

Class thông thường hữu ích khi cần kiểm soát constructor, thêm hành vi domain hoặc tương thích với cấu trúc dự án hiện có. Có thể giữ tất cả thuộc tính là `final`, cung cấp getter và các phương thức tạo bản sao như `withDisplayName(...)`.

Ưu điểm là có thể đóng gói quy tắc cập nhật trong entity. Ví dụ, phương thức đổi tên có thể kiểm tra tên mới trước khi trả về instance tiếp theo. Không nên thêm setter công khai chỉ để làm hài lòng cơ chế mapping nếu constructor mapping đã đáp ứng nhu cầu.

### 3.3. Kotlin data class

Trong Kotlin, `data class` với các thuộc tính `val` là cách biểu diễn bất biến phổ biến. Phương thức `copy(...)` do Kotlin sinh cho phép tạo bản sao với một số thuộc tính thay đổi trong khi giữ các thuộc tính còn lại.

```kotlin
@Table("customers")
data class Customer(
    @Id val id: Long? = null,
    val email: String,
    @Column("display_name") val displayName: String,
    @Version val version: Long? = null
)
```

```kotlin
val renamed = customer.copy(displayName = "Anh An")
```

Kotlin support và cách xử lý constructor mặc định phụ thuộc phiên bản Spring Data, Kotlin và compiler plugin đang dùng. Hãy sử dụng phiên bản tương thích và kiểm thử materialization thực tế, đặc biệt khi có default parameter, nullable property hoặc nhiều constructor.

## 4. Cập nhật entity bất biến bằng cách tạo bản sao

Vì entity không có setter, việc thay đổi dữ liệu nghiệp vụ được biểu diễn bằng một instance mới. Có thể tạo phương thức `with...` hoặc phương thức domain có tên theo hành vi, ví dụ `rename(...)`.

### 4.1. Tạo phương thức wither

Một *wither* là phương thức trả về một instance mới có một thuộc tính được thay đổi, còn các thuộc tính khác được giữ nguyên. Quy ước tên thường là `with` cộng với tên thuộc tính.

```java
@Table("customers")
public record Customer(
        @Id Long id,
        String email,
        @Column("display_name") String displayName,
        @Version Long version
) {
    public Customer withDisplayName(String newDisplayName) {
        return new Customer(id, email, newDisplayName, version);
    }

    public Customer withEmail(String newEmail) {
        return new Customer(id, newEmail, displayName, version);
    }

    public Customer withId(Long newId) {
        return new Customer(newId, email, displayName, version);
    }

    public Customer withVersion(Long newVersion) {
        return new Customer(id, email, displayName, newVersion);
    }
}
```

`withDisplayName` phục vụ cập nhật nghiệp vụ. `withId` và `withVersion` minh họa cách tạo instance với giá trị metadata mới khi cần. Spring Data có thể nhận diện wither theo quy ước để thay đổi thuộc tính bất biến trong các bước xử lý mapping; nếu không có wither thích hợp, framework có thể dùng persistence constructor để tạo instance mới. Với record, canonical constructor cũng là cơ chế tự nhiên để materialize một trạng thái mới.

Không nên viết wither sửa trường hiện tại rồi trả về `this`; điều đó phá vỡ ý nghĩa bất biến. Một wither phải tạo object mới và giữ nguyên các thuộc tính không được yêu cầu thay đổi.

### 4.2. Phương thức domain diễn đạt hành vi

Tên `withDisplayName` mô tả việc thay một giá trị. Với nghiệp vụ có quy tắc, tên hành vi như `rename` có thể thể hiện ý định rõ hơn:

```java
public Customer rename(String newDisplayName) {
    if (newDisplayName == null || newDisplayName.isBlank()) {
        throw new IllegalArgumentException("Display name is required");
    }

    return new Customer(id, email, newDisplayName.trim(), version);
}
```

Entity vẫn bất biến vì phương thức trả về instance mới. Quy tắc kiểm tra được tập trung gần dữ liệu mà nó bảo vệ. Với quy tắc phụ thuộc database hoặc nhiều aggregate, Service vẫn là nơi điều phối phù hợp; không đưa truy vấn repository vào entity.

### 4.3. Copy constructor hoặc factory method

Không nhất thiết phải tạo một wither cho mọi thuộc tính. Có thể dùng factory hoặc phương thức `copy` nhận các giá trị cần thay đổi. Ví dụ:

```java
public Customer withProfile(String newEmail, String newDisplayName) {
    return new Customer(id, newEmail, newDisplayName, version);
}
```

Với nhiều thuộc tính, một phương thức copy có thể giúp giảm việc gọi chuỗi wither và tránh tạo nhiều object trung gian. Tuy nhiên, chữ ký phương thức phải dễ đọc và không làm người gọi vô tình ghi đè metadata như ID hoặc version.

## 5. ID được sinh và việc tạo instance mới

Khi insert, database có thể sinh khóa chính. Entity bất biến không thể nhận ID mới bằng cách gán vào trường `id` hiện tại. Spring Data cần tạo instance khác chứa giá trị ID vừa nhận.

Với entity dùng `@Id`, có thể cung cấp wither `withId(...)` để biểu diễn cách tạo bản sao với ID mới. Spring Data cũng có thể sử dụng persistence constructor để materialize một instance mới với giá trị ID đã được sinh, tùy cấu trúc entity và cơ chế mapping được chọn.

Ví dụ thao tác insert:

```java
Customer draft = new Customer(
        null,
        "an@example.com",
        "An Nguyen",
        null
);

return customerRepository.save(draft);
```

Không giả định `draft` sẽ được cập nhật tại chỗ. `save` trả về publisher chứa entity đã lưu; hãy sử dụng entity phát ra từ publisher đó:

```java
return customerRepository.save(draft)
        .map(saved -> {
            // saved có thể chứa ID được database sinh.
            return saved;
        });
```

Nếu bỏ qua giá trị trả về và tiếp tục sử dụng `draft`, code có thể vẫn thấy `id == null` dù bản ghi đã được tạo thành công.

Với một số chiến lược ID do ứng dụng cấp trước, quy tắc xác định entity mới có thể khác. Spring Data dựa trên entity information, `@Id` và nếu có `@Version` để xác định trạng thái mới/cũ. Hãy thiết kế chiến lược ID nhất quán và không dùng ID giả để ép framework thực hiện insert.

## 6. Cập nhật bản sao qua Repository trong luồng reactive

Một thao tác cập nhật thường gồm ba bước: đọc entity hiện tại, tạo bản sao với thay đổi mong muốn và lưu bản sao. Các bước được nối bằng Reactor để kết quả và lỗi tiếp tục đi qua cùng pipeline.

### 6.1. Ví dụ Repository

```java
import org.springframework.data.repository.reactive.ReactiveCrudRepository;
import reactor.core.publisher.Mono;

public interface CustomerRepository
        extends ReactiveCrudRepository<Customer, Long> {

    Mono<Customer> findByEmail(String email);
}
```

`findById` được kế thừa từ `ReactiveCrudRepository`; kết quả là `Mono<Customer>` vì có thể không tìm thấy bản ghi hoặc có tối đa một bản ghi.

### 6.2. Service tạo bản sao rồi lưu

```java
@Service
public class CustomerService {

    private final CustomerRepository repository;

    public CustomerService(CustomerRepository repository) {
        this.repository = repository;
    }

    public Mono<Customer> rename(Long id, String newDisplayName) {
        return repository.findById(id)
                .switchIfEmpty(Mono.error(
                        new CustomerNotFoundException(id)))
                .map(customer -> customer.rename(newDisplayName))
                .flatMap(repository::save);
    }
}
```

Ý nghĩa từng bước:

1. `findById` đọc trạng thái hiện tại từ database.
2. `switchIfEmpty` chuyển trường hợp không tồn tại thành lỗi nghiệp vụ.
3. `map` gọi `rename` và tạo một `Customer` mới. Bước này chỉ biến đổi object đồng bộ.
4. `flatMap` gọi `save` vì `save` trả về một `Mono<Customer>` khác.
5. Publisher cuối cùng phát ra entity đã lưu hoặc phát lỗi nếu thao tác thất bại.

Không dùng `map(repository::save)` vì như vậy kết quả sẽ là `Mono<Mono<Customer>>`. Dùng `flatMap` để nối một publisher vào pipeline hiện tại.

### 6.3. Giữ metadata khi tạo bản sao

Khi tạo bản sao cho thao tác update, phải giữ ID và version của entity đã đọc. Ví dụ `rename` giữ nguyên `id`, `email` và `version`, chỉ thay `displayName`. Nếu vô tình tạo entity mới với `id == null`, Repository có thể hiểu đó là insert. Nếu bỏ `version` hoặc đặt version sai, thao tác cập nhật có versioning có thể bị xem là trạng thái mới hoặc bị từ chối do xung đột.

Vì vậy, nên tạo bản sao từ entity hiện tại thay vì tạo object mới chỉ với các trường được client gửi. Những trường không có trong request vẫn cần được bảo toàn.

## 7. Optimistic locking và thuộc tính @Version

`@Version` cho phép Spring Data Relational kiểm tra entity có đang được cập nhật dựa trên phiên bản mới nhất hay không. Đây là cơ chế hữu ích khi nhiều request có thể đọc cùng một hàng rồi cùng ghi thay đổi.

Ví dụ entity:

```java
@Table("customers")
public record Customer(
        @Id Long id,
        String email,
        @Column("display_name") String displayName,
        @Version Long version
) {
    public Customer rename(String value) {
        return new Customer(id, email, value, version);
    }
}
```

Giả sử hai request cùng đọc bản ghi có `version = 5`:

```text
Request A đọc version 5       Request B đọc version 5
          |                              |
          v                              v
Tạo bản sao A                 Tạo bản sao B
          |                              |
          v                              v
Lưu thành công: version 6     Lưu với version cũ 5
          |                              |
          v                              v
          +--------------------> Phát hiện xung đột
                                  Optimistic locking failure
```

Khi A cập nhật thành công, version trong database tăng. B vẫn giữ version cũ, do đó update của B không còn khớp với phiên bản hiện tại và có thể thất bại bằng lỗi optimistic locking. Ứng dụng cần quyết định có trả lỗi xung đột cho client, đọc lại dữ liệu để người dùng xử lý hay thử lại khi nghiệp vụ cho phép.

### 7.1. Không tự tăng version trong phương thức copy

Phương thức `rename` nên giữ nguyên version vừa đọc. Spring Data quản lý việc kiểm tra và tăng version trong quá trình lưu. Không tự cộng version trong `rename` hoặc mapper; việc tự tăng có thể làm sai lệch cơ chế kiểm tra optimistic locking.

### 7.2. Dùng entity trả về sau save

Với entity bất biến, `save` có thể trả về một instance mới có version đã được tăng. Hãy truyền instance trả về cho các bước tiếp theo:

```java
return repository.save(updated)
        .flatMap(saved -> auditRepository.recordCustomerChange(saved)
                .thenReturn(saved));
```

Nếu bước audit cần cùng transaction với thao tác cập nhật, hãy đặt cả hai thao tác trong một transaction reactive. Ví dụ trên chỉ minh họa việc dùng entity đã lưu; transaction cần được cấu hình riêng theo yêu cầu nghiệp vụ.

### 7.3. Xử lý xung đột

Không phải mọi xung đột đều nên tự động retry. Nếu hai người dùng sửa cùng một tên hiển thị, retry có thể ghi đè ý định của người đến trước. Với dữ liệu có tính cộng dồn hoặc thao tác có thể thực hiện lại an toàn, retry có thể phù hợp sau khi đọc lại trạng thái. Quyết định này thuộc về nghiệp vụ.

API có thể biểu diễn xung đột bằng HTTP `409 Conflict` hoặc dùng `ETag`/`If-Match` nếu hợp đồng hỗ trợ cập nhật có điều kiện. Dù chọn cách nào, không nên trả một response thành công giả khi thao tác lưu bị từ chối do version cũ.

## 8. Những lưu ý khi làm việc với collection và object lồng nhau

Một record có thể chứa tham chiếu tới `List`, `Map` hoặc object khác. Việc thuộc tính tham chiếu là `final` không làm collection bên trong tự động bất biến.

Ví dụ:

```java
public record ShoppingCart(Long id, List<CartLine> lines) {
}
```

Người gọi vẫn có thể sửa list ban đầu sau khi truyền vào record. Có thể tạo bản sao bất biến trong constructor:

```java
public record ShoppingCart(Long id, List<CartLine> lines) {
    public ShoppingCart {
        lines = List.copyOf(lines);
    }
}
```

`List.copyOf` tạo một collection không thể sửa qua tham chiếu được trả về. Đây là bất biến nông: nếu `CartLine` tự nó mutable, phần tử vẫn có thể bị thay đổi. Khi cần bất biến sâu, các phần tử cũng nên là kiểu bất biến hoặc được bảo vệ bằng cách phù hợp.

Khi cập nhật collection, tạo list mới và tạo entity mới:

```java
List<CartLine> newLines = new ArrayList<>(cart.lines());
newLines.add(newLine);

ShoppingCart updatedCart = new ShoppingCart(cart.id(), newLines);
```

Đối với aggregate được Spring Data Relational lưu bằng `@MappedCollection`, hãy xác định rõ collection thuộc aggregate và tuân theo quy tắc mapping. Việc thay thế collection có thể khiến Spring Data ghi lại các phần tử phụ thuộc; cần hiểu SQL được phát ra và kiểm thử trên database mục tiêu. Không dùng collection bất biến như một cách thay thế cho thiết kế aggregate hoặc transaction.

## 9. Constructor, wither và callback trong vòng đời mapping

Spring Data có các điểm mở rộng trong vòng đời entity như entity callback. Khi entity bất biến, callback cần trả về instance cần tiếp tục được sử dụng thay vì sửa object tại chỗ. Ví dụ một callback trước khi convert có thể chuẩn hóa một thuộc tính và trả về bản sao mới.

Không nên đưa mọi quy tắc nghiệp vụ vào callback. Callback phù hợp với xử lý hạ tầng hoặc quy tắc mapping nhất quán, chẳng hạn chuẩn hóa metadata. Các hành vi như phê duyệt đơn hàng, kiểm tra hạn mức hay quyết định quyền cập nhật vẫn nên nằm trong Service/domain logic để có thể gọi và kiểm thử rõ ràng.

Khi cần custom conversion giữa kiểu database và kiểu Java, đăng ký converter theo cơ chế Spring Data R2DBC thay vì ép kiểu thủ công trong constructor. Constructor nên nhận các giá trị đã được chuyển đổi sang kiểu thuộc tính của entity.

## 10. Kiểm thử entity bất biến và cập nhật bản sao

Kiểm thử cần bao gồm cả mapping đọc từ database, thao tác insert có ID sinh ra và update có version. Unit test phương thức copy giúp bảo đảm các thuộc tính không liên quan được giữ nguyên; integration test xác nhận Spring Data thực sự materialize và lưu được kiểu entity bất biến.

### 10.1. Unit test phương thức tạo bản sao

```java
Customer current = new Customer(
        12L,
        "an@example.com",
        "An",
        5L
);

Customer renamed = current.rename("Anh An");

assertThat(renamed).isNotSameAs(current);
assertThat(renamed.id()).isEqualTo(current.id());
assertThat(renamed.email()).isEqualTo(current.email());
assertThat(renamed.displayName()).isEqualTo("Anh An");
assertThat(renamed.version()).isEqualTo(current.version());
assertThat(current.displayName()).isEqualTo("An");
```

Test này xác nhận instance mới được tạo, ID/email/version được giữ lại và instance cũ không đổi.

### 10.2. Kiểm thử luồng reactive

Với Reactor Test, có thể kiểm tra Service trả về entity mới sau thao tác lưu:

```java
Customer current = new Customer(12L, "an@example.com", "An", 5L);
Customer updated = new Customer(12L, "an@example.com", "Anh An", 6L);

when(repository.findById(12L)).thenReturn(Mono.just(current));
when(repository.save(any(Customer.class))).thenReturn(Mono.just(updated));

StepVerifier.create(service.rename(12L, "Anh An"))
        .expectNext(updated)
        .verifyComplete();

verify(repository).save(argThat(customer ->
        customer.id().equals(12L)
                && customer.displayName().equals("Anh An")
                && customer.version().equals(5L)));
```

Ví dụ giả định Service giữ version cũ khi tạo bản sao và Repository trả về instance đã lưu với version mới. Trong test thực tế, khai báo đầy đủ mock, matcher và exception theo lớp của dự án.

### 10.3. Integration test với R2DBC

Integration test nên xác nhận:

- Entity bất biến được đọc và materialize đúng từ hàng database.
- `@Column` ánh xạ đúng tên cột khác biệt với thuộc tính Java.
- Insert trả về instance có ID được sinh.
- Update trả về instance có version mới khi dùng `@Version`.
- Hai thao tác cập nhật dựa trên cùng một version tạo ra xung đột như dự kiến.
- Constructor được đánh dấu `@PersistenceCreator` được chọn khi entity có nhiều constructor.
- Collection mapping hoạt động đúng nếu entity có `@MappedCollection`.

Không chỉ mock Repository để kết luận constructor mapping hoạt động. Cơ chế materialization, generated ID, SQL và optimistic locking cần được kiểm thử với database và driver phù hợp.

## 11. Lỗi thường gặp và cách xử lý

### Không tìm được constructor phù hợp

Kiểm tra constructor có nhận đủ thuộc tính cần thiết, tên tham số có khớp tên thuộc tính hay không và metadata tên tham số có được giữ trong build hay không. Nếu có nhiều constructor, đánh dấu persistence constructor bằng `@PersistenceCreator`.

### Tên tham số constructor bị nhầm với tên cột

Tên tham số Java cần tương ứng với thuộc tính entity. `@Column("display_name")` ánh xạ thuộc tính `displayName` tới cột `display_name`; constructor vẫn nhận tham số `displayName`.

### Wither sửa object hiện tại

Một wither phải tạo instance mới. Nếu phương thức thay đổi trường mutable rồi trả về `this`, entity không còn bất biến và có thể gây side effect ở những nơi đang giữ tham chiếu.

### Bỏ qua giá trị trả về của save

Với entity bất biến, `save` không cập nhật object đầu vào tại chỗ. Luôn tiếp tục từ entity được phát ra bởi publisher của `save`, đặc biệt khi cần ID được sinh hoặc version mới.

### Tạo bản sao update nhưng làm mất ID hoặc version

Nếu bản sao không giữ ID, thao tác có thể bị nhận diện như insert. Nếu version không phản ánh trạng thái vừa đọc, optimistic locking có thể hoạt động sai hoặc từ chối update. Tạo bản sao từ entity hiện tại và chỉ thay đổi những thuộc tính nghiệp vụ cần thay đổi.

### Tự tăng version trước khi save

Để Spring Data quản lý version. Bản sao dùng version đã đọc để kiểm tra xung đột; framework tăng version khi update thành công.

### Dùng `map` để gọi một phương thức trả về publisher

`map` tạo publisher lồng nhau nếu hàm ánh xạ trả về `Mono` hoặc `Flux`. Dùng `flatMap` để nối publisher vào pipeline.

### Collection bên trong entity vẫn mutable

Trường `final List<T>` chỉ cố định tham chiếu, không cố định nội dung list. Dùng bản sao bất biến và các phần tử bất biến nếu cần kiểm soát sâu hơn.

## 12. Quy trình áp dụng cho một entity bất biến

Khi thiết kế entity mới hoặc chuyển entity mutable sang immutable, có thể thực hiện theo thứ tự:

1. Xác định bảng, cột, khóa chính, kiểu dữ liệu và constraint trong schema.
2. Tạo record hoặc class với constructor thể hiện đầy đủ trạng thái cần ánh xạ.
3. Khai báo `@Table`, `@Id`, `@Column` và `@Version` khi phù hợp.
4. Nếu có nhiều constructor, đánh dấu persistence constructor bằng `@PersistenceCreator`.
5. Bảo đảm tên tham số constructor tương ứng tên thuộc tính Java và build giữ metadata cần thiết.
6. Tạo wither hoặc phương thức domain trả về instance mới cho những thao tác cập nhật cần thiết.
7. Giữ ID và version khi tạo bản sao cho update.
8. Kết hợp `find`, copy và `save` bằng `map`/`flatMap` trong pipeline reactive.
9. Dùng entity trả về từ `save` cho các bước tiếp theo.
10. Kiểm thử constructor mapping, generated ID, version và xung đột cập nhật với database thực tế.

## 13. Checklist ghi nhớ

- [ ] Entity bất biến không có setter làm thay đổi trạng thái sau khi khởi tạo.
- [ ] Spring Data có thể tạo entity thông qua persistence constructor hoặc factory method.
- [ ] Java record phù hợp với mô hình dữ liệu có các thuộc tính cố định.
- [ ] `@PersistenceCreator` được dùng khi cần chỉ rõ constructor/factory để materialize entity.
- [ ] Tên tham số constructor khớp tên thuộc tính Java; `@Column` chỉ ánh xạ tên cột database.
- [ ] Wither tạo instance mới và giữ các thuộc tính không thay đổi.
- [ ] Khi insert, phải sử dụng entity phát ra từ `save` để nhận ID được sinh.
- [ ] Khi update, bản sao giữ ID và version đã đọc.
- [ ] `@Version` được Spring Data quản lý; không tự tăng version trong phương thức copy.
- [ ] Dùng `flatMap` khi nối thao tác trả về `Mono`/`Flux`.
- [ ] Collection và object lồng bên trong cũng được xem xét về tính bất biến.
- [ ] Integration test xác nhận mapping, generated ID và optimistic locking trên database phù hợp.

Ánh xạ thuộc tính bất biến dựa trên constructor hoặc factory method giúp Spring Data R2DBC tạo entity từ dữ liệu quan hệ mà không cần setter. Khi nghiệp vụ cần thay đổi trạng thái, ứng dụng tạo bản sao có chủ đích và lưu bản sao đó qua Repository. Việc giữ đúng ID, version và sử dụng giá trị trả về từ `save` giúp mô hình bất biến hoạt động nhất quán với vòng đời lưu trữ reactive.
