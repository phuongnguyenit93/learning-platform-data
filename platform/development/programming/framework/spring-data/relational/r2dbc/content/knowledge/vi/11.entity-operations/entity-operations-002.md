# Insert thực thể và nhận kết quả sau khi lưu

## 1. Insert thực thể trong Spring Data R2DBC

Một thao tác tạo dữ liệu mới thường bắt đầu từ một đối tượng Java do tầng nghiệp vụ tạo ra. Ứng dụng cần chuyển các thuộc tính của đối tượng thành giá trị có thể ghi xuống database, thực hiện câu lệnh INSERT, nhận kết quả từ R2DBC driver và trả lại thông tin của thực thể sau khi lưu.

Với Spring Data R2DBC, có hai API thường được dùng:

- **ReactiveCrudRepository.save(entity):** API repository quen thuộc. Spring Data xác định entity là mới hay đã tồn tại để chọn thao tác insert hoặc update.
- **R2dbcEntityTemplate.insert(...).using(entity):** API template diễn đạt rõ thao tác insert, phù hợp khi muốn yêu cầu tạo bản ghi mới một cách tường minh.

Cả hai API đều trả về publisher reactive. Kết quả không phải lúc nào cũng chính là object đầu vào. Database có thể sinh khóa chính, version hoặc giá trị mặc định; Spring Data có thể tạo một instance đã được cập nhật metadata đó và phát ra qua publisher trả về.

Vì vậy, khi insert, cần hiểu ba việc: khi nào Spring Data quyết định insert, database trả lại những giá trị nào, và cách sử dụng thực thể đã lưu sau khi publisher hoàn tất.

## 2. Luồng insert từ entity đến database

Giả sử ứng dụng cần tạo một khách hàng mới trong PostgreSQL. Entity Java có các trường `id`, `name` và `email`; database tự sinh giá trị `id`.

~~~text
Service tạo entity mới
        |
        v
Repository.save(entity)
hoặc R2dbcEntityTemplate.insert(...)
        |
        v
MappingR2dbcConverter
        |
        v
Tạo INSERT và bind giá trị
        |
        v
R2DBC Driver
        |
        v
PostgreSQL thực hiện INSERT
        |
        v
Database sinh ID / default / version
        |
        v
Driver trả kết quả được hỗ trợ
        |
        v
Spring Data ánh xạ kết quả
        |
        v
Mono<Entity đã lưu>
~~~

Các bước chính:

1. Tầng nghiệp vụ tạo entity với các giá trị đầu vào.
2. Spring Data đọc metadata mapping như `@Table`, `@Id`, `@Column`.
3. Mapping converter chuyển các property cần thiết thành giá trị store.
4. Spring Data tạo câu INSERT và bind tham số qua R2DBC driver.
5. Database kiểm tra constraint, ghi bản ghi và có thể sinh giá trị như identity hoặc version.
6. Driver và dialect cung cấp thông tin trả về mà Spring Data cần để hoàn thiện entity.
7. Publisher phát ra entity sau khi lưu thành công hoặc phát lỗi nếu thao tác thất bại.

Việc lấy ID sinh tự động phụ thuộc vào database, dialect và khả năng trả generated values của driver. Với các dialect được Spring Data hỗ trợ, mapping infrastructure xử lý phần lớn chi tiết này. Khi dùng database hoặc driver đặc thù, cần kiểm tra khả năng trả generated key và hành vi thực tế.

## 3. Khai báo entity và schema có khóa chính tự sinh

### 3.1. Entity với @Id

Ví dụ dùng Java record:

~~~java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Table;

@Table("customers")
public record Customer(
        @Id Long id,
        String name,
        String email
) {}
~~~

`@Table("customers")` ánh xạ record với bảng `customers`. `@Id` đánh dấu property định danh. Kiểu `Long` là kiểu nullable, phù hợp khi entity mới chưa có ID và database sẽ sinh ID sau khi insert.

### 3.2. Schema PostgreSQL

~~~sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(150) NOT NULL,
    email VARCHAR(320) NOT NULL UNIQUE
);
~~~

Cột `id` được PostgreSQL tạo tự động khi INSERT không cung cấp giá trị cho cột đó. Các cột `name` và `email` bắt buộc có giá trị; `email` còn có unique constraint.

Khi entity mới có `id = null`, Spring Data có thể nhận diện đây là entity mới và thực hiện insert. Database sinh ID, rồi Spring Data đưa ID đó vào kết quả trả về.

Không nên đặt ID giả như `0L` để biểu thị entity mới. Dùng kiểu wrapper nullable như `Long` và để ID chưa có giá trị cho đến khi database tạo ra. Với kiểu ID primitive, giá trị mặc định có thể được dùng trong quy tắc nhận diện newness, nhưng kiểu wrapper thường biểu đạt ý định rõ ràng hơn.

## 4. Tạo bản ghi bằng ReactiveCrudRepository.save()

### 4.1. Khai báo repository

~~~java
import org.springframework.data.repository.reactive.ReactiveCrudRepository;

public interface CustomerRepository
        extends ReactiveCrudRepository<Customer, Long> {
}
~~~

`ReactiveCrudRepository<Customer, Long>` cung cấp các thao tác CRUD reactive. Phương thức `save(S entity)` trả về `Mono<S>`, tức một publisher có thể phát ra entity sau khi thao tác hoàn tất.

### 4.2. Gọi save với entity mới

~~~java
Customer input = new Customer(
        null,
        "An Nguyen",
        "an@example.test"
);

Mono<Customer> savedCustomer = customerRepository.save(input);
~~~

Đoạn mã trên tạo publisher mô tả thao tác lưu. Do Reactor sử dụng mô hình lazy, việc gán kết quả vào biến `savedCustomer` chưa có nghĩa câu INSERT đã chạy. Thao tác được thực thi khi publisher có subscriber, ví dụ khi WebFlux xử lý response hoặc khi test dùng StepVerifier.

Có thể sử dụng entity được phát ra sau khi lưu:

~~~java
return customerRepository.save(input)
        .doOnNext(saved ->
                log.info("Created customer with id={}", saved.id()));
~~~

Ở đây, log chỉ chạy khi publisher phát ra entity đã lưu. Nếu thao tác insert thất bại, publisher phát lỗi và `doOnNext` không được gọi.

### 4.3. Luôn sử dụng giá trị được trả về

Với entity mutable, Spring Data có thể cập nhật ID hoặc version vào instance. Với entity immutable như Java record, Spring Data không thể gán lại property. Nó có thể tạo instance mới chứa các giá trị được database sinh ra rồi phát instance đó.

Vì vậy, nên viết:

~~~java
return customerRepository.save(input)
        .flatMap(saved -> {
            log.info("Generated id: {}", saved.id());
            return customerRepository.findById(saved.id());
        });
~~~

Không nên giả định `input.id()` đã có ID ngay sau khi gọi `save(input)`. Với record, giá trị của object đầu vào không thay đổi; ID cần đọc từ object được publisher phát ra.

Nguyên tắc này cũng hữu ích với entity immutable có constructor hoặc wither. Hãy coi kết quả của `save` là phiên bản đã được persistence layer hoàn thiện và dùng nó cho các bước tiếp theo.

## 5. Dùng R2dbcEntityTemplate.insert() khi cần insert tường minh

Repository `save` lựa chọn insert hoặc update dựa trên trạng thái mới/cũ của entity. Nếu nghiệp vụ muốn diễn đạt rõ ràng rằng thao tác này phải tạo một bản ghi mới, có thể dùng `R2dbcEntityTemplate`.

~~~java
import org.springframework.data.r2dbc.core.R2dbcEntityTemplate;
import org.springframework.stereotype.Service;
import reactor.core.publisher.Mono;

@Service
public class CustomerService {

    private final R2dbcEntityTemplate template;

    public CustomerService(R2dbcEntityTemplate template) {
        this.template = template;
    }

    public Mono<Customer> insert(Customer customer) {
        return template.insert(Customer.class).using(customer);
    }
}
~~~

Fluent API `insert(Customer.class).using(customer)` chỉ định rõ kiểu entity và object cần insert. Publisher trả về là `Mono<Customer>`, cho phép nhận entity sau khi Spring Data hoàn thành thao tác.

Sử dụng insert tường minh trong những trường hợp:

- Một thao tác chỉ được phép tạo bản ghi mới.
- Muốn tránh nhầm lẫn giữa insert và update khi entity có ID được gán sẵn.
- Muốn sử dụng API template thay vì repository.
- Cần phối hợp các thao tác insert với query hoặc update chuyên biệt ở tầng persistence.

Nếu khóa chính đã tồn tại, database thường từ chối insert do vi phạm primary key hoặc unique constraint. Insert không tự chuyển thành update và cũng không phải một câu lệnh upsert.

## 6. Phân biệt save, insert và upsert

Các tên gọi này có ý nghĩa khác nhau:

| API / khái niệm | Cách quyết định | Ý nghĩa |
|---|---|---|
| `ReactiveCrudRepository.save(entity)` | Dựa trên việc entity được nhận diện là mới hay đã tồn tại | Insert entity mới hoặc update entity hiện có |
| `R2dbcEntityTemplate.insert(...).using(entity)` | Luôn yêu cầu thao tác insert | Tạo bản ghi mới; lỗi nếu vi phạm constraint |
| SQL `INSERT ... ON CONFLICT ...` của PostgreSQL | Theo điều kiện conflict được chỉ định trong SQL | Insert hoặc thực hiện hành động khi conflict |
| SQL `MERGE` hoặc upsert của database | Theo cú pháp và điều kiện của database | Kết hợp insert/update theo quy tắc cụ thể |

`save` không đồng nghĩa với SQL upsert. Spring Data xác định entity mới hay cũ trước khi thực hiện thao tác. Nó không tự bảo đảm hành vi kiểu "nếu khóa đã tồn tại thì cập nhật, nếu chưa có thì insert" trong một câu lệnh nguyên tử.

Nếu nghiệp vụ cần upsert theo một unique key, hãy dùng câu SQL hoặc API database hỗ trợ upsert phù hợp với hệ quản trị. Với PostgreSQL, có thể sử dụng `INSERT ... ON CONFLICT` thông qua `DatabaseClient`, nhưng cần tự thiết kế phần trả kết quả và mapping.

Ví dụ SQL PostgreSQL:

~~~sql
INSERT INTO customers (name, email)
VALUES (:name, :email)
ON CONFLICT (email)
DO UPDATE SET name = EXCLUDED.name
RETURNING id, name, email;
~~~

Đây là cú pháp PostgreSQL. Không thể mặc định sao chép sang mọi database. Việc dùng upsert cũng cần xác định rõ trường nào được phép ghi đè, tránh làm mất cập nhật mới hơn hoặc dữ liệu không thuộc quyền của request hiện tại.

## 7. Spring Data xác định entity mới như thế nào?

Khi gọi `save`, Spring Data cần biết nên insert hay update. Quy tắc này được gọi là **entity state detection** hoặc nhận diện trạng thái mới/cũ.

### 7.1. Dựa vào ID

Với entity không có version property, Spring Data thường kiểm tra ID:

- ID là `null`: entity được xem là mới, thực hiện insert.
- ID có giá trị: entity được xem là đã tồn tại, thực hiện update.

Ví dụ:

~~~java
Customer newCustomer = new Customer(
        null,
        "An Nguyen",
        "an@example.test"
);

customerRepository.save(newCustomer); // new entity -> insert
~~~

Khi ID đã được gán:

~~~java
Customer existingCustomer = new Customer(
        42L,
        "An Nguyen",
        "an@example.test"
);

customerRepository.save(existingCustomer); // existing state -> update
~~~

Quy tắc này đơn giản khi ID do database sinh tự động và entity mới chưa có ID.

### 7.2. Dùng @Version để nhận diện newness và optimistic locking

Nếu entity có property được đánh dấu `@Version`, Spring Data có thể dùng version để xác định trạng thái trước khi xét ID. Với version property kiểu wrapper, giá trị `null` biểu thị entity mới; sau khi insert, version được khởi tạo. Khi update, version được kiểm tra và tăng theo cơ chế optimistic locking.

~~~java
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;
import org.springframework.data.relational.core.mapping.Table;

@Table("customers")
public record Customer(
        @Id Long id,
        @Version Long version,
        String name,
        String email
) {}
~~~

Cách này hữu ích khi ID được gán trước ở phía ứng dụng, ví dụ UUID, nhưng entity vẫn cần được nhận diện là mới. Schema cần có cột version tương ứng.

Không thêm `@Version` chỉ để ép insert nếu ứng dụng không có nhu cầu quản lý optimistic locking. Version là một phần của concurrency control và cần được xử lý nhất quán.

### 7.3. Dùng Persistable khi cần quy tắc newness tùy chỉnh

Với ID được gán thủ công và không dùng version, có thể triển khai `Persistable<ID>` để tự cung cấp trạng thái mới/cũ thông qua `isNew()`.

~~~java
import org.springframework.data.domain.Persistable;
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Transient;
import org.springframework.data.relational.core.mapping.Table;

@Table("external_customers")
public class ExternalCustomer implements Persistable<String> {

    @Id
    private String id;

    @Transient
    private boolean newEntity = true;

    @Override
    public String getId() {
        return id;
    }

    @Override
    public boolean isNew() {
        return newEntity;
    }

    public void markPersisted() {
        this.newEntity = false;
    }
}
~~~

Đây là phần minh họa cơ chế. Trong ứng dụng thực tế, trạng thái `newEntity` phải được chuyển sang false sau khi insert thành công, bằng lifecycle callback phù hợp với phiên bản Spring Data hoặc bằng cách quản lý trạng thái ở tầng domain/persistence. Nếu flag luôn true, lần gọi save tiếp theo có thể lại yêu cầu insert.

Với entity immutable, việc duy trì trạng thái newness có thể cần một thiết kế khác, chẳng hạn version property hoặc factory/state object phù hợp. Không nên dùng một cờ mutable tùy tiện mà không xác định lúc nào nó được cập nhật.

## 8. Nhận ID và giá trị do database sinh ra

### 8.1. Database-generated identity

Với cột identity:

~~~sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(150) NOT NULL,
    email VARCHAR(320) NOT NULL UNIQUE
);
~~~

Entity mới có thể đặt ID là null:

~~~java
Customer input = new Customer(null, "An Nguyen", "an@example.test");
~~~

Sau khi insert, database tạo ID. Khi driver/dialect hỗ trợ trả generated value và mapping được cấu hình đúng, Spring Data đưa ID vào entity kết quả.

~~~java
return customerRepository.save(input)
        .map(saved -> {
            Long generatedId = saved.id();
            return saved;
        });
~~~

Không nên tự gọi một câu SELECT riêng để đoán ID vừa tạo hoặc dùng `MAX(id)`. Cách đó không an toàn khi nhiều request insert đồng thời. Hãy lấy generated key từ kết quả insert do driver và Spring Data quản lý.

### 8.2. Các cột có default value

Database có thể tự đặt giá trị mặc định:

~~~sql
CREATE TABLE audit_events (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    event_type VARCHAR(80) NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
~~~

Nếu ứng dụng không cung cấp `created_at`, database có thể dùng default. Tuy nhiên, việc giá trị default có xuất hiện trong entity được trả về hay không phụ thuộc vào cách Spring Data và driver lấy generated values. Không nên giả định mọi cột default đều tự động được trả lại trong mọi dialect.

Nếu cần chắc chắn có giá trị trong object kết quả, hãy kiểm tra khả năng returning/generated values của database và driver. Với SQL tùy chỉnh, PostgreSQL có thể dùng `RETURNING` để yêu cầu trả lại các cột:

~~~sql
INSERT INTO audit_events (event_type)
VALUES (:eventType)
RETURNING id, event_type, created_at;
~~~

Đây là cú pháp PostgreSQL. Khi dùng `DatabaseClient`, cần map các cột trả về thành object theo cách tường minh.

### 8.3. Giá trị version

Nếu entity dùng `@Version`, Spring Data quản lý version khi insert/update. Entity mới thường có version null (với kiểu wrapper); sau insert, version được khởi tạo theo cơ chế của Spring Data. Khi cập nhật, version được dùng để phát hiện dữ liệu đã thay đổi bởi transaction khác.

Hãy sử dụng version từ entity được trả về để tiếp tục xử lý. Với entity immutable, object đầu vào có thể vẫn giữ version null trong khi object kết quả đã có version mới.

## 9. Entity mutable và immutable sau khi insert

### 9.1. Entity mutable

Một entity class thông thường có thể có setter cho ID:

~~~java
@Table("customers")
public class MutableCustomer {

    @Id
    private Long id;

    private String name;

    public Long getId() {
        return id;
    }

    public void setId(Long id) {
        this.id = id;
    }

    public String getName() {
        return name;
    }
}
~~~

Mapping infrastructure có thể điền ID được sinh vào entity theo cơ chế mapping. Dù vậy, code ứng dụng vẫn nên dùng entity được phát ra từ publisher vì đây là giá trị đã được persistence layer hoàn thiện.

### 9.2. Entity immutable

Với record:

~~~java
@Table("customers")
public record Customer(
        @Id Long id,
        String name,
        String email
) {}
~~~

Không thể gọi setter để cập nhật ID. Spring Data sử dụng constructor/property population strategy để tạo instance có các giá trị đã được cập nhật. Do đó:

~~~java
return customerRepository.save(
        new Customer(null, "An Nguyen", "an@example.test")
).flatMap(saved -> {
    // Dùng saved.id(), không dùng ID từ record đầu vào
    return customerRepository.findById(saved.id());
});
~~~

Đây là lý do quan trọng để không bỏ qua giá trị trả về của `save` hoặc `insert`.

### 9.3. Không giữ giả định object đầu vào luôn được cập nhật

Một số entity mutable có thể thấy ID thay đổi trên cùng instance; một số entity immutable cần instance mới. Hành vi cụ thể phụ thuộc entity model và mapping strategy. Code an toàn nhất là dùng giá trị được publisher trả về thay vì phụ thuộc vào việc object đầu vào có bị mutate hay không.

## 10. Xử lý kết quả insert trong reactive pipeline

### 10.1. Dùng flatMap để thực hiện bước tiếp theo

Nếu sau khi tạo khách hàng cần tạo một bản ghi liên quan, hãy lấy ID từ entity đã lưu:

~~~java
public Mono<CustomerProfile> createCustomer(CreateCustomerRequest request) {
    Customer customer = new Customer(
            null,
            request.name(),
            request.email()
    );

    return customerRepository.save(customer)
            .flatMap(savedCustomer -> {
                CustomerProfile profile = new CustomerProfile(
                        null,
                        savedCustomer.id(),
                        request.displayName()
                );

                return profileRepository.save(profile);
            });
}
~~~

Publisher của profile chỉ được tạo sau khi customer đã được insert và ID đã có. Đây là cách ghép các thao tác phụ thuộc nhau trong Reactor mà không cần gọi `block()`.

Nếu hai thao tác phải thành công hoặc rollback cùng nhau, đặt transaction reactive ở service và bảo đảm toàn bộ publisher được trả về trong cùng pipeline.

### 10.2. Dùng map khi chỉ biến đổi kết quả đồng bộ

Nếu chỉ cần chuyển entity đã lưu thành response DTO, dùng `map`:

~~~java
return customerRepository.save(customer)
        .map(saved -> new CustomerResponse(
                saved.id(),
                saved.name(),
                saved.email()
        ));
~~~

`map` phù hợp với phép biến đổi đồng bộ, không trả về publisher khác. Nếu bước tiếp theo cần gọi repository hoặc dịch vụ reactive khác, dùng `flatMap`.

### 10.3. Không gọi block hoặc subscribe bên trong service

Không nên viết:

~~~java
Customer saved = customerRepository.save(customer).block();
~~~

hoặc:

~~~java
customerRepository.save(customer).subscribe();
~~~

`block()` chặn thread để chờ kết quả và có thể gây nghẽn event-loop trong WebFlux. `subscribe()` tạo subscription riêng, khiến tầng gọi mất quyền quản lý vòng đời, lỗi, cancellation và transaction.

Hãy trả về `Mono<Customer>` để framework hoặc tầng gọi đăng ký subscription. Trong WebFlux, controller có thể trả trực tiếp publisher cho Spring xử lý.

## 11. Tạo API POST trả về thực thể đã lưu

Ví dụ service:

~~~java
@Service
public class CustomerService {

    private final CustomerRepository repository;

    public CustomerService(CustomerRepository repository) {
        this.repository = repository;
    }

    public Mono<Customer> create(String name, String email) {
        Customer customer = new Customer(null, name, email);
        return repository.save(customer);
    }
}
~~~

Controller WebFlux:

~~~java
@RestController
@RequestMapping("/customers")
public class CustomerController {

    private final CustomerService service;

    public CustomerController(CustomerService service) {
        this.service = service;
    }

    @PostMapping
    public Mono<ResponseEntity<Customer>> create(
            @RequestBody CreateCustomerRequest request) {

        return service.create(request.name(), request.email())
                .map(saved -> ResponseEntity
                        .created(URI.create("/customers/" + saved.id()))
                        .body(saved));
    }
}
~~~

Response thành công có thể chứa HTTP 201 Created, header Location trỏ đến resource vừa tạo và body có ID do database sinh. Việc trả entity trực tiếp chỉ phù hợp với API đơn giản; ứng dụng thực tế thường dùng response DTO để kiểm soát dữ liệu công khai, tránh lộ field nội bộ hoặc thông tin nhạy cảm.

## 12. Insert nhiều thực thể với saveAll

Reactive repository cung cấp `saveAll` để lưu một tập entity:

~~~java
Flux<Customer> inputs = Flux.just(
        new Customer(null, "An Nguyen", "an@example.test"),
        new Customer(null, "Binh Tran", "binh@example.test")
);

Flux<Customer> savedCustomers = customerRepository.saveAll(inputs);
~~~

Kết quả là một `Flux<Customer>` phát ra các entity đã lưu. Nếu database sinh ID, hãy đọc ID từ từng phần tử được phát ra.

Không nên giả định `saveAll` luôn tạo một câu SQL multi-row INSERT hoặc một batch duy nhất. Cách thực thi phụ thuộc repository implementation, driver và phiên bản Spring Data. Nếu cần hiệu năng bulk insert, hãy đo thực tế và cân nhắc API batch hoặc SQL chuyên biệt phù hợp với database.

Nếu một phần tử vi phạm unique constraint, publisher có thể phát lỗi. Cần xác định nghiệp vụ muốn toàn bộ batch atomic hay chấp nhận xử lý từng phần. Transaction boundary và cách tiêu thụ publisher quyết định phạm vi rollback; không nên mặc định mọi `saveAll` tự động có cùng một transaction.

## 13. Transaction khi insert nhiều bước

Giả sử nghiệp vụ tạo Order rồi tạo các OrderLine. ID của Order chỉ có sau khi insert root thành công. Có thể nối các bước bằng `flatMap`:

~~~java
@Transactional
public Mono<Order> createOrder(CreateOrderRequest request) {
    Order order = new Order(null, request.customerId(), "NEW");

    return orderRepository.save(order)
            .flatMap(savedOrder -> {
                List<OrderLine> lines = request.lines().stream()
                        .map(line -> new OrderLine(
                                null,
                                savedOrder.id(),
                                line.sku(),
                                line.quantity()
                        ))
                        .toList();

                return orderLineRepository.saveAll(lines)
                        .then(Mono.just(savedOrder));
            });
}
~~~

Đây là ví dụ minh họa với OrderLine được lưu qua repository riêng; nếu dòng hàng là thành phần của aggregate theo Spring Data Relational, nên thiết kế mapping và lưu root theo aggregate model phù hợp. Điểm chính ở đây là ID sinh ra được lấy từ `savedOrder` để tạo các bản ghi phụ thuộc.

Với reactive transaction, phương thức transactional cần trả về publisher để Spring quản lý subscription và transaction context. Không tự subscribe bên trong. Nếu thao tác thứ hai thất bại và các publisher cùng tham gia transaction, transaction manager có thể rollback thao tác trước đó.

Nếu các bước ghi thuộc nhiều database hoặc nhiều transaction manager khác nhau, một `@Transactional` đơn lẻ không tự tạo ra transaction phân tán. Khi đó cần thiết kế cơ chế nhất quán phù hợp, ví dụ outbox hoặc saga tùy kiến trúc.

## 14. Xử lý lỗi khi insert

Insert có thể thất bại vì nhiều nguyên nhân:

- Vi phạm primary key hoặc unique constraint.
- Thiếu giá trị cho cột NOT NULL.
- Giá trị không phù hợp kiểu dữ liệu hoặc giới hạn độ dài.
- Foreign key tham chiếu đến bản ghi không tồn tại.
- Database mất kết nối hoặc timeout.
- Driver không hỗ trợ kiểu bind hoặc generated value như mong đợi.

Các lỗi này được truyền dưới dạng error signal trong reactive publisher. Có thể chuyển exception tầng persistence thành lỗi nghiệp vụ hoặc API error ở service/web boundary.

Ví dụ ánh xạ lỗi unique constraint ở mức minh họa:

~~~java
return customerRepository.save(customer)
        .onErrorMap(
                DuplicateKeyException.class,
                ex -> new EmailAlreadyRegisteredException(customer.email())
        );
~~~

Tên exception và cách driver ánh xạ constraint violation có thể khác theo database/driver. Cần kiểm tra root cause hoặc SQL state để phân loại chính xác. Không nên bắt mọi exception rồi trả về một thông báo "email đã tồn tại", vì lỗi network hoặc schema cũng có thể bị che mất.

Nếu client gửi lại request sau timeout, cần cân nhắc idempotency. Lần insert đầu có thể đã thành công ở database nhưng response bị mất trên đường truyền. Một request lặp lại có thể gặp unique constraint. Với thao tác tạo quan trọng, có thể dùng idempotency key hoặc một business key có unique constraint để xác định kết quả đã được tạo trước đó.

## 15. Insert với ID do ứng dụng gán

Không phải hệ thống nào cũng dùng ID tự tăng. Một số domain tạo UUID hoặc mã định danh trước khi ghi.

Ví dụ:

~~~java
UUID id = UUID.randomUUID();

Customer customer = new Customer(
        id,
        "An Nguyen",
        "an@example.test"
);
~~~

Nếu entity không có version property và ID đã có giá trị, Spring Data có thể xem entity là đã tồn tại và chọn update khi gọi `save`. Vì vậy, không nên chỉ gán ID rồi giả định `save` chắc chắn thực hiện insert.

Có một số lựa chọn:

- Dùng `R2dbcEntityTemplate.insert(...).using(entity)` để yêu cầu insert tường minh.
- Dùng `@Version` wrapper property nếu phù hợp với nhu cầu optimistic locking và newness detection.
- Triển khai `Persistable<ID>` để cung cấp quy tắc `isNew()` tùy chỉnh, đồng thời quản lý đúng thời điểm entity chuyển sang trạng thái đã lưu.

Ví dụ dùng template:

~~~java
UUID id = UUID.randomUUID();
Customer customer = new Customer(id, "An Nguyen", "an@example.test");

return template.insert(Customer.class).using(customer);
~~~

Cú pháp này yêu cầu insert ngay cả khi ID đã được gán. Database vẫn kiểm tra primary key và unique constraint. Nếu ID đã tồn tại, insert thất bại trừ khi SQL được thiết kế riêng theo cơ chế upsert.

## 16. Các lưu ý về ID và kiểu dữ liệu

### 16.1. Kiểu ID phải tương thích với schema

Nếu cột ID là BIGINT, entity thường dùng `Long`. Nếu database dùng UUID, entity có thể dùng `UUID` nếu driver/dialect hỗ trợ. Tránh chuyển đổi ID qua String không cần thiết vì có thể gây lỗi mapping hoặc làm mất khả năng dùng kiểu dữ liệu native.

### 16.2. Không dùng giá trị ID tạm làm dấu hiệu newness tùy tiện

Một số ứng dụng dùng ID 0 hoặc số âm để biểu thị entity mới. Cách này có thể tương tác không như mong đợi với quy tắc state detection. Dùng null cho ID database-generated, hoặc quy tắc `Persistable`/version được thiết kế rõ ràng cho assigned ID.

### 16.3. ID sinh ra không phải thứ tự nghiệp vụ

ID identity thường dùng để định danh và liên kết bản ghi. Không nên suy ra thời gian tạo, thứ tự nghiệp vụ hoặc thứ tự request chỉ từ ID. Nếu nghiệp vụ cần timestamp hoặc sequence riêng, hãy lưu trường tương ứng và dùng cơ chế sinh giá trị có chủ đích.

## 17. Kiểm thử insert và kết quả sau khi lưu

### 17.1. Kiểm thử repository với StepVerifier

~~~java
@Test
void shouldInsertCustomerAndReturnGeneratedId() {
    Customer input = new Customer(
            null,
            "An Nguyen",
            "an@example.test"
    );

    StepVerifier.create(customerRepository.save(input))
            .assertNext(saved -> {
                assertThat(saved.id()).isNotNull();
                assertThat(saved.name()).isEqualTo("An Nguyen");
            })
            .verifyComplete();
}
~~~

Test này subscribe vào publisher và xác nhận entity trả về có ID. Cần dùng database test thật hoặc Testcontainers để kiểm tra generated key và hành vi driver.

### 17.2. Xác nhận dữ liệu thực sự tồn tại

Có thể đọc lại bằng ID trả về:

~~~java
StepVerifier.create(
        customerRepository.save(input)
                .flatMap(saved -> customerRepository.findById(saved.id()))
)
.assertNext(found -> {
    assertThat(found.email()).isEqualTo("an@example.test");
})
.verifyComplete();
~~~

Đọc lại giúp xác nhận cả insert lẫn mapping chiều đọc. Nếu chỉ kiểm tra publisher phát ra một entity, vẫn chưa xác nhận mọi cột đã được ghi đúng.

### 17.3. Kiểm tra constraint violation

Nên có test cho các trường hợp:

- Email trùng unique constraint.
- Thiếu trường NOT NULL.
- Foreign key không tồn tại.
- ID được gán đã có trong database.
- Giá trị quá dài hoặc sai kiểu.
- Insert trong transaction nhiều bước bị rollback khi bước sau thất bại.

Mock repository hữu ích cho unit test service, nhưng không thay thế integration test vì không kiểm tra SQL, generated key, constraint và driver.

## 18. Checklist khi tạo thực thể mới

Khi triển khai chức năng insert, hãy xác nhận:

1. Entity có `@Table` và `@Id` đúng schema.
2. Kiểu ID tương thích với cột database.
3. Quy tắc sinh ID là database-generated hay application-assigned.
4. Entity mới được Spring Data nhận diện là new theo ID, version hoặc `Persistable`.
5. Chọn `save` khi muốn repository quyết định insert/update; chọn template `insert` khi cần insert tường minh.
6. Publisher được trả về cho tầng gọi và có subscriber thực sự tiêu thụ.
7. Dùng entity được phát ra từ publisher để nhận generated ID, version và giá trị được cập nhật.
8. Không giả định `save` là upsert.
9. Xử lý unique, foreign key và NOT NULL constraint như error signal.
10. Dùng transaction reactive khi nhiều thao tác cần atomic.
11. Kiểm thử với database/driver thực tế để xác nhận generated values và mapping.

## 19. Kết luận

Spring Data R2DBC hỗ trợ insert thực thể theo mô hình reactive thông qua `ReactiveCrudRepository.save` hoặc thao tác insert tường minh của `R2dbcEntityTemplate`. Repository `save` dựa trên trạng thái mới/cũ để chọn insert hoặc update; template insert luôn biểu đạt yêu cầu tạo bản ghi mới. Hai thao tác này không đồng nghĩa với SQL upsert.

Khi database sinh ID, version hoặc giá trị mặc định, hãy lấy thông tin từ entity mà publisher trả về. Điều này đặc biệt quan trọng với entity immutable như record, vì object đầu vào có thể không được thay đổi. Hãy ghép bước tiếp theo bằng `map` hoặc `flatMap`, giữ transaction reactive xuyên suốt khi cần và để lỗi database được truyền qua reactive pipeline một cách rõ ràng.

Hiểu đúng state detection, generated values và kết quả sau khi lưu giúp thao tác insert an toàn hơn, nhất quán hơn và dễ kiểm thử trong ứng dụng Spring Data R2DBC.
