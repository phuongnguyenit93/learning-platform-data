# Mặc định, cột được sinh và tác động đến ánh xạ thực thể

Trong thiết kế schema quan hệ, database có thể tự cung cấp giá trị cho một cột khi insert, tự tăng khóa chính, tính một cột từ các cột khác hoặc cập nhật metadata thông qua trigger. Những cơ chế này giúp dữ liệu nhất quán ngay cả khi có nhiều ứng dụng cùng ghi vào database. Tuy nhiên, chúng ảnh hưởng trực tiếp đến cách Spring Data R2DBC tạo câu lệnh SQL và ánh xạ hàng kết quả trở lại entity.

Điểm quan trọng là phân biệt giá trị mặc định với giá trị được sinh. `DEFAULT` chỉ cung cấp giá trị khi câu lệnh insert không chỉ định giá trị cho cột hoặc yêu cầu dùng từ khóa `DEFAULT`; một giá trị SQL `NULL` tường minh thường không kích hoạt default. Cột identity hoặc generated column có quy tắc riêng và thường không nên được ứng dụng ghi trực tiếp. Trong entity, các annotation như `@Id`, `@ReadOnlyProperty`, `@InsertOnlyProperty`, `@Transient` và `@Column` quyết định thuộc tính nào tham gia mapping và ghi dữ liệu.

## 1. Các loại giá trị do database quản lý

Database có thể tạo hoặc thay đổi giá trị theo nhiều cách. Chúng có vẻ giống nhau ở góc nhìn ứng dụng nhưng có ngữ nghĩa khác nhau.

| Cơ chế | Thời điểm áp dụng | Ví dụ | Ứng dụng có nên ghi trực tiếp? |
|---|---|---|---|
| `DEFAULT` | Khi insert bỏ qua cột hoặc chỉ định `DEFAULT` | `status DEFAULT 'NEW'` | Thường để database điền nếu muốn dùng default |
| Identity/sequence | Khi insert một hàng mới | `id GENERATED ... AS IDENTITY` | Thường không tự cấp ID nếu database quản lý |
| Generated/computed column | Khi insert/update các cột nguồn | `line_total AS (quantity * unit_price)` | Không ghi trực tiếp vào cột được tính |
| Trigger-generated value | Khi trigger chạy trong insert/update | `created_at`, `updated_at`, audit metadata | Phụ thuộc quy tắc; nếu trigger là nguồn chính thì ứng dụng không nên ghi đè |
| Giá trị do ứng dụng gán | Trước khi insert/update | `status`, `display_name` | Ứng dụng chịu trách nhiệm cung cấp |

### 1.1. DEFAULT là giá trị mặc định khi không chỉ định

Ví dụ schema:

```sql
CREATE TABLE orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_code VARCHAR(32) NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'NEW',
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

Khi insert chỉ cung cấp `order_code`, database điền `status` và `created_at`:

```sql
INSERT INTO orders (order_code)
VALUES ('ORD-000123');
```

Ngược lại, nếu câu lệnh chỉ định `NULL` cho `status`, default không được dùng:

```sql
INSERT INTO orders (order_code, status)
VALUES ('ORD-000123', NULL);
```

Vì `status` có `NOT NULL`, câu lệnh trên thất bại. Nếu cột cho phép null, kết quả sẽ là `NULL`, không phải `'NEW'`.

Có thể yêu cầu dùng default một cách tường minh:

```sql
INSERT INTO orders (order_code, status)
VALUES ('ORD-000123', DEFAULT);
```

Điểm khác nhau cần nhớ:

- Bỏ cột khỏi danh sách insert: database có thể áp dụng default.
- Chỉ định `DEFAULT`: yêu cầu database áp dụng default của cột.
- Bind hoặc ghi `NULL`: cung cấp giá trị null tường minh; default thông thường không được kích hoạt.

## 2. DEFAULT tác động thế nào đến INSERT do Spring Data R2DBC tạo?

Spring Data R2DBC tạo SQL từ metadata entity. Với thuộc tính persistent được ánh xạ, framework có thể đưa cột vào câu lệnh insert và bind giá trị từ entity. Nếu thuộc tính Java là `null`, không nên mặc định rằng framework sẽ tự bỏ cột khỏi câu lệnh để database áp dụng default. Tùy đường ghi, phiên bản và mapping, null có thể được gửi như một giá trị SQL `NULL`.

Ví dụ entity:

```java
@Table("orders")
public record OrderEntity(
        @Id Long id,
        @Column("order_code") String orderCode,
        String status,
        @Column("created_at") Instant createdAt
) {
}
```

Nếu tạo entity với `status == null` và `createdAt == null`, việc hai thuộc tính này có được bỏ qua để dùng default hay được bind thành null phụ thuộc cách mapping/insert được cấu hình. Không dựa vào giả định rằng `null` luôn có nghĩa “không cung cấp cột”. Hãy kiểm tra SQL được sinh và dùng annotation/cách insert phù hợp.

### 2.1. Dùng @ReadOnlyProperty cho giá trị do database quản lý

`@ReadOnlyProperty` đánh dấu một thuộc tính được đọc từ database nhưng không được ghi vào database qua mapping Spring Data. Đây là lựa chọn phù hợp cho cột do database tự tạo hoặc tự cập nhật, ví dụ:

- Cột có default mà ứng dụng luôn muốn database cung cấp.
- Cột generated/computed.
- Cột được trigger quản lý.
- Metadata chỉ đọc mà ứng dụng cần nhận khi query entity.

Ví dụ:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.ReadOnlyProperty;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("orders")
public record OrderEntity(
        @Id Long id,
        @Column("order_code") String orderCode,
        String status,
        @ReadOnlyProperty
        @Column("created_at") Instant createdAt
) {
}
```

Với `createdAt` được đánh dấu `@ReadOnlyProperty`, Spring Data vẫn có thể đọc cột `created_at` và ánh xạ vào record, nhưng không ghi giá trị thuộc tính này trong thao tác insert/update entity thông thường. Khi insert, database có thể áp dụng `DEFAULT CURRENT_TIMESTAMP`; khi update, ứng dụng không ghi đè giá trị do database quản lý.

Đổi lại, ứng dụng không thể dùng thuộc tính đó để chủ động ghi một thời điểm tùy ý qua `save`. Nếu có use case cần ghi thủ công, cần thiết kế đường ghi riêng hoặc chọn mô hình khác thay vì đánh dấu read-only toàn bộ.

### 2.2. @ReadOnlyProperty khác @Transient

Hai annotation này không thể thay thế cho nhau:

| Annotation | Đọc từ database | Ghi vào database | Mục đích |
|---|---:|---:|---|
| `@ReadOnlyProperty` | Có | Không | Thuộc tính persistent do database/nguồn khác quản lý |
| `@Transient` | Không | Không | Thuộc tính chỉ tồn tại trong object Java, không thuộc mapping schema |

Ví dụ `totalAmount` được database tính từ các cột khác cần được đọc về entity nên có thể dùng `@ReadOnlyProperty`. Một thuộc tính `formattedLabel` chỉ được tính trong Java và không có cột tương ứng nên dùng `@Transient` hoặc không đưa vào persistence constructor theo cách phù hợp.

### 2.3. @InsertOnlyProperty dành cho thuộc tính chỉ ghi khi insert

`@InsertOnlyProperty` đánh dấu thuộc tính chỉ được ghi khi insert, không được ghi trong update. Nó hữu ích cho giá trị do ứng dụng cung cấp lúc tạo và cần giữ nguyên về sau, ví dụ một mã nguồn nhập liệu hoặc giá trị ban đầu được chụp tại thời điểm tạo.

```java
import org.springframework.data.annotation.InsertOnlyProperty;

@Table("orders")
public record OrderEntity(
        @Id Long id,
        @Column("order_code") String orderCode,
        @InsertOnlyProperty
        @Column("source_channel") String sourceChannel,
        String status
) {
}
```

`sourceChannel` vẫn có thể được ghi trong insert nếu entity cung cấp giá trị; khi update, Spring Data không ghi đè thuộc tính này. Annotation này không có nghĩa “bỏ cột để dùng database default”. Nếu mục tiêu là để database luôn tạo giá trị, `@ReadOnlyProperty` phù hợp hơn.

## 3. Cột identity và khóa chính được sinh

### 3.1. Khai báo ID do database cấp

Ví dụ PostgreSQL:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email VARCHAR(254) NOT NULL UNIQUE
);
```

Entity:

```java
@Table("customers")
public record CustomerEntity(
        @Id Long id,
        String email
) {
}
```

Khi tạo entity mới, `id` thường là `null`. Spring Data nhận diện entity mới và thực hiện insert; database cấp ID theo identity strategy. `save` phát ra entity đã lưu, thường có ID được gán từ giá trị generated key do driver trả về.

```java
CustomerEntity draft = new CustomerEntity(null, "an@example.com");

return customerRepository.save(draft)
        .map(saved -> {
            // Dùng saved.id(), không giả định draft đã được sửa tại chỗ.
            return saved;
        });
```

Với entity bất biến như record, giá trị ID mới được thể hiện trong instance được phát ra từ publisher. Luôn dùng entity trả về của `save` cho các bước tiếp theo.

### 3.2. ID không null thường có nghĩa entity đã tồn tại

Trong cơ chế nhận diện entity mới mặc định, ID khác null thường khiến Spring Data xem entity là đã tồn tại và chọn update. Nếu ứng dụng tự cấp ID trước khi insert, cần chú ý quy tắc xác định trạng thái mới/cũ. Thuộc tính `@Version` có thể tham gia vào entity state detection; hãy thiết kế ID/version nhất quán và kiểm tra hành vi theo phiên bản Spring Data.

Không tự gán một ID giả chỉ để tránh generated key. Nếu dùng UUID do ứng dụng cấp, hãy chọn chiến lược ID phù hợp và bảo đảm repository biết entity đó là mới bằng cơ chế được Spring Data hỗ trợ.

### 3.3. GENERATED BY DEFAULT và GENERATED ALWAYS

Một số database hỗ trợ identity với hai chính sách:

- `GENERATED BY DEFAULT`: database tạo ID khi ứng dụng không cung cấp giá trị; có thể cho phép giá trị tường minh theo quy tắc database.
- `GENERATED ALWAYS`: database yêu cầu giá trị identity do chính database sinh, trừ cú pháp override đặc biệt được cho phép.

Chọn loại phù hợp với chính sách cấp ID. Nếu ID luôn do database quản lý, không gửi giá trị thủ công từ ứng dụng. Cú pháp cụ thể khác nhau giữa PostgreSQL, SQL Server, MySQL và các hệ quản trị khác.

### 3.4. Khả năng trả generated values phụ thuộc driver và dialect

Spring Data R2DBC sử dụng khả năng generated values của R2DBC driver và dialect để nhận ID sau insert. Các database/driver có mức hỗ trợ khác nhau. Generated ID thường là trường hợp phổ biến được framework xử lý, nhưng không nên suy rộng rằng mọi cột default, trigger hoặc generated expression đều luôn được trả về trong cùng thao tác `save`.

Nếu ứng dụng cần các giá trị generated khác ID, hãy xác nhận dialect/driver có trả các cột đó hay không. Khi không được trả về, đọc lại entity sau insert trong một truy vấn tiếp theo hoặc dùng SQL có `RETURNING` nếu database hỗ trợ và đường truy vấn được thiết kế phù hợp.

## 4. Generated/computed columns

Generated column là cột có giá trị được database tính từ biểu thức trên các cột khác. Ứng dụng không nên gửi giá trị vào cột này vì database là nguồn tạo ra nó.

Ví dụ PostgreSQL:

```sql
CREATE TABLE order_lines (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    quantity INTEGER NOT NULL,
    unit_price NUMERIC(19, 2) NOT NULL,
    line_total NUMERIC(19, 2)
        GENERATED ALWAYS AS (quantity * unit_price) STORED
);
```

Entity:

```java
@Table("order_lines")
public record OrderLineEntity(
        @Id Long id,
        Integer quantity,
        @Column("unit_price") BigDecimal unitPrice,
        @ReadOnlyProperty
        @Column("line_total") BigDecimal lineTotal
) {
}
```

`lineTotal` được đọc từ database nhưng không được ghi từ entity. Khi `quantity` hoặc `unitPrice` thay đổi, database tính lại giá trị theo quy tắc generated column.

### 4.1. Generated column khác DEFAULT

`DEFAULT` chỉ được dùng khi insert không cung cấp giá trị cho cột. Generated column được tính từ biểu thức đã khai báo và có thể được tính lại khi các cột nguồn thay đổi.

Ví dụ:

- `status DEFAULT 'NEW'`: giá trị mặc định ban đầu; sau đó ứng dụng có thể update `status`.
- `line_total GENERATED ALWAYS AS (quantity * unit_price)`: giá trị được tính từ hai cột nguồn; ứng dụng không update trực tiếp `line_total`.

### 4.2. Không dùng @Transient cho generated column cần đọc

Nếu đánh dấu `lineTotal` là `@Transient`, Spring Data không map cột `line_total` từ database vào entity. Khi đó ứng dụng không nhận được giá trị đã tính, trừ khi tự map qua projection hoặc SQL callback. `@ReadOnlyProperty` phù hợp hơn khi cột cần được đọc nhưng không ghi.

### 4.3. Generated expression và giới hạn database

Khả năng generated column, kiểu expression được phép, stored/virtual và cách tính khi update khác nhau giữa các hệ quản trị. Một số database chỉ hỗ trợ expression xác định (deterministic) hoặc hạn chế tham chiếu cột khác. Hãy kiểm tra tài liệu schema của database mục tiêu và migration tương ứng.

## 5. Trigger-generated values

Trigger có thể tự điền hoặc cập nhật metadata khi insert/update. Ví dụ trigger đặt `created_at` khi insert và `updated_at` mỗi khi hàng thay đổi.

```sql
CREATE TABLE documents (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title VARCHAR(200) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL,
    updated_at TIMESTAMPTZ NOT NULL
);
```

Một trigger `BEFORE INSERT OR UPDATE` có thể gán `NEW.created_at` khi insert và `NEW.updated_at` mỗi lần update. Entity tương ứng:

```java
@Table("documents")
public record DocumentEntity(
        @Id Long id,
        String title,
        @ReadOnlyProperty
        @Column("created_at") Instant createdAt,
        @ReadOnlyProperty
        @Column("updated_at") Instant updatedAt
) {
}
```

Khi trigger là nguồn thời gian chính, đánh dấu các cột này read-only để câu lệnh ghi từ entity không ghi đè giá trị trigger. Nếu ứng dụng cũng dùng Spring Data auditing (`@CreatedDate`, `@LastModifiedDate`) để gán cùng cột, cần chọn một nguồn sở hữu rõ ràng. Hai cơ chế cùng ghi một cột có thể tạo kết quả phụ thuộc thứ tự thực thi.

### 5.1. Trigger và giá trị trả về sau insert/update

Một số database/driver có thể trả hàng đã được trigger chỉnh sửa qua cơ chế `RETURNING` hoặc generated values. Một số trường hợp chỉ trả ID hoặc không trả các cột do trigger sinh. Không giả định entity phát ra từ `save` luôn chứa mọi giá trị trigger.

Nếu cần dữ liệu mới nhất, có thể đọc lại bằng ID sau khi insert/update:

```java
return documentRepository.save(document)
        .flatMap(saved -> documentRepository.findById(saved.id()));
```

Việc đọc lại tạo thêm một lượt truy vấn. Nếu cần tính nhất quán ngay sau ghi, thực hiện trong transaction phù hợp và kiểm tra hành vi database/driver. Với SQL tùy chỉnh, có thể dùng `RETURNING` nếu dialect hỗ trợ.

## 6. Mapping generated values trong Spring Data R2DBC

### 6.1. Vai trò của @Column

`@Column` xác định tên cột tương ứng với thuộc tính Java và có thể điều khiển việc quote tên cột theo cấu hình. Nó không tự làm cột thành generated, không tự yêu cầu database dùng default và không tự ngăn ghi giá trị.

Ví dụ:

```java
@Column("created_at") Instant createdAt
```

chỉ ánh xạ `createdAt` sang `created_at`. Nếu muốn thuộc tính chỉ đọc, cần metadata phù hợp như `@ReadOnlyProperty`; nếu muốn database default được dùng, schema phải định nghĩa default và câu insert phải không cung cấp giá trị tường minh cho cột đó.

### 6.2. Vai trò của @ReadOnlyProperty

Annotation này phù hợp với cột persistent được đọc từ database nhưng không ghi qua Spring Data. Dùng cho generated column, cột trigger-managed hoặc default luôn do database cấp. Thuộc tính vẫn có thể xuất hiện trong kết quả select và được materialize vào entity.

### 6.3. Vai trò của @InsertOnlyProperty

Annotation này giữ giá trị chỉ ghi khi insert, không ghi lại trong update. Dùng khi ứng dụng muốn cung cấp giá trị ban đầu và giữ nguyên nó. Nó không phải cách chung để bỏ qua null và kích hoạt default database.

### 6.4. Vai trò của @Transient

Thuộc tính `@Transient` nằm ngoài mapping persistence. Spring Data không đọc hoặc ghi nó như một cột. Dùng cho dữ liệu tính toán trong Java hoặc trạng thái tạm thời không có trong schema.

### 6.5. Vai trò của @Id và @Version

`@Id` đánh dấu khóa chính; nếu database sinh khóa, Spring Data/driver có thể trả giá trị generated ID vào entity kết quả. `@Version` phục vụ optimistic locking và được Spring Data quản lý khi dùng thao tác persistence phù hợp. Cả hai có ngữ nghĩa riêng, không phải annotation thay thế cho `@ReadOnlyProperty` của một cột computed thông thường.

## 7. Default chỉ áp dụng khi insert, không tự áp dụng lại khi update

Giá trị `DEFAULT` trong schema thường được áp dụng khi insert bỏ qua cột. Nếu sau đó ứng dụng update cột thành `NULL`, database không tự thay null bằng default.

Ví dụ:

```sql
UPDATE orders
SET status = NULL
WHERE id = :id;
```

Lệnh này ghi null nếu schema cho phép, hoặc thất bại nếu cột `NOT NULL`. Nó không đặt lại status thành `'NEW'`.

Nếu muốn khôi phục default bằng SQL, có thể dùng cú pháp:

```sql
UPDATE orders
SET status = DEFAULT
WHERE id = :id;
```

Khả năng và cú pháp `SET column = DEFAULT` phụ thuộc database. Nếu API có hành động “reset về mặc định”, hãy biểu diễn hành động đó rõ ràng thay vì dùng null làm tín hiệu mơ hồ.

## 8. Phân biệt null, không cung cấp và giá trị mặc định trong API

Một request update có thể cần phân biệt ba trạng thái:

1. Không gửi thuộc tính: giữ nguyên giá trị hiện tại.
2. Gửi `null`: xóa giá trị nếu cột nullable và nghiệp vụ cho phép.
3. Gửi một giá trị cụ thể: thay bằng giá trị đó.

Với request insert, có thể có thêm ý nghĩa “để database tự áp dụng default”. Không phải DTO đơn giản với một trường nullable luôn phân biệt được các trường hợp này. Nếu cần, dùng kiểu biểu diễn sự hiện diện như wrapper `FieldUpdate<T>`, JSON Merge Patch semantics hoặc các command riêng.

Ví dụ thiết kế command:

```java
public sealed interface FieldValue<T> {
    record Omitted<T>() implements FieldValue<T> {}
    record ExplicitNull<T>() implements FieldValue<T> {}
    record Present<T>(T value) implements FieldValue<T> {}
}
```

Tầng Service diễn giải từng trạng thái rồi quyết định giữ nguyên, ghi null, ghi giá trị hoặc bỏ cột để database dùng default. Không chuyển cả ba trạng thái thành `null` trước khi persistence layer nhận được command.

## 9. Dùng DatabaseClient khi cần điều khiển DEFAULT tường minh

Nếu cần chọn động giữa bỏ cột và chỉ định `DEFAULT`, SQL tùy chỉnh có thể biểu diễn rõ hơn mapping entity thông thường.

### 9.1. Insert bỏ qua cột

```java
return databaseClient.sql("""
        INSERT INTO orders (order_code)
        VALUES (:orderCode)
        RETURNING id, order_code, status, created_at
        """)
        .bind("orderCode", orderCode)
        .map((row, metadata) -> new OrderInsertResult(
                row.get("id", Long.class),
                row.get("order_code", String.class),
                row.get("status", String.class),
                row.get("created_at", OffsetDateTime.class)))
        .one();
```

Ví dụ dùng cú pháp `RETURNING` của PostgreSQL để nhận các cột sau insert. `RETURNING` không phải cú pháp SQL portable cho mọi database; cần dùng cách generated values tương ứng với dialect/driver khác. Kiểu Java đọc từ `created_at` cũng cần xác nhận theo driver và conversion đã cấu hình.

### 9.2. Dùng DEFAULT tường minh

```java
return databaseClient.sql("""
        INSERT INTO orders (order_code, status)
        VALUES (:orderCode, DEFAULT)
        RETURNING id, order_code, status
        """)
        .bind("orderCode", orderCode)
        .map((row, metadata) -> /* map result */)
        .one();
```

Không thể bind từ khóa `DEFAULT` như một giá trị parameter. Nó là cú pháp SQL. Nếu muốn tùy chọn cột, hãy xây dựng một trong các câu SQL đã được ứng dụng định nghĩa trước, rồi bind các giá trị dữ liệu; không nối trực tiếp nội dung request vào SQL.

### 9.3. Tách đường insert theo lựa chọn

Nếu request cho phép client hoặc nghiệp vụ chọn trạng thái ban đầu, có thể có hai câu insert:

- Có status: insert `(order_code, status)` với `:status`.
- Dùng default: insert chỉ `(order_code)` hoặc dùng `DEFAULT`.

Cả hai câu lệnh đều phải bind giá trị an toàn. Việc chọn câu nào do enum/command nội bộ quyết định, không do chuỗi SQL tùy ý từ client.

## 10. Generated values và entity bất biến

Entity bất biến không có setter để nhận giá trị database sinh. Spring Data có thể tạo instance mới bằng constructor mapping hoặc cơ chế wither phù hợp để đưa generated ID/giá trị được trả về vào entity.

Ví dụ record:

```java
@Table("orders")
public record OrderEntity(
        @Id Long id,
        @Column("order_code") String orderCode,
        String status,
        @ReadOnlyProperty
        @Column("created_at") Instant createdAt
) {
}
```

Sau khi lưu:

```java
return repository.save(new OrderEntity(
        null, "ORD-000123", "NEW", null));
```

Hãy dùng instance được phát ra từ `save`. Tuy nhiên, chỉ dựa vào việc entity là record không bảo đảm mọi cột generated được driver trả về. Nếu `createdAt` chưa có trong instance trả về, đọc lại theo ID hoặc dùng câu SQL có cơ chế trả generated values phù hợp.

Với class bất biến có nhiều constructor, bảo đảm Spring Data chọn đúng persistence constructor bằng quy ước hoặc `@PersistenceCreator`. Tên tham số phải tương ứng property Java, còn `@Column` xử lý tên cột database.

## 11. Auditing và database defaults có thể xung đột

Spring Data auditing có thể điền `@CreatedDate` và `@LastModifiedDate` trước khi ghi entity. Database cũng có thể định nghĩa `DEFAULT CURRENT_TIMESTAMP` hoặc trigger cập nhật timestamp.

Nếu cả hai cùng quản lý một cột, cần chọn một nguồn chính:

- **Ứng dụng quản lý:** dùng `@CreatedDate`/`@LastModifiedDate`; database có thể không cần default hoặc default chỉ là dự phòng cho writer khác.
- **Database quản lý:** dùng `@ReadOnlyProperty` cho cột được trigger/default quản lý; không để auditing ghi cùng thuộc tính.
- **Nhiều writer độc lập:** cân nhắc trigger/database-level audit để mọi writer tuân theo cùng quy tắc.

Không dùng `@CreatedDate` và `@ReadOnlyProperty` cùng một thuộc tính nếu mục tiêu là auditing callback phải ghi giá trị vào cột; hai annotation thể hiện hai chính sách ghi khác nhau. Hãy quyết định rõ trước khi khai báo entity.

## 12. Kiểm thử default và generated columns

Mock Repository không đủ để kiểm tra database có áp dụng default hoặc generated expression đúng hay không. Cần integration test với schema và driver thực tế.

### 12.1. Kiểm thử database default

Tạo entity bỏ qua cột read-only có default, insert qua Repository, sau đó đọc lại và xác nhận database đã gán giá trị:

```java
StepVerifier.create(orderRepository.save(newOrder))
        .assertNext(saved -> {
            assertThat(saved.id()).isNotNull();
        })
        .verifyComplete();

StepVerifier.create(orderRepository.findById(savedId))
        .assertNext(found -> {
            assertThat(found.status()).isEqualTo("NEW");
            assertThat(found.createdAt()).isNotNull();
        })
        .verifyComplete();
```

Ví dụ minh họa cần giữ `savedId` từ entity trả về trong test thực tế. Nếu generated columns được driver trả ngay sau insert, có thể kiểm tra trực tiếp entity `saved`; nếu không, follow-up select là cách xác nhận giá trị đã được lưu.

### 12.2. Kiểm thử null tường minh

Dùng `DatabaseClient` hoặc SQL test để insert `NULL` cho cột nullable và xác nhận kết quả là null thay vì default. Đây là kiểm tra quan trọng để chứng minh sự khác biệt giữa omission và explicit null.

### 12.3. Kiểm thử generated column

Insert/update các cột nguồn rồi đọc lại `line_total`. Xác nhận database tự tính đúng và ứng dụng không cố ghi vào generated column. Nếu SQL update cố thay đổi generated column, database thường từ chối.

### 12.4. Kiểm thử trigger-generated values

Thực hiện insert và update rồi đọc lại timestamp/actor. Xác nhận trigger được gọi trên đúng loại thao tác và giá trị do trigger tạo không bị ứng dụng ghi đè.

### 12.5. Kiểm thử entity mapping

Kiểm tra:

- `@ReadOnlyProperty` vẫn đọc cột vào entity.
- `@ReadOnlyProperty` không đưa cột vào insert/update thông thường.
- `@InsertOnlyProperty` được ghi khi insert và không ghi lại khi update.
- `@Transient` không tham gia đọc/ghi persistence.
- `@Column` ánh xạ đúng tên cột khác biệt với tên property.
- Generated ID được nhận từ `save` và code dùng instance trả về.

## 13. Lỗi thường gặp

### Mong rằng Java null sẽ kích hoạt DEFAULT

Nếu câu SQL vẫn chỉ định cột và bind `NULL`, database không dùng default. Bỏ cột khỏi insert hoặc dùng `DEFAULT` tường minh.

### Dùng @Transient cho cột generated cần đọc

`@Transient` loại thuộc tính khỏi mapping. Dùng `@ReadOnlyProperty` nếu cần đọc cột nhưng không ghi.

### Dùng @InsertOnlyProperty để kích hoạt default

Annotation này chỉ ngăn ghi thuộc tính khi update; nó vẫn là thuộc tính được ghi ở insert nếu có giá trị. Nếu muốn database luôn tạo cột, dùng read-only mapping hoặc SQL insert bỏ cột.

### Cho rằng @Column tự làm cột read-only

`@Column` chủ yếu xác định tên cột và mapping liên quan. Nó không thay thế `@ReadOnlyProperty`.

### Cố ghi vào generated/computed column

Database có thể từ chối vì cột được tính tự động. Đánh dấu read-only và chỉ ghi các cột nguồn.

### Mong mọi giá trị trigger được trả về từ save

Driver/dialect có thể chỉ trả generated ID hoặc tập cột được hỗ trợ. Đọc lại entity hoặc dùng `RETURNING` khi database hỗ trợ.

### Nghĩ DEFAULT áp dụng cho UPDATE

Default không tự chạy lại khi update cột thành null. Dùng `SET column = DEFAULT` nếu database hỗ trợ và nghiệp vụ yêu cầu reset.

### Vừa dùng auditing callback vừa dùng trigger cho cùng cột

Hai nguồn ghi có thể ghi đè nhau. Chọn một chủ sở hữu chính hoặc quy định rõ thứ tự và phạm vi.

### Dùng entity trả về cũ sau save

Entity bất biến không nhận generated ID/values tại chỗ. Dùng instance phát ra từ publisher hoặc đọc lại theo ID.

### Chỉ kiểm tra bằng unit test

Default, identity, generated column và trigger là hành vi của database/driver. Cần integration test trên hệ quản trị thực tế.

## 14. Quy trình thiết kế entity có cột do database quản lý

1. Phân loại từng cột: ứng dụng cung cấp, database default, identity, generated expression hay trigger-managed.
2. Xác định default có chỉ dùng khi insert hay cần reset khi update.
3. Thiết kế schema với kiểu dữ liệu, nullability, default expression và generation rule phù hợp.
4. Khai báo `@Id` cho khóa chính do database cấp.
5. Dùng `@ReadOnlyProperty` cho cột cần đọc nhưng database là nguồn ghi chính.
6. Dùng `@InsertOnlyProperty` cho giá trị ứng dụng cung cấp khi insert nhưng giữ nguyên khi update.
7. Dùng `@Transient` cho thuộc tính không thuộc schema.
8. Dùng `@Column` để ánh xạ tên property và tên cột; không nhầm nó với chính sách read-only.
9. Kiểm tra SQL insert thực tế để bảo đảm cột default được bỏ qua thay vì bind null.
10. Xác nhận driver/dialect trả generated ID và các generated values cần thiết.
11. Nếu giá trị không được trả ngay, đọc lại entity hoặc dùng SQL `RETURNING` theo database.
12. Viết migration và integration test cho insert, update, null, default, generated expression và trigger.

## 15. Checklist ghi nhớ

- [ ] Đã phân biệt default, identity, generated column và trigger-generated value.
- [ ] Hiểu rõ omission, `DEFAULT` và explicit `NULL` có ý nghĩa khác nhau.
- [ ] Không giả định thuộc tính Java null tự làm database áp dụng default.
- [ ] `@ReadOnlyProperty` được dùng cho cột đọc được nhưng không ghi qua mapping.
- [ ] `@InsertOnlyProperty` chỉ dùng cho giá trị được ghi lúc insert và giữ nguyên khi update.
- [ ] `@Transient` chỉ dùng cho thuộc tính không thuộc persistence mapping.
- [ ] `@Column` không bị nhầm với chính sách generated/read-only.
- [ ] Generated ID được lấy từ entity trả về của `save`.
- [ ] Generated columns không bị ứng dụng cố ghi trực tiếp.
- [ ] Generated values ngoài ID đã được xác nhận theo driver/dialect.
- [ ] Auditing callback và trigger không cùng ghi một cột ngoài ý muốn.
- [ ] Raw SQL/DatabaseClient tự quản lý default và audit columns khi cần.
- [ ] API phân biệt không cung cấp, null tường minh và yêu cầu dùng default nếu nghiệp vụ cần.
- [ ] Integration test chạy trên database/driver mục tiêu.

Default và generated columns giúp database giữ các quy tắc dữ liệu ở một nơi, nhưng Spring Data R2DBC chỉ có thể ánh xạ đúng khi entity thể hiện rõ cột nào được ghi và cột nào chỉ đọc. Hiểu sự khác nhau giữa bỏ cột, gửi null, dùng `DEFAULT`, identity, computed column và trigger giúp tránh lỗi insert/update khó phát hiện. Khi dùng đúng `@ReadOnlyProperty`, `@InsertOnlyProperty`, `@Transient` và `@Id`, đồng thời xác nhận generated values qua driver/dialect, entity có thể phản ánh chính xác trạng thái mà database đã lưu.
