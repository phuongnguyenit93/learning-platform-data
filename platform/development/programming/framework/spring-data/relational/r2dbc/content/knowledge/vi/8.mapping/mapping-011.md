# Phân biệt giá trị mặc định trong Java với giá trị mặc định của cơ sở dữ liệu

## 1. Hai nơi có thể cung cấp giá trị mặc định

Khi tạo một bản ghi bằng Spring Data R2DBC, một thuộc tính có thể nhận giá trị mặc định từ hai nơi khác nhau:

- **Java:** giá trị do JVM, field initializer, constructor, factory method hoặc logic nghiệp vụ của ứng dụng gán cho object.
- **Cơ sở dữ liệu:** giá trị được định nghĩa trong schema bằng `DEFAULT`, identity, sequence, generated column hoặc trigger theo khả năng của hệ quản trị.

Hai cơ chế này hoạt động ở hai thời điểm khác nhau. Java tạo và khởi tạo object trước khi ứng dụng gửi lệnh ghi. Database áp dụng default khi thực thi câu lệnh SQL nếu câu lệnh cho phép database sử dụng giá trị đó.

Ví dụ, ứng dụng có entity `Task` với thuộc tính `status`. Java có thể khởi tạo `status` thành `PENDING`; database cũng có thể định nghĩa `status DEFAULT 'PENDING'`. Kết quả nhìn thấy có thể giống nhau, nhưng nguồn quyết định khác nhau:

- Nếu Java gán `PENDING` và câu INSERT ghi giá trị đó, database nhận giá trị do ứng dụng gửi.
- Nếu câu INSERT bỏ cột `status`, database mới có cơ hội áp dụng `DEFAULT 'PENDING'`.
- Nếu câu INSERT gửi `NULL`, database nhận `NULL`; default thông thường không tự thay thế giá trị `NULL`.

Trong Spring Data R2DBC, cần hiểu cả vòng đời object Java lẫn câu SQL mà mapping layer tạo ra. Chỉ nhìn giá trị field trong debugger chưa đủ để biết database sẽ dùng default nào.

## 2. Giá trị mặc định khi Java tạo object

Khi một object được tạo, JVM khởi tạo các field trước khi chạy phần khởi tạo field và constructor của class. Nếu lập trình viên không gán giá trị, Java sử dụng giá trị mặc định theo kiểu dữ liệu.

| Kiểu field | Giá trị mặc định của Java |
| --- | --- |
| `byte`, `short`, `int`, `long` | `0` |
| `float`, `double` | `0.0` |
| `char` | ký tự Unicode `\u0000` |
| `boolean` | `false` |
| Kiểu tham chiếu như `String`, `Integer`, `Long`, entity khác | `null` |

Ví dụ:

```java
public class Task {
    private Long id;
    private String title;
    private int retryCount;
    private boolean enabled;
    private String status;
}
```

Khi tạo `new Task()`, nếu không có constructor hoặc field initializer khác, các field có giá trị:

```text
id          = null
title       = null
retryCount  = 0
enabled     = false
status      = null
```

Đây là giá trị trong bộ nhớ Java. Chúng chưa phải là giá trị đã được ghi vào database.

### 2.1. Field initializer và constructor

Ứng dụng có thể khai báo giá trị khởi tạo ngay tại field:

```java
public class Task {
    private Long id;
    private String title;
    private int retryCount = 3;
    private boolean enabled = true;
    private String status = "PENDING";
}
```

Hoặc gán trong constructor/factory method:

```java
public class Task {

    private Long id;
    private String title;
    private int retryCount;
    private boolean enabled;
    private String status;

    public static Task create(String title) {
        Task task = new Task();
        task.title = title;
        task.retryCount = 3;
        task.enabled = true;
        task.status = "PENDING";
        return task;
    }
}
```

Các giá trị `3`, `true` và `PENDING` là chính sách khởi tạo của ứng dụng. Nếu Spring Data R2DBC ghi các thuộc tính này vào câu INSERT, database sẽ nhận các giá trị tường minh đó. Default trong schema sẽ không được dùng cho những cột đã có giá trị được gửi lên.

### 2.2. Primitive và wrapper có ý nghĩa khác nhau

Một field primitive như `int` luôn có giá trị số, ít nhất là `0`; nó không thể biểu diễn trạng thái “chưa cung cấp”. Wrapper `Integer` có thể là `null`:

```java
private int retryCount;       // mặc định Java là 0
private Integer maxAttempts;  // mặc định Java là null
```

Sự khác biệt này quan trọng khi cần phân biệt:

- Người dùng chủ động chọn `0`.
- Ứng dụng chưa nhận được giá trị.
- Ứng dụng muốn database tự áp dụng default.

Tuy nhiên, đổi `int` thành `Integer` chỉ giúp Java biểu diễn được `null`; điều đó không tự động làm cho Spring Data R2DBC bỏ cột khỏi câu INSERT. `null` và “không gửi cột” là hai trạng thái khác nhau ở tầng SQL.

## 3. Giá trị mặc định do cơ sở dữ liệu cung cấp

Database định nghĩa default trong schema. Ví dụ PostgreSQL:

```sql
CREATE TABLE task (
    id           BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title        VARCHAR(200) NOT NULL,
    status       VARCHAR(30) NOT NULL DEFAULT 'PENDING',
    retry_count  INTEGER NOT NULL DEFAULT 3,
    enabled      BOOLEAN NOT NULL DEFAULT TRUE,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

Ở đây, database có thể tự cung cấp:

- `id` thông qua identity.
- `status` bằng `PENDING`.
- `retry_count` bằng `3`.
- `enabled` bằng `TRUE`.
- `created_at` bằng thời điểm hiện tại theo đồng hồ database.

Các default này thuộc schema và được áp dụng khi câu lệnh INSERT không cung cấp giá trị cho cột hoặc yêu cầu rõ `DEFAULT`.

### 3.1. Bỏ cột khỏi INSERT

Khi bỏ một cột khỏi danh sách INSERT, database có thể áp dụng default của cột đó:

```sql
INSERT INTO task (title)
VALUES ('Send welcome email');
```

Database tự điền các cột còn lại theo schema:

```text
title        = 'Send welcome email'
status       = 'PENDING'
retry_count  = 3
enabled      = TRUE
created_at   = thời điểm hiện tại của database
id           = giá trị identity được cấp
```

Đây là cách rõ ràng để yêu cầu database áp dụng default cho các cột không xuất hiện trong câu INSERT.

### 3.2. Dùng từ khóa `DEFAULT`

SQL cũng cho phép yêu cầu default tường minh cho một cột trong nhiều hệ quản trị:

```sql
INSERT INTO task (title, status, retry_count)
VALUES ('Send receipt', DEFAULT, DEFAULT);
```

Trong ví dụ này, database áp dụng default cho `status` và `retry_count`. Cú pháp chi tiết có thể khác theo hệ quản trị; cần tham khảo tài liệu của database đang dùng.

### 3.3. Gửi `NULL` không giống bỏ cột

Đây là khác biệt quan trọng nhất:

```sql
-- Database có thể áp dụng DEFAULT 'PENDING'
INSERT INTO task (title)
VALUES ('Task A');

-- Database nhận NULL cho status; default không tự thay thế NULL
INSERT INTO task (title, status)
VALUES ('Task B', NULL);
```

Nếu cột `status` có ràng buộc `NOT NULL`, câu lệnh thứ hai thường thất bại vì đã gửi `NULL`. Nếu cột cho phép null, giá trị được lưu là `NULL`, không phải `PENDING`.

Có thể ghi nhớ ba ý nghĩa riêng biệt:

| Cách ghi | Ý nghĩa |
| --- | --- |
| Không đưa cột vào danh sách INSERT | Cho database quyết định theo default hoặc nullable của cột |
| Gửi từ khóa `DEFAULT` | Yêu cầu database dùng default được định nghĩa |
| Gửi giá trị `NULL` | Yêu cầu lưu SQL NULL, nếu schema cho phép |

## 4. So sánh trực tiếp Java default và database default

| Tiêu chí | Giá trị mặc định Java | Giá trị mặc định database |
| --- | --- | --- |
| Nơi định nghĩa | Field, constructor, factory hoặc logic ứng dụng | DDL/schema, identity, sequence, generated expression hoặc trigger |
| Thời điểm áp dụng | Khi tạo object hoặc chạy logic ứng dụng | Khi database thực thi câu lệnh phù hợp |
| Phạm vi | Các object được khởi tạo bởi logic Java đó | Mọi client ghi vào database theo quy tắc schema |
| Phụ thuộc kết nối database | Không | Có |
| Có thể bị giá trị gửi lên ghi đè | Giá trị sau có thể thay đổi field | Có, nếu INSERT gửi giá trị tường minh thay vì bỏ cột hoặc dùng DEFAULT |
| Thể hiện `NULL` | Field tham chiếu có thể là `null` | SQL `NULL` là một giá trị riêng, khác default |
| Đồng hồ thời gian | Thường dùng đồng hồ của tiến trình ứng dụng | Có thể dùng đồng hồ của database |

Hai cơ chế không loại trừ nhau. Một ứng dụng có thể đặt default trong Java để object có trạng thái hợp lệ trước khi lưu, đồng thời có default trong database để bảo vệ dữ liệu khi một client khác ghi vào. Nhưng cần xác định rõ nguồn nào là thẩm quyền và cách ghi nào được sử dụng.

## 5. Điều gì xảy ra khi Spring Data R2DBC lưu entity?

Spring Data R2DBC dùng mapping metadata và converter để chuyển entity Java thành dữ liệu ghi xuống database. Repository hoặc `R2dbcEntityTemplate` sau đó tạo câu lệnh SQL phù hợp và thực thi thông qua R2DBC SPI.

Ví dụ entity:

```java
@Table("task")
public class Task {

    @Id
    private Long id;

    private String title;
    private String status;
    private Integer retryCount;
}
```

Giả sử ứng dụng tạo object:

```java
Task task = new Task();
task.setTitle("Send welcome email");
task.setStatus("PENDING");
task.setRetryCount(3);
```

Khi lưu, các giá trị `PENDING` và `3` đã tồn tại trong object. Mapping layer có thể ghi các giá trị đó vào câu INSERT. Khi database nhận giá trị tường minh, default của cột không được sử dụng.

Điểm cần chú ý là thuộc tính Java có giá trị `null` không đồng nghĩa với việc cột chắc chắn bị loại khỏi câu INSERT. Mapping layer có thể biểu diễn `null` thành tham số SQL NULL. Cách tạo câu lệnh phụ thuộc mapping metadata, annotation, API ghi và phiên bản Spring Data Relational đang dùng. Vì vậy, không nên thiết kế dựa trên giả định “field null thì database tự áp dụng default”. Hãy kiểm tra SQL và bind parameter thực tế hoặc chủ động điều khiển danh sách cột được INSERT.

### 5.1. Java đã gán default thì database không tự thay thế

Ví dụ:

```java
public class Task {
    private String status = "PENDING";
}
```

Nếu câu INSERT gửi `status = 'PENDING'`, database chỉ lưu giá trị đó. Ngay cả khi schema có `DEFAULT 'NEW'`, database cũng không đổi giá trị gửi lên thành `NEW`.

Điều này có thể tạo ra sự khác nhau nếu Java và schema khai báo default không đồng nhất:

```java
private String status = "PENDING";
```

```sql
status VARCHAR(30) NOT NULL DEFAULT 'NEW'
```

Các bản ghi tạo qua ứng dụng Java có thể nhận `PENDING`, trong khi các bản ghi tạo từ SQL client khác có thể nhận `NEW`. Nếu đây không phải chủ ý, cần thống nhất chính sách mặc định và cập nhật cả code lẫn migration schema.

### 5.2. `null` không phải cơ chế bỏ cột đáng tin cậy

Ví dụ:

```java
Task task = new Task();
task.setTitle("Send welcome email");
task.setStatus(null);
```

Chỉ từ object này, không thể kết luận chắc chắn database sẽ nhận default. Nếu mapping tạo `INSERT INTO task (title, status) VALUES (?, ?)` và bind tham số thứ hai là SQL NULL, default không chạy.

Khi cần database cung cấp giá trị, hãy dùng cách đảm bảo cột không được ghi trong câu INSERT hoặc dùng `DEFAULT` tường minh. Với Spring Data Relational, có thể cân nhắc `@ReadOnlyProperty` cho thuộc tính do database quản lý hoàn toàn, hoặc dùng SQL tường minh qua `DatabaseClient` khi cần điều khiển chính xác từng cột.

## 6. Dùng `@ReadOnlyProperty` cho thuộc tính do database quản lý

Spring Data cung cấp annotation `@ReadOnlyProperty` trong package `org.springframework.data.annotation`. Annotation này đánh dấu thuộc tính chỉ đọc đối với thao tác ghi của Spring Data: thuộc tính vẫn có thể được đọc từ database và ánh xạ vào entity, nhưng không được ghi như thuộc tính thông thường.

Ví dụ, database luôn chịu trách nhiệm tạo `status` và `created_at`:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.ReadOnlyProperty;
import org.springframework.data.relational.core.mapping.Table;

import java.time.OffsetDateTime;

@Table("task")
public class Task {

    @Id
    private Long id;

    private String title;

    @ReadOnlyProperty
    private String status;

    @ReadOnlyProperty
    private OffsetDateTime createdAt;
}
```

Với schema:

```sql
CREATE TABLE task (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title VARCHAR(200) NOT NULL,
    status VARCHAR(30) NOT NULL DEFAULT 'PENDING',
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

Các thuộc tính `status` và `createdAt` được đánh dấu chỉ đọc nên Spring Data không ghi giá trị Java của chúng trong thao tác ghi thông thường. Điều này cho phép database áp dụng default khi tạo bản ghi.

`@ReadOnlyProperty` phù hợp khi ứng dụng không được phép tự đặt hoặc sửa thuộc tính đó. Nếu có use case cần gửi một giá trị `status` cụ thể, annotation này không phù hợp cho thuộc tính đó vì nó luôn loại thuộc tính khỏi thao tác ghi theo mapping.

Annotation cũng không có nghĩa entity Java tự động nhận mọi giá trị default sau INSERT. Việc giá trị database sinh ra có được trả về và gán lại vào object hay không phụ thuộc cơ chế generated values, driver, dialect và API insert đang dùng. Nếu cần giá trị chắc chắn ngay sau khi ghi, hãy sử dụng cơ chế trả về phù hợp hoặc truy vấn lại bản ghi.

## 7. Dùng `DatabaseClient` khi cần bỏ cột một cách tường minh

Nếu muốn kiểm soát chính xác câu INSERT để database áp dụng default, có thể dùng `DatabaseClient` và chỉ liệt kê những cột ứng dụng thực sự cung cấp.

Ví dụ PostgreSQL:

```java
public Mono<Task> createTask(DatabaseClient databaseClient, String title) {
    return databaseClient.sql("""
            INSERT INTO task (title)
            VALUES (:title)
            RETURNING id, title, status, retry_count, enabled, created_at
            """)
            .bind("title", title)
            .map((row, metadata) -> new Task(
                    row.get("id", Long.class),
                    row.get("title", String.class),
                    row.get("status", String.class),
                    row.get("retry_count", Integer.class),
                    row.get("enabled", Boolean.class),
                    row.get("created_at", OffsetDateTime.class)))
            .one();
}
```

Ví dụ giả định `Task` có constructor tương ứng. `RETURNING` là cú pháp PostgreSQL dùng để trả các giá trị của hàng vừa được insert, bao gồm những cột database tự sinh hoặc áp dụng default. Các database khác có thể dùng cú pháp hoặc API generated values khác.

Điểm quan trọng là câu INSERT chỉ liệt kê `title`. Database tự cung cấp `status`, `retry_count`, `enabled`, `created_at` và `id` theo schema. `RETURNING` giúp ứng dụng nhận lại những giá trị đã được database quyết định trong cùng thao tác.

Nếu không có `RETURNING` hoặc cơ chế trả generated values tương ứng, ứng dụng có thể thực hiện một truy vấn đọc sau khi insert để lấy trạng thái đầy đủ. Khi làm vậy, cần xác định khóa nhận diện bản ghi vừa tạo và transaction phù hợp.

### 7.1. Dùng `DEFAULT` tường minh

Nếu muốn một câu SQL truyền giá trị cho một số cột và yêu cầu database tự chọn default cho các cột khác, có thể viết:

```java
databaseClient.sql("""
        INSERT INTO task (title, status, retry_count)
        VALUES (:title, DEFAULT, DEFAULT)
        RETURNING id, title, status, retry_count
        """)
        .bind("title", title)
        .map((row, metadata) -> /* map kết quả */)
        .one();
```

Đây là cách thể hiện rõ ý định “dùng default” trong SQL. Không cần bind tham số cho vị trí có từ khóa `DEFAULT`. Cần xác nhận cú pháp trên database và driver cụ thể.

### 7.2. Khi có lựa chọn giữa giá trị ứng dụng và default database

Giả sử use case cho phép người dùng chọn `status`; nếu không cung cấp thì database dùng default. Cần phân biệt hai trường hợp “không cung cấp” và “cung cấp NULL”. Có thể tạo hai nhánh SQL có danh sách cột khác nhau:

```java
if (status == null) {
    return databaseClient.sql("""
            INSERT INTO task (title)
            VALUES (:title)
            RETURNING id, title, status
            """)
            .bind("title", title)
            .map((row, metadata) -> /* map kết quả */)
            .one();
}

return databaseClient.sql("""
        INSERT INTO task (title, status)
        VALUES (:title, :status)
        RETURNING id, title, status
        """)
        .bind("title", title)
        .bind("status", status)
        .map((row, metadata) -> /* map kết quả */)
        .one();
```

Đoạn mã chỉ minh họa cách tách hai trường hợp. Trong ứng dụng thực tế, nên đóng gói việc xây dựng câu lệnh và mapping vào repository hoặc persistence adapter, không đặt SQL trực tiếp trong controller. Tên bảng và tên cột phải là hằng số hoặc được kiểm soát; không nối chuỗi identifier từ dữ liệu người dùng.

## 8. Chọn nơi đặt default theo trách nhiệm dữ liệu

Không có quy tắc rằng mọi default phải nằm trong Java hoặc mọi default phải nằm trong database. Nơi đặt default phụ thuộc ý nghĩa của dữ liệu và ai là bên có thẩm quyền.

### 8.1. Đặt default trong Java khi đó là quy tắc domain

Ví dụ, một đối tượng yêu cầu mới luôn bắt đầu ở trạng thái `DRAFT`. Đây có thể là một quy tắc domain, không chỉ là chi tiết lưu trữ:

```java
public class PurchaseOrder {

    private OrderStatus status;

    private PurchaseOrder() {
        this.status = OrderStatus.DRAFT;
    }

    public static PurchaseOrder create() {
        return new PurchaseOrder();
    }
}
```

Factory method bảo đảm object mới được tạo qua domain API có trạng thái hợp lệ. Khi lưu, ứng dụng có thể ghi `DRAFT` xuống database. Schema vẫn nên có `NOT NULL` và có thể có `DEFAULT` như lớp bảo vệ bổ sung cho các client khác, nhưng quy tắc nghiệp vụ được thể hiện trong domain model.

### 8.2. Đặt default trong database khi database là nguồn có thẩm quyền

Một số giá trị được quyết định tốt nhất ở database:

- `created_at` dùng đồng hồ database để mọi ứng dụng cùng ghi có một nguồn thời gian nhất quán.
- ID identity hoặc sequence do database cấp.
- Cờ trạng thái mặc định dùng chung cho nhiều client khác nhau.
- Giá trị được tạo từ expression hoặc trigger theo chính sách dữ liệu tập trung.

Ví dụ:

```sql
created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
```

Nếu Java tự gán `Instant.now()`, thời gian phụ thuộc đồng hồ và cấu hình timezone của từng instance ứng dụng. Nếu database gán `CURRENT_TIMESTAMP`, nguồn thời gian nằm ở database. Hai giá trị có thể chênh lệch nếu đồng hồ không đồng bộ hoặc transaction được xử lý trong các thời điểm khác nhau.

### 8.3. Kết hợp hai lớp nhưng phải thống nhất

Một ứng dụng có thể khởi tạo default trong Java để object luôn hợp lệ và khai báo default trong database để bảo vệ dữ liệu khi có client khác. Tuy nhiên, cần giữ hai chính sách đồng nhất và xác định cách ghi.

Ví dụ, cả Java và schema đều dùng `PENDING`. Nếu một SQL client khác bỏ cột status, database vẫn tạo `PENDING`. Nếu ứng dụng Java tạo object và ghi `PENDING`, kết quả cũng là `PENDING`. Nếu thay đổi default thành `QUEUED`, cần cập nhật cả factory/domain logic và migration schema nếu đó là thay đổi nghiệp vụ mong muốn.

Không nên duy trì hai default khác nhau một cách vô tình, vì dữ liệu tạo từ các đường ghi khác nhau sẽ có hành vi khác nhau.

## 9. Default, NULL và ràng buộc NOT NULL

Default và `NOT NULL` giải quyết hai vấn đề khác nhau:

- `DEFAULT` cung cấp giá trị khi INSERT bỏ cột hoặc dùng từ khóa `DEFAULT`.
- `NOT NULL` ngăn lưu SQL NULL vào cột.

Ví dụ:

```sql
status VARCHAR(30) NOT NULL DEFAULT 'PENDING'
```

Kết hợp hai thuộc tính này có nghĩa:

- INSERT bỏ `status`: database dùng `PENDING`.
- INSERT ghi `DEFAULT` cho `status`: database dùng `PENDING`.
- INSERT ghi `NULL` cho `status`: database từ chối do `NOT NULL`.
- INSERT ghi `'ACTIVE'`: database lưu `'ACTIVE'` nếu các ràng buộc khác cho phép.

`NOT NULL` không tự điền default. Nếu cột chỉ có `NOT NULL` mà không có `DEFAULT`, INSERT bỏ cột có thể thất bại vì không có giá trị hợp lệ để lưu.

Tương tự, Java field là `null` không chứng minh cột database cho phép null. Schema mới là nơi xác định ràng buộc cuối cùng. Hãy thiết kế nullability của entity, validation ở ứng dụng và constraint ở database nhất quán với nhau.

## 10. Giá trị được database sinh và dữ liệu trả về entity

Sau khi database áp dụng default, object Java trong bộ nhớ không nhất thiết tự có giá trị mới. Ví dụ, database đã sinh `created_at`, nhưng field `task.getCreatedAt()` có thể vẫn là `null` nếu thao tác insert không trả giá trị đó về và mapping layer không cập nhật entity.

Cần phân biệt:

1. **Giá trị đã lưu:** database đã ghi default hoặc generated value vào hàng.
2. **Giá trị trong object Java:** object chỉ có giá trị mà ứng dụng đã gán hoặc persistence operation trả về và gán lại.

Đối với ID được sinh, Spring Data R2DBC có cơ chế xử lý generated ID tùy database và driver. Với các cột default khác, khả năng lấy lại giá trị phụ thuộc API, dialect và driver. Không nên suy ra rằng mọi cột `DEFAULT` sẽ tự động được điền vào object sau `save`.

Nếu nghiệp vụ cần dùng ngay `created_at` hoặc `status` sau khi lưu, có thể:

- Dùng câu lệnh có `RETURNING` hoặc cơ chế generated values được database/driver hỗ trợ.
- Đọc lại bản ghi sau khi insert.
- Tự gán giá trị trong Java nếu ứng dụng là nguồn có thẩm quyền và không cần lấy giá trị từ database.

Hãy kiểm tra kết quả thực tế bằng integration test với đúng driver và database. Một unit test chỉ tạo object Java không thể chứng minh database đã áp dụng default.

## 11. Default cho ngày giờ và khác biệt đồng hồ

Ngày giờ là trường hợp dễ có hai nguồn default khác nhau.

Java có thể gán:

```java
private Instant createdAt = Instant.now();
```

Database có thể gán:

```sql
created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
```

Nếu nhiều ứng dụng cùng ghi vào một database, dùng thời gian do database cấp có thể giúp tập trung nguồn thời gian. Nếu domain cần thời điểm sự kiện được tạo ở ứng dụng trước khi ghi, Java có thể là nguồn phù hợp. Cần xác định rõ ý nghĩa của timestamp:

- Thời điểm người dùng thực hiện hành động.
- Thời điểm ứng dụng nhận request.
- Thời điểm database ghi nhận transaction.
- Thời điểm một tiến trình xử lý hoàn tất.

Các mốc này không nhất thiết giống nhau. Không nên dùng một field `createdAt` cho nhiều ý nghĩa khác nhau.

Ngoài ra, `CURRENT_TIMESTAMP` và `Instant.now()` có thể chịu ảnh hưởng bởi độ chính xác đồng hồ, cách database biểu diễn timezone và cách driver chuyển kiểu. Nên dùng kiểu thời gian phù hợp như `Instant` hoặc `OffsetDateTime`, thống nhất UTC ở tầng trao đổi và kiểm tra mapping của driver.

## 12. Default cho ID, sequence và generated column

ID cũng là một loại giá trị có thể được tạo ở Java hoặc database.

### 12.1. ID do Java tạo

Ứng dụng có thể tạo UUID trước khi insert:

```java
UUID id = UUID.randomUUID();
```

Ưu điểm là ID có sẵn trước khi ghi và có thể dùng trong các object hoặc event trước khi database xác nhận. Đổi lại, ứng dụng phải thống nhất kiểu UUID và cách biểu diễn với schema, driver và các hệ thống liên quan.

### 12.2. ID do database tạo

Database có thể dùng identity hoặc sequence:

```sql
id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
```

Ứng dụng để ID chưa có giá trị và persistence layer sử dụng cơ chế generated ID phù hợp. Database cấp ID khi insert. Việc ID được trả lại và gán vào entity phụ thuộc database, driver và cách Spring Data thực thi insert.

Không nên tự đặt `0` vào field ID primitive rồi kỳ vọng mọi driver hiểu đó là “chưa có ID”. Với ID sinh tự động, kiểu wrapper như `Long` giúp biểu diễn trạng thái chưa có ID bằng `null`; mapping metadata và cơ chế generated ID vẫn cần được cấu hình đúng.

### 12.3. Generated column và trigger

Một số database hỗ trợ generated column hoặc trigger để tính giá trị từ dữ liệu khác. Những giá trị này thuộc quyền quyết định của database. Nếu ứng dụng không được phép gửi giá trị cho cột đó, hãy loại cột khỏi thao tác ghi hoặc dùng mapping chỉ đọc phù hợp. Cách khai báo generated column và khả năng trả giá trị về entity phụ thuộc hệ quản trị.

## 13. Quản lý default bằng database migration

Default thuộc schema nên cần được quản lý bằng migration có phiên bản. Ví dụ migration:

```sql
ALTER TABLE task
    ALTER COLUMN status SET DEFAULT 'PENDING';

ALTER TABLE task
    ALTER COLUMN created_at SET DEFAULT CURRENT_TIMESTAMP;
```

Thay đổi default thường chỉ ảnh hưởng các bản ghi được insert sau khi thay đổi schema. Nó không tự động cập nhật những hàng cũ đã có giá trị. Nếu cần sửa dữ liệu lịch sử, migration phải có câu UPDATE riêng và cần đánh giá tác động.

Ví dụ:

```sql
UPDATE task
SET status = 'PENDING'
WHERE status IS NULL;
```

Câu UPDATE này là thay đổi dữ liệu tường minh, khác với việc đặt default cho các INSERT tương lai. Trước khi chạy migration dữ liệu, cần kiểm tra số hàng bị ảnh hưởng và ý nghĩa nghiệp vụ của các giá trị cũ.

Trong Spring Data R2DBC, annotation mapping không thay thế migration schema. `@Table`, `@Column` và `@ReadOnlyProperty` mô tả cách ánh xạ entity; chúng không tự bảo đảm schema có đúng default, constraint hoặc generated expression. Schema cần được tạo và nâng cấp bằng quy trình migration hoặc quản trị database phù hợp.

## 14. Kiểm thử sự khác biệt giữa hai loại default

Để xác nhận default database, cần kiểm thử qua database thật hoặc test database dùng đúng hệ quản trị/driver cần hỗ trợ. Unit test Java chỉ xác nhận giá trị khởi tạo trong object.

Một integration test có thể kiểm tra hai đường ghi:

1. INSERT bỏ cột `status` và xác nhận database trả `PENDING`.
2. INSERT truyền `status = 'ACTIVE'` và xác nhận database lưu `ACTIVE`.
3. Nếu cột `NOT NULL`, thử truyền SQL NULL và xác nhận database từ chối.
4. Đọc lại bản ghi để xác nhận các giá trị generated như ID và `created_at`.

Ví dụ SQL kiểm thử:

```sql
INSERT INTO task (title)
VALUES ('Default status test')
RETURNING status;

INSERT INTO task (title, status)
VALUES ('Explicit status test', 'ACTIVE')
RETURNING status;
```

Kết quả mong đợi lần lượt là `PENDING` và `ACTIVE`, nếu schema có `DEFAULT 'PENDING'`. Câu lệnh `RETURNING` ở ví dụ này dành cho PostgreSQL; với hệ quản trị khác, dùng cách truy vấn lại hoặc cơ chế trả generated values tương ứng.

Khi kiểm thử qua repository, cần biết SQL mà Spring Data phát ra. Có thể bật log SQL ở môi trường test hoặc dùng công cụ quan sát statement của driver để kiểm tra danh sách cột và tham số bind. Không nên bật log chứa dữ liệu nhạy cảm ở production.

## 15. Các lỗi thường gặp

| Triệu chứng | Nguyên nhân có thể có | Cách xử lý |
| --- | --- | --- |
| Database luôn nhận `0` dù cột có default khác | Field Java primitive `int` có giá trị `0` và được ghi tường minh | Dùng wrapper nếu cần biểu diễn chưa cung cấp; chủ động bỏ cột khỏi INSERT khi muốn DB default |
| Database nhận `NULL` thay vì default | Mapping bind SQL NULL cho thuộc tính Java `null` | Kiểm tra SQL; bỏ cột hoặc dùng `DEFAULT` tường minh |
| Giá trị lưu khác với default schema | Java initializer/constructor đã gán giá trị và INSERT gửi giá trị đó | Thống nhất nguồn default hoặc để database quản lý cột |
| Entity sau `save` vẫn có `createdAt = null` | Database đã sinh giá trị nhưng thao tác insert không trả/gán cột đó vào entity | Dùng generated values/`RETURNING` hoặc đọc lại bản ghi |
| Một số client tạo dữ liệu có status khác nhau | Java và schema có default không đồng nhất | Đồng bộ chính sách và migration |
| INSERT thất bại do NOT NULL | Cột bị gửi NULL hoặc bị bỏ nhưng không có default | Xem schema và cách bind; đặt default hoặc cung cấp giá trị hợp lệ |
| Cột generated bị ghi đè | Ứng dụng vẫn gửi giá trị vào cột database quản lý | Loại cột khỏi thao tác ghi hoặc dùng mapping read-only phù hợp |

## 16. Quy tắc lựa chọn trong ứng dụng Spring Data R2DBC

Khi thiết kế một thuộc tính có default, có thể lần lượt xác định:

1. Giá trị đó có phải invariant hoặc quy tắc domain cần tồn tại ngay khi tạo object không? Nếu có, hãy thể hiện trong constructor hoặc factory method.
2. Nhiều ứng dụng/client khác nhau có cùng cần một default không? Nếu có, database default có thể là lớp bảo vệ chung.
3. Database có phải nguồn có thẩm quyền cho giá trị đó, ví dụ thời điểm ghi nhận hoặc ID không? Nếu có, hãy để database sinh giá trị và không ghi đè từ Java.
4. Câu INSERT có thực sự bỏ cột hoặc dùng `DEFAULT` không? Kiểm tra SQL được tạo; không suy luận từ field `null`.
5. Entity có cần nhận lại giá trị sau insert không? Nếu có, dùng cơ chế trả generated values hoặc truy vấn lại.
6. Java mapping và schema migration có thống nhất về nullability, default và kiểu dữ liệu không?
7. Có integration test xác nhận hành vi trên driver/database thực tế không?

Giá trị mặc định trong Java giúp object có trạng thái khởi tạo theo logic ứng dụng. Giá trị mặc định trong database giúp schema cung cấp giá trị khi câu INSERT không gửi cột hoặc yêu cầu `DEFAULT`. Trong Spring Data R2DBC, ranh giới quyết định nằm ở SQL và tham số mà mapping layer thực sự gửi xuống database. Hiểu rõ khác biệt giữa giá trị tường minh, SQL NULL và cột bị bỏ khỏi INSERT sẽ giúp tránh các lỗi dữ liệu khó phát hiện khi ứng dụng có nhiều đường ghi hoặc dùng các giá trị do database sinh ra.
