# Thiết kế dữ liệu có thể rỗng và giá trị mặc định

Khi thiết kế mô hình dữ liệu cho Spring Data Relational R2DBC, cần quyết định rõ thuộc tính nào được phép không có giá trị, thuộc tính nào bắt buộc và thuộc tính nào có giá trị mặc định. Ba khái niệm này liên quan nhưng không đồng nghĩa. Một cột có thể cho phép `NULL` và vẫn có `DEFAULT`; một cột `NOT NULL` cũng có thể có `DEFAULT`; còn một thuộc tính Java được gán `null` không tự động yêu cầu cơ sở dữ liệu dùng giá trị mặc định.

Thiết kế đúng cần thống nhất giữa schema, entity, API và câu lệnh ghi. Nếu các lớp này hiểu khác nhau về null hoặc default, ứng dụng có thể ghi đè giá trị mặc định, từ chối dữ liệu hợp lệ hoặc vô tình xóa dữ liệu khi cập nhật.

## 1. Phân biệt NULL, giá trị bị bỏ qua và DEFAULT

Khi một bản ghi được tạo, có ít nhất ba trạng thái đầu vào cần phân biệt:

1. Client gửi một giá trị cụ thể, chẳng hạn `nickname = "An"`.
2. Client gửi `null`, thể hiện rõ rằng thuộc tính không có giá trị.
3. Client không gửi thuộc tính đó, có thể có nghĩa là dùng default, giữ nguyên giá trị hoặc để tầng nghiệp vụ quyết định.

Trong SQL, `NULL` biểu thị giá trị chưa biết hoặc không hiện diện theo ngữ nghĩa của cột. Nó không phải chuỗi rỗng, số 0 hay giá trị mặc định.

`DEFAULT` là biểu thức mà cơ sở dữ liệu dùng khi câu lệnh ghi yêu cầu áp dụng default. Với câu `INSERT`, default thường được áp dụng khi cột bị bỏ khỏi danh sách cột hoặc khi câu lệnh chỉ định từ khóa `DEFAULT`.

Ví dụ:

```sql
CREATE TABLE customer_profile (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email VARCHAR(255) NOT NULL,
    nickname VARCHAR(100) NULL,
    marketing_opt_in BOOLEAN NOT NULL DEFAULT FALSE,
    status VARCHAR(20) NOT NULL DEFAULT 'NEW',
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

Với schema trên:

- `email` bắt buộc phải có giá trị.
- `nickname` được phép lưu `NULL`.
- `marketing_opt_in` không được `NULL`; nếu cột bị bỏ khỏi `INSERT`, database dùng `FALSE`.
- `status` không được `NULL`; nếu cột bị bỏ khỏi `INSERT`, database dùng `'NEW'`.
- `created_at` được database gán thời điểm mặc định khi không truyền giá trị.

| Cách ghi | Cột nullable không có default | Cột có `DEFAULT 'NEW'` |
| --- | --- | --- |
| Bỏ cột khỏi `INSERT` | Lưu `NULL` nếu schema cho phép. | Database dùng `'NEW'`. |
| Ghi `NULL` tường minh | Lưu `NULL`. | Lưu `NULL` nếu cột cho phép; default không được kích hoạt. |
| Ghi giá trị cụ thể | Lưu giá trị đó. | Lưu giá trị đó, ghi đè default. |
| Ghi từ khóa `DEFAULT` | Dùng default của cột; nếu không khai báo, hành vi phụ thuộc hệ quản trị. | Database dùng `'NEW'`. |

Nếu cột có `NOT NULL DEFAULT ...`, việc ghi `NULL` tường minh thường bị từ chối bởi ràng buộc `NOT NULL`. Default không có nghĩa database tự thay mọi giá trị `NULL` bằng giá trị mặc định.

## 2. Thiết kế nullability trong schema

Nullability nên xuất phát từ quy tắc nghiệp vụ. Hãy tự hỏi một thuộc tính có thể chưa biết, chưa được cung cấp hoặc không áp dụng tại thời điểm bản ghi được tạo hay không.

Một số ví dụ:

- `middle_name` có thể không tồn tại với một người.
- `delivered_at` chưa có giá trị khi đơn hàng chưa được giao.
- `cancelled_reason` chỉ có giá trị khi đơn hàng bị hủy.
- `email` có thể bắt buộc trong hệ thống dùng email làm định danh đăng nhập.
- `created_at` thường phải có ngay khi tạo bản ghi.

Không nên đặt tất cả cột thành nullable để việc insert dễ dàng. Schema lỏng lẻo khiến dữ liệu không hợp lệ lọt vào hệ thống và buộc mọi truy vấn phải xử lý nhiều trường hợp bất thường.

### Dùng NOT NULL cho dữ liệu bắt buộc

```sql
CREATE TABLE product (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    sku VARCHAR(64) NOT NULL UNIQUE,
    name VARCHAR(200) NOT NULL,
    price NUMERIC(12, 2) NOT NULL,
    description TEXT NULL
);
```

`sku`, `name` và `price` là các thuộc tính bắt buộc. `description` có thể vắng mặt. Ràng buộc `NOT NULL` được database thực thi cho mọi đường ghi, kể cả khi dữ liệu đến từ ứng dụng khác, câu SQL trực tiếp hoặc batch job.

`NOT NULL` khác với kiểm tra chuỗi không rỗng. Nếu `name` không được phép là chuỗi chỉ có khoảng trắng, cần thêm validation ở tầng ứng dụng và có thể thêm constraint phù hợp ở database.

### Dùng CHECK cho quy tắc giá trị

Nullability chỉ trả lời một cột có được phép `NULL` hay không. Nó không xác định toàn bộ miền giá trị hợp lệ.

```sql
CREATE TABLE product_price (
    product_id BIGINT PRIMARY KEY,
    amount NUMERIC(12, 2) NOT NULL,
    currency CHAR(3) NOT NULL,
    CONSTRAINT chk_product_price_nonnegative CHECK (amount >= 0)
);
```

Constraint `CHECK` bảo vệ quy tắc `amount` không âm ngay tại database. Hãy kết hợp `NOT NULL` với `CHECK` khi cần, vì trong SQL biểu thức `CHECK` có kết quả `UNKNOWN` với một số phép so sánh chứa `NULL`; chỉ `CHECK (amount >= 0)` không thay thế được `NOT NULL`.

## 3. Biểu diễn nullable trong Java và Kotlin

Schema có thể cho phép `NULL`, vì vậy kiểu dữ liệu trong entity cần biểu diễn được trạng thái đó.

Trong Java, các kiểu primitive như `int`, `long` và `boolean` không thể chứa `null`. Nếu cột có thể rỗng, hãy dùng kiểu wrapper tương ứng như `Integer`, `Long` hoặc `Boolean`, hoặc một kiểu tham chiếu phù hợp.

```java
import java.math.BigDecimal;
import java.time.LocalDateTime;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;
import org.springframework.lang.Nullable;

@Table("customer_profile")
public record CustomerProfile(
    @Id Long id,
    String email,
    @Nullable String nickname,
    Boolean marketingOptIn,
    String status,
    @Column("created_at") LocalDateTime createdAt
) {}
```

Trong ví dụ:

- `nickname` được đánh dấu `@Nullable` vì schema cho phép `NULL`.
- `marketingOptIn` dùng `Boolean`, nên có thể biểu diễn `true`, `false` và `null`. Có thể thay bằng `boolean` nếu hợp đồng ứng dụng luôn yêu cầu giá trị cụ thể.
- `status` và `createdAt` là kiểu tham chiếu nhưng schema yêu cầu `NOT NULL`; ứng dụng phải bảo đảm chúng có giá trị trước khi ghi hoặc để database tạo default theo một câu lệnh insert phù hợp.

`@Nullable` giúp diễn đạt ý định và hỗ trợ công cụ phân tích nullability. Nó không thay thế ràng buộc `NOT NULL` trong database. Ngược lại, việc dùng kiểu Java không nullable cũng không tự tạo constraint trong schema nếu schema được quản lý riêng.

Đối với `Optional<T>`, thường nên dùng nó ở kiểu trả về hoặc API biểu diễn kết quả có thể vắng mặt. Với thuộc tính entity, kiểu tham chiếu nullable và annotation nullability thường dễ tương thích hơn với mapping và constructor của Spring Data.

### Nullability trong Kotlin

Kotlin biểu diễn nullability trực tiếp trong kiểu:

```kotlin
@Table("customer_profile")
data class CustomerProfile(
    @Id val id: Long? = null,
    val email: String,
    val nickname: String?,
    val marketingOptIn: Boolean?,
    val status: String,
    val createdAt: LocalDateTime
)
```

`String?` cho phép `null`; `String` không cho phép giá trị null theo type system của Kotlin. Khi dùng Spring Data với Kotlin, metadata nullability của Kotlin được sử dụng trong quá trình mapping. Dù vậy, database vẫn là nơi thực thi các ràng buộc toàn vẹn cuối cùng.

Không nên đặt `String?` chỉ vì muốn né lỗi validation. Hãy dùng nullable type khi nghiệp vụ thực sự cho phép thiếu giá trị.

## 4. Giá trị mặc định thuộc về database hay ứng dụng?

Giá trị mặc định có thể được gán ở nhiều tầng:

- **Database default:** được khai báo trong DDL và áp dụng khi câu lệnh insert bỏ qua cột hoặc chỉ định `DEFAULT`.
- **Application default:** được gán trong factory, constructor, service hoặc DTO mapping trước khi gọi repository.
- **Domain default:** là quy tắc khởi tạo của mô hình miền, thường phản ánh quyết định nghiệp vụ.
- **Trigger hoặc generated expression:** database tính giá trị dựa trên các cột khác hoặc thời điểm ghi.

| Nơi đặt default | Phạm vi tác động | Phù hợp khi |
| --- | --- | --- |
| Database `DEFAULT` | Mọi client ghi vào bảng. | Muốn bảo vệ dữ liệu nhất quán kể cả ngoài ứng dụng hiện tại. |
| Factory/service | Các luồng tạo dữ liệu đi qua ứng dụng. | Giá trị là quyết định nghiệp vụ cần được thể hiện trong code. |
| Constructor/domain factory | Mọi đối tượng được tạo theo mô hình đó. | Giá trị là invariant hoặc trạng thái khởi tạo của domain object. |
| Trigger/generated column | Database cần tính toán theo dữ liệu hoặc quy tắc tập trung. | Giá trị phụ thuộc nhiều nguồn ghi hoặc cần thực thi ở database. |

Ví dụ, nếu mọi đơn hàng mới phải có trạng thái `NEW`, có thể đặt default ở database để bảo vệ cả những client ghi ngoài ứng dụng. Nếu trạng thái khởi tạo phụ thuộc loại đơn hàng, quy tắc đó nên được quyết định trong domain/service và truyền giá trị rõ ràng.

Tránh khai báo hai default khác nhau ở ứng dụng và database. Ví dụ, Java mặc định `status = "NEW"` nhưng database mặc định `'PENDING'`. Khi một luồng ghi bỏ qua giá trị, kết quả sẽ phụ thuộc cách câu lệnh được tạo. Nếu cả hai tầng cùng có default, hãy thống nhất một giá trị và xác định tầng nào là nguồn quyết định chính.

### Default không phải là giá trị thay thế NULL

Giả sử cột `status` có `DEFAULT 'NEW'`:

```sql
INSERT INTO orders (customer_id) VALUES (10);
-- status nhận giá trị 'NEW'

INSERT INTO orders (customer_id, status) VALUES (10, NULL);
-- lỗi nếu status là NOT NULL; nếu nullable thì lưu NULL
```

Default cũng không tự chạy khi cập nhật một cột thành `NULL`. Muốn đặt lại default trong câu `UPDATE`, cần chỉ định `SET status = DEFAULT` nếu hệ quản trị hỗ trợ cú pháp đó.

## 5. Cách database default tương tác với Spring Data R2DBC

Đây là điểm dễ gây nhầm lẫn nhất khi dùng entity mapping.

Nếu ứng dụng muốn database tạo giá trị default, cột đó phải được bỏ khỏi câu lệnh `INSERT` hoặc câu lệnh phải chỉ định từ khóa `DEFAULT`. Nếu Spring Data tạo câu lệnh có cột đó và bind giá trị Java `null`, database nhận `NULL` tường minh. Default không được kích hoạt.

Vì vậy, không nên suy luận rằng thuộc tính entity bằng `null` thì Spring Data chắc chắn bỏ cột đó khỏi `INSERT`. Hành vi mapping và câu lệnh được tạo phụ thuộc cách ghi, phiên bản và metadata. Hãy xác nhận SQL thực tế khi dựa vào database default.

Có ba hướng thiết kế phổ biến:

1. Ứng dụng tự gán giá trị trước khi gọi `save`.
2. Cột hoàn toàn do database quản lý và được đánh dấu read-only nếu phù hợp.
3. Dùng câu lệnh SQL tùy chỉnh để chủ động bỏ cột khỏi danh sách insert.

### Ứng dụng gán default trước khi save

Nếu default là quy tắc nghiệp vụ của ứng dụng, có thể dùng factory:

```java
public record NewCustomerProfile(
    String email,
    String nickname,
    Boolean marketingOptIn
) {
    public static NewCustomerProfile create(
            String email,
            String nickname,
            Boolean marketingOptIn) {
        return new NewCustomerProfile(
            email,
            nickname,
            marketingOptIn != null ? marketingOptIn : Boolean.FALSE
        );
    }
}
```

Service chuyển command thành entity với giá trị đã xác định:

```java
public Mono<CustomerProfile> create(NewCustomerProfile command) {
    CustomerProfile profile = new CustomerProfile(
        null,
        command.email(),
        command.nickname(),
        command.marketingOptIn(),
        "NEW",
        LocalDateTime.now()
    );

    return repository.save(profile);
}
```

Với cách này, ứng dụng gửi `false`, `NEW` và thời điểm tạo một cách tường minh. Database default không phải nguồn tạo các giá trị đó trong lần insert này. Cần bảo đảm các luồng ghi khác cũng tuân theo quy tắc nếu tính nhất quán là bắt buộc.

### Cột chỉ do database quản lý

Spring Data Relational có annotation `@ReadOnlyProperty` để đánh dấu thuộc tính không được ghi vào database trong thao tác insert/update do mapping thực hiện. Thuộc tính vẫn có thể được đọc khi entity được tải.

Ví dụ:

```java
import org.springframework.data.annotation.ReadOnlyProperty;

@Table("customer_profile")
public record CustomerProfile(
    @Id Long id,
    String email,
    @ReadOnlyProperty
    @Column("created_at")
    LocalDateTime createdAt
) {}
```

Cách này phù hợp với cột do database quản lý mà ứng dụng không được phép cập nhật. Tuy nhiên, việc đánh dấu read-only không đồng nghĩa mọi driver và mọi đường insert sẽ tự động trả về toàn bộ giá trị generated. Nếu cần dùng giá trị default ngay sau insert, hãy kiểm tra cơ chế generated values của driver hoặc tải lại bản ghi bằng ID.

Không dùng `@ReadOnlyProperty` cho cột mà ứng dụng cần thay đổi ở các lần cập nhật tiếp theo. Annotation này loại thuộc tính khỏi thao tác ghi của mapping, không chỉ bỏ qua nó khi insert.

### Dùng SQL tường minh để bỏ qua cột default

Khi cần kiểm soát chính xác cột nào được insert, có thể dùng `DatabaseClient` hoặc custom repository fragment. Ví dụ PostgreSQL:

```java
import java.time.LocalDateTime;

import org.springframework.r2dbc.core.DatabaseClient;
import org.springframework.stereotype.Repository;
import reactor.core.publisher.Mono;

@Repository
public class CustomerProfileWriter {

    private final DatabaseClient databaseClient;

    public CustomerProfileWriter(DatabaseClient databaseClient) {
        this.databaseClient = databaseClient;
    }

    public Mono<CustomerProfile> insert(
            String email,
            String nickname) {

        return databaseClient.sql("""
                INSERT INTO customer_profile (email, nickname)
                VALUES (:email, :nickname)
                RETURNING id, email, nickname,
                          marketing_opt_in, status, created_at
                """)
            .bind("email", email)
            .bindNull("nickname", String.class)
            .map((row, metadata) -> new CustomerProfile(
                row.get("id", Long.class),
                row.get("email", String.class),
                row.get("nickname", String.class),
                row.get("marketing_opt_in", Boolean.class),
                row.get("status", String.class),
                row.get("created_at", LocalDateTime.class)
            ))
            .one();
    }
}
```

Trong câu lệnh này:

- `email` được bind bằng giá trị bắt buộc.
- `nickname` được ghi `NULL` tường minh bằng `bindNull`.
- `marketing_opt_in`, `status` và `created_at` không xuất hiện trong danh sách cột insert, nên database áp dụng default đã khai báo.
- `RETURNING` là cú pháp PostgreSQL để trả về hàng vừa được tạo. Hệ quản trị khác có thể cần cách lấy generated values khác.

R2DBC không cho bind Java `null` bằng `.bind(name, null)` theo cách thông thường. Dùng `.bindNull(name, Type.class)` để truyền SQL NULL. Khi muốn database default, không bind `null`; hãy bỏ cột khỏi câu lệnh hoặc dùng cú pháp `DEFAULT` phù hợp.

## 6. Cẩn thận với kiểu primitive và giá trị Java mặc định

Java tự gán giá trị mặc định cho field primitive khi tạo đối tượng:

| Kiểu primitive | Giá trị ban đầu |
| --- | --- |
| `boolean` | `false` |
| `byte`, `short`, `int`, `long` | `0` |
| `float`, `double` | `0.0` |
| `char` | ký tự `\u0000` |

Những giá trị này không biểu thị SQL `NULL`. Nếu entity có `boolean marketingOptIn`, một đối tượng mới có giá trị `false` ngay cả khi client không gửi trường đó. Khi lưu, ứng dụng có thể ghi `false` tường minh và khiến database không dùng default.

Với wrapper, giá trị ban đầu thường là `null`, nhưng điều đó vẫn không bảo đảm cột được bỏ khỏi câu `INSERT`. Wrapper chỉ cho phép mô hình hóa null trong Java; quyết định SQL được tạo như thế nào vẫn thuộc mapping/driver.

Hãy chọn kiểu dựa trên hợp đồng:

- Dùng primitive khi giá trị luôn bắt buộc và có ý nghĩa ngay khi tạo đối tượng.
- Dùng wrapper khi cần phân biệt có giá trị với chưa có giá trị.
- Dùng `@Nullable` để diễn đạt rõ thuộc tính có thể null.
- Dùng factory hoặc command riêng để phân biệt giá trị không được cung cấp với giá trị người dùng chủ động chọn.

## 7. NULL trong truy vấn SQL và query method

SQL sử dụng logic ba giá trị: `TRUE`, `FALSE` và `UNKNOWN`. Vì vậy, so sánh với `NULL` bằng toán tử `=` không hoạt động như so sánh thông thường.

Không viết:

```sql
SELECT *
FROM customer_profile
WHERE nickname = NULL;
```

Hãy dùng:

```sql
SELECT *
FROM customer_profile
WHERE nickname IS NULL;
```

Để tìm giá trị đã có:

```sql
SELECT *
FROM customer_profile
WHERE nickname IS NOT NULL;
```

Với derived query method, Spring Data hỗ trợ các tên thể hiện null predicate, ví dụ:

```java
Flux<CustomerProfile> findByNicknameIsNull();

Flux<CustomerProfile> findByNicknameIsNotNull();
```

Nếu cần tìm theo một giá trị cụ thể, dùng query method tương ứng:

```java
Flux<CustomerProfile> findByStatus(String status);
```

Không nên truyền `null` vào `findByStatus` rồi kỳ vọng Spring Data hiểu đó là `IS NULL` trong mọi trường hợp. Hãy khai báo phương thức thể hiện rõ điều kiện null hoặc dùng truy vấn tường minh.

Với SQL tùy chỉnh, nếu tham số có thể null, phải thiết kế điều kiện rõ ràng. Ví dụ, truy vấn có bộ lọc tùy chọn có thể dùng hai nhánh SQL hoặc xây dựng `Criteria` theo việc tham số có mặt hay không. Tránh viết điều kiện mơ hồ khiến một giá trị null vừa có nghĩa “bỏ qua bộ lọc” vừa có nghĩa “chỉ tìm bản ghi có cột null”.

## 8. NULL, giá trị rỗng và dữ liệu không hợp lệ

| Giá trị | Ý nghĩa |
| --- | --- |
| SQL `NULL` | Không có giá trị theo ngữ nghĩa của cột. |
| Chuỗi `''` | Có một chuỗi với độ dài bằng 0. |
| Chuỗi `'   '` | Có chuỗi chỉ chứa khoảng trắng. |
| Số `0` | Một giá trị số hợp lệ, không phải null. |
| Boolean `false` | Một giá trị boolean hợp lệ, không phải null. |
| JSON `null` | Giá trị null bên trong tài liệu JSON; khác với SQL NULL của cả cột. |

Nếu nghiệp vụ coi chuỗi rỗng như không có dữ liệu, hãy chuẩn hóa đầu vào hoặc thêm validation. Không nên dựa vào database tự chuyển chuỗi rỗng thành NULL vì hành vi có thể khác giữa hệ quản trị.

Với cột JSON, cần phân biệt SQL NULL của cột và giá trị JSON `null` bên trong tài liệu. Chúng có thể cho kết quả khác nhau trong phép lọc, index và toán tử JSON.

## 9. PATCH và ý nghĩa của trường bị bỏ qua

Một request tạo mới và một request cập nhật một phần không nên tự động dùng cùng ngữ nghĩa null.

Với thao tác tạo mới:

- Trường bị bỏ qua có thể nhận default.
- Trường được gửi `null` có thể lưu SQL NULL nếu schema cho phép.
- Trường bắt buộc phải có giá trị hợp lệ.

Với PATCH:

- Trường bị bỏ qua thường có nghĩa là giữ nguyên dữ liệu hiện tại.
- Trường được gửi `null` có thể có nghĩa là xóa giá trị hiện tại.
- Trường được gửi giá trị cụ thể có nghĩa là cập nhật thành giá trị đó.

Một DTO chỉ có thuộc tính nullable thường không phân biệt được “client không gửi trường” và “client gửi trường với null” sau khi deserialize. Nếu API cần phân biệt hai trạng thái này, hãy dùng kiểu biểu diễn có trạng thái `present` riêng, JSON tree hoặc wrapper phù hợp.

Ví dụ mô hình khái niệm:

```java
public record FieldChange<T>(
    boolean present,
    T value
) {
    public static <T> FieldChange<T> absent() {
        return new FieldChange<>(false, null);
    }

    public static <T> FieldChange<T> of(T value) {
        return new FieldChange<>(true, value);
    }
}
```

Khi áp dụng:

- `present = false`: không thay đổi cột.
- `present = true` và `value = null`: chủ động ghi SQL NULL nếu schema cho phép.
- `present = true` và `value` có dữ liệu: cập nhật bằng giá trị đó.

Đây là mô hình biểu diễn ý nghĩa; bộ giải mã JSON cần được thiết kế để giữ lại thông tin trường có xuất hiện trong request hay không. Đừng để mapper gán `null` cho mọi trường bị bỏ qua rồi truyền nguyên entity vào `save`, vì điều đó có thể xóa dữ liệu hiện có.

## 10. Validation ở ứng dụng và constraint ở database

Validation ở API giúp trả lỗi dễ hiểu trước khi gọi database. Constraint ở database bảo vệ dữ liệu trước mọi nguồn ghi. Hai lớp này bổ sung cho nhau.

Ví dụ DTO:

```java
import jakarta.validation.constraints.Email;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Size;

public record CreateCustomerRequest(
    @NotBlank
    @Email
    String email,

    @Size(max = 100)
    String nickname
) {}
```

Trong controller, kích hoạt validation bằng `@Valid` khi ứng dụng đã cấu hình Jakarta Bean Validation:

```java
@PostMapping
public Mono<CustomerProfile> create(
        @Valid @RequestBody Mono<CreateCustomerRequest> request) {
    return request.flatMap(service::create);
}
```

Cần kiểm tra cách WebFlux xử lý validation cho kiểu request body reactive trong phiên bản Spring đang dùng. Dù validation API thành công, database vẫn phải có `NOT NULL`, `UNIQUE`, `CHECK` hoặc foreign key cần thiết để bảo vệ tính toàn vẹn.

Không nên dùng `@NotNull` trên một DTO PATCH nếu hợp đồng cho phép client chủ động gửi null để xóa giá trị. Validation phải phản ánh ý nghĩa của từng loại request.

## 11. Giá trị thời gian và default

Các cột thời gian thường cần một quyết định rõ ràng: thời gian do ứng dụng cung cấp hay thời gian do database tạo.

```sql
CREATE TABLE audit_event (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    event_type VARCHAR(80) NOT NULL,
    occurred_at TIMESTAMP NOT NULL,
    recorded_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

`occurred_at` có thể là thời điểm nghiệp vụ xảy ra do ứng dụng hoặc nguồn sự kiện cung cấp. `recorded_at` có thể là thời điểm database ghi nhận bản ghi.

Hai thời điểm này không nhất thiết giống nhau. Nếu cần thời gian nhất quán giữa nhiều ứng dụng, cần thống nhất timezone, kiểu cột và nguồn đồng hồ. `CURRENT_TIMESTAMP` có ngữ nghĩa phụ thuộc hệ quản trị và transaction; hãy đọc tài liệu database để hiểu độ chính xác và thời điểm được tính.

Với PostgreSQL, `TIMESTAMP WITH TIME ZONE` và `TIMESTAMP WITHOUT TIME ZONE` có ngữ nghĩa khác nhau. Hãy chọn kiểu Java và converter tương ứng với schema, thay vì chỉ đổi tên kiểu mà không xét timezone.

## 12. Thay đổi nullability và default bằng migration

Schema thay đổi cần có lộ trình để dữ liệu cũ và ứng dụng đang chạy cùng tương thích.

Giả sử cần thêm cột `status` bắt buộc với default `NEW` vào bảng đã có dữ liệu. Một migration có thể thực hiện:

```sql
ALTER TABLE orders
ADD COLUMN status VARCHAR(20) DEFAULT 'NEW';

UPDATE orders
SET status = 'NEW'
WHERE status IS NULL;

ALTER TABLE orders
ALTER COLUMN status SET NOT NULL;
```

Cú pháp trên là PostgreSQL. Các hệ quản trị khác có thể có cú pháp và chiến lược triển khai khác. Với bảng lớn, cần đánh giá lock, thời gian backfill và khả năng triển khai theo từng giai đoạn.

Một lộ trình an toàn thường gồm:

1. Thêm cột theo cách tương thích với phiên bản ứng dụng đang chạy.
2. Backfill dữ liệu cũ nếu cần.
3. Triển khai ứng dụng mới ghi và đọc cột.
4. Xác minh dữ liệu không còn vi phạm quy tắc.
5. Thêm hoặc siết constraint `NOT NULL`.
6. Loại bỏ logic tương thích cũ sau khi mọi instance đã nâng cấp.

Khi bỏ default, hãy kiểm tra mọi client ghi dữ liệu. Một ứng dụng cũ có thể đang dựa vào default đó dù code mới đã gửi giá trị tường minh.

## 13. Kiểm thử nullability và default với R2DBC

Kiểm thử bằng mock repository không chứng minh database đã áp dụng default hoặc constraint đúng. Cần kiểm thử tích hợp với loại database và driver thực tế.

| Trường hợp | Điều cần xác nhận |
| --- | --- |
| Insert cột nullable với SQL NULL | Database lưu NULL và đọc lại đúng. |
| Insert bỏ qua cột có default | Database sinh giá trị default. |
| Insert truyền giá trị tường minh | Giá trị truyền vào ghi đè default. |
| Insert NULL vào cột NOT NULL | Database từ chối thao tác. |
| Update cột thành NULL | Chỉ thành công nếu schema cho phép. |
| PATCH bỏ qua trường | Giá trị hiện tại được giữ nguyên. |
| PATCH gửi null | Cột được xóa giá trị theo đúng hợp đồng API. |
| Đọc entity có cột nullable | Mapping không làm hỏng khi giá trị database là NULL. |

Với PostgreSQL, có thể dùng Testcontainers và `@DataR2dbcTest` hoặc một test cấu hình Spring Boot đầy đủ. Khi test database default, hãy kiểm tra câu lệnh thực tế có bỏ cột đó khỏi `INSERT` hay không.

Ví dụ kiểm thử publisher bằng Reactor Test:

```java
StepVerifier.create(repository.findByNicknameIsNull())
    .expectNextMatches(profile -> profile.nickname() == null)
    .verifyComplete();
```

Ví dụ giả định dữ liệu test đã được chuẩn bị. Trong kiểm thử insert, hãy đọc lại bản ghi từ database để xác nhận giá trị được lưu thực sự, không chỉ kiểm tra object đầu vào.

## 14. Các lỗi thiết kế thường gặp

| Lỗi | Hậu quả | Cách xử lý |
| --- | --- | --- |
| Nghĩ rằng Java null luôn kích hoạt database default | Insert có thể ghi NULL tường minh và bỏ qua default. | Kiểm tra SQL; bỏ cột khỏi insert hoặc dùng SQL DEFAULT. |
| Dùng primitive cho cột nullable | Không thể biểu diễn trạng thái null; giá trị 0/false có thể bị ghi ngoài ý muốn. | Dùng wrapper hoặc kiểu nullable phù hợp. |
| Dùng nullable cho dữ liệu bắt buộc | Dữ liệu không hợp lệ có thể đi sâu vào hệ thống. | Dùng validation và constraint NOT NULL. |
| Dùng chuỗi rỗng thay cho NULL | Các truy vấn và quy tắc nghiệp vụ có thể hiểu sai trạng thái dữ liệu. | Chuẩn hóa và quy định rõ ý nghĩa. |
| Dùng một DTO cho cả create và PATCH | Không phân biệt trường bị bỏ qua với trường được gửi null. | Dùng command/DTO có ngữ nghĩa riêng. |
| Đặt default khác nhau ở Java và database | Kết quả phụ thuộc đường ghi. | Chọn nguồn quyết định và đồng bộ giá trị. |
| Cho rằng default tự áp dụng khi UPDATE | Giá trị cũ hoặc NULL vẫn được lưu. | Dùng câu lệnh cập nhật phù hợp, ví dụ SET column = DEFAULT nếu được hỗ trợ. |
| Chỉ kiểm tra bằng mock | Không phát hiện lỗi mapping, SQL, constraint hoặc default thật. | Có integration test với database tương thích. |

## 15. Quy trình thiết kế một thuộc tính nullable hoặc có default

Khi thêm một thuộc tính vào entity và schema, hãy đi theo trình tự:

1. **Xác định ngữ nghĩa nghiệp vụ:** giá trị có thể chưa biết, không áp dụng hay bắt buộc?
2. **Quyết định nullability:** chọn NULL hoặc NOT NULL và ghi rõ constraint trong migration.
3. **Quyết định default:** default thuộc database, domain hay application service?
4. **Chọn kiểu Java/Kotlin:** primitive hay wrapper, nullable annotation hay Kotlin nullable type.
5. **Xác định ngữ nghĩa insert:** client bỏ qua trường, gửi null hay gửi giá trị? Database có cần tự tạo default không?
6. **Xác định ngữ nghĩa update/PATCH:** null có nghĩa xóa giá trị hay giữ nguyên? Trường bị bỏ qua có nghĩa gì?
7. **Chọn cách ghi:** repository mapping thông thường, read-only property cho cột DB-managed hoặc SQL tùy chỉnh để bỏ cột.
8. **Kiểm thử trên database thật:** xác minh NULL, DEFAULT, constraint, mapping và dữ liệu sau insert/update.
9. **Triển khai migration theo giai đoạn:** bảo đảm dữ liệu cũ và các phiên bản ứng dụng đang chạy tương thích.

Một mô hình dữ liệu tốt làm cho ý nghĩa của từng trạng thái trở nên rõ ràng ở mọi tầng. `NULL` là trạng thái dữ liệu được schema cho phép; `DEFAULT` là quy tắc áp dụng khi câu lệnh yêu cầu database tạo giá trị; còn việc bỏ qua một trường trong API là quyết định của hợp đồng ứng dụng. Khi ba khái niệm này được phân biệt và ánh xạ nhất quán qua Java/Kotlin, Spring Data R2DBC và SQL, dữ liệu sẽ dễ kiểm soát hơn và các thao tác tạo, cập nhật ít gây mất mát thông tin.
