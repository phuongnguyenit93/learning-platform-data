# Phối hợp migration với khởi động ứng dụng R2DBC

## 1. Vì sao migration cần được phối hợp với startup?

Ứng dụng Spring Data R2DBC thường cần schema database tồn tại trước khi repository và service bắt đầu xử lý request. Schema bao gồm bảng, cột, khóa chính, unique constraint, foreign key, index, view và những đối tượng database khác mà câu truy vấn phụ thuộc vào.

Trong môi trường phát triển, một script tạo bảng thủ công có thể đủ để chạy thử. Khi ứng dụng được triển khai nhiều lần, có nhiều môi trường hoặc nhiều phiên bản cùng tồn tại, việc thay đổi schema cần được quản lý có lịch sử và có thể lặp lại một cách xác định. Đây là vai trò của **database migration**.

Migration là tập thay đổi schema hoặc dữ liệu được phiên bản hóa. Công cụ như Flyway hoặc Liquibase đọc các migration, kiểm tra thay đổi nào đã được áp dụng và thực thi phần còn thiếu.

Với ứng dụng R2DBC, cần phối hợp hai việc:

1. Migration phải hoàn tất trước khi ứng dụng thực thi truy vấn phụ thuộc vào schema mới.
2. Ứng dụng runtime phải kết nối database qua R2DBC driver và ConnectionFactory.

Một điểm quan trọng là nhiều công cụ migration phổ biến như Flyway và Liquibase sử dụng JDBC để kết nối database, trong khi đường truy cập dữ liệu của ứng dụng vẫn có thể dùng R2DBC. Hai đường kết nối này phục vụ hai nhiệm vụ khác nhau và có thể cùng tồn tại trong một ứng dụng.

## 2. Phân biệt migration với kết nối R2DBC runtime

Có thể hình dung kiến trúc như sau:

~~~text
                    Spring Boot startup
                            |
             +--------------+--------------+
             |                             |
             v                             v
      Migration subsystem            R2DBC runtime
      Flyway / Liquibase             Spring Data R2DBC
             |                             |
             v                             v
       JDBC DataSource                 ConnectionFactory
             |                             |
             v                             v
        JDBC Driver                    R2DBC Driver
             |                             |
             +--------------+--------------+
                            |
                            v
                      Same Database
                            |
                            v
                Schema / tables / indexes
~~~

Migration subsystem thay đổi schema bằng JDBC. R2DBC runtime đọc và ghi dữ liệu nghiệp vụ bằng reactive driver.

| Thành phần | Nhiệm vụ |
|---|---|
| Flyway hoặc Liquibase | Quản lý và áp dụng migration |
| JDBC DataSource | Cấp kết nối JDBC cho migration tool |
| JDBC driver | Giao tiếp với database theo JDBC |
| R2DBC ConnectionFactory | Cấp kết nối reactive cho ứng dụng |
| R2DBC driver | Giao tiếp với database theo R2DBC SPI |
| Spring Data R2DBC | Mapping entity và cung cấp repository/template |
| Schema history/changelog | Ghi nhận migration đã áp dụng |

Dùng JDBC cho migration không làm ứng dụng chuyển sang JDBC ở runtime. Ứng dụng vẫn có thể dùng ReactiveCrudRepository, R2dbcEntityTemplate và DatabaseClient cho mọi thao tác dữ liệu thông thường.

Ngược lại, chỉ khai báo R2DBC driver không tự cung cấp JDBC driver cho Flyway hoặc Liquibase. Nếu migration tool cần JDBC, classpath và cấu hình phải có JDBC driver tương ứng.

## 3. Chọn công cụ quản lý schema

### 3.1. Flyway

Flyway quản lý migration theo phiên bản và thứ tự. Cách phổ biến là tạo file SQL có tên theo quy ước:

~~~text
src/main/resources/
└── db/
    └── migration/
        ├── V1__create_customers.sql
        ├── V2__create_orders.sql
        ├── V3__add_customer_status.sql
        └── R__customer_active_view.sql
~~~

- Migration versioned thường có dạng V1, V2, V3 và được áp dụng theo thứ tự.
- Tên mô tả sau hai dấu gạch dưới giúp người đọc hiểu mục đích.
- Repeatable migration có tiền tố R và được chạy lại khi nội dung thay đổi theo quy tắc của Flyway.
- Flyway lưu lịch sử migration trong bảng schema history, mặc định thường là flyway_schema_history.

Ví dụ migration đầu tiên:

~~~sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(150) NOT NULL,
    email VARCHAR(320) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
~~~

Migration tiếp theo có thể thêm cột:

~~~sql
ALTER TABLE customers
ADD COLUMN status VARCHAR(30) NOT NULL DEFAULT 'ACTIVE';
~~~

Khi migration đã được áp dụng ở một môi trường chia sẻ, không sửa nội dung file cũ để thay đổi lịch sử. Hãy tạo version mới. Việc chỉnh sửa migration đã chạy có thể làm checksum không khớp và khiến Flyway báo lỗi validation.

### 3.2. Liquibase

Liquibase quản lý thay đổi bằng changelog. Changelog có thể được viết bằng XML, YAML, JSON hoặc định dạng SQL được hỗ trợ.

Ví dụ cấu trúc:

~~~text
src/main/resources/
└── db/
    └── changelog/
        ├── db.changelog-master.yaml
        └── changes/
            ├── 001-create-customers.yaml
            └── 002-add-customer-status.yaml
~~~

Một changelog YAML đơn giản:

~~~yaml
databaseChangeLog:
  - changeSet:
      id: 001-create-customers
      author: team
      changes:
        - createTable:
            tableName: customers
            columns:
              - column:
                  name: id
                  type: BIGINT
                  constraints:
                    primaryKey: true
                    nullable: false
              - column:
                  name: name
                  type: VARCHAR(150)
                  constraints:
                    nullable: false
              - column:
                  name: email
                  type: VARCHAR(320)
                  constraints:
                    nullable: false
~~~

Liquibase ghi nhận changeSet đã chạy trong các bảng DATABASECHANGELOG và DATABASECHANGELOGLOCK. Changelog master là điểm vào để Liquibase tìm các changeSet.

### 3.3. Không chạy hai công cụ migration trên cùng schema nếu không có chủ đích

Flyway và Liquibase đều quản lý lịch sử schema theo cách riêng. Nếu cả hai cùng tự động thay đổi một schema mà không có quy ước rõ, có thể xảy ra:

- Hai nguồn lịch sử migration không đồng bộ.
- Một công cụ không biết thay đổi do công cụ kia thực hiện.
- Khó xác định thứ tự thay đổi.
- Khó khôi phục hoặc kiểm tra schema giữa các môi trường.

Thông thường, chọn một công cụ làm nguồn quản lý schema chính cho mỗi database/schema. Nếu tổ chức có lý do dùng nhiều công cụ, cần phân chia ownership rõ ràng, ví dụ theo schema riêng và pipeline riêng.

## 4. Cấu hình Flyway cùng Spring Data R2DBC

Giả sử ứng dụng dùng PostgreSQL. Gradle có thể khai báo dependency theo hướng:

~~~groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-data-r2dbc'

    runtimeOnly 'org.postgresql:r2dbc-postgresql'

    implementation 'org.flywaydb:flyway-core'
    runtimeOnly 'org.flywaydb:flyway-database-postgresql'
    runtimeOnly 'org.postgresql:postgresql'
}
~~~

Spring Boot dependency management nên quản lý phiên bản tương thích. Tùy phiên bản Flyway, database module riêng như flyway-database-postgresql có thể là dependency cần thiết.

Hai driver có vai trò khác nhau:

- org.postgresql:r2dbc-postgresql là R2DBC driver cho runtime.
- org.postgresql:postgresql là JDBC driver cho Flyway.

### 4.1. Cấu hình hai URL

Ví dụ application.yml:

~~~yaml
spring:
  r2dbc:
    url: r2dbc:postgresql://localhost:5432/shop
    username: shop_app
    password: change-me

  flyway:
    url: jdbc:postgresql://localhost:5432/shop
    user: shop_migrator
    password: change-me
    locations: classpath:db/migration
    enabled: true
~~~

Hai URL trỏ tới cùng database nhưng dùng scheme và driver khác nhau:

- R2DBC URL bắt đầu bằng r2dbc:.
- JDBC URL bắt đầu bằng jdbc:.

Có thể dùng cùng tài khoản trong môi trường phát triển, nhưng production thường nên tách quyền:

- Tài khoản migration được cấp quyền DDL cần thiết để tạo/sửa bảng, index và constraint.
- Tài khoản runtime chỉ có quyền DML cần cho ứng dụng, ví dụ SELECT, INSERT, UPDATE và DELETE trên các bảng được phép.

Tách quyền giúp giảm rủi ro khi ứng dụng runtime bị khai thác hoặc có lỗi ghi dữ liệu. Không cần cấp quyền ALTER/DROP cho tài khoản runtime nếu ứng dụng không có yêu cầu đó.

Không commit password thật vào repository. Dùng biến môi trường, secret manager hoặc cơ chế quản lý secret của nền tảng triển khai.

### 4.2. Flyway chạy ở đâu trong startup?

Khi Flyway auto-configuration được bật, Spring Boot tạo Flyway bean và thực hiện migration trong quá trình khởi tạo application context. Database initialization dependency infrastructure của Boot giúp các bean phụ thuộc vào database initialization được khởi tạo sau khi migration hoàn tất.

Kết quả mong muốn:

~~~text
Application startup
       |
       v
Create migration DataSource
       |
       v
Flyway validates history
       |
       v
Flyway applies pending migrations
       |
       v
Migration completed
       |
       v
R2DBC repositories/services
       |
       v
Application ready
~~~

Nếu migration thất bại, startup thường thất bại thay vì để ứng dụng phục vụ request với schema chưa đúng. Đây là hành vi fail-fast có ích cho môi trường production: lỗi migration phải được phát hiện ở deployment/startup.

Với bean tự viết có chạy query ngay trong giai đoạn khởi tạo, cần xác định rõ dependency ordering. Tránh thực hiện truy vấn database trong constructor hoặc @PostConstruct trước khi chắc chắn migration đã chạy. Khi thật sự cần một bean phụ thuộc database initialization, có thể dùng cơ chế dependency phù hợp của Spring Boot như @DependsOnDatabaseInitialization trên phiên bản hỗ trợ.

## 5. Cấu hình Liquibase cùng R2DBC

Liquibase cũng thường sử dụng JDBC để thực thi changelog. Với PostgreSQL, dependency có thể gồm:

~~~groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-data-r2dbc'
    runtimeOnly 'org.postgresql:r2dbc-postgresql'

    implementation 'org.liquibase:liquibase-core'
    runtimeOnly 'org.postgresql:postgresql'
}
~~~

Cấu hình application.yml:

~~~yaml
spring:
  r2dbc:
    url: r2dbc:postgresql://localhost:5432/shop
    username: shop_app
    password: change-me

  liquibase:
    url: jdbc:postgresql://localhost:5432/shop
    user: shop_migrator
    password: change-me
    change-log: classpath:db/changelog/db.changelog-master.yaml
    enabled: true
~~~

Liquibase đọc changelog master, xác định changeSet nào chưa được áp dụng và thực thi chúng qua JDBC. Lịch sử được ghi trong DATABASECHANGELOG; DATABASECHANGELOGLOCK giúp điều phối việc chạy changelog.

Không cấu hình Flyway và Liquibase cùng quản lý một schema nếu chưa có ownership và thứ tự migration rõ ràng. Chọn một công cụ phù hợp với quy trình nhóm và chuẩn hóa cách chạy giữa local, CI và production.

## 6. SQL script initialization của Spring Boot

Spring Boot còn hỗ trợ khởi tạo database bằng các script như schema.sql và data.sql. Đây là cơ chế đơn giản để tạo schema hoặc dữ liệu ban đầu, thường hữu ích trong ví dụ nhỏ, test hoặc môi trường phát triển.

Ví dụ:

~~~text
src/main/resources/
├── schema.sql
└── data.sql
~~~

schema.sql:

~~~sql
CREATE TABLE IF NOT EXISTS customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(150) NOT NULL,
    email VARCHAR(320) NOT NULL
);
~~~

data.sql:

~~~sql
INSERT INTO customers (name, email)
VALUES ('An Nguyen', 'an@example.test');
~~~

Có thể cấu hình:

~~~yaml
spring:
  sql:
    init:
      mode: always
      schema-locations: classpath:schema.sql
      data-locations: classpath:data.sql
~~~

Spring Boot hỗ trợ script initialization cho JDBC và R2DBC. Với R2DBC, script được thực thi thông qua cơ chế khởi tạo dựa trên ConnectionFactory. Các property thuộc nhóm spring.sql.init được dùng để cấu hình hành vi này.

### 6.1. Chế độ initialization

Các giá trị mode thường dùng:

| Giá trị | Ý nghĩa |
|---|---|
| embedded | Chỉ khởi tạo database embedded theo mặc định |
| always | Luôn chạy script initialization |
| never | Tắt script initialization |

Nếu cần schema cho PostgreSQL/MySQL trong môi trường phát triển, mode always có thể bật script. Nhưng không nên đưa script tạo lại schema hoặc chèn dữ liệu mẫu vào production mà không hiểu rõ tác động.

### 6.2. Khi dùng Flyway hoặc Liquibase

Nếu Flyway/Liquibase là nguồn quản lý schema, nên tắt script initialization không cần thiết:

~~~yaml
spring:
  sql:
    init:
      mode: never
~~~

Điều này tránh có hai cơ chế cùng tạo hoặc thay đổi bảng trong startup. Một schema có thể bị thay đổi theo thứ tự khó đoán nếu script initialization và migration tool cùng hoạt động mà không có dependency rõ ràng.

Script initialization không cung cấp đầy đủ lịch sử migration, checksum, versioning và quy trình nâng cấp schema như Flyway/Liquibase. Vì vậy, nó thường phù hợp với schema đơn giản, test hoặc prototype hơn là quản lý thay đổi lâu dài của production.

## 7. Đảm bảo migration hoàn tất trước khi ứng dụng phục vụ request

Startup ordering là phần quan trọng nhất khi phối hợp migration và R2DBC.

### 7.1. Dựa vào auto-configuration chuẩn của Spring Boot

Khi dùng Flyway hoặc Liquibase theo cấu hình chuẩn, hãy để Spring Boot quản lý migration bean và dependency ordering. Không tự chạy thêm một migration lần nữa trong ApplicationRunner hoặc CommandLineRunner nếu auto-configuration đã thực hiện.

Tạo thêm một bước migration thủ công có thể gây:

- Migration chạy hai lần.
- Hai thành phần cạnh tranh cùng migration lock.
- Khó xác định migration thất bại ở bước nào.
- Startup phụ thuộc thứ tự bean tình cờ.

### 7.2. Không query schema trong constructor

Không nên:

~~~java
@Component
class StartupVerifier {

    StartupVerifier(DatabaseClient client) {
        client.sql("SELECT COUNT(*) FROM customers")
                .fetch()
                .one()
                .block();
    }
}
~~~

Constructor được gọi khi Spring tạo bean. Việc query ở đây có thể xảy ra trước khi migration hoàn tất, đồng thời block thread trong quá trình khởi động.

Nếu cần kiểm tra dữ liệu sau migration, hãy dùng cơ chế startup task có thứ tự rõ ràng và reactive publisher được tiêu thụ đúng cách, hoặc để một deployment health check thực hiện kiểm tra sau khi ứng dụng sẵn sàng. Không đặt công việc blocking vào constructor.

### 7.3. Phân biệt application startup và readiness

Một process có thể đã mở cổng HTTP nhưng chưa sẵn sàng phục vụ nghiệp vụ. Trong môi trường orchestration, readiness probe nên chỉ thành công khi migration và các dependency cần thiết đã sẵn sàng.

Nếu migration được chạy như một job riêng trước deployment, readiness của ứng dụng cần xác nhận schema version tương thích với binary đang chạy. Không nên chỉ kiểm tra TCP port hoặc việc process còn sống.

### 7.4. Migration fail-fast

Nếu migration không thể kết nối database, checksum sai hoặc DDL thất bại, ứng dụng không nên âm thầm tiếp tục như thể schema đã sẵn sàng.

Hãy để deployment báo lỗi, thu thập log migration và xử lý nguyên nhân. Tắt migration chỉ để làm startup thành công có thể khiến ứng dụng chạy trên schema sai phiên bản và gây lỗi dữ liệu khi request đầu tiên tới.

## 8. Migration trong môi trường nhiều replica

Trong Kubernetes hoặc môi trường scale-out, có thể có nhiều instance ứng dụng khởi động gần như cùng lúc. Nếu mỗi instance đều tự chạy migration, migration tool phải xử lý cạnh tranh.

Flyway và Liquibase có cơ chế khóa/lịch sử để điều phối migration. Tuy nhiên, cách triển khai thường dễ kiểm soát hơn là chạy migration một lần trong pipeline hoặc job chuyên biệt trước khi scale application replicas.

Ví dụ deployment flow:

~~~text
Build artifact
     |
     v
Run migration job
     |
     v
Migration successful?
     |
  +--+--+
  |     |
 No    Yes
  |     |
  v     v
Stop  Deploy application
      replicas
         |
         v
      Readiness
         |
         v
      Serve traffic
~~~

Lợi ích:

- Chỉ có một bước chịu trách nhiệm thay đổi schema.
- Có thể cấp credential DDL riêng cho migration job.
- Application runtime không cần quyền thay đổi schema.
- Dễ tách log migration khỏi log runtime.
- Có thể chặn deployment nếu migration thất bại.
- Dễ phối hợp migration với phiên bản binary sẽ được phát hành.

Nếu vẫn bật migration tự động trong mọi instance, cần xác nhận locking, timeout và behavior khi nhiều process cùng khởi động theo phiên bản công cụ/database đang dùng.

## 9. Quản lý profile và môi trường

Cấu hình migration thường khác giữa local, test, staging và production.

Ví dụ profile local:

~~~yaml
spring:
  flyway:
    enabled: true
    locations: classpath:db/migration

  r2dbc:
    url: r2dbc:postgresql://localhost:5432/shop
~~~

Ví dụ profile test có thể dùng database do Testcontainers cung cấp:

~~~yaml
spring:
  flyway:
    enabled: true

  sql:
    init:
      mode: never
~~~

Production có thể chạy migration trong deployment job riêng và tắt auto migration trong application:

~~~yaml
spring:
  flyway:
    enabled: false
~~~

Khi chọn cách này, pipeline phải bảo đảm migration job hoàn tất trước khi application version mới được triển khai. Nếu không, ứng dụng có thể chạy trước schema.

Không nên để profile test vô tình dùng database phát triển hoặc production. URL, username và password phải được cấp từ môi trường tương ứng. Tránh lưu credential thật trong file YAML được commit.

## 10. Version hóa migration và quy tắc không sửa lịch sử

Migration cần có thứ tự và ý nghĩa rõ ràng. Ví dụ:

~~~text
V1__create_customers.sql
V2__create_orders.sql
V3__add_customer_status.sql
V4__create_customer_email_index.sql
~~~

Khi V2 đã chạy ở staging hoặc production, nếu phát hiện thiếu cột, hãy tạo V5 để sửa. Không sửa V2 rồi kỳ vọng tất cả môi trường tự trở về trạng thái giống nhau.

Lý do:

- Môi trường A có thể đã chạy V2 cũ.
- Môi trường B có thể chưa chạy V2.
- Checksum migration có thể khác nhau.
- Một số database không hỗ trợ rollback DDL đầy đủ.
- Lịch sử triển khai sẽ không còn tái lập được.

Với Liquibase, changeSet đã được áp dụng cũng nên được xem là bất biến. Nếu cần sửa schema, tạo changeSet mới thay vì chỉnh changeSet đã chạy trên môi trường chia sẻ.

Migration history là một phần của trạng thái hệ thống. Cần lưu migration trong version control cùng mã nguồn và review như một thay đổi ứng dụng.

## 11. Thiết kế migration tương thích với rolling deployment

Một thay đổi schema có thể được triển khai trong khi phiên bản ứng dụng cũ và mới cùng chạy. Vì vậy, migration cần cân nhắc backward/forward compatibility.

Ví dụ muốn đổi cột name thành display_name.

Cách nguy hiểm:

1. Rename name thành display_name ngay.
2. Deploy code mới.
3. Replica cũ vẫn chạy và truy vấn name.
4. Request trên replica cũ thất bại.

Một cách an toàn hơn là **expand-and-contract**:

### Giai đoạn 1: Expand

Thêm cột mới, giữ cột cũ:

~~~sql
ALTER TABLE customers
ADD COLUMN display_name VARCHAR(150);
~~~

### Giai đoạn 2: Deploy code tương thích

Deploy code có thể đọc cột cũ hoặc mới và ghi đồng bộ cả hai theo kế hoạch chuyển đổi. Trong giai đoạn rolling deployment, phiên bản cũ vẫn dùng cột cũ.

### Giai đoạn 3: Backfill

Sao chép dữ liệu cũ sang cột mới:

~~~sql
UPDATE customers
SET display_name = name
WHERE display_name IS NULL;
~~~

Với bảng lớn, backfill nên được chia batch hoặc chạy như một job riêng để tránh transaction quá lớn và lock kéo dài.

### Giai đoạn 4: Chuyển ứng dụng

Deploy phiên bản chỉ dùng display_name sau khi dữ liệu đã được backfill và mọi replica cũ đã ngừng hoạt động.

### Giai đoạn 5: Contract

Ở một release sau, khi không còn code dùng cột cũ, mới xóa cột name:

~~~sql
ALTER TABLE customers
DROP COLUMN name;
~~~

Tách các giai đoạn giúp giảm nguy cơ schema mới phá phiên bản ứng dụng cũ trong rolling deployment.

## 12. Migration dữ liệu và backfill

Migration không chỉ tạo bảng hoặc thêm cột. Có thể cần chuyển đổi dữ liệu cũ sang cấu trúc mới.

Ví dụ thêm normalized_email:

~~~sql
ALTER TABLE customers
ADD COLUMN normalized_email VARCHAR(320);
~~~

Backfill:

~~~sql
UPDATE customers
SET normalized_email = LOWER(TRIM(email))
WHERE normalized_email IS NULL;
~~~

Sau đó có thể tạo unique index nếu quy tắc nghiệp vụ yêu cầu email chuẩn hóa là duy nhất:

~~~sql
CREATE UNIQUE INDEX uq_customers_normalized_email
ON customers (normalized_email);
~~~

Trước khi tạo unique index, phải xác định và xử lý dữ liệu trùng hiện có. Nếu có nhiều email sau chuẩn hóa giống nhau, migration sẽ thất bại hoặc không thể tạo constraint.

Với bảng lớn, không nên mặc định một UPDATE toàn bảng là an toàn. Hãy xem xét:

- Kích thước bảng và tốc độ ghi.
- Lock duration.
- Transaction log/WAL growth.
- Replication lag.
- Batch size và checkpoint.
- Khả năng chạy lại job.
- Cách xử lý bản ghi mới được ghi trong lúc backfill.

Backfill dài thường phù hợp với job có thể quan sát tiến độ và retry hơn là một migration startup giữ transaction lớn.

## 13. DDL transaction và giới hạn rollback

Không phải database nào cũng hỗ trợ transaction cho mọi câu lệnh DDL theo cùng một cách. Một số thay đổi schema có thể commit ngầm hoặc có giới hạn khi chạy trong transaction.

Vì vậy:

- Không giả định một migration thất bại luôn rollback toàn bộ DDL.
- Kiểm tra semantics DDL của database mục tiêu.
- Dùng migration nhỏ, dễ xác định trạng thái sau lỗi.
- Có kế hoạch forward-fix nếu không thể rollback an toàn.
- Sao lưu và kiểm tra restore trước thay đổi có rủi ro cao.
- Tránh xóa/đổi kiểu cột chứa dữ liệu quan trọng trong cùng bước deploy ứng dụng.

Flyway/Liquibase giúp quản lý lịch sử và thực thi migration, nhưng không tự làm mọi thay đổi DDL có thể rollback. Khả năng rollback phụ thuộc database và nội dung migration.

## 14. Migration lock và xử lý khởi động đồng thời

Khi nhiều process cùng chạy migration, công cụ cần cơ chế tránh hai process đồng thời thay đổi schema.

- Flyway sử dụng schema history và cơ chế locking để điều phối migration.
- Liquibase dùng bảng DATABASECHANGELOGLOCK để quản lý lock.

Nếu process bị dừng khi đang migration, cần xem trạng thái database, log và lock trước khi can thiệp thủ công. Không tùy tiện xóa bảng lịch sử hoặc lock row khi chưa xác định migration có còn chạy hay không.

Trong production, migration job đơn lẻ thường giúp giảm contention. Nếu dùng startup migration ở nhiều replica, cần đặt timeout và quan sát rõ trường hợp một replica phải chờ migration lock.

## 15. Cấu hình nhiều database hoặc nhiều schema

Một ứng dụng có thể dùng nhiều ConnectionFactory R2DBC và nhiều schema/database. Mỗi database cần migration plan riêng.

Ví dụ:

~~~text
Application
├── Customer database
│   ├── R2DBC ConnectionFactory
│   └── Customer migrations
└── Order database
    ├── R2DBC ConnectionFactory
    └── Order migrations
~~~

Không nên dùng một bộ migration location chung cho nhiều database nếu các thay đổi không áp dụng cho cả hai.

Với nhiều database, có thể:

- Chạy migration job riêng cho từng database.
- Tạo Flyway/Liquibase instance riêng với JDBC URL, schema và changelog/location tương ứng.
- Dùng tài khoản migration riêng cho từng database.
- Kiểm tra từng migration thành công trước khi ứng dụng phụ thuộc database đó được readiness.
- Tách rõ repository/template/ConnectionFactory của từng database.

Một transaction manager R2DBC chỉ quản lý ConnectionFactory mà nó được cấu hình. Việc migration cả hai database thành công không tạo transaction phân tán cho thao tác runtime giữa chúng.

Nếu nghiệp vụ cần ghi đồng thời hai database, phải thiết kế saga, outbox hoặc cơ chế phối hợp phù hợp. Migration startup chỉ giải quyết schema của từng database.

## 16. Tạo dữ liệu mẫu và seed data

Dữ liệu khởi tạo có thể được chia thành hai loại:

- **Reference data:** danh mục ổn định như loại trạng thái, đơn vị đo hoặc mã quốc gia.
- **Sample/test data:** dữ liệu minh họa chỉ dành cho local hoặc test.

Reference data có thể được quản lý qua migration nếu thay đổi của nó cần được version hóa. Hãy dùng khóa ổn định và thao tác có thể chạy lặp lại an toàn khi công cụ hỗ trợ.

Sample data nên nằm trong profile hoặc script test riêng. Không để data.sql chứa user mẫu, password mặc định hoặc dữ liệu minh họa được nạp vào production ngoài ý muốn.

Nếu dùng Flyway repeatable migration để quản lý view hoặc dữ liệu tham chiếu, cần hiểu rằng file có thể được chạy lại khi checksum thay đổi. Câu lệnh phải được thiết kế phù hợp với hành vi chạy lại.

Không dùng migration để nạp lượng dữ liệu nghiệp vụ khổng lồ. Import lớn nên là batch job có checkpoint, theo dõi và retry riêng.

## 17. Kiểm tra schema tương thích với ứng dụng

Migration thành công không tự chứng minh code runtime tương thích. Ứng dụng có thể cần:

- Bảng hoặc cột mới.
- Kiểu dữ liệu chính xác.
- Unique constraint hoặc foreign key.
- Index hỗ trợ query.
- Default value và nullability đúng.
- View hoặc function được tạo.
- Quyền truy cập của tài khoản runtime.

Có thể thêm một kiểm tra schema version hoặc smoke query sau migration. Với Flyway, lịch sử có thể được đọc từ schema history; với Liquibase, từ DATABASECHANGELOG. Tuy nhiên, code ứng dụng không nên tự sửa schema chỉ để khớp version.

Nếu cần kiểm tra cụ thể, chạy một query nhỏ qua R2DBC sau khi migration hoàn tất và trước khi đánh dấu instance ready. Việc kiểm tra này cần có ordering rõ ràng và không nên đặt trong constructor bean.

## 18. Kiểm thử migration cùng R2DBC bằng Testcontainers

Integration test nên xác nhận cả hai đường kết nối:

1. Database container được khởi động.
2. Flyway/Liquibase chạy migration bằng JDBC.
3. Spring Data R2DBC tạo ConnectionFactory.
4. Repository hoặc R2dbcEntityTemplate truy cập schema vừa được tạo.
5. Test kiểm tra CRUD và query thực tế.

Ví dụ dependency test cho PostgreSQL:

~~~groovy
dependencies {
    testImplementation 'org.springframework.boot:spring-boot-starter-test'
    testImplementation 'org.testcontainers:junit-jupiter'
    testImplementation 'org.testcontainers:postgresql'
}
~~~

Có thể dùng Testcontainers để cấp một PostgreSQL dùng chung cho migration và R2DBC. Cấu hình test phải cung cấp cả hai URL:

- JDBC URL cho Flyway/Liquibase.
- R2DBC URL cho Spring Data R2DBC.

Ví dụ ý tưởng cấu hình bằng DynamicPropertySource:

~~~java
@DynamicPropertySource
static void databaseProperties(DynamicPropertyRegistry registry) {
    registry.add("spring.flyway.url", postgres::getJdbcUrl);
    registry.add("spring.flyway.user", postgres::getUsername);
    registry.add("spring.flyway.password", postgres::getPassword);

    registry.add("spring.r2dbc.url", () ->
            postgres.getJdbcUrl().replace(
                    "jdbc:postgresql:",
                    "r2dbc:postgresql:"
            )
    );
    registry.add("spring.r2dbc.username", postgres::getUsername);
    registry.add("spring.r2dbc.password", postgres::getPassword);
}
~~~

Đoạn code minh họa giả định container PostgreSQL đã được khai báo và khởi động trong test class. Kiểm tra cú pháp URL theo driver và phiên bản đang dùng; không hardcode host/port vì Testcontainers có thể cấp cổng động.

### 18.1. Kiểm tra migration được chạy

Có thể kiểm tra bảng hoặc cột được tạo bằng một query qua DatabaseClient:

~~~java
StepVerifier.create(
        databaseClient.sql("""
                SELECT COUNT(*)
                FROM information_schema.tables
                WHERE table_name = 'customers'
                """)
            .map((row, metadata) -> row.get(0, Long.class))
            .one()
    )
    .expectNext(1L)
    .verifyComplete();
~~~

Cú pháp metadata query phụ thuộc database. Với PostgreSQL, có thể dùng information_schema hoặc catalog phù hợp. Mục tiêu là xác nhận schema đã tồn tại qua R2DBC runtime path.

### 18.2. Kiểm tra repository sử dụng schema mới

Sau khi migration, thực hiện insert/select qua repository:

~~~java
StepVerifier.create(
        customerRepository.save(
                new Customer(null, "An", "an@example.test", "ACTIVE")
        )
)
.assertNext(saved -> assertThat(saved.id()).isNotNull())
.verifyComplete();
~~~

Test này chứng minh migration và R2DBC mapping phối hợp được. Chỉ kiểm tra Flyway bean thành công chưa đủ nếu code runtime có thể dùng sai URL, schema hoặc credential.

## 19. Pipeline CI/CD cho migration

Một pipeline triển khai có thể được tổ chức:

~~~text
Compile / unit tests
        |
        v
Build application artifact
        |
        v
Start ephemeral database
        |
        v
Run migrations
        |
        v
Run R2DBC integration tests
        |
        v
Package / publish artifact
        |
        v
Backup / deployment approval as required
        |
        v
Run production migration job
        |
        v
Deploy application version
        |
        v
Readiness and smoke tests
~~~

CI nên kiểm tra migration từ schema rỗng và cả nâng cấp từ schema phiên bản trước nếu dự án cần hỗ trợ upgrade. Test schema rỗng xác nhận toàn bộ lịch sử có thể tạo database mới; test upgrade xác nhận migration mới tương thích với dữ liệu đã tồn tại.

Production migration job nên:

- Dùng đúng artifact/changelog của release.
- Có credential DDL riêng.
- Chạy một lần theo deployment orchestration.
- Ghi log và lưu kết quả.
- Dừng deployment nếu migration thất bại.
- Có backup/restore hoặc forward-fix plan phù hợp với mức độ rủi ro.

Không chạy migration production bằng tài khoản runtime của ứng dụng nếu có thể tách quyền.

## 20. Quan sát và xử lý lỗi startup

Các lỗi phổ biến:

| Dấu hiệu | Nguyên nhân có thể | Hướng xử lý |
|---|---|---|
| Flyway không tìm thấy JDBC driver | Chỉ khai báo R2DBC driver | Thêm JDBC driver cho database |
| R2DBC kết nối thành công nhưng migration thất bại | JDBC URL/driver/credential sai | Kiểm tra spring.flyway.url và JDBC dependency |
| Migration báo checksum mismatch | File versioned đã bị sửa sau khi áp dụng | Khôi phục lịch sử hoặc tạo migration mới theo quy trình |
| Không tìm thấy migration | Sai locations hoặc file naming | Kiểm tra classpath và quy ước tên file |
| Ứng dụng lỗi vì thiếu bảng | Migration tắt hoặc chạy sau code khởi tạo query | Bật migration hoặc sửa startup ordering |
| Nhiều replica chờ migration | Nhiều process cùng tranh lock | Dùng migration job riêng hoặc cấu hình chờ phù hợp |
| SQL script chạy hai lần | Script initializer và Flyway/Liquibase cùng hoạt động | Chọn một cơ chế quản lý schema |
| Runtime bị permission denied | Tài khoản R2DBC thiếu quyền DML hoặc schema usage | Cấp quyền tối thiểu cần thiết |
| Migration thành công nhưng repository lỗi | Mapping/cột/schema không khớp hoặc R2DBC URL trỏ database khác | So sánh JDBC và R2DBC target, kiểm tra entity mapping |
| Migration timeout | Database chưa sẵn sàng, lock hoặc DDL dài | Kiểm tra database health, lock và thời gian migration |
| DDL thất bại giữa chừng | Database có giới hạn transaction DDL | Xác định trạng thái thực tế và forward-fix an toàn |
| Test chạy local nhưng CI lỗi | Database/driver version hoặc URL khác nhau | Dùng cùng loại/version database trong Testcontainers |

### 20.1. Kiểm tra JDBC và R2DBC có trỏ cùng database

Một lỗi nguy hiểm là Flyway chạy migration vào database A nhưng ứng dụng R2DBC kết nối database B. Cả hai kết nối đều có thể thành công, nhưng repository vẫn báo thiếu bảng.

Hãy so sánh:

- Host và port.
- Database name.
- Schema/catalog.
- Username và quyền.
- Search path/default schema.
- SSL và các tham số kết nối.
- Profile đang active.

Không chỉ so sánh tên môi trường. Kiểm tra database identity thực tế bằng query phù hợp nếu cần.

### 20.2. Không bỏ qua lỗi migration để giữ ứng dụng sống

Nếu migration thất bại, tránh cấu hình để ứng dụng tiếp tục phục vụ request trên schema không tương thích. Điều đó có thể tạo lỗi ghi một phần hoặc làm hỏng dữ liệu.

Hãy phân loại lỗi kết nối, checksum, lock, permission và DDL. Sau đó sửa migration hoặc môi trường, rồi chạy lại theo chính sách công cụ. Không xóa lịch sử migration để ép startup thành công.

## 21. Những anti-pattern cần tránh

- Dùng schema.sql và Flyway/Liquibase cùng thay đổi một schema mà không có ordering.
- Chỉ khai báo R2DBC driver nhưng quên JDBC driver cần cho migration tool.
- Đặt migration logic trong constructor hoặc @PostConstruct.
- Dùng block() trong quá trình khởi tạo reactive application.
- Chạy migration bằng tài khoản runtime có quyền DDL quá rộng.
- Sửa file migration đã được áp dụng trên môi trường chia sẻ.
- Cho mọi replica tự thực hiện backfill lớn khi khởi động.
- Xóa thủ công bảng lịch sử hoặc lock mà không xác định trạng thái.
- Deploy binary mới trước khi schema tương thích.
- Rename/drop cột ngay trong một release khi replica cũ vẫn còn chạy.
- Để ứng dụng phục vụ traffic dù migration bắt buộc thất bại.
- Dùng migration để import dữ liệu nghiệp vụ khối lượng lớn.
- Giả định migration rollback luôn khôi phục được DDL trên mọi database.

## 22. Checklist phối hợp migration và R2DBC startup

Trước khi triển khai, xác nhận:

1. Đã chọn một công cụ migration chính cho database/schema.
2. Migration file được lưu trong version control và có tên/phiên bản rõ.
3. Đã thêm JDBC driver nếu Flyway/Liquibase cần JDBC.
4. R2DBC driver và ConnectionFactory được cấu hình riêng cho runtime.
5. JDBC URL và R2DBC URL trỏ đúng cùng database/schema.
6. Credential migration có quyền DDL cần thiết.
7. Credential runtime chỉ có quyền dữ liệu tối thiểu.
8. Migration chạy trước các thao tác runtime phụ thuộc schema.
9. Không query database trong constructor hoặc startup hook không có ordering.
10. Script initializer được tắt nếu migration tool là nguồn schema chính.
11. Migration thất bại làm deployment/startup thất bại theo chính sách.
12. Nhiều replica không tạo ra migration race ngoài kiểm soát.
13. Migration tương thích với rolling deployment hoặc được chia expand/contract.
14. Backfill lớn có kế hoạch batch và quan sát riêng.
15. Testcontainers xác nhận migration và R2DBC repository cùng hoạt động.
16. CI kiểm tra cả database mới và upgrade từ schema hiện hữu khi cần.
17. Có backup/restore hoặc forward-fix plan cho thay đổi rủi ro cao.
18. Readiness chỉ thành công khi schema và dependency cần thiết đã sẵn sàng.

## 23. Kết luận

Phối hợp migration với startup ứng dụng R2DBC đòi hỏi tách rõ nhiệm vụ thay đổi schema và truy cập dữ liệu runtime. Flyway hoặc Liquibase thường dùng JDBC để áp dụng migration; Spring Data R2DBC vẫn dùng R2DBC ConnectionFactory và driver cho repository, template và DatabaseClient. Vì vậy, một ứng dụng có thể cần cả JDBC driver lẫn R2DBC driver cho cùng database.

Với cấu hình Spring Boot chuẩn, migration có thể chạy trong quá trình khởi tạo application context và các thành phần phụ thuộc database initialization được sắp thứ tự phù hợp. Không nên tự query database trong constructor hoặc bỏ qua lỗi migration. Script schema.sql/data.sql phù hợp với khởi tạo đơn giản; dự án cần quản lý schema lâu dài thường nên dùng một công cụ migration có lịch sử.

Trong production, cân nhắc chạy migration như một job riêng trước khi triển khai application replicas, dùng tài khoản DDL riêng, giữ migration đã áp dụng bất biến và thiết kế thay đổi tương thích với rolling deployment. Kiểm thử bằng database thật hoặc Testcontainers, xác nhận cả migration JDBC lẫn truy vấn R2DBC. Khi hai đường kết nối cùng nhìn thấy đúng schema và readiness chỉ mở sau khi migration thành công, ứng dụng mới có thể khởi động và phục vụ dữ liệu một cách đáng tin cậy.
