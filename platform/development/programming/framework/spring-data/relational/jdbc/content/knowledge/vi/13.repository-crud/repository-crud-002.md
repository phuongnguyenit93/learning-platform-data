# Kết hợp giao diện CRUD với PagingAndSortingRepository

Trong **Spring Data Relational JDBC**, repository là cổng truy cập dữ liệu của aggregate. `CrudRepository` cung cấp các thao tác tạo, đọc, cập nhật và xóa cơ bản; `PagingAndSortingRepository` bổ sung khả năng đọc dữ liệu theo trang và sắp xếp. Kết hợp hai giao diện giúp một repository vừa có API CRUD vừa hỗ trợ truy vấn danh sách lớn theo từng phần.

Khi dùng Spring Data hiện đại, cần chú ý thay đổi quan trọng từ **Spring Data 3.0**: `PagingAndSortingRepository` không còn kế thừa `CrudRepository`. Vì vậy, nếu cần cả hai nhóm phương thức, hãy khai báo cả hai interface trong repository của mình. Nhiều ví dụ cũ chỉ kế thừa `PagingAndSortingRepository` vì chúng được viết cho phiên bản trước 3.0.

Bài học này trình bày cấu trúc interface, cách gọi các phương thức CRUD, `Pageable`, `PageRequest`, `Sort`, cách tạo query có phân trang và những lưu ý khi dùng trong ứng dụng Spring Data JDBC.

## 1. Hai giao diện giải quyết hai nhóm nhu cầu

`CrudRepository` định nghĩa các thao tác CRUD phổ biến:

| Phương thức | Mục đích |
| --- | --- |
| `save(entity)` | Lưu một entity |
| `saveAll(entities)` | Lưu nhiều entity |
| `findById(id)` | Tìm theo ID, trả `Optional` |
| `existsById(id)` | Kiểm tra ID có tồn tại |
| `findAll()` | Đọc tất cả entity |
| `findAllById(ids)` | Đọc theo một tập ID |
| `count()` | Đếm số entity |
| `deleteById(id)` | Xóa theo ID |
| `delete(entity)` | Xóa entity |
| `deleteAll()` | Xóa toàn bộ entity |

`PagingAndSortingRepository` bổ sung hai dạng đọc danh sách:

| Phương thức | Mục đích |
| --- | --- |
| `findAll(Sort sort)` | Đọc danh sách theo thứ tự sắp xếp |
| `findAll(Pageable pageable)` | Đọc một trang dữ liệu, có thể kèm thông tin sắp xếp |

CRUD trả lời câu hỏi **thực hiện thao tác gì trên aggregate?** Paging/sorting trả lời **đọc tập kết quả theo thứ tự và phạm vi nào?** Hai nhóm có thể cùng tồn tại trong một repository.

### 1.1. Thay đổi hierarchy từ Spring Data 3.0

Ở các phiên bản Spring Data trước 3.0, `PagingAndSortingRepository` kế thừa `CrudRepository`. Vì vậy, code cũ thường chỉ cần:

```java
// Ví dụ theo hierarchy của các phiên bản Spring Data cũ.
interface CustomerRepository
        extends PagingAndSortingRepository<Customer, Long> {
}
```

Từ Spring Data 3.0, hai interface được tách riêng và cùng kế thừa marker interface `Repository`:

```text
                 Repository<T, ID>
                    /       \
                   /         \
          CrudRepository   PagingAndSortingRepository
              (CRUD)          (Page / Sort)
                   \           /
                    \         /
                 CustomerRepository
```

Do đó, nếu ứng dụng dùng Spring Data 3.x và cần cả hai nhóm API, khai báo:

```java
interface CustomerRepository
        extends CrudRepository<Customer, Long>,
                PagingAndSortingRepository<Customer, Long> {
}
```

Đây là kiểu kết hợp nhiều interface Java. Spring Data tạo một repository proxy triển khai các thao tác phù hợp; không cần tự viết class implement từng phương thức. Generic type phải nhất quán: `Customer` là domain type và `Long` phải đúng kiểu của thuộc tính `@Id`.

## 2. Khai báo entity và repository hoàn chỉnh

Ví dụ entity khách hàng:

```java
import java.time.Instant;
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Table;

@Table("customer")
public record Customer(
        @Id Long id,
        String fullName,
        String email,
        String status,
        Instant createdAt
) {}
```

Schema PostgreSQL minh họa:

```sql
CREATE TABLE customer (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    full_name VARCHAR(120) NOT NULL,
    email VARCHAR(255) NOT NULL UNIQUE,
    status VARCHAR(30) NOT NULL,
    created_at TIMESTAMP NOT NULL
);
```

Khai báo repository:

```java
import org.springframework.data.repository.CrudRepository;
import org.springframework.data.repository.PagingAndSortingRepository;

public interface CustomerRepository
        extends CrudRepository<Customer, Long>,
                PagingAndSortingRepository<Customer, Long> {
}
```

Khi Spring Boot đã cấu hình Spring Data JDBC và repository scanning, Spring tạo bean `CustomerRepository` để inject vào service. Nếu cấu hình thủ công ngoài Spring Boot, cần bật repository infrastructure phù hợp, chẳng hạn `@EnableJdbcRepositories` và `DataSource`/transaction manager.

Ví dụ service:

```java
import java.util.Optional;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class CustomerService {

    private final CustomerRepository repository;

    public CustomerService(CustomerRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public Customer create(Customer customer) {
        return repository.save(customer);
    }

    public Optional<Customer> findById(Long id) {
        return repository.findById(id);
    }

    @Transactional
    public void delete(Long id) {
        repository.deleteById(id);
    }
}
```

`@Transactional` ở các phương thức ghi thể hiện ranh giới transaction cho thao tác nghiệp vụ. Với một lệnh CRUD đơn giản, repository cũng có cơ chế transaction theo cấu hình Spring Data; đặt transaction ở service hữu ích khi một nghiệp vụ cần phối hợp nhiều thao tác trong cùng một transaction.

## 3. Đọc toàn bộ, sắp xếp và phân trang khác nhau thế nào?

Ba cách gọi thường gặp:

```java
// 1. Đọc toàn bộ dữ liệu, không chỉ định thứ tự.
Iterable<Customer> all = repository.findAll();

// 2. Đọc toàn bộ dữ liệu theo thứ tự.
Iterable<Customer> sorted = repository.findAll(
        Sort.by(Sort.Direction.ASC, "fullName"));

// 3. Đọc một trang, có thứ tự.
Page<Customer> page = repository.findAll(
        PageRequest.of(0, 20, Sort.by("createdAt").descending()));
```

| API | Phạm vi dữ liệu | Kiểu kết quả |
| --- | --- | --- |
| `CrudRepository.findAll()` | Tất cả hàng phù hợp | `Iterable<T>` |
| `PagingAndSortingRepository.findAll(Sort)` | Tất cả hàng, được sắp xếp | `Iterable<T>` |
| `PagingAndSortingRepository.findAll(Pageable)` | Một trang theo số trang/kích thước/sắp xếp | `Page<T>` |

`findAll(Sort)` chỉ thay đổi thứ tự, không giới hạn số hàng. Nếu bảng có hàng triệu bản ghi, gọi phương thức này vẫn có thể tải một tập kết quả rất lớn. Khi cần giới hạn số hàng trả về, dùng `Pageable`.

## 4. Pageable và PageRequest

`Pageable` mô tả yêu cầu phân trang: số trang, kích thước trang và thứ tự sắp xếp. `PageRequest` là một implementation thường dùng để tạo yêu cầu này.

Ví dụ:

```java
import org.springframework.data.domain.PageRequest;
import org.springframework.data.domain.Pageable;
import org.springframework.data.domain.Sort;

Pageable pageable = PageRequest.of(0, 20);
Pageable secondPage = PageRequest.of(1, 20);

Pageable newestFirst = PageRequest.of(
        0,
        20,
        Sort.by(Sort.Direction.DESC, "createdAt")
);
```

Quy tắc quan trọng:

- **Số trang bắt đầu từ 0.** `PageRequest.of(0, 20)` là trang đầu, `PageRequest.of(1, 20)` là trang thứ hai.
- Kích thước trang phải lớn hơn 0.
- Offset được tính từ số trang và kích thước: `offset = pageNumber × pageSize`.
- Có thể đưa `Sort` vào `PageRequest` để một yêu cầu mang cả pagination và sorting.
- Dùng `Pageable.unpaged()` khi thật sự muốn không phân trang; trong endpoint public, không nên để client tùy ý yêu cầu toàn bộ dữ liệu.

### 4.1. Sắp xếp theo nhiều tiêu chí

Có thể kết hợp nhiều `Sort.Order`:

```java
Sort sort = Sort.by(
        Sort.Order.desc("createdAt"),
        Sort.Order.asc("fullName"),
        Sort.Order.asc("id")
);

Pageable pageable = PageRequest.of(0, 20, sort);
Page<Customer> page = repository.findAll(pageable);
```

Ý nghĩa:

1. Khách hàng tạo gần đây được hiển thị trước.
2. Nếu cùng thời điểm, sắp xếp theo tên tăng dần.
3. Nếu vẫn bằng nhau, dùng ID tăng dần để có thứ tự phân định.

Tiêu chí cuối có tính duy nhất (thường là khóa chính) giúp thứ tự ổn định hơn khi nhiều hàng có cùng giá trị sắp xếp. Nếu chỉ sort theo `createdAt` và nhiều bản ghi có cùng timestamp, thứ tự giữa chúng không được bảo đảm.

### 4.2. Sort dùng tên property Java

Trong Spring Data repository, `Sort.by("createdAt")` thường tham chiếu **persistent property** của entity, không phải tên cột SQL vật lý. Với `NamingStrategy` mặc định, `createdAt` có thể được ánh xạ sang cột `created_at`.

```java
// Tên property Java.
Sort.by("createdAt");

// Nếu property Java tên createdAt nhưng cột SQL là created_at,
// không nên mặc định truyền tên cột SQL vào Sort.
Sort.by("created_at");
```

Dòng thứ hai có thể không được mapping nhận diện vì `created_at` không phải property Java. Nếu có `@Column("created_at")`, hãy sort theo property được khai báo trong entity, ví dụ `createdAt`.

Không sắp xếp theo property transient, tên tùy ý hoặc thuộc tính lồng không được hỗ trợ như một persistent path. Với custom query, cần kiểm tra quy tắc alias/column và khả năng áp dụng sort của query đó.

## 5. Nhận Page<T> và đọc metadata

`Page<T>` chứa nội dung của trang hiện tại cùng metadata để điều hướng:

```java
Pageable pageable = PageRequest.of(
        0,
        20,
        Sort.by(Sort.Direction.DESC, "createdAt")
);

Page<Customer> page = repository.findAll(pageable);

List<Customer> content = page.getContent();
int currentPage = page.getNumber();
int pageSize = page.getSize();
long totalElements = page.getTotalElements();
int totalPages = page.getTotalPages();
boolean hasNext = page.hasNext();
boolean hasPrevious = page.hasPrevious();
```

Các giá trị:

| Phương thức | Ý nghĩa |
| --- | --- |
| `getContent()` | Danh sách entity trong trang hiện tại |
| `getNumber()` | Số trang hiện tại, bắt đầu từ 0 |
| `getSize()` | Kích thước trang được yêu cầu |
| `getNumberOfElements()` | Số phần tử thực tế trong trang hiện tại |
| `getTotalElements()` | Tổng số phần tử phù hợp với truy vấn |
| `getTotalPages()` | Tổng số trang dựa trên tổng số phần tử và page size |
| `hasNext()` | Còn trang kế tiếp không |
| `hasPrevious()` | Có trang trước không |
| `isFirst()` / `isLast()` | Trang hiện tại có phải trang đầu/cuối không |

Ví dụ, nếu tổng số khách hàng phù hợp là 47 và kích thước trang là 20:

| Trang (0-based) | Phần tử | Nội dung |
| --- | ---: | --- |
| 0 | 20 | Phần tử 1–20 |
| 1 | 20 | Phần tử 21–40 |
| 2 | 7 | Phần tử 41–47 |

`getTotalPages()` trả `3`. Trang cuối có `getNumberOfElements()` bằng `7` dù `getSize()` vẫn bằng `20`.

### 5.1. Vì sao Page có thể tốn thêm một truy vấn?

Để tạo metadata chính xác cho `Page<T>`, Spring Data thường cần biết tổng số hàng phù hợp. Bên cạnh câu query lấy dữ liệu của trang, framework có thể thực hiện thêm **count query**. Với bảng lớn hoặc điều kiện lọc phức tạp, phép đếm có thể đáng kể về chi phí.

Nếu giao diện chỉ cần biết "còn dữ liệu để tải tiếp hay không", không nhất thiết phải hiển thị tổng số trang. Với query method hỗ trợ, cân nhắc kiểu trả về `Slice<T>` hoặc danh sách có `Pageable` để giảm nhu cầu tính tổng. Khả năng cụ thể phụ thuộc loại query và phiên bản Spring Data JDBC; kiểm tra API được hỗ trợ trong phiên bản dự án.

## 6. Kết hợp CRUD với query method có Pageable

Repository không chỉ phân trang `findAll()`. Có thể khai báo query method theo tên:

```java
import org.springframework.data.domain.Page;
import org.springframework.data.domain.Pageable;

public interface CustomerRepository
        extends CrudRepository<Customer, Long>,
                PagingAndSortingRepository<Customer, Long> {

    Page<Customer> findByStatus(String status, Pageable pageable);
}
```

Gọi:

```java
Pageable pageable = PageRequest.of(
        0,
        10,
        Sort.by(Sort.Direction.ASC, "fullName")
);

Page<Customer> activeCustomers =
        repository.findByStatus("ACTIVE", pageable);
```

Spring Data phân tích tên method `findByStatus` để tạo điều kiện lọc theo property `status`; `Pageable` cung cấp giới hạn, offset và sort. Không cần tự nối chuỗi `LIMIT`/`OFFSET` trong query method.

Có thể khai báo query method chỉ nhận `Sort` khi cần lấy tất cả kết quả theo thứ tự:

```java
Iterable<Customer> findByStatus(String status, Sort sort);
```

`Pageable` đã bao gồm thông tin sort. Thông thường chỉ truyền một `Pageable` thay vì đồng thời truyền cả `Pageable` và một `Sort` riêng cho cùng mục đích.

### 6.1. Tham số lọc và tham số phân trang

Ví dụ một method có nhiều tham số:

```java
Page<Customer> findByStatusAndFullNameContainingIgnoreCase(
        String status,
        String keyword,
        Pageable pageable
);
```

`status` và `keyword` là điều kiện nghiệp vụ; `pageable` là thông tin điều khiển truy vấn. Trong các query method Spring Data, tham số `Pageable`/`Sort` được nhận diện đặc biệt và không trở thành điều kiện bind thông thường. Đặt `Pageable` ở cuối chữ ký method giúp API dễ đọc và tránh nhầm lẫn.

## 7. Dùng repository trong service và REST API

Service nên nhận yêu cầu phân trang và trả về kết quả phù hợp:

```java
import org.springframework.data.domain.Page;
import org.springframework.data.domain.Pageable;
import org.springframework.stereotype.Service;

@Service
public class CustomerQueryService {

    private final CustomerRepository repository;

    public CustomerQueryService(CustomerRepository repository) {
        this.repository = repository;
    }

    public Page<Customer> findByStatus(
            String status,
            Pageable pageable) {
        return repository.findByStatus(status, pageable);
    }
}
```

Một controller Spring MVC có thể nhận `Pageable` trực tiếp khi ứng dụng đã có Spring Data web support:

```java
import org.springframework.data.domain.Page;
import org.springframework.data.domain.Pageable;
import org.springframework.data.web.PageableDefault;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;

@RestController
class CustomerController {

    private final CustomerQueryService service;

    CustomerController(CustomerQueryService service) {
        this.service = service;
    }

    @GetMapping("/customers")
    Page<Customer> list(
            @RequestParam(defaultValue = "ACTIVE") String status,
            @PageableDefault(size = 20, sort = "createdAt")
            Pageable pageable) {
        return service.findByStatus(status, pageable);
    }
}
```

Ví dụ request:

```http
GET /customers?status=ACTIVE&page=0&size=20&sort=createdAt,desc
```

Các tham số phổ biến:

- `page`: số trang, mặc định 0.
- `size`: số phần tử mỗi trang.
- `sort`: property và hướng sắp xếp; có thể lặp tham số để tạo nhiều tiêu chí, ví dụ `sort=createdAt,desc&sort=id,asc`.

`@PageableDefault` cung cấp giá trị mặc định cho endpoint, không thay thế việc kiểm soát đầu vào. Với API public, nên giới hạn page size tối đa và chỉ cho phép sort theo các property hợp lệ. Tránh để người dùng yêu cầu `size=1000000` hoặc truyền tên cột tùy ý.

Không nhất thiết trả trực tiếp entity cho client trong mọi ứng dụng. Có thể ánh xạ `Page<Customer>` thành DTO và giữ lại metadata phân trang:

```java
public record CustomerItem(
        Long id,
        String fullName,
        String email
) {}

Page<CustomerItem> response = page.map(customer ->
        new CustomerItem(
                customer.id(),
                customer.fullName(),
                customer.email()
        )
);
```

`Page.map` biến đổi nội dung mà vẫn giữ metadata của trang.

## 8. Sort động an toàn và ổn định

Sort thường được nhận từ query parameter. Không chuyển nguyên chuỗi do client gửi thành SQL. Thay vào đó, whitelist các property được phép:

```java
Sort.Direction direction = "desc".equalsIgnoreCase(requestDirection)
        ? Sort.Direction.DESC
        : Sort.Direction.ASC;

String property = switch (sortKey) {
    case "name" -> "fullName";
    case "created" -> "createdAt";
    case "email" -> "email";
    default -> throw new IllegalArgumentException("Unsupported sort key");
};

Sort sort = Sort.by(direction, property)
        .and(Sort.by(Sort.Order.asc("id")));

Pageable pageable = PageRequest.of(pageNumber, pageSize, sort);
```

Trong ví dụ, key bên ngoài `name` được ánh xạ sang property Java `fullName`. Thêm `id` làm tiêu chí phụ để thứ tự ổn định khi các giá trị chính bằng nhau.

Các nguyên tắc:

- Chỉ chấp nhận property đã biết và persistent.
- Hướng sort chỉ nhận `ASC` hoặc `DESC`.
- Giới hạn page number và page size theo khả năng ứng dụng.
- Thêm một khóa phân định duy nhất nếu thứ tự chính có thể trùng.
- Không dùng tên cột từ input để nối trực tiếp vào SQL.

Spring Data tạo SQL từ mapping metadata và dialect, nhưng whitelist vẫn cần thiết để kiểm soát API, tránh property không tồn tại và tránh cho client truy vấn theo trường không được phép.

## 9. Giới hạn và tác động hiệu năng của offset pagination

Phân trang thông thường dùng page number/size, tương ứng với offset và limit trong SQL. Với trang đầu:

```sql
SELECT id, full_name, email, status, created_at
FROM customer
ORDER BY created_at DESC, id ASC
LIMIT 20 OFFSET 0;
```

Trang tiếp theo:

```sql
SELECT id, full_name, email, status, created_at
FROM customer
ORDER BY created_at DESC, id ASC
LIMIT 20 OFFSET 20;
```

Đây là SQL minh họa cho PostgreSQL; Spring Data JDBC render cú pháp phân trang theo dialect. Khi offset lớn, database có thể phải duyệt/bỏ qua nhiều hàng trước khi trả kết quả. Vì vậy, page number rất lớn có thể chậm dù page size nhỏ.

Ngoài hiệu năng, dữ liệu có thể thay đổi giữa hai lần request:

1. Client đọc trang 0.
2. Một bản ghi mới được chèn lên đầu thứ tự.
3. Client đọc trang 1 bằng offset cũ.
4. Một số bản ghi có thể bị lặp hoặc bị bỏ qua do vị trí hàng đã dịch chuyển.

Thêm sort ổn định giúp xử lý các hàng có giá trị sort bằng nhau, nhưng **không tạo snapshot nhất quán xuyên nhiều HTTP request**. Nếu cần duyệt dữ liệu lớn, liên tục thay đổi hoặc theo thứ tự khóa, cân nhắc keyset/scrolling pagination được phiên bản và loại repository hỗ trợ, hoặc thiết kế cursor dựa trên giá trị sắp xếp cùng khóa duy nhất. Không tự coi `PageRequest` là cursor pagination.

## 10. Một số lỗi thường gặp

| Hiện tượng | Nguyên nhân có thể | Hướng xử lý |
| --- | --- | --- |
| Không gọi được `save` sau khi chỉ kế thừa `PagingAndSortingRepository` | Spring Data 3.x không còn để P&S kế thừa CRUD | Kế thừa thêm `CrudRepository` hoặc dùng hierarchy repository phù hợp |
| Không tìm thấy `findAll(Pageable)` | Repository chưa kế thừa P&S hoặc thiếu import đúng package | Kiểm tra `org.springframework.data.repository.PagingAndSortingRepository` |
| Không có kết quả như mong muốn ở trang đầu | Nhầm page index bắt đầu từ 1 | Dùng page 0 cho trang đầu |
| Trang cuối có ít phần tử hơn page size | Đây là hành vi bình thường khi tổng số hàng không chia hết page size | Dùng `getNumberOfElements()` để biết số phần tử thực tế |
| Thứ tự giữa các request thay đổi | Sort không có tiêu chí duy nhất hoặc dữ liệu được cập nhật | Thêm khóa chính làm tie-breaker; cân nhắc cursor nếu cần |
| Sort báo property không tồn tại | Truyền tên cột SQL thay vì property Java hoặc property không persistent | Đối chiếu entity, `@Column` và mapping metadata |
| Query trả chậm dù page size nhỏ | Offset quá lớn, thiếu index hoặc count query tốn kém | Xem execution plan, index, count và chiến lược pagination |
| Tổng số trang không như mong đợi | Điều kiện lọc/count hoặc dữ liệu thay đổi giữa các truy vấn | Kiểm tra điều kiện query và thời điểm dữ liệu được đọc |
| Client có thể yêu cầu trang rất lớn | Endpoint chưa giới hạn `size` | Đặt page size mặc định/tối đa và validate request |

## 11. Quy trình chọn API phù hợp

| Nhu cầu | API nên cân nhắc |
| --- | --- |
| Lưu một aggregate | `CrudRepository.save` |
| Tìm một aggregate theo ID | `CrudRepository.findById` |
| Xóa theo ID | `CrudRepository.deleteById` |
| Lấy tập nhỏ, có giới hạn rõ ràng và không cần metadata trang | Query có giới hạn hoặc cơ chế lấy danh sách phù hợp |
| Lấy tất cả hàng theo một thứ tự | `PagingAndSortingRepository.findAll(Sort)` |
| Lấy một trang và cần tổng số phần tử/trang | `PagingAndSortingRepository.findAll(Pageable)` |
| Lọc theo điều kiện và phân trang | Derived query method có `Pageable` |
| Duyệt lượng dữ liệu rất lớn | Xem xét scrolling/keyset/cursor phù hợp thay vì offset rất lớn |

Không dùng `findAll()` rồi mới cắt danh sách bằng `subList` để giả lập phân trang. Cách đó đã tải toàn bộ kết quả vào bộ nhớ và không tận dụng giới hạn ở database.

## 12. Bài tập thực hành

**Bài 1 — Kết hợp interface.** Tạo `CustomerRepository` kế thừa cả `CrudRepository<Customer, Long>` và `PagingAndSortingRepository<Customer, Long>`. Gọi `save`, `findById`, `deleteById` và `findAll(Pageable)` để quan sát hai nhóm API cùng hoạt động.

**Bài 2 — Sắp xếp.** Lấy 20 khách hàng đầu tiên theo `createdAt` giảm dần, sau đó thêm `fullName` tăng dần và `id` tăng dần làm tiêu chí phụ. Thử tạo nhiều hàng có cùng timestamp.

**Bài 3 — Phân trang query method.** Thêm `findByStatus(String status, Pageable pageable)`. Tạo đủ dữ liệu cho ít nhất ba trang, đọc trang 0, 1, 2 và so sánh `getTotalElements()`, `getTotalPages()`, `getNumberOfElements()`.

**Bài 4 — REST API.** Tạo endpoint nhận `page`, `size` và `sort`. Đặt page size mặc định 20, giới hạn tối đa 100 và whitelist các property được phép sort.

**Bài 5 — Đánh giá count và offset.** Quan sát SQL/plan của một truy vấn `Page`; so sánh chi phí khi đọc trang đầu với trang có offset lớn. Xác định trường hợp giao diện thực sự cần tổng số trang.
