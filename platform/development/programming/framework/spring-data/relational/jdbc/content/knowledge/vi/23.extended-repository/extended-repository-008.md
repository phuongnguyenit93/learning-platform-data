# Giữ đồng bộ quy tắc mapping và giao dịch giữa mã sinh tự động và SQL tự viết

Trong **Spring Data JDBC**, repository và **JdbcAggregateTemplate** có thể sinh SQL từ metadata của aggregate. Khi cần thao tác đặc biệt, ứng dụng cũng có thể viết SQL trực tiếp qua **@Query**, **JdbcTemplate** hoặc **NamedParameterJdbcTemplate**. Hai cách tiếp cận có thể cùng tồn tại trong một ứng dụng, nhưng phải dùng chung một hợp đồng dữ liệu: tên bảng/cột, kiểu dữ liệu, ID, version, quan hệ aggregate và ranh giới transaction.

Điểm quan trọng là **SQL tự viết không tự động kế thừa mọi hành vi của đường lưu aggregate**. Một câu lệnh JDBC trực tiếp chỉ thực hiện những gì SQL mô tả. Nó không tự áp dụng mapping metadata, custom converter, entity callback, auditing, optimistic locking hoặc đồng bộ collection con giống thao tác **repository.save(...)**. Người viết phải xác định phần nào Spring Data đang quản lý và phần nào cần thực hiện tường minh.

Bài này trình bày cách phối hợp hai đường truy cập dữ liệu sao cho dữ liệu nhất quán, transaction có thể rollback cùng nhau và các quy tắc mapping không bị lệch.

## 1. Hai đường thực thi SQL trong cùng ứng dụng

Spring Data JDBC thường có hai nhóm thao tác:

1. **SQL do Spring Data sinh**: repository CRUD hoặc **JdbcAggregateTemplate** sử dụng metadata của entity/aggregate để tạo câu lệnh. Framework biết **@Table**, **@Column**, **@Id**, **@Version**, embedded object và các collection được ánh xạ.
2. **SQL do ứng dụng viết**: **@Query**, repository fragment dùng **JdbcTemplate**, hoặc code JDBC khác thực thi câu lệnh do lập trình viên định nghĩa. Đường này phù hợp với truy vấn/bulk update đặc biệt, ghi audit, báo cáo hoặc tích hợp bảng legacy.

~~~mermaid
flowchart TD
    A[Application Service] --> B[Spring Data Repository / JdbcAggregateTemplate]
    A --> C[Custom Repository Fragment / JdbcTemplate]
    B --> D[Mapping metadata + generated SQL]
    C --> E[SQL do ứng dụng viết]
    D --> F[Spring-managed DataSource / transaction]
    E --> F
    F --> G[(Database)]
~~~

Hai đường có thể cùng tham gia một transaction nếu chúng sử dụng **cùng DataSource và transaction manager được Spring quản lý**. Tuy nhiên, chúng không có cùng mức độ tự động hóa:

| Khả năng | Repository / Aggregate Template | SQL qua JdbcTemplate |
|---|---|---|
| Dùng metadata entity | Có | Không tự động |
| Sinh tên bảng/cột | Có theo mapping | Lập trình viên ghi identifier vật lý |
| Chuyển đổi kiểu theo Spring Data mapping | Có | Thường phải bind/map kiểu JDBC tường minh |
| Lưu aggregate và child theo mapping | Có | Chỉ làm đúng phần SQL đã viết |
| Generated ID khi insert aggregate | Có cơ chế hỗ trợ | Cần tự lấy generated key nếu cần |
| Optimistic locking qua @Version | Có trên đường lưu aggregate chuẩn | Phải viết điều kiện và tăng version |
| Entity callbacks/auditing | Được tích hợp trong đường Spring Data phù hợp | Không tự chạy chỉ vì dùng cùng DataSource |
| Transaction | Tham gia transaction Spring | Tham gia nếu dùng cùng DataSource/transaction manager |

Không nên coi hai cách là hai implementation tương đương. Chúng là hai tầng trừu tượng khác nhau trên cùng database.

## 2. Metadata mapping là hợp đồng chung với schema

Ví dụ aggregate root:

~~~java
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("customers")
public record Customer(
        @Id Long id,
        @Version Long version,
        @Column("display_name") String name,
        String email,
        boolean active
) {}
~~~

DDL tương ứng:

~~~sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    version BIGINT NOT NULL,
    display_name VARCHAR(120) NOT NULL,
    email VARCHAR(200) NOT NULL UNIQUE,
    active BOOLEAN NOT NULL
);
~~~

Metadata xác định:

- **@Table("customers")** ánh xạ aggregate root tới bảng **customers**.
- **@Id** xác định khóa chính **id**.
- **@Version** đánh dấu cột version dùng cho optimistic locking.
- **@Column("display_name")** ánh xạ property Java **name** sang cột vật lý **display_name**.
- **email** và **active** dùng tên cột theo naming strategy mặc định trong ví dụ.

Repository có thể dùng CRUD được sinh tự động:

~~~java
import org.springframework.data.repository.CrudRepository;

public interface CustomerRepository
        extends CrudRepository<Customer, Long> {
}
~~~

Khi Spring Data tạo SQL, nó dựa trên metadata để biết cột nào cần đọc/ghi. Khi viết SQL thủ công, phải dùng **tên bảng và tên cột thực tế trong database**, không dùng tên property Java nếu chúng khác nhau.

Ví dụ SQL trực tiếp phải dùng **display_name**:

~~~sql
UPDATE customers
SET display_name = ?
WHERE id = ?;
~~~

Không nên viết **SET name = ?** chỉ vì property trong record tên **name**. **@Column** không tự sửa câu SQL mà lập trình viên đã viết.

## 3. Đường lưu tự động giữ những quy tắc nào?

Với thao tác:

~~~java
Customer current = customers.findById(id).orElseThrow();

Customer changed = new Customer(
        current.id(),
        current.version(),
        "Tên mới",
        current.email(),
        current.active()
);

Customer saved = customers.save(changed);
~~~

Spring Data JDBC sử dụng mapping metadata để tạo câu **UPDATE** phù hợp. Với entity có **@Version**, câu lệnh có điều kiện version cũ và cập nhật version mới. Về mặt ý nghĩa, SQL tương đương:

~~~sql
UPDATE customers
SET display_name = ?,
    email = ?,
    active = ?,
    version = ?
WHERE id = ?
  AND version = ?;
~~~

Chi tiết thứ tự cột và cú pháp phụ thuộc dialect, nhưng framework quản lý việc ánh xạ property, bind giá trị và optimistic locking cho đường lưu aggregate chuẩn.

Ngoài ra, tùy cấu hình ứng dụng, đường Spring Data có thể tích hợp:

- Custom conversions đã đăng ký với Spring Data Relational.
- Entity callbacks và lifecycle events.
- Auditing như **@CreatedDate**, **@LastModifiedDate**, **@CreatedBy**, **@LastModifiedBy**.
- Mapping embedded property và collection thuộc aggregate.
- Cơ chế lấy generated key cho ID được database cấp.

Khi chuyển một thao tác từ **repository.save(...)** sang SQL trực tiếp, cần xác định những hành vi nào trong danh sách trên vẫn cần thiết và tự đảm bảo chúng.

## 4. SQL tự viết dùng tên vật lý và bind parameter

Giả sử cần ghi lịch sử thay đổi khách hàng vào bảng audit:

~~~sql
CREATE TABLE customer_audit (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    event_type VARCHAR(40) NOT NULL,
    customer_version BIGINT NOT NULL,
    created_at TIMESTAMP NOT NULL,
    CONSTRAINT fk_customer_audit_customer
        FOREIGN KEY (customer_id) REFERENCES customers(id)
);
~~~

Đây là bảng audit riêng, không phải property của aggregate **Customer**. Một custom repository fragment có thể dùng **NamedParameterJdbcTemplate**:

~~~java
public interface CustomerAuditOperations {
    int insertAudit(Long customerId, String eventType, Long version);
}
~~~

Implementation:

~~~java
import org.springframework.jdbc.core.namedparam.MapSqlParameterSource;
import org.springframework.jdbc.core.namedparam.NamedParameterJdbcTemplate;

public class CustomerAuditOperationsImpl
        implements CustomerAuditOperations {

    private final NamedParameterJdbcTemplate jdbc;

    public CustomerAuditOperationsImpl(NamedParameterJdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    @Override
    public int insertAudit(
            Long customerId,
            String eventType,
            Long version
    ) {
        String sql = """
            INSERT INTO customer_audit (
                customer_id,
                event_type,
                customer_version,
                created_at
            )
            VALUES (
                :customerId,
                :eventType,
                :version,
                CURRENT_TIMESTAMP
            )
            """;

        var parameters = new MapSqlParameterSource()
                .addValue("customerId", customerId)
                .addValue("eventType", eventType)
                .addValue("version", version);

        return jdbc.update(sql, parameters);
    }
}
~~~

Repository kết hợp CRUD và fragment:

~~~java
public interface CustomerRepository
        extends CrudRepository<Customer, Long>,
                CustomerAuditOperations,
                CustomerSqlOperations {
}
~~~

Với custom fragment, implementation thường được đặt theo quy ước tên fragment cộng hậu tố **Impl**, ở đây là **CustomerAuditOperationsImpl**. Spring Data ghép implementation fragment vào repository proxy.

Các giá trị đầu vào được bind bằng named parameter. Điều này giúp driver xử lý kiểu JDBC và tránh nối trực tiếp dữ liệu người dùng vào chuỗi SQL. Tên bảng/cột vẫn là identifier do lập trình viên quản lý.

## 5. Giữ các thao tác trong cùng transaction

Một use case có thể vừa cập nhật aggregate bằng repository, vừa ghi audit bằng SQL thủ công. Nếu hai thao tác phải thành công hoặc thất bại cùng nhau, đặt transaction ở application service:

~~~java
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class CustomerService {
    private final CustomerRepository customers;

    public CustomerService(CustomerRepository customers) {
        this.customers = customers;
    }

    @Transactional
    public Customer rename(Long id, String newName) {
        Customer current = customers.findById(id)
                .orElseThrow(() -> new IllegalArgumentException("Customer not found"));

        Customer changed = new Customer(
                current.id(),
                current.version(),
                newName,
                current.email(),
                current.active()
        );

        Customer saved = customers.save(changed);

        int auditRows = customers.insertAudit(
                saved.id(),
                "RENAMED",
                saved.version()
        );

        if (auditRows != 1) {
            throw new IllegalStateException(
                    "Expected one audit row, got " + auditRows);
        }

        return saved;
    }
}
~~~

Trong cấu hình Spring thông thường, repository JDBC và **NamedParameterJdbcTemplate** cùng dùng DataSource đã được Spring quản lý. Khi cả hai tham gia cùng transaction manager, lệnh **UPDATE** của repository và lệnh **INSERT** audit tham gia cùng transaction.

Kết quả:

- Nếu cập nhật khách hàng và ghi audit đều thành công, transaction commit cả hai.
- Nếu ghi audit thất bại và exception làm transaction rollback, thay đổi khách hàng cũng được rollback.
- Nếu use case ném lỗi sau cả hai câu lệnh nhưng trước commit, cả hai thay đổi vẫn rollback theo transaction.

Không gọi **Connection.commit()** hoặc tự mở một connection độc lập trong fragment. Việc đó có thể tách SQL thủ công khỏi transaction mà Spring đang quản lý.

### Điều kiện để hai đường cùng transaction

Cần bảo đảm:

1. Repository và **JdbcTemplate/NamedParameterJdbcTemplate** dùng cùng DataSource.
2. Các thao tác được điều phối bởi cùng transaction manager phù hợp với DataSource đó.
3. Service method chạy trong transaction Spring được kích hoạt bởi **@Transactional**.
4. Code JDBC dùng Spring template, không tự mở connection riêng rồi commit độc lập.
5. Không chuyển thao tác sang thread khác và kỳ vọng transaction thread-bound tự truyền sang thread mới.

Nếu ứng dụng có nhiều DataSource, mỗi nguồn có thể có transaction manager riêng. Hai thao tác trên hai DataSource khác nhau không tự trở thành một transaction nguyên tử chỉ vì cùng nằm trong một method có **@Transactional**. Khi cần nhất quán xuyên nhiều hệ thống/database, phải thiết kế distributed transaction hoặc transactional outbox/saga tùy yêu cầu.

## 6. Cập nhật trực tiếp một aggregate phải tự giữ optimistic locking

Đôi khi SQL tự viết cần cập nhật một cột của chính aggregate root. Nếu root dùng **@Version**, SQL trực tiếp phải tự thực hiện quy tắc version.

Ví dụ thêm method vào custom fragment:

~~~java
public interface CustomerSqlOperations {
    int updateEmailIfVersionMatches(
            Long id,
            Long expectedVersion,
            String newEmail
    );
}
~~~

Implementation:

~~~java
@Override
public int updateEmailIfVersionMatches(
        Long id,
        Long expectedVersion,
        String newEmail
) {
    String sql = """
        UPDATE customers
        SET email = :email,
            version = version + 1
        WHERE id = :id
          AND version = :expectedVersion
        """;

    var parameters = new MapSqlParameterSource()
            .addValue("id", id)
            .addValue("expectedVersion", expectedVersion)
            .addValue("email", newEmail);

    return jdbc.update(sql, parameters);
}
~~~

Câu SQL này tự thực hiện ba việc:

1. Tìm đúng root theo **id**.
2. Chỉ cập nhật nếu version trong database vẫn bằng **expectedVersion**.
3. Tăng version khi cập nhật thành công.

Service diễn giải update count:

~~~java
import org.springframework.dao.OptimisticLockingFailureException;
import org.springframework.transaction.annotation.Transactional;

@Transactional
public Customer changeEmailWithSql(
        Long id,
        Long expectedVersion,
        String newEmail
) {
    int affected = customers.updateEmailIfVersionMatches(
            id,
            expectedVersion,
            newEmail
    );

    if (affected == 0) {
        throw new OptimisticLockingFailureException(
                "Customer no longer has the expected version");
    }

    if (affected != 1) {
        throw new IllegalStateException(
                "Expected one updated customer, got " + affected);
    }

    return customers.findById(id).orElseThrow();
}
~~~

Sau câu lệnh SQL, đọc lại aggregate để nhận giá trị email và version mới từ database. SQL trực tiếp không tự cập nhật một object **Customer** đang nằm trong bộ nhớ.

Nếu không đưa version vào điều kiện và không tăng version, một request cũ có thể ghi đè thay đổi mới mà không bị optimistic locking phát hiện. Không nên cho rằng chỉ cần entity có **@Version** là mọi câu **UPDATE** tự viết sẽ được Spring Data JDBC sửa lại.

### Khi nào nên dùng save thay cho direct update?

Nếu thao tác chỉ thay đổi trạng thái thông thường của aggregate và không có lý do SQL đặc biệt, đường an toàn hơn thường là:

1. Đọc root.
2. Gọi hành vi domain để tạo trạng thái mới.
3. Gọi **repository.save(...)**.
4. Dùng object trả về để nhận version mới.

Dùng direct update khi có lý do cụ thể như bulk operation, biểu thức SQL đặc thù hoặc tối ưu đã được đo lường, và khi đã xác định rõ cách giữ version, auditing và các tác động phụ.

## 7. Mapping thủ công phải khớp converter và kiểu dữ liệu

Spring Data JDBC có thể dùng custom converter để chuyển kiểu domain sang kiểu lưu trữ. Khi dùng **JdbcTemplate**, không nên mặc định converter của Spring Data tự chạy cho mọi tham số và **ResultSet** mà JdbcTemplate xử lý.

Ví dụ entity có enum:

~~~java
enum CustomerStatus {
    ACTIVE, SUSPENDED
}
~~~

Nếu mapping Spring Data lưu enum bằng tên, SQL trực tiếp cần truyền giá trị tương ứng:

~~~java
parameters.addValue("status", CustomerStatus.ACTIVE.name());
~~~

Nếu ứng dụng dùng converter lưu mã **A/S**, SQL thủ công cũng phải dùng đúng mã đó hoặc gọi một mapper/conversion component chung. Nếu không, đường repository có thể đọc **ACTIVE** đúng trong khi đường SQL tự viết lưu **A** hoặc ngược lại.

Các điểm phải thống nhất:

| Dữ liệu | Mapping Spring Data | SQL tự viết cần chú ý |
|---|---|---|
| Enum | Custom converter hoặc cách lưu mặc định | Bind đúng giá trị vật lý được schema lưu |
| BigDecimal | Converter/JDBC type phù hợp | Giữ precision/scale, tránh chuyển qua double |
| Ngày giờ | Converter và kiểu temporal | Dùng đúng DATE, TIMESTAMP, timezone semantics |
| UUID | Converter/driver/database type | Dùng đúng kiểu vật lý và cách bind |
| Value object | Converter hoặc embedded mapping | Chuyển đổi thủ công nếu SQL truy cập cột của value object |
| Nullable property | Mapping về wrapper/reference | Không bind primitive/default thay cho NULL ngoài ý muốn |

Khi SQL thủ công cần đọc dữ liệu về object, **RowMapper** phải tự chuyển đổi giá trị theo cùng quy tắc domain. Không nên có hai cách diễn giải khác nhau cho cùng một cột ở hai đường code.

## 8. Embedded object và prefix cột

Một object **@Embedded** được trải thành các cột trong bảng của root. Ví dụ:

~~~java
public record Address(String street, String city) {}

@Table("customers")
public record Customer(
        @Id Long id,
        @Embedded(prefix = "shipping_") Address shippingAddress
) {}
~~~

DDL:

~~~sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    shipping_street VARCHAR(180),
    shipping_city VARCHAR(100)
);
~~~

Repository/aggregate template hiểu metadata embedded và ánh xạ object **Address** qua các cột **shipping_street**, **shipping_city**.

SQL tự viết phải dùng các tên vật lý đó:

~~~sql
UPDATE customers
SET shipping_street = :street,
    shipping_city = :city
WHERE id = :id;
~~~

Không dùng **shippingAddress** như một cột JSON giả định, cũng không dùng **street** nếu DDL không có cột đó. Nếu embedded object có quy tắc **USE_NULL/USE_EMPTY**, SQL thủ công cũng cần giữ đúng ý nghĩa của nhóm cột khi tất cả đều null; bản thân câu **UPDATE** không tự áp dụng chính sách dựng object của Spring Data.

## 9. Collection child và ranh giới aggregate

Spring Data JDBC quản lý aggregate theo root. Với **@MappedCollection**, metadata mô tả bảng child, cột ID tham chiếu root và có thể có cột key/index. Khi lưu root qua repository, framework biết cách đồng bộ collection theo mapping.

Ví dụ:

~~~java
@Table("purchase_orders")
public record PurchaseOrder(
        @Id Long id,
        @MappedCollection(idColumn = "order_id", keyColumn = "line_no")
        List<OrderLine> lines
) {}

@Table("order_lines")
public record OrderLine(String sku, int quantity) {}
~~~

SQL trực tiếp cập nhật một hàng **order_lines** chỉ tác động hàng được chỉ định. Nó không tự đồng bộ collection theo cách **repository.save(order)** thực hiện. Một lần save aggregate có thể thay thế các hàng child theo trạng thái collection hiện tại, vì vậy thao tác direct SQL và lần save kế tiếp có thể ghi đè hoặc loại bỏ thay đổi nếu hai đường không cùng hiểu một trạng thái.

Trước khi viết SQL trực tiếp lên bảng child, cần trả lời:

- Child có thực sự thuộc vòng đời của aggregate root không?
- **order_id** và **line_no** có được giữ đúng không?
- Có vi phạm invariant giữa các dòng hàng và tổng đơn không?
- Lần **save(root)** tiếp theo có thể thay thế các hàng child vừa sửa không?
- Cần khóa/version root để ngăn cập nhật đồng thời không?

Nếu child thuộc aggregate, ưu tiên thay đổi collection trên root và lưu root. Chỉ cập nhật bảng child trực tiếp khi đường ghi được thiết kế để phối hợp với aggregate, version, transaction và invariant. Nếu child có vòng đời độc lập thực sự, hãy xem xét mô hình hóa nó thành aggregate riêng thay vì lách ranh giới sở hữu.

## 10. Entity callbacks và auditing không tự chạy với SQL JDBC tùy ý

Spring Data JDBC có thể tích hợp entity callbacks và auditing trong các thao tác persistence do Spring Data quản lý. Ví dụ auditing có thể tự điền **createdAt** hoặc **lastModifiedAt** trước khi lưu.

Một câu lệnh:

~~~sql
UPDATE customers
SET display_name = :name
WHERE id = :id;
~~~

thực thi qua **JdbcTemplate** không tự gọi callback của aggregate. Nó cũng không tự cập nhật **last_modified_at** chỉ vì entity có **@LastModifiedDate**.

Nếu direct SQL cần giữ auditing, hãy đưa cột vào câu lệnh:

~~~sql
UPDATE customers
SET display_name = :name,
    last_modified_at = CURRENT_TIMESTAMP
WHERE id = :id;
~~~

Nếu hệ thống dùng auditor như **lastModifiedBy**, SQL cần nhận giá trị actor từ context nghiệp vụ và bind rõ ràng. Cần giữ cùng quy tắc timezone, clock và giá trị mặc định với đường lưu tự động.

Không nên giả định database default, trigger và Spring auditing luôn tạo ra cùng một giá trị. Chọn một nguồn quy tắc rõ ràng hoặc bảo đảm các nguồn phối hợp không ghi đè lẫn nhau.

## 11. Phân biệt @Query với JdbcTemplate

SQL tự viết có thể xuất hiện ở nhiều mức khác nhau:

| Cách viết | Ai quản lý việc thực thi? | Mapping kết quả |
|---|---|---|
| Derived repository method | Spring Data repository | Theo property và metadata |
| @Query trên repository | Spring Data repository infrastructure | Theo kiểu trả về và mapping được hỗ trợ |
| @Modifying @Query | Spring Data repository infrastructure thực thi DML | Thường trả update count hoặc void; không tự trả entity đã cập nhật |
| Custom fragment + JdbcTemplate | Code fragment của ứng dụng | Do RowMapper/ResultSetExtractor hoặc code tự viết |
| JdbcAggregateTemplate | Spring Data JDBC aggregate infrastructure | Theo metadata aggregate |

**@Query** vẫn đi qua repository infrastructure, nhưng câu SQL và identifier do lập trình viên định nghĩa. Không được nhầm rằng chỉ vì method nằm trong repository nên mọi quy tắc của **save** sẽ tự động áp dụng cho một câu **UPDATE** tùy chỉnh.

**JdbcTemplate** là mức thấp hơn: ứng dụng trực tiếp kiểm soát SQL, tham số, RowMapper và số hàng bị ảnh hưởng. Đổi lại, ứng dụng tự chịu trách nhiệm nhiều hơn về mapping và lifecycle.

## 12. @Modifying và update count

Một modifying query có thể trả số hàng bị tác động:

~~~java
@Modifying
@Query("""
    UPDATE customers
    SET active = FALSE
    WHERE id = :id
    """)
int deactivate(@Param("id") Long id);
~~~

Update count có thể là:

- **1**: một hàng được báo là đã tác động.
- **0**: không hàng nào được báo là tác động; có thể ID không tồn tại, điều kiện không khớp hoặc version cũ.
- **Lớn hơn 1**: nhiều hàng bị tác động; có thể đúng với bulk query nhưng bất ngờ nếu kỳ vọng một root.

Đối với custom SQL dùng **JdbcTemplate**, **update(...)** cũng trả số hàng bị tác động. Cần diễn giải số đếm theo điều kiện **WHERE** và semantics của database/driver. Không nên mặc định **0** luôn có nghĩa “không tồn tại” nếu câu lệnh có điều kiện trạng thái hoặc version.

## 13. Tránh hai đường ghi cập nhật cùng dữ liệu mà không có quy ước

Một lỗi thiết kế phổ biến là cùng một property có thể được cập nhật bởi:

- **repository.save(entity)**,
- **@Modifying @Query**,
- **JdbcTemplate.update(...)**,
- một job batch hoặc ứng dụng khác.

Nếu mỗi đường dùng quy tắc riêng, dữ liệu có thể mất tính nhất quán. Ví dụ repository tăng **version**, nhưng SQL trực tiếp không tăng; một đường cập nhật **last_modified_at**, đường kia quên; một đường lưu enum theo tên, đường kia lưu mã.

Hãy thiết lập quy ước:

1. Chọn đường ghi chuẩn cho aggregate.
2. Ghi rõ trường hợp nào được phép dùng direct SQL.
3. Nếu direct SQL thay đổi aggregate versioned, luôn kiểm tra và tăng version.
4. Đồng bộ cột auditing và converter.
5. Không cập nhật child ngoài root nếu nó thuộc vòng đời aggregate.
6. Đưa các thao tác phối hợp vào cùng transaction.
7. Có integration test chứng minh hai đường ghi không làm sai trạng thái đọc lại.

Nếu direct SQL và **save** cùng sửa một root trong một transaction, phải dùng version/state mới nhất. Không tiếp tục save một object cũ với version cũ sau khi câu SQL trực tiếp đã tăng version; thao tác đó phải bị optimistic locking từ chối nếu version được triển khai đúng.

## 14. Kiểm tra transaction thực sự dùng chung

Một cách kiểm tra thực tế là tạo một use case có hai thao tác:

1. Repository cập nhật một cột của aggregate.
2. Custom fragment insert một hàng audit.

Sau đó chủ động làm bước audit thất bại trong môi trường test. Nếu cả hai dùng chung transaction, thay đổi aggregate cũng phải rollback. Nếu aggregate vẫn thay đổi nhưng audit không có, hai thao tác không nằm trong cùng transaction như mong đợi hoặc rollback không được kích hoạt.

Các nguyên nhân thường gặp:

- Hai template dùng hai DataSource khác nhau.
- Repository và JDBC template gắn với transaction manager khác nhau.
- Một đường code tự mở connection và commit.
- Một thao tác chạy ở thread khác.
- Transaction bị tách bởi propagation như **REQUIRES_NEW**.
- Exception bị bắt và nuốt trước khi transaction manager biết cần rollback.
- Method được gọi nội bộ trong cùng object khiến proxy-based **@Transactional** không được áp dụng theo cách mong muốn.

Không cần tự commit sau từng câu SQL trong một service transaction. Spring transaction manager quản lý connection và commit/rollback khi ranh giới transaction kết thúc.

## 15. Integration test cho tính nhất quán

Có thể viết test tích hợp để chứng minh repository và custom SQL cùng tham gia một transaction. Ví dụ use case đổi tên khách hàng và ghi audit; khi audit thất bại, tên khách hàng phải giữ nguyên.

Mô hình test khái quát:

~~~java
@Test
void rollsBackAggregateUpdateWhenAuditInsertFails() {
    Customer before = customerRepository.save(
            new Customer(null, null, "Lan", "lan@example.com", true)
    );

    assertThrows(RuntimeException.class, () ->
            customerService.renameAndFailAudit(before.id(), "Lan Nguyen")
    );

    Customer after = customerRepository.findById(before.id()).orElseThrow();

    assertEquals("Lan", after.name());
    assertEquals(0, auditRepository.countByCustomerId(before.id()));
}
~~~

Đây là ví dụ về ý tưởng kiểm tra; test thực tế cần cấu hình database, transaction test và cách cố ý gây lỗi audit phù hợp. Tránh chỉ mock repository/JdbcTemplate nếu mục tiêu là xác minh transaction manager và DataSource thật sự phối hợp.

## 16. Các lỗi thường gặp khi trộn generated SQL và SQL tự viết

| Triệu chứng | Nguyên nhân có thể | Cách xử lý |
|---|---|---|
| SQL trực tiếp báo không có cột | Dùng tên property Java thay cho tên cột vật lý | Đối chiếu @Table, @Column, naming strategy và DDL |
| Repository đọc được nhưng RowMapper đọc sai | Hai đường chuyển đổi enum/time/UUID khác nhau | Chuẩn hóa converter hoặc mapping thủ công |
| Version không phát hiện cập nhật đồng thời | Direct SQL bỏ điều kiện version hoặc không tăng version | Thêm WHERE version = :expectedVersion và tăng version |
| Save sau direct update bị optimistic-lock failure | Object đang giữ version cũ | Reload aggregate hoặc dùng version mới sau direct update |
| Audit còn nhưng aggregate rollback hoặc ngược lại | Hai thao tác không cùng transaction | Kiểm tra DataSource, transaction manager và propagation |
| Child bị mất sau lần save root | Direct SQL thay đổi child nhưng collection root đang cũ | Đồng bộ trạng thái aggregate trước khi save |
| lastModifiedAt không đổi | SQL thủ công không gọi auditing callback | Cập nhật cột trong SQL hoặc dùng đường Spring Data |
| ID insert thủ công không được trả về | Dùng JdbcTemplate.update mà không lấy generated key | Dùng KeyHolder/PreparedStatementCreator hoặc repository save |
| Dữ liệu enum không đọc lại được | SQL lưu mã khác với converter | Dùng chung quy tắc chuyển đổi |
| Câu update tác động nhiều hàng ngoài ý muốn | Điều kiện WHERE quá rộng | Dùng khóa/điều kiện chặt và kiểm tra update count |
| Transaction không rollback khi có lỗi | Exception bị nuốt hoặc transaction không bao trùm cả hai đường | Để lỗi truyền ra hoặc cấu hình rollback phù hợp; kiểm tra proxy và transaction manager |

## 17. Quy trình phối hợp hai đường persistence

Khi thêm SQL tự viết vào ứng dụng Spring Data JDBC, thực hiện theo trình tự:

1. **Xác định aggregate root và schema**: biết bảng, ID, version, child table và ràng buộc.
2. **Xác định đường ghi chuẩn**: repository/template hay custom SQL; tránh hai đường ghi trùng nhau không có quy ước.
3. **Đối chiếu metadata**: @Table, @Column, @Id, @Version, embedded prefix, @MappedCollection.
4. **Viết SQL bằng identifier vật lý**: tên bảng/cột phải khớp migration đang triển khai.
5. **Đồng bộ kiểu dữ liệu**: enum, thời gian, UUID, tiền tệ, nullability và custom converter.
6. **Giữ invariant**: cập nhật root/child, version, auditing và ràng buộc theo đúng quy tắc nghiệp vụ.
7. **Chọn transaction boundary**: đặt @Transactional ở application service nếu nhiều thao tác phải nguyên tử.
8. **Kiểm tra update count và generated key**: hiểu rõ SQL thủ công trả thông tin gì.
9. **Reload khi cần trạng thái database mới nhất**: object trong bộ nhớ không tự thay đổi sau direct DML.
10. **Viết integration test**: kiểm tra rollback, mapping và concurrency bằng database/driver tương ứng.

~~~mermaid
flowchart TD
    A[Use case cần thao tác dữ liệu] --> B{Có thể dùng repository/template?}
    B -->|Có| C[Để Spring Data sinh SQL từ metadata]
    B -->|Không hoặc cần SQL đặc biệt| D[Viết @Query hoặc custom JDBC fragment]
    C --> E{Có phối hợp SQL thủ công?}
    D --> E
    E -->|Có| F[Đối chiếu mapping, version, callbacks và child]
    E -->|Không| G[Kiểm tra transaction của đường chuẩn]
    F --> H[Đặt transaction boundary chung]
    G --> I[Thực thi]
    H --> I
    I --> J[Kiểm tra kết quả và trạng thái đọc lại]
~~~

## 18. Nguyên tắc ghi nhớ

- Repository và **JdbcAggregateTemplate** sinh SQL từ mapping metadata; SQL tự viết phải dùng đúng identifier vật lý trong database.
- **@Table**, **@Column**, **@Id**, **@Version**, converter và embedded/collection mapping tạo thành hợp đồng giữa Java và schema.
- **JdbcTemplate** không tự áp dụng toàn bộ Spring Data mapping, entity callbacks, auditing hoặc optimistic locking.
- SQL trực tiếp cập nhật root versioned phải tự kiểm tra version cũ và tăng version.
- SQL trực tiếp trên bảng child phải tôn trọng aggregate boundary, **idColumn**, key/index và quy tắc đồng bộ collection.
- Dùng cùng DataSource và transaction manager để repository và JDBC template tham gia một transaction Spring.
- Đặt **@Transactional** ở application service khi nhiều thao tác phải commit/rollback cùng nhau.
- Không tự mở connection hoặc commit độc lập trong custom fragment nếu muốn tham gia transaction hiện tại.
- Update count không phải generated ID hoặc entity đã cập nhật; reload nếu cần trạng thái mới nhất.
- Đồng bộ enum, temporal values, UUID, nullability, auditing và converter giữa hai đường ghi.
- Dùng integration test với database thật hoặc Testcontainers để xác nhận transaction và mapping cùng hoạt động.

Trong Spring Data JDBC, có thể kết hợp SQL do framework sinh với SQL tự viết một cách an toàn khi cả hai cùng tuân theo **một hợp đồng mapping, một bộ quy tắc aggregate và một ranh giới transaction rõ ràng**. Hãy để repository/template xử lý đường lưu aggregate thông thường; chỉ dùng SQL trực tiếp cho phần thật sự cần kiểm soát, và tự chịu trách nhiệm về mapping, version, auditing, child data cùng transaction mà đường tự động vốn đã hỗ trợ.
