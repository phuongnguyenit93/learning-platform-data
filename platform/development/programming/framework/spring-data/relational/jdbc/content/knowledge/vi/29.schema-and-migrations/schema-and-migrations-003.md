# Phân biệt SQL initialization với migration có phiên bản

Spring Data JDBC ánh xạ aggregate vào các bảng quan hệ, nhưng không tự suy ra và tạo toàn bộ schema database từ domain model. Ứng dụng vẫn cần một cách quản lý bảng, cột, khóa ngoại, index và constraint trước khi repository hoạt động.

Trong Spring Boot, hai cách phổ biến để chuẩn bị schema là **SQL initialization** bằng các script như `schema.sql`/`data.sql` và **versioned database migration** bằng Flyway hoặc Liquibase. Cả hai đều có thể chạy SQL khi ứng dụng khởi động, nhưng giải quyết hai bài toán khác nhau:

- SQL initialization chủ yếu nạp một tập script khởi tạo theo cấu hình startup.
- Versioned migration quản lý các thay đổi schema theo từng phiên bản, ghi nhận thay đổi nào đã áp dụng và tiếp tục từ trạng thái hiện tại của database.

Hiểu đúng khác biệt giúp tránh chạy lại script tạo bảng trên database đã có dữ liệu, tránh hai công cụ cùng sửa schema và bảo đảm các phiên bản ứng dụng có thể triển khai an toàn.

## 1. Schema database trong Spring Data JDBC

Giả sử domain có aggregate root `Customer`:

```java
@Table("customers")
public record Customer(
    @Id Long id,
    String name,
    String email,
    boolean active
) {}
```

Repository:

```java
public interface CustomerRepository
        extends ListCrudRepository<Customer, Long> {
}
```

Spring Data JDBC sử dụng mapping metadata để tạo SQL đọc và ghi cho aggregate. Tuy nhiên, bảng `customers` phải tồn tại với cột và kiểu tương thích:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(160) NOT NULL,
    email VARCHAR(255) NOT NULL UNIQUE,
    active BOOLEAN NOT NULL
);
```

Spring Data JDBC không tự tạo schema từ entity như một ORM có cơ chế schema generation. Mapping mô tả cách object tương ứng với schema; schema cần được chuẩn bị bằng script, migration hoặc quy trình database provisioning riêng.

Ngoài bảng root, schema có thể cần:

- Bảng con và foreign key cho các collection được ánh xạ bằng `@MappedCollection`.
- Cột version cho optimistic locking khi dùng `@Version`.
- Unique constraint bảo vệ invariant.
- Index cho các truy vấn thường dùng.
- Default, trigger và generated column do database quản lý.
- Bảng phục vụ audit hoặc outbox.

Các đối tượng database này là một phần của hợp đồng persistence. Chúng cần được quản lý cùng với source code ứng dụng.

## 2. SQL initialization là gì?

SQL initialization là cách chạy một hoặc nhiều script SQL khi Spring Boot khởi tạo datasource/application context. Script thường được dùng để:

- Tạo schema ban đầu.
- Tạo bảng và index cho database mới.
- Nạp dữ liệu mẫu hoặc dữ liệu tham chiếu.
- Chuẩn bị database nhúng cho development/test.

Spring Boot hỗ trợ các script mặc định có tên `schema.sql` và `data.sql`. Có thể đặt chúng trên classpath, thường trong `src/main/resources`.

Ví dụ cấu trúc:

```text
src/main/resources/
├── schema.sql
└── data.sql
```

`schema.sql` chứa DDL:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(160) NOT NULL,
    email VARCHAR(255) NOT NULL UNIQUE,
    active BOOLEAN NOT NULL
);
```

`data.sql` chứa dữ liệu khởi tạo:

```sql
INSERT INTO customers (name, email, active)
VALUES
    ('An Nguyen', 'an@example.test', TRUE),
    ('Binh Tran', 'binh@example.test', TRUE);
```

Khi script initialization được bật, Spring Boot chạy schema script trước data script để bảng được tạo trước khi insert dữ liệu.

### 2.1. SQL initialization không phải lịch sử migration

Các script này mô tả trạng thái cần khởi tạo ở thời điểm startup. Spring Boot không tự xem mỗi lần sửa `schema.sql` là một phiên bản migration mới, cũng không tự lưu lịch sử từng thay đổi schema tương ứng.

Ví dụ, sau khi ứng dụng đã chạy lần đầu, developer sửa `schema.sql` để thêm cột:

```sql
ALTER TABLE customers ADD COLUMN phone VARCHAR(30);
```

Nếu script được chạy lại trên database đã có bảng, câu lệnh `CREATE TABLE` ban đầu có thể lỗi vì bảng đã tồn tại. Nếu chỉ thêm câu ALTER vào cuối, lần khởi động tiếp theo có thể lại cố thêm cùng cột và thất bại.

Có thể viết DDL kiểu idempotent như `CREATE TABLE IF NOT EXISTS` hoặc kiểm tra sự tồn tại của đối tượng trước khi tạo. Nhưng điều đó không thay thế được migration có phiên bản: script vẫn không cho biết database đã trải qua thay đổi nào, theo thứ tự nào, và dữ liệu cũ cần được chuyển đổi ra sao.

## 3. Cấu hình SQL initialization trong Spring Boot

Spring Boot cung cấp các thuộc tính dưới prefix `spring.sql.init`.

Ví dụ:

```yaml
spring:
  sql:
    init:
      mode: always
      schema-locations: classpath:/db/init/schema.sql
      data-locations: classpath:/db/init/data.sql
      continue-on-error: false
```

Các thuộc tính thường dùng:

| Property | Ý nghĩa |
| --- | --- |
| `spring.sql.init.mode` | Quyết định có chạy script initialization hay không. |
| `spring.sql.init.schema-locations` | Vị trí script DDL tạo/cập nhật schema. |
| `spring.sql.init.data-locations` | Vị trí script nạp dữ liệu. |
| `spring.sql.init.platform` | Tên platform dùng để chọn script riêng cho database. |
| `spring.sql.init.continue-on-error` | Có tiếp tục khi script gặp lỗi hay dừng startup. |
| `spring.sql.init.encoding` | Encoding của file script. |
| `spring.sql.init.separator` | Ký tự phân tách statement trong script. |

### 3.1. Chọn mode

`spring.sql.init.mode` có các giá trị:

| Giá trị | Hành vi |
| --- | --- |
| `embedded` | Chỉ chạy initialization cho embedded database. Đây là mặc định thông thường. |
| `always` | Chạy script cho cả database không nhúng, ví dụ PostgreSQL/MySQL. |
| `never` | Không chạy script initialization. |

Ví dụ, khi muốn Spring Boot chạy script với PostgreSQL trong môi trường development:

```yaml
spring:
  sql:
    init:
      mode: always
```

Trong production dùng migration tool, thường tắt SQL initialization:

```yaml
spring:
  sql:
    init:
      mode: never
```

Không nên đặt `always` toàn cục rồi mang script tạo bảng/data mẫu vào production mà chưa xác định rõ tác động khi ứng dụng khởi động nhiều lần.

### 3.2. Chọn script theo database platform

Có thể khai báo:

```yaml
spring:
  sql:
    init:
      mode: always
      platform: postgresql
```

Spring Boot có thể tìm script chung và script theo platform, ví dụ:

```text
src/main/resources/
├── schema.sql
├── data.sql
├── schema-postgresql.sql
└── data-postgresql.sql
```

Cách này hữu ích khi development dùng nhiều database có cú pháp DDL khác nhau. Tuy nhiên, khi số lượng thay đổi schema tăng, việc duy trì nhiều bộ script khởi tạo song song trở nên khó quản lý. Migration có phiên bản thường phù hợp hơn cho schema thay đổi theo thời gian.

### 3.3. Continue on error

Mặc định script initialization dừng khi gặp lỗi. Có thể đặt `continue-on-error` để tiếp tục, nhưng không nên bật chỉ nhằm che giấu lỗi schema.

Ví dụ, nếu câu CREATE TABLE thất bại nhưng data.sql vẫn tiếp tục insert, ứng dụng có thể khởi động với database chưa được chuẩn bị đúng. Với script schema quan trọng, fail-fast thường giúp phát hiện cấu hình sai sớm hơn.

### 3.4. Vị trí script tùy chỉnh

Có thể tổ chức script trong thư mục riêng:

```yaml
spring:
  sql:
    init:
      schema-locations: classpath:/db/init/schema.sql
      data-locations: classpath:/db/init/reference-data.sql
```

Nếu cần nhiều file, có thể khai báo nhiều resource location theo cú pháp property của Spring Boot. Hãy kiểm tra đúng resource path trong artifact được đóng gói; file có trong source tree nhưng không nằm trong classpath của JAR thì startup không thể đọc được.

## 4. Versioned migration là gì?

Versioned migration là một thay đổi database được đặt tên/định danh theo phiên bản và được migration tool theo dõi sau khi áp dụng.

Ví dụ một ứng dụng phát triển schema theo các bước:

1. Tạo bảng customers.
2. Thêm cột phone.
3. Thêm index cho email.
4. Thêm cột trạng thái xác minh email.
5. Backfill dữ liệu cũ và thêm constraint.

Thay vì sửa một file schema duy nhất, mỗi bước được lưu thành migration riêng:

```text
src/main/resources/db/migration/
├── V1__create_customers.sql
├── V2__add_phone_to_customers.sql
├── V3__add_email_index.sql
└── V4__add_email_verified.sql
```

Migration tool đọc các file, xác định phiên bản nào đã chạy, rồi áp dụng những phiên bản còn thiếu theo thứ tự. Nó lưu metadata vào bảng lịch sử trong database.

Điều này tạo ra một lịch sử có thể kiểm tra được: database đã được đưa tới phiên bản schema nào và bởi những migration nào.

## 5. Flyway với Spring Boot

Flyway là một migration tool phổ biến trong ứng dụng Spring Boot. Khi thêm dependency Flyway phù hợp với phiên bản Spring Boot và database, Boot có thể auto-configure Flyway để chạy migration khi application context khởi động.

Các file versioned SQL mặc định thường nằm trong:

```text
src/main/resources/db/migration/
```

Ví dụ:

```text
V1__create_customers.sql
V2__add_phone_to_customers.sql
V3__create_customer_status_index.sql
```

Quy ước tên thường có dạng:

- `V`: migration có phiên bản.
- Số phiên bản: thứ tự/định danh phiên bản.
- `__`: dấu phân cách giữa version và mô tả.
- Phần mô tả: giải thích ngắn thay đổi.

### 5.1. Migration đầu tiên

`V1__create_customers.sql`:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(160) NOT NULL,
    email VARCHAR(255) NOT NULL UNIQUE,
    active BOOLEAN NOT NULL
);
```

### 5.2. Migration tiếp theo

`V2__add_phone_to_customers.sql`:

```sql
ALTER TABLE customers
ADD COLUMN phone VARCHAR(30);
```

`V3__create_customer_status_index.sql`:

```sql
CREATE INDEX idx_customers_active
ON customers(active);
```

Mỗi file thể hiện một thay đổi độc lập. Khi database đã áp dụng V1 và V2, lần chạy tiếp theo chỉ cần áp dụng V3 nếu chưa có migration mới hơn.

### 5.3. Bảng lịch sử Flyway

Flyway lưu thông tin migration đã chạy trong bảng lịch sử, thường là `flyway_schema_history`. Bảng này ghi nhận version, description, checksum, thời điểm chạy và trạng thái thực thi.

Checksum giúp phát hiện trường hợp file migration đã được áp dụng nhưng nội dung bị sửa sau đó. Một nguyên tắc quan trọng là **không sửa migration versioned đã chạy ở môi trường dùng chung/production**. Khi cần thay đổi tiếp, hãy tạo migration version mới.

Nếu migration cũ chưa được áp dụng ở bất kỳ database dùng chung nào, nhóm có thể quyết định chỉnh sửa theo quy trình phát triển nội bộ. Nhưng sau khi đã phát hành, lịch sử migration nên được xem là bất biến.

### 5.4. Cấu hình Flyway

Ví dụ Spring Boot:

```yaml
spring:
  flyway:
    enabled: true
    locations: classpath:db/migration
```

Một số thuộc tính thường gặp:

| Property | Ý nghĩa |
| --- | --- |
| `spring.flyway.enabled` | Bật/tắt Flyway auto-configuration. |
| `spring.flyway.locations` | Vị trí migration. |
| `spring.flyway.schemas` | Schema database mà Flyway quản lý theo cấu hình. |
| `spring.flyway.table` | Tên bảng lịch sử migration. |
| `spring.flyway.baseline-on-migrate` | Cho phép baseline database không trống theo cấu hình. |

Tên property và tùy chọn cụ thể cần đối chiếu phiên bản Spring Boot/Flyway đang dùng. Không bật `baseline-on-migrate` chỉ để bỏ qua lỗi migration trên database hiện có; baseline cần một quy trình xác nhận trạng thái schema trước đó.

## 6. Liquibase với Spring Boot

Liquibase cũng quản lý thay đổi schema theo phiên bản, nhưng cách định nghĩa thay đổi thường dựa trên changelog và changeset.

Một cấu trúc thường gặp:

```text
src/main/resources/db/changelog/
├── db.changelog-master.yaml
└── changes/
    ├── 001-create-customers.yaml
    └── 002-add-phone.yaml
```

Master changelog có thể include các file con:

```yaml
databaseChangeLog:
  - include:
      file: changes/001-create-customers.yaml
      relativeToChangelogFile: true
  - include:
      file: changes/002-add-phone.yaml
      relativeToChangelogFile: true
```

Một changeset tạo bảng:

```yaml
databaseChangeLog:
  - changeSet:
      id: 001-create-customers
      author: app-team
      changes:
        - createTable:
            tableName: customers
            columns:
              - column:
                  name: id
                  type: BIGINT
                  autoIncrement: true
                  constraints:
                    primaryKey: true
                    nullable: false
              - column:
                  name: name
                  type: VARCHAR(160)
                  constraints:
                    nullable: false
              - column:
                  name: email
                  type: VARCHAR(255)
                  constraints:
                    nullable: false
                    unique: true
```

Liquibase xác định một changeset qua các thông tin định danh như `id`, `author` và đường dẫn changelog. Các changeset đã chạy được ghi nhận trong bảng `DATABASECHANGELOG`; Liquibase cũng sử dụng bảng khóa `DATABASECHANGELOGLOCK` để điều phối việc chạy changelog.

### 6.1. Cấu hình Liquibase

Ví dụ:

```yaml
spring:
  liquibase:
    enabled: true
    change-log: classpath:/db/changelog/db.changelog-master.yaml
```

Liquibase có thể định nghĩa schema thay đổi bằng YAML, XML, JSON hoặc SQL changelog. Việc chọn format chủ yếu phụ thuộc thói quen đội phát triển, nhu cầu review và khả năng diễn đạt thay đổi.

### 6.2. Changeset và checksum

Liquibase theo dõi changeset đã chạy và checksum của nó. Không sửa changeset đã triển khai để thay đổi kết quả lịch sử. Tạo changeset mới cho thay đổi tiếp theo, trừ khi đang xử lý một tình huống phát triển chưa phát hành theo quy trình rõ ràng.

Liquibase hỗ trợ rollback ở mức changeset khi có rollback definition hoặc có thể tự suy ra cho một số loại change. Tuy nhiên, không phải mọi thay đổi SQL đều có thể rollback tự động và an toàn. Với thao tác xóa dữ liệu hoặc chuyển đổi không đảo ngược, cần thiết kế rollback/restore riêng.

## 7. So sánh SQL initialization, Flyway và Liquibase

| Tiêu chí | SQL initialization | Flyway | Liquibase |
| --- | --- | --- | --- |
| Mục tiêu chính | Khởi tạo schema/data khi startup | Quản lý migration theo version | Quản lý thay đổi schema bằng changelog/changeset |
| Định dạng | SQL scripts | SQL hoặc Java migration tùy cấu hình | YAML, XML, JSON, SQL |
| Theo dõi lịch sử | Không có lịch sử migration chuẩn | Có bảng history | Có bảng DATABASECHANGELOG |
| Thứ tự thay đổi | Theo script/resource được cấu hình | Theo version migration | Theo thứ tự changeset/changelog |
| Phát hiện sửa file đã chạy | Không có checksum migration tích hợp tương đương | Có checksum | Có checksum changeset |
| Phù hợp | Database nhúng, test, bootstrap đơn giản | Schema thay đổi tuần tự theo version | Schema cần changelog đa định dạng và metadata changeset |
| Rollback | Developer tự viết/điều phối | Cần chiến lược rollback phù hợp; không mặc định mọi SQL đảo ngược được | Có rollback support nhưng phụ thuộc change và rollback definition |
| Dữ liệu production hiện hữu | Không tự quản lý chuyển đổi phiên bản | Có baseline/migration history | Có baseline/changelog sync theo quy trình |

Điểm khác biệt lớn nhất là **migration tool quản lý lịch sử thay đổi database**, còn SQL initialization chỉ chạy script theo cấu hình startup.

Flyway và Liquibase giải quyết bài toán tương tự nhưng không nên chạy đồng thời để cùng quản lý một schema. Chọn một công cụ làm nguồn sự thật cho migration của database.

## 8. Không chạy song song nhiều cơ chế tạo schema

Một lỗi cấu hình phổ biến là đồng thời để:

- `schema.sql` tạo bảng.
- Flyway chạy `V1__create_tables.sql` cũng tạo các bảng đó.
- Liquibase lại chạy changelog tạo cùng bảng.

Kết quả có thể là lỗi “table already exists”, dữ liệu được seed hai lần hoặc trạng thái schema khác nhau giữa môi trường.

Nếu dự án chọn Flyway:

```yaml
spring:
  sql:
    init:
      mode: never
  flyway:
    enabled: true
```

Nếu chọn Liquibase:

```yaml
spring:
  sql:
    init:
      mode: never
  liquibase:
    enabled: true
```

Có thể giữ một số script nạp fixture cho test hoặc dữ liệu tham chiếu, nhưng cần phân định rõ ai sở hữu schema và thứ tự chạy. Tránh để SQL initialization và migration tool cùng tạo/sửa một tập bảng.

Đặc biệt, không dùng `data.sql` để seed dữ liệu nghiệp vụ production mỗi lần ứng dụng khởi động. Dữ liệu tham chiếu cần thiết có thể được quản lý bằng migration hoặc một quy trình seed idempotent riêng.

## 9. Chọn cách nào cho từng môi trường?

Một cách phân chia thường gặp:

| Môi trường | Cách tiếp cận |
| --- | --- |
| Unit test không cần database | Không cần schema initialization. |
| Test slice dùng embedded database | Có thể dùng `schema.sql`/`data.sql` hoặc migration nếu cần kiểm tra schema thật. |
| Integration test PostgreSQL/MySQL | Chạy migration trên Testcontainers để kiểm tra đúng dialect. |
| Local development mới | Migration có phiên bản giúp database local theo kịp code. |
| Staging/production | Flyway hoặc Liquibase quản lý schema trước khi code phụ thuộc thay đổi được chạy. |
| Demo database dùng một lần | SQL initialization có thể đơn giản và đủ dùng. |

### 9.1. SQL initialization cho test

Ví dụ test slice:

```java
@DataJdbcTest
class CustomerRepositoryTest {

    @Autowired
    CustomerRepository customers;

    @Test
    void savesAndReadsCustomer() {
        Customer saved = customers.save(
            new Customer(null, "An Nguyen", "an@example.test", true)
        );

        assertThat(customers.findById(saved.id()))
            .contains(saved);
    }
}
```

Nếu dùng embedded database và schema script, Boot có thể chạy initialization theo mode mặc định. Nếu muốn test migration, thêm Flyway/Liquibase dependency và chạy cùng migration như production. Cần tránh để cả hai cơ chế tạo schema trùng nhau.

### 9.2. Integration test với Testcontainers

Khi production dùng PostgreSQL, test migration trên PostgreSQL container giúp phát hiện khác biệt DDL, kiểu dữ liệu, index và constraint:

```java
@Testcontainers
@DataJdbcTest
@AutoConfigureTestDatabase(
    replace = AutoConfigureTestDatabase.Replace.NONE
)
class CustomerPostgresMigrationTest {

    @Container
    static PostgreSQLContainer<?> postgres =
        new PostgreSQLContainer<>("postgres:16-alpine");

    @DynamicPropertySource
    static void configure(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
    }
}
```

Ví dụ minh họa cấu hình datasource. Dự án cần dependency Testcontainers PostgreSQL, Flyway hoặc Liquibase nếu muốn test migration, và phiên bản container phù hợp với production.

## 10. Migration thay đổi schema và dữ liệu

Migration không chỉ tạo bảng. Nó còn phải chuyển dữ liệu cũ sang cấu trúc mới.

Giả sử ban đầu bảng customers chỉ có:

```sql
CREATE TABLE customers (
    id BIGINT PRIMARY KEY,
    name VARCHAR(160) NOT NULL
);
```

Phiên bản sau cần thêm email bắt buộc. Không nên đơn giản thêm cột NOT NULL nếu bảng đang có dữ liệu mà chưa có giá trị email.

Một chiến lược an toàn hơn:

### Bước 1: Expand — thêm cột nullable

```sql
ALTER TABLE customers
ADD COLUMN email VARCHAR(255);
```

### Bước 2: Backfill dữ liệu hiện tại

```sql
UPDATE customers
SET email = CONCAT('legacy-', id, '@example.invalid')
WHERE email IS NULL;
```

Giá trị backfill chỉ là ví dụ; dữ liệu thực tế cần quy tắc nghiệp vụ hợp lệ, không nên tạo địa chỉ giả nếu email là thông tin xác thực.

### Bước 3: Deploy code tương thích

Code mới có thể đọc cả row cũ và mới trong giai đoạn chuyển tiếp, hoặc ghi email cho các bản ghi mới. Nếu rolling deployment có nhiều phiên bản ứng dụng cùng chạy, phải bảo đảm code cũ không bị lỗi khi schema đã được mở rộng.

### Bước 4: Siết constraint sau khi dữ liệu đã hợp lệ

```sql
ALTER TABLE customers
ALTER COLUMN email SET NOT NULL;
```

Cú pháp thay đổi constraint tùy database. Sau khi backfill và xác minh không còn NULL, mới áp dụng NOT NULL.

Đây là ví dụ của **expand-and-contract migration**: mở rộng schema để code cũ/mới cùng hoạt động, chuyển dữ liệu và traffic, rồi mới loại bỏ cấu trúc cũ hoặc siết constraint.

## 11. Nguyên tắc viết migration an toàn

Một migration tốt cần:

- Có phạm vi thay đổi rõ ràng và tên mô tả.
- Có thể review độc lập trong code review.
- Được kiểm thử trên database/dialect mục tiêu.
- Không sửa nội dung migration đã áp dụng ở môi trường dùng chung.
- Cân nhắc thời gian khóa bảng và tác động lên dữ liệu lớn.
- Có kế hoạch backfill và rollback/restore nếu cần.
- Tương thích với thứ tự triển khai ứng dụng.
- Được chạy bằng cùng một quy trình trong local, CI, staging và production.

### 11.1. Không gộp thay đổi không liên quan

Một migration có thể chứa nhiều câu lệnh cần thiết cho cùng một thay đổi nghiệp vụ, nhưng tránh gộp các thay đổi không liên quan thành một file khổng lồ. Migration nhỏ, có mục đích rõ giúp dễ xác định lỗi và hiểu lịch sử schema.

### 11.2. Không sửa migration đã phát hành

Giả sử `V2__add_phone_to_customers.sql` đã chạy trên staging và production. Nếu sau đó phát hiện cần đổi kiểu cột, hãy tạo `V4__change_phone_type.sql` hoặc version tiếp theo phù hợp. Không chỉnh lại V2 rồi kỳ vọng database đã chạy sẽ tự nhận nội dung mới.

Migration tool thường lưu checksum. Sửa file đã chạy có thể khiến Flyway/Liquibase báo checksum mismatch hoặc yêu cầu thao tác repair có chủ đích. Không dùng repair để che giấu việc lịch sử migration bị sửa sai.

### 11.3. DDL transaction phụ thuộc database

Một số database hỗ trợ transactional DDL cho nhiều loại câu lệnh; một số lệnh hoặc database có thể tự commit hoặc có giới hạn transaction. Vì vậy, rollback migration không phải lúc nào cũng đồng nghĩa database trở lại đúng trạng thái trước khi migration bắt đầu.

Với migration có nguy cơ cao, cần backup/restore strategy và rehearsal trên bản sao dữ liệu có kích thước gần production.

## 12. Spring Data JDBC mapping phải đi cùng migration

Một thay đổi domain model thường kéo theo thay đổi schema.

Ví dụ thêm property:

```java
@Table("customers")
public record Customer(
    @Id Long id,
    String name,
    String email,
    @Column("email_verified") boolean emailVerified
) {}
```

Migration tương ứng cần tạo cột `email_verified`:

```sql
ALTER TABLE customers
ADD COLUMN email_verified BOOLEAN NOT NULL DEFAULT FALSE;
```

Trong ví dụ này, default giúp các row hiện tại có giá trị hợp lệ nếu database hỗ trợ và áp dụng default theo câu DDL. Sau migration, Spring Data JDBC có thể đọc/ghi property mới.

Khi thay đổi mapping, hãy kiểm tra đồng bộ:

- Tên table và column.
- Kiểu SQL tương thích với kiểu Java.
- Nullability.
- ID và version column.
- Foreign key cho aggregate child.
- Index và unique constraint.
- Default/trigger/generated column.
- Converter nếu dữ liệu lưu khác kiểu domain.

Một entity compile thành công không chứng minh schema production đã tương thích.

## 13. Quản lý dữ liệu tham chiếu và dữ liệu mẫu

Cần phân biệt ba loại dữ liệu:

| Loại dữ liệu | Ví dụ | Cách quản lý gợi ý |
| --- | --- | --- |
| Schema structure | Table, column, index, constraint | Flyway/Liquibase hoặc provisioning tool. |
| Reference data cần có | Quốc gia, loại trạng thái chuẩn, permission mặc định | Migration có phiên bản hoặc quy trình seed có kiểm soát. |
| Test/demo fixture | Một vài customer mẫu cho test/UI demo | Test fixture, `@Sql`, factory hoặc script riêng theo profile. |

Không nên để một file `data.sql` chứa dữ liệu demo chạy trên mọi môi trường, đặc biệt production. Dữ liệu demo có thể gây trùng unique key, làm nhiễu báo cáo hoặc tạo tài khoản không mong muốn.

Với dữ liệu tham chiếu, migration có thể insert các giá trị cần thiết và theo dõi cùng version schema. Nếu dữ liệu được vận hành viên chỉnh sửa thường xuyên, cần xác định ownership và cơ chế đồng bộ riêng; không nên ghi đè mọi thay đổi vận hành mỗi lần migrate.

## 14. Kiểm tra trạng thái schema và startup

Khi ứng dụng khởi động, nên xác định rõ quy trình:

1. Database đã sẵn sàng kết nối.
2. Migration tool kiểm tra lịch sử và áp dụng migration còn thiếu.
3. Spring Data JDBC repositories được khởi tạo và sử dụng schema tương thích.
4. Application bắt đầu nhận traffic.

Với SQL initialization, script phải chạy đúng thứ tự và đúng mode. Với Flyway/Liquibase, migration phải hoàn tất trước khi code thực hiện query phụ thuộc schema mới.

Trong hệ thống có nhiều application instance cùng khởi động, migration tool có cơ chế quản lý lịch sử/locking để tránh các instance tự ý chạy lại cùng migration. Dù vậy, cần tổ chức deployment sao cho migration không tạo ra lock kéo dài hoặc downtime ngoài dự kiến.

Nếu migration thất bại, ứng dụng nên dừng startup hoặc không nhận traffic thay vì tiếp tục chạy trên schema chưa tương thích.

## 15. Những lỗi thường gặp

| Hiện tượng | Nguyên nhân | Hướng xử lý |
| --- | --- | --- |
| Startup báo table already exists | `schema.sql` bị chạy lại trên database đã có bảng hoặc nhiều cơ chế cùng tạo schema. | Chọn một schema owner; dùng migration cho thay đổi lâu dài. |
| Startup lỗi duplicate key khi chạy data.sql | Script seed chạy lại trên dữ liệu đã tồn tại. | Dùng fixture test hoặc seed idempotent có kiểm soát. |
| Đã sửa schema.sql nhưng database cũ không được cập nhật đúng | SQL initialization không lưu lịch sử phiên bản schema. | Tạo migration mới. |
| Flyway báo checksum mismatch | File migration đã chạy bị sửa nội dung. | Khôi phục migration cũ và tạo migration mới; chỉ repair theo quy trình có chủ đích. |
| Liquibase báo changeset đã thay đổi | Checksum của changeset khác với lần đã chạy. | Không sửa changeset đã triển khai; tạo changeset mới. |
| Repository lỗi missing column | Mapping mới được deploy trước migration tạo cột. | Triển khai migration tương thích trước code phụ thuộc cột. |
| Production có dữ liệu cũ nhưng thêm NOT NULL thất bại | Chưa backfill giá trị trước khi siết constraint. | Expand nullable, backfill, xác minh rồi mới NOT NULL. |
| H2 test pass nhưng PostgreSQL fail | DDL, type, function hoặc constraint khác dialect. | Chạy migration test trên đúng database bằng Testcontainers. |
| Flyway và Liquibase cùng sửa bảng | Hai migration tool cùng quản lý một schema. | Chọn một nguồn sự thật cho schema migration. |
| SQL init chạy trong production ngoài dự kiến | `spring.sql.init.mode` đặt `always` hoặc profile dùng chung. | Tắt bằng `never` ở môi trường dùng migration. |
| Migration chạy quá lâu khi deploy | Backfill lớn hoặc DDL giữ lock. | Chia migration, batch backfill và rehearsal trên dữ liệu gần production. |

## 16. Quy trình lựa chọn và triển khai

Khi thiết kế schema cho ứng dụng Spring Data JDBC:

1. Xác định môi trường và mục đích: database tạm thời, test, demo hay dữ liệu lâu dài.
2. Với schema đơn giản dùng một lần, cân nhắc `schema.sql`/`data.sql`.
3. Với schema phát triển theo nhiều phiên bản, chọn Flyway hoặc Liquibase.
4. Chỉ định một công cụ làm nguồn sự thật cho thay đổi schema.
5. Lưu migration trong source control cùng code.
6. Viết migration theo từng thay đổi có mục đích và không sửa file đã phát hành.
7. Backfill dữ liệu trước khi thêm constraint bắt buộc.
8. Dùng expand-and-contract khi cần rolling deployment.
9. Chạy migration trong CI và integration test với đúng database/dialect.
10. Đảm bảo migration hoàn tất trước khi application nhận traffic.
11. Tắt SQL initialization ở môi trường đã do migration tool quản lý.
12. Quản lý test fixture và reference data theo ownership riêng.

> **SQL initialization chuẩn bị database bằng các script chạy theo cấu hình startup; versioned migration ghi nhận và áp dụng từng thay đổi schema theo lịch sử phiên bản.** Với Spring Data JDBC, hãy dùng script đơn giản cho database tạm thời hoặc test phù hợp, và dùng Flyway/Liquibase để quản lý schema thay đổi lâu dài qua các môi trường. Không để nhiều cơ chế cùng tạo/sửa một schema.
