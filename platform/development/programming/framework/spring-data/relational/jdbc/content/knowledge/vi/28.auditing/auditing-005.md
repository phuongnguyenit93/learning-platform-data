# Điều khiển thời gian bằng DateTimeProvider và quy ước múi giờ

Spring Data JDBC hỗ trợ auditing để tự động ghi nhận thời điểm tạo, thời điểm cập nhật và người thực hiện thao tác trên aggregate. Các annotation như `@CreatedDate` và `@LastModifiedDate` đánh dấu thuộc tính cần được điền; `DateTimeProvider` cung cấp giá trị thời gian mà auditing infrastructure sử dụng.

Trong ứng dụng chạy trên nhiều máy chủ hoặc phục vụ người dùng ở nhiều múi giờ, không nên để timestamp phụ thuộc ngẫu nhiên vào timezone mặc định của JVM, máy chủ database hoặc máy của người dùng. Hãy xác định một quy ước thống nhất: dùng một thời điểm tuyệt đối (thường là `Instant` theo UTC) để lưu audit, điều khiển nguồn thời gian bằng `Clock`/`DateTimeProvider`, và chỉ chuyển sang múi giờ địa phương khi hiển thị hoặc xử lý ngày nghiệp vụ.

Bài học trình bày cách cấu hình `DateTimeProvider`, cách chọn kiểu thời gian, cách phối hợp timezone của ứng dụng và database, xử lý DST, kiểm thử thời gian cố định và những lỗi thường gặp.

## 1. Auditing timestamp và DateTimeProvider

Auditing trả lời các câu hỏi như:

- Bản ghi được tạo lúc nào?
- Lần cuối bản ghi được thay đổi lúc nào?
- Ai tạo hoặc cập nhật bản ghi?
- Những giá trị này được xác định theo nguồn thời gian nào?

Các annotation thường dùng:

| Annotation | Ý nghĩa |
| --- | --- |
| `@CreatedDate` | Thời điểm tạo aggregate/bản ghi. |
| `@LastModifiedDate` | Thời điểm sửa gần nhất. |
| `@CreatedBy` | Actor tạo dữ liệu. |
| `@LastModifiedBy` | Actor sửa gần nhất. |

`DateTimeProvider` là abstraction cung cấp thời điểm hiện tại cho auditing handler. Nó trả về `Optional<TemporalAccessor>`, nên có thể cung cấp `Instant`, `LocalDateTime` hoặc kiểu temporal phù hợp với mô hình dữ liệu.

Nếu không cấu hình provider riêng, Spring Data sử dụng provider thời gian mặc định. Provider mặc định tiện cho ứng dụng đơn giản, nhưng phụ thuộc nguồn thời gian mặc định của runtime. Một provider tùy chỉnh giúp tập trung quy ước thời gian, inject `Clock` và thay thế clock khi kiểm thử.

Điều quan trọng: `DateTimeProvider` quyết định giá trị auditing được gán trong pipeline Spring Data. Nó không tự đổi timezone của database session, không cấu hình JDBC driver và không thay đổi cách database hiển thị timestamp.

## 2. Bật auditing cho Spring Data JDBC

Kích hoạt auditing bằng `@EnableJdbcAuditing` trong cấu hình:

```java
package com.example.config;

import org.springframework.context.annotation.Configuration;
import org.springframework.data.jdbc.repository.config.EnableJdbcAuditing;

@Configuration
@EnableJdbcAuditing
public class JdbcAuditingConfiguration {
}
```

Khi được bật, Spring Data JDBC đăng ký cơ chế auditing để điền các thuộc tính được đánh dấu trong aggregate khi thực hiện thao tác persistence được hỗ trợ.

Ví dụ aggregate:

```java
package com.example.orders.domain;

import java.math.BigDecimal;
import java.time.Instant;

import org.springframework.data.annotation.CreatedDate;
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.LastModifiedDate;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_order")
public record PurchaseOrder(
    @Id Long id,
    String status,
    BigDecimal totalAmount,
    @CreatedDate Instant createdAt,
    @LastModifiedDate Instant lastModifiedAt
) {
}
```

Schema minh họa với PostgreSQL:

```sql
CREATE TABLE purchase_order (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    status VARCHAR(30) NOT NULL,
    total_amount NUMERIC(18, 2) NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL,
    last_modified_at TIMESTAMP WITH TIME ZONE NOT NULL
);
```

Trong ví dụ này, `createdAt` và `lastModifiedAt` biểu diễn thời điểm tuyệt đối bằng `Instant`. Kiểu cột SQL phải phù hợp database và JDBC driver đang dùng; phần sau sẽ phân biệt các kiểu timestamp theo từng hệ quản trị.

`@CreatedDate` thường được gán khi insert. `@LastModifiedDate` được gán khi insert và khi cập nhật theo cấu hình mặc định `modifyOnCreate = true`. Có thể thay đổi hành vi này nếu nghiệp vụ muốn trường modified chỉ bắt đầu có giá trị sau lần sửa đầu tiên.

## 3. Tạo DateTimeProvider dựa trên Clock

Không nên gọi `Instant.now()` trực tiếp ở nhiều nơi trong domain hoặc repository. Inject `Clock` giúp ứng dụng có một nguồn thời gian rõ ràng và cho phép thay thế bằng clock cố định trong test.

```java
package com.example.config;

import java.time.Clock;
import java.time.Instant;
import java.time.temporal.TemporalAccessor;
import java.util.Optional;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.data.auditing.DateTimeProvider;
import org.springframework.data.jdbc.repository.config.EnableJdbcAuditing;

@Configuration
@EnableJdbcAuditing(dateTimeProviderRef = "auditDateTimeProvider")
public class JdbcAuditingConfiguration {

    @Bean
    Clock auditClock() {
        return Clock.systemUTC();
    }

    @Bean
    DateTimeProvider auditDateTimeProvider(Clock auditClock) {
        return () -> Optional.<TemporalAccessor>of(
            Instant.now(auditClock)
        );
    }
}
```

Các phần chính:

- `Clock.systemUTC()` cung cấp clock theo UTC.
- `Instant.now(auditClock)` đọc thời điểm từ clock được inject.
- `DateTimeProvider` đóng gói giá trị đó cho auditing infrastructure.
- `dateTimeProviderRef` chỉ rõ bean provider được dùng khi bật JDBC auditing.

Tên bean trong `dateTimeProviderRef` phải khớp với bean provider. Nếu có nhiều bean `Clock`, dùng `@Qualifier` hoặc đánh dấu bean phù hợp bằng `@Primary` để tránh inject nhầm nguồn thời gian.

`Clock.systemUTC()` không có nghĩa mọi timestamp trong database tự động được lưu/hiển thị UTC. Nó chỉ bảo đảm provider tạo ra một instant theo UTC. Database column type, driver và session timezone vẫn cần được cấu hình phù hợp.

## 4. Tùy chỉnh hành vi auditing khi tạo mới

Có thể cấu hình các thuộc tính auditing tường minh:

```java
@Configuration
@EnableJdbcAuditing(
    dateTimeProviderRef = "auditDateTimeProvider",
    modifyOnCreate = true,
    setDates = true
)
public class JdbcAuditingConfiguration {
    // Clock và DateTimeProvider bean được khai báo tại đây
}
```

- `setDates = true` bật việc gán các trường ngày được đánh dấu.
- `modifyOnCreate = true` cho phép `@LastModifiedDate` được gán ngay khi tạo.
- Nếu đặt `modifyOnCreate = false`, trường modified không được điền chỉ vì lần insert đầu tiên; nó sẽ được cập nhật ở lần sửa sau theo auditing behavior.

Chọn quy ước theo ý nghĩa nghiệp vụ. Nhiều hệ thống muốn cả created và last-modified đều có giá trị ngay sau insert, nên giữ mặc định là phù hợp. Không dùng `createdAt` để biểu diễn thời điểm import hoặc thời điểm người dùng đăng ký nếu hai khái niệm đó khác nhau; thêm field riêng khi cần.
## 5. Kết hợp thời gian với thông tin người thực hiện

Auditing có thể ghi cả timestamp lẫn actor:

```java
@Table("purchase_order")
public record PurchaseOrder(
    @Id Long id,
    String status,
    @CreatedDate Instant createdAt,
    @LastModifiedDate Instant lastModifiedAt,
    @CreatedBy String createdBy,
    @LastModifiedBy String lastModifiedBy
) {
}
```

Khai báo `AuditorAware` để lấy actor hiện tại:

```java
@Bean
AuditorAware<String> auditorAware(CurrentActorProvider actors) {
    return () -> actors.currentActorId();
}
```

Bật cả hai provider:

```java
@Configuration
@EnableJdbcAuditing(
    dateTimeProviderRef = "auditDateTimeProvider",
    auditorAwareRef = "auditorAware"
)
public class JdbcAuditingConfiguration {
    // Các bean auditClock, auditDateTimeProvider và auditorAware.
}
```

Nên lưu một định danh ổn định của actor, chẳng hạn user ID hoặc service account ID, thay vì display name có thể thay đổi. Với thao tác chạy nền không có người dùng đăng nhập, hãy xác định rõ actor hệ thống như `SYSTEM_IMPORT` hoặc `BATCH_RECONCILIATION` theo quy ước ứng dụng.

Nếu `AuditorAware` trả về `Optional.empty()`, auditing không có actor để gán. Nếu cột actor là `NOT NULL`, cần bảo đảm mọi luồng ghi đều có actor hợp lệ hoặc cung cấp giá trị hệ thống rõ ràng. Không tự gán một người dùng giả chỉ để tránh null.

### Request thread và background worker

Trong request đồng bộ, actor thường lấy từ security context hiện tại. Với `@Async`, scheduler hoặc message consumer, không nên giả định security context tự truyền sang thread khác. Hãy truyền actor/context rõ ràng hoặc cấu hình cơ chế propagation phù hợp.

Một job chạy theo lịch không nhất thiết có người dùng cụ thể; actor có thể là service account. Điều quan trọng là audit phản ánh đúng nguồn thay đổi để có thể giải thích sau này.

## 6. Chọn kiểu dữ liệu thời gian

Không phải mọi kiểu Java thời gian đều biểu diễn cùng một khái niệm:

| Kiểu Java | Biểu diễn | Phù hợp với |
| --- | --- | --- |
| `Instant` | Một điểm tuyệt đối trên timeline, chuẩn UTC. | Audit timestamp, thời điểm tạo/cập nhật, event time. |
| `OffsetDateTime` | Ngày giờ kèm UTC offset, ví dụ +07:00. | Khi cần giữ offset tại thời điểm ghi nhận. |
| `ZonedDateTime` | Ngày giờ cùng vùng múi giờ có quy tắc, ví dụ Asia/Ho_Chi_Minh. | Lịch/sự kiện cần giữ zone ID và quy tắc DST; thường cần lưu zone riêng khi persist. |
| `LocalDateTime` | Ngày giờ trên đồng hồ, không có offset hoặc zone. | Giờ địa phương theo nghiệp vụ khi zone được quản lý riêng. |
| `LocalDate` | Ngày lịch, không có giờ hoặc zone. | Ngày sinh, ngày hóa đơn, ngày nghiệp vụ. |

Đối với `createdAt` và `lastModifiedAt`, `Instant` thường là lựa chọn rõ ràng nhất vì audit cần biết chính xác một sự kiện xảy ra khi nào trên timeline chung.

`LocalDateTime` không xác định được một instant nếu thiếu timezone. Ví dụ `2026-11-13T09:00` có thể có nghĩa 09:00 ở TP.HCM hoặc 09:00 ở Tokyo; đó là hai thời điểm tuyệt đối khác nhau. Không nên dùng `LocalDateTime` cho audit timestamp phân tán nếu không có quy ước zone cố định và được kiểm soát ở mọi tầng.

`OffsetDateTime` giữ offset, nhưng offset không phải tên vùng. `+07:00` không lưu các quy tắc lịch sử/tương lai của `Asia/Ho_Chi_Minh`. Nếu nghiệp vụ cần biết vùng nào được chọn, lưu thêm zone ID dạng chuỗi.

### Không trộn lẫn instant với thời gian địa phương

Ví dụ:

```java
Instant occurredAt = Instant.now(clock);

ZonedDateTime displayTime =
    occurredAt.atZone(ZoneId.of("Asia/Ho_Chi_Minh"));
```

`occurredAt` là thời điểm dùng chung cho hệ thống. `displayTime` là cách biểu diễn thời điểm đó trên đồng hồ địa phương. Hai biến thể hiện cùng một sự kiện, không phải hai timestamp độc lập.

## 7. Quy ước UTC khi lưu và múi giờ khi hiển thị

Một quy ước dễ vận hành cho hệ thống nhiều vùng là:

1. Lấy thời điểm từ `Clock` theo UTC.
2. Ghi audit dưới dạng instant.
3. Truyền timestamp qua API dưới dạng ISO-8601 có `Z` hoặc offset rõ ràng.
4. Chỉ chuyển sang timezone người dùng ở tầng presentation.
5. Khi lọc theo ngày địa phương, chuyển ranh giới ngày thành instant trước khi bind vào SQL.

Ví dụ response API:

```json
{
  "createdAt": "2026-11-13T02:00:00Z"
}
```

UI tại TP.HCM có thể hiển thị cùng instant là 09:00 ngày 13/11/2026. UI ở vùng khác sẽ hiển thị theo timezone tương ứng. Không ghi ngược giá trị đã format cho UI vào cột audit.

Dùng `ZoneId` rõ ràng thay vì phụ thuộc timezone mặc định của máy chạy:

```java
ZoneId userZone = ZoneId.of("Asia/Ho_Chi_Minh");

ZonedDateTime localDisplay =
    createdAt.atZone(userZone);

String formatted =
    DateTimeFormatter.ofPattern("dd/MM/yyyy HH:mm")
        .withZone(userZone)
        .format(createdAt);
```

Format chỉ phục vụ hiển thị. Với API và log liên hệ thống, ưu tiên định dạng ISO-8601 có offset để không mất thông tin về instant.
## 8. Kiểu timestamp trong database và JDBC driver

Kiểu cột SQL quyết định database lưu và diễn giải thời gian như thế nào. Tên kiểu giống nhau giữa các hệ quản trị không bảo đảm semantics giống nhau.

| Database | Kiểu thường gặp | Semantics cần nhớ |
| --- | --- | --- |
| PostgreSQL | `timestamp with time zone` / `timestamptz` | Lưu một instant đã chuẩn hóa; khi hiển thị, giá trị được biểu diễn theo timezone của session. Không giữ nguyên tên vùng timezone ban đầu. |
| PostgreSQL | `timestamp without time zone` | Lưu các thành phần ngày/giờ, không chứa offset hay timezone. |
| MySQL | `TIMESTAMP` | Database chuyển đổi giữa timezone session và UTC khi ghi/đọc; timezone session có ảnh hưởng. |
| MySQL | `DATETIME` | Lưu giá trị ngày/giờ dạng literal, không tự mang timezone. |
| SQL Server | `datetimeoffset` | Lưu ngày/giờ cùng offset; không lưu tên vùng như `Asia/Ho_Chi_Minh`. |
| SQL Server | `datetime2` | Lưu ngày/giờ không có offset. |

Với PostgreSQL, cột `timestamptz` phù hợp cho audit instant. Khi query, PostgreSQL có thể hiển thị cùng instant dưới offset khác tùy session timezone; điều đó không có nghĩa sự kiện đã thay đổi.

Với MySQL, cần cấu hình timezone session nhất quán và hiểu rõ khác biệt giữa `TIMESTAMP` và `DATETIME`. Nếu dùng `DATETIME` để lưu UTC, ứng dụng phải thống nhất rằng các thành phần ngày/giờ trong cột luôn được hiểu là UTC; database không thể suy ra điều đó từ kiểu cột.

Với SQL Server, `datetimeoffset` giữ offset tại thời điểm lưu nhưng không giữ zone ID hoặc quy tắc DST của một vùng. Nếu cần tái tạo vùng đã chọn, lưu zone ID riêng.

### Kiểm tra mapping thực tế

Spring Data JDBC, Spring Framework và JDBC driver cùng tham gia chuyển đổi Java time type sang SQL type. Hãy xác nhận mapping của phiên bản và driver đang dùng bằng integration test trên đúng database đích. Không suy luận rằng vì Java property là `Instant` thì mọi database sẽ tự chọn cùng một kiểu cột.

Quy ước phải thống nhất ở cả ba nơi:

- Java property type.
- SQL column type.
- JDBC driver/session timezone behavior.

Nếu cần converter tùy chỉnh, đặt converter ở cấu hình Spring Data JDBC và kiểm thử round-trip: ghi một instant có phần nano, đọc lại rồi so sánh theo precision thực tế của cột.

## 9. Tránh trộn thời gian của ứng dụng và thời gian của database

Có hai nguồn thời gian thường gặp:

- Application clock: `DateTimeProvider` dùng `Clock` của JVM.
- Database clock: `CURRENT_TIMESTAMP` trong default, trigger hoặc custom SQL.

Hai nguồn có thể lệch nhau vì đồng hồ máy chủ, NTP, cấu hình timezone, transaction timestamp semantics và độ chính xác. Ví dụ một aggregate có `createdAt` do auditing gán bằng app clock nhưng `lastModifiedAt` lại được cập nhật bằng trigger dùng DB clock. Khi so sánh, có thể thấy timestamp không tăng như kỳ vọng.

Chọn một nguồn có thẩm quyền cho từng nhóm trường:

- Nếu auditing do ứng dụng quản lý, dùng `DateTimeProvider` nhất quán và tránh ghi đè cùng field bằng `CURRENT_TIMESTAMP` trong SQL.
- Nếu database là nguồn thời gian chuẩn, dùng default/trigger hoặc câu SQL cập nhật theo DB clock một cách nhất quán; đừng đồng thời kỳ vọng `@CreatedDate` là nguồn duy nhất cho field đó.
- Đồng bộ đồng hồ các host bằng NTP hoặc dịch vụ thời gian của hạ tầng. UTC không tự sửa được clock skew giữa hai máy.

`DateTimeProvider` không phải một database clock provider. Nó chỉ trả giá trị thời gian cho auditing callback trong ứng dụng. Nếu SQL trực tiếp tự ghi timestamp, cần quy ước riêng cho đường ghi đó.

## 10. Múi giờ của JVM, connection và database session

Một ứng dụng có thể chạy trên máy có timezone mặc định khác timezone database session. Nếu code dùng `LocalDateTime.now()` hoặc `ZoneId.systemDefault()`, kết quả phụ thuộc môi trường chạy.

Để giảm khác biệt:

1. Dùng `Clock.systemUTC()` cho nguồn audit instant.
2. Cấu hình timezone session của database/connection theo quy ước UTC khi phù hợp.
3. Không dùng timezone mặc định của JVM làm implicit business rule.
4. Kiểm tra timezone của connection pool sau khi lấy connection và khi trả connection về pool.
5. Ghi log timestamp dưới định dạng ISO-8601 có offset hoặc `Z`.
6. Kiểm thử với JVM timezone khác UTC để phát hiện phụ thuộc ngầm.

Cách cấu hình session timezone phụ thuộc database và driver. Ví dụ PostgreSQL có thể cấu hình timezone ở database, role hoặc session; MySQL có thiết lập session timezone riêng. Không dùng một câu lệnh `SET TIME ZONE` chung cho mọi hệ quản trị. Nếu connection pool chạy câu lệnh khởi tạo session, bảo đảm reset/kiểm soát state để một request không làm rò timezone sang request tiếp theo.

## 11. Chuyển ngày địa phương thành khoảng thời gian để truy vấn

Một yêu cầu như “lấy tất cả đơn được tạo trong ngày 13/11 tại TP.HCM” là yêu cầu theo ngày địa phương, không phải một khoảng UTC cố định có độ dài luôn bằng 24 giờ.

Chuyển ngày và zone thành hai instant:

```java
LocalDate requestedDate = LocalDate.of(2026, 11, 13);
ZoneId zone = ZoneId.of("Asia/Ho_Chi_Minh");

Instant fromInclusive =
    requestedDate.atStartOfDay(zone).toInstant();

Instant toExclusive =
    requestedDate.plusDays(1).atStartOfDay(zone).toInstant();
```

Sau đó bind hai instant vào SQL theo khoảng nửa mở:

```sql
SELECT id, created_at
FROM purchase_order
WHERE created_at >= :fromInclusive
  AND created_at < :toExclusive
ORDER BY created_at, id;
```

Dùng `[from, to)` giúp không phải tạo “23:59:59.999999” ở cuối ngày và tránh sai số precision. Ngày địa phương kế tiếp là ranh giới kết thúc.

### Vì sao không cộng cố định 24 giờ?

Ở vùng có daylight saving time, một ngày địa phương có thể dài 23 hoặc 25 giờ khi đồng hồ đổi. Vì vậy hãy tính đầu ngày kế tiếp từ `LocalDate.plusDays(1)` trong cùng `ZoneId`, không lấy instant đầu ngày rồi cộng `Duration.ofHours(24)`.

Việt Nam hiện không áp dụng DST, nhưng ứng dụng phục vụ nhiều quốc gia vẫn cần xử lý quy tắc vùng timezone. Cơ sở timezone của Java được cập nhật theo phiên bản JDK; với hệ thống phụ thuộc lịch vùng, cần giữ runtime timezone database được cập nhật.

### Không cast cột timestamp sang date nếu không cần

Cách viết như `DATE(created_at) = :date` có thể:

- Dùng timezone session không đúng với timezone người dùng.
- Làm mất khả năng dùng index thông thường trên cột do áp dụng function.
- Gây khác biệt giữa database/dialect.

Tính hai instant boundary ở ứng dụng rồi bind vào điều kiện range thường rõ ràng và thân thiện với index hơn.
## 12. Khi nào cần giữ giờ địa phương và zone ID?

Không phải mọi dữ liệu thời gian đều nên đổi thành `Instant`. Audit timestamp mô tả một sự kiện đã xảy ra trên timeline. Ngược lại, một lịch hẹn có thể mô tả ý định “gặp lúc 09:00 theo giờ địa phương của khách hàng”.

Ví dụ lịch hẹn:

```java
public record Appointment(
    LocalDateTime localStart,
    String zoneId
) {
    public ZonedDateTime startInZone() {
        return localStart.atZone(ZoneId.of(zoneId));
    }

    public Instant startInstant() {
        return startInZone().toInstant();
    }
}
```

Ở đây cần giữ cả local date-time và zone ID vì quy tắc nghiệp vụ có thể là “09:00 tại vùng này”, kể cả khi quy tắc timezone thay đổi trong tương lai. Với lịch hẹn đã được chốt thành một thời điểm tuyệt đối, có thể lưu thêm instant đã xác định để biết chính xác thời điểm thực thi.

### Khoảng trống và giờ lặp do DST

Khi chuyển một `LocalDateTime` sang một zone có DST, có hai tình huống đặc biệt:

- Giờ không tồn tại: đồng hồ nhảy qua một khoảng giờ khi bắt đầu DST.
- Giờ bị lặp: đồng hồ quay lùi, một giờ địa phương có thể ứng với hai instant.

Có thể kiểm tra bằng `ZoneRules`:

```java
LocalDateTime local = LocalDateTime.of(2026, 11, 1, 1, 30);
ZoneId zone = ZoneId.of("America/New_York");

List<ZoneOffset> validOffsets =
    zone.getRules().getValidOffsets(local);

if (validOffsets.isEmpty()) {
    throw new IllegalArgumentException("Local time is in a DST gap");
}

if (validOffsets.size() > 1) {
    // Giờ bị lặp: nghiệp vụ cần chọn offset/occurrence cụ thể.
}
```

Đối với thời điểm do người dùng nhập, hãy xác định chính sách khi giờ bị lặp hoặc không tồn tại. Không để quyết định quan trọng phụ thuộc vào cách API mặc định tự điều chỉnh giờ trong một DST transition.

## 13. Độ chính xác timestamp và round-trip

Java `Instant` có độ chính xác nano giây, nhưng database column có thể lưu ít chữ số thập phân hơn. Ví dụ PostgreSQL timestamp thường có precision microsecond; MySQL có thể khai báo `DATETIME(6)` hoặc `TIMESTAMP(6)`; SQL Server `datetime2(7)` hỗ trợ precision khác.

Nếu clock tạo ra `2026-11-13T02:00:00.123456789Z` nhưng database chỉ lưu microsecond, giá trị đọc lại có thể là `2026-11-13T02:00:00.123457Z` hoặc bị làm tròn/cắt theo driver và database. Không nên viết test yêu cầu bằng tuyệt đối nano giây nếu cột không hỗ trợ precision đó.

Cần:

- Chọn precision phù hợp nhu cầu và database.
- Kiểm tra round-trip bằng chính JDBC driver production.
- So sánh theo precision mà database bảo đảm.
- Không dùng timestamp làm khóa duy nhất nếu hai thao tác có thể có cùng thời điểm; dùng ID/version riêng.
- Không tự cắt precision ở mọi tầng nếu chưa thống nhất quy tắc rounding.

Timestamp audit thường không cần nano giây. Millisecond hoặc microsecond có thể đủ, nhưng quyết định dựa trên yêu cầu truy vết và khả năng của hệ quản trị.

## 14. Kiểm thử DateTimeProvider bằng Clock cố định

`Clock.fixed(...)` giúp test không phụ thuộc thời điểm thực thi. Có thể cung cấp clock test là bean `@Primary` để provider production tự inject clock này:

```java
@TestConfiguration
static class FixedAuditClockConfiguration {

    @Bean
    @Primary
    Clock fixedAuditClock() {
        return Clock.fixed(
            Instant.parse("2026-11-13T02:00:00Z"),
            ZoneOffset.UTC
        );
    }
}
```

Integration test minh họa:

```java
@Test
void auditingUsesConfiguredClock() {
    PurchaseOrder saved = repository.save(
        new PurchaseOrder(null, "CREATED", new BigDecimal("125.00"),
            null, null)
    );

    Instant expected = Instant.parse("2026-11-13T02:00:00Z");

    assertThat(saved.createdAt()).isEqualTo(expected);
    assertThat(saved.lastModifiedAt()).isEqualTo(expected);
}
```

Test cần nạp cấu hình JDBC auditing và clock test vào application context. Tên constructor, repository và fixture phải khớp domain thực tế của ứng dụng.

`Clock.fixed` luôn trả cùng một instant. Để kiểm tra `@LastModifiedDate` thay đổi sau update, dùng một clock test có thể điều khiển hoặc khởi tạo context với các thời điểm cố định khác nhau. Không dùng `Thread.sleep(...)` để chờ đồng hồ chạy qua một khoảng thời gian; test sẽ chậm và dễ không ổn định.

### Kiểm thử chuyển đổi timezone

Có thể kiểm tra việc hiển thị cùng instant ở các vùng khác nhau:

```java
Instant instant = Instant.parse("2026-11-13T02:00:00Z");

ZonedDateTime hcm =
    instant.atZone(ZoneId.of("Asia/Ho_Chi_Minh"));

ZonedDateTime tokyo =
    instant.atZone(ZoneId.of("Asia/Tokyo"));

assertThat(hcm.toInstant()).isEqualTo(instant);
assertThat(tokyo.toInstant()).isEqualTo(instant);
assertThat(hcm.getHour()).isEqualTo(9);
assertThat(tokyo.getHour()).isEqualTo(11);
```

Hai biểu diễn có giờ địa phương khác nhau nhưng cùng instant. Test này kiểm tra quy ước hiển thị mà không cần phụ thuộc timezone mặc định của JVM.

## 15. Migration schema và dữ liệu cũ

Khi thêm auditing vào bảng đã tồn tại, cần quyết định cách xử lý các row cũ:

- Thêm `created_at`/`last_modified_at` nullable trước, backfill bằng thời điểm migration hoặc dữ liệu lịch sử đáng tin cậy, rồi mới đổi thành `NOT NULL`.
- Nếu không biết thời điểm tạo thật, đừng gán một giá trị giả rồi coi nó là timestamp lịch sử chính xác. Có thể lưu `legacy_imported_at` hoặc đánh dấu nguồn dữ liệu.
- Đồng bộ timezone và kiểu cột trước khi deploy code ghi kiểu Java mới.
- Kiểm tra precision và converter trên database thực tế.
- Với bảng lớn, backfill theo batch để hạn chế lock và tải ghi.

Ví dụ migration hai giai đoạn:

```sql
ALTER TABLE purchase_order
    ADD COLUMN created_at TIMESTAMP WITH TIME ZONE NULL,
    ADD COLUMN last_modified_at TIMESTAMP WITH TIME ZONE NULL;
```

Sau khi backfill và xác nhận không còn null, mới áp dụng constraint `NOT NULL` trong migration tiếp theo. Kiểu SQL ở ví dụ là PostgreSQL; thay bằng kiểu tương ứng của database đang dùng.

## 16. Những lỗi thường gặp

| Lỗi | Hậu quả | Cách xử lý |
| --- | --- | --- |
| Dùng `LocalDateTime.now()` cho audit toàn hệ thống | Kết quả phụ thuộc timezone JVM và không xác định instant nếu thiếu zone. | Dùng `Instant` từ UTC clock. |
| Chỉ cấu hình `Clock.systemUTC()` rồi cho rằng DB đã ở UTC | Session/column mapping vẫn có thể chuyển đổi hoặc hiển thị theo timezone khác. | Kiểm tra column type, driver và session timezone. |
| Trộn auditing app clock với SQL `CURRENT_TIMESTAMP` trên cùng field | Timestamp có thể lệch do clock skew hoặc transaction semantics. | Chọn một nguồn thời gian có thẩm quyền. |
| Lưu `OffsetDateTime` rồi kỳ vọng giữ zone ID | Offset không chứa quy tắc vùng timezone. | Lưu zone ID riêng nếu nghiệp vụ cần. |
| Dùng `LocalDateTime` cho lịch hẹn quốc tế mà không lưu zone | Không thể diễn giải đúng thời điểm ở các vùng khác nhau. | Lưu local time cùng `ZoneId` hoặc instant đã xác định. |

| Dùng `Thread.sleep` trong test timestamp | Test chậm và không ổn định. | Inject `Clock.fixed` hoặc clock điều khiển được. |
| So sánh nano giây sau round-trip database | Test thất bại do precision column/driver thấp hơn. | So sánh theo precision được hỗ trợ. |
| Chỉ kiểm tra máy dev | Production có thể dùng timezone/session/driver khác. | Integration test trên cùng loại database và cấu hình gần production. |

## 17. Quy trình thiết kế quy ước thời gian

Trước khi bật auditing, hãy thống nhất:

1. Field nào là audit instant, field nào là ngày/giờ nghiệp vụ địa phương?
2. Audit property dùng `Instant` hay kiểu khác? Vì sao?
3. `DateTimeProvider` lấy thời gian từ app clock hay database clock?
4. Bean `Clock` nào là nguồn chuẩn? Có dùng `Clock.systemUTC()` không?
5. `@EnableJdbcAuditing` đã tham chiếu đúng provider chưa?
6. Database column type và JDBC driver có round-trip đúng instant không?
7. Session timezone và connection pool được quản lý như thế nào?
8. API truyền timestamp có `Z`/offset rõ ràng không?
9. Ngày địa phương được chuyển thành range instant như thế nào?
10. Có xử lý DST gap/overlap cho lịch hẹn không?
11. Precision của database có phù hợp yêu cầu không?
12. Test đã dùng clock cố định và database thật tương ứng chưa?

## 18. Câu hỏi tự kiểm tra

- `DateTimeProvider` cung cấp giá trị nào cho auditing infrastructure?
- Vì sao nên inject `Clock` thay vì gọi `Instant.now()` rải rác?
- `@CreatedDate` và `@LastModifiedDate` khác nhau ở ý nghĩa nào?
- `modifyOnCreate` ảnh hưởng thế nào đến trường modified khi insert?
- Vì sao `Instant` phù hợp với audit timestamp hơn `LocalDateTime`?
- `OffsetDateTime` có lưu tên vùng timezone như `Asia/Ho_Chi_Minh` không?
- `Clock.systemUTC()` có tự cấu hình timezone database session không?
- PostgreSQL `timestamptz` có giữ lại zone ID ban đầu không?
- Vì sao không nên trộn app clock với SQL `CURRENT_TIMESTAMP` cho cùng một field?
- Làm thế nào lấy toàn bộ dữ liệu của một ngày địa phương mà vẫn đúng khi DST thay đổi?
- Vì sao cần kiểm tra precision sau round-trip qua JDBC?
- Làm thế nào kiểm thử auditing mà không dùng `Thread.sleep`?

Một quy ước thời gian rõ ràng bắt đầu từ việc phân biệt **instant của sự kiện** với **cách biểu diễn trên đồng hồ địa phương**. Dùng `DateTimeProvider` dựa trên `Clock` để kiểm soát nguồn audit time, ưu tiên `Instant` cho thời điểm tạo/cập nhật, thống nhất kiểu cột và timezone session, rồi chuyển sang `ZoneId` ở tầng hiển thị hoặc khi diễn giải ngày nghiệp vụ. Kiểm thử bằng clock cố định và round-trip trên database thật để tránh phụ thuộc vào môi trường chạy.
