# Triển khai repository, converter và quy tắc nghiệp vụ

Trong **Spring Data Relational JDBC**, một use case hoàn chỉnh cần kết nối ba phần: repository để truy cập aggregate, converter để ánh xạ kiểu domain với kiểu JDBC và quy tắc nghiệp vụ để bảo vệ trạng thái hợp lệ. Nếu chỉ tạo repository interface mà domain model chưa có invariant, ứng dụng vẫn có thể lưu dữ liệu sai. Nếu có value object nhưng thiếu converter, mapping có thể không biết cách ghi/đọc kiểu đó. Nếu service không có transaction boundary, nhiều thao tác repository có thể không còn nguyên tử.

Bài này xây dựng một aggregate đơn hàng từ schema đến test. Ví dụ dùng:

- **PurchaseOrder** làm aggregate root.
- **OrderLine** làm entity con thuộc vòng đời đơn hàng.
- **OrderNumber** và **Sku** làm value object được lưu dưới dạng chuỗi.
- Custom converters để chuyển value object sang/về JDBC.
- Repository để đọc/lưu aggregate.
- Domain methods để bảo vệ quy tắc thêm dòng hàng và xác nhận đơn.
- Application service với **@Transactional**.
- Migration và test để xác nhận mapping, business rules và persistence.

Spring Data JDBC tập trung vào aggregate root và transaction rõ ràng. Không cần tạo repository cho từng bảng con nếu các hàng đó thuộc cùng aggregate.

## 1. Xác định use case và quy tắc nghiệp vụ

Giả sử hệ thống bán hàng cần hỗ trợ:

1. Tạo đơn hàng ở trạng thái **DRAFT**.
2. Thêm một hoặc nhiều dòng hàng.
3. Mỗi dòng có SKU, số lượng và đơn giá.
4. Không cho phép SKU trùng trong cùng đơn.
5. Không cho phép số lượng hoặc đơn giá âm/không hợp lệ.
6. Không cho sửa dòng hàng sau khi đơn đã xác nhận.
7. Chỉ xác nhận đơn có ít nhất một dòng hàng.
8. Tổng tiền phải bằng tổng số lượng nhân đơn giá của các dòng.

Các quy tắc này thuộc domain model. Repository chịu trách nhiệm lưu/tìm aggregate; service điều phối use case và transaction.

### 1.1. Aggregate boundary

~~~text
PurchaseOrder (aggregate root)
  ├── id
  ├── version
  ├── orderNumber
  ├── customerId
  ├── status
  ├── currencyCode
  ├── totalAmount
  └── lines
        ├── OrderLine (sku, quantity, unitPrice)
        └── OrderLine (sku, quantity, unitPrice)
~~~

**OrderLine** không có repository riêng vì nó chỉ được tạo/sửa/xóa thông qua đơn hàng. **PurchaseOrderRepository** là cổng persistence duy nhất cho aggregate này.

Nếu sau này dòng hàng có vòng đời độc lập, được quản lý bởi một use case khác và có thể thay đổi mà không cần tải đơn hàng, hãy đánh giá lại aggregate boundary. Không tách repository chỉ vì bảng child có primary key.

## 2. Thiết kế schema trước khi viết mapping

Ví dụ schema PostgreSQL:

~~~sql
CREATE TABLE purchase_order (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    version BIGINT NOT NULL,
    order_number VARCHAR(32) NOT NULL,
    customer_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL,
    currency_code CHAR(3) NOT NULL,
    total_amount NUMERIC(19, 2) NOT NULL,
    CONSTRAINT uk_purchase_order_number UNIQUE (order_number)
);

CREATE TABLE order_line (
    purchase_order_id BIGINT NOT NULL,
    line_number INTEGER NOT NULL,
    sku VARCHAR(50) NOT NULL,
    quantity INTEGER NOT NULL,
    unit_price NUMERIC(19, 2) NOT NULL,
    CONSTRAINT pk_order_line
        PRIMARY KEY (purchase_order_id, line_number),
    CONSTRAINT fk_order_line_order
        FOREIGN KEY (purchase_order_id)
        REFERENCES purchase_order(id)
);
~~~

Thiết kế này thể hiện:

- Mỗi đơn hàng có một ID database sinh.
- **version** dùng cho optimistic locking.
- **order_number** duy nhất.
- **order_line** thuộc đơn hàng qua **purchase_order_id**.
- **line_number** lưu vị trí của dòng trong collection.
- **sku** được lưu bằng chuỗi.
- Tiền được lưu bằng **NUMERIC**, tránh dùng floating-point.

**customer_id** là khóa tham chiếu tới customer trong ví dụ. Nếu cần foreign key, thêm constraint tương ứng theo schema thực tế. Bài này không đưa Customer vào aggregate đơn hàng vì khách hàng có vòng đời độc lập.

Đưa DDL vào Flyway/Liquibase migration của dự án. Không chỉ tạo bảng thủ công trên máy phát triển, vì schema phải được tái tạo nhất quán ở CI và production.

## 3. Tạo value object cho dữ liệu nghiệp vụ

Value object giúp biểu diễn khái niệm domain có validation riêng. Ví dụ OrderNumber:

~~~java
import java.util.Objects;
import java.util.regex.Pattern;

public record OrderNumber(String value) {

    private static final Pattern FORMAT =
            Pattern.compile("PO-[0-9]{4}-[0-9]{4,}");

    public OrderNumber {
        Objects.requireNonNull(value, "order number is required");
        value = value.trim().toUpperCase();

        if (!FORMAT.matcher(value).matches()) {
            throw new IllegalArgumentException(
                    "Invalid order number: " + value);
        }
    }
}
~~~

**OrderNumber** không chỉ là một String. Nó đảm bảo mọi instance được tạo đều có định dạng hợp lệ. Khi đọc dữ liệu cũ từ database, converter cũng sẽ đi qua constructor này; dữ liệu sai định dạng sẽ được phát hiện thay vì âm thầm lan vào domain.

Tương tự, tạo value object cho SKU:

~~~java
import java.util.Objects;
import java.util.regex.Pattern;

public record Sku(String value) {

    private static final Pattern FORMAT =
            Pattern.compile("[A-Z0-9][A-Z0-9_-]{1,49}");

    public Sku {
        Objects.requireNonNull(value, "sku is required");
        value = value.trim().toUpperCase();

        if (!FORMAT.matcher(value).matches()) {
            throw new IllegalArgumentException("Invalid SKU: " + value);
        }
    }
}
~~~

Validation trong value object nên phản ánh quy tắc ổn định của khái niệm đó. Quy tắc phụ thuộc use case, ví dụ “chỉ cho thêm dòng khi đơn còn DRAFT”, thuộc aggregate root.

## 4. Viết custom converters cho Spring Data JDBC

Spring Data JDBC cần biết cách chuyển custom type sang giá trị JDBC và ngược lại. Với **OrderNumber** và **Sku**, database lưu chuỗi, còn domain dùng value object.

### 4.1. Converter ghi OrderNumber thành String

~~~java
import org.springframework.core.convert.converter.Converter;
import org.springframework.data.convert.WritingConverter;

@WritingConverter
public class OrderNumberToStringConverter
        implements Converter<OrderNumber, String> {

    @Override
    public String convert(OrderNumber source) {
        return source.value();
    }
}
~~~

### 4.2. Converter đọc String thành OrderNumber

~~~java
import org.springframework.core.convert.converter.Converter;
import org.springframework.data.convert.ReadingConverter;

@ReadingConverter
public class StringToOrderNumberConverter
        implements Converter<String, OrderNumber> {

    @Override
    public OrderNumber convert(String source) {
        return new OrderNumber(source);
    }
}
~~~

### 4.3. Converter cho SKU

~~~java
import org.springframework.core.convert.converter.Converter;
import org.springframework.data.convert.WritingConverter;

@WritingConverter
public class SkuToStringConverter implements Converter<Sku, String> {

    @Override
    public String convert(Sku source) {
        return source.value();
    }
}
~~~

~~~java
import org.springframework.core.convert.converter.Converter;
import org.springframework.data.convert.ReadingConverter;

@ReadingConverter
public class StringToSkuConverter implements Converter<String, Sku> {

    @Override
    public Sku convert(String source) {
        return new Sku(source);
    }
}
~~~

Annotation **@WritingConverter** và **@ReadingConverter** xác định chiều chuyển đổi. Điều này hữu ích khi source/target là các kiểu đơn giản như String và Spring có nhiều converter mặc định.

### 4.4. Đăng ký converter

Với cấu hình Java, có thể đăng ký converter thông qua **AbstractJdbcConfiguration**:

~~~java
import java.util.List;

import org.springframework.context.annotation.Configuration;
import org.springframework.data.jdbc.repository.config.AbstractJdbcConfiguration;

@Configuration
public class JdbcMappingConfiguration
        extends AbstractJdbcConfiguration {

    @Override
    protected List<?> userConverters() {
        return List.of(
                new OrderNumberToStringConverter(),
                new StringToOrderNumberConverter(),
                new SkuToStringConverter(),
                new StringToSkuConverter()
        );
    }
}
~~~

Khi dùng Spring Boot, kiểm tra cấu hình JDBC hiện tại trước khi thêm cấu hình tùy chỉnh. Đảm bảo custom converters được đưa vào **JdbcCustomConversions** mà Spring Data JDBC đang sử dụng; không tạo thêm một **DataAccessStrategy** hoặc mapping context độc lập ngoài ý muốn.

Không đăng ký cùng một converter nhiều lần ở nhiều configuration class. Giữ danh sách converter tập trung và viết test để xác nhận cả chiều đọc lẫn chiều ghi.

### 4.5. Converter nên làm gì?

Converter nên tập trung vào biểu diễn dữ liệu:

- Chuyển value object sang kiểu JDBC đơn giản.
- Parse kiểu JDBC thành value object.
- Chuẩn hóa định dạng lưu trữ ổn định.
- Báo lỗi khi dữ liệu lưu trữ không hợp lệ.

Không đặt quy tắc nghiệp vụ use case như kiểm tra tồn kho hoặc trạng thái đơn hàng trong converter. Converter được gọi bởi mapping infrastructure; nó không phải nơi điều phối repository hay transaction.

## 5. Tạo domain model cho aggregate

Trạng thái đơn hàng:

~~~java
public enum OrderStatus {
    DRAFT,
    CONFIRMED,
    CANCELLED
}
~~~

Entity con:

~~~java
import java.math.BigDecimal;
import java.util.Objects;

public record OrderLine(
        Sku sku,
        int quantity,
        BigDecimal unitPrice
) {

    public OrderLine {
        Objects.requireNonNull(sku, "sku is required");
        Objects.requireNonNull(unitPrice, "unit price is required");

        if (quantity <= 0) {
            throw new IllegalArgumentException(
                    "Quantity must be greater than zero");
        }
        if (unitPrice.signum() < 0) {
            throw new IllegalArgumentException(
                    "Unit price cannot be negative");
        }
    }

    public BigDecimal lineTotal() {
        return unitPrice.multiply(BigDecimal.valueOf(quantity));
    }
}
~~~

**OrderLine** tự bảo vệ các điều kiện cục bộ của một dòng hàng. Quy tắc “SKU không được lặp trong cùng đơn” cần được kiểm tra ở aggregate root vì nó phụ thuộc các dòng hàng khác.

### 5.1. Aggregate root với business methods

~~~java
import java.math.BigDecimal;
import java.util.ArrayList;
import java.util.List;
import java.util.Objects;

import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_order")
public record PurchaseOrder(
        @Id Long id,
        @Version Long version,
        @Column("order_number") OrderNumber orderNumber,
        @Column("customer_id") Long customerId,
        OrderStatus status,
        @Column("currency_code") String currencyCode,
        @Column("total_amount") BigDecimal totalAmount,
        @MappedCollection(
                idColumn = "purchase_order_id",
                keyColumn = "line_number"
        )
        List<OrderLine> lines
) {

    public PurchaseOrder {
        Objects.requireNonNull(orderNumber, "order number is required");
        Objects.requireNonNull(customerId, "customer is required");
        Objects.requireNonNull(status, "status is required");
        Objects.requireNonNull(currencyCode, "currency is required");
        Objects.requireNonNull(totalAmount, "total amount is required");
        lines = List.copyOf(lines == null ? List.of() : lines);

        if (totalAmount.signum() < 0) {
            throw new IllegalArgumentException(
                    "Total amount cannot be negative");
        }
    }

    public static PurchaseOrder draft(
            OrderNumber orderNumber,
            Long customerId,
            String currencyCode) {

        return new PurchaseOrder(
                null,
                null,
                orderNumber,
                customerId,
                OrderStatus.DRAFT,
                currencyCode,
                BigDecimal.ZERO,
                List.of()
        );
    }

    public PurchaseOrder addLine(
            Sku sku,
            int quantity,
            BigDecimal unitPrice) {

        ensureDraft();
        OrderLine newLine = new OrderLine(sku, quantity, unitPrice);

        boolean skuAlreadyExists = lines.stream()
                .anyMatch(line -> line.sku().equals(sku));

        if (skuAlreadyExists) {
            throw new IllegalStateException(
                    "SKU already exists in this order: " + sku.value());
        }

        List<OrderLine> updatedLines = new ArrayList<>(lines);
        updatedLines.add(newLine);

        BigDecimal updatedTotal = totalAmount.add(newLine.lineTotal());

        return new PurchaseOrder(
                id,
                version,
                orderNumber,
                customerId,
                status,
                currencyCode,
                updatedTotal,
                updatedLines
        );
    }

    public PurchaseOrder confirm() {
        ensureDraft();

        if (lines.isEmpty()) {
            throw new IllegalStateException(
                    "An order must contain at least one line");
        }

        BigDecimal calculatedTotal = lines.stream()
                .map(OrderLine::lineTotal)
                .reduce(BigDecimal.ZERO, BigDecimal::add);

        if (calculatedTotal.compareTo(totalAmount) != 0) {
            throw new IllegalStateException(
                    "Order total does not match its lines");
        }

        return new PurchaseOrder(
                id,
                version,
                orderNumber,
                customerId,
                OrderStatus.CONFIRMED,
                currencyCode,
                totalAmount,
                lines
        );
    }

    private void ensureDraft() {
        if (status != OrderStatus.DRAFT) {
            throw new IllegalStateException(
                    "Only draft orders can be changed");
        }
    }
}
~~~

Aggregate root giữ invariant:

- Chỉ đơn DRAFT mới được thêm dòng.
- Mỗi SKU chỉ xuất hiện một lần trong đơn.
- Số lượng và đơn giá hợp lệ.
- Tổng tiền được tính lại từ dòng hàng.
- Chỉ đơn có ít nhất một dòng mới được xác nhận.
- Đơn đã xác nhận không thể tiếp tục sửa theo các method hiện có.

Constructor canonical cũng kiểm tra dữ liệu cơ bản để tránh tạo instance không hợp lệ qua các đường khởi tạo khác. Domain method trả về instance mới và giữ ID/version đã đọc; repository sẽ quản lý version mới khi lưu.

Ví dụ này dùng cùng một currency cho toàn bộ đơn. Nếu nghiệp vụ hỗ trợ nhiều loại tiền trong một đơn, cần mô hình hóa currency ở từng dòng và định nghĩa quy tắc quy đổi/tổng tiền rõ ràng.

## 6. Tạo repository cho aggregate root

~~~java
import java.util.Optional;

import org.springframework.data.repository.CrudRepository;

public interface PurchaseOrderRepository
        extends CrudRepository<PurchaseOrder, Long> {

    Optional<PurchaseOrder> findByOrderNumber(OrderNumber orderNumber);
}
~~~

Repository chỉ được tạo cho **PurchaseOrder**, là aggregate root. Không tạo **OrderLineRepository** nếu dòng hàng chỉ được quản lý thông qua đơn.

Method **findByOrderNumber** dùng custom value object. Converter ghi OrderNumber thành String khi bind parameter và đọc String thành OrderNumber khi map kết quả. Unique constraint ở database bảo vệ giả định một order number chỉ thuộc một đơn.

Nếu finder theo order number không tìm thấy, kết quả là **Optional.empty()**. Nếu dữ liệu có nhiều hàng trùng, repository không tự chọn một hàng; đó là vi phạm invariant cần xử lý.

## 7. Application service điều phối repository và transaction

Command cho use case:

~~~java
import java.math.BigDecimal;

public record CreateOrderCommand(
        String orderNumber,
        Long customerId,
        String currencyCode
) {}

public record AddOrderLineCommand(
        String sku,
        int quantity,
        BigDecimal unitPrice
) {}
~~~

Exception nghiệp vụ:

~~~java
public class OrderNotFoundException extends RuntimeException {
    public OrderNotFoundException(Long id) {
        super("Order not found: " + id);
    }
}
~~~

Service:

~~~java
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class PurchaseOrderService {

    private final PurchaseOrderRepository repository;

    public PurchaseOrderService(PurchaseOrderRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public PurchaseOrder createDraft(CreateOrderCommand command) {
        PurchaseOrder draft = PurchaseOrder.draft(
                new OrderNumber(command.orderNumber()),
                command.customerId(),
                command.currencyCode()
        );

        return repository.save(draft);
    }

    @Transactional
    public PurchaseOrder addLine(
            Long orderId,
            AddOrderLineCommand command) {

        PurchaseOrder current = repository.findById(orderId)
                .orElseThrow(() -> new OrderNotFoundException(orderId));

        PurchaseOrder changed = current.addLine(
                new Sku(command.sku()),
                command.quantity(),
                command.unitPrice()
        );

        return repository.save(changed);
    }

    @Transactional
    public PurchaseOrder confirm(Long orderId) {
        PurchaseOrder current = repository.findById(orderId)
                .orElseThrow(() -> new OrderNotFoundException(orderId));

        return repository.save(current.confirm());
    }
}
~~~

Mỗi method biểu diễn một use case. Service tải aggregate, gọi domain method rồi lưu. **@Transactional** đặt boundary cho cả lần đọc và ghi, giúp các thao tác thuộc use case hoàn tất cùng nhau.

Không đưa business rule vào repository method hoặc converter. Repository là persistence abstraction; domain model quyết định trạng thái nào hợp lệ.

### 7.1. Tại sao gọi save sau domain method?

Spring Data JDBC không có dirty checking kiểu JPA. Sau khi gọi **current.addLine(...)**, ứng dụng có instance mới **changed**; phải gọi **repository.save(changed)** để ghi xuống database.

Với aggregate immutable, giữ instance trả về từ **save** vì nó có thể chứa ID/version do Spring Data JDBC quản lý. Không tiếp tục dùng object đầu vào với version cũ cho lần ghi tiếp theo.

### 7.2. Optimistic locking

**@Version** trên root giúp phát hiện hai transaction cùng cập nhật một đơn từ cùng version. Khi transaction đầu tiên lưu thành công, version tăng. Transaction thứ hai dùng version cũ sẽ không cập nhật được và nhận lỗi optimistic locking.

Đây là lý do version thuộc aggregate root. Các dòng hàng thay đổi thông qua root nên cạnh tranh được phát hiện ở ranh giới aggregate.

## 8. Cấu hình Spring Boot

Với Spring Boot, dependency thường gồm:

~~~xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-jdbc</artifactId>
</dependency>

<dependency>
    <groupId>org.postgresql</groupId>
~~~

Boot BOM quản lý version Spring Data JDBC và driver khi có trong dependency management. Không đặt version riêng cho từng module Spring Data nếu không có lý do tương thích cụ thể.

Cấu hình kết nối ví dụ:

~~~yaml
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/shop
    username: shop_app
    password: configure-through-secret-store
  sql:
    init:
      mode: never
~~~

Ví dụ đặt schema bằng Flyway hoặc Liquibase. Khi dùng migration tool, không đồng thời bật cơ chế schema initialization khác có thể tạo cùng bảng.

## 9. Migration schema và dữ liệu hiện hữu

Nếu ứng dụng đã có dữ liệu đơn hàng, cần đảm bảo schema mới tương thích với dữ liệu cũ:

1. Xác nhận tên bảng/cột và kiểu dữ liệu thực tế.
2. Kiểm tra mọi hàng có **version** hợp lệ trước khi bật optimistic locking.
3. Chuẩn hóa **order_number** và **sku** theo format value object.
4. Xử lý dữ liệu trùng trước khi thêm unique constraint.
5. Xác nhận dòng hàng có **line_number** duy nhất trong từng đơn.
6. Đối chiếu tổng tiền lưu trữ với tổng dòng hàng.
7. Chạy migration trên bản sao dữ liệu hoặc staging.

Nếu thêm cột version vào bảng hiện hữu:

~~~sql
ALTER TABLE purchase_order
ADD COLUMN version BIGINT NOT NULL DEFAULT 0;
~~~

Đây là ví dụ PostgreSQL. Kiểm tra lock duration và chiến lược backfill theo kích thước bảng/phiên bản database. Với bảng lớn, migration có thể cần chia giai đoạn để giảm lock.

Không bật converter validation quá chặt trước khi dữ liệu cũ được chuẩn hóa. Ví dụ nếu database có SKU chữ thường hoặc khoảng trắng, converter mới có thể chuẩn hóa về uppercase; nhưng cần xác định collation/uniqueness và dữ liệu trùng sau chuẩn hóa.

## 10. Kiểm thử business rules độc lập với database

Các invariant quan trọng nên được kiểm tra bằng unit test domain:

~~~java
import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;

import java.math.BigDecimal;
import org.junit.jupiter.api.Test;

class PurchaseOrderTest {

    private PurchaseOrder draft() {
        return PurchaseOrder.draft(
                new OrderNumber("PO-2026-0001"),
                42L,
                "USD"
        );
    }

    @Test
    void addsLineAndRecalculatesTotal() {
        PurchaseOrder updated = draft().addLine(
                new Sku("CHAIR-01"),
                2,
                new BigDecimal("19.50")
        );

        assertThat(updated.lines()).hasSize(1);
        assertThat(updated.totalAmount())
                .isEqualByComparingTo("39.00");
    }

    @Test
    void rejectsDuplicateSku() {
        PurchaseOrder withLine = draft().addLine(
                new Sku("CHAIR-01"),
                1,
                new BigDecimal("19.50")
        );

        assertThatThrownBy(() -> withLine.addLine(
                new Sku("CHAIR-01"),
                1,
                new BigDecimal("19.50")
        )).isInstanceOf(IllegalStateException.class);
    }

    @Test
    void cannotConfirmAnEmptyOrder() {
        assertThatThrownBy(() -> draft().confirm())
                .isInstanceOf(IllegalStateException.class);
    }

    @Test
    void cannotAddLineAfterConfirmation() {
        PurchaseOrder confirmed = draft()
                .addLine(
                        new Sku("CHAIR-01"),
                        1,
                        new BigDecimal("19.50")
                )
                .confirm();

        assertThatThrownBy(() -> confirmed.addLine(
                new Sku("DESK-01"),
                1,
                new BigDecimal("50.00")
        )).isInstanceOf(IllegalStateException.class);
    }
}
~~~

Unit test không cần Spring context hoặc database. Nó kiểm tra quy tắc domain một cách nhanh và xác định.

## 11. Kiểm thử converter

Converter nên được kiểm thử riêng:

~~~java
import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;

import org.junit.jupiter.api.Test;

class OrderNumberConverterTest {

    private final OrderNumberToStringConverter writer =
            new OrderNumberToStringConverter();
    private final StringToOrderNumberConverter reader =
            new StringToOrderNumberConverter();

    @Test
    void convertsOrderNumberToDatabaseStringAndBack() {
        OrderNumber orderNumber = new OrderNumber("po-2026-0001");

        String stored = writer.convert(orderNumber);
        OrderNumber restored = reader.convert(stored);

        assertThat(stored).isEqualTo("PO-2026-0001");
        assertThat(restored).isEqualTo(orderNumber);
    }

    @Test
    void rejectsInvalidStoredValue() {
        assertThatThrownBy(() -> reader.convert("INVALID"))
                .isInstanceOf(IllegalArgumentException.class);
    }
}
~~~

Test này xác nhận chiều ghi lưu đúng format, chiều đọc khôi phục đúng value object và dữ liệu lưu không hợp lệ bị từ chối.

Nếu converter cần hỗ trợ dữ liệu cũ nhiều format, viết parser có quy tắc tương thích rõ ràng và test từng format. Không âm thầm trả về một giá trị mặc định khi parse thất bại.

## 12. Kiểm thử mapping và repository với database

**@DataJdbcTest** có thể dùng để kiểm tra repository, mapping và converter. Import cấu hình converter vào test slice:

~~~java
import static org.assertj.core.api.Assertions.assertThat;

import java.math.BigDecimal;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.data.jdbc.DataJdbcTest;
import org.springframework.context.annotation.Import;

@DataJdbcTest
@Import(JdbcMappingConfiguration.class)
class PurchaseOrderRepositoryTest {

    @Autowired
    PurchaseOrderRepository repository;

    @Test
    void savesAndReloadsAggregateUsingCustomConverters() {
        PurchaseOrder draft = PurchaseOrder.draft(
                new OrderNumber("PO-2026-0002"),
                42L,
                "USD"
        ).addLine(
                new Sku("CHAIR-02"),
                2,
                new BigDecimal("25.00")
        );

        PurchaseOrder saved = repository.save(draft);

        PurchaseOrder loaded = repository
                .findByOrderNumber(new OrderNumber("PO-2026-0002"))
                .orElseThrow();

        assertThat(loaded.id()).isEqualTo(saved.id());
        assertThat(loaded.orderNumber())
                .isEqualTo(new OrderNumber("PO-2026-0002"));
        assertThat(loaded.lines()).hasSize(1);
        assertThat(loaded.lines().get(0).sku())
                .isEqualTo(new Sku("CHAIR-02"));
        assertThat(loaded.totalAmount())
                .isEqualByComparingTo("50.00");
    }
}
~~~

Test chứng minh converter hoạt động ở cả chiều ghi và đọc thông qua repository, không chỉ khi gọi trực tiếp converter.

Nếu production dùng PostgreSQL, nên chạy integration test với PostgreSQL qua Testcontainers hoặc database test tương đương. Embedded database có thể khác về identity, type mapping, precision, constraint và SQL dialect.

## 13. Kiểm thử service transaction và optimistic locking

Test service nên gọi Spring bean từ ApplicationContext để transaction proxy hoạt động:

~~~java
@SpringBootTest
class PurchaseOrderServiceIntegrationTest {

    @Autowired
    PurchaseOrderService service;

    @Autowired
    PurchaseOrderRepository repository;

    @Test
    void createsAddsLineAndConfirmsOrder() {
        PurchaseOrder created = service.createDraft(
                new CreateOrderCommand(
                        "PO-2026-0003",
                        42L,
                        "USD"
                )
        );

        PurchaseOrder withLine = service.addLine(
                created.id(),
                new AddOrderLineCommand(
                        "DESK-01",
                        1,
                        new BigDecimal("120.00")
                )
        );

        PurchaseOrder confirmed = service.confirm(withLine.id());

        assertThat(confirmed.status()).isEqualTo(OrderStatus.CONFIRMED);
        assertThat(confirmed.totalAmount())
                .isEqualByComparingTo("120.00");
        assertThat(repository.findById(created.id())).isPresent();
    }
}
~~~

Trong test thực tế, cần seed/cleanup dữ liệu, xử lý order number unique và dùng database engine phù hợp. Không đặt **@Transactional** trên test nếu mục tiêu là quan sát transaction độc lập của từng service call sau khi method đã kết thúc.

Để kiểm thử optimistic locking, tạo hai bản sao aggregate cùng version:

1. Đọc cùng một order hai lần trong hai transaction độc lập.
2. Lưu thay đổi của bản sao thứ nhất.
3. Thử lưu bản sao thứ hai với version cũ.
4. Xác nhận lần lưu thứ hai thất bại bằng optimistic locking exception.

Test cạnh tranh cần transaction/connection độc lập; không mô phỏng hai transaction bằng hai object trong cùng một persistence operation.

## 14. Thêm custom query khi repository cần tìm kiếm

Không phải mọi query đều cần method CRUD. Ví dụ tìm đơn hàng theo khách hàng và trạng thái:

~~~java
public interface PurchaseOrderRepository
        extends CrudRepository<PurchaseOrder, Long> {

    Optional<PurchaseOrder> findByOrderNumber(OrderNumber orderNumber);

    List<PurchaseOrder> findByCustomerIdAndStatusOrderByIdDesc(
            Long customerId,
            OrderStatus status
    );
}
~~~

Nếu derived query không diễn đạt được SQL cần thiết, dùng **@Query**:

~~~java
@Query("""
    SELECT id, version, order_number, customer_id, status,
           currency_code, total_amount
    FROM purchase_order
    WHERE customer_id = :customerId
      AND status = :status
    ORDER BY id DESC
    """)
List<PurchaseOrder> findByCustomerAndStatus(
        @Param("customerId") Long customerId,
        @Param("status") OrderStatus status
);
~~~

Custom query phải trả các cột cần thiết cho mapping của kiểu trả về. Với aggregate có collection child, query root không tự động đảm bảo mọi child được tải giống như repository findById; xác nhận mapping behavior của query và phiên bản Spring Data JDBC đang dùng. Nếu query chỉ cần projection, trả DTO/projection phù hợp thay vì cố ánh xạ thành aggregate không đầy đủ.

## 15. Đặt quy tắc nghiệp vụ ở đúng lớp

Phân chia trách nhiệm:

| Thành phần | Trách nhiệm |
| --- | --- |
| Value object | Validation và chuẩn hóa của một giá trị đơn |
| Entity con | Invariant cục bộ của dòng hàng |
| Aggregate root | Invariant giữa nhiều dòng và trạng thái toàn đơn |
| Repository | Tìm/lưu aggregate, query persistence |
| Converter | Chuyển domain type sang/về JDBC type |
| Application service | Điều phối use case, repository và transaction |
| Controller/API | Chuyển request/response và mã lỗi giao thức |
| Database constraint | Bảo vệ invariant dữ liệu ở cấp database |

Ví dụ:

- SKU đúng format: **Sku**.
- Số lượng lớn hơn 0: **OrderLine**.
- Không trùng SKU trong cùng đơn: **PurchaseOrder**.
- Đơn chỉ xác nhận khi có dòng: **PurchaseOrder.confirm()**.
- Order number duy nhất giữa các transaction: unique constraint.
- Tìm đơn theo mã: **PurchaseOrderRepository**.
- Chuyển OrderNumber sang VARCHAR: converter.
- Tạo đơn và lưu: **PurchaseOrderService** với **@Transactional**.

Không đặt toàn bộ validation trong controller. Use case có thể được gọi từ REST, message consumer, scheduler hoặc batch; domain invariant phải luôn được bảo vệ.

## 16. Lỗi thường gặp

| Triệu chứng | Nguyên nhân có thể | Cách xử lý |
| --- | --- | --- |
| Không map được custom type | Converter chưa đăng ký hoặc sai chiều | Kiểm tra userConverters, @ReadingConverter, @WritingConverter |
| Ghi được nhưng đọc lỗi | Thiếu reading converter hoặc dữ liệu cũ không hợp lệ | Viết converter đọc và test round-trip |
| Converter được gọi sai chiều | Source/target đơn giản gây mơ hồ | Đánh dấu converter đọc/ghi rõ ràng |
| Value object không được chuẩn hóa | Chỉ normalize trong converter ghi | Đặt invariant trong constructor/value object |
| Dữ liệu sai lọt qua khi đọc | Converter bỏ qua validation | Parse và validate giá trị lưu trữ |
| Repository không lưu child | Sai aggregate boundary hoặc mapping collection | Kiểm tra @MappedCollection, foreign key và key column |
| Dòng hàng mất thứ tự | Không lưu collection index/key | Dùng key column và kiểm tra mapping |
| Tổng tiền không khớp dòng | Có đường cập nhật total độc lập | Tính total trong aggregate và kiểm tra invariant |
| Hai request ghi đè nhau | Thiếu version hoặc không xử lý optimistic lock | Dùng @Version và xử lý conflict |
| Rule chỉ được kiểm tra ở controller | Use case khác bỏ qua validation | Đưa invariant vào value object/aggregate |
| Test repository không thấy converter | Test slice không import cấu hình custom | Import cấu hình mapping vào test |
| Schema cũ không tương thích | Mapping giả định tên/kiểu cột khác | Khớp annotation với schema và kiểm thử migration |

## 17. Quy trình triển khai trong dự án thật

1. Chọn một use case và mô tả contract nghiệp vụ.
2. Xác định aggregate root, entity con và value object.
3. Kiểm tra schema hiện tại, khóa, nullability và dữ liệu cũ.
4. Viết migration cần thiết và xử lý duplicate/invalid data.
5. Tạo value object với validation ổn định.
6. Viết converter đọc/ghi và đăng ký tập trung.
7. Tạo aggregate root với business methods bảo vệ invariant.
8. Tạo repository cho root và finder phù hợp.
9. Tạo service method có transaction boundary rõ.
10. Viết unit test cho business rules và converter.
11. Viết repository integration test trên database mục tiêu.
12. Viết service transaction/optimistic locking test.
13. Đo query count, latency và hành vi ghi.
14. Triển khai theo giai đoạn và theo dõi lỗi mapping/runtime.

Nếu use case có query báo cáo hoặc bulk SQL, giữ chúng trong JdbcTemplate khi đó là abstraction phù hợp. Không ép mọi truy vấn thành repository chỉ để có một kiểu code thống nhất.

## 18. Bài tập thực hành

**Bài 1 — Value object.** Tạo OrderNumber và Sku có validation. Viết test cho giá trị hợp lệ, chữ thường, khoảng trắng, chuỗi rỗng và định dạng sai.

**Bài 2 — Custom converters.** Viết converter đọc/ghi cho hai value object. Xác nhận round-trip và dữ liệu không hợp lệ bị từ chối.

**Bài 3 — Mapping aggregate.** Tạo schema purchase_order và order_line. Ánh xạ root và collection child bằng @MappedCollection.

**Bài 4 — Repository.** Tạo PurchaseOrderRepository, finder theo OrderNumber và test unique constraint.

**Bài 5 — Business rules.** Triển khai thêm dòng, từ chối SKU trùng, kiểm tra quantity/price và tính tổng.

**Bài 6 — State transition.** Triển khai DRAFT → CONFIRMED. Kiểm tra không xác nhận đơn rỗng và không sửa đơn đã xác nhận.

**Bài 7 — Service transaction.** Viết service create/add/confirm với @Transactional. Làm một bước thất bại và xác nhận thay đổi trước đó rollback.

**Bài 8 — Optimistic locking.** Thêm @Version, tạo hai transaction cùng đọc một đơn và xác nhận transaction dùng version cũ bị từ chối.

**Bài 9 — Database migration.** Thêm version vào bảng hiện hữu, chuẩn hóa order number/SKU và tạo unique constraint sau khi xử lý dữ liệu trùng.

**Bài 10 — Repository query.** Thêm finder theo customer/status. Kiểm tra cardinality, sort và plan trên dữ liệu đại diện.

**Bài 11 — Integration test.** Chạy repository/converter test với PostgreSQL hoặc database production mục tiêu; so sánh behavior với embedded database nếu dự án có dùng.

**Bài 12 — Mở rộng use case.** Thêm kiểm tra customer tồn tại hoặc tồn kho bằng repository khác trong cùng service transaction. Xác nhận toàn bộ use case rollback khi bước cuối thất bại.
