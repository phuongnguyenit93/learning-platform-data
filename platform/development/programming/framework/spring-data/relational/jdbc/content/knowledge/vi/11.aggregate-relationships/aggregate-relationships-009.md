# Thêm, thay thế, bỏ phần tử con và vòng đời dữ liệu tương ứng

Trong Spring Data JDBC, các phần tử con thuộc một aggregate được quản lý thông qua **aggregate root**. Ví dụ, một §PurchaseOrder§ sở hữu danh sách §OrderLine§. Khi nghiệp vụ thêm, thay thế hoặc bỏ một dòng hàng, ứng dụng thay đổi trạng thái của aggregate root rồi lưu root bằng repository.

Điểm quan trọng là **vòng đời của phần tử con gắn với vòng đời aggregate sở hữu nó**:

- Phần tử mới chỉ trở thành dữ liệu được lưu khi aggregate root được persist.
- Phần tử bị thay thế hoặc bỏ khỏi collection sẽ không còn thuộc trạng thái aggregate hiện tại; thay đổi đó được đồng bộ xuống database khi lưu root.
- Khi aggregate root bị xóa, các phần tử được sở hữu bên trong cũng được xử lý theo vòng đời aggregate.
- Một phần tử cần được sửa, truy vấn hoặc tồn tại độc lập thường xuyên có thể không còn phù hợp với mô hình entity con được sở hữu.

Bài học dùng ví dụ đơn hàng có danh sách dòng hàng để giải thích thao tác thêm, thay thế và xóa phần tử con, cách Spring Data JDBC đồng bộ collection, ảnh hưởng đến SQL và những dấu hiệu cần xem lại ranh giới aggregate.

## 1. Aggregate root quản lý phần tử con

Một aggregate là ranh giới nhất quán nghiệp vụ. Aggregate root là điểm truy cập chính để tạo, thay đổi và lưu các thành phần thuộc ranh giới đó.

Ví dụ đơn hàng:

§§§text
PurchaseOrder aggregate
┌─────────────────────────────────────────┐
│ PurchaseOrder (aggregate root)          │
│ id                                      │
│ status                                  │
│                                         │
│ lines                                   │
│   ├── OrderLine: SKU-A, quantity = 2    │
│   ├── OrderLine: SKU-B, quantity = 1    │
│   └── OrderLine: SKU-C, quantity = 4    │
└─────────────────────────────────────────┘
                 |
                 v
         PurchaseOrderRepository
                 |
                 v
           Spring Data JDBC
                 |
                 v
        purchase_orders + order_lines
§§§

§PurchaseOrder§ kiểm soát các quy tắc như:

- Chỉ cho sửa dòng hàng khi đơn hàng còn ở trạng thái cho phép chỉnh sửa.
- Số lượng phải lớn hơn 0.
- Không thêm một dòng có SKU không hợp lệ.
- Chỉ xác nhận đơn hàng khi có ít nhất một dòng hàng.
- Khi bỏ một dòng, trạng thái tổng thể của đơn hàng phải vẫn hợp lệ.

§OrderLine§ là phần tử được sở hữu. Trong ví dụ này, nó không có repository riêng và caller không được tự ý ghi trực tiếp một dòng hàng mà bỏ qua quy tắc của đơn hàng.

**Có bảng con không đồng nghĩa với có aggregate root riêng.** Một aggregate có thể được lưu trên nhiều bảng; repository thường được định nghĩa cho root.

## 2. Ánh xạ collection phần tử con

Spring Data JDBC dùng §@MappedCollection§ để ánh xạ collection các entity được sở hữu vào bảng liên quan.

Ví dụ schema PostgreSQL:

§§§sql
CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    status VARCHAR(30) NOT NULL
);

CREATE TABLE order_lines (
    order_id BIGINT NOT NULL
        REFERENCES purchase_orders(id),
    line_position INTEGER NOT NULL,
    sku VARCHAR(80) NOT NULL,
    quantity INTEGER NOT NULL CHECK (quantity > 0),
    PRIMARY KEY (order_id, line_position)
);
§§§

Bảng §order_lines§ có:

- §order_id§: khóa ngoại trỏ về aggregate root.
- §line_position§: vị trí của phần tử trong §List§.
- §sku§ và §quantity§: dữ liệu của dòng hàng.
- Khóa chính ghép §(order_id, line_position)§: định danh một phần tử theo vị trí trong danh sách của đơn hàng.

Ánh xạ Java:

§§§java
import org.springframework.data.relational.core.mapping.Table;

@Table("order_lines")
public record OrderLine(String sku, int quantity) {

    public OrderLine {
        if (sku == null || sku.isBlank()) {
            throw new IllegalArgumentException("SKU is required");
        }
        if (quantity <= 0) {
            throw new IllegalArgumentException("Quantity must be positive");
        }
    }
}
§§§

Aggregate root:

§§§java
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_orders")
public class PurchaseOrder {

    @Id
    private Long id;

    private String status;

    @MappedCollection(
            idColumn = "order_id",
            keyColumn = "line_position"
    )
    private List<OrderLine> lines = new ArrayList<>();

    protected PurchaseOrder() {
    }

    public PurchaseOrder(String status) {
        this.status = status;
    }

    public Long getId() {
        return id;
    }

    public String getStatus() {
        return status;
    }

    public List<OrderLine> getLines() {
        return Collections.unmodifiableList(lines);
    }
}
§§§

§idColumn§ chỉ định cột khóa ngoại trong bảng con; §keyColumn§ chỉ định cột lưu vị trí phần tử trong danh sách. Spring Data JDBC dùng metadata này để khôi phục collection khi đọc aggregate và đồng bộ collection khi ghi.

## 3. Thêm phần tử con

Khi nghiệp vụ thêm một dòng hàng, cần thực hiện thay đổi thông qua phương thức của aggregate root.

Ví dụ thêm phương thức:

§§§java
public void addLine(String sku, int quantity) {
    ensureEditable();
    lines.add(new OrderLine(sku, quantity));
}

private void ensureEditable() {
    if (!"DRAFT".equals(status)) {
        throw new IllegalStateException(
                "Only draft orders can be changed"
        );
    }
}
§§§

Sau đó service tải root, thêm dòng và lưu lại:

§§§java
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class PurchaseOrderService {

    private final PurchaseOrderRepository orders;

    public PurchaseOrderService(PurchaseOrderRepository orders) {
        this.orders = orders;
    }

    @Transactional
    public PurchaseOrder addLine(
            Long orderId, String sku, int quantity
    ) {
        PurchaseOrder order = orders.findById(orderId)
                .orElseThrow();

        order.addLine(sku, quantity);

        return orders.save(order);
    }
}
§§§

Luồng xử lý:

§§§text
Tải PurchaseOrder
       |
       v
order.addLine("SKU-D", 3)
       |
       v
Collection trong bộ nhớ có thêm OrderLine
       |
       v
orders.save(order)
       |
       v
Spring Data JDBC đồng bộ aggregate xuống database
§§§

Điểm cần nhớ: §lines.add(...)§ chỉ thay đổi object trong bộ nhớ. Dữ liệu database chỉ được cập nhật khi có thao tác persist thành công. Nếu request thất bại trước khi save, phần tử mới chưa được ghi vào database.

### 3.1. Thêm vào aggregate mới

Với aggregate chưa có ID, có thể tạo root cùng các phần tử con rồi lưu một lần:

§§§java
PurchaseOrder order = new PurchaseOrder("DRAFT");

order.addLine("SKU-A", 2);
order.addLine("SKU-B", 1);

PurchaseOrder saved = orders.save(order);
§§§

Spring Data JDBC tạo hàng root, nhận ID được database cấp rồi lưu các phần tử con với khóa ngoại tương ứng. Dùng aggregate trả về từ §save§ để lấy ID sau khi lưu.

### 3.2. Thêm nhiều phần tử trong một thao tác

Có thể thêm nhiều dòng trong một lần xử lý nghiệp vụ:

§§§java
@Transactional
public PurchaseOrder addLines(
        Long orderId, List<NewOrderLine> requestedLines
) {
    PurchaseOrder order = orders.findById(orderId)
            .orElseThrow();

    for (NewOrderLine requested : requestedLines) {
        order.addLine(requested.sku(), requested.quantity());
    }

    return orders.save(order);
}
§§§

Nếu một phần tử không hợp lệ và phương thức ném exception, transaction có thể rollback toàn bộ thao tác theo quy tắc rollback đã cấu hình. Cần tránh lưu từng phần tử qua một repository riêng vì điều đó bỏ qua ranh giới nhất quán của aggregate.

## 4. Thay thế phần tử con

Thay thế phần tử là thay đổi nội dung hoặc vị trí của một phần tử trong collection, nhưng vẫn giữ nó trong aggregate.

Ví dụ thay số lượng dòng hàng thứ nhất:

§§§java
public void replaceLine(int position, String sku, int quantity) {
    ensureEditable();

    if (position < 0 || position >= lines.size()) {
        throw new IndexOutOfBoundsException(position);
    }

    lines.set(position, new OrderLine(sku, quantity));
}
§§§

Service:

§§§java
@Transactional
public PurchaseOrder replaceLine(
        Long orderId,
        int position,
        String sku,
        int quantity
) {
    PurchaseOrder order = orders.findById(orderId)
            .orElseThrow();

    order.replaceLine(position, sku, quantity);

    return orders.save(order);
}
§§§

Trạng thái trước và sau:

§§§text
Trước:
Order 501
  position 0 -> SKU-A, quantity 2
  position 1 -> SKU-B, quantity 1

Thay thế position 1:
Order 501
  position 0 -> SKU-A, quantity 2
  position 1 -> SKU-C, quantity 5
§§§

Trong mô hình §List§, §position§ là key của phần tử trong collection. Thay phần tử ở vị trí đó có nghĩa nội dung tại vị trí ấy thay đổi.

### 4.1. Thay thế khác với sửa một thuộc tính

Với object con bất biến như record, ta thường tạo một instance mới rồi đặt vào collection. Về ý nghĩa domain, đây là thay thế giá trị ở vị trí tương ứng.

Với object con mutable, có thể thay đổi thuộc tính của object hiện tại qua một phương thức có kiểm soát. Tuy nhiên, việc thay đổi object trong bộ nhớ vẫn cần được lưu thông qua root.

Dù chọn cách nào, cần đảm bảo:

- Không để caller sửa trực tiếp collection bên trong root.
- Kiểm tra quy tắc nghiệp vụ trước khi thay thế.
- Giữ đúng vị trí nếu thứ tự có ý nghĩa.
- Không vô tình thay đổi identity hoặc dữ liệu lịch sử nếu phần tử có yêu cầu identity riêng.

### 4.2. Thay thế toàn bộ collection

Đôi khi nghiệp vụ gửi một danh sách mới thay cho toàn bộ danh sách cũ. Có thể định nghĩa phương thức rõ nghĩa:

§§§java
public void replaceAllLines(List<OrderLine> replacement) {
    ensureEditable();

    if (replacement == null) {
        throw new IllegalArgumentException(
                "Replacement lines must not be null"
        );
    }

    this.lines = new ArrayList<>(replacement);
}
§§§

Phương thức này có ý nghĩa khác với thêm một phần tử. Nó thay toàn bộ trạng thái collection hiện tại bằng collection mới.

Trước khi cho phép thay toàn bộ, cần kiểm tra:

- Danh sách mới có hợp lệ không?
- Có dòng nào đang được giữ lại về mặt nghiệp vụ không?
- Có cần lưu dấu vết các dòng đã bị thay thế không?
- Tổng tiền, thuế, tồn kho hoặc trạng thái đơn hàng cần tính lại thế nào?
- API có đang gửi danh sách đầy đủ hay chỉ gửi một phần?

Không nên coi một request PATCH chứa vài phần tử là danh sách đầy đủ rồi vô tình xóa các phần tử không có trong request.

## 5. Bỏ phần tử con khỏi collection

Khi một phần tử không còn thuộc aggregate, hãy bỏ nó qua phương thức của root.

Ví dụ:

§§§java
public void removeLine(int position) {
    ensureEditable();

    if (position < 0 || position >= lines.size()) {
        throw new IndexOutOfBoundsException(position);
    }

    lines.remove(position);
}
§§§

Service:

§§§java
@Transactional
public PurchaseOrder removeLine(Long orderId, int position) {
    PurchaseOrder order = orders.findById(orderId)
            .orElseThrow();

    order.removeLine(position);

    return orders.save(order);
}
§§§

Trước khi bỏ:

§§§text
Order 501
  position 0 -> SKU-A, quantity 2
  position 1 -> SKU-B, quantity 1
  position 2 -> SKU-C, quantity 4
§§§

Sau khi bỏ position 1:

§§§text
Order 501
  position 0 -> SKU-A, quantity 2
  position 1 -> SKU-C, quantity 4
§§§

Khi save aggregate, trạng thái collection mới được đồng bộ xuống bảng con. Phần tử đã bị bỏ không còn thuộc aggregate và hàng dữ liệu tương ứng sẽ được xử lý theo cơ chế persistence của Spring Data JDBC.

**Bỏ khỏi collection trong Java chưa đồng nghĩa xóa ngay trong database.** Nếu chưa gọi save hoặc transaction rollback, dữ liệu đã lưu vẫn còn nguyên.

### 5.1. Bỏ theo điều kiện thay vì vị trí

Nếu collection là §List§ nhưng nghiệp vụ định danh dòng bằng SKU, có thể tìm phần tử theo điều kiện:

§§§java
public void removeLineBySku(String sku) {
    ensureEditable();

    boolean removed = lines.removeIf(
            line -> line.sku().equals(sku)
    );

    if (!removed) {
        throw new IllegalArgumentException(
                "Line not found: " + sku
        );
    }
}
§§§

Nếu một SKU có thể xuất hiện nhiều lần trong một đơn hàng, cách trên sẽ xóa tất cả dòng trùng SKU. Nếu nghiệp vụ chỉ cho phép xóa đúng một dòng, cần một định danh dòng rõ ràng hoặc kiểm tra số lượng kết quả trước khi xóa.

Đừng dùng vị trí list làm identity nghiệp vụ nếu vị trí có thể thay đổi và các thao tác bên ngoài cần tham chiếu ổn định đến từng dòng.

### 5.2. Collection rỗng sau khi bỏ phần tử cuối

Sau khi xóa phần tử cuối cùng, collection có thể trở thành rỗng:

§§§java
order.removeLine(0);

if (order.getLines().isEmpty()) {
    // Đơn hàng hiện không có dòng hàng.
}
§§§

Điều đó không nhất thiết có nghĩa aggregate root phải bị xóa. Root vẫn có thể tồn tại ở trạng thái DRAFT để người dùng thêm dòng khác. Nếu nghiệp vụ không cho phép đơn hàng rỗng được xác nhận, hãy kiểm tra quy tắc ở phương thức §confirm§.

Không nên biến collection rỗng thành §null§ chỉ để biểu thị không có phần tử. Collection rỗng thường là cách biểu diễn rõ ràng hơn cho “aggregate tồn tại nhưng hiện không có phần tử con”.

## 6. Vòng đời của phần tử con trong Spring Data JDBC

Vòng đời của entity con được sở hữu gắn với aggregate root.

| Thao tác domain | Trạng thái trong bộ nhớ | Khi lưu aggregate |
| --- | --- | --- |
| Tạo aggregate mới cùng phần tử con | Root mới, collection có phần tử | Insert root và các phần tử con. |
| Thêm phần tử vào root đã tồn tại | Collection tăng phần tử | Đồng bộ collection mới xuống database. |
| Thay thế phần tử | Collection có instance/giá trị mới ở vị trí tương ứng | Đồng bộ trạng thái collection mới. |
| Bỏ phần tử | Collection không còn phần tử đó | Hàng con tương ứng được loại khỏi trạng thái aggregate đã lưu. |
| Xóa root | Root không còn tồn tại | Các entity được sở hữu cũng được xóa theo aggregate. |
| Chỉ sửa object nhưng chưa save | Bộ nhớ thay đổi, database chưa đổi | Chưa có thao tác ghi tương ứng. |
| Save thất bại và transaction rollback | Thao tác persistence không commit | Database giữ trạng thái trước transaction. |

### 6.1. Entity con không có vòng đời độc lập

Trong ví dụ §OrderLine§:

- Không tạo §OrderLineRepository§.
- Không cho phép service bất kỳ gọi save trực tiếp một dòng.
- Không dùng ID của dòng như một tham chiếu công khai nếu dòng không có identity nghiệp vụ.
- Thao tác thêm, sửa, bỏ đều thông qua §PurchaseOrder§.

Điều này giữ cho các quy tắc như tổng số lượng, trạng thái đơn hàng và điều kiện xác nhận được kiểm soát tại một điểm.

### 6.2. Xóa root và các entity được sở hữu

Khi xóa §PurchaseOrder§, Spring Data JDBC xử lý các entity được tham chiếu bên trong aggregate theo vòng đời của root. Điều này khác với xóa một aggregate độc lập được root chỉ tham chiếu bằng ID.

Ví dụ:

§§§text
PurchaseOrder 501
  ├── OrderLine A
  ├── OrderLine B
  └── OrderLine C

orders.deleteById(501)

PurchaseOrder 501 bị xóa
OrderLine A, B, C được xử lý theo ownership
Customer được tham chiếu bởi order (nếu có) vẫn tồn tại
§§§

Nếu các entity con có dữ liệu được bảng khác tham chiếu bằng khóa ngoại, việc xóa/thay thế có thể bị database ngăn lại. Đó là dấu hiệu cần đánh giá xem entity con có thực sự nên là thành phần được sở hữu hay cần trở thành aggregate riêng.

## 7. Spring Data JDBC đồng bộ collection như thế nào?

Một khác biệt quan trọng của Spring Data JDBC so với ORM có persistence context là **không có dirty checking liên tục trên object graph**.

Khi lưu aggregate đã tồn tại, Spring Data JDBC cần đồng bộ trạng thái aggregate được truyền vào. Với các entity được tham chiếu bên trong aggregate, cơ chế cập nhật collection thường là:

1. Cập nhật hàng aggregate root.
2. Xóa các hàng entity con được sở hữu hiện tại theo aggregate.
3. Chèn lại các entity con theo trạng thái collection mới.

Chiến lược này giúp persistence model rõ ràng: database phản ánh trạng thái aggregate được gửi vào. Nhưng nó cũng có hệ quả hiệu năng và identity.

Ví dụ một đơn hàng có 100 dòng, chỉ thay đổi số lượng một dòng. Không nên mặc định Spring Data JDBC chỉ phát một câu §UPDATE§ cho đúng dòng đó. Quá trình đồng bộ collection có thể xóa và chèn lại các hàng con.

§§§text
Database trước:
order_lines
  501 | 0 | SKU-A | 2
  501 | 1 | SKU-B | 1
  501 | 2 | SKU-C | 4

Object sau khi sửa:
  501
    0 -> SKU-A, 2
    1 -> SKU-B, 5
    2 -> SKU-C, 4

Save aggregate:
  Root được cập nhật
  Collection được đồng bộ theo trạng thái mới
  Các hàng con có thể được delete/insert lại
§§§

Chi tiết SQL cụ thể phụ thuộc phiên bản và mapping, nhưng khi thiết kế nên tính đến việc collection được lưu như một phần trạng thái aggregate, không như một tập entity có dirty tracking từng hàng.

### 7.1. Hệ quả với ID của phần tử con

Nếu entity con có khóa riêng, cần thận trọng khi giả định ID của nó được giữ nguyên qua các lần lưu root. Với chiến lược xóa/chèn lại các entity được sở hữu, hàng con có thể được tạo lại và giá trị định danh do database sinh có thể thay đổi tùy mapping.

Nếu hệ thống khác cần tham chiếu ổn định đến từng phần tử con, hoặc cần cập nhật chúng độc lập, đó là dấu hiệu mạnh cho thấy phần tử có thể cần trở thành aggregate root riêng.

### 7.2. Hệ quả với khóa ngoại trỏ đến entity con

Giả sử một bảng khác tham chiếu §order_lines.id§. Nếu Spring Data JDBC xóa hàng con rồi chèn lại khi save aggregate, khóa ngoại từ bảng ngoài có thể:

- Chặn việc xóa hàng con.
- Bị cascade xóa dữ liệu liên quan nếu cấu hình cascade.
- Trở thành tham chiếu mồ côi nếu không có constraint bảo vệ.

Vì vậy, **entity con được sở hữu không nên là mục tiêu tham chiếu độc lập từ các aggregate khác** nếu vòng đời lưu của root có thể tái tạo hàng con.

Nếu cần một thực thể có identity ổn định được nhiều nơi tham chiếu, hãy xem xét tách nó thành aggregate root riêng và để aggregate khác tham chiếu ID.

## 8. Thứ tự phần tử và thay thế trong List, Set, Map

Kiểu collection ảnh hưởng đến cách thêm, thay thế và bỏ phần tử.

### 8.1. List: vị trí có ý nghĩa

§List§ lưu thứ tự. Với §@MappedCollection(keyColumn = "line_position")§, vị trí có thể được lưu trong bảng con.

Các thao tác:

§§§java

lines.set(1, replacement);             // Thay tại vị trí 1
lines.remove(1);                       // Bỏ vị trí 1
§§§

Khi chèn hoặc xóa ở giữa, các vị trí sau đó có thể thay đổi. Không nên xem §line_position§ là ID nghiệp vụ bền vững nếu thứ tự có thể thay đổi.

Nếu cần tham chiếu ổn định đến dòng hàng, hãy có một mã dòng hàng riêng và thiết kế mô hình tương ứng.

### 8.2. Set: uniqueness theo equality

§Set§ không biểu diễn thứ tự và không chứa phần tử trùng theo quy tắc §equals/hashCode§.

Ví dụ:

§§§java
private Set<Tag> tags = new LinkedHashSet<>();

public void addTag(Tag tag) {
    tags.add(tag);
}

public void removeTag(Tag tag) {
    tags.remove(tag);
}
§§§

Khi dùng §Set§, cần định nghĩa equality/hash code phù hợp với domain. Nếu dùng một thuộc tính mutable trong §hashCode§ rồi thay đổi nó khi phần tử đang ở trong Set, việc tìm/xóa phần tử có thể hoạt động sai.

### 8.3. Map: key là danh tính trong collection

§Map§ phù hợp khi mỗi phần tử được xác định bởi một key trong phạm vi aggregate:

§§§java

        new LinkedHashMap<>();

public void putInstruction(String key, DeliveryInstruction value) {
    instructions.put(key, value);
}

public void removeInstruction(String key) {
    instructions.remove(key);
}
§§§

§put§ với key đã tồn tại thay thế giá trị cũ; §remove§ bỏ phần tử theo key. Key column trong mapping phải lưu được key và có kiểu SQL tương thích.

Key của Map là identity trong phạm vi collection, không tự động là ID độc lập của aggregate.

## 9. Ví dụ hoàn chỉnh với các thao tác thêm, thay thế, bỏ

Một phiên bản root có đầy đủ hành vi:

§§§java
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;
import java.util.Objects;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_orders")
public class PurchaseOrder {

    @Id
    private Long id;

    private String status;

    @MappedCollection(
            idColumn = "order_id",
            keyColumn = "line_position"
    )
    private List<OrderLine> lines = new ArrayList<>();

    protected PurchaseOrder() {
    }

    public PurchaseOrder(String status) {
        this.status = Objects.requireNonNull(status);
    }

    public Long getId() {
        return id;
    }

    public String getStatus() {
        return status;
    }

    public List<OrderLine> getLines() {
        return Collections.unmodifiableList(lines);
    }

    public void addLine(String sku, int quantity) {
        ensureEditable();
        lines.add(new OrderLine(sku, quantity));
    }

    public void replaceLine(
            int position, String sku, int quantity
    ) {
        ensureEditable();
        checkPosition(position);
        lines.set(position, new OrderLine(sku, quantity));
    }

    public void removeLine(int position) {
        ensureEditable();
        checkPosition(position);
        lines.remove(position);
    }

    public void removeLineBySku(String sku) {
        ensureEditable();

        boolean removed = lines.removeIf(
                line -> line.sku().equals(sku)
        );

        if (!removed) {
            throw new IllegalArgumentException("Line not found");
        }
    }

    public void confirm() {
        if (lines.isEmpty()) {
            throw new IllegalStateException(
                    "Cannot confirm an empty order"
            );
        }
        ensureEditable();
        status = "CONFIRMED";
    }

    private void ensureEditable() {
        if (!"DRAFT".equals(status)) {
            throw new IllegalStateException(
                    "Only draft orders can be edited"
            );
        }
    }

    private void checkPosition(int position) {
        if (position < 0 || position >= lines.size()) {
            throw new IndexOutOfBoundsException(position);
        }
    }
}

import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class PurchaseOrderService {

    private final PurchaseOrderRepository orders;

    public PurchaseOrderService(PurchaseOrderRepository orders) {
        this.orders = orders;

    public PurchaseOrder addLine(
            Long orderId, String sku, int quantity

        order.addLine(sku, quantity);
        return orders.save(order);
    }

    @Transactional
    public PurchaseOrder replaceLine(
            Long orderId, int position,
            String sku, int quantity

        PurchaseOrder order = load(orderId);
        order.replaceLine(position, sku, quantity);
        return orders.save(order);
    }

    @Transactional
    public PurchaseOrder removeLine(
            Long orderId, int position
    ) {
        PurchaseOrder order = load(orderId);
        order.removeLine(position);
        return orders.save(order);
    }

    private PurchaseOrder load(Long id) {
        return orders.findById(id).orElseThrow();
    }

Trong ví dụ thực tế, nên bổ sung xử lý không tìm thấy đơn hàng, lỗi nghiệp vụ, optimistic locking nếu có cập nhật đồng thời và các thông báo API phù hợp.

## 10. Thêm, thay thế, bỏ phần tử có ảnh hưởng gì đến database?

| Thao tác | Trạng thái aggregate sau thao tác | Hệ quả persistence |
| --- | --- | --- |
| §addLine§ | Có thêm phần tử | Lưu trạng thái collection mới; phần tử mới được insert vào bảng con. |
| §replaceLine§ | Một phần tử được thay bằng giá trị mới | Lưu trạng thái collection mới; có thể đồng bộ bằng xóa/chèn lại các hàng con. |
| §removeLine§ | Phần tử không còn trong collection | Hàng con tương ứng bị loại khỏi trạng thái aggregate đã lưu. |
| §replaceAllLines§ | Toàn bộ collection đổi | Database được đồng bộ với danh sách mới; phần tử cũ không còn có thể bị xóa. |
| §save§ chưa được gọi | Chỉ object trong bộ nhớ đổi | Database chưa nhận thay đổi. |
| §save§ rollback | Transaction không commit | Thay đổi không được lưu bền vững. |
| §delete(root)§ | Aggregate không còn | Các entity được sở hữu cũng được xử lý theo vòng đời root. |

Bảng này mô tả ý nghĩa nghiệp vụ và kết quả mong đợi. Số lượng, thứ tự và chi tiết câu lệnh SQL cụ thể phụ thuộc mapping, database và phiên bản Spring Data JDBC.

### 10.1. Không đồng nhất replace với update một hàng

Trong ORM có persistence context, dirty checking có thể phát hiện một property thay đổi và tạo câu update cho hàng tương ứng. Spring Data JDBC có mô hình aggregate persistence khác; không nên dựa vào dirty checking để suy luận câu SQL.

Nếu yêu cầu kỹ thuật bắt buộc cập nhật đúng một hàng con mà không tái tạo collection, cần cân nhắc một truy vấn SQL tùy chỉnh hoặc thiết kế phần tử thành aggregate độc lập. Tuy nhiên, khi bỏ qua repository root, ứng dụng phải tự bảo vệ các bất biến liên quan.

### 10.2. Giao dịch cho thay đổi aggregate

Khi một thao tác nghiệp vụ gồm nhiều câu SQL để lưu root và collection, transaction giúp các thay đổi đó được commit hoặc rollback cùng nhau theo cấu hình. Repository CRUD thường có transaction configuration mặc định; đặt §@Transactional§ ở service giúp xác định rõ ranh giới của thao tác nghiệp vụ, đặc biệt khi phối hợp nhiều repository hoặc nhiều bước.

Không nên chia một lần thay đổi aggregate thành nhiều transaction độc lập nếu điều đó có thể để lại root và collection ở trạng thái không nhất quán.

## 11. Khi nào phần tử con cần trở thành aggregate riêng?

Hãy xem xét lại thiết kế nếu phần tử con có một hoặc nhiều đặc điểm:

- Có identity nghiệp vụ ổn định và được nhiều nơi tham chiếu.
- Có vòng đời độc lập với root.
- Cần được tạo, sửa, xóa qua API hoặc repository riêng.
- Có lượng dữ liệu lớn, cần phân trang.
- Có tần suất cập nhật cao và độc lập với root.
- Có thể được nhiều aggregate cùng tham chiếu.
- Việc lưu root khiến toàn bộ collection bị đồng bộ lại với chi phí lớn.
- Có dữ liệu khác tham chiếu đến ID phần tử con và cần giữ identity ổn định.

Ví dụ, nếu §OrderLine§ cần được các hệ thống fulfillment, invoice và analytics tham chiếu độc lập, hãy xem xét tạo §OrderLine§ thành aggregate root với ID riêng, còn §PurchaseOrder§ giữ tham chiếu đến nó theo thiết kế domain phù hợp.

Sơ đồ trước khi tách:

§§§text
PurchaseOrder aggregate
  ├── OrderLine A
  ├── OrderLine B
  └── OrderLine C
§§§

Sau khi tách:

§§§text
PurchaseOrder aggregate
  id = 501

OrderLine aggregate A
  id = 7001
  orderId = 501

OrderLine aggregate B
  id = 7002
  orderId = 501
§§§

Khi đó, thêm hoặc xóa §OrderLine§ là thao tác repository riêng và service phải đảm bảo các quy tắc xuyên aggregate cần thiết. Không được tách chỉ để né cơ chế delete/insert của collection nếu phần tử vẫn phải luôn nhất quán cùng root.

## 12. Các lỗi thường gặp

**“Thêm phần tử vào List là database đã có hàng mới.”** Không đúng. Collection trong bộ nhớ chỉ thay đổi; phải persist aggregate root.

**“Có thể tạo OrderLineRepository cho mọi dòng hàng.”** Không nên nếu §OrderLine§ là entity con được sở hữu. Thao tác độc lập có thể bỏ qua quy tắc của §PurchaseOrder§.

**“Xóa khỏi List là hàng con bị xóa ngay lập tức.”** Không đúng. Hàng database được đồng bộ khi lưu root và transaction commit.

**“Thay một phần tử chỉ phát UPDATE cho đúng hàng đó.”** Không nên giả định như vậy. Spring Data JDBC có thể xóa và chèn lại các entity được sở hữu khi cập nhật aggregate.

**“Vị trí List là ID ổn định của dòng hàng.”** Không đúng. Vị trí có thể thay đổi khi chèn hoặc xóa phần tử trước nó.

**“Collection rỗng nghĩa là phải xóa aggregate root.”** Không đúng. Root có thể tồn tại ở trạng thái chưa có phần tử; quy tắc nghiệp vụ quyết định có cho phép trạng thái đó hay không.

**“Xóa root chỉ xóa hàng root.”** Không đúng với aggregate có entity được sở hữu. Các thành phần được sở hữu cũng thuộc vòng đời root.

**“Nếu child có ID thì nó chắc chắn là aggregate root.”** Không đúng. Một entity con vẫn có thể có khóa riêng nhưng được quản lý trong aggregate root.

**“Đặt ON DELETE CASCADE ở mọi khóa ngoại sẽ đơn giản hóa code.”** Không đúng. Cascade ở sai hướng có thể xóa dữ liệu độc lập hoặc dữ liệu lịch sử. Phân biệt ownership nội bộ với tham chiếu giữa aggregate.

**“Gửi một danh sách rút gọn từ API rồi save là chỉ cập nhật các phần tử được gửi.”** Không đúng nếu API đang thay toàn bộ collection. Phải phân biệt thao tác thêm/bỏ/thay thế cụ thể với thay toàn bộ trạng thái danh sách.

## 13. Quy trình triển khai thao tác collection an toàn

Khi thêm, thay thế hoặc bỏ phần tử con, thực hiện theo thứ tự:

1. **Tải aggregate root** bằng repository.
2. **Kiểm tra quyền và trạng thái** để xác định root có cho phép thay đổi không.
3. **Gọi phương thức domain** như §addLine§, §replaceLine§ hoặc §removeLine§.
4. **Kiểm tra bất biến**: số lượng hợp lệ, không trùng, giới hạn collection, trạng thái đơn hàng.
5. **Lưu root** bằng repository.
6. **Commit transaction**; nếu có lỗi, xử lý rollback và phản hồi phù hợp.
7. **Dùng aggregate trả về** từ §save§ khi cần ID hoặc trạng thái đã persist.
8. **Kiểm tra tác động dữ liệu** nếu collection lớn, có FK phụ thuộc hoặc có yêu cầu identity ổn định.

§§§mermaid
flowchart TD
    A["Request thêm/thay thế/bỏ phần tử"] --> B["Load aggregate root"]
    B --> C{"Root cho phép chỉnh sửa?"}
    C -->|No| X["Từ chối theo nghiệp vụ"]
    C -->|Yes| D["Thay đổi collection qua root"]
    D --> E["Kiểm tra bất biến"]
    E --> F{"Hợp lệ?"}
    F -->|No| X
    F -->|Yes| G["repository.save(root)"]
    G --> H{"Transaction commit?"}

Nếu nhiều người dùng có thể sửa cùng một aggregate, hãy cân nhắc optimistic locking với §@Version§. Nếu không, một request tải trạng thái cũ có thể ghi đè thay đổi của request khác theo chiến lược lưu aggregate.

## 15. Ghi nhớ

- Entity con thuộc aggregate được tạo, thay thế và bỏ thông qua aggregate root.
- Thay đổi collection trong Java chưa làm thay đổi database; cần lưu root và transaction commit.
- §@MappedCollection§ xác định quan hệ collection với bảng con thông qua khóa ngoại và key column.
- Với §List§, vị trí là key trong collection, không nhất thiết là identity nghiệp vụ ổn định.
- Spring Data JDBC không dựa trên dirty checking của persistence context; cập nhật collection được sở hữu có thể xóa và chèn lại các hàng con để đồng bộ trạng thái aggregate.
- Phần tử bị bỏ khỏi collection sẽ không còn thuộc aggregate sau khi trạng thái mới được persist.
- Xóa aggregate root cũng xử lý các entity được sở hữu theo vòng đời của root; aggregate độc lập chỉ được tham chiếu bằng ID không bị xóa theo.
- Collection lớn, phần tử có identity ổn định, cần phân trang hoặc cập nhật độc lập là dấu hiệu nên đánh giá lại ranh giới aggregate.
- Giao dịch, khóa ngoại và optimistic locking cần phối hợp để bảo vệ dữ liệu khi có nhiều thao tác đồng thời.

Khi thiết kế đúng, thao tác thêm, thay thế và bỏ phần tử con là những thay đổi có kiểm soát trên aggregate root. **Vòng đời dữ liệu trong database phải phản ánh vòng đời domain**: phần tử được sở hữu đi theo root; phần tử có vòng đời độc lập cần một ranh giới aggregate và chính sách tham chiếu riêng.
