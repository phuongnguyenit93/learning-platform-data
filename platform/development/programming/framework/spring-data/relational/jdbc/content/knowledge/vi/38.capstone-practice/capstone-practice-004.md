# Tạo bộ lọc đơn hàng, phân trang và projection báo cáo trong Spring Data JDBC

## 1. Bài toán thực tế

Một màn hình quản lý đơn hàng thường cần nhiều khả năng:

- Lọc theo trạng thái đơn hàng.
- Lọc theo khoảng thời gian tạo.
- Tìm theo mã đơn hoặc thông tin khách hàng.
- Sắp xếp theo thời gian tạo, tổng tiền hoặc trạng thái.
- Chia kết quả thành từng trang.
- Hiển thị báo cáo gồm tên khách hàng, số dòng hàng và tổng tiền.

Không phải mọi yêu cầu đọc dữ liệu đều cần tải toàn bộ aggregate Order. Một màn hình danh sách có thể chỉ cần vài cột từ orders, customers và order_lines. Nếu tải đầy đủ aggregate cho từng hàng rồi mới tính báo cáo trong Java, ứng dụng có thể đọc nhiều dữ liệu hơn mức cần thiết.

Trong Spring Data JDBC, nên phân biệt hai loại truy vấn:

1. **Aggregate query:** tải Order đầy đủ qua repository khi cần xử lý nghiệp vụ trên aggregate.
2. **Read/report query:** lấy một projection hoặc DTO chứa các cột cần hiển thị, thường dùng custom query với JOIN và phép tổng hợp.

Bài học này xây dựng cả hai loại để thấy khi nào nên dùng repository method, khi nào cần JdbcAggregateTemplate và khi nào nên dùng custom repository fragment với NamedParameterJdbcTemplate.

## 2. Mô hình dữ liệu ví dụ

Giả sử ứng dụng quản lý Order, Customer và OrderLine:

~~~text
customers
  id
  name

orders
  id
  order_number
  customer_id
  status
  created_at

order_lines
  id
  order_id
  sku
  quantity
  unit_price
~~~

Order là aggregate root. OrderLine thuộc aggregate Order. Customer là aggregate khác và được Order tham chiếu bằng customer_id.

Entity Order:

~~~java
import java.math.BigDecimal;
import java.time.Instant;
import java.util.List;

import org.springframework.data.annotation.Id;
import org.springframework.data.jdbc.core.mapping.AggregateReference;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("orders")
public class Order {

    @Id
    private Long id;

    @Column("order_number")
    private String orderNumber;

    private OrderStatus status;

    @Column("created_at")
    private Instant createdAt;

    @Column("customer_id")
    private AggregateReference<Customer, Long> customer;

    @MappedCollection(idColumn = "order_id")
    private List<OrderLine> lines;

    // Constructors, getters and domain methods.
}
~~~

Enum trạng thái:

~~~java
public enum OrderStatus {
    PENDING,
    CONFIRMED,
    PAID,
    SHIPPED,
    CANCELLED
}
~~~

Schema migration minh họa:

~~~sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(200) NOT NULL
);

CREATE TABLE orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_number VARCHAR(40) NOT NULL UNIQUE,
    customer_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL,
    CONSTRAINT fk_orders_customer
        FOREIGN KEY (customer_id) REFERENCES customers(id)
);

CREATE TABLE order_lines (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL,
    sku VARCHAR(60) NOT NULL,
    quantity INTEGER NOT NULL,
    unit_price DECIMAL(18, 2) NOT NULL,
    CONSTRAINT fk_order_lines_order
        FOREIGN KEY (order_id) REFERENCES orders(id)
);

CREATE INDEX ix_orders_status_created_at
    ON orders(status, created_at DESC);

CREATE INDEX ix_orders_customer_id
    ON orders(customer_id);

CREATE INDEX ix_order_lines_order_id
    ON order_lines(order_id);
~~~

Kiểu timestamp, identity và cú pháp index có thể cần điều chỉnh theo database. Index cần dựa trên truy vấn thực tế và execution plan, không nên thêm mọi index có thể nghĩ tới.

## 3. Bộ lọc đơn hàng bằng derived query

Với các điều kiện đơn giản dựa trên property của aggregate root, Spring Data JDBC có thể suy ra SQL từ tên method.

Repository:

~~~java
import java.time.Instant;
import java.util.List;

import org.springframework.data.domain.Page;
import org.springframework.data.domain.Pageable;
import org.springframework.data.domain.Slice;
import org.springframework.data.domain.Sort;
import org.springframework.data.repository.CrudRepository;
import org.springframework.data.repository.PagingAndSortingRepository;

public interface OrderRepository
        extends CrudRepository<Order, Long>,
                PagingAndSortingRepository<Order, Long> {

    List<Order> findByStatus(OrderStatus status);

    Page<Order> findByStatusAndCreatedAtBetween(
            OrderStatus status,
            Instant from,
            Instant to,
            Pageable pageable
    );

    Slice<Order> findByStatus(
            OrderStatus status,
            Pageable pageable
    );

    List<Order> findByStatus(
            OrderStatus status,
            Sort sort
    );

    List<Order> findByOrderNumberStartingWith(
            String prefix,
            Pageable pageable
    );
}
~~~

Trong các phiên bản Spring Data hiện đại, CrudRepository và PagingAndSortingRepository là hai interface riêng biệt. Nếu repository cần cả CRUD và paging/sorting, khai báo cả hai như ví dụ.

Một số keyword thường dùng:

| Keyword | Ví dụ method | Điều kiện SQL |
|---|---|---|
| And | findByStatusAndCustomerId | Hai điều kiện AND |
| Or | findByStatusOrPriority | Hai điều kiện OR |
| Between | findByCreatedAtBetween | Khoảng giá trị |
| GreaterThanEqual | findByCreatedAtGreaterThanEqual | >= |
| LessThan | findByCreatedAtLessThan | < |
| In | findByStatusIn | IN |
| IsNull | findByCancelledAtIsNull | IS NULL |
| StartingWith | findByOrderNumberStartingWith | LIKE prefix% |
| Containing | findByOrderNumberContaining | LIKE %value% |
| OrderBy | findByStatusOrderByCreatedAtDesc | ORDER BY |

Query derivation trong Spring Data JDBC có giới hạn: nó chủ yếu hỗ trợ các property đơn giản trực tiếp trên aggregate root và không tự tạo JOIN tùy ý để lọc theo bảng liên quan.

Ví dụ findByStatusAndCreatedAtBetween phù hợp vì cả status và createdAt là property của Order. Nếu muốn lọc theo customer.name hoặc tổng tiền tính từ order_lines, hãy dùng custom query/read model.

## 4. Lọc động khi các tham số là tùy chọn

Một API tìm kiếm thường cho phép người dùng chỉ nhập một vài điều kiện. Ví dụ:

~~~text
GET /orders?status=PAID&from=2026-01-01&to=2026-02-01
~~~

Nếu viết một method cho mọi tổ hợp status/from/to/customer, repository sẽ có quá nhiều method.

Có thể dùng Criteria và JdbcAggregateTemplate để xây dựng điều kiện động.

Filter object:

~~~java
public record OrderFilter(
        OrderStatus status,
        Instant createdFrom,
        Instant createdBefore
) {}
~~~

Custom service:

~~~java
import org.springframework.data.domain.Page;
import org.springframework.data.domain.PageImpl;
import org.springframework.data.domain.Pageable;
import org.springframework.data.jdbc.core.JdbcAggregateTemplate;
import org.springframework.data.relational.core.query.Criteria;
import org.springframework.data.relational.core.query.Query;

public class OrderSearchService {

    private final JdbcAggregateTemplate template;

    public OrderSearchService(JdbcAggregateTemplate template) {
        this.template = template;
    }

    public Page<Order> search(
            OrderFilter filter,
            Pageable pageable
    ) {
        Criteria criteria = Criteria.empty();

        if (filter.status() != null) {
            criteria = criteria.and("status").is(filter.status());
        }

        if (filter.createdFrom() != null) {
            criteria = criteria.and("createdAt")
                    .greaterThanOrEquals(filter.createdFrom());
        }

        if (filter.createdBefore() != null) {
            criteria = criteria.and("createdAt")
                    .lessThan(filter.createdBefore());
        }

        Query baseQuery = Query.query(criteria);

        Query pageQuery = baseQuery.with(pageable);

        List<Order> content = template.findAll(
                pageQuery,
                Order.class
        );

        long total = template.count(baseQuery, Order.class);

        return new PageImpl<>(content, pageable, total);
    }
}
~~~

`Criteria` và `Query` là immutable value objects. Mỗi lần gọi and hoặc with, cần gán giá trị trả về vào biến để giữ điều kiện mới.

`Query.with(pageable)` áp dụng offset, limit và sort của Pageable. Dùng query gốc không có page limit để đếm tổng số aggregate phù hợp.

`JdbcAggregateTemplate.count(query, Order.class)` trả số aggregate root khớp điều kiện. Kết quả PageImpl chứa nội dung trang, thông tin Pageable và tổng số kết quả.

### 4.1. Chú ý tên property và tên cột

Criteria dùng property mapping của entity. Ví dụ property Java createdAt được ánh xạ sang created_at theo NamingStrategy hoặc @Column.

Khi viết SQL thuần trong @Query hoặc JdbcTemplate, phải dùng tên cột database thực tế, ví dụ created_at. Không trộn tên property Java với tên cột SQL.

### 4.2. Không đưa giá trị đầu vào vào tên cột

Giá trị filter phải được bind như parameter. Không nối trực tiếp giá trị người dùng vào SQL.

Criteria API quản lý việc bind giá trị. Với NamedParameterJdbcTemplate, dùng named parameter. Nếu cần sort động trong SQL tùy chỉnh, hãy ánh xạ lựa chọn sort qua whitelist cột được phép thay vì nối trực tiếp chuỗi từ request.

## 5. Phân trang: Page, Slice và List

Spring Data hỗ trợ nhiều kiểu trả kết quả cho query method:

| Kiểu trả về | Thông tin | Chi phí truy vấn |
|---|---|---|
| Page<T> | Nội dung trang, page number, page size, tổng phần tử và tổng trang | Có thể chạy thêm count query |
| Slice<T> | Nội dung hiện tại và có trang tiếp theo hay không | Thường lấy thêm một hàng để xác định hasNext |
| List<T> + Pageable | Chỉ nội dung trong phạm vi trang | Không tạo Page metadata và không cần count query |
| List<T> + Sort | Toàn bộ kết quả được sắp xếp | Không có giới hạn trang |
| Stream<T> | Đọc kết quả theo luồng | Có thể giữ connection mở cho tới khi stream đóng |

### 5.1. Khi nào dùng Page?

Dùng Page khi giao diện cần hiển thị:

- Tổng số đơn hàng phù hợp filter.
- Tổng số trang.
- Nút đi tới trang cuối.
- Thông tin kiểu “đang xem 21–40 trên 537 đơn hàng”.

Ví dụ:

~~~java
Pageable pageable = PageRequest.of(
        0,
        20,
        Sort.by(
                Sort.Order.desc("createdAt"),
                Sort.Order.desc("id")
        )
);

Page<Order> page = orders.findByStatusAndCreatedAtBetween(
        OrderStatus.PAID,
        from,
        to,
        pageable
);
~~~

Page thường cần count query để xác định tổng số phần tử. Count có thể tốn chi phí nếu điều kiện phức tạp hoặc bảng lớn.

### 5.2. Khi nào dùng Slice?

Nếu giao diện chỉ cần nút “Tải thêm” hoặc “Trang tiếp theo”, tổng số trang có thể không cần thiết.

~~~java
Slice<Order> slice = orders.findByStatus(
        OrderStatus.PENDING,
        PageRequest.of(
                0,
                30,
                Sort.by(Sort.Order.desc("createdAt"))
        )
);
~~~

Slice chỉ cần biết còn dữ liệu tiếp theo hay không. Spring Data JDBC có thể lấy thêm một hàng so với page size để xác định hasNext.

### 5.3. Khi nào dùng List với Pageable?

Nếu caller chỉ cần một tập kết quả có giới hạn, không cần Page metadata:

~~~java
List<Order> recentOrders = orders.findByOrderNumberStartingWith(
        "ORD-",
        PageRequest.of(
                0,
                50,
                Sort.by(Sort.Order.desc("createdAt"))
        )
);
~~~

Cách này tránh count query được dùng để tạo Page. Caller tự quản lý thông tin trang nếu cần.

### 5.4. Sắp xếp ổn định

Không nên phân trang theo một cột có thể trùng mà không có tie-breaker.

Ví dụ nhiều đơn hàng có cùng createdAt. Nếu chỉ sort theo createdAt, thứ tự giữa các hàng cùng timestamp có thể không ổn định khi database thực thi các trang khác nhau.

Dùng thêm khóa duy nhất:

~~~java
Sort sort = Sort.by(
        Sort.Order.desc("createdAt"),
        Sort.Order.desc("id")
);
~~~

Thứ tự này giúp kết quả ổn định hơn giữa các trang. Với dữ liệu thay đổi liên tục, offset pagination vẫn có thể khiến hàng dịch chuyển giữa các trang; cân nhắc keyset/seek pagination nếu workload cần điều hướng sâu và ổn định.

## 6. Giới hạn của @Query khi phân trang

Spring Data JDBC cho phép viết SQL tường minh bằng @Query, nhưng string-based query không hỗ trợ truyền Pageable, PageRequest, Sort hoặc Limit như query derivation.

Ví dụ này không phải cách hợp lệ để yêu cầu framework tự rewrite SQL:

~~~java
@Query("SELECT * FROM orders WHERE status = :status")
Page<Order> findByStatus(
        OrderStatus status,
        Pageable pageable
);
~~~

Với @Query dạng chuỗi, nếu cần giới hạn kết quả, phải viết LIMIT/OFFSET hoặc cú pháp tương ứng của database và bind tham số một cách tường minh.

Ngoài ra, query trả aggregate entity phải cung cấp các cột phù hợp với mapping/RowMapper. Query report trả DTO nên dùng RowMapper hoặc ResultSetExtractor riêng nếu kết quả không phải cấu trúc aggregate.

Đây là lý do nên chọn derived query cho filter root đơn giản và dùng custom repository fragment cho report SQL phức tạp.

## 7. Projection báo cáo: chỉ lấy dữ liệu cần hiển thị

Projection là cách biểu diễn một phần dữ liệu cần cho use case đọc. Nó không nhất thiết là aggregate root và không nên bị lưu ngược lại bằng repository save.

Ví dụ báo cáo danh sách đơn hàng cần:

- ID đơn hàng.
- Mã đơn hàng.
- Trạng thái.
- Tên khách hàng.
- Ngày tạo.
- Tổng tiền.
- Số dòng hàng.

Tạo DTO:

~~~java
import java.math.BigDecimal;
import java.time.Instant;

public record OrderReportRow(
        Long orderId,
        String orderNumber,
        String status,
        String customerName,
        Instant createdAt,
        BigDecimal totalAmount,
        long lineCount
) {}
~~~

SQL:

~~~sql
SELECT
    o.id AS order_id,
    o.order_number,
    o.status,
    c.name AS customer_name,
    o.created_at,
    COALESCE(
        SUM(ol.quantity * ol.unit_price),
        0
    ) AS total_amount,
    COUNT(ol.id) AS line_count
FROM orders o
JOIN customers c ON c.id = o.customer_id
LEFT JOIN order_lines ol ON ol.order_id = o.id
WHERE o.status = :status
GROUP BY
    o.id,
    o.order_number,
    o.status,
    c.name,
    o.created_at
ORDER BY o.created_at DESC, o.id DESC;
~~~

SQL này chỉ trả một hàng cho mỗi Order nhờ GROUP BY. LEFT JOIN giữ lại đơn hàng chưa có dòng hàng. COALESCE làm tổng tiền của đơn không có dòng hàng trở thành 0.

Nếu dùng phép JOIN nhiều collection một-nhiều cùng lúc, cần cẩn thận cross product làm SUM và COUNT bị nhân lên. Khi đó hãy tổng hợp từng collection trong subquery/CTE riêng hoặc dùng chiến lược query phù hợp.

## 8. Tạo custom repository fragment cho report

Khi report cần JOIN, GROUP BY, count query riêng và DTO mapping, một custom repository fragment thường rõ ràng hơn việc cố nhồi mọi thứ vào method name.

Fragment interface:

~~~java
import org.springframework.data.domain.Page;
import org.springframework.data.domain.Pageable;

public interface OrderReportQuery {

    Page<OrderReportRow> findReport(
            OrderReportFilter filter,
            Pageable pageable
    );
}
~~~

Filter:

~~~java
public record OrderReportFilter(
        OrderStatus status,
        Instant createdFrom,
        Instant createdBefore
) {}
~~~

Repository chính:

~~~java
public interface OrderRepository
        extends CrudRepository<Order, Long>,
                PagingAndSortingRepository<Order, Long>,
                OrderReportQuery {
}
~~~

Implementation:

~~~java
@Repository
public class OrderReportQueryImpl implements OrderReportQuery {

    private final NamedParameterJdbcTemplate jdbc;

    public OrderReportQueryImpl(NamedParameterJdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    @Override
    public Page<OrderReportRow> findReport(
            OrderReportFilter filter,
            Pageable pageable
    ) {
        StringBuilder where = new StringBuilder(" WHERE 1 = 1 ");
        MapSqlParameterSource params = new MapSqlParameterSource();

        if (filter.status() != null) {
            where.append(" AND o.status = :status ");
            params.addValue("status", filter.status().name());
        }

        if (filter.createdFrom() != null) {
            where.append(" AND o.created_at >= :createdFrom ");
            params.addValue("createdFrom", filter.createdFrom());
        }

        if (filter.createdBefore() != null) {
            where.append(" AND o.created_at < :createdBefore ");
            params.addValue("createdBefore", filter.createdBefore());
        }

        String joins = """
                FROM orders o
                JOIN customers c ON c.id = o.customer_id
                LEFT JOIN order_lines ol ON ol.order_id = o.id
                """;

        String countSql = """
                SELECT COUNT(DISTINCT o.id)
                """ + joins + where;

        long total = jdbc.queryForObject(
                countSql,
                params,
                Long.class
        );

        String dataSql = """
                SELECT
                    o.id AS order_id,
                    o.order_number,
                    o.status,
                    c.name AS customer_name,
                    o.created_at,
                    COALESCE(
                        SUM(ol.quantity * ol.unit_price),
                        0
                    ) AS total_amount,
                    COUNT(ol.id) AS line_count
                """ + joins + where + """
                GROUP BY
                    o.id,
                    o.order_number,
                    o.status,
                    c.name,
                    o.created_at
                ORDER BY o.created_at DESC, o.id DESC
                LIMIT :limit OFFSET :offset
                """;

        params.addValue("limit", pageable.getPageSize());
        params.addValue("offset", pageable.getOffset());

        List<OrderReportRow> content = jdbc.query(
                dataSql,
                params,
                (rs, rowNum) -> new OrderReportRow(
                        rs.getLong("order_id"),
                        rs.getString("order_number"),
                        rs.getString("status"),
                        rs.getString("customer_name"),
                        rs.getTimestamp("created_at").toInstant(),
                        rs.getBigDecimal("total_amount"),
                        rs.getLong("line_count")
                )
        );

        return new PageImpl<>(content, pageable, total);
    }
}
~~~

Đây là ví dụ cho database hỗ trợ LIMIT/OFFSET và kiểu timestamp có thể đọc qua JDBC Timestamp. Với database khác, thay cú pháp phân trang và cách đọc thời gian theo dialect/driver.

Trong implementation này, ORDER BY được cố định theo created_at DESC và id DESC. Pageable chỉ cung cấp page size và offset; sort trong Pageable không được tự động áp dụng vào SQL của custom fragment. Nếu API cần sort động, hãy chuyển sort key qua whitelist và tạo ORDER BY từ các cột đã được ứng dụng cho phép.

Count query dùng COUNT(DISTINCT o.id) vì JOIN order_lines có thể tạo nhiều hàng cho cùng một đơn. Nếu đếm trực tiếp COUNT(*), tổng số đơn sẽ bị nhân theo số dòng hàng.

### 8.1. Vì sao report cần count query riêng?

Page<OrderReportRow> cần tổng số đơn hàng phù hợp filter. Query lấy report có GROUP BY và JOIN, vì vậy count query phải đếm số order root duy nhất theo cùng điều kiện lọc.

Count query phải dùng cùng predicates với query dữ liệu. Nếu một filter được thêm vào data query nhưng bị quên trong count query, totalElements và totalPages sẽ sai.

### 8.2. Bảo vệ SQL động

Trong ví dụ, các giá trị filter đều được bind bằng named parameters. Tên cột, JOIN và ORDER BY là cấu trúc SQL do ứng dụng kiểm soát.

Không viết:

~~~java
String sql = "SELECT * FROM orders WHERE status = '" + status + "'";
~~~

Cũng không nối trực tiếp tên cột hoặc hướng sort từ request:

~~~java
sql += " ORDER BY " + request.getSortField();
~~~

Nếu muốn cho phép người dùng chọn sort field, ánh xạ giá trị request qua whitelist:

~~~java
String sortColumn = switch (sortKey) {
    case "createdAt" -> "o.created_at";
    case "orderNumber" -> "o.order_number";
    case "status" -> "o.status";
    default -> "o.created_at";
};
~~~

Direction cũng cần giới hạn thành ASC hoặc DESC. Parameter binding bảo vệ giá trị; nó không thể bind tên cột hoặc keyword SQL.

## 9. Projection khác aggregate entity như thế nào?

| Đặc điểm | Aggregate Order | OrderReportRow |
|---|---|---|
| Mục đích | Xử lý nghiệp vụ | Hiển thị/báo cáo |
| Dữ liệu | Toàn bộ aggregate theo mapping | Chỉ các cột cần thiết |
| Có collection OrderLine | Có thể có | Chỉ số liệu tổng hợp |
| Repository save | Có | Không |
| JOIN nhiều bảng | Không phải mục tiêu chính của aggregate mapping | Phù hợp |
| Mapping | Spring Data JDBC aggregate converter | RowMapper/custom mapping |
| Dùng cho command | Có | Không nên |
| Dùng cho dashboard | Có thể quá nhiều dữ liệu | Phù hợp |

Không nên gọi repository.save(reportRow) hoặc cố biến report DTO thành một aggregate. Projection là kết quả đọc.

Nếu cần cập nhật Order, tải aggregate qua OrderRepository, gọi domain method rồi save. Nếu chỉ cần hiển thị bảng báo cáo, đọc projection trực tiếp từ database.

## 10. Phân trang sâu và keyset pagination

Offset pagination đơn giản:

~~~sql
SELECT id, order_number, created_at
FROM orders
ORDER BY created_at DESC, id DESC
LIMIT :limit OFFSET :offset;
~~~

Nhưng khi offset lớn, database có thể phải duyệt qua nhiều hàng trước khi trả kết quả. Khi dữ liệu thay đổi giữa các request, hàng có thể dịch chuyển giữa trang.

Keyset pagination dùng giá trị cuối cùng của trang trước để lấy trang tiếp theo.

Giả sử trang trước kết thúc ở:

~~~text
created_at = 2026-10-10T10:00:00Z
id         = 150
~~~

Query trang tiếp theo:

~~~sql
SELECT id, order_number, created_at
FROM orders
WHERE
    created_at < :lastCreatedAt
    OR (
        created_at = :lastCreatedAt
        AND id < :lastId
    )
ORDER BY created_at DESC, id DESC
LIMIT :limit;
~~~

Điều kiện dùng cả created_at và id để tạo thứ tự tổng duy nhất. Cần index phù hợp với cặp cột được dùng để sắp xếp và lọc.

Keyset pagination phù hợp với feed, lịch sử giao dịch và danh sách lớn cần đi tiếp liên tục. Nó không trực tiếp cung cấp tổng số trang như Page offset-based.

## 11. Validation cho filter và pageable

Filter đầu vào cần được kiểm tra trước khi truy vấn:

- from không được sau to.
- Page number không âm.
- Page size phải lớn hơn 0.
- Page size nên có giới hạn tối đa.
- Sort key phải nằm trong whitelist.
- Các enum status phải thuộc tập giá trị hợp lệ.
- Chuỗi tìm kiếm nên có giới hạn độ dài.

Ví dụ:

~~~java
public Pageable normalize(Pageable requested) {
    int page = Math.max(requested.getPageNumber(), 0);

    int size = Math.min(
            Math.max(requested.getPageSize(), 1),
            100
    );

    Sort sort = Sort.by(
            Sort.Order.desc("createdAt"),
            Sort.Order.desc("id")
    );

    return PageRequest.of(page, size, sort);
}
~~~

Trong API thực tế, có thể trả lỗi 400 khi page hoặc size không hợp lệ thay vì âm thầm sửa giá trị. Ví dụ trên minh họa một chính sách normalize; hãy chọn contract phù hợp với API.

Không cho phép người dùng sort theo property không được hỗ trợ hoặc cột nhạy cảm nếu query/report không có ý định cung cấp.

## 12. Index và query plan cho bộ lọc đơn hàng

Bộ lọc status + created_at thường phù hợp với index ghép:

~~~sql
CREATE INDEX ix_orders_status_created_at
ON orders(status, created_at DESC);
~~~

Nếu query luôn sắp xếp theo created_at và ID, có thể đánh giá index:

~~~sql
CREATE INDEX ix_orders_status_created_id
ON orders(status, created_at DESC, id DESC);
~~~

Đối với lọc theo customer:

~~~sql
CREATE INDEX ix_orders_customer_created
ON orders(customer_id, created_at DESC);
~~~

Với bảng order_lines, index order_id giúp JOIN và tổng hợp theo đơn:

~~~sql
CREATE INDEX ix_order_lines_order
ON order_lines(order_id);
~~~

Index có chi phí ghi và dung lượng. Dùng EXPLAIN/EXPLAIN ANALYZE trên database mục tiêu để xác định index nào có ích. Không tạo index chỉ vì một cột xuất hiện trong một filter hiếm dùng.

## 13. Transaction và consistency của report

Một report query có JOIN nhiều bảng. Nếu dữ liệu thay đổi trong lúc query, kết quả phụ thuộc isolation level và database.

Ví dụ một transaction cập nhật OrderLine trong khi report đang tính tổng tiền. Tùy isolation level, report có thể nhìn thấy snapshot nhất quán hoặc kết quả theo semantics riêng của database.

Nếu report chỉ hiển thị dữ liệu tổng hợp gần nhất, một read transaction thông thường có thể đủ. Nếu báo cáo tài chính cần snapshot nhất quán qua nhiều truy vấn, xác định rõ isolation level, transaction boundary và cách lấy dữ liệu.

Khi Page cần chạy data query và count query riêng, hai câu query có thể quan sát hai thời điểm khác nhau nếu không nằm trong transaction phù hợp. Điều này có thể khiến content size và total count chênh nhẹ khi dữ liệu đang thay đổi.

Nếu nghiệp vụ yêu cầu total và content phải cùng snapshot, thực hiện hai query trong một transaction với isolation phù hợp cho database. Không tăng isolation level tùy tiện vì có thể ảnh hưởng concurrency.

## 14. Kiểm thử bộ lọc, phân trang và projection

Nên kiểm thử theo từng điều kiện và tổ hợp:

| Test case | Điều cần xác nhận |
|---|---|
| Không truyền filter | Trả tất cả order trong phạm vi truy vấn |
| Lọc theo status | Chỉ trả đúng trạng thái |
| Lọc from | Không lấy hàng trước thời điểm bắt đầu |
| Lọc to | Không lấy hàng tại/sau mốc exclusive |
| Lọc from + to | Khoảng thời gian đúng |
| Page đầu | Offset 0 và giới hạn đúng |
| Page kế tiếp | Không trùng hoặc bỏ sót khi dữ liệu ổn định |
| Sort có tie-breaker | Thứ tự ổn định khi createdAt trùng |
| Page rỗng | Content rỗng, total chính xác |
| Slice | hasNext đúng mà không cần total |
| Report không có lines | Tổng tiền 0 và lineCount 0 |
| Report có nhiều lines | SUM và COUNT chính xác |
| Count query | Đếm order duy nhất, không đếm row JOIN |
| SQL filter | Bind parameter, không nối input vào SQL |
| Database mục tiêu | Dialect, timestamp và LIMIT/OFFSET hoạt động đúng |

Ví dụ test repository:

~~~java
@DataJdbcTest
class OrderRepositoryTest {

    @Autowired
    OrderRepository orders;

    @Test
    void returnsOnlyPaidOrdersInRequestedPage() {
        Pageable pageable = PageRequest.of(
                0,
                10,
                Sort.by(
                        Sort.Order.desc("createdAt"),
                        Sort.Order.desc("id")
                )
        );

        Page<Order> result = orders.findByStatusAndCreatedAtBetween(
                OrderStatus.PAID,
                Instant.parse("2026-01-01T00:00:00Z"),
                Instant.parse("2026-02-01T00:00:00Z"),
                pageable
        );

        assertThat(result.getContent())
                .allMatch(order -> order.getStatus() == OrderStatus.PAID);

        assertThat(result.getSize()).isEqualTo(10);
    }
}
~~~

Test này minh họa assertion cơ bản. Dữ liệu test cần được chuẩn bị để xác nhận cả boundary thời gian, sort và count query.

### 14.1. Test report query

Report nên được kiểm thử bằng dữ liệu có số dòng hàng khác nhau:

~~~text
Order A: 2 lines, total 150
Order B: 0 lines, total 0
Order C: 3 lines, total 420
~~~

Assertion cần kiểm tra:

- Mỗi order chỉ xuất hiện một lần.
- lineCount đúng.
- totalAmount đúng.
- Order không có line vẫn xuất hiện nếu dùng LEFT JOIN.
- Page total đếm số Order, không đếm số OrderLine.

Nên chạy test trên cùng loại database với production nếu SQL dùng cú pháp hoặc kiểu dữ liệu đặc thù.

## 15. Quy trình xây dựng chức năng tìm kiếm và báo cáo

1. Xác định dữ liệu nào thuộc aggregate Order và dữ liệu nào chỉ cần cho read model.
2. Định nghĩa OrderFilter với các điều kiện tùy chọn.
3. Dùng derived query cho filter đơn giản trên property aggregate root.
4. Dùng Criteria và JdbcAggregateTemplate khi cần ghép điều kiện root động.
5. Chọn Page nếu cần total count; chọn Slice hoặc List + Pageable nếu không cần.
6. Luôn sắp xếp ổn định bằng một khóa duy nhất làm tie-breaker.
7. Tạo DTO projection cho report, dashboard hoặc bảng danh sách.
8. Dùng custom repository fragment và RowMapper cho JOIN/GROUP BY.
9. Viết count query riêng và bảo đảm đếm distinct aggregate root.
10. Bind tất cả giá trị filter; whitelist mọi sort column/direction động.
11. Kiểm tra index và query plan trên database mục tiêu.
12. Kiểm thử page boundary, dữ liệu rỗng, aggregation và concurrent updates.

## 16. Những lỗi thường gặp

| Biểu hiện | Nguyên nhân có thể | Cách xử lý |
|---|---|---|
| Repository có quá nhiều method tìm kiếm | Tạo method cho mọi tổ hợp filter tùy chọn | Dùng Criteria/Query để xây dựng điều kiện động |
| Derived query không lọc được customer.name | Query derivation JDBC giới hạn ở property đơn giản của aggregate root | Dùng JOIN trong custom query/report fragment |
| Page query chạy chậm | Count query hoặc filter không có index | Đo count riêng, kiểm tra execution plan |
| Count lớn hơn số order | JOIN child tạo nhiều hàng cho một root | Dùng COUNT(DISTINCT order_id) |
| Order không có line bị mất khỏi report | Dùng INNER JOIN với order_lines | Dùng LEFT JOIN nếu cần giữ order rỗng |
| Tổng tiền bị nhân lên | JOIN nhiều collection tạo cross product | Tổng hợp riêng bằng subquery/CTE |
| @Query không nhận Pageable | String-based query Spring Data JDBC không hỗ trợ dynamic Pageable/Sort | Dùng derived query hoặc tự bind LIMIT/OFFSET |
| DTO không map được | Custom query mặc định dùng entity RowMapper | Dùng custom RowMapper/ResultSetExtractor hoặc custom repository |
| Trang bị trùng hoặc thiếu hàng | Sort không ổn định hoặc dữ liệu thay đổi giữa request | Thêm ID tie-breaker; cân nhắc keyset pagination |
| Page total khác nội dung | Data query và count query dùng điều kiện khác nhau hoặc chạy ở snapshot khác | Dùng chung predicates và transaction isolation phù hợp |
| Sort gây SQL injection | Nối sort field từ request vào SQL | Whitelist cột và direction |
| Page size quá lớn | Không giới hạn tham số API | Validate và đặt maximum page size |
| List view tải quá nhiều dữ liệu | Tải toàn bộ aggregate dù chỉ cần vài cột | Dùng DTO projection/read model |
| Report query trả quá nhiều dòng | GROUP BY hoặc JOIN không phù hợp | Kiểm tra cardinality và query plan |
| H2 pass nhưng production fail | Khác dialect hoặc kiểu dữ liệu | Test bằng database mục tiêu/Testcontainers |

## 17. Bài tập thực hành

### Bài 1 — Derived filters

Tạo các method tìm Order theo status, createdAt và orderNumber prefix. Kiểm thử từng keyword And, Between, GreaterThanEqual và StartingWith.

### Bài 2 — Dynamic Criteria

Tạo OrderFilter với status, createdFrom và createdBefore tùy chọn. Dùng Criteria.empty(), thêm điều kiện theo từng field và chạy bằng JdbcAggregateTemplate.

### Bài 3 — Page và Slice

Tạo endpoint trả Page<Order> và endpoint trả Slice<Order>. Bật SQL logging, so sánh query data và count query.

### Bài 4 — Stable sorting

Tạo nhiều Order có cùng createdAt. Phân trang với createdAt DESC và id DESC. Xác nhận không trùng kết quả giữa các trang khi dữ liệu không đổi.

### Bài 5 — Report DTO

Tạo OrderReportRow và custom repository fragment. JOIN orders với customers và order_lines, tính totalAmount và lineCount.

### Bài 6 — Count query chính xác

Tạo một order có nhiều lines và một order không có line. Xác nhận report trả một hàng mỗi order và count query dùng COUNT(DISTINCT o.id).

### Bài 7 — SQL injection prevention

Thử truyền chuỗi có dấu nháy và SQL fragment vào filter. Xác nhận giá trị được bind và sort key chỉ chấp nhận whitelist.

### Bài 8 — Keyset pagination

Viết query trang tiếp theo dựa trên createdAt và id của hàng cuối trang trước. So sánh với offset pagination khi dữ liệu lớn.

### Bài 9 — Query plan và index

Chạy EXPLAIN cho filter status + created_at. Thử index ghép và so sánh execution plan trước/sau.

### Bài 10 — Database thật

Chạy migration, derived filters, report query và pagination trên database bằng Testcontainers. Kiểm tra cú pháp phân trang, timestamp mapping và count query.

## 18. Ghi nhớ

- Derived query phù hợp với filter đơn giản trên property trực tiếp của aggregate root.
- Query derivation trong Spring Data JDBC không tự tạo JOIN tùy ý cho property của aggregate khác.
- Dùng Criteria và JdbcAggregateTemplate khi cần xây dựng điều kiện động.
- Page cung cấp tổng số phần tử và có thể cần count query; Slice chỉ cần biết có dữ liệu tiếp theo.
- Pageable hỗ trợ offset, limit và sort cho query method; sort cần có tie-breaker duy nhất.
- String-based @Query của Spring Data JDBC không tự nhận Pageable/Sort/Limit; nếu cần phân trang, phải viết giới hạn SQL và bind tham số.
- Projection DTO phù hợp cho báo cáo, dashboard và list view cần JOIN/aggregation.
- Custom repository fragment với NamedParameterJdbcTemplate và RowMapper là lựa chọn rõ ràng cho report SQL phức tạp.
- Count query phải đếm distinct aggregate root khi JOIN collection một-nhiều.
- LEFT JOIN giữ lại aggregate không có child; COALESCE xử lý tổng hợp rỗng.
- Không nối input vào SQL; bind giá trị và whitelist sort field/direction.
- Query count, execution plan, index và số dòng trả về đều cần được đo khi tối ưu.
