# Truy vấn entity có thành phần con và kiểm tra SQL tải bổ sung

Trong Spring Data JDBC, một aggregate thường gồm aggregate root và các entity con được lưu ở bảng riêng. Khi khai báo một phương thức repository bằng **@Query**, câu SQL tùy chỉnh dùng để tìm và ánh xạ **aggregate root**. Spring Data JDBC vẫn phải dựng aggregate đầy đủ, vì vậy các collection như **List**, **Set** hoặc **Map** có thể được tải bằng những câu SQL bổ sung.

Đây là điểm dễ bỏ sót khi đọc code: một lời gọi repository có thể chạy nhiều statement. SQL trong **@Query** không tự động trở thành một truy vấn JOIN để dựng mọi collection. Nếu phương thức trả về nhiều root, các truy vấn tải thành phần con có thể lặp lại theo từng aggregate và tạo mẫu N+1.

Bài học dùng ví dụ đơn hàng có danh sách dòng hàng để giải thích:

1. **@Query** ánh xạ kết quả SQL vào root như thế nào.
2. Vì sao collection con vẫn được tải bằng SQL riêng.
3. Cách ước lượng và nhận diện query count bổ sung.
4. Cách đọc log SQL và kiểm tra trên database thật.
5. Khi nào nên dùng custom **RowMapper**, **ResultSetExtractor** hoặc DTO/read model.
6. Những giới hạn của string-based query và Single Query Loading.

## 1. Aggregate có thành phần con

Giả sử một đơn hàng có nhiều dòng hàng:

~~~text
PurchaseOrder (aggregate root)
    |
    +-- OrderLine
    +-- OrderLine
    +-- OrderLine
~~~

Bảng root là **purchase_orders**; bảng con là **order_lines**. Mỗi dòng hàng có cột **order_id** tham chiếu đến khóa chính của đơn.

Mapping Java:

~~~java
package com.example.shop.order.domain;

import java.math.BigDecimal;
import org.springframework.data.relational.core.mapping.Table;

@Table("order_lines")
public class OrderLine {

    private String sku;
    private int quantity;
    private BigDecimal unitPrice;

    private OrderLine() {
    }

    public String getSku() {
        return sku;
    }

    public int getQuantity() {
        return quantity;
    }

    public BigDecimal getUnitPrice() {
        return unitPrice;
    }
}
~~~

Aggregate root:

~~~java
package com.example.shop.order.domain;

import java.time.LocalDateTime;
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_orders")
public class PurchaseOrder {

    @Id
    private Long id;

    @Column("order_code")
    private String orderCode;

    private String status;

    @Column("created_at")
    private LocalDateTime createdAt;

    @MappedCollection(
            idColumn = "order_id",
            keyColumn = "line_no"
    )
    private List<OrderLine> lines = new ArrayList<>();

    private PurchaseOrder() {
    }

    public Long getId() {
        return id;
    }

    public String getOrderCode() {
        return orderCode;
    }

    public String getStatus() {
        return status;
    }

    public LocalDateTime getCreatedAt() {
        return createdAt;
    }

    public List<OrderLine> getLines() {
        return Collections.unmodifiableList(lines);
    }
}
~~~

**@MappedCollection** cho Spring Data JDBC biết collection lines được lưu ở bảng con, với order_id liên kết về root và line_no làm key cho phần tử List.

DDL minh họa:

~~~sql
CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_code VARCHAR(40) NOT NULL UNIQUE,
    status VARCHAR(20) NOT NULL,
    created_at TIMESTAMP NOT NULL
);

CREATE TABLE order_lines (
    order_id BIGINT NOT NULL,
    line_no INTEGER NOT NULL,
    sku VARCHAR(80) NOT NULL,
    quantity INTEGER NOT NULL,
    unit_price NUMERIC(15, 2) NOT NULL,

    PRIMARY KEY (order_id, line_no),
    CONSTRAINT fk_order_line_order
        FOREIGN KEY (order_id)
        REFERENCES purchase_orders(id)
        ON DELETE CASCADE,
    CONSTRAINT ck_order_line_quantity
        CHECK (quantity > 0),
    CONSTRAINT ck_order_line_price
        CHECK (unit_price >= 0)
);
~~~

Đây là một aggregate có hai bảng. Việc trả về một PurchaseOrder đồng nghĩa framework cần có cả dữ liệu root lẫn các dòng hàng thuộc về nó.

## 2. @Query tùy chỉnh tìm root như thế nào?

Khai báo repository:

~~~java
package com.example.shop.order.repository;

import com.example.shop.order.domain.PurchaseOrder;
import java.util.List;

import org.springframework.data.jdbc.repository.query.Query;
import org.springframework.data.repository.CrudRepository;
import org.springframework.data.repository.query.Param;

public interface PurchaseOrderRepository
        extends CrudRepository<PurchaseOrder, Long> {

    @Query("""
        SELECT
            o.id,
            o.order_code,
            o.status,
            o.created_at
        FROM purchase_orders o
        WHERE o.status = :status
        ORDER BY o.created_at DESC
        """)
    List<PurchaseOrder> findCustomByStatus(
            @Param("status") String status
    );
}
~~~

Khi gọi:

~~~java
List<PurchaseOrder> orders =
        repository.findCustomByStatus("OPEN");
~~~

Spring Data JDBC thực thi câu SQL do bạn khai báo để lấy các dòng của bảng root. Kết quả được ánh xạ bằng **RowMapper** mặc định giống như những truy vấn do Spring Data JDBC tự sinh.

Sau khi có các root, framework tiếp tục tải các collection được ánh xạ trong aggregate. Với lines, cần có câu SQL tương tự:

~~~sql
SELECT
    order_id,
    line_no,
    sku,
    quantity,
    unit_price
FROM order_lines
WHERE order_id = :orderId;
~~~

Vì vậy, câu SQL trong **@Query** không phải là toàn bộ hoạt động đọc aggregate.

**Điểm cần nhớ:** @Query quyết định cách tìm các root. Cấu trúc mapping của aggregate vẫn quyết định những dữ liệu liên quan cần được tải thêm.

## 3. Vì sao collection con được tải bằng SQL bổ sung?

Spring Data JDBC sử dụng cách đọc aggregate theo cấu trúc ownership. Với query tùy chỉnh, RowMapper mặc định dùng kết quả SQL để populate:

- Aggregate root.
- Embedded entities.
- Quan hệ one-to-one.
- Các array kiểu primitive được lưu bằng SQL array type.

Đối với collection entity như **Map**, **List**, **Set** và array của entity, Spring Data JDBC tạo các truy vấn riêng để tải chúng.

Ví dụ một root có thuộc tính:

~~~java
@MappedCollection(idColumn = "order_id")
private List<OrderLine> lines;
~~~

Câu **@Query** lấy purchase_orders không tự dựng danh sách OrderLine chỉ vì SQL có thêm một JOIN. Cơ chế RowMapper mặc định cần các cột theo định dạng mà nó hiểu cho root và những quan hệ được hỗ trợ; collection entity được tải theo cơ chế riêng.

Điều này giúp framework quản lý toàn bộ aggregate mà không yêu cầu mọi custom SQL phải tự viết logic nhóm các hàng con vào đúng collection.

### 3.1. Một root: đếm câu SQL

Giả sử gọi một query trả về đúng một đơn hàng, và aggregate có một collection lines.

Mô hình tải truyền thống:

~~~text
1. @Query:
   SELECT ... FROM purchase_orders WHERE ...

2. Query collection:
   SELECT ... FROM order_lines WHERE order_id = ?

Tổng minh họa: 2 SELECT
~~~

Nếu aggregate có thêm một collection độc lập, chẳng hạn notes, cần thêm một truy vấn tải collection đó.

~~~text
1. SELECT purchase_orders
2. SELECT order_lines
3. SELECT order_notes

Tổng minh họa: 3 SELECT
~~~

Đây là query count theo số đường collection được tải. Số câu cụ thể còn phụ thuộc mapping, loại quan hệ và phiên bản Spring Data JDBC.

### 3.2. Danh sách nhiều root: nguy cơ N+1

Giả sử custom query trả về 50 đơn hàng và mỗi đơn có một collection lines. Câu SQL root chỉ chạy một lần, nhưng collection cần được tải cho từng root.

Mẫu truy vấn có thể quan sát:

~~~text
1. SELECT ... FROM purchase_orders WHERE status = 'OPEN'

2. SELECT ... FROM order_lines WHERE order_id = 101
3. SELECT ... FROM order_lines WHERE order_id = 102
4. SELECT ... FROM order_lines WHERE order_id = 103
...
51. SELECT ... FROM order_lines WHERE order_id = 150
~~~

Công thức minh họa:

\[
Q = 1 + N
\]

Trong đó:

- Q là số SELECT.
- N là số aggregate root trả về.
- 1 là câu query tùy chỉnh tìm root.
- N là các query bổ sung để tải một collection cho từng root.

Với 50 root:

\[
Q = 1 + 50 = 51
\]

Nếu mỗi root có hai collection được tải riêng:

\[
Q = 1 + 2N
\]

Với 50 root:

\[
Q = 1 + 2 \times 50 = 101
\]

Đây là một dạng **N+1 query**. Đừng chỉ nhìn thấy một annotation @Query rồi kết luận phương thức repository chỉ thực thi một câu SQL.

### 3.3. Một collection lớn không đồng nghĩa nhiều query

Nếu chỉ tải một root có 100 dòng hàng, truy vấn collection có thể trả về 100 hàng trong một ResultSet:

~~~text
SELECT root             -> 1 statement
SELECT 100 child rows   -> 1 statement

Tổng: 2 statement
~~~

Phân biệt:

- **Query count:** số statement SQL.
- **Row count:** số hàng kết quả.
- **Payload size:** lượng dữ liệu truyền từ database.
- **Materialization cost:** chi phí dựng các object Java.

Một query trả về hàng nghìn hàng vẫn chỉ là một statement, nhưng có thể tốn thời gian và bộ nhớ.

## 4. @Query có JOIN nhưng collection vẫn tải riêng

Một lỗi suy luận phổ biến là nghĩ rằng nếu thêm JOIN vào SQL tùy chỉnh thì Spring Data JDBC sẽ tự nhóm các dòng con vào collection.

Ví dụ:

~~~java
@Query("""
    SELECT
        o.id,
        o.order_code,
        o.status,
        l.line_no,
        l.sku,
        l.quantity,
        l.unit_price
    FROM purchase_orders o
    LEFT JOIN order_lines l ON l.order_id = o.id
    WHERE o.status = :status
    """)
List<PurchaseOrder> findOrdersWithLines(
        @Param("status") String status
);
~~~

SQL trên tạo một ResultSet có thể lặp lại các cột root cho từng dòng hàng. Nhưng RowMapper mặc định của aggregate không tự động hiểu mọi cặp cột JOIN tùy ý là một collection cần nhóm.

Các cột kết quả phải tuân theo định dạng mà RowMapper mặc định mong đợi. Với collection entity, Spring Data JDBC vẫn tạo truy vấn riêng để tải chúng. Do đó, JOIN trong SQL root không bảo đảm loại bỏ query bổ sung.

Nếu muốn ánh xạ một ResultSet JOIN thành root cùng collection bằng một lần đọc, bạn phải tự kiểm soát việc nhóm hàng bằng một **ResultSetExtractor** hoặc một cơ chế mapping tùy chỉnh phù hợp. Khi làm vậy, bạn đang chịu trách nhiệm về việc gom đúng root, tránh trùng lặp và tạo đúng các thành phần con.

### 4.1. Lọc root theo child không có nghĩa chỉ tải child phù hợp

Ví dụ muốn tìm các đơn có sản phẩm SKU BOOK-01:

~~~java
@Query("""
    SELECT o.id, o.order_code, o.status, o.created_at
    FROM purchase_orders o
    WHERE EXISTS (
        SELECT 1
        FROM order_lines l
        WHERE l.order_id = o.id
          AND l.sku = :sku
    )
    """)
List<PurchaseOrder> findOrdersContainingSku(
        @Param("sku") String sku
);
~~~

EXISTS lọc danh sách **đơn hàng** theo điều kiện có ít nhất một dòng phù hợp.

Khi Spring Data JDBC dựng aggregate, collection lines của mỗi đơn vẫn được tải theo mapping. Thông thường collection chứa **tất cả dòng hàng của đơn**, không chỉ dòng có SKU BOOK-01.

Đây là hai yêu cầu khác nhau:

- Tìm đơn có chứa một SKU.
- Lấy riêng những dòng hàng có SKU đó.

Nếu màn hình chỉ cần các dòng phù hợp, hãy dùng DTO/read query chuyên biệt. Không nên cố biến collection aggregate thành một projection con bằng cách thêm điều kiện vào câu query root.

## 5. Những cột nào phải có trong câu @Query?

Khi dùng RowMapper mặc định, câu SQL phải trả về dữ liệu theo định dạng mà RowMapper mong đợi.

Các nguyên tắc quan trọng:

- Phải có các cột cần thiết cho những thuộc tính được truyền vào constructor của entity.
- Các thuộc tính được gán qua setter, wither hoặc field access có thể không bắt buộc phải xuất hiện trong kết quả.
- Thuộc tính không có cột tương ứng sẽ không được gán.
- Embedded entity và quan hệ one-to-one cần tên cột theo quy tắc mapping.
- Collection entity được tải bằng query riêng.

Ví dụ root có constructor:

~~~java
public PurchaseOrder(
        String orderCode,
        String status
) {
    this.orderCode = orderCode;
    this.status = status;
}
~~~

SQL phải cung cấp cả các cột được dùng trong constructor:

~~~sql
SELECT
    id,
    order_code,
    status
FROM purchase_orders
WHERE status = :status;
~~~

Nếu thiếu một cột bắt buộc cho constructor, việc ánh xạ có thể thất bại.

### 5.1. Embedded và one-to-one cần alias đúng

Giả sử root có một thuộc tính address với trường city:

~~~java
class PurchaseOrder {
    private Address address;
}
~~~

Câu query cần trả cột theo tiền tố tên quan hệ và dấu gạch dưới:

~~~sql
SELECT
    o.id,
    o.order_code,
    o.address_city
FROM purchase_orders o
WHERE o.id = :id;
~~~

Quy tắc alias là tên thuộc tính quan hệ cộng dấu gạch dưới rồi đến tên thuộc tính bên trong. Với property address.city, cột cần có nhãn address_city.

Điều này khác với collection lines: collection không được populate bằng cách thêm alias kiểu lines_sku vào query root; nó được tải bằng statement riêng.

## 6. @Query và Single Query Loading

Spring Data JDBC 3.2 giới thiệu Single Query Loading để tải nhiều aggregate bằng một SQL khi aggregate và database đủ điều kiện.

Tuy nhiên, theo giới hạn được tài liệu Spring Data Relational hiện hành mô tả, Single Query Loading chỉ áp dụng cho các phương thức find của CrudRepository, không áp dụng cho:

- Derived query methods.
- Annotated query methods dùng @Query.

Do đó, bật cờ:

~~~java
context.setSingleQueryLoadingEnabled(true);
~~~

không có nghĩa một method @Query sẽ tự động tải root và mọi collection trong một SQL. Method này vẫn dùng cơ chế tải mặc định đối với collection.

Ngoài ra, Single Query Loading còn có các giới hạn khác như nested collections, AggregateReference, embedded entities và hỗ trợ dialect. Hãy xem tài liệu đúng phiên bản Spring Data JDBC trước khi dựa vào chiến lược này.

### 6.1. Bảng so sánh

| Cách truy vấn | Tải root | Collection entity | Single Query Loading |
|---|---|---|---|
| CrudRepository.findById | Query repository | Query riêng theo cách truyền thống | Có thể áp dụng nếu đủ điều kiện |
| CrudRepository.findAll | Query repository | Query riêng theo cách truyền thống | Có thể áp dụng nếu đủ điều kiện |
| Derived query | Query được sinh từ tên method | Query riêng | Không áp dụng theo giới hạn hiện hành |
| Annotated @Query | SQL tùy chỉnh | Query riêng | Không áp dụng theo giới hạn hiện hành |
| DTO/read query | SQL được thiết kế cho dữ liệu đọc | Chỉ trả dữ liệu được query yêu cầu | Không cần aggregate loading |

## 7. String-based @Query có giới hạn gì?

Custom query bằng chuỗi SQL có một số giới hạn cần nhớ.

### 7.1. Chỉ dùng named parameters

Spring Data JDBC hỗ trợ named parameters:

~~~java
@Query("""
    SELECT id, order_code, status
    FROM purchase_orders
    WHERE status = :status
      AND created_at >= :fromDate
    """)
List<PurchaseOrder> findByStatusAndDate(
        @Param("status") String status,
        @Param("fromDate") LocalDateTime fromDate
);
~~~

Không dùng positional placeholder kiểu ?1 như một số module Spring Data khác. Dùng tên tham số rõ ràng giúp SQL dễ đọc và tránh nhầm thứ tự.

Nếu compiler bật cờ -parameters, Spring có thể khám phá tên tham số Java mà không cần @Param. Trong tài liệu và ví dụ, dùng @Param giúp ý định hiển thị rõ.

### 7.2. Không nhận Pageable, Sort hoặc Limit như query parameter

String-based query không hỗ trợ pagination hoặc các tham số Sort, PageRequest, Limit theo cách tự viết lại câu SQL. Nếu cần giới hạn kết quả, phải diễn đạt trực tiếp trong SQL và bind tham số phù hợp.

Ví dụ với PostgreSQL:

~~~java
@Query("""
    SELECT id, order_code, status, created_at
    FROM purchase_orders
    WHERE status = :status
    ORDER BY created_at DESC
    LIMIT :maxRows
    """)
List<PurchaseOrder> findLatestByStatus(
        @Param("status") String status,
        @Param("maxRows") int maxRows
);
~~~

LIMIT là cú pháp PostgreSQL và một số database khác hỗ trợ; cú pháp giới hạn hàng phụ thuộc database. Hãy viết theo dialect thực tế.

Lưu ý rằng giới hạn root không loại bỏ query tải collection. Nếu query trả về 20 root, các collection của 20 aggregate vẫn cần được tải theo chiến lược mapping.

### 7.3. Named query cũng có hành vi tương tự

Spring Data JDBC hỗ trợ named query trong file:

~~~text
META-INF/jdbc-named-queries.properties
~~~

Tên mặc định thường được tạo từ tên domain class và tên repository method, hoặc có thể đặt qua thuộc tính name của @Query.

Named query được xử lý tương tự query khai báo trực tiếp bằng annotation. Vì vậy, việc chuyển SQL từ annotation sang file properties không làm collection loading biến mất.

## 8. Kiểm tra SQL tải bổ sung bằng log

Cách đáng tin cậy nhất để hiểu một method thực sự chạy bao nhiêu SQL là quan sát JDBC statement.

Có thể bật log trong application.yml:

~~~yaml
logging:
  level:
    org.springframework.jdbc.core.JdbcTemplate: DEBUG
    org.springframework.jdbc.core.StatementCreatorUtils: TRACE
~~~

Hoặc bật rộng hơn:

~~~yaml
logging:
  level:
    org.springframework.jdbc: DEBUG
~~~

Log có thể cho thấy:

- Câu SQL tùy chỉnh trong @Query.
- Các câu SELECT tải collection.
- Giá trị tham số bind và kiểu bind nếu bật log chi tiết.
- Các câu SQL khác do service hoặc transaction thực hiện.

Cẩn thận với TRACE trong môi trường có dữ liệu thật: log bind parameter có thể chứa thông tin nhạy cảm. Chỉ bật trong thời gian điều tra và dùng dữ liệu test khi có thể.

### 8.1. Một lần gọi repository trông như thế nào trong log?

Với một đơn hàng và một collection, log có thể thể hiện mô hình:

~~~text
Executing SQL:
SELECT id, order_code, status, created_at
FROM purchase_orders
WHERE status = ?

Executing SQL:
SELECT order_id, line_no, sku, quantity, unit_price
FROM order_lines
WHERE order_id = ?
~~~

Nếu query trả về nhiều đơn hàng, hãy quan sát số lần statement thứ hai được thực thi và các giá trị order_id được bind.

Không chỉ tìm số dòng log. Một statement có thể được log ở nhiều tầng, vì vậy hãy phân biệt log chuẩn bị SQL, log bind parameter và log thực thi statement.

### 8.2. Đếm theo use case

Khi đo query count, hãy:

1. Chuẩn bị dữ liệu cố định.
2. Bắt đầu bộ đếm ngay trước lời gọi repository.
3. Gọi đúng một method.
4. Ghi nhận statement SQL thực thi trong khoảng thời gian đó.
5. Tách câu query root khỏi query tải collection.
6. Kiểm tra số lượng root thực tế được trả về.
7. Lặp lại với một root, 10 root và 100 root.
8. So sánh query count và thời gian.

Không tính câu SQL khởi động, migration hoặc truy vấn health check vào cùng một phép đo.

Có thể dùng datasource proxy hoặc thư viện quan sát JDBC trong integration test để đếm statement thay vì phân tích log bằng mắt. Mục tiêu là đo đúng một thao tác và giữ dữ liệu test ổn định.

## 9. Integration test cho custom query và collection

Một integration test có giá trị nên xác nhận cả kết quả domain và các truy vấn được phát sinh.

Ví dụ kiểm tra kết quả:

~~~java
@DataJdbcTest
class PurchaseOrderRepositoryTest {

    @Autowired
    PurchaseOrderRepository repository;

    @Test
    void customQueryReturnsOrdersWithTheirLines() {
        List<PurchaseOrder> orders =
                repository.findCustomByStatus("OPEN");

        assertThat(orders).hasSize(2);
        assertThat(orders)
                .allSatisfy(order ->
                        assertThat(order.getLines()).isNotNull()
                );
    }
}
~~~

Test này cần fixture tạo sẵn hai đơn hàng cùng các dòng hàng trong database test. Nó xác nhận kết quả đã được dựng thành aggregate, nhưng chưa tự chứng minh query count.

Để đo số statement, tích hợp một datasource proxy hoặc statement counter và reset counter trước lời gọi repository. Sau đó kiểm tra số SELECT root và collection riêng biệt.

Một kịch bản hữu ích:

| Fixture | Root trả về | Collection | Điều cần quan sát |
|---|---:|---|---|
| A | 1 | 1 collection | Query root và query con |
| B | 10 | 1 collection | Query collection có lặp theo root không |
| C | 10 | 2 collection | Có bao nhiêu statement cho từng collection |
| D | 10 | Nested collection | Số query tăng theo từng tầng như thế nào |

Không nên chỉ mock repository hoặc mock RowMapper rồi kết luận về SQL. Query count là hành vi ở tầng JDBC/database nên cần kiểm tra bằng integration test có datasource thật hoặc database test phù hợp.

## 10. Khi nào dùng custom RowMapper hoặc ResultSetExtractor?

Nếu câu query chỉ cần lọc root và vẫn muốn Spring Data JDBC tự dựng collection, dùng RowMapper mặc định là đơn giản nhất. Framework sẽ tải collection theo cơ chế riêng.

Nếu cần điều khiển cách đọc ResultSet, @Query cho phép cấu hình:

- rowMapperClass
- rowMapperRef
- resultSetExtractorClass
- resultSetExtractorRef

### 10.1. RowMapper phù hợp với một dòng kết quả thành một object

RowMapper nhận một hàng ResultSet và chuyển thành một object. Nó phù hợp cho:

- Scalar/primitive result.
- DTO có cấu trúc một hàng.
- Một root được ánh xạ theo cấu trúc cột cụ thể.

Ví dụ định nghĩa một read model:

~~~java
public record PurchaseOrderSummary(
        Long id,
        String orderCode,
        String status
) {
}
~~~

Có thể viết RowMapper riêng để ánh xạ đúng ba cột. Nếu dùng custom RowMapper cho một @Query, đăng ký class hoặc bean theo thuộc tính tương ứng của annotation.

### 10.2. ResultSetExtractor phù hợp khi cần nhóm nhiều hàng

Một câu JOIN có thể trả về nhiều hàng cho cùng một root:

~~~text
order_id | order_code | line_no | sku
---------+------------+---------+---------
100      | SO-100     | 0       | BOOK-01
100      | SO-100     | 1       | PEN-02
101      | SO-101     | 0       | BAG-03
~~~

Nếu muốn dựng một DTO có danh sách dòng hàng từ một ResultSet như vậy, cần nhóm theo order_id:

~~~text
ResultSet
    |
    +-- order_id = 100
    |      +-- OrderSummary #100
    |      +-- Line BOOK-01
    |      +-- Line PEN-02
    |
    +-- order_id = 101
           +-- OrderSummary #101
           +-- Line BAG-03
~~~

ResultSetExtractor cho phép duyệt toàn bộ ResultSet và tự xây dựng cấu trúc nhóm. Đây là cách phù hợp hơn RowMapper đơn giản khi một root xuất hiện trên nhiều hàng.

Tuy nhiên, khi tự nhóm kết quả, bạn chịu trách nhiệm xử lý:

- Root bị lặp qua nhiều hàng.
- Collection rỗng khi LEFT JOIN không có child.
- Thứ tự các phần tử.
- Null và kiểu dữ liệu.
- Trùng child do nhiều JOIN.
- Các quan hệ nested.
- Bộ nhớ khi ResultSet lớn.

### 10.3. Custom mapper có ảnh hưởng lifecycle events

Theo tài liệu Spring Data JDBC, sử dụng custom RowMapper hoặc ResultSetExtractor qua QueryMappingConfiguration, rowMapperClass hoặc resultSetExtractorClass sẽ tắt Entity Callbacks và Lifecycle Events cho quá trình mapping đó. Custom mapping có thể tự thực hiện callbacks/events nếu cần.

Nếu ứng dụng dựa vào auditing hoặc callback sau khi đọc, hãy hiểu rõ tác động này trước khi chuyển sang mapper tùy chỉnh.

## 11. Khi chỉ cần dữ liệu đọc, hãy dùng DTO/read model

Một màn hình tìm kiếm có thể chỉ cần mã đơn, trạng thái và SKU phù hợp. Không nhất thiết phải trả về PurchaseOrder đầy đủ cùng toàn bộ collection.

Ví dụ với NamedParameterJdbcTemplate:

~~~java
public record OrderLineSearchResult(
        Long orderId,
        String orderCode,
        String status,
        String sku,
        int quantity
) {
}
~~~

~~~java
@Repository
public class OrderSearchQuery {

    private final NamedParameterJdbcTemplate jdbc;

    public OrderSearchQuery(NamedParameterJdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    public List<OrderLineSearchResult> findBySku(String sku) {
        String sql = """
            SELECT
                o.id AS order_id,
                o.order_code,
                o.status,
                l.sku,
                l.quantity
            FROM purchase_orders o
            JOIN order_lines l ON l.order_id = o.id
            WHERE l.sku = :sku
            ORDER BY o.id DESC
            """;

        return jdbc.query(
                sql,
                Map.of("sku", sku),
                (rs, rowNum) -> new OrderLineSearchResult(
                        rs.getLong("order_id"),
                        rs.getString("order_code"),
                        rs.getString("status"),
                        rs.getString("sku"),
                        rs.getInt("quantity")
                )
        );
    }
}
~~~

Truy vấn này chỉ trả các dòng phù hợp. Nó không cần tải toàn bộ aggregate và các collection khác.

Phân biệt mục đích:

| Nhu cầu | Cách tiếp cận |
|---|---|
| Thay đổi trạng thái đơn và bảo vệ invariant | Tải aggregate root, gọi domain method, lưu repository |
| Tìm đơn theo điều kiện SQL tùy chỉnh nhưng vẫn cần aggregate đầy đủ | @Query trả về root; chấp nhận collection loading bổ sung |
| Hiển thị danh sách với vài cột | DTO/read query |
| Báo cáo JOIN nhiều bảng | SQL projection, RowMapper hoặc ResultSetExtractor |
| Tối ưu tải aggregate bằng một SQL | Xem Single Query Loading nếu method và aggregate đủ điều kiện |

DTO/read model không thay thế aggregate trong các use case ghi. Nó giúp truy vấn đọc không phải dựng dữ liệu mà màn hình không dùng.

## 12. @Modifying và cập nhật trực tiếp bảng con

@Query cũng có thể dùng với @Modifying để thực hiện UPDATE/DELETE trực tiếp:

~~~java
@Modifying
@Query("""
    UPDATE order_lines
    SET quantity = :quantity
    WHERE order_id = :orderId
      AND line_no = :lineNo
    """)
int updateLineQuantity(
        @Param("orderId") Long orderId,
        @Param("lineNo") Integer lineNo,
        @Param("quantity") Integer quantity
);
~~~

Câu lệnh này cập nhật trực tiếp bảng con mà không tải aggregate root. Nó có thể hữu ích cho một thao tác kỹ thuật được thiết kế rõ, nhưng cần lưu ý:

- Nó không gọi entity lifecycle callbacks/events.
- Auditing fields không tự được cập nhật nếu SQL không tự cập nhật chúng.
- Nó không tự chạy domain method của root.
- Nó có thể bỏ qua invariant như “chỉ sửa dòng khi đơn ở trạng thái OPEN”.
- Nó không tự áp dụng optimistic locking của root.
- Cần kiểm tra số hàng bị cập nhật và xử lý trường hợp không tìm thấy dòng.

Nếu cần cập nhật bảng con trực tiếp, SQL phải thể hiện các điều kiện nghiệp vụ quan trọng, ví dụ:

~~~sql
UPDATE order_lines l
SET quantity = :quantity
WHERE l.order_id = :orderId
  AND l.line_no = :lineNo
  AND EXISTS (
      SELECT 1
      FROM purchase_orders o
      WHERE o.id = l.order_id
        AND o.status = 'OPEN'
  );
~~~

Dù có điều kiện trạng thái, thao tác vẫn cần xem xét concurrency và version. Một custom UPDATE không tự tương đương với việc tải aggregate, kiểm tra invariant trong Java rồi lưu root.

Đối với thao tác nghiệp vụ thường xuyên, nếu phải lặp lại nhiều logic để tái tạo bảo vệ của aggregate, hãy xem lại ranh giới domain hoặc thiết kế một command service phù hợp.

## 13. Những lỗi thường gặp khi đọc custom query có collection

| Triệu chứng/nhận định | Nguyên nhân hoặc cách hiểu | Cách xử lý |
|---|---|---|
| Thấy một câu @Query nhưng log có nhiều SELECT | Collection entity được tải bằng query riêng | Đếm statement theo từng aggregate và collection |
| JOIN child nhưng collection vẫn rỗng hoặc query thêm | RowMapper mặc định không tự nhóm JOIN tùy ý thành collection | Dùng ResultSetExtractor hoặc để framework tải collection riêng |
| Danh sách 100 root chạy rất nhiều SQL | Mẫu N+1 ở collection loading | Đo số query, cân nhắc DTO hoặc chiến lược tải phù hợp |
| Chỉ lọc root theo SKU nhưng muốn collection chỉ chứa SKU đó | Điều kiện root query không tự lọc collection mapping | Dùng DTO/read query dành cho kết quả con |
| Query thiếu cột gây lỗi mapping | Constructor cần cột chưa được SELECT | Trả đủ cột cho constructor và alias đúng |
| Quan hệ one-to-one không được dựng | Alias cột chưa theo tên quan hệ + dấu gạch dưới | Dùng alias như address_city |
| Bật Single Query Loading nhưng @Query vẫn có SQL bổ sung | Annotated query không nằm trong phạm vi hỗ trợ | Dùng CrudRepository find method đủ điều kiện hoặc read query |
| @Query không nhận Pageable/Sort | String-based query không tự viết lại SQL | Đưa ORDER BY/LIMIT/OFFSET vào SQL và bind tham số |
| Custom RowMapper làm callback không chạy | Custom result mapping tắt lifecycle callbacks/events | Tự xử lý callback nếu nghiệp vụ cần |
| @Modifying cập nhật nhưng audit/version không đổi | SQL chạy trực tiếp, bỏ qua lifecycle và domain flow | Tự cập nhật trường cần thiết và kiểm soát invariant/concurrency |

## 14. Quy trình điều tra một method @Query

Khi một method trả về aggregate có collection chạy nhiều SQL, có thể điều tra theo thứ tự:

**Bước 1 — Đọc domain mapping.** Xác định root có bao nhiêu collection, embedded entity và quan hệ one-to-one.

**Bước 2 — Đọc câu SQL custom.** Xem query lấy root hay đang JOIN các bảng con; cột nào được trả về và alias ra sao.

**Bước 3 — Xác định return type.** Method trả root, list root, DTO, stream hay scalar?

**Bước 4 — Dự đoán mapping.** RowMapper mặc định sẽ populate root/embedded/one-to-one; collection entity sẽ được tải riêng.

**Bước 5 — Xem chiến lược tải.** Annotated @Query không dùng Single Query Loading theo giới hạn hiện hành.

**Bước 6 — Bật SQL log.** Ghi lại query root và các statement tải collection.

**Bước 7 — Tăng số root test.** So sánh một root với 10 hoặc 100 root để nhận ra query count có tăng tuyến tính không.

**Bước 8 — Chọn cách đọc.** Nếu cần aggregate đầy đủ, giữ mapping và cân nhắc phương thức find được hỗ trợ Single Query Loading. Nếu chỉ cần kết quả màn hình, dùng DTO/read model. Nếu cần tự nhóm JOIN, dùng ResultSetExtractor và chịu trách nhiệm mapping.

**Bước 9 — Đo lại.** Kiểm tra query count, số hàng, thời gian và lượng dữ liệu trả về trên database mục tiêu.

~~~text
Repository method @Query
        |
        v
Custom SQL tìm root
        |
        v
Default RowMapper map root
        |
        +---- Embedded / one-to-one
        |         -> map từ kết quả query nếu alias đúng
        |
        +---- List / Set / Map of entities
                  -> SQL tải bổ sung
                          |
                          v
                  Đếm statement / phát hiện N+1
                          |
             +------------+-------------+
             |            |             |
             v            v             v
         Aggregate      DTO/read     Custom ResultSet
         đầy đủ         projection   Extractor
             |            |             |
             v            v             v
       Giữ invariant   Chỉ lấy dữ   Tự nhóm ResultSet
       và save root    liệu cần      và quản lý mapping
~~~

## 15. Bài tập tự suy luận

**Tình huống A — Một đơn có 20 dòng hàng**

Một @Query trả về đúng một PurchaseOrder có collection lines. Có thể kết luận 21 câu SQL không?

**Gợi ý:** Không. Một root và một collection thường có query root cùng query collection; 20 là số hàng kết quả, không phải số statement.

**Tình huống B — Một query trả về 100 đơn hàng**

Mỗi đơn có một collection lines. Tải truyền thống có thể tạo mẫu query count nào?

**Gợi ý:** Một query root và các query tải collection cho từng root; mô hình N+1 là 1 + N.

**Tình huống C — Query dùng JOIN để lọc SKU**

Câu query chỉ chọn những đơn có ít nhất một dòng SKU BOOK-01. Collection lines của đơn có chỉ còn các dòng SKU đó không?

**Gợi ý:** Không mặc định. Query root lọc đơn; collection aggregate được tải theo mapping riêng và có thể chứa tất cả dòng của đơn.

**Tình huống D — Muốn trả root cùng collection bằng một ResultSet JOIN**

Chỉ thêm JOIN vào @Query có đủ không?

**Gợi ý:** Không. RowMapper mặc định không tự nhóm mọi hàng JOIN thành collection. Cần ResultSetExtractor hoặc custom mapping có trách nhiệm gom root và child.

**Tình huống E — Bật Single Query Loading**

Method @Query có tự động chuyển sang Single Query Loading không?

**Gợi ý:** Không theo giới hạn hiện hành; chiến lược này chỉ áp dụng cho các find methods của CrudRepository khi đủ điều kiện.

**Tình huống F — Cập nhật child bằng @Modifying**

Câu UPDATE trực tiếp bảng order_lines có tự kiểm tra trạng thái root, gọi callbacks và cập nhật version không?

**Gợi ý:** Không. Đây là modifying query chạy trực tiếp; phải tự thể hiện điều kiện nghiệp vụ, auditing và concurrency cần thiết.

## 16. Ghi nhớ

| Thành phần | Vai trò |
|---|---|
| @Query | Khai báo SQL tùy chỉnh để tìm root |
| Default RowMapper | Ánh xạ root, embedded và one-to-one từ ResultSet |
| Collection entity | List, Set, Map, entity arrays; được tải bằng SQL riêng |
| @MappedCollection | Xác định bảng con và cột liên kết với root |
| N+1 | Query root cộng các query bổ sung theo từng root |
| @Query + JOIN | Không tự động nhóm ResultSet thành collection |
| ResultSetExtractor | Tự nhóm nhiều hàng thành cấu trúc đọc |
| DTO/read model | Chỉ tải dữ liệu cần cho màn hình/báo cáo |
| Single Query Loading | Không áp dụng cho annotated @Query theo giới hạn hiện hành |
| @Modifying | Thực thi SQL trực tiếp, không chạy lifecycle callbacks/events |
| SQL logging | Cách xác nhận query bổ sung thực tế |

**Một câu SQL tùy chỉnh không đồng nghĩa một lần đọc aggregate chỉ có một statement.** @Query lấy root và RowMapper mặc định ánh xạ các thuộc tính được hỗ trợ; collection entity vẫn được tải bằng SQL riêng. Khi trả về nhiều root, điều đó có thể tạo N+1. Hãy kiểm tra log SQL, phân biệt aggregate loading với DTO/read query, và chỉ tự JOIN/group ResultSet khi bạn sẵn sàng chịu trách nhiệm cho mapping cùng các lifecycle behavior liên quan.
