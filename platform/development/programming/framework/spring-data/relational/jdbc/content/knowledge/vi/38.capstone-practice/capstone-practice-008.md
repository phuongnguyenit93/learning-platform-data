# Kiểm thử với Testcontainers và đo chi phí truy vấn

Một repository test chạy trên H2 có thể xác nhận mapping và CRUD cơ bản, nhưng không chứng minh câu SQL hoạt động giống PostgreSQL hoặc MySQL trong production. Database engine, JDBC driver, kiểu dữ liệu, index, optimizer và transaction behavior đều ảnh hưởng đến kết quả. **Testcontainers** giúp chạy database thật trong container để integration test sử dụng cùng engine với môi trường triển khai.

Sau khi test chạy đúng, bước tiếp theo là hiểu chi phí truy vấn. Một method repository có thể thực thi nhiều câu SQL, tải nhiều hàng hơn cần thiết hoặc dùng execution plan không hiệu quả. Cần kết hợp ba loại bằng chứng:

1. **Integration test trên database thật:** xác minh mapping, constraint, transaction và query behavior.
2. **Đo ở tầng JDBC/repository:** đếm statement, đo thời gian thực thi và phát hiện N+1.
3. **Execution plan của database:** xem optimizer đọc bảng/index, ước lượng số hàng và thực tế xử lý bao nhiêu dữ liệu.

## 1. Vì sao dùng Testcontainers?

Testcontainers khởi chạy database trong Docker container và cung cấp connection tới database đó cho test. Với Spring Boot, annotation **@ServiceConnection** có thể tạo connection details tự động từ container.

Với PostgreSQL:

~~~mermaid
flowchart TD
    Test["Spring Data JDBC integration test"]
    Boot["@DataJdbcTest + @ServiceConnection"]
    Container["PostgreSQLContainer"]
    Details["JdbcConnectionDetails"]
    DataSource["Boot DataSource + PostgreSQL driver"]
    Repo["Spring Data JDBC Repository"]
    DB[("PostgreSQL trong Docker")]
    Test --> Boot --> Container
    Container --> Details --> DataSource
    Boot --> Repo --> DataSource --> DB
~~~

Test dùng đúng SQL dialect, kiểu dữ liệu và optimizer của PostgreSQL. Container cũng giúp mỗi lần chạy test có môi trường database được kiểm soát và có thể tái tạo.

Testcontainers không tự làm test trở thành benchmark production. Tốc độ còn phụ thuộc CPU/RAM Docker, storage, cache, network, phiên bản database và lượng dữ liệu được nạp.

## 2. Khai báo dependency

Ví dụ dưới đây dùng Spring Boot 4.x, Spring Data JDBC và PostgreSQL Testcontainers:

~~~groovy
dependencies {
    testImplementation("org.springframework.boot:spring-boot-starter-test")
    testImplementation("org.springframework.boot:spring-boot-data-jdbc-test")
    testImplementation("org.springframework.boot:spring-boot-testcontainers")

    testImplementation("org.testcontainers:postgresql")
    testImplementation("org.testcontainers:junit-jupiter")
    testRuntimeOnly("org.postgresql:postgresql")
}
~~~

Để các version được Spring Boot dependency management/BOM quản lý. Nếu dùng Spring Boot 3.x, tên module test và package annotation khác; cần dùng import/dependency tương ứng với phiên bản dự án.

Docker daemon phải hoạt động khi chạy test. Testcontainers sẽ tải image nếu image chưa có trên máy, khởi động container và dừng container theo lifecycle đã cấu hình.

## 3. Viết repository integration test với PostgreSQL

Ví dụ entity Order:

~~~java
package com.example.sales.order;

import java.time.Instant;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Table;

@Table("orders")
public class Order {

    @Id
    private Long id;

    private Long customerId;
    private String status;
    private Instant createdAt;

    protected Order() {
    }

    public Order(Long customerId, String status, Instant createdAt) {
        this.customerId = customerId;
        this.status = status;
        this.createdAt = createdAt;
    }

    public Long getId() {
        return id;
    }

    public Long getCustomerId() {
        return customerId;
    }

    public String getStatus() {
        return status;
    }

    public Instant getCreatedAt() {
        return createdAt;
    }
}
~~~

Repository:

~~~java
package com.example.sales.order;

import java.util.List;

import org.springframework.data.domain.Pageable;
import org.springframework.data.jdbc.repository.query.Query;
import org.springframework.data.repository.CrudRepository;
import org.springframework.data.repository.query.Param;

public interface OrderRepository extends CrudRepository<Order, Long> {

    List<Order> findByCustomerIdAndStatusOrderByCreatedAtDesc(
        Long customerId,
        String status,
        Pageable pageable
    );

    @Query("""
        SELECT *
        FROM orders
        WHERE customer_id = :customerId
          AND status = :status
        ORDER BY created_at DESC
        LIMIT :limit
        """)
    List<Order> findRecentOrders(
        @Param("customerId") Long customerId,
        @Param("status") String status,
        @Param("limit") int limit
    );
}
~~~

Schema migration:

~~~sql
CREATE TABLE orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL
);
~~~

Repository method có derived query và method dùng @Query đều được kiểm thử trên PostgreSQL. Điều này giúp phát hiện khác biệt về mapping cột, kiểu timestamp, giới hạn kết quả và cú pháp SQL.

## 4. Khởi động PostgreSQLContainer và kết nối bằng @ServiceConnection

Test class:

~~~java
package com.example.sales.order;

import java.time.Instant;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.data.jdbc.test.autoconfigure.DataJdbcTest;
import org.springframework.boot.jdbc.test.autoconfigure.AutoConfigureTestDatabase;
import org.springframework.boot.jdbc.test.autoconfigure.AutoConfigureTestDatabase.Replace;
import org.springframework.boot.testcontainers.service.connection.ServiceConnection;
import org.testcontainers.containers.PostgreSQLContainer;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;

import static org.assertj.core.api.Assertions.assertThat;

@DataJdbcTest
@Testcontainers
@AutoConfigureTestDatabase(replace = Replace.NONE)
class OrderRepositoryPostgresTests {

    @Container
    @ServiceConnection
    static final PostgreSQLContainer<?> postgres =
        new PostgreSQLContainer<>("postgres:17-alpine");

    @Autowired
    private OrderRepository orders;

    @Test
    void savesAndLoadsOrder() {
        Order saved = orders.save(
            new Order(101L, "OPEN", Instant.parse("2026-01-10T10:00:00Z"))
        );

        Order loaded = orders.findById(saved.getId()).orElseThrow();

        assertThat(loaded.getCustomerId()).isEqualTo(101L);
        assertThat(loaded.getStatus()).isEqualTo("OPEN");
    }
}
~~~

**@ServiceConnection** tạo connection details từ PostgreSQL container. **Replace.NONE** nói rõ rằng test phải giữ DataSource kết nối container. Trong các phiên bản Spring Boot hiện hành, **Replace.NON_TEST** cũng có thể giữ DataSource auto-configured được nhận diện là test database.

Với **@DataJdbcTest**, Spring Boot chỉ tải các cấu hình cần cho Spring Data JDBC; component thông thường và configuration properties không tự động được scan. Nếu test cần một bean cấu hình riêng, hãy import nó hoặc dùng **@EnableConfigurationProperties**.

### Transaction của DataJdbcTest

DataJdbcTest mặc định chạy test method trong transaction và rollback khi kết thúc. Điều này giúp các test độc lập với nhau. Container PostgreSQL có thể được dùng chung cho các method trong class, trong khi dữ liệu tạo trong transaction của mỗi test được rollback.

Nếu muốn kiểm tra dữ liệu đã commit hoặc chạy benchmark qua nhiều connection, cần thiết kế transaction boundary riêng. Không suy luận rằng container bị xóa sau mỗi test; container thường sống theo lifecycle class/test suite.

## 5. Tạo schema và dữ liệu kiểm thử có thể tái lập

Một test có 3 hàng dữ liệu không đủ để đánh giá index hoặc optimizer trên bảng có hàng trăm nghìn bản ghi. Muốn đo query cost, dataset phải phản ánh tương đối:

- Số lượng hàng.
- Phân bố customer/status.
- Tỷ lệ giá trị phổ biến và hiếm.
- Tỷ lệ NULL nếu schema cho phép.
- Độ dài chuỗi và kích thước các cột.
- Quan hệ giữa bảng root và collection con.

Có thể dùng Flyway/Liquibase để tạo schema giống production, sau đó dùng fixture SQL riêng để nạp dữ liệu kiểm thử.

Ví dụ PostgreSQL tạo dữ liệu lớn trong môi trường test:

~~~sql
INSERT INTO orders (customer_id, status, created_at)
SELECT
    1 + (g % 10000),
    CASE
        WHEN g % 5 = 0 THEN 'CANCELLED'
        WHEN g % 3 = 0 THEN 'CONFIRMED'
        ELSE 'OPEN'
    END,
    TIMESTAMPTZ '2025-01-01 00:00:00+00'
        + (g % 365) * INTERVAL '1 day'
FROM generate_series(1, 200000) AS g;

ANALYZE orders;
~~~

Đoạn seed này dùng PostgreSQL-specific function **generate_series**. Nó tạo 200.000 hàng với phân bố customer và status có thể tái lập. Lệnh **ANALYZE** cập nhật thống kê mà PostgreSQL optimizer dùng khi chọn execution plan.

Với bảng lớn, nên nạp dữ liệu ở bước setup đã commit hoặc bằng migration/fixture riêng. Nếu test slice đang bọc toàn bộ test trong transaction, hãy hiểu rõ transaction nào nhìn thấy dữ liệu và thời điểm thống kê được cập nhật.

Không dùng dữ liệu thật có thông tin cá nhân hoặc bí mật production trong container test. Hãy tạo dữ liệu tổng hợp nhưng giữ phân bố gần với workload cần đo.

## 6. Kiểm thử chức năng trước khi đo hiệu năng

Trước khi xem query plan, xác minh query trả đúng dữ liệu:

~~~java
@Test
void findsRecentOpenOrdersForCustomer() {
    List<Order> result = orders.findRecentOrders(101L, "OPEN", 20);

    assertThat(result)
        .hasSizeLessThanOrEqualTo(20)
        .allSatisfy(order -> {
            assertThat(order.getCustomerId()).isEqualTo(101L);
            assertThat(order.getStatus()).isEqualTo("OPEN");
        });
}
~~~

Một query nhanh nhưng trả thiếu hàng, sai thứ tự hoặc bỏ sót điều kiện nghiệp vụ không phải tối ưu thành công. Kiểm thử tính đúng đắn phải đứng trước đo chi phí.

Các tình huống nên có:

- Customer không có Order.
- Customer có nhiều Order.
- Status phổ biến và status hiếm.
- Trang đầu và trang sâu.
- Giá trị filter biên và dữ liệu lớn.
- Aggregate có collection con nếu query tải cả aggregate.
- Transaction rollback và constraint violation.

## 7. Đo thời gian repository method

Có thể đo thời gian từ lúc gọi repository đến khi method trả kết quả bằng System.nanoTime:

~~~java
long start = System.nanoTime();

List<Order> result = orders.findRecentOrders(101L, "OPEN", 50);

long elapsedNanos = System.nanoTime() - start;
long elapsedMicros = TimeUnit.NANOSECONDS.toMicros(elapsedNanos);

log.info("findRecentOrders returned {} rows in {} microseconds",
    result.size(), elapsedMicros);
~~~

Đo ở tầng repository bao gồm nhiều chi phí hơn thời gian SQL:

- Lấy connection.
- Gửi query và nhận dữ liệu.
- Đọc ResultSet.
- Mapping hàng thành domain object.
- Xây dựng collection và trả kết quả.

Đây là con số gần với chi phí mà application service quan sát được. Nó không thay thế execution plan của database.

Không nên viết test chức năng kiểu “query phải chạy dưới 20 ms” trong CI thông thường. Thời gian có thể thay đổi theo CPU, tải máy, Docker, cache và tài nguyên CI. Hãy ghi nhận thời gian hoặc dùng ngưỡng rộng trong performance suite riêng.

## 8. Đếm câu SQL và phát hiện N+1

Một method repository có thể thực thi nhiều statement do aggregate mapping, collection con, query phụ hoặc code gọi repository lặp lại. Đếm statement giúp phát hiện N+1 và những thay đổi làm tăng số lần truy cập database.

Thư viện **datasource-proxy** có thể bọc DataSource để ghi log query, thời gian, số SELECT/INSERT/UPDATE/DELETE và các lỗi thực thi.

Dependency test:

~~~groovy
dependencies {
    testImplementation("net.ttddyy:datasource-proxy:1.11.1")
}
~~~

Tạo proxy từ DataSource gốc:

~~~java
DataSource observedDataSource =
    ProxyDataSourceBuilder.create(actualDataSource)
        .name("orders-test")
        .countQuery()
        .afterQuery((executionInfo, queryInfoList) -> {
            if (executionInfo.getElapsedTime() >= 100) {
                log.warn("Slow SQL: {} ms, queries={}",
                    executionInfo.getElapsedTime(),
                    queryInfoList.size());
            }
        })
        .build();
~~~

Proxy phải được đăng ký làm DataSource mà JdbcTemplate/Spring Data JDBC thực sự sử dụng trong test context. Hãy bọc DataSource gốc thay vì tạo một connection pool thứ hai. Chỉ bật query/parameter logging trong test hoặc môi trường kiểm soát vì SQL parameters có thể chứa dữ liệu nhạy cảm.

Sau khi bật query counting:

~~~java
QueryCountHolder.clear();

List<Order> result = orders.findRecentOrders(101L, "OPEN", 20);

QueryCount count = QueryCountHolder.getGrandTotal();
log.info("SELECT={}, total={}, elapsed={} ms",
    count.getSelect(),
    count.getTotal(),
    count.getTime());
~~~

QueryCountHolder mặc định lưu số liệu theo thread-local. Hãy gọi clear trước mỗi phép đo/test và lưu ý rằng tác vụ chạy ở thread khác không tự cộng vào counter của thread hiện tại. Có thể dùng SingleQueryCountHolder khi cần số liệu tích lũy qua nhiều thread, nhưng phải chủ động reset.

### Nhận biết N+1

Giả sử một service tải 100 customer rồi gọi repository lấy Order cho từng customer:

~~~java
for (Customer customer : customers) {
    List<Order> customerOrders =
        orders.findByCustomerId(customer.getId());
    // Xử lý kết quả.
}
~~~

Mẫu code này có thể tạo 1 query lấy customer và thêm 100 query lấy Order. Query count tăng theo số customer.

Hãy so sánh số statement khi test với 1, 10 và 100 parent records. Nếu query count tăng tuyến tính ngoài dự kiến, kiểm tra các vòng lặp gọi repository, cách tải aggregate và khả năng dùng query theo tập ID hoặc read projection.

Không mặc định mọi aggregate load chỉ cần một statement. Điều cần kiểm tra là số query có phù hợp với mapping và không tăng bất ngờ theo số hàng.

## 9. Xem query plan bằng EXPLAIN của PostgreSQL

PostgreSQL cung cấp **EXPLAIN** để hiển thị execution plan mà optimizer chọn. Thêm **ANALYZE** để thực thi câu lệnh và hiển thị số liệu thực tế; thêm **BUFFERS** để xem hoạt động đọc/ghi buffer.

Ví dụ:

~~~sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, customer_id, status, created_at
FROM orders
WHERE customer_id = 101
  AND status = 'OPEN'
ORDER BY created_at DESC
LIMIT 50;
~~~

Các thành phần cần đọc:

| Thông tin | Ý nghĩa |
|---|---|
| Startup cost / total cost | Chi phí optimizer ước lượng, không phải thời gian millisecond |
| rows | Số hàng optimizer ước lượng ở node |
| actual time | Thời gian thực tế ở node |
| actual rows | Số hàng thực tế node trả về |
| loops | Số lần node được thực thi |
| Buffers: shared hit | Block đã có trong shared buffer |
| Buffers: shared read | Block phải đọc từ storage vào shared buffer |
| temp read/written | Dữ liệu tạm được đọc/ghi, thường liên quan sort/hash lớn |

**EXPLAIN ANALYZE thực sự chạy query.** Với SELECT, nó đọc dữ liệu như câu lệnh bình thường. Với INSERT/UPDATE/DELETE, nó thực thi thao tác ghi; chỉ chạy trên dữ liệu test và dùng transaction rollback nếu phù hợp.

### Đọc estimated rows và actual rows

Nếu optimizer ước lượng 20 hàng nhưng thực tế trả 50.000 hàng, thống kê hoặc phân bố dữ liệu có thể khác giả định của optimizer. Kiểm tra:

- Thống kê bảng/index đã cập nhật chưa.
- Giá trị filter có phân bố lệch/skew không.
- Các cột có tương quan mà optimizer chưa biết không.
- Parameter thực tế có chọn giá trị rất phổ biến hay rất hiếm.

Với PostgreSQL, chạy ANALYZE sau khi nạp dữ liệu lớn trong môi trường benchmark:

~~~sql
ANALYZE orders;
~~~

Sequential Scan không phải lúc nào cũng xấu. Với bảng nhỏ hoặc query trả phần lớn hàng, đọc tuần tự có thể rẻ hơn index lookup. Hãy đánh giá số hàng, buffers, actual time và workload thay vì chỉ nhìn tên node.

## 10. Xem query plan bằng EXPLAIN ANALYZE của MySQL

MySQL 8.4 hỗ trợ:

~~~sql
EXPLAIN ANALYZE
SELECT id, customer_id, status, created_at
FROM orders
WHERE customer_id = 101
  AND status = 'OPEN'
ORDER BY created_at DESC
LIMIT 50;
~~~

MySQL hiển thị plan dạng TREE với thông tin như:

- Estimated cost và estimated rows.
- Actual time để trả hàng đầu tiên và hoàn tất iterator.
- Actual rows được trả về.
- Số vòng lặp của iterator.

EXPLAIN ANALYZE cũng thực thi câu SELECT. Cú pháp và loại statement được hỗ trợ khác với PostgreSQL; hãy dùng tài liệu đúng phiên bản MySQL đang chạy trong container.

## 11. Ví dụ tối ưu index dựa trên query plan

Query thường dùng:

~~~sql
SELECT id, customer_id, status, created_at
FROM orders
WHERE customer_id = 101
  AND status = 'OPEN'
ORDER BY created_at DESC
LIMIT 50;
~~~

Nếu plan cho thấy database phải scan nhiều hàng rồi sort trước khi lấy 50 kết quả, có thể thử index ghép:

~~~sql
CREATE INDEX idx_orders_customer_status_created
ON orders(customer_id, status, created_at DESC);
~~~

Index này đặt các cột equality filter trước, sau đó là cột sort. Đây là giả thuyết cần kiểm chứng bằng execution plan và workload thực tế, không phải công thức đúng cho mọi query.

Sau khi tạo index:

1. Chạy lại cùng query với cùng dữ liệu và parameter.
2. So sánh estimated/actual rows.
3. So sánh buffers đọc và thời gian thực tế.
4. Kiểm tra query có bỏ được sort hoặc giảm số hàng cần đọc không.
5. Đo cả chi phí ghi vì index mới làm INSERT/UPDATE/DELETE tốn thêm công việc.

Không thêm index chỉ để một test cụ thể chạy nhanh. Mỗi index tiêu tốn storage, tăng chi phí ghi và cần bảo trì.

## 12. Phân biệt query cost, query latency và repository latency

Ba con số thường được gọi chung là “chi phí truy vấn” nhưng đo những thứ khác nhau:

| Chỉ số | Đo gì | Công cụ |
|---|---|---|
| Optimizer cost | Ước lượng nội bộ để so sánh plan | EXPLAIN |
| Database execution time | Thời gian thực thi ở database | EXPLAIN ANALYZE, database monitoring |
| JDBC statement elapsed time | Thời gian gọi execute qua JDBC | datasource-proxy, JDBC listener |
| Repository method latency | Thời gian từ lúc gọi method đến khi trả object | Timer/StopWatch/Micrometer |
| Request latency | Thời gian toàn bộ request | HTTP metrics/tracing |

Optimizer cost không phải millisecond và không thể so sánh trực tiếp giữa PostgreSQL và MySQL. JDBC elapsed time có thể bao gồm network round trip và driver processing. Repository latency còn bao gồm mapping object và các thao tác Java sau khi query trả về.

Để tìm bottleneck, hãy đặt các số liệu cạnh nhau thay vì chỉ chọn một chỉ số.

## 13. Metrics với Spring Boot Actuator và Micrometer

Khi có Actuator và Micrometer phù hợp trên classpath, Spring Boot có thể tự instrument DataSource và Spring Data repository:

- **jdbc.connections**: số connection active, idle, maximum và minimum của pool.
- **hikaricp**: các metric riêng của HikariCP.
- **spring.data.repository.invocations**: thời gian và số lần gọi repository method.

Repository metrics cho biết method nào được gọi nhiều hoặc có latency cao. DataSource metrics cho biết pool đang bị sử dụng đến mức nào. Chúng không thay thế query-level logging hoặc EXPLAIN plan.

Ví dụ cấu hình dependency Actuator:

~~~groovy
dependencies {
    implementation("org.springframework.boot:spring-boot-starter-actuator")
    runtimeOnly("io.micrometer:micrometer-registry-prometheus")
}
~~~

Các endpoint/registry được expose theo cấu hình quản trị của ứng dụng. Không mở metrics endpoint ra ngoài phạm vi vận hành được phép; metric tags cũng cần tránh chứa SQL parameter hoặc dữ liệu cá nhân.

## 14. Phương pháp đo lặp lại có ý nghĩa

Một phép đo duy nhất không đủ để kết luận query đã nhanh hơn. Hãy kiểm soát:

### Dataset

- Cùng số lượng hàng và phân bố dữ liệu.
- Cùng index, constraint và migration.
- Cùng giá trị parameter hoặc cùng nhóm parameter đại diện.
- Cập nhật statistics sau khi seed.

### Môi trường

- Cùng phiên bản PostgreSQL/MySQL và JDBC driver.
- Cùng CPU/RAM giới hạn cho container.
- Tránh chạy nhiều benchmark cạnh tranh trên cùng Docker host.
- Phân biệt lần chạy cold cache và warm cache.
- Không tính thời gian pull image/container startup vào thời gian query.

### Quy trình đo

1. Chạy một số lượt warm-up để JVM, driver và database ổn định.
2. Chạy nhiều lần với cùng điều kiện.
3. Ghi median và percentile như p95, không chỉ lấy một lần nhanh nhất.
4. Ghi query count, result row count, execution plan và buffers.
5. Đo trước/sau thay đổi index hoặc SQL bằng cùng dataset.
6. Kiểm tra kết quả trả về vẫn giống nhau.

Không nên dùng một ngưỡng thời gian quá chặt trong unit test thông thường. CI runner và Docker host có tải khác nhau. Hãy giữ assertion chức năng và query-count regression trong test suite chính; chạy benchmark latency trong pipeline/performance environment riêng.

## 15. Dùng Testcontainers cho query-plan regression

Một test chuyên biệt có thể xác minh query vẫn trả đúng dữ liệu và execution plan không bị thay đổi theo hướng xấu rõ rệt. Tuy nhiên, plan text có thể thay đổi giữa database version và statistics, vì vậy tránh so sánh toàn bộ output bằng chuỗi cố định.

Có thể kiểm tra những đặc tính có ý nghĩa:

- Query không tạo số statement bất thường.
- Không tải hàng chục nghìn hàng khi chỉ cần 50 hàng.
- Index quan trọng vẫn tồn tại.
- Số hàng thực tế và số vòng lặp không tăng bất thường.
- Query trả đúng thứ tự và giới hạn kết quả.

Nếu cần assertion dựa trên plan, hãy parse output theo database version và chỉ kiểm tra những điều kiện ổn định. Đừng buộc mọi test phải dùng một loại scan cụ thể; optimizer có thể chọn plan khác mà vẫn nhanh hơn.

## 16. Các lỗi thường gặp

| Lỗi | Hệ quả | Cách xử lý |
|---|---|---|
| Chỉ test trên H2 | Không phát hiện khác biệt dialect/driver | Dùng Testcontainers với database production |
| Dùng dataset quá nhỏ | Optimizer chọn plan không đại diện | Seed dữ liệu có cardinality và skew thực tế |
| Đo ngay query đầu tiên | Cache/JIT/container startup làm sai số | Warm-up và đo nhiều lượt |
| Chỉ nhìn EXPLAIN cost | Nhầm cost ước lượng với thời gian thực | Dùng ANALYZE và actual metrics |
| Không cập nhật statistics sau seed | Optimizer ước lượng sai | Chạy ANALYZE hoặc lệnh cập nhật stats tương ứng |
| Chỉ đo repository method | Không biết query nào gây chậm | Kết hợp JDBC query listener và execution plan |
| Chỉ đếm query, không đo số hàng | Query ít nhưng tải quá nhiều dữ liệu | Theo dõi rows và result size |
| Không nhận diện N+1 | Query count tăng theo số parent | So sánh query count khi tăng kích thước dữ liệu |
| Thêm index theo cảm tính | Tăng storage và chi phí ghi | Đo plan trước/sau và kiểm tra workload |
| Dùng EXPLAIN ANALYZE trên dữ liệu thật mà không kiểm soát | Query ghi có thể thực sự thay đổi dữ liệu | Chỉ chạy trên test data, transaction rollback nếu phù hợp |
| Assert latency rất thấp trong CI | Test flaky theo tài nguyên runner | Dùng benchmark suite riêng |
| Log toàn bộ SQL parameters trong production | Có thể lộ dữ liệu nhạy cảm | Giới hạn logging và che/redact parameter |

## 17. Quy trình thực hành đề xuất

1. Tạo PostgreSQL Testcontainer với cùng major version như production.
2. Dùng @ServiceConnection để Boot cấu hình JDBC DataSource.
3. Dùng @DataJdbcTest cho repository/mapping tests và giữ DataSource container bằng Replace.NONE hoặc chính sách NON_TEST phù hợp.
4. Chạy Flyway/Liquibase để tạo schema giống ứng dụng.
5. Seed dataset đại diện và cập nhật database statistics.
6. Viết functional tests xác minh kết quả, thứ tự, constraint và transaction.
7. Bật datasource-proxy trong test để ghi query count và elapsed time.
8. Dùng EXPLAIN ANALYZE để kiểm tra execution plan của query chậm.
9. Thử index hoặc query rewrite rồi đo lại với cùng dataset.
10. Dùng Actuator/Micrometer để theo dõi repository latency và pool metrics ở môi trường chạy thật.
11. Tách performance benchmark khỏi unit test để tránh CI flakiness.
12. Ghi lại database version, driver version, dataset size, index và cấu hình container cùng kết quả đo.

## 18. Bài thực hành

1. Tạo OrderRepository với derived query lọc customer/status và sắp xếp theo createdAt.
2. Chạy repository test trên PostgreSQLContainer với @DataJdbcTest và @ServiceConnection.
3. Tạo schema bằng Flyway và seed tối thiểu 200.000 Order trong container.
4. Chạy ANALYZE sau khi seed dữ liệu PostgreSQL.
5. Gọi repository method và đo thời gian bằng System.nanoTime hoặc Micrometer Timer.
6. Bọc DataSource bằng datasource-proxy trong test context; ghi query count và thời gian từng statement.
7. Tăng số parent/child records và kiểm tra query count để phát hiện N+1.
8. Chạy EXPLAIN (ANALYZE, BUFFERS) cho query PostgreSQL; ghi lại actual rows, loops và buffers.
9. Thêm index ghép theo filter/sort; chạy lại cùng query và so sánh plan.
10. Thực hiện cùng bài tập trên MySQL 8.4 với EXPLAIN ANALYZE.
11. Bật Actuator metrics và quan sát repository invocation cùng connection pool metrics.
12. Thiết kế performance test lặp nhiều lượt, ghi median/p95 và không dùng một ngưỡng timing quá chặt cho CI thông thường.

## 19. Ghi nhớ

Testcontainers cho Spring Data JDBC kiểm thử repository trên đúng database engine và JDBC driver, giúp phát hiện khác biệt mà embedded database có thể che giấu. Dùng @DataJdbcTest để kiểm thử slice repository, @ServiceConnection để tạo JDBC connection details và migration/fixture để chuẩn bị schema cùng dữ liệu có thể tái lập.

Đo chi phí truy vấn cần kết hợp query count, JDBC statement elapsed time, repository latency và execution plan. PostgreSQL EXPLAIN (ANALYZE, BUFFERS) và MySQL EXPLAIN ANALYZE cung cấp số liệu thực tế về rows, loops, thời gian và hoạt động đọc dữ liệu; datasource-proxy giúp đếm và ghi thời gian JDBC; Actuator/Micrometer theo dõi repository cùng connection pool. Đo nhiều lần trên dataset đại diện, so sánh trước/sau cùng điều kiện và luôn xác minh kết quả chức năng trước khi kết luận tối ưu.
