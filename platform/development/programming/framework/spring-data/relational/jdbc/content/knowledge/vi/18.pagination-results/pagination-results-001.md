# Phân biệt `List`, `Iterable`, `Optional` và kết quả đơn

Trong **Spring Data JDBC**, kiểu trả về của repository method cho biết ứng dụng mong đợi **không có, một hay nhiều kết quả** và cách caller sẽ sử dụng tập kết quả đó. Các kiểu thường gặp gồm `Optional<T>`, một đối tượng `T`, `Iterable<T>` và `List<T>`.

Điểm cần phân biệt:

- **`Optional<T>`** biểu diễn một kết quả có thể không tồn tại: có một object thì `Optional` chứa object, không có thì `Optional.empty()`.
- **`T` (một đối tượng trực tiếp)** biểu diễn một kết quả đơn; nếu không có hàng, kết quả thường là `null`. Nếu truy vấn trả nhiều hơn một hàng trong khi method chỉ nhận một kết quả, Spring Data báo lỗi kích thước kết quả.
- **`Iterable<T>`** biểu diễn một tập nhiều kết quả có thể duyệt bằng `for-each` hoặc iterator, nhưng không có thao tác truy cập theo index.
- **`List<T>`** biểu diễn một tập nhiều kết quả có thứ tự truy cập theo chỉ số, có `size()` và các thao tác của List.

Kiểu trả về cần khớp với **cardinality** của truy vấn và ý nghĩa nghiệp vụ. Dùng `Optional` cho một khách hàng tìm theo email duy nhất; dùng `List` hoặc `Iterable` cho một truy vấn có thể trả nhiều khách hàng; dùng `T` trực tiếp khi hợp đồng cho phép caller xử lý giá trị không tìm thấy dưới dạng `null`.

## 1. Ví dụ xuyên suốt: truy vấn khách hàng

Giả sử database có bảng:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(120) NOT NULL,
    email VARCHAR(200) NOT NULL UNIQUE,
    city VARCHAR(100) NOT NULL,
    active BOOLEAN NOT NULL
);
```

Entity:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Table;

@Table("customers")
public record Customer(
        @Id Long id,
        String name,
        String email,
        String city,
        boolean active
) {}
```

Repository có thể khai báo nhiều kiểu trả về tùy mục đích:

```java
import java.util.List;
import java.util.Optional;
import org.springframework.data.repository.CrudRepository;
import org.springframework.data.repository.query.Param;

public interface CustomerRepository
        extends CrudRepository<Customer, Long> {

    Optional<Customer> findByEmail(String email);

    Customer findCustomerById(Long id);

    List<Customer> findByCity(String city);

    Iterable<Customer> findByActiveTrue();
}
```

Các method trên cùng truy vấn bảng `customers`, nhưng hợp đồng kết quả khác nhau. `findByEmail` kỳ vọng tối đa một hàng vì email có ràng buộc `UNIQUE`; `findByCity` có thể trả nhiều khách hàng; `findByActiveTrue` cũng có thể trả một tập kết quả.

## 2. `Optional<T>`: một kết quả có thể vắng mặt

`Optional<T>` phù hợp với truy vấn kỳ vọng tối đa một đối tượng nhưng bản ghi có thể không tồn tại.

Ví dụ:

```java
Optional<Customer> findByEmail(String email);
```

Khi gọi:

```java
Optional<Customer> result = customers.findByEmail("lan@example.com");

if (result.isPresent()) {
    Customer customer = result.get();
    System.out.println(customer.name());
} else {
    System.out.println("Không tìm thấy khách hàng");
}
```

Có thể dùng các phương thức tiện ích:

```java
Customer customer = customers.findByEmail("lan@example.com")
        .orElseThrow(() -> new IllegalArgumentException("Customer not found"));
```

Hoặc cung cấp giá trị dự phòng:

```java
Optional<Customer> result = customers.findByEmail("lan@example.com");
Customer customer = result.orElse(defaultCustomer);
```

Hành vi:

| Số hàng phù hợp | Kết quả |
|---:|---|
| 0 | `Optional.empty()` |
| 1 | `Optional.of(customer)` |
| Nhiều hơn 1 | Lỗi kích thước kết quả, vì method yêu cầu một kết quả đơn |

`Optional` giúp caller xử lý trường hợp không tìm thấy một cách tường minh, tránh phải kiểm tra `null` ở mọi nơi. Tuy nhiên, nó **không có nghĩa** truy vấn được phép trả nhiều hàng và Spring Data tự chọn một hàng bất kỳ.

## 3. Trả về trực tiếp `T`: kết quả đơn có thể là `null`

Một repository method cũng có thể khai báo kiểu entity trực tiếp:

```java
Customer findCustomerById(Long id);
```

Với truy vấn đơn:

- Có đúng một hàng: trả về `Customer`.
- Không có hàng: kết quả có thể là `null`.
- Có nhiều hàng: Spring Data báo lỗi kích thước kết quả thay vì tự gộp nhiều object thành một.

Ví dụ:

```java
Customer customer = customers.findCustomerById(42L);

if (customer == null) {
    // Xử lý trường hợp không tìm thấy.
} else {
    System.out.println(customer.name());
}
```

Với repository API mới, `Optional<Customer>` thường diễn đạt trường hợp có thể không tìm thấy rõ hơn. Trả về `Customer` trực tiếp vẫn có thể hữu ích khi contract hoặc convention của ứng dụng chấp nhận null và caller đã xử lý đúng.

### Tránh để `null` lan truyền

Nếu method trả `Customer`, caller cần nhớ kiểm tra null trước khi gọi `customer.name()`. Nếu bỏ qua, ứng dụng có thể gặp `NullPointerException`.

Với `Optional`, caller có thể buộc xử lý trường hợp vắng mặt ngay tại nơi sử dụng:

```java
Customer customer = customers.findByEmail(email)
        .orElseThrow(() -> new CustomerNotFoundException(email));
```

Điều này khiến hợp đồng của method dễ đọc hơn: truy vấn có thể không tìm thấy, và caller phải chọn cách xử lý.

## 4. Cardinality: truy vấn một kết quả phải thực sự có tối đa một hàng

Một method trả về `Optional<Customer>` hoặc `Customer` thể hiện kỳ vọng **tối đa một kết quả**. Kỳ vọng này nên được bảo vệ bằng mô hình dữ liệu hoặc điều kiện truy vấn.

Ví dụ, nếu email phải duy nhất:

```sql
ALTER TABLE customers
ADD CONSTRAINT uq_customers_email UNIQUE (email);
```

Khi đó:

```java
Optional<Customer> findByEmail(String email);
```

có cơ sở dữ liệu bảo đảm không có hai khách hàng cùng email (theo quy tắc so sánh/collation của database).

Nếu không có ràng buộc duy nhất, method `findByEmail` vẫn có thể trả nhiều hàng. Spring Data không tự chọn một bản ghi ngẫu nhiên để đặt vào `Optional`; truy vấn đơn sẽ thất bại với lỗi kích thước kết quả, thường được biểu diễn bằng `IncorrectResultSizeDataAccessException` hoặc exception tương ứng trong tầng truy cập dữ liệu.

Nếu nghiệp vụ muốn lấy **một bản ghi đầu tiên** trong nhiều bản ghi, hãy diễn đạt rõ bằng `First`/`Top` và thứ tự:

```java
Optional<Customer> findFirstByCityOrderByNameAsc(String city);
```

Method này yêu cầu một kết quả đầu tiên theo thứ tự tên tăng dần, thay vì giả định city là duy nhất. Nếu bỏ `OrderBy`, việc chọn “đầu tiên” có thể không ổn định vì database không bảo đảm thứ tự hàng nếu không có `ORDER BY`.

## 5. `Iterable<T>`: tập kết quả có thể duyệt

`CrudRepository<T, ID>` dùng `Iterable` cho các phương thức đọc nhiều đối tượng:

```java
Iterable<T> findAll();
Iterable<T> findAllById(Iterable<ID> ids);
```

Một repository query method cũng có thể trả `Iterable<Customer>`:

```java
Iterable<Customer> findByActiveTrue();
```

Caller duyệt bằng `for-each`:

```java
for (Customer customer : customers.findByActiveTrue()) {
    System.out.println(customer.name());
}
```

Hoặc dùng iterator:

```java
Iterable<Customer> result = customers.findByActiveTrue();
var iterator = result.iterator();

while (iterator.hasNext()) {
    Customer customer = iterator.next();
    System.out.println(customer.email());
}
```

Đặc điểm của `Iterable`:

- Có thể duyệt các phần tử tuần tự.
- Không có `get(index)` hoặc `size()` trực tiếp.
- Không cam kết thứ tự nếu query không có `ORDER BY`.
- Là hợp đồng tổng quát hơn `List`, hữu ích khi caller chỉ cần duyệt.

**Không nên suy ra rằng `Iterable` đồng nghĩa với streaming hoặc cursor lazy.** Kiểu trả về chỉ cam kết khả năng duyệt. Với Spring Data JDBC, kết quả query thông thường được đọc và ánh xạ trong quá trình thực thi repository; không nên dùng `Iterable` như một bảo đảm rằng toàn bộ kết quả sẽ được tải từng hàng khi caller yêu cầu.

Nếu cần xử lý lượng dữ liệu lớn, hãy xem xét giới hạn kết quả, phân trang/lấy theo lô hoặc cơ chế JDBC streaming được thiết kế rõ ràng. Đổi `List` thành `Iterable` không tự giải quyết vấn đề bộ nhớ.

## 6. `List<T>`: tập kết quả có thể truy cập theo index

`List<T>` phù hợp khi caller cần các thao tác của Java List:

```java
List<Customer> findByCity(String city);
```

Ví dụ:

```java
List<Customer> hcmCustomers = customers.findByCity("Ho Chi Minh City");

System.out.println("Số khách: " + hcmCustomers.size());

if (!hcmCustomers.isEmpty()) {
    Customer first = hcmCustomers.get(0);
    System.out.println(first.name());
}
```

Với `List<T>`:

- Có `size()` để biết số phần tử.
- Có `get(index)` để truy cập theo vị trí.
- Có các thao tác như `isEmpty`, `stream`, `forEach`.
- Khi không có hàng, kết quả là danh sách rỗng (`[]`), không phải `null`.
- Thứ tự phần tử chỉ được bảo đảm theo thứ tự query quy định; nếu cần ổn định phải có `ORDER BY`.

Ví dụ method giới hạn kết quả:

```java
List<Customer> findTop20ByCityOrderByNameAsc(String city);
```

Method trả tối đa 20 khách hàng theo tên tăng dần. Dạng `Top`/`First` giúp giới hạn số hàng, còn `List` thể hiện kiểu collection trả về.

## 7. `CrudRepository` và `ListCrudRepository` ảnh hưởng kiểu trả về ra sao?

Hai interface CRUD khác nhau chủ yếu ở kiểu collection của một số phương thức:

```java
public interface CustomerCrudRepository
        extends CrudRepository<Customer, Long> {
}
```

Với `CrudRepository`:

```java
Iterable<Customer> all = customerCrudRepository.findAll();
Iterable<Customer> saved = customerCrudRepository.saveAll(batch);
Iterable<Customer> selected = customerCrudRepository.findAllById(ids);
```

Nếu cần `List`, có thể dùng:

```java
public interface CustomerListRepository
        extends ListCrudRepository<Customer, Long> {
}
```

Với `ListCrudRepository`:

```java
List<Customer> all = customerListRepository.findAll();
List<Customer> saved = customerListRepository.saveAll(batch);
List<Customer> selected = customerListRepository.findAllById(ids);
```

`ListCrudRepository` mở rộng `CrudRepository` và khai báo lại một số phương thức trả về `List`. `findById` vẫn trả `Optional<T>`; `existsById` vẫn trả `boolean`; `count` vẫn trả `long`. Chọn interface theo nhu cầu sử dụng collection của ứng dụng.

| Phương thức | `CrudRepository` | `ListCrudRepository` |
|---|---|---|
| `findById(ID)` | `Optional<T>` | `Optional<T>` |
| `findAll()` | `Iterable<T>` | `List<T>` |
| `findAllById(Iterable<ID>)` | `Iterable<T>` | `List<T>` |
| `save(S)` | `S` | `S` |
| `saveAll(Iterable<S>)` | `Iterable<S>` | `List<S>` |
| `existsById(ID)` | `boolean` | `boolean` |
| `count()` | `long` | `long` |

Hai interface không làm thay đổi bản chất truy vấn SQL hoặc ranh giới aggregate; khác biệt quan trọng ở đây là kiểu trả về của các thao tác nhiều kết quả.

## 8. Danh sách rỗng khác với `Optional.empty()`

Hai kiểu biểu diễn không có dữ liệu theo hai cách khác nhau:

```java
Optional<Customer> one = customers.findByEmail("missing@example.com");
List<Customer> many = customers.findByCity("No Such City");
```

Kết quả:

```text
one  -> Optional.empty()
many -> []
```

Ý nghĩa:

- `Optional.empty()` nói rằng **không có đối tượng đơn** phù hợp.
- `[]` nói rằng **tập kết quả không có phần tử nào**.

Không nên khai báo `Optional<List<Customer>>` cho truy vấn nhiều hàng thông thường. Nếu không có hàng, `List<Customer>` rỗng đã biểu diễn đầy đủ trường hợp đó. Bọc thêm `Optional` thường tạo hai tầng “không có dữ liệu” mà không mang thêm ý nghĩa hữu ích.

Tương tự, không nên trả `null` thay cho một collection khi query không có kết quả. Hợp đồng collection nên trả collection rỗng để caller có thể duyệt an toàn.

## 9. Kết quả đơn và giới hạn bằng `First`/`Top`

Nếu điều kiện truy vấn không duy nhất nhưng nghiệp vụ chỉ cần một kết quả, có thể dùng `First` hoặc `Top`:

```java
Optional<Customer> findFirstByCityOrderByNameAsc(String city);

List<Customer> findTop5ByActiveTrueOrderByNameAsc();
```

Method đầu trả về tối đa một khách hàng trong city theo tên tăng dần. Method thứ hai trả tối đa năm khách hàng đang hoạt động theo tên tăng dần.

So sánh:

| Nhu cầu | Method phù hợp |
|---|---|
| Email duy nhất, có thể không tồn tại | `Optional<Customer> findByEmail(String email)` |
| ID duy nhất, muốn xử lý null trực tiếp | `Customer findCustomerById(Long id)` hoặc dùng `findById` có sẵn |
| Tất cả khách trong một thành phố | `List<Customer> findByCity(String city)` |
| Duyệt các khách đang hoạt động | `Iterable<Customer> findByActiveTrue()` |
| Một khách đầu tiên theo thứ tự rõ ràng | `Optional<Customer> findFirstByCityOrderByNameAsc(String city)` |
| Tối đa năm khách đang hoạt động | `List<Customer> findTop5ByActiveTrueOrderByNameAsc()` |

`First`/`Top` kiểm soát số hàng được trả về; `Optional`, `List` hoặc `Iterable` tiếp tục diễn đạt hình dạng kết quả. Nếu không có `OrderBy`, “đầu tiên” không có ý nghĩa ổn định theo nghiệp vụ.

## 10. Kết quả đơn với `Optional` và lỗi nhiều hàng

Giả sử method:

```java
Optional<Customer> findByCity(String city);
```

nhưng `city` có thể xuất hiện ở nhiều khách hàng. Khi gọi:

```java
customers.findByCity("Ho Chi Minh City");
```

method kỳ vọng tối đa một hàng nhưng database có thể trả nhiều. Spring Data không tự chuyển sang List; nó báo lỗi kích thước kết quả. Kiểu trả về là một phần của hợp đồng query, vì thế cần thiết kế điều kiện truy vấn tương ứng.

Nếu city không duy nhất, đổi thành:

```java
List<Customer> findByCity(String city);
```

Nếu nghiệp vụ chỉ cần một khách cụ thể, thêm điều kiện duy nhất (ví dụ email) hoặc giới hạn và sắp xếp rõ ràng:

```java
Optional<Customer> findFirstByCityOrderByIdAsc(String city);
```

Không nên đổi `Optional` thành `List` chỉ để che lỗi dữ liệu trùng nếu email thực sự phải duy nhất. Khi đó cần ràng buộc `UNIQUE` để bảo vệ invariant ở database.

## 11. Thứ tự kết quả: `List` không tự bảo đảm thứ tự nghiệp vụ

Một `List` có thứ tự vị trí, nhưng điều đó không đồng nghĩa database trả các hàng theo thứ tự mà ứng dụng mong muốn. Nếu query không có `ORDER BY`, thứ tự kết quả không được bảo đảm.

Ví dụ:

```java
List<Customer> findByCityOrderByNameAsc(String city);
```

có ý nghĩa tương đương:

```sql
SELECT id, name, email, city, active
FROM customers
WHERE city = ?
ORDER BY name ASC;
```

Khi đó List phản ánh thứ tự do SQL quy định. Nếu cần thứ tự ổn định khi các tên bằng nhau, thêm tiêu chí phụ:

```java
List<Customer> findByCityOrderByNameAscIdAsc(String city);
```

Tương tự, `Iterable` không hứa thứ tự nào. Nếu thứ tự quan trọng, hãy khai báo `OrderBy` trong derived query hoặc dùng `Sort`/query có sắp xếp được hỗ trợ.

## 12. `Iterable` và `List` không đồng nghĩa với phân trang

`Iterable<T>` chỉ cho phép duyệt, còn `List<T>` cho phép truy cập theo index. Cả hai không tự mang thông tin:

- Trang hiện tại (`page number`).
- Kích thước trang (`page size`).
- Tổng số phần tử hoặc tổng số trang.
- Con trỏ/cursor tiếp tục đọc từ database.

Vì vậy, thay `Iterable<T>` bằng `List<T>` không phải là một chiến lược phân trang. Một `List` có thể chứa toàn bộ hàng phù hợp và chiếm nhiều bộ nhớ. Một `Iterable` cũng không mặc nhiên đọc dữ liệu từng phần.

Nếu cần phân trang, hãy sử dụng khả năng `Pageable`/`Sort` và kiểu kết quả mà **phiên bản Spring Data JDBC đang dùng** hỗ trợ, hoặc triển khai query giới hạn theo lô với điều kiện sắp xếp ổn định. Với lượng dữ liệu rất lớn, cần thiết kế cách đọc phù hợp thay vì dựa vào tên kiểu collection.

## 13. Kết quả query và aggregate mapping

Trong Spring Data JDBC, repository làm việc với aggregate root. Một kết quả `Customer` là aggregate được ánh xạ theo metadata của root; nếu root có các thành phần con thuộc aggregate, đường đọc tiêu chuẩn có thể cần truy vấn và dựng các thành phần đó.

Do đó, `List<Customer>` có thể tốn chi phí nhiều hơn số cột của bảng `customers` nếu mỗi aggregate có collection con. Cần cân nhắc khi gọi `findAll()` hoặc truy vấn trả nhiều aggregate.

Nếu màn hình chỉ cần vài cột, có thể trả DTO/projection thay vì dựng đầy đủ aggregate:

```java
public record CustomerSummary(Long id, String name, String city) {}
```

```java
@Query("""
    SELECT id, name, city
    FROM customers
    WHERE active = TRUE
    ORDER BY name
    """)
List<CustomerSummary> findActiveSummaries();
```

Đây là query đọc theo mục đích hiển thị; nó không thay thế repository aggregate dùng để cập nhật nghiệp vụ. Kiểu kết quả nên phản ánh đúng dữ liệu cần cho use case.

## 14. Một số kiểu kết quả khác cần nhận diện

Ngoài các kiểu trong bài, repository method có thể trả scalar hoặc kiểu kết quả chuyên biệt:

```java
long countByCity(String city);

boolean existsByEmail(String email);
```

- `long` diễn đạt số lượng.
- `boolean` diễn đạt kết quả kiểm tra tồn tại.

Đây không phải entity result. Không nên trả `Customer` chỉ để kiểm tra có bản ghi hay không nếu method `existsBy...` diễn đạt đúng nhu cầu và được module hỗ trợ.

Các kiểu như `Page<T>`, `Slice<T>`, `Stream<T>` hoặc cursor có quy tắc riêng và khả năng hỗ trợ phụ thuộc module/phiên bản. Đừng suy ra rằng mọi kiểu trả về trong Spring Data JPA đều hoạt động giống hệt trong Spring Data JDBC.

## 15. Các lỗi thường gặp khi chọn kiểu trả về

| Triệu chứng | Nguyên nhân thường gặp | Hướng xử lý |
|---|---|---|
| `Optional` gây lỗi khi có nhiều hàng | Query không thực sự duy nhất | Thêm ràng buộc unique, điều kiện cụ thể hoặc đổi sang collection |
| Caller gặp `NullPointerException` | Method trả `T` trực tiếp nhưng không có hàng | Dùng `Optional<T>` hoặc kiểm tra null |
| Không thể gọi `get(index)` | Kiểu trả về là `Iterable` | Dùng `ListCrudRepository` hoặc khai báo query trả List nếu cần List |
| Không có kết quả nhưng caller kiểm tra null | Collection trả về rỗng, không phải null | Dùng `isEmpty()` |
| `List` chứa quá nhiều dữ liệu | Query không giới hạn | Thêm điều kiện, `Top`/`First` hoặc cơ chế paging phù hợp |
| Thứ tự phần tử thay đổi | SQL không có `ORDER BY` | Khai báo thứ tự rõ ràng |
| `findAllById` thiếu ID | Một số ID không có hàng tương ứng; thứ tự kết quả không bảo đảm | Kiểm tra tập ID và không giả định đủ mọi ID hoặc đúng thứ tự đầu vào |
| `Iterable` bị hiểu là lazy stream | Nhầm khả năng duyệt với cách đọc dữ liệu | Thiết kế streaming/batching riêng nếu cần |
| DTO trả về thiếu trường | SQL không chọn đủ cột/alias | Đối chiếu kiểu kết quả và danh sách cột |
| `Optional<List<T>>` phức tạp không cần thiết | Bọc collection bằng Optional | Trả `List<T>` rỗng khi không có hàng |

## 16. Ví dụ application service xử lý từng kiểu kết quả

```java
import java.util.List;
import org.springframework.stereotype.Service;

@Service
public class CustomerService {
    private final CustomerRepository customers;

    public CustomerService(CustomerRepository customers) {
        this.customers = customers;
    }

    public Customer getRequiredCustomer(Long id) {
        return customers.findById(id)
                .orElseThrow(() -> new IllegalArgumentException("Customer not found"));
    }

    public List<Customer> getCustomersInCity(String city) {
        return customers.findByCity(city);
    }

    public void printActiveCustomers() {
        for (Customer customer : customers.findByActiveTrue()) {
            System.out.println(customer.name());
        }
    }
}
```

Ví dụ minh họa ba kiểu kết quả:

- `findById` trả `Optional<Customer>` vì ID có thể không tồn tại.
- `findByCity` trả `List<Customer>` vì một thành phố có nhiều khách.
- `findByActiveTrue` trả `Iterable<Customer>` vì caller chỉ cần duyệt tập kết quả.

Trong một repository thực tế, các method này có thể cùng tồn tại; hãy chọn kiểu theo cardinality và cách caller cần thao tác, không chỉ theo thói quen.

## 17. Bài thực hành: quan sát 0, 1 và nhiều kết quả

Với bảng `customers` ở phần đầu, nạp dữ liệu mẫu:

```sql
INSERT INTO customers (name, email, city, active) VALUES
    ('Lan', 'lan@example.com', 'Ho Chi Minh City', TRUE),
    ('Minh', 'minh@example.com', 'Ho Chi Minh City', TRUE),
    ('Hoa', 'hoa@example.com', 'Da Nang', FALSE);
```

Thử các method:

```java
Optional<Customer> byEmail = customers.findByEmail("lan@example.com");
Optional<Customer> missing = customers.findByEmail("missing@example.com");
List<Customer> hcm = customers.findByCity("Ho Chi Minh City");
Iterable<Customer> active = customers.findByActiveTrue();
```

Quan sát:

1. `byEmail` chứa một Customer.
2. `missing` là `Optional.empty()`.
3. `hcm` có hai phần tử.
4. `active` có thể duyệt qua các khách đang hoạt động.
5. Đổi `findByEmail` sang một điều kiện không duy nhất (ví dụ `findByCity`) nhưng vẫn trả `Optional<Customer>`; quan sát lỗi kích thước kết quả khi có nhiều hàng.
6. Đổi method đó sang `List<Customer>` để biểu diễn đúng nhiều kết quả.
7. Thử `findFirstByCityOrderByNameAsc` và quan sát vì sao `ORDER BY` cần thiết để chọn kết quả đầu tiên ổn định.

## 18. Nguyên tắc ghi nhớ

- Dùng `Optional<T>` cho **0 hoặc 1** kết quả; không dùng để che giấu query có thể trả nhiều hàng.
- Dùng `T` trực tiếp cho kết quả đơn khi caller chấp nhận xử lý `null` nếu không có hàng.
- Dùng `Iterable<T>` khi caller chỉ cần duyệt tập kết quả.
- Dùng `List<T>` khi caller cần collection có `size()` và truy cập theo index.
- Collection không có kết quả nên trả collection rỗng; `Optional.empty()` dành cho kết quả đơn vắng mặt.
- Một query đơn trả nhiều hàng sẽ gây lỗi kích thước kết quả; dùng unique constraint, điều kiện rõ ràng hoặc `First`/`Top` có sắp xếp.
- `CrudRepository` dùng `Iterable` cho một số phương thức nhiều hàng; `ListCrudRepository` trả `List` cho các phương thức tương ứng.
- `List` và `Iterable` không tự đồng nghĩa với phân trang, streaming hoặc lazy loading.
- Thứ tự chỉ được bảo đảm khi query có `ORDER BY`.
- Kiểu trả về nên phản ánh cardinality và nhu cầu thực tế của use case.

Trong Spring Data JDBC, lựa chọn `List`, `Iterable`, `Optional` hay một đối tượng đơn là một phần của hợp đồng repository. Hãy xác định trước truy vấn có thể trả bao nhiêu hàng, quy tắc duy nhất nằm ở đâu và caller cần sử dụng kết quả như thế nào. Khi kiểu trả về khớp với cardinality, code xử lý trường hợp không có dữ liệu rõ ràng hơn, tránh lỗi nhiều hàng và không vô tình tải một tập kết quả lớn hơn nhu cầu.
