# Cột tham chiếu ngược và quan hệ khóa ngoại trên bảng con

Trong mô hình quan hệ, quan hệ **một đơn hàng có nhiều dòng hàng** thường được lưu bằng một khóa ngoại đặt ở bảng con. Mỗi hàng trong bảng `order_lines` có cột `order_id` trỏ về khóa chính `purchase_orders.id`. Cột này là **cột tham chiếu ngược** theo góc nhìn từ bảng con: từ một dòng hàng, ta biết nó thuộc về đơn hàng nào.

Với **Spring Data JDBC**, quan hệ sở hữu này được biểu diễn ở aggregate root bằng `@MappedCollection(idColumn = "order_id")`. Spring Data JDBC dùng metadata đó để ghi và đọc các dòng con cùng aggregate. Cần phân biệt hai phần: annotation mô tả cách ánh xạ object sang cột; câu lệnh DDL hoặc migration mới tạo bảng, cột và ràng buộc `FOREIGN KEY` thật trong database.

Bài học dùng `PurchaseOrder` làm aggregate root và `OrderLine` làm entity con. Ta sẽ xem cách thiết kế bảng, khai báo `@MappedCollection`, lưu và đọc aggregate, truy vấn JOIN, cũng như những trường hợp nên tách đối tượng thành aggregate độc lập.

## 1. Vì sao khóa ngoại nằm ở bảng con?

Giả sử một đơn hàng có thể chứa nhiều dòng hàng:

~~~text
PurchaseOrder 1 -------------- N OrderLine

purchase_orders                 order_lines
-------------------             ----------------------
id (PK)                         id (PK)
order_number                    order_id (FK)
status                          product_id
                                quantity
                                unit_price
~~~

Một đơn hàng có thể có nhiều dòng hàng, nhưng mỗi dòng hàng trong mô hình này thuộc về đúng một đơn. Vì vậy, cột `order_id` được đặt trong bảng `order_lines`:

~~~sql
SELECT id, order_id, product_id, quantity
FROM order_lines;
~~~

Ví dụ dữ liệu:

| purchase_orders.id | order_number | status |
|---:|---|---|
| 1001 | SO-2026-001 | DRAFT |
| 1002 | SO-2026-002 | SUBMITTED |

| order_lines.id | order_id | product_id | quantity |
|---:|---:|---:|---:|
| 1 | 1001 | 501 | 2 |
| 2 | 1001 | 502 | 1 |
| 3 | 1002 | 501 | 4 |

Từ dữ liệu trên:

- Đơn `1001` có hai dòng hàng vì có hai hàng `order_lines` cùng mang `order_id = 1001`.
- Đơn `1002` có một dòng hàng.
- Dòng hàng `1` tham chiếu đến đơn `1001`, không cần một cột `line_id_1`, `line_id_2`... trong bảng cha.

Đây là cách biểu diễn chuẩn của quan hệ **one-to-many** trong relational database. Bảng ở phía “many” giữ foreign key đến bảng ở phía “one”.

## 2. Phân biệt cột tham chiếu ngược với quan hệ hai chiều trong Java

Từ “tham chiếu ngược” đôi khi khiến người học nghĩ rằng class con phải có một trường trỏ ngược đến object cha:

~~~java
class OrderLine {
    private PurchaseOrder order;
}
~~~

Với quan hệ sở hữu aggregate trong Spring Data JDBC, **không cần tạo trường `PurchaseOrder order` trong `OrderLine`**. Quan hệ được mô tả ở collection của root. Spring Data JDBC biết cột `order_id` nằm trên bảng con thông qua `@MappedCollection`.

Mô hình Java:

~~~text
PurchaseOrder (aggregate root)
    |
    | Set<OrderLine>
    |
    +------ OrderLine
    +------ OrderLine

Database:

purchase_orders.id
        ^
        |
order_lines.order_id
~~~

Hình minh họa cho thấy hai hướng biểu diễn khác nhau:

- Trong Java, root giữ collection của các phần tử thuộc aggregate.
- Trong database, mỗi hàng con giữ giá trị khóa ngoại tham chiếu đến hàng cha.

Không cần tạo một object graph hai chiều chỉ để database có foreign key. Thiết kế một chiều này phù hợp với cách Spring Data JDBC tổ chức aggregate: root là điểm truy cập và kiểm soát vòng đời các phần tử con.

### 2.1. Foreign key không phải là một cột ID con trên bảng cha

Một cách thiết kế không phù hợp là tạo các cột cố định như:

~~~sql
CREATE TABLE purchase_orders (
    id BIGINT PRIMARY KEY,
    line_id_1 BIGINT,
    line_id_2 BIGINT,
    line_id_3 BIGINT
);
~~~

Cách này giới hạn số dòng hàng, làm schema khó mở rộng và đảo ngược quan hệ one-to-many. Bảng cha không cần biết trước có bao nhiêu dòng con. Mỗi dòng con tự mang `order_id`.

### 2.2. Một foreign key có thể được hiểu bằng hai góc nhìn

Từ bảng cha, ta muốn tìm các dòng con:

~~~sql
SELECT *
FROM order_lines
WHERE order_id = 1001;
~~~

Từ bảng con, ta muốn tìm đơn hàng sở hữu dòng đó:

~~~sql
SELECT o.*
FROM purchase_orders o
JOIN order_lines l ON l.order_id = o.id
WHERE l.id = 1;
~~~

Đó là cùng một quan hệ khóa ngoại, không phải hai foreign key đối nghịch nhau.

## 3. Tạo schema với khóa ngoại ở bảng con

Ví dụ dùng Spring Boot, Spring Data JDBC và H2. DDL sau tạo khóa chính ở bảng cha, khóa chính ở bảng con và khóa ngoại `order_id` trỏ đến cha.

Tạo `src/main/resources/schema.sql`:

~~~sql
CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_number VARCHAR(40) NOT NULL UNIQUE,
    status VARCHAR(20) NOT NULL
);

CREATE TABLE order_lines (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL,
    product_id BIGINT NOT NULL,
    quantity INTEGER NOT NULL,
    unit_price DECIMAL(12, 2) NOT NULL,
    CONSTRAINT fk_order_lines_purchase_order
        FOREIGN KEY (order_id)
        REFERENCES purchase_orders(id),
    CONSTRAINT ck_order_lines_quantity
        CHECK (quantity > 0)
);

CREATE INDEX idx_order_lines_order_id
    ON order_lines(order_id);
~~~

Giải thích:

- `purchase_orders.id` là primary key của aggregate root.
- `order_lines.id` là primary key của từng dòng hàng.
- `order_lines.order_id` là foreign key tham chiếu `purchase_orders.id`.
- `NOT NULL` bảo đảm mỗi dòng hàng phải có đơn hàng sở hữu.
- `FOREIGN KEY` ngăn một dòng hàng trỏ đến đơn hàng không tồn tại.
- Index trên `order_id` hỗ trợ truy vấn các dòng thuộc một đơn và JOIN theo khóa ngoại.
- `CHECK (quantity > 0)` là ràng buộc dữ liệu bổ sung; quy tắc nghiệp vụ vẫn nên được bảo vệ trong domain object.

`GENERATED BY DEFAULT AS IDENTITY` là cú pháp phù hợp với H2 và nhiều database hiện đại, nhưng cú pháp sinh ID có thể khác theo hệ quản trị. Khi chuyển sang PostgreSQL, MySQL hoặc SQL Server, hãy điều chỉnh DDL theo database đích.

### 3.1. Vì sao `order_id` cần `NOT NULL`?

Trong mô hình này, `OrderLine` chỉ tồn tại như một phần của `PurchaseOrder`. Một dòng hàng không có đơn hàng cha là dữ liệu mồ côi, không hợp lệ theo domain. `NOT NULL` kết hợp foreign key bảo đảm:

1. Dòng hàng luôn có giá trị tham chiếu.
2. Giá trị tham chiếu phải khớp với một khóa chính đang tồn tại.

Nếu nghiệp vụ cho phép một dòng hàng chưa gắn đơn (ví dụ giỏ hàng nháp độc lập), đó có thể là một mô hình khác với vòng đời khác; không nên nới `order_id` thành nullable chỉ để né thiết kế aggregate.

### 3.2. Có cần `ON DELETE CASCADE` không?

Không bắt buộc phải khai báo `ON DELETE CASCADE`. Spring Data JDBC hiểu quan hệ sở hữu qua mapping aggregate và điều phối việc lưu/xóa các thành phần thuộc aggregate. Foreign key vẫn bảo vệ tính toàn vẹn ở database.

Nếu thêm `ON DELETE CASCADE`, database sẽ tự xóa các dòng con khi hàng cha bị xóa trực tiếp. Đây là quyết định ở tầng database, có thể hữu ích trong một số hệ thống, nhưng phải hiểu tác động đến trigger, audit và những đường xóa ngoài ứng dụng. Không dùng cascade để thay thế việc khai báo đúng quan hệ trong Spring Data JDBC.

## 4. Ánh xạ `@MappedCollection` trên aggregate root

### 4.1. Entity con `OrderLine`

Tạo `src/main/java/com/example/orders/domain/OrderLine.java`:

~~~java
package com.example.orders.domain;

import java.math.BigDecimal;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("order_lines")
public class OrderLine {

    @Id
    private Long id;

    @Column("product_id")
    private Long productId;

    private int quantity;

    @Column("unit_price")
    private BigDecimal unitPrice;

    protected OrderLine() {
        // Dành cho cơ chế ánh xạ của Spring Data JDBC.
    }

    OrderLine(Long productId, int quantity, BigDecimal unitPrice) {
        if (productId == null) {
            throw new IllegalArgumentException("productId không được null");
        }
        if (quantity <= 0) {
            throw new IllegalArgumentException("quantity phải lớn hơn 0");
        }
        if (unitPrice == null || unitPrice.signum() < 0) {
            throw new IllegalArgumentException("unitPrice không hợp lệ");
        }
        this.productId = productId;
        this.quantity = quantity;
        this.unitPrice = unitPrice;
    }

    public Long getId() {
        return id;
    }

    public Long getProductId() {
        return productId;
    }

    public int getQuantity() {
        return quantity;
    }

    public BigDecimal getUnitPrice() {
        return unitPrice;
    }

    public BigDecimal subtotal() {
        return unitPrice.multiply(BigDecimal.valueOf(quantity));
    }
}
~~~

`OrderLine` có `@Id` vì mỗi hàng con có định danh riêng trong bảng. Tuy nhiên, **có `@Id` không tự động biến nó thành aggregate root và không có nghĩa cần `OrderLineRepository`**.

Đáng chú ý: class không có thuộc tính `orderId` và không có trường `PurchaseOrder order`. Cột `order_id` sẽ được khai báo ở metadata collection trên root.

### 4.2. Aggregate root `PurchaseOrder`

Tạo `src/main/java/com/example/orders/domain/PurchaseOrder.java`:

~~~java
package com.example.orders.domain;

import java.util.Collections;
import java.util.LinkedHashSet;
import java.util.Set;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_orders")
public class PurchaseOrder {

    @Id
    private Long id;

    @Column("order_number")
    private String orderNumber;

    private String status;

    @MappedCollection(idColumn = "order_id")
    private Set<OrderLine> lines = new LinkedHashSet<>();

    protected PurchaseOrder() {
        // Dành cho cơ chế ánh xạ của Spring Data JDBC.
    }

    private PurchaseOrder(String orderNumber) {
        if (orderNumber == null || orderNumber.isBlank()) {
            throw new IllegalArgumentException("orderNumber không hợp lệ");
        }
        this.orderNumber = orderNumber;
        this.status = "DRAFT";
    }

    public static PurchaseOrder draft(String orderNumber) {
        return new PurchaseOrder(orderNumber);
    }

    public void addLine(
            Long productId,
            int quantity,
            java.math.BigDecimal unitPrice) {
        if (!"DRAFT".equals(status)) {
            throw new IllegalStateException(
                "Chỉ được thêm dòng hàng khi đơn ở trạng thái DRAFT");
        }
        lines.add(new OrderLine(productId, quantity, unitPrice));
    }

    public void submit() {
        if (!"DRAFT".equals(status)) {
            throw new IllegalStateException("Đơn không ở trạng thái DRAFT");
        }
        if (lines.isEmpty()) {
            throw new IllegalStateException(
                "Không thể gửi đơn hàng không có dòng hàng");
        }
        status = "SUBMITTED";
    }

    public Long getId() {
        return id;
    }

    public String getOrderNumber() {
        return orderNumber;
    }

    public String getStatus() {
        return status;
    }

    public Set<OrderLine> getLines() {
        return Collections.unmodifiableSet(lines);
    }
}
~~~

Điểm quan trọng nhất là:

~~~java
@MappedCollection(idColumn = "order_id")
private Set<OrderLine> lines;
~~~

- `@MappedCollection` nói rằng `lines` là collection các phần tử thuộc aggregate root.
- `idColumn = "order_id"` chỉ định tên cột khóa ngoại trên bảng được ánh xạ cho phần tử con.
- `order_id` nằm trong bảng `order_lines`, không phải trong `purchase_orders`.
- Khi lưu aggregate, Spring Data JDBC sử dụng ID của `PurchaseOrder` để gắn các hàng `OrderLine` vào root.

`@MappedCollection` **không tạo bảng hoặc tự chạy DDL**. Nó mô tả mapping. Schema vẫn phải có cột `order_id` với kiểu tương thích và foreign key thật như phần trước.

### 4.3. Vì sao không khai báo `orderId` trong `OrderLine`?

Trong mapping sở hữu này, parent-child relationship được xác định bởi collection của root. Nếu vừa khai báo `@MappedCollection(idColumn = "order_id")`, vừa thêm một thuộc tính `orderId` độc lập để ghi cùng cột, bạn có thể tạo mapping trùng lặp hoặc mâu thuẫn.

Nếu nghiệp vụ cần biết parent trong logic domain, thường có thể truyền root vào phương thức nghiệp vụ hoặc làm việc qua root. Không cần sao chép foreign key thành một field Java chỉ để database có quan hệ.

## 5. Repository được tạo cho aggregate root

Tạo `src/main/java/com/example/orders/repository/PurchaseOrderRepository.java`:

~~~java
package com.example.orders.repository;

import java.util.Optional;

import com.example.orders.domain.PurchaseOrder;
import org.springframework.data.repository.CrudRepository;

public interface PurchaseOrderRepository
        extends CrudRepository<PurchaseOrder, Long> {

    Optional<PurchaseOrder> findByOrderNumber(String orderNumber);
}
~~~

Không cần `OrderLineRepository` chỉ vì có bảng `order_lines`. Repository thao tác với root và Spring Data JDBC biết collection con qua `@MappedCollection`.

Luồng khái niệm:

~~~text
PurchaseOrderRepository.save(order)
             |
             v
        PurchaseOrder
             |
             +---- lines: Set<OrderLine>
                         |
                         v
                   order_lines
                   order_id = order.id
~~~

Số lượng câu SQL cụ thể phụ thuộc mapping và thao tác. Sơ đồ biểu diễn trách nhiệm lưu aggregate, không khẳng định framework luôn dùng một câu lệnh SQL cho cả root và children.

## 6. Lưu và đọc aggregate để quan sát cột tham chiếu ngược

### 6.1. Service tạo đơn

Tạo `src/main/java/com/example/orders/service/OrderService.java`:

~~~java
package com.example.orders.service;

import java.math.BigDecimal;

import com.example.orders.domain.PurchaseOrder;
import com.example.orders.repository.PurchaseOrderRepository;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class OrderService {

    private final PurchaseOrderRepository orders;

    public OrderService(PurchaseOrderRepository orders) {
        this.orders = orders;
    }

    @Transactional
    public PurchaseOrder createExampleOrder() {
        PurchaseOrder order = PurchaseOrder.draft("SO-2026-001");

        order.addLine(501L, 2, new BigDecimal("120000.00"));
        order.addLine(502L, 1, new BigDecimal("90000.00"));

        return orders.save(order);
    }
}
~~~

Service tạo root, thêm các dòng hàng thông qua method của root, rồi gọi repository một lần để lưu aggregate. `@Transactional` xác định ranh giới transaction cho use case khi phương thức được gọi qua Spring proxy.

### 6.2. Đọc lại root

~~~java
PurchaseOrder saved = orderService.createExampleOrder();

PurchaseOrder loaded = repository.findById(saved.getId())
    .orElseThrow();

System.out.println(loaded.getOrderNumber());
System.out.println(loaded.getLines().size());
~~~

Khi tải aggregate root, Spring Data JDBC tải các thành phần được mapping thuộc aggregate. Collection này không phải quan hệ lazy-loaded theo kiểu JPA; không nên thiết kế code dựa trên giả định rằng truy cập `getLines()` sau đó sẽ tự kích hoạt một lazy query.

### 6.3. Kiểm tra giá trị `order_id` trực tiếp

Dùng `JdbcTemplate` để quan sát bảng con:

~~~java
List<Map<String, Object>> rows = jdbcTemplate.queryForList(
    """
    SELECT id, order_id, product_id, quantity, unit_price
    FROM order_lines
    ORDER BY id
    """
);

rows.forEach(System.out::println);
~~~

Kết quả minh họa:

~~~text
{ID=1, ORDER_ID=1, PRODUCT_ID=501, QUANTITY=2, UNIT_PRICE=120000.00}
{ID=2, ORDER_ID=1, PRODUCT_ID=502, QUANTITY=1, UNIT_PRICE=90000.00}
~~~

Hai dòng hàng cùng có `ORDER_ID = 1`, vì cả hai đều thuộc đơn có ID `1`. Đây là bằng chứng trực tiếp rằng `idColumn = "order_id"` đã ánh xạ cột tham chiếu ngược ở bảng con.

## 7. `idColumn` và `keyColumn` khác nhau thế nào?

`@MappedCollection` có thể khai báo cả `idColumn` và `keyColumn`. Hai thuộc tính này phục vụ hai ý nghĩa khác nhau:

| Thuộc tính | Ý nghĩa | Ví dụ |
|---|---|---|
| `idColumn` | Cột ở bảng con lưu ID của aggregate root | `order_id` |
| `keyColumn` | Cột lưu key của collection khi cấu trúc cần key, như `Map` hoặc vị trí của `List` | `line_position` |

Với `Set<OrderLine>`, thường chỉ cần `idColumn`. Nếu dùng `List<OrderLine>` và cần lưu thứ tự, có thể khai báo `keyColumn`:

~~~java
@MappedCollection(idColumn = "order_id", keyColumn = "line_position")
private List<OrderLine> lines = new ArrayList<>();
~~~

Khi đó bảng con cần thêm cột `line_position` với kiểu số nguyên phù hợp:

~~~sql
ALTER TABLE order_lines
ADD COLUMN line_position INTEGER;
~~~

`line_position` không thay thế `order_id`: một cột xác định **dòng thuộc root nào**, cột kia xác định **vị trí/key trong collection**. Nếu dùng `Map`, key column lưu khóa của entry theo mapping. Hãy kiểm tra DDL và dữ liệu được sinh khi đổi kiểu collection.

## 8. Truy vấn JOIN vẫn dùng foreign key như SQL thông thường

`@MappedCollection` phục vụ mapping aggregate khi lưu và đọc root. Nó không cấm ứng dụng viết SQL JOIN. Ví dụ báo cáo đơn hàng và số dòng:

~~~sql
SELECT
    o.id,
    o.order_number,
    o.status,
    COUNT(l.id) AS line_count
FROM purchase_orders o
LEFT JOIN order_lines l ON l.order_id = o.id
GROUP BY o.id, o.order_number, o.status
ORDER BY o.id;
~~~

Điều kiện JOIN:

~~~sql
ON l.order_id = o.id
~~~

Đây chính là cặp cột được khai báo bằng foreign key. Có thể dùng `JdbcTemplate`/`NamedParameterJdbcTemplate` để ánh xạ kết quả thành DTO/read model. Không cần tạo repository CRUD cho `OrderLine` chỉ để đọc báo cáo.

### Truy vấn các dòng thuộc một đơn

~~~sql
SELECT l.id, l.product_id, l.quantity, l.unit_price
FROM order_lines l
WHERE l.order_id = :orderId
ORDER BY l.id;
~~~

Trong Spring JDBC, `:orderId` có thể được gắn bằng `NamedParameterJdbcTemplate`. Với SQL JDBC thuần dùng dấu `?` và bind parameter theo vị trí. Không nối trực tiếp giá trị đầu vào vào chuỗi SQL.

## 9. Khi nào không nên dùng `@MappedCollection`?

Không phải mọi foreign key đều biểu diễn một entity con thuộc aggregate root.

### 9.1. Tham chiếu đến aggregate khác

Giả sử đơn hàng tham chiếu khách hàng:

~~~text
PurchaseOrder  ------ customer_id ------> Customer
    root                                  root riêng
~~~

`Customer` có vòng đời riêng, được nhiều đơn hàng tham chiếu. Không nên đưa toàn bộ `Customer` vào collection sở hữu của `PurchaseOrder`. Thường chỉ lưu ID:

~~~java
private Long customerId;
~~~

Hoặc dùng kiểu `AggregateReference<Customer, Long>` của Spring Data Relational nếu muốn biểu đạt rõ ý nghĩa tham chiếu aggregate. Mỗi aggregate root có repository riêng khi cần truy cập.

### 9.2. Quan hệ nhiều-nhiều

Nếu một sản phẩm xuất hiện trong nhiều đơn và một đơn có nhiều sản phẩm, quan hệ domain thường không phải là “một OrderLine dùng chung cho nhiều Order”. Mỗi dòng hàng là một phần của một đơn; nó giữ `order_id` và `product_id`, trong khi `product_id` tham chiếu một aggregate Product riêng.

~~~text
PurchaseOrder 1 --- N OrderLine N --- 1 Product
~~~

Đây là hai quan hệ many-to-one từ `OrderLine` đến root `PurchaseOrder` (ownership) và root `Product` (reference). Không cần một entity Product được sở hữu trong mỗi đơn.

### 9.3. Đối tượng có vòng đời độc lập

Nếu một entity có thể được tạo, cập nhật, xóa và quản lý độc lập với root hiện tại, hãy xem xét biến nó thành aggregate root riêng. Khi đó, quan hệ database có thể vẫn là foreign key, nhưng trong domain model nó được tham chiếu bằng ID thay vì collection sở hữu.

Ví dụ `Shipment` có trạng thái vận chuyển, tracking event và quy trình cập nhật độc lập có thể là aggregate riêng, dù nó tham chiếu `purchase_order_id`.

## 10. Những lỗi thường gặp

| Hiện tượng | Nguyên nhân | Cách xử lý |
|---|---|---|
| Lưu root nhưng cột `order_id` không tồn tại | Chưa tạo DDL hoặc migration cho bảng con | Thêm cột `order_id` vào `order_lines` |
| Lỗi foreign key khi insert dòng hàng | Giá trị root ID chưa tồn tại hoặc kiểu/cột tham chiếu không khớp | Để Spring Data JDBC lưu aggregate đúng mapping; kiểm tra kiểu ID và DDL |
| `order_id` luôn null | `idColumn` không khớp tên cột hoặc mapping collection sai | Đặt `@MappedCollection(idColumn = "order_id")` và kiểm tra schema |
| Không tải được dòng hàng khi đọc root | Bảng con, tên bảng hoặc cột tham chiếu không đúng mapping | Kiểm tra `@Table`, `idColumn`, dữ liệu FK và SQL log |
| Tạo thêm `OrderLineRepository` chỉ để lưu dòng con | Nhầm entity có `@Id` với aggregate root | Thao tác thay đổi dòng hàng qua `PurchaseOrder` |
| Thêm `orderId` field vào con và bị mapping trùng | Vừa khai báo cột qua collection vừa ánh xạ property riêng | Chọn một mô hình mapping nhất quán; với owned child dùng `idColumn` |
| Dùng nhầm `@OneToMany`/`@JoinColumn` | Áp dụng annotation JPA cho Spring Data JDBC | Dùng `@MappedCollection` của Spring Data Relational |
| Truy vấn root chậm khi aggregate có nhiều child | Thiết kế aggregate quá lớn hoặc thiếu index FK | Xem lại ranh giới aggregate, index `order_id`, query plan |

### Phân biệt annotation đúng package

Trong Spring Data JDBC, các annotation thường dùng:

~~~java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;
~~~

Không nhầm với:

~~~java
// Các annotation này thuộc JPA:
import jakarta.persistence.Entity;
import jakarta.persistence.Id;
import jakarta.persistence.OneToMany;
import jakarta.persistence.JoinColumn;
~~~

Spring Data JDBC có mô hình aggregate riêng. Chỉ đổi package import mà vẫn giữ tư duy object graph hai chiều/lazy loading của JPA sẽ dẫn đến mapping và hành vi không như mong đợi.

## 11. Quy trình thiết kế quan hệ cha-con

Khi gặp một bảng con trong domain Spring Data JDBC, hãy đi theo trình tự:

1. **Xác định ownership:** bảng con có thực sự thuộc vòng đời aggregate root không?
2. **Chọn root:** thao tác nào cần bảo vệ các invariant của nhóm dữ liệu?
3. **Đặt FK ở phía many:** bảng con giữ cột tham chiếu đến primary key bảng cha.
4. **Khai báo schema:** tạo cột cùng kiểu, `NOT NULL` nếu bắt buộc, foreign key và index khi phù hợp.
5. **Ánh xạ collection:** khai báo `@MappedCollection(idColumn = "...")` trên root.
6. **Tạo repository cho root:** không suy ra repository từ số lượng bảng.
7. **Kiểm tra lưu/đọc:** quan sát dữ liệu FK và thử tải lại aggregate.
8. **Tách read query khi cần:** dùng JOIN/DAO cho báo cáo mà không thay đổi ownership.

## 12. Bài tập thực hành

### Bài 1 — Xây dựng quan hệ đơn hàng và dòng hàng

- Tạo hai bảng `purchase_orders` và `order_lines` theo DDL trong bài.
- Khai báo `PurchaseOrder` có `Set<OrderLine>` và `@MappedCollection(idColumn = "order_id")`.
- Tạo `PurchaseOrderRepository`.
- Lưu một đơn có hai dòng hàng.
- Truy vấn trực tiếp `order_lines` và xác nhận hai hàng có cùng `order_id`.

### Bài 2 — Thay đổi tên cột tham chiếu

Đổi cột `order_id` thành `purchase_order_id` trong database. Cập nhật `@MappedCollection(idColumn = "purchase_order_id")` và migration tương ứng. Giải thích vì sao chỉ đổi annotation mà không đổi DDL sẽ gây lỗi.

### Bài 3 — Thứ tự collection

Thay `Set<OrderLine>` bằng `List<OrderLine>`, thêm `keyColumn = "line_position"` và cột tương ứng. Lưu ba dòng hàng theo thứ tự, tải lại aggregate và quan sát vị trí được lưu. Giải thích vì sao `keyColumn` không phải foreign key đến root.

### Bài 4 — Tách aggregate

Giả sử `Shipment` được cập nhật độc lập sau khi đơn hàng đã gửi. Thiết kế bảng `shipments` có `purchase_order_id` tham chiếu `purchase_orders.id`, nhưng tạo `ShipmentRepository` riêng. Giải thích sự khác biệt giữa foreign key ở database và ownership của aggregate.

## 13. Kết luận

Trong quan hệ một-nhiều, **bảng con là nơi lưu khóa ngoại trỏ về bảng cha**. Với Spring Data JDBC, aggregate root khai báo collection con qua `@MappedCollection(idColumn = "order_id")`; `idColumn` chỉ tên cột tham chiếu ở bảng con. Entity con không cần một property Java trỏ ngược đến root chỉ để duy trì foreign key.

Annotation mô tả mapping object-relational, còn DDL/migration phải tạo cột `order_id`, foreign key, kiểu dữ liệu và index phù hợp. Khi root được lưu hoặc tải, Spring Data JDBC xử lý các thành phần thuộc aggregate theo mapping. Khi cần báo cáo hoặc JOIN, vẫn có thể truy vấn trực tiếp qua SQL mà không tạo repository CRUD cho từng bảng.

Hãy nhớ tách ba quyết định: **foreign key nằm ở đâu trong database, object nào sở hữu object nào trong aggregate, và repository nào là cổng truy cập nghiệp vụ**. Chúng có liên quan nhưng không phải cùng một khái niệm.
