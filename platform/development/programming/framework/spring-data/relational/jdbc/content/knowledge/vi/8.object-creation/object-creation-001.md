# Spring Data tạo đối tượng từ hàng dữ liệu như thế nào?

## 1. Từ một hàng SQL đến một đối tượng Java

Khi gọi repository:

~~~java
Optional<Book> result = bookRepository.findById(42L);
~~~

ứng dụng nhận được một đối tượng `Book`, dù database chỉ lưu một hàng trong bảng `books`. Spring Data JDBC thực hiện quá trình **đọc giá trị từ kết quả JDBC, đối chiếu metadata ánh xạ, chuyển đổi kiểu và khởi tạo đối tượng Java**.

Luồng tổng quát:

~~~mermaid
flowchart TD
    A["Repository method<br/>findById / query"] --> B["Spring Data JDBC data access"]
    B --> C["JDBC PreparedStatement"]
    C --> D["Database executes SQL"]
    D --> E["ResultSet"]
    E --> F["Row mapping / JdbcConverter"]
    F --> G["Relational mapping metadata"]
    G --> H["Convert JDBC values to Java types"]
    H --> I["Select persistence constructor"]
    I --> J["Create object"]
    J --> K["Populate remaining properties"]
    K --> L["Return entity / aggregate"]
~~~

Điểm quan trọng: **Spring Data JDBC không đơn giản lấy cột thứ nhất gán vào field thứ nhất, cột thứ hai gán vào field thứ hai**. Framework sử dụng metadata về entity, property, constructor, tên bảng/cột và converter để xác định cách tạo object. Vì vậy, thứ tự cột trong câu SQL thường không phải thứ tự tham số constructor; tên cột và metadata mapping mới là yếu tố quyết định.

Bài viết tập trung vào Spring Data JDBC trong module Spring Data Relational JDBC. Cách hiện thực nội bộ có thể thay đổi theo phiên bản, nhưng các khái niệm về mapping metadata, persistence constructor, conversion và property population là nền tảng để hiểu quá trình này.

## 2. Những thành phần tham gia vào quá trình mapping

Ở mức khái niệm, các thành phần chính gồm:

| Thành phần | Vai trò |
|---|---|
| Repository / data access strategy | Nhận yêu cầu đọc dữ liệu và thực thi thao tác JDBC phù hợp |
| JDBC ResultSet | Cung cấp giá trị của từng hàng kết quả từ database |
| Row mapper của Spring Data JDBC | Đọc từng hàng và chuyển nó thành đối tượng thông qua converter |
| JdbcConverter / mapping converter | Phối hợp metadata, conversion và object creation |
| RelationalMappingContext | Giữ metadata ánh xạ cho entity và property quan hệ |
| RelationalPersistentEntity | Mô tả một entity: bảng, identifier, constructor và property |
| RelationalPersistentProperty | Mô tả property: tên cột, kiểu Java, annotation và quy tắc mapping |
| EntityInstantiator / persistence constructor | Tạo instance theo constructor được Spring Data lựa chọn |
| PersistentPropertyAccessor | Gán property chưa được truyền vào constructor hoặc tạo instance mới với object bất biến |
| Custom conversions | Chuyển đổi kiểu SQL/JDBC và kiểu Java do ứng dụng định nghĩa |

Tên class nội bộ và cách các thành phần phối hợp có thể thay đổi theo phiên bản Spring Data. Không cần ghi nhớ toàn bộ implementation để sử dụng repository; cần hiểu vai trò của từng bước khi debug mapping.

### Luồng đọc một hàng

1. Repository hoặc câu truy vấn tùy biến yêu cầu dữ liệu.
2. JDBC thực thi SQL và trả về `ResultSet`.
3. Row mapper đọc một hàng tại thời điểm hiện tại.
4. Converter sử dụng metadata để xác định property tương ứng với các cột.
5. Giá trị JDBC được chuyển sang kiểu Java đích nếu cần.
6. Spring Data chọn persistence constructor và truyền các giá trị tương ứng.
7. Các property còn lại được gán sau khi tạo object, theo khả năng truy cập của property.
8. Với aggregate có quan hệ, Spring Data JDBC tiếp tục nạp các phần dữ liệu thuộc aggregate theo mapping của chúng.

## 3. Ví dụ dữ liệu nguồn

Giả sử database có bảng:

~~~sql
CREATE TABLE books (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    isbn_code VARCHAR(20) NOT NULL,
    title VARCHAR(200) NOT NULL,
    price DECIMAL(12, 2) NOT NULL,
    published_on DATE
);

INSERT INTO books (isbn_code, title, price, published_on)
VALUES
    ('978-0000000001', 'Spring Data JDBC', 199000.00, DATE '2025-01-15'),
    ('978-0000000002', 'Relational Mapping', 159000.00, NULL);
~~~

Entity Java:

~~~java
import java.math.BigDecimal;
import java.time.LocalDate;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("books")
public class Book {

    @Id
    private Long id;

    @Column("isbn_code")
    private String isbn;

    private String title;

    private BigDecimal price;

    @Column("published_on")
    private LocalDate publishedOn;

    // constructors, getters...
}
~~~

Các quy tắc:

- `id` là identifier do `@Id` xác định.
- `isbn` được ánh xạ tới cột `isbn_code`.
- `title` và `price` dùng tên cột theo metadata/quy ước mặc định.
- `publishedOn` được ánh xạ tới `published_on`.
- SQL `NULL` của `published_on` có thể được biểu diễn bằng `null` trong property tham chiếu `LocalDate`.

Truy vấn:

~~~sql
SELECT id, isbn_code, title, price, published_on
FROM books
WHERE id = ?;
~~~

Một hàng kết quả chứa giá trị của năm cột. Spring Data không cần biết cột nào đứng trước trong class; nó dùng tên cột và metadata mapping để đưa giá trị vào property đúng.

## 4. Bước 1: đọc ResultSet và nhận diện cột

`ResultSet` là API JDBC biểu diễn tập kết quả truy vấn. Ở mỗi hàng, driver cho phép đọc giá trị bằng tên cột hoặc index:

~~~java
long id = rs.getLong("id");
String title = rs.getString("title");
BigDecimal price = rs.getBigDecimal("price");
~~~

Spring Data JDBC sử dụng row mapping để chuyển hàng kết quả sang cấu trúc dữ liệu mà converter có thể đọc. Thay vì yêu cầu entity phải tự biết cách gọi `rs.getString(...)`, converter lấy tên cột, kiểu dữ liệu và metadata của property để thực hiện ánh xạ.

### 4.1. Mapping dựa trên tên cột

Property Java `isbn` được ánh xạ bằng:

~~~java
@Column("isbn_code")
private String isbn;
~~~

Giá trị cần đọc đến từ cột `isbn_code`. Nếu SQL trả về cột `isbn` nhưng metadata đang chờ `isbn_code`, mapping có thể không tìm thấy giá trị như mong đợi. Với query tùy biến, cần trả về tên cột hoặc alias tương thích với metadata và projection mà method yêu cầu.

**Đừng dựa vào vị trí cột trong SELECT** để suy ra thứ tự field hoặc tham số constructor. Thay đổi thứ tự cột trong SQL không nên làm thay đổi ý nghĩa mapping nếu tên cột vẫn đúng.

### 4.2. Tên cột và quy ước đặt tên

Spring Data Relational sử dụng naming strategy để liên hệ tên property với tên cột vật lý. Ví dụ `publishedOn` thường tương ứng `published_on`. `@Column` cho phép chỉ định tường minh khi schema khác quy ước.

Với database có identifier được quote, chữ hoa/chữ thường hoặc tên đặc biệt, cần xác nhận cách driver báo column label và cách dialect/naming strategy xử lý. Query tùy biến nên chọn alias có chủ đích, không đặt alias tùy tiện rồi kỳ vọng converter tự đoán.

## 5. Bước 2: chuyển đổi kiểu dữ liệu JDBC sang Java

Kiểu dữ liệu database và kiểu Java không phải lúc nào cũng giống nhau. JDBC driver trả về giá trị theo API JDBC; Spring Data JDBC sử dụng conversion infrastructure để chuyển sang kiểu property cần nhận.

| Kiểu SQL thường gặp | Kiểu Java thường dùng | Ghi chú |
|---|---|---|
| `BIGINT` | `Long` | Phù hợp identifier số |
| `INTEGER` | `Integer` | Dùng wrapper nếu cột cho phép NULL |
| `VARCHAR` | `String` | Độ dài và charset do schema quyết định |
| `DECIMAL`, `NUMERIC` | `BigDecimal` | Phù hợp dữ liệu tiền và thập phân chính xác |
| `DATE` | `LocalDate` | Chỉ biểu diễn ngày |
| `TIMESTAMP` | `LocalDateTime` | Không mang thông tin múi giờ |
| `BOOLEAN` | `Boolean` | Mapping cụ thể phụ thuộc driver/database |
| `UUID` | `UUID` | Hỗ trợ phụ thuộc database và driver |

Ví dụ cột `price DECIMAL(12, 2)` được đọc thành `BigDecimal`, thay vì dùng `double` cho số tiền cần độ chính xác thập phân.

### 5.1. NULL và kiểu Java

Nếu database trả `NULL` cho cột nullable, property Java nên có khả năng biểu diễn giá trị không có dữ liệu:

~~~java
private LocalDate publishedOn;
private Integer pageCount;
~~~

Dùng wrapper `Integer` thay cho primitive `int` khi cột có thể null. Primitive không thể biểu diễn `null`; khi mapping nhận giá trị null vào primitive hoặc constructor primitive, ứng dụng có thể gặp lỗi chuyển đổi/khởi tạo hoặc giá trị mặc định không phản ánh đúng nghiệp vụ, tùy đường mapping.

Không nên tự diễn giải SQL NULL thành `0`, chuỗi rỗng hoặc ngày hiện tại nếu nghiệp vụ không quy định như vậy.

### 5.2. Custom conversion cho kiểu miền

Giả sử domain dùng kiểu `Isbn` thay cho `String`:

~~~java
public record Isbn(String value) {
    public Isbn {
        if (value == null || value.isBlank()) {
            throw new IllegalArgumentException("ISBN không được rỗng");
        }
    }
}
~~~

Ứng dụng có thể đăng ký converter đọc và ghi để ánh xạ `VARCHAR` với `Isbn`.

Reading converter:

~~~java
import org.springframework.core.convert.converter.Converter;
import org.springframework.data.convert.ReadingConverter;

@ReadingConverter
public class StringToIsbnConverter implements Converter<String, Isbn> {
    @Override
    public Isbn convert(String source) {
        return new Isbn(source);
    }
}
~~~

Writing converter:

~~~java
import org.springframework.core.convert.converter.Converter;
import org.springframework.data.convert.WritingConverter;

@WritingConverter
public class IsbnToStringConverter implements Converter<Isbn, String> {
    @Override
    public String convert(Isbn source) {
        return source.value();
    }
}
~~~

Các converter cần được đăng ký trong cấu hình Spring Data JDBC (ví dụ qua danh sách user converters của cấu hình relational JDBC tương ứng với phiên bản đang dùng). Chỉ đặt annotation trên class converter không đảm bảo mọi ứng dụng tự phát hiện converter đó.

Custom converter nên xác định rõ chiều chuyển đổi:

- **Reading converter:** giá trị từ JDBC/database sang kiểu miền.
- **Writing converter:** kiểu miền sang kiểu JDBC/database.

## 6. Bước 3: Spring Data chọn constructor để tạo object

Sau khi có các giá trị phù hợp, Spring Data phải tạo instance. Đây là phần quan trọng để hiểu vì sao entity có thể dùng constructor, record hoặc class bất biến.

Spring Data tìm **persistence constructor** theo metadata. Những trường hợp thường gặp:

1. **Java record:** canonical constructor của record được sử dụng để tạo instance.
2. **Một constructor duy nhất:** constructor đó thường được chọn.
3. **Nhiều constructor:** có thể đánh dấu constructor phù hợp bằng `@PersistenceCreator`.
4. **Constructor không tham số:** có thể được sử dụng khi phù hợp với quy tắc lựa chọn và các constructor khác.
5. **Factory method hoặc kiểu khởi tạo được hỗ trợ:** có thể được chọn theo metadata tương ứng.

Nếu có nhiều constructor mà không có lựa chọn rõ ràng theo quy tắc Spring Data, quá trình tạo entity có thể thất bại. Hãy thiết kế constructor rõ ràng và dùng `@PersistenceCreator` khi cần chỉ định.

### 6.1. Constructor được chọn theo tên property

Ví dụ entity bất biến:

~~~java
import java.math.BigDecimal;
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.PersistenceCreator;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("books")
public class Book {

    @Id
    private final Long id;

    @Column("isbn_code")
    private final String isbn;

    private final String title;

    private final BigDecimal price;

    @PersistenceCreator
    public Book(Long id, String isbn, String title, BigDecimal price) {
        this.id = id;
        this.isbn = isbn;
        this.title = title;
        this.price = price;
    }

    public Long getId() {
        return id;
    }

    public String getIsbn() {
        return isbn;
    }

    public String getTitle() {
        return title;
    }

    public BigDecimal getPrice() {
        return price;
    }
}
~~~

Tên tham số constructor cần tương ứng với tên property Java: `id`, `isbn`, `title`, `price`. Tên cột vật lý `isbn_code` được metadata `@Column` ánh xạ về property `isbn`; constructor không cần nhận tham số tên `isbn_code`.

Điều này tách hai khái niệm:

- **Column name:** tên cột ở database.
- **Property/parameter name:** tên thuộc tính Java mà constructor nhận.

Nếu biên dịch class thông thường mà parameter name không được lưu, framework có thể thiếu thông tin để liên kết tham số constructor với property. Với Java build, cần bảo đảm cấu hình giữ parameter names (ví dụ compiler option `-parameters`) khi mapping dựa trên tên tham số. Record có metadata component/constructor rõ ràng hơn.

### 6.2. Record và canonical constructor

Với Java record:

~~~java
import java.math.BigDecimal;
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("books")
public record Book(
        @Id Long id,
        @Column("isbn_code") String isbn,
        String title,
        BigDecimal price
) {}
~~~

Record là kiểu bất biến: sau khi khởi tạo, các component không thể gán lại. Spring Data sử dụng canonical constructor để tạo record với các giá trị đã đọc.

Khi gọi `repository.save(new Book(null, ...))`, repository có thể trả về một record mới mang ID được database tạo. Vì vậy luôn dùng **giá trị trả về của `save`** để nhận phiên bản entity có identifier được cập nhật.

### 6.3. @PersistenceCreator dùng khi nào?

Nếu class có nhiều constructor:

~~~java
public class Book {

    private final Long id;
    private final String title;
    private final String isbn;

    public Book(String title) {
        this(null, title, null);
    }

    @PersistenceCreator
    public Book(Long id, String title, String isbn) {
        this.id = id;
        this.title = title;
        this.isbn = isbn;
    }

    // getters...
}
~~~

`@PersistenceCreator` chỉ ra constructor Spring Data nên dùng khi đọc dữ liệu. Annotation thuộc `org.springframework.data.annotation.PersistenceCreator`.

Constructor được chọn phải có thể nhận các giá trị cần thiết để tạo entity hợp lệ; tên tham số cần khớp với property Java tương ứng.

## 7. Bước 4: gán property sau khi constructor chạy

Không phải mọi property đều nhất thiết được truyền vào constructor. Sau khi tạo instance, Spring Data có thể điền những property còn lại thông qua cơ chế truy cập property.

Ví dụ class mutable:

~~~java
@Table("books")
public class Book {

    @Id
    private Long id;

    private String title;

    private BigDecimal price;

    public Book() {
    }

    public Long getId() {
        return id;
    }

    public void setId(Long id) {
        this.id = id;
    }

    public String getTitle() {
        return title;
    }

    public void setTitle(String title) {
        this.title = title;
    }

    public BigDecimal getPrice() {
        return price;
    }

    public void setPrice(BigDecimal price) {
        this.price = price;
    }
}
~~~

Với mô hình này, Spring Data có thể tạo instance bằng constructor không tham số rồi gán giá trị vào các property còn thiếu theo metadata và cơ chế truy cập phù hợp.

Các cách truy cập property thường gồm:

- **Field access:** ghi trực tiếp vào field khi mapping chọn field làm điểm truy cập.
- **Property/setter access:** sử dụng setter tương ứng.
- **Wither/copy method:** với object bất biến, tạo instance mới chứa property được cập nhật.
- **Constructor:** truyền property ngay trong lúc khởi tạo, tránh gán lại sau đó.

Không nên viết business logic quan trọng trong setter chỉ vì kỳ vọng setter luôn được gọi khi Spring Data đọc entity. Cách truy cập cụ thể phụ thuộc metadata và mô hình entity.

### 7.1. Object bất biến và wither

Giả sử class bất biến có property `createdAt` được gán trong lifecycle nhưng không nằm trong persistence constructor. Có thể dùng wither trả về object mới:

~~~java
public Book withCreatedAt(Instant createdAt) {
    return new Book(id, title, price, createdAt);
}
~~~

Spring Data có thể sử dụng phương thức wither theo quy ước để tạo bản sao có property mới thay vì sửa field final. Với entity bất biến, cách tốt nhất thường là đưa các giá trị cần thiết vào persistence constructor, nhất là khi chúng bắt buộc để tạo object hợp lệ.

## 8. So sánh ba cách tạo đối tượng

| Cách thiết kế | Quá trình tạo | Điểm phù hợp |
|---|---|---|
| Class mutable, constructor không tham số | Tạo instance rồi gán các property | Mô hình đơn giản, có setter/field access |
| Class bất biến, persistence constructor | Đọc giá trị rồi truyền vào constructor | Giữ invariant, tránh object ở trạng thái chưa hoàn chỉnh |
| Java record | Dùng canonical constructor với component values | DTO/domain value đơn giản, dữ liệu bất biến |

**Mutable object:**

~~~java
Book book = new Book();
book.setId(42L);
book.setTitle("Spring Data JDBC");
~~~

**Immutable object:**

~~~java
Book book = new Book(42L, "Spring Data JDBC");
~~~

Cả hai có thể biểu diễn cùng dữ liệu. Khác biệt là object mutable cho phép trạng thái trung gian và thay đổi sau khởi tạo; object immutable cần dữ liệu cần thiết được cung cấp qua constructor hoặc cơ chế tạo bản sao.

## 9. Một hàng SQL có tương ứng một aggregate hoàn chỉnh không?

Đây là điểm đặc biệt quan trọng của **Spring Data JDBC**.

Một row mapper có thể tạo aggregate root từ hàng dữ liệu của bảng chính. Tuy nhiên, aggregate có thể chứa các đối tượng con/collection được lưu ở bảng khác. Spring Data JDBC sử dụng mapping metadata để nạp những phần thuộc aggregate theo mô hình relational mapping; không nên giả định mọi object con đều nằm sẵn trong cùng một hàng kết quả.

Ví dụ:

~~~text
orders
+----+------------+
| id | order_date |
+----+------------+
| 10 | 2026-01-15 |
+----+------------+

order_lines
+----+----------+------------+-----+
| id | order_id | product_id | qty |
+----+----------+------------+-----+
|  1 |       10 |        101 |   2 |
|  2 |       10 |        205 |   1 |
+----+----------+------------+-----+
~~~

Aggregate root `Order` có thể chứa collection `lines`:

~~~java
@Table("orders")
public class Order {

    @Id
    private Long id;

    @Column("order_date")
    private LocalDate orderDate;

    @MappedCollection(idColumn = "order_id")
    private List<OrderLine> lines;

    // constructor, getters...
}
~~~

Spring Data JDBC biết `order_lines.order_id` liên kết các dòng hàng với order tương ứng. Khi tải aggregate, framework cần đọc dữ liệu root và dữ liệu các thành phần thuộc aggregate theo mapping. Chi tiết truy vấn phụ thuộc cấu trúc aggregate và implementation; không nên đồng nhất nó với một câu `JOIN` duy nhất trả về mọi cột.

### 9.1. Embedded object khác collection

Với `@Embedded`, thuộc tính của value object có thể nằm ngay trong hàng của bảng chứa. Ví dụ một `Address` được tạo từ các cột địa chỉ của cùng hàng `customers`. Prefix hoặc quy tắc embedded mapping có thể giúp tránh trùng tên cột.

Trong trường hợp này, converter đọc nhiều cột từ **cùng hàng** để tạo value object `Address`. Với collection được ánh xạ sang bảng con, framework phải tìm các hàng liên quan bằng khóa tham chiếu.

- Embedded: đọc nhiều cột của hàng cha.
- Collection thuộc aggregate: nạp dữ liệu ở bảng liên quan theo quan hệ mapping.

## 10. Mapping dữ liệu từ custom query

Spring Data JDBC có thể ánh xạ kết quả truy vấn tùy biến vào entity hoặc projection phù hợp. Ví dụ:

~~~java
public interface BookRepository extends CrudRepository<Book, Long> {

    @Query("""
        SELECT id, isbn_code, title, price, published_on
        FROM books
        WHERE price >= :minPrice
        ORDER BY title
        """)
    List<Book> findExpensiveBooks(BigDecimal minPrice);
}
~~~

Với kiểu trả về `Book`, kết quả cần cung cấp những cột mà mapping của `Book` cần. Tên cột phải phù hợp với `@Column` và naming strategy. Nếu chỉ trả về một vài cột nhưng method khai báo trả về entity đầy đủ, các property không có dữ liệu có thể không được khởi tạo như nghiệp vụ mong muốn.

Nếu chỉ cần một phần dữ liệu, hãy định nghĩa projection/DTO:

~~~java
public record BookSummary(
        String title,
        BigDecimal price
) {}
~~~

Truy vấn:

~~~java
@Query("""
    SELECT title, price
    FROM books
    WHERE price >= :minPrice
    ORDER BY title
    """)
List<BookSummary> findSummaries(BigDecimal minPrice);
~~~

Projection có constructor tương ứng với các giá trị trả về; tên/alias cột cần tương thích với cách framework ánh xạ projection. Với projection phức tạp hoặc query có join, hãy xác định rõ kiểu kết quả thay vì ép tập cột không đầy đủ thành aggregate root.

## 11. Phân biệt Spring Data JDBC mapping với RowMapper tự viết

Nếu dùng Spring JDBC trực tiếp, ứng dụng thường tự viết `RowMapper`:

~~~java
RowMapper<BookSummary> mapper = (rs, rowNum) ->
        new BookSummary(
                rs.getString("title"),
                rs.getBigDecimal("price")
        );

List<BookSummary> summaries = jdbcTemplate.query(
        "SELECT title, price FROM books",
        mapper
);
~~~

Ở đây **ứng dụng tự quyết định**:

- Cột nào được đọc.
- Đọc theo tên hay index.
- Giá trị nào truyền vào constructor.
- Xử lý null và chuyển đổi kiểu ra sao.

Với Spring Data JDBC repository, framework dựa vào mapping context, metadata và converter để thực hiện các bước đó theo quy ước và annotation.

| Tiêu chí | Spring Data JDBC Repository | Spring JDBC RowMapper tự viết |
|---|---|---|
| Chọn cột/metadata | Dựa trên mapping entity/projection | Người viết mapper quyết định |
| Tạo object | Converter và persistence constructor | Lambda/class mapper tự tạo |
| Đổi tên cột | `@Column`, naming strategy và metadata | SQL alias hoặc logic mapper |
| Chuyển kiểu | Conversion infrastructure và custom conversions | JDBC getter hoặc converter tự viết |
| Aggregate | Có quy tắc mapping aggregate | Người viết tự truy vấn và ghép object |
| CRUD | Repository hỗ trợ thao tác chuẩn | Tự viết SQL và mapper |

Không nên nghĩ `@Column` tự động thay đổi SQL do `JdbcTemplate` tự viết. Annotation thuộc metadata của Spring Data mapping; SQL/`RowMapper` thủ công vẫn do ứng dụng kiểm soát.

## 12. Tùy biến object creation và mapping

### 12.1. Dùng @PersistenceCreator

Khi entity có nhiều constructor, đánh dấu constructor được dùng để tạo entity:

~~~java
@PersistenceCreator
public Book(Long id, String title, BigDecimal price) {
    this.id = id;
    this.title = title;
    this.price = price;
}
~~~

Giữ tên tham số trùng với property Java và bảo đảm metadata parameter names có thể được phát hiện.

### 12.2. Dùng converter cho kiểu đặc biệt

Khi database lưu một kiểu đơn giản nhưng domain dùng kiểu riêng, tạo reading/writing converter và đăng ký vào cấu hình Spring Data JDBC. Không nhồi logic parse dữ liệu phức tạp vào getter hoặc setter.

### 12.3. Dùng lifecycle callback cho bước bổ sung

Spring Data Relational có callback như `AfterConvertCallback` để thực hiện xử lý sau khi entity được chuyển đổi từ dữ liệu đọc. Ví dụ có thể chuẩn hóa hoặc bổ sung thông tin dẫn xuất, nhưng callback nên có mục đích rõ ràng và không thay thế conversion/mapping chuẩn.

Khung callback:

~~~java
import org.springframework.data.relational.core.mapping.event.AfterConvertCallback;
import org.springframework.stereotype.Component;

@Component
public class BookAfterConvertCallback
        implements AfterConvertCallback<Book> {

    @Override
    public Book onAfterConvert(Book book) {
        // Chỉ thực hiện xử lý bổ sung phù hợp sau mapping.
        return book;
    }
}
~~~

Callback trả về entity được sử dụng tiếp. Với object bất biến, tạo và trả về instance mới nếu cần thay đổi dữ liệu. Đừng dùng callback để âm thầm truy vấn nhiều dữ liệu hoặc tạo side effect không cần thiết khi đọc từng entity.

## 13. Những lỗi phổ biến khi Spring Data tạo object

| Biểu hiện | Nguyên nhân có thể | Hướng kiểm tra |
|---|---|---|
| Không tìm được giá trị cho property | Tên cột/alias không khớp metadata | Kiểm tra DDL, `@Column`, naming strategy và SELECT |
| Constructor không được chọn như mong muốn | Nhiều constructor nhưng không xác định persistence constructor | Dùng `@PersistenceCreator` và kiểm tra quy tắc constructor |
| Không khởi tạo được constructor parameter | Parameter name không được giữ hoặc không trùng property | Bật `-parameters`, kiểm tra tên tham số và record |
| Lỗi chuyển đổi kiểu | Kiểu SQL và Java không tương thích hoặc thiếu converter | Kiểm tra driver, Java type và reading converter |
| Giá trị null gây lỗi | Property primitive hoặc constructor không chấp nhận null | Dùng wrapper/nullable type hoặc ràng buộc dữ liệu rõ |
| Record trả về ID null sau save | Dùng instance cũ thay vì instance `save` trả về, hoặc generated key chưa được hỗ trợ/cấu hình | Dùng giá trị trả về và kiểm tra identity/driver |
| Property không được cập nhật | Mapping access strategy không phù hợp, field bất biến không có wither/constructor | Đưa property vào constructor hoặc cung cấp cơ chế copy |
| Aggregate thiếu collection con | Quan hệ chưa khai báo đúng hoặc cột liên kết không khớp | Kiểm tra `@MappedCollection`, foreign key và schema |
| Embedded object luôn null | Các cột/prefix hoặc quy tắc nhận diện object rỗng không đúng | Kiểm tra `@Embedded`, prefix và giá trị các cột |
| Query tùy biến trả entity thiếu dữ liệu | SELECT không trả đủ cột entity cần | Trả đủ cột hoặc dùng projection chuyên biệt |

### Trình tự debug

1. Xác nhận câu SQL và các cột/alias thực tế trả về.
2. Kiểm tra `@Table`, `@Column`, `@Id` và naming strategy.
3. Kiểm tra kiểu Java, kiểu SQL, nullable và custom conversions.
4. Kiểm tra constructor được Spring Data chọn, tên tham số và property access.
5. Nếu là aggregate, kiểm tra mapping quan hệ và dữ liệu ở bảng con.
6. Nếu lỗi chỉ xảy ra ở query tùy biến, so sánh danh sách cột query trả về với entity/projection.

## 14. Bài tập thực hành

### Bài 1 — Quan sát constructor mapping

Tạo `Book` là class bất biến có `@PersistenceCreator` và các property `id`, `title`, `price`. Gọi `findById` rồi quan sát constructor được dùng. Thử đổi thứ tự cột trong câu SELECT nhưng giữ nguyên tên cột để thấy mapping không phụ thuộc thứ tự field.

### Bài 2 — Chuyển class thành record

Chuyển `Book` thành Java record. Thực hiện truy vấn đọc và insert. So sánh canonical constructor với class mutable có setter. Khi insert, lấy ID từ object mà `save` trả về.

### Bài 3 — Đổi tên cột trong database

Đổi cột `isbn` thành `isbn_code`. Thêm `@Column("isbn_code")` và kiểm tra repository vẫn ánh xạ được property `isbn`. Thử query custom trả về alias khác rồi quan sát lỗi hoặc kết quả mapping.

### Bài 4 — Xử lý giá trị NULL

Để `published_on` là NULL. Dùng `LocalDate` và sau đó thử đổi sang primitive hoặc một kiểu không thể biểu diễn null. Giải thích vì sao wrapper/reference type phù hợp hơn cho cột nullable.

### Bài 5 — Tạo custom converter

Tạo kiểu `Isbn` và converter đọc/ghi giữa `String` với `Isbn`. Đăng ký converter trong cấu hình Spring Data JDBC rồi thử lưu và đọc lại.

### Bài 6 — Aggregate có collection

Tạo `Order` có danh sách `OrderLine` được lưu ở bảng con. Dùng `@MappedCollection`, lưu aggregate và đọc lại. Theo dõi cách các hàng con được liên kết với ID của aggregate root.

### Bài 7 — So sánh repository và RowMapper

Viết một truy vấn bằng repository Spring Data JDBC và một truy vấn khác bằng `JdbcTemplate` + `RowMapper`. So sánh phần code phải tự viết, việc ánh xạ cột và cách xử lý dữ liệu null.

## 15. Ghi nhớ

- Spring Data JDBC đọc hàng thông qua JDBC result mapping rồi dùng **mapping metadata và converter** để tạo object Java.
- Việc ánh xạ dựa trên **tên cột, property metadata và conversion**, không dựa đơn thuần vào thứ tự cột trong câu SELECT.
- Spring Data chọn **persistence constructor**; record dùng canonical constructor, class có nhiều constructor nên chỉ định rõ bằng `@PersistenceCreator` khi cần.
- Các property chưa được truyền vào constructor có thể được điền sau bằng field/setter access hoặc wither/copy method.
- Kiểu dữ liệu database phải tương thích với kiểu Java; custom reading/writing converter xử lý những kiểu miền đặc biệt.
- Một hàng của bảng gốc có thể tạo aggregate root; các collection thuộc aggregate có thể cần đọc thêm từ bảng liên quan. Embedded object được dựng từ các cột cùng hàng.
- `JdbcTemplate` với `RowMapper` tự viết là cơ chế khác: ứng dụng trực tiếp quyết định cách đọc cột và khởi tạo object.
- Khi debug, kiểm tra theo thứ tự **SQL result → column mapping → type conversion → constructor → property population → aggregate mapping**.
