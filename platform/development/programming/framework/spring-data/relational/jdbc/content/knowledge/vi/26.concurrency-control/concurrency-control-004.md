# Xử lý OptimisticLockingFailureException và chính sách thử lại

Trong Spring Data JDBC, nhiều request có thể cùng đọc một aggregate rồi cùng sửa nó. Nếu hai request đều dùng trạng thái cũ, thao tác ghi đến sau có nguy cơ ghi đè thay đổi của thao tác ghi trước. **Optimistic locking** phát hiện tình huống này bằng trường phiên bản `@Version`.

Khi Spring Data JDBC phát hiện phiên bản trong database không còn khớp với phiên bản mà ứng dụng đã đọc, thao tác lưu hoặc xóa thất bại và ném `OptimisticLockingFailureException`. Đây là tín hiệu cho biết aggregate đã bị thay đổi bởi một thao tác khác; ứng dụng cần quyết định có thể thử lại an toàn hay phải trả xung đột cho caller.

Một chính sách thử lại tốt cần bảo đảm:

- Chỉ retry lỗi xung đột có thể phục hồi.
- Mỗi lần retry bắt đầu một transaction mới.
- Tải lại aggregate mới nhất và áp dụng lại ý định nghiệp vụ.
- Giới hạn số lần thử, có backoff và jitter.
- Đánh giá lại bất biến nghiệp vụ sau khi đọc trạng thái mới.
- Không lặp side effect bên ngoài database một cách vô tình.

Bài học giải thích cách `@Version` hoạt động, cách nhận diện và xử lý `OptimisticLockingFailureException`, cách triển khai retry bằng `TransactionTemplate` hoặc Spring Retry, và khi nào nên trả lỗi xung đột thay vì tự động thử lại.

## 1. Vì sao optimistic locking cần thiết?

Giả sử một sản phẩm còn 10 đơn vị tồn kho. Hai request cùng muốn giữ 7 đơn vị:

1. Request A đọc số lượng 10.
2. Request B cũng đọc số lượng 10.
3. A tính số lượng còn 3 và lưu.
4. B dựa trên dữ liệu cũ cũng tính số lượng còn 3 và lưu.

Nếu không có cơ chế phát hiện cập nhật đồng thời, cả hai thao tác có thể thành công. Hệ thống chỉ ghi nhận một lần giảm từ 10 xuống 3, trong khi thực tế đã xác nhận giữ tổng cộng 14 đơn vị. Đây là *lost update*.

Optimistic locking giả định xung đột không xảy ra thường xuyên, nên không khóa hàng trong suốt thời gian ứng dụng xử lý. Thay vào đó, nó kiểm tra xem dữ liệu có thay đổi kể từ lần đọc hay không ngay tại thời điểm ghi.

~~~text
Request A                         Request B
---------                         ---------
Đọc quantity = 10                 Đọc quantity = 10
Đọc version = 5                   Đọc version = 5
Tính quantity = 3                 Tính quantity = 3
UPDATE với version = 5
Thành công, version thành 6
                                  UPDATE với version = 5
                                  Không có hàng khớp
                                  OptimisticLockingFailureException
~~~

Request B biết rằng trạng thái nó dựa vào đã cũ. Nó có thể tải lại aggregate và quyết định có thể tiếp tục hay không.

## 2. Bật optimistic locking bằng @Version

Spring Data JDBC hỗ trợ optimistic locking thông qua thuộc tính được đánh dấu `@Version` trên aggregate root.

Ví dụ:

~~~java
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;
import org.springframework.data.relational.core.mapping.Table;

@Table("inventory_items")
public record InventoryItem(
        @Id Long id,
        String sku,
        int availableQuantity,
        @Version Long version
) {
    public InventoryItem reserve(int quantity) {
        if (quantity <= 0) {
            throw new IllegalArgumentException(
                    "Quantity must be positive"
            );
        }

        if (availableQuantity < quantity) {
            throw new InsufficientStockException(sku);
        }

        return new InventoryItem(
                id,
                sku,
                availableQuantity - quantity,
                version
        );
    }
}
~~~

Schema tương ứng:

~~~sql
CREATE TABLE inventory_items (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    sku VARCHAR(80) NOT NULL UNIQUE,
    available_quantity INTEGER NOT NULL
        CHECK (available_quantity >= 0),
    version BIGINT NOT NULL
);
~~~

Khi tạo aggregate mới, Spring Data JDBC khởi tạo version theo cơ chế của framework. Khi cập nhật aggregate hiện có, framework dùng version đã đọc để kiểm tra bản ghi còn ở phiên bản đó hay không, rồi tăng version sau lần ghi thành công.

Không tự tăng `version` trong phương thức domain thông thường. Version là metadata phục vụ concurrency do persistence layer quản lý.

### 2.1. SQL được thực hiện theo ý tưởng nào?

Giả sử aggregate đang có `id = 42` và `version = 5`. Khi lưu, câu lệnh có ý nghĩa tương đương:

~~~sql
UPDATE inventory_items
SET available_quantity = 3,
    version = 6
WHERE id = 42
  AND version = 5;
~~~

Nếu một hàng được cập nhật, thao tác thành công. Nếu không có hàng nào khớp điều kiện, có thể vì:

- Aggregate đã bị một transaction khác cập nhật và version đã tăng.
- Aggregate đã bị xóa.
- ID không còn tồn tại.
- Trạng thái persistence đã cũ so với database.

Trong trường hợp version không khớp, Spring Data JDBC báo lỗi optimistic locking thay vì âm thầm ghi đè dữ liệu mới.

SQL trên chỉ minh họa nguyên tắc kiểm tra `id` và `version`; câu SQL cụ thể do Spring Data JDBC và dialect tạo ra.

### 2.2. Nếu không có @Version thì sao?

Nếu aggregate không có thuộc tính `@Version`, Spring Data JDBC không thể dùng cơ chế optimistic locking này cho aggregate đó. Các thao tác ghi có thể ghi đè thay đổi của request khác tùy isolation và cách cập nhật.

Nếu một aggregate có nhiều request cập nhật đồng thời, hãy cân nhắc versioning và kiểm tra các invariant quan trọng ở database bằng `CHECK`, `UNIQUE`, foreign key hoặc cơ chế locking thích hợp.

### 2.3. Optimistic locking áp dụng cho update và delete

Với aggregate có version, thao tác xóa cũng cần bảo đảm version của aggregate vẫn là phiên bản mà caller đã đọc. Nếu aggregate đã bị thay đổi sau lần đọc, xóa bằng trạng thái cũ có thể thất bại với optimistic locking exception.

Điều này ngăn một request xóa aggregate dựa trên trạng thái cũ mà không biết một request khác vừa cập nhật nó.

## 3. OptimisticLockingFailureException là gì?

`OptimisticLockingFailureException` thuộc hệ thống exception của Spring DAO, trong nhóm `DataAccessException`. Đây là runtime exception biểu thị thao tác ghi không thể hoàn tất vì optimistic lock đã thất bại.

Import:

~~~java
import org.springframework.dao.OptimisticLockingFailureException;
~~~

Có thể gặp exception này khi:

- Save một aggregate versioned đã bị transaction khác cập nhật.
- Delete một aggregate versioned dựa trên version cũ.
- Hai request cùng sửa một aggregate và request đến sau dùng version không còn hiện hành.

Ví dụ:

~~~java
@Transactional
public InventoryItem reserve(
        String sku,
        int quantity
) {
    InventoryItem item = repository.findBySku(sku)
            .orElseThrow();

    InventoryItem changed = item.reserve(quantity);

    return repository.save(changed);
}
~~~

Nếu một transaction khác cập nhật `item` sau lần đọc nhưng trước khi lệnh save hoàn tất, thao tác save có thể ném `OptimisticLockingFailureException`.

### 3.1. Đây là lỗi concurrency, không phải lỗi validation

Phân biệt optimistic locking với những lỗi khác:

| Loại lỗi | Ví dụ | Có nên retry tự động? |
| --- | --- | --- |
| Optimistic locking | Version trong database khác version đã đọc | Có thể, nếu use case có thể tải lại và áp dụng lại an toàn |
| Validation nghiệp vụ | Số lượng đặt nhỏ hơn hoặc bằng 0 | Không |
| Business rule | Không đủ tồn kho sau khi đọc lại | Không retry mù; trả lỗi nghiệp vụ |
| Unique constraint | SKU hoặc email đã tồn tại | Thường không; cần xử lý xung đột dữ liệu |
| Foreign key | Tham chiếu đến hàng không tồn tại | Thường không |
| Lỗi kết nối database | Database tạm thời không truy cập được | Có chính sách riêng cho transient infrastructure failure |
| Deadlock/serialization failure | Database hủy transaction vì xung đột khóa hoặc isolation | Có thể có retry policy riêng nếu operation an toàn |

Không nên bắt mọi `DataAccessException` rồi retry. Một lỗi constraint hoặc validation không biến mất chỉ vì thực hiện lại cùng câu lệnh.

## 4. Xung đột xảy ra như thế nào?

Giả sử hai transaction cùng đọc tồn kho:

~~~text
Database ban đầu:
  sku = SKU-01
  available_quantity = 10
  version = 5
~~~

Diễn tiến:

| Thời điểm | Transaction A | Transaction B |
| --- | --- | --- |
| T1 | Đọc quantity 10, version 5 | |
| T2 | | Đọc quantity 10, version 5 |
| T3 | Tính còn 3 | Tính còn 4 |
| T4 | Save với version 5 thành công, version tăng 6 | |
| T5 | | Save với version 5 thất bại |
| T6 | | Nhận `OptimisticLockingFailureException` |

Sau T4, trạng thái hiện tại trong database là quantity 3, version 6. Transaction B không được phép ghi kết quả dựa trên quantity 10 nữa.

Nếu nghiệp vụ cho phép thử lại, B cần:

1. Kết thúc transaction thất bại.
2. Mở transaction mới.
3. Tải lại aggregate, lúc này quantity là 3 và version là 6.
4. Áp dụng lại command “giữ 6 đơn vị”.
5. Kiểm tra lại tồn kho.
6. Lưu nếu invariant vẫn hợp lệ.

Với ví dụ này, `reserve(6)` sẽ ném `InsufficientStockException` vì chỉ còn 3. Đó là kết quả đúng sau khi cập nhật lại trạng thái mới nhất.

## 5. Vì sao không retry ngay trong transaction đã thất bại?

Đây là nguyên tắc quan trọng nhất của chính sách retry.

Khi một thao tác persistence ném exception bên trong transaction, transaction có thể đã được đánh dấu rollback-only. Ngay cả khi code bắt exception và gọi `save` lần nữa, transaction đó không còn là một môi trường an toàn để tiếp tục.

Ví dụ không nên làm:

~~~java
@Transactional
public InventoryItem reserveWithBadRetry(
        String sku,
        int quantity
) {
    InventoryItem item = repository.findBySku(sku)
            .orElseThrow();

    InventoryItem changed = item.reserve(quantity);

    try {
        return repository.save(changed);
    } catch (OptimisticLockingFailureException ex) {
        // Không nên save lại object cũ trong transaction này.
        return repository.save(changed);
    }
}
~~~

Có hai vấn đề:

- Object `changed` vẫn chứa version cũ.
- Transaction có thể đã bị đánh dấu rollback-only; các thao tác tiếp theo không thể làm nó trở lại trạng thái commit được.

Ngay cả khi tải lại aggregate trong cùng method, transaction hiện tại vẫn có thể đã rollback-only và không thể commit thành công.

**Retry phải bao quanh transaction, không nằm bên trong transaction đã thất bại.** Mỗi lần thử cần có transaction mới, đọc trạng thái mới và áp dụng lại command.

~~~text
Retry coordinator
   |
   +-- Attempt 1
   |      BEGIN transaction 1
   |      Load aggregate
   |      Apply command
   |      Save -> optimistic conflict
   |      ROLLBACK transaction 1
   |
   +-- Backoff
   |
   +-- Attempt 2
          BEGIN transaction 2
          Load aggregate mới
          Re-apply command
          Save
          COMMIT hoặc ROLLBACK
~~~

## 6. Chính sách retry nên có những gì?

Một retry policy tốt cần được giới hạn rõ ràng.

### 6.1. Chỉ retry exception phù hợp

Chỉ bắt `OptimisticLockingFailureException` cho chính sách này. Không bắt `Exception` hoặc toàn bộ `DataAccessException` rồi thử lại mọi lỗi.

Nếu hệ thống có retry cho deadlock hoặc lỗi kết nối, hãy định nghĩa một policy riêng vì nguyên nhân, khả năng phục hồi và điều kiện an toàn khác nhau.

### 6.2. Giới hạn số lần thử

Không retry vô hạn. Ví dụ:

- Tổng cộng tối đa 3 lần, tính cả lần đầu.
- Nếu cả 3 lần đều xung đột, trả lỗi cho caller.
- Ghi nhận số lần retry và số lần thất bại cuối cùng.

Giới hạn giúp request không giữ thread và tài nguyên vô thời hạn khi một aggregate đang có contention cao.

### 6.3. Backoff và jitter

Nếu nhiều request cùng xung đột rồi retry ngay lập tức, chúng có thể tiếp tục đụng nhau. Đây là hiện tượng retry storm hoặc thundering herd.

Dùng khoảng chờ tăng dần:

| Lần thử tiếp theo | Ví dụ khoảng chờ cơ sở |
| --- | ---: |
| Sau lần 1 | 50 ms |
| Sau lần 2 | 100 ms |
| Sau lần 3 | Dừng nếu đã hết số lần cho phép |

**Jitter** thêm một khoảng ngẫu nhiên nhỏ để các request không đồng loạt thử lại cùng lúc.

Ví dụ exponential backoff:

\[
delay_n = \min(initialDelay \times multiplier^{n-1}, maxDelay)
\]

Jitter có thể cộng hoặc nhân ngẫu nhiên theo chính sách của ứng dụng. Giá trị cụ thể cần được điều chỉnh theo latency, throughput và mức contention.

### 6.4. Mỗi lần thử phải tải lại dữ liệu

Không dùng lại aggregate cũ:

~~~java
// Sai về ý nghĩa retry:
InventoryItem stale = repository.findBySku(sku).orElseThrow();

for (int attempt = 0; attempt < 3; attempt++) {
    try {
        return repository.save(stale.reserve(quantity));
    } catch (OptimisticLockingFailureException ex) {
        // stale vẫn là object cũ
    }
}
~~~

Đọc lại trong mỗi attempt:

~~~java
for (int attempt = 0; attempt < maxAttempts; attempt++) {
    try {
        return transactionTemplate.execute(status -> {
            InventoryItem current =
                    repository.findBySku(sku).orElseThrow();

            InventoryItem changed = current.reserve(quantity);

            return repository.save(changed);
        });
    } catch (OptimisticLockingFailureException ex) {
        // Attempt sau sẽ đọc lại aggregate trong transaction mới.
    }
}
~~~

Đoạn code trên chỉ an toàn khi mỗi lần `execute` thật sự bắt đầu và kết thúc một transaction riêng; phần tiếp theo trình bày cấu hình đầy đủ.

### 6.5. Revalidate business rules

Sau khi đọc aggregate mới, phải chạy lại quy tắc domain.

Ví dụ:

- Tồn kho có thể đã giảm.
- Đơn hàng có thể đã được xác nhận hoặc hủy.
- Tài khoản có thể đã bị khóa.
- Hạn mức tín dụng có thể đã thay đổi.
- Người dùng có thể đã mất quyền thực hiện hành động.

Nếu trạng thái mới không còn cho phép command, hãy trả lỗi nghiệp vụ. Không bỏ qua kiểm tra chỉ để retry thành công.

## 7. Retry bằng TransactionTemplate

Một cách rõ ràng để retry toàn bộ thao tác là dùng `TransactionTemplate` trong một facade không có transaction bên ngoài.

Mỗi lần gọi `execute(...)` mở một transaction, thực thi callback và kết thúc transaction trước khi trả về hoặc ném exception. Retry coordinator bắt exception ở bên ngoài callback; lần thử tiếp theo sẽ đọc dữ liệu trong transaction mới.

### 7.1. Cấu hình TransactionTemplate

Spring Boot thường cung cấp transaction manager JDBC. Có thể inject transaction manager tương ứng và tạo template:

~~~java
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.transaction.PlatformTransactionManager;
import org.springframework.transaction.support.TransactionTemplate;

@Configuration
public class TransactionConfiguration {

    @Bean
    TransactionTemplate transactionTemplate(
            PlatformTransactionManager transactionManager
    ) {
        return new TransactionTemplate(transactionManager);
    }
}
~~~

Nếu ứng dụng có nhiều transaction manager, hãy inject đúng bean quản lý DataSource mà repository đang sử dụng, có thể dùng `@Qualifier`.

### 7.2. Retry coordinator

~~~java
import java.util.concurrent.ThreadLocalRandom;

import org.springframework.dao.OptimisticLockingFailureException;
import org.springframework.stereotype.Service;
import org.springframework.transaction.support.TransactionTemplate;

@Service
public class RetryingInventoryService {

    private static final int MAX_ATTEMPTS = 3;

    private final InventoryRepository repository;
    private final TransactionTemplate transactionTemplate;

    public RetryingInventoryService(
            InventoryRepository repository,
            TransactionTemplate transactionTemplate
    ) {
        this.repository = repository;
        this.transactionTemplate = transactionTemplate;
    }

    // Method này không có @Transactional bên ngoài.
    public InventoryItem reserve(
            String sku,
            int quantity
    ) {
        for (int attempt = 1; attempt <= MAX_ATTEMPTS; attempt++) {
            try {
                return transactionTemplate.execute(status -> {
                    InventoryItem current =
                            repository.findBySku(sku)
                                    .orElseThrow();

                    InventoryItem changed =
                            current.reserve(quantity);

                    return repository.save(changed);
                });
            } catch (OptimisticLockingFailureException ex) {
                if (attempt == MAX_ATTEMPTS) {
                    throw ex;
                }

                pauseBeforeRetry(attempt);
            }
        }

        throw new IllegalStateException("Unreachable retry state");
    }

    private void pauseBeforeRetry(int attempt) {
        long baseDelay = Math.min(
                50L * (1L << (attempt - 1)),
                500L
        );

        long jitter = ThreadLocalRandom.current()
                .nextLong(0, 50);

        try {
            Thread.sleep(baseDelay + jitter);
        } catch (InterruptedException ex) {
            Thread.currentThread().interrupt();
            throw new IllegalStateException(
                    "Interrupted while waiting to retry",
                    ex
            );
        }
    }
}
~~~

Điểm quan trọng của ví dụ:

1. Method `reserve` điều phối retry nhưng không có `@Transactional` bên ngoài.
2. Mỗi attempt gọi `transactionTemplate.execute(...)`.
3. Aggregate được tải lại trong callback của từng attempt.
4. Command được áp dụng trên trạng thái mới.
5. Nếu save thất bại vì optimistic lock, callback kết thúc bằng exception và transaction đó rollback.
6. Exception được bắt bên ngoài `execute`, sau khi transaction attempt đã kết thúc.
7. Attempt tiếp theo mở transaction mới.
8. Khi hết số lần thử, exception được ném lên caller.

`TransactionTemplate` mặc định dùng propagation `REQUIRED`. Vì facade không có transaction hiện tại, mỗi lần `execute` sẽ tạo transaction mới. Nếu gọi facade này từ một transaction bên ngoài, template có thể tham gia transaction đó; khi ấy các attempt không còn độc lập như mong muốn. Hãy giữ retry coordinator ở ranh giới không có transaction bên ngoài hoặc thiết kế propagation/bean boundary một cách tường minh.

### 7.3. Không retry mọi RuntimeException

Trong ví dụ, chỉ `OptimisticLockingFailureException` được bắt. Các lỗi sau được truyền ra ngay:

- `InsufficientStockException`.
- `IllegalArgumentException`.
- `DataIntegrityViolationException`.
- Lỗi mapping hoặc lỗi lập trình.

Đây là chủ ý. Khi dữ liệu mới cho thấy không đủ tồn kho, thử lại lần thứ tư cũng không làm hàng hóa tự tăng lên.

### 7.4. Backoff không được giữ transaction mở

Trong ví dụ, thời gian chờ diễn ra sau khi `TransactionTemplate.execute` đã thất bại và transaction attempt đã kết thúc. Không giữ connection hoặc row lock trong lúc ngủ để chờ retry.

Với hệ thống có lưu lượng cao, cân nhắc retry framework có backoff hoặc cơ chế điều phối phù hợp thay vì giữ HTTP thread bằng `Thread.sleep`.

## 8. Retry bằng Spring Retry

Nếu dự án đã sử dụng Spring Retry, có thể đặt retry ở một bean facade và đặt transaction ở một bean khác. Cách tách bean giúp mỗi lần retry gọi lại method transactional qua Spring proxy.

Ví dụ facade:

~~~java
import org.springframework.dao.OptimisticLockingFailureException;
import org.springframework.retry.annotation.Backoff;
import org.springframework.retry.annotation.Retryable;
import org.springframework.stereotype.Service;

@Service
public class PlaceOrderRetryFacade {

    private final TransactionalOrderService transactionalService;

    public PlaceOrderRetryFacade(
            TransactionalOrderService transactionalService
    ) {
        this.transactionalService = transactionalService;
    }

    @Retryable(
            retryFor = OptimisticLockingFailureException.class,
            maxAttempts = 3,
            backoff = @Backoff(
                    delay = 50,
                    multiplier = 2,
                    maxDelay = 500
            )
    )
    public PurchaseOrder placeOrder(PlaceOrderCommand command) {
        return transactionalService.placeOrderOnce(command);
    }
}
~~~

Bean thực hiện đúng một attempt trong một transaction:

~~~java
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class TransactionalOrderService {

    private final InventoryRepository inventoryRepository;
    private final PurchaseOrderRepository orderRepository;

    public TransactionalOrderService(
            InventoryRepository inventoryRepository,
            PurchaseOrderRepository orderRepository
    ) {
        this.inventoryRepository = inventoryRepository;
        this.orderRepository = orderRepository;
    }

    @Transactional
    public PurchaseOrder placeOrderOnce(PlaceOrderCommand command) {
        InventoryItem current = inventoryRepository
                .findBySku(command.sku())
                .orElseThrow();

        InventoryItem changed = current.reserve(command.quantity());
        inventoryRepository.save(changed);

        return orderRepository.save(
                new PurchaseOrder(
                        null,
                        command.sku(),
                        command.quantity(),
                        "PLACED"
                )
        );
    }
}
~~~

Cấu hình Spring Retry annotation support trong ứng dụng:

~~~java
@Configuration
@EnableRetry
public class RetryConfiguration {
}
~~~

Spring Retry là thư viện riêng; cần thêm dependency phù hợp với phiên bản dự án. `@Retryable` không phải annotation do Spring Data JDBC tự cung cấp.

Cách tổ chức này có ý nghĩa:

- Retry proxy bao quanh facade.
- Mỗi attempt gọi bean `TransactionalOrderService` qua transaction proxy.
- Transactional method bắt đầu một transaction mới khi không có transaction bên ngoài.
- Nếu method ném optimistic locking exception, transaction được rollback trước khi exception quay về retry interceptor.
- Retry interceptor gọi lại method transactional cho attempt tiếp theo.

Không nên đặt retry và transaction trên cùng một method mà không hiểu thứ tự các interceptor/proxy. Nếu transaction proxy bao ngoài retry interceptor, nhiều attempt có thể chạy trong cùng transaction. Tách facade retry và transactional service giúp ranh giới rõ ràng hơn.

## 9. Retry toàn bộ use case có nhiều repository

Một use case có thể ghi qua nhiều repository trong cùng transaction:

~~~java
@Transactional
public PurchaseOrder placeOrderOnce(PlaceOrderCommand command) {
    InventoryItem inventory = inventoryRepository
            .findBySku(command.sku())
            .orElseThrow();

    inventoryRepository.save(
            inventory.reserve(command.quantity())
    );

    PurchaseOrder order = createOrder(command);

    return orderRepository.save(order);
}
~~~

Nếu thao tác save tồn kho hoặc save đơn hàng gặp optimistic lock exception, toàn bộ transaction cần rollback. Không được chỉ retry repository call thất bại rồi tiếp tục dùng các thay đổi đã thực hiện trước đó trong transaction cũ.

Retry coordinator cần gọi lại **toàn bộ use case**:

~~~text
Attempt 1 — Transaction 1
  Load inventory
  Reserve quantity
  Save inventory
  Save order -> optimistic conflict
  Rollback cả inventory và order

Attempt 2 — Transaction 2
  Load inventory mới
  Load các aggregate liên quan cần thiết
  Revalidate command
  Reserve quantity
  Save inventory
  Save order
  Commit nếu mọi thao tác thành công
~~~

Nếu transaction đầu đã giảm tồn kho nhưng sau đó lưu đơn hàng thất bại vì version của một aggregate khác, rollback phải hoàn tác cả thay đổi tồn kho. Attempt mới phải tải lại mọi aggregate mà use case dựa vào.

## 10. Khi nào nên retry và khi nào nên trả xung đột?

Không phải mọi optimistic locking exception đều nên được xử lý bằng retry tự động.

| Tình huống | Chính sách phù hợp |
| --- | --- |
| Tác vụ nội bộ cập nhật bộ đếm hoặc tồn kho, có thể đọc lại và kiểm tra lại invariant | Có thể retry giới hạn |
| Hai request cập nhật một trường độc lập nhưng aggregate root có version chung | Có thể retry nếu command có thể áp dụng lại mà không làm mất ý định khác |
| Người dùng sửa một biểu mẫu dựa trên dữ liệu cũ | Thường trả conflict để người dùng xem và giải quyết |
| Command dựa trên giá trị tuyệt đối do client gửi, ví dụ “đặt balance thành 100” | Không tự động áp dụng lại nếu có nguy cơ ghi đè thay đổi mới |
| Aggregate đã bị xóa | Thường trả not found hoặc conflict theo hợp đồng API |
| Sau khi đọc lại, business rule không còn hợp lệ | Trả lỗi nghiệp vụ, không retry tiếp |
| Xung đột liên tục sau số lần thử tối đa | Trả conflict hoặc lỗi có thể retry ở tầng caller |

### 10.1. Retry command, không replay snapshot cũ

Command thể hiện ý định nghiệp vụ:

~~~java
public record ReserveStockCommand(
        String sku,
        int quantity
) {
}
~~~

Mỗi lần retry, service đọc trạng thái mới rồi áp dụng command `reserve(quantity)`.

Không gửi lại object aggregate cũ hoặc một snapshot được client dựng từ lần đọc trước. Snapshot cũ là nguyên nhân của xung đột.

### 10.2. Reapply command có thể dẫn đến kết quả khác

Ví dụ người dùng muốn giữ 4 sản phẩm. Lần đầu đọc tồn kho 10, nhưng một request khác đã giữ 8. Sau khi retry và tải lại, tồn kho còn 2.

Khi áp dụng lại command, domain phải báo không đủ hàng. Không được bỏ qua validation để cố làm retry thành công.

Tương tự, nếu người dùng muốn đổi trạng thái đơn hàng từ `DRAFT` sang `CONFIRMED`, nhưng một request khác đã chuyển sang `CANCELLED`, retry phải kiểm tra lại state transition. Không được ghi đè trạng thái mới bằng trạng thái cũ.

## 11. Idempotency và side effects bên ngoài

Retry database operation có thể chạy thân service nhiều lần. Vì vậy, cần phân biệt thao tác database có thể lặp lại với side effect bên ngoài.

Ví dụ không an toàn:

~~~java
public PurchaseOrder placeOrder(PlaceOrderCommand command) {
    paymentClient.charge(command.paymentToken());

    return transactionTemplate.execute(status -> {
        // Cập nhật tồn kho và tạo đơn hàng
        return ...;
    });
}
~~~

Nếu transaction database thất bại do optimistic lock và facade retry, payment provider có thể bị gọi charge nhiều lần.

Không nên thực hiện side effect không thể rollback bên ngoài transaction rồi kỳ vọng retry database tự hoàn tác chúng.

Các lựa chọn thường dùng:

- Ghi một outbox event trong cùng transaction với thay đổi database, rồi worker gửi event sau commit.
- Dùng idempotency key khi gọi payment provider hoặc API bên ngoài.
- Phát event sau khi transaction commit bằng cơ chế phù hợp.
- Thiết kế consumer xử lý event lặp an toàn.
- Giữ phần retry transaction chỉ chứa thao tác database có thể rollback.

Idempotency cũng quan trọng ở API. Nếu client không nhận được response vì timeout rồi gửi lại request, server cần nhận diện cùng một yêu cầu nghiệp vụ để tránh tạo hai đơn hàng. Optimistic locking không tự cung cấp idempotency cho request.

## 12. Trả lỗi xung đột cho API

Nếu hết số lần thử, không nên che giấu lỗi bằng cách trả thành công giả. Có thể chuyển lỗi thành HTTP `409 Conflict` khi hợp đồng API biểu diễn xung đột trạng thái.

Ví dụ:

~~~java
@RestControllerAdvice
public class ApiExceptionHandler {

    @ExceptionHandler(OptimisticLockingFailureException.class)
    public ResponseEntity<ApiError> handleOptimisticLock(
            OptimisticLockingFailureException exception
    ) {
        ApiError body = new ApiError(
                "RESOURCE_MODIFIED",
                "Dữ liệu đã được thay đổi bởi một yêu cầu khác. "
                        + "Hãy tải lại và thử lại."
        );

        return ResponseEntity.status(HttpStatus.CONFLICT)
                .body(body);
    }
}
~~~

DTO lỗi:

~~~java
public record ApiError(
        String code,
        String message
) {
}
~~~

Thông báo cho caller nên giải thích rằng dữ liệu đã thay đổi và caller cần tải lại. Không nhất thiết trả chi tiết version hoặc thông tin nội bộ database ra API.

Nếu service đã retry tự động một số lần rồi vẫn thất bại, response vẫn nên phản ánh xung đột cuối cùng. Có thể ghi log/metric để đội vận hành biết aggregate nào đang có contention cao.

## 13. Theo dõi và giới hạn retry

Một retry policy cần có khả năng quan sát:

- Tổng số optimistic locking conflicts.
- Số attempt trung bình cho mỗi use case.
- Tỷ lệ request thành công sau retry.
- Tỷ lệ hết số lần thử.
- Aggregate hoặc loại nghiệp vụ thường xuyên xung đột.
- Thời gian chờ do backoff.
- Tỷ lệ lỗi nghiệp vụ sau khi đọc lại trạng thái mới.

Không log toàn bộ dữ liệu nhạy cảm của aggregate. Có thể log loại aggregate, ID nội bộ đã được phép ghi log, attempt number và correlation/request ID.

Nếu một aggregate liên tục có contention cao, retry không phải cách duy nhất để cải thiện. Cần xem xét:

- Có thể chia nhỏ aggregate hoặc giảm số use case cùng cập nhật một root không?
- Có thể gom các cập nhật thành một command duy nhất không?
- Có cần pessimistic locking cho đoạn critical section cụ thể không?
- Có thể dùng atomic SQL update với điều kiện để tránh read-modify-write không?
- Có cần đưa một bộ đếm nóng sang mô hình lưu trữ khác không?

Retry là cơ chế phục hồi khi xung đột hiếm xảy ra, không phải giải pháp cho contention liên tục.

## 14. Kiểm thử optimistic locking

Một integration test có thể tạo hai bản sao aggregate cùng version:

1. Lưu một `InventoryItem`.
2. Đọc cùng aggregate hai lần thành `firstRead` và `secondRead`.
3. Cập nhật và save `firstRead`.
4. Thử save `secondRead` dựa trên version cũ.
5. Xác nhận optimistic locking exception được ném.

Ví dụ khung test:

~~~java
@SpringBootTest
class InventoryOptimisticLockingTest {

    @Autowired
    InventoryRepository repository;

    @Test
    void rejectsSaveUsingStaleVersion() {
        InventoryItem created = repository.save(
                new InventoryItem(
                        null,
                        "SKU-01",
                        10,
                        null
                )
        );

        InventoryItem firstRead =
                repository.findById(created.id()).orElseThrow();

        InventoryItem secondRead =
                repository.findById(created.id()).orElseThrow();

        InventoryItem firstChange =
                firstRead.reserve(2);

        repository.save(firstChange);

        InventoryItem staleChange =
                secondRead.reserve(3);

        assertThrows(
                OptimisticLockingFailureException.class,
                () -> repository.save(staleChange)
        );
    }
}
~~~

Test cần chạy với database và transaction configuration phù hợp. Nếu test method tự mở transaction bao quanh toàn bộ test, hãy chú ý cách transaction của test ảnh hưởng đến việc quan sát cập nhật giữa hai lần đọc.

### 14.1. Kiểm thử retry đọc lại dữ liệu

Một test cho retry nên xác nhận:

- Attempt đầu gặp optimistic locking exception.
- Transaction đầu rollback.
- Attempt tiếp theo đọc version mới.
- Command được áp dụng lại trên dữ liệu mới.
- Nếu business rule không còn hợp lệ, lỗi nghiệp vụ được trả ra.
- Không có side effect bên ngoài bị thực hiện hai lần.

Không chỉ mock repository để ném exception một lần rồi trả thành công; integration test nên kiểm tra ranh giới transaction và trạng thái database cuối cùng.

## 15. Những lỗi thường gặp

**“OptimisticLockingFailureException có nghĩa database bị hỏng.”** Không. Đây là tín hiệu phát hiện một thao tác dựa trên version cũ không còn hợp lệ.

**“Chỉ cần thêm @Version là Spring tự retry.”** Không. `@Version` phát hiện xung đột; chính sách retry do ứng dụng thiết kế.

**“Có thể bắt exception rồi gọi save lại ngay.”** Không an toàn. Transaction có thể đã rollback-only và object vẫn giữ version cũ.

**“Retry cùng object aggregate là đủ.”** Không. Mỗi attempt phải tải lại trạng thái mới nhất và áp dụng lại command.

**“Chỉ retry repository method bị lỗi.”** Có thể làm sai atomicity khi use case đã ghi qua nhiều repository. Retry toàn bộ use case trong transaction mới.

**“Retry càng nhiều thì càng dễ thành công.”** Không. Retry vô hạn làm tăng tải và giữ request lâu. Dùng giới hạn attempt và backoff.

**“Có thể retry mọi DataAccessException.”** Không. Constraint, validation và lỗi tham chiếu thường không được giải quyết bằng retry.

**“Sau khi tải lại, cứ áp dụng command mà không kiểm tra lại.”** Không. Phải chạy lại business rules trên trạng thái mới.

**“TransactionTemplate tự bảo đảm mỗi attempt là transaction mới dù có transaction bên ngoài.”** Không. Với propagation mặc định `REQUIRED`, template tham gia transaction hiện có. Retry coordinator cần nằm ngoài transaction bên ngoài hoặc được cấu hình bean boundary phù hợp.

**“@Retryable và @Transactional đặt cùng method luôn có thứ tự đúng.”** Không nên giả định. Advisor/proxy order ảnh hưởng việc mỗi attempt có transaction mới hay không. Tách retry facade và transactional service giúp thể hiện thứ tự rõ ràng hơn.

**“Có thể gọi payment API trong transaction rồi retry toàn bộ.”** Không an toàn. Database rollback không hoàn tác side effect của hệ thống ngoài. Dùng idempotency và outbox hoặc quy trình bù trừ.

**“Mọi optimistic conflict đều nên tự động giải quyết.”** Không. Với cập nhật do người dùng thực hiện trên dữ liệu đã cũ, trả `409 Conflict` để caller xem và quyết định có thể đúng hơn.

## 16. Quy trình xử lý OptimisticLockingFailureException

Khi một thao tác ghi thất bại vì optimistic locking, hãy thực hiện:

1. **Nhận diện đúng exception:** bắt `OptimisticLockingFailureException` hoặc kiểu con phù hợp.
2. **Để transaction thất bại kết thúc:** không tiếp tục save trong transaction đã rollback-only.
3. **Kiểm tra command có thể retry không:** command có thể được áp dụng lại trên trạng thái mới mà không làm mất ý định khác không?
4. **Giới hạn số lần thử:** ví dụ tối đa 3 attempt, tính cả lần đầu.
5. **Backoff có jitter:** tránh nhiều request cùng retry tại một thời điểm.
6. **Mở transaction mới:** mỗi attempt phải có transaction độc lập.
7. **Tải lại aggregate:** không dùng lại object/version cũ.
8. **Áp dụng lại command:** chạy lại validation và invariant.
9. **Retry toàn bộ use case:** nếu nhiều repository cùng tham gia một transaction, rollback và thực hiện lại tất cả các bước cần thiết.
10. **Dừng khi hết attempt:** trả conflict hoặc ném exception để caller xử lý.
11. **Bảo vệ side effect:** dùng outbox/idempotency cho lời gọi bên ngoài.
12. **Theo dõi contention:** nếu retry thường xuyên, xem lại mô hình aggregate và workload.

~~~mermaid
flowchart TD
    A["Bắt đầu use case"] --> B["Mở transaction"]
    B --> C["Tải aggregate mới nhất"]
    C --> D["Áp dụng command và kiểm tra invariant"]
    D --> E["Lưu qua repository"]
    E --> F{"Có optimistic conflict?"}
    F -->|Không| G["Commit transaction"]
    F -->|Có| H["Rollback transaction"]
    H --> I{"Còn attempt và command retry an toàn?"}
    I -->|Không| J["Trả conflict cho caller"]
    I -->|Có| K["Backoff + jitter"]
    K --> B
    G --> L["Trả kết quả"]
~~~

## 17. Bài tập thực hành

Tạo aggregate `InventoryItem` có `id`, `sku`, `availableQuantity` và `@Version Long version`.

### Bài 1: Quan sát version

1. Tạo một inventory item.
2. Đọc lại item và quan sát version.
3. Cập nhật số lượng rồi save.
4. Đọc lại và xác nhận version tăng.
5. Xác nhận domain method không tự tăng version.

### Bài 2: Tạo xung đột stale update

1. Đọc cùng một item vào hai biến Java.
2. Cập nhật và save biến thứ nhất.
3. Dùng biến thứ hai đã cũ để save.
4. Xác nhận `OptimisticLockingFailureException`.
5. Kiểm tra database giữ thay đổi của lần save đầu.

### Bài 3: Thử lại trong transaction mới

1. Dùng `TransactionTemplate` trong một retry coordinator không có transaction bên ngoài.
2. Mỗi attempt tải lại aggregate.
3. Áp dụng command reserve.
4. Tạo xung đột ở attempt đầu.
5. Xác nhận attempt sau đọc version mới.
6. Xác nhận retry dừng khi business rule không còn hợp lệ.

### Bài 4: Retry toàn bộ nhiều repository

1. Tạo use case cập nhật tồn kho và tạo đơn hàng trong cùng transaction.
2. Tạo xung đột version ở một aggregate.
3. Xác nhận toàn bộ transaction đầu rollback.
4. Thử lại toàn bộ use case trong transaction mới.
5. Kiểm tra không có thay đổi một phần còn sót lại.

### Bài 5: Giới hạn retry

1. Đặt tối đa 3 attempt.
2. Mô phỏng xung đột liên tục.
3. Xác nhận lần thử cuối ném exception.
4. Thêm backoff và jitter.
5. Ghi nhận metric số attempt và số lần hết retry.

### Bài 6: Phân biệt conflict và lỗi nghiệp vụ

1. Tạo xung đột optimistic lock.
2. Sau khi đọc lại, làm cho số tồn kho không đủ.
3. Xác nhận service trả `InsufficientStockException`, không retry tiếp.
4. Thử với command cập nhật trạng thái đã bị một request khác chuyển sang trạng thái không cho phép.
5. Xác nhận domain rule được kiểm tra lại.

## 18. Ghi nhớ

- `@Version` cho phép Spring Data JDBC phát hiện cập nhật/xóa dựa trên trạng thái aggregate đã cũ.
- Khi version trong database không khớp version đã đọc, thao tác có thể thất bại với `OptimisticLockingFailureException`.
- Optimistic locking phát hiện xung đột; nó không tự retry.
- Không retry bên trong transaction đã thất bại hoặc dùng lại aggregate cũ.
- Retry cần bao quanh transaction để mỗi attempt chạy trong transaction mới.
- Mỗi attempt phải tải lại aggregate, áp dụng lại command và kiểm tra lại invariant nghiệp vụ.
- Nếu use case ghi qua nhiều repository trong cùng transaction, hãy rollback và retry toàn bộ use case.
- Chỉ retry exception phù hợp, giới hạn số lần thử và dùng backoff/jitter.
- Không retry validation, business rule hoặc constraint violation một cách mù quáng.
- `TransactionTemplate` với propagation `REQUIRED` chỉ tạo transaction mới khi không có transaction hiện tại; hãy thiết kế retry boundary rõ ràng.
- Có thể dùng Spring Retry ở facade riêng và gọi transactional service qua bean proxy để mỗi attempt có transaction riêng.
- Không lặp side effect ngoài database; dùng idempotency key, transactional outbox hoặc quy trình bù trừ.
- Với xung đột do người dùng sửa dữ liệu cũ, trả HTTP `409 Conflict` có thể phù hợp hơn tự động merge.
- Nếu conflict xảy ra thường xuyên, cần xem lại contention, aggregate boundary, query/update strategy và locking.

**Optimistic locking giúp phát hiện khi trạng thái ứng dụng dựa vào đã cũ. Retry chỉ an toàn khi bắt đầu từ transaction mới, tải lại dữ liệu và đánh giá lại ý định nghiệp vụ.** Chính sách đúng không cố ép mọi thao tác thành công; nó bảo đảm thay đổi mới không bị ghi đè và caller nhận được kết quả trung thực khi xung đột không thể tự giải quyết.
