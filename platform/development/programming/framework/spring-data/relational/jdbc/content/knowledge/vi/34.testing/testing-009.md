# Kiểm thử truy vấn suy diễn, @Query, projection và phân trang

Trong **Spring Data Relational JDBC**, một repository có thể cung cấp dữ liệu qua nhiều cơ chế: truy vấn suy diễn từ tên method, SQL khai báo bằng @Query, projection/read model ánh xạ bằng RowMapper, và phân trang bằng Pageable, Page hoặc Slice.

Mỗi cơ chế có một hợp đồng khác nhau. Truy vấn suy diễn được giới hạn ở property của aggregate root và không tự JOIN. String-based @Query cho phép viết SQL tường minh nhưng không tự áp dụng Pageable/Sort/Limit như derived query. Projection DTO cần mapping đúng ResultSet và thường phù hợp cho read-only view. Page cung cấp tổng số kết quả nên có thể phát sinh count query; Slice chỉ xác định còn trang tiếp theo hay không.

Kiểm thử cần xác nhận cả kết quả dữ liệu và cách query được sử dụng: điều kiện lọc, sort, count, giới hạn trang, SQL alias, mapping DTO và các trường hợp rỗng/không duy nhất. Bài này sử dụng ví dụ đơn hàng để minh họa từng cơ chế trong một Spring Data JDBC test context.

## 1. Mô hình dữ liệu dùng trong ví dụ

Aggregate root:

~~~java
@Table("purchase_order")
public class PurchaseOrder {

    @Id
    private Long id;

    @Column("customer_id")
    private Long customerId;

    private String status;

    @Column("created_at")
    private LocalDateTime createdAt;

    protected PurchaseOrder() {}

    public PurchaseOrder(Long customerId, String status, LocalDateTime createdAt) {
        this.customerId = customerId;
        this.status = status;
        this.createdAt = createdAt;
    }

    public Long getId() { return id; }
    public Long getCustomerId() { return customerId; }
    public String getStatus() { return status; }
    public LocalDateTime getCreatedAt() { return createdAt; }
}
~~~

Bảng ví dụ:

~~~sql
CREATE TABLE purchase_order (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    status VARCHAR(30) NOT NULL,
    created_at TIMESTAMP NOT NULL
);
~~~

DTO cho trang danh sách:

~~~java
public record OrderSummary(
        Long orderId,
        String status,
        String customerName,
        Long lineCount
) {}
~~~

Repository sẽ có cả derived query, annotated query và query trả projection. Trong ví dụ này, OrderSummary là read model, không phải aggregate root để lưu.

## 2. Kiểm thử truy vấn suy diễn từ tên method

Spring Data JDBC phân tích tên method để tạo SQL. Các keyword thông dụng gồm And, Or, Is, Between, LessThan, GreaterThan, Before, After, IsNull, Like, StartingWith, EndingWith, Containing, In, NotIn, True, False, IgnoreCase và OrderBy.

Ví dụ repository:

~~~java
public interface PurchaseOrderRepository
        extends CrudRepository<PurchaseOrder, Long>,
                PagingAndSortingRepository<PurchaseOrder, Long> {

    List<PurchaseOrder> findByStatus(String status);

    List<PurchaseOrder> findByCustomerIdAndStatus(
            Long customerId,
            String status
    );

    List<PurchaseOrder> findByCreatedAtAfter(LocalDateTime createdAt);

    List<PurchaseOrder> findTop5ByStatusOrderByCreatedAtDesc(String status);

    Page<PurchaseOrder> findByStatus(String status, Pageable pageable);

    Slice<PurchaseOrder> findByCustomerId(Long customerId, Pageable pageable);
}
~~~

Truy vấn suy diễn chỉ hỗ trợ property có thể dùng trong WHERE mà không cần JOIN; tài liệu Spring Data JDBC giới hạn việc derive ở các property trực tiếp của aggregate root. Derived query hiện hỗ trợ SELECT, không dùng để tự suy diễn lệnh INSERT/UPDATE/DELETE.

### Test điều kiện đơn giản

~~~java
@DataJdbcTest
class PurchaseOrderDerivedQueryTest {

    @Autowired PurchaseOrderRepository repository;
    @Autowired JdbcTemplate jdbcTemplate;

    @BeforeEach
    void setUp() {
        jdbcTemplate.update("""
                INSERT INTO purchase_order(customer_id, status, created_at)
                VALUES (?, ?, ?)
                """, 10L, "PAID", Timestamp.valueOf("2026-01-10 09:00:00"));

        jdbcTemplate.update("""
                INSERT INTO purchase_order(customer_id, status, created_at)
                VALUES (?, ?, ?)
                """, 10L, "OPEN", Timestamp.valueOf("2026-01-11 09:00:00"));

        jdbcTemplate.update("""
                INSERT INTO purchase_order(customer_id, status, created_at)
                VALUES (?, ?, ?)
                """, 20L, "PAID", Timestamp.valueOf("2026-01-12 09:00:00"));
    }

    @Test
    void filtersByStatus() {
        List<PurchaseOrder> result = repository.findByStatus("PAID");

        assertThat(result).hasSize(2);
        assertThat(result).allSatisfy(order ->
                assertThat(order.getStatus()).isEqualTo("PAID"));
    }

    @Test
    void combinesRootPropertiesWithAnd() {
        List<PurchaseOrder> result =
                repository.findByCustomerIdAndStatus(10L, "OPEN");

        assertThat(result).hasSize(1);
        assertThat(result.getFirst().getCustomerId()).isEqualTo(10L);
    }

    @Test
    void supportsTopAndOrderBy() {
        List<PurchaseOrder> result =
                repository.findTop5ByStatusOrderByCreatedAtDesc("PAID");

        assertThat(result).hasSize(2);
        assertThat(result.getFirst().getCreatedAt())
                .isAfter(result.getLast().getCreatedAt());
    }
}
~~~

Đây là ví dụ minh họa; schema và entity constructor/accessor phải khớp migration thực tế. Nếu dùng Java 17 thay vì Java 21, thay getFirst() bằng get(0).

### Kiểm thử điều kiện biên

Với mỗi derived query quan trọng, nên kiểm tra:

- Không có hàng khớp điều kiện: trả collection rỗng hoặc Optional.empty theo return type.
- Một hàng khớp: giá trị property đúng.
- Nhiều hàng khớp: toàn bộ kết quả đúng.
- Giá trị null với IsNull/IsNotNull: SQL semantics đúng.
- In với collection rỗng: xác nhận behavior phù hợp phiên bản/database và xử lý đầu vào rỗng ở service nếu cần.
- Kết hợp And/Or: điều kiện được nhóm đúng như tên method.
- OrderBy: thứ tự ổn định, có tie-breaker nếu nhiều hàng có cùng giá trị sort.

Không chỉ kiểm tra số lượng phần tử. Hãy assert ID và property để phát hiện query lọc nhầm hoặc trả sai thứ tự.

## 3. Giới hạn của query derivation

Query derivation của Spring Data JDBC không phải query builder tổng quát. Nó bị giới hạn ở các property có thể lọc mà không cần JOIN.

Ví dụ một method như:

~~~java
List<PurchaseOrder> findByCustomerName(String customerName);
~~~

không tự JOIN bảng customer nếu customer là aggregate root khác được tham chiếu bằng customerId. Với nhu cầu tìm theo tên khách hàng, hãy dùng @Query có JOIN hoặc custom repository fragment với NamedParameterJdbcTemplate.

Derived query cũng chỉ hỗ trợ SELECT. Nếu cần cập nhật/xóa bằng SQL, dùng @Modifying + @Query hoặc API persistence phù hợp.

Test nên xác nhận những truy vấn được derive nằm trong phạm vi hỗ trợ; không cố biến tên method thành biểu thức JOIN nhiều bảng. Khi điều kiện nghiệp vụ vượt phạm vi root properties, chuyển sang query tường minh để SQL dễ đọc và kiểm soát.

## 4. Kiểm thử Page, Slice và List với Pageable

Spring Data JDBC hỗ trợ Pageable cho derived query methods. Có thể trả về:

- **Page<T>**: dữ liệu của trang, số phần tử tổng cộng và tổng số trang. Framework có thể chạy thêm count query.
- **Slice<T>**: dữ liệu của trang và thông tin còn trang kế tiếp hay không. Framework lấy pageSize + 1 hàng để xác định hasNext.
- **List<T>**: chỉ lấy các hàng trong phạm vi Pageable, không tạo metadata Page và không cần count query.

Ví dụ:

~~~java
Page<PurchaseOrder> findByStatus(String status, Pageable pageable);

Slice<PurchaseOrder> findByCustomerId(Long customerId, Pageable pageable);

List<PurchaseOrder> findByStatus(String status, Pageable pageable);
~~~

Các method trên có thể có tên/parameter signature khác nhau để tránh trùng khai báo trong cùng interface. Trong ví dụ repository phần trước đã khai báo Page và Slice; nếu cần List với Pageable, đặt tên query method khác hoặc dùng một repository riêng cho ví dụ.

### Test Page

~~~java
@Test
void returnsPageContentAndTotalCount() {
    PageRequest pageRequest = PageRequest.of(
            0,
            2,
            Sort.by(
                    Sort.Order.desc("createdAt"),
                    Sort.Order.desc("id")
            )
    );

    Page<PurchaseOrder> page =
            repository.findByStatus("PAID", pageRequest);

    assertThat(page.getContent()).hasSize(2);
    assertThat(page.getTotalElements()).isEqualTo(3);
    assertThat(page.getTotalPages()).isEqualTo(2);
    assertThat(page.getNumber()).isZero();
    assertThat(page.hasNext()).isTrue();
}
~~~

Test này cần ba hàng PAID trở lên. Page có thể phát sinh count query để tính totalElements/totalPages. Không giả định count query luôn chạy nếu framework có thể suy ra tổng số từ nội dung trang trong trường hợp đặc biệt; hãy quan sát SQL khi cần kiểm tra query count.

### Test Slice

~~~java
@Test
void returnsSliceAndDetectsNextPage() {
    Pageable request = PageRequest.of(
            0,
            2,
            Sort.by(Sort.Order.asc("id"))
    );

    Slice<PurchaseOrder> slice =
            repository.findByCustomerId(10L, request);

    assertThat(slice.getContent()).hasSize(2);
    assertThat(slice.hasNext()).isTrue();
    assertThat(slice.getNumberOfElements()).isEqualTo(2);
}
~~~

Slice không cung cấp totalElements/totalPages. Nó chỉ cần biết còn dữ liệu tiếp theo. Khi caller chỉ cần nút Next/Previous hoặc infinite scrolling, Slice thường tránh được count query có thể tốn kém.

### Test trang cuối và trang rỗng

~~~java
@Test
void returnsLastSliceWithoutNextPage() {
    Pageable request = PageRequest.of(
            1,
            2,
            Sort.by(Sort.Order.asc("id"))
    );

    Slice<PurchaseOrder> slice =
            repository.findByCustomerId(10L, request);

    assertThat(slice.hasNext()).isFalse();
}

@Test
void returnsEmptyPageWhenOffsetIsBeyondResults() {
    Pageable request = PageRequest.of(20, 10);

    Page<PurchaseOrder> page =
            repository.findByStatus("MISSING", request);

    assertThat(page.getContent()).isEmpty();
    assertThat(page.getTotalElements()).isZero();
}
~~~

### Sort ổn định

Nếu chỉ sort theo createdAt và nhiều đơn có cùng timestamp, database có thể trả các hàng đồng hạng theo thứ tự không xác định. Khi người dùng chuyển trang, hàng có thể lặp hoặc bị bỏ qua giữa các request.

Dùng thêm khóa duy nhất làm tie-breaker:

~~~java
Sort sort = Sort.by(
        Sort.Order.desc("createdAt"),
        Sort.Order.desc("id")
);
~~~

Kiểm thử thứ tự trên dữ liệu có timestamp trùng nhau để xác nhận tie-breaker thực sự được áp dụng.

### Offset pagination ở trang sâu

Offset lớn có thể làm database phải đọc/bỏ qua nhiều hàng trước khi trả trang mong muốn. Nếu bảng lớn và caller đi sâu nhiều trang, đo chi phí của offset. Có thể cân nhắc keyset/seek pagination bằng điều kiện theo giá trị cuối trang, ví dụ created_at và id. Cách này thường cần query tùy chỉnh hoặc repository fragment thay vì chỉ tăng page number.

## 5. Kiểm thử @Query với SQL tường minh

@Query phù hợp khi cần viết SQL mà query derivation không biểu đạt được: JOIN, subquery, CTE, function, database-specific syntax hoặc filter đặc biệt.

Ví dụ query trả aggregate root:

~~~java
public interface PurchaseOrderRepository
        extends CrudRepository<PurchaseOrder, Long> {

    @Query("""
        SELECT *
        FROM purchase_order
        WHERE status = :status
        ORDER BY created_at DESC, id DESC
        """)
    List<PurchaseOrder> findByStatusUsingSql(
            @Param("status") String status
    );
}
~~~

Test:

~~~java
@Test
void executesAnnotatedQueryAndMapsAggregateRoot() {
    List<PurchaseOrder> result =
            repository.findByStatusUsingSql("PAID");

    assertThat(result).hasSize(2);
    assertThat(result)
            .extracting(PurchaseOrder::getStatus)
            .containsOnly("PAID");
}
~~~

Với default RowMapper, query phải trả đủ cột cho constructor của entity. Property được gán qua setter, wither hoặc field access có thể không cần nếu không có cột tương ứng; property thiếu sẽ không được thiết lập. Các one-to-one/embedded property có quy tắc alias prefix riêng. Collection entity như List, Set và Map vẫn được tải bằng query riêng.

### Test tham số named parameter

Spring Data JDBC hỗ trợ named parameters. Kiểm thử giá trị có ký tự đặc biệt để xác nhận input được bind như giá trị:

~~~java
@Query("""
    SELECT *
    FROM purchase_order
    WHERE status = :status
    """)
List<PurchaseOrder> findByStatusSql(@Param("status") String status);
~~~

Không nối input vào chuỗi SQL. Parameter binding bảo vệ giá trị đầu vào; tên bảng/cột và keyword SQL không thể bind như giá trị. Nếu cần sort động, ánh xạ property qua whitelist identifier được phép.

### Kiểm thử @Query trả về rỗng và không duy nhất

- Điều kiện không khớp: List rỗng hoặc Optional.empty theo return type.
- Query trả một entity nhưng dữ liệu có nhiều hàng: xác nhận exception về result size nếu method yêu cầu một kết quả duy nhất.
- Query trả entity: bảo đảm mọi constructor property có mặt trong ResultSet.
- Query có one-to-one: kiểm tra alias prefix.
- Aggregate có collection: kiểm tra các query collection phát sinh và dữ liệu child được dựng đúng.

## 6. Giới hạn phân trang của string-based @Query

Đây là điểm khác biệt quan trọng: tài liệu Spring Data JDBC hiện hành quy định string-based @Query **không tự nhận Pageable, PageRequest, Sort hoặc Limit như tham số đặc biệt** vì framework không viết lại SQL string để áp dụng chúng.

Nếu cần phân trang cho @Query, hãy viết SQL rõ ràng và bind limit/offset:

~~~java
@Query("""
    SELECT *
    FROM purchase_order
    WHERE status = :status
    ORDER BY created_at DESC, id DESC
    LIMIT :limit OFFSET :offset
    """)
List<PurchaseOrder> findPageUsingSql(
        @Param("status") String status,
        @Param("limit") int limit,
        @Param("offset") long offset
);
~~~

Ví dụ LIMIT/OFFSET dùng cú pháp PostgreSQL/MySQL. Điều chỉnh cho dialect khác. Nếu cần Page metadata, viết count query riêng:

~~~java
@Query("""
    SELECT COUNT(*)
    FROM purchase_order
    WHERE status = :status
    """)
long countByStatusUsingSql(@Param("status") String status);
~~~

Service có thể ghép content và count vào PageImpl:

~~~java
public Page<PurchaseOrder> findPage(String status, Pageable pageable) {
    List<PurchaseOrder> content = repository.findPageUsingSql(
            status,
            pageable.getPageSize(),
            pageable.getOffset()
    );

    long total = repository.countByStatusUsingSql(status);

    return new PageImpl<>(content, pageable, total);
}
~~~

Trong ví dụ này service phải tự đảm bảo count query dùng cùng predicate với content query. Nếu filter phức tạp, nên tái sử dụng điều kiện SQL hoặc xây dựng query fragment để tránh hai câu query lệch nhau.

Nếu chỉ cần dữ liệu của trang mà không cần total, trả List hoặc xây dựng Slice theo quy tắc pageSize + 1. Không cần chạy COUNT(*) nếu caller không sử dụng tổng số kết quả.

## 7. Kiểm thử projection bằng RowMapper

Projection DTO cần xác nhận cả SQL alias và mapping Java. Ví dụ DTO:

~~~java
public record OrderSummary(
        Long orderId,
        String status,
        String customerName,
        Long lineCount
) {}
~~~

Repository query:

~~~java
@Query(
    value = """
        SELECT
            po.id AS order_id,
            po.status AS status,
            c.name AS customer_name,
            COUNT(ol.id) AS line_count
        FROM purchase_order po
        JOIN customer c ON c.id = po.customer_id
        LEFT JOIN order_line ol ON ol.order_id = po.id
        WHERE po.status = :status
        GROUP BY po.id, po.status, c.name
        ORDER BY po.id
        """,
    rowMapperRef = "orderSummaryRowMapper"
)
List<OrderSummary> findSummaries(@Param("status") String status);
~~~

Mapper bean:

~~~java
@Configuration
public class OrderSummaryMappingConfiguration {

    @Bean
    RowMapper<OrderSummary> orderSummaryRowMapper() {
        return (rs, rowNum) -> new OrderSummary(
                rs.getLong("order_id"),
                rs.getString("status"),
                rs.getString("customer_name"),
                rs.getLong("line_count")
        );
    }
}
~~~

Trong test slice, import mapping configuration nếu bean không được scan tự động:

~~~java
@DataJdbcTest
@Import(OrderSummaryMappingConfiguration.class)
class OrderSummaryQueryTest {
    // ...
}
~~~

Test mapping:

~~~java
@Test
void mapsJoinedRowsIntoProjection() {
    List<OrderSummary> summaries =
            repository.findSummaries("PAID");

    assertThat(summaries).hasSize(1);

    OrderSummary summary = summaries.getFirst();
    assertThat(summary.orderId()).isEqualTo(100L);
    assertThat(summary.customerName()).isEqualTo("Lan");
    assertThat(summary.lineCount()).isEqualTo(2L);
}
~~~

Dữ liệu fixture cần có customer và hai order_line cho order 100. Kiểm tra thêm order không có child để xác nhận LEFT JOIN và COUNT(child.id) trả 0.

### Khi nào cần ResultSetExtractor?

RowMapper ánh xạ một ResultSet row thành một object. Nếu SQL JOIN một-to-many trả nhiều hàng cho cùng root và bạn muốn gom thành một DTO có collection, ResultSetExtractor phù hợp hơn vì nó xử lý toàn bộ ResultSet.

Ví dụ khái niệm:

~~~java
ResultSetExtractor<List<OrderWithLines>> extractor = rs -> {
    Map<Long, OrderWithLinesBuilder> orders = new LinkedHashMap<>();

    while (rs.next()) {
        Long orderId = rs.getLong("order_id");

        OrderWithLinesBuilder builder = orders.computeIfAbsent(
                orderId,
                id -> new OrderWithLinesBuilder(
                        id,
                        rsValue(rs, "status")
                )
        );

        Long lineId = rs.getObject("line_id", Long.class);
        if (lineId != null) {
            builder.addLine(
                    lineId,
                    rs.getLong("product_id"),
                    rs.getInt("quantity")
            );
        }
    }

    return orders.values().stream()
            .map(OrderWithLinesBuilder::build)
            .toList();
};
~~~

Đây là pseudocode minh họa vì lambda cần xử lý SQLException và builder cụ thể của ứng dụng. Khi dùng ResultSetExtractor, cần kiểm tra null child, duplicate row và thứ tự. Custom RowMapper/ResultSetExtractor trong Spring Data JDBC cũng có nghĩa callback/lifecycle event của entity không tự được gọi cho kết quả mapping tùy chỉnh.

## 8. Kiểm thử query có JOIN và cardinality

Một query JOIN một-to-many cần test nhiều hơn một fixture đơn giản:

- Root không có child.
- Root có đúng một child.
- Root có nhiều child.
- Hai root có child cùng product.
- JOIN thêm bảng khác nhưng không làm tổng bị nhân đôi.
- Filter theo bảng được JOIN.
- Sort và pagination theo root, không phải joined rows.

Ví dụ SQL summary nên dùng LEFT JOIN nếu root không có child vẫn cần xuất hiện:

~~~sql
SELECT
    po.id,
    COUNT(ol.id) AS line_count,
    COALESCE(SUM(ol.quantity * ol.unit_price), 0) AS total_amount
FROM purchase_order po
LEFT JOIN order_line ol ON ol.order_id = po.id
GROUP BY po.id;
~~~

Nếu thêm JOIN bảng payment, không nên tính lại SUM line trên kết quả đã nhân với payment rows. Hãy aggregate line và payment trong các subquery riêng trước khi JOIN kết quả theo order_id.

Test cần assert giá trị tổng, không chỉ số lượng DTO. Sai cardinality có thể tạo kết quả đúng số row nhưng tổng tiền sai.

## 9. Kiểm thử @Query với custom RowMapper và lifecycle

Spring Data JDBC cho phép chọn custom RowMapper hoặc ResultSetExtractor qua @Query. Tuy nhiên, custom mapping được thiết kế để ứng dụng kiểm soát cách tạo kết quả; entity callbacks và lifecycle events không tự chạy cho kết quả được map bằng các custom mapper/extractor này.

Vì vậy:

- Dùng custom mapper cho DTO/read model là lựa chọn tự nhiên.
- Nếu query trả entity và dựa vào callback/auditing/lifecycle behavior, kiểm tra kỹ việc custom mapper có làm thay đổi kỳ vọng hay không.
- Không dùng custom query projection làm đường tải aggregate rồi giả định toàn bộ aggregate lifecycle sẽ được thực thi giống repository find mặc định.
- Test callback/event riêng nếu use case phụ thuộc vào chúng.

## 10. Test slice với @DataJdbcTest

@DataJdbcTest là test slice dành cho Spring Data JDBC. Nó thường cấu hình:

- DataSource và embedded database nếu có trên classpath.
- Spring Data JDBC repositories.
- JdbcTemplate.
- Transaction cho mỗi test và rollback khi test kết thúc.

Các component thông thường không nhất thiết được scan như trong application context đầy đủ. Nếu custom RowMapper/configuration không được nạp, dùng @Import để đưa configuration cần thiết vào test context.

Ví dụ:

~~~java
@DataJdbcTest
@Import(OrderSummaryMappingConfiguration.class)
class PurchaseOrderQueryTest {

    @Autowired PurchaseOrderRepository repository;
~~~

Lưu ý transaction test mặc định:

- Dữ liệu fixture được insert trong transaction của test và rollback khi test kết thúc.
- Repository query trong test nhìn thấy fixture do cùng transaction.
- Nếu cần kiểm tra transaction commit/rollback của application service qua proxy, cần thiết kế test để transaction ngoài của test không che kết quả.
- @DataJdbcTest không tự kiểm tra HTTP/controller behavior; dùng @SpringBootTest hoặc web slice phù hợp cho tầng đó.

## 11. Kiểm thử với database production-compatible

Embedded database hữu ích cho test mapping và query cơ bản, nhưng SQL dialect, paging, type conversion và execution plan có thể khác database production.

Nếu production dùng PostgreSQL, MySQL, SQL Server hoặc Oracle, hãy bổ sung integration test trên cùng engine/driver. Testcontainers có thể khởi chạy database tạm thời và cung cấp JDBC URL cho Spring context.

Ví dụ PostgreSQL với DynamicPropertySource:

~~~java
@Testcontainers
@DataJdbcTest
class PurchaseOrderPostgresQueryTest {

    @Container
    static PostgreSQLContainer<?> postgres =
            new PostgreSQLContainer<>("postgres:16-alpine")
                    .withDatabaseName("sales")
                    .withUsername("app")
                    .withPassword("secret");

    @DynamicPropertySource
    static void databaseProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
        registry.add(
                "spring.datasource.driver-class-name",
                postgres::getDriverClassName
        );
    }
}
~~~

Đảm bảo migration/schema SQL chạy trên container trước test. Cách cấu hình container và annotation Testcontainers có thể thay đổi theo phiên bản Spring Boot/Testcontainers; điều chỉnh dependency và package import theo project.

Với projection/SQL JOIN, test đúng engine giúp phát hiện alias/type differences. Với paging, test sort, limit/offset và count trên đúng dialect. Với Single Query Loading, dùng database/dialect có hỗ trợ và xác nhận SQL thực tế.

## 12. Đo query count và tránh test chỉ kiểm tra kết quả

Một query test có thể trả đúng dữ liệu dù đang phát sinh nhiều SQL không mong muốn. Khi mục tiêu là kiểm soát N+1 hoặc count query, hãy đo statement thực tế.

Có thể dùng datasource-proxy, P6Spy hoặc instrumentation của test để đếm statement. Không gắn assertion cứng vào mọi câu SQL nội bộ nếu framework có thể thay đổi SQL giữa minor version; thay vào đó kiểm tra hành vi cần thiết như:

- Derived query Page phát sinh data query và count query khi cần.
- Slice lấy pageSize + 1 để biết hasNext.
- List + Pageable chỉ trả content trong page range và không cần metadata count.
- @Query string không tự áp dụng Pageable; SQL phải chứa limit/offset nếu cần.
- Custom projection chỉ lấy các cột read model cần.
- Query aggregate không tạo thêm statement ngoài dự kiến cho collection.

Nếu test exact statement count, cô lập fixture và không để migration/setup query bị tính vào số đo. Reset query counter ngay trước method đang kiểm thử.

## 13. Streaming query và đóng tài nguyên

Spring Data JDBC cho phép query method trả Stream để tiêu thụ kết quả dần dần. Stream giữ connection mở; caller phải đóng stream để tránh rò rỉ connection.

~~~java
@Query("SELECT * FROM purchase_order WHERE status = :status")
Stream<PurchaseOrder> streamByStatus(@Param("status") String status);
~~~

Cách dùng:

~~~java
try (Stream<PurchaseOrder> orders =
             repository.streamByStatus("ARCHIVED")) {

    orders.forEach(this::process);
}
~~~

Không trả stream ra ngoài service rồi để caller tùy ý giữ lâu. Connection vẫn mở trong lúc stream được sử dụng. Nếu xử lý từng phần tử có network call hoặc thời gian dài, cân nhắc batch/chunk thay vì giữ một database connection mở suốt workflow.

Test streaming cần xác nhận kết quả được đọc và stream được đóng. Không cố đọc tiếp sau khi đóng stream.

## 14. Những lỗi thường gặp

| Biểu hiện | Nguyên nhân | Cách xử lý |
|---|---|---|
| Derived query không tìm được property | Tên method dùng property không có trên aggregate root | Kiểm tra property name và mapping |
| Derived query cần JOIN nhưng không tạo JOIN | Derivation của JDBC giới hạn property dùng được không cần JOIN | Dùng @Query hoặc fragment |
| Page content đúng nhưng totalElements sai | Count query hoặc fixture/filter không khớp | Kiểm tra predicate và count query |
| Slice không có totalPages | Slice chỉ cung cấp hasNext | Dùng Page khi thực sự cần tổng |
| @Query không nhận Pageable | String-based JDBC query không tự viết lại SQL | Bind limit/offset trong SQL |
| @Query entity mapping lỗi constructor | Thiếu cột constructor property | SELECT đủ cột và alias đúng |
| @Query JOIN trả collection thiếu | Default RowMapper tải collection bằng query riêng | Kiểm tra mapping hoặc dùng DTO/custom extractor |
| Projection DTO lỗi alias | RowMapper đọc tên cột không tồn tại | Đồng bộ SQL alias và mapper |
| Projection custom không phát callback | Custom RowMapper/ResultSetExtractor không tự chạy lifecycle callbacks/events | Không dựa vào callback cho custom read mapping |
| Page bị trùng/mất hàng giữa các lần gọi | Sort không ổn định khi giá trị sort trùng | Thêm ID làm tie-breaker |
| Test pass trên H2 nhưng production fail | Dialect hoặc kiểu SQL khác | Chạy Testcontainers với engine production |
| @DataJdbcTest không thấy custom mapper bean | Test slice không scan configuration thông thường | Dùng @Import |
| Stream làm cạn connection pool | Stream không được đóng | Dùng try-with-resources |
| JOIN làm count/sum sai | Nhiều collection bị nhân chéo | Aggregate từng collection trước khi JOIN |

## 15. Quy trình kiểm thử một repository query mới

1. **Xác định loại query:** derived query, annotated SQL hay custom fragment.
2. **Kiểm tra phạm vi derivation:** property có nằm trực tiếp trên aggregate root và không cần JOIN không?
3. **Xác định return type:** entity, DTO, List, Slice, Page hoặc Stream.
4. **Chuẩn bị fixture có cardinality đa dạng:** 0, 1, nhiều kết quả và các giá trị trùng sort key.
5. **Test điều kiện lọc:** kết quả đúng theo ID/property, kể cả null và collection parameter nếu có.
6. **Test sort:** thứ tự đúng và ổn định.
7. **Test pagination:** content, offset, limit, hasNext, totalElements và count semantics.
8. **Test @Query mapping:** constructor fields, aliases, one-to-one prefix và collection behavior.
9. **Test projection:** RowMapper/ResultSetExtractor tạo DTO đúng; kiểm tra aggregate count/sum và LEFT JOIN.
10. **Test database mục tiêu:** chạy migration và integration test với đúng dialect/driver.
11. **Đo SQL khi cần:** query count, execution plan, result rows và latency.
12. **Đóng tài nguyên:** stream và các resource JDBC được giải phóng đúng cách.

### Bảng quyết định nhanh

| Mục tiêu kiểm thử | Cơ chế |
|---|---|
| Lọc theo property của aggregate root | Derived query |
| Điều kiện có JOIN/CTE/function | @Query hoặc repository fragment |
| Cần toàn bộ aggregate | Return aggregate root và kiểm tra owned entities |
| Chỉ cần vài cột cho read model | DTO + custom RowMapper/ResultSetExtractor |
| Cần tổng số kết quả/trang | Page |
| Chỉ cần biết còn dữ liệu tiếp theo | Slice |
| Chỉ cần content của một trang | List + Pageable trên derived query |
| SQL custom cần giới hạn kết quả | Bind LIMIT/OFFSET trong SQL |
| Dữ liệu lớn, tiêu thụ dần | Stream và try-with-resources |
| Cần xác nhận SQL dialect thật | Integration test bằng database production-compatible |

**Điểm cốt lõi:** derived query phù hợp với điều kiện đơn giản trên aggregate root; @Query dành cho SQL tường minh nhưng string-based query không tự nhận Pageable/Sort/Limit; projection DTO cần RowMapper/ResultSetExtractor đúng alias và kiểu; Page cần tổng số, Slice chỉ cần biết còn dữ liệu tiếp theo. Kiểm thử cả kết quả, count, sort, mapping, giới hạn query và database engine thực tế.
