# Bài tập mở rộng: xóa mềm, nhiều nguồn dữ liệu và nhập dữ liệu theo lô

Trong bài thực hành này, bạn sẽ xây dựng một quy trình đồng bộ danh mục sản phẩm từ database nguồn sang database đích bằng Spring Data Relational JDBC. Hệ thống giữ lại lịch sử bản ghi đã ngừng sử dụng bằng **soft delete**, đọc và ghi qua **hai DataSource**, đồng thời nhập dữ liệu theo **từng batch** để giới hạn bộ nhớ và thời gian giữ connection.

Ba kỹ năng được kết hợp trong cùng một quy trình:

1. Soft delete thay đổi trạng thái nghiệp vụ của aggregate nhưng vẫn giữ hàng trong database.
2. Nhiều DataSource yêu cầu tách JDBC operations và transaction manager theo từng database.
3. Batch import chia công việc lớn thành các chunk có thể retry và tiếp tục từ checkpoint.

Kịch bản là hệ thống catalog lấy snapshot sản phẩm từ hệ thống legacy. Mỗi lần import có một mã run riêng. Sản phẩm xuất hiện trong snapshot được đánh dấu đã nhìn thấy ở run đó. Chỉ sau khi toàn bộ snapshot được đọc và ghi thành công, những sản phẩm thuộc nguồn đồng bộ nhưng không xuất hiện mới được soft-delete. Nếu import thất bại giữa chừng, hệ thống không được đánh dấu hàng loạt sản phẩm là đã bị xóa.

## 1. Mục tiêu và kiến trúc

Sau khi hoàn thành, bạn có thể:

- Thiết kế các cột deleted_at, deleted_by và truy vấn chỉ lấy bản ghi còn hoạt động.
- Thực hiện soft delete và restore bằng SQL có điều kiện.
- Hiểu rằng Spring Data JDBC không tự động lọc mọi query để ẩn bản ghi đã xóa mềm.
- Cấu hình source DataSource và target DataSource riêng.
- Chọn transaction manager đúng cho mỗi thao tác.
- Đọc nguồn theo keyset pagination và ghi đích theo batch.
- Lưu checkpoint cùng transaction với dữ liệu của chunk.
- Chạy lại import mà không tạo bản ghi trùng.
- Chỉ soft-delete dữ liệu vắng mặt sau khi xác nhận snapshot hoàn tất.
- Kiểm thử commit, rollback, retry và lỗi giữa các chunk.

Kiến trúc tổng quát:

~~~text
Legacy database
    |
    | sourceDataSource
    v
Import coordinator
    |
    +--> đọc một trang theo source ID
    +--> validate / normalize
    |
    v
Catalog writer
    |
    | targetDataSource
    | catalogTransactionManager
    v
Catalog database
    +--> catalog_product
    +--> catalog_import_run
    +--> catalog_import_error
~~~

Database nguồn và database đích có transaction riêng. Mỗi chunk ghi vào catalog được commit độc lập; toàn bộ job không phải một transaction phân tán.

## 2. Quy tắc nghiệp vụ

Chốt quy tắc trước khi viết code:

| Câu hỏi | Quy tắc của bài thực hành |
|---|---|
| Khi nào sản phẩm bị soft-delete? | Khi không xuất hiện trong một snapshot đã nhập hoàn tất |
| Có xóa vật lý ngay không? | Không; giữ hàng để tra cứu và khôi phục |
| Sản phẩm đã bị người quản trị soft-delete có tự hoạt động lại khi import không? | Không; manual delete wins |
| Nếu SKU đã được sản phẩm khác đang hoạt động sử dụng? | Từ chối bản ghi xung đột và ghi lỗi import |
| Nếu import thất bại giữa chừng? | Không chạy bước soft-delete cuối cùng |
| Có thể chạy lại cùng import không? | Có; dùng run ID, source ID và checkpoint để idempotent |
| Có cho phép hai import cùng nguồn chạy đồng thời? | Không; chỉ một run active cho mỗi scope/source |

Nếu không xác định rõ, batch import có thể vô tình khôi phục bản ghi đã xóa thủ công, xóa sản phẩm do lỗi đọc nguồn hoặc ghi đè SKU đang được dùng.

## 3. Thiết kế schema database đích

Ví dụ dùng PostgreSQL để minh họa partial unique index và ON CONFLICT. Với database khác, chuyển cú pháp upsert và index sang dialect tương ứng.

### 3.1. Bảng sản phẩm

~~~sql
CREATE TABLE catalog_product (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    source_system VARCHAR(40) NOT NULL,
    source_id VARCHAR(100) NOT NULL,
    sku VARCHAR(80) NOT NULL,
    name VARCHAR(250) NOT NULL,
    last_seen_import_run_id UUID,
    deleted_at TIMESTAMPTZ,
    deleted_by VARCHAR(120),
    version BIGINT NOT NULL DEFAULT 0,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    last_modified_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT uq_catalog_source_record
        UNIQUE (source_system, source_id)
);

CREATE UNIQUE INDEX uq_catalog_active_sku
    ON catalog_product (sku)
    WHERE deleted_at IS NULL;

CREATE INDEX ix_catalog_import_run_seen
    ON catalog_product (source_system, last_seen_import_run_id);
~~~

source_system và source_id xác định danh tính bản ghi ở hệ thống nguồn. Cặp này giúp import nhận ra cùng một sản phẩm qua nhiều lần chạy, kể cả khi SKU thay đổi.

last_seen_import_run_id cho biết sản phẩm được nhìn thấy trong snapshot nào gần nhất. Bước kết thúc import dùng cột này để tìm bản ghi vắng mặt.

deleted_at IS NULL nghĩa là sản phẩm đang hoạt động. Timestamp vừa biểu diễn trạng thái vừa lưu thời điểm xóa; deleted_by lưu actor thực hiện thao tác.

Partial unique index bảo đảm SKU chỉ duy nhất giữa các sản phẩm đang hoạt động. Bản ghi đã soft-delete có thể giữ SKU cũ để lưu lịch sử. Đây là cú pháp PostgreSQL; với database không hỗ trợ partial index, cần thiết kế unique key khác, chẳng hạn generated column hoặc bảng quản lý SKU đang hoạt động.

### 3.2. Bảng theo dõi lần import

~~~sql
CREATE TABLE catalog_import_run (
    id UUID PRIMARY KEY,
    source_system VARCHAR(40) NOT NULL,
    scope_key VARCHAR(100) NOT NULL,
    status VARCHAR(20) NOT NULL,
    source_high_watermark VARCHAR(100),
    last_processed_source_id VARCHAR(100),
    expected_count BIGINT,
    processed_count BIGINT NOT NULL DEFAULT 0,
    started_at TIMESTAMPTZ NOT NULL,
    completed_at TIMESTAMPTZ,
    error_message TEXT
);

CREATE INDEX ix_catalog_import_run_scope_status
    ON catalog_import_run (source_system, scope_key, status);
~~~

Trạng thái có thể là RUNNING, COMPLETED, FAILED hoặc CANCELLED. last_processed_source_id là checkpoint của chunk cuối đã commit.

### 3.3. Bảng lỗi import

~~~sql
CREATE TABLE catalog_import_error (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    import_run_id UUID NOT NULL,
    source_id VARCHAR(100),
    row_number BIGINT,
    error_code VARCHAR(80) NOT NULL,
    message TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX ix_catalog_import_error_run
    ON catalog_import_error (import_run_id);
~~~

Bảng lỗi giữ lại nguyên nhân một dòng bị từ chối mà không làm mất thông tin của lần import. Quyết định tiếp tục hay dừng khi có lỗi dữ liệu phải được xác định theo nghiệp vụ.

## 4. Mapping aggregate với Spring Data JDBC

Entity Java biểu diễn trạng thái xóa mềm như property thông thường:

~~~java
import java.time.Instant;
import java.util.UUID;

import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("catalog_product")
public class CatalogProduct {

    @Id
    private final Long id;

    @Column("source_system")
    private final String sourceSystem;

    @Column("source_id")
    private final String sourceId;

    private final String sku;
    private final String name;

    @Column("last_seen_import_run_id")
    private final UUID lastSeenImportRunId;

    @Column("deleted_at")
    private final Instant deletedAt;

    @Column("deleted_by")
    private final String deletedBy;

    @Version
    private final Long version;

    // Persistence constructor, getters và withers phù hợp với mapping.
}
~~~

Đây là khung mapping cho immutable entity. Khi triển khai, cung cấp persistence constructor và wither hoặc cơ chế tạo instance mới mà phiên bản Spring Data JDBC của dự án hỗ trợ. Có thể dùng Lombok @Value và @With để giảm boilerplate.

Repository:

~~~java
public interface CatalogProductRepository
        extends CrudRepository<CatalogProduct, Long> {

    @Query("""
        SELECT *
        FROM catalog_product
        WHERE id = :id
          AND deleted_at IS NULL
        """)
    Optional<CatalogProduct> findActiveById(@Param("id") Long id);

    @Query("""
        SELECT *
        FROM catalog_product
        WHERE sku = :sku
          AND deleted_at IS NULL
        """)
    Optional<CatalogProduct> findActiveBySku(@Param("sku") String sku);
}
~~~

Ví dụ nhấn mạnh rằng query nghiệp vụ phải có điều kiện deleted_at IS NULL. Nếu dùng derived query, có thể khai báo method dựa trên property deletedAt với điều kiện IsNull, miễn là mapping và tên property phù hợp.

**Spring Data JDBC không tự động thêm bộ lọc soft-delete vào mọi query.** findById, query tùy chỉnh, SQL qua JdbcTemplate, báo cáo và truy vấn quan hệ đều cần tuân thủ chính sách này. Property deletedAt không phải cơ chế lọc tự động.

## 5. Cài đặt soft delete và restore

Soft delete là thao tác UPDATE có điều kiện, không gọi deleteById() của repository.

### 5.1. Soft delete bằng SQL

~~~sql
UPDATE catalog_product
SET deleted_at = :deletedAt,
    deleted_by = :actor,
    version = version + 1,
    last_modified_at = :deletedAt
WHERE id = :id
  AND deleted_at IS NULL
  AND version = :expectedVersion;
~~~

Điều kiện deleted_at IS NULL khiến thao tác lặp lại không xóa lại bản ghi. Điều kiện version bảo vệ khỏi cập nhật dựa trên trạng thái cũ nếu ứng dụng dùng optimistic locking.

Service minh họa:

~~~java
@Service
public class CatalogLifecycleService {

    private final NamedParameterJdbcOperations jdbc;
    private final Clock clock;

    public CatalogLifecycleService(
            @Qualifier("catalogJdbcOperations")
            NamedParameterJdbcOperations jdbc,
            Clock clock) {
        this.jdbc = jdbc;
        this.clock = clock;
    }

    @Transactional(transactionManager = "catalogTransactionManager")
    public void softDelete(long id, long expectedVersion, String actor) {
        Instant now = Instant.now(clock);

        MapSqlParameterSource parameters = new MapSqlParameterSource()
            .addValue("id", id)
            .addValue("expectedVersion", expectedVersion)
            .addValue("deletedAt", Timestamp.from(now))
            .addValue("actor", actor);

        int updated = jdbc.update(SOFT_DELETE_SQL, parameters);

        if (updated != 1) {
            throw new IllegalStateException(
                "Product is missing, already deleted, or version changed"
            );
        }
    }
}
~~~

SOFT_DELETE_SQL là hằng số chứa câu UPDATE ở trên. Ví dụ giả định actor đã được xác thực ở application layer. Không lấy actor tùy ý từ payload bên ngoài nếu thao tác yêu cầu danh tính đáng tin cậy.

### 5.2. Restore có kiểm tra xung đột

Restore đặt deleted_at và deleted_by về NULL:

~~~sql
UPDATE catalog_product
SET deleted_at = NULL,
    deleted_by = NULL,
    version = version + 1,
    last_modified_at = CURRENT_TIMESTAMP
WHERE id = :id
  AND deleted_at IS NOT NULL;
~~~

Với unique index chỉ áp dụng cho hàng active, restore có thể thất bại nếu một sản phẩm khác đã sử dụng SKU đó. Đây là xung đột nghiệp vụ cần trả về cho caller, không nên âm thầm đổi SKU.

Có thể kiểm tra SKU trước khi restore để đưa ra thông báo thân thiện, nhưng vẫn cần xử lý unique constraint vì hai request có thể chạy đồng thời.

### 5.3. Không soft-delete bằng cách xóa hàng con

Spring Data JDBC coi aggregate là đơn vị lưu trữ. Nếu soft-delete root, các hàng con vẫn tồn tại trong database. Đây thường là điều mong muốn để giữ lịch sử.

Hãy quyết định:

- Hàng con có được truy cập trực tiếp sau khi root bị xóa mềm không?
- Query hàng con có cần JOIN root và lọc deleted_at IS NULL không?
- Khi restore root, dữ liệu con có tự trở lại khả dụng không?
- Có bảng lịch sử hoặc audit riêng cần giữ lại không?

Không xóa vật lý child rows chỉ vì root chuyển trạng thái soft-delete nếu nghiệp vụ cần phục hồi aggregate.

## 6. Tách DataSource cho nguồn và đích

Bài thực hành dùng hai resource:

- sourceDataSource: đọc snapshot từ legacy database.
- catalogDataSource: ghi sản phẩm, import run, checkpoint và lỗi vào database đích.

Mỗi resource có JDBC operations và transaction manager riêng:

~~~java
@Configuration
public class ImportDataSourceConfiguration {

    @Bean
    @ConfigurationProperties("app.datasource.source")
    DataSource sourceDataSource() {
        return DataSourceBuilder.create().build();
    }

    @Bean
    @ConfigurationProperties("app.datasource.catalog")
    DataSource catalogDataSource() {
        return DataSourceBuilder.create().build();
    }

    @Bean
    NamedParameterJdbcOperations sourceJdbcOperations(
            @Qualifier("sourceDataSource") DataSource source) {
        return new NamedParameterJdbcTemplate(source);
    }

    @Bean
    NamedParameterJdbcOperations catalogJdbcOperations(
            @Qualifier("catalogDataSource") DataSource catalog) {
        return new NamedParameterJdbcTemplate(catalog);
    }

    @Bean
    PlatformTransactionManager sourceTransactionManager(
            @Qualifier("sourceDataSource") DataSource source) {
        return new JdbcTransactionManager(source);
    }

    @Bean
    PlatformTransactionManager catalogTransactionManager(
            @Qualifier("catalogDataSource") DataSource catalog) {
        return new JdbcTransactionManager(catalog);
    }
}
~~~

Nếu repository Spring Data JDBC được dùng cho catalog, cấu hình @EnableJdbcRepositories cần trỏ package repository tới catalogJdbcOperations và catalogTransactionManager. Repository nguồn có thể dùng JdbcTemplate hoặc NamedParameterJdbcTemplate trực tiếp nếu chỉ phục vụ đọc legacy.

Không dùng transaction manager của catalog để quản lý câu query chạy trên source DataSource. Cũng không giả định hai transaction manager JDBC tự tạo ra một transaction nguyên tử.

## 7. Đọc dữ liệu nguồn theo keyset pagination

Không tải toàn bộ legacy table vào một List. Đọc từng trang theo khóa tăng dần:

~~~sql
SELECT id, sku, product_name
FROM legacy_product
WHERE id > :lastSeenId
  AND id <= :highWatermark
ORDER BY id
LIMIT :pageSize;
~~~

highWatermark là ID lớn nhất được xác định ở đầu snapshot. Nó ngăn các hàng mới có ID lớn hơn liên tục kéo dài job. Với nguồn có cập nhật nội dung trong lúc import, cần thêm snapshot nhất quán, export table bất biến, CDC watermark hoặc cơ chế khóa phù hợp; chỉ chốt ID lớn nhất không đóng băng giá trị các hàng cũ.

DTO đọc nguồn:

~~~java
public record SourceProduct(
    long id,
    String sku,
    String name
) {
}
~~~

Reader:

~~~java
public class LegacyProductReader {

    private final NamedParameterJdbcOperations sourceJdbc;

    public LegacyProductReader(
            @Qualifier("sourceJdbcOperations")
            NamedParameterJdbcOperations sourceJdbc) {
        this.sourceJdbc = sourceJdbc;
    }

    public List<SourceProduct> readPage(
            long lastSeenId,
            long highWatermark,
            int pageSize) {

        return sourceJdbc.query("""
            SELECT id, sku, product_name
            FROM legacy_product
            WHERE id > :lastSeenId
              AND id <= :highWatermark
            ORDER BY id
            LIMIT :pageSize
            """,
            new MapSqlParameterSource()
                .addValue("lastSeenId", lastSeenId)
                .addValue("highWatermark", highWatermark)
                .addValue("pageSize", pageSize),
            (rs, rowNum) -> new SourceProduct(
                rs.getLong("id"),
                rs.getString("sku"),
                rs.getString("product_name")
            )
        );
    }
}
~~~

Ví dụ SQL dùng LIMIT theo PostgreSQL/MySQL. Với SQL Server hoặc Oracle, cú pháp phân trang khác nhau. Reader trả về một page hữu hạn; connection đọc nguồn có thể được trả về pool sau khi query hoàn tất.

## 8. Tạo import run và checkpoint

Trước khi đọc dữ liệu, tạo một run ở catalog database:

~~~sql
INSERT INTO catalog_import_run (
    id, source_system, scope_key, status,
    source_high_watermark, last_processed_source_id,
    expected_count, processed_count, started_at
)
VALUES (
    :runId, :sourceSystem, :scopeKey, 'RUNNING',
    :highWatermark, NULL, :expectedCount, 0, CURRENT_TIMESTAMP
);
~~~

Run ID phải ổn định trong suốt lần chạy và được lưu ở nơi có thể khôi phục khi worker restart. Nếu khởi tạo run mới sau mỗi lần restart mà không có idempotency key, hệ thống khó phân biệt retry với import mới.

Checkpoint lưu source ID cuối cùng của chunk đã commit. Việc cập nhật sản phẩm và checkpoint phải nằm trong cùng transaction catalog:

~~~text
BEGIN catalog transaction
    UPSERT chunk products
    UPDATE catalog_import_run checkpoint/count
COMMIT
~~~

Nếu transaction rollback, cả upsert lẫn checkpoint đều rollback. Khi retry, chunk được đọc lại từ checkpoint cũ và có thể ghi lại an toàn nhờ upsert idempotent.

## 9. Ghi chunk bằng batch upsert

Với import số lượng lớn, dùng NamedParameterJdbcTemplate.batchUpdate để giảm số lần gọi database. SQL PostgreSQL mẫu:

~~~sql
INSERT INTO catalog_product (
    source_system, source_id, sku, name,
    last_seen_import_run_id, deleted_at, deleted_by,
    version, last_modified_at
)
VALUES (
    :sourceSystem, :sourceId, :sku, :name,
    :runId, NULL, NULL, 0, CURRENT_TIMESTAMP
)
ON CONFLICT (source_system, source_id)
DO UPDATE SET
    sku = EXCLUDED.sku,
    name = EXCLUDED.name,
    last_seen_import_run_id = EXCLUDED.last_seen_import_run_id,
    version = catalog_product.version + 1,
    last_modified_at = CURRENT_TIMESTAMP
WHERE catalog_product.deleted_at IS NULL;
~~~

Điều kiện cuối giữ nguyên sản phẩm đã bị soft-delete thủ công. Nếu nghiệp vụ muốn import tự restore sản phẩm nguồn xuất hiện trở lại, hãy thiết kế chính sách restore tường minh và xử lý xung đột SKU trước khi bật hành vi đó.

Writer có thể tạo batch parameters:

~~~java
public record ImportProduct(
    String sourceId,
    String sku,
    String name
) {
}

@Service
public class CatalogImportWriter {

    private final NamedParameterJdbcOperations catalogJdbc;

    public CatalogImportWriter(
            @Qualifier("catalogJdbcOperations")
            NamedParameterJdbcOperations catalogJdbc) {
        this.catalogJdbc = catalogJdbc;
    }

    @Transactional(transactionManager = "catalogTransactionManager")
    public void writeChunk(
            UUID runId,
            String sourceSystem,
            List<ImportProduct> chunk,
            String lastProcessedSourceId) {

        SqlParameterSource[] parameters = chunk.stream()
            .map(product -> new MapSqlParameterSource()
                .addValue("sourceSystem", sourceSystem)
                .addValue("sourceId", product.sourceId())
                .addValue("sku", product.sku())
                .addValue("name", product.name())
                .addValue("runId", runId))
            .toArray(SqlParameterSource[]::new);

        catalogJdbc.batchUpdate(UPSERT_SQL, parameters);

        catalogJdbc.update("""
            UPDATE catalog_import_run
            SET last_processed_source_id = :lastId,
                processed_count = processed_count + :chunkSize
            WHERE id = :runId
              AND status = 'RUNNING'
            """,
            new MapSqlParameterSource()
                .addValue("lastId", lastProcessedSourceId)
                .addValue("chunkSize", chunk.size())
                .addValue("runId", runId));
    }
}
~~~

UPSERT_SQL là hằng số chứa câu lệnh SQL ở trên. Trong code thực tế, cần kiểm tra kết quả batch, xử lý BatchUpdateException và phân biệt update count với các giá trị đặc biệt như SUCCESS_NO_INFO do JDBC driver trả về. Không giả định mọi driver luôn trả đúng một update count cho mỗi dòng.

Một chunk chỉ nên được commit khi cả dữ liệu sản phẩm và checkpoint đã được ghi thành công.

## 10. Điều phối batch import

Coordinator không giữ một transaction catalog dài cho toàn bộ job. Nó đọc một page nguồn, validate, rồi gọi writer để commit một chunk:

~~~java
@Service
public class CatalogImportCoordinator {

    private final LegacyProductReader reader;
    private final CatalogImportWriter writer;
    private final ImportRunService runs;

    public CatalogImportCoordinator(
            LegacyProductReader reader,
            CatalogImportWriter writer,
            ImportRunService runs) {
        this.reader = reader;
        this.writer = writer;
        this.runs = runs;
    }

    public void execute(ImportRun run, int pageSize) {
        long lastId = run.lastProcessedSourceIdAsLong();

        while (true) {
            List<SourceProduct> page = reader.readPage(
                lastId,
                run.highWatermark(),
                pageSize
            );

            if (page.isEmpty()) {
                break;
            }

            List<ImportProduct> valid = validateAndMap(page);
            String checkpoint = Long.toString(
                page.get(page.size() - 1).id()
            );

            writer.writeChunk(
                run.id(),
                run.sourceSystem(),
                valid,
                checkpoint
            );

            lastId = page.get(page.size() - 1).id();
        }

        runs.completeAndSoftDeleteMissing(run.id());
    }
}
~~~

Đây là khung điều phối. Phần validation phải quyết định rõ một dòng lỗi sẽ dừng run hay được ghi vào bảng lỗi và bỏ qua. Nếu cho phép bỏ qua dòng lỗi, không được đánh dấu run hoàn tất như thể snapshot đầy đủ rồi soft-delete dữ liệu cũ. Có thể yêu cầu không còn lỗi nghiêm trọng trước finalization.

Trong triển khai thực tế, đọc checkpoint từ catalog database khi khởi động lại thay vì giữ nó chỉ trong biến local. Sau mỗi chunk commit, cập nhật lastId từ checkpoint đã lưu.

## 11. Chỉ soft-delete dữ liệu vắng mặt sau khi import hoàn tất

Đây là bước quan trọng nhất. Nếu đánh dấu sản phẩm vắng mặt ngay sau mỗi page, một sản phẩm nằm ở page chưa được đọc có thể bị soft-delete nhầm.

Chỉ chạy finalization sau khi:

- Đã đọc hết phạm vi snapshot nguồn.
- Tất cả chunk cần thiết đã commit.
- Checkpoint đạt high watermark.
- Số lượng đã xử lý phù hợp với expected count hoặc chính sách lỗi.
- Không có lỗi khiến snapshot bị coi là không đầy đủ.
- Run vẫn ở trạng thái RUNNING và chưa bị worker khác finalize.

SQL finalization:

~~~sql
UPDATE catalog_product
SET deleted_at = CURRENT_TIMESTAMP,
    deleted_by = :actor,
    version = version + 1,
    last_modified_at = CURRENT_TIMESTAMP
WHERE source_system = :sourceSystem
  AND deleted_at IS NULL
  AND (
      last_seen_import_run_id IS NULL
      OR last_seen_import_run_id <> :runId
  );
~~~

Trong thực tế, giới hạn thêm scope_key, tenant hoặc nhóm dữ liệu mà run sở hữu. Không chạy câu UPDATE trên toàn bộ catalog nếu nguồn chỉ quản lý một phần dữ liệu.

Sau khi soft-delete xong, cập nhật run sang COMPLETED trong cùng transaction catalog:

~~~sql
UPDATE catalog_import_run
SET status = 'COMPLETED',
    completed_at = CURRENT_TIMESTAMP
WHERE id = :runId
  AND status = 'RUNNING';
~~~

Nếu cập nhật trạng thái run thất bại, transaction finalization phải rollback để tránh dữ liệu bị soft-delete nhưng run không ghi nhận hoàn tất.

### 11.1. Bảo vệ trường hợp snapshot rỗng bất thường

Nếu nguồn trả về zero rows vì lỗi kết nối, sai filter hoặc schema thay đổi, câu finalization có thể soft-delete toàn bộ catalog thuộc scope.

Đặt guard:

- So sánh expected_count với số dòng thực đọc.
- Từ chối snapshot rỗng nếu nghiệp vụ không cho phép catalog rỗng.
- Đặt ngưỡng giảm số lượng bất thường.
- Ghi log và yêu cầu xác nhận khi snapshot giảm quá lớn.
- Chỉ finalization khi import run đã vượt qua guard.

Snapshot rỗng hợp lệ vẫn có thể xảy ra, nhưng phải là quyết định nghiệp vụ rõ ràng.

## 12. Retry, idempotency và phục hồi sau lỗi

Một job có thể dừng sau khi một số chunk đã commit. Thiết kế cần cho phép tiếp tục mà không tạo duplicate hoặc đánh dấu nhầm dữ liệu.

### 12.1. Idempotency theo source identity

Unique constraint trên (source_system, source_id) bảo đảm cùng một bản ghi nguồn không tạo nhiều sản phẩm đích. Upsert cập nhật bản ghi hiện có và ghi run ID mới.

Nếu cùng chunk được chạy lại:

- Bản ghi không bị nhân đôi.
- Giá trị sản phẩm được cập nhật theo source.
- last_seen_import_run_id tiếp tục chỉ run hiện tại.
- Checkpoint được ghi lại trong transaction của chunk.

Các side effect ngoài database như gửi email hoặc phát event cần idempotency key riêng; upsert không tự ngăn chúng chạy lặp.

### 12.2. Phục hồi khi chunk lỗi

Nếu chunk thất bại:

1. Transaction catalog rollback.
2. Sản phẩm trong chunk không được ghi một phần.
3. Checkpoint không tiến lên.
4. Coordinator đánh dấu lỗi hoặc để run có thể retry theo chính sách.
5. Worker khởi động lại đọc checkpoint đã commit gần nhất.
6. Chunk chưa commit được đọc và xử lý lại.

Không cập nhật checkpoint trước khi batch upsert thành công. Nếu checkpoint tiến trước dữ liệu, lần retry sẽ bỏ qua những hàng chưa được ghi.

### 12.3. Khi source database không thể rollback cùng target

Reader chỉ đọc nguồn, writer ghi đích. Hai database không có transaction nguyên tử chung. Nếu source thay đổi trong lúc import, snapshot có thể không nhất quán.

Giải pháp tùy yêu cầu:

- Tạo bảng snapshot/export bất biến ở nguồn.
- Dùng transaction snapshot/read-only ở nguồn nếu thời gian đọc và database cho phép.
- Chụp high watermark hoặc CDC offset.
- Dùng updated_at và version để phát hiện thay đổi, với quy tắc xử lý rõ.
- Lưu payload của từng page vào staging đích trước khi apply.

Không giữ transaction phân tán mở chỉ để cố khóa hai database trong suốt một job dài.

## 13. Chạy nhiều import và tránh race condition

Hai run đồng thời cho cùng source/scope có thể làm sai last_seen_import_run_id. Ví dụ run A và B xen kẽ ghi cùng sản phẩm; finalization của A có thể coi sản phẩm vừa được B cập nhật là vắng mặt.

Chọn một cơ chế khóa theo source/scope:

- Unique constraint cho một run RUNNING trên mỗi scope nếu database hỗ trợ partial unique index.
- Bảng lock/job lease có owner và expiry.
- Distributed lock có fencing token.
- Job scheduler bảo đảm không chạy chồng lấn.

Khi finalization, kiểm tra run vẫn là owner hợp lệ. Không chỉ dựa vào status = RUNNING nếu nhiều worker có thể xử lý cùng run.

Một worker có thể tiếp tục run sau restart, nhưng cần lease/heartbeat hoặc cơ chế fencing để worker cũ không tiếp tục ghi sau khi quyền sở hữu đã chuyển.

## 14. Xử lý sản phẩm đã soft-delete

Import có thể gặp source record tương ứng với sản phẩm đã bị xóa mềm thủ công. Bài tập chọn chính sách **manual delete wins**:

- Upsert không sửa hàng có deleted_at IS NOT NULL.
- Bản ghi vẫn bị loại khỏi truy vấn active.
- Import không tự xóa trạng thái audit của người quản trị.
- Muốn khôi phục phải gọi thao tác restore riêng có kiểm tra SKU.

Nếu nghiệp vụ yêu cầu source là nguồn sự thật duy nhất và bản ghi xuất hiện trở lại phải tự restore, hãy thay đổi upsert/finalization theo chính sách đó. Ghi rõ actor của restore và xử lý xung đột unique SKU.

Không để import tự động khôi phục bản ghi chỉ vì nó xuất hiện trong snapshot nếu hành động xóa trước đó là quyết định nghiệp vụ của người quản trị.

## 15. Tích hợp Spring Batch khi quy mô lớn

Với job phức tạp, Spring Batch cung cấp mô hình Job, Step, ItemReader, ItemProcessor và ItemWriter cùng chunk transaction.

~~~text
CatalogImportJob
    |
    +--> Step 1: CreateImportRun
    |
    +--> Step 2: Read / validate / write chunks
    |       +--> source reader
    |       +--> item processor
    |       +--> catalog writer
    |
    +--> Step 3: Verify snapshot completeness
    |
    +--> Step 4: Soft-delete missing products
    |
    +--> Step 5: Mark run COMPLETED
~~~

Spring Batch quản lý checkpoint và restart metadata theo job/step execution. Vẫn phải cấu hình transaction manager đúng cho writer database. Nếu reader và writer dùng hai DataSource, cần phân biệt transaction của reader và writer; chunk commit trên target không làm source transaction commit/rollback theo cách phân tán.

Đối với bài tập nhỏ, coordinator tự viết có thể đủ. Với job production cần retry policy, skip policy, restart, metrics và lịch sử execution, Spring Batch thường phù hợp hơn.

## 16. Kiểm thử với database thật

Hãy dùng Testcontainers hoặc môi trường integration test tương đương để kiểm tra database dialect mục tiêu. H2 không thay thế được PostgreSQL khi bài tập phụ thuộc partial index, ON CONFLICT, UUID hoặc semantics transaction cụ thể.

Nên có hai database hoặc hai container riêng để kiểm tra ranh giới resource. Nếu chỉ dùng hai schema trong cùng server, vẫn cần hiểu chúng chia sẻ hạ tầng vật lý và không tạo distributed transaction.

### 16.1. Test soft delete

- Tạo sản phẩm active.
- Gọi soft delete.
- Xác nhận deleted_at và deleted_by có giá trị.
- Xác nhận query active không trả sản phẩm.
- Xác nhận query quản trị vẫn đọc được sản phẩm đã xóa.
- Gọi soft delete lần hai và kiểm tra hành vi idempotent.
- Restore sản phẩm và xác nhận nó xuất hiện trong query active.
- Tạo xung đột SKU rồi xác nhận restore bị từ chối.

### 16.2. Test batch import thành công

1. Seed 1.200 sản phẩm ở source database.
2. Chạy import với page size 200.
3. Xác nhận có nhiều chunk được commit.
4. Kiểm tra processed_count và checkpoint.
5. Xác nhận catalog có đủ sản phẩm.
6. Xác nhận run chuyển sang COMPLETED.
7. Xác nhận các sản phẩm cũ không còn trong snapshot được soft-delete.

- Làm chunk kế tiếp thất bại.
- Xác nhận checkpoint chỉ ở chunk cuối đã commit.

- Khởi động lại cùng run.

### 16.4. Test DataSource separation

- Ghi dữ liệu nguồn chỉ vào source database.
- Xác nhận writer chỉ thay đổi catalog database.
- Làm target transaction rollback và xác nhận source không bị thay đổi.
- Chọn sai transaction manager trong một test âm để chứng minh cấu hình bean được gắn đúng.

### 16.5. Test snapshot rỗng và chạy đồng thời

- Cung cấp snapshot rỗng bất thường và xác nhận finalization bị chặn.
- Cho phép snapshot rỗng hợp lệ bằng một cấu hình nghiệp vụ rõ ràng.
- Khởi chạy hai run cùng scope và xác nhận run thứ hai bị từ chối hoặc chờ lock.
- Kiểm tra worker cũ không thể finalize sau khi lease hết hạn và quyền sở hữu đã chuyển.

## 17. Tiêu chí hoàn thành bài tập

| Nhóm | Tiêu chí |
|---|---|
| Soft delete | Query active ẩn bản ghi đã xóa; query quản trị vẫn truy cập được |
| Restore | Có kiểm tra xung đột SKU và không xóa mất audit history ngoài ý muốn |
| Mapping | Bảng, cột, version và import metadata ánh xạ đúng |
| DataSource | Source và catalog dùng đúng JDBC operations và transaction manager |
| Batch | Dữ liệu được đọc/ghi theo chunk có giới hạn |
| Checkpoint | Checkpoint commit cùng chunk data |
| Idempotency | Retry không tạo duplicate |
| Finalization | Chỉ soft-delete dữ liệu vắng mặt sau snapshot hoàn chỉnh |
| Failure handling | Lỗi giữa chừng không làm mất dữ liệu cũ hoặc đánh dấu xóa nhầm |
| Concurrency | Không có hai run cùng scope làm ghi đè trạng thái của nhau |
| Observability | Có run status, counts, checkpoint và lỗi có thể tra cứu |

## 18. Bài tập mở rộng thêm

### Bài A — Khôi phục bản ghi đã xóa

Thêm API restore cho quản trị viên. Kiểm tra SKU active trước khi restore, xử lý race condition bằng unique constraint và ghi actor/time của lần khôi phục.

### Bài B — Soft delete theo tenant

Thêm tenant_id vào product và mọi query soft-delete/finalization. Đảm bảo một import của tenant A không thể đánh dấu sản phẩm tenant B là vắng mặt.

### Bài C — Lưu staging trước khi apply

Thay vì upsert trực tiếp mỗi page, ghi source rows vào staging table theo run_id. Sau khi xác nhận số lượng và validation, apply staging vào catalog. So sánh khả năng audit, retry và chi phí lưu trữ.

### Bài D — Dùng Spring Batch

Chuyển coordinator thành Job/Step. Dùng reader có checkpoint, processor validate, writer ghi chunk, rồi thêm step finalization chỉ chạy khi các step trước hoàn tất.

### Bài E — Outbox cho sự kiện catalog

Ghi một outbox event trong cùng transaction với chunk cập nhật sản phẩm. Publisher phát sự kiện sau commit; consumer phải idempotent vì message có thể được gửi lại.

## 19. Kết luận

Bài thực hành kết hợp soft delete, nhiều DataSource và batch import trong một quy trình đồng bộ có thể phục hồi. Soft delete giữ lịch sử và yêu cầu mọi truy vấn active lọc trạng thái xóa; Spring Data JDBC không tự áp dụng bộ lọc này cho mọi đường truy cập. Hai DataSource cần JDBC operations và transaction manager riêng, vì transaction JDBC thông thường không tạo tính nguyên tử xuyên database.

Batch import nên đọc theo keyset page, ghi theo chunk và cập nhật checkpoint trong cùng transaction với dữ liệu chunk. Upsert dựa trên source identity giúp retry idempotent. Quan trọng nhất, chỉ soft-delete các sản phẩm vắng mặt sau khi snapshot đã được xác nhận đầy đủ và run được finalize thành công. Nếu import dừng giữa chừng, dữ liệu đã commit của các chunk trước có thể được giữ lại và tiếp tục từ checkpoint; bước xóa mềm cuối cùng phải chờ đến khi toàn bộ snapshot hoàn tất.

Khi triển khai production, bổ sung khóa theo scope, guard cho snapshot rỗng, theo dõi import run, chính sách lỗi dữ liệu và integration test với đúng database/driver. Những quy tắc này giúp đồng bộ dữ liệu an toàn ngay cả khi có retry, restart, thay đổi nguồn và nhiều worker.
