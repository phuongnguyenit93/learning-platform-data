# Kiểu trả về và số hàng bị ảnh hưởng

Trong **Spring Data JDBC**, khi khai báo truy vấn ghi trực tiếp bằng `@Query`, annotation `@Modifying` cho Spring Data biết câu SQL là thao tác thay đổi dữ liệu như `UPDATE` hoặc `DELETE`. Kiểu trả về của method quyết định ứng dụng có nhận được **số hàng bị ảnh hưởng** hay bỏ qua thông tin đó.

Thông thường, method có thể trả `int`/`Integer` để nhận số hàng được database báo đã cập nhật hoặc xóa, hoặc trả `void` nếu caller không cần con số này. Giá trị đếm giúp application service biết một lệnh có tác động đến dữ liệu hay không, có tác động đúng một hàng như kỳ vọng hay đã tác động nhiều hàng. Nó **không phải** là entity được cập nhật, cũng không tự cung cấp ID được sinh hay trạng thái mới của aggregate.

## 1. `@Query` và `@Modifying` giải quyết hai việc khác nhau

`@Query` khai báo SQL sẽ được thực thi. `@Modifying` đánh dấu rằng method dùng câu SQL thay đổi dữ liệu thay vì truy vấn để đọc một tập kết quả.

Ví dụ entity:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Table;

@Table("customers")
public record Customer(
        @Id Long id,
        String name,
        String email,
        boolean active
) {}
```

DDL:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(120) NOT NULL,
    email VARCHAR(200) NOT NULL UNIQUE,
    active BOOLEAN NOT NULL
);
```

Repository:

```java
import org.springframework.data.jdbc.repository.query.Modifying;
import org.springframework.data.jdbc.repository.query.Query;
import org.springframework.data.repository.CrudRepository;
import org.springframework.data.repository.query.Param;

public interface CustomerRepository extends CrudRepository<Customer, Long> {

    @Modifying
    @Query("UPDATE customers SET active = :active WHERE id = :id")
    int updateActive(
            @Param("id") Long id,
            @Param("active") boolean active
    );
}
```

Hai annotation có vai trò riêng:

- `@Query`: cung cấp câu SQL và các tham số bind.
- `@Modifying`: yêu cầu thực thi câu query theo đường thao tác ghi và lấy update count, thay vì ánh xạ một result set entity.

`@Modifying` thuộc package `org.springframework.data.jdbc.repository.query`. Không nhầm với annotation cùng tên trong module Spring Data JPA.

## 2. Kiểu trả về `int`: nhận số hàng được cập nhật

Khi gọi:

```java
int affected = customerRepository.updateActive(42L, false);
```

Spring Data JDBC thực thi câu SQL tương đương:

```sql
UPDATE customers
SET active = ?
WHERE id = ?;
```

Database/JDBC trả về update count, và method trả con số đó cho caller. Các trường hợp thường gặp:

| Số hàng được báo | Cách hiểu thông dụng |
|---:|---|
| `0` | Không có hàng nào được tính là bị tác động bởi câu lệnh. |
| `1` | Một hàng được tác động. |
| Lớn hơn `1` | Nhiều hàng được tác động; phù hợp với lệnh bulk, nhưng có thể bất ngờ nếu use case chỉ định cập nhật một root. |

Ví dụ nếu ID `42` tồn tại và câu lệnh cập nhật được thực hiện, kết quả thường là `1`. Nếu không có hàng mang ID `42`, kết quả là `0`.

**Chú ý:** cách driver/database tính update count đối với `UPDATE` có thể khác nhau trong trường hợp giá trị mới giống giá trị cũ. Một số hệ quản trị báo số hàng khớp điều kiện, một số cấu hình/driver có thể báo số hàng thực sự thay đổi. Vì vậy, `0` cần được diễn giải theo database đang dùng; không phải trong mọi hệ thống nó đều chứng minh chắc chắn rằng ID không tồn tại.

## 3. Kiểu trả về `void`: bỏ qua số hàng bị ảnh hưởng

Nếu caller không cần biết số hàng, có thể khai báo method không trả dữ liệu:

```java
@Modifying
@Query("UPDATE customers SET active = FALSE WHERE id = :id")
void deactivate(@Param("id") Long id);
```

Lời gọi:

```java
customerRepository.deactivate(42L);
```

Ứng dụng chỉ yêu cầu thực hiện câu lệnh. Nếu cần phân biệt trường hợp không có hàng nào được cập nhật, method `void` không cung cấp con số để caller kiểm tra.

Chọn `void` khi:

- Use case không cần quan tâm số hàng tác động.
- Hệ thống chỉ cần thực hiện thao tác và xử lý lỗi SQL nếu có.
- Kết quả không được dùng để quyết định bước nghiệp vụ tiếp theo.

Chọn `int` khi:

- Cần biết thao tác có tác động đến hàng nào hay không.
- Cần xác nhận đúng một hàng được cập nhật.
- Cần đo hoặc báo cáo số hàng bị thay đổi trong thao tác bulk.
- Cần phát hiện xung đột optimistic locking được biểu diễn qua update count bằng `0`.

## 4. `Integer` và các kiểu trả về khác

Với modifying query, kiểu trả về thông dụng được hỗ trợ là `void`, `int` hoặc `Integer` (tùy API/phiên bản Spring Data JDBC). `int` thường là lựa chọn đơn giản vì JDBC update count là số nguyên và method luôn trả một con số khi thao tác hoàn tất bình thường.

Không nên tự ý khai báo `boolean`, `long`, `Optional<Integer>` hoặc entity chỉ với ý định nhận update count. Đó không phải hợp đồng chuẩn của modifying query method. Nếu ứng dụng muốn kết quả boolean, hãy nhận `int` rồi chuyển đổi ở tầng service:

```java
boolean updated = customerRepository.updateActive(id, false) == 1;
```

Nếu phiên bản Spring Data JDBC cụ thể có giới hạn chữ ký khác, cần theo tài liệu/API của phiên bản đang dùng. Tránh dựa vào việc framework có thể ép kiểu tự động từ `int` sang kiểu trả về bất kỳ.

## 5. Số hàng bị ảnh hưởng không phải số hàng được `SELECT`

Hai thao tác có thể đều trả về `int` hoặc `long`, nhưng ý nghĩa khác nhau:

### `SELECT COUNT(*)`

```java
@Query("SELECT COUNT(*) FROM customers WHERE active = TRUE")
long countActiveCustomers();
```

Đây là truy vấn đọc. Database trả **giá trị của biểu thức `COUNT(*)`**; ví dụ có 25 khách hàng đang hoạt động thì kết quả là `25`.

### `UPDATE` với `@Modifying`

```java
@Modifying
@Query("UPDATE customers SET active = FALSE WHERE active = TRUE")
int deactivateAllActiveCustomers();
```

Đây là truy vấn ghi. `int` là **update count của câu lệnh**, ví dụ 25 hàng được báo là đã cập nhật. Method không trả các hàng `Customer` vừa đổi.

| Đặc điểm | `COUNT(*)` | `@Modifying` update count |
|---|---|---|
| Loại SQL | `SELECT` | `UPDATE`, `DELETE` hoặc DML phù hợp |
| Ý nghĩa số trả về | Số hàng thỏa điều kiện đếm | Số hàng database/JDBC báo bị tác động |
| Có thay đổi dữ liệu? | Không | Có |
| Cách khai báo | `@Query` đọc scalar | `@Modifying` kết hợp `@Query` |

Không dùng `@Modifying` cho truy vấn `SELECT COUNT(*)` chỉ vì kết quả là một số nguyên.

## 6. Dùng update count để kiểm soát một thao tác đơn

Giả sử use case chỉ cho phép vô hiệu hóa một khách hàng đang hoạt động. Có thể đưa điều kiện trạng thái vào SQL:

```java
@Modifying
@Query("""
    UPDATE customers
    SET active = FALSE
    WHERE id = :id AND active = TRUE
    """)
int deactivateIfActive(@Param("id") Long id);
```

Application service diễn giải update count:

```java
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class CustomerService {
    private final CustomerRepository customers;

    public CustomerService(CustomerRepository customers) {
        this.customers = customers;
    }

    @Transactional
    public boolean deactivate(Long id) {
        int affected = customers.deactivateIfActive(id);

        if (affected > 1) {
            throw new IllegalStateException(
                    "Expected at most one customer, got " + affected);
        }

        return affected == 1;
    }
}
```

Với điều kiện `id` là khóa chính, kết quả hợp lệ theo ý định là `0` hoặc `1`:

- `1`: có một hàng thỏa điều kiện và được cập nhật.
- `0`: không có hàng nào được tính là tác động; có thể ID không tồn tại hoặc khách đã inactive.
- Lớn hơn `1`: không thể xảy ra nếu điều kiện dùng đúng khóa chính và schema đúng như dự kiến; nếu xảy ra, cần điều tra giả định/schema/SQL.

Method trả `boolean` ở **application service**, không phải modifying repository method. Service chuyển số hàng thành kết quả nghiệp vụ phù hợp.

Nếu cần phân biệt `NOT_FOUND` với `ALREADY_INACTIVE`, một con số `0` không đủ thông tin. Có thể đọc trạng thái trước hoặc sau theo transaction/locking strategy phù hợp, hoặc thiết kế kết quả nghiệp vụ khác. Đừng gán một ý nghĩa duy nhất cho `0` khi SQL có nhiều lý do khiến không hàng nào khớp.

## 7. Dùng update count cho thao tác bulk

Với một tác vụ quản trị, có thể cần vô hiệu hóa tất cả khách hàng không hoạt động trong một khoảng thời gian:

```java
@Modifying
@Query("""
    UPDATE customers
    SET active = FALSE
    WHERE last_seen_at < :cutoff
      AND active = TRUE
    """)
int deactivateInactiveCustomers(@Param("cutoff") LocalDateTime cutoff);
```

Caller nhận số hàng mà database báo đã được tác động:

```java
int affected = customerRepository.deactivateInactiveCustomers(cutoff);
log.info("Đã vô hiệu hóa {} khách hàng", affected);
```

Trong bulk update, giá trị lớn hơn `1` là bình thường. Nó cho biết phạm vi dữ liệu bị tác động, không phải lỗi. Tuy nhiên, cần cân nhắc:

- Điều kiện `WHERE` có giới hạn đúng tập đối tượng không?
- Update có bỏ qua quy tắc chuyển trạng thái ở aggregate không?
- Có cần cập nhật `version`, `updated_at` hoặc audit columns không?
- Có ảnh hưởng tới cache, search index, outbox hoặc read model không?
- Transaction có giữ khóa quá lâu hoặc tạo lock contention không?
- Update count có ý nghĩa theo driver/database đang chạy không?

Bulk DML có thể hiệu quả hơn tải từng aggregate rồi gọi `save`, nhưng nó cũng bỏ qua nhiều cơ chế ở đường lưu aggregate thông thường. Chỉ dùng khi quy tắc nghiệp vụ và các tác động liên quan đã được xử lý có chủ đích.

## 8. `@Modifying` không tự quản lý transaction boundary

`@Modifying` đánh dấu kiểu thực thi câu query; nó không thay thế `@Transactional`. Nếu use case gồm nhiều thao tác cần commit/rollback cùng nhau, hãy đặt transaction ở application service:

```java
@Transactional
public void closeCustomerAndRecordAudit(Long id) {
    int affected = customers.deactivateIfActive(id);

    if (affected != 1) {
        throw new IllegalStateException("Customer was not deactivated");
    }

    auditRepository.save(new AuditEntry(id, "DEACTIVATED"));
}
```

Nếu bước ghi audit lỗi và cả hai thao tác nằm trong cùng transaction manager/database transaction, thay đổi vô hiệu hóa có thể được rollback cùng thao tác audit. Nếu không có transaction chung, dữ liệu có thể ở trạng thái một phần.

Một repository method khai báo query tùy chỉnh không nên được mặc định là đã có transaction đúng phạm vi cho mọi use case. Đặt `@Transactional` tại service nơi xác định ranh giới nghiệp vụ thường giúp ý định rõ ràng hơn. Nếu cần, có thể cấu hình transaction trực tiếp trên method repository, nhưng tránh phân tán ranh giới transaction mà không có lý do.

## 9. `@Modifying` và optimistic locking: tự đưa version vào SQL

Với `repository.save(aggregate)` và entity có `@Version`, Spring Data JDBC tự áp dụng optimistic locking theo metadata. Nhưng một câu `UPDATE` viết tay bằng `@Modifying` **không tự động được bổ sung điều kiện version** chỉ vì entity có thuộc tính `@Version`.

Giả sử bảng `invoices` có cột `version` và entity dùng `@Version`. Một modifying query cần kiểm soát version phải tự viết điều kiện:

```java
@Modifying
@Query("""
    UPDATE invoices
    SET status = :status,
        version = version + 1
    WHERE id = :id
      AND version = :expectedVersion
    """)
int updateStatusIfVersionMatches(
        @Param("id") Long id,
        @Param("expectedVersion") Long expectedVersion,
        @Param("status") String status
);
```

Diễn giải kết quả:

- `1`: một hàng khớp ID và version cũ, cập nhật thành công và version tăng.
- `0`: không có hàng khớp; có thể ID không tồn tại hoặc version đã thay đổi.
- Lớn hơn `1`: bất thường nếu `id` là khóa chính.

Service có thể chuyển `0` thành lỗi xung đột:

```java
int affected = invoices.updateStatusIfVersionMatches(id, expectedVersion, "PAID");

if (affected == 0) {
    throw new OptimisticLockingFailureException(
            "Invoice was changed or no longer exists");
}
```

Đây là cơ chế tự triển khai; ứng dụng phải bảo đảm tăng version đúng, giữ transaction phù hợp và diễn giải trường hợp không khớp. Nếu không cần SQL đặc biệt, dùng `findById`, thay đổi aggregate và `save` thường an toàn hơn vì Spring Data JDBC quản lý optimistic locking cho đường lưu chuẩn.

## 10. `@Modifying` không trả entity vừa được cập nhật

Một method như:

```java
@Modifying
@Query("UPDATE customers SET active = FALSE WHERE id = :id")
int deactivate(@Param("id") Long id);
```

chỉ trả số hàng bị tác động. Nó không trả `Customer` mới, không tự cập nhật object `Customer` đang nằm trong bộ nhớ và không cung cấp generated key.

Nếu cần object sau cập nhật, có thể đọc lại:

```java
int affected = customers.deactivate(id);

if (affected == 0) {
    return Optional.empty();
}

return customers.findById(id);
```

Đặt cả hai bước trong transaction nếu use case cần tính nhất quán giữa update và read. Nếu cần trả cả hàng được cập nhật trong một câu lệnh bằng cú pháp như `UPDATE ... RETURNING` của một số database, đừng giả định modifying query method sẽ ánh xạ result set đó thành entity; đường `@Modifying` được thiết kế để thực thi DML và nhận update count. Hãy dùng custom repository fragment với `JdbcTemplate`/`NamedParameterJdbcTemplate` và `RowMapper` nếu cần xử lý result set trả về, hoặc update rồi query lại theo cách phù hợp.

## 11. Generated ID khác với update count

Khi insert một aggregate mới bằng `repository.save`, ứng dụng thường cần nhận ID do database sinh:

```java
Customer saved = customers.save(
        new Customer(null, "Lan", "lan@example.com", true)
);

Long id = saved.id();
```

Đối tượng trả về chứa ID đã được nhận qua cơ chế generated key. Đây là hợp đồng của thao tác lưu aggregate.

Trong khi đó, một DML method có kiểu trả về `int` cho biết số hàng bị tác động. Ví dụ một `INSERT` thực thi qua modifying query có thể trả update count, nhưng con số `1` không phải ID được sinh. Nếu cần generated ID, dùng `save` hoặc một custom JDBC implementation có xử lý generated keys rõ ràng.

| Thông tin | Cách nhận |
|---|---|
| ID mới của aggregate | Dùng object trả về từ `repository.save(...)` |
| Version mới của aggregate | Dùng object trả về từ `save` khi root có `@Version` |
| Số hàng bị DML tác động | Kiểu `int`/`Integer` của modifying query |
| Entity sau DML tùy chỉnh | Đọc lại hoặc dùng custom JDBC mapper/result-set path |

## 12. Direct DML có thể bỏ qua quy tắc aggregate

Spring Data JDBC thiết kế repository quanh aggregate root. Khi gọi `save(root)`, framework dùng metadata của root và các thành phần con thuộc aggregate. Một câu SQL `UPDATE` trực tiếp chỉ tác động các cột/hàng được nêu trong câu lệnh.

Ví dụ:

```sql
UPDATE customers
SET active = FALSE
WHERE city = 'Da Nang';
```

Truy vấn này không tự gọi phương thức domain `customer.deactivate()`, không tự nạp từng aggregate, và không tự xử lý mọi tác động phụ của từng khách hàng. Nó có thể bỏ qua:

- Invariant được kiểm tra trong aggregate root.
- Logic cập nhật `@Version` nếu không được viết rõ trong SQL.
- Auditing/callbacks gắn với đường lưu aggregate thông thường.
- Cập nhật các bảng child hoặc read model phụ thuộc.
- Ghi outbox/event hoặc audit record cần thiết cho use case.

Điều này không có nghĩa direct DML luôn sai. Nó phù hợp cho thao tác bulk có quy tắc rõ, dữ liệu không cần xử lý từng aggregate hoặc tác vụ quản trị được kiểm soát. Nhưng trước khi dùng, hãy xác định những hành vi nào vốn được thực hiện khi lưu aggregate và tự xử lý phần cần thiết.

## 13. Update count khi dùng DELETE

`@Modifying` cũng có thể dùng cho câu `DELETE`:

```java
@Modifying
@Query("DELETE FROM customers WHERE active = FALSE")
int deleteInactiveCustomers();
```

Method trả số hàng mà database báo đã bị xóa. Caller có thể ghi log hoặc kiểm tra số lượng:

```java
int deleted = customers.deleteInactiveCustomers();
log.info("Đã xóa {} khách hàng không hoạt động", deleted);
```

Nếu bảng có khóa ngoại, lệnh có thể bị database từ chối hoặc kích hoạt cascade tùy DDL. Update count thường phản ánh hàng bị tác động bởi câu lệnh trực tiếp; không nên mặc định nó cộng mọi hàng bị cascade trong các bảng liên quan. Hãy kiểm tra hành vi cụ thể của DBMS.

Đối với một aggregate có child, xóa trực tiếp bảng root có thể để lại child mồ côi nếu không có cascade hoặc cleanup phù hợp. Dùng repository root hoặc thiết kế SQL/DDL có chủ đích để bảo đảm toàn bộ aggregate được xử lý đúng.

## 14. Những trường hợp `0` cần diễn giải cẩn thận

Một update count bằng `0` có thể xuất hiện vì nhiều lý do:

1. Không có hàng thỏa điều kiện `WHERE`.
2. Hàng không tồn tại.
3. Hàng tồn tại nhưng không thỏa trạng thái hiện tại, ví dụ đã inactive.
4. Version trong điều kiện optimistic locking không còn khớp.
5. Database/driver có quy tắc báo số hàng thực sự thay đổi và giá trị mới giống giá trị cũ.

Vì thế, đừng viết:

```java
if (affected == 0) {
    throw new CustomerNotFoundException(id);
}
```

trừ khi SQL và database semantics bảo đảm `0` chỉ có thể xảy ra khi không có customer. Nếu câu lệnh còn điều kiện `active = TRUE`, kết quả `0` có thể có nghĩa khách hàng đã tồn tại nhưng không còn active.

Hãy thiết kế contract nghiệp vụ rõ:

```java
public enum DeactivationResult {
    DEACTIVATED,
    ALREADY_INACTIVE_OR_NOT_FOUND
}
```

Nếu cần phân biệt hai trạng thái cuối, thực hiện thêm bước đọc hoặc dùng một câu SQL/transaction strategy có thể cung cấp đủ thông tin. Một update count đơn lẻ không mang nhiều ý nghĩa hơn con số mà nó biểu diễn.

## 15. Kiểm tra SQL và update count trong môi trường phát triển

Có thể bật log Spring JDBC để quan sát SQL và tham số bind:

```yaml
logging:
  level:
    org.springframework.jdbc.core: DEBUG
    org.springframework.jdbc.core.StatementCreatorUtils: TRACE
```

Khi kiểm tra một modifying query, hãy ghi nhận:

- SQL thực tế và điều kiện `WHERE`.
- Giá trị/kiểu của tham số bind.
- Số hàng method trả về.
- Trạng thái transaction commit hay rollback.
- Giá trị database khi đọc lại sau thao tác.

Không nên chỉ nhìn update count để kết luận dữ liệu đã bền vững. Nếu method chạy trong transaction sau đó bị rollback, số hàng đã được câu SQL tác động trong transaction không có nghĩa thay đổi cuối cùng được commit.

Log bind parameter có thể chứa email, thông tin cá nhân hoặc dữ liệu nghiệp vụ. Chỉ bật mức chi tiết trong môi trường phát triển/kiểm soát và tắt khi không cần.

## 16. Các lỗi thường gặp

| Triệu chứng | Nguyên nhân thường gặp | Hướng xử lý |
|---|---|---|
| Method `@Query` update không chạy đúng đường DML | Thiếu `@Modifying` | Đánh dấu method là modifying query |
| Muốn biết số hàng nhưng method trả `void` | Hợp đồng method bỏ kết quả update count | Đổi sang `int`/`Integer` nếu cần |
| Khai báo `boolean` để nhận thành công/thất bại | Kiểu trả về không phải hợp đồng update count thông dụng | Trả `int`, chuyển thành boolean ở service |
| Kết quả `0` bị coi luôn là không tồn tại | `WHERE` có thêm điều kiện trạng thái/version hoặc driver có semantics riêng | Diễn giải theo điều kiện và DBMS |
| Kết quả lớn hơn `1` ngoài dự kiến | Điều kiện không duy nhất hoặc thiếu filter | Kiểm tra `WHERE`, unique constraint và ý định bulk |
| Mong method trả entity mới | Modifying query trả update count, không ánh xạ entity | Query lại hoặc dùng custom mapper cho result set |
| ID mới bị hiểu là update count | Nhầm generated key với số hàng | Dùng `save` để nhận ID; DML count chỉ là số hàng |
| `@Version` không ngăn ghi đè | SQL tùy chỉnh không kiểm tra/tăng version | Thêm điều kiện version và tăng version thủ công hoặc dùng `save` |
| Dữ liệu thay đổi dù use case thất bại ở bước sau | Transaction không bao trùm toàn bộ thao tác | Đặt `@Transactional` tại application service |
| Child bị bỏ sót sau bulk delete/update | DML trực tiếp không quản lý aggregate graph | Xử lý child/cascade và invariant một cách tường minh |

## 17. Bài thực hành: quan sát số hàng bị ảnh hưởng

Với bảng `customers`, nạp dữ liệu thử:

```sql
INSERT INTO customers (name, email, active) VALUES
    ('Lan', 'lan@example.com', TRUE),
    ('Minh', 'minh@example.com', TRUE),
    ('Hoa', 'hoa@example.com', FALSE);
```

Khai báo ba method:

```java
@Modifying
@Query("UPDATE customers SET active = FALSE WHERE id = :id")
int deactivateById(@Param("id") Long id);

@Modifying
@Query("UPDATE customers SET active = FALSE WHERE active = TRUE")
int deactivateAllActive();

@Modifying
@Query("DELETE FROM customers WHERE active = FALSE")
int deleteInactive();
```

Thử theo thứ tự:

1. Gọi `deactivateById` với ID tồn tại; ghi lại update count.
2. Gọi lại với ID không tồn tại; quan sát kết quả `0`.
3. Gọi `deactivateAllActive`; quan sát số hàng bị tác động có thể lớn hơn `1`.
4. Gọi `deleteInactive`; quan sát số hàng bị xóa và kiểm tra dữ liệu sau đó.
5. Đổi method `deactivateById` thành `void`; xác nhận caller không còn nhận được update count.
6. Thực hiện update trong transaction rồi chủ động gây lỗi sau đó; kiểm tra database sau rollback để thấy update count trước rollback không chứng minh thay đổi đã commit.

Chạy các thử nghiệm trên database dùng riêng cho học tập, không dùng dữ liệu thật. Đối chiếu kết quả theo database/driver đang sử dụng vì update-count semantics có thể khác nhau trong một số trường hợp.

## 18. Nguyên tắc ghi nhớ

- Dùng `@Query` để khai báo SQL và `@Modifying` để đánh dấu query thay đổi dữ liệu.
- `int`/`Integer` nhận update count; `void` bỏ qua con số đó.
- Update count là số hàng database/JDBC báo bị tác động, không phải entity hay generated ID.
- `0`, `1` và số lớn hơn `1` cần được diễn giải theo điều kiện `WHERE`, mục đích đơn/bulk và semantics của database.
- `SELECT COUNT(*)` trả giá trị đếm; modifying query trả update count. Hai con số có nguồn gốc khác nhau.
- `@Modifying` không tự tạo transaction boundary, không tự cập nhật entity trong bộ nhớ và không tự áp dụng optimistic locking cho SQL viết tay.
- Nếu cần entity sau DML, đọc lại hoặc dùng custom JDBC result mapping phù hợp.
- Direct DML có thể bỏ qua hành vi aggregate, auditing/callbacks, child updates và side effects; xử lý các yêu cầu đó có chủ đích.
- Dùng `repository.save` khi cần cơ chế lưu aggregate chuẩn, generated ID và optimistic locking do Spring Data JDBC quản lý.

Trong Spring Data JDBC, chọn kiểu trả về của truy vấn ghi theo thông tin use case cần. `void` phù hợp khi chỉ cần thực thi; `int`/`Integer` phù hợp khi cần biết số hàng được tác động và kiểm tra kết quả. Hãy kết hợp update count với điều kiện `WHERE` rõ ràng, transaction boundary phù hợp và hiểu biết về optimistic locking để tránh diễn giải sai một con số đơn giản thành kết luận nghiệp vụ quá mức.
