# Loại trừ dữ liệu không lưu bằng `@Transient`

Trong **Spring Data JDBC**, không phải mọi thuộc tính của đối tượng Java đều cần có cột tương ứng trong cơ sở dữ liệu. Một đối tượng nghiệp vụ có thể chứa thông tin tạm để phục vụ giao diện, kết quả tính toán trong bộ nhớ, trạng thái xử lý ngắn hạn hoặc dữ liệu bổ trợ được tạo sau khi đọc từ database. Những thông tin đó không nhất thiết là một phần của trạng thái cần lưu.

Annotation **`org.springframework.data.annotation.Transient`** cho phép đánh dấu một thuộc tính là **không tham gia vào quá trình ánh xạ lưu trữ của Spring Data**. Hiểu đúng annotation này giúp tránh tạo cột không cần thiết, tránh nhầm lẫn giữa dữ liệu trong bộ nhớ và dữ liệu bền vững, đồng thời giữ ranh giới aggregate rõ ràng.

Bài học tập trung vào cách dùng `@Transient` trong **Spring Data Relational JDBC**: thuộc tính nào được đọc/ghi, vòng đời của dữ liệu không lưu, cách phối hợp với constructor và repository, sự khác biệt với các annotation gần tên, cùng những lỗi thường gặp.

## 1. Spring Data JDBC ánh xạ thuộc tính như thế nào?

Spring Data JDBC dùng thông tin ánh xạ của entity và aggregate để chuyển qua lại giữa **object Java** và **hàng dữ liệu trong database**.

Ví dụ entity sản phẩm có các thuộc tính:

~~~text
Product
  id              -> product.id
  sku             -> product.sku
  priceMinorUnits -> product.price_minor_units
  adminNote       -> thông tin tạm chỉ dùng trong Java
~~~

Giả sử bảng `product` chỉ có ba cột:

~~~sql
CREATE TABLE product (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    sku VARCHAR(80) NOT NULL,
    price_minor_units BIGINT NOT NULL
);
~~~

Ở đây, `adminNote` có thể là một ghi chú hiển thị trong quá trình nhân viên xem hoặc chỉnh sửa sản phẩm, nhưng **không phải thuộc tính cần lưu cùng sản phẩm**. Nếu ánh xạ `adminNote` như một thuộc tính thông thường, Spring Data JDBC có thể mong đợi cột tương ứng khi tạo các câu SQL đọc/ghi. Khi cột đó không tồn tại, thao tác lưu hoặc đọc có thể thất bại.

Ta muốn mô hình có hai nhóm thuộc tính:

| Nhóm | Ví dụ | Khi lưu bằng repository | Khi đọc lại bằng repository |
| --- | --- | --- | --- |
| Thuộc tính được ánh xạ | `id`, `sku`, `priceMinorUnits` | Có thể tham gia SQL `INSERT`/`UPDATE` theo cơ chế của Spring Data JDBC | Được khôi phục từ dữ liệu trong bảng |
| Thuộc tính gắn `@Transient` | `adminNote` | Không được Spring Data JDBC đưa vào thao tác ánh xạ lưu trữ | Không được nạp từ cột database |

`@Transient` không yêu cầu loại bỏ field khỏi Java class. Nó chỉ thay đổi cách **Spring Data nhận diện thuộc tính lưu trữ**.

## 2. Cú pháp chính xác của `@Transient`

Import cần dùng:

~~~java
import org.springframework.data.annotation.Transient;
~~~

Áp dụng cho thuộc tính muốn loại khỏi ánh xạ:

~~~java
@Transient
private String adminNote;
~~~

Trong entity dùng field access mặc định của Spring Data JDBC, đặt annotation trên field là cách dễ đọc và nhất quán. Khi class được thiết kế theo kiểu truy cập thuộc tính khác, vị trí annotation cần tương ứng với chiến lược ánh xạ thực tế.

Có thể hình dung:

~~~text
Ứng dụng tạo / thay đổi Product
             |
             v
        Product object
       /             \
 sku, price,...   adminNote
       |              |
       v              v
 Spring Data JDBC    @Transient
       |              |
       v              X   không tham gia mapping
 INSERT / UPDATE
       |
       v
   Bảng product
~~~

**Điểm cần phân biệt:** thuộc tính `@Transient` vẫn tồn tại trong bộ nhớ, vẫn có thể được đọc hoặc thay đổi bằng phương thức Java phù hợp. Chỉ có cơ chế mapping lưu trữ của Spring Data bỏ qua nó.

## 3. Ví dụ hoàn chỉnh: thuộc tính tạm trong entity sản phẩm

Giả sử ứng dụng có bảng `product` như ở mục 1. Một class dùng Spring Data JDBC có thể viết:

~~~java
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Transient;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("product")
public class Product {

    @Id
    private Long id;

    private String sku;

    @Column("price_minor_units")
    private long priceMinorUnits;

    @Transient
    private String adminNote;

    public Product(Long id, String sku, long priceMinorUnits) {
        if (sku == null || sku.isBlank()) {
            throw new IllegalArgumentException("SKU không được để trống");
        }
        if (priceMinorUnits < 0) {
            throw new IllegalArgumentException("Giá không được âm");
        }
        this.id = id;
        this.sku = sku;
        this.priceMinorUnits = priceMinorUnits;
    }

    public Long getId() {
        return id;
    }

    public String getSku() {
        return sku;
    }

    public long getPriceMinorUnits() {
        return priceMinorUnits;
    }

    public String getAdminNote() {
        return adminNote;
    }

    public void setAdminNote(String adminNote) {
        this.adminNote = adminNote;
    }
}
~~~

Trong ví dụ:

- `@Table("product")` chỉ định bảng.
- `@Id` đánh dấu thuộc tính định danh.
- `@Column("price_minor_units")` chỉ định cột cho `priceMinorUnits`.
- `@Transient` loại `adminNote` khỏi mapping của Spring Data JDBC.
- Constructor nhận **các thuộc tính được ánh xạ**. `adminNote` không phải tham số bắt buộc để tạo lại entity từ database.

Đây là class Java thông thường: `adminNote` có getter/setter để code nghiệp vụ hoặc giao diện sử dụng, nhưng nó không trở thành cột của bảng `product`.

### Repository

~~~java
import org.springframework.data.repository.CrudRepository;

public interface ProductRepository extends CrudRepository<Product, Long> {
}
~~~

### Lưu rồi đọc lại

~~~java
Product product = new Product(null, "BOOK-021", 185_000L);
product.setAdminNote("Đang xem trước thay đổi trên giao diện quản trị");

Product saved = productRepository.save(product);

Product reloaded = productRepository.findById(saved.getId())
        .orElseThrow();

System.out.println(reloaded.getSku());            // "BOOK-021"
System.out.println(reloaded.getPriceMinorUnits()); // 185000
System.out.println(reloaded.getAdminNote());       // null
~~~

Trong ví dụ này, `reloaded.getAdminNote()` trả `null` vì class không tự khởi tạo giá trị đó, và Spring Data JDBC không nạp nó từ database. Nếu class có field initializer hoặc constructor tự điền một giá trị mặc định thì khi đọc lại thuộc tính có thể mang giá trị mặc định ấy; **`@Transient` chỉ bảo đảm không nạp nó từ dữ liệu được ánh xạ**.

Spring Data JDBC không cung cấp persistence context cùng cơ chế giữ đối tượng managed như JPA. Lời gọi `findById` thông thường thực hiện việc đọc lại aggregate từ database, nên ví dụ có thể minh họa rõ ranh giới giữa trạng thái trong bộ nhớ và trạng thái đã lưu.

### SQL được tạo sẽ liên quan đến những cột nào?

Về mặt ý tưởng, thao tác chèn sản phẩm mới sẽ tương đương:

~~~sql
INSERT INTO product (sku, price_minor_units)
VALUES (?, ?);
~~~

Thuộc tính `adminNote` **không xuất hiện** trong danh sách cột được ánh xạ. SQL thực tế, cách lấy khóa sinh tự động và thứ tự tham số do phiên bản Spring Data JDBC, dialect và cấu hình quyết định; không nên dựa vào cú pháp minh họa làm bản chụp chính xác của mọi database.

Nếu bổ sung field `@Transient` vào class nhưng không thêm cột mới vào bảng, schema không cần đổi chỉ vì field đó.

## 4. `@Transient` tác động đến đọc và ghi

Annotation này có phạm vi rõ ràng:

**Khi ghi dữ liệu**

- Spring Data JDBC không đưa thuộc tính transient vào tập thuộc tính được ánh xạ để chèn hoặc cập nhật.
- Giá trị được gán trong Java không trở thành dữ liệu bền vững qua `repository.save(...)`.
- Chỉ đổi một field transient không làm nó trở thành thay đổi cần lưu xuống cột tương ứng.

**Khi đọc dữ liệu**

- Framework không tìm cột để nạp giá trị cho thuộc tính transient.
- Thuộc tính có thể ở giá trị mặc định Java hoặc giá trị được constructor/initializer thiết lập.
- Nếu muốn giá trị ấy xuất hiện sau khi tải entity, ứng dụng phải **tính lại, gán lại hoặc lấy từ nguồn khác** theo cách được thiết kế rõ ràng.

**Trong database**

- `@Transient` không tạo, xóa hay sửa cột của schema.
- Nếu bảng đã có cột cùng tên, annotation không tự xóa cột đó.
- Migration schema là việc riêng của cơ chế DDL/Flyway/Liquibase hoặc quy trình quản trị database.

Đặc biệt, đừng hiểu `@Transient` là một lệnh SQL hay cơ chế mã hóa dữ liệu. Nó là metadata cho quá trình mapping ở phía ứng dụng.

## 5. Khi nào nên dùng `@Transient`?

Có nhiều trường hợp hợp lý, miễn là hiểu rõ giá trị không được khôi phục từ database khi entity được tải lại.

| Trường hợp | Ví dụ | Vì sao không lưu cùng aggregate? |
| --- | --- | --- |
| Dữ liệu phục vụ giao diện trong một luồng xử lý | `adminNote`, `selectedInUi` | Chỉ có nghĩa ở thời điểm request hoặc phiên tương tác. |
| Giá trị dẫn xuất có thể tính lại | `displayLabel`, `formattedPrice` | Được tạo từ các thuộc tính đã lưu; không cần nguồn dữ liệu thứ hai. |
| Kết quả tính toán tạm | `calculatedDiscountPreview` | Chỉ phục vụ màn hình xem thử trước khi xác nhận. |
| Trạng thái xử lý nội bộ | `validationMessages`, `importWarnings` | Phản ánh kết quả của một bước xử lý, không thuộc bản ghi sản phẩm. |
| Dữ liệu bổ sung từ hệ thống khác | `inventoryPreview` lấy từ một service khác | Không muốn biến dữ liệu lấy tức thời thành thành phần thuộc aggregate được lưu. |
| Cache tính toán cục bộ | `cachedPresentationText` | Có thể tái tạo, có chính sách làm mới riêng. |

Ví dụ với nhãn hiển thị:

~~~java
@Transient
private String displayLabel;

public void prepareDisplayLabel() {
    this.displayLabel = sku + " - " + priceMinorUnits + " minor units";
}
~~~

Sau khi repository tải đối tượng, code gọi `prepareDisplayLabel()` nếu màn hình cần dữ liệu này. Không nên giả định framework tự gọi phương thức đó.

Tuy nhiên, nếu giá trị hoàn toàn được tính từ các field đã lưu và phép tính rẻ, **không tạo field transient thường còn đơn giản hơn**:

~~~java
public String getDisplayLabel() {
    return sku + " - " + priceMinorUnits + " minor units";
}
~~~

Ở cách thứ hai, giá trị được tính mỗi lần gọi, không cần giữ thêm trạng thái và không cần đồng bộ khi `sku` hoặc `priceMinorUnits` thay đổi. Với Spring Data JDBC dùng field access, một getter tính toán như vậy không nhất thiết trở thành persistent property; nếu có cấu hình property access riêng, cần xét mapping tương ứng.

### Dữ liệu dẫn xuất nào không nên chỉ giữ bằng `@Transient`?

Nếu kết quả có ý nghĩa pháp lý hoặc nghiệp vụ tại **thời điểm phát sinh** và phải giữ nguyên trong lịch sử, không nên giả định nó luôn có thể tính lại từ dữ liệu hiện tại. Ví dụ:

- Giá đã chốt của một dòng đơn hàng.
- Tỷ giá được dùng tại thời điểm thanh toán.
- Khoản thuế đã tính và xác nhận tại thời điểm phát hành hóa đơn.

Những giá trị này có thể cần được lưu bền vững như một phần trạng thái nghiệp vụ. Có thể tính được giá trị hôm nay không có nghĩa có thể tái hiện chính xác giá trị của giao dịch trong quá khứ.

## 6. Phân biệt các loại “không lưu”

Các kỹ thuật sau có tên hoặc tác dụng gần nhau nhưng không thay thế cho nhau.

| Cơ chế | Thuộc hệ thống nào? | Ý nghĩa chính | Có thay thế `@Transient` của Spring Data JDBC không? |
| --- | --- | --- | --- |
| `org.springframework.data.annotation.Transient` | Spring Data Commons, dùng bởi Spring Data JDBC | Không ánh xạ thuộc tính vào dữ liệu lưu trữ | **Có**, đây là annotation đang học. |
| `transient` (từ khóa Java) | Ngôn ngữ Java và Java Object Serialization | Đánh dấu field không tham gia cơ chế serialization mặc định của Java | Không nên xem hai cơ chế là tương đương; dùng Spring annotation để diễn đạt rõ chủ đích mapping. |
| `jakarta.persistence.Transient` | JPA/Jakarta Persistence | Không ánh xạ thuộc tính trong mô hình JPA | Không phải annotation được dùng làm hợp đồng mapping của Spring Data JDBC. |
| `com.fasterxml.jackson.annotation.JsonIgnore` | Jackson | Bỏ qua thuộc tính trong quá trình xử lý JSON theo cấu hình Jackson | **Không**; một field không trả qua JSON vẫn có thể được lưu vào DB. |
| `@ReadOnlyProperty` của Spring Data | Spring Data | Thuộc tính có thể được đọc từ kho dữ liệu nhưng không được ghi qua cơ chế mapping tương ứng | **Không**, vì `@Transient` bỏ qua cả đọc và ghi. |
| `static` (field Java) | Ngôn ngữ Java | Trạng thái thuộc class, không thuộc từng instance | Không dùng để mô tả dữ liệu tạm của từng entity. |

### 6.1. `@Transient` khác `@JsonIgnore`

Giả sử:

~~~java
@Transient
private String adminNote;
~~~

Nếu class có getter và được Jackson serialize theo cấu hình thông thường, `adminNote` **vẫn có thể xuất hiện trong JSON**. Spring Data mapping và JSON serialization là hai quá trình độc lập:

~~~text
Entity Product
  |
  +--- Spring Data JDBC  -> SQL / bảng product
  |           |
  |           +--- @Transient: bỏ qua cột mapping
  |
  +--- Jackson           -> JSON response
              |
              +--- @JsonIgnore: điều khiển thuộc tính JSON
~~~

Nếu một field cần vừa không được lưu vừa không được trả ra API, ứng dụng có thể cần **hai cơ chế khác nhau**, ví dụ `@Transient` cho persistence và `@JsonIgnore` cho JSON, hoặc tách entity khỏi response DTO.

Ngược lại, field gắn `@JsonIgnore` **vẫn có thể được Spring Data JDBC lưu** nếu nó là persistent property. Không dùng annotation JSON để quyết định schema database.

### 6.2. `@Transient` của Spring Data khác `@Transient` của JPA

Hai import trông gần giống:

~~~java
// Dùng khi ánh xạ bằng Spring Data JDBC:
import org.springframework.data.annotation.Transient;

// Annotation của JPA, thuộc một cơ chế persistence khác:
// import jakarta.persistence.Transient;
~~~

Spring Data JDBC sử dụng hệ thống mapping Spring Data Relational. Việc mang nguyên ví dụ JPA sang và chỉ sửa dependency thường dẫn đến hiểu sai hành vi. Hãy luôn kiểm tra **package của annotation**, không chỉ tên `Transient`.

### 6.3. `@Transient` khác thuộc tính chỉ đọc

Đôi khi database có cột tính sẵn hoặc một trường được database cập nhật, ứng dụng cần **đọc giá trị nhưng không ghi đè**. Trong trường hợp đó, loại khỏi cả đọc lẫn ghi bằng `@Transient` không đáp ứng nhu cầu. Cần xem cơ chế mapping read-only được Spring Data JDBC hỗ trợ, chẳng hạn `@ReadOnlyProperty` khi phù hợp, hoặc dùng truy vấn SQL/projection riêng.

Ví dụ cột `last_synced_at` do một tiến trình khác cập nhật: nếu entity cần hiển thị mốc thời gian ấy, `@Transient` sẽ khiến thông tin không được tự khôi phục. Annotation chỉ hợp lý khi thật sự **không cần mapping giá trị từ database**.

## 7. Lưu ý về constructor và entity immutable

Spring Data JDBC cần tạo object từ dữ liệu đã đọc. Framework thường bind giá trị cột database vào tham số của constructor persistence hoặc thiết lập những thuộc tính được ánh xạ sau khi khởi tạo.

**Thuộc tính `@Transient` không có giá trị từ database để bind vào constructor persistence.** Vì vậy không nên đặt nó thành tham số bắt buộc trong constructor mà Spring Data dùng để tái dựng entity.

### Ví dụ dễ gặp vấn đề

~~~java
public class ProductView {

    private final Long id;
    private final String sku;

    @Transient
    private final String editorMessage;

    // Constructor duy nhất lại yêu cầu editorMessage.
    public ProductView(Long id, String sku, String editorMessage) {
        this.id = id;
        this.sku = sku;
        this.editorMessage = editorMessage;
    }
}
~~~

Khi Spring Data JDBC materialize entity, `editorMessage` đã bị loại khỏi mapping nên không có giá trị dữ liệu tương ứng để cung cấp cho tham số ấy. Thiết kế này không có hợp đồng tạo lại object rõ ràng.

### Cách thiết kế phù hợp hơn

~~~java
import org.springframework.data.annotation.Transient;

public class ProductView {

    private final Long id;
    private final String sku;

    @Transient
    private String editorMessage;

    public ProductView(Long id, String sku) {
        this.id = id;
        this.sku = sku;
    }

    public void attachEditorMessage(String message) {
        this.editorMessage = message;
    }
}
~~~

Constructor dùng để tái dựng object chỉ yêu cầu dữ liệu được lưu, còn `editorMessage` được gắn **sau khi đọc** nếu luồng xử lý cần nó.

Nếu class có nhiều constructor hoặc factory, cần bảo đảm Spring Data xác định được constructor persistence (có thể sử dụng `@PersistenceCreator` trong trường hợp thích hợp) và metadata tên tham số phù hợp, ví dụ cấu hình compiler với `-parameters`. Với giá trị tạm có thể tính trực tiếp, một phương thức không lưu trạng thái có thể phù hợp hơn cả field transient.

### Record và immutable type

Record phù hợp với value object mà **mọi thành phần của record đều thuộc về giá trị cần lưu**, ví dụ `Money(amount, currency)`. Nếu một record component được đưa vào canonical constructor nhưng lại bị loại khỏi mapping bằng `@Transient`, khả năng materialize object cần được xem xét kỹ: framework không có cột để truyền vào thành phần đó.

Không nên thêm field transient có nhiệm vụ “làm đẹp giao diện” vào record persistence chỉ vì record ngắn gọn. Giữ domain value object đúng nghĩa, rồi tạo DTO/view model riêng cho dữ liệu trình bày khi cần.

## 8. `@Transient` và ranh giới aggregate

Spring Data JDBC coi aggregate root cùng những thành phần được ánh xạ thuộc aggregate là đơn vị lưu. Vì vậy, đánh dấu một thuộc tính tham chiếu bằng `@Transient` có thể ảnh hưởng lớn hơn trường hợp bỏ qua một chuỗi hiển thị.

Ví dụ:

~~~java
@Table("purchase_order")
public class PurchaseOrder {

    @Id
    private Long id;

    private String status;

    @Transient
    private List<OrderLine> previewLines;
}
~~~

Ở đây, `previewLines` là **danh sách tạm**; Spring Data JDBC sẽ không lưu các phần tử đó như một collection thuộc aggregate. Nếu `previewLines` thực ra là danh sách dòng hàng chính thức, gắn `@Transient` có thể khiến toàn bộ dữ liệu con không được lưu như mong đợi.

Phân biệt:

| Thuộc tính | Cách thiết kế phù hợp |
| --- | --- |
| Danh sách dòng hàng thực sự thuộc đơn hàng, phải lưu và khôi phục | Ánh xạ như collection trong aggregate bằng cơ chế Spring Data JDBC phù hợp, ví dụ `@MappedCollection` và schema tương ứng. |
| Danh sách dòng hàng giả lập để xem trước một thay đổi | Có thể là `@Transient` nếu chỉ tồn tại ở bộ nhớ trong luồng xử lý đó. |
| Thông tin khách hàng là aggregate độc lập | Thường giữ ID/reference thay vì kéo toàn bộ root khác vào graph sở hữu; không dùng `@Transient` như cách “sửa tạm” một quan hệ thiết kế sai. |
| Lịch sử cần lưu để kiểm toán | Lưu bằng mô hình bền vững tương ứng, không gắn `@Transient` chỉ vì dữ liệu hiện chưa có cột. |

Quy tắc thực tế: **chỉ loại khỏi mapping khi dữ liệu thật sự không thuộc trạng thái bền vững của aggregate**. Nếu thiếu cột hoặc quan hệ chưa được thiết kế, `@Transient` không phải giải pháp thay cho schema và domain model đúng.

## 9. `@Transient` không tạo thuộc tính truy vấn trong database

Một field bị loại khỏi mapping không có cột gắn với nó. Do đó, không nên xây repository dựa trên giả định có thể lọc hoặc sắp xếp trong SQL theo field transient:

~~~java
@Transient
private String displayLabel;
~~~

Ví dụ phương thức repository sau không có nền tảng ánh xạ cột rõ ràng cho `displayLabel`:

~~~java
// Không phù hợp nếu displayLabel chỉ là dữ liệu tạm trong Java:
List<Product> findByDisplayLabel(String displayLabel);
~~~

Tùy cách Spring Data xây dựng truy vấn và mapping, cấu hình như vậy có thể gây lỗi lúc tạo truy vấn hoặc lúc thực thi. Để lọc dữ liệu hiệu quả trong database:

- Truy vấn bằng thuộc tính **được lưu và ánh xạ**, chẳng hạn `sku`.
- Nếu cần một biểu thức tính toán từ cột, dùng SQL có biểu thức phù hợp hoặc projection đọc riêng.
- Nếu chỉ cần lọc tập nhỏ đã lấy vào bộ nhớ, có thể tính giá trị và lọc trong Java, nhưng phải xét kích thước dữ liệu và chi phí tải.

Tương tự, việc viết SQL thủ công với `JdbcTemplate`/`JdbcClient` là cơ chế khác: SQL tùy chỉnh có thể chọn bất kỳ cột hoặc biểu thức nào database cho phép. `@Transient` không chỉnh sửa câu SQL do lập trình viên viết; nó chỉ chi phối mapping của Spring Data đối với persistent property.

## 10. Có nên dùng `@Transient` cho dữ liệu nhạy cảm?

Ví dụ code có thuộc tính:

~~~java
@Transient
private String temporaryVerificationCode;
~~~

Annotation này giúp tránh việc **repository Spring Data JDBC tự lưu field đó** vào bảng entity. Nhưng bản thân nó **không**:

- Mã hóa dữ liệu trong bộ nhớ.
- Ngăn mã xuất hiện trong `toString()`, log, exception hoặc debugger.
- Ngăn Jackson serialize giá trị qua API.
- Xóa giá trị ra khỏi bộ nhớ sau khi dùng.
- Bảo đảm code khác không ghi giá trị vào database bằng SQL thủ công.
- Cung cấp chính sách hết hạn, phân quyền hay che giấu dữ liệu.

Với dữ liệu nhạy cảm hoặc tạm thời, trước hết phải chọn vị trí lưu và vòng đời phù hợp. Một field transient trong entity có thể tiện cho xử lý ngắn, nhưng không phải cơ chế bảo mật tổng thể. Với dữ liệu chỉ dùng ở HTTP request, đối tượng request/service riêng thường rõ nghĩa hơn việc gắn trạng thái đó vào entity persisted.

## 11. Các lỗi thường gặp

| Lỗi | Nguyên nhân | Cách xử lý |
| --- | --- | --- |
| Tạo field mới chỉ để hiển thị, sau đó repository báo cột không tồn tại | Spring Data đang xem field là persistent property | Gắn `@Transient` nếu thật sự là field không lưu; nếu phải lưu, thêm schema/mapping đúng. |
| Gán giá trị transient rồi mong `save` giữ nguyên sau khi đọc lại | Đã nhầm trạng thái trong bộ nhớ với trạng thái database | Tính/gán lại giá trị hoặc chuyển nó thành field lưu trữ nếu nghiệp vụ cần. |
| Import nhầm `jakarta.persistence.Transient` | Dùng annotation theo thói quen JPA | Chuyển sang `org.springframework.data.annotation.Transient` khi làm việc với Spring Data JDBC. |
| Chỉ dùng `@JsonIgnore` để loại field khỏi SQL | JSON serialization độc lập với Spring Data persistence | Chọn annotation riêng cho từng ranh giới. |
| Constructor persistence yêu cầu tham số transient | Không có dữ liệu được ánh xạ để bind tham số | Chỉ bind các property được lưu; khởi tạo/tính dữ liệu tạm sau đó. |
| Đánh dấu collection entity con bằng `@Transient` | Đã loại cả phần sở hữu cần lưu khỏi aggregate | Ánh xạ collection thực sự bằng cơ chế relational phù hợp. |
| Dùng `@Transient` cho dữ liệu cần truy vấn SQL | Không có cột nào gắn với property | Lưu giá trị, tính bằng SQL hoặc dùng projection thích hợp. |
| Dùng `@Transient` cho cột chỉ đọc từ database | Annotation loại bỏ cả chiều đọc | Cân nhắc mapping read-only hay query projection. |
| Cho rằng `@Transient` là cơ chế bảo mật | Annotation chỉ xử lý persistence mapping | Thiết kế thêm chính sách log, API, lifetime và lưu trữ dữ liệu nhạy cảm. |
| Gắn `@Transient` vào ID hoặc version vì muốn “ẩn” chúng | Làm hỏng cơ chế nhận diện và khóa lạc quan của persistence | Giữ `@Id`/`@Version` được ánh xạ; ẩn khỏi API bằng DTO/serialization khi cần. |

### Vì sao không nên gắn `@Transient` lên `@Id` hoặc `@Version`?

`@Id` và `@Version` có vai trò trong việc xác định entity, nhận biết trạng thái mới/cũ và kiểm soát cập nhật đồng thời. Nếu loại những thuộc tính này khỏi persistence mapping, repository không còn nhận được thông tin cần cho cơ chế lưu trữ tương ứng. Muốn không hiển thị ID/version trong JSON, hãy dùng DTO hoặc cấu hình serialization, **không loại chúng khỏi mapping JDBC**.

## 12. Tình huống tự thực hành

### Tình huống A — Preview tổng tiền

Ứng dụng cho phép nhân viên nhập số lượng và đơn giá, sau đó hiển thị `estimatedTotal` trước khi xác nhận đơn. Sau khi xác nhận, `finalTotal` có ý nghĩa nghiệp vụ và phải được lưu.

**Cách phân biệt:** `estimatedTotal` có thể là phép tính động hoặc transient trong model xem trước; `finalTotal` thuộc trạng thái bền vững của đơn hàng. Không đánh dấu `finalTotal` bằng `@Transient` chỉ vì có thể tính từ các dòng hàng.

### Tình huống B — Trường phục vụ JSON

Entity có `name` và `price`. API cần thêm `formattedPrice` cho frontend nhưng database chỉ cần lưu số tiền gốc.

**Cách thiết kế:** có thể xây response DTO với `formattedPrice`, hoặc tính bằng getter. Nếu thực sự cần cache nhãn này trong entity, đánh dấu field lưu cache bằng `@Transient`; cần lưu ý `@Transient` không tự quyết định JSON trả gì.

### Tình huống C — Field transient “biến mất”

Service gọi:

~~~java
Product product = repository.findById(id).orElseThrow();
product.setAdminNote("Cần kiểm tra mô tả");
repository.save(product);

Product anotherLoad = repository.findById(id).orElseThrow();
System.out.println(anotherLoad.getAdminNote());
~~~

**Kết quả dự kiến với class ở mục 3:** in ra `null`. Ghi chú chỉ nằm trong đối tượng Java đã gán; nó không được lưu vào bảng, và một lần đọc mới không khôi phục được.

### Tình huống D — Thuộc tính chưa có cột

Nhóm phát triển bổ sung `externalReference` vào entity. Giá trị này là mã chứng từ mà nghiệp vụ phải giữ vĩnh viễn, nhưng bảng chưa có cột tương ứng. Một lập trình viên đề nghị gắn `@Transient` để tránh lỗi khi chạy.

**Cách xử lý:** đây là dữ liệu nghiệp vụ cần lưu. Phải thiết kế cột và migration tương ứng, cập nhật mapping, rồi mới triển khai. Gắn `@Transient` sẽ làm mất hành vi lưu trữ mà nghiệp vụ yêu cầu.

## 13. Ghi nhớ khi thiết kế mapping

Khi cân nhắc một thuộc tính trong Spring Data JDBC, hãy lần lượt hỏi:

1. **Giá trị này có cần tồn tại sau khi ứng dụng dừng hoặc sau khi object được tải lại không?** Nếu có, hãy thiết kế persistence phù hợp.
2. **Giá trị chỉ phục vụ một lần tính toán, hiển thị hoặc xử lý tạm?** Có thể tính khi cần, dùng DTO, hoặc đánh dấu `@Transient` nếu nó là field trên entity.
3. **Giá trị có cần được truy vấn, lọc hoặc sắp xếp bằng SQL không?** Nếu có, phải có nguồn dữ liệu trong database hoặc một biểu thức/projection truy vấn rõ ràng.
4. **Giá trị có cần tham gia constructor persistence không?** Nếu bị `@Transient` loại khỏi mapping, đừng yêu cầu framework nạp nó từ một cột không tồn tại.
5. **Giá trị có thể rò rỉ qua JSON, log hoặc service khác không?** `@Transient` không kiểm soát những đường đó; xử lý riêng theo trách nhiệm của từng tầng.

**Nguyên tắc cốt lõi:** `@Transient` của Spring Data giúp entity chứa thông tin sử dụng trong bộ nhớ mà **không biến thông tin ấy thành trạng thái được repository lưu và đọc từ cơ sở dữ liệu**. Hãy dùng nó khi việc không lưu là một quyết định chủ động của mô hình, đồng thời phân biệt rõ với dữ liệu nghiệp vụ cần tồn tại bền vững.
