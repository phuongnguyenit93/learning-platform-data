# Entity con có ID và không có ID trong Spring Data JDBC

## 1. Vì sao entity con có thể có hoặc không có ID?

Spring Data JDBC tổ chức dữ liệu theo **aggregate**. Aggregate root là đối tượng đứng đầu một cụm dữ liệu có vòng đời nhất quán; các entity/value object nằm bên trong được lưu và tải như một phần của aggregate đó.

Ví dụ một đơn hàng có nhiều dòng hàng:

~~~text
PurchaseOrder (aggregate root)
    ├── OrderLine (dòng hàng thứ nhất)
    ├── OrderLine (dòng hàng thứ hai)
    └── OrderLine (dòng hàng thứ ba)
~~~

Có hai cách thiết kế phổ biến:

- **Entity con không có ID riêng:** object con được nhận diện trong ngữ cảnh aggregate, thông qua khóa ngoại trỏ về root và vị trí/khóa của nó trong collection (nếu collection cần key).
- **Entity con có ID riêng:** bảng con có thêm một cột định danh hàng, ví dụ `line_id`. Dù có ID này, object vẫn có thể là thành phần thuộc aggregate root và vẫn được quản lý theo vòng đời của aggregate.

Cần tách biệt ba khái niệm:

1. **Aggregate root ID:** định danh aggregate và là điểm truy cập chính qua repository.
2. **Child row ID:** định danh kỹ thuật của hàng trong bảng con, nếu schema và mapping có sử dụng.
3. **Collection key:** vị trí của phần tử trong `List`, hoặc key của phần tử trong `Map`; nó giúp biểu diễn cấu trúc collection và không nhất thiết là ID nghiệp vụ.

Một entity con có ID **không tự động trở thành aggregate root**. Ngược lại, entity con không có ID riêng vẫn có thể được lưu đầy đủ vì Spring Data JDBC biết nó thuộc aggregate nào.

## 2. Aggregate root và quan hệ nội bộ trong Spring Data JDBC

Spring Data JDBC tập trung vào aggregate thay vì một object graph tùy ý như ORM có lazy loading. Repository thường được định nghĩa cho **aggregate root**:

~~~java
public interface PurchaseOrderRepository
        extends CrudRepository<PurchaseOrder, Long> {
}
~~~

`PurchaseOrder` có `@Id`. Các `OrderLine` trong collection được lưu cùng aggregate qua mapping quan hệ nội bộ, thường dùng `@MappedCollection`.

Sơ đồ quan hệ trong database:

~~~mermaid
erDiagram
    PURCHASE_ORDERS ||--o{ ORDER_LINES : contains
    PURCHASE_ORDERS {
        bigint id PK
        date ordered_on
    }
    ORDER_LINES {
        bigint order_id FK
        int line_number
        varchar product_code
        int quantity
    }
~~~

Cột `order_id` trong bảng con giữ khóa ngoại tới aggregate root. Nếu child không có ID riêng, cặp `(order_id, line_number)` có thể làm khóa chính ghép trong schema. Nếu child có ID riêng, `line_id` có thể là primary key và `(order_id, line_number)` vẫn có thể được đặt unique để bảo đảm vị trí không trùng trong cùng đơn hàng.

**Spring Data JDBC quản lý quan hệ qua aggregate root.** Nó không cung cấp repository độc lập cho mọi object con chỉ vì object đó là một class Java hoặc có một cột ID.

## 3. Entity con không có ID riêng

Đây là mô hình phù hợp khi object con chỉ có ý nghĩa bên trong aggregate, không cần được tham chiếu hoặc quản lý độc lập.

Ví dụ một dòng hàng có mã sản phẩm, số lượng và đơn giá:

~~~java
import java.math.BigDecimal;
import org.springframework.data.relational.core.mapping.Table;

@Table("order_lines")
public record OrderLine(
        String productCode,
        int quantity,
        BigDecimal unitPrice
) {}
~~~

`OrderLine` không có `@Id`. Aggregate root chứa danh sách:

~~~java
import java.time.LocalDate;
import java.util.ArrayList;
import java.util.List;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_orders")
public class PurchaseOrder {

    @Id
    private Long id;

    private LocalDate orderedOn;

    @MappedCollection(idColumn = "order_id", keyColumn = "line_number")
    private List<OrderLine> lines = new ArrayList<>();

    // constructors, getters...
}
~~~

Ở đây:

- `@Id` đánh dấu ID của aggregate root.
- `@MappedCollection(idColumn = "order_id")` chỉ ra cột trong bảng con lưu ID của root.
- `keyColumn = "line_number"` lưu vị trí của phần tử trong `List`.
- `OrderLine` không cần ID riêng; nó được lưu như một phần tử của danh sách thuộc đơn hàng.

DDL tương ứng có thể là:

~~~sql
CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    ordered_on DATE NOT NULL
);

CREATE TABLE order_lines (
    order_id BIGINT NOT NULL,
    line_number INTEGER NOT NULL,
    product_code VARCHAR(40) NOT NULL,
    quantity INTEGER NOT NULL,
    unit_price DECIMAL(12, 2) NOT NULL,

    CONSTRAINT pk_order_lines
        PRIMARY KEY (order_id, line_number),

    CONSTRAINT fk_order_lines_order
        FOREIGN KEY (order_id) REFERENCES purchase_orders(id)
);
~~~

Cặp `(order_id, line_number)` định danh một dòng trong phạm vi một đơn hàng. `line_number` là khóa collection, không phải ID độc lập của `OrderLine`.

### 3.1. Khi nào chọn child không có ID?

Chọn cách này khi:

- Dòng con không có ý nghĩa ngoài aggregate root.
- Không cần tham chiếu trực tiếp dòng con từ aggregate khác.
- Việc thay đổi danh sách con được thực hiện thông qua root.
- Vị trí hoặc khóa trong collection đủ để xác định phần tử trong aggregate.
- Không cần giữ một định danh hàng con ổn định qua các lần ghi aggregate.

Ví dụ `OrderLine`, `Address` nhúng trong `Customer`, `InvoiceItem` thuộc `Invoice` thường là các object có thể được quản lý như thành phần của aggregate.

### 3.2. List, Map và Set ảnh hưởng thế nào?

`@MappedCollection` có thể mô tả quan hệ collection. Với `List`, `keyColumn` thường lưu vị trí phần tử. Với `Map`, cột key lưu khóa map. Với `Set`, không có vị trí theo thứ tự, vì vậy thường không cần key column cho thứ tự.

Ví dụ `Map<String, OrderLine>`:

~~~java
@MappedCollection(idColumn = "order_id", keyColumn = "line_code")
private Map<String, OrderLine> linesByCode = new HashMap<>();
~~~

Cột `line_code` lưu key của map. Nó không tự động là khóa chính của bảng; nếu nghiệp vụ yêu cầu duy nhất trong một đơn hàng, hãy đặt constraint phù hợp, chẳng hạn `UNIQUE(order_id, line_code)`.

Đối với `Set`, Java collection ngăn phần tử trùng theo `equals()`/`hashCode()` trong bộ nhớ, nhưng điều đó **không tự tạo unique constraint trong database**. Nếu dữ liệu được ghi từ nhiều nguồn hoặc có SQL trực tiếp, cần constraint ở schema để bảo vệ tính duy nhất.

## 4. Entity con có ID riêng

Có trường hợp bảng con cần một cột ID riêng, ví dụ dòng hàng có `line_id` do database sinh. Mô hình Java có thể khai báo:

~~~java
import java.math.BigDecimal;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("order_lines")
public class OrderLine {

    @Id
    private Long id;

    @Column("product_code")
    private String productCode;

    private int quantity;

    @Column("unit_price")
    private BigDecimal unitPrice;

    // constructor, getters...
}
~~~

Aggregate root vẫn giữ collection:

~~~java
@Table("purchase_orders")
public class PurchaseOrder {

    @Id
    private Long id;

    @MappedCollection(idColumn = "order_id", keyColumn = "line_number")
    private List<OrderLine> lines;

    // constructor, getters...
}
~~~

DDL có thể dùng:

~~~sql
CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
);

CREATE TABLE order_lines (
    line_id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL,
    line_number INTEGER NOT NULL,
    product_code VARCHAR(40) NOT NULL,
    quantity INTEGER NOT NULL,
    unit_price DECIMAL(12, 2) NOT NULL,

    CONSTRAINT fk_order_lines_order
        FOREIGN KEY (order_id) REFERENCES purchase_orders(id),

    CONSTRAINT uk_order_lines_position
        UNIQUE (order_id, line_number)
);
~~~

`line_id` định danh hàng trong bảng `order_lines`; `order_id` vẫn xác định aggregate root sở hữu dòng đó. `line_number` giữ vị trí của phần tử trong `List`.

**Có ID riêng không đồng nghĩa có vòng đời độc lập.** Nếu `OrderLine` vẫn được chứa trong `PurchaseOrder.lines`, việc đọc/ghi nó vẫn thuộc thao tác trên aggregate root. Không nên suy ra rằng chỉ cần thêm `@Id` là có thể tạo `OrderLineRepository` và cập nhật riêng dòng hàng theo cách của một aggregate root khác.

Khả năng sử dụng generated ID cho entity con và cách ID được trả về cần được xác nhận theo phiên bản Spring Data JDBC, dialect và JDBC driver đang dùng. Nếu child ID được database sinh, hãy sử dụng aggregate/entity được trả về sau thao tác lưu và kiểm tra giá trị ID trong integration test.

### 4.1. Khi nào child có ID hữu ích?

Một ID hàng con có thể hữu ích khi:

- Bảng con cần một primary key đơn để tích hợp với hệ thống khác ở mức database.
- Dữ liệu legacy đã có cột ID và schema không thể thay đổi.
- Các bảng phụ hoặc audit cần định danh một hàng con ở tầng lưu trữ.
- Cần một khóa kỹ thuật đơn thay cho khóa chính ghép dài.

Tuy vậy, nếu ID cần được giữ ổn định và được dùng rộng rãi để truy cập/cập nhật child độc lập, hãy xem xét lại aggregate boundary. Một child có định danh kỹ thuật nhưng vẫn bị quản lý như thành phần của root có thể không phù hợp với nhu cầu cập nhật độc lập.

## 5. So sánh entity con có ID và không có ID

| Tiêu chí | Child không có ID riêng | Child có ID riêng |
|---|---|---|
| Định danh trong schema | Thường dựa trên root FK và collection key | Có thêm cột ID của hàng con |
| Mapping Java | Không khai báo `@Id` trên child | Có thể khai báo `@Id` trên child theo mapping được hỗ trợ |
| Liên kết với aggregate | Qua `@MappedCollection` và FK tới root | Vẫn qua `@MappedCollection` và FK tới root |
| Repository độc lập | Không | Không tự động có; vẫn là child của aggregate |
| Vòng đời | Do aggregate root quản lý | Vẫn do aggregate root quản lý nếu còn nằm trong collection |
| Độ phức tạp schema | Thường đơn giản, có thể dùng khóa ghép | Thêm ID và cơ chế sinh/duy trì ID |
| Tham chiếu từ aggregate khác | Không nên tham chiếu trực tiếp | Có ID cũng không tự biến child thành đối tượng tham chiếu độc lập |
| Phù hợp | Value object hoặc entity phụ thuộc root | Legacy schema hoặc nhu cầu kỹ thuật về row identifier |

Một lựa chọn khác cần phân biệt: **child object không có ID** không có nghĩa database không thể xác định hàng. Database vẫn có thể dùng primary key ghép như `(order_id, line_number)`. “Không có ID” ở đây là không có property identifier độc lập trong model child, chứ không phải bảng con không cần khóa hoặc không có cách phân biệt hàng.

## 6. Lưu aggregate và vòng đời của child

Spring Data JDBC làm việc theo aggregate. Khi tạo mới root, framework ghi root và các thành phần con theo mapping. Khi cập nhật aggregate, cách ghi có thể bao gồm xóa và ghi lại các entity phụ thuộc, thay vì theo dõi từng field đã thay đổi như dirty checking của JPA.

Luồng khái quát:

~~~mermaid
flowchart TD
    A["purchaseOrderRepository.save(order)"] --> B{"Root đã tồn tại?"}
    B -->|Chưa| C["INSERT aggregate root"]
    B -->|Rồi| D["UPDATE aggregate root"]
    C --> E["Persist các child theo mapping"]
    D --> F["Thay thế/ghi lại dữ liệu child theo chiến lược aggregate"]
    E --> G["Trả aggregate đã lưu"]
    F --> G
~~~

Hệ quả:

- Không nên giả định một child row được cập nhật từng cột độc lập khi gọi `save(root)`.
- Thứ tự hoặc collection key có thể ảnh hưởng cách các dòng con được ghi lại.
- ID sinh tự động của child có thể không ổn định qua các lần lưu aggregate nếu chiến lược cập nhật thay thế các hàng con.
- Không nên để bảng ngoài aggregate tham chiếu trực tiếp ID của child chỉ vì child có cột ID.
- Khi cần lưu lịch sử thay đổi từng child, cân nhắc audit/event riêng hoặc một mô hình aggregate phù hợp.

Chi tiết câu SQL và chiến lược persistence phụ thuộc phiên bản, loại quan hệ và cấu hình. Điều quan trọng là **đặt quyền sở hữu vòng đời ở đúng aggregate root**.

## 7. Nếu child cần được truy cập độc lập, hãy cân nhắc tách aggregate

Giả sử `OrderLine` cần:

- Được cập nhật bởi một use case riêng mà không tải `PurchaseOrder`.
- Có repository và transaction boundary riêng.
- Được tham chiếu từ nhiều aggregate khác.
- Giữ ID ổn định qua các lần cập nhật.
- Có vòng đời độc lập với đơn hàng.

Khi đó, có thể cần mô hình `OrderLine` thành aggregate root hoặc entity độc lập, thay vì object con nằm trong `PurchaseOrder.lines`.

Ví dụ thiết kế:

~~~text
PurchaseOrder aggregate
    └── orderId, orderDate, customerId

OrderLine aggregate
    └── lineId, orderId, productId, quantity
~~~

DDL:

~~~sql
CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    ordered_on DATE NOT NULL
);

CREATE TABLE order_lines (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL,
    product_id BIGINT NOT NULL,
    quantity INTEGER NOT NULL,

    CONSTRAINT fk_order_lines_order
        FOREIGN KEY (order_id) REFERENCES purchase_orders(id)
);
~~~

Entity root cho dòng hàng:

~~~java
@Table("order_lines")
public class OrderLine {

    @Id
    private Long id;

    @Column("order_id")
    private Long orderId;

    @Column("product_id")
    private Long productId;

    private int quantity;

    // constructor, getters...
}
~~~

Repository riêng:

~~~java
public interface OrderLineRepository
        extends CrudRepository<OrderLine, Long> {

    List<OrderLine> findByOrderId(Long orderId);
}
~~~

Ở mô hình này `OrderLine` là aggregate root độc lập; nó có repository riêng. `orderId` là tham chiếu tới aggregate khác bằng ID, không phải quan hệ object graph được Spring Data JDBC tự quản lý như một ORM.

Việc tách aggregate có nghĩa ứng dụng phải chủ động quản lý transaction và invariant giữa `PurchaseOrder` và `OrderLine`. Không còn giả định mọi thay đổi ở hai aggregate được lưu tự động như một thao tác đơn. Cần thiết kế use case và consistency phù hợp.

## 8. Không nhầm child ID với collection key

Ba giá trị sau có thể cùng xuất hiện trong bảng con nhưng có nghĩa khác nhau:

| Cột | Ý nghĩa |
|---|---|
| `line_id` | ID riêng của hàng con, nếu có |
| `order_id` | ID aggregate root sở hữu hàng con |
| `line_number` | Vị trí/key của phần tử trong collection |

Ví dụ một hàng:

~~~text
line_id = 901
order_id = 42
line_number = 2
product_code = "P-200"
~~~

- `line_id = 901`: định danh kỹ thuật của hàng trong bảng.
- `order_id = 42`: dòng hàng thuộc đơn hàng số 42.
- `line_number = 2`: phần tử đang ở vị trí/key thứ 2 trong collection.

Nếu child không có `line_id`, cặp `(order_id, line_number)` vẫn có thể xác định duy nhất dòng hàng trong phạm vi aggregate. Không nên đặt tên cột collection key là `id` nếu điều đó làm người đọc nhầm với `@Id` của entity.

## 9. Quan hệ một-nhiều với child không ID: ví dụ đầy đủ

Giả sử đơn hàng có nhiều dòng hàng, mỗi dòng chỉ tồn tại bên trong đơn hàng.

Entity con:

~~~java
import java.math.BigDecimal;

public record OrderLine(
        String productCode,
        int quantity,
        BigDecimal unitPrice
) {}
~~~

Aggregate root:

~~~java
import java.time.LocalDate;
import java.util.ArrayList;
import java.util.List;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_orders")
public class PurchaseOrder {

    @Id
    private Long id;

    private LocalDate orderedOn;

    @MappedCollection(idColumn = "order_id", keyColumn = "line_number")
    private List<OrderLine> lines = new ArrayList<>();

    public PurchaseOrder(LocalDate orderedOn, List<OrderLine> lines) {
        this.orderedOn = orderedOn;
        this.lines = new ArrayList<>(lines);
    }

    public Long getId() {
        return id;
    }

    public LocalDate getOrderedOn() {
        return orderedOn;
    }

    public List<OrderLine> getLines() {
        return List.copyOf(lines);
    }
}
~~~

Repository:

~~~java
public interface PurchaseOrderRepository
        extends CrudRepository<PurchaseOrder, Long> {
}
~~~

Lưu aggregate:

~~~java
PurchaseOrder order = new PurchaseOrder(
        LocalDate.now(),
        List.of(
                new OrderLine("P-100", 2, new BigDecimal("50000")),
                new OrderLine("P-200", 1, new BigDecimal("75000"))
        )
);

PurchaseOrder saved = purchaseOrderRepository.save(order);
~~~

Spring Data JDBC lưu root và các phần tử con. Các dòng con được gắn với ID của root qua `order_id`; vị trí được lưu trong `line_number`.

Không có repository riêng cho `OrderLine`, vì use case thao tác dòng hàng thông qua aggregate `PurchaseOrder`.

## 10. Các lỗi thường gặp

| Biểu hiện | Nguyên nhân có thể | Hướng xử lý |
|---|---|---|
| Child không được lưu | Chưa khai báo collection mapping đúng hoặc bảng/cột không khớp | Kiểm tra `@MappedCollection`, `idColumn`, `keyColumn` và DDL |
| Child không có `@Id` nhưng vẫn được lưu | Đây là hành vi bình thường của child thuộc aggregate | Đảm bảo root có `@Id` và quan hệ được ánh xạ |
| Nhầm `line_number` là ID độc lập | Collection key bị hiểu sai vai trò | Phân biệt root FK, child ID và collection key |
| Thêm `@Id` vào child nhưng vẫn không có repository riêng | Repository được định nghĩa cho aggregate root | Tạo aggregate root riêng nếu child cần vòng đời độc lập |
| ID child thay đổi sau khi lưu lại root | Child row có thể bị thay thế trong quá trình cập nhật aggregate | Không dùng child ID làm tham chiếu ổn định; xem xét tách aggregate |
| List đọc sai thứ tự | Thiếu/sai `keyColumn` hoặc dữ liệu key không đúng | Kiểm tra cột lưu vị trí và schema |
| Map key không được giữ | Cột key của map không được mapping đúng | Khai báo `keyColumn` và kiểm tra dữ liệu |
| Có dòng con trùng | Java Set không thay thế constraint database | Đặt primary/unique constraint theo quy tắc |
| Xóa root gây lỗi foreign key | Có hàng con hoặc tham chiếu ngoài aggregate chưa được xử lý | Xem lại cascade/lifecycle và quan hệ tham chiếu |
| Child bị tham chiếu từ aggregate khác | Ranh giới aggregate chưa phù hợp | Chuyển child thành aggregate root và tham chiếu root ID |

## 11. Bài tập thực hành

### Bài 1 — Child không có ID

Tạo `PurchaseOrder` có `List<OrderLine>`. Không khai báo `@Id` trên `OrderLine`. Dùng `@MappedCollection(idColumn = "order_id", keyColumn = "line_number")` và khóa chính ghép `(order_id, line_number)` ở bảng con. Lưu rồi tải lại aggregate.

### Bài 2 — Child có ID riêng

Thêm cột `line_id` identity vào bảng `order_lines` và property `@Id Long id` vào `OrderLine`. Giữ nguyên `order_id` và `line_number`. Quan sát ID child sau khi lưu aggregate và sau khi cập nhật/lưu lại root.

### Bài 3 — Phân biệt ba cột

Với hàng `line_id = 901`, `order_id = 42`, `line_number = 2`, giải thích từng giá trị. Xác định cột nào định danh aggregate, cột nào định danh row con và cột nào giữ vị trí collection.

### Bài 4 — List và Map

Thay `List<OrderLine>` bằng `Map<String, OrderLine>`. Dùng key column để lưu mã dòng hàng. Thử tạo unique constraint trên `(order_id, line_code)` và kiểm tra khi hai dòng có cùng key.

### Bài 5 — Tách aggregate

Thiết kế use case để một dòng hàng được sửa độc lập và được tham chiếu từ nhiều nơi. Chuyển `OrderLine` thành aggregate root có repository riêng, chỉ giữ `orderId` làm tham chiếu. Xác định transaction và consistency cần thiết giữa order và line.

## 12. Ghi nhớ

- **Aggregate root ID** định danh aggregate; repository thường được định nghĩa cho root.
- Child **không cần ID riêng** để được lưu. Khóa ngoại tới root kết hợp collection key có thể xác định hàng con trong aggregate.
- Child **có ID riêng** vẫn có thể chỉ là thành phần của aggregate; `@Id` trên child không tự tạo repository hoặc vòng đời độc lập.
- `@MappedCollection` dùng `idColumn` để lưu khóa ngoại tới root và `keyColumn` để lưu vị trí/key của collection khi cần.
- Child ID, root FK và collection key là ba khái niệm khác nhau, dù có thể cùng nằm trong bảng con.
- Spring Data JDBC quản lý child thông qua aggregate root; khi cập nhật aggregate, dữ liệu child có thể được thay thế/ghi lại, vì vậy không nên mặc định child ID sinh tự động luôn ổn định.
- Nếu child cần được tham chiếu, cập nhật và quản lý độc lập, hãy cân nhắc biến nó thành aggregate root riêng và tham chiếu bằng ID.
