# Tái sử dụng fragment giữa nhiều repository

## 1. Khi nhiều repository cần cùng một khả năng

Trong Spring Data JDBC, mỗi aggregate thường có một repository riêng. Ví dụ:

~~~java
public interface CustomerRepository
        extends CrudRepository<Customer, UUID> {
}

public interface PurchaseOrderRepository
        extends CrudRepository<PurchaseOrder, Long> {
}
~~~

Khi ứng dụng phát triển, nhiều repository có thể cần cùng một khả năng bổ sung:

- Ghi một bản ghi audit theo thao tác đã thực hiện.
- Cung cấp một nhóm phương thức tìm kiếm dùng chung.
- Thực hiện một thao tác lưu trữ tùy chỉnh có cùng quy tắc.
- Bổ sung một API kỹ thuật được nhiều aggregate sử dụng.

Nếu sao chép cùng một method và implementation vào từng repository, code sẽ lặp lại và dễ lệch nhau theo thời gian. Nếu đưa tất cả vào một base repository lớn, các repository có thể phải kế thừa những method không liên quan đến aggregate của chúng.

**Repository fragment** là cách Spring Data cho phép ghép các khả năng bổ sung vào repository. Một fragment thường gồm một interface mô tả contract và một implementation cung cấp hành vi. Nhiều repository có thể cùng kế thừa một fragment interface; nếu implementation được đăng ký thành Spring bean dùng chung, các repository có thể sử dụng cùng một implementation.

Bài này giải thích cách thiết kế fragment có thể tái sử dụng, cách Spring Data ghép fragment vào repository, quy ước tìm implementation, cách chia sẻ implementation giữa nhiều repository và những điểm cần lưu ý khi fragment dùng JDBC trực tiếp.

## 2. Repository composition và fragment

Spring Data repository không nhất thiết chỉ gồm một interface CRUD. Repository có thể được tạo bằng cách kết hợp:

1. **Repository base interface:** chẳng hạn **CrudRepository<T, ID>**, cung cấp các thao tác cơ bản.
2. **Repository fragment interface:** mô tả một nhóm khả năng bổ sung.
3. **Fragment implementation:** triển khai các method của fragment.
4. **Repository base implementation:** phần implementation nền do module Spring Data cung cấp.

Có thể hình dung:

~~~text
                   CustomerRepository
                           |
              +------------+------------+
              |            |            |
              v            v            v
        CrudRepository  AuditFragment  SearchFragment
              |            |            |
              v            v            v
        CRUD support   AuditFragmentImpl SearchFragmentImpl
              \            |            /
               \           |           /
                +----------+----------+
                           |
                           v
                 Repository proxy
                           |
                           v
                        Service
~~~

Khi service inject CustomerRepository, nó nhận được một repository proxy có cả method CRUD và method từ những fragment đã ghép.

### 2.1. Fragment là một contract có thể ghép

Một fragment interface chỉ mô tả khả năng mà repository cần bổ sung. Nó không nhất thiết đại diện cho một aggregate, một bảng hoặc một repository độc lập.

Ví dụ:

~~~java
public interface AuditFragment {

    void appendAudit(
            String aggregateType,
            String aggregateId,
            String action
    );
}
~~~

Đây là một capability có thể được dùng ở nhiều repository. Implementation sẽ quyết định cách ghi audit.

### 2.2. Một repository có thể dùng nhiều fragment

~~~java
public interface CustomerRepository
        extends CrudRepository<Customer, UUID>,
                AuditFragment,
                CustomerSearchFragment {
}
~~~

Repository trên kết hợp CRUD, audit và tìm kiếm customer. Một repository khác có thể dùng AuditFragment nhưng không cần CustomerSearchFragment.

Fragment chỉ nên gom các method có một trách nhiệm rõ ràng. Đừng biến một fragment thành nơi chứa mọi method tùy chỉnh của toàn ứng dụng.

## 3. Tạo fragment dùng chung cho nhiều repository

Ta sẽ xây dựng một fragment ghi audit dùng được bởi CustomerRepository và PurchaseOrderRepository. Audit row được lưu ở bảng riêng, không phải một phần của aggregate Customer hay PurchaseOrder.

### 3.1. Tạo bảng audit

Ví dụ schema:

~~~sql
CREATE TABLE repository_audit (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    aggregate_type VARCHAR(100) NOT NULL,
    aggregate_id VARCHAR(100) NOT NULL,
    action VARCHAR(80) NOT NULL,
    occurred_at TIMESTAMP NOT NULL
);
~~~

Kiểu identity và timestamp có thể cần điều chỉnh theo database đích. Bảng này lưu loại aggregate, ID dưới dạng chuỗi, hành động và thời điểm ghi nhận.

### 3.2. Khai báo fragment interface

Tạo AuditFragment.java trong package dùng chung:

~~~java
package com.example.shared.repository;

public interface AuditFragment {

    void appendAudit(
            String aggregateType,
            String aggregateId,
            String action
    );
}
~~~

Fragment nhận aggregateType và aggregateId tường minh. Vì hai repository có thể quản lý kiểu ID khác nhau (UUID và Long), dùng chuỗi ở contract audit giúp bảng log có một định dạng chung. Service chịu trách nhiệm chuyển ID thành chuỗi.

### 3.3. Viết implementation một lần

Tạo AuditFragmentImpl.java:

~~~java
package com.example.shared.repository;

import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.stereotype.Component;

@Component
public class AuditFragmentImpl implements AuditFragment {

    private final JdbcTemplate jdbc;

    public AuditFragmentImpl(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    @Override
    public void appendAudit(
            String aggregateType,
            String aggregateId,
            String action
    ) {
        jdbc.update("""
                INSERT INTO repository_audit (
                    aggregate_type,
                    aggregate_id,
                    action,
                    occurred_at
                )
                VALUES (?, ?, ?, CURRENT_TIMESTAMP)
                """,
                aggregateType,
                aggregateId,
                action
        );
    }
}
~~~

Tên implementation theo quy ước mặc định là tên fragment interface cộng hậu tố Impl: AuditFragment → AuditFragmentImpl. @Component đăng ký implementation thành một Spring bean để có thể được dùng lại. Constructor injection cung cấp JdbcTemplate.

Implementation này không giữ trạng thái theo request trong field; nó chỉ giữ dependency dùng chung và tạo câu lệnh cho mỗi lần gọi. Vì Spring bean mặc định là singleton, implementation dùng chung phải an toàn khi nhiều request gọi đồng thời.

### 3.4. Kế thừa fragment trong repository thứ nhất

~~~java
package com.example.customer;

import java.util.UUID;

import com.example.shared.repository.AuditFragment;
import org.springframework.data.repository.CrudRepository;

public interface CustomerRepository
        extends CrudRepository<Customer, UUID>, AuditFragment {
}
~~~

### 3.5. Kế thừa cùng fragment trong repository thứ hai

~~~java
package com.example.orders;

import com.example.shared.repository.AuditFragment;
import org.springframework.data.repository.CrudRepository;

public interface PurchaseOrderRepository
        extends CrudRepository<PurchaseOrder, Long>, AuditFragment {
}
~~~

Cả hai repository đều có method appendAudit(...). Ta không cần tạo CustomerAuditFragment và PurchaseOrderAuditFragment nếu contract và hành vi thực sự giống nhau.

## 4. Sử dụng fragment từ các repository

Service có thể gọi method của fragment như method repository bình thường:

~~~java
@Service
public class CustomerService {

    private final CustomerRepository customers;

    public CustomerService(CustomerRepository customers) {
        this.customers = customers;
    }

    @Transactional
    public Customer register(Customer customer) {
        Customer saved = customers.save(customer);

        customers.appendAudit(
                "Customer",
                saved.id().toString(),
                "CREATED"
        );

        return saved;
    }
}
~~~

Service khác dùng cùng fragment:

~~~java
@Service
public class PurchaseOrderService {

    private final PurchaseOrderRepository orders;

    public PurchaseOrderService(PurchaseOrderRepository orders) {
        this.orders = orders;
    }

    @Transactional
    public PurchaseOrder create(PurchaseOrder order) {
        PurchaseOrder saved = orders.save(order);

        orders.appendAudit(
                "PurchaseOrder",
                saved.id().toString(),
                "CREATED"
        );

        return saved;
    }
}
~~~

Hai service dùng hai repository khác nhau, nhưng phần ghi audit được triển khai một lần trong AuditFragmentImpl.

### 4.1. Fragment có cần biết repository cụ thể không?

Không nhất thiết. Ví dụ này truyền aggregateType và aggregateId vào method, vì vậy implementation không cần biết nó được ghép vào CustomerRepository hay PurchaseOrderRepository.

Ưu điểm:

- Không phụ thuộc vào domain class cụ thể.
- Có thể dùng lại với nhiều kiểu ID.
- Không cần một implementation riêng cho từng repository.
- Có thể kiểm thử độc lập bằng cách kiểm tra câu insert audit.

Nhược điểm là caller phải truyền đúng aggregateType. Nếu tên loại aggregate là dữ liệu quan trọng, có thể dùng enum hoặc một value object thay cho chuỗi tự do để giảm lỗi chính tả.

## 5. Tái sử dụng fragment implementation giữa nhiều repository

Có hai khía cạnh cần phân biệt:

- **Tái sử dụng contract:** nhiều repository cùng kế thừa một fragment interface.
- **Tái sử dụng implementation:** nhiều repository cùng dùng một implementation bean.

Trong ví dụ, CustomerRepository và PurchaseOrderRepository cùng kế thừa AuditFragment. AuditFragmentImpl được đăng ký thành Spring bean dùng chung. Spring Data repository composition ghép capability đó vào cả hai repository.

### 5.1. Vì sao đăng ký implementation thành bean?

Một fragment implementation là một Spring bean bình thường. Khi được quản lý bởi Spring:

- Có thể inject các dependency như JdbcTemplate, service hoặc publisher.
- Có thể được inject vào các bean khác nếu cần.
- Có thể được dùng lại bởi nhiều repository có cùng fragment interface.
- Có thể áp dụng cấu hình bean, proxy và lifecycle do Spring quản lý.

Trong dự án, @Component là một cách đăng ký. Cũng có thể khai báo bằng @Bean trong configuration nếu cần cấu hình constructor hoặc dependency đặc biệt. Khi dùng cách khai báo thủ công, bảo đảm bean được đặt tên và được Spring Data nhận diện theo quy ước fragment của phiên bản đang dùng.

### 5.2. Package và quy ước đặt tên

Spring Data thường tìm fragment implementation theo quy ước tên và phạm vi repository configuration. Mặc định, hậu tố implementation là Impl:

| Fragment interface | Implementation mặc định |
| --- | --- |
| AuditFragment | AuditFragmentImpl |
| CustomerSearchFragment | CustomerSearchFragmentImpl |
| SoftDeleteFragment | SoftDeleteFragmentImpl |

Implementation được đặt trong package được component scan và repository configuration nhận diện. Nếu fragment nằm trong package dùng chung, hãy bảo đảm package đó được scan hoặc đăng ký implementation thành bean tường minh.

Nếu dự án thay đổi repository implementation postfix, tên lớp fragment implementation phải tuân theo postfix đã cấu hình. Không tự đổi hậu tố tùy ý rồi kỳ vọng Spring Data tự tìm thấy.

### 5.3. Một implementation dùng chung phải stateless hoặc thread-safe

Vì một bean singleton có thể phục vụ nhiều repository và nhiều request cùng lúc, không lưu dữ liệu riêng của lần gọi trong field mutable:

~~~java
// Không nên: state của một request có thể bị request khác ghi đè.
private String currentAggregateId;
~~~

Thay vào đó:

- Truyền dữ liệu theo tham số method.
- Giữ dependency bất biến trong field final.
- Để transaction/context được quản lý ở đúng tầng.
- Nếu cần cấu hình riêng cho từng repository, dùng implementation/fragment chuyên biệt hoặc truyền cấu hình tường minh.

## 6. Chia sẻ fragment nhưng vẫn cho phép hành vi riêng

Không phải mọi repository đều phải dùng cùng một implementation. Có ba tình huống phổ biến.

### Tình huống A — Contract và implementation hoàn toàn giống nhau

Ví dụ AuditFragment: mọi repository đều ghi audit row theo cùng một schema và quy tắc. Dùng một fragment interface và một implementation bean chung.

### Tình huống B — Contract chung, implementation khác nhau

Hai repository cùng cần một capability, nhưng cách thực hiện phụ thuộc domain hoặc database schema. Có thể định nghĩa contract dùng chung rồi cung cấp implementation phù hợp theo repository configuration hoặc tạo các fragment chuyên biệt mở rộng contract chung.

Ví dụ:

~~~java
public interface SearchFragment<T> {
    List<T> search(String term);
}

public interface CustomerSearchFragment
        extends SearchFragment<Customer> {
}

public interface ProductSearchFragment
        extends SearchFragment<Product> {
}
~~~

Sau đó mỗi fragment chuyên biệt có implementation riêng. Cách này tránh ép một implementation generic phải đoán domain type hoặc tên bảng tại runtime.

### Tình huống C — Logic chung nằm ở service, không phải repository

Nếu capability không phải một phần hợp đồng truy cập dữ liệu, không cần ép nó thành repository fragment. Ví dụ chuẩn hóa tên, kiểm tra quyền, gửi email hoặc điều phối quy trình nghiệp vụ thường phù hợp hơn với application/domain service.

Fragment nên đại diện cho một capability mà caller có lý do hợp lý để gọi qua repository. Nếu method chỉ là tiện ích Java không liên quan đến persistence, một component/service riêng có thể làm API rõ hơn.

## 7. Fragment dùng chung với generic type

Một fragment có thể khai báo generic khi contract thật sự áp dụng cho nhiều kiểu domain:

~~~java
public interface ValidationFragment<T> {

    void validateBeforeWrite(T aggregate);
}
~~~

Implementation:

~~~java
public class ValidationFragmentImpl<T>
        implements ValidationFragment<T> {

    private final AggregateValidator<T> validator;

    public ValidationFragmentImpl(AggregateValidator<T> validator) {
        this.validator = validator;
    }

    @Override
    public void validateBeforeWrite(T aggregate) {
        validator.validate(aggregate);
    }
}
~~~

Đây là ví dụ về generic contract và dependency chung. Trong thực tế, việc chọn đúng validator cho từng aggregate cần một cơ chế phân giải rõ ràng, chẳng hạn registry theo kiểu domain hoặc implementation chuyên biệt. Không giả định Spring Data tự truyền domain type cụ thể vào constructor generic của fragment implementation.

Nếu mỗi aggregate có validator riêng, một thiết kế rõ hơn là dùng các fragment chuyên biệt hoặc gọi validator trong application service trước khi save. Đừng tạo generic fragment chỉ để tránh vài dòng code nếu việc phân giải kiểu khiến implementation khó hiểu.

## 8. Kết hợp nhiều fragment trong cùng repository

Một repository có thể kết hợp nhiều fragment độc lập:

~~~java
public interface CustomerRepository
        extends CrudRepository<Customer, UUID>,
                AuditFragment,
                CustomerSearchFragment,
                CustomerExportFragment {
}
~~~

Mỗi fragment nên có một trách nhiệm:

| Fragment | Trách nhiệm |
| --- | --- |
| AuditFragment | Ghi nhận thao tác audit |
| CustomerSearchFragment | Tìm customer theo quy tắc tìm kiếm đặc thù |
| CustomerExportFragment | Truy vấn dữ liệu phục vụ export |

Không cần tạo một interface duy nhất với hàng chục method tùy chỉnh. Tách capability giúp repository chỉ ghép những phần nó thực sự cần.

### 8.1. Trùng method signature giữa các fragment

Nếu nhiều fragment cùng cung cấp method có chữ ký giống nhau, composition có thể trở nên khó hiểu vì thứ tự fragment ảnh hưởng đến implementation được chọn. Tránh thiết kế hai fragment không liên quan cùng định nghĩa một method signature nhưng kỳ vọng Spring Data tự phân biệt ý định.

Nếu thực sự cần override một method, hãy xác định rõ precedence và kiểm thử repository composition. Trong phần lớn trường hợp, đổi tên method hoặc hợp nhất contract sẽ dễ bảo trì hơn.

## 9. Fragment và @NoRepositoryBean khác nhau thế nào?

Hai cơ chế đều dùng interface, nhưng mục đích khác nhau:

| Cơ chế | Mục đích | Ví dụ |
| --- | --- | --- |
| Generic base repository + @NoRepositoryBean | Chia sẻ hợp đồng nền cho các repository con | BaseRepository<T, ID> |
| Repository fragment | Ghép một capability tùy chọn vào repository | AuditFragment |
| Repository fragment implementation | Cung cấp hành vi cho capability | AuditFragmentImpl |
| Custom repository base class | Thay đổi implementation nền mà repository proxy sử dụng | Một base class tùy chỉnh kế thừa implementation phù hợp của module |

Base repository thường là cha chung của các repository. Fragment là một phần có thể ghép hoặc bỏ tùy nhu cầu. Fragment interface không cần được xem như repository độc lập; không thêm @NoRepositoryBean chỉ vì tên của nó kết thúc bằng chữ Repository hoặc vì nó được nhiều repository kế thừa.

Ví dụ:

~~~java
@NoRepositoryBean
public interface BaseRepository<T, ID>
        extends CrudRepository<T, ID> {
    // Hợp đồng chung cho mọi repository con.
}

public interface AuditFragment {
    void appendAudit(String type, String id, String action);
}

public interface CustomerRepository
        extends BaseRepository<Customer, UUID>, AuditFragment {
}
~~~

Ở đây, base repository cung cấp CRUD contract tổng quát; audit fragment cung cấp một capability bổ sung.

## 10. Fragment và default method

Một số logic có thể được viết trực tiếp bằng Java default method:

~~~java
public interface FindRequiredById<T, ID> {

    Optional<T> findById(ID id);

    default T findRequiredById(ID id) {
        return findById(id).orElseThrow();
    }
}
~~~

Default method phù hợp khi logic đơn giản và có thể xây dựng từ method khác. Fragment implementation phù hợp khi cần dependency, SQL, dịch vụ hoặc thuật toán riêng.

Không cần tạo implementation class cho một method chỉ gọi findById rồi ném exception nếu default method đã thể hiện đủ ý định. Ngược lại, một fragment dùng JdbcTemplate hoặc publisher cần implementation để cung cấp hành vi.

## 11. Dùng JDBC trực tiếp trong fragment: transaction và ranh giới aggregate

Ví dụ AuditFragmentImpl dùng JdbcTemplate để ghi bảng audit. Nếu service gọi save và appendAudit trong cùng một phương thức @Transactional, hai thao tác có thể tham gia cùng transaction khi:

- Repository và JdbcTemplate dùng cùng DataSource.
- Chúng dùng transaction manager tương ứng.
- Lời gọi đi qua ranh giới transaction đang hoạt động.

Khi đó, nếu insert audit lỗi và exception kích hoạt rollback, thao tác save aggregate cũng rollback.

Tuy nhiên, JdbcTemplate không thực hiện aggregate mapping. Nó không tự gọi hành vi domain, không đồng bộ collection con và không tự áp dụng optimistic locking của đường lưu aggregate. Vì vậy:

- Chỉ dùng JDBC trực tiếp trong fragment khi capability thực sự thao tác trên bảng ngoài aggregate hoặc khi đã thiết kế rõ quy tắc ghi.
- Nếu fragment cần thay đổi aggregate, cân nhắc JdbcAggregateTemplate hoặc delegate sang application/domain service có trách nhiệm.
- Không dùng fragment như đường tắt để cập nhật bảng con và bỏ qua invariant của aggregate root.
- Không giả định @Transactional trên một method fragment tự giải quyết mọi transaction; xác định ranh giới ở use case và cùng transaction manager.

## 12. Khi nào fragment không phải lựa chọn phù hợp?

Không phải mọi phần code dùng chung đều nên là repository fragment.

| Nhu cầu | Lựa chọn thường phù hợp hơn |
| --- | --- |
| Chia sẻ CRUD contract generic | Base repository interface |
| Thêm một capability repository có implementation | Repository fragment |
| Thay đổi cách mọi repository thực hiện các method lõi | Custom repository base class |
| Điều phối nhiều repository hoặc nhiều aggregate | Application service |
| Kiểm tra invariant của một aggregate | Domain model/domain service |
| Gửi email, gọi HTTP hoặc publish message | Application service/event publisher/outbox |
| Truy vấn báo cáo phức tạp không thuộc aggregate | DAO dùng JdbcTemplate hoặc query riêng |
| Hàm tiện ích thuần Java | Component/service/helper phù hợp |

Một fragment không nên trở thành nơi điều phối cả use case. Ví dụ, approveOrderAndNotifyCustomer() thường thuộc application service vì nó phối hợp thay đổi đơn hàng, audit và thông báo; không nên đặt toàn bộ quy trình đó vào repository chỉ để tái sử dụng.

## 13. Kiểm thử fragment dùng chung

Nên kiểm thử cả implementation và việc ghép fragment vào từng repository.

### 13.1. Kiểm thử implementation

Với AuditFragmentImpl, có thể dùng integration test với database để xác nhận một lần gọi tạo đúng một audit row:

~~~java
@DataJdbcTest
class AuditFragmentImplTest {

    @Autowired
    JdbcTemplate jdbc;

    @Test
    void writesAuditEntry() {
        AuditFragment fragment = new AuditFragmentImpl(jdbc);

        fragment.appendAudit("Customer", "customer-42", "CREATED");

        Integer count = jdbc.queryForObject("""
                SELECT COUNT(*)
                FROM repository_audit
                WHERE aggregate_type = ?
                  AND aggregate_id = ?
                  AND action = ?
                """,
                Integer.class,
                "Customer",
                "customer-42",
                "CREATED"
        );

        assertThat(count).isEqualTo(1);
    }
}
~~~

Đây là skeleton minh họa; test cần schema và dependency assertion phù hợp trong dự án. Nếu implementation được inject qua Spring, có thể dùng context test để kiểm tra wiring thay vì tự tạo instance như ví dụ.

### 13.2. Kiểm thử repository composition

Kiểm tra cả hai repository đều có thể gọi method fragment:

~~~java
@SpringBootTest
class SharedAuditFragmentIntegrationTest {

    @Autowired
    CustomerRepository customers;

    @Autowired
    PurchaseOrderRepository orders;

    @Test
    void fragmentIsAvailableOnBothRepositories() {
        customers.appendAudit("Customer", "c-1", "CREATED");
        orders.appendAudit("PurchaseOrder", "42", "CREATED");

        // Đọc audit table và xác nhận cả hai entry tồn tại.
    }
}
~~~

Test này xác nhận Spring Data đã ghép fragment vào cả hai repository. Nó cũng giúp phát hiện lỗi package scanning, tên implementation hoặc bean wiring.

### 13.3. Kiểm thử transaction chung

Thêm một integration test service để xác nhận:

1. Service lưu aggregate.
2. Fragment ghi audit.
3. Cố tình làm audit insert thất bại.
4. Transaction rollback cả hai thao tác nếu chúng dùng chung DataSource/transaction manager.

Không chỉ kiểm thử fragment method riêng lẻ; kiểm thử use case mới chứng minh được ranh giới transaction như thiết kế.

## 14. Những lỗi thường gặp

| Triệu chứng | Nguyên nhân có thể | Cách xử lý |
| --- | --- | --- |
| Repository không có method fragment | Repository chưa kế thừa fragment interface hoặc composition không tìm thấy implementation | Kiểm tra extends, tên implementation, package scan và bean registration. |
| Spring không tìm thấy fragment implementation | Tên class không theo postfix hoặc class nằm ngoài phạm vi tìm kiếm | Dùng tên FragmentNameImpl, cấu hình postfix đúng hoặc đăng ký bean theo quy ước. |
| Hai repository có cùng fragment nhưng một repository lỗi | Fragment implementation chỉ được scan trong một phạm vi package | Đặt implementation ở package được scan chung hoặc đăng ký bean dùng chung. |
| Implementation không được inject dependency | Class được tạo ngoài Spring context hoặc wiring không đúng | Đăng ký implementation thành Spring bean và dùng constructor injection. |
| Dữ liệu request bị lẫn giữa các repository | Implementation singleton lưu state mutable theo lần gọi | Giữ implementation stateless/thread-safe; truyền state qua tham số. |
| Method bị implementation khác ghi đè | Nhiều fragment có cùng method signature | Tránh signature trùng hoặc xác định rõ thứ tự composition và kiểm thử. |
| Fragment dùng JDBC nhưng aggregate không nhất quán | SQL trực tiếp bỏ qua invariant hoặc version | Chuyển sang aggregate operation hoặc bảo vệ điều kiện/version một cách tường minh. |
| Audit commit dù aggregate rollback | Hai thao tác dùng transaction manager/resource khác nhau hoặc propagation độc lập | Dùng cùng DataSource/transaction manager và propagation phù hợp. |
| Fragment chứa quá nhiều nghiệp vụ | Repository đang bị dùng như application service | Tách orchestration sang service; giữ fragment là capability truy cập dữ liệu rõ ràng. |

## 15. Quy trình thiết kế fragment có thể tái sử dụng

Khi nhận thấy nhiều repository có code trùng nhau, hãy làm theo trình tự:

1. **Xác định capability:** các repository có thực sự cần cùng một hành vi hay chỉ tình cờ có method giống tên?
2. **Tạo interface nhỏ:** mô tả contract độc lập với aggregate cụ thể nếu có thể.
3. **Chọn implementation:** dùng chung một implementation nếu semantics giống nhau; nếu khác, tạo fragment chuyên biệt.
4. **Quản lý bean:** đăng ký implementation bằng component scan hoặc cấu hình Spring phù hợp.
5. **Ghép vào repository:** cho từng repository cần capability kế thừa fragment interface.
6. **Kiểm tra composition:** xác nhận method xuất hiện trên repository proxy và không xung đột method khác.
7. **Xác định transaction:** nếu fragment ghi database, bảo đảm nó tham gia transaction của use case khi cần.
8. **Bảo vệ aggregate:** không để SQL trực tiếp phá vỡ invariant hoặc bỏ qua version.
9. **Kiểm thử tái sử dụng:** kiểm tra tất cả repository dùng fragment, không chỉ implementation riêng lẻ.

## 16. Bài tập tự thực hành

**Bài tập 1 — Tạo fragment dùng chung.** Tạo AuditFragment và AuditFragmentImpl, sau đó cho CustomerRepository và PurchaseOrderRepository cùng kế thừa fragment.

**Bài tập 2 — Xác nhận composition.** Inject cả hai repository và gọi appendAudit. Kiểm tra repository proxy cung cấp method từ fragment.

**Bài tập 3 — Bean dùng chung.** Đăng ký implementation thành một Spring bean, inject JdbcTemplate qua constructor và xác nhận implementation có thể được dùng bởi cả hai repository.

**Bài tập 4 — Fragment thứ hai.** Tạo SearchFragment cho một capability tìm kiếm thực sự dùng chung. Chọn rõ liệu implementation có thể dùng chung hay cần implementation riêng cho từng domain.

**Bài tập 5 — Method signature xung đột.** Tạo hai fragment cùng khai báo một method signature, quan sát composition và giải thích vì sao nên tránh thiết kế này hoặc xác định precedence tường minh.

**Bài tập 6 — Transaction.** Gọi save aggregate và append audit trong cùng service @Transactional. Làm audit insert thất bại và xác nhận aggregate rollback trên cùng database.

**Bài tập 7 — Chọn đúng abstraction.** Với một method tiện ích, một query báo cáo, một capability repository dùng chung và một use case phối hợp nhiều aggregate, quyết định nên dùng default method, DAO, fragment hay application service.

## 17. Ghi nhớ

Repository fragment cho phép ghép một capability tùy chỉnh vào repository mà không cần đưa tất cả method vào một base interface lớn. Nhiều repository có thể cùng kế thừa một fragment interface; nếu implementation có semantics giống nhau và được đăng ký thành Spring bean, chúng có thể dùng chung một implementation.

Giữ fragment interface nhỏ, đặt tên implementation theo quy ước, bảo đảm package/bean được Spring Data nhận diện và giữ implementation an toàn khi chạy đồng thời. Dùng fragment cho hành vi thực sự thuộc contract repository; để application service điều phối use case và để aggregate root bảo vệ invariant. Nếu fragment dùng JDBC trực tiếp, hãy chủ động quản lý transaction, version và những quy tắc mà đường aggregate persistence thường đảm nhiệm.
