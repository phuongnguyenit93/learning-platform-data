# So sánh một-nhiều dùng khóa ngoại và bảng liên kết

## 1. Bài toán quan hệ một-nhiều

Quan hệ một-nhiều (one-to-many, 1:N) mô tả tình huống một đối tượng cha có thể liên kết với nhiều đối tượng con, còn mỗi đối tượng con thuộc về tối đa một đối tượng cha trong phạm vi quan hệ đó.

Ví dụ, một phòng ban có nhiều nhân viên:

- Một Department có thể có 0, 1 hoặc nhiều Employee.
- Một Employee thuộc về tối đa một Department.
- Phòng ban có thể tồn tại trước khi có nhân viên.
- Nhân viên có thể được phép chưa thuộc phòng ban nào, tùy quy tắc nghiệp vụ.

Trong database quan hệ, có hai cách biểu diễn phổ biến:

1. Đặt khóa ngoại ở bảng phía nhiều, tức bảng Employee có cột department_id trỏ tới Department.
2. Tạo một bảng liên kết riêng, ví dụ department_employee, lưu cặp department_id và employee_id.

Cả hai cách đều có thể biểu diễn quan hệ một-nhiều, nhưng chúng khác nhau về ràng buộc dữ liệu, cách ánh xạ JPA, quyền sở hữu quan hệ, câu SQL và chi phí bảo trì.

## 2. Cách 1: Khóa ngoại ở bảng phía nhiều

### 2.1. Thiết kế database

Đây là cách tự nhiên nhất khi mỗi nhân viên chỉ thuộc tối đa một phòng ban. Khóa ngoại đặt trong bảng Employee:

```sql
create table department (
    id bigint generated by default as identity primary key,
    name varchar(150) not null
);

create table employee (
    id bigint generated by default as identity primary key,
    name varchar(150) not null,
    department_id bigint,
    constraint fk_employee_department
        foreign key (department_id) references department(id)
);

create index idx_employee_department_id
    on employee(department_id);
```

Cột department_id nằm ở bảng Employee vì Employee là phía nhiều. Một hàng Employee chỉ có một giá trị department_id, nên không thể trỏ đồng thời tới nhiều phòng ban.

Nếu nghiệp vụ bắt buộc mọi nhân viên phải thuộc một phòng ban, có thể khai báo department_id NOT NULL. Nếu nhân viên được phép chưa được phân công, để cột nullable. Khóa ngoại bảo đảm giá trị khác null phải tham chiếu tới một phòng ban tồn tại.

Ràng buộc khóa ngoại bảo đảm nhân viên không tham chiếu phòng ban không tồn tại. Nó không bảo đảm mỗi phòng ban phải có ít nhất một nhân viên; một phòng ban không có nhân viên vẫn là dữ liệu hợp lệ.

### 2.2. Ánh xạ hai chiều bằng JPA

Mô hình phổ biến là đặt ManyToOne ở phía Employee và OneToMany ở phía Department:

```java
@Entity
@Table(name = "department")
public class Department {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String name;

    @OneToMany(
        mappedBy = "department",
        cascade = CascadeType.PERSIST,
        orphanRemoval = true
    )
    private List<Employee> employees = new ArrayList<>();

    protected Department() {
    }

    public Department(String name) {
        this.name = name;
    }

    public void addEmployee(Employee employee) {
        employees.add(employee);
        employee.setDepartment(this);
    }

    public void removeEmployee(Employee employee) {
        employees.remove(employee);
        employee.setDepartment(null);
    }

    public Long getId() {
        return id;
    }

    public List<Employee> getEmployees() {
        return Collections.unmodifiableList(employees);
    }
}
```

```java
@Entity
@Table(name = "employee")
public class Employee {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String name;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "department_id")
    private Department department;

    protected Employee() {
    }

    public Employee(String name) {
        this.name = name;
    }

    void setDepartment(Department department) {
        this.department = department;
    }

    public Long getId() {
        return id;
    }

    public String getName() {
        return name;
    }

    public Department getDepartment() {
        return department;
    }
}
```

Trong ví dụ này:

- Employee.department là phía sở hữu quan hệ (owning side), vì mapping khóa ngoại nằm tại ManyToOne.
- Department.employees dùng mappedBy = "department", nghĩa là phía inverse. Giá trị mappedBy là tên thuộc tính Java trong Employee, không phải tên cột department_id.
- Khi thay đổi quan hệ, cần cập nhật thuộc tính department ở phía Employee để JPA ghi đúng khóa ngoại.
- Helper addEmployee và removeEmployee cập nhật cả hai phía để object graph trong bộ nhớ nhất quán.

Nếu chỉ gọi department.getEmployees().add(employee) mà không đặt employee.department, phía sở hữu không thay đổi. JPA có thể không ghi department_id như mong muốn. Đây là lỗi phổ biến khi dùng quan hệ hai chiều.

### 2.3. Vì sao ManyToOne thường là owning side?

Khóa ngoại nằm trong bảng Employee. Khi cần gán nhân viên vào phòng ban, database cần cập nhật employee.department_id. Vì vậy thuộc tính tương ứng với cột khóa ngoại nằm ở Employee và đây là phía sở hữu mapping.

Department chỉ biểu diễn chiều điều hướng từ cha tới con. mappedBy báo cho provider rằng phía Department không sở hữu một khóa ngoại hoặc join table riêng.

Đặt ManyToOne ở phía sở hữu thường đơn giản hơn về SQL và phù hợp với cấu trúc relational: mỗi hàng con lưu trực tiếp khóa ngoại của cha.

### 2.4. Quan hệ một chiều dùng khóa ngoại

Nếu ứng dụng chỉ cần đi từ Department tới Employee và không cần thuộc tính department trong Employee, có thể ánh xạ OneToMany một chiều với JoinColumn:

```java
@Entity
public class Department {

    @Id
    @GeneratedValue
    private Long id;

    @OneToMany
    @JoinColumn(name = "department_id")
    private List<Employee> employees = new ArrayList<>();

    protected Department() {
    }
}
```

JoinColumn chỉ ra khóa ngoại nằm trong bảng đích Employee. Trong cách ánh xạ này, collection ở Department điều khiển association; Employee không cần thuộc tính tham chiếu ngược.

Lưu ý: OneToMany một chiều không có JoinColumn thường dùng join table theo quy ước mặc định của JPA. Nếu muốn khóa ngoại ở bảng con, cần khai báo JoinColumn như ví dụ trên.

SQL chính xác do provider phát ra có thể khác nhau. Một số mapping một chiều với khóa ngoại có thể khiến provider thực hiện thêm câu UPDATE để gắn khóa ngoại sau khi insert. Hãy kiểm tra SQL và ràng buộc NOT NULL với provider đang dùng. Nếu cần quan hệ hai chiều và muốn thao tác khóa ngoại rõ ràng, ManyToOne ở phía con thường dễ dự đoán hơn.

## 3. Cách 2: Bảng liên kết riêng

### 3.1. Thiết kế database

Thay vì đặt department_id trong Employee, tạo bảng department_employee để lưu liên kết:

```sql
create table department (
    id bigint generated by default as identity primary key,
    name varchar(150) not null
);

create table employee (
    id bigint generated by default as identity primary key,
    name varchar(150) not null
);

create table department_employee (
    department_id bigint not null,
    employee_id bigint not null,
    constraint pk_department_employee
        primary key (department_id, employee_id),
    constraint uk_department_employee_employee
        unique (employee_id),
    constraint fk_department_employee_department
        foreign key (department_id) references department(id),
    constraint fk_department_employee_employee
        foreign key (employee_id) references employee(id)
);
```

Điểm quyết định để đây thực sự là một-nhiều là ràng buộc UNIQUE(employee_id). Nó bảo đảm một Employee xuất hiện tối đa một lần trong bảng liên kết, tức không thể thuộc đồng thời nhiều Department.

Nếu bỏ ràng buộc duy nhất này, cùng một employee_id có thể xuất hiện với nhiều department_id. Khi đó cấu trúc cho phép nhiều-nhiều, dù tên bảng hoặc annotation được đặt là one-to-many.

Bảng liên kết có một khác biệt quan trọng so với khóa ngoại trực tiếp: Employee có thể tồn tại mà không có hàng nào trong department_employee. Khóa ngoại và unique constraint chỉ bảo đảm một liên kết hợp lệ và tối đa một cha; chúng không bắt buộc mỗi Employee phải có liên kết. Nếu nghiệp vụ yêu cầu mọi nhân viên phải thuộc một phòng ban, cần thêm quy tắc kiểm soát ở database hoặc ứng dụng phù hợp.

### 3.2. Ánh xạ OneToMany một chiều bằng JoinTable

Ví dụ Department quản lý collection Employee thông qua bảng liên kết:

```java
@Entity
@Table(name = "department")
public class Department {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String name;

    @OneToMany
    @JoinTable(
        name = "department_employee",
        joinColumns = @JoinColumn(name = "department_id"),
        inverseJoinColumns = @JoinColumn(name = "employee_id"),
        uniqueConstraints = @UniqueConstraint(
            name = "uk_department_employee_employee",
            columnNames = "employee_id"
        )
    )
    private Set<Employee> employees = new HashSet<>();

    protected Department() {
    }

    public Department(String name) {
        this.name = name;
    }

    public void addEmployee(Employee employee) {
        employees.add(employee);
    }

    public void removeEmployee(Employee employee) {
        employees.remove(employee);
    }
}
```

```java
@Entity
@Table(name = "employee")
public class Employee {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String name;

    protected Employee() {
    }

    public Employee(String name) {
        this.name = name;
    }
}
```

Trong JoinTable:

- joinColumns mô tả cột tham chiếu tới entity nguồn Department.
- inverseJoinColumns mô tả cột tham chiếu tới entity đích Employee.
- uniqueConstraints đặt ràng buộc duy nhất trên employee_id để duy trì cardinality một-nhiều.

JPA mapping mô tả ý định ở tầng object; schema thực tế vẫn cần có constraint tương ứng. Nếu schema được quản lý bằng Flyway hoặc Liquibase, hãy tạo unique constraint trong migration và để Hibernate validate schema.

Nếu dùng Set, cần thiết kế equals/hashCode của Employee an toàn cho entity và trạng thái ID trước/sau persist. Nếu không cần tính duy nhất ở tầng Java, List cũng có thể dùng; khi cần lưu thứ tự, phải cân nhắc @OrderColumn. Không nên chọn Set chỉ để hy vọng database tự bảo đảm duy nhất.

### 3.3. Khi nào join table là hợp lý?

Join table có thể hữu ích khi:

- Không thể hoặc không muốn thêm cột khóa ngoại vào bảng Employee do schema legacy hoặc bảng con được dùng bởi nhiều hệ thống.
- Liên kết được quản lý độc lập với dữ liệu Employee.
- Cần tách việc phân công/ghép nối khỏi bảng entity gốc.
- Có kế hoạch biến liên kết thành một thực thể nghiệp vụ riêng.
- Database hiện tại đã thiết kế association table và ứng dụng phải tương thích với schema đó.

Tuy nhiên, join table tạo thêm một bảng và một bước join khi cần tìm quan hệ. Với mô hình đơn giản trong đó mỗi Employee thuộc tối đa một Department, khóa ngoại ở Employee thường ít phức tạp hơn.

## 4. So sánh hai cách biểu diễn

| Tiêu chí | Khóa ngoại ở bảng con | Bảng liên kết |
|---|---|---|
| Vị trí quan hệ | employee.department_id | department_employee |
| Số bảng | Không cần bảng liên kết riêng | Thêm một bảng |
| Cardinality 1:N | Một cột FK trên mỗi Employee | UNIQUE(employee_id) trong bảng liên kết |
| Mỗi child có tối đa một parent | Được cấu trúc FK thể hiện trực tiếp | Được unique constraint bảo đảm |
| Child bắt buộc có parent | Có thể dùng FK NOT NULL | Cần quy tắc bổ sung; một child có thể không có hàng liên kết |
| Truy vấn theo parent | Lọc trực tiếp employee.department_id | Join qua bảng liên kết |
| Gán/chuyển parent | Cập nhật FK của Employee | Cập nhật hàng liên kết |
| Thay đổi schema | Thêm FK vào bảng con | Không cần thêm FK vào bảng entity con |
| Độ phức tạp | Thường thấp hơn | Cao hơn do quản lý thêm association table |
| Mở rộng thuộc tính liên kết | Cần chuyển sang association entity nếu có thuộc tính quan hệ | Có thể tiến hóa thành association entity |

Với dữ liệu mới và quan hệ đơn giản, foreign key mapping thường là lựa chọn đầu tiên. Join table nên được chọn khi có lý do về schema, quyền sở hữu hoặc vòng đời của chính association.

## 5. Owning side và mappedBy

Trong JPA, owning side là phía quyết định thay đổi association được ghi xuống database. Khái niệm này không đồng nghĩa với object cha trong mô hình nghiệp vụ.

### 5.1. Với khóa ngoại trực tiếp

Trong mapping hai chiều:

- Employee.department là owning side vì chứa @JoinColumn.
- Department.employees là inverse side vì có mappedBy = "department".

Khi thêm nhân viên:

```java
Department department = ...;
Employee employee = new Employee("An");

department.addEmployee(employee);

entityManager.persist(department);
entityManager.flush();
```

Nếu cascade persist được cấu hình từ Department sang Employee, entity mới có thể được persist cùng parent. Quan trọng là helper addEmployee phải đặt Employee.department để owning side được cập nhật.

Nếu không dùng helper, cần tự đặt cả hai phía:

```java
department.getEmployees().add(employee);
employee.setDepartment(department);
```

Không nên expose collection mutable rộng rãi nếu nhiều tầng có thể cập nhật một phía và làm object graph mất nhất quán.

### 5.2. Với join table

Trong ví dụ OneToMany + JoinTable một chiều, collection Department.employees là phía quản lý association table. Thêm hoặc xóa phần tử khỏi collection làm thay đổi các hàng trong department_employee.

Không có Employee.department để đồng bộ, nên code đơn giản hơn ở object graph. Đổi lại, mọi truy vấn từ Employee về Department phải đi qua association table hoặc được mô hình hóa thêm.

### 5.3. Vì sao mappedBy không phải tên cột?

Trong ví dụ:

```java
@OneToMany(mappedBy = "department")
private List<Employee> employees;
```

department là tên thuộc tính Java trong Employee:

```java
@ManyToOne
@JoinColumn(name = "department_id")
private Department department;
```

department_id mới là tên cột trong database. Ghi mappedBy = "department_id" là sai vì mappedBy tham chiếu thuộc tính mapping của entity phía owning, không phải tên cột SQL.

## 6. Cascade và orphanRemoval không quyết định cách lưu quan hệ

Cascade và orphanRemoval là các quy tắc vòng đời entity. Chúng không thay thế owning side và cũng không quyết định quan hệ được lưu bằng foreign key hay join table.

### 6.1. Cascade

Ví dụ:

```java
@OneToMany(
    mappedBy = "department",
    cascade = {CascadeType.PERSIST, CascadeType.MERGE}
)
private List<Employee> employees = new ArrayList<>();
```

Cascade PERSIST nghĩa là persist Department có thể lan tới Employee liên quan; cascade MERGE áp dụng tương tự cho merge. Cascade REMOVE làm thao tác remove parent lan tới child; CascadeType.ALL bao gồm tất cả loại cascade.

Không nên dùng ALL một cách máy móc. Nếu Employee có thể được dùng độc lập hoặc được tham chiếu từ nơi khác, cascade REMOVE có thể xóa dữ liệu ngoài ý muốn.

### 6.2. orphanRemoval

Với quan hệ one-to-many thể hiện child thuộc quyền sở hữu vòng đời của parent, orphanRemoval có thể xóa child khi nó bị loại khỏi association:

```java
@OneToMany(
    mappedBy = "department",
    cascade = CascadeType.PERSIST,
    orphanRemoval = true
)
private List<Employee> employees = new ArrayList<>();
```

Khi remove một Employee khỏi collection và đồng bộ persistence context, provider sẽ xóa entity con theo semantics orphan removal. Điều này phù hợp khi Employee thực sự là child riêng của Department.

Nếu chỉ muốn chuyển Employee từ Department A sang Department B, cần hiểu quy tắc orphanRemoval và cập nhật quan hệ trong cùng transaction. Không dùng orphanRemoval khi child có thể được chia sẻ hoặc cần tồn tại độc lập sau khi bỏ liên kết.

### 6.3. Xóa hàng liên kết khác với xóa entity con

Với join table, xóa một association row chỉ gỡ liên kết. Nó không nhất thiết xóa Employee. Nếu cấu hình orphanRemoval, provider có thể xóa cả entity con khi child trở thành orphan theo quan hệ. Hai hành vi này khác nhau và phải được thiết kế theo nghiệp vụ.

Tương tự, ON DELETE CASCADE trong database là referential action của database; cascade remove trong JPA là quy tắc lan truyền thao tác qua persistence context. Không nên nhầm lẫn hai cơ chế.

## 7. Truy vấn và hiệu năng

### 7.1. Lấy danh sách con theo parent

Với foreign key:

```sql
select e.*
from employee e
where e.department_id = ?;
```

Với join table:

```sql
select e.*
from employee e
join department_employee de on de.employee_id = e.id
where de.department_id = ?;
```

Foreign key mapping có ít bước hơn. Join table cần thêm join, nhưng với index đúng và lượng dữ liệu phù hợp, database vẫn có thể thực thi hiệu quả.

### 7.2. Index cần thiết

Với foreign key, thường tạo index trên employee.department_id vì truy vấn phổ biến lọc theo phòng ban.

Với join table, primary key (department_id, employee_id) hỗ trợ tìm employee theo department. Unique index trên employee_id hỗ trợ truy vấn chiều ngược và bảo đảm mỗi employee chỉ có tối đa một liên kết.

Không phải mọi database tự động tạo index cho foreign key. Hãy kiểm tra schema và execution plan thay vì giả định index đã có.

### 7.3. N+1 và fetch strategy

Dù dùng foreign key hay join table, lazy loading vẫn có thể gây N+1 nếu tải danh sách Department rồi lần lượt truy cập employees của từng phòng ban.

Giải pháp cần dựa trên use case:
- Fetch join khi cần tải parent và child trong cùng truy vấn.
- EntityGraph để chỉ định fetch plan.
- DTO projection khi màn hình chỉ cần một số trường.
- Batch fetching khi cần tải quan hệ cho nhiều parent mà không join toàn bộ.

Không nên đổi mọi quan hệ sang EAGER để tránh N+1. Điều đó có thể tải dư dữ liệu và làm truy vấn khó kiểm soát. Với collection fetch join kết hợp pagination, cần đặc biệt kiểm tra kết quả vì join có thể nhân số dòng parent theo số child.

### 7.4. Thay đổi collection lớn

Khi collection rất lớn, không nên luôn tải toàn bộ danh sách chỉ để thêm hoặc xóa một liên kết. Cần thiết kế use case cập nhật theo ID hoặc câu lệnh phù hợp, đồng thời kiểm tra SQL provider sinh ra.

Với OneToMany một chiều dùng join table, cách provider đồng bộ collection có thể tạo thêm thao tác xóa/thêm hàng liên kết. Với collection lớn, điều này có thể tốn kém. Hãy kiểm tra SQL thực tế trên Hibernate và cân nhắc association entity hoặc thao tác SQL chuyên biệt nếu workload yêu cầu.

## 8. Khi bảng liên kết nên trở thành một Entity riêng

Nếu quan hệ có thuộc tính riêng, ví dụ thời điểm phân công, vai trò của nhân viên trong phòng ban, người duyệt hoặc trạng thái hiệu lực, association không còn chỉ là một cặp khóa.

Khi đó, mô hình hóa bảng liên kết thành entity:

```java
@Entity
@Table(name = "department_assignment")
public class DepartmentAssignment {

    @Id
    @GeneratedValue
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "department_id", nullable = false)
    private Department department;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "employee_id", nullable = false)
    private Employee employee;

    @Column(nullable = false)
    private LocalDate assignedAt;

    @Column(nullable = false)
    private String role;

    protected DepartmentAssignment() {
    }
}
```

Mô hình này biến association thành đối tượng nghiệp vụ có vòng đời và dữ liệu riêng. Có thể đặt unique constraint trên employee_id nếu một nhân viên chỉ có một assignment hiện hành, hoặc dùng khóa/constraint phức tạp hơn nếu cần lưu lịch sử nhiều lần phân công.

Khi association có thuộc tính, đừng cố ép nó vào @ManyToMany hoặc một JoinTable ẩn. Entity liên kết tường minh giúp validation, audit, query và transaction rõ ràng hơn.

## 9. Những quyết định cần kiểm tra trước khi chọn

Hãy trả lời các câu hỏi sau:

1. Một child có được thuộc nhiều parent cùng lúc không? Nếu không, foreign key trực tiếp là biểu diễn tự nhiên; join table phải có unique constraint trên child key.
2. Child có bắt buộc phải có parent không? Foreign key NOT NULL có thể bảo đảm điều này trực tiếp; join table cần thêm quy tắc khác.
3. Child có vòng đời độc lập không? Nếu có, cẩn trọng với cascade REMOVE và orphanRemoval.
4. Có cần điều hướng từ child về parent không? Nếu có, mapping hai chiều với ManyToOne thường phù hợp.
5. Có lý do schema để không thêm foreign key vào bảng child không? Nếu có, join table có thể phù hợp.
6. Association có thuộc tính riêng không? Nếu có, cân nhắc association entity.
7. Query thường xuyên theo parent hay child? Thiết kế index theo hướng truy vấn.
8. Collection có thể rất lớn không? Nếu có, tránh tải toàn bộ collection cho thao tác đơn giản.
9. Schema do Hibernate hay migration quản lý? Constraint cardinality phải được tạo và kiểm tra ở database.

## 10. Kết luận

Với quan hệ một-nhiều đơn giản, khóa ngoại ở bảng phía nhiều thường là lựa chọn rõ ràng và hiệu quả. Nó biểu diễn trực tiếp rằng mỗi child có tối đa một parent; NOT NULL có thể bắt buộc child phải có parent, còn index hỗ trợ truy vấn theo parent.

Bảng liên kết hữu ích khi schema không thể hoặc không nên đặt khóa ngoại trực tiếp trong bảng child, khi association được quản lý độc lập hoặc khi cần tiến hóa thành một entity riêng. Để giữ đúng cardinality một-nhiều, cần unique constraint trên khóa child trong bảng liên kết; nếu thiếu constraint này, database thực tế cho phép nhiều-nhiều.

Trong JPA, hiểu owning side, mappedBy, JoinColumn, JoinTable, cascade và orphanRemoval là điều thiết yếu. Hãy đồng bộ đúng phía sở hữu, đặt constraint tại database, kiểm tra SQL do provider sinh ra và chọn fetch plan theo use case thực tế.
