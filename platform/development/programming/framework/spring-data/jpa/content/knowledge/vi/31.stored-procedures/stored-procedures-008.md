# Kiểm thử thủ tục trên đúng hệ quản trị mục tiêu

## 1. Vì sao phải kiểm thử trên đúng DBMS?

Stored procedure là chương trình được lưu và thực thi bên trong hệ quản trị cơ sở dữ liệu (DBMS). Spring Data JPA có thể gọi thủ tục qua annotation **@Procedure** hoặc API **StoredProcedureQuery**; JDBC cũng có thể gọi qua **CallableStatement**. Tuy nhiên, cú pháp SQL, kiểu dữ liệu, tham số, quyền thực thi, cách trả kết quả và hành vi transaction phụ thuộc vào DBMS và phiên bản cụ thể.

Một bài test chạy thành công trên H2 chưa chứng minh thủ tục sẽ chạy đúng trên PostgreSQL, MySQL, SQL Server, Oracle hoặc DB2. H2 có parser, kiểu dữ liệu, hàm, quy tắc transaction và khả năng hỗ trợ thủ tục riêng. Một số lệnh có thể chạy trong H2 nhưng lỗi trên DBMS mục tiêu; một tính năng riêng của DBMS mục tiêu cũng có thể không tồn tại trong H2.

Nguyên tắc kiểm thử:

- Chạy integration test với cùng họ DBMS mà production sử dụng.
- Cố gắng khớp phiên bản, image, extension và cấu hình quan trọng.
- Dùng đúng JDBC driver và migration SQL được triển khai ở production.
- Kiểm tra cả lời gọi từ Java lẫn kết quả thật trong database.
- Kiểm tra quyền của tài khoản ứng dụng, transaction, lỗi và các trường hợp biên.

**Ví dụ trong bài:** phần code minh họa dùng PostgreSQL 16 và Testcontainers. Đây là ví dụ cụ thể để dễ thực hành; nếu hệ thống chạy MySQL, SQL Server, Oracle hoặc một phiên bản PostgreSQL khác, hãy thay image, driver, DDL và cấu hình theo đúng môi trường production. Đề bài không chỉ rõ DBMS của dự án, vì vậy PostgreSQL trong ví dụ không phải giả định về database thực tế.

## 2. Xác định chính xác môi trường cần mô phỏng

Trước khi viết test, lấy thông tin từ cấu hình triển khai và DBA/DevOps:

| Thuộc tính | Cần xác định |
|---|---|
| DBMS | PostgreSQL, MySQL, MariaDB, SQL Server, Oracle, DB2... |
| Phiên bản | Phiên bản production đang chạy |
| JDBC driver | Driver và phiên bản ứng dụng sử dụng |
| Schema/catalog | Schema chứa procedure, table, sequence và type |
| Extensions/plugins | Extension hoặc tính năng database bắt buộc |
| Charset/collation | Quy tắc so sánh, sắp xếp và mã hóa ký tự |
| Time zone | Time zone của server, session và ứng dụng |
| Isolation | Mức isolation và thiết lập transaction |
| User/privileges | Tài khoản ứng dụng có quyền EXECUTE và quyền trên dữ liệu nào |
| SQL mode/settings | Chế độ tương thích và cấu hình ảnh hưởng cú pháp/hành vi |

Kiểm tra phiên bản database trong test bằng JDBC metadata để tránh vô tình kết nối nhầm H2 hoặc một database khác:

```java
try (Connection connection = dataSource.getConnection()) {
    DatabaseMetaData metadata = connection.getMetaData();

    assertEquals("PostgreSQL", metadata.getDatabaseProductName());
    System.out.println(metadata.getDatabaseProductVersion());
}
```

Đổi giá trị mong đợi theo DBMS thực tế. Có thể kiểm tra thêm server version bằng câu SQL riêng của vendor, ví dụ PostgreSQL dùng SELECT version() hoặc SHOW server_version. Không chỉ dựa vào tên JDBC URL: hãy kiểm tra metadata của connection mà Spring thực sự sử dụng.

## 3. Đặt procedure trong migration có thể tái lập

Stored procedure là đối tượng thuộc schema database. Hãy quản lý DDL của procedure cùng migration của bảng và kiểu dữ liệu, thường bằng Flyway hoặc Liquibase. Test phải chạy đúng các migration này trước khi gọi procedure.

Ví dụ dưới đây là migration PostgreSQL:

Tệp: src/main/resources/db/migration/V1__payment_audit.sql

```sql
CREATE SCHEMA IF NOT EXISTS app;

CREATE TABLE app.payment_audit (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    invoice_id VARCHAR(40) NOT NULL,
    amount NUMERIC(12, 2) NOT NULL,
    recorded_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE OR REPLACE PROCEDURE app.record_payment(
    IN p_invoice_id VARCHAR(40),
    IN p_amount NUMERIC(12, 2)
)
LANGUAGE plpgsql
AS $$
BEGIN
    IF p_invoice_id IS NULL OR p_amount IS NULL OR p_amount <= 0 THEN
        RAISE EXCEPTION 'amount must be positive';
    END IF;

    INSERT INTO app.payment_audit(invoice_id, amount)
    VALUES (p_invoice_id, p_amount);
END;
$$;
```

Procedure nhận mã hóa đơn và số tiền, từ chối giá trị null hoặc số tiền không dương, rồi thêm một dòng vào bảng audit. Procedure không tự commit transaction; transaction của lời gọi quyết định khi nào dữ liệu được commit hoặc rollback.

Trong dự án thực tế:

- Đặt migration procedure cạnh migration schema mà nó phụ thuộc.
- Dùng đúng schema và tên đối tượng; tránh phụ thuộc ngầm vào search_path hoặc default schema.
- Nếu procedure gọi function, sequence, view hoặc procedure khác, tạo dependency trong migration trước khi tạo procedure.
- Kiểm tra quyền EXECUTE và quyền trên các bảng mà procedure sử dụng.
- Không dùng Hibernate ddl-auto=create để thay thế migration procedure. Hibernate tạo schema entity không phải công cụ quản lý đầy đủ DDL của routine.
- Khi sửa chữ ký procedure, chú ý migration phải xử lý kiểu tham số, overload, quyền và các caller đang sử dụng.

Với MySQL, SQL Server, Oracle và DBMS khác, phải viết migration bằng cú pháp tương ứng. Ví dụ PostgreSQL dùng CALL để gọi procedure, còn function được gọi bằng SELECT; SQL Server thường dùng EXEC; MySQL dùng CALL. Không thể thay tên DBMS trong JDBC URL rồi mong cùng một file SQL hoạt động ở mọi nơi.

## 4. Tạo database thật bằng Testcontainers

Testcontainers khởi chạy database tạm thời trong container, cung cấp JDBC URL, username và password cho test rồi dọn container sau khi test kết thúc. Cách này giúp developer và CI chạy cùng một loại database mà không phải dùng chung một database test cố định.

Với Testcontainers 2.x và Gradle, có thể khai báo các dependency test như sau:

```groovy
dependencies {
    testImplementation platform("org.testcontainers:testcontainers-bom:2.0.5")
    testImplementation "org.testcontainers:testcontainers-junit-jupiter"
    testImplementation "org.testcontainers:testcontainers-postgresql"
}
```

Ứng dụng vẫn cần PostgreSQL JDBC driver tương ứng, thường đã có ở runtime nếu production dùng PostgreSQL. Module Testcontainers không tự mang JDBC driver vào classpath. Dùng BOM để các module Testcontainers có cùng phiên bản. Nếu dự án đang dùng Testcontainers 1.x, dependency và package class khác 2.x; hãy nâng cấp đồng bộ hoặc giữ đúng bộ API theo phiên bản hiện có, không trộn artifact 1.x và 2.x.

Testcontainers 2.x dùng package PostgreSQL container là **org.testcontainers.postgresql.PostgreSQLContainer**. Test hoàn chỉnh ở phần sau dùng JUnit Jupiter và Spring TestContext.

Image postgres:16.4-alpine là phiên bản ví dụ có thể tái lập. Hãy thay bằng image và phiên bản khớp production; trong pipeline quan trọng có thể pin digest thay vì tag có thể thay đổi. Nếu production dùng extension như PostGIS, pgvector hoặc image do vendor cung cấp, dùng image tương thích có cài đúng extension. Nếu production là dịch vụ database managed có tính năng riêng mà image local không mô phỏng được, bổ sung integration test trên môi trường test do nhà cung cấp hoặc đội vận hành cấp.

**@DynamicPropertySource** đăng ký URL và thông tin kết nối động trước khi Spring tạo ApplicationContext. Nếu ứng dụng cấu hình Flyway bằng URL/user/password riêng (spring.flyway.url, spring.flyway.user, spring.flyway.password), cũng phải trỏ Flyway vào cùng database container. Nếu không, ứng dụng có thể chạy migration vào database khác với database mà test đang gọi.

Đặt migration trong vị trí production đang sử dụng, ví dụ src/main/resources/db/migration, để test chạy cùng bộ migration. Nếu dùng Flyway, thêm Flyway dependency và cấu hình datasource phù hợp. Có thể đặt spring.jpa.hibernate.ddl-auto=validate để kiểm tra mapping entity với schema đã được migration tạo.

## 5. Gọi procedure qua Spring Data JPA bằng @Procedure

Spring Data JPA hỗ trợ khai báo procedure bằng **@Procedure** trên repository method. Metadata procedure có thể khai báo trực tiếp trên method hoặc qua **@NamedStoredProcedureQuery** của entity.

Ví dụ ánh xạ procedure PostgreSQL đã tạo ở trên:

```java
import java.math.BigDecimal;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.NamedStoredProcedureQuery;
import jakarta.persistence.ParameterMode;
import jakarta.persistence.StoredProcedureParameter;
import jakarta.persistence.Table;

@Entity
@Table(name = "payment_audit", schema = "app")
@NamedStoredProcedureQuery(
    name = "PaymentAudit.recordPayment",
    procedureName = "app.record_payment",
    parameters = {
        @StoredProcedureParameter(
            mode = ParameterMode.IN,
            name = "p_invoice_id",
            type = String.class
        ),
        @StoredProcedureParameter(
            mode = ParameterMode.IN,
            name = "p_amount",
            type = BigDecimal.class
        )
    }
)
public class PaymentAudit {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    protected PaymentAudit() {
    }
}
```

Repository tham chiếu tên JPA đã khai báo:

```java
import java.math.BigDecimal;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.query.Procedure;
import org.springframework.data.repository.query.Param;

public interface PaymentAuditRepository
        extends JpaRepository<PaymentAudit, Long> {

    @Procedure(name = "PaymentAudit.recordPayment")
    void recordPayment(
            @Param("p_invoice_id") String invoiceId,
            @Param("p_amount") BigDecimal amount
    );
}
```

Annotation **@NamedStoredProcedureQuery** có hai tên khác nhau:

- **name** là tên JPA dùng để tham chiếu trong EntityManager/repository.
- **procedureName** là tên thực tế của procedure trong database.

Vì vậy, @Procedure(name = "PaymentAudit.recordPayment") tham chiếu tên metadata JPA, còn procedureName = "app.record_payment" chỉ đến đối tượng database. Nếu dùng @Procedure(procedureName = "...") trực tiếp trên method thì đang tham chiếu thẳng procedure trong database và bỏ qua metadata @NamedStoredProcedureQuery.

Gọi procedure trong service có transaction rõ ràng:

```java
import java.math.BigDecimal;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class PaymentProcedureService {

    private final PaymentAuditRepository repository;

    public PaymentProcedureService(PaymentAuditRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public void recordPayment(String invoiceId, BigDecimal amount) {
        repository.recordPayment(invoiceId, amount);
    }

    @Transactional
    public void recordThenFail(String invoiceId, BigDecimal amount) {
        repository.recordPayment(invoiceId, amount);
        throw new IllegalStateException("Force rollback for integration test");
    }
}
```

Đặt transaction ở service giúp kiểm tra rõ procedure tham gia transaction của use case. Repository query method tự khai báo không nên được mặc định coi là đã có transaction chỉ vì nó nằm trong JpaRepository; ranh giới transaction ở service làm ý định rõ ràng và cho phép phối hợp nhiều thao tác.

## 6. Kiểm tra kết quả thực tế trong database

Một test tốt phải gọi procedure qua đúng đường đi mà ứng dụng dùng, sau đó truy vấn database để xác nhận side effect hoặc kết quả trả về. Không chỉ kiểm tra method được gọi bằng Mockito.

Ví dụ integration test hoàn chỉnh:

```java
import java.math.BigDecimal;
import java.sql.Connection;
import java.sql.DatabaseMetaData;
import java.sql.SQLException;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.test.context.DynamicPropertyRegistry;
import org.springframework.test.context.DynamicPropertySource;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;
import org.testcontainers.postgresql.PostgreSQLContainer;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertThrows;

@Testcontainers
@SpringBootTest
class PaymentProcedureIntegrationTest {

    @Container
    static final PostgreSQLContainer postgres =
            new PostgreSQLContainer("postgres:16.4-alpine")
                    .withDatabaseName("app")
                    .withUsername("app_user")
                    .withPassword("app_password");

    @DynamicPropertySource
    static void databaseProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
    }

    @Autowired
    private PaymentProcedureService service;

    @Autowired
    private JdbcTemplate jdbcTemplate;

    @BeforeEach
    void cleanRows() {
        jdbcTemplate.update("DELETE FROM app.payment_audit");
    }

    @Test
    void connectsToTheExpectedDatabaseProduct() throws SQLException {
        try (Connection connection =
                     jdbcTemplate.getDataSource().getConnection()) {
            DatabaseMetaData metadata = connection.getMetaData();
            assertEquals("PostgreSQL", metadata.getDatabaseProductName());
        }
    }

    @Test
    void procedureInsertsAuditRow() {
        service.recordPayment("INV-100", new BigDecimal("25.50"));

        Integer count = jdbcTemplate.queryForObject(
                "SELECT COUNT(*) FROM app.payment_audit WHERE invoice_id = ?",
                Integer.class,
                "INV-100"
        );

        assertEquals(1, count);
    }

    @Test
    void procedureParticipatesInCallerTransaction() {
        assertThrows(
                IllegalStateException.class,
                () -> service.recordThenFail(
                        "INV-ROLLBACK", new BigDecimal("12.00"))
        );

        Integer count = jdbcTemplate.queryForObject(
                "SELECT COUNT(*) FROM app.payment_audit WHERE invoice_id = ?",
                Integer.class,
                "INV-ROLLBACK"
        );

        assertEquals(0, count);
    }
}
```

Test này dùng một container tĩnh cho cả class, nạp datasource động, dọn dữ liệu trước mỗi test, xác nhận DBMS, gọi procedure và kiểm tra dữ liệu đã lưu. Cần có migration tạo schema/procedure và các bean/entity/repository/service ở phần trước. Test không đánh dấu @Transactional để truy vấn sau khi service trả về nhìn thấy kết quả đã commit. Test rollback xác minh lệnh insert do procedure thực hiện bị rollback cùng transaction của service khi exception thoát ra.

Nếu dùng @DataJpaTest, Spring Boot có thể thay datasource bằng database nhúng theo cấu hình test. Khi dùng Testcontainers, cần cấu hình để giữ datasource container (ví dụ @AutoConfigureTestDatabase(replace = Replace.NONE) nếu phù hợp với phiên bản Boot) và nạp migration/cấu hình procedure. Với @SpringBootTest, datasource thường được lấy từ cấu hình ứng dụng và DynamicPropertySource có thể ghi đè URL/credentials.

## 7. Kiểm thử bằng JDBC khi cần kiểm soát lời gọi thấp hơn

Không phải procedure nào cũng ánh xạ thuận tiện qua @Procedure. Khi cần điều khiển kiểu tham số, OUT/INOUT, cursor hoặc tính năng riêng của driver, có thể dùng JDBC CallableStatement hoặc JdbcTemplate.

Ví dụ gọi procedure PostgreSQL chỉ có IN parameter bằng JDBC:

```java
import java.math.BigDecimal;
import java.sql.PreparedStatement;
import org.springframework.jdbc.core.ConnectionCallback;
import org.springframework.jdbc.core.JdbcTemplate;

public class PaymentProcedureJdbcClient {

    private final JdbcTemplate jdbcTemplate;

    public PaymentProcedureJdbcClient(JdbcTemplate jdbcTemplate) {
        this.jdbcTemplate = jdbcTemplate;
    }

    public void record(String invoiceId, BigDecimal amount) {
        jdbcTemplate.execute((ConnectionCallback<Void>) connection -> {
            try (PreparedStatement statement = connection.prepareStatement(
                    "CALL app.record_payment(?, ?)")) {
                statement.setString(1, invoiceId);
                statement.setBigDecimal(2, amount);
                statement.execute();
            }
            return null;
        });
    }
}
```

Đây là ví dụ PostgreSQL dùng CALL cho procedure; không dùng cú pháp này để gọi function PostgreSQL, vốn được gọi trong biểu thức SELECT. Với DBMS khác, có thể cần CallableStatement với cú pháp escape {call ...}, EXEC hoặc API của driver. Luôn xác nhận cách gọi theo tài liệu driver đang dùng.

Nếu procedure có OUT parameter, CallableStatement thường cần đăng ký kiểu dữ liệu trước khi execute và đọc giá trị sau khi thực thi. Cú pháp, thứ tự đăng ký và cách lấy ResultSet phụ thuộc driver. Hãy viết test cho cả giá trị trả về lẫn side effect trong database.

## 8. IN, OUT, INOUT, ResultSet và cursor

Procedure có thể có nhiều kiểu tham số:

- **IN**: ứng dụng truyền giá trị vào.
- **OUT**: procedure trả giá trị ra.
- **INOUT**: nhận giá trị đầu vào và trả giá trị đã thay đổi.
- **REF_CURSOR/cursor**: trả tập kết quả theo cơ chế hỗ trợ của DBMS/driver.
- **ResultSet**: procedure có thể trả một hoặc nhiều tập kết quả tùy database và API.

Với Spring Data JPA:

- Nếu procedure có một OUT parameter, giá trị đó có thể được trả về trực tiếp từ repository method.
- Nếu có nhiều OUT parameter được khai báo trong @NamedStoredProcedureQuery, Spring Data JPA có thể trả Map với key là tên tham số.
- Nếu procedure trả ResultSet, các OUT parameter có thể bị bỏ qua vì method chỉ có một giá trị trả về; trường hợp cần nhiều OUT parameter có thể dùng Map theo metadata phù hợp.
- REF_CURSOR và kiểu cursor có yêu cầu riêng từ JPA provider, dialect và database. Không giả định mapping của một vendor hoạt động trên vendor khác.

Ví dụ metadata có IN và OUT:

```java
@NamedStoredProcedureQuery(
    name = "Invoice.calculateTotal",
    procedureName = "app.calculate_total",
    parameters = {
        @StoredProcedureParameter(
            mode = ParameterMode.IN,
            name = "p_invoice_id",
            type = Long.class
        ),
        @StoredProcedureParameter(
            mode = ParameterMode.OUT,
            name = "p_total",
            type = BigDecimal.class
        )
    }
)
@Entity
public class Invoice {
    @Id
    private Long id;
}
```

Repository có thể trả OUT parameter duy nhất:

```java
@Procedure(name = "Invoice.calculateTotal")
BigDecimal calculateTotal(@Param("p_invoice_id") Long invoiceId);
```

Đây là ví dụ mapping JPA minh họa; DDL của procedure và khả năng hỗ trợ OUT parameter cần được viết đúng cho DBMS mục tiêu. Với PostgreSQL, quy tắc CALL cho OUT argument phụ thuộc phiên bản: các phiên bản hiện đại yêu cầu cung cấp vị trí tham số OUT trong danh sách CALL (thường truyền NULL ở SQL trực tiếp); các phiên bản cũ có giới hạn khác. Hãy xác minh cú pháp với phiên bản production thay vì dùng một ví dụ SQL chung.

## 9. Các khác biệt DBMS cần kiểm thử

| Khu vực | Ví dụ vấn đề | Cách kiểm tra |
|---|---|---|
| Cú pháp gọi | CALL, EXEC, SELECT function, JDBC escape syntax | Gọi qua driver thật của DBMS |
| Kiểu dữ liệu | NUMBER/DECIMAL, UUID, JSON, ARRAY, enum, date/time | Kiểm tra round-trip và giá trị biên |
| Tham số | IN, OUT, INOUT, cursor, null | Kiểm tra số lượng, thứ tự, tên, kiểu và giá trị |
| Result set | Một hoặc nhiều result set, cursor | Kiểm tra số dòng, thứ tự cột và kiểu trả về |
| Tên đối tượng | Schema, catalog, chữ hoa/thường, overload | Gọi bằng tên đầy đủ, kiểm tra search path |
| Quyền | EXECUTE, quyền trên bảng, definer/invoker | Chạy test bằng tài khoản giống ứng dụng |
| Transaction | Commit, rollback, savepoint, procedure tự điều khiển transaction | Kiểm tra kết quả sau commit/rollback |
| Locking | Deadlock, lock timeout, isolation | Chạy kịch bản nhiều transaction khi có ý nghĩa |
| Thời gian | Time zone, timestamp precision, daylight saving | Test giá trị ở ranh giới thời gian |
| Collation | So sánh chuỗi, accent, Unicode, thứ tự sắp xếp | Test dữ liệu tiếng Việt và ký tự đặc biệt |
| Error handling | SQLState, vendor error code, exception mapping | Gây lỗi có chủ đích và xác minh lỗi Java |
| Migration | DDL, overload, grants, dependency | Khởi tạo database rỗng chỉ bằng migration |

Ví dụ đặc thù PostgreSQL:

- Procedure được tạo bằng CREATE PROCEDURE và gọi bằng CALL; function được gọi bằng SELECT.
- CALL hỗ trợ tham số OUT và trả một hàng kết quả chứa giá trị OUT theo quy tắc PostgreSQL.
- Người dùng cần quyền EXECUTE trên procedure.
- Nếu CALL chạy trong transaction block tường minh, procedure không thể thực hiện lệnh điều khiển transaction như COMMIT hoặc ROLLBACK bên trong. Một service Spring có @Transactional thường gọi procedure trong transaction đó, vì vậy procedure có logic tự commit cần được thiết kế và gọi theo cách khác.
- Kiểm tra schema qualification, search_path và quyền của user thực thi; procedure tồn tại chưa có nghĩa user ứng dụng gọi được.

Các điểm này khác nhau giữa các phiên bản PostgreSQL và càng khác giữa các họ DBMS. Không copy nguyên SQL hoặc giả định về transaction từ PostgreSQL sang Oracle, SQL Server hay MySQL.

## 10. Thiết kế bộ test có giá trị

Một bộ integration test cho procedure nên có các nhóm sau:

| Nhóm test | Ví dụ dữ liệu/kịch bản | Điều cần khẳng định |
|---|---|---|
| Happy path | Tham số hợp lệ | Procedure chạy, dữ liệu/kết quả đúng |
| Boundary | Số tiền 0, âm, cực đại, chuỗi dài sát giới hạn | Quy tắc nghiệp vụ và kiểu dữ liệu đúng |
| Null/optional | Tham số null, tham số có default | Hành vi đúng với SQL NULL và default |
| OUT/INOUT | Giá trị đầu vào và kết quả đầu ra | Java nhận đúng kiểu và giá trị |
| Result set | 0 dòng, 1 dòng, nhiều dòng | Mapping, thứ tự và kiểu cột đúng |
| Constraint | Khóa ngoại, unique, not-null | Lỗi database được xử lý đúng |
| Transaction | Thành công, exception giữa chừng, rollback | Side effect đúng theo ranh giới transaction |
| Permission | User không có EXECUTE hoặc thiếu quyền bảng | Lỗi quyền được phát hiện như mong đợi |
| Concurrency | Hai lời gọi cập nhật cùng một bản ghi | Locking và isolation không làm sai dữ liệu |
| Version compatibility | Chạy trên phiên bản production | SQL và procedure API tương thích thực tế |

Không cần viết mọi tổ hợp dữ liệu cho mỗi procedure. Chọn ca test theo nhánh logic, ràng buộc dữ liệu và rủi ro của procedure. Với procedure cập nhật số dư, tồn kho hoặc trạng thái thanh toán, nên có ca gọi lặp, cập nhật đồng thời và rollback để kiểm tra tính đúng đắn.

Nếu procedure xử lý một batch, kiểm tra cả batch rỗng, batch có phần tử lỗi, thứ tự xử lý, tính idempotent và cách báo cáo lỗi từng phần. Không giả định procedure sẽ rollback toàn bộ batch nếu nó tự xử lý exception và tiếp tục.

## 11. Quản lý dữ liệu test và tính lặp lại

Testcontainers tạo database mới cho vòng đời container, nhưng các test trong cùng container vẫn có thể dùng chung dữ liệu. Cần chuẩn bị trạng thái rõ ràng:

- Chạy migration từ database rỗng để xác nhận có thể tạo schema và procedure từ đầu.
- Mỗi test tạo fixture riêng bằng mã định danh duy nhất hoặc dọn dữ liệu trong @BeforeEach.
- Dọn bảng theo đúng thứ tự quan hệ khóa ngoại; cân nhắc TRUNCATE/sequence reset theo cú pháp DBMS.
- Không dựa vào thứ tự test chạy.
- Không dùng dữ liệu production hoặc thông tin bí mật production làm fixture.
- Nếu test chạy song song, tránh dùng chung khóa dữ liệu; tạo schema/database riêng hoặc tên định danh duy nhất.
- Nếu procedure có side effect ngoài database (gửi email, gọi API, publish message), kiểm soát dependency đó trong môi trường test và xác minh side effect theo đúng ranh giới.

Có thể dùng @Sql để nạp fixture hoặc cleanup, nhưng script phải tương thích DBMS mục tiêu. Với procedure, migration thường phù hợp hơn @Sql vì procedure là một phần của schema version và phải được triển khai giống production.

Nếu procedure tự commit, ghi ra database khác hoặc sử dụng autonomous transaction, cleanup bằng rollback test không đủ. Hãy tạo dữ liệu test có thể nhận diện và dọn rõ ràng sau test, đồng thời kiểm tra riêng side effect ngoài transaction chính.

## 12. Chạy trên CI

Để integration test hữu ích trong pipeline:

1. Cài Docker-compatible runtime hoặc cấu hình Testcontainers Cloud/runtime được hỗ trợ.
2. Pin DB image, Testcontainers BOM và JDBC driver.
3. Chạy migration trên database rỗng.
4. Chạy integration test với profile dành riêng cho test.
5. Thu thập log container và SQLState/vendor code khi test fail.
6. Không để test vô tình trỏ vào database production hoặc database chia sẻ.
7. Nếu cần extension hoặc cấu hình server riêng, tạo image/config test được version control.
8. Chạy nhóm test nhỏ cho pull request và nhóm đầy đủ trên pipeline chính nếu thời gian khởi động database lớn.

Testcontainers cần Docker API-compatible runtime hoặc môi trường container tương thích. Nếu CI không có Docker, hãy dùng database test do pipeline cung cấp hoặc một môi trường integration riêng có version được kiểm soát. Không thay database mục tiêu bằng H2 rồi đánh dấu test procedure là đã xác minh trên DBMS production.

## 13. Phân biệt unit test, repository test và integration test

| Loại test | Có database mục tiêu? | Phát hiện được gì? |
|---|---|---|
| Unit test service với mock repository | Không | Luồng điều khiển, xử lý exception, phối hợp service |
| Repository test với H2 | Không phải DBMS production | Một phần mapping JPA và truy vấn SQL portable |
| Integration test với Testcontainers | Có, nếu image đúng | Cú pháp procedure, driver, mapping, quyền, transaction và kết quả thật |
| Test trên môi trường DB managed tương đương production | Có, gần môi trường triển khai | Extension, cấu hình managed service và khác biệt khó mô phỏng bằng container |

Các tầng test bổ trợ nhau. Unit test chạy nhanh và phù hợp kiểm tra logic Java; integration test với database đúng loại là bằng chứng cần thiết cho procedure phụ thuộc vendor. Không cần chuyển mọi unit test sang Testcontainers, nhưng không dùng mock hoặc H2 làm bằng chứng cho stored procedure.

## 14. Lỗi thường gặp và cách khắc phục

| Lỗi | Nguyên nhân | Hướng xử lý |
|---|---|---|
| Procedure không tồn tại | Migration chưa chạy, sai schema hoặc sai tên | Kiểm tra migration history, schema và tên procedure đầy đủ |
| Function/procedure mismatch | Dùng SELECT cho procedure hoặc CALL cho function | Xác định đúng loại routine và cú pháp DBMS |
| Test pass trên H2 nhưng fail production | SQL/dialect/kiểu dữ liệu khác nhau | Chạy integration test trên DBMS mục tiêu |
| Không đủ quyền thực thi | Test dùng tài khoản owner nhưng ứng dụng dùng user hạn chế | Tạo role test giống quyền ứng dụng và kiểm tra GRANT |
| Sai số lượng/thứ tự tham số | Mapping JPA hoặc JDBC không khớp chữ ký procedure | Đối chiếu metadata IN/OUT/INOUT và kiểu JDBC |
| OUT parameter trả null hoặc sai kiểu | Provider/driver xử lý khác nhau, tên hoặc thứ tự sai | Viết test riêng cho từng OUT parameter trên driver mục tiêu |
| Dữ liệu vẫn tồn tại sau rollback test | Procedure tự commit hoặc side effect nằm ngoài transaction | Kiểm tra transaction control và thiết kế cleanup rõ ràng |
| Procedure timeout hoặc deadlock | Lock lâu, transaction chồng lấn hoặc thiếu index | Kiểm tra execution plan, lock wait và isolation trên DBMS thật |
| Test chạy không ổn định | Dữ liệu dùng chung, test song song, image không pin | Cô lập fixture và pin môi trường |
| Flyway chạy nhầm database | Datasource và Flyway có URL riêng | Trỏ cả hai vào cùng container |

Khi test thất bại, ghi lại thông tin hữu ích: DBMS product/version, JDBC driver version, tên procedure và schema, tham số (đã loại dữ liệu nhạy cảm), SQLState, vendor error code, migration version và transaction context. Không log mật khẩu, token hoặc dữ liệu cá nhân nhạy cảm.

## 15. Checklist trước khi coi procedure đã được kiểm thử

- [ ] Test kết nối đúng DBMS và phiên bản đã chọn.
- [ ] JDBC driver là driver mà ứng dụng thực tế sử dụng.
- [ ] Migration tạo được schema, bảng và procedure từ database rỗng.
- [ ] Test gọi procedure qua đúng API ứng dụng sử dụng: @Procedure, EntityManager hoặc JDBC.
- [ ] Test xác minh side effect/kết quả bằng truy vấn database.
- [ ] IN, OUT, INOUT, null, kiểu dữ liệu và ResultSet được kiểm tra khi procedure có sử dụng.
- [ ] User chạy test có quyền giống tài khoản ứng dụng.
- [ ] Commit, rollback và lỗi nghiệp vụ được kiểm tra.
- [ ] Các phụ thuộc vendor như extension, collation, time zone và SQL mode được mô phỏng khi cần.
- [ ] CI có runtime phù hợp và không kết nối nhầm database production.

## 16. Ghi nhớ

- Stored procedure phụ thuộc DBMS; kiểm thử bằng H2 không thay thế integration test trên database mục tiêu.
- Testcontainers giúp chạy database thật trong container, nhưng cần pin đúng image/version và cấu hình.
- Dùng migration production để tạo procedure trong test; không để test và production có hai định nghĩa SQL khác nhau.
- Kiểm tra cả lời gọi Java, dữ liệu thực tế, tham số, quyền, lỗi và transaction.
- @Procedure thuận tiện cho mapping Spring Data JPA; JDBC phù hợp khi cần kiểm soát chi tiết driver và tham số.
- Nếu DBMS là dịch vụ managed hoặc có extension riêng, bổ sung test trên môi trường tương đương production.
