# Thêm nhiều hàng theo lô bằng `SimpleJdbcInsert`

> **Chủ đề:** Spring Framework Data Access → `SimpleJdbcInsert` → Thêm nhiều hàng theo lô. Mục tiêu: cấu hình một `SimpleJdbcInsert`, chuẩn bị nhiều bộ tham số, gọi `executeBatch(...)`, đánh giá update counts, dùng transaction và xử lý lỗi khi chỉ một phần lô ghi thành công.

## 1. Batch insert giải quyết vấn đề gì?

Khi import file chứa nhiều mặt hàng, ghi các dòng của một đơn hàng hoặc nhập danh sách bản ghi, ta thường cần tạo nhiều hàng trong **cùng một bảng**. Việc lặp `execute(...)` cho từng phần tử gây nhiều lời gọi xuống JDBC và cơ sở dữ liệu. Batch insert cho phép cung cấp **nhiều bộ tham số cho cùng cấu trúc `INSERT`** để JDBC driver có thể xử lý hiệu quả hơn.

`SimpleJdbcInsert` (gói `org.springframework.jdbc.core.simple`) dùng `DataSource` hoặc `JdbcTemplate` và metadata của cơ sở dữ liệu để tạo câu `INSERT` với tham số bind. Nó có API cho một hàng và cho nhiều hàng:

```java
// Chèn một hàng, trả về số hàng bị ảnh hưởng.
int execute(Map<String, ?> args);

// Chèn nhiều hàng, trả về update counts của từng phần tử.
int[] executeBatch(Map<String, ?>... batch);
int[] executeBatch(SqlParameterSource... batch);
```

`SqlParameterSource` nằm trong `org.springframework.jdbc.core.namedparam`. Hai overload `executeBatch` đều nhận các bản ghi cùng bảng/cùng tập cột và trả về `int[]` theo thứ tự các phần tử gửi vào.

**Không nhầm lẫn ba khái niệm:**
- **JDBC batch:** một prepared SQL `INSERT`, nhiều bộ giá trị; driver có thể thực thi riêng hoặc tối ưu gom lệnh.
- **Multi-row SQL:** một câu lệnh có dạng `INSERT INTO t(a,b) VALUES (?,?),(?,?)`. `SimpleJdbcInsert.executeBatch` không hứa luôn sinh ra dạng SQL này.
- **Bulk load:** các cơ chế đặc thù của DB (như `COPY`, `LOAD DATA`) có thể phù hợp hơn cho khối dữ liệu rất lớn, nhưng không thuộc API `SimpleJdbcInsert`.

Batch insert thường giúp giảm overhead, nhưng mức tăng tốc phụ thuộc driver, DB, index, trigger, kích thước batch và cấu hình connection. Không có đảm bảo một batch sẽ nhanh hơn N lần so với N lệnh đơn.

## 2. Bảng ví dụ và cấu hình `SimpleJdbcInsert`

Giả sử ta chèn các dòng hàng hóa của một phiên import. Dùng schema minh họa tương thích H2:

```sql
CREATE TABLE order_item (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    import_id VARCHAR(64) NOT NULL,
    line_no INTEGER NOT NULL,
    sku VARCHAR(64) NOT NULL,
    quantity INTEGER NOT NULL CHECK (quantity > 0),
    CONSTRAINT uq_import_line UNIQUE (import_id, line_no)
);
```

Cột `id` do DB tự sinh. Bốn cột còn lại chứa dữ liệu từ từng hàng input. Ràng buộc `UNIQUE(import_id, line_no)` ngăn trùng số dòng trong một lần import.

Trong lớp repository/writer đã được cung cấp `DataSource`, cấu hình:

```java
import javax.sql.DataSource;
import org.springframework.jdbc.core.simple.SimpleJdbcInsert;

public final class OrderItemWriter {
    private final SimpleJdbcInsert insert;

    public OrderItemWriter(DataSource dataSource) {
        this.insert = new SimpleJdbcInsert(dataSource)
            .withTableName("order_item")
            .usingColumns("import_id", "line_no", "sku", "quantity");
    }
}
```

Đây là **đoạn code tích hợp**; class hoàn chỉnh còn cần method ghi. `withTableName` chọn bảng đích; `usingColumns` chỉ rõ cột sẽ xuất hiện trong câu `INSERT` và loại trừ cột `id` do DB sinh. Chỉ dùng tên bảng/cột từ cấu hình tin cậy; không đưa tên bảng do người dùng gửi vào trực tiếp.

Nếu bảng thuộc schema riêng, có thể thêm `withSchemaName(...)`. Thông thường `SimpleJdbcInsert` đọc `DatabaseMetaData` từ JDBC driver để xây dựng câu lệnh. Khi metadata không đầy đủ, chỉ định rõ cột và cân nhắc `withoutTableColumnMetaDataAccess()` theo DB/driver thực tế. Nên cấu hình instance **một lần** ở tầng data access rồi tái sử dụng; không tạo instance mới cho từng hàng.

Trước khi gọi API, validate những ràng buộc có ý nghĩa nghiệp vụ: `import_id` hợp lệ, `sku` đúng định dạng, `quantity > 0` và không có `line_no` trùng trong dữ liệu import. Vẫn cần constraint DB vì có thể xảy ra lỗi đồng thời hoặc dữ liệu không hợp lệ lọt qua tầng ứng dụng.

## 3. Cách A — `executeBatch(Map<String, ?>...)`

Mỗi `Map` chứa tên cột và giá trị cho **một hàng**. Trong method đã có field `insert`:

```java
import java.util.Map;

int[] counts = insert.executeBatch(
    Map.of(
        "import_id", "IMPORT-001",
        "line_no", 1,
        "sku", "BOOK-01",
        "quantity", 2
    ),
    Map.of(
        "import_id", "IMPORT-001",
        "line_no", 2,
        "sku", "PEN-05",
        "quantity", 4
    )
);
```

Với H2 và những insert hợp lệ đơn giản, kết quả thường là `[1, 1]`: có hai đầu vào, mỗi đầu vào báo chèn một hàng. Đây là **kết quả của driver**, không phải hằng số do Spring tự đặt. Trong JDBC, một phần tử còn có thể có giá trị đặc biệt `Statement.SUCCESS_NO_INFO` (tức `-2`).

Lưu ý:
- Key phải khớp tên cột mà `SimpleJdbcInsert` sử dụng; không tùy tiện đổi thành `importId` nếu cột thực tế là `import_id`.
- `Map.of(...)` không cho phép giá trị `null`. Nếu có cột nullable, dùng `HashMap` hoặc `MapSqlParameterSource`.
- Tham số giá trị được bind bằng prepared statement; không cần tự escape hoặc nối giá trị thành SQL.
- Không trộn nhiều loại bản ghi có cấu trúc cột khác nhau vào một `executeBatch`, bởi API sử dụng một câu `INSERT` có cấu trúc cố định.

## 4. Cách B — `executeBatch(SqlParameterSource...)`

`MapSqlParameterSource` rất hữu ích khi cần xây tham số từ DTO, có giá trị null hoặc cần khai báo SQL type. Ví dụ trong method của writer:

```java
import org.springframework.jdbc.core.namedparam.MapSqlParameterSource;
import org.springframework.jdbc.core.namedparam.SqlParameterSource;

SqlParameterSource[] rows = {
    new MapSqlParameterSource()
        .addValue("import_id", "IMPORT-002")
        .addValue("line_no", 1)
        .addValue("sku", "MOUSE-01")
        .addValue("quantity", 3),

    new MapSqlParameterSource()
        .addValue("import_id", "IMPORT-002")
        .addValue("line_no", 2)
        .addValue("sku", "PAD-02")
        .addValue("quantity", 1)
};

int[] counts = insert.executeBatch(rows);
```

Có thể dùng `addValue("optional_note", null, java.sql.Types.VARCHAR)` nếu cột nullable cần SQL type rõ. `BeanPropertySqlParameterSource` là lựa chọn khác khi đối tượng có thuộc tính JavaBean khớp tên tham số; hãy đặc biệt để ý tên thuộc tính camelCase và tên cột snake_case.

**Chọn cách nào?** `Map` tiện cho dữ liệu đã ở dạng tên-cột → giá-trị; `MapSqlParameterSource` dễ kiểm soát kiểu SQL/null hơn. Cả hai đều gọi cùng khả năng batch của `SimpleJdbcInsert`; không có quy tắc “cách B luôn nhanh hơn”.

Tạo file `src/main/java/demo/BatchInsertDemo.java`:

```java
package demo;

import java.util.Arrays;
import javax.sql.DataSource;

import org.springframework.dao.DataAccessException;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.core.namedparam.MapSqlParameterSource;
import org.springframework.jdbc.core.namedparam.SqlParameterSource;
import org.springframework.jdbc.core.simple.SimpleJdbcInsert;
import org.springframework.jdbc.datasource.DataSourceTransactionManager;
import org.springframework.jdbc.datasource.DriverManagerDataSource;
import org.springframework.transaction.support.TransactionTemplate;

public final class BatchInsertDemo {
    private BatchInsertDemo() {
    }

    public static void main(String[] args) {
        DataSource ds = new DriverManagerDataSource(
            "jdbc:h2:mem:simplejdbc_batch;DB_CLOSE_DELAY=-1", "sa", ""
        );
        JdbcTemplate jdbc = new JdbcTemplate(ds);

        jdbc.execute(
            "CREATE TABLE order_item (" +
            "id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY, " +
            "import_id VARCHAR(64) NOT NULL, " +
            "line_no INTEGER NOT NULL, " +
            "sku VARCHAR(64) NOT NULL, " +
            "quantity INTEGER NOT NULL CHECK (quantity > 0), " +
            "CONSTRAINT uq_import_line UNIQUE (import_id, line_no))"
        );

        SimpleJdbcInsert insert = new SimpleJdbcInsert(ds)
            .withTableName("order_item")
            .usingColumns("import_id", "line_no", "sku", "quantity");

        TransactionTemplate tx = new TransactionTemplate(
            new DataSourceTransactionManager(ds)
        );

        SqlParameterSource[] valid = {
            item("IMPORT-OK", 1, "BOOK-01", 2),
            item("IMPORT-OK", 2, "PEN-05", 4),
            item("IMPORT-OK", 3, "PAD-02", 1)
        };

        int[] counts = tx.execute(status -> {
            int[] result = insert.executeBatch(valid);
            requireExactlyOnePerItem(result, valid.length);
            return result;
        });

        System.out.println("validCounts=" + Arrays.toString(counts));
        System.out.println(
            "validRows=" + countRows(jdbc, "IMPORT-OK")
        );

        SqlParameterSource[] invalid = {
            item("IMPORT-BAD", 1, "MOUSE-01", 1),
            item("IMPORT-BAD", 1, "USB-02", 2)
        };

        try {
            tx.execute(status -> {
                int[] result = insert.executeBatch(invalid);
                requireExactlyOnePerItem(result, invalid.length);
                return result;
            });
        } catch (DataAccessException ex) {
            System.out.println("invalidBatch=ROLLED_BACK");
        }

        System.out.println(
            "invalidRows=" + countRows(jdbc, "IMPORT-BAD")
        );
    }

    private static SqlParameterSource item(
            String importId, int lineNo, String sku, int quantity) {
        return new MapSqlParameterSource()
            .addValue("import_id", importId)
            .addValue("line_no", lineNo)
            .addValue("sku", sku)
            .addValue("quantity", quantity);
    }

    private static void requireExactlyOnePerItem(
            int[] counts, int expectedSize) {
        if (counts.length != expectedSize) {
            throw new IllegalStateException(
                "Expected " + expectedSize + " counts, got " + counts.length
            );
        }

        for (int i = 0; i < counts.length; i++) {
            if (counts[i] != 1) {
                throw new IllegalStateException(
                    "Item " + i + " affected rows: " + counts[i]
                );
            }
        }
    }

    private static int countRows(JdbcTemplate jdbc, String importId) {
        Integer value = jdbc.queryForObject(
            "SELECT COUNT(*) FROM order_item WHERE import_id = ?",
            Integer.class,
            importId
        );
        if (value == null) {
            throw new IllegalStateException("COUNT(*) returned null");
        }
        return value;
    }
}
```

Trong thư mục `simplejdbc-batch`, chạy:

```bash
mvn -q compile exec:java -Dexec.mainClass=demo.BatchInsertDemo
```

Dòng in của chương trình (không tính log/thông điệp Maven nếu có):

```text
validCounts=[1, 1, 1]
validRows=3
invalidBatch=ROLLED_BACK
invalidRows=0
```

**Vì sao có kết quả này?** Ba item hợp lệ tạo ba hàng. Với H2, count tương ứng là `1` mỗi item. `TransactionTemplate` chỉ commit sau khi cả batch và kiểm tra count hoàn thành. Ở batch `IMPORT-BAD`, hai dòng có cùng `(import_id, line_no)`, vi phạm unique constraint. Lỗi JDBC được Spring chuyển thành `DataAccessException` phù hợp và thoát khỏi `TransactionTemplate` nên toàn lô bị rollback; sau đó `COUNT(*)` cho `IMPORT-BAD` là `0`.

**Điểm quan trọng:** không phải cứ `executeBatch` ném lỗi thì DB chưa xử lý item nào. Driver có thể đã thực thi một phần trước khi báo lỗi. Trong ví dụ, **transaction rollback** mới bảo vệ tính all-or-nothing. Với DB/driver khác, cần kiểm thử lại cú pháp identity, quy tắc batch, translation exception và update counts.

## 6. Cách đọc mảng `int[]` đúng với JDBC

`executeBatch` trả counts theo thông tin JDBC driver báo. `java.sql.Statement` định nghĩa các giá trị đặc biệt:

| Count | Ý nghĩa | Xử lý gợi ý nếu yêu cầu mỗi input chèn đúng một hàng |
| --- | --- | --- |
| `1` | Driver báo một hàng bị ảnh hưởng | Đạt kỳ vọng mục đó, nếu transaction thành công |
| `0` | Driver báo không có hàng bị ảnh hưởng | Cần giải thích theo SQL/driver và quy tắc nghiệp vụ |
| `> 1` | Driver báo nhiều hàng bị ảnh hưởng | Bất thường với `INSERT` một hàng thông thường; điều tra |
| `Statement.SUCCESS_NO_INFO` = `-2` | Lệnh thành công, **không biết** số hàng | Không được xem là “-2 hàng”; tùy hợp đồng có thể kiểm chứng thêm |
| `Statement.EXECUTE_FAILED` = `-3` | Driver báo lệnh thất bại trong update-count array | Lỗi cần được xử lý/rollback theo yêu cầu |

**Hai kiểu kiểm tra khác nhau:**
1. Yêu cầu chặt *mỗi input tạo đúng một hàng*: kiểm tra `counts.length == input.length` và `count == 1` cho mọi phần tử. Code ví dụ đang dùng chính sách này; `-2` không chứng minh được số hàng nên bị từ chối.
2. Yêu cầu *driver xác nhận thực thi thành công dù không biết số hàng*: có thể chấp nhận `-2` sau khi đã thống nhất semantics và cơ chế đối soát. Vẫn phải bắt `DataAccessException` và xử lý transaction.

Không được suy luận thành công chỉ từ `counts.length`; không cộng `-2` vào tổng hàng; không tự cho rằng `counts.length == N` thì N hàng đã commit. Một số driver sẽ ném `BatchUpdateException` (được Spring dịch thành `DataAccessException`) khi một statement lỗi, thay vì trả mảng có `-3`. Đừng thiết kế code chỉ dựa vào một đường báo lỗi.

## 7. Transaction quyết định thành công toàn lô hay từng phần

Cần xác định rõ hợp đồng import:

- **All-or-nothing:** tất cả hàng cùng commit, hoặc không hàng nào commit. Bao toàn bộ `executeBatch` cùng bước kiểm tra count trong **một transaction**.
- **Partial success:** từng chunk được commit riêng để không phải làm lại toàn bộ file. Phải lưu rõ chunk/item nào đã commit và thiết kế retry không tạo bản ghi trùng.
- **Nhiều bảng liên quan:** có thể dùng các writer/`SimpleJdbcInsert` khác nhau trong **cùng transaction** cho các bảng, nhưng thứ tự ghi cần tuân thủ foreign key; đây vẫn là nhiều batch độc lập.

Trong ứng dụng Spring có transaction manager, một service có thể dùng:

```java
import org.springframework.transaction.annotation.Transactional;

@Transactional
public void importItems(SqlParameterSource[] rows) {
    if (rows.length == 0) {
        return;
    }

    int[] counts = insert.executeBatch(rows);
    requireExactlyOnePerItem(counts, rows.length);
}
```

**Đây là đoạn tích hợp**, dùng field `insert` và helper kiểm tra counts đã khai báo ở service/repository, không phải chương trình độc lập. Với cấu hình rollback mặc định của Spring, unchecked exception thoát khỏi method được quản lý transaction dẫn đến rollback. Với checked exception cần chú ý `rollbackFor` nếu nghiệp vụ yêu cầu. Trong chế độ proxy thông dụng, lời gọi `@Transactional` **từ một method khác trên cùng instance** thường bỏ qua interceptor; xác minh transaction thật sự hoạt động.

Nếu bắt lỗi rồi nuốt exception **ngay trong** method transaction và trả success, DB có thể commit các bước đã ghi. Đặt xử lý lỗi bên ngoài ranh giới transaction, hoặc chủ động đánh dấu rollback theo tình huống.

## 8. Chia batch lớn thành các chunk

`SimpleJdbcInsert.executeBatch(...)` nhận mảng các phần tử và **không có tham số batch size** riêng trong method. Với import nhiều hàng, hãy chia mảng thành chunk theo dung lượng hợp lý rồi thử benchmark (ví dụ bắt đầu với 200–1.000 hàng/chunk; không có một kích thước tối ưu áp dụng cho mọi DB).

Giả sử `all` là `SqlParameterSource[]` đã chuẩn bị; `insert`, `tx` và `requireExactlyOnePerItem` là các thành phần từ ví dụ trên. Đoạn **minh họa bổ sung** sau thực thi tất cả chunk trong cùng một transaction:

```java
import java.util.Arrays;

int chunkSize = 500;

tx.executeWithoutResult(status -> {
    for (int from = 0; from < all.length; from += chunkSize) {
        int to = Math.min(from + chunkSize, all.length);
        SqlParameterSource[] chunk = Arrays.copyOfRange(all, from, to);

        int[] counts = insert.executeBatch(chunk);
        requireExactlyOnePerItem(counts, chunk.length);
    }
});
```

Nếu chunk cuối thất bại thì transaction chung rollback cả những chunk trước. Mặt trái là transaction dài có thể giữ lock và tạo WAL/undo lớn; với hàng triệu dòng cần cân nhắc việc commit từng chunk và biểu diễn rõ partial success.

Hãy kiểm soát bộ nhớ của chính ứng dụng: nếu đã nạp toàn bộ file vào một mảng khổng lồ, việc chia khi gọi API **không** giải quyết overhead lưu tất cả hàng. Với tập lớn, có thể đọc/validate theo lô từ nguồn và chọn ranh giới commit phù hợp.

Khi chia chunk, vẫn phải xử lý các rủi ro giống batch nhỏ: lỗi ở giữa, counts `-2`, duplicate, timeout và khả năng retry. Kích thước chunk còn chịu giới hạn số bind parameter, packet size, thời gian chờ và khả năng của driver.

## 9. `executeBatch` có lấy được generated ID cho từng hàng không?

**Không.** `executeBatch(...)` của `SimpleJdbcInsert` trả `int[]` counts, không có overload trả `KeyHolder[]`. Đối với một hàng, có API khác:

```java
SimpleJdbcInsert singleInsert = new SimpleJdbcInsert(dataSource)
    .withTableName("order_item")
    .usingColumns("import_id", "line_no", "sku", "quantity")
    .usingGeneratedKeyColumns("id");

Number id = singleInsert.executeAndReturnKey(
    new MapSqlParameterSource()
        .addValue("import_id", "ONE-ROW")
        .addValue("line_no", 1)
        .addValue("sku", "BOOK-01")
        .addValue("quantity", 1)
);
```

Đây là đoạn tích hợp minh họa; `dataSource` phải được cấp từ ứng dụng. Nếu chỉ cần chèn nhiều hàng, có thể **không cấu hình** `usingGeneratedKeyColumns` và để DB tự sinh `id` khi `executeBatch`. Nếu bắt buộc nhận ID cho **từng** hàng, chọn một trong các phương án đã kiểm chứng với DB/driver:
- Gọi `executeAndReturnKey` cho từng hàng trong transaction (đổi lấy độ đơn giản với chi phí nhiều lời gọi).
- Dùng SQL đặc thù như `INSERT ... RETURNING` hoặc cơ chế JDBC batch generated keys của driver, kiểm tra mapping returned IDs.
- Dùng khóa do ứng dụng cấp (UUID, business key), hoặc staging table có khóa tương quan, tránh đoán ID theo thứ tự.

Không dựa vào `MAX(id)`, không giả định ID liên tục hoặc tăng theo vị trí của batch: sequence/identity, transaction rollback và concurrency đều có thể tạo khoảng trống.

## 10. Idempotency, trùng dữ liệu và retry

Lô insert có thể bị gửi lại do client timeout hoặc mạng mất phản hồi. Nếu DB đã commit trước khi mất kết nối, retry toàn bộ có thể tạo duplicate. Nếu lần trước rollback, retry có thể là đúng. **Không suy diễn trạng thái commit chỉ từ việc client không nhận kết quả.**

Thiết kế an toàn thường gồm:
- Khóa yêu cầu `import_id` và khóa từng hàng như `(import_id, line_no)`, có `UNIQUE` constraint.
- Bảng theo dõi trạng thái import (ví dụ `IN_PROGRESS`, `COMPLETED`, `FAILED`) hoặc truy vấn xác minh theo business key.
- Policy rõ cho duplicate: reject, skip có đối soát, hay upsert.
- Truy vấn đối soát trước retry theo ranh giới nhất quán được lựa chọn; không chỉ dựa vào “`SELECT không thấy thì INSERT`” vì hai request đồng thời có thể cùng thấy chưa tồn tại.
- Chỉ retry những lỗi tạm thời khi biết tác động, thời gian chờ và tính idempotent; tránh retry vô hạn với constraint violation không thể tự hết.

`SimpleJdbcInsert` xây `INSERT` thông thường. Nếu cần `ON CONFLICT DO NOTHING`, `ON DUPLICATE KEY UPDATE`, `MERGE` hay `RETURNING`, chuyển sang câu SQL theo DB với `JdbcTemplate`/`NamedParameterJdbcTemplate` và kiểm tra count semantics riêng.

## 11. Hiệu năng và chọn đúng công cụ

| Tình huống | API thích hợp |
| --- | --- |
| Chèn một hàng không cần key | `SimpleJdbcInsert.execute` |
| Chèn một hàng và lấy generated key | `executeAndReturnKey` hoặc `executeAndReturnKeyHolder` |
| Chèn nhiều hàng cùng bảng, cấu trúc cột ổn định | `SimpleJdbcInsert.executeBatch` |
| Batch có SQL phức tạp, custom SQL hoặc kiểm soát batchSize | `JdbcTemplate.batchUpdate`/`NamedParameterJdbcTemplate.batchUpdate` |
| Cần trả nhiều keys, upsert, conflict handling, bulk-load đặc thù | SQL/công cụ theo DB và driver, cần benchmark và tích hợp kiểm thử |

Nên đo throughput, latency, CPU, thời gian commit, lock wait, số connection sử dụng và memory với **driver production**. Connection pool phù hợp cần được cấu hình trong ứng dụng thật; `DriverManagerDataSource` của ví dụ chỉ nhằm đơn giản hóa chạy thử. Driver có thể có tùy chọn rewrite batch thành SQL nhiều hàng, làm thay đổi update count: phải đo và kiểm thử thay vì giả định.

Tăng chunk quá lớn có thể chạm giới hạn packet, số tham số, lock và transaction log. Bắt đầu kích thước vừa phải rồi đo theo kích thước hàng, index/trigger và lượng truy cập đồng thời của hệ thống.

## 12. Lỗi phổ biến và cách tránh

**A. Vòng lặp `execute` rồi gọi đó là batch.**

```java
for (Map<String, ?> row : rows) {
    insert.execute(row);
}
```

Đây là nhiều lần insert đơn; muốn JDBC batch, chuẩn bị mảng `Map` hoặc `SqlParameterSource[]` và gọi một `executeBatch` cho từng chunk. Tuy nhiên, vòng lặp đơn vẫn có ích khi cần generated key ngay cho mỗi hàng và lượng dữ liệu nhỏ.

**B. Tạo `SimpleJdbcInsert` mới cho từng bản ghi.** Nó phải thiết lập/khám phá metadata, gây overhead và làm mất lợi ích tái sử dụng. Cấu hình một lần cho bảng và dùng lại sau đó.

**C. Sai key/column, thiếu `NOT NULL`, nhầm camelCase với snake_case.** Đặt rõ `usingColumns`, kiểm tra tên key, mapping type và chạy integration test với schema thật.

**D. Đọc count sai.** `-2` nghĩa là không biết số hàng, không phải lỗi hai hàng; `-3` là `EXECUTE_FAILED` nếu driver trả trong counts; số phần tử của mảng không chứng minh commit thành công. Kiểm tra theo yêu cầu nghiệp vụ.

**E. Không đặt transaction rồi nghĩ batch tự rollback mọi thứ.** JDBC có thể thành công một phần trước khi báo lỗi. Transaction boundary và cách xử lý exception quyết định dữ liệu được giữ lại.

**F. Dùng `executeBatch` như API nhận generated keys.** Nó trả `int[]`, không trả danh sách ID. Chọn chiến lược khác nếu cần khóa.

**G. Retry toàn batch sau timeout mà không có khóa idempotency.** Có thể tạo duplicate nếu transaction đã commit. Unique constraint và trạng thái import là cơ sở để xử lý retry.

**H. Chia chunk lớn nhưng vẫn giữ mọi hàng trong RAM.** Tách cả **cách đọc nguồn** thành từng phần nếu file quá lớn; chọn transaction strategy độc lập với memory strategy.

## 13. Checklist kiểm thử

| Ca kiểm thử | Điều phải xác minh |
| --- | --- |
| Một lô 3 hàng hợp lệ | Chèn đúng 3 hàng; với H2 demo `[1,1,1]` |
| Lô rỗng | Caller xử lý sớm, không gọi DB thừa |
| Thiếu cột NOT NULL | Exception; không commit sai |
| `quantity <= 0` | Constraint hoặc validation từ chối |
| Hai hàng cùng `import_id + line_no` | Unique violation; transaction chung rollback |
| Driver trả `SUCCESS_NO_INFO` | Policy xử lý `-2` đúng ngữ nghĩa |
| Batch lớn chia 2–3 chunk, chunk cuối lỗi | Transaction chung rollback tất cả; transaction từng chunk ghi nhận partial |
| Hai request đồng thời cùng business key | Constraint bảo vệ; xác minh retry |
| Timeout sau khi DB có thể commit | Có cơ chế xác định trạng thái trước khi retry |
| Hàng cần ID tự sinh | Không suy ra ID từ `int[]` |
| DB khác H2 | Xác minh SQL type, metadata, batch counts, exception translation và rollback với driver thật |

Integration test trên đúng DB/driver triển khai là quan trọng, nhất là khi yêu cầu count phải chính xác hoặc cần xử lý phần tử thất bại giữa batch. Có thể dùng test container và transaction isolation tương ứng với production.

## 14. Ghi nhớ

Quy trình chuẩn: **xác định cột và khóa nghiệp vụ → cấu hình `SimpleJdbcInsert` dùng lại → chuyển mỗi row thành `Map`/`SqlParameterSource` → gọi `executeBatch` → kiểm tra từng count → commit/rollback trong transaction → quản lý retry/idempotency**.
