# Yêu cầu trả khóa khi tạo PreparedStatement trong Spring JDBC

## 1. Mục tiêu và tình huống sử dụng

Sau khi thêm một bản ghi bằng `INSERT`, cơ sở dữ liệu thường tự sinh khóa chính, ví dụ cột `id` có thuộc tính `IDENTITY` hoặc `AUTO_INCREMENT`. Ứng dụng có thể cần khóa vừa sinh để trả về cho API, tạo bản ghi liên quan hoặc tiếp tục xử lý trong cùng giao dịch.

Điểm cốt lõi của bài này: **phải yêu cầu JDBC driver cho phép trả khóa sinh ngay khi tạo `PreparedStatement`**. Sau đó mới thực thi lệnh `INSERT` và đọc khóa từ `ResultSet` của JDBC hoặc `KeyHolder` của Spring. Yêu cầu trả khóa không tự tạo ra khóa; việc sinh khóa thuộc về cơ sở dữ liệu.

Ví dụ giả định bảng `customer` có cột `id` do cơ sở dữ liệu tự sinh và hai cột do ứng dụng truyền vào:

```sql
-- Ví dụ cú pháp IDENTITY kiểu SQL chuẩn, phù hợp với H2/PostgreSQL;
-- cú pháp tạo cột tự sinh ở hệ quản trị khác có thể khác.
CREATE TABLE customer (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(200) NOT NULL
);
```

Ta chèn dữ liệu bằng `INSERT INTO customer (name, email) VALUES (?, ?)` và muốn nhận lại `id`. Hai dấu `?` là tham số của `PreparedStatement`; chúng không đại diện cho khóa `id` do cơ sở dữ liệu tự cấp.

## 2. Yêu cầu khóa sinh được khai báo ở đâu?

Trong JDBC, `Connection` cung cấp các cách tạo `PreparedStatement` sau:

```java
// (1) Chỉ chuẩn bị SQL; không yêu cầu rõ việc lấy generated keys.
PreparedStatement plain = connection.prepareStatement(sql);

// (2) Bật yêu cầu trả các khóa do database sinh.
PreparedStatement withKeys = connection.prepareStatement(
        sql, Statement.RETURN_GENERATED_KEYS);

// (3) Chỉ rõ cột khóa muốn lấy theo tên.
PreparedStatement withId = connection.prepareStatement(
        sql, new String[] {"id"});
```

Ba dòng là các phương án minh họa, không phải ba statement phải tạo đồng thời. Khi sử dụng thực tế, chọn một phương án và đóng statement đúng cách.

| Lời gọi | Ý nghĩa | Khi nên dùng |
| --- | --- | --- |
| `prepareStatement(sql)` | Chuẩn bị câu lệnh và tham số; không yêu cầu rõ khóa sinh. | Chỉ cần số hàng cập nhật hoặc dữ liệu truy vấn. |
| `prepareStatement(sql, Statement.RETURN_GENERATED_KEYS)` | Yêu cầu driver cho phép lấy khóa sinh sau khi chạy. | Muốn driver xác định các cột khóa được trả. |
| `prepareStatement(sql, new String[] {"id"})` | Yêu cầu khóa ở cột có tên `id`. | Biết rõ tên cột cần trả; thường hữu ích để tránh sự khác biệt về cột mà driver tự chọn. |

`Statement.NO_GENERATED_KEYS` là cờ đối nghịch với `RETURN_GENERATED_KEYS`. Mảng `String[]` chứa **tên cột trong bảng**, không phải tên tham số Java, và phải phù hợp với quy tắc đặt tên/case của database và driver. JDBC còn có overload nhận `int[] columnIndexes`, nhưng chỉ số cột phụ thuộc cấu trúc bảng nên thông thường tên cột dễ đọc hơn.

**Quan trọng:** Cờ `RETURN_GENERATED_KEYS` được truyền vào **`Connection.prepareStatement(...)`**, không truyền vào `PreparedStatement.executeUpdate(...)`. Các overload kiểu `executeUpdate(sql, Statement.RETURN_GENERATED_KEYS)` thuộc `Statement`; không gọi các overload đó trên `PreparedStatement` đã chuẩn bị sẵn.

## 3. Quy trình JDBC thuần: tạo, gán tham số, chạy, đọc khóa

Đây là một lớp Java 17+ hoàn chỉnh về mặt cú pháp, chỉ phụ thuộc JDBC trong JDK. Nó nhận một `Connection` đang mở; mã gọi chịu trách nhiệm quản lý vòng đời `Connection`/giao dịch và cấu hình JDBC driver.

```java
// File: GeneratedKeyJdbcExample.java
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;
import java.sql.Statement;

public final class GeneratedKeyJdbcExample {

    private static final String INSERT_SQL =
            "INSERT INTO customer (name, email) VALUES (?, ?)";

    public static long insertCustomer(
            Connection connection, String name, String email)
            throws SQLException {

        // Yêu cầu trả khóa tại thời điểm tạo PreparedStatement.
        try (PreparedStatement ps = connection.prepareStatement(
                INSERT_SQL, Statement.RETURN_GENERATED_KEYS)) {

            ps.setString(1, name);
            ps.setString(2, email);

            int affectedRows = ps.executeUpdate();
            if (affectedRows != 1) {
                throw new SQLException(
                        "Expected one inserted row, got " + affectedRows);
            }

            // Chỉ đọc generated keys sau khi thực thi INSERT.
            try (ResultSet keys = ps.getGeneratedKeys()) {
                if (!keys.next()) {
                    throw new SQLException(
                            "INSERT succeeded but no generated key returned");
                }
                long id = keys.getLong(1);
                if (keys.wasNull()) {
                    throw new SQLException("Generated id is SQL NULL");
                }
                return id;
            }
        }
    }
}
```

Có thể kiểm tra **biên dịch lớp** bằng JDK 17 trở lên:

```bash
javac GeneratedKeyJdbcExample.java
```

Lớp không có `main` nên không chạy độc lập bằng `java GeneratedKeyJdbcExample`. Để chạy thật, ứng dụng cần `Connection` từ một JDBC driver tương ứng, bảng `customer` đã tạo và thao tác gọi phương thức trên. Không có stdout cố định vì khóa sinh phụ thuộc dữ liệu và cơ sở dữ liệu.

Luồng xử lý:

1. `prepareStatement(INSERT_SQL, RETURN_GENERATED_KEYS)` báo trước với driver cần lấy khóa.
2. `setString(1, ...)` và `setString(2, ...)` gán giá trị cho các dấu `?`; không ghép dữ liệu trực tiếp vào SQL.
3. `executeUpdate()` thực hiện `INSERT` và trả số hàng bị tác động, **không phải giá trị ID**.
4. `getGeneratedKeys()` mở một `ResultSet` riêng chứa các khóa mà driver trả.
5. `keys.next()` kiểm tra có hàng khóa; `keys.getLong(1)` đọc cột đầu tiên nếu khóa là kiểu số thích hợp.
6. `try-with-resources` đóng `ResultSet` và `PreparedStatement` kể cả khi có lỗi. Ví dụ không đóng `Connection` do bên gọi quản lý nó.

Nếu cần chắc chắn lấy đúng cột `id`, thay dòng tạo statement bằng:

```java
PreparedStatement ps = connection.prepareStatement(
        INSERT_SQL, new String[] {"id"});
```

Đây chỉ là một dòng thay thế **bên trong cùng khối `try-with-resources`** của ví dụ; không tạo thêm statement thứ hai.

## 4. Cách làm chính trong Spring: PreparedStatementCreator + KeyHolder

Trong Spring JDBC, `JdbcTemplate.update(PreparedStatementCreator, KeyHolder)` cung cấp chính xác khả năng này:

- `PreparedStatementCreator` là callback nhận `Connection` do `JdbcTemplate` quản lý; callback phải tạo `PreparedStatement` **đã bật khả năng trả khóa sinh** và gán tham số.
- `GeneratedKeyHolder` là nơi Spring đưa các khóa được trả về sau khi chạy `INSERT`.
- `JdbcTemplate` quản lý vòng đời tài nguyên JDBC, tham gia giao dịch Spring đã cấu hình và chuyển `SQLException` thành các ngoại lệ `DataAccessException` thích hợp.

Ví dụ dưới đây là một lớp repository có thể dùng trong ứng dụng Spring Framework 6.x với Java 17+. Ứng dụng phải cung cấp `JdbcTemplate` được cấu hình từ `DataSource` và có bảng như phần 1.

```java
// File: CustomerRepository.java
import java.sql.PreparedStatement;
import java.util.Objects;

import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.support.GeneratedKeyHolder;
import org.springframework.jdbc.support.KeyHolder;

public final class CustomerRepository {

    private static final String INSERT_SQL =
            "INSERT INTO customer (name, email) VALUES (?, ?)";

    private final JdbcTemplate jdbcTemplate;

    public CustomerRepository(JdbcTemplate jdbcTemplate) {
        this.jdbcTemplate = Objects.requireNonNull(jdbcTemplate);
    }

    public long create(String name, String email) {
        KeyHolder keyHolder = new GeneratedKeyHolder();

        int affectedRows = jdbcTemplate.update(connection -> {
            // Chỉ rõ cột khóa cần trả NGAY KHI tạo PreparedStatement.
            PreparedStatement ps = connection.prepareStatement(
                    INSERT_SQL, new String[] {"id"});
            ps.setString(1, name);
            ps.setString(2, email);
            return ps;
        }, keyHolder);

        if (affectedRows != 1) {
            throw new IllegalStateException(
                    "Expected one inserted row, got " + affectedRows);
        }

        Number key = keyHolder.getKey();
        if (key == null) {
            throw new IllegalStateException(
                    "Database did not return a generated id");
        }
        return key.longValue();
    }
}
```

Ở ví dụ này, cách gọi `connection.prepareStatement(INSERT_SQL, new String[] {"id"})` nằm ngay trong lambda `PreparedStatementCreator`. Đây là chi tiết quyết định: chỉ truyền một `KeyHolder` vào `update` **không thể tự sửa một statement vốn không yêu cầu trả khóa**. Có thể dùng `Statement.RETURN_GENERATED_KEYS` thay cho mảng tên cột nếu driver hỗ trợ tốt cách đó.

`keyHolder.getKey()` phù hợp khi thao tác trả **một hàng khóa, một giá trị khóa dạng số**. Chú ý kết quả có kiểu `Number` (ví dụ `Integer`, `Long` hoặc `BigDecimal` tùy driver); dùng `longValue()` khi domain thực sự cần `long` và giá trị nằm trong miền biểu diễn. Với UUID hoặc khóa không phải số, hoặc khi cần nhiều cột/hàng khóa, không dùng `getKey()` như thể luôn có một `long`: đọc `getKeys()`/`getKeyList()` theo cấu trúc thực tế. Spring có thể ném ngoại lệ nếu gọi `getKey()` nhưng có nhiều giá trị khóa.

Lớp `CustomerRepository` trên không có `main` và phụ thuộc thư viện Spring JDBC. Không thể biên dịch chỉ với JDK: cần các JAR Spring tương thích (và runtime cần JDBC driver/DataSource). Trong Spring Boot, cấu hình DataSource và `spring-boot-starter-jdbc` thường cung cấp các thành phần cần thiết; bản chất việc yêu cầu khóa vẫn là JDBC.

### Phân biệt với các overload `update` thông thường

```java
// Đếm số hàng được chèn; không nhận generated key qua KeyHolder.
int count = jdbcTemplate.update(
        "INSERT INTO customer (name, email) VALUES (?, ?)",
        "An", "an@example.test");

// Nhận generated key; callback tự tạo statement có chế độ trả khóa.
KeyHolder holder = new GeneratedKeyHolder();
jdbcTemplate.update(con -> {
    PreparedStatement ps = con.prepareStatement(
            "INSERT INTO customer (name, email) VALUES (?, ?)",
            Statement.RETURN_GENERATED_KEYS);
    ps.setString(1, "An");
    ps.setString(2, "an@example.test");
    return ps;
}, holder);
```

Hai đoạn là **hai thao tác INSERT độc lập để đối chiếu API**, không chạy liên tiếp với cùng một dữ liệu khi chỉ muốn chèn một hàng. Đoạn thứ hai cần `import java.sql.Statement;` và các import Spring tương ứng như ví dụ repository. Đối với nhu cầu chỉ lấy khóa sinh, dùng overload có `KeyHolder`. Không nhầm giá trị `int` do `update(...)` trả về (số hàng tác động) với giá trị khóa trong `KeyHolder`.

## 5. Chọn chế độ trả khóa thế nào cho đúng?

### Cách A — `Statement.RETURN_GENERATED_KEYS`

```java
PreparedStatement ps = connection.prepareStatement(
        INSERT_SQL, Statement.RETURN_GENERATED_KEYS);
```

Đây là yêu cầu chung để driver trả các khóa do cơ sở dữ liệu sinh. Tuy nhiên, khi không chỉ định cột, driver quyết định cột nào thích hợp để trả. Kết quả và thứ tự cột có thể khác theo driver/hệ quản trị.

### Cách B — yêu cầu cột `id` theo tên

```java
PreparedStatement ps = connection.prepareStatement(
        INSERT_SQL, new String[] {"id"});
```

Cách này thể hiện chủ đích rằng cần khóa ở cột `id`. Tên này phải trùng với cột được hỗ trợ bởi bảng/driver; một số driver áp dụng quy tắc phân biệt chữ hoa/chữ thường hoặc chỉ hỗ trợ một số kiểu khóa. Nếu muốn đọc chính xác một cột, hãy kiểm tra với database thực tế, không giả định mọi driver đều xử lý giống nhau.

### Cơ chế không thay thế việc sinh khóa của database

Giả sử bảng không tự sinh khóa, hoặc `INSERT` đã cung cấp `id` thủ công, bật `RETURN_GENERATED_KEYS` cũng không bắt database tạo thêm ID. Cần hiểu rõ schema, câu lệnh `INSERT` và chức năng của driver. JDBC có `DatabaseMetaData.supportsGetGeneratedKeys()` để hỏi mức hỗ trợ tính năng, nhưng vẫn phải thử đúng loại câu lệnh/schema trên hệ quản trị mục tiêu.

Đối với SQL đặc thù như `INSERT ... RETURNING id` (ví dụ PostgreSQL), đó là một cơ chế trả dữ liệu qua kết quả SQL cần xử lý theo semantics của driver và API được chọn; không tùy tiện trộn `RETURNING` với `getGeneratedKeys()`/`KeyHolder` nếu chưa kiểm thử.

## 6. Sai sót thường gặp và cách xử lý

| Hiện tượng/sai sót | Nguyên nhân có thể | Cách xử lý |
| --- | --- | --- |
| `INSERT` thành công nhưng `getGeneratedKeys()` rỗng | Statement được tạo bằng `prepareStatement(sql)` không yêu cầu khóa, hoặc driver/SQL không hỗ trợ. | Tạo lại statement bằng overload `RETURN_GENERATED_KEYS` hoặc mảng tên cột; kiểm tra driver và schema. |
| Dùng `ps.executeUpdate(sql, Statement.RETURN_GENERATED_KEYS)` | Đây là overload dành cho `Statement`, không dùng để cung cấp lại SQL/cờ trên `PreparedStatement`. | Chuyển cờ sang lúc `connection.prepareStatement(...)`, rồi gọi `ps.executeUpdate()` không tham số. |
| Dùng `affectedRows` làm ID | `executeUpdate`/`JdbcTemplate.update` trả số hàng bị ảnh hưởng. | Đọc `ResultSet` từ `getGeneratedKeys` hoặc `KeyHolder`. |
| `keyHolder.getKey()` trả `null` | Không có khóa được đưa vào holder. | Kiểm tra cách tạo statement, driver, loại `INSERT` và các khóa thực sự trả về. |
| `getKey()` báo nhiều khóa | Driver trả nhiều cột khóa hoặc nhiều hàng; `getKey()` dành cho một giá trị khóa số. | Dùng `getKeys()`/`getKeyList()` và kiểm tra map/hàng được trả. |
| Khóa là UUID nhưng gọi `getLong(1)`/`getKey()` | Giả định khóa luôn dạng số. | Đọc kiểu phù hợp, chẳng hạn `ResultSet.getObject(...)` hoặc map khóa; kiểm tra driver. |
| Mã kiểm tra giả định ID luôn tăng tuần tự hoặc không có khoảng trống | Sequence/identity có thể bỏ số khi rollback, retry, nhiều giao dịch hoặc do cơ chế cấp số. | Xem ID như định danh do DB cấp, không dùng để suy ra thứ tự commit hay số bản ghi. |
| Lưu `KeyHolder` làm field dùng chung | `GeneratedKeyHolder` là đối tượng chứa kết quả mutable, không dành để chia sẻ giữa các lượt insert đồng thời. | Tạo `new GeneratedKeyHolder()` cho từng lời gọi insert. |

Một khóa đã đọc được **không đồng nghĩa giao dịch đã commit**. Khi Spring quản lý giao dịch bằng `@Transactional`, thao tác chèn và lấy khóa có thể xảy ra trước khi commit; giao dịch vẫn có thể rollback. Không phát hành sự kiện bên ngoài chỉ dựa trên việc đã có khóa nếu cần tính nhất quán với commit.

## 7. Kiểm thử theo đúng mục tiêu bài học

Với một database thử nghiệm có cột `id` sinh tự động, kiểm tra các trường hợp sau:

1. **Trường hợp chuẩn:** gọi `create("An", "an@example.test")`, nhận ID; truy vấn theo ID thấy đúng `name`, `email`. Không hard-code ID bắt đầu từ `1`.
2. **Khẳng định cấu hình tại thời điểm chuẩn bị:** kiểm tra implementation dùng `Connection.prepareStatement(INSERT_SQL, RETURN_GENERATED_KEYS)` hoặc overload tên cột trong `PreparedStatementCreator`; chỉ thêm `KeyHolder` là chưa đủ.
3. **Đường lỗi:** nếu driver không hỗ trợ hoặc không trả khóa, phương thức phải báo lỗi rõ ràng, không trả ID giả định như `0`.
4. **Giao dịch rollback:** nếu chèn nằm trong giao dịch rồi rollback, xác minh bản ghi không tồn tại dù chương trình có thể đã quan sát ID sinh ra.
5. **Tính tương thích:** chạy test tích hợp với cùng hệ quản trị/JDBC driver được dùng ở production; kết quả khóa và cách đặt tên cột là phần phụ thuộc driver.

Khi test, cần dùng cơ sở dữ liệu thật hoặc môi trường tương đương để kiểm tra khả năng trả khóa. Mock chỉ xác minh callback gọi đúng overload, không chứng minh được driver thực sự cấp khóa.

## 8. Câu hỏi tự kiểm tra

**Câu 1.** Vì sao `jdbcTemplate.update(sql, args...)` không đủ nếu cần trả ID vừa sinh?  
Vì overload này trả số hàng bị tác động và không đưa kết quả khóa vào `KeyHolder`. Cần dùng `update(PreparedStatementCreator, KeyHolder)` với statement được tạo bằng chế độ cho phép trả khóa.

**Câu 2.** Lựa chọn `Statement.RETURN_GENERATED_KEYS` và `new String[] {"id"}` khác nhau ở đâu?  
Lựa chọn đầu yêu cầu khóa sinh nói chung và để driver quyết định cột phù hợp; lựa chọn sau chỉ rõ cột `id` cần lấy. Cả hai đều được truyền khi **tạo** `PreparedStatement`.

**Câu 3.** Nếu `executeUpdate()` trả `1` thì có chắc `getGeneratedKeys()` chứa `id = 1` không?  
Không. `1` là số hàng đã cập nhật; khóa sinh phụ thuộc database/driver và phải đọc, kiểm tra riêng.

## 9. Ghi nhớ

```text
Connection / JdbcTemplate
        |
        v
prepareStatement(sql, RETURN_GENERATED_KEYS hoặc ["id"])
        |
        v
setXxx(...) -> executeUpdate()
        |
        +--> số hàng tác động (int)
        |
        v
getGeneratedKeys() / Spring KeyHolder
        |
        v
kiểm tra có khóa, số cột và kiểu khóa trước khi sử dụng
```

**Quy tắc thực hành:** Yêu cầu khóa sinh **khi khởi tạo `PreparedStatement`**; thực thi `INSERT` và đọc kết quả khóa là hai bước tiếp theo. Với Spring JDBC, `PreparedStatementCreator` quyết định statement có được cấu hình đúng hay không, còn `KeyHolder` chỉ nhận kết quả.
