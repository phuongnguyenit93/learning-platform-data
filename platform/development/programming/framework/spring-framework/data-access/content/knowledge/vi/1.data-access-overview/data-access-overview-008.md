# Ví dụ xuyên suốt: lưu, tìm và cập nhật đơn hàng

## 1. Bài toán và mục tiêu học tập

Giả sử một hệ thống bán hàng cần thực hiện ba thao tác quen thuộc: **lưu** đơn hàng mới gồm nhiều dòng sản phẩm, **tìm** lại đơn theo mã và **cập nhật** trạng thái đơn từ NEW sang PAID. Đây là ví dụ xuyên suốt cho phần tổng quan về *Spring Framework Data Access*: một nghiệp vụ có dữ liệu quan hệ, nhiều câu SQL và yêu cầu nhất quán.

Sau bài này, bạn cần giải thích được đường đi của dữ liệu từ service đến database; phân biệt vai trò của DataSource, repository, JDBC template và transaction manager; hiểu vì sao lưu đơn và các dòng sản phẩm phải cùng transaction; xử lý kết quả không tìm thấy và tránh ghi đè khi nhiều yêu cầu cập nhật đồng thời. Ví dụ dùng **Spring JDBC** để nhìn thấy SQL trực tiếp. Spring Data JDBC và JPA có thể thay thế cơ chế truy cập, nhưng không thay đổi các câu hỏi nghiệp vụ cốt lõi.

**Quy ước nghiệp vụ:**

- Khách hàng có mã 42 mua 2 cuốn sách BOOK-01 (120.00 mỗi cuốn) và 1 cây bút PEN-01 (10.00). Tổng tiền là 250.00.
- Khi tạo, đơn có trạng thái NEW và version = 0. Sau khi thanh toán hợp lệ, trạng thái thành PAID và version tăng thành 1.
- Một đơn gồm bản ghi cha trong bảng orders và nhiều bản ghi con trong order_items. Không được để đơn cha tồn tại nếu lưu bất kỳ dòng con nào thất bại.
- Ví dụ chỉ mô phỏng xác nhận thanh toán, **không** tích hợp cổng thanh toán hoặc xây HTTP API. Trong hệ thống thực, cần xác minh kết quả thanh toán đáng tin cậy trước khi đánh dấu PAID.

## 2. Bản đồ luồng dữ liệu

| Thành phần | Trách nhiệm trong ví dụ |
| --- | --- |
| Application/runner | Gửi yêu cầu tạo, đọc và thanh toán đơn; trong ứng dụng web, controller có thể đảm nhiệm vai trò nhận yêu cầu. |
| OrderService | Kiểm tra dữ liệu, tính tổng, điều phối nhiều thao tác, đặt ranh giới transaction và áp dụng quy tắc chuyển trạng thái. |
| OrderRepository | Thực thi INSERT, SELECT, UPDATE; chuyển các dòng ResultSet thành đối tượng Java; không tự quyết định nghiệp vụ thanh toán. |
| NamedParameterJdbcTemplate | Bind tham số SQL, quản lý thao tác JDBC lặp lại, chuyển SQLException thành hệ DataAccessException của Spring. |
| DataSource | Cung cấp kết nối database; connection được transaction manager gắn với transaction hiện hành. |
| Transaction manager | Bắt đầu, commit hoặc rollback các thao tác cùng transaction. |
| Database | Lưu bền vững dữ liệu, áp dụng primary key, foreign key, kiểu dữ liệu và điều kiện cập nhật. |

Luồng tạo đơn: caller → OrderService.create → tính tổng → OrderRepository.insertOrder → nhận generated key → insert từng order_item → commit. Nếu có lỗi chưa được xử lý giữa chừng, transaction rollback cả phần cha lẫn các phần con.

Luồng tìm: caller → OrderService.find → repository SELECT đơn cha → SELECT các dòng hàng → ghép OrderView. Không tìm thấy mã thì trả Optional.empty(), không ngầm tạo đơn mới.

Luồng cập nhật: caller đưa id và version đã đọc → service yêu cầu UPDATE có điều kiện trạng thái NEW và version khớp → database báo số dòng được cập nhật. Một dòng nghĩa là thành công; không dòng nào nghĩa là bản ghi không tồn tại, đã đổi trạng thái hoặc đã bị thao tác khác cập nhật.

## 3. Dữ liệu mẫu và cấu trúc bảng

Ta dùng mô hình gọn nhưng đủ thể hiện quan hệ một–nhiều:

- **orders**: id, customer_id, status, total_amount, version.
- **order_items**: id, order_id, sku, quantity, unit_price.
- total_amount tính ở service từ quantity × unit_price và lưu dạng DECIMAL; tiền trong Java dùng BigDecimal, không dùng double.
- version là số nguyên để kiểm soát cập nhật đồng thời. Mỗi lần chuyển trạng thái thành công, tăng version lên 1.

Đây là SQL cho H2 của ví dụ; đặt tại src/main/resources/schema.sql:

~~~sql
CREATE TABLE orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    status VARCHAR(16) NOT NULL,
    total_amount DECIMAL(19, 2) NOT NULL,
    version BIGINT NOT NULL DEFAULT 0
);

CREATE TABLE order_items (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL REFERENCES orders(id),
    sku VARCHAR(64) NOT NULL,
    quantity INT NOT NULL CHECK (quantity > 0),
    unit_price DECIMAL(19, 2) NOT NULL CHECK (unit_price >= 0)
);
~~~

Khóa ngoại chặn dòng hàng trỏ đến đơn không tồn tại. CHECK bảo vệ dữ liệu ngay tại database, kể cả khi có ứng dụng khác truy cập. Ràng buộc này chưa tự tính lại total_amount hay kiểm soát mọi chuyển trạng thái; service và các chính sách dữ liệu thực tế vẫn cần xử lý.

### 4.1. Mô hình Java

Đặt trong src/main/java/example/orders/OrderModels.java:

~~~java
package example.orders;

import java.math.BigDecimal;
import java.util.List;

record ItemInput(String sku, int quantity, BigDecimal unitPrice) {}

record OrderHeader(
        long id,
        long customerId,
        String status,
        BigDecimal totalAmount,
        long version) {}

record OrderLine(String sku, int quantity, BigDecimal unitPrice) {}

record OrderView(
        long id,
        long customerId,
        String status,
        BigDecimal totalAmount,
        long version,
        List<OrderLine> items) {}
~~~

ItemInput đại diện cho dữ liệu đầu vào đã được caller truyền cho service. OrderHeader và OrderLine là kết quả của hai truy vấn quan hệ; OrderView ghép chúng thành một câu trả lời nghiệp vụ. Các record nằm cùng package với service/repository và cố ý không khai báo public để giữ ví dụ gọn.

### 4.2. Repository: SQL và ánh xạ kết quả

Đặt trong src/main/java/example/orders/OrderRepository.java:

~~~java
package example.orders;

import java.math.BigDecimal;
import java.util.List;
import java.util.Map;
import java.util.Optional;

import org.springframework.jdbc.core.namedparam.MapSqlParameterSource;
import org.springframework.jdbc.core.namedparam.NamedParameterJdbcTemplate;
import org.springframework.jdbc.support.GeneratedKeyHolder;
import org.springframework.jdbc.support.KeyHolder;
import org.springframework.stereotype.Repository;

@Repository
public class OrderRepository {
    private final NamedParameterJdbcTemplate jdbc;

    public OrderRepository(NamedParameterJdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    public long insertOrder(long customerId, BigDecimal totalAmount) {
        KeyHolder keys = new GeneratedKeyHolder();
        int changed = jdbc.update("""
                INSERT INTO orders (customer_id, status, total_amount, version)
                VALUES (:customerId, 'NEW', :totalAmount, 0)
                """,
                new MapSqlParameterSource()
                        .addValue("customerId", customerId)
                        .addValue("totalAmount", totalAmount),
                keys,
                new String[] {"ID"});

        if (changed != 1 || keys.getKey() == null) {
            throw new IllegalStateException("Không lấy được id của đơn hàng");
        }
        return keys.getKey().longValue();
    }

    public void insertLine(long orderId, ItemInput item) {
        int changed = jdbc.update("""
                INSERT INTO order_items (order_id, sku, quantity, unit_price)
                VALUES (:orderId, :sku, :quantity, :unitPrice)
                """,
                new MapSqlParameterSource()
                        .addValue("orderId", orderId)
                        .addValue("sku", item.sku())
                        .addValue("quantity", item.quantity())
                        .addValue("unitPrice", item.unitPrice()));

        if (changed != 1) {
            throw new IllegalStateException("Không lưu được dòng hàng");
        }
    }

    public Optional<OrderHeader> findHeader(long id) {
        List<OrderHeader> rows = jdbc.query("""
                SELECT id, customer_id, status, total_amount, version
                FROM orders
                WHERE id = :id
                """,
                Map.of("id", id),
                (rs, rowNum) -> new OrderHeader(
                        rs.getLong("id"),
                        rs.getLong("customer_id"),
                        rs.getString("status"),
                        rs.getBigDecimal("total_amount"),
                        rs.getLong("version")));

        return rows.stream().findFirst();
    }

    public List<OrderLine> findLines(long orderId) {
        return jdbc.query("""
                SELECT sku, quantity, unit_price
                FROM order_items
                WHERE order_id = :id
                ORDER BY id
                """,
                Map.of("id", orderId),
                (rs, rowNum) -> new OrderLine(
                        rs.getString("sku"),
                        rs.getInt("quantity"),
                        rs.getBigDecimal("unit_price")));
    }

    public int markPaidIfUnchanged(long id, long expectedVersion) {
        return jdbc.update("""
                UPDATE orders
                SET status = 'PAID', version = version + 1
                WHERE id = :id
                  AND status = 'NEW'
                  AND version = :version
                """,
                Map.of("id", id, "version", expectedVersion));
    }
}
~~~

Điểm cần đọc kỹ:

1. Tham số :customerId, :totalAmount, :id… được bind qua prepared statement. Không nối dữ liệu đầu vào thành chuỗi SQL, vì vừa dễ sai kiểu vừa mở đường cho SQL injection.
2. GeneratedKeyHolder nhận khóa id được database tạo. Ở H2, cột khóa sinh tự động được yêu cầu bằng tên ID. Một database/driver khác có thể yêu cầu điều chỉnh tên cột hoặc cách trả generated keys.
3. query dùng RowMapper chuyển từng hàng ResultSet thành record. SELECT có thể trả danh sách rỗng; ở đây Optional biểu thị rõ “không có đơn”.
4. UPDATE trả số hàng bị tác động; kết quả này quan trọng hơn việc chỉ kiểm tra xem lệnh SQL có ném exception hay không. Không có exception không đồng nghĩa đã cập nhật được bản ghi.
5. Repository không mở/đóng Connection thủ công và không tự commit. Các template tham gia transaction đã được Spring gắn với luồng thực thi hiện hành.

### 4.3. Service: nghiệp vụ và ranh giới transaction

Đặt trong src/main/java/example/orders/OrderService.java:

~~~java
package example.orders;

import java.math.BigDecimal;
import java.util.List;
import java.util.Optional;

import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class OrderService {
    private final OrderRepository repository;

    public OrderService(OrderRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public long create(long customerId, List<ItemInput> items) {
        if (customerId <= 0 || items == null || items.isEmpty()) {
            throw new IllegalArgumentException("Khách hàng và dòng hàng không hợp lệ");
        }

        BigDecimal total = BigDecimal.ZERO;
        for (ItemInput item : items) {
            if (item == null
                    || item.sku() == null
                    || item.sku().isBlank()
                    || item.quantity() <= 0
                    || item.unitPrice() == null
                    || item.unitPrice().signum() < 0) {
                throw new IllegalArgumentException("Dòng hàng không hợp lệ");
            }
            total = total.add(
                    item.unitPrice().multiply(BigDecimal.valueOf(item.quantity())));
        }

        long orderId = repository.insertOrder(customerId, total);
        for (ItemInput item : items) {
            repository.insertLine(orderId, item);
        }
        return orderId;
    }

    @Transactional(readOnly = true)
    public Optional<OrderView> find(long id) {
        return repository.findHeader(id)
                .map(header -> new OrderView(
                        header.id(),
                        header.customerId(),
                        header.status(),
                        header.totalAmount(),
                        header.version(),
                        repository.findLines(header.id())));
    }

    @Transactional
    public void pay(long id, long expectedVersion) {
        int changed = repository.markPaidIfUnchanged(id, expectedVersion);
        if (changed != 1) {
            throw new IllegalStateException(
                    "Đơn không tồn tại, không còn NEW hoặc version đã thay đổi");
        }
    }
}
~~~

Ở create, mọi INSERT diễn ra trong cùng transaction. Spring mặc định rollback khi exception không kiểm tra (RuntimeException) hoặc Error thoát khỏi phương thức transactional. Lỗi ràng buộc từ JDBC được chuyển thành DataAccessException (cũng là RuntimeException), nên một dòng hàng lỗi làm rollback cả đơn. Không bắt rồi nuốt exception ở giữa, vì như vậy service có thể commit dữ liệu dở dang.

Ở find, readOnly = true là gợi ý tối ưu và thể hiện ý định chỉ đọc; không nên coi nó là cơ chế bảo mật hay lời bảo đảm mọi database sẽ từ chối ghi. Ở pay, điều kiện version giúp tránh hai yêu cầu đồng thời đều nghĩ mình đang cập nhật cùng trạng thái NEW.

### 4.4. Chạy ba thao tác theo đúng thứ tự

Đặt trong src/main/java/example/orders/OrderDemoApplication.java:

~~~java
package example.orders;

import java.math.BigDecimal;
import java.util.List;

import org.springframework.boot.CommandLineRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;

@SpringBootApplication
public class OrderDemoApplication {
    public static void main(String[] args) {
        SpringApplication.run(OrderDemoApplication.class, args);
    }

    @Bean
    CommandLineRunner demo(OrderService service) {
        return args -> {
            long id = service.create(42L, List.of(
                    new ItemInput("BOOK-01", 2, new BigDecimal("120.00")),
                    new ItemInput("PEN-01", 1, new BigDecimal("10.00"))));

            OrderView before = service.find(id).orElseThrow();
            System.out.printf(
                    "Tạo đơn #%d: %s, tổng %s, %d món, version=%d%n",
                    before.id(), before.status(), before.totalAmount(),
                    before.items().size(), before.version());

            service.pay(id, before.version());

            OrderView after = service.find(id).orElseThrow();
            System.out.printf(
                    "Đọc lại đơn #%d: %s, tổng %s, version=%d%n",
                    after.id(), after.status(), after.totalAmount(),
                    after.version());
        };
    }
}
~~~

Dùng JDK 21 và Gradle tương thích (chẳng hạn Gradle 8.5), chạy từ thư mục dự án:

~~~bash
gradle bootRun
~~~

Với H2 mới và cấu hình logging ở trên, hai dòng do chương trình in ra là:

~~~text
Tạo đơn #1: NEW, tổng 250.00, 2 món, version=0
Đọc lại đơn #1: PAID, tổng 250.00, version=1
~~~

Mã đơn #1 giả định database H2 rỗng khi ứng dụng bắt đầu. Nếu đổi sang database đã có dữ liệu, id có thể khác. Giá trị tổng vẫn là 250.00 và thao tác cập nhật hợp lệ vẫn đưa version từ 0 lên 1.

## 5. Giải phẫu từng thao tác

### 5.1. Lưu đơn: nhất quán giữa bảng cha và bảng con

Service tính tổng 2 × 120.00 + 1 × 10.00 = 250.00, sau đó insert vào orders để nhận id. Các insert vào order_items sử dụng id đó làm khóa ngoại. Vì tất cả chạy trong cùng transaction, tính chất **atomicity** được áp dụng: hoặc toàn bộ đơn được ghi thành công, hoặc tất cả tác động của transaction được rollback.

Giả sử INSERT dòng thứ hai vi phạm độ dài sku của cột VARCHAR(64). Database báo lỗi, Spring chuyển thành DataIntegrityViolationException thuộc họ DataAccessException. Nếu exception thoát khỏi create, transaction rollback cả orders và order_items đã ghi trong cùng transaction. Đây là lý do transaction đặt tại service, nơi hiểu toàn bộ đơn là một đơn vị công việc, thay vì đặt ở từng câu INSERT riêng lẻ.

Không nên xem foreign key là thay thế transaction: foreign key giữ tính hợp lệ của tham chiếu, nhưng riêng nó không bảo đảm “đủ cả đơn và tất cả dòng hàng”. Tương tự, @Transactional không thay thế các constraint bảo vệ dữ liệu.

### 5.2. Tìm đơn: ánh xạ dữ liệu và trường hợp không tồn tại

SELECT đầu lấy id, customer_id, status, total_amount, version; SELECT tiếp theo lấy những dòng có order_id tương ứng. Repository trả OrderHeader và List<OrderLine>; service xây OrderView. Nếu không có dòng cha, Optional.empty() được trả về mà không truy vấn dòng con.

Hai truy vấn phục vụ đúng một đơn. Khi cần lấy hàng trăm đơn, nếu mỗi đơn đều truy vấn dòng con riêng sẽ tạo vấn đề **N+1 query**. Lúc đó cân nhắc JOIN, batch query theo tập id, phân trang hoặc projection phù hợp. Cách đọc một đơn ở ví dụ này là chủ ý để làm rõ chức năng của repository.

### 5.3. Cập nhật: điều kiện trạng thái và optimistic locking

Câu SQL chỉ chuyển NEW → PAID khi cả id, status và version khớp. Xét hai tác vụ đều đọc version = 0:

1. Tác vụ A cập nhật trước: database đổi status thành PAID, version thành 1, số dòng cập nhật = 1.
2. Tác vụ B vẫn gửi expectedVersion = 0: điều kiện WHERE không còn khớp, số dòng cập nhật = 0; service báo xung đột nghiệp vụ.

Đây là **optimistic locking** ở mức SQL; không cần giữ khóa trong suốt khoảng thời gian người dùng xem và xử lý đơn. Nhưng UPDATE có điều kiện chưa đủ cho mọi bài toán đồng thời: việc sửa số lượng tồn kho, cộng trừ số dư hoặc thao tác trên nhiều bản ghi có thể đòi hỏi isolation phù hợp, locking hoặc thiết kế transaction khác. Không mặc định rằng một lần kiểm tra trước UPDATE là an toàn nếu UPDATE cuối không có điều kiện.

## 6. Các tình huống cần tự kiểm chứng

| Tình huống | Điều mong đợi | Cơ chế quyết định |
| --- | --- | --- |
| Tạo đơn với hai món hợp lệ | Một orders và hai order_items được commit; tổng 250.00 | @Transactional và generated id |
| Tìm id không tồn tại | Optional.empty() | SELECT + ánh xạ Optional |
| Một dòng hàng vi phạm constraint sau khi đã INSERT đơn cha | Không còn phần dữ liệu mới của transaction | Rollback do DataAccessException |
| Thanh toán đơn NEW với version chính xác | Một dòng được cập nhật, status PAID, version +1 | UPDATE có điều kiện |
| Gửi lại version cũ hoặc thanh toán lần hai | Không dòng nào được cập nhật; service báo lỗi | status/version trong WHERE |
| Database không kết nối được | Thao tác thất bại với ngoại lệ truy cập dữ liệu | DataSource và DataAccessException |

Để kiểm chứng rollback, có thể thử truyền một sku dài hơn 64 ký tự (sau khi xác định trước số bản ghi), bắt exception tại tầng gọi bên ngoài transaction và kiểm tra số orders/order_items trước–sau bằng truy vấn đếm. Không bắt exception bên trong create rồi trả về thành công. Để kiểm chứng xung đột, giữ version đã đọc trước lần pay thành công và thử pay lại với version cũ.

## 7. Những lựa chọn và lỗi phổ biến khi áp dụng thực tế

**Chọn cách truy cập dữ liệu.** JDBC thuần yêu cầu tự quản Connection, PreparedStatement, ResultSet và transaction. Spring JDBC vẫn dùng SQL do lập trình viên viết nhưng giảm mã lặp, dùng DataSource và thống nhất exception. Spring Data JDBC/JPA cung cấp cách ánh xạ repository/aggregate hoặc entity ở mức cao hơn; dù chọn công cụ nào, vẫn phải xác định ranh giới nghiệp vụ, transaction, constraint, query và cập nhật đồng thời.

**Không đặt transaction sai chỗ.** @Transactional thường hoạt động qua Spring proxy. Gọi phương thức transactional từ bean khác như runner → service trong ví dụ là trường hợp đúng. Một phương thức trong cùng đối tượng gọi trực tiếp một phương thức @Transactional khác (self-invocation) có thể bỏ qua proxy, nên không tự giả định annotation sẽ được áp dụng. Bên cạnh đó, transaction không tự trải qua lời gọi mạng hoặc bao trùm các hệ thống bên ngoài.

**Không dùng double cho tiền.** Dùng BigDecimal và decimal column, xác định đơn vị tiền tệ, scale và quy tắc làm tròn rõ ràng. Bài mẫu sử dụng giá trị hai chữ số thập phân; hệ thống thực nên chuẩn hóa giá đầu vào và kiểm tra tràn/giới hạn số.

**Không đồng nhất lỗi kỹ thuật với lỗi nghiệp vụ.** Không tìm thấy đơn là một kết quả có thể dự kiến. Database mất kết nối, trùng khóa hoặc lỗi constraint là lỗi truy cập dữ liệu. Một UPDATE trả về 0 có thể do id sai, trạng thái không cho phép hoặc version cũ; nếu API cần mã lỗi khác nhau, service phải phân biệt bằng logic/truy vấn bổ sung phù hợp mà vẫn giữ an toàn đồng thời. Không trả nguyên SQL và thông tin kết nối cho người dùng cuối.

**Không ghép SQL bằng dữ liệu đầu vào.** Named parameter được bind an toàn cho giá trị; tên bảng/cột hoặc ORDER BY động không được bảo vệ chỉ bằng placeholder. Nếu cần SQL động, dùng danh sách cho phép với các tên đã kiểm chứng.

**Không lấy H2 làm bằng chứng tương thích mọi database.** H2 hữu ích cho bài học, nhưng dialect, khóa sinh tự động, isolation, precision và constraint có thể khác PostgreSQL, MySQL hoặc hệ quản trị khác. Production cần migration có phiên bản (chẳng hạn Flyway/Liquibase), index, kiểm thử với database mục tiêu, chính sách pool kết nối và giám sát transaction. Với hệ thống thanh toán thật còn cần idempotency, xác nhận từ nhà cung cấp và xử lý sự kiện nhất quán.

## 8. Câu hỏi tự kiểm tra

1. Nếu bỏ @Transactional ở create, điều gì có thể xảy ra khi INSERT dòng hàng thứ hai thất bại?
2. Vì sao service phải tính totalAmount trước khi lưu, và database vẫn cần CHECK/foreign key?
3. Tìm một id chưa tồn tại khác gì lỗi mất kết nối database?
4. Vì sao UPDATE status chỉ theo id có nguy cơ ghi đè khi hai yêu cầu đến gần như đồng thời?
5. Tại sao @Transactional(readOnly = true) không phải là cách kiểm soát quyền SELECT?
6. Nếu chuyển repository sang JPA, những trách nhiệm nào của service và database vẫn giữ nguyên?

**Ghi nhớ:** Bài toán dữ liệu không dừng ở “chạy được câu SQL”. Một thao tác đơn hàng đúng cần có dữ liệu hợp lệ, ánh xạ rõ ràng, ranh giới transaction bao phủ nghiệp vụ, xử lý trường hợp không tìm thấy và kiểm soát cập nhật đồng thời. Spring Data Access cung cấp hạ tầng để thực hiện các yêu cầu đó nhất quán; trách nhiệm thiết kế quy tắc nghiệp vụ vẫn thuộc về ứng dụng.
