# StaxEventItemWriter

Trong Spring Batch, StaxEventItemWriter là một ItemWriter dùng để ghi từng item thành các phần tử XML trong cùng một tài liệu XML. Writer sử dụng cơ chế StAX (Streaming API for XML) kết hợp với Spring OXM Marshaller để chuyển object Java thành XML. Nó phù hợp với các batch cần xuất dữ liệu lớn theo từng chunk mà không phải dựng toàn bộ cây XML trong bộ nhớ.

Writer tạo một phần tử gốc, sau đó marshal từng item thành phần tử con. Ví dụ, mỗi Order được chuyển thành một phần tử order bên trong phần tử orders. StaxEventItemWriter còn tham gia lifecycle của Step và hỗ trợ lưu checkpoint để có thể restart. Để dùng an toàn, cần cấu hình marshaller, root tag, resource, encoding và state nhất quán; đồng thời hiểu cách file output tương tác với transaction của chunk.

## 1. StaxEventItemWriter làm gì?

StaxEventItemWriter nhận các item từ chunk và ghi chúng thành các phần tử XML. Nó không tự đọc dữ liệu và cũng không quyết định quy tắc nghiệp vụ của item; trách nhiệm của nó là serialize object thành XML và quản lý tài liệu đầu ra.

Ví dụ ba Order được ghi thành một file:

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<orders>
    <order>
        <id>1001</id>
        <customerId>501</customerId>
        <amount>125.50</amount>
    </order>
    <order>
        <id>1002</id>
        <customerId>502</customerId>
        <amount>89.00</amount>
    </order>
    <order>
        <id>1003</id>
        <customerId>503</customerId>
        <amount>210.00</amount>
    </order>
</orders>
~~~

Trong ví dụ:

- orders là root element của tài liệu.
- Mỗi order là một item được marshal.
- Các trường bên trong phần tử được quyết định bởi mapping của object và marshaller.
- Writer quản lý phần mở đầu, root element, các item và phần đóng tài liệu.

Nếu Job xử lý hàng triệu item, StAX cho phép ghi tuần tự ra resource thay vì giữ toàn bộ document trong một DOM tree. Bộ nhớ vẫn cần cho chunk, object hiện tại, buffer và hoạt động của marshaller, nhưng không phải chứa toàn bộ XML output.

## 2. StAX và Spring OXM Marshaller

StAX là API xử lý XML theo luồng. Spring Batch dùng StAX event writer để phát các sự kiện XML ra output. Spring OXM cung cấp abstraction Marshaller, chịu trách nhiệm chuyển một object Java thành XML.

Luồng ghi:

~~~text
ItemReader
    |
    v
ItemProcessor
    |
    v
Chunk
    |
    v
StaxEventItemWriter
    |
    +--> root element
    |
    +--> OXM Marshaller cho item 1
    |
    +--> OXM Marshaller cho item 2
    |
    +--> OXM Marshaller cho item N
    |
    v
XML Resource
~~~

Marshaller có thể được triển khai bằng Jaxb2Marshaller hoặc một implementation OXM khác hỗ trợ kết quả StAX. Với JAXB, annotation trên model xác định tên element, attribute, thứ tự và cách biểu diễn các trường.

Cần chọn đúng dependency/API theo phiên bản Spring:
- Spring Framework 6 và Spring Batch 5 dùng namespace Jakarta XML Binding (jakarta.xml.bind).
- Các ứng dụng Spring Framework 5/Spring Batch 4 cũ thường dùng Javax XML Binding (javax.xml.bind).

Không trộn javax và jakarta JAXB annotation trong cùng một model nếu marshaller runtime chỉ hỗ trợ một hệ.

## 3. Tạo model XML bằng JAXB

Ví dụ model đại diện cho một đơn hàng:

~~~java
import jakarta.xml.bind.annotation.XmlAccessType;
import jakarta.xml.bind.annotation.XmlAccessorType;
import jakarta.xml.bind.annotation.XmlElement;
import jakarta.xml.bind.annotation.XmlRootElement;

import java.math.BigDecimal;

@XmlRootElement(name = "order")
@XmlAccessorType(XmlAccessType.FIELD)
public class OrderXml {

    @XmlElement
    private long id;

    @XmlElement
    private long customerId;

    @XmlElement
    private BigDecimal amount;

    public OrderXml() {
    }

    public OrderXml(long id, long customerId, BigDecimal amount) {
        this.id = id;
        this.customerId = customerId;
        this.amount = amount;
    }
}
~~~

@XmlRootElement(name = "order") xác định element gốc khi một object OrderXml được marshal. StaxEventItemWriter sẽ đặt element này bên trong root document mà writer quản lý.

@XmlAccessorType(XmlAccessType.FIELD) yêu cầu JAXB đọc trực tiếp field. Có thể dùng property access hoặc annotation chi tiết hơn tùy model. JAXB model thường cần constructor không tham số theo yêu cầu của provider và cách binding đang dùng.

Nếu item đầu vào của batch là domain object, không nhất thiết phải gắn JAXB annotation lên domain model. Có thể dùng processor chuyển domain object thành DTO chuyên dùng cho XML để giữ ranh giới giữa model nghiệp vụ và format trao đổi.

## 4. Cấu hình Jaxb2Marshaller

Khai báo một marshaller và chỉ định các lớp JAXB cần binding:

~~~java
@Bean
Jaxb2Marshaller orderMarshaller() {
    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(OrderXml.class);
    return marshaller;
}
~~~

Nếu có nhiều model liên quan, có thể đăng ký nhiều class hoặc dùng package scanning theo cấu hình phù hợp. Với XML có namespace, schema hoặc adapter đặc biệt, cấu hình các thuộc tính tương ứng trên marshaller.

Ví dụ marshaller có schema:

~~~java
@Bean
Jaxb2Marshaller orderMarshaller() {
    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(OrderXml.class);
    marshaller.setSchema(
            new ClassPathResource("xml/order-export.xsd"));
    return marshaller;
}
~~~

Việc cấu hình schema cho JAXB marshaller có thể giúp xác thực khi marshal, tùy implementation và cách cấu hình. Cần kiểm tra schema có khớp namespace, element, type và thứ tự trường thực tế hay không. Không mặc định rằng mọi file XML do writer tạo ra đều được validate với XSD nếu ứng dụng chưa cấu hình validation.

## 5. Cấu hình StaxEventItemWriter bằng Builder

Spring Batch cung cấp StaxEventItemWriterBuilder để cấu hình writer:

~~~java
@Bean
StaxEventItemWriter<OrderXml> orderXmlWriter(
        Marshaller orderMarshaller,
        Resource outputResource) {

    return new StaxEventItemWriterBuilder<OrderXml>()
            .name("orderXmlWriter")
            .resource(outputResource)
            .marshaller(orderMarshaller)
            .rootTagName("orders")
            .encoding("UTF-8")
            .overwriteOutput(true)
            .saveState(true)
            .build();
}
~~~

Các cấu hình chính:

- name(...): tên ổn định của writer, được dùng khi lưu state trong ExecutionContext.
- resource(...): file hoặc resource nhận XML output.
- marshaller(...): chuyển từng item thành XML.
- rootTagName(...): tên phần tử gốc bao quanh các item.
- encoding(...): encoding của tài liệu, thường dùng UTF-8.
- overwriteOutput(...): quyết định xử lý resource đã tồn tại khi bắt đầu một output mới.
- saveState(...): bật lưu checkpoint để hỗ trợ restart.

Tên writer cần ổn định qua các lần chạy và triển khai nếu cần khôi phục checkpoint cũ. Đổi tên có thể khiến key state trong ExecutionContext không còn khớp.

Các method khả dụng có thể thay đổi theo phiên bản Spring Batch. Khi dùng builder của phiên bản cụ thể, kiểm tra API tương ứng cho các tùy chọn như XML version, standalone, header/footer callback, transactional và force sync.

## 6. Đặt root element và tên item element

rootTagName định nghĩa element bao ngoài toàn bộ item. Tên element của từng item thường đến từ JAXB metadata của class được marshal hoặc mapping của OXM marshaller.

Ví dụ:

~~~java
.rootTagName("orders")
~~~

và model:

~~~java
@XmlRootElement(name = "order")
public class OrderXml {
    // Các trường của đơn hàng
}
~~~

Kết quả là:

~~~xml
<orders>
    <order>...</order>
    <order>...</order>
</orders>
~~~

Root tag nên là một tên XML hợp lệ và thống nhất với contract mà hệ thống nhận yêu cầu. Không đặt root tag thành tên của item nếu tài liệu phải chứa nhiều item cùng loại.

Nếu cần ghi nhiều loại item trong một tài liệu, cần thiết kế model/Marshaller sao cho mỗi item được marshal thành element hợp lệ trong cùng root. Kiểm tra schema và consumer hỗ trợ các loại phần tử con đó.

## 7. Đưa domain object qua processor trước khi marshal

Không nhất thiết phải ghi trực tiếp entity hoặc domain object. Có thể chuyển dữ liệu sang XML DTO trong processor:

~~~java
@Bean
ItemProcessor<Order, OrderXml> orderXmlProcessor() {
    return order -> new OrderXml(
            order.getId(),
            order.getCustomerId(),
            order.getAmount());
}
~~~

Step khi đó có kiểu input và output khác nhau:

~~~java
@Bean
Step exportOrdersStep(
        JobRepository jobRepository,
        PlatformTransactionManager transactionManager,
        ItemReader<Order> orderReader,
        ItemProcessor<Order, OrderXml> orderXmlProcessor,
        ItemWriter<OrderXml> orderXmlWriter) {

    return new StepBuilder("exportOrdersStep", jobRepository)
            .<Order, OrderXml>chunk(200, transactionManager)
            .reader(orderReader)
            .processor(orderXmlProcessor)
            .writer(orderXmlWriter)
            .build();
}
~~~

Cách này giúp định dạng XML độc lập với schema database và domain model. Nếu schema XML thay đổi, có thể thay DTO/processor/marshaller mà không phải thay đổi entity nghiệp vụ.

Processor cũng là nơi phù hợp để chuẩn hóa giá trị, chuyển enum thành code, định dạng ngày giờ theo contract hoặc loại bỏ field nội bộ không được xuất.

## 8. Cấu hình XML declaration và encoding

XML declaration thường chứa version và encoding, ví dụ:

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
~~~

Encoding của writer phải khớp encoding được khai báo trong XML và cách consumer đọc file. UTF-8 là lựa chọn phổ biến cho trao đổi dữ liệu đa ngôn ngữ.

Nếu output chứa tiếng Việt, hãy kiểm tra cả:
- Encoding của writer.
- Encoding thực tế của file trên filesystem.
- XML declaration.
- Encoding mà hệ thống downstream dùng khi đọc.
- Các ký tự cần escape trong nội dung XML.

Không chỉ đổi chuỗi khai báo encoding="UTF-8" mà vẫn ghi byte theo charset khác. Việc đó tạo tài liệu có khai báo không khớp dữ liệu thực tế.

Nếu cần XML version hoặc standalone declaration đặc biệt, dùng cấu hình được hỗ trợ bởi phiên bản writer và xác nhận output thực tế bằng XML parser.

## 9. HeaderCallback và FooterCallback

StaxEventItemWriter hỗ trợ callback để thêm nội dung XML ở đầu hoặc cuối tài liệu, ví dụ comment, processing instruction hoặc metadata theo contract. Callback nhận một StAX event writer để ghi sự kiện.

Ví dụ thêm comment ở header:

~~~java
StaxWriterCallback header = writer -> {
    XMLEventFactory factory = XMLEventFactory.newFactory();
    writer.add(factory.createComment("Generated by Spring Batch"));
};
~~~

Có thể cấu hình callback qua builder hoặc setter tương ứng của phiên bản Spring Batch:

~~~java
@Bean
StaxEventItemWriter<OrderXml> orderXmlWriter(
        Marshaller orderMarshaller,
        Resource outputResource) {

    StaxWriterCallback header = writer -> {
        XMLEventFactory factory = XMLEventFactory.newFactory();
        writer.add(factory.createComment("Order export"));
    };

    return new StaxEventItemWriterBuilder<OrderXml>()
            .name("orderXmlWriter")
            .resource(outputResource)
            .marshaller(orderMarshaller)
            .rootTagName("orders")
            .headerCallback(header)
            .saveState(true)
            .build();
}
~~~

Callback phải ghi event XML hợp lệ ở đúng vị trí lifecycle. Không ghi thêm một root element độc lập trong header nếu writer đã tự quản lý root element. Tương tự, footer callback không được tạo cấu trúc khiến root bị đóng hai lần hoặc document có nhiều root.

Nếu chỉ cần thêm comment hoặc processing instruction, callback là phù hợp. Nếu cần thay đổi cấu trúc XML phức tạp, nên thiết kế model/marshaller hoặc writer chuyên biệt thay vì chèn chuỗi XML tùy tiện.

## 10. Ghi XML theo chunk

StaxEventItemWriter tham gia chunk-oriented Step giống các ItemWriter khác. Khi chunk được hoàn thành, writer ghi các item của chunk; transaction boundary và cơ chế buffer của writer quyết định khi nào nội dung thực sự được đẩy ra resource.

Ví dụ chunk size 200:

~~~text
Chunk 1: 200 OrderXml -> marshal -> ghi XML items -> commit
Chunk 2: 200 OrderXml -> marshal -> ghi XML items -> commit
Chunk 3: 200 OrderXml -> marshal -> ghi XML items -> commit
...
Step kết thúc -> đóng root/document và resource
~~~

Chunk size không quyết định root tag hay cấu trúc item. Nó quyết định nhóm item được xử lý trong một transaction. Khi chunk thất bại, các item có thể được xử lý lại theo retry/restart semantics của Step.

Không chia file thành nhiều tài liệu XML độc lập nếu contract yêu cầu một document duy nhất. Writer quản lý một root element cho resource của Step và ghi các item như phần tử con.

## 11. Transactional writer và rollback

Writer có thể hỗ trợ transactional behavior bằng cách buffer nội dung của chunk và chỉ ghi phần đã hoàn tất khi transaction commit. Khi transaction rollback, phần output chưa commit có thể được loại khỏi buffer thay vì để lại một phần chunk trong file.

Thuộc tính transactional của StaxEventItemWriter cần được hiểu theo phiên bản framework và transaction synchronization được cấu hình. Nếu tắt transactional behavior, dữ liệu có thể được ghi trực tiếp ra resource trước khi transaction database commit.

Điểm quan trọng: filesystem không tự tham gia cùng transaction JDBC. Ngay cả khi writer phối hợp commit/rollback ở mức chunk, không nên coi database và file là một distributed atomic transaction. Process crash hoặc lỗi filesystem đúng thời điểm có thể khiến business data và output file không đồng bộ.

Để bảo vệ dữ liệu:
- Giữ transactional behavior phù hợp với yêu cầu.
- Kiểm thử lỗi writer và rollback ở giữa chunk.
- Dùng file staging theo JobInstance.
- Chỉ publish output sau khi Job/Step hoàn thành và xác thực.
- Có checksum, record count hoặc manifest để đối soát.
- Thiết kế bước publish có thể retry an toàn.

## 12. Checkpoint và restart

StaxEventItemWriter là một ItemStream writer và có thể lưu state trong Step ExecutionContext. Khi Step restart, writer dùng checkpoint đã lưu để tiếp tục output resource.

Các điều kiện quan trọng:

- Writer có tên ổn định.
- Resource path không thay đổi giữa lần chạy đầu và restart.
- saveState(true) được bật khi cần checkpoint.
- File đã ghi dở còn tồn tại và không bị chỉnh sửa bên ngoài.
- Marshaller, root tag, encoding và format vẫn tương thích.
- Job được restart cùng JobInstance và identifying JobParameters.
- Các component upstream giữ cùng ý nghĩa dữ liệu và thứ tự item.

Nếu output file bị xóa hoặc thay bằng file khác trong khi metadata vẫn giữ checkpoint, writer có thể không khôi phục đúng. Không xóa file cũ trước khi restart và không append thủ công bên ngoài lifecycle của writer.

Đối với restart, cần kiểm thử chính xác hành vi của phiên bản StaxEventItemWriter đang dùng: cách lưu vị trí, cách mở lại resource và cách xử lý phần root/footer đã ghi ở lần trước. Đừng dựa vào suy đoán rằng writer chỉ nối thêm byte vào cuối file.

## 13. Tên file ổn định theo JobInstance

Nếu mỗi JobInstance tạo một tài liệu XML, output path nên ổn định qua các lần restart của instance đó.

Có thể tạo path từ JobInstance ID trong JobExecutionListener:

~~~java
public class XmlOutputPathListener implements JobExecutionListener {

    @Override
    public void beforeJob(JobExecution execution) {
        long instanceId =
                execution.getJobInstance().getInstanceId();

        String path =
                "/batch/output/orders-" + instanceId + ".xml";

        execution.getExecutionContext().putString(
                "xml.output.path", path);
    }
}
~~~

Writer step-scoped lấy path từ Job ExecutionContext:

~~~java
@Bean
@StepScope
StaxEventItemWriter<OrderXml> orderXmlWriter(
        Marshaller orderMarshaller,
        @Value("#{jobExecutionContext['xml.output.path']}")
        String outputPath) {

    return new StaxEventItemWriterBuilder<OrderXml>()
            .name("orderXmlWriter")
            .resource(new FileSystemResource(outputPath))
            .marshaller(orderMarshaller)
            .rootTagName("orders")
            .encoding("UTF-8")
            .saveState(true)
            .build();
}
~~~

JobInstance ID giữ nguyên khi restart cùng instance, còn JobExecution ID thay đổi. Vì vậy, tên output theo JobInstance giúp writer mở lại đúng resource và khôi phục checkpoint.

Trong môi trường nhiều JobRepository hoặc nhiều môi trường deploy, ID có thể chỉ unique trong phạm vi repository. Có thể thêm tên Job, tenant hoặc environment đã chuẩn hóa vào thư mục output.

## 14. overwriteOutput và file đã tồn tại

overwriteOutput quyết định writer có được phép thay thế resource đã tồn tại khi bắt đầu ghi output mới hay không. Chính sách này cần được chọn theo vòng đời JobInstance.

Cần phân biệt:
- **JobInstance mới:** thường tạo một file output mới với tên riêng.
- **Restart cùng JobInstance:** phải tiếp tục resource cũ theo checkpoint.
- **Chạy lại logic nghiệp vụ mới:** tạo JobInstance mới và output path mới nếu muốn giữ lịch sử.

Không bật overwrite một cách máy móc rồi cho rằng restart luôn an toàn. Cần xác nhận writer phân biệt khởi chạy mới và restart có checkpoint trong phiên bản đang dùng. Không xóa file trước khi framework có cơ hội khôi phục state.

Nếu file tồn tại nhưng không có checkpoint hợp lệ, đó có thể là output orphan do crash hoặc metadata không đồng bộ. Cần điều tra JobExecution/StepExecution và dữ liệu đã commit trước khi quyết định xóa, đổi tên hoặc tạo lại file.

## 15. shouldDeleteIfEmpty

Một số cấu hình StaxEventItemWriter cho phép xóa resource nếu không có item nào được ghi, thông qua tùy chọn shouldDeleteIfEmpty.

Tùy chọn này có thể hữu ích nếu downstream chỉ mong đợi file khi có dữ liệu. Tuy nhiên, cần xác định rõ hợp đồng:
- File rỗng có phải là một kết quả hợp lệ không?
- Consumer phân biệt không có file với file XML có root rỗng như thế nào?
- Job hoàn tất không có item có được coi là thành công không?
- Restart có thể tiếp tục sau trạng thái không có item không?

Nếu downstream yêu cầu một document XML hợp lệ kể cả khi không có item, giữ file với root element rỗng có thể phù hợp hơn. Nếu không có file mang ý nghĩa "không có dữ liệu", cấu hình delete-if-empty có thể thích hợp. Hãy kiểm thử cả hai trường hợp và thống nhất với consumer.

## 16. XML namespace và schema

XML contract có thể yêu cầu namespace, prefix, attribute hoặc schema version. Các thông tin này thường được định nghĩa trong JAXB annotations hoặc mapping của marshaller.

Ví dụ:

~~~java
@XmlRootElement(
        name = "order",
        namespace = "urn:example:orders:v1")
@XmlAccessorType(XmlAccessType.FIELD)
public class OrderXml {

    @XmlElement(namespace = "urn:example:orders:v1")
    private long id;
}
~~~

Cần bảo đảm root element do writer tạo và item element do marshaller tạo tương thích về namespace. Nếu root không có namespace nhưng item dùng namespace khác, consumer hoặc XSD có thể từ chối document.

Với namespace prefix, JAXB provider có thể chọn prefix mặc định hoặc prefix được cấu hình. Không nên phụ thuộc vào prefix cụ thể nếu contract chỉ yêu cầu namespace URI. Nếu downstream yêu cầu prefix cố định, cần cấu hình provider hoặc custom namespace mapping và kiểm thử output.

Nên kiểm tra XML bằng XSD/contract của consumer, bao gồm:
- Namespace URI.
- Root element.
- Item element.
- Required/optional element.
- Attribute và element ordering nếu schema quy định.
- Date/time format.
- Decimal precision.
- Null/empty value handling.

## 17. Xử lý null, collection và kiểu dữ liệu

Marshaller quyết định cách Java value được biểu diễn trong XML. Những trường hợp cần chú ý:

- null có thể bị bỏ qua hoặc biểu diễn bằng xsi:nil, tùy JAXB annotation và cấu hình.
- Collection có thể được bao bởi một wrapper element hoặc ghi các element lặp lại, tùy model.
- BigDecimal cần precision/scale phù hợp với contract.
- Date/time cần timezone và format nhất quán.
- Enum có thể được marshal theo tên enum hoặc giá trị được định nghĩa bởi adapter.
- Boolean và numeric type cần format mà consumer hiểu.

Ví dụ collection có wrapper:

~~~java
@XmlElementWrapper(name = "lines")
@XmlElement(name = "line")
private List<OrderLineXml> lines;
~~~

Kết quả có dạng:

~~~xml
<order>
    <lines>
        <line>...</line>
        <line>...</line>
    </lines>
</order>
~~~

Không dựa vào default mapping nếu XML là giao diện tích hợp giữa nhiều hệ thống. Hãy khai báo rõ các element quan trọng và xác nhận với schema hoặc sample file được consumer chấp nhận.

## 18. Header/footer và tài liệu XML hoàn chỉnh

XML document phải có đúng một root element. Writer quản lý root và việc đóng tài liệu khi Step hoàn tất. Header/footer callback chỉ nên thêm các event phù hợp ở vị trí callback được gọi.

Không ghi một root element thứ hai trong header hoặc footer. Không để footer đóng root mà writer sẽ tự đóng lần nữa. Không ghi text tự do chưa escape vào XML event stream.

Nếu cần metadata ở cấp document, có thể:
- Đưa metadata vào attribute hoặc element con của root theo schema.
- Tạo wrapper model phù hợp.
- Dùng callback để thêm comment hoặc processing instruction.
- Tạo custom writer nếu cấu trúc tài liệu vượt quá khả năng writer tiêu chuẩn.

Nếu cần một phần tử metadata trước tất cả order, nhưng vẫn nằm trong root, kiểm tra thứ tự event mà writer và callback tạo ra. Consumer thường dựa vào schema và thứ tự element nên không nên chèn tùy tiện.

## 19. Resource lifecycle và file locking

StaxEventItemWriter mở resource trong lifecycle của Step và đóng khi Step kết thúc. Không mở cùng một file từ một component khác trong lúc writer đang hoạt động.

Các nguyên tắc:
- Chỉ một writer sở hữu một output resource tại một thời điểm.
- Không để log, callback hoặc service khác ghi trực tiếp vào cùng file.
- Bảo đảm thư mục output tồn tại và process có quyền ghi.
- Đóng writer qua lifecycle của framework.
- Không đọc file như output hoàn chỉnh trước khi Step kết thúc.
- Không xóa hoặc rename file khi writer đang mở.
- Theo dõi dung lượng đĩa và xử lý lỗi I/O.

Nếu Job bị kill đột ngột, file có thể chưa có closing root element hoặc footer. Đó là output chưa hoàn chỉnh và không nên được consumer xử lý. Dùng thư mục staging hoặc extension .part, rồi publish sau khi kiểm tra thành công.

## 20. Partitioning và nhiều writer song song

StaxEventItemWriter không nên được nhiều worker dùng đồng thời để ghi vào cùng một file nếu không có cơ chế phối hợp rõ ràng. XML event stream cần thứ tự nhất quán; nhiều writer độc lập có thể xen lẫn event hoặc tạo document không hợp lệ.

Với partitioning, một cách phổ biến là mỗi partition ghi một file riêng:

~~~text
orders-instance-52/
    partition-0.xml
    partition-1.xml
    partition-2.xml
    partition-3.xml
~~~

Sau khi worker hoàn tất, một Step tổng hợp hoặc publish có thể:
- Đọc từng file XML và hợp nhất item vào document cuối.
- Dùng một Job/Step riêng để tạo file tổng.
- Publish manifest trỏ tới nhiều file partition nếu consumer hỗ trợ.

Không nối chuỗi XML file bằng cách ghép byte đơn giản nếu mỗi file có XML declaration và root element riêng. Cần parse từng document và ghi item vào một root document mới, hoặc thiết kế output theo một định dạng nhiều file có manifest.

Mỗi partition nên có resource path ổn định qua restart của partition. Tên file có thể kết hợp JobInstance ID và partition name/key.

## 21. Quan sát và xử lý lỗi marshal

Lỗi marshal có thể xảy ra do model không hợp lệ, annotation sai, kiểu dữ liệu không hỗ trợ, schema mismatch hoặc giá trị runtime không thể chuyển đổi.

Nên ghi nhận:
- JobInstance ID và JobExecution ID.
- Step name.
- Writer name.
- Business key của item nếu có thể xác định an toàn.
- Loại exception marshal.
- Số item/chunk đã commit trước lỗi.
- Output resource và kích thước file.

Không ghi toàn bộ object nếu có dữ liệu cá nhân hoặc bí mật. Một lỗi marshal có thể xuất hiện ở một item cụ thể; nếu Step có skip policy, chỉ skip khi nghiệp vụ cho phép và item có thể được cách ly. Không skip mọi lỗi XML vì lỗi mapping/schema có thể ảnh hưởng tất cả item.

Nếu schema hoặc cấu hình marshaller sai, cần fail Step sớm thay vì tiếp tục tạo một file chứa dữ liệu không tương thích.

## 22. Kiểm thử StaxEventItemWriter

Nên kiểm thử output bằng XML parser hoặc schema validation, không chỉ so sánh chuỗi XML. Khoảng trắng, attribute order và namespace prefix có thể thay đổi mà document vẫn tương đương về cấu trúc.

Các kịch bản quan trọng:

| Kịch bản | Điều cần xác nhận |
|---|---|
| Một item | Có đúng root và một item element |
| Nhiều item | Mỗi item được marshal thành element riêng |
| Không có item | Hành vi file rỗng/root rỗng/delete-if-empty đúng hợp đồng |
| Unicode | Tiếng Việt và ký tự đặc biệt giữ đúng encoding |
| XML special characters | &, <, >, quote được escape hợp lệ |
| Null field | Được bỏ qua hoặc biểu diễn đúng schema |
| Namespace | Root và item có namespace đúng |
| XSD | Output validate với schema của consumer |
| Header/footer | Callback không làm hỏng cấu trúc document |
| Marshal exception | Step xử lý lỗi theo policy và không publish file lỗi |
| Chunk rollback | Phần chunk chưa commit không bị coi là output hoàn tất |
| Restart | Writer khôi phục checkpoint và không ghi trùng item |
| File tồn tại | overwrite/restart xử lý theo cấu hình |
| Partitioning | Worker không ghi đè hoặc xen lẫn output của nhau |
| Disk/I/O error | Job thất bại rõ và resource được đóng |

Một integration test restart:
1. Chạy Job với nhiều chunk.
2. Làm writer hoặc Step thất bại sau một vài chunk đã commit.
3. Xác nhận JobExecution FAILED và file staging còn lại.
4. Restart cùng JobInstance và cùng output path.
5. Xác nhận writer tiếp tục từ checkpoint.
6. Parse XML hoàn chỉnh, kiểm tra root, số item và business key không trùng.
7. Validate XSD và chỉ publish khi mọi kiểm tra cần thiết đạt.

## 23. Lỗi thường gặp khi cấu hình StaxEventItemWriter

**Quên cấu hình Marshaller.** Writer không biết cách chuyển item Java thành XML.

**Root tag không khớp contract.** Document có cấu trúc khác mà consumer mong đợi.

**Model thiếu JAXB mapping phù hợp.** Item có thể marshal sai element, sai namespace hoặc không marshal được.

**Trộn javax và jakarta JAXB.** Annotation và runtime provider không tương thích.

**Encoding khai báo không khớp byte thực tế.** Consumer có thể đọc sai ký tự.

**Không bật saveState khi cần restart.** Writer không có checkpoint phù hợp để tiếp tục.

**Đổi writer name hoặc resource path.** Metadata cũ không còn trỏ tới đúng output state.

**Xóa file khi restart.** Các chunk đã commit trước đó có thể bị mất.

**Dùng chung một writer cho nhiều partition.** Event XML có thể xen lẫn và document bị hỏng.

**Cho consumer đọc file đang ghi.** Consumer có thể nhận document chưa có closing root.

**Ghi XML bằng string callback tùy tiện.** Có thể tạo XML không well-formed hoặc sai namespace.

**Cho rằng file và database commit nguyên tử.** Filesystem không tự tham gia transaction JDBC.

## 24. Quy trình triển khai StaxEventItemWriter

Khi xây dựng Step xuất XML, hãy thực hiện theo trình tự:

1. Xác định XML contract: root, item element, namespace, schema và encoding.
2. Tạo XML DTO hoặc JAXB model phù hợp với contract.
3. Cấu hình Spring OXM Marshaller và chọn đúng Jakarta/Javax theo phiên bản.
4. Khai báo StaxEventItemWriter với name, resource, marshaller và rootTagName.
5. Chọn encoding, overwrite, saveState và transactional theo yêu cầu.
6. Dùng processor để chuyển domain object thành XML DTO nếu cần.
7. Gắn writer vào chunk-oriented Step với chunk size phù hợp.
8. Giữ writer name, output path và mapping ổn định khi cần restart.
9. Dùng staging và publish riêng để downstream chỉ nhận XML hoàn chỉnh.
10. Với partitioning, tạo output resource riêng cho từng worker rồi tổng hợp có kiểm soát.
11. Kiểm thử XML bằng parser/XSD, Unicode, null, marshal failure, rollback và restart.
12. Theo dõi I/O, dung lượng file, số item ghi và lỗi marshal trong vận hành.

StaxEventItemWriter phù hợp khi cần xuất nhiều item thành một XML document theo luồng. Marshaller quyết định cách mỗi object trở thành element; writer quản lý root, resource và checkpoint; chunk transaction xác định ranh giới xử lý. Khi giữ cấu hình ổn định, kiểm soát resource lifecycle và publish file sau khi hoàn tất, ứng dụng có thể tạo XML lớn mà vẫn hỗ trợ restart và cung cấp tài liệu hợp lệ cho hệ thống nhận.
