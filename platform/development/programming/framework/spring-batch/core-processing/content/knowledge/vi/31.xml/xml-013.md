# Kiểm thử XML reader và writer trong Spring Batch

Trong Spring Batch, XML thường được đọc và ghi theo từng fragment thay vì nạp toàn bộ tài liệu vào bộ nhớ. Reader phổ biến là **StaxEventItemReader**; writer tương ứng là **StaxEventItemWriter**. Hai thành phần này phối hợp với StAX để đọc hoặc ghi luồng XML, còn Spring OXM như **Jaxb2Marshaller** chuyển đổi giữa XML fragment và object Java.

Kiểm thử XML reader và writer cần xác nhận nhiều hơn việc Job kết thúc COMPLETED. Reader phải tìm đúng fragment, ánh xạ đúng kiểu dữ liệu, xử lý namespace và dữ liệu lỗi theo mong đợi. Writer phải tạo XML well-formed, đặt đúng root element, marshal đúng field, đóng document và khôi phục trạng thái phù hợp khi restart.

Một chiến lược kiểm thử tốt chia thành ba lớp:

1. **Unit test reader/writer:** kiểm tra riêng cách đọc và ghi fragment bằng file hoặc resource nhỏ.
2. **Restart và failure test:** kiểm tra ExecutionContext, lỗi XML, lỗi marshalling và việc đóng resource.
3. **Step integration test:** chạy Step thật để xác nhận reader, processor, writer, transaction, listener và JobRepository phối hợp đúng.

Bài học này dùng Spring Batch 5 với Java configuration làm ví dụ. Một số builder hoặc test API có thể khác giữa các phiên bản Spring Batch; hãy dùng dependency version của dự án khi triển khai.

## 1. Kiến trúc XML reader và writer

Một luồng XML batch thường có cấu trúc:

~~~xml
<trades>
    <trade>
        <isin>US0000000001</isin>
        <quantity>10</quantity>
        <price>125.50</price>
    </trade>
    <trade>
        <isin>US0000000002</isin>
        <quantity>20</quantity>
        <price>98.75</price>
    </trade>
</trades>
~~~

Reader không nhất thiết phải deserialize cả document thành một object lớn. StaxEventItemReader tìm các phần tử fragment được cấu hình, ví dụ mỗi phần tử trade, rồi chuyển fragment thành object Java.

Writer làm chiều ngược lại: nhận từng object hoặc một chunk object, marshal thành XML fragment và ghi vào file nằm trong root element do writer quản lý.

~~~mermaid
flowchart LR
    A["XML input"] --> B["StaxEventItemReader"]
    B --> C["Unmarshaller"]
    C --> D["Java item"]
    D --> E["Processor"]
    E --> F["Java output item"]
    F --> G["Marshaller"]
    G --> H["StaxEventItemWriter"]
    H --> I["XML output"]
~~~

Các thành phần chính:

| Thành phần | Trách nhiệm |
|---|---|
| StaxEventItemReader | Đọc XML stream và tách fragment |
| Unmarshaller | Chuyển XML fragment thành object Java |
| ItemProcessor | Kiểm tra hoặc biến đổi object |
| Marshaller | Chuyển object Java thành XML fragment |
| StaxEventItemWriter | Ghi fragment và quản lý document/root |
| ExecutionContext | Lưu trạng thái reader/writer để restart |

Một lỗi trong XML có thể phát sinh ở bước parse, unmarshal, process hoặc marshal. Kiểm thử cần phân biệt rõ vị trí lỗi để xác nhận đúng component chịu trách nhiệm.

## 3. Tạo model JAXB để kiểm thử

Ví dụ một item giao dịch:

~~~java
import jakarta.xml.bind.annotation.XmlAccessType;
import jakarta.xml.bind.annotation.XmlAccessorType;
import jakarta.xml.bind.annotation.XmlElement;
import jakarta.xml.bind.annotation.XmlRootElement;

import java.math.BigDecimal;

@XmlRootElement(name = "trade")
@XmlAccessorType(XmlAccessType.FIELD)
public class Trade {

    @XmlElement(required = true)
    private String isin;

    @XmlElement
    private int quantity;

    @XmlElement
    private BigDecimal price;

    public Trade() {
    }

    public Trade(String isin, int quantity, BigDecimal price) {
        this.isin = isin;
        this.quantity = quantity;
        this.price = price;
    }

    public String getIsin() {
        return isin;
    }

    public int getQuantity() {
        return quantity;
    }

    public BigDecimal getPrice() {
        return price;
    }
}
~~~

Một số điểm cần có cho JAXB:

- Class thường cần constructor không tham số.
- Annotation xác định root element và cách ánh xạ field.
- Kiểu dữ liệu cần có hỗ trợ marshal/unmarshal.
- Tên element phải khớp với XML input/output contract.
- Với namespace, cần khai báo namespace phù hợp trong annotation hoặc package metadata.

Không nên chỉ test object bằng equals nếu model chưa override equals/hashCode. Có thể assert từng field hoặc dùng assertion library so sánh thuộc tính.

## 4. Cấu hình Jaxb2Marshaller

Spring OXM cung cấp Jaxb2Marshaller để dùng chung cho reader và writer:

~~~java
@Bean
Jaxb2Marshaller tradeMarshaller() {
    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(Trade.class);
    return marshaller;
}
~~~

Trong test thuần Java không dùng Spring context, có thể khởi tạo marshaller và gọi afterPropertiesSet() trước khi dùng:

~~~java
Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
marshaller.setClassesToBeBound(Trade.class);
marshaller.afterPropertiesSet();
~~~

Jaxb2Marshaller thực hiện cả hai interface Marshaller và Unmarshaller, nên cùng một cấu hình có thể được dùng để đọc và ghi.

Với model lớn, có thể cấu hình context path hoặc các class cần bind. Hãy bảo đảm các class JAXB được phát hiện trong context. Lỗi thiếu class hoặc annotation thường xuất hiện khi khởi tạo marshaller hoặc khi marshal/unmarshal.

## 5. Cấu hình StaxEventItemReader

Ví dụ reader đọc từng fragment trade:

~~~java
@Bean
@StepScope
StaxEventItemReader<Trade> tradeReader(
        Jaxb2Marshaller tradeMarshaller,
        @Value("#{jobParameters['input.file']}") String inputFile) {

    return new StaxEventItemReaderBuilder<Trade>()
        .name("tradeReader")
        .resource(new FileSystemResource(inputFile))
        .addFragmentRootElements("trade")
        .unmarshaller(tradeMarshaller)
        .saveState(true)
        .build();
}
~~~

Ý nghĩa:

- name là tên ổn định dùng cho state trong ExecutionContext.
- resource là file XML đầu vào.
- addFragmentRootElements xác định element đại diện cho một item.
- unmarshaller chuyển fragment XML thành Trade.
- saveState bật lưu trạng thái để hỗ trợ restart.

Nếu XML chứa nhiều element trade bên trong root trades, reader trả về từng Trade riêng. Nó không cần deserialize cả danh sách thành một object duy nhất.

### Vì sao reader thường dùng StepScope?

Đường dẫn input.file thường là JobParameter. @StepScope trì hoãn việc tạo target reader cho đến khi StepExecution tồn tại, giúp SpEL lấy được tham số của lần chạy hiện tại.

Với partitioning, mỗi worker có thể nhận file hoặc phạm vi khác nhau từ StepExecutionContext. Khi đó reader cũng cần StepScope để lấy giá trị riêng của worker.

## 6. Kiểm thử reader độc lập bằng ByteArrayResource

Unit test reader không cần khởi chạy cả Job. Có thể cung cấp XML nhỏ bằng ByteArrayResource:

~~~java
@Test
void readsTradeFragments() throws Exception {
    String xml = """
        <trades>
            <trade>
                <isin>US0000000001</isin>
                <quantity>10</quantity>
                <price>125.50</price>
            </trade>
            <trade>
                <isin>US0000000002</isin>
                <quantity>20</quantity>
                <price>98.75</price>
            </trade>
        </trades>
        """;

    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(Trade.class);
    marshaller.afterPropertiesSet();

    StaxEventItemReader<Trade> reader =
        new StaxEventItemReaderBuilder<Trade>()
            .name("tradeReaderTest")
            .resource(new ByteArrayResource(
                xml.getBytes(StandardCharsets.UTF_8)
            ))
            .addFragmentRootElements("trade")
            .unmarshaller(marshaller)
            .build();

    reader.open(new ExecutionContext());
    try {
        Trade first = reader.read();
        Trade second = reader.read();
        Trade end = reader.read();

        assertEquals("US0000000001", first.getIsin());
        assertEquals(10, first.getQuantity());
        assertEquals(new BigDecimal("125.50"), first.getPrice());

        assertEquals("US0000000002", second.getIsin());
        assertEquals(20, second.getQuantity());
        assertEquals(new BigDecimal("98.75"), second.getPrice());

        assertNull(end);
    } finally {
        reader.close();
    }
}
~~~

Test xác nhận:

- Reader mở được resource XML.
- Mỗi fragment trade tạo ra đúng một object.
- Các field được unmarshal đúng kiểu.
- Khi hết fragment, read() trả null.
- Reader được đóng kể cả khi assertion hoặc read phát sinh lỗi.

Dùng BigDecimal trong assertion để tránh sai số của floating point. XML decimal 125.50 nên được kiểm tra bằng BigDecimal tương ứng.

Nếu test cần kiểm tra file bị khóa hoặc xóa sau close trên operating system, dùng FileSystemResource thay vì ByteArrayResource.

## 8. Kiểm thử reader với namespace

XML thực tế thường có namespace:

~~~xml
<trades xmlns="urn:example:trades">
    <trade>
        <isin>US0000000004</isin>
        <quantity>8</quantity>
        <price>50.00</price>
    </trade>
</trades>
~~~

Tên element có namespace có thể không tương đương với tên local đơn giản. Cách ánh xạ phụ thuộc StAX fragment selection và JAXB metadata.

Với JAXB, model có thể khai báo namespace:

~~~java
@XmlRootElement(
    name = "trade",
    namespace = "urn:example:trades"
)
@XmlAccessorType(XmlAccessType.FIELD)
public class Trade {
    // Các field và annotation tương ứng.
}
~~~

Khi kiểm thử namespace:

- Dùng XML mẫu có đúng namespace URI và prefix thực tế.
- Kiểm tra fragment root được tìm thấy.
- Kiểm tra JAXB ánh xạ đúng element con.
- Không chỉ assert tên prefix, vì prefix có thể khác nhưng namespace URI vẫn giống.
- Kiểm tra cả XML có default namespace và XML dùng prefix tường minh nếu hệ thống nhận cả hai.

Ví dụ:

~~~xml
<t:trades xmlns:t="urn:example:trades">
    <t:trade>
        <t:isin>US0000000004</t:isin>
        <t:quantity>8</t:quantity>
        <t:price>50.00</t:price>
    </t:trade>
</t:trades>
~~~

Một test namespace tốt xác nhận giá trị nghiệp vụ sau unmarshal, không chỉ xác nhận reader trả về một item.

## 9. Kiểm thử reader khi XML không hợp lệ

Các lỗi XML có thể xảy ra ở nhiều mức:

- Document không well-formed, ví dụ thẻ mở không có thẻ đóng.
- Element fragment không đúng cấu trúc.
- Field bắt buộc bị thiếu.
- Giá trị không chuyển được sang kiểu Java.
- Namespace không đúng.
- Dữ liệu không thỏa XSD hoặc validation rule.
- Resource không tồn tại hoặc không đọc được.

Ví dụ XML sai cú pháp:

~~~xml
<trades>
    <trade>
        <isin>US0000000005</isin>
        <quantity>10</quantity>
    </trade>
~~~

Kiểm thử nên xác nhận lỗi xuất hiện ở đúng giai đoạn:

1. Tạo reader với resource XML lỗi.
2. Gọi open().
3. Gọi read() để parser tiêu thụ fragment.
4. Xác nhận exception được ném theo contract của phiên bản đang dùng.
5. Kiểm tra cause chain để xác định lỗi parse hoặc unmarshal.
6. Đóng reader trong finally.

Không nên luôn khẳng định open() phải thất bại. Một số lỗi chỉ được phát hiện khi parser đọc đến phần tử bị lỗi.

### Không assert quá phụ thuộc message

Message từ parser có thể thay đổi theo JDK, JAXB provider hoặc phiên bản Spring. Ưu tiên assert loại exception ở ranh giới ứng dụng và nguyên nhân gốc có ý nghĩa, thay vì so sánh toàn bộ message.

Nếu ứng dụng chuyển exception XML thành exception nghiệp vụ riêng, test lớp chuyển đổi đó và kiểm tra Step phân loại lỗi đúng.

## 10. Kiểm thử XML rỗng và không có fragment

Các input sau có ý nghĩa khác nhau:

~~~xml
<trades/>
~~~

Document rỗng về mặt item nhưng vẫn là XML hợp lệ.

~~~xml
<orders>
    <order>...</order>
</orders>
~~~

Document hợp lệ nhưng không có fragment trade mà reader đang tìm.

~~~text
(empty file)
~~~

Resource không có nội dung XML.

Cần quyết định theo contract:

- XML root rỗng có phải batch hợp lệ với 0 item không?
- Không tìm thấy fragment có phải dữ liệu sai cấu trúc không?
- File 0 byte là lỗi hay nguồn rỗng được chấp nhận?
- Có cần Step validation trước khi chạy reader không?

Test từng trường hợp riêng. Không gom chúng thành một assertion chung rằng reader trả null, vì XML rỗng hợp lệ và file XML hỏng có hành vi khác nhau.

## 11. Kiểm thử reader restart bằng ExecutionContext

Reader restartable cần lưu trạng thái vào ExecutionContext. Test trực tiếp lifecycle có thể xác nhận item đã đọc không bị đọc lại sau khi mở reader lần nữa.

Ví dụ:

~~~java
@Test
void resumesFromSavedExecutionContext() throws Exception {
    ExecutionContext context = new ExecutionContext();

    StaxEventItemReader<Trade> firstReader = createTradeReader();
    firstReader.open(context);

    Trade first = firstReader.read();
    assertEquals("US0000000001", first.getIsin());

    firstReader.update(context);
    firstReader.close();

    StaxEventItemReader<Trade> restartedReader = createTradeReader();
    restartedReader.open(context);
    try {
        Trade next = restartedReader.read();
        assertEquals("US0000000002", next.getIsin());
    } finally {
        restartedReader.close();
    }
}
~~~

Trong test thực tế, createTradeReader() phải tạo reader mới có cùng name, resource và fragment configuration. ExecutionContext được dùng lại để mô phỏng checkpoint.

Cần xác nhận:

- Reader có name ổn định.
- saveState được bật.
- update() được gọi tại checkpoint mong muốn.
- Context được lưu trước khi reader close.
- Reader mới dùng cùng nguồn và cấu hình tương thích.
- Item tiếp theo đúng vị trí mong đợi.

Đây là test lifecycle ở mức reader. Test restart toàn Job vẫn cần JobRepository và JobLauncherTestUtils để xác nhận checkpoint được Spring Batch lưu và khôi phục trong execution thật.

## 12. Cấu hình StaxEventItemWriter

Writer ghi object Java thành XML fragment bên trong root element:

~~~java
@Bean
@StepScope
StaxEventItemWriter<Trade> tradeWriter(
        Jaxb2Marshaller tradeMarshaller,
        @Value("#{jobParameters['output.file']}") String outputFile) {

    return new StaxEventItemWriterBuilder<Trade>()
        .name("tradeWriter")
        .resource(new FileSystemResource(outputFile))
        .marshaller(tradeMarshaller)
        .rootTagName("trades")
        .overwriteOutput(true)
        .saveState(true)
        .build();
}
~~~

Các phần quan trọng:

- name đặt tên ổn định cho writer state.
- resource xác định file XML output.
- marshaller chuyển Trade thành fragment.
- rootTagName xác định root element bao quanh các fragment.
- overwriteOutput quyết định hành vi khi file đã tồn tại theo cấu hình writer.
- saveState bật lưu trạng thái phục vụ restart.

Nếu file output được dùng cho restart, không cấu hình overwrite hoặc append một cách tùy tiện. Chính sách file phải phù hợp với JobInstance và checkpoint.

## 13. Kiểm thử writer độc lập

Có thể test writer với file tạm và kiểm tra XML sau khi đóng:

~~~java
@TempDir
Path tempDirectory;

@Test
void writesTradeFragmentsInsideRootElement() throws Exception {
    Path output = tempDirectory.resolve("trades.xml");

    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(Trade.class);
    marshaller.afterPropertiesSet();

    StaxEventItemWriter<Trade> writer =
        new StaxEventItemWriterBuilder<Trade>()
            .name("tradeWriterTest")
            .resource(new FileSystemResource(output))
            .marshaller(marshaller)
            .rootTagName("trades")
            .overwriteOutput(true)
            .build();

    writer.open(new ExecutionContext());
    try {
        Chunk<Trade> chunk = new Chunk<>();
        chunk.add(new Trade(
            "US0000000001", 10, new BigDecimal("125.50")
        ));
        chunk.add(new Trade(
            "US0000000002", 20, new BigDecimal("98.75")
        ));

        writer.write(chunk);
    } finally {
        writer.close();
    }

    assertTrue(Files.exists(output));
    assertTrue(Files.size(output) > 0);
}
~~~

Đoạn test trên xác nhận file được tạo và writer đóng. Chỉ kiểm tra file tồn tại hoặc size lớn hơn 0 là chưa đủ; cần parse lại XML và kiểm tra fragment cùng field.

Trong test production, nếu write() ném exception và close() cũng có thể ném exception, giữ nguyên lỗi gốc và ghi nhận lỗi close. Có thể dùng helper cleanup hoặc try-with-resources wrapper phù hợp với API ItemStream.

## 14. Kiểm thử writer bằng round-trip reader

Một cách hữu ích để kiểm tra writer là đọc lại file do writer tạo bằng StaxEventItemReader.

Quy trình:

1. Tạo một số Trade object.
2. Ghi chúng bằng StaxEventItemWriter.
3. Đóng writer để hoàn tất root document.
4. Tạo StaxEventItemReader trỏ đến file output.
5. Đọc lại từng fragment.
6. So sánh giá trị field với object ban đầu.
7. Xác nhận reader trả null sau fragment cuối.

Ví dụ phần đọc lại:

~~~java
StaxEventItemReader<Trade> verificationReader =
    new StaxEventItemReaderBuilder<Trade>()
        .name("verificationReader")
        .resource(new FileSystemResource(output))
        .addFragmentRootElements("trade")
        .unmarshaller(marshaller)
        .build();

verificationReader.open(new ExecutionContext());
try {
    Trade first = verificationReader.read();
    Trade second = verificationReader.read();

    assertEquals("US0000000001", first.getIsin());
    assertEquals(new BigDecimal("125.50"), first.getPrice());

    assertEquals("US0000000002", second.getIsin());
    assertEquals(new BigDecimal("98.75"), second.getPrice());

    assertNull(verificationReader.read());
} finally {
    verificationReader.close();
}
~~~

Round-trip kiểm tra cả marshalling lẫn parsing. Tuy nhiên, nếu cùng một cấu hình JAXB có lỗi mapping đối xứng, reader và writer có thể cùng hiểu sai theo một cách. Với contract quan trọng, bổ sung assertion trên XML structure hoặc test fixture độc lập do đối tác cung cấp.

## 15. Kiểm tra XML well-formed độc lập

Ngoài round-trip bằng cùng Spring Batch reader, có thể dùng XML parser tiêu chuẩn để xác nhận output là document hợp lệ.

Ví dụ dùng DocumentBuilder:

~~~java
DocumentBuilderFactory factory =
    DocumentBuilderFactory.newInstance();

factory.setNamespaceAware(true);

DocumentBuilder builder = factory.newDocumentBuilder();
Document document = builder.parse(output.toFile());

assertEquals(
    "trades",
    document.getDocumentElement().getLocalName() == null
        ? document.getDocumentElement().getNodeName()
        : document.getDocumentElement().getLocalName()
);
~~~

Test này xác nhận document có thể parse và root element đúng. Có thể tiếp tục đếm element trade và kiểm tra namespace URI.

Với XML không tin cậy, cấu hình parser test và production để vô hiệu hóa external entity/DTD theo yêu cầu bảo mật. Không bật external entity chỉ để test một file fixture đơn giản.

## 16. Kiểm thử writer với XML namespace

Nếu output yêu cầu namespace, model JAXB hoặc package metadata phải khai báo namespace phù hợp. Test cần parse XML và kiểm tra namespace URI.

Ví dụ mong muốn:

~~~xml
<t:trades xmlns:t="urn:example:trades">
    <t:trade>
        <t:isin>US0000000006</t:isin>
        <t:quantity>3</t:quantity>
        <t:price>15.00</t:price>
    </t:trade>
</t:trades>
~~~

Không assert prefix t nếu prefix không phải một phần contract. Các prefix như t, ns2 hoặc mặc định có thể thay đổi mà namespace URI vẫn giữ nguyên.

Nên kiểm tra:

- Root namespace URI.
- Namespace URI của fragment.
- Tên local element.
- Số fragment.
- Giá trị field.
- Thứ tự element nếu contract yêu cầu.

## 17. Kiểm thử XSD validation

Nếu XML phải tuân theo schema XSD, cần kiểm thử cả tài liệu hợp lệ và không hợp lệ.

Có thể cấu hình Jaxb2Marshaller với schema được quản lý trong classpath, tùy API của phiên bản Spring OXM:

~~~java
@Bean
Jaxb2Marshaller tradeMarshaller() {
    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(Trade.class);
    marshaller.setSchemas(
        new ClassPathResource("xsd/trades.xsd")
    );
    return marshaller;
}
~~~

XSD có thể ràng buộc:

- Element bắt buộc.
- Kiểu số và giới hạn giá trị.
- Thứ tự element.
- Namespace.
- Cardinality.
- Pattern hoặc enumeration.

Test nên có fixture XML hợp lệ và fixture vi phạm schema. Xác nhận lỗi được phát hiện ở giai đoạn unmarshal/validation phù hợp với cấu hình.

Một lưu ý: validation do JAXB marshaller cung cấp phụ thuộc cách fragment được marshal/unmarshal và schema được cấu hình. Nếu contract yêu cầu validate toàn bộ document, có thể cần một Step validation riêng dùng Validator của JAXP trên file hoàn chỉnh.

## 18. Kiểm thử dữ liệu không ánh xạ được

Một số XML well-formed nhưng giá trị không thể chuyển thành kiểu Java:

~~~xml
<trade>
    <isin>US0000000007</isin>
    <quantity>ten</quantity>
    <price>20.00</price>
</trade>
~~~

Element quantity tồn tại nhưng không thể chuyển thành integer. Đây là lỗi mapping/unmarshal, khác với lỗi cú pháp XML.

Kiểm thử cần xác nhận:

- Reader ném exception phù hợp.
- Cause chain chỉ ra lỗi chuyển kiểu.
- Step có policy skip/retry/fail phù hợp với nghiệp vụ.
- Không tạo object một phần được xem như hợp lệ.
- Listener ghi nhận lỗi theo đúng giai đoạn nếu Step có skip.

Không skip mọi lỗi unmarshal một cách mặc định. Một số lỗi có thể là dữ liệu riêng lẻ, nhưng lỗi schema hoặc namespace sai hàng loạt có thể chỉ ra file đầu vào không đúng contract và nên fail sớm.

## 19. Kiểm thử file XML bị cắt giữa chừng

Một file có thể bị truncate do upload chưa hoàn tất hoặc tiến trình tạo file bị dừng:

~~~xml
<trades>
    <trade>
        <isin>US0000000008</isin>
        <quantity>2</quantity>
        <price>30.00</price>
    </trade>
    <trade>
        <isin>US0000000009</isin>
~~~

Parser có thể đọc được fragment đầu rồi gặp lỗi khi đọc phần còn lại hoặc khi phát hiện document chưa kết thúc. Điều này có nghĩa reader có thể đã trả một số item trước khi document lỗi.

Test nên xác nhận:

- Item hợp lệ trước vị trí lỗi có thể đã được đọc.
- Lỗi parse cuối file làm Step kết thúc theo policy.
- Writer hoặc database không công bố dữ liệu chưa hoàn chỉnh ngoài chính sách.
- Resource được đóng khi Step kết thúc.
- Restart không giả định file nguồn đã hoàn chỉnh nếu nguồn có thể thay đổi.

Với file trao đổi, nên kiểm tra kích thước, checksum hoặc marker upload hoàn tất trước khi khởi chạy Job. Không đọc file đang được producer ghi dở.

## 20. Kiểm thử XML reader với StepScope

Nếu reader dùng JobParameters, test trực tiếp reader target ngoài StepScope có thể không mô phỏng đúng lifecycle. Có thể dùng Spring Batch test utilities để kích hoạt scope.

Một cách là chạy Step bằng JobLauncherTestUtils với JobParameters chứa input.file. Cách khác, với test hẹp cho một scoped bean, dùng StepScopeTestUtils hoặc thiết lập StepExecution trong test context theo phiên bản spring-batch-test đang dùng.

Ví dụ ý tưởng:

~~~java
StepExecution stepExecution = MetaDataInstanceFactory.createStepExecution(
    new JobParametersBuilder()
        .addString("input.file", inputPath.toString())
        .toJobParameters()
);

Trade first = StepScopeTestUtils.doInStepScope(
    stepExecution,
    () -> tradeReader.read()
);
~~~

Đây là minh họa về cách kích hoạt StepScope. Trong test thực tế, reader cần được mở trong cùng scope, gọi read, rồi đóng bằng try/finally; không chỉ gọi read trên proxy chưa open.

Nếu test một Step hoàn chỉnh, JobLauncherTestUtils thường sát hành vi production hơn vì Spring Batch tự quản lý open/update/close.

## 21. Kiểm thử Step hoàn chỉnh với spring-batch-test

Khi cần xác nhận reader, processor, writer và JobRepository phối hợp đúng, dùng spring-batch-test.

Ví dụ test:

~~~java
@SpringBatchTest
@SpringJUnitConfig(BatchTestConfiguration.class)
class XmlImportStepTest {

    @Autowired
    private JobLauncherTestUtils jobLauncherTestUtils;

    @Test
    void importsXmlFile() throws Exception {
        JobParameters parameters = new JobParametersBuilder()
            .addString("input.file", "src/test/resources/trades.xml")
            .addString("output.file", "build/test-output/trades-out.xml")
            .toJobParameters();

        JobExecution execution =
            jobLauncherTestUtils.launchStep(
                "importXmlStep",
                parameters
            );

        assertEquals(BatchStatus.COMPLETED, execution.getStatus());

        StepExecution stepExecution =
            execution.getStepExecutions().iterator().next();

        assertEquals(2, stepExecution.getReadCount());
        assertEquals(2, stepExecution.getWriteCount());
        assertEquals(0, stepExecution.getReadSkipCount());
    }
}
~~~

Cấu hình test cần có Job/Step mà JobLauncherTestUtils sử dụng. Với dự án có nhiều Job, cần gắn đúng Job vào test utility theo cách cấu hình được hỗ trợ.

### Điều gì được kiểm tra ở đây?

- JobParameters được truyền vào Step.
- StepScope được kích hoạt.
- Reader mở XML input.
- Processor chạy trên từng item.
- Writer ghi XML output.
- ExecutionContext và StepExecution được cập nhật.
- JobRepository lưu metadata.
- Step đóng resource khi kết thúc.

Sau khi Step chạy, vẫn cần đọc output file và xác nhận XML có nội dung đúng. BatchStatus COMPLETED chỉ chứng minh flow hoàn tất theo trạng thái, không chứng minh mapping XML chính xác.

## 22. Kiểm thử reader và writer cùng processor

Processor có thể thay đổi dữ liệu trước khi ghi:

~~~java
@Bean
ItemProcessor<Trade, Trade> normalizeTradeProcessor() {
    return trade -> new Trade(
        trade.getIsin().trim(),
        trade.getQuantity(),
        trade.getPrice().setScale(2, RoundingMode.HALF_UP)
    );
}
~~~

Test Step nên dùng input có khoảng trắng hoặc scale khác nhau và kiểm tra output đã được chuẩn hóa.

Tách test:

- Reader test xác nhận object đầu vào.
- Processor test xác nhận quy tắc biến đổi.
- Writer test xác nhận object được serialize.
- Step test xác nhận pipeline ghép đúng thứ tự.

Cách chia này giúp lỗi mapping không bị nhầm với lỗi processor hoặc writer.

## 23. Kiểm thử lỗi writer và transaction

Writer có thể lỗi vì:

- Output path không có quyền ghi.
- Thư mục không tồn tại.
- Disk đầy.
- Marshaller không hỗ trợ một kiểu object.
- XML encoding hoặc resource gặp lỗi I/O.
- Resource đã đóng hoặc bị dùng sai lifecycle.

Test có thể dùng resource không ghi được hoặc một writer giả lập ném exception để xác nhận Step thất bại.

Cần phân biệt:

- Exception trong marshal trước khi ghi fragment.
- IOException trong lúc ghi file.
- Exception khi close hoàn tất document.
- Lỗi database ở writer khác nếu Step có composite writer.

Nếu Step dùng database và file writer cùng lúc, transaction database không tự rollback file đã flush. Với output XML cần công bố nhất quán, hãy ghi staging file rồi publish sau khi Step thành công.

## 24. Kiểm thử close và resource lifecycle

Reader/writer XML có resource cần được đóng. Test cần xác nhận:

- Reader close sau Step thành công.
- Reader close sau processor exception.
- Writer close sau write exception.
- StAX reader/writer giải phóng underlying stream.
- Lỗi close được ghi nhận và không làm mất lỗi chính.
- File tạm không bị giữ handle sau khi Step kết thúc.

Khi kiểm thử độc lập, dùng try/finally để gọi close. Khi kiểm thử Step thật, để Spring Batch quản lý lifecycle và quan sát file/resource sau khi Step hoàn tất.

Không gọi close từ nhiều nơi nếu component đã được framework quản lý. Nếu một custom composite chứa nhiều ItemStream delegate, đăng ký delegate hoặc chuyển tiếp open/update/close đúng cách.

## 25. Kiểm thử restart toàn Step

Để test restart thực tế:

1. Dùng XML input có nhiều fragment.
2. Cấu hình commit interval nhỏ để có nhiều chunk.
3. Cho Step thất bại sau khi một chunk đã commit.
4. Xác nhận StepExecution đầu FAILED và ExecutionContext có checkpoint.
5. Restart cùng JobInstance bằng identifying JobParameters ban đầu.
6. Xác nhận reader tiếp tục từ vị trí đúng.
7. Xác nhận writer tiếp tục output theo chính sách restart.
8. Kiểm tra không bỏ sót hoặc ghi trùng item.

Với XML reader, restart cần cùng nguồn và cấu trúc tương thích. Nếu file input bị thay đổi giữa lần chạy và restart, checkpoint có thể trỏ đến vị trí không còn tương ứng với nội dung cũ.

Nên lưu hoặc kiểm tra checksum/version của input nếu nguồn có thể bị thay thế. Với file output, writer name và resource phải ổn định trong cùng JobInstance để framework khôi phục đúng state.

## 26. Kiểm thử skip và retry cho XML

Không phải lỗi XML nào cũng nên được skip hoặc retry.

| Lỗi | Retry | Skip | Hướng xử lý thường gặp |
|---|---|---|---|
| File chưa sẵn sàng hoặc upload chưa xong | Có thể retry trước khi mở Step | Không | Chờ nguồn hoàn tất |
| XML sai cú pháp | Thường không | Thường không cho cả file | Reject file và báo nguồn |
| Một fragment vi phạm quy tắc nghiệp vụ | Không nhất thiết | Có thể | Skip item nếu contract cho phép |
| Dịch vụ enrichment timeout | Có thể | Có thể sau retry nếu nghiệp vụ cho phép | Retry có giới hạn |
| Output disk đầy | Thường không retry item ngay | Không | Fail Step và xử lý hạ tầng |
| JAXB mapping/schema sai trên toàn file | Không | Thường không | Fail sớm, sửa contract |

StaxEventItemReader có thể phát hiện lỗi parse ở cấp document thay vì item. Nếu XML không well-formed, không nên giả định framework có thể skip riêng fragment bị lỗi và tiếp tục an toàn.

Với dữ liệu nghiệp vụ lỗi nhưng XML vẫn hợp lệ, processor có thể ném exception riêng để Step áp dụng skip policy. Khi đó test cần xác nhận processSkipCount tăng và các item hợp lệ vẫn được ghi.

## 27. Kiểm thử XML theo schema và contract đối tác

Một XML có thể well-formed nhưng vẫn sai contract. Ví dụ:

- Sai namespace URI.
- Thiếu element bắt buộc.
- Thứ tự element sai.
- Giá trị nằm ngoài enumeration.
- Decimal có scale không hợp lệ.
- Date/time không theo format yêu cầu.
- Có thêm element không được phép.
- Sai version của root document.

Tạo fixture theo contract:

- Một file hợp lệ tối thiểu.
- Một file hợp lệ đầy đủ.
- Một file có namespace prefix khác nhưng cùng URI.
- Một file thiếu element bắt buộc.
- Một file sai kiểu dữ liệu.
- Một file sai namespace.
- Một file bị truncate.
- Một file rỗng theo định nghĩa nghiệp vụ.

Tên fixture nên mô tả tình huống để test dễ đọc, ví dụ trades-valid.xml, trades-missing-price.xml hoặc trades-wrong-namespace.xml.

Không dùng một file fixture duy nhất cho mọi test vì khi thay đổi model, test có thể không còn phân biệt được lỗi nào đang được kiểm tra.

## 28. Kiểm thử hiệu năng và kích thước XML

StaxEventItemReader dùng StAX để đọc theo stream, phù hợp với file lớn hơn cách deserialize toàn bộ document. Tuy nhiên, test nhỏ không chứng minh được hành vi với file lớn.

Các kiểm thử hiệu năng có thể đo:

- Thời gian đọc theo số fragment.
- Heap usage khi tăng kích thước file.
- Kích thước object graph của một fragment.
- Thời gian marshal từng chunk.
- Tốc độ ghi output.
- Ảnh hưởng của namespace và validation.
- Thời gian restart từ checkpoint.

Không cần tạo file cực lớn trong mọi unit test. Có thể tạo fixture nhỏ cho logic và một performance/integration test riêng chạy với dữ liệu đại diện.

Nếu một fragment chứa danh sách con rất lớn, streaming document không có nghĩa object fragment đó cũng nhỏ. Cần giới hạn kích thước fragment và thiết kế model phù hợp.

## 29. Kiểm thử XML security

XML parser cần được cấu hình an toàn với nguồn không tin cậy. External entity hoặc DTD có thể dẫn tới truy cập tài nguyên ngoài dự kiến nếu parser cho phép.

Các nguyên tắc:

- Không bật external general entities nếu không cần.
- Không cho phép external DTD tùy tiện.
- Hạn chế truy cập schema từ URL không tin cậy.
- Dùng schema local đã được kiểm soát khi cần validation.
- Kiểm tra giới hạn kích thước input và độ sâu/nesting phù hợp.
- Không log toàn bộ XML chứa dữ liệu nhạy cảm.
- Kiểm thử XML có DOCTYPE hoặc external entity và xác nhận chính sách từ chối phù hợp.

Cấu hình StAX factory hoặc parser phụ thuộc cách tạo XMLInputFactory và phiên bản Spring Batch. Nếu cần custom factory, xác nhận builder/API trong version đang dùng và kiểm thử thực tế thay vì giả định parser mặc định có cùng security flags trên mọi runtime.

## 30. Test helper để tạo reader và writer

Để tránh lặp cấu hình, có thể tách factory helper trong test:

~~~java
private Jaxb2Marshaller createMarshaller() throws Exception {
    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(Trade.class);
    marshaller.afterPropertiesSet();
    return marshaller;
}

private StaxEventItemReader<Trade> createReader(Resource resource)
        throws Exception {
    return new StaxEventItemReaderBuilder<Trade>()
        .name("tradeReaderTest")
        .resource(resource)
        .addFragmentRootElements("trade")
        .unmarshaller(createMarshaller())
        .saveState(true)
        .build();
}

private StaxEventItemWriter<Trade> createWriter(Path output)
        throws Exception {
    return new StaxEventItemWriterBuilder<Trade>()
        .name("tradeWriterTest")
        .resource(new FileSystemResource(output))
        .marshaller(createMarshaller())
        .rootTagName("trades")
        .overwriteOutput(true)
        .saveState(true)
        .build();
}
~~~

Helper chỉ nên giữ phần cấu hình lặp lại. Mỗi test vẫn cần chỉ rõ fixture, hành động và assertion để mục tiêu kiểm tra không bị ẩn.

Nếu helper tạo marshaller mới mỗi lần, test độc lập và tránh chia sẻ mutable state. Nếu tái sử dụng marshaller singleton, xác nhận provider implementation thread-safe theo cách ứng dụng sử dụng.

## 31. Ma trận kiểm thử đề xuất

Có thể tổ chức test suite theo bảng:

| Nhóm | Trường hợp | Assertion chính |
|---|---|---|
| Reader cơ bản | Nhiều fragment | Số item và field đúng |
| Reader empty | Root không có fragment | Kết quả theo policy empty input |
| Reader parse | XML malformed | Exception parse được nhận diện |
| Reader mapping | Giá trị sai kiểu | Unmarshal failure |
| Reader namespace | Prefix/default namespace | Namespace URI và field đúng |
| Reader restart | Lưu rồi khôi phục context | Đọc tiếp đúng fragment |
| Writer cơ bản | Ghi nhiều object | Root và fragment đúng |
| Writer round-trip | Ghi rồi đọc lại | Field giữ nguyên |
| Writer encoding | UTF-8 và ký tự Unicode | Nội dung không lỗi mã hóa |
| Writer failure | Marshal/I/O exception | Step thất bại và resource đóng |
| Step integration | Reader-processor-writer | BatchStatus và counters đúng |
| Step restart | Thất bại sau chunk commit | Không mất hoặc ghi trùng item |
| Schema | XML hợp lệ/không hợp lệ | Validation đúng contract |
| Security | DTD/external entity | Chính sách parser được áp dụng |

Không phải mọi hàng đều cần thành một test class riêng. Hãy nhóm theo component và dùng fixture dùng chung khi chúng biểu diễn cùng contract.

## 32. Những lỗi kiểm thử thường gặp

### Chỉ kiểm tra Job COMPLETED

Job có thể hoàn tất nhưng XML mapping sai hoặc output thiếu field. Đọc lại file và kiểm tra nội dung.

### Dùng XML fixture quá nhỏ

Một fragment đơn không kiểm tra được nhiều item, EOF, restart hoặc namespace. Bổ sung fixture có nhiều fragment và tình huống lỗi.

### Không đóng reader/writer trong unit test

Resource có thể bị giữ và ảnh hưởng test sau. Dùng try/finally hoặc lifecycle helper.

### Assert chuỗi XML chính xác từng byte

Marshaller có thể thay đổi whitespace, attribute order hoặc namespace prefix mà XML vẫn tương đương. Parse XML và assert cấu trúc/giá trị, trừ khi contract yêu cầu byte-level output.

### Dùng cùng reader để xác nhận writer duy nhất

Round-trip hữu ích nhưng không thay thế kiểm tra XML structure độc lập. Reader và writer có thể cùng chia sẻ một mapping sai.

### Bỏ qua namespace

Test chỉ dùng XML không namespace có thể bỏ sót lỗi thường gặp khi tích hợp đối tác.

### Không kiểm thử restart state

Reader có thể đọc đúng từ đầu nhưng sai khi khôi phục ExecutionContext. Tạo test checkpoint riêng.

### Thay đổi input giữa restart

Checkpoint chỉ có ý nghĩa khi nguồn tương ứng vẫn ổn định. Kiểm tra checksum/version hoặc bảo đảm file bất biến.

### Skip mọi exception XML

Lỗi document-level như malformed XML thường không thể xử lý bằng cách bỏ một item. Phân biệt lỗi fragment nghiệp vụ và lỗi cấu trúc toàn document.

### Chỉ assert file tồn tại

File có thể rỗng, thiếu root closing tag hoặc không có fragment. Parse output và kiểm tra record.

### Dùng parser test không an toàn

Test parser có thể mở external entity hoặc truy cập file/URL ngoài dự kiến. Dùng cấu hình XML an toàn và fixture kiểm soát.

## 33. Quy trình xây dựng test suite XML

Khi kiểm thử một pipeline XML trong Spring Batch, có thể làm theo trình tự:

1. **Xác định contract XML:** root, fragment, namespace, field, schema và encoding.
2. **Tạo model JAXB:** khai báo root element, field và kiểu dữ liệu.
3. **Cấu hình marshaller:** dùng chung mapping phù hợp cho reader và writer.
4. **Test reader độc lập:** nhiều fragment, empty input, malformed XML, namespace và mapping.
5. **Test reader restart:** lưu ExecutionContext rồi mở reader mới để đọc tiếp.
6. **Test writer độc lập:** ghi chunk, đóng writer và parse output.
7. **Test round-trip:** ghi object rồi đọc lại để kiểm tra field.
8. **Test schema/security:** dữ liệu hợp lệ, sai schema, DTD và external entity.
9. **Test Step integration:** chạy reader, processor và writer với JobLauncherTestUtils.
10. **Test failure/restart:** xác nhận resource close, checkpoint và dữ liệu không trùng.
11. **Kiểm tra output cuối:** parse XML, đếm fragment, xác nhận root và nội dung.
12. **Tách performance test:** dùng file đại diện khi cần đánh giá bộ nhớ và tốc độ.

## 34. Những điểm cần nhớ

- StaxEventItemReader đọc từng XML fragment; StaxEventItemWriter ghi object thành fragment trong root document.
- Jaxb2Marshaller có thể dùng làm cả Marshaller và Unmarshaller.
- Reader cần cấu hình fragment root element đúng với XML input.
- Writer cần rootTagName, resource và marshaller đúng contract.
- Unit test reader bằng ByteArrayResource hoặc file tạm giúp kiểm tra mapping độc lập.
- Unit test writer phải đóng writer và parse output; chỉ kiểm tra file tồn tại là chưa đủ.
- Round-trip reader/writer hữu ích nhưng cần thêm kiểm tra XML structure độc lập.
- Kiểm thử namespace theo URI, không phụ thuộc prefix.
- Kiểm thử riêng XML malformed, fragment sai kiểu, document rỗng và file bị truncate.
- saveState, writer name ổn định và ExecutionContext cần được kiểm tra trong restart test.
- spring-batch-test và JobLauncherTestUtils giúp chạy Step thật với JobParameters và kiểm tra StepExecution counters.
- Job COMPLETED không chứng minh XML output đúng; cần parse và xác nhận record.
- Không skip mọi lỗi XML; phân biệt lỗi dữ liệu riêng lẻ với lỗi cấu trúc toàn document.
- Kiểm tra XML security, external entities, schema và giới hạn input.
- Dùng fixture mô tả rõ tình huống và giữ test độc lập theo component.

Kiểm thử XML reader và writer hiệu quả cần bao phủ cả mapping, cấu trúc document, lifecycle resource và khả năng restart. Khi kiểm tra riêng reader/writer rồi xác nhận lại bằng một Step integration test, ta có thể xác định lỗi ở đúng tầng và bảo đảm file XML đầu ra đáp ứng contract mà hệ thống nhận yêu cầu.
