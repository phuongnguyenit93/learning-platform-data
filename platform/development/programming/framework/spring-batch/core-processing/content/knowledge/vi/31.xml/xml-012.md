# XML lỗi giữa chừng

Trong Spring Batch, XML input thường được đọc theo từng fragment bằng `StaxEventItemReader`. Nếu file bị hỏng ở giữa luồng, parser có thể đọc và xử lý được một số fragment trước khi gặp lỗi cú pháp XML. Những chunk đã commit vẫn có thể được giữ lại, nhưng phần còn lại của tài liệu thường không thể tiếp tục đọc một cách an toàn vì XML parser cần cấu trúc tài liệu hợp lệ để xác định ranh giới phần tử.

Điểm quan trọng là phân biệt **XML không well-formed** với **một record XML hợp lệ nhưng dữ liệu nghiệp vụ không hợp lệ**. Lỗi cấu trúc như thiếu thẻ đóng, thẻ lồng sai hoặc ký tự markup bất hợp lệ thường là lỗi parser nghiêm trọng; skip policy không thể tự tìm lại ranh giới đáng tin cậy để tiếp tục. Ngược lại, một phần tử XML hoàn chỉnh nhưng chứa giá trị nghiệp vụ sai có thể được kiểm tra ở Processor và xử lý bằng skip/reject nếu quy tắc nghiệp vụ cho phép.

## 1. XML lỗi giữa chừng có thể xảy ra như thế nào?

Một file XML có thể bị lỗi trước khi Job bắt đầu, trong lúc Reader đang đọc, hoặc tại cuối file khi parser phát hiện tài liệu chưa hoàn chỉnh.

Ví dụ file XML hợp lệ:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<orders>
    <order>
        <id>ORD-1001</id>
        <amount>125.50</amount>
    </order>
    <order>
        <id>ORD-1002</id>
        <amount>89.90</amount>
    </order>
</orders>
```

Một số lỗi thường gặp:

```xml
<!-- Thiếu thẻ đóng order -->
<orders>
    <order><id>ORD-1001</id></order>
    <order><id>ORD-1002</id>
</orders>
```

```xml
<!-- Thẻ lồng sai thứ tự -->
<orders>
    <order>
        <id>ORD-1001</order>
    </id>
</orders>
```

```xml
<!-- File bị cắt giữa nội dung -->
<orders>
    <order><id>ORD-1001</id></order>
    <order><id>ORD-1002</id><amount>89.
```

Parser có thể đã trả về các phần tử `order` đầu tiên trước khi gặp lỗi ở một phần tử sau. Với trường hợp file bị cắt ở cuối, các record trước đó có thể hợp lệ nhưng phần tử gốc hoặc record cuối chưa được đóng.

## 2. StaxEventItemReader đọc XML theo fragment

`StaxEventItemReader<T>` sử dụng StAX (Streaming API for XML) để đọc XML theo luồng sự kiện, không cần nạp toàn bộ tài liệu vào bộ nhớ. Thông thường, ứng dụng chỉ định tên phần tử gốc của mỗi record bằng `addFragmentRootElements(...)` và cung cấp `Unmarshaller` để chuyển fragment thành object.

Ví dụ cấu trúc:

```text
orders.xml
  |
  +--> <orders>                 phần tử gốc tài liệu
         |
         +--> <order> ... </order>  fragment 1 -> Order
         +--> <order> ... </order>  fragment 2 -> Order
         +--> <order> ... </order>  fragment 3 -> Order
```

Reader chỉ trả về từng `order` fragment cho chunk pipeline. Phần tử gốc `<orders>` là cấu trúc bao ngoài; mỗi `<order>` là một item. Việc đọc theo fragment giúp xử lý file lớn theo từng item và từng chunk.

## 3. Cấu hình StaxEventItemReader

Ví dụ cấu hình với Spring Batch 5 và JAXB:

```java
import org.springframework.batch.core.configuration.annotation.StepScope;
import org.springframework.batch.item.xml.StaxEventItemReader;
import org.springframework.batch.item.xml.builder.StaxEventItemReaderBuilder;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Bean;
import org.springframework.core.io.FileSystemResource;
import org.springframework.oxm.jaxb.Jaxb2Marshaller;

@Bean
public Jaxb2Marshaller orderMarshaller() {
    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(OrderXml.class);
    return marshaller;
}

@Bean
@StepScope
public StaxEventItemReader<OrderXml> orderXmlReader(
        @Value("#{jobParameters['inputFile']}") String inputFile,
        Jaxb2Marshaller orderMarshaller) {

    return new StaxEventItemReaderBuilder<OrderXml>()
            .name("orderXmlReader")
            .resource(new FileSystemResource(inputFile))
            .addFragmentRootElements("order")
            .unmarshaller(orderMarshaller)
            .saveState(true)
            .build();
}
```

`OrderXml` là lớp JAXB tương ứng với một phần tử `<order>`. `@StepScope` cho phép Reader nhận file từ JobParameters của StepExecution hiện tại. `saveState(true)` bật lưu trạng thái đọc để Spring Batch có thể khôi phục vị trí khi restart.

Ví dụ lớp JAXB tối giản:

```java
import jakarta.xml.bind.annotation.XmlAccessType;
import jakarta.xml.bind.annotation.XmlAccessorType;
import jakarta.xml.bind.annotation.XmlElement;
import jakarta.xml.bind.annotation.XmlRootElement;

@XmlRootElement(name = "order")
@XmlAccessorType(XmlAccessType.FIELD)
public class OrderXml {

    @XmlElement(name = "id")
    private String id;

    @XmlElement(name = "amount")
    private String amount;

    public String getId() { return id; }
    public String getAmount() { return amount; }
}
```

Giữ các giá trị đầu vào ở dạng `String` trong lớp XML có thể giúp phân biệt lỗi parse XML với lỗi chuyển đổi nghiệp vụ. Processor có thể parse `amount` thành `BigDecimal` và đưa ra exception có ngữ nghĩa rõ ràng nếu giá trị không hợp lệ.

## 4. Phân biệt lỗi cú pháp XML và lỗi dữ liệu của một record

Không phải mọi lỗi xuất hiện khi đọc XML đều có cùng khả năng phục hồi.

| Loại lỗi | Ví dụ | Cách xử lý phù hợp |
|---|---|---|
| XML không well-formed | Thiếu thẻ đóng, thẻ lồng sai, markup hỏng | Dừng xử lý file, cách ly và sửa/nhận lại file. |
| XML bị truncate | File kết thúc giữa một element | Xem file là chưa hoàn chỉnh; nhận lại hoặc tạo lại file. |
| Không khớp XSD | Thiếu element bắt buộc, sai cấu trúc theo schema | Validate và từ chối file, hoặc áp dụng quy tắc record-level nếu thiết kế cho phép. |
| Unmarshal lỗi trong fragment hoàn chỉnh | Kiểu hoặc cấu trúc field không map được | Có thể phân loại riêng; chỉ skip khi fragment đã được tách an toàn và parser còn tiếp tục được. |
| Lỗi nghiệp vụ sau mapping | Số tiền âm, mã trạng thái không được hỗ trợ | Validate trong Processor; skip/reject nếu nghiệp vụ cho phép. |
| Lỗi ghi database | Deadlock, timeout, constraint violation | Retry hoặc fail theo exception và chính sách transaction. |

Lỗi well-formedness là lỗi cấu trúc của luồng XML. Sau một lỗi parser fatal, parser chuẩn thường không thể xác định chắc chắn vị trí bắt đầu record kế tiếp. Vì vậy, không nên xem lỗi đó như một item độc lập có thể bỏ qua bằng `.skip(...)` rồi tiếp tục đọc phần còn lại.

## 5. Vì sao skip policy không tự khôi phục XML hỏng?

Skip policy trong Spring Batch quyết định có bỏ qua một exception trong quá trình đọc, xử lý hoặc ghi hay không. Tuy nhiên, policy không sửa parser state và không biết cách tái đồng bộ một tài liệu XML bị hỏng.

Ví dụ:

```text
<orders>
  <order>...</order>     fragment 1: đọc được
  <order>...</order>     fragment 2: đọc được
  <order>                 bắt đầu fragment 3
    <id>ORD-3</id>
  <wrong-close>           markup lỗi
  <order>...</order>     parser không thể tin cậy ranh giới tiếp theo
</orders>
```

Ngay cả khi cấu hình `.skip(XMLStreamException.class)`, điều đó không bảo đảm StAX reader có thể tiếp tục từ record tiếp theo. Parser có thể đã ở trạng thái lỗi và không thể tiếp tục phát event hợp lệ. Hành vi thực tế còn phụ thuộc exception được Reader bọc lại và trạng thái stream; không nên dựa vào skip exception parser để phục hồi cấu trúc tài liệu.

Nếu cần bỏ qua record lỗi và tiếp tục các record sau, format đầu vào phải có ranh giới record độc lập và có thể nhận diện lại an toàn. XML tài liệu thông thường không cung cấp cơ chế resynchronization như vậy sau một lỗi well-formedness fatal.

## 6. Điều gì xảy ra khi lỗi xuất hiện sau một số chunk đã commit?

Giả sử Job đọc 1.000 order mỗi chunk. Hai chunk đầu đã commit, nhưng parser gặp markup lỗi khi đang đọc chunk thứ ba:

```text
JobExecution #1
  Chunk 1: 1.000 items -> COMMIT
  Chunk 2: 1.000 items -> COMMIT
  Chunk 3: parser error -> ROLLBACK / Step FAILED
  Các item sau lỗi: chưa đọc được
```

Các thay đổi nghiệp vụ trong chunk đã commit thường vẫn được giữ. Chunk đang lỗi không được commit; metadata checkpoint thường chỉ phản ánh ranh giới commit trước đó.

Nếu restart cùng JobInstance với cùng file hỏng, Reader khôi phục checkpoint đã lưu và sẽ đọc lại phần chưa commit. Khi tới vị trí XML lỗi, parser lại gặp lỗi tương tự. Restart không thể tự sửa file nguồn.

```text
Restart cùng JobInstance
  |
  v
Khôi phục checkpoint sau Chunk 2
  |
  v
Đọc lại phần bắt đầu Chunk 3
  |
  v
Gặp cùng markup lỗi
  |
  v
Step tiếp tục FAILED
```

Nếu lỗi nằm ở cuối file, Reader có thể đã trả về các fragment cuối cùng hợp lệ nhưng parser chỉ phát hiện thiếu thẻ đóng khi đọc tiếp đến EOF. Các chunk đã commit vẫn được giữ, nhưng lần đọc tiếp theo khi restart có thể tiếp tục gặp lỗi ở EOF.

## 7. Quy trình kiểm tra XML trước khi chạy Job

Với file XML trao đổi giữa các hệ thống, cách vận hành đáng tin cậy là xác nhận file đã được ghi xong và kiểm tra cấu trúc trước khi khởi chạy Job xử lý nghiệp vụ.

Một quy trình phổ biến:

```text
Producer ghi orders.xml.part
          |
          v
Producer đóng file hoàn toàn
          |
          v
Đổi tên thành orders.xml
          |
          v
Validate well-formedness / XSD
          |
      +---+---+
      |       |
      v       v
   Hợp lệ   Không hợp lệ
      |       |
      v       v
Launch Job  Quarantine + báo lỗi
```

Producer nên ghi file dưới tên tạm, sau đó đóng file và đổi tên sang tên chính thức. Job chỉ nhận file có tên chính thức. Điều này giảm nguy cơ Reader mở file khi producer vẫn đang ghi dở.

Nếu filesystem hỗ trợ, `Files.move(..., StandardCopyOption.ATOMIC_MOVE)` có thể dùng để công bố file hoàn chỉnh bằng rename nguyên tử trong cùng filesystem. Không phải mọi filesystem hoặc network mount đều hỗ trợ atomic move; cần kiểm tra môi trường triển khai.

## 8. Kiểm tra XML well-formed trước khi xử lý

Có thể dùng Java XML Validation API để parse toàn bộ tài liệu trước khi launch Job. Việc validate bằng `StreamSource` là streaming theo parser, không yêu cầu nạp toàn bộ cây XML vào memory như DOM.

```java
import java.nio.file.Path;

import javax.xml.XMLConstants;
import javax.xml.transform.stream.StreamSource;
import javax.xml.validation.SchemaFactory;

public class XmlPreValidator {

    public void validateWellFormed(Path xmlFile) throws Exception {
        SchemaFactory factory = SchemaFactory.newInstance(
                XMLConstants.W3C_XML_SCHEMA_NS_URI);
        factory.setProperty(XMLConstants.ACCESS_EXTERNAL_DTD, "");
        factory.setProperty(XMLConstants.ACCESS_EXTERNAL_SCHEMA, "");

        // Parse XML để kiểm tra cấu trúc; không cần schema nếu chỉ kiểm tra well-formed.
        var schema = factory.newSchema();
        var validator = schema.newValidator();
        validator.setProperty(XMLConstants.ACCESS_EXTERNAL_DTD, "");
        validator.setProperty(XMLConstants.ACCESS_EXTERNAL_SCHEMA, "");
        validator.validate(new StreamSource(xmlFile.toFile()));
    }
}
```

Ví dụ trên minh họa việc parse và kiểm tra tài liệu với Validator không gắn XSD cụ thể. Nếu cần kiểm tra schema, tạo `Schema` từ file XSD rồi dùng Validator đó:

```java
var schema = factory.newSchema(xsdFile.toFile());
var validator = schema.newValidator();
validator.setProperty(XMLConstants.ACCESS_EXTERNAL_DTD, "");
validator.setProperty(XMLConstants.ACCESS_EXTERNAL_SCHEMA, "");
validator.validate(new StreamSource(xmlFile.toFile()));
```

Các thuộc tính `ACCESS_EXTERNAL_DTD` và `ACCESS_EXTERNAL_SCHEMA` hạn chế truy cập tài nguyên ngoài khi parser xử lý XML/XSD. Với XML không tin cậy, cần cấu hình parser an toàn và không cho phép tải DTD/schema tùy ý từ mạng.

Pre-validation có nghĩa file được đọc thêm một lần: một lần để xác nhận cấu trúc, một lần bởi batch Reader để xử lý record. Đổi lại, Job có thể từ chối file hỏng trước khi ghi dữ liệu nghiệp vụ. Nếu file rất lớn, thao tác validate vẫn có thể streaming nhưng sẽ tốn thêm I/O.

## 9. Validate với XSD để phát hiện sai schema

Well-formed XML chưa chắc đúng schema nghiệp vụ. Ví dụ `<order>` có thể hợp lệ về cú pháp nhưng thiếu `id`, có element sai thứ tự hoặc chứa cấu trúc không được XSD cho phép.

Ví dụ XSD đơn giản:

```xml
<xs:schema xmlns:xs="http://www.w3.org/2001/XMLSchema">
  <xs:element name="orders">
    <xs:complexType>
      <xs:sequence>
        <xs:element name="order" minOccurs="0" maxOccurs="unbounded">
          <xs:complexType>
            <xs:sequence>
              <xs:element name="id" type="xs:string"/>
              <xs:element name="amount" type="xs:decimal"/>
            </xs:sequence>
          </xs:complexType>
        </xs:element>
      </xs:sequence>
    </xs:complexType>
  </xs:element>
</xs:schema>
```

Nếu một file phải tuân thủ toàn bộ schema trước khi import, validate XSD toàn file trước khi chạy Job. Khi XSD không hợp lệ, ghi nhận vị trí lỗi và cách ly file.

Nếu yêu cầu nghiệp vụ là chấp nhận các record hợp lệ và loại riêng record không hợp lệ, không nên mặc định dùng validation toàn file theo cách khiến một record sai làm từ chối toàn bộ file. Có thể đọc fragment, map thành DTO đủ linh hoạt rồi validate từng record trong Processor. Cần xác định rõ quy tắc với XML fragment thiếu field hoặc sai kiểu để việc unmarshal không dừng parser trước khi Processor nhận item.

## 10. Xử lý lỗi nghiệp vụ ở cấp record

Một XML fragment có thể hoàn toàn well-formed nhưng giá trị bên trong không hợp lệ:

```xml
<order>
    <id>ORD-1003</id>
    <amount>-25.00</amount>
</order>
```

Đây là record hợp lệ về cấu trúc XML; quy tắc nghiệp vụ có thể không cho phép amount âm. Để phân loại lỗi ở cấp item, có thể parse giá trị thành kiểu phù hợp trong Processor và ném exception nghiệp vụ:

```java
import java.math.BigDecimal;

import org.springframework.batch.item.ItemProcessor;

public class OrderProcessor
        implements ItemProcessor<OrderXml, ProcessedOrder> {

    @Override
    public ProcessedOrder process(OrderXml item) {
        BigDecimal amount;
        try {
            amount = new BigDecimal(item.getAmount());
        } catch (NumberFormatException ex) {
            throw new InvalidOrderException("Invalid amount", ex);
        }

        if (amount.signum() < 0) {
            throw new InvalidOrderException("Amount cannot be negative");
        }

        return new ProcessedOrder(item.getId(), amount);
    }
}
```

Sau đó cấu hình skip cho exception nghiệp vụ nếu chính sách cho phép:

```java
return new StepBuilder("importOrdersStep", jobRepository)
        .<OrderXml, ProcessedOrder>chunk(500, transactionManager)
        .reader(orderXmlReader)
        .processor(orderProcessor)
        .writer(orderWriter)
        .faultTolerant()
        .skip(InvalidOrderException.class)
        .skipLimit(100)
        .listener(orderSkipListener)
        .build();
```

Ở đây parser đã tạo được một `OrderXml` hoàn chỉnh; lỗi được phát hiện trong Processor và có thể được skip theo policy. Cần ghi reject record theo khóa nghiệp vụ để tránh duplicate nếu chunk rollback và item được xử lý lại khi restart.

## 11. Nếu bắt buộc phải tiếp tục sau một record XML hỏng

Một tài liệu XML chuẩn không có ranh giới phục hồi chung sau markup hỏng. Nếu yêu cầu nghiệp vụ bắt buộc phải tiếp tục xử lý các record phía sau, cần thay đổi cách đóng gói dữ liệu hoặc định nghĩa một giao thức framing riêng.

Các lựa chọn:

1. **Một XML document cho mỗi record:** mỗi file có thể được parse và cách ly độc lập. Một file hỏng không ngăn đọc file kế tiếp.
2. **Một file archive chứa nhiều XML độc lập:** ví dụ mỗi entry trong ZIP là một XML document riêng, có manifest và trạng thái xử lý theo entry.
3. **Producer ghi record độc lập theo message:** mỗi message chứa một XML document hoàn chỉnh và có ID riêng.
4. **Định dạng record có framing:** mỗi record có độ dài hoặc delimiter ngoài XML được quy định rõ, để reader có thể tìm lại ranh giới mà không đoán cấu trúc XML.
5. **Custom recovery parser:** chỉ dùng nếu định dạng có quy tắc resynchronization được đặc tả, kiểm thử kỹ và có thể chứng minh không ghép nhầm record.

Không nên dùng regex để tìm chuỗi `<order>` tiếp theo sau parser error. Chuỗi đó có thể xuất hiện trong CDATA, comment, attribute hoặc nội dung text; parser không thể xác định chắc đó là phần tử thực sự. Cách phục hồi dựa vào tìm chuỗi có thể tạo record sai hoặc bỏ qua dữ liệu.

## 12. Cách xử lý file lỗi trong quy trình batch

Một quy trình vận hành rõ ràng nên phân loại file trước khi import:

| Trạng thái file | Hành động |
|---|---|
| Chưa hoàn tất, vẫn mang tên `.part` | Chưa launch Job. |
| Đã đóng nhưng XML không well-formed | Cách ly file, ghi lỗi parser và yêu cầu producer gửi lại. |
| Well-formed nhưng sai XSD | Cách ly hoặc áp dụng quy trình xử lý schema version phù hợp. |
| Well-formed và đúng schema, có record sai nghiệp vụ | Import record hợp lệ, ghi reject cho record sai theo skip policy. |
| File hợp lệ và toàn bộ record thành công | Publish kết quả và đánh dấu batch hoàn tất. |

Có thể lưu thông tin lỗi trong bảng `batch_file_audit`:

```text
batch_file_audit
--------------------------------------------------------------
file_id | checksum | status     | error_line | error_message
--------------------------------------------------------------
F-1001  | ...      | REJECTED   | 2451       | XML not well-formed
F-1002  | ...      | PROCESSING | null       | null
F-1003  | ...      | COMPLETED  | null       | null
```

Audit giúp tránh launch lặp cùng file, truy vết nguyên nhân và phân biệt file lỗi cấu trúc với record bị reject. Nên lưu checksum hoặc version để biết file có bị thay đổi giữa các lần chạy hay không.

## 13. Restart khi file XML bị sửa

Giả sử JobInstance được tạo với `inputFile=orders.xml` và đã commit một số chunk trước khi lỗi parser. Sau đó producer sửa nội dung file tại cùng đường dẫn.

Restart cùng JobInstance sẽ dùng checkpoint cũ. Nếu nội dung file đã thay đổi, vị trí item cũ có thể không còn tương ứng với cùng record. Điều này có thể làm bỏ sót hoặc xử lý trùng dữ liệu.

Quy tắc an toàn:

- Không sửa file input đã được một JobInstance bắt đầu xử lý.
- Giữ file bất biến trong suốt vòng đời restart.
- Lưu checksum, kích thước, thời điểm nhận hoặc object version làm metadata của batch.
- Nếu file cần được sửa hoặc producer gửi lại phiên bản mới, tạo file version mới và một JobInstance mới với identifying parameter thể hiện version/checksum.
- Chỉ reset/reprocess cùng JobInstance khi có quy trình vận hành rõ ràng, hiểu ảnh hưởng đến checkpoint và dữ liệu đã commit.

Ví dụ JobParameters:

```java
JobParameters parameters = new JobParametersBuilder()
        .addString("fileId", "orders-2026-11-15-v2", true)
        .addString("inputFile", "/data/in/orders-v2.xml", true)
        .addString("checksum", checksum, true)
        .toJobParameters();
```

Nếu nội dung đã sửa là một batch nghiệp vụ mới, identifying parameters mới giúp tạo JobInstance riêng. Writer vẫn cần idempotency/business key để bảo vệ dữ liệu nếu cùng record xuất hiện trong hai phiên bản file.

## 14. Phân biệt lỗi XML với lỗi transaction và Writer

Không phải mọi Job failure khi đọc XML đều do parser:

- Parser có thể ném lỗi khi tài liệu không well-formed.
- Unmarshaller có thể không map được fragment.
- Processor có thể ném exception do dữ liệu nghiệp vụ.
- Writer có thể thất bại do database, disk hoặc constraint.
- JobRepository có thể không lưu được checkpoint do metadata database mất kết nối.

Khi điều tra, cần xem exception cause chain, vị trí dòng/cột nếu có, StepExecution, read/process/write counts và checkpoint. Không nên chỉ dựa vào thông báo tổng quát `Job failed`.

Nếu parser báo lỗi tại dòng 2451, hãy đối chiếu file gốc đúng checksum và kiểm tra nội dung quanh vị trí đó. Nếu lỗi ở Writer, XML có thể hoàn toàn hợp lệ; cần kiểm tra database và transaction. Nếu lỗi metadata xảy ra sau khi target đã commit, restart cần dựa trên Writer idempotent để tránh duplicate.

## 15. Kiểm thử XML lỗi giữa chừng

Nên kiểm thử các trường hợp file hỏng ở nhiều vị trí và xác nhận dữ liệu đã commit, trạng thái Job và hành vi restart.

Các kịch bản hữu ích:

1. **XML hợp lệ:** tất cả fragment được đọc và ghi đúng.
2. **Markup lỗi giữa file:** một số chunk đầu commit, parser gặp lỗi, Step/Job thất bại.
3. **Thiếu root closing tag:** các fragment có thể đã được đọc trước khi lỗi xuất hiện ở EOF.
4. **File truncate giữa fragment:** record cuối không hoàn chỉnh và parser không thể trả item hoàn chỉnh.
5. **Sai schema:** pre-validation từ chối file trước khi ghi dữ liệu nếu chính sách là all-or-nothing.
6. **Sai dữ liệu nghiệp vụ trong fragment hợp lệ:** Processor ném exception và skip/reject đúng policy.
7. **Restart file vẫn hỏng:** cùng JobInstance tiếp tục gặp lỗi tại cùng vùng chưa commit.
8. **Sửa file và tạo instance version mới:** Job xử lý phiên bản mới theo checkpoint mới, không dùng checkpoint cũ cho nội dung đã thay đổi.
9. **Duplicate khi restart:** Writer không tạo record nghiệp vụ trùng cho các chunk đã commit hoặc item được thử lại.

Ví dụ integration test nên xác nhận:

```java
assertEquals(BatchStatus.FAILED, jobExecution.getStatus());
assertEquals(expectedCommittedCount, countRowsInTarget(batchId));
assertTrue(jobExecution.getAllFailureExceptions().stream()
        .anyMatch(this::hasXmlParsingCause));
```

Đây là assertion minh họa; `hasXmlParsingCause` là helper của test để tìm lỗi parser trong cause chain. Không nên phụ thuộc vào một class exception duy nhất nếu Reader bọc lỗi XML qua các lớp exception khác nhau giữa các phiên bản.

Khi kiểm thử restart, dùng cùng identifying JobParameters và cùng file checksum để tái hiện đúng JobInstance. Sau đó sửa file thành một version mới và xác nhận JobInstance mới được tạo nếu nghiệp vụ yêu cầu xử lý lại.

## 16. Những lỗi thường gặp

| Lỗi | Hậu quả | Cách xử lý |
|---|---|---|
| Skip mọi XML parser exception | Parser có thể đã mất khả năng đồng bộ và không đọc được fragment sau. | Fail file, cách ly và yêu cầu nguồn gửi lại hoặc sửa file. |
| Cho rằng chunk đã commit sẽ rollback khi XML lỗi | Dữ liệu các chunk đã commit vẫn tồn tại. | Theo dõi checkpoint và thiết kế Writer idempotent. |
| Restart file vẫn hỏng và kỳ vọng tự vượt qua lỗi | Reader gặp lại cùng vùng XML lỗi chưa commit. | Sửa/nhận lại file hoặc dùng định dạng record độc lập. |
| Sửa file tại cùng đường dẫn rồi restart checkpoint cũ | Vị trí checkpoint có thể trỏ đến record khác. | Giữ file immutable; version/checksum mới tạo JobInstance mới. |
| Dùng regex tìm thẻ tiếp theo để phục hồi | Có thể nhầm text, comment, CDATA hoặc attribute với element. | Dùng parser chuẩn và framing được đặc tả nếu cần recovery. |
| Nhầm lỗi nghiệp vụ với lỗi well-formedness | Từ chối cả file khi chỉ một record sai, hoặc skip lỗi cấu trúc nguy hiểm. | Tách parse, schema validation và business validation. |
| Producer ghi file trong khi Reader đang mở | Job có thể đọc file chưa hoàn chỉnh. | Dùng tên tạm `.part`, đóng file rồi publish bằng rename. |
| Xem footer hoặc số record đã đọc là bằng chứng file hợp lệ | Parser có thể phát hiện lỗi ở EOF sau nhiều record. | Validate toàn file và chỉ publish sau khi Job hoàn tất. |

## Kết luận

Khi XML lỗi giữa chừng, `StaxEventItemReader` có thể đã trả về và Spring Batch đã commit một số fragment trước khi parser gặp lỗi. Các chunk đã commit thường được giữ; chunk chưa commit có thể được đọc lại khi restart. Nếu tài liệu không well-formed, parser chuẩn thường không thể tự tìm ranh giới record kế tiếp, nên skip policy không phải cơ chế phục hồi đáng tin cậy cho lỗi markup. Hãy kiểm tra file hoàn chỉnh và XSD trước khi xử lý khi yêu cầu là all-or-nothing, giữ input immutable qua restart, cách ly file hỏng và dùng Processor/skip policy cho lỗi nghiệp vụ của fragment hợp lệ. Nếu cần tiếp tục sau record XML hỏng, hãy thiết kế đầu vào thành các XML document hoặc record độc lập có ranh giới phục hồi rõ ràng.
