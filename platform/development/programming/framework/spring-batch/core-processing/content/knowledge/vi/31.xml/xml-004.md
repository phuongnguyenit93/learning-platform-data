# Resource XML lớn và streaming

Khi Spring Batch cần xử lý một file XML rất lớn, cách đọc toàn bộ tài liệu vào một cây DOM thường không phù hợp. DOM tạo object đại diện cho phần lớn hoặc toàn bộ cấu trúc XML trong bộ nhớ. Với file có hàng triệu phần tử, bộ nhớ có thể tăng nhanh, gây garbage collection liên tục hoặc OutOfMemoryError.

Cách tiếp cận phù hợp hơn là **streaming**: parser đọc tuần tự XML, tìm từng phần tử nghiệp vụ cần xử lý, chuyển một fragment thành object rồi giao object đó cho chunk pipeline. Spring Batch cung cấp **StaxEventItemReader** để đọc các fragment XML theo kiểu streaming và kết hợp với Spring OXM, chẳng hạn Jaxb2Marshaller, để chuyển fragment thành Java object.

Streaming giúp bộ nhớ phụ thuộc chủ yếu vào fragment đang đọc và chunk đang xử lý, thay vì toàn bộ tài liệu. Tuy nhiên, nó không làm cho mọi XML trở nên nhẹ: một fragment đơn lẻ quá lớn, object graph quá sâu hoặc chunk size quá cao vẫn có thể tiêu thụ nhiều memory.

## 1. Vì sao XML lớn cần streaming?

Một file XML có thể chứa hàng trăm nghìn hoặc hàng triệu record:

~~~xml
<orders>
    <order>
        <id>1001</id>
        <customerId>C001</customerId>
        <amount>125.50</amount>
    </order>
    <order>
        <id>1002</id>
        <customerId>C002</customerId>
        <amount>89.00</amount>
    </order>
    <!-- Hàng triệu order khác -->
</orders>
~~~

Nếu ứng dụng dùng DOM parser để parse toàn bộ file, parser có thể tạo một node cho mỗi element, attribute và text node. Sau đó code thường giữ cả Document hoặc danh sách object trong memory.

Với file lớn, chi phí không chỉ là kích thước file trên đĩa. Một XML 1 GB có thể tạo object graph trong JVM lớn hơn đáng kể do object header, reference, String, collection và dữ liệu đã decode.

Streaming xử lý tuần tự:

~~~text
XML file
   |
   v
StAX parser đọc event
   |
   v
Tìm fragment <order>
   |
   v
Unmarshal một order
   |
   v
ItemProcessor
   |
   v
ItemWriter
   |
   v
Commit chunk
   |
   v
Đọc fragment tiếp theo
~~~

Parser không cần giữ toàn bộ document trong bộ nhớ. Khi fragment hiện tại đã được chuyển thành object và xử lý xong, các event và object không còn được tham chiếu có thể được garbage collector thu hồi.

## 2. DOM, SAX và StAX khác nhau thế nào?

Java có nhiều mô hình parse XML. Chọn mô hình phù hợp phụ thuộc cách ứng dụng cần truy cập tài liệu.

| Mô hình | Cách hoạt động | Memory và cách dùng |
|---|---|---|
| DOM | Parse thành cây document | Dễ truy cập ngẫu nhiên, thường giữ nhiều node trong memory |
| SAX | Parser phát callback khi gặp start/end element và text | Streaming, ít memory nhưng code callback cần quản lý state |
| StAX | Ứng dụng chủ động kéo event từ parser | Streaming, dễ kiểm soát tiến trình đọc tuần tự |
| JAXB | Map XML sang Java object | Là lớp binding, có thể dùng cùng StAX để unmarshal từng fragment |

DOM thuận tiện khi tài liệu nhỏ và cần truy cập nhiều vị trí. SAX phù hợp với pipeline event-driven. StAX phù hợp khi ứng dụng muốn chủ động lấy event tiếp theo và xử lý fragment theo thứ tự.

JAXB không phải một mô hình streaming độc lập cho toàn bộ file. Nếu unmarshal toàn bộ root document thành object chứa danh sách lớn, ứng dụng vẫn có thể giữ toàn bộ object graph. Kết hợp StAX với JAXB theo từng fragment giúp giới hạn phạm vi object được tạo.

## 3. StAX là gì?

StAX (Streaming API for XML) cung cấp cách đọc và ghi XML theo event hoặc cursor.

Hai API đọc chính:

- XMLStreamReader: cursor-based, ứng dụng gọi next() để di chuyển tới event tiếp theo.
- XMLEventReader: iterator/event-based, trả về từng XMLEvent.

Một số event thường gặp:

- START_DOCUMENT và END_DOCUMENT.
- START_ELEMENT và END_ELEMENT.
- CHARACTERS hoặc CDATA.
- COMMENT và PROCESSING_INSTRUCTION.

Ví dụ đọc event bằng XMLStreamReader:

~~~java
XMLInputFactory factory = XMLInputFactory.newFactory();

try (InputStream input = Files.newInputStream(path)) {
    XMLStreamReader reader =
            factory.createXMLStreamReader(input);

    try {
        while (reader.hasNext()) {
            int event = reader.next();

            if (event == XMLStreamConstants.START_ELEMENT) {
                System.out.println(reader.getLocalName());
            }
        }
    } finally {
        reader.close();
    }
}
~~~

Đây là ví dụ cơ bản để minh họa cursor. Trong ứng dụng thực tế, cần xử lý exception, đóng cả stream và parser đúng lifecycle, đồng thời cấu hình parser an toàn với XML không tin cậy.

StaxEventItemReader của Spring Batch sử dụng mô hình StAX event để tìm fragment và cung cấp từng fragment cho Unmarshaller.

## 4. Fragment là gì?

Trong một tài liệu XML lớn, fragment là phần tử con đại diện cho một đơn vị nghiệp vụ có thể xử lý độc lập.

Ví dụ:

~~~xml
<orders>
    <order>
        <id>1001</id>
        <amount>125.50</amount>
    </order>
    <order>
        <id>1002</id>
        <amount>89.00</amount>
    </order>
</orders>
~~~

Ở đây:

- orders là root element của document.
- order là fragment root.
- Mỗi order có thể trở thành một item trong Spring Batch.

Reader sẽ tìm từng phần tử order, tạo representation cho fragment đó và gọi Unmarshaller để chuyển thành object Order.

Không nên chọn root element quá lớn nếu nó chứa toàn bộ danh sách record. Nếu fragment root là orders, reader có thể phải unmarshal toàn bộ tập order cùng lúc, làm mất lợi ích streaming.

## 5. StaxEventItemReader trong Spring Batch

StaxEventItemReader là ItemReader dùng StAX để đọc từng XML fragment. Nó thường được kết hợp với một Spring OXM Unmarshaller.

Các cấu hình quan trọng:

- Resource: XML file hoặc resource đầu vào.
- Fragment root element: tên phần tử đại diện cho một item.
- Unmarshaller: chuyển fragment thành Java object.
- saveState: lưu reader state để hỗ trợ restart.
- strict: quy định reader có báo lỗi nếu resource không tồn tại hay không.
- XMLInputFactory: cấu hình StAX parser.

Reader được dùng trong chunk Step như một ItemReader thông thường. Mỗi lần read() trả về một object đã được unmarshal; khi hết fragment, reader trả về null.

## 6. Khai báo model Java cho XML fragment

Giả sử mỗi order có ID, customer ID và amount:

~~~java
@XmlRootElement(name = "order")
@XmlAccessorType(XmlAccessType.FIELD)
public class OrderXml {

    private Long id;

    private String customerId;

    private BigDecimal amount;

    public Long getId() {
        return id;
    }

    public String getCustomerId() {
        return customerId;
    }

    public BigDecimal getAmount() {
        return amount;
    }
}
~~~

Tên element và mapping phải khớp với XML thực tế. Nếu XML dùng namespace, cần khai báo namespace tương ứng trong JAXB annotations hoặc package-level schema mapping.

Ví dụ XML:

~~~xml
<order>
    <id>1001</id>
    <customerId>C001</customerId>
    <amount>125.50</amount>
</order>
~~~

Nếu model dùng field khác tên element, cần annotation như XmlElement. Với attribute thay vì child element, dùng XmlAttribute.

## 7. Cấu hình Jaxb2Marshaller

Spring OXM cung cấp Jaxb2Marshaller để cấu hình JAXB binding:

~~~java
@Bean
public Jaxb2Marshaller orderMarshaller() {
    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(OrderXml.class);
    return marshaller;
}
~~~

Có thể dùng context path hoặc packagesToScan tùy cách tổ chức model. Với danh sách class rõ ràng, classesToBeBound giúp xác định chính xác kiểu object được hỗ trợ.

Unmarshaller nhận fragment XML và tạo một OrderXml. Vì reader chỉ chuyển từng fragment, ứng dụng không cần tạo object chứa toàn bộ danh sách order.

JAXB mapping vẫn cần được kiểm soát: kiểu dữ liệu, nullability, namespace, date/time format, adapter và validation đều có thể làm unmarshal thất bại.

## 8. Cấu hình StaxEventItemReaderBuilder

Ví dụ reader xử lý mỗi phần tử order:

~~~java
@Bean
@StepScope
public StaxEventItemReader<OrderXml> orderXmlReader(
        @Value("#{jobParameters['inputFile']}") Resource resource,
        Jaxb2Marshaller orderMarshaller) {

    XMLInputFactory inputFactory = XMLInputFactory.newFactory();
    inputFactory.setProperty(XMLInputFactory.SUPPORT_DTD, false);
    inputFactory.setProperty(
            XMLInputFactory.IS_SUPPORTING_EXTERNAL_ENTITIES,
            false);

    return new StaxEventItemReaderBuilder<OrderXml>()
            .name("orderXmlReader")
            .resource(resource)
            .addFragmentRootElements("order")
            .unmarshaller(orderMarshaller)
            .xmlInputFactory(inputFactory)
            .saveState(true)
            .strict(true)
            .build();
}
~~~

Ý nghĩa:

- name cung cấp tên ổn định cho reader và checkpoint.
- resource chỉ định file XML đầu vào.
- addFragmentRootElements("order") xác định element được đọc thành item.
- unmarshaller chuyển fragment thành OrderXml.
- xmlInputFactory cung cấp parser đã cấu hình.
- saveState(true) cho phép reader lưu tiến độ đọc.
- strict(true) yêu cầu resource phải tồn tại theo chế độ strict của reader.

Các phương thức builder cần khớp phiên bản Spring Batch trong dự án. Với phiên bản có API khác, dùng các setter tương ứng trên StaxEventItemReader.

Ví dụ tạo XMLInputFactory trong bean StepScope giúp mỗi StepExecution có parser factory riêng. Không chia sẻ một parser hoặc reader mutable giữa nhiều worker nếu implementation không bảo đảm thread safety.

## 9. XMLInputFactory và bảo mật parser

XML có thể chứa DTD và external entity. Nếu parser cho phép resolve external entity từ file hoặc URL, một XML không tin cậy có thể truy cập tài nguyên ngoài ý muốn, gây rò rỉ dữ liệu hoặc tạo tải không cần thiết.

Đối với file đầu vào không tin cậy, nên tắt DTD và external entity khi parser provider hỗ trợ:

~~~java
XMLInputFactory factory = XMLInputFactory.newFactory();

factory.setProperty(XMLInputFactory.SUPPORT_DTD, false);
factory.setProperty(
        XMLInputFactory.IS_SUPPORTING_EXTERNAL_ENTITIES,
        false);
~~~

Tùy StAX provider, một số property có thể không được hỗ trợ hoặc có hành vi khác. Hãy kiểm tra cấu hình thực tế và fail startup nếu policy bảo mật bắt buộc không thể được áp dụng. Không âm thầm bỏ qua lỗi cấu hình bảo mật.

Không bật DTD hoặc external entity chỉ để giải quyết một file có entity reference mà chưa đánh giá nguồn dữ liệu. Nếu XML cần entity nội bộ, hãy xác định cách hỗ trợ an toàn và giới hạn parser theo hợp đồng file.

## 10. Bộ nhớ của streaming phụ thuộc fragment và chunk

Streaming không có nghĩa memory luôn rất nhỏ. Một cách hình dung:

~~~text
Memory của Step
  =
  parser buffers
  + fragment XML hiện tại
  + object được unmarshal
  + items trong chunk
  + processor/writer working set
~~~

Nếu fragment order nhỏ và chunk size 100, memory thường dễ kiểm soát hơn so với parse toàn bộ document thành một List lớn.

Nhưng nếu một fragment chứa hàng trăm nghìn transaction con, fragment đó vẫn có thể rất lớn. JAXB sẽ tạo object graph cho toàn fragment. Hãy chọn fragment root ở cấp đơn vị xử lý hợp lý.

Các biện pháp:

- Chọn fragment root nhỏ và độc lập.
- Không giữ danh sách item đã xử lý trong singleton hoặc listener.
- Giới hạn collection lồng bên trong một fragment nếu có thể.
- Chọn chunk size theo kích thước object thực tế.
- Tránh processor giữ reference tới fragment sau khi xử lý.
- Theo dõi heap, allocation rate và garbage collection khi chạy dữ liệu đại diện.

## 11. Chunk size ảnh hưởng memory và transaction

StaxEventItemReader trả từng fragment, còn chunk size quyết định số item được giữ trong một transaction trước khi commit.

Ví dụ:

~~~java
@Bean
public Step importOrdersStep(
        JobRepository jobRepository,
        PlatformTransactionManager transactionManager,
        ItemReader<OrderXml> orderXmlReader,
        ItemProcessor<OrderXml, Order> orderProcessor,
        ItemWriter<Order> orderWriter) {

    return new StepBuilder("importOrdersStep", jobRepository)
            .<OrderXml, Order>chunk(100, transactionManager)
            .reader(orderXmlReader)
            .processor(orderProcessor)
            .writer(orderWriter)
            .build();
}
~~~

Chunk size nhỏ:

- Giảm số object cùng nằm trong working set.
- Commit thường xuyên hơn.
- Có thể tăng overhead transaction và I/O.

Chunk size lớn:

- Có thể cải thiện throughput với writer batch.
- Giữ nhiều item hơn trong memory.
- Transaction kéo dài hơn và rollback có thể tốn kém hơn.

Hãy benchmark với kích thước fragment thực tế. Không chọn chunk size chỉ dựa trên kích thước file tổng.

## 12. XML có namespace

XML thường sử dụng namespace:

~~~xml
<orders xmlns="urn:example:orders">
    <order>
        <id>1001</id>
        <amount>125.50</amount>
    </order>
</orders>
~~~

Element order có namespace URI là urn:example:orders. Hai element cùng local name nhưng khác namespace là hai tên XML khác nhau.

Khi dùng JAXB, model cần khai báo namespace phù hợp:

~~~java
@XmlRootElement(
        name = "order",
        namespace = "urn:example:orders")
@XmlAccessorType(XmlAccessType.FIELD)
public class OrderXml {
    // Fields...
}
~~~

Cần kiểm tra cách fragment matching của phiên bản StaxEventItemReader đang dùng khi có namespace. Builder nhận tên fragment root theo API của nó; nếu tài liệu có nhiều namespace dùng cùng local name, hãy xác minh reader có thể phân biệt đúng hoặc dùng custom fragment reader dựa trên QName.

Không bỏ namespace khỏi XML chỉ để đơn giản hóa mapping nếu namespace là một phần hợp đồng dữ liệu.

## 13. XML lồng nhau và chọn fragment root

Không phải mọi element lặp lại đều là record độc lập.

Ví dụ:

~~~xml
<orders>
    <order>
        <id>1001</id>
        <lines>
            <line>
                <sku>A-01</sku>
                <quantity>2</quantity>
            </line>
            <line>
                <sku>B-02</sku>
                <quantity>1</quantity>
            </line>
        </lines>
    </order>
</orders>
~~~

Nếu chọn order làm fragment root, một item OrderXml chứa cả danh sách line. Đây thường là lựa chọn hợp lý nếu nghiệp vụ xử lý đơn hàng nguyên vẹn.

Nếu chọn line làm fragment root, reader sẽ tạo từng line riêng, nhưng cần biết order ID và ngữ cảnh cha. StAX fragment reader không tự động giữ toàn bộ ancestor object như một ORM graph. Có thể cần custom reader hoặc thay đổi cấu trúc xử lý.

Chọn fragment root theo đơn vị nghiệp vụ có thể xử lý độc lập. Không chọn element con chỉ vì nó lặp lại nhiều lần.

## 14. Nhiều loại fragment trong một file

Một tài liệu có thể chứa nhiều loại record:

~~~xml
<batch>
    <order>...</order>
    <customer>...</customer>
    <order>...</order>
</batch>
~~~

StaxEventItemReader có thể được cấu hình để nhận nhiều fragment root theo API phiên bản tương ứng, nhưng kiểu dữ liệu trả về và xử lý khác loại record cần được thiết kế rõ.

Một lựa chọn là tạo một lớp envelope hoặc hierarchy model chung. Lựa chọn khác là dùng custom reader trả về một sealed type hoặc interface, sau đó processor phân nhánh theo loại fragment.

Nếu thứ tự và loại record quan trọng, reader cần giữ đúng thứ tự tài liệu. Nếu các loại fragment có schema và lifecycle khác nhau, tách thành các Step hoặc luồng ingest riêng có thể dễ vận hành hơn.

Không cấu hình một reader thành một item type chung nếu unmarshaller không thể xác định loại fragment một cách an toàn.

## 15. XML encoding và XML declaration

XML có thể khai báo encoding trong prolog:

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<orders>
    ...
</orders>
~~~

Khi parser nhận byte stream trực tiếp, XML parser có thể dùng BOM và XML declaration để xác định encoding theo quy tắc XML. Tránh tự bọc InputStream bằng InputStreamReader dùng platform default charset trước khi đưa vào StAX, vì khi đó byte đã bị decode theo charset có thể sai.

Với Spring Resource, StaxEventItemReader làm việc với resource và StAX parser. Hãy bảo đảm input là stream byte và XML declaration khớp encoding thực tế.

Nếu file không có declaration, XML có quy tắc mặc định encoding và autodetection riêng. Đừng suy đoán tùy ý; yêu cầu nguồn công bố charset và kiểm thử với byte thực tế.

## 16. XML không well-formed và lỗi ở cuối file

Parser streaming phát hiện lỗi khi đi tới vị trí có cấu trúc không hợp lệ. Một file có thể chứa hàng trăm nghìn fragment hợp lệ trước khi parser phát hiện thẻ đóng bị thiếu ở cuối.

Ví dụ:

~~~xml
<orders>
    <order><id>1</id></order>
    <order><id>2</id></order>
    <!-- Phần cuối bị truncate -->
~~~

Các chunk trước có thể đã commit. Khi parser tới EOF và phát hiện XML không well-formed, Step thất bại. Rollback chỉ áp dụng cho transaction chunk hiện tại; các chunk đã commit trước đó vẫn tồn tại.

Vì vậy, nếu output cần được consumer xem như một tài liệu hoàn chỉnh, đừng publish output cuối trước khi Job thành công. Ghi vào staging rồi publish sau khi Step/Job hoàn tất là một cách giảm nguy cơ consumer đọc kết quả dở dang.

## 17. Validate XML bằng XSD mà không tải toàn bộ document

Một file lớn có thể cần kiểm tra theo XML Schema. Tránh parse toàn bộ file vào DOM chỉ để validate.

Java XML Validation API có thể làm việc theo stream hoặc SAX source. Có thể dùng Validator với SAXSource hoặc một pipeline SAX/StAX được thiết kế phù hợp để validate khi đọc.

Ví dụ khái niệm dùng Validator và StreamSource:

~~~java
SchemaFactory schemaFactory =
        SchemaFactory.newInstance(
                XMLConstants.W3C_XML_SCHEMA_NS_URI);

Schema schema = schemaFactory.newSchema(xsdResource.getURL());

Validator validator = schema.newValidator();

try (InputStream input = xmlResource.getInputStream()) {
    validator.validate(new StreamSource(input));
}
~~~

Cách này validate stream mà không yêu cầu ứng dụng tự xây dựng DOM toàn bộ. Tuy nhiên, nó thực hiện một lượt đọc riêng trước khi Spring Batch xử lý, nên file có thể bị đọc hai lần.

Nếu cần validate và process trong cùng một lượt, cần thiết kế pipeline streaming có schema validation gắn với parser hoặc custom reader. Không giả định StaxEventItemReader tự động validate XSD chỉ vì JAXB mapping thành công.

Với XSD import/include, kiểm soát schema location và external access. Không cho XML hoặc schema không tin cậy tự tải tài nguyên tùy ý.

## 18. Xử lý record không hợp lệ

Một fragment có thể well-formed nhưng không hợp lệ theo schema hoặc quy tắc nghiệp vụ.

Có ba lớp lỗi khác nhau:

1. **XML syntax error**: cấu trúc XML không well-formed; parser có thể không tiếp tục an toàn.
2. **Binding error**: fragment không map được sang Java type, ví dụ kiểu số hoặc ngày sai.
3. **Business validation error**: object tạo được nhưng dữ liệu không đáp ứng quy tắc nghiệp vụ.

Không phải mọi lỗi XML đều phù hợp để skip. Nếu toàn bộ document bị truncate hoặc thẻ lồng nhau sai, ranh giới fragment sau đó có thể không xác định được. Step thường nên thất bại.

Nếu một fragment riêng lẻ hợp lệ về cấu trúc nhưng sai giá trị, có thể chuyển thành exception nghiệp vụ trong processor và dùng skip policy nếu nghiệp vụ cho phép.

Đối với lỗi unmarshal, có thể phân loại exception cụ thể nếu reader phát ra loại exception ổn định trong phiên bản framework. Hãy kiểm thử exception thực tế và tránh skip quá rộng.

## 19. Restart và state của StaxEventItemReader

StaxEventItemReader hỗ trợ ItemStream và có thể lưu state khi saveState(true). Tên reader phải ổn định để reader khôi phục checkpoint tương ứng.

Ví dụ:

~~~java
return new StaxEventItemReaderBuilder<OrderXml>()
        .name("orderXmlReader")
        .resource(resource)
        .addFragmentRootElements("order")
        .unmarshaller(orderMarshaller)
        .saveState(true)
        .build();
~~~

Khi Step restart, reader sử dụng state đã lưu để tiếp tục theo vị trí item. Cách định vị cụ thể phụ thuộc implementation và phiên bản. Một số reader đếm item đã đọc rồi phải parse/bỏ qua các fragment trước checkpoint khi mở lại; vì vậy restart ở gần cuối một XML rất lớn có thể tốn thời gian khởi động lại.

Hãy đo restart với file có kích thước thực tế, không chỉ đo lần chạy đầu. Nếu thời gian seek/replay là vấn đề, có thể cần chia nguồn thành file nhỏ hơn, tạo index/manifest hoặc thiết kế partition theo resource.

Các điều kiện cần giữ ổn định:

- Reader name.
- Fragment root configuration.
- Resource nội dung bất biến.
- Charset và XML namespace/schema mapping.
- Cách sắp xếp fragment trong tài liệu.

Nếu file bị thay đổi giữa lần chạy và restart, checkpoint theo item count có thể trỏ tới fragment khác.

## 20. StepScope và resource XML runtime

Đường dẫn file thường được truyền qua JobParameters. Reader nên dùng StepScope để late-bind Resource:

~~~java
@Bean
@StepScope
public StaxEventItemReader<OrderXml> orderXmlReader(
        @Value("#{jobParameters['inputFile']}") Resource resource,
        Jaxb2Marshaller orderMarshaller) {
    // ...
}
~~~

StepScope giúp reader được tạo trong phạm vi StepExecution và nhận resource của lần chạy hiện tại.

JobParametersValidator nên kiểm tra inputFile bắt buộc trước khi Step chạy. Có thể kiểm tra resource tồn tại và đọc được trong bước chuẩn bị. Đừng đợi tới lúc reader mở file lớn mới phát hiện parameter bị thiếu hoặc path sai.

Nếu resource được lưu trên network storage hoặc object storage, hãy kiểm tra tính ổn định của nội dung qua restart và khả năng stream của Resource implementation.

## 21. XML lớn và file nén

XML có thể được nén bằng gzip để giảm storage và network transfer. Nếu dùng resource nén, cần mở stream giải nén trước khi parser nhận byte XML.

Một pipeline có thể là:

~~~text
orders.xml.gz
     |
     v
GZIPInputStream
     |
     v
StAX parser
     |
     v
XML fragments
     |
     v
Unmarshaller
     |
     v
Chunk processing
~~~

Cần lưu ý:

- Resource phải mở được nhiều lần nếu reader restart cần reopen.
- GZIPInputStream là stream tuần tự; không thể seek tùy ý như file thường.
- Restart có thể phải giải nén và đọc bỏ qua các fragment trước checkpoint.
- Tốc độ CPU giải nén có thể trở thành bottleneck.
- File gzip hỏng có thể chỉ phát hiện lỗi checksum ở cuối stream.

Với file nén rất lớn và restart thường xuyên, cân nhắc chia nhỏ archive thành các file độc lập hoặc dùng định dạng có index. Một resource stream không hỗ trợ random access có thể khiến restart chậm.

## 22. Partitioning XML lớn

Có thể chia một nguồn XML lớn thành nhiều phần để xử lý song song, nhưng XML là một document có cấu trúc. Không được cắt file tùy tiện theo byte hoặc dòng vì có thể cắt giữa tag, attribute, entity hoặc multibyte character.

Các chiến lược an toàn hơn:

- Chia file upstream thành nhiều XML document độc lập, mỗi file có root hợp lệ.
- Dùng một bước ingest streaming để tạo các shard hợp lệ theo fragment boundary.
- Lưu manifest gồm tên shard, checksum và số record.
- Mỗi worker đọc một shard bằng StaxEventItemReader riêng.
- Dùng partition context truyền resource path và metadata cho worker.

Nếu muốn partition trực tiếp một file XML duy nhất, cần một cơ chế index/byte offset hiểu cấu trúc XML và encoding. Không chia theo khoảng byte đơn thuần.

## 23. StAX parser và concurrency

XMLInputFactory và các parser/reader object thường không được thiết kế để chia sẻ tùy tiện giữa nhiều thread. Một XMLStreamReader hoặc XMLEventReader là stateful cursor; không dùng chung cho nhiều worker.

Với partitioning:

- Mỗi worker nên có reader và parser state riêng.
- Mỗi worker nhận resource hoặc shard riêng.
- Dùng StepScope cho reader stateful.
- Không chia sẻ XMLStreamReader giữa các thread.
- Nếu các worker đọc cùng một resource, phải có thiết kế phân vùng/index rõ ràng.

Một XMLInputFactory có thể được cấu hình dùng chung tùy provider, nhưng cách an toàn là tạo factory theo reader hoặc bảo đảm provider hỗ trợ concurrency theo tài liệu. Không suy ra thread safety chỉ vì factory là object singleton.

## 24. Ghi XML lớn theo streaming

Nếu Job cần xuất XML lớn, tránh xây dựng DOM hoặc một object graph chứa toàn bộ output. Có thể dùng StAX XMLStreamWriter để ghi tuần tự từng record.

Ví dụ khái niệm:

~~~java
XMLStreamWriter writer =
        XMLOutputFactory.newFactory()
                .createXMLStreamWriter(outputStream, "UTF-8");

writer.writeStartDocument("UTF-8", "1.0");
writer.writeStartElement("orders");

for (Order order : orders) {
    writer.writeStartElement("order");

    writer.writeStartElement("id");
    writer.writeCharacters(order.id().toString());
    writer.writeEndElement();

    writer.writeStartElement("amount");
    writer.writeCharacters(order.amount().toPlainString());
    writer.writeEndElement();

    writer.writeEndElement();
}

writer.writeEndElement();
writer.writeEndDocument();
writer.flush();
writer.close();
~~~

Trong Spring Batch, custom ItemWriter có thể giữ XMLStreamWriter mở trong lifecycle ItemStream và ghi từng chunk. Cần triển khai open/update/close để quản lý resource và restart.

Writer phải tạo XML well-formed sau khi nhiều chunk được ghi. Nếu Job dừng giữa chừng, file có thể thiếu closing root element. Nên ghi vào staging và chỉ publish sau khi Job hoàn tất thành công.

## 25. Custom streaming writer và restart

Với custom XML writer, checkpoint cần lưu đủ thông tin để tiếp tục đúng vị trí hoặc chiến lược restart cần được thiết kế lại.

Một số lựa chọn:

- Ghi từng shard XML độc lập thay vì append vào một document duy nhất.
- Lưu vị trí byte nếu có thể khôi phục an toàn và encoding/format ổn định.
- Ghi từng fragment vào file tạm rồi tạo root document ở bước cuối.
- Dùng writer hỗ trợ restart và quản lý state theo ItemStream.
- Khi restart, tạo output mới từ checkpoint hoặc xóa staging file dở dang theo policy.

Không chỉ lưu byte offset nếu writer chưa bảo đảm byte offset nằm đúng ranh giới XML và encoding. Với UTF-8, offset có thể nằm giữa một multibyte character nếu tính toán sai. Cũng cần tính đến closing tags, namespace declarations và trạng thái XMLStreamWriter.

Đối với nhiều hệ thống, tạo các file XML shard độc lập rồi ghép bằng một bước streaming cuối cùng dễ restart và đối soát hơn việc nối một document duy nhất qua nhiều transaction.

## 26. Xử lý lỗi giữa một file XML lớn

Một file lớn có thể thất bại vì:

- XML malformed.
- Fragment không unmarshal được.
- Business validation thất bại.
- Database writer lỗi.
- Resource bị mất hoặc hết dung lượng.
- JVM dừng khi đang đọc hoặc ghi.

Khi reader parse XML lỗi ở fragment cuối, các chunk đã commit trước đó vẫn tồn tại. Restart có thể khôi phục reader state nếu file không đổi và reader hỗ trợ saveState.

Nếu input file bị thay thế, checkpoint không còn đáng tin. Hãy lưu checksum hoặc immutable resource identifier làm Job metadata.

Nếu output XML đang được tạo dở, đừng để consumer đọc file đó như một tài liệu hoàn chỉnh. Dùng staging name, trạng thái publish hoặc manifest để chỉ công bố khi hoàn tất.

## 27. Monitoring và giới hạn tài nguyên

Với XML lớn, theo dõi các chỉ số:

| Metric | Mục đích |
|---|---|
| readCount | Số fragment đọc thành công |
| processCount | Số item được xử lý |
| writeCount | Số item được ghi |
| readSkipCount | Fragment lỗi đọc bị skip |
| processSkipCount | Item lỗi nghiệp vụ bị skip |
| commitCount | Số chunk commit |
| rollbackCount | Số rollback |
| read/processor/write duration | Xác định bottleneck |
| heap usage | Theo dõi memory |
| GC pause/allocation rate | Phát hiện áp lực object allocation |
| input bytes and checksum | Nhận diện resource đang xử lý |

Log nên có JobExecution ID, StepExecution ID, resource name và fragment business key nếu có. Không log toàn bộ fragment XML vì có thể tạo log rất lớn hoặc lộ dữ liệu nhạy cảm.

Đặt giới hạn kích thước file, độ sâu XML, số fragment và kích thước fragment nếu nguồn không tin cậy. Parser streaming giảm memory toàn document nhưng không tự bảo vệ khỏi một fragment cực lớn hoặc input độc hại.

## 28. Kiểm thử streaming reader

Nên có fixture chứa nhiều fragment và xác nhận mỗi fragment được trả về như một item riêng.

Ví dụ XML:

~~~xml
<orders>
    <order><id>1</id><amount>10.00</amount></order>
    <order><id>2</id><amount>20.00</amount></order>
    <order><id>3</id><amount>30.00</amount></order>
</orders>
~~~

Test cần xác nhận:

- Reader trả về ba OrderXml.
- ID và amount được unmarshal đúng.
- Lần read tiếp theo trả null.
- Reader close giải phóng stream.
- Reader có thể mở lại và khôi phục state theo ExecutionContext.
- Namespace và encoding được xử lý đúng.

Không chỉ test JAXB unmarshal trực tiếp một object. Cần test StaxEventItemReader để xác nhận fragment boundary và thứ tự record.

## 29. Kiểm thử XML lớn và memory behavior

Tạo file test có số lượng fragment đủ lớn để kiểm tra streaming thực tế, nhưng không nhất thiết phải commit một file khổng lồ vào repository.

Có thể sinh fixture theo stream:

~~~java
try (BufferedWriter writer = Files.newBufferedWriter(
        xmlPath,
        StandardCharsets.UTF_8)) {

    writer.write("<orders>");

    for (int i = 1; i <= 1_000_000; i++) {
        writer.write("<order><id>");
        writer.write(Integer.toString(i));
        writer.write("</id></order>");
    }

    writer.write("</orders>");
}
~~~

Chạy Step và xác nhận tổng readCount/writeCount. Theo dõi heap trong một môi trường test phù hợp để xem memory có tăng tuyến tính theo số fragment hay được giữ ở mức tương đối ổn định.

Một test functional đơn thuần không chứng minh streaming nếu file quá nhỏ. Cần kiểm tra implementation không giữ tất cả item trong List, không có listener tích lũy object và writer không buffer toàn bộ output.

## 30. Kiểm thử XML malformed và fragment lỗi

Các trường hợp nên có:

- Thiếu closing tag ở cuối file.
- Tag lồng sai thứ tự.
- Attribute hoặc element không đúng kiểu JAXB.
- Namespace không khớp.
- Entity reference bị từ chối theo security policy.
- Fragment nghiệp vụ thiếu field bắt buộc.
- File rỗng hoặc thiếu root element.
- File bị truncate giữa multibyte character.
- File nén bị hỏng ở cuối stream.

Xác nhận loại lỗi, Step status và dữ liệu đã commit. Với XML malformed, không giả định reader có thể skip một fragment rồi tiếp tục vì parser có thể mất khả năng xác định cấu trúc tài liệu.

## 31. Kiểm thử restart với XML lớn

Một test restart cần chạy cùng JobInstance qua hai JobExecution:

~~~text
Input: 10 fragment
Chunk size: 3

Lần chạy đầu:
  Fragment 1-3 -> COMMIT
  Fragment 4-6 -> COMMIT
  Fragment 7-9 -> lỗi trước COMMIT

Restart:
  Reader khôi phục checkpoint đã commit
  Fragment chưa commit được đọc lại
  Fragment 10 được xử lý

Kết quả:
  Mọi fragment hợp lệ được xử lý đúng một lần
~~~

Kiểm tra:

- Reader name không đổi.
- saveState được bật.
- JobParameters identifying giữ nguyên.
- File input có cùng checksum.
- Reader tiếp tục đúng fragment.
- Chunk đã commit không bị ghi trùng.
- Chunk chưa commit được xử lý lại.
- Output được publish sau khi Job thành công.

Đối với file rất lớn, đo cả thời gian khởi tạo reader khi restart. Nếu reader phải đọc lại các fragment trước checkpoint, thời gian đó có thể tăng theo vị trí checkpoint.

## 32. Những lỗi thường gặp

### Dùng DOM cho file rất lớn

DOM giữ nhiều node của toàn bộ document trong memory. Dùng StAX/SAX hoặc chia file thành tài liệu nhỏ.

### Chọn root document làm fragment

Unmarshaller nhận cả danh sách record lớn và tạo object graph lớn. Chọn element con đại diện cho một item nghiệp vụ.

### Nghĩ JAXB tự động streaming

Unmarshal toàn root vẫn có thể tải toàn bộ danh sách vào memory. Kết hợp JAXB với StAX theo từng fragment.

### Fragment đơn lẻ quá lớn

Streaming vẫn phải materialize fragment hiện tại. Chọn fragment root nhỏ hơn hoặc xử lý nội dung lồng nhau bằng custom streaming logic.

### XMLInputFactory cho phép external entity

Có nguy cơ truy cập tài nguyên ngoài ý muốn. Tắt DTD và external entity theo khả năng provider, kiểm thử policy bảo mật.

### Không xử lý namespace

Fragment matching hoặc JAXB binding không nhận đúng element. Khai báo namespace và kiểm thử QName thực tế.

### XML có multiline hoặc cấu trúc lồng phức tạp nhưng chọn sai fragment root

Reader có thể tạo item không đúng đơn vị nghiệp vụ. Chọn fragment theo boundary độc lập.

### Skip lỗi parser một cách rộng rãi

Khi document malformed, parser có thể không tiếp tục an toàn. Phân biệt lỗi cú pháp toàn document với lỗi dữ liệu của một fragment.

### Chia XML theo byte để chạy song song

Có thể cắt giữa tag, entity hoặc ký tự nhiều byte. Chia thành XML shard hợp lệ tại fragment boundary.

### Dùng chung parser state giữa worker

XMLStreamReader là cursor stateful. Tạo reader/parser riêng cho mỗi worker.

### Publish output trước khi Job hoàn tất

Consumer có thể đọc tài liệu thiếu closing tag. Ghi staging và publish sau khi thành công.

### Thay input giữa restart

Checkpoint không còn trỏ tới cùng fragment. Giữ resource bất biến và xác minh checksum.

## 33. Quy trình thiết kế streaming XML

Khi xử lý XML lớn trong Spring Batch, hãy xác định:

1. Kích thước file và số lượng fragment dự kiến.
2. Fragment root nào đại diện cho một item nghiệp vụ độc lập.
3. Kích thước lớn nhất của một fragment.
4. XML có namespace, attribute, nested collection hoặc multiline text không?
5. Charset và XML declaration có đúng với byte nguồn không?
6. Có cần JAXB binding hay custom StAX reader?
7. XMLInputFactory đã tắt DTD/external entities cho input không tin cậy chưa?
8. XSD validation được thực hiện theo stream hay đang tạo DOM?
9. Chunk size có phù hợp với kích thước object và writer không?
10. Reader có saveState và tên ổn định không?
11. Resource có bất biến qua restart không?
12. Partitioning có dùng các XML shard hợp lệ thay vì cắt byte không?
13. Output có được giữ ở staging tới khi Job hoàn tất không?
14. Test có bao phủ namespace, encoding, malformed XML, restart và file lớn không?

Với XML lớn, streaming bằng StAX cho phép Spring Batch đọc từng fragment và chuyển từng item sang chunk pipeline mà không cần giữ toàn bộ document trong memory. StaxEventItemReader kết hợp với Unmarshaller như Jaxb2Marshaller là lựa chọn phù hợp khi mỗi fragment là một đơn vị nghiệp vụ độc lập. Hãy chọn fragment root nhỏ, cấu hình parser an toàn, giữ nguồn ổn định qua restart và publish output sau khi Job hoàn tất để xử lý XML lớn có thể kiểm soát về memory, hiệu năng và khả năng phục hồi.
