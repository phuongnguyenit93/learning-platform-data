# Kiểm thử TLS bằng test certificate

## 1. Vì sao cần test certificate?

Trong **Spring gRPC**, TLS bảo vệ kết nối giữa client và server bằng mã hóa, kiểm tra tính toàn vẹn và xác thực danh tính server. Với mutual TLS (mTLS), server còn yêu cầu client trình certificate để xác minh workload gọi tới.

Kiểm thử TLS không nên chỉ xác nhận rằng channel mở được. Một bộ test tốt cần chứng minh cả trường hợp hợp lệ lẫn trường hợp phải bị từ chối:

- Client tin cậy CA ký certificate server và xác minh đúng hostname.
- Client từ chối certificate không nằm trong trust chain.
- Client từ chối certificate có SAN không khớp authority/hostname.
- Server mTLS chấp nhận client certificate hợp lệ.
- Server mTLS từ chối client thiếu certificate hoặc certificate không được tin cậy.
- Lỗi handshake không làm RPC đi vào business handler.

**Test certificate** là certificate và private key được tạo riêng cho test, ký bởi test CA do test kiểm soát. Chúng giúp kiểm thử handshake thật mà không dùng credential production.

## 2. Certificate chain cần có gì?

Một kịch bản TLS cơ bản thường có:

| Thành phần | Vai trò |
| --- | --- |
| Test CA certificate | Trust anchor mà test client dùng để xác minh server |
| Server certificate | Certificate của gRPC server, có SAN khớp hostname client sử dụng |
| Server private key | Private key tương ứng với server certificate |
| Client certificate | Certificate của workload client khi kiểm thử mTLS |
| Client private key | Private key tương ứng với client certificate |

Server certificate cần Extended Key Usage phù hợp với server authentication. Client certificate dùng cho mTLS cần client authentication. Certificate server phải có Subject Alternative Name (SAN), ví dụ DNS:localhost khi test kết nối tới localhost.

Không dựa vào Common Name (CN) để thay thế SAN trong kiểm tra hostname hiện đại. Cũng không dùng certificate không có SAN rồi tắt hostname verification để test chạy qua.

## 3. Tạo test CA và certificate bằng OpenSSL

Có thể tạo certificate fixture trong thư mục tạm của test hoặc tạo trước trong thư mục test resources. Ví dụ dưới đây dùng OpenSSL và một CA tự ký chỉ dành cho test.

Tạo CA key và CA certificate:

~~~bash
openssl req -x509 -newkey rsa:3072 -nodes \
  -keyout test-ca.key -out test-ca.crt \
  -days 7 -subj "/CN=Spring gRPC Test CA" \
  -addext "basicConstraints=critical,CA:TRUE" \
  -addext "keyUsage=critical,keyCertSign,cRLSign"
~~~

Tạo server private key và CSR:

~~~bash
openssl req -newkey rsa:2048 -nodes \
  -keyout server.key -out server.csr \
  -subj "/CN=localhost"
~~~

Tạo file mở rộng certificate server, ví dụ server.ext:

~~~ini
basicConstraints=critical,CA:FALSE
keyUsage=critical,digitalSignature,keyEncipherment
extendedKeyUsage=serverAuth
subjectAltName=DNS:localhost
~~~

Ký server certificate bằng test CA:

~~~bash
openssl x509 -req -in server.csr \
  -CA test-ca.crt -CAkey test-ca.key -CAcreateserial \
  -out server.crt -days 3 -sha256 \
  -extfile server.ext
~~~

Tạo client key và CSR:

~~~bash
openssl req -newkey rsa:2048 -nodes \
  -keyout client.key -out client.csr \
  -subj "/CN=spring-grpc-test-client"
~~~

File client.ext:

~~~ini
basicConstraints=critical,CA:FALSE
keyUsage=critical,digitalSignature
extendedKeyUsage=clientAuth
subjectAltName=URI:spiffe://test.local/spring-grpc-client
~~~

Ký client certificate:

~~~bash
openssl x509 -req -in client.csr \
  -CA test-ca.crt -CAkey test-ca.key -CAcreateserial \
  -out client.crt -days 3 -sha256 \
  -extfile client.ext
~~~

Kiểm tra chain và mục đích sử dụng:

~~~bash
openssl verify -CAfile test-ca.crt server.crt
openssl verify -CAfile test-ca.crt client.crt
openssl x509 -in server.crt -noout -text
openssl x509 -in client.crt -noout -text
~~~

Kết quả verify phải thành công. Khi xem certificate, kiểm tra SAN và Extended Key Usage. Server certificate phải có serverAuth; client certificate phải có clientAuth.

Các lệnh dùng RSA để ví dụ dễ đọc; thuật toán và kích thước key trong môi trường thật cần theo tiêu chuẩn bảo mật của tổ chức và cấu hình TLS đang triển khai.

## 4. Quy tắc quản lý test private key

Test CA và private key có quyền ký certificate, vì vậy phải giới hạn phạm vi sử dụng:

- Chỉ dùng trong test; không dùng lại CA hoặc private key của production.
- Không đặt test key trong thư mục main resources hoặc đóng gói vào artifact production.
- Nếu commit fixture vào repository, dùng dữ liệu giả lập, quyền truy cập hạn chế và ghi rõ chỉ dành cho test.
- Tốt hơn, tạo certificate trong test setup vào thư mục tạm, sau đó xóa khi test kết thúc.
- Đặt thời hạn ngắn nhưng đủ cho CI; không để test phụ thuộc vào một ngày hết hạn đã qua.
- Không tắt xác minh certificate để tránh phải quản lý fixture.

Nếu tạo certificate động trong Java, có thể dùng thư viện test chuyên dụng hoặc công cụ của build pipeline. Dù dùng cách nào, test vẫn phải kiểm tra trust chain và hostname như client production.

## 5. Tạo TLS context cho gRPC Java

Với Netty transport, gRPC Java cung cấp GrpcSslContexts để tạo Netty SslContext từ certificate, key và trust manager.

Các import trong ví dụ dùng artifact grpc-netty với package io.grpc.netty và io.netty. Nếu dự án dùng grpc-netty-shaded, dùng các package shaded tương ứng và không trộn hai loại Netty class trong cùng một builder.

Ví dụ tạo server context cho TLS một chiều:

~~~java
import io.grpc.netty.GrpcSslContexts;
import io.netty.handler.ssl.SslContext;

SslContext serverTls = GrpcSslContexts.forServer(
        serverCertificate.toFile(),
        serverPrivateKey.toFile())
        .build();
~~~

Client tin cậy test CA:

~~~java
import io.grpc.netty.GrpcSslContexts;
import io.netty.handler.ssl.SslContext;

SslContext clientTls = GrpcSslContexts.forClient()
        .trustManager(testCaCertificate.toFile())
        .build();
~~~

Client chỉ tin CA test đã chỉ định. Không sử dụng trust manager chấp nhận mọi certificate hoặc bỏ qua hostname verification.

## 6. Chạy test server TLS trên cổng động

Có thể dùng NettyServerBuilder để khởi động một gRPC server thực trên cổng 0, để hệ điều hành cấp cổng trống:

~~~java
import io.grpc.Server;
import io.grpc.netty.NettyServerBuilder;
import io.netty.handler.ssl.SslContext;

Server server = NettyServerBuilder
        .forPort(0)
        .sslContext(serverTls)
        .addService(testService)
        .build()
        .start();

int port = server.getPort();
~~~

Client kết nối tới localhost bằng TLS:

~~~java
import io.grpc.ManagedChannel;
import io.grpc.netty.NettyChannelBuilder;
import io.netty.handler.ssl.SslContext;
import java.util.concurrent.TimeUnit;

ManagedChannel channel = NettyChannelBuilder
        .forAddress("localhost", port)
        .sslContext(clientTls)
        .build();
~~~

Sau đó gọi generated blocking hoặc async stub như một RPC bình thường. Vì channel và server dùng Netty transport thật, test thực hiện TLS handshake thực thay vì giả lập transport.

Trong test, luôn đóng channel và server trong finally hoặc lifecycle hook:

~~~java
try {
    // Thực hiện RPC assertions.
} finally {
    channel.shutdownNow();
    server.shutdownNow();
    channel.awaitTermination(5, TimeUnit.SECONDS);
    server.awaitTermination(5, TimeUnit.SECONDS);
}
~~~

Đoạn finally minh họa việc shutdown và chờ có giới hạn thời gian; nếu await trả false, ghi nhận teardown thất bại để test không che giấu thread hoặc channel còn sống. Nếu test có nhiều trường hợp, tạo fixture dùng chung trong setup/teardown và không để server chạy sót giữa các test.

## 7. Kiểm thử hostname và SAN

Client không chỉ cần tin CA; nó còn phải xác minh certificate được cấp cho đúng server name. Nếu client kết nối tới localhost, certificate cần SAN DNS:localhost.

Test thành công:

~~~java
ManagedChannel channel = NettyChannelBuilder
        .forAddress("localhost", port)
        .sslContext(clientTls)
        .build();

CatalogServiceGrpc.CatalogServiceBlockingStub stub =
        CatalogServiceGrpc.newBlockingStub(channel);

GetItemResponse response = stub.getItem(request);
assertEquals("item-42", response.getItemId());
~~~

Test hostname không khớp có thể dùng authority khác với SAN:

~~~java
ManagedChannel wrongHostChannel = NettyChannelBuilder
        .forAddress("localhost", port)
        .overrideAuthority("wrong.example.test")
        .sslContext(clientTls)
        .build();

CatalogServiceGrpc.CatalogServiceBlockingStub wrongHostStub =
        CatalogServiceGrpc.newBlockingStub(wrongHostChannel);

assertThrows(StatusRuntimeException.class,
        () -> wrongHostStub.getItem(request));
~~~

Test âm cần xác minh RPC thất bại do TLS hostname verification và business handler không nhận request. Status bề mặt thường là UNAVAILABLE do handshake/transport failure; chi tiết cause phụ thuộc phiên bản Netty và gRPC Java. Không nên chỉ assert một chuỗi exception message dễ thay đổi.

## 8. Kiểm thử certificate không được tin cậy

Tạo một CA khác không ký server certificate. Dùng CA đó làm trust manager của client:

~~~java
SslContext untrustedClientTls = GrpcSslContexts.forClient()
        .trustManager(otherTestCaCertificate.toFile())
        .build();

ManagedChannel untrustedChannel = NettyChannelBuilder
        .forAddress("localhost", port)
        .sslContext(untrustedClientTls)
        .build();
~~~

RPC phải thất bại trong quá trình handshake vì client không xây dựng được trust chain tới CA đã cấu hình. Xác minh business handler không được gọi. Điều này chứng minh test đang kiểm tra xác thực certificate thực sự, không chỉ kiểm tra server có mở port.

Các trường hợp bổ sung nên có:

- Server certificate hết hạn.
- Server certificate chưa có hiệu lực tại thời điểm test.
- Certificate thiếu SAN phù hợp.
- Certificate có EKU không phù hợp vai trò server.
- CA bị thay đổi hoặc không còn trong trust bundle.

Với test ngày hết hạn, tạo fixture có thời gian hiệu lực được kiểm soát hoặc dùng test clock/certificate fixture chuyên biệt. Không làm test phụ thuộc vào ngày chạy CI bằng cách dùng certificate sắp hết hạn.

## 9. Kiểm thử mutual TLS

mTLS yêu cầu server xác minh certificate client. Với Netty, cấu hình server SslContext yêu cầu client certificate:

~~~java
import io.grpc.netty.GrpcSslContexts;
import io.netty.handler.ssl.ClientAuth;
import io.netty.handler.ssl.SslContext;

SslContext mutualTlsServerContext = GrpcSslContexts
        .forServer(serverCertificate.toFile(),
                serverPrivateKey.toFile())
        .trustManager(testCaCertificate.toFile())
        .clientAuth(ClientAuth.REQUIRE)
        .build();
~~~

Client có certificate được CA tin cậy ký:

~~~java
SslContext mutualTlsClientContext = GrpcSslContexts.forClient()
        .trustManager(testCaCertificate.toFile())
        .keyManager(clientCertificate.toFile(),
                clientPrivateKey.toFile())
        .build();
~~~

Kết nối thành công khi:

- Client xác minh được server certificate và hostname.
- Server xác minh được client certificate theo trust manager.
- Client certificate có mục đích clientAuth phù hợp.
- Certificate và private key tương ứng.

Negative test: tạo client context chỉ có trust manager mà không có key manager, sau đó gọi server yêu cầu ClientAuth.REQUIRE. Handshake phải thất bại và business handler không chạy.

Một test khác dùng client certificate do CA không được server tin cậy ký. Server phải từ chối handshake.

## 10. TLS identity không tự động là application authorization

mTLS xác minh peer/workload ở tầng transport. Nó không tự quyết định certificate đó được gọi mọi RPC hoặc đọc mọi resource.

Ví dụ, server có thể xác minh SAN của client là spiffe://test.local/spring-grpc-client. Ứng dụng cần ánh xạ identity này thành principal/workload policy rồi kiểm tra quyền method hoặc resource.

Nếu RPC còn mang bearer token của người dùng, hai identity có mục đích khác nhau:

| Credential | Danh tính |
| --- | --- |
| Client certificate | Workload/service đang mở kết nối |
| Bearer token | User hoặc delegated principal mà request đại diện |

Test mTLS thành công chỉ chứng minh transport chấp nhận certificate. Cần test riêng authorization để chứng minh workload hoặc user chỉ được phép gọi đúng method.

## 11. Tích hợp test certificate với Spring gRPC

Có hai lớp test bổ sung cho nhau:

1. **Transport integration test:** khởi động Netty gRPC server/channel với test certificate để xác minh handshake, trust chain, SAN và mTLS. Cách này cô lập hành vi TLS của gRPC Java.
2. **Spring context integration test:** khởi động application context với cấu hình server/client TLS của đúng phiên bản Spring gRPC đang dùng, inject service/stub thực tế và gọi RPC qua TLS.

Ví dụ Netty trực tiếp không tự chứng minh các property hoặc customizer trong Spring Boot đã được cấu hình đúng. Spring gRPC có thể thay đổi tên property và cách tùy biến builder giữa các phiên bản; dùng reference của phiên bản dự án để cấu hình test context, không sao chép property từ phiên bản khác.

Trong Spring context test, kiểm tra:

- Server được khởi động với certificate/key test.
- Client bean dùng trust store/test CA dự kiến.
- Nếu bật mTLS, server yêu cầu client certificate.
- Generated stub được inject từ channel TLS đã cấu hình.
- Application service được gọi khi handshake thành công.
- Handshake thất bại thì handler không nhận request.

## 12. Kiểm tra TLS test có thật sự đáng tin?

Một test TLS có chất lượng phải thất bại khi bỏ hoặc thay đổi một điều kiện bảo mật:

| Thay đổi trong test | Kết quả mong đợi |
| --- | --- |
| Đổi trust CA sang CA không ký server cert | Handshake thất bại |
| Đổi authority thành hostname không có trong SAN | Handshake thất bại |
| Bỏ client cert khi server yêu cầu mTLS | Handshake thất bại |
| Dùng client cert do CA lạ ký | Handshake thất bại |
| Dùng đúng CA, SAN và key pair | Handshake thành công |
| Dùng certificate có EKU sai vai trò | Handshake bị từ chối theo TLS provider |
| Tắt TLS ở client nhưng server chỉ nhận TLS | Kết nối thất bại |

Ngoài handshake, kiểm tra server invocation count để bảo đảm request bị từ chối không chạy business logic. Không chỉ assert exception; một số lỗi có thể xảy ra sau khi transport đã tạo channel nhưng trước khi RPC được gửi.

## 13. Sai lầm thường gặp

1. **Dùng trust-all manager trong test.** Test không còn chứng minh client xác minh server certificate.
2. **Bỏ hostname verification để certificate tự ký chạy được.** SAN mismatch sẽ không bị phát hiện.
3. **Dùng chung certificate production trong test.** Lộ private key và làm test phụ thuộc môi trường thật.
4. **Chỉ test TLS thành công.** Không chứng minh trust chain, hostname hoặc mTLS được enforce.
5. **Dùng certificate thiếu SAN.** Có thể tạo test phụ thuộc hành vi cũ của TLS provider.
6. **Nhầm clientAuth và serverAuth EKU.** Certificate đúng CA nhưng sai mục đích vẫn không phù hợp.
7. **Cho rằng mTLS thay thế authorization.** Peer identity cần được ánh xạ và kiểm tra quyền.
8. **Không đóng channel/server sau test.** Có thể rò rỉ thread và làm test sau bị ảnh hưởng.
9. **Chỉ test Netty trực tiếp rồi kết luận Spring auto-configuration đúng.** Cần Spring context test cho cấu hình tích hợp thực tế.

## 14. Bài tập vận dụng

Với một Spring gRPC CatalogService:

1. Tạo test CA, server certificate có SAN DNS:localhost và client certificate có EKU clientAuth.
2. Khởi động Netty server trên cổng động với TLS.
3. Gọi RPC bằng client tin cậy test CA và xác minh response thành công.
4. Thử CA không tin cậy và hostname không khớp; xác minh handshake thất bại, handler không chạy.
5. Bật mTLS với ClientAuth.REQUIRE; xác minh client có certificate được chấp nhận.
6. Bỏ client certificate và thử certificate do CA lạ ký; xác minh server từ chối.
7. Chạy Spring context test với TLS configuration của phiên bản Spring gRPC trong dự án.
8. Đóng server/channel và xóa temporary key material sau mỗi test suite.

**Tiêu chí hoàn thành:** người học tạo được test certificate có CA, SAN và EKU phù hợp; kiểm thử TLS server authentication, hostname verification, trust chain và mTLS; xác minh lỗi handshake không đi vào business handler; đồng thời phân biệt transport identity với authorization của ứng dụng.
