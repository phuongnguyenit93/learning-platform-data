# Caching hoặc pooling kết nối và session trong JMS

> **Chương:** JMS  
> **Module:** SPRING_BOOT_INTEGRATION — tích hợp Spring Boot với HTTP client, cơ sở dữ liệu, cache, message broker và các adapter Spring Integration, chú trọng cấu hình, hợp đồng dữ liệu, giao dịch, xử lý lỗi, trùng lặp, kiểm thử và quan sát.  
> **Mục tiêu:** Hiểu khi nào nên cache hoặc pool JMS Connection, Session, Producer và Consumer; cấu hình an toàn trong Spring Boot, kiểm soát tài nguyên, phục hồi khi broker gặp lỗi.

Một ứng dụng nhận đơn hàng và gửi hàng nghìn sự kiện qua JMS mỗi phút. Mỗi lần gọi **JmsTemplate.convertAndSend(...)** cần làm việc với kết nối và phiên JMS. Tạo mới kết nối, session, producer rồi đóng hoàn toàn sau từng message gây chi phí lớn khi lưu lượng tăng. **Caching** và **pooling** giúp tái sử dụng tài nguyên, nhưng chúng có cách quản lý và giới hạn khác nhau.

Điểm cần nhớ ngay từ đầu: **caching/pooling là tối ưu vòng đời tài nguyên**, không phải bảo đảm giao message đúng một lần. Broker vẫn có thể redeliver sau lỗi; một send có thể đã thành công dù client chưa nhận được phản hồi. Thiết kế tích hợp cần thêm giao dịch, idempotency, retry và quan sát.

## 1. Tài nguyên JMS nằm ở đâu?

~~~mermaid
flowchart LR
    A["Service / @JmsListener"] --> B["JmsTemplate / Listener Container"]
    B --> C["ConnectionFactory"]
    C --> D["Connection"]
    D --> E["Session"]
    E --> F["MessageProducer / MessageConsumer"]
    F --> G["JMS Broker"]
~~~

| Tài nguyên | Vai trò | Quy tắc quan trọng |
| --- | --- | --- |
| **ConnectionFactory** | Factory để tạo JMS Connection | Có thể là factory nguyên bản, cache wrapper hoặc pool wrapper |
| **Connection** | Kết nối logic/physical transport tới broker | Tốn chi phí mở; có thể dùng nhiều session tùy provider |
| **Session** | Ngữ cảnh send/receive, ack và local transaction | **Không được sử dụng đồng thời một Session từ nhiều thread** |
| **MessageProducer** | Gửi message đến destination | Có thể cache/tái sử dụng theo cơ chế của wrapper |
| **MessageConsumer** | Nhận từ queue/topic, có thể gắn selector/subscription | Giữ consumer lâu có thể giữ tài nguyên/subscription ngoài dự kiến |
| **JmsTemplate** | Quản lý send/receive và đóng logical resources đúng quy ước | Bản thân template không đồng nghĩa ConnectionFactory có pool |
| **DefaultMessageListenerContainer** | Quản lý consumer chạy nền và tài nguyên của listener | Có mức caching connection/session/consumer riêng |

Trong dự án Spring Boot dùng Spring Framework 6 trở lên, JMS API dùng package **jakarta.jms**. Với phiên bản cũ có thể gặp **javax.jms**. Các dependency của broker, cache và pool phải tương thích cùng hệ JMS API.

### Vì sao không chia sẻ một Session cho tất cả request?

Session chứa trạng thái xử lý message, acknowledgment, transaction và consumer/producers của một phiên. Ví dụ hai HTTP request đồng thời cùng sử dụng một Session singleton rồi thao tác commit/rollback có thể làm lẫn ranh giới giao dịch. Một Connection có thể phục vụ nhiều Session, nhưng mỗi thao tác đồng thời cần Session được cấp phát theo đúng hợp đồng thread confinement của JMS/provider.

Không lưu **Session** hoặc **MessageProducer** vào một field của singleton service để nhiều thread dùng chung. Trong Spring, **JmsTemplate** và listener container đảm nhiệm tạo, sử dụng và trả tài nguyên thông qua **ConnectionFactory** đã cấu hình.

## 2. Caching và pooling khác nhau thế nào?

| Tiêu chí | **Spring CachingConnectionFactory** | **JMS pool** |
| --- | --- | --- |
| Cách hoạt động | Giữ kết nối dùng chung và các Session nhàn rỗi để tái sử dụng | Quản lý nhiều kết nối/session, cấp phát khi mượn và nhận lại khi đóng logical resource |
| Cơ chế phổ biến | **org.springframework.jms.connection.CachingConnectionFactory** | **org.messaginghub.pooled.jms.JmsPoolConnectionFactory** hoặc pool riêng của provider |
| Số Connection | Thường một physical Connection cho mỗi factory | Có thể giới hạn nhiều physical Connection |
| Số Session | **sessionCacheSize** là số session idle giữ lại **theo loại session**, không phải trần đồng thời | **maxSessionsPerConnection** thường là trần session cho mỗi connection |
| Khi hết session rảnh | Có thể tạo thêm session rồi đóng thật khi trả nếu cache đầy | Có thể mượn connection khác, chờ, timeout hoặc báo lỗi tùy policy |
| Producer/Consumer | Có tùy chọn cache producer và consumer | Chính sách cache/reuse phụ thuộc pool/provider |
| Thường phù hợp | Tải nhẹ đến vừa, producer ổn định, muốn giảm chi phí tạo resource | Nhiều operation song song, cần kiểm soát capacity/backpressure |
| Rủi ro | Nhầm cache size với giới hạn; cache consumer không cần thiết | Hết slot, borrow chờ dài, session leak, tăng quá nhiều connection ở quy mô cluster |

Không có lựa chọn luôn nhanh hơn: throughput còn chịu ảnh hưởng bởi broker, message persistence, transaction, acknowledgment, độ trễ mạng, kích thước message và concurrency.

### Pooling: có giới hạn capacity

~~~mermaid
flowchart TD
    A["Operation cần Session"] --> B{"Còn Session idle?"}
    B -->|Có| C["Borrow"]
    B -->|Không, còn capacity| D["Tạo Session trong giới hạn"]
    B -->|Không, đạt max| E["Wait / Timeout / Fail"]
    C --> F["Send / Receive"]
    D --> F
    F --> G["Close logical resource"]
    G --> H["Return Session to pool"]
~~~

Nếu code mượn tài nguyên rồi quên đóng, session tiếp tục bị tính là active; request sau có thể mắc kẹt khi pool đạt capacity. Ngược lại, đóng **logical connection/session** sau operation không nhất thiết đóng socket vật lý.

## 3. Dùng CachingConnectionFactory trong Spring Boot

**CachingConnectionFactory** mở rộng **SingleConnectionFactory**: duy trì connection mục tiêu, cache session và có thể cache producer/consumer tạo từ session. Các thiết lập thường dùng:

| Cấu hình | Tác dụng |
| --- | --- |
| **setSessionCacheSize(n)** | Giữ tối đa n Session idle cho từng kiểu session/ack mode |
| **setCacheProducers(true/false)** | Có cache producer đã tạo qua Session hay không |
| **setCacheConsumers(true/false)** | Có cache consumer đã tạo qua Session hay không |
| **setReconnectOnException(true/false)** | Cơ chế thay connection mục tiêu khi gặp JMS Exception |

Mặc định phổ biến của **sessionCacheSize** trong Spring là **1**. **Đó không phải giới hạn Session chạy đồng thời.** Nếu cùng lúc 20 request cần session thì wrapper có thể tạo thêm session ngoài số lượng đang cache; khi được trả về, chỉ một số session idle được giữ lại. Vì vậy cache phù hợp để giảm churn hơn là làm quota manager.

### 3.1. Khai báo wrapper khi đã có factory của provider

Ví dụ bean **nativeJmsConnectionFactory** được cấu hình trước đó bằng provider; lớp sau bọc factory và đặt cache:

~~~java
package example.integration.jms;

import jakarta.jms.ConnectionFactory;
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.Primary;
import org.springframework.jms.connection.CachingConnectionFactory;

@Configuration
public class JmsCachingConfiguration {
    @Bean
    @Primary
    public CachingConnectionFactory cachedConnectionFactory(
            @Qualifier("nativeJmsConnectionFactory")
            ConnectionFactory nativeFactory) {

        CachingConnectionFactory caching =
                new CachingConnectionFactory(nativeFactory);
        caching.setSessionCacheSize(10);
        caching.setCacheProducers(true);
        caching.setCacheConsumers(false);
        return caching;
    }
}
~~~

Đây là ví dụ dành cho ứng dụng **chủ động khai báo native provider bean**. Nếu dùng auto-configuration của Spring Boot thì có thể đã có cache wrapper; tránh bọc thêm một tầng mà không hiểu rõ cấu hình thực tế.

Trong những phiên bản Spring Boot có hỗ trợ cấu hình này, có thể dùng:

~~~yaml
spring:
  jms:
    cache:
      enabled: true
      session-cache-size: 10
~~~

Cấu hình **spring.jms.cache** điều khiển Spring cache wrapper, không phải giới hạn **maxConnections** của một provider pool. Cần đối chiếu configuration metadata của phiên bản Boot đang sử dụng.

### 3.2. Gửi message qua JmsTemplate

~~~java
package example.integration.jms;

import org.springframework.jms.core.JmsTemplate;
import org.springframework.stereotype.Service;

@Service
public class OrderEventPublisher {
    private final JmsTemplate jmsTemplate;

    public OrderEventPublisher(JmsTemplate jmsTemplate) {
        this.jmsTemplate = jmsTemplate;
    }

    public void publish(String orderId, String eventId) {
        jmsTemplate.convertAndSend(
                "orders.created",
                orderId,
                message -> {
                    message.setStringProperty("eventType", "OrderCreated");
                    message.setStringProperty("eventId", eventId);
                    return message;
                }
        );
    }
}
~~~

**JmsTemplate** quản lý scope của Session, Producer và operation. Khi wrapper có cache, thao tác close tại cuối operation có thể trả Session về cache để lần sau dùng tiếp. **eventId** là ID ổn định cho một sự kiện cụ thể; không tạo eventId mới trong mỗi lần retry cùng một thông điệp.

### 3.3. Cache producer và consumer có giống nhau không?

Producer thường gửi nhiều lần đến một tập destination tương đối ổn định, vì vậy tái sử dụng producer có thể giảm overhead. Consumer có lifecycle phức tạp hơn:

- Consumer có thể gắn với **message selector**, durable/shared subscription hoặc topic.
- Cache consumer từ những selector động có thể giữ resource không còn hữu ích.
- Listener container thường tự giữ Session/Consumer lâu dài theo cache level.
- Khi kết hợp nhiều tầng cache, khó nhìn thấy chính xác ai đang sở hữu Session/Consumer.

Với ứng dụng chủ yếu **gửi** bằng JmsTemplate và **nhận** bằng **@JmsListener**, có thể chọn **setCacheConsumers(false)** ở factory dùng cho producer, còn listener container tự quản lý consumer. Khi hai luồng dùng chung wrapper, cần kiểm tra lại lựa chọn theo provider, transaction và concurrency thực tế.

## 4. Dùng JMS pool để kiểm soát số connection và session

Một lựa chọn phổ biến trong môi trường Jakarta JMS là thư viện **pooled-jms** với **JmsPoolConnectionFactory**. Pool có thể giới hạn connection vật lý và session cho mỗi connection, giúp kiểm soát lượng tài nguyên dùng với broker khi có nhiều request đồng thời.

### 4.1. Ví dụ Java

Đoạn cấu hình sau giả định thư viện **org.messaginghub:pooled-jms** tương thích với Jakarta JMS của ứng dụng, và đã có bean **nativeJmsConnectionFactory**:

~~~java
package example.integration.jms;

import jakarta.jms.ConnectionFactory;
import org.messaginghub.pooled.jms.JmsPoolConnectionFactory;
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.Primary;

@Configuration
public class JmsPoolingConfiguration {

    @Bean(destroyMethod = "stop")
    @Primary
    public JmsPoolConnectionFactory pooledConnectionFactory(
            @Qualifier("nativeJmsConnectionFactory")
            ConnectionFactory nativeFactory) {

        JmsPoolConnectionFactory pool = new JmsPoolConnectionFactory();
        pool.setConnectionFactory(nativeFactory);
        pool.setMaxConnections(4);
        pool.setMaxSessionsPerConnection(16);
        pool.setBlockIfSessionPoolIsFull(true);
        return pool;
    }
}
~~~

**Không bật đồng thời JmsCachingConfiguration và JmsPoolingConfiguration** như hai bean cùng **@Primary** trong một ứng dụng. Đây là hai phương án cấu hình riêng; chọn một và kiểm tra bean nào thực sự được tiêm cho JmsTemplate/listener.

Với 4 connections × 16 sessions/connection, capacity lý thuyết của một instance là khoảng **64 sessions**. Thực tế còn phụ thuộc cách pool phân phối session, active/idle, transaction, provider và cách Connection được mượn. Khi ứng dụng chạy 10 instance, giới hạn toàn hệ thống có thể gần **640 pooled sessions**, nên phải tính tài nguyên broker theo số replica.

Khi **blockIfSessionPoolIsFull** được bật, request thiếu slot có thể chờ. Nên cấu hình borrow timeout theo API của **đúng phiên bản pooled-jms** và đặt timeout phù hợp với request SLA; đừng để một HTTP worker bị chặn vô hạn nếu broker hoặc consumer đang chậm.

### 4.2. Spring Boot với provider pool

Trong các phiên bản Spring Boot cung cấp Artemis pooling integration, có thể cấu hình dạng:

~~~yaml
spring:
  artemis:
    mode: native
    broker-url: tcp://localhost:61616
    pool:
      enabled: true
      max-connections: 4
      max-sessions-per-connection: 16
  jms:
    cache:
      enabled: false
~~~

Ví dụ yêu cầu starter/provider và thư viện pool phù hợp với Spring Boot đang dùng. Kiểm tra tên property và dependency theo version đã khóa trong dự án. **ActiveMQ Classic** và **Artemis** có prefix cấu hình/provider khác nhau; không sao chép nguyên thuộc tính **spring.artemis** cho ActiveMQ Classic.

Khi bật provider pool, tắt Spring cache wrapper sẽ tránh vô tình có hai lớp quản lý session. Trường hợp cố ý dùng hai tầng cần kiểm thử rõ tài nguyên thực tế và hành vi reconnect, vì pool capacity có thể bị che bởi cache bên ngoài.

### 4.3. Chọn kích thước pool

Một quy trình định cỡ:

1. Xác định **peak concurrency** của producer, listener, task nền trên **mỗi instance**.
2. Tính tổng giới hạn có thể xảy ra trên **tất cả replicas**.
3. Đặt **maxConnections**, **maxSessionsPerConnection** và timeout mượn theo tài nguyên broker có thể phục vụ.
4. Theo dõi số session active/idle/waiting, borrow latency, send latency, consumer throughput và lỗi.
5. Chỉ tăng giới hạn khi xác nhận pool saturation là nguyên nhân, đồng thời kiểm tra tải broker và database.

Pool lớn có thể tăng throughput khi bottleneck nằm ở kết nối/session; nếu bottleneck thật là broker disk, persistence, consumer logic hoặc HTTP downstream, pool lớn chỉ tạo thêm áp lực.

## 5. Listener container có cơ chế cache riêng

Spring **DefaultMessageListenerContainer (DMLC)** quản lý việc tạo listener threads, JMS Session, MessageConsumer và hồi phục khi nhận message lỗi. Với **@JmsListener**, ứng dụng thường cấu hình một **DefaultJmsListenerContainerFactory**.

~~~java
package example.integration.jms;

import jakarta.jms.ConnectionFactory;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.jms.config.DefaultJmsListenerContainerFactory;
import org.springframework.jms.listener.DefaultMessageListenerContainer;

@Configuration
public class ListenerConfiguration {
    @Bean
    public DefaultJmsListenerContainerFactory listenerFactory(
            ConnectionFactory connectionFactory) {

        DefaultJmsListenerContainerFactory factory =
                new DefaultJmsListenerContainerFactory();
        factory.setConnectionFactory(connectionFactory);
        factory.setConcurrency("2-6");
        factory.setSessionTransacted(true);
        factory.setCacheLevel(
                DefaultMessageListenerContainer.CACHE_CONSUMER);
        return factory;
    }
}
~~~

~~~java
package example.integration.jms;

import org.springframework.jms.annotation.JmsListener;
import org.springframework.stereotype.Component;

@Component
public class OrderEventListener {
    private final OrderConsumerService orderService;

    public OrderEventListener(OrderConsumerService orderService) {
        this.orderService = orderService;
    }

    @JmsListener(
            destination = "orders.created",
            containerFactory = "listenerFactory")
    public void handle(String orderId) {
        orderService.processIdempotently(orderId);
    }
}
~~~

**OrderConsumerService** trong ví dụ là service nghiệp vụ cần tự triển khai. Khi listener session transacted ném exception, container rollback phiên JMS, nên broker có thể redeliver. Service nghiệp vụ phải xử lý idempotent.

| Cache level của DMLC | Tài nguyên thường được giữ |
| --- | --- |
| **CACHE_NONE** | Không chủ động cache JMS resource giữa các chu kỳ receive |
| **CACHE_CONNECTION** | Connection |
| **CACHE_SESSION** | Connection và Session |
| **CACHE_CONSUMER** | Connection, Session và MessageConsumer |
| **CACHE_AUTO** | DMLC tự chọn theo môi trường và transaction manager |

Chọn **CACHE_CONSUMER** phù hợp với listener lâu dài trên queue ổn định, khi không có yêu cầu transaction manager đặc biệt. **Nếu dùng JTA/XA** cần xem lại cache level và cách resource được enlist; một số provider/transaction manager muốn cấp lại session cho mỗi transaction. Không ép CACHE_CONSUMER chỉ vì benchmark local tốt hơn.

### Concurrency và session capacity

Thiết lập **2-6** yêu cầu listener container có thể chạy từ mức tối thiểu đến tối đa tùy tải và chính sách scaling. Thông thường mỗi consumer đang chạy cần một session/consumer riêng. Nếu pool max sessions nhỏ hơn số listener thực tế cộng với số producer, có thể xảy ra đợi session, timeout hoặc starvation.

Đặc biệt, một ứng dụng có nhiều **@JmsListener** hoặc vừa JMS outbound vừa JMS inbound có thể dùng chung một ConnectionFactory. Tính tổng tài nguyên, không chỉ nhìn concurrency một listener.

### Queue và topic khác nhau

- Với **queue**, nhiều consumer cạnh tranh thường tăng throughput, nhưng thứ tự hoàn thành nghiệp vụ có thể thay đổi.
- Với **topic**, subscription khác nhau có thể cùng nhận bản sao message. Tăng subscriber không có nghĩa chia tải như queue.
- Với **durable/shared subscription**, client ID và subscription name phải tuân hợp đồng JMS và giới hạn của provider, đặc biệt khi chạy nhiều replicas.

Đối với nghiệp vụ cần thứ tự theo order ID hoặc account ID, cần routing/partitioning và chính sách concurrency phù hợp; tăng số consumer tùy tiện có thể phá thứ tự cập nhật.

## 6. Tái sử dụng tài nguyên không tạo giao dịch phân tán

Session JMS có thể tham gia **local JMS transaction** hoặc một **external/JTA transaction** nếu provider và transaction manager hỗ trợ. Cache/pool chỉ quản lý lifecycle của resource; không thay đổi bản chất giao dịch.

| Trường hợp | Bảo đảm cần phân biệt |
| --- | --- |
| **JMS Session transacted** | Commit/rollback của message trong phạm vi session transaction |
| **AUTO_ACKNOWLEDGE** | Acknowledge theo semantics JMS và listener container tương ứng |
| **CLIENT_ACKNOWLEDGE** | Ứng dụng điều khiển ack theo session; cần hiểu phạm vi ack của session |
| **JDBC @Transactional** | Quản lý database transaction được enlist; không mặc nhiên rollback message đã gửi qua JMS |
| **JTA/XA** | Chỉ phối hợp atomically các resource XA thực sự được enlist với transaction manager phù hợp |

Ví dụ failure window khi consumer ghi PostgreSQL:

~~~text
1. Broker giao OrderCreated(eventId=E123).
2. Consumer ghi database và COMMIT.
3. Process chết trước khi JMS Session COMMIT/ACK.
4. Broker giao lại E123.
5. Nếu không deduplicate, consumer có thể ghi nghiệp vụ hai lần.
~~~

Vì vậy consumer nên có **inbox/processed_message** với unique **eventId** lưu trong cùng transaction database với side effect. Nếu đang phát thông điệp sau DB commit, **transactional outbox** là cách giữ lại ý định phát message để publisher retry. Một session pool lớn không thể giải quyết vấn đề duplicate delivery hoặc missing event.

### Ví dụ inbox chống xử lý trùng

~~~sql
CREATE TABLE processed_message (
    consumer_name VARCHAR(100) NOT NULL,
    event_id VARCHAR(100) NOT NULL,
    processed_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    PRIMARY KEY (consumer_name, event_id)
);
~~~

~~~java
@Transactional
public void process(String eventId, String orderId) {
    int created = jdbcTemplate.update("""
            INSERT INTO processed_message (consumer_name, event_id)
            VALUES ('order-consumer', ?)
            ON CONFLICT DO NOTHING
            """, eventId);

    if (created == 0) {
        return;
    }

    orderRepository.applyOrderCreated(orderId);
}
~~~

Ví dụ SQL sử dụng PostgreSQL; **orderRepository.applyOrderCreated(...)** đại diện cho thao tác nghiệp vụ trong **cùng datasource/transaction manager** với processed_message. Nếu transaction rollback, cả dấu xử lý và kết quả nghiệp vụ rollback để lần redelivery có thể xử lý lại. Ví dụ listener trước đó chỉ nhận orderId nên trong hệ thống thật cần **message contract chứa eventId** và mapping tương ứng vào service.

### Session bị trả về khi transaction chưa kết thúc?

Khi dùng JMS API trực tiếp, lập trình viên phải commit/rollback, ack và close đúng thứ tự. Pool có cơ chế thu hồi/cleanup, nhưng không nên dựa vào nó để sửa code đang giữ Session transacted dở. Khi dùng **JmsTemplate** và listener container, để Spring kiểm soát phiên sẽ giảm rủi ro tài nguyên bị đưa cho luồng khác sai lifecycle.

## 7. Broker restart, reconnect và kết quả gửi không chắc chắn

Một Connection vật lý có thể bị ngắt khi broker restart hoặc mạng bị phân vùng. Cache/pool cần phát hiện resource lỗi và tạo lại các connection/session tương ứng. Tuy nhiên không phải mọi trường hợp lỗi đều có thể xác định message đã được broker nhận hay chưa.

~~~mermaid
sequenceDiagram
    participant A as Producer
    participant P as Cache / Pool
    participant B as JMS Broker
    A->>P: send(eventId=E123)
    P->>B: Message E123
    Note over B: Broker đã nhận/lưu
    B--xP: Mất kết nối trước ACK
    P-->>A: JMSException hoặc timeout
    A->>P: Retry send E123
    P->>B: Message E123
    Note over B: Có thể nhận hai bản sao cùng eventId
~~~

Một số hướng xử lý:

1. **Dùng eventId ổn định** khi retry cùng sự kiện; consumer dedup theo eventId.
2. **Retry có giới hạn và backoff**, tránh bắn liên tiếp làm broker mới khởi động quá tải.
3. **Quan sát reconnect/JMSException**; phân biệt lỗi cấu hình và lỗi tạm thời.
4. **Outbox** nếu dữ liệu DB và message phải được phối hợp tin cậy.
5. **DLQ và poison-message policy** nếu consumer không thể xử lý một message.
6. **Reconciliation** khi nghiệp vụ cần xác nhận trạng thái cuối cùng ở các hệ thống độc lập.

Wrapper có thể thay physical Connection sau exception, nhưng không thể tự rollback side effect đã commit ở hệ thống khác. Đồng thời, pool/consumer cần lifecycle shutdown phù hợp để không giữ kết nối zombie sau rolling deployment.

## 8. Chọn cache hay pool cho từng tình huống

| Kịch bản | Hướng chọn | Cần xác minh |
| --- | --- | --- |
| Producer tải đều, ít thread, gửi cùng queue | Spring **CachingConnectionFactory** | Tỷ lệ tái sử dụng session/producer, send latency |
| Producer burst lớn, nhiều thread | **JMS pool** có giới hạn và borrow timeout | Pool saturation, số connection trên toàn cluster, broker capacity |
| Consumer chạy lâu qua **@JmsListener** | Cache level của **DMLC**, có thể dùng connection factory phù hợp | Listener concurrency, broker consumer count, selectors |
| JMS + DB cùng yêu cầu atomic XA | XA-capable provider factory và JTA transaction manager | Enlistment, recovery, DMLC cache level; pool thường không tự hỗ trợ XA |
| JMS sender từ Spring Integration adapter | Chọn factory cho adapter/JmsTemplate theo tải | Ai sở hữu Session và transaction; không chồng cache |
| Đẩy sự kiện DB đến broker tin cậy | Outbox publisher + caching/pooling phù hợp | DB commit, duplicate send, retry, consumer inbox |

**JmsPoolConnectionFactory thông dụng không phải một giải pháp XA pooling mặc định.** Nếu ứng dụng cần XA, xác minh phiên bản thư viện/provider và integration với JTA transaction manager. Không coi việc bọc một XAConnectionFactory vào pool thường là đủ để có transaction phân tán đúng.

## 9. Những lỗi cấu hình dễ gặp

**Nhầm sessionCacheSize với max concurrent sessions.** CachingConnectionFactory có thể tạo thêm session ngoài cache để xử lý request đồng thời. Dùng pool khi cần giới hạn thật.

**Tăng maxConnections nhưng quên số replicas.** Bốn connection trên mỗi instance nhân với 30 pods là 120 connection vật lý dự kiến, chưa kể các loại client khác.

**Giữ Session trong singleton bean.** Session không an toàn để nhiều thread dùng đồng thời, đặc biệt với ack/transaction.

**Không close resource mượn từ pool.** Session bị giữ active khiến các request mới chờ hoặc timeout. Code JMS trực tiếp cần try-with-resources hoặc finally phù hợp.

**Cache consumer động vô thời hạn.** Các selector và subscription đã cũ có thể giữ resource trên broker. Xem xét disable cacheConsumers hoặc để listener container quản lý.

**Bật cache wrapper và provider pool chồng nhau.** Hai vòng đời resource gây khó quan sát borrow/return, reconnect và capacity. Nếu phải kết hợp, cần test cụ thể.

**Quá nhiều listener nhằm xử lý backlog.** Bottleneck thực có thể là DB lock hoặc API downstream; tăng consumer làm số message retry/tranh chấp tăng.

**Tin rằng close() luôn đóng physical socket.** Với cache/pool, thường chỉ đóng handle logic hoặc trả session về cache/pool; chỉ destroy factory/stop pool ở lifecycle shutdown.

**Tin rằng caching bảo đảm exactly-once.** Lost ACK, process crash và redelivery có thể tạo duplicate. Chống trùng bằng business key/event ID.

## 10. Observability và tuning

Theo dõi ít nhất:

| Chỉ số | Ý nghĩa |
| --- | --- |
| **Active/idle connections** | Số socket/broker resources đang giữ |
| **Active/idle/waiting sessions** | Pool có đang cạn slot hoặc bị session leak |
| **Session creation rate** | Cache có đang tái sử dụng hiệu quả |
| **Borrow wait/timeout** | Operation có bị kẹt trước khi gửi message |
| **Send/receive latency** | Tách trễ do pool, broker và business handler |
| **Listener concurrency** | Consumer thực tế có đúng với giới hạn không |
| **Queue depth / age** | Message backlog và tuổi message cũ nhất |
| **Redelivery / DLQ** | Lỗi xử lý, message bị lặp hoặc poison message |
| **Reconnect / JMSException** | Chất lượng kết nối và khả năng phục hồi broker |
| **Outbox/inbox lag** | Độ trễ đồng bộ nghiệp vụ xuyên DB–broker |

Không phải thư viện pool/provider nào cũng tự expose mọi metric qua Spring Boot Actuator. Có thể cần exporter của broker, JMX hoặc instrumentation phù hợp. Đừng suy ra pool không nghẽn chỉ vì CPU application thấp: thread có thể đang chờ borrow.

Quy trình đo:

1. **Baseline** với cùng broker, persistent-delivery mode, kích thước message và transaction mode.
2. **Load test** mức tải bình thường và burst, đo throughput, p95/p99, session active/idle.
3. **Kiểm tra nút nghẽn** là pool hay broker/consumer/database trước khi tăng capacity.
4. **Tăng từng tham số**, tính tổng replica và broker limit.
5. **Fault injection**: restart broker, cắt mạng ngắn, làm chậm consumer, xác minh recovery và duplicate handling.

## 11. Kiểm thử cần có trước production

| Tình huống | Điều cần chứng minh |
| --- | --- |
| Gửi nhiều message tuần tự | Gửi đủ, caching giảm session/producer churn so với không cache |
| Burst lớn hơn sessionCacheSize | Concurrent send vẫn chạy đúng, không chia sẻ cùng Session đồng thời |
| Burst vượt pool capacity | Chờ/timeout/failed theo policy; không làm treo vô hạn mọi HTTP worker |
| Listener scale từ 2 tới 6 consumers | Không vượt resource budget; semantics queue/topic đúng |
| Broker restart giữa send | Kết nối hồi phục, retry không tạo side effect trùng |
| Consumer commit DB rồi chết trước ack | Redelivery được inbox/business key dedup |
| Message thất bại liên tục | Retry có giới hạn, DLQ được cấu hình và quan sát |
| Rolling deploy | Listener dừng, connection/pool được đóng theo lifecycle |
| External XA nếu có | Resource được enlist và recovery đúng khi lỗi giữa commit |

Khi kiểm tra việc tạo connection/session, redelivery và failover, nên dùng broker thật trong integration test, ví dụ Apache ActiveMQ Artemis qua Testcontainers hoặc môi trường test tương ứng. Mock JmsTemplate chỉ chứng minh lời gọi service, không kiểm chứng hành vi pool dưới lỗi mạng.

## 12. Checklist triển khai

- Đã chọn đúng JMS API **jakarta.jms**/**javax.jms** phù hợp Spring Boot, Spring Framework và provider.
- Biết chính xác **ConnectionFactory bean nào** được JmsTemplate, listener và Spring Integration adapter sử dụng.
- Chỉ cấu hình một lớp caching/pooling chính cho producer theo nhu cầu; mọi tầng bổ sung đều có lý do và test.
- Không chia sẻ Session giữa nhiều thread; đóng logical resource đúng thời điểm.
- Sizing theo số operation đồng thời **và số replicas**, có timeout borrow/backpressure.
- Listener concurrency, cache level, selectors và queue/topic semantics được thiết kế rõ.
- Session transaction và DB transaction được phân biệt; XA chỉ dùng khi đã xác minh provider/manager.
- Có eventId, inbox/outbox, idempotent consumer và chính sách retry/DLQ cho các thao tác quan trọng.
- Có metric về saturation, queue backlog, redelivery, latency và reconnect.
- Đã test burst, crash, broker restart, DB commit trước ack và shutdown.
