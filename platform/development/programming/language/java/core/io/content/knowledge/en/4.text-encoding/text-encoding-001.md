# Relationship Between Bytes, UTF-16 `char`, Code Points, and Displayed Characters

> **Scope:** Java Core – I/O → Text Encoding. This lesson explains why “one character” does not always correspond to one `byte`, one Java `char`, or one Unicode code point; and how to read, write, count, slice, and display text correctly in Java. Examples use Java 17 unless another version is noted.

## 1. Four Data Layers to Distinguish

When saving a person's name or an emoji to a file, the system passes through several different representations:

`User-perceived text → grapheme clusters → sequence of Unicode code points → sequence of UTF-16 code units in the String/char API → byte[] by charset when encoding to I/O.`

Reading a file happens in the reverse direction: **bytes** must be **decoded** using a charset to produce a character string. It is impossible to infer what bytes mean without encoding information.

| Layer | Unit of Measurement | Representation in Java | Key Takeaways |
| --- | --- | --- | --- |
| **Byte** | 8 bits, bit value 0–255 | `byte`/`byte[]`, `InputStream`, `ByteBuffer` | Java `byte` has signed values -128…127, but its bit pattern is still 8 bits. The byte count depends on the charset. |
| **UTF-16 code unit** | 16 bits | A `char` element; `String.length()` counts code units | A code point outside the BMP uses **two** `char`s (a surrogate pair). |
| **Unicode code point** | Value `U+0000`…`U+10FFFF` | Commonly `int`, `String.codePoints()`, `codePointAt` | Unicode code identification unit; a “visible character” can still consist of **multiple** code points. |
| **Grapheme cluster** (extended grapheme cluster) | A unit of text that users typically treat as “one character” when selecting/deleting | No corresponding primitive data type; can be segmented using regex `\X` since Java 9 | A cluster may consist of base letter + combining marks, emoji + variation selector, emoji + ZWJ, or regional indicator pairs. |
| **Glyph / rendered shape** | Shape generated by a font and text shaping engine | Belongs to the UI renderer, not a `String` type | The number of glyphs, display cells, and graphemes **are not necessarily equal**. |

**Precise terminology:** in the Java specification, `char` is a **UTF-16 code unit**, not guaranteed to be a “complete Unicode character.” `String` provides APIs and indices based on UTF-16 code units, even though modern Java runtimes may optimize internal storage via other mechanisms (such as compact strings). Do not infer in-memory byte layout solely from `String.length()`.

### How do bytes differ from characters?

- `A` is code point **U+0041**. UTF-8 stores it as **1 byte** `41`; UTF-16 needs **1 code unit** `0041`.
- Precomposed `é` is **U+00E9**. UTF-8 stores it as **2 bytes** `C3 A9`; UTF-16 needs **1 code unit** `00E9`.
- `🙂` is **U+1F642**, outside the BMP. UTF-8 stores it as **4 bytes** `F0 9F 99 82`; UTF-16 uses two code units `D83D DE42`, yet it is only **1 code point** and normally **1 grapheme cluster**.
- `é` as letter `e` plus a combining mark is **U+0065 U+0301**. UTF-8 consists of **3 bytes** `65 CC 81`, UTF-16 consists of **2 code units**, it has **2 code points**, yet a reader usually sees it as **1 grapheme cluster** (looking like `é`).
- Emoji **👩‍💻** is typically the sequence `U+1F469` (woman), `U+200D` (zero-width joiner), `U+1F4BB` (laptop). This sequence comprises **11 UTF-8 bytes**, **5 UTF-16 code units**, **3 code points**, and is normally **1 extended grapheme cluster**; unsupported fonts or software may render it as multiple shapes.

The two words “character” and “length” easily cause confusion unless it is specified whether you are measuring **bytes**, **code units**, **code points**, or **grapheme clusters**.

## 2. UTF-8 and UTF-16 Operate at Two Different Steps

**Unicode** defines the code point system and text processing rules. **UTF-8** and **UTF-16** are ways to transform code points into encoding units (code units). A **charset** also includes the corresponding encoding/decoding rules. Code points are not synonymous with bytes.

- **UTF-8:** a Unicode scalar value is encoded into **1–4 bytes**. ASCII U+0000…U+007F uses 1 byte. Non-ASCII characters can occupy 2, 3, or 4 bytes. UTF-8 is variable-length but does not depend on byte order like UTF-16.
- **UTF-16:** a Unicode scalar value in the BMP that is not a surrogate needs **1 16-bit code unit**; code points `U+10000`…`U+10FFFF` need **2 code units** forming a surrogate pair. When writing UTF-16 to a file, each code unit must in turn be serialized into **bytes** in the appropriate byte order, such as UTF-16BE or UTF-16LE.
- **Java `String` and `char`:** in terms of API semantics, `String` indices follow UTF-16 code units. However, when reading/writing UTF-8 files, Java encodes/decodes between these units and byte sequences; this does not mean the file must be stored as UTF-16.
- **BOM:** some UTF-16 files have a byte-order mark to indicate endianness; UTF-8 does not need a BOM to determine byte order. Do not unconditionally strip/keep a BOM: follow the data format contract.
- A `byte` in Java is signed; when printing in hex, use `b & 0xFF` to get the unsigned value 0–255. Do not use `String.length()` as the byte size that a UTF-8 payload will occupy.

### 2.1. Converting between bytes and strings always requires a charset

~~~java
import java.nio.charset.StandardCharsets;

// Fragment example: valid UTF-8 input data.
String text = "Tiếng Việt 🙂";
byte[] bytes = text.getBytes(StandardCharsets.UTF_8);       // Encode
String restored = new String(bytes, StandardCharsets.UTF_8); // Decode
boolean equal = text.equals(restored);                      // true
~~~

This is a **fragment** illustrating the conversion step; `StandardCharsets.UTF_8` ensures the result does not depend on the machine's default charset. For payloads coming from the network, databases, or legacy files, **you cannot assume bytes are always UTF-8**; you must know the actual contract. Since JDK 18, JEP 400 specifies UTF-8 as the default charset for affected Java SE APIs, but this change does not automatically convert legacy files.

For valid UTF-8 data, encoding and then decoding with the same charset preserves the content. If the byte array does not match the encoding, the `new String(bytes, UTF_8)` constructor may replace invalid byte sequences with a replacement character; when strict validation is needed, use `CharsetDecoder` configured with `CodingErrorAction.REPORT`.

## 3. `char` and Surrogate Pairs in Java

The `char` type holds **16 bits**. Unicode could once represent common codes in a single 16-bit unit, but today many code points lie outside the **Basic Multilingual Plane (BMP, U+0000…U+FFFF)**. UTF-16 represents supplementary code points using two `char`s:

- **High surrogate:** from `U+D800` to `U+DBFF`.
- **Low surrogate:** from `U+DC00` to `U+DFFF`.
- A high surrogate immediately followed by a valid low surrogate represents a single code point from `U+10000` to `U+10FFFF`.

Example:

~~~text
Emoji 🙂 = U+1F642
UTF-16 high surrogate = 0xD83D
UTF-16 low surrogate  = 0xDE42
"🙂".length()          = 2
"🙂".codePointCount(0, 2) = 1
~~~

**Note on Unicode scalar values:** the total code point space is `U+0000`…`U+10FFFF`, but **U+D800…U+DFFF** are reserved for surrogates and are **not** valid Unicode scalar values for direct UTF-8 encoding. A `String` can still contain unpaired surrogates due to slicing operations or malformed data sources. In that case, `codePoints()`/`codePointCount()` handle unpaired surrogates per the API contract, **which does not guarantee that the string is a valid Unicode scalar sequence**.

APIs to remember:

| API | Returned Unit / Operation |
| --- | --- |
| `s.length()` | Number of **UTF-16 code units** in the string |
| `s.charAt(i)` | A `char` at **UTF-16 index**, which may be only half of a surrogate pair |
| `s.codePointAt(i)` | Code point at UTF-16 position `i` if a valid surrogate pair is encountered; returns the single unit value if unpaired |
| `s.codePointCount(begin, end)` | Number of code points in the **UTF-16 index** range, including unpaired surrogates counted individually |
| `s.codePoints()` | `IntStream` of code points; valid surrogate pairs are combined |
| `s.chars()` | `IntStream` of **char code unit** values; does not combine surrogate pairs |
| `s.offsetByCodePoints(index, count)` | Shifts a UTF-16 position by a number of **code points**, returning a UTF-16 position |
| `Character.charCount(cp)` | Number of UTF-16 code units required to represent the code point (1 or 2) |
| `Character.toChars(cp)` / `StringBuilder.appendCodePoint(cp)` | Converts a code point into one or two code units to insert into a string |

**Important warning:** the indices of `substring(begin,end)`, `charAt(i)`, `indexOf`/`lastIndexOf`, and most position-based `String` APIs are **UTF-16 positions**. If you call `substring(0, 1)` on a string starting with an emoji outside the BMP, you can split a surrogate pair in half.

### 3.1. Iterating over code points properly

~~~java
// Fragment: 's' is an initialized Java String.
for (int i = 0; i < s.length(); ) {
    int cp = s.codePointAt(i);
    // Process cp here, e.g., Character.isLetter(cp).
    i += Character.charCount(cp);
}
~~~

The loop above advances by **code point**, not by grapheme. For Vietnamese strings containing combining marks, one iteration may receive the base letter and the next iteration the combining mark; for ZWJ emoji, it visits multiple code points even though the user sees a single combined emoji.

## 4. A “Displayed Character” Can Consist of Multiple Code Points

Text processing software often uses **extended grapheme clusters** defined by Unicode Text Segmentation (UAX #29) to approximate user-perceived units. Key examples:

| Data | Code Point Sequence | Code Point Count | Typical Graphemes |
| --- | --- | --- | --- |
| `A` | `U+0041` | 1 | 1 |
| Precomposed `é` | `U+00E9` | 1 | 1 |
| Decomposed `é` | `U+0065 U+0301` | 2 | 1 |
| `🙂` | `U+1F642` | 1 | 1 |
| `🇻🇳` | `U+1F1FB U+1F1F3` (regional indicators) | 2 | 1 |
| `👩‍💻` | `U+1F469 U+200D U+1F4BB` | 3 | 1 |

Combination rules depend on the **Unicode version** and the segmentation library; adding new emojis can change results across runtime versions. Rendering also depends on fonts, operating systems, text shaping libraries, and language. One grapheme is not guaranteed to be **one glyph**, one pixel width, or one monospace cell.

### 4.1. Java regex `\X` for extended grapheme clusters

Since **Java 9**, `java.util.regex.Pattern` supports `\X` (matches one extended grapheme cluster) and `\b{g}` (grapheme cluster boundary). In a Java string literal, the backslash must be escaped: write `"\\X"` so the regex engine receives `\X`.

~~~java
// Fragment for Java 9+.
java.util.regex.Matcher m =
    java.util.regex.Pattern.compile("\\X").matcher(text);
int graphemes = 0;
while (m.find()) {
    graphemes++;
}
~~~

`text` is the string to count. On Java 8, **do not rely on `\X`** because Java 8 regex documentation does not include this syntax. If an application requires grapheme segmentation matching a specific Unicode version across multiple JDKs, check the algorithm version, test with real data, and consider a dedicated Unicode library such as ICU4J per project requirements.

### 4.2. Is `BreakIterator` the same as `\X`?

`java.text.BreakIterator.getCharacterInstance(locale)` can find character boundaries for UI tasks, but **you should not assume** its results match the exact **extended grapheme cluster** rules of regex `\X` across every JDK version/locale, especially for ZWJ-joined emojis. If the technical requirement specifies Unicode UAX #29, **test** boundaries with sample strings in the target deployment environment.

## 5. Standalone Runnable Example: Counting All Four Layers

Save as **`UnicodeLayers.java`** (runs on Java 17, using `\X` available since Java 9):

~~~java
import java.nio.charset.StandardCharsets;
import java.util.regex.Matcher;
import java.util.regex.Pattern;

public class UnicodeLayers {
    private static final Pattern GRAPHEME = Pattern.compile("\\X");

    private static int graphemeCount(String value) {
        Matcher matcher = GRAPHEME.matcher(value);
        int count = 0;
        while (matcher.find()) {
            count++;
        }
        return count;
    }

    private static void inspect(String label, String value) {
        int bytes = value.getBytes(StandardCharsets.UTF_8).length;
        int chars = value.length();
        int codePoints = value.codePointCount(0, chars);
        int graphemes = graphemeCount(value);
        System.out.printf(
            "%s: bytes=%d, chars=%d, codePoints=%d, graphemes=%d%n",
            label, bytes, chars, codePoints, graphemes
        );
    }

    public static void main(String[] args) {
        inspect("A", "A");
        inspect("e-composed", "\u00E9");
        inspect("e-decomposed", "e\u0301");
        inspect("smile", "\uD83D\uDE42");
        inspect("woman-technologist", "\uD83D\uDC69\u200D\uD83D\uDCBB");
    }
}
~~~

Compile/run:

~~~bash
javac --release 17 UnicodeLayers.java
java UnicodeLayers
~~~

**Verified stdout:**

~~~text
A: bytes=1, chars=1, codePoints=1, graphemes=1
e-composed: bytes=2, chars=1, codePoints=1, graphemes=1
e-decomposed: bytes=3, chars=2, codePoints=2, graphemes=1
smile: bytes=4, chars=2, codePoints=1, graphemes=1
woman-technologist: bytes=11, chars=5, codePoints=3, graphemes=1
~~~

What to observe:

1. `e-composed` and `e-decomposed` usually look identical yet have **different byte counts, code unit counts, and code point counts**.
2. `smile` has only **1 code point** yet `String.length() == 2` because of the surrogate pair.
3. `woman-technologist` is **one extended grapheme cluster** yet consists of multiple code points combined via ZWJ.
4. Byte counts are measured in the specified **UTF-8** encoding; encoding the file to UTF-16 would produce different byte counts. Grapheme counts reflect the running Java segmentation algorithm, not a measurement of “rendered shapes” on screen.

## 6. Standalone Runnable Example: Why `charAt`/`substring` Easily Split Incorrectly

Save as **`UnicodeIndex.java`**:

~~~java
public class UnicodeIndex {
    public static void main(String[] args) {
        String text = "A\uD83D\uDE42B"; // A + 🙂 + B

        System.out.println("utf16=" + text.length());
        System.out.println("codePoints="
            + text.codePointCount(0, text.length()));
        System.out.printf("charAt(1)=U+%04X%n", (int) text.charAt(1));
        System.out.printf("codePointAt(1)=U+%04X%n", text.codePointAt(1));

        int afterTwoPoints = text.offsetByCodePoints(0, 2);
        System.out.println("indexAfterTwoCodePoints=" + afterTwoPoints);
        System.out.println("middle=" + text.substring(1, afterTwoPoints));
        System.out.println("splitSurrogate="
            + Character.isHighSurrogate(text.substring(1, 2).charAt(0)));
    }
}
~~~

~~~bash
javac --release 17 UnicodeIndex.java
java UnicodeIndex
~~~

Stdout:

~~~text
utf16=4
codePoints=3
charAt(1)=U+D83D
codePointAt(1)=U+1F642
indexAfterTwoCodePoints=3
middle=🙂
splitSurrogate=true
~~~

The string has four UTF-16 positions: index 0 is `A`, indices 1–2 are the high/low surrogates of `🙂`, and index 3 is `B`. `substring(1,2)` contains only **an unpaired high surrogate**; it is **not** a complete emoji character. `offsetByCodePoints(0,2)` returns the **UTF-16 index 3**, not the “value of the second code point.”

This handles **code point boundaries**, which still does not guarantee **grapheme cluster** boundaries. If the string is `e\u0301`, slicing after the `e` code point separates the accent mark from the base letter; to operate on “user-perceived characters,” grapheme segmentation is required.

## 7. Strings That Look Identical Yet `equals` Returns `false`: Normalization

Unicode allows the same text to be represented by different sequences of code points. For example, precomposed `é` (`U+00E9`) and `e` + `U+0301` may look identical, yet their Java strings differ at the code unit level.

~~~java
// Fragment can be placed inside main; java.text.Normalizer is part of Java SE.
String composed = "\u00E9";
String decomposed = "e\u0301";

System.out.println(composed.equals(decomposed)); // false
System.out.println(
    java.text.Normalizer.normalize(
        composed, java.text.Normalizer.Form.NFC
    ).equals(
        java.text.Normalizer.normalize(
            decomposed, java.text.Normalizer.Form.NFC
        )
    )
); // true
~~~

- **NFC** produces canonical normalized form with composition where applicable; **NFD** performs canonical decomposition. `Normalizer` belongs to Java SE, not an external dependency.
- **Normalization is not encode/decode**: it can transform code point sequences representing canonically equivalent content, whereas encode/decode converts between characters and bytes according to a charset.
- `String.equals` checks the sequential content of code units; it does not automatically apply NFC/NFD, does not compare by locale, and does not compare “visual similarity.”
- **Do not blindly normalize** data used for hashing, digital signatures, identifier matching, passwords, protocols, or database queries; normalization rules must be agreed upon across all inputs and storage layers. Visually similar characters with **different code points** (homoglyphs) are also not guaranteed to be unified by normalization.
- For language-sensitive sorting/comparison, consider the `Collator` API and locale rules; that is a separate topic from counting bytes/UTF-16/code points/graphemes.

## 8. File Reading/Writing: Where Encoding Sits in the Data Path

~~~text
           WRITE                               READ
String/char (UTF-16 API)                  byte[]/InputStream
        |                                         |
   UTF-8 encoder                             UTF-8 decoder
        |                                         |
  byte[] / OutputStream                    String/char (UTF-16 API)
        |                                         |
   file / network                      process code points /
                                       graphemes as needed
~~~

**Correct:** APIs with an explicit charset contract, such as `Files.writeString(path, text, StandardCharsets.UTF_8)` and `Files.readString(path, StandardCharsets.UTF_8)` (since Java 11); or `InputStreamReader(input, StandardCharsets.UTF_8)` for streams in Java 8.

**Common mistake:** reading UTF-8 bytes one by one and casting each byte to `char` to assemble Vietnamese strings. For example, `é` has bytes `C3 A9`, not two “letters” corresponding to two bytes. You need a UTF-8 decoder processing complete byte sequences or a stateful decoder across reads.

**Buffer boundaries:** the UTF-8 byte sequence of a single code point can be split across two `InputStream.read(...)` calls. Do not decode each chunk independently with `new String(chunk, UTF_8)` if a chunk might end in the middle of a multi-byte sequence; use a stateful decoder or a `Reader` class that preserves decoder state across reads.

**Invalid data:** on systems that must reject malformed UTF-8 instead of silently replacing it, you can use:

~~~java
// Fragment: example of validating malformed UTF-8 bytes.
java.nio.charset.CharsetDecoder decoder =
    java.nio.charset.StandardCharsets.UTF_8.newDecoder()
        .onMalformedInput(java.nio.charset.CodingErrorAction.REPORT)
        .onUnmappableCharacter(java.nio.charset.CodingErrorAction.REPORT);

byte[] invalid = {(byte) 0xC3, (byte) 0x28};
// decoder.decode(ByteBuffer.wrap(invalid)) throws CharacterCodingException.
~~~

This snippet shows the configuration; to execute it, call `decoder.decode(java.nio.ByteBuffer.wrap(invalid))` inside a method with `throws java.nio.charset.CharacterCodingException` or a `try/catch` block. The relationship to remember: **bytes** are decoded into **UTF-16 code units in the String API**; from there, code points and graphemes serve text processing, rather than re-creating an encoding step again.

## 9. Length Counting, String Slicing, and Input Limits

Do not use vague variable names like `maxCharacters` when the limit unit is undefined. The question to answer before choosing an API is: **what unit is the limit measured in?**

| Requirement | Measurement / Solution | Pitfalls |
| --- | --- | --- |
| API or protocol limited by **UTF-8 bytes** | `s.getBytes(UTF_8).length` | `s.length()` is not payload length; do not cut bytes in the middle of a UTF-8 sequence. |
| Library/API defining length in **UTF-16 code units** | `s.length()` | Emojis outside the BMP count as two. |
| Unicode analysis by **code point** | `s.codePointCount(0,s.length())`, `s.codePoints()` | Combining marks, ZWJ, and flag emojis have multiple code points; unpaired surrogates require validation. |
| UI counting user-perceived characters | Segment **extended grapheme clusters** | Different Unicode versions and product rules may require testing. |
| Slicing/truncating strings for display | Slice at computed **grapheme boundaries** and test rendering | Slicing by code point can still split combining marks/ZWJ; grapheme count alone also does not measure screen width. |
| Terminal width, column alignment | Display-width measurement library suited to the terminal/font | A grapheme may have width 0, 1, 2, or other depending on the renderer; ANSI control codes also affect layout. |
| Search/matching normalization | Define normalization, case folding, locale/collation | `equalsIgnoreCase` does not handle all Unicode/locale rules or confusable text. |

**Practical example:** A form limiting a nickname to “10 characters” likely expects 10 graphemes, whereas an API checking 10 UTF-16 code units will count many emojis as two and treat precomposed accented letters differently from decomposed ones. If the backend also enforces a 40-byte UTF-8 limit, you need **two** separate constraints: graphemes for UX and bytes for storage. The byte limit may be reached either before or after the grapheme count depending on the content.

**When slicing by code point:** use `offsetByCodePoints` to find the UTF-16 index for `substring`. **When slicing by grapheme:** iterate with the `\X` matcher, capture `matcher.end()` (the UTF-16 position after the cluster), and slice there. Java regex indices are measured in UTF-16 code units, but the matcher already determines where the cluster ends.

~~~java
// Java 9+ fragment: take at most 3 graphemes, preserving the original data.
java.util.regex.Matcher matcher =
    java.util.regex.Pattern.compile("\\X").matcher(text);
int endIndex = 0;
int count = 0;
while (count < 3 && matcher.find()) {
    endIndex = matcher.end();
    count++;
}
String firstThreeGraphemes = text.substring(0, endIndex);
~~~

The snippet above is valid only when `text` is declared as a `String` in scope. If there are fewer than 3 graphemes, the result is the entire string; if empty, the result is an empty string. For strict limits, you must decide how to handle clusters with unfamiliar code points or older Unicode versions.

## 10. Common Mistakes to Avoid

1. **“One `char` is one Unicode letter.”** `char` is a 16-bit code unit; code points outside the BMP require a surrogate pair.
2. **“`String.length()` is the number of visible characters.”** It counts code units; it does not measure bytes, code points, or graphemes.
3. **“`codePointCount` is the number of input characters.”** Combining sequences, ZWJ emojis, and flags often have multiple code points but one grapheme.
4. **“UTF-8 uses one byte per character.”** True only for ASCII; UTF-8 uses 1 to 4 bytes per Unicode scalar value.
5. **“`String` is stored as a UTF-8 `byte[]`.”** The API represents strings as UTF-16; JDK memory optimizations are an implementation detail.
6. **“`substring` slices by code point.”** Indices are UTF-16; it can easily split a surrogate pair.
7. **“Use `String.chars()` to iterate over code points.”** `chars()` yields code units; use `codePoints()` for code points.
8. **“`new String(bytes)` always reads Vietnamese correctly.”** Constructors without an explicit charset depend on the default charset; you need to know the actual encoding.
9. **“Decoding each buffer separately always works.”** A byte sequence can span two buffers; preserve decoder state.
10. **“`equals` compares visually.”** Precomposed letters and base letters + combining marks can evaluate to `equals == false`.
11. **“One grapheme = one glyph = one display cell.”** The renderer/font/shaping engine determines glyphs and width.
12. **“An unpaired surrogate is a valid Unicode character for encoding.”** It is invalid UTF-16 data in terms of Unicode scalar sequences; you must decide whether to report an error or replace it.
13. **“Upgrading the JDK alone guarantees new emojis display properly.”** Rendering also depends on fonts/UI and Unicode versions; the segmenter and renderer are two distinct steps.

## 11. Thought Exercises

1. How many UTF-8 bytes, UTF-16 `char`s, code points, and grapheme clusters does the string `"🙂"` occupy?
2. Are `"\u00E9"` and `"e\u0301"` equal under `equals`? How can they be normalized for canonical comparison?
3. Why is `"A🙂B".substring(1,2)` not a complete emoji? Use `offsetByCodePoints` instead.
4. An API accepts a nickname of at most 12 “visible characters,” while storage allows at most 48 UTF-8 bytes: how many types of limits must be checked?
5. A UTF-8 file is read in 4096-byte blocks. A 4-byte code point straddles a block boundary: what must the decoder do?
6. Why can the symbol `👩‍💻` have 3 code points yet only one grapheme, and still potentially render as multiple shapes?

**Suggested answers:**

1. **4 UTF-8 bytes, 2 UTF-16 code units, 1 code point, typically 1 grapheme**.
2. `equals` is `false` because the UTF-16 sequences differ; normalize both sides with `Normalizer.Form.NFC` before comparing.
3. The range `1..2` contains only the high surrogate. Obtain the end index using `offsetByCodePoints(1,1)` (returns 3), then call `substring(1,3)`.
4. Two independent limits: at most 12 graphemes for UX and at most 48 UTF-8 bytes for protocol/storage.
5. Retain the incomplete bytes or decoder state across the next read before resolving the code point; do not decode individual chunks with the `String` constructor.
6. The zero-width joiner connects the sequence under grapheme/emoji rules; the renderer may still lack the font or ligature support.
