# Reading Pattern Branch Coverage in Java 21+: `switch`, `when`, Records, and `null`

## 1. Goal: Measuring Execution Paths, Not Just Whether a Line Ran

In a Java 21 program using **pattern matching**, a `switch` block can contain multiple **type patterns**, **record patterns**, **`when` guards**, a `case null` branch, and a fallback branch. When running tests, two different questions need to be answered:

1. **Line coverage:** has that line of code ever been executed?
2. **Branch coverage (C1):** how many of the control branches generated by the compiler for `if`/`switch` decisions have the tests traversed?

A green line in a coverage report does not prove that every condition of a pattern has been tested. Conversely, a `case` that has run **once** does not necessarily verify both true/false outcomes of a guard, the non-matching outcome of a nested record pattern, or the fallback path.

This lesson guides you on how to read coverage accurately at the **pattern branch** level, build a test matrix for each data type, understand the colors in a JaCoCo report, and avoid confusing **business branches** with **bytecode branches** generated by the compiler.

Scope: Java **21+** (pattern matching for `switch` and record patterns are finalized), testing with JUnit 5, and measuring coverage with JaCoCo. Percentage numbers in illustrative examples must come from **actual reports**; do not guess % merely by counting `case` labels.

## 2. What Is Branch Coverage in JaCoCo?

JaCoCo is a tool that measures which Java code was executed during tests. Common counters:

| Counter | What it measures | When is it useful? |
| --- | --- | --- |
| **Instructions (C0)** | Number of bytecode instructions executed/missed | Observing execution at the instruction-block level |
| **Lines** | Source lines with debug info mapped from bytecode | Seeing which lines were skipped |
| **Branches (C1)** | Branches of `if` and `switch` decisions in bytecode | Checking true/false paths and switch selections |
| **Methods** | Methods executed | Detecting completely unexecuted methods |
| **Complexity** | Cyclomatic complexity calculated by JaCoCo from control flow | Seeing whether any decision outcomes remain untested |

Mathematically:

~~~text
Branch coverage (%) =
    100 × (number of covered branches / total measured branches)
~~~

If a report displays **14 covered / 16 total**, the ratio is **87.5%**. This is only an arithmetic example to explain how to read the column, **not** a measured ratio of the program in this lesson.

JaCoCo identifies branches from **bytecode** after compilation. A single `case` label in source code can lead to multiple internal decisions (type checks, guard checks, jumps to another branch); the number of branches JaCoCo reports **does not necessarily equal** the number of `case` lines or the number of branches you count by eye.

**Note on exceptions:** by JaCoCo's counter definition, exception handling flows **are not counted as C1 branches**. Therefore, high or 100% branch coverage does not prove that you have tested all errors, exceptions, invalid null inputs, or abnormal business cases.

## 3. How to Read Indicators in the HTML Report

In the JaCoCo HTML report, the `Missed Branches` and `Cov.` metrics at the package/class/method level indicate whether uncovered branches remain. When opening the source page (if debug information is present), JaCoCo uses **diamonds** on lines that have branches:

- **Red diamond:** no branches at that decision point were executed.
- **Yellow diamond:** **only some** of the branches at that point were executed.
- **Green diamond:** all branches JaCoCo identified at that point were executed.

Line background color is a different layer of information about instruction coverage. If the line `case String s when s.isBlank() -> ...` is highlighted green on its body, that only tells you the body code ran; you still need to check the **diamond / missed branches column** and the test case matrix to draw conclusions about the guard's entry/exit paths.

**Practical reading workflow:**

1. Open the module/package overview: identify which classes have many `Missed Branches`.
2. Navigate to the method containing the pattern-matching `switch`.
3. Open the source view and inspect the diamonds on `switch`, `when`, and related decision lines.
4. Cross-reference with **concrete test inputs** to see which branch was not taken.
5. Add tests with values that flip the condition or create a non-matching case.
6. Re-run tests + report and compare the changes. Do not "boost %" by deleting conditions or adding a `default` that hides logic bugs.

Without proper source line debug info, C1 metrics can still be computed, but mapping back to the exact source line in the UI will be limited.

## 4. Understanding Paths of Type Patterns and `when` Guards

Java 21 example:

~~~java
static String classify(Object value) {
    return switch (value) {
        case null -> "NULL";
        case String s when s.isBlank() -> "BLANK";
        case String s -> "TEXT:" + s;
        default -> "OTHER";
    };
}
~~~

Business paths that should be tested:

| Input | Selected branch | What it proves |
| --- | --- | --- |
| `null` | `case null` | Null-handling policy exists |
| `"   "` | `String s when s.isBlank()` | Type pattern matches, guard is true |
| `"Java"` | `String s` | Type pattern matches, guard is false, falls through to next String branch |
| `42` | `default` | Does not match String, handles other types |

**Common mistake:** only testing `classify("   ")`, seeing that the guarded case ran, and concluding "the String cases are fully covered". You are still missing a regular `String` case to test **guard false** and the fall-through to the subsequent `case String s`.

A guard is evaluated **only after** the pattern match succeeds; the guard does not run for inputs of a non-matching type. Therefore, you should not equate "guard false" with "type pattern false". They are two distinct reasons for not selecting a branch.

Place a more specific guarded case before a general String case. Placing `case String s` before `case String s when ...` causes a compile-time **dominance** error, not a runtime branch to test.

## 5. With `&&` and `||`, a Single Case Has Multiple Sub-Conditions

A case with a compound guard:

~~~java
case TextJob(var text) when text == null || text.isBlank() ->
    "EMPTY_TEXT";
~~~

To read coverage for this logic, you should test at minimum:

- `TextJob(null)`: `text == null` is **true**; `text.isBlank()` **does not run** due to `||` short-circuiting.
- `TextJob("   ")`: first condition is false, `isBlank()` is **true**.
- `TextJob("Java")`: both sides are false, so this guarded case is not selected; moves to the plain `case TextJob(var text)`.
- A non-`TextJob` value: type pattern does not match; the guard does not even execute.

Similarly:

~~~java
case ResizeJob(var width, var height)
        when width <= 0 || height <= 0 -> "INVALID_SIZE";
~~~

Do not only test `ResizeJob(0, 7)`. When `width <= 0` is true, `height <= 0` is skipped. Add `ResizeJob(4, 0)` to test the case where **the second operand determines the outcome**, and `ResizeJob(4, 3)` to test both being false, leading to the valid branch.

At the source level, this is the approach of **testing sub-conditions**. At the JaCoCo level, the branch counter depends on compiled bytecode and report filters; you should not claim "3 tests = 100% C1" without actually running the tool.

## 6. Nested Record Patterns: Separating Record Match, Guard, and Null Component Paths

Suppose:

~~~java
record Point(int x, int y) {}
record MoveJob(Point target) {}
~~~

A `switch` has two patterns of the same type with different levels of specificity:

~~~java
static String describe(Object value) {
    return switch (value) {
        case MoveJob(Point(var x, var y)) when x == y ->
            "DIAGONAL:" + x;
        case MoveJob(Point(var x, var y)) ->
            "MOVE:" + x + "," + y;
        case MoveJob(var target) ->
            "NO_TARGET";
        case null -> "NULL";
        default -> "OTHER";
    };
}
~~~

You should test **at least three states**:

1. `MoveJob(new Point(2, 2))`: nested record `Point` matches, guard `x == y` is true → `DIAGONAL:2`.
2. `MoveJob(new Point(2, 5))`: nested record matches, guard is false → second `Point` case → `MOVE:2,5`.
3. `MoveJob(null)`: the outer selector is **non-null**, but the `target` component is null so nested `Point(...)` does not match; `case MoveJob(var target)` is selected → `NO_TARGET`.

A subtle point: `case null` in a switch only handles a **null selector**; it does not replace null checks for a record's **components**. If tests only cover a null selector without a null component, you are still missing an important business path.

**Do not count branches by pattern name:** the three cases above traverse two levels of deconstruction and one guard; the compiler may emit type-check and null-check decisions in bytecode. JaCoCo may display filtered/aggregated branches differently from a manual mental model. Use a test matrix to evaluate **behavior**, and use JaCoCo C1 to observe **bytecode coverage**.

## 7. `sealed` + Exhaustive Switch Does Not Automatically Guarantee High Coverage

A sealed hierarchy restricts its subtypes:

~~~java
sealed interface Job permits TextJob, ResizeJob, MoveJob {}
record TextJob(String text) implements Job {}
record ResizeJob(int width, int height) implements Job {}
record MoveJob(Point target) implements Job {}
~~~

A `switch` covering all three subtype groups can be considered **exhaustive** by the compiler without needing `default`:

~~~java
static String kind(Job job) {
    return switch (job) {
        case null -> "NULL";
        case TextJob(var text) -> "TEXT";
        case ResizeJob(var w, var h) -> "RESIZE";
        case MoveJob(var target) -> "MOVE";
    };
}
~~~

**Exhaustiveness** is a compile-time conclusion: the set of cases covers all permitted selector types. **Coverage** is a runtime result after running tests: how far the control paths were actually executed. An exhaustive switch whose tests only call `kind(new TextJob("Hi"))` still has not tested the behavior of `ResizeJob`, `MoveJob`, or `null`.

Some fallback branches generated by the compiler may serve unusual binary-compatibility scenarios (such as a sealed hierarchy changing after compilation). You should not write meaningless tests just to "touch" an unusual bytecode branch or distort the domain model.

JaCoCo **0.8.11** is the official release supporting Java 21 and includes filters for part of the compiler-generated bytecode for **record patterns** and **exhaustive switch expressions**. When working with Java 21+, use a JaCoCo version that supports your running Java version and read the release notes, because compiler-generated code filters can change reported percentages/indicators across versions.

## 8. Complete Java 21+ Program with a 10-Scenario Matrix

Create the file **`PatternBranchCoverageDemo.java`**:

~~~java
public class PatternBranchCoverageDemo {
    sealed interface Job permits TextJob, ResizeJob, MoveJob {}

    record TextJob(String text) implements Job {}
    record ResizeJob(int width, int height) implements Job {}
    record Point(int x, int y) {}
    record MoveJob(Point target) implements Job {}

    static String route(Job job) {
        return switch (job) {
            case null -> "NULL";

            case TextJob(var text)
                    when text == null || text.isBlank() ->
                "EMPTY_TEXT";

            case TextJob(var text) ->
                "TEXT:" + text;

            case ResizeJob(var w, var h)
                    when w <= 0 || h <= 0 ->
                "INVALID_SIZE";

            case ResizeJob(var w, var h) ->
                "AREA:" + (w * h);

            case MoveJob(Point(var x, var y))
                    when x == y ->
                "DIAGONAL:" + x;

            case MoveJob(Point(var x, var y)) ->
                "MOVE:" + x + "," + y;

            case MoveJob(var target) ->
                "NO_TARGET";
        };
    }

    static void check(String name, String expected, Job value) {
        String actual = route(value);
        if (!expected.equals(actual)) {
            throw new AssertionError(name + ": expected "
                    + expected + " but got " + actual);
        }
        System.out.println(name + " -> " + actual);
    }

    public static void main(String[] args) {
        check("null", "NULL", null);
        check("text-null", "EMPTY_TEXT", new TextJob(null));
        check("text-blank", "EMPTY_TEXT", new TextJob("   "));
        check("text-valid", "TEXT:Java", new TextJob("Java"));
        check("size-width", "INVALID_SIZE", new ResizeJob(0, 7));
        check("size-height", "INVALID_SIZE", new ResizeJob(4, 0));
        check("size-valid", "AREA:12", new ResizeJob(4, 3));
        check("move-diagonal", "DIAGONAL:2",
                new MoveJob(new Point(2, 2)));
        check("move-regular", "MOVE:2,5",
                new MoveJob(new Point(2, 5)));
        check("move-no-target", "NO_TARGET", new MoveJob(null));
    }
}
~~~

Compile and run with **JDK 21 or later**:

~~~bash
javac --release 21 PatternBranchCoverageDemo.java
java PatternBranchCoverageDemo
~~~

Expected output:

~~~text
null -> NULL
text-null -> EMPTY_TEXT
text-blank -> EMPTY_TEXT
text-valid -> TEXT:Java
size-width -> INVALID_SIZE
size-height -> INVALID_SIZE
size-valid -> AREA:12
move-diagonal -> DIAGONAL:2
move-regular -> MOVE:2,5
move-no-target -> NO_TARGET
~~~

The program uses `main` as a **behavior verification harness**: each case confirms the exact result or throws `AssertionError` if wrong. Running the file with `java` only verifies program output; **it does not automatically generate a JaCoCo report**. To measure C1, the program must be run in a session with the JaCoCo agent/instrumentation or via a build/test pipeline configured with the agent.

## 9. Test Matrix: From Case Names to Path Evidence

| Test ID | Input | Result | Key path |
| --- | --- | --- | --- |
| T1 | `null` | `NULL` | Null selector |
| T2 | `TextJob(null)` | `EMPTY_TEXT` | Text pattern match, left side of `||` is true |
| T3 | `TextJob("   ")` | `EMPTY_TEXT` | Left side false, `isBlank()` true |
| T4 | `TextJob("Java")` | `TEXT:Java` | String guard false, takes regular branch |
| T5 | `ResizeJob(0, 7)` | `INVALID_SIZE` | `w <= 0` true, right side short-circuits |
| T6 | `ResizeJob(4, 0)` | `INVALID_SIZE` | `w <= 0` false, `h <= 0` true |
| T7 | `ResizeJob(4, 3)` | `AREA:12` | Resize guard false, takes regular branch |
| T8 | `MoveJob(Point(2,2))` | `DIAGONAL:2` | Nested Point match, guard true |
| T9 | `MoveJob(Point(2,5))` | `MOVE:2,5` | Nested Point match, guard false |
| T10 | `MoveJob(null)` | `NO_TARGET` | Nested Point fails due to null component, Move fallback |

This matrix helps explain **why** a business path has been tested, rather than merely citing an overall percentage. You can add other cases if there are additional business conditions such as negative numbers, large numbers causing `int` overflow, long usernames, locales, exceptions, or objects that mutate over time.

**Important observation:** T2 and T3 enter the same branch returning `EMPTY_TEXT`, yet they differ in short-circuit decisions. Only checking "the output of each case" will miss this distinction; this is why **case-label coverage** and **branch/condition coverage** are not the same thing.

## 10. Putting the Matrix into JUnit 5 for JaCoCo to Collect Coverage

In a Maven project, main code is typically placed at `src/main/java/PatternBranchCoverageDemo.java` and test code at `src/test/java/PatternBranchCoverageTest.java` (this minimal example uses the default package; real projects should use a consistent package).

A JUnit 5 test using `@ParameterizedTest` + `@MethodSource`:

~~~java
import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.params.provider.Arguments.arguments;

import java.util.stream.Stream;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.Arguments;
import org.junit.jupiter.params.provider.MethodSource;

class PatternBranchCoverageTest {
    @ParameterizedTest(name = "{0}")
    @MethodSource("cases")
    void routeCases(String id,
                    PatternBranchCoverageDemo.Job input,
                    String expected) {
        assertEquals(expected, PatternBranchCoverageDemo.route(input));
    }

    static Stream<Arguments> cases() {
        return Stream.of(
            arguments("null", null, "NULL"),
            arguments("text-null",
                new PatternBranchCoverageDemo.TextJob(null),
                "EMPTY_TEXT"),
            arguments("text-blank",
                new PatternBranchCoverageDemo.TextJob("   "),
                "EMPTY_TEXT"),
            arguments("text-valid",
                new PatternBranchCoverageDemo.TextJob("Java"),
                "TEXT:Java"),
            arguments("size-width",
                new PatternBranchCoverageDemo.ResizeJob(0, 7),
                "INVALID_SIZE"),
            arguments("size-height",
                new PatternBranchCoverageDemo.ResizeJob(4, 0),
                "INVALID_SIZE"),
            arguments("size-valid",
                new PatternBranchCoverageDemo.ResizeJob(4, 3),
                "AREA:12"),
            arguments("move-diagonal",
                new PatternBranchCoverageDemo.MoveJob(
                    new PatternBranchCoverageDemo.Point(2, 2)),
                "DIAGONAL:2"),
            arguments("move-regular",
                new PatternBranchCoverageDemo.MoveJob(
                    new PatternBranchCoverageDemo.Point(2, 5)),
                "MOVE:2,5"),
            arguments("move-no-target",
                new PatternBranchCoverageDemo.MoveJob(null),
                "NO_TARGET")
        );
    }
}
~~~

Each row in `cases()` becomes an independent test run with its own input and expected value. This test asserts **correct results**; the coverage tool records which bytecode paths were actually traversed. A test with assertions **does not** by itself prove completeness for unlisted input cases.

Note: the `assertEquals` statement here checks the result of the `route` method; if you want to measure production code accurately, inspect the report on **`PatternBranchCoverageDemo.route`**, rather than substituting the project-wide percentage (which also includes test/harness/utility code).

## 11. Configuring JaCoCo in Maven and Opening the Report

Example plugin configuration for a Maven project with JUnit 5, suitable for Java 21. In `pom.xml`, place the JUnit 5 dependency under `<dependencies>` and plugins under `<build><plugins>`. Minimal configuration:

~~~xml
<properties>
    <maven.compiler.release>21</maven.compiler.release>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
</properties>

<dependencies>
    <dependency>
        <groupId>org.junit.jupiter</groupId>
        <artifactId>junit-jupiter</artifactId>
        <version>5.11.4</version>
        <scope>test</scope>
    </dependency>
</dependencies>

<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-surefire-plugin</artifactId>
            <version>3.5.2</version>
        </plugin>

        <plugin>
            <groupId>org.jacoco</groupId>
            <artifactId>jacoco-maven-plugin</artifactId>
            <version>0.8.16</version>
            <executions>
                <execution>
                    <goals>
                        <goal>prepare-agent</goal>
                    </goals>
                </execution>
                <execution>
                    <id>coverage-report</id>
                    <phase>verify</phase>
                    <goals>
                        <goal>report</goal>
                    </goals>
                </execution>
            </executions>
        </plugin>
    </plugins>
</build>
~~~

This is an **inner configuration snippet** of a valid `pom.xml`, not a standalone POM file because it lacks the `<project>` root element, Maven coordinates of the project, and other declarations.

If the project already has compiler/Surefire/JUnit configuration, **merge** the necessary parts instead of adding duplicate plugins. Only when the JaCoCo agent runs in the JVM executing JUnit will you get valid coverage measurements.

Run:

~~~bash
mvn clean verify
~~~

On a successful build, the `prepare-agent` goal activates instrumentation when Surefire runs unit tests, and the `report` goal in the `verify` phase generates reports, typically at:

~~~text
target/site/jacoco/index.html
target/site/jacoco/jacoco.xml
target/site/jacoco/jacoco.csv
~~~

The path may differ if the project configures a different output directory or is multi-module. Open `index.html`, select the package containing `PatternBranchCoverageDemo`, select the class, and click the `route` method to inspect C1/diamonds.

**Do not treat any specific coverage number as a result of this lesson:** the `main` program was run to verify its output; the steps above guide **you to run JaCoCo in Maven yourself** and read the report for your own JDK/compiler/build/test suite. Bytecode filters and generated code can cause results to vary across JaCoCo/JDK versions.

## 12. When You See Yellow on a Pattern Line, How Should You Add Tests?

Suppose the report still shows partial branch coverage in the `TextJob` region:

~~~java
case TextJob(var text)
        when text == null || text.isBlank() ->
    "EMPTY_TEXT";
case TextJob(var text) ->
    "TEXT:" + text;
~~~

**Proper reasoning:**

1. Check whether tests already include both **TextJob** and **non-TextJob** inputs. If you only test String inputs in a switch on `Object`, other subtype patterns may not have appeared yet.
2. Is `TextJob(null)` present? This case tests the left side `text == null` being true.
3. Is `TextJob("  ")` present? This case makes the left side false and the right side `isBlank()` true.
4. Is `TextJob("ok")` present? This case makes the guard false and selects the regular `TextJob` case.
5. Is a **null selector** (distinct from a `TextJob` containing a null component) present?
6. Re-run the report and check which branches remain missed. Do not guess from colors alone without verifying **which branch increased**.

For `MoveJob`, if there is only a `Point(2,2)` test (guard true), add `Point(2,5)` to produce guard false; add `MoveJob(null)` to test the nested pattern failing due to a null component.

If missed branches remain after these tests, inspect the decision points in the **bytecode/report** and consider compiler-generated code or other paths. Avoid adding a "meaningless" test just to push up the percentage; every test should correspond to a plausible behavior or a technical contract worth protecting.

## 13. Common Misreadings in Coverage Reports

### 13.1. 100% C1 Does Not Mean Every Input Is Correct

Branch coverage only indicates that instrumented branches ran; it **does not** tell you whether assertions are strong enough, whether tests check wrong results, or whether data edge cases are covered.

For example, with the condition `width > 0`, trying `width = 1` and `width = 0` may traverse both branches, yet does not automatically test `width * height` overflow. To verify logic correctness, use boundary-value tests, property-based tests, or mutation testing where appropriate.

### 13.2. A C1 Report Is Not MC/DC

The four true/false combinations of a compound Boolean expression may matter under **MC/DC** testing criteria (each sub-condition independently shown to affect the decision). JaCoCo C1 **does not** directly report MC/DC percentages.

For `w <= 0 || h <= 0`, a test suite aiming to demonstrate the independent effect of both conditions will need appropriate inputs, such as `(0,3)`, `(4,0)`, and `(4,3)`; reports must still be read according to the definition of the metric you are actually using.

### 13.3. Do Not Assume One Case = One Branch

Type tests, nested record deconstruction, guards, and switch dispatch can generate multiple bytecode branches. Some compiler-generated branches may also be **filtered out of the report** by JaCoCo. Therefore, do not calculate `tested 7 cases / 8 cases = 87.5% C1` and record it as a JaCoCo figure.

**In practice, record two separate results:** the number of business cases/scenarios tested (from the matrix) and the measured C1 (from the report). They complement rather than replace each other.

### 13.4. Exception Paths Are Not in the C1 Branch Counter

JaCoCo does not count exception handling as C1 branches. Tests should still include cases that throw exceptions on invalid data, such as a record constructor forbidding null, a command handler rejecting an invalid state, or a parser encountering malformed input.

Do not try to "reach 100% C1" by omitting exception tests; **C1 and behavioral completeness are two different concepts**.

### 13.5. Source Layout and Compiler Bytecode Affect Display

Multiple decisions may sit on the same source line, for example:

~~~java
case TextJob(var t) when t == null || t.isBlank() -> "EMPTY_TEXT";
~~~

JaCoCo's mapping of bytecode to source lines may place multiple branches on one line/diamond. Splitting long conditions across readable lines can aid code review, but it does not automatically change the behavior or true number of branches of the same logic. What matters is reading the method-level metric and cross-referencing it with the test matrix.

### 13.6. JaCoCo Version and Generated Code

JaCoCo 0.8.11 officially supports Java 21 and adds filters for certain compiler-generated bytecode for record patterns and exhaustive switch expressions. Newer releases may change JDK support or filtering. Avoid mechanically comparing percentages between two builds running different tool versions or different compilers/JDKs without noting the measurement conditions.

## 14. Workflow for Reviewing Pattern Branch Coverage

A practical workflow to apply when reviewing a pull request:

1. **Read the pattern switch structure:** list each type/record pattern, guard, and general branch or `case null`.
2. **Draw a test matrix:** each input group must have examples for pattern match, guard true/false, and nested pattern non-match where meaningful.
3. **Write tests with assertions:** do not just invoke the method. On every path, verify the return value or exception contract.
4. **Run build/tests with a JDK-compatible JaCoCo:** ensure the agent runs in the JVM executing the tests.
5. **Read coverage at the method scope:** check `Missed Branches`, not just the module-wide %.
6. **Cross-reference coverage with the matrix:** identify unexecuted cases and check the assertion quality of executed ones.
7. **Classify gaps:** business path needing a test, untested guard/short-circuit, exception path needing a dedicated test, or compiler-generated/report artifact.
8. **Add meaningful tests**, re-run, and approve only when both behavior and coverage meet project criteria.

You can use a simple review table:

| Input group | Test exists? | Assertion strong enough? | Gap in branch report? | Action |
| --- | --- | --- | --- | --- |
| Null selector | Yes/No | Yes/No | Yes/No | Add null handling/test |
| Type pattern match | Yes/No | Yes/No | Yes/No | Verify expected branch output |
| Guard true | Yes/No | Yes/No | Yes/No | Add guard-true case |
| Guard false | Yes/No | Yes/No | Yes/No | Add fall-through to next case |
| Nested record component null | Yes/No | Yes/No | Yes/No | Add nested no-match case |
| Error path/exception | Yes/No | Yes/No | Not fully reflected in C1 | Assert exception separately |

## 15. Coverage Reading Exercises

**Exercise 1.** Given a method with two branches `case String s when s.isBlank()` and `case String s`, what paths do the two tests `"   "` and `"Java"` prove? Do you also need to test `null` or other types if the method accepts `Object`?

**Exercise 2.** With the guard `w <= 0 || h <= 0`, why do only testing `(0,5)` and `(3,2)` fail to prove the path where the right operand is true? Provide one additional input.

**Exercise 3.** Given `MoveJob(Point(var x,var y)) when x == y`, `MoveJob(Point(var x,var y))`, and `MoveJob(var target)`, predict which branch is selected for three values: `Point(1,1)`, `Point(1,3)`, and component `target = null`.

**Exercise 4.** A JaCoCo report for a method shows 17 covered branches and 20 total branches. What is the C1 percentage? Why should you not infer the number of `case` labels from these two numbers?

**Exercise 5.** An exhaustive switch over a sealed interface has 100% C1, but tests have not checked that the command constructor throws `IllegalArgumentException` when the quantity is negative. Is the test suite complete enough? Why or why not?

**Answers:**

- Exercise 1: `"   "` tests guard true; `"Java"` tests guard false and the regular String branch. With an `Object` selector, you also need to consider `case null` and other type branches per the method's contract.
- Exercise 2: add `(3,0)`: left side is false, right side is true. `(3,2)` tests both being false.
- Exercise 3: respectively the **DIAGONAL** branch, the **MOVE** branch, and the **NO_TARGET** branch.
- Exercise 4: **85%**; that is the number of bytecode branches counted by JaCoCo, not source `case` labels.
- Exercise 5: **not yet sufficient**; exception paths are not counted in C1 by JaCoCo's definition and still require dedicated assertions to verify the data contract.

## 16. Summary

To **read pattern branch coverage** accurately in Java 21:

- Use **JaCoCo Branches (C1)** to see how far `if`/`switch` bytecode branches have been executed, but **do not** convert `case` counts directly into C1.
- With `when`, test **both guard true and guard false**; with `&&`/`||`, examine each meaningful short-circuit path.
- With **nested record patterns**, test matching components, non-matching components, and null components; with a switch on a reference type, consider a null selector.
- With a **sealed hierarchy**, remember that **exhaustiveness is compile-time**, whereas coverage is **runtime**.
- Use **test matrix + assertions + JaCoCo report** together. A high percentage is a signal, not proof that the program is correct on all inputs.
