# Distinguishing Internal Diagnostic Information from User-Facing Messages in Java Exceptions

## 1. Learning Objectives

After this lesson, you will be able to:

- Distinguish **internal diagnostic information** (*diagnostic information*) from **public messages** (*user-facing error message*) when a Java operation fails.
- Understand why you should not return `exception.getMessage()`, stack traces, file paths, SQL statements, or infrastructure details directly to users.
- Preserve the original exception and cause chain in the appropriate diagnostic layer, while designing **stable error types, error codes, and messages** at the API boundary.
- Classify validation errors, resource-not-found errors, business errors, and system errors instead of turning everything into the same message or HTTP status.
- Design `requestId`/`correlationId` so users can report incidents without seeing technical details.
- Write structured logs, avoid leaking sensitive data, and avoid logging the same error repeatedly across multiple layers.
- Test that public messages do not expose secrets in `Throwable` while retaining enough information for engineers to investigate.

This lesson uses Java 17+ and standalone, framework-independent examples. Sections on HTTP and logging libraries are explicitly noted as illustrative at the application boundary, not a real HTTP server.

## 2. One Incident — Two Audiences for Information

Suppose an invoice-reading feature calls the storage layer. A read attempt fails with an `IOException` containing technical strings such as an internal path, server name, or connection address.

**Operations engineers** need to know the exception type, call stack, cause, which operation failed, timestamp, request ID, and involved component to find the root cause.

**Users** need to know which operation could not be performed, what they can do next, whether they should retry, and how to provide a reference code for support lookup. They typically do not need to know server addresses, Java class names, or stack traces.

| Criterion | Internal Diagnostics | User-Facing Message |
| --- | --- | --- |
| Purpose | Detect, classify, investigate, and resolve errors | Understand the issue and know the next step |
| Audience | Engineers/personnel with appropriate permissions | End users, API clients, or integrating systems |
| Content | Throwable, stack trace, cause, suppressed, request ID, component, and necessary context | Stable error code, safe description, reasonable guidance, reference code |
| Level of detail | Can be high, but must still control sensitive data | Only the necessary level of detail, without exposing implementation |
| Lifecycle | Logs, tracing, monitoring systems, incident records | UI, HTTP response, CLI, email, product notifications |
| Stability | May change across code versions, libraries, system structure | Should be stable per API contract and localizable |
| Example | `IOException` in `InvoiceRepository` causes `InvoiceLoadException` | "Unable to load the invoice right now. Please try again later. Reference ID: RQ-1042." |

**Core principle:** do not send raw diagnostic records to users. **Translate errors at the trust boundary**: keep appropriate data for engineers, while exposing a safe and understandable error contract.

~~~text
Client sends request
        |
        v
Application / API boundary
        |
        v
Repository calls infrastructure
        |
        +--> IOException("host=db-private, path=/var/...")  [internal details]
                    |
                    v
          InvoiceLoadException(message, cause)
                    |
          +---------+---------------------------------+
          |                                           |
          v                                           v
  Internal diagnostics                          Public error
  type, cause, stack trace                      code + safe message
  requestId, operation                          + requestId
  controlled logs/traces                        no infrastructure leaked
~~~

## 3. What Does a Throwable Contain and Why Not Expose It Raw?

A `Throwable` in Java has multiple sources of information:

- `getClass().getName()`: the exception class name, often reflecting the library or technology in use.
- `getMessage()`: detailed text that may be generated by the I/O layer, JDBC, HTTP library, framework, or developer.
- `getCause()`: the underlying cause exception, which may itself have its own cause.
- `getStackTrace()`: the call path with class names, methods, source files, and line numbers when available.
- `getSuppressed()`: additional exceptions retained by certain mechanisms, especially `try-with-resources`.
- `printStackTrace()`: a representation of the Throwable, its causes, and suppressed exceptions for diagnostics.

All of this information **is not inherently safe to output to clients**. For example, `SQLException` may contain SQL details and table names; `IOException` may contain server paths; SDK exceptions may carry endpoints, response bodies, or internal resource IDs. An exception message is not text that has been vetted for security and clarity.

### Three Common Public Exposure Mistakes

**Mistake 1 — returning the exception message directly:**

~~~java
return error.getMessage();
~~~

This is **illustrative code** in a method returning a string. `getMessage()` can be `null`, cryptic, vary across versions, or contain internal information.

**Mistake 2 — returning the raw stack trace:**

~~~java
StringWriter writer = new StringWriter();
error.printStackTrace(new PrintWriter(writer));
return writer.toString();
~~~

This is **illustrative code** assuming `error` is a `Throwable` and `java.io` classes are imported. It puts diagnostic data into the public response. A stack trace can expose package names, classes, methods, paths, and sensitive information contained in the message/cause.

**Mistake 3 — hiding everything behind a meaningless phrase:** the user only receives "Error" without knowing which request was rejected, whether the operation can be retried, or whether input needs to be adjusted. Security **does not require removing all useful information**; you need to expose safe, contract-compliant, actionable information.

## 4. Separating Three Layers: Technical Cause, API-Meaningful Error, and Public Message

Distinguish between:

1. **Technical cause:** for example `IOException`, `SQLException`, or a connection failure to a dependent service.
2. **Abstraction-layer exception:** for example `InvoiceLoadException`, `PaymentRejectedException`, or `DocumentNotFoundException`.
3. **User/client representation:** for example `{code, message, requestId}` with an appropriate HTTP status.

The repository/service boundary can translate a technical exception into an application-layer exception:

~~~java
try {
    return storage.read(invoiceId);
} catch (IOException original) {
    throw new InvoiceLoadException(
            "Không thể đọc hóa đơn " + invoiceId, original);
}
~~~

This is an **illustrative snippet**, assuming the corresponding variables/classes exist and the `InvoiceLoadException(String, Throwable)` constructor is declared.

The service layer still preserves **the original `IOException` object as the cause** for investigation. However, `InvoiceLoadException.getMessage()` is **not necessarily** the public message: it may contain an internal ID or context intended only for logs.

At the HTTP/UI boundary, an error mapper decides the error code and public message based on the classified error type. The communication layer should **not** use the raw exception class name to build messages, because class names are implementation details.

**Preserve the cause for tracing; filter public information for contract and security.** These are two complementary responsibilities, not conflicting ones.

## 5. Designing an Error Contract for Users

A public error data structure might include:

~~~json
{
  "code": "DOCUMENT_UNAVAILABLE",
  "message": "Không thể tải tài liệu lúc này. Vui lòng thử lại sau.",
  "requestId": "RQ-1042"
}
~~~

This is an **illustrative JSON sample**, not a response from a running HTTP server in this lesson.

Fields should have a clear contract:

| Field | Meaning | Notes |
| --- | --- | --- |
| `code` | Stable, meaningful error code for clients | Do not tie to class/driver names that may change |
| `message` | Short, clear, and safe wording | Do not copy stack traces or technical messages |
| `requestId` | Reference code for looking up logs/traces | Do not embed secrets, tokens, or sensitive identifiers; control length/format |
| `details` (contract-dependent) | Structured info to help fix input | Include only fields permitted for public disclosure |
| HTTP status (if HTTP API) | Cause category at the protocol layer | Must accurately reflect the error and business contract |

The `message` can be displayed in the user's language, while `code` remains stable so clients can make decisions without comparing natural-language strings.

Validation error example:

~~~json
{
  "code": "INVALID_INPUT",
  "message": "Vui lòng nhập địa chỉ email hợp lệ.",
  "details": [
    {"field": "email", "reason": "invalid_format"}
  ],
  "requestId": "RQ-1043"
}
~~~

This is also only an **illustrative JSON example**. Returning a field name like `email` may be reasonable if it is the user's own input; never automatically echo back secret values they just entered.

### What Content Is Helpful to Users?

- **Identify the action:** "Unable to load document", "Unable to save changes" instead of "System error".
- **Actionable state:** "Please check the email format" for validation errors.
- **Reasonable retry guidance:** for transient errors, you may suggest retrying later, but avoid advising unconditional retries for operations with side effects.
- **Reference code:** helps support look up the issue without requiring users to send stack traces, tokens, or private data.
- **Do not over-assert:** a timeout does not prove a transaction was not executed; messages must be cautious, especially for payments or order creation.

Public messages should be stable in meaning, while wording, translations, and presentation may evolve with the product. Clients should not parse `message` to drive control logic; use `code` and structured fields instead.

## 6. Standalone Java 17 Example: Preserving Cause Without Leaking Internal Details

Create the file **SafeErrorBoundaryDemo.java** with the full content below. The program does not call a real network or database; it simulates an I/O error containing infrastructure information to verify that the public message does not leak that information.

~~~java
import java.io.IOException;

public class SafeErrorBoundaryDemo {

    static final class DocumentLoadException extends RuntimeException {
        DocumentLoadException(String message, Throwable cause) {
            super(message, cause);
        }
    }

    record PublicError(String code, String message, String requestId) {
    }

    static String loadDocument(String id) {
        try {
            throw new IOException(
                    "host=db-private.local; path=/srv/private; password=secret");
        } catch (IOException original) {
            throw new DocumentLoadException(
                    "Không đọc được tài liệu " + id, original);
        }
    }

    static PublicError toPublicError(
            DocumentLoadException error, String requestId) {
        return new PublicError(
                "DOCUMENT_UNAVAILABLE",
                "Không thể tải tài liệu lúc này. Vui lòng thử lại sau.",
                requestId);
    }

    public static void main(String[] args) {
        String requestId = "RQ-1042";

        try {
            loadDocument("invoice-7");
        } catch (DocumentLoadException error) {
            Throwable cause = error.getCause();

            // Sample diagnostic info, intentionally not printing the sensitive message.
            System.out.println("INTERNAL type: "
                    + error.getClass().getSimpleName());
            System.out.println("INTERNAL cause type: "
                    + cause.getClass().getSimpleName());
            System.out.println("INTERNAL cause retained: "
                    + (cause instanceof IOException));

            // This structure is the data intended for the client.
            PublicError response = toPublicError(error, requestId);

            System.out.println("PUBLIC code: " + response.code());
            System.out.println("PUBLIC message: " + response.message());
            System.out.println("PUBLIC requestId: "
                    + response.requestId());

            boolean leaksSecret =
                    response.message().contains("db-private")
                    || response.message().contains("password")
                    || response.message().contains("/srv/private");

            System.out.println("PUBLIC leaks internals: " + leaksSecret);
        }
    }
}
~~~

Compile and run with Java 17 or newer:

~~~bash
javac -encoding UTF-8 SafeErrorBoundaryDemo.java
java SafeErrorBoundaryDemo
~~~

**Expected, deterministic stdout:**

~~~text
INTERNAL type: DocumentLoadException
INTERNAL cause type: IOException
INTERNAL cause retained: true
PUBLIC code: DOCUMENT_UNAVAILABLE
PUBLIC message: Không thể tải tài liệu lúc này. Vui lòng thử lại sau.
PUBLIC requestId: RQ-1042
PUBLIC leaks internals: false
~~~

### Key Takeaways from the Example

1. The `IOException` is simulated with a message containing a literal hostname, path, and password. No real credentials are used; these strings only test disclosure risk.
2. The data-reading layer creates `DocumentLoadException` and passes `original` as the cause via `super(message, cause)`. Error details remain preserved internally.
3. The communication layer builds `PublicError` from the error type and a valid `requestId`. It does not call `error.getMessage()` or `cause.getMessage()` to construct the response.
4. The `INTERNAL` lines demonstrate **selected safe information** printed for classroom purposes. In a real system, diagnostics are typically sent to an access-controlled logger/tracing system; the example intentionally avoids printing the full sensitive cause to the console.
5. The line `PUBLIC leaks internals: false` confirms the public message does not contain the markers injected into the original exception. In real projects, tests should cover **the entire public payload**, not just the message field.
6. `PublicError` is a Java 17 record, using accessors `code()`, `message()`, and `requestId()`. The program runs standalone without framework dependencies.

**Limitation:** the `contains` check in the example is an illustrative test and does not replace security review of output content. A system with many types of secrets, identifiers, and payloads needs proper filtering mechanisms, contract reviews, and testing.

## 7. Error Classification: Not Every Error Has the Same Public Message

For APIs, especially HTTP APIs, distinguish between errors caused by input, resource state, business rules, and infrastructure. Illustrative guide:

| Scenario | Application-Layer Error Type | Usually Appropriate HTTP Status | Example Safe Message |
| --- | --- | --- | --- |
| Malformed request | Validation exception | 400 Bad Request | "Invalid input data." |
| Invalid authentication | Authentication failure | 401 Unauthorized | "Please sign in again." |
| Insufficient permissions | Authorization failure | 403 Forbidden | "You do not have permission to perform this action." |
| Resource not found per contract | Not-found exception | 404 Not Found | "Document not found." |
| State or business conflict | Conflict/domain exception | 409 Conflict, if contract fits | "Data has changed. Please reload." |
| Infrastructure temporarily unavailable | Service unavailable | 503 Service Unavailable if accurate | "Service is temporarily unavailable." |
| Unexpected server error | Internal error | 500 Internal Server Error | "Unable to process the request right now." |

This table is only a **guideline**; choosing a specific HTTP status code must be based on semantics and the API contract. Do not turn every exception into 500 just to keep code shorter, nor assign 503 to every `IOException` without verifying that it is truly "temporarily unavailable".

### Do Not Expose Resource Existence When Unauthorized

A request to access a document may result in 403 or 404 depending on security policy. Some systems intentionally avoid disclosing the existence of resources that the user is not authorized to view. Therefore, mapping an exception to a message like "Document X exists, but you cannot view it" can create an information disclosure vulnerability.

If an ID is invalid, the message should include only parts of the input permitted for display. Do not include raw tokens, session IDs, or another user's data in the error response.

### Do Not Claim an Operation Did Not Execute Just Because of a Timeout

For example, a payment API times out: the backend may have already executed the transaction, while the result has not reached the client. A message like "Payment failed, click submit again now" can lead to duplicate operations. In this case, provide a cautious status, a reference code, and a way to check the result/idempotency per the contract.

## 8. Standalone Java 17 Example: Mapper Selecting Messages by Error Type

The following **ErrorClassificationDemo.java** file illustrates classifying four scenarios and producing different messages. It does **not** start an HTTP server; the `status` field only simulates the status code needed at an HTTP adapter.

~~~java
import java.io.IOException;

public class ErrorClassificationDemo {

    static final class DocumentMissingException extends RuntimeException {
        DocumentMissingException(String message) {
            super(message);
        }
    }

    static final class BackendUnavailableException extends RuntimeException {
        BackendUnavailableException(String message, Throwable cause) {
            super(message, cause);
        }
    }

    record ApiError(int status, String code, String message) {
    }

    static void execute(String scenario) {
        switch (scenario) {
            case "invalid" ->
                    throw new IllegalArgumentException("internal field x invalid");
            case "missing" ->
                    throw new DocumentMissingException("path=/srv/private/42");
            case "down" ->
                    throw new BackendUnavailableException(
                            "Storage backend failed",
                            new IOException("host=db-private.local"));
            case "unexpected" ->
                    throw new IllegalStateException("internal state corrupted");
            default -> {
                // Success: no exception thrown.
            }
        }
    }

    static ApiError mapToPublic(RuntimeException error) {
        if (error instanceof IllegalArgumentException) {
            return new ApiError(
                    400, "INVALID_INPUT", "Dữ liệu nhập không hợp lệ.");
        }
        if (error instanceof DocumentMissingException) {
            return new ApiError(
                    404, "NOT_FOUND", "Không tìm thấy tài liệu.");
        }
        if (error instanceof BackendUnavailableException) {
            return new ApiError(
                    503, "SERVICE_UNAVAILABLE",
                    "Dịch vụ tạm thời không khả dụng.");
        }
        return new ApiError(
                500, "INTERNAL_ERROR",
                "Không thể xử lý yêu cầu lúc này.");
    }

    public static void main(String[] args) {
        String[] scenarios = {
                "invalid", "missing", "down", "unexpected", "ok"
        };

        for (String scenario : scenarios) {
            try {
                execute(scenario);
                System.out.println(scenario + " -> SUCCESS");
            } catch (RuntimeException error) {
                ApiError response = mapToPublic(error);
                System.out.println(scenario + " -> "
                        + response.status() + " "
                        + response.code() + " | "
                        + response.message());
            }
        }
    }
}
~~~

Compile and run:

~~~bash
javac -encoding UTF-8 ErrorClassificationDemo.java
java ErrorClassificationDemo
~~~

**Expected, deterministic stdout:**

~~~text
invalid -> 400 INVALID_INPUT | Dữ liệu nhập không hợp lệ.
missing -> 404 NOT_FOUND | Không tìm thấy tài liệu.
down -> 503 SERVICE_UNAVAILABLE | Dịch vụ tạm thời không khả dụng.
unexpected -> 500 INTERNAL_ERROR | Không thể xử lý yêu cầu lúc này.
ok -> SUCCESS
~~~

The example illustrates the logic:

- `IllegalArgumentException` for the chosen request is mapped to an input error. In a real system, you should not catch **every** `IllegalArgumentException` globally and blame the client by default: the error could also come from a server bug. The adapter must distinguish intentional input-validation exceptions from unexpected exceptions.
- `DocumentMissingException` expresses the resource-not-found policy. Exposing 404 is only valid when it does not leak restricted-access information.
- `BackendUnavailableException` retains the `IOException` cause inside the application, while the response does not reveal the hostname.
- Unexpected `IllegalStateException` falls into the generic server error branch with a safe message instead of returning `internal state corrupted`.
- The `ok` branch throws no exception and is handled as success. Do not create an "error envelope" for an operation that succeeded.

In production, define more expressive exception types rather than relying on overly generic system exceptions when mapping public codes.

## 9. Internal Logging: Enough Diagnostics Does Not Mean Logging Everything

At the diagnostic layer, you need to know the operation, outcome, context, and exception. A useful log event typically contains:

| Field | Example | Reason |
| --- | --- | --- |
| Timestamp | Incident time per logging system | Correlate events over time |
| Severity | `WARN`, `ERROR` | Classify impact level per policy |
| Event name | `document.load.failed` | Query/count by a stable event type |
| Request/correlation ID | `RQ-1042` | Link logs with requests/tracing |
| Component | `DocumentService` | Identify the originating component |
| Operation | `loadDocument` | Identify the operation being performed |
| Safe resource reference | Controlled/hashed ID if permitted | Scope the incident without leaking info |
| Exception type | `DocumentLoadException` | Group root causes |
| Cause chain, stack trace | Per permissions and security policy | Diagnose location, nature, and propagation path |

**Internal logs are not inherently an absolutely safe place.** Logs may be exported to third-party services, retained long-term, replicated across environments, or accessed by many people. No policy permits freely logging passwords, access tokens, auth cookies, private keys, payment data, or personal data just because a log is labeled "internal".

### Java Built-in Logging

The JDK includes `java.util.logging.Logger`. In a class with a `logger` variable and an exception `error`, you can use:

~~~java
logger.log(
        java.util.logging.Level.SEVERE,
        "document.load.failed requestId=" + requestId,
        error);
~~~

This is an **illustrative code snippet**, assuming `logger` is already created, `requestId` is a safe value, and `error` is a `Throwable`. The `Logger.log(Level, String, Throwable)` overload records the exception so the logger/handler can format details when appropriate. It is more useful than concatenating only `error.getMessage()`, because the cause and stack trace are not actively discarded.

However, the logger/formatter may print the messages of the entire cause chain, which **may contain secrets**. Therefore, "passing Throwable to the logger" must go hand in hand with data security design, storage configuration, access control, masking, and testing. If third-party exceptions might contain secrets, a reliable filtering/redaction policy is needed before outputting data, rather than relying solely on changing the public message.

### With SLF4J or Other Logging Frameworks

A common logging library may provide a similar overload:

~~~java
logger.error("document.load.failed requestId={}", requestId, error);
~~~

This snippet is **illustrative code using the SLF4J API**, not standalone Java SE; it requires specific logging dependencies and configuration. The goal is to show how to pass the exception object to the logger instead of embedding the stack trace directly into the client message. With any logger, verify the exact overload/library version in use and how the backend formats `Throwable`.

The `requestId` field should live in structured context if the tooling supports it, rather than encoding all data into a single hard-to-query string. However, structured logging does not replace the requirement to exclude sensitive data.

## 10. Correlation ID and Two-Way Linking

A **Request ID** is a reference code for a single request. A **Correlation ID** can span multiple related operations or services. A **Trace ID** is typically tied to a distributed tracing system. Naming varies by infrastructure; do not assume they are always the same concept.

Simple flow:

~~~text
Client -> API receives request RQ-1042
              |
              +--> Service: loadDocument
              |          |
              |          +--> Adapter: IOException
              |
              +--> Log event: document.load.failed
              |       requestId = RQ-1042
              |       internal Throwable / safe context
              |
              +--> Response:
                      code = DOCUMENT_UNAVAILABLE
                      message = Không thể tải tài liệu lúc này.
                      requestId = RQ-1042
~~~

Users can report "Reference ID RQ-1042" to support; engineers with appropriate permissions can look up logs using the same code.

### Key Principles

- Generate or normalize the ID at a trust boundary. Do not blindly trust every ID header sent by clients and write it raw into logs.
- Validate the format and length of the ID to prevent log injection, arbitrary data, or oversized values.
- The ID should not contain secrets, access tokens, emails, or personally identifiable information unless necessary.
- Propagate the ID across components via an explicit mechanism. Every log entry must receive the correct ID of the current request.
- Maintain appropriate access control and log retention periods. A public ID is not an authorization mechanism to look up internal data.

When using thread pools or async callbacks, do not assume every `ThreadLocal` automatically follows the task. If the library supports MDC, propagate the context as prescribed by the framework, clear the context in `finally` when returning the thread to the pool, and avoid mixing up another user's request ID. Java SE does not provide a unified MDC mechanism equivalent to all logging frameworks.

## 11. Where to Log to Avoid Repeating the Same Error?

An error can pass through multiple layers:

~~~text
Repository -> Service -> Controller/API mapper -> HTTP response
~~~

If the repository, service, and controller all call `logger.error(..., error)` and then rethrow the same exception, a single failed request can produce three identical stack traces. Monitoring systems may miscount this as three incidents, polluting diagnostics and increasing log costs.

A pragmatic principle:

- **Layer that knows the cause and can recover:** may handle it or log a recovery event if it has observability value.
- **Layer that only adds API meaning:** translate the exception with cause; it does not necessarily need to log the full stack trace there.
- **Boundary responsible for reporting the final failure:** log once per policy with the request ID, error type, context, and appropriate Throwable.
- **External monitoring systems:** may receive metrics/traces per policy without duplicating every stack trace by default.

There is no rule that every application may only log once in all circumstances. If layers add **independent, valuable information**, multiple events at appropriate levels can be reasonable. However, avoid repeating identical logs with no new context.

**Note:** validation errors that users can fix themselves usually should not be logged at the same severity as a database outage. Severity levels should reflect operational impact and expectations, not merely the presence of an exception.

## 12. Preserving the Cause Chain and Suppressed Exceptions for Diagnostics

When translating a technical error into a more meaningful exception:

~~~java
public final class InvoiceLoadException extends RuntimeException {
    public InvoiceLoadException(String message, Throwable cause) {
        super(message, cause);
    }
}
~~~

This is a **standalone Java class** if saved in `InvoiceLoadException.java` and used in the same-named context. The two-argument constructor preserves `getCause()` as the original Throwable object.

Distinguish:

- `getMessage()` on the wrapper: context of the current abstraction layer.
- `getCause()`: the exception that caused the failure, including its own type, message, and stack trace.
- `getSuppressed()`: secondary exceptions retained when needed, such as resource-closing errors in `try-with-resources`.
- `printStackTrace()`: a display format of the cause chain for controlled debugging.

If you only copy `original.getMessage()` and create a new exception without a cause, you can lose critical stack traces and suppressed exceptions. If you just append class/method names into the public message to "have enough info", you leak implementation details without creating a structured cause chain.

**Do not reconstruct an exception from the original message** when you can pass the original Throwable directly. Tests can use `assertSame(original, translated.getCause())` to verify the exact same object is retained.

Even so, **preserving the cause does not grant permission to expose the cause to all audiences**. At the public boundary, error codes and messages must still be mapped separately.

## 13. Sensitive Data Risks in Logs and Error Responses

Data can leak through multiple channels:

1. **Source exception message:** libraries may embed SQL, URLs, filenames, response bodies, or headers containing tokens.
2. **Application-written wrapper message:** developers concatenate entire request payloads or PII-containing inputs into errors.
3. **Structured log fields:** fields like `requestBody`, `email`, `sessionId`, or `Authorization` may be logged accidentally.
4. **Stack trace and cause chain:** may include sensitive messages at any level.
5. **Monitoring/tracing metadata:** tags or baggage may contain sensitive identifiers if attached carelessly.
6. **User-facing notifications:** screens, emails, CLIs, support chatbots, or APIs may expose internal details to unauthorized parties.
7. **Log injection:** untrusted data with newlines, control characters, or long payloads can corrupt log formatting if unhandled.

### Risk Mitigation Measures

- **Do not put secrets into exception messages in the first place** when you control the throwing layer.
- Log only fields genuinely needed for diagnostics, applying consistent exclusion/masking rules for PII, credentials, and sensitive content.
- Review and configure loggers/formatters, export pipelines, tracing agents, and retention policies.
- Enforce access control on log/tracing systems and maintain data-incident response procedures.
- Reject or sanitize untrusted strings used in logs/IDs, avoiding reliance on ad-hoc string trimming in every catch block.
- Write tests with fake canary secrets: inject a marker into the cause and assert the public payload does not contain the marker.
- For public messages, prefer **approved codes and templates** over "bad-word filtering" on unstructured technical messages.

**No fixed keyword list can prove a string is completely free of sensitive data.** The most reliable approach is an architecture that only permits public data selected by contract, rather than outputting technical data and trying to strip out dangerous strings.

## 14. Expected Errors and Unexpected Errors Should Have Different Disclosure Levels

### Validation: State What Needs Fixing, Without Over-Disclosing

For example, a product quantity input form. The message "Quantity must be greater than 0" is helpful and usually safe. There is no need to print the class name `NumberFormatException`, the `Integer.parseInt` location, or the full request JSON. If the input is a password, OTP, or token, never echo the raw entered value.

### Business Rules: Communicate State Accurately

For example, an expired reservation or insufficient balance. These can be expected business states; users need to know how to proceed, and engineers may not need an ERROR stack trace for every case if the system treats it as a normal rejection.

However, if a business rule involves another user's data, consider visibility permissions. Do not disclose "another account owns this resource" if that is restricted information.

### Infrastructure Incidents: Safe Messages, No Speculation

Timeouts, DNS, JDBC, storage, or service dependency errors can prevent an operation from completing as expected. Public messages should generally only state that the operation cannot be processed right now and provide a reference code. If an error is truly proven transient, you may advise retrying per policy.

Do not imply that retrying is always safe for payments, sending emails, creating orders, or operations with side effects. When the final outcome is unknown, ask users to check transaction status using an ID/idempotency key or follow the defined product flow.

### Programming Bugs: Do Not Blame the User

An unexpected `NullPointerException` or `IllegalStateException` on the server is usually not a user input error. Public mapping should not say "Your input is invalid" just because of an exception name. Report a safe system error while keeping full diagnostic details within secure bounds.

## 15. Handling Exceptions at the API Boundary

An error-handling boundary might look like:

~~~text
try {
    result = service.perform(request);
    return successResponse(result);
} catch (KnownValidationException e) {
    return safeValidationResponse(e);
} catch (KnownBusinessException e) {
    return safeBusinessResponse(e);
} catch (RuntimeException e) {
    logUnexpectedFailureWithContext(e);
    return safeInternalErrorResponse();
}
~~~

This is **illustrative pseudocode**, not standalone Java. In a real project, functions must be defined and output data must be authorized. Handle exceptions within specific scopes; do not catch `Throwable` and automatically turn critical `Error`s into a fake success response.

If the application uses Spring, Jakarta REST, Servlet, or another framework, the final error handler is typically an exception mapper, controller advice, filter, or appropriate middleware layer. Specific hook names and mechanisms depend on the framework; the principle of **separating public messages from internal diagnostics** remains unchanged.

### When Should Technical Errors Not Be Returned to Callers?

If a public API is intended for developers, you **may** return certain technical details designed into the contract (validation codes, invalid fields, parameters permitted for disclosure). What to avoid is accidentally returning unstable or sensitive implementation details such as raw SQL, token contents, internal addresses, stack traces, and exception classes.

In other words, a "public API for developers" does not mean an "unrestricted debug endpoint". Debug information must go through separate access controls and security policies.

## 16. Testing: Public Payload, Cause, and Logging Policy

A good test suite verifies both sides **independently**.

| Case | What Must Be Verified |
| --- | --- |
| I/O error with cause containing sensitive string | Public code/message does not contain that string |
| Error translated at service layer | `translated.getCause()` is the same original Throwable |
| Validation with known error type | Client receives the correct code and message |
| Backend unavailable error | Client receives a safe message, not host/path |
| Unexpected error | Client receives a generic system error, not a stack trace |
| Request ID | Same valid code appears in response and allowed diagnostic events |
| Normal success | Does not produce errors or unnecessary ERROR logs |
| Concurrent requests | Context does not mix up request IDs across threads |
| Exception with suppressed/cause chain | Diagnostic system can trace per policy |
| Repeated validation errors | Severity/metrics do not trigger unnecessary incident alerts |

### JUnit 5 — Testing No Information Leakage from Original Message

The following snippet is **illustrative only in a test project with JUnit 5** and the `SafeErrorBoundaryDemo` class accessible in scope:

~~~java
IOException original = new IOException("password=canary-secret");
SafeErrorBoundaryDemo.DocumentLoadException internal =
        new SafeErrorBoundaryDemo.DocumentLoadException(
                "Lỗi tầng lưu trữ", original);

SafeErrorBoundaryDemo.PublicError response =
        SafeErrorBoundaryDemo.toPublicError(internal, "RQ-TEST");

assertSame(original, internal.getCause());
assertEquals("DOCUMENT_UNAVAILABLE", response.code());
assertFalse(response.message().contains("canary-secret"));
assertFalse(response.message().contains("password="));
assertEquals("RQ-TEST", response.requestId());
~~~

This snippet requires importing `java.io.IOException` and static assertions from `org.junit.jupiter.api.Assertions`. It is not a standalone Java program. A thorough production test should serialize the entire API response and assert that **the full payload** contains no markers; it should also test validation fields and error messages generated across multiple adapters.

### Logging Tests Should Not Require Fixed Stack Trace Lines

Filenames, line numbers, class locations, and logger formats can change across JDKs, dependency versions, or environments. Test contract-level elements such as event name, request ID, error type, cause identity, and redaction policy. If you want to test logs in a structured way, use an appropriate appender/test handler instead of parsing fragile console strings.

A test checking "no password in the public response" **does not guarantee internal logs are also safe**. Separately test logging/export for fake secrets, access controls, and sensitive fields per security requirements.

## 17. Common Mistakes and How to Fix Them

1. **Returning `e.getMessage()` directly:** replace with a public error mapper using contract-defined codes/messages.
2. **Returning `e.toString()`:** it typically contains the class name and technical message, not user-facing text.
3. **Returning the raw stack trace:** keep it for authorized diagnostics; responses should contain only permitted information.
4. **Lumping everything into "Unknown error":** classify expected errors so users know how to proceed.
5. **Returning 500 for all errors or 200 with `success=false`:** for HTTP APIs, choose status codes by contract semantics instead of hiding classification.
6. **Treating every `IllegalArgumentException` as a user error:** distinguish intentional validation errors from server bugs.
7. **Dropping the cause when translating errors:** use a constructor accepting `Throwable cause` to preserve the stack trace/root cause.
8. **Logging only `e.getMessage()`:** this can lose the cause chain; design exception logging per security policy.
9. **Logging every Throwable and request body raw:** this can leak secrets or PII into third-party logs.
10. **Logging stack traces at every layer:** causes duplicate logs, noisy alerts, and higher costs.
11. **Putting tokens or emails into `requestId`:** creates a public identifier containing sensitive data.
12. **Trusting unvalidated request IDs:** can cause log injection, correlation mix-ups, or oversized data.
13. **Not clearing MDC/ThreadLocal in thread pools:** can mix context across requests.
14. **Driving client logic by comparing localized message strings:** rely on structured codes instead.
15. **Advising retry on every error:** can cause duplicate actions for operations with side effects.
16. **Reporting "does not exist" when policy forbids disclosure:** design access control and public statuses properly.
17. **Equating public safety with hiding everything:** messages must be both safe **and** sufficiently helpful.
18. **Assuming "internal logs" need no security:** logs still require data controls, retention, access control, and export governance.
19. **Catching every `Throwable` to return 500:** can mask critical `Error`s and corrupt the application lifecycle.
20. **Testing only the message without testing the full response body:** secrets can leak from another field.

## 18. Pre-Release Review Checklist

Before deploying error-handling features to production, verify:

- Are internal exceptions/causes clearly separated from the public error DTO?
- Does each expected error type have a stable code and appropriate message?
- Are there actionable user fields instead of an overly generic error message when disclosure is permitted?
- Does the HTTP status or API status accurately reflect the cause/contract?
- Is there a safe `requestId` field to help support correlate logs?
- Does the error response avoid leaking stack traces, technical exception types, SQL, paths, hostnames, tokens, or sensitive bodies?
- Do logs contain enough information to distinguish errors and trace causes while still meeting security policies?
- Do you avoid logging the same exception multiple times when layers only rethrow?
- When using thread pools/async, is correlation context propagated and cleared properly?
- Are retry messages appropriate for idempotency and the fact that a transaction might not have failed?
- Have tests injected fake secrets into cause/message and verified **the entire public response**?
- Are expected errors, unexpected system errors, and success paths each tested separately?

**Conclusion:** A Java exception contains rich information for **engineers to diagnose root causes**, but not all of that information is appropriate or safe for **users**. Good design preserves the cause and necessary context in controlled internal layers; at the communication boundary, it translates errors into stable codes, clear and safe messages, and traceable reference IDs. Both channels must support each other without sacrificing security or investigability.
