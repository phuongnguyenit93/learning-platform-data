# Testing message, context properties, and cause when appropriate — Java Exception Testing

## 1. Learning Objectives

After this lesson, you will be able to:

- Define the **error contract** that a Java method must provide when it fails.
- Write tests that verify **exception type**, **message**, **context properties**, and **cause** without over-coupling to implementation details.
- Use JUnit 5: <code>assertThrows</code>, <code>assertThrowsExactly</code>, <code>assertEquals</code>, <code>assertSame</code>, <code>assertInstanceOf</code>, <code>assertAll</code>, and <code>assertDoesNotThrow</code> for their intended purposes.
- Choose the appropriate message comparison: exact match, checking a stable substring, error code, or structured data.
- Prove that exception translation across layers **preserves the exact cause object** and does not lose diagnostic context.
- Test exceptions from validation, business logic, I/O, timeout, or asynchronous operations according to each API's contract.
- Avoid tests that merely check "any exception was thrown", catch too broadly, compare literal stack traces, or rely on unguaranteed JVM messages.
- Separate properties that **must remain stable for callers** from internal diagnostic information that should not be locked down by unit tests.

This lesson belongs to **Java Core — exception**, section **Testing**. The first programs use standalone Java 17+. The JUnit 5 examples require the JUnit Jupiter library in the project; this lesson does not assume JUnit is built into the JDK.

## 2. Exception testing is contract testing, not just checking "an error occurred"

Suppose the method <code>loadDocument("DOC-42")</code> reads a document from a repository. If the lower layer throws an <code>IOException</code>, the service may translate it into an application-layer exception. The caller does not necessarily need to know the concrete I/O class, but may depend on these elements:

1. **A meaningful error type:** <code>DocumentLoadException</code>.
2. **A published message:** for example, “Không thể tải tài liệu”.
3. **Context properties:** <code>documentId="DOC-42"</code>, <code>operation="LOAD"</code>.
4. **Cause:** preserving the original <code>IOException</code> for diagnostics.
5. **No fake success result:** a failed operation must be represented accurately according to the contract.
6. **No internal information leakage** when turning the exception into a user-facing message.

A test that only writes:

~~~java
assertThrows(RuntimeException.class,
        () -> service.loadDocument("DOC-42"));
~~~

is an **illustrative JUnit 5 snippet**. It is very weak if the service is required to throw a specific domain exception type, because <code>NullPointerException</code>, <code>IllegalStateException</code>, or many other bugs are also subclasses of <code>RuntimeException</code>. The test could turn "green" even when the service fails in the wrong way.

A more meaningful test must be tied to **what the caller has the right to expect**. Not every property of a Throwable needs to be asserted. Choose the parts that belong to the public contract or serve a specific diagnostic requirement.

## 3. Categories of information that can be tested

| Aspect | Observable API | When to test |
| --- | --- | --- |
| Exception type | <code>getClass()</code>, <code>instanceof</code>, JUnit <code>assertThrows</code> | When the caller branches handling based on error type |
| Message | <code>getMessage()</code> | When the message or part of its content is an actual contract |
| Context properties | Application-defined getters/record accessors | When the caller needs an error code, task ID, operation, or retry status |
| Direct cause | <code>getCause()</code> | When upper layers need to preserve the original error or classify the root reason |
| Cause chain | Looping through <code>getCause()</code> | When multiple wrapper layers are valid and a deeper cause must be found |
| Suppressed exceptions | <code>getSuppressed()</code> | For cleanup, try-with-resources, or secondary errors that must be retained |
| Stack trace | <code>getStackTrace()</code> | Only when trace recording behavior is a specific diagnostic requirement |
| Public error code | <code>code()</code>, <code>getErrorCode()</code>, or error DTO | When clients should not parse free-form messages |
| Async error boundary | <code>Future.get()</code>, <code>CompletableFuture.join()</code> | When errors are wrapped according to the async contract |

### What should not be asserted by default

- Source line numbers in a stack trace.
- Specific frame order or frame count.
- Messages of NPE, SQLException, or IOException generated by the JVM/driver/library if they are not part of your contract.
- Full log text rendered by a framework across all versions.
- A message containing file paths, hostnames, tokens, or internal details that are not published as stable.

**Question to ask before writing an assert:** “If the implementation changes while caller behavior remains correct, should this assertion still PASS?”

## 4. assertThrows: catching the exception and returning the object itself

JUnit 5 provides:

~~~java
DocumentLoadException thrown =
        assertThrows(DocumentLoadException.class,
                () -> service.loadDocument("DOC-42"));
~~~

This is an **illustrative JUnit 5 snippet**, assuming <code>service</code> and the <code>DocumentLoadException</code> class exist. If the executable does not throw a matching exception, the assertion fails. If it throws the exact requested type or an acceptable subtype, the assertion succeeds and returns the caught Throwable object.

You can then inspect it further:

~~~java
assertEquals("Không thể tải tài liệu", thrown.getMessage());
assertEquals("DOC-42", thrown.documentId());
assertEquals("LOAD", thrown.operation());
assertNotNull(thrown.getCause());
~~~

These assertions should only be used when the service publishes those exact properties as in the example. If the message is allowed to vary by locale, do not force the test to match a single Vietnamese sentence. If the caller needs a stable error code, check the error code first.

### Why keep the thrown variable?

Writing it standalone:

~~~java
assertThrows(DocumentLoadException.class,
        () -> service.loadDocument("DOC-42"));
~~~

only checks the exception type. Storing the result in <code>thrown</code> lets you inspect the message, fields, and cause **from the same execution**, avoiding calling the operation multiple times.

Especially with I/O, transactions, or operations with side effects, do not call the service two or three times just to check each property individually. Repeated calls may return different states, incur costs, or create unintended side effects.

## 5. How assertThrows and assertThrowsExactly differ

In JUnit Jupiter:

- <code>assertThrows(Expected.class, executable)</code> accepts <code>Expected</code> **or its subclasses**.
- <code>assertThrowsExactly(Expected.class, executable)</code> requires **that exact class**, rejecting subclasses. This API is available in modern JUnit Jupiter versions, including JUnit 5.8+.

Illustrative example:

~~~java
class ApplicationException extends RuntimeException {
}

class DocumentException extends ApplicationException {
}

assertThrows(ApplicationException.class,
        () -> { throw new DocumentException(); });

assertThrowsExactly(DocumentException.class,
        () -> { throw new DocumentException(); });
~~~

This is an **illustrative JUnit 5 snippet**. Both assertions above will succeed.

If the contract allows the system to extend errors via subclasses, <code>assertThrowsExactly</code> can make the test overly rigid. If the API truly requires an exact non-hierarchical error type, the exact check is appropriate.

### Distinguishing broad catching from intentional checking

<code>assertThrows(RuntimeException.class, ...)</code> may be valid for a test that only requires any runtime error. However, for specific validation, check <code>IllegalArgumentException</code> or a published domain class.

A common poor choice:

~~~java
assertThrows(Exception.class, () -> parseAndSave(input));
~~~

This is **illustrative code**. This test can PASS due to an unrelated bug such as an I/O failure, rather than the intended validation error. Narrow the exception type and also inspect its semantic properties.

## 6. Testing messages: when to use exact comparison?

For a message **owned by the application, stable, and published as part of the contract**, you can use:

~~~java
assertEquals("Số lượng phải lớn hơn 0", thrown.getMessage());
~~~

Advantage: the test catches unintended changes to wording, diacritics, or caller-facing phrasing. Disadvantage: minor punctuation or translation changes will also fail the test.

Exact comparison is appropriate when:

- The message is an intentional part of the contract.
- The system does not apply localization at the layer under test.
- Users/callers must receive this exact template.
- The test protects a specific text requirement, such as an approved accessibility/UX notice.

### When to check only the stable part?

If the message is allowed to include additional details or IDs managed by the application, a softer assertion can make sense:

~~~java
assertTrue(thrown.getMessage().contains("Không thể tải tài liệu"));
~~~

This is an **illustrative JUnit 5 snippet**. However, <code>contains</code> can be too weak or produce false PASSes—for example, a long message containing that phrase while expressing the wrong state. You can check <code>startsWith</code> or an approved pattern, but only when it is genuinely part of the contract.

If the message can be null, calling <code>getMessage().contains(...)</code> will itself throw a <code>NullPointerException</code>, producing a confusing test failure. You can use:

~~~java
String message = thrown.getMessage();
assertNotNull(message);
assertTrue(message.contains("Không thể tải tài liệu"));
~~~

These lines are **illustrative JUnit code**. It produces a clearer failure when the exception has no message.

### When should you not test the text?

Messages from <code>NumberFormatException</code> thrown by <code>Integer.parseInt()</code>, <code>NullPointerException</code> from the runtime, or <code>IOException</code> from the filesystem are not text that the application fully controls. If the test needs to identify the error type, assert the class; if there is an application-defined wrapper, check the wrapper's message or a stable error code rather than locking onto underlying library details.

**Rule:** test values that the caller has the right to rely on, not incidental details of an implementation.

## 7. Context properties: should be data, not just embedded in a string

An application-layer exception class might look like:

~~~java
final class DocumentLoadException extends RuntimeException {
    private final String documentId;
    private final String operation;

    DocumentLoadException(
            String message, String documentId,
            String operation, Throwable cause) {
        super(message, cause);
        this.documentId = documentId;
        this.operation = operation;
    }

    String documentId() {
        return documentId;
    }

    String operation() {
        return operation;
    }
}
~~~

This is an **illustrative class definition**, usable as a standalone or nested class if visibility is adjusted. The two fields provide structured data to the calling layer.

Test:

~~~java
assertEquals("DOC-42", error.documentId());
assertEquals("LOAD", error.operation());
~~~

Better than parsing the message:

~~~java
assertTrue(error.getMessage().contains("DOC-42"));
~~~

Containing the ID in the message does not prove that the object exposes the context property the caller needs. When the ID is kept in a field, the application can change or translate the message without breaking the data contract.

### Which properties should be context?

Keep only properties needed for API semantics or diagnostics:

- Document/order ID if permitted for use in the current layer.
- Operation code such as <code>LOAD</code>, <code>SAVE</code>, <code>DELETE</code>.
- Fixed domain error code such as <code>DOCUMENT_UNAVAILABLE</code>.
- A <code>retryable</code> flag if a genuinely valid retry policy has been defined.
- A correlation/request ID reference that is safe per the contract.
- Object state or resource type if it does not violate access permissions.

Do not store passwords, access tokens, or full sensitive payloads in exception context just for testing convenience. Context may be logged or propagated across multiple layers.

### Messages are not always public messages

An internal exception may have a diagnostic message containing internal IDs. Responses sent to users should usually be built from **stable error codes and safe templates**, rather than sending <code>Throwable.getMessage()</code> directly. Therefore, service tests and error mapper tests may verify two **different** contracts.

## 8. Checking cause: type, content, or identity?

When a layer translates <code>IOException</code> into <code>DocumentLoadException</code>, a key question is “is the original exception preserved?”.

~~~java
try {
    return repository.read(documentId);
} catch (IOException original) {
    throw new DocumentLoadException(
            "Không thể tải tài liệu",
            documentId,
            "LOAD",
            original);
}
~~~

This is an **illustrative code snippet inside a suitable method**. The constructor receives <code>original</code> as the cause, so:

~~~java
assertSame(original, translated.getCause());
~~~

is the strongest check if the test can hold **the exact original instance**. <code>assertSame</code> verifies that both references point to the same object. This is stronger than:

~~~java
assertEquals(original.getClass(),
        translated.getCause().getClass());
~~~

because two different exceptions can share the same class.

### Comparing the three levels

| Assertion | What it proves | Limitation |
| --- | --- | --- |
| <code>assertNotNull(error.getCause())</code> | A cause exists | Does not know whether it is the right cause |
| <code>assertInstanceOf(IOException.class, error.getCause())</code> | Cause is of the expected type | Does not prove it is the exact source instance |
| <code>assertSame(original, error.getCause())</code> | Direct cause is the exact **same object** | Appropriate only if the contract requires preserving the exact cause |

In JUnit 5, <code>assertEquals</code> on exceptions is usually not equivalent to <code>assertSame</code>; standard Throwables do not define equality across stack trace, type, message, and cause. When you want to check identity, use <code>assertSame</code> for clarity.

### Why not just compare the cause's message?

A wrapper might copy the original message while losing the stack trace:

~~~java
throw new DocumentLoadException(
        original.getMessage(),
        documentId,
        "LOAD",
        null);
~~~

This is **illustrative code intentionally unsuitable when cause preservation is required**. The caller sees a similar message, but <code>getCause() == null</code> and the trail back to the initial exception is lost. An identity test with <code>assertSame</code> catches that bug.

However, not every API needs the **direct cause** to be the exact same object. Some layers intentionally add intermediate wrappers. When the contract only requires that “the cause chain preserves the original error”, the test should walk the chain and check at the appropriate level rather than rigidly demanding a single layer.

## 9. Standalone Java 17 example: message, context, and cause contract

This program uses a simple self-check mechanism so it can run with only the JDK. It does not replace JUnit in a project, but clearly demonstrates checking the same exception across multiple properties.

Save the file **ExceptionContractDemo.java**:

~~~java
import java.io.IOException;

public class ExceptionContractDemo {

    static final class DocumentLoadException extends RuntimeException {
        private final String documentId;
        private final String operation;

        DocumentLoadException(
                String message, String documentId,
                String operation, Throwable cause) {
            super(message, cause);
            this.documentId = documentId;
            this.operation = operation;
        }

        String documentId() {
            return documentId;
        }

        String operation() {
            return operation;
        }
    }

    static final class FakeRepository {
        final IOException original =
                new IOException("simulated storage failure");

        String read(String documentId) throws IOException {
            throw original;
        }
    }

    static String load(String documentId, FakeRepository repository) {
        if (documentId == null || documentId.isBlank()) {
            throw new IllegalArgumentException("documentId không được trống");
        }

        try {
            return repository.read(documentId);
        } catch (IOException original) {
            throw new DocumentLoadException(
                    "Không thể tải tài liệu",
                    documentId,
                    "LOAD",
                    original);
        }
    }

    static void require(boolean condition) {
        if (!condition) {
            throw new AssertionError("Contract failed");
        }
    }

    public static void main(String[] args) {
        FakeRepository repository = new FakeRepository();

        try {
            load("DOC-42", repository);
            throw new AssertionError("Expected DocumentLoadException");
        } catch (DocumentLoadException failure) {
            require("Không thể tải tài liệu".equals(
                    failure.getMessage()));
            require("DOC-42".equals(failure.documentId()));
            require("LOAD".equals(failure.operation()));
            require(failure.getCause() == repository.original);

            System.out.println("Type: "
                    + failure.getClass().getSimpleName());
            System.out.println("Message: " + failure.getMessage());
            System.out.println("Context documentId: "
                    + failure.documentId());
            System.out.println("Context operation: "
                    + failure.operation());
            System.out.println("Same original cause: "
                    + (failure.getCause() == repository.original));
            System.out.println("Contract: PASS");
        }
    }
}
~~~

Compile and run with Java 17+:

~~~bash
javac -encoding UTF-8 ExceptionContractDemo.java
java ExceptionContractDemo
~~~

**Exact stdout:**

~~~text
Type: DocumentLoadException
Message: Không thể tải tài liệu
Context documentId: DOC-42
Context operation: LOAD
Same original cause: true
Contract: PASS
~~~

### Explanation

1. <code>FakeRepository.original</code> holds an <code>IOException</code> with a stable identity for the test to compare against.
2. <code>load</code> has a guard for an invalid ID, then catches the exact <code>IOException</code> at the repository layer.
3. The wrapper preserves a meaningful service-layer message, two context fields, and **the exact cause object**.
4. The <code>catch (DocumentLoadException)</code> block runs only for the matching error type. The <code>require</code> conditions make the program fail with an <code>AssertionError</code> if any property is incorrect.
5. All output is printed after the checks PASS, so stdout is deterministic and does not depend on timing or thread pools.
6. The original <code>IOException</code> message is retained for diagnostics, but the example stdout does not expose raw technical exception details to the user.

In a real project, use a test framework that clearly reports which assertion failed, rather than writing a generic <code>require</code> helper as shown in this demo.

## 10. JUnit 5: a complete test for an exception with context

The example below uses JUnit Jupiter. It shows how to check four groups of properties in **a single invocation** and how to test the validation branch as well.

Save the file **DocumentServiceTest.java** in the project's test source set where JUnit Jupiter is configured:

~~~java
import static org.junit.jupiter.api.Assertions.*;

import java.io.IOException;
import org.junit.jupiter.api.Test;

class DocumentServiceTest {

    static final class DocumentLoadException extends RuntimeException {
        private final String documentId;
        private final String operation;

        DocumentLoadException(
                String message,
                String documentId,
                String operation,
                Throwable cause) {
            super(message, cause);
            this.documentId = documentId;
            this.operation = operation;
        }

        String documentId() {
            return documentId;
        }

        String operation() {
            return operation;
        }
    }

    static final class FakeRepository {
        final IOException original =
                new IOException("disk temporarily unavailable");

        String read(String documentId) throws IOException {
            throw original;
        }
    }

    static String loadDocument(String documentId, FakeRepository repository) {
        if (documentId == null || documentId.isBlank()) {
            throw new IllegalArgumentException(
                    "documentId không được trống");
        }

        try {
            return repository.read(documentId);
        } catch (IOException original) {
            throw new DocumentLoadException(
                    "Không thể tải tài liệu",
                    documentId,
                    "LOAD",
                    original);
        }
    }

    @Test
    void translationKeepsMessageContextAndOriginalCause() {
        FakeRepository repository = new FakeRepository();

        DocumentLoadException error = assertThrowsExactly(
                DocumentLoadException.class,
                () -> loadDocument("DOC-7", repository));

        assertAll("DocumentLoadException contract",
                () -> assertEquals(
                        "Không thể tải tài liệu", error.getMessage()),
                () -> assertEquals("DOC-7", error.documentId()),
                () -> assertEquals("LOAD", error.operation()),
                () -> assertSame(repository.original, error.getCause()));
    }

    @Test
    void blankDocumentIdReportsValidationError() {
        FakeRepository repository = new FakeRepository();

        IllegalArgumentException error = assertThrowsExactly(
                IllegalArgumentException.class,
                () -> loadDocument("   ", repository));

        assertEquals("documentId không được trống", error.getMessage());
        assertNull(error.getCause());
    }
}
~~~

### Prerequisites to run

- Java 17+ to compile the example code.
- The **JUnit Jupiter** (JUnit 5) library declared for the test source set.
- A JUnit Jupiter test runner enabled via Maven Surefire, Gradle Test, or a compatible IDE.
- <code>assertThrowsExactly</code> requires a JUnit Jupiter version that includes this API (JUnit 5.8+).

If the project uses Maven with a standard layout, the example can be placed at:

~~~text
src/test/java/DocumentServiceTest.java
~~~

This is a **suggested project structure path**, not a file created in the current task. Run it with your project's build tool once the appropriate dependencies are configured, for example:

~~~bash
mvn test
~~~

This is a **command for a Maven project with tests configured**, not a command you can run directly with a bare JDK. The expected outcome is **2 tests passed**, with no fixed business stdout because JUnit runners format reports differently by tool and version.

### Why use assertAll?

<code>assertAll</code> groups multiple independent assertions for the same error. When several properties fail at once, the framework can report all assertion failures together, giving you the full picture instead of stopping at the first failure. However, every expression must be prepared safely: if you dereference an unexpected null before entering <code>assertAll</code>, the test can still fail in a hard-to-read way.

<code>assertThrowsExactly</code> is chosen in this example because the lesson intentionally defines a concrete wrapper type. If the contract accepts subclasses, using <code>assertThrows</code> is more flexible.

## 11. Testing the non-throwing path: assertDoesNotThrow

Exception testing also needs to prove that **the valid path does not raise an error**. For example, a validation method:

~~~java
static void validateQuantity(int quantity) {
    if (quantity <= 0) {
        throw new IllegalArgumentException(
                "quantity must be positive");
    }
}
~~~

This is an **illustrative Java snippet** inside a suitable class.

JUnit:

~~~java
assertDoesNotThrow(() -> validateQuantity(1));

IllegalArgumentException error = assertThrowsExactly(
        IllegalArgumentException.class,
        () -> validateQuantity(0));

assertEquals("quantity must be positive", error.getMessage());
~~~

This is **illustrative JUnit 5 code**. Combining both cases prevents an implementation that always throws or always returns normally from slipping through a test suite that only covers one branch.

For a method that returns a value:

~~~java
String result = assertDoesNotThrow(() -> normalize("  a  "));
assertEquals("a", result);
~~~

This is **illustrative code**, assuming <code>normalize</code> is designed to return a trimmed string. If an operation is genuinely permitted to throw certain controlled exceptions that the caller still accepts, do not mechanically force the test to use <code>assertDoesNotThrow</code>.

## 12. Cause chain: which level is the contract?

A multi-layered system may produce:

~~~text
HttpAdapterException
   |
   +-- ServiceException
          |
          +-- IOException
~~~

If the adapter's contract only requires **preserving the original cause**, do not write tests that hardcode two fixed wrapper levels when adding or removing an intermediate wrapper does not affect the caller.

Two ways to check:

### 12.1. Checking the direct cause

~~~java
assertSame(original, serviceError.getCause());
~~~

Appropriate when the constructor/service commits to keeping the exact <code>original</code> at the first cause level.

### 12.2. Checking that a cause is present in the chain

If additional valid wrappers exist:

~~~java
Throwable current = outer;
boolean containsOriginal = false;

while (current != null) {
    if (current == original) {
        containsOriginal = true;
        break;
    }
    current = current.getCause();
}

assertTrue(containsOriginal);
~~~

This is an **illustrative JUnit 5 snippet** with <code>outer</code> and <code>original</code> created beforehand, assuming the chain has no cycles. In a general-purpose diagnostic utility, you can add an identity set to guard against malformed Throwable cycles. Do not replace the identity check with a message comparison because multiple exceptions can share the same text.

### Do not unwrap indiscriminately

An exception may have a valid cause that does not represent the failure the calling layer should handle directly. For example, a domain layer intentionally translates <code>SQLException</code> into <code>DocumentLoadException</code>. If test or application code simply hunts for the root cause to decide business behavior, it may bypass the policy established at the domain layer.

**Test both the semantics of the wrapper class and cause preservation when appropriate**, not just the root cause.

## 13. Standalone Java 17 example: cause chain and suppressed exceptions

Save the file **CauseChainDemo.java**:

~~~java
import java.io.IOException;

public class CauseChainDemo {

    static void require(boolean condition) {
        if (!condition) {
            throw new AssertionError("Unexpected exception structure");
        }
    }

    public static void main(String[] args) {
        IOException root = new IOException("read timeout");
        IllegalStateException middle =
                new IllegalStateException("storage failure", root);
        RuntimeException outer =
                new RuntimeException("request failure", middle);
        IOException cleanup = new IOException("cleanup failure");
        outer.addSuppressed(cleanup);

        Throwable directCause = outer.getCause();
        Throwable deepestCause = directCause.getCause();
        Throwable[] suppressed = outer.getSuppressed();

        require(directCause == middle);
        require(deepestCause == root);
        require(suppressed.length == 1);
        require(suppressed[0] == cleanup);

        System.out.println("Outer: "
                + outer.getClass().getSimpleName());
        System.out.println("Direct cause: "
                + directCause.getClass().getSimpleName());
        System.out.println("Root cause: "
                + deepestCause.getClass().getSimpleName());
        System.out.println("Root identity: " + (deepestCause == root));
        System.out.println("Suppressed count: " + suppressed.length);
        System.out.println("Suppressed identity: "
                + (suppressed[0] == cleanup));
        System.out.println("Checks: PASS");
    }
}
~~~

Compile and run:

~~~bash
javac -encoding UTF-8 CauseChainDemo.java
java CauseChainDemo
~~~

**Exact stdout:**

~~~text
Outer: RuntimeException
Direct cause: IllegalStateException
Root cause: IOException
Root identity: true
Suppressed count: 1
Suppressed identity: true
Checks: PASS
~~~

### What this example proves

- <code>outer.getCause()</code> points to **the same instance** <code>middle</code>.
- <code>middle.getCause()</code> points to **the same instance** <code>root</code>.
- <code>getSuppressed()</code> holds the secondary exception <code>cleanup</code>, distinct from the cause chain.
- Reading cause and suppressed exceptions does not require printing the full stack trace.
- These two error-recording channels have different semantics: cause describes why the failure happened, while suppressed stores additional exceptions per the resource-handling mechanism.

Do not force all exceptions into a cause chain in an arbitrary order just to satisfy a test; doing so distorts semantics. For multiple independent errors, you may need an aggregate result type, a list of errors, or a dedicated policy.

## 14. Checked exceptions also need contract testing

It is not only <code>RuntimeException</code> that is tested with <code>assertThrows</code>. A Java API might declare:

~~~java
String read(Path path) throws IOException {
    return Files.readString(path);
}
~~~

This is an **illustrative snippet**, requiring imports for <code>Path</code>, <code>Files</code>, and <code>IOException</code>. When testing under deterministic and appropriate I/O conditions, you can write:

~~~java
IOException error = assertThrows(IOException.class,
        () -> reader.read(path));
~~~

This is **illustrative JUnit 5 code**. However, a test should not assume a specific I/O error based solely on the real filesystem state of a CI runner. The same file might be deleted, have its permissions changed, or be created by another process.

If the goal is to test **how the service translates IOException**, use a fake repository that throws **the exact pre-created instance**, as in sections 9–10. That keeps the test:

- Independent of the operating system.
- Free of special permissions or hardcoded paths.
- Free of opening real files and causing race conditions.
- Clear for cause identity comparisons.
- Easy to reproduce on CI and developer machines.

For filesystem integration tests, you can use a temporary directory and clean up resources properly. However, that is an I/O integration test, not the smallest unit needed to verify a service's exception contract.

## 15. Testing user-facing messages vs. testing internal messages

An infrastructure error might contain a message like:

~~~text
connection refused to internal-db:5432
~~~

The service layer preserves this cause for diagnostics, but the API should not expose that raw message to users. Instead, the error mapper may return:

~~~json
{
  "code": "DOCUMENT_UNAVAILABLE",
  "message": "Không thể tải tài liệu lúc này. Vui lòng thử lại sau.",
  "requestId": "RQ-1042"
}
~~~

This is **illustrative JSON**, not a response from a server started in this lesson.

The two test suites should be separated:

1. **Service test:** correct wrapper type, internal message if part of the contract, context and cause preserved.
2. **API/error mapper test:** correct error code, status, and public message; no hostname, token, SQL, internal paths, or stack trace.

A security test can inject a fake secret into the source <code>IOException</code> and then verify that **the entire response payload** does not contain that secret. Do not check only the message field if other fields could also leak data.

### Do not rely on exact text for every error

A localized public message may differ by locale. In that case, test code/status/semantics and only assert specific text in tests dedicated to that locale/template. Do not try to use a single exact Vietnamese assertion across all locales.

**Internal diagnosability and public safety are two independent properties.** A system can preserve causes very well while leaking technical errors in responses; conversely, responses may be safe while the service drops causes. Test both if both are required.

## 16. Do not assert literal stack traces unnecessarily

An anti-pattern:

~~~java
assertEquals(
        "at com.example.Service.load(Service.java:42)",
        error.getStackTrace()[0].toString());
~~~

This is **illustrative JUnit code intentionally discouraged**. Line numbers, file names, frame ordering, and compiler/JIT/test runner differences can break the test even when the system is correct.

If the requirement is “the exception has a stack trace to aid diagnostics”, you can check at a reasonable level:

~~~java
assertTrue(error.getStackTrace().length > 0);
~~~

Even this assertion has limits: some exceptions are designed with <code>writableStackTrace=false</code>, or the runtime applies JVM-dependent optimizations. If the system intentionally uses lightweight exceptions, the test must reflect that policy rather than imposing a blanket condition on every Throwable.

If the main goal is preserving the original cause, <code>assertSame(original, error.getCause())</code> usually aligns much better with the contract than comparing frame counts.

## 17. Testing messages with dynamic parameters

A message may include an ID, quantity, or operation name. Do not merely check “some non-null string exists”:

~~~java
assertNotNull(error.getMessage());
~~~

This assertion does not prove the message has sufficient context. However, embedding IDs directly into the message is not always the best choice either.

**If the API has structured fields**, prefer:

~~~java
assertEquals("DOC-7", error.documentId());
assertEquals("LOAD", error.operation());
~~~

And check only the stable part of the message:

~~~java
assertTrue(error.getMessage().startsWith("Không thể tải tài liệu"));
~~~

If the exact message is published as part of the contract:

~~~java
assertEquals("Không thể tải tài liệu DOC-7",
        error.getMessage());
~~~

These are all **illustrative JUnit 5 snippets**; they represent **different hypothetical contracts**, not three assertions that must all be placed on a single implementation.

### Messages can be null

Per the <code>Throwable</code> contract, a message can be null. Some APIs intentionally construct exceptions with no message but with their own error code and context. Therefore, tests must know when a non-null message is required and when null is acceptable.

Do not blindly call <code>getMessage().contains(...)</code> on an unverified assumption; if needed, assert <code>assertNotNull</code> first so the test itself does not throw a confusing NPE.

## 18. assertInstanceOf, class equality, and abstraction level

JUnit Jupiter provides <code>assertInstanceOf</code> to assert that an object belongs to a class/interface; some versions offer an overload that returns the cast value for further use.

Example:

~~~java
Throwable cause = error.getCause();
IOException io = assertInstanceOf(IOException.class, cause);
assertNotNull(io.getMessage());
~~~

This is **illustrative JUnit 5 code**. If the contract requires the cause to be an I/O exception type or a subtype of it, this assertion is appropriate.

If the exact class is required:

~~~java
assertEquals(IOException.class, cause.getClass());
~~~

Be careful, though: an implementation that replaces <code>IOException</code> with a more meaningful subclass may still satisfy the contract, whereas an exact class comparison will fail the test. For cause identity tests, prefer <code>assertSame(original, cause)</code> when the source instance is under your control.

**Do not turn tests into a mirror of internal structure.** Tests should protect the user-facing contract of that layer, not force wrapper/driver classes to keep a specific concrete class if that is not published.

## 19. Exceptions in Future and CompletableFuture

When a task runs asynchronously, the exception may not surface directly at the initiation or submit call.

With <code>Future.get()</code>, task failures are typically reported via <code>ExecutionException</code>. With <code>CompletableFuture.join()</code>, normal completion failures are reported via <code>CompletionException</code>; cancellation may throw <code>CancellationException</code> directly according to each future's semantics.

Illustrative JUnit example:

~~~java
IOException original = new IOException("network error");
CompletableFuture<String> failed = new CompletableFuture<>();
failed.completeExceptionally(original);

CompletionException wrapper =
        assertThrows(CompletionException.class, failed::join);

assertSame(original, wrapper.getCause());
~~~

This is **illustrative JUnit 5 code**; you must import the corresponding <code>java.io</code> and <code>java.util.concurrent</code> classes. When calling <code>get()</code> instead of <code>join()</code>, the exception type reported to the caller differs:

~~~java
ExecutionException wrapper =
        assertThrows(ExecutionException.class, failed::get);

assertSame(original, wrapper.getCause());
~~~

This is also **illustrative JUnit 5 code** using the failed future from the previous snippet. The goal is to test the wrapper class according to the API used to observe the result.

Do not simply write <code>assertThrows(IOException.class, failed::join)</code> and conclude the code is broken when the assertion fails: the contract of <code>join()</code> does not promise to throw the original checked exception directly. You must understand how the API wraps errors.

For a complex pipeline, a cause may pass through multiple <code>CompletionException</code> or stage wrappers. Tests should identify **which error level is meaningful to the caller**, rather than automatically unwrapping every layer and ignoring domain error codes.

## 20. Cases where exceptions can be replaced or masked

### 20.1. finally throws a new exception

~~~java
try {
    operation();
} finally {
    cleanupThatThrows();
}
~~~

This is **illustrative code**, assuming both calls exist. If <code>operation()</code> already threw an error and <code>cleanupThatThrows()</code> also throws, the error from <code>finally</code> can replace the original error. A test that only checks the final type does not guarantee the primary cause was preserved.

If you need to preserve multiple errors when closing resources, prefer <code>try-with-resources</code> for suitable <code>AutoCloseable</code> resources. Closing errors can be recorded in the primary error's <code>getSuppressed()</code>. When the contract requires it, test suppressed exceptions instead of only the cause.

### 20.2. Wrapper created with a message without passing the cause

~~~java
catch (IOException original) {
    throw new DocumentLoadException(
            original.getMessage(),
            documentId,
            "LOAD",
            null);
}
~~~

This is **illustrative code intentionally wrong when the contract requires preserving the cause**. A message test might still PASS, but <code>assertSame(original, thrown.getCause())</code> will catch the defect.

### 20.3. Catching too broadly

~~~java
catch (RuntimeException any) {
    throw new DocumentLoadException(
            "Không thể tải tài liệu",
            documentId,
            "LOAD",
            any);
}
~~~

This is **illustrative code**. If a <code>NullPointerException</code> bug in the service is translated into a document load error, a test that only checks for <code>DocumentLoadException</code> will miss the misclassification. Design tests for cases that **should not be translated** or narrow the catch to the appropriate infrastructure type.

## 21. Testing negative cases: what should not happen?

Good testing not only confirms an expected error branch but also protects branches from misclassification.

| Scenario | What to protect |
| --- | --- |
| Blank input | Validation exception has the right type/message; repository is not called |
| Valid input, repository succeeds | Returns data; no exception thrown |
| Repository throws IOException | Domain wrapper preserves context and cause |
| Repository throws a RuntimeException bug outside the translation contract | Not disguised as a validation or “not found” error |
| Cause message contains a secret | Public response does not leak the secret |
| Domain message is localized | Error code stays stable; test localized messages at the right layer |
| Async task fails | Wrapper from <code>join/get</code> has the expected cause |
| Try-with-resources fails on both operation and close | Primary and suppressed errors match the contract |

### Verifying a dependency is not called on the validation path

If you use a fake repository with a counter:

~~~java
final class CountingRepository {
    int calls;

    String read(String id) {
        calls++;
        return "ok";
    }
}
~~~

This is an **illustrative class**, not a complete test. When the ID is invalid, the test can verify that the validation method throws the expected exception and <code>calls == 0</code>. This catches implementations that perform I/O before validating.

However, do not attach a “dependency not called” assertion if the design does not publish that ordering or if side effects are unaffected; test conditions that reflect real requirements.

## 22. Testing message and cause in a multi-attribute test

A readable pattern is grouping assertions by responsibility:

~~~java
DocumentLoadException error = assertThrowsExactly(
        DocumentLoadException.class,
        () -> service.loadDocument("DOC-7"));

assertAll("public exception contract",
        () -> assertEquals("DOCUMENT_UNAVAILABLE", error.code()),
        () -> assertEquals("DOC-7", error.documentId()),
        () -> assertEquals("LOAD", error.operation()));

assertAll("diagnostic cause",
        () -> assertNotNull(error.getCause()),
        () -> assertSame(original, error.getCause()));
~~~

This is an **illustrative snippet** with a service, an exception type having <code>code()</code>, and an <code>original</code> variable created during test setup. The <code>assertAll</code> groups clearly separate caller-facing data from diagnostic data.

**Avoid overly broad tests:** do not cram dozens of independent scenarios into a single test where it becomes hard to tell which step failed. One test can have multiple assertions when all of them describe **a single failure and a single contract**.

If the public message is mapped at the controller layer, do not force the service exception to also contain the exact public message. Test at the proper boundary.

## 23. Which test level should verify which property?

### Service-layer unit tests

Suitable for:

- Exception type thrown by the service.
- Published service-layer message or error code.
- Context: document ID, operation, resource type.
- Cause: identity of the source exception.
- Valid input paths, validation, and error mapping.

### Repository-layer integration tests

Suitable for:

- How JDBC, filesystem, or HTTP client libraries report errors.
- Infrastructure error translation at the adapter per contract.
- Proper resource closing on both success and failure paths.

Avoid integration tests that depend on unstable hostnames or OS-specific paths unless necessary.

### API contract tests

Suitable for:

- Status and error code received by the client.
- Public message for the selected locale.
- Context fields permitted in the output.
- No leakage of secrets, raw causes, stack traces, or infrastructure details.
- Correlation/request ID per contract.

### End-to-end tests

Suitable for proving that a failure workflow displays an appropriate message and recovery path, but you should not replace all unit tests with expensive e2e tests just to assert cause identity.

**A property should be tested at the layer that owns that contract.** Testing the same technical message at every layer creates brittle tests and risks leaking internal details.

## 24. Choosing assertions for variable messages

A practical guide:

| Message | Suggested assertion | Reason |
| --- | --- | --- |
| Fixed public application template | <code>assertEquals(expected, message)</code> | Protects published wording |
| Message with a stable semantic segment | <code>assertNotNull</code> + <code>contains</code>/<code>startsWith</code> | Ignores secondary non-contract context |
| Message varying by locale | Test with a specific locale or error code | Avoids depending on the machine's default locale |
| Message generated by JDK/driver | Check type/cause; avoid exact text | Avoids coupling to implementation |
| Message containing internal secrets | Test that public payload **does not** contain the secret; internal logs follow policy | Security |
| Message contains an ID but API has a <code>documentId</code> field | Assert the field; check only the stable part of the message | Avoids parsing data from text |
| Message is allowed to be null | Test the nullable contract; do not blindly call <code>contains</code> | Reflects actual API behavior |

Do not use overly broad regexes like <code>.*error.*</code> just to “test that there is text”. It can PASS when the content is no longer useful. Likewise, do not write regexes matching every punctuation mark of a library error if the contract does not promise them.

## 25. Common mistakes in exception tests

1. **Writing only <code>assertThrows(Exception.class, ...)</code>:** can PASS due to an unrelated error.
2. **Calling the service multiple times to check each property:** the operation may have side effects or different outcomes.
3. **Choosing <code>assertThrowsExactly</code> when subclasses are valid:** makes the test overly rigid toward the exception hierarchy.
4. **Choosing an overly broad <code>assertThrows</code> when an exact type is required:** may miss wrong type translation.
5. **Asserting exact JDK/driver messages:** fragile across runtime or library upgrades.
6. **Checking only that the message contains an ID:** fails to protect structured context fields.
7. **Using <code>assertEquals</code> when trying to prove the same Throwable instance:** use <code>assertSame</code> instead.
8. **Checking only that cause is non-null:** may retain the wrong exception.
9. **Checking only the root cause while ignoring the domain wrapper type:** may miss incorrect API mapping.
10. **Snapshotting raw stack traces:** line numbers and frames are unstable.
11. **Testing I/O errors with real files when a fake suffices:** creates slow, OS-dependent tests.
12. **Using <code>catch (Exception)</code> in a test and asserting <code>true</code>:** can accidentally catch errors thrown by assertions or the test itself.
13. **Not testing the success branch:** an implementation that always throws can still PASS a negative-only test suite.
14. **Not testing the public response:** the service may preserve cause properly while the adapter leaks secrets.
15. **Treating <code>getCause()</code> as never null:** the test may throw NPE instead of a clear assertion failure.
16. **Not distinguishing <code>Future.get</code> and <code>CompletableFuture.join</code>:** assertions expect the wrong wrapper exception.
17. **Ignoring suppressed exceptions in try-with-resources:** misses important cleanup errors required by the contract.
18. **Asserting all errors are retryable:** retryability must follow actual semantics and side effects.
19. **Putting real sensitive data in fixtures/test output:** use safe fake markers instead.
20. **Testing too many unpublished internal details:** tests obstruct legitimate refactoring.

## 26. Checklist before finishing a test

Ask yourself:

1. Does the method have a clear **failure contract**?
2. Does the test catch the right exception type, or an overly broad superclass?
3. Is an exact type required, or are subclasses also acceptable?
4. Is the message published as stable? If not, which error code or semantic part should be checked?
5. Which context properties does the caller actually need: code, ID, operation, retryable, correlation ID?
6. Are context fields asserted directly instead of parsed from the message?
7. If the layer wraps errors, does the test retain the original object for <code>assertSame</code>?
8. Does the contract require the direct cause or merely preserving the root cause in the chain?
9. Do suppressed exceptions need to be checked when cleanup fails?
10. Does the test avoid depending on raw stack traces, line numbers, or JDK/driver wording?
11. Are both the success branch and validation branch tested separately?
12. If using fakes/mocks, are they deterministic enough to avoid flaky tests?
13. Is the public response tested to ensure it does not leak sensitive information from the original exception?
14. Are async APIs observed through the contract-defined wrapper exception?
15. If the implementation changes while preserving the contract, will the test suite still PASS?

## 27. Summary

- **Exceptions are part of an API's contract**, not just an event that throws an error.
- Verify exception type with <code>assertThrows</code> or <code>assertThrowsExactly</code> depending on whether subtypes are accepted.
- Verify **message** when it is meaningful and published as stable; avoid locking onto incidental JVM/library wording.
- Verify **context** via structured getters/fields rather than extracting IDs from message strings.
- Verify **cause** with <code>assertSame(original, error.getCause())</code> when the exact same object must be preserved; check the chain if the contract allows intermediate wrappers.
- Distinguish causes, suppressed exceptions, async errors, and client-facing public messages.
- Use fakes to produce deterministic errors, keeping tests independent of the filesystem or network.
- Test both valid and failure branches thoroughly without coupling to non-contract implementation details.

**Conclusion:** a good exception test does not stop at asking “did it throw?”. It verifies **the right error type, sufficient context, an appropriate message, and preserved cause when needed**, while avoiding brittle tests tied to incidental details of the JVM, logs, or infrastructure layers.
