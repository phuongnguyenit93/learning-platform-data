# `AssertionError` and the `assert` Statement in Java

`assert` is a Java statement used to check an **internal program assumption** (*internal invariant*): a condition the programmer believes must be true if the rest of the code operates as designed. When assertions are **enabled** and the condition is false, Java throws `java.lang.AssertionError`. When assertions are **disabled**, Java **does not evaluate** either the condition or the accompanying detail expression.

This is an important difference from regular validation: `assert` is **disabled by default** in a typical JVM run, and can be enabled/disabled via startup options. Therefore, do not use `assert` as the sole mechanism to verify public API parameters, user data, access permissions, balances, or conditions that affect correctness in production.

This lesson belongs to Java Core – Exception, in the **Error and Initialization** context, focusing on the syntax and mechanism of `assert`, `AssertionError` in the inheritance hierarchy, `-ea`/`-da` flags, differences between assertions and contract exceptions, expression evaluation, side effects, relation to class initialization, and a standalone Java 17+ example.

## 1. Identifying `AssertionError`

Simplified hierarchy:

~~~text
java.lang.Object
    └── java.lang.Throwable
        ├── java.lang.Exception
        │   └── java.lang.RuntimeException
        │       ├── IllegalArgumentException
        │       ├── IllegalStateException
        │       └── NullPointerException
        └── java.lang.Error
            └── java.lang.AssertionError
~~~

Implications:

- `AssertionError` is an **unchecked throwable** because it extends `Error`.
- The compiler **does not require** declaring `throws AssertionError`.
- `catch (Exception e)` **does not catch** `AssertionError`, because `Error` is not under the `Exception` branch.
- `catch (AssertionError e)`, `catch (Error e)`, or `catch (Throwable e)` can catch it by type, but **you should not catch and ignore it by default** in business code.
- `AssertionError` usually signals a **violated programming assumption or internal check**, not a way to represent every input error or ordinary business error.

**The name `Error` does not mean every `AssertionError` is generated by the JVM itself.** Code can explicitly write `throw new AssertionError("...");`, or use the `assert` statement so the JVM performs the check depending on whether assertions are enabled or disabled.

## 2. Syntax of the `assert` Statement

Java has two forms:

~~~java
assert condition;
~~~

and:

~~~java
assert condition : detailExpression;
~~~

`condition` must have type `boolean` or `Boolean` (if `Boolean`, it requires unboxing to a boolean value when evaluated). `detailExpression` is an expression that must not have type `void`; it helps produce a detailed message when the assertion fails.

Example:

~~~java
int size = 5;
assert size >= 0;
assert size < 100 : "size exceeds internal limit: " + size;
~~~

These lines are **Java code snippets** inside a method or block. If assertions are enabled:

- When the condition is true, Java continues without throwing an error.
- When the condition is false, Java throws `AssertionError`.
- If `: detailExpression` is present and the condition is false, Java evaluates the detail expression to construct `AssertionError`.

To run in a program, you do not have to import `assert` or `AssertionError`; `assert` is a language keyword, and `AssertionError` belongs to `java.lang`.

### `assert` is a statement, not a method

`assert condition;` does not return a value to be used as an expression:

~~~java
boolean ok = assert (5 > 0); // DOES NOT COMPILE.
~~~

This is a counterexample. `assert` is a statement, not a method call like `check(...)` and not an operator with a return value.

## 3. Mechanism When Assertions Are Enabled

Suppose:

~~~java
int count = -1;
assert count >= 0 : "count must not be negative";
System.out.println("continue");
~~~

If assertions are enabled for the running class, the condition `count >= 0` is `false`. Java creates and throws `AssertionError` with the computed message. The line `System.out.println("continue")` **does not run**, unless an appropriate handler changes the control flow.

Logic flow:

~~~text
Reach assert statement
          |
          v
Assertions enabled for class?
     |                 |
    No                Yes
     |                 |
 Skip entire       Evaluate condition
 assert                 |
                    +---+---+
                    |       |
                  true     false
                    |       |
                Continue   If present: compute detail
                            |
                            v
                       throw AssertionError
~~~

If the detail contains a number or an object, the appropriate `AssertionError` constructor creates the error description according to API semantics. **Do not treat automatic message formatting as a stable machine-readable protocol.**

### When the condition is `true`, the detail is not evaluated

~~~java
assert 2 + 2 == 4 : expensiveDiagnostic();
~~~

If assertions are enabled and the condition is true, `expensiveDiagnostic()` **does not run**. If assertions are disabled, neither the condition nor `expensiveDiagnostic()` runs. Only when assertions are enabled **and** the condition is false is the detail expression evaluated.

This is why detail expressions should be simple, should not mutate program state, and should not throw secondary errors that mask the root cause.

## 4. Mechanism When Assertions Are Disabled

With the usual default when assertions are not enabled via JVM arguments, the statement:

~~~java
assert calculateCondition() : createDetail();
~~~

is **skipped** in terms of runtime evaluation:

- `calculateCondition()` is not called.
- `createDetail()` is not called.
- No `AssertionError` is thrown by this assert statement itself.
- Surrounding statements still run normally.

This easily causes confusion when testing code in an IDE: an IDE might configure `-ea` for unit tests but not for a regular application run. With the same source code, if the run configuration differs, an assertion may be checked in one environment but skipped in another.

**Do not infer from not seeing an `AssertionError` that the invariant has been verified**; check whether assertions were actually enabled.

### Assert is not a security mechanism

Dangerous counterexample:

~~~java
assert currentUser.isAdmin() : "Permission denied";
deleteAllRecords();
~~~

This is an illustrative snippet, not a security pattern. When assertions are disabled, there is no permission check, and the delete call still executes. Access permissions must be checked by a security/authorization mechanism that is always active by design, not by `assert`.

## 5. Enabling and Disabling Assertions with JVM Options

Commonly used options:

| Option | Meaning |
| --- | --- |
| `-ea` or `-enableassertions` | Enables assertions for non-system classes in the default scope |
| `-da` or `-disableassertions` | Disables assertions in the default scope |
| `-ea:ten.lop` | Enables for a specific class named by its qualified name |
| `-ea:ten.package...` | Enables for a package and its subpackages according to option rules |
| `-da:ten.lop` | Disables for a specific class |
| `-esa` or `-enablesystemassertions` | Enables assertions for system classes |
| `-dsa` or `-disablesystemassertions` | Disables for system classes |

Two commands for the standalone program later in this lesson:

~~~bash
java -da AssertionLanguageDemo
java -ea AssertionLanguageDemo
~~~

The `-ea`/`-da` arguments must be received by the JVM as **launch options**, before the main class name in the two commands above.

The class/package name forms below are only illustrative if the corresponding classes exist on the classpath:

~~~bash
java -ea:com.example.orders.OrderService com.example.Main
java -ea:com.example.orders... com.example.Main
~~~

Do not copy a nonexistent package verbatim into the main example program and expect Java to create the class automatically.

### Scope-based enabling is not an unlimited system-wide toggle

`-ea` is not synonymous with "enable every assertion in every class across the entire JVM without exception." The JVM has separate rules for system classes and the `-esa`/`-dsa` options. When diagnosing, you need to know which classes are actually enabled.

Build/test environments such as Maven, Gradle, or IDEs may pass JVM flags through runner configurations. Looking only at the `javac` command is not enough to know whether assertions are enabled at runtime.

## 6. `-ea` Is a Runtime Option, Not a Special Compile-Time Check

Compile:

~~~bash
javac AssertionLanguageDemo.java
~~~

Run disabled/enabled:

~~~bash
java -da AssertionLanguageDemo
java -ea AssertionLanguageDemo
~~~

**You do not need to compile twice.** The bytecode of the same class can run under both assertion-checking modes. Enabling/disabling is chosen by the JVM/class loader when the class is initialized according to the relevant rules.

Do not change Java syntax to `assert enabled(...)` just to turn assertions on; `assert` is a language keyword, while the enable/disable policy is managed by the JVM.

## 7. `Class.desiredAssertionStatus()` Helps Inspect Configuration

Java provides:

~~~java
System.out.println(MyClass.class.desiredAssertionStatus());
~~~

In this snippet, `MyClass` is a hypothetical class. The `desiredAssertionStatus()` method indicates the desired assertion status for the class according to class loader settings. It is useful for **diagnosing configuration** in simple examples.

However, do not build a business system around repeatedly calling that method instead of using `assert` with proper syntax. In complex class initialization cases, assertion status also relates to class loading/initialization rules; do not use this method as an automatic replacement for all runtime checks.

In the upcoming standalone program, a normal class run with `-da` will display `false`; when run with `-ea` for that class, it will display `true`.

## 8. Do Not Use `assert` for Public API Input Conditions

Wrong example:

~~~java
static int dividePositive(int numerator, int denominator) {
    assert denominator > 0 : "denominator must be positive";
    return numerator / denominator;
}
~~~

If assertions are disabled, the input `denominator = -2` still slips through and the method returns a negative result, violating the contract "denominator must be positive". With `denominator = 0`, the `/` operator throws `ArithmeticException`, but that does not guarantee all condition violations are caught with the right type.

The right way for a **mandatory precondition**:

~~~java
static int dividePositive(int numerator, int denominator) {
    if (denominator <= 0) {
        throw new IllegalArgumentException(
                "denominator must be positive");
    }
    return numerator / denominator;
}
~~~

This condition is **always evaluated** when the method runs. When the input is invalid, the caller sees `IllegalArgumentException` per the contract.

### Null checks should also not use assert

Do not do:

~~~java
static String trimRequired(String input) {
    assert input != null;
    return input.trim();
}
~~~

When assertions are disabled, `input == null` still proceeds to `trim()` and causes a `NullPointerException` at the point of use, instead of an explicit check at the boundary.

Prefer:

~~~java
static String trimRequired(String input) {
    java.util.Objects.requireNonNull(input, "input");
    return input.trim();
}
~~~

If the input is non-null but may be empty/blank, you need to add `isBlank()` or corresponding rules. `requireNonNull` only checks for a null reference, not all input conditions.

## 9. When Should You Use `assert`?

Commonly valuable situations:

1. **Internal invariants** just established by the module's own code that need verification in debug/test environments.
2. **Postconditions** (*postcondition*) that an algorithm promises must hold if the preceding steps are correct.
3. **Relationships between internal variables** guaranteed by logic—for example, a computed index must be within bounds before being passed to another API.
4. **Branches not expected to be reached** according to a proof over closed states, though assert cannot be used as the sole safety measure if continuing would cause harm.
5. **Detecting programming bugs when debug assertions are enabled** without forcing all expensive checks to run in production.

The following example illustrates a simple algorithm postcondition:

~~~java
static int clampToRange(int value, int min, int max) {
    if (min > max) {
        throw new IllegalArgumentException("min > max");
    }
    int result = Math.min(max, Math.max(min, value));
    assert result >= min && result <= max
            : "clamp result is outside expected bounds";
    return result;
}
~~~

This is a valid Java method. `min > max` is invalid input and is always rejected; the assertion checks the **internal postcondition** that the algorithm just computed. When `-ea` is enabled, if the code has a bug that makes the postcondition false, `AssertionError` helps detect it.

### An unbreakable rule

A proper assertion should have this property:

> If you remove all `assert` statements, the program still performs its business logic and preserves all required preconditions/safety conditions.

If removing `assert` causes the program to skip validation, fail to increment a counter, fail to write data, or change the primary result, the assertion is being misused.

## 10. Side Effects in an Assert Condition Are a Design Bug

Dangerous pattern:

~~~java
int counter = 0;
assert ++counter > 0;
System.out.println(counter);
~~~

If assertions are enabled, `counter` increments to `1`. If assertions are disabled, `counter` **remains 0**. Same input, different program state.

The snippet above is an intentional counterexample; it is only used to prove that **condition evaluation depends on `-ea`**.

How to separate the side effect:

~~~java
int counter = 0;
counter++;
assert counter > 0;
System.out.println(counter);
~~~

Now the increment `counter++` always happens, regardless of assertion status. The assert part only checks the assumption.

### Side effects can hide inside a method

~~~java
assert saveRecordAndReturnSuccess();
~~~

If `saveRecordAndReturnSuccess()` writes data, the write operation only runs when assertions are enabled. This is a severe bug.

Prefer:

~~~java
boolean saved = saveRecordAndReturnSuccess();
assert saved : "record was not saved";
~~~

This is an illustrative snippet with a hypothetical method. However, if a save failure is an expected business error, `saved == false` must be handled **with normal logic or a contract exception**, not just an assert. Assert is only appropriate if `saved == false` is truly an impossible invariant by design.

## 11. Detail Expressions Should Not Have Side Effects Either

Counterexample:

~~~java
assert balance >= 0 : chargePenaltyAndDescribe();
~~~

If the condition is true or assertions are disabled, `chargePenaltyAndDescribe()` does not run. If assertions are enabled and the condition is false, it runs **on the error-creation path**. Thus, charging a penalty depends on assertion status—which is unacceptable.

Better:

~~~java
assert balance >= 0
        : "negative internal balance=" + balance;
~~~

The message should be short, easy to diagnose, and free of sensitive data. For expensive detail expressions, computing them only on failure can be useful, but they **must not perform mandatory state changes**.

### The detail expression does not run if the condition is true

~~~java
assert value != null : expensiveExplain(value);
~~~

If `value != null` and assertions are enabled, Java **does not call `expensiveExplain`**. But if the condition is false, the detail itself could throw another exception. In that case, the exception arising while computing the detail may propagate out instead of an `AssertionError` as the reader expects.

Therefore, do not put complex or unsafe calls in the expression after `:`.

## 12. `AssertionError` Differs from Regular Runtime Exceptions

Comparison table:

| Condition | Usually Appropriate Mechanism | Why? |
| --- | --- | --- |
| Public method parameter is null when disallowed | `Objects.requireNonNull` → `NullPointerException` | Precondition is always checked |
| Passed quantity is negative | `IllegalArgumentException` | Invalid argument value |
| Object is not currently in an active state | `IllegalStateException` | Receiver state does not allow the operation |
| File/network connection lost | `IOException` or corresponding layer exception | Infrastructure error that must be handled per contract |
| Internal invariant that should never be false | `assert` to verify when enabled | Detects bugs during run/debug |
| Algorithm error that must always stop execution even when `-ea` is off | `throw new IllegalStateException(...)` or appropriate type | Does not depend on JVM flags |
| Valid business result `DECLINED` | Result/enum/record | Not a broken internal assumption |

The biggest difference is that **an `assert` statement may not run at all**. Mandatory business contract conditions must not be placed solely where they can be stripped out like this.

### `AssertionError` is not the same as `IllegalStateException`

Both can suggest an invalid state, but:

- `IllegalStateException` is a `RuntimeException`, under the `Exception` branch, suitable for state errors that callers may receive per contract.
- `AssertionError` is under `Error`, primarily signaling a broken programming assumption / internal invariant.
- `catch (Exception)` catches `IllegalStateException` but **does not** catch `AssertionError`.
- Explicitly throwing `new AssertionError(...)` is **not** controlled by `-ea`; only the **`assert` language statement** is enabled/disabled that way.

Do not turn a normal state error into `AssertionError` just to report a "stronger" error.

## 13. The `assert` Statement vs. `throw new AssertionError`

These two approaches differ:

~~~java
assert false : "internal invariant failed";
~~~

and:

~~~java
throw new AssertionError("internal invariant failed");
~~~

With the `assert` statement:

- When `-ea` is off, Java skips the statement.
- When `-ea` is on, it throws `AssertionError` because the condition is false.

With `throw new AssertionError(...)`:

- The error **is always thrown** if that code path is executed, regardless of `-ea` or `-da`.
- No checked exception declaration is needed.
- It can be useful in certain cases proving a branch is unreachable, but you should consider whether doing so matches the contract.

### Using `assert false` for an "impossible" branch?

~~~java
switch (status) {
    case "OPEN" -> processOpen();
    case "CLOSED" -> processClosed();
    default -> {
        assert false : "unexpected status: " + status;
    }
}
~~~

This is an illustrative snippet requiring `status` and two appropriate methods. When assertions are disabled, the `default` branch **does nothing** other than completing the block. If a new status appears, the program may silently continue.

If you require **always stopping** on an unsupported status:

~~~java
switch (status) {
    case "OPEN" -> processOpen();
    case "CLOSED" -> processClosed();
    default -> throw new IllegalStateException(
            "unexpected status: " + status);
}
~~~

This form expresses a safe contract independent of assertion status. With enums and switch expressions in newer Java versions, there are also compile-time exhaustiveness checks; do not rely on `assert false` to replace proper state-handling design.

## 14. Java 17+ — Standalone Program Demonstrating Disabled and Enabled `assert`

The following program shows that:

- When assertions are disabled, neither the condition nor the message of `assert` runs.
- When `-ea` is enabled, a `true` condition runs without running the message; a `false` condition causes `AssertionError` to appear.
- Input checks using `Objects.requireNonNull` and `IllegalArgumentException` **always work** even when `-ea` is off.
- `throw new AssertionError` works independently of assertion flags.
- The program catches `AssertionError` only for observation in a learning example; **ignoring an Error in production is not recommended**.

Save as **`AssertionLanguageDemo.java`**:

~~~java
import java.util.Objects;

public class AssertionLanguageDemo {
    private static int conditionCalls;
    private static int detailCalls;

    public static void main(String[] args) {
        System.out.println("enabled="
                + AssertionLanguageDemo.class.desiredAssertionStatus());

        assert condition(true) : detail();
        System.out.println(
                "trueCheck conditionCalls=" + conditionCalls
                        + ", detailCalls=" + detailCalls);

        try {
            assert condition(false) : detail();
            System.out.println("falseCheck completed");
        } catch (AssertionError error) {
            System.out.println(
                    "falseCheck caught=" + error.getMessage());
        }
        System.out.println(
                "afterFalse conditionCalls=" + conditionCalls
                        + ", detailCalls=" + detailCalls);

        try {
            validateRequest(null, 2);
        } catch (NullPointerException error) {
            System.out.println(
                    "nullInput="
                            + error.getClass().getSimpleName()
                            + ":" + error.getMessage());
        }

        try {
            validateRequest("A-1", 0);
        } catch (IllegalArgumentException error) {
            System.out.println(
                    "badQuantity=" + error.getMessage());
        }

        try {
            throw new AssertionError("explicit failure");
        } catch (AssertionError error) {
            System.out.println(
                    "explicit=" + error.getMessage());
        }

        System.out.println("done");
    }

    static boolean condition(boolean result) {
        conditionCalls++;
        return result;
    }

    static String detail() {
        detailCalls++;
        return "invariant failed";
    }

    static void validateRequest(String orderId, int quantity) {
        Objects.requireNonNull(orderId, "orderId");

        if (orderId.isBlank()) {
            throw new IllegalArgumentException(
                    "orderId must not be blank");
        }
        if (quantity <= 0) {
            throw new IllegalArgumentException(
                    "quantity must be positive");
        }
    }
}
~~~

Compile:

~~~bash
javac AssertionLanguageDemo.java
~~~

### Running with assertions disabled

~~~bash
java -da AssertionLanguageDemo
~~~

**Exact stdout in `-da` mode:**

~~~text
enabled=false
trueCheck conditionCalls=0, detailCalls=0
falseCheck completed
afterFalse conditionCalls=0, detailCalls=0
nullInput=NullPointerException:orderId
badQuantity=quantity must be positive
explicit=explicit failure
done
~~~

**Explanation:**

1. `-da` disables assertions for the class, so `desiredAssertionStatus()` returns `false`.
2. Both `condition(true)` and `condition(false)` **are not called**, so `conditionCalls` stays `0`.
3. `detail()` does not run either, so `detailCalls` stays `0`.
4. The branch with the false condition **does not throw** an `AssertionError` from assert, so it prints `falseCheck completed`.
5. The two preconditions `requireNonNull`/`quantity <= 0` still execute and throw the right exception types.
6. `throw new AssertionError("explicit failure")` still throws the Error, because it is not an `assert` statement.

### Running with assertions enabled

~~~bash
java -ea AssertionLanguageDemo
~~~

**Exact stdout in `-ea` mode:**

~~~text
enabled=true
trueCheck conditionCalls=1, detailCalls=0
falseCheck caught=invariant failed
afterFalse conditionCalls=2, detailCalls=1
nullInput=NullPointerException:orderId
badQuantity=quantity must be positive
explicit=explicit failure
done
~~~

**Explanation:**

1. `-ea` enables assertions for the class, so `desiredAssertionStatus()` returns `true`.
2. The first assert calls `condition(true)` and increments the counter to `1`. Since the condition is true, `detail()` is not called.
3. The second assert calls `condition(false)`, incrementing the counter to `2`. Because it is false, Java calls `detail()` once and throws `AssertionError("invariant failed")`.
4. The `catch (AssertionError error)` handler is only for demonstration, so it prints `falseCheck caught=invariant failed`.
5. The validation parts produce the same results as in `-da` mode.
6. `throw new AssertionError` produces the same result in both modes.

### Why does the program have a side effect in `condition()`?

`condition()` increments a counter to **empirically prove** that `assert` can skip evaluating its expression. This is an intentional demo technique, **not a design to follow in business code**. Real application logic must place all required side effects outside `assert` statements.

### Does it need any test library or database dependencies?

No. The program uses JDK 17, `java.util.Objects`, and the built-in `java.lang.AssertionError` class. You only need to create one Java file, run `javac`, and use the two `java` commands above.

## 15. Throwing `AssertionError` Directly and Its Constructors

Java has constructors such as:

~~~java
new AssertionError()
new AssertionError("message")
new AssertionError(42)
new AssertionError(false)
new AssertionError((Object) someValue)
~~~

These are illustrative object-creation snippets with an appropriate `someValue` variable. `AssertionError` provides overloads for several primitive types and `Object` to support the detail expression of `assert`.

In particular, when using the constructor taking `Object`:

~~~java
Throwable root =
        new IllegalStateException("source invariant failed");

AssertionError error =
        new AssertionError((Object) root);

System.out.println(error.getCause() == root);
// true
~~~

The `AssertionError(Object detailMessage)` constructor has a special rule: if the detail object is a `Throwable`, it can be set as the **cause** of the `AssertionError`. This is specific API behavior and should not be confused with constructors of every exception class.

If you want an application error with a message/cause under a normal contract, use an appropriate `Exception`/`RuntimeException` subclass instead of defaulting to `AssertionError`.

### `AssertionError` does not replace checked exception handling

Suppose file-reading code can throw `IOException`. Writing:

~~~java
try {
    loadConfiguration();
} catch (java.io.IOException cause) {
    throw new AssertionError(cause);
}
~~~

is an illustrative snippet. It turns a checked `IOException` into an `Error`, which is usually **inappropriate** if configuration might be missing or a connection might fail during normal operation. Callers will not see the original checked contract, and `catch(Exception)` will not catch the new error either.

If you need to translate abstractions, consider a custom `Exception` or `RuntimeException` with a constructor preserving the cause, with a clear design rationale. Only use `AssertionError` if the failure genuinely describes a violated internal assumption, not just any infrastructure error.

## 16. Assertions in Constructors and Object State

A constructor may use `assert` to check an internal invariant, but must not use it as the sole condition for accepting caller data.

Wrong:

~~~java
final class UserId {
    private final String value;

    UserId(String value) {
        assert value != null : "value must not be null";
        this.value = value;
    }
}
~~~

When assertions are disabled, the constructor allows creating a `UserId` with `value == null`, breaking the object's invariant contract.

Prefer:

~~~java
final class UserId {
    private final String value;

    UserId(String value) {
        java.util.Objects.requireNonNull(value, "value");
        if (value.isBlank()) {
            throw new IllegalArgumentException("value is blank");
        }
        this.value = value;
        assert !this.value.isBlank();
    }
}
~~~

Here:

- The first two validations **always run**, protecting the constructor contract.
- The final assertion is only an additional check on the established invariant.
- If assertions are disabled, the object still cannot be successfully constructed with null or blank input.

Not every constructor needs a trailing assert. If the condition is already proven by simple code, you do not need to add redundant checks.

## 17. Assertions in Exception-Handling Branches

A common mistake is thinking `assert false` can be used as a default for any caught exception:

~~~java
try {
    doSomething();
} catch (java.io.IOException e) {
    assert false : e;
}
~~~

This is an illustrative snippet with `doSomething()`, not a standalone program. With `-da`, the handler **catches `IOException` and does nothing**; execution continues, causing the I/O error to be completely swallowed.

If this layer does not know how to recover, it is usually better to:

~~~java
try {
    doSomething();
} catch (java.io.IOException cause) {
    throw new IllegalStateException(
            "cannot complete the operation", cause);
}
~~~

Or let the checked `IOException` propagate via `throws IOException` per contract. When catching an exception, you must **handle it, wrap/translate it with cause, or rethrow it** according to the layer's responsibility—not rely on `assert false`.

## 18. `AssertionError` in Static Initializers

Because this topic belongs to the **Error and Initialization** group, you need to understand the impact of assertions while the JVM is initializing a class.

Example:

~~~java
final class StaticInvariant {
    static final int SIZE = calculateSize();

    static {
        assert SIZE > 0 : "static size must be positive";
    }

    static int calculateSize() {
        return -1;
    }

    static int size() {
        return SIZE;
    }
}
~~~

This is a valid Java class. Its behavior depends on whether assertions are enabled for `StaticInvariant` when the class is initialized:

- **Assertions disabled:** the `static` block does not check `SIZE > 0`; the class can initialize successfully with `SIZE == -1`.
- **Assertions enabled:** the `SIZE > 0` check fails and the statement throws `AssertionError` during class initialization.
- `AssertionError` is a subtype of `Error`. Under class initialization rules, an escaping throwable that is already an `Error` can be propagated directly on the first failure, **without necessarily being wrapped in `ExceptionInInitializerError`**.
- After class initialization fails, the class definition can be marked **erroneous**; subsequent active uses typically receive `NoClassDefFoundError` in the same class loader rather than re-running the static initializer.

This is why you should not treat an assertion as the sole safeguard for **static state required for operation**.

### What if invalid values must never be accepted even under `-da`?

Replace the assertion with a check that always runs:

~~~java
final class StaticValidated {
    static final int SIZE = calculateSize();

    static {
        if (SIZE <= 0) {
            throw new IllegalStateException(
                    "static size must be positive");
        }
    }

    static int calculateSize() {
        return -1;
    }
}
~~~

This is an illustrative class that compiles cleanly (the static block can still complete normally according to compiler analysis). When the initializer throws `IllegalStateException`—a `RuntimeException`, not an `Error`—the JVM typically wraps the initialization failure in `ExceptionInInitializerError`.

**Both approaches can still leave the class erroneous.** If the failure is a recoverable operational condition (such as reading configuration or opening a network connection), it is usually better to move the work to a **factory/loader** with a clear checked/unchecked contract and retry path, rather than failing class initialization.

## 19. Assertions in Static Initializers and When Status Takes Effect

The JVM manages enabling/disabling assertions per class loader and the status applied when a class is initialized. Therefore, using `assert` during class initialization has specific nuances.

Special rules about a class being used **while that same class is still initializing** should not be oversimplified into "every assert always follows a self-written boolean at the start of the program." For normal code, use `-ea`/`-da` explicitly at startup and avoid building initialization logic that depends on whether assertions can be enabled.

Practical takeaways:

1. `assert` is a skippable check; it does not replace mandatory validation.
2. An `AssertionError` escaping class initialization can render the class unusable for subsequent active uses.
3. Moving failure-prone operations into normal methods or instance factories gives the system a clearer recovery path.

## 20. `catch (Exception)`, `catch (Error)`, and `catch (Throwable)`

The following snippet illustrates **catch behavior**, not production advice:

~~~java
try {
    throw new AssertionError("internal bug");
} catch (Exception e) {
    System.out.println("Exception branch");
} catch (AssertionError e) {
    System.out.println("AssertionError branch");
}
~~~

Output:

~~~text
AssertionError branch
~~~

`catch(Exception)` does not catch subtypes of `Error`. This is not a reason for every service to switch to `catch(Throwable)`.

### Why should you not catch and ignore `AssertionError`?

A failed assertion usually means **an assumption in the code is wrong**. If code catches it and continues as if nothing happened:

- Object state may no longer match what the algorithm expects.
- Subsequent steps may produce hard-to-spot corrupted data.
- Debugging loses the original point of failure.
- If the assertion was during initialization, the class may already be in a failed-initialization state.

In a test runner or some low-level frameworks, a handler may catch `AssertionError` to **record a failed test result**, but that is a specialized responsibility.

If you must log and propagate the error, you need a very clear policy; **do not write `catch(Throwable)` to turn every `Error` into a normal business result**.

## 21. Java's `assert` vs. JUnit Assertions

Two things that often share a name but have different mechanisms:

**Java language assertion:**

~~~java
assert actual == expected : "values differ";
~~~

**JUnit 5 assertion:**

~~~java
org.junit.jupiter.api.Assertions.assertEquals(expected, actual);
~~~

The JUnit snippet is an **illustrative snippet requiring JUnit 5**, not part of the standalone Java 17 program above.

Differences:

| Criterion | Java `assert` | JUnit 5 `assertEquals` |
| --- | --- | --- |
| What is it? | Language statement | Testing framework method |
| Requires external library outside JDK? | No | Yes |
| Depends on `-ea` to run the check? | **Yes** | **No**, method is called like normal code |
| When unsatisfied? | `AssertionError` if assertions are enabled | Framework throws a test failure error, usually a subtype of `AssertionError` |
| Primary role | Checking internal invariants when enabled | Asserting expected results of a test |
| When assertions are disabled | Skips both condition and detail | Test method still executes |

To test the outcome of a feature, you should usually use the framework's assertion tools, such as `assertEquals` or `assertThrows`, rather than letting your entire test suite depend on `-ea`.

### What does `AssertionError` mean in a test runner?

A test framework may use `AssertionError` or its subclass to signal a failed test; the runner catches it, records it, and continues running other tests. This is an **intentional specialized mechanism**, not a precedent for business applications to catch every `AssertionError` and continue.

## 22. Common Misconceptions

### Mistake 1 — Thinking `assert` always runs

No. In typical JVM runs, assertions may be disabled. You need `-ea` when you want them checked.

### Mistake 2 — Using `assert` to validate user input

Input can be invalid by design; you need always-on validation with `IllegalArgumentException`, `NullPointerException`, or a structured result.

### Mistake 3 — Assuming `catch (Exception)` catches `AssertionError`

No. `AssertionError extends Error`, not `Exception`.

### Mistake 4 — Thinking `AssertionError` is a checked exception

No. All subtypes of `Error` are unchecked; no `throws` declaration is required.

### Mistake 5 — Thinking `throw new AssertionError` is also disabled by `-da`

No. Assertion options only affect the **`assert` statement**, not explicit `throw` statements.

### Mistake 6 — Putting counter updates in an assert condition

When assertions are disabled, the update is skipped. Side effects must live in normal statements.

### Mistake 7 — Putting network/data-write operations in the detail expression

Detail only runs when assertions are enabled and the condition is false; it cannot serve as a mandatory business path.

### Mistake 8 — Using `assert false` to handle `IOException`

With `-da`, the catch block may do nothing and accidentally swallow the exception.

### Mistake 9 — Thinking `assert false` always stops execution

Not if assertions are disabled. If you must always stop, throw an appropriate exception/Error by design.

### Mistake 10 — Treating `AssertionError` as the most severe error and using it for every failure

Business impact does not determine `Error` inheritance. A severe connection failure may still require `IOException` or a custom `Exception`.

### Mistake 11 — Using `assert` instead of authorization

Security must be checked independently of `-ea`/`-da` status.

### Mistake 12 — Assuming every error in a static block is always wrapped in `ExceptionInInitializerError`

If the throwable is already an `Error`, the JVM can propagate that object directly on the first initialization failure. `AssertionError` belongs to this group.

### Mistake 13 — Thinking a class re-initializes itself after an `AssertionError` in a static block

No. A failed class initialization can mark the class definition erroneous; subsequent active uses typically encounter `NoClassDefFoundError`.

### Mistake 14 — Thinking JUnit `assertEquals` depends on `-ea`

No. It is a framework method call, executed under normal test logic.

### Mistake 15 — Assuming the detail expression is always evaluated

No. It is only evaluated if assertions are enabled and the condition is false.

### Mistake 16 — Using `assert obj != null` and then dereferencing `obj`

When assertions are disabled, null remains and dereferencing can throw an NPE deeper in the logic, failing to establish a clear contract.

### Mistake 17 — Catching `AssertionError` and using a default fallback

If an internal invariant is wrong, a fallback can hide a bug and corrupt data. Determine true recoverability before continuing.

### Mistake 18 — Using `assert` to check transactional invariant rules

Balance/limit/security checks must always run and usually require synchronization/transaction mechanisms; `assert` does not solve transaction consistency.

### Mistake 19 — Treating the `AssertionError` message as a machine error code

Messages are primarily for humans and can change. Use a distinct exception type or error code when automated branching is needed.

### Mistake 20 — Putting `assert` in place of configuration data validation

Configuration is input from the environment and can be wrong. Report a meaningful exception with a clear recovery/restart path, independent of assertion flags.

## 23. Checklist for Using `assert` Properly

Before adding an `assert` statement, answer:

1. **Is this an internal invariant** that preceding logic was already responsible for guaranteeing?
2. **If assertions are disabled, is the code still correct and safe?** If not, use `if`/`throw`.
3. **Does the condition have side effects?** Never use the condition's evaluation to perform mandatory state changes.
4. **Does the detail expression have side effects?** It should not.
5. **Does the data come from a public API/HTTP/file/database?** If so, validation must always run.
6. **Is there a more suitable contract exception?** NPE/IAE/ISE/IOException is usually clearer for expected errors.
7. **Do you need to collect user errors to return multiple messages?** Use a validation result mechanism, do not rely on assert.
8. **Does the test environment enable `-ea`?** Check your run configuration if you want assertions executed.
9. **Should you use JUnit assertions to test results?** Usually yes.
10. **If an assertion fails, should the program stop the operation?** Do not catch and ignore without a specialized policy.
11. **Is the assertion inside a static initializer?** It can prevent the class from initializing when enabled.
12. **Does the message contain sensitive data?** Do not put tokens/secrets or full user data into the message.

A great self-check: **imagine deleting every `assert` from the source**. If the application still satisfies its contracts, safety policies, and side-effect ordering, you are using assertions close to their intended purpose.

## 25. Summary

**`assert` is a toggleable tool for checking internal assumptions, and `AssertionError` is an unchecked `Error` thrown when assertions are enabled and the condition is false.** Do not use `assert` to replace public API preconditions, security, external data validation, or mandatory side effects, because the entire assert expression may not be evaluated. Use `-ea` when you want to verify invariants during development/testing; use appropriate exceptions such as `IllegalArgumentException`, `NullPointerException`, or `IllegalStateException` for always-enforced contracts.

If an `AssertionError` escapes a static initializer, class initialization can fail and make the class unusable for subsequent active uses. Finally, clearly distinguish Java language assertions from test framework assertion methods: **JUnit tests via method calls, independent of whether `-ea` is enabled for `assert` statements**.
