# Exceptions in SLF4J

## 1. How Does SLF4J Log Exceptions?

**SLF4J (Simple Logging Facade for Java)** is a unified API for Java applications to emit log events. SLF4J does not itself decide the format and destination of every log record; a compatible **provider/backend** such as Logback, Log4j 2 via the appropriate provider, or slf4j-simple handles the log output.

When an operation throws an exception, proper logging needs to answer three questions:

1. **What failed?** State the operation, event code, component, and technical correlation ID if available.
2. **What is the impact level?** Choose ERROR, WARN, INFO, or DEBUG based on the final outcome and recoverability.
3. **Where is the technical root cause?** Pass the **Throwable** itself to the logging API so the backend can display the stack trace, nested causes, and suppressed exceptions when supported.

Example of declaring a logger per class:

~~~java
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public class OrderService {
    private static final Logger log =
            LoggerFactory.getLogger(OrderService.class);
}
~~~

When handling an error at the responsible boundary:

~~~java
try {
    persistOrder(orderId);
} catch (java.io.IOException e) {
    log.error("Order persistence failed, orderId={}", orderId, e);
    throw e;
}
~~~

This is an **illustrative snippet inside a method that already has log, orderId, and persistOrder**. The **e** parameter at the end is a Throwable object, which SLF4J recognizes according to its parameterized logging rules; the backend can output the stack trace. However, the example above only makes sense when this layer is chosen as the final error-logging point: if an upper layer also logs the same exception, it can create duplicate logs. Section 6 explains how to organize responsibilities.

**Logging does not handle the exception on behalf of the program.** After logging, the code must still perform rollback, conditional retry, a valid fallback, return an error result, or propagate the exception to a layer that can handle it.

## 2. Key APIs for Logging Exceptions

SLF4J provides overloads for each log level. The following examples use the name **log** for a variable of type **org.slf4j.Logger**.

| Call | Main behavior | When to use |
| --- | --- | --- |
| **log.error("Cannot save order", e)** | Passes the Throwable directly so the backend can display the stack trace | Final error with clear context, no placeholders needed |
| **log.error("Cannot save orderId={}", id, e)** | Replaces the placeholder with id and accepts the Throwable as the last argument | Need contextual data along with the exception |
| **log.warn("Temporary issue", e)** | Preserves the Throwable at WARN level | Anomaly/recovery with a reason worth investigating |
| **log.debug("Attempt failed", e)** | Preserves the Throwable at DEBUG level if enabled | Per-attempt diagnostics, avoiding noise in production |
| **log.info("Recovered orderId={}", id)** | Logs a success event; no Throwable | Marks that recovery has completed |
| **log.atError().setCause(e).log("Operation failed")** | Fluent API in SLF4J 2.x, explicitly attaching the cause | Want to express the exception clearly and add fields |

The **error(String, Throwable)** and **error(String, Object...)** overloads have different meanings. With the pattern **log.error("message", e)**, the Throwable parameter is already the cause; you should not expect it to be substituted into a placeholder in the message string. Parameterized logging with context arguments and a trailing Throwable works through SLF4J's throwable candidate detection mechanism.

Safe, readable example:

~~~java
log.error("PAYMENT_FAILED requestId={} provider={}",
        requestId, providerName, exception);
~~~

In this call there are **two placeholders** for requestId and providerName; **exception** is the trailing Throwable object handled as the error cause, not substituted into a third placeholder.

## 3. Distinguishing Exception Object, Exception Message, and Stack Trace

### 3.1. Logging Only getMessage() Often Lacks Information

~~~java
log.error("Request failed: {}", exception.getMessage());
~~~

This is a valid log line if **exception** exists and can return a message. However, the value passed to the logger is only a **String**; the logger does not receive a Throwable. The throw location, nested causes, and stack trace are not automatically attached.

If you are investigating a real error, prefer:

~~~java
log.error("Request failed, requestId={}", requestId, exception);
~~~

Or when no additional arguments are needed:

~~~java
log.error("Request failed", exception);
~~~

The exact output depends on the provider and layout. Some configurations print only the message, while others print the full stack trace. **Passing the Throwable** is the prerequisite for the backend to have the exception data; it does not force every backend to display the stack trace in every configuration.

### 3.2. Throwable.toString() Is Different from Throwable

~~~java
log.error("Failure: {}", exception.toString());
~~~

**exception.toString()** only produces a string containing the type name and message (if any); it does not attach the Throwable object to the log event. Similarly, string concatenation like **"Failure: " + exception** does not let SLF4J receive the cause.

**Throwable.printStackTrace()** can print the stack trace directly to System.err, but it bypasses log levels, patterns, routing, structured context, and centralized log management systems. Therefore, you should use the logger API instead of calling printStackTrace in production business code.

### 3.3. Position of Throwable in Arguments

A common mistake is using a placeholder without being sure which overload Java selects:

~~~java
// Avoid using a single placeholder like this when there is only a Throwable.
log.error("Failure: {}", exception);
~~~

When the **exception** variable has type **Throwable** or a subclass, Java may select the **error(String, Throwable)** overload. In that case, **{}** may be left literal in the message because exception is used as the cause. Write it more clearly:

~~~java
log.error("Failure while calling gateway", exception);
~~~

Or if you want a data field substituted into the message:

~~~java
log.error("Failure for requestId={}", requestId, exception);
~~~

In SLF4J versions supporting parameterized logging, a trailing Throwable argument is recognized appropriately. Do not pass **exception.getMessage()** in the last position as a substitute for Throwable: that is a String and carries no stack trace.

## 4. Placeholders {} and Argument Count

SLF4J uses the **{}** token to substitute arguments into a message. This is neither **String.format("%s")** nor the **{0}** parameterization style of **java.util.logging (JUL)**.

Example:

~~~java
log.warn("Payment retry attempt={} requestId={}", attempt, requestId);

log.error("Payment failed attempt={} requestId={}",
        attempt, requestId, exception);
~~~

In the second call, there are **two placeholders for two business arguments**; exception at the end is handled as the Throwable. Avoid:

~~~java
log.error("Payment failed attempt={} requestId={} cause={}",
        attempt, requestId, exception);
~~~

If the goal is to output the stack trace, do not use a separate placeholder to "print the exception" as ordinary data. Keep the cause explicit and let the layout/encoder handle it. If you need the exception type as a searchable field, add a dedicated field (for example, **error_type**) through your project's structured logging mechanism.

**Note:** For regular arguments, SLF4J normally defers formatting the final string when the log level is disabled. However, **expressions passed to the Java call are still evaluated beforehand**:

~~~java
log.debug("Expensive diagnostics={}", buildLargeReport());
~~~

If **buildLargeReport()** is expensive, it still runs before the logger decides whether to log. When needed, use a guard check:

~~~java
if (log.isDebugEnabled()) {
    log.debug("Expensive diagnostics={}", buildLargeReport());
}
~~~

The code snippets above assume **log** and the referenced variables/methods already exist; they are not standalone programs.

## 5. Fluent API in SLF4J 2.x: setCause

SLF4J 2.x provides **LoggingEventBuilder**. It lets you attach the cause explicitly while also adding arguments, key-value pairs, or markers within the supported API.

~~~java
log.atError()
        .setCause(exception)
        .addArgument(requestId)
        .log("Request failed, requestId={}");
~~~

Another approach uses key-value pairs:

~~~java
log.atError()
        .setCause(exception)
        .addKeyValue("requestId", requestId)
        .addKeyValue("operation", "authorize")
        .log("Payment provider failed");
~~~

Here **setCause(exception)** explicitly specifies the throwable, separate from the formatting arguments. **addKeyValue** supplies key-value pairs for the event; whether the backend displays or stores them as independent fields depends on the provider/encoder/layout. A backend that only supports plain text may render them differently from a backend that supports structured logging.

Version notes:

- **SLF4J 1.7:** The common API uses the **error/warn/info/debug/trace** overloads with placeholders and Throwable; there is no **atError()** API as in SLF4J 2.0.
- **SLF4J 2.x:** Adds the fluent API **atError(), atWarn(), setCause(), addArgument(), addKeyValue()**.
- **The provider/backend must be compatible with the API version.** SLF4J 2.x uses a provider model; do not arbitrarily mix an SLF4J 2.x API with an SLF4J 1.7-era binding.

In this article, examples using the fluent API apply only to SLF4J 2.x. For older projects, you can use **log.error("Message", exception)**, which is simple and compatible across many versions.

## 6. Logging Exceptions at the Right Layer to Avoid Duplicates

The same exception can travel through Repository → Service → Controller. If all three layers call **log.error(..., e)** and then rethrow, the system can emit three stack traces for a single error.

### Poor Practice

~~~java
// Repository:
catch (SQLException e) {
    log.error("Database failed", e);
    throw e;
}

// Service:
catch (SQLException e) {
    log.error("Service failed", e);
    throw e;
}

// Controller:
catch (SQLException e) {
    log.error("Request failed", e);
    throw e;
}
~~~

The snippets above **illustrate catch blocks in three separate places**, not a single complete method. When every layer simply logs and propagates the same exception upward, the ERROR log count is inflated, making it hard for readers to tell how many requests actually failed.

### Better Approach

- **Repository:** If unable to recover, rethrow the exception or wrap it with appropriate technical details while preserving the cause.
- **Service:** If a safe retry/fallback exists, execute it and record notable state transitions.
- **Boundary responsible for the final outcome:** Log ERROR once when the request truly fails, or INFO/WARN when it has recovered and that fact has observability value.

Example of wrapping the cause without logging yet:

~~~java
try {
    saveOrder(orderId);
} catch (SQLException e) {
    throw new OrderStorageException(
            "Cannot persist orderId=" + orderId, e);
}
~~~

This is an illustrative snippet; **OrderStorageException** must be defined in the project. When the outer layer catches the final error, it can log once with the entire **cause chain**. If you construct a new exception without passing **e** as the cause, you lose the path to the original error.

**It is not always strictly one log per exception.** A DEBUG record at retry time and an ERROR record at the final outcome can complement each other. What should be avoided is logging at the same level, with the same stack trace and the same meaning, multiple times without adding new information.

## 7. Choosing the Log Level for Different Exception Types

Exception logging should be based on **actual impact and final outcome**. Not every IOException must be ERROR, nor must every IllegalArgumentException be WARN.

| Scenario | Usually appropriate level | Why |
| --- | --- | --- |
| Temporary dependency error, automatic retry succeeds | DEBUG, sometimes WARN when noteworthy | Avoids counting each attempt as a failed final request |
| Fallback used because a secondary service has issues | WARN | There is degradation or a switch to a backup path |
| Primary task fails after all retries | ERROR | Real impact; root cause needs to be recorded |
| User sends invalid input according to API contract | INFO/DEBUG or not logged, depending on policy | Bad input is not necessarily a server error |
| An important job fails to complete | ERROR | The system failed to complete a critical task |
| Exception from normal task cancellation | DEBUG/INFO or not logged | Avoids turning every cancellation into an incident |
| Bug or violated system invariant | ERROR at the final handler | Needs code investigation and stack trace preservation |

For example, a request that fails on the first attempt but succeeds on retry can emit **ATTEMPT_FAILED** at DEBUG and **OPERATION_RECOVERED** at INFO. Once retries are exhausted, the **OPERATION_FAILED** event is logged at ERROR at the final boundary.

An error handled by a fallback must also be evaluated for quality degradation. If the fallback fails or corrupts data, do not mechanically log "Recovered".

## 8. Runnable Example with Java 17, Maven, and SLF4J 2.x

This example demonstrates two cases:

1. Loading an invoice encounters an I/O error with no recovery path in the demo: log **ERROR** with the Throwable and return a failed result.
2. An **optional** retry-count configuration has a format error: use a safe default and log **WARN** using the fluent **setCause** API for investigation.

The example intentionally performs no real network or payment operations. It uses **slf4j-simple** as the provider so it can run standalone after Maven downloads dependencies; real applications can use Logback or another suitable backend.

Structure:

~~~text
slf4j-exception-demo/
  pom.xml
  src/
    main/
      java/
        demo/
          ExceptionSlf4jDemo.java
~~~

        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    </properties>

    <dependencies>
        <dependency>
            <groupId>org.slf4j</groupId>
            <artifactId>slf4j-api</artifactId>
            <version>2.0.16</version>
        </dependency>
        <dependency>
            <groupId>org.slf4j</groupId>

~~~

Contents of **src/main/java/demo/ExceptionSlf4jDemo.java**:

~~~java
package demo;

import java.io.IOException;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public final class ExceptionSlf4jDemo {
    private static final Logger log =
            LoggerFactory.getLogger(ExceptionSlf4jDemo.class);

    public static void main(String[] args) {
        String invoiceId = "INV-42";

        try {
            loadInvoice(invoiceId);
        } catch (IOException e) {
            log.error("INVOICE_FETCH_FAILED invoiceId={}", invoiceId, e);
            System.out.println("RESULT | " + invoiceId + " | failed");
        }

        String configuredRetries = "many";
        int retryLimit;

        try {
            retryLimit = parseRetryLimit(configuredRetries);
        } catch (IllegalArgumentException e) {
            retryLimit = 3;
            log.atWarn()
                    .setCause(e)
                    .addKeyValue("setting", "retryLimit")
                    .log("Invalid optional retry limit; using default");
        }

        System.out.println(
                "RESULT | retryLimit=" + retryLimit + " | fallback");
    }

    private static String loadInvoice(String invoiceId)
            throws IOException {
        throw new IOException("Simulated gateway timeout");
    }

    private static int parseRetryLimit(String raw) {
        int value = Integer.parseInt(raw);

        if (value < 1) {
            throw new IllegalArgumentException("retry limit must be positive");
        }

        return value;
    }
}
~~~

Run in the **slf4j-exception-demo** directory with **JDK 17+ and Maven**:

~~~bash
mvn -q compile exec:java -Dexec.mainClass=demo.ExceptionSlf4jDemo
~~~

Two **stdout lines printed by the program itself**, in order:

~~~text
RESULT | INV-42 | failed
RESULT | retryLimit=3 | fallback
~~~

With the **slf4j-simple** provider, ERROR and WARN logs along with stack traces are typically written to **stderr**. They appear alongside program output when the terminal merges stdout/stderr; you should not assume a strict ordering between two separate streams or a fixed number of stack trace lines. Typical log contents:

~~~text
ERROR ... INVOICE_FETCH_FAILED invoiceId=INV-42
java.io.IOException: Simulated gateway timeout
    at demo.ExceptionSlf4jDemo.loadInvoice(...)
    ...

WARN ... Invalid optional retry limit; using default
java.lang.NumberFormatException: For input string: "many"
    ...
~~~

This is **illustrative output with ellipses (...)**, because prefixes, thread names, stack trace lines, and key-value formatting depend on the provider, layout, library version, and execution environment. What matters is verifying that **the original exceptions remain in the log**: IOException for the load failure and NumberFormatException for the invalid configuration. With the fluent API, **setCause(e)** attaches the cause directly. The example finishes normally because all errors are handled according to the policy written in main.

Maven may need to download dependencies on the first run. If your project already uses Spring Boot or dependency management, do not add **slf4j-simple** alongside the backend configured by the framework. An application should normally have only **one suitable SLF4J provider** to avoid conflicts or unexpected behavior.

## 9. Stack Trace and Cause Chain

One exception can wrap another exception. Example:

~~~java
try {
    callGateway();
} catch (IOException e) {
    throw new IllegalStateException(
            "Payment gateway unavailable", e);
}
~~~

This is an illustrative snippet. When the outer layer calls:

~~~java
log.error("Payment operation failed", wrappedException);
~~~

If **wrappedException** preserves the cause from IOException, the backend can output both the IllegalStateException stack trace and the **Caused by: java.io.IOException** section. As a result, investigators receive both the business context and the technical root cause.

Key points to remember:

- **Throwable.getMessage()** is the error message, not the full stack trace.
- **Throwable.getCause()** links to the underlying cause exception; the outer wrapper must pass the cause to the appropriate constructor.
- **Throwable.getSuppressed()** holds suppressed errors in cases such as try-with-resources; formatters can display them.
- **Stack traces are not always needed at WARN/DEBUG.** Logging excessive stack traces for frequent, transient errors can be costly and noisy.
- **Do not drop the cause just to shorten the message.** If you do not want to output the trace at a certain point, you can use a lower log level or an appropriate encoder while still preserving the exception in the execution flow.

## 10. Handled Exceptions: Retry, Fallback, and Final Outcome

Example of an HTTP client making three attempts:

~~~text
Attempt 1: IOException -> retry
Attempt 2: IOException -> retry
Attempt 3: success     -> operation recovered
~~~

A logging strategy could be:

~~~java
log.debug("ATTEMPT_FAILED operation={} attempt={}",
        operation, attempt, e);

log.info("OPERATION_RECOVERED operation={} attempts={}",
        operation, attempts);
~~~

These snippets illustrate logging points once the corresponding outcome is known. When the retry budget is exhausted and the final operation fails, instead of logging ERROR for every attempt, a responsible layer can log:

~~~java
log.error("OPERATION_FAILED operation={} attempts={}",
        operation, maxAttempts, lastException);
~~~

Before retrying, verify whether the operation is **idempotent** or protected by an **idempotency key**. A timeout can occur after the server has already processed the request, so resending a payment, order creation, or email operation can cause duplicate side effects.

A recovered status should only be logged **after the operation has genuinely completed according to its contract**, not prematurely before a commit or required confirmation step.

## 11. What Should Be Included in the Message and Context?

A good exception log includes the following minimum information:

| Field / context | Example | Why |
| --- | --- | --- |
| **event_code** | INVOICE_FETCH_FAILED | Stable searching even when wording changes |
| **operation** | loadInvoice | Identifies which operation failed |
| **service / logger_name** | billing / demo.InvoiceService | Identifies the affected component |
| **request_id / trace_id** | req-17 | Correlates events from the same request |
| **error_type** | IOException | Filters by error type |
| **attempt / max_attempts** | 2 / 3 | Distinguishes retries from final failure |
| **outcome** | failed / recovered / degraded | Reflects the business outcome |
| **Throwable** | IOException + cause chain | Enables stack trace output when needed |

Depending on the project, context can be passed via **placeholders**, **MDC**, or **SLF4J 2.x key-value pairs**.

### MDC and Considerations When Working with Thread Pools

**MDC (Mapped Diagnostic Context)** is a mechanism for holding key-value data bound to the logging execution context. Example:

~~~java
import org.slf4j.MDC;

MDC.put("requestId", requestId);
try {
    processRequest();
} finally {
    MDC.remove("requestId");
}
~~~

This is an illustrative snippet inside a method that already has **requestId** and **processRequest()**. Some backends require an appropriate pattern/layout to print MDC into logs; the SLF4J API alone does not guarantee every field will appear.

With thread pools, you must **clean up MDC in a finally block**, because threads can be reused for other requests. Do not assume MDC automatically propagates across asynchronous tasks, virtual threads, or executors: check your framework's specific propagation mechanism. Do not put sensitive data or high-cardinality IDs into alert grouping keys.

### Controlling Sensitive Data

Do not log passwords, tokens, API keys, cookies, access headers, private keys, sensitive payment details, or full user payloads. **exception.getMessage()** from third-party libraries may contain URLs, query parameters, or system details unsuitable for centralized logs. Use approved context fields, mask/redact data before logging, and apply retention and access-control policies.

If an error log already contains a secret, changing the level from ERROR to DEBUG does not fix the exposure; you must fix the log emission point and check the storage pipeline.

## 12. Common Mistakes When Logging Exceptions with SLF4J

| Mistake | Consequence | How to improve |
| --- | --- | --- |
| **log.error("Failed: {}", e.getMessage())** when a trace is needed | Keeps only a string, loses Throwable | **log.error("Failed", e)** or pass e last after fields |
| String concatenation with **e.toString()** | Does not attach cause to the logging event | Pass Throwable via the proper overload |
| Using **log.error("Failure: {}", e)** with only a Throwable | May pick the Throwable overload and leave placeholder unreplaced | Use **log.error("Failure", e)** |
| Logging ERROR at every layer and rethrowing | One error creates multiple duplicate records | Choose a boundary to log the final outcome |
| Logging ERROR for every recovered retry | False alarms and log bloat | DEBUG/WARN depending on impact, retry metrics, ERROR for final failure |
| Logging stack traces for every validation error | Noise and potential data exposure | Separate expected input errors from system errors |
| Wrapping an exception without preserving the cause | Loses the original root cause | Pass the original exception to the constructor |
| Using **atError()** in an SLF4J 1.7 project | API does not exist | Use the Throwable overload or upgrade together |
| Multiple conflicting providers/bindings | Unpredictable log output behavior | Use a single compatible provider per framework |
| Having SLF4J API without a provider | Expected logs may not appear | Configure an appropriate provider/backend |
| Not clearing MDC in a thread pool | Context leaks between requests | Clear in finally or use a framework-supported scope |
| Logging only a message without request/operation | Hard to investigate | Add an event code and safe technical context |

## 13. Self-Check Questions

**1.** Why is log.error("Failed", e) usually better than log.error("Failed: {}", e.getMessage()) for investigation?

Because the first call passes the Throwable object, allowing the backend to output the stack trace and cause; the second call only passes a String.

**2.** In log.error("Request id={} failed", requestId, e), how many placeholders are there for regular data?

There is **one** placeholder for requestId; **e** at the end is recognized as the event's Throwable.

**3.** When should you use log.atError().setCause(e).log("Failed")?

When using **SLF4J 2.x** and you want to declare the cause explicitly or combine it with fluent arguments/key-value pairs.

**4.** If an operation fails twice on retry and then succeeds, does it need to log three ERRORs?

No. You should distinguish attempt failures from the final outcome; retries can be logged at DEBUG, while the recovered result is logged at an appropriate level.

**5.** Is it helpful for both the Repository and Controller layers to log the same stack trace and rethrow the exception?

Usually no. Without adding new context, logs are duplicated and distort the perceived incident count.

**6.** Why can log output on machine A differ from machine B even with the same SLF4J API?

Because the provider/backend, format, configuration, log levels, dependencies, and stdout/stderr collection may differ. SLF4J is a facade and does not enforce a single layout across all backends.

**7.** What should you do with MDC when a thread pool reuses threads?

Clear or restore the context in **finally**, and only propagate approved keys to other workers using a defined propagation mechanism.

**Key takeaway:** When logging exceptions with SLF4J, pass the **Throwable** to the appropriate overload or use **setCause** in SLF4J 2.x, choose the log level based on actual impact, preserve the cause chain, and avoid duplicate logging across layers. Contextual messages with safe data make error diagnosis far more effective than a standalone exception message string.
