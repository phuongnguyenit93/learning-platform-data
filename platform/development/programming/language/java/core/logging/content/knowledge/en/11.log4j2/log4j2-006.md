# log4j2.xml in Java: Configuring Log4j 2 from Basics to Operations

## 1. What is `log4j2.xml` and Why Do You Need It?

In a Java application using **Apache Log4j 2**, business code typically calls a logging API:

```java
logger.info("event=order.created order_id={}", orderId);
logger.error("event=payment.failed order_id={}", orderId, failure);
```

These are illustrative lines inside a method that already has the variables `logger`, `orderId`, and `failure`. The code only describes **what event occurred**. Which levels are accepted, whether logs go to the console or a file, what format is emitted, and whether an event is routed to multiple destinations should be controlled at the configuration layer.

**`log4j2.xml`** is a common XML configuration file for Log4j 2. It defines the set of logging components and how they are wired together, allowing you to adjust logging behavior without modifying individual statements in Java code.

A simple model:

```text
Java code calls logger
        |
        v
Log4j 2 logger + level / filter
        |
        v
<Loggers> configuration decides destinations
        |
        +-------------> <Console> + PatternLayout --> stdout/stderr
        |
        +-------------> <RollingFile> + Layout   --> rolling file
        |
        +-------------> other appender           --> corresponding destination
```

The `log4j2.xml` file helps answer:

- Does the application log from `INFO`, `WARN`, or `DEBUG` by default?
- Can `DEBUG` be enabled only for a package experiencing an issue?
- Do log records go to `SYSTEM_OUT`, `SYSTEM_ERR`, a file, or multiple destinations?
- Does each line include a timestamp, thread, logger name, level, message, and exception information?
- Why does an event appear twice or not appear at all?
- When running on a developer machine, staging, and production, how is the right configuration selected?

**Logging configuration is not business error handling.** Logging `ERROR` does not automatically retry, roll back, return HTTP 500, or guarantee that an alert is sent. Configuration only controls how a logging event is accepted and published.

## 2. Conditions for `log4j2.xml` to Take Effect

### 2.1. Correct Log4j 2 and Corresponding Libraries Required

Log4j 2 has multiple modules:

| Component | Role |
| --- | --- |
| `log4j-api` | API for Java code to call `LogManager.getLogger(...)`, `logger.info(...)`, `logger.error(...)` |
| `log4j-core` | Implementation that handles configuration, logger context, appenders, layouts, filters, and logging components |
| `log4j2.xml` | Configuration file loaded by `log4j-core`, not a Java library |
| `log4j-slf4j2-impl` | Bridge from SLF4J 2.x to Log4j 2 if application code uses the SLF4J API |
| `log4j-to-slf4j` | Forwards Log4j 2 API calls to SLF4J; must not be used together with the SLF4J → Log4j 2 bridge in a closed loop |

The examples in this article use the **Log4j 2 API directly** with `log4j-api` and `log4j-core`, so no SLF4J bridge is needed. If your project uses `org.slf4j.Logger` instead of `org.apache.logging.log4j.Logger`, choose **one** provider/binding matching the exact SLF4J version. Avoid installing conflicting forwarding directions or multiple competing backends at the same time.

**Log4j 1.x and Log4j 2 are different.** Legacy `log4j.properties` files or older `log4j.xml` configurations cannot be assumed to work as-is like `log4j2.xml`. You need to know which libraries are actually on the runtime classpath.

### 2.2. Where to Place the File?

In a typical Maven project:

```text
my-app/
├── pom.xml
└── src/
    ├── main/
    │   ├── java/
    │   └── resources/
    │       └── log4j2.xml
    └── test/
        └── resources/
            └── log4j2-test.xml
```

`src/main/resources/log4j2.xml` is placed on the classpath by Maven during packaging. Log4j 2 can automatically locate configuration files based on supported names and formats. `log4j2-test.xml` is a common configuration name for tests, typically taking precedence in test mode when present on the classpath; this allows setting a lighter policy for unit/integration tests.

**There is no need to write custom XML-reading code** using `FileInputStream` just to initialize Log4j 2 in a standard Maven setup. For the sample project in Section 5, the runtime automatically loads `log4j2.xml` from resources unless overridden by another configuration or launch option.

### 2.3. Selecting a Different File at Startup

You can specify the configuration path using Log4j 2's system property:

```bash
java -Dlog4j2.configurationFile=/opt/app/config/log4j2.xml -cp ... com.example.Main
```

This is **illustrative syntax**; `...` must be replaced with the application's actual classpath. When running via Maven, Spring Boot, a container, or another launcher, how JVM properties are passed depends on the launch tool. Do not confuse `-Dlog4j2.configurationFile` with a business key-value pair in a log message.

When multiple files with the same name exist across dependencies or multiple configurations are selected by a launcher, which file gets loaded may differ from expectations. An important check is to **verify which file is actually loaded at runtime**, rather than just looking at the file open in your IDE.

## 3. Minimal Structure of `log4j2.xml`

An easy-to-understand minimal configuration:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<Configuration status="WARN">
    <Appenders>
        <Console name="CONSOLE" target="SYSTEM_OUT">
            <PatternLayout pattern="%level|%logger|%msg%n"
                           charset="UTF-8" />
        </Console>
    </Appenders>

    <Loggers>
        <Root level="info">
            <AppenderRef ref="CONSOLE" />
        </Root>
    </Loggers>
</Configuration>
```

Meaning:

1. **`<Configuration>`:** The root element containing the Log4j 2 configuration. The `status="WARN"` attribute in this example limits internal status messages from the configurator on supported versions. It does **not** set the application-wide business log level.
2. **`<Appenders>`:** Declares output destinations. Here there is one `Console` appender named `CONSOLE`.
3. **`<Console>`:** Selects `target="SYSTEM_OUT"`; `SYSTEM_ERR` can be used when appropriate for the deployment policy.
4. **`<PatternLayout>`:** Determines how an event is formatted into text; `%level`, `%logger`, `%msg`, and `%n` are conversion patterns.
5. **`<Loggers>`:** Declares logger policies, including the root logger and package/class loggers.
6. **`<Root level="info">`:** The default level for loggers that do not have a more specific rule.
7. **`<AppenderRef ref="CONSOLE"/>`:** Connects the root logger to the appender declared with `name="CONSOLE"`.

Having an appender **without attaching an `AppenderRef`** to an appropriate logger does not guarantee records will reach that destination. Conversely, an `AppenderRef` pointing to a non-existent appender name can cause a configuration error.

### Configuration Is Not "A Sequential List of Executable Statements"

XML describes components and the relationships between them. You should not think of Log4j 2 as executing `<Console>`, `<PatternLayout>`, and `<Root>` sequentially like a normal program. The components are built into a runtime configuration, and logging events are then processed through the logger–appender–layout relationships.

## 4. Log Levels and Package-Level Loggers

Common levels in Log4j 2:

```text
TRACE < DEBUG < INFO < WARN < ERROR < FATAL
```

`ALL` and `OFF` are special level settings. If a logger has a threshold of `INFO`, typically `INFO`, `WARN`, `ERROR`, and `FATAL` events are accepted, while `DEBUG` and `TRACE` are not generated on that logger.

Example when more detailed logs are needed for the orders package:

```xml
<Loggers>
    <Logger name="com.example.orders" level="debug" />
    <Logger name="com.example.payments" level="warn" />

    <Root level="info">
        <AppenderRef ref="CONSOLE" />
    </Root>
</Loggers>
```

This is a **snippet of `log4j2.xml`**, and it only works if the `CONSOLE` appender is already declared in the same configuration. It illustrates configuring loggers by package name; other sections like `<Configuration>` and `<Appenders>` are omitted.

In this model:

- `com.example.orders` and loggers with hierarchical names beneath it can log `DEBUG`.
- `com.example.payments` and its child hierarchy only log from `WARN` by default.
- Other loggers use the `INFO` level from root, unless a more specific configuration exists.
- You do not need to declare a `<Logger>` tag for every single class if you want to apply a policy to an entire package.

In Java code, a common choice is to use the class name:

```java
private static final org.apache.logging.log4j.Logger LOG =
        org.apache.logging.log4j.LogManager.getLogger(OrderService.class);
```

This is an illustrative snippet inside the `OrderService` class. If the class has the fully qualified name `com.example.orders.OrderService`, the `com.example.orders` logger configuration can apply by name hierarchy. **The logger structure is based on the logger name string**, not by automatically scanning Java directories or discovering every package in a JAR.

### Source Logger Level and Appender Filter Are Two Separate Layers

A `DEBUG` call can be discarded before an event is even created if the logger does not allow it. Even if an appender has a filter accepting all levels, it cannot emit a record that the source logger already blocked.

Conversely, if the source logger accepts `INFO` but an appender has a filter allowing only `WARN` and above, `INFO` still will not appear at that destination. When investigating "missing logs," check **logger level, logger filter, appender, appender filter, and log collector** in order.

## 5. Standalone Java 17 + Maven Example

Goal: the application logs from `INFO` by default; only the `edu.example.logging.service` package has `DEBUG` enabled. Both loggers write to the console with a pattern without timestamps so the output can be compared deterministically.

Sample project:

```text
log4j2-xml-demo/
├── pom.xml
└── src/
    └── main/
        ├── java/
        │   └── edu/
        │       └── example/
        │           └── logging/
        │               ├── App.java
        │               └── service/
        │                   └── PaymentService.java
        └── resources/
            └── log4j2.xml
```

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0"

    </properties>

    <dependencies>
        <dependency>
            <groupId>org.apache.logging.log4j</groupId>
            <artifactId>log4j-api</artifactId>
            <version>2.23.1</version>

            <groupId>org.apache.logging.log4j</groupId>

    <build>

```

Both Log4j 2 dependencies are set to the **same version**. The pinned versions serve as a reproducible example and **do not represent the latest version or current security update recommendations**. In real-world use, check security advisories and project version compatibility; avoid keeping older Log4j versions with known vulnerabilities.

### 5.2. `src/main/resources/log4j2.xml`

```xml
<?xml version="1.0" encoding="UTF-8"?>
<Configuration status="WARN">
    <Appenders>
        <Console name="STDOUT" target="SYSTEM_OUT">
            <PatternLayout pattern="%level|%c{1}|%msg%n"
                           charset="UTF-8" />
        </Console>
    </Appenders>

    <Loggers>
        <Logger name="edu.example.logging.service"
                level="debug"
                additivity="false">
            <AppenderRef ref="STDOUT" />
        </Logger>

        <Root level="info">
            <AppenderRef ref="STDOUT" />
        </Root>
    </Loggers>
</Configuration>
```

Notes:

- `Logger name="edu.example.logging.service"` selects the service package hierarchy.
- `level="debug"` enables debug logging on this branch.
- `additivity="false"` prevents records from the service branch from being forwarded to parent/root logger appenders.
- **Because additivity is disabled, you must attach a dedicated `AppenderRef` to the service logger** if you want records from this branch to be printed to the console.
- `Root level="info"` keeps the default policy for loggers outside the service branch.
- `%c{1}` shortens the logger name to its rightmost segment, producing `App` or `PaymentService` in the output.
- `%msg` outputs the message after substituting `{}` parameters; `%n` adds a newline.

### 5.3. `src/main/java/edu/example/logging/App.java`

```java
package edu.example.logging;

import edu.example.logging.service.PaymentService;
import org.apache.logging.log4j.LogManager;
import org.apache.logging.log4j.Logger;

public final class App {
    private static final Logger LOG = LogManager.getLogger(App.class);

    private App() {
    }

    public static void main(String[] args) {
        LOG.info("application.started");
        new PaymentService().process("O-17");
        LOG.debug("application.debug_hidden");
    }
}
```

### 5.4. `src/main/java/edu/example/logging/service/PaymentService.java`

```java
package edu.example.logging.service;

import org.apache.logging.log4j.LogManager;
import org.apache.logging.log4j.Logger;

public final class PaymentService {
    private static final Logger LOG =
            LogManager.getLogger(PaymentService.class);

    public void process(String orderId) {
        LOG.debug("payment.prepare order={}", orderId);
        LOG.info("payment.completed order={}", orderId);
        LOG.warn("payment.review order={}", orderId);
    }
}
```

### 5.5. Compile, Run, and Output

Requires JDK 17+ and Maven. From the project directory:

```bash
mvn -q compile exec:java -Dexec.mainClass=edu.example.logging.App
```

**Four log lines emitted by the application code under the sample configuration:**

```text
INFO|App|application.started
DEBUG|PaymentService|payment.prepare order=O-17
INFO|PaymentService|payment.completed order=O-17
WARN|PaymentService|payment.review order=O-17
```

Maven or the runtime environment may print its own messages in addition to these four log lines; the output above represents the expected application events when the sample configuration is loaded.

Explanation:

1. `App` is in package `edu.example.logging`, not under `...service`, so its effective level is `INFO` from root: `application.started` is logged.
2. `PaymentService` is under `edu.example.logging.service`, which has level `DEBUG`: the `payment.prepare` event is accepted, along with the `INFO` and `WARN` events.
3. `application.debug_hidden` belongs to logger `App`, which is filtered out at level `INFO` and therefore not emitted.
4. `additivity="false"` and `AppenderRef ref="STDOUT"` on the service logger cause each service event to be emitted **once** to this appender without propagating up to root.
5. `PatternLayout` formats `%level`, `%c{1}`, and `%msg` into each line's content. The `{}` placeholders in code are substituted before `%msg` outputs the message.

**Try changing it:** If you change `Root level="info"` to `Root level="debug"`, `application.debug_hidden` will appear (assuming no other filter blocks it). If you change the `service` logger from `debug` to `warn`, the `DEBUG` and `INFO` events from `PaymentService` will no longer appear; `WARN` will still be emitted.

**Do not assume XML changes take effect immediately.** Under the default configuration, editing the file does not necessarily cause a long-running process to reload it automatically. You must restart or use a supported configuration monitoring mechanism to apply changes while running.

## 6. `additivity`: A Common Cause of Duplicate or Missing Logs

Log4j 2 loggers have a name-based hierarchy, for example:

```text
Root
  |
  +-- edu.example.logging
         |
         +-- edu.example.logging.service
                 |
                 +-- edu.example.logging.service.PaymentService
```

Events from the class-named logger `...PaymentService` can reach appenders attached to matching logger configurations along the hierarchy path. When **`additivity="true"`** (usually the default), events are forwarded to the appenders of parent logger configurations. When **`additivity="false"`**, forwarding stops at that logger configuration.

Cases:

| Configuration | Possible Outcome |
| --- | --- |
| Service logger has `AppenderRef=STDOUT`, root also has `STDOUT`, additivity=true | An event may be logged **twice** to the same console. |
| Service logger has `AppenderRef=STDOUT`, additivity=false | The event goes to the console through service once. |
| Service logger has no `AppenderRef`, additivity=true | Can use the appender configured on root. |
| Service logger has no `AppenderRef`, additivity=false | Events may **reach no appender at all** and disappear from output. |

**Setting `additivity=false` is not a universal fix for duplicates.** It can also inadvertently block a shared collection channel. When duplicates occur, inspect every appender, parent logger, route, and collector. An event sent to **two different destinations** is intentional fan-out, not automatically a bug.

### Does Root's Log Level Re-filter Events from Child Loggers?

In hierarchical Log4j 2 configurations, the **determined level of the source logger** decides whether an event is created/logged; forwarding to root's appenders via additivity **does not automatically re-apply Root's level threshold as a second filter**.

For example: logger `com.example.orders` is set to `DEBUG`, root is at `INFO`, and only root has a Console appender. `DEBUG` events accepted by the child logger can still appear on root's console through additivity. If you want the console to receive only `WARN` and above regardless of source, you must configure a filter on the appropriate appender or appender reference.

## 7. Appenders and Layouts: Destinations vs. Formatting

`<Appenders>` defines where logs are sent. An appender can use a layout to format events. Common choices:

| Appender | Purpose |
| --- | --- |
| `Console` | Writes to stdout or stderr; typically suitable for containers and development environments. |
| `File` | Writes to a fixed file; has no built-in rotation policy. |
| `RollingFile` | Writes to a file and rotates based on size/time policies. |
| `AsyncAppender` | Pushes events through a queue to referenced appenders; has operational trade-offs around buffering and data loss. |
| Other appenders | Connect to specialized destinations depending on installed modules and dependencies. |

Example of a readable console configuration:

```xml
<Console name="CONSOLE" target="SYSTEM_OUT">
    <PatternLayout
        pattern="%d{yyyy-MM-dd'T'HH:mm:ss.SSSXXX} %-5level [%thread] %logger - %msg%n%ex"
        charset="UTF-8" />
</Console>
```

This is only a **snippet inside `<Appenders>`**, not a standalone configuration. The pattern includes timestamp, level, thread, logger name, message, and exception. For operational data, a timestamp with date and timezone offset helps correlate across multiple systems; the Java example in Section 5 intentionally omits timestamps to make stdout verification easier.

Common conversion words:

- `%d{...}`: Event timestamp formatted according to the date-time pattern.
- `%level` or `%p`: Log level.
- `%thread` or `%t`: Thread name.
- `%logger` or `%c`: Logger name; `%c{1}` takes the shortened name segment.
- `%msg` or `%m`: Message after parameter substitution.
- `%X{trace_id}`: MDC/ThreadContext value if present.
- `%ex`, `%throwable`: Exception details if the event has a cause/throwable.
- `%n`: Newline character.

XML pattern attributes do not use `printf` syntax; `{}` parameter substitution in the Log4j 2 API happens at the message level, and `%msg` is how the layout renders that message.

### Choosing Charset and Event Boundaries

Set `charset="UTF-8"` consistently with whatever reads the logs to avoid corrupting Unicode characters (such as Vietnamese text). For text console/file output, `%n` generally separates records by line; however, a message or stack trace can still contain **embedded newlines**, so a collector assuming "one line = one event" needs multiline support or an appropriate structured format.

A `PatternLayout` that manually concatenates strings to look like JSON can break when values contain quotes, backslashes, or control characters. For true JSON, use an appropriate JSON layout/encoder and verify the output by parsing it, not just by eyeballing curly braces.

## 8. Writing Files and Rotating with `RollingFile`

Long-running applications may need to write to files and cap disk growth. Illustrative configuration snippet inside `<Appenders>`:

```xml
<RollingFile
    name="ROLLING"
    fileName="logs/application.log"
    filePattern="logs/application-%d{yyyy-MM-dd}-%i.log.gz">

    <PatternLayout
        charset="UTF-8"
        pattern="%d{ISO8601} %-5level %logger - %msg%n%ex" />

    <Policies>
        <TimeBasedTriggeringPolicy interval="1" modulate="true" />
        <SizeBasedTriggeringPolicy size="10 MB" />
    </Policies>

    <DefaultRolloverStrategy max="7" />
</RollingFile>
```

You also need to attach it in `<Loggers>` when actually using it:

```xml
<Root level="info">
    <AppenderRef ref="ROLLING" />
</Root>
```

These are **two configuration snippets** illustrating only the appender and its reference; do not paste them directly into the sample `log4j2.xml` from Section 5 while keeping a second `Root` element. To extend the sample, replace the existing `Root` or add an `AppenderRef` inside it.

Attributes:

- `fileName`: The active file currently receiving log records.
- `filePattern`: Naming pattern for rotated files; here it includes the date, index `%i`, and `.gz` compression suffix.
- `TimeBasedTriggeringPolicy`: Rotates based on time according to Log4j 2's mechanism.
- `SizeBasedTriggeringPolicy`: Triggers when the size condition is reached.
- `DefaultRolloverStrategy max="7"`: Limits the rollover counter index per Log4j 2's strategy; **it does not automatically guarantee keeping only seven days of logs**.

If you need a policy to delete old logs by age, total disk size, or compliance requirements, you must configure and test an appropriate retention mechanism. `RollingFile` does not automatically guarantee that all data has been backed up or shipped to a central store.

In containers, writing files to an ephemeral filesystem can lose data when containers are replaced. For many deployments, **writing JSON/text to stdout and letting a collector gather it** is easier to operate than managing files inside every application; the choice depends on the actual architecture.

## 9. Properties and Changing Configuration Across Environments

An application often needs different log levels across local, staging, and production. Factors that may vary:

- Root level (`INFO` or `WARN`).
- Level for a package under investigation (`DEBUG`).
- File storage paths and rolling policies.
- Console or collector destination.
- Display pattern and security policies.

Log4j 2 supports **property substitution** in configuration, using reference syntax such as `${sys:demo.logLevel}` or `${env:APP_ENV}` in appropriate contexts.

Example XML snippet using a JVM system property:

```xml
<Root level="${sys:demo.logLevel}">
    <AppenderRef ref="CONSOLE" />
</Root>
```

When using this snippet, you must **declare and attach the `CONSOLE` appender** as in previous examples, and pass a valid value, for example:

```bash
java -Ddemo.logLevel=debug -cp ... com.example.Main
```

These are **illustrative configuration and command snippets**, not a complete runnable command. Do not expect the configuration to work properly if the property is missing, misspelled, or contains an unsupported level. For production, use valid default values or tested configuration validation.

### Should Everything Be Put in Environment Variables?

No. Environment variables and system properties are suitable for non-sensitive configuration values such as log levels or file paths. Do not put passwords, access tokens, or secrets into log patterns or status output just because the configuration system allows variable lookups.

For `PatternLayout`, if you need a consistent pattern across multiple appenders, you can declare a property in `<Properties>` and reference it in the layouts. Using properties does not change Logger/Appender/Layout semantics; it only reduces duplication and lowers the risk of mistakes when updating configuration.

### Environment-Specific Configuration Files

You can use a different configuration file per environment via startup options, or the same file with controlled properties. Some frameworks (such as Spring Boot) have their own conventions and configuration extensions; **do not assume a plain Log4j 2 `log4j2.xml` is equivalent to every framework-specific configuration file**. When using a framework, check the selected backend, configuration path, and initialization order.

## 10. Reloading Configuration Automatically When the File Changes

Log4j 2 supports monitoring and reloading configuration in appropriate scenarios. Example:

```xml
<Configuration status="WARN" monitorInterval="30">
    <!-- Appenders and Loggers as in a normal configuration -->
</Configuration>
```

With this mechanism, Log4j 2 can check the configuration source for changes periodically—every 30 seconds in this example—**when the monitored configuration source is accessible and supports monitoring**. This is not a guarantee that every edit in an IDE or inside a JAR will be reloaded immediately.

Notes:

1. Verify that the configuration source is a watchable file in the deployment environment; resources packaged inside a JAR or dynamically generated configurations behave differently.
2. Reloading can affect active appenders, files, queues, or connection threads; test it before relying on it in production.
3. Editing `log4j2.xml` in source code **does not mean** the file inside the running JVM has changed; you need to build/copy/deploy it.
4. When temporarily increasing log verbosity, have a plan to return levels to normal; excessive `DEBUG` logging can increase disk usage, CPU load, and data exposure risk.

In most cases, **restarting with the new configuration file and verifying the output** is easier to control than relying on untested auto-reload.

## 11. Filters and Avoiding False Alerts

A `Filter` decides whether an event is accepted, denied, or passed along based on context. Log4j 2 allows configuring filters at multiple levels; where a filter is placed determines its scope.

Example of a console appender that **only accepts `WARN` and above**:

```xml
<Console name="WARN_CONSOLE" target="SYSTEM_OUT">
    <ThresholdFilter
        level="warn"
        onMatch="ACCEPT"
        onMismatch="DENY" />
    <PatternLayout pattern="%level|%c{1}|%msg%n"
                   charset="UTF-8" />
</Console>
```

This snippet belongs inside `<Appenders>`. To receive events, a logger or root must reference `WARN_CONSOLE`. If the source logger is set to `INFO`, it can create `INFO` events, but the appender above will still drop events below `WARN`.

Distinguish between:

- **Logger level:** Restricts events right at the source.
- **Filter attached to a logger:** Applies custom rules at the logger beyond just the level.
- **Filter attached to an appender:** Affects a single output channel.
- **Filter on `AppenderRef`:** Applies when a logger configuration sends events to a referenced destination.
- **Configuration-wide filter:** Can affect multiple components depending on placement and filter type.

For example, if you need a file to store all `INFO` logs while an alert channel only receives `ERROR`, configure two appenders and place the filter on the **alert channel**, rather than raising Root to `ERROR` and losing `INFO` data in the general channel.

**Log levels do not replace an alerting mechanism.** A single `ERROR` line may not warrant waking an on-call engineer; alerts typically need to evaluate failure rates, sample counts, duration, and business impact.

## 12. Throwables, Stack Traces, and Parameterized Messages

In the Log4j 2 API, passing a `Throwable` properly gives the layout the data needed to print a stack trace:

```java
try {
    gateway.charge(orderId);
} catch (GatewayException failure) {
    logger.error("event=payment.failed order_id={}", orderId, failure);
    throw failure;
}
```

This is **illustrative code**; `gateway`, `GatewayException`, `logger`, and `orderId` belong to a real application, not a standalone program. Place logging where responsibility for determining the final outcome lies, and avoid logging the same exception at every layer before rethrowing it.

When a `Throwable` is present, the pattern can use `%ex` or `%throwable` to render the exception. Avoid logging only `failure.getMessage()` when you need the exception type, cause chain, and stack trace.

Key points:

- **Message vs. Throwable:** `%msg` is primarily the message text; `Throwable` information must be preserved by the backend and emitted according to configuration.
- **Exceptions can contain secrets:** Exception messages and stack traces may include URLs with tokens, SQL queries, or input data. Sanitize sensitive data before logging.
- **Appropriate levels:** A transient error that retries and succeeds is not necessarily an `ERROR`; a final failed outcome usually belongs at `ERROR`. When Log4j 2 uses `FATAL`, it is specific to this API/backend, not a level provided by every Java logging library.
- **Do not count `ERROR` lines as failed request counts:** Retries, multi-layer logging, and collector redeliveries can create duplicates; logs can also be lost.

A pattern containing timestamps and exceptions should be tested with real errors in staging to ensure operators see useful root causes without exposing secrets.

## 13. Structured Logging: JSON, ThreadContext, and Correlation IDs

Plain text such as:

```text
INFO|PaymentService|payment.completed order=O-17
```

is human-readable, but analysis systems must parse the message string to query `order_id` separately. With structured logging, each attribute can live in its own field:

```json
{
  "timestamp": "2026-01-01T10:15:30Z",
  "level": "INFO",
  "service": "checkout",
  "event_code": "payment.completed",
  "order_id": "O-17",
  "trace_id": "tr-42",
  "message": "Thanh toán hoàn tất"
}
```

This is an **example of the desired output structure**, not JSON automatically produced by the sample `PatternLayout`.

Log4j 2 supports multiple layouts and related modules, including JSON logging options. Common choices include `JsonLayout` in Log4j Core or `JsonTemplateLayout` in its corresponding module when the dependency is declared. Exact syntax and emitted fields depend on the layout, version, and configuration; **do not assume that simply swapping `PatternLayout` for a JSON layout name will make all business fields appear automatically in the output**.

With the Log4j 2 API, `ThreadContext` can attach context across a series of events:

```java
import org.apache.logging.log4j.ThreadContext;

try {
    ThreadContext.put("trace_id", "tr-42");
    logger.info("event=order.created");
} finally {
    ThreadContext.remove("trace_id");
}
```

This is an **illustrative snippet** inside a method that has a `logger` variable. Text configurations can read this context via `%X{trace_id}`. With asynchronous processing or thread pools, verify context propagation and proper cleanup so a previous request's `trace_id` never "leaks" into the next request.

**Watch out for cardinality:** `trace_id` and `order_id` are valuable for tracing a single event, but they should not be used as labels on aggregated metrics because the number of distinct values can grow too large. For dashboards, fields such as `event_code` and `error_code` are usually better for grouping when they come from a bounded set.

## 14. Security and Performance Considerations

### 14.1. Configuration Security

- **Do not trust XML from untrusted sources:** Plugin loading, lookups, and output paths can affect the application. Production configuration files should be managed as deployment artifacts with restricted write permissions.
- **Keep Log4j 2 updated:** Avoid older versions with publicly disclosed security vulnerabilities; consult official security advisories when choosing real dependencies. A configuration file cannot compensate for bugs in the underlying library.
- **Never log secrets:** Passwords, session tokens, API keys, card data, sensitive request/response bodies, and certain exception values must not be emitted across destinations just because a pattern prints them.
- **Restrict permissions on log files:** The `logs/` directory, file permissions, retention, backups, collector read access, and search UI access controls are all separate concerns outside the XML file.
- **Limit overly verbose configuration logging:** The status logger or internal diagnostics can expose paths and configuration details; enable them only in a controlled manner.

### 14.2. Performance and Reliability

- Enabling `DEBUG` on a hot path can increase CPU, memory, and I/O usage; use package-level settings when investigating a specific component.
- `PatternLayout` formats timestamps, threads, loggers, and exceptions for every event; stack traces in particular can be very large. Choose useful fields and avoid redundant logging.
- Synchronous appenders can increase latency if output is slow. Asynchronous appenders can reduce wait time, but they introduce queues, capacity limits, and potential log loss if the JVM terminates abruptly.
- Returning from `logger.info(...)` **does not prove the data has reached a central store**; monitor collectors, queues, shipping errors, and storage health.
- In container environments, stdout/stderr are usually collected by the platform. If routing to local files, ensure a corresponding file-reading mechanism is in place.
- For audit or business events that require guaranteed delivery, design a dedicated reliable mechanism; standard logging does not guarantee exactly-once delivery.

## 15. Troubleshooting When `log4j2.xml` Has No Effect

If editing the XML does not change the logs as expected, check in order:

```text
(1) Is the application using Log4j 2 Core?
        |
        +-- No -> Check backend, provider, bridge, dependencies.
        |
        +-- Yes -> (2) Is the right log4j2.xml being loaded?
                         |
                         +-- No -> Check classpath,
                         |          filename, config path,
                         |          test config, or launcher.
                         |
                         +-- Yes -> (3) Does the logger level/filter accept it?
                                      |
                                      +-- No -> Check logger name and level.
                                      |
                                      +-- Yes -> (4) Is AppenderRef attached?
                                                   |
                                                   +-- No -> Fix Loggers.
                                                   |
                                                   +-- Yes -> (5) Are Appender/filter/layout working?
                                                                |
                                                                +-- No -> Check status log,
                                                                |          file permissions, path.
                                                                |
                                                                +-- Yes -> (6) Is the Collector/GUI receiving it?
                                                                             |
                                                                             +-- No -> Check stream,
                                                                             |          parser, index,
                                                                             |          time, permissions.
```

### Common Failure Symptoms

| Symptom | Possible Cause | How to Check |
| --- | --- | --- |
| Edited `log4j2.xml` but output did not change | File is not on the runtime classpath, overridden by another config, or not reloaded | Identify the actually loaded file, build/packaging steps, and JVM options. |
| No logs at all | Missing `log4j-core`, XML syntax error, unattached appender, or level set too high | Check dependencies, status output, and logger → appender wiring. |
| `DEBUG` is hidden despite low root level | Specific logger sets a higher level, filter blocks it, or another backend is active | Check the effective logger name and active filters. |
| A line appears twice | Same appender on both child and root with additivity, or collector resending | Trace the routing path and count at each destination. |
| Service branch logger produces nothing | `additivity=false` without an `AppenderRef` | Attach an appropriate appender or reconsider propagation. |
| Missing stack trace | Throwable not passed, layout does not render it, or collector drops multiline logs | Check the logging API call, pattern, and pipeline. |
| Corrupted Vietnamese/Unicode text | Mismatched charset between encoder, collector, and viewer | Use UTF-8 end-to-end. |
| File not created | Path, write permissions, directory, `RollingFile` config, or unreferenced appender | Check status logs and runtime environment. |
| File does not rotate or wrong retention | Policy/`filePattern` or rollover strategy differs from expectations | Test actual rollover and configure retention separately. |
| Logs lost during shutdown | Async queue or collector not flushed; process exits too quickly | Check shutdown policy and transport behavior. |
| Structured logs cannot be queried by field | JSON layout not emitting the field or collector not parsing it | Inspect raw output bytes and collector mapping. |
| Different behavior between test and production | `log4j2-test.xml`, system properties, or framework startup differences | Compare runtime classpath, launch config, and filenames. |

### Viewing Internal Configuration Errors

You can enable Log4j 2's diagnostic mode in an appropriate environment, such as passing the system property `-Dlog4j2.debug=true` when starting the JVM to get more configuration status output. Do not leave internal debug mode running long-term in production unnecessarily, as it can increase output volume and reveal infrastructure details. Control who has access to those status lines.

**Do not scatter `System.out.println` across every service to "fix" logging.** If configuration is not loading, verify the backend and classpath instead of replacing the logging architecture with ad-hoc print statements.

## 16. Testing Configuration Changes

For each change, maintain a **logger name × level × destination** matrix and a set of sample events:

| Logger | Event | Expected Under Section 5 Config |
| --- | --- | --- |
| `edu.example.logging.App` | `INFO application.started` | Emitted once to `STDOUT` |
| `edu.example.logging.App` | `DEBUG application.debug_hidden` | Blocked |
| `edu.example.logging.service.PaymentService` | `DEBUG payment.prepare` | Emitted once to `STDOUT` |
| `edu.example.logging.service.PaymentService` | `INFO payment.completed` | Emitted once to `STDOUT` |
| `edu.example.logging.service.PaymentService` | `WARN payment.review` | Emitted once to `STDOUT` |

You can use an integration test that runs the application with a dedicated `log4j2.xml`, captures stdout, and checks lines for stable `event_code` or message values. If the pattern includes timestamps or dynamic thread names, avoid exact full-line string comparisons; parse or assert on the relevant fields instead.

For file/JSON logging, also test:

1. The file/destination actually exists and the process has write permissions.
2. Bytes are decoded with the chosen charset and Unicode messages are intact.
3. Each event has proper boundaries and stack traces/multiline messages are handled.
4. JSON (if used) parses cleanly and contains the expected level, timestamp, service, and context fields.
5. Synthetic sensitive data does not appear at any destination.
6. No duplicate logs appear on the same channel when appenders exist on both child and parent loggers.
7. When using rolling files, `filePattern` and retention behave according to policy.
8. On configuration error during startup/reload, operations receive a diagnostic signal.

In unit tests, avoid mutating shared logger configurations across parallel tests without isolation. Restore the logger context/appenders after each test so other tests are not affected.

## 17. Self-Check Exercises

### Exercise 1 — Analyzing Configuration

Suppose:

```xml
<Appenders>
    <Console name="A" target="SYSTEM_OUT">
        <PatternLayout pattern="%level|%msg%n" />
    </Console>
</Appenders>

<Loggers>
    <Logger name="com.example.orders"
            level="debug"
            additivity="false">
        <AppenderRef ref="A" />
    </Logger>

    <Root level="info">
        <AppenderRef ref="A" />
    </Root>
</Loggers>
```

These are snippets **inside `<Configuration>`**, not a standalone XML file.

Questions:

1. Will a `DEBUG` call from `com.example.orders.OrderService` appear on the console?
2. Will a `DEBUG` call from `com.example.payments.PaymentService` appear on the console?
3. Will an `INFO` call from `com.example.orders.OrderService` be logged twice because root also references A?
4. If `<AppenderRef ref="A" />` is removed from the orders logger while keeping `additivity="false"`, what happens?

**Answers:**

1. Yes, the orders branch enables `DEBUG` and has appender A.
2. No, the payments logger uses root's `INFO` threshold.
3. No, because `additivity=false` on the orders logger configuration stops forwarding to root.
4. Logs in the orders branch may not go to A or any appender at all, because the path to root was cut off. This is a serious configuration mistake when changing appenders.

### Exercise 2 — Debugging Missing `DEBUG` Logs

The application sets root to `INFO` and package `com.example.orders` to `DEBUG`, yet operators still do not see `DEBUG` on the console. List at least four places to check.

**Hint:** Does the logger name in code actually start with `com.example.orders`? Is the expected XML file being loaded? Is the appender receiving events from that logger? Is an appender/filter blocking `DEBUG`? Is the backend actually Log4j 2 Core? Is the collector/UI filtering out `DEBUG` events?

### Exercise 3 — Designing Two Channels

Requirement: the stdout channel receives `INFO` and above for all services; a dedicated file receives `WARN` and above for the payments package. Propose a logger/appender structure.

**Hint:** Set Root to `INFO` attached to Console. Declare a separate `File`/`RollingFile` appender with a `WARN` filter. Configure logger `com.example.payments` with an `AppenderRef` to the file and keep additivity enabled so records continue to root/console. Pay attention to the file's filter, the source logger's level, and preventing duplicate writes to the same channel. Verify output with an `INFO`/`WARN`/`ERROR` matrix across multiple packages.

### Exercise 4 — Valid XML, No Effect in the App

After editing `src/main/resources/log4j2.xml`, a running process still logs in the old format. Explain why and choose verification steps before concluding that Log4j 2 does not support the configuration.

**Hint:** The file in source is not the file the process is using; a build/redeploy may be required, a `log4j2-test.xml` file or system property may take precedence, and monitoring/reload may not be enabled or may not work for the loaded source type. Check the classpath, loaded configuration, and lifecycle before touching business code.

### Exercise 5 — Log File Handling and Security

A service logs a payment token inside `%msg` and uses both Console and RollingFile. If you only strip the token on the console, is the issue resolved safely?

**Hint:** No. Every appender can emit data from the same event. You must prevent secrets from entering the event in code in the first place, and check every encoder/layout, file, collector, read permission, and retention policy. Having parameter substitution or patterns does not mean data is automatically masked.

### Exercise 6 — Explaining Configuration Limits

Why does `<Root level="error">` not guarantee that every business error is recorded, and why is seeing `ERROR` in logs insufficient for calculating HTTP error rates?

**Hint:** Root `ERROR` only filters events emitted by code that meet the criteria; code might not log an error, or events might be blocked/lost along the logging pipeline. A single request might produce multiple `ERROR`s due to retries or duplicate logging, while HTTP 5xx responses might be returned by a proxy before the application ever logs anything. Error-rate calculations require reliable request-completion metrics and a clear denominator.

**Conclusion:** Understanding `log4j2.xml` means tracing the path **`Logger → level/filter → AppenderRef → Appender → Layout → output`**, identifying the real runtime configuration file, configuring by package, avoiding duplicate or lost logs from additivity, verifying charset/Throwable/rolling behavior, and testing configurations with sample events that have predictable outcomes.
