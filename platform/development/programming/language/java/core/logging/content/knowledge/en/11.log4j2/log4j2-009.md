# Log4j2 Bridges in Java Logging: Forwarding Direction, Configuration, and Avoiding Loops

A **Log4j2 bridge (Log4j 2 bridge/adapter)** is a component that enables an application or library using one **logging API** to send events to another **logging implementation**, without modifying every log call in the source code. For example, code written with SLF4J can be handled by Log4j 2 Core; or code written directly with the Log4j 2 API can forward events to SLF4J and then to Logback.

The most important point: **bridges are directional**. `log4j-slf4j2-impl` and `log4j-to-slf4j` **do not do the same thing**. Choosing the wrong direction or putting two opposing bridges into the same runtime can create a circular forwarding route, causing logging errors or initialization failures.

This lesson focuses on **Log4j 2** and explains APIs, bridges, backends, dependency selection, a Java 17+ example with Maven, how to verify actual logs, and common configuration mistakes.

## 1. Why Are Logging Bridges Needed?

Java applications often use multiple libraries:

- Application code may call `org.slf4j.Logger`.
- Another library calls `org.apache.logging.log4j.Logger` from the Log4j 2 API.
- An older library uses `java.util.logging.Logger` (JUL).
- Some components use Apache Commons Logging (JCL) or Java Platform Logging.

If each API uses an independent backend, the application can end up with **multiple ways of setting levels, multiple formatters, multiple destinations, and multiple configuration files**, making operations difficult. A bridge creates a forwarding direction so that the necessary events can be handled by a **deliberately chosen primary backend**.

```text
Different logging APIs
    |
    +-- SLF4J ----------------------+
    +-- JUL ------------------------+--> appropriate bridge --> Log4j 2 API --> Log4j Core --> appender
    +-- Apache Commons Logging ----+
    +-- Log4j 2 API -------------------------------- direct ---------+
```

This diagram shows the **model with Log4j 2 Core as the final destination**. If the application chooses **Logback as the primary backend**, the path is reversed on the Log4j 2 API branch:

```text
Log4j 2 API --> log4j-to-slf4j --> SLF4J --> Logback --> appender
SLF4J ----------------------------------------^
```

In both cases, **the application does not need to initialize two backends managing the same event**. Choose one primary processing destination, then add the necessary adapters to route the remaining APIs to that destination.

### Easily Confused Terms

| Component | Function | Examples |
| --- | --- | --- |
| **Logging API** | Interfaces/calls that Java code directly uses | Log4j 2 API, SLF4J API, JUL API |
| **Backend/implementation** | Processes events and output configuration | Log4j Core, Logback, JUL |
| **Bridge/adapter** | Receives events from one API and forwards them to another API | `log4j-slf4j2-impl`, `log4j-to-slf4j` |
| **Appender/handler** | Dispatches events after the backend to the output destination | Log4j Console/RollingFile, JUL ConsoleHandler |
| **Facade** | API that decouples application code from the backend | SLF4J, Log4j API in the separated API/Core design |

**A bridge is not an appender.** A bridge answers the question "if code calls API A, can backend B receive it?"; an appender answers "once an event reaches the backend, which console, file, or collector is it sent to?".

## 2. Important Log4j 2 Forwarding Direction Table

| Logging API | Desired Processing Destination | Commonly Used Artifact/Bridge | Notes |
| --- | --- | --- | --- |
| **SLF4J 2.x** | Log4j 2 API → Log4j Core | `log4j-slf4j2-impl` | Configure output using Log4j 2 |
| **SLF4J 1.7.x** | Log4j 2 API → Log4j Core | `log4j-slf4j-impl` | For older SLF4J branches; do not use as a substitute for the 2.x adapter |
| **Log4j 2 API** | SLF4J → backend such as Logback | `log4j-to-slf4j` | **Opposite direction** from the two artifacts above |
| **JUL** | Log4j 2 API → Log4j Core | `log4j-jul` | Usually requires configuring `java.util.logging.manager` early at JVM startup |
| **Apache Commons Logging (JCL)** | Log4j 2 API → Log4j Core | `log4j-jcl` | Consider the JCL version and existing logging environment |
| **Legacy Log4j 1.x API** | Log4j 2 API/Core | `log4j-1.2-api` | Compatibility layer during migration; does not guarantee 100% of all legacy APIs |

The artifact names belong to the **Apache Log4j 2** group. Exact dependencies, Maven/Gradle scopes, and support for legacy APIs must be verified against your system version. This table does not mean every application must install all of these bridges: **only add the API branches that are actually used**.

### Two Safety Rules to Remember

1. **When Log4j Core is chosen as the backend:** receive SLF4J 2.x via `log4j-slf4j2-impl`; do not add `log4j-to-slf4j`.
2. **When Logback is chosen as the backend:** receive Log4j 2 API calls via `log4j-to-slf4j`; do not add `log4j-slf4j2-impl` or `log4j-slf4j-impl`.

Do not place `log4j-slf4j2-impl` and `log4j-slf4j-impl` into the runtime at the same time to "support both versions": the two SLF4J branches have different API requirements; choose based on the existing SLF4J version and resolve the dependency tree consistently.

## 3. Model A: SLF4J 2.x → Log4j 2 Core

This is a common case when business code or libraries call SLF4J, but you want **Log4j 2 Core** to be responsible for writing logs.

```text
OrderService uses SLF4J API
          |
          | LoggerFactory.getLogger(...)
          | LOG.info(...)
          v
      SLF4J 2.x
          |
          | log4j-slf4j2-impl
          v
      Log4j 2 API
          |
          v
      Log4j 2 Core
          |
          +--> ConsoleAppender
          +--> RollingFileAppender
```

Typical dependencies include `slf4j-api`, `log4j-slf4j2-impl`, `log4j-api`, and `log4j-core` (some artifacts may be pulled in via transitive dependencies). To manage versions, use the **Log4j BOM** or your framework's dependency management. Simply adding `log4j-slf4j2-impl` **does not replace a fully configured backend/implementation** if you expect Log4j Core to write to files/console.

Example application code using SLF4J:

```java
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public final class OrderService {
    private static final Logger LOG =
            LoggerFactory.getLogger(OrderService.class);

    public void create(String orderId) {
        LOG.info("event=order_created orderId={}", orderId);
    }
}
```

This is an **illustrative class** without `main` and requires the SLF4J dependency. The class does not import `log4j-core` or know appender names. If you switch backends in the future, code using the SLF4J API can remain unchanged in many cases.

A library using the Log4j 2 API directly can also send logs to **Log4j Core itself** without going through a bridge:

```java
// Fragment in a class with a Log4j API dependency.
private static final org.apache.logging.log4j.Logger LOG =
        org.apache.logging.log4j.LogManager.getLogger(OrderService.class);
```

If both APIs send to Log4j Core, configure levels, layouts, and appenders in **Log4j 2** for consistent results.

## 4. Java 17 + Maven Example: Two APIs Writing Through Log4j Core

This example clarifies the mechanism with a program using **two APIs**:

- `org.slf4j.Logger` is bridged to Log4j 2 via `log4j-slf4j2-impl`.
- `org.apache.logging.log4j.Logger` goes directly to Log4j 2.
- A `Console` appender writes to **stderr** with a fixed pattern for reading the output.

The program runs with **JDK 17 and Maven**. Versions are pinned for a concrete example, **not as a claim of the latest version**.

Project structure:

```text
log4j2-bridge-demo/
├── pom.xml
└── src/main/
    ├── java/com/example/logging/Log4j2BridgeDemo.java
    └── resources/log4j2.xml
```

### 4.1. `pom.xml`

```xml
<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>

    <groupId>com.example</groupId>
    <artifactId>log4j2-bridge-demo</artifactId>
    <version>1.0.0</version>

    <properties>
        <maven.compiler.release>17</maven.compiler.release>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
        <log4j.version>2.26.1</log4j.version>
    </properties>

    <dependencyManagement>
        <dependencies>
            <dependency>
                <groupId>org.apache.logging.log4j</groupId>
                <artifactId>log4j-bom</artifactId>
                <version>${log4j.version}</version>
                <type>pom</type>
                <scope>import</scope>
            </dependency>
        </dependencies>
    </dependencyManagement>

    <dependencies>
        <dependency>
            <groupId>org.slf4j</groupId>
            <artifactId>slf4j-api</artifactId>
            <version>2.0.17</version>
        </dependency>
        <dependency>
            <groupId>org.apache.logging.log4j</groupId>
            <artifactId>log4j-api</artifactId>
        </dependency>
        <dependency>
            <groupId>org.apache.logging.log4j</groupId>
            <artifactId>log4j-core</artifactId>
            <scope>runtime</scope>
        </dependency>
        <dependency>
            <groupId>org.apache.logging.log4j</groupId>
            <artifactId>log4j-slf4j2-impl</artifactId>
            <scope>runtime</scope>
        </dependency>
    </dependencies>

    <build>
        <plugins>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-compiler-plugin</artifactId>
                <version>3.13.0</version>
            </plugin>
            <plugin>
                <groupId>org.codehaus.mojo</groupId>
                <artifactId>exec-maven-plugin</artifactId>
                <version>3.5.0</version>
                <configuration>
                    <mainClass>com.example.logging.Log4j2BridgeDemo</mainClass>
                    <classpathScope>runtime</classpathScope>
                </configuration>
            </plugin>
        </plugins>
    </build>
</project>
```

**POM Check:** `log4j-bom` pins the versions of `log4j-api`, `log4j-core`, and `log4j-slf4j2-impl` to the same branch. `slf4j-api` is declared separately because the Log4j BOM does not necessarily manage the SLF4J version. The `${log4j.version}` string in the POM is **Maven property interpolation**, with no backslashes in the actual XML content.

### 4.2. `log4j2.xml`

Place the file at `src/main/resources/log4j2.xml`:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<Configuration status="WARN">
    <Appenders>
        <Console name="Console" target="SYSTEM_ERR">
            <PatternLayout pattern="%level | %logger - %msg%n"/>
        </Console>
    </Appenders>
    <Loggers>
        <Root level="info">
            <AppenderRef ref="Console"/>
        </Root>
    </Loggers>
</Configuration>
```

This file uses **Log4j 2** syntax (not `logback.xml`). `Root level="info"` accepts INFO and above. `PatternLayout` intentionally omits the timestamp for easier verification; real-world deployments should include a timestamp with timezone and tracing context.

### 4.3. `Log4j2BridgeDemo.java`

```java
package com.example.logging;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public final class Log4j2BridgeDemo {
    private static final Logger SLF4J_LOG =
            LoggerFactory.getLogger(Log4j2BridgeDemo.class);

    private static final org.apache.logging.log4j.Logger LOG4J_LOG =
            org.apache.logging.log4j.LogManager.getLogger(
                    "com.example.logging.native");

    public static void main(String[] args) {
        System.out.println("slf4jName=" + SLF4J_LOG.getName());

        SLF4J_LOG.info("source=slf4j event=accepted id={}", "req-17");
        LOG4J_LOG.warn("source=log4j2 event=retry attempt={}", 2);

        System.out.println("completed=true");
    }
}
```

The class uses SLF4J for the first event and the Log4j API for the second event; it does **not** call both APIs for the same event, so there is no duplicate logging caused by source code. Both APIs can flow to the same configured Log4j 2 `Console` appender.

### 4.4. Running and Verifying

In the directory containing `pom.xml`:

```bash
mvn -q compile exec:java
```

**Stdout lines printed by the program, in exact order:**

```text
slf4jName=com.example.logging.Log4j2BridgeDemo
completed=true
```

**Logging lines from the application on stderr, matching the pattern:**

```text
INFO | com.example.logging.Log4j2BridgeDemo - source=slf4j event=accepted id=req-17
WARN | com.example.logging.native - source=log4j2 event=retry attempt=2
```

The Maven plugin or runtime environment may print its own build information; if the terminal merges stdout and stderr, **the interleaving order between the two streams is not guaranteed**. The result to verify is that both the SLF4J logger and the Log4j API logger are written **by the same Log4j 2 PatternLayout** with one line per event.

If you remove the `log4j-slf4j2-impl` provider from the runtime without replacing it with another SLF4J provider, the `SLF4J_LOG.info(...)` call will no longer be received by Log4j Core via this path; SLF4J 2.x may warn that no provider was found and fall back to a NOP logger. Conversely, the Log4j API call will still reach Log4j Core. This is how to distinguish a **missing bridge** from a **misconfigured appender**.

## 5. Model B: Log4j 2 API → SLF4J → Logback

An application using **Logback as its primary backend** may depend on a library that emits logs through the Log4j 2 API. You want to keep Logback's configuration and appenders, without initializing a separate Log4j Core just to log from that library.

In that case:

```text
Library using Log4j API
           |
           v
      log4j-to-slf4j
           |
           v
         SLF4J
           |
           v
   Logback (primary backend)
           |
           +--> ConsoleAppender / RollingFileAppender
```

Typical components include `log4j-api`, `log4j-to-slf4j`, `slf4j-api`, and an SLF4J backend such as `logback-classic`, with **compatible versions**. Do not install `log4j-core` just to "combine" them if the goal is to route all events to Logback; do not install `log4j-slf4j2-impl` in this configuration.

**Library code does not necessarily need to change:**

```java
// Fragment inside a library that already uses the Log4j 2 API.
private static final org.apache.logging.log4j.Logger LOG =
        org.apache.logging.log4j.LogManager.getLogger(LibraryWorker.class);
```

With `log4j-to-slf4j`, Log4j API calls are forwarded to SLF4J, and then handled by the Logback backend. `LibraryWorker` here is an illustrative class; the fragment does not run standalone.

In Spring Boot, `spring-boot-starter-logging` typically provides Logback and the adapters needed for Boot's default configuration. If switching the application to `spring-boot-starter-log4j2`, you must review dependencies and exclude conflicting bridges/providers rather than simply adding the new starter on top of the old one. Do not assume every Boot version has the same dependency tree.

## 6. Why Must Opposing Bridges Not Be Installed Together?

This is the most serious mistake in this topic:

```text
SLF4J API
   |
   | log4j-slf4j2-impl
   v
Log4j 2 API
   |
   | log4j-to-slf4j
   v
SLF4J API
   |
   +--> back to Log4j 2 API, ...
```

The two adapters above create a **circular forwarding path**, defeating the goal of having a single final backend. Depending on the version, the configuration may be rejected by the framework, throw an error on startup, or fall into broken logging behavior; **do not try to fix this by adding more providers**.

**Do not combine:**

- `log4j-to-slf4j` with `log4j-slf4j2-impl`;
- `log4j-to-slf4j` with `log4j-slf4j-impl`;
- `log4j-slf4j2-impl` with `log4j-slf4j-impl` on the same runtime path.

However, having both **`slf4j-api`** and **`log4j-api`** is not automatically an error: both APIs can coexist so libraries can compile and run. What must be controlled is **which implementation/provider/bridge is selected**.

### How to Self-Check with Maven

```bash
mvn dependency:tree
```

If the project has a large dependency tree, you can filter the relevant groups:

```bash
mvn dependency:tree -Dincludes=org.apache.logging.log4j:*,org.slf4j:*,ch.qos.logback:*
```

This is a standard Maven Dependency Plugin command; the filter syntax may need appropriate escaping/quoting for your shell. Inspect both **direct and transitive dependencies**, because a starter or library may pull in `log4j-to-slf4j`, `logback-classic`, `slf4j-simple`, or another provider.

Focus on the questions: "**Which APIs does the code use? Which single backend will do the final writing? Which single bridge direction must each other API take?**"

If you need to remove a dependency brought in by a library, use Maven `<exclusions>` or the equivalent mechanism in Gradle on the exact dependency that pulls in the unwanted bridge/provider. Excluding a JAR based solely on its name without checking who uses it can cause logs from other libraries to be lost.

## 7. Bridging JUL (java.util.logging) to Log4j 2

An application or library may write logs using the JDK API:

```java
// Fragment using only java.util.logging.
java.util.logging.Logger jul =
        java.util.logging.Logger.getLogger("com.example.legacy");
jul.info("event=legacy_ready");
```

To forward JUL calls to the Log4j API/Core, Log4j 2 provides **`log4j-jul`**. A common startup configuration is to put the artifact on the runtime classpath and pass a **JVM system property**:

```bash
java -Djava.util.logging.manager=org.apache.logging.log4j.jul.LogManager -cp "..." com.example.Main
```

This command is an **illustrative template**, not runnable standalone because `...` and `com.example.Main` represent the classpath and main class of your actual application. You must configure the classpath to include compatible Log4j 2 modules.

**Why must it be declared on the JVM command line?** `java.util.logging.LogManager` can be initialized very early and only selects its implementation during initialization. Setting the property after JUL has already been initialized is usually too late to replace the LogManager. Do not expect calling `System.setProperty` inside a running service to reconfigure the JUL bridge path the same way as JVM startup.

There are other JUL bridge installation/initialization options supported by the Log4j documentation; choose based on your framework/container architecture. Exercise particular caution when running inside an application server that already manages JUL itself.

**Common confusion:** `log4j-jul` routes **JUL → Log4j 2 API**; `log4j-to-jul` routes **Log4j API → JUL**. The names are similar, but the final destinations are completely different. Likewise, do not place `jul-to-slf4j` and `slf4j-to-jul` together in opposing directions when they point to each other.

## 8. Bridging Other APIs and Migrating Legacy Applications

A large application may include libraries using JCL or the Log4j 1.x API. When the primary destination is Log4j Core, the corresponding modules can help consolidate logs:

| Source | Related Module | Important Notes |
| --- | --- | --- |
| Apache Commons Logging | `log4j-jcl` | Check the JCL version, discovery mechanism, and any existing JCL bridges |
| Log4j 1.x API | `log4j-1.2-api` | Partial support for legacy APIs/configurations; code and config changes may be needed during migration |
| Java Platform Logging (`System.Logger`) | `log4j-jpl` | Depends on the `System.LoggerFinder` mechanism, Java modules, and initialization timing |
| SLF4J 1.x | `log4j-slf4j-impl` | For 1.x code/API, do not confuse with `log4j-slf4j2-impl` |

**Migration is not just swapping JARs.** With the Log4j 1.x API, classes, appenders, configuration syntax, and lifecycle may differ from Log4j 2. Avoid continuing to deploy the old Log4j 1.x runtime just to avoid updating configuration. Evaluate the compatibility module, identify missing APIs, and test startup, file rolling, exception stack traces, and shutdown.

If a library uses SLF4J while the main app uses Log4j 2, you do not need to rewrite every `LoggerFactory` call to `LogManager`: a correctly directed bridge solves the problem. If a pure Java library only wants to provide a logging API to its host application, the library should avoid forcing the application to choose a specific logging backend.

## 9. How Do Bridges Affect Levels, Exceptions, and Context?

### Levels

APIs do not share the exact same set of levels. Log4j 2 has `TRACE`, `DEBUG`, `INFO`, `WARN`, `ERROR`, `FATAL`; SLF4J primarily uses `TRACE` through `ERROR`; JUL uses `FINE`, `INFO`, `WARNING`, `SEVERE`, and others.

Inside a bridge, levels are **converted** according to the module's policy. When the Log4j API forwards to SLF4J, levels without a direct equivalent (such as `FATAL`) must be mapped; you cannot expect the target backend to preserve every semantic detail of the source API.

When an event does not appear, check:

1. Does the **source API** logger allow the corresponding level?
2. Is the bridge actually selected and running in the right direction?
3. Does the **target backend** logger/filter allow the event?
4. Does the appender/collector write and retain the event?

### Throwable

An appropriate bridge typically forwards the exception object/event structure from the source API, while **final stack trace formatting** is decided by the layout/encoder/appender. For example, with SLF4J:

```java
// Fragment in a catch block that already has log, requestId, and Throwable e.
log.error("event=payment_failed requestId={}", requestId, e);
```

Do not treat `e.getMessage()` as a substitute for a stack trace; pass the `Throwable` to the API and verify that the output destination displays `Caused by`/stack frames.

### MDC / ThreadContext

SLF4J supports MDC, whereas Log4j 2 has `ThreadContext`. A bridge can partially map context, but forwarding and rendering behavior depends on the implementation; **do not assume every MDC key, marker, location info, or attribute has identical semantics across all bridges**.

When using executors/async/reactive code, thread-bound context may not automatically follow the request. You must propagate and clear context, and configure the layout to include the required fields, such as `requestId`/`traceId`. Do not create per-request logger names or log tokens/credentials just for correlation.

### Latency and Data Volume

Every bridge adds a translation layer; chaining multiple bridges sequentially can increase overhead and make debugging harder. For applications with high throughput requirements, prefer a **direct path from the source API to the primary backend** rather than unnecessary stacked adapters. When using async appenders, review queue capacity, drop/backpressure policies, and shutdown behavior to prevent record loss.

## 10. Choosing a Backend in Spring Boot Deployments

In a typical Spring Boot application, the default backend from the logging starter is **Logback**. If you use Logback as the final destination and a library calls the Log4j API, the **`log4j-to-slf4j`** path is the standard model.

If the project decides to switch to **Log4j 2 Core**, you can use `spring-boot-starter-log4j2` instead of the default logging starter, while reviewing other starters/libraries that might pull in Logback or an opposing bridge.

A decision workflow:

1. Identify the desired backend: **Logback** or **Log4j Core**.
2. Inspect the actual dependency tree; do not guess based only on imports in one class.
3. For **Logback**: keep the Logback provider and use `log4j-to-slf4j` if you need to receive Log4j API calls.
4. For **Log4j Core**: keep Log4j Core and use `log4j-slf4j2-impl` if receiving SLF4J 2.x; check JUL/JCL bridges if needed.
5. Exclude opposing providers/bridges and any backends that are no longer the final destination.
6. Use the appropriate backend configuration: `logback-spring.xml` for Logback loaded by Spring Boot, or `log4j2-spring.xml`/`log4j2.xml` according to Log4j 2 integration.
7. Test emitting an event from each API in the dependency tree and verify **a single final backend**, level, logger name, throwable, correlation ID, and output destination.

**Do not use `logback-spring.xml` to configure Log4j Core**, and do not rely on `log4j2.xml` to control Logback: each backend has its own syntax and loading mechanism.

## 11. Common Mistakes When Configuring Log4j2 Bridges

| Symptom | Possible Cause | Resolution |
| --- | --- | --- |
| SLF4J logs do not appear, Log4j API still prints | Missing appropriate SLF4J provider or wrong provider version | Check `log4j-slf4j2-impl` with SLF4J 2.x, classpath, and warnings |
| Logging loop error reported | Both `log4j-to-slf4j` and `log4j-slf4j2-impl`/reverse binding are present | Pick one direction, exclude the unwanted bridge |
| SLF4J reports "multiple providers" | Multiple providers such as Logback and Log4j bridge are present together | Keep only the provider matching the chosen backend |
| Using SLF4J 2.x but only `log4j-slf4j-impl` is present | Binding is for SLF4J 1.x | Switch to the compatible `log4j-slf4j2-impl` |
| Using Logback but `log4j-slf4j2-impl` is installed | Chose a bridge to Log4j instead of to SLF4J | Use `log4j-to-slf4j` and the Logback provider |
| JUL logs do not reach Log4j | Missing `log4j-jul` or `java.util.logging.manager` was not set early | Configure the bridge properly at JVM startup |
| JCL logs take a different path | Multiple JCL bridges or another discovery mechanism is active | Review JCL API and `log4j-jcl`/competing adapters |
| `DEBUG` does not appear | Target logger/backend threshold is `INFO` or filtered at the appender | Check level/filter by category and appender |
| Events appear twice | Appender additivity, multiple API paths, or duplicate logging in code | Verify 1 event goes through exactly one route and check additivity config |
| Stack trace is not logged | Throwable was not passed or layout omits exceptions | Use the overload accepting Throwable and a layout that includes exceptions |
| Log4j 2 config is not loaded | Wrong file name/location or the actual backend is not Log4j Core | Check `log4j2.xml`, classpath, and startup logs |
| Security issue after adding a bridge | Unsupported version chosen or old dependency pulled in | Use a maintained version, scan dependencies, and follow update policies |

Do not fix a "no logs appearing" issue by adding every artifact named `log4j`. That usually increases forwarding paths, provider conflicts, and the burden of determining the final backend.

## 12. Checklist to Prove Your Bridge Configuration Is Correct

1. **Draw a one-way diagram**: for each source API, trace it to a single final backend and clear appender.
2. **Audit the runtime classpath**: ensure there are no two opposing SLF4J↔Log4j bridges; keep only the provider matching the SLF4J API in use.
3. **Choose compatible versions**: use a BOM/dependency management; do not randomly mix Log4j 2 and SLF4J versions.
4. **Verify backend configuration**: `log4j2.xml`/Log4j Core or `logback.xml`/Logback in the right place.
5. **Emit one event from each API**: verify the actual log count, logger name, level, message, and throwable.
6. **Cross-check output destinations**: console stdout/stderr, files, and collectors must receive the expected events by design.
7. **Verify the JUL bridge early**: if using `log4j-jul`, the LogManager property must be present from JVM startup or use an officially supported runtime-compatible approach.
8. **Verify context across threads**: `requestId`/`traceId` must be propagated and cleared properly to avoid cross-request contamination.
9. **Do not log sensitive data**: tokens, passwords, session cookies, and unnecessary user data must not be placed in messages/context.
10. **Re-run after every dependency change**: startup, exception handling, and shutdown must all be verified; do not just check that the JARs downloaded successfully.

**Conclusion:** A "Log4j2 bridge" is not a single universal JAR used across every system. Choosing a bridge must be based on **which API is emitting logs** and **which backend is allowed to do the final writing**. When the direction is chosen correctly, library code written with SLF4J, Log4j 2 API, JUL, or JCL can all be managed by one consistent logging system; when chosen incorrectly, the system is prone to loops, duplicate logs, lost logs, and startup failures.
