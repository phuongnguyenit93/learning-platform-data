# Size-Based Rotation in Java Logging

**Size-based log rotation** is the mechanism of **closing or moving the current log file to an archive file and opening a new file for writing** when the file's data size reaches a configured threshold. The goal is to prevent a single log file from growing indefinitely over time while retaining some history for troubleshooting.

For example: an application is writing to `app.log` with a configured threshold of around 10 MB. When the file reaches the threshold, the system may rename it to `app.1.log` and start a new `app.log` file. As the new file continues to fill up, older archives can be shifted by index, compressed, or deleted according to the **retention policy**.

**Key takeaway:** *rotation* is the action of switching to a new file; *retention* is deciding how many files or how long to keep them; *compression* is compressing archives. These three are related, but they are **not synonymous**. Simply configuring a size threshold does not guarantee that the system will never run out of disk space.

## 1. How Size-Based Rotation Works

Conceptual diagram for an application with a single writer:

~~~text
Application emits log event
           |
           v
Logger -> Handler / Appender
           |
           v
Check bytes currently written
           |
        Threshold exceeded?
        /           \
      No            Yes
       |             |
       v             v
Write to         Complete record /
current file     rotate current file
       |             |
       |             v
       |         Save under archive name
       |             |
       |             v
       |         Open new file to continue writing
       |             |
       +-------------+
                     |
                     v
                Write event
~~~

The diagram above illustrates the general logic. **The exact order of checking and rollover for a record near the threshold depends on the implementation.** A backend may finish writing the record before deciding to rotate, or it may estimate the size of the next event. You should not rely on `maxFileSize` / `limit` as an absolute byte ceiling in every situation.

Key concepts:

| Term | Meaning | Example |
| --- | --- | --- |
| **Active file** | The file currently being written to by the appender/handler | `app.log` |
| **Archive** | A file that has been moved out of the active writing state | `app.1.log`, `app-2026-11-09.3.log.gz` |
| **Size threshold** | The size mark used to trigger rollover | `10MB` or `10485760` bytes |
| **Rollover/rotation** | Closing/moving/renaming the old file and preparing a new file | `app.log` → archive |
| **Generation/index** | A sequence number used to distinguish archives | `0`, `1`, `2` or token `%i` |
| **Retention** | Limit on kept archives by count, time, or total size | Keep 5 files; keep 7 days |
| **Compression** | Compressing archive files to reduce disk usage | `.gz`, `.zip` |
| **Rotation error** | An error during rename, file creation, compression, or archive deletion | Permission denied, disk full, file lock |

An archive file is usually **already-written history**, not a file that continues receiving messages. However, naming and generation ordering vary by policy; do not assume a higher-numbered file is always newer without reading the backend's convention.

## 2. Why Use Size-Based Rotation?

A Java process that emits logs continuously can generate gigabytes of data if it only appends to a single file. That causes problems for:

- **Disk space:** an ever-growing file can fill up the entire partition/volume.
- **Log reading tools:** opening or transferring a huge file can be slow, hard to download, and hard to share.
- **Collectors:** some ingestion or shipping systems work better with moderately sized files.
- **Operations:** smaller split archives are easier to store, compress, inspect, and delete according to policy.
- **Impact during incidents:** an oversized file can make incident analysis or recovery time-consuming.

However, size-based rotation **does not reduce the number of events generated by the application**. It only splits the file into smaller parts. If too many INFO logs are emitted per loop iteration, you still need to fix the **log level, message volume, sampling, or observability design**. Do not use rotation to hide log spam issues.

### Rotation vs. Truncation and File Deletion

~~~text
Rotation:  app.log -> app.1.log, then create a new app.log
Truncate:  keep the name app.log, clear existing content
Deletion:  completely remove old archives
~~~

`truncate` can lose history without creating an archive; deleting a file that is still held open by a process may also fail to free disk space as expected on some filesystems. You need to know what reopen/rename mechanism the backend uses before combining it with external tools.

## 3. Size Is Measured in Bytes, Not Character Count

The threshold of JUL `FileHandler.limit` is specified in **bytes**, while Logback allows writing `maxFileSize` with suffixes such as `KB`, `MB`, `GB`.

A short message does not necessarily produce a correspondingly short file, because the actual written data also includes:

- Timestamp, level, logger name, thread, and context information.
- Line breaks, delimiters, and encoding.
- Multi-line stack traces when an exception occurs.
- Field names, braces/quotes when outputting JSON.
- Headers/footers of certain formatters/encoders.
- Byte-length differences for Unicode characters in UTF-8.

For example, the message `"Xin chào"` contains Vietnamese characters that encode into multiple bytes in UTF-8. **Do not use `String.length()` to deduce the exact file size** after passing through a formatter/encoder.

In addition, size thresholds are typically **approximate trigger marks**. A log event with a very long stack trace can push the file past the threshold before rotation completes. Therefore, if the destination has a hard file size limit (such as an upload limit), test with large events and put measures in place to **limit record size** at the source.

### Estimating Data Volume

Suppose:

- Each event after encoding averages **500 bytes**.
- The application emits **200 events/second**.
- On average, it generates about **100,000 bytes** per second (approximately 100 kB).
- Around **6 MB** per minute under steady traffic.

A file with a **60 MB** threshold may roll over roughly every ten minutes under the assumptions above; actual traffic varies by event type, peak hours, and exceptions. Measure from the real system rather than estimating solely from HTTP request counts.

## 4. JUL: java.util.logging.FileHandler Supports Rotation Built-In

Java Util Logging (JUL) includes `java.util.logging.FileHandler` in the JDK. You do not need to install Logback just to rotate files by size.

An important constructor:

~~~java
FileHandler(String pattern, int limit, int count, boolean append)
~~~

Meaning:

| Parameter | Meaning | Notes |
| --- | --- | --- |
| `pattern` | File naming pattern | Supports special tokens `%g`, `%u`, `%t`, `%h` |
| `limit` | Approximate maximum **bytes per file** | `0` means no limit |
| `count` | Number of files in the rotation cycle | At least 1; not the number of archives in addition to the active file |
| `append` | Whether to append to an existing file when opening | `false` may lose old content on initialization |

Example:

~~~java
FileHandler handler = new FileHandler(
        "/var/log/myapp/app-%g.log",
        10 * 1024 * 1024,
        5,
        true);
~~~

This is an **illustrative snippet inside a Java method**. It assumes `java.util.logging.FileHandler` has been imported, that the `/var/log/myapp` directory exists, and that the account running the JVM has write permissions. It is not guaranteed to work on Windows when using a Linux path.

With `limit` around **10 MiB** and `count=5`, `FileHandler` uses a **rotating file ring** with generations typically from 0 to 4. **`count=5` means five output files in the rotation cycle, not five archives plus one active file.** Once the cycle is full, the oldest file in the cycle may be overwritten.

### JUL Filename Tokens

| Token | Meaning |
| --- | --- |
| `%g` | Generation number used for rotation |
| `%u` | Unique number to resolve conflicts when a file is in use |
| `%t` | System temporary directory |
| `%h` | User home directory |
| `%%` | A literal percent sign |

If `count > 1` without `%g` in the pattern, `FileHandler` may automatically append the generation to the filename. When opening logs from multiple processes, `%u` helps distinguish files via `FileHandler`'s lock mechanism; the JDK documentation notes that the reliability of this uniqueness mechanism is guaranteed primarily on **local filesystems**, and it should not be treated as a distributed locking solution over NFS.

**Do not confuse JUL `FileHandler`'s `%g`/`%u` with Logback's `%d`/`%i`.** They belong to two different formatting systems.

### Why Append and Restart Matter

If `append=false`, the handler may initialize by opening/truncating an existing file according to JUL's mechanism, causing data from the previous run not to be preserved as expected. `append=true` is appropriate when you need to continue appending to an existing file, but it does not replace retention or rotation policies.

On restart, verify:

- Is data in the active file and archives preserved as configured?
- Can the new process acquire the lock and open the file matching the pattern?
- Does the path change depending on `user.dir`, `%t`, or `%h`?
- Are write permissions still valid after `logrotate`/deployment creates a new file?

Do not assume a restart will always create the exact same `app.log` file; tokens and lock rules can cause the name to change.

## 5. Runnable Java 17+ Example: Rotating After 300 Bytes

This example uses **JUL `FileHandler`**, creates a temporary directory, emits multiple records to trigger rotation, and checks the results. All file operations take place in the program's **new temporary directory**, without touching production log files.

Create **SizeRotationDemo.java**:

~~~java
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.List;
import java.util.logging.FileHandler;
import java.util.logging.Formatter;
import java.util.logging.LogRecord;
import java.util.logging.Logger;
import java.util.stream.Stream;

public final class SizeRotationDemo {
    public static void main(String[] args) throws IOException {
        Path dir = Files.createTempDirectory("jul-size-rotation-");
        String pattern = dir.resolve("demo-%g.log").toString();
        Logger logger = Logger.getLogger("demo.rotation.SizeRotationDemo");
        logger.setUseParentHandlers(false);

        FileHandler handler = new FileHandler(pattern, 300, 3, false);
        handler.setFormatter(new Formatter() {
            @Override
            public String format(LogRecord record) {
                return record.getLevel().getName() + " | "
                        + formatMessage(record) + System.lineSeparator();
            }
        });
        logger.addHandler(handler);
        try {
            for (int i = 0; i < 25; i++) {
                logger.info("event=processed seq=" + i
                        + " data=" + "x".repeat(70));
            }
        } finally {
            handler.flush();
            logger.removeHandler(handler);
            handler.close();
        }

        List<Path> logs;
        try (Stream<Path> files = Files.list(dir)) {
            logs = files.filter(p -> p.getFileName().toString()
                            .matches("demo-[0-2]\\.log"))
                    .toList();
        }
        boolean latestFound = false;
        for (Path file : logs) {
            latestFound |= Files.readString(file).contains("seq=24 ");
        }

        System.out.println("rotated=" + (logs.size() > 1));
        System.out.println("withinCount=" + (logs.size() <= 3));
        System.out.println("latestPresent=" + latestFound);

        for (Path file : logs) {
            Files.deleteIfExists(file);
        }
        Files.deleteIfExists(dir);
    }
}
~~~

Compile and run:

~~~bash
javac --release 17 SizeRotationDemo.java
java SizeRotationDemo
~~~

**Verified stdout on JDK 17+:**

~~~text
rotated=true
withinCount=true
latestPresent=true
~~~

Explanation:

1. `Files.createTempDirectory` creates an isolated directory to avoid name collisions or depending on write permissions for `/var/log`.
2. `new FileHandler(pattern, 300, 3, false)` requests an approximate limit of **300 bytes per file**, with up to **three rotating files**.
3. The formatter produces one text line per record. `"x".repeat(70)` makes each event large enough to hit the threshold after just a few events.
4. `logger.setUseParentHandlers(false)` prevents records from also being printed to the root console handler; this does not affect `FileHandler` rotation.
5. `handler.close()` releases the file/lock before reading back and deleting the test files.
6. `rotated=true` proves more than one generation exists; `withinCount=true` proves the file count matches `count=3`.
7. `latestPresent=true` checks that the last record `seq=24` is still present within the active/archive cycle.

The program **does not assert that all 25 events are kept**. Because there are only three files and each is small, the oldest generations are discarded as the cycle wraps around enough times. That is **bounded retention with intentional loss of older history**, not a Java bug.

**Why not print the exact names and sizes of each file?** Those details can vary by newline characters, formatter/encoding, and generation switch timing across operating systems. The example verifies key invariants instead of depending on exact filenames or total byte counts.

### Note on Cleanup in the Example

The temporary path is created exclusively for this run; the program removes the `FileHandler`, closes it, and deletes the files after testing. If another exception occurs before the cleanup step, the temporary directory may remain; this is a learning example, not a temp-file management library for every failure case. In a real system, manage handler lifecycle and file permissions in the logging configuration layer.

## 6. Configuring JUL Size Rotation with logging.properties

Instead of creating `FileHandler` in `main`, an application can configure it via `logging.properties`:

~~~properties
handlers = java.util.logging.FileHandler
.level = INFO

java.util.logging.FileHandler.pattern = /var/log/myapp/app-%u-%g.log
java.util.logging.FileHandler.limit = 10485760
java.util.logging.FileHandler.count = 5
java.util.logging.FileHandler.append = true
java.util.logging.FileHandler.level = ALL
java.util.logging.FileHandler.formatter = java.util.logging.SimpleFormatter
~~~

**Meaning:** a `FileHandler` with an approximate threshold of **10 MiB**, five rotating files, append on reopen, and `SimpleFormatter` producing text. The `%u` token reduces filename conflicts between handlers/processes on local disk; `%g` distinguishes generations.

Command to run the compiled application:

~~~bash
java -Djava.util.logging.config.file=logging.properties MyApplication
~~~

`MyApplication` is a **hypothetical application class with `main()`**, not a class provided in this lesson. Place the JVM property before the class name or `-jar`, and verify that the properties file path is correct relative to the working directory.

Requirements for the configuration to work:

- The `/var/log/myapp` directory exists and **the Java process has write/create/rename permissions**.
- The JUL configuration is actually loaded and not overridden by a framework or other initialization code.
- Logger/handler levels allow the events that need to be logged.
- The volume has free space/quota; file locks do not suffer unexpected conflicts.
- `limit > 0` if you want size-based rotation; `limit=0` means **unlimited**.

### Be Careful with count=1

If `count=1` and `limit` is very small, the handler has only one file slot in the rotation cycle; upon rotation, old content may be lost without any real historical archive. If the goal is to recover from incidents from a few hours earlier, choose `count` and `limit` based on actual log generation volume.

Rough calculation example: 5 files × 10 MiB ≈ **50 MiB of rotating data window**, excluding lock files, metadata, record size overshoot, and other activity. **Do not treat this number as a hard disk usage guarantee** for every incident, especially with very long events or multiple processes.

## 7. Logback: RollingFileAppender and Rollover Policies

For applications using SLF4J + Logback, `RollingFileAppender` is the component dedicated to file logging with rotation. Logback has two concepts:

- **RollingPolicy:** defines what happens during rollover, archive filenames, where to continue writing, retention, and compression.
- **TriggeringPolicy:** determines **when** to roll over; in some policies, the same object handles both responsibilities.

Logback supports the following size-related options:

| Option | Characteristics | Recommended Use |
| --- | --- | --- |
| `SizeAndTimeBasedRollingPolicy` | Each time period has archives indexed by `%i`, bounded by `maxFileSize` | When you need to split files by a size threshold **and** manage history by day/month |
| `TimeBasedRollingPolicy` | Archives by time period with optional `totalSizeCap` | When you only need to cap total archive size without requiring per-file size limits |
| `FixedWindowRollingPolicy` + `SizeBasedTriggeringPolicy` | Rotation using a fixed index window | Legacy configuration; Logback now recommends avoiding it due to expensive renames |
| Plain `FileAppender` | Appends to a file with no built-in rotation | Unsuitable if you need to bound file growth |

**Do not choose FixedWindow just because "size-based" sounds more direct.** Modern Logback documentation considers `FixedWindowRollingPolicy` an older approach and discourages it; so that learners can easily get daily retention and per-file size limits, `SizeAndTimeBasedRollingPolicy` is the primary example below.

### What Is Special About SizeAndTimeBasedRollingPolicy?

Example pattern:

~~~text
archive/app-%d{yyyy-MM-dd}.%i.log
~~~

- **`%d{yyyy-MM-dd}`** sets the time period boundary; here it is daily.
- **`%i`** is the archive file index **within a time period**; numbers increment when multiple size-based rollovers occur on the same day.
- **Both `%d` and `%i` are required** in `fileNamePattern` for the size-and-time policy.
- **`maxFileSize`** is the size that triggers a rollover before the current time period ends.
- **`maxHistory`** is the number of **time periods** (such as days) to keep archives, **not the total number of files**.
- **`totalSizeCap`** limits the total size of saved **archives**, working alongside `maxHistory`; it should not be treated as a strict cap on the active file and all currently open files.
- **`cleanHistoryOnStart`** can request cleanup of old archives at startup, useful for applications with infrequent rollovers.

When 50 archive files are created on the same day, setting `maxHistory=7` **does not mean keeping only 7 files**; it specifies at most 7 days of history, and then the total archive size cap (if configured) is applied on top.

In some modern Logback versions, archive deletion runs **asynchronously** after rollover. Do not check immediately after a single event to assert that all old files have already been deleted on the spot.

## 8. Logback 1.5.18 Example: Combining Size and Time

This example uses **Java 17+, Maven, and Logback 1.5.18**. Within the same day, whenever the log reaches about **1 KB**, the appender saves an archive with index `%i`; the active file is named `app.log`.

Structure:

~~~text
├── pom.xml
~~~

### 8.2. LogbackSizeDemo.java

Create `src/main/java/demo/LogbackSizeDemo.java`:

~~~java
package demo;

import ch.qos.logback.classic.LoggerContext;
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.stream.Stream;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public final class LogbackSizeDemo {
    public static void main(String[] args) throws IOException {
        Path dir = Files.createTempDirectory("logback-size-demo-");
        System.setProperty("LOG_DIR", dir.toString().replace('\\', '/'));

        LoggerContext context =
                (LoggerContext) LoggerFactory.getILoggerFactory();
        Logger log = LoggerFactory.getLogger(LogbackSizeDemo.class);
        for (int i = 0; i < 90; i++) {
            log.info("event=processed seq={} data={}", i, "x".repeat(100));
        }
        context.stop();

        long archives = 0;
        Path archiveDir = dir.resolve("archive");
        if (Files.isDirectory(archiveDir)) {
            try (Stream<Path> paths = Files.list(archiveDir)) {
                archives = paths.filter(Files::isRegularFile).count();
            }
        }
        System.out.println("activeExists=" + Files.isRegularFile(dir.resolve("app.log")));
        System.out.println("archivesCreated=" + (archives > 0));
    }
}
~~~

The program sets the `LOG_DIR` JVM property **before the first call to `LoggerFactory`** so Logback reads the temporary directory during initialization. This is why the class does not declare a static `Logger` field initialized earlier than `main()`.

Calling `context.stop()` lets the backend close the appender before inspecting the files, which is suitable for a short test program. In a long-running application, the framework/backend typically manages shutdown. **Do not call `stop()` after every log event.**

### 8.3. logback.xml

Create `src/main/resources/logback.xml`:

~~~xml
<configuration>
  <appender name="ROLLING" class="ch.qos.logback.core.rolling.RollingFileAppender">
    <file>${LOG_DIR}/app.log</file>
    <rollingPolicy class="ch.qos.logback.core.rolling.SizeAndTimeBasedRollingPolicy">
      <fileNamePattern>${LOG_DIR}/archive/app-%d{yyyy-MM-dd}.%i.log</fileNamePattern>
      <maxFileSize>1KB</maxFileSize>
      <maxHistory>2</maxHistory>
      <totalSizeCap>10KB</totalSizeCap>
    </rollingPolicy>
    <encoder><pattern>%level | %msg%n</pattern></encoder>
  </appender>
  <root level="INFO"><appender-ref ref="ROLLING"/></root>
</configuration>
~~~

In this configuration:

- `<file>` is the active file: `app.log`.
- `fileNamePattern` places archives in the `archive` directory, with date and index.
- `maxFileSize=1KB` is small **only to trigger rotation quickly in the test**; production needs a threshold chosen based on workload.
- `maxHistory=2` means keeping history for a two-day period (since the pattern uses days), not two files.
- `totalSizeCap=10KB` applies to total archive size via Logback's cleanup mechanism; it is not an instantaneous hard limit on the entire directory.
- Encoder `%level | %msg%n` outputs one event per line.

~~~bash
mvn -q compile exec:java -Dexec.mainClass=demo.LogbackSizeDemo
~~~


Results:

2. The INFO records are large enough to trigger rotation within the same day.

`SizeAndTimeBasedRollingPolicy` **combines both mechanisms**. It has a size threshold to split files multiple times per day and a date boundary to organize retention; it is not a policy that only counts bytes while ignoring time.

## 9. Why FixedWindowRollingPolicy Is Not the Modern Default

Some older documentation shows:

~~~xml
<rollingPolicy class="ch.qos.logback.core.rolling.FixedWindowRollingPolicy">
  <fileNamePattern>app.%i.log.gz</fileNamePattern>
  <minIndex>1</minIndex>
  <maxIndex>5</maxIndex>
</rollingPolicy>
<triggeringPolicy class="ch.qos.logback.core.rolling.SizeBasedTriggeringPolicy">
  <maxFileSize>10MB</maxFileSize>
</triggeringPolicy>
~~~

This is a **historical configuration fragment**, not a complete XML file to copy into a new project.

The fixed-window mechanism has to rename multiple files upon rotation to maintain an index range. Renaming can be slow and problematic on some filesystems, especially when files are held open by another process. Modern Logback documentation marks `FixedWindowRollingPolicy` as **deprecated** and **discourages its use for new configurations**.

For typical needs, consider:

- `TimeBasedRollingPolicy` + retention/cap if you only need to clean up archives by day/total size.
- `SizeAndTimeBasedRollingPolicy` if **each archive file** needs to be split at a specific size threshold.

If you must maintain an existing fixed-window configuration, check the Logback version, error/status messages, and test rollover on the real filesystem before upgrading; do not arbitrarily mix incompatible policies in the same appender.

## 10. Size Rotation with Log4j 2 (Brief Comparison)

In Log4j 2, a **RollingFile Appender** can combine:

- **`SizeBasedTriggeringPolicy`** to trigger rollover at a size threshold.
- **`filePattern`** to name archives.
- **Rollover strategy** to manage indexing, compression, and retention policy.

The terminology is similar to Logback, but it is **Log4j 2's API/configuration**—do not copy `SizeAndTimeBasedRollingPolicy` directly from Logback into `log4j2.xml`. If the runtime uses Log4j 2, read the configuration and documentation for that backend, and do not expect `logback.xml` or `logging.properties` to take effect.

Common ground: **the size threshold triggers rollover, the strategy/policy determines archiving and retention**, while file permissions, volume space, and log collection determine whether operations are safe.

## 11. Designing Retention for Your Needs

A small threshold makes files easy to read but can create **a huge number of archives**. A large threshold reduces the number of rollovers, but files become harder to process and may exceed collector limits.

Example comparing two hypothetical configurations:

| Parameter | Configuration A | Configuration B |
| --- | --- | --- |
| Per-file threshold | 10 MiB | 100 MiB |
| Average events/second | 100 | 100 |
| Assumed bytes/event | 500 | 500 |
| Log data/day | About 4.32 GB | About 4.32 GB |
| Rotations needed/day (estimated) | ~412 | ~41 |
| Main risk | Many files, rename/cleanup overhead | Large files, long download/read times |

These figures are estimates based on **100 × 500 × 86,400 = 4,320,000,000 bytes/day** and do not reflect a specific workload. For actual design, you must also account for peak hours, long exception logs, compression ratios, and expected retention.

### Do Not Confuse File Count with Retention Duration

With JUL `limit=10MiB,count=5`, the amount of history depends only on **data size and log emission rate**. A burst of log spam can overwrite all five files in seconds. The system makes no guarantee to "keep three days" just because there are five files.

With Logback `maxHistory=7` in a daily pattern, retention is **by day** for archives, but if daily log volume spikes and `totalSizeCap` is small, older archives may be cleaned up earlier to stay within the cap.

If you have **audit** or regulatory minimum-retention requirements, use a durable storage/collection system with an independent policy. Local rotation is not an immutable audit mechanism.

### Does Compression Help?

Compressing archives to `.gz` can reduce disk usage, especially for repetitive text logs. However:

- Compression ratios depend on content and are not uniformly 100% predictable.
- Compression consumes CPU and I/O.
- Enough temporary space is needed during rollover/compression.
- Some collectors tail compressed files differently from active files; you must design clearly which files are ingested.

Do not assume compressed archives shrink by a fixed ratio and size storage too close to the limit.

## 12. File and Filesystem Permissions During Rotation

A process that can write to `app.log` does not necessarily have permission to **rename, create archives, create new files, or delete old archives**. On POSIX filesystems:

- Appending to an existing file: requires write permission on the file and traverse permission on parent directories.
- Creating a new file: requires **write + execute** permission on the target directory.
- Renaming/deleting a file: typically requires permissions on the directory, also subject to ACLs/sticky bits/policies.
- Archive path in a different directory: requires appropriate permissions on **both source and destination**.
- Compression: may require additional temporary space and permissions to open/write compressed files.

On Windows, NTFS ACL rules and file-sharing handles can cause rename/delete to be denied even while writing to the current file succeeds. On NFS/SMB/network volumes, locking, rename, and consistency semantics may differ from local disk.

Do not fix errors by running the JVM as **root/Administrator** or applying `chmod 777` to the entire log directory. Identify the **service user**, actual permissions, and which rollover operation is failing, then grant the minimum required permissions.

Non-permission causes should also be checked:

- Out of disk space or inodes.
- **Read-only** filesystem/mount.
- Disk quota exceeded.
- Log archives located on a different volume.
- Wrong path or missing parent directory.
- File locked by another process.
- Backend configuration not loaded or appender failed to start.

## 13. Log Rotation When Multiple JVMs/Processes Write Together

Local rotation is safest when **one backend owns one active file**. If two JVMs write to the same file and both rotate independently:

- Both may detect the size threshold being exceeded at nearly the same time.
- One process may rename the file while the other still holds the file descriptor.
- Log lines may go into the old file or the expected path under an unexpected name.
- Archives may be overwritten, missing, or lack the expected sequence.
- Locking mechanisms may fail or behave differently from local disk on network volumes.

**JUL `%u`** helps distinguish filenames between concurrent `FileHandler` instances on a local filesystem, but it is not a distributed rotation coordination protocol. In Logback, **prudent mode** has specific constraints and should not be assumed to combine safely with size-and-time or archive compression across multiple JVMs without checking official documentation.

Safer approaches include:

1. Give each process **its own file path** containing an instance/pod ID when policy allows.
2. Have each process write to **stdout/stderr**, letting the host/container runtime/collector handle rotation.
3. Use a centralized log collection service, with each process acting as an independent source.
4. When sharing a file is unavoidable, use a mechanism explicitly documented as supported by the backend and filesystem, and test real contention and failover.

Do not treat a single-process test as proof that rotation is safe in a cluster.

## 14. Docker, Kubernetes, and External logrotate

In containers, many Java applications do not need to manage `RollingFileAppender` directly: they can write to **stdout/stderr** and leave rotation, retention, shipping, and monitoring to the container runtime/collector.

When writing to files inside a container is required:

- Choose a writable volume with the right UID/GID, ACLs, and capacity.
- Do not write to a read-only image layer.
- Plan archive paths, size limits, and compression/deletion permissions.
- Do not let multiple processes rotate the same active file on a shared mount.
- Verify that the collector continues tailing the active file after rollover without dropping log segments between rename and reopen.

### Do Not Let Two Systems Rotate the Same File Without Coordination

For example, the application's Logback renames `app.log`, while the OS `logrotate` tool also renames/truncates that file on a schedule. Two independent mechanisms can:

- Rename the same file in a race condition.
- Write to the descriptor of a file that has already been renamed or unlinked.
- Create a new active file with different permissions, preventing the JVM from opening it.
- Lose or duplicate log lines during **`copytruncate`**.

Choose **one primary owner** responsible for rotating the file, or a coordination method supported by both the backend and the OS. Do not treat `copytruncate` as lossless: it has a race window between copying and truncating.

In Kubernetes, log preservation needs are usually better solved with **log shipping** and centralized storage rather than expecting archives inside an ephemeral Pod to survive Pod replacement.

## 15. How Big Should the Size Threshold and Retention Be?

There is no "10 MB is always right" or "keeping three files is always enough." A practical decision process:

1. **Measure data:** total log bytes/day, hourly variance, average event size, and P99 event size.
2. **Define goals:** how many minutes/hours of local logs are needed for debugging? Does the collector have a file size limit?
3. **Choose file size:** small enough for tools to handle, not so small that renaming/compression happens constantly.
4. **Choose retention:** generation count (JUL), number of time periods (Logback), total archive cap if available.
5. **Reserve capacity:** leave headroom for the active file, archives, compression, temp files, and unexpected bursts.
6. **Verify permissions:** the JVM account can create new files, rename archives, and perform cleanup.
7. **Test under workload:** write enough to cross the threshold several times, test restarts, and test repeated rollovers.
8. **Monitor in production:** disk usage metrics, appender errors, archive growth, file retention, and collector ingestion.

### A Simple Sizing Calculation

Suppose an application produces **600 MiB of logs/day**. If using JUL `limit=20MiB`, `count=10`, the total retention window is approximately **200 MiB**, equivalent to about **8 hours** at the average rate, *if logs are evenly distributed*. During an incident with many error events, this window can shrink drastically.

If you need to retain logs for incident investigation for at least **three days**, that JUL configuration will not suffice even with ten files. Increase storage capacity, ship logs to centralized storage, or choose an appropriate time-based retention mechanism.

Similarly, Logback `maxHistory=3` (with a daily pattern) does not by itself guarantee enough space for three days if the storage cap is smaller than the generated volume; you must design **both time and capacity**.

## 16. Common Size-Based Rotation Issues

| Symptom | Possible Cause | Resolution |
| --- | --- | --- |
| File grows indefinitely without rotating | JUL `limit=0`, Logback using plain `FileAppender`, policy not loaded | Check active handler/appender and runtime configuration |
| Rotation happens, but old logs are gone | Small JUL `count` overwriting archives; retention too short | Increase capacity or ship logs to centralized storage |
| File exceeds threshold by a few bytes or one large event | Threshold is an approximate trigger; event is oversized | Test with very long records; cap event size |
| Logs stop appearing after rollover | Unable to create new file, missing permissions, or wrong target | Check status/handler errors and directory permissions |
| Rotates only when a new record arrives | Trigger is checked on log emission, not a continuous timer | Distinguish event-driven triggers from system schedules |
| Appender reports missing `%i` | `SizeAndTimeBasedRollingPolicy` has an invalid pattern | Include both `%d` and `%i` |
| Set `maxHistory=5` but more than five files exist | `maxHistory` counts **time periods**, not files | Check date/month pattern and total archive cap |
| `totalSizeCap` does not keep total directory size strictly under cap | Cap applies primarily to archives; active file and async cleanup still exist | Monitor total disk usage and leave headroom |
| Archives are not compressed | Pattern lacks compression extension or config does not support it | Check `fileNamePattern`/rolling policy |
| Archive rename fails on Windows | File held by another process or ACL/sharing mode | Check process/file handles and choose an appropriate policy |
| Logs lost after deploy/restart | `append=false`, path changed, or ephemeral directory | Check `append`, persistent storage, and log shipping |
| Logs appear twice | Multiple handlers/appenders, additivity, duplicate bridges | Trace a single event through the pipeline |
| Both Logback and `logrotate` operate on the same file | Two competing rotation systems | Choose one owner or integrate safe reopen |
| Multiple JVMs write to the same file, corrupted archives | No locking/rename coordination between processes | Use one file per instance or stdout/collector |
| Disk full despite rotation | Missing retention/cleanup, multiple appenders, archives outside cap scope | Check disk, quota, inodes, and actual retention |
| JUL `%u` creates multiple file groups | Handler/process lock conflict | Check instances, locks, and filenames; do not delete locks arbitrarily |

### What If the System Reports No Error to Business Code?

Logging backends can write errors to an **internal channel** without throwing exceptions when application code calls `logger.info(...)`. For Logback, check **StatusManager/status listeners** and startup diagnostics. For JUL, check **`FileHandler` `ErrorManager`** and stderr/config. After fixing an issue, emit a test event with a known ID and verify it appears in the active file or the appropriate archive.

Do not rely solely on "no exception thrown" to conclude that rotation is preserving data.

## 17. Practice Exercises

### Exercise 1 — Meaning of count

Given JUL:

~~~java
new FileHandler("logs/app-%g.log", 1_048_576, 4, true);
~~~

**Question:** Does this configuration guarantee keeping four archives plus one active file, or four files in total? What happens if too many logs are generated?

**Answer:** The `FileHandler` cycle has **four files in total**. Once it wraps around, older generations are replaced; it does not guarantee retention by number of days.

### Exercise 2 — File Larger Than limit

`FileHandler` has `limit=1000` bytes, but a single event contains a stack trace several thousand bytes long. **Question:** Must Java split a single exception across multiple files so that no file exceeds 1000 bytes?

**Answer:** **No.** The limit is an approximate rotation trigger; it is not a guarantee to split individual large events into multiple parts. Cap event sizes and test with realistic payloads.

### Exercise 3 — Logback maxHistory

A `SizeAndTimeBasedRollingPolicy` has `fileNamePattern="app-%d{yyyy-MM-dd}.%i.log"`, `maxFileSize=5MB`, `maxHistory=7`.

**Question:** Can there be 30 archives in the same day? Does this configuration automatically keep exactly 7 files?

**Answer:** **There can be many files per day** due to the `%i` index; `maxHistory=7` is a limit of **7 daily periods**, not 7 files. Disk usage also depends on `totalSizeCap` and cleanup.

### Exercise 4 — Why Does Rotation Fail While Append Still Works?

A process has write permission on `app.log`, but lacks permission to create new files in the directory. **Question:** What behavior can occur?

**Answer:** Appending to the current file may succeed; when rotating, renaming/creating the active or archive file fails. Check directory permissions, not just file permissions.

### Exercise 5 — Two JVMs Using the Same File

Two instances write to and rotate `/data/app.log` on a shared volume. **Question:** Why is simply choosing the same size threshold not enough?

**Answer:** Rotation involves renaming, file locking, reopening, cleanup, and concurrent writes. You need a supported coordination mechanism, or give each instance its own file or route logs via stdout and a collector.

### Exercise 6 — Sizing Based on Throughput

A service generates about **1 MiB of logs per minute** and uses 6 JUL files with `limit=10MiB`. At a constant rate, how long is the average history window?

**Answer:** About **60 minutes**, since the total capacity is roughly `6 × 10MiB = 60MiB`. This is an **estimate**, not guaranteed retention; log bursts and record sizes affect it.

## 18. Size-Based Rotation Implementation Checklist

- [ ] Confirm the **actual backend**: JUL, Logback, Log4j 2, or another system.
- [ ] Distinguish **byte threshold**, **trigger condition**, and **retention**.
- [ ] For JUL, verify `limit`, `count`, `append`, `%g`/`%u`.
- [ ] For Logback, use the appropriate policy and include both `%d` and `%i` when choosing size-and-time.
- [ ] Distinguish `maxHistory` by **period** from `totalSizeCap` by archive size.
- [ ] Do not treat the size threshold as an absolute byte ceiling for every event.
- [ ] Leave disk/quota headroom for the active file, archives, compression, and bursts.
- [ ] Ensure the JVM user has write permissions on **the file and archive directory**, including rename/delete.
- [ ] Do not let two independent JVMs/appenders rotate the same active file without explicit support.
- [ ] Do not use external `logrotate` and backend rotation simultaneously without a coordination mechanism.
- [ ] Test actual rollover multiple times, including restarts, file permissions, and collector tailing.
- [ ] Use a test event with a known ID to verify archives and the active file; do not rely only on startup success.
- [ ] Monitor log-volume growth, rotation errors, archive cleanup, and remaining disk space.
- [ ] For Docker/Kubernetes, prefer stdout/stderr and the platform's logging pipeline where appropriate.
- [ ] If durable auditing is required, use a dedicated storage system rather than relying on a local file ring.

**Conclusion:** Size-based rotation is the mechanism of **keeping each log file at a manageable size and switching to a new file when a threshold is reached**. JUL provides `FileHandler(limit, count, append)`; Logback provides `RollingFileAppender` and rolling policies. A sound design must account for **byte-based sizing, retention, create/rename permissions, restarts, multiple processes, collectors, and actual disk capacity**. Rotation helps control file size; it **does not by itself guarantee zero log loss or long-term history retention**.
