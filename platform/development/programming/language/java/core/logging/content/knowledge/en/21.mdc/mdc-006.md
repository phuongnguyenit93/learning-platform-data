# Per-User MDC — Safely Attaching User Context to Java Logs

## 1. Concept and Scope

**MDC (Mapped Diagnostic Context)** is a mechanism for storing key–value pairs for logging. While a request is being processed, an application can place **requestId**, **actorType**, **actorRef**, or other permitted correlation fields into the MDC so that the Logger and encoder output them alongside multiple log events within that processing scope.

**Per-user MDC** is the practice of putting **reference information about a verified acting user/principal** into the logging context, and then **clearing or restoring the context according to the proper lifecycle** to prevent one user's information from accidentally appearing in another user's logs.

An illustrative log sequence:

~~~text
INFO | requestId=req-101 actorType=user actorRef=usr-7 | event=request.started
INFO | requestId=req-101 actorType=user actorRef=usr-7 | event=order.validated
WARN | requestId=req-101 actorType=user actorRef=usr-7 | event=dependency.slow durationMs=800
~~~

Here, **actorRef=usr-7** is a pseudonymous reference ID, not an email or token. **requestId** identifies a single processing execution; **actorRef** identifies the actor according to policy; **event** is a stable event code. The three lines above are a formatting example, not the default output of every backend.

**MDC is not an authentication or authorization mechanism**. Having actorRef in the MDC only indicates that some piece of code set that value; it does not prove the user has permission to access data. Authorization decisions must rely on the security context and trusted policy checks.

### Learning Objectives

After this lesson, you will know how to:

1. Choose the right user fields instead of logging an entire user profile.
2. Distinguish between user/actor, requestId, traceId, tenant, and subject.
3. Obtain actorRef from a verified identity rather than from a self-declared client header.
4. Use **org.slf4j.MDC** to set, read, remove, and restore context.
5. Prevent user mix-ups when HTTP worker threads are reused.
6. Propagate context in a controlled manner to ExecutorService, CompletableFuture, and background tasks.
7. Configure Logback to output MDC in text or structured logging formats.
8. Verify behavior with a Java 17 program and deterministic stdout.

## 2. Why Per-User MDC?

In a multi-request application, code might log:

~~~java
LOG.info("event=order.started");
LOG.info("event=order.validated");
LOG.warn("event=payment.retry");
~~~

This is only an illustrative snippet requiring a declared Logger. If a thousand requests arrive simultaneously, three log lines are not enough to distinguish which request caused an error. You could manually pass IDs into every call:

~~~java
LOG.info("event=order.started requestId={} actorRef={}",
        requestId, actorRef);
~~~

However, that is easy to forget in the repository layer or in a library that uses its own Logger. MDC helps create context at the **processing boundary**, and the backend can then automatically include those fields in log events:

~~~text
HTTP request
     |
     v
Authentication / trusted identity
     |
     v
Create request-scoped MDC
  requestId=req-101
  actorType=user
  actorRef=usr-7
     |
     v
Controller -> Service -> Repository
     |           |           |
   LOG.info    LOG.warn    LOG.error
     |           |           |
     +-----------+-----------+
                 |
                 v
         Logback encoder
         (%X{requestId},
          %X{actorRef})
                 |
                 v
         stdout / file / collector
                 |
                 v
       finally: restore or clear
~~~

MDC supports log consistency, but **does not replace passing business parameters**: if order processing needs a customerId or permissions, business code must still obtain them from a trusted source and pass them through the appropriate API rather than depending on MDC.

## 3. Distinguishing Identifiers

| Field | Example | Meaning | What to Avoid |
| --- | --- | --- | --- |
| requestId | req-101 | A single processing execution/request | Treating it as a user ID |
| actorType | user / anonymous / service | Type of acting principal | Assuming every request is authenticated |
| actorRef | usr-7 | Reference code for the acting principal | Logging raw email/JWT/token directly |
| traceId | trace ID | Cross-service flow correlation | Generating it from email or customerId |
| spanId | span ID | Processing step of a trace | Using it instead of requestId |
| tenantRef | tenant-3 | Associated tenant | Using it as the basis for authorization |
| subjectRef | usr-9 | Target entity being acted upon | Conflating it with actor |
| jobId | job-45 | Background task | Forcing every job to belong to the most recent user |
| event | order.created | Stable event type | Adding dynamic IDs into the event name |
| errorCode | ACCESS_DENIED | Stable error code | Using raw exception.message |

Across different systems, the field name might be userId, actorId, or actorRef. This lesson uses **actorRef** because it clearly represents an actor reference without implying direct identifying data by default. The project team should choose **a single unified schema** so dashboards and queries do not break.

**An opaque ID is not automatically anonymous.** If actorRef can be linked to a user record, it is still personal-related data and requires access controls, retention limits, and data-handling policies. Do not simply hash an email without a key and conclude it is non-identifiable.

### One User, Many Requests

One user can generate many requests, so actorRef stays the same while requestId differs. An anonymous request still has a requestId but **does not need an actorRef**. A system task can have actorType=service and a jobId without attaching a user.

Illustrative JSON objects:

~~~json
{"event":"catalog.view","requestId":"req-102","actorType":"anonymous"}
{"event":"order.created","requestId":"req-103","actorType":"user","actorRef":"usr-7"}
{"event":"report.started","jobId":"job-45","actorType":"service","actorRef":"svc-report"}
~~~

Do not use the same actorRef="anonymous" and treat all unauthenticated visitors as a single user. If anonymous behavior analysis is needed, use a mechanism compliant with consent and data protection rules rather than placing an indefinite tracking ID in logs.

## 4. Choosing Which User Data Is Allowed in MDC

**Consider logging:** requestId, actorType, an opaque actorRef when there is a valid need, tenantRef when supporting multi-tenant investigations, managed traceId/spanId, and schema-compliant event/errorCode.

**Do not log in raw form:** passwords, access tokens, refresh tokens, API keys, private keys, Authorization headers, session cookies, payment card numbers, full JWTs, raw HTTP bodies, or principal `object.toString()`.

Evaluation table:

| Data | Recommendation | Reason |
| --- | --- | --- |
| System-generated or validated requestId | Commonly used | Find logs for the same request |
| actorType | Useful when verified | Distinguish user, service, anonymous |
| Opaque actorRef | Only when genuinely needed | Can be linked back to an individual |
| tenantRef | Architecture-dependent, with ACL | Must prevent log leakage across tenants |
| Email, name, phone number | Avoid by default | Direct identifiers and privacy risk |
| JWT/credential | Do not log | Exposes authentication secrets |
| Full user roles/permissions | Avoid by default | May expose internal policies/privileges |
| IP and user-agent | Weigh carefully | May constitute identifying data |
| Stack traces and exception messages | Selective | May contain paths, payloads, and sensitive data |

**Data minimization** does not mean stripping all context. It means each field needs a clear purpose and appropriate storage permissions. If traceId alone is sufficient to locate the entire request, downstream services do not necessarily all need to log actorRef.

### The Identity Source Must Be Trusted

For HTTP:

~~~text
Incoming request
    |
    v
Authentication middleware
    |
    v
Verified principal / service identity
    |
    +--> Authorization (separate)
    |
    v
Allowlist logging fields
    |
    v
MDC scope
    |
    v
Application events
~~~

Do not take actorRef from a client-sent header such as X-User-Id and label it as a verified user. If a trusted gateway forwards identity via headers, there must be trust-boundary protection and corresponding verification mechanisms.

**Using MDC.get("actorRef") to grant permissions is wrong**. MDC can be set by auxiliary code and does not have the integrity or lifecycle designed for authorization.

## 5. How Does MDC Work in SLF4J + Logback?

Basic APIs of **org.slf4j.MDC**:

| API | Role |
| --- | --- |
| MDC.put(key, value) | Attaches a String value to the current thread's context |
| MDC.get(key) | Reads the value of a key in the current context |
| MDC.remove(key) | Removes a single key |
| MDC.clear() | Clears the thread's entire MDC map |
| MDC.getCopyOfContextMap() | Captures a copy of the current map, which may be null |
| MDC.setContextMap(map) | Replaces the current MDC map with the provided values |
| MDC.putCloseable(key, value) | Sets a key and returns a resource to remove it on close |

In typical Logback implementations, context is thread-local and can be captured by the backend into logging events. A thread pool worker **does not automatically inherit all of the caller's MDC**. Do not assume identical behavior across SLF4J + Logback, Log4j 2, JUL, or other providers.

### Example of a Short Scope

~~~java
// Java snippet inside a class where LOG is already declared.
try (org.slf4j.MDC.MDCCloseable request =
        org.slf4j.MDC.putCloseable("requestId", "req-101");
     org.slf4j.MDC.MDCCloseable actor =
        org.slf4j.MDC.putCloseable("actorRef", "usr-7")) {
    LOG.info("event=order.created");
}
~~~

This snippet is **not a standalone program**. Upon exiting try-with-resources, the closeables remove their keys, even if an exception occurs.

**Watch out for nested scopes:** MDCCloseable does not guarantee restoring the previous value of the same key. If an outer scope already has requestId and an inner scope overwrites it, closing the inner scope may remove the key instead of restoring the prior value. For nested contexts, **snapshot/restore** or use a tested abstraction.

## 6. Proper Lifecycle: Set, Log, and Restore

A server may use the same thread to handle request A and then request B. If actorRef from request A is not cleaned up, an anonymous request B could be tagged with the wrong actorRef.

Illustrative mistake:

~~~text
Request A: actorType=user actorRef=usr-7
Request B: actorType=anonymous actorRef=usr-7   <-- CONTEXT LEAK
~~~

This is a logging context bug; it does not mean request B was actually authenticated as usr-7.

Basic **snapshot/restore** pattern:

~~~java
// Illustrative snippet; requires importing MDC and Map,
// variables trustedRequestId/approvedActorRef exist in the real context.
Map<String, String> before = MDC.getCopyOfContextMap();
try {
    MDC.clear();
    MDC.put("requestId", trustedRequestId);
    MDC.put("actorType", "user");
    MDC.put("actorRef", approvedActorRef);

    // Business processing and logging go here.
} finally {
    if (before == null) {
        MDC.clear();
    } else {
        MDC.setContextMap(before);
    }
}
~~~

### Why Restore Previous Instead of Always Calling Clear?

A tracing library may set traceId/spanId in an outer scope. If an inner module calls MDC.clear() when finishing, it can wipe out the outer scope's fields as well. **Restore previous** returns the context to its initial state, preserving valid pre-existing keys.

However, if the thread already leaked an actorRef from a previous request at the start, restoring previous simply brings back that bad state. A trusted **outermost request boundary** must still ensure **a new request does not inherit the previous user's identity**. Define clearly which module owns full clearing and which modules only add/restore specific fields.

### Lifecycle Rules

1. Generate request/correlation IDs at a trusted boundary or validate incoming IDs.
2. Verify the user before creating authenticated fields.
3. Set actorType and actorRef according to an allowlist.
4. Run logger calls inside `try`.
5. Clean up/restore MDC in `finally`.
6. For async processing, implement dedicated propagation and cleanup.
7. Do not let context live longer than the logical operation requires.

Do not log secrets at DEBUG under the assumption that production runs at INFO. Log levels can be changed during incident investigation, and collectors may store logs across multiple environments.

## 7. Runnable Example: Java 17 + Maven + SLF4J + Logback

This example simulates **two consecutive requests on the main thread** and a **single-worker ExecutorService**:

- Request A has user usr-7; request B is anonymous.
- MDC is set on the caller and captured before submitting the task.
- The worker installs the captured context, logs, and then restores the previous state.
- Logs after the two requests do not carry the old user context.
- No HTTP server or database is needed, allowing clear observation of the MDC mechanism.

### 7.4. src/main/java/demo/MdcUserDemo.java

~~~java
package demo;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;

import java.util.Map;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public final class MdcUserDemo {
    private static final Logger LOG =
            LoggerFactory.getLogger(MdcUserDemo.class);

    private MdcUserDemo() {
    }

    public static void main(String[] args) throws Exception {
        ExecutorService executor = Executors.newSingleThreadExecutor();

        try {
            LOG.info("event=app.ready");

            handleRequest(executor, "req-101", "user", "usr-7");
            handleRequest(executor, "req-102", "anonymous", null);

            executor.submit(() ->
                    LOG.info("event=worker.after_requests")).get();

            LOG.info("event=app.finished");
        } finally {
            executor.shutdown();
        }
    }

    private static void handleRequest(
            ExecutorService executor,
            String requestId,
            String actorType,
            String actorRef) throws Exception {

        Map<String, String> previous = MDC.getCopyOfContextMap();

        try {
            MDC.clear();
            MDC.put("requestId", requestId);
            MDC.put("actorType", actorType);

            if (actorRef != null) {
                MDC.put("actorRef", actorRef);
            }

            LOG.info("event=request.started");

            Map<String, String> captured =
                    MDC.getCopyOfContextMap();

            executor.submit(() -> {
                Map<String, String> workerPrevious =
                        MDC.getCopyOfContextMap();
                try {
                    setOrClear(captured);
                    LOG.info("event=work.saved");
                } finally {
                    setOrClear(workerPrevious);
                }
            }).get();

            LOG.info("event=request.finished");
        } finally {
            setOrClear(previous);
        }
    }

    private static void setOrClear(Map<String, String> context) {
        if (context == null || context.isEmpty()) {
            MDC.clear();
        } else {
            MDC.setContextMap(context);
        }
    }
}
~~~

**This is a complete Java class.** The single-thread executor and `Future.get()` calls make the ordering of logger calls predictable. In this lesson, `handleRequest` only simulates a trusted identity; there is no real authentication code.

**Calling `MDC.clear()` at the start of the request is intentional for this demo**, because no tracing framework owns another context. On a real server, clearing could erase a traceId set by an outer scope; align on ownership and choose the appropriate field set/restore mechanism.

### 7.6. Output Explanation

1. **app.ready** occurs before setting MDC, so all three keys are empty.
2. **req-101** sets `actorType=user` and `actorRef=usr-7`; `request.started`, `work.saved`, and `request.finished` all have that context.
3. **work.saved for req-101** is logged from the worker thread, but receives the snapshot via `setContextMap(captured)`.
4. The worker saves `workerPrevious` and restores it in `finally`, so req-101's context does not get stuck in the thread pool.
5. **req-102** (anonymous) does not set `actorRef`; none of its three events print `usr-7`.
6. **worker.after_requests** runs on the same single-thread executor but has no MDC from either request, demonstrating proper cleanup in the demo flow.
7. **app.finished** also has no request MDC once `handleRequest` has restored `previous`.
8. **shutdown** stops accepting new tasks; in the demo, all tasks were awaited to completion via `Future.get()`.

This example **does not prove** that all context in async servlets, reactive pipelines, virtual threads, or across the network is propagated automatically. Each execution model requires an appropriate propagation procedure.

## 8. Applying to an HTTP Filter or Interceptor

In a web framework, user MDC should be created **after identity has been authenticated**, or in two stages: set `requestId` before authentication, and add `actorRef` after authentication.

A **Java pseudocode** snippet:

~~~java
// Pseudocode: not a standalone Servlet/Spring program.
// trustedRequestId and principal come from a verified source.
Map<String, String> before = MDC.getCopyOfContextMap();
try {
    MDC.put("requestId", trustedRequestId);
    MDC.put("actorType",
            authenticated ? "user" : "anonymous");

    if (authenticated) {
        MDC.put("actorRef", approvedActorRef);
    } else {
        MDC.remove("actorRef");
    }

    // filterChain.doFilter(request, response);
} finally {
    if (before == null) {
        MDC.clear();
    } else {
        MDC.setContextMap(before);
    }
}
~~~

### Boundaries to Consider

- **Filter running before authentication:** cannot yet know the verified `actorRef`. Do not blindly take it from query parameters or headers.
- **Filter running after authentication:** can obtain an approved ID from a trusted principal.
- **Error dispatch:** error-handling paths sometimes run on a different dispatch; ensure MDC is set/restored properly.
- **Async servlets or callbacks:** may run on different threads; do not assume the original thread's scope covers everything.
- **Batch scheduler/job:** has no direct user; use `actorType=service` and `jobId` if needed.
- **Anonymous request:** do not log a fake `actorRef`, but still include `requestId` for investigation.
- **Tenant:** `tenantRef` must come from a trusted source; do not use MDC as proof of resource access rights.

In Spring or a specific framework, filter placement must be based on the actual security chain and execution model. There is no single filter position that is right for every application.

## 9. Propagating MDC Across ExecutorService and CompletableFuture

**The caller's MDC does not automatically follow every task**. A task may run in a thread pool after the request has already finished. If the worker does not receive a snapshot, logs may lack context; if it does not restore, the next task may carry the old actor.

Procedure:

1. Snapshot the caller's MDC at submission time.
2. Propagate only approved fields if a restriction policy exists.
3. The worker saves its previous MDC.
4. The worker sets the snapshot (or clears according to contract).
5. Run the task.
6. In `finally`, restore previous.
7. Do not use the snapshot as a basis for authorization: permissions may change between submission and execution.

Illustrative wrapper:

~~~java
// Method snippet requiring imports for java.util.Map and org.slf4j.MDC.
static Runnable withMdc(Runnable task,
                        Map<String, String> snapshot) {
    return () -> {
        Map<String, String> previous = MDC.getCopyOfContextMap();
        try {
            if (snapshot == null) {
                MDC.clear();
            } else {
                MDC.setContextMap(snapshot);
            }
            task.run();
        } finally {
            if (previous == null) {
                MDC.clear();
            } else {
                MDC.setContextMap(previous);
            }
        }
    };
}
~~~

This is an illustrative method that belongs inside a class. In production, prefer framework-compatible task decorators or propagation libraries rather than creating inconsistent custom wrappers.

**`CompletableFuture.supplyAsync`**, reactive pipelines, and virtual threads each have their own scheduling/context characteristics. Do not infer a one-to-one mapping between a thread and a user. One user may have many requests, one request may run across many threads, and one pool thread may serve many users over time.

### User Context Is Not Permission Context

If a job is submitted by user `usr-7` but runs after the user loses permissions, snapshotting `actorRef` must not be treated as continued authorization. Business logic must determine valid identity/permissions at execution time according to contract, not based on an MDC snapshot.

### Do Not Propagate Arbitrary Fields

Copying the entire MDC can carry over information set by other libraries, including data that should not leave the request boundary. Propagate only approved keys—typically `requestId`/`traceId`, and `actorRef` when genuinely needed. If a worker does not need to know the user for logging, consider omitting `actorRef`.

## 10. MDC Does Not Automatically Propagate Over the Network

In microservices:

~~~text
Gateway -> Order Service -> Payment Service
   |            |                |
thread A      thread B          thread C
~~~

MDC on thread A does not automatically appear on threads B or C. Request/trace context can be propagated over protocols, but **do not treat a header/baggage containing `userRef` as proof of authentication**. Identity for business logic must be verified through a dedicated security propagation mechanism.

- **traceId/spanId** serve distributed tracing.
- **requestId** serves per-request search depending on architecture.
- **actorRef** only needs to be logged in services where there is a need/policy.
- Do not put emails or tokens into tracing baggage; baggage can traverse external systems.

A downstream service may only need `traceId` for investigation without logging `actorRef`. This reduces the spread of personal data across the logging platform.

## 11. Structured Logging: Putting MDC into Queryable Fields

A Logback text pattern:

~~~xml
<pattern>%d{yyyy-MM-dd'T'HH:mm:ss.SSSXXX} %-5level requestId=%X{requestId} actorType=%X{actorType} actorRef=%X{actorRef} %logger - %msg%n</pattern>
~~~

is only the **pattern element inside an encoder**, not a complete configuration file. This format is human-readable, but `key=value` text does not automatically become typed fields in a collector.

An illustrative **JSON Lines** record:

~~~json
{"schemaVersion":1,"timestamp":"2026-11-09T10:15:00.125Z","level":"INFO","service":"order-api","event":"order.created","requestId":"req-101","actorType":"user","actorRef":"usr-7","outcome":"success"}
~~~

To query by field:

- The backend must actually have an appropriate JSON/structured encoder.
- The encoder must include MDC fields in the payload under the specified names.
- The collector must parse and index/map those fields.
- Do not create duplicate `actorRef` keys from both MDC and event key-values with different values.
- A missing `actorRef` for anonymous requests must have a clear meaning, rather than treating an empty string as a real user.
- The JSON encoder must escape quotes, newlines, and control characters.
- Maintain `schemaVersion`/migration when changing field naming or semantics.

### MDC and SLF4J 2 Key-Value Logging

MDC is typically used for fields that **apply across multiple events within a scope**. A field that applies only to a single event should be placed on that event itself:

~~~java
// Illustrative code snippet; LOG and orderId are already declared.
LOG.atInfo()
        .addKeyValue("event", "order.created")
        .addKeyValue("orderId", orderId)
        .addKeyValue("outcome", "success")
        .log("Order accepted");
~~~

SLF4J 2 provides key-value pairs, but **does not automatically guarantee that every encoder outputs JSON or that collectors index fields properly**. Verify the backend, encoder, and results in the log-receiving system.

## 12. Actor, Subject, Anonymous, Service, and Multi-Tenant

**Actor** is the executing principal; **subject** is the person or resource being acted upon. They differ when a support agent updates a customer's account.

~~~json
{"event":"account.support_update","actorType":"user","actorRef":"staff-12","subjectRef":"customer-8","requestId":"req-900","outcome":"success"}
~~~

This is illustrative data. Logging only `userId=customer-8` could mislead investigators into thinking the customer performed the action themselves. **subjectRef** is usually an attribute of a specific event and does not necessarily belong in MDC for every log in the request.

| Scenario | Appropriate Context |
| --- | --- |
| Authenticated user | `actorType=user`, permitted `actorRef`, `requestId` |
| Anonymous | `actorType=anonymous`, `requestId`, `actorRef` absent |
| Cron/scheduler | `actorType=service`, `jobId`, `actorRef` if appropriate |
| Service-to-service | Verified service identity, `traceId` |
| Support acting on behalf of user | Staff's `actorRef`, customer's `subjectRef` |
| Multi-tenant | Verified `tenantRef` and isolated log access permissions |

**`tenantRef` in MDC does not automatically enforce row-level security**. Authorization in the storage/business layer must be checked separately. Dashboards and log stores must also enforce access controls; otherwise, one tenant's logs could be viewed by another tenant.

## 13. Security, Retention, and Log Injection

User MDC can turn individual events into records describing user behavior. You need:

1. **Data minimization:** only purposeful fields; never dump the principal.
2. **No credential logging:** access tokens, refresh tokens, passwords, cookies, or private keys.
3. **Allowlist:** approved MDC keys and size/format limits.
4. **Escaping:** client data can contain newlines/control characters that forge log entries.
5. **Access control:** who is allowed to search `actorRef` and in which environments?
6. **Retention:** how long are logs kept and what are the personal-data handling procedures?
7. **Tenant isolation:** prevent unauthorized cross-tenant queries.
8. **Masking/pseudonymization:** use a verified design; simple hashing does not automatically anonymize.
9. **Exception messages:** be careful with `Throwable` or `object.toString()` containing sensitive data.
10. **Review recipients:** logs may be shipped to SIEM, cloud collectors, CI/CD, or third-party systems.

**Do not assume every event needs `actorRef`.** System events like `service.started`, `health.checked`, or `cache.evicted` may only need `service`, `event`, and `traceId` if relevant. Logging `actorRef` everywhere increases the privacy surface and indexing cost.

### Performance and Cardinality

MDC is a small map, but copying it into every task has a cost. Do not create hundreds of keys or stuff an entire JSON profile into a single field. **`actorRef` typically has very high cardinality**; do not use it as an unbounded metric label. For metrics, choose bounded labels; use logs/traces with appropriate access controls when investigating a specific user.

### Not a Replacement for an Audit Store

`ConsoleAppender`/`FileAppender` can be filtered, drop events when queues fill, or fail on I/O errors. A `LOG.info` line with `actorRef` **is not sufficient to guarantee durable auditing**. If an event must be recorded before business completion, use an audit/event store or an appropriate transactional mechanism rather than relying solely on MDC.

## 14. Common Mistakes

| Mistake | Consequence | Fix |
| --- | --- | --- |
| Setting `actorRef` from client-sent `X-User-Id` | Logs can be spoofed | Obtain from verified principal |
| Using `MDC.get` for authorization | Incorrect access grants | Use dedicated security context |
| Logging JWT, email, or raw objects | Data exposure across many records | Opaque reference, allowlist |
| Not clearing after a request | Request B carries A's actor | Scope/`finally` |
| Clearing in nested scope without restoring | Loses `traceId` or outer context | Snapshot/restore |
| Nesting `putCloseable` with same key expecting restore | Loses outer scope value | Manage nested scopes properly |
| Assuming MDC automatically crosses executor | Worker lacks user context | Capture/install/restore |
| Copying entire MDC to every worker | Spreads unnecessary data | Propagate only approved fields |
| Anonymous keeps previous `actorRef` | Logs tagged with wrong user | Remove/do not set `actorRef` |
| Putting `userRef` into event name | Cannot group event types | Separate field, fixed event code |
| Backend does not output `%X` or MDC JSON | Fields missing from logs | Configure encoder properly |
| Confusing JUL `ConsoleHandler` with Logback | Expected MDC not visible | Verify provider/backend |
| Mixing up actor and subject | Misattributes who acted | Separate `actorRef`/`subjectRef` |
| Enabling DEBUG logging for all request payloads | Data leaks/high volume | Selective safe logging |
| Renaming `actorRef` without migration | Alerts/searches break | Schema versioning |
| Attaching `actorRef` to metric labels | High cardinality and privacy risk | Use bounded labels for metrics |

## 15. Diagnostic Procedure When User MDC Is Missing or Wrong

1. Was the log emitted **before or after authentication**?
2. Was `actorRef` taken from a verified principal or client data?
3. Was MDC set **on the same thread** as the Logger call?
4. Did the request cross **ExecutorService, CompletableFuture, or reactive** boundaries?
5. Was the snapshot created **before or after setting `actorRef`**?
6. Did the worker install the snapshot and restore in `finally`?
7. Is the thread pool leaking keys from a previous task?
8. Did a nested scope remove an outer scope's key?
9. Does the Logback encoder output `%X{actorRef}` and `%X{requestId}`?
10. Does the collector parse, rename, drop, or mask those fields?
11. Was `actorRef` confused with `subjectRef`/`tenantRef`?
12. Do any logs contain tokens, emails, or PII outside policy?
13. Was the event filtered out by level/filter before reaching the appender?
14. Have two requests from different users on the same worker been tested?
15. Is a schema migration or framework context propagation fix needed?

**A missing `actorRef` is not enough to conclude a request is anonymous.** The event may have been emitted before authentication, context may have been passed to the wrong thread, the encoder may not output the field, or policy may have intentionally excluded it.

## 16. Testing Checklist

A useful test suite should cover:

- Authenticated request logs `actorType=user` and permitted `actorRef`.
- Anonymous request logs `actorType=anonymous` and has no `actorRef`.
- Two consecutive requests on the same pool do not mix up users.
- Worker receives the exact approved snapshot.
- Subsequent worker task does not retain the previous task's `actorRef`.
- Exceptions in request/task still execute `finally`.
- Nested scope restores `previous` properly without losing tracing context.
- Service principal/job has appropriate `actorType` and `jobId`.
- Delegated access distinguishes actor and subject.
- `tenantRef` is not mixed up or leaked via cross-tenant log store queries.
- Encoder outputs MDC fields; collector queries match the schema.
- No prohibited tokens, passwords, or emails appear at any log level.
- Long fields or inputs containing newlines are validated/escaped.
- Field renames have compatibility tests for alerts/dashboards.

For the program in Section 7, the three observable pieces of evidence are: `req-101` has `usr-7`, `req-102` is `anonymous` with no `actorRef`, and `worker.after_requests` has no MDC remaining. These are **results of the demo flow**, not an automatic guarantee for every server or framework.

## 17. Questions and Answers

**Q1.** Is per-user MDC the same as authentication?

**A:** No. MDC is only for logging context; permission information relies on a verified security context.

**Q2.** Why is `actorRef` different from `requestId`?

**A:** `actorRef` represents the acting principal, while `requestId` represents a single processing execution. One user can have many requests.

**Q3.** When a request is anonymous, is `actorRef` needed?

**A:** Not necessarily; typically it has `actorType=anonymous` and no `actorRef`.

**Q4.** Can `actorRef` be taken from `X-User-Id` sent by the client?

**A:** It cannot be treated as a verified identity without a corresponding trust boundary and verification.

**Q5.** Why must MDC be cleared or restored in `finally`?

**A:** To guarantee cleanup even when an exception occurs, preventing user leaks between requests.

**Q6.** Does `MDCCloseable` automatically restore the old value of the same key in a nested scope?

**A:** Not guaranteed; `close` removes the key. Use snapshot/restore if you need to preserve `previous`.

**Q7.** Does MDC automatically travel from the caller to an `ExecutorService`?

**A:** Do not assume so; an appropriate propagation mechanism is required.

**Q8.** Why must a worker restore the pre-task context?

**A:** To avoid leaking the current task's context to the next task or breaking a valid context from an outer wrapper.

**Q9.** Why is `actorRef` missing from logs even though `MDC.put` was called?

**A:** The backend/encoder may not be outputting the key, the logger call may be running on a different thread, or the collector may not be parsing it.

**Q10.** Is an opaque `userRef` completely anonymous data?

**A:** No. If it can be linked to an individual, it still requires privacy policies.

**Q11.** Does MDC automatically propagate to another microservice?

**A:** No. Trace/request context requires separate propagation; identity for business logic requires separate verification.

**Q12.** When a support agent updates a customer's account, who are the actor and the subject?

**A:** The actor is the staff member, and the subject is the customer account; both fields should be distinguished during investigation/auditing.

**Q13.** Should `actorRef` be used as an unbounded metric label?

**A:** No; it easily creates high cardinality and personal-data risks.

**Q14.** Does `actorRef` in a `ConsoleAppender` automatically create a durable audit trail?

**A:** No. Logging can be filtered, dropped, or fail on I/O; auditing requires an appropriate storage mechanism.

**Q15.** In the demo, why does `worker.after_requests` not have `usr-7`?

**A:** Each task restored `workerPrevious` in `finally`; the worker thread was reused without retaining the previous task's user context.

## 18. Conclusion

**Per-user MDC** is a technique for attaching **minimal, permitted principal context** to log events and managing its lifecycle properly.

Remember six principles:

1. **Actor from a trusted source**, not from self-declared client data.
2. **Few, meaningful fields**: `requestId`, `actorType`, `actorRef` when needed, and controlled trace/tenant context.
3. **Accurate scoping**: set inside `try`, clean up/restore in `finally`.
4. **Async is not automatic**: capture/install/restore when crossing worker or framework execution contexts.
5. **Schema and encoder must match**: MDC fields are actually output and parsed by the collector.
6. **Do not use MDC in place of security/audit**: access rights must be authenticated; audit durability requires dedicated storage.

An application can call `MDC.put` successfully and still produce wrong logs if `actorRef` is unverified, the encoder does not print the field, or a worker thread retains old context. **Per-user MDC is only trustworthy when the identity source, context propagation, cleanup, schema, and data-protection policies are all tested.**
