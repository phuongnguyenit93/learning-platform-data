# Log4j2 Version Management in Java Projects

## 1. Why is Log4j2 version management part of logging?

**Apache Log4j 2** is a multi-module logging system: an API for Java code to emit events, an implementation/backend to process events, and additional bridges, layouts, appenders, or integrations. An application can work in a development environment yet fail at runtime if logging JARs are resolved from incompatible versions or if multiple competing backends are present.

**Log4j2 version management** is not just changing a number in pom.xml or build.gradle. It includes:

- Identifying the version **actually present on the runtime classpath**.
- Aligning the versions of modules released by Log4j.
- Checking transitive dependencies and framework-managed versions.
- Choosing the right bridge for SLF4J/JUL/Log4j 1 when genuinely needed.
- Tracking security patches, maintenance lifecycle, and JDK requirements.
- Testing logging behavior, configuration, performance, and rollback capability after an upgrade.

For example, a system using Log4j API version A with Log4j Core version B can encounter linkage errors at runtime, even though the Java source code still compiles. Conversely, importing the BOM correctly does not prevent an older library from bringing in Log4j 1 or another provider in the deployment package.

The goal of this lesson is to **establish a single consistent version source, verify resolved dependencies, and perform controlled upgrades**. The versions in the examples are illustrative and explicitly pinned; before deploying in production, consult the official release pages, security advisories, and organizational policies.

## 2. Distinguishing Log4j2 artifacts

A project does not necessarily need every artifact. Common components include:

| Maven Artifact | Role | When is it needed? |
| --- | --- | --- |
| **org.apache.logging.log4j:log4j-api** | Log4j 2 API, containing LogManager, Logger | Source code uses the Log4j API directly |
| **org.apache.logging.log4j:log4j-core** | Main backend for processing Log4j events | The application chooses Log4j Core as its implementation |
| **org.apache.logging.log4j:log4j-bom** | Bill of Materials to align Log4j module versions | Managing dependencies with Maven/Gradle |
| **org.apache.logging.log4j:log4j-slf4j2-impl** | Provider/bridge receiving logs from **SLF4J 2.x** and routing to Log4j API/Core | Libraries or code use SLF4J 2, and the target backend is Log4j Core |
| **org.apache.logging.log4j:log4j-slf4j-impl** | Binding for **SLF4J 1.x** | Only in an SLF4J 1.x ecosystem that needs the corresponding binding |
| **org.apache.logging.log4j:log4j-to-slf4j** | Routes Log4j API calls to SLF4J | When the target backend is in the SLF4J ecosystem, such as Logback; never use in the opposite direction alongside the bridge above |
| **org.apache.logging.log4j:log4j-1.2-api** | Partial compatibility bridge for the Log4j 1.x API | Controlled legacy migration plans |
| **org.apache.logging.log4j:log4j-jul** | Integration/bridge for Java Util Logging | When you want to route JUL according to the documented mechanism |
| **Other layout/appender modules** | Integration for JSON formats, special sources/sinks, etc. | Add only when architectural requirements demand it |

### How do API, implementation, and bridge differ?

~~~text
Application using Log4j 2 API:
Java code --> log4j-api --> log4j-core --> Console/File/Collector

Application using SLF4J 2 API with Log4j Core backend:
Java code --> slf4j-api --> log4j-slf4j2-impl
          --> log4j-api --> log4j-core --> Console/File/Collector

Application using Log4j 2 API with Logback backend:
Java code --> log4j-api --> log4j-to-slf4j
          --> slf4j-api --> Logback --> Console/File/Collector
~~~

**Do not use log4j-to-slf4j and log4j-slf4j2-impl simultaneously** in the same pipeline. These two bridges route events in opposite directions, which can create a routing loop or runtime errors. Similarly, **log4j-slf4j-impl** and **log4j-slf4j2-impl** are not two optional add-on dependencies: they serve two different SLF4J generations.

**An application** needs to choose one clear logging backend. **A library** should normally depend only on a logging API and let the application decide the implementation; do not force the entire system to use a provider chosen by the library.

## 3. Meaning of versions and release lifecycle

Log4j 2 versions typically follow the format:

~~~text
MAJOR.MINOR.PATCH
Example: 2.26.1
~~~

- **MAJOR:** A major change may include breaking changes and require migration.
- **MINOR:** A new feature branch may be added according to the project's compatibility policy.
- **PATCH:** Bug fixes, incident fixes, or security patches; do not assume there are no behavioral changes that require testing.

Apache publishes maintenance statuses, such as:
- **Active development (AD):** A branch under active development; per published policy, not every experimental release on this branch should be assumed to be a safe production choice.
- **Active maintenance (AM):** A stable, maintained branch suitable for production according to project policy.
- **End-of-maintenance (EOM):** Virtually no regular bug fixes remain; new security releases may be very limited.
- **End-of-life (EOL):** No longer maintained by the project.

Lifecycle statuses can change over time. **Do not assume a version is still safe just because it was once the latest**, or because the source code still runs on the current JDK.

When deciding to upgrade, check all of the following together:
1. **Release notes** for bug fixes and behavioral changes.
2. **Security advisories** to see which artifacts/versions are actually affected.
3. **Maintenance status** to avoid staying on an unmaintained branch long-term.
4. **System requirements**: JDK version, deployment environment, frameworks, and plugins.
5. **Integration compatibility**: SLF4J, bridges, appenders, layouts, XML/JSON/YAML configuration, and log collection agents.

**Log4j 1.x and Log4j 2.x differ by more than just a patch.** Log4j 1.x reached end-of-life long ago; its namespaces, configuration style, and internal components differ significantly. Migrating from Log4j 1 must be planned, not done by simply changing a JAR name in the build.

## 4. Using a BOM as a unified version source

A **BOM (Bill of Materials)** is a POM that manages the versions of a group of dependencies. Apache provides **log4j-bom** to manage Log4j 2 artifacts consistently.

A BOM is useful when a project needs:
- log4j-api for Java code;
- log4j-core at runtime;
- a bridge such as log4j-slf4j2-impl;
- additional appender/layout modules as needed.

Instead of writing separate version numbers in each dependency, you declare the **Log4j version in one place** and let the build tool resolve the modules according to the BOM.

**Limitations to understand:** The Log4j BOM manages the Log4j module group; it does not automatically guarantee that **org.slf4j:slf4j-api**, Spring Boot, Jackson, or every library in the system uses a compatible version. If a dependency declares a version directly, a framework imports a different BOM, a build script forces a version, or JARs are packaged manually, the outcome may differ from expectations. You must inspect the **resolved dependency tree**, not just read the POM contents.

## 5. Maven: dependencyManagement with log4j-bom

Example of a Java 17 project with **Log4j API** at compile time and **Log4j Core** at runtime:

~~~xml
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.apache.logging.log4j</groupId>
            <artifactId>log4j-bom</artifactId>
            <version>2.26.1</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>

<dependencies>
    <dependency>
        <groupId>org.apache.logging.log4j</groupId>
        <artifactId>log4j-api</artifactId>
    </dependency>
    <dependency>
        <groupId>org.apache.logging.log4j</groupId>
        <artifactId>log4j-core</artifactId>
        <scope>runtime</scope>
    </dependency>
</dependencies>
~~~

**This is an illustrative POM snippet**, not a complete pom.xml: place these blocks inside a valid project element. The number **2.26.1** is a Log4j 2 release published by Apache and used in the official BOM documentation. It is a **pinned sample version**, not an instruction to use this version forever or a claim about what the latest version is at any given time.

Why do the dependencies omit a version?

- **dependencyManagement** imports the BOM to manage versions.
- When Maven resolves **log4j-api** and **log4j-core**, it uses the corresponding managed version information.
- You only need to change one BOM version when intentionally upgrading a set of modules.

**Scope differs from role:** log4j-api is a compile dependency in this example; log4j-core can be runtime because the code does not directly import internal Core classes. Maven still includes Core on the runtime classpath for logging. If the code actually uses a module's API at compile time, the scope must reflect that.

**Do not add the BOM as a regular runtime dependency.** In Maven, the correct import form is **type=pom** and **scope=import** inside **dependencyManagement**.

## 6. Gradle: using platform and avoiding version drift

In Gradle Groovy DSL:

~~~groovy
dependencies {
    implementation platform(
        'org.apache.logging.log4j:log4j-bom:2.26.1'
    )

    implementation 'org.apache.logging.log4j:log4j-api'
    runtimeOnly 'org.apache.logging.log4j:log4j-core'
}
~~~

In Gradle Kotlin DSL:

~~~kotlin
dependencies {
    implementation(platform("org.apache.logging.log4j:log4j-bom:2.26.1"))
    implementation("org.apache.logging.log4j:log4j-api")
    runtimeOnly("org.apache.logging.log4j:log4j-core")
}
~~~

Both snippets are **examples of the dependencies block** in build.gradle or build.gradle.kts, assuming the project already applies the appropriate Java plugin and configures a repository such as Maven Central. In Gradle, `platform` contributes **version constraints** to resolution; if another dependency requests a different version or a rule forces a version, the final result still needs to be verified.

Some projects use `enforcedPlatform` to impose stronger constraints, but caution is needed when the project is a library or has other dependency consumers. **Do not choose enforcedPlatform just to make everything "certain"** without evaluating its impact on the dependency graph and downstream projects using the library.

### Checking the selected version in Gradle

~~~bash
./gradlew dependencies --configuration runtimeClasspath
./gradlew dependencyInsight --dependency log4j-core --configuration runtimeClasspath
./gradlew dependencyInsight --dependency log4j-api --configuration runtimeClasspath
~~~

On Windows, you can use **gradlew.bat**. These commands show how artifacts appear and why a particular version was chosen. Do not look only at the declared dependencies in build.gradle.

## 7. Runnable Maven + Java 17 example with BOM 2.26.1

The example below demonstrates configuring **a single place for version management** and verifying that the application actually logs through **Log4j Core**. The output is designed to be deterministic by using a pattern without timestamps or thread names.

### 7.1. Directory structure

~~~text
log4j-version-demo/
  pom.xml
  src/
    main/
      java/
        demo/
          Log4jVersionDemo.java
      resources/
        log4j2.xml
~~~

### 7.2. Complete pom.xml

~~~xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>

    <groupId>demo</groupId>
    <artifactId>log4j-version-demo</artifactId>
    <version>1.0.0</version>

    <properties>
        <maven.compiler.release>17</maven.compiler.release>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    </properties>

    <dependencyManagement>
        <dependencies>
            <dependency>
                <groupId>org.apache.logging.log4j</groupId>
                <artifactId>log4j-bom</artifactId>
                <version>2.26.1</version>
                <type>pom</type>
                <scope>import</scope>
            </dependency>
        </dependencies>
    </dependencyManagement>

    <dependencies>
        <dependency>
            <groupId>org.apache.logging.log4j</groupId>
            <artifactId>log4j-api</artifactId>
        </dependency>
        <dependency>
            <groupId>org.apache.logging.log4j</groupId>
            <artifactId>log4j-core</artifactId>
            <scope>runtime</scope>
        </dependency>
    </dependencies>

    <build>
        <plugins>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-compiler-plugin</artifactId>
                <version>3.13.0</version>
            </plugin>
            <plugin>
                <groupId>org.codehaus.mojo</groupId>
                <artifactId>exec-maven-plugin</artifactId>
                <version>3.5.0</version>
            </plugin>
        </plugins>
    </build>
</project>
~~~

In this example, no version is added to log4j-api or log4j-core. Neither slf4j-simple nor Logback is needed because the Java code uses the **Log4j API** directly and the target backend is Core.

### 7.3. src/main/resources/log4j2.xml

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<Configuration>
    <Appenders>
        <Console name="OUT" target="SYSTEM_OUT">
            <PatternLayout pattern="%p | %c{1} | %m%n"/>
        </Console>
    </Appenders>

    <Loggers>
        <Root level="info">
            <AppenderRef ref="OUT"/>
        </Root>
    </Loggers>
</Configuration>
~~~

The pattern intentionally uses **%p** (level), **%c{1}** (logger name shortened to the last segment), **%m** (message), and **%n** (newline). Console uses **SYSTEM_OUT** so stdout can be compared directly. In production systems, patterns usually also include timestamps, thread names, trace IDs, and exception formatting.

### 7.4. src/main/java/demo/Log4jVersionDemo.java

~~~java
package demo;

import org.apache.logging.log4j.LogManager;
import org.apache.logging.log4j.Logger;

public final class Log4jVersionDemo {
    private static final Logger LOG =
            LogManager.getLogger(Log4jVersionDemo.class);

    public static void main(String[] args) {
        LOG.debug("STARTUP_DIAGNOSTIC hidden by INFO");
        LOG.info("SERVICE_STARTED component={}", "billing");
        LOG.warn("DEPENDENCY_SLOW attempt={}", 2);
        System.out.println("APP_OK");
    }
}
~~~

This is a valid Java 17 program using Log4j API parameterization with **{}**. The file name matches the public class name; the `demo` package matches the directory path.

### 7.5. Running and verifying

In the directory containing pom.xml, with JDK 17 or later and Maven installed:

~~~bash
mvn -q compile exec:java -Dexec.mainClass=demo.Log4jVersionDemo
~~~

**Exact application stdout produced by the program:**

~~~text
INFO | Log4jVersionDemo | SERVICE_STARTED component=billing
WARN | Log4jVersionDemo | DEPENDENCY_SLOW attempt=2
APP_OK
~~~

Analysis:

1. Root is set to INFO, so **LOG.debug** is suppressed.
2. **LOG.info** produces an INFO record, replacing the placeholder with `billing`.
3. **LOG.warn** produces a WARN record, replacing the placeholder with `2`.
4. **PatternLayout** shows the short class name without the package prefix.
5. **System.out.println** prints `APP_OK` after the two log calls.
6. Because the Console target is SYSTEM_OUT, the application output appears in this order under this configuration. Maven or plugins may print additional messages if there are dependency download issues, separate from the three lines of program output.

The example does not rely on "printing the version" to prove the right JAR was selected. Inspecting **resolved dependencies** with the build tool in the next section is what reveals the actual version.

### 7.6. Viewing resolved Log4j versions

~~~bash
mvn dependency:tree -Dincludes=org.apache.logging.log4j
~~~

When configured properly, the dependency graph shows **log4j-api** and **log4j-core** at the version managed by the BOM, such as 2.26.1. The exact tree structure also depends on Maven plugins, other dependencies, and conflict resolution.

To view the full POM after applying parent configuration, profiles, and dependency management:

~~~bash
mvn help:effective-pom
~~~

Do not confuse the **declared POM** with the **classpath of the packaged artifact**. For fat JARs, container images, or custom packaging plugins, also inspect the dependencies inside the artifact actually being deployed.

## 8. When code uses SLF4J 2 with Log4j2 as the backend

Many frameworks and libraries log through **org.slf4j.Logger**. If you decide to use **Log4j Core** as the final backend, an appropriate provider/bridge is required.

In an application that already has a compatibly managed **SLF4J 2.x API**, add the runtime dependency under the Log4j BOM:

~~~xml
<dependency>
    <groupId>org.apache.logging.log4j</groupId>
    <artifactId>log4j-slf4j2-impl</artifactId>
    <scope>runtime</scope>
</dependency>
~~~

This is an **additional dependency snippet**, assuming the BOM is already imported and code or dependencies log through SLF4J 2.x. The bridge artifact follows the Log4j BOM version; the **version of slf4j-api** must be managed separately by the framework or compatible dependency management.

Do not mix them up:

~~~text
Do not use together:
  log4j-slf4j2-impl  +  log4j-to-slf4j

Do not treat as two providers to use simultaneously:
  log4j-slf4j-impl   +  log4j-slf4j2-impl

Do not mix:
  Logback's SLF4J provider and Log4j Core's SLF4J provider
  in the same application that only needs one backend.
~~~

**The log path must have a single consistent direction.** If an application uses Logback as its backend and needs to accept Log4j API calls, it can use **log4j-to-slf4j**; do not also add the reverse bridge.

For **SLF4J 1.x**, the binding name is different and the upgrade path is not the same as SLF4J 2.x. When upgrading Log4j2 in an older project, check the current SLF4J version instead of simply replacing `log4j-slf4j-impl` with `log4j-slf4j2-impl`.

## 9. Log4j2 and Spring Boot or framework dependency BOMs

Spring Boot applications usually already have **dependency management**. When the framework manages SLF4J, Log4j, and other components, importing another BOM yourself or hardcoding versions can alter the configuration tested by the framework.

Safe workflow:

1. Identify the **Spring Boot version**, JDK, and existing logging starters.
2. Inspect the dependency tree to see whether **Logback or Log4j Core** is the actual provider.
3. If switching to Log4j2, use the integration path/starter documented by the framework for the generation in use.
4. Override versions only when there is a clear need, typically a security patch, and verify all Log4j modules, bridges, plugins, and framework compatibility.
5. Run integration tests and verify logs in a production-like environment before releasing.

If both **spring-boot-starter-logging** and **spring-boot-starter-log4j2** are on the classpath in a way that introduces multiple providers, conflicts or unintended logging routes can occur. Do not apply blind exclusions; identify which dependency brings in each provider.

**Importing a BOM does not fix every dependency conflict.** Maven parents, framework `dependencyManagement`, BOM ordering, explicit versions, and build plugins can all affect the resolved version. Comparing **effective-pom** and **dependency:tree** before and after an upgrade provides better evidence than looking only at a single config file diff.

## 10. Transitive dependencies: a common source of old versions

Suppose the application declares a newer version of log4j-api/core, but a third-party library brings in an older logging dependency. In that case, verify:

- **Which artifact does it bring in?** log4j-api, log4j-core, old `log4j:log4j`, a bridge, or another provider?
- **Is the dependency actually present at runtime?** Test dependencies do not necessarily appear in deployment.
- **Which version does the build tool choose?** Maven has its own version resolution rules; Gradle has its own version conflict strategy.
- **Does the library use old APIs or internal classes?** Changing the version alone may not be enough.
- **Is there JAR shading/embedding?** A copy of Log4j bundled inside a library may not show up as a normal dependency.

Examples of finding dependencies in Maven:

~~~bash
mvn dependency:tree
mvn dependency:tree -Dincludes=org.apache.logging.log4j
mvn dependency:tree -Dincludes=log4j:log4j
mvn dependency:tree -Dincludes=org.slf4j
~~~

The **-Dincludes** commands filter output for easier inspection; view the full tree when you need to trace parent dependencies. If a conflicting dependency must be removed, declare an **exclusion on the exact dependency edge** and keep a supported alternative logging solution. Do not exclude a logging API that the library still uses, as this can cause **ClassNotFoundException** or **NoClassDefFoundError**.

In Gradle, use **dependencyInsight** to find why a version was selected; use package inspection tools if the build produces a shadow JAR, executable JAR, or container layer.

## 11. Security: manage Log4j2 by advisories, not by rumors

The history of Log4j vulnerabilities, especially **Log4Shell (CVE-2021-44228)**, shows that a logging library is also a critical security component. However, **you should not turn an old minimum version number into a "safe forever" rule**. Even after a major incident, new patches can still appear, including for API, Core, layout, or bridge components.

An example from an official advisory: **CVE-2026-49844** involves an invalid MapMessage-to-JSON encoding path under certain conditions; Apache recorded fixes in **2.25.5** and **2.26.1**. This highlights two points:
- **The affected artifact** can be `log4j-api`, not just `log4j-core`.
- **The right version** depends on the advisory, the maintenance branch, and how the application uses the affected feature.

Do not assume that every application using a version in the affected range is automatically exploitable; examine usage conditions, input data scope, and configuration. Conversely, do not skip an upgrade simply because the vulnerable feature "has never thrown an error" in logs.

### Verification workflow when a CVE is published

1. Read the **official advisory** from Apache Logging Services.
2. Identify **which artifacts and version ranges** are affected, not just the name "Log4j".
3. Check the SBOM, dependency tree, packaged artifacts, and containers to know the **version actually deployed**.
4. Compare exploitation conditions against configuration: layouts, appenders, lookups, untrusted data, and invoked classes.
5. Choose a fixed and still-maintained version, considering JDK and framework compatibility.
6. Upgrade related Log4j modules together; run functional tests and security tests.
7. Monitor the rollout, log collection, and error rates; prepare rollback or official mitigations if genuinely needed.

**Do not download JARs from unknown sources or arbitrarily delete classes from a JAR** as a substitute for Apache's recommended patching process. For constrained environments that cannot upgrade immediately, use **advisory-approved** mitigations and set a deadline for permanent remediation.

## 12. Java compatibility and changes during upgrades

**Do not check only the Log4j version.** A change can interact with:

| Component | What to test |
| --- | --- |
| **JDK** | Minimum Java version of the chosen branch; bytecode and module path |
| **Maven/Gradle** | Dependency management, packaging plugins, caches, and lockfiles |
| **SLF4J** | API generation 1.x or 2.x, matching provider and bridge |
| **Spring Boot/framework** | Logging starters, supported framework versions, exclusions, and configuration |
| **Appenders** | Console, file, rolling, socket, async, custom plugins |
| **Layout/encoder** | Patterns, JSON/XML, special characters, and collector parser compatibility |
| **Runtime packaging** | Fat JAR, WAR, container image, module path, server shared libraries |
| **Observability** | Logger names, JSON fields, MDC/ThreadContext, trace/correlation IDs, dashboards/alerts |

According to the current Log4j 2 installation documentation, the mainstream Log4j 2 line has a minimum requirement of **Java 8**; however, **individual branches, modules, and features may have their own requirements**. For Java 17 projects, the Maven example here is written for release 17 and uses standard Log4j APIs. When choosing a different release branch or Log4j 3, always check the official JDK requirements and corresponding migration guide.

**Minor/patch releases do not guarantee that every custom configuration plugin will run unchanged.** There may be changes in attribute names, layout handling, data formatting, or compatibility behavior with other libraries. Therefore, include Log4j configuration tests in the upgrade process, especially if logging is part of auditing or incident monitoring.

## 13. Distinguishing Log4j 1.x, Log4j 2.x, and Log4j 3

The names are easy to confuse:

- **Log4j 1.x:** Legacy line with package **org.apache.log4j**; already EOL. Do not treat it as an older version of Log4j 2.
- **Log4j 2.x:** API typically in package **org.apache.logging.log4j**; split into API, Core, and additional modules.
- **Log4j 3.x:** A different major line that may have breaking changes and separate migration requirements. Do not automatically upgrade from 2.x to 3.x by changing a version number without evaluation.

When legacy code still calls the Log4j 1.x API, Log4j 2's **log4j-1.2-api** artifact can provide partial temporary support. However, the bridge does not mean every internal API, appender, and Log4j 1.x configuration style is 100% compatible. The long-term path is usually migrating source code, dependencies, and configuration files according to the migration guide.

Avoid having **log4j:log4j** (original 1.x) coexist with bridges containing classes in the same namespace on a classpath not designed to operate that way. A library using Log4j 1 should be added to the technical migration backlog, not merely noted as a security scan warning and ignored.

## 14. Safe Log4j2 version upgrade workflow

### Step 1 — Inventory before changing anything

Record the JDK, framework, build tool, Log4j modules in use, SLF4J API version, logging provider, and current `log4j2.xml` configuration. Gather production artifacts and transitive dependencies, not just the test classpath.

### Step 2 — Define the upgrade target

Read security advisories, release notes, and the maintenance policy. Choose a stable version suited to security risks and environment requirements. An urgent security patch may take priority over the regular upgrade schedule, but it should still be tested and have a rollback plan.

### Step 3 — Update in one version management source

For Maven/Gradle using the Log4j BOM, update the BOM version and handle unwanted explicit overrides. Do not leave one module on an old version just because it was declared in a secondary POM.

### Step 4 — Resolve dependencies and check for conflicts

Inspect Maven `dependency:tree` or Gradle `runtimeClasspath`/`dependencyInsight`. Confirm that api/core and Log4j bridges/layouts/appenders are actually resolved as intended, there are no duplicate SLF4J providers, and there is no bridge loop.

### Step 5 — Compile and run tests

At a minimum, include:
- Unit tests for logging integration code or custom formatters.
- Integration tests confirming runtime initializes Log4j Core and loads `log4j2.xml` properly.
- Checks for INFO/DEBUG/WARN/ERROR levels, exception stack traces, and MDC/ThreadContext.
- Checks for critical appenders: rolling file, console, JSON layout, socket/async if used.
- Checks that parsers/collectors/downstream dashboards receive the expected format after the upgrade.

### Step 6 — Check security and performance

Scan packaged dependencies with SCA; verify advisories relevant to the modules and usage. Evaluate latency, CPU, volume, logging queues, dropped events, and restart time. Key metrics should be compared against the pre-upgrade baseline.

### Step 7 — Controlled release

Use canary or phased rollouts if the system supports them. Watch error rates, throughput, log ingestion, parsing errors, and service alerts. If issues arise, roll back using known-working artifacts and configurations while ensuring you do not inadvertently revert to a version with a critical CVE without mitigations.

### Step 8 — Record the change trail

Update the change log, lockfile/SBOM if available, approved version, test results, owner, and release timestamp. Reproducible dependency configuration helps rebuilds and future incident tracing.

## 15. Runtime verification matters more than version declarations

A piece of software can have multiple runtime environments:

~~~text
pom.xml / build.gradle
       |
       v
Build tool resolution
       |
       v
Packaged JAR/WAR or image
       |
       v
Runtime classpath
       |
       v
Actual initialized Provider/Log4j Core
       |
       v
File/console/collector receiving logs
~~~

If you update the BOM without rebuilding, old images can still carry old JARs. If the application has libraries in a server shared classpath, project dependencies may not be the ones actually loaded. If shading embeds classes into another JAR, SCA or the dependency tree may need extra inspection.

A minimal verification workflow:

1. Inspect the dependency graph **after resolution**, not just declarations.
2. Inspect the contents of the artifact or container used for deployment.
3. Run a smoke test that writes real logs, including INFO and a safe exception.
4. Identify the backend in use and check startup errors/warnings.
5. Confirm that the collector still receives complete events after the upgrade.

**Not every logging change breaks the build.** Some misconfigurations only cause logs to be dropped, duplicated, miss stack traces, or lose JSON fields at runtime. That is why logging verification must be part of the version upgrade plan.

## 16. Common mistakes in Log4j2 version management

| Mistake | Risk | Fix |
| --- | --- | --- |
| Declaring separate versions per Log4j module | API/Core/bridge may drift | Use log4j-bom and check resolved versions |
| Seeing a new API and assuming Core is also new | Runtime backend may still be old | Check runtime dependency tree and packaged artifact |
| Importing BOM without checking explicit versions | Actual version may be overridden | Inspect effective POM/resolved graph |
| Adding log4j-slf4j2-impl together with log4j-to-slf4j | Bridge routing loop | Choose only one forwarding direction |
| Keeping slf4j-simple/Logback provider with Log4j provider | Multiple backends or provider conflict | Define a single application backend |
| Using SLF4J 1.x bridge for 2.x API | API generation mismatch | Choose the binding matching the SLF4J version |
| Upgrading only direct dependencies, ignoring transitive/shaded | Old version remains in deployment | Full inventory and SCA/SBOM |
| Treating "past Log4Shell" as permanent safety proof | Missing newer CVEs | Read current advisories and patch releases |
| Upgrading without checking layout/collector | JSON/XML logs or trace IDs may change | Integration tests and ingestion checks |
| Not testing rollback | Hard to recover if appender/bridge fails | Prepare tested artifact/config |
| Believing editing POM updates runtime immediately | Old container/JAR still exists | Rebuild, redeploy, and verify runtime |
| Using Log4j 1.x bridge as a permanent solution | Hard to maintain and compatibility risks | Plan source/config migration |

## 17. Pre-merge checklist for an upgrade

- **Target version:** Clear rationale, release notes/security and maintenance status reviewed.
- **BOM:** All Log4j modules follow a single version source or have documented overrides.
- **Dependency tree:** No unexpected old Log4j versions, no unexplained transitive conflicts.
- **Backend:** Core or another backend confirmed, no bridge loops or duplicate logging paths.
- **SLF4J:** Binding/provider matches the API generation and fits the framework.
- **JDK:** Compatible with the upgraded version and required plugins.
- **Configuration:** `log4j2.xml`, appenders, filters, patterns, async, and rolling files verified.
- **Security:** Advisories checked per artifact, dependencies and SBOM scanned.
- **Testing:** Smoke tests and integration tests for log output, stack traces, and correlation IDs.
- **Observability:** Dashboards, alerts, collectors, and parsing work after upgrade.
- **Release:** Rollout, monitoring, rollback plan, and owner in place.

## 18. Self-check questions

**1. Why is specifying a version only for log4j-core without checking log4j-api risky?**

Because API and Core are two different modules. Version mismatch can cause compatibility errors, especially when newer APIs are called by code or dependencies.

**2. Does a BOM guarantee that every JAR in production has the same version?**

No. A BOM manages dependency resolution for a compatible build; packaged artifacts, explicit overrides, server classpaths, or embedded JARs still need to be inspected.

**3. When an app uses SLF4J 2.x and Log4j Core, which bridge is typically used?**

**log4j-slf4j2-impl**. Do not combine this bridge with **log4j-to-slf4j**.

**4. Why must you inspect dependency:tree after importing a BOM?**

Because you need to confirm which version was actually selected, including transitive dependencies and version conflicts.

**5. Why is an old Log4Shell patch insufficient as a security policy?**

Because subsequent advisories and new fixes have been released for various components and usage conditions. You must follow official notices and perform controlled upgrades.

**6. Should a Java library force every application to use Log4j Core?**

Normally no. A library should depend on an API and let the application decide the runtime backend to avoid conflicts and preserve implementation swappability.

**7. Why must log4j2.xml be tested after an upgrade?**

Because syntax/plugins, layouts, appenders, or log formats can change. An application may still run while logs are lost, duplicated, or no longer parsed correctly by collectors.

**8. Should you change 2.x to 3.x in the BOM without reading the migration guide?**

No. A major upgrade can contain breaking changes and different platform requirements; it requires testing and updating code/configuration as needed.

**Remember:** Log4j2 version management is managing the **entire dependency graph and log event path**, not just a version number. Use a BOM to align Log4j modules, inspect the resolved runtime classpath, choose the right bridge direction, read official advisories, and test output before/after upgrading. An application is only truly protected when the appropriate patch **has been deployed and verified**, not merely declared in a build file.
