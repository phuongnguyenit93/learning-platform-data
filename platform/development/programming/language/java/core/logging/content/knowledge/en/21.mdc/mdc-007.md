# MDC in Thread Pools — Propagating Logging Context Safely in Java

## 1. The Problem to Solve

In **Java Core Logging**, **MDC (Mapped Diagnostic Context)** is a set of key–value fields—typically including **requestId, traceId, jobId**—that a logging backend can automatically attach to each log event emitted on the processing thread.

Example log records with MDC:

~~~text
requestId=req-A INFO event=order.received orderId=ORD-17
requestId=req-A INFO event=inventory.reserved orderId=ORD-17
requestId=req-A INFO event=order.completed orderId=ORD-17
~~~

This is output illustrating a log pattern, not the default format of every backend.

A **thread pool** reuses a set of threads to run many different `Runnable`/`Callable` tasks. When an HTTP request submits work to a pool, the thread running the task **does not necessarily have the submitting thread's MDC**. Even worse, if a previous task set an MDC value and forgot to clean it up, a subsequent task may **mistakenly inherit the old requestId**.

There are two distinct bugs:

- **Missing context:** worker logs lack `requestId`/`traceId`, making it impossible to correlate events with the parent request.
- **Context leakage:** logs for request B carry request A's `requestId` because the worker thread was reused.

The standard solution is: **capture → install → execute → restore** per task. Capture a snapshot on the caller before submission, install the snapshot when the worker runs, execute the task, and restore the worker's MDC in **finally**.

**Do not treat MDC as an automatic request propagation mechanism**. MDC is primarily logging metadata at the moment a `LogEvent` is created; it does not replace transaction context, security principal, or distributed tracing.

## 2. Why Doesn't ThreadLocal Automatically Follow the Task?

Common MDC implementations store context close to the current thread's **ThreadLocal**. A `ThreadLocal` applies only to a specific thread and does not automatically transfer to another thread simply because a task is submitted.

~~~text
HTTP worker:
  MDC {requestId=req-A}
       |
       | executor.submit(task)
       v
Pool worker-1:
  MDC {} or {requestId=req-OLD}
       |
       v
  LOG.info("event=inventory.lookup")
~~~

**Executors.newFixedThreadPool(...)** and **newCachedThreadPool(...)** manage workers and may reuse previously created threads. Tasks A and B may run on the same worker, or a task may run on a different worker depending on scheduling.

**InheritableThreadLocal** does not safely solve this problem: values can be inherited when **creating a child thread**, whereas pool threads are already created or reused. **A submission boundary is not a thread creation boundary**.

| Concept | Scope |
| --- | --- |
| ThreadLocal | State of a single thread |
| InheritableThreadLocal | May be inherited when a thread is created, depending on implementation |
| Runnable/Callable | Unit of work submitted |
| ExecutorService | Manages dispatching tasks to workers |
| MDC snapshot | Copy of context taken at the caller |
| MDC restoration | Restoring the worker's state after the task |
| Request ID | Request identifier, not the worker thread name |

A **thread name** like `pool-1-thread-1` identifies the worker, not the request. The same worker can execute thousands of requests.

## 3. Signs of Missing Context and Context Leakage

**Missing context:**

~~~text
thread=http-1 requestId=req-A event=request.received
thread=pool-1 requestId=none event=inventory.reserve
~~~

**Leaked data from a previous task:**

~~~text
thread=pool-1 requestId=req-A event=job.A.completed
thread=pool-1 requestId=req-A event=job.B.started
~~~

In the second case, if job B belongs to `req-B`, the log looks syntactically valid but is **factually wrong**. Filtering logs by tenant/request can lead to false conclusions.

Example of code that **does not propagate**:

~~~java
MDC.put("requestId", "req-A");
executor.submit(() -> LOG.info("event=inventory.reserve"));
MDC.remove("requestId");
~~~

This is a snippet assuming `LOG` and `executor` already exist. The `put`/`remove` operations run on the **caller**, while `LOG.info` runs on the **worker**. There is no guarantee the worker sees `req-A`.

Example that **causes stale context**:

~~~java
executor.submit(() -> {
    MDC.put("requestId", requestId);
    service.process();
});
~~~

This is also a snippet. If `service.process()` throws an exception, there is no cleanup call; the worker may retain `requestId` for the next task. A `finally` block is required.

**A test that runs only a single task is not enough** to detect reuse bugs; intentionally run A, B, and a context-less task on the same worker.

## 4. Key SLF4J MDC APIs

With **org.slf4j.MDC**:

| Method | Meaning |
| --- | --- |
| **MDC.put(key, value)** | Assigns a key–value pair to the current thread |
| **MDC.get(key)** | Reads a key on the current thread |
| **MDC.remove(key)** | Removes a single key |
| **MDC.clear()** | Clears the entire current MDC map |
| **MDC.getCopyOfContextMap()** | Returns a copy of the Map; **may be null** |
| **MDC.setContextMap(map)** | Replaces the entire MDC Map with the provided copy |
| **MDC.putCloseable(key, value)** | Sets a key and returns a closeable scope that removes the key |

**getCopyOfContextMap()** must be called on the **caller before submit** to capture the true source context. If called inside the worker, it only returns the worker's current state, which may be empty or leaked from a previous task.

**setContextMap(null)** is supported starting in SLF4J 2.x; however, an easy-to-read wrapper typically uses **MDC.clear()** when the snapshot is null/empty and **MDC.setContextMap(snapshot)** when data is present.

**putCloseable** helps clean up a single key at the end of a try-with-resources block; **it is not a stack that restores the previous value of a key with the same name**. If a nested scope reuses `requestId`, a separate save/restore mechanism is required.

SLF4J is a **facade**: the actual backend/provider such as Logback or Log4j 2 determines how MDC is stored and written to files/console. A provider without meaningful MDC support may still expose the API while omitting the expected fields from the output.

## 5. The Four Steps: capture → install → execute → restore

Diagram:

~~~text
Caller thread                             Worker thread
-------------                             -------------
MDC {requestId=req-A}
      |
      | getCopyOfContextMap()
      v
snapshot {requestId=req-A}
      |
      +--- executor.submit(wrapper) ---->
                                          previous = worker MDC
                                          try {
                                              install(snapshot)
                                              task.run()
                                          } finally {
                                              install(previous)
                                          }
Caller can clear MDC                      Worker returns to previous state
~~~

**Capture:** take a snapshot once at the place where the request context actually exists.

**Install:** replace the worker's context before the action emits any `LogEvent`; if the caller has no MDC, **clear** the worker's MDC for the duration of the action.

**Execute:** run the task as usual, preserving the task's exception/return semantics.

**Restore:** save the worker's `previous` context and restore it in `finally`, even if the task throws a `RuntimeException`, `Error`, or is interrupted.

Why is **restore** different from **clear**? A task might run inside a valid worker context, such as `batchId=batch-7`. If the end of the task simply calls `clear`, `batchId` is lost. Restore returns the worker to its state prior to the task.

**Limitation:** if the worker's `previous` context was already polluted by an old task, restore will preserve that polluted state. You must fix the source of the leak and ensure top-level tasks pass through a cleanup boundary; do not treat the decorator as a self-healing system for pre-existing bugs.

## 6. Reusable Runnable Wrapper

An SLF4J utility class:

~~~java
import java.util.Map;
import org.slf4j.MDC;

public final class MdcWrappers {
    private MdcWrappers() {}

    private static void install(Map<String, String> context) {
        if (context == null || context.isEmpty()) {
            MDC.clear();
        } else {
            MDC.setContextMap(context);
        }
    }

    public static Runnable withMdc(Runnable action) {
        Map<String, String> captured =
                MDC.getCopyOfContextMap();

        return () -> {
            Map<String, String> previous =
                    MDC.getCopyOfContextMap();
            try {
                install(captured);
                action.run();
            } finally {
                install(previous);
            }
        };
    }
}
~~~

This is a **component Java class** requiring the SLF4J dependency and a compatible provider; it has no `main()` and does not log on its own.

Usage:

~~~java
try (MDC.MDCCloseable scope =
        MDC.putCloseable("requestId", requestId)) {
    Future<?> future = executor.submit(
            MdcWrappers.withMdc(
                    () -> service.process(orderId)));
    future.get();
}
~~~

This is a snippet assuming `executor`, `service`, `requestId`, `orderId`, and imports already exist.

**Checkpoint:** `withMdc` is called directly **on the caller before submit**, not inside the worker's lambda. The `captured` map is the data that will be installed on the worker, while `previous` is the state to restore afterward.

If an application has multiple paths that submit tasks, every relevant path must go through the decorator. A single direct `submit` call can cause intermittent MDC failures across the system.

## 7. Callable\<T\> and Future

`Callable` returns a result and can throw checked exceptions. You can write an overload:

~~~java
public static <T> java.util.concurrent.Callable<T> withMdc(
        java.util.concurrent.Callable<T> action) {
    java.util.Map<String, String> captured =
            org.slf4j.MDC.getCopyOfContextMap();

    return () -> {
        java.util.Map<String, String> previous =
                org.slf4j.MDC.getCopyOfContextMap();
        try {
            if (captured == null) org.slf4j.MDC.clear();
            else org.slf4j.MDC.setContextMap(captured);
            return action.call();
        } finally {
            if (previous == null) org.slf4j.MDC.clear();
            else org.slf4j.MDC.setContextMap(previous);
        }
    };
}
~~~

This is a **method snippet**, not a standalone program. In a real codebase, consolidate the install/restore logic into a shared helper.

**Future.get()** can throw **ExecutionException** when the inner task fails, and **InterruptedException** when the waiting thread is interrupted. Even if the task fails, the `finally` block in the wrapper still executes once the task has started and exits with an exception.

When calling **invokeAll(...)**, wrap **each Callable** before submitting to the pool. Do not wrap a `Future` after it has already been submitted, because by then part of the work has already run or is running in the wrong context.

**execute() and submit()** differ in how they report errors, but the MDC cleanup requirement in the worker is the same.

2. Request B has MDC **req-B**, submitting job B on **the same worker**.

### src/main/java/demo/MdcPoolDemo.java

~~~java
package demo;

import java.util.Map;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;

public final class MdcPoolDemo {
    private static final Logger LOG =
            LoggerFactory.getLogger(MdcPoolDemo.class);

    private MdcPoolDemo() {}

    private static void install(Map<String, String> context) {
        if (context == null || context.isEmpty()) {
            MDC.clear();
        } else {
            MDC.setContextMap(context);
        }
    }

    private static Runnable withMdc(Runnable task) {
        Map<String, String> captured = MDC.getCopyOfContextMap();

        return () -> {
            Map<String, String> previous = MDC.getCopyOfContextMap();
            try {
                install(captured);
                task.run();
            } finally {
                install(previous);
            }
        };
    }

    private static void await(Future<?> future) throws Exception {
        future.get();
    }

    public static void main(String[] args) throws Exception {
        ExecutorService pool = Executors.newSingleThreadExecutor(
                task -> new Thread(task, "mdc-worker"));

        try {
            try (MDC.MDCCloseable ignored =
                    MDC.putCloseable("requestId", "req-A")) {
                await(pool.submit(withMdc(
                        () -> LOG.info("event=job.started job=A"))));
            }

            try (MDC.MDCCloseable ignored =
                    MDC.putCloseable("requestId", "req-B")) {
                await(pool.submit(withMdc(
                        () -> LOG.info("event=job.started job=B"))));
            }

            await(pool.submit(withMdc(() -> {
                if (MDC.get("requestId") != null) {
                    throw new IllegalStateException(
                            "Worker retained a requestId");
                }
                LOG.info("event=worker.clean");
            })));
        } finally {
            pool.shutdown();
            MDC.clear();
        }
    }
}
~~~

### Run Command

With **JDK 17+**, **Maven**, and the ability to download dependencies on the first run; from the project directory:

~~~bash
mvn -q compile exec:java
~~~

**Three application log lines on stdout** when the project runs normally:

~~~text
thread=mdc-worker requestId=req-A INFO event=job.started job=A
thread=mdc-worker requestId=req-B INFO event=job.started job=B
thread=mdc-worker requestId=none INFO event=worker.clean
~~~

These are the three lines from the application/Logback, excluding environment-specific Maven/JVM messages.

### Explaining the Output

1. **newSingleThreadExecutor** reuses a single thread named **mdc-worker**.
2. **putCloseable req-A** sets MDC on the caller; **withMdc** captures it before the task is submitted.
3. The worker saves `previous`, installs `req-A`, and the Logger emits the event; Logback's **%X** reads `req-A`.
4. **finally** restores the worker context; the caller also removes `req-A` when exiting the scope.
5. Request B does the same with `req-B`, still on `mdc-worker`.
6. The probe task is created when the caller has no MDC; the wrapper clears the worker for the duration of the probe.
7. The probe asserts **MDC.get("requestId") == null**. If false, `Future.get` surfaces the error instead of failing silently.
8. When `requestId` is absent, the pattern falls back to **none**.
9. Calling **Future.get()** after each task makes the A, B, probe order deterministic for the demo. With multiple workers and independent tasks, log order can vary.
10. **pool.shutdown()** stops accepting new tasks; the demo awaits the Futures so `Thread.sleep` is unnecessary.
11. **MDC.clear()** in `main` is cleanup for this program; in real components, avoid clearing context belonging to another scope.

**Key takeaway:** MDC is not propagated by using a single-thread pool, but by wrapping at the **submission boundary** and cleaning up in **finally**.

## 9. Why Must Cleanup Be in finally?

An error-prone snippet:

~~~java
pool.submit(() -> {
    MDC.put("requestId", requestId);
    doWork();
    MDC.clear();
});
~~~

If `doWork` throws an exception, **MDC.clear()** does not run. The worker may retain the old `requestId`.

Fix scoped to task ownership:

~~~java
pool.submit(() -> {
    try {
        MDC.put("requestId", requestId);
        doWork();
    } finally {
        MDC.remove("requestId");
    }
});
~~~

This is a snippet assuming the variables are declared. It handles **a single key**, but does not propagate all caller context and does not restore a pre-existing value with the same key name.

**A wrapper that saves/restores the entire Map** is generally better suited as a general-purpose executor decorator, especially when MDC has multiple keys and nested executions. If all top-level tasks are required to start/end with an empty MDC, you can clear at a task boundary you own; do not apply that policy to nested scopes you do not own.

## 10. CompletableFuture and Async Boundaries

**CompletableFuture.runAsync** typically runs the task on a different executor from the caller:

~~~java
CompletableFuture<Void> result = CompletableFuture.runAsync(
        () -> LOG.info("event=background.started"), executor);
~~~

This is a snippet assuming `LOG`/`executor`. Without propagation, the worker may not see `requestId`.

Wrap the task:

~~~java
CompletableFuture<Void> result = CompletableFuture.runAsync(
        MdcWrappers.withMdc(
                () -> LOG.info("event=background.started")),
        executor);
~~~

**Points to watch:**

- **supplyAsync, thenApplyAsync, thenAcceptAsync, handleAsync** may switch to a new thread. Context propagation is needed at **each async boundary**.
- **Non-Async thenApply** may run on the upstream completing thread or the callback-registering thread depending on timing, so never assume the HTTP caller's MDC.
- If a continuation is registered **after the request scope has closed**, a wrapper capturing MDC at that point may capture null. Retain the **request context snapshot** that was captured earlier.
- For `Function`/`Supplier`/`Consumer`, use corresponding decorators rather than forcing them into an unsuitable `Runnable`.
- **ForkJoinPool.commonPool()** has no contract to automatically carry the caller's MDC.
- Exceptions/cancellations must not bypass `finally` at any boundary.
- If your framework provides official **context propagation**, prefer it over writing different wrappers in every service.

A method snippet for `Function`:

~~~java
static <T, R> java.util.function.Function<T, R> withContext(
        java.util.function.Function<T, R> action,
        java.util.Map<String, String> captured) {
    return value -> {
        java.util.Map<String, String> previous =
                org.slf4j.MDC.getCopyOfContextMap();
        try {
            if (captured == null) org.slf4j.MDC.clear();
            else org.slf4j.MDC.setContextMap(captured);
            return action.apply(value);
        } finally {
            if (previous == null) org.slf4j.MDC.clear();
            else org.slf4j.MDC.setContextMap(previous);
        }
    };
}
~~~

`captured` must be taken where the right context exists, not read from a worker after a thread hop.

## 11. Executor Decorator

A centralized propagation point reduces the risk of forgetting to wrap tasks:

~~~java
import java.util.concurrent.Executor;

public final class MdcExecutor implements Executor {
    private final Executor delegate;

    public MdcExecutor(Executor delegate) {
        this.delegate = delegate;
    }

    @Override
    public void execute(Runnable action) {
        delegate.execute(MdcWrappers.withMdc(action));
    }
}
~~~

This is a component class depending on `MdcWrappers`. It captures MDC when a client calls **execute(...)** on the decorator.

**Executor is not ExecutorService:** `MdcExecutor` above does not have **submit, invokeAll, shutdown**. To use the full `ExecutorService`, decorate the relevant overloads or choose a supported library/framework. Do not assume `submit` calls go through a wrapper that only implements `Executor`.

A good policy defines **which executors are used for request tasks** and ensures callers do not bypass the decorator without good reason.

## 12. ScheduledExecutorService and Recurring Jobs

A **one-shot scheduled task** for a request may need to keep the `requestId` at scheduling time, even if it executes after the HTTP response has been returned.

A **recurring job** is different: if `scheduleAtFixedRate` is called under request A and the `req-A` snapshot is held forever, every run may carry **req-A** even though it no longer belongs to that request.

~~~text
Request req-A registers recurring job
  |
  +--> run 1: requestId=req-A ?
  +--> run 2: requestId=req-A ?
  +--> run 3: requestId=req-A ?
~~~

If the job is independent, generate a distinct **jobRunId** per execution; you may keep **submittedBy** per audit policy, but do not reuse `requestId` as the correlation ID for new runs.

**Distinction:** propagation for a request-scoped one-shot task and context for a recurring background job must follow the job's semantics, not just the scheduling API.

## 13. Spring @Async and TaskDecorator

In Spring, **ThreadPoolTaskExecutor.setTaskDecorator(...)** can configure MDC propagation for tasks passing through that executor:

~~~java
executor.setTaskDecorator(task -> {
    Map<String, String> caller = MDC.getCopyOfContextMap();

    return () -> {
        Map<String, String> previous = MDC.getCopyOfContextMap();
        try {
            if (caller == null) MDC.clear();
            else MDC.setContextMap(caller);
            task.run();
        } finally {
            if (previous == null) MDC.clear();
            else MDC.setContextMap(previous);
        }
    };
});
~~~

This is a **snippet** requiring Spring Framework/SLF4J and an `executor` variable of type `ThreadPoolTaskExecutor`. It is not a standalone runnable example.

Things to verify:

1. **@Async** actually uses the executor configured with `TaskDecorator`, not a different bean.
2. `TaskDecorator` may receive a `Runnable` already wrapped by the framework, especially with `Future`.
3. Errors from tasks submitted with `Future` may be captured inside the `Future` rather than surfacing directly through the decorator.
4. Schedulers, reactive pipelines, or other executors may not go through this decorator.
5. If the framework already has context-propagation/tracing instrumentation, avoid two conflicting layers installing/restoring MDC.

Do not assume `ThreadLocal` works across every reactive thread hop; for Reactor/WebFlux, use the framework's context mechanism and tested instrumentation.

## 14. Request Boundaries and Nested MDC Scopes

In HTTP services, a common pattern is:

~~~text
HTTP Filter/Interceptor:
   validate/create requestId
   MDC.put(requestId)
         |
         v
   Controller / Service
         |
         +--> Executor task (capture snapshot here)
         |
         v
   finally cleans up context on HTTP thread
~~~

Scope pattern:

~~~java
try (MDC.MDCCloseable ignored =
        MDC.putCloseable("requestId", requestId)) {
    service.process(orderId);
}
~~~

This is a snippet. **putCloseable** removes the key on close, even on exception. If multiple keys like `traceId`/`jobId` are needed, manage each field or save/restore the entire Map.

**Nested case:** if an outer scope has `requestId=outer` and an inner scope uses `putCloseable` with `requestId=inner`, closing the inner scope may remove `requestId` instead of restoring `outer`. If nested scopes are needed, save the previous map or previous value and restore it in `finally`.

**Do not call MDC.clear() unconditionally in a component that only owns a single key** when an outer context still needs to be preserved. Conversely, a top-level request boundary that owns the entire MDC can clear it at the end by contract.

**Capture must happen before the caller cleans up MDC**. Once the scope has closed, `getCopyOfContextMap` may return null even if the task is about to be submitted.

## 15. Configuring Logback to Display MDC

To see MDC fields in logs, the backend must include them in its layout/encoder. Example:

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<configuration>
    <appender name="STDOUT"
              class="ch.qos.logback.core.ConsoleAppender">
        <target>System.out</target>
        <encoder>
            <pattern>%d{yyyy-MM-dd HH:mm:ss.SSS} %-5level [%thread] requestId=%X{requestId:-none} %logger - %msg%n</pattern>
            <charset>UTF-8</charset>
        </encoder>
    </appender>

    <root level="INFO">
        <appender-ref ref="STDOUT"/>
    </root>
</configuration>
~~~

**%X{requestId:-none}** is the MDC converter, with a fallback when the value does not exist. **%thread** is useful for observing pool thread reuse.

If using a JSON encoder, you may want a `LogEvent` like:

~~~json
{
  "level": "INFO",
  "thread": "mdc-worker",
  "requestId": "req-A",
  "event": "job.started"
}
~~~

This is an illustrative schema only. A text pattern `requestId=...` is not automatically a structured JSON field. **Both the encoder and collector must be configured to extract MDC** into the output under the right field names.

**MDC vs. event metadata:** `requestId`/`traceId` are reused across many events; `eventName`, `attempt`, and `outcome` of a single operation should usually be attached to the `LogEvent` itself rather than putting everything into MDC.

## 16. Log4j 2 ThreadContext in Thread Pools

In **Log4j 2**, the equivalent mechanisms are **ThreadContext Map** (MDC) and **ThreadContext Stack** (NDC). Log4j 2 documentation recommends taking a snapshot from the caller and installing it on the worker.

~~~java
Map<String, String> map = ThreadContext.getImmutableContext();
List<String> stack =
        ThreadContext.getImmutableStack().asList();
~~~

This is a snippet requiring `java.util.Map`/`List` and `org.apache.logging.log4j.ThreadContext`.

Using `CloseableThreadContext`:

~~~java
executor.submit(() -> {
    try (CloseableThreadContext.Instance ignored =
            CloseableThreadContext.putAll(map).pushAll(stack)) {
        LOG.info("event=task.started");
    }
});
~~~

This is a snippet assuming `executor`/`LOG`/`map`/`stack` already exist and `CloseableThreadContext` is imported.

**Be careful:** `putAll` adds/overwrites entries and **does not necessarily remove other keys already present on the worker**. If the worker must contain only the current task's map, save `previous`, clear/replace the Map, and restore it in `finally`. Stack/NDC requires separate handling as well.

Example handling only the Map:

~~~java
Map<String, String> caller = ThreadContext.getImmutableContext();

executor.execute(() -> {
    Map<String, String> previous = ThreadContext.getImmutableContext();
    try {
        ThreadContext.clearMap();
        ThreadContext.putAll(caller);
        LOG.info("event=task.started");
    } finally {
        ThreadContext.clearMap();
        ThreadContext.putAll(previous);
    }
});
~~~

**Do not confuse SLF4J MDC and Log4j ThreadContext** as two stores that always stay in sync automatically; behavior depends on the binding/bridge. Choose a consistent logging API and test the fields in the actual output.

## 17. Async Business Tasks vs. AsyncAppender

Two different processing paths:

**Offloading a business task to a pool:**

~~~text
HTTP thread MDC=req-A
  | submit Runnable
  v
Executor worker (needs req-A installed)
  | LOG.info(...)
  v
LogEvent
~~~

**Offloading log writing to an async backend:**

~~~text
Business worker MDC=req-A
  | LOG.info(...)
  v
LogEvent contains context per backend
  | queue
  v
Async logging writer
  | file/console/network
~~~

Modern logging backends typically snapshot context into the `LogEvent` at the time the Logger call is made, while the writer processes it later. However, behavior depends on the backend, version, and custom Appender.

**AsyncAppender cannot fix a business worker missing MDC before the Logger creates the event.** Setting `req-A` on the logging writer is also wrong because the writer processes events from many different requests.

Therefore, test **business task propagation** and **async logger context retention** as two independent concerns.

## 18. MDC Does Not Automatically Cross HTTP or Message Brokers

MDC is strictly **local logging context**; it is not automatically propagated across HTTP/gRPC/Kafka/RabbitMQ.

To correlate between service A and service B:

1. Define `traceId`/`requestId` in your protocol or a standard such as **W3C Trace Context**.
2. Pass it via headers/message metadata.
3. At the target service, parse/validate the data and set the local context.
4. Clean up the local context when the request/job finishes.
5. If service B also uses a thread pool, continue propagating at task boundaries.
6. Verify that backends/encoders use the same key schema.
7. Never use an MDC value as authorization proof.

**MDC does not create traces/spans on its own**. If your system already has OpenTelemetry instrumentation, prefer integrating the tracing system's context propagation rather than duplicating header logic in every service.

## 19. Exceptions, Cancellation, Shutdown, and Cleanup

| Situation | Requirement |
| --- | --- |
| Task throws exception | Restore worker MDC in `finally` |
| Callable throws checked exception | Call `Future.get` and handle `ExecutionException` |
| Worker is interrupted | Clean up in `finally`; preserve proper interrupt policy |
| `Future.cancel(true)` | Ensure cleanup if the task has already started |
| Executor rejects task | Handle `RejectedExecutionException` |
| Long queue wait | Snapshot must be taken before submit, not read from caller later |
| Recurring scheduled task | Fresh context per run |
| Pool shutdown | Await necessary tasks and flush the logging backend properly |
| Slow async logger | Manage queue/drop/flush independently |
| Thread factory changes | Per-task propagation must still work |

**Never swallow an exception just to perform cleanup.** The wrapper must restore state and let the error continue propagating through the `Executor`/`Future`.

In production code, configure **timeouts, cancellation, and awaitTermination** according to policy; the Maven example uses `Future.get` for the three tasks to guarantee deterministic test ordering, not as a shutdown strategy for every service.

## 20. How to Test Leakage and Propagation

A reliable test should run **multiple consecutive tasks on a single worker**:

1. `req-A` → wrapped task → assert logs contain `req-A`.
2. `req-B` → wrapped task → assert logs contain `req-B`.
3. Caller with no context → wrapped probe → assert `MDC.get("requestId")` is null.
4. Task inside wrapper intentionally throws an exception → subsequent probe still has no old context.
5. Pre-existing nested context on worker → `previous` is properly restored after the task.
6. MDC has two keys `requestId`/`traceId` → both are propagated properly.
7. Test a new `CompletableFuture` stage → has its own propagation.
8. Test a scheduled job → does not retain expired context.
9. Run multiple workers and multiple requests → each log carries the right ID, without requiring global ordering.
10. Test actual backend output (`%X`/JSON fields), not just `MDC.get` in Java.
11. Test that the caller scope is cleared in `finally` even when the request fails.
12. Synchronize with `Future.get`/`CountDownLatch` instead of `Thread.sleep` to avoid flaky tests.

Example failing-task snippet:

~~~java
Future<?> failure = pool.submit(withMdc(() -> {
    LOG.info("event=will.fail");
    throw new IllegalStateException("simulated failure");
}));

try {
    failure.get();
} catch (ExecutionException expected) {
    // Task intentionally fails in test.
}
~~~

This snippet assumes `pool`/`withMdc`/`LOG` and imports for `Future`/`ExecutionException`. Afterward, submit a **probe** with no MDC to confirm cleanup actually occurred.

**Do not conclude propagation works just because logs appear in the terminal.** Tests must verify that **`requestId` comes from MDC**, not from manual concatenation into the log message.

## 21. Security and Performance

MDC should be small, have a stable schema, and contain only data needed for diagnostics:

- Do not put **passwords, tokens, API keys, session cookies, Authorization headers, or card data** in MDC.
- Do not use **tenantId/requestId in MDC** in place of a trusted security context.
- Context leakage can cause tenant B's logs to be tagged with tenant A's ID.
- Validate/limit the length of client-supplied `requestId` values and escape newlines/control characters to mitigate **log injection**.
- Do not turn `requestId` values into **key names**, which causes schema explosion.
- Configure appropriate **retention** and access permissions on files, console collectors, dashboards, and backups.
- **getCopyOfContextMap** incurs allocation cost; keep the context Map small rather than storing entire request objects.
- Long queues can hold many MDC snapshots in memory; bound backlogs.
- Do not skip cleanup to optimize speed; measure CPU, p95/p99 latency, and memory under realistic workloads.
- Async logging may snapshot context one extra time into `LogEvent`, which is usually necessary to preserve metadata at the writer.

**MDC leakage does not just produce messy logs**. It corrupts event correlation and can create security issues when log systems partition query permissions by tenant/request fields.

## 22. Troubleshooting by Symptom

| Symptom | Possible Cause | Resolution |
| --- | --- | --- |
| Caller has `req-A` but worker has `none` | Missing capture/install | Wrap before submit |
| Worker B has `req-A` | Task A did not clean up MDC | Restore in `finally` |
| Sometimes works, sometimes fails | Relying on pool thread creation/inheritance | Per-task propagation |
| Wrong ID in logs after an exception | Cleanup not inside `finally` | Wrap the entire task |
| Nested task loses `batchId` | Clearing instead of restoring | Save `previous` map |
| `putCloseable` loses outer scope's ID | Closeable removes instead of restoring | Save/restore scope |
| Subsequent `CompletableFuture` stage lacks ID | Stage switched threads | Propagate at each boundary |
| Scheduled recurring job uses old ID | Request snapshot held too long | New `jobRunId` per run |
| Logback does not print `requestId` | Pattern missing `%X`/encoder missing MDC | Fix layout |
| SLF4J calls `MDC.put` but backend misses it | Provider/bridge lacks proper support | Check runtime |
| Log4j `ThreadContext` does not appear | API/bridge mismatch | Use one consistent stack |
| `@Async` lacks context | Running on an undecorated executor | Check executor bean |
| Probe after task is not clean | Wrapper bypassed or worker already polluted | Check all submission paths |
| Logs show wrong tenant | Context leakage or untrusted ID input | Clean up, validate, and audit |
| `Future` fails without caller knowing | Not calling `get`/`handle` | Handle results/errors |
| Context snapshot is empty | Captured after caller already cleared | Capture at submission time |

**Diagnostic order:** identify provider/backend → MDC on caller → capture point → whether task passes through wrapper → worker install/restore → layout/encoder → collector and thread-reuse test.

## 23. Common Design Mistakes

**1. Assuming MDC follows the request.** It normally follows the thread and requires propagation across task hops.

**2. Using InheritableThreadLocal for thread pools.** It does not equate to task-level context.

**3. Capturing inside the worker.** Too late; it may grab the wrong context.

**4. Omitting finally.** A failing task leaves the worker polluted.

**5. Only calling clear after a nested task.** This can wipe out a valid prior worker context.

**6. Only removing requestId.** Other fields such as `traceId` may remain.

**7. Thinking putCloseable automatically restores the previous key.** It removes the key on close.

**8. Wrapping the first stage and skipping later stages.** `CompletableFuture` can hop threads multiple times.

**9. Using AsyncAppender to fix business context.** If context is already lost before the `LogEvent` is created, the writer cannot recover it.

**10. Keeping req-A on a recurring job.** Each execution may belong to a different context.

**11. Not testing A → B → none.** Fails to detect stale worker context.

**12. Only printing requestId in the message.** That does not prove MDC propagation works.

**13. Using MDC as a security principal.** It is observability metadata only.

**14. Mixing incompatible providers/bridges.** Code may run while MDC fields silently disappear.

## 24. Checklist for MDC in Thread Pools

1. **Choose a real logging provider** and configure the layout/JSON encoder to extract MDC.
2. **Define a key schema**: `requestId`, `traceId`, `spanId`, `jobId`.
3. **Set MDC at the request/job boundary** and clean up when exiting the scope.
4. **Capture using getCopyOfContextMap before submit**.
5. **Install on the worker before the Logger emits events**.
6. **Restore previous in finally**, including on exceptions and interrupts.
7. **Support both Runnable and Callable**, without missing any submission paths.
8. **Use a centralized Executor/TaskDecorator** when many tasks are submitted.
9. **Propagate across every CompletableFuture async boundary** or use framework support.
10. **Create fresh context for recurring jobs** instead of retaining old `requestId` values.
11. **Do not rely on InheritableThreadLocal or worker names**.
12. **Distinguish business async tasks from async logging backends**.
13. **Propagate correlation over the network via protocol**, not MDC alone.
14. **Test a single worker running A → B → none**, plus exceptions and nested scopes.
15. **Verify actual output** with Logback/Log4j2/collector.
16. **Avoid secrets/PII**, validate IDs, and enforce retention policies.
17. **Keep MDC small**, monitoring snapshot overhead, queue sizes, and latency.

**Conclusion:** With thread pools, MDC **must be propagated per task**; it does not follow a `Runnable` automatically just because the task was submitted from an HTTP thread. The safe pattern is **capture at caller → install on worker → execute task → restore in finally**. Combined with proper scope cleanup, an encoder configured to read MDC, and thread-reuse testing, log records can be accurately tagged with `requestId`/`traceId` without leaking context across requests.
