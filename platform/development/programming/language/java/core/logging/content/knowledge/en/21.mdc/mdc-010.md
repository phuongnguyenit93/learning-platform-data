# Testing MDC in Java Logging: Right Request, Right Thread, and Zero Context Leaks

## 1. Why Test MDC?

**MDC (Mapped Diagnostic Context)** is a mechanism for attaching diagnostic key–value pairs to the logging context. In Java, application code typically uses the `org.slf4j.MDC` API to put `requestId`, `traceId`, `jobId`, or `operation` into logs. A backend such as Logback can include these values in each event, display them using `%X{requestId}`, or serialize them as JSON.

For example, an application handling two requests concurrently:

```text
INFO  requestId=req-A event=order.received
INFO  requestId=req-B event=order.received
WARN  requestId=req-A event=payment.retry
INFO  requestId=req-B event=order.completed
```

If the code forgets to set, propagate, or clear MDC, log lines may lose their ID or carry **the previous request's ID**. This is not merely a log-readability issue: it can lead to investigating the wrong transaction, skewed dashboards, and cross-request data leaks on thread pools.

**Testing MDC** must verify both **the data in MDC** and **the actual data attached to the logging event**. A test that only calls `MDC.put("requestId", "req-A")` followed by `assertEquals("req-A", MDC.get("requestId"))` only proves a map operation on a single thread—it **does not prove that real logs contain the ID**.

This guide focuses on the key test cases:

1. MDC holds the right value within the processing scope.
2. The log event actually carries the expected `requestId`.
3. MDC is **restored or cleared** when the scope exits normally.
4. MDC is still cleaned up when a method throws an exception.
5. MDC **does not automatically propagate** to tasks on an `ExecutorService`.
6. When a snapshot is explicitly propagated, the worker has the right context and does not leak it to the next task.
7. Two concurrently running requests do not mix up each other's context.
8. The layout/encoder actually outputs MDC in the expected format.
9. Tests are not flaky due to thread scheduling, global logger configuration, or a different logging backend.

The complete example suite uses **Java 17, SLF4J 2.x, Logback Classic, JUnit Jupiter 5, and Logback's `ListAppender`**. There is no need to mock static `MDC`: testing against a real provider/backend catches bugs that a mock would hide.

## 2. How MDC Differs from Thread Names and Global Variables

Distinguish the following concepts:

| Concept | Purpose | Testing Notes |
| --- | --- | --- |
| `requestId` | Correlates logs belonging to one request | Must stay accurate across steps and be cleared after the request |
| `traceId` | Correlates operations in a distributed trace | Requires propagation across processes/networks; MDC only helps emit logs |
| `spanId` | Identifies the current span | May change when the processing step/span changes |
| `jobId` | Correlates logs of a background job | Does not necessarily have an HTTP request |
| Thread name | The thread emitting the event at that moment | Thread pools reuse threads across many requests |
| Logger name | Stable log source by package/class | Do not put dynamic IDs into Logger names |
| MDC map | Diagnostic key–value set bound to the current thread | Not a global map shared across all threads |
| Logging event | The created log record | Needs a context snapshot at the time the log is emitted |

**One thread can serve many requests; one request can cross many threads.** Therefore, asserting `Thread.currentThread().getName()` is not enough to prove `requestId` is correct.

SLF4J is a facade, while storing and outputting MDC depends on the active **MDC adapter/provider**. With Logback, MDC can be retrieved from an event via `ILoggingEvent.getMDCPropertyMap()`. A backend/provider that does not support MDC as expected can cause tests to print logs normally without any context.

### 2.1. MDC APIs to Understand

| API | Core Semantics | What to Verify |
| --- | --- | --- |
| `MDC.put(key, value)` | Writes an entry for the current thread | Key/value is correct and exists only in the intended scope |
| `MDC.get(key)` | Retrieves the value by key on the current thread | Not mixed up with another task's context |
| `MDC.remove(key)` | Removes one entry from the current thread | Does not leave an old entry for the next request |
| `MDC.clear()` | Clears the entire context map of the current thread | Does not accidentally clear an outer scope's context |
| `MDC.getCopyOfContextMap()` | Returns a copy of the current map, possibly `null` | Capture on the calling thread **before submitting** |
| `MDC.setContextMap(map)` | Replaces the current thread's map with a copy of the given map | Must save/restore the previous map in `finally` |
| `MDC.putCloseable(key,value)` | Convenient scope that removes the key on close | Does not restore a previous value for the same key by default |
| `ILoggingEvent.getMDCPropertyMap()` | The MDC map attached to a Logback logging event | Inspect the actual event instead of only checking `MDC.get` |

**Version note:** Since SLF4J 2.0, `MDC.setContextMap(null)` is supported by the API; to keep the example code readable and explicit, we call `MDC.clear()` when the snapshot is `null`. The MDC map passed through the API uses `String` keys and values.

## 3. Testing Strategy: Three Layers of Verification

A useful test suite should verify behavior at three levels.

### 3.1. Unit Tests: MDC Scope Semantics

Verify that:

- `MDC.put` sets the right key/value.
- After the handler method finishes, MDC no longer holds the old request ID.
- If `requestId=req-parent` was set beforehand, a nested scope temporarily setting `req-child` must restore `req-parent` when closed.
- The scope does not accidentally erase other keys such as `traceId` or `jobId`.
- When an exception is thrown, `finally` or `AutoCloseable.close()` still cleans up the context.
- Invalid input is not turned into unexpected dynamic context.

This type of test is fast and helpful, but you still need to verify **actual events**.

### 3.2. Integration Tests: Events Captured by Logback

Attach a `ListAppender<ILoggingEvent>` to a dedicated test Logger, emit real logs, and check:

- Event count: no missing or duplicate events.
- `getLevel()`: matches INFO/WARN/ERROR.
- `getFormattedMessage()`: `{}` placeholders have been substituted.
- `getLoggerName()`: matches the expected Logger name.
- `getMDCPropertyMap().get("requestId")`: the ID attached to the **event** is correct.
- `getThrowableProxy()`: contains the Throwable when logging an error.

Prefer **asserting on `ILoggingEvent`**, and avoid merely capturing `System.out` or searching for a substring in stdout. Capturing JVM-wide stdout is easily polluted by Gradle, frameworks, logs from other tests, or encoder changes.

### 3.3. Integration/End-to-End: Is the Collector Output Correct?

Checking `ListAppender` does not guarantee that a JSON file, console pattern, or collector outputs the right fields. In a separate integration test, you can attach a `PatternLayout` or `OutputStreamAppender` to verify `%X{requestId}` appears in the output, or parse JSON Lines and assert the MDC fields.

In a web system, you can send a request through a test HTTP client, obtain the ID, and then verify the event captured at the appender/collector. However, tests relying on real agents/networks are slow and unstable; keep local unit/integration tests fast and run end-to-end tests at the appropriate test tier.

## 4. Scenario Matrix to Test

| Scenario | What Must Be Proven | What Bug Does It Prevent? |
| --- | --- | --- |
| Normal single request | Event has the right ID; MDC is cleared after processing | Missing context |
| Nested scope | Event gets the inner scope ID, then the outer scope is restored | Overwriting or accidentally clearing context |
| Processing throws an exception | Error log has the ID; MDC is still cleared in `finally` | ID leak on exception |
| MDC not set | Event does not contain a stale `requestId` | Old ID leaking into another request |
| Unwrapped executor task | Worker does not implicitly inherit caller's MDC | Misunderstanding `ThreadLocal` |
| Snapshot-wrapped executor task | Event from worker has the caller's right ID | Lost context in async execution |
| Subsequent task reusing worker | Previous task's ID is gone on the worker | Context leak in thread pool |
| Async task throws an exception | After failure, worker is still clean | Missed cleanup on exception |
| Two concurrent requests | A only carries ID A; B only carries ID B | Race conditions and cross-request contamination |
| PatternLayout/JSON encoder | Output has the right `requestId` field | Event is right, but encoder fails to render it |
| Wrong or missing provider | Test detects non-working MDC adapter/backend | False positives from mocks or NOP |
| Restart/repeated tests | Identical results, independent of test order | Shared state causing flaky tests |

**Do not assert global log ordering when two threads run concurrently.** Match events by `event name`/ID and compare sets or maps; use `Future.get`/`CountDownLatch` for synchronization instead of `Thread.sleep`.

### 5.5. `src/main/java/demo/RequestWorker.java`

```java
package demo;

import java.util.Map;
import java.util.Objects;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;

public final class RequestWorker {
    public static final String LOGGER_NAME = "demo.mdc.verify";

    private static final Logger LOG =
            LoggerFactory.getLogger(LOGGER_NAME);

    private RequestWorker() {
    }

    public static void processOrder(String requestId, String orderId) {
        try (MdcScope ignored = new MdcScope(requestId)) {
            LOG.info("event=order.accepted orderId={}", orderId);
        }
    }

    public static void processFailure(String requestId) {
        try (MdcScope ignored = new MdcScope(requestId)) {
            IllegalStateException error =
                    new IllegalStateException("simulated failure");
            LOG.error("event=order.failed", error);
            throw error;
        }
    }

    public static void logWorker(String message) {
        LOG.info(message);
    }

    // Called from the submitting thread to capture the caller's context.
    public static Runnable captureMdc(Runnable task) {
        Objects.requireNonNull(task, "task");
        Map<String, String> captured = MDC.getCopyOfContextMap();

        return () -> {
            Map<String, String> previous =
                    MDC.getCopyOfContextMap();
            try {
                if (captured == null) {
                    MDC.clear();
                } else {
                    MDC.setContextMap(captured);
                }
                task.run();
            } finally {
                restore(previous);
            }
        };
    }

    private static void restore(Map<String, String> snapshot) {
        if (snapshot == null) {
            MDC.clear();
        } else {
            MDC.setContextMap(snapshot);
        }
    }

    private static final class MdcScope implements AutoCloseable {
        private final Map<String, String> previous;

        private MdcScope(String requestId) {
            Objects.requireNonNull(requestId, "requestId");
            previous = MDC.getCopyOfContextMap();
            MDC.put("requestId", requestId);
        }

        @Override
        public void close() {
            restore(previous);
        }
    }
}
```

**Explanation of the business code:**

- `MdcScope` captures **the entire map before the scope begins**, temporarily replaces `requestId`, and restores the previous map on close. Nested scopes preserve `traceId` and other keys.
- `try-with-resources` calls `close()` even when processing throws an exception, preventing MDC from leaking to subsequent work on the same thread.
- `captureMdc` must be called on the **source thread before submitting the task**; it holds a snapshot of MDC to install on the worker.
- The worker saves its own existing context, installs the snapshot, runs the task, and restores in `finally`. This supports nested wrappers and does not assume the worker is always empty before a task.
- `MDC.clear()` is called when there is no snapshot; when a snapshot exists, `setContextMap` replaces the entire map.
- `LOGGER_NAME` is fixed per subsystem rather than embedding individual request IDs in Logger names.
- Application source code only imports SLF4J; the Logback backend lives in the test configuration.

**Limitation:** `captureMdc` only carries MDC data for logging. It does not automatically propagate security context, actual distributed tracing spans, transactions, or other `ThreadLocal` values. Your framework may provide a more comprehensive context propagation mechanism.

### 5.6. `src/test/java/demo/MdcLoggingTest.java`

```java
package demo;

import static org.junit.jupiter.api.Assertions.*;

import ch.qos.logback.classic.Level;
import ch.qos.logback.classic.Logger;
import ch.qos.logback.classic.PatternLayout;
import ch.qos.logback.classic.spi.ILoggingEvent;
import ch.qos.logback.core.read.ListAppender;
import java.util.HashMap;
import java.util.Map;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.ExecutionException;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.concurrent.TimeUnit;
import org.junit.jupiter.api.AfterEach;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.parallel.Execution;
import org.junit.jupiter.api.parallel.ExecutionMode;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;

@Execution(ExecutionMode.SAME_THREAD)
final class MdcLoggingTest {
    private Logger logger;
    private Level oldLevel;
    private boolean oldAdditivity;
    private ListAppender<ILoggingEvent> capture;

    @BeforeEach
    void attachCapture() {
        // Prevent MDC from a previous test from affecting the current test.
        MDC.clear();

        logger = (Logger) LoggerFactory.getLogger(
                RequestWorker.LOGGER_NAME);
        oldLevel = logger.getLevel();
        oldAdditivity = logger.isAdditive();

        logger.setLevel(Level.INFO);
        logger.setAdditive(false);

        capture = new ListAppender<>() {
            @Override
            protected synchronized void append(ILoggingEvent event) {
                // Capture data on the logging thread before MDC cleanup.
                event.prepareForDeferredProcessing();
                super.append(event);
            }
        };

        capture.setContext(logger.getLoggerContext());
        capture.setName("TEST_CAPTURE");
        capture.start();
        logger.addAppender(capture);
    }

    @AfterEach
    void detachCapture() {
        if (logger != null && capture != null) {
            logger.detachAppender(capture);
            capture.stop();
            logger.setLevel(oldLevel);
            logger.setAdditive(oldAdditivity);
        }
        MDC.clear();
    }

    private ILoggingEvent oneEvent() {
        assertEquals(1, capture.list.size());
        return capture.list.get(0);
    }

    @Test
    void eventContainsRequestIdAndFormattedMessage() {
        RequestWorker.processOrder("req-01", "ord-17");

        assertNull(MDC.get("requestId"));

        ILoggingEvent event = oneEvent();
        assertEquals(Level.INFO, event.getLevel());
        assertEquals(RequestWorker.LOGGER_NAME,
                event.getLoggerName());
        assertEquals("event=order.accepted orderId=ord-17",
                event.getFormattedMessage());
        assertEquals("req-01",
                event.getMDCPropertyMap().get("requestId"));
    }

    @Test
    void nestedScopeRestoresOuterContext() {
        MDC.put("requestId", "req-outer");
        MDC.put("traceId", "trace-42");

        RequestWorker.processOrder("req-inner", "ord-2");

        assertEquals("req-outer", MDC.get("requestId"));
        assertEquals("trace-42", MDC.get("traceId"));

        ILoggingEvent event = oneEvent();
        assertEquals("req-inner",
                event.getMDCPropertyMap().get("requestId"));
        assertEquals("trace-42",
                event.getMDCPropertyMap().get("traceId"));
    }

    @Test
    void failureStillRestoresContextAndRecordsThrowable() {
        IllegalStateException failure = assertThrows(
                IllegalStateException.class,
                () -> RequestWorker.processFailure("req-fail"));

        assertEquals("simulated failure", failure.getMessage());
        assertNull(MDC.get("requestId"));

        ILoggingEvent event = oneEvent();
        assertEquals(Level.ERROR, event.getLevel());
        assertEquals("req-fail",
                event.getMDCPropertyMap().get("requestId"));
        assertNotNull(event.getThrowableProxy());
    }

    @Test
    void eventWithoutContextDoesNotInventRequestId() {
        RequestWorker.logWorker("event=no.context");

        assertFalse(oneEvent().getMDCPropertyMap()
                .containsKey("requestId"));
    }

    @Test
    void rawExecutorTaskDoesNotInheritCallerMdc() throws Exception {
        ExecutorService executor =
                Executors.newSingleThreadExecutor();
        try {
            MDC.put("requestId", "req-caller");

            Future<String> result = executor.submit(() -> {
                RequestWorker.logWorker("event=async.raw");
                return MDC.get("requestId");
            });

            assertNull(result.get(5, TimeUnit.SECONDS));
            assertFalse(oneEvent().getMDCPropertyMap()
                    .containsKey("requestId"));
        } finally {
            executor.shutdownNow();
        }
    }

    @Test
    void snapshotPropagatesThenWorkerIsClean() throws Exception {
        ExecutorService executor =
                Executors.newSingleThreadExecutor();
        try {
            MDC.put("requestId", "req-async");

            Runnable wrapped = RequestWorker.captureMdc(() ->
                    RequestWorker.logWorker("event=async.wrapped"));
            MDC.clear();

            executor.submit(wrapped).get(5, TimeUnit.SECONDS);
            executor.submit(() ->
                    RequestWorker.logWorker("event=async.after"))
                    .get(5, TimeUnit.SECONDS);

            assertEquals(2, capture.list.size());
            assertEquals("req-async",
                    capture.list.get(0)
                            .getMDCPropertyMap().get("requestId"));
            assertFalse(capture.list.get(1)
                    .getMDCPropertyMap().containsKey("requestId"));
            assertNull(MDC.get("requestId"));
        } finally {
            executor.shutdownNow();
        }
    }

    @Test
    void failedAsyncTaskStillCleansWorker() throws Exception {
        ExecutorService executor =
                Executors.newSingleThreadExecutor();
        try {
            MDC.put("requestId", "req-error");

            Runnable failing = RequestWorker.captureMdc(() -> {
                RequestWorker.logWorker("event=async.will.fail");
                throw new IllegalStateException("task failed");
            });
            MDC.clear();

            Future<?> first = executor.submit(failing);
            ExecutionException failure = assertThrows(
                    ExecutionException.class,
                    () -> first.get(5, TimeUnit.SECONDS));

            assertInstanceOf(IllegalStateException.class,
                    failure.getCause());

            executor.submit(() ->
                    RequestWorker.logWorker("event=async.after.failure"))
                    .get(5, TimeUnit.SECONDS);

            assertEquals(2, capture.list.size());
            assertEquals("req-error",
                    capture.list.get(0)
                            .getMDCPropertyMap().get("requestId"));
            assertFalse(capture.list.get(1)
                    .getMDCPropertyMap().containsKey("requestId"));
        } finally {
            executor.shutdownNow();
        }
    }

    @Test
    void patternLayoutRendersCapturedContext() {
        PatternLayout layout = new PatternLayout();
        layout.setContext(logger.getLoggerContext());
        layout.setPattern(
                "requestId=%X{requestId} level=%level - %msg");
        layout.start();
        try {
            RequestWorker.processOrder("req-layout", "ord-9");

            assertEquals(
                    "requestId=req-layout level=INFO - "
                            + "event=order.accepted orderId=ord-9",
                    layout.doLayout(oneEvent()));
        } finally {
            layout.stop();
        }
    }

    @Test
    void parallelRequestsKeepSeparateIds() throws Exception {
        ExecutorService executor = Executors.newFixedThreadPool(2);
        CountDownLatch ready = new CountDownLatch(2);
        CountDownLatch start = new CountDownLatch(1);

        try {
            Future<?> a = executor.submit(() -> {
                ready.countDown();
                try {
                    if (!start.await(10, TimeUnit.SECONDS)) {
                        throw new IllegalStateException("start timeout");
                    }
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                    throw new IllegalStateException(e);
                }
                RequestWorker.processOrder("req-A", "A");
            });

            Future<?> b = executor.submit(() -> {
                ready.countDown();
                try {
                    if (!start.await(10, TimeUnit.SECONDS)) {
                        throw new IllegalStateException("start timeout");
                    }
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                    throw new IllegalStateException(e);
                }
                RequestWorker.processOrder("req-B", "B");
            });

            assertTrue(ready.await(10, TimeUnit.SECONDS));
            start.countDown();
            a.get(10, TimeUnit.SECONDS);
            b.get(10, TimeUnit.SECONDS);

            assertEquals(2, capture.list.size());

            // Independent of thread scheduling or log order.
            Map<String, String> actual = new HashMap<>();
            for (ILoggingEvent event : capture.list) {
                actual.put(event.getFormattedMessage(),
                        event.getMDCPropertyMap().get("requestId"));
            }

            assertEquals(Map.of(
                    "event=order.accepted orderId=A", "req-A",
                    "event=order.accepted orderId=B", "req-B"),
                    actual);
        } finally {
            start.countDown();
            executor.shutdownNow();
        }
    }
}
```

### 5.7. Why Does the Test Appender Call `prepareForDeferredProcessing()`?

This is a critical technical detail when testing **MDC in events**.

In Logback, an `ILoggingEvent` can **lazily retrieve MDC data** the first time `getMDCPropertyMap()` is called. A plain `ListAppender` only holds a reference to the event. If a test:

1. Emits a log while MDC has `requestId=req-A`.
2. Exits the scope and clears MDC.
3. Only then calls `event.getMDCPropertyMap()`.

then in some situations the test can capture the snapshot **too late**, reflecting the cleared context instead of the context at the time the event was emitted.

In the test suite, `ListAppender` is customized to call:

```java
event.prepareForDeferredProcessing();
```

**Right inside `append` on the logging thread**, before the scope is cleaned up. This call prepares the information needed for deferred processing, including the message and MDC according to Logback's mechanism. As a result, the test measures the **actual emitted event** rather than reading the thread context at a later point in time.

`protected synchronized void append(...)` also ensures updates to `ListAppender.list` are serialized when two workers log concurrently. Always read the list **after the `Future`s complete**; do not read an `ArrayList` being updated by workers without synchronization.

**Key distinction:** This test does not mock logging. It uses a real Logger and MDC, a real Logback backend, and real events. However, it is still an **in-process application test** and does not prove that a production collector received the event.

### 6.1. Key Takeaways from the Nine Tests

1. **MDC attached to the event:** The first test confirms `requestId=req-01` remains on the event after the scope has closed.
2. **Nested scope:** The event's ID is `req-inner`, while the calling thread is restored to `req-outer`.
3. **Exception cleanup:** The error is thrown, yet `requestId` does not leak and the ERROR event includes the Throwable.
4. **No context means no fabricated ID:** The negative test guards against false positives.
5. **Executor does not inherit caller MDC by default:** A raw worker does not receive `req-caller`.
6. **Snapshot propagation:** The wrapper transfers `req-async` to the worker; the next task does not carry this ID.
7. **Failed async task:** Cleanup still runs in `finally`, leaving no `req-error` for the subsequent task.
8. **Pattern output:** `%X{requestId}` actually renders as `requestId=req-layout` in text.
9. **Two concurrent requests:** A and B are compared **by message → requestId**, independent of thread ordering.

The suite's strength is verifying both **MDC state** and **logging event snapshots**; its limitation is that it does not yet measure collectors or cross-process tracing headers.

## 7. Testing Through `PatternLayout`, `OutputStreamAppender`, and JSON Encoders

`ListAppender` proves the event has MDC; `PatternLayout` proves text layouts use MDC. In production, output also passes through an Appender/Encoder, which may transform or filter fields.

### 7.1. PatternLayout Test

A typical pattern:

```text
%d{yyyy-MM-dd HH:mm:ss.SSS,UTC} %-5level [%thread] %logger{36} requestId=%X{requestId} - %msg%n
```

In unit tests, avoid comparing variable timestamps or thread names. Choose a simple pattern as in the test:

```text
requestId=%X{requestId} level=%level - %msg
```

and assert the exact string. When testing the production format, create a `PatternLayout`/`PatternLayoutEncoder` with the exact deployed pattern and verify **required fields**, timezone, and custom escaping rather than comparing against a hardcoded timestamp.

### 7.2. OutputStreamAppender Test

If your target is the final bytes, you can use `OutputStreamAppender<ILoggingEvent>` with `ByteArrayOutputStream` in a separate integration test:

1. Create a `PatternLayoutEncoder`, set `LoggerContext`, and configure a pattern containing `%X{requestId}`.
2. Create an `OutputStreamAppender`, attach the encoder and output stream.
3. Start the encoder/appender and attach it to the test Logger.
4. Emit a log inside an MDC scope.
5. Convert the bytes to UTF-8 and assert the output line.
6. Detach the Appender, stop it, and restore the Logger in `finally`.

This is a **procedure**, not a complete program. `ByteArrayOutputStream` must belong to a separate test so it does not alter the main configuration of the nine tests above; avoid attaching two appenders to the same output simultaneously unless duplicate logs are intended.

### 7.3. JSON Encoder

If using JSON Lines, parse each line with a standard JSON parser and assert the MDC field, for example:

```json
{
  "level": "INFO",
  "message": "event=order.accepted",
  "mdc": {
    "requestId": "req-42"
  }
}
```

This is **illustrative JSON**, not the default schema of every encoder. Native Logback `JsonEncoder`, `LogstashEncoder`, or framework encoders have **different field names and structures**; tests must match **your actual schema**. Verify data types, JSON escaping, and that each event sits on a single physical line.

Do not merely check whether the raw string contains `req-42`: the ID could accidentally appear inside `message` while being completely absent from the MDC field used by your collector or dashboard.

## 8. Concurrency Testing: Avoiding Flaky Tests

Logging tests are prone to flakiness due to contention over global state.

### 8.1. Never Use `Thread.sleep` for Synchronization

Code like this:

```java
executor.submit(() -> logger.info("event=async"));
Thread.sleep(100);
assertEquals(1, captured.size());
```

is an **illustrative anti-pattern**: after 100ms, the worker may not have been scheduled yet on a heavily loaded CI runner. The test will flake even when the application is correct.

Use `Future.get(timeout, unit)` to wait for task completion; use `CountDownLatch`/`CyclicBarrier` to coordinate threads. Always set a timeout so a failing test **fails clearly** instead of hanging forever.

### 8.2. Do Not Assert Ordering Between Two Independent Threads

In a parallel test:

```text
A: event=order.accepted orderId=A
B: event=order.accepted orderId=B
```

The system does not guarantee whether A or B appears first. Compare a `Map<message,requestId>` or `Set` instead of assuming `capture.list.get(0)` is A and `capture.list.get(1)` is B. In the example suite, iteration over the list happens **only after both `Future`s complete**.

### 8.3. Isolate `ListAppender` and Shared Loggers

A Logback `Logger` is typically shared within a `LoggerContext`. If concurrent tests modify level, additivity, or attach/detach appenders on the same Logger, they can interfere with one another.

Practices applied in the example:

- A dedicated Logger name for the suite: `demo.mdc.verify`.
- `@BeforeEach` saves level/additivity and attaches the test Appender.
- `@AfterEach` detaches/stops the Appender, restores Logger state, and calls `MDC.clear()`.
- `@Execution(SAME_THREAD)` prevents tests **within the class** that share the Logger from running in parallel.
- Each test creates its own executor and shuts it down in `finally`.
- If tests need to run in parallel at the suite level across multiple classes, use distinct Logger names/`LoggerContext` instances or appropriate isolation; a class-level annotation does not prevent unrelated code from touching its Logger.

### 8.4. Do Not Assume `ListAppender.list` Is Thread-Safe

`ListAppender` uses an internal list and should not be written to concurrently by multiple workers without synchronization. The example overrides `append` with `synchronized` and calls `prepareForDeferredProcessing` on the worker. Reading the list after `Future.get` ensures tasks have finished and avoids reading while writes are still happening.

In systems needing to capture large numbers of events or run highly concurrent tests, write a dedicated test Appender backed by an appropriate concurrent data structure rather than pushing `ListAppender` beyond what it was designed for.

## 9. Testing Propagation Across Thread Pools, CompletableFuture, and Frameworks

### 9.1. ExecutorService

The proper lifecycle:

```text
Request thread:
  MDC.put("requestId","req-A")
  snapshot = MDC.getCopyOfContextMap()
  submit(wrapped task)

Worker thread:
  previous = MDC.getCopyOfContextMap()
  install snapshot (MDC.setContextMap or MDC.clear)
  emit log event
  finally: restore previous
```

**Capture must be called on the submitting thread.** If you call `MDC.getCopyOfContextMap()` for the first time inside the worker, you capture the worker's context, not the request's. That is why the raw test and the wrapped test have opposite outcomes.

### 9.2. CompletableFuture

`CompletableFuture.supplyAsync`, `runAsync`, and `thenApplyAsync` can execute on different threads. Tests must cover **every thread-handoff boundary**, not just the first async step.

Example **code snippet**:

```java
Runnable wrapped = RequestWorker.captureMdc(() ->
        RequestWorker.logWorker("event=async.stage"));

CompletableFuture<Void> future =
        CompletableFuture.runAsync(wrapped, executor);

future.join();
```

The snippet above assumes `executor` already exists and `CompletableFuture` is imported; it is not a standalone class. `join` ensures the task finishes, but it does not propagate MDC on its own—the helper's `captureMdc` handles that. If a subsequent stage runs on another executor, wrap it as well or use a pipeline-wide propagation mechanism.

### 9.3. Spring MVC / Servlet Filters

When an application uses a `OncePerRequestFilter` or interceptor to set MDC at the start of a request, integration tests should:

1. Send requests both with and without a valid correlation header.
2. Verify that the filter generates/validates the ID before the service emits logs.
3. Verify that log events carry the right request ID.
4. Send a subsequent request on a reused thread mechanism and confirm it does not carry the previous ID.
5. Trigger an exception or error response to verify `finally`.
6. If using async dispatch, verify propagation and cleanup across the lifecycle supported by the framework.

Do not assume `@WebMvcTest` or a mock HTTP server always reproduces production thread-pool behavior; async cases may require integration tests with a real executor and filter chain.

### 9.4. Reactive and Messaging

With Reactor, callbacks can switch threads, and **Reactor Context** is not equivalent to `ThreadLocal` MDC. Tests must use the context propagation mechanisms of the reactive/tracing stack. With Kafka/RabbitMQ, create context **per message** and clean up before the next message, especially when consumer threads are reused.

A test that only sets MDC on the calling thread and sends a message does not prove that the context automatically exists in a consumer in another process. Cross-process context must be passed via **headers/metadata** and validated/restored appropriately on the receiving side.

## 10. Testing MDC with Asynchronous Logging Output

There are two distinct kinds of async behavior:

1. **Business async:** a request moves from thread A to business worker B. MDC must be propagated **before worker B emits logs**.
2. **Async logging:** the event is created on B, but an `AsyncAppender` offloads encoding/writing to thread C. MDC must be **captured into the event at creation time**, not read from thread C's MDC.

```text
Request A (MDC req-42)
    |
    | propagate snapshot
    v
Business worker B (MDC req-42)
    |
    | logger.info -> event carries context req-42
    v
AsyncAppender worker C
    |
    | encode event (do not read C's ThreadLocal)
    v
stdout / file / collector
```

Without A→B propagation, `AsyncAppender` cannot recover the lost ID. Conversely, if a custom encoder calls `MDC.get("requestId")` on thread C instead of reading the event's MDC map, it may output the wrong ID or an empty value.

### 10.1. Tests Should Verify Two Layers

- **Business propagation:** the event emitted by worker B has `getMDCPropertyMap().get("requestId") == req-42`.
- **Output snapshot:** after worker B clears MDC, the queued record still outputs `req-42` in thread C's formatter/encoder.

To test a real async pipeline, use an Appender/queue with a drain-wait mechanism, an explicit timeout, and assert output after a normal flush/shutdown. Never use `Thread.sleep` as a guarantee that "the queue is empty".

### 10.2. Do Not Use Logging to Test Access Control

`MDC.get("tenantId")` can hold arbitrary strings and is strictly for diagnostics. Security authorization tests must never rely on MDC as an authentication source. When security context is needed, use a dedicated security context mechanism with guaranteed propagation and lifecycle management.

## 11. Important Negative Tests

A good test suite does more than prove the happy path.

### 11.1. When an MDC-Capable Provider Is Missing

If the runtime only has `slf4j-api` without a suitable backend, logging may fall back to NOP. If using a provider with `NOPMDCAdapter`, `MDC.put` will not store any useful context. Tests should fail clearly when `ILoggingEvent` does not appear or lacks expected fields.

Do not mock `MDC.get` to always return `req-42` and conclude integration succeeded. The goal here is to verify **a real backend and real events**.

### 11.2. Misnamed Keys or Wrong Scope Usage

For example, if a producer calls `MDC.put("requestID", "...")` while the encoder reads `%X{requestId}`, the keys differ and output is missing. Tests should assert the **exact field name** in both the event and the formatted output.

Nested scopes can overwrite an existing `requestId`. If the code only calls `MDC.remove("requestId")` on close without restoring the prior value, the outer context is lost. The `nestedScopeRestoresOuterContext` test catches this bug.

### 11.3. Worker Retains Stale Context

When a thread pool reuses a worker, a failing task can leave behind `requestId` if there is no `finally` block. Submit a subsequent task on **the same single-thread executor** and assert the later event has no request ID. This is a much stronger leak test than merely asserting `MDC.get(...)` on the main thread.

### 11.4. Missing IDs and Untrusted Input

When the `X-Request-ID` header is missing or invalid, the application may generate a new ID according to policy. Tests should verify that empty values, overly long strings, newlines, or dangerous path fragments never enter the log context unvalidated.

To prevent log injection, test request IDs containing newlines or control characters and verify that middleware rejects or sanitizes them before `MDC.put`; backend JSON escaping alone does not replace ID validation.

### 11.5. Ordering/Timeouts Causing CI Flakiness

Parallel tests need explicit wait conditions rather than timestamps or arbitrary millisecond sleeps. For resource-sensitive tests, verify timeouts, eliminate unnecessary side effects, and ensure executors are shut down.

## 12. Security and Sensitive Data in MDC

MDC is not a dumping ground for all request data. A `MDC.getCopyOfContextMap()` snapshot preserves every key set on the calling thread; if it contains tokens, cookies, or PII, async tasks and logs may carry unauthorized data.

Guidelines:

- **Allowlist fields** for diagnostics: `requestId`, `traceId`, `spanId`, `operation`, `errorCode`, `jobId` as needed.
- Never put passwords, bearer tokens, cookies, secret keys, or sensitive payment details into MDC.
- Validate/bound client-supplied `requestId` values; do not trust a value just because it is in MDC.
- Never create Logger names with dynamic IDs or build file paths from untrusted MDC data.
- Never use MDC as an authorization or tenant-isolation mechanism.
- Verify JSON/text encoders do not leak secrets from messages, throwables, or custom fields.
- Configure retention and read permissions everywhere log data is copied.
- In tests, use synthetic IDs such as `req-A`/`req-B`; never use real personal data in fixtures.

MDC is a diagnostic utility; privacy and security requirements must be enforced at both **the event source and throughout the logging pipeline**.

## 13. Common Errors and Fixes

| Symptom | Likely Cause | How to Verify/Fix |
| --- | --- | --- |
| `MDC.get` is right, but logs lack the ID | Encoder does not output MDC or no suitable backend is present | Inspect the event map and layout separately |
| Event lacks ID after `MdcScope.close()` | `ListAppender` read MDC too late | Call `prepareForDeferredProcessing` inside `append` |
| Tests occasionally show a previous request's ID | Test forgot `MDC.clear()` or thread pool leaked context | Clean up in `@AfterEach` and inside task `finally` |
| Async task lacks ID | Not captured/propagated from caller | Snapshot before `submit`, install in worker |
| Task after an exception has stale ID | Missing cleanup in `finally` | Test failure followed by another task on the same worker |
| Outer scope loses ID after inner scope | Only removed key without restoring | Save previous map/value and restore it |
| Parallel tests fail intermittently | Asserted wrong event order; non-thread-safe Appender | Use Latch/Future, synchronize `append`, compare maps/sets |
| Tests print duplicate logs | Root has an Appender and test Logger is still additive | Use a dedicated test Logger with `setAdditive(false)` |
| Other tests' logs skew event count | Appender attached to root or shared Logger | Attach only to a dedicated Logger name |
| `ListAppender` captures no events | Appender not started, Logger level OFF, or different backend | Start appender and set test Logger level |
| `requestId` field empty in JSON | Different field name/schema path, or MDC not enabled | Parse actual JSON and verify field mapping |
| Console test has unexpected timestamp | Test depends on clock/thread | Assert stable fields; do not hardcode time |
| `System.out`-based test is unstable | Output from Gradle/frameworks mixed in | Inspect `ILoggingEvent` or a dedicated stream |
| Unit tests pass, but production loses traces | Context not propagated across network/reactive boundary | Add integration/E2E tests with headers/instrumentation |
| CI hangs on executor | Executor not shut down or `Future` waits forever | Use timeouts and `shutdownNow()` in `finally` |
| MDC contains secrets in test output | Fixture or code writes too much data | Minimize fields, mask values, and check policy |

## 14. Pre-Commit Test Quality Checklist

- [ ] Tests use the **real SLF4J API and provider/backend** of the target environment.
- [ ] Tests verify event `getMDCPropertyMap()`, not just `MDC.get()`.
- [ ] Tests check formatted message, level, and logger name when relevant.
- [ ] `ListAppender` is started/stopped and attached/detached within the test scope.
- [ ] Events are prepared before MDC cleanup if tests retain event references.
- [ ] `@BeforeEach`/`@AfterEach` reset MDC and restore Logger configuration.
- [ ] Tests cover missing MDC, nested scopes, and exception paths.
- [ ] A test covers an executor **without propagation** to document the actual boundary.
- [ ] A test covers an executor **with propagation** and verifies no ID leaks to the next task.
- [ ] A test covers a worker task throwing an exception with worker reuse.
- [ ] A test covers two concurrent requests without relying on log order.
- [ ] A test verifies that the layout/encoder outputs the exact `requestId` field read by the collector.
- [ ] Timeouts and executor shutdowns are present; no `Thread.sleep` is used.
- [ ] Limitations of local tests regarding distributed tracing/async frameworks are understood.
- [ ] MDC only contains necessary diagnostic fields and no sensitive data.
- [ ] JSON schema, key naming, escaping, and storage permissions are reviewed when using centralized logging.

A few `MDC.get` assertions on the main thread are not enough to guarantee a safe logging system under concurrency.
