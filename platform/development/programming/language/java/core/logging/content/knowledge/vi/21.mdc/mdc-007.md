# MDC trong thread pool — truyền context logging an toàn với Java

## 1. Vấn đề cần giải quyết

Trong **Java Core Logging**, **MDC (Mapped Diagnostic Context)** là một tập các trường key–value, thường gồm **requestId, traceId, jobId**, mà logging backend có thể tự thêm vào mỗi sự kiện log phát sinh trên thread đang xử lý.

Ví dụ bản ghi có MDC:

~~~text
requestId=req-A INFO event=order.received orderId=ORD-17
requestId=req-A INFO event=inventory.reserved orderId=ORD-17
requestId=req-A INFO event=order.completed orderId=ORD-17
~~~

Đây là đầu ra minh họa một pattern log, không phải format mặc định của mọi backend.

**Thread pool** tái sử dụng một số thread để chạy nhiều Runnable/Callable khác nhau. Khi một HTTP request submit công việc cho pool, thread chạy task **không nhất thiết có MDC của thread gửi**. Thậm chí nếu một tác vụ trước đã gán MDC mà quên cleanup, tác vụ sau có thể **nhận nhầm requestId cũ**.

Có hai lỗi khác nhau:

- **Missing context:** log worker không có requestId/traceId, khiến không thể liên kết sự kiện với request cha.
- **Context leakage:** log của request B mang requestId của request A do worker thread được tái sử dụng.

Giải pháp chuẩn: **capture → install → execute → restore** trên từng task. Chụp snapshot trên caller trước khi submit, cài snapshot khi worker chạy, thực thi nhiệm vụ rồi khôi phục MDC worker trong **finally**.

**Không xem MDC là cơ chế request propagation tự động**. MDC chủ yếu là metadata cho logging tại thời điểm LogEvent được tạo; không thay transaction context, security principal hay distributed tracing.

## 2. Tại sao ThreadLocal không tự đi theo task?

Các MDC implementation phổ biến giữ context gần với **ThreadLocal** của thread hiện tại. ThreadLocal chỉ áp dụng cho một thread cụ thể, không tự chuyển sang thread khác chỉ vì task được submit.

~~~text
HTTP worker:
  MDC {requestId=req-A}
       |
       | executor.submit(task)
       v
Pool worker-1:
  MDC {} hoặc {requestId=req-OLD}
       |
       v
  LOG.info("event=inventory.lookup")
~~~

**Executors.newFixedThreadPool(...)** và **newCachedThreadPool(...)** quản lý worker và có thể dùng lại những thread đã tạo từ trước. Task A và B có thể chạy trên cùng worker, hoặc một task được chạy trên worker khác tùy lịch.

**InheritableThreadLocal** không giải quyết an toàn bài toán này: giá trị có thể được kế thừa lúc **tạo thread con**, trong khi thread của pool đã có sẵn từ trước hoặc được tái sử dụng. **Submission boundary không phải thread creation boundary**.

| Khái niệm | Phạm vi |
| --- | --- |
| ThreadLocal | State của một thread |
| InheritableThreadLocal | Có thể kế thừa lúc thread được tạo, theo implementation |
| Runnable/Callable | Đơn vị công việc được submit |
| ExecutorService | Quản lý việc giao task cho worker |
| MDC snapshot | Bản sao context lấy tại caller |
| MDC restoration | Khôi phục state của worker sau task |
| Request ID | Định danh yêu cầu, không phải tên worker thread |

**Thread name** như pool-1-thread-1 xác định worker, không xác định request. Cùng worker có thể chạy hàng nghìn request.

## 3. Dấu hiệu mất context và rò context

**Thiếu context:**

~~~text
thread=http-1 requestId=req-A event=request.received
thread=pool-1 requestId=none event=inventory.reserve
~~~

**Rò dữ liệu của task trước:**

~~~text
thread=pool-1 requestId=req-A event=job.A.completed
thread=pool-1 requestId=req-A event=job.B.started
~~~

Trong trường hợp thứ hai, nếu job B thuộc req-B, log trông hợp lệ về cú pháp nhưng **sai sự thật**. Việc lọc log theo tenant/request có thể đưa ra kết luận sai.

Ví dụ code **không propagate**:

~~~java
MDC.put("requestId", "req-A");
executor.submit(() -> LOG.info("event=inventory.reserve"));
MDC.remove("requestId");
~~~

Đây là snippet, giả định LOG và executor đã có. Hai thao tác put/remove chạy ở **caller**, còn LOG.info chạy ở **worker**. Không có bảo đảm worker nhìn thấy req-A.

Ví dụ **gây stale context**:

~~~java
executor.submit(() -> {
    MDC.put("requestId", requestId);
    service.process();
});
~~~

Đây cũng là snippet. Nếu service.process() ném exception, lời gọi cleanup không có; worker có thể giữ requestId cho task tiếp theo. Cần dùng finally.

**Một bài kiểm tra chỉ chạy một task không đủ** để phát hiện lỗi reuse; hãy cố tình chạy A, B và task không có context trên cùng một worker.

## 4. Các API SLF4J MDC quan trọng

Với **org.slf4j.MDC**:

| Method | Ý nghĩa |
| --- | --- |
| **MDC.put(key, value)** | Gán một cặp key–value cho thread hiện tại |
| **MDC.get(key)** | Đọc key ở thread hiện tại |
| **MDC.remove(key)** | Xóa một key |
| **MDC.clear()** | Xóa toàn bộ MDC map hiện tại |
| **MDC.getCopyOfContextMap()** | Trả bản sao Map; **có thể null** |
| **MDC.setContextMap(map)** | Đặt lại toàn bộ MDC Map bằng bản sao được cung cấp |
| **MDC.putCloseable(key, value)** | Đặt key và trả scope có thể close để remove key |

**getCopyOfContextMap()** phải được gọi ở **caller trước submit** để chụp đúng ngữ cảnh nguồn. Nếu gọi trong worker, nó chỉ trả trạng thái hiện tại của worker, có thể rỗng hoặc bị rò từ task trước.

**setContextMap(null)** được hỗ trợ từ SLF4J 2.x; nhưng một wrapper dễ hiểu thường dùng **MDC.clear()** khi snapshot null/empty và **MDC.setContextMap(snapshot)** khi có dữ liệu.

**putCloseable** giúp dọn một key ở cuối try-with-resources; **không phải một stack restore giá trị cũ của key cùng tên**. Nếu nested scope dùng lại requestId, phải có cơ chế save/restore riêng.

SLF4J là **facade**: backend/provider thực tế như Logback hoặc Log4j 2 mới quyết định cách lưu MDC và xuất vào file/console. Một provider không hỗ trợ MDC hữu ích có thể khiến API vẫn tồn tại nhưng output không có field mong đợi.

## 5. Bốn bước capture → install → execute → restore

Sơ đồ:

~~~text
Caller thread                             Worker thread
-------------                             -------------
MDC {requestId=req-A}
      |
      | getCopyOfContextMap()
      v
snapshot {requestId=req-A}
      |
      +--- executor.submit(wrapper) ---->
                                          previous = worker MDC
                                          try {
                                              install(snapshot)
                                              task.run()
                                          } finally {
                                              install(previous)
                                          }
Caller có thể clear MDC                   Worker trở về state cũ
~~~

**Capture:** lấy snapshot một lần tại nơi thực sự có request context.

**Install:** thay context của worker trước khi action tạo LogEvent; nếu caller không có MDC thì **clear** trên worker trong thời gian chạy action.

**Execute:** chạy task như bình thường, để exception/return của task giữ đúng semantics.

**Restore:** lưu previous của worker và khôi phục trong finally, kể cả khi task ném RuntimeException, Error hoặc bị interrupt.

Vì sao **restore** khác **clear**? Một task có thể chạy bên trong một context worker hợp lệ, ví dụ batchId=batch-7. Nếu cuối task chỉ clear, batchId bị mất. Restore trả worker về trạng thái trước task.

**Giới hạn:** nếu previous của worker đã bị nhiễm dữ liệu từ task cũ, restore sẽ giữ lại trạng thái đó. Cần sửa chỗ gây rò và đảm bảo top-level tasks đều đi qua boundary cleanup; không xem decorator là hệ thống tự làm sạch những lỗi đã xảy ra.

## 6. Wrapper Runnable có thể tái sử dụng

Một lớp tiện ích SLF4J:

~~~java
import java.util.Map;
import org.slf4j.MDC;

public final class MdcWrappers {
    private MdcWrappers() {}

    private static void install(Map<String, String> context) {
        if (context == null || context.isEmpty()) {
            MDC.clear();
        } else {
            MDC.setContextMap(context);
        }
    }

    public static Runnable withMdc(Runnable action) {
        Map<String, String> captured =
                MDC.getCopyOfContextMap();

        return () -> {
            Map<String, String> previous =
                    MDC.getCopyOfContextMap();
            try {
                install(captured);
                action.run();
            } finally {
                install(previous);
            }
        };
    }
}
~~~

Đây là **lớp Java thành phần** cần dependency SLF4J và một provider tương thích, không có main() và chưa tự ghi log.

Sử dụng:

~~~java
try (MDC.MDCCloseable scope =
        MDC.putCloseable("requestId", requestId)) {
    Future<?> future = executor.submit(
            MdcWrappers.withMdc(
                    () -> service.process(orderId)));
    future.get();
}
~~~

Đây là snippet, giả định executor, service, requestId, orderId và imports đã có.

**Điểm kiểm tra:** withMdc được gọi ngay **trên caller trước submit**, không phải bên trong lambda của worker. Map captured là dữ liệu sẽ được cài lên worker, còn previous là trạng thái cần restore sau đó.

Nếu ứng dụng có nhiều nhánh gửi task, mọi nhánh liên quan cần đi qua decorator. Một nhánh submit trực tiếp có thể khiến toàn bộ hệ thống chỉ bị lỗi MDC một cách không ổn định.

## 7. Callable<T> và Future

Callable trả kết quả và có thể ném checked exception. Có thể viết overload:

~~~java
public static <T> java.util.concurrent.Callable<T> withMdc(
        java.util.concurrent.Callable<T> action) {
    java.util.Map<String, String> captured =
            org.slf4j.MDC.getCopyOfContextMap();

    return () -> {
        java.util.Map<String, String> previous =
                org.slf4j.MDC.getCopyOfContextMap();
        try {
            if (captured == null) org.slf4j.MDC.clear();
            else org.slf4j.MDC.setContextMap(captured);
            return action.call();
        } finally {
            if (previous == null) org.slf4j.MDC.clear();
            else org.slf4j.MDC.setContextMap(previous);
        }
    };
}
~~~

Đây là **method snippet**, không phải chương trình độc lập. Trong codebase thực, nên gom logic install/restore vào helper dùng chung.

**Future.get()** có thể ném **ExecutionException** khi task bên trong lỗi, và **InterruptedException** khi thread chờ bị ngắt. Dù task lỗi, finally trong wrapper vẫn thực thi khi task đã bắt đầu và kết thúc bằng exception.

Khi gọi **invokeAll(...)**, cần wrap **từng Callable** trước khi gửi vào pool. Không wrap Future sau khi nó đã được submit vì khi đó phần công việc đã chạy hoặc đang chạy sai context.

**execute() và submit()** có cách báo lỗi khác nhau, nhưng yêu cầu cleanup MDC trong worker giống nhau.

## 8. Ví dụ Java 17 + Maven + Logback chạy độc lập

Các task:

1. Request A có MDC **req-A**, submit log công việc A.
2. Request B có MDC **req-B**, submit công việc B trên **cùng worker**.
3. Caller không có requestId, submit một probe kiểm tra worker không giữ ID cũ.

### src/main/java/demo/MdcPoolDemo.java

~~~java
package demo;

import java.util.Map;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;

public final class MdcPoolDemo {
    private static final Logger LOG =
            LoggerFactory.getLogger(MdcPoolDemo.class);

    private MdcPoolDemo() {}

    private static void install(Map<String, String> context) {
        if (context == null || context.isEmpty()) {
            MDC.clear();
        } else {
            MDC.setContextMap(context);
        }
    }

    private static Runnable withMdc(Runnable task) {
        Map<String, String> captured = MDC.getCopyOfContextMap();

        return () -> {
            Map<String, String> previous = MDC.getCopyOfContextMap();
            try {
                install(captured);
                task.run();
            } finally {
                install(previous);
            }
        };
    }

    private static void await(Future<?> future) throws Exception {
        future.get();
    }

    public static void main(String[] args) throws Exception {
        ExecutorService pool = Executors.newSingleThreadExecutor(
                task -> new Thread(task, "mdc-worker"));

        try {
            try (MDC.MDCCloseable ignored =
                    MDC.putCloseable("requestId", "req-A")) {
                await(pool.submit(withMdc(
                        () -> LOG.info("event=job.started job=A"))));
            }

            try (MDC.MDCCloseable ignored =
                    MDC.putCloseable("requestId", "req-B")) {
                await(pool.submit(withMdc(
                        () -> LOG.info("event=job.started job=B"))));
            }

            await(pool.submit(withMdc(() -> {
                if (MDC.get("requestId") != null) {
                    throw new IllegalStateException(
                            "Worker retained a requestId");
                }
                LOG.info("event=worker.clean");
            })));
        } finally {
            pool.shutdown();
            MDC.clear();
        }
    }
}
~~~

### Giải thích kết quả

1. **newSingleThreadExecutor** dùng lại một thread tên **mdc-worker**.
2. **putCloseable req-A** đặt MDC trên caller; **withMdc** capture trước khi task được submit.
3. Worker lưu previous, cài req-A rồi Logger phát event; **%X** của Logback đọc được req-A.
4. **finally** restore worker context; caller cũng remove req-A khi thoát scope.
5. Request B thực hiện tương tự với req-B, vẫn trên mdc-worker.
6. Task probe được tạo khi caller không có MDC; wrapper clear worker trong thời gian chạy probe.
7. Probe assert **MDC.get("requestId") == null**. Nếu sai, Future.get sẽ báo lỗi thay vì im lặng.
8. Khi không có requestId, pattern dùng fallback **none**.
9. **Future.get()** sau từng task làm thứ tự A, B, probe xác định cho demo. Với nhiều worker và task độc lập, thứ tự log có thể khác.
10. **pool.shutdown()** ngừng nhận task mới; demo đã chờ các Future nên không cần dùng Thread.sleep.
11. **MDC.clear()** ở main là cleanup của chương trình này; trong component thực, tránh clear context thuộc scope khác.

**Điểm học tập:** MDC không được truyền nhờ dùng pool một thread, mà nhờ wrapper ở **submission boundary** và cleanup trong **finally**.

## 9. Vì sao cleanup phải là finally?

Một snippet dễ mắc lỗi:

~~~java
pool.submit(() -> {
    MDC.put("requestId", requestId);
    doWork();
    MDC.clear();
});
~~~

Nếu doWork ném exception, **MDC.clear()** không chạy. Worker có thể giữ requestId cũ.

Sửa theo scope sở hữu task:

~~~java
pool.submit(() -> {
    try {
        MDC.put("requestId", requestId);
        doWork();
    } finally {
        MDC.remove("requestId");
    }
});
~~~

Đây là snippet, giả định biến được khai báo. Nó giải quyết **một key** nhưng không propagate tất cả context của caller và không restore một giá trị cùng tên có thể đã tồn tại.

**Wrapper save/restore toàn bộ Map** thường phù hợp hơn với một executor decorator tổng quát, đặc biệt khi MDC có nhiều key và có nested execution. Nếu mọi top-level task bắt buộc phải bắt đầu/kết thúc với MDC rỗng, có thể dùng clear tại task boundary do bạn sở hữu; đừng áp chính sách ấy lên nested scope không thuộc mình.

## 10. CompletableFuture và các async boundaries

**CompletableFuture.runAsync** thường chạy task trên một executor khác với caller:

~~~java
CompletableFuture<Void> result = CompletableFuture.runAsync(
        () -> LOG.info("event=background.started"), executor);
~~~

Đây là snippet, giả định LOG/executor. Không có propagation, worker có thể không thấy requestId.

Bọc task:

~~~java
CompletableFuture<Void> result = CompletableFuture.runAsync(
        MdcWrappers.withMdc(
                () -> LOG.info("event=background.started")),
        executor);
~~~

**Điều cần chú ý:**

- **supplyAsync, thenApplyAsync, thenAcceptAsync, handleAsync** có thể chuyển sang thread mới. Cần context propagation ở **từng async boundary**.
- **thenApply không Async** có thể chạy trên thread hoàn thành upstream hoặc thread đăng ký callback tùy timing, nên không giả định MDC của HTTP caller.
- Nếu continuation được đăng ký **sau khi request scope đã đóng**, một wrapper capture MDC lúc ấy có thể nhận null. Cần giữ **snapshot request context** đã được xác định trước đó.
- Với Function/Supplier/Consumer, cần các decorator tương ứng, không ép thành Runnable không phù hợp.
- **ForkJoinPool.commonPool()** không có hợp đồng tự mang MDC của caller.
- Exception/cancellation không được bỏ qua finally ở từng boundary.
- Nếu framework cung cấp **context propagation** chính thức, ưu tiên nó thay vì viết wrapper khác nhau ở từng service.

Một method snippet cho Function:

~~~java
static <T, R> java.util.function.Function<T, R> withContext(
        java.util.function.Function<T, R> action,
        java.util.Map<String, String> captured) {
    return value -> {
        java.util.Map<String, String> previous =
                org.slf4j.MDC.getCopyOfContextMap();
        try {
            if (captured == null) org.slf4j.MDC.clear();
            else org.slf4j.MDC.setContextMap(captured);
            return action.apply(value);
        } finally {
            if (previous == null) org.slf4j.MDC.clear();
            else org.slf4j.MDC.setContextMap(previous);
        }
    };
}
~~~

Captured cần được chụp ở nơi có context đúng, không lấy từ worker sau khi đã chuyển thread.

## 11. Executor decorator

Một điểm propagation tập trung giảm rủi ro quên wrap task:

~~~java
import java.util.concurrent.Executor;

public final class MdcExecutor implements Executor {
    private final Executor delegate;

    public MdcExecutor(Executor delegate) {
        this.delegate = delegate;
    }

    @Override
    public void execute(Runnable action) {
        delegate.execute(MdcWrappers.withMdc(action));
    }
}
~~~

Đây là lớp thành phần phụ thuộc MdcWrappers. Nó capture MDC khi client gọi **execute(...)** trên decorator.

**Executor khác ExecutorService:** MdcExecutor trên không có **submit, invokeAll, shutdown**. Muốn dùng toàn bộ ExecutorService phải decorate các overload liên quan hoặc chọn thư viện/framework đã được hỗ trợ. Không mặc định mọi lời gọi submit qua một wrapper chỉ implements Executor.

Một policy tốt cần định rõ **những executor nào được dùng cho request tasks** và bảo đảm các caller không bypass decorator mà không có lý do.

## 12. ScheduledExecutorService và job lặp

**One-shot scheduled task** của một request có thể cần giữ requestId ở thời điểm schedule, kể cả nếu thực thi sau khi HTTP response đã trả.

**Recurring job** thì khác: nếu scheduleAtFixedRate được gọi dưới request A rồi snapshot req-A được giữ mãi, mọi lần chạy có thể mang **req-A** dù không còn thuộc yêu cầu đó.

~~~text
Request req-A đăng ký recurring job
  |
  +--> run 1: requestId=req-A ?
  +--> run 2: requestId=req-A ?
  +--> run 3: requestId=req-A ?
~~~

Nếu job độc lập, hãy tạo **jobRunId** riêng theo mỗi lần chạy, có thể giữ **submittedBy** theo policy audit nhưng không tái sử dụng requestId như correlation ID của các run mới.

**Phân biệt:** propagation cho one-shot task gắn với request và context cho recurring background job phải theo semantics của công việc, không chỉ API scheduling.

## 13. Spring @Async và TaskDecorator

Trong Spring, **ThreadPoolTaskExecutor.setTaskDecorator(...)** có thể cài MDC propagation cho task đi qua executor ấy:

~~~java
executor.setTaskDecorator(task -> {
    Map<String, String> caller = MDC.getCopyOfContextMap();

    return () -> {
        Map<String, String> previous = MDC.getCopyOfContextMap();
        try {
            if (caller == null) MDC.clear();
            else MDC.setContextMap(caller);
            task.run();
        } finally {
            if (previous == null) MDC.clear();
            else MDC.setContextMap(previous);
        }
    };
});
~~~

Đây là **snippet**, cần Spring Framework/SLF4J và biến executor là ThreadPoolTaskExecutor. Nó không là ví dụ chạy độc lập.

Những điều phải xác minh:

1. **@Async** thực sự dùng executor đã gắn TaskDecorator, không phải một bean khác.
2. TaskDecorator có thể nhận Runnable đã được framework wrap, đặc biệt với Future.
3. Lỗi từ task submit bằng Future có thể được giữ trong Future, không xuất trực tiếp qua decorator.
4. Scheduler/reactive pipelines hoặc executors khác có thể không đi qua decorator này.
5. Nếu framework đã có context-propagation/tracing instrumentation, tránh hai lớp wrapper cài/restore MDC xung đột.

Không mặc định ThreadLocal tương thích mọi reactive thread hop; với Reactor/WebFlux cần cơ chế context của framework và instrumentation được kiểm thử.

## 14. Request boundary và nested MDC scopes

Trong service HTTP, thường có:

~~~text
HTTP Filter/Interceptor:
   validate/create requestId
   MDC.put(requestId)
         |
         v
   Controller / Service
         |
         +--> Executor task (capture snapshot tại đây)
         |
         v
   finally dọn context trên HTTP thread
~~~

Mẫu scope:

~~~java
try (MDC.MDCCloseable ignored =
        MDC.putCloseable("requestId", requestId)) {
    service.process(orderId);
}
~~~

Đây là snippet. **putCloseable** remove key khi close, kể cả exception. Nếu cần nhiều key như traceId/jobId, phải quản lý từng field hoặc save/restore cả Map.

**Nested case:** nếu outer scope có requestId=outer, inner scope dùng putCloseable requestId=inner, sau close requestId có thể bị remove thay vì restore outer. Nếu muốn nested scope, lưu previous map hoặc previous value và restore trong finally.

**Không gọi MDC.clear() vô điều kiện ở một component chỉ sở hữu một key** khi còn outer context cần giữ. Ngược lại, một top-level request boundary sở hữu toàn bộ MDC có thể clear vào cuối theo contract.

**Thời điểm capture phải ở trước khi caller dọn MDC**. Sau khi scope đã đóng, getCopyOfContextMap có thể trả null dù task vẫn sắp được submit.

## 15. Cấu hình Logback hiển thị MDC

Để thấy field MDC trong log, backend phải đưa nó vào layout/encoder. Ví dụ:

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<configuration>
    <appender name="STDOUT"
              class="ch.qos.logback.core.ConsoleAppender">
        <target>System.out</target>
        <encoder>
            <pattern>%d{yyyy-MM-dd HH:mm:ss.SSS} %-5level [%thread] requestId=%X{requestId:-none} %logger - %msg%n</pattern>
            <charset>UTF-8</charset>
        </encoder>
    </appender>

    <root level="INFO">
        <appender-ref ref="STDOUT"/>
    </root>
</configuration>
~~~

**%X{requestId:-none}** là MDC converter, có fallback khi giá trị không tồn tại. **%thread** hữu ích để quan sát reuse pool.

Nếu dùng JSON encoder, có thể muốn một LogEvent dạng:

~~~json
{
  "level": "INFO",
  "thread": "mdc-worker",
  "requestId": "req-A",
  "event": "job.started"
}
~~~

Đây chỉ là schema minh họa. Text pattern requestId=... không tự là structured JSON field. **Encoder và collector phải được cấu hình để lấy MDC** vào output ở đúng tên field.

**MDC khác event metadata:** requestId/traceId được tái sử dụng qua nhiều event; eventName, attempt, outcome của một lần xử lý thường nên gắn ở chính LogEvent thay vì đưa toàn bộ vào MDC.

## 16. Log4j 2 ThreadContext trong thread pool

Với **Log4j 2**, cơ chế tương tự là **ThreadContext Map** (MDC) và **ThreadContext Stack** (NDC). Tài liệu Log4j 2 hướng dẫn snapshot từ caller và cài trên worker.

~~~java
Map<String, String> map = ThreadContext.getImmutableContext();
List<String> stack =
        ThreadContext.getImmutableStack().asList();
~~~

Đây là snippet cần java.util.Map/List và org.apache.logging.log4j.ThreadContext.

Dùng CloseableThreadContext:

~~~java
executor.submit(() -> {
    try (CloseableThreadContext.Instance ignored =
            CloseableThreadContext.putAll(map).pushAll(stack)) {
        LOG.info("event=task.started");
    }
});
~~~

Đây là snippet, giả định executor/LOG/map/stack đã có và import CloseableThreadContext.

**Cẩn thận:** putAll thêm/ghi đè các entry, **không nhất thiết loại hết những key khác đã có trong worker**. Nếu yêu cầu worker chỉ có map của task hiện tại, cần lưu previous, clear/replace Map và restore trong finally. Với Stack/NDC phải có logic tương ứng riêng.

Ví dụ chỉ xử lý Map:

~~~java
Map<String, String> caller = ThreadContext.getImmutableContext();

executor.execute(() -> {
    Map<String, String> previous = ThreadContext.getImmutableContext();
    try {
        ThreadContext.clearMap();
        ThreadContext.putAll(caller);
        LOG.info("event=task.started");
    } finally {
        ThreadContext.clearMap();
        ThreadContext.putAll(previous);
    }
});
~~~

**Đừng nhầm SLF4J MDC và Log4j ThreadContext** là hai kho luôn tự đồng bộ; hành vi phụ thuộc binding/bridge. Chọn API logging nhất quán và test field trên output thực.

## 17. Async business task khác AsyncAppender

Hai đường xử lý khác nhau:

**Chuyển business task sang pool:**

~~~text
HTTP thread MDC=req-A
  | submit Runnable
  v
Executor worker (cần được install req-A)
  | LOG.info(...)
  v
LogEvent
~~~

**Chuyển công việc xuất log sang backend async:**

~~~text
Business worker MDC=req-A
  | LOG.info(...)
  v
LogEvent chứa context theo backend
  | queue
  v
Async logging writer
  | file/console/network
~~~

Backend logging hiện đại thường snapshot context vào LogEvent lúc lời gọi Logger được phát, còn writer xử lý sau. Nhưng behavior phụ thuộc backend, version và custom Appender.

**AsyncAppender không sửa được việc business worker thiếu MDC trước khi Logger tạo event.** Cài req-A trên logging writer cũng không đúng vì writer xử lý event từ nhiều request khác nhau.

Vì vậy cần test **propagation của business task** và **context retention của async logger** như hai chức năng độc lập.

## 18. MDC không tự đi qua HTTP hoặc message broker

MDC chỉ là **ngữ cảnh logging cục bộ**, không tự được truyền qua HTTP/gRPC/Kafka/RabbitMQ.

Muốn correlate giữa service A và B:

1. Định nghĩa traceId/requestId trong protocol hoặc chuẩn như **W3C Trace Context**.
2. Truyền qua header/message metadata.
3. Tại service đích, parse/validate dữ liệu và thiết lập context local.
4. Dọn context local khi request/job kết thúc.
5. Nếu service B lại dùng pool, tiếp tục propagate ở task boundary.
6. Kiểm tra các backend/encoders dùng cùng key schema.
7. Không dùng value MDC như một chứng cứ ủy quyền.

**MDC không tự tạo trace/span**. Nếu hệ thống đã có OpenTelemetry instrumentation, ưu tiên tích hợp context propagation của tracing system thay vì tự nhân bản header logic ở mọi service.

## 19. Exception, cancellation, shutdown và cleanup

| Tình huống | Yêu cầu |
| --- | --- |
| Task ném exception | Finally restore worker MDC |
| Callable ném checked exception | Future.get và xử lý ExecutionException |
| Worker bị interrupt | Cleanup trong finally; giữ interrupt policy đúng |
| Future.cancel(true) | Đảm bảo cleanup nếu task đã bắt đầu |
| Executor từ chối task | Xử lý RejectedExecutionException |
| Queue chờ lâu | Snapshot phải lấy trước submit, không đọc caller sau |
| Scheduled task lặp lại | Context mới theo run |
| Pool shutdown | Chờ task cần thiết và flush logging backend đúng cách |
| Async logger chậm | Kiểm soát queue/drop/flush riêng |
| Thread factory đổi | Per-task propagation vẫn phải đúng |

**Không được swallow exception chỉ để cleanup.** Wrapper phải khôi phục state rồi cho lỗi tiếp tục đi theo Executor/Future.

Trong code production cần **timeout, cancellation và awaitTermination** theo chính sách; ví dụ Maven dùng Future.get cho ba task để bảo đảm test có thứ tự, không phải chiến lược shutdown cho mọi dịch vụ.

## 20. Cách kiểm thử leakage và propagation

Một test đáng tin nên chạy **nhiều task nối tiếp trên một worker**:

1. req-A → wrapped task → assert log có req-A.
2. req-B → wrapped task → assert log có req-B.
3. Caller không có context → wrapped probe → assert MDC.get("requestId") null.
4. Task trong wrapper cố ý ném exception → probe sau đó vẫn không có context cũ.
5. Có nested context trên worker → sau task restore đúng previous.
6. MDC có hai key requestId/traceId → cả hai được propagate đúng.
7. Thử CompletableFuture stage mới → có propagation riêng.
8. Thử scheduled job → không giữ context đã hết hạn.
9. Chạy nhiều worker và nhiều request → từng log gắn đúng ID, không cần có global ordering.
10. Test backend thật xuất %X/JSON field, không chỉ MDC.get trong Java.
11. Test caller scope được clear trong finally kể cả khi request lỗi.
12. Kiểm tra với Future.get/CountDownLatch thay vì Thread.sleep để tránh flaky test.

Ví dụ snippet task lỗi:

~~~java
Future<?> failure = pool.submit(withMdc(() -> {
    LOG.info("event=will.fail");
    throw new IllegalStateException("simulated failure");
}));

try {
    failure.get();
} catch (ExecutionException expected) {
    // Task cố ý thất bại trong test.
}
~~~

Snippet giả định có pool/withMdc/LOG và import Future/ExecutionException. Sau đó cần submit **probe** không có MDC để khẳng định cleanup thực sự xảy ra.

**Không suy ra propagation đúng chỉ vì log xuất trên terminal.** Test phải kiểm tra **requestId được lấy từ MDC**, không phải nối tay vào message.

## 21. Bảo mật và hiệu năng

MDC nên nhỏ, có schema ổn định và chỉ chứa dữ liệu cần thiết cho chẩn đoán:

- Không đặt **password, token, API key, session cookie, Authorization header, dữ liệu thẻ** trong MDC.
- Không dùng **tenantId/requestId trong MDC** thay cho security context đáng tin cậy.
- Context leakage có thể làm log của tenant B bị gắn nhầm ID tenant A.
- Validate/giới hạn độ dài requestId từ client, escape newline/control characters để giảm **log injection**.
- Không biến giá trị requestId thành **tên key** gây bùng nổ schema.
- Thiết lập **retention** và quyền truy cập phù hợp tại file, console collector, dashboard, backup.
- Dùng **getCopyOfContextMap** có chi phí allocation; giữ context Map nhỏ thay vì cả request object.
- Queue dài có thể giữ nhiều snapshot MDC trong bộ nhớ; giới hạn backlog.
- Đừng bỏ cleanup để tối ưu tốc độ; đo CPU, p95/p99 latency và memory trong workload thật.
- Async logging có thể chụp context thêm một lần vào LogEvent, nhưng thường cần để giữ đúng metadata ở writer.

**Rò MDC không chỉ gây log xấu**. Nó làm sai tính tương quan của sự kiện và có thể ảnh hưởng bảo mật khi hệ log phân vùng quyền truy vấn theo trường tenant/request.

## 22. Troubleshooting theo triệu chứng

| Hiện tượng | Nguyên nhân có thể | Cách xử lý |
| --- | --- | --- |
| Caller có req-A nhưng worker none | Thiếu capture/install | Wrap trước submit |
| Worker B có req-A | Task A không dọn MDC | Finally restore |
| Có lúc đúng, có lúc sai | Dựa vào pool thread creation/inheritance | Per-task propagation |
| Exception xong log sau sai ID | Cleanup không nằm trong finally | Bọc toàn bộ task |
| Nested task làm mất batchId | Clear thay vì restore | Lưu previous map |
| putCloseable làm mất ID của outer scope | Closeable remove, không restore | Scope save/restore |
| CompletableFuture stage sau thiếu ID | Stage đổi thread | Propagate từng boundary |
| Scheduled recurring job dùng ID cũ | Snapshot request bị giữ lâu | JobRunId từng run |
| Logback không in requestId | Pattern thiếu %X/encoder thiếu MDC | Sửa layout |
| SLF4J gọi MDC.put nhưng backend không thấy | Provider/bridge không hỗ trợ đúng | Kiểm tra runtime |
| Log4j ThreadContext không hiện | API/bridge không khớp | Dùng một stack nhất quán |
| @Async thiếu context | Chạy trên executor không có decorator | Kiểm tra executor bean |
| Probe sau task không clean | Wrapper bị bypass hoặc worker đã nhiễm | Kiểm tra mọi submission path |
| Log sai tenant | Rò context hoặc ID input không tin cậy | Cleanup, validate và audit |
| Future lỗi nhưng caller không biết | Không gọi get/handle | Xử lý kết quả/lỗi |
| Context snapshot trống | Capture sau khi caller đã clear | Capture đúng submission time |

**Thứ tự chẩn đoán:** xác định provider/backend → MDC trên caller → nơi capture → task có qua wrapper không → worker install/restore → layout/encoder → collector và test thread reuse.

## 23. Các lỗi thiết kế thường gặp

**1. Tưởng MDC theo request.** Nó thường theo thread và cần propagation khi chuyển task.

**2. Dùng InheritableThreadLocal cho thread pool.** Nó không đồng nghĩa task-level context.

**3. Capture bên trong worker.** Quá muộn, có thể lấy context sai.

**4. Không finally.** Task lỗi khiến worker bị nhiễm.

**5. Chỉ clear sau nested task.** Có thể xóa context hợp lệ trước đó của worker.

**6. Chỉ remove requestId.** Những field khác như traceId có thể vẫn còn.

**7. Nghĩ putCloseable tự restore previous key.** Nó remove key khi đóng.

**8. Wrap stage đầu rồi bỏ stage sau.** CompletableFuture có thể chuyển thread nhiều lần.

**9. Dùng AsyncAppender để sửa business context.** Context đã mất trước khi LogEvent được tạo thì writer không tự tìm lại được.

**10. Giữ req-A trên recurring job.** Mỗi execution có thể thuộc một context khác.

**11. Không test A → B → none.** Không phát hiện stale context của worker.

**12. Chỉ in requestId trong message.** Điều đó không chứng minh MDC propagation hoạt động.

**13. Dùng MDC làm security principal.** Đây chỉ là metadata quan sát.

**14. Trộn provider/bridge không tương thích.** Code có thể chạy nhưng field MDC mất.

## 24. Checklist triển khai MDC trong thread pool

1. **Chọn một logging provider thực tế**, cấu hình layout/JSON encoder lấy MDC.
2. **Định nghĩa key schema**: requestId, traceId, spanId, jobId.
3. **Đặt MDC ở request/job boundary**, cleanup khi thoát scope.
4. **Capture bằng getCopyOfContextMap trước submit**.
5. **Install trên worker trước khi Logger phát event**.
6. **Restore previous trong finally**, kể cả exception/interrupt.
7. **Hỗ trợ Runnable và Callable**, không bỏ sót những đường submit.
8. **Dùng Executor/TaskDecorator tập trung** khi có nhiều tác vụ.
9. **Propagate mọi CompletableFuture async boundary** hoặc dùng framework hỗ trợ.
10. **Tạo context riêng cho recurring job**, không giữ requestId cũ.
11. **Không dựa vào InheritableThreadLocal hoặc tên worker**.
12. **Phân biệt business async task và async logging backend**.
13. **Truyền correlation qua network bằng protocol**, không chỉ MDC.
14. **Test một worker chạy A → B → none**, và test exception/nested scope.
15. **Kiểm tra output thật** với Logback/Log4j2/collector.
16. **Tránh secret/PII**, validate ID và quy định retention.
17. **Giữ MDC nhỏ**, quan sát chi phí snapshot, queue và latency.

**Kết luận:** Với thread pool, MDC **phải được truyền theo từng task**, không tự đi theo Runnable chỉ vì task được submit từ HTTP thread. Mẫu thiết kế an toàn là **capture tại caller → install trên worker → chạy task → restore trong finally**. Khi kết hợp cleanup đúng scope, cấu hình encoder đọc MDC và test thread reuse, các bản ghi có thể được gắn requestId/traceId chính xác mà không rò ngữ cảnh giữa những request.
