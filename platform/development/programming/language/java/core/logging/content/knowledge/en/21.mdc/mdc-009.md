# MDC and Structured Logging in Java

## 1. Why Combine MDC with Structured Logging?

A Java application can handle thousands of HTTP requests, background tasks, messages, and transactions concurrently. When every component logs with a per-class logger, operators need to find the records belonging to **the same execution** without relying on reading free-form message strings.

**MDC (Mapped Diagnostic Context)** is an API that stores a set of **string key–value pairs** as diagnostic context, such as `request_id`, `correlation_id`, and `tenant_id`. The logging framework can attach these context values to events created on the corresponding thread.

**Structured logging** is the practice of representing an event as **explicitly named and typed fields**, typically JSON, so that fields can be parsed independently by collectors and search systems.

The two concepts are related but **not synonymous**:

- **MDC provides context** across multiple log calls within the same scope.
- **Structured logging provides the format/schema** so an event is machine-parseable.
- **The Encoder/Layout/Provider determines whether MDC is emitted to JSON**, whether it sits at the root or in a nested object, and which keys are retained.
- **The Collector determines parsing/mapping** so fields can be searched, filtered, and aggregated in the storage backend.

Example of the same business event:

```java
LOG.info("event=order_created order_id={}", orderId);
```

If the request has no MDC, text output might only be:

```text
INFO event=order_created order_id=ORD-101
```

If the application sets MDC and the backend emits it, a JSON representation might be:

```json
{
  "timestamp": "2026-11-09T12:00:00Z",
  "level": "INFO",
  "logger": "order-service",
  "request_id": "req-17",
  "tenant_id": "tenant-A",
  "event": "order_created",
  "order_id": "ORD-101"
}
```

This is an **illustrative application-defined schema**. There is **no** single `MDC.put(...)` call that guarantees every backend will automatically emit this exact JSON.

**Key takeaway:** repeated request/tenant/trace data should be managed as **scoped context**; data belonging to **a single event** should preferably be attached to the LogEvent as its own attributes rather than putting everything into MDC.

## 2. The Path from MDC to the Log Search System

```text
HTTP request / Message / Job
          |
          v
  Identify trusted context
  request_id, tenant_id, trace_id
          |
          v
  Scoped MDC / ThreadContext
          |
          +-----------+-----------+
          |           |           |
          v           v           v
    LOG.info(...) LOG.warn(...) LOG.error(...)
          |           |           |
          +-----------+-----------+
                      |
                      v
                Logging event
             level, time, message,
            throwable, mdc, kv pairs
                      |
                      v
             Backend / Encoder
           (Pattern / JSON template)
                      |
                +-----+-----+
                |           |
                v           v
             Text line    JSON object
                |           |
                +-----+-----+
                      |
                      v
              stdout/file/socket
                      |
                      v
             Agent / Collector
            decode / parse / map
                      |
                      v
              Index / Log query
```

Each step can lose or alter information:

1. **MDC is not set at the right time:** the LogEvent lacks `request_id`.
2. **MDC does not cross to a new thread:** an async task's events lack context or carry another request's context.
3. **Encoder does not include MDC in the output:** the logger writes successfully, but the JSON file only contains `message`.
4. **Encoder formats MDC as text:** the collector does not automatically have a `request_id` field without parsing.
5. **Collector does not parse JSON:** the entire object is stored under a single `log` or `message` field.
6. **Schema mismatch:** the dashboard queries `request.id` while the JSON contains `request_id`.
7. **Pipeline filtering or data loss:** an event may not appear due to sampling, queue drops, retention, or transport errors.

Therefore, you must verify **end-to-end**, rather than concluding everything works just because `MDC.get("request_id")` returns a value.

## 3. What Should and Should Not Be Stored in MDC?

Commonly valuable keys:

| MDC key | Meaning | When to set? |
| --- | --- | --- |
| `request_id` | ID of a single request in the current service | When request processing begins |
| `correlation_id` | ID linking multiple steps/services of a flow | After verifying or generating at a trusted boundary |
| `trace_id` | Trace identifier used to correlate with tracing | When the tracing context is available |
| `span_id` | Span identifier if needed | Within the appropriate span scope |
| `tenant_id` | Resolved/authorized tenant | After verifying tenant authorization |
| `job_id` | A single job execution | Within the job scope |
| `message_id` | A consumed message | While processing the message |
| `operation` | Stable operation group | When it describes the entire scope |
| `attempt` | Attempt number | Only if it genuinely belongs to a specific retry scope |

**Do not put in MDC**: passwords, access tokens, API keys, session cookies, OTPs, card data, objects containing PII, full HTTP requests/responses, stack traces, large bodies, or values with arbitrary user-defined key counts.

**MDC is a `Map<String, String>` according to the SLF4J API**, so `MDC.put("duration_ms", "1500")` stores the **string** value `"1500"`. A JSON encoder will normally emit:

```json
{"duration_ms":"1500"}
```

instead of:

```json
{"duration_ms":1500}
```

The second case has the JSON **number** type; this only happens when the encoder/transform is configured to convert types appropriately or when the data is attached to the event via an API that supports numeric types.

Therefore:

- **Scoped context:** `request_id`, `tenant_id`, `trace_id`.
- **Single-event attributes:** `duration_ms`, `http_status`, `retry_count`, `bytes_sent` should be **typed event attributes/key-value pairs** when supported by the backend.
- **Message:** human-readable description, but not the sole data source for dashboards.

Do not turn the logger name into `logger.getLogger("order-" + orderId)`. Logger names should represent code origin; dynamic IDs are event data.

## 4. MDC in SLF4J, Logback, Log4j2, and JUL

Java has multiple APIs and backends. You need to know exactly which component owns MDC and which component serializes it:

| System | Context API | How it enters output? | Notes |
| --- | --- | --- | --- |
| **SLF4J 2.x** | `org.slf4j.MDC` | Depends on the actual provider/encoder | SLF4J is a facade; it does not produce JSON by default |
| **Logback Classic** | `org.slf4j.MDC` | Pattern `%X{key}` or JSON encoder with MDC provider | Commonly used in SLF4J applications |
| **Log4j2** | `org.apache.logging.log4j.ThreadContext` | `PatternLayout` with `%X{key}` or `JsonTemplateLayout` with `mdc` resolver | Log4j2 calls it the Thread Context Map |
| **JUL** | No standard MDC API in `java.util.logging.LogRecord` | Custom Handler/Formatter/adapter if needed | JUL `ConsoleHandler` writes to stderr by default |
| **SLF4J Simple / NOP** | SLF4J MDC API may be a NOP depending on adapter/provider | Should not be treated as a structured JSON MDC backend | Reading/writing the MDC API is no substitute for checking the adapter and output |

With SLF4J, `MDC.put` delegates to the provider's MDC adapter. Do not assume a system using `slf4j-simple` or NOP will produce the same output as Logback. If your application uses a framework with a built-in provider, check runtime dependencies before adding a new backend to avoid multiple providers or bridge loops.

**Switching backends is not just changing a config file.** It can change:

- Field names and placement (`mdc`, `contextMap`, `threadContext`).
- How `Throwable`, logger name, timestamp, and level are rendered.
- Which API/adapter writes MDC and when snapshots are taken.
- Support for SLF4J 2.x fluent `addKeyValue`.
- JSON types of individual fields and how missing values are handled.

## 5. Setting MDC with the Right Lifecycle

In an HTTP request:

```text
Request starts
  |
  v
Authenticate / verify metadata
  |
  v
Generate or validate request_id
  |
  v
Store scoped MDC
  |
  +-- Controller log
  +-- Service log
  +-- Repository log
  |
  v
Send response
  |
  v
Restore/clear MDC in finally
```

A common SLF4J pattern:

```java
String oldRequestId = MDC.get("request_id");
MDC.put("request_id", requestId);
try {
    handleRequest();
} finally {
    if (oldRequestId == null) {
        MDC.remove("request_id");
    } else {
        MDC.put("request_id", oldRequestId);
    }
}
```

This is a **snippet inside a class that imports `org.slf4j.MDC`** and has `requestId`/`handleRequest()`, not a standalone program.

Distinctions to keep in mind:

- If **the request boundary owns the entire MDC map**, resetting the whole map may make sense.
- If you are writing a **library**, do not call `MDC.clear()` indiscriminately: it can wipe `trace_id`, `tenant_id`, or data from an outer scope.
- For nested scopes sharing **the same key**, you must **restore the previous value**.
- `try/finally` ensures cleanup runs on early returns or exceptions (barring forced process termination).
- MDC is not an auth guarantee; only set a `tenant_id` that has been verified at the business/security layer.

### How Does `MDC.putCloseable` Behave?

SLF4J provides:

```java
try (MDC.MDCCloseable ignored =
             MDC.putCloseable("request_id", requestId)) {
    LOG.info("event=request_started");
}
```

This uses `try-with-resources` to **remove the `request_id` key on close**. According to the Javadoc, `MDCCloseable.close()` **removes the key**; it does not automatically restore a previous value for that same key. It is therefore suitable when you **own the key in the current scope** and do not need nested restoration. If scope A has `request_id=A` and nested scope B sets `request_id=B` via `putCloseable`, closing B can cause A to lose the key. In libraries that support nested scopes, the save-and-restore pattern is safer.

## 6. Complete Java 17+ Example: MDC Across Two Requests and a Thread Pool

This example uses **SLF4J API 2.x + Logback Classic** to demonstrate:

1. `MDC.put` sets `request_id` and `tenant_id` for a request.
2. Multiple logger calls receive the same context fields.
3. A thread pool **does not inherit MDC by default**; context must be captured on submission and set inside the worker.
4. The pool has a single worker thread so it is reused for **two requests belonging to two different tenants**.
5. Context is **restored/cleared in `finally`**, preventing the second request from carrying the first request's data.
6. A pattern encoder prints context as text for easy verification. A separate section later switches to a JSON encoder.

Versions in this article are pinned for reproducibility and **do not claim to be the latest releases**. Real projects should align dependencies and apply appropriate patches.

Directory layout:

```text
mdc-structured-demo/
├── pom.xml
└── src/
    └── main/
        ├── java/
        │   └── example/
        │       └── logging/
        │           └── MdcStructuredDemo.java
        └── resources/
            └── logback.xml
```

### 6.2. `src/main/resources/logback.xml`

```xml
<configuration>
    <appender name="STDOUT"
              class="ch.qos.logback.core.ConsoleAppender">
        <target>System.out</target>
        <encoder>
            <charset>UTF-8</charset>
            <pattern>%level request_id=%X{request_id} tenant_id=%X{tenant_id} %logger - %msg%n</pattern>
        </encoder>
    </appender>

    <root level="INFO">
        <appender-ref ref="STDOUT"/>
    </root>
</configuration>
```

This is a **Logback** configuration, not `log4j2.xml`. The converters:

- `%level`: log level (e.g., `INFO`).
- `%X{request_id}` and `%X{tenant_id}`: read MDC data from the LogEvent.
- `%logger`: logger name; in the example code this is the fixed name `demo`.
- `%msg`: message after `{}` parameter substitution.
- `%n`: newline separating events.

`ConsoleAppender` writes to **System.out** so stdout and stderr can be inspected separately. The pattern omits a timestamp to keep **the lesson's stdout deterministic**, which does not mean production should omit timestamps.

### 6.3. `src/main/java/example/logging/MdcStructuredDemo.java`

```java
package example.logging;

import java.util.Map;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;

public final class MdcStructuredDemo {
    private static final Logger LOG =
            LoggerFactory.getLogger("demo");

    private MdcStructuredDemo() {
    }

    private static final class ContextScope
            implements AutoCloseable {
        private final Map<String, String> previous;

        private ContextScope(String requestId, String tenantId) {
            previous = MDC.getCopyOfContextMap();
            MDC.put("request_id", requestId);
            MDC.put("tenant_id", tenantId);
        }

        @Override
        public void close() {
            if (previous == null) {
                MDC.clear();
            } else {
                MDC.setContextMap(previous);
            }
        }
    }

    private static void process(
            ExecutorService pool, String requestId,
            String tenantId, String orderId) throws Exception {

        try (ContextScope ignored =
                     new ContextScope(requestId, tenantId)) {

            LOG.info("event=order_received order_id={}", orderId);

            // Capture context on the thread currently handling the request.
            Map<String, String> captured =
                    MDC.getCopyOfContextMap();

            Future<?> result = pool.submit(() -> {
                Map<String, String> oldWorker =
                        MDC.getCopyOfContextMap();
                try {
                    // captured is non-null in this example.
                    MDC.setContextMap(captured);
                    LOG.info("event=order_confirmed order_id={}",
                            orderId);
                } finally {
                    // Prevent task A's context from leaking to task B.
                    if (oldWorker == null) {
                        MDC.clear();
                    } else {
                        MDC.setContextMap(oldWorker);
                    }
                }
            });

            // Wait so output ordering between the two requests is deterministic.
            result.get();
        }
    }

    public static void main(String[] args) throws Exception {
        MDC.clear();

        ExecutorService pool =
                Executors.newSingleThreadExecutor();

        try {
            process(pool, "req-101", "tenant-A", "ORD-101");
            process(pool, "req-102", "tenant-B", "ORD-102");
        } finally {
            pool.shutdown();
            MDC.clear();
        }
    }
}
```

This is a **standalone program with `main`**, requiring the Maven dependencies above. It does not connect to a database or HTTP server; it simply simulates two requests and a thread pool.

### 6.5. Why Is This a Meaningful Test?

- Both requests run **sequentially** on the main thread, yet both use **the exact same worker** in the pool.
- When emitting events in request A, MDC holds `req-101`/`tenant-A`.
- The `captured` snapshot is taken **before submitting the task**.
- The worker applies the snapshot to **its own worker thread's** MDC before calling `LOG.info`.
- When the task finishes or throws an exception, `finally` restores the worker's previous MDC.
- `Future.get()` ensures the first task completes before the second request begins.
- The request scope also restores the previous map even if processing fails.
- The program does not rely on automatic `ThreadLocal` inheritance and does not store the tenant ID in a `static` field.
- `%X{key}` prints MDC as text; this is **context verification**, not yet JSON structured logging.

If you omit `MDC.setContextMap(captured)` in the worker, the worker's LogEvent may lack the request ID/tenant ID. If you omit cleanup in the worker, task B may inherit stale context in code paths that do not overwrite every key.

**Do not use MDC as a security principal.** The tenant IDs in this example are simulated data assumed to be valid. In a real application, the tenant must be resolved and authorized before being placed into context.

## 7. From PatternLayout to JSON: Differences in Output

The configuration in Section 6:

```text
INFO request_id=req-101 tenant_id=tenant-A demo - event=order_received order_id=ORD-101
```

is just **text**, even though it contains key-value pairs. A collector may need a parser to split out each token if you want to query the `request_id` field.

An ideal structured JSON event:

```json
{
  "timestamp": "2026-11-09T12:00:00Z",
  "level": "INFO",
  "logger": "demo",
  "message": "Order received",
  "request_id": "req-101",
  "tenant_id": "tenant-A",
  "event": "order_received",
  "order_id": "ORD-101",
  "duration_ms": 25
}
```

This is an **illustrative system-defined schema**, not actual JSON automatically generated by the Logback `PatternLayout` in Section 6.

To achieve this, you need:

1. A **JSON encoder/layout** instead of a text pattern.
2. The encoder to emit `request_id`/`tenant_id` from MDC into JSON.
3. `event`/`order_id` added as **event fields** (or extracted by the collector from the message, if necessary).
4. `duration_ms` preserved as a **number**, not coerced to a string.
5. Timestamp, severity, logger, and exception serialized according to the agreed schema.
6. The collector to understand **one event per line** and parse fields at the expected paths.

**The core shift:** MDC does not "become structured" merely because code stores key-value pairs; the encoder's output and the ingestion pipeline determine whether data is structured.

## 8. Logback Example with a JSON Encoder Including MDC

Logback Classic ships with a text encoder by default, but you can use a JSON encoder library such as **`logstash-logback-encoder`**. This library is an add-on, not part of `slf4j-api`.

To use it, the project must add the encoder dependency at a **version compatible with the project's Logback/JDK**; do not copy an arbitrary version from an old example when your organization has dependency management. The following configuration is an **appender snippet** using that encoder:

```xml
<appender name="JSON_STDOUT"
          class="ch.qos.logback.core.ConsoleAppender">
    <target>System.out</target>
    <encoder class="net.logstash.logback.encoder.LogstashEncoder">
        <includeMdc>true</includeMdc>
        <includeMdcKeyName>request_id</includeMdcKeyName>
        <includeMdcKeyName>tenant_id</includeMdcKeyName>
    </encoder>
</appender>
```

This is **not a complete `logback.xml`**. To use it, attach `<appender-ref ref="JSON_STDOUT"/>` to the root/logger and remove the text `STDOUT` appender if you do not want each event emitted twice.

Per the `logstash-logback-encoder` documentation:

- `LogstashEncoder` can include MDC entries in JSON. When `includeMdcKeyName` is specified, only the listed MDC keys are emitted.
- Without restricting keys, the encoder can emit the **entire MDC**, which is risky if MDC contains data that should not be collected.
- MDC values are **strings** by default; `MdcEntryWriter` implementations exist for type conversion, but they should be scoped to specific fields and schema-tested.
- The encoder can support SLF4J 2.x per-event **key-value pairs** depending on configuration.
- The encoder's default standard field names (such as `@timestamp`, `message`, `logger_name`) differ from the illustrative `timestamp`/`logger` schema above.

A JSON output **illustrating the shape**, without claiming exact key ordering or appender timestamp:

```json
{"@timestamp":"2026-11-09T12:00:00Z","level":"INFO","logger_name":"demo","message":"event=order_received order_id=ORD-101","request_id":"req-101","tenant_id":"tenant-A"}
```

To get typed event fields instead of parsing `event=...` from the message, you can use the fluent logging API in Section 10 together with an encoder that actually supports it. When switching the Section 6 demo to JSON, **stdout will differ** from the four text lines shown in Section 6; do not use both configurations simultaneously and expect a single fixed output.

### Version Note

`logstash-logback-encoder` is maintained independently, and different versions may require different **minimum Java levels or Jackson versions**. Before adding the artifact to a Java 17 project, check the official compatibility matrix; do not assume every encoder version runs on Java 17. The snippet above illustrates **how the configuration works**, not a full runnable Maven project.

Source: https://github.com/logfellow/logstash-logback-encoder

## 9. Log4j2: `ThreadContext` and `JsonTemplateLayout`

In Log4j2, the equivalent of MDC is the **Thread Context Map**, manipulated via `org.apache.logging.log4j.ThreadContext`:

```java
import org.apache.logging.log4j.ThreadContext;

String previous = ThreadContext.get("request_id");
ThreadContext.put("request_id", requestId);
try {
    LOG.info("event=order_received order_id={}", orderId);
} finally {
    if (previous == null) {
        ThreadContext.remove("request_id");
    } else {
        ThreadContext.put("request_id", previous);
    }
}
```

This is a snippet inside a class using the **Log4j2 API**, not a standalone program.

### PatternLayout

If you only need text:

```xml
<PatternLayout charset="UTF-8"
    pattern="%p request_id=%X{request_id} tenant_id=%X{tenant_id} - %m%n"/>
```

The `%X{key}` converter reads fields from the LogEvent's ThreadContext Map. This configuration lives inside an Appender; it **does not automatically become JSON**.

### JsonTemplateLayout

Log4j2 provides **`JsonTemplateLayout`** using templates and resolvers; it requires the `org.apache.logging.log4j:log4j-layout-template-json` artifact at a version compatible with `log4j-api`/`log4j-core`.

Example Appender:

```xml
<Console name="JSON" target="SYSTEM_OUT">
    <JsonTemplateLayout
        eventTemplateUri="classpath:MdcEvent.json"/>
</Console>
```

This snippet goes inside `<Appenders>` in `log4j2.xml`. You must also reference it via `AppenderRef` in root/logger and place `MdcEvent.json` on the classpath, e.g., `src/main/resources/MdcEvent.json`.

**Minimal** template content:

```json
{
  "level": {
    "$resolver": "level",
    "field": "name"
  },
  "message": {
    "$resolver": "message",
    "stringified": true
  },
  "request_id": {
    "$resolver": "mdc",
    "key": "request_id"
  },
  "tenant_id": {
    "$resolver": "mdc",
    "key": "tenant_id"
  }
}
```

These resolvers are supported by Log4j2: `level`, `message`, and `mdc` with `key`. This template **selects only four fields**; it does not automatically include timestamps, exceptions, thread names, or other event fields. For production use, add resolvers matching your schema, verify type/missing-value behavior, and ensure the collector parser understands the format.

**Do not confuse Log4j2 `ThreadContext` and SLF4J `MDC` as two separate stores that are always synchronized.** When SLF4J runs through a properly configured Log4j2 provider, the adapter routes to the underlying backend; if the runtime selects a different backend, behavior can differ. Avoid bridge loops and use a single intentional logging stack.

Documentation: https://logging.apache.org/log4j/2.x/manual/thread-context.html and https://logging.apache.org/log4j/2.x/manual/json-template-layout.html

## 10. MDC vs. Per-Event Key-Value Pairs

SLF4J 2.x offers a fluent logging API:

```java
LOG.atInfo()
        .addKeyValue("event", "order_created")
        .addKeyValue("order_id", orderId)
        .addKeyValue("duration_ms", durationMs)
        .log("Order created");
```

This is an illustrative snippet in a class with `LOG` of type `org.slf4j.Logger`, `orderId`, and `durationMs`. `addKeyValue` accepts an `Object`, so `durationMs` can be an integer/long in the event, unlike `MDC.put` which only stores strings.

**What should you use?**

| Data | Recommended mechanism | Why? |
| --- | --- | --- |
| `request_id` present across many events in a request | MDC | Avoids passing the ID in every logger call |
| Verified `tenant_id` in scope | MDC | Shared context for the request/message/job |
| `trace_id` and `span_id` for the scope | MDC or tracing/backend integration | Correlates logs and traces with lifecycle management |
| `order_id` for a single event | Per-event key-value | Scoped to that event, avoiding leaks to other operations |
| Numeric `duration_ms` | Per-event typed key-value | Preserves numeric type for aggregations |
| Numeric `http_status` | Per-event typed key-value | Preserves exact type |
| `reason_code` of an outcome | Per-event field | Helps group outcomes |
| Descriptive `message` | Message template + parameters | Readable and consistently formatted |
| `Throwable` | Event cause | Preserves stack trace/cause chain |

**Important note:** fluent `addKeyValue` **does not guarantee JSON fields will appear** if the provider/encoder does not support key-value serialization. With the text `PatternLayout` in Section 6, key-value pairs may not be printed at all because the pattern only includes `%msg`. With a compatible JSON encoder, they can become fields.

MDC and per-event fields can share the same key name—for example, both containing `order_id`. When that happens, the backend might emit duplicate JSON keys, nest objects, or apply a precedence rule. **Define ownership rules**: which keys belong to MDC, which belong to the event, and which are added by the collector. Avoid having two sources write the same root field independently.

## 11. Why MDC Values Are Strings and How to Preserve Types

`MDC.put("attempt", "2")` may look convenient, yet typical output:

```json
{"attempt":"2"}
```

differs from:

```json
{"attempt":2}
```

Both are valid JSON, but the field types differ:

- String `"2"` is appropriate if it is an **identifier**, such as an account code with leading zeros.
- Number `2` is appropriate if you want to **compute** on it, such as an attempt count.
- Boolean `true` is appropriate for a binary flag; the string `"true"` is not equivalent to a boolean.
- Timestamps require an explicit contract: RFC 3339 string or epoch milliseconds/nanoseconds.

**Do not blindly "auto-guess types for every MDC field."** A tenant ID like `"00123"` must keep its leading zeros rather than being converted to the number `123`. If using LogstashEncoder's `MdcEntryWriter`, only convert predefined fields and back them with schema tests.

Sensible rules:

1. Reserve MDC for **string identifiers**.
2. Use per-event typed fields for `duration_ms`, `retry_count`, `success`.
3. Align names/types in the encoder before data reaches the collector.
4. In the collector, do not automatically convert every numeric-looking value to a number if it could corrupt identifiers.
5. Schema tests should verify both **field values and data types**.

## 12. JSON Lines and Collectors: "MDC Emitted" Is Not the Finish Line

Container log collectors typically read **stdout/stderr** and expect **one event per line**. With JSON Lines (NDJSON), each LogEvent generally needs to be **one complete JSON object on a single UTF-8 line**, terminated by a newline.

Example:

```json
{"level":"INFO","request_id":"req-101","tenant_id":"tenant-A","message":"Order received"}
{"level":"INFO","request_id":"req-102","tenant_id":"tenant-B","message":"Order received"}
```

Do not confuse this with a multi-line pretty-printed JSON object:

```json
{
  "level": "INFO",
  "request_id": "req-101"
}
```

That is valid JSON if read as a whole block, but a line-framed collector may treat each line as a separate event and fail to parse it.

Pipeline checklist:

- **One event per line**, unless the collector is configured for multiline.
- **Proper escaping** for newlines, quotes, backslashes, control characters, and stack traces.
- **MDC fields emitted** under the expected names/paths.
- **Timestamp** with explicit timezone/unit, not unintentionally replaced by the collector's ingest time.
- **Severity** mapped from SLF4J/Logback/Log4j2 to the target schema.
- **Collector parses JSON**, rather than leaving the entire line under a raw `log` field.
- **No duplicate sources** if both writing to stdout and writing to a file scraped by an agent.
- **No silent data loss** from queues, filters, size limits, sampling, or retention.
- **Security** for transport, data at rest, and log-store access control.

A log can have valid MDC on stdout and still fail to match `request_id` queries on a dashboard if the collector only indexes `message`. Always test **queries against the actual field**.

## 13. Context Propagation: Thread Pools Are a Major Risk

Across many providers, MDC is bound to the **current thread** or an equivalent mechanism. A task submitted to an `ExecutorService` runs on another thread and must not be assumed to inherit MDC automatically.

Two failure modes:

**Lost context:**

```text
HTTP thread: MDC.request_id=req-101
    |
    +--> executor.submit(task)
                 |
                 v
          worker thread: MDC.request_id is empty
```

**Context leakage on thread reuse:**

```text
Worker processes task tenant-A -> MDC.tenant_id=tenant-A remains
     |
     v
Worker processes task tenant-B -> context not set -> logs wrong tenant-A
```

The general solution is **capture → set → run → restore**:

```java
Map<String, String> captured = MDC.getCopyOfContextMap();

executor.submit(() -> {
    Map<String, String> oldWorker = MDC.getCopyOfContextMap();
    try {
        if (captured == null) {
            MDC.clear();
        } else {
            MDC.setContextMap(captured);
        }
        performWork();
    } finally {
        if (oldWorker == null) {
            MDC.clear();
        } else {
            MDC.setContextMap(oldWorker);
        }
    }
});
```

This is a snippet in an application that imports `java.util.Map` and `org.slf4j.MDC`; `executor` and `performWork()` are existing application components.

**`getCopyOfContextMap` can return `null`.** According to the API, `setContextMap` replaces the current thread's map rather than updating a single key. Therefore, a decorator/framework needs clear ownership to avoid accidentally wiping context set by another library.

In production, use your framework's built-in task decorator/context propagation if available and test with a real thread pool. Do not manually copy-paste a wrapper at every task submission site without centralized management.

## 14. CompletableFuture, Reactive, Virtual Threads, and Async Logging

### CompletableFuture

`thenApplyAsync`, `thenComposeAsync`, or `supplyAsync` may execute on a different worker thread. The submitting thread's snapshot must be **applied inside the actual callback**; context set at the start of an HTTP handler does not automatically persist across an entire `CompletableFuture` chain.

### Reactive Stack

In Reactor/RxJava, signals can hop across multiple threads. **`ThreadLocal` does not reliably follow an entire processing pipeline**. Reactor provides **Reactor Context** and context propagation mechanisms; if the logging backend relies on MDC, bridge it at LogEvent emission time using the appropriate model.

### Virtual Threads

In JDK 21+, virtual threads each have their own per-thread `ThreadLocal` context. They do not guarantee that a submitting task's context will automatically propagate to every newly spawned virtual thread. Design around units of work, not thread names.

### Async Appender / Async Logger

Another issue is **when MDC is captured**:

- Context must be attached to the **LogEvent when the event is emitted**.
- Async logging may perform formatting on a separate consumer thread.
- If a custom formatter calls `MDC.get` at **formatting time** on the consumer thread, it may read stale or empty context.
- Logging frameworks generally provide snapshot/deferred processing depending on the implementation, but **you must verify your specific backend, encoder, and version**.
- Do not assume MDC is still present when the queue is drained later.

Under high load testing, verify that context IDs do not mix between events, including during full queues, exceptions, shutdowns, or deployments.

## 15. Structured Logs and Distributed Tracing

MDC often holds `trace_id`, `span_id`, or `correlation_id` to jump from a log event to a trace.

A trace-correlated event might look like:

```json
{
  "level": "ERROR",
  "service.name": "checkout-service",
  "trace_id": "4f9e7a1c",
  "span_id": "2a7c",
  "request_id": "req-101",
  "event": "payment_failed",
  "message": "Payment gateway unavailable"
}
```

This is an **illustrative schema**; the sample trace ID values in this article do not conform to OpenTelemetry/W3C trace context formatting. In real systems, trace/span IDs have specified lengths and encodings and must come from tracing instrumentation rather than being fabricated.

**MDC does not create a distributed trace.** It only attaches and serializes context if code/instrumentation has already populated it with valid IDs. Conversely, having an active span in the tracer does not guarantee MDC contains `trace_id` unless a bridge/instrumentation is in place.

OpenTelemetry defines these concepts:

- **SpanContext**: trace/span IDs and flags.
- **LogRecord attributes**: typed data on a log event.
- **Resource**: stable metadata about the telemetry-emitting entity, e.g., `service.name`.
- **Baggage**: key-value pairs propagated across service/process boundaries.

**Do not use Baggage as proof of tenant authorization or as a security principal.** Baggage can originate from untrusted clients and travel across many hops. If you need to attach a tenant ID, obtain it from a trusted resolver/authorization layer and only propagate permitted metadata. Never put tokens into MDC or Baggage.

When emitting JSON logs for a collector that uses the OpenTelemetry data model, you may need to map text fields like `request_id`/`trace_id` to actual `LogRecord` attributes/`TraceId`. A JSON object and an OTLP payload are **not equivalent** merely because both are "structured."

## 16. Handling `Throwable` in Structured Logs

A Java error typically carries several pieces of data:

- Exception class.
- Exception message.
- Stack trace and cause chain.
- Request/tenant/trace context at the time of failure.
- Log level and business event such as `order_save_failed`.

Example call:

```java
try {
    saveOrder();
} catch (RuntimeException e) {
    LOG.atError()
            .addKeyValue("event", "order_save_failed")
            .addKeyValue("order_id", orderId)
            .setCause(e)
            .log("Could not save order");
    throw e;
}
```

This is an SLF4J 2.x snippet in a class with `LOG`, `saveOrder()`, and `orderId`; it is not standalone. `setCause(e)` attaches the `Throwable` to the logging event for the encoder/backend to handle. `throw e` is a business-logic decision; logging itself **does not throw or roll back**.

A JSON encoder may place the exception into `exception.class`, `exception.message`, `stack_trace`, or another field depending on the schema. Stack traces containing newlines must be escaped inside a JSON string or structured separately so they do not break NDJSON framing.

**Do not assume `e.getMessage()` is safe data**: it can contain URLs with tokens, file paths, user input, or personal information. Establish an exception logging policy and mask sensitive data at the source.

**Avoid logging the same stack trace redundantly at every layer.** Logging the same `Throwable` at `ERROR` in repository, service, and controller before rethrowing creates nearly identical events. Choose a responsible boundary and preserve enough context to investigate.

## 17. JSON Field Collisions and Schema Ownership

When an encoder pulls data from multiple sources:

```text
LogEvent level, logger, message
MDC: request_id, tenant_id, event
Per-event: event, order_id, duration_ms
Collector: service_name, environment, trace_id
```

**key collisions** can occur. For example:

- `event` appears in both MDC and per-event attributes with different values.
- `service_name` is written by the app, but the collector overwrites it.
- `timestamp` has both creation time and ingest time.
- `trace_id` from tracing instrumentation conflicts with a manually set value.
- `user_id` is added to context by multiple middleware components.

A JSON object can technically contain duplicate keys, but many parsers pick the last value or behave inconsistently, making queries unreliable.

**Define ownership rules:**

| Field | Responsible data source |
| --- | --- |
| `timestamp` | Logging event/encoder (event time) |
| `level` | Backend/encoder |
| `logger` | Backend/encoder |
| `service.name` | Deployment/resource configuration |
| `request_id` | Request context middleware |
| `tenant_id` | Trusted tenant resolver |
| `trace_id`/`span_id` | Tracing instrumentation/context |
| `event` | Business logging call |
| `order_id` | Event-specific value |
| `duration_ms` | Measured value per event |
| `collector.received_at` | Collector when needed, distinct from event time |

This is an **illustrative convention**; organizations may use different schemas. What matters is preventing three different places from writing the same field name without a precedence policy and tests.

## 18. Data Security and Storage Cost

Structured logs are easier to search, but they also make data leaks easier if every MDC value is emitted indiscriminately.

### Sensitive Data

- Never put passwords, API keys, bearer tokens, session cookies, or OTPs into MDC.
- Never copy all HTTP headers into MDC; they may contain `Authorization`, cookies, and personal data.
- For `tenant_id`, `user_id`, or `account_id`, use safe internal IDs and enforce privacy policies.
- Do not let users dictate arbitrary **MDC key names**; dynamic keys cause schema and index churn.
- Bound value lengths; sanitize CR/LF when emitting text. JSON encoders must properly escape quotes and control characters.
- Do not assume filtering at the collector protects hops **before the collector receives the log**.
- Define retention, access controls, masking/redaction, and query auditing for the log store.

### Cardinality

`request_id` and `trace_id` usually have **very many unique values**. In systems like Loki, do not turn them into indexed labels on every event because the number of streams can explode.

They can still be stored in the **log line or structured metadata** depending on the system and version. Lower-cardinality labels like `service`, `environment`, or `namespace` are usually more suitable, though you should still verify in practice.

### Cost

A large MDC map increases the number of fields per event, bytes emitted, encoding overhead, network bandwidth, and storage cost. Do not dump the entire request/session state into MDC and emit it on every logger call.

**Rule of thumb:** keep only small, repeated, useful, and approved context fields. Large payloads or operation-specific details should be handled in dedicated events with explicit limits.

## 19. MDC in HTTP Filters, Message Consumers, and Scheduled Jobs

### HTTP Request

1. Authenticate/resolve required metadata.
2. Generate or accept `request_id` according to your trust model.
3. Open a context scope; attach `request_id`, verified tenant, and trace ID if available.
4. Invoke controller/service/repository; context is present on logger calls within the execution scope.
5. When crossing to async execution, use a propagation bridge.
6. Close the scope in `finally`.
7. Ensure request A's context never leaks to request B on reused worker threads.

### Message Consumer

Messages may carry `message_id`, `correlation_id`, and tenant metadata. Do not trust fields from an external producer without verification. Each message execution should have its own scope; retry and dead-letter paths must also clean up.

### Scheduled Job

Periodic tasks typically need `job_id`, `run_id`, `attempt`, and `operation`. If a job processes multiple tenants, **each tenant needs its own scope**—never set tenant A for the entire batch and process tenant B under tenant A's context.

### Library or Interceptor

A library that only owns `operation_id` should not clear the entire request MDC. It should save and restore the previous value of **only the keys it owns**, or use a context scope abstraction with a clear contract.

### Incomplete Authentication

An `auth_failed` log emitted before tenant verification **should not** attach `tenant_id` from an untrusted header. If you need to record the requested tenant, use a field like `requested_tenant_id_untrusted` per your security schema/policy and never let it stand in for a trusted `tenant_id`.

## 20. End-to-End Testing of MDC and Structured Logging

When verifying an implementation, do not stop at "I see the ID in the terminal."

| Step | Check | Expected result |
| --- | --- | --- |
| 1 | Set MDC for request A | Event has `request_id=A` |
| 2 | Request B runs on the same worker | Event B does not carry `request_id=A` |
| 3 | Exception thrown mid-processing | `finally` cleans up or restores context |
| 4 | Nested scope A → B → A | Value returns to A after closing B |
| 5 | Async callback switches threads | Context is properly snapshotted/applied |
| 6 | Structured JSON output | `request_id` is an actual JSON field |
| 7 | Type check | `duration_ms` is a number, `tenant_id` is a string |
| 8 | Non-ASCII / Unicode data | UTF-8 preserved in the collector |
| 9 | Quotes/newlines in message | Valid JSON, does not break framing |
| 10 | `Throwable` with cause | Stack trace emitted per schema |
| 11 | Different backend or encoder upgrade | Field names/paths do not change unexpectedly |
| 12 | Collector ingests JSON from stdout | Parser decodes into object and fields |
| 13 | Dashboard query by `request_id` | Returns exact events for that request |
| 14 | No request context | System events valid; tenant-scoped events evaluated per policy |
| 15 | Secret/PII test | No tokens, passwords, or sensitive payloads |
| 16 | Dual collection stdout + file | No unintended duplicates |
| 17 | Async queue load test | No context mixing; drop/backpressure metrics present |
| 18 | Dashboard/label cardinality | No indexed stream explosion |
| 19 | Message consumer retry | Per-attempt context, no stale reuse |
| 20 | Service startup before requests | No fake tenant attached to startup logs |

### How to Tell If JSON Is Truly Structured

Example log:

```json
{"message":"request_id=req-101 order_id=ORD-101"}
```

is not equivalent to:

```json
{"message":"Order received","request_id":"req-101","order_id":"ORD-101"}
```

The first has **a single `message` field**; the system must parse text to extract `request_id`. The second has **independent JSON fields**. Still, both require the collector to parse the object and store fields at the right paths; a raw JSON string inside a container wrapper does not automatically become indexed fields.

### Stdout and Stderr

JUL `ConsoleHandler` writes to stderr by default, whereas Logback `ConsoleAppender` can be configured for `System.out`. In containers, agents may collect both streams. Verify the **actual destination** by separating stdout/stderr or inspecting collector metadata rather than relying solely on terminal output.

## 21. Common Mistakes to Avoid

**1. "MDC is structured logging."** False. MDC is a context map; structured output requires an appropriate encoder and collector.

**2. "`MDC.put` automatically creates a JSON field."** Not guaranteed. The backend may not print MDC or may print it only inside a text message.

**3. "All MDC values have Java object types."** SLF4J's MDC map is string-to-string; numbers require typed event fields or controlled conversion.

**4. "Setting MDC on the HTTP thread is enough."** Async tasks may run on other threads; propagation is required.

**5. "Thread pools clean up MDC automatically."** Never assume this. Cleanup/restore in `finally` is required.

**6. "`MDC.putCloseable` restores the previous value."** It removes the key on close; nested scopes must be handled carefully.

**7. "Reading MDC inside an async formatter is safe."** The formatter may run on a different consumer thread; rely on context snapshotted in the LogEvent.

**8. "SLF4J Simple, Logback, and Log4j2 are identical."** APIs, providers, and encoders differ in capabilities and configuration.

**9. "If the log message contains `request_id=...`, the collector has a `request_id` field."** No, it may just be plain text.

**10. "Every MDC key should be emitted to JSON."** No. Whitelist keys and exclude secrets/PII.

**11. "Every MDC key should become an indexed label."** Wrong for high-cardinality keys like request/trace IDs.

**12. "`tenant_id` in MDC is sufficient for authorization."** No. Authorization must be independent and use trusted sources.

**13. "Baggage lets us trust tenant IDs from any request."** No. Baggage can be forged and propagated across service boundaries.

**14. "If it's valid JSON, every collector understands the schema."** No. Collectors also need the right input, framing, parser, mapping, and types.

**15. "`addKeyValue` guarantees the encoder outputs all key/value pairs to JSON."** No. Provider/encoder support and configuration determine what is emitted.

**16. "We can put the same key in both MDC and event attributes as a fallback."** This can cause collisions, conflicting values, or arbitrary parser precedence.

**17. "Put the request ID in the logger name."** Do not create large numbers of dynamic logger names; use metadata instead.

**18. "Logging exceptions is always safe."** Exception messages and stack traces can contain sensitive data.

**19. "Counting JSON log lines gives the number of successful transactions."** Logs can be dropped, duplicated, filtered, or retried; business state needs an authoritative source.

**20. "Switching providers won't affect dashboards."** Field names, nested paths, severity, MDC support, and schemas can all change.

## 22. Self-Check Questions

1. **What problem does MDC solve?** Keeping a shared set of metadata across multiple events within a single processing scope.
2. **How does structured logging differ from MDC?** Structured logging represents events with typed fields; MDC is one source of context that an encoder may use.
3. **Does `MDC.put("duration_ms", "25")` produce a JSON number?** Not by default; it is a string in MDC.
4. **How do you ensure `duration_ms` is a proper number?** Use a typed event field or controlled encoder/mapping conversion.
5. **Why shouldn't every event's `order_id` go into MDC?** It usually applies to a single event/operation and can easily leak into other events.
6. **Does SLF4J MDC automatically select a JSON backend?** No; the provider/encoder determines the output format.
7. **How does Logback `PatternLayout` read `request_id` from MDC?** `%X{request_id}`.
8. **What is the equivalent context API in Log4j2?** `ThreadContext`; `JsonTemplateLayout` has an `mdc` resolver.
9. **Does `MDC.putCloseable` automatically restore the previous value on close?** No, it removes the key.
10. **Can `getCopyOfContextMap()` return `null`?** Yes.
11. **Does `MDC.setContextMap(map)` merge into or replace the current thread's map?** According to the API, it replaces the context map.
12. **Why must a worker's MDC be restored after a task?** To avoid polluting context for the next task on a reused thread.
13. **Is `CompletableFuture.thenApplyAsync` guaranteed to run on the request thread?** No.
14. **Why shouldn't an async JSON formatter read the caller's `ThreadLocal`?** The caller may be on a different thread; the LogEvent needs a snapshotted context.
15. **Does JSON containing `"message":"tenant_id=A"` already have a `tenant_id` field?** No, it only has a message string.
16. **Can MDC be used for tenant authentication?** No; it is only logging metadata.
17. **Should MDC hold tokens or access keys?** No.
18. **Should `request_id` be a high-cardinality Loki label?** Usually no.
19. **What happens if a collector misparses timestamps?** Logs can appear at the wrong time, skewing queries and alerts.
20. **Can an event have both MDC and `addKeyValue`?** Yes, provided there is an ownership/collision policy and encoder support.
21. **Is an event with a `Throwable` automatically logged completely in JSON?** It depends on the encoder/schema and how the code passes the `Throwable`.
22. **In the demo, why do the four lines have the right request ID for each tenant?** Each request has its own scope, the worker receives a snapshot and restores context, and `Future.get` forces the two tasks to complete in call order.

## 23. Production Rollout Checklist

### Context Identification

- MDC keys have clear owners and purposes.
- `request_id` is generated/verified at the boundary.
- `tenant_id` comes from resolution/authorization, not untrusted headers.
- Trace/span IDs come from the tracing system when available, never fabricated.
- Context is attached to every appropriate request, message, job, and callback.

### Lifecycle Protection

- Scopes are opened/closed in `try/finally`.
- Nested scopes restore previous values when needed.
- `ExecutorService`/`CompletableFuture`/reactive pipelines have proper propagation.
- No mutable MDC map is shared across requests.
- Async logging captures context at the right time; backends are tested on upgrade.

### JSON Output

- Encoder supports MDC and emits only whitelisted keys.
- Event-specific fields have accurate types, especially numbers/booleans.
- Key collisions between MDC, event attributes, and collector metadata are avoided.
- Timestamp, level, logger, message, and exceptions follow the schema.
- Each JSON event is complete on a single line if the pipeline uses NDJSON.
- JSON parser/collector preserves field paths, names, types, and encoding.

### Operations and Security

- Tests verify searching by `request_id`/`tenant_id` in the log store.
- No secrets, tokens, or unnecessary PII are logged.
- Size/cardinality limits, retention, and read permissions are configured.
- Metrics/alerts exist for parser errors, log drops, and queue backlogs.
- No unintended duplicate collection paths exist.
- Contract tests cover provider/encoder changes.
- Log structure is managed as an observability contract rather than changing fields ad hoc.
