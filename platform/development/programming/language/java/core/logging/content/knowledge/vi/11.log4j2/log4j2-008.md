# Plugin của Log4j2: kiến trúc mở rộng, cách tạo và triển khai

## 1. Plugin của Log4j2 là gì?

**Plugin của Log4j2** là một thành phần mở rộng được hệ thống **Log4j Core** nhận diện, khởi tạo và kết nối vào pipeline logging, thường thông qua cấu hình. Cơ chế này cho phép bổ sung hành vi mà không cần sửa mã của chính Log4j: ví dụ tạo một **Appender** gửi sự kiện tới đích riêng, một **Filter** áp dụng quy tắc lọc, một **Layout** chuyển bản ghi sang định dạng khác hoặc một **Lookup** tìm giá trị theo quy ước.

Trong hệ thống Log4j 2, nhiều thành phần có sẵn cũng được triển khai dưới dạng plugin. Ví dụ:

~~~xml
<Console name="OUT" target="SYSTEM_OUT">
    <PatternLayout pattern="%level | %msg%n"/>
</Console>
~~~

Ở đây **Console** là một plugin Appender và **PatternLayout** là một plugin Layout. XML trên chỉ là đoạn cấu hình minh họa, cần đặt trong cấu trúc **Configuration / Appenders / Loggers** đầy đủ.

Plugin giúp cấu hình có thể mô tả **thành phần nào tồn tại, có thuộc tính gì và phụ thuộc thành phần con nào**. Log4j Core tra cứu metadata plugin, tạo instance qua factory/builder và gắn chúng vào những vị trí tương thích.

**Phân biệt quan trọng:**

- **Plugin Log4j2** là điểm mở rộng của **Log4j Core**, không phải một phương thức mới trong Logger.
- **log4j-api** cung cấp API mà ứng dụng gọi, chẳng hạn **LogManager.getLogger()** và **logger.info()**; plugin configuration thuộc **log4j-core**.
- Một **JAR dependency** chỉ chứa mã chưa chắc đã là plugin; plugin phải được khai báo và đăng ký để Log4j tìm thấy.
- Log4j có hàng loạt plugin tích hợp sẵn. Không cần tự viết plugin nếu **Console, RollingFile, PatternLayout, ThresholdFilter, MarkerFilter** hoặc các thành phần khác đã đáp ứng yêu cầu.

Mục tiêu của bài này là hiểu **khi nào cần plugin, các loại plugin phổ biến, annotation và quá trình discovery**, rồi tự tạo một plugin Filter bằng Java 17 và Maven.

## 2. Plugin nằm ở đâu trong kiến trúc Log4j2?

Một cách nhìn đơn giản:

~~~text
Mã ứng dụng
    |
    | log.info(...), log.warn(...)
    v
Log4j API
    |
    v
Log4j Core / LoggerContext
    |
    +-- Configuration, LoggerConfig, Filter
    |                      |
    |        PluginManager đọc plugin descriptor
    |        và dựng những thành phần cấu hình
    |
    +-- Appender (plugin) ---------> đích ghi
    |      |
    |      +-- Filter (plugin) ----> chọn/bỏ sự kiện
    |      |
    |      +-- Layout (plugin) ----> định dạng
    |
    +-- Lookups, Policies, Strategies, Converters...
~~~

Khi khởi tạo/cập nhật cấu hình, Log4j Core đọc tệp cấu hình như **log4j2.xml**, tìm các plugin theo **category/name**, biến các thuộc tính cấu hình thành giá trị Java và dựng đối tượng.

Khi chương trình ghi log, những đối tượng đã tạo sẽ tham gia pipeline. **Không phải cứ mỗi câu lệnh LOG.info() là Log4j lại quét toàn bộ classpath hoặc tạo lại tất cả plugin**. Discovery và cấu hình diễn ra theo vòng đời hệ thống/configuration; từng thành phần được gọi theo vai trò của nó khi xử lý sự kiện.

**Plugin không đồng nghĩa với SLF4J provider hoặc Log4j implementation.** Một ứng dụng có thể dùng trực tiếp Log4j API hoặc dùng SLF4J thông qua adapter tới Log4j Core. Dù API đầu vào khác nhau, các Appender/Filter/Layout đã cấu hình trong Log4j Core vẫn là các điểm mở rộng plugin của backend.

## 3. Những nhóm plugin thường gặp

| Loại | Công việc | Ví dụ/use case |
| --- | --- | --- |
| **Appender** | Gửi sự kiện tới một nơi nhận | Console, File, RollingFile, Socket, đích tự viết |
| **Layout/Encoder** | Chuyển LogEvent thành dữ liệu đầu ra | PatternLayout, JsonTemplateLayout, định dạng tự viết |
| **Filter** | Chấp nhận, từ chối hoặc để bước sau quyết định | ThresholdFilter, MarkerFilter, filter nghiệp vụ |
| **Lookup (StrLookup)** | Tra cứu giá trị để nội suy cấu hình hoặc log context | env, sys, ctx, lookup tùy chỉnh |
| **Pattern converter** | Xử lý token trong pattern layout | Tạo conversion token riêng |
| **TriggeringPolicy** | Quyết định khi nào RollingFile cần rollover | Theo dung lượng hoặc thời gian |
| **RolloverStrategy** | Quyết định thao tác khi rollover | Đổi tên, xóa file cũ, nén theo chính sách |
| **RewritePolicy** | Biến đổi LogEvent trong đường xử lý hỗ trợ rewrite | Thêm/điều chỉnh metadata theo quy tắc |
| **ConfigurationFactory** | Đọc và tạo cấu hình từ một nguồn/định dạng | Hỗ trợ dạng cấu hình đặc biệt |
| **TypeConverter** | Chuyển chuỗi từ cấu hình thành kiểu Java | Kiểu giá trị tùy chỉnh ở plugin attribute |

Một số category plugin có API và quy tắc riêng. **Không phải tất cả plugin đều là XML element**: plugin Lookup có category riêng và thường được gọi qua cơ chế nội suy; plugin Appender, Layout và Filter thường thuộc category **Core** khi xuất hiện thành phần trong tệp cấu hình.

Nếu chỉ muốn tăng mức log từ INFO lên DEBUG, đổi PatternLayout hoặc thêm RollingFile, bạn **không cần tạo plugin mới**; chỉ cần cấu hình các plugin có sẵn.

## 4. Trường hợp nào cần tự viết plugin?

Chỉ nên tạo plugin riêng khi các thành phần chuẩn và cách cấu hình hợp lệ không diễn đạt được yêu cầu.

**Những ví dụ có cơ sở:**

1. Cần **Filter** thực hiện một quy tắc đặc thù theo trường nghiệp vụ ổn định, không thể hiện thuận tiện bằng các Filter có sẵn.
2. Cần **Layout** ở một định dạng rất riêng nhưng vẫn tích hợp vòng đời và encoder của Log4j Core.
3. Cần **Appender** gửi log tới một hệ thống thu nhận nội bộ với protocol không được plugin chuẩn hỗ trợ, đồng thời cần quản lý kết nối, lỗi, retry và shutdown.
4. Cần **Lookup** cho một nguồn cấu hình do ứng dụng kiểm soát, với ranh giới bảo mật được xác định.
5. Cần mở rộng cơ chế rolling, định dạng hoặc cấu hình mà extension point chính thức có hỗ trợ.

**Khi chưa cần viết plugin:** yêu cầu lọc theo level, marker, chuỗi message thông dụng, xuất ra Console/RollingFile, cấu hình JSON qua layout có sẵn hoặc thêm trường context tiêu chuẩn thường đã có cách thực hiện bằng plugin chuẩn. Tự viết plugin làm tăng mã cần bảo trì, phạm vi kiểm thử, rủi ro tương thích khi nâng Log4j và bề mặt tấn công của pipeline log.

Một quy tắc thiết kế: **thử plugin tích hợp và cấu hình chính thức trước, chỉ viết phần mở rộng khi có khoảng trống chức năng cụ thể.**

## 5. Các annotation nền tảng: @Plugin, category và name

Log4j Core cung cấp annotation **org.apache.logging.log4j.core.config.plugins.Plugin**. Ví dụ khai báo plugin có tên **ExcludeExactMessage**:

~~~java
@Plugin(name = "ExcludeExactMessage", category = Node.CATEGORY)
public final class ExcludeExactMessageFilter extends AbstractFilter {
    // Thành phần plugin được triển khai ở ví dụ hoàn chỉnh bên dưới.
}
~~~

Đây là **snippet**, không phải lớp chạy độc lập. **Node.CATEGORY** là category **Core**, dùng cho nhiều thành phần thể hiện dưới dạng phần tử cấu hình. Cần import **Plugin**, **Node** và **AbstractFilter**.

Ý nghĩa:

- **name**: tên mà Log4j dùng để tra cứu plugin trong category, ví dụ thẻ XML **ExcludeExactMessage**. Trong cùng category, việc so khớp tên plugin **không phân biệt hoa/thường**.
- **category**: nhóm plugin. Việc so khớp category **phân biệt hoa/thường**; plugin viết cho cấu hình Core phải khai báo đúng category.
- **elementType**: từng được dùng trong cú pháp cấu hình cũ; trong tài liệu Log4j 2.x hiện đại, thuộc tính này **đã deprecated**. Không thêm nếu không có lý do tương thích ngược.
- **Tên plugin trùng trong cùng category**: có thể gây warning và phụ thuộc thứ tự discovery. Không chủ động đặt tên trùng plugin hệ thống để “override” nếu chưa kiểm soát classpath và rủi ro.

Plugin không được gọi chỉ vì có annotation. Log4j còn cần **metadata đăng ký** đúng lúc build để phát hiện lớp, và nếu plugin cần hiện diện trong cấu hình thì phải có **cách khởi tạo hợp lệ**.

## 6. @PluginFactory, @PluginBuilderFactory và các loại tham số

Đối với plugin xuất hiện dưới dạng phần tử trong cấu hình (như Appender, Filter, Layout), Log4j cần một cách dựng đối tượng:

| Cơ chế | Tình huống phù hợp | Ý tưởng |
| --- | --- | --- |
| **@PluginFactory** | Plugin đơn giản, ít tham số | Một static method nhận thuộc tính/phần tử từ cấu hình và trả instance |
| **@PluginBuilderFactory** | Plugin có nhiều tùy chọn, default và validation | Một static method trả Builder; các trường builder nhận giá trị cấu hình |

Các annotation truyền giá trị vào factory/builder:

- **@PluginAttribute("name")**: lấy thuộc tính dạng chuỗi từ configuration và chuyển sang kiểu của tham số bằng TypeConverter khi cần.
- **@PluginElement("name")**: inject một plugin/nút con, ví dụ một Layout nằm trong Appender hoặc một policy con.
- **@PluginConfiguration**: inject đối tượng **Configuration** hiện tại.
- **@PluginNode**: inject **Node** đang được xử lý.
- **@PluginValue**: inject giá trị văn bản của node hoặc thuộc tính value theo quy tắc plugin.
- **@PluginBuilderAttribute**: gắn thuộc tính vào trường của builder.
- **@Required**: thêm validation cho giá trị cấu hình bắt buộc trong những trường hợp hỗ trợ.

Ví dụ một chữ ký factory:

~~~java
@PluginFactory
public static ExcludeExactMessageFilter create(
        @PluginAttribute("message") String message) {
    if (message == null || message.isBlank()) {
        return null;
    }
    return new ExcludeExactMessageFilter(message);
}
~~~

Đây là **đoạn lấy từ ví dụ lớp đầy đủ**, không phải chương trình biên dịch độc lập. Khi có cấu hình:

~~~xml
<ExcludeExactMessage message="health.ping"/>
~~~

Log4j chuyển thuộc tính **message** thành tham số factory. Factory trả về instance của Filter; nếu cấu hình thiếu giá trị, ví dụ trên trả null để từ chối tạo thành phần. Trong ứng dụng thật, hãy kiểm tra **Status Logger** vì lỗi tạo plugin có thể dẫn đến cấu hình không đúng kỳ vọng.

**Builder** thường dễ quản lý hơn khi có nhiều tùy chọn, giá trị mặc định động và đối tượng con. Không cần thay plugin đơn giản bằng builder chỉ để dùng thêm một annotation.

## 7. Plugin được phát hiện như thế nào?

Bước quan trọng thường bị bỏ sót khi tự viết plugin là **annotation processing trong lúc biên dịch**.

Quy trình tiêu biểu:

~~~text
Mã Java có @Plugin
       |
       v
javac + Log4j PluginProcessor
       |
       +-- Biên dịch class .class
       |
       +-- Sinh metadata đăng ký:
           META-INF/org/apache/logging/log4j/core/
               config/plugins/Log4j2Plugins.dat
       |
       v
Đóng gói class + metadata vào JAR/classpath
       |
       v
PluginManager đọc descriptor
       |
       v
Log4j Core biết tên/category và tạo plugin từ cấu hình
~~~

**Log4j2Plugins.dat** là một **descriptor nhị phân do annotation processor tạo ra**, không phải tệp text mà developer nên tự viết hoặc sửa thủ công.

Theo thứ tự discovery trong tài liệu Log4j 2.x, Log4j ưu tiên descriptor trên classpath, có hỗ trợ descriptor trong OSGi, rồi mới đến một số cơ chế tìm theo package cũ. Những cách như:

- thuộc tính **log4j.plugin.packages**,
- **PluginManager.addPackages()**,
- thuộc tính **packages** của phần tử Configuration,

đã được tài liệu Log4j 2.x đánh dấu **deprecated**. Không chọn package scanning làm phương án chính cho dự án mới; dùng annotation processing và đóng gói descriptor.

**Điều kiện vận hành:** class của plugin và descriptor phải thực sự nằm trên **runtime classpath** mà Log4j Core sử dụng. Nếu plugin được biên dịch nhưng bị thiếu trong artifact chạy, Log4j không thể tạo nó từ tên cấu hình.

### Lưu ý khi nâng JDK

Trên các bản JDK mới như JDK 23+, annotation processors không được bật mặc định theo cùng cách như trước. **Nên khai báo plugin processor tường minh trong build**, ngay cả khi bạn đang phát triển trên JDK 17, để việc build ổn định giữa môi trường và CI.

Nếu cần **GraalVM Native Image**, còn có yêu cầu riêng về **reachability metadata** để plugin hoạt động khi chạy native. Log4j có **GraalVmProcessor** dành cho mục tiêu đó; việc plugin chạy tốt trên JVM không tự bảo đảm nó đã được cấu hình đầy đủ cho native image.

## 8. Ví dụ hoàn chỉnh: tự viết một Filter plugin bằng Java 17

Ta sẽ tạo **ExcludeExactMessageFilter** để **bỏ chính xác** bản ghi có thông điệp **health.ping** tại một Console Appender. Các bản ghi khác tiếp tục đi qua pipeline.

Mục tiêu học tập:

- Dùng **@Plugin(name, category)** khai báo tên và nhóm.
- Dùng **@PluginFactory** và **@PluginAttribute** đọc cấu hình.
- Kế thừa **AbstractFilter**, override **filter(LogEvent)**.
- Dùng **DENY** khi trùng message và **NEUTRAL** khi không trùng.
- Dùng **PluginProcessor** tạo descriptor, không dựa vào package scanning.
- Chạy mã qua **Log4j API**, kiểm tra chính plugin của **Log4j Core** đã được áp dụng.

**Phạm vi ví dụ:** chỉ lọc một message cố định để dễ kiểm chứng. Trong production, không nên bỏ mọi lỗi liên quan health check; hãy dùng tên sự kiện an toàn và chính sách kiểm soát log/audit phù hợp.

Ví dụ dùng **Log4j 2.26.1**, **Maven** và **JDK 17+**; cần Maven có thể tải dependency từ kho được cấu hình. Phiên bản ở đây được cố định để ví dụ tái lập được, không phải lời khuyên mọi dự án phải sử dụng đúng phiên bản này.

**Tại sao khai báo annotationProcessorPaths?** Để Maven gọi **PluginProcessor**, sinh descriptor. Chỉ có **log4j-core** ở runtime và annotation trên class không phải luôn đủ trong mọi toolchain hoặc JDK mới.

### 8.3. ExcludeExactMessageFilter.java

~~~java
package example.logging;

import org.apache.logging.log4j.core.Filter.Result;
import org.apache.logging.log4j.core.LogEvent;
import org.apache.logging.log4j.core.config.Node;
import org.apache.logging.log4j.core.config.plugins.Plugin;
import org.apache.logging.log4j.core.config.plugins.PluginAttribute;
import org.apache.logging.log4j.core.config.plugins.PluginFactory;
import org.apache.logging.log4j.core.filter.AbstractFilter;

@Plugin(name = "ExcludeExactMessage", category = Node.CATEGORY)
public final class ExcludeExactMessageFilter extends AbstractFilter {

    private final String messageToExclude;

    private ExcludeExactMessageFilter(String messageToExclude) {
        super(Result.DENY, Result.NEUTRAL);
        this.messageToExclude = messageToExclude;
    }

    @PluginFactory
    public static ExcludeExactMessageFilter create(
            @PluginAttribute("message") String message) {

        if (message == null || message.isBlank()) {
            return null;
        }
        return new ExcludeExactMessageFilter(message);
    }

    @Override
    public Result filter(LogEvent event) {
        String text = event.getMessage().getFormattedMessage();
        return messageToExclude.equals(text)
                ? Result.DENY : Result.NEUTRAL;
    }
}
~~~

**Các điểm cần hiểu:**

1. **@Plugin(name = "ExcludeExactMessage", category = Node.CATEGORY)** đăng ký class với tên cấu hình **ExcludeExactMessage** thuộc nhóm Core.
2. **@PluginFactory** được hệ thống cấu hình dùng để tạo instance.
3. **@PluginAttribute("message")** nhận giá trị từ thuộc tính message của phần tử XML.
4. Constructor **super(Result.DENY, Result.NEUTRAL)** khai báo giá trị onMatch/onMismatch cho AbstractFilter. Logic **filter(LogEvent)** trong ví dụ trực tiếp trả các Result tương ứng.
5. **getFormattedMessage()** lấy message đã áp dụng tham số; điều kiện so sánh **equals()** nhằm tránh lọc nhầm message gần giống.
6. Nếu không trùng message, **NEUTRAL** nghĩa là **không đưa ra quyết định chặn tại Filter này**, không phải cam kết bản ghi sẽ xuất bất kể level hoặc Filter khác.
7. Factory từ chối giá trị rỗng bằng cách trả null. Khi cấu hình thiếu thuộc tính, bạn cần kiểm tra Status Logger và xác nhận ứng dụng không khởi chạy với chính sách log sai lệch.
8. Lớp này override chỉ **filter(LogEvent)**, thích hợp để gắn vào **Appender** như ví dụ. Nếu mang nó lên giai đoạn lọc Logger rất sớm, những overload khác của **AbstractFilter** có thể trả NEUTRAL; để áp dụng nhất quán ở nhiều stage phải triển khai overload thích hợp và kiểm thử riêng.

Ở bản production, có thể kiểm tra LogEvent/message null một cách phòng vệ, dùng mã sự kiện ổn định thay vì chuỗi tự do, và đo chi phí của **getFormattedMessage()** khi khối lượng log rất lớn.

### 8.4. log4j2.xml

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<Configuration>
    <Appenders>
        <Console name="OUT" target="SYSTEM_OUT">
            <PatternLayout pattern="%level | %msg%n"/>
            <ExcludeExactMessage message="health.ping"/>
        </Console>
    </Appenders>

    <Loggers>
        <Root level="info">
            <AppenderRef ref="OUT"/>
        </Root>
    </Loggers>
</Configuration>
~~~

**Console** và **PatternLayout** là các plugin có sẵn. **ExcludeExactMessage** là plugin vừa tạo. Nó được đặt **bên trong Console Appender**, vì vậy chỉ kiểm soát các bản ghi đi qua OUT; một Appender khác có thể có Filter riêng.

**Root level="info"** chặn DEBUG từ giai đoạn logger. **target="SYSTEM_OUT"** là cấu hình đầu ra của **Console Appender Log4j 2**; đừng nhầm với **java.util.logging.ConsoleHandler** của JDK, vốn thường ghi stderr.

**pattern="%level | %msg%n"** in mức log, dấu phân cách, message, và xuống dòng. Cấu hình này cố ý không in thời gian để đầu ra không thay đổi giữa những lần chạy. Trong production nên xem xét timestamp, logger name, requestId và cách xuất Throwable.

### 8.5. PluginDemo.java

~~~java

import org.apache.logging.log4j.Logger;

public final class PluginDemo {
~~~

### 8.6. Biên dịch và chạy

Trong thư mục **log4j2-plugin-demo** với Maven/JDK 17+:

~~~bash
mvn -q clean compile exec:java -Dexec.mainClass=example.logging.PluginDemo
~~~

**Stdout của chương trình, với plugin và cấu hình trên:**

~~~text
INFO | order.accepted orderId=ord-17
WARN | inventory.slow attempt=2
~~~

Chương trình không gọi **System.out.println()**; hai dòng được **Log4j Core Console Appender** xuất ra stdout. Maven có thể có thông báo riêng về quá trình build hoặc môi trường; khối trên mô tả hai dòng log ứng dụng.

| Lời gọi | Root level | Filter ở Console | Kết quả |
| --- | --- | --- | --- |
| INFO health.ping | Cho qua | DENY vì trùng message | Không in |
| INFO order.accepted | Cho qua | NEUTRAL | In INFO |
| WARN inventory.slow | Cho qua | NEUTRAL | In WARN |
| DEBUG cache.lookup | Không đạt INFO | Không tới Appender | Không in |

**Điều gì chứng minh plugin đã hoạt động?** Hai bản ghi INFO cùng vượt mức Root. Nếu không có plugin Filter, **health.ping** cũng sẽ xuất ra. Khi plugin được tạo và gắn thành công, chỉ đúng thông điệp này bị DENY.

Để kiểm tra descriptor sau compile, xem có tệp:

~~~text
target/classes/META-INF/org/apache/logging/log4j/core/config/plugins/Log4j2Plugins.dat
~~~

Nếu tệp không tồn tại, phải xem annotation processing và output của compiler trước khi nghi ngờ XML.

### 8.7. Cấu hình theo mục đích

Một cách kiểm thử hữu ích: đổi **message="health.ping"** thành **message="order.accepted orderId=ord-17"** rồi chạy lại. Khi đó bản ghi order.accepted bị loại còn health.ping có thể xuất, cho thấy giá trị XML được inject vào factory.

Đây chỉ là cách **thử cấu hình trên dự án demo**. Trong sản phẩm thật, không thay quy tắc lọc mà chưa đánh giá hệ quả vận hành: một thay đổi có thể khiến mất log quan trọng, bao gồm log lỗi hoặc kiểm toán.

## 9. Từ demo đến plugin production: những điểm phải thiết kế thêm

Một plugin chạy được chưa chắc đã phù hợp để vận hành lâu dài.

### A. Chọn đúng mức can thiệp

- **Global/Logger filter:** có thể quyết định sớm, giúp giảm chi phí tạo LogEvent nếu áp dụng đúng overload và stage.
- **AppenderRef filter:** phân luồng/giới hạn ở tham chiếu tới Appender.
- **Appender filter:** chỉ loại bản ghi khi đã tới một đích, phù hợp nếu mục tiêu là bỏ log khỏi đích đó.
- **Layout:** xử lý biểu diễn dữ liệu, không nên lạm dụng để quyết định chính sách phát/không phát sự kiện.
- **Appender:** quyết định cách ghi, tài nguyên và lỗi xuất bản; không nên ẩn nhiều hành vi đặc thù trong Filter khi chức năng thực là transport.

Log4j Filter có **ACCEPT**, **DENY**, **NEUTRAL**. Trong các stage khác nhau, **ACCEPT** có thể mang ngữ nghĩa sớm hơn việc kiểm tra level, đặc biệt ở giai đoạn Logger; **NEUTRAL** tiếp tục luồng quyết định hiện có. Không thay DENY bằng ACCEPT một cách máy móc, và kiểm tra chính xác stage mà Filter tham gia.

### B. Chi phí xử lý

Dự án có hàng chục nghìn log mỗi giây cần chú ý:

- Tránh regex phức tạp hoặc parse JSON lại cho mọi LogEvent nếu chỉ cần so sánh một mã sự kiện.
- Tránh gọi API mạng, truy vấn DB hoặc I/O bên trong **filter()**.
- Không gọi logger ngay trong plugin Filter theo đường log mà plugin đang chặn; có thể tạo vòng lặp hoặc deadlock.
- Giữ trạng thái bất biến hoặc thread-safe; cùng plugin có thể được dùng bởi nhiều thread.
- Kiểm thử khả năng filter xử lý message null, exception message, format có tham số và log bất đồng bộ.
- Chọn **logger level** hoặc built-in filter nếu mục tiêu chỉ là loại mức DEBUG/TRACE; không tạo plugin cho chức năng ngưỡng đơn giản.

### C. Bảo mật và độ tin cậy

- Tránh đưa bí mật, token, cookie, nội dung cá nhân hoặc payload chưa làm sạch vào thông điệp log hay metadata plugin.
- Đừng dùng Filter như phương án che bí mật duy nhất: bản ghi được chấp nhận có thể vẫn chứa thông tin nhạy cảm; phải giảm dữ liệu ngay từ nguồn và dùng encoder/redaction phù hợp.
- Nếu plugin đọc file, classpath, biến môi trường hoặc hệ thống ngoài, kiểm soát phạm vi truy cập và không xử lý nội dung không tin cậy như cấu hình được phép thực thi.
- Không bật những lookup/extension có rủi ro chỉ để khắc phục lỗi discovery. Đặc biệt phải cập nhật Log4j theo chính sách bảo mật của dự án và hiểu ảnh hưởng của nội suy cấu hình.
- Appender tùy chỉnh phải có chính sách khi không gửi được log: xử lý lỗi, retry, hàng đợi, ngắt kết nối, shutdown và giới hạn bộ nhớ.
- Log audit bắt buộc có yêu cầu riêng về đầy đủ, toàn vẹn và retention; không tùy tiện bỏ bằng plugin lấy mẫu hoặc filter vì lý do giảm chi phí.

Một quy tắc lọc giống **health.ping** chỉ nên loại sự kiện thành công/định kỳ được cho phép, không lọc chung chung tất cả tên có chứa **health**, vì có thể làm mất **health.failed**.

## 10. Plugin factory/builder: kiểm soát cấu hình và vòng đời

Khi plugin có thuộc tính, nên định nghĩa:

1. **Thuộc tính bắt buộc:** ví dụ Appender cần name, endpoint hoặc policy cụ thể.
2. **Giá trị mặc định:** rõ ràng, an toàn, không phụ thuộc ngẫu nhiên vào classpath.
3. **Validation:** từ chối giá trị sai sớm và phát lỗi cấu hình phù hợp qua Status Logger.
4. **Đối tượng con:** dùng **@PluginElement** khi plugin cần Layout, Filter con hoặc các policy khác.
5. **Vòng đời:** Appender/Filter/resource holder có thể cần start/stop/close, đồng bộ hóa và cleanup phù hợp Log4j Core.
6. **Khả năng tái cấu hình:** thay tệp XML hoặc môi trường có thể dẫn đến plugin instance mới; quản lý tài nguyên, trạng thái và thread khi cấu hình lại.
7. **Truy vết cấu hình:** plugin name, category và error thông báo đủ rõ để điều tra.

Nếu plugin nhiều lựa chọn, **@PluginBuilderFactory** kết hợp Builder có lợi: builder fields dùng **@PluginBuilderAttribute** và giá trị mặc định trong Java; phương thức build() kiểm tra ràng buộc. Không cần dùng Builder cho mọi Filter một thuộc tính như demo.

### Factory có thể thất bại thế nào?

Factory của demo trả null nếu thiếu **message**. Khi đó Log4j có thể ghi lỗi nội bộ rồi tiếp tục cấu hình những phần khác; **không tự kết luận** Filter đã được gắn chỉ vì XML có thẻ mang tên plugin. Đưa bài kiểm tra “health.ping phải bị bỏ” vào automated test, và xem Status Logger khi khởi động để phát hiện sai cấu hình.

## 11. Đóng gói plugin trong JAR, multi-module và shaded JAR

Với dự án một module như demo, **target/classes** chứa class, resource **log4j2.xml** và descriptor được sinh. Khi đóng JAR, phải bảo đảm descriptor đi theo class.

Với dự án nhiều module:

- Module plugin được biên dịch với **PluginProcessor** và tạo descriptor của riêng module.
- Module ứng dụng cuối khai báo dependency runtime đến plugin JAR, đồng thời chứa **log4j-core** thích hợp.
- Tệp cấu hình của ứng dụng tham chiếu plugin bằng **name** đã khai báo; chỉ nhắc đến plugin trong XML không tự làm JAR xuất hiện trên classpath.

**Lỗi khó phát hiện khi đóng shaded/uber JAR:** nhiều dependency có thể cùng chứa tệp **Log4j2Plugins.dat** ở đường dẫn giống nhau. Nếu công cụ đóng gói **chỉ giữ một descriptor** và bỏ các descriptor còn lại, một số plugin sẽ biến mất dù các class vẫn tồn tại. Cần dùng chiến lược **merge/transform descriptor thích hợp với phiên bản Log4j và công cụ build**, rồi kiểm thử artifact đã đóng gói; không đơn thuần copy một file và xóa tất cả file trùng.

**Nếu chạy native image:** annotation processor đăng ký plugin cho JVM chưa đủ cho mọi trường hợp. Kiểm tra thêm GraalVM reachability metadata do Log4j hỗ trợ và cấu hình native image của ứng dụng.

**Nếu chạy OSGi:** cơ chế discovery có thể tính đến descriptor trong bundle đang hoạt động; phải kiểm thử vòng đời bundle và thứ tự tải plugin riêng.

## 12. Plugin Lookups, PatternConverter và những khác biệt quan trọng

Một plugin **Lookup** thường triển khai **StrLookup** với category **StrLookup.CATEGORY**. Nó không nhất thiết là một thẻ XML Core. Lookup dùng cơ chế nội suy để lấy giá trị theo tiền tố và ngữ cảnh; phải hiểu chỗ nào được đánh giá khi **đọc cấu hình** và chỗ nào được đánh giá theo **LogEvent**.

Một plugin **PatternConverter** bổ sung một conversion token cho **PatternLayout**. Nó khác Lookup: PatternConverter được dùng khi layout format log event, và một số converter có thể tối ưu để giảm cấp phát bộ nhớ. Không chọn Lookup chỉ để thay thế mọi conversion token; hiệu năng và ngữ nghĩa có thể khác nhau.

Plugin **Appender** thường phức tạp hơn Filter vì phải quản lý I/O, lỗi ghi, tài nguyên và lifecycle. Nếu chỉ muốn đổi format Console, bắt đầu bằng **PatternLayout** hoặc encoder có sẵn thay vì viết một Appender mới.

Plugin **TypeConverter** phục vụ biến đổi thuộc tính cấu hình được đọc thành kiểu của Java factory/builder; nó không phải chức năng chuyển LogEvent sang JSON. Chọn đúng extension point giúp plugin có trách nhiệm rõ ràng và dễ kiểm thử.

## 13. Những lỗi dễ gặp khi viết plugin

| Triệu chứng | Nguyên nhân thường gặp | Cách xử lý |
| --- | --- | --- |
| Log4j báo không biết tên plugin | Thiếu descriptor hoặc plugin JAR không ở runtime | Kiểm tra PluginProcessor, Log4j2Plugins.dat và classpath |
| Có class nhưng XML không dùng được | Thiếu @Plugin hoặc category/name không khớp | Kiểm tra annotation và tên thẻ XML |
| Plugin được tìm thấy nhưng không khởi tạo | Thiếu @PluginFactory/@PluginBuilderFactory cho plugin Core trong cấu hình | Kiểm tra static factory/builder và validation |
| Factory nhận null dù XML có giá trị | Sai tên @PluginAttribute, cấu hình sai hoặc converter không phù hợp | Đối chiếu đúng tên thuộc tính/kiểu |
| Filter custom không loại log | Gắn sai stage, override sai overload hoặc trả NEUTRAL | Kiểm tra vị trí Filter và filter(LogEvent)/overload tương ứng |
| DEBUG không xuất dù Filter cho qua | Root/Logger level ở INFO | Kiểm tra level trước Filter/Appender |
| Plugin chạy trong IDE nhưng mất khi deploy | Đóng gói bỏ descriptor hoặc JAR | Kiểm tra artifact cuối và classpath chạy thật |
| Plugin biến mất trong fat JAR | Nhiều Log4j2Plugins.dat không được merge | Dùng cách merge descriptor và kiểm thử sau package |
| Log xuất hai lần | Additivity hoặc nhiều AppenderRef | Kiểm tra cấu trúc Loggers/Appenders |
| Trùng tên plugin | Plugin collision trong cùng category | Dùng tên riêng, xem warning về discovery |
| Tùy chỉnh package scanning không hiệu quả | Dựa vào API discovery đã deprecated | Ưu tiên annotation processor |
| Ứng dụng dùng SLF4J + backend khác | Cấu hình Log4j Core không phải đường thực tế | Xác định logging provider/backend trước |
| Custom Appender làm request chậm | I/O đồng bộ, retry hoặc lock trong append | Thiết kế backpressure, timeout và shutdown |
| Filter tạo log đệ quy | Plugin gọi lại cùng pipeline | Bỏ logging nội bộ trên đường filter hoặc dùng cơ chế chẩn đoán thích hợp |
| Plugin không chạy trong native image | Thiếu metadata/reflection config | Kiểm tra GraalVM reachability và build native |

### Kiểm tra theo thứ tự nào?

1. Đảm bảo ứng dụng thực sự dùng **Log4j Core** làm backend.
2. Đảm bảo plugin JAR và **log4j-core** ở runtime classpath, đúng version tương thích.
3. Xem có **Log4j2Plugins.dat** trong output build/JAR không.
4. Kiểm tra **@Plugin name/category**, factory/builder và thuộc tính cấu hình.
5. Kiểm tra tệp **log4j2.xml** có được nạp và thẻ plugin nằm đúng vị trí không.
6. Xem **Status Logger** để biết lỗi discovery, tạo plugin hoặc conversion.
7. Gửi các bản ghi thử ở nhiều level, gồm trường hợp phải bị lọc và trường hợp phải được giữ.
8. Kiểm thử artifact đóng gói, không chỉ đường chạy trong IDE.

Nếu đang dùng Maven, lệnh:

~~~bash
mvn dependency:tree
~~~

giúp thấy phiên bản **log4j-api**, **log4j-core**, adapter SLF4J và các thư viện mang plugin. Tránh trộn Log4j 2.x với API/plugin annotation của Log4j 3.x vì có khác biệt về cấu trúc phiên bản.

## 14. Plugin và cấu hình động: điều cần kiểm thử

Log4j 2 có thể hỗ trợ tái cấu hình tùy cơ chế configuration và môi trường. Khi cập nhật cấu hình, instance plugin mới có thể được dựng, instance cũ cần được dừng/dọn theo vòng đời.

Đối với plugin có trạng thái:

- Không giữ một connection static mà mọi instance mới đều tranh quyền đóng.
- Dùng concurrency control thích hợp nếu Filter/Appender có state.
- Đảm bảo **start/stop** và shutdown không làm thất thoát log ngoài chính sách được chấp nhận.
- Kiểm tra khi configuration reload lỗi: ứng dụng giữ cấu hình cũ hay dùng fallback, điều gì xảy ra với log quan trọng?
- Không giả định một plugin được đăng ký trong JVM đồng nghĩa sẽ hoạt động trên mọi LoggerContext/ClassLoader ở môi trường đa module.
- Với multi-tenant hoặc môi trường cô lập, tránh cache dữ liệu ngữ cảnh sai phạm vi.

Đối với plugin không có state như Filter so sánh chuỗi trong demo, việc giữ trường **messageToExclude** là bất biến giúp dễ kiểm thử hơn. Tuy vậy, nhiều thread có thể đi qua cùng instance nên mọi sửa đổi tương lai vẫn cần đánh giá thread-safety.

## 15. Kiểm thử plugin trước khi triển khai

Một test plugin có ý nghĩa nên bao gồm **mã nguồn, cấu hình và packaging**, không chỉ gọi trực tiếp factory rồi kiểm tra return value.

**Kiểm thử đơn vị:**

- Factory nhận đúng **message** và trả instance.
- Giá trị rỗng được xử lý đúng chính sách.
- **health.ping** trả DENY.
- **order.accepted** trả NEUTRAL.
- Có sự kiện lỗi như **health.failed** thì không bị loại nhầm.

**Kiểm thử tích hợp:**

- Đặt **log4j2.xml** vào classpath thực.
- Bật log mức INFO/WARN và kiểm tra output của Appender.
- Kiểm tra không xuất DEBUG khi Root level INFO.
- Thử một plugin thiếu/không khởi tạo và xác nhận hệ thống phát tín hiệu cấu hình lỗi có thể quan sát được.
- Chạy sau khi build/package để kiểm chứng metadata descriptor không bị mất.

**Kiểm thử phi chức năng:**

- Throughput khi số lượng event lớn.
- CPU và memory allocation trong Filter.
- Thread-safety khi nhiều Logger phát đồng thời.
- Chi phí mỗi event nếu phải format message sớm.
- Tác động khi reload configuration và shutdown.
- Khả năng giữ log quan trọng và bảo vệ dữ liệu nhạy cảm.

Không đo benchmark logging chỉ bằng một lần chạy vài dòng: cần làm nóng JVM, xem overhead encoder/IO/backend và đo trên cấu hình gần production.

## 16. Những câu hỏi hay gặp

### Plugin Log4j2 có phải Java ServiceLoader provider không?

Không phải cùng một khái niệm. **PluginManager/PluginProcessor/Log4j2Plugins.dat** là cơ chế đăng ký thành phần mở rộng của **Log4j Core**. **SLF4J provider** là cơ chế nối facade SLF4J 2.x tới một implementation logging; đó là vai trò khác.

### Có thể tạo plugin chỉ bằng cách thả JAR vào thư mục không?

Chỉ khi JAR có class và descriptor phù hợp, JAR thực sự có trên runtime classpath/bundle được Log4j tải và cấu hình tham chiếu đúng plugin. Chỉ tồn tại tệp JAR trên ổ đĩa không đồng nghĩa nó đã được classloader tải và discovery.

### @Plugin với @PluginFactory khác nhau thế nào?

**@Plugin** công bố loại, tên/category. **@PluginFactory** cho Core plugin trong cấu hình biết **tạo instance như thế nào** và nhận các thuộc tính/nút con. Hai annotation phối hợp với annotation processor để cấu hình chạy được. Không phải mọi category plugin đều cần một factory theo cùng quy tắc Core.

### NEUTRAL có nghĩa chấp nhận chắc chắn không?

Không. Nó có nghĩa **Filter đó không quyết định từ chối hoặc chấp nhận dứt khoát** và để pipeline tiếp tục đánh giá. Bản ghi vẫn có thể bị level, Filter khác hoặc Appender từ chối.

### Khi nào dùng @PluginBuilderFactory?

Khi thành phần có nhiều thuộc tính, default, nested plugin, validation và vòng đời đáng kể. Một Builder giúp cấu hình rõ ràng và thuận tiện cho test. Với Filter một thuộc tính, **@PluginFactory** thường đủ.

### Tại sao plugin chạy trên JDK 17 nhưng không được tìm thấy khi nâng JDK?

Hãy kiểm tra **annotation processing**. Một số toolchain/JDK mới không tự chạy processor nếu chưa cấu hình tường minh. Kiểm tra metadata sau compile và khai báo **PluginProcessor** ở build, không dựa vào quét package đã deprecated.

### Có nên viết plugin để loại bỏ toàn bộ log từ một package không?

Thông thường không cần plugin mới. Có thể cấu hình mức log cho **LoggerConfig** theo tên package và additivity, hoặc dùng các Filter tích hợp. Viết plugin khi cần chính sách đặc thù mà cấu hình có sẵn chưa đáp ứng được.

### Plugin có quyền truy cập dữ liệu nhạy cảm trong LogEvent không?

Tùy vị trí và API, plugin có thể nhận message, Throwable và context data. Điều này cần được xem như một thành phần tin cậy của pipeline: kiểm soát dependency, input, quyền truy cập, dữ liệu đầu ra và tính an toàn khi log dữ liệu chưa được làm sạch.

## 17. Checklist tạo plugin Log4j2

1. Xác định **mục tiêu chức năng**; thử plugin tích hợp sẵn trước.
2. Chọn **extension point đúng**: Filter, Appender, Layout, Lookup, Converter hay Policy.
3. Đặt tên **@Plugin** rõ ràng, duy nhất trong category; dùng category chính xác.
4. Với plugin Core xuất hiện trong cấu hình, cung cấp **@PluginFactory** hoặc **@PluginBuilderFactory**.
5. Nhận giá trị qua **@PluginAttribute**, **@PluginElement** và validation khi phù hợp.
6. Bật **PluginProcessor**; xác nhận có **Log4j2Plugins.dat** sau build.
7. Bảo đảm class và descriptor đi cùng **JAR trên runtime classpath**; kiểm tra shaded JAR và native image nếu có.
8. Gắn plugin đúng vị trí trong cấu hình; phân biệt **Logger, AppenderRef, Appender** và các stage Filter.
9. Thiết kế thread-safety, hiệu năng, lifecycle, bảo mật, error handling và chính sách logging rõ ràng.
10. Thử cả trường hợp **phải nhận, phải bỏ, lỗi cấu hình, khác level, đa luồng và artifact cuối**.

**Kết luận:** **Plugin của Log4j2** là cơ chế mở rộng Log4j Core thông qua **annotation, descriptor và factory/builder**, giúp đưa thành phần tùy chỉnh vào cấu hình mà không sửa Log4j. Hãy ưu tiên plugin chuẩn khi đủ dùng; nếu cần tạo plugin mới, phải hiểu **discovery lúc build, stage trong pipeline, cách đóng gói và khả năng kiểm thử** để không làm mất log hoặc tạo lỗi vận hành khó phát hiện.
