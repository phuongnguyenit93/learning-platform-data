# What Is SLF4J? A Logging Facade in Java

## 1. Concept and Purpose

**SLF4J** stands for **Simple Logging Facade for Java**. It is a **logging facade (intermediate API layer)** that allows Java code to record events through unified interfaces without depending directly on a specific log output mechanism. Familiar components include `org.slf4j.Logger`, `org.slf4j.LoggerFactory`, and `org.slf4j.MDC`.

For example, a service class only needs to know how to call:

~~~java
// Illustration in a project that already has the SLF4J dependency.
private static final org.slf4j.Logger LOG =
        org.slf4j.LoggerFactory.getLogger(OrderService.class);

LOG.info("operation=checkout orderId={} outcome={}", orderId, "success");
~~~

The `LOG.info(...)` statement indicates that there is an event to record. Whether that event appears in the **console, a file, JSON, or a centralized system**, which levels are accepted, how it is formatted, and how files are rotated are primarily determined by the **logging provider/backend** and its corresponding configuration.

Distinguish these roles from the start:

- **SLF4J API:** where application code calls `trace`, `debug`, `info`, `warn`, `error`, checks log levels, writes parameterized logs, and uses MDC.
- **Provider/backend:** the implementation behind the API, such as Logback, Log4j 2 when connected via the proper adapter, or a simple provider. The backend handles level filtering, encoding, and emitting records through appenders/handlers.
- **Appender/handler:** the component that pushes events to a destination, such as stdout, a file, or a collector; component names and configuration vary by backend.

**SLF4J is not a standalone file-writing system, is not a centralized log collection tool, and is not built into the JDK.** Adding `slf4j-api` alone does not guarantee that the application already has a place to output logs.

## 2. Why Do We Need a Facade?

A Java application typically consists of many components developed by different teams. If each library forced the program to use a specific logging API, the application would struggle to unify configuration and could produce multiple separate log outputs. SLF4J provides a common call point:

~~~text
Application / library code
        |
        v
     SLF4J API
  (Logger, LoggerFactory,
   levels, placeholders, MDC)
        |
        v
   SLF4J provider / adapter
        |
        v
 Logging backend
 (e.g., Logback)
        |
        v
Appender -> console / file / collector
~~~

The diagram illustrates a case where an application uses SLF4J with a provider. A provider can be both an implementation and a forwarder to another logging framework; not every block is always a separate library.

**Practical benefits:**

1. **Decoupling code from the backend:** business classes use `org.slf4j.Logger`; when changing how logs are emitted, you mostly swap dependencies, update configuration, and test compatibility instead of editing every `info`/`warn` call.
2. **Consistent calling convention:** the project shares a class-based logger convention, common levels, and `{}` placeholder syntax.
3. **Centralized configuration:** operations teams can choose INFO/DEBUG thresholds, appenders, encoders, retention, and other properties according to the backend in use.
4. **Suitable for reusable libraries:** a library can depend on the SLF4J API, leaving the host application to decide the actual provider.
5. **Support for parameterized messages and context:** avoids unnecessary manual string concatenation and attaches request IDs, trace IDs, or intentional diagnostic fields.

A facade **does not guarantee** that swapping backends is completely equivalent: log levels, configuration, JSON encoders, async logging, MDC, and exception rules can differ across implementations. The shared API reduces coupling at the call sites, while operational behavior still requires testing.

## 3. Core Concepts

### 3.1. Logger and LoggerFactory

`Logger` is the interface for emitting events. `LoggerFactory` obtains a logger by name or by class:

~~~java
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public class CheckoutService {
    private static final Logger LOG =
            LoggerFactory.getLogger(CheckoutService.class);

    public void checkout(String orderId, int itemCount) {
        LOG.info("checkout started orderId={} itemCount={}",
                orderId, itemCount);
    }
}
~~~

This is a snippet in a project that already has SLF4J; it compiles when the dependency is provided. Declaring `private static final` keeps a single stable logger per class rather than recreating it on every request. Naming the logger after the class makes it easy to filter or change the log level for a specific package in the backend.

Application code should not create a new logger just to write a single line, and should not use `System.out.println(...)` as a replacement for all logging in a production system.

### 3.2. Log Levels

SLF4J has five common levels:

| Level | Primary Purpose | Examples |
| --- | --- | --- |
| `TRACE` | Detailed trace of each execution step | Conditional branches, selected intermediate values |
| `DEBUG` | Technical information for debugging | Cache miss, retry decision, component state |
| `INFO` | Meaningful operational milestones | Task completed, application ready |
| `WARN` | Abnormal situation, but execution can continue | Fallback triggered, retry attempt |
| `ERROR` | Important operation failed | Request could not be processed, data could not be saved |

Typically, setting the logger threshold to `INFO` drops `TRACE` and `DEBUG` events, while `INFO`, `WARN`, and `ERROR` pass the logger threshold. **Whether an event is actually emitted still depends on filters, appenders, and provider configuration.** Classifying a situation as WARN or ERROR should be based on actual impact, not merely on the presence of an exception.

### 3.3. Placeholders and Parameterized Messages

An obvious advantage of SLF4J is the **`{}` placeholder**:

~~~java
// Illustration: variables orderId, itemCount, durationMs are already defined.
LOG.info("operation=checkout orderId={} itemCount={} durationMs={}",
        orderId, itemCount, durationMs);
~~~

The logger receives the template and the arguments. The backend can format the message as:

~~~text
operation=checkout orderId=O-17 itemCount=3 durationMs=12
~~~

The line above is an **illustrative message body**, excluding the timestamp, log level, thread, and logger name added by the layout. SLF4J's `{}` placeholder differs from `{0}` in `java.util.logging` and `%s` in `String.format`. Do not mix syntaxes across APIs.

Prefer keeping templates stable, with clear field names and units such as `durationMs` and `sizeBytes`. Messages like `"value={} {}"` are hard to interpret during later investigation.

**Cost note:** even though SLF4J can skip formatting the message when a log level is disabled, Java still evaluates argument expressions before the method call. For example, `LOG.debug("data={}", expensiveDescription())` still calls `expensiveDescription()` even when DEBUG is disabled. Appropriate ways to defer evaluation are covered in section 7.

### 3.4. Logger Is the API; the Provider Decides Output

There is no universal SLF4J API syntax to specify which log file must be created, what rotation size to use, or what timestamp pattern to apply. These are configured per backend, such as `logback.xml` for Logback or `log4j2.xml` for Log4j 2.

Consequently, two applications can run the exact same `LOG.info("...")` line yet produce different outputs due to different log levels, providers, encoders, or output destinations. When logs disappear, check both whether **the API has a suitable provider** and the filtering configuration.

## 4. Relationship Between SLF4J, Logback, Log4j 2, and java.util.logging

Similar library names can easily cause confusion:

| Component | Role | Built into JDK? |
| --- | --- | --- |
| **SLF4J API** | Facade and interfaces called by application code | No |
| **Logback Classic** | Backend with an SLF4J provider, providing loggers/appenders/encoders | No |
| **Log4j 2** | Logging framework with its own API/Core; has an adapter to act as an SLF4J provider | No |
| **`java.util.logging` (JUL)** | Standard logging API and implementation in the JDK | Yes |
| **`slf4j-simple`** | Simple SLF4J provider, useful for examples and small applications | No |

You should not write "SLF4J = Logback". They are often used **together**, but their roles are distinct. An application can use the SLF4J API and choose another compatible provider. If a third-party library uses JUL or the Log4j 2 API directly, the application may need a **bridge** to unify the log stream (see section 9).

### Why Let the Host Application Choose the Provider?

A **reusable Java library** should declare a dependency on the appropriate logging API and avoid forcing every application to use a backend chosen by the library. At the final application layer, select **one suitable SLF4J provider** and configure operations as needed.

If every dependency brings its own provider, the application may end up with multiple competing providers. SLF4J 2.x typically warns about this situation and picks one of the discovered providers; you should not rely on classpath order to predict which provider will win.

## 5. Runnable Example: Java 17 + Maven + SLF4J + Logback

Because `org.slf4j.*` is not part of the JDK, running a real program requires adding dependencies. The example below uses **SLF4J API 2.0.17** and **Logback Classic 1.5.18** as illustrative versions compatible with Java 17. These are concrete versions for reproducing the exercise, **not a claim that they are the latest versions**. In a real project, use versions approved by your dependency management system or project update policy.

Structure:

~~~text
slf4j-intro/
  pom.xml
  src/main/java/example/Slf4jIntroDemo.java
  src/main/resources/logback.xml
~~~

### 5.1. Create pom.xml

~~~xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0
             https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>
    <groupId>example</groupId>
    <artifactId>slf4j-intro</artifactId>
    <version>1.0.0</version>

    <properties>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    </properties>

    <dependencies>
        <dependency>
            <groupId>org.slf4j</groupId>
            <artifactId>slf4j-api</artifactId>
            <version>2.0.17</version>
        </dependency>
        <dependency>
            <groupId>ch.qos.logback</groupId>
            <artifactId>logback-classic</artifactId>
            <version>1.5.18</version>
        </dependency>
    </dependencies>

    <build>
        <plugins>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-compiler-plugin</artifactId>
                <version>3.13.0</version>
                <configuration>
                    <release>17</release>
                </configuration>
            </plugin>
            <plugin>
                <groupId>org.codehaus.mojo</groupId>
                <artifactId>exec-maven-plugin</artifactId>
                <version>3.5.0</version>
                <configuration>
                    <mainClass>example.Slf4jIntroDemo</mainClass>
                </configuration>
            </plugin>
        </plugins>
    </build>
</project>
~~~

`slf4j-api` provides `Logger` and `LoggerFactory`; `logback-classic` provides the SLF4J provider and the backend to emit events. Declaring `logback-classic` also pulls in the required libraries via Maven transitive dependencies. The example lists both dependencies to show each side's role; in larger applications, use a BOM/dependency management where appropriate and avoid declaring mismatched versions.

### 5.2. Create Slf4jIntroDemo.java

~~~java
package example;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public final class Slf4jIntroDemo {
    private static final Logger LOG =
            LoggerFactory.getLogger(Slf4jIntroDemo.class);

    private Slf4jIntroDemo() {
    }

    public static void main(String[] args) {
        String orderId = "O-17";
        int itemCount = 3;

        LOG.debug("step=validate orderId={} itemCount={}",
                orderId, itemCount);
        LOG.info("operation=checkout orderId={} itemCount={}",
                orderId, itemCount);

        int total = itemCount * 10;
        LOG.info("operation=checkout outcome=success total={}", total);
    }
}
~~~

The logger is created by class name. With the root threshold set to INFO in the configuration below, the `DEBUG` line is filtered out and the two `INFO` lines appear. The program does not call `System.out.println`: the lines are written through SLF4J and then Logback.

### 5.3. Create logback.xml

~~~xml
<configuration>
    <appender name="STDOUT"
              class="ch.qos.logback.core.ConsoleAppender">
        <target>System.out</target>
        <encoder>
            <pattern>%level %msg%n</pattern>
        </encoder>
    </appender>

    <root level="INFO">
        <appender-ref ref="STDOUT"/>
    </root>
</configuration>
~~~

This file is placed at `src/main/resources/logback.xml` so that it appears on the runtime classpath. `ConsoleAppender` writes to stdout, the `%level %msg%n` pattern prints the log level, message text, and a newline, and the root level INFO filters out DEBUG in the example.

### 5.4. Run the Program

From the `slf4j-intro` directory, using JDK 17+ and Maven:

~~~bash
mvn -q compile exec:java
~~~

The two **application log lines on stdout** under the illustrative configuration:

~~~text
INFO operation=checkout orderId=O-17 itemCount=3
INFO operation=checkout outcome=success total=30
~~~

There is no DEBUG line. Maven or internal logging may emit additional tool messages depending on the environment, but the application output according to the declared pattern consists of the two lines above.

If you change `<root level="INFO">` to `<root level="DEBUG">` and run it again, the `step=validate...` line will appear before the two INFO lines. If you change `<target>System.out</target>` or the pattern, the output also changes even though **the Java code does not change**.

**Correctness check:** `3 × 10 = 30`; package name `example` matches the path `src/main/java/example/Slf4jIntroDemo.java`; Maven compiler declares Java 17; `{}` templates have the exact number of arguments; `logback.xml` defines one appender and one root logger referencing that appender.

## 6. Logging Messages, Exceptions, and Context

### 6.1. Logging Exceptions While Preserving the Stack Trace

With SLF4J, pass the `Throwable` using the appropriate overload:

~~~java
// Illustrative snippet inside a catch block; LOG is an SLF4J Logger.
try {
    loadOrder(orderId);
} catch (java.io.IOException e) {
    LOG.error("operation=loadOrder orderId={} outcome=failed",
            orderId, e);
    throw e;
}
~~~

This is a **non-standalone snippet**: `loadOrder`, `orderId`, `LOG`, and the enclosing method's `throws IOException` declaration must exist. In SLF4J's parameterized logging convention, a trailing `Throwable` is normally recognized as the event's exception rather than a value requiring an extra `{}`. A compatible backend can print the stack trace and `Caused by` chain.

You can also write:

~~~java
LOG.error("Load order failed", e);
~~~

Do not just log `LOG.error("Failed: {}", e.getMessage())` and treat it as sufficient: that only records the exception message without attaching the `Throwable` object for the backend to display the stack trace. If the service layer wraps an exception with `new IllegalStateException("...", e)`, the original cause is preserved.

**Do not log ERROR at every layer and rethrow** if an upper layer is already responsible for logging the same failure; duplicate records create noise and waste resources. Choose an appropriate logging boundary, enrich the exception with needed details, and preserve the cause.

### 6.2. MDC and Correlation IDs

SLF4J provides **MDC (Mapped Diagnostic Context)** to attach contextual information to logs. Basic usage:

~~~java
// Illustrative snippet while handling a single request.
import org.slf4j.MDC;

MDC.put("requestId", requestId);
try {
    LOG.info("operation=checkout started");
    performCheckout();
} finally {
    MDC.remove("requestId");
}
~~~

This snippet is inside a scope where `LOG`, `requestId`, and `performCheckout` exist; it is not a standalone program. The `finally` block prevents leaking the previous request's context onto a reused thread.

For MDC values to actually appear in Logback console output, the pattern configuration can include:

~~~xml
<pattern>%level requestId=%X{requestId} %msg%n</pattern>
~~~

MDC is a useful context mechanism, but it **does not automatically propagate values across thread pools, `CompletableFuture`, or asynchronous boundaries**. Context propagation depends on the framework, provider, and execution model. Some backends do not support MDC in the same way; do not assume calling `MDC.put` will produce data in the output if the backend does not use that context.

### 6.3. SLF4J 2.x Fluent API

SLF4J 2.x supports a fluent style:

~~~java
// Illustration in a class that already has Logger LOG, orderId, and durationMs.
LOG.atInfo()
   .addKeyValue("operation", "checkout")
   .addKeyValue("orderId", orderId)
   .addKeyValue("durationMs", durationMs)
   .log("Checkout completed");
~~~

This style lets you pass key/value fields along with the event. **Do not confuse the key/value API with getting JSON automatically.** The provider and layout/encoder must support it and be configured to emit fields in the desired format. A plain text layout using only `%msg` may not display all additional key/value pairs.

The SLF4J facade operates at the API layer. If you want structured JSON logging, indexing, retention, or cross-service tracing, you must configure or add the supporting components outside the API.

## 7. Performance: Parameterized Logging and Lazy Evaluation

Suppose a method that builds an object description is very expensive:

~~~java
// Illustration: expensiveDescription(order) builds a string solely for logging.
LOG.debug("order={}", expensiveDescription(order));
~~~

**Important:** Java evaluates `expensiveDescription(order)` before calling `LOG.debug`, even if the logger is not accepting DEBUG. SLF4J defers rendering the message with placeholders, but it does not automatically defer argument expressions.

When computing the message is expensive, you can guard it:

~~~java
if (LOG.isDebugEnabled()) {
    LOG.debug("order={}", safeDescription(order));
}
~~~

In SLF4J 2.x, you can use a `Supplier` with the fluent API:

~~~java
LOG.atDebug()
   .addArgument(() -> safeDescription(order))
   .log("order={}");
~~~

Both snippets are **illustrative code** in a class that already has `LOG`, `order`, and the data-formatting function. `safeDescription` must have no side effects and only access data permitted for logging. The lambda avoids building the description when DEBUG is disabled; when DEBUG is enabled, building the message and writing the log still consume CPU, memory, and I/O.

For simple arguments that are already available, such as `int count` or `String orderId`, direct placeholders are usually enough. Avoid cluttering code with guards on every minor line. Optimize based on log frequency, message construction cost, and measurements under a realistic workload.

Additional points to remember:

- Logging inside hot loops can emit thousands or millions of records.
- Console, file, and network targets all incur I/O; an async appender can offload cost to a queue, though it still carries the risk of blocking or dropping events when full.
- Measure CPU, allocations/GC, bytes/s, throughput, and p95/p99 latency when changing log levels or backends.
- Parameterized messages do not automatically mask passwords, tokens, or personal data, nor do they automatically protect against newlines in untrusted input. Choose safe fields and an appropriate encoder.

## 8. Dependencies and Providers in SLF4J 2.x

### 8.1. You Need Both the Right API and a Provider

In a program using SLF4J, dependencies can flow as follows:

~~~text
Application source
  -> slf4j-api 2.x
  -> compatible SLF4J 2.x provider
  -> log output backend
~~~

For Logback Classic, the provider is supplied by Logback itself. For Log4j 2, the corresponding adapter/provider is supplied by the appropriate module; for JUL, there is a dedicated provider such as `slf4j-jdk14` to forward SLF4J calls to JUL.

**SLF4J 2.x uses a provider mechanism via Java `ServiceLoader`.** SLF4J 1.7-era bindings using `StaticLoggerBinder` are not compatible provider mechanisms for the 2.x API. When upgrading, check that the API and provider versions belong to compatible branches rather than keeping old dependencies just because their names look familiar.

### 8.2. No Provider Found

If only `slf4j-api` is present without a compatible provider, SLF4J 2.x may emit a startup diagnostic such as **"No SLF4J providers were found"** and fall back to a no-operation (**NOP**) logger that emits nothing. The Java program can still execute its business logic normally, but `LOG.info(...)` messages may not appear anywhere. Do not treat "no logs seen" as proof that a method did not run.

In that case, inspect the application's runtime dependencies and ensure the provider is on the **runtime classpath**, not only on the test classpath or compile classpath of another module.

### 8.3. Multiple Providers

When multiple providers are discovered simultaneously, SLF4J may warn and pick one of them. This leads to unexpected output or configuration. Do not rely on classpath order. Choose one primary provider, exclude redundant backend dependencies, and inspect the transitive dependency tree.

For example, a situation to avoid accidentally: having both the Logback provider and `slf4j-simple` on the runtime classpath at the same time. For a small demo, one provider is enough.

### 8.4. How to Inspect Dependencies

With Maven, you can inspect:

~~~bash
mvn dependency:tree
~~~

With Gradle, refer to:

~~~bash
./gradlew dependencies --configuration runtimeClasspath
~~~

On Windows, you can use `gradlew.bat` instead of the Unix script in projects with the Gradle Wrapper. These commands do not replace checking logs at runtime: a library may appear with the right name while its version, provider, or configuration is still incompatible.

## 9. Bridges and Adapters: Unifying Log Sources

An application may depend on libraries that use different logging APIs. A bridge **redirects records from a source API to another API/target** so that logging policy and collection remain unified.

General examples:

| Module | Redirection Direction | Scenario |
| --- | --- | --- |
| `jul-to-slf4j` | JUL -> SLF4J | A library using `java.util.logging` needs to route through the shared provider |
| `log4j-to-slf4j` | Log4j 2 API -> SLF4J | A library calls the Log4j 2 API, while the application uses another SLF4J provider |
| `slf4j-jdk14` | SLF4J -> JUL | You want JUL as the backend for SLF4J calls |
| `log4j-slf4j2-impl` | SLF4J 2.x -> Log4j 2 | You want Log4j 2 as the backend for an application using SLF4J 2.x |

**Do not combine two adapters in opposite directions to form a loop.** For example:

- `jul-to-slf4j` together with `slf4j-jdk14` risks creating a JUL -> SLF4J -> JUL route.
- `log4j-to-slf4j` together with `log4j-slf4j2-impl` risks creating a Log4j 2 -> SLF4J -> Log4j 2 route.

This is a logging architecture bug, not just a cosmetic warning; it can cause forwarding loops or broken behavior. Identify the **final destination backend**, then keep only bridges pointing in one direction toward that destination. For the JUL bridge, installing the handler and removing old handlers must follow the module's documentation; simply adding the JAR is not always enough to route all JUL events.

Some applications using large frameworks already have logging and dependencies configured for you. In that case, check the mechanism provided by the framework before adding providers or bridges manually.

## 10. SLF4J and Structured Logging / Tracing

### 10.1. Parameterized Text Is Not Automatically Structured Data

~~~java
LOG.info("operation=checkout durationMs={} status={}", 35, "success");
~~~

The message above has a readable structure, but the backend may still store only a single `message` string. True structured logging typically requires an encoder/layout that stores separate fields with appropriate types, for example:

~~~json
{
  "level": "INFO",
  "operation": "checkout",
  "durationMs": 35,
  "status": "success"
}
~~~

This is **illustrative JSON data**, not output automatically generated by the `LOG.info` call above. SLF4J 2.x has a key/value API, but printing or storing it as JSON is still determined by the backend and encoder.

### 10.2. SLF4J Does Not Replace Distributed Tracing

In microservices systems, distributed tracing uses trace/span IDs to follow a request across multiple services. SLF4J is a logging API; it can include `traceId` and `spanId` in logs when an appropriate tool creates and propagates that context, but `LOG.trace(...)` by itself does not create a distributed trace.

A line at the `TRACE` level is simply detailed logging; a record carrying a `traceId` can have level `INFO` or `ERROR`. Do not conflate the two meanings of the word "trace".

## 11. Common Mistakes When Using SLF4J

| Symptom / Mistake | Common Cause | How to Fix |
| --- | --- | --- |
| `slf4j-api` is present, but no logs appear | Missing compatible provider, NOP, wrong threshold, or wrong target | Check runtime classpath, provider, and configuration |
| Multiple provider warnings | Competing providers or transitive dependencies | Choose one primary provider and exclude extras |
| Using 1.7 bindings with 2.x API | Different discovery mechanism; incompatible provider | Use a provider that supports SLF4J 2.x |
| Writing `{0}` instead of `{}` | Mixing JUL and SLF4J syntax | Use the API's correct placeholder |
| String concatenation at DEBUG level | String construction cost occurs even when log level is off | Use placeholders, guards, or `Supplier` when needed |
| Logging only `e.getMessage()` | No `Throwable` passed for the backend to print the stack trace | Pass the exception using the proper overload |
| Logging ERROR and rethrowing at every layer | Multiple records for a single error | Choose a single layer responsible for logging |
| MDC from a previous request appears in the next | MDC not cleared when using a thread pool | Clear MDC in `finally` or an appropriate scope |
| Using key/value API but seeing no JSON | Encoder does not emit fields as expected | Configure a supporting backend/encoder |
| Adding bidirectional bridges | Circular log routing, abnormal behavior | Use adapters pointing one way toward the final backend |
| Printing entire sensitive objects | Data leaks and log bloat | Select safe fields, limit length, and escape output |

Good application logging also requires **observing from an operator's perspective**: which logs are enough to distinguish failures, which are just noise, which must be retained, and who is permitted to read them. SLF4J provides the API, while log-level policies, retention, access control, and data governance must be designed by the application and operations system.

## 12. Checklist for Adopting SLF4J in a Project

1. **Choose a unified API:** application and library code call `org.slf4j.Logger` when it fits the architecture.
2. **Choose a compatible provider:** place one valid provider on the runtime classpath; manage versions via Maven/Gradle and inspect the dependency tree.
3. **Configure the backend:** package/root levels, appenders, layouts/encoders, file/console targets, and rotation/retention if needed.
4. **Create loggers per class:** use `LoggerFactory.getLogger(SomeClass.class)`, typically `private static final`.
5. **Write meaningful messages:** use `{}`, fields like `operation`, `requestId`, `outcome`, and units of measurement; avoid logging large objects.
6. **Preserve `Throwable`:** when reporting errors, pass the exception through the proper API so the backend has the stack trace/cause; avoid duplicate logging.
7. **Clean up context:** use MDC sensibly, clear it in `finally`, and propagate context across async tasks properly.
8. **Check performance/security:** reduce logging on hot paths, use `Supplier` for expensive data, strip secrets, escape input, and measure log volume.
9. **Test actual output:** run at least one INFO case, one filtered DEBUG case, and one exception case; verify destination, format, and diagnostic completeness.
10. **Audit bridges:** list JUL/Log4j libraries and select only adapters pointing in the right direction so no loops form.

**Key takeaway:** **SLF4J is an intermediate logging API layer**, not a backend and not part of the JDK. Java code calls `Logger` in a unified way; the **provider/backend** determines processing and log output destinations. Choose one compatible provider, configure levels and output clearly, use placeholders and `Throwable` properly, and manage sensitive data, MDC, and bridges so that logs are both useful and reliable.
