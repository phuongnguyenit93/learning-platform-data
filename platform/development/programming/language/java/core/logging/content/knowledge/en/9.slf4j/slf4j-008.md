# Multiple Bindings in SLF4J: Causes, Diagnosis, and Resolution

## 1. Understanding the Problem

**Multiple bindings** is a situation where the runtime classpath contains **multiple implementations connecting the SLF4J API to a logging backend**. When this happens, the application may still run, but the actual logging mechanism used is no longer clearly determined by the project's intended configuration. A different backend may be selected, logs may appear in an unexpected format, desired configuration may be lost, or logs may disappear altogether if NOP is selected.

SLF4J (**Simple Logging Facade for Java**) provides a unified API for calls such as:

```java
Logger logger = LoggerFactory.getLogger(OrderService.class);
logger.info("event=order.created orderId={}", orderId);
```

This is an **illustrative code snippet**, assuming `OrderService`, `orderId`, and the SLF4J imports are already present. The SLF4J API itself is not responsible for writing logs to files or the console. **One** backend implementation must be connected at runtime.

An especially important point is that the terminology has changed across versions:

- **SLF4J 1.7.x and earlier:** uses a **binding** with the `org.slf4j.impl.StaticLoggerBinder` class. The warning is properly referred to as `multiple bindings`.
- **SLF4J 2.0.x:** uses a **provider** implementing `org.slf4j.spi.SLF4JServiceProvider`, discovered via Java `ServiceLoader`. The corresponding situation is **multiple providers**. Many teams still refer to it generically as "multiple bindings" out of habit, but the discovery mechanism and compatibility rules differ.

Choose **one backend that the application intends to use** and keep a binding/provider compatible with the `slf4j-api` version. Do not resolve the issue by silencing warnings without knowing which backend was selected.

## 2. Diagram: API, Provider, and Logging Backend

```text
Controller / Service / Repository
               |
               v
           slf4j-api
               |
               v
    One selected binding/provider
               |
        +------+-------+-----------------+
        |              |                 |
        v              v                 v
     Logback        Log4j 2            JUL
   via Logback  log4j-slf4j2-impl  slf4j-jdk14
        |              |                 |
        +--------------+-----------------+
               |
               v
        Handler / Appender / Sink
           console, file, collector
```

The diagram represents **mutually exclusive alternatives**, not that an application should load all three providers. Having multiple libraries in a project call SLF4J is normal; the conflict occurs when multiple artifacts **provide a provider/binding** at runtime.

Some common artifacts:

| Artifact | Role | Is it a direct provider/binding? |
| --- | --- | --- |
| `org.slf4j:slf4j-api` | Logging interface | No |
| `ch.qos.logback:logback-classic` | Logback backend and SLF4J integration | Yes |
| `org.slf4j:slf4j-simple` | Lightweight backend, typically logs to console | Yes |
| `org.slf4j:slf4j-nop` | Backend that discards log calls | Yes, but intentionally outputs no logs |
| `org.slf4j:slf4j-jdk14` | Routes SLF4J calls to `java.util.logging` | Yes |
| `org.slf4j:slf4j-reload4j` | Routes SLF4J to reload4j | Yes |
| `org.apache.logging.log4j:log4j-slf4j2-impl` | Provider for **SLF4J 2.x** via Log4j 2 | Yes |
| `org.apache.logging.log4j:log4j-slf4j-impl` | Binding for **SLF4J 1.7.x** via Log4j 2 | Yes, for 1.7.x |
| `org.slf4j:jul-to-slf4j` | Routes JUL logs to the SLF4J API | No; this is a reverse-direction bridge |
| `org.apache.logging.log4j:log4j-to-slf4j` | Routes Log4j API calls to SLF4J | No; not an SLF4J provider |

In particular, `slf4j-nop` **is still a provider**. If it is accidentally selected, the fact that the application prints no logs does not mean business errors have disappeared.

## 3. SLF4J 1.7: Why Do "Multiple Bindings" Occur?

SLF4J 1.7 looks for the class `org/slf4j/impl/StaticLoggerBinder.class` on the classpath. Different binding JARs can contain this exact same class path.

For example, the classpath simultaneously contains the binding from `slf4j-simple` 1.7.x and `slf4j-log4j12` or another 1.7.x binding:

```text
Application
  + slf4j-api-1.7.x.jar
  + slf4j-simple-1.7.x.jar
  + another-slf4j-1.7-binding.jar
```

The name `another-slf4j-1.7-binding.jar` here is only a diagram placeholder, not a real dependency coordinate.

The application may print warning lines like:

```text
SLF4J: Class path contains multiple SLF4J bindings.
SLF4J: Found binding in [...]
SLF4J: Found binding in [...]
SLF4J: Actual binding is of type [...]
```

This is an **illustrative message pattern**; actual JAR paths and binding types vary by classpath. SLF4J attempts to bind to one implementation rather than duplicating every event to all bindings simultaneously. The selection order is not a stable contract for an application to rely on. The same set of dependencies under different packaging, test execution, fat JAR builds, or classloaders can yield different results.

Consequence: one environment logs through backend A while another logs through backend B, leading to different levels, layouts, appenders, and output destinations. Redundant bindings must be excluded from the **final runtime artifact**.

## 4. SLF4J 2.x: "Multiple Providers" and ServiceLoader

Starting with SLF4J 2.0, `LoggerFactory` uses Java `ServiceLoader` to discover `SLF4JServiceProvider` implementations. A provider JAR declares a service provider at the path:

```text
META-INF/services/org.slf4j.spi.SLF4JServiceProvider
```

For example, the classpath includes both `slf4j-simple:2.0.x` and `slf4j-nop:2.0.x`:

```text
Application
  + slf4j-api-2.0.x.jar
  + slf4j-simple-2.0.x.jar
  + slf4j-nop-2.0.x.jar
```

SLF4J may emit a warning like:

```text
SLF4J(W): Class path contains multiple SLF4J providers.
SLF4J(W): Found provider [...]
SLF4J(W): Found provider [...]
SLF4J(I): Connected with provider of type [...]
```

This is an **abbreviated warning pattern**, not fixed program stdout. Reporter syntax/prefixes and paths may vary by version. Even though the runtime selects one provider, that selection should not be treated as a normal configuration mechanism. The ignored provider might be the very backend the application actually needs.

### 4.1. When No Compatible Provider Exists

If `slf4j-api` 2.x cannot find a 2.x provider, SLF4J emits a warning about no providers found and uses the **NOP fallback**. In that case, SLF4J calls may produce no logs, even though the Java program still runs.

Conversely, an application using `slf4j-api` 1.7.x with only a 2.x provider present will not find a valid `StaticLoggerBinder`. This is not multiple bindings, but an **API/implementation generation mismatch**.

Comparison table:

| SLF4J API | Implementation on Classpath | Behavior to Check |
| --- | --- | --- |
| 1.7.x | One compatible 1.7.x binding | Connects via `StaticLoggerBinder` |
| 1.7.x | Two 1.7.x bindings | **Multiple bindings** warning; one binding is selected |
| 2.0.x | One compatible 2.0.x provider | Connects via `ServiceLoader` |
| 2.0.x | Two 2.0.x providers | **Multiple providers** warning; one provider is selected |
| 2.0.x | Only a 1.7.x binding | Old binding is ignored; may fall back to NOP if no 2.x provider exists |
| 1.7.x | Only a 2.0.x provider | No compatible 1.7 binding; may fall back to NOP |
| 2.0.x | No provider | **No providers** warning; NOP fallback |

Do not confuse a "multiple providers" warning with a "no providers found" warning. The two problems have different fixes: the first **removes the redundant provider**; the second **adds a compatible provider**.

### 4.2. Versions Must Be Compatible

SLF4J recommends matching the provider's **major.minor** version to `slf4j-api`. For example, `slf4j-api:2.0.x` pairs with `slf4j-simple:2.0.x`; patch versions do not have to be identical, but should be managed consistently via dependency management. Upgrading only the API to 2.x while keeping a 1.7.x binding does not form a working configuration.

Source compatibility when calling `org.slf4j.Logger` does not mean providers from different generations can be mixed arbitrarily.

## 5. Real-World Causes of Multiple Providers Appearing Together

### 5.1. Adding Backends Directly Twice

For example, a project declares:

```groovy
dependencies {
    implementation 'org.slf4j:slf4j-api:2.0.20'
    runtimeOnly 'org.slf4j:slf4j-simple:2.0.20'
    runtimeOnly 'org.slf4j:slf4j-nop:2.0.20'
}
```

Both `runtimeOnly` declarations are providers for SLF4J 2.x. This is an **intentionally broken configuration to illustrate a conflict**, not a recommended setup.

### 5.2. Transitive Dependencies Pulling in a Backend

The application intends to use Logback, but a third-party library depends on `slf4j-simple`, `slf4j-reload4j`, or another backend. Because Maven/Gradle pulls in transitive dependencies, both providers can exist even if the build file only declares one provider directly.

Use the dependency tree to find **the path that pulled in the provider** instead of randomly deleting JARs. A well-behaved library using SLF4J typically declares a dependency only on `slf4j-api`; a reusable library should not impose a provider on the consuming application.

### 5.3. Framework Already Providing Logging

For example, in a Spring Boot application with default Logback-based logging, manually adding `slf4j-simple` or a Log4j 2 provider can create a conflict. Identify which backend the framework is managing before making changes.

Intentionally switching backends requires replacing the corresponding starters/dependencies and reviewing bridges—not simply adding a new provider alongside the old one.

### 5.4. Differences Between Test and Runtime, IDE and Packaged Artifacts

Sometimes `gradle run` shows no warning while `test` warns, or running in the IDE works fine while the packaged JAR warns. The cause is differing classpaths: `runtimeClasspath`, `testRuntimeClasspath`, startup module dependencies, libraries bundled into a fat JAR, or libraries provided by the deployment environment.

Inspect the classpath **in the exact environment where the warning appears**; do not assume the test classpath matches the production classpath.

## 6. Runnable Java 17 Example: Identifying the Active Provider

This real-world problem requires the SLF4J library, so the example **does not use pure JDK alone**; we create a small Gradle project using SLF4J 2.0.20 and a single provider, `slf4j-simple:2.0.20`. This version is a fixed baseline for the example; when applying it to a real project, use the compatible version managed by your project.

Structure:

```text
multiple-bindings-demo/
  settings.gradle
  build.gradle
  src/main/java/demo/MultipleBindingsDemo.java
```

**`settings.gradle`:**

```groovy
rootProject.name = 'multiple-bindings-demo'
```

**`build.gradle` (Groovy DSL):**

```groovy
plugins {
    id 'application'
}

repositories {
    mavenCentral()
}

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(17)
    }
}

dependencies {
    implementation 'org.slf4j:slf4j-api:2.0.20'
    runtimeOnly 'org.slf4j:slf4j-simple:2.0.20'
}

application {
    mainClass = 'demo.MultipleBindingsDemo'
}
```

**`src/main/java/demo/MultipleBindingsDemo.java`:**

```java
package demo;

import org.slf4j.ILoggerFactory;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public final class MultipleBindingsDemo {
    public static void main(String[] args) {
        // Set before LoggerFactory initializes the provider.
        System.setProperty(
                "org.slf4j.simpleLogger.logFile", "System.out");
        System.setProperty(
                "org.slf4j.simpleLogger.showDateTime", "false");
        System.setProperty(
                "org.slf4j.simpleLogger.defaultLogLevel", "info");

        ILoggerFactory factory = LoggerFactory.getILoggerFactory();
        System.out.println("factory=" + factory.getClass().getName());

        Logger logger = LoggerFactory.getLogger(MultipleBindingsDemo.class);
        logger.info("event=provider.ready");
    }
}
```

Run from the `multiple-bindings-demo` directory using Gradle with Java 17 support, JDK 17 installed, and access to download dependencies from Maven Central:

```bash
gradle run --quiet
```

If a Gradle Wrapper is already generated in the project, you can use `./gradlew run --quiet` on Unix systems or `gradlew.bat run --quiet` on Windows. The example does not include the wrapper itself; if Gradle or the wrapper is not installed, you will need to install or prepare it first.

**Program stdout with the exact example configuration and no other provider interfering:**

```text
factory=org.slf4j.simple.SimpleLoggerFactory
[main] INFO demo.MultipleBindingsDemo - event=provider.ready
```

Explanation:

- `LoggerFactory.getILoggerFactory()` reveals the **actual `ILoggerFactory` selected**; with `slf4j-simple`, it is `org.slf4j.simple.SimpleLoggerFactory`.
- `LoggerFactory.getLogger(...)` returns a logger from the active provider.
- The program configures `slf4j-simple` to write to stdout and disables timestamps for more deterministic output. By default without configuration, `slf4j-simple` typically outputs logs to **stderr**, so stdout and stderr should not be treated as identical in that case.
- `{ }` and other formatting options are not the focus here; the goal is to identify the provider, not to compare message formatting syntax.

### 6.1. Trying the Multiple-Provider Scenario

**Only in the demo project**, add to `dependencies` in `build.gradle`:

```groovy
runtimeOnly 'org.slf4j:slf4j-nop:2.0.20'
```

Now the runtime has both `slf4j-simple` and `slf4j-nop` as 2.x providers. When run, SLF4J may warn about **multiple providers**; the printed `ILoggerFactory` class will help identify which provider was chosen. Do not assume a fixed winner or fixed stdout during a conflicted run. If NOP is selected, the `event=provider.ready` line will not be printed.

**Fixing it in the demo:** remove the `slf4j-nop` line you just added, run again, and confirm only `SimpleLoggerFactory` is active and the message is output. In practice, if NOP appears transitively, locate the root dependency and exclude it on the appropriate dependency edge.

## 7. Diagnosing in Gradle

Run commands in the actual Gradle project, focusing on the **application startup module**, not just a library module.

### 7.1. Viewing All Runtime Dependencies

```bash
gradle dependencies --configuration runtimeClasspath
```

With an existing Gradle Wrapper:

```bash
./gradlew dependencies --configuration runtimeClasspath
```

On Windows PowerShell, use `.\gradlew.bat` instead of `./gradlew`. In a multi-project build, you can prefix the task path like `gradle :app:dependencies --configuration runtimeClasspath` if the application module is actually named `app` in the project; that module name is just a structural example.

Look for these artifacts:

```text
slf4j-api
slf4j-simple
slf4j-nop
slf4j-jdk14
slf4j-reload4j
logback-classic
log4j-slf4j2-impl
log4j-slf4j-impl
```

This list contains **keywords to check for**, not artifacts that are all allowed simultaneously. Also pay attention to the version Gradle actually selects after dependency resolution.

### 7.2. Finding Which Dependency Pulls In a Provider

For example, if you see `slf4j-simple` unexpectedly:

```bash
gradle dependencyInsight --configuration runtimeClasspath --dependency slf4j-simple
```

If you see `logback-classic`:

```bash
gradle dependencyInsight --configuration runtimeClasspath --dependency logback-classic
```

`dependencyInsight` shows the dependency path and selected version, helping you pinpoint where to exclude the dependency. If only one provider appears in `runtimeClasspath` but tests warn, also inspect:

```bash
gradle dependencies --configuration testRuntimeClasspath
```

When the application runs via `bootRun`, a Docker image, or a fat JAR, also check the final artifact and the classpath configuration of that environment.

### 7.3. Intentionally Excluding Redundant Providers

If you chose `slf4j-simple` for a demo, do not declare `slf4j-nop`, `logback-classic`, or another provider in the same runtime. If you chose Logback in a framework, keep Logback and exclude any redundant provider pulled in transitively.

In Gradle, you can exclude a module from a specific dependency using `exclude group: ..., module: ...`. Place the exclusion on **the dependency that actually pulls in the redundant provider** as shown by the dependency tree. Avoid blanket exclusions across all configurations without understanding the impact, and especially do not blindly exclude `slf4j-api`, since application libraries still require this API.

A fix is complete when the runtime classpath contains **only the one intended provider** and log calls actually output through that backend—not merely when the warning disappears.

## 8. Diagnosing in Maven

In Maven, use the dependency tree:

```bash
mvn dependency:tree
```

Search for `slf4j-api`, `logback-classic`, `slf4j-simple`, `slf4j-nop`, Log4j bridges, and the dependencies that bring them in. Check runtime scope, test scope, and different modules.

Example Maven configuration **selecting only `slf4j-simple` for a small application**:

```xml
<dependencies>
    <dependency>
        <groupId>org.slf4j</groupId>
        <artifactId>slf4j-api</artifactId>
        <version>2.0.20</version>
    </dependency>
    <dependency>
        <groupId>org.slf4j</groupId>
        <artifactId>slf4j-simple</artifactId>
        <version>2.0.20</version>
        <scope>runtime</scope>
    </dependency>
</dependencies>
```

This is a **snippet inside `pom.xml`**, not a complete Maven POM file. For a reusable library, typically **declare only `slf4j-api`**; the application project is responsible for choosing the backend at runtime.

If a transitive dependency pulls in an unwanted provider, place `<exclusions>` on that specific dependency after verifying the path. Do not randomly edit the repository cache or manually delete JAR files and consider the issue solved.

## 9. How to Identify Which Backend Is Selected

In addition to startup warnings, you can print diagnostic info at a checkpoint:

```java
System.out.println(
        org.slf4j.LoggerFactory
                .getILoggerFactory()
                .getClass()
                .getName()
);
```

This is a **code snippet** for use in a program that already has SLF4J on the classpath; it is not a standalone program. The output might be:

```text
org.slf4j.simple.SimpleLoggerFactory
```

or an `ILoggerFactory` from another backend. The returned value is evidence of **which factory is in use**, not a guarantee that every message will appear; backend levels, filters, and output configuration still affect the result.

SLF4J 2.x also offers the `slf4j.provider` option in supported versions (from 2.0.9) to specify the provider class. This is not a default measure to mask conflicts: it can make selection deterministic when there is a legitimate reason, but it **does not replace cleaning up the runtime classpath** and must be evaluated against the project's lifecycle and version.

If the application prints no logs, check in order:

1. Are the API and provider/binding from compatible generations?
2. Does the runtime have the exact intended provider?
3. Which backend does the actual `ILoggerFactory` belong to?
4. Does the logger level allow the event, and are the layout and appender configured to output properly?
5. Is output going to stdout, stderr, a file, or a collector?
6. Is `slf4j-nop` configured or is NOP fallback swallowing logs?

### 9.1. Avoid Confusing SLF4J Warnings with Application Log Data

SLF4J initialization warnings are typically printed directly to stderr by its internal reporting mechanism; they do not necessarily pass through the provider selected by the application. Do not expect changing `logback.xml` or lowering the application log level to fix classpath conflict warnings.

## 10. Logging Bridges: Avoiding Loops Beyond Multiple Bindings

Multiple providers and routing loops are two different errors, though both commonly appear when switching backends.

Example of the intended direction:

```text
Application calls SLF4J API
         |
         v
 log4j-slf4j2-impl
         |
         v
       Log4j 2
```

If you **simultaneously** include `log4j-to-slf4j` (which routes Log4j API calls back to SLF4J) in the same pipeline, a routing loop can occur:

```text
SLF4J -> Log4j 2 -> SLF4J -> Log4j 2 -> ...
```

Therefore, do not deploy `log4j-slf4j2-impl` together with `log4j-to-slf4j`. Similarly, when bridging JUL with SLF4J, check the bridge direction and selected backend; do not simultaneously route SLF4J to JUL and JUL back to SLF4J without checking for forwarding loops.

**Classify correctly before fixing:**

- `slf4j-api`: API, not a provider.
- `log4j-slf4j2-impl`: SLF4J 2.x provider targeting Log4j 2.
- `log4j-to-slf4j`: adapter routing calls from Log4j API to SLF4J.
- `jul-to-slf4j`: adapter routing JUL to SLF4J.
- `logback-classic`: Logback backend connected directly by SLF4J.
- `slf4j-nop`: provider that intentionally discards all events.

Removing a bridge because you mistook it for a provider can break log routing from another framework. Keeping both opposing bridges can cause other errors. Draw the **routing arrows** of your logging pipeline accurately before adding or removing dependencies.

## 11. Proper Practices in Multi-Module Projects

In a project with shared libraries and multiple runnable applications, separate responsibility for deciding the backend:

- **Library module:** compile against `slf4j-api`; do not impose a fixed logging provider on applications consuming the library.
- **Executable application:** choose **one** compatible backend/provider and configure log levels, appenders, formats, and output policies.
- **Integration tests:** may use a test-specific provider if needed, but avoid having two providers on the test runtime classpath or interpreting test warnings as production warnings.
- **Framework-managed application:** let the starter/framework manage logging properly; if switching backends, update the entire group of related dependencies and bridges.
- **Deployment:** inspect the actual dependencies in the distributed artifact, because a successful build configuration does not guarantee the packaged artifact contains only one provider.

This policy keeps libraries implementation-independent and prevents one module from accidentally dictating logging for the entire system.

## 12. Step-by-Step Troubleshooting Workflow

Suppose the application prints a multiple-provider warning:

1. **Record the full warning** and the `slf4j-api` version in use. For 1.7, look for `StaticLoggerBinder`; for 2.x, look for `SLF4JServiceProvider`.
2. **Identify the target backend** of the application: Logback, Log4j 2, JUL, Simple, or intentional NOP.
3. **Inspect the runtime dependency graph** from the startup module; in Gradle use `dependencies` and `dependencyInsight`, and in Maven use `dependency:tree`.
4. **Find the source of the extra provider**: direct dependency, transitive dependency, starter, test scope, or fat JAR/deployment.
5. **Adjust the exact dependency edge** so the runtime retains a single provider matching the SLF4J API; review bridges to avoid bidirectional loops.
6. **Re-run in the environment that reported the warning**, check the active factory, confirm the warning is gone, and verify `INFO`/error logs actually reach the intended destination.
7. **Check other important classpaths** if applicable: tests, other applications in a multi-project build, and the final packaged artifact.

Quick reference table:

| Symptom | Likely Cause | What to Check |
| --- | --- | --- |
| `Class path contains multiple SLF4J bindings` | Two bindings from the 1.7 family | Find JARs containing `StaticLoggerBinder` |
| `Class path contains multiple SLF4J providers` | Two providers from the 2.x family | Find `SLF4JServiceProvider` implementations |
| `No SLF4J providers were found` | No provider compatible with 2.x | Add a matching-generation provider or fix the mismatch |
| 1.7 binding present but 2.x API reports it ignored | New-generation provider is missing | Replace the old binding with a 2.x provider |
| Logger runs but produces no output | NOP selected, or wrong level/filter/output | Print `ILoggerFactory`, check backend and appender |
| Test warns, real app does not warn | Test classpath differs from runtime | Inspect `testRuntimeClasspath` and the corresponding runtime |
| Build tree is clean but fat JAR warns | Packaging added another provider | Inspect dependencies bundled into the artifact |
| Log4j reports routing/bridge error | Opposing bridges coexist | Check `log4j-to-slf4j` alongside `log4j-slf4j2-impl` |

## 13. Common Mistakes When Fixing

1. **Removing `slf4j-api` to stop the warning.** The API is still needed by code and libraries calling SLF4J; the culprit is usually an extra or incompatible provider/binding.
2. **Adding `slf4j-nop` to hide the warning when logs are still needed.** NOP discards events; selecting it by mistake can lose diagnostic and operational logs.
3. **Looking only at directly declared dependencies.** Transitive providers from starters or other libraries still end up at runtime.
4. **Assuming whichever provider wins today will always win.** Never rely on JAR/classpath ordering to resolve conflicts.
5. **Mixing `slf4j-api` 2.x with a 1.7.x binding.** The new API does not use legacy `StaticLoggerBinder`; it requires a matching-generation provider.
6. **Silencing the warning and declaring it fixed.** Always verify the factory, real log events, levels, and output destination.
7. **Adding Log4j 2 while keeping the bridge from Log4j back to SLF4J.** This can cause a forwarding loop, a completely different error from a multiple-providers warning.
8. **Modifying a shared library to enforce a provider.** Backend decisions belong to the runnable application; libraries should depend only on the API unless a special contract requires otherwise.
9. **Checking the wrong classpath.** `compileClasspath`, `runtimeClasspath`, `testRuntimeClasspath`, and the deployed artifact can all differ.
10. **Changing multiple dependencies at once.** When you no longer know which change fixed the issue, it becomes very hard to verify the impact on logging and transitive dependencies.

## 14. Checklist Before Finalizing the Fix

- [ ] Accurately identified whether it is SLF4J 1.7 (binding) or SLF4J 2.x (provider).
- [ ] Only **one** matching implementation/provider remains on the application's runtime classpath.
- [ ] `slf4j-api` and the provider/binding use compatible generations.
- [ ] Located and excluded the conflicting dependency at its source, without editing the cache directly.
- [ ] If using a framework, the selected backend aligns with the framework's logging starter/configuration.
- [ ] No opposing bridges exist that could create a forwarding loop.
- [ ] The factory name from `LoggerFactory.getILoggerFactory()` matches the expected backend.
- [ ] Verified that `INFO`, `WARN`, `ERROR`, and exception logs actually reach the intended destination.
- [ ] Verified the test classpath and deployed artifact when they differ from the development runtime.
- [ ] For reusable libraries, declared only the SLF4J API dependency without forcing a backend on library consumers.

**Conclusion:** "Multiple bindings" does not mean a log is emitted twice by all backends; it warns that **the classpath contains multiple paths connecting SLF4J to an implementation**, leaving the actual backend in use poorly controlled. For SLF4J 1.7, inspect `StaticLoggerBinder`; for 2.x, inspect `SLF4JServiceProvider`. Keep only one compatible provider, confirm the selected `ILoggerFactory`, and verify that real logs reach their intended destination.
