# Đọc giá trị MDC trong Java Logging: MDC.get, snapshot, layout và kiểm thử

## 1. Đọc giá trị MDC nghĩa là gì?

**MDC** (Mapped Diagnostic Context) là vùng ngữ cảnh dạng **key–value**, giúp các bản ghi log trong một phạm vi xử lý mang cùng thông tin liên kết, chẳng hạn `request_id`, `trace_id` hoặc `job_id`. Trong ứng dụng Java sử dụng **SLF4J** và backend tương thích như **Logback**, một giá trị MDC có thể được:

1. Đặt vào ngữ cảnh bằng `MDC.put(key, value)`.
2. Đọc trực tiếp trong mã Java bằng `MDC.get(key)`.
3. Đọc bản sao toàn bộ ngữ cảnh bằng `MDC.getCopyOfContextMap()`.
4. Đưa vào dòng text qua converter layout như `%X{request_id}`.
5. Xuất ra trường riêng trong JSON khi encoder hỗ trợ MDC và được cấu hình phù hợp.

Ví dụ một lần xử lý yêu cầu:

```java
MDC.put("request_id", "req-42");
try {
    String currentId = MDC.get("request_id");
    log.info("event=order.created");
} finally {
    MDC.remove("request_id");
}
```

Đây là **đoạn minh họa trong một method** đã có biến `log`, không phải một chương trình Java độc lập. Khi chạy với một backend MDC tương thích, biến `currentId` nhận chuỗi `"req-42"`. Backend logging có thể đồng thời gắn giá trị đó vào event. Sau khi xóa key, `MDC.get("request_id")` thường trả về `null`.

**Điểm cần nhớ nhất:** `MDC.get` đọc ngữ cảnh **hiện tại tại nơi gọi**, không phải truy vấn một kho log lịch sử, không phải đọc context của thread khác, và không bảo đảm một logging event đã được xuất ra console hoặc collector.

### Tình huống thực tế

Hai request A và B được xử lý xen kẽ:

```text
INFO  request_id=req-A event=request.received
INFO  request_id=req-B event=request.received
WARN  request_id=req-A event=inventory.cache_miss
ERROR request_id=req-B event=payment.failed
INFO  request_id=req-A event=request.completed
```

MDC giúp gắn ID phù hợp cho event ngay khi phát log. Nhưng một lời gọi `MDC.get("request_id")` trong request B phải đọc ra ID của **B**, không phải ID còn sót từ A. Vì vậy, bài học về **đọc** MDC phải đi cùng hiểu biết về **phạm vi, vòng đời và truyền ngữ cảnh**.

## 2. Những phương thức SLF4J MDC cần nắm

Với SLF4J API, một số phương thức chính:

| API | Ý nghĩa | Kết quả/lưu ý |
| --- | --- | --- |
| `MDC.put(String key, String val)` | Đặt/cập nhật giá trị trong ngữ cảnh hiện tại | Key/value là chuỗi; không phải object typed. |
| `MDC.get(String key)` | Đọc giá trị cho một key | Trả `String` hoặc `null` nếu key không có. |
| `MDC.remove(String key)` | Xóa một key trong ngữ cảnh hiện tại | Không xóa những key khác. |
| `MDC.clear()` | Xóa toàn bộ MDC của phạm vi hiện tại | Có thể làm mất ngữ cảnh do framework/scope cha đặt. |
| `MDC.getCopyOfContextMap()` | Lấy bản sao map context | Trả `Map<String,String>` hoặc `null` nếu không có map. |
| `MDC.setContextMap(map)` | Thay context hiện tại bằng map được chỉ định | Phù hợp để restore snapshot đã lưu. |
| `MDC.putCloseable(key, val)` | Đặt key và nhận scope `MDCCloseable` có thể đóng | Khi đóng sẽ bỏ key; không tự hiểu là luôn restore giá trị cũ ở nested scope. |
| `MDC.getMDCAdapter()` | Truy cập adapter do provider/backend cung cấp | Chủ yếu để chẩn đoán/tích hợp; tránh phụ thuộc implementation trong nghiệp vụ. |

MDC của SLF4J là **facade API**: cách dữ liệu được lưu, copy, đồng bộ với backend và đưa vào event phụ thuộc provider/adapter. Với Logback Classic, việc đọc theo thread là cách sử dụng quen thuộc; các framework bất đồng bộ có thể cần truyền context riêng.

### `get` có kiểu trả về gì?

`MDC.get("request_id")` luôn trả **`String` hoặc `null`** theo contract của SLF4J, không trả một `Optional`, integer hay một object chứa metadata.

Ví dụ:

```java
String requestId = MDC.get("request_id");
if (requestId == null) {
    // Không có request_id ở context hiện tại.
}
```

Đây là đoạn code trong một method đã import `org.slf4j.MDC`.

**Không được đồng nhất các trường hợp**:

| Trường hợp | Giá trị khi đọc | Ý nghĩa |
| --- | --- | --- |
| Key chưa được đặt | `null` | Không có entry đó trong MDC hiện tại. |
| Key đã đặt là `"req-42"` | `"req-42"` | Có ID để ghi log/liên kết. |
| Key được đặt là chuỗi rỗng `""` | `""` | Entry có thể tồn tại nhưng giá trị không hữu ích. |
| Key đặt là chuỗi `"null"` | `"null"` | Đây là **bốn ký tự** n-u-l-l, không phải `null` Java. |
| Đang đọc ở thread khác | Có thể `null` hoặc context của thread ấy | Không tự kế thừa request context của thread gọi. |

Đừng dùng `if (requestId == "")` để kiểm tra chuỗi rỗng; trong Java, nên dùng `requestId.isEmpty()` hoặc `requestId.isBlank()` sau khi đã kiểm tra `null`.

### Tên key phân biệt chữ hoa và chữ thường

`"request_id"` khác `"requestId"` hoặc `"REQUEST_ID"`. Khi chương trình đặt:

```java
MDC.put("request_id", "req-42");
```

thì:

```java
MDC.get("request_id"); // "req-42"
MDC.get("requestId");  // null nếu key đó không tồn tại
```

Không có cơ chế mặc định tự chuyển camelCase thành snake_case. **Chọn tên key nhất quán** giữa filter, mã Java, pattern, JSON encoder và collector.

## 3. Đọc một key đúng cách: thiếu dữ liệu và fallback

Không phải mọi bản ghi đều nằm trong HTTP request. Startup job, scheduled task, shutdown hook và background worker có thể không có `request_id`. Vì vậy, giá trị `null` **có thể bình thường**.

### Cách đọc đơn giản

```java
String requestId = MDC.get("request_id");

if (requestId != null && !requestId.isBlank()) {
    log.debug("event=context.found request_id={}", requestId);
} else {
    log.debug("event=context.absent");
}
```

Đây là **đoạn minh họa** trong phương thức có `log`. Khi cần một chuỗi hiển thị an toàn, có thể dùng fallback:

```java
String requestId = MDC.get("request_id");
String displayId = (requestId == null || requestId.isBlank())
        ? "unavailable"
        : requestId;
```

**Cẩn thận với fallback giả:** `"unavailable"` tiện cho UI hoặc log chẩn đoán, nhưng **không phải một request ID thật**. Nếu mọi request thiếu ID đều được gắn `"unavailable"`, tìm kiếm có thể gộp nhầm nhiều request không liên quan.

### `getOrDefault` thuộc Map, không thuộc MDC

Một lỗi API thường gặp:

```java
// KHÔNG có phương thức MDC.getOrDefault trong API SLF4J chuẩn.
// MDC.getOrDefault("request_id", "none");
```

Cách dùng đúng là đọc `MDC.get(...)` rồi xử lý `null`, hoặc dùng một map snapshot an toàn:

```java
Map<String, String> context = MDC.getCopyOfContextMap();
String requestId = context == null
        ? "none"
        : context.getOrDefault("request_id", "none");
```

Đây là đoạn code minh họa với `java.util.Map` đã import. `Map.getOrDefault` là API của Java Map; nó không phải tính năng đặc biệt của MDC. Ngoài ra, nếu map có key với giá trị `null` theo implementation cho phép, `getOrDefault` không nhất thiết thay bằng default; nên xác định quy ước vắng mặt cho ứng dụng.

### Đọc dạng số/boolean cần parse và validation

Các value của MDC thường là string:

```java
String attemptText = MDC.get("attempt");
Integer attempt = null;

if (attemptText != null) {
    try {
        attempt = Integer.valueOf(attemptText);
    } catch (NumberFormatException badValue) {
        // Chọn hành vi fallback theo chính sách.
    }
}
```

Đây là mã minh họa. Với `duration_ms` hoặc `attempt`, tốt hơn là giữ **kiểu số** trong dữ liệu sự kiện có cấu trúc nếu backend hỗ trợ, thay vì dùng MDC để biến mọi thuộc tính nghiệp vụ thành chuỗi rồi parse lại.

**Không dùng giá trị đọc từ MDC để quyết định nghiệp vụ quan trọng** như authorization, tenant isolation, tính tiền hoặc chống gian lận. MDC phục vụ logging/tracing; context có thể thiếu, được khôi phục sai hoặc đến từ nguồn header chưa được xác thực.

## 4. Đọc toàn bộ MDC bằng `getCopyOfContextMap()`

Khi cần chuyển context sang một tác vụ khác hoặc kiểm tra nhiều field, có thể lấy snapshot:

```java
Map<String, String> snapshot = MDC.getCopyOfContextMap();

if (snapshot != null) {
    String requestId = snapshot.get("request_id");
    String traceId = snapshot.get("trace_id");
}
```

`snapshot` là bản sao ở thời điểm gọi. Tùy provider/adapter, khi MDC không có dữ liệu, phương thức có thể trả `null`. **Luôn xét cả `null`**, không gọi ngay `snapshot.get(...)` hoặc `snapshot.size()` nếu chưa kiểm tra.

### Snapshot không phải live view

Ví dụ:

```java
MDC.put("request_id", "req-1");
Map<String, String> snapshot = MDC.getCopyOfContextMap();

MDC.put("request_id", "req-2");

String oldValue = snapshot.get("request_id"); // "req-1"
String newValue = MDC.get("request_id");      // "req-2"
```

Với adapter MDC sao chép map đúng contract, snapshot giữ giá trị cũ. Đây là yếu tố giúp truyền context tại **thời điểm submit task**, không vô tình dùng giá trị mới sau khi thread gọi đã chuyển sang request khác.

**Đừng chỉnh map snapshot rồi cho rằng MDC hiện tại sẽ đổi.** Ví dụ `snapshot.put("request_id", "...")` chỉ thao tác trên map copy nếu map đó cho phép thay đổi. Muốn cập nhật context hoạt động, dùng `MDC.put(...)`; muốn thay toàn bộ, dùng `MDC.setContextMap(...)` trong scope được kiểm soát.

### Có thể log toàn bộ map để debug không?

Có thể về mặt kỹ thuật, nhưng **không nên dùng**:

```java
log.info("MDC={}", MDC.getCopyOfContextMap());
```

trên production khi chưa biết rõ nội dung các key. Map có thể chứa tenant/user ID, correlation ID hoặc trường nhạy cảm do framework/thư viện thêm. Nên log một **allowlist field** đã được phê duyệt:

```java
String requestId = MDC.get("request_id");
log.debug("event=context.read request_id={}", requestId);
```

Đây là code minh họa; phải có `log` và import cần thiết. Với ID từ client, validation/escaping vẫn cần áp dụng trước khi đặt vào MDC.

## 5. Vì sao đọc MDC phải hiểu vòng đời?

Một service có thể dùng thread pool. Thread A xử lý request 1 rồi tái sử dụng để xử lý request 2. Nếu request 1 đặt `MDC.put("request_id","req-1")` và không xóa, request 2 có thể đọc được ID cũ.

### Cách giới hạn scope cơ bản

```java
MDC.put("request_id", requestId);
try {
    doWork();
} finally {
    MDC.remove("request_id");
}
```

Đây là đoạn minh họa trong method đã có `requestId` và `doWork()`.

`finally` bảo đảm dọn key khi code hoàn tất bình thường hoặc ném exception trong cùng thread. Tuy nhiên, **`remove` không khôi phục giá trị cũ** nếu trước đó đã có `request_id` từ scope bên ngoài.

Ví dụ scope lồng nhau:

```text
Scope cha: request_id=req-parent
    |
    +-- Scope con đặt request_id=req-child
    |
    +-- Scope con remove(request_id)
    |
Scope cha: request_id bị mất, thay vì req-parent
```

Nếu ứng dụng có nested scopes, chọn cách **snapshot rồi restore**.

### Snapshot và restore an toàn cho scope lồng nhau

```java
Map<String, String> previous = MDC.getCopyOfContextMap();

try {
    MDC.put("request_id", requestId);
    doWork();
} finally {
    if (previous == null) {
        MDC.clear();
    } else {
        MDC.setContextMap(previous);
    }
}
```

Đây là mã minh họa. Nó giúp khôi phục toàn bộ context như trước khi vào scope, kể cả key của framework/tracing. Nhưng một lưu ý thiết kế quan trọng: nếu framework **cố ý thay đổi context cha trong thời gian scope con chạy**, restore snapshot có thể ghi đè thay đổi đó. Vì vậy, cần có quy tắc **ai là owner của từng key và vòng đời của từng scope**.

### `MDC.putCloseable` có thay thế mọi cách restore không?

SLF4J cung cấp `MDC.putCloseable`:

```java
try (MDC.MDCCloseable ignored =
        MDC.putCloseable("request_id", requestId)) {
    doWork();
}
```

Đây là đoạn minh họa cần `requestId` và `doWork()`. Sau `try-with-resources`, closeable giúp gỡ key được đặt. **Không dùng nó như bảo đảm tự khôi phục giá trị cũ trong mọi trường hợp nested override.** Nếu có thể có `request_id` của scope cha, snapshot/restore hoặc một scope abstraction nắm rõ previous value là lựa chọn dễ chứng minh hơn.

## 6. Ví dụ Java 17 + Maven chạy được: đọc một key, đọc snapshot, qua executor và khôi phục

Bài thực hành sau dùng **SLF4J + Logback** để cho thấy cả hai mặt:

- `MDC.get`/`getCopyOfContextMap` được đọc **bằng Java**.
- `%X{request_id}` được đọc **bởi layout** và xuất ra console.
- Thread worker không tự có MDC của thread submit.
- Chủ động truyền snapshot qua executor giúp worker đọc đúng.
- Sau khi kết thúc, context được restore nên không lẫn dữ liệu.

Để output có thể kiểm chứng chính xác, ta dùng một worker thread, chờ `Future.get()` và không in timestamp/thread động.

### 6.3. Tệp `src/main/resources/logback.xml`

```xml
<configuration>
    <appender name="CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
        <target>System.out</target>
        <encoder class="ch.qos.logback.classic.encoder.PatternLayoutEncoder">
            <pattern>%level|rid=%X{request_id}|tenant=%X{tenant_id}|%msg%n</pattern>
            <charset>UTF-8</charset>
        </encoder>
    </appender>

    <root level="INFO">
        <appender-ref ref="CONSOLE" />
    </root>
</configuration>
```

Pattern dùng `%X{request_id}` và `%X{tenant_id}`. Khi key không tồn tại, hai phần chuyển đổi này hiển thị chuỗi rỗng trong cấu hình Logback mẫu. Chúng ta giữ nguyên chữ `rid=` và `tenant=` để thấy rõ lúc giá trị trống.

### 6.4. Tệp `src/main/java/demo/MdcReadDemo.java`

```java
package demo;

import java.util.Map;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;

public final class MdcReadDemo {
    private static final Logger LOG =
            LoggerFactory.getLogger(MdcReadDemo.class);

    private MdcReadDemo() {
    }

    private static String display(String value) {
        return value == null ? "<null>" : value;
    }

    private static void restore(Map<String, String> oldContext) {
        if (oldContext == null) {
            MDC.clear();
        } else {
            MDC.setContextMap(oldContext);
        }
    }

    private static Runnable withContext(Runnable action) {
        Map<String, String> captured =
                MDC.getCopyOfContextMap();

        return () -> {
            Map<String, String> workerBefore =
                    MDC.getCopyOfContextMap();

            try {
                restore(captured);
                action.run();
            } finally {
                restore(workerBefore);
            }
        };
    }

    public static void main(String[] args) throws Exception {
        Map<String, String> mainBefore =
                MDC.getCopyOfContextMap();

        ExecutorService pool =
                Executors.newSingleThreadExecutor();

        try {
            System.out.println("read.before="
                    + display(MDC.get("request_id")));

            MDC.put("request_id", "req-42");
            MDC.put("tenant_id", "tenant-7");

            System.out.println("read.request_id="
                    + display(MDC.get("request_id")));
            System.out.println("read.missing="
                    + display(MDC.get("missing")));

            LOG.info("event=request.started");

            Map<String, String> snapshot =
                    MDC.getCopyOfContextMap();

            System.out.println("read.snapshot.request_id="
                    + snapshot.get("request_id"));

            MDC.put("request_id", "req-43");
            System.out.println("read.current_after_change="
                    + display(MDC.get("request_id")));
            System.out.println("read.snapshot_unchanged="
                    + snapshot.get("request_id"));

            MDC.put("request_id", "req-42");

            Future<?> noPropagation = pool.submit(() ->
                    LOG.info("event=worker.without_context"));
            noPropagation.get();

            Future<?> withPropagation = pool.submit(
                    withContext(() ->
                            LOG.info("event=worker.with_context")));
            withPropagation.get();

            LOG.info("event=request.completed");
        } finally {
            restore(mainBefore);
            pool.shutdown();
        }

        System.out.println("read.after="
                + display(MDC.get("request_id")));
        LOG.info("event=outside.request");
        System.out.println("PASS mdc_read_and_restore");
    }
}
```

```text
read.before=<null>
read.request_id=req-42
read.missing=<null>
INFO|rid=req-42|tenant=tenant-7|event=request.started
read.snapshot.request_id=req-42
read.current_after_change=req-43
read.snapshot_unchanged=req-42
INFO|rid=|tenant=|event=worker.without_context
INFO|rid=req-42|tenant=tenant-7|event=worker.with_context
INFO|rid=req-42|tenant=tenant-7|event=request.completed
read.after=<null>
INFO|rid=|tenant=|event=outside.request
PASS mdc_read_and_restore
```

Maven có thể in thông tin riêng ngoài các dòng ứng dụng; bảng output trên thể hiện nội dung chương trình và Logback khi chỉ cấu hình mẫu được nạp. Không có timestamp hoặc tên thread động trong pattern.

### 6.6. Vì sao từng dòng đúng?

1. `read.before=<null>`: trước khi đặt key, `MDC.get("request_id")` không có giá trị; helper `display` in chữ `<null>` thay cho Java `null`.
2. `read.request_id=req-42`: đọc trực tiếp key vừa được đặt trên main thread.
3. `read.missing=<null>`: key `missing` chưa từng được đặt trong scope.
4. `event=request.started`: Logback layout đọc cả `request_id` và `tenant_id` qua hai converter `%X`.
5. `read.snapshot.request_id=req-42`: snapshot chụp ngay sau bản ghi bắt đầu.
6. Sau `MDC.put("request_id","req-43")`, `MDC.get` thấy `req-43`, còn snapshot cũ vẫn chứa `req-42`.
7. Mã đặt lại `req-42` trước khi submit các task.
8. `worker.without_context` được chạy ở một worker thread mới, không tự kế thừa MDC của main thread trong Logback mẫu, nên hai trường trống.
9. `withContext` chụp snapshot khi tạo Runnable ở main thread và áp vào worker trong thời gian `action.run()`; vì vậy event thứ hai của worker đọc đúng cả hai field.
10. `finally` của wrapper khôi phục context trước đó của worker, giúp tránh giữ ID khi thread được tái sử dụng.
11. `Future.get()` chờ mỗi công việc hoàn tất trước bước tiếp theo, nên thứ tự log trong ví dụ được xác định.
12. `restore(mainBefore)` trả main thread về ngữ cảnh ban đầu; `read.after=<null>` và event `outside.request` chứng minh scope demo không để ID dư.
13. Dòng `PASS mdc_read_and_restore` chỉ là chỉ báo hoàn thành đường chương trình. Để **assert tự động** chính xác hơn, hãy thêm test đọc từng event và kết quả xuất như phần kiểm thử bên dưới.

**Quan trọng:** ví dụ này không phải phép chứng minh mọi framework, mọi SLF4J provider và mọi executor đều có chính xác chính sách kế thừa như Logback ở đây. Khi chuyển backend, cần kiểm thử thực tế.

## 7. Đọc MDC trong layout: `%X{key}` khác `MDC.get(key)` như thế nào?

Hai cách đọc phục vụ hai mục đích:

```java
String requestId = MDC.get("request_id");
```

đọc cho **mã Java đang thực thi**.

Trong `logback.xml`:

```xml
<pattern>%d{HH:mm:ss.SSS} %-5level rid=%X{request_id} %logger - %msg%n</pattern>
```

cho **layout** biết phải lấy `request_id` từ ngữ cảnh của logging event để in vào text.

Hãy tách rõ:

| Hành động | Đối tượng nhận giá trị | Khi nào có ý nghĩa? |
| --- | --- | --- |
| `MDC.get("request_id")` | Code Java | Khi code cần log/chẩn đoán ngữ cảnh hiện tại. |
| `MDC.getCopyOfContextMap()` | Code Java | Khi cần snapshot context hoặc kiểm thử nhiều key. |
| `%X{request_id}` | Logback/Log4j 2 layout | Khi encoder tạo text theo pattern, dựa trên context đã gắn vào event. |
| JSON MDC provider | Encoder JSON | Khi cần field `request_id` riêng để tìm kiếm ở collector. |
| `ILoggingEvent.getMDCPropertyMap()` | Code test/integration Logback | Khi cần xem context đi vào **event**. |

### Chỉ đặt MDC không có nghĩa console tự hiển thị

Giả sử code gọi:

```java
MDC.put("request_id", "req-42");
LOG.info("event=order.created");
```

nhưng pattern là:

```xml
<pattern>%level|%msg%n</pattern>
```

thì output text không có request ID, vì layout **chỉ in level và message**. Để hiển thị, dùng converter `%X{request_id}` hoặc cấu hình encoder JSON xuất MDC.

Đây là lỗi phổ biến: developer kiểm tra `MDC.get` thấy giá trị đúng rồi kết luận collector phải có field. **Chưa đủ**: cần xác minh encoder, appender và collector.

### Converter với giá trị vắng mặt

Ở Logback, `%X{request_id}` trả phần văn bản trống nếu không có entry thích hợp trong pattern mẫu. Một số backend/converter hỗ trợ cú pháp fallback hoặc default, nhưng cú pháp/semantics khác nhau theo thư viện và phiên bản.

Không nên sao chép một pattern fallback từ Log4j 2 sang Logback mà chưa kiểm tra. Nếu hệ thống thực sự cần một giá trị mặc định có ý nghĩa, hãy xác định nó ở ranh giới event hoặc chọn converter phù hợp với backend.

### AsyncAppender đọc MDC lúc nào?

Một backend có thể xử lý event ở thread khác khi dùng async logging. Với Logback, event có dữ liệu MDC được chuẩn bị/capture cho quá trình xử lý deferred của appender khi cần. Đừng giả định layout luôn gọi lại `MDC.get` trên thread nghiệp vụ vào đúng lúc xuất byte.

Điều cần kiểm tra là **MDC map trong logging event** và output thực, đặc biệt khi code xóa context ngay sau lời gọi logger. Một hệ thống async cấu hình đúng vẫn có thể xuất request ID của event dù thread xử lý cuối không giữ MDC của request.

## 8. Đọc MDC trong Log4j 2: `ThreadContext.get`

Log4j 2 có API `org.apache.logging.log4j.ThreadContext` để quản lý diagnostic context map. Nó tương tự về mục đích nhưng **không cùng class** với SLF4J `MDC`.

Ví dụ:

```java
import org.apache.logging.log4j.ThreadContext;

ThreadContext.put("request_id", "req-42");
try {
    String requestId = ThreadContext.get("request_id");
    log.info("event=request.received");
} finally {
    ThreadContext.remove("request_id");
}
```

Đây là đoạn code minh họa trong phương thức đã có `log`. Với Log4j 2 API, có thể đọc toàn bộ context bằng API map như `ThreadContext.getImmutableContext()`, trả về một view/map không nên sửa trực tiếp; nếu cần dùng snapshot độc lập, hãy tạo bản sao bằng `new HashMap<>(...)`.

Ví dụ:

```java
Map<String, String> snapshot =
        new java.util.HashMap<>(ThreadContext.getImmutableContext());

String requestId = snapshot.get("request_id");
```

Đây là snippet có `java.util.Map` đã import. Tên getter map khác `MDC.getCopyOfContextMap()` của SLF4J; **không coi hai API là cú pháp hoán đổi**.

Một pattern trong Log4j 2 có thể là:

```xml
<PatternLayout
    pattern="%level|rid=%X{request_id}|%c{1}|%m%n"
    charset="UTF-8" />
```

Đoạn XML này cần nằm trong appender thích hợp của `log4j2.xml`, không dùng như cấu hình Logback.

### Dùng SLF4J API nhưng backend là Log4j 2

Khi SLF4J 2.x được nối sang Log4j 2 bằng provider tương thích, cách `MDC` được ánh xạ vào context backend phụ thuộc adapter/provider đang chạy. Nên thống nhất **API mà mã ứng dụng sử dụng**, tránh tự gọi song song `MDC.put` và `ThreadContext.put` cho cùng field khi chưa hiểu chúng có dùng chung dữ liệu hay không.

Một test đúng trong kiến trúc này gồm: gọi API ứng dụng, kiểm tra `MDC.get` nếu đó là contract, kiểm tra event/backend và xác nhận field `request_id` ở output cuối. Không suy luận từ tên JAR rằng mọi lớp adapter hoạt động giống nhau.

### JUL có MDC chuẩn không?

`java.util.logging` của JDK có `Logger`, `LogRecord`, `Handler` và `Formatter`, nhưng không có một API MDC chung tương đương `org.slf4j.MDC`. Nếu ứng dụng chỉ dùng JUL, phải chọn cách cung cấp correlation phù hợp (truyền ID rõ ràng, wrapper, filter/formatter hoặc bridge) rồi kiểm thử. **Không gọi `MDC.get` và mặc định JUL tự hiểu context này** nếu chưa có cầu nối/backend tương thích.

## 9. Đọc MDC qua các ranh giới thread và async

Giá trị MDC của thread nhận request **không mặc nhiên** sẵn sàng ở mọi thread khác. Đây là lý do hàng đầu khi debug “`MDC.get("request_id")` trả null trong executor”.

### Ví dụ sai kỳ vọng

```java
MDC.put("request_id", "req-42");

executor.submit(() -> {
    String id = MDC.get("request_id");
    log.info("event=background.started request_id={}", id);
});
```

Đây là đoạn code minh họa. Tác vụ có thể chạy trên worker thread không mang MDC của thread submit. Nó có thể trả null, hoặc đọc **ngữ cảnh cũ của worker** nếu một tác vụ trước không cleanup.

### Nguyên tắc propagation

1. Đọc `MDC.getCopyOfContextMap()` ở **thread tạo/submitting task**.
2. Gắn snapshot vào Runnable/Callable hoặc cơ chế context propagation của framework.
3. Ở worker thread, lưu ngữ cảnh hiện có.
4. Đặt snapshot của request cho thời gian thực thi công việc.
5. Chạy logic và phát log.
6. Khôi phục context trước đó trong `finally`, kể cả lỗi.
7. Test worker thread được tái sử dụng giữa request A và B.

Ví dụ đã chạy đầy đủ trong phần 6 thực hiện các bước này cho một `Runnable`. Trong hệ thống thật, còn có `Callable`, callback, `CompletableFuture`, cancellation, nested tasks và framework riêng. **Không tự tin rằng một wrapper duy nhất bao phủ mọi async boundary**.

### `InheritableThreadLocal` có giải quyết được?

Không hoàn toàn. Worker pool thường được tạo trước khi request đến và được tái sử dụng cho nhiều request. Cơ chế “kế thừa tại thời điểm thread con được tạo” không phải “nhận context tại thời điểm task được submit”. Đó là hai thời điểm khác nhau.

Logback không nên bị giả định sẽ tự kế thừa mọi MDC từ thread cha sang worker thread trong pool. Hãy xác minh theo backend và cách tạo thread thực.

### Reactive và tracing instrumentation

Trong Reactor/WebFlux hoặc framework reactive, callback có thể di chuyển qua nhiều thread. Đọc `MDC.get` trực tiếp ở một callback có thể cho kết quả không như request đầu vào nếu chưa tích hợp context propagation. Nên dùng cơ chế context của framework và cầu nối MDC được chính framework/tracing SDK hỗ trợ.

Với OpenTelemetry hoặc tracing tương tự, `trace_id` có thể đến từ **span context**. Nếu ứng dụng dùng SDK/tracing chuẩn, ưu tiên lấy ID từ nguồn tracing tin cậy và để instrumentation gắn log context thay vì tự đặt các giá trị `trace_id` chưa chuẩn.

## 10. Đọc MDC trong HTTP filter và message consumer

### HTTP request

Một pattern phổ biến là đặt `request_id` ngay đầu chu kỳ request:

```java
String requestId = chooseTrustedRequestId(request);
Map<String, String> before = MDC.getCopyOfContextMap();

try {
    MDC.put("request_id", requestId);
    service.handle(request);
} finally {
    if (before == null) MDC.clear();
    else MDC.setContextMap(before);
}
```

Đây là **snippet** trong framework có các biến/phương thức tương ứng, không phải chương trình độc lập. `chooseTrustedRequestId` đại diện cho logic kiểm tra/tạo ID theo chính sách; không dùng giá trị header chưa validate nguyên văn.

Khi trong service gọi `MDC.get("request_id")`, bạn đang đọc ngữ cảnh do filter đặt. Nhưng các tình huống async dispatch, callback hoặc request rời thread ban đầu có thể yêu cầu hook lifecycle/propagation bổ sung.

**Cần lấy request ID ở đâu?** Quy tắc nên do gateway/framework đặt ra. Nếu chấp nhận header như `X-Request-ID`, giới hạn độ dài và ký tự, không tin header để làm authorization, không dùng ID chứa newline/secret, và thống nhất khi nào tạo mới.

### Message consumer

Message queue thường có `message_id` hoặc `correlation_id`. Một lần xử lý message có thể:

```java
String messageId = metadata.messageId();
MDC.put("message_id", messageId);

try {
    String current = MDC.get("message_id");
    consumer.handle(message);
} finally {
    MDC.remove("message_id");
}
```

Đây là snippet có `metadata`, `consumer` và `message` của ứng dụng. Nếu consumer chạy nested scope hoặc framework đã có MDC, snapshot/restore toàn context tốt hơn `remove` đơn giản.

**Không dùng `MDC.get("request_id")` như điều kiện bắt buộc trong mọi background job**. Một scheduled task có thể không có HTTP request, nhưng lại có `job_run_id` hữu ích. Chọn key phù hợp loại công việc.

## 11. Đọc MDC và structured JSON logging

Một log text có thể trông như:

```text
INFO rid=req-42 event=order.created order_id=O-17
```

Để truy vấn `request_id` như một field riêng, cần encoder JSON phù hợp và cấu hình nó lấy MDC. Ví dụ schema kết quả mong muốn:

```json
{
  "timestamp": "2026-01-01T10:15:30Z",
  "level": "INFO",
  "service": "checkout",
  "event_code": "order.created",
  "request_id": "req-42",
  "order_id": "O-17",
  "message": "Đã tạo đơn"
}
```

Đây chỉ là **ví dụ output có cấu trúc**, không phải JSON mặc định từ `PatternLayoutEncoder`.

Phân biệt ba nơi lưu:

| Dữ liệu | Nên phát từ đâu? | Vì sao? |
| --- | --- | --- |
| `request_id` | MDC/context của request | Chung cho nhiều event trong request. |
| `trace_id` | Tracing context hoặc MDC được đồng bộ | Dùng liên kết trace. |
| `event_code` | Key-value của từng event | Loại sự kiện thay đổi ở mỗi lần gọi log. |
| `order_id` | Field của event hoặc scope hẹp có chủ đích | Không phải mọi event của request đều liên quan cùng order. |
| `service`, `environment` | Cấu hình deployment/encoder | Tương đối ổn định trong process. |
| `duration_ms` | Field số của event | Cần giữ kiểu số cho truy vấn/aggregation. |

Một lời gọi SLF4J 2.x:

```java
log.atInfo()
        .addKeyValue("event_code", "order.created")
        .addKeyValue("order_id", orderId)
        .log("Đã tạo đơn");
```

không tự đặt `event_code` vào MDC. Hai luồng dữ liệu khác nhau: **event key-value** và **context map**. Encoder có thể xuất cả hai nếu được cấu hình.

**MDC giữ các value kiểu String**, nên nếu bạn đặt `MDC.put("attempt", "3")`, encoder có thể xuất giá trị đó dưới dạng **JSON string**, không tự biến thành integer. Với số lượt thử hoặc thời gian, nên dùng field typed của logging event nếu khả năng encoder hỗ trợ.

### Tại sao đọc được `MDC.get` nhưng JSON thiếu field?

Có thể do:

- Encoder không xuất MDC mặc định hoặc đã tắt MDC provider.
- Bộ lọc field ở encoder chỉ cho một số key.
- Tên key trong MDC khác schema đầu ra.
- Event được tạo trước khi MDC được đặt hoặc sau khi đã cleanup.
- Async propagation không đưa key tới thread tạo event.
- Collector không parse đúng JSON hoặc mapping loại field.
- Runtime đang nạp backend/cấu hình khác mong đợi.

Cần kiểm tra từ **MDC hiện tại → event → encoder → byte output → collector/index**.

## 12. Kiểm thử `MDC.get` và context map

Bài test đúng nên kiểm tra cả **giá trị tại thời điểm đọc** lẫn **việc không để dữ liệu rò sang scope khác**.

### Các assertion trực tiếp

Trong unit test có backend hỗ trợ MDC:

```java
Map<String, String> before = MDC.getCopyOfContextMap();

try {
    MDC.put("request_id", "req-42");

    String requestId = MDC.get("request_id");
    if (!"req-42".equals(requestId)) {
        throw new AssertionError("wrong MDC request_id");
    }

    Map<String, String> copy = MDC.getCopyOfContextMap();
    if (copy == null
            || !"req-42".equals(copy.get("request_id"))) {
        throw new AssertionError("wrong MDC snapshot");
    }
} finally {
    if (before == null) MDC.clear();
    else MDC.setContextMap(before);
}
```

Đây là đoạn code nằm trong method test đã có `MDC` và `java.util.Map`. Nó kiểm tra key và snapshot ở **cùng thread**; chưa chứng minh log cuối có chứa context.

### Kiểm thử snapshot không bị thay đổi

Thực hiện:

1. `MDC.put("request_id", "req-A")`.
2. `Map snapshot = MDC.getCopyOfContextMap()`.
3. `MDC.put("request_id", "req-B")`.
4. Assert `MDC.get(...)` là `req-B`.
5. Assert `snapshot.get(...)` vẫn là `req-A`.
6. Khôi phục context trước bài test.

Đây là thử nghiệm trọng tâm cho mọi code dùng snapshot khi submit async task.

### Kiểm thử nested scopes

Mở scope cha có `request_id=req-parent`, vào scope con đổi thành `req-child`, sau đó thoát scope con. Assert cha lại đọc được `req-parent`. Thử cả đường con ném exception; khôi phục phải xảy ra trong `finally`.

### Kiểm thử thread pool

Dùng `Executors.newSingleThreadExecutor()` để buộc **tái sử dụng một worker thread**:

- Task A có context A.
- Task B có context B.
- Task C không có context nào.
- Sau từng task, worker không giữ ID của task trước.

Thử với cả task thành công và task ném exception. Nếu có wrapper/SDK propagation, assert context tại **nơi log được phát** trong worker, không chỉ tại thread submit.

### Kiểm thử logging event, không chỉ MDC hiện tại

Với Logback Classic, có thể gắn một `ListAppender<ILoggingEvent>` vào logger test rồi xem:

```java
event.getMDCPropertyMap().get("request_id")
```

Đây là snippet: `event` phải là một `ILoggingEvent` thu được trong test đã khởi tạo Logback và appender phù hợp. Kết quả phản ánh context đi cùng **event**, không phải gọi lại `MDC.get` trên thread test sau đó.

Có thể kiểm tra thêm `getLevel()`, `getFormattedMessage()` và `getThrowableProxy()`. Sau test cần tháo/dừng appender tạm và hoàn nguyên cấu hình logger; tránh ảnh hưởng những test chạy song song.

### Kiểm thử output thực và collector

Sau khi event test đúng:

1. Dùng encoder/layout thật để định dạng event.
2. Kiểm tra `%X{request_id}` trong text hoặc JSON field `request_id`.
3. Xác minh UTF-8, quote, newline, dữ liệu thiếu và fallback theo schema.
4. Phát hai request với ID khác nhau qua server/consumer thật.
5. Xác nhận kho log tập trung không gắn nhầm ID giữa request.
6. Xác nhận các event ngoài request không mang giá trị cũ.
7. Kiểm tra thông tin nhạy cảm giả không xuất trong mọi kênh.

**Không coi việc `MDC.get` trả đúng trong unit test là bằng chứng collector đã có log.** Chỉ có thể kết luận điều đó sau khi kiểm tra cả đường xuất/thu thập.

## 13. Bảo mật khi đọc và xuất giá trị MDC

Các context key có thể chứa thông tin liên kết người dùng/tenant, route hoặc dữ liệu từ header. Một số rủi ro:

- `MDC.get("tenant_id")` trả ID chưa được xác thực từ header client.
- `request_id` chứa newline hoặc ký tự điều khiển, gây **log injection**.
- `MDC.getCopyOfContextMap()` bị in nguyên ra logger và làm lộ toàn bộ context.
- `MDC` chứa token, cookie, Authorization header hoặc dữ liệu cá nhân.
- Context giữ lại trên worker thread và bị gắn nhầm vào request khác.
- Encoder JSON xuất nhiều field hơn người vận hành dự kiến.
- Collector cho phép người không có quyền tra log theo ID nhạy cảm.

**Không dùng MDC làm nguồn sự thật cho authorization.** Ví dụ kiểm tra quyền truy cập dựa trên `MDC.get("tenant_id")` là sai mô hình nếu MDC có thể thiếu hoặc đến từ nguồn không tin cậy. Quyết định bảo mật phải dựa trên security context đã xác thực; MDC chỉ là thông tin phục vụ quan sát và cần được thiết lập từ nguồn đáng tin khi ghi log.

### Validation giá trị trước khi đưa vào MDC

Một hợp đồng request ID đơn giản có thể là:

- Dài 1–64 ký tự.
- Chỉ chứa chữ cái, chữ số, dấu chấm, gạch dưới, gạch ngang.
- Không chứa newline, tab, ký tự điều khiển hoặc secret.
- Header thiếu/sai thì tạo ID mới theo chính sách.

Ví dụ đoạn code kiểm tra:

```java
static boolean validRequestId(String value) {
    return value != null
            && value.length() >= 1
            && value.length() <= 64
            && value.matches("[A-Za-z0-9._-]+");
}
```

Đây là helper minh họa trong một Java class. Nó **không phải** validator W3C trace ID; trace ID chuẩn cần được xử lý bằng tracing instrumentation. Tương tự, có field hợp lệ về định dạng **không chứng minh** nó đáng tin để xác thực người gọi.

### Đọc rồi log lại có tạo log trùng không?

Khi code gọi:

```java
String id = MDC.get("request_id");
log.info("request_id={}", id);
```

bạn đã **đưa context vào message**. Nếu layout cũng dùng `%X{request_id}`, một dòng có thể chứa ID hai lần:

```text
INFO rid=req-42 request_id=req-42
```

Không nhất thiết sai, nhưng có thể làm log dài, tăng volume và gây parser hiểu nhầm. Nếu mục tiêu chỉ là gắn ID vào mọi event, **đặt MDC một lần rồi để layout/encoder đọc** thường hợp lý hơn việc thủ công thêm ID vào từng message.

## 14. Hiệu năng và quy ước sử dụng

`MDC.get("key")` là thao tác nhỏ nhưng không có nghĩa có thể gọi tràn lan trong hot path mà không đo. Bản thân chi phí logging còn gồm formatting, JSON serialization, I/O, queue và collector.

Các quy tắc hữu ích:

1. Đặt `request_id` một lần ở ranh giới request, không tạo ID mới cho mỗi message.
2. Dùng key tên ổn định; tránh các tên key theo request như `"request_" + id` làm map tăng không giới hạn.
3. Giữ context nhỏ và không chứa object lớn; SLF4J MDC lưu value dạng string.
4. Chỉ lấy `getCopyOfContextMap()` khi cần snapshot toàn bộ; đọc một key thì `MDC.get` rõ ràng hơn.
5. Tránh in toàn bộ snapshot mỗi lần log.
6. Nếu dùng propagation wrapper, cân nhắc chi phí copy map cho hàng triệu task rất nhỏ.
7. Không xem `MDC.get` là cơ chế chia sẻ state liên-thread; chọn API data passing thích hợp cho nghiệp vụ.
8. Không dùng `request_id` làm metric label có cardinality cao; tìm ID ở log/tracing, nhóm metric theo service/event/error code ổn định.
9. Kiểm tra thời điểm capture MDC khi dùng async appender/backend.
10. Khi đẩy context qua mạng, truyền những trường được cho phép và có giới hạn kích thước header/metadata.

**MDC không bền vững và không lưu lịch sử.** Khi process kết thúc, context trong bộ nhớ biến mất; gọi `MDC.get` không lấy lại được ID của request hôm qua. Để tìm log cũ, dùng kho log/tracing có retention và quyền truy cập phù hợp.

## 15. Bảng chẩn đoán lỗi khi đọc MDC

| Hiện tượng | Nguyên nhân thường gặp | Cách kiểm tra |
| --- | --- | --- |
| `MDC.get("request_id") == null` | Key chưa đặt, đã xóa hoặc đang ở ngoài request | Xác định điểm đặt, scope, lifecycle. |
| `MDC.get("requestId")` trả null dù log có `request_id` | Sai tên key/case | Chuẩn hóa tên key chính xác. |
| `getCopyOfContextMap()` trả null | Không có map/context ở thời điểm gọi, tùy adapter | Kiểm tra null trước khi đọc; xác minh provider. |
| Snapshot giữ ID cũ sau `MDC.put` mới | Snapshot là copy, không live view | Lấy snapshot mới nếu thực sự cần current map. |
| Worker thread không thấy ID | Không có context propagation | Snapshot tại submit, áp và restore trong worker. |
| Worker B đọc ID của task A | Quên dọn/restore trong thread pool | Dùng `finally`; test worker reuse. |

| Event async thiếu ID sau khi đã cleanup | Context chưa được capture đúng tại event creation | Kiểm tra async appender/deferred processing. |
| `MDC.get` luôn null dù `put` vừa gọi | Provider/adapter không hỗ trợ hoặc logging runtime sai | Kiểm tra SLF4J provider/backend và cảnh báo startup. |
| JUL ghi log nhưng `MDC.get` không có ý nghĩa | JUL không có MDC chuẩn và thiếu bridge/tích hợp | Thiết kế context/handler phù hợp. |
| ID trong message nhưng không query theo field được | Context bị nối vào text, không xuất field JSON | Dùng encoder có cấu trúc hoặc parser có kiểm thử. |
| Output có ID của request khác | Thread reuse, context đặt sai hoặc HTTP filter lifecycle lỗi | Test hai request xen kẽ, cleanup/cancellation. |
| Text chứa nhiều dòng giả | ID chưa validate có newline | Giới hạn độ dài/charset; encode/escape đúng. |
| Một ID xuất hai lần trong một dòng | Vừa in `%X` vừa tự thêm ID vào `%msg` | Chọn một nơi hiển thị hoặc chấp nhận rõ chủ đích. |
| Không thấy log dù MDC đúng | Logger level, filter, appender hoặc collector | Chẩn đoán đường event đến output, không chỉ MDC. |

### Quy trình xác minh từ mã nguồn đến kho log

```text
MDC.put(key,value) đã chạy trong scope?
   |
   +-- Không --> Kiểm tra filter/interceptor/job wrapper.
   |
   +-- Có --> MDC.get(key) cùng thread/scope đúng?
                |
                +-- Không --> Sai key, cleanup sớm hoặc adapter.
                |
                +-- Có --> Có đổi thread/process?
                             |
                             +-- Có --> Xem propagation và trust boundary.
                             |
                             v
                         Logging event có MDC map đúng?
                             |
                             +-- Không --> Kiểm tra capture/async/backend.
                             |
                             v
                         Layout/encoder có xuất key?
                             |
                             +-- Không --> %X / JSON MDC provider / config.
                             |
                             v
                         Collector có parse và giữ field?
                             |
                             +-- Không --> Check ingest/filter/mapping.
                             |

```

Đừng khắc phục việc thiếu MDC bằng cách chèn `System.out.println(MDC.getCopyOfContextMap())` vào mọi chỗ. Cách đó dễ lộ dữ liệu và làm thay đổi volume log. Ưu tiên test nhỏ có ID giả và kiểm tra đường đi theo từng tầng.

## 16. Bài tập tự kiểm tra

### Bài 1 — Đọc key đang có

Cho:

```java
MDC.put("request_id", "req-91");
String a = MDC.get("request_id");
String b = MDC.get("requestId");
```

Hãy xác định `a` và `b` trong backend MDC tương thích khi trước đó không có `requestId`.

**Đáp án:** `a` bằng `"req-91"`. `b` bằng `null` vì hai key khác nhau. Không phải vì `get` lỗi mà vì key có phân biệt tên.

### Bài 2 — Đọc sau cleanup

Cho:

```java
MDC.put("request_id", "req-A");
MDC.remove("request_id");
String result = MDC.get("request_id");
```

**Đáp án:** `result` là `null` trong scope này. Nếu request code cần ID sau khi cleanup, nó phải giữ một biến nghiệp vụ/đối số riêng phù hợp, không trông chờ MDC còn dữ liệu mãi.

### Bài 3 — Snapshot và giá trị hiện tại

```java
MDC.put("request_id", "A");
Map<String, String> copy = MDC.getCopyOfContextMap();
MDC.put("request_id", "B");
```

Hỏi `copy.get("request_id")` và `MDC.get("request_id")` trả gì?

**Đáp án:** `copy` giữ `"A"`, còn `MDC.get` trả `"B"`. Snapshot là bản sao tại thời điểm gọi.

### Bài 4 — Chọn cách đọc khi dữ liệu có thể thiếu

Ứng dụng có cả HTTP request và scheduled job; `MDC.get("request_id")` đôi lúc trả null. Có phải tất cả đều là bug?

**Đáp án:** Không. Job có thể không có HTTP request. Chỉ coi là bug khi **contract của ngữ cảnh cụ thể** yêu cầu field đó tồn tại. Với job, `job_run_id` có thể phù hợp hơn.

### Bài 5 — Đọc qua executor

Thread main đặt `request_id=req-A`. Một task trên thread pool đọc `MDC.get("request_id")` nhận null. Vì sao? Cách sửa?

**Đáp án:** MDC không tự propagate an toàn tới worker pool. Capture context ở thread submit, áp vào worker trước khi chạy tác vụ, rồi khôi phục context trước đó trong `finally`; hoặc dùng framework propagation chính thức.

### Bài 6 — Nested scopes

Scope cha có `request_id=req-parent`. Scope con đặt `req-child` rồi gọi `MDC.remove("request_id")`. Điều gì sai?

**Đáp án:** Giá trị cha bị mất. Nếu scope có thể lồng nhau, cần lưu previous value/map và restore, không chỉ remove mù quáng.

### Bài 7 — Log có MDC nhưng text không hiển thị

Developer đã đặt `MDC.put("request_id", "req-42")`; `MDC.get` trả đúng. Pattern lại chỉ là `%level %msg%n`. Tại sao console không có ID?

**Đáp án:** Pattern không có converter đọc MDC. Thêm `%X{request_id}` hoặc cấu hình encoder có cấu trúc xuất MDC, rồi kiểm tra logging event và output thực.

### Bài 8 — JSON giữ kiểu nào?

`MDC.put("attempt", "3")` rồi encoder JSON xuất MDC. `attempt` có tự trở thành số JSON không?

**Đáp án:** Không nên giả định. MDC lưu chuỗi; encoder có thể xuất `"attempt":"3"`. Nếu consumer cần số, truyền field typed ở event qua API/encoder phù hợp hoặc mapping có kiểm soát.

### Bài 9 — Phân biệt dữ liệu chẩn đoán và dữ liệu bảo mật

Một ứng dụng đọc `tenant_id` từ MDC để cho phép user xem đơn hàng của tenant đó. Điều này có an toàn không?

**Đáp án:** Không nên lấy MDC làm nguồn authorization. Tenant được phép phải đến từ security context đã xác thực và kiểm tra quyền. MDC chỉ có thể phản ánh ID đã tin cậy để ghi log, và vẫn cần bảo vệ dữ liệu đó.

### Bài 10 — Kiểm tra đọc không rò context

Viết test chạy hai công việc A và B trên cùng một worker thread, sau đó thêm một công việc ngoài request. Kỳ vọng là gì?

**Đáp án:** Task A đọc A, task B đọc B và task ngoài request không đọc được A/B. Wrapper phải capture/restore mỗi task; test cả trường hợp task ném exception.

### Bài 11 — MDC và Throwable

Một lỗi được ghi bằng `log.error("failed", ex)` và event có `request_id`. Nếu console không thấy request ID, có thể kết luận `MDC.get` đã trả null?

**Đáp án:** Chưa. Cần kiểm tra event MDC map và pattern/encoder có xuất trường hay không. Throwable xuất được không đồng nghĩa với converter MDC đã được cấu hình.

### Bài 12 — Đọc context ngoài phạm vi

Ứng dụng có log ở startup, request thread và shutdown hook. Đâu là nơi có thể dùng `request_id` đáng tin?

**Đáp án:** Khi request scope hợp lệ đã được thiết lập và propagation đúng. Startup/shutdown thường không có request ID; nên dùng service/environment, operation hoặc thông tin job phù hợp. Không tạo request ID chung giả cho mọi sự kiện.

## 17. Checklist áp dụng vào dự án Java

- [ ] Biết backend/provider đang hoạt động và API MDC tương ứng.
- [ ] Thống nhất tên key; `request_id` khác `requestId`.
- [ ] `MDC.get(key)` được xử lý như `String | null`, không ép kiểu mù quáng.
- [ ] Có quy tắc cho key vắng mặt, chuỗi rỗng và fallback hiển thị.
- [ ] Chỉ dùng MDC cho context logging, không làm nguồn authorization.
- [ ] Đặt context ở đúng ranh giới request/job/message.
- [ ] Khi có nested scope, snapshot/restore ngữ cảnh cha trong `finally`.
- [ ] Đã kiểm thử hai request liên tiếp trên một worker thread.
- [ ] Async/executor/reactive có propagation và cleanup phù hợp.
- [ ] Dùng `getCopyOfContextMap` khi thực sự cần snapshot; kiểm tra null.
- [ ] Hiểu snapshot không cập nhật khi gọi `MDC.put` về sau.
- [ ] Layout có `%X{key}` nếu muốn text hiển thị MDC.
- [ ] Encoder JSON có provider/map field MDC đúng khi cần structured logging.
- [ ] Test logging event map riêng với test output/collector.
- [ ] Không log toàn bộ context map hoặc header chứa secret.
- [ ] ID từ client được validate; không nhận newline/log injection.
- [ ] Không gắn request ID động vào metric label cardinality cao.
- [ ] Event sau cleanup không mang ID của request cũ.
- [ ] Không kỳ vọng MDC lưu lịch sử sau khi request hoặc process kết thúc.

**Kết luận:** `MDC.get(key)` đọc **một giá trị chuỗi trong context hiện tại**, `MDC.getCopyOfContextMap()` cung cấp **snapshot** để kiểm tra hoặc truyền sang tác vụ khác, còn `%X{key}`/encoder JSON quyết định **giá trị đó có được xuất trong log hay không**. Để sử dụng đúng, phải xử lý `null`, đặt tên key nhất quán, hiểu ranh giới thread, khôi phục context khi scope kết thúc và kiểm thử cả sự kiện lẫn đầu ra thực.
