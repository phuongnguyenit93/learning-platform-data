# Log4j2 Plugins: Extension Architecture, Creation, and Deployment

## 1. What Is a Log4j2 Plugin?

A **Log4j2 Plugin** is an extension component recognized, instantiated, and wired into the logging pipeline by **Log4j Core**, typically through configuration. This mechanism lets you add behavior without modifying Log4j's own source code: for example, creating an **Appender** that sends events to a custom destination, a **Filter** that applies filtering rules, a **Layout** that formats log records into another representation, or a **Lookup** that resolves values by convention.

In Log4j 2, many built-in components are themselves implemented as plugins. For example:

~~~xml
<Console name="OUT" target="SYSTEM_OUT">
    <PatternLayout pattern="%level | %msg%n"/>
</Console>
~~~

Here, **Console** is an Appender plugin and **PatternLayout** is a Layout plugin. The XML above is just an illustrative configuration snippet and must be placed inside a complete **Configuration / Appenders / Loggers** structure.

Plugins allow configuration to describe **which components exist, what attributes they have, and which child components they depend on**. Log4j Core looks up plugin metadata, creates instances via a factory or builder, and attaches them at compatible points.

**Important distinctions:**

- A **Log4j2 Plugin** is an extension point of **Log4j Core**, not a new method on `Logger`.
- **log4j-api** provides the API that applications call, such as **LogManager.getLogger()** and **logger.info()**; plugin configuration belongs to **log4j-core**.
- A **JAR dependency** containing code is not automatically a plugin; a plugin must be declared and registered so that Log4j can discover it.
- Log4j ships with a wide range of built-in plugins. You do not need to write a custom plugin if **Console, RollingFile, PatternLayout, ThresholdFilter, MarkerFilter**, or other built-in components already meet your requirements.

The goal of this article is to understand **when a plugin is needed, common plugin categories, annotations, and the discovery process**, and then build a custom Filter plugin using Java 17 and Maven.

## 2. Where Do Plugins Fit in the Log4j2 Architecture?

A simplified view:

~~~text
Application code
    |
    | log.info(...), log.warn(...)
    v
Log4j API
    |
    v
Log4j Core / LoggerContext
    |
    +-- Configuration, LoggerConfig, Filter
    |                      |
    |        PluginManager reads plugin descriptors
    |        and builds configured components
    |
    +-- Appender (plugin) ---------> output destination
    |      |
    |      +-- Filter (plugin) ----> accept/reject events
    |      |
    |      +-- Layout (plugin) ----> formatting
    |
    +-- Lookups, Policies, Strategies, Converters...
~~~

When initializing or updating configuration, Log4j Core reads a configuration file such as **log4j2.xml**, looks up plugins by **category/name**, converts configuration attributes into Java values, and constructs the objects.

When the application logs events, those constructed objects participate in the pipeline. **Log4j does not rescan the entire classpath or recreate every plugin on every LOG.info() call.** Discovery and configuration happen during the system/configuration lifecycle; each component is invoked according to its role when processing events.

**A plugin is not synonymous with an SLF4J provider or a Log4j implementation.** An application may use the Log4j API directly or use SLF4J through an adapter to Log4j Core. Regardless of the front-end API, the Appenders, Filters, and Layouts configured in Log4j Core remain backend plugin extension points.

## 3. Common Plugin Categories

| Type | Responsibility | Examples / Use Cases |
| --- | --- | --- |
| **Appender** | Sends events to a destination | Console, File, RollingFile, Socket, custom destination |
| **Layout/Encoder** | Converts a LogEvent into output data | PatternLayout, JsonTemplateLayout, custom format |
| **Filter** | Accepts, denies, or defers the decision to the next step | ThresholdFilter, MarkerFilter, business-rule filter |
| **Lookup (StrLookup)** | Looks up values for configuration interpolation or log context | env, sys, ctx, custom lookup |
| **Pattern converter** | Processes tokens in a pattern layout | Creating a custom conversion token |
| **TriggeringPolicy** | Decides when RollingFile should roll over | Size-based or time-based |
| **RolloverStrategy** | Decides actions during rollover | Renaming, deleting old files, policy-based compression |
| **RewritePolicy** | Transforms a LogEvent in a rewrite-enabled pipeline | Adding/adjusting metadata by rules |
| **ConfigurationFactory** | Reads and creates configuration from a source/format | Supporting a specialized configuration format |
| **TypeConverter** | Converts configuration strings into Java types | Custom value types for plugin attributes |

Some plugin categories have their own APIs and rules. **Not every plugin is an XML element**: Lookup plugins have their own category and are typically invoked through interpolation, whereas Appender, Layout, and Filter plugins usually belong to the **Core** category when appearing as elements in a configuration file.

If you only want to change the log level from INFO to DEBUG, adjust a PatternLayout, or add a RollingFile, you **do not need to create a new plugin**; simply configure the built-in plugins.

## 4. When Should You Write a Custom Plugin?

You should only create a custom plugin when standard components and valid configurations cannot express your requirement.

**Justified examples:**

1. You need a **Filter** that enforces a domain-specific rule based on a stable business field, which cannot be conveniently expressed with built-in Filters.
2. You need a **Layout** in a highly specialized format that still integrates with Log4j Core's lifecycle and encoders.
3. You need an **Appender** that sends logs to an internal ingestion system using a protocol not supported by standard plugins, while managing connections, errors, retries, and shutdown.
4. You need a **Lookup** for an application-controlled configuration source with well-defined security boundaries.
5. You need to extend rolling, formatting, or configuration mechanisms where an official extension point is supported.

**When you do not need a plugin:** filtering by level, marker, or common message strings, writing to Console/RollingFile, configuring JSON via a built-in layout, or adding standard context fields can usually be achieved with standard plugins. Writing a custom plugin increases code maintenance, testing scope, compatibility risk when upgrading Log4j, and the attack surface of the logging pipeline.

A good design rule: **try built-in plugins and official configuration first; only write an extension when there is a concrete functional gap.**

## 5. Core Annotations: @Plugin, category, and name

Log4j Core provides the annotation **org.apache.logging.log4j.core.config.plugins.Plugin**. Example declaration of a plugin named **ExcludeExactMessage**:

~~~java
@Plugin(name = "ExcludeExactMessage", category = Node.CATEGORY)
public final class ExcludeExactMessageFilter extends AbstractFilter {
    // The plugin component is implemented in the complete example below.
}
~~~

This is a **snippet**, not a standalone runnable class. **Node.CATEGORY** is the **Core** category, used for many components represented as configuration elements. You need to import **Plugin**, **Node**, and **AbstractFilter**.

Meaning of the attributes:

- **name**: the name Log4j uses to look up the plugin within its category, such as the XML tag **ExcludeExactMessage**. Within the same category, plugin name matching is **case-insensitive**.
- **category**: the plugin group. Category matching is **case-sensitive**; plugins written for Core configuration must declare the exact category.
- **elementType**: previously used in older configuration syntax; in modern Log4j 2.x documentation, this attribute is **deprecated**. Do not add it unless required for backward compatibility.
- **Duplicate plugin names in the same category**: can cause warnings and depend on discovery order. Do not intentionally reuse a built-in plugin's name to "override" it unless you fully control the classpath and understand the risks.

A plugin is not invoked merely because it has the annotation. Log4j also requires **registration metadata** generated at build time to discover the class, and if the plugin is used in configuration, it must have a **valid instantiation mechanism**.

## 6. @PluginFactory, @PluginBuilderFactory, and Parameter Annotations

For plugins that appear as elements in configuration (such as Appender, Filter, Layout), Log4j needs a way to construct the object:

| Mechanism | Best Fit | Idea |
| --- | --- | --- |
| **@PluginFactory** | Simple plugins with few parameters | A static method accepts attributes/elements from configuration and returns an instance |
| **@PluginBuilderFactory** | Plugins with many options, defaults, and validation | A static method returns a Builder; builder fields receive configuration values |

Annotations that pass values into a factory or builder:

- **@PluginAttribute("name")**: extracts a string attribute from configuration and converts it to the parameter type using a TypeConverter when needed.
- **@PluginElement("name")**: injects a child plugin/node, such as a Layout inside an Appender or a child policy.
- **@PluginConfiguration**: injects the current **Configuration** object.
- **@PluginNode**: injects the **Node** currently being processed.
- **@PluginValue**: injects the node's text value or `value` attribute according to plugin rules.
- **@PluginBuilderAttribute**: binds an attribute to a builder field.
- **@Required**: adds validation for mandatory configuration values in supported contexts.

Example of a factory signature:

~~~java
@PluginFactory
public static ExcludeExactMessageFilter create(
        @PluginAttribute("message") String message) {
    if (message == null || message.isBlank()) {
        return null;
    }
    return new ExcludeExactMessageFilter(message);
}
~~~

This is an **excerpt from the full class example**, not a standalone compilable program. When configured as:

~~~xml
<ExcludeExactMessage message="health.ping"/>
~~~

Log4j passes the **message** attribute as the factory parameter. The factory returns a Filter instance; if the configuration omits the value, the example above returns `null` to reject creating the component. In a real application, check the **Status Logger** because plugin creation failures can lead to unexpected logging behavior.

A **Builder** is usually easier to manage when there are many options, dynamic defaults, and child objects. There is no need to replace a simple plugin with a builder just to use an extra annotation.

## 7. How Are Plugins Discovered?

A critical step often overlooked when writing a custom plugin is **compile-time annotation processing**.

Typical workflow:

~~~text
Java code with @Plugin
       |
       v
javac + Log4j PluginProcessor
       |
       +-- Compile .class files
       |
       +-- Generate registration metadata:
           META-INF/org/apache/logging/log4j/core/
               config/plugins/Log4j2Plugins.dat
       |
       v
Package classes + metadata into JAR/classpath
       |
       v
PluginManager reads descriptor
       |
       v
Log4j Core resolves name/category and creates plugin from configuration
~~~

**Log4j2Plugins.dat** is a **binary descriptor generated by the annotation processor**, not a text file that developers should write or edit manually.

According to the discovery order in the Log4j 2.x documentation, Log4j prioritizes descriptors on the classpath, supports descriptors in OSGi, and only then falls back to legacy package-based mechanisms. Approaches such as:

- the **log4j.plugin.packages** property,
- **PluginManager.addPackages()**,
- the **packages** attribute on the Configuration element,

are marked **deprecated** in the Log4j 2.x documentation. Do not choose package scanning as the primary approach for new projects; use annotation processing and package the generated descriptor.

**Operational requirement:** both the plugin class and its descriptor must actually be present on the **runtime classpath** used by Log4j Core. If the plugin is compiled but missing from the runtime artifact, Log4j cannot instantiate it from its configuration name.

### Notes When Upgrading the JDK

On newer JDK versions such as JDK 23+, annotation processors are not enabled by default in the same way as before. **Declare the plugin processor explicitly in your build**, even if you are developing on JDK 17, so that builds remain consistent across local environments and CI.

If you need **GraalVM Native Image**, there are additional requirements for **reachability metadata** so the plugin works at native runtime. Log4j provides **GraalVmProcessor** for that purpose; a plugin working on the JVM does not automatically guarantee it is properly configured for a native image.

## 8. Complete Example: Writing a Filter Plugin in Java 17

We will create **ExcludeExactMessageFilter** to **deny exact matches** of the log message **health.ping** on a Console Appender. All other log records continue through the pipeline.

Learning objectives:

- Use **@Plugin(name, category)** to declare the plugin name and category.
- Use **@PluginFactory** and **@PluginAttribute** to read configuration.
- Extend **AbstractFilter** and override **filter(LogEvent)**.
- Return **DENY** when the message matches and **NEUTRAL** when it does not.
- Use **PluginProcessor** to generate the descriptor rather than relying on package scanning.
- Run code through **Log4j API** and verify that the **Log4j Core** plugin is applied.

**Example scope:** this filters only a single fixed message for easy verification. In production, you should not suppress all health-check-related errors; use safe event names and appropriate log/audit control policies.

### 8.1. Directory Structure

~~~text
log4j2-plugin-demo/

  src/
    main/
      java/
        example/
          logging/
            ExcludeExactMessageFilter.java

~~~

### 8.2. pom.xml

This example uses **Log4j 2.26.1**, **Maven**, and **JDK 17+**; Maven must be able to download dependencies from your configured repository. The version is pinned here to keep the example reproducible, not as a recommendation that every project must use this exact version.


**Why declare annotationProcessorPaths?** So Maven invokes **PluginProcessor** and generates the descriptor. Simply having **log4j-core** at runtime and the annotation on the class is not always sufficient across all toolchains or newer JDKs.

### 8.3. ExcludeExactMessageFilter.java

~~~java
package example.logging;

import org.apache.logging.log4j.core.Filter.Result;
import org.apache.logging.log4j.core.LogEvent;
import org.apache.logging.log4j.core.config.Node;
import org.apache.logging.log4j.core.config.plugins.Plugin;
import org.apache.logging.log4j.core.config.plugins.PluginAttribute;
import org.apache.logging.log4j.core.config.plugins.PluginFactory;
import org.apache.logging.log4j.core.filter.AbstractFilter;

@Plugin(name = "ExcludeExactMessage", category = Node.CATEGORY)
public final class ExcludeExactMessageFilter extends AbstractFilter {

    private final String messageToExclude;

    private ExcludeExactMessageFilter(String messageToExclude) {
        super(Result.DENY, Result.NEUTRAL);
        this.messageToExclude = messageToExclude;
    }

    @PluginFactory
    public static ExcludeExactMessageFilter create(
            @PluginAttribute("message") String message) {

        if (message == null || message.isBlank()) {
            return null;
        }
        return new ExcludeExactMessageFilter(message);
    }

    @Override
    public Result filter(LogEvent event) {
        String text = event.getMessage().getFormattedMessage();
        return messageToExclude.equals(text)
                ? Result.DENY : Result.NEUTRAL;
    }
}
~~~

**Key points to understand:**

1. **@Plugin(name = "ExcludeExactMessage", category = Node.CATEGORY)** registers the class under the configuration name **ExcludeExactMessage** in the Core category.
2. **@PluginFactory** is used by the configuration system to create an instance.
3. **@PluginAttribute("message")** receives the value from the XML element's `message` attribute.
4. The constructor **super(Result.DENY, Result.NEUTRAL)** passes `onMatch` and `onMismatch` values to `AbstractFilter`. In this example, **filter(LogEvent)** directly returns the corresponding `Result` values.
5. **getFormattedMessage()** retrieves the message after parameter substitution; comparing with **equals()** avoids accidentally filtering similar messages.
6. When the message does not match, **NEUTRAL** means **this Filter makes no blocking decision**, not a guarantee that the record will be output regardless of level or other Filters.
7. The factory rejects blank values by returning `null`. When an attribute is missing in configuration, check the Status Logger and verify that the application does not start with an unintended logging policy.
8. This class overrides only **filter(LogEvent)**, which is suitable for attaching to an **Appender** as shown. If placed at an early Logger filtering stage, other overloads of **AbstractFilter** may return `NEUTRAL`; to apply consistently across multiple stages, implement the appropriate overloads and test them separately.

In production, you can defensively check for null `LogEvent`/`message`, use stable event codes instead of free-form strings, and measure the cost of **getFormattedMessage()** under very high log volumes.

### 8.4. log4j2.xml

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<Configuration>
    <Appenders>
        <Console name="OUT" target="SYSTEM_OUT">
            <PatternLayout pattern="%level | %msg%n"/>
            <ExcludeExactMessage message="health.ping"/>
        </Console>
    </Appenders>

    <Loggers>
        <Root level="info">
            <AppenderRef ref="OUT"/>
        </Root>
    </Loggers>
</Configuration>
~~~

**Console** and **PatternLayout** are built-in plugins. **ExcludeExactMessage** is the plugin we just created. It is placed **inside the Console Appender**, so it only controls records passing through `OUT`; another Appender can have its own Filter.

**Root level="info"** blocks DEBUG logs at the logger stage. **target="SYSTEM_OUT"** is the output setting of **Log4j 2's Console Appender**; do not confuse it with the JDK's **java.util.logging.ConsoleHandler**, which typically writes to `stderr`.

**pattern="%level | %msg%n"** prints the log level, separator, message, and newline. This configuration intentionally omits timestamps so output remains deterministic across runs. In production, consider including timestamps, logger names, `requestId`, and `Throwable` formatting.

### 8.5. PluginDemo.java

~~~java
package example.logging;

import org.apache.logging.log4j.LogManager;
import org.apache.logging.log4j.Logger;

public final class PluginDemo {

    private static final Logger LOG =
            LogManager.getLogger(PluginDemo.class);

    public static void main(String[] args) {
        LOG.info("health.ping");
        LOG.info("order.accepted orderId={}", "ord-17");
        LOG.warn("inventory.slow attempt={}", 2);
        LOG.debug("cache.lookup key=order-17");
    }
}
~~~

### 8.6. Compile and Run

In the **log4j2-plugin-demo** directory with Maven/JDK 17+:

~~~bash
mvn -q clean compile exec:java -Dexec.mainClass=example.logging.PluginDemo
~~~

**Program stdout with the plugin and configuration above:**

~~~text
INFO | order.accepted orderId=ord-17
WARN | inventory.slow attempt=2
~~~

The program never calls **System.out.println()**; both lines are written to stdout by the **Log4j Core Console Appender**. Maven may print its own build or environment messages; the block above shows the two application log lines.

| Call | Root level | Filter on Console | Result |
| --- | --- | --- | --- |
| INFO health.ping | Passes | DENY due to message match | Not printed |
| INFO order.accepted | Passes | NEUTRAL | Printed as INFO |
| WARN inventory.slow | Passes | NEUTRAL | Printed as WARN |
| DEBUG cache.lookup | Below INFO | Does not reach Appender | Not printed |

**What proves the plugin worked?** Both INFO records pass the Root level. Without the Filter plugin, **health.ping** would also be printed. Once the plugin is built and attached, only that exact message is denied.

To verify the descriptor after compilation, check for the file:

~~~text
target/classes/META-INF/org/apache/logging/log4j/core/config/plugins/Log4j2Plugins.dat
~~~

If the file does not exist, inspect annotation processing and compiler output before suspecting the XML.

### 8.7. Purposeful Configuration Test

A useful verification test: change **message="health.ping"** to **message="order.accepted orderId=ord-17"** and run again. The `order.accepted` record is then dropped while `health.ping` is printed, confirming that the XML attribute value is injected into the factory.

This is only a way to **test configuration on a demo project**. In a real product, never change filtering rules without assessing operational impact: a single change can drop critical logs, including error or audit logs.

## 9. From Demo to Production Plugin: Additional Design Considerations

A plugin that merely works is not necessarily ready for long-term operation.

### A. Choosing the Right Interception Point

- **Global/Logger filter:** can decide early, helping reduce `LogEvent` creation overhead if the right overloads and stage are used.
- **AppenderRef filter:** routes or restricts events at a specific reference to an Appender.
- **Appender filter:** drops records only when they reach a particular destination, suitable when the goal is to exclude logs from that destination alone.
- **Layout:** handles data presentation and should not be misused to decide whether events are emitted.
- **Appender:** decides how writing, resources, and publishing errors are handled; do not hide transport-level behavior inside a Filter.

Log4j Filters use **ACCEPT**, **DENY**, and **NEUTRAL**. Across different stages, **ACCEPT** can take precedence over level checks—especially at the Logger stage—while **NEUTRAL** continues the existing decision flow. Do not mechanically replace `DENY` with `ACCEPT`, and verify the exact stage where your Filter participates.

### B. Processing Overhead

Applications handling tens of thousands of logs per second must pay attention to:

- Avoid complex regexes or re-parsing JSON for every `LogEvent` when comparing a single event code suffices.
- Avoid network calls, database queries, or I/O inside **filter()**.
- Never invoke a logger from inside a Filter plugin on the same logging path it is filtering; doing so can cause infinite recursion or deadlocks.
- Keep state immutable or thread-safe; the same plugin instance can be shared across multiple threads.
- Test how the filter handles null messages, exception messages, parameterized formats, and asynchronous logging.
- Prefer **logger levels** or built-in filters if the goal is simply to drop DEBUG/TRACE; do not write a plugin for simple threshold filtering.

### C. Security and Reliability

- Avoid placing secrets, tokens, cookies, personal data, or unsanitized payloads into log messages or plugin metadata.
- Do not rely on a Filter as your sole secret-masking mechanism: accepted records may still contain sensitive data; minimize data at the source and use proper encoders/redaction.
- If a plugin reads files, classpath resources, environment variables, or external systems, restrict access scope and never treat untrusted content as executable configuration.
- Do not enable risky lookups or extensions just to work around a discovery issue. In particular, keep Log4j updated according to your project's security policy and understand the implications of configuration interpolation.
- A custom Appender must define a failure policy: error handling, retries, queuing, disconnects, shutdown, and memory bounds.
- Mandatory audit logs have strict requirements for completeness, integrity, and retention; do not arbitrarily drop them with sampling or filter plugins to save costs.

A rule like **health.ping** should only exclude permitted periodic/success events—never filter broadly on every name containing **health**, which could drop **health.failed**.

## 10. Plugin Factory/Builder: Controlling Configuration and Lifecycle

When a plugin has attributes, you should define:

1. **Required attributes:** for example, an Appender needing a name, endpoint, or specific policy.
2. **Default values:** explicit, safe, and not accidentally dependent on the classpath.
3. **Validation:** reject invalid values early and emit clear configuration errors via the Status Logger.
4. **Child objects:** use **@PluginElement** when the plugin requires a Layout, child Filter, or other policies.
5. **Lifecycle:** Appenders, Filters, and resource holders may need `start`/`stop`/`close`, synchronization, and cleanup aligned with Log4j Core.
6. **Reconfigurability:** changing the XML file or environment can create new plugin instances; manage resources, state, and threads cleanly during reconfiguration.
7. **Configuration traceability:** plugin name, category, and error messages must be clear enough for troubleshooting.

If a plugin has many options, **@PluginBuilderFactory** with a Builder is advantageous: builder fields use **@PluginBuilderAttribute** with Java defaults, and `build()` enforces constraints. You do not need a Builder for every single-attribute Filter like the demo.

### How Can a Factory Fail?

The demo's factory returns `null` if **message** is missing. Log4j may log an internal error and continue configuring the remaining components; **do not assume** the Filter was attached just because the XML contains the plugin tag. Include a "health.ping must be dropped" check in automated tests, and inspect the Status Logger on startup to catch misconfigurations.

## 11. Packaging Plugins in JARs, Multi-Module Projects, and Shaded JARs

For a single-module project like the demo, **target/classes** contains the compiled classes, **log4j2.xml**, and the generated descriptor. When packaging a JAR, ensure the descriptor is included alongside the classes.

For multi-module projects:

- The plugin module is compiled with **PluginProcessor** and generates its own descriptor.
- The final application module declares a runtime dependency on the plugin JAR along with a compatible **log4j-core**.
- The application's configuration file references the plugin by its declared **name**; merely mentioning the plugin in XML does not put the JAR on the classpath.

**A subtle bug in shaded/uber JARs:** multiple dependencies can contain **Log4j2Plugins.dat** at the exact same path. If the packaging tool **keeps only one descriptor** and discards the rest, some plugins will disappear even though their classes are present. Use a **descriptor merge/transform strategy appropriate for your Log4j version and build tool**, and test the final packaged artifact; never simply copy one file and overwrite duplicates.

**When running a native image:** the annotation processor registering the plugin for the JVM is not sufficient in all cases. Check the GraalVM reachability metadata supported by Log4j and your application's native image configuration.

**When running in OSGi:** discovery may inspect descriptors in active bundles; test bundle lifecycles and plugin loading order separately.

## 12. Lookups, PatternConverters, and Key Differences

A **Lookup** plugin typically implements **StrLookup** under the **StrLookup.CATEGORY** category. It does not have to be a Core XML element. Lookups use interpolation to resolve values by prefix and context; you must understand which expressions are evaluated when **reading configuration** and which are evaluated per **LogEvent**.

A **PatternConverter** plugin adds a conversion token to **PatternLayout**. It differs from a Lookup: a PatternConverter runs when the layout formats a log event, and some converters can be optimized to reduce memory allocations. Do not choose a Lookup just to replace every conversion token; performance and semantics differ.

An **Appender** plugin is generally more complex than a Filter because it must manage I/O, write failures, resources, and lifecycle. If you only want to change the Console format, start with **PatternLayout** or a built-in encoder rather than writing a new Appender.

A **TypeConverter** plugin converts configuration attributes into Java types for factories and builders; it is not for serializing a `LogEvent` to JSON. Choosing the right extension point keeps each plugin focused and easier to test.

## 13. Common Pitfalls When Writing Plugins

| Symptom | Common Cause | How to Fix |
| --- | --- | --- |
| Log4j reports unknown plugin name | Missing descriptor or plugin JAR not on runtime classpath | Check PluginProcessor, Log4j2Plugins.dat, and classpath |
| Class exists but XML cannot use it | Missing @Plugin or category/name mismatch | Verify annotation and XML tag name |
| Plugin found but not instantiated | Missing @PluginFactory/@PluginBuilderFactory for a Core config plugin | Check static factory/builder and validation |
| Factory receives null despite XML value | Wrong @PluginAttribute name, misconfiguration, or incompatible converter | Match exact attribute name and type |
| Custom Filter does not drop logs | Attached at wrong stage, wrong overload overridden, or returns NEUTRAL | Check Filter placement and `filter(LogEvent)` / overloads |
| DEBUG not printed even though Filter allows it | Root/Logger level is INFO | Check levels before Filter/Appender |
| Plugin works in IDE but disappears on deploy | Packaging dropped the descriptor or JAR | Inspect final artifact and actual runtime classpath |
| Plugin disappears in fat JAR | Multiple Log4j2Plugins.dat files were not merged | Configure descriptor merging and test after packaging |
| Logs printed twice | Additivity or multiple AppenderRefs | Inspect Loggers/Appenders structure |
| Duplicate plugin name | Plugin collision in the same category | Use a unique name and check discovery warnings |
| Custom package scanning has no effect | Relying on deprecated discovery APIs | Prefer the annotation processor |
| App uses SLF4J + another backend | Log4j Core config is not on the active path | Identify the actual logging provider/backend first |
| Custom Appender slows down requests | Synchronous I/O, retries, or locks in `append` | Design backpressure, timeouts, and shutdown |
| Filter causes recursive logging | Plugin logs back into the same pipeline | Remove internal logging on the filter path or use appropriate diagnostics |
| Plugin fails in native image | Missing metadata/reflection config | Check GraalVM reachability and native build config |

### What Order Should You Troubleshoot In?

1. Confirm the application actually uses **Log4j Core** as its backend.
2. Confirm the plugin JAR and **log4j-core** are on the runtime classpath with compatible versions.
3. Check whether **Log4j2Plugins.dat** exists in the build output or JAR.
4. Verify **@Plugin name/category**, the factory/builder, and configuration attributes.
5. Verify **log4j2.xml** is being loaded and the plugin tag is in the right location.
6. Check the **Status Logger** for discovery, instantiation, or conversion errors.
7. Send test records at multiple levels, including cases that should be filtered and cases that should be kept.
8. Test the packaged artifact, not only the IDE run configuration.

If you are using Maven, the command:

~~~bash
mvn dependency:tree
~~~

reveals the versions of **log4j-api**, **log4j-core**, SLF4J adapters, and libraries carrying plugins. Avoid mixing Log4j 2.x with Log4j 3.x APIs or plugin annotations due to structural version differences.

## 14. Plugins and Dynamic Reconfiguration: What to Test

Log4j 2 supports reconfiguration depending on the configuration mechanism and environment. When configuration reloads, new plugin instances may be constructed while old instances must be stopped and cleaned up according to the lifecycle.

For stateful plugins:

- Do not hold a static connection that every new instance races to close.
- Use proper concurrency control if the Filter or Appender maintains state.
- Ensure **start/stop** and shutdown do not lose logs outside acceptable policy.
- Test what happens when a configuration reload fails: does the application keep the old configuration or fall back, and what happens to critical logs?
- Do not assume a plugin registered in the JVM will work across every `LoggerContext` or `ClassLoader` in multi-module environments.
- In multi-tenant or isolated environments, avoid caching context data in the wrong scope.

For stateless plugins like the string-matching Filter in the demo, keeping **messageToExclude** immutable makes testing easier. Even so, multiple threads can pass through the same instance, so any future changes must still be evaluated for thread safety.

## 15. Testing a Plugin Before Deployment

A meaningful plugin test suite should cover **source code, configuration, and packaging**, not just calling the factory directly and checking its return value.

**Unit tests:**

- Factory receives the **message** attribute and returns an instance.
- Blank values are handled according to policy.
- **health.ping** returns `DENY`.
- **order.accepted** returns `NEUTRAL`.
- Error events like **health.failed** are not mistakenly dropped.

**Integration tests:**

- Place **log4j2.xml** on the actual classpath.
- Log at INFO/WARN levels and verify Appender output.
- Verify DEBUG is not emitted when Root level is INFO.
- Test a missing or uninitialized plugin and confirm the system emits observable configuration error signals.
- Run tests after build/packaging to verify the metadata descriptor is intact.

**Non-functional tests:**

- Throughput under high event volume.
- CPU and memory allocation inside the Filter.
- Thread safety when multiple Loggers emit concurrently.
- Per-event cost when formatting messages early.
- Impact during configuration reload and shutdown.
- Preservation of critical logs and protection of sensitive data.

Do not benchmark logging with a single run of a few lines: warm up the JVM, account for encoder/I/O/backend overhead, and measure under a production-like configuration.

## 16. Frequently Asked Questions

### Is a Log4j2 plugin a Java ServiceLoader provider?

They are not the same concept. **PluginManager/PluginProcessor/Log4j2Plugins.dat** is **Log4j Core**'s extension registration mechanism. An **SLF4J provider** connects the SLF4J 2.x facade to a logging implementation; that is a different role.

### Can you install a plugin just by dropping a JAR into a directory?

Only if the JAR contains the class and its descriptor, the JAR is actually on the runtime classpath or bundle loaded by Log4j, and the configuration references the plugin properly. Merely having a JAR file on disk does not mean a classloader has loaded and discovered it.

### How do @Plugin and @PluginFactory differ?

**@Plugin** declares the plugin's type, name, and category. **@PluginFactory** tells a Core configuration plugin **how to create an instance** and receive attributes/child nodes. Both annotations work together with the annotation processor so the configuration can run. Not every plugin category requires a factory following the same Core rules.

### Does NEUTRAL mean definitely accepted?

No. It means **that Filter neither decisively denies nor accepts the event**, allowing the pipeline to continue evaluation. The record can still be rejected by log levels, another Filter, or the Appender.

### When should you use @PluginBuilderFactory?

When a component has many attributes, defaults, nested plugins, validation, and a non-trivial lifecycle. A Builder keeps configuration clear and convenient to test. For a single-attribute Filter, **@PluginFactory** is usually enough.

### Why does a plugin work on JDK 17 but fail to be discovered after upgrading the JDK?

Check **annotation processing**. Some newer toolchains and JDKs do not run processors automatically unless explicitly configured. Verify the generated metadata after compilation and declare **PluginProcessor** in the build rather than relying on deprecated package scanning.

### Should you write a plugin to suppress all logs from a package?

Usually, no new plugin is needed. You can configure the log level for a **LoggerConfig** by package name and additivity, or use built-in Filters. Write a plugin when you need a specialized policy that built-in configuration cannot express.

### Can a plugin access sensitive data inside a LogEvent?

Depending on its placement and API, a plugin can receive the message, `Throwable`, and context data. Treat it as a trusted pipeline component: control dependencies, inputs, access permissions, output data, and safety when handling unsanitized log data.

## 17. Log4j2 Plugin Creation Checklist

1. Define the **functional goal**; try built-in plugins first.
2. Choose the **right extension point**: Filter, Appender, Layout, Lookup, Converter, or Policy.
3. Give **@Plugin** a clear, unique name within its category; use the exact category.
4. For Core plugins used in configuration, provide **@PluginFactory** or **@PluginBuilderFactory**.
5. Accept values via **@PluginAttribute**, **@PluginElement**, and apply validation where appropriate.
6. Enable **PluginProcessor**; verify **Log4j2Plugins.dat** exists after building.
7. Ensure classes and descriptors travel together in the **JAR on the runtime classpath**; check shaded JARs and native images if applicable.
8. Attach the plugin at the right place in configuration; distinguish **Logger, AppenderRef, Appender**, and Filter stages.
9. Design clearly for thread safety, performance, lifecycle, security, error handling, and logging policy.
10. Test **accepted cases, denied cases, configuration errors, different levels, multithreading, and the final packaged artifact**.

**Conclusion:** **Log4j2 Plugins** are the mechanism for extending Log4j Core through **annotations, descriptors, and factories/builders**, letting you plug custom components into configuration without modifying Log4j itself. Prefer standard plugins whenever they suffice; when you must build a new plugin, understand **build-time discovery, pipeline stages, packaging, and testing** so you do not drop logs or introduce hard-to-diagnose operational issues.
