# What is MDC? Mapped Diagnostic Context in Java Logging

## Lesson Objectives

When multiple requests are processed concurrently in a Java application, log lines are often interleaved. Looking only at the timestamp and thread name does not always tell you which line belongs to which request. **MDC (Mapped Diagnostic Context)** helps attach **key–value pairs describing context** to logging events generated within a processing scope, so that the same requestId, traceId, or operation appears consistently across log lines without having to pass them manually into every message.

This lesson belongs to the **MDC** group of **Java Core Logging**, directly answering the question **"What is MDC?"**. You will learn:

- The concept and purpose of MDC in multi-request/multi-thread Java applications.
- The differences between **MDC**, message, logger name, level, thread, Marker, SLF4J fluent key–value, and distributed tracing.
- The **put, get, remove, clear, putCloseable, getCopyOfContextMap, setContextMap** APIs of **org.slf4j.MDC**.
- How Logback prints MDC via **%X{key}** and provides a default value when a key is missing.
- The **set → log → remove** lifecycle to prevent context leakage between requests in a thread pool.
- Why MDC **does not automatically propagate across every executor, CompletableFuture, or service boundary**, and how to copy/restore context in a controlled manner.
- How MDC fields can flow into JSON logging, security limits, cardinality, and common pitfalls.
- A compiled and tested **Java 17 + SLF4J + Logback** example with deterministic output for both the request thread and worker thread.

## 1. What is MDC?

**MDC** stands for **Mapped Diagnostic Context**. Simply put, it is a set of **key–value** pairs, typically Strings, attached by the logging system to the current execution context.

For example:

~~~text
requestId = req-17
operation = payment
~~~

Suppose the application logs sequentially:

~~~text
INFO  | requestId=req-17 | event=request.started
WARN  | requestId=req-17 | event=dependency.retry attempt=2
INFO  | requestId=req-17 | event=request.completed status=200
~~~

The three lines above share the same **requestId=req-17**, helping operators link them into a single processing flow. Developers do not always have to concatenate **requestId=...** into every message if the backend/encoder is configured to read values from MDC.

**MDC is not a storage system or a database.** It does not store events itself, does not open log files, does not create distributed traces, and does not guarantee that every record is emitted. MDC only provides **additional context** for a logging API/backend capable of reading that information.

### The Problem MDC Solves

Imagine a service receiving two requests:

~~~text
Request A: create order OD-42
Request B: refund RF-19
~~~

If it only logs:

~~~text
INFO  validating input
INFO  validating input
WARN  retry downstream
INFO  completed
INFO  completed
~~~

it is hard to tell which request the retry belongs to. If each request has its own requestId in MDC, the log format can become:

~~~text
INFO  requestId=req-A validating input
INFO  requestId=req-B validating input
WARN  requestId=req-A retry downstream
INFO  requestId=req-B completed
INFO  requestId=req-A completed
~~~

The requestId information solves the **correlation** problem: linking events belonging to the same unit of work. It **does not replace** a meaningful message, business outcome, or exception details.

## 2. Where Does MDC Sit in the Logging Pipeline?

A typical pipeline using **SLF4J API + Logback**:

~~~mermaid
flowchart LR
    A["HTTP request / Job"] --> B["Set MDC"]
    B --> C["Business code calls SLF4J Logger"]
    C --> D["Logback creates LoggingEvent"]
    D --> E["Appender + Layout/Encoder"]
    E --> F["Console / File / Collector"]
    B -. "requestId, operation" .-> D
~~~

Step-by-step explanation:

1. At the start of a request or job, the code/framework identifies the **requestId** and puts it into MDC.
2. Inner processing layers can still use familiar loggers such as **LOG.info** or **LOG.warn**.
3. The logging backend such as **Logback** retrieves the MDC information associated with the event according to its mechanism.
4. The layout or JSON encoder decides **which MDC fields are emitted and how they are printed**.
5. When the request finishes, the code must **remove the keys that were set**, usually in a **finally** block or an AutoCloseable scope.
6. For tasks that switch threads, context needs to be **propagated by the application's mechanism**; simply setting MDC on the parent thread does not guarantee the worker will see it.

MDC in **SLF4J** is a facade API. Runtime storage/retrieval behavior for MDC depends on the provider/backend's **MDCAdapter**. Logback Classic supports MDC per thread of execution; systems that do not support it or use a no-op adapter may not produce the same output.

## 3. How MDC Differs from Message, Logger, and Other Context Types

| Item | Example | Meaning |
| --- | --- | --- |
| **MDC key/value** | requestId=req-17 | Shared context for multiple events within the same scope |
| **Logger name** | com.example.checkout.OrderService | Name of the logger source, usually by class/package |
| **Log level** | INFO, WARN, ERROR | Severity/verbosity level of the event |
| **Message** | event=order.created orderId=OD-42 | What happened |
| **Thread name** | http-worker-4 | Thread emitting/recording the event; not a request ID |
| **Marker** | AUDIT, SECURITY | Additional tag for an event or group of events via the API |
| **Fluent key–value** | status=200 attached to a single log call | Field specific to a single logging event |
| **Trace context** | traceId/spanId | Distributed tracing context managed by a tracing system |
| **MDC** | requestId, operation, tenantId | Logging context map that can be emitted across multiple events |

**A logger name should not contain a dynamic requestId.** A logger is typically long-lived and reused across many requests; requestId is variable data and should go into MDC or an event field.

**MDC does not automatically turn a message into structured JSON.** If the pattern is text, MDC may simply be printed as a string. If using a JSON encoder that supports MDC, each key can be emitted as a JSON field; the structure and data types also depend on the encoder.

**MDC also does not replace distributed tracing.** Simply adding a traceId to logs does not generate traces/spans, does not propagate traceId over HTTP headers, and does not send telemetry to a tracing backend. For real tracing, proper instrumentation and propagators are required; MDC is only one way to surface context in logs.

## 4. Key APIs of org.slf4j.MDC

With **SLF4J**, basic MDC operations are static methods on **org.slf4j.MDC**.

| API | Effect | When to use |
| --- | --- | --- |
| **MDC.put(key, value)** | Sets/replaces the value for a key in the current context | When a request starts or when adding context |
| **MDC.get(key)** | Reads the current value of a key | Diagnostics or conditional checks |
| **MDC.remove(key)** | Removes a single key | Cleaning up a key owned by this scope |
| **MDC.clear()** | Clears the entire current context | When this scope owns the entire context |
| **MDC.putCloseable(key, value)** | Sets a key and returns a closeable scope whose close removes the key | Use in try-with-resources |
| **MDC.getCopyOfContextMap()** | Returns a copy of the current String–String pairs or null | Preparing to pass context to a worker |
| **MDC.setContextMap(map)** | Replaces the current context with a copy of the provided map | Restoring/setting context on the receiving thread |
| **MDC.getMDCAdapter()** | Accesses the underlying backend adapter in use | Integration diagnostics when truly needed |

A small example:

~~~java
// Illustrative snippet inside an application method that already has LOG.
MDC.put("requestId", "req-17");
try {
    LOG.info("event=request.started");
    LOG.info("event=request.completed status=200");
} finally {
    MDC.remove("requestId");
}
~~~

Even if code inside the try block throws an exception, the finally block still removes requestId when execution reaches it. This is especially necessary with a **thread pool**, because a worker thread may handle the next request immediately afterward.

### putCloseable and try-with-resources

~~~java
// Illustrative snippet: LOG is already declared.
try (MDC.MDCCloseable ignored =
             MDC.putCloseable("requestId", "req-17")) {
    LOG.info("event=request.started");
}
~~~

Upon leaving the scope, **close() removes the requestId key**. The advantage is not having to manually write a finally block for a single key. **Important:** according to the SLF4J API, putCloseable is a scope that **removes the key on close**, not **automatic restoration of a previous value**. If the key already had a value from an outer scope and you overwrite it, closing the scope does not automatically bring back the old value.

If you want to override and then **restore the original context**, save a snapshot beforehand and set the snapshot back afterward, rather than expecting putCloseable to behave like a stack of values.

### clear() or remove()?

- If you only created **requestId**, it is best to call **remove("requestId")** when finished.
- If a middleware owns the entire MDC at the start/end of a task, it can call **clear()** per that contract.
- If code runs inside a scope where the framework has already set traceId/tenantId, calling **clear()** indiscriminately can wipe out keys belonging to the outer scope.

**Ownership principle:** the component that adds a key is responsible for cleaning up that key, and should not delete context information owned by another component.

## 5. What Scope Is MDC: Thread, Request, or Process?

A common misconception is that "MDC is a request-wide global variable." This is **incorrect**.

With **Logback Classic**, MDC is typically managed per **thread**. A request processed sequentially on one thread can have its own context, but when work switches threads, the context is **not guaranteed to follow automatically**.

For example:

~~~text
Thread http-1: MDC.requestId = req-A
Thread http-2: MDC.requestId = req-B
Thread worker-1: may not have requestId yet
~~~

MDC does not turn into a JVM-wide global variable or a shared map for all requests. Static API calls do not mean **the map is a global shared map**; they operate on the thread's adapter/context according to the backend.

In classic synchronous applications, thread and request boundaries may overlap most of the time. However, with **ExecutorService, CompletableFuture, async servlets, message consumers, or reactive pipelines**, a single request can move across multiple threads, and conversely a single thread can handle multiple requests.

Therefore:

- **Do not assume every child thread inherits MDC**; specifically for executors/thread pools, Logback documents the need to copy and set the context.
- **Do not assume old context is automatically cleared** when a thread pool reuses a thread.
- **Do not use ThreadLocal/MDC as a distributed context propagation mechanism** over the network.
- If the framework supports context propagation, use the mechanism managed by the framework/tracing layer rather than rewriting it in every callback.

## 6. Complete Java 17 + Logback Example: Scope and Async Propagation

This hands-on example uses **Java 17**, **SLF4J API**, and **Logback Classic**. It demonstrates four behaviors with deterministic log output:

1. Outside the scope, **requestId** is not set yet, so the pattern prints **missing**.
2. Inside the scope, multiple events have **requestId=req-17** even though the messages do not concatenate the ID themselves.
3. A task submitted to **ExecutorService** does not automatically have requestId.
4. After **copying context to the worker**, the event has requestId; at the end of the task, the context is restored, avoiding leakage into subsequent tasks.

### File src/main/resources/logback.xml

~~~xml
<configuration>
  <appender name="CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
    <encoder class="ch.qos.logback.classic.encoder.PatternLayoutEncoder">
      <charset>UTF-8</charset>
      <pattern>%level | requestId=%X{requestId:-missing} | operation=%X{operation:-none} | %msg%n</pattern>

  </root>

~~~

Pattern breakdown:
- **%level** outputs INFO/WARN...
- **%X{requestId:-missing}** reads the MDC key requestId; when absent, it uses **missing**.
- **%X{operation:-none}** reads the operation key; if missing, it prints **none**.
- **%msg** gets the message formatted with SLF4J arguments.
- **%n** adds a newline.
- Root **INFO** allows both INFO and WARN in this exercise.

**The words missing/none are fallback values solely for readability**, and should not be interpreted as real requestIds. The backend only outputs fields selected by the configured pattern or encoder. Without %X in this pattern, setting MDC in code still will not make the ID appear on the console.

### File src/main/java/com/example/logging/MdcDemo.java

~~~java
package com.example.logging;

import java.util.Map;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;

public class MdcDemo {
    private static final Logger LOG = LoggerFactory.getLogger(MdcDemo.class);

    private static void restoreContext(Map<String, String> previous) {
        if (previous == null) {
            MDC.clear();
        } else {
            MDC.setContextMap(previous);
        }
    }

    public static void main(String[] args) throws Exception {
        LOG.info("event=application.ready");

        try (MDC.MDCCloseable request =
                     MDC.putCloseable("requestId", "req-17")) {
            LOG.info("event=request.started orderId={}", "OD-42");

            try (MDC.MDCCloseable operation =
                         MDC.putCloseable("operation", "payment")) {
                LOG.warn("event=dependency.retry attempt={}", 2);
            }

            ExecutorService executor = Executors.newSingleThreadExecutor();
            try {
                executor.submit(
                        () -> LOG.info("event=async.without_context")).get();

                Map<String, String> captured = MDC.getCopyOfContextMap();
                executor.submit(() -> {
                    Map<String, String> previous = MDC.getCopyOfContextMap();
                    try {
                        restoreContext(captured);
                        LOG.info("event=async.with_context");
                    } finally {
                        restoreContext(previous);
                    }
                }).get();

                executor.submit(
                        () -> LOG.info("event=async.after_context")).get();
            } finally {
                executor.shutdown();
                if (!executor.awaitTermination(5, TimeUnit.SECONDS)) {
                    executor.shutdownNow();
                }
            }

            LOG.info("event=request.completed status={}", 200);
        }

        LOG.info("event=application.idle");
    }
}
~~~

### Compile and Run

In the directory containing pom.xml:

~~~bash
mvn -q compile exec:exec "-Dexec.executable=java" "-Dexec.args=-classpath %classpath com.example.logging.MdcDemo"
~~~

The Maven Exec Plugin spawns a **child JVM** with the project's classpath, keeping the program isolated from Maven's own logging runtime. The example compiles and runs successfully with JDK 17+/Logback using the dependency above.

**Eight output lines in exact order from Logback ConsoleAppender** (excluding Maven or terminal-specific lines):

~~~text
INFO | requestId=missing | operation=none | event=application.ready
INFO | requestId=req-17 | operation=none | event=request.started orderId=OD-42
WARN | requestId=req-17 | operation=payment | event=dependency.retry attempt=2
INFO | requestId=missing | operation=none | event=async.without_context
INFO | requestId=req-17 | operation=none | event=async.with_context
INFO | requestId=missing | operation=none | event=async.after_context
INFO | requestId=req-17 | operation=none | event=request.completed status=200
INFO | requestId=missing | operation=none | event=application.idle
~~~

This output has been **tested and verified**. Timestamp and thread name are omitted from the pattern so the result does not vary by machine or time.

### Detailed Analysis of the Eight Lines

1. **application.ready** is emitted before setting MDC, so both requestId and operation use their fallbacks.
2. **request.started** runs inside the requestId scope, having only requestId=req-17.
3. **dependency.retry** runs inside the requestId scope nested with operation=payment, so both fields appear. **WARN** does not by itself prove the request failed; this may be a recovered retry.
4. **async.without_context** is emitted on the ExecutorService worker; the worker does not automatically see the main thread's MDC.
5. **async.with_context** uses **getCopyOfContextMap()** on the submitting thread and **setContextMap()** on the worker, so requestId is present.
6. **async.after_context** runs next on that same worker after restoring the previous context. requestId is missing again, proving the code does not leak context into the next task in the example.
7. **request.completed** returns to the main thread, where requestId is still active; passing the snapshot to the worker did not clear MDC on main.
8. **application.idle** runs after try-with-resources closes the request scope, so requestId is gone.

**Testing technique:** calling **Future.get()** after each task makes the output order deterministic. Submitting multiple async tasks without waiting can interleave the lines; MDC helps with correlation, **it does not guarantee global ordering**.

### Analyzing restoreContext

~~~java
// This is a helper method in MdcDemo, not a built-in SLF4J API.
private static void restoreContext(Map<String, String> previous) {
    if (previous == null) {
        MDC.clear();
    } else {
        MDC.setContextMap(previous);
    }
}
~~~

The goal is to **restore the exact context the worker already had before running the task**:
- If the worker had no MDC beforehand, we clear it after the task.
- If the worker already had another valid context, we restore the previous map.
- You should not simply call **MDC.clear()** in every case when the code does not own the entire context.
- Because **getCopyOfContextMap()** returns a copy, we avoid sharing the same mutable map between two threads in an uncontrolled way.

**Warning:** when a framework already provides automatic context propagation, you should not nest multiple inconsistent custom wrappers on top of it. Standardize ownership and copy/restore rules at an appropriate layer.

## 7. A Simple Pattern for HTTP Requests

In a traditional server application, the start of a request is usually the right place to set the correlation ID. Illustrative example:

~~~java
// This is Java pseudocode inside a request handler/filter, not a standalone program.
String requestId = validateOrGenerateRequestId(request);
try (MDC.MDCCloseable scope =
             MDC.putCloseable("requestId", requestId)) {
    handleRequest(request);
}  // MDC key is removed here.
~~~

**validateOrGenerateRequestId(request)** is a hypothetical business helper that must be implemented in the actual framework. Do not accept a client-provided header verbatim without validation: an overly long ID, one containing newlines/control characters, or one containing sensitive data can cause log injection risks and storage overhead.

In a real servlet filter, interceptor, or middleware, you typically need to:

1. Accept a validly formatted requestId or generate a new ID.
2. Set allowed MDC keys, such as requestId, traceId, route.
3. Forward to business processing.
4. Log completion and required metrics **before cleaning up the context**, if you want those lines to carry the same ID.
5. **Clean up keys in finally**, even when the handler throws an exception.
6. If the request transitions to async processing, use the corresponding framework lifecycle/propagation mechanism rather than assuming a synchronous filter spans the entire processing duration.

**Do not conflate requestId with userId.** RequestId identifies a single execution; userId/tenantId may be sensitive data depending on policy. Do not put emails, customer names, or access tokens into MDC just to search logs faster.

## 8. MDC in Thread Pools and CompletableFuture

Thread pools make the MDC problem both useful and error-prone. For example:

~~~text
HTTP thread A: MDC.requestId=req-A
Executor worker-1: runs task from A
HTTP thread B: MDC.requestId=req-B
Executor worker-1: later runs task from B
~~~

If task A sets MDC on worker-1 without cleaning it up, task B can **accidentally read req-A**, even though task B belongs to a different request. More dangerous than a missing requestId is a log line carrying the **wrong requestId**.

### Context Propagation Rules

A principled safe wrapper:

~~~java
// Illustrative snippet inside a method with an executor and a Runnable task.
Map<String, String> captured = MDC.getCopyOfContextMap();

executor.submit(() -> {
    Map<String, String> previous = MDC.getCopyOfContextMap();
    try {
        if (captured == null) {
            MDC.clear();
        } else {
            MDC.setContextMap(captured);
        }
        task.run();
    } finally {
        if (previous == null) {
            MDC.clear();
        } else {
            MDC.setContextMap(previous);
        }
    }
});
~~~

**Critical condition:** the snapshot must be captured on the thread **that currently holds the right context**, typically before submitting the task. Capturing inside the worker after the task has already switched threads will not recover the submitting thread's requestId.

This pattern should be encapsulated in an **executor decorator, task wrapper, or framework mechanism** rather than copy-pasted at every submit call. In production code, account for exceptions, cancellation, result synchronization, shutdown, context nesting, and reused tasks.

### CompletableFuture

With **CompletableFuture.supplyAsync(...)** or **thenApplyAsync(...)**, callbacks may run on a different thread or pool. **Do not assume MDC automatically follows the future chain**. If your system has context propagation from Spring, Micrometer, OpenTelemetry, or another async framework, find the right framework integration and verify it with logs containing requestId. Otherwise, apply snapshot and restore at the appropriate execution boundaries.

### Reactive Pipelines and Virtual Threads

With reactive programming, relying solely on ThreadLocal-based MDC can be wrong because a single request moves across multiple threads. Prefer the reactive framework's context and its corresponding logging integration. With virtual threads on JDKs newer than Java 17, evaluate context propagation according to the actual runtime; **do not extrapolate that every concurrency model behaves like a classic thread pool**.

**Core takeaway:** MDC is **local logging context tied to the backend's execution mechanism**, not by itself a standard for propagating data across all async boundaries.

## 9. MDC in JSON Logging

MDC can go into a text pattern:

~~~text
INFO requestId=req-17 operation=payment event=dependency.retry
~~~

Or be emitted as fields by a **JSON encoder**:

~~~json
{
  "@timestamp": "2026-11-09T13:20:30.123Z",
  "level": "WARN",
  "logger_name": "com.example.logging.MdcDemo",
  "message": "event=dependency.retry attempt=2",
  "requestId": "req-17",
  "operation": "payment"
}
~~~

The JSON above is an **illustrative structural example**, not the fixed output of the Maven project in section 6, because that project uses **PatternLayoutEncoder** and outputs text.

In **logstash-logback-encoder**, **LogstashEncoder** can emit MDC entries as JSON fields. According to the library's documentation, the default configuration typically includes all MDC entries, but you should **only emit allowed keys** to prevent data leaks and schema collisions.

A JSON encoder configuration fragment:

~~~xml
<!-- Illustrative fragment: requires adding the logstash-logback-encoder dependency
     and placing this encoder inside an appropriate Logback appender. -->
<encoder class="net.logstash.logback.encoder.LogstashEncoder">
  <includeMdc>true</includeMdc>
  <includeMdcKeyName>requestId</includeMdcKeyName>
  <includeMdcKeyName>operation</includeMdcKeyName>
</encoder>
~~~

When specifying these **includeMdcKeyName** entries, other MDC keys are not emitted by the encoder's MDC provider per the documented mechanism. **Do not place another encoder in the same appender**; this configuration replaces PatternLayoutEncoder rather than supplementing the running text example.

### MDC Values and JSON Types

The MDC API typically uses **String–String** pairs. When an encoder outputs JSON, they usually have the JSON string type:

~~~json
{"requestId":"req-17","attempt":"2"}
~~~

The string **"2"** differs from the number **2** in JSON. Some encoders have type-conversion mechanisms for configured fields, but do not assume every MDC value automatically becomes a number/boolean. If the analytics backend requires a numeric type, align the schema and encoder or put that data into a properly typed event structured field.

### Avoiding Key Collisions

If MDC contains keys like **level**, **logger_name**, or **message** and the JSON encoder also emits standard fields with those same names, it can produce **duplicate JSON keys** or cause ingestion conflicts. Do not use MDC to overwrite system fields. Choose clear namespaces, restrict the list of keys, and validate actual JSON output with a parser.

Using JSON does not mean data is automatically redacted. If you put an access token into MDC, the encoder can repeat that token across very many events before the scope is cleaned up.

## 10. How Does MDC Differ from SLF4J Fluent Key–Value Pairs?

SLF4J 2 allows setting key–value pairs **for a single logging event** via the fluent API. For example:

~~~java
// Illustrative snippet; LOG is of type org.slf4j.Logger.
LOG.atInfo()
        .addKeyValue("orderId", "OD-42")
        .addKeyValue("itemCount", 2)
        .log("event=order.created");
~~~

Key differences:

| MDC | Fluent key–value |
| --- | --- |
| Attaches context to multiple log calls within a scope | Attaches fields to one specific log call |
| Uses put/remove/clear or putCloseable | Uses LoggingEventBuilder before log() |
| Suitable for shared requestId/traceId/operation | Suitable for event-specific orderId, status, durationMs |
| Requires lifecycle management and propagation | Does not persist context across calls |
| Can be emitted via %X or an MDC JSON provider | Requires an encoder/backend that supports key–value pairs |

**There is no absolute one-or-the-other choice.** A single record may need both:
- **MDC.requestId** to tie it to the request.
- **event-level orderId/status/durationMs** to describe the specific action.

The backend must be configured so that the needed fields are actually emitted. If you only use PatternLayoutEncoder with **%msg** and **%X**, fluent key–values will not necessarily become JSON columns on their own; check your formatter/encoder.

## 11. Distinguishing MDC from Distributed Tracing

A distributed system might process:

~~~text
Gateway -> Order Service -> Payment Service -> Database
~~~

To trace across multiple services, you need **trace context propagation** over the network (for example, HTTP headers following a standard) and appropriate instrumentation. A **traceId** can be placed into MDC to appear in each service's logs, but **MDC is only where the ID is surfaced in the logging context**, not the mechanism that creates or propagates spans.

An illustrative log example:

~~~json
{
  "service.name": "payment-api",
  "traceId": "7cfa...",
  "spanId": "c410...",
  "logger": "com.example.payment.PaymentService",
  "message": "event=payment.authorized"
}
~~~

The keys **service.name, traceId, spanId** are only an **example schema**; your backend/OpenTelemetry integration may use different names or structures. Do not generate an arbitrary traceId independently in each service and expect traces to link together.

### Correlation ID vs. Trace ID

- **requestId**: an ID chosen by the application or gateway to identify a request; format and reliability depend on the system.
- **traceId**: an ID managed by the tracing system for a trace, with its own formatting and propagation rules.
- **spanId**: the ID of a span within a trace.
- **tenantId**: tenant identifier, which may be sensitive and must comply with policy.
- **operation**: processing step name, suitable for a short scope or event field.

**An ID alone does not prove a successful outcome.** Combine level, event name, status, exception, timestamp, and business data sources to understand an event.

## 12. Common Mistakes When Using MDC

| Symptom | Common Cause | How to Fix |
| --- | --- | --- |
| Pattern prints requestId=missing | Key not set, case mismatch in key name, or scope already ended | Verify MDC.put uses the exact name and timing relative to the log call |
| ID visible on main, missing in Executor | Context not propagated across thread pool | Snapshot on submitting thread, set/restore on worker |
| Task B shows task A's requestId | Worker thread reused without cleaning up MDC | Remove/restore in finally of each task |
| Log prints message fine but no MDC | Pattern lacks %X or JSON encoder does not include MDC | Check layout/encoder and field names |
| RequestId lost between CompletableFuture stages | Each stage may run on a different thread | Use context propagation at async boundaries |
| After closing putCloseable, old key is not back | putCloseable only removes the key on close | Snapshot and restore if overwriting an outer value |
| Calling MDC.clear wipes framework's traceId | Code clears the entire context it does not own | Only remove keys you added or restore a snapshot |
| Duplicate requestId in JSON | Collision between MDC and event fields, or encoder configured with two sources | Standardize schema and restrict included keys |
| MDC in code but another backend does not emit it | Unsupported adapter/provider or different config | Verify SLF4J provider and MDC adapter |
| Logs mixed up when calling another HTTP service | MDC does not propagate over the network | Use proper headers/tracing propagation |
| requestId too long or contains newlines | Untrusted ID accepted from client | Validate format, enforce length limit, escape |
| Log volume grows too large | Attaching many long fields to every event | Keep key set small, reduce repetitive data |
| ERROR loses traceId | Exception handled after MDC scope has closed | Log exception inside scope or preserve context for logging |
| MDC appears in text but missing in JSON index | Collector/ingest renames or drops fields | Inspect raw JSON and verify mapping |
| Context leaks between test cases | Test does not clean up MDC after running | Remove keys/clear per ownership in teardown |

**Notable pitfall:** logging in a **catch** block or callback after the request scope has exited can lose the ID, even if the business method initially set MDC correctly. When designing the lifecycle, know whether the **last log needing correlation** is emitted before closing the context.

## 13. Performance, Cardinality, and Security

MDC is useful, but not free.

### Performance

- MDC operations carry context-management overhead; per Logback documentation, avoid mutating MDC at very high frequency per log line inside hot loops.
- Taking a snapshot/copy of the map for every task also consumes memory and CPU; measure under very high throughput.
- Every MDC field is emitted repeatedly across many records, increasing bytes written, indexing, and storage cost.
- In some async pipelines, snapshots/log events are prepared at different points in time; test actual output rather than assuming a later map mutation will affect earlier events.
- Avoid putting very large objects, full JSON payloads, or unbounded strings into MDC.

### Cardinality

Fields like **requestId** have very high cardinality because each new request has a new ID. Search systems can index them as keywords for querying, but you should not use requestId as a **metric label** for aggregations with cardinality limits. Those are two different storage and analytics problems.

Fields like **operation** or **environment** have smaller value sets, though you should still avoid generating uncontrolled dynamic values.

### Security and Privacy

Do not log into MDC:
- Passwords, access tokens, API keys, session cookies, or OTPs.
- Payment card numbers, private keys, or credentials.
- Full request/response payloads or headers containing secrets.
- Personal data without a valid processing basis and appropriate safeguards.

If tenantId/userId must be logged for diagnostics, evaluate whether it is permitted, whether pseudonymization/masking is needed, retention limits, and log read permissions. **MDC is emitted repeatedly across many records**, so a misplaced sensitive value can amplify the severity of a leak.

Untrusted input can contain **newlines, control characters, or log-forging characters**. Validate, sanitize, and bound data; use a JSON encoder with proper escaping when appropriate. However, valid JSON does not replace secret data controls.

### Context Ownership

The component setting context must know clearly:
- Which keys are under its management?
- When does the scope end?
- Are any async tasks still running after the scope ends?
- Is it overwriting an existing key?
- Should it remove a single key or restore the entire map?
- Which backend actually consumes the MDC adapter?

If you cannot answer these, the risk of context leakage or attaching the wrong correlation ID is very high.

## 14. Designing a Clean and Clear MDC Convention

A pragmatic schema for a Java service might look like:

| Key | Example Value | When to use |
| --- | --- | --- |
| **requestId** | req-17 | Tie together multiple events of the same request |
| **traceId** | ID issued by tracing system | Correlate telemetry across services |
| **spanId** | Current span ID | Locate the processing segment within a trace |
| **operation** | payment.authorize | Tie to a clearly scoped processing step |
| **tenantId** | approved identifier | Only when policy permits and with controls |
| **jobId** | batch-2026-11-09 | Correlation for background jobs |
| **messageId** | msg-42 | Correlation in message consumers |
| **environment** | staging | Can be set from deployment config instead of MDC |

**You do not need to attach every field to every request.** Choose data that genuinely aids investigation and assess the sensitivity of each field.

A good convention should specify:
1. **Consistent key naming** and casing (requestId differs from requestID).
2. **Source of values**, such as gateway, tracing system, or job scheduler.
3. **Lifetime scope** and the component responsible for cleanup.
4. **Propagation across thread/service switches**.
5. **Fallback values** when context is absent.
6. **Allowlist of fields to emit** in text and JSON.
7. **Length limits, format validation, and data policies**.
8. **Compatibility with parsers, dashboards, and alerts** when changing backends/encoders.

Using a small, clear set of keys usually works better in operations than stuffing all business data into MDC.

## 15. How to Verify MDC Yourself in a Java Application

A testing checklist:

1. **Without MDC:** log before the scope and confirm the fallback renders correctly.
2. **With one key:** set requestId and verify multiple log calls carry the same ID.
3. **With multiple keys:** set operation in a short scope and check that it appears only in that scope.
4. **After scope ends:** log another record; requestId/operation must be gone if cleaned up properly.
5. **Two consecutive requests on the same worker:** ensure no mixing of the previous request's ID.
6. **Async task without propagation:** confirm context is missing as expected, rather than treating it as a formatter bug.
7. **Async task with propagation:** snapshot before submit, set on worker, verify the event receives the right ID.
8. **Task after propagation:** check that context is restored and does not leak to another task.
9. **Throwable:** log the exception inside the scope to preserve context and verify the stack trace belongs to the right request.
10. **JSON encoder:** parse the record, check keys are present/non-duplicate, String type, and agreed schema.
11. **Unicode/quotes/newlines in messages:** confirm the encoder handles them properly without breaking the parser.
12. **Different provider:** if switching from Logback to another provider, verify MDC support and actual formatting.
13. **Load test:** monitor context copy overhead and repeated data byte volume.
14. **Security:** test untrusted IDs in a test environment and verify validation/escaping.
15. **Operational docs:** describe how to trace a requestId/traceId across services and time ranges.

Do not simply grep a single line with requestId and conclude the entire pipeline is correct. **A dangerous bug is a wrong ID that still looks valid**, such as task B mistakenly logging A's requestId due to thread reuse.

### A Programmatic Verification

The example in section 6 demonstrated:
- On the main thread, requestId exists within the scope.
- The Executor worker does not automatically inherit the ID.
- The worker has the ID when given a snapshot.
- The worker is restored after completion.
- The main thread is cleaned up after the request ends.

In a real application, add unit/integration tests at the **filter/interceptor/task decorator** where context is set and propagated, rather than testing only business code.

## 16. Self-Check Questions

**Question 1.** What does MDC stand for?  
**Answer:** Mapped Diagnostic Context, a key–value diagnostic context map.

**Question 2.** Why use MDC instead of concatenating requestId into every message?  
**Answer:** It lets the backend emit context consistently across many logging events in the same scope, reducing code duplication and aiding correlation.

**Question 3.** Does MDC automatically create distributed traces across microservices?  
**Answer:** No. Separate tracing context and network propagation are required; MDC can only display those IDs in logs.

**Question 4.** Why does requestId appear on the main thread but go missing in an Executor?  
**Answer:** Logback MDC does not guarantee inheritance across executors; you must pass a snapshot or use framework context propagation.

**Question 5.** Why must MDC be cleaned up in finally or try-with-resources?  
**Answer:** To prevent context from leaking to subsequent requests/tasks on the same thread and to guarantee cleanup even when an exception occurs.

**Question 6.** Does putCloseable automatically restore the previous value of the same key?  
**Answer:** Not according to the SLF4J contract: close removes the key. To restore an outer context, you must intentionally snapshot and restore.

**Question 7.** Is MDC.clear always better than removing a single key?  
**Answer:** No. clear removes all keys, which can wipe context managed by the framework or an outer scope.

**Question 8.** If MDC.put was called but the pattern lacks %X, will requestId automatically appear on the console?  
**Answer:** Not necessarily. The layout/encoder must be configured to emit MDC.

**Question 9.** If MDC contains attempt="2", will a JSON encoder definitely output the number 2?  
**Answer:** No. MDC typically holds Strings; the JSON type is determined by the encoder/schema.

**Question 10.** Should you put an access token into MDC for debugging?  
**Answer:** No. The token can be repeated on every log line in the scope and collected/stored.

**Question 11.** Why must context propagation also restore the worker's previous map?  
**Answer:** So the new task does not leak its requestId to the next task and does not break valid context already present on the worker.

**Question 12.** If two records have the same thread name, are they guaranteed to belong to the same request?  
**Answer:** No. Thread pools reuse threads; proper correlation ID/trace context is needed.

## Key Takeaways

**MDC is a key–value context that lets multiple logging events of the same request/job share diagnostic information, typically requestId or traceId.** In SLF4J + Logback, code sets context via the MDC API and the backend outputs it via **%X** or a JSON encoder. **MDC requires a clear lifecycle**: set before logging, clean up in finally/try-with-resources, and copy/restore across async boundaries. Do not treat it as a global variable, a tracing system, a durable store, or a place for sensitive data. Proper MDC usage should **tie the right events to the right context** without leaking data to other requests.
