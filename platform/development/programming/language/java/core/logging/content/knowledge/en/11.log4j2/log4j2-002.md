# Logger in Log4j2 — Usage and Internal Mechanics

## 1. What is a Logger and what do you need to learn?

In **Apache Log4j 2**, a **Logger** is the object Java code uses to emit logging events. Application code calls methods such as **trace()**, **debug()**, **info()**, **warn()**, **error()**, or **fatal()** on the Logger; the logging system relies on configuration to decide which events are processed, which Appender they are routed to, and in what format they are output.

A typical example:

~~~java
import org.apache.logging.log4j.LogManager;
import org.apache.logging.log4j.Logger;

public class OrderService {
    private static final Logger LOG = LogManager.getLogger(OrderService.class);

    public void create(String orderId) {
        LOG.info("event=order.created orderId={}", orderId);
    }
}
~~~

This snippet is a component class; it **does not have a main()** method, so it is not a standalone application. It uses the **Log4j API** and requires the appropriate dependencies. The key point is that business code only states **what event occurred**; the Log4j2 configuration decides **which events are accepted and where they are written**.

After this lesson, you will be able to:

- Create and reuse a Logger using **org.apache.logging.log4j.LogManager.getLogger(...)**.
- Distinguish between **Logger (API)**, **LoggerConfig (configuration)**, **LoggerContext**, **LogEvent**, and **Appender**.
- Understand the Logger naming system, log levels, and package-based configuration inheritance.
- Use **parameterized logging** with **{}** placeholders, check **isDebugEnabled()**, and understand the limitations of this check.
- Attach **Marker**, **ThreadContext**, and exceptions properly, distinguishing event data from message text.
- Read a **log4j2.xml** configuration containing Root, Logger, AppenderRef, PatternLayout, and **additivity**.
- Run a Java 17 + Maven + Log4j2 project and verify the tested output.
- Identify common mistakes regarding Logger names, duplicate logs, context across threads, async logging, performance, and security.

**Scope:** This lesson belongs to the **Log4j2** section in **Java Core Logging** and focuses on Logger. Appender, Filter, Layout, async, and reconfiguration are explained just enough to understand how Logger works, without turning into a full Log4j Core customization guide.

## 2. Architecture: Logger does not write to files or the console itself

A useful mental model:

~~~text
Application Java
    |
    | LogManager.getLogger(LoggerDemo.class)
    v
Log4j API Logger
    | (name, level methods, message, Marker, Throwable...)
    v
LoggerContext + active Configuration
    |
    +--> LoggerConfig matching the logger name
    |       |
    |       +--> level + Filters
    |       +--> AppenderRef(s)
    |       +--> additivity to parent LoggerConfig
    |
    v
LogEvent
    |
    v
Appender (Console, File, RollingFile, ...)
    |
    v
Layout/Encoder (PatternLayout, JSON Template Layout, ...)
    |
    v
stdout / file / observation target
~~~

The diagram emphasizes **roles**, not every detail of the call order across all configurations. Filters can be applied in multiple places, and async logging can offload part of the work to another thread. However, two foundational distinctions must always be clear:

1. **Logger** is the object on the code side and belongs to the Log4j API. It has a name and emits logging requests.
2. **LoggerConfig** belongs to the **Log4j Core** configuration system. It binds level, Filter, AppenderRef, and additivity to the corresponding Loggers.

You do not need to create a LoggerConfig for every class to have a Logger. If code requests a Logger named **com.example.order.OrderService** while the configuration only declares **com.example.order**, Log4j Core can bind the class's Logger to the LoggerConfig at that package level.

| Component | Responsibility | Identifying sign |
| --- | --- | --- |
| **Logger** | Call point from the application, Logger name, and log-emitting methods | LOG.info(...), LOG.warn(...) |
| **Log4j2 LogManager** | Factory/access point for the appropriate Logger and LoggerContext | org.apache.logging.log4j.LogManager |
| **LoggerContext** | Context of a logging system, holding the active configuration | An application can have multiple contexts depending on the environment |
| **Configuration** | Defines LoggerConfigs, Appenders, Filters, Layouts | log4j2.xml, other configuration formats |
| **LoggerConfig** | Determines level, appender routing, and additivity by name | Configured logger name/package |
| **LogEvent** | Data of a single event: level, message, context, marker, Throwable | Passed through the pipeline to Appender |
| **Appender** | Receives the event and forwards it to the output destination | Console, RollingFile, Async... |
| **Layout** | Formats an event into structured text/bytes | PatternLayout, JSON Template Layout |
| **Filter** | Can accept, deny, or pass on to other rules for evaluation | By level, marker, or event attributes |

**Do not confuse with JUL:** Log4j2's **org.apache.logging.log4j.LogManager** is different from **java.util.logging.LogManager** in the JDK. Both share the short name LogManager, but they serve two different APIs and configuration systems.

## 3. Obtaining a Logger properly

### 3.1. Common pattern: one Logger per class

~~~java
import org.apache.logging.log4j.LogManager;
import org.apache.logging.log4j.Logger;

public class PaymentService {
    private static final Logger LOG = LogManager.getLogger(PaymentService.class);

    public void accept(String paymentId) {
        LOG.info("event=payment.accepted paymentId={}", paymentId);
    }
}
~~~

This is a component class that can compile when dependencies are present; it has no main method. A **private static final** field is the standard way to reuse a Logger instead of requesting a Logger on every method call.

**Why use the class name?** Log4j2 can use the fully qualified class name, such as **com.example.payment.PaymentService**, as the logger name. Operators can enable DEBUG specifically for the **com.example.payment** package without enabling it system-wide.

You can also write:

~~~java
private static final Logger LOG = LogManager.getLogger();
~~~

In common usage, the **no-argument getLogger()** infers the calling class automatically; using **getLogger(PaymentService.class)** lets readers see the class name directly. Both are valid patterns under the Log4j2 API, though with shared wrappers/utilities you must pay attention to which calling class the Logger name gets bound to.

### 3.2. Custom Logger names

You can use a string name:

~~~java
Logger audit = LogManager.getLogger("com.example.audit");
~~~

This is useful when an application wants a functional logging group. However, custom names must follow a stable convention. Do not create new Loggers with names containing **userId**, **requestId**, timestamps, or a random value per request: dynamic names are hard to configure, cause namespace bloat, and do not replace correlation fields.

**General rule of thumb:** use class/package names for technical logs; event names like **order.created** or **payment.failed** belong in the message or structured attributes, rather than turning into thousands of separate logger names.

### 3.3. Loggers are reusable and thread-safe

The Log4j API Logger is designed to be reused across multiple threads. You do not need to synchronize every **LOG.info** call in a service. However, Logger thread-safety **does not mean every piece of data you pass in is immutable**; formatted or referenced objects can be mutated later, especially with async pipelines. Ensure logged data has an appropriate lifecycle and snapshotting strategy.

**Do not** store a Logger in a per-request mutable field or pass a Logger around as a kind of transaction context. A Logger is an event-emitting tool; request context should be passed separately.

## 4. Logger name hierarchy and LoggerConfig selection

Log4j2 uses dot-separated naming rules to find the matching LoggerConfig. For example:

~~~text
Logger in code:
  com.example.order.OrderService
  com.example.order.CheckoutService
  com.example.payment.PaymentService

LoggerConfig:
  Root                         level=ERROR
  com.example                  level=INFO
  com.example.payment          level=DEBUG
~~~

If there is no specific LoggerConfig for **com.example.order**, Loggers in that package use the closest matching LoggerConfig, such as **com.example**. Loggers in payment will use the specific **com.example.payment** configuration.

**Pay attention to hierarchical names:** configuration names are prefixes along dot boundaries. **com.example.pay** is not an ancestor of **com.example.payment.Service** just because both strings share a few leading characters. Always specify the exact package/class name.

### 4.1. Logger hierarchy vs. LoggerConfig hierarchy

This is an architectural distinction worth learning:

- **Loggers in code** do not need to hold parent/child pointers themselves like Logger structures in some older logging implementations.
- **LoggerConfig** is the component that forms the name-based configuration hierarchy and determines log level inheritance and Appender routing.
- **Root LoggerConfig** is the fallback configuration used when no more specific configuration exists.

At runtime, a Logger is linked to the active LoggerConfig. After Log4j2 reloads its configuration, the Logger can be linked to a different LoggerConfig while the code keeps the same Logger field. Therefore, changing configuration does not require modifying any **LOG.info()** calls.

### 4.2. What is the role of the Root Logger?

The Root LoggerConfig provides defaults for Loggers that have no more specific configuration. In Log4j2 XML, it is written as:

~~~xml
<Root level="ERROR">
  <AppenderRef ref="STDOUT"/>
</Root>
~~~

This declaration is **only a configuration snippet**; a full Appenders and Configuration section is required to run. Root differs from a package LoggerConfig:

~~~xml
<Logger name="com.example.order" level="DEBUG" additivity="false">
  <AppenderRef ref="FILE"/>
</Logger>
~~~

Root has no package-style name. If an application's logger is not defined separately, its level and Appenders are determined by Root or an ancestor LoggerConfig.

## 5. Log levels: which events does a Logger accept?

The standard levels commonly used in Log4j2, from lowest to highest priority:

~~~text
ALL < TRACE < DEBUG < INFO < WARN < ERROR < FATAL < OFF
~~~

**ALL** and **OFF** are typically used as special thresholds: ALL lets every standard level pass at the check point; OFF blocks standard events. TRACE is very detailed; DEBUG aids investigation; INFO reflects operational milestones; WARN highlights abnormal but handleable conditions; ERROR/FATAL indicate serious failures depending on application policy.

Example:

~~~java
LOG.trace("attempted parse details");
LOG.debug("selected strategy={}", strategy);
LOG.info("event=order.created orderId={}", orderId);
LOG.warn("event=inventory.retry retry={}", retry);
LOG.error("event=payment.failed orderId={}", orderId);
~~~

This is an illustrative snippet inside a method with the corresponding variables, not a standalone program. When the matching LoggerConfig threshold is **INFO**, events at TRACE/DEBUG are typically filtered out by the level check; INFO/WARN/ERROR proceed for further evaluation.

| LoggerConfig level | TRACE | DEBUG | INFO | WARN | ERROR |
| --- | --- | --- | --- | --- | --- |
| ERROR | Denied | Denied | Denied | Denied | Passed |
| WARN | Denied | Denied | Denied | Passed | Passed |
| INFO | Denied | Denied | Passed | Passed | Passed |
| DEBUG | Denied | Passed | Passed | Passed | Passed |
| TRACE | Passed | Passed | Passed | Passed | Passed |
| OFF | Denied | Denied | Denied | Denied | Denied |

This table assumes **standard levels, no intervening Filters, and the matching LoggerConfig selected**. Once an event passes the level check, it can still be rejected by a Filter or AppenderRef, or fail at the sink; **“passed” does not automatically mean successfully persisted**.

### 5.1. When is isDebugEnabled() useful?

~~~java
if (LOG.isDebugEnabled()) {
    LOG.debug("expensive diagnostic={}", computeDiagnostic());
}
~~~

This is an illustrative integration snippet, where **computeDiagnostic()** is an application-defined function. Java evaluates arguments before invoking a method; if the function that builds diagnostic data is CPU- or I/O-intensive, checking the level first avoids computing it when debug is disabled.

However:

- For cheap values, **parameterized logging** is usually clear and convenient enough; there is no need to wrap every statement in an `if`.
- **isDebugEnabled()** primarily answers whether the Logger currently allows DEBUG; it does not guarantee that a downstream Appender will write the record.
- If the configuration changes between the check and emitting the log, the outcome may differ; never use `isDebugEnabled` to drive business logic.
- The Fluent API provides a way to log with a `Supplier` to defer message construction per the API contract; use it as needed and verify in tests.

**Never use log levels to replace a business `if`:** “allow payment” is a business decision; it must never depend on whether the Logger has INFO enabled.

## 6. Parameterized logging and Message in Log4j2

### 6.1. The default placeholder is {}

Good pattern:

~~~java
LOG.info("event=order.created orderId={} amount={}", orderId, amount);
~~~

By default, the Log4j API uses the **{}** placeholder style for parameterized messages. The values `orderId` and `amount` are passed as arguments; the backend/MessageFactory formats the resulting message.

Compare with string concatenation:

~~~java
LOG.debug("state=" + expensiveState.toString());
~~~

In the concatenation example, **expensiveState.toString()** can be evaluated even when DEBUG is disabled. With parameterized logging, parameter formatting is handled according to the API and implementation contract, yet **Java still evaluates argument expressions before the method call**. Therefore, **LOG.debug("value={}", expensiveOperation())** still invokes `expensiveOperation()` before the backend knows whether the event will be filtered out. Use a level check or an appropriate lazy mechanism when the cost is genuinely significant.

### 6.2. MessageFactory can affect formatting

Log4j2 supports different **MessageFactory** implementations. The **{}** pattern is the common default convention, but a Logger created with a specialized MessageFactory may interpret messages differently, such as printf-style formatting. Do not arbitrarily replace **{}** with **%s** or **{0}** without checking the active API/MessageFactory.

Beyond plain Strings, Log4j2 also has the **Message** type for structured data. This is useful when events need to be parsed in the backend; however, the structured choice must match the active encoder/layout, not just change the argument type.

### 6.3. Message vs. event code

A message like:

~~~text
Order ORD-42 was created
~~~

can change wording, language, or formatting. In systems that require reliable querying, you should include an **event key** such as **order.created**, along with structured fields like **order_id**, **service**, and **request_id**. Do not build dashboards with regexes that depend on the entire prose sentence.

An example sufficient for a learning environment:

~~~java
LOG.info("event=order.created orderId={}", orderId);
~~~

In production, if logs are emitted as JSON or under a shared schema, expose the event name and `orderId` as true structured attributes via an appropriate Message/Context/encoder mechanism rather than re-parsing message text.

## 7. Logger, Marker, ThreadContext, and Throwable

Logger offers several ways to attach information for troubleshooting. Each mechanism addresses a different need.

### 7.1. Marker: event classification label

A **Marker** is a named label that can be attached to a logging request. Example:

~~~java
import org.apache.logging.log4j.Marker;
import org.apache.logging.log4j.MarkerManager;

private static final Marker AUDIT = MarkerManager.getMarker("AUDIT");

// Inside a method:
LOG.info(AUDIT, "event=order.accepted orderId={}", orderId);
~~~

This is an integration snippet inside a class that has a Logger, not a standalone program. A Marker can be included in a layout or used in filters/routing if the configuration supports it.

**A Marker does not by itself create a trustworthy audit log.** If an event has compliance/retention obligations, you must separately design the sink, access controls, retention, and delivery guarantees; simply tagging it with `AUDIT` does not make the data secure.

### 7.2. ThreadContext: current request/trace information

**ThreadContext** provides a context map/stack to attach key–value pairs to events, such as **requestId**, **traceId**, and **spanId**. A clean way to manage scope:

~~~java
import org.apache.logging.log4j.CloseableThreadContext;

try (CloseableThreadContext.Instance ignored =
             CloseableThreadContext.put("requestId", requestId)) {
    LOG.info("event=order.accepted orderId={}", orderId);
}
~~~

The snippet above requires `requestId`/`orderId` variables in the method; it is not a standalone program. Exiting the `try` block closes the scope and restores/clears the managed context, preventing `requestId` from leaking into the next task on a reused thread.

**Important limitations:**

- The context map is typically thread-bound. Offloading work to **ExecutorService**, **CompletableFuture**, virtual threads, or async pipelines may not automatically carry the right context.
- If context must be propagated, use a propagation mechanism with an explicit contract, capture snapshots when needed, and clean up context in a scope/`finally` block.
- Putting **traceId/spanId** into events does not automatically create distributed tracing; proper instrumentation and propagation are required.
- Never put passwords, access tokens, session cookies, or sensitive data into ThreadContext.

In PatternLayout, a field can be read with **%X{requestId}**. If the key is absent in the current scope, it typically renders as an empty string in that layout pattern.

### 7.3. Throwable: error details and stack trace

When an exception occurs, attach the **Throwable** so the logging backend can process the stack trace:

~~~java
try {
    chargeCard();
} catch (PaymentGatewayException ex) {
    LOG.atError()
       .withThrowable(ex)
       .log("event=payment.charge_failed orderId={}", orderId);
}
~~~

This illustrative snippet requires defining **chargeCard**, **PaymentGatewayException**, and the `orderId` variable; it is **not** a standalone program. The **Fluent API** makes attaching an exception explicit, avoiding ambiguity in overloads that take `Throwable` as the final parameter.

To use fluent logging, call **LOG.atInfo()**, **LOG.atWarn()**, or **LOG.atError()** and finish with **log(...)**. If you forget the terminating `log(...)` call, the event will not be emitted.

**Do not log the same exception at every layer** unless it adds handling context; doing so creates duplicate logs. Log errors at the boundary where a handling decision is made, preserving the cause chain appropriately. Exception messages can contain secrets or user data, so a redaction policy is necessary.

## 8. Appender, LoggerConfig, and additivity

### 8.1. Which Appenders receive an event?

A LoggerConfig holds references to Appenders. A single LoggerConfig can send events to Console, File, RollingFile, or other Appenders. Each destination has its own format, filters, and handling policy.

~~~text
Logger: com.example.order.OrderService
  -> LoggerConfig com.example.order (level INFO)
      -> AppenderRef FILE
      -> ancestor LoggerConfig/Root AppenderRef CONSOLE (if additivity allows)
~~~

An **AppenderRef** can have its own level threshold or filter; an Appender can also have filters. Setting a Logger to DEBUG does not force every sink to receive DEBUG.

### 8.2. additivity=true can send logs to multiple destinations

By default, non-Root LoggerConfigs have **additivity=true**: an accepted event can be forwarded to the Appenders of the matching LoggerConfig **and its ancestor LoggerConfigs**, until a LoggerConfig with `additivity=false` is reached or it reaches Root.

Example:

~~~xml
<Logger name="com.example.order" level="INFO">
  <AppenderRef ref="FILE"/>
</Logger>
<Root level="ERROR">
  <AppenderRef ref="CONSOLE"/>
</Root>
~~~

This is an illustrative XML snippet requiring the declared Appenders. When the `order` LoggerConfig at INFO accepts an INFO event, the event can reach both FILE and CONSOLE because default additivity allows it, even though Root is configured at ERROR. **Do not assume the Root level will re-filter an event already accepted by a child LoggerConfig along the additivity path.** Filters and AppenderRefs can still affect it.

If FILE and CONSOLE both feed into the same centralized destination, you may see duplicate logs.

### 8.3. additivity=false stops forwarding events to ancestor Appenders

~~~xml
<Logger name="com.example.order" level="INFO" additivity="false">
  <AppenderRef ref="FILE"/>
</Logger>
~~~

That LoggerConfig uses its own AppenderRefs and stops accumulating ancestor Appenders. This is the right approach when you genuinely want an independent pipeline. **Do not set `additivity=false` out of habit** if the LoggerConfig has no output destination of its own, or events may have nowhere to go.

**Key distinction:** The Logger name in Java is the source name. The **name** attribute of LoggerConfig defines the configuration scope. The **ref** in AppenderRef must match the exact name of a declared Appender.

## 9. Complete runnable Java 17 + Maven + Log4j2 example

This example uses **Log4j2 2.25.3**, including **log4j-api** and **log4j-core** at the same version, with the Maven Compiler Plugin targeting **Java 17**. This is the exact version used to **compile and verify stdout**; in real projects, use a maintained Log4j 2 release and manage dependencies consistently with a BOM where appropriate.

Running the example will demonstrate:

1. A Logger named **demo.logging.LoggerDemo** uses the **demo.logging** LoggerConfig at level INFO.
2. The DEBUG call is dropped; INFO and WARN proceed.
3. The **AUDIT** Marker is printed when present.
4. **requestId** appears only inside the **CloseableThreadContext** block.
5. **additivity=false** prevents events from being duplicated by the Root Appender.

### 9.3. The src/main/resources/log4j2.xml file

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<Configuration>
  <Appenders>
    <Console name="STDOUT" target="SYSTEM_OUT">
      <PatternLayout pattern="%level|%logger{1}|%marker|req=%X{requestId}|%message%n"/>
    </Console>
  </Appenders>
  <Loggers>
    <Logger name="demo.logging" level="INFO" additivity="false">
      <AppenderRef ref="STDOUT"/>
    </Logger>
    <Root level="ERROR">
      <AppenderRef ref="STDOUT"/>
    </Root>
  </Loggers>
</Configuration>
~~~

Explanation:

- **Console name="STDOUT" target="SYSTEM_OUT"** defines the output target on stdout.
- **PatternLayout** controls the format: severity, shortened Logger name, Marker, requestId, message, and newline.
- **Logger name="demo.logging"** applies to Loggers in that namespace, including **demo.logging.LoggerDemo**.
- **level="INFO"** drops DEBUG/TRACE logging requests under standard level rules.
- **additivity="false"** prevents events accepted by this configured logger from being forwarded to the Root Appender, avoiding duplicate output.
- **Root level="ERROR"** is the fallback configuration for Loggers without a more specific configuration; Root does not cause INFO events from the `demo.logging` LoggerConfig to be blocked by a second level check.

If you want to see all TRACE/DEBUG lines in the example, change the level on the **demo.logging** LoggerConfig, and also check any filters/targets if you added them to the configuration.

### 9.4. The src/main/java/demo/logging/LoggerDemo.java file

~~~java
package demo.logging;

import org.apache.logging.log4j.CloseableThreadContext;
import org.apache.logging.log4j.LogManager;
import org.apache.logging.log4j.Logger;
import org.apache.logging.log4j.MarkerManager;

public final class LoggerDemo {
    private static final Logger LOG = LogManager.getLogger(LoggerDemo.class);

    public static void main(String[] args) {
        LOG.debug("order.trace id={}", "ORD-42");
        LOG.info("order.created id={}", "ORD-42");
        try (CloseableThreadContext.Instance ignored =
                     CloseableThreadContext.put("requestId", "req-42")) {
            LOG.info(MarkerManager.getMarker("AUDIT"), "order.accepted id={}", "ORD-42");
            LOG.warn("payment.retry count={}", 1);
        }
        System.out.println("debugEnabled=" + LOG.isDebugEnabled());
        System.out.println("infoEnabled=" + LOG.isInfoEnabled());
    }
}
~~~

Key takeaways:

- **Logger** is held in a `static final` field.
- The **{}** placeholders accept arguments such as `orderId` and retry count.
- The `AUDIT` Marker is attached only to that specific event.
- `ThreadContext` is populated within a clearly scoped block and cleaned up upon exit.
- **isDebugEnabled** and **isInfoEnabled** reflect the corresponding level state at the Logger, not a guarantee that the sink persisted the output.

### 9.5. Running and verifying stdout

In the directory containing **pom.xml**, run:

~~~bash
mvn -q -B compile exec:java "-Dexec.mainClass=demo.logging.LoggerDemo"
~~~

This command uses Maven to download dependencies, compile for Java 17, and execute the class. It requires a JDK supporting target 17 and Maven access to the dependencies (or cached artifacts).

**Exact stdout verified when compiling/running** with Log4j2 2.25.3:

~~~text
INFO|LoggerDemo||req=|order.created id=ORD-42
INFO|LoggerDemo|AUDIT|req=req-42|order.accepted id=ORD-42
WARN|LoggerDemo||req=req-42|payment.retry count=1
debugEnabled=false
infoEnabled=true
~~~

If Maven is run without the **-q** option, it may print additional Maven logs before/after the program output; the lines above are the **demo stdout** for the command shown.

### 9.6. Why is there no debug line?

The Logger belongs to the **demo.logging** scope, configured at **level=INFO**. The **LOG.debug(...)** call does not meet the threshold. As a result:

- There is no **order.trace id=ORD-42** line in the output;
- **LOG.isDebugEnabled()** prints **false**;
- **LOG.isInfoEnabled()** prints **true**;
- INFO and WARN pass through the LoggerConfig and Appender.

### 9.7. Why is requestId missing at the start/end but present in the middle?

**CloseableThreadContext.put("requestId", "req-42")** is only active within the scope of the two middle log statements. PatternLayout reads **%X{requestId}**, so:

- The first INFO has no `requestId`;
- The INFO with Marker AUDIT and the WARN inside the scope carry **req-42**;
- When the scope exits, the context is cleared, preventing the value from sticking to subsequent tasks.

In multi-threaded server systems, you still need to test propagation across executors/async boundaries; a proper single-thread scope **does not automatically solve** every thread-handoff case.

### 9.8. Why does each event produce only one line?

The **demo.logging** LoggerConfig already attaches `STDOUT`. Setting **additivity=false** prevents events from continuing up to the Root Appender. If changed to `true`, events accepted by this LoggerConfig could be forwarded to Root's `STDOUT` and printed twice because both configurations reference the same console target. That is a consequence of Appender routing, not a bug where code called `LOG.info` twice.

## 10. Using Logger in real-world applications

### 10.1. Choosing levels by event

There is no single rule for every team, but the following table is a useful starting point:

| Level | Appropriate examples |
| --- | --- |
| TRACE | Very detailed execution trace of a parser or processing step |
| DEBUG | Information to help identify root causes during investigation |
| INFO | Meaningful operational events, lifecycle state transitions |
| WARN | Retries, fallbacks, handleable anomalies |
| ERROR | Failed operations or noteworthy errors at processing boundaries |
| FATAL | Critical failures affecting a component's ability to operate |

Do not log INFO on every method call under high request volume. Do not use ERROR for expected business cases (such as invalid user input that returns a valid error response), as it creates noisy dashboards and alerts.

### 10.2. Stable event names, varying data in parameters

Example:

~~~java
LOG.info("event=order.submitted orderId={} channel={}", orderId, channel);
LOG.warn("event=inventory.lookup_retry attempt={} timeoutMs={}", attempt, timeoutMs);
~~~

These snippets belong inside a method where the corresponding variables exist. The goal is to give both humans and tools a consistent **event** identifier. For systems requiring true structured logging, use Message/ThreadContext/JSON Layout appropriately rather than assuming a parser can always extract every field from plain text.

### 10.3. Do not turn Logger into a business logic gate

Wrong:

~~~java
if (LOG.isInfoEnabled()) {
    sendReceiptEmail();
}
~~~

This makes sending emails depend on logging configuration. Business conditions must be evaluated independently, while logging records the outcome:

~~~java
sendReceiptEmail();
LOG.info("event=receipt.sent orderId={}", orderId);
~~~

Both snippets illustrate usage inside a method where the required variables/functions are defined; they do not run standalone.

### 10.4. Log Throwables at the right place

Log errors where they can be interpreted or a handling decision can be made, along with an error code and necessary context:

~~~java
LOG.atError()
   .withThrowable(error)
   .log("event=inventory.lookup_failed dependency={} orderId={}",
        dependencyName, orderId);
~~~

This snippet requires `error`, `dependencyName`, and `orderId` variables in the method. Do not log the same error in the controller, service, and repository without a distinct reason; it multiplies log volume and makes it harder for on-call engineers to pinpoint the actual failed operation.

### 10.5. Logs and UI messages serve different purposes

A Logger serves operations; messages shown to users may be localized. Never expose raw stack traces to the UI. Event codes and technical attributes should remain stable, while user-facing phrasing can vary by language and wording.

## 11. Package-level Logger configuration and runtime changes

With Log4j2, you typically adjust levels in **log4j2.xml** or another supported Log4j Core configuration format. You can place the configuration file on the classpath under a name recognized by the framework or use an appropriate startup property, such as **log4j2.configurationFile**, when you need to specify the configuration source explicitly.

For example, to enable DEBUG only for payment:

~~~xml
<Loggers>
  <Logger name="com.example.payment" level="DEBUG"/>
  <Root level="INFO">
    <AppenderRef ref="STDOUT"/>
  </Root>
</Loggers>
~~~

This is a configuration snippet requiring an `STDOUT` Appender declared elsewhere. Because the `payment` LoggerConfig has no AppenderRef of its own and default additivity is `true`, matching events can be forwarded to the ancestor/Root Appender. If a filter or an AppenderRef with its own level limit is present, DEBUG events may still be dropped there.

**Reconfiguration note:** A Logger in code can continue to be held in a `static final` field while its association to a LoggerConfig updates when a new configuration is activated. However, avoid mutating runtime configuration through unmanaged internal calls; doing so can cause missing/duplicate Appenders, lost output, or issues while a sink is actively writing.

### 11.1. When you only want to adjust one Logger

Do not modify every package by turning Root to TRACE in production. Prefer a specific logger name:

~~~xml
<Logger name="com.example.payment" level="DEBUG"/>
~~~

If Log4j2 is configured via a file, verify that the file is detected and the new setting takes effect on the intended Logger. Framework-based applications may use their own logging configuration layer or orchestrate Log4j2; identify the actual runtime provider.

### 11.2. Notes on async Loggers

Log4j2 supports **async logging**, where I/O work can be offloaded to another thread. There are **AsyncAppender** and **AsyncLogger**; they are not the same mechanism and have different dependency/configuration requirements.

Async can reduce blocking time on the calling thread in some workloads, but it carries risks of **full queues, blocking/dropping, lost records on abrupt shutdown, or reordered output**. Never assume async is always better: measure latency, throughput, memory, and backpressure under realistic workloads.

Never make any critical business operation depend on an async log having been durably persisted, unless the system has an explicit audit contract.

## 12. Distinguishing Log4j2 Logger from other logging APIs

In Java, multiple APIs can coexist in a single application:

| API | Logger class | Obtain Logger via |
| --- | --- | --- |
| **Log4j2 API** | org.apache.logging.log4j.Logger | org.apache.logging.log4j.LogManager.getLogger(...) |
| **JUL** | java.util.logging.Logger | java.util.logging.Logger.getLogger(...) |
| **SLF4J** | org.slf4j.Logger | org.slf4j.LoggerFactory.getLogger(...) |

You cannot arbitrarily swap package imports and keep all syntax identical. JUL configuration uses **java.util.logging.LogManager**, which differs from Log4j2; SLF4J is typically a facade requiring a compatible provider/backend.

If an application uses the SLF4J API but wants Log4j Core as its backend, it needs a supported adapter/provider and dependencies wired in the right direction. If a library uses JUL, a bridge into the shared backend can be used. **Never install bridges in both directions simultaneously**, as that can create logging loops or duplicate output.

**Log4j 1.x** with the **org.apache.log4j.Logger** import is a legacy generation, distinct from Log4j2's **org.apache.logging.log4j.Logger** API. Do not mix Log4j 1 and Log4j 2 examples or configurations.

## 13. Common mistakes when using Logger

### 13.1. Wrong Logger name in configuration

**Symptom:** Configured **com.example.orders** at DEBUG, yet the Logger in code named **com.example.order.OrderService** still does not print debug logs.

**Explanation:** The two names are different. Check the package/class and the actual Logger name. Dots define hierarchy boundaries; do not rely on “looks similar” to assume a configuration matches.

### 13.2. Having Log4j API without a matching backend

**Symptom:** Log4j2 does not read `log4j2.xml` or output differs from expectations.

**Explanation:** The runtime/implementation dependency may be missing or replaced by another option from a framework. Check `log4j-api`, `log4j-core`, providers, and adapters; do not stack multiple backends without understanding the dependency graph.

### 13.3. DEBUG is enabled but no log lines appear

Check the matching LoggerConfig, its level, Filters across layers, AppenderRefs, and the output destination. **LOG.isDebugEnabled()** is useful information, but it does not confirm that output was written to a file or collector.

### 13.4. Log lines appear twice

**Common cause:** The same event is routed to both the child LoggerConfig's Appender and an ancestor's Appender due to **additivity=true**. Inspect the configuration and decide clearly where logs should go; to isolate them, set `additivity=false` alongside an appropriate AppenderRef.

### 13.5. additivity=false makes logs disappear

If a dedicated LoggerConfig has no Appender attached and additivity is disabled, events are not forwarded to the parent's Appender. Fix the routing path before concluding that the Logger is broken.

### 13.6. String concatenation or expensive calls at DEBUG

Even when a log is not emitted, Java may already have built the String or executed the function to compute an argument. Use **{}**, avoid manual `toString()` calls, and consider `isDebugEnabled` or the API's `Supplier` overloads when data is expensive to produce.

### 13.7. Letting ThreadContext leak to another request

Thread pools reuse threads; if `ThreadContext.put` is called without cleanup, the next request can inherit stale IDs. Use scoped/try-with-resources management, and verify propagation and cleanup on error paths as well.

### 13.8. Treating Marker as proof of audit persistence

A Marker is just a label; the sink can still lose data, drop it via filters/sampling, or hit I/O errors. Tested audit policies and access controls are required if data retention is mandatory.

### 13.9. Logging exceptions multiple times or losing the Throwable

Logging just a message like **"Something went wrong"** is insufficient. Conversely, logging full stack traces at every layer creates noisy logs. Choose handling boundaries, attach the Throwable where appropriate, and include an error code and enough context for investigation.

### 13.10. Using outdated Log4j2 versions

A logging framework is a runtime dependency in production and must be kept up to date with maintenance releases and security advisories. Do not copy old, unmaintained Log4j 2 versions from online tutorials. In a project, manage versions consistently across API/Core and extension modules (for example via **log4j-bom**) and inspect the dependency tree.

## 14. Performance, data safety, and logging quality

### 14.1. Choose enough data to act on

A good event includes an **event name**, appropriate level, service/version, `requestId`/`traceId` if available, dependency, outcome, and error code when needed. Avoid overly terse messages like “Error” or “Failed” without context.

Example:

~~~text
event=inventory.lookup_failed dependency=inventory-db requestId=req-42 errorType=TimeoutException
~~~

Specific contents must comply with data policies. A technical event may contain non-sensitive operational IDs, but should not dump entire transaction records or payloads without justification.

### 14.2. Never log secrets at any level

Never log passwords, tokens, API keys, session cookies, private keys, full payment card numbers, or sensitive payloads. Logging at DEBUG **does not guarantee safety**, because DEBUG can be enabled during troubleshooting. Fields in ThreadContext, Marker-associated data, or exception messages must also be controlled.

Log injection can occur when user data contains newlines or control characters. If structured logging is needed, use an encoder/layout with proper escaping instead of manually concatenating JSON strings.

### 14.3. Log volume and cardinality

Do not create a different Logger name per request. Do not put `requestId`, `userId`, or raw URLs containing IDs into high-cardinality metric labels. If detailed correlation is needed, place IDs into log/trace fields with controlled retention and access permissions.

Verbose logging at TRACE/DEBUG can increase CPU, allocations, I/O, network traffic, and storage usage. Enable it scoped by package for the needed duration; test slow sinks, full queues, and shutdown behavior.

### 14.4. One event and multiple telemetry signals

A Logger emits events; it **does not automatically generate metrics or distributed traces**. ThreadContext can carry a `traceId`, but separate instrumentation/propagation is required to produce spans. During investigations, combine log events with metrics (error rate, latency) and traces if the system has them.

## 15. Production Logger verification checklist

When seeing “missing logs” or “too many logs,” check in this order:

1. **Correct Logger instance/name?** Verify package/class, and do not confuse Log4j2 API with JUL/SLF4J.
2. **Correct runtime provider?** Is a compatible implementation present and was `log4j2.xml` loaded?
3. **Which LoggerConfig applies?** Specific name or closest ancestor? What is the Root level?
4. **Is the level appropriate?** Do DEBUG/INFO/WARN/ERROR meet the configured threshold?
5. **Is a Filter dropping the record?** Check Filters at all relevant layers.
6. **Is AppenderRef configured properly?** Is the Appender declared, started, and receiving records?
7. **Is additivity causing duplicates or blocking forwarding?** Trace the path to ancestor Appenders.
8. **Does the Layout output required fields?** Are Marker and `requestId` included in the pattern/encoder?
9. **Is context propagation accurate?** Ensure request IDs do not leak when threads are reused.
10. **Is the sink/collector receiving data?** Check stdout/stderr, file permissions, buffers, queues, exporters, and downstream filters.

Do not look at a `LOG.info` call alone and conclude a line is guaranteed to be in a file. Verify the API, configuration, and actual output destination.

## 17. Review questions and answers

**1. Is a Logger in Log4j2 the same as a LoggerConfig?**  
No. Logger is the API handle in Java code. LoggerConfig belongs to Log4j Core configuration and controls level/filter/Appender routing.

**2. Do you need a separate LoggerConfig for every class?**  
No. A package-level LoggerConfig can serve multiple class-level Loggers in that package.

**3. Can a Logger named com.example.order.CheckoutService use the com.example.order configuration?**  
Yes, if no more specific LoggerConfig exists and the name hierarchy applies as expected.

**4. Why might some INFO logs not reach a file even when the Logger level is INFO?**  
Because a Filter, AppenderRef, Appender, sink, or downstream pipeline can block or fail on them. Passing the level check is only one step.

**5. If Root is ERROR, can a child LoggerConfig at INFO with additivity=true send INFO events to the Root Appender?**  
Yes. Appender routing via additivity does not by default re-apply the Root threshold as if it were a fresh call to the Root Logger. Filters/AppenderRefs can still drop them.

**6. Should additivity=false be set on every LoggerConfig?**  
No. You must ensure the LoggerConfig has an appropriate AppenderRef; otherwise events may have nowhere to be written.

**7. Does isDebugEnabled() returning false mean DEBUG is not emitted on that Logger?**  
It indicates the Logger does not accept DEBUG at the time of the check; do not use it as a business condition or as a substitute for verifying the final sink.

**8. Does parameterized logging {} automatically prevent expensiveOperation() from running when DEBUG is disabled?**  
No. Java evaluates argument expressions before the call; if an argument is genuinely expensive, use a level check or a lazy API.

**9. Does the AUDIT Marker by itself guarantee that a record is durably stored?**  
No. A Marker is just a label; delivery/retention/audit guarantees depend on the pipeline.

**10. Why should ThreadContext be cleaned up?**  
To prevent one task's `requestId`/`traceId` from leaking into another task on a reused thread.

**11. What is the difference between org.apache.logging.log4j.LogManager and java.util.logging.LogManager?**  
One belongs to the Log4j2 API; the other belongs to the JDK's JUL. They do not share a configuration system without a corresponding integration/bridge.

**12. Should enabling DEBUG on Root in production be the first troubleshooting step?**  
Usually no. Choose a specific package, a time window, and a log-volume observation plan before increasing verbosity broadly.

## 19. Key takeaways

**Logger is the event-emitting handle in application code.** **LoggerConfig is what determines level, filter, appender, and additivity policies by Logger name** in Log4j Core. A class-level Logger is typically held in a **static final** field, uses parameterized messages with **{}**, and records context/Throwable data in a controlled manner.

When logs do not appear as expected, trace **logger name → LoggerConfig → level/filter → AppenderRef/additivity → layout → sink**. The verified Maven example shows a Logger emitting INFO/WARN with scoped Marker and `requestId`, while DEBUG is filtered out and events are not duplicated thanks to `additivity=false`.
