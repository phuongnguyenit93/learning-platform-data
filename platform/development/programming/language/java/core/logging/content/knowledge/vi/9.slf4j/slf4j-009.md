# Version compatibility của SLF4J trong Java

## 1. Tại sao phải kiểm tra tính tương thích phiên bản?

**SLF4J (Simple Logging Facade for Java)** là API giúp ứng dụng và thư viện Java gọi `logger.info(...)`, `logger.warn(...)` hay `logger.error(...)` mà không gắn chặt mã nguồn với một backend duy nhất. SLF4J **không tự đảm nhiệm toàn bộ việc ghi log**: khi chạy, nó cần một implementation thích hợp được kết nối qua *binding* hoặc *provider*.

Một ứng dụng có thể biên dịch thành công vì đã có `slf4j-api` nhưng **không thấy log trong runtime** vì thiếu provider, provider sai thế hệ hoặc bị chọn nhầm. Nâng Java, Spring Boot, Logback, Log4j 2 hoặc một thư viện transitively phụ thuộc SLF4J đều có thể thay đổi dependency được nạp cuối cùng.

Để kiểm tra version compatibility, cần xét đồng thời:

1. **API SLF4J:** phiên bản dùng để compile và phiên bản thực sự được tải trong JVM.
2. **Binding/provider:** thành phần nối API với backend; cơ chế đăng ký của nó phải phù hợp với SLF4J API.
3. **Backend:** Logback, Log4j 2, JUL, Simple hoặc NOP; từng backend có yêu cầu version và Java riêng.
4. **Build/runtime classpath:** dependency trực tiếp, dependency bắc cầu, BOM, bridge, fat JAR và classloader của container.
5. **Tính năng API đang gọi:** code dùng fluent API 2.0 không thể giả định API 1.7 cũng có các phương thức tương ứng.

**Phân biệt ba lớp tương thích:** mã nguồn có biên dịch lại được (*source compatibility*) không; bytecode có liên kết được (*binary compatibility*) không; và toàn bộ bộ logging có khởi tạo, xuất log ở đúng đích khi chạy (*runtime compatibility*) không. Ba kết luận có thể khác nhau.

## 2. SLF4J API, binding/provider và backend

```text
                  Java application / library
                              |
                  org.slf4j.Logger API
                              |
                         slf4j-api
                              |
              +---------------+---------------+
              |                               |
       1.7.x: binding                  2.0.x: provider
       StaticLoggerBinder             SLF4JServiceProvider
              |                         via ServiceLoader
              +---------------+---------------+
                              |
                 Đúng một implementation
             /            |             \
        Logback      Log4j 2 adapter    slf4j-simple
             \            |             /
                    Appender / sink
                              |
                   stdout / file / collector
```

- **API:** các lớp trong package `org.slf4j` như `Logger`, `LoggerFactory`, `MDC`, `Marker`. Ứng dụng thường lập trình dựa trên API này.
- **Binding ở SLF4J 1.7 và cũ hơn:** một JAR công bố implementation qua lớp `org.slf4j.impl.StaticLoggerBinder`.
- **Provider ở SLF4J 2.0 trở lên:** một JAR/module cung cấp implementation của `org.slf4j.spi.SLF4JServiceProvider` và được tìm qua `ServiceLoader`.
- **Backend:** thực thi chính sách level, filter, formatter, appender, I/O. Ví dụ `logback-classic` là implementation SLF4J trực tiếp; `log4j-slf4j2-impl` là cầu nối từ SLF4J 2 sang Log4j 2.
- **Bridge:** chuyển sự kiện từ API logging khác vào SLF4J hoặc ngược lại. Bridge và provider không đồng nghĩa; chiều chuyển tiếp rất quan trọng.

Trong ứng dụng thông thường, nên có **một provider SLF4J được lựa chọn rõ ràng** trên runtime classpath. Nhiều provider không phải cách chuẩn để “ghi log đồng thời tới nhiều nơi”; hãy chọn một backend và cấu hình nhiều appender/sink ở backend đó.

## 3. Điểm thay đổi lớn nhất: SLF4J 1.7 và 2.0

### SLF4J 1.7.x: tìm StaticLoggerBinder

SLF4J 1.7 tìm một lớp đặc biệt:

```text
org.slf4j.impl.StaticLoggerBinder
```

Đây là cơ chế *binding* cũ. Các ví dụ lịch sử gồm `slf4j-simple:1.7.x` và `logback-classic:1.2.x`. Chúng được thiết kế để ghép với API của thế hệ 1.7.

### SLF4J 2.0.x: dùng Java ServiceLoader

Từ 2.0, SLF4J chuyển sang tìm:

```text
org.slf4j.spi.SLF4JServiceProvider
```

bằng `java.util.ServiceLoader`. Khi chạy trên classpath, một provider thường được đăng ký qua tệp:

```text
META-INF/services/org.slf4j.spi.SLF4JServiceProvider
```

SLF4J 2.0 **không còn dùng `StaticLoggerBinder` để lựa chọn backend**. Vì thế nếu nâng `slf4j-api` từ 1.7 lên 2.0 mà giữ nguyên `slf4j-simple:1.7.x` hoặc `logback-classic:1.2.x`, API mới có thể thông báo binding cũ bị bỏ qua, sau đó dùng NOP do không có provider hợp lệ. Code vẫn có thể chạy trong khi log nghiệp vụ biến mất.

Ở chiều ngược lại, API 1.7 không có cơ chế nhận provider 2.0 qua `ServiceLoader`. Chỉ thêm `slf4j-simple:2.0.x` cho ứng dụng đang chạy API 1.7 không tạo ra binding 1.7.

### SLF4J 2.0 thêm fluent logging API

Ngoài các lời gọi quen thuộc, SLF4J 2.0 cho phép:

```java
// Đoạn mã minh họa trong ứng dụng đã có SLF4J 2.x.
logger.atInfo()
      .addKeyValue("orderId", "O-17")
      .log("Order accepted");
```

Method `atInfo()` không có trong interface `Logger` của SLF4J 1.7. Nếu mã compile với 2.0 nhưng runtime nạp `slf4j-api:1.7.x`, một lời gọi tới method mới có thể gây `NoSuchMethodError`. Tương thích ngược của những lời gọi API cũ **không có nghĩa mọi tính năng mới cũng tồn tại trong API cũ**.

## 4. Ma trận ghép phiên bản

| SLF4J API tại runtime | Provider/binding | Kết quả mong đợi |
| --- | --- | --- |
| `1.7.x` | `slf4j-simple:1.7.x` | **Phù hợp:** cùng thế hệ StaticLoggerBinder. |
| `2.0.x` | `slf4j-simple:2.0.x` | **Phù hợp:** ServiceLoader và provider 2.0. |
| `1.7.x` | `logback-classic:1.2.x` | **Tổ hợp lịch sử phù hợp:** nhưng dòng Logback này đã cũ. |
| `2.0.x` | `logback-classic:1.6.x` | **Phù hợp về thế hệ:** cần JDK 11+ và bộ Logback nhất quán. |
| `2.0.x` | `slf4j-simple:1.7.x` | **Không phù hợp:** binding cũ bị API 2.0 bỏ qua. |
| `1.7.x` | `slf4j-simple:2.0.x` | **Không phù hợp:** API 1.7 không tìm provider 2.0. |
| `2.0.x` | `logback-classic:1.2.x` | **Không phù hợp:** implementation cũ dùng binding 1.7. |
| `2.0.x` | Không có provider | Cảnh báo thiếu provider; thường mặc định NOP. |
| `2.0.x` | Hai hoặc nhiều provider 2.0 | Có thể cảnh báo nhiều provider; cần chọn một bộ hợp lệ. |

Đối với provider phát hành trong nhóm `org.slf4j`, **major.minor của API và provider phải khớp**, ví dụ `slf4j-api:2.0.20` kết hợp `slf4j-simple:2.0.20`. Patch có thể khác trong cùng dòng theo quy tắc của SLF4J, nhưng đồng bộ patch thường dễ kiểm tra và cập nhật bảo mật hơn.

**Logback và Log4j 2 dùng phiên bản của riêng chúng.** Không tìm `logback-classic:2.0.20` chỉ vì API đang ở `2.0.20`; hãy đọc compatibility matrix của chính Logback, Log4j và JDK.

Mọi dòng trong bảng còn phụ thuộc điều kiện khác như version Java, dependency nội bộ và cấu hình. **Cùng thế hệ API/provider là điều kiện cần nhưng chưa tự bảo đảm mọi cấu hình runtime đều hoạt động.**

## 5. Source compatibility và binary compatibility

SLF4J chủ trương giữ API mà ứng dụng sử dụng ổn định. Những lời gọi lâu đời như:

```java
// Đoạn mã bên trong service đã khai báo logger SLF4J.
logger.info("Loaded orderId={}", orderId);
logger.warn("Retry for orderId={}", orderId);
logger.error("Failed for orderId={}", orderId, exception);
```

thường có thể tiếp tục hoạt động khi ứng dụng chuyển từ runtime 1.7 sang 2.0, miễn API/provider của runtime được ghép đúng. Một thư viện dependency đã **compile với slf4j-api 1.7** không nhất thiết cần biên dịch lại chỉ vì ứng dụng sử dụng 2.0.

Tuy nhiên, phải xét:

- **Thư viện chỉ dùng public API hay dùng internal SPI?** Nếu dùng `org.slf4j.impl.StaticLoggerBinder` hoặc class nội bộ của implementation, khả năng tương thích khác với mã chỉ gọi `Logger.info`.
- **Có method mới không?** Code dùng `atDebug()` hoặc `atInfo()` cần API 2.x khi compile và runtime.
- **API JAR nào thực sự được tải?** Maven/Gradle có thể giải quyết xung đột theo rule riêng; một server có thể cung cấp JAR khác runtime classpath trong IDE.
- **Một class có được load nhiều lần qua classloader khác không?** Container/plugin architecture có thể khiến hiện tượng provider không hiển thị cho API dù dependency có trong hệ thống.

*Source compatibility* là khả năng biên dịch lại source. *Binary compatibility* là khả năng bytecode cũ liên kết được với API mới. *Runtime compatibility* còn cần backend/provider đúng, phát được log và giữ các hành vi vận hành cần thiết.

Nếu gặp `NoSuchMethodError`, `NoClassDefFoundError`, `ClassNotFoundException`, `AbstractMethodError` hay `ServiceConfigurationError`, không suy đoán nguyên nhân chỉ từ tên lỗi: xem stack trace, class nào gây lỗi và JAR nào thực sự chứa class được tải.

## 6. JDK version và phiên bản backend

SLF4J 2.0.x **yêu cầu Java 8 trở lên**, nên API có thể dùng với Java 17. Nhưng backend có yêu cầu độc lập:

| Thành phần | JDK / phiên bản cần chú ý |
| --- | --- |
| SLF4J 1.7.x | API đời cũ; không có fluent API 2.0. |
| SLF4J 2.0.x | Java 8+, dùng ServiceLoader. |
| Logback 1.3.x | Hỗ trợ SLF4J 2.0, Java 8; dòng đã cũ. |
| Logback 1.4.x | Hỗ trợ SLF4J 2.0, Java 11; dòng đã cũ. |
| Logback 1.6.x | Hỗ trợ SLF4J 2.0, Java 11+; có thay đổi cấu hình so với dòng cũ. |
| Log4j 2 với `log4j-slf4j2-impl` | Chọn bản Log4j cùng họ dependency và JDK tương ứng theo tài liệu Log4j. |

Nếu Java runtime cũ hơn bytecode của backend/provider, JVM có thể ném `UnsupportedClassVersionError`. Lệnh kiểm tra cơ bản:

```bash
java -version
javac -version
```

Toolchain/`--release 17` của dự án quy định bytecode **do dự án tự compile**; nó không tự biên dịch lại dependency đã phát hành cho một JDK khác.

Đặc biệt với **Spring Boot**, starter logging và BOM thường chọn một bộ Logback/SLF4J đã được framework kiểm thử. Nếu muốn nâng riêng SLF4J/Logback, hãy xác nhận compatibility theo **phiên bản Spring Boot đang chạy**, dependency management, namespace `javax.*`/`jakarta.*` và JDK trước khi override. Không coi ví dụ POM độc lập ở dưới là danh sách dependency nên copy vào mọi ứng dụng Spring Boot.

## 7. Chọn Logback, Log4j 2 và bridge đúng hướng

### Logback

Logback cung cấp backend cho SLF4J trực tiếp thông qua `logback-classic` cùng `logback-core` phù hợp. Một sơ đồ phiên bản thường gặp với Java 17:

```text
slf4j-api:2.0.x
        |
logback-classic:1.6.x
        |
logback-core:1.6.x
```

Đây là mô tả quan hệ, không phải dependency graph có hướng bắt buộc như trong POM. Khi lựa chọn version, để dependency management giải quyết cả bộ nhất quán. Nếu đã chọn Logback làm provider thì không nên đồng thời đưa `slf4j-simple` vào runtime.

Việc nâng Logback còn có thể đòi hỏi sửa cấu hình XML. Ví dụ các bản Logback mới đã thay đổi cách xử lý điều kiện dùng Janino. Vì vậy, **không dừng việc kiểm thử ở compile**, phải khởi động bằng cấu hình thực tế và xác nhận appender/filter/rolling file hoạt động đúng.

### Log4j 2

Nếu backend đích là Log4j 2, chọn adapter đúng thế hệ SLF4J:

| API nguồn | Adapter chuyển tới Log4j 2 |
| --- | --- |
| SLF4J 1.7.x/cũ hơn | `org.apache.logging.log4j:log4j-slf4j-impl` |
| SLF4J 2.0.x | `org.apache.logging.log4j:log4j-slf4j2-impl` |

Đừng nhầm với `log4j-to-slf4j`, là bridge đi từ **Log4j API → SLF4J**. Kết hợp nó với `log4j-slf4j2-impl` trong cùng pipeline có thể tạo vòng lặp:

```text
SLF4J -> log4j-slf4j2-impl -> Log4j API
   ^                             |
   +-------- log4j-to-slf4j ------+
```

Nếu dùng Log4j 2 làm đích, đồng bộ các module Log4j với BOM/constraints phù hợp và giữ duy nhất hướng chuyển tiếp cần thiết.

### JUL và chiều chuyển tiếp

- `slf4j-jdk14`: hướng **SLF4J → java.util.logging (JUL)**.
- `jul-to-slf4j` cùng `SLF4JBridgeHandler`: hướng **JUL → SLF4J**.

Nếu triển khai đồng thời hai chiều và cài bridge, có thể tạo vòng lặp:

```text
SLF4J -> slf4j-jdk14 -> JUL -> jul-to-slf4j -> SLF4J -> ...
```

Nguyên tắc là **một backend đích và các bridge đổ về đích đó**. Không thêm mọi adapter có tên logging với hy vọng hệ thống tự hợp nhất.

## 8. Ví dụ Java 17 chạy được: SLF4J API 2.0 và provider cùng phiên bản

Đây là project Maven nhỏ sử dụng `slf4j-api:2.0.20` và `slf4j-simple:2.0.20`. Hai số version được **pin để minh họa tổ hợp tái lập**; không phải khẳng định đó mãi là release mới nhất.

Cấu trúc thư mục:

```text
slf4j-version-demo/
├── pom.xml
└── src/
    └── main/
        └── java/
            └── demo/
                └── Slf4jVersionDemo.java
```

File `pom.xml`:

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>
    <groupId>demo</groupId>
    <artifactId>slf4j-version-demo</artifactId>
    <version>1.0.0</version>

    <properties>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
        <maven.compiler.release>17</maven.compiler.release>
    </properties>

    <dependencies>
        <dependency>
            <groupId>org.slf4j</groupId>
            <artifactId>slf4j-api</artifactId>
            <version>2.0.20</version>
        </dependency>
        <dependency>
            <groupId>org.slf4j</groupId>
            <artifactId>slf4j-simple</artifactId>
            <version>2.0.20</version>
            <scope>runtime</scope>
        </dependency>
    </dependencies>

    <build>
        <plugins>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-compiler-plugin</artifactId>
                <version>3.13.0</version>
            </plugin>
            <plugin>
                <groupId>org.codehaus.mojo</groupId>
                <artifactId>exec-maven-plugin</artifactId>
                <version>3.3.0</version>
                <configuration>
                    <mainClass>demo.Slf4jVersionDemo</mainClass>
                </configuration>
            </plugin>
        </plugins>
    </build>
</project>
```

File `src/main/java/demo/Slf4jVersionDemo.java`:

```java
package demo;

import org.slf4j.ILoggerFactory;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public final class Slf4jVersionDemo {

    private static final Logger LOG =
            LoggerFactory.getLogger(Slf4jVersionDemo.class);

    private Slf4jVersionDemo() {
    }

    public static void main(String[] args) {
        ILoggerFactory factory = LoggerFactory.getILoggerFactory();

        System.out.println("FACTORY="
                + factory.getClass().getSimpleName());
        System.out.println("INFO_ENABLED=" + LOG.isInfoEnabled());

        LOG.info("Order {} accepted", "O-17");

        LOG.atInfo()
                .addKeyValue("orderId", "O-17")
                .log("Order accepted with fluent API");
    }
}
```

Chạy từ thư mục chứa `pom.xml` bằng JDK 17+ và Maven có quyền tải dependency:

```bash
mvn -q -Dorg.slf4j.simpleLogger.defaultLogLevel=info compile exec:java
```

**Stdout chính xác từ hai câu `System.out.println` của chương trình:**

```text
FACTORY=SimpleLoggerFactory
INFO_ENABLED=true
```

Hai lời gọi `LOG.info(...)` và `LOG.atInfo()...` còn tạo thông điệp qua backend `slf4j-simple`, mặc định hướng tới **stderr**. Định dạng của những dòng log đó (logger name, thread, key-value) phụ thuộc backend/config và có thể xen với stdout khác nhau theo môi trường. Vì vậy **không coi hai dòng trên là toàn bộ output của terminal**.

Vì sao ví dụ có ích:

1. `slf4j-api:2.0.20` cho phép biên dịch cả lời gọi cổ điển và fluent API.
2. `slf4j-simple:2.0.20` cung cấp provider runtime cùng họ `2.0.x`.
3. `LoggerFactory.getILoggerFactory()` cho biết implementation đã được chọn; `SimpleLoggerFactory` là dấu hiệu provider Simple.
4. Provider được khai báo ở Maven `runtime` vì code Java chỉ import API, còn implementation chỉ cần khi chạy.
5. Nếu bỏ provider, SLF4J 2.0 thường cảnh báo thiếu provider và trở về NOP; nếu thay provider bằng binding 1.7 cũ, API 2.0 không thể sử dụng binding đó.

Khi dùng **thư viện chia sẻ**, thường chỉ khai báo dependency `slf4j-api` ở scope cần thiết và để ứng dụng cuối chọn provider. Thêm provider vào thư viện ở runtime/compile scope có thể vô tình áp đặt backend lên mọi ứng dụng sử dụng thư viện.

## 9. Tương đương trong Gradle (Groovy DSL)

Với một project Java có source `demo.Slf4jVersionDemo` như trên:

```groovy
plugins {
    id 'java'
    id 'application'
}

repositories {
    mavenCentral()
}

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(17)
    }
}

dependencies {
    implementation 'org.slf4j:slf4j-api:2.0.20'
    runtimeOnly 'org.slf4j:slf4j-simple:2.0.20'
}

application {
    mainClass = 'demo.Slf4jVersionDemo'
}
```

Chạy với Gradle Wrapper:

```bash
./gradlew run
```

Trên Windows dùng `gradlew.bat run`. Đây là ví dụ build độc lập; trong dự án Spring Boot, đừng thêm `slf4j-simple` nếu starter đã cung cấp Logback mà chưa có lý do thay backend.

## 10. Cảnh báo version compatibility và cách xử lý

### 10.1. Không có provider

Thông báo tiêu biểu trong SLF4J 2.x:

```text
SLF4J: No SLF4J providers were found.
SLF4J: Defaulting to no-operation (NOP) logger implementation
```

Điều này cho biết API đã khởi tạo nhưng không tìm được implementation phù hợp. Ứng dụng có thể vẫn chạy bình thường, trong khi các event SLF4J bị bỏ qua. Cần kiểm tra **runtime dependency**, provider đã khai báo ở đúng scope và JAR được đóng gói thực sự.

### 10.2. Binding cũ bị SLF4J 2.x bỏ qua

Thông báo tiêu biểu:

```text
SLF4J: Class path contains SLF4J bindings targeting slf4j-api versions 1.7.x or earlier.
```

Hãy tìm `logback-classic:1.2.x`, `slf4j-simple:1.7.x` hoặc binding cũ khác trong dependency tree. Đổi sang provider phù hợp 2.0 và gỡ artifact không sử dụng. Không xử lý bằng cách thêm một binding 1.7 khác.

### 10.3. Nhiều provider cùng lúc

Nếu có `logback-classic` và `slf4j-simple` cùng làm provider, SLF4J có thể phát thông báo nhiều provider. Mã có thể xuất log qua một implementation, nhưng lựa chọn đó không nên được coi là ổn định theo ý định của ứng dụng. Tìm nguồn dependency transitively kéo theo provider dư và loại bỏ đúng artifact.

### 10.4. NoSuchMethodError hoặc NoClassDefFoundError

Kiểm tra method/class trong stack trace và origin của JAR thực sự tải. Ví dụ `atInfo()` không có trong API 1.7 dù code đã compile với 2.0. Một backend/SPi mismatch cũng có thể làm lỗi khởi tạo. Nếu dependency tree trong IDE đúng mà artifact deploy sai, cần kiểm tra classloader, fat JAR và thư viện do container cung cấp.

### 10.5. Lỗi khi đóng gói fat JAR

Provider SLF4J 2.x được phát hiện qua `ServiceLoader`. Khi shade/merge JAR, nếu bỏ mất hoặc ghi đè tệp:

```text
META-INF/services/org.slf4j.spi.SLF4JServiceProvider
```

thì provider có thể không được tìm thấy dù class implementation vẫn nằm trong artifact. Cần cấu hình merge service descriptors đúng cách nếu dùng shade, kiểm tra nội dung JAR đã đóng gói và chạy thử **chính artifact deploy**, không chỉ chạy ứng dụng từ IDE.

Trong ứng dụng sử dụng JPMS module path, việc module khai báo/cung cấp service còn phụ thuộc module descriptor; không giả định việc copy JAR vào thư mục bất kỳ là đủ.

## 11. Điều tra dependency hiệu lực với Maven/Gradle

**Maven:**

```bash
mvn dependency:tree
mvn dependency:tree -Dincludes=org.slf4j:*,ch.qos.logback:*,org.apache.logging.log4j:*
```

Đọc cây phụ thuộc để biết phiên bản `slf4j-api` được chọn, provider nào được đưa vào runtime, nhóm Logback/Log4j nào xuất hiện và artifact nào kéo thêm binding/bridge. Dependency management và nearest-definition/mediation của Maven có thể khiến version thực tế khác version một thư viện mong đợi.

**Gradle:**

```bash
./gradlew dependencies --configuration runtimeClasspath
./gradlew dependencyInsight --configuration runtimeClasspath --dependency slf4j-api
./gradlew dependencyInsight --configuration runtimeClasspath --dependency logback-classic
```

Trong multi-module, thay bằng task của module ứng dụng cụ thể như `:app:dependencies`, `:app:dependencyInsight`. Cần xem **runtimeClasspath**, không chỉ `compileClasspath`, bởi provider có thể chỉ xuất hiện khi chạy.

Nếu project chứa nhiều JAR hoặc chạy trong application server, so sánh output build tool với **classpath thực tế của process deploy**. Có thể in ra ở chế độ chẩn đoán:

```java
// Mã minh họa bên trong chương trình đã có SLF4J runtime.
System.out.println(
        org.slf4j.LoggerFactory.getILoggerFactory()
                .getClass().getName());
```

Thông tin factory là một bằng chứng hữu ích về provider đang được nạp; nó chưa bảo đảm level, appender, format và remote collector đều chính xác. Cần phát một event thử nghiệm và xác nhận event đến nơi nhận mong muốn.

## 12. Tương thích khi dùng framework và thư viện bên thứ ba

**Thư viện:** nên lập trình dựa trên `slf4j-api` và để ứng dụng quyết định implementation. Một thư viện compile với SLF4J 1.7 có thể chạy tốt trên runtime API 2.0 khi chỉ dùng các method công khai ổn định. Đừng vội thêm thêm `slf4j-api:1.7.x` như JAR thứ hai chỉ vì dependency cũ từng dùng nó.

**Ứng dụng độc lập:** lựa chọn một provider với backend phù hợp, pin hoặc quản lý version bằng BOM/constraints để tránh version “trôi” theo dependency transitively được cập nhật.

**Spring Boot:** starter thường đã đưa logging implementation và bridge thích hợp vào classpath. Nếu nâng hoặc đổi backend, dùng tài liệu cho phiên bản Spring Boot đang chạy. Việc tự thêm `slf4j-simple` cùng Logback là nguyên nhân phổ biến dẫn đến nhiều provider.

**Tích hợp JUL/Commons Logging/Log4j:** xác định hướng bridge cho từng API. Ví dụ `jul-to-slf4j` chỉ chuyển JUL về SLF4J khi bridge handler được cài đặt; một JAR có tên bridge nằm trong classpath chưa chắc mọi lời gọi JUL tự chuyển hướng. Ngược lại, dùng đồng thời `slf4j-jdk14` và `jul-to-slf4j` đã cài có thể làm log quay vòng.

## 13. Quy trình nâng SLF4J 1.7 → 2.0 có kiểm chứng

1. **Ghi lại trạng thái hiện hành:** API, binding, backend, bridge, version JDK, Spring Boot/framework, dependency tree và artifact deploy.
2. **Chọn bộ phiên bản mục tiêu:** API SLF4J 2.0.x, một provider 2.0 phù hợp, backend và JDK đáp ứng tài liệu tương thích; cân nhắc BOM framework.
3. **Thay binding cũ:** gỡ các artifact chỉ dành cho `StaticLoggerBinder`, thêm provider theo `ServiceLoader`, thay Log4j adapter 1.7 bằng adapter 2.0 nếu cần.
4. **Rà soát bridge:** vẽ hướng xử lý event, tránh vòng lặp JUL ↔ SLF4J hay Log4j ↔ SLF4J.
5. **Rà soát dependency transitive:** kiểm tra API, provider nào thực sự được resolve; loại provider dư, đồng bộ Logback-core/classic và các module backend.
6. **Biên dịch/kiểm thử trên đúng JDK:** nếu dùng fluent API, phải biên dịch và chạy với API 2.0; không dựa trên bytecode của Java project để kết luận JAR dependency chạy được.
7. **Kiểm tra khởi tạo provider:** không có cảnh báo NOP, binding cũ hoặc nhiều provider; xác nhận factory được chọn như dự kiến.
8. **Kiểm tra log ở nơi nhận:** INFO, WARN, ERROR, exception stack trace, MDC/context, marker/structured attributes và các mức/filter quan trọng.
9. **Chạy artifact cuối:** fat JAR/WAR hoặc container image trên môi trường giống production; xác nhận ServiceLoader metadata và classpath.
10. **Quan sát sau triển khai:** so sánh số event quan trọng và sink thực nhận; có cách quay lại bộ dependency cũ nếu gặp lỗi.

Không thực hiện nâng cấp chỉ vì “pom.xml hiển thị 2.0”. Điều kiện hoàn tất là **ứng dụng deploy thật ghi được log phù hợp và không có mismatch ẩn**.

## 14. Các tình huống điển hình

**Tình huống A — chỉ nâng API:** Project có `slf4j-api:2.0.x` nhưng `logback-classic:1.2.x`. Đây là tổ hợp sai thế hệ provider. Chọn Logback phù hợp SLF4J 2.0 và JDK/framework, đồng thời gỡ binding cũ.

**Tình huống B — Log4j 2 + SLF4J 2:** Thêm `log4j-slf4j-impl` thay vì `log4j-slf4j2-impl`. Adapter sai thế hệ; cần đổi adapter theo API thực tế. Không để `log4j-to-slf4j` tạo hướng chuyển tiếp ngược lại.

**Tình huống C — thư viện cũ:** Library đã compile với SLF4J 1.7, ứng dụng chạy API 2.0 với provider 2.0. Các lời gọi công khai thông thường của thư viện vẫn có thể hoạt động; kiểm tra xem library có dùng internal SLF4J hoặc binding cũ hay không.

**Tình huống D — code dùng fluent nhưng deploy sai API:** Source có `logger.atInfo()`, compile tốt với 2.0 nhưng runtime lấy API 1.7 từ server. Cần điều chỉnh classpath/classloader để chạy đúng API, không thể sửa chỉ bằng thay provider.

**Tình huống E — lỗi chỉ xuất hiện sau đóng gói:** Chạy qua Maven tốt, fat JAR thiếu thông tin `META-INF/services`. Cần sửa bước shade/merge services và thử trên artifact đã build.

## 15. Bài tập và checklist trước khi phát hành

**Bài tập 1:** Chạy ví dụ Maven ở mục 8. Giải thích vì sao `FACTORY=SimpleLoggerFactory` chứng minh provider Simple được chọn, nhưng không tự kiểm chứng đã ghi vào file/collector.

**Bài tập 2:** Nhìn vào cặp `slf4j-api:2.0.x` và `slf4j-simple:1.7.x`. Dự đoán lý do log bị bỏ, phân biệt `StaticLoggerBinder` với `SLF4JServiceProvider`.

**Bài tập 3:** Vẽ hướng của bốn artifact `jul-to-slf4j`, `slf4j-jdk14`, `log4j-to-slf4j` và `log4j-slf4j2-impl`. Chỉ ra vì sao kết hợp hai hướng đảo chiều có thể tạo loop.

**Bài tập 4:** Một ứng dụng Java 17 có `slf4j-api:2.0.x`, `logback-classic:1.2.x` và `slf4j-simple:2.0.x`. Nhận diện hai vấn đề: Logback 1.2 sai thế hệ, và provider Simple dư nếu định dùng Logback. Lập kế hoạch gỡ/đổi dependency trước khi chạy thử.

**Checklist code review:**

- [ ] Xác định đúng version `slf4j-api` **tại runtime**, provider/binding tương ứng và JDK.
- [ ] Với provider nhóm SLF4J, major.minor khớp API; patch được quản lý có chủ đích.
- [ ] Chọn một provider mong muốn, không vô tình NOP hoặc nhiều provider.
- [ ] Logback/Log4j backend, core module, cấu hình và JDK tương thích theo ma trận chính thức.
- [ ] Các bridge đều hướng về backend đã chọn, không có cặp chuyển tiếp vòng tròn.
- [ ] Fluent API 2.0 chỉ được dùng với API có method tương ứng.
- [ ] Dependency tree/BOM/Spring Boot version và classpath deploy đã được đối chiếu.
- [ ] Đóng gói giữ được `ServiceLoader` service descriptor của provider 2.0.
- [ ] Smoke test từ artifact chạy thật tạo được log tới sink dự kiến.
- [ ] Không có cảnh báo thiếu provider, binding cũ bị bỏ qua hoặc nhiều provider ngoài chủ ý.
