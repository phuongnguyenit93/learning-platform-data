# Removing MDC Values in Java Logging: remove, clear, and Lifecycle-Proper Context Restoration

## 1. Why Remove MDC Values?

**MDC (Mapped Diagnostic Context)** is a mechanism for attaching **key–value** pairs to the logging context of an execution thread. In Java applications using **SLF4J**, values such as **request_id**, **trace_id**, **operation**, or **log-permitted tenant_id** can be added to many log records without manually passing them into every logger call.

For example, when processing request A:

~~~text
INFO | request_id=req-A | operation=createOrder | ORDER_STARTED
INFO | request_id=req-A | operation=saveOrder   | ORDER_SAVED
~~~

Request A finishes. A thread in the web server can immediately handle request B. If **request_id=req-A** remains in the MDC, request B's logs may carry ID A:

~~~text
INFO | request_id=req-A | operation=           | REQUEST_B_STARTED
~~~

This is a **context leak**: information from one request is retained and mistakenly attached to another unit of work. The consequence is not merely dashboards querying the wrong request; it can leak metadata across tenants or mislead incident investigations.

**Removing MDC values** is the operation of ending the lifetime of one or more keys when they are no longer valid for the current work. Three core rules:

1. **Remove only what you own** when only a single key's lifetime ends.
2. **Remove or restore in a finally block** so exceptions and early returns do not skip cleanup.
3. **In nested scopes, restore the previous value instead of blindly removing it** if the key already existed.

This article focuses on **removing MDC values properly** in SLF4J, Logback, and request/thread pool scenarios, while also comparing with Log4j 2's **ThreadContext**.

## 2. Revisiting the Nature of MDC

Commonly used SLF4J APIs:

~~~java
MDC.put("request_id", "req-42");
String requestId = MDC.get("request_id");
MDC.remove("request_id");
~~~

MDC is a façade API of **org.slf4j.MDC**. It delegates to the logging provider/backend's MDC adapter at runtime. With Logback, MDC is typically bound to the current thread; some backends or providers may implement it differently. Therefore, **do not assume every provider stores, propagates, or outputs MDC in the same way**.

| Data category | Examples | Typical scope |
| --- | --- | --- |
| Resource context | service, release, environment | Instance / application |
| Request context | request_id, trace_id | A single request or message |
| Operation context | operation=createOrder | A single operation |
| Attempt context | attempt=2 | A specific attempt |
| Event context | event_code, outcome, error_type | A single log event |

Static fields such as **service** are typically configured at the encoder or collector level. There is no need to put everything into MDC and call **clear()** in every method.

**MDC is not a business data store, not a cache, and does not replace a tracing context.** It is supplementary metadata for logs, with a lifetime that must be carefully controlled.

## 3. MDC.remove(key): Removing a Single Key

API:

~~~java
MDC.remove("operation");
~~~

**remove(key)** deletes a single mapping from the current MDC without automatically removing other values.

Suppose the MDC before cleanup is:

~~~text
request_id = req-42
trace_id   = trace-example
operation  = reserveStock
~~~

After:

~~~java
MDC.remove("operation");
~~~

Remaining context:

~~~text
request_id = req-42
trace_id   = trace-example
~~~

This is usually the right choice when **a method/service only owns the operation field** while request_id and trace_id must remain for subsequent steps.

Key characteristics from the SLF4J API:
- **remove(key)** takes the key name, not the value.
- If the key does not exist, the operation has nothing to remove.
- **A null key is invalid**; SLF4J may throw an IllegalArgumentException.
- Removing a key causes **MDC.get(key)** to return null when the key is no longer present.
- It **does not restore** an older value that was overwritten by the same key.
- It **does not modify logs that were already generated or stored**.

Properly scoped example:

~~~java
MDC.put("operation", "reserveStock");
try {
    reserveStock();
} finally {
    MDC.remove("operation");
}
~~~

This snippet is **illustrative**, assuming the **reserveStock()** method and the **org.slf4j.MDC** import already exist. If **operation** already had another value before entering this method, this code will lose the old value; section 6 explains how to restore it in nested scopes.

## 4. MDC.clear(): Clearing the Entire Current Map

API:

~~~java
MDC.clear();
~~~

**clear()** removes all key–value pairs in the provider's current MDC map, not just request_id.

Before:

~~~text
request_id = req-42
trace_id   = trace-example
operation  = createOrder
~~~

After **MDC.clear()**, all three keys are no longer in the current map.

Comparison:

| Operation | Effect | When to consider |
| --- | --- | --- |
| **MDC.remove("operation")** | Removes only operation | When owning only operation |
| **MDC.remove("request_id")** | Removes only request_id | When owning only request_id |
| **MDC.clear()** | Clears the entire current map | When the owner of a request/job boundary wants to clean up the entire context belonging to that scope |
| **MDC.getCopyOfContextMap()** | Gets a copy of the map, may be null | When state needs to be saved for restoration |
| **MDC.setContextMap(previous)** | Replaces the map with a saved copy | When restoring a nested scope |

**Do not call MDC.clear() arbitrarily inside a helper or library method.** The caller may have already set **trace_id**, **tenant_id**, or **request_id**. A helper that clears everything wipes out the caller's context, causing subsequent logs to lose correlation.

### When is clearing everything appropriate?

At the **outermost boundary** owned by that component, for example:
- At the end of an HTTP request in a filter designed to manage the entire MDC.
- At the end of a standalone job after creating a dedicated context for that job.
- At the end of work on a worker thread before the thread is reused, if that worker boundary itself owns the entire MDC for the task.

If a scope already has context from a caller and only **adds a few keys**, restoring a snapshot is usually safer than wiping everything clean.

**clear is not a command to delete data already sent to a collector.** Events that have already been emitted or queued may contain a copy of the context captured at the time they were created.

## 5. Why Use try/finally?

Unsafe code:

~~~java
MDC.put("request_id", requestId);
handleRequest();
MDC.clear();
~~~

If **handleRequest()** throws an exception, the clear call may never execute. Similarly, returning mid-method or errors in processing branches can skip cleanup.

Standard pattern:

~~~java
MDC.put("request_id", requestId);
try {
    handleRequest();
} finally {
    MDC.remove("request_id");
}
~~~

This is an illustrative snippet in a method where **requestId** and **handleRequest()** are already declared. Whether handleRequest completes normally, returns early, or throws an exception, Java executes finally under normal control-flow semantics when exiting that block.

If the scope owns the entire context:

~~~java
MDC.clear();
try {
    MDC.put("request_id", requestId);
    MDC.put("operation", "handleRequest");
    handleRequest();
} finally {
    MDC.clear();
}
~~~

The initial clear is only appropriate when this is a **boundary permitted to reset the context**. Do not copy this pattern verbatim into a method where the caller has already established a trace context.

### Lesson on ownership

**Who sets the context? Who has the right to remove it?**

- Request filters/middleware typically manage request_id.
- Tracing instrumentation manages trace_id/span_id.
- Service methods can manage their own operation.
- A helper should not remove keys belonging to outer layers.
- Shared libraries should avoid clearing the host application's MDC.

The rule **“the component that creates a scope must be responsible for ending that scope”** helps reduce leaks and prevent accidental deletion.

## 6. Nested Scopes: Removing Does Not Mean Restoring

This is an easy mistake to make when using MDC.

Initially:

~~~text
operation=createOrder
~~~

Inside a child method:

~~~java
MDC.put("operation", "reserveStock");
try {
    reserveStock();
} finally {
    MDC.remove("operation");
}
~~~

After the child method finishes, **operation is completely removed** instead of returning to **createOrder**. The **remove** call has no idea what the previous value was.

### The right way: save the old value and restore it

~~~java
String previousOperation = MDC.get("operation");

MDC.put("operation", "reserveStock");
try {
    reserveStock();
} finally {
    if (previousOperation == null) {
        MDC.remove("operation");
    } else {
        MDC.put("operation", previousOperation);
    }
}
~~~

Result:
- If operation was previously **createOrder**, it is restored.
- If operation did not previously exist, the key is removed.
- Other keys such as request_id remain intact.

This is **illustrative code**, not a standalone Java class. Use this pattern when a scope only overrides **a single key** and does not need to replace the entire map.

### Why not always call clear in finally?

If a child method calls **MDC.clear()**, it can wipe out the parent scope's request_id and trace_id as well. Even though nothing leaks, logs for subsequent steps will lose necessary context. **Over-cleaning is also a bug**.

## 7. MDC.putCloseable and try-with-resources

SLF4J provides the API:

~~~java
try (MDC.MDCCloseable ignored =
             MDC.putCloseable("operation", "reserveStock")) {
    reserveStock();
}
~~~

Upon exiting try-with-resources, **close() removes the operation key**. This mechanism is very convenient when the key **does not yet exist in the parent scope** or when you intentionally want the key gone after the scope.

**Pay close attention:** MDCCloseable **does not automatically save and restore the old value**. If **operation=createOrder** already existed, calling **MDC.putCloseable("operation","reserveStock")** and then closing the scope will **remove** operation rather than reverting it to createOrder.

Example:

~~~java
MDC.put("operation", "createOrder");

try (MDC.MDCCloseable ignored =
             MDC.putCloseable("operation", "reserveStock")) {
    // MDC.get("operation") is "reserveStock".
}

// MDC.get("operation") is null, not "createOrder".
~~~

This snippet illustrates the mechanism, not a program that cleans up the outer scope; in real usage, the outer scope must still be cleaned up according to its lifecycle. If the key might already exist, use **save/restore** as in section 6 or snapshot the whole map.

| Need | Suitable solution |
| --- | --- |
| Set a new key and remove it when the scope ends | **putCloseable** |
| Manually manage a simple key | **put + try/finally + remove** |
| Override an existing key and restore the old value | **MDC.get beforehand + MDC.put/remove in finally** |
| Change multiple keys and restore everything | **getCopyOfContextMap + setContextMap** |
| Boundary owning the entire MDC after a request | **clear in finally** per policy |

## 8. Snapshotting and Restoring the Entire Map

When a scope modifies multiple keys or needs to pass context to a worker, a well-controlled approach is to save a snapshot:

~~~java
Map<String, String> previous = MDC.getCopyOfContextMap();

try {
    MDC.put("operation", "createOrder");
    MDC.put("attempt", "2");
    doWork();
} finally {
    if (previous == null) {
        MDC.clear();
    } else {
        MDC.setContextMap(previous);
    }
}
~~~

This is an illustrative snippet requiring the **java.util.Map** import and appropriate variables/methods.

**MDC.getCopyOfContextMap()** returns a **copy**, which may be null if no context exists yet. **MDC.setContextMap(map)** clears the current map and populates it with entries from the snapshot; it does not merge.

Therefore:
- You need to know which keys the scope intends to **restore**.
- If previous is null, calling clear is a clear handling approach compatible across versions and providers.
- If previous has data, setContextMap(previous) restores the saved key/value set.
- In nested scopes, ensure a method does not unexpectedly alter the caller's state outside its contract.

**Do not use MDC.setContextMap(null) as a portable pattern** if the project might run on SLF4J 1.x or another provider; null argument support is documented for SLF4J 2.0.0 and later. Using the null → clear branch makes the intent clearer.

### When is snapshotting unsuitable?

If multiple layers of code modify MDC without an ownership convention, restoring the entire map can **erase new fields** intentionally added by a child layer that need to persist after the call. Therefore, snapshot/restore should accompany well-defined scopes, not replace lifecycle design.

### 9.4. src/main/java/demo/MdcCleanupDemo.java

~~~java
package demo;

import java.util.Map;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;

public final class MdcCleanupDemo {
    private static final Logger LOG =
            LoggerFactory.getLogger(MdcCleanupDemo.class);

    public static void main(String[] args) {
        // Demo initializes at a boundary it owns.
        MDC.clear();
        MDC.put("request_id", "req-42");

        try {
            LOG.info("REQUEST_STARTED");

            MDC.put("operation", "createOrder");
            try {
                LOG.info("OPERATION_STARTED");

                // Child scope overrides: must save previous value.
                String previous = MDC.get("operation");
                MDC.put("operation", "reserveStock");

                try {
                    LOG.info("STOCK_RESERVED");
                } finally {
                    if (previous == null) {
                        MDC.remove("operation");
                    } else {
                        MDC.put("operation", previous);
                    }
                }

                LOG.info("OPERATION_RESUMED");
            } finally {
                // Only operation ends here.
                MDC.remove("operation");
            }

            LOG.info("REQUEST_AFTER_OPERATION");
        } finally {
            // End of request: clear the entire context
            // managed by this demo boundary.
            MDC.clear();
        }

        LOG.info("AFTER_REQUEST");

        Map<String, String> after = MDC.getCopyOfContextMap();
        System.out.println(
                "MDC_EMPTY=" + (after == null || after.isEmpty()));
    }
}
~~~

### 9.6. Output analysis

1. **REQUEST_STARTED** has request_id but no operation yet.
2. **OPERATION_STARTED** has operation=createOrder.
3. The reserveStock scope overrides operation; **STOCK_RESERVED** carries operation=reserveStock.
4. The child scope's finally block **restores** createOrder; **OPERATION_RESUMED** proves this.
5. The operation scope's finally block calls **MDC.remove("operation")**; **REQUEST_AFTER_OPERATION** retains request_id while operation is empty.

8. There is no need to create a new Logger per request; Logger is a shared category, while MDC changes per scope.

**Key point:** The demo does not clear MDC after **every LOG.info call**. The context is kept for an appropriate unit of work and cleaned up when the **scope** ends.

## 10. Using putCloseable in the Right Place

Another snippet, when the **attempt** key **does not yet exist** in the caller:

~~~java
try (MDC.MDCCloseable ignored =
             MDC.putCloseable("attempt", "2")) {
    LOG.info("PAYMENT_ATTEMPT_STARTED");
}

// Out of scope: attempt has been removed.
~~~

This is an illustrative snippet inside a class that has Logger LOG. For **putCloseable** to work, the provider must support MDC as expected.

If **attempt=1** already existed outside, this example with attempt=2 will cause **attempt to be removed** after close instead of restoring 1. Use save/restore to preserve the parent value.

Do not overuse **MDC.clear()** right after putCloseable: close is already responsible for removing the key it manages, whereas clear can wipe out the caller's request_id/trace_id.

## 11. Thread Pools: Why Cleanup Is Especially Critical

Web servers and ExecutorService use **thread pools**, where a single thread processes multiple tasks over time:

~~~text
Thread worker-1
  |
  +-- Request A: MDC request_id=A
  |   |
  |   +-- Process / log
  |   +-- FINALLY: remove or clear
  |
  +-- Request B: MDC request_id=B
      |
      +-- Process / log
      +-- FINALLY: remove or clear
~~~

If A does not clean up MDC, B may inherit request_id=A because the thread is reused.

### Leak-prone code example

~~~java
public void handleMessage(Message message) {
    MDC.put("message_id", message.id());
    process(message);

    // If process throws an exception, cleanup will not run.
    MDC.remove("message_id");
}
~~~

This is **illustrative code**, not standalone Java. It demonstrates a control-flow bug: cleanup is placed after logic that can throw an exception.

### Fixing with finally

~~~java
public void handleMessage(Message message) {
    MDC.put("message_id", message.id());
    try {
        process(message);
    } finally {
        MDC.remove("message_id");
    }
}
~~~

If the system has other context from middleware, remove only message_id owned by this method. If this is a boundary managing all context, clear can be used, but verify it does not discard caller context.

## 12. Context Propagation to ExecutorService

**Properly clearing MDC on the main/request thread does not automatically ensure worker threads are cleaned up properly.** When submitting a task to an ExecutorService, MDC is generally not propagated automatically.

Capture → install → restore pattern:

~~~java
Map<String, String> captured = MDC.getCopyOfContextMap();

Future<?> task = executor.submit(() -> {
    Map<String, String> oldWorkerContext =
            MDC.getCopyOfContextMap();

    try {
        if (captured == null) {
            MDC.clear();
        } else {
            MDC.setContextMap(captured);
        }

        performTask();
    } finally {
        if (oldWorkerContext == null) {
            MDC.clear();
        } else {
            MDC.setContextMap(oldWorkerContext);
        }
    }
});

task.get();
~~~

This is an **illustrative snippet**, requiring Map/Future imports, an executor and performTask, and exception handling for task.get().

Explanation:
- **captured** is taken on the submitting thread **before** the source context goes out of scope.
- The worker saves **oldWorkerContext** so it does not corrupt any pre-existing state.
- **setContextMap(captured)** establishes the context for the duration of the worker's task execution.
- **finally** clears or restores the worker's map.
- **task.get()** is only used if the caller wants to wait for task completion; it is not a condition for cleanup to run in the worker.

**Do not just set MDC on the source thread and assume the worker will see it.** For Logback MDC, the documentation notes that child threads do not automatically receive a copy of MDC in many scenarios; thread pools require controlled propagation even more.

**Do not put MDC into a shared static variable to “pass it to another thread”.** Doing so can cause race conditions between requests. Use an Executor wrapper, task decorator, or official framework context propagation when available in the project.

### CompletableFuture cases

CompletableFuture tasks may execute on a different executor than the current thread. To supply MDC to each task, propagation must be applied at the corresponding boundary. An MDC value on the main thread does not become a “global context” for all callbacks.

### Reactive / virtual thread cases

Work movement across threads in reactive pipelines and the virtual thread model require separate evaluation. Do not rely on the assumption that an entire request always runs on a single carrier thread or that a ThreadLocal propagates properly across every operator. Use the framework's official context API or instrumentation and test cleanup under cancellation/error.

## 13. Cleaning Up MDC on Exceptions, Timeouts, and Cancellation

A request can terminate abnormally due to:
- Validation errors.
- IOException or dependency failures.
- Timeouts.
- Cancellation.
- Early returns.
- Client disconnection.
- Unchecked exceptions.

**try/finally** handles most synchronous exit paths where Java can execute the finally block. For asynchronous tasks, cleanup must reside in the **executing task's scope**, not only at the submission site.

Example:

~~~java
MDC.put("operation", "authorize");
try {
    if (isCached()) {
        return cachedResult();
    }

    return authorizePayment();
} finally {
    MDC.remove("operation");
}
~~~

This is a snippet inside a method with an appropriate return type and defined variables and methods. Whether returning from the cache branch or the authorize branch, finally still runs.

However, scenarios such as **JVM termination (kill), process crash, or sudden system shutdown** do not guarantee that finally has run. Logging context cleanup is a technique to prevent leaks **while the JVM continues executing**, not a durability guarantee after a crash.

When a task is interrupted, do not swallow **InterruptedException** arbitrarily; cleanup must still occur via finally as control flow exits the scope.

## 14. MDC.remove and MDC.clear Do Not Delete Already-Logged Records

Suppose:

~~~text
T0: MDC request_id=req-42
T1: Logger creates event E1
T2: Event E1 is placed into the async logging queue
T3: Request ends, MDC.clear()
T4: Async appender writes E1 to file
~~~

In backends that capture context when creating a logging event, E1 can still be emitted with **request_id=req-42** at T4. This is desired behavior so that an event preserves its accurate source context.

Therefore:
- **MDC.clear()** only cleans up the current context via the adapter; **it does not modify already-emitted events**.
- It does not delete logs from files, collectors, archives, or dashboards.
- It is not a tool for erasing previously stored personal data.
- In a custom async Handler/Appender, snapshot the context at event creation time rather than reading the file-writing worker's ThreadLocal after the request has already ended.

If you need to remove a sensitive field from an already-written pipeline, it must be handled through the storage system's **redaction, retention, data deletion, and access control** policies; MDC cleanup does not replace them.

## 15. Log4j 2 ThreadContext: Equivalent Operations

If the application uses the **Log4j 2 API** directly, the corresponding mechanism is **org.apache.logging.log4j.ThreadContext**.

| SLF4J MDC | Log4j 2 ThreadContext | Meaning |
| --- | --- | --- |
| MDC.put(key,value) | ThreadContext.put(key,value) | Set context map entry |
| MDC.get(key) | ThreadContext.get(key) | Read key |
| MDC.remove(key) | ThreadContext.remove(key) | Remove a single key |
| MDC.clear() | ThreadContext.clearMap() | Clear context map |
| No direct map-only API pair | ThreadContext.clearAll() | Clear both context map **and stack** |

Example:

~~~java
import org.apache.logging.log4j.ThreadContext;

ThreadContext.put("request_id", requestId);
try {
    processRequest();
} finally {
    ThreadContext.remove("request_id");
}
~~~

This is illustrative code requiring the Log4j 2 dependency. **clearMap()** differs from **clearAll()**: Log4j 2 has both a **Context Map** and a **Context Stack**, so clearAll clears both.

**Do not mix SLF4J MDC and Log4j 2 ThreadContext in the same project without understanding the provider/bridge.** Depending on the logging stack, they may or may not share context through an adapter. Check actual output and the documentation for the version in use.

When using Spring Boot or a framework that manages logging, use the API/context propagation supported by that system rather than manually adding multiple providers or bidirectional bridges.

## 16. How to Verify That MDC Is Actually Removed

When testing, do not just inspect logs by eye. You can assert the state:

~~~java
MDC.put("request_id", "req-42");
MDC.put("operation", "createOrder");

MDC.remove("operation");

if (MDC.get("operation") != null) {
    throw new AssertionError("operation must be removed");
}
if (!"req-42".equals(MDC.get("request_id"))) {
    throw new AssertionError("request_id must remain");
}

MDC.clear();

Map<String, String> after = MDC.getCopyOfContextMap();
if (after != null && !after.isEmpty()) {
    throw new AssertionError("MDC must be empty");
}
~~~

This is an illustrative snippet in a method with appropriate **Map** and **MDC** imports. It verifies:
1. remove(operation) does not accidentally delete request_id.
2. clear() leaves the current context empty.

However, **testing state on the current thread** is not enough to catch all leaks in a thread pool. Integration tests with real tasks and a real logging backend are needed.

### Testing for leaks between two requests

- Run request A with request_id=A.
- Finish A, including an exception branch.
- Have the same worker thread process B with request_id=B or no ID.
- Ensure B does not output A in its logs.
- Repeat with multiple concurrent tasks, timeouts, or cancellations.
- Verify logs from asynchronous callbacks still carry the correct context.
- Verify the parent scope does not lose trace_id after a nested scope ends.

### Backend integration tests

- Configure **%X{request_id}** or a JSON encoder that includes MDC.
- Emit logs inside and outside the scope.
- Parse the output; verify the ID is present inside the scope and absent outside it.
- Do not merely assert **MDC.get(...) == null** while ignoring that the layout might be reading from a different context source.

## 17. Managing MDC in Request Filters and Interceptors

An HTTP filter/middleware is usually the right place to set request context once:

~~~java
String previous = MDC.get("request_id");

MDC.put("request_id", validatedRequestId);
try {
    continueFilterChain();
} finally {
    if (previous == null) {
        MDC.remove("request_id");
    } else {
        MDC.put("request_id", previous);
    }
}
~~~

This is **Java-style pseudocode** inside a filter that already has **validatedRequestId** and **continueFilterChain()**; it is not a standalone servlet class.

The **save/restore** pattern protects pre-existing context from outer layers. If this filter is the sole boundary owning the entire MDC, stronger cleanup can be designed, but it must align with tracing, security, and the framework.

### With asynchronous requests

In many web frameworks, returning control from a request handler does not mean all asynchronous work has finished. When a task executes on another thread:
- Propagate the necessary context to the task.
- Set the context in the appropriate worker scope.
- Clean up in the worker's finally block.
- Do not retain request A's context on the thread processing task B.
- Do not put secrets or raw requests into MDC for “easier tracking”.

Specific mechanisms for Spring Boot, servlet async, Reactor, or tracing instrumentation vary by framework/version; verify empirically rather than applying a single ThreadLocal wrapper across every model.

## 18. Null Values, Invalid Keys, and Different Providers

A few edge cases to keep in mind:

### Null keys

SLF4J MDC APIs require **non-null keys** for put/get/remove. Do not call **MDC.remove(null)** as a way to “clear everything”; use **MDC.clear()** for the entire map.

### Null values

SLF4J notes that whether **MDC.put(key, null)** is supported depends on the adapter/backend. Do not use null as a portable convention to delete a key. **MDC.remove(key)** expresses the intent accurately and is less ambiguous.

### Providers without real MDC support

Some SLF4J providers may use **NOPMDCAdapter**, so put/get/remove do not retain context like Logback does. Do not run an example with slf4j-simple and assume Logback will behave the same way.

To test MDC, use a **provider with real MDC support**, such as the Logback configuration in section 9, and check the layout. If the Maven dependency graph contains multiple SLF4J providers, resolve the conflict instead of relying on whichever provider happens to be picked.

### Should all context be cleared at application shutdown?

Do not treat shutdown as a request cleanup mechanism. Request context must be cleaned up **as soon as the scope ends** because threads can be reused throughout the process's lifetime. Clearing at shutdown is far too late to prevent cross-request leakage.

## 19. Security and Privacy When Cleaning Up MDC

MDC often contains fields repeated across **many logs** of the same request, so security mistakes can amplify widely.

**Do not put the following types of data into MDC:**
- Passwords, access/refresh tokens, API keys, private keys.
- Session cookies, Authorization headers.
- Raw request/response bodies.
- Sensitive payment data.
- Personal data unnecessary for diagnostics.
- Mutable references to large business objects.

Instead, you can choose:
- Valid and permitted request_id/trace_id.
- operation, event_code, outcome.
- Approved tenant_id or internal codes that do not expose secrets.
- release, service, environment at the appropriate configuration layer.

### Proper cleanup is also a security requirement

If request A of tenant X leaves **tenant_id=X** in MDC and the worker thread handles request B of tenant Y, B's logs may be misattributed to X. This affects both operational analytics and data isolation.

**MDC.clear() after a request finishes does not make already-written data disappear.** Log access control, retention, redaction, and data deletion workflows must still be enforced in the storage system.

## 20. Context Cardinality and Cost

MDC enriches logs with request_id, trace_id, and operation. Fields have different **cardinality**:

- **level, operation, service:** usually have a relatively small set of values.
- **request_id, trace_id, order_id:** can differ on almost every request.
- **raw_url, exception_message:** vary widely and may contain data that should not be stored.

**High cardinality does not mean request_id should be omitted from logs**; this ID is very useful for finding requests. However, do not use request_id as a metric label for every time series. Nor should every field be indexed unconditionally in the collector.

Proper cleanup does not by itself reduce the size of valid events, but it avoids **attaching stale context** to unrelated events. Beyond cleanup, manage log volume, DEBUG/TRACE levels, and retention.

## 21. When to Remove a Key, When to Restore, When to Clear?

Quick decision table:

| Scenario | Choice |
| --- | --- |
| Method adds a key that did not exist and owns that key | remove(key) in finally |
| Scope needs automatic cleanup of a new key via try-with-resources | putCloseable |
| Child scope overrides an existing caller key | Save old value; put back or remove in finally |
| Child scope changes multiple caller fields | Snapshot getCopyOfContextMap and restore map |
| Request/job boundary owns the entire map | clear() in finally per contract |
| Worker thread receives context from submitter | Capture → install → restore/clear at worker boundary |
| Need to remove context from an event already written to file/collector | MDC cannot handle this; use storage/deletion policies |
| Using Log4j 2 API directly | ThreadContext.remove/clearMap/clearAll per scope to clean |

**There is no single cleanup call that is right in every situation.** Questions to ask before removing: “Which scope does this key belong to? Which keys do I have the right to remove? Does the caller have a value that needs to be restored?”

## 22. Common Mistakes

| Mistake | Consequence | Fix |
| --- | --- | --- |
| Calling remove after logic without finally | Exceptions skip cleanup | Use try/finally |
| Calling clear inside a helper | Loses caller's request_id/trace_id | Remove only keys you own |
| Assuming remove restores the old value | Parent scope loses operation | Save and restore the value |
| Assuming putCloseable auto-restores overwritten keys | Key is deleted on close | Use only for new keys or restore manually |
| Using MDC.put(key,null) to delete | Behavior depends on backend | Use remove(key) |
| Calling remove(null) to clear everything | Null key is invalid | Use clear() if permitted |
| Cleaning MDC on submitter thread, not worker | Thread pool may retain stale context | Use finally in the worker |
| Assuming context auto-propagates across CompletableFuture | Worker logs lack request ID | Propagate explicitly |
| Using a static currentRequestId variable | Race conditions | Scoped MDC/context |
| Forgetting to restore the previous map | Child scope corrupts caller state | Snapshot/restore |
| Passing entire MDC across trust boundaries | Risk of leaking metadata | Allowlist permitted fields |
| Using a non-MDC provider and seeing tests PASS | No real context output | Verify provider and layout |
| Checking only MDC.get without inspecting output | Output may omit the key | Integration tests |
| Treating clear as “deleting written logs” | Data still exists in collector | Retention/redaction policies |
| Putting tokens in MDC | Tokens appear across many lines | Never collect secrets in the first place |
| Cleaning up only at shutdown | Thread pool leaks between requests | Clean up as soon as the scope ends |

## 23. Production Checklist

1. **Define ownership:** Which middleware sets request_id, which tracing sets trace_id, which service sets operation?
2. **Use finally:** Every normal exit path cleans up on time.
3. **Do not over-clear:** Helpers clean up only fields they own.
4. **Nested scopes:** Restore values before overriding.
5. **putCloseable:** Understand that close only removes the key, without restoring the old value.
6. **Thread pools:** Test requests A/B running on the same worker after reuse.
7. **Async:** Capture, install, and restore context on the executing thread.
8. **Exceptions:** Verify cleanup on exceptions, timeouts, and early returns.
9. **Backend:** Verify Logback/Log4j 2/SLF4J provider and layout actually output MDC.
10. **Events:** Asynchronous logging must preserve context captured at event creation.
11. **Security:** Do not put tokens/passwords/secrets into MDC.
12. **Tracing:** Use trace_id/span_id from the tracing system, not randomly self-generated ones.
13. **Collector:** Verify fields after ingestion, not just by reading MDC state.
14. **Resources:** Manage cardinality, indexing, retention, and log volume.
15. **Regression testing:** Add cleanup tests when modifying filters, interceptors, or executors.

## 24. Self-Check Questions

**1. How does MDC.remove("operation") differ from MDC.clear()?**  
remove deletes only operation; clear deletes all key/value pairs in the current MDC map.

**2. Why must cleanup be placed in finally?**  
So that exceptions, early returns, or other control-flow branches do not bypass context cleanup.

**3. If operation was previously createOrder, and we put operation=reserveStock and then remove it, what is the result?**  
operation is no longer in MDC. It **does not** automatically revert to createOrder.

**4. Does putCloseable restore the old value when a key is overwritten?**  
No. close deletes the key; it does not save the previous value to restore it.

**5. When a child scope owns only one key, should it call clear on the whole map?**  
Generally no, because it can wipe out the parent scope's request_id and trace_id.

**6. Why does MDC easily leak with thread pools?**  
Because threads are reused; stale context can remain if the previous request did not clean up.

**7. Is clearing MDC on the submitting thread sufficient for ExecutorService?**  
No. The worker thread needs its own cleanup/restoration after the task runs.

**8. After MDC.clear(), can an event already in an async queue still have request_id?**  
Possibly yes, if the backend captured the context when creating the event; clear does not modify already-created events.

**9. What corresponding removal APIs do SLF4J MDC and Log4j 2 ThreadContext have?**  
MDC.remove corresponds to ThreadContext.remove; MDC.clear is similar to ThreadContext.clearMap for the map. Log4j 2 clearAll also clears the stack.

**10. Should Authorization headers or access tokens be placed in MDC for easier debugging?**  
No. MDC can appear across many events, increasing the risk of leaking secrets.
