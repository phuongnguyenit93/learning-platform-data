# Escaping Input Data When Logging in Java

## 1. Lesson Objectives

**Escaping input data in logging** means converting characters that have special meaning for the **target log format** into a safe representation, so that untrusted values cannot forge records, break structure, confuse analysis systems, or mislead log readers.

For example, if a client-supplied username contains newline characters (CR/LF), a text logging statement can inadvertently create an extra line that looks like a system ERROR message. In that case, an attacker does not necessarily need file write permissions: they only need to control **a single value that the application writes into the log**.

After this lesson, you will be able to:

- Identify **log injection / log forging** and untrusted data sources.
- Distinguish between **validation**, **sanitization**, **output escaping/encoding**, **redaction**, and **structured logging**.
- Understand why using placeholders in SLF4J/Log4j2 is good practice, yet **insufficient** to prevent CRLF injection.
- Write a **standalone Java 17** example using JUL that demonstrates a forged log line and how to turn data into a safe single line.
- Choose an escaping strategy appropriate for text logs, CSV/TSV, JSON, and log viewing UIs.
- Test Unicode control characters, long strings, personal data, MDC/trace context, and multi-stage log output pipelines.

## 2. Root Problem: External Data Becomes Log Syntax

Consider the intended log line:

~~~text
WARNING Authentication rejected for user=alice
~~~

The application allows clients to provide a username. If a client sends a string containing the two control characters **CR** (carriage return, U+000D) and **LF** (line feed, U+000A), along with content that looks like a system message, the raw log can turn into:

~~~text
WARNING Authentication rejected for user=alice
ERROR authentication granted user="root"
~~~

A single rejected login event is now displayed as **two lines**. The second line was not produced by the application granting access; it is purely attacker-controlled content. Yet an operator or a line-based parser may mistake it for an independent event.

**Problem name:** **log forging / log injection**, commonly classified under **CWE-117: Improper Output Neutralization for Logs**. This attack can compromise the integrity of observability data, mislead investigations, cover tracks, or cause parser failures.

### 2.1. Four Components of a Log Event

An event may consist of:

~~~text
timestamp | severity | logger | event_type | user_input | request_id
~~~

Where:

- **timestamp, severity, logger, event_type** should come from the logging system or a controlled event structure.
- **user_input** is typically external data: username, user-agent, headers, URL, form fields, message body.
- **request_id / trace_id** also sometimes come from untrusted headers; just calling something “metadata” does not make it safe.

If the entire string is concatenated into text without encoding rules, external values can **escape the boundary of a field**, inject delimiters, or create new lines.

### 2.2. Escaping Does Not Mean Banning All Newlines

A genuine multi-line stack trace is normal. Application-defined log messages may also need to preserve multi-line structure in some cases. The goal of escaping is to **protect record and field boundaries**; it does not necessarily mean stripping all control characters from all original data.

For example, a JSON event can preserve content containing newlines as a **validly encoded JSON string**, whereas a text log that defines each line as one event should convert newlines in **input data** into visible representations (such as a backslash + n).

## 3. Which Inputs Must Be Treated as Untrusted?

A practical rule: **any value not generated by the application itself under a strict contract may carry control characters or special delimiters**.

| Source | Examples | Why control is needed? |
| --- | --- | --- |
| HTTP query / form / JSON body | username, search term, address, comment | Clients can inject newlines, quotes, delimiters, or very long payloads. |
| HTTP header | User-Agent, Referer, X-Request-ID | Some headers are client-controlled; proxies may modify them but do not make all values trustworthy. |
| URL and request path | encoded path, query string | May contain percent-encoded sequences and multiple decoding layers. |
| Database record | display name, notes from DB | Data already stored **does not mean it is safe for logging**; stored log injection is possible. |
| Message queue / webhook | payload, correlation ID | External producers or upstream services may be buggy or compromised. |
| Exception message | SDK/DB/HTTP client error messages | May echo back URLs, hostnames, user input, or sensitive information. |
| MDC / ThreadContext | userId, tenantId, requestId, traceId | When populated from requests or headers, they still must be validated/encoded; context does not sanitize itself. |
| File name/path | upload filename, object key | May contain control characters or strings resembling log headers. |
| Values from external config | tenant label, endpoint, service name | May be malformed; requires contracts and edit access controls. |

**Trust boundaries** can appear multiple times. For instance, a client sends a request ID header, the application copies it into MDC, Logback formats it as text, and a collector parses it into JSON. Without proper validation/encoding, a special character can break structure at **any layer that interprets it as syntax**.

Do not assume every value passing through a framework is already escaped. An HTTP framework parsing a request does not mean it has normalized messages to be safe for every logging layout.

## 4. Character Types to Watch Out For

### 4.1. CR/LF: The Classic Threat for Single-Line Logs

- **CR**, symbol CR or U+000D: moves the cursor back to the start of the line in many environments.
- **LF**, symbol LF or U+000A: line feed.
- **CRLF**, two consecutive characters: commonly used as a line ending in many protocols and systems.

If a log consumer treats each line as one event, input containing raw CR/LF can split the event. The typical transformation for a single-line text format is:

~~~text
Original data:   alice + CR + LF + ERROR fake
Logged data:     alice\r\nERROR fake
~~~

On the second line, **\r** and **\n** are visible characters consisting of a backslash and a letter, **not actual CR and LF**. The text line remains a single record.

### 4.2. Tabs and Delimiters

If logs use **|**, commas, tabs, equals signs, or quotes to separate fields, input containing those characters can cause a parser to misinterpret the number of columns or field values.

Example of a custom format:

~~~text
event=login|user=alice|outcome=DENIED
~~~

Client-supplied user input containing an extra pipe character and an outcome string can cause a naive parser to produce another field:

~~~text
event=login|user=alice|outcome=APPROVED|outcome=DENIED
~~~

Even without CRLF, this is still **field injection**. To keep this format, you must have an encoding/delimiting mechanism **understood by the parser**, or use structured logging instead of manual string concatenation.

Putting double quotes around the user value is only safe if there are rules for escaping quotes, backslashes, and record separators, and the parser follows those exact rules. You cannot take JSON escaping and assume it works as CSV escaping or pipe-delimited formatting.

### 4.3. Terminal Escapes and Unicode Control Characters

Some data may contain:

- **TAB**, **NUL**, **ESC**, and C0/C1 control characters.
- **U+0085** (next line), **U+2028** (line separator), **U+2029** (paragraph separator).
- **ANSI escape sequences** starting with ESC, which can cause terminals to colorize text, move the cursor, or clear the display.
- **Bidirectional formatting controls** such as U+202E and characters in the directional embedding/isolate group, which can make readers see characters in a different order from how they are stored in data.
- Extremely long strings or unusual Unicode characters that hit limits or cause inconsistent handling in collectors/renderers.

Not every special Unicode character is dangerous in every format. However, for **single-line text logs** and terminals/dashboards, you must account for them when defining boundaries, encoding, and UI rendering. For standardized ID fields (such as traceId), you should **validate against a specific grammar**, not merely escape.

## 5. Distinguishing Validation, Escaping, Sanitization, and Redaction

| Technique | Purpose | Example |
| --- | --- | --- |
| **Input validation** | Determines whether data conforms to the allowed domain. | Request ID consists only of letters, digits, hyphens, and has a length limit; traceId has the exact number of hex characters. |
| **Output escaping/encoding** | Ensures data remains **data** in the output format. | Newline in text → visible string \\n; string in JSON → valid JSON string. |
| **Sanitization** | Cleans/transforms according to policy, which may lose information. | Strips control characters if the field is not allowed to contain them. |
| **Redaction / masking** | Prevents unintended storage of sensitive data. | Do not log passwords or access tokens; replace with [REDACTED] when needed. |
| **Truncation / size limit** | Bounds resources and payload size. | Caps field size and adds a truncated indicator. |
| **Structured logging** | Keeps fields separate and lets an encoder generate the target syntax. | JSON object with event, username, outcome. |

These techniques **complement one another**; they do not replace one another.

- Alphanumeric-only validation fits **traceId**, but should not be mechanically applied to multilingual usernames.
- Escaping CRLF alone does not handle tokens/passwords or dangerous HTML content when rendered in a browser.
- Redacting sensitive data alone does not prevent newlines inside a valid username.
- Converting to a JSON string alone does not control multi-megabyte payloads or secret contents.
- Logging with placeholders alone does not change how a text layout outputs lines.

A manageable processing order is:

~~~text
Data from untrusted source
       │
       ▼
Validate type, syntax, and contract limits
       │
       ▼
Select fields truly needed for logging (data minimization)
       │
       ▼
Redact/mask sensitive data
       │
       ▼
Structured event / constant message template
       │
       ▼
Encode for the sink format using a trusted encoder
       │
       ▼
Collector, index, and viewer with their own checks
~~~

**Do not JSON-encode at input and then pass that JSON-encoded string into a JSON encoder a second time** unless the system intentionally stores an *escaped string*. Double escaping alters data and makes querying difficult. Store and pass values in their original data types, and encode only at **the serialization boundary for the specific format**.

## 6. Standalone Java 17 Example: Log Forging and Single-Line Escaping

This program uses **java.util.logging** (JUL), built into JDK 17. To make stdout easy to verify, we use a demo **Handler** that writes directly to stdout and a **Formatter** that processes every text message before output. The first part demonstrates **unsafe output**, and the second part uses the formatter to keep the event on one line.

The **escapeOneLine** method follows an illustrative policy:

1. CR, LF, TAB, backslash, and double quote are represented with readable escape sequences.
2. Other control characters, U+2028/U+2029, certain directional controls, and unpaired surrogates are represented as **\\uXXXX**.
3. Remaining Unicode text characters are preserved, avoiding corruption of Vietnamese diacritics.
4. The logger uses a **constant template** and separate parameters instead of using input as the template.

Name the file **SecureLoggingDemo.java**:

~~~java
import java.util.Locale;
import java.util.logging.Formatter;
import java.util.logging.Handler;
import java.util.logging.Level;
import java.util.logging.LogRecord;
import java.util.logging.Logger;

public final class SecureLoggingDemo {

    private static String escapeOneLine(String value) {
        StringBuilder out = new StringBuilder(value.length());
        for (int i = 0; i < value.length();) {
            int cp = value.codePointAt(i);
            i += Character.charCount(cp);

            switch (cp) {
                case '\r' -> out.append("\\r");
                case '\n' -> out.append("\\n");
                case '\t' -> out.append("\\t");
                case '\\' -> out.append("\\\\");
                case '"' -> out.append("\\\"");
                default -> {
                    boolean unsafeControl = Character.isISOControl(cp)
                            || cp == 0x2028 || cp == 0x2029
                            || (cp >= 0x202A && cp <= 0x202E)
                            || (cp >= 0x2066 && cp <= 0x2069)
                            || (cp >= 0xD800 && cp <= 0xDFFF);
                    if (unsafeControl) {
                        out.append(String.format(Locale.ROOT, "\\u%04X", cp));
                    } else {
                        out.appendCodePoint(cp);
                    }
                }
            }
        }
        return out.toString();
    }

    private static Handler safeStdoutHandler() {
        Handler handler = new Handler() {
            @Override
            public void publish(LogRecord record) {
                if (!isLoggable(record)) {
                    return;
                }
                System.out.print(getFormatter().format(record));
            }

            @Override
            public void flush() {
                System.out.flush();
            }

            @Override
            public void close() {
                flush();
            }
        };

        handler.setLevel(Level.ALL);
        handler.setFormatter(new Formatter() {
            @Override
            public String format(LogRecord record) {
                // formatMessage applies JUL template/parameters.
                String body = formatMessage(record);
                return record.getLevel().getName() + " "
                        + escapeOneLine(body)
                        + System.lineSeparator();
            }
        });
        return handler;
    }

    public static void main(String[] args) {
        String userInput =
                "alice\r\nERROR authentication granted user=\"root\"";

        // Only to demonstrate the harm: concatenate raw string and print to terminal.
        System.out.println("RAW:");
        System.out.println(
                "WARNING Authentication rejected for user=" + userInput);

        Logger logger = Logger.getLogger("demo.auth");
        logger.setUseParentHandlers(false);
        logger.setLevel(Level.ALL);

        Handler handler = safeStdoutHandler();
        logger.addHandler(handler);
        try {
            System.out.println("SAFE:");
            logger.log(Level.WARNING,
                    "Authentication rejected for user={0}", userInput);
        } finally {
            logger.removeHandler(handler);
            handler.close();
        }
    }
}
~~~

Compile and run with no dependencies outside the JDK:

~~~bash
javac SecureLoggingDemo.java
java SecureLoggingDemo
~~~

**Expected stdout**:

~~~text
RAW:
WARNING Authentication rejected for user=alice
ERROR authentication granted user="root"
SAFE:
WARNING Authentication rejected for user=alice\r\nERROR authentication granted user=\"root\"
~~~

In the **RAW** section, the actual CR/LF characters cause the reader to see two lines. In the **SAFE** section, the CR/LF characters are converted into the visible string **\\r\\n**, and quotes in the data become **\\"**. The result is only **one physical log line** for the WARNING event (aside from the SAFE label). The forged ERROR line no longer appears as an independent record.

Some terminals behave slightly differently with a raw CR character; the key point is that CR/LF can split or overwrite how a line is displayed. The output above shows the line-by-line representation under normal viewing.

### Why Does This Code Run and Produce Deterministic Output?

- The program uses only **java.util.logging** and **java.lang** classes from JDK 17.
- JUL **logger.log(Level, String, Object)** accepts parameters separately. **Formatter.formatMessage** applies the template containing **{0}** before passing it through **escapeOneLine**.
- A dedicated handler is attached, and **setUseParentHandlers(false)** prevents records from propagating to the root logger's default ConsoleHandler, avoiding extra console lines.
- The formatter does not include timestamps or thread names, so stdout does not depend on time or locale.
- The demo runs synchronously on a single thread; there are no ordering races.
- The escape function does not split valid surrogate pairs and does not strip normal Vietnamese diacritics.
- **safeStdoutHandler** is for demonstration only. In production, you should not write a minimal custom handler like this: it lacks concurrency policies, batching, retries, error handling, memory bounds, and useful metadata.

### What Does the Demo Not Guarantee?

The **escapeOneLine** function is suitable for **single-line text messages written to stdout**. It is not a universal sanitizer:

- If you put the result into a **JSON string**, you must use a JSON encoder; manually inserting text-syntax escapes and then JSON-encoding again causes double escaping.
- If you display the result in an **HTML dashboard**, you must render it via a text node or HTML-escape it at the UI layer. HTML characters such as less-than/greater-than signs in text logs are not encoded by this function.
- If the log format uses **|** or CSV delimiters, you must define escaping specific to that field grammar.
- If logs contain **valid multi-line stack traces**, you need a dedicated event framing convention rather than forcing error semantics to be stripped.
- The demo has no length limit. Production systems must bound input/log events to avoid exhausting RAM/disk.

## 7. Using SLF4J and Logback Properly

In Java projects already using **SLF4J**, the common pattern is:

~~~java
// Illustrative: requires SLF4J API, provider, and classes/variables in the application.
logger.warn("Login rejected for user {}", userInput);
~~~

**This is better than direct string concatenation** because the message template is a constant, and the framework can defer formatting and optimize when that log level is disabled. However, **the userInput parameter can still contain CR/LF**. If the backend formats with a text pattern like **%msg%n** without escaping, log forging can still occur.

Risky pattern:

~~~java
// BAD: using input to build part of the format/template.
logger.warn("Login rejected for " + userInput + " with role {}",
        role);
~~~

A better approach is to keep the template constant and put all external data into parameters/structured fields:

~~~java
// Prefer: message template is not determined by the user.
logger.warn("Login rejected for user {} with role {}",
        userInput, role);
~~~

**You still must configure the encoder/layout properly.** Placeholders solve many API and template issues, but they do not automatically perform output encoding for text logs.

### 7.1. With Plain-Text Logback

A common pattern configuration:

~~~xml
<encoder>
    <pattern>%d{ISO8601} %-5level %logger - %msg%n</pattern>
</encoder>
~~~

This pattern **does not by itself guarantee** that input inside the message has CRLF neutralized. If compatibility with single-line text logs is required:

- Prefer a **proven encoder** that supports escaping untrusted fields.
- Or establish a **central formatting policy** aligned with the target grammar (for example, a tested custom converter/formatter), rather than having each module call ad-hoc replace methods.
- Test messages, MDC, markers, exception messages, and every field included in the pattern.
- Verify logs **in the output file/stdout after the encoder runs** and **after the collector**, not just the initial Java string.

Do not pick a random regex in configuration and assume it handles all CR, LF, Unicode separators, delimiters, and control characters. Backend replacement mechanisms can be used for specific cases, but they must be scoped and tested against the actual runtime version.

### 7.2. Structured Logging with SLF4J 2.x

SLF4J 2.x supports a fluent API and key-value pairs. An **illustrative example in a project with a compatible logger and backend**:

~~~java
logger.atWarn()
      .addKeyValue("event", "auth.reject")
      .addKeyValue("username", userInput)
      .addKeyValue("outcome", "DENIED")
      .log("Authentication rejected");
~~~

Significance: values are modeled as **fields** rather than squeezed into a single text message. However, the API does not force every backend to output JSON. **You must configure a provider and encoder/layout that actually serializes key-value pairs safely**. If the backend ignores fields or concatenates them into unescaped text, the risk remains.

Do not treat the API as proof that logs are safe; inspect the actual output.

## 8. JSON Structured Logging: The Preferred Solution

OWASP recommends a **structured log format**, such as JSON, instead of arbitrary text formats that are prone to line injection. In a well-designed JSON Lines stream, each physical line is a JSON object; inside each string, newlines must be represented as escape sequences according to JSON rules.

An illustrative event:

~~~json
{
  "event": "auth.reject",
  "severity": "WARN",
  "username": "alice\r\nERROR fake-event",
  "outcome": "DENIED"
}
~~~

This is **multi-line formatted JSON for readability**. When written as **JSON Lines** for a collector, the encoder writes the object on a single physical line:

~~~json
{"event":"auth.reject","severity":"WARN","username":"alice\r\nERROR fake-event","outcome":"DENIED"}
~~~

In the JSON example, **\\r\\n** are escape sequences inside a JSON string. When a JSON parser reads it back, the **username** field value may contain actual CR/LF in memory; however, **the raw JSON line** is not broken into a new record.

**Use a proper JSON serializer/encoder**; do not build JSON manually by concatenation:

~~~java
// BAD: if userInput contains double quotes, backslashes, or newlines,
// the resulting JSON may have invalid syntax and reintroduce log injection.
String badJson = "{\"user\":\"" + userInput + "\"}";
~~~

Example with **Jackson** (illustrative; requires the jackson-databind dependency and proper exception handling):

~~~java
// Illustrative fragment in a project with Jackson dependency.
ObjectMapper mapper = new ObjectMapper();
Map<String, Object> event = Map.of(
        "event", "auth.reject",
        "username", userInput,
        "outcome", "DENIED");
String json = mapper.writeValueAsString(event);
~~~

This Jackson snippet **is not a standalone program**; you must import the classes, have the dependency, and handle JsonProcessingException. A JSON serializer handles quoting and control characters for **string values**, but it does not replace redaction or size limits. If you then pass the **json** variable into a pattern logger with a prefix/suffix, the resulting output line may **no longer be valid JSON Lines**; it is better to use a structured encoder integrated with the logging backend and emit **one event = one object**.

### Backend Configuration Must Be Verified

- **Log4j2**: provides **JSON Template Layout** to produce structured output from templates. Log4j2 documentation recommends it over PatternLayout when structured JSON is needed.
- **Logback**: choose a JSON/structured encoder compatible with the exact versions of Logback, SLF4J, and application frameworks in use; verify that it actually writes fields, exceptions, and MDC with the expected schema.
- **Spring Boot**: structured logging capabilities depend on the Boot version and backend. Do not assume every logging starter outputs JSON by default.
- **JUL**: requires an appropriate formatter/handler or bridge if JSON is desired; the default SimpleFormatter is not JSON Lines.
- **Collector**: must preserve JSON object framing and not parse by naively splitting on commas or quotes.

**Do not treat JSON as a cure-all**: a JSON record can be syntactically valid yet still contain secrets, be truncated, be routed to the wrong tenant, or be rendered unsafely with innerHTML in a web UI.

## 9. Log4j2: Encoding for the Target Output

Log4j2 **Pattern Layout** includes the **enc / encode** converter supporting **HTML, XML, JSON, and CRLF**. For text logs where the immediate goal is to block CR/LF in the message, an example PatternLayout is:

~~~xml
<PatternLayout pattern="%d{ISO8601} %-5level %logger - %enc{%m}{CRLF}%n"/>
~~~

**Meaning:** the **%m** portion has CR/LF converted into visible representations before being appended to the pattern. This is **CRLF encoding for the message**, not protection for the entire event. If the pattern also includes **%X{requestId}**, exceptions, markers, or other untrusted fields, they also need appropriate encoding for the same format.

If you need a **proper JSON object**, Log4j2 documentation recommends **JSON Template Layout** rather than trying to construct JSON out of PatternLayout and multiple %enc converters. Choose the right layout, template, output charset, schema, and pipeline compatibility.

Points to remember:

- **%enc{%m}{CRLF}** does not mean other delimiters, all Unicode controls, or HTML content are handled.
- **JSON** escaping is only appropriate when building a proper JSON string context; inserting it arbitrarily into text logs does not create structured logging.
- Never let user input determine the **pattern**, appender configuration, lookup expression, or logging template.
- Check both **message** and **metadata** from ThreadContext/MDC. An unvalidated request ID can appear in multiple pattern positions.
- Exact converter names and behavior must be verified on the **Log4j2 version** used in your system.

## 10. CSV/TSV and Custom Delimited Formats

Sometimes organizations export logs to CSV, TSV, or delimited text for table ingestion. This is a **different escaping context from JSON**.

### 10.1. CSV

Under common CSV rules:

- Fields containing commas, quotes, or line breaks must be quoted appropriately.
- A double quote inside a quoted field is typically represented as **two double quotes**.
- A valid CSV record can span multiple physical lines if a field contains newlines; therefore **CSV does not inherently guarantee one event = one line**.
- If exporting CSV to a spreadsheet, data starting with **=, +, -, @** or related control/whitespace characters can trigger **formula injection** when spreadsheet software interprets it. This is a *different* risk from log forging and requires separate mitigation at the spreadsheet export step.

Do not take CSV quoting and treat it as JSON escaping. For logging with machine-readable records and line-by-line streaming, **JSON Lines** is usually easier to control than multiline CSV.

### 10.2. TSV and Pipe-Delimited Formats

Tabs or **|** characters in data can break structure. You must have a clear grammar/encoder and a matching parser, or switch to JSON. Simply calling **replace("|", "")** loses information and can leave other structural breakouts such as CR/LF, quotes, or control characters.

### 10.3. Logs Displayed in a Web Interface

A string escaped for JSON/text **is not necessarily safe to insert into HTML**. Viewers should render content using **textContent/text nodes** or an auto-escaping template mechanism, never innerHTML with untrusted log data.

If the interface includes syntax highlighting, linkifiers, or Markdown renderers, they can open an additional interpretation layer. Test inputs containing tags, markup, and unusual URLs, and ensure no execution occurs in the browser. Do not share a single escape function across HTML, JSON, and plain text because each format has a different grammar.

## 11. Commonly Overlooked Points When Escaping

### 11.1. MDC, requestId, and traceId

An application might log:

~~~java
// Illustrative, requires backend/SLF4J dependency.
org.slf4j.MDC.put("requestId", requestIdFromHeader);
logger.info("Received request");
~~~

If the pattern includes **%X{requestId}**, this input appears even when the message itself contains nothing malicious. Therefore, you must **validate** requestId at the HTTP boundary, limit its length and allowed character set, and **encode** it on output when needed.

For W3C traceId, there is a well-defined hex format and size; validate against that format rather than accepting any string. Do not assume a header named "trace-id" has been normalized by the framework.

### 11.2. Exceptions and Stack Traces

Exception messages can contain URLs, file paths, or externally supplied input. In addition, stack traces are normally **validly multi-line**. There are two common options:

1. Structured logging stores **exception.type, exception.message, exception.stacktrace** as separate fields, each properly encoded.
2. Text logging allows multi-line stack traces but uses clearly defined **record framing/correlation** (for example, a collector configured for multiline), while preventing **untrusted messages** from injecting lines that look like log headers.

Do not strip entire stack traces just to protect against CRLF. At the same time, do not log raw exceptions if they contain credentials, secrets, or sensitive bodies.

### 11.3. Multiple Encodings or Inconsistent Decoding

Suppose a string sent over HTTP contains percent-encoded CR/LF. The HTTP layer may decode it before the application receives it. If one layer checks for the literal string **%0D%0A** while another layer has already decoded it to CRLF, the check can be bypassed.

Principles:

- Establish a **canonical representation** of data at the validation point.
- Do not decode/normalize multiple times uncontrollably.
- On output, the encoder must receive the canonical data and escape the **actual characters**.
- Do not blindly trust a string that was already escaped upstream; double escaping or downstream re-decoding can occur.

With Java Unicode strings, test valid surrogate pairs, unpaired surrogates, Vietnamese diacritics, emojis, and special separators. Only process by individual **char** when you understand the impact on Unicode; for character-length limits, consider **code points** instead of slicing arbitrarily in the middle of a surrogate pair.

### 11.4. Long Log Inputs and Resources

A multi-megabyte string without CRLF can still cause a logging system to consume excessive CPU/RAM, increase GC pressure, fill queues/disks, or get truncated by a collector. You should:

- Limit length **by field type**, rather than necessarily using one limit for every event.
- Clearly decide the unit of measurement: code points, UTF-16 code units, or UTF-8 bytes.
- Do not slice in the middle of a surrogate pair or arbitrarily cut JSON output in a way that produces an invalid record.
- If truncating, add metadata such as **truncated=true**, original length (if non-sensitive), and event ID; never produce syntactically broken records.
- Limit event counts and write rates for inputs that can be sent continuously to prevent log flooding.

**Note**: some encoders apply limits per **field value**, not to the entire event or encoded byte count. Distinguish these levels when sizing collectors.

### 11.5. Redaction Must Happen Before Data Leaves the Trust Zone

Do not rely solely on a collector to strip secrets if raw stdout/files are already collected, buffered, or displayed elsewhere. Prefer **not logging secrets in the first place**. When recording security events, log **the event type, authorized subject, outcome, and correlation ID**, rather than raw tokens, cookies, passwords, or personal data.

Escaping does not make a secret any less secret. For example, if a password contains no CRLF, escaping leaves the password intact: that is still a policy violation.

## 12. Recommended Design Pattern for a Java Service

A well-operable design includes:

1. **Consistent logger API**: SLF4J with a compatible backend/provider, or JUL where appropriate.
2. **Constant event names and message templates**: never let user input construct log templates, layouts, or logger configurations.
3. **Clear field schema**: event, severity, service, environment, traceId, requestId, outcome, and permitted business fields.
4. **Per-field validation**: e.g., UUID/traceId/requestId by pattern; for usernames with Unicode, do not force ASCII-only.
5. **Data minimization + masking**: do not log secrets/PII beyond the authorized scope.
6. **Structured encoder**: JSON Lines or an equivalent verified schema, where one event is serialized into one complete record.
7. **Size limits and rate controls**: prevent a single input from overwhelming the log pipeline.
8. **Shared contract with collector/parser**: do not use regexes splitting on unescaped delimiters; align on charset (typically UTF-8) and behavior for oversized records.
9. **Safe viewer**: text rendering/HTML escaping and proper access controls.
10. **Regression tests**: a suite of injection payloads tested end-to-end from controller/consumer to file, collector, and dashboard.

### Trust Boundary Diagram

~~~text
HTTP / Queue / DB (untrusted field values)
            │
            ▼
    Typed validation (domain grammar)
            │
            ▼
  Structured event + redact + limit
            │
            ▼
    Logging API + trusted template
            │
            ▼
  JSON encoder / text encoder per sink
            │
            ▼
  Console/File → Collector → Storage
            │
            ▼
    Viewer renders as data
~~~

If **each layer concatenates strings and then decodes/encodes inconsistently**, more transformation steps lead to more bugs. It is better to keep fields structured as long as possible and serialize only at the respective output boundary.

## 13. Security Testing with Synthetic Data

Run tests with a **dedicated message ID**; verify the number of records written, field contents after parsing, and absence of forged records. Test data should consist only of synthetic strings created by the test team, containing no real passwords or tokens.

| Test input | Target | Security expectation |
| --- | --- | --- |
| **alice** | Baseline | Exactly one record; value preserved. |
| **alice + LF + ERROR fake** | Newline injection | One-line text shows escaped LF; JSON remains a single object. |
| **alice + CRLF + WARN fake** | Windows-style log forging | No forged WARN severity record created. |
| **alice + CR** | Lone carriage return | Does not overwrite the start of the line on a terminal. |
| **TAB, pipe, comma, quote** | Field/delimiter injection | Parser recovers the exact field count/values. |
| **Multiple backslashes** | Double escape/parser mismatch | One serialize/deserialize round-trip recovers the exact value. |
| **NUL, ESC, U+0085** | Control chars / terminal | Does not control the terminal or break log boundaries. |
| **U+2028, U+2029** | Unicode line/paragraph separators | Does not split records unexpectedly in viewer/collector. |
| **U+202E and bidi controls** | Display spoofing | Consistent encoding/display policy applied. |
| **Vietnamese diacritics and emoji** | Unicode correctness | No valid characters lost, no encoding errors introduced. |
| **Input larger than max field** | Log flooding / truncation | Event bounded, truncated flag valid, JSON unbroken. |
| **String containing HTML markup** | Viewer injection | Browser displays as text, does not render as DOM/JS. |
| **requestId from header** | MDC injection | ID is validated and encoder handles context fields as well. |
| **Exception containing input** | Stack trace + message | No forged event created, relevant error info preserved. |

### Assertions to Perform

- **One accepted log call → one logical event** at the designated point, not split into multiple records by input. Note that collectors may retry and cause duplicates; tests may need to separate framing from delivery.
- **Event severity/logger/timestamp cannot be influenced by input**. System fields come from the logging API or controlled schema.
- **JSON parses successfully**, and values can be recovered accurately (except for fields intentionally redacted/truncated).
- **No secrets** appear in raw output or after ingestion.
- **Size limits** still work properly with multi-byte characters.
- **Viewer** does not execute HTML/JS or ANSI escapes from fields.
- **MDC and nested fields** are handled, not only the message.
- **Logging during system errors** (disk full, appender error, collector offline) does not turn logging into another security vulnerability or leak data in error messages.

For payloads with invisible control characters, construct them in tests using Unicode code point expressions or explicit escape literals; avoid pasting invisible control characters directly into files where they are hard to review.

## 14. Verifying Logback/Log4j2/Spring Boot in Real Applications

### Step 1: Identify the Backend

Does the application use SLF4J or JUL? Is the actual provider Logback, Log4j2, or another backend? The same logger call can be serialized completely differently depending on configuration. Having a logback.xml file in the repository does not prove the runtime loaded it.

### Step 2: Identify the Actual Format Written

- Logback with pattern **%msg%n** is a text layout; you must verify CRLF handling.
- Log4j2 PatternLayout can use the **%enc{%m}{CRLF}** converter, but other fields still need encoding.
- Does the structured encoder emit **a schema-defined object** or just a JSON message embedded inside a text line?
- Do exception stack traces belong to the same event, or is the collector splitting them into multiple records?
- Are there legacy downstream parsers that do not support new quoting/escaping?

### Step 3: Test the Entire Pipeline

Use harmless test payloads containing CRLF, quotes, and Unicode controls. Send them through the API or message consumer and inspect:

~~~text
source input
  → application event
  → console/file bytes
  → collector parsed event
  → indexed event
  → dashboard rendering
~~~

A unit test on **escapeOneLine** only proves one function. To conclude that the system is free from log injection, you must test end-to-end, especially where the collector splits by line and where the dashboard renders fields.

### Step 4: Protect Code and Configuration

- Never accept input as a layout pattern, file path, logger name, or template from public endpoints.
- Keep logging backends updated according to policy; address advisories related to configuration lookups, plugins, and dependencies.
- Review how production log configurations differ from test/dev; ensure test configs are not accidentally packaged.
- Protect log storage from unauthorized modification/deletion; enforce retention and access controls.
- If high-assurance audit evidence is required, implement durable storage and appropriate tamper detection rather than relying solely on escaping.

## 15. Common Misconceptions

**1. “Using SLF4J curly braces eliminates log injection.”** False. It keeps the template stable, but parameter data can still contain CR/LF if the layout does not encode it.

**2. “Replacing newlines is enough.”** False. Lone CRs, quotes/delimiters, ANSI controls, Unicode separators, and fields other than the message also matter.

**3. “Escape all special characters immediately upon receiving HTTP input.”** Not recommended. This alters business data and easily causes double encoding; validate against the domain and encode for the output context.

**4. “JSON format is always 100% safe.”** A syntactically valid JSON encoder protects structure, but it does not prevent logging secrets, oversized payloads, log flooding, or XSS in an improperly rendered viewer.

**5. “Only the message is untrusted data.”** False. requestId, MDC, filenames, exception messages, service metadata, and other fields can all contain external input.

**6. “If it is escaped for writing to a file, it is safe to display with innerHTML.”** False. HTML is a different output context.

**7. “Sanitizing by deleting all CR/LF has no trade-offs.”** False. You can lose data needed for investigations, especially in exceptions or comments. Rule-based escaping is usually better than blind stripping.

**8. “One regex in config is enough to protect every format.”** False. You need to know the grammar, backend, version, all fields, and consumers.

**9. “It is fine to log raw request bodies at DEBUG because dev is low risk.”** False. Secrets/PII and injection payloads can still enter dev/CI logs and be shipped to shared systems.

**10. “Length limits are unrelated to security.”** False. Log flooding can exhaust resources and cause critical events to be dropped under overload.

**11. “Checking unit test output on one machine is enough.”** Insufficient. Terminals, containers, collectors, and viewers can handle control characters differently.

**12. “JSON escaping and CSV escaping are interchangeable.”** False. Quoting, delimiter, and record framing rules differ, and CSV also carries formula injection risks when opened in spreadsheets.

## 17. Conclusion

**Escaping input data in logging means protecting the boundary between untrusted data and log syntax.** Preventing log forging requires controlling CR/LF, delimiters, control characters, metadata, and how downstream layers interpret the output. For modern Java applications, prefer **constant templates + typed fields + redaction + structured encoder (JSON) + size limits + end-to-end tests**. When plain text is still used, escaping must be designed for **the exact format and consumer**, not based on a random replace call.

**Key takeaway:** validation is about *whether a value is valid*; escaping is about *how a value is safely represented in output*; redaction is about *which data must not appear in logs*. A secure system needs all three.
