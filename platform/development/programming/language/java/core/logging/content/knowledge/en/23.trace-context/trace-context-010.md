# Trace-Based Log Analysis

## 1. Goal and Problem Statement

In a multi-component Java application, a single request may pass through an API, business services, databases, message queues, and external services. When a request fails, each component typically writes its own logs. Reading each log file in chronological order makes it easy to miss the root cause because other requests are running interleaved.

**Trace-based log analysis** is the process of finding log records belonging to the same execution flow, correlating them with span and timing information, and cross-referencing them with distributed tracing to answer:

- Where did the request start, which services did it traverse, and how did it end?
- In which operation was the error first recorded? Which errors are merely consequences of an earlier error?
- Were there any retries, timeouts, asynchronous processing, or parallel branches?
- What evidence from logs, spans, metrics, and source code is sufficient to conclude the root cause?

The goal is not merely to group every line that shares an identifier: a single trace can contain many spans, multiple branches, and multiple secondary errors. It is essential to distinguish **correlation** (belonging to the same execution flow) from **causation** (which operation actually led to the failure).

## 2. How Do Traces, Spans, and Log Records Relate?

- A **Trace** represents the complete or partial journey of an operation across components. `trace_id` identifies the trace, typically 16 bytes / 32 hex characters in the W3C Trace Context format.
- A **Span** represents a unit of work with a start/end time, attributes, status, and optional parent–child relationships. `span_id` is typically 8 bytes / 16 hex characters. Multiple spans share the same `trace_id`.
- A **Log event** is a point-in-time record of state or an event. If tagged with `trace_id` and `span_id` from the active context, the log can be linked to the corresponding trace/span.
- **Parent span** defines the parent–child relationship in trace data. `parent_span_id` in logs is an optional attribute if the system explicitly records it; not all log formats include that field.
- **Request ID** is usually generated by the application or gateway; it can correlate a single request, but it cannot replace `trace_id` when work crosses multiple services or messages.

For example, an HTTP `POST /checkout` request has a span in `checkout-api` and a span in `payment-service`. The two spans have different `span_id` values and the same `trace_id`. Logs from both services can be queried together using `trace_id`; to understand which operation called which, continue cross-referencing parent–child spans and timestamps.

A trace being sampled and exported to a tracing backend **does not mean** all of its logs have been stored; conversely, a missing trace in the tracing backend **does not prove** that logs containing `trace_id` are invalid. Sampling, retention, collection configuration, and export latency are separate mechanisms.

## 3. Essential Fields for Effective Analysis

| Field | Investigation Meaning | What to Check |
| --- | --- | --- |
| `timestamp` | Event time according to the source clock | Whether timezone, precision, and clock synchronization are present |
| `service.name` / `service` | Service emitting the log | Consistent naming across deployments |
| `trace_id` | Correlates records across services | Valid format, propagated across service boundaries |
| `span_id` | Links log to a specific operation | Must come from the active span, not randomly generated |
| `severity` / `level` | Filters errors, warnings, and info | Do not use a lone `ERROR` to conclude the root cause |
| `message` / `event.name` | Execution flow and failure point | Should have clear, searchable event descriptions |
| `error.type`, `exception.type` | Categorizes the failure | Preserve the exact error type; stack traces may live in a separate field |
| `duration_ms`, `http.response.status_code` | Cross-checks latency and outcome | Distinguish operation duration from the gap between two log lines |
| `parent_span_id`, `operation` | Adds relationship and operation context | Depends on whether the system records them |
| `deployment.environment`, `service.version` | Scopes environment and version | Very useful when an error only occurs after a deployment |

Use **structured logs** (e.g., JSONL, where each line is a JSON object) for reliable querying. Standardize field names across the application, collector, and search tools. In OpenTelemetry, `trace_id`/`span_id` have defined positions in the LogRecord model; display field names in the storage backend may be mapped differently. Do not assume every Java logging framework automatically attaches trace context.

## 4. Example: Reconstructing a Failed Request

Suppose the services emit the following events; all timestamps are in UTC. The `parent_span_id` column represents the relationship provided by the observability system, not a relationship inferred solely by sorting lines.

| UTC | Service | Span | Parent span | Event |
| --- | --- | --- | --- | --- |
| 02:00:00.010 | `checkout-api` | `00f067aa0ba902b7` | — | Received `POST /checkout` |
| 02:00:00.030 | `payment-service` | `b7ad6b7169203331` | `00f067aa0ba902b7` | Started payment request |
| 02:00:02.032 | `payment-service` | `b7ad6b7169203331` | `00f067aa0ba902b7` | Timeout error from payment gateway |
| 02:00:02.044 | `checkout-api` | `00f067aa0ba902b7` | — | Checkout failed |

All share:

```text
trace_id = 4bf92f3577b34da6a3ce929d0e0e4736
```

An evidence-based reading:

1. The `checkout-api` span receives the request; subsequently, the `payment-service` span is invoked.
2. `payment-service` records a timeout before `checkout-api` logs the final failure. The log in checkout **may be a consequence** of the payment error.
3. The ~2-second gap between the payment start log and the timeout log **is not automatically the exact span duration**. To determine execution time, inspect span start/end timestamps, clock skew between services, and any retries.
4. The most immediate evidenced cause is **the timeout observed in `payment-service`**. You still need to check the gateway call span, retries, connection state, timeout configuration, and the gateway's logs/metrics before concluding why the gateway was slow.

This example shows that log ordering helps form hypotheses, while span relationships and additional evidence help test those hypotheses.

## 5. End-to-End Trace Investigation Workflow

### Step 1 — Obtain the Trail from the Initial Event

Start from the error code, alert, API response, timestamp, environment, and `trace_id` in logs or response headers (if the system explicitly returns it). Do not search only by generic messages like “request failed”: that usually mixes multiple requests together.

Verify that `trace_id` has a valid format and has not been truncated, altered, renamed across fields, or regenerated between services. According to W3C Trace Context, the 16-byte trace-id and 8-byte parent-id must not be all zeros. A valid-looking trace ID still does not guarantee that propagation worked properly.

### Step 2 — Query All Services Within a Reasonable Time Window

Search for the **exact `trace_id`** across logs from the same environment and time window around the incident. Syntax varies by platform (Loki, Elasticsearch/OpenSearch, Cloud Logging, etc.); the example below is an *illustrative query*, not universal syntax for every tool:

```text
trace_id = "4bf92f3577b34da6a3ce929d0e0e4736"
sort timestamp ascending
show timestamp, service, span_id, severity, message
```

Check whether all expected participating services appear. If a service is missing, inspect propagation, collectors, severity filters, retention, and logging during asynchronous processing; do not rush to conclude that the service was never called.

### Step 3 — Build the Timeline and Group by Span

- Sort by **event timestamp**, while also keeping an eye on **ingest timestamp** if the pipeline receives logs late or out of order.
- Group by `service` and then `span_id`; cross-reference operation names, start/end times, statuses, and parent/child relationships in the tracing backend.
- Mark the timestamps for request receipt, dependency calls, retries, timeouts, thrown exceptions, caught exceptions, and the final response.
- If there are parallel branches, map each branch separately; two consecutive log lines do not imply a caller–callee relationship.
- For Kafka/message queue flows, look for trace context in **message headers** on both producer and consumer sides, along with message IDs to understand enqueueing, delay, redelivery, and processing.

### Step 4 — Distinguish Root Errors from Propagated Errors

For example: `payment-service` logs `SocketTimeoutException`; `checkout-api` subsequently logs `PaymentFailedException`. The checkout error may simply be a symptom of the downstream timeout. Conversely, if checkout sent invalid parameters, a validation error in payment could be a consequence of a bug in checkout. Check stack traces, returned error codes, related spans, and source code.

Do not treat every `ERROR` as the “root cause”. Some error logs are expected from retry branches, circuit breakers, or business logic; conversely, serious issues may only be logged as `WARN` or recorded as metrics.

### Step 5 — Validate Hypotheses and Impact Scope

Compare the failed trace against a successful trace for the same endpoint/version, comparing per-span latency, retry frequency, and changes after a deployment. Use metrics for aggregate questions such as error rate, p95/p99, or saturation; use traces/logs for the details of a single request. Document your conclusion with **evidence**, **uncertainties**, **remediation steps**, and post-fix verification criteria.

## 6. Querying JSONL Logs in Practice

Suppose `app-*.jsonl` files contain one JSON object per line with the keys `timestamp`, `service`, `trace_id`, `span_id`, `severity`, and `message`. If `jq` is available and all ISO 8601 timestamps are normalized to UTC, you can filter and sort as follows:

```bash
TRACE_ID='4bf92f3577b34da6a3ce929d0e0e4736'
jq -r --arg trace "$TRACE_ID" \
  'select(.trace_id == $trace) |
   [.timestamp, .service, .severity, .span_id, .message] |
   @tsv' app-*.jsonl | sort
```

`jq` parses the JSON logs, and `sort` works here because the first column is a uniformly formatted UTC timestamp. If timestamps use different timezones or formats, they must be parsed and normalized before sorting. Multi-line logs such as stack traces should be packaged by the collector into **a single structured event**; running plain `grep` can split lines belonging to the same exception.

To search for errors within the same trace, you can add a condition:

```text
trace_id = "<trace to investigate>" AND severity IN ("ERROR", "FATAL")
```

Do not look only at ERRORs: INFO/WARN logs preceding the error, retry branches, and downstream states often explain why the failure occurred.

## 7. Java 17 Example: Filtering and Sorting Logs for a Trace

The following program runs standalone on JDK 17+ with no external libraries required. Log data is simulated in memory to focus on filtering by `trace_id` and sorting by event time. In practice, data can come from JSONL files, a search engine, or a collector.

Save as **`TraceLogAnalyzer.java`**:

```java
import java.time.Instant;
import java.util.Comparator;
import java.util.List;

public class TraceLogAnalyzer {
    record Event(
            Instant timestamp,
            String service,
            String traceId,
            String spanId,
            String level,
            String message) {
    }

    public static void main(String[] args) {
        String target = "4bf92f3577b34da6a3ce929d0e0e4736";
        String other = "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa";

        // Intentionally place events out of chronological order.
        List<Event> events = List.of(
            new Event(Instant.parse("2026-11-10T02:00:02.032Z"),
                "payment-service", target, "b7ad6b7169203331",
                "ERROR", "Gateway timeout"),
            new Event(Instant.parse("2026-11-10T02:00:00.010Z"),
                "checkout-api", target, "00f067aa0ba902b7",
                "INFO", "POST /checkout accepted"),
            new Event(Instant.parse("2026-11-10T02:00:00.015Z"),
                "checkout-api", other, "1111111111111111",
                "INFO", "Unrelated request"),
            new Event(Instant.parse("2026-11-10T02:00:00.030Z"),
                "payment-service", target, "b7ad6b7169203331",
                "INFO", "Charge requested"),
            new Event(Instant.parse("2026-11-10T02:00:02.044Z"),
                "checkout-api", target, "00f067aa0ba902b7",
                "ERROR", "Checkout failed")
        );

        events.stream()
            .filter(event -> target.equals(event.traceId()))
            .sorted(Comparator.comparing(Event::timestamp)
                .thenComparing(Event::service))
            .forEach(event -> System.out.println(
                event.timestamp() + " | " + event.service()
                + " | " + event.level()
                + " | span=" + event.spanId()
                + " | " + event.message()));
    }
}
```

Compile and run:

```bash
javac --release 17 TraceLogAnalyzer.java
java TraceLogAnalyzer
```

Expected output:

```text
2026-11-10T02:00:00.010Z | checkout-api | INFO | span=00f067aa0ba902b7 | POST /checkout accepted
2026-11-10T02:00:00.030Z | payment-service | INFO | span=b7ad6b7169203331 | Charge requested
2026-11-10T02:00:02.032Z | payment-service | ERROR | span=b7ad6b7169203331 | Gateway timeout
2026-11-10T02:00:02.044Z | checkout-api | ERROR | span=00f067aa0ba902b7 | Checkout failed
```

Understand the limitation of this example: filtering and sorting logs **does not reconstruct the span tree**, because the `Event` record does not contain full parent–child or start/end information. In a real system, correlate with the trace backend using the `trace_id` + `span_id` pair rather than guessing relationships solely from timestamp ordering.

## 8. Linking Java Logs with OpenTelemetry

In a Java application using OpenTelemetry, instrument HTTP servers/clients, JDBC, and messaging appropriately to create/receive context, then configure a bridge to inject trace/span IDs into logs. For example, with SLF4J/Logback, a bridge can insert `trace_id` and `span_id` into MDC or export correlation fields directly via OTLP; **the exact configuration depends on the version and instrumentation setup**.

Typical flow:

```text
HTTP/gRPC/message receives context
          ↓
Extract trace context → active span
          ↓
Business code logs with trace_id/span_id
          ↓
Logger / collector normalizes logs
          ↓
Log backend queries by trace_id
          ↕
Tracing backend opens span details for the same trace_id
```

W3C `traceparent` has the format:

```text
00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
```

The parts correspond to version, trace-id, parent-id, and trace-flags. The value `01` sets the sampled flag in this example; it does **not** mean every log is guaranteed to be stored or every span is guaranteed to be exported successfully. When an outbound request creates a child span, the `parent-id` in the outgoing header is typically the ID of the current outbound span.

If you must populate MDC manually, retrieve the IDs from the **active span context**, verify that the context is valid, and ensure cleanup/restoration using `try/finally` or a scope-closing mechanism. MDC is typically thread-bound; handing off a request to an `Executor`, `CompletableFuture`, or reactive pipeline without propagating context properly will cause **lost IDs or trace mix-ups between two requests**. Prefer supported integrations/instrumentations and verify actual log output rather than generating a custom `trace_id` per line.

Do not put secrets, Authorization headers, cookies, payment tokens, or sensitive personal data into logs just to make trace correlation easier. `trace_id` is a high-cardinality investigation key; apply appropriate access controls, retention, and data governance rules.

## 9. Common Misdiagnosis Scenarios

| Symptom | Possible Cause | How to Verify |
| --- | --- | --- |
| Only API logs appear, downstream service missing | Context not propagated, field renamed, collector filtering logs | Check inbound/outbound context and logs right at the boundary |
| One request contains multiple `trace_id` values | New trace started in the wrong place, context lost in async/messaging | Inspect `traceparent` and instrumentation at each hop |
| Logs from two requests have mixed IDs | MDC not cleaned up, thread reuse | Check MDC restore/clear logic, run concurrency tests |
| Logs have `trace_id` but trace cannot be opened | Sampling, exporter failure, backend lag, or mismatched retention | Check sampling/export pipeline and time window |
| Log timestamps conflict with caller–callee order | Clock skew, log buffering, ingestion delay | Compare span times with event/ingest timestamps |
| Multiple ERRORs appear in one trace | Error wrapped/propagated or retried multiple times | Find the earliest *causally related* error, not just the first ERROR line |
| Span has no logs but is marked as error | Level filter, instrumentation emits no logs, data not retained | Inspect span events/status; do not assume corresponding logs exist |
| Message consumer has a different trace than producer | Context not written to or read from message headers | Check context encode/decode, retries, and dead-letter queue |
| Trace is too long, search is slow | Many spans/logs or unbounded query | Narrow by time range, service, and event, then expand intentionally |

**Especially for asynchronous processing:** a trace may represent relationships via span links rather than a direct parent–child tree. A message may be processed under a new trace while still carrying a link to the source context; concluding that a “link was lost” must be based on actual spans/links data.

## 10. Writing Verifiable Investigation Conclusions

An investigation report should clearly answer:

1. **Scope:** environment, version, endpoint/consumer, time window, and one or a few representative `trace_id` values.
2. **Timeline:** request receipt time, relevant spans/downstream calls, error timestamp, and final response, including timezone.
3. **Evidence:** short log snippets with `trace_id`/`span_id`, root exception, span status/duration, and metrics showing impact scope.
4. **Hypotheses and confidence level:** what has been proven, and what still requires logs/traces from another dependency.
5. **Actions:** fix propagation/instrumentation if data is missing; fix logic or dependency configuration if evidence supports it; verify with a reproduction request and compare before–after traces.

Example of a sound conclusion: “In trace `4bf92f…`, `payment-service` logged `Gateway timeout` at 02:00:02.032Z; `checkout-api` logged `Checkout failed` at 02:00:02.044Z. The payment span is the first branch to investigate. There is not yet enough data to confirm whether the gateway itself failed or the client timeout is configured too low; we need to check the HTTP client span duration, retry count, and gateway metrics.”

That is a much better conclusion than simply writing “checkout failed because of payment”: it identifies the evidence, the boundaries of current knowledge, and the next verification step.

## 11. Checklist Before Considering Analysis Complete

- Confirmed the exact `trace_id` and time window, and searched across all services that actually participated.
- Distinguished `span_id`, request ID, and message ID; checked context propagation over HTTP and messaging where applicable.
- Sorted events by normalized timestamp and accounted for clock skew or late-arriving logs.
- Cross-referenced parent/child spans or span links; did not infer causation solely from log order.
- Distinguished the originating error from wrapped, propagated, or retry-repeated errors.
- Checked sampling, retention, exporter, and collector behavior before concluding logs/traces are missing.
- Verified findings with metrics/traces or reproduction runs when needed; did not over-interpret a single trace.
- Minimized sensitive data and avoided using `trace_id` as a high-cardinality metric label.

**Remember:** `trace_id` helps *find the right events*, `span_id` and span relationships help *understand the execution branch*, and logs + tracing + metrics + source code help *verify the root cause*. A good analysis records both what was observed and what cannot yet be concluded.
