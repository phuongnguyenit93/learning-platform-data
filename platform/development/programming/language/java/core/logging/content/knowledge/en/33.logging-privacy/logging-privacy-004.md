# Masking Sensitive Data in Java Logging

## 1. Goal: Maintain Observability Without Leaking Information

**Masking sensitive data (data masking/redaction in logging)** is the process of omitting, removing, partially obscuring, or replacing sensitive values before a log record is stored, displayed, forwarded to a collector, or shared. For example, replacing a test card number `4111111111111111` with `****1111`, or replacing an entire access token with `[REDACTED]`.

In Java, a single logger call can emit data in many places: **message**, **arguments**, **exceptions and stack traces**, **MDC/ThreadContext**, **HTTP headers**, **request body**, **URL/query**, **objects converted via `toString()`**, JSON event attributes, and records generated by third-party libraries. Therefore, using regex only to patch the message is **not enough**.

Practical goals in order of priority:

1. **Do not collect / do not log** unnecessary data.
2. **Log only allowlisted fields**, prioritizing event codes, statuses, and less sensitive internal identifiers.
3. **Mask/redact/tokenize** fields where a partial value is genuinely needed for investigation, with an explicit policy and repeatable verification.
4. **Add a defense layer at the formatter/appender/collector** to mitigate application code mistakes; do not treat this as an absolute guarantee.
5. **Protect the log lifecycle** with access control, encryption, retention, and deletion according to policy.

**Masking does not make data harmless.** An email that exposes its first character and domain can still help identify a user; the last four digits of a card can sometimes be combined with other data. You must weigh necessity against information protection requirements in context.

## 2. Classify Data Before Designing Rules

A typical policy can group data as follows (adjust to your system and applicable regulations):

| Category | Examples | Default Strategy | Why |
| --- | --- | --- | --- |
| Authentication secrets | Password, PIN, OTP, access/refresh token, API key, session cookie, Authorization header | **Do not log** the value; replace with a presence flag or `[REDACTED]` | Even a short string can grant real access |
| Keys and cryptographic material | Private key, seed, recovery code, configuration secret | **Do not log**, including prefix/suffix when not needed | Risk of system compromise |
| Payment information | PAN/card number, CVV, account number | Do not log; keep only the minimum allowed field, e.g., last4 per policy | Sensitive financial data |
| Personal information (PII) | Email, phone number, address, national/personal ID, health data | Avoid logging or mask/pseudonymize by purpose | Easy to re-identify and subject to privacy requirements |
| HTTP request/response | Query string, body, headers, cookies | Log only method, route template, status, duration, error code | May contain tokens and PII in unpredictable locations |
| Connection/database | JDBC URL with credentials, SQL bind values, integration URI | Log service name, error code, and latency; do not log credentials/sensitive binds | Connection strings and SQL statements can carry secrets |
| Operational data | Event code, service name, status, duration, correlation ID | Allow according to schema and retention | Sufficient for monitoring without raw data |

A policy **cannot** rely solely on field names. `userId` may be a personal identifier, `traceId` may help correlate behavior, and a seemingly harmless `errorMessage` may contain a token inside a URL.

Apply the *data minimization* principle: keep only data genuinely needed for debugging, monitoring, incident investigation, security, or auditing; define the purpose before logging.

## 3. Distinguish Techniques Commonly Grouped Under "Masking"

| Technique | Transformation | Recoverability or Linkability |
| --- | --- | --- |
| **Omit/drop field** | Exclude the field from the log | Cannot be recovered from that record; usually the safest |
| **Full redaction** | `token=[REDACTED]` | Does not reveal the original value via the redacted field |
| **Partial masking** | `a***@example.test` or `****1111` | Retains part of the data; still carries inference/re-identification risk |
| **Pseudonymization** | Replace user with a reference code | Can correlate events; still carries privacy risk |
| **Tokenization** | Replace data with a lookup token managed by a system | Recoverable via a token vault if authorized |
| **Hashing** | Transform input into a digest | One-way by function, but easy to guess for small value sets |
| **Keyed HMAC** | Produce a stable identifier from a secret and message | Useful for controlled correlation; requires key protection and rotation |
| **Encryption** | Encrypt the original data | Decryptable with a key; the record still contains encrypted sensitive data |

**Directly hashing an email/phone number with SHA-256 does not equal anonymization.** The value space can be guessed or brute-forced. HMAC with a separately managed key reduces offline guessing but still produces a linkable identifier and requires governance policies. Tokenization/HMAC does not replace a privacy assessment.

When you only need to know "whether the Authorization header was sent," logging `authorizationPresent=true` is usually better than any masked form of the token.

## 4. Filter at the Source Before Passing Data to the Logger

Safer approach:

~~~java
// Illustration: log only allowlisted fields; do not log the full request or DTO.
log.info("login result={} reason={} requestId={}",
        safeResult, safeReasonCode, requestId);
~~~

The variables above must be **normalized and approved for logging** before calling the logger. This is an SLF4J/Log4j 2 snippet with an already-declared logger, not a standalone Java program.

Risky approach:

~~~java
// DO NOT do this: objects may contain passwords, tokens, emails, or cookies.
log.info("incoming request={}", request);
log.error("login failed, headers={}", headers);
log.debug("user profile={}", user.toString());
~~~

Even when DEBUG is disabled, enabling DEBUG during an incident can accidentally dump all data. `toString()` auto-generated by Lombok, records, or an IDE may add new fields later without any change to the logging code.

A good design is to create a **SafeLogEvent** or a map containing only allowed fields, for example:

~~~text
eventCode: "LOGIN_DENIED"
result: "DENIED"
reasonCode: "INVALID_CREDENTIALS"
requestId: "req-7f2a"
credentialPresent: true
~~~

This is an **illustrative schema**. Do not place raw emails, passwords, tokens, or full HTTP requests into the event and expect a formatter to strip them later.

## 5. Three Boundaries You Must Control

~~~text
Data source (HTTP/DB/queue/config)
   │
   ├─ [1] App/service: select fields + sanitize/mask per schema
   ▼
Log API: message + arguments + Throwable + MDC
   │
   ├─ [2] Logger/Formatter/Appender/Encoder: second-line defense
   ▼
File / stdout / socket / agent
   │
   ├─ [3] Collector/index/storage: ingest policy + access control + retention
   ▼
Dashboard / query / export / archive / backup
~~~

**[1] Before the logger call** is the most important line of defense: here the code knows the field type, purpose, and logging permissions. **[2] At the logging backend** is a supplemental mitigation layer when logs are emitted from places outside your control; regex may not cover every message/exception/context. **[3] At the collector/storage** you need ingest rules and governance because logs may come from many service versions or libraries.

Once data has been sent to a sink, masking in the UI dashboard **does not remove the raw data** in files, indexes, archives, or exports. Preventing sensitive data from entering the pipeline in the first place is always less risky.

## 6. Standalone Java 17 Example: Mask Properly Before Logging

This example uses `java.util.logging` (JUL), requiring no libraries outside the JDK. The program proactively **does not pass raw secrets** to the logger; emails are masked, synthetic card numbers keep only the last 4 digits, and `reasonCode` is allowlisted to also block unwanted data containing newlines.

Create **SensitiveMaskDemo.java**:

~~~java
import java.util.Locale;
import java.util.logging.ConsoleHandler;
import java.util.logging.Formatter;
import java.util.logging.Level;
import java.util.logging.LogRecord;
import java.util.logging.Logger;

public final class SensitiveMaskDemo {
    private static final Logger LOG =
            Logger.getLogger(SensitiveMaskDemo.class.getName());

    private static String maskEmail(String input) {
        if (input == null) return "[REDACTED]";
        int at = input.indexOf('@');
        if (at < 1 || at != input.lastIndexOf('@') ||
                at == input.length() - 1) return "[REDACTED]";
        String local = input.substring(0, at);
        String domain = input.substring(at + 1);
        if (!local.matches("[A-Za-z0-9._%+-]{1,64}") ||
                !domain.matches("[A-Za-z0-9.-]{1,253}") ||
                domain.indexOf('.') < 0) return "[REDACTED]";
        return local.charAt(0) + "***@" +
                domain.toLowerCase(Locale.ROOT);
    }

    private static String maskCard(String digits) {
        if (digits == null || !digits.matches("[0-9]{12,19}"))
            return "[REDACTED]";
        return "****" + digits.substring(digits.length() - 4);
    }

    private static String safeReason(String reason) {
        return "INVALID_INPUT".equals(reason) ? "INVALID_INPUT" : "OTHER";
    }

    public static void main(String[] args) {
        ConsoleHandler handler = new ConsoleHandler();
        handler.setLevel(Level.INFO);
        handler.setFormatter(new Formatter() {
            @Override
            public String format(LogRecord event) {
                return event.getLevel().getName() + " "
                        + formatMessage(event) + System.lineSeparator();
            }
        });
        LOG.setUseParentHandlers(false);
        LOG.setLevel(Level.INFO);
        LOG.addHandler(handler);
        try {
            String email = "alice@example.test";
            String testCard = "4111111111111111";
            String testSecret = "TEST_SECRET_DO_NOT_LOG";
            String untrustedReason = "INVALID_INPUT\nERROR forged";

            LOG.log(Level.INFO, "auth result={0} user={1} reason={2}",
                    new Object[]{"DENIED", maskEmail(email),
                            safeReason(untrustedReason)});
            LOG.log(Level.INFO, "payment result={0} card={1}",
                    new Object[]{"REJECTED", maskCard(testCard)});
            LOG.log(Level.INFO, "credential_present={0}",
                    !testSecret.isEmpty());
        } finally {
            LOG.removeHandler(handler);
            handler.flush();
            handler.close();
        }
    }
}
~~~

Run with JDK 17+:

~~~bash
javac --release 17 SensitiveMaskDemo.java
java SensitiveMaskDemo
~~~

**Exact standard error (stderr)**, because `ConsoleHandler` writes to stderr:

~~~text
INFO auth result=DENIED user=a***@example.test reason=OTHER
INFO payment result=REJECTED card=****1111
INFO credential_present=true
~~~

**Standard output (stdout):** empty. Exit code: `0`.

Explanation:

- `maskEmail(...)` allows only a small subset of ASCII addresses for demonstration; if the input does not match, it returns `[REDACTED]` instead of attempting to print the original value. This is **not** a full email syntax validator or a Unicode/internationalized email masker.
- `maskCard(...)` checks for a 12–19 digit string—**it does not validate card numbers or perform a Luhn check**—and keeps the last four digits. In real systems, use last4 only when policy permits; never log CVV/PIN.
- `testSecret` is used only to derive the `credential_present` boolean; the secret string itself is never placed into `LogRecord`.
- `safeReason(...)` accepts only `INVALID_INPUT`. Unrecognized strings, including strings containing newline characters used for log injection, are mapped to `OTHER`.
- JUL's `Formatter.formatMessage(event)` properly formats `{0}`, `{1}`, and `{2}` placeholders. The formatter does not mask automatically; **the data passed in has already been sanitized**.
- `LOG.setUseParentHandlers(false)` avoids duplicate logging through the root handler in the demo; it is not a security control replacing sink governance.

**Example boundary:** a masked email still reveals the first character and domain. If the domain or identity is unnecessary, policy may replace it with `[REDACTED_EMAIL]` entirely. For card numbers, systems should generally **never pass a full PAN into service logging** in the first place; this example only illustrates the masking rule clearly.

## 7. API Design for Sensitive Fields: Deny by Default

Instead of returning `toString()` from a DTO containing all attributes, create a log-event descriptor class with a **fixed list of fields**:

~~~java
// Illustration of an internal schema independent of any logging framework.
record LoginAuditView(
        String eventCode,
        String result,
        String reasonCode,
        String correlationId,
        boolean credentialPresent) {}
~~~

At the application layer, convert business objects into `LoginAuditView` using a controlled mapping. **Do not** add `password`, `accessToken`, or `rawHeaders` to this record. If a new field is added to the domain DTO, it will not automatically slip into the approved log schema.

In structured logging tools, emit only the fields of `LoginAuditView` or a validated allowlist map. When data cannot be classified, choose **not to log** rather than serializing everything and hoping regex will hide it all.

Critical edge cases:

- `null`, malformed, or oversized input: return a sentinel such as `[REDACTED]` or omit the field.
- Masking failure: **fail closed** (do not log raw data) and increment a safe metric; never write `catch (Exception e) { return raw; }`.
- Input data must be size-bounded to protect against CPU-heavy regexes or log amplification.
- For mutable objects processed by an async logger, take a snapshot of safe fields at event time; do not pass the entire sensitive object onto the queue.

## 8. Common Leak Locations Beyond the Message

Masking the message while ignoring the following sources can still leave you exposed:

| Source | Risk Example | Mitigation |
| --- | --- | --- |
| **Throwable.getMessage()** | HTTP client exception containing a URL with a token; SQL exception containing a query | Log error code + exception class; restrict stack traces to controlled, vetted channels |
| **Suppressed/cause chain** | Secret information appears in nested exceptions | Evaluate the entire chain/stack trace under policy |
| **MDC / ThreadContext** | `MDC.put("email", rawEmail)` exposes it on every event | Allow only correlation IDs or already-masked attributes |
| **HTTP headers** | Authorization, Cookie, Set-Cookie, X-API-Key | Denylist secret headers outright; better yet, allowlist safe headers |
| **URL/query string** | `?access_token=...`, email in query | Log a route template without query parameters instead of the full URI |
| **HTTP body** | Passwords, OTPs, documents, PII | Do not log bodies by default; debugging requires a dedicated environment and approval workflow |
| **Database/SQL** | Bind parameters or JDBC URL with credentials | Log error code, statement identifier, duration; omit raw bind values |
| **JSON encoder** | May serialize more fields than `PatternLayout` | Define a schema, exclude fields, and test actual JSON output |
| **Exception renderer** | Layout appends stack trace even when pattern only specifies `%msg` | Verify exact output when a `Throwable` is present |
| **Access logs, proxy/ingress** | Written outside Java application code | Check configuration at the web server/gateway/collector |

Do not fix just one place and conclude the entire pipeline is safe. Another appender—especially audit, debug, console, or a secondary exporter—may still receive raw records.

## 9. JUL: Custom Formatter/Filter and Limitations

`java.util.logging` consists of:

- `Logger` creates a `LogRecord` from a message, parameters, and a `Throwable`.
- `Filter.isLoggable(LogRecord)` decides whether the record is allowed to proceed.
- `Handler` receives the record, uses `Formatter.format(LogRecord)` to produce text, and writes to a sink.
- `LogRecord.getMessage()`, `getParameters()`, and `getThrown()` can contain sensitive data from the start.

**Note:** `Filter` has a boolean-returning interface (allow/deny), not an API designed to transform or strip individual fields inside a record. If your goal is to mask a field, it is better to **sanitize before calling `Logger.log`** or write a well-scoped custom formatter/handler.

The example in section 6 uses:

~~~java
LOG.log(Level.INFO, "auth result={0} user={1} reason={2}",
        new Object[]{"DENIED", maskEmail(email), safeReason(reason)});
~~~

This is an illustrative line assuming a `reason` variable declared elsewhere in the program; the principle is that **safe values are produced before becoming log arguments**. A custom `Formatter` can redact message text before output, but it must account for `LogRecord.getThrown()` and untouched parameters. If multiple handlers exist, an unmasked handler can still write the raw data.

JUL's `Formatter.formatMessage(record)` only formats; it is not a tool to prevent secret leaks. Using `record.getMessage()` instead of `formatMessage(record)` may skip parameters, but **does not make the event safe**: the raw data is still inside the record.

## 10. SLF4J and Logback: Prefer Masking in Application Code

SLF4J is a facade; the actual backend determines the layout and output destination. For applications using SLF4J + Logback:

~~~java
// Illustrative snippet; LOG and the variables are already declared.
LOG.info("login result={} email={} errorCode={}",
        safeResult, maskEmail(email), safeErrorCode);
~~~

The `{}` placeholder only passes arguments separately and defers formatting. It **does not automatically strip secrets**. The following call can still leak:

~~~java
// Avoid: the backend still receives the raw token when INFO is enabled.
LOG.info("Authorization token={}", rawToken);
~~~

If using the **SLF4J 2.x Fluent API**, you can attach safe fields:

~~~java
LOG.atInfo()
        .addKeyValue("eventCode", "LOGIN_DENIED")
        .addKeyValue("reasonCode", safeErrorCode)
        .addKeyValue("userRef", maskedUserRef)
        .log("login denied");
~~~

This snippet runs only when the project uses SLF4J 2.x and the logger and corresponding variables are initialized. Whether `addKeyValue` fields are printed to the log depends on the encoder/layout. Do not pass `rawToken` or unprocessed PII into the builder.

### Logback PatternLayout: A Limited Second Line of Defense

Logback supports the `%replace(...)` conversion; for example, a **supplemental masking layer** only for messages matching `token=...`:

~~~xml
<!-- Fragment inside a Logback appender encoder; test against your running version. -->
<pattern>%d %-5level %logger - %replace(%msg){'(?i)(token=)\S+', '$1[REDACTED]'}%n</pattern>
~~~

If the message contains `token=sample_value`, the pattern is intended to replace the matched value with `token=[REDACTED]`.

**This is not a comprehensive leak-prevention mechanism:**

- Regex catches only **known patterns** in the selected string portion; it does not cover JSON objects, new key names, escaped/Unicode variants, or emails in other fields.
- `%msg` is only the message. Exceptions, stack traces, MDC, or fields emitted separately by an encoder are **not necessarily masked**.
- Logback may append exception output depending on the pattern/layout; you must test events containing a `Throwable`, not just messages.
- Running regex on every log line adds overhead; a poorly written pattern can cause performance issues, especially on very long messages.
- Sinks using different encoders, such as a JSON encoder, need corresponding policies of their own.

Do not write a custom `PatternLayout` that triggers `getFormattedMessage()` or `toString()` on a payload **before masking**, and then assume the data never existed in the logging system. The goal remains eliminating secrets at the source.

## 11. Log4j 2: PatternLayout, JSON, and Filtering Layers

With the Log4j 2 API, parameterized calls also **do not mask automatically**:

~~~java
// Illustrative snippet; requires the Log4j 2 API and an initialized LOG.
LOG.warn("login rejected userRef={} reason={}",
        maskedUserRef, safeReasonCode);
~~~

Log4j 2 `PatternLayout` supports `%replace{pattern}{regex}{substitution}`. Example fragment:

~~~xml
<PatternLayout pattern="%d %-5p %c - %replace{%msg}{(?i)(token=)\S+}{$1[REDACTED]}%n"/>
~~~

The pattern above only illustrates replacing a `token=...` pattern in the **message**. Log4j 2 also supports `RegexReplacement` at the `PatternLayout` level applied to the layout's formatted output string, but you should not conclude that all leak paths are blocked by it. You must test the exact encoder, exception rendering, MDC, markers, arguments, and extra fields.

When schema-based JSON logging is needed, Log4j 2 recommends **JSON Template Layout** for structured output. With `JsonTemplateLayout`, you should **explicitly select allowed resolvers/fields** and inspect the resulting JSON file; do not enable serializing entire objects or exception messages containing secrets just because the event is JSON. The corresponding `log4j-layout-template-json` dependency is required when using this layout.

Log4j 2's `DENY` filter can block **an entire event**, but it cannot mask a single field out of the box. The rule "must not contain sensitive data" belongs to schema design and the redaction pipeline, not a level-based threshold filter.

## 12. MDC, ThreadContext, and Safe Correlation

MDC (in SLF4J/Logback) and `ThreadContext` (in Log4j 2) attach request metadata across multiple log events. This is a frequently overlooked leak point:

~~~java
// Avoid: email/token follows every log event on the current thread.
MDC.put("email", rawEmail);
MDC.put("token", rawToken);
~~~

Replace with a less sensitive or already-sanitized identifier:

~~~java
// Illustration in an app using SLF4J.
MDC.put("requestId", safeRequestId);
try {
    runBusinessLogic();
} finally {
    MDC.remove("requestId");
}
~~~

Variables/methods must be declared in your application, and `safeRequestId` must be validated for format, length, and origin. Do not treat a UUID or correlation ID as strictly public data; it still allows linking multiple events together.

With thread pools, coroutine/reactive workflows, or virtual threads, manage **context propagation scope** properly. Avoid letting context from one request leak into the next due to forgetting to remove/clear it. Do not call `MDC.clear()` indiscriminately if you do not own the entire thread context; you may wipe information managed by another framework.

In Log4j 2, apply the same rules to `ThreadContext.put/remove`. If a JSON backend automatically includes all MDC entries in its output, every value you put into MDC must be treated as **potentially appearing in logs**.

## 13. Stack Traces and Exceptions: Hard-to-Spot Leak Sources

Exception messages often contain source data:

~~~java
// Avoid sending unvetted error objects to a public/general log channel.
LOG.error("HTTP request failed", ex);
~~~

This is an illustrative SLF4J/Log4j 2 snippet. When `ex.getMessage()` contains a URL, token, SQL bind values, or a request body, the renderer may print that information. The `cause` chain and `suppressed exceptions` can carry similar data.

Choose an approach appropriate to your security level:

- **General channel:** log event code, error category, HTTP status, validated request identifier, and an allowlisted reason classification.
- **Restricted investigation channel:** when stack traces are genuinely needed, allow them by policy, use dedicated protection/retention controls, and test full exception rendering.
- **Do not convert an unvetted exception to text and mask it with a single regex**, because stack traces can span multiple formats and cause layers.
- **Do not create a new exception containing a copy of a secret** in its message just to make debugging easier.

Dropping stack traces completely is not always reasonable: it can destroy investigative evidence. The solution is channel tiering, data-type control, and access control; when needed, build a safe error DTO for general logs.

## 14. Log Injection: Keep Separate from Masking

**Log injection/forging** occurs when an untrusted value contains newlines or control characters that produce forged log records:

~~~text
reason=INVALID_INPUT
ERROR admin authenticated successfully
~~~

If user input is concatenated directly into a single-line log file, a human reader or pipeline parser may misinterpret this as two separate events. Masking sensitive data and preventing log injection **are two distinct requirements**.

Countermeasures:

1. For statuses and reason codes, use an **allowlist enum/code**. The Java 17 example returns `OTHER` for unrecognized input, never forwarding `\n` to the log.
2. For text fields that must be stored, use a structured encoder and sanitize/escape control characters for the target format; test CR, LF, tab, NUL, and unusual Unicode.
3. Bound field length to prevent log amplification and expensive regex evaluation.
4. Do not rely on `String.replace("\n", "")` as the sole fix across all formats: CR, other control characters, encodings, and structured data remain.
5. For JSON, use a real JSON encoder instead of hand-concatenating quoted strings; JSON escaping **does not** mean secrets are redacted.

The `safeReason` method in the example accepts only the exact value `INVALID_INPUT`; therefore, `"INVALID_INPUT\nERROR forged"` is mapped to `OTHER`. The business intent is still recorded without injecting a fake log line.

## 15. Regex Masking: When to Use It and Where Its Limits Are

Regex is often useful as **defense in depth** for relatively stable patterns, such as `token=...` in logs from a third-party library that is hard to modify. However, regex should not be used as the primary mechanism for all secrets.

Difficult cases:

- Different key names: `accessToken`, `auth`, `Authorization`, `apikey`, `api_key`, and case variants.
- Secrets inside JSON that are escaped, base64-encoded, URL-encoded, or split across lines.
- Values in fields whose data type is not plain message text.
- Emails/phone numbers with Unicode, country codes, punctuation, and international formats.
- Secrets inside a **Throwable**, MDC, user-agent, SQL, headers, or object `toString()`.
- Regexes matching benign strings (destroying investigative evidence) or missing secrets due to format changes.
- Regexes suffering from catastrophic backtracking on long inputs.

If regex is used to mask a pattern, build **positive** (must mask), **negative** (must not over-mask), and **adversarial** (newlines, escaped, encoded, size limits) test cases. Never accept "one regex masks all sensitive data."

If a key/value genuinely holds a credential, the safer choice is **not logging that field at all** rather than masking its prefix or suffix.

## 16. Structured Logging and Ingest Policy

A safe JSON event might look like this:

~~~json
{
  "eventCode": "LOGIN_DENIED",
  "result": "DENIED",
  "reasonCode": "INVALID_CREDENTIALS",
  "requestId": "req-7f2a",
  "credentialPresent": true
}
~~~

**Do not** assume this event is completely harmless: the request ID can still be correlated with a user in another system; appropriate access controls and retention are still required.

When a pipeline has multiple layers:

- **Application:** emit events using an allowlist. Do not place secret fields into MDC or JSON arguments.
- **Encoder/formatter:** configure it to emit selected fields with standard formatting and escaping. If redaction is needed, verify parts outside the message.
- **Agent/collector:** enforce ingest policies, adjust exports, restrict viewing of any remaining secrets/PII; add metrics and alerts for rule violations.
- **Index/storage:** encrypt in transit and at rest, enforce read access controls, audit access, and apply retention and on-demand deletion.
- **Dashboard/export:** ensure UI masking is not the sole safeguard; raw data in storage still needs handling.

A collector may receive old files or records sent by applications before an upgrade. Therefore, you must account for **historical data** in indexes, archives, and backups when updating policies.

## 17. Testing Masking: Use Synthetic Data and Assert No Leaks

A high-quality test does not only check `maskEmail`; it verifies **the actual full output of the appender/encoder**.

| Test | Synthetic Data | Expectation |
| --- | --- | --- |
| Valid email per demo | `alice@example.test` | `a***@example.test` or full redaction per policy |
| Malformed email | `not_an_email` | `[REDACTED]`, no raw output |
| 16-digit test card | `4111111111111111` | `****1111` if policy allows last4 |
| Invalid card string | `12-34-not-a-card` | `[REDACTED]` |
| Synthetic token | `TEST_SECRET_DO_NOT_LOG` | **Must not appear in any field or stack trace** |
| Reason with newline | `INVALID_INPUT\nERROR forged` | No forged log line appears |
| HTTP request | Authorization/Cookie/query with fake secret | Emits only method, route template, status, duration |
| Throwable | Message/cause containing secret sentinel | Not leaked in emitted stack trace |
| MDC | Secret in prior context | Absent from subsequent events or threads |
| JSON encoder | Unexpected field or nested object with secret | Dropped by allowlist or fails validation |
| Async appender | Snapshot and background logging | No raw sensitive object passed onto the queue |
| Multiple sinks | Console, file, network, audit | Every destination has policy-compliant protection |

Use a **highly distinctive synthetic sentinel** in tests, such as `TEST_SECRET_DO_NOT_LOG`, and assert that the string does not appear in the final text or JSON. Use fake emails on the `.test` domain and public test card numbers in tests—never copy real secrets from production.

For SLF4J/Logback integration tests, use an in-memory test appender and inspect every field of `ILoggingEvent` or the encoder output; checking only `getFormattedMessage()` while ignoring `getThrowableProxy()` and MDC leaves the test incomplete.

For Log4j 2, test the JSON event after layout execution as well, because `PatternLayout` and `JsonTemplateLayout` emit data differently. Also run smoke tests from the application to the collector to verify ingest layers.

A CI suite should fail if a secret sentinel appears in any output, while also verifying that valid events still retain enough monitoring information—avoiding "security by turning off all logging."

## 18. HMAC/Pseudonym Techniques for Controlled Correlation

Sometimes you need to correlate multiple logs belonging to the same subject without recording the original email or identifier. When the purpose is legitimate and data processing is authorized, you can consider a **HMAC**-based pseudonym:

~~~text
Internal subjectId
   -> normalize input and purpose
   -> HMAC with environment-specific secret key
   -> encoded pseudonym (length-bounded by design)
   -> log pseudonym, eventCode, status
~~~

This is an **architecture diagram**, not production-ready code. You must define key access permissions, entropy sources, standard algorithms, key rotation rules, correlation stability, and cross-environment linkability. Never store the HMAC key in source code, logged configuration, or alongside the same event.

- HMAC resists offline guessing better than an unkeyed hash for low-entropy values.
- Pseudonymized data may still fall under personal data regulations due to linkability.
- Each service can use a different key/scope to limit unnecessary cross-service correlation.
- When keys rotate, the same subject may produce a different code; you need an operational plan for that.
- If correlation is not needed, **omitting the identifier altogether** is usually better than creating a pseudonym.

Do not invent homegrown "encryption" using Base64 or substituting a few characters; Base64 is a trivially reversible encoding, not masking or encryption.

## 19. Performance, Async Logging, and Handling Masking Failures

A masking rule may run on every log event. Under high load, monitor both **cost** and **safety**:

- Prefer transformations driven by **schema and field type**, rather than running many complex regexes over full text.
- Avoid building stack traces or serializing full requests only to redact them afterward.
- Do not pass an object containing secrets to an async logger expecting a worker thread to mask it before it leaves the process; queues, debug dumps, and other appenders can still observe the object.
- For events that cannot be masked per policy, choose to **drop the field or drop the non-essential event**—do not log the raw value to "avoid losing logs."
- A masking failure is an operational signal: increment a secret-free metric, alert, and investigate on an authorized channel.
- Never write an error handler like `catch(Exception ex){ log.error("mask failed raw={}", raw); }`; the error-handling branch itself can leak the data.
- Benchmark with realistic traffic and backends: throughput, latency, GC, drop rate, redaction coverage, and false positive/negative rates.

If a backend has multiple destinations, a misconfigured appender or bypassed filter can still expose data. Reviews must account for every event path as well as backup and export mechanisms.

## 20. Responding When a Secret Has Already Landed in Logs

Masking only protects **future records**. When a real token or personal data is discovered in logs, treat it as a security incident:

1. **Contain the spread:** disable or fix the log source and tighten access permissions appropriately; do not re-print the token to "verify" it.
2. **Assess the scope:** timeline, environments, files/indexes/collectors, log viewers, exports, and backups that may hold raw copies.
3. **Revoke/rotate credentials** if the secret is active; check for abnormal usage through a secure channel.
4. **Handle existing copies:** plan deletion or isolation based on retention, system capabilities, and evidence/compliance requirements; do not delete haphazardly and destroy incident evidence.
5. **Follow notification procedures:** coordinate with security/privacy teams and applicable legal requirements.
6. **Prevent recurrence:** add regression tests, linter/config reviews, and checks on library and collector logging.

Do not consider masking a value on the dashboard as resolving the incident if the raw data still exists in files, indexes, exports, caches, or archives.

## 21. Design and Code Review Checklist

1. Are sensitive fields classified and "allowed to log" defined by purpose?
2. Are passwords, tokens, private keys, cookies, and authentication credentials **prohibited from logging** rather than partially masked?
3. Do logs contain only **allowlisted event codes, statuses, error codes, correlation IDs**, and schema-defined fields?
4. Is there any code logging entire requests, responses, DTOs, headers, or exceptions without evaluating their inner fields?
5. Does source masking handle nulls, malformed inputs, Unicode, oversized data, and failures using a fail-closed approach?
6. If email or last4 is logged, is exposing the remaining portion genuinely necessary and permitted by policy?
7. Have messages, arguments, MDC, `Throwable`, suppressed causes, JSON fields, access logs, and all appenders been checked?
8. Is backend regex only a secondary defense layer, or is it currently the sole measure?
9. Are there tests with synthetic sentinels asserting they never appear at the final sink?
10. Are there tests for CR/LF injection, JSON escaping, data truncation, and false positives?
11. Are stored logs protected with TLS, encryption at rest, RBAC, access auditing, retention, and export controls?
12. If a secret leaks, are incident response, credential rotation, copy remediation, and regression test procedures in place?

## 22. Self-Check Questions

1. Why is `logger.info("request={}", request)` still dangerous even with parameterized logging?
2. Compare **not logging**, **email masking**, **tokenization**, and **HMAC pseudonymization** in terms of recoverability/linkability.
3. Why does the regex `token=\S+` fail to protect an `Authorization` header in JSON or `Throwable.getMessage()`?
4. Does masking `%msg` in Logback/Log4j 2 guarantee that stack traces and MDC are clean?
5. How many events can `MDC.put("email", rawEmail)` affect?
6. Why shouldn't you log a raw exception if it contains an HTTP URL with credentials?
7. How is the string `INVALID_INPUT\nERROR forged` handled in the Java 17 example?
8. If masking fails, is returning the raw data to avoid losing logs safe?
9. Why does directly hashing an email with SHA-256 still carry re-identification risk?
10. A token leaked into logs yesterday; does adding masking today fix all existing copies?
11. When can last4 be used, and when must the entire card number be redacted?
12. Why must assertions check the actual encoder/collector output, not just a single masking function?

**Hints:** (1) the object may contain secrets and the backend will render it; (2) they differ in information exposure and linkability; (3) regex inspects only a specific pattern/string; (4) no; (5) many events sharing the same context; (6) exception messages/causes can leak secrets; (7) it is mapped to `OTHER`; (8) it must fail closed; (9) small value sets are easy to brute-force; (10) no, historical data must be addressed; (11) according to purpose and policy; (12) each sink may encode data differently.
