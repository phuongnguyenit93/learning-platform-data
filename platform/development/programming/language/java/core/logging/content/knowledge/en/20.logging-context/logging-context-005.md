# Operation Context in Java Logging

## 1. What Is Operation Context?

**Operation context** is the set of information describing **which business or technical operation is currently being executed** when a log event is emitted. When reading a log line, we do not just want to know "an INFO/ERROR occurred"; we also want to answer:

- What operation is being performed: creating an order, processing a payment, syncing data, handling a message, or running a batch job?
- Which execution instance of that operation is this?
- Is this operation a sub-step of a larger operation?
- Which request/job/workflow does it belong to, and which business entity is involved?
- Which step has started, completed, failed, or been retried?
- How long did it take, what was the outcome, and can it be linked to the corresponding trace/metrics?

Example of logs **without operation context**:

```text
INFO  | started
INFO  | reserved stock
WARN  | payment retry
INFO  | completed
```

If multiple requests run concurrently, it is difficult to determine whether these four lines belong to the same checkout or four different tasks.

Example of logs **with operation context**:

```json
{"level":"INFO","operation":"checkout","operationId":"op-17","requestId":"req-42","event":"operation_started"}
{"level":"INFO","operation":"reserve_inventory","operationId":"op-18","parentOperationId":"op-17","requestId":"req-42","event":"stock_reserved"}
{"level":"WARN","operation":"checkout","operationId":"op-17","requestId":"req-42","event":"payment_retry","attempt":2}
{"level":"INFO","operation":"checkout","operationId":"op-17","requestId":"req-42","event":"operation_finished","outcome":"SUCCESS","durationMs":30}
```

These JSON lines are **sample data**, not output automatically generated by JUL/Logback. They illustrate the idea: the same `operationId` links events of one operation; `parentOperationId` shows that the reserve step belongs to checkout; `requestId` links back to the initial request.

**Operation context is not a single standard Java class.** It is a data model and usage convention of the application. In Java code, it can be represented as an immutable record, explicit method parameters, SLF4J MDC, Log4j 2 Thread Context, or telemetry context, depending on the architecture.

## 2. Distinguishing Commonly Confused Context Types

A Java application can have multiple layers of identifiers:

| Concept | Question to answer | Example |
|---|---|---|
| **Operation name** | What kind of work is the program doing? | `checkout`, `reserve_inventory` |
| **Operation ID** | Which specific execution of the operation is this? | `op-17` |
| **Parent operation ID** | Which parent operation spawned this operation? | `op-17` is the parent of `op-18` |
| **Request ID** | Which HTTP request did this processing flow originate from? | `req-42` |
| **Job/workflow ID** | Which background task is being executed? | `job-104` |
| **Business ID** | What is the related business entity? | `orderId=ORD-7` |
| **Trace ID** | Which spans belong to the same distributed trace? | Value per tracing convention |
| **Span ID** | Which specific span within the trace is this? | Value per tracing SDK |
| **Attempt** | Which retry attempt is this? | `attempt=2` |
| **Event name** | What just happened inside the operation? | `payment_retry` |
| **Outcome** | Did the operation succeed, fail, or get cancelled? | `SUCCESS`, `FAILED`, `CANCELLED` |

**Do not use these IDs interchangeably without intentional design.**

- A single HTTP request can trigger **multiple operations**.
- An operation can run **without an HTTP request**: cron jobs, message consumers, batch jobs, or scheduled tasks.
- A business order can go through **multiple different operations** over several hours.
- An operation can continue across multiple services and messages; the original `requestId` may no longer exist.
- `traceId` is the ID of a trace; `operationId` is the ID of an operation in the application model. They can be linked, but they are **not the same by default**.
- A nested operation can have its own ID and a `parentOperationId` pointing to the parent operation.

A good schema should describe **the meaning and lifecycle of each ID**, not just standardize key names.

## 3. What Does Operation Context Serve?

### 3.1. Correlating multiple log lines of a single execution

Suppose checkout has five steps: validating data, reserving inventory, authorizing payment, persisting the order, and sending confirmation. If all of them log with `operationId=op-17` or a clear parent relationship, operators can reconstruct the flow without having to match messages based on line order.

### 3.2. Defining operation boundaries

Events with clear names:

```text
operation_started
inventory_reserved
payment_authorized
order_persisted
operation_finished
```

show where the progress is and which steps have completed. However, **not every step needs to be logged at INFO** in every system: high-load systems may need DEBUG for normal steps, INFO for significant state transitions, and ERROR at the responsible boundary when a task fails.

### 3.3. Attaching duration and outcome

A completion event can include `outcome=SUCCESS`, `durationMs=30`, and `operationId=op-17`. This information helps investigate slow tasks, but a log event **does not replace latency metrics**. If you need accurate p95/p99, use histograms/metrics with proper operation dimensions, because logs can be filtered, sampled, or dropped when a collector fails.

### 3.4. Analyzing errors in asynchronous systems

When processing moves from a request thread to an `ExecutorService` or message queue, context helps identify which operation the worker events still belong to. However, **there is no automatic context propagation mechanism shared across all APIs and backends**; an explicit mechanism is required.

## 4. Designing Fields for Operation Context

A sample JSON log:

```json
{
  "timestamp": "2026-11-09T08:15:03.125Z",
  "level": "INFO",
  "service": "orders-api",
  "logger": "com.example.orders.CheckoutService",
  "event": "payment_authorized",
  "operation": {
    "name": "checkout",
    "id": "op-17",
    "parentId": null
  },
  "requestId": "req-42",
  "orderId": "ORD-7",
  "outcome": "SUCCESS",
  "durationMs": 18
}
```

This is an **illustrative schema**, not a mandatory one. Real systems might use `operation.name`, `operation_id`, `operationId`, or a nested object structure, but it must be consistent and compatible with the collector.

Fields should follow these rules:

1. **Stable, low-cardinality operation names**: `checkout` instead of `checkout_order_ORD-7`.
2. **Operation ID independent of the message**: a clear field value, not requiring regex extraction from text.
3. **Parent identifier can be null** for root operations; do not fabricate a parent.
4. **Event name describes what happened**, such as `payment_authorized`, not just `"done"`.
5. **Outcome has a standardized vocabulary**: `SUCCESS`, `FAILED`, `CANCELLED`, `TIMEOUT`, etc.; define the meaning of each value.
6. **Explicit duration unit** such as `durationMs`; should be a numeric type.
7. **Do not embed dynamic IDs in field names**; use an `operationId` field with a value instead of a key like `op_17`.
8. **Do not stuff PII/secrets** into the context just because it persists throughout the operation.

If a service operates across multiple APIs, document and test the schema rather than relying on word-of-mouth conventions.

## 5. Operation Lifecycle: Start, Intermediate Steps, Completion

An operation typically has a lifecycle:

```text
operation_started
       |
       v
  step_started?  ---> step_failed? ---> retry?
       |
       v
  step_completed
       |
       v
 operation_finished  [SUCCESS]
       |
       +---------- or operation_failed [FAILED]
       +---------- or operation_cancelled [CANCELLED]
```

This diagram is conceptual. Not every operation has the same number of steps, and there is no need to emit a log line for every transition in a very high-throughput system.

### 5.1. Logging events at clear boundaries

When starting:

```json
{"operation":"checkout","operationId":"op-17","event":"operation_started","outcome":"STARTED"}
```

When a step completes:

```json
{"operation":"reserve_inventory","operationId":"op-18","parentOperationId":"op-17","event":"inventory_reserved","outcome":"SUCCESS","durationMs":12}
```

When the root operation finishes:

```json
{"operation":"checkout","operationId":"op-17","event":"operation_finished","outcome":"SUCCESS","durationMs":30}
```

**Do not log `operation_finished SUCCESS` unconditionally in a `finally` block.** If an exception, cancellation, or timeout occurs, the outcome must reflect the actual result. You can log a completion event with `outcome=FAILED` and exception details, or use an `operation_failed` event according to your chosen schema.

### 5.2. Avoiding duplicate logs across layers

For example, a database error is logged at ERROR in the repository, service, and controller, all with the same `operationId`. If three layers log the same exception, dashboards may count three ERRORs even though only one operation actually failed.

Define a responsible boundary:

- Lower layers return/propagate errors while preserving the cause, adding contextual information when appropriate.
- The layer that decides the operation's outcome logs the final error once, unless there is a reason to track individual retry steps separately.
- If logging retry attempts, use `attempt`, `step`, and a distinct event name so readers do not confuse them with the final failure.

## 6. How to Hold Operation Context in Java

Common strategies:

| Strategy | Pros | Limitations |
|---|---|---|
| **Explicit parameter passing** | Clear data flow, easy to test, thread-independent | Adds parameters across many layers |
| **Immutable record/object** | Clear snapshot, prevents implicit mutation | Still needs a way to reach logging call sites |
| **Scoped `ThreadLocal`** | Convenient for synchronous code on the same thread | Does not automatically propagate to thread pools or other tasks |
| **SLF4J MDC** | Integrates with many patterns/encoders | Depends on backend/provider and propagation mechanism |
| **Log4j 2 Thread Context** | Integrates with Log4j 2 logging context | Specific API and semantics |
| **Tracing/telemetry context** | Correlates traces/spans via instrumentation | Does not automatically carry all business operation fields |

**Choose based on your purpose.** For critical business logic, explicit/immutable context reduces thread coupling; for multi-layer logging, MDC can serve as a convenience layer to display context without manually passing it to every logger call.

### 6.1. Why is immutable context usually safer?

If a mutable context map is shared across requests or between a producer and an async worker, one thread could modify `orderId` after an event has already been enqueued. The backend might read a different value from the one at the time the event occurred.

A Java `record` or immutable object created at the operation boundary fixes the IDs in place. However, when adding fields that hold mutable objects (lists, maps, entities), make appropriate snapshots/copies; a `record` itself does not make nested objects immutable.

### 6.2. Scope boundaries

A scope must have **clear open and close points**:

```text
Receive request / start job
    |
    +-- Create operation context
    +-- Open scope
    |       |
    |       +-- Log steps
    |       +-- Optionally open child scopes
    |       +-- Pass context explicitly to workers
    |
    +-- Close scope in finally / try-with-resources
    +-- Request thread returns to its previous state
```

If the scope is not closed, a thread pool can reuse a thread that still holds the `operationId` of an old request: logs of the subsequent request get tagged with the wrong ID. This is a **correctness and privacy** issue, not merely unreadable logs.

## 7. Standalone Java 17+ Example: Scoped Operation Context and Async Propagation

The following example uses only **JDK 17**, requiring no Maven or external libraries. It demonstrates:

1. An immutable `OperationContext` model as a `record`.
2. A scope using `ThreadLocal` that automatically **restores the previous context** via `try-with-resources`, even with nested operations.
3. A child step with its own `operationId` and `parentOperationId` pointing to the parent operation.
4. Passing an **explicit context snapshot** to an `ExecutorService`.
5. Attaching the snapshot to each `LogRecord` before the formatter outputs the log, preventing the formatter from reading the wrong thread's context.
6. Stable output without dynamic timestamps; durations are hardcoded **for illustration**, not actual measurements.

In production systems, SLF4J MDC or a tracing SDK can be used instead of a custom JUL event; this self-written example is intended to explain the principles.

### 7.1. Create `OperationContextDemo.java`

```java
import java.util.Objects;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.logging.ConsoleHandler;
import java.util.logging.Formatter;
import java.util.logging.Level;
import java.util.logging.LogRecord;
import java.util.logging.Logger;

public final class OperationContextDemo {
    private static final Logger LOG =
            Logger.getLogger("demo.OrderService");

    private static final ThreadLocal<OperationContext> CURRENT =
            new ThreadLocal<>();

    private record OperationContext(
            String name,
            String operationId,
            String parentOperationId,
            String requestId,
            String orderId) {
    }

    private static final class Scope implements AutoCloseable {
        private final OperationContext previous;
        private boolean closed;

        private Scope(OperationContext next) {
            previous = CURRENT.get();
            CURRENT.set(Objects.requireNonNull(next));
        }

        static Scope open(OperationContext context) {
            return new Scope(context);
        }

        @Override
        public void close() {
            if (closed) {
                return;
            }
            if (previous == null) {
                CURRENT.remove();
            } else {
                CURRENT.set(previous);
            }
            closed = true;
        }
    }

    private static final class EventRecord extends LogRecord {
        private static final long serialVersionUID = 1L;

        private final OperationContext snapshot;
        private final String outcome;
        private final long durationMs;

        EventRecord(
                Level level,
                String event,
                OperationContext snapshot,
                String outcome,
                long durationMs) {
            super(level, event);
            this.snapshot = snapshot;
            this.outcome = outcome;
            this.durationMs = durationMs;
        }
    }

    private static final class EventFormatter extends Formatter {
        @Override
        public String format(LogRecord record) {
            if (!(record instanceof EventRecord event)) {
                return record.getLevel().getName()
                        + " event=" + formatMessage(record) + "\n";
            }

            OperationContext context = event.snapshot;
            return record.getLevel().getName()
                    + " operation="
                    + (context == null ? "none" : context.name())
                    + " operationId="
                    + (context == null ? "-" : context.operationId())
                    + " parentOperationId="
                    + (context == null ? "-"
                                       : context.parentOperationId())
                    + " requestId="
                    + (context == null ? "-" : context.requestId())
                    + " orderId="
                    + (context == null ? "-" : context.orderId())
                    + " event=" + formatMessage(record)
                    + " outcome=" + event.outcome
                    + " durationMs=" + event.durationMs
                    + "\n";
        }
    }

    private static void emit(
            String eventName, String outcome, long durationMs) {
        EventRecord event = new EventRecord(
                Level.INFO,
                eventName,
                CURRENT.get(),
                outcome,
                durationMs);
        event.setLoggerName(LOG.getName());
        LOG.log(event);
    }

    public static void main(String[] args) throws Exception {
        LOG.setUseParentHandlers(false);
        LOG.setLevel(Level.INFO);

        ConsoleHandler handler = new ConsoleHandler();
        handler.setLevel(Level.ALL);
        handler.setFormatter(new EventFormatter());
        LOG.addHandler(handler);

        ExecutorService executor =
                Executors.newSingleThreadExecutor();

        try {
            OperationContext checkout = new OperationContext(
                    "checkout", "op-17", "-", "req-42", "ORD-7");

            try (Scope rootScope = Scope.open(checkout)) {
                emit("operation_started", "STARTED", 0);

                OperationContext inventory = new OperationContext(
                        "reserve_inventory",
                        "op-18",
                        checkout.operationId(),
                        checkout.requestId(),
                        checkout.orderId());

                try (Scope childScope = Scope.open(inventory)) {
                    emit("stock_reserved", "SUCCESS", 12);
                }

                // Child scope is closed: CURRENT is restored to checkout.
                OperationContext snapshot = CURRENT.get();

                Future<?> paymentTask = executor.submit(() -> {
                    // Thread pool does not automatically inherit the caller's ThreadLocal.
                    try (Scope workerScope = Scope.open(snapshot)) {
                        emit("payment_authorized", "SUCCESS", 18);
                    }
                });
                paymentTask.get();

                emit("operation_finished", "SUCCESS", 30);
            }

            // Root scope is closed: no operation context remains.
            emit("after_scope", "NONE", 0);
        } finally {
            executor.shutdown();
            LOG.removeHandler(handler);
            handler.flush();
            handler.close();
        }
    }
}
```

### 7.2. Compile and run

From the directory containing `OperationContextDemo.java`, using JDK 17 or later:

```bash
javac -encoding UTF-8 OperationContextDemo.java
java OperationContextDemo
```

**Stderr output produced by JUL `ConsoleHandler`:**

```text
INFO operation=checkout operationId=op-17 parentOperationId=- requestId=req-42 orderId=ORD-7 event=operation_started outcome=STARTED durationMs=0
INFO operation=reserve_inventory operationId=op-18 parentOperationId=op-17 requestId=req-42 orderId=ORD-7 event=stock_reserved outcome=SUCCESS durationMs=12
INFO operation=checkout operationId=op-17 parentOperationId=- requestId=req-42 orderId=ORD-7 event=payment_authorized outcome=SUCCESS durationMs=18
INFO operation=checkout operationId=op-17 parentOperationId=- requestId=req-42 orderId=ORD-7 event=operation_finished outcome=SUCCESS durationMs=30
INFO operation=none operationId=- parentOperationId=- requestId=- orderId=- event=after_scope outcome=NONE durationMs=0
```

No stdout output is produced by the program itself. The numbers `0`, `12`, `18`, and `30` are **fixed sample data for the lesson**, not actual machine timings. The formatter intentionally omits timestamps, thread names, and system details so the output can be verified deterministically; production systems need standard metadata and escaping.

### 7.3. Why does the example produce this output?

- `Scope.open(checkout)` attaches the root context `op-17` to the main thread.
- The child scope `reserve_inventory` attaches `op-18` with parent `op-17`. When the child scope closes, `Scope.close()` restores checkout **without clearing the root context**.
- Before submitting the task, the application captures `snapshot = CURRENT.get()`. The worker thread opens **its own scope** with that snapshot and cleans up after emitting the event.
- `paymentTask.get()` waits for the task to complete before emitting `operation_finished`; thus the five lines in the demo appear in a predictable order. With multiple tasks running in parallel, **there is no equivalent global ordering**.
- `emit(...)` creates an `EventRecord` containing an **immutable snapshot** at emission time. The formatter reads the record's snapshot rather than accessing the logging thread's `ThreadLocal`.
- After the root scope closes, `CURRENT.get()` is null; the `after_scope` event outputs `operation=none` and `-` for the IDs.
- `LOG.setUseParentHandlers(false)` prevents duplicate logging via parent handlers; `ConsoleHandler` writes to stderr by default.
- `ExecutorService.shutdown()` requests termination of the demo's worker pool. It does not guarantee that logs have been delivered to a production collector.
- The `Formatter` in this example only renders safe static IDs; for user-supplied strings, escaping or a structured encoder must be used to prevent log injection.

### 7.4. Why not use a global mutable context?

Suppose a static map is updated with `operationId` for each request. When two requests run concurrently, request A could log with B's ID. `ThreadLocal` avoids such sharing during synchronous execution on the same thread; an immutable record prevents modifying the snapshot's contents.

However, `ThreadLocal` does not automatically propagate to workers/tasks and does not replace explicit context attachment at message queue boundaries. The example demonstrates **capture beforehand, install in the worker, restore in finally**.

### 7.5. This is a mechanism example, not a production encoder

The text output in section 7 has `key=value` pairs but is not JSON with standardized fields. `EventRecord` is a custom class for the example; standard JUL does not automatically build an operation context map. In production, leverage:

- Logging APIs/backends that support structured arguments and MDC/Thread Context.
- JSON encoders/layouts with a clear schema.
- Tracing SDKs with official context propagation for traces/spans.
- Framework lifecycle/middleware/interceptors to open and close scopes consistently.

Do not build a custom complex logging framework if your existing backend and framework already handle these parts safely.

## 8. Operation Context in SLF4J MDC

**SLF4J MDC** (Mapped Diagnostic Context) allows putting key/value pairs into the thread's logging context according to the provider/backend mechanism. For example, Logback can read these values in a pattern or JSON encoder.

Illustration inside a method that has a `LOG` variable of type `org.slf4j.Logger`:

```java
import java.util.Map;
import org.slf4j.MDC;

Map<String, String> previous = MDC.getCopyOfContextMap();
try {
    MDC.put("operation", "checkout");
    MDC.put("operationId", "op-17");
    MDC.put("requestId", "req-42");

    LOG.info("event=operation_started");
    LOG.info("event=order_accepted orderId={}", "ORD-7");
} finally {
    if (previous == null) {
        MDC.clear();
    } else {
        MDC.setContextMap(previous);
    }
}
```

This is an **illustrative snippet**, not a standalone Java program. It saves the previous context, sets the keys, and then **restores the entire previous map** in `finally`. Restoring is useful when an operation nests inside a scope that already has a parent's MDC: calling `MDC.clear()` unconditionally could wipe out context that the outer layer still needs.

### 8.1. Logback PatternLayout reading MDC

Example of a simple `logback.xml`:

```xml
<configuration>
    <appender name="CONSOLE"
              class="ch.qos.logback.core.ConsoleAppender">
        <target>System.out</target>
        <encoder>
            <pattern>%-5level op=%X{operation} operationId=%X{operationId} requestId=%X{requestId} %logger{0} - %msg%n</pattern>
        </encoder>
    </appender>

    <root level="INFO">
        <appender-ref ref="CONSOLE"/>
    </root>
</configuration>
```

Here `%X{operationId}` reads the `operationId` key from MDC if the event/backend has that data. **Configuration does not generate `operationId` automatically**, and calling `MDC.put` does not guarantee every JSON encoder will automatically output MDC keys as JSON fields; always verify the actual encoder and schema.

**Distinction:** the JUL example in section 7 logs a `LogRecord` carrying a custom record. `SLF4J MDC` is a different API; do not copy `%X{operationId}` into JUL `SimpleFormatter` and expect JUL to understand it.

### 8.2. Nested MDC scopes require proper restoration

If the root scope has `operationId=op-17` and a child scope temporarily sets `operationId=op-18`, when the child scope closes, the root **must receive `op-17` back**. Simply removing the key can break the root correlation. Saving and restoring a snapshot at scope boundaries is one way to implement this.

With APIs like `MDC.putCloseable`, check your version's semantics and how nested scopes behave: **closing a single key does not automatically restore an overwritten previous value**. When complex nested context policies are needed, use a tested scope helper capable of full restoration.

### 8.3. MDC adapters depend on the provider

Not every SLF4J backend/provider implements MDC and async propagation in the same way. Some adapters provide full functionality, while others have no-op operations or do not include MDC in the output. Check the actual runtime provider, dependency tree, and active appender/encoder before concluding that operation context was "lost by MDC".

## 9. Propagating Context to ExecutorService, CompletableFuture, and Message Queues

### 9.1. Do not rely on ThreadLocal moving automatically

With:

```java
// Illustrates a false expectation; CURRENT/executor variables must be declared.
CURRENT.set(context);
executor.submit(() -> {
    // Do not assume CURRENT.get() == context on this thread.
    doWork();
});
```

`ThreadLocal` is data bound to the **current thread**, not automatically bound to every task. A thread pool may use a different thread, a reused thread, or the same thread in special executor cases; do not rely on such coincidence.

### 9.2. Capture -> install -> execute -> restore

For MDC, the same principle applies:

```java
// Snippet: executor and LOG already exist, along with SLF4J MDC.
Map<String, String> captured = MDC.getCopyOfContextMap();

executor.submit(() -> {
    Map<String, String> previous = MDC.getCopyOfContextMap();
    try {
        if (captured == null) {
            MDC.clear();
        } else {
            MDC.setContextMap(captured);
        }

        LOG.info("event=worker_step_finished");
    } finally {
        if (previous == null) {
            MDC.clear();
        } else {
            MDC.setContextMap(previous);
        }
    }
});
```

**Why save `previous` in the worker?** Because a thread in the pool might already carry context left behind by another task or set by the framework. The helper must avoid corrupting prior state and prevent subsequent requests from using the wrong `operationId`. However, if unexpected context is discovered on a worker thread, also investigate your propagation/lifecycle policy rather than treating restore as a cure-all for leaks.

With `CompletableFuture.supplyAsync`, `@Async`, reactive streams, or callbacks, execution can hop across different threads at each stage. Integrate with the appropriate framework/context propagation API; a single `ExecutorService` wrapper does not automatically cover every scheduler type.

### 9.3. Across service or message broker boundaries

`ThreadLocal` and MDC are **in-process** mechanisms and do not naturally cross HTTP/gRPC/message brokers. When an operation crosses to another service, pass **permitted, bounded metadata** in headers/envelopes or via standard tracing propagation.

Example of an illustrative message envelope:

```json
{
  "messageType": "PaymentRequested",
  "operationId": "op-17",
  "requestId": "req-42",
  "orderId": "ORD-7",
  "attempt": 1
}
```

The consumer can extract validated fields, open a new scope for its own step, and attach `parentOperationId` or the appropriate correlation relationship. **Never blindly trust IDs/context sent by external clients**: validate them, enforce size/character limits, and never let users determine security authorization based on `operationId`.

For distributed tracing, prefer framework/SDK-supported propagation mechanisms (such as trace context) instead of manually stuffing trace IDs into text strings. Business context like `orderId` is application-specific data and should not be broadcast everywhere unnecessarily.

### 9.4. Retries and Idempotency

A retry can keep the same **business operationId** to link attempts while adding `attempt=1/2/3` to distinguish them. In another architecture, each attempt is a child operation with its own ID and a shared parent. Both can be valid; what matters is documenting the **granularity of an operation**.

**An operation ID is not an idempotency key.** If an API must prevent duplicate transaction processing, it needs dedicated idempotency rules, state storage, and verification. Log correlation does not guarantee exactly-once processing.

## 10. Measuring Operation Duration Properly

To measure duration within the same JVM, use monotonic relative time such as `System.nanoTime()`, rather than taking the difference of `System.currentTimeMillis()` for short operations where immunity to clock adjustments is needed.

Example snippet:

```java
long startedNanos = System.nanoTime();
try {
    performOperation();
} finally {
    long elapsedNanos = System.nanoTime() - startedNanos;
    long durationMs =
            java.util.concurrent.TimeUnit.NANOSECONDS
                    .toMillis(elapsedNanos);
    // Emit event with durationMs and properly determined outcome.
}
```

`performOperation()` here is an undefined placeholder method, so this is not a standalone program. `System.nanoTime()` is suitable for measuring elapsed intervals within a single process, **not as an absolute timestamp to send over the network**. If an operation spans multiple services, use telemetry/tracing and measure at appropriate boundaries.

### 10.1. Encode outcomes explicitly

Do not do this:

```java
// Wrong if there is no error state handling:
try {
    performOperation();
} finally {
    LOG.info("event=operation_finished outcome=SUCCESS");
}
```

If `performOperation()` throws an exception, that line still logs SUCCESS. Track the state instead:

```java
String outcome = "FAILED";
long started = System.nanoTime();
try {
    performOperation();
    outcome = "SUCCESS";
} finally {
    long durationMs =
            java.util.concurrent.TimeUnit.NANOSECONDS.toMillis(
                    System.nanoTime() - started);
    // Emit outcome and durationMs using the appropriate event/schema.
}
```

The second snippet is still not standalone and requires a separate policy for cancellation/timeout. If a method can return a failure result **without throwing an exception**, the outcome must also be determined from that result rather than assuming completion means SUCCESS.

### 10.2. Do not measure using log line order

An async appender or collector may write logs later than when the event occurred. Computing duration from collector timestamps can include queue/network latency. Record duration at the operation boundary or use spans/metrics with proper elapsed-time semantics.

## 11. Structured Logging, JSON, and Operation Context

When the collector supports JSON, context should be top-level or structured fields:

```json
{
  "timestamp": "2026-11-09T08:15:03.125Z",
  "level": "ERROR",
  "service": "orders-api",
  "event": "payment_authorization_failed",
  "operation": "checkout",
  "operationId": "op-17",
  "requestId": "req-42",
  "orderId": "ORD-7",
  "outcome": "FAILED",
  "attempt": 3,
  "error": {
    "type": "java.io.IOException",
    "message": "gateway unavailable"
  }
}
```

This is an **illustrative** JSON example. It is not produced automatically just because code uses `MDC.put` or `LOG.info`.

### 11.1. Structured fields vs. text containing key=value pairs

A message like:

```text
operationId=op-17 event=payment_failed orderId=ORD-7
```

helps humans do rough text searches, but a collector may only see it as **a single message string**. If you want to query by `operationId` as a field, the encoder/logger API must emit it as a JSON field, or the collector must parse the text with explicit rules.

For example:

```json
{"message":"operationId=op-17 event=payment_failed orderId=ORD-7"}
```

is different from:

```json
{"operationId":"op-17","event":"payment_failed","orderId":"ORD-7"}
```

**Do not assume a JSON encoder automatically splits a message string into fields.** You must actively configure the source of structured attributes, MDC, the SLF4J fluent key-value API, or a backend-specific event model.

### 11.2. Do not cram the entire operation context into the logger name

Do not do this:

```java
// Anti-pattern: creating logger names per operation ID.
Logger logger = Logger.getLogger("checkout." + operationId);
```

`operationId` is dynamic per-event data, whereas a logger name is usually a stable package/class/category. Putting IDs into logger names increases the number of loggers, makes level configuration difficult, and can cause memory pressure.

Instead, use:

```java
// Illustrates a stable logger name:
Logger logger =
        Logger.getLogger("com.example.orders.CheckoutService");
```

and place `operationId` in the event/context separately.

## 12. Operation Context and Distributed Tracing: Related but Different

A **trace** describes the path of an operation across components, with **spans** representing individual units of work, parent-child relationships, and durations. Operation context can enrich logs with business data and link them to traces.

Example:

```text
HTTP request: req-42
    |
    +-- traceId = trace-...
    |
    +-- Operation checkout / op-17
           |
           +-- Span HTTP controller
           +-- Operation reserve_inventory / op-18
           |      +-- Span database query
           |
           +-- Span call payment service
           +-- Operation finalize_order / op-19
```

An operation does not have to match a single span 1:1: one operation may encompass multiple spans, or one span may encompass multiple application steps, depending on instrumentation.

**Do not fabricate a trace ID by generating an arbitrary string and claim you have distributed tracing.** Tracing requires context propagation, span lifecycles, sampling, timing, and a backend capable of linking the data. `operationId` is only one dimension of correlation.

In an observability system, you can typically:

- Search logs by `operationId` to view all business events.
- Search traces by `traceId` to inspect latency and span relationships.
- Link logs to spans when valid `traceId` and `spanId` are present.
- Use metrics grouped by `operation.name` and `outcome` to measure error rates and latency.

Do not put a **per-request unique `operationId`** into metric labels, as this creates high cardinality. For metrics, use operation names and low-cardinality label sets; for logs/traces, detailed IDs can be retained according to query and storage policies.

## 13. Nested Scopes, Concurrency, and Subtle Pitfalls

### 13.1. A child operation must not clear the parent operation's context

For example, checkout opens a scope, inventory opens a child scope, and then inventory closes. If inventory's close logic simply calls `CURRENT.remove()`, the root checkout loses its context. In the Java 17 example, `Scope.close()` restores `previous`, so the root context remains intact.

This also applies to MDC: when overriding keys, you must have a policy to restore previous values.

### 13.2. Context can leak on thread pools

Every execution path must clean up the scope, including exceptions and early returns. Use `try-with-resources` or `try/finally`; never write code that sets context at the start of a method and only clears it at the end of the happy path.

### 13.3. Do not share a mutable map across multiple tasks

A mutable context map passed by reference to a worker can be mutated while another task is still using it. Copy/snapshot the necessary values before submitting; distinguish between capture (copy) and reference sharing. An immutable record with `String` fields illustrates a safe choice.

### 13.4. Operation IDs can be lost at boundaries

When an event is pushed to Kafka/RabbitMQ or an HTTP request is sent to another service, the producer's `ThreadLocal` stays in the old JVM. The consumer must receive the context via message headers/envelope according to a contract, validate it, establish a new scope, and then clean up.

### 13.5. Virtual threads do not automatically propagate every context

Java introduced virtual threads in JDK 21, but that does not mean every context and MDC automatically propagates across async boundaries. Propagation behavior depends on the thread type, framework, and API. The demo uses Java 17 and a standard thread pool; when upgrading the JDK or switching frameworks, verify the supported context propagation policy rather than assuming it works.

### 13.6. Operation context must not depend on log ordering

Multiple producers/consumers, async appenders, or collectors can alter the order in which log lines appear. Business ordering should use operation/step IDs, timestamps, and sequence/attempt numbers where appropriate; do not infer causality solely from which line appears first in a file.

## 14. Exceptions, Retries, and Cancellation

When an operation fails, context must still be attached to the error event:

```json
{
  "level": "ERROR",
  "event": "operation_failed",
  "operation": "checkout",
  "operationId": "op-17",
  "requestId": "req-42",
  "outcome": "FAILED",
  "attempt": 3,
  "error.type": "java.net.SocketTimeoutException"
}
```

This is a sample, not output from `OperationContextDemo`.

Guidelines:

- Pass `Throwable` to the logger using the appropriate overload so the encoder preserves the stack trace/cause.
- If a retry is acceptable, log a `retry_scheduled` or `attempt_failed` event at an appropriate level; do not declare the entire operation FAILED while it is still retrying.
- Once retries are exhausted, the final completion event should reflect the **final outcome**.
- When cancelled or timed out, distinguish `CANCELLED`/`TIMEOUT` if the system needs to measure them separately.
- If an exception is logged at multiple layers, operators can mistake one failure for multiple failures; choose a boundary to log the final error.
- Avoid logging full request/response bodies and authentication data into the context in error paths.

SLF4J example:

```java
// Snippet: LOG is an SLF4J Logger, error is an actual Throwable.
LOG.error("event=operation_failed operationId={}", operationId, error);
```

The code above is only an **API illustration**; when structured `operationId` is needed, use MDC, key-value arguments, or an appropriate backend encoder rather than assuming a placeholder will become a JSON field. With JUL, use the `LOG.log(Level.SEVERE, "...", error)` overload to preserve the `Throwable` in `LogRecord`.

## 15. Security and Data Limits in Operation Context

Context tends to be attached to **every event in an operation**. If it contains a secret, that secret may appear hundreds of times across log files, queues, collectors, and backups.

**Do not put into operation context:**

- Passwords, API keys, bearer tokens, session cookies, or `Authorization` headers.
- Card numbers, credentials, or secrets from configuration.
- Full request/response payloads without a clear need.
- Personal data unnecessary for diagnostics or disallowed by policy.

**Prefer:** operation name, random/opaque IDs sufficient for tracing, status, outcome type, step, attempt, duration, error code, and permitted business identifiers.

Considerations:

- If `operationId` is derived from user input, it may contain newlines or control characters; use server-generated/validated IDs and escape via the serializer.
- JSON encoders escape syntax but **do not automatically mask PII or secrets**.
- Context headers arriving from the network must be validated for length, structure, and trustworthiness.
- Knowing an `operationId` must not grant a user access to another user's logs/operations; authorization is a separate mechanism.
- Retention and log access policies must match the sensitivity of the business identifiers stored.
- Never let request A's context leak into request B's logs due to forgetting to clear a thread pool.

## 16. Operations: What to Log, What to Measure?

An operation scope can emit many logs, but you should not log every state at INFO out of habit. Suggested guide:

| Situation | Logging/telemetry approach | Notes |
|---|---|---|
| Operation started | INFO or DEBUG depending on traffic | Include operation name/ID and timestamp |
| Normal intermediate step | DEBUG if high volume, INFO if significant | Avoid logging large payloads unnecessarily |
| Unusually slow step | WARN when exceeding a notable threshold | Include `durationMs` and operation name |
| Valid retry | WARN/INFO/DEBUG based on impact | Attach attempt and reason |
| Final operation failure | ERROR at the responsible boundary | Preserve Throwable and outcome |
| Operation completed | INFO if full workflow traceability is needed | Include duration and outcome |
| Aggregate error rate/latency | Metrics histograms/counters | Avoid `operationId` as a metric label |
| Cross-service call relationships | Distributed tracing | Requires official trace/span context |
| Mandatory audit | Durable audit/event store | Logs can be dropped, rotated, or deleted |

If you want **each operation to have exactly one summary record**, you can use an `operation_completed` event containing outcome, duration, attempt count, and error code. However, when errors span multiple layers or a request triggers multiple operations, define the granularity clearly.

### 16.1. Sampling and logging volume

At high traffic, logging `operation_started` and `operation_finished` for every request can generate massive volume. You can:

- Keep required ERROR/WARN events according to policy.
- Sample high-frequency success events when permitted.
- Use metrics to aggregate throughput and latency.
- During investigations, enable detailed logging for a specific operation/service within a controlled window.

Sampling must be designed so it does not lose mandatory audit evidence; also account for sampling when using logs to infer event counts.

### 16.2. Structured logs at the collector

When outputting JSON Lines, each log event should be a single JSON object on one physical line, with `operationId` as a field rather than hidden inside `message`. The collector needs to parse it properly and have an indexing/cost strategy. Even when events are serialized correctly, async queues/shippers can delay or drop logs, so having context does not create a delivery guarantee.

## 17. Common Pitfalls and Troubleshooting

| Symptom | Possible cause | How to fix |
|---|---|---|
| Worker logs are missing `operationId` | `ThreadLocal`/MDC does not automatically propagate to thread pools | Capture, install, and restore context in the task |
| Request B logs A's `operationId` | Context not cleared when thread is reused | Use `try/finally`; check middleware |
| Root loses ID when child operation closes | Cleared without restoring previous context | Use nested scopes with a previous snapshot |
| Multiple steps share dynamic logger names | Putting IDs in logger name instead of fields | Keep logger names per class, context per event |
| JSON has `operationId` but queries miss it | ID is embedded in the message string | Use structured fields / proper JSON encoder |
| `MDC.put` called but output is empty | Pattern/encoder doesn't read the key or provider doesn't support it | Check the actual MDC adapter/backend |
| Operation logged as SUCCESS despite throwing | `finally` unconditionally logs success | Track outcome across `try/catch/finally` |
| Retries counted as multiple failed operations | Not distinguishing attempts from final outcome | Attach `attempt`, `event`, and counting rules |
| Context lost across message broker | IDs not propagated via envelope/headers | Use a safe metadata contract |
| Context is right but trace doesn't link | `operationId` is not a trace/span ID | Use standard tracing context and correlation |
| Negative/weird duration on clock adjustment | Using wall-clock time for elapsed time | Use `System.nanoTime()` within the same process |
| Duplicate ERRORs appear | Logging the same exception at multiple layers | Pick a single responsible boundary |
| `operationId` causes high-cardinality metrics | Using dynamic IDs as metric labels | Only use low-cardinality operation name/outcome |
| Context contains tokens/PII | Putting all request fields into MDC | Restrict fields, apply redaction and retention |
| Logs appear out of business order | Async queues, multiple threads/collectors | Use timestamps, step IDs, and parent relationships |

### 17.1. Systematic debugging workflow

1. Identify the operation to inspect and its agreed `operation` name.
2. Check **a single raw event** at the emission source (before the collector) to see if `operationId` is present.
3. Check where the scope is opened, where it is closed, and whether there are error/early-return paths.
4. If the issue happens in a worker, verify capture/propagate/restore.
5. Verify whether the data was attached to `LogRecord`/MDC or only held in a local variable.
6. Check whether the formatter/encoder emits context as real fields.
7. Compare raw events against what the collector parsed/indexed, considering rotation, async queues, and schema.
8. Verify that `operationId` matches root/child relationships, `requestId`, and `traceId`.
9. Check for sensitive data exposure or context mixing across requests.

## 18. Self-Check Exercises

### Exercise A — Requests and operations are not the same

A request `req-42` triggers `checkout` and `send_confirmation`. Should they share one `operationId` or use two IDs?

**Hint:** if these are two operations with independent lifecycles/outcomes, you can use `op-17` and `op-19`, along with `requestId=req-42` or a correlation/workflow ID to link them. Do not use the request ID as the operation ID for every step if doing so loses the ability to distinguish operations.

### Exercise B — Nested scopes

Root `checkout/op-17` opens step `inventory/op-18`; when the child step finishes, MDC `operationId` disappears.

**Cause:** the child scope cleared the key without restoring the root. Fix by using a helper that saves/restores the previous MDC map or uses scoped immutable context.

### Exercise C — ExecutorService

A task running in a thread pool logs `operation=none` even though the caller set `ThreadLocal`.

**Cause:** `ThreadLocal` is only bound to the caller's thread. Capture the context and open/close a scope inside the task; do not use an uncontrolled shared mutable map.

### Exercise D — Final outcome and retries

A payment operation retries three times: the first two time out, and the third succeeds. Should the operation be logged as FAILED after the first attempt?

**Hint:** no, if the operation is still continuing. Log attempt events with `attempt=1,2,3` and the operation's final outcome as SUCCESS, while deciding the log level of transient failures according to policy.

### Exercise E — Context security

A middleware puts the entire request object, including the `Authorization` header, into MDC.

**Risk:** the token can appear in many logs and be stored in files/collectors/backups. Replace it with an allowlist of safe fields and verify that the encoder only outputs permitted fields.

## 19. Operation Context Implementation Checklist

- [ ] Defined `operation.name`, `operationId`, `parentOperationId`, `requestId`, and `traceId` according to their distinct purposes.
- [ ] Operation names are stable, while IDs identify individual executions.
- [ ] Each operation has clear lifecycle/outcome/attempt fields if required by the business.
- [ ] Scopes open at the right boundary and always restore in `finally` / `try-with-resources`.
- [ ] Child operations do not accidentally clear the root context.
- [ ] Context is immutable or snapshotted before enqueuing/submitting tasks.
- [ ] Async/task executors propagate context explicitly and clean up on the worker thread.
- [ ] Across HTTP/message queues, safe propagation contracts are used rather than relying on `ThreadLocal`.
- [ ] Formatters/encoders output operation context as real fields when querying is needed.
- [ ] MDC/Thread Context is supported by the actual backend/provider and configured properly.
- [ ] `Throwable`, error codes, outcome, and duration are recorded at the appropriate boundary.
- [ ] Duration is measured with an appropriate elapsed-time clock, not inferred from log arrival time.
- [ ] Dynamic logger names or metric labels containing per-request IDs are avoided.
- [ ] Passwords, tokens, sensitive payloads, and disallowed IDs are never logged.
- [ ] Tested for duplicate logs, operation leaks, cross-thread propagation, and schema compliance.
- [ ] Distinguished log correlation from metrics, tracing, and audit durability.
- [ ] Covered normal flows, nested operations, failures, retries, cancellations, and worker reuse in tests.

**Conclusion:** operation context enables logs to answer **"which operation, which execution, how does it relate to its parent step, and what was the outcome?"**. In Java, you can use immutable context objects, scoped `ThreadLocal`, MDC, or tracing integrations, but **lifecycle, propagation, and restoration** must be managed explicitly. When outputting structured JSON, context must be emitted as properly parsed fields; when processing asynchronously, snapshot/restore is mandatory to avoid losing or mixing contexts. Operation context improves diagnosability, but it does not automatically turn logs into distributed traces, accurate metrics, or a durable audit store.
