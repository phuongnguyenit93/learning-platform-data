# SLF4J API in Java

## 1. What Problem Does SLF4J Solve?

A Java application typically has business logic, a data access layer, an HTTP client, and multiple external libraries. If each component directly depends on a different logging system, changing where logs are output, the log level, or the format becomes difficult to manage.

**SLF4J (Simple Logging Facade for Java)** provides a **unified programming interface (API)** for Java code to write logs. Application code typically works with `org.slf4j.Logger` and `org.slf4j.LoggerFactory`, while a **provider/backend** at runtime performs the actual logging.

Example call inside a Java class:

```java
private static final org.slf4j.Logger LOG =
        org.slf4j.LoggerFactory.getLogger(OrderService.class);

LOG.info("event=order_created order_id={}", orderId);
```

This is **illustrative code inside the `OrderService` class**, not a standalone program. The code calls the SLF4J API to express an event; it does not decide whether logs go to a file, the console, or a centralized system.

Model:

```text
Java Code (OrderService, PaymentService, ...)
                 |
                 v
             SLF4J API
       Logger / LoggerFactory
                 |
                 v
     Provider / Logging backend
   (Logback, slf4j-simple, ...)
                 |
                 v
    Formatter / Appender / Filter
                 |
          +------+------+
          |             |
          v             v
       Console         File / collector
```

**A facade differs from a backend:** The SLF4J API defines how to *invoke* logging; the backend decides how to *execute* it. Having only `slf4j-api` does not mean the program will create a log file. With SLF4J 2.x, the program needs a compatible provider at runtime to output events as desired.

## 2. Important Components in the API

| Component | Role |
| --- | --- |
| `org.slf4j.Logger` | Logging interface: `trace`, `debug`, `info`, `warn`, `error` |
| `org.slf4j.LoggerFactory` | Retrieves a logger by name or by class |
| `org.slf4j.Marker` | Event label for filtering/categorizing when supported by the backend |
| `org.slf4j.MarkerFactory` | Creates or looks up a marker by name |
| `org.slf4j.MDC` | Diagnostic context holding key-value pairs for the processing thread, depending on backend/adapter capabilities |
| `org.slf4j.event.Level` | Type representing a log level for APIs that require a level value |
| `org.slf4j.spi.LoggingEventBuilder` | Fluent-syntax event builder interface, available since SLF4J 2.x |

Most business code only needs `LoggerFactory` and `Logger`. Markers, MDC, the fluent builder, and structured data fields are used when there are specific tracing or operational requirements.

Because SLF4J is an API, the backend can be changed while `LOG.info(...)` calls remain the same. However, **support for displaying key-value pairs, MDC, caller location, stack trace formatting, and filtering levels** may differ between providers. Changing the backend still requires verifying configuration and output.

## 3. Retrieving a Class-Based Logger with `LoggerFactory`

In a regular Java class, use:

```java
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public final class OrderService {
    private static final Logger LOG =
            LoggerFactory.getLogger(OrderService.class);

    public void create(String orderId) {
        LOG.info("event=order_created order_id={}", orderId);
    }
}
```

This snippet is **a valid class when the SLF4J API is on the classpath**, but it does not have `main`. Key points:

- `LoggerFactory.getLogger(OrderService.class)` retrieves a logger whose name is bound to the class. With packages, the name is typically the fully qualified class name such as `com.example.orders.OrderService`.
- `private static final` keeps the logger reference at the class level, allowing multiple `OrderService` instances to share it.
- Each call to `create` still passes its own `orderId`. Sharing a logger **does not mean** sharing order IDs or request data.
- Business code does not need to create a new logger per order, does not need to add an appender per request, and should not modify global log configuration inside processing methods.

You can retrieve a logger by a string name using `LoggerFactory.getLogger("com.example.order")`. The class-based approach usually makes it easier to identify the source and supports package-based filtering; custom names are suitable when a project needs a special event group.

Do not create a dynamically named logger like `"order." + orderId` for each order. The logger name should identify the **source**; `order_id` and `correlation_id` are attributes of the **log record**.

## 4. The Five Log Levels in SLF4J

| Level | Reference Meaning | Example |
| --- | --- | --- |
| `ERROR` | Unexpected error or critical failure requiring investigation | Unable to save the order even after recovery attempts |
| `WARN` | Degradation or anomaly that may affect the system | Cache error; the system falls back to an alternative path |
| `INFO` | Normal event with operational value | Order is created or rejected according to business rules |
| `DEBUG` | Technical details for investigation | Processing branch selection, internal check results |
| `TRACE` | Very fine-grained execution flow details | Small steps usually needed only during diagnostics |

The corresponding methods are `LOG.error`, `LOG.warn`, `LOG.info`, `LOG.debug`, and `LOG.trace`. The standard SLF4J `Logger` **does not have a `fatal` method**, nor does it use `Level.SEVERE` from `java.util.logging` (JUL).

**Choose the level based on impact, not solely on the presence of an exception.** A payment declined by the bank may be an `INFO` outcome. A failed retry where a subsequent request succeeds may be `WARN` or `DEBUG`. When an entire critical operation fails unexpectedly, `ERROR` is usually appropriate.

Calling `LOG.error` does not automatically roll back a transaction, rethrow an exception, or return HTTP 500. Logging only records the event; error-handling logic must still be implemented in code.

When a backend sets the typical threshold to `INFO`, `DEBUG` and `TRACE` may be filtered out. Another appender or filter may also apply further filtering, so **calling the API does not guarantee the record will reach every destination**.

## 5. Parameterized Messages with `{}`

SLF4J supports **parameterized logging**: using a fixed message template and passing varying values as arguments.

```java
LOG.info("event=order_created order_id={}", orderId);

LOG.warn("event=dependency_slow service={} duration_ms={}",
        serviceName, durationMs);

LOG.debug("event=page_loaded page={} count={}",
        page, count);
```

These are three illustrative calls inside a class that already has `LOG`. The `{}` notation is **SLF4J's placeholder**, not `String.format` or `MessageFormat` syntax. In JUL, parameter placeholders typically look like `{0}`, `{1}`; do not mix the two styles.

Comparison:

```java
// String created by concatenation on the caller side:
LOG.debug("order=" + orderId + ", state=" + state);

// SLF4J receives the template and arguments separately:
LOG.debug("order={} state={}", orderId, state);
```

The second approach gives the message a stable template and can avoid premature formatting when the `DEBUG` level is disabled. It also helps developers keep `event` names and field names consistent across multiple places in the codebase.

Some principles:

1. The number of `{}` placeholders should match the number of arguments used for formatting. Review messages when adding or removing fields.
2. `null` values are handled by the API/backend; do not construct vague messages when a clear result code can be used.
3. Dynamic arguments do not automatically mean safe data. A string containing newlines can still cause **log injection** if the encoder does not escape it properly.
4. `{}` does not automatically turn a log line into **structured JSON**. Output only has separate data fields when the backend/encoder or pipeline supports it.
5. Do not log passwords, tokens, OTPs, full card numbers, or sensitive personal data in arguments.

A stable message template does not mean every business flow must use the same generic sentence. `order_created` and `order_cancelled` are two events with different meanings; they need event names that accurately reflect what happened.

## 6. Java 17+ Example Running with Maven and SLF4J 2.x

SLF4J is a library outside the JDK. This example uses version `2.0.16` for both `slf4j-api` and `slf4j-simple` for reproducibility, **without claiming this is the latest version**. `slf4j-simple` is a small provider suitable for demonstrating API calls.

Project structure:

```text
slf4j-api-demo/
├── pom.xml
└── src/
    └── main/
        └── java/
            └── example/
                └── logging/
                    └── Slf4jApiDemo.java
```


Contents of `src/main/java/example/logging/Slf4jApiDemo.java`:

```java
package example.logging;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public final class Slf4jApiDemo {
    private static final Logger LOG =
            LoggerFactory.getLogger(Slf4jApiDemo.class);

    private Slf4jApiDemo() {
    }

    private static void checkout(String orderId, boolean approved) {
        LOG.info("event=checkout_started order_id={}", orderId);

        if (!approved) {
            LOG.info(
                    "event=payment_declined order_id={} reason_code={}",
                    orderId, "CARD_EXPIRED");
            return;
        }

        LOG.atInfo()
                .addArgument(orderId)
                .log("event=payment_authorized order_id={}");
    }

    public static void main(String[] args) {
        checkout("ORD-101", true);
        checkout("ORD-102", false);
        System.out.println("flow_finished");
    }
}
```

To compile, from the `slf4j-api-demo` directory, using JDK 17+ and Maven:

```bash
mvn -q -DskipTests package
mvn -q org.apache.maven.plugins:maven-dependency-plugin:3.7.1:copy-dependencies -DoutputDirectory=target/dependency
```

Run on Linux/macOS:

```bash
java -cp "target/classes:target/dependency/*" example.logging.Slf4jApiDemo
```

Run on Windows (classpath uses `;`):

```powershell
java -cp "target\classes;target\dependency\*" example.logging.Slf4jApiDemo
```

Maven needs to download dependencies/plugins on the first run if they are not yet in the local cache. The run command requires both the API and the provider on the classpath. Do not add another provider alongside `slf4j-simple` in this exercise.

**Exact stdout of the program:**

```text
flow_finished
```

With `slf4j-simple` accepting `INFO` by default, the following **message** parts are written sequentially to stderr. The provider may prepend thread name, log level, logger name, and prefix details; the lines below are **only the message part**, without claiming the exact full-line format:

```text
event=checkout_started order_id=ORD-101
event=payment_authorized order_id=ORD-101
event=checkout_started order_id=ORD-102
event=payment_declined order_id=ORD-102 reason_code=CARD_EXPIRED
```

The terminal may display stdout and stderr together without guaranteeing interleaved ordering. The program simulates business branches and does not connect to a payment gateway or database: the events illustrate **code paths**, not proof that an actual transaction occurred.

Notable observations:

- Both `checkout` calls use the same class-based logger.
- `LOG.info("...{}", orderId)` and `LOG.atInfo().addArgument(orderId).log("...{}")` format messages with parameters under the same principle.
- `payment_declined` is simulated as a normal outcome, so it uses `INFO`.
- `slf4j-simple` is the chosen provider to make logs appear without writing a custom appender.

## 7. Choosing the Right Provider for the SLF4J API

Some runtime options:

| Component | Function |
| --- | --- |
| `slf4j-api` | Interface for Java code to call logging; by itself does not choose an output destination |
| `slf4j-simple` | Simple provider, suitable for examples and small applications |
| Compatible `logback-classic` version | Provider with Logback's logging configuration capabilities |
| `slf4j-jdk14` | Provider routing SLF4J calls to JUL |
| Compatible `log4j-slf4j2-impl` version | Provider routing SLF4J 2.x to the Log4j 2 backend |

In an application, there should be **one intentional provider**. If multiple providers are on the classpath, SLF4J may warn and pick one of them; do not rely on selection order.

With **SLF4J 2.x**, providers are discovered via Java's service mechanism (`ServiceLoader`). **SLF4J 1.7** previously used bindings with `org.slf4j.impl.StaticLoggerBinder`. A 1.7 binding does not automatically become a valid 2.x provider; API and provider versions must be aligned.

If only `slf4j-api` 2.x is present and no suitable provider is found, SLF4J may print a notice at initialization and fall back to a **NOP (no-operation)** logger. In that case, the code can still run, but `info`/`warn` calls will not produce application logs as expected.

If the application uses a framework such as Spring Boot, a logging provider may already be included via starters/dependency management. Before manually adding `slf4j-simple` or Logback, inspect the project's existing runtime dependencies to avoid multiple providers.

## 8. `Logger` Overloads and `Throwable`

SLF4J provides several call forms:

```java
LOG.info("Start processing");
LOG.info("order_id={}", orderId);
LOG.warn("service={} attempt={}", serviceName, attempt);
LOG.error("event=order_save_failed order_id={}", orderId, error);
```

This is illustrative code inside a class with `LOG`. `error` on the last line assumes `error` is a `Throwable` object. In matching overloads, a trailing `Throwable` argument is separated from the format arguments so the provider can render the stack trace.

Compare two approaches:

```java
// Passing only a String, not a Throwable:
LOG.error("save failed: {}", error.getMessage());

// Passing a Throwable so the backend can log the stack trace:
LOG.error("save failed for order_id={}", orderId, error);
```

The first call can lose the stack trace and cause chain. The second call preserves the exception object in the logging event, depending on the provider's rendering capabilities.

**Log an exception at the right boundary.** If the repository, service, and controller layers all call `LOG.error(..., e)` and rethrow, the same error can generate multiple `ERROR` records. Usually, pick the place that knows the final outcome of the request/job, preserve the cause when wrapping exceptions across layers, and log with sufficient context at the responsible boundary.

A log statement does not replace exception handling. If a required step fails, the application must still return an error status, retry, rollback, or rethrow according to the business contract. Logging `ERROR` does not make Java stop on its own.

## 9. Fluent Logging in SLF4J 2.x

SLF4J 2.x adds a way to build an event via a builder:

```java
LOG.atInfo()
        .addArgument(orderId)
        .log("event=order_created order_id={}");
```

- `atInfo()` selects the `INFO` level.
- `addArgument(orderId)` adds an argument to replace the placeholder.
- `log(...)` **emits the event**. Without calling `log`, the logging call is incomplete.

Important methods:

| Fluent API | Effect |
| --- | --- |
| `atTrace()`, `atDebug()`, `atInfo()`, `atWarn()`, `atError()` | Starts a builder at the given level |
| `atLevel(org.slf4j.event.Level.INFO)` | Selects the level via enum |
| `setMessage("...")` | Sets the message |
| `addArgument(value)` | Adds a formatting argument |
| `addArgument(() -> expensive())` | Defers argument creation using a supplier |
| `addKeyValue("order_id", id)` | Attaches a key-value attribute to the event |
| `addMarker(marker)` | Attaches a marker |
| `setCause(throwable)` | Attaches an exception |
| `log()` / `log("...")` | Completes the call |

Example with a `Throwable`:

```java
LOG.atError()
        .addArgument(orderId)
        .setCause(error)
        .log("event=order_save_failed order_id={}");
```

Example passing key-value pairs:

```java
LOG.atInfo()
        .addKeyValue("event", "order_created")
        .addKeyValue("order_id", orderId)
        .addKeyValue("outcome", "SUCCESS")
        .log("Order created");
```

**Do not confuse `addKeyValue` with automatic JSON output.** The builder can attach attributes to the event, but the provider/encoder/collector decides whether those attributes are displayed or stored as separate fields. If you want a centralized system to search by `order_id`, verify the actual output of the pipeline.

## 10. Performance: Parameterization and Argument Evaluation

A common misconception is that `LOG.debug("{}", expensive())` has zero cost when DEBUG is disabled. In reality, **Java evaluates method arguments before calling the method**.

```java
// expensive() runs even when DEBUG is disabled:
LOG.debug("snapshot={}", expensive());

// First approach: check the level first:
if (LOG.isDebugEnabled()) {
    LOG.debug("snapshot={}", expensive());
}

// Second approach: supplier with SLF4J 2.x:
LOG.atDebug()
        .addArgument(() -> expensive())
        .log("snapshot={}");
```

The snippets above are patterns for use inside a class with `LOG` and `expensive()`. A supplier defers computing the data if the log level is not enabled. Only use the more complex form when computing the data is genuinely expensive; logging an ordinary ID or integer does not need over-optimization.

Do not put business side effects inside a supplier: if logging is disabled, the supplier may not run. Transaction correctness must be independent of whether logging is enabled.

Logging optimization also involves message length, object `toString()` calls, formatters, synchronization, I/O, buffering, network, and storage cost. Do not use the number of `LoggerFactory` calls as the sole metric of performance.

## 11. `Marker`: Labeling Events

`Marker` helps identify event groups according to policy:

```java
import org.slf4j.Marker;
import org.slf4j.MarkerFactory;

Marker security = MarkerFactory.getMarker("SECURITY");
LOG.warn(security, "event=login_blocked reason_code={}",
        "TOO_MANY_ATTEMPTS");
```

This is illustrative code inside a class with `LOG`. The `SECURITY` marker **does not automatically make** a message an immutable audit record or route logs to a security file. The backend/filter must be configured to use the marker.

With the fluent API:

```java
LOG.atWarn()
        .addMarker(security)
        .addKeyValue("reason_code", "TOO_MANY_ATTEMPTS")
        .log("event=login_blocked");
```

A marker should be a stable category name such as `SECURITY` or `AUDIT`. Do not create a new marker for every `orderId`, `requestId`, or account number. Varying values belong in the data fields of each event.

## 12. `MDC`: Attaching Correlation IDs to a Processing Flow

**Mapped Diagnostic Context (MDC)** is an API for diagnostic attributes tied to the execution context, such as request ID, correlation ID, and task ID.

Example inside a class that already has `LOG`:

```java
import org.slf4j.MDC;

void process(String requestId, String orderId) {
    try (MDC.MDCCloseable ignored =
                 MDC.putCloseable("request_id", requestId)) {
        LOG.info("event=order_received order_id={}", orderId);
        LOG.info("event=order_checked order_id={}", orderId);
    }
}
```

This is an **illustrative method snippet**, not a standalone runnable program. When `MDCCloseable` is closed, the key that was set is **removed** from the context; this method does not automatically restore a previous value of the same key. If nesting multiple scopes with the same key, an appropriate save-and-restore mechanism is needed.

Important limitations:

- MDC is **context**; it is not a variable stored in a `static final` logger.
- The backend/adapter must support MDC and the encoder must be configured to output those fields. Not every provider prints MDC.
- Thread pools reuse threads: the context must be cleared to prevent subsequent requests from inheriting stale metadata.
- When processing asynchronously or switching threads, the context does not necessarily propagate automatically. Pass `correlation_id` via a framework-supported mechanism or explicitly.
- Do not put passwords, tokens, or sensitive information into MDC; they may pass through multiple collection systems.

If two runs process the same order, `order_id` may be the same while `request_id` differs. The order ID helps trace the entity's lifecycle; the request ID helps distinguish individual executions.

## 13. How a Bridge Differs from a Provider

A project may contain libraries that call JUL or the Log4j 2 API instead of SLF4J. A **bridge** forwards events from one API to another. A **provider** executes logs received from SLF4J.

```text
Code using SLF4J --------------> SLF4J API ---> Provider ---> Destination
Library using JUL ---> JUL-to-SLF4J ---------> Provider ---> Destination
```

Some examples:

| Library | Log Forwarding Direction |
| --- | --- |
| `jul-to-slf4j` | JUL -> SLF4J, when the bridge is properly installed |
| `jcl-over-slf4j` | Commons Logging API -> SLF4J |
| `log4j-to-slf4j` | Log4j 2 API -> SLF4J |
| `slf4j-jdk14` | SLF4J -> JUL, acting as a provider |
| `log4j-slf4j2-impl` | SLF4J 2.x -> Log4j 2, acting as a provider |

Do not configure a two-way bridge such as **JUL -> SLF4J** while also selecting **SLF4J -> JUL** as the provider. Similarly, avoid creating a loop between the Log4j 2 API and the SLF4J -> Log4j 2 provider. A loop can cause duplicate logs or initialization errors.

A library using the SLF4J API usually **should not force end applications to use a specific backend**. The application decides the provider, while bridges are managed by the system configuration layer. In Spring Boot or applications with starters, check existing logging dependencies before adding another adapter.

## 14. Structured Logs and Stable Messages

Source code may emit a message like:

```java
LOG.info("event=payment_declined order_id={} reason_code={}",
        orderId, "CARD_EXPIRED");
```

A centralized logging platform may expect structured data:

```json
{
  "timestamp": "2026-11-09T12:00:00Z",
  "level": "INFO",
  "service": "checkout-service",
  "event": "payment_declined",
  "order_id": "ORD-102",
  "reason_code": "CARD_EXPIRED",
  "correlation_id": "req-7a"
}
```

This is **illustrative JSON**, not the default output of `slf4j-simple` or a guarantee of `LOG.info`. Producing output like this requires a properly configured backend, encoder, or collector.

Effective design practices:

1. Keep `event` stable, using a name that accurately represents the event that occurred.
2. Use `reason_code` from a managed set of codes; do not rely verbatim on messages from external libraries.
3. Use clear field names and units such as `duration_ms`, avoiding mixing seconds in one place and milliseconds in another.
4. Propagate `request_id`/`correlation_id` with the proper lifecycle so all logs belonging to a single execution can be found.
5. Distinguish a retry attempt from the final outcome: multiple log lines do not automatically mean multiple successful transactions.
6. Avoid using logs as the sole source of truth for financial figures, auditing, or official data state.

Renaming an `event` or changing the unit of a field used by dashboards can break queries and alerts; treat these fields as an observability contract.

## 15. Data Safety and Boundary Error Handling

The logging API has many convenient overloads, but it does not automatically guarantee that logged data is always safe:

- Do not put passwords, API keys, tokens, OTPs, card numbers, or full requests/responses into logs.
- Input values containing newlines, control characters, or delimiters must be handled by an appropriate encoder/formatter to prevent **log injection**.
- Exception messages may contain internal URLs, user data, or access credentials; do not assume `e.getMessage()` is harmless data.
- Enabling overly verbose log levels can generate high traffic and increase storage costs; monitor retention and access permissions at the destination system.
- Log at the place that decides the final outcome, minimizing multiple stack traces for a single failure.

The distinction between business events and technical events remains important. For example, an expired card is an expected outcome; losing connection to the payment gateway during checkout may be a technical incident. Choosing the right `event`/`reason_code` and level helps operators know how to respond.

## 16. Common SLF4J API Mistakes

**Mistake 1 — declaring only the API and forgetting the provider:** code compiles, but no events appear. Check SLF4J initialization notices and configure the runtime dependency.

**Mistake 2 — adding multiple providers:** the classpath has both `slf4j-simple` and Logback at the same time. Choose one appropriate provider.

**Mistake 3 — using an SLF4J 1.7 binding with API 2.x:** provider discovery differs. Align dependencies and remove incompatible old bindings.

**Mistake 4 — confusing `{}` with `{0}`:** SLF4J and JUL have different syntax; the message may print the literal placeholder.

**Mistake 5 — passing only `error.getMessage()`:** loses the `Throwable` object for printing the stack trace. Use an overload that takes `Throwable` or `setCause`.

**Mistake 6 — computing expensive data before checking the level:** `LOG.debug("{}", expensive())` still evaluates the argument. Use `isDebugEnabled()` or a fluent supplier when worthwhile.

**Mistake 7 — forgetting `log()` in the fluent API:** the builder does not emit an event unless the terminal method is called.

**Mistake 8 — assuming `addKeyValue` always outputs JSON:** a compatible backend/encoder is required and the pipeline must be verified.

**Mistake 9 — storing request context in a `static` field:** can mix data across threads. Use parameters or MDC with a proper lifecycle.

**Mistake 10 — failing to clear MDC when a request ends:** thread pools can carry stale context into new requests.

**Mistake 11 — adding a two-way bridge:** logs can loop or recurse infinitely. Check the forwarding direction of each adapter/provider.

**Mistake 12 — treating the `AUDIT` marker as an audit ledger:** a marker is only metadata; auditing and data preservation requirements need a dedicated system.

## 17. Choosing an API by Need

| Need | Suggested Call |
| --- | --- |
| Log a normal event | `LOG.info("event=order_created id={}", id)` |
| Log degradation to monitor | `LOG.warn("event=cache_unavailable cache={}", cache)` |
| Log a final failure with exception | `LOG.error("event=save_failed id={}", id, e)` |
| Log technical details | `LOG.debug("step={} count={}", step, count)` |
| Avoid expensive computation when DEBUG is off | `LOG.atDebug().addArgument(() -> expensive()).log("data={}")` |
| Attach fields for a supporting backend | `LOG.atInfo().addKeyValue("order_id", id).log("created")` |
| Label an event | `LOG.warn(marker, "event=security_alert")` |
| Attach a per-request ID | `MDC.putCloseable("request_id", id)` with a `try` scope |
| Name a logger stably by class | `LoggerFactory.getLogger(MyClass.class)` |

These are illustrative calls; variables like `id`, `e`, `marker`, or `expensive` must be declared accordingly. Choosing the right API is the first step, while log levels, provider configuration, and data handling determine actual observability.

## 18. Knowledge Self-Check

1. **Is SLF4J a backend that writes log files on its own?** No. It is an API; the backend/provider performs the actual logging.
2. **Which method retrieves a class-based logger?** `LoggerFactory.getLogger(MyClass.class)`.
3. **What placeholder does SLF4J use for arguments?** `{}`, not JUL's `{0}`.
4. **Does `LOG.error(...)` throw an exception on its own?** No. It is a logging call.
5. **What can happen in SLF4J 2.x if there is no provider?** An initialization warning and a NOP logger, so events are not output as expected.
6. **Should two providers be included in the same runtime?** Generally no; choose one intentional provider.
7. **Does `LOG.error("{}", e.getMessage())` preserve the `Throwable` object?** No. When a stack trace is needed, pass `e` using the appropriate overload or `setCause`.
8. **In the fluent API, has `LOG.atInfo().addArgument(id)` logged yet?** Not yet; `log(...)` must be called.
9. **Does `addKeyValue` automatically produce JSON?** No. A compatible provider/encoder is required.
10. **Is MDC data stored inside a `static final` logger?** No. It is a processing context whose lifecycle must be managed.
11. **If `DEBUG` is disabled, does `LOG.debug("{}", expensive())` evaluate `expensive()`?** Yes, because Java evaluates arguments before calling the method.
12. **Can a JUL -> SLF4J bridge be used together with an SLF4J -> JUL provider?** No, because it creates a forwarding loop.
13. **Does the `SECURITY` marker automatically guarantee the log is an audit trail?** No. A marker only helps categorize events.
14. **Why should `event` and `reason_code` names be kept stable?** So queries, alerts, statistics, and comparisons across deployments are less likely to break.
15. **Can you rely on the count of `payment_authorized` log lines to determine the official number of recorded transactions?** No; logs can be lost, duplicated, or delayed. You must reconcile against actual business state.

**Key takeaway:** Use `Logger` and `LoggerFactory` so Java code logs through a consistent API. Choose one suitable SLF4J 2.x provider at runtime; use `{}` for parameters, select levels by meaning, pass `Throwable` when needed, and use the fluent API, Markers, and MDC with discipline. Writing, formatting, retention, and searching of logs are the responsibility of the backend and observability infrastructure.
