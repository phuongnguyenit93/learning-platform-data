# Filters in Log4j2 (Apache Log4j 2)

## 1. What is a Filter?

A **Filter in Log4j2** is a component that decides whether a logger call or a `LogEvent` should continue through the logging pipeline. A filter can evaluate the **log level, marker, message, context data (Thread Context), time, or event emission rate**. This allows an application to retain useful information while limiting unnecessary logs.

For example: the console displays INFO and above for operational monitoring, while a file only records WARN/ERROR/FATAL for incident troubleshooting. This is a **destination-based filtering** policy, which does not necessarily remove INFO logs from the entire system.

Distinguishing the components:

- **Logger**: the API called by Java code; works with LoggerConfig to determine the effective log level.
- **Filter**: evaluates conditions and returns an accept, deny, or neutral result at each stage.
- **Appender**: receives events to write to the console/file/network or forward to another destination.
- **Layout**: formats the event as text, JSON, or another suitable format.
- **AppenderRef**: the connection path from a LoggerConfig to an appender. Log4j2 also allows adding a `level` threshold and a filter on this connection path.

Overview diagram:

~~~text
Logger.debug/info/warn/error(...)
           |
           v
[Logger stage: global filter, logger-level threshold]
           |
           v
[LoggerConfig stage: logger filters, parent logger]
           |
           v
[AppenderControl: AppenderRef level + AppenderRef filter]
           |
           v
[Appender: appender filter]
           |
           v
Layout/encoder -> console, file, collector, ...
~~~

The diagram above shows the main stages of Log4j Core; it does not mean a project must use all four filter types. Blocking early is usually more economical than letting an event travel almost all the way through the pipeline before being discarded.

## 2. Three Filter Results: ACCEPT, DENY, NEUTRAL

Log4j2 filters return `Filter.Result`, which has three values:

| Result | Meaning | Key Point to Remember |
| --- | --- | --- |
| `ACCEPT` | Accept at the current filter stage | May end evaluation of remaining filters in the same stage; does not guarantee the event will be written to the final destination |
| `DENY` | Reject the event at that filter point | The event does not continue down the rejected processing path |
| `NEUTRAL` | No decisive conclusion | Allows the next filter or the stage's rules to continue deciding |

Many standard filters have two attributes:

~~~xml
<ThresholdFilter level="WARN"
                 onMatch="NEUTRAL"
                 onMismatch="DENY"/>
~~~

- `onMatch`: the result when the condition is satisfied.
- `onMismatch`: the result when the condition is not satisfied.

In many standard filters, the default values are **`onMatch="NEUTRAL"`, `onMismatch="DENY"`**; to make configurations easier for readers and test suites to understand, explicitly specify both attributes in important configurations. Special or custom filters may be configured differently.

**NEUTRAL is not DENY.** For example, when `ThresholdFilter` matches WARN and returns NEUTRAL, the appender can still write WARN because no other filter rejects it. If you set `onMatch="DENY"`, then the WARN event itself will be discarded.

**ACCEPT does not behave the same at every stage.** By Log4j2's mechanism, a global filter runs at the initial stage before event creation. An ACCEPT result from a global filter can allow event creation **without going through the normal logger level comparison at the initial stage**; with NEUTRAL, the logger threshold continues to take effect. At later stages, ACCEPT does not revive an event that was already rejected earlier.

## 3. Filter Configuration Locations

### 3.1. Global Filter in Configuration

A global filter is placed directly under the `<Configuration>` element and affects the broad scope of the LoggerContext.

~~~xml
<!-- Example inside the <Configuration> element; not a complete file. -->
<MarkerFilter marker="IMPORTANT"
              onMatch="NEUTRAL"
              onMismatch="DENY"/>
~~~

Only calls with the matching IMPORTANT marker pass this global filter; after that, the normal logger threshold is still evaluated because the match result is NEUTRAL. Events without the marker are immediately DENIED early.

A global filter is suitable when you need a broadly applied rule that can be thoroughly tested. However, it can easily drop WARN/ERROR logs from libraries that do not attach markers. Exercise special caution before enabling it in production.

If you replace `onMatch="NEUTRAL"` with `ACCEPT`, the combined behavior with the logger level at the initial stage **may change**. Do not treat "global ACCEPT" as a normal way to configure levels; test it specifically.

### 3.2. LoggerConfig Filter in Logger or Root

A LoggerConfig filter is placed inside `<Logger>` or `<Root>`, serving a specific logger or package.

~~~xml
<!-- Example snippet inside <Loggers>. -->
<Logger name="example.checkout" level="DEBUG">
    <ThresholdFilter level="INFO"
                     onMatch="NEUTRAL"
                     onMismatch="DENY"/>
    <AppenderRef ref="CONSOLE"/>
</Logger>
~~~

The logger threshold allows DEBUG and above, but the LoggerConfig filter will block DEBUG when the event reaches the corresponding stage. If the sole goal is "INFO and above", **changing the logger level to INFO** is usually simpler and filters earlier.

When `additivity="true"` (typically the default), an event can propagate to parent LoggerConfigs and their appenders; filters along that path can continue to take effect. Therefore, you must check both child and parent loggers, not just the filter closest to the call site.

### 3.3. AppenderRef Filter: Policy for a Single Connection Path

A LoggerConfig can reference multiple appenders, each path having a different level and filter:

~~~xml
<!-- Example inside <Root> or <Logger>. -->
<AppenderRef ref="CONSOLE"/>
<AppenderRef ref="WARN_FILE" level="WARN"/>
~~~

`level="WARN"` on AppenderRef restricts the path to WARN_FILE to WARN and above only. CONSOLE is not constrained by the level of another AppenderRef. This is often a convenient way to separate logs by severity **without needing a complex filter plugin**.

An AppenderRef path can also filter by marker:

~~~xml
<AppenderRef ref="AUDIT_FILE">
    <MarkerFilter marker="AUDIT"
                  onMatch="NEUTRAL"
                  onMismatch="DENY"/>
</AppenderRef>
~~~

Only events carrying the matching AUDIT marker are forwarded to AUDIT_FILE along that path. An event that does not enter AUDIT_FILE can still go to CONSOLE if another AppenderRef exists.

### 3.4. Appender Filter: Policy of the Appender Itself

A filter placed inside an appender definition controls the events reaching that destination:

~~~xml
<Appenders>
    <Console name="WARN_CONSOLE" target="SYSTEM_OUT">
        <ThresholdFilter level="WARN"
                         onMatch="NEUTRAL"
                         onMismatch="DENY"/>
        <PatternLayout pattern="%level %msg%n"/>
    </Console>
</Appenders>
~~~

This snippet needs to be connected to a logger via `AppenderRef` to receive events. If the filter is inside the appender, the event may have already been created and had much of its data prepared before being discarded. Filtering by level at the logger or AppenderRef can reduce overhead when policy allows.

### Quick Comparison of the Four Locations

| Location | Scope | Key Point to Note |
| --- | --- | --- |
| Global/Configuration | Entire configuration, at the initial stage | ACCEPT can affect logger level checking |
| LoggerConfig | Per logger/package and loggers along the additivity path | Can be confused with logger threshold; requires understanding the parent-child path |
| AppenderRef | Per **single path** to an appender | Has its own `level` attribute, often cleaner than a filter for simple thresholds |
| Appender | Per **target appender** | Filters relatively late; may not reduce event creation cost |

## 4. Common Filter Types

### 4.1. ThresholdFilter: Minimum Level

~~~xml
<ThresholdFilter level="WARN"
                 onMatch="NEUTRAL"
                 onMismatch="DENY"/>
~~~

It matches events at least as severe as WARN. With Log4j2's standard level hierarchy, WARN, ERROR, and FATAL match; INFO, DEBUG, and TRACE do not.

**Do not confuse with LevelMatchFilter.** ThresholdFilter does not mean "exactly WARN only".

### 4.2. LevelMatchFilter: Exact Single Level

~~~xml
<LevelMatchFilter level="ERROR"
                  onMatch="NEUTRAL"
                  onMismatch="DENY"/>
~~~

It only matches events with **the exact ERROR level**. WARN and FATAL do not match. If you want WARN and above, use ThresholdFilter WARN.

### 4.3. LevelRangeFilter: Level Range

`LevelRangeFilter` allows selecting a range within Log4j2's level ordering. The `minLevel`/`maxLevel` attributes depend on how Log4j interprets severity—do not infer from the English names alone. Test both endpoints and levels outside the range, especially when custom levels are used.

If you only need INFO and above or only exact ERROR, using ThresholdFilter or LevelMatchFilter is clearer.

### 4.4. MarkerFilter: Labeled Events

A marker is attached by Java code when logging:

~~~java
// Example in a project with Log4j2 API, LOG, and orderId.
import org.apache.logging.log4j.Marker;
import org.apache.logging.log4j.MarkerManager;

Marker audit = MarkerManager.getMarker("AUDIT");
LOG.info(audit, "operation=checkout orderId={} outcome={}",
        orderId, "accepted");
~~~

Configuration:

~~~xml
<MarkerFilter marker="AUDIT"
              onMatch="NEUTRAL"
              onMismatch="DENY"/>
~~~

allows events with the matching marker to proceed. Log4j2 markers can have parent-child relationships, and MarkerFilter's match condition can include corresponding descendant markers. A marker is a classification label; it is **not an authentication, anonymization, or guaranteed log persistence mechanism**.

### 4.5. ContextMapFilter: Filtering by Thread Context

Log4j2 provides `ThreadContext`, which holds key/value pairs bound to the thread context. `ContextMapFilter` uses those pairs:

~~~xml
<ContextMapFilter operator="AND"
                  onMatch="NEUTRAL"
                  onMismatch="DENY">
    <KeyValuePair key="operation" value="checkout"/>
    <KeyValuePair key="debugScope" value="enabled"/>
</ContextMapFilter>
~~~

The AND condition requires both `operation=checkout` and `debugScope=enabled`. If you choose `operator="OR"`, at least one matching key/value pair in the list is sufficient.

Example code to set a scoped context:

~~~java
// Example in a scope where LOG is available.
import org.apache.logging.log4j.CloseableThreadContext;

try (CloseableThreadContext.Instance ignored =
        CloseableThreadContext.put("operation", "checkout")
                              .put("debugScope", "enabled")) {
    LOG.info("event=checkout-validated");
}
~~~

Context must be managed when requests cross thread pools or asynchronous tasks; do not assume all thread-local data automatically propagates across `CompletableFuture`. Context values should not contain passwords, tokens, or sensitive data.

### 4.6. DynamicThresholdFilter: Context-Based Threshold

`DynamicThresholdFilter` can use the value of a context key to select a threshold:

~~~xml
<DynamicThresholdFilter key="diagnosticProfile"
                        defaultThreshold="ERROR">
    <KeyValuePair key="verbose" value="DEBUG"/>
    <KeyValuePair key="normal" value="INFO"/>
</DynamicThresholdFilter>
~~~

This example describes a dynamic threshold policy; **where the filter is attached matters greatly**. If placed on an appender, it cannot receive DEBUG events that were already blocked at the initial logger stage. To implement "enable DEBUG per request", you must design the entire path—logger, initial stage, and permission to set the context value—not just drop a filter into the file.

### 4.7. RegexFilter and StringMatchFilter: Inspecting the Message

~~~xml
<RegexFilter regex=".*event=healthcheck.*"
             onMatch="DENY"
             onMismatch="NEUTRAL"/>
~~~

This example discards messages containing `event=healthcheck`. `RegexFilter` matches the **entire** message against the pattern, so use `.*` to check for a substring in the middle. It has a `useRawMsg` attribute: for some parameterized message types, enabling this option can inspect the raw template instead of the formatted message with arguments substituted.

Filtering formatted messages can force the system to build the string even when the event is later discarded, increasing CPU and memory allocations. Rules based on wording are also fragile if message content changes. Whenever possible, prefer markers or context fields with stable semantics. If you must use regex, test inputs containing newlines, regex complexity, and edge cases.

`StringMatchFilter` checks for the occurrence of a text snippet in the message, which is easier to understand than regex when you only need a substring match, though it still shares the limitations of message-based filtering.

### 4.8. BurstFilter: Rate Limiting

~~~xml
<BurstFilter level="INFO"
             rate="20"
             maxBurst="100"
             onMatch="NEUTRAL"
             onMismatch="DENY"/>
~~~

`BurstFilter` limits event frequency at levels within its scope, allowing a short burst up to `maxBurst` and an average rate per `rate`. Events more severe than the threshold are handled according to the plugin's own rules.

This is a way to reduce repetitive logs, **not a guarantee against losing records**. Do not blindly apply rate limiting to audit logs or events that must be fully persisted. Always measure the number of dropped events and verify that critical incident signals still survive.

## 5. Runnable Java 17 Example: Console INFO+, File WARN+

We will build a program using **Log4j API and Log4j Core**, without needing SLF4J. The XML configuration will determine which appender receives which log levels. **Log4j 2.26.1** is chosen as a concrete version for illustration, not as a claim that it is required or the latest in every environment. Real projects should apply their own dependency management and security policies.

Structure:

~~~text
log4j2-filter-demo/
  pom.xml
  src/main/java/example/FilterDemo.java
  src/main/resources/log4j2.xml
~~~

### 5.1. Create pom.xml

~~~xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0
                             https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>

    <groupId>example</groupId>
    <artifactId>log4j2-filter-demo</artifactId>
    <version>1.0.0</version>

    <properties>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    </properties>

    <dependencies>
        <dependency>
            <groupId>org.apache.logging.log4j</groupId>
            <artifactId>log4j-api</artifactId>
            <version>2.26.1</version>
        </dependency>
        <dependency>
            <groupId>org.apache.logging.log4j</groupId>
            <artifactId>log4j-core</artifactId>
            <version>2.26.1</version>
        </dependency>
    </dependencies>

    <build>
        <plugins>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-compiler-plugin</artifactId>
                <version>3.13.0</version>
                <configuration>
                    <release>17</release>
                </configuration>
            </plugin>
            <plugin>
                <groupId>org.codehaus.mojo</groupId>
                <artifactId>exec-maven-plugin</artifactId>
                <version>3.5.0</version>
                <configuration>
                    <mainClass>example.FilterDemo</mainClass>
                </configuration>
            </plugin>
        </plugins>
    </build>
</project>
~~~

`log4j-api` contains `LogManager` and `Logger`; `log4j-core` implements the backend and supports filters, appenders, and layouts. Do not mix incompatible API/Core versions.

### 5.2. Create FilterDemo.java

~~~java
package example;

import org.apache.logging.log4j.LogManager;
import org.apache.logging.log4j.Logger;

public final class FilterDemo {
    private static final Logger LOG =
            LogManager.getLogger(FilterDemo.class);

    private FilterDemo() {
    }

    public static void main(String[] args) {
        String requestId = "R-7";

        LOG.debug("step=enter requestId={}", requestId);
        LOG.info("event=start requestId={}", requestId);
        LOG.warn("event=fallback requestId={} reason={}",
                requestId, "cache-miss");
        LOG.error("event=failed requestId={} reason={}",
                requestId, "timeout");
    }
}
~~~

The program emits four calls: DEBUG, INFO, WARN, and ERROR. The Java code makes no mention of log files; routing is managed by `log4j2.xml`.

### 5.3. Create log4j2.xml

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<Configuration status="WARN">
    <Appenders>
        <Console name="CONSOLE" target="SYSTEM_OUT">
            <PatternLayout pattern="%level %msg%n"/>
        </Console>

        <File name="WARN_FILE"
              fileName="target/warn-only.log"
              append="false">
            <ThresholdFilter level="WARN"
                             onMatch="NEUTRAL"
                             onMismatch="DENY"/>
            <PatternLayout pattern="%level %msg%n"/>
        </File>
    </Appenders>

    <Loggers>
        <Root level="INFO">
            <AppenderRef ref="CONSOLE"/>
            <AppenderRef ref="WARN_FILE"/>
        </Root>
    </Loggers>
</Configuration>
~~~

Place the file at `src/main/resources/log4j2.xml`.

- `Root level="INFO"` discards the DEBUG call.
- `CONSOLE` has no separate filter and receives INFO, WARN, ERROR.
- `WARN_FILE` has a ThresholdFilter for WARN, so it only receives WARN and ERROR.
- `append="false"` recreates the test file on each run of the example instead of appending to old logs. Production systems need retention design and should not wipe historical logs.
- `PatternLayout` prints only the level and message, keeping output simple without timestamps or thread names.

Maven creates the `target` directory during compilation; the file path is relative to the working directory. If running the application another way, check the current working directory and write permissions.

### 5.4. Compile and Run

In the `log4j2-filter-demo` directory:

~~~bash
mvn -q compile exec:java
~~~

**Application log lines on stdout**:

~~~text
INFO event=start requestId=R-7
WARN event=fallback requestId=R-7 reason=cache-miss
ERROR event=failed requestId=R-7 reason=timeout
~~~

Contents of `target/warn-only.log`:

~~~text
WARN event=fallback requestId=R-7 reason=cache-miss
ERROR event=failed requestId=R-7 reason=timeout
~~~

These are two **destinations** with different filters. Maven may print its own tool output, but the application log lines matching the pattern are the ones above. DEBUG does not appear in either destination because Root INFO already filtered it out at the logger stage.

**Try changing the configuration:**

1. Change Root from INFO to DEBUG: the console gains `DEBUG step=enter requestId=R-7`. The file still only receives WARN/ERROR.
2. Remove ThresholdFilter from WARN_FILE: the file receives INFO/WARN/ERROR per Root INFO.
3. Replace ThresholdFilter with `<LevelMatchFilter level="ERROR" onMatch="NEUTRAL" onMismatch="DENY"/>`: the file only receives **exact ERROR**, not WARN.
4. Remove the filter from WARN_FILE and replace `<AppenderRef ref="WARN_FILE"/>` with `<AppenderRef ref="WARN_FILE" level="WARN"/>`: this example produces the same result, but the threshold is checked on the AppenderRef path.

## 6. Combining Multiple Conditions with Filters

`<Filters>` can contain multiple child filters. They are evaluated in order: `DENY` or `ACCEPT` ends the chain's decision at that stage; `NEUTRAL` lets the next filter continue evaluating. Therefore, **order and onMatch/onMismatch** determine the actual logical operation.

### 6.1. AND Condition: AUDIT Marker and WARN+

~~~xml
<!-- Snippet placed inside the appender to be filtered. -->
<Filters>
    <MarkerFilter marker="AUDIT"
                  onMatch="NEUTRAL"
                  onMismatch="DENY"/>
    <ThresholdFilter level="WARN"
                     onMatch="NEUTRAL"
                     onMismatch="DENY"/>
</Filters>
~~~

If the event lacks the AUDIT marker, the first filter returns DENY. If it has AUDIT but is INFO level, the first filter returns NEUTRAL and the second returns DENY. Only events with the AUDIT marker **and** WARN+ pass both conditions. When both return NEUTRAL, the event proceeds according to the appender's rules.

### 6.2. OR Condition: AUDIT Marker or ERROR+

~~~xml
<Filters>
    <MarkerFilter marker="AUDIT"
                  onMatch="ACCEPT"
                  onMismatch="NEUTRAL"/>
    <ThresholdFilter level="ERROR"
                     onMatch="ACCEPT"
                     onMismatch="DENY"/>
</Filters>
~~~

If the AUDIT marker matches, it immediately returns ACCEPT. If it does not match, NEUTRAL allows checking the level condition. ERROR/FATAL matches the second condition and returns ACCEPT; other levels are DENIED. **Do not let the first filter return DENY when the marker does not match**, because then the second filter will never get a chance to evaluate.

Both examples are **XML snippets to place inside a stage that supports Filters**, not complete configurations. In particular, an appender filter **cannot rescue** an INFO event that was already dropped by a logger set to WARN.

### 6.3. Behavior Verification Matrix

| Event | AND (AUDIT and WARN+) | OR (AUDIT or ERROR+) |
| --- | --- | --- |
| INFO, no marker | Drop | Drop |
| INFO, AUDIT marker | Drop | Keep if it reached this stage |
| WARN, no marker | Drop | Drop |
| WARN, AUDIT marker | Keep | Keep |
| ERROR, no marker | Drop | Keep |
| ERROR, AUDIT marker | Keep | Keep |

The table assumes all events **have passed the logger and reached Filters**. If the logger level or a global filter blocks an event early, the actual outcome may be that it is dropped before this table applies.

## 7. Level, Additivity, and Filter: Easily Confused Relationships

### Log Levels

Common level order from most severe to least severe:

~~~text
FATAL > ERROR > WARN > INFO > DEBUG > TRACE
~~~

`ALL` and `OFF` are special thresholds; Log4j2 also supports custom levels. With Root INFO, DEBUG/TRACE calls are normally blocked at the start of the pipeline. An appender's `ThresholdFilter level="DEBUG"` cannot "re-enable" an event that has already been dropped.

### Additivity

Loggers have hierarchical relationships based on package names—for example, `example.checkout.Service` belongs to the `example.checkout` branch. When additivity is enabled, an event can propagate up to parent loggers and reach the parent's appenders. Filters on a parent LoggerConfig can take effect; AppenderRefs can specify different levels.

If the same appender is attached through both a child logger and root, logs may be written twice. This is a **routing path** issue, not caused by a filter duplicating events.

### ACCEPT Result

`ACCEPT` at one stage is not a "permanent pass". Global ACCEPT has special behavior with logger-level checking at the initial stage; an ACCEPT inside an appender's Filters does not bypass stages already traversed. When diagnosing, record **where the filter is placed** before drawing conclusions.

### Cost

An event DENIED at an appender may have already incurred the cost of creating the event, capturing the timestamp, context, and possibly formatting the message. Filters placed earlier generally have a better chance of reducing overhead. `RegexFilter` on formatted messages can be expensive under high log volume.

Additionally, Java still evaluates argument expressions before calling the logger. For example, `LOG.debug("details={}", expensiveDescribe(order))` still computes `expensiveDescribe(order)` before DEBUG is blocked. Use lazy message APIs or guards where appropriate, and do not place business side effects in code meant only for logging.

## 8. Practical Applications of Filters

### 8.1. Separating a Warning File

The console can keep INFO+, while a warning file uses an AppenderRef level of WARN or ThresholdFilter WARN. When adding a logger for a specific package, remember to check whether it propagates through root and which filters are attached to each path. If you still need INFO history for investigations, do not rely solely on a WARN file without an alternative source.

### 8.2. Tracking Special Events

An `AUDIT` or `SECURITY_EVENT` marker helps classify events and route them to a dedicated destination. However, a marker is just a label; it does not guarantee integrity, access control, or durable storage. For mandatory audit events, design an end-to-end reliable policy and verify that filters do not accidentally drop them.

### 8.3. Reducing Health-Check Logs

A system may produce thousands of identical INFO health-check logs per second. You can choose not to log each successful check, move counts to metrics, or filter by marker/context. Using regex on message strings can cause false matches when templates change. In particular, never suppress **failed health-check** events due to an overly broad filter.

### 8.4. Enabling DEBUG for a Group of Requests

ContextMapFilter or DynamicThresholdFilter can be part of a per-request investigation policy. However, you must ensure the logger can produce the required DEBUG level, important events are not dropped, and context values are only set by trusted components. Limit how long it stays enabled and monitor log volume and latency.

## 9. Troubleshooting Checklist When Logs Are Missing

If code called `LOG.info(...)` but the corresponding line is missing, trace through the pipeline:

1. **Verify runtime and config file:** `log4j-api` and `log4j-core` are compatible, `log4j2.xml` is actually on the classpath, and the backend initialized properly. If code uses SLF4J, check the adapter/provider pointing to Log4j2.
2. **Check logger name and threshold:** class/package loggers may have their own level. TRACE/DEBUG will not pass Root INFO under normal circumstances.
3. **Global filter:** is it returning DENY early? Is a marker condition configured too strictly?
4. **LoggerConfig filter:** are filters on child/parent loggers and additivity configured appropriately?
5. **AppenderRef:** does `ref` match the appender name, does `level` exclude INFO on the path you are checking, and is there a marker/context filter?
6. **Appender filter:** do ThresholdFilter, LevelMatchFilter, RegexFilter, and `Filters` have the right conditions and onMismatch values?
7. **Destination:** are the file path, write permissions, disk space, stdout/stderr, buffering, async queue, rotation, and collector working?
8. **Merged configs or bridges:** are there multiple configs, multiple backends, or circular log-forwarding paths causing unexpected output?

Use Log4j Core's status logging or configuration initialization messages to detect plugins that failed to load. When debugging configuration, test a DEBUG/INFO/WARN/ERROR matrix along with at least one matching and non-matching marker and context event. Reduce diagnostic logging once fixed.

## 10. Security and Operations

Filters help control **log destinations and volume**, but they are **not a secret-redaction tool**. Do not print passwords, tokens, cookies, or payloads containing unnecessary personal data and expect regex to filter them all out. Select safe fields at the event emission site and use an encoder with proper escaping for newlines and control characters from untrusted input.

A filtering policy also does not replace retention, file permissions, transport encryption, or storage policies. Logs may be copied via collectors/backups; events dropped by a filter cannot be recovered from that destination if no other copy exists.

Especially with `BurstFilter` or sampling/rate-limiting mechanisms, measure dropped events and ensure a path exists to preserve critical events. Do not claim logging is "free" just because a filter drops 99% of lines at the end of the pipeline.

## 11. Common Mistakes

| Mistake | Consequence | Fix |
| --- | --- | --- |
| Treating ACCEPT as bypassing all stages | Easy to misunderstand why logs appear or not | Clearly note filter placement and stage |
| Confusing NEUTRAL with DENY | Unclear why events continue | Treat NEUTRAL as passing the decision onward |
| Using ThresholdFilter WARN to get only WARN | ERROR/FATAL still pass through | Use LevelMatchFilter WARN if exact match is needed |
| Using an appender filter to recover DEBUG | DEBUG was already blocked at the logger | Configure level or global stage deliberately |
| Setting onMismatch=DENY on the first filter in an OR | Subsequent filters never get evaluated | Use NEUTRAL on mismatch for OR branches |
| Applying RegexFilter to every event | High rendering/CPU cost, fragile on text changes | Prefer level, marker, or context |
| Forgetting AppenderRef | Appender receives no events | Attach the matching ref in Logger/Root |
| Ignoring additivity | Duplicate logs or unexpected filtering on parent path | Inspect the child-parent logger route |
| Leaving BurstFilter unbounded/unmonitored | Losing events needed for investigation | Track drops and exempt critical logs from sampling |
| Using filters instead of redaction | Secret leakage | Emit only safe fields; encode/escape per destination |
| Looking only at the Root level line | Missing per-stage filters | Inspect the entire pipeline from source to appender |
