# Generic Records and Parameterized Components in Java

A `record` in Java is a specialized class declaration designed to carry data. A **generic record** combines the record structure with **type parameters**, enabling the same data template to apply to many kinds of values while the compiler still enforces type relationships. For example, `Pair<String, Integer>` holds a `String` key and an `Integer` value, while `Pair<Long, String>` uses that exact same record declaration with two different type arguments.

This lesson focuses on **how to declare generic records, the meaning of parameterized record components, the members generated by the compiler, the relationship between type parameters and constructors/accessors, implementing generic interfaces, data validation, and runtime limitations to know**. The examples run on Java 17 or later.

## 1. What Is a Record and Why Combine It with Generics?

A record declares a *state description* in its header, which is a sequence of **record components** with names and types:

```java
record User(String name, int age) {
}
```

This is an illustrative declaration without `main`. From the list of components, Java provides the members needed to use the record as structured data: `private final` component fields, accessors named identically to the components (`name()`, `age()`), a canonical constructor, `equals`, `hashCode`, and `toString`, unless some of those members are explicitly declared according to record rules.

If each component were replaced by `Object` for reuse across multiple data types, callers would have to cast and the compiler would no longer know the relationship between input and output elements. Generic records solve that:

```java
record Box<T>(T value) {
}
```

Here:

- `Box<T>` is the **generic record declaration**; `T` is the record's type parameter.
- `T value` is a **parameterized record component**: the `value` component has a type that depends on `T`.
- `Box<String>` and `Box<Integer>` are two **uses** of the record, supplying type arguments for `T`.
- `value()` of `Box<String>` has expression type `String`; `value()` of `Box<Integer>` has expression type `Integer` at the call site.
- Two instantiations do not create two distinct JVM classes; Java uses type erasure for generics.

A regular record also does not automatically make data *deeply immutable*: the component field is final, yet the object referenced by the component can still be mutable. This is very important for components of type `List<T>`, `Map<K,V>`, or arrays.

## 2. Basic Syntax of a Generic Record

General form:

```java
record RecordName<T1, T2>(T1 first, T2 second) {
    // Constructor, validation, methods, or static members if needed.
}
```

The snippet above is a syntax pattern, not a standalone runnable Java class. `T1` and `T2` are type parameters declared immediately after the record name. Within the component list, they are used like normal types.

### Complete Example: Pair with Two Type Variables

Create the file `GenericPairDemo.java`:

```java
public class GenericPairDemo {
    record Pair<K, V>(K key, V value) {
    }

    public static void main(String[] args) {
        Pair<String, Integer> score = new Pair<>("Lan", 9);
        Pair<Long, String> status = new Pair<>(100L, "OK");

        String student = score.key();
        Integer mark = score.value();

        System.out.println(student + ": " + mark);
        System.out.println(status.key() + " -> " + status.value());
        System.out.println(score);
    }
}
```

Compile and run with JDK 17+:

```bash
javac GenericPairDemo.java
java GenericPairDemo
```

`stdout`:

```text
Lan: 9
100 -> OK
Pair[key=Lan, value=9]
```

Explanation:

1. `Pair<K,V>` declares two independent type parameters: `K` is the type of the `key` component, and `V` is the type of the `value` component.
2. `Pair<String,Integer>` binds `K=String`, `V=Integer` for the `score` variable. The compiler allows assigning `score.key()` to `String` and `score.value()` to `Integer`.
3. `Pair<Long,String>` is the same record used with different data types.
4. The diamond syntax `new Pair<>(...)` lets the compiler infer type arguments from context and constructor arguments.
5. The record's accessors are `key()` and `value()`; it **does not automatically generate** `getKey()` or `getValue()`.
6. The record-generated `toString()` displays the record name and each component according to the declared structure; in this example, `Pair[key=Lan, value=9]`.

If `new Pair<>("Lan", 9)` were replaced with `new Pair<>(9, "Lan")` while still assigning to `Pair<String,Integer>`, the compiler would reject it because the two type arguments are incompatible with the contract at the assignment site.

## 3. Tracing Type Parameters Across Individual Record Components

A generic record can use type parameters in one or more components, and can combine them with concrete-typed components:

```java
record Event<ID, P>(
        ID id,
        String topic,
        P payload,
        java.time.Instant createdAt) {
}
```

This is an illustrative declaration. Let's tabulate the signature:

| Member | Declared Type | Depends On |
| --- | --- | --- |
| `id` | `ID` | First type argument of `Event<ID,P>` |
| `topic` | `String` | Fixed type, does not depend on type arguments |
| `payload` | `P` | Second type argument of `Event<ID,P>` |
| `createdAt` | `Instant` | Fixed type |
| `id()` | `ID` | Same `ID` as component `id` |
| `payload()` | `P` | Same `P` as component `payload` |

With `Event<Long, String>`, the compiler treats `id()` as returning `Long` and `payload()` as returning `String`. With `Event<String, byte[]>`, `id()` returns `String` while `payload()` returns `byte[]`. Regardless of `Event`'s type arguments, `topic()` always returns `String` and `createdAt()` always returns `Instant`.

**How to read it:** whenever you see `T` or another type variable name in the header, locate the `<T>` declaration right after the record name. Positions using the same `T` in the record share the same type choice. A component that does not use a type variable keeps its normally declared type.

### Nested Generic Components

You can declare record components such as:

```java
record Batch<T>(
        String label,
        java.util.List<T> items,
        java.util.Map<String, T> index) {
}
```

`T` is used in two generic type arguments: `List<T>` and the `V` value of `Map<String,T>`. With `Batch<Integer>`, `items()` has type `List<Integer>` and `index()` has type `Map<String,Integer>`. The generics inside the components are not redeclaring a new `T`: they are using the `T` already present in the record header.

A component can be `List<List<T>>`, `Map<String, List<T>>`, or `Optional<T>`; read from the outer generic inward.

## 4. Members Java Provides from Generic Record Components

Consider:

```java
record Box<T>(T value) {
}
```

At the API-reading model level, you can picture the corresponding members:

```java
// This is only an explanatory model, not how
// Java translates a record into source code.
final class Box<T> {
    private final T value;

    public Box(T value) {
        this.value = value;
    }

    public T value() {
        return value;
    }

    // equals(Object), hashCode(), toString() are provided.
}
```

The model above **does not replace all semantics of a record**, yet makes it clear how the generic type parameter flows from the component to the constructor and accessor.

### 4.1. Component Fields Are Final

Each record component corresponds to a `private final` instance field. Once the canonical constructor finishes, that field cannot be reassigned:

```java
record Count<T>(T value) {
    // void replace(T x) {
    //     this.value = x; // Error: component field is final.
    // }
}
```

Generic typing and final fields are two independent properties. `T` checks **the value type**, while `final` prevents **changing the reference in the field**. If `T` is a mutable object type, callers can still modify the internal state of the object the record holds.

### 4.2. Accessors Have Types Dependent on Type Arguments

With `record Box<T>(T value)`, the accessor `value()` has return type `T`. Therefore:

```java
Box<String> a = new Box<>("Java");
String text = a.value();

// Integer wrong = a.value(); // Compile error.
```

These are illustrative usage lines; to run, place them inside a class/method where `Box<T>` is declared. There is no need to write a cast `(String) a.value()` in properly typed calling code.

### 4.3. Canonical Constructor Has a Parameter List Matching Components

Record `Pair<K,V>(K key,V value)` has a canonical constructor corresponding to the two components, in exact order. You can read the constructor relationship as `Pair(K key, V value)`. This is a source-level type relationship, not two different runtime constructors for `String` and `Integer`.

A record can declare additional constructors, yet any *non-canonical* constructor must delegate to another constructor of the same record via `this(...)` so all components are properly initialized.

### 4.4. `equals`, `hashCode`, and `toString`

Records provide equality based on the record type and component values, along with matching hash functions and textual representations. With `record Pair<K,V>(K key,V value)`, `Pair<String,Integer>` and `Pair<String,Number>` remain different parameterizations of **the same runtime class `Pair`**. When actual components contain equal values, `equals` can return true even if the generic declarations on two variables differ.

Conversely, if a component is an array, comparing the component's array reference does not automatically compare individual array elements. If value equality by array content is needed, appropriate handling must be designed (such as using an immutable structure with content-based `equals` or implementing the record methods consistently).

## 5. Canonical Constructors and Compact Constructors in Generic Records

Records can validate component conditions before assigning them to fields. The **compact constructor** syntax is especially useful because it avoids repeating the parameter list.

### Complete Example: Immutable List Copy

Create `GenericBatchDemo.java`:

```java
import java.util.ArrayList;
import java.util.List;
import java.util.Objects;

public class GenericBatchDemo {
    record Batch<T>(String name, List<T> items) {
        Batch {
            Objects.requireNonNull(name, "name");
            items = List.copyOf(items);
        }
    }

    public static void main(String[] args) {
        List<String> mutable = new ArrayList<>(
                List.of("Java", "Kotlin"));

        Batch<String> batch = new Batch<>("languages", mutable);
        mutable.add("Scala");

        System.out.println(batch.name());
        System.out.println(batch.items());
        System.out.println(mutable);
    }
}
```

Run:

```bash
javac GenericBatchDemo.java
java GenericBatchDemo
```

`stdout`:

```text
languages
[Java, Kotlin]
[Java, Kotlin, Scala]
```

Explanation:

- `Batch<T>` declares one concrete-typed component `String name` and one nested generic component `List<T> items`.
- `Batch { ... }` is a compact canonical constructor; it sits in the record body **without** an explicit parameter list.
- Inside a compact constructor, the names `name` and `items` refer to the **implicit parameters** corresponding to the record components. Assigning `items = List.copyOf(items)` modifies the parameter value that will be stored into the `items` field after the constructor body finishes.
- `List.copyOf` creates an unmodifiable list and, when necessary, a copy holding the existing elements. Thus modifying `mutable` after creating `Batch` does not alter the element count in `batch.items()`.
- `List.copyOf` does not accept null elements; if the input is null or contains null, the operation can throw `NullPointerException`. This is the API's behavior, **not** `T` automatically preventing null.
- The copy above is a **shallow copy**: if `T` is a mutable object (such as `StringBuilder`), mutating that object's contents can still be observed through the list inside the record.

In a compact constructor, **do not** assign `this.items = ...` directly. Component field initialization happens after the compact constructor body completes, using the corresponding parameters.

### Explicit Canonical Constructor

If you want to declare the canonical constructor explicitly with all parameters, you must initialize the component fields precisely:

```java
import java.util.Objects;

record NonNullValue<T>(T value) {
    NonNullValue(T value) {
        this.value = Objects.requireNonNull(value);
    }
}
```

This is a valid Java declaration; it has no `main`. The canonical constructor has the exact list of component parameters. You cannot declare both a compact canonical constructor and another canonical constructor in the same record.

### Checking Constraints in Constructors

A generic record `Range<T>` does not automatically know that every `T` is comparable. If the constructor needs to compare endpoints, declare a bound right on the type parameter:

```java
record Range<T extends Comparable<? super T>>(T start, T end) {
    Range {
        java.util.Objects.requireNonNull(start);
        java.util.Objects.requireNonNull(end);
        if (start.compareTo(end) > 0) {
            throw new IllegalArgumentException("start > end");
        }
    }
}
```

The bound `Comparable<? super T>` tells the compiler that `T` can be compared with another `T`, within compatible inheritance bounds. If `T` lacks an appropriate bound, the call `start.compareTo(end)` is not guaranteed by the compiler.

## 6. Bounded Type Parameters on Generic Records

Constraints can be declared directly in the record header:

```java
record Measurement<N extends Number>(String unit, N value) {
    double asDouble() {
        return value.doubleValue();
    }
}
```

Here:

1. `N` is declared at `Measurement<N extends Number>`.
2. `Number` is the upper bound: `N` must satisfy a subtype relationship with `Number`.
3. Component `value` uses `N`; accessor `value()` returns `N` at compile time.
4. Instance method `asDouble()` returns primitive `double`, not `N`. The compiler allows calling `doubleValue()` because the bound guarantees it.

Runnable example in `BoundedRecordDemo.java`:

```java
public class BoundedRecordDemo {
    record Measurement<N extends Number>(String unit, N value) {
        double asDouble() {
            return value.doubleValue();
        }
    }

    record Range<T extends Comparable<? super T>>(T start, T end) {
        Range {
            if (start.compareTo(end) > 0) {
                throw new IllegalArgumentException("start > end");
            }
        }
    }

    public static void main(String[] args) {
        Measurement<Integer> count = new Measurement<>("items", 12);
        Measurement<Double> weight = new Measurement<>("kg", 2.5);
        Range<Integer> interval = new Range<>(1, 10);

        System.out.println(count.asDouble());
        System.out.println(weight.asDouble());
        System.out.println(interval.start() + ".." + interval.end());
    }
}
```

Run:

```bash
javac BoundedRecordDemo.java
java BoundedRecordDemo
```

`stdout`:

```text
12.0
2.5
1..10
```

`Measurement<String>` is invalid because `String` does not extend `Number`. `Range<Integer>` is valid because `Integer` has the corresponding `Comparable<Integer>` relationship.

### Multiple Bounds

You can use multiple bounds for one type parameter:

```java
record Ranked<T extends Number & Comparable<T>>(T value) {
}
```

If there is a class bound, it must precede interface bounds; interface bounds are joined with `&`. `extends` is used for both class and interface bounds in type parameter declarations. When you only need to hold data without invoking specific behaviors, **do not** impose bounds on every `T`.

## 7. Generic Records Implementing Generic Interfaces

A record cannot `extends` an arbitrary class; it directly extends `java.lang.Record` and is final. However, a record **can implement interfaces**, including generic interfaces, thereby participating in abstract contracts.

Create `GenericRecordInterfaceDemo.java`:

```java
public class GenericRecordInterfaceDemo {
    interface Identified<ID> {
        ID id();
    }

    record Entity<ID, T>(ID id, T payload)
            implements Identified<ID> {
    }

    static <ID> void printId(Identified<ID> value) {
        System.out.println(value.id());
    }

    public static void main(String[] args) {
        Entity<Long, String> message =
                new Entity<>(42L, "queued");

        printId(message);
        System.out.println(message.payload());
    }
}
```

Run:

```bash
javac GenericRecordInterfaceDemo.java
java GenericRecordInterfaceDemo
```

`stdout`:

```text
42
queued
```

Explanation:

- `Identified<ID>` declares the contract `ID id()`.
- `Entity<ID,T>` declares two record type parameters of its own.
- `implements Identified<ID>` **passes** the record's type parameter `ID` as the interface's type argument.
- Record component `ID id` generates the corresponding accessor `id()` and fulfills the interface method; no extra `getId()` needs to be written.
- Method `printId` declares its own type parameter `ID`; when passed `Entity<Long,String>`, the compiler can infer the corresponding ID type.
- Not every interface is automatically satisfied by a record via components alone. The name, return type, and method contract must genuinely match; if an interface requires `getId()`, component `id` does not generate that method.

A record can also implement multiple interfaces. Because a record itself is final, you cannot write `class Derived extends Entity<...>` to inherit from it.

## 8. Generic Instance Methods in Records

In addition to using the record's type parameter, an instance method can also declare **a new type parameter** at method scope. This allows a record to hold `T` while a transformation produces `R`.

Create `GenericRecordMethodDemo.java`:

```java
import java.util.function.Function;

public class GenericRecordMethodDemo {
    record Box<T>(T value) {
        <R> Box<R> map(Function<? super T, ? extends R> converter) {
            return new Box<>(converter.apply(value));
        }
    }

    public static void main(String[] args) {
        Box<String> text = new Box<>("Java");
        Box<Integer> size = text.map(String::length);
        Box<String> description = size.map(n -> "length=" + n);

        System.out.println(size.value());
        System.out.println(description.value());
    }
}
```

Run:

```bash
javac GenericRecordMethodDemo.java
java GenericRecordMethodDemo
```

`stdout`:

```text
4
length=4
```

Reading each constraint:

| Symbol | Declared At | Meaning at Call `text.map(String::length)` |
| --- | --- | --- |
| `T` | `record Box<T>` | Type of the currently held value: `String` |
| `R` | `<R> Box<R> map(...)` | Result type of the transformation: `Integer` |
| `? super T` | Wildcard used in `Function` | Function accepts values of type `T` |
| `? extends R` | Wildcard used in `Function` | Function produces values compatible with `R` |

`Box<String>` and `Box<Integer>` are the same record declaration, yet calling `map` creates a new object carrying a different type argument at compile time. This does not mutate the `text` object.

### Static Methods and Record Type Parameters

A static method cannot directly use `record Box<T>`'s `T` as an independent type because `T` is tied to an instantiation of the record, whereas static methods belong to the class. If you want a generic static factory, declare a **method** type parameter:

```java
record Box<T>(T value) {
    static <U> Box<U> of(U value) {
        return new Box<>(value);
    }
}
```

The snippet above is valid though it has no `main`. For example, `Box.of("hello")` can infer `U=String`. `U` on the method is a different type variable from `T` on the record; the type argument of `Box<U>` is determined from `U` when creating the result.

## 9. Type Inference When Creating Generic Records

Like other generic classes, generic records can use the diamond `<>` for Java to infer type arguments. There are two important sources of inference: **target type** and **constructor arguments**.

### Selecting Type by Target

```java
record Pair<K, V>(K key, V value) {}

Pair<String, Integer> p = new Pair<>("A", 1);
```

The compiler uses the target type `Pair<String,Integer>` and the passed data to apply `K=String`, `V=Integer`. If an argument is changed to an incompatible type, `javac` reports an error.

### Selecting Type by Initializer

```java
var p = new Pair<>("A", 1);
```

With Java 17, `var` infers the local variable type from the initializer; here it can infer `Pair<String,Integer>`. `var` does not make the variable dynamically typed and does not declare additional type parameters. Once inferred, the compiler still checks `p`'s accessors against the determined static type.

### Explicit Type Arguments and Raw Types

```java
Pair<String, Integer> a = new Pair<String, Integer>("A", 1);
Pair<String, Integer> b = new Pair<>("A", 1);
```

These two forms declare the exact same type contract for `a` and `b`. The diamond form is shorter.

Avoid raw types:

```java
Pair raw = new Pair("A", 1);
```

Raw types weaken generics type checking and can emit `rawtypes`/`unchecked` warnings. Do not treat records as an exception: generic records remain subject to raw-type rules just like regular generic classes.

### Primitive Type Arguments Are Not Supported

`Pair<int, double>` is syntactically invalid as generic type arguments. You must use wrappers `Pair<Integer, Double>`; boxing/unboxing converts primitive values where appropriate.

## 10. Generic Records Holding Collections and Nested Types

A generic record is not limited to direct `T` components; it can hold generic collections with linked type arguments.

Create `NestedGenericRecordDemo.java`:

```java
import java.util.List;
import java.util.Map;

public class NestedGenericRecordDemo {
    record Catalog<K, V>(
            Map<K, List<V>> entries,
            String label) {
    }

    public static void main(String[] args) {
        Map<String, List<Integer>> scores = Map.of(
                "Lan", List.of(8, 9),
                "Mai", List.of(7));

        Catalog<String, Integer> catalog =
                new Catalog<>(scores, "scores");

        List<Integer> lan = catalog.entries().get("Lan");
        System.out.println(catalog.label());
        System.out.println(lan);
        System.out.println(lan.get(0));
    }
}
```

Run:

```bash
javac NestedGenericRecordDemo.java
java NestedGenericRecordDemo
```

`stdout`:

```text
scores
[8, 9]
8
```

Reading types layer by layer:

1. `Catalog<K,V>` declares `K` and `V`.
2. Component `entries` has type `Map<K,List<V>>`.
3. With `Catalog<String,Integer>`, accessor `entries()` has type `Map<String,List<Integer>>`.
4. `Map.get(Object)` returns the map's `V`, which is `List<Integer>` here; note that `Map.get` takes `Object` in the Java API, even though the map's key is declared `String`.
5. `List<Integer>.get(0)` has expression type `Integer`.

Similarly, an `Optional<T>` component helps represent presence/absence via the `Optional` API, though the generic type itself does not forbid a null component; forbidding null requires explicit checking or an invariant.

## 11. Invariance of Generic Type Arguments

Even though `Integer extends Number`, you cannot assign `Pair<String,Integer>` directly to `Pair<String,Number>`:

```java
record Pair<K, V>(K key, V value) {}

Pair<String, Integer> integerPair = new Pair<>("A", 7);
// Pair<String, Number> numberPair = integerPair; // Invalid.
```

Java's generic type arguments are fundamentally **invariant**. This remains true for records even though component fields are final and records have no setters; the compiler applies the generic typing rules of `Pair<K,V>`, and does not automatically convert it to covariance just because a record is immutable at the field level.

### Using Wildcards When Flexible Reading Is Needed

```java
Pair<String, ? extends Number> numberView = integerPair;
Number number = numberView.value();
```

These are illustrative lines placed in scope with `Pair<K,V>` and `integerPair`. The wildcard `? extends Number` accepts a record whose value is a subtype of `Number`. When reading `numberView.value()`, the compiler allows treating the result as `Number`.

You cannot arbitrarily change the component type of an already-created record because there are no setters; when a different record is needed, create a new object with the appropriate target type. If you want to accept multiple types when **designing methods**, wildcards on parameters can be useful, such as `Pair<String, ? extends Number>` or `Pair<?, ?>`.

### A Raw Record Is Not "Any Valid Pair"

Raw `Pair` discards compile-time type relationships. `Pair<?,?>` preserves the information that the record has two unknown type parameters and helps avoid many unchecked operations. If you only need to print the record or read components as `Object`, wildcards are better than raw types.

## 12. `equals` and Type Arguments: Runtime Data Must Be Considered

Generic typing checks at compile time, yet two parameterizations of the same record do not cause Java to generate separate runtime classes. Example:

Create `RecordEqualityDemo.java`:

```java
public class RecordEqualityDemo {
    record Pair<K, V>(K key, V value) {
    }

    public static void main(String[] args) {
        Pair<String, Integer> exact = new Pair<>("A", 1);
        Pair<String, Number> wide = new Pair<>("A", 1);

        System.out.println(exact.getClass().equals(wide.getClass()));
        System.out.println(exact.equals(wide));
        System.out.println(exact.hashCode() == wide.hashCode());
    }
}
```

Run `javac RecordEqualityDemo.java` and `java RecordEqualityDemo`:

```text
true
true
true
```

Both objects share the same runtime class `Pair`, with components holding equal string `"A"` and boxed integer `Integer(1)`. The fact that one variable has type argument `V=Integer` and the other has `V=Number` does not force `equals` to return false.

**Do not overgeneralize** this to "two differently named generic record types with identical components will be equal": record equality only compares against objects of the same record class. Also do not assume `Integer(1)` and `Long(1L)` are equal under `equals`; they are different wrapper types whose `equals` are not equivalent.

### Cases That Are Not Deeply Immutable

- Component is `ArrayList<T>`: the component field cannot be reassigned, yet `add` can be called via a reference if the list is mutable.
- Component is `Map<K,V>`: keys/values can be modified through a mutable map, unless copied/wrapped with an appropriate policy.
- Component is `T[]`: array elements can be mutated, so protection requires cloning upon receipt and upon return.
- Component is itself a mutable `T` object: holding a final reference does not freeze that object's state.

When a record is a DTO shared across parts of a program, clearly document component mutability and use **defensive copies** at appropriate boundaries.

## 13. Defensive Copies and the Limits of "Immutable Records"

This is the most common mistake when a record component is a generic collection:

```java
record BadSnapshot<T>(java.util.List<T> items) {}
```

Creating `BadSnapshot<String> snapshot = new BadSnapshot<>(mutableList)` does not automatically copy the list. `snapshot.items()` returns the exact reference stored. If the caller still holds the list and mutates it, the snapshot will observe those changes.

### Better Design for a `List<T>` Component

```java
record Snapshot<T>(java.util.List<T> items) {
    Snapshot {
        items = java.util.List.copyOf(items);
    }
}
```

`List.copyOf` creates an unmodifiable list; at the same time the input cannot be null and cannot contain null elements. If the input is already a suitable immutable list, the implementation may reuse it instead of always allocating a copy; the reliable contract is that the resulting snapshot does not change when modifying the source list via an alias.

However, if each `T` is a mutable object, `List.copyOf` only protects the list structure and **does not clone individual elements**. Deep cloning or immutable representations of individual elements are required if the problem truly demands deep immutability.

### With Arrays, Defend at Both Ends

```java
record Bytes(byte[] data) {
    Bytes {
        data = data.clone();
    }

    @Override
    public byte[] data() {
        return data.clone();
    }
}
```

This snippet is a valid declaration without `main`. The constructor clones the data upon receipt; the accessor clones again so callers cannot mutate the internal array directly. Array components also raise the issue of record `equals`/`hashCode`: by default they do not automatically compare array contents; if you want to use a record as a value with byte-level equality, design consistent overrides or choose a different representation.

Takeaway: **type parameter T**, **final component**, and **immutability of the object graph** are three different concepts.

## 14. Type Erasure and Reflection on Generic Records

Records are classes in the JVM; generic records undergo **type erasure** like other generic classes. `Box<String>` and `Box<Integer>` do not have two specialized runtime classes. However, generic metadata of **the record declaration and components** can be read via reflection.

Create `RecordReflectionDemo.java`:

```java
import java.lang.reflect.RecordComponent;
import java.util.List;

public class RecordReflectionDemo {
    record Container<T>(List<T> values) {
    }

    public static void main(String[] args) {
        Container<String> a = new Container<>(List.of("A"));
        Container<Integer> b = new Container<>(List.of(1));

        System.out.println(a.getClass().equals(b.getClass()));
        System.out.println(Container.class.isRecord());

        RecordComponent component =
                Container.class.getRecordComponents()[0];

        System.out.println(component.getName());
        System.out.println(component.getType().getTypeName());
        System.out.println(component.getGenericType().getTypeName());
    }
}
```

Run:

```bash
javac RecordReflectionDemo.java
java RecordReflectionDemo
```

`stdout`:

```text
true
true
values
java.util.List
java.util.List<T>
```

Explanation:

- `getClass()` shows both objects have the same class `Container`.
- `Class.isRecord()` identifies that this class is a record.
- `Class.getRecordComponents()` returns `RecordComponent`s in the order components were declared. The example only has `values`, so index `0` is taken.
- `getName()` returns the component name.
- `getType()` returns the runtime class of the erased component type, here `java.util.List`.
- `getGenericType()` describes the declared generic type `List<T>`, because the generic signature of declarations can be recorded in the class file.

Reflection reading `java.util.List<T>` does not mean instance `a` carries `T=String` or instance `b` carries `T=Integer` for the JVM to enforce element types on its own. Type erasure still applies at runtime; declaration metadata and the type arguments of a specific reference are two different sources of information.

Do not use `getClass()` to distinguish `Container<String>` from `Container<Integer>`. If a serialization mechanism needs to understand `List<String>` or deeply nested types, you usually must pass appropriate target type metadata via `Type`, type tokens, or that library's API.

## 15. Generic Records vs. Generic Classes

Both use type parameters and both obey type erasure. The key differences come from **the record mechanism**, not from Generics:

| Aspect | Generic Record | Regular Generic Class |
| --- | --- | --- |
| Declaration | `record Pair<K,V>(K key,V value)` | `class Pair<K,V> { ... }` |
| Components/state | Header is the canonical state description; component fields are final | Choose fields yourself; can be mutable/final |
| Accessors | Java generates `key()`, `value()` matching component names | Write accessors yourself if wanted |
| Canonical constructor | Canonical constructor with parameters matching components | Design constructors yourself |
| equals/hashCode/toString | Provided based on components (unless validly overridden) | Inherited from `Object` if not self-defined |
| Class inheritance | Record is final and cannot extend arbitrary classes | Can inherit according to Java rules |
| Interfaces | Can implement generic interfaces | Can implement generic interfaces |
| Type parameters/erasure | Java Generics rules apply | Java Generics rules apply |
| Deep immutability | **Not automatically guaranteed** when components reference mutable objects | Depends on design |

**Choose a generic record** when an object primarily represents a set of values, a concise API is desired, and component semantics fit. **Choose a class** when you need to extend another superclass, internal state differs from the component list, lifecycle involves many mutations, or you want full control over the state model. Do not choose a record solely for shorter code if the API genuinely needs different encapsulation.

## 16. A Comprehensive Example: Record as a Typed Processing Result

An API often needs to return multiple related values. A generic record is a suitable structure for bundling results while keeping types clear.

Create `GenericResultDemo.java`:

```java
import java.util.List;
import java.util.Objects;
import java.util.function.Function;

public class GenericResultDemo {
    record Result<T>(T value, List<String> warnings) {
        Result {
            value = Objects.requireNonNull(value);
            warnings = List.copyOf(warnings);
        }

        <R> Result<R> map(Function<? super T, ? extends R> mapper) {
            return new Result<>(mapper.apply(value), warnings);
        }
    }

    public static void main(String[] args) {
        Result<String> input =
                new Result<>("Java", List.of("normalized"));

        Result<Integer> length = input.map(String::length);

        System.out.println(input.value());
        System.out.println(length.value());
        System.out.println(length.warnings());
    }
}
```

Run:

```bash
javac GenericResultDemo.java
java GenericResultDemo
```

`stdout`:

```text
Java
4
[normalized]
```

Type analysis:

1. `Result<T>` holds primary data in component `T value` and metadata in `List<String> warnings`.
2. `Result<String>` applies `T=String`, so `input.value()` has type `String`.
3. `map` declares a **method** type parameter `<R>`. With `String::length`, `R` is inferred as `Integer`, so `Result<R>` becomes `Result<Integer>` at the call site.
4. `warnings` does not depend on `T` or `R`; both input and result can appropriately share an unmodifiable list because the constructor runs `List.copyOf`.
5. `Result<Integer>` cannot be assigned directly to `Result<String>`. The type parameter is kept consistent by the compiler.
6. `Objects.requireNonNull(value)` and `List.copyOf(warnings)` represent additional runtime invariants. If the mapper returns null, `Result<R>`'s constructor will throw `NullPointerException`; Generics by itself does not prevent null.
7. Because `Result` is a record, creating a new result does not mutate `input`.

This example only serves the lesson on generic records and parameterized components. If an application needs a result model with success/failure branches, separate types can be designed with sealed interfaces and records in an advanced lesson.

## 17. Syntactic Constraints to Remember

| Situation | Valid? | Explanation |
| --- | --- | --- |
| `record Box<T>(T value) {}` | Yes | Record declares a type parameter. |
| `record Pair<K,V>(K key,V value) {}` | Yes | Multiple type variables. |
| `record Metrics<N extends Number>(N value) {}` | Yes | Bounded type parameter. |
| `record Items<T>(List<T> data) {}` | Yes, if List is imported | Nested generic component using `T`. |
| `record ArrayBox<T>(T[] values) {}` | Yes | Array-typed component of `T`; watch mutability. |
| `record Bad<T>(T value) { T extra; }` | No | Records cannot declare new instance fields outside components. |
| `record Bad<T>(T value) extends Parent {}` | No | Records cannot extend arbitrary superclasses. |
| `class Child extends Box<String> {}` | No, if Box is a record | Records are implicitly final. |
| `record Bad<T>(T value) { static T shared; }` | No | Static members cannot use the record's instance type parameter. |
| `record Bad(int x, ...)` with primitive type argument `T=int` | No | Generics require reference types as type arguments, not `int`. |
| `record Pair<K,V>(K key,V value) implements Serializable {}` | Yes, if interface is imported/qualified | Records can implement interfaces; they do not implement `Serializable` by default. |

The `Bad` examples are written to **illustrate compiler errors**; do not put them into a runnable file expecting successful compilation.

### Be Careful with Generic Varargs

A record header can use a varargs component in the last position just like constructor varargs, yet if the varargs depends on a non-reifiable generic type (like `T...`), the compiler may warn about possible heap pollution. Do not treat a record's final fields as a reason to ignore unchecked/varargs warnings. For public APIs, it is usually easier to design safely using a `List<T>` component combined with defensive copying.

### Null, `equals`, and Serialization

- `record Pair<K,V>(K key,V value)` can by default hold null in reference components; to forbid null, validate in the canonical constructor.
- Generated `equals`/`hashCode` rely on component values, without checking per-instance type arguments.
- Records **do not automatically** implement `Serializable` merely by being records. If Java serialization is needed, declare implementing the interface and understand record-specific serialization mechanics; do not infer it from generic types.
- Annotations on components can target the record component, field, accessor, or constructor parameter depending on annotation targets; this mechanism is independent of basic type parameter syntax.

## 18. Common Mistakes and How to Fix Them

### Mistake 1: Thinking Accessors Are Always `getX()`

`record Pair<K,V>(K key,V value)` provides `key()`/`value()`. Calling `getKey()` will not compile unless you declare that method yourself.

### Mistake 2: Omitting Type Arguments When Using Records

`Pair raw = new Pair("A", 1)` loses type information and produces raw/unchecked warnings. Use `Pair<String,Integer>` or `var pair = new Pair<>("A",1)` when inferred types are clear. If the types are genuinely unknown, use `Pair<?,?>` instead of a raw type.

### Mistake 3: Believing Final Components Make Collections Deeply Immutable

`record Box<T>(List<T> values)` only has a final field; it does not clone the list or make elements immutable. Consider `List.copyOf`, null checks, and deep copying when business needs require it.

### Mistake 4: Misunderstanding Type Invariance on Records

`Pair<String,Integer>` is not a subtype of `Pair<String,Number>`. When a flexible view for reading `Number` is needed, consider `Pair<String,? extends Number>`. Do not use unchecked casts just to silence compile errors.

### Mistake 5: Forgetting Bound Conditions

`Measurement<N extends Number>` does not accept `String` as a type argument. If an algorithm needs `Comparable`, declare the appropriate bound; do not cast blindly to `Comparable`.

### Mistake 6: Confusing Record Type Parameters with Method Type Parameters

`record Box<T>(T value) { <R> Box<R> map(...) { ... } }` has `T` belonging to the record and `R` belonging to the method. Each invocation of `map` can infer a different `R`, whereas the receiver's `T` is already determined by the type of `Box<T>`.

### Mistake 7: Expecting Runtime to Know `Pair<String,Integer>`

`getClass()` returns the same record class regardless of type arguments. Declaration metadata can be read with reflection, yet does not guarantee the JVM checks each object against `K=String`, `V=Integer`.

### Mistake 8: Writing Constructors Without Completing Component Initialization

Explicit canonical constructors must assign component fields. Compact constructors have their implicit assignments completed by the compiler after the body; do not assign `this.component` inside a compact constructor. Non-canonical constructors must call another constructor of the record via `this(...)`.

### Mistake 9: Placing Instance State Outside the Header

Records do not allow declaring arbitrary extra instance fields. If mutable state outside components is needed, a class is usually more suitable. Static constants or helper methods can be declared following Java rules.

## 20. Checklist When Designing a Generic Record

When preparing to create a generic record for a project, answer the following questions:

1. Does the record genuinely represent **a data-carrying set of components**? If deep custom lifecycle/state is needed, consider a class.
2. Where are type parameters `T`, `K`, `V` declared, and which components do they constrain? Are bounds needed?
3. What types do the record-generated accessors return at each concrete type argument?
4. Which invariants must the constructor protect (null, range, empty list, relationships between components)?
5. Are there mutable reference components? Is defensive copying, deep copying, or an immutable API needed?
6. Which operations should be instance methods, and which need a generic method `<R>` distinct from the record's type parameter?
7. Does the record need to implement a generic interface to fit a common contract?
8. Do callers need wildcards `? extends`/`? super` to accept multiple type arguments, or are concrete types enough?
9. Is custom equality/hashCode needed because a component holds an array or business equality differs from the default?
10. Are you relying on runtime generic type arguments that type erasure does not provide?

Generic records bring conciseness in declaration **and** type safety at compile time. Always trace type parameters from the record header to each component, accessor, and constructor; then evaluate independent runtime constraints such as null, mutability, and equality. That way of reading helps use records for DTOs, value objects, data pairs, and processing results while keeping APIs accurate, understandable, and verifiable.
