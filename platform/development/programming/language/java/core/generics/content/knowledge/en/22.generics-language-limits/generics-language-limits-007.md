# Disallowing Default Values for Type Parameters in Java Generics

## 1. Language limit to remember

In Java, when declaring a generic class, interface, record, or generic method, you can declare **type parameters** and place **bounds** on them. However, Java **has no syntax for declaring a default value for a type parameter**, such as "if the caller omits the type argument, automatically treat `T` as `String`".

The following snippets are **intentionally invalid** in Java 17:

```java
// INTENTIONALLY DOES NOT COMPILE — Java does not support default type arguments.
class Box<T = String> { }

interface Repository<T = Object> { }

record Pair<K, V = String>(K key, V value) { }

class Utility {
    static <T = String> T make() {
        return null;
    }
}
```

`T = String`, `V = String`, and `<T = String>` are not valid syntax in Java generic declarations. You cannot fix them by changing `String` to `Object`, using another wrapper, or adding an annotation.

The valid forms are:

```java
class Box<T> { }

interface Repository<T> { }

record Pair<K, V>(K key, V value) { }

class Utility {
    static <T> T make() {
        return null;
    }
}
```

If you want to restrict accepted types, Java provides `extends`, such as `<T extends Number>`. If you want to omit repeating type arguments at **the call site**, Java provides **type inference** and **the diamond operator `<>`**. If you want a default choice with **domain semantics** like "use `String`", create a factory method or specialized subtype.

> **Core distinction:** A *default type argument* is a rule attached directly to a type parameter declaration; *type inference* is the process where the compiler finds an appropriate type for **each expression/call** based on context and constraints. Java supports the latter, not the former.

## 2. Terminology: type parameter, type argument, bound, and inference

Consider:

```java
class Holder<T> {
    T value;
}
```

- `T` in `class Holder<T>` is the declared **type parameter**.
- `String` in `Holder<String>` is the **type argument** supplied at the usage site.
- In `Holder<T extends Number>`, `Number` is the **upper bound**, restricting which types can substitute for `T`.
- In `new Holder<>()`, `<>` asks the compiler to **infer type arguments** at the object-creation expression.
- In `Holder<?>`, `?` is a **wildcard**, representing an unknown type argument—not a default of `Object`.

Each usage carries a distinct meaning:

| Syntax | Valid? | Meaning |
|---|---|---|
| `class Holder<T> {}` | Yes | Declares a type parameter `T` |
| `class Holder<T = String> {}` | No | Java does not support default type arguments |
| `class Holder<T extends Number> {}` | Yes | Constrains `T` to be a subtype of `Number` |
| `Holder<String> h;` | Yes | Uses explicit type argument `String` |
| `Holder<?> h;` | Yes | Uses a wildcard for an unknown type argument |
| `Holder h;` | Yes, discouraged | Uses a **raw type** and bypasses generic checks in many places |
| `Holder<> h;` | No | Diamond cannot be used in a variable's type name |
| `Holder<String> h = new Holder<>();` | Yes | Diamond infers from the target type |
| `var h = new Holder<>();` | Yes with matching constructor | `var` takes its type from the initializer, not a `String` default |

Do not equate the compiler "figuring out" a type with the class having declared a default type.

## 3. Why does omitting type arguments not mean "use a default"?

Suppose the class is:

```java
class Container<T> {
    T value;
}
```

There are three ways to view it:

```java
Container<String> typed = new Container<>();
Container raw = new Container();
var inferred = new Container<>();
```

In this example, the default constructor generated by Java can be called with no arguments because the class declares no custom constructor.

- `typed` has static type `Container<String>` from the left-hand declaration.
- `raw` has raw type `Container`; the compiler does not know the argument `T`, and certain operations may trigger `rawtypes`/`unchecked` warnings.
- `inferred` has no `String` target context and the constructor takes no arguments. With an unbounded `T` like this, the compiler infers `Object`; the variable has static type `Container<Object>`.

The `Object` outcome in the last case is **the result of type inference lacking tighter constraints**, not a default type argument declared by `Container<T>`. If the constructor takes parameters or the expression has a different target type, the outcome can differ.

Saying "Java automatically defaults every `T` to `Object`" is also **false**. Type variables can have bounds; type inference uses context and type-selection rules. `Object` is simply a common outcome for an unbounded type parameter in an unconstrained expression.

## 4. Runnable example: diamond does not mean default type

Create the file **`NoDefaultTypeArgumentDemo.java`**:

```java
public class NoDefaultTypeArgumentDemo {

    static class Box<T> {
        private T value;

        Box() {
        }

        Box(T value) {
            this.value = value;
        }

        void set(T value) {
            this.value = value;
        }

        T get() {
            return value;
        }
    }

    public static void main(String[] args) {
        Box<String> targeted = new Box<>();
        targeted.set("Java");

        var inferred = new Box<>(42);
        Integer n = inferred.get();

        var noTarget = new Box<>();
        noTarget.set("first");
        noTarget.set(3);
        Object last = noTarget.get();

        System.out.println(targeted.get());
        System.out.println(n);
        System.out.println(last);
    }
}
```

Compile/run on JDK 17 or later:

```bash
javac NoDefaultTypeArgumentDemo.java
java NoDefaultTypeArgumentDemo
```

Stdout:

```text
Java
42
3
```

Analysis:

1. `Box<String> targeted = new Box<>()` has target context `Box<String>`; the parameterless constructor still infers `T = String`.
2. `var inferred = new Box<>(42)` has no target type due to `var`, but **the constructor argument** `42` contributes to inferring `T = Integer` (via boxing).
3. `var noTarget = new Box<>()` has no constraints on the unbounded type variable `T`, so the element type is inferred as `Object`.
4. `noTarget.set("first")` and `noTarget.set(3)` are both valid because `String` and `Integer` are reference types assignable to `Object`.
5. `set(...)` calls **after** the declaration do not make `noTarget`'s type "learn" from `String` and switch to `Integer`; the type is fixed at the initializer.

To test the compiler yourself, try adding this line at the end of `main`:

```java
// INTENTIONAL ERROR, do not add to the runnable version:
// targeted.set(10); // Compiler rejects because targeted's T is String.
```

Diamond merely **elides rewriting** the type argument when the compiler can infer it; it adds no default syntax to `Box`.

## 5. `var` does not supply a default type argument

`var` is a **local-variable type inference** mechanism (Java 10+), not notation for an optional generic type argument.

Compare:

```java
java.util.List<String> a = new java.util.ArrayList<>();
var b = new java.util.ArrayList<String>();
var c = new java.util.ArrayList<>();
```

The inferred static types:

| Variable | Static type |
|---|---|
| `a` | `List<String>` |
| `b` | `ArrayList<String>` |
| `c` | `ArrayList<Object>` when no more specific info exists |

The difference between `a` and `b` is not just shorter vs longer syntax: `a` is declared through the `List` interface, whereas `b` infers the concrete implementation class `ArrayList`.

A common misconception is:

> "I wrote `var list = new ArrayList<>()`, then `list.add("A")`, so the compiler will default the list's type to `String`."

False: `list` was already determined as `ArrayList<Object>` given the zero-arg constructor and absence of a target type. Calling `add("A")` does not alter the variable's static type.

If a list of strings is required, state the intent explicitly in either of two ways:

```java
java.util.List<String> list = new java.util.ArrayList<>();
var another = new java.util.ArrayList<String>();
```

Both forms let the compiler reject adding an `Integer` to a list meant to hold only `String`.

## 6. Type arguments inferred from constructors differ from defaults

A constructor can supply type information to the compiler through **the types of passed arguments**.

Create the file **`ConstructorInferenceDemo.java`**:

```java
public class ConstructorInferenceDemo {

    record Pair<L, R>(L left, R right) {
    }

    public static void main(String[] args) {
        Pair<String, Integer> a = new Pair<>("age", 21);

        var b = new Pair<>("score", 99);

        String label = b.left();
        Integer score = b.right();

        System.out.println(a.left() + "=" + a.right());
        System.out.println(label + "=" + score);
    }
}
```

Commands:

```bash
javac ConstructorInferenceDemo.java
java ConstructorInferenceDemo
```

Stdout:

```text
age=21
score=99
```

In `new Pair<>("score", 99)`, the compiler sees constructor arguments `String` and `int` (boxed to `Integer` during inference), so it infers type arguments `L = String`, `R = Integer` even with `var` on the left.

In `new Pair<>("age", 21)`, the target type `Pair<String, Integer>` also contributes inference context.

These are two different constraint sources, both **belonging to the specific call**. They do not give `Pair<L,R>` two default type arguments in its declaration.

## 7. An upper bound is not a default value

Java supports:

```java
class NumericBox<T extends Number> {
    T value;
}
```

`T extends Number` means **`T` must be `Number` or a valid subtype of `Number`**, not "`T` defaults to `Number` whenever `<...>` is omitted".

Valid usages:

```java
NumericBox<Integer> a = new NumericBox<>();
NumericBox<Double> b = new NumericBox<>();
NumericBox<Number> c = new NumericBox<>();
```

Whereas:

```java
// INTENTIONALLY INVALID:
NumericBox<String> bad = new NumericBox<>();
```

is rejected by the compiler because `String` does not extend `Number`.

### Bounds affect inference results when constraints are absent

With a class like `NumericBox<T extends Number>`, if you write `var x = new NumericBox<>()` with no data constraining `T` further, the compiler can choose `Number` as a compatible type according to its bounds. This is a **type-inference rule based on upper bounds**, not a generic default declared with `T = Number` syntax.

### Runnable example with a bound

File **`BoundIsNotDefaultDemo.java`**:

```java
public class BoundIsNotDefaultDemo {

    static class NumericBox<T extends Number> {
        private T value;

        void set(T value) {
            this.value = value;
        }

        T get() {
            return value;
        }
    }

    public static void main(String[] args) {
        NumericBox<Integer> integers = new NumericBox<>();
        integers.set(8);

        var inferred = new NumericBox<>();
        inferred.set(2.5);

        Number asNumber = inferred.get();

        System.out.println(integers.get());
        System.out.println(asNumber);
    }
}
```

Run:

```bash
javac BoundIsNotDefaultDemo.java
java BoundIsNotDefaultDemo
```

Stdout:

```text
8
2.5
```

Whether the example uses explicit `<Integer>` or infers from `<>`, the compiler still enforces the `T extends Number` bound. An upper bound **narrows the set of allowed types**, whereas a default type argument (nonexistent in Java) would be a rule **picking a single type when information is omitted**.

With multiple bounds, such as `<T extends Number & Comparable<T>>`, there is still no default type parameter. Bound order affects erasure and which members are callable on `T`, rather than adding `= SomeType` syntax.

## 8. Generic methods also have no default type parameters

This limit does not apply only to classes or records. A generic method is declared like:

```java
static <T> T identity(T value) {
    return value;
}
```

You cannot declare:

```java
// INTENTIONALLY DOES NOT COMPILE:
static <T = String> T identity(T value) {
    return value;
}
```

When calling `identity("hello")`, the compiler infers `T = String` from the argument. When a call lacks sufficient information, the compiler continues applying inference rules rather than reading a default type argument from the declaration.

A generic method can be invoked with an **explicit type witness**:

```java
Utility.<String>identity("hello")
```

If `identity` is a contextually visible static method on `Utility`, `<String>` at the call site **sets the method's type argument**. It does not alter how the method is declared and is not a cast.

## 9. Runnable example: target typing and method type witnesses

Create the file **`GenericMethodInferenceDemo.java`**:

```java
import java.util.ArrayList;
import java.util.List;

public class GenericMethodInferenceDemo {

    static <T> List<T> empty() {
        return new ArrayList<>();
    }

    static <T> T echo(T value) {
        return value;
    }

    public static void main(String[] args) {
        List<String> targetTyped = empty();
        targetTyped.add("A");

        var inferredWithoutTarget = empty();
        inferredWithoutTarget.add(10);
        inferredWithoutTarget.add("B");

        var explicitlyTyped =
                GenericMethodInferenceDemo.<String>empty();
        explicitlyTyped.add("C");

        String echoed = echo("Java");

        System.out.println(targetTyped);
        System.out.println(inferredWithoutTarget);
        System.out.println(explicitlyTyped);
        System.out.println(echoed);
    }
}
```

Compile/run:

```bash
javac GenericMethodInferenceDemo.java
java GenericMethodInferenceDemo
```

Stdout:

```text
[A]
[10, B]
[C]
Java
```

Explanation:

- `List<String> targetTyped = empty()` supplies a target type so the compiler infers `T` compatible with `String`.
- `var inferredWithoutTarget = empty()` lacks a `List<String>` target type and `empty()` takes no arguments. With unbounded `T` here, `T` is inferred as `Object`.
- `GenericMethodInferenceDemo.<String>empty()` supplies an explicit type witness, giving the result type `List<String>`.
- `echo("Java")` infers from the `String` method argument; no type witness is needed.

`<String>` on a static method call is how **the caller chooses the type argument**, not a default defined by `<T>`.

## 10. You cannot "drop trailing type arguments" of a generic class

In some languages with default generic parameters, you can write a multi-parameter type and omit trailing arguments. **Java does not support that convention.**

Given:

```java
record Pair<K, V>(K key, V value) {
}
```

Usages:

```java
Pair<String, Integer> valid =
        new Pair<>("age", 20);
```

And:

```java
// INTENTIONALLY INVALID:
Pair<String> missingOne;
Pair<String, Integer, Boolean> tooMany;
```

In the type name `Pair<K,V>`, Java requires **the exact number of type arguments** matching the declaration whenever you use a parameterized type. It does not fill in `V = Object`, `V = String`, or anything else to complete `Pair<String>`.

If you omit all type arguments in a variable type:

```java
Pair raw;
```

that is a **raw type**, not "`Pair<Object,Object>` by default". Raw types exist for legacy compatibility and carry type-safety limitations.

Note: Java allows **inferring all type arguments** at a creation expression using the diamond `new Pair<>(...)`. That differs from writing a partial argument list in the type name `Pair<String>`.

## 11. `<>` is not optional generic arguments everywhere

The diamond `<>` is syntax used in certain **class instance creation expressions** to infer type arguments. It is not a general symbol meaning "omit type arguments anywhere".

Compare:

```java
java.util.List<String> values = new java.util.ArrayList<>();
```

This line is valid because `<>` appears on **the object-creation right-hand side**.

However:

```java
// INTENTIONALLY INVALID:
java.util.List<> values;
```

`List<>` is not valid syntax for declaring a variable's generic type. When you need a type with an unknown argument, use `List<?>`:

```java
java.util.List<?> values = java.util.List.of("A");
```

`List<?>` means "a list with an unspecified type argument"—not "default to `Object`" and not the raw type `List`.

### A wildcard is not a default either

`List<?>` merely describes the limits of what the compiler knows about an arbitrary list. You can read elements as `Object`, but you cannot arbitrarily add a `String` or `Integer` to a list with an unknown wildcard.

`List<Object>` is a parameterized type with the **concrete** argument `Object`; it cannot directly substitute for `List<String>` because Java Generics is invariant.

## 12. Constructor overloading does not set a default for `T`

Java supports overloaded constructors or default **value** parameters via overloading, yet that is **not equivalent to a default type argument**.

For example:

```java
class Result<T> {
    private final T value;

    Result() {
        this.value = null;
    }

    Result(T value) {
        this.value = value;
    }

    T get() {
        return value;
    }
}
```

This is a valid class. It has two constructors:

- `Result()` creates an object with `value = null`.
- `Result(T value)` creates an object with a supplied value.

**Neither constructor says `T` defaults to `String`.** If the caller writes:

```java
Result<String> a = new Result<>();
Result<Integer> b = new Result<>();
```

both use the no-argument constructor while having different type arguments.

A method taking a **default value** like `Result(T initialValue)` also does not declare a "default type `T`". A type parameter and the value stored inside an object live at two different conceptual levels.

## 13. Alternative design 1: static factory methods returning concrete types

If the domain need is "when we want a box of strings, give callers a short, clear call", create a factory with a **concrete return type** instead of looking for `class Box<T = String>` syntax.

Create the file **`NamedFactoryDemo.java`**:

```java
import java.util.ArrayList;
import java.util.List;

public class NamedFactoryDemo {

    static final class Box<T> {
        private final List<T> elements = new ArrayList<>();

        void add(T item) {
            elements.add(item);
        }

        List<T> items() {
            return List.copyOf(elements);
        }
    }

    static Box<String> strings() {
        return new Box<>();
    }

    static Box<Integer> integers() {
        return new Box<>();
    }

    static <T> Box<T> empty() {
        return new Box<>();
    }

    public static void main(String[] args) {
        var text = strings();
        text.add("A");

        var numbers = integers();
        numbers.add(10);

        Box<Long> longs = empty();
        longs.add(20L);

        System.out.println(text.items());
        System.out.println(numbers.items());
        System.out.println(longs.items());
    }
}
```

Run:

```bash
javac NamedFactoryDemo.java
java NamedFactoryDemo
```

Stdout:

```text
[A]
[10]
[20]
```

`strings()` has explicit return type `Box<String>`, and `integers()` returns `Box<Integer>`. `empty()` is a generic factory letting callers pick the type argument via target type or type witness.

**Advantage:** Clear API; callers do not have to repeat type arguments in common cases.

**Limitation:** Factory names are explicitly designed for specific domain choices. They **do not** give the `Box<T>` declaration a language-managed default type argument.

If `null` data were allowed, `List.copyOf(elements)` would reject `null` when building the result. This program only adds non-null elements.

## 14. Alternative design 2: factory with a convention-based default type

Sometimes you want both a "default call path" and a "flexible call path". You can design two methods with **clear names**, or overload using genuinely distinct input parameters.

Create the file **`FactoryChoiceDemo.java`**:

```java
import java.util.ArrayList;
import java.util.List;

public class FactoryChoiceDemo {

    static final class Bucket<T> {
        private final List<T> items = new ArrayList<>();

        void add(T value) {
            items.add(value);
        }

        List<T> snapshot() {
            return List.copyOf(items);
        }
    }

    static Bucket<String> defaultTextBucket() {
        return new Bucket<>();
    }

    static <T> Bucket<T> bucketOf(T first) {
        Bucket<T> result = new Bucket<>();
        result.add(first);
        return result;
    }

    static <T> Bucket<T> emptyBucket() {
        return new Bucket<>();
    }

    public static void main(String[] args) {
        var defaultText = defaultTextBucket();
        defaultText.add("hello");

        var numbers = bucketOf(7);
        numbers.add(8);

        var explicit =
                FactoryChoiceDemo.<Double>emptyBucket();
        explicit.add(2.5);

        System.out.println(defaultText.snapshot());
        System.out.println(numbers.snapshot());
        System.out.println(explicit.snapshot());
    }
}
```

Compile/run:

```bash
javac FactoryChoiceDemo.java
java FactoryChoiceDemo
```

Stdout:

```text
[hello]
[7, 8]
[2.5]
```

Note that `defaultTextBucket()` merely expresses a **default chosen by the API author**. It does not make `Bucket<T>` support `T = String` in its declaration.

Do not define two overloads that differ only in generic return type:

```java
// INTENTIONALLY INVALID — return types cannot be used to overload:
static Bucket<String> create() { return new Bucket<>(); }
static <T> Bucket<T> create() { return new Bucket<>(); }
```

Two methods with the same name and empty parameter lists cannot be distinguished solely by return type or type parameter. Use distinct names, or meaningfully distinct parameter signatures.

## 15. Alternative design 3: subtype fixing the type argument

Another approach is defining a **non-generic subclass** that fixes the parent class's type:

```java
class Box<T> {
    private final T value;

    Box(T value) {
        this.value = value;
    }

    T get() {
        return value;
    }
}

class StringBox extends Box<String> {
    StringBox(String value) {
        super(value);
    }
}
```

These are valid class declarations; they contain no `main`.

`StringBox` declares no `T` of its own; it **extends** `Box<String>`. Callers can write `new StringBox("hello")` instead of `new Box<String>("hello")`, and the compiler knows `get()` returns `String` when viewed through `StringBox`.

This differs from a default generic argument:

- `Box<Integer>` remains a valid usage of `Box<T>`.
- `StringBox` is **a separate class** from `Box<T>` with its own name and inheritance relationship.
- Java does not let you write `Box` and automatically interpret it as `StringBox` or `Box<String>`.

### Runnable example

File **`SpecializedSubtypeDemo.java`**:

```java
public class SpecializedSubtypeDemo {

    static class Box<T> {
        private final T value;

        Box(T value) {
            this.value = value;
        }

        T get() {
            return value;
        }
    }

    static final class StringBox extends Box<String> {
        StringBox(String value) {
            super(value);
        }
    }

    public static void main(String[] args) {
        StringBox text = new StringBox("ready");
        Box<Integer> number = new Box<>(12);

        String message = text.get();

        System.out.println(message);
        System.out.println(number.get());
    }
}
```

Commands:

```bash
javac SpecializedSubtypeDemo.java
java SpecializedSubtypeDemo
```

Stdout:

```text
ready
12
```

Subclass specialization is useful when `StringBox` is truly a domain concept or needs extra APIs/validation. When you merely want a concise way to create a generic object, a factory method from the previous section usually introduces fewer classes.

## 16. Alternative design 4: using target types at API boundaries

Often you do not need a dedicated factory to "default" a type. The caller simply specifies **the type the program expects** on the left-hand side or in the return type.

For example:

```java
static <T> java.util.List<T> emptyList() {
    return new java.util.ArrayList<>();
}

static java.util.List<String> names() {
    return emptyList();
}
```

These two methods must be placed inside a class.

`names()` declares a `List<String>` result, so the compiler has a clear target type for the generic `emptyList()` call. Callers of `names()` do not need a type witness.

Similarly:

```java
static void consumeStrings(java.util.List<String> values) {
    System.out.println(values.size());
}

static void demo() {
    consumeStrings(new java.util.ArrayList<>());
}
```

`consumeStrings`'s parameter type supplies context for the diamond in `new ArrayList<>()`.

This is **target typing**, not Java creating a default generic parameter. It keeps type intent at **the usage boundary** and keeps client code concise whenever the compiler has enough context.

## 17. Raw types are not a substitute for default type arguments

An anti-pattern is dropping `<...>` altogether:

```java
java.util.List values = new java.util.ArrayList();
values.add("text");
values.add(100);
```

This may compile with raw/unchecked warnings. However, `values` is a **raw `List`**, not a `List<String>` with a default argument.

Risks:

- The compiler does not fully check element types during `add`.
- Assigning raw data to a `List<String>` variable via unchecked conversion can cause **heap pollution**.
- A `ClassCastException` can appear later when an element is read as `String`.

`List<Object>` is also not synonymous with raw `List`:

```java
java.util.List<Object> values =
        new java.util.ArrayList<>();
```

This line has an explicit generic type argument `Object`. The compiler consistently enforces that elements are treated as `Object`, even though the list can hold both `String` and `Integer`.

**When the type argument is unknown and you only need to read**, `List<?>` is usually better than raw `List`, because the wildcard preserves compile-time type constraints.

## 18. Default type arguments would not solve type erasure

Even if Java had default type arguments (in reality **it does not**), picking a type argument at compile time still would not turn Generics into reified types. In real Java:

```java
var a = new Box<>("A");
var b = new Box<>(10);
```

if both objects are direct instances of the same generic class `Box`, `getClass()` normally returns the same runtime class, because type arguments are erased.

Create the file **`GenericRuntimeIdentityDemo.java`**:

```java
public class GenericRuntimeIdentityDemo {

    static class Box<T> {
        private final T value;

        Box(T value) {
            this.value = value;
        }

        T get() {
            return value;
        }
    }

    public static void main(String[] args) {
        Box<String> text = new Box<>("A");
        Box<Integer> number = new Box<>(10);

        System.out.println(
                text.getClass() == number.getClass());
        System.out.println(
                Box.class.getTypeParameters()[0].getName());
    }
}
```

Run:

```bash
javac GenericRuntimeIdentityDemo.java
java GenericRuntimeIdentityDemo
```

Stdout:

```text
true
T
```

`getClass()` only shows the object's runtime class; `getTypeParameters()` shows that `Box` declares a type variable named `T`. It does not reveal that each instance was created with any default type argument—because Java has no such default, and objects generally do not carry the type argument used in source code.

Using a subclass `StringBox extends Box<String>` lets reflection read the declared generic superclass on **the subclass**, yet that does not turn a type argument into an automatic default across all `Box` instances.

## 19. Distinguishing easily confused "default" concepts

In Java, the word "default" can refer to very different features.

| Concept | Supported by Java? | Is it a default type argument? |
|---|---|---|
| Default value of a reference field is `null` | Yes | No |
| Default value of a primitive field like `int` is `0` | Yes | No |
| No-argument constructor | Can exist or be declared explicitly | No |
| Overloading methods to provide default values | Can be designed manually | No |
| `default` method in an interface | Yes (Java 8+) | No |
| Diamond `new Box<>()` | Yes | No; it is type inference |
| `var x = expression` | Yes (local inference) | No |
| Upper bound `<T extends Number>` | Yes | No |
| Raw type `Box` | Yes for compatibility | No |
| Wildcard `Box<?>` | Yes | No |
| Declaration `class Box<T = String>` | **No** | This is the unsupported syntax |

### Interface `default` methods are unrelated to type arguments

For example:

```java
interface Printer<T> {
    void print(T value);

    default void printTwice(T value) {
        print(value);
        print(value);
    }
}
```

This is a valid interface. The `default` keyword here declares **a default implementation of an instance method in an interface**, not a `T = String` default.

An interface with default methods must still be used as `Printer<String>`, `Printer<Integer>`, `Printer<?>`, or in raw-type contexts under normal rules.

## 20. Type inference does not always pick `Object`

An overly broad conclusion is:

> "Because there are no default type arguments, omitting `<T>` makes the compiler automatically pick `Object`."

False, because the compiler can infer from multiple sources:

1. **Target type:** `Box<String> x = new Box<>()` suggests `String`.
2. **Constructor arguments:** `var x = new Box<>(123)` suggests `Integer`.
3. **Method arguments:** `identity("A")` suggests `String`.
4. **Return context:** `List<String> names() { return Collections.emptyList(); }` supplies a target type in the return expression.
5. **Bounds:** `<T extends Number>` narrows the candidate types.
6. **Explicit type witness:** `Factory.<String>empty()` fixes `String` at the call site.

Java type inference is a constraint-solving system, not an "if absent, assign `Object`" rule. Only in specific cases **lacking other useful constraints**, such as `var x = new Box<>()` with an unbounded type parameter and no-argument constructor, is `Object` a typical result.

Conversely, if you write **raw type** `Box x`, the compiler does not infer `T = Object` the same way as `Box<Object> x`; it is a raw type with its own rules.

## 21. Common mistakes and fixes

**Mistake 1 — Writing `class Box<T = String>`.** Unsupported in Java. Fix to `Box<T>`, and add `static Box<String> strings()` if a specific domain choice is desired.

**Mistake 2 — Using `<T extends String>` to simulate a `String` default.** `extends` is a **bound**, not a default. Moreover `String` is final, so picking this bound only restricts the subtype set; it does not create syntax to omit the type argument and default to `String`.

**Mistake 3 — Thinking `new Box<>()` always chooses `String` if the program mostly works with strings.** The compiler does not infer from domain habits. There must be a target type, constructor arguments, type witness, or factory returning a concrete type.

**Mistake 4 — Writing `Box<> x;`.** Diamond cannot be used as a variable's type name. Write `Box<String> x;`, `Box<?> x;`, or `var x = new Box<>()` if you understand the inferred type.

**Mistake 5 — Using raw `Box` as a "default".** Raw types discard generic information and can lead to unchecked operations; they are not equivalent to `Box<Object>` or `Box<String>`.

**Mistake 6 — Using `Box<?>` like `Box<Object>`.** Unknown wildcards allow reading safely according to bounds, yet restrict arbitrarily passing a new `T` to methods taking `T`.

**Mistake 7 — Assuming `var` infers a type from subsequent `set` calls.** The variable's type is fixed at the initializer; later statements do not change it.

**Mistake 8 — Dropping one argument of `Pair<K,V>` expecting a default.** `Pair<String>` is invalid if `Pair` declares two type parameters. Supply all arguments or use diamond at the class instance creation expression.

**Mistake 9 — Thinking an explicit type witness is a cast.** `<String>` in `Factory.<String>empty()` participates in type checking; it does not coerce an arbitrary object to `String`.

**Mistake 10 — Using different return types to overload two parameterless factories with the same name.** Java does not use return types to distinguish overloads. Pick different names or meaningfully different parameter contracts.

**Mistake 11 — Adding a no-argument constructor and thinking `T` now has a default.** A constructor only chooses how **values** are initialized, not a default type argument.

**Mistake 12 — Confusing interface `default` methods with default generic parameters.** Same word "default", completely different syntactic roles.

**Mistake 13 — Using unchecked casts to pretend there is a generic default.** Unchecked casts can mask compile-time errors and turn them into `ClassCastException` later; placing types at API boundaries is better.

**Mistake 14 — Assuming runtime `getClass()` will report a "defaulted" `Box<String>`.** Type erasure causes multiple generic instantiations to share the same runtime class; that information generally cannot be recovered from an instance.

## 22. Choosing API designs by requirement

| Requirement | Sensible syntax | Reason |
|---|---|---|
| Each caller knows the type argument | `Box<String> box = new Box<>();` | Diamond uses target type |
| Type can be inferred from a value | `var box = new Box<>(42);` | Constructor argument suggests `Integer` |
| Variable needs an explicit type argument with `var` | `var box = new Box<String>();` | Initializer explicitly specifies `String` |
| Want a "default to `String`" creator | `static Box<String> strings()` | API convention, independent of unsupported generic syntax |
| Want a generic factory returning caller-chosen type | `static <T> Box<T> empty()` | Target typing or type witness |
| Need a class with a fixed `String` contract | `class StringBox extends Box<String>` | Specialized subtype |
| Only reading from a `Box` with unknown `T` | `Box<?>` | Safely preserves generic bounds |
| Need to constrain `T` to numbers | `Box<T extends Number>` | Bound, not default |
| Want multiple type parameters | `Pair<K,V>` with all args | No partial type-argument defaults |
| Want to pick a default initial value | Constructor/factory taking a value | Default value differs from type argument |
| Need to support legacy code | Use raw types only at unavoidable boundaries | Isolates unchecked warnings |

Do not try to simulate default generic parameters using layers of unchecked casts, raw types, or return-type-only overloads. Clear factory names make APIs easier to read and test.

## 23. Practice exercises with answers

### Exercise 1 — Distinguishing syntax forms

Among the lines below, which one is invalid?

```java
class Box<T> { }                // A
class Other<T = String> { }     // B
class Numeric<T extends Number> { } // C
```

**Answer:** B is invalid because Java has no default type arguments. A and C are valid; C uses an upper bound.

### Exercise 2 — Inference from the left-hand side

```java
Box<String> a = new Box<>();
```

How is `T` determined, assuming `Box` has a no-argument constructor?

**Answer:** The compiler infers `String` from the target type `Box<String>`. No default type argument is needed.

### Exercise 3 — `var` and an empty constructor

```java
var b = new Box<>();
```

If `Box<T>` is unbounded and the constructor takes no data for inference, what is the static type of `b`?

**Answer:** `Box<Object>` in the described case. That is a result of type inference, not a raw `Box`.

### Exercise 4 — Constructor with an argument

```java
var c = new Box<>(10);
```

If `Box` has constructor `Box(T value)`, what will `T` normally be?

**Answer:** `Integer` after boxing `10` and inferring from the constructor argument.

### Exercise 5 — Empty generic method

```java
static <T> java.util.List<T> empty() {
    return new java.util.ArrayList<>();
}
```

How can you get a `List<String>` without changing the method declaration?

**Answer:** Use `List<String> list = empty();` or `var list = Factory.<String>empty();` if the static method belongs to `Factory`.

### Exercise 6 — Is a raw type a default?

```java
Box raw = new Box();
```

Is this equivalent to `Box<String>`?

**Answer:** No. This is a raw type; compile-time generic checking is degraded.

### Exercise 7 — Multiple type parameters

```java
record Pair<K, V>(K key, V value) { }
```

Is `Pair<String>` valid?

**Answer:** No. Once using the parameterized form, exactly two arguments are required. You can use `Pair<String,Integer>` or diamond at a creation expression if the compiler can infer both.

### Exercise 8 — Bounds

Does `<T extends Number>` mean "`T` defaults to `Number`"?

**Answer:** No. It specifies an upper bound; type inference may rely on the bound, yet there is no default type argument.

### Exercise 9 — Factory for a common type

If a system frequently creates `Box<String>`, how can callers avoid repeating `String`?

**Answer:** Provide `static Box<String> strings()` or a subtype `StringBox` when semantically warranted; keep `Box<T>` generic as usual.

### Exercise 10 — Wildcards

Is `Box<?>` a way to write "default `T` to `Object`"?

**Answer:** No. `?` represents an unknown type argument and restricts write operations that depend on `T`.

### Exercise 11 — Return-type-only overloading

Can two parameterless methods `Box<String> create()` and `<T> Box<T> create()` with the same name coexist side by side?

**Answer:** No. Return type and type parameter alone do not distinguish identical method signatures.

### Exercise 12 — Runtime

What class do `new Box<String>("a").getClass()` and `new Box<Integer>(1).getClass()` both return?

**Answer:** The same runtime class `Box`, due to type erasure. Source-level type arguments do not generate separate runtime classes per instantiation.

## 24. Checklist when facing a "default `T` to `String`" requirement

1. **Clarify whether the requirement is a type or a value.** "Default `T` to `String`" differs from "initial value is an empty string".
2. **Check whether the caller has a target type.** If so, use diamond/generic factory inference.
3. **Check whether constructors or methods take arguments carrying type info.** Types can be inferred from inputs.
4. **If there is neither target type nor input**, inference may pick `Object` or a bounded type; specify the type argument explicitly if a concrete type is required.
5. **If many callers consistently need `String`**, create a factory returning `Box<String>` to centralize intent.
6. **If a distinct subtype makes domain sense**, create `StringBox extends Box<String>` instead of trying to treat raw `Box` as `String`.
7. **If an API has multiple type parameters**, do not expect Java to allow dropping trailing parameters like default syntax in some other languages.
8. **Avoid raw types and unchecked casts** to fake defaults.
9. **Test the compiler with an invalid case:** a `Box<String>` must reject non-`String` values in methods expecting `T`.
10. **Verify the actual Java version:** diamond and local-variable inference arrived in different releases; these examples target Java 17+.

### Quick self-check question

If you see a line:

```java
var items = new java.util.ArrayList<>();
```

ask yourself: "Does the compiler have any evidence to infer `String` here?" In this snippet there is none, so the typical outcome is `ArrayList<Object>`. If the intent is a list of strings, write the type explicitly in a valid spot instead of expecting a nonexistent default generic parameter.

## 25. Summary and references

**Java Generics does not support default values for type parameters in declarations.** You cannot write `class Box<T = String>` or `<T = String>` on a generic method. `extends` only sets bounds; raw types omit type arguments; wildcards express unknown types; and diamond, `var`, and generic method inference infer types at **the usage site**.

When you want callers to avoid repeating a type argument, appropriate design choices are usually:

- **Diamond + target typing:** `Box<String> x = new Box<>()`.
- **Explicit type argument in the initializer:** `var x = new Box<String>()`.
- **Inference from data:** `var x = new Box<>("text")`.
- **Generic static factory:** `List<String> x = empty()` or `Factory.<String>empty()`.
- **Named factory for a common type:** `Box<String> strings()`.
- **Specialized subtype when warranted:** `StringBox extends Box<String>`.

These solutions preserve compile-time type checking without relying on raw types or unsafe casts. None of them turns default generic arguments into a feature Java does not support.
