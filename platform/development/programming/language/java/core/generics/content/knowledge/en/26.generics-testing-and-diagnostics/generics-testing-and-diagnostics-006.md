# Comparing Generic Signatures, Erased Signatures, and Bridge Methods in Java Class Files

## 1. Objective: Understanding the Same Method Across Three Representation Layers

When reading Java Generics, you regularly see rich type information in **source code**:

```java
class Holder<T> {
    T get() { return null; }
    void set(T value) {}
}
```

However, after `javac`, the JVM operates on **method descriptors** whose type variables have undergone *erasure*. Inside the class file there can still be a `Signature` attribute storing the generic declaration for tools like Reflection. When overriding occurs after substituting a type argument, or when a covariant return type is used, the compiler may also generate a **bridge method**.

This lesson guides a systematic comparison across:

1. **Generic signatures in source**: type variables `<T>`, bounds, `List<String>`, overriding, and inference.
2. **Erased signatures in JVM descriptors**: the types the JVM uses to identify fields/methods and perform linkage.
3. **Generic `Signature` attribute**: metadata describing type parameters and generic arguments readable by Java Reflection.
4. **Bridge/synthetic methods**: methods generated by the compiler to preserve proper overriding/dispatch after erasure or with covariant return types.
5. **Empirical outputs**: `javac --release 17`, `javap -p -s -v -c`, and Reflection `Method.isBridge()`, `Method.isSynthetic()`, `getGenericReturnType()`.

After this lesson, you can inspect a class file and explain: why source only has `String get()` yet bytecode shows both `Object get()` and `String get()`; why `get()` on a superclass returns `Object` after erasure while `StringHolder` still overrides properly; why Reflection sees methods not written in source; and when an erasure conflict is a compile-time error instead of being fixed by a compiler-generated bridge.

## 2. Three Things Commonly Confused: Java Method Signature, JVM Descriptor, and Generic Signature

The word "signature" is used in multiple senses; separate the contexts carefully.

| Concept | Purpose | Example |
| --- | --- | --- |
| **Java source method declaration** | Expresses API and type-checking rules | `public T get()` |
| **Java method signature per JLS** | Identifies methods/overloading at the language level; focuses on name and parameter types/type parameters | `get()` |
| **JVM method descriptor** | Encodes parameter types **and return type** for the JVM | `()Ljava/lang/Object;` |
| **Class-file `Signature` attribute** | Records generic metadata when needed | `()TT;` |
| **Bridge method** | Compiler-generated method preserving overriding/dispatch relationships | `Object get()` calling `String get()` |
| **Method flag `ACC_BRIDGE`** | Marks a bridge method | `0x0040` |
| **Method flag `ACC_SYNTHETIC`** | Marks a compiler-generated member not written directly in source | `0x1000` |

**Key point:** in Java source, changing only the return type generally **does not create a valid overload**. Yet in a class file, a class can contain a bridge `Object get()` and an implementation `String get()` with the same name, same parameter list, and **different descriptor return types**. This is code generated by the compiler under JVM rules, not an invitation to manually declare two Java methods differing only in return type.

### 2.1. Descriptors Use JVM Syntax, Not Source Generic Names

Example:

```java
T get();
void set(T value);
```

if `T` has no explicit bound, it erases to `Object`. Corresponding descriptors:

```text
()Ljava/lang/Object;
(Ljava/lang/Object;)V
```

Quick syntax guide:

- `(` ... `)` is the list of parameter descriptors.
- `V` is `void` return.
- `I` is `int`; `J` is `long`; `Z` is `boolean`.
- `Lpkg/ClassName;` is a reference type; `/` is used in internal names.
- `[` precedes the element descriptor of an array.
- Descriptors **never contain** `<String>`, `? extends`, or type variable `T`.

Another example:

```java
String get();
void set(String value);
int count();
String[] names();
```

descriptors:

```text
()Ljava/lang/String;
(Ljava/lang/String;)V
()I
()[Ljava/lang/String;
```

The line `()[Ljava/lang/String;` means a zero-argument method returning a `String[]` array.

### 2.2. The `Signature` Attribute Uses Its Own Grammar

Example:

```text
()TT;
```

In the generic signature grammar, `TT;` represents a type variable named `T`. Note that the first `T` is the type-variable marker and the second `T` is the variable name.

For:

```java
List<String> tags();
```

the class file can contain:

```text
descriptor: ()Ljava/util/List;
Signature: ()Ljava/util/List<Ljava/lang/String;>;
```

The JVM needs `List` in the descriptor; `Signature` retains the `String` type argument for generic-aware tools.

Do not interpret `Signature` as the JVM descriptor used for dispatch. They serve different purposes.

### 2.3. JVM Erasure and Reflection Do Not Contradict Each Other

A commonly heard statement is "Java Generics are erased at runtime." More accurately:

- **Type arguments of object instances are not reified into separate runtime classes** such as `ArrayList<String>` and `ArrayList<Integer>`.
- **Method descriptors** use erased types.
- The compiler can store **generic declaration metadata** in the `Signature` attribute, allowing Reflection to return `TypeVariable`, `ParameterizedType`, etc.

You cannot call `list.getClass()` and expect to know the exact generic argument of the variable that created the list. However, you can read the generic declaration on classes/fields/methods that carry the corresponding metadata.

## 3. How Does Type Erasure Transform Types?

Suppose:

```java
class Holder<T> {
    private T value;

    T get() {
        return value;
    }

    void set(T value) {
        this.value = value;
    }
}
```

`T` has no explicitly written bound, so its default upper bound is `Object`. The erasure of `T` is `Object`.

| Source Declaration | Type After Erasure |
| --- | --- |
| Field `T value` | Field `Object value` |
| Return `T get()` | Return `Object get()` |
| Parameter `void set(T)` | Parameter `void set(Object)` |
| `List<String>` | `List` |
| `Map<String,Integer>` | `Map` |
| `T[]` when `T` is unbounded | `Object[]` |
| `T extends Number` | `Number` |

### 3.1. The First Bound Governs Erasure

Given a generic method:

```java
public <N extends Number> N echo(N number) {
    return number;
}
```

The erasure of `N` is `Number`, **not `Object`**. Descriptor:

```text
(Ljava/lang/Number;)Ljava/lang/Number;
```

Corresponding generic `Signature`:

```text
<N:Ljava/lang/Number;>(TN;)TN;
```

It indicates a method type variable `N` with bound `Number`, parameter `N`, and return `N`. Looking only at the descriptor loses the relationship "input and output share the same `N`", though you still see both have raw type `Number`.

With multiple bounds, erasure depends on the first bound according to Java rules. Thus you must inspect the actual declaration rather than assuming every type variable erases to `Object`.

### 3.2. Parameterized Types Erase to Their Raw Type

```java
public List<String> tags() {
    return List.of("java", "generics");
}
```

Descriptor:

```text
()Ljava/util/List;
```

`Signature`:

```text
()Ljava/util/List<Ljava/lang/String;>;
```

Any tool inspecting only the descriptor will not know the `String` element type. Only tools reading `Signature` see the generic argument from the declaration.

### 3.3. Type Erasure Does Not Turn `List<Integer>` into `List<String>`

At compile time:

```java
List<String> names = new ArrayList<>();

// Does not compile:
// List<Integer> numbers = names;
```

Invariance/type checking remains in force at the source level. Erasure occurs as part of compilation/JVM representation; it does not make ill-typed assignments valid.

Conversely, raw types and unchecked conversions can introduce bad data, leading to delayed errors like `ClassCastException`. Bridge methods do not cure heap pollution caused by raw types.

## 4. Why Does the Compiler Need a Bridge When Overriding a Generic Superclass?

An example:

```java
class Holder<T> {
    public T get() {
        return null;
    }
}

class StringHolder extends Holder<String> {
    @Override
    public String get() {
        return "Java";
    }
}
```

In Java source, `StringHolder.get()` **overrides** `Holder<String>.get()` because `T` is substituted with `String` in the inheritance relationship.

At the JVM level, however:

- Erased `Holder.get()` has descriptor `()Ljava/lang/Object;`.
- `StringHolder.get()` as you wrote it has descriptor `()Ljava/lang/String;`.

If the JVM had only `String get()` while a call through a `Holder<String>` variable targeted the `Object get()` descriptor, dispatch would lack a subclass implementation matching the erased descriptor.

Therefore, the compiler can generate a bridge:

```java
// Pseudocode explaining bytecode, NOT handwritten source:
public Object get() {
    return this.get(); // Calls the subclass's String get().
}
```

In the JVM, the two `get` methods are distinguished by their return type descriptors. The bridge method has return type `Object` matching the erased superclass API and delegates to the `String` implementation.

### 4.1. For Parameter `set(T)`, the Bridge Needs a Cast

Source:

```java
class Holder<T> {
    public void set(T value) {
    }
}

class StringHolder extends Holder<String> {
    @Override
    public void set(String value) {
    }
}
```

The erased superclass method accepts `Object`, whereas `StringHolder`'s source method accepts `String`. The compiler can additionally generate:

```java
// Pseudocode bridge, not declared manually:
public void set(Object value) {
    set((String) value);
}
```

This method accepts `Object` at the erased JVM boundary, performs `checkcast String`, and invokes the typed `set(String)` implementation.

**Consequence:** crossing a raw/reflection boundary and passing an `Integer` into the `set(Object)` bridge can throw `ClassCastException`. The bridge preserves dispatch and type safety within the bounds the JVM can check, without turning an `Integer` into a `String`.

### 4.2. Bridges Are a Class-File Implementation Detail

Source authors **do not** declare bridges manually and should not invoke them through normal Java APIs as independent overloads. The compiler decides where methods are needed to preserve override semantics.

Not **every** generic method gets a bridge. Bridges typically appear only when descriptor compatibility is needed from inheritance/interface implementation or covariant returns.

## 5. Complete Example: Superclass, Subclass, Interface, and Bridges

Create the file **`GenericBytecodeDemo.java`**:

```java
import java.lang.reflect.InvocationTargetException;
import java.lang.reflect.Method;
import java.util.Arrays;
import java.util.Comparator;
import java.util.List;

public class GenericBytecodeDemo {
    static class Holder<T> {
        private T value;

        Holder(T value) {
            this.value = value;
        }

        public T get() {
            return value;
        }

        public void set(T value) {
            this.value = value;
        }

        public <N extends Number> N echo(N number) {
            return number;
        }

        public List<String> tags() {
            return List.of("java", "generics");
        }
    }

    static final class StringHolder extends Holder<String> {
        StringHolder(String value) {
            super(value);
        }

        @Override
        public String get() {
            return super.get().toUpperCase();
        }

        @Override
        public void set(String value) {
            super.set(value.trim());
        }
    }

    interface Mapper<T> {
        T apply(T value);
    }

    static final class Uppercase implements Mapper<String> {
        @Override
        public String apply(String value) {
            return value.toUpperCase();
        }
    }

    public static void main(String[] args) throws Exception {
        Holder<String> holder = new StringHolder(" java ");
        holder.set(" bridge ");
        System.out.println("dispatch=" + holder.get());
        System.out.println("generic-method=" + holder.echo(7));

        System.out.println("generic-field="
                + Holder.class.getDeclaredField("value")
                      .getGenericType().getTypeName());

        System.out.println("generic-super="
                + StringHolder.class.getGenericSuperclass()
                      .getTypeName());

        Method[] methods = StringHolder.class.getDeclaredMethods();
        Arrays.sort(methods, Comparator.comparing(Method::toString));

        for (Method method : methods) {
            System.out.println("method=" + method.getName()
                    + ",parameter="
                    + Arrays.toString(method.getParameterTypes())
                    + ",returns="
                    + method.getReturnType().getSimpleName()
                    + ",bridge=" + method.isBridge()
                    + ",synthetic=" + method.isSynthetic());
        }

        Method getTyped =
                StringHolder.class.getDeclaredMethod("get");
        Method setBridge =
                StringHolder.class.getDeclaredMethod(
                        "set", Object.class);

        System.out.println("get-by-object-method="
                + (getTyped.getReturnType() == String.class));
        System.out.println("set-object-bridge="
                + setBridge.isBridge());

        try {
            setBridge.invoke(holder, 42);
        } catch (InvocationTargetException ex) {
            System.out.println("invalid-bridge-arg="
                    + ex.getCause().getClass().getSimpleName());
        }

        System.out.println("mapper="
                + new Uppercase().apply("hi"));
        System.out.println("mapper-bridge="
                + Uppercase.class
                  .getDeclaredMethod("apply", Object.class)
                  .isBridge());
    }
}
```

Compile and run with Java 17:

```bash
javac --release 17 -Xlint:all GenericBytecodeDemo.java
java GenericBytecodeDemo
```

The program compiled cleanly with `-Xlint:all`. Stdout on the test JDK:

```text
dispatch=BRIDGE
generic-method=7
generic-field=T
generic-super=GenericBytecodeDemo$Holder<java.lang.String>
method=get,parameter=[],returns=Object,bridge=true,synthetic=true
method=get,parameter=[],returns=String,bridge=false,synthetic=false
method=set,parameter=[class java.lang.Object],returns=void,bridge=true,synthetic=true
method=set,parameter=[class java.lang.String],returns=void,bridge=false,synthetic=false
get-by-object-method=true
set-object-bridge=true
invalid-bridge-arg=ClassCastException
mapper=HI
mapper-bridge=true
```

The result `get-by-object-method=true` reflects Reflection's preference for the more specific return type when looking up `getDeclaredMethod("get")` in this example; when analyzing a class file with multiple methods sharing name/parameters yet differing in return type, **iterate `getDeclaredMethods()` and check return types/bridge flags** rather than assuming every `get` is one method.

### 5.1. Why `dispatch=BRIDGE`?

The variable `holder` has static type `Holder<String>`, while the actual object is `StringHolder`. The `set`/`get` calls have a typed `String` contract; after erasure, JVM call sites can use `Holder`'s `Object` descriptors. Bridge methods dispatch to `StringHolder`'s implementations, and `StringHolder` trims `" bridge "` to `"bridge"` and uppercases it to `"BRIDGE"`.

This demonstrates **overriding working properly** across erased JVM descriptors. It is not that the runtime knows `Holder<String>` as a new specialized class.

### 5.2. Why `generic-field=T`?

`Field.getGenericType()` reads the generic metadata of the declaration `private T value`. It returns a `TypeVariable` named `T`. Using `Field.getType()` instead of `getGenericType()` returns the erased field type `Object.class`.

### 5.3. Why `generic-super=Holder<String>`?

`StringHolder` is declared `extends Holder<String>`, and the generic superclass metadata remains in the class file. `getGenericSuperclass()` returns a `ParameterizedType` describing that exact declaration.

Reflection does not automatically turn the generic field `T` in `Holder` into `String` when you call `Holder.class.getDeclaredField("value").getGenericType()` directly. To infer `T=String` in the context of `StringHolder`, a resolver must combine the `StringHolder extends Holder<String>` relationship.

### 5.4. Why Are There Four `method=` Lines?

In `StringHolder`:

- Typed `String get()` is the method you wrote; `bridge=false`, `synthetic=false`.
- Bridge `Object get()` is the compiler-generated method; `bridge=true`, `synthetic=true`.
- Typed `void set(String)` is the method you wrote.
- Bridge `void set(Object)` is the compiler-generated method.

Output is sorted by `Method.toString()` in the program for easy test comparison; Reflection does not promise a stable order from `getDeclaredMethods()` without sorting.

### 5.5. Why `invalid-bridge-arg=ClassCastException`?

Reflection invokes `StringHolder`'s `set(Object)` with `Integer` `42`. The bridge exists and accepts an `Object` per the erased descriptor, yet inside it must cast `Object` to `String` before calling `set(String)`. The cast fails, Reflection wraps the exception in `InvocationTargetException`, and the program extracts the cause with `getCause()` to print `ClassCastException`.

This demonstrates the bridge's runtime mechanism, **not a recommendation to call bridges via Reflection in application code**.

### 5.6. Why `mapper-bridge=true`?

`Mapper<T>` declares `T apply(T value)`, which erases to descriptor `(Ljava/lang/Object;)Ljava/lang/Object;`.

`Uppercase implements Mapper<String>` implements `String apply(String value)`, with descriptor `(Ljava/lang/String;)Ljava/lang/String;`.

The compiler generates `Object apply(Object)` as a bridge so calls through the `Mapper` interface dispatch properly to the `String` implementation. The mechanism is identical to a generic superclass, appearing here in a **generic interface implementation**.

## 6. Inspecting Class Files with `javap`

After compiling `GenericBytecodeDemo.java`, run from the directory containing the `.class` files:

```bash
javap -p -s 'GenericBytecodeDemo$Holder'
javap -p -s 'GenericBytecodeDemo$StringHolder'
javap -p -s 'GenericBytecodeDemo$Uppercase'
```

In some Windows shells, use:

```powershell
javap -p -s 'GenericBytecodeDemo$Holder'
javap -p -s 'GenericBytecodeDemo$StringHolder'
javap -p -s 'GenericBytecodeDemo$Uppercase'
```

Quote names containing `$` so the shell does not misinterpret nested class names; in Bash use single quotes or escape `$`. If running from another directory, add `-classpath path/to/classes`.

Flags:

- `-p` displays private members as well.
- `-s` prints descriptors.
- `-v` prints verbose class-file details, including attributes and flags.
- `-c` disassembles the `Code` attribute into JVM instructions.

### 6.1. `Holder<T>` Under `javap -p -s`

Verified excerpt:

```text
class GenericBytecodeDemo$Holder<T> {
  private T value;
    descriptor: Ljava/lang/Object;

  GenericBytecodeDemo$Holder(T);
    descriptor: (Ljava/lang/Object;)V

  public T get();
    descriptor: ()Ljava/lang/Object;

  public void set(T);
    descriptor: (Ljava/lang/Object;)V

  public <N extends java.lang.Number> N echo(N);
    descriptor: (Ljava/lang/Number;)Ljava/lang/Number;

  public java.util.List<java.lang.String> tags();
    descriptor: ()Ljava/util/List;
}
```

`javap` displays readable generic syntax from metadata, **yet the `descriptor:` lines are still erased types**.

What to observe:

- Field `T` → descriptor `Object`.
- Constructor taking `T` → descriptor taking `Object`.
- `T get()` → descriptor returning `Object`.
- `void set(T)` → descriptor taking `Object`.
- Bounded `N extends Number` → descriptor parameter and return `Number`.
- `List<String>` → descriptor is simply `List`.

### 6.2. `StringHolder` Under `javap -p -s`

Excerpt:

```text
final class GenericBytecodeDemo$StringHolder
    extends GenericBytecodeDemo$Holder<java.lang.String> {

  GenericBytecodeDemo$StringHolder(java.lang.String);
    descriptor: (Ljava/lang/String;)V

  public java.lang.String get();
    descriptor: ()Ljava/lang/String;

  public void set(java.lang.String);
    descriptor: (Ljava/lang/String;)V

  public void set(java.lang.Object);
    descriptor: (Ljava/lang/Object;)V

  public java.lang.Object get();
    descriptor: ()Ljava/lang/Object;
}
```

The two `set` lines and two `get` lines **do not all come from source code**. `javap` reveals the extra methods generated by the compiler in the class file. With `-s` you verify exact descriptors; with `-v` you verify bridge/synthetic flags.

### 6.3. `Uppercase` Under `javap -p -s`

Excerpt:

```text
final class GenericBytecodeDemo$Uppercase
    implements GenericBytecodeDemo$Mapper<java.lang.String> {

  public java.lang.String apply(java.lang.String);
    descriptor: (Ljava/lang/String;)Ljava/lang/String;

  public java.lang.Object apply(java.lang.Object);
    descriptor: (Ljava/lang/Object;)Ljava/lang/Object;
}
```

This is the classic pattern when implementing a generic interface with a concrete type argument. The typed method returns `String`; the bridge preserves the erased interface descriptor `Object->Object`.

### 6.4. `-s` Is Not the `Signature` Attribute

It is easy to confuse them because the `-s` option prints **descriptors** while the attribute is named **`Signature`**. To see the separate `Signature:` field in verbose output:

```bash
javap -p -v 'GenericBytecodeDemo$Holder'
```

The output is long because it contains the constant pool, attributes, bytecode, and other metadata. Search for these keywords:

```text
descriptor:
Signature:
ACC_BRIDGE
ACC_SYNTHETIC
```

Always read an excerpt with surrounding context instead of grepping a single line and attributing a `Signature` to the wrong neighboring method.

## 7. Reading Verbose Class Files: Where Does `descriptor` Differ from `Signature`?

For `Holder<T>`, `javap -p -v` shows entries like:

```text
private T value;
  descriptor: Ljava/lang/Object;
  Signature: #...    // TT;
```

For `get()`:

```text
public T get();
  descriptor: ()Ljava/lang/Object;
  Signature: #...    // ()TT;
```

For `set(T)`:

```text
public void set(T);
  descriptor: (Ljava/lang/Object;)V
  Signature: #...    // (TT;)V
```

For the bounded method:

```text
public <N extends java.lang.Number> N echo(N);
  descriptor: (Ljava/lang/Number;)Ljava/lang/Number;
  Signature: #...    // <N:Ljava/lang/Number;>(TN;)TN;
```

For `tags()`:

```text
public java.util.List<java.lang.String> tags();
  descriptor: ()Ljava/util/List;
  Signature: #...    // ()Ljava/util/List<Ljava/lang/String;>;
```

The `#...` indices are constant-pool references and **vary across compilations/JDKs**. What matters is the `// ...` generic signature content and how it differs from the descriptor.

### 7.1. What Does `TT;` Mean?

In the `Signature` grammar:

```text
T<name>;
```

represents a type variable with that name. For example, variable name `T` produces:

```text
TT;
```

and variable name `N` produces:

```text
TN;
```

Do not mistake this for a descriptor referencing a class named `T` or `N`; type variables are generic metadata, while JVM method descriptors use erased types.

### 7.2. Generic Method `<N extends Number>` Has Two Layers of Information

In source code, the compiler ensures `echo` accepts and returns **the same `N`** for each generic invocation:

```java
Integer integer = holder.echo(7);
Double decimal = holder.echo(1.5);
```

Yet the JVM descriptor only says `Number -> Number`. The `Signature` metadata retains the `(TN;)TN;` relationship for compilers/tools needing declaration details.

A call site may have casts inserted by the compiler after reading the result from the erased descriptor. Whether a specific cast exists depends on the compiler-generated bytecode and the type used at the call site.

### 7.3. When Is There No `Signature`?

Not **every** method or field in a class file needs a `Signature`. For instance, a method using only concrete non-generic types like `void ping()` may have only a descriptor.

Do not treat `Signature` as mandatory on every method or as something the JVM checks for dispatch. Descriptors and JVM verification/linkage operate on JVM-level information, whereas `Signature` serves generic reflection/metadata.

## 8. Inspecting `ACC_BRIDGE` and `ACC_SYNTHETIC` Flags

Command:

```bash
javap -p -v 'GenericBytecodeDemo$StringHolder'
```

The test class file contains two bridge methods:

```text
public void set(java.lang.Object);
  descriptor: (Ljava/lang/Object;)V
  flags: (0x1041) ACC_PUBLIC, ACC_BRIDGE, ACC_SYNTHETIC
```

```text
public java.lang.Object get();
  descriptor: ()Ljava/lang/Object;
  flags: (0x1041) ACC_PUBLIC, ACC_BRIDGE, ACC_SYNTHETIC
```

Meaning:

- `ACC_PUBLIC`: the method's access flag.
- `ACC_BRIDGE`: bridge method generated by the compiler to preserve method relationship correctness.
- `ACC_SYNTHETIC`: method not declared directly as an ordinary source-level member.

Both bridges in the example carry `ACC_BRIDGE` and `ACC_SYNTHETIC`. However, **synthetic does not always mean bridge**. The compiler can generate other synthetic members for different compilation needs; use `ACC_BRIDGE` itself or `Method.isBridge()` to identify bridges.

### 8.1. Reading the Bytecode of Bridge `set(Object)`

Run:

```bash
javap -p -c 'GenericBytecodeDemo$StringHolder'
```

The `set(Object)` bridge looks roughly like:

```text
public void set(java.lang.Object);
  Code:
     0: aload_0
     1: aload_1
     2: checkcast     #... // class java/lang/String
     5: invokevirtual #... // Method set:(Ljava/lang/String;)V
     8: return
```

Constant pool indices and offsets can vary. The core sequence is:

1. Load `this`.
2. Load the `Object` argument.
3. `checkcast` to `String`.
4. Invoke the typed `set(String)` method.
5. Return.

If the actual `Object` is not a `String`, `checkcast` throws `ClassCastException`.

### 8.2. Reading the Bytecode of Bridge `get()`

The `Object get()` bridge typically has a structure close to:

```text
public java.lang.Object get();
  Code:
     0: aload_0
     1: invokevirtual #... // Method get:()Ljava/lang/String;
     4: areturn
```

No cast down to `String` is needed on the bridge's return: a `String` result is already usable as an `Object`. The JVM receives a reference compatible with `Object`.

Do not confuse this bridge with other `checkcast` instructions that may appear inside **typed `StringHolder.get()`** when it calls `super.get()` returning `Object` and needs to use the result as `String`.

### 8.3. Do Not Depend on Specific Bytecode Offsets

Compilers/JDKs can change instruction layouts, constant-pool entry counts, or `javap` formatting. When testing, verify **descriptors, method flags, and delegation/cast relationships**, rather than asserting exact bytecode offsets or constant-pool indices verbatim.

## 9. Using Reflection to Compare Source, Erasure, and Generic Metadata

Java Reflection provides several API pairs with distinct meanings.

### 9.1. Erased Type with `getReturnType()`

```java
Method method = Holder.class.getDeclaredMethod("get");

Class<?> erased = method.getReturnType();
```

For `Holder<T>.get()`, `erased` is `Object.class`. This return type matches the erased JVM descriptor.

### 9.2. Generic Declaration with `getGenericReturnType()`

```java
Type generic = method.getGenericReturnType();
```

For `Holder<T>`, the result is a `TypeVariable` named `T`. Printing `getTypeName()` typically shows `T`.

`Method.getGenericParameterTypes()` works similarly for parameter types: `set(T)` has generic parameter `T`, while `getParameterTypes()` gives `Object`.

### 9.3. Field Reflection Also Distinguishes Both Types

```java
Field field = Holder.class.getDeclaredField("value");

Class<?> erased = field.getType();
Type generic = field.getGenericType();
```

The results describe `Object` and `T` respectively. This is how to inspect generic metadata preserved on declarations.

### 9.4. Generic Superclass from a Concrete Subclass

```java
Type parent = StringHolder.class.getGenericSuperclass();
```

It describes `Holder<String>`, typically as a `ParameterizedType`.

Distinguish between:

```java
Holder.class.getTypeParameters()
```

which returns the declared type variable `T`, and:

```java
StringHolder.class.getGenericSuperclass()
```

which describes how a concrete subclass substitutes `String` for `T` in its immediate superclass declaration.

To resolve the type of field `T` **in the context of** a subclass with multiple inheritance levels, a type resolver must compose type-variable mappings rather than grabbing a `Field` object and assuming `T` automatically becomes `String`.

### 9.5. Identifying Bridges via Reflection

```java
for (Method method : StringHolder.class.getDeclaredMethods()) {
    System.out.println(method.getName()
            + ":" + method.isBridge()
            + ":" + method.isSynthetic());
}
```

`getDeclaredMethods()` can return multiple methods with the same name and parameter list yet different return types, because the JVM class file contains bridges. For stable tests, filter/sort and inspect return types/parameter types as well.

Flags:

```java
method.isBridge()
method.isSynthetic()
```

are two **separate** queries.

### 9.6. Do Not Design a Reflection Framework Treating Every Method as Source API

If a framework scans `getDeclaredMethods()` and registers all of them as user-defined handlers, bridge methods can cause **duplicate registrations**: both typed `get()` and bridge `get()` are seen.

A common strategy is skipping methods where `isBridge()` is true when you only want source-level handlers, though do not apply this blindly in every framework: some problems need bridges to analyze dispatch paths and compatibility. Define the scan's goal before filtering.

## 10. Bridges Can Appear Due to Covariant Returns Even Without Generics

This is a frequently overlooked point.

Create the file **`CovariantBridge.java`**:

```java
class CovariantBridge {
    static class Parent {
        Number value() {
            return 1;
        }
    }

    static class Child extends Parent {
        @Override
        Integer value() {
            return 2;
        }
    }

    public static void main(String[] args) {
        System.out.println(new Child().value());

        for (var method : Child.class.getDeclaredMethods()) {
            System.out.println(method.getName()
                    + ":" + method.getReturnType().getSimpleName()
                    + ":" + method.isBridge()
                    + ":" + method.isSynthetic());
        }
    }
}
```

Commands:

```bash
javac --release 17 -Xlint:all CovariantBridge.java
java CovariantBridge
```

Output from the test run:

```text
2
value:Integer:false:false
value:Number:true:true
```

This example matched the Reflection ordering in the verified run, yet `getDeclaredMethods()` does not guarantee order across environments. If used as an automated test, sort before comparing.

`javap -p -s 'CovariantBridge$Child'` displays:

```text
java.lang.Integer value();
  descriptor: ()Ljava/lang/Integer;

java.lang.Number value();
  descriptor: ()Ljava/lang/Number;
```

`Child` source returns `Integer`, while `Parent` source returns `Number`. The JVM descriptors differ in return type, so the compiler generates a bridge returning `Number` to preserve dispatch. **There is no `<T>` anywhere in this example.**

Conclusion: bridges are closely associated with Java Generics, yet **they are not exclusive to Generics**. They can also arise from return-type covariance.

## 11. Distinguishing Bridge, Overload, Override, and Synthetic

| Scenario | Declared/Created By | Meaning |
| --- | --- | --- |
| `String get()` overriding `T get()` with `T=String` | Java source author | Override under Java's Generics rules |
| `Object get()` with `ACC_BRIDGE` | Compiler | Bridges erased superclass descriptor to typed override |
| `void set(Object)` with `ACC_BRIDGE` | Compiler | Casts `Object` to `String` then calls `set(String)` |
| Two source methods `process(String)` and `process(Integer)` | Java source author | Valid overloading, not a bridge |
| `Integer value()` overriding `Number value()` | Java source author | Covariant-return overriding |
| Synthetic bridge `Number value()` | Compiler | Preserves non-generic superclass descriptor |
| Another synthetic method | Compiler/tooling | May not be a bridge |

### 11.1. Do Not Treat Every Same-Named Method as a Bridge

A class with two valid overloads:

```java
void log(String value) {}
void log(Integer value) {}
```

has distinct parameter descriptors and both can be ordinary source methods; `isBridge()` is normally false.

Bridges arise from overriding/erasure/covariant-return relationships, not simply from sharing a method name.

### 11.2. Do Not Manually Call Bridges as Normal Overloads

In `StringHolder` source, you do not write:

```java
// Cannot use this to declare a parallel source overload
// differing only by return type:
// public Object get() { ... }
```

A JVM class file can contain compiler-generated methods that you cannot define with the same signature in Java source. Use the normal typed API and let the compiler/JVM handle the bridging.

## 12. Name Clashes After Erasure: The Compiler Does Not Auto-Generate Bridges to Fix Every Error

A common misconception when learners first encounter bridges is thinking "if two methods erase the same way, the compiler always adds a bridge." In reality, **no**.

### 12.1. Two Overloads Differing Only in Generic Argument

Create the file **`ErasureClash.java`**:

```java
import java.util.List;

class ErasureClash {
    void process(List<String> names) {
    }

    void process(List<Integer> numbers) {
    }
}
```

Run:

```bash
javac --release 17 ErasureClash.java
```

The compiler reports:

```text
name clash: process(List<Integer>) and
process(List<String>) have the same erasure
```

The two overloads look distinct in generic source, yet the erasure of both parameter lists is raw `List`.

You must fix the **API declaration**, for example:

```java
void processNames(List<String> names) {}
void processNumbers(List<Integer> numbers) {}
```

or use a single generic method if the implementation is genuinely identical. Casting at call sites or invoking `javap` cannot rescue an invalid source declaration.

### 12.2. Conflict with a Generic Superclass That Is Not an Override

Create the file **`BadOverride.java`**:

```java
class BadOverride {
    static class Parent<T> {
        void set(T value) {
        }
    }

    static class Child extends Parent<String> {
        void set(Object value) {
        }
    }
}
```

The Java 17 compiler reports:

```text
name clash: set(Object) in Child and
set(String) in Parent have the same erasure,
yet neither overrides the other
```

`Child` declares `set(Object)` while the inherited method after substituting `T` in the generic relationship is `set(String)`. Having the same erased descriptor does not turn `set(Object)` into a valid override under Java source rules.

The right way is:

```java
static class Child extends Parent<String> {
    @Override
    void set(String value) {
    }
}
```

And let the compiler generate a bridge if needed. Do not change the parameter from `String` to `Object` expecting "matching the bytecode descriptor is enough."

### 12.3. `@Override` Helps Catch Mistakes Early

Always consider putting `@Override` on methods intended to override. If you accidentally get a parameter type wrong or declare a new overload, the compiler immediately points out that the method does not properly override.

Bridge methods are generated from a **valid override relationship**, not as a relaxation of override rules.

## 14. How to Analyze Real Class-File Issues

### 14.1. Step 1: Compile Cleanly and Identify the Version

```bash
javac -version
javac --release 17 -Xlint:all GenericBytecodeDemo.java
```

`--release 17` sets the language/API/class-file target to Java 17 when supported by the running compiler. It is a more reliable way to reproduce examples than `-source 17` alone when API targeting also matters.

### 14.2. Step 2: Inspect Descriptors with `-s`

```bash
javap -p -s 'GenericBytecodeDemo$Holder'
javap -p -s 'GenericBytecodeDemo$StringHolder'
```

Write down the method name + descriptor pairs. Do not jump to analyzing the generic signature `javap` prints in the header while ignoring the `descriptor:` line.

### 14.3. Step 3: Inspect `Signature` and Flags with `-v`

```bash
javap -p -v 'GenericBytecodeDemo$Holder'
javap -p -v 'GenericBytecodeDemo$StringHolder'
```

Look for `Signature:`, `ACC_BRIDGE`, and `ACC_SYNTHETIC`. Note that a class can have a **class-level** `Signature` for its generic superclass, while individual methods may or may not have their own `Signature`.

### 14.4. Step 4: Inspect Cast/Delegation Instructions with `-c`

```bash
javap -p -c 'GenericBytecodeDemo$StringHolder'
```

Check that the `set(Object)` bridge performs `checkcast String` and calls the typed `set`; the `get(Object)` bridge delegates to typed `get(String)`. When you need to understand why `ClassCastException` happens, this is direct evidence.

### 14.5. Step 5: Cross-Check with Reflection

Use:

```java
Class<?> type = StringHolder.class;

for (Method method : type.getDeclaredMethods()) {
    System.out.println(method.toGenericString()
            + " bridge=" + method.isBridge()
            + " synthetic=" + method.isSynthetic());
}
```

Reflection provides the runtime view; `javap` provides the class-file view. When both confirm bridge flags and signatures, you avoid mistaking compiler/tool artifacts for handwritten source.

### 14.6. Step 6: Verify Dynamic Dispatch Through a Superclass/Interface Variable

```java
Holder<String> ref = new StringHolder("hi");
String value = ref.get();
```

The call is compiled in the `Holder<String>` context, yet runtime dispatch must still reach the `StringHolder` override. Correct runtime behavior is the key criterion, not merely the presence of a bridge flag.

### 14.7. Step 7: Do Not Rely on Reflection Ordering

`Class.getDeclaredMethods()` has no ordering guarantee. When writing assertions, filter by name, parameter types, return type, and flags, or sort the results.

A bridge method can share the same name/parameter list as a typed method if only the return type differs. Hence a test using only `getDeclaredMethod("get")` without checking flags/return type may miss the bridge. Iterate all declared methods when auditing.

## 15. Reflection and Frameworks: When Do Bridges Cause Duplicates?

A dependency injection container, serializer, annotation scanner, or RPC framework may scan method declarations via Reflection. If it treats all `getDeclaredMethods()` as source-level APIs, a class with both:

```text
String get()
Object get()  [bridge]
```

could accidentally be registered as two handlers, two bean properties, or two operations.

A common handling pattern is:

```java
if (method.isBridge()) {
    continue;
}
```

when the scanner's goal is **methods declared by the programmer in source**. However:

- Some frameworks need bridges to link annotations/overridden method metadata.
- A bridge might not carry the same metadata/annotations as the typed implementation.
- Tools that must distinguish override trees and generic declarations may need to **resolve the corresponding method**, not simply skip every bridge.

Therefore, do not turn "always skip bridges" into a universal rule. Define whether the scanner needs to represent *source-level methods*, *all JVM methods*, or *overridden generic contracts*.

### 15.1. `isSynthetic()` Is Not Equivalent to Filtering `isBridge()`

A synthetic method can exist as a compiler-generated artifact unrelated to bridges. If you only want to filter bridges, use `isBridge()`. Filtering all compiler-generated methods is a broader policy requiring careful handling of special cases.

### 15.2. Generic Metadata Does Not Automatically Validate Runtime Data

Reflection seeing `List<String>` in `Signature` does not mean every element in a runtime list is a `String`. Raw/unchecked operations can still introduce bad data. Type tokens and generic signatures state the **declared type**, without validating the runtime object graph.

A real deserialization framework must use metadata to convert/validate data rather than casting a raw `List` and calling it done.

## 16. `javap` and Java Reflection Answer Different Questions

| Question | Appropriate Tool |
| --- | --- |
| What is the JVM method descriptor? | `javap -s`, `javap -v` |
| What generic `Signature` is in the class file? | `javap -v` |
| Does the method have `ACC_BRIDGE`/`ACC_SYNTHETIC`? | `javap -v` |
| How does the bridge cast/delegate? | `javap -c` |
| Does the method have `isBridge()` at runtime? | Java Reflection |
| Erased parameter/return types in Reflection? | `getParameterTypes()`, `getReturnType()` |
| Generic parameter/return metadata? | `getGenericParameterTypes()`, `getGenericReturnType()` |
| Declared generic superclass? | `Class.getGenericSuperclass()` |
| Which methods were declared in source? | Source code + Reflection/`javap` cross-check |
| Does a field value actually satisfy its type arguments? | Real data validation, not just Reflection `Signature` |

Getting the full picture usually requires combining **source, `javap`, Reflection, and runtime tests**. Looking at only one layer of representation can lead to wrong conclusions.

## 17. Why Can Class Files Contain Methods You "Cannot Write" in Java Source?

JVM bytecode format rules and Java source rules are not identical.

Java method overloading in source relies on JLS method signatures, which forbid overloading based solely on return type. Yet JVM method descriptors include the return descriptor, and `javac` can emit bridges to preserve binary-level dispatch.

Consequently, in bytecode:

```text
get:()Ljava/lang/String;
get:()Ljava/lang/Object;
```

can coexist. Java source does not let you declare `String get()` and `Object get()` side by side as two ordinary overloads.

**Big takeaway:** never reason backward that every class-file method corresponds to a handwritten Java source method. `ACC_BRIDGE`, `ACC_SYNTHETIC`, and reading source help tell them apart.

### 17.1. Bridges Also Affect Static Analyzers

If a tool simply counts public methods in a class file, it may count both bridges and typed implementations, reporting a larger number than in source. When defining API-surface rules, decide explicitly whether bridges are counted.

### 17.2. Having a `Signature` Does Not Mean Having a Bridge

A `List<String> tags()` method has a `Signature` retaining its type argument, yet normally needs no bridge if it is not part of an override relationship requiring a bridge descriptor.

A generic class `Holder<T>` has many `Signature` entries, yet **`Holder` itself** does not necessarily contain any bridge. Bridges are generated on subclasses or interface implementors when actually required.

## 18. Class-File Metadata and Binary Compatibility

Type erasure helps Java Generics maintain compatibility with pre-Generics libraries in many cases, yet do not conclude that **every generic signature change is binary-compatible**.

For example, changing a raw parameter type `List` to `Collection` changes the JVM descriptor; existing compiled client bytecode may fail to link to the new method. Conversely, changing only a generic type argument inside `Signature` without changing the descriptor might leave JVM-level method identity intact, yet still alter source type checking and cause compile errors upon recompilation.

Bridges are part of the mechanism that preserves overriding/binary method lookup when a specialized subclass method has a different descriptor due to erasure or return covariance.

### 18.1. When Modifying a Generic Superclass or Interface

A change from:

```java
interface Mapper<T> {
    T apply(T input);
}
```

to a contract with a different bound/return/parameter can change erased descriptors, causing compatibility problems for previously compiled classes. Evaluate:

- Source compatibility when clients recompile.
- Binary compatibility with already-compiled clients.
- Override/bridge methods regenerated by the compiler.
- Whether Reflection-based frameworks depend on `Signature`/bridge metadata.

Do not strip synthetic bridge methods via bytecode post-processing just because "source didn't declare them"; doing so can break required dispatch paths.

### 18.2. Bytecode Tools Should Preserve Appropriate Attributes

If a build step optimizes or transforms class files, stripping `Signature` may not break JVM linkage immediately, yet it loses generic information needed by Reflection, serializers, or frameworks. Stripping bridges is even more dangerous because they can serve as method dispatch entry points.

When debugging differences between a regular build and an obfuscated/shaded/instrumented build, inspect descriptors, `Signature`, flags, and bridge bytecode.

## 19. Common Pitfalls When Learning from `javap`

### Pitfall 1 — Seeing `javap` print `T` and saying the JVM actually calls a method taking `T`

Inaccurate. `javap` reconstructs readable generic signatures from metadata, yet the descriptor for an unbounded type variable is still `Object`. The JVM has no `T` parameter type in descriptors.

### Pitfall 2 — Assuming `Signature` and descriptor are the same data

Wrong. Descriptors govern JVM-level types/linkage; `Signature` stores generic metadata in a different grammar.

### Pitfall 3 — Thinking `Signature` stores type arguments of every object instance

Wrong. It describes **declarations**, not per-instance type arguments at runtime.

### Pitfall 4 — Thinking only generic methods need bridges

Wrong. A subclass overriding a generic superclass/interface with a concrete typed method can need a bridge; non-generic covariant returns can also generate bridges.

### Pitfall 5 — Thinking every generic method generates a bridge

Wrong. Bridges are generated when needed to preserve overriding/dispatch. A standalone generic method like `Holder.echo` can have a `Signature` without needing any bridge.

### Pitfall 6 — Assuming `synthetic=true` always equals `bridge=true`

Wrong. Bridges are synthetic in verified `javac` output, yet synthetic members can also serve other purposes.

### Pitfall 7 — Manually writing `void set(Object)` to override a specialized `void set(T)`

This causes a name clash ("same erasure, yet neither overrides"). Define the override with the properly typed parameter per source rules, and the compiler will generate the bridge automatically.

### Pitfall 8 — Overloading `process(List<String>)` and `process(List<Integer>)`

Invalid due to identical erasure. Bridges are not a mechanism for resolving name-clashing overload declarations.

### Pitfall 9 — Iterating Reflection without sorting and asserting order

`getDeclaredMethods()` has no ordering guarantee. Sort or filter using all necessary criteria.

### Pitfall 10 — A framework registering a bridge as a second handler

Can happen when scanning all declared methods without distinguishing source APIs from synthetic compiler artifacts.

### Pitfall 11 — Treating the cast inside a bridge as a compiler bug

`checkcast` in `set(Object)` preserves type safety while delegating to the `String`-accepting method. If Reflection/raw code passes the wrong type, `ClassCastException` is the expected outcome.

### Pitfall 12 — Comparing constant-pool indices across compilers

`#...` numbers, offsets, and formatting details are unstable. Compare the semantics of descriptors, `Signature`, flags, and delegation paths.

### Pitfall 13 — Using Reflection generic types to claim a runtime collection is safe

Generic metadata does not check elements. If code uses raw/unchecked casts, heap pollution can still happen.

### Pitfall 14 — Confusing method descriptors with Java overloading rules

In JVM descriptors, the return type is encoded. In Java source, overloading solely by return type is disallowed. Bridges are generated by the compiler under separate rules.

### Pitfall 15 — Running `javap` only on the subclass

You need to inspect **both the superclass/interface erased descriptor** and **the subclass implementation/bridge** to explain why the bridge exists.

## 20. Checklist When Encountering Bridges or Generic Erasure Errors

1. Identify the compiler/JDK version and compile target; in this lesson use `--release 17`.
2. Open the source declarations of superclass/interface and subclass; locate type parameters/bounds.
3. Write down source signatures after **substituting type arguments**, e.g., `T = String`.
4. Compute each method's erasure based on its bounds, not assuming `Object` if a bound exists.
5. Use `javap -p -s` to confirm descriptors on both superclass/interface and subclass.
6. Use `javap -p -v` to find `Signature:` on relevant classes/fields/methods.
7. For extra methods absent from source, check `ACC_BRIDGE` and `ACC_SYNTHETIC`.
8. Use `javap -p -c` to see which method the bridge delegates to and what it casts.
9. Use Reflection `getDeclaredMethods()`, `isBridge()`, `isSynthetic()`, and return/parameter types to verify at runtime.
10. Do not rely on Reflection ordering; sort or filter before asserting.
11. Verify dynamic dispatch through a variable of the superclass/interface type.
12. For `name clash` errors, distinguish declaration conflicts from valid overrides with bridges.
13. For generic fields/returns, separate `getType()`/`getReturnType()` from `getGenericType()`/`getGenericReturnType()`.
14. When changing APIs or transforming class files, evaluate source/binary compatibility and framework Reflection.
15. Do not use raw/unchecked code as proof that bridges work; if testing runtime errors, isolate them in test examples.
16. Note explicitly that details such as constant-pool indices depend on the compiler/class-file tool.

## 21. Practice Exercises and Answers

### Exercise 1 — Erasure of an Unbounded Type Variable

Given:

```java
class Box<T> {
    T value();
}
```

**Question:** What is the return descriptor of `value()` if `T` has no explicit bound?

<details>
<summary>Answer</summary>

The erasure of `T` is `Object`, so the method descriptor is `()Ljava/lang/Object;`. If the class file retains a generic method `Signature`, the return part uses `TT;`, e.g., `()TT;`.

</details>

### Exercise 2 — A Bound Changes the Descriptor

Given:

```java
<N extends Number> N twice(N n);
```

**Question:** What are the erased parameter/return types?

<details>
<summary>Answer</summary>

Both erase to `Number`, so the descriptor is `(Ljava/lang/Number;)Ljava/lang/Number;`. The generic `Signature` preserves the `N` type relationship on both input and output.

</details>

### Exercise 3 — `List<String>` in the Return Type

```java
List<String> names();
```

**Question:** Why doesn't the descriptor contain `String`?

<details>
<summary>Answer</summary>

The parameterized type `List<String>` erases to `List`, so the descriptor is `()Ljava/util/List;`. The generic `Signature` can record `()Ljava/util/List<Ljava/lang/String;>;`.

</details>

### Exercise 4 — Why Does `StringHolder` Need `Object get()`?

Given:

```java
class Base<T> {
    T get() { return null; }
}
class Derived extends Base<String> {
    @Override String get() { return "x"; }
}
```

<details>
<summary>Answer</summary>

The erased `Base.get` descriptor returns `Object`, while typed `Derived.get` returns `String`. The compiler can generate an `Object get()` bridge in `Derived` so calls through the erased `Base` method descriptor dispatch to the typed override.

</details>

### Exercise 5 — Why Does the `set(Object)` Bridge Have a Cast?

<details>
<summary>Answer</summary>

The typed implementation method accepts `String`, while the erased superclass method accepts `Object`. The bridge must cast the `Object` argument to `String` before delegating. If a caller passes an `Integer` through a raw/reflection boundary, the cast throws `ClassCastException`.

</details>

### Exercise 6 — Are Bridge and Synthetic Flags the Same?

<details>
<summary>Answer</summary>

No. `ACC_BRIDGE` identifies bridges; `ACC_SYNTHETIC` marks compiler-generated members more broadly. In the Java 17 `javac` example, bridges have both flags, yet not every synthetic method is a bridge.

</details>

### Exercise 7 — Non-Generic Covariant Return

If `Parent` returns `Number` and `Child` overrides returning `Integer`, can a bridge appear?

<details>
<summary>Answer</summary>

Yes. In the `CovariantBridge` example, the compiler generated the typed `Integer value()` implementation and a `Number value()` bridge. This bridge is due to covariant return, even with no generic type parameters declared.

</details>

### Exercise 8 — Overload Error After Erasure

```java
void save(List<String> names) {}
void save(List<Integer> counts) {}
```

**Question:** Does the compiler generate a bridge to distinguish the two methods?

<details>
<summary>Answer</summary>

No. Both share the same erased parameter type `List`, causing a name clash. You must change the signatures/names or redesign the API.

</details>

### Exercise 9 — Reflection Sees Two `get` Methods

If Reflection on a subclass lists one typed `get` and one bridge `get`, how does a scanner register only user-declared methods?

<details>
<summary>Answer</summary>

One approach is filtering out `method.isBridge()` and also considering `isSynthetic()` and the framework's context. Check return types because the JVM can hold the same name/parameters with different return descriptors. If the scanner needs to link generic override metadata, it may need to resolve the bridge rather than simply skipping it.

</details>

### Exercise 10 — Generic Superclass and Generic Field

`StringHolder extends Holder<String>` yet `Holder.value` has generic type `T`. Why doesn't `Holder.class.getDeclaredField("value").getGenericType()` automatically return `String.class`?

<details>
<summary>Answer</summary>

`Holder`'s field declaration still uses type variable `T`. `StringHolder`'s generic superclass metadata stores the mapping `T->String`, yet Reflection on `Holder`'s field directly does not carry the subclass's context. A resolver must combine both metadata sources.

</details>

### Exercise 11 — `javap -s` or `javap -v`?

<details>
<summary>Answer</summary>

`-s` prints descriptors. `-v` displays verbose attributes/flags, including `Signature` and `ACC_BRIDGE`. Use `-c` to view JVM instructions and `-p` to include private members.

</details>

### Exercise 12 — Does a Bridge Guarantee That `List<String>` Actually Contains Only `String`?

<details>
<summary>Answer</summary>

No. Bridges preserve dispatch when generic overriding/covariant returns need matching descriptors. They do not validate individual elements inside generic collections or prevent heap pollution from raw/unchecked operations.

</details>

## 22. Summary

To read Generics accurately in class files, examine **all three layers**:

1. **Source generic declaration** telling the compiler the type relationships: `T get()`, `void set(T)`, `<N extends Number> N echo(N)`, `List<String> tags()`.
2. **Erased JVM descriptor** used at runtime to identify/call methods: `Object` for unbounded `T`, `Number` for bounded `N`, `List` for `List<String>`.
3. **Generic `Signature` metadata** allowing tools to recover type declarations: `()TT;`, `(TT;)V`, `<N:Ljava/lang/Number;>(TN;)TN;`, and nested generic type arguments.

When a specialized generic subclass override or covariant return has a different descriptor, the compiler can emit a **bridge method**. On Java 17, `javap -v` reveals `ACC_BRIDGE, ACC_SYNTHETIC` flags; Reflection confirms them with `Method.isBridge()` and `isSynthetic()`. Bridges only connect descriptors/dispatch paths for valid relationships—they do **not** fix name-clashing declarations and do **not** reify generic types of object instances.

A reliable workflow is: **read source → compute erasure → inspect `javap -s` → inspect `Signature`/flags with `javap -v` → view bridge bytecode with `javap -c` → cross-check Reflection and runtime dispatch**. Mastering this workflow lets you tell apart user-declared APIs, Generics metadata, and bytecode methods the compiler must emit so Java overriding works properly.
