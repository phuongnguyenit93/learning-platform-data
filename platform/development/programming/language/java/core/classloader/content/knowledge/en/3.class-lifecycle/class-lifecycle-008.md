# Distinguishing Class Linking from Class Initialization in Java

## 1. What Needs to Be Distinguished

When a Java application refers to a class, the JVM does not necessarily run that class's `static` statements immediately. Two phases that are often confused are **class linking** and **class initialization**:

- **Linking**: The JVM checks and prepares a loaded class/interface so that it can participate in execution. The three related activities are **verification**, **preparation**, and **resolution**.
- **Initialization**: The JVM executes the initialization logic for the class's `static` variables and `static { ... }` blocks (for an interface, the field initialization expressions), corresponding to the special initialization method `<clinit>` if the class file has this method.

Overview:

```text
Class name + ClassLoader
        │
        ▼
Loading: find/define class from bytecode
        │
        ▼
Linking
   ├─ Verification: check class file and bytecode constraints
   ├─ Preparation: create static fields, assign default values
   └─ Resolution: resolve symbolic references when needed
        │
        ▼
Initialization
   ├─ ensure required superclass (and certain superinterfaces) are initialized
   ├─ run initializers for static fields and static blocks
   └─ complete or transition to erroneous state
        │
        ▼
Use the class and its members
```

**The diagram only shows logical relationships, not an absolute JVM schedule.** According to the specification, a class must be loaded before linking, and **verification + preparation must complete before initialization**. Specifically, **resolution is allowed to be deferred**: references may be resolved only when actually used, even after the class has already been initialized. Therefore, do not infer that every dependency has already been resolved before the first line of `static`.

A practical way to remember this: **linking prepares a class definition for the JVM to use; initialization executes that class's own initialization code**.

## 2. What Activities Does Linking Include?

**Verification** checks the class file and bytecode type safety; typical errors are `ClassFormatError` or `VerifyError`. **Preparation** creates the `static` fields with default values (`0`, `false`, `null`), without yet executing application assignments or `static` blocks. **Resolution** looks up the class/field/method described by a symbolic reference and checks linkage conditions; it can occur early or late. Constants with `ConstantValue` are assigned in a separate step at the start of **initialization** according to JVMS §5.5, and must not be equated with running Java initializers during preparation.

For example, `static int count = 42;` has the default value `0` after preparation and receives `42` when the initializer is executed. `static final int LIMIT = 42;` is a constant variable and may be inlined by the compiler at use sites; merely reading it does not require initializing the declaring type. Both tasks can complete even when no object has been created yet.

## 3. What Does Initialization Actually Do?

During class initialization, the JVM ensures the required prerequisites (such as initializing the superclass first), and then executes `static` field assignments/initialization expressions and `static { ... }` blocks **in the order they appear in source code**, corresponding to the logic of the special `<clinit>` method generated by the compiler if needed.

```java
static int a = calculateA();    // initialization step written by the program
static { log("block 1"); }      // initialization block
static int b = calculateB();    // next initialization step
```

These expressions can perform I/O, call methods, modify state, and throw exceptions. Therefore, initialization has observable side effects; linking by itself is not the execution of a static initializer.

**Do not confuse the three mechanisms:**

- `<clinit>`: the **class/interface** initialization method; executed by the JVM during the initialization phase, not called directly from Java source.
- `<init>`: the **object** constructor; runs during instance creation after class initialization requirements have been satisfied.
- **Instance** field initialization: part of object initialization; does not occur merely because the class has been linked/initialized.

A class without its own `static` initialization logic may not have a `<clinit>` in its class file; that does not mean the JVM completely skips the initialization state rules for the class.

## 4. When Does the JVM Require Initialization?

Initialization is required when creating an instance `new T()`, calling a `static` method declared by T, reading/writing a `static` field declared by T (reading an inlined constant variable alone does not trigger it), or using certain reflection APIs such as `Class.forName(name)`.

Conversely, merely obtaining `T.class`, creating `new T[10]`, calling `ClassLoader.loadClass`, or calling `Class.forName(name, false, loader)` **does not by itself** require initializing T. For an inherited field, consider **the class that actually declares the field**, not just the type name on the left side in source. The next article analyzes the triggers, parent/child ordering, and multithreaded cases in detail.

## 5. Runnable Example: A Class Loaded but Not Yet Initialized

Create the `LifecycleDemo.java` file below (Java 17+):

```java
public class LifecycleDemo {
    static class Parent {
        static {
            System.out.println("Parent initialized");
        }

        static int count = 7;
    }

    static class Child extends Parent {
        static {
            System.out.println("Child initialized");
        }

        static void ping() {
            System.out.println("Child.ping");
        }
    }

    public static void main(String[] args) throws Exception {
        System.out.println("A: class literal");
        Class<?> token = Child.class;

        System.out.println("B: load without initialization");
        Class<?> loaded = Class.forName(
                Child.class.getName(),
                false,
                LifecycleDemo.class.getClassLoader()
        );

        System.out.println("same Class object: " + (token == loaded));

        System.out.println("C: inherited static field");
        System.out.println("count=" + Child.count);

        System.out.println("D: Child static method");
        Child.ping();

        System.out.println("E: done");
    }
}
```

Run in the terminal:

```bash
javac LifecycleDemo.java
java LifecycleDemo
```

Exact stdout on the first run in a fresh JVM:

```text
A: class literal
B: load without initialization
same Class object: true
C: inherited static field
Parent initialized
count=7
D: Child static method
Child initialized
Child.ping
E: done
```

**Explanation of the order:**

1. Obtaining `Child.class` and using `Class.forName(..., false, ...)` return the `Class` object for the same class; neither requires running `Child.<clinit>`.
2. `Child.count` is declared in `Parent`. Reading that field triggers initialization of **Parent**, so `Parent initialized` is printed before `count=7`; it does not trigger initialization of Child.
3. Calling `Child.ping()` is an active use of a `static` method declared in Child. The JVM initializes Child (Parent is already done) and only then runs the body of `ping()`.

The example lets you observe **the timing of initialization**; it does not directly measure when the JVM chose to perform the verification/preparation/resolution steps.

## 6. Superclass, Interface, and ClassLoader Relationships

### 6.1. Superclass Before Subclass

When initializing a class, the JVM needs to initialize uninitialized superclasses before that class. Thus, the first `new Child()` can run the initializer of Parent and then Child. A **static field declared in Parent** initializes only Parent even when the source writes `Child.field` (as in section 6).

When initializing a class, the modern Java specification also requires initializing the relevant **superinterfaces that declare default methods** before that class. Do not say that *every* interface a class implements is initialized before the class; an interface without default methods may remain uninitialized.

### 6.2. Interfaces Differ from Classes

An interface is initialized when a trigger requires it, such as accessing a `static` field it declares that is **not a compile-time constant**. Initialization of an interface **does not automatically initialize all of its superinterfaces**.

In an interface, fields are implicitly `public static final`, though not all of them are compile-time constants. For example:

```java
interface Flag {
    int CONSTANT = 10;
    int RUNTIME_VALUE = Integer.parseInt("20");
}
```

Reading `Flag.CONSTANT` does not require initializing Flag; reading `Flag.RUNTIME_VALUE` requires initializing Flag.

### 6.3. One Binary Name Can Have Multiple Initialization States

With plugin mechanisms or containers that use multiple class loaders, the same binary name `com.example.Plugin` defined by two different defining loaders corresponds to **two runtime classes**. They have independent `static` fields and initialization states. The JVM does not use a single "initialized" table keyed by the **textual name** of the class.

Likewise, successful initialization of the same `Class<?>` is shared among threads in the JVM; calling a `static` method repeatedly does not run `<clinit>` again.

## 7. Quick Comparison to Avoid Confusion

| Question | Linking | Initialization |
|---|---|---|
| Purpose | Check and prepare the class for the JVM to use, resolving references when needed | Execute the `static` initialization logic of the class/interface |
| Must already be loaded? | Yes | Yes |
| Runs `static { ... }` blocks? | No | Yes, when the class has such blocks |
| Creates `static` fields and assigns defaults? | Yes, during preparation | Values may be replaced by initializers |
| Can produce errors? | `VerifyError`, `LinkageError` such as `NoSuchMethodError` | `ExceptionInInitializerError`, erroneous init state |
| Timing | Verification/preparation before initialization; resolution may be deferred | According to active-use conditions |
| Re-runs on a second static method call? | Typically does not re-run all of linking on every call | Does not re-run a completed `<clinit>` |
| Directly observable? | Via bytecode, loaded classes, linkage errors, VM tools | Via static initializer side effects and error states |

## 8. Self-Check Questions

1. **Does `Class.forName("x.Y", false, loader)` require running `Y.<clinit>`?** No; the `false` argument does not require initialization.
2. **May the JVM initialize a class that has not undergone verification/preparation?** No; both must complete before initialization.
3. **Must every symbolic reference be resolved before the first line of `static`?** No; resolution can be lazy and may continue after initialization.
4. **What value does `static int n = 5` have at preparation time?** The default value `0`; the assignment of `5` belongs to initialization.
5. **When `static final int N = 5` is used in another class, does it require initializing the declaring class?** No; it is a constant variable and may be inlined.
6. **Does reading `Sub.field` initialize Sub or Super if `field` is declared in Super?** Only the class that actually declares the field, Super, must be initialized when accessing a non-constant-variable field.
7. **Do two ClassLoaders defining two classes with the same name share a single `<clinit>` execution?** No; they are two different runtime classes.
8. **If the first initialization fails, does calling again execute `<clinit>` a second time?** No; the runtime class transitions to an erroneous state and subsequent uses will fail.

When debugging ClassLoader behavior, determine **which runtime class** is in question, **how far that class has been loaded/linked**, and **which operation actually requires initialization**. This is the right way to explain cases where a `Class<?>` already exists yet the static initializer has not run, or where initialization throws an error even though the bytecode was previously accepted by the JVM.
