# Why must a class loader receive the exact class name and matching bytecode?

When the JVM requests loading a class named `com.example.Order`, the class loader must supply bytecode that actually describes **`com.example.Order`**. Having a valid `.class` file is not enough: the bytecode inside contains **the class name declared in the class file structure**. If the name requested by the JVM and the name embedded in the bytecode do not match, the class cannot be defined under that name.

This rule protects the consistency of class identity, type linkages, method invocations, and dynamic loading. It is especially important when writing a custom `ClassLoader`, reading bytecode from JARs, directories, networks, databases, or after a bytecode transformation step.

## 1. Three name concepts to distinguish

Consider the following Java code:

~~~java
package com.example;

public class Order {
}
~~~

| Concept | Corresponding value | Meaning |
| --- | --- | --- |
| *Binary name* | `com.example.Order` | The name used by APIs such as `ClassLoader.loadClass(String)` and `defineClass(String, …)` for ordinary classes. |
| *Internal name* (JVM internal name) | `com/example/Order` | The slash-separated form that appears in the `this_class` entry of the class file. |
| Common resource path | `com/example/Order.class` | The location commonly used to locate bytecode by directory/JAR convention; the path itself does not determine the class name inside. |

In a class file, the `this_class` field points to a `CONSTANT_Class_info` entry in the constant pool, from which the internal name of the class being defined is obtained. The JVM can convert the internal name `com/example/Order` into the binary name `com.example.Order` to check it against the request.

**Key takeaway:** renaming `Another.class` to `Order.class` or moving the file into the right directory *does not modify* `this_class`. The bytecode still describes the old name. Class names are also case-sensitive: `Order` is different from `order`.

Nested classes have binary names of the form `com.example.Outer$Inner` (if that is the name generated by the compiler). Do not replace `$` with `.` in the name passed to `loadClass`.

## 2. From the requested name to bytecode

General flow for an **ordinary named class**:

~~~text
Request to load "com.example.Order"
             |
             v
ClassLoader.loadClass("com.example.Order")
             |
             +--> Already loaded? / found by parent delegation?
             |                   |
             |                   +--> Yes: return the found Class
             |
             v
Custom loader's findClass("com.example.Order")
             |
             v
Locate/read the right bytecode source and verify readability
             |
             v
defineClass("com.example.Order", bytes, 0, bytes.length)
             |
             +--> Invalid bytecode/unsupported version: corresponding error
             +--> this_class describes a different name: NoClassDefFoundError
             |
             v
Class<?> representing the defined class
~~~

Simplified diagram: `loadClass` normally checks for an already-loaded class and delegates to the parent loader before calling `findClass`; a custom implementation can alter this policy. Therefore, **not every call to `loadClass` leads to `defineClass`**, especially when the class has already been found by a parent loader.

A common `findClass` implementation converts the binary name into a resource path:

~~~java
String resourcePath = binaryName.replace('.', '/') + ".class";
~~~

That conversion helps **locate the right resource**, but it does not verify the bytecode's identity. The class-definition step still has to check the requested name against the class file data.

For `defineClass(String name, byte[] b, int off, int len)`, the `name` parameter is the **expected binary name**. Per the API contract, if `name` is non-`null` and does not match the name encoded in the bytecode, the JVM throws `NoClassDefFoundError`. The JVM also checks that the class file has a valid structure and version.

## 3. Why must the JVM verify the exact name?

### 3.1. Preserving consistent type identity

A runtime class is not identified solely by file contents or by a name in isolation. For ordinary classes, type identity depends on **both the binary name and the defining class loader**. Two different loaders can define two classes both named `com.example.Order`, and they are two distinct types in the JVM.

Conversely, within *a single class definition*, if the JVM accepted a request for `com.example.Order` while allowing bytecode that declares `com.example.Customer`, the very same `Class` object would have two conflicting names. Any place that tracks names or links classes would lose consistency.

### 3.2. Keeping type references and linking accurate

Bytecode can contain symbolic references to superclasses, interfaces, fields, methods, and other types by name. The *linking/resolution* process relies on those references and the class loader context to find the exact type referred to. If an arbitrary name could be assigned to a different class file, code using `com.example.Order` could end up linking against a completely different structure than expected.

Name matching helps catch loading the wrong class early; it does not guarantee that the entire bytecode is valid. The JVM also performs format checks, access checks, loading constraints, and bytecode verification at the appropriate stages.

### 3.3. Catching packaging and bytecode transformation bugs early

A name mismatch is often a symptom of a broken operation: copying or renaming a `.class` file, mispackaging a JAR, applying *relocation/shading* rules without updating the bytecode, or mapping a name to the wrong resource. Rather than running a different class under the requested name, the JVM fails immediately at definition time.

This is a **consistency** check, not a digital signature check or proof that the bytecode is safe. Access permissions, code provenance, and other security checks are separate responsibilities.

## 4. Runnable Java example: same bytecode, right name and wrong name

Save the entire snippet below into **`NameMismatchDemo.java`**. The `Actual` class has no `package`, so its binary name is `Actual`.

~~~java
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;

public class NameMismatchDemo {
    static final class ByteArrayLoader extends ClassLoader {
        Class<?> define(String binaryName, byte[] bytes) {
            return defineClass(binaryName, bytes, 0, bytes.length);
        }
    }

    public static void main(String[] args) throws IOException {
        byte[] bytecode = Files.readAllBytes(Path.of("Actual.class"));

        try {
            new ByteArrayLoader().define("Expected", bytecode);
            System.out.println("Khong phat hien loi");
        } catch (NoClassDefFoundError e) {
            System.out.println("Sai ten: " + e.getClass().getSimpleName());
        }

        Class<?> clazz = new ByteArrayLoader().define("Actual", bytecode);
        System.out.println("Ten dung: " + clazz.getName());
    }
}

class Actual {}
~~~

Open a terminal **in the directory containing the source file**, using JDK 17 or later:

~~~bash
javac NameMismatchDemo.java
java NameMismatchDemo
~~~

Expected output:

~~~text
Sai ten: NoClassDefFoundError
Ten dung: Actual
~~~

Step-by-step explanation:

1. `javac` produces `NameMismatchDemo.class` and `Actual.class`. The second file has `this_class` corresponding to the name `Actual`.
2. Calling `define("Expected", bytecode)` deliberately requests the name `Expected` while the bytecode itself declares `Actual`. `defineClass` detects the mismatch and throws `NoClassDefFoundError`. The program prints only **the error type name** because the detailed message may vary across JVMs.
3. Calling `define("Actual", bytecode)` uses the matching name, so it defines the class successfully and prints `Actual`.
4. Two separate `ByteArrayLoader` instances keep the two definitions isolated in the example. The code intentionally calls `defineClass` directly via a subclass method to test the contract between name and bytecode; it does not simulate the full delegation algorithm of `loadClass`.

**Practical note:** `defineClass` is a `protected final` method. Normal applications do not call it directly from outside; custom code places the call inside a `ClassLoader` subclass, typically in `findClass`. Defining two classes with the same binary name by two different defining loaders is allowed by the JVM, but instances of those two types cannot be cast to each other.

## 5. Distinguishing name errors from other class-loading errors

| Situation | Typical outcome | Meaning |
| --- | --- | --- |
| Cannot find a class by name in `loadClass`'s lookup mechanism | `ClassNotFoundException` | The loader could not supply the requested class; this is a checked exception commonly thrown by `loadClass`/`Class.forName`. |
| Valid class file, but `this_class` does not match the `name` passed to `defineClass` | `NoClassDefFoundError` | The bytecode describes **a different class** from the name the JVM is defining. |
| Bytecode does not follow valid class file structure | `ClassFormatError` | A content formatting problem, not necessarily a name mismatch. |
| Class file was compiled for a JVM version not supported by the runtime | `UnsupportedClassVersionError` | Incompatible bytecode version; a subclass of `ClassFormatError`. |
| Defined class fails verification rules | `VerifyError` | A bytecode type/flow constraint issue during verification, not a name mismatch. |
| Attempting to redefine the same binary name in the same defining loader | `LinkageError` | Duplicate definition or loading constraint violation; distinct from using two separate loaders. |

`NoClassDefFoundError` also has other causes, such as when a dependency was present at compile time but cannot be found or loaded at runtime. Therefore, **you cannot conclude from the exception name alone that `this_class` is wrong**; inspect the message, stack trace, and class-loading path.

## 6. Applying this when writing a custom ClassLoader

A custom loader should preserve the following invariants:

1. **Preserve the requested binary name.** In `findClass(String name)`, use `name` as the input to route to the JAR, directory, or bytecode source. Convert dots to slashes only when constructing a conventional resource path.
2. **Fetch the exact bytes of the class file and read the complete data.** Do not assign the requested name based solely on the filename or a fuzzy lookup result. Bytecode is not a Java source snippet or a UTF-8 text string.
3. **Pass the exact name to `defineClass(name, bytes, 0, bytes.length)`.** The API allows passing `null` when the name is unknown; however, passing the expected binary name enforces an explicit identity check and is the recommended approach for name-based loaders.
4. **Keep delegation and loader scoping intentional.** If the parent has already loaded a class, standard `loadClass` returns that class. If designing a child-first loader, remember that the same binary name under a different defining loader creates a distinct runtime type.
5. **Separate lookup failures from definition failures.** When the source does not contain the requested name, `findClass` should throw `ClassNotFoundException`; when `defineClass` receives unsuitable bytecode, do not swallow `LinkageError` and turn it into a "file not found" message.
6. **Capture enough context for diagnostics.** On failure, record the requested binary name, resource/JAR source, expected defining loader, and root cause. There is no need to dump the entire bytecode into logs.

### Two common real-world mistakes

**Renaming a file without updating the class file contents.** A file containing `com/vendor/OldName` is copied to `com/app/NewName.class`. The loader finds the resource at the new path, but `defineClass("com.app.NewName", bytes, …)` still fails. You must rebuild or properly rewrite the bytecode to update the actual name, not just rename the file.

**Reading the wrong entry from a JAR.** The loader is handling `com.example.Order` but accidentally reads the `com/example/Customer.class` entry. The fact that both entries exist and are valid class files does not help: `this_class` in the read entry is still `com/example/Customer`. Verify the mapping binary name → resource path → class-file content.

## 7. Key points to remember and self-check

- **Requesting a name means defining the class with that exact name:** `name` in `defineClass` must match the binary name described by `this_class` when `name` is non-`null`.
- **A path is not identity:** filenames or directories are only storage/lookup mechanisms; the class file structure holds the true identity.
- **Having the right name is not enough:** the bytecode must also satisfy format, version, verification rules, and other linking constraints.
- **Name plus defining loader forms runtime identity:** the same name under two loaders can represent two distinct types; when delegation succeeds, a child loader may return a class defined by its parent loader.

Quick check: a loader receives `loadClass("com.example.Invoice")`, finds the resource `com/example/Invoice.class`, but the `this_class` field points to `com/example/Receipt`. Can `Invoice` be defined from this bytecode? **No.** The path matches, but the name inside the bytecode is wrong; calling `defineClass("com.example.Invoice", …)` throws `NoClassDefFoundError`. Fix the data or the mapping to the right bytecode; do not alter the requested name to "work around" the contract with the caller.
