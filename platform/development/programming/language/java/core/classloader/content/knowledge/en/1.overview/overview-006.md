# An End-to-End Example: Host Application and Plugin in Java ClassLoader

## 1. The Problem and What to Observe

Suppose a **host** application wants to support multiple extensible features (plugins). The host knows a shared **Java contract**, without needing to know the implementation class names in advance or recompile whenever a new plugin is added. Each plugin is packaged in an independent JAR file and loaded while the host is running.

This article builds a runnable Java 17+ example from start to finish, answering the following questions:

- Through which interface do the host and plugin see each other?
- Who loads the API class, and who loads the plugin's implementation class?
- Why is having the same class name not necessarily the same Java type?
- How does `ServiceLoader` find plugins via JAR metadata?
- When replacing a JAR or closing a `URLClassLoader`, what actually happens?

The goal is to understand **the class loading path and the contract between the host and the plugin**. This is an example of plugins running in the **same JVM**, not a security sandbox and not spawning separate processes.

## 2. Architecture Diagram and Class-Loading Boundary

~~~text
JVM
├── Application ClassLoader (parent)
│   ├── demo.api.GreetingPlugin        ← shared API, owned by the host
│   └── demo.host.HostApp              ← host application
│
└── URLClassLoader (child, parent = GreetingPlugin's loader)
    └── hello-plugin.jar
        ├── demo.plugins.HelloPlugin   ← implementation class
        └── META-INF/services/demo.api.GreetingPlugin
~~~

`HostApp` creates a `URLClassLoader` whose **parent** is the ClassLoader that loaded `GreetingPlugin`. Under the standard delegation behavior of `URLClassLoader`, when a plugin needs `demo.api.GreetingPlugin`, the plugin's loader asks its parent first. Therefore, both the host and the plugin share **the exact same** `Class<?>` object for the interface.

Conversely, `HelloPlugin` only exists inside the plugin JAR, not on the host's startup classpath. When this implementation is needed, the child ClassLoader finds it inside the JAR.

Dependency flow:

~~~text
host source ──depends on──> api source
plugin source ─depends on──> api source
host runtime ──loads───────> plugin JAR via URLClassLoader
~~~

**Design rule:** The shared API belongs on the host/parent side; the plugin JAR only carries the implementation and the service declaration file. If each side tries to use a copy of the API defined by its own loader, type casting can fail, even when both classes have the same fully qualified name.

## 3. Directory Structure

Create the following small project; the `build/` and `dist/` directories will be generated by the compilation commands in Section 5:

~~~text
host-plugin-demo/
├── api/
│   └── demo/api/GreetingPlugin.java
├── host/
│   └── demo/host/HostApp.java
├── plugin/
│   └── demo/plugins/HelloPlugin.java
└── plugin-resources/
    └── META-INF/services/demo.api.GreetingPlugin
~~~

### 3.1. Shared API: `api/demo/api/GreetingPlugin.java`

~~~java
package demo.api;

public interface GreetingPlugin {
    String id();

    String greet(String name);
}
~~~

`GreetingPlugin` is the stable contract. The host only calls `id()` and `greet(String)` through this interface, without `import`ing or directly instantiating `HelloPlugin`.

### 3.2. Plugin: `plugin/demo/plugins/HelloPlugin.java`

~~~java
package demo.plugins;

import demo.api.GreetingPlugin;

public final class HelloPlugin implements GreetingPlugin {
    @Override
    public String id() {
        return "hello";
    }

    @Override
    public String greet(String name) {
        return "Hello, " + name + "!";
    }
}
~~~

The implementation class has a default `public` no-argument constructor (since no constructor is explicitly declared), satisfying `ServiceLoader`'s classpath-based provider instantiation mechanism. It references the API interface at compile time, but the API's bytecode **does not need to be repackaged** inside the plugin JAR.

### 3.3. Registering the Provider via JAR Resources

Create the text file **`plugin-resources/META-INF/services/demo.api.GreetingPlugin`** with a single line:

~~~text
demo.plugins.HelloPlugin
~~~

The filename must match the **fully qualified name of the interface**; each effective line in the file is the fully qualified name of a provider. This is **not** a Java file, and it must be placed in the JAR at the exact `META-INF/services/` location. If it is missing or the path is misspelled, `ServiceLoader` will typically not find the provider, even though `HelloPlugin.class` is present in the JAR.

### 3.4. Host: `host/demo/host/HostApp.java`

~~~java
package demo.host;

import demo.api.GreetingPlugin;

import java.net.URL;
import java.net.URLClassLoader;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.ServiceLoader;

public final class HostApp {
    private HostApp() {
    }

    public static void main(String[] args) throws Exception {
        if (args.length != 1) {
            throw new IllegalArgumentException(
                    "Usage: HostApp <path-to-plugin-jar>");
        }

        Path pluginJar = Path.of(args[0]).toAbsolutePath().normalize();
        if (!Files.isRegularFile(pluginJar)) {
            throw new IllegalArgumentException("Plugin JAR not found: " + pluginJar);
        }

        // The shared API has already been loaded from the host application's classpath.
        ClassLoader parent = GreetingPlugin.class.getClassLoader();
        URL[] pluginUrls = {pluginJar.toUri().toURL()};

        // URLClassLoader only owns finding the plugin's bytecode/resources.
        try (URLClassLoader pluginLoader = new URLClassLoader(pluginUrls, parent)) {
            Class<?> apiSeenByPlugin =
                    pluginLoader.loadClass("demo.api.GreetingPlugin");

            System.out.println(
                    "Shared API: " + (apiSeenByPlugin == GreetingPlugin.class));

            // Explicitly pass the loader containing the provider and META-INF/services.
            ServiceLoader<GreetingPlugin> services =
                    ServiceLoader.load(GreetingPlugin.class, pluginLoader);

            int count = 0;
            for (GreetingPlugin plugin : services) {
                count++;
                System.out.println("Plugin ID: " + plugin.id());
                System.out.println("Greeting: " + plugin.greet("Java"));
                System.out.println(
                        "Implementation from child: "
                                + (plugin.getClass().getClassLoader() == pluginLoader));
            }
            System.out.println("Providers: " + count);
        }
    }
}
~~~

Three key points in the host code:

1. `GreetingPlugin.class.getClassLoader()` identifies the loader that defined the API. Passing it as the **parent** ensures the plugin uses the same communication type.
2. `ServiceLoader.load(GreetingPlugin.class, pluginLoader)` requests provider discovery using the plugin's loader. `ServiceLoader` typically only looks up and instantiates providers when **iteration** begins.
3. `try (URLClassLoader ...)` calls `close()` after use, releasing resources held by the loader (such as JAR file handles); it **does not** force the JVM to immediately unload the loaded classes.

## 4. Distinguishing Build-Time Classpath and Runtime Classpath

| Phase | Classpath | Purpose |
|---|---|---|
| Compile API | No external libraries needed | Produce `GreetingPlugin.class` |
| Compile host | `build/api` | Host recognizes the interface |
| Compile plugin | `build/api` | Plugin implements the exact interface |
| Run host | `build/api` and `build/host` | **Do not** put `hello-plugin.jar` on the main classpath |
| Load plugin at runtime | URL of `hello-plugin.jar` | Child ClassLoader finds the provider and implementation class |

The host must launch **without** the plugin JAR on the system classpath. If the JAR is placed there, the Application ClassLoader may load `HelloPlugin` directly, preventing the experiment from demonstrating the intended loader boundary.

## 5. Compiling, Packaging, and Running

Requirements: **JDK 17 or higher**, with `java`, `javac`, and `jar` on `PATH`. Run the commands from the `host-plugin-demo/` directory. Use the exact files created in Section 3.

**Bash (Linux, macOS, Git Bash):**

~~~bash
mkdir -p build/api build/host build/plugin dist/plugins

javac -encoding UTF-8 -d build/api \
  api/demo/api/GreetingPlugin.java

javac -encoding UTF-8 -cp build/api -d build/host \
  host/demo/host/HostApp.java

javac -encoding UTF-8 -cp build/api -d build/plugin \
  plugin/demo/plugins/HelloPlugin.java

cp -R plugin-resources/META-INF build/plugin/

jar --create --file dist/plugins/hello-plugin.jar -C build/plugin .

java -cp "build/api:build/host" \
  demo.host.HostApp dist/plugins/hello-plugin.jar
~~~

**Windows PowerShell:**

~~~powershell
New-Item -ItemType Directory -Force build/api,build/host,build/plugin,dist/plugins | Out-Null

javac -encoding UTF-8 -d build/api api/demo/api/GreetingPlugin.java

javac -encoding UTF-8 -cp build/api -d build/host host/demo/host/HostApp.java

javac -encoding UTF-8 -cp build/api -d build/plugin plugin/demo/plugins/HelloPlugin.java

Copy-Item -Path plugin-resources/META-INF -Destination build/plugin -Recurse -Force

jar --create --file dist/plugins/hello-plugin.jar -C build/plugin .

java -cp "build/api;build/host" demo.host.HostApp dist/plugins/hello-plugin.jar
~~~

At the packaging step, `build/plugin/` contains only `demo/plugins/HelloPlugin.class` and `META-INF/services/demo.api.GreetingPlugin`. You can verify this with:

~~~bash
jar --list --file dist/plugins/hello-plugin.jar
~~~

Make sure the two essential entries are present: `demo/plugins/HelloPlugin.class` and `META-INF/services/demo.api.GreetingPlugin`. The `jar --list` command may also list directories and `META-INF/MANIFEST.MF`.

**Exact stdout of running the host with one plugin on the specified classpath:**

~~~text
Shared API: true
Plugin ID: hello
Greeting: Hello, Java!
Implementation from child: true
Providers: 1
~~~

Identifiers such as `URLClassLoader@...` are not printed because the suffix depends on the run. The `true` lines above directly verify what we want to learn, rather than relying on the ClassLoader's `toString()` string.

## 6. Execution Flow in the JVM, End to End

1. The JVM starts `demo.host.HostApp` using the Application ClassLoader; `GreetingPlugin` is also defined from `build/api` on this classpath.
2. The host checks that the JAR exists and creates `URLClassLoader(pluginUrls, parent)`. **Creating the loader does not mean all classes in the JAR are loaded immediately**.
3. The host calls `pluginLoader.loadClass("demo.api.GreetingPlugin")`. The child loader delegates to its parent. The parent already has the interface, so the result is the exact `GreetingPlugin.class`: `Shared API: true`.
4. `ServiceLoader.load(...)` creates the service lookup object. When the `for` loop begins, `ServiceLoader` searches for the `META-INF/services/demo.api.GreetingPlugin` resource visible to `pluginLoader`.
5. The service file points to `demo.plugins.HelloPlugin`. The child loader asks the parent first; the parent does not find the implementation on the host classpath, so the child loader loads `HelloPlugin.class` from the plugin JAR.
6. When linking the implementation class with the interface, `demo.api.GreetingPlugin` is resolved through the same parent. Thus `HelloPlugin` is genuinely a `GreetingPlugin` that the host can invoke.
7. `ServiceLoader` instantiates the provider and returns the object via the interface; the host calls `id()` and `greet("Java")`. `plugin.getClass().getClassLoader() == pluginLoader` is `true`.
8. At the end of the `try` block, the loader is closed. Loading a class into the JVM, closing the JAR source, and unloading the class during GC are **three separate points in time**.

A common point of confusion: **parent delegation does not mean every class is loaded by the parent**. The child loader asks the parent to look first; when the parent does not have `HelloPlugin`, the child loader can still define it from the JAR.

## 7. Class Identity: A Fully Qualified Name Is Not Enough

In the JVM, reference type identity is determined by **the binary name of the class/interface together with the ClassLoader that defined it**. For example, two classes both named `demo.api.GreetingPlugin` but *defined by two independent loaders* are two distinct types. Common errors are `ClassCastException` or `ServiceConfigurationError: ... not a subtype` when one side tries to use a provider from the other.

The current example avoids conflicts because:

- There is only **one copy of the API used at runtime**: `GreetingPlugin.class` belongs to the Application ClassLoader.
- The plugin loader uses this API through its parent.
- The plugin JAR contains the implementation and metadata; the host can interact with the plugin through the shared interface.

Do not conclude that **merely copying the API into two JARs immediately creates two different types**. With `URLClassLoader`'s default parent delegation, even if the child JAR accidentally contains the API, the parent is still usually asked first. The problem arises when **two loaders actually define the API themselves** (for example, two independent classloaders, or a special child-first strategy). Types like `String` or types in `java.*` are still managed by the platform's loader mechanism in their own way.

A useful check is to compare **`Class<?>` with `==`**, just like `Shared API` in the program; checking `getName()` alone is not enough.

## 8. Extending the Example in a Controlled Way

**Adding a second plugin.** Create `ByePlugin implements GreetingPlugin`, place its class in the same plugin JAR, and add the fully qualified name `demo.plugins.ByePlugin` on another line of `META-INF/services/demo.api.GreetingPlugin`. If both providers can be instantiated and conform to the interface, the loop will iterate over both providers. The order depends on the declaration/discovery order of the providers; business logic should not infer priority from an arbitrary JAR order.

**Updating the plugin version.** Compile a new JAR, create a **new ClassLoader** pointing to the new JAR, and look up the provider from the new loader. Existing objects and classes do not automatically turn into the new version. To give the old loader a chance to be garbage-collected, the host must drop references to old objects/classes/loaders; at the same time, the plugin must stop threads, unregister listeners, close resources, and clear any `ThreadLocal` or caches that might hold those references. Calling `close()` alone does not guarantee class unloading.

**Plugins needing external dependencies.** If a library is not in the parent, add the dependency JARs to the plugin loader's `URL[]` (or package them properly with conflict control). Do not assume plugins can arbitrarily share any library version: parent-first may pick the host's version, whereas separate loaders may produce incompatible class versions.

**Resources and metadata.** A ClassLoader not only finds `.class` files but also serves resources via `getResource(s)`. `ServiceLoader` on the classpath uses `META-INF/services/...` configuration files to discover providers. Therefore, "the class is in the JAR" and "the service is discovered" are two different conditions.

**Thread Context ClassLoader (TCCL).** Some frameworks call the `ServiceLoader.load(GreetingPlugin.class)` overload that uses the thread's context classloader. In that situation, the provider might not be found if the context classloader is still the host's loader. This example explicitly passes `pluginLoader` to avoid an implicit dependency on TCCL. When integrating real libraries that require temporarily setting the context classloader, always restore the previous value in a `finally` block and understand the impact on code running on the same thread.

## 9. Common Errors and How to Verify

| Symptom | Common Cause | How to Check / Fix |
|---|---|---|
| `Providers: 0` | Missing `META-INF/services/...`, wrong FQCN, or JAR is not in the passed loader | `jar --list --file ...`; inspect the service descriptor contents; verify the loader's URLs |
| `ServiceConfigurationError` | Wrong provider name, class not public / cannot be instantiated, missing dependency, or provider does not match the interface | Check `cause` and stack trace, recompile against the same API; verify constructor and classpath |
| `NoClassDefFoundError` | Provider references a dependency class not visible from the plugin loader | Add the dependency to the loader's URLs or provide it via the parent by design |
| `ClassCastException` or "not a subtype" | Host/provider use two API `Class<?>` objects defined by different loaders | Print `Class.getClassLoader()`; compare `Class<?>` with `==`; share the API via the parent |
| `Implementation from child: false` | Plugin class was loaded by the parent first, usually because the plugin JAR is on the host classpath | Re-run with only `build/api;build/host` (Windows) or `build/api:build/host` (Bash) |
| Changed the JAR file but still seeing old behavior | Objects/classes still belong to the old loader; plugin was not reloaded with a new loader | Create a new loader/provider, swap business references in a controlled way, then clean up the old one |

**Two diagnostic notes:** `ClassNotFoundException` is a checked exception typically thrown from an explicit class lookup request; `NoClassDefFoundError` can appear when the JVM links/initializes a class and cannot find a dependency even though the original class itself was found. Also, `ServiceLoader` itself may wrap provider errors in a `ServiceConfigurationError`; always read the root stack trace rather than guessing solely from the provider count.

## 10. Safety Scope and Design Decisions

- A JAR loaded via `URLClassLoader` executes **real code in the same process and with the same OS permissions as the host**. ClassLoader is a JVM-level class name resolution and isolation mechanism, **not a security boundary** for untrusted code. Untrusted plugins should run in a separate process/container with appropriate access controls.
- The API should remain stable: changing the signature of `GreetingPlugin` can break binary compatibility for older plugins. You can add plugin version/compatibility metadata and validate it before activation.
- Lifecycle management should be the host's responsibility: load, initialize, activate, stop, close resources, and drop references. This minimal example only demonstrates **load → call → close**.
- The example uses **classpath/unnamed modules**. Plugin systems built with JPMS named modules have their own `module-info.java` and `ModuleLayer` rules; `URLClassLoader` cannot be assumed to cover all JPMS plugin requirements.

## 11. Post-Run Self-Check

1. Remove `META-INF/services/demo.api.GreetingPlugin` from the JAR, repackage, and run: the host still finds the API but discovers no providers; explain why `Providers: 0`.
2. Restore the service descriptor, keeping the host command without the plugin JAR on the main classpath: verify `Shared API: true` and `Implementation from child: true`. Explain the **two different results** using the parent delegation rule.
3. Change `HelloPlugin.greet()` to return a different string, recompile and repackage only the plugin, then re-run the host: the contract and host code remain unchanged. Identify which parts are reused and why the new JVM or new ClassLoader sees the new bytecode.

**Key takeaway:** The host and plugin communicate through **the same API defined by the parent**, the plugin implementation is loaded by the **child loader**, and `ServiceLoader` reads JAR metadata to instantiate providers; closing the loader and updating versions must be managed as the lifecycle of a dynamic component.
