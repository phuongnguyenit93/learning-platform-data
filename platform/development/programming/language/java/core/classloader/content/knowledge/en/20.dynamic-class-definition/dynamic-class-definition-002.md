# Dynamic Proxy and Interface Visibility in Java ClassLoader

## 1. The Problem: Why Does an Interface Exist Yet Fail to Create a Dynamic Proxy?

Java Dynamic Proxy is a mechanism for creating **a class that implements an interface at runtime**, without needing to precompile a fixed implementation. The core API is `java.lang.reflect.Proxy.newProxyInstance`:

~~~java
Object proxy = Proxy.newProxyInstance(
        chosenLoader,
        new Class<?>[] { SomeService.class },
        invocationHandler
);
~~~

In a simple program, choosing `SomeService.class.getClassLoader()` or a compatible loader usually works. However, in a plugin system, application server, JPMS layer, or hot reload, a `Class<?>` object of the interface may **not be visible by name** from the ClassLoader chosen to define the proxy. In that case, Java can throw **`IllegalArgumentException`** in the proxy creation call itself.

**Key concept:** It is not enough for the loader to “find an interface with the same name”. It must find **the exact same `Class<?>` object of the interface**.

Java 17 defines the condition to check for each interface `i` and loader `cl`:

~~~java
Class.forName(i.getName(), false, cl) == i
~~~

The `==` operator checks **runtime Class identity**, not string name equality. If the expression returns false, `i` is **not visible by name** through the loader requested for the proxy. If `Class.forName` throws `ClassNotFoundException`, the interface cannot even be found by that loader.

In many cases, the error arises because:

- Choosing the **bootstrap/platform loader** for an interface that only exists in the application loader.
- Choosing a **sibling loader** that cannot delegate to where the interface was defined.
- A child-first plugin loader defines its own copy of an **interface with the same binary name** as the host's version.
- **Types appearing in the public method signatures** of the interface are not visible through the proxy loader.
- A **non-public** interface resides in a different package/module, has a different defining loader, or is inaccessible under `Proxy` rules.
- A **sealed** (Java 17) or **hidden** interface is invalid for Dynamic Proxy to implement.
- A group of interfaces has methods with identical signatures but incompatible return types.

This article explains the Java 17 conditions, how to choose a loader, a runnable “not visible / sees a duplicate / sees the right one” experiment, limitations with JPMS, `InvocationHandler` handling, common errors, and how to design plugin boundaries.

## 2. What Flow Does Dynamic Proxy Follow?

A proxy object has two main parts:

1. A **runtime proxy class** generated by the JDK, which implements the specified interfaces and extends `java.lang.reflect.Proxy`.
2. An **InvocationHandler** containing the logic to handle calls through the interface methods.

~~~text
Consumer code
   |
   v
SomeService service = (SomeService) proxy;
   |
   v
service.request("x")
   |
   v
Generated proxy class
   |
   v
InvocationHandler.invoke(proxy, Method request, ["x"])
   |
   v
Handler logic -> return value / throw exception
   |
   v
Consumer receives result
~~~

When a proxy is created properly, `proxy instanceof SomeService` is true; casting `(SomeService) proxy` succeeds. When invoking a method through the proxy, the JDK passes three pieces of information to the handler:

- `proxy`: the proxy instance itself.
- `method`: a `java.lang.reflect.Method` describing the invoked interface method; it may belong to an inherited superinterface.
- `args`: the argument array; if the method has no parameters, it may be **`null`**, and must not be assumed to be an empty array.

The handler returns an `Object`. The proxy must convert the return value to match the declared return type: primitives require the matching wrapper type to unbox, and reference types must be assignable; a type mismatch may throw `ClassCastException` or `NullPointerException`.

Dynamic Proxy **does not automatically execute the body of a concrete implementation**. If the handler wants to forward to a target object, the handler must explicitly invoke the target; if it wants to compute a value, it computes it itself. For **default methods** of an interface, `InvocationHandler.invokeDefault` (Java 16+) is the option when you want to invoke the actual default implementation.

## 3. Interface Visibility Is Identity, Not Name

According to the JVM specification, a class/interface is identified by **(binary name, defining ClassLoader)**. Two loaders can define two separate interfaces named `api.Greeter`:

~~~text
Host application loader:
    api.Greeter  -> Class H

Plugin child-first loader:
    api.Greeter  -> Class P

H.getName().equals(P.getName()) == true
H == P                              == false
~~~

If the host passes `H` to `Proxy.newProxyInstance(pluginLoader, new Class<?>[]{H}, h)`, but `pluginLoader.loadClass("api.Greeter")` returns `P`, the proxy **is not created**. That loader sees **P**, not **H**, by binary name.

Two variants to distinguish:

| Symptom | Result when querying the interface via the proxy loader |
| --- | --- |
| Loader cannot find the interface | `ClassNotFoundException` when attempting `Class.forName` |
| Loader finds an interface with the same name but a separate copy | `Class.forName(..., loader) != expectedInterface` |
| Loader properly delegates to parent and receives the same Class | `Class.forName(..., loader) == expectedInterface` |

The second case is very dangerous when looking only at logs: the interface name is completely right, yet the identity is wrong. This is also the source of `ClassCastException` “`api.Greeter cannot be cast to api.Greeter`” and provider **not a subtype** errors in other plugin architectures.

**The proxy condition does not require all interfaces to be defined by the passed-in loader itself.** A child loader **can delegate** shared interfaces to its parent and still create a valid proxy, as long as the lookup result is the exact same runtime Class.

## 4. API Signature and the Meaning of Each Parameter

Java 17 signature:

~~~java
public static Object newProxyInstance(
        ClassLoader loader,
        Class<?>[] interfaces,
        InvocationHandler h
)
~~~

- `loader`: the loader used by the JDK to **define the proxy class** and check visibility.
- `interfaces`: the set of **Class objects representing interfaces** that the proxy class will implement, in the specified order.
- `h`: the InvocationHandler invoked when an interface method is executed.

Recommended usage:

~~~java
Greeter proxy = (Greeter) Proxy.newProxyInstance(
        Greeter.class.getClassLoader(),
        new Class<?>[] { Greeter.class },
        (p, method, arguments) -> "Hello"
);
~~~

This is an **illustrative snippet** assuming `Greeter` has the corresponding method signature, not a standalone runnable file. To run reliably and get accurate results, see the complete program in section 7.

### 4.1. Can You Pass a Null Loader?

`loader == null` means using the bootstrap class loader under circumstances permitted by the API. It is **not** a symbol for “auto choose suitable loader”. For an application interface defined by the application loader, the bootstrap loader normally **cannot see that interface**, so passing null does not solve the problem.

### 4.2. The Interface Array Needs Real Class<?> Objects

`interfaces` does not accept string names; it takes the actual `Class<?>` objects of the interfaces. If you need to load by name from a plugin, you must explicitly verify the provenance and identity of each Class. Do not turn a list of names from external input into arbitrary interfaces and then expect the proxy to act as a security boundary.

### 4.3. Why Doesn't the Handler Determine Visibility?

`InvocationHandler` is passed **after** selecting the loader and interface Class objects. The handler can be a host lambda, but that does not allow a proxy Class lacking access or visibility to the interface to simply be generated. The visibility check happens during proxy generation, before the handler is called.

## 5. Constraints in Proxy.newProxyInstance on Java 17

For a proxy class to be validly created, Java 17 requires multiple conditions, not just visibility:

| Condition | Reason |
| --- | --- |
| Every element of `interfaces` is an interface | Proxy creates an implementation of interfaces; it does not extend an arbitrary class |
| Interface is not `hidden` | Hidden classes do not support lookup by name as required |
| Interface is not `sealed` | A dynamic proxy is not a static permitted implementation in a sealed hierarchy |
| No repeated `Class<?>` in the array | The interfaces list must have no duplicates |
| Every interface is visible by name through the loader | `Class.forName(i.getName(), false, loader) == i` |
| Every type in the **public method signatures** of the interfaces is also visible by name | The proxy class must validly declare method descriptors |
| All **non-public interfaces** must be in the same package and module, and defined by the specified loader | Ensures a single proxy class can access all the interfaces |
| Identical method signatures must have compatible return types | Proxy generates only one implementation for a signature |
| Does not exceed VM class/interface limits | Class files/the VM have structural limits |

Violating these restrictions typically causes `newProxyInstance` to throw **`IllegalArgumentException`**. A null array, null element, or null handler can cause `NullPointerException`; some legacy runtime policies may report `SecurityException`, depending on the JVM and security manager configuration.

**The visibility case whose exact logic to remember:**

~~~java
boolean visible =
        Class.forName(iface.getName(), false, chosenLoader) == iface;
~~~

In real code, the statement requires `throws ClassNotFoundException` or a `try/catch`. If `visible` is false even though the names match, change the loader or fix how the shared API is loaded; do not “fix” it by comparing Strings.

## 6. Which ClassLoader Should You Choose When Creating a Proxy?

### 6.1. A Public Interface on the Application Classpath

Common approach:

~~~java
ClassLoader loader = ServiceApi.class.getClassLoader();
Object proxy = Proxy.newProxyInstance(
        loader, new Class<?>[] { ServiceApi.class }, handler);
~~~

**Illustrative code**, assuming `ServiceApi` and `handler` are valid. Choosing the API's defining loader is advantageous because that loader must be able to see the interface itself, though you still need to consider **signature types** and any additional interfaces when creating a multi-interface proxy.

### 6.2. Multiple Interfaces from Multiple Loaders

If a proxy must implement both `ApiA.class` and `ApiB.class`, the loader needs to see **both runtime Classes** by name, including the types used in public method signatures. A child loader that has a common parent and knows about both interfaces may be suitable; there is no “take the first interface's loader” formula that always works.

Diagram:

~~~text
         Common parent loader
        /                    \
  Interface A               Interface B
        \                    /
         \                  /
         chosen proxy loader
             sees A and B?
                 |
            yes -> proxy
            no  -> IllegalArgumentException
~~~

If A and B reside in **sibling loaders** without proper delegation, you need a shared loader architecture or another adapter/boundary. You cannot force two Classes with the same name and different loaders to become one.

### 6.3. Host API and Plugin Implementation

Common design:

~~~text
      Host/CommonLoader
         shared.Api
         shared.Dto
             ^
             | parent delegation
             |
         PluginLoader
       plugin.Implementation
       plugin.PrivateDependency
~~~

If the host needs to cast the proxy to `shared.Api`, ensure that `shared.Api` is **a single shared runtime Class**, typically defined by a common parent. The plugin loader can look up its own implementation/private dependencies; Dynamic Proxy is not a reason to copy the service interface into each plugin.

### 6.4. Thread Context ClassLoader

`Thread.currentThread().getContextClassLoader()` (TCCL) is useful for discovery frameworks, but it is **not always the right choice** for `Proxy.newProxyInstance`. The TCCL might be a plugin loader using child-first loading for a different copy of the API, or a loader that cannot see the host's API.

Do not default to:

~~~java
Proxy.newProxyInstance(
        Thread.currentThread().getContextClassLoader(),
        new Class<?>[] { HostApi.class },
        handler
);
~~~

If the TCCL cannot see **the exact HostApi Class**, the call fails. Use an explicit visibility check and choose the loader based on ownership of the contract.

## 7. Complete Java 17+ Experiment: Not Visible, Sees a Duplicate, Sees the Right One

The experiment uses:

- A public `api.Greeter` interface on the **host classpath**.
- A bytecode copy of the **same interface** in a separate directory `shadow-classes`.
- An isolated `URLClassLoader` that cannot see the host API.
- A custom `URLClassLoader` that is child-first for the exact name `api.Greeter` to create a **runtime duplicate**.
- A proxy created from the host API's loader, sharing the right Class.

### 7.1. Directory Tree

~~~text
proxy-visibility-demo/
├── src-api/
│   └── api/
│       └── Greeter.java
└── src-host/
    └── ProxyVisibilityDemo.java
~~~

After compilation:

~~~text
host-classes/
├── ProxyVisibilityDemo.class
├── ProxyVisibilityDemo$ShadowLoader.class
└── api/
    └── Greeter.class

shadow-classes/
└── api/
    └── Greeter.class
~~~

**Do not put `shadow-classes` on the host's `java -cp`**, so that the parent application class loader only knows about the host API copy. `ShadowLoader` receives that path as a separate `URLClassLoader` root.

### 7.2. File src-api/api/Greeter.java

~~~java
package api;

public interface Greeter {
    String greet(String name);
}
~~~

The interface is public, non-sealed, and only references Java core `String` in its method signature. Therefore, the example focuses on the visibility of **the interface itself**, without being affected by another hard-to-find DTO.

### 7.3. File src-host/ProxyVisibilityDemo.java

~~~java
import api.Greeter;

import java.net.URL;
import java.net.URLClassLoader;
import java.nio.file.Path;
import java.lang.reflect.InvocationHandler;
import java.lang.reflect.Proxy;

public class ProxyVisibilityDemo {
    static final class ShadowLoader extends URLClassLoader {
        ShadowLoader(Path classes) throws Exception {
            super(
                    new URL[] { classes.toAbsolutePath().toUri().toURL() },
                    ProxyVisibilityDemo.class.getClassLoader()
            );
        }

        @Override
        protected Class<?> loadClass(String name, boolean resolve)
                throws ClassNotFoundException {
            if (!name.equals("api.Greeter")) {
                return super.loadClass(name, resolve);
            }

            synchronized (getClassLoadingLock(name)) {
                Class<?> found = findLoadedClass(name);
                if (found == null) {
                    found = findClass(name);
                }
                if (resolve) {
                    resolveClass(found);
                }
                return found;
            }
        }
    }

    static boolean visible(ClassLoader loader, Class<?> type) {
        try {
            return Class.forName(type.getName(), false, loader) == type;
        } catch (ClassNotFoundException e) {
            return false;
        }
    }

    static InvocationHandler handler() {
        return (proxy, method, args) -> {
            if (method.getName().equals("greet")) {
                return "Hello, " + args[0];
            }
            throw new UnsupportedOperationException(method.getName());
        };
    }

    public static void main(String[] args) throws Exception {
        if (args.length != 1) {
            throw new IllegalArgumentException(
                    "Usage: ProxyVisibilityDemo <shadow-classes-dir>");
        }

        ClassLoader hostLoader = Greeter.class.getClassLoader();

        try (URLClassLoader isolated = new URLClassLoader(
                        new URL[0],
                        ClassLoader.getPlatformClassLoader());
             ShadowLoader shadow = new ShadowLoader(Path.of(args[0]))) {

            System.out.println("isolated sees host interface: "
                    + visible(isolated, Greeter.class));

            try {
                Proxy.newProxyInstance(
                        isolated,
                        new Class<?>[] { Greeter.class },
                        handler());
                System.out.println("isolated rejected: false");
            } catch (IllegalArgumentException expected) {
                System.out.println("isolated rejected: true");
            }

            Class<?> foreign = shadow.loadClass("api.Greeter");
            System.out.println("shadow same name: "
                    + foreign.getName().equals(Greeter.class.getName()));
            System.out.println("shadow same Class: "
                    + (foreign == Greeter.class));
            System.out.println("shadow sees host interface: "
                    + visible(shadow, Greeter.class));

            try {
                Proxy.newProxyInstance(
                        shadow,
                        new Class<?>[] { Greeter.class },
                        handler());
                System.out.println("shadow host proxy rejected: false");
            } catch (IllegalArgumentException expected) {
                System.out.println("shadow host proxy rejected: true");
            }

            Object foreignProxy = Proxy.newProxyInstance(
                    shadow,
                    new Class<?>[] { foreign },
                    handler());

            System.out.println("foreign proxy is host Greeter: "
                    + (foreignProxy instanceof Greeter));
            System.out.println("foreign proxy call: "
                    + foreign.getMethod("greet", String.class)
                             .invoke(foreignProxy, "Ada"));

            Greeter good = (Greeter) Proxy.newProxyInstance(
                    hostLoader,
                    new Class<?>[] { Greeter.class },
                    handler());

            System.out.println("shared proxy is host Greeter: "
                    + (good instanceof Greeter));
            System.out.println("shared proxy call: "
                    + good.greet("Ada"));
        }
    }
}
~~~

### 7.4. Compiling and Running

From the `proxy-visibility-demo` directory with JDK 17+:

~~~bash
javac --release 17 -d host-classes src-api/api/Greeter.java src-host/ProxyVisibilityDemo.java
javac --release 17 -d shadow-classes src-api/api/Greeter.java
java -cp host-classes ProxyVisibilityDemo shadow-classes
~~~

These three commands share the same basic syntax across PowerShell, CMD, bash, and zsh because no separator is needed to list multiple classpath entries.

**Exact expected stdout** for the code and directory structure above:

~~~text
isolated sees host interface: false
isolated rejected: true
shadow same name: true
shadow same Class: false
shadow sees host interface: false
shadow host proxy rejected: true
foreign proxy is host Greeter: false
foreign proxy call: Hello, Ada
shared proxy is host Greeter: true
shared proxy call: Hello, Ada
~~~

### 7.5. Explanation of Each Case

**Loader cannot see the interface:**

- `isolated` has the platform loader as its parent, **not the application loader** that contains `api.Greeter`.
- Its URL list is empty, so `Class.forName("api.Greeter", false, isolated)` cannot find the host API.
- The call `newProxyInstance(isolated, [Greeter.class], handler)` is rejected with `IllegalArgumentException`.

**Loader sees its own copy with the same name:**

- `shadow` extends `URLClassLoader` but overrides `loadClass` **only for `api.Greeter`** to be child-first, loading bytes from `shadow-classes`.
- The Class defined by shadow itself differs from the host's `Greeter.class`, even though both have `getName() == "api.Greeter"`.
- Passing **host Greeter.class** with `shadow` fails the visibility condition because shadow will find the duplicate Class.
- Passing the **foreign Class** to shadow is valid, however: shadow sees its own Class, so the proxy is created.
- However, the foreign proxy implements the foreign `api.Greeter`, not the host `api.Greeter`. Therefore, `instanceof Greeter` is false. Reflection via the foreign interface can still invoke `greet("Ada")`.

**Choosing the right shared/host loader:**

- `hostLoader` sees the exact `Greeter.class`.
- The proxy is defined to implement the host's interface Class, casting to `Greeter` succeeds, and calling the method returns the expected string.

**Experimental conclusion:** Being able to create a proxy in the plugin loader does not mean the host can cast it to an interface of the same name. You must unify the **contract Class identity** at the exchange boundary.

## 8. Choosing the Right Interface Class When a Plugin Has a Duplicate API

There are two distinct decisions:

1. **Whose interface do I want the proxy to implement?** If the host will use the proxy via `HostApi`, the interface array **must contain the host's `HostApi.class`**.
2. **Which loader can see that exact Class?** Choose a loader for which `Class.forName(HostApi.class.getName(), false, loader) == HostApi.class`, and which can also see the signature types and the other interfaces.

If you only switch the interface array to the `PluginApi` version to make `newProxyInstance` stop throwing errors, you may create a proxy that **works inside the plugin** but **cannot be used through the host contract**. The proper fix is usually to place the API types in a **parent/common loader**, forcing the plugin to delegate `shared.api.*` back to it.

An adapter can convert data between two incompatible contracts when the loader cannot be unified, but you should not force a cast to the wrong runtime Class.

## 9. Checking Types in Public Method Signatures

Java 17 also requires **the referenced types appearing in all public method signatures** of the proxy interfaces and inherited superinterfaces to be visible by name through the chosen loader.

Example interface:

~~~java
package api;

public interface Processor {
    api.dto.Result process(api.dto.Request input);
}
~~~

This is **illustrative code**, assuming `api.dto.Request` and `api.dto.Result` already exist. Even if `Processor.class` is visible through the loader, the proxy still might not be defined if the loader cannot see the exact runtime Classes corresponding to `Request` and `Result`.

This can happen when:

- The host API interface resides in the parent loader, but a DTO from the same contract is accidentally defined separately by the child loader.
- A public interface method uses exception/return/parameter types residing in another module/plugin loader that is not properly visible to the chosen proxy loader.
- An inherited superinterface introduces a referenced type that the author overlooked by only checking directly declared methods.

**Do not check only the visibility of the surface interface.** You need to design the entire **API surface** consistently: parameter types, return types, related interfaces, and public method signatures. Private implementation types that are not exposed in the signatures can remain isolated.

A basic illustrative checker:

~~~java
static boolean visibleByName(ClassLoader loader, Class<?> type) {
    try {
        return Class.forName(type.getName(), false, loader) == type;
    } catch (ClassNotFoundException e) {
        return false;
    }
}
~~~

This is an **illustrative snippet**, not a general test covering every type, because array/primitive types and method signature traversal have their own subtleties. When building a framework, you must handle `void`, primitives, array component types, and all inherited methods according to the rules.

## 10. Non-Public Interfaces: Same Package/Module and Defining Loader

An interface with only package-private access, for example:

~~~java
package internal;

interface HiddenContract {
    String value();
}
~~~

is not like a `public` interface. Dynamic Proxy can still implement non-public interfaces under appropriate conditions, but Java 17 requires that for **all non-public proxy interfaces**:

- They are in the **same package and same module**.
- They are **defined by the loader specified for the proxy**.
- The module containing the non-public interfaces can access all requested interface types.

A proxy class with a non-public interface is typically non-public and placed in the package/module of those non-public interfaces. Therefore, merely asking “does the loader see the interface” is **not enough** to prove the combination of interfaces is valid.

This is why you cannot arbitrarily mix:

~~~text
package a; interface A { ... }  // non-public
package b; interface B { ... }  // non-public
~~~

into a single proxy implementing both if they are in different packages/modules. The expected error is `IllegalArgumentException` in the proxy creation call.

If a plugin API needs to be shared with code outside the package/module, consider a **public interface located in an appropriately exported package**, instead of using a package-private interface as a cross-loader contract. Do not try to work around this with `setAccessible(true)`; JPMS and Dynamic Proxy have their own structural constraints.

## 11. JPMS: Which Module Is the Proxy Class Placed In?

Since Java 9+, Dynamic Proxy must also comply with the Java Platform Module System (**JPMS**). The name/package/module of the proxy class **must not be assumed to be fixed**. Java 17 selects where to generate the proxy so that its accessibility is compatible with the proxy interfaces.

Common branches in the Javadoc:

| Proxy interfaces | Where is the proxy class placed? |
| --- | --- |
| All public, belonging to appropriately exported/opened packages | Public proxy in an unconditionally exported but non-open package; package/module name is not guaranteed |
| Contains non-public interfaces | Non-public proxy in the package/module of the non-public interfaces, provided they share the same package/module and loader |
| Includes a public interface in a package that is not exported and not broadly opened | The proxy may be a public class in a **dynamic module**, in a package that is not exported and not opened |
| Mixed accessibilities | The lowest accessibility of the interfaces governs the accessibility of the proxy class |

A **dynamic module** here is a named module created by the proxy mechanism at runtime, not a module name you declare yourself in `module-info.java`. A proxy in a dynamic module may be hidden by encapsulation from constructor reflection outside the module.

For example:

~~~java
Object p = Proxy.newProxyInstance(loader, interfaces, handler);
~~~

is recommended over the pattern of generating a proxy class and then manually invoking its constructor via reflection. The `Proxy.getProxyClass` API is **deprecated** in Java 17, because proxy classes belonging to named/dynamic modules may not allow callers outside the module to invoke their constructor via reflection. `Proxy.newProxyInstance` handles the required contract conditions.

### Module Exports/Opens and Interface Visibility Differ

- **Visible by name** asks whether the loader resolves to the **exact Class object**.
- **Readability/exports/opens** asks which code/modules have permission to access types/packages at runtime.
- The two conditions are related but **not equivalent**. A loader can see a Class by name while a module/caller still does not have permission to access it directly.
- You should not randomly use `--add-opens`/`--add-exports` to fix duplication errors caused by a class loader. If the Class identities differ, changing access flags will not merge the two Classes.

## 12. Dynamic Proxy Does Not Support Sealed/Hidden Interfaces in Java 17

Java 17 has sealed types, for example:

~~~java
public sealed interface Operation permits FixedOperation {
    int run();
}

final class FixedOperation implements Operation {
    @Override
    public int run() {
        return 1;
    }
}
~~~

**Illustrative code**, not a runnable file with a main method. `Operation` is a sealed interface; a Dynamic Proxy class is not listed in the compiler-declared permits clause, so Java 17 `Proxy.newProxyInstance` **rejects** this kind of interface under the **non-sealed interface** restriction. This is not an error caused by loader visibility.

Similarly, a **hidden interface** does not satisfy the visible-by-name interface requirement. Do not try to use `Lookup.defineHiddenClass` and force the proxy generator to implement a hidden interface; the Java 17 API requires non-hidden interfaces.

An arbitrary class also cannot be supplied in the `interfaces` array; every element must be an **interface type**. For a regular marker interface or an interface with default methods, a proxy can be created if the other conditions are met.

## 13. Multiple Interfaces with Overlapping Methods

Dynamic Proxy can implement more than one interface:

~~~java
interface A {
    Number get();
}

interface B {
    Integer get();
}
~~~

**Illustrative snippet**. The two methods have the same name and parameters, but covariant return types: `Integer` is assignable to `Number`. Java can create a proxy if the loader/access conditions are satisfied.

Conversely:

~~~java
interface Left {
    String value();
}

interface Right {
    Integer value();
}
~~~

**Illustrative snippet**. The two return types are incompatible, so a single proxy cannot implement both with the same method signature and satisfy the rules; `newProxyInstance` may throw `IllegalArgumentException`.

When both A and B declare the same method name/parameter signature:

- **The order of interfaces** in the array matters. The Method object passed to the handler may belong to the **earlier interface** in the array containing that method, even if the caller invokes it through a reference of another interface type.
- If the method is `Object`'s `equals`, `hashCode`, or `toString`, the handler receives a Method whose declaring class is `java.lang.Object`.
- Checked exceptions thrown from the handler must be compatible with the **throws clauses** of the overlapping method signatures. Otherwise, the proxy may wrap them in `UndeclaredThrowableException`.

Do not use `method.getDeclaringClass()` as the sole check to know which interface reference the caller invoked through; for overlapping methods, the Javadoc explicitly states it is insufficient.

## 14. Handler: Default Methods, Object Methods, and Exceptions

### 14.1. Object Methods Also Pass Through the Handler

The proxy forwards calls to public `equals`, `hashCode`, and `toString` methods from `Object` to the InvocationHandler. If the handler only handles one business method and throws `UnsupportedOperationException` for everything else, framework/logging code calling `proxy.toString()` can fail.

A handler clear enough to illustrate this:

~~~java
InvocationHandler h = (proxy, method, args) -> {
    switch (method.getName()) {
        case "toString":
            return "GreeterProxy";
        case "hashCode":
            return System.identityHashCode(proxy);
        case "equals":
            return proxy == args[0];
        case "greet":
            return "Hello, " + args[0];
        default:
            throw new UnsupportedOperationException(method.toString());
    }
};
~~~

**Illustrative code snippet** requiring appropriate variables and interface. Inside the handler, do not call `proxy.toString()` to implement `toString`, because it will dispatch back into the same handler and cause recursion. For `equals`, decide on clear semantics instead of blindly delegating to a target without the same identity.

### 14.2. Invoking a Default Method

Java 17 supports:

~~~java
if (method.isDefault()) {
    return InvocationHandler.invokeDefault(
            proxy, method, args == null ? new Object[0] : args);
}
~~~

This is an **illustrative snippet** used inside InvocationHandler. `InvocationHandler.invokeDefault` (Java 16+) executes the default implementation according to the proxy interface rules; use it only when `method` is genuinely a permitted default method. If the handler returns a result itself, the default method does not run automatically.

### 14.3. Undeclared Checked Exceptions

If the handler throws a checked exception not permitted by the interface method's `throws` clause, the call through the proxy may throw `UndeclaredThrowableException`. That is a `RuntimeException` wrapper, not evidence that the proxy loader saw the wrong interface.

Errors by layer:

| Stage | Typical Error |
| --- | --- |
| Creating proxy; interface not visible/invalid | `IllegalArgumentException` |
| Creating proxy; null interface array, element, or handler | `NullPointerException` |
| Casting proxy to a different runtime interface Class | `ClassCastException` |
| Handler returns null for a primitive | `NullPointerException` when unboxing |
| Handler returns a value incompatible with declared return | `ClassCastException` |
| Handler throws a checked exception outside `throws` | `UndeclaredThrowableException` |
| JPMS reflection on encapsulated proxy constructor | `IllegalAccessException` / corresponding access error |
| Class initialization/linkage/dependency failure | `LinkageError` or context-appropriate error |

**Do not lump every error in an application using Dynamic Proxy into a ClassLoader error.** Separate errors during proxy generation, during handler dispatch, and when the caller casts/consumes the result.

## 15. Designing Proxies in a Plugin System

A typical architecture:

~~~text
                         Host process
             +--------------------------------+
             | Shared API (loader H)          |
             | api.Service                    |
             | api.Request / api.Response     |
             +----------------+---------------+
                              ^
                 parent delegation
                              |
          +-------------------+------------------+
          |                                      |
       Plugin A                                 Plugin B
       loader A                                 loader B
       impl.*                                   impl.*
       private.lib.*                            private.lib.*
          |                                      |
      handler A                              handler B
          |                                      |
          +-------- proxy as api.Service --------+
                              |
                           Host caller
~~~

Principles:

1. **Place the service API in a common parent loader/module** where both the host and plugins see the same runtime Class.
2. **Do not package a copy of the API that gets re-defined child-first** just so the plugin compiles. You can put the API dependency on the compile classpath without bundling a duplicate into the packaged plugin, depending on your Maven/Gradle setup.
3. **DTOs, callbacks, and exception types** in public method signatures are also part of the shared contract; not just the main interface.
4. **Use the host's interface array** if the proxy needs to be returned to the host. Do not use a Class of the same name defined by the plugin itself.
5. **Choose a proxy loader that sees all interfaces** and signature types; do not default to using the TCCL.
6. **Separate implementation logic from API identity.** The InvocationHandler can invoke the plugin's private target; results/exceptions must be converted to a valid shared contract.
7. **Do not rely on a proxy to sandbox plugin code.** A JDK proxy only dispatches method invocations; the handler/target code still has the permissions of its corresponding process/container.
8. **Manage lifecycle/hot reload.** Caches of proxy Classes and references from the InvocationHandler can keep old plugin ClassLoaders alive longer than expected. When reloading, intentionally release references and create a new loader/target.

If using `ServiceLoader` to discover implementations and wrap them in a proxy, the ServiceLoader provider must also implement the exact shared service Class. A proxy is not a way to bypass the “provider not a subtype” error.

## 16. Example of Checking Before Creating a Proxy

This is a **sample helper** (not a general validator covering every condition):

~~~java
static void requireVisible(
        ClassLoader chosen, Class<?> iface)
        throws ClassNotFoundException {
    if (!iface.isInterface()) {
        throw new IllegalArgumentException(
                "Not an interface: " + iface.getName());
    }
    Class<?> fromChosen = Class.forName(
            iface.getName(), false, chosen);
    if (fromChosen != iface) {
        throw new IllegalArgumentException(
                "Same binary name, different runtime Class: "
                + iface.getName());
    }
}
~~~

**Strength:** the helper provides a clearer message about matching names with different loaders, which is useful for logging.

**Limitation:** the helper does not check duplicate interfaces in the array, sealed/hidden restrictions, non-public rules, module access, return-type compatibility, or types referenced in public signatures. For a production framework, you should let `Proxy.newProxyInstance` perform the full checks and use the helper only for diagnostics.

Using `Class.forName(name, false, chosen)` **does not require running the static initializer** of the interface just for the visibility check, avoiding unnecessary side effects during preflight.

## 17. Diagnosing an IllegalArgumentException When Creating a Proxy

Systematic approach:

1. **Get the exact loader passed to `newProxyInstance`.** Do not look only at `Thread.currentThread().getContextClassLoader()` if the code passed a different loader.
2. **Inspect the actual `Class<?>` objects in the interface array.** For each element: `isInterface()`, `getName()`, `getClassLoader()`, `getModule()`.
3. **Test the visibility predicate**: `Class.forName(iface.getName(), false, chosenLoader) == iface` and record clearly whether it throws `ClassNotFoundException` or finds the same name with a different Class.
4. **Inspect the loader hierarchy**: parent-first, package-based child-first, sibling loader, or layer-specific loader.
5. **Check for duplicate API JARs** in the plugin classpath/fat JAR, application server, or hot reload build.
6. **Check public method signatures** and inherited interfaces for any DTO/exception/parameter/return type that the proxy loader cannot see.
7. **Check non-public interfaces**: same package, module, and loader per JDK rules?
8. **Check sealed/hidden interfaces**, duplicate Class objects, and conflicting return signatures.
9. **For JPMS**, inspect module membership and package exports/opens; do not equate an access issue with type identity.
10. **After fixing**, test proxy creation, casting to the host interface, and invoking methods; successful creation alone does not guarantee that casting across the boundary works properly.

A logging helper:

~~~java
static void describe(Class<?> c) {
    System.out.println("name=" + c.getName());
    System.out.println("loader=" + c.getClassLoader());
    System.out.println("module=" + c.getModule());
}
~~~

This is an **illustrative code snippet**, without a main method. When seeing two types with the same binary name but different loaders, also print `(a == b)`; string names do not establish identity.

You can enable class loading logging in OpenJDK/HotSpot:

~~~bash
java -Xlog:class+load=info -cp host-classes ProxyVisibilityDemo shadow-classes
~~~

JVM logs do not have fixed stdout formatting and vary by JDK. If you need to inspect the generated proxy class, some JVMs provide diagnostic settings, but **do not rely on the `$Proxy0` name or generated package** as a long-term contract.

## 18. Common Mistakes

| Mistake | Correct Understanding |
| --- | --- |
| “If the interface names match, a proxy can be created” | The loader must see the **exact runtime Class** |
| “I already have the Class<?>, so any loader can create the proxy” | The passed loader must be able to look up the interface by name with the right identity |
| “Using the bootstrap loader is auto” | The bootstrap loader usually cannot see application interfaces |
| “A child loader different from the parent definitely cannot see the parent's API” | Delegation can return the right API Class |
| “A plugin loader that defines its own API copy still works with HostApi” | The proxy may work inside the plugin, but the host cast fails |
| “Only the main interface needs to be visible” | Public method signature types and inherited interfaces must also be visible |
| “Dynamic Proxy can implement a concrete class” | JDK Dynamic Proxy implements interfaces; it does not extend an arbitrary class |
| “Sealed interfaces can be proxied freely” | Java 17 requires non-sealed interfaces |
| “Non-public interfaces from any package can be combined into one proxy” | Must satisfy same-package/module/loader conditions |
| “The `$ProxyN` name/package is fixed” | Proxy class names and dynamic modules are not guaranteed to be fixed |
| “`getProxyClass` is the preferred way to create instances” | In Java 17 this API is deprecated; use `newProxyInstance` |
| “InvocationHandler automatically calls default methods” | The handler must dispatch them, optionally using `InvocationHandler.invokeDefault` |
| “`equals`/`hashCode`/`toString` do not go through the handler” | Calls to these Object methods are also dispatched |
| “Any checked exception from the handler is thrown directly to the caller” | A checked exception not in `throws` may be wrapped |
| “The TCCL is always right” | The TCCL might not see the host Class or might see a duplicate |
| “A proxy can fix SPI type duplication” | The API/shared contract still requires a single runtime Class |
| “Use ClassCastException to diagnose proxy constructor errors” | Proxy construction errors are usually IllegalArgumentException; a cast mismatch happens afterward |

## 19. Exercises and Self-Check Questions

**1. Why does the JDK check `Class.forName(i.getName(), false, loader) == i` instead of `getName().equals`?**  
Because the same binary name can be defined by different defining loaders into distinct runtime types.

**2. A child loader properly delegates the shared API to its parent. Can it create a proxy for the parent API?**  
Yes, if all interfaces/signature types are visible with the exact identity and the other restrictions are also satisfied.

**3. The loader cannot find the interface Class. What is the typical error from `newProxyInstance`?**  
`IllegalArgumentException` for an interface visibility violation, not necessarily a `ClassNotFoundException` propagating out.

**4. The loader finds an interface with the same name but a different Class. Is fixing it by passing that interface copy into the array enough for the host to use the proxy?**  
No; the proxy will implement the plugin's interface, and the host may fail to cast it. You need to share the exact contract Class.

**5. What if `Greeter.class` is visible, but a method has a `Request` parameter from a different loader?**  
Proxy creation may still fail because public method signature types must also be visible.

**6. Can two non-public interfaces belonging to two different packages share a single proxy?**  
No, under Java 17 constraints for non-public proxy interfaces.

**7. Why is a sealed interface invalid as a proxy interface in Java 17?**  
Because a dynamic proxy class is not among the static permitted implementations and the `Proxy` API requires non-sealed interfaces.

**8. How does `InvocationHandler.invoke` receive args when a method has no parameters?**  
`args` may be `null`.

**9. What happens if the handler returns null for a method returning `int`?**  
The proxy call may throw `NullPointerException` when unboxing.

**10. What happens if the handler throws a checked exception that is not in `throws`?**  
It may be wrapped in `UndeclaredThrowableException`.

**11. Can you rely on the name `$Proxy0` to determine the right module?**  
No. The name/package/module of the proxy class is not a stable interface for business logic to depend on.

**12. What needs to be tested after fixing the loader?**  
Successful proxy creation, casting to the host API, method handling, return values/exceptions, and compatibility of types in the signatures.
