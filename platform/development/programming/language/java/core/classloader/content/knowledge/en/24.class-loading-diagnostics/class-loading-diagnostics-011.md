# Reconciling the Actual Runtime Classpath with the Build Tool Dependency Tree

## 1. Problem to Solve

A Java project compiling successfully with Maven or Gradle **does not guarantee that the JVM at runtime uses the exact set of JARs/classes visible in the build tool's dependency tree**. When the application is launched via an IDE, test runner, application server, executable JAR, Docker image, plugin host, or custom ClassLoader, a class can be defined by **a different loader**, from **a different library version**, or even from **dynamically generated/transformed bytes**.

Familiar scenarios:

- `mvn dependency:tree` or `gradle dependencies` shows library v2, yet the stack trace reports `NoSuchMethodError` corresponding to runtime v1.
- The build passes and tests run fine, yet deploying to Tomcat reports `ClassCastException` or `NoClassDefFoundError`.
- `java.class.path` looks right, yet a dependency is loaded from the `WEB-INF/lib` directory, a nested JAR inside an executable artifact, or a separate plugin ClassLoader.
- Removing a dependency from `pom.xml`/`build.gradle` still leaves runtime using that class because it is provided by the application server or an agent layer.
- Some classes appear multiple times on the classpath; the version actually used differs from the one you expect.

**Goal:** determine the **classpath/module path at build time**, the **resolved dependency graph**, the **actual JVM runtime path**, the **ClassLoader that defines the class**, and the **actual artifact bytes**. Do not infer one of these facts solely from another.

This article targets Java 17+, using Maven and Gradle as examples; most of the ClassLoader identification techniques apply to Java in general.

## 2. Distinguishing Five Perspectives on the Same Dependency

| Perspective | Question | Tools |
|---|---|---|
| **Declared dependencies** | What does the project declare? | `pom.xml`, `build.gradle(.kts)`, version catalog |
| **Resolved dependency graph** | How did the build tool select versions/modules and resolve conflicts? | `dependency:tree`, Gradle `dependencies`/`dependencyInsight` |
| **Resolved classpath** | Which output files/JARs are in the compile/runtime/test classpath for each configuration? | Maven `dependency:build-classpath`; Gradle `runtimeClasspath`/`testRuntimeClasspath` |
| **Launch context** | With which arguments, working directory, module path, manifest, launcher, container, or agents is the process actually started? | command line, build launch task, runtime properties, process diagnostics |
| **Runtime class source/defining loader** | Which loader defined a specific class in the JVM, and from what source? | `Class.getClassLoader()`, `getProtectionDomain()`/`CodeSource`, `-Xlog:class+load` |

Each layer answers a different part. **The dependency tree is not an "exact manifest of every class loaded into the JVM"**. It typically does not show all of:
- application/test output directories;
- server-provided JARs/classes outside the build project;
- JARs added at launch via `-cp`, `--module-path`, manifest, or a custom launcher;
- dependencies appended by Java agents;
- nested JARs handled by Spring Boot or custom launchers;
- classes created via bytecode generation;
- code loaded by a plugin loader or container loader;
- differences between test runtime, production runtime, and JPMS module layers.

## 3. Classpath Is Not the ClassLoader Graph

### 3.1. Classpath Is a Set of Sources for One or More Loaders

Basic command:

```bash
java -cp "app/classes:libs/a.jar:libs/b.jar" com.example.Main
```

On Linux/macOS, the separator between classpath entries is typically `:`. On Windows, use `;`:

```powershell
java -cp "app\classes;libs\a.jar;libs\b.jar" com.example.Main
```

With the **default launcher and application class loader**, entry order can affect which class with the same binary name is found first. However:

- Parent delegation may return a class already defined in the parent.
- A loader that has already loaded a name can return the existing class via `findLoadedClass`.
- A custom loader may use child-first loading, loader-specific URLs, a network source, or generated bytecode.
- Named modules use module resolution and module-to-loader mapping, not just the `-cp` file list.
- A process can have multiple independent ClassLoaders with their own sources and rules.

Therefore, **saying "it is on the classpath" is not enough** to explain where a class is actually defined from.

### 3.2. Class Identity at Runtime

For normal classes, a runtime class's identity consists of its **binary name and defining ClassLoader**. Two classes with the same name from two independent loaders can be two different runtime types:

```text
Loader-A ──define──▶ com.example.Widget [type A]
Loader-B ──define──▶ com.example.Widget [type B]

"type A" != "type B"
```

Conversely, two child loaders can both delegate to their parent and therefore receive **the same `Class<?>` object**, even if both call `loadClass("com.example.Widget")`.

When debugging, observe:
- `type.getName()`;
- `type.getClassLoader()` (defining loader);
- `type.getModule()` and its layer if JPMS is used;
- `type.getProtectionDomain().getCodeSource()` if available.

**Do not simply print `System.getProperty("java.class.path")` and conclude that you know all runtime sources.**

## 4. Compile Classpath, Runtime Classpath, and Test Classpath Are Three Different Sets

### 4.1. Compile Classpath

Contains classes/libraries sufficient for the compiler to resolve symbols during compilation. It may include **APIs for compilation** without automatically guaranteeing that those implementation JARs appear in the runtime artifact.

For example, the tool/build configures a library at compile time under a specific scope/policy, while the app server provides that library at runtime. The build passes, and if the server version has an ABI mismatch, runtime reports an error.

### 4.2. Runtime Classpath

Contains the code/implementations required for the main application. Runtime often needs additional dependencies not required at compile time (driver/database implementation, logging backend, service provider) and may exclude certain **compile-only** artifacts.

### 4.3. Test Classpath

Typically includes:
- main output (classes/resources);
- test output (classes/resources);
- main runtime dependencies;
- test framework/assertion/mocking libraries;
- fixtures/test-specific resources.

A test may pass because `testRuntimeClasspath` inadvertently includes a library that the production runtime does not have. Conversely, the application server may have a JAR that local tests do not see.

**Rule:** you must compare the **right configuration, the right source set, and the right launch task**. Do not use the compile dependency tree to infer the runtime directly, or use testRuntimeClasspath to claim that the production distribution will be identical.

## 5. Maven: Reading dependency:tree in the Right Context

### 5.1. Basic Command

At the Maven project root or a selected module:

```bash
mvn dependency:tree
```

The tree output shows the dependencies resolved by Maven according to the project and plugin execution. Illustrative example:

```text
com.acme:app:jar:1.0
+- com.acme:core:jar:1.0:compile
|  \- org.example:codec:jar:2.0:compile
\- com.acme:web:jar:1.0:compile
   \- org.example:codec:jar:1.5:compile (omitted for conflict)
```

This is an **illustrative output**, not output captured from a specific project. `omitted for conflict` and the exact formatting depend on the Maven Dependency Plugin version; some versions/options only display the selected nodes without printing all omitted branches.

Maven typically applies **nearest definition** for version conflicts (if depths are equal, declaration order matters). The result is also influenced by:
- `dependencyManagement` in the parent/BOM;
- declared versions of direct dependencies;
- exclusions;
- scopes and scope transitivity;
- optional dependencies;
- active profiles;
- plugin/build configuration.

**Do not look only at `pom.xml` to guess the transitively selected version**; inspect the resolved tree with the exact Maven profiles/properties.

### 5.2. The Right Module and the Right Profile

In a multi-module Maven reactor:

```bash
mvn -pl :service-app dependency:tree
```

`:service-app` is an example artifactId; replace it with the actual module. To compare profile environments:

```bash
mvn -Pproduction -pl :service-app dependency:tree
```

If CI uses `-Pproduction` while your local machine does not enable it, the dependency tree can differ. Similarly, property-based profiles, OS/JDK activation, and the parent POM version can also change resolution.

**An artifact appearing in module A's tree does not guarantee it appears in module B's runtime classpath**.

### 5.3. How Maven Scopes Matter

| Maven scope | Typical impact |
|---|---|
| `compile` | Compile, runtime, and test classpaths |
| `provided` | Compile/test; provided at runtime by the JDK/server/host depending on the deployment model |
| `runtime` | Runtime/test; the compiler does not need that API to compile the app |
| `test` | Test compile/runtime; not part of main runtime |
| `system` | Local file declared via a system path; should not be used in modern designs |
| `import` | Only for `pom` dependencies in `dependencyManagement`; imports a BOM to manage versions, not a runtime JAR |

This is an overview of Maven scopes and does not replace checking the **effective POM** and actual results. For example, a `provided`-scoped servlet API may be absent from the WAR's `WEB-INF/lib`, yet **present in Tomcat** as defined by the container loader.

### 5.4. Exporting the Dependency Runtime Classpath

The Maven Dependency Plugin has the goal:

```bash
mvn dependency:build-classpath -Dmdep.includeScope=runtime -Dmdep.outputFile=runtime-cp.txt
```

Depending on the plugin version, accompanying parameters can be set via the goal's Maven properties; check the plugin version in use if the output differs from what you expect.

**Important:** this output lists the **dependency artifact paths** exported by the plugin for the selected configuration; it **does not necessarily include the main output directory, manifest Class-Path, server-provided JARs, or classloader URLs from the launcher**. Therefore, to reconstruct the Java launch command, you also need to add the appropriate `target/classes`, resources, packaging, and launch configuration.

To inspect the effective project model when you suspect a parent/BOM/profile is causing divergence:

```bash
mvn help:effective-pom
mvn help:active-profiles
```

Detailed parameters, goal availability, and messages may vary by plugin version. Do not modify a BOM/exclusion based solely on a single `dependency:tree` line before confirming which runtime class source is actually causing the error.

## 6. Gradle: Distinguishing runtimeClasspath from testRuntimeClasspath

### 6.1. Viewing the Resolved Runtime Tree

With the Gradle Java plugin:

```bash
./gradlew dependencies --configuration runtimeClasspath
./gradlew dependencies --configuration testRuntimeClasspath
```

On Windows PowerShell:

```powershell
.\gradlew.bat dependencies --configuration runtimeClasspath
.\gradlew.bat dependencies --configuration testRuntimeClasspath
```

For a multi-project build:

```bash
./gradlew :app:dependencies --configuration runtimeClasspath
```

`:app` is only an **example project name**. Replace it with the corresponding project path in your actual build.

The Gradle `dependencies` report displays the resolved dependency graph, including the versions selected after conflict resolution, constraints, and variants. Illustrative example:

```text
runtimeClasspath - Runtime classpath of source set 'main'.
+--- org.example:codec:1.0 -> 2.1
\--- org.example:transport:3.0
     \--- org.example:codec:2.1
```

The notation `1.0 -> 2.1` means version 1.0 was requested, yet resolution selected 2.1 in this configuration; it does not guarantee that at runtime bytes will be loaded solely from a single file of that name if the launcher/container adds other sources.

### 6.2. Using dependencyInsight to Find the Reason for a Version

```bash
./gradlew :app:dependencyInsight --dependency org.example:codec --configuration runtimeClasspath
```

This command helps answer:
- Which path pulled the dependency in?
- Why was version X selected?
- Are there constraints, conflicts, force/platform/strict versions, or variant rules?
- Are there multiple requested versions yet only one resolved component version?

Gradle conflict resolution **is not identical to Maven's nearest-wins**. Gradle typically chooses an appropriate version according to conflict resolution/constraints—by default it may select the higher version under common conditions—but `strictly`, `force`, dependency substitution, platforms/capabilities, variants, and resolution strategy can alter the outcome. **Do not guess** a dependency version solely from declaration order in `build.gradle`.

### 6.3. Printing the Classpath Used by a Java Source Set

In a Gradle Kotlin DSL project with the Java plugin applied, you can define a task:

```kotlin
import org.gradle.api.tasks.SourceSetContainer

plugins {
    java
}

tasks.register("printMainRuntimeClasspath") {
    doLast {
        val sourceSets = extensions.getByType<SourceSetContainer>()
        val main = sourceSets.getByName("main")
        println(main.runtimeClasspath.asPath)
    }
}
```

This is a **`build.gradle.kts` snippet**, not Java source code. If the project already has `plugins { ... }`, integrate only the necessary import/task; do not add a duplicate `plugins` block.

Run:

```bash
./gradlew printMainRuntimeClasspath
```

`main.runtimeClasspath` includes the **main output directories** plus runtime dependencies according to Java plugin/source-set semantics; printing `configurations.runtimeClasspath.get().asPath` alone can omit the project's own output directories. Even so, the classpath printed by Gradle still does not prove that an **IDE launch, custom JavaExec task, executable JAR, or server** uses that exact string.

### 6.4. Gradle Run/Test/Application Packaging

When debugging, note the **actual task used**:
- `test` typically uses the test runtime classpath and forked test worker JVMs.
- A `JavaExec` task has a `classpath` that can be customized beyond the default runtimeClasspath.
- The Application plugin's `run`/start scripts obtain their classpath from the distribution defined by the plugin/build.
- A fat/shadow JAR has merged/relocated contents; it does not necessarily preserve individual JAR files per the resolved graph.
- An IDE Gradle import may run using the IDE classpath instead of the Gradle `run` task, depending on launch settings.

Therefore, compare both the **Gradle resolved graph** and the **task's effective classpath/process command**.

## 7. How Compile vs. Runtime Differences Cause NoSuchMethodError

Suppose code compiles with library `codec-v1`:

```java
public static String encode() {
    return "encoded";
}
```

After compilation, another JAR containing the same class name—but **no longer having the `encode()` method**—is placed on the runtime classpath. The Java compiler already generated the corresponding method reference in the caller's constant pool. When the JVM resolves the call, the target method does not exist in the class actually loaded, so it throws:

```text
java.lang.NoSuchMethodError
```

Points to remember:
- Two classes having the **same binary name** does not guarantee the same **binary API**.
- The JVM loads classes according to the runtime loader/search path rather than reading the build-time dependency tree.
- `NoSuchMethodError` is a `LinkageError` (via `IncompatibleClassChangeError`).
- It is not a `ClassNotFoundException`; the JVM may have found the class, yet the runtime API does not match the compile-time API.
- Changing the library from v1 to v2 does not automatically recompile the **caller bytecode** if you only copy the JAR into runtime.

## 8. Complete Java 17+ Example: Compile with v1, Run with v2

This experiment does not need Maven/Gradle, because the goal is to **prove with a plain JVM** that differing build-time and runtime classpaths can produce `NoSuchMethodError`.

### 8.1. Directory Structure

Create:

```text
classpath-mismatch/
├── src/
│   ├── v1/demo/lib/Codec.java
│   ├── v2/demo/lib/Codec.java
│   └── app/demo/app/Main.java
└── out/
    ├── v1/
    ├── v2/
    └── app/
```

Both `Codec.java` files declare the **same fully qualified binary name** `demo.lib.Codec`, yet we compile them into two independent output directories.

### 8.2. Version v1: src/v1/demo/lib/Codec.java

```java
package demo.lib;

public final class Codec {
    private Codec() {
    }

    public static String origin() {
        return "lib-v1";
    }

    public static String encode() {
        return "encoded";
    }
}
```

### 8.3. Version v2: src/v2/demo/lib/Codec.java

```java
package demo.lib;

public final class Codec {
    private Codec() {
    }

    public static String origin() {
        return "lib-v2";
    }

    public static String newer() {
        return "new API";
    }
}
```

V2 keeps `origin()` but removed `encode()` — this is a **binary-incompatible change** for a caller compiled with v1.

### 8.4. App: src/app/demo/app/Main.java

```java
package demo.app;

import demo.lib.Codec;

public final class Main {
    public static void main(String[] args) {
        System.out.println("runtime library: " + Codec.origin());

        try {
            System.out.println("encode: " + Codec.encode());
        } catch (NoSuchMethodError error) {
            System.out.println("caught: NoSuchMethodError");
        }
    }
}
```

### 8.5. Separate Compilation

In the `classpath-mismatch` directory, using JDK 17+:

```bash
javac --release 17 -d out/v1 src/v1/demo/lib/Codec.java
javac --release 17 -d out/v2 src/v2/demo/lib/Codec.java
javac --release 17 -cp out/v1 -d out/app src/app/demo/app/Main.java
```

The crucial point: **the app is compiled with `-cp out/v1`**, where `Codec.encode()` exists. Only at runtime do we choose one of the two versions.

### 8.6. Running with the Correct v1 Version

On Linux/macOS:

```bash
java -cp "out/app:out/v1" demo.app.Main
```

On Windows PowerShell:

```powershell
java -cp "out/app;out/v1" demo.app.Main
```

Stdout:

```text
runtime library: lib-v1
encode: encoded
```

### 8.7. Replacing Runtime with v2

On Linux/macOS:

```bash
java -cp "out/app:out/v2" demo.app.Main
```

On Windows PowerShell:

```powershell
java -cp "out/app;out/v2" demo.app.Main
```

Stdout:

```text
runtime library: lib-v2
caught: NoSuchMethodError
```

**Exact explanation:**
1. The caller `demo.app.Main` was compiled with `Codec` v1, so its constant pool contains a reference to `demo.lib.Codec.encode:()Ljava/lang/String;`.
2. The runtime `-cp` has `out/app` and **`out/v2`**, but **not `out/v1`**.
3. `Codec.origin()` exists in v2, so the program prints `lib-v2`: proof that **the runtime class actually comes from the v2 API**, not from the dependency declaration.
4. When resolving `Codec.encode()`, the JVM cannot find a matching method in the v2 runtime class, so it throws `NoSuchMethodError`.
5. The `catch` in the app code keeps stdout stable, independent of the long message/stack trace generated by the JVM.

In production systems, **catching `NoSuchMethodError` and letting the application continue normally is discouraged**. This is an intentional mechanism in the demo to observe the failure. A runtime dependency ABI error normally requires blocking startup or fixing the deployment.

### 8.8. What If Both v1 and v2 Are on the Classpath?

Try on Linux/macOS:

```bash
java -cp "out/app:out/v1:out/v2" demo.app.Main
java -cp "out/app:out/v2:out/v1" demo.app.Main
```

Expected results:
- Putting `out/v1` first → `Codec` v1 is normally found first by the application loader; the two lines correspond to `lib-v1` and `encoded`.
- Putting `out/v2` first → `Codec` v2 is normally selected; prints `lib-v2` and `caught: NoSuchMethodError`.

On Windows, replace the `:` separator with `;`. **This is the demo's standard application classpath model**, not a universal rule for custom ClassLoaders, module layers, or containers. If a parent loader has already defined the same binary name, the entry order in the child does not determine the actual source class either.

### 8.9. Reading the Caller's Bytecode

```bash
javap -verbose -classpath out/app demo.app.Main
```

Look for constant-pool references to `demo/lib/Codec.origin` and `demo/lib/Codec.encode`. If using `javap -c`, look for the invocation instructions in the `main` body.

After switching runtime to v2, **the caller class file does not modify itself** to change `encode()` to `newer()`. That is the core principle leading to binary linkage errors.

## 9. Printing Information About the Class Actually Defined by the JVM

To know "where `demo.lib.Codec` comes from" in a running process, use a probe on the **actual `Class<?>`**, not just the build report.

### 9.1. File RuntimeClassProbe.java

```java
import java.net.URL;
import java.security.CodeSource;
import java.security.ProtectionDomain;

public final class RuntimeClassProbe {
    public static void report(Class<?> type) {
        System.out.println("class=" + type.getName());

        ClassLoader loader = type.getClassLoader();
        System.out.println("defining loader="
                + (loader == null ? "<bootstrap>" : loader.toString()));

        Module module = type.getModule();
        System.out.println("module="
                + (module.isNamed() ? module.getName() : "<unnamed>"));

        ProtectionDomain pd = type.getProtectionDomain();
        CodeSource source = pd == null ? null : pd.getCodeSource();
        URL url = source == null ? null : source.getLocation();

        System.out.println("code source="
                + (url == null ? "<unavailable>" : url));

        ClassLoader tccl =
                Thread.currentThread().getContextClassLoader();
        System.out.println("TCCL="
                + (tccl == null ? "<bootstrap>" : tccl.toString()));
    }

    public static void main(String[] args) {
        report(RuntimeClassProbe.class);
    }
}
```

Compile and run as a regular Java 17 program:

```bash
javac --release 17 RuntimeClassProbe.java
java RuntimeClassProbe
```

**There is no fixed stdout for the loader name, URL, and TCCL.** Those values depend on the actual environment, which is what we want to diagnose. The lines `class=RuntimeClassProbe` and `module=<unnamed>` are typical values when running the `java RuntimeClassProbe` example on the classpath, but they do not replace inspecting the process.

To inspect a dependency class in your application:

```java
// Snippet at a location where the compile-time type is already available:
RuntimeClassProbe.report(demo.lib.Codec.class);
```

The call above requires the class `demo.lib.Codec` to be available at compile time. When you are not allowed to import the class due to module access or want to avoid a direct link, use a `Class.forName` approach with the **appropriate loader** and catch the appropriate exceptions.

### 9.2. CodeSource Is Useful but Not Absolute

`type.getProtectionDomain().getCodeSource().getLocation()` can show:
- `file:/.../out/v2/`;
- `file:/.../some-lib.jar`;
- a URL from the class loader/launcher;
- or `null` if no source information is available.

**Limitations:**
- Not every loader has a useful CodeSource; generated classes and some containers/transformers may return `null` or a synthetic source.
- Nested JAR launchers may return specific schemes/URLs.
- A CodeSource location indicates the source attached to the ProtectionDomain, **not cryptographic proof that the bytes match 100% of the file currently on disk**.
- If the JAR on disk is replaced after the class has already loaded, the CodeSource path may still look the same while the JVM holds the old class bytes.
- If a Java agent transforms a class before definition, the source JAR may not match the final bytecode received by the JVM.

You should combine CodeSource with class loading logs, artifact checksums, version/build metadata, and the runtime loader graph.

## 10. java.class.path Does Not Reveal All Loading Sources

In a program:

```java
System.out.println(
        System.getProperty("java.class.path"));
```

This snippet prints the system property related to the application classpath, which is useful as a starting check. However:

- Custom `URLClassLoader` instances have their own URLs not necessarily present in `java.class.path`.
- JPMS named modules go through `--module-path` and module layer resolution; the module path does not appear in full like ordinary classpath entries.
- Executable/fat/nested JAR launchers may build their own runtime loaders.
- Java agents can add JARs to the bootstrap/system loader search.
- A servlet/container/plugin host has its own loader graph.
- The application's `-cp` can be overridden according to launcher/manifest rules.
- The program may be packaged as a native image, which does not correspond to a traditional JVM classpath model.

**The right question:** "Which defining loader defined a specific class, and from which source, in the actual process?" Not just "What string does java.class.path currently hold?".

## 11. The Case of java -jar, Manifest Class-Path, and Executable JARs

The command:

```bash
java -jar app.jar
```

selects the main class from the JAR's manifest according to `-jar` rules. With the standard Java launcher, `-jar` **ignores `-cp`/`CLASSPATH` as the usual user classpath** for that application. A manifest may include a `Class-Path` entry listing relative JARs external to the artifact.

Example manifest:

```text
Manifest-Version: 1.0
Main-Class: com.example.Main
Class-Path: lib/a.jar lib/b.jar
```

This is **illustrative manifest content**, which must be packaged properly inside `META-INF/MANIFEST.MF`, not a standalone shell command.

With common Spring Boot executable JARs:
- Implementation dependencies may reside in `BOOT-INF/lib`.
- App classes may be in `BOOT-INF/classes`.
- A custom launcher creates a class loader to serve nested JARs.
- `java.class.path` may only show the path to the executable artifact, **without listing every nested library JAR**.

Therefore, `mvn dependency:tree` may be right and the executable artifact may have the right dependencies, yet the runtime class source still needs to be verified through the actual loader/launcher.

### Inspecting the Final Artifact

```bash
jar --list --file app.jar
```

Replace `app.jar` with the actual file. For a WAR, inspect `WEB-INF/lib` and `WEB-INF/classes`; for a JAR, examine the manifest and the locations of packaged resources/dependencies.

**Do not confuse the build workspace's `target/classes`/`build/classes/java/main` directory with the contents of the deployed artifact.**

## 12. App Servers: "provided" Means the Container Is the Runtime Source

A web application can declare a `provided` dependency for the Servlet API (specific package and artifact names depend on the Jakarta/Java EE version). The build tool compiles successfully, yet the WAR typically does not package the provided JAR into `WEB-INF/lib`. The **container** supplies the API via a shared loader.

Conceptual diagram:

```text
Bootstrap / Platform
        │
  Container Common Loader
        │
  Webapp ClassLoader
        ├── WEB-INF/classes
        └── WEB-INF/lib/*.jar
```

This means:
- `dependency:tree` still shows the `provided` dependency in the build model;
- the runtime webapp source may be supplied by the common/container loader;
- the container version may differ from the compile version;
- two webapps can have different private dependency versions or share a container library;
- local unit tests run by Maven/Gradle do not accurately reproduce the container's loader graph.

With Tomcat, the webapp loader has local-first rules for many web application classes and delegation exceptions for platform/container APIs. **Do not assume default ClassLoader parent-first delegation applies to every kind of loader without reading the container/version documentation.**

### How to Check Properly

- Print `type.getClassLoader()` and `CodeSource` inside the container process, not only in local tests.
- List the JARs in the actual WAR/lib and shared/container libs.
- Check parent delegation/order and excluded/filtered packages.
- If deployed across multiple nodes/pods, ensure every node actually runs the same artifact/image version.
- Compare the compile-time class API with the class at container runtime.
- Inspect the loader used by the framework, TCCL, and SPI libraries.

An issue that occurs only after a redeploy can also involve **old loader generations** retained by a host registry/thread, not simply a version mismatch.

## 13. JPMS: The Module Path Is Another Source

With Java 9+, a program can be launched with:

```bash
java --module-path mods --module my.app/my.app.Main
```

Not all modules visible in `mods` are necessarily resolved. A runtime class is associated with a **Module** and may reside in a **ModuleLayer**.

When debugging:

```java
// Snippet:
Class<?> type = my.app.SomeType.class;
System.out.println(type.getModule().getName());
System.out.println(type.getModule().getLayer());
System.out.println(type.getClassLoader());
```

This is a snippet, and the class `my.app.SomeType` is just an example. When the same loader serves multiple modules, `ClassLoader` is not enough to determine package exports/readability; you must inspect `Module`.

Typical errors:
- `module not found` due to module path/root/resolution;
- `IllegalAccessError` or `InaccessibleObjectException` when `exports`/`opens` do not match;
- `ClassNotFoundException` because the queried loader/layer does not own the class;
- `ClassCastException` if the same binary name is defined in different loaders/layers.

**Do not turn a JPMS access error into "Gradle/Maven picked the wrong version"** before verifying the dependency graph and module rules.

## 14. Test Runners: The Dependency Tree Is Right, but the Test JVM Differs from the Production JVM

### 14.1. Maven Surefire

Maven Surefire/Failsafe may use forked JVM workers, provider-specific class loading, and test classpaths. Options such as:
- `forkCount`;
- `reuseForks`;
- `useSystemClassLoader`;
- `argLine`;
- test classpath customization;

can change the process/ClassLoader used for tests.

A test seeing a library via `test` scope does not prove production has that library. Conversely, a container runtime may have server-provided libraries that Surefire does not.

### 14.2. Gradle Test

The Gradle `Test` task typically runs tests in forked JVM workers. Configurations such as `maxParallelForks` and `forkEvery` affect the parallel/fork lifecycle, but **do not automatically guarantee a separate JVM for each test method**.

If tests pass with `./gradlew test` yet fail with `java -jar`:
- compare `testRuntimeClasspath` and main `runtimeClasspath`;
- check which test dependencies are not packaged;
- check JVM options/agents and system properties;
- determine whether fixtures/mock frameworks override any classes;
- compare the application launcher and the actual artifact.

### 14.3. IDE Launch

An IDE may use a classpath from the IDE model, Gradle import, or delegated build/run. A run configuration can also select a different JDK, working directory, env vars, and module path.

To reproduce production, record the **exact launch command** or use the right task/distribution, rather than inferring solely from project dependencies.

## 15. Java Agents and Bytecode Transformation

Agents can:
- transform class bytes when a class is defined;
- perform retransformation/redefinition according to JVM APIs and conditions;
- add JARs to the bootstrap/system classloader search;
- generate proxy/helper classes;
- alter the class order/source you observe.

If `CodeSource` points to the right JAR yet the method bytecode or a `VerifyError` does not match the artifact on disk, ask:
- Is there a `-javaagent` or runtime attach?
- Is there instrumentation by an AOP/coverage/mock framework?
- Which agent transformed the class? Can the transformed bytes be dumped?
- Was the class redefined/retransformed after loading?

**The dependency tree does not know the exact transformed bytes**. That is why diagnosing `ClassFormatError`/`VerifyError` requires the class-file bytes both before and after transformation, not just dependency versions.

## 16. Reading Runtime Class Sources via JVM Logging

On HotSpot/JDK 17, you can enable `-Xlog:class+load=info` at process startup, then filter for the exact binary name suspected of using the wrong version:

```bash
java -Xlog:class+load=info -cp "out/app:out/v2" demo.app.Main
```

On Windows, replace the `:` classpath separator with `;`. The source in a log line is a useful runtime indicator, but you must cross-check it against the defining loader and `CodeSource` of the **runtime `Class<?>`**, because one binary name can be defined by multiple loaders. For a running process, `jcmd PID VM.command_line` and `VM.classloader_stats` add launch/loader details; check `jcmd PID help` and guard sensitive information in the output. The `-verbose:class`/`-Xlog` article in this chapter provides full guidance on tags, levels, output, and log filtering.
## 17. Detecting Duplicate Candidate Classes via Resource Enumeration

When you suspect two JARs both contain a `demo/lib/Codec.class`, calling `ClassLoader.getResources("demo/lib/Codec.class")` on the **right runtime loader** can list the candidate URLs:

```java
// Snippet inside a method; loader is the ClassLoader under investigation.
var entries = loader.getResources("demo/lib/Codec.class");
while (entries.hasMoreElements()) {
    System.out.println(entries.nextElement());
}
```

The method requires handling `IOException`. Resource enumeration does not prove the first URL is the bytes the JVM actually defined: parent-first/child-first policies, module encapsulation, generated classes, and bytecode transformation can make class lookup differ. Always cross-check against `Class.getClassLoader()` and the `CodeSource`/class-load log of the running class. The "Listing resources with duplicate names..." article has a dedicated experiment on `getResource` (winner), `getResources` (candidates), and parent/URL lookup order.
## 18. Dependency Trees and Dependency Conflicts: How Maven Differs from Gradle

Suppose the declared graph is:

```text
app
├── library-A ── codec:1.5
└── library-B ── codec:2.1
```

**Maven:** for dependencies with the same group/artifact that can conflict, the nearest-definition rule, tie-order, and dependencyManagement/BOM determine the final version in a given scope/configuration.

**Gradle:** the configuration's conflict resolution/constraints/capabilities/variants and strategies determine the final component; default behavior differs from Maven, while version forcing/strict constraints/platforms can govern the outcome.

For both, you need to ask:
1. **Which version did the build tool select in the right configuration?**
2. **Was that artifact version actually placed into the final JAR/WAR/distribution?**
3. **Did the runtime launcher add or remove any sources?**
4. **Which ClassLoader actually defined the class?**
5. **Do the runtime bytes match the API that the caller was compiled against?**

Changing only the dependency declaration without checking the following four questions can produce a false fix: local tests turn green, yet the staging server still loads an old JAR from common lib.

## 19. Scopes and Exclusions: Missing at Runtime or Provided Elsewhere?

Two contrasting groups of scenarios:

### 19.1. Missing Dependency

The build tool compiles successfully against the library's API, yet the runtime deployment excludes that library. When the JVM executes code needing a class inside it, you may encounter:
- `ClassNotFoundException` from an explicit lookup;
- `NoClassDefFoundError` from a symbolic reference requiring resolution;
- service discovery failures if the provider implementation is missing.

Investigate:
- dependency scope, exclusions, and optional flags;
- packaging plugin and the final artifact;
- the actual production classpath;
- module resolution if using JPMS;
- loader visibility and TCCL.

### 19.2. Dependency Provided by the Server or Another Loader

The build tree does not list a version for the runtime host, yet the server has the JAR in its shared libs. A class may load successfully, yet have the wrong API version, causing `NoSuchMethodError`/`NoSuchFieldError`/`IllegalAccessError`.

Investigate:
- container common libs;
- `WEB-INF/lib`;
- extension/plugin loader sources;
- child-first/parent-first policy;
- duplicate binary names and CodeSource;
- the actual process/container image version.

With Maven `provided`, not packaging the dependency inside the artifact may **be the intended design**, yet you must reconcile it against the **actual server API/version**.

## 20. Failure Taxonomy to Avoid Wrong Fixes

| Symptom | What May Have Happened | What to Check |
|---|---|---|
| `ClassNotFoundException` | The requested loader could not find the class | Binary name, loader, URLs, packaging, module graph |
| `NoClassDefFoundError` | A class needed by the JVM is unavailable, or class initialization previously failed | Dependency chain, cause, initialization |
| `NoSuchMethodError` | The caller was built against an API containing the method, while the runtime class lacks the exact signature | Compile/runtime version mismatch and CodeSource |
| `NoSuchFieldError` | Runtime field name/descriptor mismatch | ABI and selected JAR |
| `IncompatibleClassChangeError` | Mismatched class/interface or static/instance contract | Binary compatibility |
| `ClassCastException` between two identical names | Different defining ClassLoaders | Loader identities, parent/shared API |
| `UnsupportedClassVersionError` | The runtime JDK does not recognize the class-file version | `java -version`, `javap -verbose`, `--release` |
| `ClassFormatError` | Invalid class-file bytes | Actual bytes, artifact corruption, transformer |
| `VerifyError` | Bytecode invalid according to the verifier | Post-transform bytes, frames, agent |
| `IllegalAccessError`/`InaccessibleObjectException` | Package/member access was denied | JPMS requires/exports/opens, runtime package |
| `ServiceConfigurationError` | Invalid provider config/constructor/classloader/module | `META-INF/services`, `uses/provides`, TCCL |

Every symptom in the table requires **the first error + class source + loader** to classify; do not draw automatic conclusions solely from the exception name.

## 21. A Repeatable Diagnostic Workflow

### Step A — Freeze the Launch Parameters

Record:
- Java runtime version (`java -version`);
- build tool version and active profiles;
- artifact/build commit/checksum;
- exact launch command, working directory, env vars;
- classpath/module-path/manifest/launcher;
- JVM flags and Java agents;
- container image and shared libs, if any.

Do not copy secrets from `VM.system_properties`, the command line, or the environment into public logs/trackers.

### Step B — Verify the Resolved Graph

Maven:

```bash
mvn dependency:tree
mvn help:effective-pom
```

Gradle:

```bash
./gradlew :app:dependencies --configuration runtimeClasspath
./gradlew :app:dependencyInsight --dependency org.example:codec --configuration runtimeClasspath
```

Run with the **exact module/profile/configuration** of the failing application. If tests fail, inspect the test runtime; if production fails, inspect the main runtime and packaging.

### Step C — Verify the Actual Artifact

- Inspect the JAR/WAR contents, `META-INF/MANIFEST.MF`, and bundled libs.
- Reconcile checksums/build IDs against the artifact in the image/server.
- Check dependency scope, exclusions/relocation, and packaging plugins.
- Check whether a library is provided by the server/host/agent outside the build tool.

### Step D — Verify the Defining Loader and Class Source

- Record `Class.getClassLoader()` and `getModule()`.
- Record `CodeSource` if available.
- Use `-Xlog:class+load=info` to locate the class source.
- Use `getResources` when duplicate entries are suspected.
- When plugins are involved, check whether shared API types are defined by the parent or redefined by a child.

### Step E — Compare the ABI and Bytecode

- `javap -verbose`/`-c` on both the **runtime artifact** and **compile artifact**;
- compare method names + descriptors, field types, and class/interface flags;
- if an agent/transformer is present, dump/compare the post-transformation bytes;
- compare JDK class-file major/minor versions;
- reproduce with a **fresh JVM or a fresh ClassLoader** if the old class is already cached.

### Step F — Fix the Root Cause at the Right Layer

- Wrong build graph → adjust dependency declarations, constraints/BOM, and exclusions/scopes properly.
- Wrong artifact packaging → fix packaging/distribution, rebuild the image, and redeploy.
- Wrong launcher/classpath → fix the run task, manifest, container libs, or IDE configuration.
- Wrong loader isolation → place the shared API in the parent, or fix delegation/module layers.
- Incompatible ABI → align compile/runtime versions or rebuild callers.
- Agent generates invalid bytecode → fix the transformer, rather than only changing JAR declarations.

After the fix, you must **confirm that the runtime class source changed as expected**, rather than stopping once `mvn dependency:tree`/`gradle dependencies` looks "cleaner".

## 22. Maven and Gradle Quick Checklist

| Question | Maven | Gradle |
|---|---|---|
| Dependency graph? | `mvn dependency:tree` | `dependencies --configuration runtimeClasspath` |
| Why was a version selected? | effective POM, dependencyManagement, and tree | `dependencyInsight --dependency ...` |
| Main runtime dependencies? | `dependency:build-classpath` with the appropriate scope | `runtimeClasspath` |
| Test dependencies? | Test scope/Surefire classpath | `testRuntimeClasspath` |
| Where are main output classes? | typically `target/classes` | typically `build/classes/java/main` |
| Packaging? | JAR/WAR/assembly/shade/Boot plugin | JAR/distribution/shadow/Boot task |
| Launch process? | `java -jar`, exec plugin, Surefire, container | `run`/`JavaExec`/`test`/IDE/distribution |
| Runtime class source? | JVM probe/`-Xlog:class+load` | JVM probe/`-Xlog:class+load` |

**Note:** these directory structures are common conventions and can be changed by build customizations. Do not assume a project uses `target/classes` or `build/classes/java/main` solely from the tool name; inspect the actual configuration.

## 23. Self-Check Exercises

1. **Does the Maven dependency tree report every loaded class accurately?** No; it is a graph based on build configuration, not a log of runtime class definitions.
2. **If two JARs contain the same binary name on the classpath, what determines which class is used?** Loader/search/delegation order and already-loaded state; not simply the newest version.
3. **Does `java.class.path` list every custom URLClassLoader URL?** No.
4. **Must TestRuntimeClasspath match runtimeClasspath?** No; tests add frameworks/fixtures and separate outputs.
5. **Is Maven `provided` being excluded from a WAR definitely a bug?** No; the container may be the runtime API source.
6. **What does Gradle dependencyInsight answer?** Why a dependency/version/variant was selected for a configuration.
7. **What can happen if the caller compiles against `Codec.encode()` yet the runtime class lacks that method?** `NoSuchMethodError`.
8. **What does the line `runtime library: lib-v2` in the demo confirm?** That `Codec.origin()` was invoked on the runtime class from version v2 on the demo's classpath.
9. **Is `CodeSource` always the exact JAR path of the final class bytes?** No; it may be null/synthetic or the bytes may have been transformed.
10. **When running `java -jar`, is adding `-cp` the default way to replace the user classpath?** No; `-jar` uses its own launcher/manifest mechanism.
11. **Must an executable JAR with nested libs appear in full inside java.class.path?** No.
12. **Does `Class.getClassLoader()` return the initiating loader or the defining loader?** The defining loader.
13. **Can two classes with the same name defined by different loaders always be cast to each other?** No.
14. **Is a module on the module path guaranteed to be resolved?** No.
15. **Does `getResources("p/Foo.class")` prove that Foo was defined from the first URL?** No; resource lookup is not identical to class loading.
16. **If CodeSource points to the right JAR, what can still cause a `VerifyError`?** An agent/transformer modifying the bytes before the JVM defines the class.
17. **Local unit tests pass yet the container fails: what needs to be compared?** Test vs. prod classpath, packaging, server libs, loader hierarchy, and runtime JDK.
18. **What if you fix the dependency tree yet runtime still fails?** You must check the deployed artifact, launch context, loader, and class source.
19. **Do Maven and Gradle resolve version conflicts identically?** No.
20. **What is the minimum data needed to diagnose a mismatch effectively?** The root error, class name, defining loader, CodeSource/log, runtime JDK, resolved graph, and launch command.
