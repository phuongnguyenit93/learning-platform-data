# When Do You Need to Extend ClassLoader in Java?

**Extending `java.lang.ClassLoader`** means writing a subclass to control **how the JVM finds class data and defines runtime classes**. It is a specialized tool, not the default solution for every `ClassNotFoundException` error or every dynamic JAR loading need.

**Guideline for choosing a solution:** Prefer classpath/module path, `URLClassLoader`, `ServiceLoader`, or module layers if they already solve the problem. Only write a custom `ClassLoader` when you genuinely need **a new source of class bytecode, a separate namespace/isolation, or an intentional bytecode selection/transformation policy** that the built-in tools cannot satisfy.

In Java, a runtime class identity is determined by the pair:

```text
(binary name, defining class loader)
```

Therefore, a custom loader is not merely “another path to find files”. It can alter **type identity, castability, package-private access, static state, dependency resolution, and the unload/reload lifecycle**.

## 1. First: What Does the Default ClassLoader Do?

Modern JVMs have bootstrap/platform/application loaders to locate platform classes and application classes. The standard `ClassLoader` uses the **parent delegation** model:

```text
child.loadClass("plugin.Example")
         |
         v
findLoadedClass(name)
         |
         +-- class already known? -> return
         |
         v
parent.loadClass(name) (or bootstrap lookup)
         |
         +-- found? -> return class provided by parent/ancestor
         |
         v
child.findClass(name)
         |
         +-- find own bytecode, then defineClass(...)
         |
         v
Resulting Class<?>
```

The default `loadClass(String, boolean)` checks whether the class is already loaded, delegates to the parent, and only then calls `findClass`. If the `resolve` parameter is `true`, it also calls `resolveClass` per the API contract. **`loadClass` is not synonymous with running the static initializer**: a class may be loaded/linked but is only initialized when required by a program or JVM operation.

For a custom loader that **still wants parent-first**, the extension approach recommended by the Javadoc is to override **`findClass(String)`**, not immediately override `loadClass`. That way, you retain the base class's delegation algorithm, already-loaded class checks, locking, and resolution.

The methods have different roles:

| API | Purpose | Usually needs overriding? |
|---|---|---|
| `loadClass(String)` | Entry point to load a class by binary name | **No** if parent-first is acceptable |
| `loadClass(String, boolean)` | Coordinates cache, parent, findClass, resolve | Only when a different delegation policy is needed and the consequences are understood |
| `findClass(String)` | Finds/defines a class provided **by this loader** | **Yes** for a custom parent-first bytecode source |
| `defineClass(String, byte[], int, int)` | Converts valid class file bytes into a runtime class | **Call**, do not override (protected final method) |
| `findLoadedClass(String)` | Queries a class already associated with the initiating loader | Useful if overriding loadClass yourself |
| `resolveClass(Class<?>)` | Completes appropriate linking | Call per `loadClass` rules; not initialization |
| `findResource(String)` / `findResources(String)` | Finds resources provided by the loader | When the loader also serves resources |
| `getClassLoadingLock(String)` | Lock coordinating class loading by class name | Need to know when replacing `loadClass`/using parallel loading |

**Do not call `defineClass` every time an already-loaded name is requested.** A loader cannot redefine the same binary name into a second runtime class of that same loader; attempting to do so can result in a `LinkageError` related to duplicate definition. To create a new generation of classes, you must design a new defining loader and manage its lifetime.

## 2. When Should You Actually Create a Custom ClassLoader?

Some legitimate needs:

### A. Class data is not located in a URL/JAR/directory understood by built-in loaders

For example, an environment that receives **bytecode from memory**, an internal data store, content generated by an in-program compiler, or a custom storage format. Once you have the class file `byte[]`, a custom loader can call `defineClass` to bring the class into the JVM.

`URLClassLoader` works well with URLs pointing to a directory/JAR. If your source is a `Map<String,byte[]>` or bytecode provided via an internal API, overriding `findClass` can be simpler than forcing the data into a JAR file on disk.

**Security:** Having bytecode in memory or encrypted at rest **does not make it safe code**. Verify trusted origin, integrity, size, dependencies, and execution permissions before defining. You should not write a loader that downloads and runs arbitrary bytecode from the network just because it is possible.

### B. Creating a namespace for a plugin or application part with its own lifecycle

Two plugins may use two versions of a library with the same binary name. With different **defining loaders**, they can coexist as distinct runtime classes:

```text
Parent/AppLoader:
    shared.api.Plugin          (a shared contract)
       ^                 ^
       |                 |
PluginLoaderA       PluginLoaderB:
    impl.A              impl.B
    lib.VersionX        lib.VersionY
```

Separate loaders isolate implementations/dependencies, but **the shared API must be delegated to the common loader**; if the `shared.api.Plugin` interface is also defined separately in each child, casting and service exchange may fail.

Plugin loading can be implemented using `URLClassLoader` with an appropriate parent; no custom subclass is needed unless you must customize delegation, resource lookup, or the code source.

### C. Needing a delegation policy other than parent-first for a defined scope

Some plugin/server applications want **child-first** for their own dependencies so they are not overridden by a same-named version from the parent. In that case, a custom `loadClass` may be considered, but there must be **specific namespace rules**, such as prioritizing the parent for `java.*`, runtime-appropriate `javax.*`, and `shared.api.*`, while only self-loading first for `plugin.internal.*`.

This is **more difficult and higher-risk** than overriding `findClass`. Lack of synchronization, omitting `findLoadedClass`, mishandling `resolveClass`, or redefining the shared API yourself can cause `LinkageError`, `ClassCastException`, or `IllegalAccessError`. You should try an existing loader framework/container first.

### D. Generating/transforming bytecode in an application pipeline

A custom loader can be one step in a compiler system, bytecode generator, or transformation pipeline: obtaining class bytes, inspecting/transforming them, and calling `defineClass`. However, if the goal is to **instrument classes that the JVM has already loaded or is loading**, consider **`java.lang.instrument.Instrumentation`**, a Java agent, a bytecode library, `MethodHandles.Lookup#defineClass`, or hidden classes depending on the case; not every modification requires replacing the original loader class.

### E. Separating the lifecycles of plugin generations

The JVM generally does not support “replacing class bytes and re-initializing the same runtime class”. To bring a new version with the same binary name into use, one approach is to **create a new defining loader**, rebuild instances/services in the new namespace, and then remove references to the old loader and objects.

This is a hot-reload architecture, **not a guarantee that simply creating a new class loader means the JVM has unloaded the old loader**. Threads, static references, caches, context class loaders, and registries can keep the old class loader alive for a long time.

## 3. Situations Where You Should NOT Rush to Extend ClassLoader

| Practical problem | Preferred approach | When to consider a custom loader? |
|---|---|---|
| Application cannot see a JAR library | Fix `--class-path`, manifest `Class-Path`, or module path | When classes must be located from a non-standard source |
| Want to add a JAR/directory URL in an isolated scope | `URLClassLoader` with a chosen parent | When a different delegation policy or data source is needed |
| Want to find an implementation by interface | `ServiceLoader` + provider declarations | When you need to self-organize multiple namespaces/provider loaders |
| Want to reference a class by string name | `Class.forName(name, initialize, loader)` or `loader.loadClass(name)` | When no built-in loader can supply the class |
| Want to reduce class initialization time | Defer usage, use `Class.forName(..., false, ...)` when appropriate | Usually does **not** need a custom loader |
| Want to load additional modules | JPMS module path / `ModuleLayer` | When the module architecture also requires a custom loader policy |
| Want to change methods/bytecode of a running class | Java agent/Instrumentation, appropriate bytecode tools | A loader is only one piece if the pipeline defines new classes |
| Want to load a new class in the same package/nest context | `MethodHandles.Lookup#defineClass` or hidden-class APIs when conditions are met | When a namespace/lifetime larger than a lookup is needed |
| Want to run **untrusted** third-party plugins | Design isolated execution at the process/container level, verify code, control permissions | **ClassLoader alone is not a security sandbox** |
| Want “one static singleton across all plugins” | Place the contract/state intentionally in the shared loader | Separate custom loaders usually create **multiple copies of static state**, opposite to the goal |

Some common misconceptions:

- `ClassLoader` is **not** an automatic dependency management tool like Maven/Gradle.
- `ClassLoader` does **not** replace `module-info.java` access permissions, exports/opens, package access, or JVM verification.
- `ClassLoader` does **not** force every resource URL to become a `File`; resources can come from a JAR, JRT, the network, or memory.
- Trying to create a new loader to “fix” `NoClassDefFoundError` without diagnosing the cause is counterproductive: the error may result from a missing dependency, failed initialization, invalid bytecode, a version conflict, or loader constraints.

## 4. Java 17+ Example: Defining a Plugin Class from byte[] with a Custom Loader

This demo illustrates a real need: the application **only has the service API on the application classpath**, while the implementation resides in memory supplied to the custom loader. To make the exercise easily reproducible, we read bytes from a separate `.class` file, but **do not add the plugin directory to the runtime classpath**. In a real system, the `byte[]` might come from an in-memory compiler or a trusted internal source.

Source directory:

```text
loader-demo/
├── src/
│   ├── api/
│   │   └── Greeter.java
│   ├── plugin/
│   │   └── HelloGreeter.java
│   └── app/
│       └── LoaderDemo.java
└── out/
    ├── app/
    └── plugin/
```

### 4.1. Shared Contract

File **`src/api/Greeter.java`**:

```java
package api;

public interface Greeter {
    String greet();
}
```

### 4.2. Plugin Implementation

File **`src/plugin/HelloGreeter.java`**:

```java
package plugin;

import api.Greeter;

public final class HelloGreeter implements Greeter {
    static {
        System.out.println("Plugin initialized");
    }

    @Override
    public String greet() {
        return "hello-from-bytes";
    }
}
```

### 4.3. Application and Custom Loader

File **`src/app/LoaderDemo.java`**:

```java
package app;

import api.Greeter;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.Map;

public final class LoaderDemo {
    static final class MemoryLoader extends ClassLoader {
        private final Map<String, byte[]> definitions;

        MemoryLoader(ClassLoader parent, Map<String, byte[]> definitions) {
            super(parent);
            this.definitions = Map.copyOf(definitions);
        }

        @Override
        protected Class<?> findClass(String name)
                throws ClassNotFoundException {
            byte[] bytes = definitions.get(name);
            if (bytes == null) {
                throw new ClassNotFoundException(name);
            }

            return defineClass(name, bytes, 0, bytes.length);
        }
    }

    public static void main(String[] args) throws Exception {
        ClassLoader appLoader = LoaderDemo.class.getClassLoader();

        try {
            Class.forName("plugin.HelloGreeter", false, appLoader);
            System.out.println("Parent sees plugin: true");
        } catch (ClassNotFoundException expected) {
            System.out.println("Parent sees plugin: false");
        }

        byte[] classBytes = Files.readAllBytes(Path.of(args[0]));
        MemoryLoader custom = new MemoryLoader(appLoader,
                Map.of("plugin.HelloGreeter", classBytes));

        Class<?> type = custom.loadClass("plugin.HelloGreeter");
        System.out.println("Defined by custom: "
                + (type.getClassLoader() == custom));
        System.out.println("Class loaded, initialization pending");

        Greeter greeter =
                (Greeter) type.getDeclaredConstructor().newInstance();

        System.out.println("Message: " + greeter.greet());
        System.out.println("Shared Greeter: "
                + (custom.loadClass("api.Greeter") == Greeter.class));
        System.out.println("Same Class on repeat: "
                + (custom.loadClass("plugin.HelloGreeter") == type));
    }
}
```

**Why only override `findClass`?** Because `MemoryLoader` inherits the default `loadClass`, the JVM checks already-loaded classes and delegates to the parent before calling `findClass`. When the plugin implementation is not found by the parent, `findClass` receives the bytes and uses `defineClass` to define a new runtime class. When looking up `api.Greeter`, the parent defines the contract, so the app and plugin use **the same interface**.

### 4.4. Compile and Run

On Linux/macOS/Git Bash, from the `loader-demo` directory:

```bash
mkdir -p out/app out/plugin

javac --release 17 -d out/app \
  src/api/Greeter.java src/app/LoaderDemo.java

javac --release 17 -cp out/app -d out/plugin \
  src/plugin/HelloGreeter.java

java -cp out/app app.LoaderDemo out/plugin/plugin/HelloGreeter.class
```

On Windows PowerShell:

```powershell
New-Item -ItemType Directory -Force -Path out/app, out/plugin | Out-Null
javac --release 17 -d out/app src/api/Greeter.java src/app/LoaderDemo.java
javac --release 17 -cp out/app -d out/plugin src/plugin/HelloGreeter.java
java -cp out/app app.LoaderDemo out/plugin/plugin/HelloGreeter.class
```

Output verified with `javac --release 17` and a Java 17-compatible JDK 21:

```text
Parent sees plugin: false
Defined by custom: true
Class loaded, initialization pending
Plugin initialized
Message: hello-from-bytes
Shared Greeter: true
Same Class on repeat: true
```

**Exact step-by-step explanation:**

1. The runtime classpath only contains `out/app`. The parent/application loader finds `api.Greeter` and `app.LoaderDemo`, and **cannot find** `plugin.HelloGreeter`. Therefore, the first line is `false`.
2. The plugin bytecode has been compiled into `out/plugin`, but that directory **is not on the runtime classpath**. The program reads the `HelloGreeter.class` file directly into a `byte[]`.
3. `MemoryLoader.findClass("plugin.HelloGreeter")` is called after the parent fails to find it; `defineClass` creates a runtime class whose defining loader is the `MemoryLoader` instance.
4. `custom.loadClass(...)` only loads the class and does not necessarily run the static initializer. Therefore, the line `Class loaded, initialization pending` appears before `Plugin initialized`.
5. The reflective constructor call triggers initialization of the plugin, and then the constructor and `greet()` run.
6. `custom.loadClass("api.Greeter")` delegates to the parent, so it returns **the exact same `Class` object** that the application code is using. Casting to `Greeter` succeeds.
7. The subsequent `custom.loadClass("plugin.HelloGreeter")` receives the same runtime `Class<?>` from that loader without redefining the class.

**Limitations of this example:** This loader holds a `Map` containing mutable `byte[]` values purely for demonstration. `Map.copyOf` copies the map structure, **not the underlying byte arrays inside**; if the data comes from an untrusted caller or can be mutated concurrently, you must clone/control ownership and validate the bytecode. The example also does not implement resource lookup, package metadata, CodeSource, or a resource-closing lifecycle. A production system needs these steps according to its actual requirements.

## 5. Key Decisions When Designing Your Own Loader

### 5.1. Bytecode Source and Naming

`ClassLoader.findClass(String name)` receives a **binary name** such as `com.example.Widget`, not `com/example/Widget.class`. If the source is a directory/JAR, the resource path can be derived when needed:

```java
String entry = name.replace('.', '/') + ".class";
```

This is a non-standalone illustrative line suitable for ordinary class binary names. When building a real-world loader, you must validate package/name legality, prevent traversal, restrict inputs, and read only from trusted sources. Do not accept an arbitrary string and concatenate it into a filesystem path without validating the path and root directory.

`defineClass(name, bytes, 0, bytes.length)` requires valid **class-file bytes**. If the supplied binary name does not match the class name inside the bytes, the JVM may throw `NoClassDefFoundError`. If the bytecode is malformed or violates type verification rules, you may encounter `ClassFormatError` or `VerifyError`. A custom loader **does not bypass** JVM verification.

### 5.2. Choosing the Right Parent

Choosing an appropriate parent enables sharing API classes and JDK platform classes:

```java
ClassLoader parent = SharedService.class.getClassLoader();
ClassLoader custom = new MemoryLoader(parent, definitions);
```

This is an illustrative snippet; `SharedService` and `definitions` must be declared. The goal is for the child loader and the application to use the same runtime `SharedService` via delegation.

**Do not choose `null` as the parent merely because you want “complete isolation”** if the plugin still needs types/libraries defined by the application loader. A `null` parent represents the bootstrap path in `ClassLoader`, so it may not see shared APIs from the application loader.

Choosing different parent loaders leads to different results when the same class name is already present in the parent. Parent-first can also unintentionally “win” over the plugin's own class version if the parent contains a class with the same name.

### 5.3. Do You Need to Override loadClass for Child-First?

In most cases, no. However, if there is a serious namespace isolation requirement, an illustrative strategy is:

```text
loadClass(name, resolve):
    lock by name
    if already loaded -> return loaded class
    if name belongs to shared/JDK APIs -> try parent first
    if name belongs to private plugin namespace:
         try child's findClass first
         if not found -> fallback to parent per policy
    other names -> parent-first
    if resolve -> resolveClass(result)
    return result
```

This is **pseudocode**, not a complete implementation. Several difficult points must be controlled:

- `getClassLoadingLock(name)` and `findLoadedClass(name)` to avoid creating duplicate classes under concurrency.
- `ClassNotFoundException` is used for the not-found case; **do not arbitrarily catch and ignore `VerifyError`, `LinkageError`, or `SecurityException` in order to use another class version**.
- Do not define `java.*` yourself; `ClassLoader.defineClass` has explicit restrictions, and many platforms also have their own package/module policies.
- `shared.api.*` usually must be parent-first so classes/interfaces can cross the boundary between the plugin and the host.
- If code in the plugin contains method signatures referencing types defined incompatibly by different loaders, JVM **loading constraints** can cause a `LinkageError`.
- If you invert delegation for classes without handling resource lookup or service discovery correspondingly, classes and resources may unexpectedly come from two different sources.

If you already have a container/plugin framework, it is better to understand and configure the framework's loader policy before writing your own loader.

### 5.4. Do You Need findResource/findResources?

If the same source supplies `.class` files and resources such as configuration, service descriptors, images, or schemas, the loader may need to implement:

```java
protected URL findResource(String name)
protected Enumeration<URL> findResources(String name)
```

`ClassLoader.getResource` and `getResources` have their own delegation/search rules. A resource name has the form `"plugin/config.json"` (with `/` separators), not a binary name `plugin.config`. A custom loader that returns the right `Class<?>` yet cannot find `META-INF/services/...` can still prevent `ServiceLoader` from recognizing the provider.

If resources reside in memory or a custom scheme, provide an appropriate URL stream handler or an API to access them directly as a stream; do not expect every resource to be convertible into a `File`. Creating a custom protocol URL requires considering policy, lifetime, and connection complexity.

### 5.5. Packages, Sealing, Protection Domains, and Code Sources

`defineClass` enforces constraints on class name, package, and signing certificate sets. When working with signed JARs, package sealing, `CodeSource`, or when specific metadata/protection domains are needed, **you should not simply read bytes, call the default `defineClass` overload, and assume all metadata is preserved**.

`SecureClassLoader`, `URLClassLoader`, `definePackage`, and the `defineClass(..., ProtectionDomain)` overload provide tools for related scenarios. For a production custom loader, you must follow proper package/certificates/signers rules when bringing classes from multiple sources into the same loader.

Read the Javadoc for `defineClass`: defining names in `java.*` is restricted; the name parameter must match the binary name inside the class-file bytes when provided.

### 5.6. Concurrency: Parallel-Capable Loaders

`ClassLoader` supports the **parallel capable** model. Subclasses can register via `registerAsParallelCapable()` from the static initializer of **the subclass itself**, provided that the appropriate superclasses are already registered and no instance has been created yet; the API returns a boolean indicating the result.

This enables per-class-name locking instead of a single loader-wide lock in appropriate cases. **Do not enable it yourself if your implementation does not yet guarantee thread-safety** of maps, caches, I/O, transformations, and namespaces. If you override `loadClass` yourself and omit locking, two threads requesting the same class simultaneously can cause a duplicate definition or a race condition. A parent-first implementation inherited from `ClassLoader` is usually lower-risk for beginners.

### 5.7. Lifecycle: Closing a Source Does Not Mean Unloading Classes Immediately

`URLClassLoader` implements `Closeable`; closing it releases JAR/file handles within the loader's capability and prevents loading additional classes/resources through the paths it manages. However, already-loaded classes can still be used, and `close()` **does not force the garbage collector to unload them immediately**.

The custom `MemoryLoader` in the example has no long-lived native/file open resources, yet it can still retain byte arrays/metadata. A production loader with network sources, file handles, or long-lived caches should have an appropriate lifecycle API while also managing references to classes, objects, threads, and TCCL.

## 6. Identifying Risks Before Extending a Loader

A custom loader intervenes in where the JVM obtains class bytes and where **types are defined**. Consequently, a feature intended only to introduce a new class-loading source can still alter critical boundaries:

| Symptom | What to check |
| --- | --- |
| `ClassCastException` despite the same class name | Do both sides receive **the same `Class<?>` of the shared API**, or did each loader define its own copy? |
| `ClassNotFoundException` / `NoClassDefFoundError` | Is the name/source missing, is a dependency invisible, or did the class fail initialization earlier? |
| `ClassFormatError`, `VerifyError`, `UnsupportedClassVersionError` | Does the read bytecode match the expected structure, verification, and target JVM? |
| `LinkageError` | Is there a duplicate definition, binary incompatibility, or loading constraint violation between loaders? |
| Resource/provider not found | Does the loader support resource lookup and the same SPI identifiers? |
| Old plugin is not reclaimed | Which thread, TCCL, registry, cache, JAR handle, or object is retaining the loader? |

**Do not handle every error by switching to child-first or swallowing `LinkageError` to try different bytes.** First identify the defining loader, binary name, byte source, and root cause. The rest of this chapter examines these very boundaries in depth, from parent selection to error handling, type identity, and lifecycle. A class loader by itself is not a sandbox for untrusted code.

## 7. Comparing Alternatives: URLClassLoader, ServiceLoader, ModuleLayer

### URLClassLoader

When you have a directory/JAR at an appropriate URL and want to load classes/resources from that path:

```java
import java.net.URL;
import java.net.URLClassLoader;
import java.nio.file.Path;

Path jar = Path.of("plugins/sample.jar");
URL[] urls = { jar.toUri().toURL() };

try (URLClassLoader loader =
        new URLClassLoader(urls, MyApp.class.getClassLoader())) {
    Class<?> type = loader.loadClass("plugins.Sample");
    // Use type within the required scope.
}
```

This is an **illustrative snippet**, not a standalone `main` file because it requires `MyApp` and an appropriate JAR. `URLClassLoader` already implements class/resource lookup from directories/JARs, open resource management, and many necessary behaviors; **there is no need to rewrite `findClass` for this use case**.

Note that `URLClassLoader` inherits parent delegation by default. If the parent already has a class with the same name, the parent may win and the loader simply returns the parent's class. Intentional dependency isolation requires a higher-level solution, not merely adding a URL.

### ServiceLoader

When the application only needs implementations of a service interface and does not need to manage class bytes:

```java
ServiceLoader<MyService> services =
        ServiceLoader.load(MyService.class, pluginLoader);
```

This is an illustrative snippet requiring real `MyService` and `pluginLoader`. `ServiceLoader` manages discovery based on `META-INF/services` or named-module `provides`, while the class loader manages visibility/runtime class identity. You can combine **`ServiceLoader` with the built-in `URLClassLoader`**, without forcing a custom subclass.

### JPMS ModuleLayer

With named modules, the module path, dependency graph, readability, and module access can be resolved via `java.lang.module.Configuration` / `ModuleLayer`. A framework can establish a new layer and attach suitable loaders. This is a different mechanism from arbitrarily reading `.class` files via `findClass`.

If the problem is “plugins have `module-info.java` and need module-level isolation”, evaluate module layers first, because writing your own loader does not automatically provide module readability/exports/opens.

### MethodHandles.Lookup / hidden classes

If a framework generates a class **closely tied to a lookup class** (such as a helper class in the corresponding runtime package), `MethodHandles.Lookup#defineClass` can define the class in the lookup class's loader/package under the corresponding constraints. `defineHiddenClass` serves cases of bytecode-generated classes that do not need to be looked up again by an ordinary binary name.

You should not assume this is a complete replacement for a loader when an independent plugin namespace is needed; they solve a different class of problem.

### Instrumentation / Java agent

If you want to observe/modify bytecode at class load events or retransform/redefine within the limits of the Instrumentation API, a Java agent is the dedicated choice. Creating a custom loader does not allow arbitrarily replacing all classes already defined by the parent/JVM.

## 8. A Practical Decision Workflow

Ask in order:

1. **Is the class source an ordinary JAR/directory?** Yes → try the classpath/module path or `URLClassLoader`.
2. **Is the goal only to find service implementations?** Yes → try `ServiceLoader`/JPMS `provides`.
3. **Do you need to load an exact class name with a known loader?** Yes → use `Class.forName(name, initialize, loader)` or `loader.loadClass(name)`.
4. **Does the bytecode come from a source that cannot be naturally represented by URLClassLoader?** Yes → consider a subclass overriding `findClass`.
5. **Do two versions with the same binary name need to coexist?** Yes → design separate defining loaders and shared contracts; consider a container/module framework.
6. **Is child-first truly needed?** Only when you have namespace isolation rules and test for type identity/delegation errors; not as a default.
7. **Do you need to replace an already-defined class in the same loader?** Evaluate Instrumentation or a new loader generation; a second `defineClass` with the same name in the same loader will not solve it.
8. **Is there a requirement to run untrusted code?** Shift isolation/security to process design, OS sandbox/container, and code provenance control; a loader alone is not enough.
9. **Is there a plan for closing, cleanup, and unloading?** Review strong references, threads/TCCL, caches, opened JARs, registrations, and lifecycle before implementing.
10. **Can you write tests that run on the real deployment runtime?** You must test class identity, classpath, resource loading, module access, concurrency, and root-cause errors.

The question “When do you need to extend `ClassLoader`?” usually has the best answer: **“when we own a specialized class-definition mechanism, and have proven that the built-in APIs are insufficient”**. Do not start by subclassing just because you want to call `loadClass`.

## 9. Quality Checklist for a Custom-Written ClassLoader

- [ ] `findClass` returns `Class<?>` if finding/defining succeeds; throws `ClassNotFoundException` properly when **not found**.
- [ ] Input is a **binary name**; if converted to a resource path, use the appropriate `pkg/Type.class` name and control the source.
- [ ] `defineClass` is passed the correct bytes and binary name; do not define a duplicate name in the same loader.
- [ ] Parent has the required shared API/JDK types; do not inadvertently redefine shared APIs in the child.
- [ ] If using a custom `loadClass`, locking, `findLoadedClass`, fallback/resolve, and exception propagation are handled properly.
- [ ] Resource discovery/`ServiceLoader` finds the right descriptors if the provider source uses the same loader.
- [ ] Size, trusted origin, and integrity of bytes are controlled; do not treat the loader as a sandbox.
- [ ] Policies for modules, package-private access, sealing, code source/signers, and native libraries are in place if needed by the system.
- [ ] Do not indefinitely retain references to plugin loaders/instances when unloading is required.
- [ ] Tests cover not only the happy path: missing class, missing dependency, invalid bytecode, version mismatch, duplicate class, concurrency, and version replacement.

## 10. Self-Check Exercises

**1. When a JAR on the filesystem needs to be loaded dynamically, do you have to subclass `ClassLoader`?** Not necessarily; usually try `URLClassLoader` with an appropriate parent first.

**2. Why override `findClass` instead of `loadClass` in a parent-first loader?** Because the base class already handles already-loaded class checks, parent delegation, synchronization, and resolution; `findClass` only adds how to locate your own class source.

**3. Why must the classloader in the example use the application loader as its parent?** Because the plugin implements `api.Greeter` and the app needs to cast to **the same runtime interface**; the parent provides the shared contract.

**4. Does `loadClass` run `static { ... }` immediately?** Not by the default contract. Initialization happens when required by the program/JVM, such as creating an instance.

**5. Do two loaders calling `defineClass("p.Widget", sameBytes, ...)` create the same runtime class?** No. Different defining loaders produce different class identities.

**6. Should `ClassNotFoundException` be used to mask a `VerifyError`?** No. A not-found error is different from invalid bytecode; the real cause must be reported.

**7. When you want provider implementations to be selected based on the plugin's loader, which API should you choose?** Usually `ServiceLoader.load(serviceType, pluginLoader)` or an appropriate module-layer approach; there is no need to implement SPI discovery yourself.

**8. Does a custom ClassLoader guarantee that a plugin is trustworthy and cannot access system resources?** No. It is not a standalone security sandbox mechanism.

**9. Does `URLClassLoader.close()` force unloading of all classes it defined?** No. It closes resources managed by the loader, but class unloading depends on the JVM/garbage collection and having no remaining references.

**10. When should you invest in a custom delegation policy?** When you have a defined namespace isolation requirement, have chosen the shared API boundary, know the list of packages to prioritize for parent/child, and have tests for type identity, linkage, and concurrency.

**Remember:** Only extend `ClassLoader` when you need to change **how class bytes are supplied or the namespace/loading policy**. For a parent-first custom loader, start with `findClass` and `defineClass`, keep the shared API in the parent, and do not forget **class identity, resources, modules, concurrency, security, and lifecycle**. For ordinary JARs and SPI, leverage `URLClassLoader`/`ServiceLoader` first.
