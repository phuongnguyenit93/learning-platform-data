# Default CLASS Policy Without @Retention in Java

## 1. Core Rule

When defining an annotation with `@interface` that **does not declare the `@Retention` meta-annotation**, Java applies the **default retention policy `RetentionPolicy.CLASS`**.

```java
@interface InternalMarker {
    String value();
}
```

`InternalMarker` does not specify `@Retention(...)`, yet according to Java's rules, its usages are treated as annotations with the `CLASS` policy: the annotation information is typically written into the `.class` file by the compiler, while **the Java Reflection API at runtime does not return that annotation via `getAnnotation`, `getDeclaredAnnotations`, or `isAnnotationPresent`**.

Omitting `@Retention` does **not** mean `SOURCE` (existing only in source code) or `RUNTIME` (readable via reflection). The exact default is **`CLASS`**.

Three concerns should be separated:

1. **Declaration source:** `@interface` defines an annotation type and its elements.
2. **Retention policy:** determines through which stages the annotation is retained.
3. **Processor:** what the compiler, bytecode analysis tools, or runtime programs can do with that metadata.

`CLASS` describes the metadata lifecycle; it **does not automatically generate business behavior** and does not guarantee accessibility via reflection.

## 2. The Three Policies: SOURCE, CLASS, and RUNTIME

Java SE defines `java.lang.annotation.RetentionPolicy` with three values:

| Policy | Metadata at source/compile time | Present in `.class` file generated by a standard compiler? | Readable by standard Java reflection at runtime? |
| --- | --- | --- | --- |
| `SOURCE` | Yes | No, per the retention policy | No |
| `CLASS` | Yes | Yes, except for exceptions depending on the applicable target kind; the JVM is not required to retain it for runtime | No |
| `RUNTIME` | Yes | Yes | Yes, at locations that have a corresponding reflection API |

**`CLASS` is the default** when a `@Retention` declaration is missing. For an annotation at common declaration locations such as `TYPE`, `METHOD`, `FIELD`, this data is compiled into class-file metadata. For special targets such as annotations on **local variable** declarations (`LOCAL_VARIABLE`), do not overgeneralize this into a guarantee that every CLASS annotation will always be stored in the class file in the same form.

Saying "the JVM is not required to retain CLASS annotations at runtime" states the retention specification; saying "Java reflection does not retrieve it like a RUNTIME annotation" is what to keep in mind when writing code.

### 2.1. Syntax for Using @Retention

```java
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;

@Retention(RetentionPolicy.SOURCE)
@interface SourceMarker {}

@Retention(RetentionPolicy.CLASS)
@interface ClassMarker {}

@Retention(RetentionPolicy.RUNTIME)
@interface RuntimeMarker {}

@interface DefaultMarker {} // Equivalent to CLASS in terms of retention policy.
```

These declarations are valid in Java 17+. `RetentionPolicy` is an enum belonging to Java SE; `@Retention` is a meta-annotation placed on an **annotation type definition**, not placed on a method to "change the retention" of that method.

Writing `@Retention(RetentionPolicy.CLASS)` is an **explicit** declaration. Omitting `@Retention` altogether on `DefaultMarker` causes the default rule to take effect. The two cases share the same retention policy, but **the metadata about whether `@Retention` itself is declared differs**.

### 2.2. The @Retention Meta-Annotation Does Not Mean the Annotation's Value

Example:

```java
@Retention(RetentionPolicy.RUNTIME)
@interface Visible {
    String value();
}

@Visible("hello")
class Feature {}
```

Here `@Retention` configures **the `Visible` type**; `@Visible("hello")` is **an annotation usage** on `Feature`. Changing the retention policy requires editing the declaration of the annotation type (`Visible`), not adding `@Retention` on the class using it.

## 3. Why Is CLASS Different from RUNTIME?

A Java file typically goes through three stages:

```text
.java source code
     |
     | javac reads annotation declarations and checks syntax/target/values
     v
.class bytecode file
     |
     | JVM loads the class; libraries/tools can process metadata
     v
Running program and Reflection API
```

With `SOURCE`, the compiler does not store annotation usages in the class file per the retention policy; source-processing tools may still inspect them.

With `CLASS`, the compiler writes the annotation into the class file at supported locations, but **Java SE reflection does not expose it as a runtime annotation**.

With `RUNTIME`, the metadata is retained so that **the corresponding reflection APIs** can read it. For example, an annotation with `@Target(METHOD)` and `RUNTIME` can be queried using `Method.getAnnotation(...)`.

An easy way to remember this:

> An annotation without `@Retention` usually still exists in bytecode, but does not appear when querying standard Java reflection for annotations at runtime.

This explains why "opening the `.class` file shows the annotation" and "`method.getAnnotation(...)` returns the annotation" are two different observations.

### 3.1. Class-File Attribute Names That Reveal the Difference

In a class file generated by `javac`, annotations placed on method/class declarations are typically represented through attributes such as:

- `RuntimeVisibleAnnotations`: stores annotations with `RUNTIME` retention so runtime reflection can see them at supported locations.
- `RuntimeInvisibleAnnotations`: stores `CLASS` annotations on declarations; the name "Invisible" here refers to visibility for runtime reflection, **not that the bytecode does not contain the annotation**.

`SOURCE` annotations are not included in these attributes per the retention policy. Additionally, there are other attribute kinds related to parameter annotations and type annotations depending on the location. These should be distinguished from annotations attached directly to a method.

## 4. Standalone Java 17+ Example: No @Retention Is CLASS

Create the file **DefaultRetentionDemo.java** with the full contents below. The annotations are declared in the same file to keep the example simple, with no dependencies outside the JDK.

```java
import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;
import java.lang.reflect.Method;

@Target(ElementType.METHOD)
@interface DefaultTag {
    String value();
}

@Retention(RetentionPolicy.CLASS)
@Target(ElementType.METHOD)
@interface ClassTag {
    String value();
}

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
@interface RuntimeTag {
    String value();
}

@Retention(RetentionPolicy.SOURCE)
@Target(ElementType.METHOD)
@interface SourceTag {
    String value();
}

public class DefaultRetentionDemo {
    @DefaultTag("default")
    @ClassTag("class")
    @RuntimeTag("runtime")
    @SourceTag("source")
    public void execute() {}

    public static void main(String[] args)
            throws NoSuchMethodException {
        Method method = DefaultRetentionDemo.class
                .getDeclaredMethod("execute");

        System.out.println(method.isAnnotationPresent(DefaultTag.class));
        System.out.println(method.isAnnotationPresent(ClassTag.class));
        System.out.println(method.isAnnotationPresent(RuntimeTag.class));
        System.out.println(method.isAnnotationPresent(SourceTag.class));

        RuntimeTag runtime = method.getAnnotation(RuntimeTag.class);
        System.out.println(runtime.value());
    }
}
```

Compile and run using JDK 17 or later in the directory containing the file:

```bash
javac DefaultRetentionDemo.java
java DefaultRetentionDemo
```

Stdout output:

```text
false
false
true
false
runtime
```

**Why does this produce this output?**

1. `@DefaultTag` **does not declare `@Retention`**, so it uses the default `CLASS` policy. Reflection returns `false` even though the annotation was used in source.
2. `@ClassTag` has an explicit `@Retention(CLASS)` declaration. It is also not visible via reflection, so it prints `false`.
3. `@RuntimeTag` has `@Retention(RUNTIME)`. Because it is attached directly to the `execute()` method, reflection returns `true` and retrieves the value `"runtime"`.
4. `@SourceTag` has `@Retention(SOURCE)`. There is no runtime annotation for reflection to read, so it prints `false`.
5. `Method.getDeclaredMethod("execute")` returns the exact parameterless method; it does not require additional compiler flags such as `-parameters`.

Four annotations of different types are written together on one method. `@Target(METHOD)` makes the compiler validate the usage location; **`@Target` does not change the retention** of each type.

### 4.1. Viewing CLASS Annotations in Bytecode

After compiling, run:

```bash
javap -v DefaultRetentionDemo
```

In the metadata section of `execute()`, you can find the labels **`RuntimeVisibleAnnotations`** and **`RuntimeInvisibleAnnotations`**. The JDK `javap` tool displays parsed class-file information:

- `RuntimeVisibleAnnotations` relates to `RuntimeTag`.
- `RuntimeInvisibleAnnotations` relates to **both `DefaultTag` and `ClassTag`**.
- `SourceTag` is not present in the class file in the method's annotation section.

Do not treat constant pool indices or the line order printed by `javap -v` as a stable API: they can vary by compiler/JDK. What to observe is that **CLASS annotations have metadata in the class file, but are absent from the program's reflection results**.

### 4.2. Try Removing Only @Retention from RuntimeTag

If you change:

```java
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
@interface RuntimeTag {
    String value();
}
```

to:

```java
@Target(ElementType.METHOD)
@interface RuntimeTag {
    String value();
}
```

then `RuntimeTag` switches to the default `CLASS` policy. When recompiled and run again, `method.getAnnotation(RuntimeTag.class)` returns `null`. The original example calling `runtime.value()` will throw a `NullPointerException` if the handling code is not updated.

Therefore, when reading metadata via reflection, **check for null** or use `isAnnotationPresent` according to context. If the intent is for the runtime application to always be able to read it, declare `RUNTIME` explicitly from the start.

## 5. When Should the Default CLASS Policy Be Used?

Not every annotation needs to be queried by the application at runtime. The `CLASS` policy is suitable when you want to store metadata in the class file without needing to expose it via standard Java reflection.

Examples of requirement categories that may apply:

- **Bytecode analysis or transformation tools**: a tool may read class files and inspect the annotations retained inside them.
- **Internal descriptive conventions at the class-file level**: metadata needs to accompany the compiled artifact for a build or analysis workflow, without needing to be queried directly via `Method.getAnnotation`.
- **Annotations that only need processing at compile time**: if all information is only needed while the compiler reads source code, `SOURCE` may be more suitable, though `CLASS` remains meaningful when metadata needs to be kept after compilation.

Important point: just because an annotation is `CLASS` **does not mean a tool will automatically process it**. Tools that recognize and read the annotation must be designed or configured separately.

### 5.1. When Should You Choose RUNTIME?

Choose `@Retention(RetentionPolicy.RUNTIME)` when designing an annotation that **the running program needs to read via reflection**, such as custom runtime configuration or framework introspection. Example:

```java
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;

@Retention(RetentionPolicy.RUNTIME)
@interface FeatureFlag {
    boolean enabled() default true;
}
```

This is only a metadata definition. To actually enable/disable a feature, runtime code still needs to retrieve `FeatureFlag` and apply the `enabled()` value. Adding `RUNTIME` **only allows access**; it does not make Java enable/disable features automatically.

### 5.2. When Should You Choose SOURCE?

Choose `@Retention(RetentionPolicy.SOURCE)` if the annotation is only for the compiler or source-processing tools and does not need to reside in the class file. A Java SE example is `@Override`, which is checked by the compiler during compilation.

However, **do not guess the policy solely from its intended purpose**: inspect the actual definition of the annotation. If a library defines its own annotation and omits `@Retention`, its policy still defaults to `CLASS`, regardless of whether the annotation name looks like it is meant for runtime.

## 6. Are Omitting @Retention and Declaring @Retention(CLASS) Completely Identical?

Regarding **the retention policy of annotation usages**, the following two definitions have the same meaning:

```java
@interface A {}

@Retention(RetentionPolicy.CLASS)
@interface B {}
```

In both cases, the compiler applies the `CLASS` policy to the corresponding annotation. However, regarding **the annotation type declaration**, they are not identical:

- `A` does not have the `@Retention` meta-annotation declared.
- `B` has the `@Retention(CLASS)` meta-annotation explicitly declared.

Because `@Retention` is an annotation with `RUNTIME` retention, reflection code inspecting **the annotation type definition** directly can distinguish them:

```java
// Illustrative code in a context where A and B are already defined:
boolean aHasRetention = A.class.isAnnotationPresent(Retention.class); // false
boolean bHasRetention = B.class.isAnnotationPresent(Retention.class); // true
```

These two differing values **do not change the default policy**. If building a tool that reads annotation definitions, you must understand that an absent `@Retention` means `CLASS`, not "no policy".

In large projects, explicitly writing `@Retention(CLASS)` sometimes helps readers avoid having to remember the default value; omitting it remains completely valid in the language.

## 7. CLASS Retention, @Target, and @Inherited Are Different Concerns

An annotation can have multiple meta-annotations, but **each one answers a different question**.

| Meta-annotation | Answers the question | Changes the CLASS default? |
| --- | --- | --- |
| `@Retention` | Until which stage is the annotation retained? | Yes, if `SOURCE` or `RUNTIME` is specified; or explicitly declares `CLASS` |
| `@Target` | Which declaration/type-use kinds can it be attached to? | No |
| `@Documented` | Should API documentation generation tools display the annotation? | No |
| `@Inherited` | Within class annotation inheritance limits, can lookups from a superclass apply? | No |
| `@Repeatable` | Can an annotation type be repeated on the same element? | No |

Example:

```java
import java.lang.annotation.ElementType;
import java.lang.annotation.Target;

@Target(ElementType.TYPE)
@interface InternalType {}
```

`InternalType` has `@Target(TYPE)` but **no `@Retention`**, so it remains `CLASS`. Adding `@Documented` or `@Inherited` does not automatically promote it to `RUNTIME` either.

A `CLASS` annotation marked with `@Inherited` still cannot be read as a runtime annotation through commonly used reflection methods, because it does not have `RUNTIME` retention. If inherited lookup behavior at runtime is genuinely needed, consider the target, retention, and reflection query rules together.

## 8. Some Misconceptions to Avoid

### 8.1. "Without @Retention, It Is Not Stored Anywhere"

False. For most standard class/method/field declarations, **an annotation without `@Retention` is stored by the compiler as a `CLASS` annotation in the class file**. To prevent it from being stored in the class file per the retention policy, explicitly declare `SOURCE`.

### 8.2. "If It Is Already in the .class File, Java Reflection Can Read It"

False. `CLASS` is the exact example that demonstrates the difference. Class-file analysis tools can read the attributes intended for `CLASS`, whereas `Method.getAnnotation` only provides metadata retained for runtime according to the appropriate reflection mechanism.

### 8.3. "The Java Compiler Does Not Process CLASS Annotations"

False. The compiler must resolve the annotation type, check syntax, `@Target` applicability, and element types and values; the compiler and configured annotation processors can also read the annotation at compile time. **Not being readable by runtime reflection does not mean the compiler ignores it.**

### 8.4. "@Retention(CLASS) Applies to Every Annotation in a File"

False. `@Retention` applies to **each individual annotation type declaration**, not as a global setting for a file, package, or project. Two annotations defined in the same file can have different retentions.

### 8.5. "Changing CLASS to RUNTIME Only Requires Changing the Reflection Code"

False. The retention policy resides on the annotation type. To run reflection, the annotation must be defined with `RUNTIME`, and classes that use the annotation must also be recompiled when necessary so that metadata for those usages is written with the new policy. Using artifacts compiled under the old policy can cause the observed metadata to differ from expectations.

### 8.6. "For an Annotation to Work, RUNTIME Must Always Be Used"

False. Annotations processed by the compiler or build tools at compile time remain useful with `SOURCE` or `CLASS`. `RUNTIME` is only needed when a runtime component genuinely needs to access the metadata via a supported mechanism.

### 8.7. "When @Retention Is Absent, getAnnotation(Retention.class) Returns CLASS"

False. If you query **the `@Retention` meta-annotation on the annotation type itself** when that declaration lacks `@Retention`, `getAnnotation(Retention.class)` returns `null`. The default `CLASS` policy is defined by Java, not an implicit meta-annotation automatically added to the reflection object.

### 8.8. "Adding RUNTIME Is Sufficient for All Target Locations"

Inaccurate. Core Java reflection does not provide an API to inspect **local variable** declarations analogous to `Method`, `Field`, or `Parameter`. `@Target` and runtime observability must be considered by annotation location kind; `RUNTIME` does not automatically create a new reflection API.

## 9. Quick Verification Workflow in a Project

When encountering a custom-defined annotation and wanting to know whether it can be read at runtime:

1. **Open the `@interface` declaration.** Look for `@Retention` on that annotation type itself.
2. **If `@Retention` is absent, conclude policy = `CLASS`.** Do not infer it from the annotation's name or intended function.
3. **If `@Retention` is present, read the exact value.** `SOURCE`, `CLASS`, and `RUNTIME` differ in their lifecycles.
4. **Check `@Target` and the actual usage location.** The corresponding reflection API may be `Class`, `Method`, `Field`, `Parameter`, or `AnnotatedType`; not every location has a direct reflection object.
5. **Check the code/tool consuming the metadata.** Runtime reflection, annotation processors, and bytecode scanners have visibility into different forms of metadata.
6. **If still unclear, create a short example.** Use `javac` to compile, `javap -v` to observe bytecode, and `getAnnotation` to observe runtime reflection.

**Self-check question:** An annotation has `@Target(METHOD)`, no `@Retention`, and is used on `run()`. Which statements are true?

- The compiler can process it during compilation: **True**.
- It has the `CLASS` retention policy: **True**.
- It usually has metadata in the class file: **True**.
- `runMethod.getAnnotation(ThatAnnotation.class)` is guaranteed to return the annotation object: **False**.
- Adding `@Target(METHOD)` is enough to turn it into RUNTIME: **False**.

## 10. Practice Exercises

1. **Observe the default CLASS policy:** Compile `DefaultRetentionDemo.java`, then run `javap -v DefaultRetentionDemo`. Locate `DefaultTag` and `ClassTag` under `RuntimeInvisibleAnnotations`. Compare with the reflection result of `false` for both.
2. **Change retention:** Add `@Retention(RetentionPolicy.RUNTIME)` to the `DefaultTag` definition, recompile the entire file, and predict the four boolean values printed. After the change, the first value becomes `true`.
3. **Try SOURCE:** Change `ClassTag` to `@Retention(SOURCE)`. Use `javap -v` to explain why `ClassTag` is no longer in the method's metadata.
4. **Read the meta-annotation:** In a test file that defines `DefaultTag` and `ClassTag`, call `DefaultTag.class.getAnnotation(Retention.class)` and `ClassTag.class.getAnnotation(Retention.class)`. How do the results differ, and does that alter the policy of their usages?
5. **Design problem:** You create `@BusinessRule` for an annotation processor to check source code during build. Do you need the data in the class file after compilation? If not, consider `SOURCE`; if so, consider `CLASS`. If the application needs to read it via reflection at runtime, choose `RUNTIME` and explain the code that needs to consume the metadata.

**Key takeaway:** **Not declaring `@Retention` ⇒ `RetentionPolicy.CLASS`**. For annotations on standard declarations, the compiler keeps them in `.class`, but the Java Reflection API does not treat them as runtime-accessible annotations. Specify `@Retention(RUNTIME)` when runtime reflection is genuinely needed; choose `SOURCE` when the information is only needed during the compilation phase.
