# RetentionPolicy.CLASS: Annotations Are Stored in Class Files but Cannot Be Read by Standard Reflection

An annotation in Java can be useful **after compilation** without **needing to appear via Reflection when the program runs**. This is precisely what `RetentionPolicy.CLASS` means.

With the `CLASS` policy, the compiler writes information about the annotation usage into the `.class` file. Bytecode-reading tools can find that information, but standard Reflection APIs such as `Class.getAnnotation(...)`, `getDeclaredAnnotation(...)`, and `getDeclaredAnnotations()` **do not return annotations with `CLASS` retention**. This still holds when the JVM has loaded the class containing the annotation.

This is a common point of confusion: "present in the class file" and "queryable from a `Class<?>` object via Reflection" are **two different capabilities**.

## 1. Retention Determines Until Which Stage an Annotation Is Retained

Retention is the **retention policy for annotation metadata**. Java declares it using the `@Retention` meta-annotation in `java.lang.annotation`:

```java
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;

@Retention(RetentionPolicy.CLASS)
@interface BuildMarker {
}
```

Here:

- `BuildMarker` is an annotation type defined by us.
- `@Retention(RetentionPolicy.CLASS)` describes the retention policy of **usages of `@BuildMarker`**.
- `CLASS` keeps the metadata in the `.class` file generated by the compiler, but does not require the VM to make this annotation available to Reflection.
- This meta-annotation **does not directly produce business behavior**. Any tool that wants to process `BuildMarker` must read it and apply logic itself.

The three values of `RetentionPolicy`:

| Policy | Metadata on the compiled class | Standard Reflection at runtime | Example purpose |
| --- | --- | --- | --- |
| `SOURCE` | Not retained in `.class` | Not readable | Analysis/directives during the source code stage or annotation processing |
| **`CLASS`** | **Stored in `.class`** | **Not readable** | Tools that read or transform bytecode after compilation |
| `RUNTIME` | Stored in `.class` | Readable if an appropriate annotation is actually present | Programs/frameworks querying annotations via Reflection |

If `@Retention` is omitted on an annotation type, **the default value is `RetentionPolicy.CLASS`**, not `RUNTIME`. This is the default for an **annotation type declaration**, and it does not mean every standard Java annotation uses `CLASS`; each standard annotation can choose a different retention.

Keeping the annotation in the `.class` file allows the metadata to be used in bytecode processing steps without turning it into part of the Reflection runtime API.

## 2. Flow of an Annotation with CLASS Retention

Suppose we have:

```java
@Retention(RetentionPolicy.CLASS)
@Target(ElementType.TYPE)
@interface BuildHint {
    String value();
}

@BuildHint("verify-bytecode")
class Job {
}
```

When compiling `Job.java`:

1. The compiler parses the Java code and checks the syntax/type of `@BuildHint("verify-bytecode")`. For example, `value()` returns `String`, so a string is an appropriate value type.
2. The compiler generates the class file and writes the `BuildHint` metadata attached to `Job` according to the annotation representation in the class file.
3. A tool that knows how to read the class file structure can locate that metadata to analyze, index, or transform bytecode.
4. If running code calls `Job.class.getAnnotation(BuildHint.class)`, standard Reflection returns `null`. It does not expose the `@BuildHint` usage mentioned above.
5. No code is automatically invoked simply because the annotation appears in `.class`.

You can visualize it as:

```text
Job.java
  @BuildHint("verify-bytecode")
        |
        | javac: checks annotation usage
        v
Job.class
  has annotation metadata (CLASS)
        |
        +----> tool reading the class file directly: can see it
        |
        +----> JVM loads Job.class
                    |
                    +----> Job.class.getAnnotation(BuildHint.class)
                                   |
                                   v
                                  null
```

The deciding factor lies in **the mechanism the consumer uses to read metadata**:

- **Reading the class file/bytecode:** tools can read `CLASS` data.
- **Using standard Java Reflection on the loaded class:** does not return `CLASS` data.
- **Simply running the program:** no annotation processing happens automatically without explicit logic.

## 3. Runnable Java 17+ Example: A Single Class with SOURCE, CLASS, and RUNTIME

Create a single file **`ClassRetentionDemo.java`**:

```java
import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

@Retention(RetentionPolicy.SOURCE)
@Target(ElementType.TYPE)
@interface SourceHint {
}

@Retention(RetentionPolicy.CLASS)
@Target(ElementType.TYPE)
@interface ClassHint {
    String value();
}

// No @Retention declared: defaults to CLASS.
@Target(ElementType.TYPE)
@interface DefaultHint {
}

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.TYPE)
@interface RuntimeHint {
    String value();
}

@SourceHint
@ClassHint("bytecode")
@DefaultHint
@RuntimeHint("runtime")
class TaggedService {
}

public class ClassRetentionDemo {
    public static void main(String[] args) {
        Class<TaggedService> type = TaggedService.class;

        System.out.println(type.getDeclaredAnnotation(ClassHint.class));
        System.out.println(type.isAnnotationPresent(DefaultHint.class));
        System.out.println(type.getDeclaredAnnotation(RuntimeHint.class).value());
        System.out.println(type.getDeclaredAnnotations().length);

        // Reads the policy on the *annotation type*, not
        // the @ClassHint usage on TaggedService.
        System.out.println(
                ClassHint.class.getAnnotation(Retention.class).value());
    }
}
```

Set your terminal's working directory to the folder containing the file, then run with JDK 17+:

```bash
javac --release 17 ClassRetentionDemo.java
java ClassRetentionDemo
```

Exact stdout:

```text
null
false
runtime
1
CLASS
```

**Why does each line output this?**

1. `getDeclaredAnnotation(ClassHint.class)` returns `null` because **the `@ClassHint` usage on `TaggedService` has `CLASS` retention**.
2. `isAnnotationPresent(DefaultHint.class)` returns `false` because `DefaultHint` does not declare `@Retention` and therefore also uses `CLASS`.
3. `getDeclaredAnnotation(RuntimeHint.class).value()` returns `"runtime"` because the `@RuntimeHint` usage has `RUNTIME` retention.
4. `getDeclaredAnnotations().length` is `1`: on `TaggedService`, only `RuntimeHint` is visible to standard Reflection among the four annotations placed in the source.
5. `ClassHint.class.getAnnotation(Retention.class).value()` returns `CLASS`. **This is a different query:** it reads the `@Retention` annotation attached to **the definition of the `ClassHint` type**. `@Retention` itself is retained until runtime, so it can be read via Reflection. This does **not** turn usages of `@ClassHint` into annotations with `RUNTIME` retention.

The example uses annotation types in the same default package so it can run standalone in a single file. The file must be named `ClassRetentionDemo.java` because it contains `public class ClassRetentionDemo`.

## 4. Verifying That CLASS Metadata Is Actually in the .class File Using javap

After compiling the example above, inspect **the file of the annotated class itself**, not the file of the annotation type:

```bash
javap -v -p TaggedService
```

`javap` is a tool bundled with the JDK for inspecting class file information; `-v` displays bytecode/class file details, and `-p` includes private members when present.

In the details of **`TaggedService.class`**, look for the attributes named:

```text
RuntimeInvisibleAnnotations:
    ... ClassHint ...
    ... DefaultHint ...

RuntimeVisibleAnnotations:
    ... RuntimeHint ...
```

This is an **illustration of the structure to look for**, not a verbatim copy of `javap` output. Constant pool indices, how annotation names are printed, and display order may vary by JDK/compiler.

What the result means:

- `@ClassHint`: has been compiled into the class file, in the **`RuntimeInvisibleAnnotations`** attribute.
- `@DefaultHint`: is also in the **`RuntimeInvisibleAnnotations`** attribute because it does not declare `@Retention`.
- `@RuntimeHint`: is in the **`RuntimeVisibleAnnotations`** attribute.
- `@SourceHint`: has no corresponding annotation entry in `TaggedService.class`, because it has `SOURCE` retention.

Do not infer from the word "Runtime" in the attribute name that Java Reflection will see all metadata there. `RuntimeInvisibleAnnotations` is the official name of **the class-file attribute that stores annotations that are not visible at runtime via standard Reflection**. Conversely, `RuntimeVisibleAnnotations` contains runtime-visible annotations that Reflection can return according to the API's rules.

For further comparison, try:

```bash
javap -v -p ClassHint
```

This command inspects **`ClassHint.class`**, which is the annotation type definition. It can display the `@Retention(CLASS)` meta-annotation itself with the runtime-visible attribute of **`@Retention`**. Do not confuse information on the `ClassHint` definition with the `@ClassHint` usage on `TaggedService`.

### Why Is It Called RuntimeInvisibleAnnotations?

The class file format distinguishes two groups of annotations on declarations:

- `RuntimeVisibleAnnotations`: the VM must store/expose these appropriately so that runtime reflection APIs can access them according to the defined mechanism.
- `RuntimeInvisibleAnnotations`: the information resides in the class file, but the VM is not required to expose it to standard Reflection.

When an annotation is attached to a **method parameter** or a **type-use** location, the class file has corresponding specialized attributes, such as `RuntimeInvisibleParameterAnnotations` or `RuntimeInvisibleTypeAnnotations`. They follow the same idea of **visibility by retention**, but not every annotation resides in the declaration attribute `RuntimeInvisibleAnnotations`.

Therefore, when inspecting bytecode, select the right class and the right kind of annotated location. The main example above attaches annotations to a **class declaration**, so it uses `RuntimeInvisibleAnnotations` and `RuntimeVisibleAnnotations`.

## 5. Why Can't Reflection Read CLASS Metadata?

Java Reflection works through runtime representations such as `Class`, `Method`, `Field`, `Constructor`, and `Parameter`. Reflection's annotation-reading APIs, by the language/API contract, are designed for annotations with **`RetentionPolicy.RUNTIME`**.

Calls like the following do not open the `.class` file to decode all attributes of the class file format themselves:

```java
TaggedService.class.getAnnotation(ClassHint.class);           // null
TaggedService.class.getDeclaredAnnotation(ClassHint.class);   // null
TaggedService.class.isAnnotationPresent(ClassHint.class);     // false
```

These lines are **illustrative snippets placed inside a method/statement block**, using the types from Example 3.

Switching from `getAnnotation` to `getDeclaredAnnotation` or `getAnnotationsByType` **is not a trick to obtain `CLASS` annotations**. Those APIs differ mainly in how they consider directly declared, inherited, or valid repeatable annotations; they still obey runtime visibility.

If `ClassHint` must be accessed after compilation, a tool needs to work with the **class file structure** (for example, a bytecode reader), rather than simply switching to another method on `Class<?>`.

### Avoid Confusing "the JVM Does Not Store It" with "Reflection Does Not Return It"

`RetentionPolicy.CLASS` specifies that the metadata **is present in the compiled class file**. When the JVM loads the class file, it is not required to expose that metadata to Java Reflection. How the VM stores it internally once the class is loaded is an implementation detail; you should not infer a guarantee that `CLASS` data can be queried through the Reflection API.

Put accurately:

> `CLASS` is a policy of **storing information in the class file**; **it cannot be read via standard Reflection**, and no business behavior runs automatically simply because the metadata still exists.

## 6. Who Can Leverage CLASS Annotations?

Different consumers read annotations at different times:

| Timing | Reading method | Can utilize CLASS? | Notes |
| --- | --- | --- | --- |
| During source compilation | Compiler or annotation processor working on the element model | Yes | A configured processor can see annotations on source at compile-time |
| After compilation, before execution | Tool analyzing or transforming `.class` files | Yes | Can read `RuntimeInvisibleAnnotations` from bytecode |
| At startup/runtime, where a tool reads the class file bytes itself | Bytecode reader used by an application/framework | Yes, if the metadata is still in the bytes | This is **reading the class file**, not standard Java Reflection |
| At runtime, using `Class.getAnnotation(...)` | Java Reflection | **No** | Standard APIs only see appropriate annotations with `RUNTIME` |

**Example scenario:** a build tool scans class files to catalog components annotated with `@BuildHint`, or a bytecode tool reads the annotation to perform transformations. That tool can use `CLASS` information without instantiating the marked class.

A `CLASS` annotation does not automatically force the compiler to run a processor, does not automatically generate new source files, and does not automatically require a framework to scan class files. **The consumer must be specifically installed and activated**.

### Reflection and Bytecode Readers in the Same Application

A framework at runtime **can** choose to scan bytecode directly, obtain `CLASS` metadata, and then configure behavior. This does not contradict the statement "standard Reflection cannot read it." Both happen at runtime, yet they are **two different paths for accessing metadata**.

When reading framework documentation, you need to clearly distinguish whether the framework uses **Reflection** or a **class-file metadata reader**. From the mere fact that "the framework runs at startup," you cannot yet infer which mechanism it uses.

## 7. Is CLASS a Better Choice Than RUNTIME in All Cases?

No. Choose retention based on **the consumer's needs**.

Choose `CLASS` when the metadata is primarily intended for class-file-reading tools, bytecode instrumentation, build checks, or a pipeline that needs data in the binary without needing Reflection.

Choose `RUNTIME` if **the program expects to read the annotation via Java Reflection**. For example, an application writes:

```java
if (componentClass.isAnnotationPresent(ServiceMarker.class)) {
    // Actively register the component based on metadata.
}
```

If `ServiceMarker` has `CLASS` retention, this condition will evaluate to `false` because the annotation is not visible, even if the source has `@ServiceMarker`. If you want to check it via Reflection, you need to choose `RUNTIME` retention for `ServiceMarker`.

Choose `SOURCE` if the annotation is only needed at compile-time and does not need to be carried over into the class file.

| Specific need | Recommended retention |
| --- | --- |
| Annotation processor checking source conventions, no data needed in `.class` | `SOURCE` is usually sufficient |
| Post-compilation tool scanning `.class` to inspect/transform | `CLASS` |
| Java code calling `getAnnotation` at runtime | `RUNTIME` |
| Both bytecode tooling and Reflection are needed | `RUNTIME` |
| Consumer is not yet known | Identify the consumer and reading mechanism before choosing |

Retaining metadata across more stages can increase the amount of information carried in the artifact. However, **`CLASS` is not a security or secrecy mechanism**: the data is written in `.class`, so anyone with the class file and an appropriate tool can view it. Do not put secret keys, passwords, or tokens into annotation values assuming that because Reflection cannot read them, the data will be safe.

## 8. Two Independent Concepts: Retention and Target

An annotation often has both:

```java
@Retention(RetentionPolicy.CLASS)
@Target({ElementType.TYPE, ElementType.METHOD})
@interface BuildHint {
    String value();
}
```

- `@Retention(CLASS)`: **how long the metadata is retained and whether Reflection can see it**.
- `@Target({TYPE, METHOD})`: **which kinds of locations the annotation is allowed to be attached to**.

`TYPE` covers appropriate type declarations; `METHOD` is for methods. If you need to mark a parameter, use `ElementType.PARAMETER`; if you need a type-use position, use `ElementType.TYPE_USE`. Target affects valid placement locations and the corresponding class-file attribute format, and **does not change the retention policy**.

An annotation with target `TYPE` and retention `CLASS` still **does not automatically appear via Reflection** just because it is placed on a class. Conversely, an annotation with target `METHOD` and retention `RUNTIME` can be read from the right `Method` object via Reflection, provided the program locates the right method.

## 9. What Happens When @Inherited Is Present?

`@Inherited` is a meta-annotation that governs how **Reflection queries class annotations with `RUNTIME` retention** on subclasses in specific cases. It does not automatically promote `CLASS` to `RUNTIME`.

Example illustrating the policy:

```java
import java.lang.annotation.Inherited;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;

@Inherited
@Retention(RetentionPolicy.CLASS)
@interface Marker {
}

@Marker
class Parent {
}

class Child extends Parent {
}
```

Even with `@Inherited`, `Child.class.getAnnotation(Marker.class)` still cannot retrieve `Marker`. `Marker` itself has `CLASS` retention, so Reflection does not expose this annotation on `Parent`, and inheritance rules cannot make it appear.

`@Inherited` applies only to querying annotations on **classes and appropriate class inheritance relationships**, not as a mechanism that causes all annotations from interfaces/methods/fields to be inherited automatically. This is an independent aspect from the choice of metadata retention.

## 10. Factors That Can Cause CLASS Metadata to Disappear from Released Artifacts

A standard `javac` run with `RetentionPolicy.CLASS` writes the annotation according to the language/class file contract. However, if you inspect the final artifact in a multi-step pipeline, you must be aware that the class file may undergo further processing:

1. **Bytecode weaving/instrumentation:** tools read, modify, and rewrite the class file; depending on configuration, annotation data may be preserved or altered.
2. **Shrinking/obfuscation:** shrinking or transformation tools may strip attributes that are not requested to be kept.
3. **Class file replacement:** if the runtime is loading a different artifact/build than the one inspected with `javap`, the results do not reflect the same binary.
4. **Simply checking the wrong class:** annotations on methods/parameters/type-use may reside in another attribute, not in the class's top-level declaration section.

Therefore, when a user reports "`@Retention(CLASS)` is used, yet the tool cannot find it," check **the exact `.class` file output by the build**, the retention policy, the exact annotation location, and the transformation tool configuration. This differs from the case where Reflection returns `null`: when using Reflection with `CLASS`, `null` is the expected behavior.

## 11. Common Misconceptions

**"CLASS means the annotation only remains on `Class<?>` types."** False. The name `CLASS` here refers to **the data retention stage**, not `java.lang.Class` or `ElementType.TYPE`.

**"Once an annotation is stored in .class, `Class.getAnnotation` can definitely read it."** False. Reflection has its own runtime visibility contract. `CLASS` metadata can be read by class-file processing tools.

**"If `@Retention` is omitted, the default is `RUNTIME`."** False. The default is `CLASS`. This is why many custom annotations do not show up when queried via Reflection.

**"`@Inherited` enables Reflection to read CLASS annotations."** False. `@Inherited` does not override retention.

**"`RuntimeInvisibleAnnotations` means the class file does not contain the annotation."** False. This is in fact an attribute that **contains** annotations, though they are not exposed to standard Reflection.

**"`@Retention(RUNTIME)` will automatically execute the annotation's logic."** False. Even though the data is readable, there must be code or a framework that actively queries and processes it.

**"CLASS annotations are secret because they cannot be read via Reflection."** False. Anyone who has the class file can analyze the bytecode and see the metadata.

**"Running a framework at runtime means it can only read via Reflection."** False. A framework can read the class file bytes itself; you need to check its specific mechanism rather than guessing from its execution timing.

## 12. Self-Check

### Question 1: Reading the Output

In the `ClassRetentionDemo` example in Section 3, why does `type.getDeclaredAnnotation(ClassHint.class)` return `null` while `javap -v -p TaggedService` can still display `ClassHint`?

**Hint:** the two reading methods use two different layers of APIs: runtime Reflection and a class-file reader.

### Question 2: Default Retention

If you omit `@Retention` entirely on a custom annotation type, what policy will it have? Can you call `getAnnotation` to read a usage of that annotation on a class?

**Answer:** `CLASS`; the usage is not exposed via standard Reflection.

### Question 3: Choosing a Design

Tool A inspects metadata after compilation by reading `.class` directly. Program B calls `SomeClass.class.getAnnotation(Flag.class)` at runtime. If both use `@Flag`, which retention satisfies both?

**Answer:** `RUNTIME`, because the class file still contains the metadata and Reflection also needs to see it.

### Question 4: Analyzing Bytecode Attributes

Suppose `@Hint` is attached directly to a class and has `@Retention(CLASS)`. In the `javap -v` output of **that class**, should you look for `RuntimeInvisibleAnnotations` or `RuntimeVisibleAnnotations`?

**Answer:** `RuntimeInvisibleAnnotations`. For annotations in other locations such as parameter/type-use, you must look up the corresponding specialized attribute.

### Question 5: Meta-Annotation of the Annotation Type Itself

Why can `ClassHint.class.getAnnotation(Retention.class).value()` return `CLASS` even though `TaggedService.class.getAnnotation(ClassHint.class)` returns `null`?

**Answer:** the first query reads `@Retention` **on the `ClassHint` definition**, while the second query reads **the `@ClassHint` usage on `TaggedService`**. The two queried annotations are two different metadata items with different retention policies.

### Question 6: A Practical Mistake

You use `@Retention(CLASS)` for `@AutoRegister`, and then write runtime code:

```java
if (MyComponent.class.isAnnotationPresent(AutoRegister.class)) {
    register(MyComponent.class);
}
```

Why is the `register` method not called based solely on that annotation? If you want to continue using Reflection, what needs to be changed?

**Answer:** `isAnnotationPresent` is Reflection and does not see `CLASS` annotations. If you want to detect it via Reflection, `@AutoRegister` must have `RUNTIME` retention (and the program still needs to actively invoke the registration logic). Another option is to design a mechanism that reads metadata directly from bytecode, though that is a different processing approach.

## 13. Checklist When Designing or Debugging CLASS Retention

1. **Who is the consumer?** A compiler/annotation processor, a bytecode tool, or Reflection?
2. **When is it read?** During source compilation, after compilation, or when the program runs?
3. **What retention does the annotation type declare?** If none is declared, remember that `CLASS` is the default.
4. **Are you inspecting the right class file?** For a class declaration, look for the exact `RuntimeInvisibleAnnotations` attribute in the annotated class's file.
5. **Is there any artifact transformation tool?** Inspect the final binary actually used by the tool or the JVM.
6. **Are you confusing querying `@Retention` on the annotation type with querying a usage of that annotation?**
7. **Are you expecting Reflection to read `CLASS`?** If so, revisit the requirement and choose `RUNTIME` or change the reading mechanism.
8. **Is the consumer actually implemented?** An annotation by itself is metadata; it does not automatically enable application functionality.

The takeaway for `RetentionPolicy.CLASS` is very concrete: **annotations are preserved in the class file so that tools needing bytecode can leverage them, while not appearing via standard Java Reflection at runtime**. Understanding this boundary clearly helps you choose the right retention and avoid puzzling `getAnnotation(...) == null` bugs when designing custom annotations.
