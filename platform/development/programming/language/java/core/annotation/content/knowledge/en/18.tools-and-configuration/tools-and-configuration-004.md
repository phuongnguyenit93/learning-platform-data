# javac: -processor, -processorpath, and --processor-module-path

Java has a compile-time **annotation processing** mechanism. An annotation processor implements the §javax.annotation.processing.Processor§ interface (typically extending §AbstractProcessor§), reads source declarations through the compiler model, and can check for errors, emit diagnostics, or generate sources/resources. For a processor to actually run, it is necessary to distinguish between **which processor to select** and **where javac looks for that processor**.

Three main options:

- **§-processor§**: specifies the **fully qualified names of the processor classes** to run, for example §-processor tools.LogProcessor§. This is an **explicit selection** mechanism that bypasses the default auto-discovery process.
- **§-processorpath§** or its long form **§--processor-path§**: declares the **path containing the processor classes/JARs and dependencies** when they are loaded via the **classpath/unnamed module**.
- **§--processor-module-path§**: declares the **module path dedicated to processors packaged as named modules**. Processor modules must provide the §javax.annotation.processing.Processor§ service with an appropriate §provides ... with ...§ declaration.

They are not three different ways of writing the same option. A single command may need to both specify the **processor to run** and declare **where to find the processor**, while choosing either the classpath or JPMS mechanism to match how the processor is packaged.

## 1. Distinguishing the application classpath from the processor search path

A Java compilation command works with **two logical environments**:

1. **Compilation environment**: the sources and dependencies that the application source code is allowed to reference, configured with §-classpath§/§--class-path§ or §--module-path§ and the appropriate source paths.
2. **Processor runtime environment**: the processor classes and libraries that **javac must load to run during compilation itself**, configured with §-processorpath§ or §--processor-module-path§.

Example:

~~~bash
javac --release 17 -cp libs/app-api.jar -processorpath tools/processor.jar -processor tools.LogProcessor -d out src/demo/Example.java
~~~

This is an **illustrative command** (the corresponding paths/JARs must exist). It means:

- §-cp libs/app-api.jar§: the application is compiled with the API contained in §app-api.jar§.
- §-processorpath tools/processor.jar§: javac loads the processor implementation from §processor.jar§.
- §-processor tools.LogProcessor§: runs the processor with the class name §tools.LogProcessor§.
- §--release 17§: compiles source/APIs targeting Java 17.
- §-d out§: writes the application's class files to the §out§ directory.

**Do not assume that §-cp§ and §-processorpath§ are a single path.** They serve different functions. If **no processor path is declared**, in classpath mode javac can search for processors on the **user classpath** when discovery is enabled. However, once §-processorpath§ is set, that path determines the processor classpath search area; missing a required processor dependency there can cause §ClassNotFoundException§/§NoClassDefFoundError§ when loading the processor, even if the app compilation classpath contains a similar-looking dependency.

### Quick reference table

| Option | Role | Typical value |
| --- | --- | --- |
| §-processor tools.P1,tools.P2§ | Selects the names of processors to run | Comma-separated list of **binary class names** |
| §-processorpath path§ | Where to find processors and dependencies on the classpath | Class directory or JAR |
| §--processor-path path§ | Long form of the processor path | Same as §-processorpath§ |
| §--processor-module-path path§ | Where to find **named processor modules** | Directory containing module artifacts or modular JAR |
| §-cp path§, §--class-path path§ | Classpath of the code **being compiled** | App API/dependency |
| §--module-path path§ | Module path of the code **being compiled** | Application JPMS dependencies |
| §-proc:none§ | Disables annotation processing | No processor runs |
| §-proc:only§ | Performs annotation processing only, without compiling application class files | Validation/source generation |
| §-proc:full§ | Performs annotation processing and then compiles | Processing + compilation |
| §-Akey=value§ | Passes an option to a processor | §-Amode=explicit§ |
| §-s dir§ | Where to store source files generated by processors | §-s generated§ |
| §-d dir§ | Where to store class files generated by javac | §-d classes§ |

**Path separators:** for a processor path containing multiple entries, Windows uses §;§ and Linux/macOS use §:§. Paths must follow how the shell/OS interprets them. The example commands in this article use §/§ for file names and a single path, so they can be easily applied across multiple environments.

## 2. -processor: explicitly selecting a processor by class name

Syntax:

~~~bash
javac -processor tools.LogProcessor -processorpath build/classpath-processor -d build/app src/demo/Example.java
~~~

This is a **complete command once the files from the example in Section 5 have been prepared**. §-processor§ takes one or more **fully qualified class names** of processors, separated by commas **with no spaces needed**:

~~~bash
javac -processor tools.FirstProcessor,tools.SecondProcessor -processorpath build/processors -d build/app src/demo/Example.java
~~~

The second command is **for syntax illustration only**: two processor classes with those exact names and valid constructors/providers must actually exist.

Points to remember:

- §-processor§ is a **class name**, not an annotation name (§@Generate§), not a module name, and not a path to a JAR.
- If the processor class does not exist on the processor search path or does not implement §Processor§ properly, javac reports an error before or during processing.
- Using §-processor§ makes builds reproducible: the list of processors is selected explicitly, rather than accidentally loading every discovered provider.
- A processor typically needs an accessible no-argument constructor and must implement §javax.annotation.processing.Processor§ (directly or through §AbstractProcessor§).
- §-processor§ **bypasses the default discovery mechanism**. Therefore, in examples using §-processor§, a §META-INF/services/...§ file is **not required**.
- A processor specified by §-processor§ still operates across processing rounds and selects annotations based on §getSupportedAnnotationTypes()§/§@SupportedAnnotationTypes§.

Distinguish this from §-Akey=value§: §-A§ does not select a processor, but instead provides a configuration value via §processingEnv.getOptions()§ **for a processor that has already been selected/loaded**.

## 3. -processorpath: finding processors on the classpath

The short name §-processorpath§ and the long name §--processor-path§ serve the same role. A path can point to:

- A compiled directory containing the processor's §.class§ files.
- A JAR containing the processor implementation.
- Multiple directories/JARs separated by the path separator appropriate for the operating system.
- Dependencies required for the **processor to run** (not just for the application source to compile).

If the processor is in the §build/classpath-processor§ directory, the command:

~~~bash
javac --release 17 -processorpath build/classpath-processor -processor tools.LogProcessor -d build/app src/demo/Example.java
~~~

will instruct javac to load §tools.LogProcessor§ from the processor path. In Section 5, the processor actually resides in package §tools§, so the class file has a corresponding path such as §build/classpath-processor/tools/LogProcessor.class§.

### Auto-discovering processors on the classpath

If §-processor§ is **not** used, javac can discover processors on the processor path using the Java service provider mechanism. For a regular classpath/JAR, the following resource is needed:

~~~text
META-INF/services/javax.annotation.processing.Processor
~~~

The contents of that file list provider classes, one fully qualified class name per line:

~~~text
tools.LogProcessor
~~~

When §META-INF/services/javax.annotation.processing.Processor§ **is packaged inside the processor JAR/directory on the processor path**, javac can discover that provider if annotation processing is enabled. The service file has a special location; it is **not a Java source file** and **not an annotation type**.

Two common approaches:

1. **Explicit selection:** §-processor tools.LogProcessor -processorpath ...§. Does not require a service file.
2. **Discovery on the processor path:** provide the §META-INF/services/...§ resource and configure §-processorpath ...§; javac finds the registered processors.

For builds requiring processor source control and security, you should use explicit configuration or a clear list of processor dependencies, rather than depending on a JAR unexpectedly containing a service provider.

### Notes for JDK 23 and later

**Starting in JDK 23**, javac **no longer implicitly runs annotation processing simply because a processor is found on the classpath without a processing configuration option**. This change prevents processor code from being executed automatically just from adding a dependency.

**Configure it explicitly** using §-processor§, §--processor-path§, §--processor-module-path§, or enable §-proc:full§/§-proc:only§ when appropriate. Specifying §--processor-path§ with a service provider is indeed one way to request processing. With JDK 17/21/22, some older setups may implicitly process processors from the classpath; do not rely on that behavior for builds that need to work across multiple JDKs.

§-proc:full§ was introduced in JDK 21 and has been backported to many update releases of older JDK lines, including certain JDK 17u releases. If an environment uses a very old JDK 17 build that does not recognize §-proc:full§, use explicit configuration with §-processor§ and the processor path, or check the JDK update release being used.

## 4. --processor-module-path: finding a processor as a named JPMS module

When a processor is packaged as a **named module**, use:

~~~bash
javac --processor-module-path build/modules -d build/app src/demo/Example.java
~~~

Unlike §-processorpath§, §--processor-module-path§ requires artifacts following the **Java Platform Module System (JPMS)**. A processor in a named module must declare that it provides the §javax.annotation.processing.Processor§ service.

Example §module-info.java§:

~~~java
module demo.processor {
    requires java.compiler;
    provides javax.annotation.processing.Processor
        with tools.LogProcessor;
}
~~~

Meaning:

- §module demo.processor§: the processor's module name.
- §requires java.compiler§: allows the module to use §javax.annotation.processing§ and §javax.lang.model§ from the JDK module §java.compiler§.
- §provides javax.annotation.processing.Processor with tools.LogProcessor§: registers the §tools.LogProcessor§ implementation for the javac environment's ServiceLoader.
- §exports tools§ is not needed just to provide the processor service to javac; §provides§ is a separate mechanism for providers.

**A module name is not a processor class name.** In the example, the module name is §demo.processor§, while the class name is §tools.LogProcessor§. Do not pass §-processor demo.processor§ just because that is the module name; §-processor§ uses the processor class name.

### Distinguishing --module-path and --processor-module-path

| Configuration | What purpose does it serve? |
| --- | --- |
| §--module-path app-modules§ | Modules that the **application source** needs during compilation |
| §--processor-module-path processor-modules§ | Modules containing **annotation processors** and dependencies for javac to load/run |

Both kinds of modules can coexist in a single build, but belong to two different roles. For example, an application in an **unnamed module/classpath** can still be processed by a processor packaged in a **named module**; the runnable example in Section 6 demonstrates this case.

When a processor module has dependencies, the corresponding dependency modules must be placed on the processor module path. The app's §-cp§ does not automatically add them to the processor layer.

## 5. Runnable example A — classpath processor with -processor and -processorpath

Create the directory structure:

~~~text
project/
├── src/
│   ├── processor/
│   │   ├── module-info.java
│   │   └── tools/
│   │       └── LogProcessor.java
│   └── app/
│       └── demo/
│           └── Example.java
└── build/
    ├── classpath-processor/
    ├── classpath-app/
    ├── modules/
    │   └── demo.processor/
    └── module-app/
~~~

The §build/...§ directories are **output directories** created before running javac. Specifically, JDK javac does not automatically create every directory passed to §-d§, so create §build/classpath-processor§, §build/classpath-app§, §build/modules/demo.processor§, and §build/module-app§ beforehand. In this section, only §LogProcessor.java§ and §Example.java§ are needed; the §module-info.java§ file is used in Section 6.

### File src/processor/tools/LogProcessor.java

~~~java
package tools;

import java.util.Set;
import javax.annotation.processing.*;
import javax.lang.model.SourceVersion;
import javax.lang.model.element.TypeElement;

@SupportedAnnotationTypes("*")
@SupportedSourceVersion(SourceVersion.RELEASE_17)
@SupportedOptions("mode")
public final class LogProcessor extends AbstractProcessor {
    private boolean printed;

    @Override
    public boolean process(Set<? extends TypeElement> annotations,
                           RoundEnvironment round) {
        if (!printed && !round.processingOver()) {
            TypeElement sample = processingEnv.getElementUtils()
                    .getTypeElement("demo.Example");
            if (sample != null) {
                System.out.println("processor=" + sample.getQualifiedName());
                System.out.println("mode=" +
                    processingEnv.getOptions().getOrDefault("mode", "none"));
                printed = true;
            }
        }
        return false;
    }
}
~~~

Notable points:

- §@SupportedAnnotationTypes("*")§ declares that the processor can receive all annotation types; this is a setup so the demo runs easily on source without custom annotations, not a choice that should be used by default for every production processor.
- §@SupportedSourceVersion(RELEASE_17)§ declares the source version that the processor supports.
- §@SupportedOptions("mode")§ declares that the processor accepts the §mode§ option; the value is obtained via §processingEnv.getOptions()§.
- §printed§ ensures there is no duplicate logging across multiple processing rounds.
- §process§ returns §false§ so as not to claim all annotations from other processors.
- §Elements.getTypeElement("demo.Example")§ only needs the model from javac, without needing to run the §Example§ class.

With real tools, you should use §Messager§ to report diagnostics instead of §System.out§, and clearly define the scope of annotations to process.

### File src/app/demo/Example.java

~~~java
package demo;

public class Example {
    public static void main(String[] args) {
        System.out.println("app=ok");
    }
}
~~~

The §Example.java§ file has no custom annotations. The processor is activated through the compiler options and §@SupportedAnnotationTypes("*")§.

### Step 1: compile the classpath processor

In the §project§ directory, after creating the output directories:

~~~bash
javac --release 17 -encoding UTF-8 -d build/classpath-processor src/processor/tools/LogProcessor.java
~~~

After this step, the path containing the processor's bytecode is §build/classpath-processor/tools/LogProcessor.class§.

### Step 2: use the processor during app compilation

~~~bash
javac --release 17 -encoding UTF-8 -processorpath build/classpath-processor -processor tools.LogProcessor -Amode=explicit -d build/classpath-app src/app/demo/Example.java
~~~

**Exact stdout of the second javac command (tested on JDK 24 with §--release 17§):**

~~~text
processor=demo.Example
mode=explicit
~~~

This command **runs the processor** and also compiles §Example.java§ into a class file at §build/classpath-app/demo/Example.class§.

Now run the application:

~~~bash
java -cp build/classpath-app demo.Example
~~~

**Application's own stdout:**

~~~text
app=ok
~~~

The two different outputs show a fundamental distinction: **the processor runs in javac's JVM at compile time**, whereas §main§ runs later in the application's JVM. The processor does not automatically run again each time the application starts.

## 6. Runnable example B — the same processor packaged in a named module

Keep §LogProcessor.java§ and §Example.java§ identical to Section 5. Add the following file.

### File src/processor/module-info.java

~~~java
module demo.processor {
    requires java.compiler;
    provides javax.annotation.processing.Processor
        with tools.LogProcessor;
}
~~~

This is the source module declaration for javac to build a **named processor module**. §provides ... with ...§ is how ServiceLoader discovers the implementation. There is no need to create a §META-INF/services/javax.annotation.processing.Processor§ file for this module.

### Step 1: compile the processor module

~~~bash
javac --release 17 -encoding UTF-8 -d build/modules/demo.processor src/processor/module-info.java src/processor/tools/LogProcessor.java
~~~

Output structure after compiling:

~~~text
build/
└── modules/
    └── demo.processor/
        ├── module-info.class
        └── tools/
            └── LogProcessor.class
~~~

The §build/modules§ directory is where javac looks for modules; each subdirectory such as §demo.processor§ is an exploded module. An exploded module can be replaced with a modular JAR placed on the processor module path.

### Step 2: use --processor-module-path

~~~bash
javac --release 17 -encoding UTF-8 --processor-module-path build/modules -Amode=module -d build/module-app src/app/demo/Example.java
~~~

**Exact stdout of the app compilation command (tested with JDK 24, §--release 17§):**

~~~text
processor=demo.Example
mode=module
~~~

This output confirms that javac finds the processor from the named module with the provider declared in §module-info.class§. The §Example§ application still does not need its own §module-info.java§; the application is compiled as a classpath application in the example.

If you simply replace the command above with:

~~~bash
javac --release 17 -encoding UTF-8 --module-path build/modules -d build/module-app src/app/demo/Example.java
~~~

then you are **not** configuring the processor module path. §--module-path§ here is the **application's dependency path**, not a replacement for §--processor-module-path§. This is a **configuration comparison snippet**, not a command expected to produce §processor=...§ on stdout.

### Is -processor still needed when provides is already present?

In this example, it is **not needed**, because §--processor-module-path§ together with the §provides§ service declaration is sufficient for the processor to be discovered. If you want to specify exactly one or more processors for the build, you can add the appropriate processor names via §-processor§ according to the contract of the javac version in use.

The “named processor module” property pertains to the **processor's path and module descriptor**, independent of whether the application uses the classpath or JPMS.

## 7. -proc:none, -proc:only, and -proc:full

Three very useful modes when debugging or configuring a build:

| Value | Annotation processing | Compiling application class files |
| --- | --- | --- |
| §-proc:none§ | No | Yes, if the source is valid |
| §-proc:only§ | Yes | Does not run the compilation step to produce application class files |
| §-proc:full§ | Yes | Yes |

Reusing the classpath processor from Section 5:

### Running compilation with the processor disabled

~~~bash
javac --release 17 -encoding UTF-8 -proc:none -processorpath build/classpath-processor -d build/no-process src/app/demo/Example.java
~~~

**No §processor=...§ on stdout**: only the app is compiled. In the example, the command succeeds and the application's class file can be generated in §build/no-process§. §-proc:none§ is a flag that actively **disables annotation processing**, even if a processor is present on the processor path.

### Running only the processor without generating application class files

~~~bash
javac --release 17 -encoding UTF-8 -proc:only -processorpath build/classpath-processor -processor tools.LogProcessor -Amode=only -d build/proc-only src/app/demo/Example.java
~~~

**Stdout:**

~~~text
processor=demo.Example
mode=only
~~~

In this mode, javac does not generate §build/proc-only/demo/Example.class§. However, if the processor is designed to generate **source/resource files**, the annotation processing phase can still produce those artifacts depending on the processor logic and the §-s§/§-d§ options.

### Full processing and compilation

§-proc:full§ requests both annotation processing and compilation. Check the javac version before using it on older JDK 17 releases because the §full§ value was backported to certain update releases. In the demo with an explicit §-processor§, there is no need to add §-proc:full§ to get processing+compilation when using a modern javac version.

## 8. ServiceLoader: different registration rules between the two mechanisms

| Criterion | Processor classpath | Named processor module |
| --- | --- | --- |
| Path | §-processorpath§/§--processor-path§ | §--processor-module-path§ |
| Automatic registration | §META-INF/services/javax.annotation.processing.Processor§ | §provides javax.annotation.processing.Processor with ...§ in §module-info.java§ |
| Direct processor selection | §-processor tools.LogProcessor§ | Can specify the appropriate processor class name |
| Dependency location | Classpath for the processor | JPMS modules for the processor |
| Module descriptor required? | No | Yes, to be an explicit named module with a provider declaration |
| Must app be a named module? | No | **No**; the module processor demo processes a classpath app |
| Result | Processor runs during compilation | Processor runs during compilation |

**Common warning:** merely having §@SupportedAnnotationTypes§ on a processor is **not enough for it to be auto-discovered**. §@SupportedAnnotationTypes§ determines which annotations the processor receives **after it has been loaded/instantiated**; a ServiceLoader resource, §-processor§, or named-module §provides§ is what solves **finding and loading the implementation**.

Within the same source project, you can build the processor for either the classpath or a named module; **do not mix mismatched metadata**. When copying a JAR to the processor module path, check that it has a §module-info.class§ with §provides§ or has an appropriate module/service registration mechanism. A classpath JAR with a §META-INF/services§ resource does not automatically become an explicit named module with a proper module descriptor.

## 9. Options -A, -s, -d, and -XprintRounds/-XprintProcessorInfo

Annotation processors typically receive configuration via §-Akey=value§:

~~~bash
javac --release 17 -processorpath build/classpath-processor -processor tools.LogProcessor -Amode=debug -d build/classpath-app src/app/demo/Example.java
~~~

In code, §processingEnv.getOptions().get("mode")§ returns §debug§. To avoid compiler warnings about unrecognized options, the processor should declare §@SupportedOptions("mode")§ or override §getSupportedOptions()§.

Some additional options:

- **§-d dir§**: sets the class output directory. Create the output directory beforehand; processors writing classes/resources to the corresponding Filer output location may depend on this configuration.
- **§-s dir§**: sets the generated source output directory. Used when a processor generates §.java§ files; it is not a processor search path.
- **§-XprintRounds§**: displays annotation processing rounds, especially useful when a processor generates sources that trigger additional rounds.
- **§-XprintProcessorInfo§**: displays which processor is invoked and which annotations it is asked to process; used to diagnose why a processor does not run or does not receive the expected annotation types.

Example to clearly observe what javac executes:

~~~bash
javac --release 17 -XprintRounds -XprintProcessorInfo -processorpath build/classpath-processor -processor tools.LogProcessor -Amode=inspect -d build/classpath-app src/app/demo/Example.java
~~~

**Do not treat the output of debug flags as fixed stdout for this article**: it may vary across JDKs, annotations in the source, and the number of processing rounds. When automated testing is needed, assert on the functional output §processor=...§, generated files, or compiler diagnostics rather than relying on individual javac log lines.

## 10. Diagnostic workflow when a processor does not run

### Case 1: Processor is in dependencies, but there is no result

First, check whether annotation processing is **explicitly** enabled, especially on JDK 23+. For a classpath processor when you want exact selection, use §-processor tools.LogProcessor -processorpath ...§. For a named module, use §--processor-module-path ...§ and ensure the module declares §provides§.

### Case 2: javac reports processor not found

Common error example:

~~~text
error: Annotation processor 'tools.LogProcessor' not found
~~~

The exact message depends on the javac version. Check:

- Whether the class name includes the full package, for example §tools.LogProcessor§ rather than §LogProcessor§.
- Whether the class file/JAR actually exists under the processor path/module path.
- Whether the processor and its dependencies were **compiled beforehand** before compiling the app source.
- Whether the class implements §javax.annotation.processing.Processor§ and has an appropriate public/no-arg constructor.
- If using the module path, whether §module-info.class§ contains §provides ... with ...§.

Do not fix this by blindly dumping all libraries onto the app classpath: you must distinguish between the compilation environment and the processor runtime environment.

### Case 3: Processor is present, but does not process the expected annotation

§-processor§ only ensures that javac attempts to load/run the processor; which annotations are processed is determined by §getSupportedAnnotationTypes()§. If the processor only supports §com.example.Check§ while the source uses a different annotation, the processor may not be invoked for the expected annotation. Check:

- The package/name of the annotation must match exactly.
- The source annotation has a valid §@Target§ at its usage site.
- The compiler is compiling the right source and classes paths.
- Whether §@SupportedSourceVersion§ matches the language level.
- Round behavior and which processor claims the annotation.
- §-XprintRounds§ and §-XprintProcessorInfo§ to inspect the flow.

### Case 4: ClassNotFoundException or NoClassDefFoundError when the processor runs

A processor may depend on third-party libraries **used only while the processor is running**. If that library is not on the processor search path, loading the processor will fail even if app dependencies are complete. Place the library in the right location:

- Classpath processor: add the JAR to §-processorpath§ using the OS separator.
- Named processor module: add the dependency modules to §--processor-module-path§ and declare §requires§ in the module descriptor according to the proper JPMS relationships.

Do not assume that the application's §--module-path§ will automatically satisfy every processor runtime dependency.

### Case 5: Two processors both generate the same file

ServiceLoader may discover multiple processors from different JARs. If both generate the same source name via §Filer§, javac can report a duplicate file creation error. Restrict the processor list using §-processor§, narrow processor dependencies, or adjust the processors' contracts.

### Case 6: Using -proc:only and not seeing the application's .class files

This is the **correct** behavior of §-proc:only§. To compile the app after processing, omit §-proc:only§ or run another compilation pass. Use §-proc:full§ when the javac version supports it, or run a command with an explicit §-processor§ in the default processing + compilation mode.

### Case 7: Using --module-path instead of --processor-module-path

§--module-path§ provides application modules; it does **not** equate to searching for processor providers. Choose §--processor-module-path§ for named processor modules and check §provides javax.annotation.processing.Processor with ...§.

## 11. When to choose each strategy?

**Strategy A — Processor classpath with explicit -processor**

Suitable for an internal tool, annotation processing exercises, small builds, or a compilation process where you need to know the exact processor running:

~~~bash
javac --release 17 -processorpath build/classpath-processor -processor tools.LogProcessor -d build/classpath-app src/app/demo/Example.java
~~~

Pros: easy to understand, no service metadata needed, easy to reproduce issues. Cons: processor names and dependencies must be explicitly configured.

**Strategy B — Processor classpath using service auto-discovery**

Suitable when distributing a processor JAR packaged with a service provider resource and the build explicitly manages processor dependencies. §-processor§ is not required, but you must configure the processor path and enable processing accordingly. Use §-XprintProcessorInfo§ to observe what gets discovered.

**Strategy C — Named processor module**

Suitable for build tooling that has modularized the processor and its dependencies according to JPMS. Use §--processor-module-path§ and a §module-info.java§ with §provides§. This is a separation of the processor runtime layer, not a requirement that the application itself must be a named module.

In CI or security-sensitive builds, processors are **code that javac can execute during the build**. Allow only trusted processors/JARs, pin dependency versions, control search paths, and do not assume “annotation processing only reads metadata so no code gets executed”.

## 12. Knowledge self-check

**1. How does §-processor§ differ from §-processorpath§?** §-processor§ selects the implementation class name to run; §-processorpath§ tells javac where to find that class and its dependencies when using a classpath-based processor.

**2. When adding §my-processor.jar§ to the app's §-cp§, does the processor always run?** You cannot assume so. Discovery, service metadata, search path, JDK version, and whether processing is requested determine whether the processor runs. Starting in JDK 23, processing must be configured explicitly.

**3. For a named processor module, which file declares the service provider?** §module-info.java§, using §provides javax.annotation.processing.Processor with tools.LogProcessor;§ in the module descriptor.

**4. Does §--module-path§ replace §--processor-module-path§?** No. The former serves module dependencies of the application source; the latter serves annotation processors in named modules.

**5. When using §-proc:only§, can the §Example§ program be run immediately afterward?** Not unless an application class file already exists from another compilation step, because §-proc:only§ does not perform compilation to produce §Example.class§.

**6. What should be used to pass the string §mode=debug§ to a processor?** §-Amode=debug§; read it via §processingEnv.getOptions()§ and you should declare §@SupportedOptions("mode")§.

**7. In whose runtime does a processor run?** It is loaded and executed by javac **during compilation**, in a different JVM from the one that runs §demo.Example.main§ afterward.

**8. Is having §@SupportedAnnotationTypes("*")§ sufficient for ServiceLoader to find a processor automatically?** No. Registration is required via a §META-INF/services§ file on the processor classpath, §provides§ in a named module, or specifying §-processor§ explicitly.

**Conclusion:** ask in order **“which processor should run?”** (§-processor§), **“where should it be found?”** (§-processorpath§ if classpath, §--processor-module-path§ if named modules), and **“in what mode should annotations be processed?”** (§-proc:none/only/full§ or the corresponding explicit configuration). When these three answers are clear, an annotation processing build becomes more stable, easier to debug, and less dependent on javac's implicit discovery mechanism.
