# Distinguishing Inherited Method Lookup from Method Annotation Inheritance in Java

In Java, there are two questions that are easily mistaken for the same one:

1. **Can a subclass find a method inherited from a superclass or interface via reflection?**
2. **If the subclass overrides that method, do annotations on the parent method automatically appear on the overriding method?**

The answers are, respectively, **yes under the appropriate method lookup conditions**, and **no under standard Java reflection**. For example, `Child.class.getMethod("run")` can return a `Method` **declared in `Parent`**. When reading annotations from that `Method`, you see the original annotation because you are holding the exact reflection object of the **parent method**. However, when `Child` declares its own `run()` to override it, `getMethod("run")` returns **Child's** method; annotations present only on `Parent.run()` are not automatically transferred.

This topic covers **reflection lookup rules and annotation ownership**. It is especially important for frameworks that use method annotations for endpoint registration, validation, logging, authorization, or execution time measurement.

## 1. Three Concepts to Keep Separate

**Method inheritance** is a Java language mechanism: a subclass can use eligible non-private instance methods from its superclass, and can inherit methods from interfaces, including default methods. Access scope, overriding, interface resolution, and related rules determine which members are actually inherited. Not every method declared on a superclass is a method inherited by the subclass.

**Method lookup via reflection** is the use of APIs such as `Class.getMethod(...)`, `Class.getMethods()`, and `Class.getDeclaredMethod(...)` to obtain a `java.lang.reflect.Method` object. These APIs have different search scopes: public members including inherited methods, or only methods declared directly in a single class/interface.

**Method annotation inheritance** is a separate rule. Java has no general rule that automatically copies annotations from an overridden method down to an overriding method. Java's `@Inherited` meta-annotation only has meaning when querying annotations on a **class declaration** across superclasses according to the `java.lang.annotation.Inherited` contract.

Something that seems contradictory yet is completely accurate:

> It is possible to **find a method declared by a superclass** and then read the annotation on that method itself, while **method annotations are never inherited onto a new method**.

## 2. Comparing APIs for Retrieving a Method

| API | Search Scope | Retrieves Inherited Methods? | Notes |
| --- | --- | --- | --- |
| `SomeType.class.getMethod("name", parameterTypes...)` | **Public method** matching the name and parameter types | **Yes**, via public member lookup across the class, superclasses, and superinterfaces | Returns the `Method` belonging to where the selected method is declared; throws `NoSuchMethodException` if not found |
| `SomeType.class.getMethods()` | Set of **public methods** of the class/interface, including inherited public members | **Yes** | Array order is not guaranteed; may include synthetic/bridge methods generated by the compiler |
| `SomeType.class.getDeclaredMethod("name", parameterTypes...)` | Method **declared on SomeType itself** | **No** | Can return public, protected, package-private, or private methods; requires exact name and parameter types |
| `SomeType.class.getDeclaredMethods()` | Methods declared directly in SomeType | **No** | Does not include inherited methods; result has no fixed order |
| `method.getDeclaringClass()` | Class/interface that declares the method reflected by `Method` | Not a lookup operation | Used to identify which method the annotation being read actually belongs to |
| `method.getAnnotation(A.class)` | Annotation of type `A` on the **current Method** | **Does not** walk up to parent methods | Returns `null` if the annotation is not present on this Method |
| `method.getAnnotationsByType(A.class)` | Annotations of type `A` on the **current Method**, including handling repeatable annotation containers | **Does not** walk up to overridden methods | Used when `A` is repeatable |

**Important point:** `getMethod("run")` takes the **method name and parameter types**, not the return type; if overloaded, you must specify the exact parameter types, for example `getMethod("save", String.class, int.class)`. Method overloading is not synonymous with method overriding. When bridge methods or covariant return types are involved, method selection via reflection has specific subtleties; you should inspect the returned methods rather than assuming each source-level name/signature corresponds to only one reflection `Method`.

## 3. Without Overriding: Finding the Parent's Method and Reading the Parent's Annotation

Consider the following illustrative code:

~~~java
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;

@Retention(RetentionPolicy.RUNTIME)
@interface Trace {}

class Parent {
    @Trace
    public void run() {}
}

class Child extends Parent {
    // Does not declare run().
}
~~~

If inside another method you write:

~~~java
var method = Child.class.getMethod("run");
System.out.println(method.getDeclaringClass().getSimpleName()); // Parent
System.out.println(method.isAnnotationPresent(Trace.class));      // true
~~~

This is **an illustrative snippet that must be placed inside a method handling `ReflectiveOperationException`**; a complete runnable example is in section 6.

Why is the result `true`?

1. `getMethod("run")` searches for a **public member method** that can be invoked on `Child`.
2. `Child` does not override `run()`, so reflection returns the `Method` object representing `Parent.run()`.
3. `getDeclaringClass()` returns `Parent.class`. The `@Trace` annotation is declared **on `Parent.run()` itself**.
4. `method.getAnnotation(Trace.class)` reads the annotation from the parent method being reflected; **it is not an annotation that was copied onto a method of Child**.

Conversely:

~~~java
Child.class.getDeclaredMethod("run"); // Throws NoSuchMethodException.
~~~

Because `Child` **does not declare** the `run()` method. `getDeclaredMethod` strictly never extends its scope to superclass methods; if you want to look up across the hierarchy, the application must walk up `getSuperclass()` itself when needed.

## 4. With Overriding: Annotations on the Parent Method Do Not Automatically Appear on the Child Method

Replace `Child` with:

~~~java
class Child extends Parent {
    @Override
    public void run() {}
}
~~~

Then:

~~~java
var method = Child.class.getMethod("run");
System.out.println(method.getDeclaringClass().getSimpleName()); // Child
System.out.println(method.isAnnotationPresent(Trace.class));      // false
~~~

`@Override` helps the compiler verify that `Child.run()` actually overrides an appropriate method; it **does not copy the `@Trace` annotation**. The method in the subclass is a distinct declaration with its own metadata. If the annotation is also required on the overriding method under standard reflection, you must **declare `@Trace` directly on `Child.run()`**, or design a custom utility to search for metadata on parent methods according to a defined policy.

Even if the `Trace` annotation is defined as follows:

~~~java
import java.lang.annotation.ElementType;
import java.lang.annotation.Inherited;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

@Inherited
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
@interface Trace {}
~~~

…then **`@Inherited` still has no effect in making `Child.run()` receive `@Trace` from `Parent.run()`**. According to the `java.lang.annotation.Inherited` documentation, this annotation only enables looking up the **superclass** when querying an annotation declared on a **class declaration**. For method declarations (or annotations on interfaces), that meta-annotation does not automatically create a corresponding inheritance mechanism.

In summary:

- **Without overriding:** `Child.class.getMethod("run")` can return `Parent.run()`, so it sees the annotation on `Parent.run()`.
- **With overriding, without re-annotating:** `Child.class.getMethod("run")` returns `Child.run()`, so it does not see annotations that exist only on `Parent.run()`.
- **With overriding and re-annotating:** the annotation on `Child.run()` is read normally, because it is declared directly there.

## 5. @Inherited Works on Class Annotations, Not Method Annotations

Compare the method scenario above with an actual class annotation:

~~~java
import java.lang.annotation.ElementType;
import java.lang.annotation.Inherited;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

@Inherited
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@interface Group {
    String value();
}

@Group("base")
class Parent {}

class Child extends Parent {}
~~~

The snippet above is a **syntactically standalone declaration example** and does not share class names with other examples in this article.

~~~java
var group = Child.class.getAnnotation(Group.class);
System.out.println(group.value()); // base
System.out.println(Child.class.getDeclaredAnnotation(Group.class)); // null
~~~

The two results above do not contradict each other: `Class.getAnnotation(...)` checks whether the annotation type has `@Inherited` and can search for the annotation on superclasses; `getDeclaredAnnotation(...)` only inspects annotations declared directly on `Child`. For a `Method`, there is no automatic lookup of parent methods merely because the annotation type has `@Inherited`.

Comparison table:

| Query | Automatically Considers Superclass Annotations? |
| --- | --- |
| `Child.class.getAnnotation(Group.class)`, where `Group` has `@Inherited` | **Yes**, according to the `@Inherited` rule on classes |
| `Child.class.getDeclaredAnnotation(Group.class)` | **No** |
| `Child.class.getMethod("run")` when not overridden | Can find the **parent method**; the annotation is visible because the returned `Method` is the parent method itself |
| `Child.run()` overrides without annotating, using `Method.getAnnotation(Trace.class)` | **Does not** automatically search for `Parent.run()` metadata |
| `Child.class.getAnnotationsByType(Group.class)` | Can consider inherited class annotations depending on the contract, repeatable/container |
| `childMethod.getAnnotationsByType(Trace.class)` | Only metadata on the current method/container; does not automatically traverse the override hierarchy |

Note that `@Inherited` **does not** cause an annotation from an **interface** to automatically appear on a class implementing that interface. This case also requires separate handling when a framework wants to retrieve metadata from interfaces.

## 6. Runnable Java 17 Example: Covering Inherited, Overridden, and Interface Default Methods

Create a single file **MethodInheritanceDemo.java**:

~~~java
import java.lang.annotation.*;
import java.lang.reflect.Method;
import java.util.Arrays;

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.TYPE)
@Inherited
@interface ClassTag { String value(); }

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
@Inherited
@interface Action { String value(); }

@ClassTag("parent-class")
class Parent {
    @Action("parent-inherited")
    public void inherited() {}

    @Action("parent-change")
    public void change() {}

    @Action("parent-protected")
    protected void guarded() {}
}

class Child extends Parent {}

class OverridingChild extends Parent {
    @Override public void change() {}
}

interface Greeter {
    @Action("interface-default")
    default void hello() {}
}

class GreeterChild implements Greeter {}
class GreeterOverride implements Greeter {
    @Override public void hello() {}
}

public class MethodInheritanceDemo {
    static void show(String label, Class<?> type, String methodName) throws Exception {
        Method method = type.getMethod(methodName);
        Action marker = method.getAnnotation(Action.class);
        System.out.println(label + ":owner=" +
                method.getDeclaringClass().getSimpleName() +
                ",annotation=" + (marker == null ? "none" : marker.value()));
    }

    public static void main(String[] args) throws Exception {
        show("inherited", Child.class, "inherited");
        show("sameSignature", Child.class, "change");
        show("overridden", OverridingChild.class, "change");
        show("defaultInherited", GreeterChild.class, "hello");
        show("defaultOverridden", GreeterOverride.class, "hello");
        System.out.println("childDeclared=" +
                Arrays.stream(Child.class.getDeclaredMethods())
                    .anyMatch(m -> m.getName().equals("inherited")));
        System.out.println("childPublicMethodsContains=" +
                Arrays.stream(Child.class.getMethods())
                    .anyMatch(m -> m.getName().equals("inherited")));
        System.out.println("protectedInGetMethods=" +
                Arrays.stream(Child.class.getMethods())
                    .anyMatch(m -> m.getName().equals("guarded")));
        System.out.println("protectedDeclaredOnParent=" +
                Parent.class.getDeclaredMethod("guarded")
                        .getAnnotation(Action.class).value());
        System.out.println("classAnnotationInherited=" +
                OverridingChild.class.getAnnotation(ClassTag.class).value());
    }
}
~~~

Using JDK 17 or later, open a terminal in the directory containing the file and run:

~~~bash
javac --release 17 -encoding UTF-8 MethodInheritanceDemo.java
java MethodInheritanceDemo
~~~

**Verified stdout when compiled with `--release 17` and running the program:**

~~~text
inherited:owner=Parent,annotation=parent-inherited
sameSignature:owner=Parent,annotation=parent-change
overridden:owner=OverridingChild,annotation=none
defaultInherited:owner=Greeter,annotation=interface-default
defaultOverridden:owner=GreeterOverride,annotation=none
childDeclared=false
childPublicMethodsContains=true
protectedInGetMethods=false
protectedDeclaredOnParent=parent-protected
classAnnotationInherited=parent-class
~~~

### Reading the Output to Understand the Underlying Behavior

**The first two lines (`inherited` and `sameSignature`).** `Child` does not redeclare `inherited()` or `change()`. `getMethod` retrieves the two `Method` objects of `Parent` along with the annotations attached to **those methods themselves**. `getDeclaringClass()` tells us this is `Parent`'s metadata, not a new annotation declared on `Child`.

**The `overridden` line.** `OverridingChild` overrides `change()` without placing `@Action` on the overriding method. Reflection returns `OverridingChild.change()`, where the annotation is absent, even though the `Action` annotation type **intentionally has `@Inherited`**. This is direct evidence that `@Inherited` does not enable inheritance for method annotations.

**The `defaultInherited` and `defaultOverridden` lines.** `GreeterChild` uses the default method `Greeter.hello()` without overriding it, so `getMethod("hello")` returns the method declared on the `Greeter` interface and sees the annotation on that method itself. `GreeterOverride` has its own overriding method and does not re-annotate it, so it does not see the annotation. This is still **Method lookup**, not inheritance of method annotations from an interface.

**The three lines about declared/public/protected.** `Child`'s `getDeclaredMethods()` does not contain the `inherited()` method because `Child` does not declare it; `getMethods()` contains it because the parent's method is public. The `Parent.guarded()` method is protected, so it is absent from the public `getMethods()` list; however, `Parent.class.getDeclaredMethod("guarded")` returns that method, and `@Action` can be read from it.

**The `classAnnotationInherited` line.** `OverridingChild` does not have `@ClassTag` applied to it, yet `Class.getAnnotation(ClassTag.class)` reads the value `parent-class` from the superclass because the annotation **on the class** is marked with `@Inherited`. That is a separate mechanism and does not affect methods.

In a real application, if a method is overridden while metadata from the parent remains meaningful, there must be **annotation combination rules defined by the framework/application**. Standard Java reflection does not automatically decide metadata inheritance according to such business policies.

## 7. Lookup Cases That Commonly Cause Misunderstandings

### 7.1. Public Methods vs. Protected/Private Methods

`getMethod` and `getMethods` focus exclusively on **public methods**. If a parent method is protected, package-private, or private, do not search for it with `Child.class.getMethod(...)` just because the subclass has permission to call or see it in another Java context.

- `Parent.class.getDeclaredMethod("protectedMethod")` can retrieve the protected method if the name/parameter types match.
- `Child.class.getDeclaredMethod("protectedMethod")` still will not find the parent method if Child does not redeclare it.
- When you need to traverse the class hierarchy manually, start from `Child.class` and successively use `getDeclaredMethod` and `getSuperclass`; you must clearly define the scope you want to search.
- **Private methods are not overridden in the Java sense.** A method with the same name/signature in a subclass may be an independent declaration; do not group them into an override chain and infer inherited metadata.

Obtaining a `Method` via reflection and **reading annotations** is different from invoking the method with `invoke` or changing accessibility. With encapsulated modules, accessing or invoking non-public members can be controlled by Java access checks and JPMS. Do not assume that finding a method means being able to invoke it.

### 7.2. Interface Methods and Default Methods

`getMethods()` and `getMethod(...)` can return public methods from interfaces, including default methods. If a class does not override them, the selected `Method` object may belong to the original interface, and therefore has the interface method's annotation.

However, if the class **implements** an abstract interface method with its own method, or **overrides** a default method, annotations on the interface method **do not automatically exist** on the implementing class's method.

Example:

~~~java
interface Api {
    @Action("declared-on-interface")
    void submit();
}

class ApiImpl implements Api {
    @Override public void submit() {}
}
~~~

This is an **illustrative snippet**, requiring the `Action` annotation type to exist. `ApiImpl.class.getMethod("submit").getAnnotation(Action.class)` returns `null` if the implementation does not re-annotate it; `Api.class.getMethod("submit")` has `@Action`. If a framework wants to accept annotations from an interface as default configuration, it must look up the interface hierarchy itself.

### 7.3. Repeatable Annotations Do Not Change Method Inheritance Rules Either

When `@Action` or another annotation is **repeatable**, use `method.getAnnotationsByType(Action.class)` to retrieve multiple annotations that may be stored inside a container on **the same method**.

However, `getAnnotationsByType` does not automatically find an overridden superclass method. It solves **unpacking the container**, not **traversing the override hierarchy**. To combine both, the application must define how to find parent/interface methods, invoke `getAnnotationsByType` separately on each `Method`, and then decide on precedence, overriding, or accumulation.

### 7.4. Bridge/Synthetic Methods and Generic Overrides

When generic methods or covariant return types are involved in overriding, the Java compiler may generate **bridge methods** to preserve binary compatibility. Reflection can see these methods through `getDeclaredMethods()` and identify them using `Method.isBridge()`/`Method.isSynthetic()`.

An annotation-scanning framework should not assume "one method in source code has only one `Method` object in bytecode". When multiple methods with the same name and parameter types appear due to bridge/return types, you must select the right business method using clear criteria. Do not infer from bridge metadata that an annotation was inherited under `@Inherited` rules; how the compiler handles annotations on synthetic methods does not substitute for a hierarchy lookup policy.

### 7.5. Method.getDeclaringClass() Is a Valuable Diagnostic Step

If you see `Child.class.getMethod("work").isAnnotationPresent(A.class)` return true even though `Child` does not contain a `work` declaration in source code, also print:

~~~java
System.out.println(method.getDeclaringClass().getName());
~~~

If the result is a superclass or interface, the explanation is usually that **the Method of that class/interface itself was found**. If the result is `Child`, you need to inspect annotations on the method declared directly on Child, bridge methods, and custom frameworks that may use parent class metadata at another layer.

## 8. How Should a Framework Find Annotations from Overridden Methods?

This is an **API decision that you design**, not an implicit behavior of `Method.getAnnotation`. Clarify these questions first:

1. **Accept annotations only on the current implementing method?** Use `type.getMethod(name, parameterTypes)` (for public methods) and then read `getDeclaredAnnotation` or `getAnnotationsByType` on the returned `Method`. If the override is not annotated, treat it as absent.
2. **Allow methods in a superclass to provide default annotations?** After identifying the current method, proactively traverse superclasses using `getDeclaredMethod(name, parameterTypes)`. If a direct annotation is encountered on a parent class, apply a clear precedence policy, such as "the annotation on the method closest to the subclass wins".
3. **Allow metadata declared on interfaces?** You must traverse direct/indirect superinterfaces, not just `getSuperclass()`. Define conflict rules in case two interfaces declare the same method with different metadata.
4. **Are there repeatable annotations?** You must decide whether to merge all of them, pick the nearest one, or have the subclass annotation shadow the parent annotation. Do not merge blindly.
5. **Are there overloads, generic bridges, or covariant returns?** You must resolve the corresponding method by its appropriate signature; when executing the scan policy, consider `isBridge()`/`isSynthetic()` and parameter matching after type erasure.
6. **Are there private/static methods or methods that merely share the same name?** Do not treat them as an override relationship when the language does not consider them overrides. If metadata on those methods still needs to be examined, explicitly establish a different policy, such as "scan all declarations with the same name".

A simple strategy for a framework that only uses public methods:

~~~text
Start from the target class
    ↓
Determine the public Method actually selected: getMethod(name, parameters)
    ↓
Check annotations declared on the Method itself
    ↓
If absent and policy allows fallback:
    traverse superclass declarations and superinterface declarations
    ↓
Read annotations only from the found Method, with override/signature handling
    ↓
Apply the published precedence, conflict, and repeatable rules
~~~

This is **process pseudocode**, not compilable Java source. Java does not provide an `inheritMethodAnnotations=true` flag for reflection methods; higher-level frameworks may implement their own conventions, so always read the library's contract rather than inferring directly from Java reflection.

If implementing manually, you must clarify the **traversal order**: current class, nearest superclass, nearest interfaces, inherited interfaces, and how to handle diamond interfaces. This order must be consistent and covered by tests, especially for security annotations or rules that can alter application behavior.

## 9. Common Mistakes and How to Avoid Them

**Mistake 1 — Thinking getMethod seeing an annotation means the subclass inherited the annotation.** Print `method.getDeclaringClass()`. If it is the parent class, you are reading metadata of the parent method that was found, and there is no overriding method in the child yet.

**Mistake 2 — Assuming @Inherited makes overriding methods retain annotations.** `@Inherited` only takes effect when querying a **class declaration** across superclasses. On method annotations, it does not enable inheritance.

**Mistake 3 — Using getDeclaredMethod to find inherited methods.** This API only reads direct declarations; use `getMethod` for public inherited members or traverse the hierarchy manually if you need protected/package-private methods.

**Mistake 4 — Using getMethods and assuming every result is a method of the class being inspected.** A method in the result may be declared on a superclass or interface; check `getDeclaringClass()` before attaching metadata to the class being scanned.

**Mistake 5 — Reading class annotations instead of method annotations.** `Child.class.getAnnotation(A.class)` and `Child.class.getMethod("work").getAnnotation(A.class)` refer to two different annotated elements, with different inheritance rules.

**Mistake 6 — Thinking getAnnotationsByType will automatically walk up to parent methods.** This API handles repeatable annotations on the same element; merging across a method hierarchy must be done manually.

**Mistake 7 — Scanning only superclasses and forgetting interface methods.** Annotations on an interface's abstract/default methods can be important to a framework; however, Java reflection does not automatically transfer them to the implementation.

**Mistake 8 — Scanning by name while ignoring parameter types and overloads.** Two methods with the same name but different parameters are not the same declaration; you must use exact parameter types and account for bridge methods in generic overrides.

**Mistake 9 — Calling reflection and thinking annotations automatically trigger behavior.** Annotations are only metadata. For logging, transactions, or authorization, there must be a consumer that processes the metadata and tests for the specific execution path.

## 10. Self-Check Exercises

Given three classes:

~~~java
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
@interface Audit {}

class A {
    @Audit public void save() {}
}

class B extends A {}

class C extends A {
    @Override public void save() {}
}
~~~

*This is a short illustrative snippet; you need to import `java.lang.annotation.*` when compiling it separately.*

**Question 1.** What is `B.class.getMethod("save").getDeclaringClass()`? **`A.class`**, because B does not override it.

**Question 2.** What does `B.class.getMethod("save").isAnnotationPresent(Audit.class)` return? **`true`**, because it is querying `A.save()` itself.

**Question 3.** Does `B.class.getDeclaredMethod("save")` succeed? **No**, it throws `NoSuchMethodException` because B does not declare that method.

**Question 4.** What does `C.class.getMethod("save").isAnnotationPresent(Audit.class)` return? **`false`**, because the returned Method represents `C.save()`, which is not annotated.

**Question 5.** If `@Inherited` is added to the `Audit` declaration, does the answer to Question 4 change? **No**; that meta-annotation does not inherit method annotations.

**Question 6.** If you want C to also have `@Audit` via standard reflection, what is the simplest way? **Place `@Audit` directly on `C.save()`**. If you want a rule that "takes the parent annotation when the child method is not annotated", you must write or use a consumer with an additional lookup policy.

**Question 7.** If you want to find `@Audit` on `A.save()` when starting only from `C.class`, while still keeping the overriding method unannotated, how can you do it? **Call `A.class.getDeclaredMethod("save")` after walking up to the superclass**, and then read the annotation on A's Method; associating the result with C is a separate decision.
