# javac: -proc:only, -proc:none, -A, and -s in Java Annotation Processing

## 1. Four Options That Control Different Things

Annotation processing is part of the Java compilation process. The `javac` compiler can load **annotation processors** written in Java, allowing them to inspect declarations, report diagnostics, and generate additional source/class files or resources through the standard `javax.annotation.processing` and `javax.annotation.processing.Filer` APIs.

When using this tool, four easily confused options are:

| Option | Primary Function | Does Not Mean |
| --- | --- | --- |
| **`-proc:only`** | Runs only annotation processing, **without performing the subsequent compilation phase to produce class files for the input sources** | Does not mean the processor cannot generate `.java` files |
| **`-proc:none`** | Compiles without **running annotation processors** | Does not mean ignoring all annotations or skipping the compiler's syntax-checking step |
| **`-Akey[=value]`** | Passes a name/value option to the **processor**, which the processor itself reads and interprets | Not a Java system property option or a flag that automatically generates source files |
| **`-s directory`** | Selects the directory for **Java sources generated by the annotation processor** | Not the directory for `.class` files; the class output directory uses `-d` |

In particular, `-proc:only` and `-proc:none` are **two opposing modes**; do not pass both in the same command. Meanwhile, `-A` and `-s` can be combined with `-proc:only` or with a build run that performs both annotation processing and compilation.

The goal of this article is to understand their exact functions, how to combine options, runnable examples, and common configuration mistakes. The examples use **Java 17+**, without requiring Spring, Lombok, or any libraries outside the JDK.

## 2. Background: How Does javac Discover and Execute Processors?

An annotation processor is a class that implements `javax.annotation.processing.Processor`, typically extending `AbstractProcessor`. The processor is instantiated by the compiler, provided with a `ProcessingEnvironment`, and invoked via `process(...)` across processing rounds.

The steps that can take place:

```text
.java source files
  |
  |  javac parses sources and discovers annotation processors
  v
Annotation processing (may consist of multiple rounds)
  |         |
  |         +-- Messager: reports errors/warnings
  |         +-- Filer: generates new .java source files
  v
Compile original sources and generated sources -> .class files
```

Depending on the mode:

- `-proc:only`: runs the annotation processing branch, **without the subsequent full compilation step**.
- `-proc:none`: skips the annotation processing branch and proceeds through normal compilation.
- A command configuring a processor **without `-proc:only` or `-proc:none`**: performs annotation processing and then compiles; on newer JDKs, processors should be enabled **explicitly**.

A processor can create source files via:

```java
JavaFileObject source = processingEnv.getFiler()
        .createSourceFile("generated.Hello");
```

When the writer/stream is closed properly, the new source is examined by the compiler in the appropriate processing rounds. The `-s` option determines the target directory for that source file; it does not determine which processor is run.

### 2.1. Do Not Overlook the Default Difference Since JDK 23

Starting in **JDK 23**, `javac` **no longer automatically runs annotation processors merely because a processor is found on the classpath** when there is no explicit annotation processing configuration. This change is intended to prevent accidentally executing processors present on the classpath.

To keep builds reproducible across JDK versions, use explicit options such as:

```bash
javac -processor MyProcessor -processorpath path/to/processors ...
```

or the appropriate annotation processing configurations of your build tool. When using `-proc:only`, you have already indicated the intent to run only annotation processing. Adding `-processor` specifies **the exact processor class** to run, without relying on service discovery.

The `-proc:full` option means **annotation processing + compilation** on javac versions that support it; it was added and backported to several older JDK update releases. If you need to run on a JDK 17 release that has not been updated, you should use **an explicit `-processor` without `-proc:full`**, as shown in the example in the following section.

## 3. -proc:only — Annotation Processing Only

Syntax:

```bash
javac -proc:only -processor SomeProcessor -processorpath processor-classes -s generated Input.java
```

**Accurate meaning:** The compiler processes annotations, can report errors, and can generate files, but **does not perform the class compilation phase for the sources being processed** after annotation processing finishes. Therefore, `-proc:only` is commonly used for:

- Validating annotation constraints in a separate step of a pipeline.
- Generating Java source files based on input declarations, prior to a separate compilation command.
- Diagnosing processor behavior without needing to produce application class output yet.
- Separating the generation step from the compilation step to observe the output more easily.

**Do not confuse:** `-proc:only` does not mean "cannot create files". A processor can still use `Filer.createSourceFile`, `createResource`, or other appropriate APIs. `-proc:only` simply does not compile the sources into class files like a normal build run.

A valid two-phase workflow:

```text
Phase 1: -proc:only
  -> processor checks annotations
  -> creates generated/GeneratedGreeting.java

Phase 2: -proc:none
  -> javac compiles Demo.java and generated/GeneratedGreeting.java
  -> produces the application's .class files
```

In the second phase, `-proc:none` avoids re-running the processor, preventing duplicate file generation or turning the generation round into a hard-to-control build loop.

### 3.1. -proc:only Can Still Report Compilation Errors

"Not compiling class files" **does not mean javac skips reading or checking the sources**. Javac still has to parse enough to serve annotation processing; the processor can emit `Diagnostic.Kind.ERROR`, or the compiler can encounter source errors. A `-proc:only` run can still finish with a non-zero exit code.

### 3.2. Inspecting the Output After -proc:only

If the processor generates source files via `Filer`, look for the Java files in the directory specified by `-s`. Do not look for `Demo.class` as a sign that the processor succeeded: producing class files is not the goal of `-proc:only`.

Conversely, if no new source files appear, check whether the processor **was actually loaded**, whether the annotation type is supported, or whether the processor only performs validation without generating code.

## 4. -proc:none — Compile Without Running Annotation Processors

Syntax:

```bash
javac -proc:none -cp processor-classes -d app-classes Demo.java generated/GeneratedGreeting.java
```

With `-proc:none`, the compiler does not call `Processor.process`. However:

- Java annotation syntax and language rules still apply; source code containing annotations is not treated as ignored text because of this flag.
- The compiler still processes Java declarations to produce class files; annotations with appropriate retention can still appear in the class files according to their retention policy.
- No code is generated by a processor during **this invocation**. If the code references a class that is supposed to be generated by a processor and that class does not exist yet, the compiler can report `cannot find symbol`.
- Sources that were already generated **in a previous step** can still be compiled when listed as inputs or via an appropriate source path configuration.

**Practical example:** Use `-proc:none` when verifying pure compilation, avoiding processors in untrusted environments, or executing the second compilation phase after `-proc:only`.

`-proc:none` is not an option to "disable Java annotations". It only **disables the annotation processors** run by the compiler in that step.

### 4.1. When Does -proc:none Cause a Build to Fail?

A class writing:

```java
System.out.println(GeneratedGreeting.message());
```

will fail to compile if `GeneratedGreeting` has not yet been provided as source or class. If a project relies on a processor to generate it automatically yet uses `-proc:none` from the start, this error is **expected and predictable**.

When you want to compile while still generating code, do not use `-proc:none`; alternatively, run generation in an earlier step and ensure the generated source is included in the compilation.

## 5. -Akey[=value] — Passing Configuration to Processors

Syntax:

```bash
javac -processor SomeProcessor -Akey=value Input.java
javac -processor SomeProcessor -Aflag Input.java
javac -processor SomeProcessor -Acompany.region=west Input.java
```

`-A` provides **processor-specific options**: the key name consists of one or more dot-separated Java identifiers, typically written as `-Akey=value`. The form without `=value` is used for valueless flags. Do not split `-A` and the key into two separate shell arguments.

The processor reads them via:

```java
String salutation = processingEnv
        .getOptions().getOrDefault("salutation", "Hello");
```

`getOptions()` returns a `Map<String, String>` containing the options passed by `javac` to annotation processing. **`javac` itself does not understand the business meaning of `salutation`**; the processor decides whether to use it to change generated content, enable logging, or apply a certain rule.

The processor should declare supported options via:

```java
@SupportedOptions("salutation")
```

or by overriding `getSupportedOptions()`. If you pass a key that is not supported by any processor, `javac` may emit a warning like "unrecognized processor options"; do not treat `-A` as a general compiler option.

### 5.1. Some Practical Guidelines

- **Clear configuration:** choose names like `salutation` or `project.region`; do not create ambiguous keys or keys that depend on argument position.
- **Default values:** the processor itself should supply an appropriate default when the key is absent from the map.
- **Value validation:** if an option must be an integer, boolean, or enum, parse and validate it in the processor and use `Messager.ERROR` when invalid.
- **Shell quoting:** when a value contains spaces, quotes, or special characters, use quoting appropriate for Bash/PowerShell; the shell determines how argv is passed to javac.
- **Do not confuse with `-Dname=value` or environment variables:** those are different configuration mechanisms and do not automatically appear in `ProcessingEnvironment.getOptions()`.
- **Do not use for secrets:** command-line arguments can be visible in build logs, shell history, or process information; do not embed tokens or passwords into generated source.

`-A` **is not a reliable standalone mechanism for enabling annotation processing**. Specify the processor/processor path or the appropriate `-proc` option explicitly; when using `-proc:none`, no processor consumes `-A`.

## 6. -s directory — Directory for Generated Java Sources

Syntax:

```bash
javac -processor SomeProcessor -s generated-sources Input.java
```

`-s` sets the **source output directory** for Java source files created by the compiler/annotation processor through the appropriate mechanism. For example, if a processor calls:

```java
processingEnv.getFiler().createSourceFile("com.example.GeneratedMapper");
```

with `-s generated-sources`, it typically produces:

```text
generated-sources/
  com/
    example/
      GeneratedMapper.java
```

In the case of modules, javac may organize directories by **module hierarchy before package hierarchy**. You should not assume all projects write sources at the root of `-s`.

**Distinguishing `-s` from `-d`:**

| Option | Primary Output | Example |
| --- | --- | --- |
| `-s generated` | Generated `.java` source files | `generated/GeneratedGreeting.java` |
| `-d app-classes` | Compiled `.class` bytecode | `app-classes/Demo.class` |
| `-processorpath processor-classes` | **Input**, where processors and their dependencies are located | `processor-classes/GreetingProcessor.class` |
| `-cp processor-classes` | **Input**, classpath used to resolve types of the program being compiled | `processor-classes/GenerateGreeting.class` |

`-s` **does not activate processors by itself**, does not create annotations on its own, and does not mean all input sources are copied there. If no processor generates Java sources, the `-s` directory may be empty.

Generated source output should reside in a separate directory, not mixed with handwritten source code; during repeated builds, you need to prevent stale files from causing broken builds or throwing `FilerException` due to generating duplicate paths within a processor session.

## 7. Complete Java 17+ Example: Two-Step and Single-Step Compilation

The example consists of **three Java files** in the same empty working directory, using only standard JDK APIs. The processor reads `@GenerateGreeting`, accepts the `-Asalutation` option, and then uses `Filer` to generate the `GeneratedGreeting` class with a `message()` method. We compare:

1. **`-proc:only`** to generate `.java`, followed by **`-proc:none`** to compile and run.
2. Running the processor and compiling **in the same command** (without `-proc:only`/`-proc:none`, specifying `-processor` explicitly).
3. **`-s`** specifies where generated files are placed; **`-A`** changes the greeting value.

### 7.1. GenerateGreeting.java File

```java
import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

@Retention(RetentionPolicy.SOURCE)
@Target(ElementType.TYPE)
public @interface GenerateGreeting {
    String name();
}
```

`SOURCE` retention is sufficient: the processor runs at compile time, and runtime reflection is not needed to read this annotation. The example uses the default package to keep commands short; in real projects, use a clearly named package.

### 7.2. GreetingProcessor.java File

```java
import java.io.IOException;
import java.io.Writer;
import java.util.Set;

import javax.annotation.processing.AbstractProcessor;
import javax.annotation.processing.RoundEnvironment;
import javax.annotation.processing.SupportedAnnotationTypes;
import javax.annotation.processing.SupportedOptions;
import javax.annotation.processing.SupportedSourceVersion;
import javax.lang.model.SourceVersion;
import javax.lang.model.element.Element;
import javax.lang.model.element.ElementKind;
import javax.lang.model.element.TypeElement;
import javax.tools.Diagnostic;

@SupportedAnnotationTypes("GenerateGreeting")
@SupportedOptions("salutation")
@SupportedSourceVersion(SourceVersion.RELEASE_17)
public final class GreetingProcessor extends AbstractProcessor {
    private boolean generated;

    @Override
    public boolean process(Set<? extends TypeElement> annotations,
                           RoundEnvironment roundEnv) {
        if (roundEnv.processingOver()) {
            System.out.println("PROCESSOR final");
            return true;
        }

        for (Element element : roundEnv
                .getElementsAnnotatedWith(GenerateGreeting.class)) {
            if (generated) {
                continue;
            }
            if (element.getKind() != ElementKind.CLASS) {
                processingEnv.getMessager().printMessage(
                        Diagnostic.Kind.ERROR,
                        "Only classes supported", element);
                continue;
            }

            String name = element
                    .getAnnotation(GenerateGreeting.class).name();
            String salutation = processingEnv.getOptions()
                    .getOrDefault("salutation", "Hello");

            // Restrict input to generate a safe Java string literal in the demo.
            if (!name.matches("[A-Za-z]+")
                    || !salutation.matches("[A-Za-z]+")) {
                processingEnv.getMessager().printMessage(
                        Diagnostic.Kind.ERROR,
                        "Use letters A-Z for name and salutation",
                        element);
                continue;
            }

            try (Writer writer = processingEnv.getFiler()
                    .createSourceFile("GeneratedGreeting", element)
                    .openWriter()) {
                writer.write("public final class GeneratedGreeting {\n");
                writer.write("  private GeneratedGreeting() {}\n");
                writer.write("  public static String message() { return \""
                        + salutation + ", " + name + "\"; }\n");
                writer.write("}\n");

                generated = true;
                System.out.println("PROCESSOR generated");
            } catch (IOException e) {
                processingEnv.getMessager().printMessage(
                        Diagnostic.Kind.ERROR, e.getMessage(), element);
            }
        }

        return true;
    }
}
```

**Reading the processor:**

- `@SupportedAnnotationTypes("GenerateGreeting")` indicates which annotation the processor handles. This name has no package in the example; when using a package, declare the **fully qualified name**.
- `@SupportedOptions("salutation")` advertises the key supported via `-Asalutation=...`.
- `processingEnv.getOptions()` reads the actual value; if the key is missing, `Hello` is used.
- `Filer.createSourceFile("GeneratedGreeting", element)` creates a Java source file for the `GeneratedGreeting` type; `element` attaches originating element information so build tools can track relationships.
- `generated` holds the processor's state within a session, avoiding attempts to create the same file name multiple times.
- `processingOver()` is used to handle the final round; the processor does not generate new types in the final round.
- The code accepts only A–Z characters to keep Java string literal generation simple and safe. In a real processor supporting Unicode or arbitrary characters, strings must be encoded/escaped according to Java literal rules; never concatenate unvalidated input directly into source code.

`process` returns `true` to claim the annotation type; it does **not** mean processing rounds have stopped.

### 7.3. Demo.java File

```java
@GenerateGreeting(name = "Lan")
public class Demo {
    public static void main(String[] args) {
        System.out.println(GeneratedGreeting.message());
    }
}
```

`Demo` intentionally references `GeneratedGreeting` even though that class has not been written beforehand: the processor must generate it before the application can compile and run.

### 7.4. Step 1 — Compile the Annotation and Processor

Create directories to store processor bytecode and demo outputs, and from the directory containing the three files run:

```bash
mkdir -p processor-classes generated app-classes full-classes full-sources
javac --release 17 -d processor-classes GenerateGreeting.java GreetingProcessor.java
```

This command creates `GenerateGreeting.class` and `GreetingProcessor.class` in `processor-classes`. The `--release 17` option ensures the source and API target Java 17. The example commands below use Bash on Linux/macOS; on Windows PowerShell, create directories with `New-Item -ItemType Directory -Force` and replace the classpath separator `:` with `;`.

### 7.5. Step 2 — Annotation Processing Only with -proc:only

```bash
javac --release 17 -cp processor-classes \
  -processorpath processor-classes \
  -processor GreetingProcessor \
  -proc:only -Asalutation=Hello \
  -s generated Demo.java
```

**Processor stdout** output:

```text
PROCESSOR generated
PROCESSOR final
```

After this command, the file `generated/GeneratedGreeting.java` is created; its contents are equivalent to:

```java
public final class GeneratedGreeting {
    private GeneratedGreeting() {}
    public static String message() { return "Hello, Lan"; }
}
```

**Important:** `-proc:only` does not produce `Demo.class` or `GeneratedGreeting.class` for the application. The command also does not run `Demo`'s `main`. This is a **compile-time generation** task, not running the application.

### 7.6. Step 3 — Compile Existing Sources with -proc:none

```bash
javac --release 17 -proc:none -cp processor-classes \
  -d app-classes Demo.java generated/GeneratedGreeting.java

java -cp processor-classes:app-classes Demo
```

**Application** output:

```text
Hello, Lan
```

In this step, `javac` compiles `Demo.java` along with the generated `GeneratedGreeting.java`, and `-proc:none` ensures the processor **does not run again**. `-cp processor-classes` helps the compiler find the `GenerateGreeting.class` annotation; when running the application, `Demo` uses `GeneratedGreeting.class` in `app-classes`.

**Intentional error test:** if you compile only `Demo.java` with `-proc:none`, without including `GeneratedGreeting.java` or its `.class` in the source/class path, the compiler will report an error saying it cannot find `GeneratedGreeting`.

### 7.7. Alternative — A Single Command for Both Processing and Compilation

Without using `-proc:only` and `-proc:none`, while still **specifying the processor explicitly** to avoid relying on JDK 23+ defaults:

```bash
javac --release 17 -cp processor-classes \
  -processorpath processor-classes \
  -processor GreetingProcessor \
  -Asalutation=Hi \
  -s full-sources -d full-classes Demo.java

java -cp processor-classes:full-classes Demo
```

Processor and application output:

```text
PROCESSOR generated
PROCESSOR final
Hi, Lan
```

In this mode:

- `full-sources/GeneratedGreeting.java` contains the source generated by the processor, with the content `"Hi, Lan"`.
- `full-classes/` contains the compiled bytecode of `Demo` and `GeneratedGreeting`.
- No second `javac` command is needed for the generated source: the compiler combines processing + compilation in the same invocation.
- The example suite **was tested on JDK 21** using `--release 17`; the commands with explicit processor specifications make it suitable for both JDK 17+ environments and the new policy starting in JDK 23.

**Stdout note:** Since this is a minimal example, the processor prints two fixed lines; other compilers or build tools may add their own diagnostics or notes. Do not treat the log order of a complex build as a business contract.

## 8. Option Combination Scenarios

| Command or Option Group | Expected Result |
| --- | --- |
| `-proc:only -processor GreetingProcessor -Asalutation=Hello -s generated` | The processor runs and can generate sources into `generated`; application classes are not built |
| `-proc:none -d app-classes` | Compiles only; does not run processors; previously generated sources must be supplied separately |
| `-processor GreetingProcessor -Asalutation=Hi -s full-sources -d full-classes` | Runs the processor and then compiles in a full flow |
| `-proc:none -Asalutation=Hi` | No processor is run to consume the option; no new sources are expected |
| `-proc:only -s generated` without a valid processor | May not generate sources; check processor configuration and diagnostics |
| `-proc:none -s generated` | `-s` does not generate Java sources on its own when annotation processing is disabled |

For a processor to be loaded successfully, distinguish between these three paths:

- `-processorpath`: the path used to locate and load processors and their required dependencies.
- `-cp`: the classpath for types referenced by the program being compiled, including annotation types if needed.
- `-s`: the **output** directory for sources created by the processor, not a path for finding processors.

If the project is modular, you may need `--processor-module-path` or module path configuration instead of classpath; do not apply the default-package example verbatim to a real module structure.

## 9. Warnings on Reproducible and Safe Builds

### 9.1. Do Not Rely on Implicit Processor Discovery

On JDK 23+, javac requires explicit annotation processing configuration in cases where it previously could automatically discover processors on the classpath. A build that "works on an older machine but does not generate code on a newer machine" is often caused by relying on implicit discovery.

Fix: declare the processor with `-processor` or a build tool plugin that fully supports processor path/annotation processing. Verify using `-XprintProcessorInfo` or appropriate diagnostic options if supported by the compiler.

### 9.2. Use a Clean Output Directory

Generated Java source is a build artifact. If you run twice while keeping the previous run's sources and re-running the processor at the same time, it is easy to cause type name conflicts or use stale artifacts. Design separate output directories for each mode and clean the appropriate build directories when needed, without accidentally deleting handwritten source code.

### 9.3. Protect the Trust Boundary

An annotation processor is **Java code executed during the build**, so `-processorpath` needs to be controlled like an executable dependency. Do not load processors from untrusted sources merely to read annotations. `-proc:none` can be useful when you need the compiler not to execute unapproved processors, though a project depending on generated code may fail to compile unless safely generated artifacts are provided.

### 9.4. Limitations of -A and Sensitive Data

`-A` is suitable for simple configuration such as a profile name or generation mode, and is not appropriate for passing passwords or tokens on the command line. Build logs or tooling may record arguments. A processor can also write options into generated code if designed to do so, so values must be controlled.

### 9.5. Do Not Confuse Processor Success with Build Success

A processor may generate valid source that still hits errors during the compilation step; a successful `-proc:only` run **does not guarantee** that the subsequent `-proc:none` step will succeed. Conversely, a successful `-proc:none` compilation against existing classes does not prove that annotation validation ran in the current build.

In CI, if both generation and compilation are required, the pipeline should check the exit codes of **both phases** (or use full mode with an explicit processor) instead of only checking that a generated directory exists.

## 10. Common Mistakes and How to Fix Them

**1. Thinking -proc:only must produce .class files.** Incorrect. `-proc:only` performs only annotation processing and does not produce the program's class output like normal compilation. Compile the appropriate Java sources in the next step.

**2. Using -proc:none while expecting the processor to generate types.** Incorrect. If the code requires a generated class, you must generate it beforehand or enable processing.

**3. Using -s instead of -d.** `-s` is for generated `.java` files; `-d` is for compiled `.class` files.

**4. Assuming -A enables annotation processing.** `-A` passes options to a processor that is already being run. Configure the processor explicitly and check `@SupportedOptions`.

**5. Writing -A salutation=Hello as separate arguments.** Use `-Asalutation=Hello`, keeping the key attached directly to `-A`.

**6. Passing a key not declared by the processor.** `javac` may warn that the key is not recognized by any processor. Declare valid `@SupportedOptions` or `getSupportedOptions()`.

**7. Confusing processorpath and classpath.** The processor might be loaded while the compiler cannot find the annotation type; or the compiler sees the annotation while the processor is not loaded. Configure both as needed.

**8. Not specifying the processor on newer JDKs.** Relying on automatic processor discovery on the classpath can prevent annotation processing from running starting in JDK 23. Use `-processor` or an appropriate build setup.

**9. Passing option values containing spaces without escaping/quoting.** The shell splits arguments before javac receives them. Use quoting syntax compatible with your execution environment.

**10. Checking only that the generated file exists without checking timestamps/builds.** Stale files can allow the program to compile without proving the processor just ran. Use clean output directories and processor logs.

**11. Thinking -proc:only guarantees all code is valid.** The compiler does not perform the full class compilation phase; run a separate compilation step to detect symbol or generated-source errors.

**12. Expecting javac options in getOptions().** `ProcessingEnvironment.getOptions()` reflects `-A` options intended for processors, not general `javac` flags such as `-s` or `-proc`.

**13. Thinking -s creates sources on its own without a processor.** The `-s` directory only specifies where to write; processor code calling Filer is required for files to be generated.

**14. Combining -proc:only and -proc:none in the same command.** The two modes are not cumulative flags. Choose exactly one purpose for each `javac` invocation.

## 11. Checklist for Configuring Annotation Processing in a Project

1. Identify which processor classes need to run; specify them explicitly via your build tool or `-processor`.
2. Check processor dependencies and `-processorpath`/processor module path.
3. Verify that source code can see the annotation types via the classpath/module path.
4. Decide between **generation/validation only** (`-proc:only`) or **processing with compilation**.
5. If splitting into two steps, use `-proc:none` in the compile step so the processor does not run again; include the appropriate generated sources/classes as inputs.
6. Set the generated Java source directory with `-s`; set class output with `-d`.
7. Declare the `-A` keys supported by the processor and validate input values.
8. Eliminate reliance on implicit discovery, especially on JDK 23 and later.
9. Check logs/exit codes, generated artifacts, and class outputs after each step.
10. Test on the CI JDK version, configure clean build directories, and avoid mixing generated code with handwritten source.

## 12. Practice Exercises

1. **Change -A configuration:** Re-run the example with `-Asalutation=Welcome`. Predict the contents of `GeneratedGreeting.java` and the application output. Explain why javac itself does not understand the meaning of `Welcome`.
2. **Omit -A:** Remove `-Asalutation=...` from the processor execution command. Predict the default value `Hello` used by the processor code.
3. **Separate sources/classes:** Change `-s generated` to `-s source-out` while keeping `-d app-classes`. Verify the exact directories where `.java` and `.class` files appear.
4. **Disable processors:** Try `javac -proc:none -cp processor-classes -d app-classes Demo.java` without a previously generated type. Record the symbol error and fix it by supplying the generated source.
5. **Two-step vs. single-step:** Compare the two pipelines in Section 7 in terms of output file lists. State the benefits of separating generation and what to watch out for regarding stale artifacts.
6. **Undeclared key:** Pass `-Aunknown.option=yes`. Observe the warning from javac and update `@SupportedOptions` if the processor actually needs that key.
7. **Invalid value error:** Try `-Asalutation=Hello123`. The processor will report ERROR because the demo accepts only ASCII letters; explain that this is processor logic rather than a general `-A` rule.
8. **JDK testing:** Check the compiler in use with `javac -version`. Compare the results with and without `-processor`, especially from JDK 23 onward.
9. **Safety analysis:** If a processor resides in an unfamiliar dependency, explain why having a build execute it automatically poses a risk and when `-proc:none` helps limit unintended execution.
10. **Modularization:** Design separate package/module structures for the annotation and processor; identify what needs to change in `@SupportedAnnotationTypes`, processor paths, and where generated sources are written.

- [JDK 23 Annotation Processing Policy Change — OpenJDK Quality Outreach](https://inside.java/2024/06/18/quality-heads-up/): explains why processors should be enabled explicitly.

**Remember:** `-proc:only` means **annotation processing only**, `-proc:none` means **compilation without annotation processing**, `-A` is **an option passed to the processor**, and `-s` is **the directory for Java sources generated by the processor**. Combine these flags properly with `-processor`, `-processorpath`, `-cp`, and `-d` to keep builds reproducible across JDK versions.
