# Ability to Process SOURCE Annotations and Limitations When Annotations Are on Type Uses

## 1. SOURCE Annotations Can Still Be Processed at Compile Time

In Java, an annotation type is declared using `@interface`. `@Retention` determines until which stage an annotation is retained; it does **not** determine whether the compiler/annotation processor can read the annotation while processing source code.

Example:

```java
import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

@Retention(RetentionPolicy.SOURCE)
@Target(ElementType.TYPE)
@interface CompileCheck {
    String value();
}

@CompileCheck("domain")
class DomainService {}
```

This is a syntax illustration snippet; there is no `main`. While `javac` is compiling `DomainService`, an appropriate annotation processor **can find** `@CompileCheck`, read the `value()` element, and produce diagnostics or generated files. However, after compilation, the **usage** of `@CompileCheck("domain")` on `DomainService` is not retained in `DomainService.class`, because the retention is `SOURCE`.

That is not a contradiction: **a processor works on the program model at compile time; reflection works on the metadata remaining at runtime**.

| Annotation retention | Processor when compiling source containing the annotation | Bytecode of the annotated element | Standard reflection at runtime |
| --- | --- | --- | --- |
| `SOURCE` | Can read in the appropriate compile-time model | Does not store that annotation usage | Cannot read |
| `CLASS` | Can read | Stored, typically in the corresponding runtime-invisible attribute | Cannot read |
| `RUNTIME` | Can read | Stored, typically in the corresponding runtime-visible attribute | Can read if using the right location/API |

If an annotation type does **not** declare `@Retention`, Java's default is `RetentionPolicy.CLASS`.

**Distinguishing definition and usage:** `SourceTag.class` (the class file of the *annotation type* itself) may still be generated by `javac`, and the meta-annotation `@Retention(SOURCE)` on the type definition may also appear in the bytecode of that definition. What is discarded under SOURCE is **the usage of `@SourceTag` on another class/field/method/type-use**.

## 2. Which API Does a Processor Use to Read SOURCE Annotations?

JSR 269 (Pluggable Annotation Processing API) uses the interfaces in `javax.annotation.processing` and `javax.lang.model`.

Key components:

- `javax.annotation.processing.Processor` or `AbstractProcessor`: where processing logic is implemented when invoked by the compiler.
- `ProcessingEnvironment`: provides `Elements`, `Types`, `Messager`, `Filer`, and processing options.
- `RoundEnvironment`: provides the root elements of the processing round and operations such as `getElementsAnnotatedWith(...)`.
- `Element`: models a **declaration** in the program, such as a class, method, field, parameter, or package.
- `TypeMirror`: models a **Java type** used at a location, such as a field type, return type, generic argument, array, or wildcard.
- `AnnotationMirror`: the modeled representation of an annotation in the compiler, without requiring an annotation object to be created via Java reflection.
- `AnnotatedConstruct.getAnnotationMirrors()`: reads annotation mirrors on an appropriate `Element` **or `TypeMirror`**.

Example of a processor commonly handling annotations on class declarations:

```java
for (Element element : roundEnv.getElementsAnnotatedWith(CompileCheck.class)) {
    // element represents the declaration carrying @CompileCheck.
}
```

However, calling `getElementsAnnotatedWith(...)` returns **matching annotated Elements**, **not a list of every syntactic location of the annotation in the AST**. This is an important limitation when an annotation sits deep inside a **type-use** position such as a generic argument.

A standard annotation processor is not runtime reflection, and does not require `@Retention(RUNTIME)` to see source annotations; however, the processor must be appropriately **registered/enabled** by the compiler, must operate within the relevant source processing environment, and must use an API capable of representing the location where the annotation is actually attached.

## 3. How TYPE_USE Differs from Annotations on Declarations

Since Java 8, `ElementType.TYPE_USE` allows an annotation to be placed at a **type-use** position (*type use*), for example:

```java
List<@TypeNote("element") String> names;
```

Here `@TypeNote` is attached to **the `String` type inside the type argument of `List`**, not directly to the field declaration `names` in the sense of declaration metadata.

Comparison:

```java
@SourceTag("declaration")
class Catalog {
    List<@TypeNote("argument") String> items;
}
```

- `@SourceTag` annotates the **class declaration** `Catalog`, so `Catalog` is an annotated `TypeElement`.
- `@TypeNote` annotates the **type argument `String`** in the type of field `items`. The field declaration element is a `VariableElement`, whereas the annotation is on a **child TypeMirror** of the field's type.
- When merely reading `field.getAnnotationMirrors()` or querying `RoundEnvironment.getElementsAnnotatedWith(TypeNote.class)`, a program **must not assume** it will see every annotation located inside a generic type structure. It must navigate to the exact type use and read `getAnnotationMirrors()` on that `TypeMirror`.

Further distinguishing three commonly confused targets:

| Target | Location | Example |
| --- | --- | --- |
| `ElementType.TYPE` | Declaration of a class, interface, annotation type... | `@SourceTag class Catalog {}` |
| `ElementType.TYPE_PARAMETER` | Type variable declaration in generics | `class Box<@Marker T> {}` |
| `ElementType.TYPE_USE` | Type-use position | `List<@Marker String>`; cast type, return type, type argument... |

If an annotation type only has the `TYPE_USE` target, it is not treated as a declaration annotation in all positions. On the other hand, an annotation with multiple targets can produce interpretations depending on **the exact syntactic context**; when the goal is to inspect type uses, use the type-model API instead of relying on Element annotations by default.

## 4. Runnable Java 17+ Program: SOURCE Declaration and SOURCE Type-Use

This example creates an actual annotation processor, and then uses it to verify:

1. The `@SourceTag` annotation (retention `SOURCE`) on a class declaration is found via `RoundEnvironment.getElementsAnnotatedWith`.
2. The `@TypeNote` annotation (retention `SOURCE`) on the type argument in `List<@TypeNote String>` is **not** returned as a separate element by `getElementsAnnotatedWith(TypeNote.class)` in this fixture.
3. The processor still finds `@TypeNote` by retrieving the `TypeMirror` of the field, navigating to the generic type argument, and reading `getAnnotationMirrors()` on that component type.
4. After compilation, the class file of `Sample` no longer contains **the usages of** `@SourceTag`/`@TypeNote` because the retention is `SOURCE`.

### 4.1. File Structure

```text
src/
├── demo/
│   ├── SourceTag.java
│   ├── TypeNote.java
│   └── Sample.java
└── tools/
    └── InspectProcessor.java
```

Only JDK 17 or later is needed to run this. The two annotation types and the processor will be compiled first so that the processor can load its annotation types; then the compiler uses `-processor` to activate the processor when compiling the annotated code.

### File 1: `src/demo/SourceTag.java`

```java
package demo;

import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

@Retention(RetentionPolicy.SOURCE)
@Target(ElementType.TYPE)
public @interface SourceTag {
    String value();
}
```

`SourceTag` is an annotation used on **type declarations**. Setting `@Retention(SOURCE)` does not prevent the processor from observing the usage while the compiler is still processing the source.

### File 2: `src/demo/TypeNote.java`

```java
package demo;

import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

@Retention(RetentionPolicy.SOURCE)
@Target(ElementType.TYPE_USE)
public @interface TypeNote {
    String value();
}
```

`TypeNote` has the **`TYPE_USE`** target, and in this program is used on a **generic type argument**, which is a position inside a `DeclaredType`.

### File 3: `src/demo/Sample.java`

```java
package demo;

import java.util.List;

@SourceTag("compile-only")
public class Sample {
    private List<@TypeNote("item-type") String> names;

    public List<@TypeNote("result-type") String> names() {
        return names;
    }
}
```

`@SourceTag("compile-only")` is attached to the `Sample` class. The two usages of `@TypeNote` are located on **the `String` type argument**, once in the type of field `names` and once in the return type of the `names()` method. To illustrate the API limitation clearly, the processor below intentionally navigates into the generic type argument of the **field**; the annotation in the return type is a case that can be extended further.

### File 4: `src/tools/InspectProcessor.java`

```java
package tools;

import demo.SourceTag;
import demo.TypeNote;
import java.util.Set;
import javax.annotation.processing.AbstractProcessor;
import javax.annotation.processing.RoundEnvironment;
import javax.annotation.processing.SupportedAnnotationTypes;
import javax.annotation.processing.SupportedSourceVersion;
import javax.lang.model.SourceVersion;
import javax.lang.model.element.AnnotationMirror;
import javax.lang.model.element.Element;
import javax.lang.model.element.ElementKind;
import javax.lang.model.element.TypeElement;
import javax.lang.model.type.DeclaredType;
import javax.lang.model.type.TypeMirror;

@SupportedAnnotationTypes({"demo.SourceTag", "demo.TypeNote"})
@SupportedSourceVersion(SourceVersion.RELEASE_17)
public class InspectProcessor extends AbstractProcessor {
    @Override
    public boolean process(
            Set<? extends TypeElement> annotations,
            RoundEnvironment round) {
        if (round.processingOver()) {
            return false;
        }

        System.out.println("DECLARED-MATCHES="
                + round.getElementsAnnotatedWith(SourceTag.class).size());
        System.out.println("TYPE-USE-MATCHES="
                + round.getElementsAnnotatedWith(TypeNote.class).size());

        for (Element cls : round.getElementsAnnotatedWith(SourceTag.class)) {
            SourceTag tag = cls.getAnnotation(SourceTag.class);
            System.out.println("SOURCE-TAG=" + tag.value());

            for (Element member : cls.getEnclosedElements()) {
                if (member.getKind() != ElementKind.FIELD) {
                    continue;
                }

                DeclaredType listType = (DeclaredType) member.asType();
                TypeMirror typeArg = listType.getTypeArguments().get(0);
                for (AnnotationMirror mirror : typeArg.getAnnotationMirrors()) {
                    System.out.println("TYPE-ARG="
                            + mirror.getAnnotationType()
                                    .asElement().getSimpleName());
                }
            }
        }
        return false;
    }
}
```

**Processor explanation:**

- `@SupportedAnnotationTypes` lists the annotation types supported by the processor. `@SupportedSourceVersion(RELEASE_17)` specifies the language level that the processor declares support for; `javac --release 17` helps keep the experiment consistent.
- `process(...)` can be called across **multiple rounds**. The code checks `round.processingOver()` to skip the final round; the example does not generate new source files, so the expected output is printed once in the round that contains the matching annotations.
- `round.getElementsAnnotatedWith(SourceTag.class)` finds the `TypeElement` of `Sample` because the annotation is on a **declaration**.
- `cls.getAnnotation(SourceTag.class)` is a **compile-time language-model API** utility for reading source annotations inside a processor; it is **not** reflection's `java.lang.Class.getAnnotation(...)`. In many processors, using `AnnotationMirror` is advantageous when you do not want to load the annotation type from the processor class loader.
- `round.getElementsAnnotatedWith(TypeNote.class)` **does not return a separate Element for the generic type argument `String`** in this fixture; the observed output is `0`. This illustrates a limitation of the **Element**-lookup API, not a claim that a processor cannot read `TYPE_USE`.
- `member.asType()` returns the declared type of the field. For the field `List<String> names`, that type is a `DeclaredType`; `getTypeArguments().get(0)` retrieves the `TypeMirror` of `String` inside `List`.
- `typeArg.getAnnotationMirrors()` is the key: it provides annotations on the corresponding **type use**, including `SOURCE` retention when the source model contains that information.

This processing logic is intentionally limited to **a known fixture having one field with one type argument**. Production processors must check `TypeKind`, `instanceof DeclaredType`, the number of type arguments, member variety, and invalid/partially compiled code states before casting or calling `get(0)`.

### 4.2. javac Commands (Using JDK 17+)

From the directory containing `src`, pre-create the two output directories `classes` and `out`, or let `javac -d` create the package tree under the output directory:

```bash
javac --release 17 -d classes src/demo/SourceTag.java src/demo/TypeNote.java src/tools/InspectProcessor.java
javac --release 17 -cp classes -processorpath classes -processor tools.InspectProcessor -d out src/demo/SourceTag.java src/demo/TypeNote.java src/demo/Sample.java
```

Phase 1 compiles the annotation types and the processor. Phase 2 uses `-processorpath classes` and `-processor tools.InspectProcessor` to **explicitly activate** the processor; there is no need to rely on an IDE or build tool auto-discovering the processor. `-cp classes` lets the compiler see the compiled annotation types; the source annotation files are also listed in the sample compilation pass.

**Stdout of the second `javac` command:**

```text
DECLARED-MATCHES=1
TYPE-USE-MATCHES=0
SOURCE-TAG=compile-only
TYPE-ARG=TypeNote
```

This is the verified output from running with `javac 21 --release 17`; the fixture parameters and APIs are all Java 17 compatible. If another processor generates additional source files or a build executes multiple rounds, the number of times output is printed may differ; therefore, **do not treat the example's round count as a contract for all processors**.

To inspect the class file after compilation:

```bash
javap -v -classpath out demo.Sample
```

When inspecting `demo.Sample`, **there will be no usages of `@SourceTag("compile-only")` and `@TypeNote("item-type"/"result-type")`** in the corresponding annotation metadata of `Sample.class`, because both types use `SOURCE` retention. Do not inspect `SourceTag.class`/`TypeNote.class` and draw the wrong conclusion: those are class files of the annotation type *definitions*, not the annotated `Sample`.

The sample program has no `main` method: **the output here appears during compilation via the annotation processor**, not as the result of running `java demo.Sample`.

## 5. Why getElementsAnnotatedWith Does Not Replace Reading TypeMirror

The JSR 269 model distinguishes between **declarations** and **type uses**:

```text
TypeElement Sample
├── annotation on declaration: @SourceTag("compile-only")
├── VariableElement names
│   └── DeclaredType List<...>
│       └── TypeMirror String
│           └── @TypeNote("item-type")   ← TYPE_USE
└── ExecutableElement names()
    └── returnType: DeclaredType List<...>
        └── TypeMirror String
            └── @TypeNote("result-type") ← TYPE_USE
```

`RoundEnvironment.getElementsAnnotatedWith(...)` helps find annotated **elements**. It is not a recursive query across every child `TypeMirror`, every type variable, every type argument, and every annotated Java expression.

For `TYPE_USE`, the processor must navigate to the **appropriate type location**:

- Field: `VariableElement.asType()`, then locate the right level inside `DeclaredType`/`ArrayType`/`WildcardType`/... .
- Method: `ExecutableElement.getReturnType()`, `getParameters()` and parameter types, exception types, or type parameters when present.
- Supertype: `TypeElement.getSuperclass()` and `getInterfaces()` if annotations are placed on the relevant type uses.
- Generic nested type: traverse `DeclaredType.getTypeArguments()` across multiple levels. A type `Map<@A String, List<@B Integer>>` has annotations along **two different paths**.
- Array: annotations can sit on the component type or at different array levels; do not assume all annotations are attached at the same level.

`Element.getAnnotationMirrors()` and `TypeMirror.getAnnotationMirrors()` are both valid, but they inspect **two different model objects**. Retrieving annotation mirrors from a field declaration **does not guarantee finding** an annotation attached only to a type argument. Similarly, retrieving annotations on the outer type `List<...>` does not automatically include annotations on the type argument `String`.

You should not simply count `getElementsAnnotatedWith` and conclude "the processor does not support annotations on type uses". The correct conclusion is: **type-use annotations require reading the right part of the type model or traversing deeper into the syntax tree when needed**.

## 6. Practical Limitations of the Standard Annotation Processing Model

### 6.1. SOURCE Retention Is Not the Limitation

A `@Retention(SOURCE)` annotation on a class declaration can be read by a processor right during compilation. A `@Retention(SOURCE)` annotation on a type argument can also be read using the corresponding `TypeMirror.getAnnotationMirrors()` as shown in the example. Failing to find an annotation is usually due to **the location or the API being queried**, not because the retention is `SOURCE`.

Conversely, reflection when running `java` **has no magic** to recover SOURCE annotation usages that have already been discarded from bytecode.

### 6.2. Not Every Type-Use Position Is an Element

Java allows type-use annotations in many positions, such as generic arguments, array components, casts, matching `instanceof` patterns, object creation expressions, local variable types, and other type positions permitted by the language. Not all of those syntactic positions are represented as an `Element` obtainable via `RoundEnvironment.getElementsAnnotatedWith`.

`TypeMirror` is very useful when a type is associated with declarations such as fields, methods, parameters, and supertypes. However, to inspect **an annotation precisely on a cast, expression, syntactic branch, or local variable position**, the `javax.lang.model` model may not provide enough information. With the `javac` compiler, the syntax-tree APIs `com.sun.source.tree` and `com.sun.source.util.Trees`/`TreePathScanner` may be needed to examine `AnnotatedTypeTree` and the corresponding AST positions.

**Important:** `com.sun.source.*` are compiler tree APIs provided by `javac`; the level of support or coupling to the compiler may vary across tools or compilers. Do not treat them as a mandatory part of every JSR 269 implementation.

### 6.3. A Processor Does Not Scan Everything on the Classpath

During a `javac` pass, a processor operates on the **root elements and rounds** provided by the compiler, along with the types it can query through the model. It **does not automatically scan all source files or the entire dependency repository** to find every type-use annotation. In particular, SOURCE annotations are no longer stored in the class files of compiled dependencies, so a processor processing another project **cannot read back SOURCE usages from those dependency class files**.

If the problem requires analyzing all compiled dependencies, you must switch to a bytecode approach; however, SOURCE annotations on compiled usages will still not exist in the bytecode, regardless of how powerful the bytecode reader tool is.

### 6.4. Rounds, Discovery, and Processor Activation

`@SupportedAnnotationTypes` declares the scope of supported annotation names, but it does not mean "whenever an annotation appears on **any type use**, the processor will always be automatically discovered and processed". Activation also depends on build configuration, processor path, the selected processor, the current round, and the kinds of elements the compiler passes in for processing.

In the example, the processor is **explicitly activated via `-processor tools.InspectProcessor`** and there is a `@SourceTag` on the class; we do not rely on whether an annotation located only inside a nested generic argument is sufficient to trigger the processor in every environment.

Across different JDK versions and build tools, annotation processor auto-discovery policies may differ. For a test or pipeline that requires reproducible behavior, configure the processor explicitly.

### 6.5. An Annotation Processor Is Not Where Runtime Logic Runs

A processor can typically use `Messager` to emit compile-time warnings/errors, `Filer` to generate source/resource files, or analyze types and elements according to rules. It **does not cause an annotation type to be retained at runtime**, unless the annotation type already has an appropriate retention policy.

A `SOURCE` annotation is suitable for compile-time linting/checks, adapter generation, rule-based boilerplate generation, or checking type structures while source code is being compiled. If a framework needs to read metadata via reflection after deployment, choose `RUNTIME` for the annotations that need to be read — or produce another intermediate output at compile time.

## 7. AnnotationMirrors, Element Values, and Analysis Safety

`getAnnotationMirrors()` returns `AnnotationMirror` objects, each indicating the **annotation type** and the element values specified in the source/bytecode model. Example:

```java
for (AnnotationMirror annotation : typeArg.getAnnotationMirrors()) {
    System.out.println(annotation.getAnnotationType());
}
```

The snippet above is an illustration assuming `TypeMirror typeArg` is already available; the complete program in section 4 uses this exact API.

If you want to read the `"item-type"` value of `@TypeNote("item-type")`, there are two common approaches:

1. Use a typed proxy via `typeMirror.getAnnotation(TypeNote.class)` in a context where the processor can load the corresponding annotation type, and then call `value()`.
2. Use `AnnotationMirror` and `ElementValuesWithDefaults` via `Elements.getElementValuesWithDefaults(annotation)` to obtain a value model that includes applicable defaults. This is a more general approach when handling multiple annotation types, enum types, or class literals that are difficult to load into the processor class loader.

When reading the model:

- Do not assume an annotation mirror is always at `index 0`, because multiple annotations may be present.
- Verify the exact annotation type by name or model elements instead of casting blindly.
- Do not assume every `TypeMirror` is a `DeclaredType`; primitives, arrays, wildcards, type variables, intersections, and error types have different representations.
- If you need the exact path in nested generic types, write a traversal function that walks **each layer of the type structure**, rather than blindly taking only `getTypeArguments().get(0)` for all cases.
- When processing a program that has compilation errors, you may encounter `ErrorType` or an incomplete model and need to report diagnostics safely instead of crashing the processor.

## 8. Comparison with Reflection and Bytecode Analysis

| Question | JSR 269 processor at compile time | Class-file analyzer | Java reflection at runtime |
| --- | --- | --- | --- |
| Sees `@Retention(SOURCE)` on a class being compiled? | Possible | No, once `SOURCE` is stripped from the target class file | No |
| Sees SOURCE on `List<@TypeNote String>` in source being compiled? | Possible if traversing the right type model/AST | No | No |
| Sees CLASS annotations still stored in the class file? | Possible with the compiler model in the appropriate context | Yes | Not via standard `getAnnotation` |
| Sees RUNTIME annotations? | Possible | Yes | Yes, when using the right element and API |
| Detects annotations on a cast/local type-use? | May require compiler tree APIs | If retention preserves it and the location is encoded appropriately | Not guaranteed by standard declaration reflection APIs |
| Emits warnings at the source location? | Yes, using `Messager`/compiler trees when appropriate | Does not directly have a standard compile-time source model | No |
| Creates Java objects from annotations? | Not the primary purpose | Not the primary purpose | Does not automatically instantiate business objects; only returns reflection metadata |

Reflection also has APIs for type uses retained until runtime, such as `AnnotatedType` and `AnnotatedParameterizedType`. These are **separate runtime APIs**, not `javax.lang.model.type.TypeMirror`. SOURCE annotations do not appear in these runtime APIs because retention already removed the annotation usages from the class file.

## 9. Common Misconceptions

### Misconception 1: "Retention SOURCE Means the Processor Cannot See the Annotation"

False. `@Retention(SOURCE)` can be observed by the compiler/processor while processing source code. The annotation disappears from **the target class file after compilation**, not the moment the compiler starts reading the source.

### Misconception 2: "getElementsAnnotatedWith Will Find Every @TypeNote"

Insufficient. The API returns **Elements**; annotations on nested type arguments, casts, and other type-use positions may not correspond to a declaration element reported by this API. Identify the exact syntactic location and read `TypeMirror.getAnnotationMirrors()` or the appropriate tree API.

### Misconception 3: "getAnnotationMirrors on a Field Must See Annotations in List<@TypeNote String>"

Not necessarily. The field declaration and the `String` type argument are **two different model entities**. In this example, you must traverse from `VariableElement.asType()` → `DeclaredType.getTypeArguments()` → `TypeMirror.getAnnotationMirrors()`.

### Misconception 4: "Having a Processor Means SOURCE Will Appear in Runtime Bytecode"

False. A processor can **generate additional source/resource files** containing analysis results, but it does not automatically change the retention of the original SOURCE usages. `Sample.class` in the example does not contain those usages of SOURCE annotations.

### Misconception 5: "Writing @Target(TYPE_USE) Automatically Makes the Processor Check Every Expression"

False. `@Target` makes annotation placement valid at those locations; it does not write AST analysis logic by itself. To validate type uses in every position, you must define the coverage scope and select the appropriate model/tree APIs.

### Misconception 6: "SOURCE Annotations Can Be Read from a Compiled Dependency JAR"

You cannot read back a SOURCE usage that has already been stripped from a dependency's bytecode. To check those usages, you must process the dependency source during its compilation, or use a separately exported analysis result.

### Misconception 7: "The Processor Must Always Be Invoked Just Because an Annotation Is Present on a Type Argument"

Do not rely on that without testing the processor configuration. In the example, we activate the processor **explicitly** and also have an annotation on a declaration for straightforward verification. Build/CI pipelines need explicit configuration of the processor path, processor selection, and round behavior.

## 10. Workflow for Designing SOURCE Annotations for Type-Use Checking

A workflow to apply in a project:

1. **Determine the retention policy:** if checks are only needed at compile time, `SOURCE` is usually appropriate; do not choose `RUNTIME` just so a processor can read it.
2. **Determine the target:** use `TYPE`/`FIELD`/`METHOD`/... for declarations; `TYPE_USE` for type uses; and `TYPE_PARAMETER` for type-parameter declarations. Targets can be combined when genuinely needed.
3. **Write a reproducible processor:** declare supported annotation types and source version, configure the processor path, and select the processor explicitly in tests.
4. **Start from root/declaration elements:** use `RoundEnvironment` for declaration annotations; retrieve the `Element` instances to analyze.
5. **Traverse the type model:** at fields, methods, parameters, and supertypes, obtain the `TypeMirror`, follow generic arguments, array components, wildcard bounds, etc., and read annotation mirrors at the right level.
6. **Assess model limitations:** if local variables, casts, or expression syntax are needed, consider using `Trees`/`TreePathScanner` in supported compiler environments; do not claim full scanning based solely on `getElementsAnnotatedWith`.
7. **Emit clear diagnostics:** use `Messager` and attach them to the right location when possible; handle cases where types have errors or the compiler runs multiple rounds.
8. **Verify the class file:** for SOURCE, running `javap -v` on the **annotated** class will not show usages of the SOURCE annotation. If you see the annotation name in the class file of the annotation type itself, that is a different situation.
9. **Test counterexamples:** one annotation on a class declaration, one on a nested type argument, one in a return type, and one at an expression/cast position if required by the project. Ensure the analysis code actually inspects every promised location.

**Key takeaway:** SOURCE annotations **can be processed by an annotation processor during compilation**, even in many `TYPE_USE` scenarios. The limitation does not lie in the word `SOURCE`, but in **the ability to observe the annotation's location using the right compile-time API**. `RoundEnvironment.getElementsAnnotatedWith(...)` targets declaration elements, whereas annotations on nested type uses typically must be accessed via `TypeMirror.getAnnotationMirrors()` or compiler tree APIs. After compilation, usages of SOURCE annotations no longer remain in the target class file for reflection/runtime or bytecode tools to read back.
