# Configuring annotation processors in build tools and syncing with IDEs

A Java annotation processor does not run automatically just because the source has `@Generate...` or because the processor JAR is in the project's dependencies. For **annotation checking and code generation at compile time** to be consistent across developer machines, CI, Maven/Gradle, and IDEs, we need to properly configure **where the compiler looks for processors**, **how processors are selected**, **the source set being processed**, **the generated sources directory**, and **the JDK used for compilation**.

A familiar example: a processor reads `@GenerateFlag` and creates the `GeneratedFlag` class during compilation; application code calls `GeneratedFlag.value()`. When the processor runs properly, both the generated code and the application compile. If the IDE does not run the processor even though Maven/Gradle succeeds, the IDE may report `Cannot resolve symbol 'GeneratedFlag'`. If CI switches to JDK 23+ while the configuration relies solely on implicit processor discovery on the classpath, code generation can also suddenly stop working.

**Core principle:** the build script is the primary source of configuration, processors are declared **explicitly**, generated sources directories are managed by the build, and the IDE needs to **reload/sync** the build model rather than using arbitrary custom settings that differ from CI.

## 1. Distinguishing between annotation API, processor, and generated code

Typically, there are three independent roles:

| Component | What does it contain? | Where does it need to appear? |
|---|---|---|
| **Annotation API** | `@interface GenerateFlag` or `@interface Mapper` referenced by application code | Compile classpath of the module using the annotation |
| **Annotation processor** | A class implementing `javax.annotation.processing.Processor` or extending `AbstractProcessor` | Compiler **processor path**, along with dependencies the processor needs at execution time |
| **Generated sources/classes** | Java sources/classes generated by the processor | Included in compilation by the compiler and recognized by the IDE as generated sources |

Example of a project structure:

```text
root/
├── annotation-api/
│   └── src/main/java/com/example/api/GenerateFlag.java
├── annotation-processor/
│   ├── src/main/java/com/example/apt/FlagProcessor.java
│   └── src/main/resources/META-INF/services/
│       └── javax.annotation.processing.Processor
└── app/
    ├── src/main/java/com/example/app/Main.java
    └── build.gradle / pom.xml
```

The processor typically depends on the annotation API so it can read the annotation class. The application module depends on the annotation API to **compile its sources**, and configures the application module's annotation processor to **run the processor during the compile task**. This differs from adding the processor as an ordinary runtime dependency.

Notes:

- **Compile classpath** tells the compiler about types like `GenerateFlag`, `List`, application libraries, etc.
- **Processor path** tells the compiler about the JAR/classes of `FlagProcessor` and dependencies used **by the processor**.
- **Runtime classpath** only needs the classes that the application actually uses at runtime; a processor that runs purely at compile time is usually not needed at runtime.
- Generated code is a *build artifact*, not a source file to be manually copied into `src/main/java` or committed to Git by default.

For simple projects, the annotation and processor can be packaged into a single JAR; however, separating API/implementation prevents the app from carrying all of the processor's heavy dependencies on the runtime or compile classpath. When splitting into modules, you must ensure dependencies and build order produce the processor JAR before the app needs it.

## 2. How does the compiler find and invoke processors?

The standard Java mechanism is the **JSR 269 / Pluggable Annotation Processing API**. A processor typically:

```java
@SupportedAnnotationTypes("com.example.api.GenerateFlag")
@SupportedSourceVersion(SourceVersion.RELEASE_17)
public class FlagProcessor extends AbstractProcessor {
    @Override
    public boolean process(
            Set<? extends TypeElement> annotations,
            RoundEnvironment roundEnv) {
        // Check annotations / generate sources using Filer.
        return true;
    }
}
```

This is a **method skeleton** rather than a self-compiling file: it still needs imports, the actual classes/interfaces, and processor configuration. The processor is loaded by the compiler and then invoked across multiple rounds if necessary. `@Retention(SOURCE)` on the annotation is sufficient for the processor to see the annotation during source compilation; there is no need to force RUNTIME retention if runtime does not consume the metadata.

There are two common ways to select processors:

**A. Service discovery:** the processor JAR contains the file:

```text
META-INF/services/javax.annotation.processing.Processor
```

Inside, each line is the **fully qualified class name** of a processor:

```text
com.example.apt.FlagProcessor
```

When annotation processing is enabled and discovery is permitted on the processor path, Java uses the provider mechanism to locate processors. This service file is a **resource packaged inside the processor JAR**, not a line of code in `pom.xml` or `build.gradle`. If the processor is packaged as a named module (JPMS), it can use the `provides javax.annotation.processing.Processor with ...` declaration in `module-info.java` via the corresponding module-path approach.

**B. Specifying the processor class via `-processor`:** for example:

```bash
javac -processor com.example.apt.FlagProcessor ...
```

This approach selects the class explicitly; when using it, you must ensure the processor and its dependencies are on the appropriate `-processorpath` or `--processor-module-path`. Depending on the build tool, the equivalent option is written in the plugin configuration rather than writing the `javac` command directly.

**Safety and reproducibility:** you should explicitly specify which processors are allowed to run. You should not rely on "whichever JAR happens to be on the compile classpath and has a provider file gets executed" as intended behavior.

## 3. Important change starting in JDK 23: no automatic discovery as before

This is a prominent reason why a build "previously generated code, then lost generated code after upgrading the JDK".

- In JDK versions **up to 22**, traditional `javac` could automatically discover and run processors on the classpath without an explicit annotation processing option.
- **Starting in JDK 23**, `javac` no longer enables annotation processing automatically in that way when there is no explicit annotation processing configuration/option. This change was announced by Oracle/OpenJDK to reduce the risk of unintended processor execution.
- You can specifically request a processor using `-processor`, set the processor path/module path, or enable `-proc:full`/`-proc:only` mode depending on compiler capabilities. For security control, **explicitly specifying the processors to run** and a dedicated path is still better than re-enabling all implicit discovery.

Three main modes:

| Option | Purpose |
|---|---|
| `-proc:none` | Compile **without running** annotation processing |
| `-proc:only` | Run annotation processing only, without proceeding to normal compilation into classes |
| `-proc:full` | Annotation processing **and** compilation |

`-proc:full` has been backported to many LTS update lines, but do not assume every older JDK 17 build supports it: use a still-maintained patch version or specify the processor using `-processor`. When testing on JDK 23+, explicitly setting `-processor` and the processor path makes the outcome clearer.

**Distinguishing the compiler JDK from `--release`:** if you run `javac` from JDK 24 with `--release 17`, the default rules for processor discovery belong to the **running javac (JDK 24)**, whereas `--release 17` controls the target language/API level. Therefore, merely writing `<release>17</release>` or Gradle `options.release = 17` **does not revert JDK 24's discovery behavior back to JDK 17**.

This point is very important when the IDE uses a different JDK from CI even though both build "Java 17".

## 4. Runnable Java 17 example: generating a class during the compile step

This pure `javac` example intentionally **specifies the processor explicitly** so it does not rely on the JDK's default discovery. Even when using a newer JDK, the program is still compiled with `--release 17`.

Place the following three files in **the same empty working directory**. For simplicity, the example uses the *default package*; in real projects, you should use full package names.

### File GenerateFlag.java

```java
import java.lang.annotation.*;

@Retention(RetentionPolicy.SOURCE)
@Target(ElementType.TYPE)
public @interface GenerateFlag {}
```

### File FlagProcessor.java

```java
import java.io.Writer;
import java.util.Set;
import javax.annotation.processing.*;
import javax.lang.model.SourceVersion;
import javax.lang.model.element.*;
import javax.tools.*;

@SupportedAnnotationTypes("GenerateFlag")
@SupportedSourceVersion(SourceVersion.RELEASE_17)
public class FlagProcessor extends AbstractProcessor {
    private boolean created = false;

    @Override
    public boolean process(Set<? extends TypeElement> annotations,
                           RoundEnvironment round) {
        if (round.processingOver() || created) return true;

        for (Element element :
                round.getElementsAnnotatedWith(GenerateFlag.class)) {
            try {
                JavaFileObject file = processingEnv.getFiler()
                        .createSourceFile("GeneratedFlag", element);

                try (Writer out = file.openWriter()) {
                    out.write("public final class GeneratedFlag { "
                            + "public static String value() { "
                            + "return \"processor-ran\"; } }");
                }

                created = true;
                processingEnv.getMessager().printMessage(
                        Diagnostic.Kind.NOTE, "GeneratedFlag created");
            } catch (Exception ex) {
                processingEnv.getMessager().printMessage(
                        Diagnostic.Kind.ERROR, ex.getMessage(), element);
            }
        }
        return true;
    }
}
```

Main idea: `RoundEnvironment` finds classes annotated with `@GenerateFlag`; `Filer.createSourceFile` creates a new Java source file; `Messager` prints a NOTE so we know the processor ran. The `created` flag prevents creating duplicate sources with the same name in subsequent rounds. In real-world applications, generated source names must have proper namespacing/collision-avoidance logic and thorough validation.

### File Main.java

```java
@GenerateFlag
public class Main {
    public static void main(String[] args) {
        System.out.println(GeneratedFlag.value());
    }
}
```

Notably, `Main.java` **does not contain a definition of `GeneratedFlag`**. That class must be generated by the processor during compilation.

### How to compile

Create three empty directories in the current directory: `processor-classes`, `app-classes`, and `generated`. Then:

```bash
javac --release 17 -d processor-classes GenerateFlag.java FlagProcessor.java

javac --release 17 \
  -cp processor-classes \
  -processorpath processor-classes \
  -processor FlagProcessor \
  -s generated \
  -d app-classes \
  Main.java

java -cp app-classes Main
```

The line-continuation `\` characters here use **Bash** syntax; in Windows PowerShell or cmd, put the entire `javac` command on **one line**:

```powershell
javac --release 17 -cp processor-classes -processorpath processor-classes -processor FlagProcessor -s generated -d app-classes Main.java
java -cp app-classes Main
```

Output:

```text
Note: GeneratedFlag created
processor-ran
```

`Note: GeneratedFlag created` is printed by `javac` during annotation processing; `processor-ran` is the **stdout of the Main program**. A new file appears:

```text
generated/GeneratedFlag.java
```

and the corresponding `.class` files appear in `app-classes`.

This experiment was verified with a `javac` supporting `--release 17`; both the processor and the application compile successfully, the generated source file exists, and the program prints `processor-ran`. This is clearer proof than merely checking that the source contains `@GenerateFlag`.

Try **removing `-processor FlagProcessor` and `-processorpath processor-classes`** when running with JDK 23+ javac, then clean `app-classes`/`generated`: if there is no other configuration enabling processing, the `GeneratedFlag` class will not be generated and `Main.java` will fail with "cannot find symbol". That is a test that helps identify a missing processor, not a bug in the `@GenerateFlag` annotation.

## 5. Maven 3.x: declaring the compiler plugin and processor path

With **Maven 3 + Maven Compiler Plugin 3.x**, the standard approach is to configure `maven-compiler-plugin` in `pom.xml`. The example below uses **fictitious coordinates** to illustrate two pre-packaged artifacts:

- `com.example:flag-annotations:1.0.0` contains the annotation API.
- `com.example:flag-processor:1.0.0` contains the processor and service registration / processor class.

These are **not real dependencies that can be downloaded from Maven Central**. Replace them with the coordinates and versions of the project/library you actually use.

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0
         https://maven.apache.org/xsd/maven-4.0.0.xsd">
  <modelVersion>4.0.0</modelVersion>

  <groupId>com.example</groupId>
  <artifactId>app</artifactId>
  <version>1.0.0</version>

  <properties>
    <maven.compiler.release>17</maven.compiler.release>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
  </properties>

  <dependencies>
    <!-- Annotation type visible when compiling application source. -->
    <dependency>
      <groupId>com.example</groupId>
      <artifactId>flag-annotations</artifactId>
      <version>1.0.0</version>
      <scope>provided</scope>
    </dependency>
  </dependencies>

  <build>
    <plugins>
      <plugin>
        <groupId>org.apache.maven.plugins</groupId>
        <artifactId>maven-compiler-plugin</artifactId>
        <version>3.14.1</version>
        <configuration>
          <release>17</release>

          <annotationProcessorPaths>
            <path>
              <groupId>com.example</groupId>
              <artifactId>flag-processor</artifactId>
              <version>1.0.0</version>
            </path>
          </annotationProcessorPaths>

          <annotationProcessors>
            <annotationProcessor>com.example.apt.FlagProcessor</annotationProcessor>
          </annotationProcessors>
        </configuration>
      </plugin>
    </plugins>
  </build>
</project>
```

**Note:** `com.example.apt.FlagProcessor` in this POM is an **illustrative class name of a real packaged processor**. It differs from `FlagProcessor` in the pure `javac` default-package example in section 4; you must choose the **exact fully qualified name** when applying it to your project.

Explanation of key points:

- `<release>17</release>`: compiles against Java 17 source/API; **the actual JDK running Maven must still support this option**.
- `<annotationProcessorPaths>`: places the processor JAR and its dependencies on the processor path used by the plugin, separate from the application's compile classpath.
- `<annotationProcessors>`: lists the processor classes you want to run rather than allowing every discovered processor to run. This is a transparent allowlist and helps identify `processor not found` errors.
- The `flag-annotations` dependency: provides the annotation type for application sources. `provided` is used **if the runtime does not need that annotation JAR itself**; for annotations used at runtime/reflection, choose the scope appropriate for your actual needs. Do not copy `provided` unconditionally for every library.
- There is no need to add the processor as an ordinary `compile`/`implementation` dependency just to activate it.

Verification commands:

```bash
mvn -U clean compile
mvn -q -DskipTests=false test
```

`mvn clean compile` clears old generated artifacts and verifies that the processor actually creates new sources. The default path is typically `target/generated-sources/annotations` in common plugin configurations; builds can customize it, so rely on `-s`/the actual configuration rather than assuming every project is identical.

If the processor is only used for `src/test/java`, you must configure **test compilation** accordingly; the paths/classpaths of main and test do not automatically match. When editing the POM, **reload the Maven project** in your IDE instead of merely adding a folder manually.

### Caution regarding JDK 23 and Maven plugin versions

Starting in JDK 23, you should not rely on the legacy auto-discovery. Specify processors explicitly in the appropriate Maven plugin. With Maven Compiler Plugin 3.x, `annotationProcessorPaths` and `annotationProcessors` are the standard configuration. Documentation across plugin versions may differ regarding the default for `proc`; prioritize the documentation for **the exact version pinned in your POM** and the behavior of the actual JDK used by Maven.

If you intentionally use `<proc>full</proc>` to enable broad discovery, understand that it allows processors found via the corresponding mechanism to run; this approach **does not replace** managing which processors are permitted to execute.

## 6. Maven 4 + Maven Compiler Plugin 4.x: dependency type for processors

**Do not confuse Maven 3.x configuration with Maven 4.x.** Maven Compiler Plugin **4.x** versions targeting Maven 4 support declaring processors via dependency types such as:

- `processor`;
- `classpath-processor`;
- `modular-processor`.

Example **illustrative snippet** following the Maven 4 design (must be placed inside a valid Maven 4 POM with a real dependency version chosen):

```xml
<dependencies>
  <dependency>
    <groupId>com.example</groupId>
    <artifactId>flag-processor</artifactId>
    <version>1.0.0</version>
    <type>classpath-processor</type>
  </dependency>
</dependencies>
```

`classpath-processor` indicates a processor that runs from the processor classpath; `modular-processor` is for modular processors that run via the module path; `processor` lets the plugin infer the location when appropriate. Choose the right type for how the processor is packaged and the documentation of the version you use; do not assign multiple types indiscriminately.

This approach produces explicit dependency metadata so the plugin knows it is a processor rather than an ordinary runtime library. **Do not convert an entire Maven 3 configuration to Maven 4 via mechanical renaming**: check whether Maven 4 and the 4.x plugin have actually been adopted by the project, as well as the configuration of each processor.

## 7. Gradle: configuring annotationProcessor separately from compileOnly/implementation

The Gradle Java plugin provides a dedicated dependency configuration named `annotationProcessor`. For the main source set, `compileJava` uses a processor path derived from this configuration; `Gradle` does not simply treat every JAR on the compile classpath as a processor.

### build.gradle (Groovy DSL)

```groovy
plugins {
    id 'java'
}

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(17)
    }
}

dependencies {
    // Annotation type used by source code.
    compileOnly 'com.example:flag-annotations:1.0.0'

    // Actual compiler plugin / code generator.
    annotationProcessor 'com.example:flag-processor:1.0.0'

    // If test sources also use the annotation/processor:
    testCompileOnly 'com.example:flag-annotations:1.0.0'
    testAnnotationProcessor 'com.example:flag-processor:1.0.0'
}
```

### build.gradle.kts (Kotlin DSL)

```kotlin
plugins {
    java
}

java {
    toolchain {
        languageVersion.set(JavaLanguageVersion.of(17))
    }
}

dependencies {
    compileOnly("com.example:flag-annotations:1.0.0")
    annotationProcessor("com.example:flag-processor:1.0.0")

    testCompileOnly("com.example:flag-annotations:1.0.0")
    testAnnotationProcessor("com.example:flag-processor:1.0.0")
}
```

The `com.example` coordinates are **illustrative** and will not run without the corresponding artifacts; replace them with real artifacts or `project(":annotation-processor")` in a multi-module project.

**Do not confuse them:**

- `implementation`: libraries needed for application sources to compile and run.
- `compileOnly`: libraries needed at compile time that are not automatically included at runtime; suitable for an annotation API not needed at runtime.
- `annotationProcessor`: annotation processors for the `main` compilation step.
- `testAnnotationProcessor`: annotation processors when compiling the **test source set**.
- `testImplementation` or `testCompileOnly`: test source dependencies, independent of whether the processor is run.

If an annotation has RUNTIME retention and the application actually reads it via reflection, placing the annotation API only in `compileOnly` may be **inappropriate**; choose `implementation` or a scope that ensures the runtime classpath meets your needs.

For internal dependencies, you can use:

```groovy
dependencies {
    compileOnly project(':annotation-api')
    annotationProcessor project(':annotation-processor')
}
```

Gradle will build the processor project according to the dependency graph when configured properly; do not manually copy a JAR into an IDE directory and expect CI to know about it automatically.

### Verifying Gradle with an actual build

```bash
./gradlew clean compileJava
./gradlew clean compileTestJava
./gradlew dependencies --configuration annotationProcessor
./gradlew compileJava --info
```

On Windows, use `gradlew.bat` instead of `./gradlew` when running in cmd/PowerShell as appropriate. With Gradle Wrapper, use the wrapper committed in the repo so the Gradle version is consistent between local machines and CI. The `dependencies` command helps verify that the right processor artifact appears in the configuration.

Typically, Java annotation processor generated sources are located under `build/generated/sources/annotationProcessor/java/main` for the main source set and a similar location for tests. However, this is a **Gradle build output directory**, not a mandatory directory for all configurations/plugins. Check `JavaCompile.options.generatedSourceOutputDirectory` or task outputs if the project has a custom configuration.

### Adding compiler arguments when a processor has custom options

A processor can read options from `ProcessingEnvironment.getOptions()` when the compiler passes `-Akey=value`. For example, if **the processor actually supports** the option `flag.mode=strict`:

```groovy
tasks.withType(JavaCompile).configureEach {
    options.compilerArgs += ['-Aflag.mode=strict']
}
```

```kotlin
tasks.withType<JavaCompile>().configureEach {
    options.compilerArgs.add("-Aflag.mode=strict")
}
```

If the processor does not declare or read the `flag.mode` option, this example has no functional effect and the compiler may emit a warning about an unrecognized option. **This is not a standard Java flag**: the value is part of the processor's own contract.

In Gradle, use appropriate compiler argument providers or task inputs if an option affects generated code output and you want to ensure accurate incremental builds / build cache behavior. Do not store inputs that change the output in a place outside the Gradle model unknown to the build task.

## 8. Moving from javac commands to build tools: configuration mapping

| `javac` mechanism | Maven 3.x | Gradle |
|---|---|---|
| `-cp` / `--class-path` | `<dependencies>` and appropriate scope | `implementation`, `api`, `compileOnly`, ... |
| `-processorpath` | `<annotationProcessorPaths>` | `annotationProcessor` / `testAnnotationProcessor` |
| `-processor com.example.apt.FlagProcessor` | `<annotationProcessors>` | `-processor` compiler args option when an explicit allowlist is also needed |
| `-Akey=value` | Appropriate compiler argument/processor option | `options.compilerArgs` / argument provider |
| `-s path` | Plugin-managed generated-sources directory | Generated source output directory of `JavaCompile` |
| `--release 17` | `<release>17</release>` | Toolchain and/or `options.release = 17` |
| `-proc:none` | `proc=none` configuration if disabling is needed | `options.compilerArgs` if disabling explicitly is required |

**Two notes on mapping:**

1. `annotationProcessor` is a **dependency configuration**, not an annotation type. Source compilation can succeed even if the processor path configuration is empty if application code does not yet reference the generated classes. Therefore, a green build does not always prove the processor ran.
2. `-processor` means **specifying which processor class to execute**, whereas `-processorpath` only specifies **where to load processors from**. A processor class being on the path does not guarantee it is selected, and selecting a class name without the artifact means the compiler cannot run it either.

To investigate the root cause of a failure, verify **both sides**: discovery/selection **and** classpath/path.

## 9. Syncing IntelliJ IDEA with Maven/Gradle

According to IntelliJ IDEA documentation, for Maven/Gradle projects that configure annotation processors in their build script, the IDE can **automatically enable annotation processing and import the processor path** when importing/reloading the project.

IDE settings location:

```text
Settings
  → Build, Execution, Deployment
  → Compiler
  → Annotation Processors
```

This page may include the following options:

- **Enable annotation processing:** enables processing when the IDE compiles using IntelliJ's own compiler.
- **Obtain processors from project classpath** or **Processor path:** selects the processor source per profile and import configuration.
- **Processor FQ Name:** a specific list of processors if explicitly specified.
- **Production sources / Test sources:** locations of generated sources from IDE builds.
- **Annotation processor options:** processor-specific option pairs (if supported by the tool).

For projects **imported from Maven/Gradle**, you should generally:

1. **Update `pom.xml` or `build.gradle(.kts)` first.**
2. **Reload All Maven Projects** or **Reload All Gradle Projects** so the IDE picks up the new model.
3. Verify the compiler JDK, processor path, and **Enable annotation processing** if IntelliJ builds internally.
4. If IntelliJ uses **delegated build/run** via Gradle, check the actual Gradle configuration; in this case, the build engine is Gradle, so the IDE's internal compiler settings do not override the Gradle configuration.
5. Verify that the generated sources directory is properly marked and recognized. With Maven, the import mechanism may look for directories under `target/generated-sources`; with Gradle, the path is typically in the build directory loaded by the IDE from the Gradle model.

**Do not maintain two conflicting manual configurations**: the IDE enables processor A while CI runs B; the IDE uses a different version; a custom output directory is set that the build tool is unaware of. When that happens, the editor "sees" a class that CI fails to generate, or CI succeeds while the editor shows red errors. Prioritize importing from the build script to prevent drift.

### Choosing the JDK in three different places

When discrepancies arise, distinguish between:

- **Project SDK/Language Level:** tells the IDE which version the source code targets.
- **JDK running Maven/Gradle:** the JVM executing the build tool/compilation (Gradle may use a separate toolchain for `JavaCompile`).
- **`--release` or target compatibility:** the compiled API/language/bytecode level.

For example: IDE Project SDK 17, Gradle daemon running on JVM 21, Java toolchain configured to 17; another project using Maven on JDK 24 with `<release>17</release>`. **These are not identical configurations**, especially since `javac` annotation processing behavior varies with the executing JDK version.

To debug, inspect the IDE's **Build Output** and the actual command line / Gradle task / Maven goal. If code is generated on the CLI but the IDE still reports unresolved symbols, check **Reload Project**, generated source roots, and build delegation before modifying Java source files.

## 10. Eclipse and other IDEs: same principles, different integrations

Eclipse/JDT has its own annotation processing and build integration mechanisms. When importing a Maven project, it may use Maven integration and annotation processing support components; Gradle projects may use Buildship/Gradle import. Depending on the IDE version and installed plugins, the level of automatic processor configuration, generated source folder setup, and incremental behavior may differ.

Therefore, a safer approach than following a fixed menu checklist is:

1. Verify `mvn clean compile` or `./gradlew clean compileJava` **on the command line** as the baseline.
2. Ensure the IDE has imported the project from the correct build file and the dependency model is refreshed.
3. Check whether annotation processing is enabled for the **actual module and source set**.
4. Verify the processor JAR, generated sources folder, output path, and JDK/toolchain.
5. If the IDE integration is incomplete, you can **delegate the build to Maven/Gradle**, instead of manually adding JARs in the IDE and treating that as the primary configuration.

There is no guarantee that every IDE version uses the same paths or handles `META-INF/services` the same way, so prioritize the documentation for the specific IDE version you are using.

## 11. CI and reproducible builds: criteria for verifying that a processor runs

A pipeline should verify not only that **the Java code compiles successfully**, but also that **the expected artifacts are actually generated**.

Verification steps:

1. **Pin the JDK/toolchain** and Maven/Gradle/Compiler Plugin versions.
2. **Run a clean build** to remove stale outputs that could mask a processor failing to run.
3. **Check the invoked tasks/goals**: Maven `compiler:compile`, Gradle `compileJava`, or the corresponding task—not just `test` tasks that may be cached/up-to-date.
4. **Verify the generated source path** and actual class files (or run a smoke test using the generated classes).
5. **Add a negative test**: intentionally provide an invalid annotation and expect the processor to emit `Diagnostic.Kind.ERROR` if the processor performs validation.
6. **Keep compiler options consistent**, including `-A...`, source sets, JDK, and processor selection.
7. **Do not commit generated build outputs** as a temporary workaround for the IDE: if `GeneratedFlag.java` already sits in the source tree, the build may pass even when the processor is not triggered.

A very useful test is like the example in section 4: the `Main` class references `GeneratedFlag` **without providing that class in the initial sources**. If compiling on a clean build results in `GeneratedFlag` existing and `Main` running correctly, you have direct proof of code generation.

For processors that only emit warnings/checks without generating sources, design an input file that **must trigger a diagnostic error** to verify the processor actually runs. A green build of a program that does not use generated classes can be a "false positive" for annotation processing configuration.

## 12. Incremental compilation and generated sources

Especially with Gradle, annotation processing affects **incremental Java compilation** and the build cache. Gradle distinguishes processors that can be processed incrementally under models such as **isolating** and **aggregating**, when they meet Gradle's constraints.

Concepts:

- **Isolating:** output primarily originates from a single annotated input; Gradle can link generated files to their corresponding source.
- **Aggregating:** output aggregates multiple annotated sources, such as indexing all `@Handler` elements; changing one input may affect the aggregated artifact.
- **Non-incremental:** Gradle may need to recompile more broadly or in full if the processor does not satisfy the corresponding contract.

Do not declare a processor as isolating/aggregating merely to speed things up; if the processor does not adhere to Gradle's input/output access model, the output may **fail to update adequately** when sources change. Refer to Gradle's "Incremental annotation processing" documentation and rules regarding `Filer`, classpath, annotation retention, and task inputs.

**Generated source outputs are build products:**

- Do not manually edit files in `target/generated-sources` or `build/generated/...`; the next build may overwrite or delete them.
- Do not generate into `src/main/java` unless there is a clear architectural requirement and an overwrite-prevention mechanism. Doing so easily leads to duplicate classes, Git noise, and the IDE seeing stale sources.
- When upgrading a processor version that changes output, run a clean build once to remove old sources/classes.
- If the processor reads external configuration files, the tool must declare these inputs to the build system so the cache/incremental compiler does not reuse stale results incorrectly.
- For the `main` and `test` source sets, output folders and processor dependencies may differ; ensure both are wired into the IDE model.

## 13. Common errors and quick diagnosis

| Symptom | Common cause | First check |
|---|---|---|
| `Cannot find symbol GeneratedX` during compilation | Processor did not run or did not generate the class; generated sources were not compiled | Check `-processor`/processor path, generated directory, clean compile |
| Maven/Gradle CLI build succeeds, IDE editor shows red errors | IDE has not reloaded, generated sources are not recognized, different JDK/profile | Reload project, check build delegation and annotation processing settings |
| IDE build succeeds, CI fails | Depends on configuration present only on the IDE machine or stale outputs | CI clean build with pinned Wrapper/JDK |
| Generated code disappears after upgrading to JDK 23+ | Relied on classpath auto-discovery | Explicitly declare processor and processor path |
| `Annotation processor 'X' not found` | Missing processor JAR or wrong class name | Check dependency resolution, FQCN, processor path |
| `ServiceConfigurationError` / provider fails to load | Invalid service file, class not packaged, or missing processor dependency | Check `META-INF/services/...` inside the JAR and the processor's classpath |
| `FilerException: Attempt to recreate a file` | Processor generates a duplicate file with the same name across multiple rounds or from multiple processors | Log output name/origin, prevent duplicate generation |
| Sources generated but IDE does not update | Generated folder not recognized by the model, task did not run, or stale cache | Inspect generated output, rebuild/reimport, check source roots |
| Test sources missing generated classes | Processor only configured for `main` | Corresponding Gradle `testAnnotationProcessor` / Maven testCompile |
| Build very slow or incremental runs produce wrong results | Processor is non-incremental or inputs/outputs are undeclared | Check Gradle `--info`, processor documentation, compare with a clean build |
| Processor runs but finds no annotations | Mismatched `@SupportedAnnotationTypes`/`@Target`/retention, wrong package | Verify exact FQCN, sources being compiled, and rounds |
| `-proc:none` is enabled | Annotation processing is disabled | Inspect actual compiler arguments, remove flag if processor is needed |

### Do not treat the symptom by copying generated classes

If someone copies `GeneratedFlag.java` from `build/generated` into `src/main/java`, the red errors in the IDE may disappear, yet CI still lacks the processor. Later, when the processor is fixed and re-enabled, the project can hit a **duplicate class** error or end up with two different versions. The right fix is to correct the **build configuration, dependencies, and IDE import**.

### Ask "who is doing the compiling?" before changing settings

Four questions to check in order:

1. Is the command executed by `javac`, Maven, Gradle, or the IDE compiler?
2. Which actual JDK runs the compiler, and what is the `--release`/toolchain?
3. Are the processor path, processor class selection, and source set being compiled accurate?
4. Do the generated sources appear on the filesystem, and does the IDE import the roots properly from the build system?

That is how you distinguish between an error where **the processor is not executed**, an error where **the processor runs but receives no input**, an error where **the processor runs and emits a validation error**, and an error where **the IDE fails to index the output**.

## 14. Configuring processor options consistently

Many processors accept `-Akey=value`, retrieved via:

```java
String mode = processingEnv.getOptions().get("flag.mode");
```

This is a Java snippet **inside the processor**, not a standalone statement; `flag.mode` is an option name defined by the processor itself, not a standard Java option.

With Maven 3.x, flags can be passed via `compilerArgs` when supported by the plugin/version:

```xml
<configuration>
  <compilerArgs>
    <arg>-Aflag.mode=strict</arg>
  </compilerArgs>
</configuration>
```

With Gradle Groovy:

```groovy
tasks.withType(JavaCompile).configureEach {
    options.compilerArgs += ['-Aflag.mode=strict']
}
```

With Gradle Kotlin DSL:

```kotlin
tasks.withType<JavaCompile>().configureEach {
    options.compilerArgs.add("-Aflag.mode=strict")
}
```

For the compiler to recognize this option as **declared and supported by the processor**, the processor can use `@SupportedOptions("flag.mode")` or override `getSupportedOptions()`. If undeclared, `javac` may warn that the option was not recognized by any processor.

When the same option affects code generation, standardize it in the build script/CI; do not set `flag.mode=strict` separately only in the IDE. For Gradle incremental builds/build cache, option values that affect task outputs must be modeled appropriately, such as via a Compiler Argument Provider when dynamic inputs are involved.

## 15. Security notes and limitations of annotation processing

**An annotation processor is code executed by the compiler environment during the build.** A processor JAR is not a "passive" configuration file: it can execute Java code whenever someone builds the project.

Therefore:

- Use dependencies from trusted sources, pin versions, and inspect the dependency chain.
- Avoid auto-execution of processors that happen to appear on the compile classpath; allow only known and necessary processors.
- Do not unconditionally enable `-proc:full` to scan everything without a security review.
- Do not pass secrets in `-A...` if they could be exposed in build logs, diagnostics, or outputs. Use secret-management mechanisms provided by CI/build tools and restrict how processors handle them.
- Inspect the output generated by processors, because generated code becomes part of the final program's sources.
- Distinguish source-inspection tools from true annotation processors: annotation processors are invoked by the compiler, whereas some standalone code generators use custom Gradle/Maven tasks or extensions rather than JSR 269.

If you use Kotlin `kapt`, Kotlin Symbol Processing (KSP), or a mixed Kotlin/Java project, the configuration may differ from **pure Java `annotationProcessor`**. Do not assume the Gradle Java plugin's `annotationProcessor` will process all Kotlin sources; use the plugin/task suited to the technology in use.

## 16. Practical exercises and knowledge check

### Exercise 1 — Annotation API present but processor missing

A project has `implementation("com.example:annotations:1.0")`, so sources containing `@Mapper` compile, but `UserMapperImpl` is not generated. What could be the cause?

**Answer:** having the annotation type on the compile classpath **does not guarantee that the processor is configured or running**. Check the corresponding `annotationProcessor(...)` in Gradle or the processor path/processor selection in Maven. Additionally, verify that the processor JAR actually generates that class type and receives valid annotation inputs.

### Exercise 2 — Changing the JDK and --release

Maven runs on JDK 24 with `<release>17</release>`. Can you rely on JDK 17 javac's auto-discovery rules?

**Answer:** no. `--release 17` restricts the language/API target, whereas the default annotation processor handling follows the behavior of the running **JDK 24 javac**. You need to configure the processor explicitly.

### Exercise 3 — Choosing a Gradle configuration

Which configuration is most suitable for the `main` Java compiler to run a processor without placing the processor on the runtime classpath?

**Answer:** `annotationProcessor("group:processor:version")`. For the annotation API, use `compileOnly` if it is only needed at compile time, or `implementation` if the application needs it at runtime.

### Exercise 4 — IDE differs from CI

`./gradlew clean compileJava` succeeds and generated sources exist in `build/generated`, yet IntelliJ reports unresolved symbols. Should you copy the generated files into `src/main/java`?

**Answer:** no. Reload the Gradle project, and check how the IDE delegates builds, the project SDK/toolchain, annotation processing settings, and generated source roots.

### Exercise 5 — ServiceLoader and processor selection

A JAR contains `META-INF/services/javax.annotation.processing.Processor`, but a JDK 23 build has no annotation processing options or processor path. Is simply placing the JAR on the compile classpath enough?

**Answer:** you should not expect it to work. JDK 23+ requires explicit configuration to enable annotation processing. Specifying the processor and processor path via the build tool is much more reliable.

### Exercise 6 — In which round is the file generated?

The processor generates `GeneratedFlag.java` in Round 1. Do you need to manually recompile `GeneratedFlag.java` like a normal source file?

**Answer:** when `javac` performs annotation processing according to contract and the file is properly created via `Filer`, the compiler includes the new source in subsequent rounds/compilation; the `javac` experiment above proved it gets compiled into `GeneratedFlag.class` within that same build. There is no need to copy it into the source tree or run a separate manual compile command for this case.

### Exercise 7 — CI build is green while the processor is disabled

If the application does not reference any generated classes, does a successful `mvn compile` prove that the processor ran?

**Answer:** no. You need to inspect outputs/diagnostics, create an invalid test input that must trigger an `ERROR`, or add a smoke test referencing the generated class.

### Exercise 8 — -Werror and processor diagnostics

A processor prints a `WARNING` because an input is suboptimal. With `-Werror`, can the build fail?

**Answer:** yes, because the flag instructs the compiler to treat warnings as errors as specified. To see the actual situation, check the compiler args and diagnostics in the build log.

### Exercise 9 — Where the "source of truth" configuration lives

The processor needs to run in CI, Maven CLI, and IntelliJ. Should you only check "Enable annotation processing" in the IDE and leave the processor undeclared in the POM?

**Answer:** no. Declare it completely in the POM and reload the Maven project; IDE settings provide corresponding support and do not replace the build script.

### Exercise 10 — Test source set

Main sources have code generated properly by Gradle, but code in `src/test/java` that relies on the processor fails. What should you check?

**Answer:** the processor dependency for the test source set, such as `testAnnotationProcessor`, and the annotation API for tests; do not assume `annotationProcessor` from main automatically applies to every compilation task.

## 17. Implementation checklist and official documentation

Before concluding that "annotation processing is working", verify that:

- [ ] The right **actual JDK running compilation** and source/target toolchain are used.
- [ ] The annotation API is on the compile classpath of the source set that uses it.
- [ ] The processor JAR **and its dependencies** are on the processor path.
- [ ] The processor is properly selected/registered (FQCN, service file, or module provider).
- [ ] JDK 23+ has an explicit configuration enabling annotation processing.
- [ ] `mvn clean compile` or `./gradlew clean compileJava` actually generates code into a clean output.
- [ ] Generated sources are managed by Maven/Gradle; outputs are not copied/committed as a substitute for the build.
- [ ] The IDE has imported/reloaded the build model, with the appropriate JDK and generated source roots.
- [ ] CI uses reproducible versions and has smoke/negative tests.
- [ ] Processor `-A...` options are declared and synchronized across build/CI/IDE.
