# `@Documented` and Publishing Annotations in Javadoc

## 1. What Is `@Documented` Used For?

In Java, a custom annotation can attach metadata to a class, method, field, or other elements. However, **not every annotation appearing in source code is automatically published in the API documentation generated by `javadoc`**.

`java.lang.annotation.Documented` is a **meta-annotation** used on an **annotation type declaration**. When an annotation type is marked with `@Documented`, usages of that annotation are considered **part of the public contract** of the annotated element. Documentation tools such as `javadoc` will, by default, display that annotation when generating documentation for the corresponding element.

Example:

~~~java
import java.lang.annotation.Documented;
import java.lang.annotation.ElementType;
import java.lang.annotation.Target;

@Documented
@Target(ElementType.METHOD)
@interface PublicRule {
    String value();
}
~~~

When `@PublicRule("must-validate")` is applied to a method belonging to a public API, the Javadoc tool will by default display that annotation's information in the method's documentation section.

Without `@Documented`, Javadoc by default **does not publish the usage of that annotation** on the API declaration, even though the annotation still exists in source code and may be processed by other tools.

Important point: **`@Documented` controls the presentation of metadata in API documentation**; it does not determine where an annotation is allowed to be placed, nor does it generate business behavior on its own.

## 2. Mechanism: Declaring the Annotation, Using the Annotation, Generating Javadoc

There are three distinct places to distinguish:

1. **Defining the annotation type** with `@interface`. You apply `@Documented` to this definition.
2. **Using the annotation** on a class or method, for example `@PublicRule("must-validate")`. This is where the documentation tool can display the metadata.
3. **Running the `javadoc` tool** to generate HTML or a documentation format provided by a doclet. It is the tool that reads the code/metadata and decides how to display it based on `@Documented`.

~~~text
@Documented
@interface PublicRule { ... }
            |
            | publishes the annotation type in the API contract
            v
@PublicRule("must-validate")
public void save() { ... }
            |
            v
      javadoc processes
            |
            v
Public method documentation displays @PublicRule along with its value
~~~

If source code contains annotations but **the documentation tool has not been run yet**, no HTML will appear automatically. If an annotation has not been marked with `@Documented`, Javadoc by default will not display that usage in the API description even though it may still be readable at other stages.

`@Documented` only marks metadata as something that **should be presented as part of the public contract**. It does not force callers to invoke the method differently, does not perform condition checks on its own, and has no callback running before or after the method.

### Distinguishing Between a Documented Annotation Type and Displayed Annotation Usages

A public annotation type can still have **its own Javadoc page**, for example a page describing its `value()` and `level()` elements, if it is included in the source set processed by Javadoc. That **does not depend** on whether it has `@Documented`.

What `@Documented` adds is that **when that annotation type is used on another class or method, the usage and annotation value become part of that element's documentation**.

Example:

- The definition page for `InternalTag` can appear in Javadoc if `InternalTag` is a public annotation type.
- However, `@InternalTag` applied to `ApiService` will not automatically be displayed in `ApiService`'s documentation if the `InternalTag` type is not marked with `@Documented`.

That is the difference between **documenting an annotation type** and **publishing an annotation applied to another API**.

## 3. Syntax and Characteristics of `java.lang.annotation.Documented`

The standard declaration in Java SE 17 shows:

~~~java
@Documented
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.ANNOTATION_TYPE)
public @interface Documented {
}
~~~

This is the **API form for illustration**, not code to overwrite the built-in definition in the JDK.

What these mean:

- `@Documented` itself is a **marker annotation**: there are no elements to pass.
- `@Target(ANNOTATION_TYPE)` means `@Documented` can only be applied to **annotation type declarations**, such as `@interface PublicTag`. Placing it directly on a regular class or method is an invalid target.
- `@Retention(RUNTIME)` is the retention of **the `Documented` meta-annotation itself**. This does not require a custom annotation marked with it to use `RUNTIME`.
- `@Documented` is also marked by `@Documented` itself; this is a valid characteristic of a standard meta-annotation.

A valid custom declaration typically has all three meta-annotations:

~~~java
import java.lang.annotation.Documented;
import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

@Documented
@Retention(RetentionPolicy.RUNTIME)
@Target({ElementType.TYPE, ElementType.METHOD})
public @interface PublishedTag {
    String value();
}
~~~

`@Target`, `@Retention`, and `@Documented` answer three different questions: **where it can be applied, how long it is retained, and whether it is published in the API documentation**.

## 4. Java 17 Hands-On Example: Comparing Annotations With and Without `@Documented`

We will create a public API with two annotations:

- `@PublishedTag`: has `@Documented`, so its usage must be published in default Javadoc.
- `@InternalTag`: does not have `@Documented`, so its usage is not published on the default API page.

Both have `@Retention(RUNTIME)` to separately demonstrate that **runtime reflection can still read both**, regardless of whether they have `@Documented` or not.

Place the four Java files in the `src/example/docs/` directory of a standalone practice folder.

### 4.1. `src/example/docs/PublishedTag.java`

~~~java
package example.docs;

import java.lang.annotation.Documented;
import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

/** Marks information to be published alongside the API. */
@Documented
@Retention(RetentionPolicy.RUNTIME)
@Target({ElementType.TYPE, ElementType.METHOD})
public @interface PublishedTag {
    /** Describes the public commitment level. */
    String value();
}
~~~

### 4.2. `src/example/docs/InternalTag.java`

~~~java
package example.docs;

import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

/** Marks metadata for internal tooling. */
@Retention(RetentionPolicy.RUNTIME)
@Target({ElementType.TYPE, ElementType.METHOD})
public @interface InternalTag {
}
~~~

`InternalTag` is a public annotation type; it can still have its own description page. The difference being examined is **displaying the usages of `@InternalTag` in other API documentation**.

### 4.3. `src/example/docs/ApiService.java`

~~~java
package example.docs;

/** Example service API. */
@PublishedTag("stable")
@InternalTag
public class ApiService {

    /**
     * Returns a greeting.
     *
     * @param name the name of the person to greet
     * @return a greeting containing the name
     */
    @PublishedTag("public-operation")
    @InternalTag
    public String greet(String name) {
        return "Hello, " + name;
    }
}
~~~

On both the `ApiService` declaration and the `greet` method, both annotations are **syntactically valid**, have the same retention, and can both be detected by reflection. However, the metadata of `PublishedTag` is marked as part of the **public documentation contract**, whereas the metadata of `InternalTag` is not.

### 4.4. `src/example/docs/DocumentationDemo.java`

~~~java
package example.docs;

import java.lang.annotation.Documented;
import java.lang.reflect.Method;

/** Demonstrates that Documented and runtime reflection are independent. */
public class DocumentationDemo {
    public static void main(String[] args)
            throws ReflectiveOperationException {
        Class<ApiService> type = ApiService.class;
        Method method = type.getMethod("greet", String.class);

        System.out.println("PublishedTag has @Documented: "
                + PublishedTag.class.isAnnotationPresent(Documented.class));
        System.out.println("InternalTag has @Documented: "
                + InternalTag.class.isAnnotationPresent(Documented.class));

        System.out.println("Published on class: "
                + type.isAnnotationPresent(PublishedTag.class));
        System.out.println("Internal on class: "
                + type.isAnnotationPresent(InternalTag.class));
        System.out.println("Published on method: "
                + method.isAnnotationPresent(PublishedTag.class));
        System.out.println("Internal on method: "
                + method.isAnnotationPresent(InternalTag.class));
        System.out.println("Published value: "
                + type.getAnnotation(PublishedTag.class).value());
    }
}
~~~

### 4.5. Compile and Run

Open a terminal in the parent directory of `src/`. Use JDK 17 or higher:

~~~bash
javac -encoding UTF-8 -d out src/example/docs/PublishedTag.java src/example/docs/InternalTag.java src/example/docs/ApiService.java src/example/docs/DocumentationDemo.java
java -cp out example.docs.DocumentationDemo
~~~

**Exact stdout:**

~~~text
PublishedTag has @Documented: true
InternalTag has @Documented: false
Published on class: true
Internal on class: true
Published on method: true
Internal on method: true
Published value: stable
~~~

Both annotations are readable via runtime reflection because they both use `RetentionPolicy.RUNTIME`. The difference in having `@Documented` **does not cause an annotation to disappear at runtime**.

### 4.6. Generate Javadoc and Inspect the Output

Also from the parent directory of `src/`, run:

~~~bash
javadoc -quiet -encoding UTF-8 -docencoding UTF-8 -d docs -public src/example/docs/PublishedTag.java src/example/docs/InternalTag.java src/example/docs/ApiService.java src/example/docs/DocumentationDemo.java
~~~

Open the resulting file:

~~~text
docs/example/docs/ApiService.html
~~~

In the documentation page for class `ApiService`, observe:

1. The class declaration is displayed together with the **`@PublishedTag`** annotation and the value `"stable"`, because `PublishedTag` has `@Documented`.
2. The declaration of method `greet` is displayed together with **`@PublishedTag`** and the value `"public-operation"`.
3. **`@InternalTag` is not published as an annotation on the class/method** in default Javadoc because it lacks `@Documented`.
4. The Javadoc `/** ... */` comments on the class and method are still displayed through the normal documentation mechanism, unrelated to `@Documented`.

Positioning, how `value=` text is rendered, links, and HTML layout may vary across JDK versions or doclets. Verify the **presence and meaning** of the annotation in the API page, rather than comparing exact HTML characters.

A few important points about the tools:

- `javac` performs **compilation**. `java` runs `main`, whereas `javadoc` generates documentation from source/API; they are separate commands.
- The `-d docs` option specifies the documentation output directory, unrelated to retention.
- The `-public` option selects declarations with public visibility to include in the documentation; therefore a private element is not published merely because its annotation has `@Documented`.
- An annotation without `@Documented` **does not mean it cannot be processed** by a compiler, framework, reflection, or code inspection tool.

## 5. How `@Documented` Differs from Javadoc Comments and Javadoc Tags

In Java, the word “documented” can easily cause confusion between three mechanisms.

### 5.1. Javadoc Comments `/** ... */`

~~~java
/** Calculates the total amount after applying the discount. */
public int total() {
    return 100;
}
~~~

This is **part of a method definition**, not a standalone Java program. A Javadoc comment provides **natural-language explanatory content** for an element. Programmers write tags such as `@param`, `@return`, `@throws`, and `@since` inside the comment for the documentation tool to interpret.

### 5.2. The `@Documented` Annotation

~~~java
@Documented
@interface ApiStatus {
    String value();
}
~~~

This is a **meta-annotation placed on an annotation type**. It indicates that usages of `@ApiStatus` belong to the public documentation contract. `@Documented` **does not generate prose descriptions** for `ApiStatus` on its own.

### 5.3. The Java Annotation `@Deprecated` and the Javadoc Tag `@deprecated`

Here is a classic example of an annotation and a Javadoc tag that have related purposes but different mechanisms:

~~~java
/**
 * Old API.
 *
 * @deprecated Use newApi() instead.
 */
@Deprecated(since = "1.2", forRemoval = false)
public void oldApi() {
}
~~~

The snippet above is **an illustrative method declaration**, which must be placed inside a class to compile. `@Deprecated` is an annotation recognized by Java, the compiler, and tools; `@deprecated` inside `/** ... */` is a Javadoc tag explaining the replacement. Standard `@Deprecated` is also designed to appear in API documentation; it does not replace migration guidance text.

Comparison:

| Mechanism | Where is it placed? | Primary role |
| --- | --- | --- |
| `/** ... */` | Before a Java declaration | Writes descriptive API content |
| `@param`, `@return`, `@deprecated` | Inside a Javadoc comment | Structures documentation information |
| `@Documented` | On an `@interface` definition | Publishes annotation usages in API documentation |
| `@Deprecated` | On the Java element to mark | Metadata marking an obsolete API |

You cannot write `@Documented` inside a Javadoc comment expecting it to become a meta-annotation; nor can you use only a `/** ... */` description block to change an annotation's target, retention, or readability via reflection.

## 6. Relationship with `@Target`, `@Retention`, and `@Inherited`

Three different meta-annotations are used for three independent requirements.

| Meta-annotation | Question answered | Practical effect |
| --- | --- | --- |
| `@Target` | Where is the annotation valid? | The compiler checks annotation placement |
| `@Retention` | Until which stage is the metadata kept? | Source, class file, or accessible at runtime |
| `@Documented` | Does the annotation usage belong to the published API contract? | Javadoc by default displays marked annotations |
| `@Inherited` | When looking up annotations on a subclass, can the annotation from the superclass be found? | Affects metadata lookup on classes according to specific inheritance rules |

### 6.1. Is `RetentionPolicy.RUNTIME` Required for `@Documented` to Work?

**No.** `javadoc` works with the declaration/source model and does not need to call runtime reflection to know where an annotation has been applied. An annotation with `@Retention(RetentionPolicy.SOURCE)` can still be **displayed in Javadoc** if the annotation type is marked with `@Documented`.

Valid example fragment:

~~~java
import java.lang.annotation.Documented;
import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

@Documented
@Retention(RetentionPolicy.SOURCE)
@Target(ElementType.TYPE)
@interface SourceApiMark {
}

@SourceApiMark
class Contract {
}
~~~

This code illustrates `SOURCE` retention: Javadoc processing from source can publish `@SourceApiMark` on `Contract` when the element is selected for documentation; however, runtime reflection on `Contract.class` **cannot see** that annotation. If you want `javadoc` to generate documentation for `Contract` in a sample project, you must include that declaration in the source set with an appropriate documentation visibility option.

Conversely, an annotation **without `@Documented` but with `RUNTIME` retention** can still be read normally via reflection, just like `@InternalTag` in the example.

Key distinction: Javadoc publishing metadata and Reflection reading metadata **solve two different problems**.

### 6.2. Does `@Documented` Make an Annotation Automatically Inherited?

No. `@Inherited` controls whether **certain annotation lookup APIs on a subclass** can find annotations from the superclass. `@Documented` only addresses publishing annotation information in documentation.

- With `@Documented` but without `@Inherited`: Javadoc can display the annotation on the marked class itself, but Java does not treat the subclass as inheriting the annotation under reflection just because of `@Documented`.
- With `@Inherited` but without `@Documented`: reflection queries on the subclass can see the inherited annotation according to `@Inherited` rules (with appropriate retention), but Javadoc by default does not publish those annotation usages solely due to `@Inherited`.
- With both: the two mechanisms coexist while retaining independent roles. Do not infer that a subclass's Javadoc will necessarily copy all metadata from the superclass; how it is displayed depends on documentation conventions and tools.

Avoid confusing `@Inherited` with the Javadoc inline tag `{@inheritDoc}`: `{@inheritDoc}` is used to inherit **documentation comment content** in cases supported by Javadoc, and is not a Java annotation at all.

## 7. When Should You Use `@Documented`?

Use it when the annotation information is genuinely **a meaningful part of the public API** that library users need to see in the documentation. For example:

- `@StableApi`: publishes stability level or compatibility guarantees according to library policy.
- `@RequiresPermission("REPORT_READ")`: if access permission is an official contract of the API and has an enforcement handler.
- `@Experimental`: informs users that an API is experimental and subject to change.
- `@SchemaHint`: if schema information needs to be published when using the API.

These are **custom annotation names designed for illustration**, not mandatory annotations built into Java SE.

It is not necessary to use `@Documented` for metadata intended only for **internal tooling**, such as a marker added for generating technical reports, build checks, or supporting implementation details that do not need to be included in the contract for API consumers.

When choosing `@Documented`, keep in mind that **annotation element values may appear in public documentation**. Never put secret keys, passwords, tokens, or sensitive internal details in annotation metadata; whether or not it is published in Javadoc is not a data security mechanism.

### API Design Choices

Suppose a library exposes a method:

~~~java
@RequiresPermission("INVOICE_WRITE")
public void submitInvoice() {
}
~~~

This is **an illustrative declaration snippet**; there is no `RequiresPermission` definition yet and it is not a standalone program. If that is a constraint API integrators must know about, `@Documented` helps Javadoc display the information. However, displaying it does not guarantee that **the permission-checking mechanism is actually working**. The system still needs a corresponding interceptor, validator, or authorization logic.

If an annotation only marks a method for build tools, omitting `@Documented` can keep API documentation focused on the information library users actually need.

## 8. Advanced Case: `@Documented` and `@Repeatable`

A repeatedly used annotation may need to be represented via a **containing annotation type**. The JLS requires that if a repeatable annotation type is marked `@Documented`, then **the containing annotation type must also be marked `@Documented`**.

Example of a valid declaration:

~~~java
import java.lang.annotation.Documented;
import java.lang.annotation.Repeatable;

@Documented
@Repeatable(Tags.class)
@interface Tag {
    String value();
}

@Documented
@interface Tags {
    Tag[] value();
}
~~~

If `@Documented` is kept on `Tag` but removed from `Tags`, the repeatable annotation definition no longer satisfies the language constraint and causes a compile-time error.

The reverse direction **is allowed**: the containing type has `@Documented` while the repeated annotation type does not. In practical design, however, you should maintain consistency regarding what is considered part of the public contract.

The example above is only intended to illustrate definitions related to documentation; when designing a repeatable annotation in a real project, you must also ensure that `@Target`, `@Retention`, and the container's `value()` contract are compatible.

## 9. Common Mistakes

**Mistake 1 — “Apply `@Documented` directly to a method to make it appear in Javadoc.”** Incorrect target. `@Documented` must be applied to the `@interface` declaration of the annotation that the method uses.

**Mistake 2 — “Without `@Documented`, the annotation does not work.”** False. An annotation can still be used normally by the compiler, frameworks, runtime reflection, or annotation processors; by default, it is simply not published in the element's Javadoc.

**Mistake 3 — “`@Documented` turns an annotation into a runtime annotation.”** False. The retention of a custom annotation is determined by `@Retention`, independently of `@Documented`.

**Mistake 4 — “`@Documented` automatically writes descriptions about the class/method.”** False. It displays the annotation's metadata; API descriptions still need to be written inside `/** ... */`.

**Mistake 5 — “Without `@Documented`, a separate Javadoc page cannot be generated for the annotation type.”** False. An annotation type's Javadoc page documents the **type declaration**; `@Documented` affects **the places where that type is used**.

**Mistake 6 — “`@Documented` forces Javadoc to display private APIs as well.”** False. The documentation output scope depends on `javadoc` options such as `-public` or `-private`. Meta-annotations do not override visibility filters.

**Mistake 7 — “An annotation on a public API with `@Documented` is guaranteed to be enforced.”** False. Displaying a constraint in documentation does not implement that constraint itself.

**Mistake 8 — “`@Documented` and `@Inherited` are the same mechanism.”** False. One belongs to API documentation; the other belongs to metadata inheritance rules when looking up annotations on classes.

**Mistake 9 — “The Javadoc tag `@deprecated` is the `@Documented` annotation.”** False. `@deprecated` is a documentation tag, whereas `@Documented` is a Java meta-annotation.

## 10. Self-Check Exercises

**Question 1.** Given `@interface Marker {}` and a public class `@Marker class A {}`, does Javadoc by default publish the usage of `@Marker` in the documentation of `A`?

**Answer:** No, if `Marker` is not marked with `@Documented`. However, `Marker` itself can still have its own type documentation page if it is included in the processed source set.

**Question 2.** Should `@Documented` be placed on `@interface Marker` or `class A`?

**Answer:** On the `Marker` annotation type declaration, because `Documented` has `@Target(ANNOTATION_TYPE)`.

**Question 3.** If an annotation uses `@Documented` and `@Retention(SOURCE)`, can Javadoc processing from source publish it? Can runtime reflection read it?

**Answer:** Javadoc can publish the usage according to `@Documented` rules, but runtime reflection does not see the annotation since it is discarded due to `SOURCE`.

**Question 4.** In the Section 4 example, `InternalTag` is not published in `ApiService`'s documentation. Why does `isAnnotationPresent(InternalTag.class)` still return `true`?

**Answer:** `InternalTag` has `RUNTIME` retention. `@Documented` and runtime retention serve two separate purposes.

**Question 5.** If you want library users to know that a public method requires a certain permission, can `@Documented` replace the permission-checking mechanism?

**Answer:** No. It helps display the contract commitment in documentation; the permission-checking behavior still requires an execution/enforcement handler.

**Question 6.** A `@Repeatable` annotation is marked with `@Documented`, but the container annotation does not have `@Documented`. Is there a problem?

**Answer:** Yes. The JLS specifies that the containing annotation type must also be marked with `@Documented`.

**Hands-on exercise:** Run the complete example in Section 4 and inspect `ApiService.html`. Next, add `@Documented` to `InternalTag`, regenerate Javadoc into a different output directory, and observe the change. Finally, keep `@Documented` but change the retention of `PublishedTag` to `SOURCE`, recompile, and compare the HTML against the reflection output. Explain each result according to the **three layers: source metadata, API documentation, and runtime reflection**.
