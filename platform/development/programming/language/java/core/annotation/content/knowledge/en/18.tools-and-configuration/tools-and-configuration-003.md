# Separating the Annotation Library, Processor, and Consumer Application in Java Core

When building annotation processing in Java, a reliable organizational approach is to **separate the three responsibilities into three independent artifacts**:

1. **Annotation API/library**: declares `@interface` and the API types that application code needs to know when writing `@...`.
2. **Annotation processor**: a tool that **runs at compile time**, reads annotations via the Java Language Model, validates declarations, or generates code using `Filer`.
3. **Consumer/application**: code that uses the annotations and (if any) the code generated by the processor.

You should not put everything in the same module and expect the compiler to compile and run the newly written processor within that very same compilation pass. Separating artifacts helps establish a **clear build order**, **role-appropriate classpaths**, and **avoidance of dependency cycles**, while making the processor easier to test and reuse across multiple applications.

This article uses Java 17+ and a practical example consisting of **2 input JARs and 1 application**. The example has been verified with `javac --release 17`: the processor generates a new Java class, and then the program uses the generated class during the same consumer compilation step.

## 1. Learning Objectives

You will be able to:

- Split the source into `annotation-api`, `annotation-processor`, and `consumer-app`, without confusing the three artifacts with three arbitrary packages.
- Identify compile-time dependencies, **processor execution** dependencies, and runtime dependencies.
- Understand why the processor must be **compiled before it is loaded to process** consumer source.
- Distinguish between `-cp`, `-processorpath`, `-processor`, `-s`, `-d`, and `--release 17`.
- Understand how `META-INF/services/javax.annotation.processing.Processor` is used for service discovery, as distinct from `@SupportedAnnotationTypes`.
- Write a simple `AbstractProcessor` processor using `RoundEnvironment`, `Filer.createSourceFile(...)`, and `Messager`.
- Compile using manual commands **on Bash or PowerShell**, then run the application that uses the class generated by the processor.
- Translate the concept to Gradle/Maven, and understand `compileOnly`/`annotationProcessor` and the origin of dependency cycles.
- Avoid common errors such as processor `ClassNotFoundException`, `Annotation processor not found`, missing generated source, duplicate filer, and the compiler not performing processing.

## 2. Why Separate Them?

Suppose the library has an annotation:

~~~java
@GenerateMessage("Hello from compile time")
public class App {}
~~~

The goal is that when `javac` processes `App`, the processor generates the class:

~~~java
package demo.generated;

public final class MessageInfo {
    public static final String TEXT = "Hello from compile time";

    private MessageInfo() {}
}
~~~

And the program uses the generated class:

~~~java
System.out.println(MessageInfo.TEXT);
~~~

For the entire workflow to succeed, we need to solve **three different problems**:

- The compiler must recognize `GenerateMessage` as a valid annotation type when reading the consumer's source.
- The compiler must **load and run** the pre-compiled processor implementation, along with all classes that the processor depends on.
- The compiler must include the source generated by the processor in the consumer compilation process so that `MessageInfo` exists when the consumer runs.

If the three responsibilities are mixed together, errors such as missing processor class files, the API not being on the processor path, or generated sources not being compiled can easily occur. This is not a limitation of annotation syntax, but rather a **build organization and compilation environment** issue.

## 3. The Correct Dependency Diagram

~~~text
annotation-api
  └── demo.api.GenerateMessage       --> annotation-api.jar
                 ^                            ^
                 |                            |
                 | (compile API)              | (consumer compile classpath)
                 |                            |
annotation-processor                 consumer-app
  └── demo.processor.MessageProcessor     ├── demo.app.App (@GenerateMessage)
        |                                  └── demo.app.Main
        ├── implements Processor                   |
        ├── depends on annotation-api.jar         | javac loads processor
        └── produces annotation-processor.jar      v
                                            generated MessageInfo.java
                                                   |
                                                   v
                                             MessageInfo.class
                                                   |
                                                   v
                                         java demo.app.Main
~~~

Key relationships:

| Artifact | What must it see when compiling itself? | At which stage is it used? | Responsibility |
| --- | --- | --- | --- |
| `annotation-api.jar` | Java standard annotation API | Consumer compile classpath, processor compile classpath, and processor execution path when needed | Declaring the annotation contract |
| `annotation-processor.jar` | `annotation-api.jar` and `java.compiler` standard API | Loaded by the compiler during the **consumer compilation** step | Reading metadata, validating, generating code |
| `consumer-app` | Annotation API and generated types created by the processor | Consumer compilation, then application runtime | Business logic and using generated code |

The desired dependency direction is:

~~~text
annotation-processor ---> annotation-api
consumer-app ---------> annotation-api (compile time)
compiler executing consumer --> annotation-processor (+ its dependencies)
~~~

There **should not be** a direction `annotation-api → annotation-processor` or `annotation-processor → consumer-app`. If the processor imports consumer classes, you can easily create a **dependency cycle**: compiling the app requires the processor, while compiling the processor requires the app. Inside the processor, instead of directly importing consumer classes, use `TypeElement`, `Element`, and the language model APIs to inspect the declarations being compiled.

The three artifacts here are **build modules/projects** in practical terminology; this example does not use the Java Platform Module System and has no `module-info.java`. If using actual JPMS, configuring `--module-path`/`--processor-module-path` is a variant that must be handled separately.

## 4. Designing the Directory Structure

The example uses a minimal source tree to make running `javac` commands straightforward:

~~~text
annotation-example/
├── annotation-api/
│   └── src/demo/api/GenerateMessage.java
├── annotation-processor/
│   └── src/demo/processor/MessageProcessor.java
├── consumer-app/
│   └── src/demo/app/
│       ├── App.java
│       └── Main.java
└── build/                        (generated during the build process)
    ├── api/
    ├── processor/
    ├── app/
    ├── generated/
    ├── annotation-api.jar
    └── annotation-processor.jar
~~~

Each class's package must still match its directory path under `src`. A more common structure in Gradle/Maven is `src/main/java/demo/...`, but for running commands manually in this article, `src/demo/...` keeps things more concise.

Do not commit `build/` to version control if it is temporary output: `.class` files, generated sources, and output JARs are normally rebuilt. In real-world projects, you should use a build tool rather than maintaining a long list of manual commands yourself.

## 5. Artifact 1 — Annotation API Library

Create the file **`annotation-api/src/demo/api/GenerateMessage.java`**:

~~~java
package demo.api;

import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

@Retention(RetentionPolicy.SOURCE)
@Target(ElementType.TYPE)
public @interface GenerateMessage {
    String value();
}
~~~

**Why `public`?** The consumer source is in a different package (`demo.app`), so the annotation type must be accessible from outside the `demo.api` package.

**Why `SOURCE` retention?** The goal of this demo is **compile-time processing**. The compiler can inspect the annotation in source code; there is no need to retain the annotation at runtime just so the processor can generate a file. If a real application requires runtime reflection on the annotation, `CLASS`/`RUNTIME` can be used depending on the need, though that is a separate API decision.

**Why `@Target(TYPE)`?** This annotation may only be used on appropriate type declarations, such as classes. `@Target` helps the compiler validate where it is applied.

The annotation API **does not import the processor**, does not call `Filer`, does not need `AbstractProcessor`, and does not depend on the consumer's business classes. It is a thin JAR that can be published independently for both the processor and the consumer to reference.

When the consumer uses:

~~~java
@GenerateMessage("Hello from compile time")
public class App {}
~~~

`"Hello from compile time"` is the value of the annotation element `value()`. The processor code will read this string at compile time and embed it into the generated source.

## 6. Artifact 2 — Annotation Processor

Create the file **`annotation-processor/src/demo/processor/MessageProcessor.java`**:

~~~java
package demo.processor;

import demo.api.GenerateMessage;
import java.io.IOException;
import java.io.Writer;
import java.util.Set;
import javax.annotation.processing.AbstractProcessor;
import javax.annotation.processing.RoundEnvironment;
import javax.annotation.processing.SupportedAnnotationTypes;
import javax.annotation.processing.SupportedSourceVersion;
import javax.lang.model.SourceVersion;
import javax.lang.model.element.Element;
import javax.lang.model.element.TypeElement;
import javax.tools.Diagnostic;
import javax.tools.JavaFileObject;

@SupportedAnnotationTypes("demo.api.GenerateMessage")
@SupportedSourceVersion(SourceVersion.RELEASE_17)
public final class MessageProcessor extends AbstractProcessor {
    private boolean generated;

    @Override
    public boolean process(
            Set<? extends TypeElement> types,
            RoundEnvironment round) {

        if (round.processingOver()) {
            return false;
        }

        Set<? extends Element> marked =
                round.getElementsAnnotatedWith(GenerateMessage.class);

        if (marked.isEmpty()) {
            return false;
        }

        if (marked.size() != 1 || generated) {
            processingEnv.getMessager().printMessage(
                    Diagnostic.Kind.ERROR,
                    "Demo expects exactly one marked class");
            return true;
        }

        Element element = marked.iterator().next();
        String value = element.getAnnotation(
                GenerateMessage.class).value();

        // Simplify generating the Java string literal in the demo.
        if (!value.matches("[A-Za-z ]+")) {
            processingEnv.getMessager().printMessage(
                    Diagnostic.Kind.ERROR,
                    "Only English letters and spaces allowed",
                    element);
            return true;
        }

        try {
            JavaFileObject output =
                    processingEnv.getFiler().createSourceFile(
                            "demo.generated.MessageInfo", element);

            try (Writer writer = output.openWriter()) {
                writer.write(
                        "package demo.generated;\n"
                        + "public final class MessageInfo {\n"
                        + "  public static final String TEXT = \""
                        + value + "\";\n"
                        + "  private MessageInfo() {}\n"
                        + "}\n");
            }
            generated = true;

        } catch (IOException exception) {
            processingEnv.getMessager().printMessage(
                    Diagnostic.Kind.ERROR,
                    "Cannot generate: " + exception.getMessage(),
                    element);
        }

        return true;
    }
}
~~~

This is a **complete processor class** using Java 17. Notable parts:

1. `@SupportedAnnotationTypes("demo.api.GenerateMessage")` declares that the processor supports the annotation type by its **fully qualified name**. The name `demo.processor.MessageProcessor` is the processor class name and must not be placed in `@SupportedAnnotationTypes`.
2. `@SupportedSourceVersion(SourceVersion.RELEASE_17)` declares support for source level 17. It does not replace `javac --release 17`.
3. `AbstractProcessor` provides `processingEnv`, the environment containing `Filer`, `Messager`, and `Elements/Types`.
4. `RoundEnvironment.getElementsAnnotatedWith(...)` retrieves the declarations annotated with `@GenerateMessage` in the **current processing round**.
5. `processingOver()` detects the final round. A processor may be invoked across multiple rounds; you should not assume a single callback.
6. `Filer.createSourceFile("demo.generated.MessageInfo", element)` creates a **new Java source file** and declares `element` as the originating element, which is useful for tooling and incremental builds.
7. `Writer` writes **Java source code**, rather than directly emitting bytecode. Afterward, the compiler can process the generated source in subsequent rounds and compile it.
8. `generated` prevents attempting to recreate the same file within the same processor run. `Filer` enforces a rule that the same output name cannot be created multiple times; trying to do so can throw `FilerException`.
9. `Messager` reports diagnostics through the compiler. When encountering invalid data or an I/O error, the demo reports `Diagnostic.Kind.ERROR`; this is better than merely printing to `System.out` or swallowing the exception.
10. `return true` means the processor **claims** the provided annotation types according to the processor contract; it does not mean the `java` command has executed the application.

**Intentional limitations of the demo:** This processor only supports **exactly one annotated class** for a single output with a fixed name `demo.generated.MessageInfo`. If there are multiple `@GenerateMessage` classes, you would need to redesign the generated class naming or aggregation mechanism; the demo reports an error instead of silently overwriting. It also accepts only English letters and spaces so it can assemble a safe Java string literal in a simple way. In a real library, properly construct/escape Java string literals, or use a code-generation API, instead of arbitrarily concatenating user input into source code.

### Why Does the Processor Need the Annotation API on Its Classpath?

The file above contains the line:

~~~java
import demo.api.GenerateMessage;
~~~

and the method call:

~~~java
element.getAnnotation(GenerateMessage.class);
~~~

Therefore, the processor **must see `GenerateMessage.class`** both when compiling the processor and when the compiler **loads and runs** the processor. These are two distinct points in time. In the manual example, we pass `annotation-api.jar` to:

- `-cp` when compiling `MessageProcessor.java`.
- `-processorpath` when `javac` loads the processor to compile the app.

If the API JAR is missing from the processor path, the error may be `NoClassDefFoundError: demo/api/GenerateMessage` or a corresponding loading error, even if the consumer compile classpath already includes the API JAR. The rule is: **the processor path is the class-loading environment for the processor and its dependencies**, not just the location holding a single processor class.

## 7. Artifact 3 — Consumer Application

### 7.1. `consumer-app/src/demo/app/App.java`

~~~java
package demo.app;

import demo.api.GenerateMessage;

@GenerateMessage("Hello from compile time")
public class App {}
~~~

This is the source that the compiler/processor reads. The `App` class does not call `MessageProcessor` and does not need to import the processor implementation.

### 7.2. `consumer-app/src/demo/app/Main.java`

~~~java
package demo.app;

import demo.generated.MessageInfo;

public class Main {
    public static void main(String[] args) {
        System.out.println(MessageInfo.TEXT);
    }
}
~~~

At the time the source is written, `MessageInfo.java` **does not yet exist** in the source tree. It appears during the app compilation process, generated by the processor. Therefore, **do not compile `Main.java` separately before enabling processing** and conclude that the project is broken. A single compilation task containing both `App.java` and `Main.java`, with the processor properly configured, allows `javac` to parse the generated source to resolve `demo.generated.MessageInfo`.

This is an important real-world use case for annotation processors: the consumer programmer uses types generated from declared structures, without needing to import or invoke the processor in runtime code.

## 8. Real Build with JDK 17+: API → Processor → Consumer

Start from the `annotation-example` root directory as shown in the diagram.

### 8.1. On Bash/Linux/macOS

~~~bash
mkdir -p build/api build/processor build/app build/generated

# 1. Compile and package the annotation API.
javac --release 17 -proc:none -d build/api \
  annotation-api/src/demo/api/GenerateMessage.java
jar --create --file build/annotation-api.jar -C build/api .

# 2. Compile the processor, which depends on the annotation API.
javac --release 17 -proc:none \
  -cp build/annotation-api.jar \
  -d build/processor \
  annotation-processor/src/demo/processor/MessageProcessor.java
jar --create --file build/annotation-processor.jar \
  -C build/processor .

# 3. Compile the consumer and run the packaged processor.
javac --release 17 \
  -cp build/annotation-api.jar \
  -processorpath build/annotation-processor.jar:build/annotation-api.jar \
  -processor demo.processor.MessageProcessor \
  -s build/generated \
  -d build/app \
  consumer-app/src/demo/app/App.java \
  consumer-app/src/demo/app/Main.java

# 4. Run the newly compiled application.
java -cp build/app:build/annotation-api.jar demo.app.Main
~~~

The `\` character is used for line continuation in Bash/POSIX. On Windows, the classpath/processorpath separator must be `;`, not `:`.

### 8.2. On Windows PowerShell

~~~powershell
New-Item -ItemType Directory -Force build/api,build/processor,build/app,build/generated

javac --release 17 -proc:none -d build/api annotation-api/src/demo/api/GenerateMessage.java
jar --create --file build/annotation-api.jar -C build/api .

javac --release 17 -proc:none -cp build/annotation-api.jar -d build/processor annotation-processor/src/demo/processor/MessageProcessor.java
jar --create --file build/annotation-processor.jar -C build/processor .

javac --release 17 -cp build/annotation-api.jar -processorpath "build/annotation-processor.jar;build/annotation-api.jar" -processor demo.processor.MessageProcessor -s build/generated -d build/app consumer-app/src/demo/app/App.java consumer-app/src/demo/app/Main.java

java -cp "build/app;build/annotation-api.jar" demo.app.Main
~~~

The Java source files are **exactly** the same as written in Sections 5–7. Do not create the `MessageInfo.java` source manually.

### 8.3. Verifiable Results

Stdout of the final `java` command:

~~~text
Hello from compile time
~~~

After compilation, two important outputs exist:

~~~text
build/generated/demo/generated/MessageInfo.java
build/app/demo/generated/MessageInfo.class
~~~

The source file written by the processor has the content:

~~~java
package demo.generated;

public final class MessageInfo {
    public static final String TEXT = "Hello from compile time";
    private MessageInfo() {}
}
~~~

**Verified:** This example was actually compiled with `javac --release 17` on a JDK supporting Java 17, packaged into two JARs, ran the processor during the consumer compilation stage, confirmed that the generated source exists, and ran the application producing the exact stdout shown above.

Do not mistake the processor's output for the output of the `java` command: **the processor runs while `javac` is compiling**, whereas the line `Hello from compile time` is printed when `java demo.app.Main` executes. If you want to observe the compiler's annotation processing rounds, you can try `javac -XprintRounds -XprintProcessorInfo ...` on compilers that support those options; this is diagnostic output, not part of the application's stdout.

## 9. Precisely Understanding Paths and `javac` Options

| Option | Purpose in the example |
| --- | --- |
| `--release 17` | Compiles source/API/bytecode targeting Java 17; does not enable processors by itself |
| `-proc:none` | Disables annotation processing when pre-compiling the API and processor |
| `-cp build/annotation-api.jar` | Makes `GenerateMessage` visible to the **consumer source** |
| `-processorpath processor.jar:api.jar` | Lets the **JVM running javac** find the processor and its dependencies |
| `-processor demo.processor.MessageProcessor` | Explicitly selects the processor implementation without needing ServiceLoader discovery |
| `-s build/generated` | Specifies where the compiler places **generated Java source** |
| `-d build/app` | Specifies where the compiler places **compiled class files** for the consumer and generated types |
| `jar --create --file ...` | Packages the compiled class files into a JAR |
| `java -cp ... demo.app.Main` | Runs the consumer program after compilation completes |

**`-cp` differs from `-processorpath`.** The compiler processing `App.java` source needs to see the annotation API via the compile classpath. However, the processor's class loader needs to see the processor implementation along with its dependencies on the processor path. Putting `annotation-api.jar` on **both** is intentional, not redundant duplication in the demo.

**`-s` differs from `-d`.** `-s` holds the `.java` files generated by the processor; `-d` holds the `.class` files emitted by the compiler. You must not assume that simply seeing `MessageInfo.java` means the class has been compiled or that the application will run.

**`-processor` differs from `@SupportedAnnotationTypes`.** `-processor` specifies the **implementation class** to invoke; the meta-annotation declares the **annotation types that the implementation recognizes**. Both must be correct, but they answer two different questions.

**`--release` differs from `@SupportedSourceVersion`.** One controls the source/API/bytecode compatibility of the compilation, while the other is a capability statement on the processor. You should test your processor with the toolchain you intend to support.

### Does the Runtime Dependency Need the Annotation API?

In the demo, `GenerateMessage` has `SOURCE` retention and the runtime code in `Main` only reads `MessageInfo.TEXT`. The `java` command includes `annotation-api.jar` on the classpath to make the three-artifact model easier to follow, but **this is not required for every application that only uses source-level annotations**. If another app/runtime artifact directly references the annotation API or another library, the corresponding runtime dependencies must be added.

You should not automatically place the **processor JAR** on the application's runtime classpath. A processor is strictly a build-time tool; the demo application **does not need** `MessageProcessor.class` to run.

## 10. Processor Discovery via ServiceLoader

The main example uses `-processor`, so it does not require a service registration file. For the compiler to **discover** the processor when the processor JAR appears on the processor search path, the standard service provider configuration mechanism is to create a resource inside the processor artifact:

~~~text
annotation-processor/
└── resources/
    └── META-INF/
        └── services/
            └── javax.annotation.processing.Processor
~~~

Contents of the `javax.annotation.processing.Processor` file:

~~~text
demo.processor.MessageProcessor
~~~

This is the **processor class name**, not the annotation type name `demo.api.GenerateMessage`.

When packaging, the path inside the JAR must be exact:

~~~text
META-INF/services/javax.annotation.processing.Processor
~~~

If packaging manually with `jar`, add the resource to the processor JAR in addition to the compiled classes. When using Gradle/Maven with the standard source layout, placing the file in `annotation-processor/src/main/resources/META-INF/services/...` will allow standard build tools to include the resource in the JAR.

`@SupportedAnnotationTypes` only declares which annotations the processor handles; **it does not automatically generate the service file or register the processor**. Other mechanisms such as an auto-service library can help generate this file, but Java Core itself does not automatically create a service registration when it encounters `@SupportedAnnotationTypes`.

**JDK version note:** How annotation processing is enabled/defaulted in `javac` has changed across JDK releases and build tool configurations. For reproducible builds, always configure the processor dependency/processor path and the activation/discovery mechanism explicitly, rather than simply expecting “adding the JAR to the classpath will run it automatically”. For this exercise, using `-processor` is deterministic, and the demo has been verified when compiling with Java 17.

## 11. Organizing with Gradle: Separating Compile Dependencies and Processor Dependencies

In a multi-project Gradle build, the modules can be named:

~~~text
settings.gradle
annotation-api/
annotation-processor/
consumer-app/
~~~

Illustrative `settings.gradle` content:

~~~groovy
rootProject.name = 'annotation-example'
include 'annotation-api', 'annotation-processor', 'consumer-app'
~~~

All three projects use the appropriate `java-library`/`java`/`application` plugin and the Java 17 toolchain. In `annotation-processor/build.gradle`, declare that the processor depends on the API:

~~~groovy
plugins {
    id 'java-library'
}

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(17)
    }
}

dependencies {
    implementation project(':annotation-api')
}
~~~

For `consumer-app/build.gradle`:

~~~groovy
plugins {
    id 'application'
}

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(17)
    }
}

dependencies {
    compileOnly project(':annotation-api')
    annotationProcessor project(':annotation-processor')
    annotationProcessor project(':annotation-api')
}

application {
    mainClass = 'demo.app.Main'
}

tasks.withType(JavaCompile).configureEach {
    options.compilerArgs += [
        '-processor', 'demo.processor.MessageProcessor'
    ]
}
~~~

This is an **illustrative Gradle configuration**, assuming you move the source files to the Gradle `src/main/java` layout and create the corresponding Java configuration/plugin for `annotation-api`. The explicit `-processor` option means ServiceLoader is not needed for the demo; in a project that already packages processor registration via a service file, you can usually omit the manual compilerArgs and let the processor be discovered through the dependency in the appropriate configuration.

Explanation of the configurations:

- `implementation project(':annotation-api')` **in the processor module**: the processor needs the API to compile and run.
- `compileOnly project(':annotation-api')` **in the consumer**: the annotation API is used to compile source but is not a runtime dependency by default; suitable for this `SOURCE`-only example. If the consumer also needs the API at runtime, use `implementation` instead of `compileOnly`.
- `annotationProcessor project(':annotation-processor')`: Gradle places the processor onto the **processor path** of the consumer's compile task, which does not mean packaging the processor into the application.
- `annotationProcessor project(':annotation-api')`: explicitly puts the API onto the processor execution path, preventing missing dependencies when the processor references `GenerateMessage.class`. In a build with full dependency metadata/transitive runtime dependencies, the API might already be brought onto the processor path via the processor dependency; the illustrative configuration specifies it explicitly so learners can see both sides.
- `tasks.withType(JavaCompile)...-processor`: enables the explicitly specified processor class even when `META-INF/services` has not been packaged.

When moving to Gradle, let the tool manage build order via the dependency graph instead of invoking `javac` manually. `consumer-app` is not a dependency of `annotation-processor`; they are connected through the API and the compilation task.

### What About Maven?

Maven should also have three separate artifacts/child modules, for example:

~~~text
parent
├── annotation-api
├── annotation-processor
└── consumer-app
~~~

- The **processor** POM depends on the annotation API.
- The **consumer** POM declares the annotation API as a compile dependency. If it is retention/source-only and not needed at runtime, the scope can be designed according to the dependency model; do not force `provided` as a mechanical replacement when the app actually needs the API at runtime.
- Configure the Maven Compiler Plugin to place the **processor artifact and its required dependencies** onto the annotation processor path; in newer plugin versions, you can use the corresponding processor dependency declaration mechanism. When you want to explicitly specify the processor, declare the processor class using the configuration supported by the plugin.
- Ensure the tool/build is tested with JDK 17 and explicit annotation processing configuration. Exact option names and DSL details depend on the Maven Compiler Plugin version; check the documentation for the exact version in use before copying a POM.

**More important than any specific Gradle/Maven syntax:** the annotation API and the processor are **two distinct artifacts** with different dependency roles. The consumer should not need the processor JAR on its runtime classpath just to run business logic.

## 12. Common Error Scenarios and How to Handle Them

### 12.1. `Annotation processor '...' not found`

**Symptom:** `javac` cannot find `demo.processor.MessageProcessor`.

Check:

1. Has the processor been compiled into `.class` files inside the JAR?
2. Does `-processorpath` point to the right JAR and not mistakenly to a source folder?
3. Does `-processor` use the **fully qualified class name** `demo.processor.MessageProcessor`?
4. Is the processor class `public`, and does it have an appropriate public no-arg constructor? For a public class with no explicitly defined constructor, Java provides an appropriate default no-argument constructor.
5. Is the processor using a module-path/JPMS execution mode different from the classpath example?

### 12.2. `NoClassDefFoundError: demo/api/GenerateMessage` When Loading the Processor

The processor imports and references `GenerateMessage.class`, but the API JAR is missing from the processor execution path. You need to add **annotation-api.jar** to the processor path or package/declare its runtime dependency properly. Placing the API JAR only on the consumer's `-cp` does not guarantee the processor class loader can see it.

### 12.3. Consumer Fails to Compile the Annotation Type

If `App.java` reports that `demo.api.GenerateMessage` cannot be found, the issue is usually that the **consumer compile classpath** is missing `annotation-api.jar`. Add `-cp build/annotation-api.jar` or the equivalent `compileOnly/implementation` dependency.

### 12.4. Processor Does Not Run, Yet the Consumer Still Compiles

You may not have enabled processing, or may be missing `-processor`, missing a service descriptor, using the wrong processor path, or using a toolchain with a different auto-discovery policy. Do not conclude that the processor has run simply because `GenerateMessage` was accepted by the compiler.

Check the output `build/generated/.../MessageInfo.java` or use options to trace processors/rounds. In the demo, because `Main` imports the generated type, if the processor does not run, compilation will fail to resolve `demo.generated.MessageInfo`; this is a way to detect the failure via the compilation result.

### 12.5. `cannot find symbol MessageInfo`

Do not manually copy the generated class into the source module as a “quick fix” and end up maintaining two copies. Verify that `Main.java` and `App.java` are compiled in a single task with the processor running and that Filer generated the source in the correct package.

### 12.6. `FilerException: Attempt to recreate a file for type ...`

A processor attempted to create the same fully qualified name more than once during the same compilation, or there is an identically named class/file already processed by the compiler. Ensure each generated type is created only once, manage state across processing rounds, and choose output names that do not conflict with user-written source files. In the demo, the `generated` flag prevents duplication.

### 12.7. Dependency Cycle Between the API, Processor, and Consumer

Architectural mistake:

~~~text
consumer needs processor
processor imports consumer classes
consumer cannot compile before processor
~~~

How to fix: declare the annotation in a separate API; the processor imports only the API and inspects consumer classes through `Element`/`TypeMirror` provided by the compiler. If the processor needs a shared contract, move that contract into the API or an appropriate shared artifact—do **not** import the app.

### 12.8. Putting the Processor in the Consumer's `implementation`

When a processor is solely a compile-time tool, placing it in runtime dependencies bloats the artifact size and can easily cause classloading conflicts. Use the appropriate processor-path/`annotationProcessor` configuration. Only include the processor at runtime when there is a clearly designed special requirement, not for ordinary `@GenerateMessage` processing.

### 12.9. Omitting the Service File in the JAR

If using auto-discovery, the JAR must contain `META-INF/services/javax.annotation.processing.Processor` with the exact path and the processor implementation name. Placing the resource at the wrong path, writing the annotation type name instead of the processor name, or failing to package the resource into the JAR will all cause discovery to fail.

### 12.10. Testing on Only One JDK and Assuming All JDK Versions Behave Identically

Processors execute inside the compiler environment; discovery/toolchain configuration and source language levels can change. Keep `--release`, test on the target JDK, verify `@SupportedSourceVersion`, and use explicit compiler configuration. Do not rely on auto-processing simply from an arbitrary JAR added to the classpath.

### 12.11. Concatenating User Data into Java Source Strings Without Escaping

The demo only allows `[A-Za-z ]+` so it can construct a Java string literal simply. A real processor must properly escape double quotes, backslashes, newlines, and relevant Unicode cases, or use a code-generation library. If you omit validation and concatenate annotation values directly into generated source, the code can easily become syntactically invalid and risks generating unintended source.

### 12.12. Confusing Source Retention with Runtime Accessibility

`@Retention(SOURCE)` is sufficient for the processor to handle the annotation during the compile phase; however, the running program cannot rely on `App.class.getAnnotation(GenerateMessage.class)` to retrieve the annotation via runtime reflection. If a runtime feature needs it, use `RUNTIME` retention and design the API/runtime dependencies accordingly.

## 13. QA Checklist for the Three Artifacts

| Question | Acceptance criterion |
| --- | --- |
| Is the annotation API separated? | Contains `public @interface GenerateMessage`, with no dependency on the processor/consumer |
| Does the processor depend on the API in the right direction? | `annotation-processor → annotation-api` |
| Which dependencies does the consumer need? | Annotation API on the compile path; processor on the processor path |
| Is the API JAR on the processor execution path? | Yes, if the processor loads/imports that annotation type |
| Is the processor explicitly selected by the compiler? | `-processor demo.processor.MessageProcessor` or valid discovery |
| Does the compiler run processing? | Yes, not disabled by `-proc:none` at the consumer compilation step |
| Is the build order correct? | Compile API → compile processor → compile consumer |
| Where is the generated source? | `build/generated/demo/generated/MessageInfo.java` |
| Where is the generated class? | `build/app/demo/generated/MessageInfo.class` |
| What does the application print? | `Hello from compile time` |
| Is there a dependency cycle back to the consumer inside the processor? | No |
| Is the source level consistent? | The demo uses `javac --release 17` at every step |

### Advanced Verification Suggestions

If your real-world project is larger than the demo, test at least three scenarios:

1. **No annotated declarations present:** the processor does not generate spurious source files; the program does not depend on a generated class that does not exist in this scenario.
2. **Valid annotation:** the expected class is generated, both source and bytecode compile, and the application can use the generated API.
3. **Invalid annotation / annotation used too many times:** the compiler emits clear diagnostics, does not create duplicate sources, and does not insert unescaped input values as Java literals.

In addition, a clean build (`clean build`) must regenerate all generated files. If only the generated source is deleted and the processor does not run on the next build, the application should not accidentally “pass” due to stale classes remaining in the output directory.

## 14. Practice Exercises

1. **Change the annotation value:** Replace `@GenerateMessage("Hello from compile time")` with `@GenerateMessage("Build is ready")` and rebuild the consumer. Predict the generated source and stdout.
2. **Trace the paths:** Temporarily remove `annotation-api.jar` from the consumer's compile classpath; observe the compiler error and explain how it differs from removing the API JAR from the processor path.
3. **Missing processor:** Remove `-processor demo.processor.MessageProcessor` without setting up a service descriptor. Observe whether the compiler can find the processor in that environment; do not conflate this with a build that has discovery configured.
4. **Inspect source generation:** After compiling, open `build/generated/demo/generated/MessageInfo.java` and check the constant. Verify that the corresponding class exists in `build/app`.
5. **Duplicate error:** Apply `@GenerateMessage` to two classes and observe the demo diagnostic "expects exactly one marked class"; propose an improvement for naming the generated type based on `Element.getSimpleName()` to support multiple classes.
6. **Using Messager:** Try the value `@GenerateMessage("Hello!")`. The character-restricted processor will report a compile error. Explain why a compile-time diagnostic is more helpful than letting the generated Java source fail.
7. **Service registration:** Add the `META-INF/services/javax.annotation.processing.Processor` file to the processor JAR, containing `demo.processor.MessageProcessor`, and try removing `-processor` in a build where annotation processing/discovery is explicitly enabled.
8. **Runtime separation:** Try running with only `java -cp build/app demo.app.Main`. Analyze why, for this `SOURCE`-only example where the generated class only contains a `String`, the processor and annotation API JAR do not need to be loaded by the application at runtime in this case.
9. **Gradle:** Move the Java sources to `src/main/java`. Configure three subprojects, verify `annotationProcessor` for the consumer and `implementation` for the processor, and run a clean compile.
10. **Maven:** Create a parent project with three artifacts and configure the appropriate version of the Maven Compiler Plugin; explain the roles of the processor path and the regular classpath.
11. **Change retention:** Replace `SOURCE` with `RUNTIME` and add a runtime reflection query. Adjust the runtime dependency and distinguish between the processor's role and reading the annotation at runtime.
12. **Advanced API design:** When consumers A and B both use the processor, examine how to publish an API JAR and a processor JAR as compatible versions. Explain how to minimize the consumer's runtime dependency requirements.

## 15. Summary

Separating the **annotation API**, **annotation processor**, and **consumer** does more than make the code cleaner; it accurately reflects the three environments:

- **Contract definition**: `annotation-api.jar` is shared with the consumer source and the processor.
- **Compile-time execution**: `annotation-processor.jar` is loaded by `javac` along with its dependencies, detects annotations, and can generate source.
- **Running the application**: the consumer uses compiled bytecode and generated classes; it typically **does not need** the processor on its runtime classpath.

The core principle is **correct dependency direction, correct build order, and correct compiler paths**. `-cp` serves type resolution for source code, `-processorpath` serves loading the processor, `-processor` or a service provider determines which processor runs, `-s` holds generated source files, and `-d` holds compiled class files. When each piece is placed in its proper role, annotation processing becomes a verifiable build step rather than unpredictable automatic behavior.
