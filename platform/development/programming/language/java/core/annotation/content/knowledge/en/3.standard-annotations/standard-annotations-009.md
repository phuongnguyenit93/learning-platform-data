# Distinguishing Java SE Annotations from External Library Annotations

## 1. Why Do We Need to Distinguish Them?

In Java, annotations all use the `@TenAnnotation` syntax, yet **they do not have the same origin and do not have the same operating mechanism**. An annotation can be defined in Java SE, in a third-party library/framework, or directly in the project source code.

When reading:

```java
@Override
@Deprecated
public String toString() {
    return "example";
}
```

we encounter two standard Java SE annotations. However, when reading:

```java
@org.junit.jupiter.api.Test
void shouldCalculateTotal() {
    // A test method managed by JUnit
}
```

we encounter an annotation belonging to **JUnit Jupiter**, which requires the corresponding library in the project and must be run with an appropriate testing tool.

The fact that **Java supports annotation syntax** does not mean Java automatically knows what to do with every annotation. Most annotations only provide metadata; concrete behavior occurs when the compiler, a tool, or a program/framework reads and processes that metadata.

Distinguish them using three questions:

1. **Who defines the annotation?** Java SE, an external library, or the project itself?
2. **Is an additional dependency needed?** Does the JDK already provide the annotation type, or must the corresponding artifact be downloaded?
3. **Who processes it, and when?** The Java compiler, an annotation processor, a test runner, a framework runtime, or the application's reflection code?

Do not look only at the `@` prefix or the fact that an annotation appears at runtime and conclude that it is a standard Java annotation.

## 2. What Are Java SE Annotations?

**Java SE (Java Platform, Standard Edition)** provides a built-in set of annotations and meta-annotations in its standard APIs. Commonly encountered types reside in `java.lang` and `java.lang.annotation`; several other standard APIs also define their own annotations.

Basic examples that can be used directly in a Java 17+ application **without declaring any third-party dependency**:

| Annotation | Fully qualified name/package | Primary purpose | Related component |
| --- | --- | --- | --- |
| `@Override` | `java.lang.Override` | Requests verification that a method actually overrides/implements a valid method | Java compiler |
| `@Deprecated` | `java.lang.Deprecated` | Marks an API as no longer recommended for use | Compiler, IDE, documentation, and metadata-reading tools |
| `@SuppressWarnings` | `java.lang.SuppressWarnings` | Instructs the compiler to suppress recognized warning categories | Java compiler |
| `@FunctionalInterface` | `java.lang.FunctionalInterface` | Verifies that an interface satisfies the functional interface contract | Java compiler |
| `@SafeVarargs` | `java.lang.SafeVarargs` | Asserts safety on valid generic/varargs declarations to reduce related warnings | Java compiler |
| `@Target` | `java.lang.annotation.Target` | Declares the locations where an annotation is allowed to appear | Compiler; annotation definition |
| `@Retention` | `java.lang.annotation.Retention` | Declares the metadata retention policy: SOURCE, CLASS, RUNTIME | Compiler, class file, reflection |
| `@Documented` | `java.lang.annotation.Documented` | Marks that an annotation should appear in API documentation generated by supporting tools | Documentation tools, such as Javadoc |
| `@Inherited` | `java.lang.annotation.Inherited` | Allows looking up an annotation on a superclass according to specific inheritance rules for class declarations | Java reflection |
| `@Repeatable` | `java.lang.annotation.Repeatable` | Allows applying an annotation type multiple times according to container rules | Compiler and annotation-reading APIs |

Annotations in `java.lang` are imported implicitly; for meta-annotations belonging to `java.lang.annotation`, an explicit `import` is usually required.

**Note:** "Provided by Java SE" refers to the **API origin**, not a claim that the annotation will automatically trigger business logic. For example, `@Deprecated` affects tools and warnings, but does not by itself prevent users from calling the method.

### 2.1. Java SE Annotations Understood Directly by the Compiler

```java
class Base {
    String label() {
        return "base";
    }
}

class Child extends Base {
    @Override
    @Deprecated(since = "17")
    String label() {
        return "child";
    }
}
```

In this example:

- `@Override` causes the compiler to report an error if `label()` no longer overrides a valid method in the parent type; no method invocation mechanism is generated by the annotation.
- `@Deprecated(since = "17")` indicates the version in which deprecation begins; this is information for the compiler/tools, not a prohibition against usage.
- Both types are Java SE standard annotations and can be applied to the same method if valid with respect to `@Target`.

Some standard annotations are checked by the compiler for placement or contract compliance; `@SafeVarargs`, for instance, **is not valid on every method**. Its specific requirements should be read, rather than assuming all standard annotations can be placed anywhere.

### 2.2. Meta-Annotations Are Also Standard Annotations

A meta-annotation is **an annotation used to describe another annotation type**. For example:

```java
import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
@interface AuditAction {
    String value();
}
```

`@Retention` and `@Target` here are provided by **Java SE**. `@AuditAction` is a **custom annotation**, even though it uses two standard meta-annotations. Do not regard `@AuditAction` as a built-in JDK annotation simply because `@Target` or `@Retention` appears on it.

## 3. What Are External Library Annotations?

These are annotation types packaged and distributed by a library, framework, or organization other than the standard Java SE API suite. Java still accepts them because **libraries can also declare `@interface`** in accordance with the Java language.

| Ecosystem | Example annotation and package | Processing library/component | Typical usage |
| --- | --- | --- | --- |
| JUnit Jupiter | `org.junit.jupiter.api.Test` | JUnit Jupiter and the test execution platform | Marks a test method to be discovered by the test engine |
| Spring Framework | `org.springframework.stereotype.Component` | Spring container with the corresponding component scanning mechanism | Marks a type as a candidate for Spring bean registration |
| Spring Framework | `org.springframework.transaction.annotation.Transactional` | Spring's transaction infrastructure | Declares transaction semantics when the invocation manner and configuration are supported |
| Jakarta Bean Validation | `jakarta.validation.constraints.NotNull` | Bean Validation provider or an integration that invokes validation | Declares a constraint that the value must not be null |
| Project Lombok | `lombok.Getter` | Lombok's compiler integration tool | Generates getters at compile time according to configuration and support capabilities |

**These examples are not Java SE APIs.** The project needs to include the corresponding library in its dependencies/classpath/module path at compile time, and in many cases also requires appropriate runtime tooling or configuration.

### 3.1. JUnit: The Test Runner Executes the Tests

```java
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.assertEquals;

class CalculatorTest {
    @Test
    void addsNumbers() {
        assertEquals(4, 2 + 2);
    }
}
```

**This is code using JUnit Jupiter, not a standalone runnable Java SE program.** It requires the JUnit Jupiter dependency and a test runner supporting JUnit Platform (such as a Gradle test task configuration or tooling in an IDE).

`@Test` tells JUnit that the `addsNumbers()` method is a test; **`java CalculatorTest` is not a test execution command equivalent to the JUnit runner**. Without JUnit on the classpath, `javac` cannot resolve the `org.junit.jupiter.api.*` imports.

### 3.2. Spring: Annotations Require the Spring Container and Infrastructure

```java
import org.springframework.stereotype.Component;
import org.springframework.transaction.annotation.Transactional;

@Component
class AccountService {
    @Transactional
    public void transfer() {
        // Business logic is written here
    }
}
```

This is illustrative code that requires Spring dependencies; **it cannot be compiled with the plain JDK**. `@Component` takes effect when Spring scans and registers the type into an appropriate ApplicationContext. `@Transactional` requires transaction management to be enabled/configured along with the corresponding interceptor mechanism to apply an actual transaction; a method invoked in a way that bypasses the interception mechanism may not have a transaction applied as expected.

The Java compiler only verifies that the annotation type exists and that its usage is valid under language rules; the Java compiler **does not automatically create a Spring bean or start a transaction** simply because it encounters `@Component` or `@Transactional`.

### 3.3. Jakarta Validation: Constraints Also Need a Validation Mechanism

```java
import jakarta.validation.constraints.NotNull;

class OrderRequest {
    @NotNull
    String customerId;
}
```

`@NotNull` here belongs to the **Jakarta Validation** API, not Java SE. The constraint is enforced when a Bean Validation provider is present and the application/framework actually invokes the validation mechanism on the object; merely instantiating `new OrderRequest()` and leaving `customerId == null` **does not automatically raise an error**.

`jakarta.validation.constraints.NotNull` must also be distinguished from similarly named annotations such as `org.jetbrains.annotations.NotNull` or `javax.annotation.Nonnull`: similar names **do not guarantee the same origin, contract, or processing tool**.

### 3.4. Lombok: Annotations Serving the Compilation Phase

```java
import lombok.Getter;

class Customer {
    @Getter
    private String name;
}
```

`@Getter` belongs to Lombok. In an environment where Lombok is properly integrated and configured, Lombok's tooling can generate getters at compile time. The plain Java compiler **does not by itself recognize the request to generate a getter from `@Getter`**. Lombok's compiler-integration mechanism must be distinguished from annotations that frameworks read via reflection at runtime.

Do not lump all external library annotations into a single "runs at runtime" group: JUnit is tied to a test engine, Spring is tied to a container/proxy/interceptor, Jakarta Validation is tied to a validator, while Lombok processes during compilation.

## 4. Comparison Across Practical Aspects

| Criterion | Standard Java SE Annotations | External Library Annotations |
| --- | --- | --- |
| Definition source | Standard Java SE API, present in the corresponding JDK | JAR/module of the library or framework |
| Is an external dependency outside the JDK needed to reference it? | No, if the API belongs to the Java SE module set available in the current environment | Usually yes |
| Java syntax | `@AnnotationName`, can declare elements and values | **Identical** Java syntax |
| Syntax, `@Target`, and value type checks | Java compiler | **Still performed by the Java compiler** |
| Primary semantic processing | Compiler, Java SE tools, libraries, or application code depending on the type | Library, framework, annotation processor, or external tool depending on the type |
| Retention | Defined individually by each type; does not default to RUNTIME | Defined individually by each type; does not default to RUNTIME |
| Reflection | Only metadata eligible under RUNTIME retention can be read | Also follows Java rules for retention and reflection |
| Portability | Does not depend on external libraries, though still depends on the Java version supporting the API | Requires compatibility with the library version, configuration, and deployment environment |

Not every Java SE annotation has an "auto-executing behavior"; nor does every external annotation require a large framework. There can be annotations that serve solely as metadata for a dedicated tool to read.

## 5. Standalone Java 17+ Program: Distinguishing Java SE and Custom Annotations

This example intentionally **uses no external libraries** to show clearly that standard Java SE annotations (`@Deprecated`, `@Retention`, `@Target`) and a custom annotation (`@Purpose`) can coexist side by side.

Create the file **AnnotationOriginDemo.java**:

```java
import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;
import java.lang.reflect.Method;

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
@interface Purpose {
    String value();
}

public class AnnotationOriginDemo {
    @Deprecated(since = "17")
    @Purpose("learning")
    public static String hello() {
        return "Hello Java";
    }

    public static void main(String[] args) throws NoSuchMethodException {
        Method method = AnnotationOriginDemo.class.getDeclaredMethod("hello");

        System.out.println(method.isAnnotationPresent(Deprecated.class));
        System.out.println(method.getAnnotation(Purpose.class).value());
        System.out.println(hello());
    }
}
```

Using JDK 17 or later, in the directory containing the file:

```bash
javac AnnotationOriginDemo.java
java AnnotationOriginDemo
```

Stdout output:

```text
true
learning
Hello Java
```

**Explanation:**

1. `@Deprecated` comes from `java.lang.Deprecated`, a standard Java SE type. It has **RUNTIME retention**, so `isAnnotationPresent(Deprecated.class)` returns `true`.
2. `@Purpose` is defined by this file itself using `@interface`. It is **neither a standard Java SE annotation nor an external library annotation**.
3. `@Retention` and `@Target` come from `java.lang.annotation`. Thanks to `@Retention(RUNTIME)`, Java reflection can read `@Purpose("learning")` and extract the string `learning`.
4. Both annotations are attached to the `hello()` method; only the code in `main()` actively reads them. A normal call to `hello()` still returns `Hello Java`.

This code snippet can be used to separate **the origin of the annotation definition** from **the mechanism that reads the annotation**. Java SE reflection can read a custom or third-party annotation, provided that the annotation is available at runtime and retained properly.

### 5.1. Why Are Not All Annotations Visible via Reflection?

`@Override` and `@SuppressWarnings` are standard annotations but have a **SOURCE** retention policy, so reflection at runtime cannot see them. Conversely, `@Deprecated` has **RUNTIME**. An external library annotation can likewise be SOURCE, CLASS, or RUNTIME.

Therefore, "readable via reflection" must not be used as a criterion to classify Java SE versus external library annotations. Retention is **a property of each individual annotation type**, independent of who provides it.

## 6. How to Identify an Annotation's Origin When Reading a Project

When encountering an unfamiliar annotation, proceed in the following order:

1. **Open its definition or import** to obtain the fully qualified class name. For example, `@Test` at the top of a file could be imported from JUnit or another library; the short name `Test` alone is not enough.
2. **Check whether the annotation resides in the JDK or a dependency artifact.** Use Go to Declaration in the IDE; inspect External Libraries, the Maven/Gradle dependency graph, or the JAR/module name containing the class.
3. **Read `@Target` and `@Retention`.** They indicate the allowed attachment locations and whether the metadata can appear at runtime, without directly indicating who executes the logic.
4. **Find the tool that consumes the annotation.** The Java compiler, an annotation processor, a JUnit runner, a Spring context/proxy, a validator, or the project's reflection code are very different mechanisms.
5. **Check the dependencies and activation configuration.** Successfully compiling because the annotation type is on the classpath **does not guarantee** that the corresponding framework logic is running.
6. **Consult the documentation for the specific annotation and library version.** Two libraries sharing the name `@Transactional`, `@NotNull`, or `@Test` do not necessarily have the same contract and behavior.

For example, the following imports clearly show the origin:

```java
import java.lang.annotation.Retention;                // Java SE
import org.junit.jupiter.api.Test;                    // JUnit Jupiter
import org.springframework.stereotype.Component;      // Spring
import jakarta.validation.constraints.NotNull;       // Jakarta Validation
```

The snippet above **is only for illustrating how to read packages**; to compile all of these imports in the same file, the corresponding dependencies for JUnit, Spring, and Jakarta Validation must be provided.

### 6.1. Do Not Guess by Package Prefix Alone

- `java.lang.Override` is a Java SE API.
- `javax.annotation.processing.Generated` also belongs to the **standard API bundled with the JDK** (the `java.compiler` module), even though its package starts with `javax`.
- `jakarta.validation.constraints.NotNull` belongs to Jakarta Validation and **is not part of Java SE**.
- Many APIs formerly used `javax.*` names in Java EE or in external libraries; the presence of `javax` is not enough to conclude that it is packaged in the current JDK.
- Some annotations share the same short name but belong to different packages; the import determines which type is actually used.

Therefore, **the full package + artifact/module source + documentation for the version in use** is a more reliable basis than the short name.

### 6.2. What Is the Difference Between Having and Not Having the Dependency?

Code using an external annotation typically has three distinct states that should be separated:

| State | What can happen |
| --- | --- |
| Missing the dependency containing the annotation when compiling source | The compiler reports that the package/symbol cannot be found when encountering the import or usage of that type |
| Annotation type is on the classpath, but the required processor/configuration is missing | The code can compile, but the intended effect of the framework/test/tool is not yet activated |
| Proper library, processor, configuration, and execution flow are present | The annotation can be processed according to the library's own contract |

The specific behavior also depends on the architecture: an annotation processor needs to be enabled in the build; tests need to be discovered by the JUnit runner; transactions in Spring are typically tied to a proxy/interceptor mechanism; validation needs to be invoked on the relevant execution path.

## 7. Distinguishing Three Commonly Confused Aspects

### 7.1. Different Origins

- **Java SE annotation:** the definition resides in the standard Java SE API; for example, `@Override`.
- **Third-party annotation:** the definition comes from a dependency outside Java SE; for example, `org.junit.jupiter.api.Test`.
- **Custom annotation:** self-defined within the project; for example, `@Purpose` in Section 5.

They share the same `@...` syntax, yet the classification depends on **where the type is defined**. A project's custom annotation can also become a third-party annotation for another project once published as a library.

### 7.2. Where It Is Defined Differs from Where It Is Processed

For example, `@Test` is defined by JUnit and processed by JUnit; `@Deprecated` is defined by Java SE and can be read by the compiler/IDE; `@Purpose` is defined by the project and processed by the reflection code in `main()`.

Even an annotation **defined by Java SE** can still be inspected by an external library, and an annotation **defined by an external library** still obeys all of Java's annotation syntax rules.

### 7.3. Retention Does Not Determine Who "Runs" the Annotation

`@Retention(RUNTIME)` only states that metadata can be preserved for reading via reflection at runtime. It **does not activate a test runner, dependency injection system, validation, or transactions**.

Similarly, `@Retention(SOURCE)` does not make an annotation "useless": a SOURCE annotation can be important to the compiler or tools during the source-code processing phase.

## 8. Common Mistakes

**1. Seeing `@Test` and assuming it is built into the JDK.** The JDK does not provide JUnit Jupiter by itself. Check `org.junit.jupiter.api.Test` and the test dependencies.

**2. Seeing `javax` and assuming it belongs to Java SE; seeing `jakarta` and assuming the Java compiler processes it automatically.** You must determine exactly which module/JAR the class resides in. Jakarta EE and Java SE are different platforms.

**3. Adding `@Component` and expecting Java to create a bean automatically.** A Spring context and appropriate bean discovery configuration are required.

**4. Adding `@NotNull` and believing the object can never be null.** This is a constraint declaration and requires an appropriate validation processor; the field can still hold null if there is no checking mechanism.

**5. Assuming every external library works via reflection.** Lombok is an example of compiler-phase processing/integration. Annotation processors can also read metadata at compile time.

**6. Thinking an annotation not readable via reflection is from an external library or ineffective.** `@Override` belongs to Java SE yet has SOURCE retention; many custom/third-party annotations are likewise not retained until runtime.

**7. Confusing `@Retention` and `@Target` with annotations from the declaring library.** They are standard Java SE meta-annotations, regardless of whether the annotation they describe is self-defined or located in a library.

**8. Assuming "compiles successfully" equals "processed by the framework".** Having the dependency is an initial condition; there must also be a test engine, bean scanning, interceptor, validator, or appropriate configuration for each use case.

## 9. Self-Check Exercises

1. For `@Override`, `@Deprecated`, `@Retention`, JUnit's `@Test`, Spring's `@Transactional`, and Lombok's `@Getter`, write down the **fully qualified name**, **provider/source**, **primary processor**, and **whether an external dependency outside the JDK is required**.
2. In the `AnnotationOriginDemo` program, try adding `@Override` onto `hello()` (a static method that does not override anything). Predict the compilation error and explain why the error occurs even though `@Override` is not read via reflection.
3. Remove `@Retention(RetentionPolicy.RUNTIME)` from the `@Purpose` definition, then observe the result when reading via reflection. The default rule is CLASS retention; explain why `getAnnotation(Purpose.class)` no longer provides the annotation in that case. (Update the code before calling `.value()` to avoid dereferencing null.)
4. Given a project that has `import jakarta.validation.constraints.NotNull` without invoking validation and without using a framework integrating a validator: explain why a null value can still be assigned, as well as the conditions required for the constraint to be checked.
5. In a test class using JUnit, try removing the JUnit dependency and reading the compiler message. After adding the dependency back, find how to run the test through JUnit Platform instead of invoking `java` directly on the test class.

**Takeaway when applying:** Java SE defines the common syntax and a set of standard annotations. Libraries can define their own annotations using that same language. To understand an annotation, always inspect **the imported type, where it is packaged, `@Target`/`@Retention`, and the component that actually processes it**. That is the basis for knowing what dependencies the project needs and what effect the annotation produces.
