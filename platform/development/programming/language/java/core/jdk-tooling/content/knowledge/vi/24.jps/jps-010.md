# Giới hạn của jps

**jps** là công cụ JDK dùng để liệt kê các Java HotSpot Virtual Machine (JVM) đã được instrument trên hệ thống đích. Công cụ hữu ích khi cần tìm nhanh một JVM và local VM identifier (LVMID), nhưng kết quả không phải danh mục đầy đủ mọi process Java, không phải API quản trị ổn định và không thay thế công cụ giám sát hoặc quản lý process của hệ điều hành.

Trong Oracle JDK 24, lệnh jps được ghi rõ là **experimental và unsupported**. Định dạng output, tùy chọn và khả năng sử dụng có thể thay đổi hoặc bị loại bỏ trong các bản JDK tương lai. Vì vậy, hãy dùng jps cho kiểm tra thủ công và điều tra tại thời điểm chạy; với automation lâu dài, nên chọn API hoặc công cụ được hỗ trợ cho mục đích đó.

## 1. jps chỉ nhìn thấy một tập JVM nhất định

jps không quét mọi chương trình có liên quan đến Java. Nó liệt kê các **instrumented Java HotSpot VMs** mà người chạy lệnh có quyền quan sát.

Điều này tạo ra ba giới hạn:

1. JVM không thuộc HotSpot hoặc không được instrument theo cơ chế mà jps sử dụng có thể không xuất hiện.
2. JVM chạy dưới tài khoản khác có thể bị ẩn bởi quyền truy cập của hệ điều hành.
3. JVM nằm trong host/container hoặc process namespace khác có thể không nằm trong phạm vi mà lệnh jps hiện tại quan sát được.

Ví dụ:

~~~bash
jps
~~~

Output minh họa:

~~~text
31840 com.example.ApiServer
32004 com.example.BatchWorker
~~~

Output chỉ cho biết hai JVM mà jps tìm thấy trong phạm vi hiện tại. Nó không chứng minh rằng máy chỉ có hai process Java.

### jps không phải trình liệt kê process tổng quát

Nếu cần danh sách process của hệ điều hành, dùng công cụ tương ứng.

Linux/macOS:

~~~bash
ps -ef
~~~

Windows PowerShell:

~~~powershell
Get-Process
~~~

Nếu cần tìm process Java bằng tên executable hoặc command line, có thể lọc bằng công cụ OS. Kết quả của OS tool vẫn phụ thuộc quyền truy cập và namespace, nhưng nó có phạm vi process tổng quát hơn jps.

### Không thấy JVM không đồng nghĩa JVM không chạy

Nếu jps không liệt kê ứng dụng, hãy kiểm tra:

- Ứng dụng còn sống hay đã kết thúc.
- Lệnh đang chạy trên đúng host và đúng container hay chưa.
- User chạy jps có quyền quan sát process hay không.
- JVM có phải HotSpot và có được nhận diện theo cơ chế instrumented VM hay không.
- Ứng dụng có được khởi chạy bằng custom launcher hay không.
- PID namespace hoặc môi trường cô lập có làm thay đổi phạm vi quan sát không.

Đừng kết luận service đã dừng chỉ vì jps không in ra tên của service.

## 2. LVMID không phải lúc nào cũng là OS PID

jps hiển thị **local VM identifier (LVMID)** cho mỗi JVM tìm thấy. LVMID thường trùng với process identifier của hệ điều hành, nhưng Oracle không bảo đảm hai giá trị luôn giống nhau.

Sự khác biệt này quan trọng khi dùng kết quả jps làm đầu vào cho lệnh OS như kill, taskkill, ps -p hoặc công cụ quản trị process.

Ví dụ output:

~~~text
31840 com.example.ApiServer
~~~

31840 là LVMID được jps báo cáo. Trên nhiều hệ thống, đây cũng là PID của JVM process, nhưng phải xác minh trên chính host đang chạy ứng dụng trước khi thao tác.

Linux/macOS:

~~~bash
ps -p 31840 -o pid,ppid,user,etime,args
~~~

Windows PowerShell:

~~~powershell
Get-CimInstance Win32_Process -Filter "ProcessId = 31840" |
    Select-Object ProcessId, ParentProcessId, Name, CommandLine
~~~

Nếu thông tin process không khớp ứng dụng dự kiến, dừng lại và xác định đúng process. Không dùng LVMID như một định danh toàn cục hoặc lưu cố định trong cấu hình service.

### PID có thể được tái sử dụng

PID chỉ có ý nghĩa trong vòng đời process và phạm vi hệ điều hành. Khi process kết thúc, hệ điều hành có thể cấp lại cùng PID cho process mới.

Một quy trình không an toàn là lưu PID từ buổi điều tra trước rồi dùng lại nhiều giờ hoặc nhiều ngày sau để gửi lệnh dừng process. Trước thao tác có tác động, phải xác minh lại PID, process name, user, command line và thời điểm khởi chạy.

### Snapshot có thể lỗi thời ngay lập tức

jps thu thập thông tin tại một thời điểm. Trong lúc lệnh chạy:

- Một JVM có thể vừa khởi động.
- Một JVM khác có thể vừa kết thúc.
- PID có thể được tái sử dụng.
- Quyền hoặc trạng thái container có thể thay đổi.

Vì vậy, output là snapshot phục vụ điều tra, không phải trạng thái liên tục hoặc cam kết process vẫn tồn tại sau khi lệnh hoàn tất.

## 3. Tên class hoặc JAR có thể không đầy đủ

Mặc định, jps hiển thị LVMID và tên ngắn của main class hoặc JAR. Tên ngắn có thể bỏ package của class hoặc đường dẫn của JAR, nên hai ứng dụng khác nhau có thể trông giống nhau.

Dùng:

~~~bash
jps -l
~~~

Tùy chọn -l yêu cầu tên package đầy đủ của main class hoặc đường dẫn đầy đủ của JAR. Tuy vậy, thông tin này vẫn phụ thuộc cách JVM được khởi chạy.

### Custom launcher có thể trả về Unknown

jps dùng Java launcher để lấy tên class/JAR và main arguments. Nếu JVM được khởi chạy bằng custom launcher, các thông tin đó có thể không có sẵn. Khi đó, jps có thể in Unknown.

Ví dụ minh họa:

~~~text
31840 Unknown
~~~

Unknown không nhất thiết có nghĩa JVM bị lỗi hoặc không chạy ứng dụng Java. Nó có thể chỉ phản ánh cách process được khởi chạy không cung cấp metadata mà jps cần.

Khi gặp trường hợp này:

- Xác minh process bằng công cụ hệ điều hành.
- Kiểm tra service configuration hoặc launcher script.
- Xem command line nếu có quyền và không làm lộ secret.
- Dùng công cụ quản lý service/container để xác định workload.
- Dùng jcmd nếu JVM có thể attach và cần chẩn đoán sâu hơn.

### Embedded JVM và main arguments

Một ứng dụng native có thể nhúng JVM qua JNI Invocation API. Trong trường hợp này, thông tin main class hoặc arguments có thể khác với ứng dụng chạy bằng java launcher. Tùy cách khởi tạo, -m có thể không có giá trị và tài liệu jps cho biết output có thể là null đối với embedded JVM.

Không nên dựa vào việc mọi JVM đều có main class và danh sách arguments giống nhau.

## 4. Quyền truy cập giới hạn kết quả

jps chỉ liệt kê các JVM mà principal chạy lệnh có quyền truy cập theo cơ chế kiểm soát của hệ điều hành.

Ví dụ, một service chạy bằng tài khoản appuser có thể không hiển thị đầy đủ với người dùng thông thường khác. Trên hệ thống production, quyền process inspection thường được giới hạn để tránh người dùng đọc thông tin của service khác.

Khi kết quả thiếu:

1. Xác định user sở hữu JVM.
2. Kiểm tra quyền đọc process metadata và cơ chế attach của hệ điều hành.
3. Chạy công cụ bằng tài khoản vận hành được cấp quyền phù hợp theo quy trình.
4. Không tự động nâng quyền lên administrator/root chỉ để làm danh sách đầy đủ.
5. Ghi rõ phạm vi quyền khi lưu kết quả audit.

Quyền cao hơn có thể làm lộ command line, system properties hoặc dữ liệu nhạy cảm. Chỉ dùng quyền cần thiết và giới hạn người được xem kết quả.

## 5. Output không ổn định để parse bằng script

Oracle khuyến cáo không viết script parse output của jps vì format có thể thay đổi ở các phiên bản tương lai.

Output tổng quát có dạng:

~~~text
lvmid [ [ classname | JARfilename | "Unknown" ] [ arg* ] [ jvmarg* ] ]
~~~

Các token được phân tách bằng whitespace. Nếu một argument chứa khoảng trắng, việc xác định ranh giới giữa các argument có thể trở nên mơ hồ.

Ví dụ:

~~~text
31840 com.example.ApiServer -Dapp.label=production server
~~~

Không thể chỉ tách chuỗi theo dấu cách rồi chắc chắn biết production server là một giá trị property hay hai token riêng biệt.

### Tại sao parse jps nguy hiểm?

- Output format có thể thay đổi vì công cụ không được hỗ trợ như API ổn định.
- Tên class/JAR có thể là Unknown.
- Argument có thể chứa whitespace.
- Process có thể biến mất giữa lúc đọc và lúc thao tác.
- PID có thể được tái sử dụng.
- Kết quả bị giới hạn bởi quyền và namespace.
- Một dòng output không cung cấp đủ dữ liệu để xác định duy nhất một service.

Không dùng đoạn script kiểu sau làm cơ chế quản trị production:

~~~powershell
jps | ForEach-Object {
    $parts = $_ -split " "
    Stop-Process -Id $parts[0]
}
~~~

Ví dụ này đặc biệt nguy hiểm vì nó dừng mọi PID được in ra mà không xác minh process nào cần dừng.

### Dùng công cụ phù hợp cho automation

| Nhu cầu | Lựa chọn phù hợp |
|---|---|
| Lấy PID của chính ứng dụng Java | ProcessHandle.current().pid() |
| Liệt kê process hệ điều hành | ps, tasklist, PowerShell/CIM |
| Quản lý service | systemd, Windows Service Manager hoặc orchestration platform |
| Chẩn đoán một JVM | jcmd |
| Theo dõi JVM liên tục | JMX/monitoring agent được bảo vệ |
| Tìm nhanh JVM thủ công | jps |

Nếu cần duy trì automation, hãy dùng API có hợp đồng ổn định và định danh service từ hệ thống quản lý deployment thay vì parse text output của jps.

## 6. Tùy chọn hiển thị thông tin có thể làm lộ dữ liệu

jps có các tùy chọn bổ sung để hiển thị tên đầy đủ và arguments:

| Tùy chọn | Thông tin | Giới hạn |
|---|---|---|
| -q | Chỉ LVMID | Không cung cấp tên để phân biệt service |
| -l | Tên class đầy đủ hoặc đường dẫn JAR | Có thể lộ cấu trúc package/path |
| -m | Arguments truyền cho main method | Có thể chứa dữ liệu nhạy cảm |
| -v | JVM arguments | Có thể chứa -D properties, path và secret bị cấu hình sai |
| -V | Chỉ LVMID theo mô tả JDK 24 | Kiểm tra help của đúng phiên bản JDK |

Trên OpenJDK 24.0.2, jps -q và jps -V đều cho output chỉ có LVMID; hành vi và tùy chọn cần được kiểm tra theo JDK đang dùng.

### Vì sao -m và -v cần thận trọng?

Ví dụ một ứng dụng được khởi chạy sai cách:

~~~bash
java -Ddb.password=example-secret -jar app.jar
~~~

Nếu dùng jps -v, giá trị property có thể xuất hiện trong output. Đây chỉ là ví dụ minh họa một cấu hình không nên dùng; không đưa secret thật vào JVM arguments.

Tương tự, -m có thể hiển thị token hoặc thông tin người dùng nếu ứng dụng truyền chúng trong main arguments.

Nguyên tắc:

- Dùng -q nếu chỉ cần định danh.
- Chỉ dùng -m hoặc -v khi thực sự cần điều tra.
- Không gửi output nguyên bản lên ticket, chat hoặc log công khai.
- Redact password, token, URL có credential và dữ liệu nhạy cảm.
- Không truyền secret trực tiếp qua command line nếu có cơ chế secret management phù hợp hơn.

## 7. Remote discovery phụ thuộc jstatd và RMI

jps có thể truy vấn JVM trên host từ xa bằng hostid, nhưng đây không phải giao thức remote discovery tự hoạt động mà không cần cấu hình phía server.

Ví dụ:

~~~bash
jps -l app-host.example:1099
~~~

Với giao thức mặc định RMI, jps giả định máy đích đang chạy jstatd. Nếu không chỉ định port, RMI registry mặc định dùng cổng 1099.

Các điều kiện cần có:

- jstatd đang chạy trên host đích.
- RMI registry và port được cấu hình đúng.
- Network route và firewall cho phép kết nối cần thiết.
- Remote host cho phép truy cập theo chính sách.
- Quyền truy cập và cấu hình bảo mật RMI phù hợp.
- Hostname, port và server name khớp cấu hình thực tế.

Nếu thiếu một điều kiện, remote listing có thể thất bại dù JVM đích vẫn đang chạy.

### Remote RMI là bề mặt quản trị

Không mở jstatd/RMI ra mạng công khai chỉ để tiện xem PID. Dịch vụ remote cần được giới hạn bằng firewall, network segmentation và cấu hình bảo mật theo tài liệu JDK.

Trong production, cân nhắc dùng monitoring agent, JMX được bảo vệ hoặc công cụ quản lý hạ tầng đã được phê duyệt. Nếu chỉ cần xác định process trên host, công cụ quản trị OS/SSH có thể phù hợp hơn.

### LVMID ở remote host không phải PID trên máy local

Nếu jps trả về LVMID của JVM ở app-host.example, con số đó thuộc môi trường đích. Không dùng nó với kill, taskkill hoặc ProcessHandle trên máy local.

Mọi thao tác tiếp theo phải được thực hiện trên đúng host và namespace.

## 8. Container và PID namespace làm thay đổi cách nhìn process

Container thường sử dụng PID namespace. Một process có thể có PID khác nhau khi quan sát từ bên trong container và từ host.

Ví dụ minh họa:

~~~text
Host namespace
└── Java process: PID 42000

Container namespace
└── Cùng Java process: PID 1
~~~

Trong container, JVM có thể là PID 1. Trên host, cùng process đó có PID 42000. Đây là hai góc nhìn khác nhau của cùng process.

### Cách kiểm tra

Từ host, có thể dùng:

~~~bash
docker top my-java-container
~~~

Hoặc chạy công cụ process trong container nếu image có cài đặt:

~~~bash
docker exec my-java-container ps -ef
~~~

Nếu image tối giản không có ps, dùng công cụ container runtime hoặc kiểm tra /proc trong đúng namespace.

Với Kubernetes, xác định đúng cluster, node, pod và container trước khi kiểm tra PID. PID bên trong container không nên được coi là PID trên node.

### jps không thay thế công cụ container

Nếu jps chạy trên host nhưng JVM nằm trong namespace khác, kết quả phụ thuộc cách process namespace và quyền được cấu hình. Không giả định rằng mọi JVM trong container đều hiển thị giống JVM chạy trực tiếp trên host.

Dùng docker top, docker exec, kubectl exec hoặc công cụ node-level theo đúng quyền vận hành để tìm process trong môi trường tương ứng.

## 9. jps không cung cấp trạng thái sức khỏe hay số liệu JVM

jps chỉ nhằm liệt kê JVM và metadata khởi chạy cơ bản. Nó không cho biết đầy đủ:

- JVM có đang xử lý request hay bị treo không.
- CPU usage, memory pressure hoặc GC pause.
- Heap đang dùng bao nhiêu.
- Thread nào bị block hoặc deadlock.
- HTTP health check của service.
- Kết nối database hoặc queue còn hoạt động không.
- JVM có lỗi nghiệp vụ hoặc mất kết nối phụ thuộc không.

Một dòng như:

~~~text
31840 com.example.ApiServer
~~~

chỉ chứng minh jps đã nhận diện một JVM tại thời điểm đó. Nó không chứng minh API server khỏe mạnh.

### Dùng công cụ tiếp theo

Sau khi xác minh đúng JVM, có thể dùng jcmd:

~~~bash
jcmd 31840 VM.version
jcmd 31840 VM.flags
jcmd 31840 VM.command_line
jcmd 31840 Thread.print
jcmd 31840 GC.heap_info
~~~

Một số diagnostic command có thể tốn tài nguyên hoặc ghi file lớn. Ví dụ heap dump có thể gây pause, cần dung lượng đĩa đáng kể và chứa dữ liệu nhạy cảm. Đọc help của từng command trước khi dùng trên production.

Để đánh giá sức khỏe service, kết hợp:

- Application health endpoint.
- Metrics CPU, memory, GC, thread pool và request latency.
- Log và distributed tracing.
- JMX/monitoring agent được bảo vệ.
- OS/container resource metrics.
- Alert và service-level objective.

## 10. jps là công cụ experimental và unsupported

Oracle JDK 24 ghi rõ lệnh jps là **experimental and unsupported**. Điều này có nghĩa:

- Format output có thể thay đổi.
- Tùy chọn có thể thay đổi hoặc bị loại bỏ.
- Công cụ có thể không còn có trong một bản JDK tương lai.
- Không nên xây dựng giao diện automation quan trọng dựa trên output của nó.
- Không nên coi behavior quan sát trên một vendor/version là bảo đảm cho mọi JDK.

Trên OpenJDK 24.0.2, các lệnh jps, jps -q, jps -l, jps -m, jps -v và jcmd -l đã chạy trong môi trường kiểm tra. Điều này chỉ xác nhận behavior của runtime cụ thể đó; không biến jps thành API được hỗ trợ ổn định.

Kiểm tra cú pháp của JDK đang cài:

~~~bash
jps --help
java --version
~~~

Không giả định mọi JDK vendor hoặc version đều có cùng tùy chọn và output.

## 11. Lựa chọn thay thế tùy theo mục tiêu

### Chỉ cần PID của chương trình Java hiện tại

Dùng Java ProcessHandle API, có từ Java 9:

~~~java
public final class CurrentPid {
    public static void main(String[] args) {
        System.out.println("PID=" + ProcessHandle.current().pid());
    }
}
~~~

Biên dịch với Java 17:

~~~bash
javac --release 17 CurrentPid.java
~~~

Chạy:

~~~bash
java CurrentPid
~~~

Output có dạng:

~~~text
PID=31840
~~~

Giá trị thay đổi theo process thực tế. API này phù hợp khi chính ứng dụng cần biết PID của nó.

### Cần liệt kê process của hệ điều hành

Linux/macOS:

~~~bash
ps -eo pid,ppid,user,comm
~~~

Windows PowerShell:

~~~powershell
Get-CimInstance Win32_Process |
    Select-Object ProcessId, ParentProcessId, Name
~~~

Các công cụ này liệt kê process theo cơ chế OS, không chỉ JVM. Quyền truy cập và namespace vẫn có thể giới hạn kết quả.

### Cần chẩn đoán JVM cụ thể

~~~bash
jcmd 31840 help
jcmd 31840 VM.version
~~~

jcmd phù hợp để gửi diagnostic command đến JVM. Công cụ cần chạy trên cùng máy với JVM mục tiêu và thông thường cần cùng effective user/group ID. Không dùng PID cũ mà chưa xác minh lại.

### Cần quản lý service

Dùng service manager hoặc orchestration platform:

- systemd trên Linux.
- Windows Service Manager trên Windows.
- Docker hoặc Kubernetes cho workload container.
- Nền tảng quản lý ứng dụng của tổ chức.

Service manager biết service identity, restart policy, dependency và lifecycle tốt hơn một danh sách PID tạm thời.

### Cần giám sát liên tục

Dùng metrics, JMX hoặc monitoring agent được bảo vệ. jps không phải hệ thống telemetry và không cung cấp lịch sử process.

## 12. Quy trình xử lý khi jps cho kết quả không như mong đợi

### Không thấy ứng dụng

1. Xác minh ứng dụng vẫn đang chạy bằng service manager hoặc OS process tool.
2. Kiểm tra đúng host, container và PID namespace.
3. Kiểm tra quyền của tài khoản chạy jps.
4. Xác nhận runtime là JVM HotSpot được instrument.
5. Kiểm tra custom launcher và khả năng tên class hiển thị là Unknown.
6. Dùng jcmd hoặc monitoring tool nếu cần chẩn đoán sâu hơn.

### Chỉ thấy Unknown

1. Xác minh process bằng OS tool.
2. Kiểm tra custom launcher hoặc cách nhúng JVM.
3. Không dựa vào tên class/JAR trong output.
4. Dùng service configuration và deployment metadata để nhận diện ứng dụng.

### LVMID không khớp PID quan sát từ host

1. Xác định jps chạy bên trong hay bên ngoài container.
2. Kiểm tra PID namespace.
3. Xác minh process bằng công cụ OS trong cùng môi trường.
4. Không dùng LVMID remote/container trên host local.

### Remote query thất bại

1. Xác nhận jstatd đang chạy ở host đích.
2. Kiểm tra RMI registry, port và server name.
3. Kiểm tra firewall, DNS và route.
4. Xác nhận quyền truy cập và chính sách remote management.
5. Nếu không cần RMI, chuyển sang công cụ quản trị host hoặc monitoring đã được phê duyệt.

### Script parse sai kết quả

1. Ngừng dùng output jps làm giao diện automation.
2. Không tách token theo whitespace để suy ra arguments.
3. Dùng ProcessHandle, OS process API hoặc service manager.
4. Thêm kiểm tra process identity trước mọi thao tác có tác động.

## 13. Checklist sử dụng jps an toàn

- Xác nhận JDK version và jps --help trước khi dựa vào tùy chọn.
- Nhớ jps là experimental/unsupported trong Oracle JDK 24.
- Hiểu rằng jps chỉ liệt kê instrumented HotSpot JVM có thể truy cập.
- Không kết luận JVM không chạy chỉ vì jps không liệt kê nó.
- Không mặc định LVMID luôn là OS PID.
- Xác minh process, user, command line và start time trước thao tác.
- Nhớ PID có thể được tái sử dụng.
- Dùng -l để phân biệt class/JAR khi tên ngắn không đủ.
- Chấp nhận khả năng custom launcher hiển thị Unknown.
- Cẩn trọng với -m và -v vì arguments có thể chứa secret.
- Không parse output jps bằng script production.
- Khi remote query, kiểm tra jstatd/RMI và bảo vệ network access.
- Trong container, xác định đúng PID namespace.
- Dùng jcmd cho diagnostic command thay vì kỳ vọng jps cung cấp health/metrics.
- Dùng ProcessHandle để lấy PID của chính ứng dụng.
- Dùng OS/service manager/orchestrator để quản lý process.
- Redact command line và diagnostic output trước khi chia sẻ.
- Lưu thời điểm, host, namespace và JDK version cùng bằng chứng audit.

## 14. Thuật ngữ cần nhớ

| Thuật ngữ | Ý nghĩa |
|---|---|
| jps | Công cụ JDK liệt kê instrumented HotSpot JVM |
| Instrumented JVM | JVM có metadata mà công cụ quản trị JVM có thể nhận diện |
| LVMID | Local VM identifier do jps báo cáo |
| PID | Process ID của hệ điều hành |
| PID reuse | Hệ điều hành tái sử dụng PID sau khi process kết thúc |
| Custom launcher | Launcher tự xây dựng thay cho Java launcher tiêu chuẩn |
| Unknown | Tên class/JAR hoặc main arguments không lấy được từ launcher |
| jstatd | Dịch vụ hỗ trợ truy vấn thông tin JVM từ xa qua RMI |
| RMI registry | Registry dùng để tìm remote object trong Java RMI |
| PID namespace | Không gian PID riêng, thường dùng trong container |
| ProcessHandle | API Java truy cập định danh và thông tin native process |
| jcmd | Công cụ gửi diagnostic command đến JVM |
| Unsupported tool | Công cụ không có cam kết ổn định và có thể thay đổi hoặc bị loại bỏ |
| Snapshot | Kết quả quan sát tại một thời điểm, không phải trạng thái liên tục |

jps hữu ích để tìm nhanh JVM trong một môi trường local có quyền truy cập phù hợp. Giới hạn về phạm vi HotSpot, quyền, LVMID, launcher, container, remote RMI và output không ổn định khiến công cụ không phù hợp làm nền tảng quản trị tự động. Hãy dùng jps để định hướng điều tra, xác minh process bằng OS tools và dùng ProcessHandle, jcmd hoặc service monitoring cho nhu cầu chuyên biệt.
