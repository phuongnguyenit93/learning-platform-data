# Reading Argument Output with jps

`jps` (Java Virtual Machine Process Status Tool) is a command-line tool included with the JDK for listing instrumented HotSpot JVMs on a target machine. When reading its output, you need to distinguish four components: the **LVMID**, the main class name or JAR, the **application arguments** passed to `main()`, and the **JVM arguments** passed to the Java launcher.

Commonly used options:

- `jps -m` displays application arguments.
- `jps -v` displays JVM arguments.
- `jps -l` displays the full class name or JAR path.
- `jps -lmv` combines all three groups of information.

Oracle JDK 21 documentation marks `jps` as experimental and unsupported; the output format may change in future releases. Use this tool for interactive diagnostics, check the syntax with `jps -help` for the running JDK, and avoid building automation that depends on column splitting of the output.

## 1. Structure of jps Output

General output syntax:

```text
lvmid [ [ classname | JARfilename | "Unknown" ] [ arg* ] [ jvmarg* ] ]
```

| Component | Meaning |
|---|---|
| `lvmid` | Local JVM identifier, the identifier of the JVM found by `jps` |
| `classname` | Main class name; short or full form depending on options |
| `JARfilename` | Name or path of the JAR file used to launch the application |
| `arg*` | Arguments passed to `main(String[] args)` |
| `jvmarg*` | Arguments passed to the JVM/Java launcher, such as `-Xmx` or `-Dname=value` |
| `Unknown` | Class/JAR and application arguments could not be determined, common with custom launchers |

`lvmid` usually matches the operating system process ID, but it is not guaranteed to always be the same. When you need to pass an identifier to another tool, verify the PID using an operating system tool or an appropriate management tool.

Fields in the output are separated by whitespace. If an application argument contains spaces, the text output may not clearly show argument boundaries. Therefore, you should not parse `jps` output as a stable machine-readable format.

## 2. Listing JVMs with Default jps

Run:

```sh
jps
```

Illustrative example output:

```text
24680 ArgumentOutputDemo
25120 OrderService
25210 jps
```

Each line typically consists of the LVMID and the short name of the main class or JAR. The short class name omits the package; the JAR path may also be shortened.

The output may include the running `jps` process itself, in addition to other Java applications that the current account is permitted to observe. The PIDs in the example are for illustration only; on a real machine, the values change with each launch.

If an application does not appear, that does not necessarily mean it is not running. `jps` only reports instrumented JVMs that the current user has permission to access and that the tool can detect.

## 3. Displaying Application Arguments with -m

The `-m` option displays the arguments passed to the `main()` method:

```sh
jps -m
```

Example:

```text
24680 ArgumentOutputDemo --profile=staging --port=8080
25120 OrderService --spring.profiles.active=prod
25210 jps -m
```

For an application launched with:

```sh
java com.example.ArgumentOutputDemo --profile=staging --port=8080
```

The two values `--profile=staging` and `--port=8080` are application arguments. The Java launcher passes them into the `String[] args` array of the `main()` method.

Some embedded JVMs or JVMs launched through special mechanisms may display `null` instead of application arguments. If the application uses a custom launcher, `jps` may not be able to determine these arguments.

Do not confuse application arguments with system properties:

- `--profile=staging` after the main class name is an application argument.
- `-Dapp.mode=demo` before the main class name is a JVM/system property argument.
- `-Xmx128m` before the main class name is a JVM memory option.

## 4. Displaying Full Class Names or JAR Paths with -l

The `-l` option displays the full package name of the main class or the full path to the JAR:

```sh
jps -l
```

Example:

```text
24680 com.example.tools.ArgumentOutputDemo
25120 /opt/services/order-service/order-service.jar
25210 jdk.jcmd/sun.tools.jps.Jps
```

This is useful when multiple applications share the same short class name, such as multiple modules all having a `Main` class. The full package name helps distinguish them.

For applications run from a JAR, `-l` helps identify which JAR was used to launch the process. The displayed path may depend on how the launcher and platform provide information to the JVM.

## 5. Displaying JVM Arguments with -v

The `-v` option displays the arguments passed to the JVM:

```sh
jps -v
```

Example:

```text
24680 ArgumentOutputDemo -Xms64m -Xmx128m -Dapp.mode=demo -Dregion=ap-southeast-1
25120 OrderService -Xms512m -Xmx2g -Dspring.profiles.active=prod
25210 jdk.jcmd/sun.tools.jps.Jps -Dapplication.home=/opt/jdk
```

Commonly seen arguments:

| Argument | Meaning |
|---|---|
| `-Xms64m` | Initial heap size |
| `-Xmx128m` | Maximum heap limit |
| `-Dapp.mode=demo` | Sets a system property for the application |
| `-Dregion=ap-southeast-1` | Example of a custom system property |
| `-ea` | Enables assertions according to the specified scope |

`-v` is useful when you need to confirm whether a JVM was launched with the expected heap limit, system properties, or runtime flags.

Not all configuration information appears in `-v`. Some values may come from environment variables, configuration files, custom launchers, container runtimes, or be modified by code after the JVM starts.

## 6. Combining -l, -m, and -v

You can combine the options:

```sh
jps -l -m -v
```

Or write them in short form:

```sh
jps -lmv
```

Example output line for an application:

```text
24680 com.example.tools.ArgumentOutputDemo --profile=staging --port=8080 -Xms64m -Xmx128m -Dapp.mode=demo
```

How to read it:

1. `24680` is the LVMID.
2. `com.example.tools.ArgumentOutputDemo` is the full main class name.
3. `--profile=staging --port=8080` are the application arguments.
4. `-Xms64m -Xmx128m -Dapp.mode=demo` are the JVM arguments.

The field order is identifier, class/JAR, application arguments, then JVM arguments. However, because tokens are separated by whitespace and there is no stable machine-readable schema, use this only for manual diagnostics.

## 7. Displaying Only Identifiers with -q and -V

The `-q` option suppresses the class name, JAR name, and application arguments, keeping only the local JVM identifier:

```sh
jps -q
```

Example:

```text
24680
25120
25210
```

Use `-q` when you only need a list of JVM identifiers. Do not use this output to decide which application to act on because the class/JAR name is hidden.

According to Oracle JDK 21 documentation, `-V` also suppresses the class name, JAR name, and application arguments, leaving only the list of LVMIDs:

```sh
jps -V
```

Some older JDK documentation describes `-V` differently from JDK 21 documentation. Therefore, check `jps -help` and the man page for the exact JDK you are using. When your goal is to view JVM arguments, use lowercase `-v`; do not confuse `-V` with `-v`.

## 8. Distinguishing Application Arguments and JVM Arguments

This is the most important distinction when reading argument output.

Example launch command:

```sh
java -Xms64m -Xmx128m -Dapp.mode=demo -cp out com.example.ArgumentOutputDemo --profile=staging --port=8080
```

| Part of the command | Type |
|---|---|
| `-Xms64m` | JVM argument |
| `-Xmx128m` | JVM argument |
| `-Dapp.mode=demo` | JVM/system property argument |
| `-cp out` | Java launcher option |
| `com.example.ArgumentOutputDemo` | Main class |
| `--profile=staging` | Application argument |
| `--port=8080` | Application argument |

`jps -m` focuses on the application arguments passed to `main()`. `jps -v` focuses on the JVM arguments. If you need to view both, use `jps -lmv`.

Not every token in the shell command appears verbatim in `jps` output. The shell may expand environment variables, quotes, or wildcards before invoking the Java launcher. The output reflects the information recorded by the JVM/tooling, not an exact copy of the original shell command line.

## 9. Hands-On Java 17+ Example: Creating a JVM with Recognizable Arguments

Create the source file `src/com/example/ArgumentOutputDemo.java`:

```java
package com.example;

import java.util.Arrays;
import java.util.concurrent.CountDownLatch;

public class ArgumentOutputDemo {
    public static void main(String[] args) throws InterruptedException {
        System.out.println("PID=" + ProcessHandle.current().pid());
        System.out.println("APP_ARGS=" + Arrays.toString(args));

        // Keep the JVM running so it can be inspected from another terminal.
        new CountDownLatch(1).await();
    }
}
```

Compile:

```sh
mkdir -p out
javac -d out src/com/example/ArgumentOutputDemo.java
```

Run the application with both JVM arguments and application arguments:

```sh
java -Xms64m -Xmx128m -Dapp.mode=demo -cp out com.example.ArgumentOutputDemo --profile=staging --port=8080
```

Program output:

```text
PID=24680
APP_ARGS=[--profile=staging, --port=8080]
```

`24680` is an illustrative PID; the actual value is printed by `ProcessHandle.current().pid()`. The program waits indefinitely so the JVM remains alive when you open a second terminal.

From the second terminal, run:

```sh
jps -lmv
```

Find the line with the `com.example.ArgumentOutputDemo` class. The corresponding line looks like:

```text
24680 com.example.ArgumentOutputDemo --profile=staging --port=8080 -Xms64m -Xmx128m -Dapp.mode=demo
```

The output may also contain other JVMs, including the `jps` process that was just launched. After practicing, press Ctrl+C in the terminal running the program to terminate the demo process.

## 10. Launching via a JAR

If the application is launched using an executable JAR:

```sh
java -Xmx512m -Dapp.env=production -jar order-service.jar --port=8080 --region=vn
```

`jps -lmv` may display output like:

```text
25120 /opt/services/order-service.jar --port=8080 --region=vn -Xmx512m -Dapp.env=production
```

Here:

- The JAR path is the launch target.
- `--port=8080` and `--region=vn` are the application arguments that the launcher passes to `main()`.
- `-Xmx512m` and `-Dapp.env=production` are the JVM arguments.

Use `-l` to view the full JAR path instead of the short name. If a deployment system creates multiple copies of a JAR with the same name in different directories, the full path helps identify the exact artifact that is running.

## 11. When jps Displays Unknown

`jps` uses information provided by the Java launcher to identify the class/JAR name and application arguments. If a JVM is launched using a custom launcher, that information may not be available.

Example:

```text
24680 Unknown
```

`Unknown` does not automatically mean the JVM is broken. It may indicate that the launcher does not provide the metadata `jps` needs to display the application name and main arguments.

When you encounter this case:

1. Use the LVMID to find the corresponding process.
2. Inspect the command line using operating system tools.
3. Check startup logs or the service definition.
4. Use `jcmd -l` and diagnostic commands if the JVM supports attach.
5. Check how the custom launcher initializes the JVM.

Do not assume `jps -m` will always recover application arguments when the launcher does not provide that information.

## 12. Process Visibility Scope of jps

`jps` only lists instrumented HotSpot JVMs that the tool has permission to access. The list may be restricted by the user/group of the account running `jps`, operating system permissions, container/PID namespaces, the attach mechanism, or JVM vendor differences.

Running `jps` under a different account may produce a different list. Do not use the absence of a line in the output as sole proof that a process does not exist.

In containers, run `jps` inside the appropriate container or PID namespace if you need to observe JVMs there. A PID viewed from the host may differ from the PID inside the container.

## 13. Viewing JVMs on a Remote Host

`jps` supports a host identifier (`hostid`) to query JVMs on another machine over supported protocols and configurations. With the default RMI protocol when specifying a hostname, the documentation requires `jstatd` to be running on the target host.

Host identifier syntax:

```text
[protocol:][[//]hostname][:port][/servername]
```

Illustrative example:

```sh
jps -l app-host.example.com:1099
```

This example assumes that a remote `jstatd` and RMI registry are configured on port 1099 and that the current machine has access permissions.

Remote monitoring does not work automatically just by adding a hostname. You must set up `jstatd`, RMI, and network permissions according to the JDK documentation. Only enable this service in controlled environments; do not expose administrative endpoints to untrusted networks.

## 14. Do Not Parse jps Output as a Stable Protocol

Oracle recommends not writing scripts that depend on the structure of `jps` output because the format may change in future releases.

Reasons:

- Fields are separated by whitespace.
- Application arguments can contain spaces.
- Class/JAR names and their display format can vary by launcher.
- JVM implementations and versions can differ.
- The tool is marked experimental and unsupported.

If you need automation, prefer the Process API or a service manager to manage processes launched by your application; use PIDs from a trusted source; use `jcmd` for JVM diagnostic commands; and use JMX or an observability system with a well-defined schema when you need long-term data.

Do not split output by fixed column positions or assume every line has the same number of tokens.

## 15. Security Note: Arguments Can Expose Secrets

`jps -m` and `jps -v` can display command-line arguments. Sensitive values can be exposed if passed via application arguments like `--password=...`, JVM system properties like `-Dservice.token=...`, launcher flags, or URLs with embedded credentials.

Do not pass passwords, API tokens, private keys, or secrets directly on the command line. These values can appear in process listings, diagnostic logs, monitoring tools, or incident support data.

Use a secret manager, a file protected with restricted permissions, a credential provider, or a secret-injection mechanism appropriate for your runtime. When sharing `jps` output, review and redact sensitive information first.

## 16. jps and Related Tools

| Tool | Purpose |
|---|---|
| `jps` | Lists instrumented JVMs and displays class/JAR/arguments |
| `jcmd -l` | Lists local JVMs that can be attached to |
| `jcmd PID help` | Views diagnostic commands supported by a specific JVM |
| `jcmd PID VM.command_line` | Views command-line information if the JVM supports the command |
| `ps` / Task Manager | Views processes at the operating system level |
| `jstat` | Monitors certain JVM statistics such as GC |
| JMX | Monitors and manages JVMs via MBeans |

Because `jps` is marked experimental and unsupported in Oracle JDK 21 documentation, consider `jcmd -l` for diagnostic workflows based on modern JDK tools. Process visibility still depends on permissions and the attach environment.

Not every `jcmd` command is available on every JVM or every version. Query the target JVM with `jcmd PID help` before invoking a specific diagnostic command.

## 17. Common Issues and Troubleshooting

| Symptom | Common Cause | Resolution |
|---|---|---|
| Application not visible in `jps` | Different user, container namespace, or uninstrumented/unattachable JVM | Run under the right user/namespace and check with a process manager |
| Only LVMID numbers shown | `-q` or `-V` was used | Run `jps -l` or `jps -lmv` |
| Application arguments not shown | `-m` was not used or the launcher did not provide metadata | Use `jps -m` and check the launcher |
| JVM arguments not shown | `-v` was not used | Run `jps -v` |
| Class name is shortened | Default output was used | Use `jps -l` |
| Displays `Unknown` | JVM is running via a custom launcher or metadata is unavailable | Check the command line, service definition, and logs |
| LVMID differs from expected PID | LVMID is not guaranteed to always be the OS PID | Verify the PID using OS tools |
| Application arguments split incorrectly | Arguments contain whitespace making output ambiguous | Do not parse output; check the original config/launcher |
| Output differs between two JDKs | Format/options may change across releases | Read `jps -help` and the documentation for the exact version |
| Remote host returns no results | `jstatd`/RMI is not configured or the port is blocked | Check the remote service, registry, and network policy |
| Output contains sensitive data | Secrets were passed on the command line | Replace with a secret manager/credential provider and redact output |

## 18. Workflow for Reading Argument Output During Investigation

When you need to determine what configuration an application is running with:

1. Run `jps` to get an initial list of JVMs.
2. Use `jps -l` to identify the full class or JAR.
3. Use `jps -m` to view application arguments.
4. Use `jps -v` to view JVM arguments.
5. Use `jps -lmv` if you need to view all groups at once.
6. Cross-check the LVMID against the operating system PID.
7. Confirm key values in the application's logs/configuration.
8. Redact secrets before saving or sharing output.
9. If deeper diagnostics are needed, use `jcmd` against the right JVM.
10. Record the JDK version and commands used so results are reproducible.

For heap issues, check `-Xms` and `-Xmx` in the JVM arguments. For application profiles, check the corresponding application argument or system property. For missing-process issues, check user, container, and attach permissions before concluding the JVM is not running.
