# Monitoring Java Compilation Output

## 1. Monitoring Output in the Compilation Pipeline

When compiling Java, the compiler produces several different kinds of output. To know whether compilation succeeded, you need to observe the right type of output at the right stage.

Outputs can be divided into four groups:

1. **Compiler diagnostics:** errors, warnings, and notes detected by the compiler in the source code or during processing.
2. **Process output:** information written by the compiler or build tool to standard output (stdout) and standard error (stderr).
3. **Generated artifacts:** .class files, source files generated by annotation processors, native headers, and other build products.
4. **Build execution report:** task status, cache status, execution time, and results from Gradle, Maven, or CI.

These groups are related but not synonymous. A compilation run may print nothing to the terminal and still generate .class files successfully. Conversely, a log with many lines of messages does not mean compilation succeeded; you need to check diagnostics and the process exit code.

General observation flow:

~~~text
Java source files
      |
      v
Compiler / build task
      |
      +----> stdout / stderr / diagnostics
      |
      +----> generated source files
      |
      +----> .class files
      |
      +----> build task result and exit code
      |
      v
Inspect artifacts and verify behavior
~~~

The goal of monitoring output is to answer: did the compiler run, which sources were processed, were there any errors or warnings, which files were generated, where are they located, and did the build actually finish successfully?

## 2. Default Output of javac

Basic javac command:

~~~bash
javac Hello.java
~~~

If the source is valid and the compiler does not need to emit additional messages, javac usually prints no success message. The .class file is created in the current directory or in the location specified by the -d option.

Silence after a javac command does not mean the compiler did not run. Check the exit code and the output artifacts.

Example file src/demo/Hello.java:

~~~java
package demo;

public class Hello {
    public static void main(String[] args) {
        System.out.println("Hello from compiled class");
    }
}
~~~

Compile from the project root directory:

~~~bash
javac --release 17 -encoding UTF-8 -d out src/demo/Hello.java
~~~

Output structure:

~~~text
project/
├── src/
│   └── demo/
│       └── Hello.java
└── out/
    └── demo/
        └── Hello.class
~~~

The -d option specifies the root directory for storing class files. The compiler creates subdirectories matching the class package. Therefore, the demo.Hello class is saved at out/demo/Hello.class.

Run the program with the classpath pointing to the root directory containing the package:

~~~bash
java -cp out demo.Hello
~~~

Application stdout:

~~~text
Hello from compiled class
~~~

You need to distinguish application stdout from compiler output. The line Hello from compiled class appears when the JVM runs the program, not when javac compiles the source.

## 3. Distinguishing stdout, stderr, Diagnostics, and Exit Code

A command-line process can write data to two standard streams:

- **stdout:** normal output, such as program results or information intentionally printed by the tool.
- **stderr:** error messages, warnings, or diagnostic information. A tool may use stderr for many kinds of messages, not only errors.
- **Exit code:** the termination status of the process, usually 0 on success and non-zero on failure.

Do not classify errors based solely on the output stream. A tool may write warnings to stderr and still return exit code 0. Other tools may write normal logs to stderr. The exit code together with diagnostics and the resulting artifacts show the complete status.

With javac, compilation errors usually include the file name, line, column, message, and a position indicator. For example:

~~~java
public class Broken {
    public static void main(String[] args) {
        int count = "ten";
    }
}
~~~

The compiler reports an error stating that a String value cannot be assigned to an int variable. The exact wording and formatting of diagnostics may vary by JDK, locale, and compiler options.

A compilation run should be evaluated using three questions:

1. Is there any ERROR diagnostic?
2. Is the exit code of javac/build tool equal to 0?
3. Were the expected artifacts created or updated in the right place?

If the build tool reports success but the artifacts do not appear, check the output directory, source set/module configuration, and which tasks actually ran. If the artifacts exist but the build returns an error, a step after compilation may have failed.

## 4. Capturing Logs and Preserving the Exit Code

When running compilation in a terminal or CI, save logs so they can be reviewed when a build fails. Preserve the exit code before running another command, because a command that reads the log can overwrite the shell's last exit code.

### Bash on Linux/macOS

~~~bash
javac --release 17 -encoding UTF-8 -d out src/demo/Hello.java > compile.stdout.log 2> compile.stderr.log
compile_status=$?

echo "javac exit code: $compile_status"
cat compile.stdout.log
cat compile.stderr.log

if [ "$compile_status" -ne 0 ]; then
    exit "$compile_status"
fi
~~~

Stdout and stderr are saved separately. The compile_status variable captures the exit code of javac immediately after the process finishes.

If you use a pipe with tee to both view and save the log, note that the default exit code of a pipeline is usually the exit code of the last command. In Bash, you can enable pipefail so that a javac failure is not masked by tee.

~~~bash
set -o pipefail
javac --release 17 -d out src/demo/Hello.java 2>&1 | tee compile.log
compile_status=$?
~~~

### PowerShell on Windows

~~~powershell
javac --release 17 -encoding UTF-8 -d out src/demo/Hello.java *> compile.log
$compileStatus = $LASTEXITCODE

Write-Output "javac exit code: $compileStatus"
Get-Content compile.log

if ($compileStatus -ne 0) {
    exit $compileStatus
}
~~~

For native programs like javac, PowerShell stores the process exit code in LASTEXITCODE. Capture that value immediately after the command being monitored, before calling Get-Content or another command.

Do not rely only on PowerShell's $? variable after a sequence of commands if your goal is to know the exact exit code of a native process. $? indicates the success status of the most recent PowerShell command; LASTEXITCODE holds the exit code of the most recent native program.

## 5. Monitoring Detailed javac Activity

When you need to know which files the compiler is reading, how it processes the classpath, or what work it is performing, use the -verbose option:

~~~bash
javac -verbose --release 17 -d out src/demo/Hello.java
~~~

The -verbose option instructs the compiler to print information about internal operations such as reading source/class files and writing class files. This is diagnostic logging, not application output. Log details and content depend on the JDK, classpath, sources, and environment, so you should not use exact verbose log text as a stable test assertion.

You can combine verbose with redirection to save it:

~~~bash
javac -verbose --release 17 -d out src/demo/Hello.java > javac-verbose.log 2>&1
~~~

Use verbose when you need to investigate:

- Did the compiler find the source files to compile?
- Which classes is the compiler loading from the classpath or module path?
- Which directory are class files being written to?
- Which directory, JAR, or module was a dependency found in?
- Why does a compilation run take an unusual amount of time or behave unexpectedly?

Do not enable verbose for every CI build unless necessary. The logs can become very long, making it harder to find the main error and increasing storage usage.

## 6. Monitoring Warnings and Errors

Compiler diagnostics help detect syntax errors, type errors, deprecated APIs, and many other issues. You can adjust warning levels using javac options.

### -Xlint

The -Xlint option enables additional warning categories:

~~~bash
javac -Xlint:all --release 17 -d out src/demo/Hello.java
~~~

You can select specific warning categories instead of all. For example:

~~~bash
javac -Xlint:deprecation -Xlint:unchecked --release 17 -d out src/demo/Hello.java
~~~

Common categories:

| Category | Description |
|---|---|
| deprecation | Use of APIs marked as deprecated. |
| unchecked | Generic operations with incomplete type checking. |
| rawtypes | Use of raw types instead of declaring type parameters. |
| serial | Issues related to serialization and serialVersionUID. |
| fallthrough | Switch cases that may fall through to the next case. |
| finally | Certain finally blocks that may discard control-flow results or exceptions. |
| path | Issues related to search paths. |

Available warning categories and exact details depend on the compiler version. You can check the supported list in the javac documentation for your exact JDK or by running javac -X.

### -Werror and -Xdiags

You can instruct the compiler to treat warnings as errors:

~~~bash
javac -Xlint:all -Werror --release 17 -d out src/demo/Hello.java
~~~

When using -Werror, a single warning can cause compilation to fail. This is useful in CI if the project has a zero-warning policy, but you should align with the team and address intentional warnings before enabling it.

The -Xdiags:verbose option requests more detailed diagnostic formatting on compilers that support it:

~~~bash
javac -Xdiags:verbose --release 17 -d out src/demo/Hello.java
~~~

Verbose formatting helps diagnose certain type or overload errors, but the messages should not be parsed by scripts as a stable API. If you need programmatic integration, prefer the Java Compiler API and Diagnostic API.

## 7. Tracking Where Class Files and Generated Sources Are Stored

Javac provides several options to control output directories. Separating artifact types keeps builds easier to manage and avoids confusing human-written sources with sources generated by the compiler or annotation processors.

| Option | Output |
|---|---|
| -d directory | Root directory for compiled class files. |
| -s directory | Root directory for source files generated by annotation processors. |
| -h directory | Root directory for native headers generated for JNI when applicable during compilation. |

Example:

~~~bash
javac --release 17 -d build/classes -s build/generated/sources -h build/generated/headers src/demo/Hello.java
~~~

If no annotation processor generates sources or no native declarations require headers, the corresponding directories may not be created. Do not assume an option was ignored just because a directory is empty; verify whether the sources and processors actually require those artifacts.

For annotation processing, you can observe processing rounds and invoked processors using extended javac options:

~~~bash
javac -XprintRounds -XprintProcessorInfo -d build/classes -s build/generated/sources src/demo/UseGeneratedType.java
~~~

The -XprintRounds and -XprintProcessorInfo options are useful for checking whether a processor was discovered and executed. These are extended javac options; verify support on the JDK you are using.

Common annotation processing modes:

- -proc:none: do not run annotation processing.
- -proc:only: run annotation processing only, without normal compilation.
- Default: the compiler may run annotation processing if matching processors are found on the processor path or classpath as configured.

If processor-generated sources are incorrect, check the processor path, processor version, processing rounds, the -s directory, and diagnostics. Do not edit generated sources directly if the build process will regenerate them.

## 8. Inspecting .class File Contents

After compilation, you can use javap to inspect the contents of class files. javap is a tool bundled with the JDK that lets you view class structure, methods, bytecode, and metadata.

Example:

~~~bash
javap -classpath out demo.Hello
~~~

This command displays the class declaration and public members as presented by javap.

To view bytecode:

~~~bash
javap -classpath out -c demo.Hello
~~~

The -c option prints the bytecode instructions of methods. To view more detailed information:

~~~bash
javap -classpath out -verbose demo.Hello
~~~

javap's verbose mode is specific to the javap tool, distinct from javac -verbose. Its output can include the constant pool, flags, descriptors, attributes, and debug information stored in the class file.

You can use javap to verify:

- Does the class file have the right package and class name?
- Were the expected methods generated?
- Does the bytecode contain the expected instructions or calls?
- Does the class file contain appropriate metadata such as line numbers, generic signatures, or annotations?
- Did the compiler use the release/target required by the project?

To inspect class file version information and the constant pool, use javap -verbose. Do not look at only a few lines of bytecode to conclude that the entire application is compatible; you also need to check dependencies, runtime, and runtime behavior.

## 9. Monitoring Output Through Gradle and Maven

When using a build tool, javac is usually invoked inside a task or plugin. Therefore, terminal logs also contain build tool orchestration output, task status, and dependency information.

### Gradle

For projects using the Java plugin, the compileJava task compiles the main source set:

~~~bash
./gradlew compileJava --console=plain
~~~

On Windows, you can use:

~~~powershell
.\gradlew.bat compileJava --console=plain
~~~

Add --info for additional diagnostic information when needed:

~~~bash
./gradlew compileJava --info --console=plain
~~~

Common task outcomes:

- **UP-TO-DATE:** current outputs are considered valid based on inputs and task state; Gradle does not need to re-execute the task.
- **FROM-CACHE:** Gradle retrieved the corresponding outputs from the build cache.
- **NO-SOURCE:** the task had no matching sources to process.
- **EXECUTED:** the task executed during this build.

Default outputs of the Java plugin are typically located in build/classes/java/main for the main source set and build/classes/java/test for the test source set. Projects can customize these paths.

If a task is UP-TO-DATE, not seeing javac run in the terminal is normal. To investigate why a task did or did not execute, check inputs/outputs, task outcomes, and --info logs. Only use --rerun-tasks when you genuinely need to force tasks to re-run and understand the impact on related tasks.

### Maven

For Maven, the compile phase compiles main sources:

~~~bash
mvn compile
~~~

For additional diagnostic information:

~~~bash
mvn -X compile
~~~

The -X option enables very detailed debug logging; avoid enabling it routinely in CI or sharing logs publicly if they might contain internal paths, repository details, or sensitive data. The -e option prints stack traces when Maven encounters errors.

Default Maven outputs are typically located in target/classes. Sources generated by plugins may be in target/generated-sources or a directory configured by the plugin.

Distinguish the compile phase from test and package. A successful mvn compile confirms the compile step completed; it does not prove tests ran or that the final JAR was packaged.

## 10. Distinguishing New Output, Stale Output, and Cache

The mere existence of a .class file is not enough to prove that the latest compilation produced it. The file might remain from a previous build, come from a cache, or originate from another source/output directory.

Common situations:

- The build tool reports UP-TO-DATE or FROM-CACHE: the task did not necessarily invoke javac in the current run.
- Deleting or renaming a source class: the old corresponding .class file may still exist if the output directory was not cleaned.
- Changing compiler, toolchain, processor, or classpath configuration: may change task inputs and require recompilation.
- Sharing an output directory across multiple build configurations: class files from a previous build may be mistaken for current results.

To verify reliably, identify the output directory of the right task, observe the task outcome, check timestamps or artifact contents, and run a clean build according to project procedures when a clean comparison is needed. Clean tasks typically delete generated build outputs; only run them when you understand that those artifacts will be regenerated.

In CI, store logs and artifacts per job/build ID. Do not mix .class files from multiple jobs or commits into the same directory without a clear separation convention.

## 11. Organizing Output Monitoring in CI

A compilation pipeline can collect the following evidence:

1. **Build identity:** commit, branch, build number, JDK vendor/version, operating system, and architecture.
2. **Compiler configuration:** release, encoding, classpath/module path, annotation processors, and compiler flags.
3. **Diagnostics:** stdout/stderr or merged logs, warning/error status, and exit code.
4. **Artifact inventory:** paths, sizes, checksums, and types of generated artifacts.
5. **Task outcome:** which tasks ran, which came from cache, and which were skipped due to no source.
6. **Verification:** running appropriate tests or inspecting output classes/JARs with the corresponding tools.

Do not retain logs indefinitely if they contain sensitive information or are large. Apply appropriate retention policies, mask tokens/secrets, and restrict artifact access permissions. Never print all environment variables or command lines containing passwords into logs.

When compilation fails, logs should help readers quickly identify the source file, first diagnostic, compiler version, command/flags, and failing task. When compilation succeeds, artifacts must be linked to the exact commit and build identity for traceability.

## 12. Common Pitfalls When Monitoring Output

| Symptom | Possible Cause | How to Check |
|---|---|---|
| javac runs but prints nothing | Compilation succeeded and javac has no default success message. | Check the exit code and .class files. |
| Logs exist but the build still fails | Logs may just be verbose output; a diagnostic or later task failed. | Search for ERROR and check the final build exit code. |
| No .class files found | Wrong output directory, sources not compiled, or compilation failed. | Check -d, task outcome, and diagnostics. |
| Old .class files still remain | Output directory contains artifacts from a previous build. | Check timestamps/build ID and clean per project workflow when needed. |
| Warnings do not fail the build | Compiler defaults to emitting warnings only. | Use appropriate -Xlint options; consider -Werror per project policy. |
| Annotation processor does not appear to run | Processor not discovered, wrong processor path, or processing disabled. | Check processor path, -proc, and -XprintRounds/-XprintProcessorInfo. |
| Gradle does not invoke the compiler | Task is UP-TO-DATE, FROM-CACHE, or NO-SOURCE. | Check task outcome and inputs/outputs. |
| Maven compile succeeds but no JAR exists | The compile phase does not run package. | Run the package phase per project workflow if a JAR artifact is needed. |
| CI reports success despite javac error | Script lost the exit code, pipeline only captured tee's status, or a later command masked the error. | Save the exit code immediately after the process; use pipefail in Bash. |
| Verbose logs are too large | Detailed diagnostic mode enabled for all builds. | Enable only during investigation and limit retention. |

## 13. Compilation Output Monitoring Checklist

- [ ] Verified the correct JDK/compiler version and the executed compile command.
- [ ] Distinguished stdout, stderr, diagnostics, and exit code.
- [ ] Preserved the exit code before running subsequent log-processing commands.
- [ ] Confirmed output locations via -d or build tool configuration.
- [ ] Verified expected class files or generated sources.
- [ ] Read warnings/errors and enabled appropriate -Xlint options when needed.
- [ ] Used -verbose or build-tool debug/info mode only for diagnostic purposes.
- [ ] Distinguished new outputs from stale artifacts or cached outputs.
- [ ] Verified annotation processors and generated outputs if used by the project.
- [ ] Stored logs/artifacts by build identity and protected sensitive data.
- [ ] Verified test/package separately if those steps are required by the goal.

Effective output monitoring combines logs, diagnostics, exit codes, and artifacts. When each type of evidence is checked in its proper role, you can determine exactly what the compiler did, why a build failed, and which files were actually produced.
