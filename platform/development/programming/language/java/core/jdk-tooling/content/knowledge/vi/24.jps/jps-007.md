# Thiếu process trong jps

## 1. Hiện tượng và ý nghĩa

Khi chạy lệnh **jps** nhưng không thấy một ứng dụng Java đang hoạt động, hoặc danh sách chỉ hiển thị chính tiến trình **jps**, đây là tình huống thường gặp khi chẩn đoán JVM.

**jps** (Java Virtual Machine Process Status Tool) là công cụ dòng lệnh trong JDK dùng để liệt kê các JVM HotSpot đã được instrument trên máy đích. Công cụ chỉ hiển thị các JVM mà tài khoản đang chạy lệnh có quyền truy cập. Vì vậy, kết quả jps không phải danh sách đầy đủ mọi tiến trình có chứa Java trên toàn hệ điều hành.

Nguyên nhân thường gặp:

- Ứng dụng đã dừng hoặc đang chạy trên máy, container hay môi trường khác.
- jps được chạy bằng tài khoản khác với tài khoản khởi chạy ứng dụng.
- JVM không cung cấp performance data cần thiết cho việc phát hiện.
- Ứng dụng nằm trong Docker, WSL hoặc process namespace riêng.
- Máy đang dùng một JVM implementation hoặc custom launcher có hành vi khác.
- Đang gọi nhầm jps từ JDK khác hoặc một bản cài không đầy đủ.

Cần phân biệt **không tìm thấy JVM** với **đã tìm thấy JVM nhưng không hiển thị tên class/JAR mong muốn**. Nếu ứng dụng dùng custom launcher, jps có thể hiển thị Unknown cho tên class hoặc JAR; điều đó không có nghĩa tiến trình đã biến mất.

## 2. Hiểu giới hạn của jps

Theo tài liệu Oracle, jps liệt kê các instrumented HotSpot JVM trên hệ thống đích và chỉ báo cáo JVM mà người chạy lệnh có quyền truy cập. Công cụ này được đánh dấu experimental/unsupported; định dạng output có thể thay đổi giữa các phiên bản JDK.

Một số giới hạn cần nhớ:

- jps tập trung vào instrumented HotSpot JVM, không phải bộ liệt kê mọi tiến trình hệ điều hành.
- Danh sách bị giới hạn bởi quyền truy cập của tài khoản hiện tại.
- Lệnh mặc định tìm JVM trên local host. Truy vấn remote host cần cấu hình jstatd trên máy đích.
- LVMID (local VM identifier) thường trùng PID hệ điều hành nhưng không được bảo đảm luôn như vậy.
- Với custom launcher, tên class/JAR và main arguments có thể hiện là Unknown.
- Không nên viết script phụ thuộc vào cấu trúc từng cột hoặc parse output jps như một API ổn định.

Nếu jps không hiển thị một process, hãy xác minh tiến trình ở cấp hệ điều hành trước khi kết luận ứng dụng không chạy.

Tài liệu: [The jps Command — Java SE 26](https://docs.oracle.com/en/java/javase/26/docs/specs/man/jps.html).

## 3. Kiểm tra đúng công cụ JDK đang được gọi

Máy có thể cài nhiều JDK. Terminal, IDE, service hoặc script có thể gọi các bản jps khác nhau.

Windows PowerShell:

```powershell
Get-Command java -All
Get-Command jps -All
$env:JAVA_HOME
java -version
jps --help
```

Linux:

```bash
command -v java
command -v jps
echo "$JAVA_HOME"
java -version
jps --help
```

macOS:

```bash
command -v java
command -v jps
/usr/libexec/java_home -V
java -version
jps --help
```

Nếu jps không được nhận diện:

1. Kiểm tra đã cài JDK đầy đủ hay chỉ có runtime rút gọn.
2. Kiểm tra thư mục bin của đúng JDK có nằm trong PATH hay không.
3. Dùng đường dẫn trực tiếp tới jps trong JDK cần kiểm tra.
4. So sánh vendor và phiên bản JDK dùng để chạy ứng dụng với JDK dùng để chạy công cụ chẩn đoán.

Không mặc định rằng JAVA_HOME của terminal cũng là JDK mà Windows service, systemd unit, IDE hoặc container đang sử dụng.

## 4. Dùng các tùy chọn jps để mở rộng thông tin

Khi lệnh cơ bản chưa đủ thông tin, thử từng tùy chọn:

| Lệnh | Thông tin hiển thị |
|---|---|
| **jps** | LVMID và tên class/JAR dạng ngắn |
| **jps -q** | Chỉ hiển thị LVMID |
| **jps -l** | Tên class đầy đủ hoặc đường dẫn JAR |
| **jps -m** | Các tham số truyền vào main() |
| **jps -v** | Các tham số JVM |

Ví dụ:

```bash
jps
jps -q
jps -l
jps -m
jps -v
```

Output minh họa:

```text
24801 com.example.Main
25120 jdk.jcmd/sun.tools.jps.Jps
```

Các con số trong output thay đổi theo mỗi lần chạy. Việc thấy chính jps trong danh sách là bình thường vì bản thân công cụ cũng chạy trên JVM.

Cách đọc kết quả:

- Nếu jps có process nhưng jps -l cho thấy tên khác, hãy kiểm tra module/class/JAR thực tế.
- Nếu tên là Unknown, kiểm tra custom launcher hoặc cách ứng dụng được khởi chạy.
- Nếu jps -q có ID nhưng không có tên ứng dụng ở output khác, xác minh ID bằng công cụ hệ điều hành.
- Nếu chỉ có process jps, điều đó chỉ chứng minh công cụ hiện tại nhìn thấy chính nó; chưa chứng minh mọi JVM khác đều đã dừng.

Lưu ý bảo mật: -m và -v có thể hiển thị tham số khởi chạy. Tránh chia sẻ output chưa che token, mật khẩu hoặc đường dẫn nội bộ.

## 5. Kiểm tra ứng dụng có thực sự đang chạy không

Trước khi sửa cấu hình Java, hãy tìm tiến trình bằng công cụ của hệ điều hành. Cách này giúp phân biệt process đã dừng với JVM đang chạy nhưng jps không thể liệt kê.

### 5.1. Windows PowerShell

Dùng CIM để xem PID, tên executable, đường dẫn và command line:

```powershell
Get-CimInstance Win32_Process |
    Where-Object { $_.Name -in @('java.exe', 'javaw.exe') } |
    Select-Object ProcessId, Name, ExecutablePath, CommandLine
```

Nếu ứng dụng chạy qua service wrapper hoặc native launcher, tên executable có thể không phải java.exe/javaw.exe. Khi đó, kiểm tra service tương ứng trong Services hoặc truy vấn tiến trình theo tên wrapper.

### 5.2. Linux

```bash
ps -eo pid,user,args | grep -E '[j]ava(w)?'
pgrep -af java
```

Xem PID, user sở hữu và command line. Nếu service do systemd quản lý, kiểm tra trạng thái service và cấu hình ExecStart:

```bash
systemctl status <service-name>
systemctl show <service-name> -p MainPID -p User -p ExecStart
```

### 5.3. macOS

```bash
ps -axo pid,user,command | grep -E '[j]ava(w)?'
pgrep -fl java
```

Nếu ứng dụng được khởi chạy bởi một launcher riêng, hãy tìm process cha hoặc service quản lý ứng dụng thay vì chỉ lọc chuỗi java.

### 5.4. Diễn giải kết quả

- Không có process liên quan: kiểm tra service, log khởi động, lịch chạy và lỗi startup.
- Có process Java nhưng jps không liệt kê: tiếp tục kiểm tra user, perfdata, JVM implementation và container.
- Có process native launcher chứa JVM nhúng: jps có thể thấy nếu JVM HotSpot được instrument và quyền truy cập cho phép; lọc tên java.exe hoặc chuỗi java có thể bỏ sót loại process này.
- PID đã thay đổi: ứng dụng có thể vừa restart; dùng PID hiện tại thay vì PID lưu từ lần kiểm tra trước.

## 6. Nguyên nhân 1: chạy jps bằng tài khoản khác

Đây là nguyên nhân phổ biến trong môi trường server.

Ví dụ, ứng dụng chạy bằng tài khoản service appuser, nhưng quản trị viên lại chạy jps bằng tài khoản cá nhân. Cơ chế kiểm soát truy cập của hệ điều hành có thể ngăn tài khoản đó nhìn thấy JVM của appuser.

Cách kiểm tra:

```bash
ps -eo pid,user,args | grep -E '[j]ava(w)?'
id
```

Nếu xác định service chạy dưới tài khoản appuser, chạy lệnh chẩn đoán bằng chính tài khoản đó theo chính sách hệ thống:

```bash
sudo -u appuser jps -l
```

Trên Windows, xác định account chạy Windows service và thực hiện chẩn đoán bằng account có quyền truy cập phù hợp. Nếu cần quyền quản trị, tuân theo chính sách cấp quyền của tổ chức.

Không nên mặc định chạy mọi công cụ bằng root hoặc Administrator. Quyền cao hơn không tự sửa được sai khác về user, namespace hay cấu hình instrumentation.

## 7. Nguyên nhân 2: performance data bị tắt hoặc không truy cập được

HotSpot có cơ chế performance data phục vụ các công cụ giám sát. Tùy chọn JVM -XX:+UsePerfData được bật mặc định. Nếu ứng dụng khởi chạy với -XX:-UsePerfData, JVM không tạo các thư mục hsperfdata_<userid> dùng cho performance data.

Kiểm tra command line và cấu hình service để tìm tùy chọn này:

```bash
jps -v
```

Nếu đã biết PID:

```bash
jcmd <PID> VM.command_line
```

Nếu cấu hình có -XX:-UsePerfData, hãy xác minh lý do tùy chọn được bật. Khi chính sách vận hành cho phép và công cụ giám sát cần performance data, có thể bỏ tùy chọn tắt hoặc cấu hình bật lại bằng -XX:+UsePerfData, sau đó restart JVM theo kế hoạch triển khai.

Lưu ý:

- Thay đổi cờ JVM thường cần khởi động lại tiến trình.
- Không tự thay đổi production flag khi chưa đánh giá tác động và chính sách vận hành.
- Không xóa thủ công file hoặc thư mục performance data của JVM đang chạy.
- Trên Linux, kiểm tra quyền truy cập thư mục tạm/perfdata và filesystem chứa chúng.
- Nếu dùng bản build hoặc JVM khác HotSpot, kiểm tra tài liệu riêng của nhà cung cấp.

Nguồn: [The java Command — Java SE 26](https://docs.oracle.com/en/java/javase/26/docs/specs/man/java.html).

## 8. Nguyên nhân 3: JVM nằm trong Docker hoặc process namespace khác

Lệnh jps chạy trên host không nhất thiết nhìn thấy JVM chạy trong một Docker container có process namespace riêng. jcmd -l trên host cũng không liệt kê JVM trong Docker process riêng theo tài liệu JDK.

Hãy kiểm tra từ bên trong container:

```bash
docker ps
docker exec <container-name> jps -l
docker exec <container-name> ps -ef
```

Nếu image chỉ có JRE hoặc không chứa công cụ JDK, jps có thể không tồn tại. Khi đó, dùng ps trong container hoặc kiểm tra PID qua runtime quản lý container.

Với Kubernetes:

```bash
kubectl get pods -n <namespace>
kubectl exec -n <namespace> <pod-name> -- jps -l
kubectl exec -n <namespace> <pod-name> -- ps -ef
```

Nếu cần dùng jcmd, chạy nó trong cùng môi trường container và bằng user phù hợp với JVM:

```bash
docker exec <container-name> jcmd <PID> VM.version
```

PID nhìn từ host có thể khác PID trong container. Không sao chép PID giữa hai namespace mà chưa xác định đúng process mapping.

Với WSL hoặc VM, chạy jps trong cùng môi trường hệ điều hành nơi JVM đang chạy. Một lệnh trên Windows host không tự động liệt kê JVM trong Linux WSL hoặc VM riêng.

## 9. Nguyên nhân 4: đang kiểm tra nhầm máy hoặc nhầm môi trường

jps không tự quét toàn bộ máy chủ trong mạng. Nếu ứng dụng chạy trên host khác, hãy chạy lệnh trực tiếp trên host đích, ví dụ qua SSH:

```bash
ssh <user>@<host> 'jps -l'
```

Oracle cũng hỗ trợ hostid để truy vấn từ xa:

```bash
jps -l <hostname>
```

Cách này yêu cầu jstatd đang chạy trên máy đích cùng registry/port phù hợp và người gọi có quyền truy cập. Chỉ cấu hình remote monitoring khi đã được phê duyệt và có biện pháp kiểm soát truy cập mạng phù hợp.

Nếu không cần remote jstatd, chạy jps qua SSH trên chính host đích thường dễ kiểm soát hơn.

## 10. Nguyên nhân 5: dùng JVM khác HotSpot hoặc custom launcher

jps được mô tả cho các instrumented Java HotSpot VM. Nếu ứng dụng sử dụng Eclipse OpenJ9 hoặc một JVM implementation khác, khả năng liệt kê và công cụ đi kèm có thể khác. Hãy dùng công cụ đúng theo nhà cung cấp runtime.

Kiểm tra thông tin runtime của ứng dụng nếu đã xác định được PID hoặc log startup:

```bash
java -version
jcmd <PID> VM.version
jcmd <PID> VM.command_line
```

Với custom launcher hoặc JVM được nhúng bằng JNI:

- Process có thể không mang tên java hoặc java.exe.
- jps có thể hiển thị Unknown thay cho tên class/JAR và main arguments.
- OS process listing theo chuỗi java có thể bỏ sót tiến trình native có JVM nhúng.
- Hãy tìm process owner, service wrapper hoặc launcher gốc.

Unknown là giới hạn hiển thị tên ứng dụng; không đồng nghĩa với việc jps không tìm thấy JVM.

## 11. Khi đã có PID, dùng jcmd để xác minh JVM

Nếu OS process listing đã tìm được PID nhưng jps không hiển thị process, có thể thử jcmd trực tiếp.

Liệt kê JVM mà jcmd nhìn thấy:

```bash
jcmd -l
```

Kiểm tra một process đã biết:

```bash
jcmd <PID> help
jcmd <PID> VM.version
jcmd <PID> VM.command_line
```

Ý nghĩa:

- help: liệt kê các diagnostic command mà JVM mục tiêu hỗ trợ.
- VM.version: in thông tin phiên bản HotSpot/JDK của tiến trình.
- VM.command_line: hiển thị command line dùng để khởi chạy JVM.

jcmd phải chạy trên cùng máy và với effective user/group phù hợp với tiến trình JVM. Nếu target nằm trong container, chạy lệnh ở container hoặc namespace tương ứng.

Nếu OS tìm được PID nhưng jcmd không attach được, kiểm tra lại PID có đúng là JVM không, process còn sống không, user/group có khớp không và runtime có hỗ trợ diagnostic attach không. Đọc thông báo lỗi cụ thể trước khi thay đổi cấu hình.

Tài liệu: [The jcmd Command — Java SE 24](https://docs.oracle.com/en/java/javase/24/docs/specs/man/jcmd.html).

## 12. Quy trình chẩn đoán theo thứ tự

Thực hiện lần lượt để tránh thay đổi cấu hình khi chưa xác định nguyên nhân:

1. **Kiểm tra công cụ:** xác nhận đúng JDK và jps đang được gọi.
2. **Chạy lệnh chi tiết:** thử jps -l, sau đó jps -m hoặc jps -v nếu cần.
3. **Xác minh process hệ điều hành:** dùng ps, pgrep hoặc PowerShell CIM để tìm PID.
4. **Đối chiếu user:** xác định account đang chạy JVM và account đang chạy jps.
5. **Đối chiếu môi trường:** xác nhận cùng host, container, WSL, VM và process namespace.
6. **Kiểm tra instrumentation:** xem JVM có tắt UsePerfData hoặc có cấu hình đặc biệt không.
7. **Kiểm tra runtime:** xác định JVM HotSpot hay implementation khác.
8. **Dùng PID đã xác minh:** chạy jcmd <PID> VM.version và VM.command_line khi quyền cho phép.
9. **Kiểm tra service log:** nếu process không tồn tại, đọc log và trạng thái service để tìm lỗi startup hoặc restart.
10. **Ghi nhận nguyên nhân:** lưu command, user, host/container, PID, JDK vendor/version và thông báo lỗi.

Không kết luận ứng dụng đã dừng chỉ vì output jps rỗng hoặc chỉ có chính jps.

## 13. Bảng lỗi và cách xử lý nhanh

| Hiện tượng | Nguyên nhân có thể | Cách xử lý |
|---|---|---|
| jps chỉ hiện chính nó | JVM mục tiêu không được instrument, không có quyền hoặc ở namespace khác | Kiểm tra OS process list, user và container |
| jps không được nhận diện | PATH thiếu JDK bin hoặc chỉ cài runtime rút gọn | Kiểm tra JAVA_HOME, vị trí jps và cài đặt JDK |
| jps -l hiện Unknown | JVM dùng custom launcher hoặc embedded launcher | Xác minh PID bằng OS và dùng jcmd nếu có quyền |
| jps chạy bằng user A không thấy service của user B | OS access control hạn chế quyền quan sát | Chạy công cụ bằng service account được phép |
| Host không thấy JVM trong Docker | Process namespace/container riêng | Chạy jps hoặc ps bên trong container |
| jps không thấy JVM đã tắt perfdata | Có thể JVM dùng -XX:-UsePerfData | Kiểm tra command line và cấu hình startup |
| jps remote không kết nối | Thiếu jstatd, RMI registry, port hoặc quyền truy cập | Kiểm tra cấu hình remote monitoring; cân nhắc SSH vào host |
| OS thấy PID nhưng jcmd không attach | Sai user/group, PID không còn hợp lệ hoặc attach bị hạn chế | Xác minh PID, user, namespace và runtime |
| Có nhiều java executable | PATH hoặc service cấu hình nhiều JDK | Xác định executable thật của process và đường dẫn service |
| Script parse sai output | Định dạng jps không ổn định | Không dùng output jps như API; dùng OS process API phù hợp |

## 14. Những lưu ý vận hành và bảo mật

- jps -m và jps -v có thể làm lộ tham số ứng dụng, đường dẫn và giá trị nhạy cảm nếu được sao chép vào ticket/log.
- Không mở remote jstatd ra mạng rộng nếu chưa có đánh giá bảo mật và kiểm soát truy cập.
- Không chạy công cụ dưới quyền cao hơn mức cần thiết.
- Không xóa hsperfdata hoặc thay đổi quyền thư mục tạm của hệ thống một cách tùy tiện.
- Không bật lại performance data hoặc thay JVM flag trên production nếu chưa có change plan.
- Không dùng jps như nguồn kiểm kê duy nhất cho toàn bộ hạ tầng; kết hợp service manager, container orchestrator và OS process inventory.
- Vì jps là công cụ experimental/unsupported và output có thể thay đổi, tránh dùng nó làm giao diện tự động hóa ổn định.

## 15. Tổng kết

Khi thiếu process trong jps, trước tiên hãy nhớ rằng công cụ chỉ liệt kê các instrumented HotSpot JVM mà tài khoản hiện tại có quyền truy cập. Output rỗng không đồng nghĩa ứng dụng chắc chắn đã dừng.

Các điểm cần kiểm tra:

- Đúng JDK và đúng jps trong PATH.
- Process có thực sự tồn tại theo OS process list hay không.
- User chạy jps có quyền truy cập JVM hay không.
- JVM có tắt performance data bằng -XX:-UsePerfData hay không.
- Ứng dụng có nằm trong Docker, WSL, VM hoặc host khác hay không.
- JVM có phải HotSpot và có dùng custom launcher không.
- Khi đã có PID, dùng jcmd <PID> VM.version và VM.command_line để xác minh.

Hãy xác định đúng host, user, namespace và PID trước khi thay đổi JVM configuration. Cách làm này giúp tìm nguyên nhân thực tế và tránh restart hoặc sửa cờ JVM không cần thiết.
