# Inspecting a module descriptor with javap

A module descriptor is metadata that describes a Java module: the module name, dependencies, exported or opened packages, used services, and provided service providers. In the Java Platform Module System (JPMS), the descriptor is written in source code as **module-info.java** and compiled into **module-info.class**.

The **javap** tool reads a class file and displays its internal structure. When inspecting a module descriptor, javap helps verify that directives such as `requires`, `exports`, `opens`, `uses`, and `provides` have been recorded accurately by the compiler.

A basic command:

~~~bash
javap -v path/to/module-info.class
~~~

The **-v** (verbose) option displays access flags, the constant pool, and detailed class file attributes, including the Module attribute that holds most of the module descriptor information.

## 1. What is a module descriptor?

A module is Java's unit of packaging and dependency management. It groups packages, declares which modules it depends on, and specifies which packages are accessible to other modules.

The descriptor is declared in a file named exactly module-info.java:

~~~java
module com.example.orders {
    requires java.logging;
    exports com.example.orders.api;
    opens com.example.orders.model;
}
~~~

Meaning:

- **module com.example.orders**: the module name.
- **requires java.logging**: the module depends on java.logging.
- **exports com.example.orders.api**: allows other modules to access public types in this package according to module rules.
- **opens com.example.orders.model**: allows deep reflection into the package according to JPMS rules.

Javac compiles module-info.java into module-info.class. This file is not a regular class with a main method; it is a special class file containing module metadata.

When inspecting a module descriptor, distinguish between:

- **module-info.java** is the source text written by the developer.
- **module-info.class** is the binary representation generated by the compiler.
- **Module attribute** is the attribute in the class file that contains the module name and directives.
- **javap** is the tool that reads class files, letting you view the compiled representation.

## 2. The special module-info.class file

The module descriptor is stored in a class file named module-info.class. This file follows the class file structure, but has its own rules:

- The internal class name is module-info.
- Class access_flags has the **ACC_MODULE** bit set.
- The class file contains a Module attribute.
- The file declares no fields or methods like a normal Java class.
- It may contain other attributes such as ModulePackages or ModuleMainClass depending on the module content and packaging.

**ACC_MODULE** has the value 0x8000 in ClassFile.access_flags. This flag identifies a module descriptor, not a modifier to add to a regular Java class.

When javap reads module-info.class, the beginning of the output typically has the following general form:

~~~text
Classfile .../module-info.class
  Compiled from "module-info.java"
  minor version: ...
  major version: ...
  flags: (0x8000) ACC_MODULE
  this_class: ... // module-info
  super_class: 0
  interfaces: 0, fields: 0, methods: 0
  ...
Module:
  ...
~~~

Constant pool indices, class file version, and attribute counts vary by JDK and module content. This is an example illustrating the structure, not a fixed output for line-by-line comparison.

## 3. Compiling a module to generate module-info.class

With a module source path, the root directory contains one subdirectory per module:

~~~text
project/
└── src/
    └── com.example.app/
        ├── module-info.java
        └── com/
            └── example/
                └── app/
                    └── Main.java
~~~

Example module-info.java:

~~~java
module com.example.app {
    requires java.logging;
    exports com.example.app.api;
}
~~~

From the project root directory, create the output directory and compile:

~~~bash
mkdir -p mods
javac --release 17 --module-source-path src -d mods -m com.example.app
~~~

Where:

- **--release 17** compiles against Java 17 APIs and language features.
- **--module-source-path src** specifies the root of the directory tree containing module sources.
- **-d mods** specifies the output directory.
- **-m com.example.app** instructs javac to compile the module named com.example.app.

After compilation, the output structure typically looks like:

~~~text
mods/
└── com.example.app/
    ├── module-info.class
    └── com/
        └── example/
            └── app/
                └── Main.class
~~~

The descriptor file sits directly under the module's root directory in the output directory. This is the path you can pass directly to javap.

## 4. Using javap -v to read the module descriptor

Direct command:

~~~bash
javap -v mods/com.example.app/module-info.class
~~~

Javap displays the class file and its attributes. The key section is named **Module:**. A condensed output snippet might look like this:

~~~text
Classfile .../module-info.class
  flags: (0x8000) ACC_MODULE
  ...
Module:
  #... ,0                                   // com.example.app
  #...                                       // requires
  #... ,0                                   // java.base mandated
  #...                                       // java.logging
  #...                                       // exports
  #...                                       // com.example.app.api
~~~

Constant pool numbers are replaced with ellipses because indices depend on the actual file. When running javap, read the module names and directives after the comments; do not rely on index numbers from another example.

You can use an absolute path if running from another directory:

~~~bash
javap -v C:/work/project/mods/com.example.app/module-info.class
~~~

On Windows, forward slashes are generally accepted by javap in paths. If a path contains spaces, enclose it in quotes according to shell rules.

### Why use -v?

If you only use:

~~~bash
javap module-info.class
~~~

the displayed information may not be sufficient to inspect internal attributes and flags. **-v** displays class file details, including the Module attribute, access flags, and related attributes.

The **-p** (private) option is useful when inspecting a class with private members. A module descriptor has no regular fields or methods to list, so -p is usually unnecessary when only inspecting module-info.class.

## 5. Meaning of directives in the Module attribute

The Module attribute stores information about the module and its directives. When javap displays the Module section, recognize the following groups:

| Directive | Meaning |
|---|---|
| requires | This module depends on another module |
| exports | Package is exposed to other modules |
| opens | Package is opened for deep reflection |
| uses | The module uses a service |
| provides | The module provides an implementation of a service |

### requires

~~~java
module com.example.app {
    requires java.logging;
}
~~~

The module requires the java.logging module. In a module descriptor, requires can be accompanied by modifiers:

- **transitive**: the dependent module re-exports this dependency to modules that depend on it.
- **static**: the dependency is needed at compile time but is not required to be present during runtime resolution in the same way as a regular requires.

Example:

~~~java
module com.example.api {
    requires transitive java.sql;
    requires static java.compiler;
}
~~~

In javap, the corresponding flags may appear as **ACC_TRANSITIVE** and **ACC_STATIC_PHASE** in the requires section of the Module attribute. These are module-specific flags; do not confuse them with method or class access_flags.

The java.base module is implicitly required by every normal module. Therefore, javap typically shows requires java.base with the mandated flag, even if module-info.java does not explicitly write this directive.

### exports

~~~java
module com.example.library {
    exports com.example.library.api;
    exports com.example.library.spi to com.example.plugin;
}
~~~

- Exports without a module list: the package is exported broadly.
- Exports with a module list: qualified export; only the listed modules can access the package under module rules.

Exports controls normal access to public types in the package. It does not turn package-private classes or members into public ones.

In javap, the exports section shows the package and may include a list of target modules if it is a qualified export.

### opens

~~~java
module com.example.model {
    opens com.example.model.entity;
    opens com.example.model.internal to com.example.orm;
}
~~~

Opens serves deep reflection, for example when a framework needs to access non-public fields or constructors. Opens is not the same as exports:

- Exports allows normal access to public types and public/protected members according to Java rules.
- Opens allows deep reflection within the scope of the opened module, commonly used for serialization, dependency injection, or ORM.

An entire module can be opened with:

~~~java
open module com.example.model {
}
~~~

An open module opens all packages of the module for deep reflection. In this case, individual opens directives are not declared inside the module descriptor.

### uses

~~~java
module com.example.app {
    uses com.example.spi.GreetingService;
}
~~~

The uses directive declares that the module will consume a service via ServiceLoader. It informs the module system which service type the module needs during resolution.

### provides

~~~java
module com.example.provider {
    provides com.example.spi.GreetingService
        with com.example.impl.DefaultGreetingService;
}
~~~

The provides directive declares a service implementation. The service name and provider are recorded in the Module attribute.

The provider module must satisfy ServiceLoader rules: the provider class must be instantiable via a supported mechanism, typically a public class with a public no-argument constructor or a suitable provider method.

## 6. Module-specific flags in the descriptor

In addition to ACC_MODULE in ClassFile.access_flags, the Module attribute has its own flags:

| Flag | Hex value | Location and meaning |
|---|---:|---|
| ACC_OPEN | 0x0020 | The module is an open module |
| ACC_SYNTHETIC | 0x1000 | The module was synthetically generated |
| ACC_MANDATED | 0x8000 | The module was included by rule or mandatory tooling |

In the requires section of the Module attribute, there are separate flags:

| Flag | Hex value | Meaning |
|---|---:|---|
| ACC_TRANSITIVE | 0x0020 | Dependency is required transitively |
| ACC_STATIC_PHASE | 0x0040 | Dependency is mandatory only at compile time |
| ACC_SYNTHETIC | 0x1000 | Directive was synthetically generated |
| ACC_MANDATED | 0x8000 | Directive was added by mandatory rule |

These bit values must be decoded according to the exact field. For example, 0x0020 in the Module attribute can be ACC_OPEN; in requires flags it is ACC_TRANSITIVE; in class access_flags it is ACC_SUPER; in method access_flags it is ACC_SYNCHRONIZED.

This is why a class file parser must know which structure it is reading before interpreting a bitmask.

## 7. Module-related attributes

The Module attribute is the main part, but module-info.class may contain additional attributes:

- **ModulePackages:** lists packages belonging to the module, including non-exported packages.
- **ModuleMainClass:** identifies the module's main class if the module is packaged with a main class.
- **ModuleTarget:** target platform metadata in certain artifacts.
- **ModuleHashes:** module hash metadata in certain packaging and module verification workflows.

Not every module descriptor has all of these attributes. They depend on how the module was compiled, packaged, and which tools created the artifact.

When javap displays ModulePackages: or ModuleMainClass:, those are separate attributes in the class file, not requires/exports/opens directives from module-info.java.

## 8. Viewing a module descriptor inside a JAR

When a module is packaged into a JAR, module-info.class usually resides at the root of the archive:

~~~text
com.example.app.jar
├── META-INF/
│   └── MANIFEST.MF
├── module-info.class
└── com/
    └── example/
        └── app/
            └── Main.class
~~~

Use jar to describe the module:

~~~bash
jar --describe-module --file build/com.example.app.jar
~~~

This command displays the module name, dependencies, and package/service metadata in a human-readable summary. It is useful for quickly checking module contents after packaging.

To inspect the detailed class file structure, extract module-info.class or run javap on the appropriate module/class. You can list the JAR contents:

~~~bash
jar --list --file build/com.example.app.jar
~~~

Then extract module-info.class into a temporary directory and run:

~~~bash
javap -v extracted/module-info.class
~~~

Do not confuse **jar --describe-module** with **javap -v**: jar outputs a module description, whereas javap decodes the class file and its attributes.

## 9. Using javap with the module path

In addition to pointing directly to module-info.class, javap can locate classes inside a module via the module path.

General syntax:

~~~bash
javap --module-path mods --module com.example.app com.example.app.Main
~~~

The command above asks javap to find class Main in module com.example.app on the module path mods.

To view the bytecode of a class in a module:

~~~bash
javap -c --module-path mods --module com.example.app com.example.app.Main
~~~

To view detailed class information:

~~~bash
javap -v --module-path mods --module com.example.app com.example.app.Main
~~~

These commands inspect class Main in the module. If your goal is the descriptor, specify the module-info.class file directly or use jar's describe-module command. Keeping these two goals separate avoids confusing class members with module directives.

## 10. Java 17+ hands-on example: three modules and ServiceLoader

The following example creates three modules:

- **com.example.greeter.api** exports the service interface.
- **com.example.greeter.provider** provides the implementation.
- **com.example.greeter.app** consumes the service via ServiceLoader.

Source structure:

~~~text
service-demo/
└── src/
    ├── com.example.greeter.api/
    │   ├── module-info.java
    │   └── com/example/greeter/GreetingService.java
    ├── com.example.greeter.provider/
    │   ├── module-info.java
    │   └── com/example/greeter/impl/DefaultGreetingService.java
    └── com.example.greeter.app/
        ├── module-info.java
        └── com/example/greeter/app/Main.java
~~~

### API module

File src/com.example.greeter.api/module-info.java:

~~~java
module com.example.greeter.api {
    exports com.example.greeter;
}
~~~

File src/com.example.greeter.api/com/example/greeter/GreetingService.java:

~~~java
package com.example.greeter;

public interface GreetingService {
    String greeting();
}
~~~

The module exports the package containing the interface so other modules can reference the service type.

### Provider module

File src/com.example.greeter.provider/module-info.java:

~~~java
module com.example.greeter.provider {
    requires com.example.greeter.api;

    provides com.example.greeter.GreetingService
        with com.example.greeter.impl.DefaultGreetingService;
}
~~~

File src/com.example.greeter.provider/com/example/greeter/impl/DefaultGreetingService.java:

~~~java
package com.example.greeter.impl;

import com.example.greeter.GreetingService;

public final class DefaultGreetingService
        implements GreetingService {

    public DefaultGreetingService() {
    }

    @Override
    public String greeting() {
        return "Hello from modular ServiceLoader.";
    }
}
~~~

The implementation package does not need to be exported just for ServiceLoader to use the provider declared with provides. The module descriptor supplies the provider information to the module system.

### Application module

File src/com.example.greeter.app/module-info.java:

~~~java
module com.example.greeter.app {
    requires com.example.greeter.api;
    uses com.example.greeter.GreetingService;
}
~~~

File src/com.example.greeter.app/com/example/greeter/app/Main.java:

~~~java
package com.example.greeter.app;

import com.example.greeter.GreetingService;
import java.util.ServiceLoader;

public class Main {
    public static void main(String[] args) {
        GreetingService service = ServiceLoader
                .load(GreetingService.class)
                .findFirst()
                .orElseThrow();

        System.out.println(service.greeting());
    }
}
~~~

The application module declares uses because it looks up GreetingService providers at runtime.

### Compiling the three modules

From the service-demo root directory:

~~~bash
mkdir -p mods
javac --release 17 \
    --module-source-path src \
    -d mods \
    -m com.example.greeter.api,com.example.greeter.provider,com.example.greeter.app
~~~

After compilation, the output looks like:

~~~text
mods/
├── com.example.greeter.api/
│   ├── module-info.class
│   └── com/example/greeter/GreetingService.class
├── com.example.greeter.provider/
│   ├── module-info.class
│   └── com/example/greeter/impl/DefaultGreetingService.class
└── com.example.greeter.app/
    ├── module-info.class
    └── com/example/greeter/app/Main.class
~~~

### Inspecting the descriptors

View the application module descriptor:

~~~bash
javap -v mods/com.example.greeter.app/module-info.class
~~~

The Module section should show:

- Module name com.example.greeter.app.
- Requires com.example.greeter.api.
- Uses com.example.greeter.GreetingService.
- Requires java.base may appear with the mandated flag.

View the provider descriptor:

~~~bash
javap -v mods/com.example.greeter.provider/module-info.class
~~~

The Module section should show:

- Module name com.example.greeter.provider.
- Requires com.example.greeter.api.
- Provides com.example.greeter.GreetingService.
- Provider com.example.greeter.impl.DefaultGreetingService.

Constant pool indices and line alignment depend on the JDK version; verify by the actual directive and class names.

### Running the application

~~~bash
java --module-path mods \
    -m com.example.greeter.app/com.example.greeter.app.Main
~~~

Output:

~~~text
Hello from modular ServiceLoader.
~~~

The provider module is discovered on the module path and linked during module resolution through service binding because the application module declares uses. The application does not need to directly require the provider module to use the service abstraction.

## 11. Common mistakes when inspecting descriptors

**module-info.class not found**

Check the output directory after compilation. With --module-source-path src and -d mods, the descriptor is usually under the module directory inside mods, not directly in mods.

**Javap reports class not found**

Pass the exact path to module-info.class in the command, or use --module-path and --module when inspecting a class in a module. Check the module name and output directory.

**Directive missing from the descriptor**

Check whether the right module-info.java was compiled, whether the build is using stale output, and whether javac compiled the right module. Clean the output before rebuilding if necessary.

**Confusing the Module attribute with ACC_MODULE**

ACC_MODULE is the class access flag that identifies module-info.class. The Module attribute is what contains requires, exports, opens, uses, and provides.

**Confusing exports with opens**

Exports is for normal access to public APIs. Opens is for deep reflection. A framework that needs reflection into private fields typically requires the package to be opened to the appropriate module.

**ServiceLoader provider not found**

Verify that the application module has uses, the provider module has provides, the provider module is on the module path, and the provider implementation meets ServiceLoader rules.

**Confusing requires transitive with regular requires**

Transitive makes a dependency part of the forwarded dependency contract. Use it only when the module's public API actually exposes types from that dependency and dependent modules need to read those types.

**Reading a class's class file instead of the descriptor**

javap -v Main.class displays metadata for class Main, not the module's Module attribute. To inspect the descriptor, target module-info.class.

**Relying on line ordering in the output**

Javap displays directive names and constant pool information; ordering, indices, and formatting may change. Read the directive semantics instead of comparing the output as a fixed string.

## 12. Module descriptor inspection workflow

1. Identify the module name and the location of module-info.java.
2. Compile the module using --module-source-path and -d.
3. Locate the exact path to module-info.class in the output.
4. Run javap -v on the descriptor.
5. Check ACC_MODULE and the Module attribute.
6. Cross-check requires, exports, opens, uses, and provides against the source.
7. Check module-specific flags such as transitive, static phase, and open.
8. Use jar --describe-module to inspect the module after packaging.
9. Use java --module-path to test module resolution and service binding.
10. If results are unexpected, inspect the actual artifact rather than just reading the source.

A module descriptor is the contract between a module and the rest of the application. javap helps confirm that this contract was written into the class file as intended. Combining javap -v, jar --describe-module, and a test run with the module path catches dependency, export, reflection, or service provider errors early in the build process.
