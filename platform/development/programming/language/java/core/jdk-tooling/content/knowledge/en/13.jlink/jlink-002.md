# Custom Runtime Image with jlink

A custom runtime image is a Java runtime tailored for an application or a group of applications, containing only the Java modules required to run them. Instead of requiring the target machine to install a full JDK, a development team can use the `jlink` tool to link the modules into a standalone runtime directory and distribute it together with the application.

This approach helps control the runtime version, reduce unnecessary components, and create a custom launcher for the application. However, the runtime image must be built with the right module graph, the right JDK version, and for the right target operating system/architecture. An image missing a module, resource, service provider, or native dependency may build successfully yet fail at runtime.

## 1. What is a custom runtime image?

The JDK is the Java development toolkit, typically including:

- The Java launcher and JVM for running applications.
- Platform modules such as `java.base`, `java.logging`, `java.sql`, and many others.
- The `javac` compiler, and packaging/inspection tools such as `jar`, `jmod`, `javap`, and `jdeps`.
- Development and documentation tools such as `javadoc`, `jshell`, and other utilities.

A runtime image created by `jlink` contains only the modules and runtime components linked for the selected set of applications. It can include the `java` launcher, runtime libraries, configuration files, legal notices, and required resources. Typically, it does not include full development tools such as `javac` or `javadoc`.

A runtime image is not just a JAR file or a directory containing only `java.exe`. It is a complete runtime structure generated by the JDK that can be executed directly on a compatible platform without needing a separate full JDK installed on the target machine.

Custom runtime images are commonly used when:

- Distributing desktop or command-line applications bundled with their own runtime.
- Deploying Java services on servers or in containers.
- Building a runtime with a small, well-controlled set of modules.
- Keeping the application's runtime consistent across environments.
- Reducing the deployed component footprint and removing unnecessary tools on the machine running the application.

## 2. How does jlink work?

`jlink` reads modules from the module path, resolves the module graph starting from the specified root modules, and links the required modules into the output image.

A basic workflow:

1. Compile the application into a named module or prepare a modular JAR.
2. Place the application module and the required JDK modules on the module path.
3. Use `--add-modules` to select the root modules.
4. `jlink` resolves `requires` declarations and adds the necessary dependent modules.
5. Selected plugins can strip debug metadata, header files, or man pages, or compress resources.
6. `jlink` creates the runtime image in the `--output` directory.

Model:

~~~text
Application source
       |
       v
     javac
       |
       v
Application module
       |
       +------------------+
       |                  |
       v                  v
Application module    JDK jmods
       |                  |
       +--------+---------+
                |
                v
              jlink
                |
                v
        Custom runtime image
                |
                v
        Application launcher
~~~

`jlink` does not compile Java source code in place of `javac`, nor does it automatically convert a classpath-based program into a named module. The tool links modules that have already been compiled or packaged.

## 3. Prerequisites

To create a custom runtime image, prepare:

- A JDK that includes the `jlink` tool.
- An application module with an explicit module descriptor, typically `module-info.class`.
- Dependent modules accessible on the module path.
- Main class configuration if you want to create a custom launcher.
- A new or empty output directory to receive the runtime image.

An application that only runs on the classpath without a module descriptor must be converted into a proper named module before entering the `jlink` workflow. Automatic modules can be used in certain module-path scenarios, but they are not suitable inputs for `jlink` to link into a runtime image. Verify the module descriptor and dependencies before creating the image.

Check the tools:

~~~bash
java -version
javac -version
jlink --version
~~~

You should use `javac` and `jlink` from the same JDK distribution to avoid mismatches between module metadata, the compiler, and the linker. The JDK's `jmods` directory contains the platform modules in JMOD format; this is typically part of the module path during linking.

## 4. Practical example: creating a modular application

This example creates a small application with the module name `com.acme.hello`. The application uses `java.logging` to demonstrate a module dependency and prints a greeting.

Source directory structure:

~~~text
jlink-demo/
└── src/
    ├── module-info.java
    └── com/
        └── acme/
            └── hello/
                └── Main.java
~~~

File `src/module-info.java`:

~~~java
module com.acme.hello {
    requires java.logging;
}
~~~

File `src/com/acme/hello/Main.java`:

~~~java
package com.acme.hello;

import java.util.logging.Logger;

public class Main {
    private static final Logger LOGGER = Logger.getLogger(Main.class.getName());

    public static void main(String[] args) {
        String name = args.length == 0 ? "Java" : args[0];
        LOGGER.fine("Greeting requested");
        System.out.println("Hello, " + name + "!");
    }
}
~~~

`LOGGER.fine` writes a log entry at the FINE level. With the default logging configuration, this level is not printed to the console, so stdout for the example only contains the greeting line.

## 5. Compiling the module

Run the commands from the `jlink-demo` root directory.

On Linux or macOS:

~~~bash
javac -d mods/com.acme.hello src/module-info.java src/com/acme/hello/Main.java
~~~

On Windows PowerShell:

~~~powershell
javac -d mods/com.acme.hello src/module-info.java src/com/acme/hello/Main.java
~~~

After compilation, the output module structure is:

~~~text
mods/
└── com.acme.hello/
    ├── module-info.class
    └── com/
        └── acme/
            └── hello/
                └── Main.class
~~~

The `mods` directory is the module path root. The `com.acme.hello` subdirectory is the module directory containing the module descriptor and the module's classes.

You can inspect the module descriptor:

~~~bash
java --describe-module com.acme.hello --module-path mods
~~~

This command tells the Java launcher to read the module from the module path and describe its declarations. The output shows that the `com.acme.hello` module requires `java.logging`.

## 6. Analyzing dependencies with jdeps

Before linking the image, you can use `jdeps` to analyze the application's static module dependencies:

~~~bash
jdeps --module-path mods --print-module-deps --module com.acme.hello
~~~

For the example above, the module dependency list may look like:

~~~text
java.base,java.logging
~~~

`java.base` is the core platform module that every Java module implicitly reads. `java.logging` is explicitly required in `module-info.java`.

The `--print-module-deps` option prints a reduced list of dependent modules, which can be used as input for `jlink --add-modules`. Static analysis results do not necessarily detect every dependency loaded dynamically via reflection, class names in configuration, service providers, or native code. Review dynamic loading paths and test the actual application.

If the application uses `ServiceLoader`, check the `uses` and `provides` declarations in the module descriptor as well as the provider modules needed in the image.

## 7. Creating a custom runtime image with jlink

`jlink` needs to locate both the application modules and the JDK modules. Therefore, the module path typically includes the JDK's `jmods` directory and the `mods` directory containing the application modules.

### Linux and macOS

The path separator for module path entries is a colon:

~~~bash
jlink \
  --module-path "$JAVA_HOME/jmods:mods" \
  --add-modules com.acme.hello \
  --launcher hello=com.acme.hello/com.acme.hello.Main \
  --strip-debug \
  --no-header-files \
  --no-man-pages \
  --output image
~~~

### Windows PowerShell

The path separator for module path entries is a semicolon:

~~~powershell
jlink --module-path "$env:JAVA_HOME\jmods;mods" --add-modules com.acme.hello --launcher hello=com.acme.hello/com.acme.hello.Main --strip-debug --no-header-files --no-man-pages --output image
~~~

Option breakdown:

| Option | Purpose |
|---|---|
| `--module-path` | Where to find JMODs and application modules. |
| `--add-modules` | Selects the root modules to link; dependencies are resolved according to the module graph. |
| `--launcher` | Creates a custom launcher named `hello` to run the specified module and main class. |
| `--strip-debug` | Strips debug information from the linked classes. |
| `--no-header-files` | Excludes development header files from the image. |
| `--no-man-pages` | Excludes man pages from the image. |
| `--output` | The output runtime image directory. |

The launcher name follows the syntax `name=module/mainclass`. In the example, `hello` is the command name, `com.acme.hello` is the module, and `com.acme.hello.Main` is the main class.

The `image` directory should not exist yet or should be empty. If an old image is already there, choose a new output path or clean the project-managed build directory before re-running `jlink`.

The options for stripping debug info, header files, and man pages make the image smaller. If you need line numbers for production troubleshooting or headers for native integration, consider keeping the corresponding components.

## 8. Running the application from the runtime image

After `jlink` finishes, the runtime image has the default `java` launcher and the custom `hello` launcher.

On Linux/macOS:

~~~bash
./image/bin/hello Ada
~~~

On Windows PowerShell:

~~~powershell
.\image\bin\hello Ada
~~~

Exact output:

~~~text
Hello, Ada!
~~~

You can run the application using the image's default Java launcher without the custom launcher:

~~~bash
./image/bin/java -m com.acme.hello/com.acme.hello.Main Ada
~~~

On Windows:

~~~powershell
.\image\bin\java.exe -m com.acme.hello/com.acme.hello.Main Ada
~~~

Output:

~~~text
Hello, Ada!
~~~

A custom launcher lets users run the application by its own command name without having to remember the module/main-class syntax. It still uses the linked runtime image and the modules selected when creating the image.

If the application takes arguments, pass them after the launcher name just like invoking any regular command-line program.

## 9. Runtime image structure

The exact structure depends on the operating system and JDK version. An image typically looks like this:

~~~text
image/
├── bin/
│   ├── java
│   └── hello
├── conf/
├── legal/
├── lib/
│   ├── modules
│   └── ...
└── release
~~~

On Windows, the `bin` directory contains executables such as `java.exe` and the custom launcher; there may also be supporting batch files for the launcher. File names and native libraries in the image vary by platform.

Main components:

- `bin`: The Java launcher, custom launchers, and required executables.
- `conf`: Runtime configuration files.
- `legal`: License information and legal notices for the linked modules.
- `lib`: Runtime libraries, the module image, configuration files, and required native libraries.
- `release`: Metadata about the runtime distribution.

The image is a directory tree that can be packaged into an archive or included in an installer according to the product's release process. Do not copy only `bin/java` to the target machine, as the JVM also needs the libraries and data in the other directories.

## 10. Inspecting modules included in the image

Use the Java launcher inside the image to list the linked modules:

~~~bash
./image/bin/java --list-modules
~~~

On Windows:

~~~powershell
.\image\bin\java.exe --list-modules
~~~

For the example, the list may include:

~~~text
com.acme.hello
java.base@24.0.2
java.logging@24.0.2
~~~

The version suffix after `@` depends on the JDK used to build the image. The list above illustrates output from JDK 24.0.2; when using a different JDK, the displayed version will differ.

You can describe a specific module:

~~~bash
./image/bin/java --describe-module java.logging
~~~

If the image is missing a module that the application needs, check the module descriptor, dependencies, and the `--add-modules` option. Do not arbitrarily add all modules just to make an error disappear; determine which modules are actually required.

## 11. Selecting root modules and managing the module graph

`--add-modules` accepts one or more module names, separated by commas:

~~~bash
jlink --module-path "$JAVA_HOME/jmods:mods" --add-modules com.acme.hello,java.sql --output image
~~~

The selected modules are the root modules. `jlink` then resolves modules required via `requires` and includes the necessary dependencies in the image.

Key points to understand:

- `java.base` is always present in a Java runtime.
- `requires` declarations create explicit module dependencies.
- Transitive dependencies can expand the module graph.
- `requires static` only requires a module at compile time and does not automatically force that module to be present at runtime.
- Modules loaded dynamically via reflection or configuration may not appear in static dependency analysis.

You can use `ALL-MODULE-PATH` to select all modules on the module path, but this usually produces a larger image and does not clearly express the minimal set of dependencies. Only use it when the goal is genuinely to include all modules on the module path in resolution.

The `--limit-modules` option restricts the set of observable modules during resolution. It is useful for tightly controlled runtimes, but if set too narrowly, linking may fail with missing modules. Only use it after thoroughly understanding the dependency graph.

## 12. Service binding and ServiceLoader

An application can use a Service Provider Interface (SPI) to discover implementations at runtime. The consumer module declares `uses`, while the provider module declares `provides ... with ...`.

Example application module:

~~~java
module com.acme.app {
    uses com.acme.spi.GreetingProvider;
}
~~~

Provider module:

~~~java
module com.acme.greeting.english {
    requires com.acme.spi;
    provides com.acme.spi.GreetingProvider
        with com.acme.greeting.english.EnglishGreetingProvider;
}
~~~

When linking the runtime, if you need to automatically include provider modules and their dependencies in the image, you can use:

~~~bash
jlink --module-path "$JAVA_HOME/jmods:mods" --add-modules com.acme.app --bind-services --output image
~~~

`--bind-services` instructs jlink to link modules that provide services used by the selected modules, along with their required dependencies. This option can make the image larger because provider modules are also included.

If the application does not use SPI or you have already explicitly selected the provider modules, enabling service binding is unnecessary. When unsure which module provides a service, you can run `jlink --suggest-providers` with the service type name to see suggestions from the module path.

## 13. Customizing image size and contents

One of the reasons for using jlink is to reduce components unnecessary for the application. Common plugins include:

| Option | Effect |
|---|---|
| `--strip-debug` | Removes debug metadata. |
| `--no-header-files` | Excludes header files used for native development. |
| `--no-man-pages` | Excludes command manual pages. |
| `--compress` | Compresses resources in the image according to the level supported by the JDK version. |
| `--bind-services` | Adds service provider modules and their dependencies. |

The compression option varies by JDK version. Some older releases use numeric values like `--compress=2`; newer releases may support forms such as `--compress=zip-6`. Check `jlink --list-plugins` and `jlink --help` on the exact JDK used for the build before putting a compression option into a shared script.

View the list of plugins:

~~~bash
jlink --list-plugins
~~~

Do not optimize solely for size. Stripping debug metadata can make troubleshooting errors harder; excluding header files may be unsuitable if the product also ships a native SDK. Determine what runtime and operational contents are actually needed before enabling plugins.

## 14. Applications using resources, reflection, or native libraries

An application module may contain resources such as properties files, templates, certificates, or data needed at runtime. When compiling and packaging the module, ensure resources are placed properly in the module tree or modular JAR so they are linked into the image.

Some dependencies cannot be inferred completely from bytecode:

- Class names constructed from configuration strings and loaded via reflection.
- Service providers discovered through ServiceLoader.
- Drivers or plugins registered outside the static module graph.
- Native libraries loaded via `System.loadLibrary` or `System.load`.
- Configuration or data files located outside the module.

For reflection, the module must be included in the image if the application might load it at runtime, and appropriate module access permissions must be configured. For SPI, consider `--bind-services` or adding the provider module explicitly. For native libraries, ensure the binaries and native dependencies are distributed, discoverable, and compatible with the runtime image.

`jlink` links Java modules; it does not compile C/C++, does not guarantee that external native dependencies are installed on the target machine, and does not replace a native library packaging workflow.

## 15. Differences between classpath and module path

`jlink` works with the module graph, so the module path is a critical part of the configuration.

| Concept | Purpose |
|---|---|
| Classpath | Locates classes and JARs using the traditional class-loader mechanism. |
| Module path | Locates named modules, modular JARs, and JMODs to resolve the module graph. |
| JDK jmods | The JDK's platform modules in JMOD format. |
| Application module directory | A directory containing `module-info.class` and the application module's classes. |
| Runtime image | The linked output for running the application on a compatible platform. |

An application that runs with `java -cp` cannot necessarily be fed directly into `jlink`. It needs a module descriptor and dependencies compatible with the module system.

For legacy applications that depend on many classpath libraries, you may need to design module descriptors, check for split packages, identify dependencies, and test running on the module path before linking the runtime.

## 16. Platform and JDK version compatibility

Runtime images are platform-specific. An image built on Windows x64 cannot be used as-is as a Linux x64 or macOS ARM64 runtime. Native libraries, executables, and binary formats depend on the operating system and architecture.

The build pipeline should produce a separate image for each target:

| Target | Runtime image to build |
|---|---|
| Windows x64 | An image built from a JDK and native dependencies compatible with Windows x64. |
| Linux x64 | An image compatible with Linux x64 and the supported native ABI. |
| Linux ARM64 | An image compatible with Linux AArch64. |
| macOS ARM64 | An image compatible with macOS on Apple Silicon. |

You also need to control the JDK version. JDK JMOD modules are tied to the distribution version; use the appropriate JDK to compile, link, and test the image. If you want to support multiple Java versions, build and test images for each target version rather than assuming a single image works across all runtimes.

## 17. Incorporating a custom runtime image into distribution

`jlink` produces an image directory, not a complete installer. A distribution workflow typically includes:

1. Building a runtime image for each operating system/architecture.
2. Placing configuration files, external data, and deployment resources where the application expects them.
3. Checking executable permissions on launchers on Unix-like systems.
4. Packaging the image directory along with documentation and required components.
5. Testing on a clean environment without a full JDK installed.
6. Reviewing licenses/legal notices of the distributed modules.
7. Signing or verifying artifacts according to release policy.
8. Testing updates, rollbacks, and logging/diagnostics configuration.

Do not assume the target machine has the same system libraries as the build machine. If the application requires native libraries or external tools, include them in the installation package or clearly document the environment dependencies.

## 18. Common errors and troubleshooting

| Symptom | Common cause | Resolution |
|---|---|---|
| `Error: Module ... not found` | Module path is missing JMODs or the application module. | Check `--module-path`, module names, and the location of module directories/JARs/JMODs. |
| `jlink` rejects a classpath application | The application lacks an explicit module descriptor. | Convert the application into a named module and declare dependencies. |
| `FindException` or module resolution error | A required module is missing, dependency versions mismatch, or the module path is wrong. | Check `module-info.java`, `jdeps`, and the module path. |
| Launcher runs but reports missing class | A module or dependency was not included in the image, or a resource/dynamic dependency was missed. | Identify the missing module, check reflection/services, and run integration tests. |
| `ServiceLoader` cannot find a provider | The provider module was not linked or the descriptor lacks `provides`. | Add the provider module or use `--bind-services` as appropriate. |
| Image is larger than expected | Too many root modules selected, `ALL-MODULE-PATH` enabled, or unnecessary service providers linked. | Analyze dependencies and select only the necessary root modules. |
| Output directory cannot be used | The output directory already exists and is non-empty. | Choose a new directory or clean the designated build directory. |
| Image runs on build machine but fails on target | Different OS/CPU, missing native library, or missing shared library dependency. | Build a target-specific image and test in a matching environment. |
| Image lacks an expected tool | Only required runtime modules are linked; development tools are not included. | Determine whether the tool can be packaged separately or whether the corresponding JDK module can be linked. |
| Custom launcher not found | Incorrect launcher name or module/main-class syntax, or looking in the wrong output directory. | Check `--launcher` and the file listing in `image/bin`. |

To diagnose module resolution, you can run jlink with `--verbose` to inspect linking details:

~~~bash
jlink --verbose --module-path "$JAVA_HOME/jmods:mods" --add-modules com.acme.hello --output image
~~~

Inspect the list of modules in the image with `java --list-modules` and test running the application from the runtime image itself. A successful build does not replace runtime testing.

## 19. Recommended build and test workflow

A reproducible workflow should perform the following steps:

1. Select the JDK and target platform.
2. Compile the application into a named module.
3. Verify the module descriptor and dependencies.
4. Use `jdeps --print-module-deps` to assist with static dependency analysis.
5. Review reflection, ServiceLoader, resources, JNI, and dependencies outside the module graph.
6. Use `jlink --module-path` and `--add-modules` to create the image.
7. Add `--launcher` if you want to provide a custom command.
8. Enable only optimization plugins that fit operational needs.
9. List modules using the runtime image and verify the launcher.
10. Run unit/integration tests against the final image.
11. Test on a clean machine and on each target operating system/architecture.
12. Record the JDK version, module list, jlink command, and artifact metadata to reproduce the image.

If you want to compare two builds, keep the JDK, dependencies, compiler options, module list, and plugins stable. Changing any of those factors can alter the size or contents of the image.

## 20. Pre-release checklist

- The application is a named module with a valid module descriptor.
- All dependent modules are found on the module path.
- Root modules in `--add-modules` accurately reflect the application.
- Service providers and their dependencies are included when needed.
- Resources, reflection, and native libraries have been verified.
- The runtime image is built with a JDK matching the target.
- Both the default launcher and custom launcher execute properly.
- `java --list-modules` shows the expected set of modules.
- Integration tests run on the runtime image, not only on the development JDK.
- The image is tested on a clean environment matching the target OS/CPU.
- Legal notices and distribution requirements are preserved.
- Build scripts record the JDK version, module path, module roots, and jlink options.

A custom runtime image helps distribute Java applications together with a runtime that has a controlled set of modules. `jlink` resolves the module graph from root modules, links the runtime, and creates launchers in the image. To keep the image small while ensuring it works correctly, analyze dependencies, account for services/reflection/native code, test the final image on the right platform, and maintain a reproducible build process.
