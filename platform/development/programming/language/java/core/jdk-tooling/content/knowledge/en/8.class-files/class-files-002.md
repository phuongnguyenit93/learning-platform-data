# Class file structure

A **class file** is the standard binary format generated by the Java compiler so that the JVM can load, verify, and execute a class. The file typically has the `.class` extension, though the format itself is not machine code for a specific processor. It contains bytecode, type information, a constant pool, and metadata describing the class, fields, methods, and related attributes.

The class file structure is defined in the *Java Virtual Machine Specification (JVMS)*. Thanks to having a unified format, bytecode compiled on one operating system can run on another operating system when the target JVM supports the corresponding class file version and the APIs/dependencies required by the program.

## 1. Overview of a class file

A class file has a fixed order of components:

```text
ClassFile
├── magic
├── minor_version
├── major_version
├── constant_pool
├── access_flags
├── this_class
├── super_class
├── interfaces
├── fields
├── methods
└── attributes
```

Meaning of each component:

| Component | Role |
|---|---|
| `magic` | Identifies the file as a valid class file format |
| `minor_version`, `major_version` | Specifies the class file format version |
| `constant_pool` | Contains class names, field/method names, strings, data types, and constant references |
| `access_flags` | Flags describing the class kind and access permissions |
| `this_class` | Index in the constant pool identifying the class being described |
| `super_class` | Index identifying the direct superclass |
| `interfaces` | List of interfaces implemented by the class |
| `fields` | List of declared fields |
| `methods` | List of methods and constructors |
| `attributes` | Extended metadata at the class, field, method, or bytecode level |

Integer fields in the class file format are stored in big-endian byte order. Some basic data types in the specification:

- `u1`: 1-byte unsigned integer.
- `u2`: 2-byte unsigned integer.
- `u4`: 4-byte unsigned integer.

More complex items are built from these fields. For example, `attribute_length` is a `u4`, indicating the number of bytes in the attribute's data section.

## 2. Magic number and version

The first four bytes of a class file are the magic number:

```text
0xCAFEBABE
```

The magic number helps the JVM and analysis tools recognize whether the data is a class file. If the file is corrupted, truncated, or not a class file, the JVM may report a format error such as `ClassFormatError`.

Immediately following the magic number are:

- `minor_version`: the minor version.
- `major_version`: the major version of the class file format.

Some common major versions:

| Java platform | Class file major version |
|---:|---:|
| Java 8 | 52 |
| Java 11 | 55 |
| Java 17 | 61 |
| Java 21 | 65 |

For example, a class file with major version 61 corresponds to Java 17. A Java 17 JVM cannot load a class file that requires a higher major version than that JVM supports.

Since Java 12, class files use the special minor version 65535 to mark bytecode that depends on preview features of that specific Java version. To run this kind of class file, the runtime needs `--enable-preview` enabled and must match that exact release. Minor version 65535 should not be treated as a regular Java version.

## 3. Constant pool

`constant_pool` is the central constant table of a class file. Many other parts of the file do not store class names or method names repeatedly; instead, they store an index pointing to the appropriate entry in the constant pool.

For example, the class description may reference a `CONSTANT_Class_info` entry, which in turn points to a `CONSTANT_Utf8_info` entry containing the class name. Method names and descriptors are organized using the same referencing mechanism.

### 3.1. Table structure

A class file has a `constant_pool_count` field indicating the number of slots in the table, including the unused slot 0. Valid entries are typically indexed starting from 1.

Each entry begins with a `tag` byte identifying the entry type, followed by data specific to that type. Some common tags:

| Tag | Entry type | General content |
|---:|---|---|
| 1 | `CONSTANT_Utf8` | String in Modified UTF-8 format |
| 3 | `CONSTANT_Integer` | 32-bit integer constant |
| 4 | `CONSTANT_Float` | 32-bit floating-point constant |
| 5 | `CONSTANT_Long` | 64-bit integer constant |
| 6 | `CONSTANT_Double` | 64-bit floating-point constant |
| 7 | `CONSTANT_Class` | Class or interface name reference |
| 8 | `CONSTANT_String` | String reference |
| 9 | `CONSTANT_Fieldref` | Field reference |
| 10 | `CONSTANT_Methodref` | Class method reference |
| 11 | `CONSTANT_InterfaceMethodref` | Interface method reference |
| 12 | `CONSTANT_NameAndType` | Name and descriptor pair |
| 15 | `CONSTANT_MethodHandle` | Method handle reference |
| 16 | `CONSTANT_MethodType` | Method type descriptor |
| 17 | `CONSTANT_Dynamic` | Dynamic constant |
| 18 | `CONSTANT_InvokeDynamic` | Dynamic call site reference |
| 19 | `CONSTANT_Module` | Module name |
| 20 | `CONSTANT_Package` | Package name |

Valid tags depend on the class file version. Not every older JDK understands constant pool types added in newer releases.

### 3.2. Reference relationships

For example, a `CONSTANT_Methodref` entry does not store the entire class name, method name, and parameter types as a single string. It references:

1. `class_index`: a `CONSTANT_Class` entry indicating the class that owns the method.
2. `name_and_type_index`: a `CONSTANT_NameAndType` entry describing the method's name and descriptor.

This organization allows multiple components to share strings and type information. When reading `javap -verbose`, you will see constant pool entries along with their indices.

`CONSTANT_Long` and `CONSTANT_Double` occupy two index slots in the constant pool; the slot immediately following them cannot be used as an independent entry. This is an error-prone detail when writing a custom class file parser.

Strings in `CONSTANT_Utf8` entries use **Modified UTF-8** per the class file specification, which is not identical to standard UTF-8. When using a class file parsing library, let the library handle this encoding rather than decoding bytes manually with a naive assumption.

## 4. Access flags, this_class, and super_class

Following the constant pool are the fields describing the class:

- `access_flags`: flags such as public, final, interface, abstract, enum, annotation, or module.
- `this_class`: `CONSTANT_Class` index identifying the name of the class being described.
- `super_class`: `CONSTANT_Class` index of the direct superclass.

Some common flags:

| Flag | Meaning |
|---|---|
| `ACC_PUBLIC` | The class has public access |
| `ACC_FINAL` | The class cannot be subclassed |
| `ACC_SUPER` | Enables modern JVM semantics for superclass method invocation |
| `ACC_INTERFACE` | This is an interface |
| `ACC_ABSTRACT` | Abstract class or interface |
| `ACC_ANNOTATION` | This is an annotation type |
| `ACC_ENUM` | This is an enum type |
| `ACC_MODULE` | The class file describes a module |

Allowed flags and their interpretation also depend on the structure type. The same bit can have different meanings in a class, field, or method context.

For `java.lang.Object`, the `super_class` field is 0 because it is the root class with no superclass. For a regular class, this index references its direct superclass. `this_class` and `super_class` do not store text names directly; they point to the constant pool.

## 5. Interfaces, fields, and methods

### 5.1. Interfaces

`interfaces_count` specifies the number of interfaces the class implements. Next is the `interfaces` array, where each element is a `CONSTANT_Class` index.

Example:

```java
public class ReportService implements Runnable, AutoCloseable {
    @Override
    public void run() {
    }

    @Override
    public void close() {
    }
}
```

The class file of `ReportService` contains references to `Runnable` and `AutoCloseable` in the interfaces table. The methods implementing the interfaces are described in the methods table.

### 5.2. Fields

`fields_count` specifies the number of fields declared in the class. Each `field_info` describes:

- Access flags such as public, private, protected, static, final, volatile, or transient.
- `name_index`: the field name in the constant pool.
- `descriptor_index`: the descriptor representing the field type.
- Additional attributes, such as `ConstantValue`, `Signature`, or annotations.

Example:

```java
public class Account {
    private long id;
    public static final int MAX_RETRY = 3;
}
```

The `id` field has descriptor `J` (long); `MAX_RETRY` has descriptor `I` (int). Eligible constants may be represented using a `ConstantValue` attribute.

### 5.3. Methods

`methods_count` specifies the number of methods and constructors described. Each `method_info` has:

- Access flags such as public, private, static, final, abstract, synchronized, or native.
- `name_index`: the method name; constructors use the special name `<init>`, and class initializers use `<clinit>`.
- `descriptor_index`: the descriptor describing parameters and return type.
- A list of attributes, usually including `Code` for methods with a bytecode body.

Example:

```java
public int add(int left, int right) {
    return left + right;
}
```

The method descriptor is:

```text
(II)I
```

The two `I` characters inside the parentheses are the two `int` parameters; the `I` after the parentheses is the `int` return type.

Some basic descriptors:

| Java type | Descriptor |
|---|---|
| `boolean` | `Z` |
| `byte` | `B` |
| `char` | `C` |
| `short` | `S` |
| `int` | `I` |
| `long` | `J` |
| `float` | `F` |
| `double` | `D` |
| `void` | `V` |
| `String` | `Ljava/lang/String;` |
| `int[]` | `[I` |
| `String[]` | `[Ljava/lang/String;` |

Descriptors are an important part of method linking. Two methods with the same name but different parameters will have different descriptors. Generic types generally do not appear in JVM descriptors after type erasure; generic information may be preserved separately in the `Signature` attribute.

## 6. Attributes: the extensible part of a class file

After fields and methods come `attributes_count` and the list of class-level attributes. Each attribute has a general structure:

```text
attribute_info {
    u2 attribute_name_index;
    u4 attribute_length;
    u1 info[attribute_length];
}
```

- `attribute_name_index` points to a `CONSTANT_Utf8` entry containing the attribute name.
- `attribute_length` is the length of the data payload.
- `info` holds data specific to the attribute type.

Attributes can appear at multiple levels: class, field, method, and inside the `Code` attribute. Some important attributes:

| Attribute | Purpose |
|---|---|
| `SourceFile` | Records the original source file name |
| `SourceDebugExtension` | Extended debugging information |
| `InnerClasses` | Describes nested class relationships |
| `EnclosingMethod` | Describes which method or initializer contains a local/anonymous class |
| `NestHost`, `NestMembers` | Represents nestmate relationships |
| `Signature` | Stores generic signatures |
| `ConstantValue` | Constant value of an eligible field |
| `Exceptions` | List of exceptions declared in `throws` |
| `RuntimeVisibleAnnotations` | Annotations that must be retained for runtime inspection |
| `RuntimeInvisibleAnnotations` | Annotations not required to be visible at runtime |
| `BootstrapMethods` | Bootstrap information for dynamic call sites and dynamic constants |
| `Record` | Metadata for record classes |
| `PermittedSubclasses` | List of permitted subclasses for a sealed class |
| `Module` | Module declaration metadata in `module-info.class` |

Attributes allow the class file format to evolve over time without changing its fundamental layout. The JVM ignores optional attributes it does not need to process; attributes with mandatory semantics according to the specification must be handled properly.

Not all comments in source code appear in the class file. Regular comments are stripped during compilation. Source, line number, local variable, or annotation information exists only when the compiler generates the corresponding attributes and according to their retention/configuration.

## 7. Code attribute and method bytecode

Methods with an executable body usually contain a `Code` attribute. This is where the method's bytecode is stored.

Simplified structure:

```text
Code_attribute
├── max_stack
├── max_locals
├── code_length
├── code[]
├── exception_table
└── attributes
```

Key fields:

- `max_stack`: maximum depth of the operand stack required by the method.
- `max_locals`: number of slots needed for local variables and parameters.
- `code_length`: number of bytes in the bytecode array.
- `code[]`: sequence of JVM instructions.
- `exception_table`: exception catch ranges and handler locations.
- `attributes`: metadata for the code section, such as line numbers, local variables, and stack maps.

The JVM is a stack-based machine. Many instructions read operands from the operand stack, perform an operation, and push the result back onto the stack. Other instructions manipulate local variable slots, create objects, invoke methods, access fields, or control execution flow.

Source code example:

```java
public class MathBox {
    public static int add(int a, int b) {
        return a + b;
    }
}
```

Compile and inspect bytecode:

```sh
javac MathBox.java
javap -c MathBox
```

The exact bytecode output depends on the JDK and compilation details, but the body typically contains instructions to load two local variables onto the operand stack, add the integers, and return the result. You should not assume that bytecode from every compiler version is identical down to every index or instruction order.

Some attributes commonly found inside `Code`:

- `LineNumberTable`: maps bytecode offsets to source line numbers so debuggers can display approximate locations.
- `LocalVariableTable`: names and scopes of local variables if generated by the compiler.
- `LocalVariableTypeTable`: generic type information for local variables when present.
- `StackMapTable`: frames used for type checking and control-flow verification.

Abstract and native methods do not have a regular bytecode body, so they do not have a `Code` attribute like concrete methods. For abstract methods, behavior is implemented by subclasses; for native methods, execution resides outside Java bytecode, typically via JNI or another native mechanism.

## 8. Bytecode verification and class loading

When the JVM loads a class, the class file is processed through the loading, linking, and initialization steps. At a high level:

1. **Loading:** locates the class file from the classpath, module path, or another class loader and creates the class representation in the JVM.
2. **Verification:** checks whether the class file is valid and whether the bytecode complies with the JVM's type-safety rules.
3. **Preparation:** allocates memory for static variables and assigns default values according to JVM rules.
4. **Resolution:** converts symbolic references in the constant pool into direct references when needed.
5. **Initialization:** executes class initialization, including the class initializer `<clinit>` when present.

Verification checks many conditions such as instruction structure, data types on the operand stack, validity of control-flow branches, and relationships between frames. `StackMapTable` supports this process in modern class file versions.

Successful class file generation by `javac` is one layer of checking; the JVM still performs checks during loading and linking. A corrupted or hand-crafted class file that violates the specification can cause `ClassFormatError`, `VerifyError`, or other linkage errors.

Arbitrarily modified bytecode should not be used as a substitute for source code and a controlled build process.

## 9. Practical example: inspecting class file structure

Create `Sample.java`:

```java
public class Sample {
    private final String name;

    public Sample(String name) {
        this.name = name;
    }

    public String greeting() {
        return "Hello, " + name;
    }

    public static void main(String[] args) {
        System.out.println(new Sample("JVM").greeting());
    }
}
```

Compile:

```sh
javac -g -parameters Sample.java
```

Run the program:

```sh
java Sample
```

Output:

```text
Hello, JVM
```

Inspect members:

```sh
javap -p Sample
```

Inspect bytecode:

```sh
javap -c -p Sample
```

Inspect full details:

```sh
javap -verbose -p Sample
```

In the verbose output, look for these sections:

- `Classfile`: file path and file metadata.
- `minor version` and `major version`: class file version.
- `Constant pool`: constants and references.
- `flags`: class access flags.
- `this_class`, `super_class`: current class and superclass.
- `fields`: the `name` field.
- `methods`: constructor, `greeting`, and `main`.
- `Code`: bytecode, max stack, max locals, and exception table.
- `LineNumberTable`, `LocalVariableTable`: debug information if generated.

Specific offsets, constant pool indices, and exact bytecode instructions are not a stable interface to rely on across compiler versions. Focus on structural relationships and meaning rather than memorizing fixed indices.

## 10. Special class files and modern language features

Class files do not only describe regular Java classes.

**Interface:** marked with the appropriate access flag and may contain abstract, default, static, or private methods depending on the Java version.

**Enum:** uses enum metadata/flags and typically has compiler-generated helper methods and fields such as `values()` or `valueOf()`.

**Annotation:** a special kind of interface with metadata describing annotation elements.

**Record:** the class file contains `Record` metadata describing record components. The compiler also generates corresponding members according to record rules.

**Sealed class/interface:** the `PermittedSubclasses` attribute records the allowed subclasses.

**Nested class:** nested classes are represented by separate class files when they have corresponding class definitions; the `InnerClasses` attribute and related metadata describe their relationships.

**Module:** the `module-info.class` file stores module declarations, with the `ACC_MODULE` access flag and the `Module` attribute. This is not a regular application class with a `main` method.

This metadata helps the JVM and tools understand high-level language constructs after they have been compiled into the class file format.

## 11. Limitations and caveats when analyzing class files

- **Bytecode is not machine code:** bytecode consists of JVM instructions; the JVM may interpret or JIT-compile it at runtime.
- **Full source code is not present:** local variable names and line numbers are only available if the corresponding debug information was saved. Regular comments are not preserved.
- **Generics undergo type erasure:** descriptors use erased types; some generic information is stored in the `Signature` attribute.
- **Internal names differ from display names:** class names in the constant pool typically use slashes, such as `java/lang/String`, whereas Java source names use dots.
- **Class files are version-dependent:** older JVMs may not understand newer major versions or newer tags/attributes.
- **Do not edit binaries directly:** incorrect changes to offsets, lengths, constant pool indices, or stack maps can make a class file invalid.
- **Not every class file has a `Code` attribute:** abstract interface methods and native methods are examples that lack a regular bytecode body.
- **Not all attributes share the same scope:** an attribute is only valid at specific locations as defined by the JVMS.

A class file parser must read in the correct order, understand tags and versions, handle constant pool indices, skip or decode attributes per the specification, and validate length bounds. If you need to manipulate bytecode in a project, use a dedicated library such as ASM instead of modifying byte arrays with assumed offsets.

## 12. Common errors

| Symptom | Possible cause | Resolution |
|---|---|---|
| `ClassFormatError: Truncated class file` | File is truncated or binary data is incomplete | Rebuild the artifact cleanly; check the copy/download process |
| `ClassFormatError: Bad magic number` | The JVM received a non-class file or a corrupted file | Verify the classpath and artifact contents; do not rename extensions to fake a class file |
| `UnsupportedClassVersionError` | Class file major version is newer than the running JVM | Use a newer runtime or compile targeting an older release |
| `VerifyError` | Invalid bytecode or verification metadata | Rebuild with a standard compiler; if using bytecode instrumentation, check frames and stack maps |
| `NoClassDefFoundError` | Missing dependency at load time or the class failed to initialize in a prior scenario | Check classpath/module path, dependencies, and earlier initialization errors |
| `ClassNotFoundException` | The class loader could not find the requested class by name | Check the fully qualified class name and output root location |
| `javap` reports class not found | Incorrect classpath for `javap` or class file has not been generated yet | Use `javap -classpath out com.example.App` and verify the output root |
| Variable names missing in output | Compiler did not generate `LocalVariableTable` | Compile with `-g` and inspect debug information again |
| Stale `.class` files remain | Compiler does not clean up class files no longer generated in a new build | Clean and recompile into an empty output directory |

## 13. Checklist for reading a class file

When analyzing a class file, follow this order:

1. Verify that the magic number is `CAFEBABE`.
2. Read the major/minor version to determine format and compatibility.
3. Inspect the constant pool to find class names, superclass, interfaces, and references.
4. Read the access flags to determine the class kind.
5. Check interfaces, fields, and methods.
6. For concrete methods, inspect the `Code` attribute and bytecode.
7. Check attributes such as `Signature`, `Exceptions`, annotations, `InnerClasses`, or `Record`.
8. Inspect `StackMapTable` and debug information when analyzing verification or debugging issues.
9. Cross-check the classpath/module path and dependencies when the JVM fails to load a class.

The class file is the bridge between Java source code and the JVM. Once you understand the magic number, version, constant pool, class/field/method tables, `Code` attribute, and metadata, you can read compiler output, understand class-loading errors, and analyze bytecode systematically instead of viewing `.class` files as an opaque binary blob.
