# Application Image with jpackage

## 1. What is an application image?

An **application image** is an application directory generated by the **jpackage** tool. The image contains the application's native launcher, the required payload, and a Java runtime image so the application can run on the target machine without requiring the user to install Java separately.

You can think of an application image as consisting of three parts:

1. **Application launcher:** an OS-specific executable that allows users to open the application like a regular program.
2. **Application payload:** JARs, classes, resources, default configuration files, and other application content that need to be packaged.
3. **Java runtime image:** a runtime generated by jpackage using jlink, or a pre-built runtime image passed via the `--runtime-image` option.

An application image is one of jpackage's output formats, produced with the **app-image** type. It is a structured directory, not a JAR file or an installer. Users can run the launcher inside the image directory; the development team can test the image before creating an installer or distributing it.

The main benefit is packaging the application together with a compatible runtime, generating a platform-specific launcher, and reducing manual Java installation steps for end users. The image still depends on the operating system, CPU architecture, and any native libraries the application requires.

## 2. Distinguishing application image, JAR, runtime image, and installer

These artifact types solve different problems:

| Artifact | Content and purpose |
|---|---|
| Executable JAR | Packages Java classes/resources and launch metadata; the target machine still needs a compatible Java runtime. |
| Runtime image | A Java runtime created with jlink; by itself it does not include a launcher or a complete application payload. |
| Application image | Native launcher, application payload, and runtime image organized into a runnable directory. |
| Installer/package | Platform installer such as MSI, EXE, DMG, PKG, DEB, or RPM depending on the OS and JDK; can install files, shortcuts, and OS integrations. |

A typical workflow:

~~~text
Source code + dependencies
          |
          v
       JAR files
          |
          v
        jpackage
          |
          +----> application launcher
          +----> application payload
          +----> Java runtime image
          |
          v
     Application image
          |
          +----> test / archive / distribute
          |
          v
       Installer
~~~

An application image can be created directly from the application or used as input for jpackage to create an installer via the `--app-image` option. For example, on Windows you can create an MSI from a tested image. Available installer types depend on the operating system and packaging tools present on the build machine.

Do not confuse **--type app-image** with **--type msi** or **--type dmg**. `app-image` creates an application directory; the others create an installation package for their respective platforms.

## 3. How does jpackage work?

jpackage takes information about the application, determines the entry point, gathers the content to be packaged, and generates a launcher. By default, if no pre-built runtime image is provided, jpackage uses **jlink** to create a suitable runtime and places it inside the application image.

For non-modular applications, jpackage takes the main JAR and main class. For modular applications, jpackage takes the module path and main module. Depending on the application type, the tool determines which modules are needed in the runtime image; additional modules can be specified with `--add-modules`.

Main steps:

1. Read the input JARs or modules and launcher information.
2. Determine the modules required in the runtime image.
3. Create a runtime using jlink or copy the provided runtime image.
4. Generate the native launcher and launch configuration.
5. Package the application payload together with the runtime into the destination directory.

jpackage is a JDK tool. You should use a full JDK on the build machine because tools such as jpackage, jlink, and other Java utilities are required.

Check the version and options supported by the JDK in use:

~~~bash
jpackage --version
jpackage --help
~~~

Platform options can differ between Windows, Linux, and macOS as well as between JDK versions. Check the help output of the exact JDK on your build machine before putting commands into CI.

## 4. Preparing a non-modular application

The example below creates a simple Java application, packages it into a JAR, and then builds an application image.

Source structure:

~~~text
hello-app/
├── src/
│   └── demo/
│       └── Hello.java
├── classes/
├── input/
└── dist/
~~~

File **src/demo/Hello.java**:

~~~java
package demo;

public class Hello {
    public static void main(String[] args) {
        System.out.println("Hello from jpackage application image!");
    }
}
~~~

Compile the source and create the JAR:

~~~bash
mkdir -p classes input dist

javac --release 17 -encoding UTF-8 -d classes src/demo/Hello.java

jar --create \
    --file input/hello.jar \
    --main-class demo.Hello \
    -C classes .
~~~

**--release 17** targets the Java 17 API and bytecode level. The JAR is placed in the **input** directory, and **demo.Hello** is the main class.

On Windows PowerShell, you can create the directories with:

~~~powershell
New-Item -ItemType Directory -Force classes, input, dist | Out-Null
~~~

Then run the same javac and jar commands. The example paths use forward slashes, which are supported by JDK tools on Windows.

## 5. Creating an application image for a non-modular application

From the root **hello-app** directory, run:

~~~bash
jpackage --type app-image \
    --name HelloApp \
    --app-version 1.0.0 \
    --input input \
    --main-jar hello.jar \
    --main-class demo.Hello \
    --dest dist
~~~

Meaning of the options:

- **--type app-image:** requests creating an application image.
- **--name HelloApp:** sets the name of the image and primary launcher.
- **--app-version 1.0.0:** sets the application version.
- **--input input:** specifies the directory containing the files to package.
- **--main-jar hello.jar:** selects the main JAR; the path is resolved relative to the input directory.
- **--main-class demo.Hello:** specifies the class containing the main method.
- **--dest dist:** sets the parent directory where the generated image will be placed.

If `--dest` is omitted, jpackage writes output to the current working directory by default. Always specify the destination directory explicitly so CI and packaging scripts can locate artifacts consistently.

When using `--main-jar`, you can specify `--main-class` so the launcher does not have to rely on `Main-Class` in the manifest. `--main-class` is only used together with `--main-jar`. For modular applications, use `--module` instead of this pair of options.

The command above creates an application image named HelloApp inside `dist`. On Windows, the launcher is typically named `HelloApp.exe`; on Linux, the launcher is `HelloApp`; on macOS, the image is typically a `HelloApp.app` bundle.

### Console application on Windows

The Hello example prints output to the console. When creating the image on Windows, add the platform option **--win-console** to generate a console launcher:

~~~powershell
jpackage --type app-image --name HelloApp --app-version 1.0.0 --input input --main-jar hello.jar --main-class demo.Hello --dest dist --win-console
~~~

`--win-console` is a Windows-specific option. Typical GUI applications may not need a console launcher. Check `jpackage --help` on the target platform before using OS-specific options.

## 6. Running the application image and verifying output

After jpackage finishes, run the launcher inside the image.

Windows PowerShell:

~~~powershell
.\dist\HelloApp\HelloApp.exe
~~~

Linux:

~~~bash
./dist/HelloApp/bin/HelloApp
~~~

On macOS, you can open the application bundle:

~~~bash
open dist/HelloApp.app
~~~

To observe stdout when running the console example from a terminal on macOS, you can invoke the executable inside the bundle directly:

~~~bash
./dist/HelloApp.app/Contents/MacOS/HelloApp
~~~

Output printed by the application:

~~~text
Hello from jpackage application image!
~~~

The launcher paths above reflect the typical layout of an application image on each operating system. Directory names, configuration file locations, and some internal components may vary depending on the JDK, platform, and packaging options.

When running an application image, the launcher uses the runtime packaged with the image. Users do not need to rely on `JAVA_HOME` or a system-wide Java installation to launch the application. However, the application may still require native libraries, file permissions, devices, or other OS components.

## 7. Application image for modular applications

For modular applications, use **--module-path** to specify where modules are located and **--module** to specify the main module and main class.

Example:

~~~bash
jpackage --type app-image \
    --name ModularHello \
    --module-path mods \
    --module com.example.app/com.example.app.Main \
    --dest dist
~~~

Where:

- **mods** contains the application module and its dependency modules.
- **com.example.app** is the main module name.
- **com.example.app.Main** is the module's main class.
- jpackage links the main module into the runtime image.

If the main class is already declared in the appropriate module metadata, you can use the form **--module com.example.app**; however, specifying the main class explicitly makes the packaging command easier to read and verify.

Additional required modules can be added:

~~~bash
jpackage --type app-image \
    --name ModularHello \
    --module-path mods \
    --module com.example.app/com.example.app.Main \
    --add-modules java.sql,java.logging \
    --dest dist
~~~

`--add-modules` accepts a comma-separated list of module names. Add the modules your application actually needs, especially when modules are loaded dynamically or via reflection and cannot be fully determined from static dependencies.

`--module` and `--main-jar` are two different ways to specify the entry point; do not pass both at the same time. If the application is modular, use module path and main module. If the application is non-modular, use the input directory, main JAR, and main class.

## 8. Generated vs. pre-built runtime image

By default, jpackage creates a runtime image using jlink. The runtime bundled with the application image is typically stripped down according to jpackage's default options, for example removing debug information, header files, man pages, and native commands unnecessary for the application.

This makes the image smaller than a full JDK. The runtime image does not include the `javac` compiler, `javadoc`, or the full set of development tools found in a JDK.

There are two ways to control the runtime:

**Approach 1: let jpackage invoke jlink automatically.**

Use `--add-modules` to add required modules and `--jlink-options` to pass appropriate jlink options. Check the target JDK's help to see default values and supported options.

Example:

~~~bash
jpackage --type app-image \
    --name HelloApp \
    --input input \
    --main-jar hello.jar \
    --main-class demo.Hello \
    --add-modules java.sql \
    --dest dist
~~~

**Approach 2: create a separate runtime image with jlink and pass it to jpackage.**

Example of creating a runtime image for a modular application:

~~~bash
jlink \
    --module-path "$JAVA_HOME/jmods:mods" \
    --add-modules com.example.app \
    --output custom-runtime
~~~

On Windows, the separator for multiple module path entries is typically a semicolon; on Linux/macOS it is typically a colon. Adjust the paths to match your actual JDK and module locations.

Then use the created runtime image:

~~~bash
jpackage --type app-image \
    --name ModularHello \
    --module-path mods \
    --module com.example.app/com.example.app.Main \
    --runtime-image custom-runtime \
    --dest dist
~~~

When `--runtime-image` is passed, jpackage copies the specified runtime image into the application image instead of generating a new runtime with jlink. The runtime must match the target OS and architecture and contain all modules the application needs.

Distinguish between the target bytecode release and the bundled runtime version. For example, if you compile with `javac --release 17` but run jpackage from JDK 24, the default runtime image is built from JDK 24. If you want to bundle a Java 17 runtime, use jpackage/JDK 17 or create a Java 17 runtime image with jlink and pass it via `--runtime-image`. Always inspect the actual runtime inside the image.

## 9. Packaging dependencies, resources, and application content

For non-modular applications, `--input` specifies the directory containing the files included in the application image. This directory can contain the main JAR, dependency JARs, external resources, and files the application needs at runtime.

Example:

~~~text
input/
├── hello.jar
├── lib/
│   ├── logging.jar
│   └── database-driver.jar
└── config/
    └── app-defaults.properties
~~~

jpackage places the files in the input directory into the application payload. Verify that the launcher has a classpath configuration matching the dependency JARs and that the application can locate resources in their packaged paths. A simple way to reduce dependency configuration is to build an executable/fat JAR in your project's build pipeline and test the image built from that JAR.

The **--app-content** option lets you add files or directories to the payload outside the input directory:

~~~bash
jpackage --type app-image \
    --name HelloApp \
    --input input \
    --main-jar hello.jar \
    --main-class demo.Hello \
    --app-content extra-data,licenses \
    --dest dist
~~~

`--app-content` can be specified multiple times. The paths must exist and be specified relative to the working directory when running jpackage.

Do not package development environment config files, private keys, passwords, tokens, or secrets into the application image. If the application needs environment-specific configuration, provide an external configuration mechanism and protect read/write permissions on those files.

Native libraries must also match the target platform and architecture. A DLL, SO, or DYLIB file from another OS cannot be substituted for one another. Test native library loading paths and system dependencies on a clean machine.

## 10. Customizing the launcher and JVM arguments

jpackage provides options to configure how the launcher starts the application.

| Option | Purpose |
|---|---|
| --arguments | Default arguments passed to the main class when the user does not supply their own arguments. |
| --java-options | Options passed to the Java runtime, such as heap size or system properties. |
| --icon | Launcher/package icon in a format supported by the platform. |
| --description | Application description. |
| --vendor | Application vendor name. |
| --app-version | Application/package version. |
| --add-launcher | Creates an additional launcher with its own configuration. |
| --verbose | Prints detailed packaging output. |

Example setting JVM options and default arguments:

~~~bash
jpackage --type app-image \
    --name HelloApp \
    --input input \
    --main-jar hello.jar \
    --main-class demo.Hello \
    --java-options "-Xms128m" \
    --java-options "-Xmx512m" \
    --arguments "--mode=desktop" \
    --dest dist
~~~

`--java-options` is for the JVM; `--arguments` is for the Java program. The two argument types serve different purposes. Do not put secrets on the command line because they may appear in logs or process lists depending on the environment.

### Creating a secondary launcher with --add-launcher

You can create a Properties file for a secondary launcher, such as **launchers/report.properties**:

~~~properties
arguments=--mode=report
java-options=-Xmx512m
description=Report mode
~~~

Create the image with both the primary and secondary launchers:

~~~bash
jpackage --type app-image \
    --name HelloApp \
    --input input \
    --main-jar hello.jar \
    --main-class demo.Hello \
    --add-launcher Reports=launchers/report.properties \
    --dest dist
~~~

The `Reports` launcher uses the options defined in the Properties file. Certain keys can override the primary launcher's command-line configuration, such as `main-jar`, `main-class`, `arguments`, `java-options`, `icon`, or `description`. The supported keys depend on the JDK and platform; see `jpackage --help`.

## 11. Application image layout by operating system

Application images have different structures across platforms because the launcher and runtime are OS-dependent.

### Windows

A typical image looks like:

~~~text
HelloApp/
├── HelloApp.exe
├── app/
│   ├── HelloApp.cfg
│   └── hello.jar
└── runtime/
    ├── bin/
    └── lib/
~~~

The EXE file is the native launcher. The `app` directory contains the payload and launcher configuration; `runtime` contains the Java runtime image. Filenames and internal details may vary by JDK version.

### Linux

An image typically looks like:

~~~text
HelloApp/
├── bin/
│   └── HelloApp
└── lib/
    ├── app/
    │   ├── HelloApp.cfg
    │   └── hello.jar
    └── runtime/
~~~

The launcher resides in `bin`; the application payload and runtime typically reside under `lib`.

### macOS

The application image is typically a **HelloApp.app** bundle:

~~~text
HelloApp.app/
└── Contents/
    ├── Info.plist
    ├── MacOS/
    │   └── HelloApp
    ├── app/
    └── runtime/
~~~

`Info.plist` contains bundle metadata; the launcher executable resides in `Contents/MacOS`. You can open the bundle from Finder or use the `open` command.

These are reference layouts. Do not hard-code internal paths of the runtime or launcher configuration in your application without a clear reason. Use the launcher generated by jpackage and appropriate Java APIs to locate resources.

## 12. Application image and installer

After testing the application image, you can use that same image as input for the installer creation step.

For example on Windows, if the JDK and system support MSI:

~~~powershell
jpackage --type msi --name HelloApp --app-image dist\HelloApp --dest packages
~~~

On macOS or Linux, the package types and required native tools differ. Check `jpackage --help` on the build machine to see supported package types, such as DMG/PKG on macOS or DEB/RPM on Linux when the corresponding tools are installed.

An installer can integrate shortcuts, menus, file associations, installation directories, and OS metadata. These integrations belong to the installer packaging step and depend on platform options. An application image by itself is simply a runnable application directory; it does not register the application with the OS like an installer does.

The `--app-image` option allows jpackage to build a package from an already built and tested image. This separates creating the runtime/application payload from creating the installer, while letting you reuse the same image in an appropriate packaging workflow.

## 13. Testing and verifying the application image

A jpackage command finishing successfully only confirms that the tool generated output matching the requested configuration. You must test the actual image before distributing it.

Verification checklist:

1. Confirm the image directory was created under the expected `--dest`.
2. Check that the launcher exists and has executable permissions on Linux/macOS.
3. Run the launcher on a clean machine with the target OS and architecture.
4. Confirm the application runs without relying on a system-wide Java installation.
5. Verify resources, dependency JARs, native libraries, and configuration files.
6. Test default arguments, user-supplied arguments, and JVM options.
7. Check logs, stdout/stderr, exit codes, and behavior when configuration is missing.
8. Confirm the bundled runtime matches the intended release and includes required security patches.
9. Record checksums and the build identity of the image before release.

You can enable verbose output to investigate the packaging process:

~~~bash
jpackage --type app-image --verbose \
    --name HelloApp \
    --input input \
    --main-jar hello.jar \
    --main-class demo.Hello \
    --dest dist
~~~

When you need to inspect module dependencies, `jdeps` can help analyze static dependencies of a JAR:

~~~bash
jdeps --print-module-deps --multi-release 17 input/hello.jar
~~~

The output of `jdeps` is supporting information for selecting modules. Dependencies loaded via reflection, configuration, or `ServiceLoader` may need to be declared explicitly and tested separately.

If the image is compressed into a ZIP for distribution, preserve the entire directory structure and required attributes, especially executable permissions on Unix platforms. Do not extract only the EXE launcher or the binary in `bin` and send it alone, because the bundled runtime and payload are also required.

## 14. Platform compatibility and runtime updates

Application images are platform-specific:

- Windows images are for Windows and the corresponding CPU architecture.
- Linux images must match the architecture and system library requirements of the target environment.
- macOS images must match the Intel or Apple Silicon architecture that the JDK/runtime was built for.
- Native libraries must be compiled for the target OS, architecture, and ABI.

jpackage is not a cross-compiler for building images for every OS from a single build machine. In practice, releases usually require building images on runners matching each target platform and testing the artifacts on that platform.

The runtime bundled inside the image is an isolated copy. When the build machine installs a new JDK patch, older application images do not automatically update their runtime. You must rebuild the image using the updated JDK or new runtime image, run tests, and release a new application build.

For public distribution, check code signing requirements, notarization on macOS, antivirus policies, and platform package metadata. Signing and release workflows may require separate tools or certificates beyond creating the `app-image`.

## 15. Common errors when creating an application image

| Symptom | Possible cause | Resolution |
|---|---|---|
| jpackage cannot find the main JAR | Wrong `--input` or `--main-jar` name is not relative to the input directory. | Check the JAR file and relative path. |
| Main class not found | Main class has wrong package or JAR does not contain that class. | Use `jar tf` to inspect contents and specify the exact fully qualified name. |
| Image runs on build machine but not on another machine | Missing native dependency, different architecture, or different OS requirements. | Test on a clean machine matching the target platform. |
| Application reports missing module | Runtime image does not contain a dynamically loaded module or required dependency. | Use `--add-modules` or a runtime image built with jlink containing all required modules. |
| Dependency JAR not found | Dependency is missing from payload or launcher configuration/classpath is incorrect. | Include the dependency in the packaging pipeline and check the launcher config. |
| Image uses a higher Java release than expected | jpackage builds the runtime from the JDK running the tool. | Check `jpackage --version`; use the right JDK or `--runtime-image`. |
| Launcher does not show console on Windows | Using a GUI launcher for an app that needs stdin/stdout. | Build the image with `--win-console`. |
| Image is too large | Runtime includes unnecessary modules or excess payload. | Analyze dependencies, trim modules, and remove unneeded files from input. |
| Native library fails to load | Wrong OS/architecture binary or incorrect search path. | Verify binary format, ABI, and library loading locations. |
| Missing shortcuts/file associations | Building an `app-image` instead of an installer, or missing platform package options. | Build an appropriate installer and configure OS integration. |
| Fails to run after extraction | Archive stripped executable permissions or altered directory structure. | Recreate the archive preserving metadata and check launcher permissions. |
| Old image still has runtime vulnerabilities | Bundled runtime is not updated along with the system JDK. | Rebuild the image with a patched JDK/runtime and re-release. |

## 16. Building an application image in CI

A pipeline can be divided into the following steps:

1. Check out the exact commit and set up an organization-supported JDK.
2. Build the application and dependencies using Gradle/Maven or javac/jar.
3. Prepare the input directory containing only the runtime files needed for distribution.
4. Run jpackage with `--type app-image`, explicit name, version, entry point, and destination directory.
5. Inspect the runtime image, launcher, payload, and native dependencies.
6. Run a smoke test using the application image's launcher.
7. Store artifacts by OS/architecture, commit, and JDK version.
8. Generate checksums and sign code if required by the release process.
9. Only use tested images to create installers or publish to distribution channels.

Pin the JDK/toolchain and record the jpackage version, jlink version, OS, architecture, module list, and packaging options. This helps reproduce the image and investigate differences between builds.

Keep the input directory clean. Do not package test files, build logs, unnecessary source files, caches, or secrets. If production-specific configuration is needed, provision it through a secure deployment mechanism rather than embedding sensitive data in the image.

## 17. Pre-release checklist for application images

- [ ] Determined whether the application is modular or non-modular.
- [ ] Selected the correct main JAR/main class or main module.
- [ ] Verified all required dependencies, resources, and native libraries.
- [ ] Explicitly selected the JDK version used to run jpackage.
- [ ] Confirmed the runtime version bundled inside the image.
- [ ] Used `--type app-image` and specified `--dest` explicitly.
- [ ] Configured `--add-modules` or a custom runtime image if needed.
- [ ] Verified launcher, arguments, JVM options, and icon.
- [ ] Tested on a clean machine for each target OS/architecture.
- [ ] Confirmed the image runs without requiring a system-wide Java installation.
- [ ] Preserved directory structure and file permissions when archiving/distributing.
- [ ] Planned to rebuild the image when the runtime receives security patches.
- [ ] Checked code signing, notarization, and installer requirements if required by the distribution channel.

An application image packages a Java application into a directory with a native launcher, payload, and dedicated runtime. When entry points, runtime modules, dependencies, and target platforms are properly controlled, jpackage produces an artifact that is easy to test, distribute, and pass along to the installer creation step.
