# JVM Process Visibility with jps

## 1. What Is Process Visibility?

When a machine runs multiple Java applications, administrative tools need to identify which JVMs are active, which process belongs to which application, and which accounts can view their information.

**Process visibility** is the ability of a user or tool, as permitted by the operating system, to read information about a process. This permission depends on account identity, OS access rights, machine or container boundaries, and the JVM instrumentation mechanism.

In the JDK, **jps** (Java Virtual Machine Process Status Tool) lists instrumented HotSpot JVMs on the target system. jps only reports JVMs that the account running the tool has permission to access.

Basic command:

~~~bash
jps
~~~

Or to list only JVM identifiers:

~~~bash
jps -q
~~~

jps helps observe JVM processes. It is not a tool for listing every operating system process, and it does not guarantee that every running JVM will appear in the output.

## 2. Why OS Permissions Determine the jps List

jps relies on instrumentation information provided by the JVM. The operating system controls which accounts can read that information.

The list may be restricted by:

- The user or security principal running jps.
- The user owning the target JVM.
- Permissions to read process information and the instrumentation area.
- Permissions to access the temporary directory or data area used by the JVM.
- Security configuration and how the JVM was launched.
- Machine, container, and process namespace boundaries.

On many systems, the simplest and safest approach is to run jps under the same account that launched the Java application you want to observe.

For example, if a Java service runs under the `service-app` account, a developer account will not necessarily see all information for that service. Running jps under a different user may return an incomplete list of processes even though the application is still running.

You should not default to running every command as Administrator or root just to get a broader list. Elevated privileges can expose information from other applications and accounts.

## 3. Which JVMs Does jps Observe?

jps focuses on instrumented HotSpot JVMs that are accessible to the tool. It is not a general-purpose list of every program whose name contains `java`.

Cases that may not appear or may appear incomplete:

- JVMs owned by another account that the current user does not have permission to observe.
- JVMs running on another machine when remote monitoring is not configured.
- JVMs located in another container or PID namespace.
- JVMs that have just terminated or are still starting up when jps queries them.
- JVMs that do not provide the instrumentation required by jps.
- Java processes launched via a custom launcher where the class/JAR name and main arguments cannot be read.
- Applications compiled into a native executable that are no longer standard JVM processes.

Therefore, not finding a process in jps does not guarantee that the application has stopped. Cross-check with OS process tools, the service manager, and the deployment environment.

## 4. Distinguishing lvmid and OS PID

jps displays the **local VM identifier (lvmid)** for each JVM it finds.

The lvmid usually matches the operating system process ID, but it is not guaranteed to always be the same. Therefore:

- Use the lvmid to identify a JVM in jps output.
- When you need the exact OS PID, cross-check using the platform's process management tools.
- Do not save an old PID and reuse it after the process has terminated.
- Do not assume the host PID is the same as the PID seen from inside a container.

Example:

~~~text
82240 JpsVisibilityProbe alpha beta
94336 jdk.jshell/jdk.internal.jshell.tool.JShellToolProvider
~~~

In the sample output, `82240` is the lvmid of the `JpsVisibilityProbe` JVM. In standard HotSpot environments it typically matches the OS PID, but you should still verify it when using OS tools or working across namespaces.

## 5. jps Syntax and Observation Options

General syntax:

~~~text
jps [-q] [-m] [-l] [-v] [hostid]
jps -help
~~~

Commonly used options:

| Option | Information Displayed |
|---|---|
| No options | lvmid and the short name of the main class or JAR. |
| -q | Displays only the local VM identifier. |
| -m | Displays arguments passed to the main method. |
| -l | Displays the full class name or full JAR path. |
| -v | Displays arguments passed to the JVM. |
| -help | Displays usage help. |

Multiple options can be combined, for example:

~~~bash
jps -lmv
~~~

Note: jps is marked as experimental and unsupported in JDK documentation. Options and output format may change across JDK versions or vendors. Check `jps -help` for the exact JDK you are using.

## 6. Using -q When You Only Need a List of Identifiers

If you only need to know which JVMs are observable and retrieve their lvmids, use:

~~~bash
jps -q
~~~

Example output:

~~~text
82240
94336
21864
39180
51276
~~~

`-q` hides the class/JAR name and main arguments. This is suitable when you only need a list of IDs for further cross-referencing.

`-q` does not grant additional access permissions. If the user is not permitted to observe a JVM, this option will not make that JVM appear.

## 7. Using -m and -l to Identify Applications

When multiple JVMs are running at the same time, looking at the lvmid alone may not be enough to identify an application.

Use `-m` to view main arguments:

~~~bash
jps -m
~~~

Example:

~~~text
82240 JpsVisibilityProbe alpha beta
94336 JShellToolProvider --feedback silent
21864 JShellToolProvider --feedback concise
~~~

Use `-l` to view the full name of the main class or JAR:

~~~bash
jps -l
~~~

Example:

~~~text
82240 JpsVisibilityProbe
94336 jdk.jshell/jdk.internal.jshell.tool.JShellToolProvider
21864 jdk.jshell/jdk.internal.jshell.tool.JShellToolProvider
~~~

If two applications have the same main class, combine lvmid, main arguments, deployment metadata, and OS tools to identify the right process.

For JVMs launched via a custom launcher, jps may fail to retrieve the class/JAR name or main arguments and display `Unknown`.

## 8. Using -v to Observe JVM Arguments

The `-v` option displays the arguments passed to the JVM at startup:

~~~bash
jps -v
~~~

Example:

~~~text
82240 JpsVisibilityProbe -Xms32m -Dprobe.mode=visibility
94336 JShellToolProvider -Xms8m -Djdk.module.main=jdk.jshell
~~~

JVM arguments can help identify:

- Heap settings such as `-Xms` and `-Xmx`.
- System properties passed via `-D`.
- GC or diagnostic flags.
- Application-related modules or classpath.

`-v` output can expose internal paths, endpoints, environment names, and sensitive configuration. If the application passes tokens or passwords via the command line or system properties, that information may appear in the output.

Only share output after reviewing and redacting sensitive data. Avoid using `-v` in production unless necessary.

## 9. Java 17+ Example to Test Visibility

Create the file **JpsVisibilityProbe.java**:

~~~java
public class JpsVisibilityProbe {
    public static void main(String[] args) throws Exception {
        System.out.println(
                "JpsVisibilityProbe ready; pid=" +
                ProcessHandle.current().pid());

        Thread.sleep(120_000);
    }
}
~~~

`ProcessHandle.current().pid()` prints the PID of the current process. `Thread.sleep` keeps the JVM running for two minutes to allow time for observation.

Compile:

~~~bash
javac --release 17 -encoding UTF-8 JpsVisibilityProbe.java
~~~

In the first terminal, run:

~~~bash
java -Xms32m -Dprobe.mode=visibility JpsVisibilityProbe alpha beta
~~~

Example stdout:

~~~text
JpsVisibilityProbe ready; pid=82240
~~~

The PID in the example is for illustration only; each run will have a different PID.

In the second terminal, run:

~~~bash
jps -q
jps -m
jps -l
jps -v
~~~

Expected results to verify:

- The PID/lvmid of `JpsVisibilityProbe` appears in the list.
- `-m` displays `alpha beta`.
- `-l` displays `JpsVisibilityProbe`.
- `-v` displays `-Xms32m` and `-Dprobe.mode=visibility`.

After testing, stop the sample program with `Ctrl+C`.

This example was compiled with `javac --release 17` and verified with `jps` on JDK 24.0.2.

## 10. Visibility on Windows, Linux, and macOS

Specific permission mechanisms depend on the operating system.

### Windows

- jps runs under the current Windows account.
- Access to processes and instrumentation data is governed by Windows security tokens, ACLs, and how the service was started.
- Processes running under another service account may not be fully visible to the current user.
- When you need to cross-check OS PIDs, you can use Task Manager or PowerShell.

Example of viewing Java processes with PowerShell:

~~~powershell
Get-CimInstance Win32_Process |
    Where-Object { $_.Name -match 'java' } |
    Select-Object ProcessId, Name, CommandLine
~~~

`CommandLine` may contain sensitive information; only view and share it when authorized.

### Linux

- A process typically belongs to a specific UID and GID.
- Permission to read instrumentation and process information depends on the user, filesystem, and system configuration.
- Running jps under the exact service account usually yields the most accurate results.
- Containers, PID namespaces, and mount namespaces can restrict process visibility.

Cross-check user and processes:

~~~bash
id
ps -eo user,pid,args | grep '[j]ava'
~~~

### macOS

- Process permissions depend on the user and macOS protection mechanisms.
- JVMs running under another user may not expose information to the current account.
- Use the appropriate deployment account and check processes with Activity Monitor or `ps` when cross-checking is needed.

Do not arbitrarily change permissions on JVM instrumentation directories or temporary files using `chmod`/`chown`. Incorrect changes can break observability or affect the security of other processes.

## 11. Distinguishing Listing Permission from Attach Permission

Whether jps can see a JVM and whether another tool can attach to that JVM are two separate operations.

jps primarily reports instrumented JVMs and information that the current account can read. Tools like `jcmd` send diagnostic commands through a separate communication mechanism with the JVM.

As a result, you may encounter situations such as:

- jps lists the JVM, but `jcmd` cannot attach due to permissions or the Attach mechanism.
- jps does not list the JVM because it cannot read the instrumentation.
- OS tools see the process, but jps does not recognize it as an instrumented JVM.
- A JVM can run normally even if monitoring tools do not have permission to observe it.

Do not conclude that a successful jps listing means every diagnostic command is permitted. Check the specific permissions and mechanism of the next tool you plan to use.

## 12. JVMs Running in Docker and Containers

Containers create boundaries for process namespaces, filesystems, and users. Therefore, jps running on the host will not necessarily see JVMs inside a container.

When observation is needed:

1. Identify the container running the JVM.
2. Run the tool inside the same container or an environment sharing the same process namespace.
3. Ensure the image includes jps or an appropriate JDK tool.
4. Use a user with permission to read the JVM's instrumentation.
5. Run `jps -q` or `jps -l` inside that environment.
6. Use the lvmid visible in the current namespace for further cross-referencing.

Docker example:

~~~bash
docker exec -it <container-name> jps -l
~~~

Kubernetes example:

~~~bash
kubectl exec -it <pod-name> -c <container-name> -- jps -l
~~~

These commands require the container/pod name and appropriate access permissions. The PID inside the container may differ from the PID on the host.

JDK 24 also notes that jps running on the host does not list JVMs inside Docker containers via the default local mechanism. Run the tool in the appropriate container environment rather than assuming the host can observe every namespace.

## 13. Observing Remote JVMs Using hostid

jps supports the `hostid` parameter to query JVMs on another host when the target machine has `jstatd` configured.

Example:

~~~bash
jps -l remote.example:1099
~~~

In this usage:

- `remote.example` is the hostname or IP of the target machine.
- `1099` is the default RMI registry port.
- `jstatd` on the target machine provides an RMI interface for `jps`/`jstat` tools to retrieve JVM information.

`jstatd` requires access to the instrumentation of the target JVMs. JDK 24 marks `jstatd` as experimental, unsupported, and deprecated; this tool will be removed in a future release.

**Important security risk:** `jstatd` does not authenticate remote clients. When running, it can expose instrumentation information for every JVM that the user running `jstatd` has permission to observe to clients on the network.

Do not start `jstatd` in production or on untrusted networks without a security review. Consider firewalls, network isolation, service account permissions, and operational policies. If the risk cannot be controlled, do not enable `jstatd`; use local observation tools or a secured monitoring platform instead.

## 14. Process Visibility and Sensitive Information

jps options can expose more information than just the application name:

| Option | Potentially Exposed Data |
|---|---|
| jps -q | JVM identifier. |
| jps -m | Arguments passed to the main method. |
| jps -l | Package name, main class, or JAR path. |
| jps -v | JVM arguments, system properties, and startup configuration. |

Do not pass passwords, API tokens, private keys, or credentials on the command line. Prefer a secret manager, files with restricted permissions, or an appropriate secret provisioning mechanism.

If you need to send output to a support team:

- Collect only the necessary options.
- Remove tokens, internal URLs, or personal data before sharing.
- Limit the recipients.
- Do not store sensitive output in public directories or public tickets.
- Delete temporary copies according to your organization's retention policy.

Process visibility is part of operational permissions. Granting overly broad permissions can expose configuration details of many other applications.

## 15. Common Process Visibility Errors

| Symptom | Possible Cause | Resolution |
|---|---|---|
| jps does not see a running JVM | The current user lacks permission to read instrumentation, or the process is in a different namespace. | Run under the proper service account or inside the right container. |
| jps only shows a subset of JVMs | Some processes belong to other users or are restricted by OS access control. | Check process owners and permissions; do not default to system-wide privilege escalation. |
| jps displays Unknown | The JVM was launched with a custom launcher or lacks main class/JAR metadata. | Cross-check OS processes, service configuration, and startup logs. |
| jps -m shows no main arguments | Embedded JVM or launcher does not provide main argument information. | Use deployment metadata or other monitoring tools. |
| lvmid does not match OS PID | The VM identifier is not necessarily always the OS PID. | Cross-check with OS tools in the same namespace. |
| Host jps does not see container JVMs | Isolated PID namespace/container. | Run jps inside the container or an environment sharing its namespace. |
| Remote jps fails to connect | jstatd/RMI registry is not running, wrong host/port, or blocked by firewall. | Check the service, hostid, port, and network policies. |
| Remote jps returns an incomplete list | jstatd lacks permission to observe certain JVMs. | Check the user credentials of jstatd and the target JVMs. |
| -v output contains sensitive data | JVM arguments include tokens, passwords, or endpoints. | Do not share raw output; redact secrets and fix how credentials are passed. |
| Output parsing script breaks after JDK upgrade | The jps output format may change. | Do not rely on text parsers; use more stable monitoring APIs. |

## 16. Do Not Use jps Output as a Stable Inventory Interface

JDK documentation warns that the output format of jps may change in future versions. Tokens are whitespace-separated; arguments containing whitespace can make splitting and reassembling arguments ambiguous.

Therefore:

- Do not write production scripts that depend on fixed column positions.
- Do not assume the class name is always present.
- Do not assume lvmid is always the OS PID.
- Do not assume the list includes every JVM.
- Do not use jps as a replacement for an official inventory or monitoring service.

If you need to manage processes in production, prefer a service manager, container orchestration, secured JMX, or an observability platform with a stable interface and schema.

jps is suitable for quick checks, local troubleshooting, and manual operations. Due to its experimental/unsupported status, you should not build long-term inventory systems that rely entirely on this tool.

## 17. Safe JVM Process Observation Workflow

An operational workflow can be carried out as follows:

1. Identify the machine, container, and account owning the application.
2. Select the right JDK that includes the jps tool.
3. Run `jps -q` to get lvmids within the scope the current user is permitted to observe.
4. Use `jps -l` to identify the main class or JAR.
5. Only use `-m` or `-v` if you need to inspect arguments and have assessed the risk of exposing secrets.
6. Cross-check lvmid with OS processes if you need the OS PID.
7. Confirm the process is alive and belongs to the right application.
8. If diagnostic commands are needed, check permissions and use an appropriate tool such as `jcmd`.
9. If remote monitoring is needed, evaluate `jstatd` and RMI risks before enabling it.
10. Record the timestamp, user, environment, and observation limits in the operational report.

Observation permissions should be granted following the principle of least privilege: an account should only have enough permissions to inspect the JVMs within its scope of responsibility.

## 18. Checklist Before Concluding a Process Does Not Exist

- [ ] Ran jps on the correct host or container.
- [ ] Used an account with permission to observe the target JVM.
- [ ] Checked the process owner and namespace.
- [ ] Tried `jps -q` and `jps -l` to distinguish IDs from application names.
- [ ] Considered cases of custom launchers or embedded JVMs.
- [ ] Cross-checked with Task Manager, `ps`, or service/container tools.
- [ ] Distinguished listing permission from attach permission.
- [ ] Verified lvmid and OS PID before using them in other commands.
- [ ] Assessed information disclosure risks before using `-m` or `-v`.
- [ ] Conducted a security review before enabling remote `jstatd`.
- [ ] Noted that jps is an experimental/unsupported tool and its output is unstable.
