# HTML Errors in Javadoc

Javadoc generates HTML documentation from documentation comments in Java source code. These comments can contain descriptive text, HTML, inline tags, and block tags. If the HTML is poorly structured, the generated documentation page may render unexpectedly, break the layout, affect accessibility, or fail HTML validation.

**DocLint** is a tool built into `javadoc` and `javac` to detect common issues in documentation comments. The `html` check group can identify structural errors such as block elements nested inside inline elements or missing required closing tags. The `syntax` group detects syntax errors such as unescaped HTML angle brackets. The `accessibility` group detects issues such as images missing `alt` attributes or tables lacking descriptive information.

It is important to understand the limitations: DocLint is not a full HTML5 validator, does not fix incorrect content, and does not guarantee that every generated HTML page is valid. Therefore, a good workflow should check the documentation comments, the `javadoc` output, and the final HTML that readers will open.

## 1. HTML in Documentation Comments

Javadoc supports two common styles of documentation comments:

- **Traditional comment** starts with `/**` and ends with `*/`. The description can contain HTML, inline tags, and block tags.
- **Markdown documentation comment** uses lines starting with `///`. Markdown, HTML, and Javadoc tags can appear together.

Example of a traditional comment:

~~~java
/**
 * Returns a normalized name.
 * <p>
 * Leading and trailing whitespace is removed.
 * </p>
 *
 * @param name input name
 * @return normalized name
 */
public String normalize(String name) {
    return name == null ? "" : name.trim();
}
~~~

Example of a Markdown documentation comment on JDKs that support line doc comments:

~~~java
/// Returns a normalized name.
///
/// Leading and trailing whitespace is removed.
///
/// @param name input name
/// @return normalized name
public String normalize(String name) {
    return name == null ? "" : name.trim();
}
~~~

Regardless of which comment style is used, any embedded HTML must still be properly structured. Javadoc does not automatically turn invalid HTML into valid markup.

HTML in comments must conform to HTML5. For documentation generated by the standard doclet, also pay attention to the heading structure of the Javadoc page: comments for modules, packages, and types typically start headings at level 2; comments for constructors, methods, fields, and other members typically start headings at level 4. Standalone HTML pages in `doc-files` can start at heading level 1.

## 2. Which Error Groups Does DocLint Check?

DocLint divides its checks into five groups:

| Group | What it checks | Examples |
|---|---|---|
| html | Common HTML structural issues | Block element inside an inline element, missing required closing tag |
| syntax | Documentation comment syntax and Javadoc tags | Unescaped `<` or `&`, invalid Javadoc tag |
| accessibility | User and assistive technology support issues | `img` missing `alt`, `table` missing an appropriate caption or summary |
| reference | References to Java API elements | `{@link}` or `@see` pointing to a non-existent class or member |
| missing | Missing documentation comments or tags | Missing `@param`, `@return`, or documentation comment |

These groups can be enabled or disabled individually using the `-Xdoclint` option.

Some important distinctions:

- Structural HTML errors are usually reported as errors if they could cause the output to fail downstream validation tools.
- Syntax errors such as unescaped HTML characters are usually reported as errors.
- Reference errors are usually reported as errors because they can produce broken or misdirected documentation.
- Missing documentation or tags are usually reported as warnings because they typically do not make the output HTML structurally invalid.
- Accessibility issues may be reported as errors when the expected output validator would also treat them as errors.

DocLint only reports issues. It does not automatically add closing tags, fix URLs, add `alt` attributes, or rewrite documentation comments.

## 3. Missing Closing Tags

A common mistake is opening an element that requires a closing tag without closing it.

Incorrect example:

~~~java
/**
 * <p>Returns the account information.
 * <strong>The result may be cached.
 */
public String getAccountInfo() {
    return "account";
}
~~~

In this example, the `p` and `strong` tags are not closed. Browsers may automatically adjust the DOM when rendering, but browser error-recovery behavior is not guaranteed to be consistent across structures or validators.

How to fix:

~~~java
/**
 * <p>Returns the account information.</p>
 * <p><strong>The result may be cached.</strong></p>
 */
public String getAccountInfo() {
    return "account";
}
~~~

For elements such as `p`, `div`, `strong`, `em`, `a`, `ul`, `ol`, `li`, and `table`, check their opening and closing positions carefully. Some tags in HTML5 have optional end tags, but writing them explicitly generally makes comments easier to read and reduces confusion.

Void elements such as `img`, `br`, `hr`, and `meta` do not have separate closing tags. In HTML5, write `img` with the required attributes rather than trying to create an opening/closing `img` tag pair.

## 4. Improperly Nested Elements

HTML has rules about which elements are allowed inside other elements. Simply closing every tag does not guarantee a valid structure.

### Placing a block element inside an inline element

Incorrect example:

~~~html
<span>
    <div>Configuration details</div>
</span>
~~~

`span` is inline phrasing content; it should not contain `div`, which is block flow content.

Fix by using an appropriate container:

~~~html
<div>
    <p>Configuration details</p>
</div>
~~~

Or if you only need to emphasize a phrase:

~~~html
<p>
    The configuration is <strong>required</strong>.
</p>
~~~

### Nesting `p` inside `p`

Incorrect example:

~~~html
<p>
    First paragraph.
    <p>Second paragraph.</p>
</p>
~~~

A `p` element cannot contain another `p` element. Fix by separating them into two independent paragraphs:

~~~html
<p>First paragraph.</p>
<p>Second paragraph.</p>
~~~

### Placing elements in the wrong position in a list

Example to avoid:

~~~html
<ul>
    <p>Available options</p>
    <li>Fast mode</li>
    <li>Safe mode</li>
</ul>
~~~

Place the introductory paragraph before the list:

~~~html
<p>Available options:</p>
<ul>
    <li>Fast mode</li>
    <li>Safe mode</li>
</ul>
~~~

Each list item should be inside an `li`. If an item needs multiple paragraphs or a nested list, place them inside the corresponding `li`.

## 5. HTML Table Errors

Tables in Javadoc are often used to present parameters, states, or options. Common mistakes include:

- Missing `tr` structure or placing `td`/`th` outside a row.
- Nesting tables or block elements in invalid positions.
- Missing column headers.
- Missing a caption or appropriate description.
- Using tables solely for layout alignment instead of representing tabular data.

Incorrect example:

~~~html
<table>
    <tr>
        <td>Mode</td>
        <td>Description
    </tr>
</table>
~~~

The second cell is not closed, and the table has no clear header information.

Fixed example:

~~~html
<table>
    <caption>Available execution modes</caption>
    <thead>
        <tr>
            <th scope="col">Mode</th>
            <th scope="col">Description</th>
        </tr>
    </thead>
    <tbody>
        <tr>
            <td>Fast</td>
            <td>Optimized execution.</td>
        </tr>
        <tr>
            <td>Safe</td>
            <td>Additional validation.</td>
        </tr>
    </tbody>
</table>
~~~

Explanation:

- `caption` describes the table content.
- `thead` groups the header rows.
- `tbody` groups the data rows.
- `th` marks a header cell.
- `scope="col"` indicates that the header applies to the column.
- Each `tr` contains the corresponding `td` or `th` cells.

Not every table requires the same level of complexity, but a clear caption and headers help screen reader users understand the data better.

## 6. Missing `alt` Attributes and Accessibility Errors

Images in Javadoc must have appropriate alternative text. If an image conveys information but lacks `alt`, users who cannot see the image may miss important content.

Incorrect example:

~~~html
<img src="images/module-graph.png">
~~~

Fixed example:

~~~html
<img src="images/module-graph.png"
     alt="Module app depends on library and model">
~~~

If an image is purely decorative and provides no information, use an empty `alt`:

~~~html
<img src="images/decorative-divider.png" alt="">
~~~

Some guidelines:

- Describe the content or function of the image, rather than just writing `"image"` or `"picture"`.
- Do not repeat the caption verbatim if doing so does not help the reader.
- Do not use the filename as `alt` if the filename does not describe the image.
- For complex diagrams, provide an additional text explanation near the image.
- Verify the image path to ensure the resource is actually copied into the generated documentation.

For tables, add an appropriate `caption` or title and mark header rows/columns with `th`. DocLint's `accessibility` group detects common issues such as images missing `alt` or tables missing descriptive information.

## 7. Link and HTML Attribute Errors

Links in documentation comments usually use the `a` tag. Common mistakes include:

- Missing `href` or an invalid `href` value.
- Missing quotes around attribute values.
- URLs containing unescaped `&` characters.
- Nesting one `a` tag inside another `a` tag.
- Links without meaningful labels.
- Using relative paths that do not exist in the output.

Incorrect example:

~~~html
<a href=https://example.com/search?a=1&b=2>Search</a>
~~~

Fix:

~~~html
<a href="https://example.com/search?a=1&amp;b=2">Search documentation</a>
~~~

When pointing to Java APIs, prefer Javadoc reference tags:

~~~java
/**
 * Uses {@link java.util.List} to store results.
 * See {@link java.lang.String#trim()} for whitespace handling.
 */
~~~

This allows Javadoc to resolve classes and members against the Java API and generate links to the exact page in the documentation set.

Incorrect nested link example:

~~~html
<a href="https://example.com">
    Documentation <a href="https://example.com/api">More</a>
</a>
~~~

Fix by splitting into two separate links:

~~~html
<a href="https://example.com">Documentation</a>
<a href="https://example.com/api">API reference</a>
~~~

DocLint `reference` checks Java references in Javadoc tags; it does not guarantee that every web URL in `href` exists or responds successfully. Use a separate link checker to verify external URLs and resource paths in the output.

## 8. Unescaped Special Characters

In documentation comments, `<`, `>`, and `&` have special meaning in HTML. When you want to display them as literal text, escape them properly.

| Character to display | How to write it |
|---|---|
| `<` | `&lt;` |
| `>` | `&gt;` |
| `&` | `&amp;` |

Incorrect example:

~~~java
/**
 * Accepts a List<String> as input.
 * The condition is a < b && b > 0.
 */
~~~

Javadoc may interpret `<String>` as an HTML tag and the `<`, `>`, `&` characters as markup or syntax characters.

How to fix when describing code:

~~~java
/**
 * Accepts a {@code List<String>} as input.
 * The condition is {@code a < b && b > 0}.
 */
~~~

Or using HTML entities:

~~~java
/**
 * Accepts a List&lt;String&gt; as input.
 * The condition is a &lt; b &amp;&amp; b &gt; 0.
 */
~~~

`{@code}` is suitable for displaying identifiers, expressions, or short code snippets. `{@literal}` is suitable when you need to display literal text without interpreting it as HTML or nested Javadoc tags.

Do not mechanically use HTML entities for all code. Choose `{@code}`, `{@literal}`, or entities based on the intended display.

## 9. Confusing Javadoc Tags with HTML

A documentation comment has two syntax groups to distinguish:

- HTML tags such as `p`, `div`, `a`, `table`, and `img`.
- Javadoc tags such as `@param`, `@return`, `@throws`, `{@link}`, and `{@code}`.

Example:

~~~java
/**
 * Returns the account identifier.
 *
 * @param accountId account identifier
 * @return formatted identifier
 */
~~~

Block tags start at the beginning of a line, after whitespace and the leading `*` of the comment. If a line of text starts with `@` but is not a Javadoc tag, Javadoc may misinterpret it as a block tag.

Example when you want to display an email or `@` symbol at the beginning of a line:

~~~java
/**
 * Contact: &#064;support.example.com
 */
~~~

Use an entity to display `@` at the start of a line without creating a block tag.

If you misspell a tag name or place a tag in the wrong position, DocLint may report a `syntax` error. If the tag is valid but references a non-existent method, field, or parameter, that is usually a `reference` error.

## 10. Headings and `id` Attributes in Javadoc Pages

Javadoc pages generated by the standard doclet already have their own heading structure. If a documentation comment adds headings at the wrong level, the document structure can become difficult to navigate by keyboard or screen reader.

According to the HTML rules in JDK 26 Javadoc:

| Comment location | Starting heading level |
|---|---|
| Module declaration | `h2` |
| Package declaration | `h2` |
| Class/interface/type | `h2` |
| Constructor and member | `h4` |
| Standalone HTML in `doc-files` | `h1` |

For example, in a method comment, do not start with `h1`:

~~~java
/**
 * <h1>Configuration</h1>
 * Explains the configuration options.
 */
public void configure() {
}
~~~

Use a heading appropriate for the member's location:

~~~java
/**
 * <h4>Configuration</h4>
 * Explains the configuration options.
 */
public void configure() {
}
~~~

For short sections of content, using `p` or `strong` may be more appropriate than creating a new heading.

### The `id` attribute

The standard doclet uses identifiers to generate anchors for classes and members. If you manually set an `id` that matches a Java identifier, a collision can occur.

Example to avoid:

~~~html
<div id="normalize">Normalization rules</div>
~~~

If the class has a method named `normalize`, this `id` can conflict with the anchor generated by Javadoc.

Fix by using an `id` containing a character that is not valid in a Java identifier, such as a hyphen:

~~~html
<div id="normalization-rules">Normalization rules</div>
~~~

Every `id` must still be unique within the generated HTML page.

## 11. Using `pre`, `code`, and `snippet` Properly

Code samples are a frequent source of HTML errors because Java angle brackets and special characters are easily misinterpreted as markup.

Example using `{@code}` for a short expression:

~~~java
/**
 * Returns a {@code List<String>} containing the results.
 */
~~~

For a code block:

~~~java
/**
 * Example:
 * <pre>{@code
 * List<String> names = List.of("Ada", "Grace");
 * System.out.println(names);
 * }</pre>
 */
~~~

Javadoc processes the content of `{@code}` as literal code and renders it in a monospace font. `pre` preserves whitespace and line breaks in the code block.

With modern JDKs, you can use `{@snippet}` to present code samples with syntax highlighting and support for referencing external snippets:

~~~java
/**
 * Example:
 * {@snippet :
 * List<String> names = List.of("Ada", "Grace");
 * System.out.println(names);
 * }
 */
~~~

When using HTML `pre`/`code` directly, the structure should be:

~~~html
<pre><code class="language-java">
System.out.println("Hello");
</code></pre>
~~~

Do not place `p`, `div`, or other block elements inside `pre`/`code` in a way that breaks structure. Do not insert raw Java code containing `<` and `&` directly into HTML without using `{@code}`, `{@snippet}`, `{@literal}`, or proper entity escaping.

## 12. Running DocLint to Find HTML Errors

JDK 26 supports the following options:

| Option | Purpose |
|---|---|
| `-Xdoclint` | Enables recommended checks for documentation comments |
| `-Xdoclint:html` | Checks only the `html` group |
| `-Xdoclint:syntax` | Checks comment syntax, escaped characters, and tags |
| `-Xdoclint:accessibility` | Checks accessibility issues |
| `-Xdoclint:reference` | Checks references to Java API elements |
| `-Xdoclint:missing` | Checks for missing comments and tags |
| `-Xdoclint:all` | Enables all check groups |
| `-Xdoclint:none` | Disables all DocLint checks |
| `-Werror` | Treats warnings as build errors |

In JDK 26 `javadoc`, DocLint is enabled by default. You can explicitly specify the groups to check so build commands remain readable and consistent.

Check HTML, syntax, and accessibility:

~~~bash
javadoc -Xdoclint:html,syntax,accessibility -d docs -sourcepath src -subpackages com.example.api
~~~

Check all groups and fail the build on warnings:

~~~bash
javadoc -Xdoclint:all -Werror -encoding UTF-8 -d docs -sourcepath src -subpackages com.example.api
~~~

To check only HTML:

~~~bash
javadoc -Xdoclint:html -d docs -sourcepath src -subpackages com.example.api
~~~

To exclude one group from all checks:

~~~bash
javadoc -Xdoclint:all,-missing -d docs -sourcepath src -subpackages com.example.api
~~~

Do not disable DocLint entirely just to make a build pass. When warnings or errors occur, identify the group, inspect the reported location, and fix the root cause in the comment.

## 13. Reading and Fixing Diagnostics

When an error is detected, `javadoc` typically prints the diagnostic kind, filename, line number, and character position. Illustrative example:

~~~text
NameFormatter.java:12: error: element not closed: p
 * <p>Returns the normalized value.
   ^
1 error
~~~

The exact message depends on the JDK version and markup type. When resolving diagnostics:

1. Identify the reported file and line.
2. Read the entire documentation comment containing that line.
3. Determine whether the error belongs to `html`, `syntax`, `accessibility`, `reference`, or `missing`.
4. Fix the HTML or Javadoc tag at the source.
5. Re-run the same `javadoc` command.
6. Inspect the HTML output to verify layout and content.

A single error can trigger multiple diagnostics because improperly nested markup causes the parser to misinterpret subsequent content. Fix the first structural error and re-run before addressing remaining warnings.

## 14. Complete Example: Fixing HTML in Javadoc

Create `NameFormatter.java`:

~~~java
package com.example.api;

import java.util.List;

/**
 * Formats user-facing names.
 *
 * <p>This class normalizes whitespace before displaying names.</p>
 *
 * <h2>Examples</h2>
 * <ul>
 *     <li>Removes leading whitespace.</li>
 *     <li>Removes trailing whitespace.</li>
 * </ul>
 *
 * <p>For more details, see {@link java.util.List}.</p>
 */
public final class NameFormatter {

    private NameFormatter() {
    }

    /**
     * Normalizes a list of names.
     *
     * <p>Example input:</p>
     * <pre>{@code
     * List<String> names = List.of("Ada ", "Grace ");
     * }</pre>
     *
     * <table>
     *     <caption>Normalization behavior</caption>
     *     <thead>
     *         <tr>
     *             <th scope="col">Input</th>
     *             <th scope="col">Output</th>
     *         </tr>
     *     </thead>
     *     <tbody>
     *         <tr>
     *             <td>" Ada "</td>
     *             <td>"Ada"</td>
     *         </tr>
     *         <tr>
     *             <td>"Grace "</td>
     *             <td>"Grace"</td>
     *         </tr>
     *     </tbody>
     * </table>
     *
     * @param names names to normalize
     * @return normalized names
     */
    public static List<String> normalizeAll(List<String> names) {
        return names.stream()
                .map(String::trim)
                .toList();
    }
}
~~~

Notes on the example:

- All `p` tags are properly closed.
- The class heading starts at `h2`.
- The table has `caption`, `thead`, `tbody`, and `scope` on column headers.
- The code sample uses `pre` and `{@code}` to escape angle brackets.
- The reference to `List` uses a Javadoc link tag.
- `@param` and `@return` accurately describe the method.

Generate Javadoc on JDK 17 or later:

~~~bash
javadoc -Xdoclint:all -Werror -encoding UTF-8 -d docs -sourcepath src com.example.api
~~~

If the source is at `src/com/example/api/NameFormatter.java`, the command above generates documentation in the `docs` directory.

You can open the page:

~~~text
docs/com/example/api/NameFormatter.html
~~~

To verify the generated page, inspect the table, headings, code block, and Java SE API link. The Java source can also be compiled separately:

~~~bash
javac --release 17 -d out src/com/example/api/NameFormatter.java
~~~

Compiling the source does not replace running `javadoc`; the two tools check different aspects.

## 15. Validating HTML After Javadoc Generation

DocLint checks documentation comments in the source. Downstream HTML validators check the complete HTML pages after the standard doclet has generated them.

Validating the HTML output helps catch issues that DocLint cannot see, such as:

- HTML added by a custom taglet.
- HTML in `header`, `footer`, `title`, or `help` file options.
- Conflicts between comment content and structure generated by the standard doclet.
- Links to resources that do not exist in the output.
- External URLs that are no longer reachable.
- HTML errors that only appear when content sections are assembled into a complete page.

Validation workflow:

1. Generate documentation using `javadoc` with DocLint.
2. Open key HTML pages in a browser.
3. Use an HTML conformance validator to check the complete page structure.
4. Use a link checker to scan internal and external URLs.
5. Check accessibility with an appropriate tool.
6. Re-run the build after fixing comments or doclet configuration.

Do not rely solely on `javadoc` exiting with code `0`. A page can be generated successfully while still containing HTML errors or broken links.

## 16. Suppressing DocLint Only When Necessary

In some legacy projects, older documentation comments may exist that cannot be fixed immediately. Javadoc allows suppressing specific DocLint groups via annotation:

~~~java
@SuppressWarnings("doclint:html")
public class LegacyFormatter {
}
~~~

Multiple groups can be suppressed:

~~~java
@SuppressWarnings({"doclint:html", "doclint:accessibility"})
public class LegacyDocumentation {
}
~~~

Points to consider:

- Suppression only hides diagnostics; it does not fix the HTML.
- An annotation on a declaration can affect that declaration and nested declarations according to DocLint rules.
- Suppressing at the class level can hide many issues across the class's members.
- Do not suppress an entire package just to avoid fixing invalid markup.
- Document the reason and a plan to remove the suppression when possible.

Only suppress errors that have been reviewed and intentionally accepted. For HTML errors that can be fixed directly, fix the comment instead of disabling the check.

## 17. Common Errors and Fixes

| Symptom | Possible cause | How to fix |
|---|---|---|
| `element not closed` | Missing required closing tag | Add the closing tag in the right place |
| `block element inside inline element` | `div`, `p`, or `ul` nested inside `span`/`a` | Use an appropriate block container and avoid invalid nesting |
| `invalid HTML nesting` | Improperly nested `p`, `a`, list, or `table` | Check HTML5 content model rules |
| `unescaped angle bracket` | Writing `List<String>` or `a < b` directly | Use `{@code}`, `{@literal}`, or `&lt;`/`&gt;` |
| `unescaped ampersand` | URL or text contains raw `&` | Use `&amp;` in HTML attributes and text |
| `invalid documentation tag` | Misspelled tag name or misplaced block tag | Check the Javadoc tag and line-start placement |
| `missing alt attribute` | Image lacks alternative text | Add a descriptive `alt` or empty `alt=""` for decorative images |
| `table accessibility warning` | Table lacks a `caption` or clear headers | Add `caption`, `th`, and `scope` |
| Inappropriate heading level | Using `h1` in a method comment or skipping heading levels | Choose heading levels based on the declaration kind |
| Java link not found | Wrong class/member name or signature | Check the reference and parameter types |
| Page still invalid after DocLint passes | DocLint is not a full HTML validator | Validate the HTML output with a dedicated validator |
| Broken HTML after using a taglet | Taglet emits invalid markup | Inspect taglet output and validate the final page |

## 18. Pre-Release Javadoc Checklist

- [ ] Documentation comments use valid HTML5.
- [ ] Elements requiring end tags are closed in the right places.
- [ ] Block and inline elements are not improperly nested.
- [ ] Lists use `li` inside `ul` or `ol`.
- [ ] Tables have clear row/column structure and an appropriate `caption`.
- [ ] Images have appropriate `alt` text.
- [ ] Links have valid `href` values and meaningful labels.
- [ ] There are no nested anchor tags.
- [ ] `<`, `>`, and `&` in code/text are properly escaped.
- [ ] Headings follow the appropriate level for module, package, type, or member.
- [ ] Custom `id` values do not collide with Java element anchors and are unique.
- [ ] Javadoc runs with `-Xdoclint:all`.
- [ ] CI considers `-Werror` to prevent new warnings.
- [ ] HTML output is opened and visually inspected.
- [ ] An HTML validator and link checker are run for important documentation.
- [ ] Any suppressions have clear reasons and are reviewed periodically.

## 19. Key Takeaways

- HTML errors in Javadoc can break layout, accessibility, or HTML output validity.
- DocLint has five groups: `html`, `syntax`, `accessibility`, `reference`, and `missing`.
- The `html` group detects common structural errors such as block elements inside inline elements or missing required closing tags.
- The `syntax` group detects unescaped HTML characters and malformed Javadoc tags.
- The `accessibility` group checks issues such as images missing `alt` and tables lacking appropriate descriptions.
- Use `{@code}` or `{@literal}` to display code and special characters safely.
- Write headings at the appropriate level for the declaration's position on the Javadoc page.
- Javadoc does not automatically fix invalid HTML, and DocLint is not a full HTML5 validator.
- Combine `-Xdoclint:all`, `-Werror`, an HTML validator, a link checker, and visual inspection.
- Only suppress DocLint for specific reasons; suppression is not a substitute for fixing markup.
