# Heap sizing in Java: choosing heap size based on workload and memory limits

**Heap sizing** is the process of determining an appropriate Java heap capacity so an application can retain its live object set, absorb allocation bursts, and meet latency/throughput targets without exceeding the memory limits of the host or container.

A heap that is too small causes frequent GC runs, wastes application time on collection, and can trigger **OutOfMemoryError**. A heap that is too large consumes RAM budget needed by other parts of the JVM, co-located processes on the same host, and the operating system. A good heap size must be measured under a realistic workload, then verified using GC logs, heap metrics, and application performance.

## 1. What is the Java heap?

The Java heap is the memory area the JVM uses to allocate most objects and arrays created by an application. The Garbage Collector (GC) identifies reachable objects, reclaims memory from objects that are no longer used, and reuses the reclaimed heap space.

For example:

~~~java
Customer customer = new Customer();
byte[] payload = new byte[1024 * 1024];
~~~

The `Customer` object and the `payload` array are allocated on the heap. Local variables and references may reside in a stack frame or be optimized away by the JIT, but the objects they point to generally still live on the heap.

Heap sizing focuses on heap capacity. It does not directly set a limit on the entire process memory.

### How does the heap differ from process memory?

A JVM also requires several other memory regions:

| Memory region | Contents |
|---|---|
| Java heap | Application objects and arrays |
| Metaspace | Class and class loader metadata |
| Code cache | Native code generated by the JIT compiler |
| Thread stacks | Per-platform-thread stacks |
| Direct buffers | Off-heap buffers, commonly used for I/O |
| GC and JVM native structures | Internal structures, reference tables, and GC support regions |
| JNI/native allocations | Memory allocated by native libraries or JNI code |
| Shared libraries and memory mappings | Libraries, files, and memory-mapped regions |

Therefore, `-Xmx2g` does not mean the entire process will use at most 2 GiB. If a container has a 2 GiB limit and the heap is allowed to consume nearly all of it, the JVM can still be terminated by the OS/container when metaspace, thread stacks, direct buffers, or native allocations push total memory past the limit.

## 2. Distinguishing used, committed, reserved, and max heap

These four concepts frequently appear in logs, JMX, the `Runtime` API, and diagnostic tools:

| Concept | Meaning |
|---|---|
| **Used** | Heap space currently occupied by objects |
| **Committed** | Heap space the JVM has committed and can use immediately |
| **Reserved** | Address space the JVM has reserved for the heap; does not mean all of this space is occupying physical RAM |
| **Max** | Maximum heap limit the JVM is allowed to use |

In the Java Management API:

~~~java
Runtime runtime = Runtime.getRuntime();

long used = runtime.totalMemory() - runtime.freeMemory();
long committed = runtime.totalMemory();
long max = runtime.maxMemory();
~~~

- `totalMemory()` returns the current heap capacity the JVM has committed.
- `freeMemory()` returns the free space within the committed heap region.
- `maxMemory()` returns the maximum heap limit.

Therefore:

~~~text
used = committed - free
used <= committed <= max
~~~

This is the general relationship for reading heap values. Actual values can change during GC and heap resizing.

Illustrative example:

~~~text
used      = 420 MiB
committed = 768 MiB
reserved  = 2 GiB
max       = 2 GiB
~~~

The application is using about 420 MiB for objects; the JVM has committed 768 MiB and can expand the heap up to a maximum of 2 GiB. `reserved` should not be interpreted as 2 GiB of physical RAM currently being consumed.

## 3. Two key options: -Xms and -Xmx

### 3.1. -Xms: initial and minimum heap

`-Xms` sets the initial heap size and the minimum heap level the JVM maintains while running.

Example:

~~~sh
java -Xms256m -jar app.jar
~~~

The JVM starts with a minimum heap of 256 MiB. If `-Xms` is not set, the JVM chooses the initial size based on ergonomics and the environment.

### 3.2. -Xmx: maximum heap

`-Xmx` sets the maximum limit of the Java heap.

Example:

~~~sh
java -Xmx2g -jar app.jar
~~~

The JVM cannot expand the Java heap beyond 2 GiB. If the application needs more heap and GC cannot reclaim enough objects, allocation can fail and throw `OutOfMemoryError: Java heap space`.

### 3.3. Combining Xms and Xmx

Example:

~~~sh
java -Xms512m -Xmx2g -jar app.jar
~~~

The initial/minimum heap is 512 MiB and can grow up to 2 GiB.

| Configuration | Behavior |
|---|---|
| `-Xms256m -Xmx2g` | Heap can grow from 256 MiB to 2 GiB |
| `-Xms2g -Xmx2g` | Initial, minimum, and maximum heap are all 2 GiB |
| Neither set | JVM chooses values automatically based on ergonomics and the environment |

Setting `-Xms` equal to `-Xmx` is commonly used for services with steady load and a clear RAM budget. This configuration reduces heap expansion and shrinking, though it also makes the JVM hold the full heap size from the start.

If you need to reduce footprint when the application is idle or when running multiple JVMs on the same host, you can keep `-Xms` lower than `-Xmx`. GC can resize the heap within the allowed range according to the collector's goals.

The suffixes `k`, `m`, and `g` specify size units. For example, `-Xms512m`, `-Xmx2g`.

## 4. Automatic heap selection via JVM ergonomics

If `-Xms` and `-Xmx` are not specified, HotSpot uses ergonomics to choose initial and maximum values based on the runtime environment.

In JDK 24, the key default percentage options are:

| Option | Default | Meaning |
|---|---:|---|
| `-XX:InitialRAMPercentage` | 1.5625% | Percentage of RAM used to calculate the initial heap |
| `-XX:MaxRAMPercentage` | 25% | Percentage of RAM used to calculate the maximum heap limit |
| `-XX:MinRAMPercentage` | 50% | Maximum percentage used for the heap in environments with very small RAM |

`MinRAMPercentage` has a misleading name: it is not the minimum heap percentage. It is the maximum percentage allocated to the heap for small heaps, around 125 MiB according to the JDK documentation.

The JVM determines the maximum RAM used for heap calculation based on the smaller of physical memory and the environment limits detected by the JVM. As a result, the same application can receive different maximum heap sizes when running on a laptop, a server, or in a container.

You can inspect the current flags:

~~~sh
java -XX:+PrintFlagsFinal -version
~~~

Filter heap-related flags on Linux/macOS:

~~~sh
java -XX:+PrintFlagsFinal -version 2>&1 | grep -E 'InitialHeapSize|MaxHeapSize|InitialRAMPercentage|MaxRAMPercentage|MaxRAM'
~~~

On Windows PowerShell:

~~~powershell
java -XX:+PrintFlagsFinal -version | Select-String 'InitialHeapSize|MaxHeapSize|InitialRAMPercentage|MaxRAMPercentage|MaxRAM'
~~~

### 4.1. Tuning heap by RAM percentage

For example, setting the maximum heap to 60% of the RAM the JVM is allowed to use for sizing:

~~~sh
java -XX:MaxRAMPercentage=60 -jar app.jar
~~~

Setting the initial heap to 15%:

~~~sh
java -XX:InitialRAMPercentage=15 -XX:MaxRAMPercentage=60 -jar app.jar
~~~

These percentages are inputs to ergonomics. Verify the actual `InitialHeapSize` and `MaxHeapSize` using `VM.flags` or `PrintFlagsFinal`.

`-XX:MaxRAM` can be used to set the input RAM limit for heap sizing calculations. For example:

~~~sh
java -XX:MaxRAM=512m -XX:InitialRAMPercentage=12.5 -XX:MaxRAMPercentage=50 -XshowSettings:vm -version
~~~

In this test case:

- MaxRAM is set to 512 MiB.
- InitialRAMPercentage is 12.5%, corresponding to an InitialHeapSize of 64 MiB.
- MaxRAMPercentage is 50%, corresponding to a MaxHeapSize of 256 MiB.

`MaxRAM` does not set a hard OS-level memory limit for the process. It only adjusts the RAM amount the JVM uses as the basis for ergonomics. Process/container limits are still enforced by the operating system or platform.

## 5. Heap sizing in Docker and Kubernetes

When running the JVM inside a Linux container, the JVM can read the container's memory and CPU limits to select resources. In JDK 24, `UseContainerSupport` is enabled by default on Linux.

For example, a container has a 2 GiB memory limit. The JVM uses `MaxRAMPercentage` to compute the heap limit from the RAM it detects from the environment. With the default 25%, the maximum heap can be around 512 MiB if the 2 GiB limit is the basis for sizing.

Do not assume the heap is always allowed to occupy all container memory. The container must also hold:

- Metaspace and code cache.
- Thread stacks.
- Direct buffers and native memory.
- Internal GC/JVM structures.
- Native libraries and memory mappings.
- Auxiliary processes or sidecars if they share the memory budget at the pod/host level.

Illustrative example: a container has a 2 GiB limit and you have measured that about 512 MiB is needed for native memory plus headroom. The remaining budget for maximum heap is about 1.5 GiB. In that case, you can consider:

~~~sh
java -Xms512m -Xmx1536m -jar app.jar
~~~

This is only a budget example, not a universal formula for every application. Measure non-heap/native memory under real load; if actual usage is higher, lower Xmx or increase the memory limit.

### 5.1. Checking container support

You can enable logging to see how the JVM detects container limits:

~~~sh
java -Xlog:os+container=trace -XX:+PrintFlagsFinal -version
~~~

Inspect the flags:

~~~sh
java -XX:+PrintFlagsFinal -version | grep -E 'UseContainerSupport|MaxRAM|MaxRAMPercentage|MaxHeapSize'
~~~

On JDK 24, `UseContainerSupport` applies only to Linux. If the JVM fails to detect container limits, the heap may be calculated from the host's RAM and exceed the container budget. Check logs and container metrics when deploying in this environment.

Do not apply `-XX:MaxRAMPercentage` mechanically. The right percentage depends on your heap live set, native memory, thread count, direct buffers, sidecars, and actual container limits.

## 6. Budgeting memory before setting Xmx

A practical approach is to start from the process/container memory limit and subtract everything not intended for the Java heap.

~~~text
Process / container memory limit
       |
       +-- Native memory, metaspace, code cache
       |
       +-- Thread stacks and direct buffers
       |
       +-- GC/JVM structures and libraries
       |
       +-- Safety headroom
       |
       v
Maximum budget available for Java heap
~~~

You can use an estimation formula:

~~~text
Heap budget <= Process memory limit
               - measured non-heap/native usage
               - safety headroom
~~~

Example:

| Component | Illustrative budget |
|---|---:|
| Container limit | 2048 MiB |
| Native, metaspace, stacks, direct buffers | 300 MiB |
| JVM/GC overhead and libraries | 100 MiB |
| Headroom for load fluctuations | 200 MiB |
| Remaining for heap | 1448 MiB |

In this example, an Xmx of around 1.4 GiB can be a starting point for testing. Afterward, run a representative workload and verify that the heap has enough room for the live set, allocation bursts, and GC.

Do not choose Xmx based solely on total host RAM. If multiple JVMs run on the same host, each process needs its own budget share, including native memory.

## 7. Choosing Xms and Xmx by workload

### 7.1. Steady-load services

If a service has a steady load, a clear memory budget, and you want to avoid heap resizing, you can set Xms close to or equal to Xmx.

~~~sh
java -Xms1g -Xmx1g -jar service.jar
~~~

Ensure the container has enough memory for the 1 GiB heap plus all native/non-heap usage and headroom.

### 7.2. Variable-load applications

If an application has idle periods and traffic spikes, set Xms lower than Xmx to give the JVM room to expand.

~~~sh
java -Xms256m -Xmx1536m -jar worker.jar
~~~

Monitor committed heap, GC pauses, and RSS to confirm that heap expansion/shrinking does not cause issues.

### 7.3. Batch jobs

Batch jobs may require a large heap during a data-processing phase. Size the heap based on the largest batch size, the number of objects retained simultaneously, the degree of streaming, and the number of parallel workers.

If a batch can be split or processed via streaming, reducing the number of concurrently live objects can be more effective than simply increasing Xmx.

### 7.4. Cache-heavy applications

Caches keep objects reachable so GC cannot reclaim them. If a cache occupies most of the heap, configure cache size limits, TTL, or an eviction policy. Increasing Xmx only delays the problem when a cache grows without bound.

## 8. Measuring heap live set and allocation before sizing

Heap sizing should be based on metrics under a representative workload:

- Heap used and committed over time.
- Heap occupancy after GC cycles.
- Live set: data that remains reachable after GC reclaims dead objects.
- Allocation rate: volume of objects allocated over time.
- Promotion rate: objects promoted to the old generation.
- GC pause frequency and duration.
- Full GC count and trigger reasons.
- Process RSS/container memory usage.
- Request latency, throughput, and error rate.

High heap usage while a workload is running is not necessarily a problem. What matters is whether GC reclaims enough memory, whether the live set is stable, and whether the heap has enough headroom for the next allocation burst.

If heap usage after each GC keeps growing under an equivalent workload, investigate retained object references or an ever-growing cache. Increasing Xmx does not fix a memory leak; it only extends the time before the heap fills up.

Do not rely on a single measurement or a brief heap spike to set a permanent configuration. Collect data across multiple load cycles, including peak traffic and batch jobs.

## 9. Inspecting the current heap with jcmd

Find the JVM PID:

~~~sh
jcmd -l
~~~

View current flags:

~~~sh
jcmd <pid> VM.flags
~~~

Look for `InitialHeapSize` and `MaxHeapSize` along with the active collector.

View heap information:

~~~sh
jcmd <pid> GC.heap_info
~~~

A G1 output might look like:

~~~text
garbage-first heap   total reserved 98304K, committed 65536K, used 42429K
  region size 1024K, 2 young (2048K), 1 survivors (1024K)
Metaspace       used 145K, committed 384K, reserved 1114112K
~~~

Numbers vary by JVM and workload. Read the reserved, committed, and used columns accurately; Metaspace is reported separately because it is not part of the Java heap.

View JVM information:

~~~sh
jcmd <pid> VM.info
~~~

Diagnostic commands must be run on the same machine and as the same effective user/group that started the JVM. If attaching fails, check the PID, user, and permissions.

### 9.1. Histograms and heap dumps for deeper investigation

When you need to find which classes occupy the most heap:

~~~sh
jcmd <pid> GC.class_histogram
~~~

When you need to analyze the object graph and references:

~~~sh
jcmd <pid> GC.heap_dump filename=heap.hprof
~~~

These are high-impact operations. A histogram can take time depending on heap size; a heap dump may trigger a Full GC and produce a large file. Run them only when you have a clear investigation goal, sufficient disk space, and can tolerate the latency impact.

Open the `.hprof` file with a heap analysis tool such as Eclipse Memory Analyzer or JDK Mission Control compatible with the file format and version.

## 10. Practical example: measuring max heap and inspecting with jcmd

The following Java example retains 8 arrays of 4 MiB each. The program prints the heap limit reported by the JVM and the total retained payload size. The `--hold` argument keeps the JVM running for an extra 30 seconds so you can attach with `jcmd`.

Create `HeapSizingProbe.java`:

~~~java
import java.util.ArrayList;
import java.util.List;

public class HeapSizingProbe {
    private static final int MIB = 1024 * 1024;
    private static final List<byte[]> retained = new ArrayList<>();

    public static void main(String[] args) throws InterruptedException {
        Runtime runtime = Runtime.getRuntime();
        System.out.println("maxHeapMiB=" + runtime.maxMemory() / MIB);

        for (int i = 0; i < 8; i++) {
            retained.add(new byte[4 * MIB]);
        }

        System.out.println("retainedMiB=" + (retained.size() * 4));

        if (args.length > 0 && "--hold".equals(args[0])) {
            System.out.println("heap-probe-ready");
            Thread.sleep(30_000);
        }
    }
}
~~~

Compile with Java 17 or later:

~~~sh
mkdir -p out
javac --release 17 -d out HeapSizingProbe.java
~~~

Run with a 32 MiB initial heap and 96 MiB maximum heap:

~~~sh
java -Xms32m -Xmx96m -cp out HeapSizingProbe
~~~

Exact stdout:

~~~text
maxHeapMiB=96
retainedMiB=32
~~~

The output confirms that `Runtime.maxMemory()` reflects the 96 MiB limit and the program retains 32 MiB of payload. Actual used heap also includes objects, collections, and auxiliary JVM structures.

To inspect a running JVM, add `--hold`:

~~~sh
java -Xms32m -Xmx96m -cp out HeapSizingProbe --hold
~~~

Stdout:

~~~text
maxHeapMiB=96
retainedMiB=32
heap-probe-ready
~~~

Open a second terminal and find the PID:

~~~sh
jcmd -l
~~~

View flags:

~~~sh
jcmd <pid> VM.flags
~~~

Inspect the heap:

~~~sh
jcmd <pid> GC.heap_info
~~~

In testing with JDK 24.0.2, the program compiled with `javac --release 17` and printed the exact two stdout lines in normal mode. In `--hold` mode, `jcmd VM.flags` confirmed `InitialHeapSize=33554432` and `MaxHeapSize=100663296`; `GC.heap_info` reported G1 heap reserved 96 MiB, committed 55 MiB, and used around 42 MiB at the time of measurement. Used and committed values can vary between runs.

You can test percentage-based sizing with:

~~~sh
java -XX:MaxRAM=512m -XX:InitialRAMPercentage=12.5 -XX:MaxRAMPercentage=50 -XshowSettings:vm -version
~~~

In JDK 24.0.2, this command reported a max heap of 256 MiB; `PrintFlagsFinal` confirmed an initial heap of 64 MiB and a max heap of 256 MiB.

## 11. Using GC logs to verify heap sizing

Enable unified GC logging:

~~~sh
java -Xms256m -Xmx1536m "-Xlog:gc*:file=gc.log:time,uptime,level,tags" -jar app.jar
~~~

GC logs help you observe:

- Which collector the JVM selected.
- Heap occupancy before and after each GC.
- Pause duration and GC type.
- How heap capacity/committed size changes.
- Whether Full GCs occur.
- Allocation failures or evacuation failures.
- Signs of continuous GC reclaiming very little memory.

An illustrative log line:

~~~text
[info][gc] GC(12) Pause Young (Normal) 512M->128M(1024M) 18.5ms
~~~

Common interpretation:

- `512M`: heap occupancy before GC.
- `128M`: occupancy after GC.
- `1024M`: heap capacity at the time of the event.
- `18.5ms`: pause duration.

This is a format illustration; actual log output varies by collector and JDK version.

If the heap frequently approaches Xmx, GC does not free enough objects, or many Full GCs occur, investigate the live set, allocation rate, and potential leaks. If the heap still has plenty of headroom yet pauses remain long, the cause may relate to collector configuration, object graph, humongous allocations, or workload rather than simply lacking Xmx.

## 12. Heap sizing with G1 GC

G1 is HotSpot's default collector on modern server-class configurations and is designed to balance throughput with relatively predictable pause times.

G1 automatically tunes the young generation and collection work based on application behavior. When sizing with G1:

- Start with ergonomic defaults.
- Set Xmx if you need to cap the heap within a budget.
- You can set a pause target with `-XX:MaxGCPauseMillis` when you have clear latency requirements.
- Avoid pinning the young generation with `-Xmn` or `-XX:NewRatio` unless data proves it is necessary.
- Re-measure throughput and pauses after each change.

Example:

~~~sh
java -Xms512m -Xmx2g -XX:+UseG1GC -XX:MaxGCPauseMillis=200 -jar app.jar
~~~

`MaxGCPauseMillis=200` is a target/hint for the collector, not a guarantee that every pause will be under 200 ms. A tighter pause target can cause GC to run more frequently and reduce throughput.

If G1 does not meet your requirements, review the GC logs and tuning guide before changing multiple flags at once.

## 13. Distinguishing insufficient heap from a memory leak

Both situations can cause `OutOfMemoryError`, but their remedies differ.

| Symptom | Heap too small | Memory leak or retaining objects too long |
|---|---|---|
| Live set after GC | Stable but close to the limit | Steadily increases across comparable cycles |
| GC | Runs frequently due to low headroom | Reclaims less and less even as GC runs |
| Heap usage | Fluctuates near high levels | Post-GC baseline rises over time |
| Histogram/heap dump | Object counts may remain stable | Specific classes/collections grow continuously |
| Remediation | Consider raising Xmx or reducing allocation/live set | Find retaining references, fix lifecycle/cache |

An application can have both an undersized heap and a memory leak. Compare multiple snapshots or recordings taken at different times under comparable workloads.

## 14. Types of OutOfMemoryError related to sizing

| Message | Memory area / common cause | Investigation direction |
|---|---|---|
| `Java heap space` | Not enough Java heap left to allocate objects | Check Xmx, live set, allocation rate, histogram, and heap dump |
| `GC overhead limit exceeded` | JVM spends most of its time in GC while reclaiming very little memory | Check live set, leaks, allocation pressure, and GC logs |
| `Metaspace` | Class metadata exceeds limit or classloaders retain classes too long | Check class loading, classloaders, and Metaspace |
| `Direct buffer memory` | Insufficient memory for off-heap direct buffers | Check direct buffer lifecycle and direct memory limits |
| `unable to create native thread` | Insufficient native resources or thread/process limit exceeded | Check thread count, stack size, and OS/container limits |

Do not increase Xmx to handle every kind of OutOfMemoryError. For example, `Metaspace` and `Direct buffer memory` reside outside the Java heap.

You can enable automatic heap dumps on OOME:

~~~sh
java -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=./dumps -Xmx1g -jar app.jar
~~~

Create the target directory beforehand, and ensure the JVM has write permissions and sufficient disk space. Heap dumps may contain sensitive data; protect the files and delete them according to your retention policy.

## 15. Practical heap sizing workflow

1. Identify the memory limits of the host, container, and the budget allocated to each JVM.
2. Estimate native/non-heap memory and the safety headroom to reserve.
3. Run a representative workload to collect heap usage, live set, allocation rate, and GC behavior.
4. Check current Xms/Xmx using `jcmd <pid> VM.flags`.
5. Check committed/used heap using `jcmd <pid> GC.heap_info`.
6. Collect GC logs across peak traffic, batch jobs, and idle periods.
7. Choose Xmx based on live set, burst headroom, and process/container limits.
8. Choose Xms based on startup footprint, load stability, and memory budget.
9. Change a small group of flags at a time, keep the workload constant, and re-measure.
10. Compare GC pauses, throughput, latency, process RSS, and container memory.
11. Monitor after deployment to detect differences between production load and tests.
12. Investigate memory leaks if the post-GC live set grows continuously.

### Checklist

- [ ] Distinguished the Java heap from total process memory.
- [ ] Understood used, committed, reserved, and max heap.
- [ ] Identified current Xms and Xmx.
- [ ] Checked MaxRAM and RAM percentage flags.
- [ ] Verified whether the JVM detects container limits.
- [ ] Budgeted for metaspace, thread stacks, direct buffers, and native memory.
- [ ] Measured live set and allocation rate under a representative workload.
- [ ] Collected GC logs across peak load.
- [ ] Distinguished insufficient heap from a memory leak.
- [ ] Verified GC pauses, throughput, and latency after changes.
- [ ] Reserved headroom for load fluctuations and process/container overhead.
- [ ] Protected heap dumps and diagnostic files.

Effective heap sizing starts with the live set and a realistic memory budget. Use Xms to control the initial/minimum heap, Xmx or RAM percentage flags to cap the maximum heap, and verify with `jcmd`, GC logs, and a representative workload. When the heap has enough room for live objects and allocation bursts while still leaving RAM for native memory, the JVM can maintain more stable GC behavior, latency, and throughput.
