# Scanning JARs with jdeprscan

**`jdeprscan`** is a command-line tool included with the JDK for scanning class files, class directories, or JAR files to find usages of Java APIs marked as deprecated. It is especially useful when inspecting compiled libraries or applications where full source code is no longer available, or when preparing to upgrade to a new JDK version.

When you pass a JAR to `jdeprscan`, the tool reads the class files inside the archive and reports any references it detects to deprecated Java platform APIs. It does not modify bytecode, replace legacy APIs, or automatically verify that an application is compatible with a newer JDK.

## 1. Why Scan JARs?

Java maintains compatibility over long periods, but some older APIs may be superseded, marked deprecated, or scheduled for removal in a future release.

A JAR may have been built a long time ago and still contain references to deprecated APIs. If a development team only inspects the current source code, they may miss:

- Pre-compiled internal libraries.
- Dependencies packaged with the application.
- Class files generated by a separate build process.
- Deprecated APIs used in source code that is no longer compiled regularly.
- APIs marked *deprecated for removal* that risk disappearing in a future JDK.

Scanning JARs helps compile a list of locations to review before upgrading the JDK, replacing dependencies, or releasing a new version.

Common use cases:

- Checking an application's JAR before upgrading the JDK.
- Inspecting pre-compiled internal or third-party libraries.
- Finding deprecated APIs in release artifacts.
- Finding APIs marked for removal.
- Checking multiple JARs in a CI pipeline or ahead of a migration.

## 2. What Does jdeprscan Check?

`jdeprscan` analyzes bytecode and matches detected references against the list of deprecated Java platform APIs for the selected version.

The tool accepts the following input types:

- A directory containing a package hierarchy and class files.
- A JAR file.
- An individual class file.
- A fully qualified class name.

The tool focuses on deprecated Java SE/JDK APIs. It is not a general-purpose scanner for every `@Deprecated` annotation in third-party libraries or an organization's own source code.

Keep these distinctions in mind:

| Tool | Primary Input | Purpose |
| --- | --- | --- |
| `jdeprscan` | JAR, class file, class directory, or class name | Scans bytecode for usage of deprecated JDK APIs |
| `javac -Xlint:deprecation` | Source code being compiled | Warns when source code uses deprecated APIs recognized by the compiler |
| `javadoc` | Source code and documentation comments | Generates API documentation |
| `jdeps` | Class file, JAR, or module | Analyzes dependencies between classes, packages, and modules |

`jdeprscan` is useful when an artifact has already been built and you want to inspect the binary itself. If source code is available, combine it with compiler warnings to catch issues during the build process.

## 3. Checking Installation and Viewing Help

`jdeprscan` is a JDK tool. Verify your environment:

```bash
java -version
javac -version
jdeprscan --version
```

View the full syntax:

```bash
jdeprscan --help
```

If the terminal does not recognize the command:

- Verify that a full JDK is installed on the machine.
- Check that the JDK's `bin` directory is in `PATH`.
- Check that `JAVA_HOME` points to the JDK root directory.
- Open a new terminal after changing environment variables.

You can also invoke the tool directly from the JDK's `bin` directory. The list of releases supported by `--release` depends on the `jdeprscan` version; run `jdeprscan --help` on the exact JDK you are using.

## 4. Basic Syntax for Scanning JARs

Syntax:

```text
jdeprscan [options] {dir|jar|class} ...
```

Scan a single JAR:

```bash
jdeprscan app.jar
```

Scan multiple JARs in a single invocation:

```bash
jdeprscan app.jar lib/helper.jar lib/legacy-client.jar
```

Select an API version to check against:

```bash
jdeprscan --release 17 app.jar
```

Enable verbose processing output:

```bash
jdeprscan --verbose app.jar
```

Where:

- `app.jar`: the JAR to inspect.
- `--release 17`: checks against the deprecated API set of Java SE 17.
- `--verbose`: displays additional details during processing.

`--release` selects the API version used to evaluate deprecation status. It does not recompile the JAR, does not change the class file major version, and does not turn the JAR into an artifact compatible with that version.

If `--release` is omitted, the tool uses the API set of the JDK running `jdeprscan`.

## 5. Complete Example: Creating a JAR That Uses a Deprecated API

The example below uses `java.util.Date.getYear()`, a deprecated method. The goal is to build a JAR containing that reference and scan it with `jdeprscan`.

Project structure:

```text
project/
  src/
    com/
      example/
        audit/
          LegacyApiUse.java
  out/
  dist/
```

Create the file **`src/com/example/audit/LegacyApiUse.java`**:

```java
package com.example.audit;

import java.util.Date;

public final class LegacyApiUse {
    private LegacyApiUse() {
    }

    public static int legacyYear(Date date) {
        return date.getYear();
    }
}
```

The `Date.getYear()` method returns the year minus 1900 and is deprecated. This example intentionally keeps this call to produce bytecode that `jdeprscan` can detect.

### Step 1: Compile the class

**Windows PowerShell:**

```powershell
New-Item -ItemType Directory -Force out, dist | Out-Null
javac --release 17 -Xlint:deprecation -d out src/com/example/audit/LegacyApiUse.java
```

**macOS/Linux:**

```bash
mkdir -p out dist
javac --release 17 -Xlint:deprecation -d out src/com/example/audit/LegacyApiUse.java
```

The compiler emits a warning about using a deprecated API. Use `-Xlint:deprecation` to request more detailed diagnostics.

The class file is generated at:

```text
out/
  com/
    example/
      audit/
        LegacyApiUse.class
```

### Step 2: Package into a JAR

Run:

```bash
jar --create --file dist/legacy-app.jar -C out .
```

Inspect the contents:

```bash
jar --list --file dist/legacy-app.jar
```

The listing should include:

```text
com/example/audit/LegacyApiUse.class
```

### Step 3: Scan the JAR

Check against Java 17 APIs:

```bash
jdeprscan --release 17 dist/legacy-app.jar
```

The tool reports the class containing the reference to the deprecated method. Sample output looks like:

```text
class com/example/audit/LegacyApiUse uses deprecated method java/util/Date.getYear()I
```

The exact formatting may vary by JDK version. The key information is the class containing the reference and the deprecated API identified.

This example only requires compiling the class and packaging the JAR; you do not need to run the program for `jdeprscan` to detect the reference in bytecode.

## 6. Selecting an API Version with --release

The `--release` option lets you choose the Java SE version used as the baseline for checking:

```bash
jdeprscan --release 17 app.jar
```

This is useful when:

- The application is built to support Java 17.
- You want to evaluate deprecation status against a specific release's APIs.
- You want to compare results when raising the baseline from Java 17 to Java 21 or a newer release.
- You want to check APIs deprecated in a target version rather than only against the JDK installed on your machine.

Comparison example:

```bash
jdeprscan --release 17 app.jar
jdeprscan --release 21 app.jar
```

An API may have different deprecation status or metadata across releases. Therefore, scan results depend on the selected API version.

**Do not confuse `jdeprscan --release` with `javac --release`:**

- `javac --release 17` restricts the language features, bytecode version, and platform APIs used by the compiler during compilation.
- `jdeprscan --release 17` selects the Java 17 deprecated API set to check against when scanning a binary.

If the installed tool does not support the release you need to check, use a JDK version that supports that release or inspect the supported list with `jdeprscan --help`.

## 7. Finding Only APIs Deprecated for Removal

Some APIs are marked not only as deprecated, but also *for removal*. This indicates that the API may be removed in a future release.

Example in source code:

```java
@Deprecated(since = "1.2", forRemoval = true)
public void oldOperation() {
    // ...
}
```

The `--for-removal` option limits scan results or the API listing to APIs marked for removal in the selected API set.

Scan a JAR:

```bash
jdeprscan --for-removal app.jar
```

Combine with a specific release:

```bash
jdeprscan --release 24 --for-removal app.jar
```

List APIs marked for removal:

```bash
jdeprscan --for-removal --list
```

Notes:

- `--for-removal` filters the results; it does not mean the tool removes APIs from the JAR.
- The for-removal status depends on the selected release.
- An API may be deprecated in an older release but only marked for removal in a newer release.
- Some older releases do not support combining with `--for-removal`; check `jdeprscan --help` for the limits of your version.

When planning a JDK upgrade, prioritize addressing for-removal findings because they represent a higher compatibility risk.

## 8. Listing Deprecated APIs with --list

The `--list` option displays the set of deprecated APIs known to the tool for the selected release. This is a listing mode, not a JAR scanning mode.

List for the current JDK:

```bash
jdeprscan --list
```

List for Java 17:

```bash
jdeprscan --release 17 --list
```

List only APIs marked for removal:

```bash
jdeprscan --for-removal --list
```

You can use this command to:

- Look up deprecated APIs in a specific release.
- Check whether an API is in the deprecated list.
- Identify which APIs are marked for removal.
- Understand why scan results change when changing `--release`.

Do not pass a JAR, class, or target directory when using `--list`; this mode only prints the API list and does not scan artifacts.

## 9. Scanning Class Directories and Individual Class Files

In addition to JARs, you can scan a directory containing class files:

```bash
jdeprscan --release 17 out
```

The tool processes classes in the package directory tree under the specified directory.

You can specify an individual class file:

```bash
jdeprscan --release 17 out/com/example/audit/LegacyApiUse.class
```

Or a fully qualified class name:

```bash
jdeprscan --release 17 com.example.audit.LegacyApiUse
```

For nested classes, the class name uses `$` as a separator, for example:

```bash
jdeprscan 'com.example.Outer$Inner'
```

Wrap names containing `$` in quotes so the shell does not interpret it as a variable.

Scanning a class directory is useful when you want to check compiler output before packaging a JAR. Scanning a JAR is useful when you want to inspect the exact artifact that will be released.

## 10. Resolving Dependencies with --class-path

When a scanned class references other types, `jdeprscan` may need to locate those dependent classes to resolve references. Use `--class-path` to provide the locations of dependency JARs or directories.

Example:

```text
project/
  app.jar
  lib/
    helper.jar
    common.jar
```

Scan the application JAR and provide dependencies:

```bash
jdeprscan --release 17 --class-path "lib/helper.jar;lib/common.jar" app.jar
```

On Windows, the classpath uses semicolons:

```powershell
jdeprscan --release 17 --class-path "lib\helper.jar;lib\common.jar" app.jar
```

On macOS/Linux, the classpath uses colons:

```bash
jdeprscan --release 17 --class-path "lib/helper.jar:lib/common.jar" app.jar
```

`--class-path` provides dependencies for type resolution. It does not mean all JARs on the classpath automatically become scan targets. If you want to check deprecated APIs inside `helper.jar`, pass that JAR as a separate scan argument:

```bash
jdeprscan --release 17 --class-path "lib/common.jar" app.jar lib/helper.jar
```

## 11. Commonly Used Options

| Option | Purpose |
| --- | --- |
| `--release <release>` | Selects the Java SE version providing the deprecated API set to check against |
| `--for-removal` | Scans or lists only APIs deprecated for removal |
| `--class-path <path>` | Provides search paths for dependencies to resolve classes |
| `--list` or `-l` | Lists deprecated APIs without scanning a target |
| `--verbose` or `-v` | Displays verbose processing information |
| `--version` | Prints the short version of the tool |
| `--full-version` | Prints the full version string |
| `--help` or `-h` | Displays help |

Combined example:

```bash
jdeprscan --release 17 --for-removal --verbose --class-path "lib/helper.jar" app.jar
```

The command above checks for APIs marked for removal against Java 17, enables verbose output, and provides a dependency for resolution.

## 12. Reading and Handling Scan Results

`jdeprscan` output typically indicates:

- The class in the artifact that uses a deprecated API.
- The member kind used, such as a method or field.
- The class/package name owning the deprecated API.
- The method/field name and JVM descriptor, if applicable.

Illustrative example:

```text
class com/example/audit/LegacyApiUse uses deprecated method java/util/Date.getYear()I
```

You can read the result as follows:

- `com/example/audit/LegacyApiUse`: the class in the JAR with the call to review.
- `java/util/Date`: the JDK class owning the API.
- `getYear()`: the deprecated method.
- `I`: the JVM descriptor indicating the method returns `int`.

When a finding is reported:

1. Identify the class in the artifact calling the API.
2. Locate the corresponding source code, if available.
3. Read the API documentation for the target release to understand why it was deprecated.
4. Check the recommended replacement API.
5. Update the source code or upgrade the dependency.
6. Rebuild the JAR.
7. Re-scan with the same release to compare results.

`jdeprscan` detects where references occur, but it does not automatically choose a replacement API suitable for your business logic. Replacing an API requires considering behavior, timezone, nullability, performance, and application compatibility.

## 13. Example: Replacing a Deprecated API

In the earlier example, `Date.getYear()` returns the year offset from 1900. With `java.util.Date`, you can migrate to `java.time` to obtain the year according to a calendar date and chosen timezone.

Example:

```java
package com.example.audit;

import java.time.LocalDate;
import java.time.ZoneId;
import java.util.Date;

public final class ModernDateUse {
    private ModernDateUse() {
    }

    public static int year(Date date) {
        return date.toInstant()
            .atZone(ZoneId.systemDefault())
            .toLocalDate()
            .getYear();
    }

    public static int fixedDateYear() {
        return LocalDate.of(2025, 1, 1).getYear();
    }
}
```

This code uses `java.time` instead of `Date.getYear()`. When converting temporal data, choose a timezone appropriate for your business requirements; `ZoneId.systemDefault()` depends on the host machine configuration and may not be suitable for systems that require a fixed timezone.

After replacing the API, recompile and build a new JAR:

```bash
javac --release 17 -d out src/com/example/audit/ModernDateUse.java
jar --create --file dist/modern-app.jar -C out .
jdeprscan --release 17 dist/modern-app.jar
```

If there are no remaining references to deprecated APIs in the scanned classes, the tool will not report any corresponding findings. This does not mean all application dependencies are free of deprecated APIs; scan all relevant artifacts according to your desired scope.

## 14. Limitations to Understand

`jdeprscan` is a static analysis tool operating on class files. Therefore:

- It does not run the application or check runtime execution paths.
- It does not replace unit tests or integration tests.
- It does not automatically fix deprecated APIs.
- It does not scan all dependency JARs simply because they appear in `--class-path`; pass each artifact you want to inspect separately.
- It focuses on deprecated Java/JDK platform APIs, not on inventorying every deprecated API in third-party libraries.
- Calls constructed dynamically via reflection, class/method names loaded from configuration, or dynamic class-loading mechanisms may not be detected as direct bytecode references.
- If dependencies needed for class resolution are missing, results may include unresolved-type notices; add the appropriate classpath and review warnings.

Accordingly, a scan with zero findings does not prove an application has zero risk when upgrading the JDK. Combine binary scanning with source code checks, dependency reviews, tests, and JDK migration guides.

## 15. Integrating JAR Scanning into CI

You can add `jdeprscan` after the artifact build step:

1. Build the application and dependencies.
2. Package the release JAR.
3. Run `jdeprscan --release <baseline> app.jar`.
4. Save the scan output as an artifact/log.
5. Review newly introduced deprecated APIs.
6. Scan with `--for-removal` to prioritize high-risk findings.
7. Fix source code or update dependencies.
8. Rebuild and re-scan before releasing.

Example check commands:

```bash
jdeprscan --release 17 --for-removal app.jar
jdeprscan --release 17 app.jar
```

Do not assume every matched finding automatically causes the `jdeprscan` process to return a non-zero exit code. If CI policy requires failing the build when deprecated APIs are detected, inspect the output with a script or also use `javac -Xlint:deprecation -Werror` during source compilation. Distinguish between tool errors, dependency resolution errors, and actual deprecated API findings.

## 16. Common Errors

| Symptom | Common Cause | Resolution |
| --- | --- | --- |
| `jdeprscan` is not recognized | JDK is not installed or `PATH` lacks the `bin` directory | Check `JAVA_HOME` and `PATH` |
| No results even though source has warnings | The scanned JAR does not contain the newly built class, or the reference is not in the tool's recognized API list | Verify the right artifact with `jar --list` and select the appropriate release |
| API appears in one release but not another | Deprecation status changes across API releases | Use `--release` matching the baseline you want to evaluate |
| Cannot resolve dependencies | Required classpath is missing | Add `--class-path` |
| Scanned `app.jar` but did not see APIs in `helper.jar` | Dependencies do not automatically become scan targets | Pass `helper.jar` separately as an argument |
| Want for-removal APIs but results are too broad | For-removal filter is not enabled | Add `--for-removal` and choose the appropriate release |
| Used `--list` expecting to scan a JAR | `--list` only lists APIs | Remove `--list` and pass the JAR as a target |
| Command reports an invalid release | The current JDK does not support the selected release or the option combination is invalid | Check `jdeprscan --help` |
| Calls via reflection are not detected | API names are constructed or loaded dynamically at runtime | Inspect source/configuration and supplement with tests/runtime analysis |

## 17. Recommended JAR Scanning Workflow

When evaluating an application before a JDK upgrade:

1. Identify the main JAR and all dependencies that need inspection.
2. Determine the current Java baseline and the target JDK version for the upgrade.
3. Run `jdeprscan --release <baseline> app.jar` to establish a deprecated API baseline.
4. Scan each key dependency JAR; use `--class-path` to assist resolution.
5. Use `--for-removal` to find APIs at risk of removal.
6. Cross-reference findings with source code and the API documentation for the corresponding release.
7. Replace deprecated APIs or upgrade dependencies to fixed versions.
8. Rebuild artifacts and re-scan.
9. Enable compiler warnings `-Xlint:deprecation` and `-Werror` policy for source builds where appropriate.
10. Run tests on the target JDK to verify actual compatibility.

Store scan results alongside the JAR version, JDK version, and selected release so you can compare across builds.

## 18. Key Takeaways

- `jdeprscan` scans bytecode in JARs, class files, or directories to find usage of deprecated JDK APIs.
- Use `jdeprscan app.jar` to scan a JAR.
- Use `--release` to select the API version baseline for evaluation.
- Use `--for-removal` to focus on deprecated APIs scheduled for removal.
- Use `--list` to view the deprecated API list; this mode does not scan artifacts.
- Use `--class-path` to supply dependencies for class resolution.
- Dependencies must be passed separately if you want to scan those dependencies themselves.
- `jdeprscan` does not modify JARs and does not replace testing or runtime verification.
- Combine binary scanning, compiler warnings, dependency updates, and testing on the target JDK to reduce upgrade risk.

By incorporating `jdeprscan` into the artifact verification workflow, development teams can detect deprecated JDK API usage early, prioritize for-removal APIs, and prepare for controlled Java upgrades.
