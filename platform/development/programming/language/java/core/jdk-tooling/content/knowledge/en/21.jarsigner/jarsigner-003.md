# Verifying JAR Signatures with `jarsigner`

`jarsigner` is a JDK tool used to sign and verify digital signatures of JAR files. When verifying a signed JAR, the tool confirms that the signature was generated by the key corresponding to the signer's certificate, checks the digests of signed entries, and reports warnings about certificates, trust chains, timestamps, algorithms, and unprotected entries.

Basic verification command:

~~~text
jarsigner -verify application.jar
~~~

In a release workflow, you should perform a more detailed check:

~~~text
jarsigner -verify -strict -verbose -certs application.jar
~~~

Interpreting the output requires separating three questions:

1. **Integrity:** Do the signed files still match their digests at the time of signing?
2. **Certificate:** Is the signer certificate valid, does it have an appropriate code-signing purpose, and is the certificate chain validated against the trust policy?
3. **Identity:** Does the certificate belong to the exact publisher expected by the organization?

A mathematically valid signature does not by itself prove that the publisher is trustworthy. You must verify the fingerprint, certificate identity, and trust chain using an independent source.

The toolchain tested for this article is `jarsigner 24.0.2`. Syntax and algorithm policies may change across JDK versions; check `jarsigner --help`, `keytool -printcert -help`, and the documentation for the exact toolchain being deployed.

## 1. How Digital Signatures Work in a JAR

Digital signatures use a private key to sign data and the corresponding public key to verify it. The private key must be kept secret; a digital certificate binds the public key to the subject's identity under a certification system.

When signing a JAR, `jarsigner` adds information to the `META-INF` directory:

~~~text
application.jar
  META-INF/
    MANIFEST.MF
    RELEASE.SF
    RELEASE.RSA
  com/example/App.class
  config/application.properties
~~~

Key components:

| Component | Role |
|---|---|
| `META-INF/MANIFEST.MF` | Contains metadata and digests of signed entries |
| `RELEASE.SF` | Signature file containing digests of the manifest or manifest sections |
| `RELEASE.RSA` | Signature block containing the signature of the `.SF` file and the signer's certificate/certificate chain |
| `.DSA`, `.EC` | Signature block extensions that may be used depending on key type and algorithm |

The name `RELEASE` is just an example. The actual name is typically derived from the signing alias or from the `-sigfile` option.

Signing and verification flow:

~~~text
JAR entries
    |
    v
Manifest: digest for each signed entry
    |
    v
Signature file (.SF): digest of manifest/sections
    |
    v
Private key signs the .SF file
    |
    v
Signature block (.RSA / .DSA / .EC)
    |
    v
Certificate and signature are stored in JAR
    |
    v
jarsigner -verify
    |
    +--> Verify signature block and .SF
    +--> Compare .SF digests with manifest
    +--> Recalculate entry digests
    +--> Check algorithm constraints
    +--> Report certificate and timestamp warnings
~~~

If the content of a signed entry is modified, the recalculated digest no longer matches the manifest and verification fails. If an entry is added after signing, that entry may not be covered by the original signature and will be reported as unsigned.

## 2. Distinguishing Signature Integrity from Signer Trust

When running `jarsigner -verify`, the tool can verify the signature using the public key in the certificate packaged with the JAR. This answers whether the signed data matches the signature.

Trusting the signer requires additional checks:

- Does the certificate match the expected organization or publisher identity?
- Does the fingerprint match the value published through an independent channel?
- Does the certificate chain lead to a CA/trust anchor accepted by the organization?
- Was the certificate valid at the time of signing according to the timestamp?
- Do Key Usage or Extended Key Usage allow code signing?
- Has the certificate or key been revoked according to the checking policy?
- Do the signing algorithm and key length meet current security policies?

A self-signed certificate can produce a mathematically valid signature for a test JAR, but it does not establish a publisher identity verified by a trusted CA. Therefore, the `jar verified` result must be read together with the warnings and certificate information.

Do not rely on the alias name alone to identify a publisher. An alias is only an entry name in the verifier's keystore; it is not a signed identity inside the JAR.

## 3. Syntax and Verification Options

Verification syntax:

~~~text
jarsigner -verify [options] jar-file [alias...]
~~~

Commonly used options:

| Option | Purpose |
|---|---|
| `-verify` | Verify the signature and integrity of the JAR |
| `-strict` | Convert severe warnings into errors via the exit code |
| `-verbose` | Display detailed information per entry |
| `-verbose:all` | Display details for each entry and signer information |
| `-verbose:grouped` | Group entries by signer |
| `-verbose:summary` | Summarize entries by signer |
| `-certs` | Display certificate information when combined with `-verify` and `-verbose` |
| `-keystore file` | Specify a keystore to match certificates against aliases |
| `-revCheck` | Enable certificate revocation checking via OCSP/CRL |
| `-version` | Display tool version |
| `-help` | Display help |

Quick verification example:

~~~text
jarsigner -verify application.jar
~~~

Inspecting each entry and signer:

~~~text
jarsigner -verify -verbose -certs application.jar
~~~

Strict verification:

~~~text
jarsigner -verify -strict -verbose -certs application.jar
~~~

If you need to confirm that the JAR was signed by an expected alias in the keystore:

~~~text
jarsigner -verify -strict -verbose -certs -keystore release-signers.p12 application.jar release-signer
~~~

When passing aliases after the JAR filename, `jarsigner` checks whether the certificate used to verify the entries matches one of the specified aliases in the keystore. If you need to match against multiple allowed signers, pass the list of aliases according to the tool's syntax.

`-keystore` in verify mode can help display the alias corresponding to a certificate. Do not treat the mere presence of a certificate in an arbitrary keystore as sufficient proof to accept a publisher; you must still apply the trust policy and verify the fingerprint.

## 4. Reading `-verbose` Output

When using `-verbose`, the output may display symbols next to each entry:

| Symbol | Meaning |
|---|---|
| `s` | The entry's signature was verified |
| `m` | The entry is listed in the manifest |
| `k` | At least one certificate matches an entry in the keystore |

Illustrative example:

~~~text
s k     1200 Mon Jan 12 10:00:00 UTC 2026 META-INF/MANIFEST.MF
smk     2450 Mon Jan 12 10:00:00 UTC 2026 com/example/App.class
smk      620 Mon Jan 12 10:00:00 UTC 2026 config/application.properties

- Signed by "CN=Example Release Signer, O=Example"
    Digest algorithm: SHA-384
    Signature algorithm: SHA384withRSA, 3072-bit key

jar verified.
~~~

This is illustrative output; dates, sizes, certificate names, algorithms, and line grouping depend on the actual artifact, JDK, and signer.

Key points to understand:

- `s` indicates the entry signature was verified.
- `m` indicates the entry has a section in the manifest.
- `k` indicates the certificate matches an entry in the checked keystore.
- `k` does not by itself prove that the certificate is from a trusted CA or the expected publisher.
- The `jar verified` line does not replace reading the warnings at the end of the output.

When a JAR has multiple signers, `-certs` helps inspect the certificate of each signer. Use `-verbose:summary` when you need a concise report, or `-verbose:all` when you need to trace every entry.

## 5. Verifying Individual Entry Signatures

JAR verification consists of these main steps:

1. Verify the signature in the signature block against the `.SF` file.
2. Compare the digests in the `.SF` file with the corresponding sections in the manifest.
3. Read each signed entry, recalculate its digest, and compare it with the value in the manifest.
4. Check whether any algorithm is disabled under the JDK's security policy.

If a signed class or resource is modified after signing, the digest comparison step will fail.

### 5.1. JAR Modified After Signing

Suppose `application.jar` has been signed. If someone modifies the contents of `com/example/App.class`, the digest will not match the signed value and `jarsigner -verify` will report a verification error.

If a new file is added after signing, the new file may not be protected by the original signature. In that case, the JAR may still contain validly signed entries while simultaneously having unsigned entries.

For release artifacts, check both conditions:

- No signed entry has been modified.
- No unexpected unsigned entry is present.

Do not simply look for the `jar verified` line and ignore warnings about unsigned entries.

### 5.2. Inspecting `META-INF` Contents

Use `jar` to list entries:

~~~text
jar --list --file application.jar
~~~

Focus on:

- `META-INF/MANIFEST.MF`
- `.SF` files
- Signature block files `.RSA`, `.DSA`, or `.EC`
- Classes/resources that must be signed
- Unfamiliar entries or files added after the signing process

`jar --list` only displays the archive contents; it does not verify signatures. Use `jarsigner -verify` to check integrity.

## 6. Inspecting Certificates with `keytool`

`jarsigner -certs` displays certificates during verification. `keytool` provides dedicated commands to inspect certificate and keystore details.

### 6.1. Reading Certificates Embedded in a JAR

~~~text
keytool -printcert -jarfile application.jar -v
~~~

This command prints the certificate found in the signed JAR, including subject, issuer, validity period, algorithms, and fingerprints.

Use the fingerprint to compare against the value published by the issuer through an independent channel, such as a release portal or authenticated signing documentation.

Do not download a JAR and blindly trust the fingerprint printed from that same JAR. An attacker can replace both the artifact and the certificate if the verifier has no independent reference value.

### 6.2. Viewing Certificates in a Keystore

~~~text
keytool -list -v -keystore release-signers.p12 -storetype PKCS12
~~~

This command lists aliases, entry types, and certificate chains in the keystore. If no password is provided, the tool may prompt for it.

To inspect a standalone certificate:

~~~text
keytool -printcert -file signer.cer -v
~~~

`keytool -printcert` only displays certificate information. It does not replace `jarsigner -verify` and does not prove that all entries in the JAR are intact.

### 6.3. Checking Important Attributes

When reviewing a certificate, pay attention to:

- Subject: the identity to which the certificate was issued.
- Issuer: the CA or entity that issued the certificate.
- Serial number: the certificate's serial number.
- Validity: the start and end dates of validity.
- SHA-256 fingerprint: the fingerprint for out-of-band verification.
- Key Usage: permissions for using the public key.
- Extended Key Usage: intended purposes, such as code signing.
- Certificate chain: the associated intermediate certificates and root CA.

If the chain cannot be validated, it may be due to a missing intermediate certificate, an untrusted CA, or a build environment lacking the appropriate trust anchor. Determine the root cause according to your organization's PKI policy.

## 7. Understanding Certificate Chains and Trust

The certificate in the signature block authenticates the signer's public key. A higher-level CA certificate can authenticate the signer's certificate; this chain must lead to a trust anchor accepted by the verification environment.

A chain typically looks like:

~~~text
JAR signer certificate
        |
        v
Intermediate code-signing CA
        |
        v
Organization / Public root CA
        |
        v
Trusted by verification policy
~~~

If a certificate is self-signed, there is no external CA attesting to its identity. This is why the JDK may report a severe warning even though the digests and mathematical signature still match.

When verifying a vendor's JAR:

1. Obtain the expected fingerprint from a trusted release channel.
2. Print the certificate from the JAR using `keytool -printcert -jarfile`.
3. Compare the fingerprint and subject with the published information.
4. Confirm the issuer/chain against your trust policy.
5. Verify that the certificate is valid and has an appropriate code-signing purpose.
6. Check revocation according to organizational policy.

Do not import an unverified certificate into the truststore just to make `jarsigner -strict` pass. Adding a trust anchor alters the environment's trust decisions and requires approval under PKI policy.

## 8. Timestamps and Signing Time

Code-signing certificates have an expiration date. If a JAR is signed while the certificate is valid and the signature includes a valid timestamp, verifiers can confirm the signing time even after the signer certificate expires.

When signing, you can request a timestamp from a TSA:

~~~text
jarsigner -keystore release-signers.p12 -tsa https://tsa.example.org -signedjar application-signed.jar application.jar release-signer
~~~

`https://tsa.example.org` is only an example URL; replace it with a TSA endpoint approved by your organization or certificate provider.

`jarsigner` uses the Time-Stamp Protocol (TSP) per RFC 3161. The timestamp token is stored alongside the signature block when the TSA processes the request successfully.

You can use `-tsacert alias` if the TSA certificate in the keystore contains Subject Information Access pointing to the TSA. The TSA certificate must exist in the keystore when using this option.

When verifying, check:

- Whether a timestamp is present.
- Whether the signing time falls within the signer certificate's validity period.
- Whether the TSA certificate is valid and its chain is validated.
- Whether the timestamp has expired or is considered invalid.
- Whether the timestamp's digest and signature algorithms are accepted by current policy.

If there is no timestamp, the JDK may issue a `noTimestamp` warning. This is an informational warning; over the long term, the JAR may become difficult to validate after the signer certificate expires or after a future revocation date.

## 9. Certificate Revocation Checking

A certificate may be revoked before its expiration date, for example if the private key is compromised or the certificate was mis-issued.

The `-revCheck` option enables revocation checking:

~~~text
jarsigner -verify -revCheck -verbose -certs application.jar
~~~

When enabled, `jarsigner` may make network connections to fetch an OCSP response or CRL. If the build environment is offline or a firewall blocks the endpoints, this step may fail or not complete as expected.

Define a clear policy:

- Is revocation checking mandatory on every verification?
- Does the CI environment have network access to OCSP/CRL endpoints?
- If the revocation service is temporarily unreachable, how should the pipeline handle it?
- How are the results archived for auditing?

Do not assume a certificate has not been revoked simply because the verify command was run without `-revCheck`. According to JDK 24.0.2 help, revocation checking is not enabled by default.

## 10. Understanding `-strict` and Exit Codes

This is critical when integrating signature verification into CI.

If you only run `jarsigner -verify`, the tool may return exit code `0` even when severe warnings are present. Use `-strict` to reflect severe warnings in the exit code:

~~~text
jarsigner -verify -strict -verbose -certs application.jar
~~~

According to JDK 24 documentation:

- Exit code `1`: signing or verification operation failed.
- No failure but severe warnings present: default exit code is `0`; with `-strict`, the exit code is the bitwise OR of the warning codes.
- Only informational warnings or no warnings: exit code `0`.

Common severe warning codes:

| Warning | Code | Meaning |
|---|---:|---|
| `hasExpiredCert` | 4 | Signer certificate has expired |
| `notYetValidCert` | 4 | Signer certificate is not yet valid |
| `chainNotValidated` | 4 | Certificate chain could not be validated |
| `signerSelfSigned` | 4 | Signer certificate is self-signed |
| `disabledAlg` | 4 | Algorithm is considered insecure and has been disabled |
| `badKeyUsage` | 8 | Key Usage does not allow code signing |
| `badExtendedKeyUsage` | 8 | Extended Key Usage does not allow code signing |
| `hasUnsignedEntry` | 16 | JAR contains entries not integrity-checked by a signature |
| `notSignedByAlias` | 32 | Entry was not signed by the requested alias |
| `tsaChainNotValidated` | 64 | TSA certificate chain is invalid |

Codes can be combined using bitwise OR. For example, an expired certificate with invalid Key Usage can produce code `12` (`4 + 8`).

Some informational warnings do not have their own exit code, such as:

- `noTimestamp`: signature has no timestamp.
- `legacyAlg`: algorithm is considered risky but not yet disabled.
- `hasExpiringCert`: signer certificate is about to expire.
- `hasExpiringTsaCert`: TSA certificate is about to expire.

Therefore, `-strict` does not automatically turn all informational warnings into errors. CI pipelines should save the output and enforce separate policies if the organization wants to block these warnings as well.

## 11. Signing Algorithms and Security Policies

`jarsigner` checks algorithms against JDK security properties, including:

- `jdk.jar.disabledAlgorithms`
- `jdk.security.legacyAlgorithms`

If a JAR uses a disabled algorithm, its signature may be treated as unsigned. Legacy algorithms that are not yet disabled may trigger an informational warning.

When signing new artifacts:

- Use digest and signature algorithms supported by the JDK and accepted by organizational policy.
- Choose a key size that meets current security requirements.
- Do not use MD5 or SHA-1 for new signatures.
- Do not downgrade algorithms solely for compatibility with very old runtimes without a risk assessment.
- Check the default algorithms of the JDK in use, as defaults can change across releases.
- Ensure the certificate has appropriate Key Usage and Extended Key Usage extensions.

You can specify algorithms when signing:

~~~text
jarsigner -digestalg SHA-256 -sigalg SHA256withRSA -keystore release-signers.p12 -signedjar application-signed.jar application.jar release-signer
~~~

This is an example RSA configuration; the actual algorithms must be compatible with your private key, target JDK, and current policy. On newer JDKs, the default digest/signature algorithms may be stronger than this example configuration. Do not hardcode older algorithms in build scripts without a documented compatibility reason.

## 12. Verifying JARs with Multiple Signers

A JAR can be signed multiple times by multiple signers. Each signing operation with a different alias can add a separate `.SF` and signature block pair in `META-INF`.

Example:

~~~text
META-INF/
  RELEASE.SF
  RELEASE.RSA
  AUDIT.SF
  AUDIT.EC
~~~

When verifying, `jarsigner` checks the signatures present in the JAR. If you need to restrict accepted signers, pass the expected aliases along with `-keystore`:

~~~text
jarsigner -verify -strict -verbose -certs -keystore release-signers.p12 application.jar release-signer audit-signer
~~~

Confirm:

- All required signers according to the release policy are present.
- No unauthorized signers are present.
- Each signer has a valid certificate chain and appropriate usage purpose.
- Critical entries are signed as required.
- No unsigned entries or entries signed by unexpected aliases exist.

When a JAR is signed sequentially by multiple signers, the manifest may be updated to add sections for new entries. Previous signatures can remain valid as long as the previously signed entries are not modified.

## 13. Java 17 Workflow: Create JAR, Sign, and Verify

The following example creates a small application, packages it into a JAR, generates a self-signed certificate for a learning environment, signs the artifact, and verifies the signature.

Structure:

~~~text
project/
  src/
    com/
      example/
        Hello.java
  build/
    classes/
    hello.jar
    hello-signed.jar
    training.p12
~~~

### 13.1. Source Code

File `src/com/example/Hello.java`:

~~~java
package com.example;

public final class Hello {
    private Hello() {
    }

    public static void main(String[] args) {
        System.out.println("Hello, signed JAR!");
    }
}
~~~

### 13.2. Compile and Create JAR

Run from the `project` root directory.

Windows PowerShell:

~~~powershell
New-Item -ItemType Directory -Force build\classes | Out-Null

javac --release 17 -encoding UTF-8 `
    -d build\classes `
    src\com\example\Hello.java

jar --create `
    --file build\hello.jar `
    --main-class com.example.Hello `
    -C build\classes .
~~~

macOS/Linux:

~~~sh
mkdir -p build/classes

javac --release 17 -encoding UTF-8 \
    -d build/classes \
    src/com/example/Hello.java

jar --create \
    --file build/hello.jar \
    --main-class com.example.Hello \
    -C build/classes .
~~~

Run the unsigned JAR:

~~~text
java -jar build/hello.jar
~~~

Stdout:

~~~text
Hello, signed JAR!
~~~

### 13.3. Create a Test Keystore

Use `keytool` to generate an RSA key pair and a self-signed certificate:

~~~text
keytool -genkeypair -alias training-signer -keyalg RSA -keysize 3072 -validity 365 -storetype PKCS12 -keystore build/training.p12 -dname "CN=Training Signer, OU=Java Core, O=Example, C=VN"
~~~

`keytool` will prompt for the keystore password. In a learning environment, you can use a dedicated keystore. Do not use the self-signed certificate from this example for production releases.

### 13.4. Sign the JAR

~~~text
jarsigner -keystore build/training.p12 -storetype PKCS12 -digestalg SHA-256 -sigalg SHA256withRSA -signedjar build/hello-signed.jar build/hello.jar training-signer
~~~

If you do not pass the password on the command line, `jarsigner` will prompt for it. This is more appropriate for interactive examples; in CI, retrieve secrets from a secret manager or a protected authentication path mechanism.

After signing, inspect the signature entries:

~~~text
jar --list --file build/hello-signed.jar
~~~

In `META-INF`, there will be a manifest, `.SF` file, and signature block corresponding to the `training-signer` alias.

### 13.5. Verify the Signature

Check the signature and inspect the certificate:

~~~text
jarsigner -verify -verbose -certs build/hello-signed.jar
~~~

Print the embedded certificate:

~~~text
keytool -printcert -jarfile build/hello-signed.jar -v
~~~

Run the application after signing:

~~~text
java -jar build/hello-signed.jar
~~~

Stdout:

~~~text
Hello, signed JAR!
~~~

Because the lab certificate is self-signed, the verification output may warn that the signer certificate is not trusted. This is expected in a learning environment; it illustrates the difference between signature/integrity verification and a signer identity validated by a CA.

When adding `-strict`:

~~~text
jarsigner -verify -strict -verbose -certs build/hello-signed.jar
~~~

The JDK may return a non-zero exit code due to severe warnings about the self-signed certificate or unvalidated chain. This does not mean the Java source code failed to compile or that entry digests were definitely altered; read the exact warnings to identify the issue.

In a real release environment, replace the self-signed certificate with a code-signing certificate issued by an accepted CA, use an approved TSA, and verify against your organization's trust policy.

## 14. Automating Multi-JAR Verification in PowerShell

`jarsigner -verify` accepts one JAR per invocation. Alias arguments following the JAR name specify signer aliases, not a list of JARs. Therefore, to verify multiple artifacts, use a loop.

Example:

~~~powershell
$targets = @(
    Get-ChildItem .\build\libs -Filter *.jar -File -Recurse |
        Where-Object {
            $_.Name -notlike '*-sources.jar' -and
            $_.Name -notlike '*-javadoc.jar'
        }
)

if ($targets.Count -eq 0) {
    throw "No release JAR files were found."
}

New-Item -ItemType Directory -Force .\build\signature-reports | Out-Null

$failed = @()

foreach ($item in $targets) {
    Write-Host "Verifying $($item.FullName)..."

    $report = & jarsigner -verify -strict -verbose:summary -certs $item.FullName 2>&1
    $exitCode = $LASTEXITCODE

    $reportPath = Join-Path .\build\signature-reports ($item.BaseName + ".txt")
    $report | Set-Content -Encoding UTF8 $reportPath

    if ($exitCode -ne 0) {
        $failed += "$($item.FullName) (exit code $exitCode)"
    }
}

if ($failed.Count -gt 0) {
    $failed | ForEach-Object { Write-Error $_ }
    throw "One or more JAR signature checks failed."
}
~~~

This script:

- Finds JARs in the build directory.
- Excludes source JARs and Javadoc JARs.
- Verifies each JAR with `-strict`.
- Saves a separate report for each artifact.
- Collects artifacts with a non-zero exit code.
- Fails the build if any JAR does not pass strict verification.

If two directories contain JARs with the same `BaseName`, adjust the report naming scheme to avoid overwriting reports. If you need to check a specific signer alias, add `-keystore` and the approved alias to the verify command.

## 15. Integrating Signature Verification in CI/CD

A release pipeline should verify artifacts immediately after signing and before publishing:

1. Build the JAR from an approved commit.
2. Generate an artifact inventory and checksums.
3. Sign the JAR with the release key/certificate.
4. Obtain a timestamp from an approved TSA.
5. Run `jarsigner -verify -strict -verbose:summary -certs`.
6. Check the signer certificate, fingerprint, and chain.
7. Check informational warnings against the release policy.
8. Verify that all entries requiring protection are signed.
9. Archive the raw verification report alongside the artifact.
10. Publish the exact verified file; do not modify the JAR after verification.

Example command for a single artifact:

~~~text
jarsigner -verify -strict -verbose:summary -certs build/application-signed.jar
~~~

If multiple signers are allowed:

~~~text
jarsigner -verify -strict -verbose:summary -certs -keystore release-signers.p12 build/application-signed.jar release-signer
~~~

Do not place real passwords directly in pipeline scripts or command lines. Use a secret manager, environment variables, or restricted-permission secret files as supported by the JDK.

Retain:

- The signed JAR and checksums.
- JDK/`jarsigner` version.
- Certificate fingerprint and signer alias.
- Timestamp and TSA certificate details.
- The verification command that was run.
- Exit code and raw output.
- Policy review results for informational warnings.

If an artifact is re-signed, repackaged, or updated after verification, you must re-run verification on the exact final file to be published.

## 16. Troubleshooting Signature Verification

### `jar is unsigned`

**Cause:** The JAR has no valid signature or the signature algorithms have been disabled.

**Resolution:** Inspect `META-INF`, `.SF` files, signature blocks, and algorithms. Confirm that the correct artifact was signed before release.

### `invalid SHA-256 signature file digest`

**Cause:** The digest in the signature file does not match the current manifest.

**Resolution:** Check whether the JAR was modified after signing, the manifest was updated out-of-band, or the signature file was replaced. Rebuild the artifact from a trusted source and re-sign.

### `digest error` or entry digest mismatch

**Cause:** An entry's content differs from its content at signing time.

**Resolution:** Identify the modified entry, trace the artifact's provenance, and rebuild. Do not ignore mismatches and proceed with publishing.

### `This jar contains unsigned entries`

**Cause:** There are files in the JAR not covered by the current signature, such as files added after signing.

**Resolution:** Determine whether unsigned entries are permitted. If release policy requires the entire payload to be signed, recreate the JAR and sign it again after all changes are complete.

### `signer certificate is self-signed`

**Cause:** The certificate does not have a CA chain validated against the trust policy.

**Resolution:** Use a certificate issued by a CA accepted by your organization or follow an approved internal trust process. Verify the fingerprint through an independent channel.

### `certificate chain not validated`

**Cause:** Missing intermediate certificate, untrusted root CA, or missing chain data in the verification environment.

**Resolution:** Inspect the certificate with `-certs`/`keytool`, confirm the chain and trust anchor against policy, and verify that the build environment has the proper PKI configuration.

### `signer certificate has expired`

**Cause:** The certificate is expired at verification time or lacks a valid timestamp proving an appropriate signing time.

**Resolution:** Check the timestamp token, signer certificate validity period, and TSA chain. Re-sign a new release with a valid certificate when necessary.

### `timestamp is invalid`

**Cause:** Invalid TSA certificate chain, unverified timestamp token, or expired TSA certificate.

**Resolution:** Check the TSA chain, signing time, and TSA endpoint; use an approved TSA and re-verify.

### `disabled algorithm`

**Cause:** The JAR uses a digest or signature algorithm disabled by JDK security properties.

**Resolution:** Re-sign using an appropriate algorithm and key size. Do not edit `jdk.jar.disabledAlgorithms` to bypass errors just to make a release pass.

### `badKeyUsage` or `badExtendedKeyUsage`

**Cause:** The certificate was not issued for code-signing purposes.

**Resolution:** Request a certificate with extensions matching the code-signing policy; do not use TLS certificates or certificates with the wrong purpose.

### Exit code `0` despite warnings

**Cause:** The command did not use `-strict`, or the warnings are informational.

**Resolution:** Use `-strict` to fail on severe warnings and apply separate policies for `noTimestamp`, `legacyAlg`, or other informational warnings.

### `aliasNotInStore` or `notSignedByAlias`

**Cause:** The signer in the JAR does not match the requested alias, or the certificate is not in the specified keystore.

**Resolution:** Check the keystore, alias, and signer certificate. Verify the fingerprint before accepting an alternative alias.

## 17. Checklist Before Accepting a Signed JAR

- [ ] Confirmed JDK and `jarsigner` version.
- [ ] Ran `jarsigner -verify`.
- [ ] Ran strict verification according to release policy.
- [ ] No signed entries were modified or had digest mismatches.
- [ ] No unsigned entries outside the permitted list.
- [ ] Verified all required signers and aliases.
- [ ] Inspected the certificate chain with `-certs`.
- [ ] Verified the fingerprint against an independent source.
