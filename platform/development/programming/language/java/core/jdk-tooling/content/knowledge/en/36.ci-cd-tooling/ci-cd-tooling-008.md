# Using jdeps in CI

## 1. What is jdeps and why include it in CI?

`jdeps` is a static dependency analysis tool bundled with the JDK. It reads bytecode in class files, class directories, or JARs to determine which classes/packages/modules are referenced. The results help detect missing dependencies, dependencies on JDK internal APIs, determine required modules, and generate dependency graphs.

Integrating `jdeps` into Continuous Integration (CI) helps inspect artifacts after compile/package, before release:

- Detect classes that are referenced but absent from the classpath or module path.
- Detect applications using JDK internal APIs such as `sun.misc.Unsafe`.
- Verify dependencies between Java modules.
- Determine the set of modules needed for a custom runtime image with `jlink`.
- Generate graphs for architecture reviews or investigating newly introduced dependencies.
- Track API dependencies separately from dependencies that only appear inside method bodies.

`jdeps` analyzes compiled bytecode. It does not replace the compiler, unit tests, integration tests, dependency vulnerability scanners, or runtime smoke tests. A build should run `jdeps` after the artifact is created and all dependencies are available for resolution.

## 2. Prerequisites and identifying the right JDK

`jdeps` is located in the JDK's `bin` directory:

~~~bash
java --version
javac --version
jdeps --version
jdeps --help
~~~

Example on JDK 24.0.2:

~~~text
24.0.2
~~~

The build agent must have a JDK installed, not just a JRE. Verify that `jdeps` is invoked from the same JDK/toolchain that the pipeline intends to use. If CI has multiple JDKs, print the version before analyzing so the build log is traceable.

On Windows PowerShell:

~~~powershell
Get-Command java, javac, jdeps | Select-Object Name, Source
$env:JAVA_HOME
~~~

On Linux/macOS:

~~~bash
command -v java
command -v javac
command -v jdeps
echo "$JAVA_HOME"
~~~

You can invoke the executable directly under `JAVA_HOME/bin` to avoid picking up the wrong version from PATH. On Windows, executables typically have the `.exe` extension.

## 3. Types of input jdeps analyzes

`jdeps` accepts one or more paths:

- A `.class` file.
- A directory containing class files.
- A JAR.
- A module or module path suitable for module analysis options.

Examples:

~~~bash
# Analyze a JAR
jdeps app.jar

# Analyze a class directory
jdeps build/classes

# Analyze a single class
jdeps build/classes/com/example/Main.class

# Analyze multiple artifacts
jdeps service.jar shared-library.jar
~~~

In CI, you should analyze the final artifact or the main build class output. Analyzing only an unpackaged source file may miss dependencies generated by the build process, generated classes, or packaging configuration.

For multi-module projects, run the analysis on each released JAR or pass multiple artifacts to the same command. Clearly record the corresponding module/path so the results are easy to correlate with the build graph.

## 4. Understanding dependency output formats

Summary output example:

~~~text
app.jar -> java.base
app.jar -> java.sql
~~~

This indicates that the JAR references packages belonging to two JDK modules. For unresolved dependencies, the output may contain:

~~~text
app.jar -> not found
   com.example.app.Main -> com.example.lib.TextHelper not found
~~~

A dependency line describes the relationship between a source class/package and a target class/package. Results can be displayed at multiple levels:

| Level | Purpose |
|---|---|
| Module | View the Java modules that the artifact depends on. |
| Package | View dependencies between packages. |
| Class | View exactly which class references which class. |
| Summary | View an archive's dependency summary. |

By default, dependency analysis filters out some internal relationships within a package/archive. If you need more detail, choose verbose mode or an appropriate filter.

## 5. Syntax and key options

General syntax:

~~~bash
jdeps [options] <path ...>
~~~

Commonly used options in CI:

| Option | Meaning |
|---|---|
| `-s` / `-summary` | Print dependency summary only. |
| `-v` / `-verbose` | Print class-level dependencies. |
| `-verbose:package` | Print package-level dependencies. |
| `-verbose:class` | Print class-level dependencies. |
| `--missing-deps` | Find unresolved dependencies. |
| `--jdk-internals` | Find references to JDK internal APIs. |
| `--class-path` | Specify the classpath to search for dependencies. |
| `--module-path` | Specify the module path. |
| `--list-deps` | List module dependencies. |
| `--list-reduced-deps` | List module dependencies after removing implied readability edges. |
| `--print-module-deps` | Print a comma-separated list of modules, usable with `jlink`. |
| `--check` | Check the module descriptor and dependency graph. |
| `--api-only` | Only analyze dependencies appearing in public/protected APIs. |
| `--dot-output` | Export the dependency graph in DOT format. |
| `--multi-release` | Select the version to analyze in a multi-release JAR. |
| `--generate-module-info` | Generate a suggested module descriptor for a non-modularized JAR. |

In JDK 24, the summary option is `-s` or `-summary`; do not use `--summary`.

You can view all options for your exact JDK with:

~~~bash
jdeps --help
~~~

Option names and support may differ across JDK versions. Pipelines should verify the version before invoking newer options.

## 6. Overview dependency analysis

Run summary:

~~~bash
jdeps -s target/app.jar
~~~

Example:

~~~text
app.jar -> java.base
app.jar -> java.sql
~~~

View package-level dependencies:

~~~bash
jdeps -verbose:package target/app.jar
~~~

View class-level dependencies:

~~~bash
jdeps -verbose:class target/app.jar
~~~

Do not filter internal dependencies when you need full visibility:

~~~bash
jdeps -v target/app.jar
~~~

Verbose output is useful when an unexpected module dependency appears and you need to identify which class creates the reference. For large artifacts, class-level output can be very long; save it to a report file or filter to only relevant packages/classes.

## 7. Providing classpath and module path

`jdeps` needs to know where to find dependencies outside the JDK.

### Classpath

~~~bash
jdeps --missing-deps --class-path "lib/*" target/app.jar
~~~

You can pass multiple directories and JARs using the OS classpath separator:

- Windows: semicolon `;`.
- Linux/macOS: colon `:`.

Examples:

~~~bash
# Windows
jdeps --class-path "target/classes;lib/*" target/app.jar

# Linux/macOS
jdeps --class-path "target/classes:lib/*" target/app.jar
~~~

The classpath must contain the runtime dependencies needed for analysis. If a valid JAR is missing, `jdeps` may report `not found` even if the application still builds in another step.

### Module path

For modular applications:

~~~bash
jdeps --module-path "mods:lib" --module com.example.app --list-deps
~~~

`--module-path` specifies where to find modules; `--module` selects the root module to analyze. Do not use classpath instead of module path when you need to check module descriptors and the module graph.

## 8. Finding missing dependencies with --missing-deps

This is a critical check in CI:

~~~bash
jdeps --missing-deps --class-path "target/dependency/*" target/app.jar
~~~

When dependencies are complete, the output usually has no missing lines. If a dependency is missing, for example:

~~~text
app.jar -> not found
   com.example.app.Main -> com.example.lib.TextHelper not found
~~~

**Important note about exit code:** in JDK 24.0.2, `jdeps --missing-deps` can return exit code 0 even when it prints `not found` dependencies. Therefore, checking only `$LASTEXITCODE` or the process status is not sufficient as a CI gate. You must inspect the output content and explicitly return an error code when findings are present.

Do not use `--ignore-missing-deps` in standard quality gate steps. That option allows analysis to continue when dependencies are missing and can mask errors that the pipeline needs to catch.

Before concluding that an artifact is broken, confirm that the classpath/module path has all dependencies in the right scope. If dependencies are loaded dynamically via reflection or service configuration, static analysis may not see every runtime relationship.

## 9. Detecting JDK internal APIs

Run:

~~~bash
jdeps --jdk-internals target/app.jar
~~~

Example when bytecode references `sun.misc.Unsafe`:

~~~text
internal-api.jar -> jdk.unsupported
   com.example.InternalApi -> sun.misc.Unsafe JDK internal API (jdk.unsupported)

Warning: JDK internal APIs are unsupported and private to JDK implementation
~~~

JDK internal APIs are not stable public contracts. They can be encapsulated, changed, or removed between JDK versions, making applications incompatible after an upgrade.

`jdeps --jdk-internals` usually prints warnings and suggests replacement APIs. On JDK 24.0.2, the command may still return exit code 0 when internal APIs are found. CI needs to read the output to enforce policy:

- Fail the build when internal APIs are detected in application code.
- Or allow documented exceptions with a clear justification and expiration date.
- Analyze third-party dependencies separately if you want to govern libraries as well.
- Do not automatically ignore all warnings just because a dependency is vendor-provided.

If you pass a classpath containing many libraries to `--jdk-internals`, the tool may also analyze classes on the classpath. Be clear about whether you want to check application code or the entire dependency tree before choosing the inputs.

## 10. Separating API dependencies from implementation dependencies

`--api-only` only inspects dependencies appearing in public/protected APIs of public classes, for example:

- Parameter types of public methods.
- Return types.
- Public/protected field types.
- Checked exceptions in method signatures.
- Types appearing in other API signatures.

Run:

~~~bash
jdeps --api-only target/app.jar
~~~

Compare with class-level analysis:

~~~bash
jdeps -v target/app.jar
~~~

A library may be used inside a method body without appearing in the public API. `--api-only` helps detect dependencies leaked into a library's contract, which is useful when designing APIs or splitting modules.

Do not use API-only results as a substitute for full dependency analysis. It intentionally omits many implementation dependencies.

## 11. Analyzing module dependencies and generating jlink input

List module dependencies:

~~~bash
jdeps --list-deps --module-path mods --module com.example.app
~~~

Print the reduced dependency graph:

~~~bash
jdeps --list-reduced-deps --module-path mods --module com.example.app
~~~

Print a comma-separated list of modules:

~~~bash
jdeps --print-module-deps --module-path mods --module com.example.app
~~~

Example:

~~~text
java.base,java.sql
~~~

This list can be used as input for `jlink` to create a custom runtime image:

~~~bash
jlink --add-modules java.base,java.sql --output build/runtime-image
~~~

`--print-module-deps` retrieves module dependencies with implied edges reduced. For custom runtimes, you still need to check dynamically loaded modules, service providers, and modules required by the application at runtime. The static list does not always cover every module loaded via reflection or plugins.

## 12. Checking module descriptors with --check

For JARs with `module-info.class`, you can check the descriptor:

~~~bash
jdeps --check com.example.app --module-path target/modular-app.jar
~~~

The output includes:

- The current module descriptor.
- Suggested module dependencies after analysis.
- Transitive reduced graph.
- Unused qualified exports, if any.

`--check` helps review module descriptors after source or dependency changes. If the module path contains multiple modules, pass the full path so the tool can resolve the graph.

This option is for module names, not for checking a regular classpath JAR without a module descriptor.

## 13. Generating module-info.java for non-modularized JARs

For a JAR without a module descriptor:

~~~bash
jdeps --generate-module-info build/module-info target/library.jar
~~~

The tool generates a suggested `module-info.java` file in the target directory. Example:

~~~java
module text.helper {
    exports com.example.lib;
}
~~~

The generated descriptor is only a starting point. You need to review:

- Module name.
- Packages to export.
- `requires` and `requires transitive`.
- Qualified exports.
- Reflection and service loading.
- Split packages or dependencies that cannot be expressed directly.

Do not put a `jdeps`-generated descriptor straight into production without reviewing and test-compiling it. For open modules, the tool provides the `--generate-open-module` option.

## 14. Exporting dependency graphs as CI artifacts

Generate DOT output:

~~~bash
jdeps --dot-output build/reports/jdeps --class-path "target/dependency/*" target/app.jar
~~~

The output directory may contain:

~~~text
build/reports/jdeps/
├── app.jar.dot
└── summary.dot
~~~

You can save DOT files as pipeline artifacts so reviewers can open them with Graphviz or other Mermaid/graph visualization tools. Graphs help spot new dependencies, package coupling, and complex module graphs.

When building multiple JARs, create a separate output directory per run or clean old reports before writing to avoid mixing graphs from other artifacts.

## 15. Multi-release JARs

A multi-release JAR can contain different classes for different Java releases in the same archive. Use `--multi-release` to select the version to analyze:

~~~bash
jdeps --multi-release 17 --list-deps target/multi-release-library.jar
~~~

The value can be an integer 9 or greater, or `base`. Choose the exact release that the production application actually runs on. Analyzing only the base version may miss dependencies in classes placed under `META-INF/versions/N`.

Do not use `--multi-release 17` for regular JARs without a multi-release layout. First confirm the manifest has `Multi-Release: true` and the JAR contains the appropriate versioned classes.

## 16. Filters and deep dependency analysis

Useful filtering options:

| Option | Purpose |
|---|---|
| `--package` | Only find dependencies of the specified package. |
| `--regex` | Filter dependencies using a regular expression. |
| `--require` | Filter by module dependency. |
| `-include` | Restrict classes included in the analysis. |
| `-filter:package` | Filter dependencies within the same package. |
| `-filter:archive` | Filter dependencies within the same archive. |
| `-filter:module` | Filter dependencies within the same module. |
| `-filter:none` | Do not filter internal dependencies by package/archive by default. |
| `--recursive` | Recursively traverse runtime dependencies. |
| `--no-recursive` | Do not recursively traverse dependencies. |
| `--inverse` | Find artifacts that directly/indirectly depend on the selected node. |

Example finding dependencies related to a package:

~~~bash
jdeps --package com.example.lib -v target/app.jar
~~~

Find artifacts depending on a module:

~~~bash
jdeps --inverse --require java.sql target/*.jar
~~~

The `--package`, `--regex`, and `--require` filters are mutually exclusive in a single invocation. `--inverse` must be used with an appropriate filter. Check `jdeps --help` before combining complex options.

## 17. Creating a Java 17 fixture for practice

A dependency library:

`libsrc/com/example/lib/TextHelper.java`:

~~~java
package com.example.lib;

public final class TextHelper {
    private TextHelper() {
    }

    public static String normalize(String value) {
        return value == null ? "" : value.trim().toLowerCase();
    }
}
~~~

Application using the library and JDBC API:

`appsrc/com/example/app/Main.java`:

~~~java
package com.example.app;

import com.example.lib.TextHelper;
import java.sql.Connection;
import java.sql.DriverManager;

public class Main {
    public static void main(String[] args) throws Exception {
        String value = TextHelper.normalize(" CI ");
        System.out.println("jdeps CI ready: " + value);

        try (Connection ignored =
                 DriverManager.getConnection("jdbc:invalid:")) {
            System.out.println(ignored);
        } catch (java.sql.SQLException expected) {
            System.out.println("JDBC module resolved");
        }
    }
}
~~~

Compile and package the library:

~~~bash
javac --release 17 -d build/lib libsrc/com/example/lib/TextHelper.java
jar --create --file lib/text-helper.jar -C build/lib .
~~~

Compile the application with the dependency:

~~~bash
javac --release 17 -cp lib/text-helper.jar -d build/app appsrc/com/example/app/Main.java
jar --create --file dist/app.jar --main-class com.example.app.Main -C build/app .
~~~

Run on Windows:

~~~powershell
java -cp "dist/app.jar;lib/text-helper.jar" com.example.app.Main
~~~

On Linux/macOS:

~~~bash
java -cp "dist/app.jar:lib/text-helper.jar" com.example.app.Main
~~~

Exact stdout:

~~~text
jdeps CI ready: ci
JDBC module resolved
~~~

## 18. Checking dependencies on the fixture

List modules:

~~~bash
jdeps --list-deps --class-path lib/text-helper.jar dist/app.jar
~~~

Output:

~~~text
java.base
java.sql
~~~

Print module list:

~~~bash
jdeps --print-module-deps --class-path lib/text-helper.jar dist/app.jar
~~~

Output:

~~~text
java.base,java.sql
~~~

Find missing dependencies when the library JAR is not passed:

~~~bash
jdeps --missing-deps dist/app.jar
~~~

Output contains:

~~~text
app.jar -> not found
com.example.app.Main -> com.example.lib.TextHelper not found
~~~

Add the dependency to the classpath:

~~~bash
jdeps --missing-deps --class-path lib/text-helper.jar dist/app.jar
~~~

No missing output remains. In a verification run on JDK 24.0.2, both this command and the missing-dependency command returned exit code 0; the difference is in the output. This is why CI needs to parse findings instead of only checking the exit code.

Generate graph:

~~~bash
jdeps --dot-output build/reports/jdeps --class-path lib/text-helper.jar dist/app.jar
~~~

Verify that `app.jar.dot` and `summary.dot` are created in the report directory.

## 19. Module descriptor check example

Create module sources:

`modulesrc/com.example.modapp/module-info.java`:

~~~java
module com.example.modapp {
    requires java.sql;
}
~~~

`modulesrc/com.example.modapp/com/example/modapp/Main.java`:

~~~java
package com.example.modapp;

import java.sql.Connection;
import java.sql.DriverManager;
import java.sql.SQLException;

public class Main {
    public static void main(String[] args) {
        try (Connection ignored =
                 DriverManager.getConnection("jdbc:invalid:")) {
            System.out.println(ignored);
        } catch (SQLException expected) {
            System.out.println("module dependency ready");
        }
    }
}
~~~

Compile and package the module:

~~~bash
javac --release 17 --module-source-path modulesrc -d build/mods -m com.example.modapp
jar --create --file dist/modapp.jar --main-class com.example.modapp.Main -C build/mods/com.example.modapp .
~~~

Check:

~~~bash
jdeps --check com.example.modapp --module-path dist/modapp.jar
jdeps --list-deps --module-path dist/modapp.jar --module com.example.modapp
~~~

Verified results on JDK 24.0.2 show that the descriptor requires `java.base` and `java.sql`; the module list also contains those exact two modules.

## 20. Creating a CI gate with PowerShell

Because `jdeps` can return exit code 0 even when output contains findings, the script needs to check both the process exit code and the output content.

Example `scripts/check-jdeps.ps1`:

~~~powershell
param(
    [Parameter(Mandatory = $true)]
    [string]$Artifact,

    [string]$ClassPath = ""
)

$ErrorActionPreference = "Stop"

$missingArgs = @("--missing-deps")
if ($ClassPath) {
    $missingArgs += @("--class-path", $ClassPath)
}
$missingArgs += $Artifact

$missingOutput = & jdeps @missingArgs 2>&1
if ($LASTEXITCODE -ne 0) {
    throw "jdeps --missing-deps failed: $LASTEXITCODE"
}

$missingText = $missingOutput -join [Environment]::NewLine
if ($missingText -match "\bnot found\b") {
    Write-Error ("Missing bytecode dependencies:" +
        [Environment]::NewLine + $missingText)
    exit 1
}

$internalOutput = & jdeps --jdk-internals $Artifact 2>&1
if ($LASTEXITCODE -ne 0) {
    throw "jdeps --jdk-internals failed: $LASTEXITCODE"
}

$internalText = $internalOutput -join [Environment]::NewLine
if ($internalText -match "JDK internal API") {
    Write-Error ("JDK internal API usage detected:" +
        [Environment]::NewLine + $internalText)
    exit 1
}

Write-Host "jdeps checks passed: $Artifact"
~~~

Run:

~~~powershell
.\scripts\check-jdeps.ps1 -Artifact target/app.jar -ClassPath (Get-Content target/runtime-classpath.txt -Raw)
~~~

This script enforces a policy to fail on missing dependencies or JDK internal APIs. If the organization permits an exception, create an allowlist with an owner, reason, and expiration date; do not remove the check step.

In JDK 24.0.2 testing:

- Artifact with `text-helper.jar` present: script prints `jdeps checks passed` and exits with code 0.
- Missing `text-helper.jar`: script prints missing class and exits with code 1.
- Artifact referencing `sun.misc.Unsafe`: script detects `JDK internal API` and exits with code 1.

## 21. Integrating into Gradle

You can create a task that runs after the JAR is packaged:

~~~groovy
tasks.register('jdepsCheck') {
    dependsOn tasks.jar

    doLast {
        def exeName = System.getProperty('os.name')
            .toLowerCase().contains('windows') ? 'jdeps.exe' : 'jdeps'
        def jdepsExe = new File(
            System.getProperty('java.home'), "bin/" + exeName
        )
        def artifact = tasks.jar.archiveFile.get().asFile

        def runJdeps = { List<String> command ->
            def process = new ProcessBuilder(command)
                .redirectErrorStream(true).start()
            def output = process.inputStream.getText('UTF-8')
            def exitCode = process.waitFor()
            if (exitCode != 0) {
                throw new GradleException(
                    "jdeps exited " + exitCode + ":\n" + output
                )
            }
            return output
        }

        def missingOutput = runJdeps([
            jdepsExe.absolutePath,
            '--missing-deps',
            '--class-path',
            configurations.runtimeClasspath.asPath,
            artifact.absolutePath
        ])

        if (missingOutput.contains('not found')) {
            throw new GradleException(
                "Missing dependencies detected:\n" + missingOutput
            )
        }

        def internalOutput = runJdeps([
            jdepsExe.absolutePath,
            '--jdk-internals',
            artifact.absolutePath
        ])

        if (internalOutput.contains('JDK internal API')) {
            throw new GradleException(
                "JDK internal API usage detected:\n" + internalOutput
            )
        }

        logger.lifecycle("jdeps checks passed for " + artifact.name)
    }
}
~~~

Run:

~~~bash
gradle clean jdepsCheck
~~~

The task retrieves the classpath from `runtimeClasspath`, checks missing dependencies and internal APIs separately, and fails the build when findings occur. In projects using a Java toolchain different from the Gradle daemon's JDK, obtain the `jdeps` executable from the exact toolchain instead of defaulting to the daemon's `java.home`.

This task was verified with Gradle 9.2.1 on JDK 24.0.2: `clean jdepsCheck` built the JAR, ran both analyses, and ended with `BUILD SUCCESSFUL` on the valid fixture.

## 22. Integrating into Maven and GitHub Actions

Maven can generate the runtime classpath using the Dependency Plugin:

~~~bash
mvn -B clean package
mvn -B dependency:build-classpath -Dmdep.outputFile=target/runtime-classpath.txt
~~~

Then run the check script on the JAR:

~~~powershell
.\scripts\check-jdeps.ps1 -Artifact target/app.jar -ClassPath (Get-Content target/runtime-classpath.txt -Raw)
~~~

GitHub Actions example with Maven on Linux:

~~~yaml
name: Java dependency analysis

on:
  pull_request:
  push:

jobs:
  jdeps:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '17'
          cache: maven

      - name: Build
        run: mvn -B clean package

      - name: Resolve runtime classpath
        run: mvn -B dependency:build-classpath -Dmdep.outputFile=target/runtime-classpath.txt

      - name: Check missing dependencies
        shell: bash
        run: |
          classpath="$(cat target/runtime-classpath.txt)"
          output="$(jdeps --missing-deps --class-path "$classpath" target/app.jar 2>&1)"
          printf '%s\n' "$output"
          if printf '%s\n' "$output" | grep -q 'not found'; then
            echo "Missing bytecode dependency detected"
            exit 1
          fi

      - name: Check JDK internal APIs
        shell: bash
        run: |
          output="$(jdeps --jdk-internals target/app.jar 2>&1)"
          printf '%s\n' "$output"
          if printf '%s\n' "$output" | grep -q 'JDK internal API'; then
            echo "JDK internal API usage detected"
            exit 1
          fi
~~~

Replace `target/app.jar` with your project's actual artifact. If building multiple modules, loop over the released JARs or create a task per module. If using Gradle, invoke `gradle jdepsCheck` in the workflow after the build step.

Pin the JDK and build tools in CI so analysis output is comparable across runs. When upgrading the JDK, review dependency graph changes and internal API warnings.

## 23. Limitations of static dependency analysis

`jdeps` reads references in bytecode. It may not fully detect:

- Class names constructed dynamically via reflection.
- Classes loaded from plugins or custom class loaders.
- Service providers selected by runtime configuration.
- Dependencies hidden in scripts, JNI, or native libraries.
- Resources/configurations loaded only at runtime.
- Dependencies appearing only on a code path not fully analyzed.

Therefore, a clean `jdeps` result does not prove the application will run successfully in every environment. Combine it with tests, startup smoke tests, service checks, and runtime observability.

Conversely, a `not found` finding may appear when the provided classpath is incomplete or dependencies are distributed in a custom way. Confirm packaging and runtime dependencies before modifying source code.

`jdeps` also does not evaluate security vulnerabilities, licenses, dependency versions, or API quality. Use dedicated SCA/vulnerability scanning tools for those goals.

## 24. Common errors when using jdeps in CI

| Symptom | Cause | Resolution |
|---|---|---|
| `jdeps is not recognized` | Build agent only has JRE installed or wrong PATH. | Install JDK and invoke the exact `JAVA_HOME/bin/jdeps`. |
| Dependency shows `not found` | Classpath/module path is missing JARs or outputs. | Pass the complete runtime classpath/module path. |
| Findings appear but CI still passes | Only checking jdeps exit code. | Parse output and explicitly exit 1 on `not found` or internal API. |
| Too many internal API warnings | Analyzing third-party dependencies as well. | Restrict inputs/`-include` or set separate policies for internal code and third-party libraries. |
| Module not found | Using classpath instead of module path or missing root module. | Use `--module-path` and `--module` properly. |
| `--check` reports module does not exist | Module path missing JAR or wrong module name. | Verify module descriptor and module name. |
| Empty DOT graph or missing files | Incorrect input or output path. | Verify artifact, write permissions, and `--dot-output`. |
| Multi-release JAR gives different results | Target release not selected for analysis. | Use the appropriate `--multi-release` value. |
| API-only misses dependencies | Dependency is only inside method bodies. | Use full dependency analysis instead of `--api-only`. |
| Runtime dependency still missing despite jdeps passing | Reflection, plugins, service loader, or native dependencies. | Add integration/smoke tests and runtime configuration checks. |
| Pipelines on different machines give different output | Different JDK versions or dependency resolution. | Pin toolchain, dependency versions, and build image. |

## 25. Checklist for deploying jdeps in CI

- Build agent has a JDK and invokes the right `jdeps`.
- JDK/toolchain version is logged.
- Analyze artifacts after compile/package.
- `--class-path` or `--module-path` contains dependencies of the right scope.
- Include a `--missing-deps` step and check output for `not found`.
- Have a policy for `--jdk-internals`.
- Do not confuse exit code 0 with zero findings.
- For modular JARs, check `--check` and `--list-deps`.
- For custom runtimes, review `--print-module-deps` before using `jlink`.
- Save DOT output if dependency graphs need review.
- Select the right version for multi-release JARs.
- Run tests/smoke tests to verify dynamic dependencies.
- Pin JDK, plugins, and build tools in CI.
- Review new findings before merging or releasing.
