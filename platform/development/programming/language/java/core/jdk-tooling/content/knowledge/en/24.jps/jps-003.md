# Process PIDs with jps

A **PID (Process ID)** is a numeric identifier assigned by the operating system to a running process. When a Java application starts on a JVM, the JVM process typically has its own PID. The JDK's **jps** tool lists the instrumented HotSpot JVMs observable by the current user account and displays each JVM's identifier along with its main class name or JAR file.

PIDs are useful when you need to locate the right Java process to inspect JVM details, capture a thread dump, check the heap, investigate an incident, or stop a service according to operational procedures. However, a PID is only valid within a single operating system scope and for the lifetime of that process; it can be reused after the process terminates.

In JDK 24, Oracle documentation marks jps as an experimental and unsupported tool. It is suitable for manual operational checks, but its output should not be treated as a stable interface for building long-term automation.

## 1. Processes, PIDs, and the JVM

A **process** is a running program managed by the operating system. Each process has its own address space, resources, and identifier. The PID is the number assigned to the process by the operating system.

When running a typical Java application, the operating system sees a single JVM process. Inside that process, there can be many Java threads, class loaders, a heap, metaspace, compiler threads, garbage collector threads, and other runtime components.

Example:

~~~text
Operating System
│
├── PID 1200: java -jar api-server.jar
│   ├── Main thread
│   ├── HTTP worker threads
│   ├── GC threads
│   └── JIT compiler threads
│
├── PID 1250: java -jar batch-worker.jar
│   ├── Main thread
│   └── Worker threads
│
└── PID 1300: java -jar report-service.jar
    ├── Main thread
    └── Scheduler threads
~~~

In this example, there are three JVM processes, each with its own PID. A single JVM can contain hundreds or thousands of threads while still appearing as one process at the operating system level.

### PID vs. Thread ID

- **PID** identifies a process at the operating system level.
- **Java thread ID** identifies a thread inside the JVM.
- **OS thread ID** identifies a native thread managed by the operating system.
- **Parent PID (PPID)** is the PID of the parent process that spawned the current process.

jps lists JVM processes; it does not list individual Java threads. To inspect threads running inside a JVM, use tools such as jcmd with the `Thread.print` command, or jstack.

### Is a PID a permanent identifier?

No. A PID is only meaningful within the operating system scope and while the process exists. Once the process terminates, the operating system may reuse that PID for another process.

Therefore, do not store a PID in configuration as a fixed service identifier. Before issuing diagnostic commands or stopping a process, always re-verify the process name, user, start time, and command line.

## 2. What is jps?

jps is a command-line tool bundled with the JDK for listing **instrumented Java HotSpot Virtual Machines** on a target system.

General syntax in JDK 24:

~~~bash
jps [-q] [-mlvV] [hostid]
jps --help
~~~

If `hostid` is omitted, jps searches for JVMs on the local machine. If `hostid` is provided, the tool queries JVMs on the specified host using the corresponding protocol and port.

jps displays the local VM identifier (LVMID) for each JVM found. On a local machine, the LVMID is typically the PID of the JVM process, though the JDK documentation explicitly notes that it is not guaranteed to always match the OS PID.

By default, the output has the form:

~~~text
lvmid  short-class-name-or-jar
~~~

Illustrative example:

~~~text
31840 com.example.ApiServer
31912 Jps
32004 com.example.BatchWorker
~~~

- 31840 is the LVMID of the JVM running `com.example.ApiServer`.
- 31912 is the jps process itself running at the time of listing.
- 32004 is the LVMID of the JVM running `com.example.BatchWorker`.

The numbers above are illustrative only. Actual PIDs vary by operating system, launch instance, and environment.

### jps is not a general process listing tool

jps only lists HotSpot JVMs that are detectable and within the access permissions of the current account. It does not replace `ps`, `tasklist`, or the operating system's process manager.

Some JVMs may not appear or may display incomplete information in the following cases:

- The JVM is running under another account that the current user does not have permission to observe.
- The JVM is running inside a container or a separate process namespace.
- The JVM was started with a custom launcher that prevents determining the class or JAR name.
- The process terminated while jps was collecting information.
- The JVM or platform does not support the enumeration mechanism used by jps.

If the tool cannot identify the launcher, the class or JAR name may appear as `Unknown`. In some situations, the output may report `process information unavailable`.

## 3. jps Options

JDK 24 supports the following options:

| Option | Meaning |
|---|---|
| -q | Displays only the local VM identifier, omitting class/JAR names and arguments |
| -m | Displays the arguments passed to the main method |
| -l | Displays the full package-qualified main class name or full path to the JAR |
| -v | Displays the arguments passed to the JVM |
| -V | Displays only the local VM identifier, similar to quiet mode |
| --help | Displays usage instructions |

You can combine `-m`, `-l`, and `-v` to see more details. Avoid enabling options that print command-line arguments if the output might contain secrets.

### -q: retrieve only the PID/LVMID

~~~bash
jps -q
~~~

Example output:

~~~text
31840
31912
32004
~~~

Use `-q` when you only need a list of identifiers for further lookup. Class/JAR names and arguments are suppressed.

### -l: full class name or JAR path

~~~bash
jps -l
~~~

Example output:

~~~text
31840 com.example.server.ApiServer
31912 jdk.jcmd/sun.tools.jps.Jps
32004 /opt/apps/batch-worker.jar
~~~

Depending on how the application was launched, jps displays the full main class name or the JAR path. This option is useful when multiple applications share the same short class name.

### -m: main method arguments

~~~bash
jps -m
~~~

Suppose an application is started with:

~~~bash
java com.example.BatchWorker nightly region-west
~~~

Illustrative output:

~~~text
32004 com.example.BatchWorker nightly region-west
~~~

The values after the class/JAR name are the arguments passed to `main(String[] args)`. For an embedded JVM, this section may be empty.

### -v: JVM arguments

~~~bash
jps -v
~~~

Example:

~~~text
31840 com.example.server.ApiServer -Xms512m -Xmx2g -Dapp.profile=production
~~~

The values after the class/JAR name are the arguments passed to the JVM, such as `-Xms`, `-Xmx`, `-Dsystem.property`, or other JVM flags.

**Security warning:** JVM arguments may contain passwords, tokens, connection strings, or other sensitive data if the application is insecurely configured. Do not paste full `-v` output into tickets, centralized logs, or chat channels. Use `-q` if you only need the PID, and redact sensitive values before sharing diagnostic output.

### -V: identifier only

In Oracle JDK 24 documentation, `-V` is also described as displaying only local VM identifiers, similar to the quiet output mode. Do not confuse this with older documentation from certain earlier JDK versions that described `-V` differently. Always check `jps --help` and the documentation for the exact JDK version you are using.

### Combining options

~~~bash
jps -lm
~~~

This command displays the LVMID, the full class/JAR name, and the main method arguments.

~~~bash
jps -lv
~~~

This command displays the full class/JAR name and the JVM arguments.

~~~bash
jps -mlv
~~~

This command displays the full class/JAR name, main arguments, and JVM arguments. The output can be long and risks exposing sensitive information.

## 4. Workflow for Finding a Java Application's PID

A common manual workflow is:

1. Run `jps` to list JVMs.
2. Use `-l` to distinguish classes/JARs when multiple applications are running.
3. Note the LVMID of the JVM to investigate.
4. Verify the PID using an operating system tool.
5. Use `jcmd` with the verified PID to inspect JVM details.
6. Perform process-impacting actions only after confirming the right service and authorization.

Example:

~~~bash
jps -l
~~~

Illustrative output:

~~~text
31840 com.example.ApiServer
32004 com.example.BatchWorker
~~~

Suppose you need to inspect `ApiServer`: take LVMID 31840 and verify the process.

### Linux or macOS

~~~bash
ps -p 31840 -o pid,ppid,user,etime,args
~~~

Columns:

- `pid`: process ID.
- `ppid`: parent process ID.
- `user`: account owning the process.
- `etime`: elapsed time the process has been running.
- `args`: command line.

### Windows PowerShell

~~~powershell
Get-Process -Id 31840 |
    Select-Object Id, ProcessName, StartTime
~~~

If you need the command line and parent PID:

~~~powershell
Get-CimInstance Win32_Process -Filter "ProcessId = 31840" |
    Select-Object ProcessId, ParentProcessId, Name, CommandLine
~~~

The command line may contain secrets. Only view or record the fields you need, and redact sensitive information before sharing.

### Why re-verify the PID?

jps and OS tools collect information at different points in time. A process may exit between the two commands, or the operating system may reuse the PID.

Before sending any command to a PID, confirm:

- The process still exists.
- The executable name or main class matches.
- The process owner user matches.
- The command line and deployment directory match.
- The start time is consistent.
- The process belongs to the intended host or container.

Never use an old PID saved from a previous check to stop or modify a process without re-verifying it first.

## 5. Using jcmd After Finding the PID

jps answers which JVMs are running. `jcmd` sends diagnostic commands to a specific JVM to gather deeper information.

List JVMs visible to `jcmd`:

~~~bash
jcmd -l
~~~

Check the JVM version:

~~~bash
jcmd 31840 VM.version
~~~

View the command line used to start the JVM:

~~~bash
jcmd 31840 VM.command_line
~~~

View current JVM flags:

~~~bash
jcmd 31840 VM.flags
~~~

List diagnostic commands supported by the JVM:

~~~bash
jcmd 31840 help
~~~

Capture a thread dump:

~~~bash
jcmd 31840 Thread.print
~~~

The `Thread.print` command helps investigate running or blocked threads. It does not change the PID; it collects thread states inside the JVM.

`jcmd` must run on the same machine as the target JVM and typically requires the same effective user/group ID that started the JVM. Access permissions depend on the operating system and runtime configuration.

### How do jps, jcmd, and ps differ?

| Tool | Scope | Purpose |
|---|---|---|
| jps | Observable HotSpot JVMs | List JVMs and LVMIDs |
| jcmd -l | Attachable JVMs, excluding certain isolated processes/containers | List JVMs for diagnostics |
| jcmd PID command | A specific JVM | Send a diagnostic command |
| ps / tasklist | Operating system processes | List and verify processes |
| ProcessHandle | Java API | Retrieve PID and process info from within a Java program |

`jcmd` provides many commands with varying levels of impact. Start with read-only commands such as `VM.version`, `VM.command_line`, `VM.flags`, and `help`. Commands like `GC.heap_dump`, `GC.run`, or operations that alter logging can generate load, write large files, or affect runtime behavior; read the command's `help` and assess the impact before running them in production.

## 6. PIDs in Containers and Multi-Namespace Environments

In containerized environments, the PID can differ between the host and the container due to PID namespaces.

Example:

~~~text
Host PID namespace
└── Container process: host PID 42000
    └── Container PID namespace
        └── Java process: container PID 1
~~~

Inside the container, the Java process may have PID 1. On the host, that same process may have PID 42000. These two numbers do not conflict; they are observed from two different namespaces.

The JDK 24 `jcmd` documentation explicitly states that `jcmd -l` does not list JVMs running in a separate Docker process. When a JVM runs inside a container, you may need to use container or OS tools to locate the PID.

Example:

~~~bash
docker top my-java-container
~~~

Or inspect processes inside the container:

~~~bash
docker exec my-java-container ps -ef
~~~

If the image does not include `ps`, you can use container management tools or inspect `/proc` in the appropriate PID namespace.

When working with processes in Kubernetes, distinguish between the PID inside the container and the PID on the node. Run diagnostics inside the right pod/container and use cluster management tools to identify the corresponding node, container, and service.

Never send `kill` or `jcmd` to a PID just because the number matches a PID observed on another host. Always verify the exact namespace and process.

## 7. Finding JVMs on a Remote Host

jps supports a host identifier (`hostid`) to query JVMs on another host.

The `hostid` syntax per the JDK documentation:

~~~text
[protocol:][[//]hostname][:port][/servername]
~~~

If only `hostname` is provided, the default protocol is RMI. jps assumes a `jstatd` process is running on the target host. If no port is specified for RMI, the default registry port is 1099.

Example:

~~~bash
jps -l app-host.example:1099
~~~

This requires `jstatd` and an appropriate RMI registry on the target machine, along with matching network access and security configuration. It is not a way to query arbitrary remote JVMs without prior setup.

### Notes on using jstatd

`jstatd` provides a JVM monitoring service over RMI. Exposing RMI or `jstatd` to a network can create a remote administration surface. Enable it only in approved environments, and restrict network access, authentication, and security configuration according to the JDK documentation.

An LVMID returned from a remote host is an identifier within that target environment. Do not pass that number to `kill` or `taskkill` on your local machine.

For production systems, it is generally better to use organization-approved monitoring agents, secured JMX, or infrastructure management tools rather than exposing RMI services solely to check PIDs.

## 8. Getting the PID Inside a Java Program with ProcessHandle

Since Java 9, the `ProcessHandle` API provides a way to obtain the current process's PID and access OS-level process information.

Java 17+ example:

~~~java
public final class PidDemo {
    public static void main(String[] args) {
        long pid = ProcessHandle.current().pid();
        System.out.println("PID=" + pid);
    }
}
~~~

Save as `PidDemo.java`.

Compile:

~~~bash
javac --release 17 PidDemo.java
~~~

Run:

~~~bash
java PidDemo
~~~

Sample output:

~~~text
PID=31840
~~~

The PID varies with the actual process and may differ on each run. In this example, 31840 is illustrative only.

### Looking up process information by PID

`ProcessHandle.of(long pid)` returns an `Optional<ProcessHandle>`. If the process does not exist or cannot be accessed, the `Optional` may be empty.

Example:

~~~java
import java.util.Optional;

public final class ProcessLookup {
    public static void main(String[] args) {
        if (args.length != 1) {
            System.err.println("Usage: java ProcessLookup <pid>");
            System.exit(2);
        }

        long pid = Long.parseLong(args[0]);
        Optional<ProcessHandle> result = ProcessHandle.of(pid);

        if (result.isEmpty()) {
            System.out.println("Process not found: " + pid);
            return;
        }

        ProcessHandle process = result.get();
        ProcessHandle.Info info = process.info();

        System.out.println("PID=" + process.pid());
        System.out.println("Alive=" + process.isAlive());
        System.out.println("Command=" +
                info.command().orElse("unavailable"));
        System.out.println("Start=" +
                info.startInstant().map(Object::toString)
                        .orElse("unavailable"));
    }
}
~~~

Compile:

~~~bash
javac --release 17 ProcessLookup.java
~~~

Run with an existing PID:

~~~bash
java ProcessLookup 31840
~~~

Illustrative output:

~~~text
PID=31840
Alive=true
Command=/path/to/java
Start=2026-11-10T10:00:00Z
~~~

The `Command` and `Start` values depend on the operating system and access permissions. In some environments, the command or start instant may be unavailable.

### Listing processes visible to the program

`ProcessHandle.allProcesses()` returns a snapshot of processes visible from the current process:

~~~java
ProcessHandle.allProcesses()
        .filter(process -> process.info().command()
                .map(command -> command.toLowerCase().contains("java"))
                .orElse(false))
        .forEach(process -> System.out.printf(
                "PID=%d COMMAND=%s%n",
                process.pid(),
                process.info().command().orElse("unavailable")
        ));
~~~

This snippet illustrates how to filter processes; output depends on the operating system and permissions. `allProcesses()` does not guarantee that every returned process is still alive when used, because processes can be created or terminated asynchronously.

### ProcessHandle is not a replacement for jps

- `ProcessHandle` is a Java API for identifying and interacting with native processes.
- `jps` is a JDK tool specifically for listing instrumented HotSpot JVMs.
- `ProcessHandle.allProcesses()` can see non-Java processes if the OS allows it.
- `jps` can provide the main class or JAR name in a JVM-oriented format.
- Both are constrained by OS permissions and process namespace boundaries.

If a program only needs its own PID, `ProcessHandle.current().pid()` is the direct approach. If external process management is needed, consider OS APIs or appropriate operational tools.

## 9. Troubleshooting Missing PIDs or JVMs

### jps does not show the application

Check:

1. Whether the application is still running or has already exited.
2. Whether you are using the right JDK and target host.
3. Whether the account running jps has permission to observe the JVM.
4. Whether the JVM is inside a container or a different PID namespace.
5. Whether the JVM was started with a custom launcher.
6. Whether the tool supports the JVM/runtime in use.
7. Try OS tools such as `ps`, `tasklist`, or `Get-Process`.

### Class name appears as Unknown

jps obtains class/JAR information from the launcher mechanism. If the JVM was started with a custom launcher or the metadata is unavailable, jps may be unable to determine the class/JAR name and arguments.

In that case, use OS process inspection, or `jcmd` if the PID and attach permissions are available.

### Process information unavailable

This message can appear if the process exits during collection or if permissions are insufficient. Re-check with an OS tool, then run `jps`/`jcmd` again once the process is stable.

### jcmd reports it cannot attach

Common causes:

- `jcmd` is not running on the same host.
- The user/group does not match the account that started the JVM.
- The PID no longer exists or has been reused.
- The JVM is in another container or namespace.
- The JVM does not support the Attach API or attach is disabled.
- The runtime and toolchain are incompatible.
- Operating system policies block attach.

Do not arbitrarily run tools with elevated privileges just to bypass an error. Confirm the owner, environment, and authorized access procedure first.

### The PID exists, but it belongs to a different process

PIDs can be reused. If the original Java process exited, the old PID may now belong to a new process. Verify the process name, command line, user, and start time before performing any process-impacting operation.

## 10. Using PIDs for Safe Diagnostics

Once the right JVM is identified, use tools in order of increasing impact.

| Goal | Suggested Command | Impact |
|---|---|---|
| List JVMs | jps -l | Read-only |
| Check version | jcmd PID VM.version | Read-only |
| Check flags | jcmd PID VM.flags | Read-only |
| View command line | jcmd PID VM.command_line | Read-only; may expose secrets |
| Inspect threads | jcmd PID Thread.print | Diagnostic collection; may add load |
| Inspect heap | jcmd PID GC.heap_info | Diagnostic collection |
| Create heap dump | jcmd PID GC.heap_dump file.hprof | High impact; writes a large file and may contain sensitive data |
| Stop process | Service manager or OS process tool | Alters service state |

Replace `PID` with the actual verified number. For high-impact commands, read `help` first and follow the service's runbook.

### Never stop a process based solely on a number

Before stopping a JVM:

1. Confirm the exact service and environment.
2. Confirm the process owner and command line.
3. Check whether active traffic, jobs, or transactions are running.
4. Prefer graceful shutdown via the service manager, application endpoint, or orchestration platform.
5. Use OS termination according to procedure only when graceful shutdown is not possible.
6. Confirm the service has stopped and run health checks after restart.

A PID alone does not tell you how critical a process is. Stopping the wrong PID can disrupt a service or cause loss of in-flight data.

## 11. Security When Viewing PIDs and Command Lines

Process information can reveal internal structure and sensitive data.

- `jps -v` can expose system properties and JVM arguments.
- `jps -m` can expose arguments containing user data or tokens.
- `jps -l` can reveal package names and installation paths.
- `jcmd VM.command_line` can expose the entire command line.
- `ProcessHandle.Info.commandLine()` may also contain sensitive data depending on the application.

Avoid passing secrets directly via JVM arguments or command lines when safer secret-management options exist. During audits, collect only necessary fields, redact sensitive values before saving, and restrict access to logs.

`jps` and `jcmd` also allow operators to inspect processes. Grant attach and diagnostic command permissions only to trusted accounts. Never expose `jstatd`/RMI or management endpoints to a public network merely for convenient PID lookup.

## 12. Is jps Suitable for Automation Scripts?

Oracle JDK 24 marks jps as experimental and unsupported. The documentation also warns that the output format may change and recommends against writing scripts that parse jps output.

The output is whitespace-delimited; arguments can contain spaces, making token-to-argument mapping ambiguous.

If automation is needed:

- Use the `ProcessHandle` API when logic lives inside a Java program.
- Use OS process APIs or orchestration platforms when managing services.
- Use approved JMX/monitoring agents for long-term JVM observability.
- Use `jcmd` for controlled diagnostic commands.
- Never assume a PID is a fixed identifier across restarts.
- Never parse jps output with naive string splitting and feed the result into a kill command.

### Choosing the right tool

| Need | Suitable Tool |
|---|---|
| Quickly find local JVMs | jps |
| List only LVMIDs | jps -q |
| View main class/JAR | jps -l |
| View JVM startup flags | jps -v or jcmd PID VM.flags |
| View full OS processes | ps, tasklist, Get-Process, ProcessHandle |
| Diagnose a specific JVM | jcmd PID command |
| View Java threads | jcmd PID Thread.print |
| Continuous monitoring | JMX/agent/monitoring platform |
| Manage container processes | Docker/Kubernetes and OS tools |

## 13. Checklist for Finding and Verifying a PID

- Identify the exact host, container, and PID namespace.
- Run `jps` in the matching JDK/runtime environment.
- Use `jps -l` when you need to distinguish classes/JARs.
- Use `jps -q` when you only need a list of LVMIDs.
- Limit `-m` and `-v` because they can expose command-line arguments.
- Record the LVMID and re-verify it with an OS process tool.
- Confirm process name, user, command line, and start time.
- Remember that an LVMID is usually, but not necessarily, the OS PID.
- Do not treat a PID as a permanent identifier; the OS can reuse PIDs.
- Run `jcmd` on the same host with appropriate permissions.
- Read `help` before running high-impact diagnostic commands.
- Use a service manager or orchestration platform to stop services according to procedure.
- Do not parse `jps` output as a stable automation interface.
- For containers, locate the PID in the correct namespace.
- Redact command lines and diagnostic output before sharing.
- Record evidence with the timestamp, host, runtime version, and service identity.

## 14. Key Terminology

| Term | Meaning |
|---|---|
| Process | A running program managed by the operating system |
| PID | Process ID assigned by the operating system |
| PPID | PID of the parent process |
| LVMID | Local VM identifier displayed by JVM tools |
| JVM process | A process running a Java Virtual Machine |
| Java thread | A thread of execution inside the JVM |
| OS thread ID | Thread identifier at the operating system level |
| jps | JDK tool that lists instrumented HotSpot JVMs |
| jcmd | Tool for sending diagnostic commands to a JVM |
| jstatd | Service that allows `jstat`/`jps` tools to access JVM info remotely over RMI |
| ProcessHandle | Java API for identifying and interacting with native processes |
| PID namespace | Mechanism for isolating PID spaces, commonly used in containers |
| PID reuse | Operating system reusing a PID after a previous process exits |
| Attach API | Mechanism allowing tools to attach to a running JVM |
| Diagnostic command | Command that collects or affects JVM state |

`jps` is a quick way to locate JVMs and LVMIDs on a local machine. Treat the PID as a temporary identifier, verify it with an operating system tool, and then use `jcmd` or `ProcessHandle` to gather the information you need. In containers, remote environments, and production, always confirm the right host/namespace, access permissions, and impact level before interacting with a process.
