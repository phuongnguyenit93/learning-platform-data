# Listing Java Processes with jps

**jps** (Java Virtual Machine Process Status Tool) is a command-line tool included with the JDK for listing instrumented JVMs on a target machine that the current user has permission to access. It helps you quickly identify running Java applications, retrieve the local VM identifier, and view the launch class/JAR name along with certain application and JVM arguments.

Basic command:

~~~bash
jps
~~~

The output typically looks like this:

~~~text
57916 ProcessProbe
58320 Jps
~~~

The first column is the **local VM identifier (lvmid)**. The next column is the short name of the main class or JAR. The `Jps` line may be the `jps` process itself that you just ran.

When you need the full class name, application arguments, and JVM arguments:

~~~bash
jps -lmv
~~~

Example:

~~~text
57916 com.example.ProcessProbe alpha beta -Ddemo.mode=sample -Xms16m
~~~

Where:

- 57916 is the lvmid of the JVM.
- com.example.ProcessProbe is the fully qualified name of the main class.
- alpha beta are the arguments passed to the main method.
- -Ddemo.mode=sample and -Xms16m are arguments passed to the JVM at startup.

The lvmid changes on each run. It often matches the operating system process PID, though this is not guaranteed in every case.

## 1. What Is jps Used For?

In Java development and operations environments, a single machine may run multiple JVMs simultaneously:

- Backend applications.
- Application servers.
- IDEs.
- Build daemons.
- Java test runners.
- JShell.
- Monitoring or diagnostic tools.
- Java processes embedded in native applications.

When you need to check which JVMs are running, jps provides a concise list without requiring you to read the entire operating system process list.

Common practical scenarios:

- Finding the JVM of a service that needs diagnostics.
- Distinguishing between multiple applications that share the same main class name, such as Main.
- Identifying the PID/lvmid before running jcmd.
- Checking whether specific JVM arguments were passed at startup.
- Determining whether an application was launched from a class or a JAR.
- Verifying whether a JVM is still running after a restart or deployment.

jps is a quick discovery and diagnostic tool. It does not replace a process manager, service supervisor, container orchestrator, or production monitoring system.

## 2. Which Processes Does jps List?

jps searches for **instrumented Java HotSpot VMs** on the target machine. It only displays JVMs that the current account is permitted to access under the operating system and JVM security mechanisms.

This means:

- jps is not a list of all operating system processes.
- A JVM run by another user may not appear.
- A JVM with restricted attach access or without appropriate metadata may not be listed.
- A JVM running in a different container or process namespace may not be visible in the same scope.
- A JVM using a custom launcher may display `Unknown` instead of a class/JAR name.
- A JVM may terminate right after jps reads the list, creating a race condition when you use the lvmid for follow-up diagnostics.

If jps does not display an application, you cannot immediately conclude that the application is not running. Also check the operating system process list, service manager, container runtime, and access permissions.

### jps May Also Appear in the List

When running jps, the jps process itself may be listed in the output:

~~~text
58320 Jps
~~~

This is normal behavior. Do not mistake the Jps line for the target application.

## 3. Installing and Verifying the jps Command

jps is located in the JDK's `bin` directory. Use an installed JDK and ensure `PATH` points to the correct `bin` directory.

Check on Windows PowerShell:

~~~powershell
Get-Command jps
where.exe jps
~~~

Linux/macOS:

~~~bash
which jps
command -v jps
~~~

View supported syntax:

~~~bash
jps --help
~~~

Check the Java version being invoked:

~~~bash
java -version
~~~

jps is not part of a minimal JRE runtime. If a system only has a stripped-down runtime image without diagnostic tools, the `jps` executable may not be present.

Use `jps` from the JDK that matches the environment under investigation. When multiple JDKs are installed on the machine, verify the actual paths of `jps` and `java` to avoid accidentally using a tool from a different JDK.

## 4. Output Structure

The general output format of jps is:

~~~text
lvmid [ [classname | JARfilename | "Unknown"] [arg*] [jvmarg*] ]
~~~

Components:

| Component | Meaning |
|---|---|
| lvmid | Local VM identifier of the JVM |
| classname | Main class used to launch the application |
| JARfilename | JAR used as the entry point |
| Unknown | The tool could not determine the class/JAR |
| arg | Argument passed to the main method |
| jvmarg | Argument passed to the JVM at startup |

Tokens in the output are separated by whitespace. If an argument contains spaces, mapping tokens back to individual arguments can become ambiguous. Therefore, the JDK documentation recommends against writing scripts that depend on parsing jps output; the format may also change across releases.

### lvmid and PID

The lvmid typically matches the operating system process PID. However, the exact name of this column is local VM identifier, and you should not assume a one-to-one correspondence with the OS PID in all environments or implementations.

If you need to perform OS-level operations such as terminating a process, verify the PID with an operating system tool before taking action. Do not take a number from jps output and assume it is a valid PID in every environment.

### Class and JAR Names

If an application is launched using a main class:

~~~text
57916 com.example.ProcessProbe
~~~

If launched using an executable JAR, the JAR name may appear instead of the class name.

Without options, jps usually displays the short form, omitting the package or JAR path. Use `-l` to see the fuller form.

## 5. Important Options

### Show Only the Local VM Identifier: -q

~~~bash
jps -q
~~~

The `-q` option suppresses the class/JAR name and main method arguments, leaving only the list of local VM identifiers.

Example:

~~~text
57916
58320
94336
~~~

Use this when you only need a list of IDs or want to reduce output verbosity.

### Show the Full Name: -l

~~~bash
jps -l
~~~

`-l` displays the full package name of the main class or the full path to the launch JAR.

Example:

~~~text
57916 com.example.ProcessProbe
58320 jdk.jcmd/sun.tools.jps.Jps
~~~

For modular applications, the output may include the module/class format as presented by the tool. For JARs, the output may contain the full file path.

Use `-l` when multiple applications share the same short name such as `Main`, `Server`, or `Launcher`.

### Show Main Method Arguments: -m

~~~bash
jps -m
~~~

`-m` displays the arguments passed to the main method.

If launched with:

~~~bash
java com.example.ProcessProbe alpha beta
~~~

the output may look like:

~~~text
57916 ProcessProbe alpha beta
~~~

For some embedded JVMs, the main arguments value may be `null` or unavailable.

Main arguments are not the same as JVM arguments. For example, `alpha` and `beta` belong to the application; they are not `-Xmx` or `-Dproperty`.

### Show JVM Arguments: -v

~~~bash
jps -v
~~~

`-v` displays the arguments passed to the JVM at startup.

Example:

~~~text
57916 ProcessProbe -Ddemo.mode=sample -Xms16m -Xmx512m
~~~

Common groups of arguments:

- -Xms: initial heap size.
- -Xmx: maximum heap size.
- -Dname=value: system property.
- -XX:+UseG1GC: enables a JVM flag.
- -XX:MaxMetaspaceSize=...: limits metaspace size.

Actual output depends on how the JVM was launched and the JDK version. Not all settings appear as simple arguments; some values may come from environment variables, configuration files, or the launcher mechanism.

**Security note:** `-v` can expose sensitive information if an application passes passwords, tokens, or secrets via command-line arguments or system properties. Never paste raw output into tickets, chats, or public logs before reviewing and redacting sensitive data.

### Combining Options

You can combine `-m`, `-l`, and `-v`:

~~~bash
jps -lmv
~~~

This is useful when you need to identify an application and understand how its JVM was started.

These options can be combined according to jps syntax. Use only the combination you need to avoid overly long output or exposing command-line secrets.

## 6. Distinguishing Main Arguments from JVM Arguments

This is a key point when reading jps output.

Consider the launch command:

~~~bash
java -Ddemo.mode=sample -Xms16m \
    -cp build/classes \
    com.example.ProcessProbe alpha beta
~~~

Classification:

| Value | Type | Displayed by jps |
|---|---|---|
| -Ddemo.mode=sample | JVM system property | -v |
| -Xms16m | JVM option | -v |
| -cp build/classes | Startup classpath option | Depends on how the tool presents metadata |
| com.example.ProcessProbe | Main class | Default or -l |
| alpha beta | Main method arguments | -m |

Do not confuse `-m` with `-v`:

- `-m` answers which arguments the application received in `main`.
- `-v` answers which startup arguments the JVM received.

If you want to see both, use `-lmv`.
## 7. Complete Java 17+ Example: Creating a Process for jps to Find

This example creates a Java process that runs for two minutes. During that time, open a second terminal and use jps to list the process.

Structure:

~~~text
jps-demo/
└── src/
    └── com/
        └── example/
            └── ProcessProbe.java
~~~

### ProcessProbe.java

~~~java
package com.example;

public final class ProcessProbe {
    private ProcessProbe() {
    }

    public static void main(String[] args) throws InterruptedException {
        System.out.println("ProcessProbe started");
        Thread.sleep(120_000);
    }
}
~~~

### Compile with Java 17+

From the `jps-demo` root directory:

Linux/macOS:

~~~bash
mkdir -p build/classes

javac --release 17 \
    -d build/classes \
    src/com/example/ProcessProbe.java
~~~

Windows PowerShell:

~~~powershell
New-Item -ItemType Directory -Force build/classes | Out-Null
javac --release 17 -d build/classes src/com/example/ProcessProbe.java
~~~

### Run the Process

~~~bash
java -Ddemo.mode=sample -Xms16m \
    -cp build/classes \
    com.example.ProcessProbe alpha beta
~~~

Program output:

~~~text
ProcessProbe started
~~~

The program sleeps for 120 seconds. Leave this terminal open and open a second terminal.

### List JVMs

~~~bash
jps
~~~

You will see a line with the short name `ProcessProbe` and its lvmid. Other Java processes running on the machine may also appear.

### View Full Name and Arguments

~~~bash
jps -lmv
~~~

Sample output observed on JDK 24.0.2:

~~~text
57916 com.example.ProcessProbe alpha beta -Ddemo.mode=sample -Xms16m
~~~

`57916` is just the lvmid from that test run; the number will differ on your machine.

### Verify Each Option

~~~bash
jps -l
jps -m
jps -v
jps -q
~~~

You can compare:

- `-l` displays `com.example.ProcessProbe`.
- `-m` displays `alpha beta`.
- `-v` displays `-Ddemo.mode=sample` and `-Xms16m`.
- `-q` displays only the lvmid.

After 120 seconds, the process exits and no longer appears in subsequent `jps` runs.

## 8. Listing Remote Java Processes with hostid

jps supports specifying a `hostid` to find JVMs on a remote machine. With a hostname, the tool uses RMI and assumes `jstatd` is running on the target host.

Example:

~~~bash
jps -l app-server.example.com
~~~

Specify the RMI registry port:

~~~bash
jps -lm app-server.example.com:1099
~~~

The full `hostid` form can include protocol, hostname, port, and server name:

~~~text
[protocol:][[//]hostname][:port][/servername]
~~~

When a hostname is specified without a protocol, the default protocol is `rmi`. The default RMI registry port is `1099` if no port is specified.

Remote listing requires:

- `jstatd` running on the target host.
- An operational RMI registry according to configuration.
- Firewall rules allowing connections to the required ports.
- Appropriate access permissions and security configuration.
- `jps` on the source machine using the correct `hostid`.

Do not expose `jstatd` on a public network or grant overly broad access. This is a remote diagnostic tool; restrict network access, identities, and permissions according to operational policy.

Remote `jps` is not a substitute for a monitoring agent or service discovery. If you only need to diagnose a single machine, prefer running `jps` directly on that host.

## 9. Limitations and Support Status of jps

The JDK documentation describes jps as an **experimental and unsupported** tool. Its options and output format may change or be removed in future releases.

Key limitations to keep in mind:

- Lists only JVMs that the tool has permission to access.
- Not guaranteed to show every Java process on the operating system.
- Not guaranteed that the lvmid is always the OS PID.
- Class/JAR name may appear as `Unknown` if the JVM uses a custom launcher.
- Main arguments may be unavailable for embedded JVMs.
- Output is whitespace-delimited, which can be ambiguous if arguments contain spaces.
- A process may exit immediately after being listed.
- Container/process namespaces and attach policies can affect JVM visibility.
- Not a stable interface for production scripts.

Therefore, use jps for manual discovery and investigation. If you need reliable automation, use an appropriate process management API, service manager, container orchestration, JMX/metrics, or a supported monitoring tool.

## 10. Why Can't jps Find an Application?

### Running jps as a Different User

jps is constrained by operating system access permissions. If the application runs under a different user, your current jps invocation may not be able to list it.

Check which account runs the service and invoke the tool with an identity permitted to access it. Do not grant broader privileges than necessary just to get a complete list.

### The Application Has Already Exited

If the JVM terminates before or while jps queries it, it will no longer appear. Check the service status and run the command again.

### JVM Uses a Custom Launcher or Embedded Mode

If the JVM was created using the JNI Invocation API or a custom launcher, jps may not be able to locate the main class/JAR name. Output may show `Unknown` or omit main arguments.

Use the OS process list, service metadata, or application logs to identify the process.

### Attach Is Restricted

Some environments disable or restrict the Attach API. Containers, filesystem permissions, user namespaces, or runtime policies can affect discovery.

Check the JVM configuration and access permissions against the documentation for your JDK. Do not enable attach for all processes unless your environment requires it.

### Wrong JDK on PATH

`PATH` may point to a different JDK than the one running the application. Check:

~~~powershell
Get-Command java
Get-Command jps
~~~

Or on Linux/macOS:

~~~bash
which java
which jps
java -version
~~~

### Application Running in Another Container

jps on the host will not necessarily see JVMs inside containers with separate process namespaces. Run the tool inside the target container or use container management tools to inspect processes.

### Displayed Name Is Unknown

The class/JAR name is unavailable via launcher metadata. Use the lvmid together with OS process inspection and log/service metadata to identify it.

## 11. Using lvmid with jcmd for Further Diagnostics

Once you have located the target JVM, you can use `jcmd` to issue diagnostic commands.

List JVMs visible to `jcmd`:

~~~bash
jcmd -l
~~~

View commands supported by the target JVM:

~~~bash
jcmd <pid> help
~~~

For example, view the JVM command line:

~~~bash
jcmd <pid> VM.command_line
~~~

View JVM flags:

~~~bash
jcmd <pid> VM.flags
~~~

View version information:

~~~bash
jcmd <pid> VM.version
~~~

Replace `<pid>` with the appropriate process identifier. Verify that the lvmid actually works as a PID in that environment; if not, find the PID using an operating system tool.

jps only helps you locate the JVM. `jcmd` provides deeper diagnostic commands, so only run appropriate commands while understanding their impact.

## 12. Comparing jps with Operating System Process Lists

| Tool | Scope | Key Information |
|---|---|---|
| jps | Instrumented JVMs the user has permission to access | lvmid, main class/JAR, main args, JVM args |
| jcmd -l | JVMs listable via the Attach API | PID and JVM identification info |
| ps | Operating system processes | PID, user, command line |
| Get-Process | Windows processes | PID, process name, and process info |
| Get-CimInstance Win32_Process | Windows processes | PID, executable path, command line |
| Service manager | Managed services | service status, configuration, and lifecycle |

Linux/macOS:

~~~bash
ps -eo pid,user,args
~~~

Windows PowerShell:

~~~powershell
Get-CimInstance Win32_Process |
    Select-Object ProcessId, Name, ExecutablePath, CommandLine
~~~

OS process lists can show more processes than jps, though they lack deep awareness of JVM structure. Conversely, jps focuses on JVMs but is limited by permissions and instrumented process visibility.

A process command line may contain passwords or tokens. Review and redact sensitive data before sharing output.

## 13. Should You Parse jps Output in Scripts?

You should not build automation that depends on the text output of jps.

Reasons:

- jps is documented by the JDK as experimental/unsupported.
- Output format may change between releases.
- Tokens are whitespace-delimited, so arguments with spaces cause ambiguity.
- The class name can be `Unknown`.
- The list depends on access permissions and process state at scan time.
- The lvmid is not guaranteed to always be the OS PID.

If you need process monitoring, use:

- The `ProcessHandle` API if a Java application needs to observe OS processes.
- A service manager or container orchestration for service lifecycle management.
- JMX or metrics for runtime information.
- `jcmd` for controlled diagnostic operations.
- OS process APIs for operational scripts that need PIDs/command lines.

If you still must parse jps in an internal script, treat it as a fragile integration, constrain the JDK scope, verify the version, handle `Unknown` and whitespace carefully, and provide a fallback.

## 14. Workflow for Using jps During Incident Investigation

1. Run `jps` to see which JVMs are currently visible.
2. Use `-l` to identify the full main class/JAR.
3. Use `-m` to distinguish applications by their main arguments.
4. Use `-v` when you need to inspect JVM arguments and system properties.
5. Record the lvmid and verify the PID if OS-level actions are needed.
6. Run `jcmd -l` to cross-check the list of attachable JVMs.
7. Run `jcmd` with the appropriate diagnostic command.
8. If the process does not appear, check the user account, container, attach policy, and service status.
9. Never share `-m`/`-v` output before removing secrets.
10. Record the JDK version and timestamp, as the process list changes continuously.

jps is well suited for the initial step of identifying a JVM in an environment with multiple Java applications. By understanding lvmid, distinguishing main arguments from JVM arguments, recognizing permission limits, and combining jps with jcmd and OS tools, you can pinpoint the right process for further diagnostics.
