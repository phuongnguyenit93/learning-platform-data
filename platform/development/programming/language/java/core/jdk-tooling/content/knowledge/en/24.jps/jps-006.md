# Listing Remote Java Processes with `jps`

`jps` (Java Virtual Machine Process Status Tool) lists the instrumented HotSpot JVMs recognized by the tool on a system. When you need to query another machine, `jps` accepts an additional `hostid`. Traditional remote connectivity relies on a `jstatd` service running on the target machine, using Java RMI to provide the process list to the client.

Core command:

~~~text
jps -l server.example.internal:1099
~~~

In this example, `server.example.internal` is the target host and `1099` is the RMI Registry port. The target host must be running `jstatd`, and the client must be able to reach both the registry and the RMI connector advertised by the daemon.

There is an important limitation with modern toolchains: on JDK 24, `jstatd` is marked as experimental, unsupported, and deprecated for removal. The service also does not authenticate remote clients. Therefore, the content below is useful for understanding legacy systems, testing in isolated networks, and handling migration; you should not deploy an open RMI service on a production network.

The toolchain used to verify this article is Zulu/OpenJDK 24.0.2. `jps` and `jstatd` syntax may differ across JDKs; always check `jps --help` and `jstatd --help` on the exact machine you are operating.

## 1. How Does Remote `jps` Work?

When running `jps` without a hostid, the tool discovers instrumented JVMs on the local machine. When a hostname is provided, the client uses RMI to query `jstatd` on that machine.

Workflow:

~~~text
Remote Java applications
       |
       v
Target host: jstatd
       |
       +--> RMI Registry (for example port 1099)
       |
       +--> RMI connector (fixed or dynamic port)
                    |
                    v
             Network / RMI
                    |
                    v
Client machine: jps host:registry-port
                    |
                    v
          Remote JVM process list
~~~

`jstatd` monitors instrumented HotSpot JVMs running on the same host where the daemon operates. It is not an agent installed inside each application, nor is it a general-purpose process management service for every type of runtime.

Key characteristics:

- `jps` only lists JVMs that the user and the operating system's access mechanisms allow it to see.
- LVMID is the local VM identifier; it usually matches the OS PID, though this is not guaranteed in all cases.
- The output does not necessarily contain every Java process on the host.
- JVMs running inside Docker/containers may not appear in the host's list.
- The class/JAR name and arguments may be unavailable if the JVM was launched via a custom launcher.

## 2. `jps` and `hostid` Syntax

Syntax shown in JDK 24.0.2:

~~~text
jps [--help]
jps [-q] [-mlvV] [<hostid>]
~~~

The help output for this version describes `hostid` simply as:

~~~text
<hostname>[:<port>]
~~~

Examples:

~~~text
jps
jps -l
jps -l app-server.example.internal
jps -l app-server.example.internal:1099
~~~

- No hostid: queries the local machine.
- With hostname: queries the remote machine using RMI by default.
- With `:port`: specifies the RMI Registry port on the target host.
- Without port: the default RMI Registry port is `1099`.

Some JDK documentation describes `hostid` in full URI form:

~~~text
[protocol:][[//]hostname][:port][/servername]
~~~

The `/servername` part is used when `jstatd` is configured with a custom RMI object name via `-n`. However, the JDK 24.0.2 help in the test environment only advertises the `hostname[:port]` form. Only use the server name suffix if the documentation for your exact JDK client confirms support.

## 3. `jps` Display Options

Commonly used options:

| Option | Meaning |
|---|---|
| `-q` | Display only the LVMID |
| `-m` | Display arguments passed to `main()` |
| `-l` | Display the full class name or JAR path |
| `-v` | Display JVM arguments |
| `-V` | Per JDK 21 documentation, suppress class/JAR and main arguments, keeping only LVMID |
| `--help` | Display help |

Examples:

~~~text
jps -q server.example.internal:1099
jps -l server.example.internal:1099
jps -m server.example.internal:1099
jps -v server.example.internal:1099
~~~

`-m` and `-v` can expose sensitive information. Command-line arguments sometimes contain tokens, passwords, URLs with credentials, internal paths, or configuration details. Use them only when necessary and restrict who can view the output.

`-l` is useful for distinguishing applications that share the same short main class name. `-q` is suitable when you only need a list of identifiers. Do not save `-v` output to CI logs or unrestricted tickets by default.

## 4. Setting Up and Starting `jstatd` on the Target Host

`jstatd` requires an RMI Registry. If no registry is found on the selected port, the daemon can create an internal registry automatically, unless `-nr` is specified.

Example using an internal registry and fixing both ports:

~~~text
jstatd -p 1099 -r 1100
~~~

Meaning:

- `-p 1099`: RMI Registry port.
- `-r 1100`: exported RMI connector port.
- If `-r` is omitted, the connector may use a random port, making firewall and NAT configuration unpredictable.
- If `-p` is omitted, the registry defaults to `1099`.

On hosts with multiple network interfaces or NAT, you may need to configure the address that RMI advertises to clients:

~~~text
jstatd -p 1099 -r 1100 -J-Djava.rmi.server.hostname=server.example.internal
~~~

The `java.rmi.server.hostname` value must be a hostname or IP address that the client machine can resolve and connect to. Do not use `127.0.0.1` for clients on other machines; loopback addresses are only suitable for tests on the same machine.

### 4.1. Using an External RMI Registry

If your organization already runs a dedicated RMI Registry, `jstatd` can connect to that registry:

~~~text
rmiregistry 2020
jstatd -nr -p 2020 -r 2021
~~~

- `rmiregistry 2020`: starts the registry on port 2020.
- `-nr`: do not create an internal registry if no external registry is found.
- `-p 2020`: connect to the registry on port 2020.
- `-r 2021`: fix the RMI connector port.

If the external registry is not yet running, `jstatd -nr` will not create a fallback registry and the command may fail.

## 5. Meaning of `jstatd` Options

According to JDK 24.0.2 help:

| Option | Meaning |
|---|---|
| `-nr` | Do not create an internal RMI Registry when an existing registry is not found |
| `-p port` | RMI Registry port to connect to or create |
| `-r rmiport` | Fixed port for the RMI connector |
| `-n rminame` | Name of the RMI object bound in the registry |
| `-Joption` | Pass a JVM option to the `jstatd` process |

The default RMI object name is `JStatRemoteHost`. If running multiple `jstatd` instances on the same host, `-n` can assign different names; the client must use a `hostid` matching the server name according to the syntax supported by that `jps` version.

`-p` and `-r` are two ports with distinct roles. When a firewall only allows port 1099 while the RMI connector is exported on a different port, the client may reach the registry but still fail to complete the connection.

## 6. Connecting from Client to Remote Host

When the daemon is running on the target host, the client invokes:

~~~text
jps -l server.example.internal:1099
~~~

If the registry runs on a different port:

~~~text
jps -l server.example.internal:2020
~~~

To view main arguments:

~~~text
jps -m server.example.internal:2020
~~~

To view full class/JAR names:

~~~text
jps -l server.example.internal:2020
~~~

The LVMID in the output belongs to the target system. Do not confuse that LVMID with the PID of the `jps` process on the client. If you need to perform further operations on the target JVM, you must run diagnostic tools on the right host and in the right namespace.

## 7. Opening Network Ports and RMI Routing

For a client query to succeed, verify the entire RMI path:

1. DNS or hostname resolves to the correct target host address.
2. The RMI Registry port (`-p`) is reachable from the client.
3. The RMI connector port (`-r`) is reachable from the client.
4. The RMI stub advertises a hostname/IP routable from the client.
5. Firewalls, NAT, and network policies allow both connections.
6. No other service is occupying the chosen ports.

Configuration example:

~~~text
Target host: app-server.example.internal
Registry port: 1099
RMI connector port: 1100
Client query: jps -l app-server.example.internal:1099
~~~

The `hostid` uses the registry port (`1099`), not the connector port (`1100`). The RMI Registry returns a stub containing the connector endpoint, so both ports are critical.

Do not open random RMI ports across the entire network. If `-r` is not fixed, the connector may use different ports across restarts, making firewall rules and connectivity checks difficult to manage.

## 8. Access Permissions and Process Visibility Limits

`jstatd` can only monitor JVMs for which it has native access permission. Therefore, the daemon must run under credentials appropriate for the target JVMs.

On Unix-like operating systems, running the daemon as root may make more JVMs visible, but it also widens the scope of exposed data. Do not run the daemon with higher privileges than necessary just to get a longer list.

Reasons a process may not appear:

- The JVM was started by a different user and the OS does not allow instrumentation access.
- The JVM is not HotSpot or is not instrumented using the mechanism supported by `jps`.
- The process exited before the query.
- The JVM is running in a different Docker/container namespace.
- The JVM was launched via a custom launcher, preventing class/JAR identification.
- The runtime environment restricts attach/instrumentation.

The `jps` output is a list of JVMs observable under the tool's permissions and mechanisms, not a complete inventory of every Java process on the machine.

## 9. Security Risks of `jstatd`

This is the most critical limitation of remote `jps`: Oracle JDK 24 documentation explicitly states that `jstatd` provides no authentication for remote clients.

This means any user with network access to the service can view instrumentation data for any JVM that the `jstatd` account is permitted to access. Process details, class/JAR names, and runtime arguments can reveal application architecture or internal configuration.

Key points to understand:

- The RMI Registry does not provide client authentication for `jstatd` on its own.
- Firewalls restricting source access can reduce the exposure surface, but they do not turn the service into an authenticated protocol.
- Running `jstatd` with a privileged account can expose information from more JVMs.
- `jstatd` uses an RMI `ObjectInputFilter` to restrict deserialized classes; this does not replace user authentication.
- The remote interface is proprietary and is guaranteed to be subject to change.

Do not expose `jstatd` directly to the Internet or untrusted networks. If you only need one-off diagnostics, prefer SSHing into the target host and running `jps` locally. If your organization needs long-term monitoring, use a management/monitoring system with authentication, authorization, and TLS in accordance with operational policy.

## 10. Support Status and Changes in JDK 24

Distinguish the support status of the two tools:

- `jps`: JDK documentation describes it as experimental and unsupported.
- `jstatd`: as of JDK 24, marked as experimental, unsupported, and deprecated for removal; it will be removed in a future release.

When running `jstatd` on JDK 24.0.2, the tool prints a deprecation warning. This is not a syntax error, but a signal to plan a migration away from the remote RMI workflow.

Some older JDK guides require a Security Manager and policy file for `jstatd`. JDK 24 has changed Security Manager policies, and current `jstatd` documentation no longer presents the legacy policy workflow as the default setup. Do not copy policy files from older JDK guides without checking the documentation for your exact runtime.

Do not build new systems with long-term dependencies on the `jstatd` remote interface. Verify whether the tool is still present in your target JDK release and prepare alternatives before upgrading.

## 11. Testing Remote `jps` on `localhost`

The lab below runs solely on the loopback interface of the same machine. Do not open the example ports to the network.

### 11.1. Creating a Target JVM Application

File `RemoteTarget.java`:

~~~java
import java.util.concurrent.TimeUnit;

public final class RemoteTarget {
    private RemoteTarget() {
    }

    public static void main(String[] args) throws InterruptedException {
        System.out.println(
                "RemoteTarget ready; pid=" + ProcessHandle.current().pid());

        TimeUnit.MINUTES.sleep(5);
    }
}
~~~

Compile:

~~~text
javac --release 17 RemoteTarget.java
~~~

Run in the first terminal:

~~~text
java RemoteTarget
~~~

Output:

~~~text
RemoteTarget ready; pid=<runtime-pid>
~~~

`<runtime-pid>` is the PID assigned by the JVM on the current machine, so its value changes on each run.

### 11.2. Starting `jstatd` on Loopback

In a second terminal, use two test ports not used by any other process:

~~~text
jstatd -p 11999 -r 11998 -J-Djava.rmi.server.hostname=127.0.0.1
~~~

This configuration creates the registry on port 11999 and fixes the connector on port 11998. Depending on how it is launched and the platform, the `jstatd` script may run the daemon in the background.

### 11.3. Querying with `jps`

In a third terminal:

~~~text
jps -l localhost:11999
~~~

The output lists instrumented JVMs visible to `jstatd`, including the `RemoteTarget` application if permissions and the environment allow. The PID and other processes will vary by machine.

You can also inspect main arguments:

~~~text
jps -m localhost:11999
~~~

When finished, stop `jstatd` and the test application. Do not leave the RMI service running after the lab.

## 12. Automation and Output Limitations

You can invoke `jps` in scripts to collect process lists, but the documentation warns against relying on parsing its output long-term because the format is subject to change.

Do not assume:

- Every line always contains a PID, class name, and arguments.
- Whitespace-separated tokens can be reconstructed into the original arguments.
- LVMID is always the OS PID.
- An `Unknown` line indicates a JVM error.
- The process list is complete across all users/containers.

If you need a stable inventory for automation, use the API of your process manager, service manager, or container orchestrator instead of parsing `jps` output.

If you only need to display the list in a terminal for an operator, `jps -l host:port` is usually easier to read than `-v`, while avoiding printing full JVM arguments that may contain secrets.

## 13. Docker, Containers, and PID Namespaces

JDK 24 `jstatd` documentation notes that the `jps` list may not include JVMs running inside Docker containers.

The cause typically relates to process namespace boundaries and instrumentation access permissions. The PID on the host may differ from the PID inside the container; a daemon on the host does not necessarily see JVMs the way it would when running in the same namespace.

Practical approaches:

- Run `jps -l` inside the container to list JVMs visible to that container.
- Use `docker exec` or the equivalent container runtime command to run the tool in the right namespace.
- Use the Kubernetes/container orchestrator API to identify the pod/container first.
- For deeper investigation, access the container or host per operational procedures and use `jcmd`, GC logs, or JFR as appropriate.

Do not treat `jps host:port` as an inventory tool for an entire container cluster.

## 14. Alternatives for Remote Process Discovery

Because `jstatd` is deprecated and lacks authentication, choose the right tool for your needs:

| Need | Better Approach |
|---|---|
| List Java processes on a remote host | SSH into the host and run `jps -l` or OS process commands |
| List JVMs inside a container | Run `jps -l` inside the container or use the orchestrator |
| Inspect runtime flags of a JVM | Access the host/container and run `jcmd <pid> VM.flags` |
| View heap/thread/GC diagnostics | Use local `jcmd`, GC logs, and heap dumps per procedure |
| Long-term remote monitoring | JMX configured with authentication/TLS or a secured monitoring agent |
| Event and performance analysis | Java Flight Recorder (JFR) and recording collection systems |

SSH does not turn `jps` into a remote RMI protocol; it simply executes the command on the target host over an authenticated login channel. This approach is usually easier to control than exposing unauthenticated `jstatd` to the network.

## 15. Troubleshooting

### `RMI Registry not available`

**Cause:** no registry is listening on the port the client is querying, wrong `-p`, or the daemon was started with `-nr` while the external registry is not yet running.

**Resolution:** verify the registry is listening on the expected port; confirm `jstatd -p` and `jps host:port` use the same registry port.

### `Connection refused`

**Cause:** the service is not listening, the daemon has stopped, a firewall is rejecting the connection, or the client is connecting to the wrong address/port.

**Resolution:** check the `jstatd` process, listeners on both `-p` and `-r`, firewalls, and DNS.

### Registry Found but Query Still Times Out

**Cause:** the RMI connector port is unreachable or the RMI stub advertises a hostname not routable from the client.

**Resolution:** fix `-r`, verify connector port reachability, and configure `java.rmi.server.hostname` to an address the client can actually reach.

### Empty List or Missing JVMs

**Cause:** the user running the daemon lacks permission to access the target JVM's instrumentation, the process is not an instrumented JVM supported by `jps`, or the process is in another container.

**Resolution:** run the daemon with appropriate credentials, check PID namespaces, and try `jps -l` directly on the host/container.

### Class Name Shows `Unknown`

**Cause:** the JVM was launched via a custom launcher, or the tool cannot retrieve the class/JAR name in the standard way.

**Resolution:** use the OS process manager or service metadata to identify the application; do not treat `Unknown` as evidence of a broken JVM.

### Correct Registry Port but `-n` Does Not Work

**Cause:** the custom RMI object name does not match the `hostid` syntax supported by the client.

**Resolution:** verify `-n` on the daemon and check the `hostid` syntax for your exact `jps` version; if the client does not support the servername suffix, use the default name or an alternative tool.

### `jstatd` Prints a Deprecation Warning

**Cause:** JDK 24 marks `jstatd` as deprecated for removal.

**Resolution:** determine whether this is a legacy system needing short-term compatibility or a workflow requiring migration; prefer SSH/local diagnostics, secured JMX, JFR, or a monitoring agent.

### Output Exposes Sensitive Arguments

**Cause:** using `-m` or `-v` without restricting access to the report.

**Resolution:** switch to `-q` or `-l` when sufficient, restrict log retention, protect output files, and handle exposed secrets according to organizational policy.
