# Choosing a JDK

## 1. Goal: Choose the Right Version and Distribution

When choosing a JDK, you need to decide four separate things:

1. **Java release:** for example, Java 17, 21, or another release. The version determines the language syntax, standard API, and bytecode format that the compiler can generate.
2. **JDK distribution:** the vendor or organization that builds, packages, releases updates, and may provide support for the JDK, such as Oracle JDK, Eclipse Temurin, Amazon Corretto, Azul Zulu, BellSoft Liberica, Microsoft Build of OpenJDK, or Red Hat build of OpenJDK.
3. **Operating system and CPU architecture:** Windows, macOS, Linux; x86-64 or ARM64; compatible installer package formats and system libraries.
4. **Intended use:** a full JDK for development and building, or a smaller runtime image for environments that only run the application.

You should not infer the Java version from a vendor name. Multiple vendors can publish different distributions of the same Java release. Conversely, the same vendor can offer multiple releases and multiple package types.

The goal is to choose a JDK that meets the project's requirements, has appropriate security updates and support, can be installed in the target environments, and can be reproduced consistently across developer machines, CI, and production.

## 2. Identify the Java Version Required by the Project

Check the existing configuration before downloading a JDK. Common places that contain version information include:

- Gradle: Java toolchain configuration, **sourceCompatibility**, **targetCompatibility**, or **options.release** in build files.
- Maven: the **maven.compiler.release** property, Maven Compiler Plugin configuration, and Maven Toolchains Plugin if the project uses it.
- Spring Boot or other frameworks: compatibility matrices between framework versions, libraries, and Java.
- CI/CD: the JDK version in workflows, build agents, or container images.
- Dockerfile and deployment manifests: the runtime version used when running the application.
- Project technical documentation: minimum version, tested version, and supported version in production.

Distinguish between three versions that may differ:

- **JDK used to run the build tool:** the JVM that launches Gradle or Maven. The Gradle/Maven version and plugins themselves may impose their own Java requirements.
- **JDK used for compiling:** the compiler that actually produces bytecode. A project can lock this version using a toolchain.
- **Java runtime used to run the application:** the JVM on the server or in the production container.

For example, a machine might run Gradle with a newer JDK while configuring a toolchain to compile the application with an older JDK. That is only valid when the Gradle version, plugins, compiler, and project configuration all support that combination. Do not assume that installing a single JDK means every tool will automatically use that exact JDK.

### Source, Bytecode, and Target API Versions

If you need to run an application on Java release N, the generated bytecode must be compatible with runtime N. Setting only the syntax or bytecode level may not fully restrict the standard APIs that the program is allowed to call.

With `javac` from Java 9 onward, the **--release N** option is the explicit way to compile for a target release: the compiler restricts syntax, bytecode, and standard APIs to match that release. For example:

~~~bash
javac --release 17 Main.java
java Main
~~~

The commands above illustrate compiling source code targeting Java 17; to run it, the machine executing the program needs a runtime compatible with the generated bytecode and a complete classpath.

If you build with a newer JDK but omit the release configuration, the compiler may default to generating bytecode for the newer JDK version. The application may then run fine on a developer machine but fail on a server running an older Java version.

A newer JDK can generally run older bytecode, but testing is still required. Removed APIs, behavioral changes, stronger encapsulation, JVM options, and third-party library differences can cause an older application to fail when upgrading the runtime. Do not treat a JDK upgrade as merely changing an installation path.

## 3. Choose an LTS or a Feature Release

Java follows a regular feature release cadence. Not every release has the same support duration. The **LTS (Long-Term Support)** designation indicates a vendor's long-term support commitment for a release; support duration, update types, and usage terms depend on the specific vendor and distribution package.

**Prefer LTS** when:

- The application runs in production for a long period.
- The organization needs a stable version to standardize across multiple teams and environments.
- Upgrade cycles for frameworks, libraries, or infrastructure are slow.
- A clear security update and support plan is required.

**Consider a newer feature release** when:

- The project needs a new Java feature not yet available in the current LTS.
- The team has the capacity to upgrade and test on a short release cycle.
- Frameworks, libraries, build plugins, and deployment environments have confirmed compatibility.
- The organization explicitly accepts the support window and has a plan to move to the next release.

No single release fits every project. Choose a release that remains supported by its vendor for the expected operational lifespan while staying compatible with frameworks, libraries, and the deployment platform. Do not choose solely based on the highest version number or what happens to be pre-installed on a personal developer machine.

Before deciding, check the vendor's official lifecycle/roadmap page. Confirm the end-of-security-updates date, patch release policy, commercial support terms, and upgrade path. The LTS label from two different vendors does not automatically mean the same support duration.

## 4. Choose a Vendor and JDK Distribution

OpenJDK is the open-source project of the Java platform. Many vendors build, test, package, and publish distributions based on OpenJDK. Therefore, when saying "use OpenJDK," you should clarify where the specific build comes from and how it is updated and supported.

Some common distributions:

| Distribution | Considerations |
|---|---|
| Oracle JDK | Oracle's distribution; review the licensing terms, update policy, and support options applicable to the exact release and intended use. |
| Eclipse Temurin | OpenJDK builds from the Eclipse Adoptium project; available across many platforms and package formats. Check the current release matrix, platforms, and support policy. |
| Amazon Corretto | OpenJDK distribution provided by Amazon; review Amazon's update schedule, supported platforms, and support policy. |
| Azul Zulu | OpenJDK distribution from Azul, with various platform options and support services. |
| BellSoft Liberica JDK | OpenJDK distribution from BellSoft; offers multiple package types, so choose the right components and platform. |
| Microsoft Build of OpenJDK | OpenJDK build published by Microsoft; check the supported releases, operating systems, and published support lifecycle. |
| Red Hat build of OpenJDK | Worth considering when the organization uses the Red Hat ecosystem and support contracts; verify certified versions and platforms. |

The list above shows example vendors, not a quality ranking. A suitable distribution should be evaluated against actual needs:

- **Security updates:** does the vendor publish patches, a release schedule, and a clear vulnerability handling process?
- **Support lifecycle:** until when is the target release supported? Is commercial support or an SLA available if the organization requires it?
- **Platform:** does it provide the exact operating system, CPU architecture, libc, and container type needed for deployment?
- **Compatibility:** is it certified by the project's frameworks, libraries, operating system, or deployment platform?
- **License:** can it be used in internal, commercial, production, and redistribution scenarios as the project requires?
- **Provenance:** are checksums, signatures, or provenance information provided to verify downloaded packages?
- **Operations:** are package repositories, container images, update workflows, and automated installation methods available?

Oracle JDK and OpenJDK builds should not be assumed identical in licensing, support, or update delivery. Terms can vary by release and intended use. Read the exact license of the artifact you plan to install instead of relying on broad statements like "Java is always free" or "Oracle JDK is always paid."

If your organization already has a vendor standard, follow that standard. If not, choose an OpenJDK distribution maintained by a trustworthy vendor with a public lifecycle and security updates, full support for your project's platforms, and license compliance. Using the same vendor and release consistently across developer machines, CI, and production reduces hard-to-trace discrepancies.

## 5. Choose Operating System, Architecture, and Package Format

Choosing the right release with the wrong architecture will still prevent the JDK from running. Before downloading, determine:

- Operating system and OS version.
- CPU architecture: x86-64/AMD64 or ARM64/AArch64.
- Environment where the JDK runs: physical machine, virtual machine, container, or CI runner.
- System libraries required by the build, such as glibc or musl on Linux.
- Installation format supported by your machine management workflow.

Common options:

| Platform | Common Formats | Notes |
|---|---|---|
| Windows | MSI or ZIP | MSI is convenient for system-wide installation; ZIP is useful when you need multiple JDKs side by side or lack installer privileges. |
| macOS | PKG or archive | Choose the right Intel or Apple Silicon/ARM64 build; do not infer architecture from device name alone. |
| Linux | DEB, RPM, or archive | Choose the right distribution family, architecture, and system library. Package managers help manage updates; archives suit isolated installations. |
| Container | JDK/JRE base image | Choose an image matching the target architecture and base OS; manage tags and digests for reproducible builds. |

On Linux/macOS, you can check the architecture with:

~~~bash
uname -m
~~~

Common values are **x86_64** for x86-64 and **aarch64** for ARM64. On Windows, you can check the architecture environment variable or Windows System information. Distinguish between the host OS architecture and the target image/container architecture.

When downloading a JDK, get it from the official site or an organization-approved repository. Verify the vendor-published checksum or signature before installing, especially when using manually downloaded archives or bringing artifacts into CI. Do not use installers from unknown sources.

For containers, avoid relying on a floating tag without an update policy. Tags can be updated over time; pinning a digest makes the image reproducible, while a scheduled update process ensures security patches are applied. Balance reproducibility with not missing updates.

## 6. Choose a Full JDK or Runtime Only

A full JDK includes the runtime and development tools such as:

- **javac:** compiles Java source code.
- **java:** launches Java programs.
- **jshell:** interactive environment for testing expressions and code snippets.
- **javadoc:** generates API documentation.
- **jar:** creates and manipulates JAR files.
- **jlink:** creates a custom runtime image containing only the required modules.
- **jdeps:** analyzes module/package dependencies.

For development, build, and testing environments, use a full JDK because the compiler and accompanying tools are required. Production environments that only run the application can use a smaller runtime image once all required modules, native libraries, and diagnostic tools have been identified.

Modern Java releases are not necessarily distributed as a separate JRE like older Java installations. You can use a full JDK or build an appropriate runtime image with a tool like **jlink**. Do not download a package advertised as a "JRE" without verifying its contents, source, and compatibility.

A practical rule is to build with a full JDK, test on a runtime matching production, and only minimize the runtime image after confirming the application runs in that image. Reducing image size must not strip away modules, CA certificates, timezone data, native libraries, or operational tools that the application needs.

## 7. Configure a Consistent JDK in the Project

Having multiple JDKs installed on the same machine is normal. The problem arises when the terminal, IDE, Gradle/Maven, and the application end up using different JDKs.

### JAVA_HOME and PATH

**JAVA_HOME** should point to the root directory of the JDK, not the **bin** directory. Place the **bin** directory of the desired JDK in PATH with the appropriate priority order. When switching JDKs, open a new terminal or reload your shell configuration so the environment updates.

Do not hard-code a personal machine's JDK installation path into source code. Use the build tool's toolchain mechanism to declare the required compiler version; the project's setup documentation should specify how to prepare the JDK.

### Gradle Toolchain

With Gradle Kotlin DSL, you can declare the JDK used for compilation as follows:

~~~kotlin
java {
    toolchain {
        languageVersion.set(JavaLanguageVersion.of(21))
    }
}

tasks.withType<JavaCompile>().configureEach {
    options.release.set(21)
}
~~~

This example uses Java 21 as the toolchain and target release. When applying it, replace the version number with your project's actual requirement and verify that your Gradle/plugin versions support that configuration. A toolchain helps the build pick the right compiler; it does not automatically change every JVM running on the machine. The JVM launching Gradle must still satisfy the requirements of the Gradle version in use.

### Maven

You can declare the compiler's target release in Maven configuration:

~~~xml
<properties>
    <maven.compiler.release>21</maven.compiler.release>
</properties>
~~~

This is an example for release 21. Use an appropriate Maven Compiler Plugin version and ensure the JDK running Maven has a compiler/API compatible with the configuration. If you need to select a specific JDK on a machine with multiple JDKs, consider the Maven Toolchains Plugin and its corresponding toolchain configuration.

Beyond build configuration, set the Project SDK in your IDE, the CI JDK, and the runtime in Docker/deployment to match the project standard. Document the release, vendor, and installation steps in onboarding docs so new team members do not have to guess.

## 8. Practical Selection Workflow

Follow this order to avoid downloading the wrong build or reinstalling multiple times:

1. **Read project requirements.** Identify the minimum Java release, target compilation release, framework requirements, build tools, and production environment.
2. **Choose the release track.** Prefer a supported LTS release if the application needs long-term operation. Choose a feature release when the project has a specific need and accepts the corresponding upgrade cadence.
3. **Choose the vendor.** Compare lifecycle, security patches, licensing, commercial support, platforms, and organizational standards.
4. **Choose the artifact.** Pick the right operating system, CPU architecture, package type, and JDK/runtime.
5. **Verify the download source.** Check the checksum or signature before installing.
6. **Standardize the environment.** Configure JAVA_HOME, PATH, IDE, Gradle/Maven toolchain, CI, and deployment runtime.
7. **Test on the target environment.** Build, run tests, and start the application using the exact release/runtime intended for production.
8. **Document the decision.** Record the vendor, release, architecture, download source, update process, and next upgrade review milestone.

### Example Decision

Suppose a new service is required to run on Java 21 and the organization wants to use LTS in production. The decision might be documented as:

- Target release: Java 21.
- Distribution: Java 21 JDK from an organization-approved vendor with security updates and a lifecycle covering the operational lifespan.
- Developer machines and CI: use the same vendor/release or an equivalent toolchain configuration.
- Compiler: set target release to 21.
- Production: run on a compatible Java 21 runtime; if using a minimal runtime image, test that image.
- Upgrades: track vendor patches, test periodically, and plan a release migration before end of support.

If an existing project requires Java 17 while a developer machine already has Java 21 installed, do not arbitrarily bump the target version just because JDK 21 is available. Keep the release supported by the project, configure the appropriate toolchain or **--release**, and test on the actual runtime the application must support.

## 9. Verify the JDK After Installation

Open a new terminal and check both the runtime and the compiler:

~~~bash
java --version
javac --version
~~~

On Windows, you can identify which executables are being resolved with:

~~~powershell
where.exe java
where.exe javac
$env:JAVA_HOME
~~~

On Linux/macOS:

~~~bash
which -a java
which -a javac
echo "$JAVA_HOME"
~~~

Then check the build tool:

~~~bash
./gradlew --version
mvn --version
~~~

Run only the command corresponding to the build tool your project uses. Compare the output against the expected release. If **java** is present but **javac** is missing, PATH may be pointing to a runtime-only or incomplete installation. If **java** and **javac** report different versions, PATH may be picking up two different installations.

When you need to determine which JVM a running Java process is using, inspect the process launch configuration, environment variables, and actual executable path. **JAVA_HOME** is just an environment variable; a launcher or IDE may be configured to use a different path.

Do not conclude everything is set up just because the **java** command succeeds. Confirm that the compiler, build tool, IDE, and deployment runtime all use the right version.

## 10. Common Mistakes When Choosing a JDK

- **Confusing a Java release with a vendor:** Java 21 is a release; Temurin, Corretto, or Oracle JDK are distribution/vendor names.
- **Picking the latest version without checking compatibility:** frameworks, plugins, libraries, or production runtimes may not support it yet.
- **Confusing the JDK running the build with the target release:** Gradle running on one JVM does not mean the application is compiled for that same release.
- **Setting source/target without target API restriction:** you may accidentally call APIs that only exist in a newer JDK; use **--release** when you need to restrict to a release.
- **Downloading the wrong architecture:** an x86-64 package will not run like an ARM64 package across all environments.
- **Installing multiple JDKs without controlling PATH:** the terminal may run a different JDK from the IDE or CI.
- **Using a runtime-only package for building:** lacks **javac** and development tools.
- **Ignoring licensing and lifecycle:** an installation that works today may not meet the organization's update, support, or distribution requirements.
- **Skipping download verification:** archives from unknown sources may be tampered with or be the wrong artifact.
- **Using container tags without an update process:** builds can become hard to reproduce or miss security patches.

## 11. Pre-Selection Checklist

- [ ] Identified the release supported by the project, frameworks, and libraries.
- [ ] Distinguished between the build-tool JVM, compilation JDK, and production runtime.
- [ ] Chose LTS or a feature release based on operational lifecycle and upgrade plans.
- [ ] Confirmed lifecycle, security updates, and license terms for the exact vendor/release.
- [ ] Selected the right operating system, CPU architecture, and package format.
- [ ] Downloaded from a trusted source and verified checksum/signature.
- [ ] Configured JAVA_HOME, PATH, IDE, and toolchain.
- [ ] Verified `java --version`, `javac --version`, and the build tool.
- [ ] Built and tested with a configuration matching the deployment environment.
- [ ] Documented the version and update process so the team can reproduce it.

Choosing the right JDK means selecting an intentional combination of Java release, distribution, platform, and support policy. When these factors are clearly documented and applied consistently, building, running, upgrading, and troubleshooting become far more predictable.
