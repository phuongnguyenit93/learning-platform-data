# Class File Compatibility in Java

A class file is the bytecode format produced by the Java compiler from source code. The JVM reads class files to load classes, verify bytecode, and execute programs. **Class file compatibility** describes the ability of a JVM to understand and load a class file generated by the compiler of a given Java version.

When an application runs across multiple JDK versions, you must control the class file version of both the application and all of its dependencies. A program may compile successfully on a development machine yet fail on a server if the class files were generated for a newer JVM. Conversely, class files with an older version can still run on a newer JVM, provided that the APIs, libraries, and behaviors used by the program are compatible.

## 1. Four Compatibility Layers to Distinguish

The phrase "Java compatibility" can refer to several different concerns:

| Compatibility type | Question to answer | Example |
|---|---|---|
| Source compatibility | Does the compiler accept this syntax and language feature? | Java 8 does not have Java 10's `var` syntax |
| Class file / bytecode compatibility | Does the JVM understand the format and bytecode in the `.class` file? | JVM 11 does not load Java 17 class files with major version 61 |
| Platform API compatibility | Does the runtime provide the classes, methods, and fields referenced by the program? | Java 8 does not have `List.of()`, which was added in Java 9 |
| Behavioral compatibility | Does the program preserve the expected behavior on the target runtime? | Changes in API behavior, timezones, charsets, or algorithms across Java releases |

A class file may have a version accepted by the JVM and still fail during linking or execution due to missing methods, missing dependencies, module differences, or behavioral changes. Therefore, checking the major version is an important step, but it is not sufficient to prove that the entire application is compatible.

## 2. Class File Version Structure

Every `.class` file starts with a header containing format identification and version information. The key fields are:

- **magic number**: four bytes **CA FE BA BE**, used to identify a class file.
- **minor_version**: the minor version, an unsigned 16-bit integer.
- **major_version**: the major version, an unsigned 16-bit integer.
- Following the header are the constant pool, access flags, class information, interfaces, fields, methods, and attributes.

The minor and major fields are stored in big-endian byte order. The JVM uses them to determine whether the class file belongs to a format supported by the runtime.

For example, a class file compiled for Java 17 typically has:

~~~text
minor version: 0
major version: 61
~~~

In this example, **61** is the major version corresponding to Java 17. When inspecting a class file version, you usually only need to check the `minor version` and `major version` lines in the `javap` output.

The class file version is per-`.class`-file metadata, not a single global number for an entire JAR. A JAR can contain classes compiled from different Java versions; the JVM only fails when it loads a specific class that it does not support.

## 4. Compatibility Direction Between Compiler and JVM

A JVM has a maximum major version that it understands. A newer JVM can generally load class files built for older Java versions, within the format range supported by the JVM. An older JVM cannot understand class files with a major version newer than what it supports.

Examples:

| Class file | Runtime | Format compatibility result |
|---|---|---|
| Java 8 / major 52 | Java 17 / max major 61 | JVM 17 understands the format |
| Java 17 / major 61 | Java 21 / max major 65 | JVM 21 understands the format |
| Java 21 / major 65 | Java 17 / max major 61 | Incompatible format |
| Java 26 / major 70 | Java 21 / max major 65 | Incompatible format |
| Java 17 / major 61 | Java 11 / max major 55 | Incompatible format |

For instance, an application compiled with default settings on JDK 21 typically produces class files with major version 65. If you deploy those files to a machine that only has Java 17, JVM 17 cannot load them.

In the opposite direction, if an application is compiled into Java 17 class files, JVM 21 can understand that format. However, this does not guarantee that all APIs or behaviors are identical; you still need to verify dependencies and runtime behavior.

## 5. UnsupportedClassVersionError

When a JVM attempts to load a class file with an unsupported version, you typically encounter this error:

~~~text
java.lang.UnsupportedClassVersionError:
  Hello has been compiled by a more recent version of the Java Runtime
  (class file version 65.0), this version of the Java Runtime only
  recognizes class file versions up to 61.0
~~~

This message indicates:

- **65.0** is the class file version of the class being loaded, corresponding to Java 21.
- **61.0** is the maximum major/minor version supported by the running runtime, corresponding to Java 17.
- The current runtime is too old for the class file.

`UnsupportedClassVersionError` is a subclass of `LinkageError`. It typically occurs while the JVM is loading the class, before the program can execute the relevant code.

There are two ways to resolve it:

1. Run the application with a newer JRE/JDK capable of loading the released class files.
2. Recompile the application and its dependencies from source with a target release matching the target runtime, if the project must support older runtimes.

Do not simply rename files or patch the major version bytes with a hex editor. Changing the header does not convert bytecode, APIs, or class file structures back to an older version; the result can still fail verification or linkage, or cause undefined behavior.

## 6. javac: -source, -target, and --release

These three options serve related but distinct purposes.

| Option | Effect |
|---|---|
| `-source N` | Selects the accepted Java syntax and language rules version |
| `-target N` | Selects the class file/bytecode version generated by the compiler |
| `--release N` | Selects the target release, including the source level, target class file version, and the Java SE API set for that release |

### Why aren't -source and -target enough?

Suppose you compile using JDK 17, but the application must run on Java 8. The command:

~~~bash
javac -source 8 -target 8 ApiDemo.java
~~~

instructs the compiler to accept Java 8 syntax and emit class files with major version 52. However, the compiler can still see the APIs of the installed JDK 17. If the source code calls a method introduced in Java 9, the compiler may accept that call and produce a version 52 class file, even though a Java 8 runtime lacks that method.

Example:

~~~java
import java.util.List;

public class ApiDemo {
    public static void main(String[] args) {
        List<String> names = List.of("Ada", "Grace");
        System.out.println(names);
    }
}
~~~

`List.of()` was added in Java 9. If you compile this code with a newer compiler using only `-source 8 -target 8`, the class file may carry major version 52 while still referencing a method that does not exist in Java 8. When running on Java 8, the application can throw `NoSuchMethodError`.

### Using --release

Starting with JDK 9, you should use **--release** when compiling for an older Java release:

~~~bash
javac --release 8 ApiDemo.java
~~~

This command will fail to compile because `List.of()` is not part of the Java 8 API. The compiler prevents source code from referencing APIs newer than the selected release.

Example for a Java 17 project:

~~~bash
javac --release 17 -encoding UTF-8 -d out src/Hello.java
~~~

`--release 17` tells the compiler to:

- Apply Java 17 language rules.
- Emit class files for Java 17 (major version 61).
- Check code against the Java SE APIs present in release 17.

`--release` has been available since JDK 9 and only supports releases provided by the current JDK compiler. Do not combine `--release` with `-source` or `-target` in the same command. On JDK 8, this option does not exist; you must use an appropriate compiler/toolchain and configure the corresponding boot class path when targeting an older Java version.

## 7. Hands-On Example: Checking the Class File Version

Create a source file **Hello.java**:

~~~java
public class Hello {
    public static void main(String[] args) {
        System.out.println("Class file compatibility");
    }
}
~~~

Suppose your machine uses JDK 21 or later, but the application needs to run on Java 17. Create the output directory and compile with release 17.

Linux/macOS:

~~~bash
mkdir -p out
javac --release 17 -encoding UTF-8 -d out src/Hello.java
~~~

Windows PowerShell:

~~~powershell
New-Item -ItemType Directory -Force out | Out-Null
javac --release 17 -encoding UTF-8 -d out src/Hello.java
~~~

Use `javap` to inspect the class file information:

~~~bash
javap -verbose -classpath out Hello
~~~

In the output, look for these two lines:

~~~text
minor version: 0
major version: 61
~~~

The result `major version: 61` confirms that the compiler generated a class file in the Java 17 format. You can filter quickly in PowerShell:

~~~powershell
javap -verbose -classpath out Hello | Select-String "minor version|major version"
~~~

Run the program:

~~~bash
java -cp out Hello
~~~

Stdout:

~~~text
Class file compatibility
~~~

To check the actual runtime, run `java -version`. If the runtime is Java 17 or newer, the JVM understands class file version 61. If the runtime is Java 11, this class file cannot be loaded.

## 8. Minor Version and Preview Features

Besides the major version, a class file also has a minor version. For standard modern Java class files, the minor version is typically 0.

Since Java 12, class files use **minor version 65535** to mark the use of preview features from a Java release. This is a special indicator; the JVM only allows running preview class files when preview is enabled and the runtime matches the exact Java release that produced the class.

For example, on JDK 26, if the source uses a Java 26 preview feature:

~~~bash
javac --enable-preview --release 26 PreviewDemo.java
java --enable-preview PreviewDemo
~~~

When inspected with `javap`, the preview class file may display:

~~~text
minor version: 65535
major version: 70
~~~

Key notes:

- `--enable-preview` must be enabled both at compile time and at runtime.
- A preview class file is tied to the exact Java release that provides that preview feature.
- Do not treat preview class files as stable release bytecode that can be moved freely across releases.
- Do not use preview features in products requiring long-term compatibility unless you accept the risk of feature changes or removal.

## 9. Class File Versions in JARs and Dependencies

A JAR is a container holding multiple entries. Each class inside it can have its own major/minor version. Consequently, your main application might target Java 17 and still fail on Java 17 if a dependency library was compiled for Java 21.

Example:

~~~text
application.jar
  com/example/Main.class       major 61
  com/example/Service.class    major 61
  dependency/
    library-class.class        major 65
~~~

If `library-class.class` is loaded by the JVM at runtime, Java 17 will not understand major version 65. The error may appear after application startup, when code first accesses a class from that dependency.

When investigating:

1. Identify the class reported in `UnsupportedClassVersionError`.
2. Determine which artifact/JAR contains that class.
3. Check the major version of that specific class.
4. Verify whether the library version supports your target Java runtime.
5. Choose a compatible dependency version or upgrade the runtime according to your deployment policy.

Use `javap` on a class in the classpath or inside a JAR:

~~~bash
javap -verbose -classpath library.jar com.example.LibraryClass
~~~

You can list the contents of a JAR:

~~~bash
jar --list --file library.jar
~~~

Do not inspect only the main classes. Check transitive dependencies, build plugins, agents, test libraries, and dynamically loaded modules as well.

## 10. Multi-Release JARs

A multi-release JAR allows a single artifact to contain multiple implementations of the same class, tailored for different Java runtimes. The JAR must include this manifest attribute:

~~~text
Multi-Release: true
~~~

Example structure:

~~~text
library.jar
  META-INF/
    MANIFEST.MF
    versions/
      11/
        com/example/Feature.class
      17/
        com/example/Feature.class
  com/
    example/
      Feature.class
~~~

When running on a Java 17 runtime, the class loader can select the entry in `META-INF/versions/17` if present; on Java 11, it can select the version in `versions/11`; if no matching entry exists, it falls back to the base class at the root. Runtimes older than Java 9 do not apply the multi-release mechanism and use the root entries.

Versioned classes must be compiled for their corresponding runtime and must preserve the library's published API contract. A multi-release JAR lets a library take advantage of newer APIs on newer runtimes while keeping a baseline implementation for older runtimes; it does not make a newer class file runnable on an older JVM.

## 11. Configuring Target Compatibility in Build Tools

Configure the target release directly in your build script so that local machines and CI enforce the same rules.

### Maven

You can set the release and source encoding in properties:

~~~xml
<properties>
    <maven.compiler.release>17</maven.compiler.release>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
</properties>
~~~

Or declare them in the Maven Compiler Plugin:

~~~xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-compiler-plugin</artifactId>
    <version>3.13.0</version>
    <configuration>
        <release>17</release>
        <encoding>UTF-8</encoding>
    </configuration>
</plugin>
~~~

Build:

~~~bash
mvn clean package
~~~

Configuring `release` ensures the compiler validates source and APIs against Java 17. In multi-module projects, check both the parent POM and child modules to avoid unintended release overrides.

### Gradle Groovy DSL

In **build.gradle**:

~~~groovy
java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(17)
    }
}

tasks.withType(JavaCompile).configureEach {
    options.release = 17
    options.encoding = 'UTF-8'
}
~~~

### Gradle Kotlin DSL

In **build.gradle.kts**:

~~~kotlin
java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(17)
    }
}

tasks.withType<JavaCompile>().configureEach {
    options.release = 17
    options.encoding = "UTF-8"
}
~~~

The toolchain selects the JDK used to build; `options.release` sets the target API and class file release. These two settings answer different questions: which compiler to use, and which release the output must be compatible with.

## 12. Compatibility Troubleshooting Workflow

### Step 1: Identify the running Java runtime

~~~bash
java -version
~~~

This is the actual JVM version invoked in your terminal or deployment environment. On machines with multiple JDKs, `java` and `javac` may point to different versions.

Windows PowerShell:

~~~powershell
Get-Command java
Get-Command javac
~~~

Linux/macOS:

~~~bash
which java
which javac
~~~

### Step 2: Identify the compiler in use

~~~bash
javac -version
~~~

Do not assume the compiler and runtime have the same version. Build tools, IDEs, containers, or CI systems may use a separate JDK.

### Step 3: Read the class file version

~~~bash
javap -verbose -classpath out com.example.Main
~~~

Read the major version and look it up in the table in section 3. If the error occurs in a dependency, run `javap` on that dependency's class.

### Step 4: Check the build configuration

Look for `--release`, `-source`, `-target`, toolchain, and compiler configuration options. Verify that the build actually passes those settings to `javac`, especially when builds are driven by an IDE or daemon.

### Step 5: Check dependencies

Identify which library owns the failing class, then check the dependency version and its published Java baseline. Update to a compatible dependency or upgrade the runtime if appropriate.

### Step 6: Clean build and test on the target runtime

Remove old build outputs according to your project workflow, rebuild using the selected release configuration, and run tests on the exact minimum Java runtime you must support. A passing build on a newer JDK alone is not enough.

## 13. Common Misconceptions

| Misconception | Correct understanding |
|---|---|
| Setting `-target 8` is enough to run on Java 8 | The bytecode may have major version 52 while still referencing APIs only available in newer Java releases |
| `-source 8` restricts the compiler to Java 8 APIs | `-source` selects the language level; it does not fully restrict runtime APIs |
| An older class file version guarantees the program runs on a newer JVM | The JVM may understand the format, but dependencies, APIs, and behavior can still be incompatible |
| Checking only the main class in a JAR is enough | Dependencies or dynamically loaded classes may still have a higher major version |
| Editing the major version with a hex editor downgrades bytecode | Changing the header does not convert bytecode or APIs |
| `--release 17` means the program will run on every Java from 17 onward | It configures compilation for Java 17; you still need to test dependencies and behavior on the deployment runtime |
| Toolchain 17 automatically ensures all dependencies target 17 | A toolchain selects the build JDK; external dependencies may still be compiled with a newer release |
| Preview class files only need the right major version | Preview also uses minor version 65535 and requires the same release runtime with `--enable-preview` |

## 14. Checklist for Releasing Multi-Version Compatible Java Applications

- [ ] Identify the minimum runtime the product must support.
- [ ] Use an appropriate JDK/compiler and explicitly configure `--release`.
- [ ] Do not rely solely on `-source` and `-target` when API control is required.
- [ ] Check the major/minor versions of main classes and key dependencies.
- [ ] Verify that transitive dependencies, plugins, and agents support the target runtime.
- [ ] Inspect multi-release JARs if libraries provide multiple implementations per Java release.
- [ ] Enable preview features only if the product accepts being tied to that exact release runtime.
- [ ] Run clean builds in CI and test on the minimum supported runtime.
- [ ] Watch for linkage errors such as `NoSuchMethodError`, `NoClassDefFoundError`, and `UnsupportedClassVersionError`.
- [ ] Document the Java baseline in build documentation and deployment guides.

## 15. Key Takeaways

- A class file contains bytecode along with major/minor versions that the JVM uses to determine whether the format is supported.
- The major version increases with each Java release; for example, Java 8 is 52, Java 17 is 61, Java 21 is 65, and Java 26 is 70.
- Newer JVMs can generally load older class files; older JVMs cannot load class files newer than what they support.
- `UnsupportedClassVersionError` typically indicates that a class file was compiled with a newer Java version than the current runtime.
- `--release` is the recommended option from JDK 9 onward to simultaneously control language level, bytecode, and target APIs.
- `-source` and `-target` alone do not fully restrict platform APIs.
- Inspect dependencies and class files inside JARs, not just your application's main classes.
- Preview class files use minor version 65535 and require enabling preview on the exact matching Java release.
- Only a clean build and testing on the target runtime can verify real-world compatibility.
