# Compression in jlink

**jlink** is a JDK tool used to link modules together with their dependencies into a custom runtime image. The **compress** plugin controls how resources are compressed in the output image, helping reduce distribution size or runtime storage footprint. This option can affect image size and CPU overhead when resources are accessed, so it should be measured on realistic workloads.

jlink compression applies to resources inside the **runtime image** generated by jlink. It is not a general-purpose option for compressing an arbitrary application JAR, does not replace ZIP/JAR compression, and does not automatically remove modules from the image. To reduce modules, you must select the appropriate root modules and review the dependency graph; to reduce locale, debug, or documentation data, you must use the corresponding options.

## 1. Compression in the runtime image creation workflow

A modular application typically takes source or module JAR/JMOD files as input. jlink resolves the selected modules, adds required dependencies, and produces a runtime image containing the launcher, runtime libraries, and required modules.

General workflow:

~~~text
Module path
   |
   +-- application module
   +-- dependency modules
   +-- JDK modules
          |
          v
     jlink resolution
          |
          v
     runtime image
       - java launcher
       - linked modules
       - runtime resources
       - compression / other plugins
~~~

The **--compress** option controls the compress plugin during the image creation phase. It can reduce the storage size of resources in the image. At runtime, the runtime still consumes resource contents in the format supported by the JVM and the image; the application does not need to manually extract the image directory before startup.

Compression is one of several ways to optimize an image. Results also depend on the number of modules, packaged resources, locale data, debug metadata, service bindings, and other plugins.

## 2. Compression syntax in modern JDKs

According to the JDK 26 documentation, the current syntax is:

~~~bash
jlink --compress=zip-N
~~~

Where N is a level from 0 to 9:

| Option | Meaning |
|---|---|
| --compress=zip-0 | No resource compression |
| --compress=zip-1 | ZIP compression at level 1 |
| --compress=zip-6 | ZIP compression at level 6; current default |
| --compress=zip-9 | Highest compression level in the supported range |

Values `zip-1` through `zip-9` represent ZIP compression levels. Higher levels aim for a better compression ratio, but may increase image creation time or related CPU overhead. Level 0 performs no compression. The default in JDK 26 is `zip-6`. Check the documentation for the exact JDK version you are using rather than assuming every jlink release shares the same syntax.

You can inspect the tool version and available plugins:

~~~bash
jlink --version
jlink --list-plugins
jlink --help
~~~

The **--list-plugins** option is especially useful when build scripts need to run across multiple JDK releases, because plugins and their syntax can change across versions.

## 3. Syntax differences between older and newer JDKs

Older JDK releases, such as JDK 21, use numeric syntax:

~~~bash
jlink --compress=0
jlink --compress=1
jlink --compress=2
~~~

Legacy meanings:

| Old syntax | Legacy meaning |
|---|---|
| --compress=0 | No compression |
| --compress=1 | Constant string sharing |
| --compress=2 | ZIP compression |

The JDK 26 documentation marks these numeric values as deprecated and introduces the new syntax:

| Legacy value | Recommended new usage in documentation |
|---|---|
| --compress=0 | --compress=zip-0 |
| --compress=1 | Legacy constant string sharing; do not equate with zip-1 |
| --compress=2 | --compress=zip-6 |

**Common point of confusion:** on JDK 26, legacy **--compress=1** means constant string sharing, whereas **--compress=zip-1** is ZIP compression level 1. The two options are not equivalent. Similarly, legacy **--compress=2** is ZIP compression, while **--compress=zip-2** is specifically ZIP level 2.

When maintaining build scripts across multiple JDK generations:

1. Identify the actual JDK used to run jlink.
2. Check **jlink --help** and **jlink --list-plugins**.
3. Choose the syntax that matches the JDK version pinned in the build.
4. Do not replace numbers with `zip-N` strings via blind search-and-replace.
5. Build the image and run smoke tests after changing options.

The Oracle JDK 21 documentation describes the legacy 0/1/2 values; the Oracle JDK 26 documentation describes `zip-0` through `zip-9` and the deprecated status of the numeric values.

## 4. Choosing a compression level by goal

The appropriate compression level depends on how the image is distributed and the runtime environment:

| Goal | Option to try | Reason |
|---|---|---|
| Prioritize simple image creation without resource compression | zip-0 | Performs no ZIP compression |
| Balance size and overhead | zip-6 | Default level in JDK 26 |
| Prioritize reducing image size | zip-9 | Highest compression level supported by documentation |
| Compare performance and size | Build multiple images with zip-0, zip-6, and zip-9 | Measure on the same module graph and workload |

There is no single optimal level for every application. Text-based resources typically compress well; already-compressed resources such as JPEG images, fonts, or other archives may shrink less. An image with many classes and resources also behaves differently from a small image containing only a few modules.

Do not draw conclusions based solely on image size. Compare at least:

- Image size on disk.
- Time taken by jlink to create the image.
- Application startup time.
- CPU usage and resource access time in a representative workload.
- Package size when bundling the image into an installer or archive for distribution.

## 5. Creating a runtime image with compression

Assume the application module has been compiled into the `mods` directory and is named `com.acme.app`. The module path must include both the application modules and the required JDK modules.

On Linux/macOS:

~~~bash
jlink --module-path "$JAVA_HOME/jmods:mods" --add-modules com.acme.app --launcher app=com.acme.app/com.acme.app.Main --compress=zip-6 --output runtime
~~~

On Windows PowerShell:

~~~powershell
jlink --module-path "$env:JAVA_HOME\jmods;mods" --add-modules com.acme.app --launcher app=com.acme.app/com.acme.app.Main --compress=zip-6 --output runtime
~~~

Explanation:

- **--module-path** specifies where jlink looks for modules. The JDK typically provides system modules in the `jmods` directory.
- **--add-modules** selects the root modules; jlink automatically adds required dependencies according to the module graph.
- **--launcher** creates a launcher named `app` pointing to the module and main class.
- **--compress=zip-6** enables ZIP compression at level 6.
- **--output runtime** places the generated runtime image in the `runtime` directory.

The output directory must meet jlink's requirements; if it already exists, use a new directory or clean the output in your build process before regenerating. Do not point the output to an installed JDK directory or a directory containing unrelated data.

Verify the image:

~~~bash
runtime/bin/java --version
runtime/bin/java --list-modules
runtime/bin/app
~~~

On Windows, the executable/launcher resides in `runtime\bin`. The launcher name and file extension depend on the platform. If you do not create a custom launcher, you can run the module using the runtime Java executable:

~~~bash
runtime/bin/java --module com.acme.app/com.acme.app.Main
~~~

A runtime image is built for the platform and architecture on which jlink is running. Typically, you need to build a separate image for each target operating system/architecture using the corresponding JDK.

## 6. Compression filter

The compress plugin allows adding a filter to specify patterns of resources to compress:

~~~bash
jlink --compress=zip-6:filter=pattern-list
~~~

The filter is a comma-separated list of patterns. The jlink documentation supports the following forms:

- Glob patterns.
- **glob:** followed by a glob pattern.
- **regex:** followed by a regular expression.
- **@filename** to read patterns from a file, one pattern per line.

Example illustrating selecting resources by file extension:

~~~bash
jlink --compress=zip-6:filter=glob:**.properties,glob:**.xml
~~~

Specific patterns should be verified against resource paths inside the image. A filter is a selection condition for resources to compress; it does not delete unmatched files from the runtime image. Unselected resources remain in the image according to the plugin's default handling.

You can inspect plugins on the current JDK:

~~~bash
jlink --list-plugins
~~~

And view all options with:

~~~bash
jlink --help
~~~

Use filters when you have a clear reason, such as wanting to compress a group of text resources while leaving other file groups uncompressed. Before applying to production, inspect the image and run the application to confirm resources are found normally.

## 7. Compression does not replace module reduction

Compression reduces the storage size of resources in the image. It does not remove unnecessary modules. To reduce footprint, you need to identify the modules your application actually uses.

Example:

~~~bash
jlink --module-path "$JAVA_HOME/jmods:mods" --add-modules com.acme.app --compress=zip-6 --output runtime
~~~

jlink links `com.acme.app` and its required dependencies. If the application pulls in unwanted modules through service binding or dependencies, review the module graph and module selection.

Related options:

| Option | Role |
|---|---|
| --add-modules | Selects root modules to include in the image |
| --limit-modules | Limits the set of observable modules during resolution |
| --bind-services | Links service provider modules and their dependencies |
| --include-locales | Limits locale data included in the image |
| --no-header-files | Excludes header files |
| --no-man-pages | Excludes man pages |
| --strip-debug | Strips debug information from the output image |
| --compress | Compresses resources in the output image |

Each option affects a different component. If the goal is a smaller image, inspect the module graph first, then compare compression and plugins that strip unnecessary components.

## 8. Combining compression with other plugins

jlink provides several plugins that can be used alongside compression. Example:

~~~bash
jlink --module-path "$JAVA_HOME/jmods:mods" --add-modules com.acme.app --strip-debug --no-header-files --no-man-pages --compress=zip-6 --output runtime
~~~

Meaning:

- **--strip-debug** strips debug information from the runtime image.
- **--no-header-files** excludes header files from the image.
- **--no-man-pages** excludes man pages from the image.
- **--compress=zip-6** compresses remaining resources at ZIP level 6.

Do not enable every optimization option out of habit. If your environment needs header files, man pages, or debug information for operations, keep them. Measure the impact of each change to know which plugins actually reduce size.

### Limiting locale data

If the application only needs a specific set of locales, you can reduce locale data using the `include-locales` plugin. Example:

~~~bash
jlink --add-modules com.acme.app,jdk.localedata --include-locales=en,vi --compress=zip-6 --output runtime
~~~

When using **--include-locales**, you must add the `jdk.localedata` module. The locale list must reflect the actual needs of the application; missing locales can cause date, number, or message formatting to behave unexpectedly.

## 9. Measuring and comparing runtime image size

To evaluate compression, build multiple images from the same module path and the same root modules. Change only the compression level between builds.

Example on Linux/macOS:

~~~bash
jlink --module-path "$JAVA_HOME/jmods:mods" --add-modules com.acme.app --compress=zip-0 --output runtime-zip0
jlink --module-path "$JAVA_HOME/jmods:mods" --add-modules com.acme.app --compress=zip-6 --output runtime-zip6
jlink --module-path "$JAVA_HOME/jmods:mods" --add-modules com.acme.app --compress=zip-9 --output runtime-zip9

du -sh runtime-zip0 runtime-zip6 runtime-zip9
~~~

On Windows PowerShell, you can compute the total file size:

~~~powershell
Get-ChildItem runtime-zip0 -Recurse -File | Measure-Object -Property Length -Sum
Get-ChildItem runtime-zip6 -Recurse -File | Measure-Object -Property Length -Sum
Get-ChildItem runtime-zip9 -Recurse -File | Measure-Object -Property Length -Sum
~~~

Record the results in a table:

| Image | Compression | Size | Build time | Startup / workload |
|---|---|---:|---:|---|
| runtime-zip0 | zip-0 | Actual measurement | Actual measurement | Actual measurement |
| runtime-zip6 | zip-6 | Actual measurement | Actual measurement | Actual measurement |
| runtime-zip9 | zip-9 | Actual measurement | Actual measurement | Actual measurement |

Do not fill in estimated numbers instead of actual measurements. Use the same build machine, same JDK, same input modules, and same configuration so the comparison is meaningful.

When measuring startup, run each image multiple times under equivalent conditions. Separate the first run, which may be affected by OS caching, from subsequent runs. If the application reads many resources, include those operations in the workload benchmark.

## 10. Verifying correctness after compression

After creating the image, verify the following aspects:

1. **Image exists**: confirm the output directory contains the launcher and runtime structure.
2. **Runtime version**: run the `java` executable inside the image to confirm the right runtime.
3. **Module list**: use `--list-modules` to inspect linked modules.
4. **Launcher**: run the launcher or module entry point.
5. **Resources**: verify the application can read properties, XML, templates, locales, and other resources.
6. **Service loading**: verify required service providers are resolved and work properly.
7. **Native libraries**: confirm native libraries match the target platform and architecture.
8. **Workload**: run representative smoke tests and integration tests.

Compression should not alter application logic. If the application fails after image creation, check the module graph, resource filtering, service binding, and differences between the runtime image and a full JDK before concluding that compression is the cause.

## 11. Common errors and misconceptions

| Symptom / misconception | Cause or correct understanding |
|---|---|
| jlink reports invalid compression value | Syntax varies by JDK; check `jlink --help` and `--list-plugins` |
| Using `--compress=1` on a newer JDK expecting ZIP level 1 | Legacy value `1` is constant string sharing; ZIP level 1 uses `zip-1` |
| Image is not much smaller | Resources are already compressed or most size comes from modules/classes/native libraries |
| Thinking `--compress` removes modules | Compression only compresses resources; select modules with `--add-modules` and `--limit-modules` |
| Runtime cannot find resources after build | Check filters or packaging configuration; verify actual entries/resources |
| Image runs on build machine but not on target machine | Different OS, CPU architecture, native libraries, or runtime configuration |
| Checking only directory size | Must check startup, workload, resource, and service behavior |
| Thinking `--strip-debug` changes compression | It is a separate plugin that strips debug metadata; measure each impact separately |
| Old image does not receive automatic security updates | Developers must rebuild and redistribute the custom runtime image from an updated JDK |

## 12. Workflow for choosing compression in a project

1. Identify the JDK release pinned in the runtime image build pipeline.
2. Run `jlink --list-plugins` to confirm the compress syntax.
3. Identify the root modules and dependencies required by the application.
4. Create a baseline image without compression or with the default compression level.
5. Create test images with `zip-0`, `zip-6`, and `zip-9` if the JDK supports the new syntax.
6. Compare size, build time, startup, and workload performance.
7. Use filters only when you have specific resource patterns and have tested them.
8. Combine with other plugins such as `strip-debug`, `include-locales`, or `no-man-pages` when appropriate.
9. Run smoke tests and integration tests on the exact runtime image to be released.
10. Record the JDK version, jlink command, and measurement results so the image can be reproduced.

## 13. Maintaining a custom runtime image

A custom runtime image does not update itself like a standalone installed and updated JDK. When a JDK receives security updates or bug fixes, the development team must rebuild the image using the updated JDK, run tests, and release the new image.

Recommended metadata to store with the artifact:

- JDK version used to build the image.
- List of linked modules.
- jlink and plugin options.
- Compression level and filter.
- Application and dependency versions.
- Target operating system/architecture.
- Smoke test and size benchmark results.

Compression does not encrypt resources and is not a security mechanism. If the application requires secrets or sensitive data, manage them through separate configuration and secret management mechanisms rather than embedding them in the runtime image.

## 14. Key takeaways

- jlink creates a custom runtime image from a module graph; the compress plugin controls resource compression in that image.
- JDK 26 uses `--compress=zip-0` through `--compress=zip-9`; the default is `zip-6`.
- `zip-0` performs no compression; `zip-9` is the highest compression level in the current range.
- The legacy `0/1/2` syntax is deprecated in JDK 26 documentation; legacy value `1` is constant string sharing, not ZIP level 1.
- Filters select resource patterns to compress; they do not delete unmatched resources from the image.
- Compression does not replace reducing modules, limiting locales, or stripping debug information.
- Measure size, startup, and workload before choosing a production compression level.
- Verify the runtime image using the launcher, `--list-modules`, and resource/service tests.
- Developers must update and re-release custom runtime images when the underlying JDK needs updates.
