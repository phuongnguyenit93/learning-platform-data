# Default Constructors and Compiler Auto-Generation Conditions in Java

## 1. Concept: What Is a Default Constructor?

When writing a regular Java class, a programmer can declare constructors to specify how objects are created. However, a class that **declares no constructors** can still be instantiated with `new ClassName()`, provided all other language conditions are satisfied. The reason is that the Java compiler can **automatically declare a default constructor** (*default constructor*) for that class.

```java
class Book {
    String title;
}
```

Inside `Book`, there is no `Book() { ... }` line at all. In this case, Java provides a **no-argument** constructor by default for use:

```java
Book book = new Book();
System.out.println(book.title); // null
```

The latter two lines are only a **code snippet placed inside an appropriate method**, not a standalone runnable program. `Book` can be instantiated because the compiler supplies a default constructor; the `title` field has the default reference value `null` because it has no explicit initializer.

**Distinguish right from the start:**

- **Default constructor** in Java Language Specification (JLS) terminology: a constructor **implicitly declared by the compiler** when a class satisfies the condition of **having no constructor declarations at all**.
- **No-argument constructor / no-arg constructor**: a constructor **with no parameters**. It can be **the default one generated by the compiler** or **written by the programmer**.
- **Parameterized constructor**: for example, `Book(String title)`. Once a class declares **at least one constructor**, the compiler **no longer automatically generates a default constructor for that class**, even when the existing constructor takes no parameters.

In introductory materials, "default constructor" is sometimes used loosely to refer to any no-argument constructor. When analyzing **the conditions under which the compiler automatically generates one**, you must use the exact meaning: **implicitly declared** is different from **explicitly declared**.

## 2. Rules Determining Whether a Default Constructor Is Generated

For a **regular Java class**, the key rule is:

> If there is **no constructor declaration** in the class body, Java implicitly declares a default constructor. If the class already has **any constructor declaration**, the compiler **does not automatically generate a default constructor**.

Quick reference table:

| Declarations in the class | Does the compiler generate a default constructor? | Is `new X()` necessarily valid? |
| --- | --- | --- |
| No constructors at all | **Yes** | **Not necessarily**: it still depends on whether the class is abstract, whether the superclass has an accessible no-argument constructor, and the accessibility of the class itself |
| Only programmer-written `X() { ... }` | **No** | Usually yes, if the constructor and class are accessible, the class can be instantiated, and the constructor is valid |
| Only `X(int id) { ... }` | **No** | No, unless another no-argument constructor is also declared |
| Both `X()` and `X(int)` | **No** | It can use the **programmer-written** `X()` |
| Has `private X() { }` | **No** | Can only be called within the scope where that constructor is accessible |
| Has method `void X() { }` but no constructor | **Yes** | A method named `X` does **not** count as a constructor |

In particular, the compiler does not "see a parameterized constructor and automatically add an empty one for convenience." The presence of **a single programmer-written constructor** is enough to prevent a default constructor from being generated.

### Syntactic Identification Tip

A constructor must have **the exact same name as the class** and **no return type**, not even `void`:

```java
class Lamp {
    Lamp() {                 // Programmer-written constructor.
        System.out.println("construct");
    }

    void Lamp() {            // Method, NOT a constructor.
        System.out.println("method");
    }
}
```

This is a valid declaration. Because `Lamp()` is already present, the compiler does **not** add a default constructor. If you remove the `Lamp()` declaration and keep only `void Lamp()`, the class still has **no explicitly declared constructor**, and the compiler will supply a default constructor.

Giving a method the same name as the class is a misleading choice; in new code, you should use method names that describe the actual behavior.

## 3. Equivalent Model: What Does the Compiler Generate?

Consider a simple class:

```java
class Plain {
}
```

In terms of **normal constructor invocation behavior**, you can think of a roughly equivalent constructor:

```java
class Plain {
    Plain() {
        super();
    }
}
```

**This is a comparison between two separate versions, not two declarations to be placed together in the same file.** The second version, written by the programmer, is no longer a *default constructor* by definition, even though it can create an object with an equivalent result.

For a regular class other than `java.lang.Object`, the default constructor calls the appropriate **no-argument constructor of the superclass**. If there is no explicit `extends`, the direct superclass defaults to `java.lang.Object`. Next, instance initializers in the current class are executed according to the rules, and then the constructor completes.

The default constructor **contains no custom logic** to compute sums, populate fields with business data, validate values, or create child objects. If a field has an initializer or the class has an instance initializer block, that initialization still runs upon instance creation — but that is the **initialization declaration of the field/block**, not business code invented by the default constructor.

### First Java 17+ Example: An Empty Class Can Still Create Objects

Save to the file **`DefaultConstructorDemo.java`**:

```java
class Student {
    String name;
    int grade;
}

public class DefaultConstructorDemo {
    public static void main(String[] args) {
        Student a = new Student();
        Student b = new Student();

        System.out.println(a.name);
        System.out.println(a.grade);
        System.out.println(a == b);
    }
}
```

Compile and run:

```bash
javac DefaultConstructorDemo.java
java DefaultConstructorDemo
```

Exact output:

```text
null
0
false
```

Explanation:

1. The `Student` class declares no constructor, so the compiler implicitly generates a no-argument default constructor.
2. The first and second `new Student()` calls create **two distinct instances**; the comparison `a == b` evaluates to `false`.
3. `name` defaults to `null` and `grade` defaults to `0` due to **the default value rules for instance fields**, not because Java silently inserts `name = null; grade = 0;` into the constructor body in a source-code sense.
4. The file contains a `public` top-level class named `DefaultConstructorDemo`, so it must be saved specifically as `DefaultConstructorDemo.java`. `Student` is a package-private top-level class in the same file.

## 4. Writing a Parameterized Constructor: The Default Constructor Disappears

This is the most common situation that causes a compilation error:

```java
class Product {
    private final String code;

    Product(String code) {
        this.code = code;
    }
}
```

The compiler sees that the constructor `Product(String)` has already been declared, so it does **not** add `Product()`. Therefore:

```java
Product one = new Product("P01"); // Valid.
// Product two = new Product();   // Error: constructor Product() not found.
```

This is an illustrative snippet to be placed inside a method; the erroneous line has been commented out. When uncommented, the compiler message typically states that the requested constructor cannot be applied to the given number/types of arguments.

**Intentional fixes:**

- If a product **must always have a code**, keep only the constructor taking a `String` and **do not support `new Product()`**. This is how you protect the invariant.
- If the API truly needs to create a product with a default code, **explicitly write** a no-argument constructor and delegate it to the main constructor.

```java
class Product {
    private final String code;

    Product() {
        this("UNKNOWN");
    }

    Product(String code) {
        if (code == null || code.isBlank()) {
            throw new IllegalArgumentException("code is required");
        }
        this.code = code;
    }

    String code() {
        return code;
    }
}
```

Both constructors in this version are declared by the programmer; there is no longer an implicit default constructor. `this("UNKNOWN")` is **constructor chaining**, creating only **one instance** and reusing the validation rule in the parameterized constructor.

### Complete Example: Before and After Writing a No-Argument Overload

Create the file **`ExplicitNoArgDemo.java`**:

```java
class Cart {
    private final String owner;

    Cart() {
        this("guest");
    }

    Cart(String owner) {
        if (owner == null || owner.isBlank()) {
            throw new IllegalArgumentException("owner required");
        }
        this.owner = owner;
    }

    String getOwner() {
        return owner;
    }
}

public class ExplicitNoArgDemo {
    public static void main(String[] args) {
        Cart first = new Cart();
        Cart second = new Cart("Lan");

        System.out.println(first.getOwner());
        System.out.println(second.getOwner());
    }
}
```

Commands:

```bash
javac ExplicitNoArgDemo.java
java ExplicitNoArgDemo
```

```text
guest
Lan
```

Here, **`Cart()` is an explicitly declared no-argument constructor**, not a default constructor automatically generated by the compiler. Because the parameterized constructor `Cart(String)` also exists, removing `Cart()` would cause the call `new Cart()` to fail compilation.

**Design implication:** having no parameters does not mean the state is initialized as intended. If a no-argument constructor genuinely needs to exist, the programmer should choose meaningful default values instead of assuming `null`/`0` fields are valid.

## 5. Important Condition: The Superclass Must Have a Callable No-Argument Constructor

Having the compiler **implicitly declare** a constructor for a subclass does not guarantee that the class will **compile successfully**.

Consider the parent class:

```java
class Base {
    Base(int id) {
    }
}

class Derived extends Base {
}
```

This example **intentionally does not compile**. `Base` has a constructor taking an `int`, so **there is no `Base()`**. `Derived` does not declare a constructor of its own, so the compiler wants to generate `Derived()`, with the key equivalent being:

```java
// class Derived extends Base {
//     Derived() {
//         super(); // Error because Base does not have Base().
//     }
// }
```

Because `super()` does not match a suitable superclass constructor, **the subclass still fails to compile**. You cannot say that "not declaring a constructor always lets you call `new Derived()`."

### Two Ways to Fix It

**Approach A — the subclass declares a constructor and calls a valid superclass constructor:**

```java
class Base {
    private final int id;

    Base(int id) {
        this.id = id;
    }

    int id() {
        return id;
    }
}

class Derived extends Base {
    Derived() {
        super(7);
    }
}
```

Once the subclass explicitly declares `Derived()`, there is no longer an implicit default constructor for `Derived`. This constructor calls `super(7)`, so it can compile if `Base(int)` is accessible.

**Approach B — the superclass provides a no-argument constructor:**

```java
class Base {
    Base() {
        System.out.println("Base()");
    }

    Base(int id) {
        System.out.println("Base(" + id + ")");
    }
}

class Derived extends Base {
    // No constructor declared.
}
```

In this version, the compiler validly declares `Derived()` implicitly because `super()` can call `Base()`. The two versions above are **two independent approaches**; do not place classes with duplicate names in the same file.

### Standalone Program Observing the Default Chain

File **`DefaultInheritanceDemo.java`**:

```java
class BaseMachine {
    BaseMachine() {
        System.out.println("BaseMachine()");
    }
}

class PrinterMachine extends BaseMachine {
    // Compiler automatically generates PrinterMachine(), calling super().
}

public class DefaultInheritanceDemo {
    public static void main(String[] args) {
        new PrinterMachine();
        System.out.println("created");
    }
}
```

Run:

```bash
javac DefaultInheritanceDemo.java
java DefaultInheritanceDemo
```

```text
BaseMachine()
created
```

Here, `PrinterMachine` does not declare a constructor, yet its default constructor can call `BaseMachine()`. This does **not** mean the compiler automatically added `BaseMachine()`: this superclass constructor was explicitly declared by the programmer.

## 6. How Access Affects Calling the Default Constructor

A default constructor has an access level corresponding to how the regular class is declared under JLS rules (for example, top-level `public` or package-private). If code at the call site **cannot access the class** or **cannot access the constructor**, `new X()` will be blocked.

### Non-`public` Top-Level Class

```java
class PackageItem {
}
```

`PackageItem` is a **package-private** top-level class, and its default constructor likewise does not grant public access from all packages. Code in the **same package** can call `new PackageItem()` if there are no other barriers; code in another package cannot directly reference `PackageItem`.

### `public` Top-Level Class

If the file `PublicItem.java` contains:

```java
public class PublicItem {
}
```

The compiler generates a default constructor with `public` access. Code from another package can call `new PublicItem()` if conditions such as class visibility, module exports, and classpath/module path are all satisfied.

Compare this with an **explicit package-private** constructor:

```java
public class PublicItem {
    PublicItem() {
    }
}
```

This is a **different version** of `PublicItem.java`, not placed simultaneously with the previous version. The class is still `public`, but the constructor `PublicItem()` does not declare `public`, so it is **package-private**. The compiler does **not** add another default constructor. Therefore, code in an external package can see the `PublicItem` type, but **cannot call `new PublicItem()`**.

**Key point:** an implicitly generated constructor gets its access level according to the rules for the default constructor, whereas a constructor **declared by you** gets its access level based on the modifier you actually write. Those two can differ even for a `public` class.

### `private` Constructor and Static Factory

```java
class Session {
    private final String id;

    private Session(String id) {
        this.id = id;
    }

    static Session guest() {
        return new Session("guest");
    }

    String id() {
        return id;
    }
}
```

Because `Session` has declared the constructor `private Session(String)`, it **has no default constructor**. External code cannot call `new Session()`, nor can it call the private constructor from an unpermitted context. Instead, the class proactively provides `Session.guest()` as a **static factory method**. A factory method is not a constructor; it calls the constructor from within the permitted scope.

When reading the error `constructor X(...) has private access`, check **access permissions** rather than jumping to the conclusion that "there is no constructor." The error "no constructor exists with this parameter list" and the error "the constructor exists but cannot be accessed" are two different situations.

## 7. An `abstract class` Can Still Have a Default Constructor

An **abstract class** cannot be instantiated directly, but it may still need a constructor to initialize the superclass portion when a subclass is created.

```java
abstract class Task {
    private String status = "new";

    String status() {
        return status;
    }
}

class EmailTask extends Task {
    // No constructor declared.
}
```

Neither `Task` nor `EmailTask` declares a constructor, so the compiler supplies an appropriate default constructor for each class. However:

```java
// Task invalid = new Task();  // Error: cannot directly instantiate an abstract class.
Task valid = new EmailTask();   // Valid in an appropriate access context.
```

These two lines are a code snippet to be placed inside a method; the erroneous line is commented out. When `new EmailTask()` is called, the subclass's default constructor calls `Task`'s appropriate default constructor to initialize the supertype portion.

### Complete Example

Create the file **`AbstractConstructorDemo.java`**:

```java
abstract class Animal {
    private String family = "animal";

    String family() {
        return family;
    }

    abstract String sound();
}

class Cat extends Animal {
    @Override
    String sound() {
        return "meow";
    }
}

public class AbstractConstructorDemo {
    public static void main(String[] args) {
        Animal pet = new Cat();

        System.out.println(pet.family());
        System.out.println(pet.sound());
    }
}
```

```bash
javac AbstractConstructorDemo.java
java AbstractConstructorDemo
```

```text
animal
meow
```

`Animal` is abstract so it cannot be instantiated directly, but its default constructor is still valid. `Cat` has a default constructor that calls `super()`, after which the `Cat.sound()` implementation is used when called through an `Animal`-typed variable. You should not infer from an abstract class disallowing `new Animal()` that it "has no constructor."

## 8. Instance Field Initializers and Instance Initializers Still Run When Only a Default Constructor Exists

Do not confuse "the compiler generates an implicit constructor" with "all instance fields end up keeping their default values." Fields and initializers still have their own initialization mechanisms.

Create the file **`DefaultWithInitializersDemo.java`**:

```java
class Counter {
    int value = 3;

    {
        value += 2;
        System.out.println("instance block: " + value);
    }

    // No constructor declared.
}

public class DefaultWithInitializersDemo {
    public static void main(String[] args) {
        Counter first = new Counter();
        Counter second = new Counter();

        System.out.println(first.value);
        System.out.println(second.value);
    }
}
```

```bash
javac DefaultWithInitializersDemo.java
java DefaultWithInitializersDemo
```

```text
instance block: 5
instance block: 5
5
5
```

Logical sequence for each `Counter` instance:

1. Instance fields have their **default values** when allocated: for `int`, that is `0`.
2. The superclass constructor is called according to the rules.
3. The field initializer `int value = 3;` runs, setting `value = 3`.
4. The instance initializer block `{ value += 2; ... }` runs, so it prints `instance block: 5`.
5. The implicit default constructor completes, with no additional programmer-written constructor logic.

The two `new` calls create two independent instances, so the block prints **twice**, and the final value of each object is `5`.

### Static Initializers Do Not Run Once per Object

```java
class Device {
    static int created;

    static {
        System.out.println("Device class initialized");
    }

    {
        created++;
    }
}
```

The snippet above has no `main`. Appropriate class initialization will run `static { ... }`, typically only once per initialized class in the corresponding class loader; whereas `{ created++; }` is an **instance initializer** and runs when each object is created. The compiler can still supply a default constructor for `Device` because these two blocks are **not constructor declarations**.

**Note:** Writing `static { ... }` or `{ ... }` in the class body does not prevent a default constructor. What prevents it is the existence of a **declared constructor**.

## 9. How Does a Programmer-Written No-Argument Constructor Differ from a Default Constructor?

Comparison table:

| Criterion | Default constructor | Programmer-written `X()` constructor |
| --- | --- | --- |
| Who declares it? | Implicitly declared by the compiler according to Java grammar | Declared in the class by the programmer |
| Existence condition | A qualifying class has **no constructor declarations** | The programmer explicitly writes `X() { ... }` |
| Number of parameters visible in source code | There is no source declaration of this constructor | **0** |
| Can contain validation/custom behavior? | No programmer-written custom body | Yes, within the valid limits of a constructor |
| Can explicitly call `this(...)`? | Does not have a programmer-declared body to do so | Yes, if an appropriate target constructor exists and rules are followed |
| Calling the superclass constructor | Uses the corresponding implicit call, typically `super()` | Can use explicit `super(...)` or `this(...)`, or an appropriate implicit `super()` |
| Access level | Follows the class's default constructor rules | Follows the modifier actually declared on the constructor |
| Eliminates the default constructor? | It is the default constructor | **Yes**, the presence of this constructor prevents the compiler from generating a default constructor |
| When the class adds a parameterized constructor | The default constructor is no longer automatically generated | The written `X()` constructor still exists unless removed |

Example illustrating two **separate versions**:

```java
// Version A:
class NoticeA {
}
// Compiler generates NoticeA().

// Version B:
class NoticeB {
    NoticeB() {
        System.out.println("created");
    }
}
// No compiler-generated default constructor for NoticeB.
```

Both `NoticeA` and `NoticeB` can be called via `new NoticeA()` and `new NoticeB()` in an appropriate access context, but only version B additionally prints `created`. A standalone `new X()` call is not enough for you to tell whether the constructor is **implicitly generated** or **explicit**; you must inspect the class declaration.

## 10. Nested Classes: Default Constructors Exist, but Instantiation Syntax Still Depends on Context

When discussing whether `new Inner()` is valid, you must distinguish between a **static nested class** and a **non-static member (inner) class**.

```java
class Outer {
    static class StaticNested {
        // No constructor declaration -> has a default constructor.
    }

    class Inner {
        // No constructor declaration -> has a default constructor.
    }
}
```

Neither `StaticNested` nor `Inner` declares a constructor, so each has its corresponding default constructor. However, the way instances are created differs:

```java
Outer.StaticNested a = new Outer.StaticNested();

Outer outer = new Outer();
Outer.Inner b = outer.new Inner();
```

This is a **code snippet to be placed inside a method**. A static nested class does not require an instance of `Outer`. A non-static inner class, on the other hand, is bound to an **enclosing instance**, so outside `Outer` you must use the syntax `outer.new Inner()` (given permitted access conditions).

In terms of implementation, the compiler may need to pass along a reference to the enclosing instance when constructing a non-static inner class. That does **not** mean you have to declare `Inner(Outer outer)` manually in source code just to use the default constructor.

### Runnable Java 17+ Example

File **`NestedDefaultDemo.java`**:

```java
class House {
    private final String name = "Blue";

    class Room {
        String describe() {
            return name + " room";
        }
    }

    static class Key {
        String describe() {
            return "key";
        }
    }
}

public class NestedDefaultDemo {
    public static void main(String[] args) {
        House house = new House();
        House.Room room = house.new Room();
        House.Key key = new House.Key();

        System.out.println(room.describe());
        System.out.println(key.describe());
    }
}
```

```bash
javac NestedDefaultDemo.java
java NestedDefaultDemo
```

```text
Blue room
key
```

`House`, `Room`, and `Key` declare no constructors of their own. Therefore, no manual constructor needs to be written in any class to run this example. However, the syntax to create a `Room` requires a specific `House`, whereas `Key` does not.

## 11. Kinds of Types with Special Constructor Rules

The rule "no constructor declared → default constructor" at the beginning was meant to explain **regular Java classes**. When moving to **enums** or **records**, Java has specialized constructor rules; you should not mechanically copy the `new ClassName()` call syntax.

### Enum: Cannot Be Instantiated with `new` from Application Code

```java
enum Status {
    NEW, DONE
}
```

This is a valid enum. Enum values are represented by the constants `NEW` and `DONE` managed by the language. You cannot write `new Status()` to arbitrarily create enum instances like a regular class. Enum constructors also have specific rules regarding access levels and initialization.

Therefore, when studying default constructors for **regular classes**, do not use an `enum` as an example to prove that "if no constructor is declared, `new X()` always works."

### Record: Record Components Are Tied to the Canonical Constructor

```java
record Point(int x, int y) {
}
```

Java 17 supports `record`. When a canonical constructor is not explicitly declared, a record has an **implicitly generated canonical constructor** matching the record's components; the proper way to create an object here is `new Point(2, 3)`, not a default no-arg constructor like an empty class. If a record has components `x` and `y` and you call `new Point()` without declaring an appropriate constructor, it will fail because of missing arguments.

A record can have additional constructors within the specific constraints of records; the applicable rules do not completely overlap with those of a regular Java class. The focus of this article is the default constructor **generated by the compiler for regular classes**.

### Anonymous Classes and Advanced Exceptions

An anonymous class (for example, `new Runnable() { ... }`) has implicit constructor declaration rules that differ from a named class; it is tied to the anonymous object creation expression and the declared supertype. You should not try to call an anonymous class's constructor by class name because an anonymous class **has no source-level class name** to call that way.

When reading the specification, cases like enums, records, and anonymous/local/inner classes have their own details. To resolve basic `new X()` errors, first check **whether X is a regular class or a special kind of declaration**.

## 12. What Happens If the Superclass Constructor Is Not Accessible?

Not only does **lacking** a no-argument constructor cause an error; **not having access** to that constructor is also enough to prevent the subclass from implicitly calling `super()`.

Example (two classes in the same file and same package, yet the private constructor is still restricted by class and nested access rules):

```java
class LockedBase {
    private LockedBase() {
    }
}

class LockedChild extends LockedBase {
    // The compiler wants to generate a default constructor calling super().
    // However, LockedBase() is private so it is not accessible from here.
}
```

This example **intentionally does not compile**. `LockedBase()` exists, but it is `private`, so `LockedChild` cannot call it. This case differs from a superclass only declaring a parameterized constructor; in both cases, what is required is **an accessible no-argument superclass constructor** if the subclass needs an implicit `super()`.

If you want to allow subclassing, design the superclass constructor with appropriate access (for example, `protected` when intending to support inheritance), or provide a parameterized superclass constructor and require the subclass to explicitly call `super(args)` in a constructor declared by the subclass.

### Valid Fixed Example

```java
class ParentRecord {
    private final String id;

    protected ParentRecord(String id) {
        this.id = id;
    }

    String id() {
        return id;
    }
}

class ChildRecord extends ParentRecord {
    ChildRecord() {
        super("child-default");
    }
}
```

This class declaration compiles. `ChildRecord` **has no compiler-generated default constructor** because it already has an explicitly declared `ChildRecord()`. It can call the superclass's `protected ParentRecord(String)` constructor using `super("child-default")`.

Another option is to put a no-argument constructor `protected ParentRecord()` in the superclass if creating an object from defaults genuinely makes sense. You should not create an empty constructor merely to "get rid of the compile error" if doing so would leave the superclass in an invalid state.

## 13. What the Compiler Does NOT Do When Generating a Default Constructor

The existence of a default constructor **does not guarantee** the following:

1. **Does not automatically generate every needed overload.** A `Car { }` class may have an implicit `Car()`, but it does not automatically get `Car(String model)` or `Car(int year)`.
2. **Does not fix a superclass missing an appropriate constructor.** If the superclass only has `Base(int)`, the compiler does not automatically generate an additional `Base()` to help the subclass.
3. **Does not bypass access permissions.** The superclass constructor must be accessible; at the call site, both the target class and constructor must also be accessible.
4. **Does not bypass `abstract`.** An abstract class can have a default constructor yet still cannot be instantiated directly with `new`.
5. **Does not automatically initialize valid business data.** Reference-type fields default to `null` and numeric types default to 0; if business constraints require otherwise, you must use an initializer, constructor, or appropriate design.
6. **Does not validate parameters automatically.** A default constructor takes no parameters; it cannot verify input names, codes, or quantities.
7. **Does not automatically create "child objects" for reference fields.** For example, `Address address;` remains `null` if not yet initialized.
8. **Does not create an object when only declaring a variable.** `User user;` does not call a constructor yet. Only an appropriate instance creation expression (for example, `new User()`) initializes an object.
9. **Does not generate a default constructor if the class already has any constructor declaration.** Even a private, protected, package-private, public, or programmer-written no-argument constructor.
10. **Does not turn a constructor into a normal method.** A constructor has no return type and is not inherited or overridden like an instance method.

Those limitations explain most beginner errors when adding a first constructor or extending a class that requires a parameterized constructor.

## 14. A Combined Program: Default, Explicit, and Inheritance

Create the file **`ConstructorCasesDemo.java`**:

```java
class EmptyBox {
    int size;
    // Compiler supplies EmptyBox().
}

class TaggedBox {
    private final String tag;

    TaggedBox() {
        this("untagged");
    }

    TaggedBox(String tag) {
        this.tag = tag;
    }

    String tag() {
        return tag;
    }
}

class DeviceBase {
    DeviceBase() {
        System.out.println("DeviceBase()");
    }
}

class MobileDevice extends DeviceBase {
    private String model = "Generic";

    // No constructor declared.
    String model() {
        return model;
    }
}

public class ConstructorCasesDemo {
    public static void main(String[] args) {
        EmptyBox box = new EmptyBox();
        TaggedBox tagged = new TaggedBox();
        MobileDevice mobile = new MobileDevice();

        System.out.println("size=" + box.size);
        System.out.println("tag=" + tagged.tag());
        System.out.println("model=" + mobile.model());
    }
}
```

Run:

```bash
javac ConstructorCasesDemo.java
java ConstructorCasesDemo
```

Output:

```text
DeviceBase()

tag=untagged
model=Generic
```

Breakdown by constructor type:

- `EmptyBox`: **compiler-generated default constructor** because there is no constructor declaration; the `size` field defaults to `0`.
- `TaggedBox`: **no implicit default constructor**; `TaggedBox()` and `TaggedBox(String)` are declared by the programmer, and the no-argument version uses `this(...)` to initialize `tag`.
- `DeviceBase`: has a **programmer-written** constructor `DeviceBase()`; that constructor prints `DeviceBase()` when called.
- `MobileDevice`: has no constructor declaration, so the compiler implicitly generates a default constructor and calls `super()`; before completing, the field initializer sets `model = "Generic"`.
- The line `DeviceBase()` appears before the remaining three `println` lines because `new MobileDevice()` executes the superclass constructor **before** the main flow begins printing the final info lines.

The example also shows that a single Java file can contain multiple package-private top-level classes, but only one `public` top-level class, which is `ConstructorCasesDemo`.

## 15. When Should You Rely on the Default Constructor?

A default constructor is suitable for classes whose object creation process is simple, requiring no mandatory input data, and where default values/field initializers are sufficient to guarantee the state.

Example:

```java
class TimerSettings {
    int retries = 3;
    boolean enabled = true;
}
```

The class declares no constructor, so `new TimerSettings()` is valid within the corresponding access scope. The field initializers provide more meaningful default values than `0` and `false` if the application design expects `3` retries and an enabled state.

Conversely, if an object **must have** a code, name, or non-null reference, a parameterized constructor is the way to clearly express the contract:

```java
class Invoice {
    private final String number;

    Invoice(String number) {
        if (number == null || number.isBlank()) {
            throw new IllegalArgumentException("number required");
        }
        this.number = number;
    }

    String number() {
        return number;
    }
}
```

Here, the fact that the compiler **does not automatically generate** `Invoice()` is beneficial: it prevents callers from creating an `Invoice` without providing an invoice number.

### "Adding a Constructor" Can Break Existing Code

Suppose the initial version is:

```java
class Customer {
}
```

Other code has already written `new Customer()`. Later, you modify it to:

```java
class Customer {
    Customer(String name) {
    }
}
```

If the call sites are **recompiled**, `new Customer()` will fail because the default constructor has disappeared. To preserve the no-argument call, you need to explicitly declare `Customer()` **and** ensure a valid state; simply adding a new constructor does not automatically keep the old one.

For publicly released libraries, changing from a public default constructor to only a parameterized constructor can also affect compatibility of already-compiled code, depending on how the API changes. Test the API from client code when adding constructors.

## 16. Diagnosing Common Errors

| Symptom | Common Cause | How to Handle |
| --- | --- | --- |
| `constructor X in class X cannot be applied to given types` when calling `new X()` | Only parameterized constructor(s) exist | Pass the proper arguments or **explicitly write** a no-argument constructor |
| Compiler reports an error at a subclass declaration with no constructor | The default constructor tries to call `super()`, but the superclass lacks an appropriate no-argument constructor | Create a subclass constructor with `super(args)` or design an appropriate superclass constructor |
| `X() has private access` | The constructor exists but is not accessible | Check scope and modifiers; use a factory if one is designed |
| `X is abstract; cannot be instantiated` | `X` is an abstract class | Create a concrete subclass; the abstract class's default constructor can still exist |
| `new Outer.Inner()` is invalid | `Inner` is a non-static member class requiring an enclosing instance | Use `outer.new Inner()` according to access permissions |
| `new EnumName()` does not work | Enums have their own instance creation rules | Use the enum constants |
| `new RecordName()` is missing arguments | A record has a canonical constructor matching its components | Pass all components or declare a valid additional constructor |
| Field `String name` is still `null` after `new X()` | The field has no initializer or assignment | Initialize the field or require the value via a constructor |
| Calling `new X()` from another package fails | The class/constructor does not have an appropriate access level | Check `public` class, constructor, package/module |
| Writing `void X()` thinking it is a custom constructor | That is a method, not a constructor | Omit the return type when intending to declare a constructor |

### Subtle Mistake: "No Constructor Declared" Does Not Mean "No Constructor"

A class `class A {}` usually **has an implicit default constructor**. Therefore, seeing no `A()` line in the source is not enough to conclude that `new A()` is an error. You must check inheritance context, abstractness, visibility, and class kind.

### Another Subtle Mistake: "Having a No-Argument Constructor" Does Not Necessarily Mean Default Constructor

In `class B { B() {} }`, a no-argument constructor exists, but it is an **explicit no-arg constructor**. When describing compiler rules, calling it a compiler-generated constructor is incorrect.

### Superclass Mistake: Misunderstanding `super()`

`super()` in a constructor context is a **superclass constructor call**, not a command to "create an additional independent superclass object." A subclass instance contains the superclass's portion of state; the constructor chain initializes parts of **the same object** according to Java rules.

### Field Mistake: Default Does Not Equal Valid

`String id;` receives `null` upon object creation, but if the API requires a non-null `id`, an empty default constructor can produce an invalid state. You must choose constructors/initializers based on **invariants**, not merely to keep the compiler from reporting errors.

## 17. Self-Check Exercises with Answers

**Question 1.** Does the class `class A { }` have a no-argument constructor? Who declares it?

**Answer:** Yes, it has a no-argument **default constructor** implicitly declared by the compiler (under regular class rules), not written by the programmer.

**Question 2.** Given `class B { B(int n) { } }`, is `new B()` valid?

**Answer:** No. The class has declared `B(int)`, so the compiler does not implicitly supply `B()`; you need `new B(5)` or to declare `B()` explicitly.

**Question 3.** Does `class C { C() { } }` have a compiler-generated default constructor?

**Answer:** No. `C()` is an **explicit no-arg constructor**; its presence prevents a default constructor.

**Question 4.** Does the compiler generate a default constructor for `class D { void D() { } }`?

**Answer:** Yes. `void D()` is a method with a `void` return type, not a constructor declaration.

**Question 5.** Does `abstract class E { }` have a default constructor? Can you call `new E()`?

**Answer:** It has a default constructor under regular class rules; you **cannot** instantiate it directly because E is an abstract class. A concrete subclass can call the appropriate superclass constructor.

**Question 6.** Does `class Base { Base(int x) {} } class Sub extends Base {}` compile?

**Answer:** No. `Sub`'s default constructor needs `super()`, but `Base` has no no-argument constructor.

**Question 7.** What if `Sub` is changed to `class Sub extends Base { Sub() { super(1); } }`?

**Answer:** Valid if `Base(int)` is accessible. `Sub()` is a programmer-written constructor, **not an implicit default constructor**.

**Question 8.** What access level does the default constructor of top-level `public class PublicThing {}` (in `PublicThing.java`) have?

**Answer:** `public` according to the default constructor rules. If you explicitly declare `PublicThing() {}` without writing `public`, the programmer-written constructor is package-private.

**Question 9.** A class has `int count = 10;` and no constructor declaration: is `new X().count` still `0`?

**Answer:** No. The field initially receives the value `0`, but the instance field initializer assigns `10` before the constructor finishes.

**Question 10.** A class has `static { ... }` and `{ ... }` but declares no constructor. Does the compiler generate a default constructor?

**Answer:** Yes; static/instance initializer blocks are **not constructor declarations**.

**Question 11.** Why is `new House.Room()` invalid if `Room` is a non-static inner class, even when it has no programmer-written constructor?

**Answer:** An enclosing instance of `House` is required; the syntax from outside is typically `house.new Room()`. Having a default constructor does not bypass the enclosing instance requirement.

**Question 12.** Given `record Pair(int left, int right) {}`, is `new Pair()` automatically valid because the record has no programmer-written constructor?

**Answer:** No. A record receives a canonical constructor matching its components; the normal call is `new Pair(1, 2)` unless a valid additional constructor is declared.

## 18. Checklist When Encountering a `new ClassName()` Error

To determine why a no-argument constructor call fails, check in order:

1. **Is this a regular class, abstract class, enum, record, or inner class?** The kind of declaration affects syntax and instantiability.
2. **Are there any constructor declarations in the class?** If not, a regular class has a default constructor; if so, the compiler does **not** add a default constructor.
3. **Is there an explicit no-arg constructor?** If so, check the access level and logic of that constructor itself.
4. **If there is only a default constructor, is the no-argument superclass constructor accessible?** Check whether a parent constructor with the appropriate parameter list exists and whether it is restricted by private or a different package.
5. **Can the class itself be instantiated directly?** Abstract classes and enums impose different constraints.
6. **Can the calling code see the class and constructor?** Pay attention to `public`, package-private, nested access, and module visibility.
7. **For an inner class, is there an enclosing instance yet?** You need `outer.new Inner()` when outside the appropriate context.
8. **Do the constructor and initializers leave the object in a valid state?** Eliminating compile errors does not mean the object satisfies business constraints.

---

**Key takeaway:** For a **regular class**, only when there are **no constructor declarations at all** does Java implicitly generate a no-argument **default constructor**. A constructor `X()` written by you also takes no parameters, yet **is not a compiler-generated default constructor**. A default constructor needs to be able to call an appropriate no-argument superclass constructor, and it does not bypass `abstract` rules, access permissions, or enclosing instance requirements. Use explicit constructors when an object requires mandatory data or an initialization process with business meaning.
