# Capturing final and effectively final variables in Java anonymous classes

> **Context:** Java Core → Class/Object → Anonymous classes.  
> **Applies to:** Java 17+; the capture rules also relate to local classes and lambdas, but the focus of this article is **anonymous classes**.

## 1. Core concepts to understand

An **anonymous class** can use local variables and parameters from the enclosing scope directly inside the class body. When a local variable or parameter is referenced from an anonymous class, that variable must be **`final` or *effectively final*** according to Java language rules.

- **Explicit `final`:** the variable is declared with the `final` modifier and cannot be reassigned outside valid initial assignment cases.
- **Effectively final:** lacks the `final` modifier, yet based on how the variable is assigned in source code, it satisfies equivalent conditions of not being modified after initialization/appropriate definite assignment.
- **Capture:** the anonymous-class object can retain and use **the value of a variable** from the enclosing scope, even after the method that created the object has returned.
- **Primitive types:** the captured value is a primitive value such as `int` or `boolean`.
- **Reference types:** the captured value is a **reference** pointing to the object, not a deep copy of the object.
- **`final` / effectively final does not make a mutable object immutable.** You can call `list.add(...)`, `builder.append(...)`, or modify an array element even though the captured reference variable cannot be reassigned.

Valid example:

~~~java
void demo() {
    int prefix = 7;
    StringBuilder text = new StringBuilder("A");

    Runnable action = new Runnable() {
        @Override
        public void run() {
            System.out.println(prefix + ":" + text);
        }
    };

    text.append("B"); // Modify the object, do not reassign the text variable.
    action.run();      // Prints: 7:AB
}
~~~

This is a **method fragment**, not a standalone Java file. `prefix` and `text` are not reassigned, so both are *effectively final*. However, the mutable StringBuilder object that `text` points to is still modified.

If you add the line `text = new StringBuilder("C");` to the method, the capture becomes invalid; the compiler reports an error because `text` is no longer effectively final, even if the assignment occurs **after** the anonymous class declaration.

**Key takeaway:** The capture rule constrains **the local variable's value**, and does not itself constrain **the state of the object referenced by the variable**. This is foundational for understanding closures, callbacks, listeners, and asynchronous tasks in Java.

## 2. What is an anonymous class and how is it created?

An anonymous class is a class **without a declared name in source code**, defined and instantiated directly within a **class instance creation expression**. It is commonly used to:

1. Quickly implement an interface.
2. Extend a class and override methods.
3. Create a short callback/handler with its own state or logic.
4. Combine behaviors encapsulated inline with data from the lexical scope.

Example:

~~~java
Runnable task = new Runnable() {
    @Override
    public void run() {
        System.out.println("Hello");
    }
};
~~~

`new Runnable() { ... }` creates an instance of an **anonymous class implementing Runnable**, rather than directly instantiating the Runnable interface. The variable `task` has declared type Runnable; the runtime object is an instance of the anonymous class generated by the compiler.

### 2.1. An anonymous class can extend a class

~~~java
abstract class Message {
    abstract String content();
}

Message message = new Message() {
    @Override
    String content() {
        return "ready";
    }
};
~~~

This is a declaration fragment. An anonymous class can extend a concrete/abstract superclass or implement an interface corresponding to the syntax `new SomeType(...) { ... }`. It does not simultaneously have a separate source-level `extends A implements B` list like a named-class declaration; the base type is in the construction expression.

### 2.2. An anonymous class has no source-level simple name

You cannot write `new AnonymousClassName()` from elsewhere, nor can you directly write a named constructor for an anonymous class as you would for a named class. Instance initialization can be written using an instance initializer block or field initializers, and the call chain uses the base class constructor when it is an appropriate superclass.

### 2.3. Compared to a local class

A **local class** has a declared name within a block:

~~~java
class Task implements Runnable {
    public void run() {
        System.out.println("Hello");
    }
}
Runnable task = new Task();
~~~

An anonymous class condenses declaration and object creation into a single expression. Both local and anonymous inner classes follow the rule of capturing final or effectively final local variables/parameters, but an anonymous class has no local name to instantiate a second object via `new Task()`.

## 3. Local variables, fields, and parameters are three different categories

All of them can appear in anonymous-class code, but **the effectively final rule only applies to captured local variables/parameters**:

| Data used | Rule when referenced by an anonymous class | Can it change over time? |
| --- | --- | --- |
| Local primitive `int count` | Must be final/effectively final | Cannot be reassigned if captured |
| Local reference `List<String> list` | Reference variable must be final/effectively final | Referent List can be mutable |
| Method parameter `String label` | Parameter must be final/effectively final | Cannot reassign parameter if captured |
| Enclosing instance field `this.count` | Effectively final does not apply as with locals | Can change if the field is mutable |
| Static field `Config.mode` | Not a captured local variable | Can change according to field semantics |
| Anonymous-class instance field `this.calls` | Belongs to the anonymous object | Can change if the field is mutable |
| Captured immutable value `String` | Reference variable is final/effectively final | String content does not change |

**Do not confuse access rules with assignment rules.** Being allowed to access a private outer instance field under nested lexical access rules does not mean a static context automatically has an enclosing instance; and a mutable field does not automatically become a local captured variable.

## 4. Explicit `final`

Declaration:

~~~java
final int multiplier = 3;

Runnable task = new Runnable() {
    @Override
    public void run() {
        System.out.println(multiplier * 2);
    }
};
~~~

`multiplier` is a final local primitive. The compiler allows the anonymous class to use it.

Adding `multiplier = 4;` causes an error because a final variable cannot be reassigned after it has been initialized.

### 4.1. A final reference can still point to a mutable object

~~~java
final StringBuilder output = new StringBuilder();

Runnable task = new Runnable() {
    @Override
    public void run() {
        output.append("X");
    }
};

task.run();
task.run();
System.out.println(output); // XX
~~~

Both runs modify the same StringBuilder. The `output` variable keeps the same reference. **Final does not mean immutable**.

### 4.2. Final does not mean all data is a compile-time constant

~~~java
final int number = Integer.parseInt("17");
~~~

`number` is final, but the initializer is evaluated at runtime and is not a constant expression. An anonymous class can still capture number, because the requirement is final/effectively final rather than a compile-time constant.

### 4.3. Sometimes you do not need to write final

Since Java 8, effectively final locals/parameters can be captured by inner classes. In Java 17, most examples do not require the `final` modifier if the variable is actually not reassigned.

## 5. How is effectively final determined?

A local variable not declared `final` is *effectively final* if it is not reassigned according to the rules in the Java Language Specification, including definite-assignment cases.

Valid:

~~~java
int base = 10;

Runnable job = new Runnable() {
    @Override
    public void run() {
        System.out.println(base + 5);
    }
};
~~~

`base` only has an initial assignment. There is no subsequent modification to the variable.

Invalid:

~~~java
int base = 10;

Runnable job = new Runnable() {
    @Override
    public void run() {
        System.out.println(base + 5);
    }
};

base = 20; // ERROR: base is not effectively final.
~~~

This is **intentionally non-compiling code**. Having the assignment appear after the anonymous class declaration **does not save it**; the compiler checks assignments across the relevant scope.

### 5.1. `++`, `--`, and compound assignments also modify the variable

If `base` is captured:

~~~java
base++;
++base;
base += 1;
base -= 2;
base = base * 2;
~~~

each operation updates **the local variable itself**. They are invalid in situations where they cause `base` to lose its effectively final status.

Conversely:

~~~java
builder.append("x");
list.add("y");
array[0]++;
box.value++;
map.put("k", "v");
~~~

update **the state of the referent or field/array element**, rather than reassigning the corresponding local reference variable. They can be valid with respect to capture, though they may violate other API contracts/concurrency constraints.

### 5.2. One initial assignment per definite-assignment path

~~~java
int chosen;
if (flag) {
    chosen = 10;
} else {
    chosen = 20;
}

Runnable job = new Runnable() {
    @Override
    public void run() {
        System.out.println(chosen);
    }
};
~~~

This is a **fragment** assuming `flag` has already been declared. Under the rules for definite assignment and effectively final, `chosen` can be captured: it is assigned when previously definitely unassigned along the paths and is definitely assigned before the point of use. There is no requirement that every captured variable must have an initializer directly in its declaration.

### 5.3. Unreachable assignments and flow analysis

Checking effectively final status follows detailed rules in the JLS and cannot be replaced by a trick like “counting = signs”. In complex flow situations, rely on the compiler/JLS to determine it accurately, or rewrite it as a clear immutable local snapshot rather than trying to exploit hard-to-read edge cases.

### 5.4. Variables do not have to be constant variables to be captured

`final/effectively final` differs from a **constant variable**. A local `int n = readFromInput();` that is not reassigned can still be captured, even though its value is only known at runtime.

## 6. Complete program 1: final and effectively final

Create the file **`AnonymousCaptureBasicsDemo.java`**:

~~~java
public class AnonymousCaptureBasicsDemo {
    public static void main(String[] args) {
        final int base = 10;
        int addition = 7;
        StringBuilder label = new StringBuilder("A");

        Runnable task = new Runnable() {
            @Override
            public void run() {
                System.out.println("Number = " + (base + addition));
                System.out.println("Label = " + label);
            }
        };

        task.run();

        label.append("B");
        task.run();

        System.out.println("After mutation = " + label);
    }
}
~~~

Compile and run:

~~~bash
javac -encoding UTF-8 AnonymousCaptureBasicsDemo.java
java AnonymousCaptureBasicsDemo
~~~

**Exact stdout:**

~~~text
Number = 17
Label = A
Number = 17
Label = AB
After mutation = AB
~~~

**Explanation:**

- `base` is declared final.
- `addition` is not explicitly final, yet is effectively final because it is not reassigned.
- `label` is an effectively final reference variable that still points to the same StringBuilder after `append`.
- The task reads the primitive sum twice, both times 17.
- The StringBuilder state changes from A to AB, so the second run prints AB.

**There is no implicit StringBuilder copy** when the anonymous class captures `label`.

## 7. Nature of capture: primitive value, reference value, and aliasing

Java variables hold values. For primitives, those are primitive values. For reference types, those are reference values to objects, not the contents of the objects themselves.

### 7.1. Primitive capture

~~~java
int number = 5;
Runnable task = new Runnable() {
    @Override
    public void run() {
        System.out.println(number);
    }
};
~~~

`number` must be effectively final. The anonymous class uses the value 5.

There is no mutable int object behind `number` for a caller to modify through an alias.

### 7.2. Reference capture

~~~java
StringBuilder first = new StringBuilder("A");
StringBuilder second = first;

Runnable task = new Runnable() {
    @Override
    public void run() {
        System.out.println(first);
    }
};

second.append("B");
task.run(); // AB
~~~

`first` is effectively final; `second` is another local reference variable pointing to the same object. Modifying the object through `second` causes the anonymous class to observe AB.

### 7.3. Capturing a reference does not create a snapshot

An anonymous class capturing a `List`, `Date`, mutable domain object, array, or StringBuilder **does not automatically freeze its contents** at instance creation time. If an API requires a snapshot, you must use an immutable representation or a defensive copy at the boundary.

### 7.4. Why the language requires effectively final

An anonymous class object can escape the method and outlive the activation that created it. Rather than allowing access to a local stack variable that could continuously be reassigned from multiple scopes, Java uses semantics that capture valid variable values. This prevents the misconception that an anonymous callback “automatically sees reassignments of a local variable”.

Nevertheless, the heap object pointed to by a captured reference can still change state according to the ownership/concurrency contract.

## 8. Complete program 2: parameters and definite assignment

Create the file **`AnonymousParameterCaptureDemo.java`**:

~~~java
public class AnonymousParameterCaptureDemo {
    static Runnable create(boolean premium, String customer) {
        int points;

        if (premium) {
            points = 20;
        } else {
            points = 5;
        }

        Runnable task = new Runnable() {
            @Override
            public void run() {
                System.out.println(customer + ":" + points);
            }
        };

        return task;
    }

    public static void main(String[] args) {
        Runnable first = create(true, "Lan");
        Runnable second = create(false, "Minh");

        first.run();
        second.run();
        first.run();
    }
}
~~~

Compile/run:

~~~bash
javac -encoding UTF-8 AnonymousParameterCaptureDemo.java
java AnonymousParameterCaptureDemo
~~~

**Exact stdout:**

~~~text
Lan:20
Minh:5
Lan:20
~~~

### 8.1. Why is `points` effectively final?

`points` is declared without being initialized immediately. Each path of the if/else assigns points once while it is still definitely unassigned, and then the variable is no longer modified. The anonymous class is created after points has been initialized along every path.

### 8.2. Why is `customer` captured?

The method parameter `customer` is not reassigned inside create. It is effectively final and is a String reference to an immutable String. Each invocation creates an anonymous-class object with that invocation's captured values.

### 8.3. Two invocations do not share a primitive variable

`create(true, "Lan")` and `create(false, "Minh")` have their own parameter/local values. The two Runnable objects use their respective captured values; there is no shared global `points`.

### 8.4. What if `customer = customer.trim()` is inside the method?

If customer is captured as in this code, reassigning the parameter makes it not effectively final, regardless of whether it occurs before or after the anonymous class creation expression.

Instead of reassigning the captured parameter, create:

~~~java
String normalizedCustomer = customer.trim();
~~~

and then capture `normalizedCustomer` if that variable is not reassigned.

## 9. Distinguishing reassignment from mutation with a table

| Expression | Modifies the captured local variable itself? | Conclusion |
| --- | --- | --- |
| `int n = 1;` | Initial assignment | Capturable if effectively final |
| `n++;` | Yes | Not allowed when n is already captured |
| `n += 1;` | Yes | Similar |
| `list = new ArrayList<>();` | Yes | Not allowed for a captured list |
| `list.add("x");` | No | Valid for capture, if the List is mutable |
| `builder.append("x");` | No | Valid for capture |
| `builder = new StringBuilder();` | Yes | Not allowed if builder is captured |
| `array[0] = 9;` | Does not reassign the array variable | Can be valid |
| `array = new int[3];` | Yes | Not allowed for a captured array |
| `box.value++;` | Does not reassign the box reference | Can be valid if the field is mutable |
| `map.put("k", v);` | Does not reassign the map reference | Can be valid if the map is mutable |
| `outer.count++;` | Modifies outer field | Not a reassignment of a captured local |

**Identify the actual l-value being written.** `box.value++` writes to a field on an object; `n++` writes to a local primitive variable.

### 9.1. When calling a mutator is disallowed by the API

A `List.of("A")` object is unmodifiable. An anonymous class capturing a reference to this List can compile cleanly, but calling `add` will throw `UnsupportedOperationException`. This is a **runtime collection contract**, not a compiler final/effectively final check.

### 9.2. When the referent is immutable

A `String` object has no methods to alter its contents; capturing a reference to a String is safe with respect to mutation of the String itself. There is no need for `new String(oldValue)` purely defensively.

## 10. Complete program 3: mutable List and array

Create the file **`AnonymousMutableReferentDemo.java`**:

~~~java
import java.util.ArrayList;
import java.util.List;

public class AnonymousMutableReferentDemo {
    public static void main(String[] args) {
        List<String> tags = new ArrayList<>(List.of("A"));
        int[] counter = {0};

        Runnable task = new Runnable() {
            @Override
            public void run() {
                counter[0]++;
                tags.add("T" + counter[0]);
                System.out.println("Task tags = " + tags);
            }
        };

        tags.add("outside");

        task.run();
        task.run();

        System.out.println("Final tags = " + tags);
        System.out.println("Count = " + counter[0]);
    }
}
~~~

Run:

~~~bash
javac -encoding UTF-8 AnonymousMutableReferentDemo.java
java AnonymousMutableReferentDemo
~~~

**Exact stdout:**

~~~text
Task tags = [A, outside, T1]
Task tags = [A, outside, T1, T2]
Final tags = [A, outside, T1, T2]
Count = 2
~~~

`tags` and `counter` are reference variables and are not reassigned. The task can modify the ArrayList and the `counter[0]` element because they are mutable referents.

A single-element array is often used as a “holder” for a counter in closure-like code. This approach is syntactically valid, but it does not always mean good design: it easily creates hidden mutable state and provides no atomicity when multiple threads invoke run.

## 11. An anonymous class can outlive the method that created it

A factory method can return a Runnable from an anonymous class. The method ends, yet the Runnable object, while still reachable, can still use the captured values.

Create the file **`AnonymousLifetimeDemo.java`**:

~~~java
public class AnonymousLifetimeDemo {
    static Runnable create(String title, StringBuilder text) {
        int lengthAtCreation = text.length();

        return new Runnable() {
            @Override
            public void run() {
                System.out.println(
                        title + "|" + lengthAtCreation + "|" + text);
            }
        };
    }

    public static void main(String[] args) {
        StringBuilder data = new StringBuilder("A");
        Runnable task = create("job", data);

        data.append("B");
        task.run();

        data.append("C");
        task.run();
    }
}
~~~

Run:

~~~bash
javac -encoding UTF-8 AnonymousLifetimeDemo.java
java AnonymousLifetimeDemo
~~~

**Exact stdout:**

~~~text
job|1|AB
job|1|ABC
~~~

### 11.1. The three captured values have different roles

- `title` is a String parameter; immutable String contents.
- `lengthAtCreation` is the primitive int 1, computed right when create runs.
- `text` is a parameter reference to the same StringBuilder that the caller holds in `data`.

After create returns, the captured int remains 1; the StringBuilder contents can continue changing A→AB→ABC through the caller's alias.

### 11.2. Object lifetime and GC

The returned anonymous-class object can keep captured referents **reachable**. If it captures a large List or domain aggregate, that object graph can survive longer than the method that created the callback. This is an ownership and resource lifetime issue, not Java copying all the data into the class itself.

### 11.3. Do not rely on compiler implementation details

The compiler may use synthetic fields/constructor parameters to store captured values, but the names/order of synthetic fields are not an application contract. Rely on semantics observed through code rather than inspecting specific field names.

## 12. `this` in an anonymous class and enclosing `Outer.this`

Inside an anonymous class instance method:

- `this` is the **anonymous-class instance**.
- `Outer.this` within an applicable lexical instance scope is the **enclosing Outer instance**.
- A local variable with the same name as a field can lead to counterintuitive shadowing/name resolution.
- `this` inside a lambda, by contrast, has **lexical this semantics**, and does not create a lambda-instance this like an anonymous class.

### 12.1. Complete program 4: who owns the field?

Create the file **`AnonymousThisDemo.java`**:

~~~java
public class AnonymousThisDemo {
    private final String name;

    AnonymousThisDemo(String name) {
        this.name = name;
    }

    Runnable build(String label) {
        return new Runnable() {
            private final String name = "anonymous";

            @Override
            public void run() {
                System.out.println("Captured = " + label);
                System.out.println("Anonymous this = " + this.name);
                System.out.println("Outer this = "
                        + AnonymousThisDemo.this.name);
            }
        };
    }

    public static void main(String[] args) {
        AnonymousThisDemo outer = new AnonymousThisDemo("outer");
        Runnable task = outer.build("local");
        task.run();
    }
}
~~~

Run:

~~~bash
javac -encoding UTF-8 AnonymousThisDemo.java
java AnonymousThisDemo
~~~

**Exact stdout:**

~~~text
Captured = local
Anonymous this = anonymous
Outer this = outer
~~~

### 12.2. Explanation

`label` is an effectively final method parameter and is captured. `this.name` is **a field of the anonymous object**. `AnonymousThisDemo.this.name` is **a field of the enclosing outer object**. They are not equivalent to a captured parameter.

If the anonymous class is created inside a **static method**, there is no enclosing AnonymousThisDemo instance for using `AnonymousThisDemo.this`. If instance state is needed, pass an outer reference or create it in an instance context.

### 12.3. Fields are not required to be effectively final

An outer instance field can be mutable and read multiple times by an anonymous class. The effectively final condition for **captured locals/parameters** does not apply directly to outer object fields. This is a common reason learners mistakenly think “every variable must be final” when looking at anonymous class code.

## 13. Local scopes, definite assignment, and shadowing

Not every identifier with the same name resolves to a captured local. An anonymous class can declare a field with the same name and **shadow** the local variable name in the enclosing scope.

~~~java
int base = 10;

Runnable task = new Runnable() {
    int base = 20;

    @Override
    public void run() {
        System.out.println(base);
    }
};
~~~

This is a fragment. `base` inside run refers to **the anonymous class's field**, so it prints 20 and does not necessarily capture the outer local base.

### 13.1. Use clear names

~~~java
int capturedBase = 10;

Runnable task = new Runnable() {
    int ownBase = 20;

    @Override
    public void run() {
        System.out.println(capturedBase + ownBase);
    }
};
~~~

The result is 30 if task.run is called. Giving distinct names to captured values and anonymous fields is usually easier to understand than shadowing.

### 13.2. There is no `method.this.local` syntax

`Outer.this` specifies the enclosing instance of a class type in an applicable context; method local variables are not fields of some `Method.this` object. If a local name is shadowed so that it is no longer accessible as expected, create another alias with a clear name before the anonymous-class expression.

### 13.3. A variable must be definitely assigned before use

~~~java
int result;
Runnable task = new Runnable() {
    public void run() {
        System.out.println(result); // Not definitely assigned.
    }
};
result = 3;
~~~

This snippet **intentionally does not compile**: the variable is captured without being definitely assigned at the point of use according to the rules; it must also satisfy effectively final. Do not rely on “it will be assigned before calling task.run” to bypass static definite-assignment analysis.

## 14. Loops: why can a basic-for index usually not be captured?

Consider:

~~~java
for (int i = 0; i < 3; i++) {
    Runnable task = new Runnable() {
        public void run() {
            System.out.println(i); // Intentionally does not compile.
        }
    };
}
~~~

`i++` makes the basic-for loop variable `i` not effectively final. Java rejects direct capture.

### 14.1. Create a snapshot per iteration

~~~java
for (int i = 0; i < 3; i++) {
    final int index = i;

    Runnable task = new Runnable() {
        public void run() {
            System.out.println(index);
        }
    };

    tasks.add(task);
}
~~~

This is a **fragment**, assuming `tasks` is a collection of an appropriate type. Each iteration creates a separate local variable `index`, assigned once and captured into that iteration's Runnable object.

### 14.2. Enhanced-for variable

With an enhanced-for loop:

~~~java
for (String name : names) {
    Runnable task = new Runnable() {
        public void run() {
            System.out.println(name);
        }
    };
}
~~~

If `name` is not reassigned in the body, the enhanced-for iteration variable can be captured per iteration according to the rules. This differs from the basic-for index `i`, which is incremented in the update clause.

## 15. Complete program 5: anonymous class capture across loops

Create the file **`AnonymousLoopCaptureDemo.java`**:

~~~java
import java.util.ArrayList;
import java.util.List;

public class AnonymousLoopCaptureDemo {
    public static void main(String[] args) {
        List<Runnable> tasks = new ArrayList<>();

        for (int i = 0; i < 3; i++) {
            final int index = i;

            tasks.add(new Runnable() {
                @Override
                public void run() {
                    System.out.println("Index = " + index);
                }
            });
        }

        for (String color : List.of("red", "blue")) {
            tasks.add(new Runnable() {
                @Override
                public void run() {
                    System.out.println("Color = " + color);
                }
            });
        }

        for (Runnable task : tasks) {
            task.run();
        }
    }
}
~~~

Run:

~~~bash
javac -encoding UTF-8 AnonymousLoopCaptureDemo.java
java AnonymousLoopCaptureDemo
~~~

**Exact stdout:**

~~~text
Index = 0
Index = 1
Index = 2
Color = red
Color = blue
~~~

Each anonymous object in the basic-for loop holds the captured int `index` from the iteration in which it was created. In the enhanced-for loop, each object holds the iteration variable `color` from its corresponding iteration. There is no scenario where all objects automatically read a shared `i = 3` after the loop, because direct capture of the variable i is disallowed by the compiler.

## 16. Snapshot versus live reference

An anonymous callback may execute later after the source data changes. You need to determine the business requirement:

- **Live reference:** the callback should observe the current state of a mutable object.
- **Snapshot:** the callback should use the value at the time it is created or registered.
- **Immutable value:** you can share the reference directly if the object is truly immutable.
- **Defensive copy:** create independent data if you need to prevent external alias mutation.

### 16.1. Capturing a mutable List directly

~~~java
List<String> source = new ArrayList<>(List.of("A"));

Runnable task = new Runnable() {
    public void run() {
        System.out.println(source);
    }
};

source.add("B");
task.run(); // [A, B]
~~~

It is not “captured when it was A, so it always prints A”. The anonymous class holds a reference to **the same ArrayList**.

### 16.2. Capturing a snapshot List

~~~java
List<String> source = new ArrayList<>(List.of("A"));
List<String> snapshot = List.copyOf(source);

Runnable task = new Runnable() {
    public void run() {
        System.out.println(snapshot);
    }
};

source.add("B");
task.run(); // [A]
~~~

`List.copyOf` creates an unmodifiable **structural snapshot** suitable for `List<String>`. String elements are immutable, so no deeper copying is needed in this situation.

### 16.3. An unmodifiable view differs from a snapshot

`Collections.unmodifiableList(source)` creates a view that blocks mutation through the view itself, yet can still reflect mutations to the underlying `source` made through another alias. Do not confuse this with a `List.copyOf` snapshot.

### 16.4. Mutable elements inside a snapshot

`List.copyOf(List<MutableItem>)` does not deep-copy MutableItem objects. If source contains a mutable element and the caller keeps an alias to modify it, a callback capturing the snapshot List can still see the element's state change. When a deep snapshot is needed, convert elements to immutable DTOs or copy them according to the contract.

## 17. Complete program 6: live state and immutable snapshot

Create the file **`AnonymousSnapshotDemo.java`**:

~~~java
import java.util.ArrayList;
import java.util.List;

public class AnonymousSnapshotDemo {
    public static void main(String[] args) {
        List<String> source = new ArrayList<>(List.of("A"));
        List<String> snapshot = List.copyOf(source);

        Runnable observer = new Runnable() {
            @Override
            public void run() {
                System.out.println("Live = " + source);
                System.out.println("Snapshot = " + snapshot);
            }
        };

        source.add("B");
        observer.run();

        try {
            snapshot.add("C");
        } catch (UnsupportedOperationException ex) {
            System.out.println("Snapshot unmodifiable");
        }

        System.out.println("Source after attempt = " + source);
    }
}
~~~

Run:

~~~bash
javac -encoding UTF-8 AnonymousSnapshotDemo.java
java AnonymousSnapshotDemo
~~~

**Exact stdout:**

~~~text
Live = [A, B]
Snapshot = [A]
Snapshot unmodifiable
Source after attempt = [A, B]
~~~

**Worth remembering:** both `source` and `snapshot` are effectively final variables, yet **one referent is mutable** and **one referent is an unmodifiable snapshot**. It is object semantics that explain the output, not which variable has the final modifier.

## 18. Reassignment of parameters is also disallowed when captured

A method parameter can be captured by an anonymous class when it is final/effectively final.

~~~java
static Runnable create(String title) {
    return new Runnable() {
        @Override
        public void run() {
            System.out.println(title);
        }
    };
}
~~~

Valid, because `title` is not reassigned.

Invalid:

~~~java
static Runnable broken(String title) {
    Runnable task = new Runnable() {
        @Override
        public void run() {
            System.out.println(title);
        }
    };
    title = title.trim(); // Captured parameter loses effectively final status.
    return task;
}
~~~

This is a **method fragment that intentionally does not compile**.

### 18.1. Normalizing input while still allowing capture

~~~java
static Runnable normalized(String input) {
    String value = input.trim();

    return new Runnable() {
        @Override
        public void run() {
            System.out.println(value);
        }
    };
}
~~~

`value` is initialized once; `input` is not captured inside the anonymous class. This is a clearer pattern than wanting to mutate the same parameter variable after capture.

### 18.2. If the parameter is a mutable object reference

`List<String> items` can be effectively final even if `items.add("X")` is called in the enclosing method or the anonymous callback. However, the List state will be shared unless copied.

## 19. Anonymous-class instance fields and callback-specific state

An anonymous class can have its own instance fields:

~~~java
Runnable task = new Runnable() {
    private int calls;

    @Override
    public void run() {
        calls++;
        System.out.println(calls);
    }
};
~~~

`calls` is **an instance field of the anonymous object**, not a captured local variable. It can be modified across invocations.

File **`AnonymousOwnStateDemo.java`**:

~~~java
public class AnonymousOwnStateDemo {
    public static void main(String[] args) {
        int step = 2;

        Runnable first = new Runnable() {
            private int count;

            @Override
            public void run() {
                count += step;
                System.out.println("First count = " + count);
            }
        };

        Runnable second = new Runnable() {
            private int count = 100;

            @Override
            public void run() {
                count += step;
                System.out.println("Second count = " + count);
            }
        };

        first.run();
        second.run();
        first.run();
    }
}
~~~

Run:

~~~bash
javac -encoding UTF-8 AnonymousOwnStateDemo.java
java AnonymousOwnStateDemo
~~~

**Exact stdout:**

~~~text
First count = 2
Second count = 102
First count = 4
~~~

`step` is a captured primitive and does not change. `count` is a separate field belonging to each anonymous object. `first` and `second` have different class implementations in source, and each object has its own state. There is no need for a local mutable holder for a callback's own counter.

### 19.1. Why does this not violate effectively final?

Effectively final governs **captured local variables/parameters** from the enclosing scope. `count++`/`count += step` inside the anonymous class modifies **the count field** belonging to the object, not the local `step`.

### 19.2. Do not use fields to hide shared-state bugs

If the callback is shared across multiple threads, anonymous-instance `count++` is still not atomic. Scope validity is not thread safety.

## 20. Anonymous class versus lambda: same capture constraint, different semantics

Both lambdas and anonymous classes can use final/effectively final local variables/parameters. However:

| Characteristic | Anonymous class | Lambda |
| --- | --- | --- |
| Implementation declaration | `new Interface() { ... }` | `(...) -> ...` |
| Has the body of a new class | Yes | Not an anonymous class |
| `this` | Anonymous object instance | Lexical enclosing `this` |
| Own instance fields in the body | Can be declared | Cannot declare fields in a lambda expression |
| Captured local variables | Final/effectively final | Final/effectively final |
| Captured mutable referent | Can still be modified | Can still be modified |
| Selecting interface methods | Can implement/override in the class body | Target must be an applicable functional interface |
| Easy to hold multiple mutable callback fields | Yes | Use an external holder/owner if needed |

Do not assume that a lambda “captures a live variable” while an anonymous class “captures a copy”, or vice versa. According to the rules, neither allows reassigning a captured local variable.

### 20.1. Comparison example

~~~java
int factor = 2;
StringBuilder buffer = new StringBuilder("A");

Runnable anon = new Runnable() {
    @Override
    public void run() {
        System.out.println(factor + ":" + buffer);
    }
};

Runnable lambda = () -> System.out.println(factor + ":" + buffer);

buffer.append("B");
anon.run();    // 2:AB
lambda.run();  // 2:AB
~~~

Only the StringBuilder referent changes.

### 20.2. Do not treat a lambda as an anonymous class

A lambda has a type corresponding to a functional interface and a runtime translation handled by the JVM/compiler; you should not depend on runtime class names/identity or synthetic implementation details of a lambda. Differences in `this` and scope are also why replacing an anonymous class with a lambda requires reviewing behavior, not merely removing boilerplate.

## 22. Concurrency: a captured reference does not make an object thread-safe

A callback can be executed from a thread pool, timer, event bus, or UI event dispatcher. With an anonymous class using a shared mutable object:

~~~java
int[] total = {0};

Runnable action = new Runnable() {
    @Override
    public void run() {
        total[0]++;
    }
};
~~~

`total` is effectively final, yet `total[0]++` **is not an atomic increment** when multiple threads run action concurrently. Updates can be lost.

### 22.1. Choose `AtomicInteger` when you need an atomic counter

File **`AnonymousAtomicCaptureDemo.java`**:

~~~java
import java.util.concurrent.atomic.AtomicInteger;

public class AnonymousAtomicCaptureDemo {
    public static void main(String[] args)
            throws InterruptedException {
        int amount = 3;
        AtomicInteger total = new AtomicInteger();

        Runnable task = new Runnable() {
            @Override
            public void run() {
                total.addAndGet(amount);
            }
        };

        Thread a = new Thread(task);
        Thread b = new Thread(task);

        a.start();
        b.start();

        a.join();
        b.join();

        System.out.println("Total = " + total.get());
    }
}
~~~

Run:

~~~bash
javac -encoding UTF-8 AnonymousAtomicCaptureDemo.java
java AnonymousAtomicCaptureDemo
~~~

**Exact stdout:**

~~~text
Total = 6
~~~

`amount` is an effectively final primitive. `total` is an effectively final AtomicInteger reference. Both tasks atomically add 3 to the same AtomicInteger; the main thread calls `join` on both before reading, so the result is deterministically 6, independent of the order of the two threads.

### 22.2. `AtomicInteger` is not a solution for every mutable graph

If an anonymous class references multiple fields or a mutable List/Map, a single AtomicInteger does not make other operations atomic or consistent. Use locks, concurrent collections, immutable snapshots, safe publication, or a dedicated owner service depending on the requirements.

### 22.3. A `final` reference does not mean child fields are `volatile`

Even when a compiler/captured field reference is stable, the underlying mutable state can still be subject to data races. To observe cross-thread updates properly under the Java Memory Model, you need **happens-before** relationships or compatible synchronization.

## 23. Special notes on UI/event listeners and callbacks

Anonymous classes appear in event listeners:

~~~java
StringBuilder state = new StringBuilder("initial");

button.addActionListener(new ActionListener() {
    @Override
    public void actionPerformed(ActionEvent event) {
        System.out.println(state);
    }
});
~~~

This is an illustrative **fragment** (requiring the corresponding Swing types/variables), not a standalone program. The local variable `state` is effectively final, but the StringBuilder's contents can change before the user clicks the button. The listener reads the **current state** of the referent, not necessarily the initial text.

Questions when designing a listener:

1. Does the listener want a **live model** or a **snapshot at registration time**?
2. Is the data mutable or immutable?
3. Does the event thread read state mutated by another thread?
4. Is the listener unregistered when no longer needed?
5. Do captured references accidentally retain a large UI object graph?

### 23.1. Do not capture heavy resources indefinitely

If a long-lived listener captures a service, session, or UI object, that object can remain alive longer than expected because the listener is still registered. GC is based on reachability. Manage lifecycle/unsubscribe appropriately.

### 23.2. Capturing a mutable request/context can lead to races

An async request callback should not by default capture a mutable Map of request parameters and then let the caller modify the Map after enqueueing. If you want “values at scheduling time” semantics, copy them into an immutable snapshot when creating the callback.

## 24. Common mistakes and how to fix them

### Mistake 1 — reassigning a captured local

~~~java
int retry = 1;
Runnable task = new Runnable() {
    public void run() {
        System.out.println(retry);
    }
};
retry++; // Intentionally does not compile.
~~~

**Fix:** determine the final/effectively final value to capture, or move genuinely mutable state into an appropriate owner object.

### Mistake 2 — reassigning a captured parameter after creating the callback

~~~java
Runnable create(String name) {
    Runnable task = new Runnable() {
        public void run() {
            System.out.println(name);
        }
    };
    name = name.trim(); // Intentionally does not compile.
    return task;
}
~~~

**Fix:** create `String normalized = name.trim();` and then capture normalized.

### Mistake 3 — assuming a final List cannot have elements added

~~~java
final List<String> items = new ArrayList<>();
items.add("A"); // Valid.
~~~

**Mindset fix:** a final variable is different from an immutable List.

### Mistake 4 — using `List.of` and thinking the error is caused by capture

~~~java
List<String> items = List.of("A");
Runnable task = new Runnable() {
    public void run() {
        items.add("B"); // Compiles, throws UOE at runtime.
    }
};
~~~

**Fix:** do not call mutators on an unmodifiable collection; use a mutable List if needed or an immutable update that creates a new List.

### Mistake 5 — capturing a mutable List and expecting a snapshot

~~~java
List<String> items = new ArrayList<>(List.of("A"));
Runnable task = new Runnable() {
    public void run() {
        System.out.println(items);
    }
};
items.add("B");
~~~

The task can print [A, B] if it runs after the mutation on the same thread. To get [A], capture `List.copyOf(items)` for String elements.

### Mistake 6 — thinking an array holder is automatically thread-safe

`int[] counter = {0};` followed by `counter[0]++` is not atomic under concurrency. If a thread-safe counter is needed, use `AtomicInteger` or an appropriate lock/owner.

### Mistake 7 — capturing a basic-for `i` directly

`i++` makes i not effectively final. **Fix:** create a final/effectively final snapshot `index = i` in each iteration.

### Mistake 8 — confusing captured locals with anonymous fields

An anonymous object has an `int count` field, and run can increment count. That does not disprove the final/effectively final rule because count **is not a captured outer local**.

### Mistake 9 — confusing anonymous `this` with outer `this`

Inside an anonymous-class method, `this` is the anonymous instance. Use `OuterClass.this` when the enclosing instance is needed and the context permits it.

### Mistake 10 — forgetting that a callback can have a long lifetime

An anonymous-class object can keep large referents alive for a long time, causing memory retention. Review registration/unregistration and capture only the necessary data.

### Mistake 11 — treating a lambda and an anonymous class as completely equivalent

The capture rules are similar, yet `this` and class semantics differ; check behavior when refactoring.

### Mistake 12 — relying on synthetic fields

The names of compiler-generated captured fields are not part of the API and can change across compilers/versions. Do not use reflection based on those names for application logic.

## 25. Checklist before using anonymous-class capture

1. Is the anonymous class created in an instance or static context?
2. Which local variables/parameters does it capture?
3. Is each captured variable final/effectively final?
4. Are there assignments, `++`/`--`, or compound assignments that break that property?
5. Are the variables definitely assigned before being used?
6. Is the captured type a primitive or a reference?
7. Is the referent mutable or immutable?
8. Are there aliases in the caller that can modify the referent?
9. Does the callback need a live value or a snapshot?
10. If a snapshot is needed, have you used an immutable projection/defensive copying?
11. Does the copied List contain mutable elements that need deeper copying?
12. Is an unmodifiable view being confused with a snapshot?
13. Is an outer instance field being mistaken for a captured local?
14. Does the anonymous class's own instance field have clear ownership?
15. Is there name shadowing between a field and a local variable?
16. Does a basic-for index have a snapshot per iteration?
17. Is an enhanced-for variable reassigned?
18. Can the anonymous object outlive the method that created it?
19. Does the captured object graph increase lifetime/memory retention?
20. Can the callback be invoked from multiple threads?
21. Do mutable operations have appropriate synchronization/atomicity?
22. Is `this` used properly for anonymous vs enclosing instance?
23. If converted to a lambda, would `this`/method resolution behavior change?
24. Are compile-time capture errors distinguished from runtime collection errors?
25. Are there code tests verifying mutation/snapshot behavior and expected output?

## 26. Exercises with answers

**Question 1.** Can an anonymous class capture a local variable not declared `final`?

**Answer:** Yes, if the variable is *effectively final* and satisfies definite-assignment/scope rules.

**Question 2.** Does `final StringBuilder text` prohibit calling `text.append`?

**Answer:** No; only reassigning the reference variable is prohibited, not StringBuilder mutators.

**Question 3.** Is assigning `text = new StringBuilder()` after the declaration of an anonymous class that already captured text valid?

**Answer:** No, if the variable loses its effectively final status. Placing the reassignment after the expression does not create an exception.

**Question 4.** If a captured primitive int does not change, will the callback always print that same primitive value?

**Answer:** If the method prints only the captured primitive itself, yes; however, the overall expression can still depend on other mutable fields/objects.

**Question 5.** Does capturing a reference create a deep copy of the object?

**Answer:** No. It uses the reference value, and aliases to the referent can still modify its state.

**Question 6.** A local `int[] counts = {0}` is captured; does `counts[0]++` compile?

**Answer:** Yes, as far as capture is concerned: the array element changes rather than the local reference; thread safety is a separate concern.

**Question 7.** Is `counts = new int[]{1}` valid when counts is already captured?

**Answer:** No, because that is a reassignment of the local reference variable.

**Question 8.** Can a parameter not declared final, yet not reassigned, be captured?

**Answer:** Yes, if it is effectively final.

**Question 9.** Can a captured parameter be trimmed using `parameter = parameter.trim()`?

**Answer:** No, if reassigning makes the parameter not effectively final. Create a normalized local to capture instead.

**Question 10.** If a captured List is a mutable ArrayList and the caller adds to it after registering the callback, will the callback see it?

**Answer:** It can see the new additions if it is the same object, depending on execution/concurrency behavior; capture does not snapshot contents.

**Question 11.** Does `List.copyOf(source)` create an appropriate structural snapshot?

**Answer:** Yes, for non-null contents per its contract, though it does not deep-copy mutable elements.

**Question 12.** Does `Collections.unmodifiableList(source)` always isolate from source?

**Answer:** No; the view can still reflect source mutations made through another alias.

**Question 13.** Why can an anonymous-class object still use captured values after the method returns?

**Answer:** The object retains the captured values according to Java semantics; the method stack frame does not need to remain active.

**Question 14.** Can capturing a large mutable object extend its lifetime?

**Answer:** Yes, if the anonymous object remains reachable and holds the object via the captured reference.

**Question 15.** Does `this` inside an anonymous class point to the outer class?

**Answer:** No; `this` is the anonymous instance. Use qualified `Outer.this` in an appropriate lexical instance context.

**Question 16.** Does an anonymous class instance field need to be effectively final?

**Answer:** No, under the captured-local rule. It is a field of the anonymous object; its mutability follows its field declaration.

**Question 17.** Must an enclosing outer instance field be final for an anonymous class to modify it?

**Answer:** No; the final/effectively final restriction here applies to captured locals/parameters, not outer instance fields.

**Question 18.** Can a basic-for loop index incremented with i++ be captured directly?

**Answer:** No, because i is not effectively final. Snapshot `index = i` on each iteration.

**Question 19.** Can an enhanced-for iteration variable that is not reassigned be captured?

**Answer:** Yes, according to the per-iteration rules of enhanced-for.

**Question 20.** Do two Runnables created by two invocations of the same factory method share a primitive parameter value?

**Answer:** Not by default; each invocation has its own argument values captured. They can point to the same object if the caller passes the same reference in.

**Question 21.** Is capturing `AtomicInteger` the reason the increment is atomic?

**Answer:** No; atomicity comes from the AtomicInteger API.

**Question 22.** Can you use an `int[] holder` and assume the data is automatically protected across threads?

**Answer:** No. Array updates are not automatically atomic.

**Question 23.** Do lambdas and anonymous classes share the same final/effectively final rule for captured locals?

**Answer:** Yes, though `this` and class body semantics differ.

**Question 24.** Why should you not trust `equals` when asking whether two references have the same object identity?

**Answer:** `equals` can compare value, whereas `==` compares identity for compatible references.

**Question 25.** What changes when replacing `list.add("x")` with `list = otherList`?

**Answer:** The first expression mutates the referent; the second reassigns the captured local variable and can be rejected by the compiler.

**Question 26.** Does a captured mutable List make the anonymous object itself mutable?

**Answer:** A mutable referent can cause the callback's output/observable behavior to change over time, even though the reference variable stays fixed; you must define the contract.

**Question 27.** If you need the text at callback creation time, should you capture StringBuilder or String?

**Answer:** Usually capture a String snapshot from `builder.toString()`, because String is immutable.

**Question 28.** If an anonymous class field and an outer local have the same name, does an unqualified identifier in the anonymous body definitely refer to the outer local?

**Answer:** No; shadowing can cause the field to be selected. Use clear, distinct names.

**Question 29.** Is a static field subject to the same final/effectively final capture rule as a local?

**Answer:** No; a static field is class state, with its own scope and concurrency rules.

**Question 30.** What is the single most important takeaway of this article?

**Answer:** An anonymous class may only capture final or effectively final local variables/parameters; for a reference variable, what is captured is the reference value to the object — **it does not inherently prohibit mutating the object**.

## 27. Summary and practical application

When an anonymous class references an external variable/parameter, ask in this exact order:

1. Is this a **local variable/parameter** or an **instance/static field**?
2. If it is a local/parameter, can the compiler determine that it is **final/effectively final**?
3. If the type is a reference, can the referent mutate or have other aliases?
4. Is the callback executed immediately, or can it be retained and invoked later/on another thread?
5. Does the API require **live state** or **snapshot state**?
6. Is a defensive copy, immutable value, ownership policy, or synchronization needed?

Guiding principle: use `final` or effectively final for valid capture; use **immutable values and snapshots** if you want data not to change; use **shared mutable objects with an API/concurrency contract** if you intentionally want mutable state updates. Avoid static/global state variables or array holders merely to work around the compiler if that introduces additional coupling.

**Distinguishing between “the captured variable's value” and “the state of the object pointed to by the reference” is the key to Java anonymous classes.** Clearly understanding this boundary helps you write listeners, callbacks, workers, GUI handlers, and asynchronous operations that are correct both at compile time and at runtime.
