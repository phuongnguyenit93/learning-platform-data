# Copy Constructors and Named Copy Factories in Java

When you need to create an object based on an existing one, Java commonly gives us two transparent design approaches: a **copy constructor** and a **named copy factory**. Both are developer-defined APIs, not an automatic feature generated by Java for every class.

A copy constructor typically takes the form `new Type(existing)`; a factory may have names such as `Type.copyOf(existing)`, `Type.snapshotOf(source)`, or `Type.duplicateAsNew(source, newId)`. The name helps users know what is preserved, what is newly created, and whether ownership relationships with child objects change.

The most important point: **creating a new root object does not necessarily create an independent copy**. If the new root still points to the same `ArrayList`, `Date`, array, or mutable element, changes on one side can cause the other side to change as well. Conversely, for immutable value objects, a copy factory can even **return the same instance** if the contract does not require a new identity.

This article belongs to **Java core - class-object**, section **Object Copying**. The content uses Java **17+**, explaining constructor/factory syntax, overload rules, validation, shallow and deep copying, defensive copies, `final` types and `record`, differences from `Object.clone()`, inheritance and object slicing, copying cyclic graphs, entity identity, exceptions, concurrency, and testing. Complete programs include file names, run commands, and **deterministic stdout**; snippets used only for explanation are clearly noted.

## 1. What Is a Copy Constructor?

In Java, a **copy constructor** is a constructor of class `T` that accepts an object of type `T` (or a related source type) to initialize a new object based on existing data.

~~~java
final class Pixel {
    private final int x;
    private final int y;

    Pixel(int x, int y) {
        this.x = x;
        this.y = y;
    }

    Pixel(Pixel source) {
        this(source.x, source.y);
    }

    String describe() {
        return "(" + x + "," + y + ")";
    }
}
~~~

This is a **valid class**, without `main` yet. Calling `new Pixel(existingPixel)` executes the `Pixel(Pixel)` constructor and creates **a new Pixel object**. The statement `this(source.x, source.y)` calls the two-parameter constructor in the same class, thereby avoiding duplication of initialization rules.

There is no dedicated keyword named `copy` or standard annotation that causes Java to automatically generate a copy constructor. The designer **must write** it and decide:

- Which fields are copied by value as-is?
- Which fields need copies of child objects?
- Should business IDs be kept or must new IDs be generated?
- Is validation needed for data retrieved from the source?
- Is `source == null` allowed?
- Must the new object always differ from the source according to `==`?

In the Pixel example with only two primitive fields, copying by value is enough for the two objects to be independent with respect to that state.

## 2. No Default Copy Constructor Like in C++

If a Java class declares:

~~~java
class Customer {
    private String name;

    Customer(String name) {
        this.name = name;
    }
}
~~~

then Java **does not automatically generate** a `Customer(Customer other)` constructor. Calling `new Customer(oldCustomer)` will not compile, because the existing constructor only accepts `String`.

Java can provide a **default no-argument constructor** in cases where a class declares no constructors at all, but that is **not a copy constructor**. And if the class already declares a constructor, the compiler does not automatically add a no-argument constructor.

Also, do not confuse this with:

~~~java
Customer second = first;
~~~

This is an illustrative statement in a context with two variables of the same type; it **only copies the reference value** and does not create a new Customer. `first == second` will be true if `first` is not null.

### Three Creation Approaches with Different Results

| Expression | Creates a new root object? | Meaning |
| --- | --- | --- |
| `T b = a;` | No | Two references point to the same object |
| `T b = new T(a);` | Yes, when the constructor returns normally | Copy constructor you define yourself |
| `T b = T.copyOf(a);` | Depends on the factory contract | May create a new instance or reuse an immutable instance |
| `T b = a.clone();` | According to the actual `clone` contract | Does not automatically mean deep copy |

Reading only the method name is **not enough**; you must check the documented contract and the implementation.

## 3. Experiment 1 — Reference Assignment Differs from Creating a Copy

Create the file **`CopyConstructorBasicsDemo.java`**:

~~~java
final class PointValue {
    private final int x;
    private final int y;

    PointValue(int x, int y) {
        this.x = x;
        this.y = y;
    }

    PointValue(PointValue source) {
        this(source.x, source.y);
    }

    String describe() {
        return "(" + x + "," + y + ")";
    }

    boolean sameCoordinates(PointValue other) {
        return other != null && x == other.x && y == other.y;
    }
}

public class CopyConstructorBasicsDemo {
    public static void main(String[] args) {
        PointValue first = new PointValue(2, 5);
        PointValue alias = first;
        PointValue copied = new PointValue(first);

        System.out.println("alias identity=" + (first == alias));
        System.out.println("copy identity=" + (first == copied));
        System.out.println("same coordinates="
                + first.sameCoordinates(copied));
        System.out.println("first=" + first.describe());
        System.out.println("copied=" + copied.describe());
    }
}
~~~

Compile and run:

~~~bash
javac -encoding UTF-8 CopyConstructorBasicsDemo.java
java CopyConstructorBasicsDemo
~~~

**Exact stdout:**

~~~text
alias identity=true
copy identity=false
same coordinates=true
first=(2,5)
copied=(2,5)
~~~

`alias` points to the exact `first` object; `copied` is a different object with equal initial values. `sameCoordinates` is a dedicated method expressing **coordinate value equality**, not `Object.equals`.

Even though Pixel and PointValue contain `final` fields, the copy constructor **still freshly initializes the fields of the new object** according to Java constructor rules. `final` prevents reassigning fields of the same object after initialization, not creating another object with the same values.

## 4. Clearer Naming: Named Copy Factory

A **named copy factory** is a static method named according to its purpose that returns an object or value appropriate for copying. For example:

~~~java
final class Snapshot {
    private final String code;

    private Snapshot(String code) {
        this.code = code;
    }

    static Snapshot copyOf(Snapshot source) {
        java.util.Objects.requireNonNull(source, "source");
        return new Snapshot(source.code);
    }

    static Snapshot fromCode(String code) {
        return new Snapshot(
                java.util.Objects.requireNonNull(code, "code"));
    }

    String code() {
        return code;
    }
}
~~~

This is a **complete class without main**. The `copyOf` factory reads state from an existing object and creates a new instance; `fromCode` takes raw data and creates an object via a different path.

The strength of a factory compared to a constructor is that **names can express multiple policies** without having to distinguish everything solely through parameter types:

- `copyOf(T source)`: equivalent value; whether identity is new or reused must be clearly stated.
- `snapshotOf(MutableSource source)`: captures a value snapshot at the time of the call.
- `duplicateAsNew(Entity source, String newId)`: duplicates data for an entity with a **different identity**.
- `deepCopyOf(Graph root)`: intentionally detaches a mutable graph by contract.
- `fromDto(Dto dto)`: converts from an external representation; not necessarily a same-type copy.
- `withStatus(State next)`: creates a version carrying a new state.

There are no **mandatory Java semantics** for these names; libraries and applications must document and enforce them consistently.

## 5. Copy Constructor or Factory? Core Differences

| Criterion | Copy constructor | Named copy factory |
| --- | --- | --- |
| Syntax | `new T(source)` | `T.copyOf(source)` |
| Purpose-descriptive name | Class name only | Can be `snapshotOf`, `duplicateAsNew`, `copyValidated` |
| Target object type | Exact class whose constructor is called | Can return an appropriate implementation per contract |
| New root identity | Yes, if `new` completes normally | Not mandatory; can reuse an immutable instance |
| Initialization rules | Constructor chaining and definite assignment | Arbitrary logic, typically calling a private constructor |
| Use with `final` fields | Convenient because initialized in constructor | Convenient when calling a valid constructor |
| Validation control | Centralized via `this(...)` | Centralized via constructor/private factory |
| Different copy policies | Requires overloading or parameters | Multiple descriptive names, reducing boolean flags |
| Polymorphism | `new Base(source)` does not automatically preserve subclass | Can dispatch the target type, though must be implemented manually |
| `null` input | Depends on constructor | Depends on factory; can be checked explicitly upfront |

**A factory does not automatically deep-copy just because it is named `deepCopyOf`.** Correctness is the result of the algorithm and testing the object graph. Similarly, a copy constructor can also be a shallow copy if it only assigns reference fields.

## 6. Copy Constructors Should Delegate to a Common Validation Path

If a class has multiple constraints, do not duplicate validation blocks in each constructor:

~~~java
final class RetryPolicy {
    private final int maxRetries;
    private final long timeoutMillis;

    RetryPolicy(int maxRetries, long timeoutMillis) {
        if (maxRetries < 0 || maxRetries > 10) {
            throw new IllegalArgumentException("retry ngoài 0..10");
        }
        if (timeoutMillis <= 0) {
            throw new IllegalArgumentException("timeout không dương");
        }
        this.maxRetries = maxRetries;
        this.timeoutMillis = timeoutMillis;
    }

    RetryPolicy(RetryPolicy other) {
        this(
                java.util.Objects.requireNonNull(
                        other, "other").maxRetries,
                other.timeoutMillis);
    }

    String describe() {
        return maxRetries + "/" + timeoutMillis;
    }
}
~~~

This is a **valid class**, without main. The copy constructor calls the primary constructor, where the invariant is defined. `Objects.requireNonNull(other)` is checked while evaluating the first argument of `this(...)`; with `other=null`, evaluation stops with a `NullPointerException` and does not continue reading `other.timeoutMillis`.

In a constructor that calls `this(...)`, that call must follow Java's rules for constructor invocation; you cannot arbitrarily place initialization statements before `this(...)` in Java 17. If validation is complex, use a static helper when evaluating arguments or a factory that accepts the input and then calls a valid constructor.

If a copy constructor **bypasses primary validation** and assigns fields directly, a future invariant change might not be enforced across all copy paths.

## 7. Experiment 2 — Validation Applies to the Copy Constructor as Well

Create the file **`ValidatedCopyDemo.java`**:

~~~java
import java.util.Objects;

final class Limits {
    private final int min;
    private final int max;

    Limits(int min, int max) {
        if (min > max) {
            throw new IllegalArgumentException("min > max");
        }
        this.min = min;
        this.max = max;
    }

    Limits(Limits source) {
        this(
                Objects.requireNonNull(source, "source").min,
                source.max);
    }

    Limits withBounds(int nextMin, int nextMax) {
        return new Limits(nextMin, nextMax);
    }

    @Override
    public String toString() {
        return "[" + min + "," + max + "]";
    }
}

public class ValidatedCopyDemo {
    public static void main(String[] args) {
        Limits original = new Limits(2, 8);
        Limits copy = new Limits(original);
        Limits updated = copy.withBounds(5, 10);

        System.out.println("original=" + original);
        System.out.println("copy=" + copy);
        System.out.println("updated=" + updated);
        System.out.println("different=" + (original != copy));

        try {
            copy.withBounds(9, 3);
        } catch (IllegalArgumentException ex) {
            System.out.println("invalid=" + ex.getMessage());
        }
        System.out.println("copy remains=" + copy);
    }
}
~~~

Compile/run:

~~~bash
javac -encoding UTF-8 ValidatedCopyDemo.java
java ValidatedCopyDemo
~~~

**Stdout:**

~~~text
original=[2,8]
copy=[2,8]
updated=[5,10]
different=true
invalid=min > max
copy remains=[2,8]
~~~

Every new result is created through the constructor that checks `min <= max`. The `withBounds` method does not “modify individual fields of copy”, but rather **constructs another object** via the valid constructor.

The original and copy are initially equal in **illustrated value** yet have different identities; updating to `[5,10]` also does not change copy.

## 8. Shallow Copy: New Root but Old Child Object

Consider the class:

~~~java
class BadNotebook {
    private java.util.ArrayList<String> tags;

    BadNotebook(java.util.ArrayList<String> tags) {
        this.tags = tags;
    }

    BadNotebook(BadNotebook other) {
        this.tags = other.tags;
    }

    void addTag(String tag) {
        tags.add(tag);
    }
}
~~~

This is a **valid class that intentionally has a non-independent copy design**. Although `new BadNotebook(source)` creates another Notebook object, `this.tags = other.tags` only copies the reference, causing both notebooks to point to **the same ArrayList**.

Diagram:

~~~text
BadNotebook original ------+
                           |
                           v
                     ArrayList tags ["java"]
                           ^
                           |
BadNotebook copy ----------+
~~~

If `copy.addTag("oop")` is called, the original also sees `oop`. That operation is called a **shallow copy** on the reference field.

Shallow copy is not always wrong: it can share **immutable** objects or dependencies intentionally shared. It is wrong when a factory/constructor promises **independence of mutable data** yet still retains an alias.

## 9. Experiment 3 — Illustrating Aliasing and Independent List Copying

Create the file **`ShallowAndListCopyDemo.java`**:

~~~java
import java.util.ArrayList;
import java.util.List;

final class LabelBook {
    private final List<String> labels;

    LabelBook(List<String> labels) {
        this.labels = labels;
    }

    LabelBook(LabelBook other) {
        this.labels = other.labels;
    }

    void add(String label) {
        labels.add(label);
    }

    List<String> view() {
        return List.copyOf(labels);
    }

    boolean sharesListWith(LabelBook other) {
        return labels == other.labels;
    }
}

final class SafeLabelBook {
    private final List<String> labels;

    SafeLabelBook(List<String> labels) {
        this.labels = new ArrayList<>(labels);
    }

    SafeLabelBook(SafeLabelBook other) {
        this(other.labels);
    }

    void add(String label) {
        labels.add(label);
    }

    List<String> view() {
        return List.copyOf(labels);
    }

    boolean sharesListWith(SafeLabelBook other) {
        return labels == other.labels;
    }
}

public class ShallowAndListCopyDemo {
    public static void main(String[] args) {
        List<String> supplied = new ArrayList<>();
        supplied.add("java");

        LabelBook original = new LabelBook(supplied);
        LabelBook shallow = new LabelBook(original);
        shallow.add("oop");

        System.out.println("shallow shares="
                + original.sharesListWith(shallow));
        System.out.println("original=" + original.view());
        System.out.println("shallow=" + shallow.view());

        SafeLabelBook safe = new SafeLabelBook(supplied);
        SafeLabelBook copy = new SafeLabelBook(safe);
        copy.add("sql");

        System.out.println("safe shares="
                + safe.sharesListWith(copy));
        System.out.println("safe=" + safe.view());
        System.out.println("copy=" + copy.view());
    }
}
~~~

Commands:

~~~bash
javac -encoding UTF-8 ShallowAndListCopyDemo.java
java ShallowAndListCopyDemo
~~~

**Exact stdout:**

~~~text
shallow shares=true
original=[java, oop]
shallow=[java, oop]
safe shares=false
safe=[java, oop]
copy=[java, oop, sql]
~~~

`SafeLabelBook` creates a new list container upon receiving input, and the copy constructor calls that constructor. Because all elements are immutable `String` values, the two instances are independent with respect to adding/removing tags.

**Note:** `SafeLabelBook` in the example is still **mutable** via `add`. The copy constructor gives instances their own collections, but does not make them immutable. It is necessary to distinguish clearly between **copy isolation** and **immutability**: two related goals that are not the same.

## 10. Copying a List Does Not Mean Copying Elements

If a list holds **mutable elements**, the approaches:

~~~java
new java.util.ArrayList<>(originalLines);
java.util.List.copyOf(originalLines);
~~~

are **illustrative expressions**, assuming the variable `originalLines` has type `List<Line>` and appropriate elements. They create/return a list containing **the same references to the Line objects**; they do not automatically create new Line objects.

Distinguish:

1. **Root copy:** creates a new object holding the list.
2. **Container copy:** creates a new list object.
3. **Element copy:** creates a copy of each mutable Line.
4. **Nested copy:** if Line has mutable child objects, continue determining the boundary that needs to be copied.

A domain-accurate deep copy does not necessarily copy **everything**, but it must isolate all mutable state that the contract promises not to share.

For example, if `Line` only has `String sku` and `int quantity`, copying Line creates a new object and can still share String sku because String is immutable. If `Line` has a mutable `Date` or `List<Discount>`, you must decide how deep to copy.

## 11. Experiment 4 — Copy Constructor for Each Mutable Element

Create the file **`DeepElementCopyDemo.java`**:

~~~java
import java.util.ArrayList;
import java.util.List;
import java.util.Objects;

final class MutableLine {
    private final String sku;
    private int quantity;

    MutableLine(String sku, int quantity) {
        this.sku = Objects.requireNonNull(sku, "sku");
        setQuantity(quantity);
    }

    MutableLine(MutableLine other) {
        this(
                Objects.requireNonNull(other, "other").sku,
                other.quantity);
    }

    void setQuantity(int next) {
        if (next < 0) {
            throw new IllegalArgumentException("quantity âm");
        }
        quantity = next;
    }

    String describe() {
        return sku + ":" + quantity;
    }
}

final class OrderDraft {
    private final List<MutableLine> lines;

    OrderDraft(List<MutableLine> input) {
        Objects.requireNonNull(input, "input");
        List<MutableLine> copied = new ArrayList<>();
        for (MutableLine line : input) {
            copied.add(new MutableLine(line));
        }
        lines = copied;
    }

    OrderDraft(OrderDraft source) {
        this(Objects.requireNonNull(source, "source").lines);
    }

    void changeQuantity(int index, int quantity) {
        lines.get(index).setQuantity(quantity);
    }

    List<String> describe() {
        return lines.stream()
                .map(MutableLine::describe)
                .toList();
    }
}

public class DeepElementCopyDemo {
    public static void main(String[] args) {
        MutableLine supplied = new MutableLine("P1", 2);
        List<MutableLine> input = new ArrayList<>();
        input.add(supplied);

        OrderDraft source = new OrderDraft(input);
        OrderDraft copy = new OrderDraft(source);

        supplied.setQuantity(99);
        copy.changeQuantity(0, 8);

        System.out.println("input=" + supplied.describe());
        System.out.println("source=" + source.describe());
        System.out.println("copy=" + copy.describe());
        System.out.println("same root=" + (source == copy));
    }
}
~~~

Compile/run:

~~~bash
javac -encoding UTF-8 DeepElementCopyDemo.java
java DeepElementCopyDemo
~~~

**Stdout:**

~~~text
input=P1:99
source=[P1:2]
copy=[P1:8]
same root=false
~~~

Here the `OrderDraft` constructor performs an **element copy**, so source does not depend on `supplied` after receiving the input; the copy does not depend on source when modifying quantity.

The `describe()` getter returns immutable `String` values, **without exposing internal MutableLine instances**. Even if the list is newly constructed and elements are copied upon creation, if a getter directly returns an internal `MutableLine`, the caller can still mutate its state and break the ownership policy. Defensive copying may be needed **on both the way in and the way out**.

## 12. A Copy Constructor Protecting Input Does Not Mean Protecting Output

For example, a `Schedule` storing a mutable `Date`:

~~~java
final class Schedule {
    private final java.util.Date when;

    Schedule(java.util.Date when) {
        this.when = new java.util.Date(
                java.util.Objects.requireNonNull(when).getTime());
    }

    Schedule(Schedule other) {
        this(other.when);
    }

    java.util.Date when() {
        return new java.util.Date(when.getTime());
    }
}
~~~

This is a valid class, without `main`. It copies `Date` on input, copies in the copy constructor, and copies before returning from the getter. If creating `new Date(...)` in the getter is omitted, the caller could receive a reference to the internal `Date` and then call `setTime`.

When building immutable value objects, it is easier to choose inherently immutable data types, such as `java.time.Instant`. However, when integrating legacy APIs that use Date or mutable collections, defensive copying is a necessary technique.

## 13. Experiment 5 — Date/Time and Snapshot Factory

Create the file **`TimestampCopyDemo.java`**:

~~~java
import java.util.Date;
import java.util.Objects;

final class TimestampSnapshot {
    private final Date instant;

    TimestampSnapshot(Date input) {
        Date checked = Objects.requireNonNull(input, "input");
        instant = new Date(checked.getTime());
    }

    TimestampSnapshot(TimestampSnapshot other) {
        this(Objects.requireNonNull(other, "other").instant);
    }

    static TimestampSnapshot snapshotOf(Date input) {
        return new TimestampSnapshot(input);
    }

    static TimestampSnapshot copyOf(TimestampSnapshot source) {
        return new TimestampSnapshot(source);
    }

    Date toDate() {
        return new Date(instant.getTime());
    }

    long epochMillis() {
        return instant.getTime();
    }
}

public class TimestampCopyDemo {
    public static void main(String[] args) {
        Date input = new Date(1000L);
        TimestampSnapshot first =
                TimestampSnapshot.snapshotOf(input);
        TimestampSnapshot second =
                TimestampSnapshot.copyOf(first);

        input.setTime(2000L);
        Date extracted = second.toDate();
        extracted.setTime(3000L);

        System.out.println("input=" + input.getTime());
        System.out.println("first=" + first.epochMillis());
        System.out.println("second=" + second.epochMillis());
        System.out.println("extracted=" + extracted.getTime());
        System.out.println("different=" + (first != second));
    }
}
~~~

Commands:

~~~bash
javac -encoding UTF-8 TimestampCopyDemo.java
java TimestampCopyDemo
~~~

**Exact stdout:**

~~~text
input=2000
first=1000
second=1000
extracted=3000
different=true
~~~

`snapshotOf(Date)` clearly expresses “capturing a timestamp value from a mutable source”; `copyOf(TimestampSnapshot)` expresses “creating a copy from an existing snapshot”. Both use the same constructor that guarantees independence.

Using `Instant` instead of `Date` in new designs can allow safer reference sharing, because `Instant` is immutable. For instants in time, do not mistake a `Date` object for being immutable just because the field holding it is marked `final`.

## 14. Named Methods Help Distinguish ID Copying from Duplicating a New Entity

Suppose an application has `DocumentDraft` with:

- `documentId`: draft identifier.
- `title`: title.
- `sections`: list of paragraphs.

Two quite different requirements:

1. **Snapshot of the same draft**: keeps the ID and data for comparison/audit.
2. **Creating a new draft from an old template**: keeps the content but receives a **new ID** provided by the caller or the system.

If both were `new DocumentDraft(old)`, readers would have difficulty telling how the ID is handled. Factories named `copyPreservingId` and `duplicateAsNew` make the difference clear.

Business rules such as unique IDs, permission to create copies, and the “draft” status must be checked at the appropriate layer. **Merely generating a new string ID in RAM does not guarantee system-wide uniqueness**, and does not replace a unique constraint in the database.

## 15. Experiment 6 — `copyPreservingId` and `duplicateAsNew`

Create the file **`NamedCopyPoliciesDemo.java`**:

~~~java
import java.util.ArrayList;
import java.util.List;
import java.util.Objects;

final class DocumentDraft {
    private final String id;
    private final String title;
    private final List<String> sections;

    private DocumentDraft(
            String id, String title, List<String> sections) {
        if (id == null || id.isBlank()) {
            throw new IllegalArgumentException("id rỗng");
        }
        this.id = id;
        this.title = Objects.requireNonNull(title, "title");
        this.sections = List.copyOf(sections);
    }

    static DocumentDraft create(
            String id, String title, List<String> sections) {
        return new DocumentDraft(id, title, sections);
    }

    static DocumentDraft copyPreservingId(
            DocumentDraft source) {
        Objects.requireNonNull(source, "source");
        return new DocumentDraft(
                source.id, source.title, source.sections);
    }

    static DocumentDraft duplicateAsNew(
            DocumentDraft source, String newId) {
        Objects.requireNonNull(source, "source");
        return new DocumentDraft(
                newId, source.title, source.sections);
    }

    DocumentDraft withTitle(String next) {
        return new DocumentDraft(id, next, sections);
    }

    String describe() {
        return id + ":" + title + sections;
    }
}

public class NamedCopyPoliciesDemo {
    public static void main(String[] args) {
        DocumentDraft original = DocumentDraft.create(
                "D1", "Java", List.of("A", "B"));

        DocumentDraft snapshot =
                DocumentDraft.copyPreservingId(original);
        DocumentDraft duplicated =
                DocumentDraft.duplicateAsNew(original, "D2");
        DocumentDraft renamed =
                duplicated.withTitle("Java 17");

        System.out.println("original=" + original.describe());
        System.out.println("snapshot=" + snapshot.describe());
        System.out.println("duplicated=" + duplicated.describe());
        System.out.println("renamed=" + renamed.describe());
        System.out.println("different roots="
                + (original != snapshot));
    }
}
~~~

Run:

~~~bash
javac -encoding UTF-8 NamedCopyPoliciesDemo.java
java NamedCopyPoliciesDemo
~~~

**Stdout:**

~~~text
original=D1:Java[A, B]
snapshot=D1:Java[A, B]
duplicated=D2:Java[A, B]
renamed=D2:Java 17[A, B]
different roots=true
~~~

All versions hold immutable `String` values and an unmodifiable snapshot `List<String>`, so immutable components can be shared without creating a mutable alias. `withTitle` creates a new object with the same ID but a new title.

**Business importance:** Two objects with the same `id=D1` do not mean there are two different documents in the database; `copyPreservingId` is only an **in-memory snapshot value**. In a storage system, a newly created record must follow its own identity policy and transaction.

## 16. `copyOf` on an Immutable Value May Return `this`

In the Java standard library, some `copyOf` factories for immutable collections **do not guarantee always creating an object with a different identity**. For example, `List.copyOf` may reuse an input that is already an appropriate unmodifiable list.

A named copy factory of an immutable value object may also choose this approach:

~~~java
record Coordinates(int x, int y) {
    static Coordinates copyOf(Coordinates source) {
        return java.util.Objects.requireNonNull(source);
    }
}
~~~

This is a valid record. The method named `copyOf` here only requires a **value-equivalent** result; it returns source directly to avoid allocation.

Do not call this contract a **fresh independent identity copy**. If the API promises a new object in terms of `!=`, you should write another explicit factory, such as `freshCopyOf`, and actually construct the object with `new`.

### Selection Rules

- Immutable value: sharing the object can be safe.
- Mutable object: returning the same object when the caller expects a separate copy usually breaks the contract.
- Entity: whether to assign a new identity or keep the ID is a **business decision**.
- Snapshot: shared immutable nodes may be used if all mutation paths are isolated.
- Graph: you must decide whether to preserve internal alias relationships.

## 18. Copy Constructors and Java 17 Records

A record has a canonical constructor that receives **each component**, but Java **does not automatically generate** a copy constructor `RecordType(RecordType other)`. You can write such a constructor yourself:

~~~java

    EmployeeInfo {
        if (name == null || name.isBlank()) {
            throw new IllegalArgumentException("name rỗng");
        }
        if (level < 1) {
            throw new IllegalArgumentException("level sai");
        }
    }

    EmployeeInfo(EmployeeInfo source) {
        this(source.name(), source.level());
    }

    EmployeeInfo withLevel(int nextLevel) {
        return new EmployeeInfo(name, nextLevel);
    }
}
~~~

This is a **valid Java 17 record**, without main. The copy constructor uses `this(source.name(), source.level())`; a null source reference will result in a `NullPointerException` when reading the component if not guarded beforehand.

Record components are held in private final fields, but **mutable components** such as `List` or arrays are **not automatically deep-copied**. Therefore, adding a copy constructor that accepts the record and calls the canonical constructor is not enough if the canonical constructor also keeps a mutable reference directly.

For records containing mutable data, you should place a defensive copy in the **compact canonical constructor**, and protect the accessor if the component remains mutable.

## 20. What Advantages Do `final` Fields Offer for Copy Constructors?

For a class with `final` fields:

~~~java
final class FileInfo {
    private final String path;
    private final long length;

    FileInfo(String path, long length) {
        this.path = java.util.Objects.requireNonNull(path);
        if (length < 0) {
            throw new IllegalArgumentException("length âm");
        }
        this.length = length;
    }

    FileInfo(FileInfo source) {
        this(source.path, source.length);
    }
}
~~~

This is a valid class. The copy constructor **initializes a new object**, so it can assign blank final fields through the constructor chain in compliance with Java rules.

This differs from `Object.clone()`: `super.clone()` typically copies field values **without running normal constructors**; when a `final` field points to a mutable object, you cannot arbitrarily write `copy.finalList = new ArrayList<>(...)` after cloning in normal Java code.

A copy constructor/factory is often more convenient when:

- You want to run validation/normalization.
- There are final reference fields that need to point to **new child objects**.
- You want to allocate IDs or resources according to custom rules.
- You want to distinguish shallow copy, deep copy, and duplicate using API names.
- You do not need to automatically preserve the subclass runtime class.

However, creating via a constructor does not **automatically deep-copy**: you still need copying code for mutable data.

## 21. Comparison with `Object.clone()` and `Cloneable`

| Aspect | Copy constructor/factory | `Object.clone()` |
| --- | --- | --- |
| Requires `implements Cloneable`? | No | Usually yes if relying on `super.clone()` |
| Runs constructor to create object? | Yes, with `new T(...)` | Does not run the normal constructor of the cloned object |
| Copying rules | Written by constructor/factory | `super.clone()` basically shallow-copies fields |
| Handling mutable references | Requires design | Requires design |
| `final` fields | Conveniently initialized in constructor | Difficult to replace a final reference after shallow clone |
| Exception | According to defined validation/operation | `CloneNotSupportedException` under the base mechanism |
| Preserves runtime subclass | Not automatic | `super.clone()` creates an object of the same runtime class |
| Clear API naming | Named according to policy | Method is usually simply named `clone` |
| Polymorphic copying | Requires a separate virtual copy contract if desired | Has the clone mechanism, though the hierarchy contract must be checked |

**Cloneable is a marker interface**; it does not declare `clone()`. `Object.clone()` has `protected` access; simply writing `implements Cloneable` does not automatically give external callers a public `clone()` method.

For domain models that require validation and control, a copy constructor/factory often **expresses the contract more clearly**. That does not mean never using `clone()`: many APIs have their own documented clone methods suited to specific needs.

## 22. Inheritance: A Superclass Copy Constructor Can “Slice” Subclass Data

Given:

~~~java
class Document {
    final String title;

    Document(String title) {
        this.title = title;
    }

    Document(Document source) {
        this(source.title);
    }
}

class PdfDocument extends Document {
    final int pages;

    PdfDocument(String title, int pages) {
        super(title);
        this.pages = pages;
    }
}
~~~

These are valid illustrative classes, without main. If `Document source = new PdfDocument("Guide", 12)`, calling `new Document(source)` creates **an exact Document**, not a PdfDocument, because Java already knows which class constructor is being called.

PdfDocument's own `pages` data **has nowhere to be stored** in the new Document. This phenomenon is sometimes called **model-level object slicing**, similar to the term in other languages; in Java, the object was never “sliced in memory”, rather we **actively created a new Base object missing the subclass state**.

### A Subclass Copy Constructor Needs to Copy Its Own State

~~~java
class CopyableDocument extends Document {
    final int version;

    CopyableDocument(String title, int version) {
        super(title);
        this.version = version;
    }

    CopyableDocument(CopyableDocument other) {
        super(other);
        this.version = other.version;
    }
}
~~~

This is a valid illustrative class when placed alongside the Document classes above. `super(other)` calls the superclass copy constructor; the subclass then initializes its own `version` field.

If the subclass has a mutable field, it must be copied according to ownership, not merely `this.mutable = other.mutable`.

## 24. Polymorphic Copying via an Overridden `copy()` Method

A hierarchy can define a virtual copy contract:

~~~java
abstract class Message {
    abstract Message copy();
}

final class Email extends Message {
    private final String subject;

    Email(String subject) {
        this.subject = subject;
    }

    Email(Email source) {
        this(source.subject);
    }

    @Override
    Email copy() {
        return new Email(this);
    }
}
~~~

This is valid illustrative code (without main). When `Message message = new Email("Hello")` and then `message.copy()` is called, **runtime dispatch** selects `Email.copy()`; the result has runtime class Email.

The difference from a copy constructor: a virtual `copy()` can preserve the **dynamic type** if each subclass implements it properly. However, all subclasses must be tested, especially if they contain mutable fields or custom business logic.

**Covariant return** allows `Email.copy()` to return type `Email` instead of `Message` when overriding appropriately. That spares code using the concrete subtype from unnecessary casts.

## 26. `copyOf` Can Accept an Interface Instead of a Concrete Class

A named copy factory can create a snapshot from data without depending on a concrete implementation. For example:

    int failed();

## 28. Copying Cyclic Graphs: A Single-Step Constructor Is Often Insufficient

Given an object graph:

~~~text
Node A ----> Node B
   ^           |
   +-----------+

Node C ----> Shared Node
Node D ----> Shared Node
~~~

If each `Node(Node source)` calls `new Node(child)` for every child, the cycle A↔B will cause infinite recursive copying. And if there are two paths to **the same child object**, creating a different copy each time it is encountered will lose the shared structure.

The general solution is to **memoize original object → copied object** in a map by **reference identity**:

~~~text
copy(source, map):
    if source == null: return null
    if source is already in map: return existing copy
    create Node copy with basic data
    record map[source] = copy IMMEDIATELY
    copy child links through the same map
    return copy
~~~

Why record it in the map before recursing? Because when encountering an edge back to source, the algorithm must find the copy currently being built instead of infinitely creating new ones.

A **named factory** `GraphCopies.deepCopyOf(root)` is very well suited here because it can manage the memo map and the scope of the entire graph, instead of forcing each public copy constructor to handle cycles independently.

## 29. Experiment 12 — `deepCopyOf` Preserving Cycles and Sharing

Create the file **`NamedGraphCopyDemo.java`**:

~~~java
import java.util.ArrayList;
import java.util.IdentityHashMap;
import java.util.List;
import java.util.Map;

final class GraphNode {
    private final String name;
    private final List<GraphNode> links = new ArrayList<>();

    GraphNode(String name) {
        this.name = name;
    }

    void connect(GraphNode other) {
        links.add(other);
    }

    GraphNode link(int index) {
        return links.get(index);
    }

    String name() {
        return name;
    }

    List<GraphNode> links() {
        return List.copyOf(links);
    }
}

final class GraphCopies {
    private GraphCopies() {
    }

    static GraphNode deepCopyOf(GraphNode root) {
        return copy(root, new IdentityHashMap<>());
    }

    private static GraphNode copy(
            GraphNode source, Map<GraphNode, GraphNode> memo) {
        if (source == null) {
            return null;
        }

        GraphNode existing = memo.get(source);
        if (existing != null) {
            return existing;
        }

        GraphNode result = new GraphNode(source.name());
        memo.put(source, result);
        for (GraphNode next : source.links()) {
            result.connect(copy(next, memo));
        }
        return result;
    }
}

public class NamedGraphCopyDemo {
    public static void main(String[] args) {
        GraphNode a = new GraphNode("A");
        GraphNode b = new GraphNode("B");

        a.connect(b);
        a.connect(b);
        b.connect(a);

        GraphNode copiedA = GraphCopies.deepCopyOf(a);
        GraphNode copiedB = copiedA.link(0);

        System.out.println("new root=" + (copiedA != a));
        System.out.println("new child=" + (copiedB != b));
        System.out.println("shared link="
                + (copiedA.link(0) == copiedA.link(1)));
        System.out.println("cycle="
                + (copiedB.link(0) == copiedA));
        System.out.println("original cycle="
                + (b.link(0) == a));
    }
}
~~~

~~~

**Exact stdout:**

~~~text

new child=true
shared link=true

~~~

This is a deep copy over **the GraphNodes and links owned by the graph**. `String name` is safely shared because it is immutable. `IdentityHashMap` avoids confusing two different Nodes that have the same name or are `equals`.

## 30. Choosing the Deep Copy Boundary Instead of Trying to Clone the Whole World

An object may hold:

- Domain data: `List<Line>`, `Address`, `Configuration`.
- Immutable value: `String`, `Instant`, a record containing simple values.
- External dependency: `Logger`, `Repository`, `DataSource`.
- Live resource: `Socket`, `InputStream`, file handle, thread, lock.
- Entity reference: an ID or an object representing the same database row.

You cannot mechanically apply “copy all references” to all of these categories. A copy of a domain document **should not** open a new database connection just because the document has a repository field. A data snapshot typically **copies only the state owned by the snapshot**, while external dependencies do not participate in the snapshot or are managed separately.

Draw the object graph and classify each edge:

| Reference edge | Reasonable policy |
| --- | --- |
| Root → immutable String | Safe to share |
| Root → privately owned mutable ArrayList | Copy container |
| Root → privately owned mutable Line | Copy element |
| Root → shared immutable configuration | Can be shared |
| Root → socket/connection | Do not deep-copy as data |
| Root → child needing preserved back-reference | Graph-aware copy with memo map |
| Root → database entity outside aggregate | May keep only the ID or apply a separate policy |

**Deep copy has a business-scoped meaning**, not “the JVM has an algorithm to copy every kind of object”.

## 31. `equals`, `hashCode`, and Identity After Copying

A copy constructor **guarantees a new object** when `new` completes normally, so `copy != source` by reference. However, `copy.equals(source)` depends on the class:

- For a class that does not override `Object.equals`, two distinct objects are normally `equals` false (comparing identity).
- For an immutable value object that overrides `equals/hashCode` by state, the copy can be **equals true** even though `== false`.
- For entity equality by business ID, a copy preserving the ID may be considered equal to the old entity; duplicateAsNew, which changes the ID, is normally not equal to the old one under that contract.
- `hashCode` is **not** a unique identifier of an instance; two objects can share the same hash even when they are not equal.

If a `copyOf` factory is allowed to return the same immutable object, `copy == source` may be true. Do not write tests assuming `!=` by default if the contract does not state a fresh identity.

Do not override `equals/hashCode` using mutable fields and then use the objects as keys of a `HashMap` while those fields change; a copy constructor does not automatically solve the risk of a key whose hash mutates.

## 32. Exceptions During Copying: Keeping the Source Intact

A safe copy API should strive to:

1. **Not mutate the source object** during the copying process.
2. Validate against a null source and check business constraints.
3. Prepare the new data before publishing the result.
4. If an error occurs, do not return a partially constructed object through the API.
5. Do not delete or release the source's resources unless the contract explicitly specifies a **move/transfer ownership** rather than a copy.

The distinction between **copy** and **move** is very important. In C++, move constructors exist; in Java Core there is no equivalent language-generated move constructor. A factory named `takeOwnershipOf` can be designed to transfer ownership, yet **it should not be called a copy** if afterward the caller is no longer allowed to modify the source or the source becomes invalidated.

With a mutable source modified by another thread during copying, merely not mutating the source from the copy method **does not yet guarantee a consistent snapshot**. The concurrency aspect requires its own mechanism.

## 34. Concurrency: A Copy Constructor Does Not Automatically Create an Atomic Snapshot

        return success;
    }

    int failure() {
        return failure;
    }
}
~~~

This is a valid illustrative class. If one thread is calling `update()` and another thread does:

~~~java
MetricsSnapshot snap =
        new MetricsSnapshot(source.success(), source.failure());
~~~

this is an **illustrative call** in a context with an appropriate `source` and `MetricsSnapshot`; the copying thread may read one count before and the other count after the change, causing the snapshot not to correspond to a consistent point in time.

Options depend on the requirements:

- Use a **shared lock** for updating the source and creating the snapshot.
- Provide a `snapshot()` method on the source with appropriate synchronization.
- Manage the state as an immutable aggregate and then perform **atomic publication** of the entire reference.
- Use versioning/retry with consistency checks if the algorithm genuinely guarantees it.
- For persistent data, use appropriate transaction isolation.

**A copy constructor by itself is not a synchronization primitive.** `final` fields on the result provide certain initialization safety guarantees if the object is constructed properly, but do not resolve races when **reading a mutable source**.

## 35. Persistence and Entity Identity: Copying Is Not an Automatic INSERT

In an ORM/database, an entity object may contain:

- An ID tied to the database record.
- A version for optimistic locking.
- Collections/lazy proxies attached to the persistence context.
- Saved/unsaved state, audit metadata, and relationships with other entities.

If you copy fields as-is and call repository.save, you cannot assume the system will always create a new record: behavior depends on the ORM, mapping, ID state, and repository. Errors can include duplicate keys, accidentally updating the old record, or copying relationships that should not be copied.

Therefore, you should distinguish:

**Snapshot:** records the current logical state and may keep the ID to identify the source; typically uses an immutable DTO/record.

**Duplicate as new:** creates a different domain entity, determines a new ID, resets fields such as status/version if required by business rules, and selects which associations are allowed to be copied.

**Copy for editing:** creates a separate draft for editing, while requiring a defined way to merge/commit back to the original entity and handle conflicts.

**Cloning the whole entity:** easily causes semantic and lifecycle confusion if the API is not explicit. `Object.clone()` should not be treated as a way to create a new database record.

## 36. How Do Copy Constructors and Named Factories Affect Inheritance?

A constructor:

~~~java
new Base(source)
~~~

always calls `Base`'s constructor; it does **not** perform virtual dispatch on the runtime subtype of source. In an open hierarchy, that causes the copy to lose subclass state.

A factory:

~~~java
Base copyOf(Base source)
~~~

**can** contain logic to select the subclass using `instanceof` or delegate via `source.copy()`, but Java **does not automatically add** that branching. A factory is just a method you write; if the factory always does `return new Base(source)`, it has the same limitation.

If the set of subtypes is finite, a sealed hierarchy and a factory can handle every case explicitly. If the hierarchy is open, a virtual `copy()` overridden in each subclass may be more suitable; at the same time, you must ensure subclasses uphold the copy contract when adding mutable state.

Not every application necessarily needs polymorphic copying. Sometimes converting to a concrete **DTO value** is simpler and safer than copying an entire object hierarchy.

## 37. Copy-on-Write and Immutable Collections

An immutable object can hold a `List<String>` captured via `List.copyOf`:

~~~java
record Notebook(List<String> pages) {
    Notebook {
        pages = List.copyOf(pages);
    }

    Notebook withPage(String page) {
        var list = new java.util.ArrayList<>(pages);
        list.add(java.util.Objects.requireNonNull(page));
        return new Notebook(list);
    }
}
~~~

This is a valid Java 17 record. `withPage` creates a **new candidate list**, then creates a new Notebook without modifying the old Notebook.

This is **application-level copy-on-write**. It differs from `java.util.concurrent.CopyOnWriteArrayList`: that collection supports concurrent mutating operations by copying its backing array according to its policy, and does **not** automatically guarantee that a domain object holding a collection is immutable.

With many updates on a large list, each copy can cost O(n) and allocate many objects. If performance becomes an issue, use a mutable builder within a closed scope and then create a snapshot, or consider persistent data structures. Optimization should be based on profiling, not using an incorrect shallow copy for speed.

## 38. Java Generics Trap: Two Copy Constructors Differing Only in Type Argument

Java uses **type erasure** for many generic types. Suppose a class attempts to declare:

~~~java
// Illustration INTENTIONALLY DOES NOT COMPILE:
class Catalog {
    Catalog(java.util.List<String> codes) {
    }

    Catalog(java.util.List<Integer> ids) {
    }
}
~~~

The two constructors `Catalog(List<String>)` and `Catalog(List<Integer>)` have the same erasure to `List`, thus creating a **name clash** under Java's overloading rules. They cannot be distinguished solely by their generic type arguments.

Named factories clearly express the two input sources:

~~~java
final class SafeCatalog {
    private final java.util.List<String> codes;

    private SafeCatalog(java.util.List<String> codes) {
        this.codes = java.util.List.copyOf(codes);
    }

    static SafeCatalog fromCodes(
            java.util.List<String> codes) {
        return new SafeCatalog(codes);
    }

    static SafeCatalog fromNumericIds(
            java.util.List<Integer> ids) {
        java.util.List<String> codes = ids.stream()
                .map(String::valueOf)
                .toList();
        return new SafeCatalog(codes);
    }
}
~~~

This is a valid class because the factories have **different names**. Both can accept `List<...>` after erasure, yet their method names differ so there is no clash.

Also avoid using a `boolean isNumeric` flag solely to distinguish conversion policies when two separate factory names are easier to understand.

## 39. Testing a Copy Contract

Tests should reflect the **actual promise** of each API, rather than applying the same criteria to every type of copy.

| Contract | Key test check |
| --- | --- |
| Fresh root object | `copy != source` |
| Value equivalence | Logical fields match; `equals` may be used if consistent with the contract |
| Immutable reuse allowed | Do not assume `copy != source` by default |
| Mutable list isolation | Modifying the copy's list does not affect the source's list |
| Mutable element isolation | Modifying an element in the copy does not affect the source's element |
| Defensive input | Modifying constructor input afterward does not affect internal state |
| Defensive output | Caller cannot mutate internal state via getter |
| Business ID policy | `copyPreservingId` keeps the ID; `duplicateAsNew` uses a new ID |
| Constructor validation | Copying and creation both enforce invariants |
| Polymorphic copy | Copy preserves the exact runtime subtype if promised by the contract |
| Cyclic graph | No infinite recursion; sharing/cycles are preserved properly |
| Exception safety | Source remains unchanged after a failed copy |
| Resource policy | Do not accidentally copy live connections/locks |
| Concurrency snapshot | Source and copy have appropriate consistency protection mechanisms |

In particular, **test mutation isolation in both directions**: mutate the copy and check the source, then mutate the source and check the copy. Comparing contents only right after the constructor does not catch mutable aliases.

If the copy constructor handles `Date`, test both the copy constructor and the getter returning Date; if using a list with mutable elements, test each element. If the class is open for inheritance, you must test a subclass that adds a mutable field.

## 40. Common Pitfalls and How to Fix Them

| Mistake | Consequence | How to fix? |
| --- | --- | --- |
| Thinking `T second=first` is a copy | Two variables point to the same object | Call a real constructor/factory if needed |
| Thinking Java auto-generates `T(T)` | Compile-time error | Declare a copy constructor yourself |
| Copy constructor assigns the same mutable list | Two roots share mutable state | Defensively copy the container |
| Copying only the list without copying mutable elements | Element mutations still leak to source | Copy elements or use immutable elements |
| Copying only on input while getter returns mutable object | Caller mutates internal state | Defensive output/projection |
| Copy constructor does not share validation | Easy to produce objects violating invariants | Call `this(...)`/validated factory |
| Using one factory named `copyOf` for two ID policies | Caller cannot tell if creating a snapshot or new entity | Split names into `copyPreservingId`/`duplicateAsNew` |
| Assuming `copyOf` is always fresh | Wrong `==` check with immutable reuse | Read contract, separate `freshCopyOf` |
| Copying Base root and expecting subtype preserved | Loses subclass state | Subclass copy constructor/virtual copy |
| Using `super.clone()` expecting constructor to run | Validation/ID initializer does not run | Choose copy constructor when constructor logic is needed |
| Having `final List` and thinking data is frozen | Target list can still mutate | Immutable snapshot/deep copy |
| Deep-copying a graph without a memo map | Infinite loop or lost sharing | Original→copy identity map |
| Copying `Socket`/`Repository` like a value | Wrong lifecycle/resource semantics | Copy only data according to ownership |
| Two constructors differing only in `List<T>` | Name clash after erasure | Named factories with distinct names |
| Assuming copy is an atomic snapshot | Concurrent source mutation can interleave | Snapshot under lock/versioning |
| Cloning an entity with the same ID then inserting | Duplicate key/accidental update | Clear ID policy, mapping, and transaction |
| Using hashCode as a copy identifier | Can collide/not durable | Business ID with its own contract |
| Not testing mutation after copying | Aliasing bugs go undetected | Before–after and bidirectional tests |

## 41. Process for Designing an Easy-to-Use Copying API

**Step 1 — define the result.** Is this a fresh object, an equivalent immutable value, a snapshot, or a new duplicate entity? Must it preserve the runtime subtype?

**Step 2 — determine ownership.** Map references from the root to mutable collections, elements, dependencies, and resources. Decide which edges must be copied.

**Step 3 — identify invariants.** Centralize validation in a shared constructor or factory; ensure no copy path bypasses checks.

**Step 4 — choose the API form.** Few policies and fixed target type: `new T(source)`. Multiple policies or type conversions: `copyOf`/`snapshotOf`/`duplicateAsNew`.

**Step 5 — handle child data.** Immutable components may be shared. For privately owned mutable components, copy the container/element/graph with the right scope.

**Step 6 — protect output.** Do not return internal mutable references through getters if the contract requires isolation.

**Step 7 — consider inheritance.** A Base copy constructor does not automatically preserve subtypes; if needed, define a polymorphic copy.

**Step 8 — write tests.** Verify identity, values, mutations, failures, cycles, subclass state, and ID policy.

**Step 9 — consider concurrency and persistence.** If the snapshot must be consistent, protect source reads; if the duplicate is a real entity, verify transactions, unique IDs, and relationships.

**Step 10 — document.** Explicitly state whether `this` may be returned, how deep the copy goes, whether external dependencies are retained, and what exceptions may occur.

## 43. Summary of Key Takeaways

- A **copy constructor** is a developer-written constructor of the form `T(T source)` that creates a new root object when `new` succeeds. Java does not generate it automatically.
- A **named copy factory** is a developer-written static method; names such as `copyOf`, `snapshotOf`, and `duplicateAsNew` help distinguish intent.
- **Deep vs. shallow copying** is not determined by the constructor/factory name, but by **which references are actually copied**.
- For mutable fields, you must consider copying the container, copying elements, and getters not exposing the representation; for immutable values, sharing is usually safe.
- Copy constructors/factories are convenient for validation and `final` fields because they use normal constructors.
- `new Base(source)` is **not automatically polymorphic**: preserving the runtime subtype requires a dedicated API/design.
- An immutable `copyOf` factory **may return the same object** if a new identity is not part of the contract.
- If a graph has cycles or shared nodes, use identity-based memoization to preserve the structure.
- Copying domain data does not mean copying resources, creating a new database record, or producing an atomic snapshot under concurrent mutation.
