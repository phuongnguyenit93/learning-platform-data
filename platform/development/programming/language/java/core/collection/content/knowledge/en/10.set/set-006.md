# Order-Independent equals and hashCode of Set

## 1. The value of a set lies in its elements, not its iteration order

Suppose two people choose the same three tags `"java"`, `"sql"`, and `"http"`. The first person chooses them in that order, while the second person chooses `"http"` first and then the remaining two tags. If the problem only cares about the chosen tags, both selections represent the same set value.

That is the meaning of equality on `Set`: **two sets with the same elements are equal, regardless of insertion order or iteration order**, provided that the sets and elements adhere to the standard equality contract.

For example, the mathematical notation `{1, 2, 3}` and `{3, 2, 1}` denote two equal sets. However, the two lists `[1, 2, 3]` and `[3, 2, 1]` are different sequences because position is significant for lists.

This does not mean every `Set` iterates in a random order:

- `LinkedHashSet` can preserve insertion order.
- `TreeSet` iterates in sorted order.
- `HashSet` makes no guarantees about iteration order.

These ordering characteristics are described in [LinkedHashSet](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/LinkedHashSet.html) and [HashSet](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/HashSet.html).

**Iteration rules** and **set equality rules** answer two different questions. A set can have a stable iteration order while `equals` still ignores that order.

To work properly with sets, you need to connect three layers of reasoning:

1. Element `equals` defines what it means to have the same value.
2. `Set`'s `equals` determines whether two sets have the same values.
3. `Set`'s `hashCode` must be consistent with that equality.

If the second layer ignores order but the third layer mixes hash codes by position, two equal sets could produce different hash codes. Therefore, the `Set` contract specifies an order-independent hash code formula. [Set.equals and Set.hashCode Contract](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/Set.html)

## 2. Conditions for two Sets to be equal

### 2.1. Same abstract Set type, same size, same elements

For a non-`null` set `a`, the meaning of `a.equals(b)` is:

1. `b` must also be a `Set`.
2. Both sets must have the same number of elements.
3. Every element of one set must be present in the other set.

There is no requirement that they "must have the same implementation class", nor is there a requirement that "the first element of this set equals the first element of the other set".

With ordinary integer elements, the following table illustrates the differences:

| a | b | a.equals(b) | Reason |
| --- | --- | --- | --- |
| Set `{1, 2, 3}` | Set `{3, 1, 2}` | `true` | Same elements |
| Set `{1, 2, 3}` | Set `{1, 2}` | `false` | Different number of elements |
| Set `{1, 2, 3}` | Set `{1, 2, 4}` | `false` | Same size but different contents |
| Set `{1, 2, 3}` | List `[1, 2, 3]` | `false` | Right-hand object is not a Set |
| Empty set | Another empty Set | `true` | Both have no elements |
| Empty set | `null` | `false` | null is not an empty set |

The curly braces in the table describe set contents in a mathematical sense; that is not Java syntax for creating a set.

`AbstractSet` provides the base implementation for this comparison: recognizing the same reference, checking that the object is a set with matching size, and then using containment checks for the elements. This is a sound mechanism for sets with consistent element identity rules; it is not a positional pair-by-pair comparison of two iterators. [AbstractSet.equals](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/AbstractSet.html#equals(java.lang.Object))

### 2.2. Same reference and same value are two different concepts

```java
// Illustrative snippet; imports are included in the full program below.
Set<Integer> first = new LinkedHashSet<>(List.of(1, 2, 3));
Set<Integer> second = new LinkedHashSet<>(List.of(3, 2, 1));

System.out.println(first == second);      // false
System.out.println(first.equals(second)); // true
```

Here, `==` asks whether the two variables hold the same reference to a single object. Two `new` calls create two distinct set objects, so the result is `false`.

`equals` asks about the set value. Two separate objects can still be equal because both contain `1`, `2`, and `3`.

Do not use `==` to check whether two query results have the same set contents. Conversely, when you want to know whether two variables are sharing the exact same mutable set, `==` is a different question and can have diagnostic value.

### 2.3. Different implementations can still be equal

A `HashSet<Integer>`, a `LinkedHashSet<Integer>`, a `TreeSet<Integer>` using natural ordering, and a set created with `Set.of(...)` can all be equal if they contain the corresponding integers.

Mutability, storage representation, and iteration order are not part of this equality check. They remain important differences when using sets, but they do not make two sets with the same elements have different values.

This is why you should not check `getClass()` before comparing ordinary sets. A condition such as `a.getClass() == b.getClass()` can reject two sets that are equal under the `Set` contract.

The declared type of a variable also does not change the underlying object. If a `HashSet` object is referenced through a variable of type `Collection` or `Object`, calling `equals` still invokes the actual object's implementation.

### 2.4. One-way containsAll is not enough

Suppose `large = {1, 2, 3}` and `small = {1, 2}`:

```java
// Illustrative snippet.
Set<Integer> large = Set.of(1, 2, 3);
Set<Integer> small = Set.of(1, 2);

large.containsAll(small); // true
large.equals(small);      // false
```

`containsAll` here only proves that `small` is a subset of `large`. It does not rule out that `large` contains other elements.

When you need to ask whether two `Set` instances are equal, use `equals` directly. Do not replace it with a one-way `containsAll`, and do not manually write two containment passes if the data already consists of contract-compliant `Set` instances.

## 3. Why is Set's hashCode the sum of element hash codes?

### 3.1. Formula for the whole set

The hash code of a `Set` is defined as the sum of the hash codes of its elements; the contribution of a `null` element is `0`.

You can visualize the formula as:

```text
hash(Set) = sum of hash(element) for every element in the set

If element is null:
    contribution of element = 0
```

The following code only illustrates the calculation according to the contract; it is not a requirement to write a helper function instead of calling `Set.hashCode()`:

```java
static int sumElementHashes(Set<?> values) {
    int result = 0;
    for (Object value : values) {
        result += value == null ? 0 : value.hashCode();
    }
    return result;
}
```

In code that uses sets, the normal way to call it is still:

```java
int hash = values.hashCode();
```

For `Integer`, the hash code is the integer value it represents. Therefore:

```text
hash({1, 2, 3}) = 1 + 2 + 3 = 6
hash({3, 2, 1}) = 3 + 2 + 1 = 6
```

Changing the order of the addends does not change the sum. That is the mechanism that makes the formula compatible with order-independent set equality. [Set.hashCode](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/Set.html#hashCode()), [Integer.hashCode](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/lang/Integer.html#hashCode())

### 3.2. Do not include element position in Set's formula

A formula like `result = 31 * result + elementHash` mixes the previous result with the next element. It can depend on order, so it is not the contract formula for `Set`.

Sorting a set and then hashing its string representation is also not a replacement for `Set.hashCode()`. A display string is meant for humans; it can be affected by formatting, element representation, and output order. Set hash codes already have their own rule.

If you are writing a class with a `Set` field, use that field's `equals` and `hashCode` in the set sense. If you are implementing `Set` yourself, you must uphold the `Set` contract; do not choose an order-based formula just because your class's iterator is ordered.

### 3.3. equals true requires the same hashCode; same hashCode is not enough

The general contract requires:

```text
a.equals(b) == true
    ⇒ a.hashCode() == b.hashCode()
```

The converse is not guaranteed:

```text
a.hashCode() == b.hashCode()
    ⇏ a.equals(b) == true
```

A completely valid example:

```text
A = {1, 4}       hash(A) = 5
B = {2, 3}       hash(B) = 5

A.equals(B) = false
```

These two sets have the same size and the same hash code sum, but different elements. This is a **hash collision**. A hash-based structure must distinguish unequal keys even when they share the same hash code; a hash code must not be treated as a unique identity. [Object.hashCode: relationship with equals](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/lang/Object.html#hashCode())

Therefore, the following comparison is wrong:

```java
// Wrong if used to conclude that two sets are equal:
boolean same = first.hashCode() == second.hashCode();
```

If you need to compare set values, write `first.equals(second)`. Hash codes help hash-based structures organize and locate data; they do not replace equality.

### 3.4. A hash code of 0 does not mean an empty set

An empty set has an empty sum, so its hash code is `0`. However, a set containing only `null` also has a hash code of `0`.

These two sets are still different:

- The empty set has size `0`.
- The set containing `null` has size `1`.
- One set has the element `null`; the other does not.

Similarly, `{0}` or `{-1, 1}` can also have a hash code sum of `0`. Use `isEmpty()` to ask whether a set is empty, not the hash code.

Not every `Set` allows `null`. The examples in this article use `HashSet` when demonstrating a set containing `null`; do not use `Set.of(null)`.

## 4. Full program: separating iteration order from equality

Save the code to **SetEqualityDemo.java**:

```java
import java.util.HashSet;
import java.util.LinkedHashSet;
import java.util.List;
import java.util.Set;
import java.util.TreeSet;

public class SetEqualityDemo {
    public static void main(String[] args) {
        Set<Integer> forward =
                new LinkedHashSet<>(List.of(1, 2, 3));
        Set<Integer> reverse =
                new LinkedHashSet<>(List.of(3, 2, 1));

        System.out.println("forward iteration: " + forward);
        System.out.println("reverse iteration: " + reverse);
        System.out.println("same reference: " + (forward == reverse));
        System.out.println("forward.equals(reverse): " + forward.equals(reverse));
        System.out.println("reverse.equals(forward): " + reverse.equals(forward));
        System.out.println("forward hash: " + forward.hashCode());
        System.out.println("reverse hash: " + reverse.hashCode());

        Set<Integer> hashed = new HashSet<>(List.of(3, 1, 2));
        Set<Integer> sorted = new TreeSet<>(List.of(2, 3, 1));
        Set<Integer> fixed = Set.of(2, 1, 3);
        System.out.println("HashSet equals forward: " + hashed.equals(forward));
        System.out.println("TreeSet equals forward: " + sorted.equals(forward));
        System.out.println("unmodifiable equals forward: " + fixed.equals(forward));

        List<Integer> list = List.of(1, 2, 3);
        System.out.println("set equals list: " + forward.equals(list));
        System.out.println("list equals set: " + list.equals(forward));
        System.out.println("reversed lists equal: "
                + list.equals(List.of(3, 2, 1)));

        Set<Integer> subset = Set.of(1, 2);
        System.out.println("contains subset: " + forward.containsAll(subset));
        System.out.println("equals subset: " + forward.equals(subset));

        Set<Integer> left = Set.of(1, 4);
        Set<Integer> right = Set.of(2, 3);
        System.out.println("left hash: " + left.hashCode());
        System.out.println("right hash: " + right.hashCode());
        System.out.println("collision sets equal: " + left.equals(right));

        Set<Integer> empty = new HashSet<>();
        Set<Integer> onlyNull = new HashSet<>();
        onlyNull.add(null);
        System.out.println("empty hash: " + empty.hashCode());
        System.out.println("null-only hash: " + onlyNull.hashCode());
        System.out.println("empty equals null-only: " + empty.equals(onlyNull));

        Set<Integer> integers = Set.of(1);
        Set<Long> longs = Set.of(1L);
        System.out.println("Integer set equals Long set: " + integers.equals(longs));
        System.out.println("numeric hashes equal: "
                + (integers.hashCode() == longs.hashCode()));
    }
}
```

```shell

java SetEqualityDemo
```

Stdout:

```text

reverse iteration: [3, 2, 1]
same reference: false
forward.equals(reverse): true
reverse.equals(forward): true
forward hash: 6
reverse hash: 6
HashSet equals forward: true
TreeSet equals forward: true
unmodifiable equals forward: true
set equals list: false
list equals set: false
reversed lists equal: false
contains subset: true
equals subset: false

```

The program intentionally prints the contents of only the first two `LinkedHashSet` instances, because their insertion order clearly shows two different sequences. Sets without a guaranteed iteration order are only used in equality comparisons or hash code calls; stdout does not depend on whatever order they happen to print on a given JVM.

Key takeaways from the output:

1. The first two lines differ, yet `equals` in both directions is `true`.
2. Same reference is `false`; same set value is still `true`.
3. Both hash codes are `6`, which is the exact sum `1 + 2 + 3`.
4. Different implementation classes, mutable or unmodifiable, do not prevent sets from being equal when their contents match.
5. A `Set` does not equal a `List`, even when both show the same three numbers in the same order.
6. Containing a subset is not enough for two sets to be equal.
7. Two different sets can share the same hash code `5`.
8. An empty set and a set containing only `null` both have hash code `0`, but they are not equal.
9. A `Set<Integer>` containing `1` does not equal a `Set<Long>` containing `1L`, even though their hash codes happen to match in this example.

## 5. Ignoring order does not mean ignoring element meaning

### 5.1. Set uses the element's equality rules

Two string sets `{"Java"}` and `{"java"}` are normally not equal, because `String.equals` is case-sensitive.

Two separate objects with the same data are also not guaranteed to be equal. If a class only uses the inherited `Object.equals`, element equality is still based on reference identity. Putting objects into a `Set` does not automatically create an "equal by all fields" rule.

For example, for a `Tag` class that has not defined equality by name, two `new Tag("java")` instances can be two different values to a set. If you want two tags with the same name to represent the same value, you must design `Tag`'s `equals` and `hashCode` consistently.

The underlying element rule must satisfy reflexivity, symmetry, transitivity, and consistency as long as the relevant data does not change. If elements violate these properties, you cannot expect the set to fix the meaning of equality on its own. [Object.equals](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/lang/Object.html#equals(java.lang.Object))

### 5.2. Generic types do not perform numeric conversion during comparison

`Integer.valueOf(1)` and `Long.valueOf(1L)` are not equal under `equals`. Therefore, two sets containing only those two values are not equal either.

Conversely, a `Set<Number>` containing an `Integer` object with value `1` can equal a `Set<Integer>` containing the same `Integer` value. Equality inspects the actual elements, not whether the generic type arguments written on the two variables are identical.

What you need to check is the type and equality rules of the stored values, not just that both sides "are numbers".

### 5.3. Set does not store occurrence counts

If you build a set from a list with duplicate elements, equal elements are collapsed into a single set value. Once that happens, equality between two sets cannot recover the discarded occurrence counts.

Example:

```text
First input:  [java, java, sql]
Second input: [java, sql, sql]

After converting each input into a set:
    both have contents {java, sql}
    the two sets are equal
```

If the problem cares about how many times each value appears, converting two sequences into `Set`s and calling `equals` answers a different question from the original requirement. You may need to count element frequencies instead of deduplicating.

If the problem cares about position and sequence, use a list model. If it only cares about the presence of each value, a set model is appropriate.

## 6. Comparing Set and List according to business requirements

| Requirement | Model to compare | Reason |
| --- | --- | --- |
| Do two selections have the same tags, each appearing at most once | `Set.equals` | Selection order does not create a value difference |
| Do two operation sequences have the exact same steps in the same order | `List.equals` | The position of each step is part of the meaning |
| Do two lists have the same frequency for each value regardless of order | Appropriate frequency-counting structure | Set discards occurrence counts |
| Do two sets have the same display sequence | Compare a sequence representation per the specific requirement | `Set.equals` intentionally ignores order |

`List.equals` compares corresponding elements in order. Therefore, two `List`s with reversed order can be unequal while two `Set`s created from them are equal. [List.equals](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/List.html#equals(java.lang.Object))

For example, two `LinkedHashSet`s with the same members but different insertion histories are still equal. If the UI needs to verify that two presentation orders match, that is a separate comparison—do not alter the meaning of set `equals` to satisfy it.

Similarly, do not compare `toString()` of two sets and conclude that the set values differ. Printed strings can differ solely due to different iteration orders. Nor should you convert every element to a string and compare those instead of `equals`: two different types can have the same display representation without having the same value meaning.

## 7. Using a Set as an element of a Set or as a key in a Map

### 7.1. Why must order not break key lookup?

Consider a lookup table whose keys are skill sets:

```java
// Illustrative snippet, not a standalone program.
Map<Set<String>, String> labels = new HashMap<>();
labels.put(Set.of("java", "sql"), "backend");

String label = labels.get(Set.of("sql", "java"));
```

If the elements are stable and the set obeys the contract, a lookup key representing the same set value should find the stored entry. The caller does not need to reproduce the exact insertion order.

For this to work, the lookup key set and the stored key set must simultaneously:

- Be equal according to `equals`.
- Have the same hash code according to the contract.

If `Set.hashCode` depended on order, an equal key could land in a different lookup bucket. The hash-sum formula avoids that contradiction.

This is also why a `Set<Set<Integer>>` can recognize `{1, 2}` and `{2, 1}` as the same set pattern. The outer layer uses the inner set's equality and hash code.

### 7.2. Collisions do not merge two different keys

If two keys are `{1, 4}` and `{2, 3}`, both have hash code `5`. A proper `HashMap` still keeps two separate entries because the key sets are not equal.

Similarly, putting both sets into a `HashSet<Set<Integer>>` does not mean the outer set drops one just because their hash codes match. A matching hash code is a signal to distinguish further using `equals`, not a duplicate-element condition.

### 7.3. Do not mutate a set's contents while it is a hash key

A set's `hashCode` is derived from its elements. Adding or removing elements can change the hash code of the entire set.

If a set is currently used as a key in a `HashMap` or as an element of a `HashSet`, mutating that set can alter the data the outer structure relies on to identify keys. Subsequent lookups and removals can no longer be reasoned about as with a stable key.

Do not use a single lucky run to conclude that doing this is safe. The `Set` contract does not specify behavior when an element currently inside a set is modified in a way that affects its equality. An inner set is also an element object to an outer set. [Set: note on mutable elements](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/Set.html)

A manageable design is to create an unmodifiable copy for the key and use stable elements. In the following example, the `members` component is a `Set<String>`, strings are immutable, and the record constructor uses `Set.copyOf` to decouple the key's contents from the input set.

Two things must be distinguished:

- Preventing additions/removals of members of the key set.
- Preventing mutations of internal data within each element in a way that affects equality.

`Set.copyOf` addresses structural mutation of the set via the input reference in the example; it does not deep-copy every element object. For mutable element types, stability must still be designed separately.

As for set structure, the copy from `Set.copyOf` does not reflect subsequent changes to the input collection. [Set.copyOf Contract](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/Set.html#copyOf(java.util.Collection))

A record whose reference field is `final` is not enough either if that field points to a mutable set. A defensive copy in the constructor helps the example preserve proper key semantics.

## 8. TreeSet with a comparator inconsistent with equals

### 8.1. TreeSet's rule must match element equality

`TreeSet` determines whether two elements are equivalent in the tree structure via the result of `compareTo` or `Comparator.compare`. A comparison result of `0` is treated by the tree set as the same element.

To fully comply with the `Set` contract, that ordering must be consistent with `equals`:

```text
compare(x, y) == 0
    must match
x.equals(y) == true
```

For integers and natural ordering, this matches standard equality. However, a case-insensitive comparator for `String` can treat `"a"` and `"A"` as equivalent, whereas `String.equals` returns `false`.

The `TreeSet` documentation explicitly states that an ordering inconsistent with `equals` still has well-defined behavior under its comparison, but does not obey the general `Set` contract. [TreeSet: consistency with equals requirement](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/TreeSet.html)

### 8.2. Loss of symmetry in equality can be observed

Suppose:

- A tree set uses a case-insensitive comparator and contains `"a"`.
- A hash set uses `String.equals` and contains `"A"`.

When the tree set checks membership of the hash set's elements, it can consider `"A"` already present because the comparator returns `0`. When the hash set checks `"a"`, it does not consider it equal to `"A"`.

Output from the example run in the next section:

```text
tree.equals(hash): true
hash.equals(tree): false
tree hash: 97
hash-set hash: 65
```

This is not an example of iteration order changing `equals`. The cause is that **the two structures are using two different definitions of whether elements are equal**.

Nor does it refute the relationship "two equal objects must have the same hash code". The data and comparator in the example caused the tree set to depart from the general `Set` contract; therefore, guarantees based on that contract no longer apply in full.

Do not use `a.equals(b) || b.equals(a)` to "fix" this result. That hides a flaw in identity-rule design and creates a new comparison that is hard to reason about.

### 8.3. Choose a unified identity rule

If the domain requires case-insensitive strings, define a canonical representation or a dedicated value type whose `equals`, `hashCode`, and comparison order align with the same meaning.

If you only need case-insensitive display while values remain case-sensitive, you can sort a representation for display without changing the data's equality rules.

Do not conclude that every `TreeSet` is problematic. An ordering consistent with `equals`, such as the natural ordering of integers in the first example, works properly with the general contract.

## 9. Full program: set keys, collisions, and the Comparator case

Save the code to **SetKeyAndComparatorDemo.java**:

```java
import java.util.HashMap;
import java.util.HashSet;
import java.util.LinkedHashSet;
import java.util.List;
import java.util.Map;
import java.util.Set;
import java.util.TreeSet;

public class SetKeyAndComparatorDemo {
    private record GroupKey(String name, Set<String> members) {
        private GroupKey {
            members = Set.copyOf(members);
        }
    }

    public static void main(String[] args) {
        Set<String> source =
                new LinkedHashSet<>(List.of("java", "sql"));
        GroupKey first = new GroupKey("backend", source);
        GroupKey second = new GroupKey("backend", Set.of("sql", "java"));

        Map<GroupKey, String> groups = new HashMap<>();
        groups.put(first, "found");
        source.add("http");

        System.out.println("key copied membership: "
                + !first.members().contains("http"));
        System.out.println("group keys equal: " + first.equals(second));
        System.out.println("group hashes equal: "
                + (first.hashCode() == second.hashCode()));
        System.out.println("lookup with reordered set: " + groups.get(second));

        Set<Set<Integer>> patterns = new HashSet<>();
        System.out.println("add first pattern: " + patterns.add(Set.of(1, 2)));
        System.out.println("add reordered pattern: "
                + patterns.add(new LinkedHashSet<>(List.of(2, 1))));
        System.out.println("unique patterns: " + patterns.size());

        Map<Set<Integer>, String> collisions = new HashMap<>();
        collisions.put(Set.of(1, 4), "first");
        collisions.put(Set.of(2, 3), "second");
        System.out.println("collision keys stored: " + collisions.size());
        System.out.println("lookup {4, 1}: " + collisions.get(Set.of(4, 1)));
        System.out.println("lookup {3, 2}: " + collisions.get(Set.of(3, 2)));

        Set<String> caseInsensitive =
                new TreeSet<>(String.CASE_INSENSITIVE_ORDER);
        caseInsensitive.add("a");
        Set<String> caseSensitive = new HashSet<>(Set.of("A"));

        System.out.println("tree.equals(hash): "
                + caseInsensitive.equals(caseSensitive));
        System.out.println("hash.equals(tree): "
                + caseSensitive.equals(caseInsensitive));
        System.out.println("tree hash: " + caseInsensitive.hashCode());
        System.out.println("hash-set hash: " + caseSensitive.hashCode());
    }
}
```

Compile and run:

```shell
javac --release 17 -encoding UTF-8 SetKeyAndComparatorDemo.java
java SetKeyAndComparatorDemo
```

Stdout:

```text
key copied membership: true
group keys equal: true
group hashes equal: true
lookup with reordered set: found
add first pattern: true
add reordered pattern: false
unique patterns: 1
collision keys stored: 2
lookup {4, 1}: first
lookup {3, 2}: second
tree.equals(hash): true
hash.equals(tree): false
tree hash: 97
hash-set hash: 65
```

How to read each group of results:

1. `source.add("http")` does not alter the members captured in key `first`. In the constructor, `members = Set.copyOf(members)` creates or uses an unmodifiable representation with the corresponding contents, rather than retaining the mutable input set.
2. Both `GroupKey` instances have the same name and the same members, so they are equal. The order in which members were constructed does not make them two different keys.
3. `groups.get(second)` finds the value stored under `first`, even though the two key objects were created separately.
4. The outer set contains only one pattern `{1, 2}`; adding a reordered pattern does not create a new element.
5. Two different set keys with the same hash code are kept as two entries in `HashMap`.
6. The final group intentionally uses a comparator inconsistent with `String.equals` to observe the loss of symmetry. This is a situation to recognize and avoid when you want the full general `Set` contract, not a recommended key design pattern.

Both standalone programs in this article were compiled with `--release 17` and run to verify the exact stdout. This option checks the language/API level and generates Java 17-compatible bytecode; it does not assert that the runtime JVM itself is JDK 17.

## 10. hashCode is not a durable content signature

A hash code returns an `int`, which can be negative, can be `0`, and can collide across many different sets. It serves the object contract and hash-based data structures.

Do not use `set.hashCode()` alone to:

- Conclude that two sets are definitely identical.
- Generate a unique identifier for contents.
- Confirm that data has not changed just because the hash code before and after is the same.
- Act as a long-term storage signature without a dedicated format and algorithm designed for that requirement.

The general contract does not require an object's hash code to remain the same across application runs. Specific types such as `Integer` or `String` have defined hash code rules, but a `Set` can hold other types. Do not generalize an observation from one example into a guarantee for all element types. [Object.hashCode](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/lang/Object.html#hashCode())

Even within a single run, two different contents can share the same hash code, such as `{1, 4}` and `{2, 3}`. Therefore, having the same hash code before and after an operation does not prove that the operation left the contents unchanged.

If the requirement is simply to check whether two current sets are equal, use `equals`. If the requirement is a verification digest for stored or transmitted data, specify that separate requirement clearly instead of treating an object's hash code as sufficient.

## 11. Computational cost and writing checks properly

Having a variable of type `Set` does not mean `equals` or `hashCode` of the whole set is an O(1) operation.

The base implementation of `AbstractSet.hashCode` iterates through the elements and sums their hash codes. Thus, computing the hash code of an entire set is different from checking a single element in a hash-based set.

Equality can short-circuit when two variables share the same reference, the other side is not a `Set`, sizes differ, or a missing element is found. When two sets are equal but are different objects, confirming equality requires comparing contents according to the respective implementation. The cost also depends on membership checks, hash codes, and element equality. [AbstractSet.equals and hashCode](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/AbstractSet.html)

Sensible choices in code that uses sets:

- Need to check set value: call `equals`.
- Need to check subset: use an appropriate containment check such as `containsAll`.
- Need to check emptiness: call `isEmpty`.
- Need to compare sequence: use an appropriate sequence model.
- Need to use as a key: keep data affecting equality and hash code stable.

Do not add a "compare hashCode first" step before every `equals` call as a default optimization. That step may require iterating over the whole set anyway, still has to call `equals` when hash codes match, and makes the code harder to read without evidence that it solves an actual cost.

Nor should you cache the hash code of a mutable set and continue using the old hash code to represent new contents. If you design an immutable value that caches its hash code for reuse, immutability and equality correctness must be guaranteed by that design.

## 12. Common mistakes and how to fix your mental model

| Misconception or wrong code | Why it is wrong | Right approach |
| --- | --- | --- |
| Two LinkedHashSets print in different orders, so they are not equal | Confuses iteration order with set value | Call `equals` to compare members |
| Two Sets must have the same class to be equal | The contract allows comparing different implementations | Check according to the Set contract |
| Same size is enough | They can contain different elements | Must have the same members |
| One-way containsAll means equal | It may only prove a subset relationship | Use `equals` when both sides are Sets |
| Same hashCode means equal | Hash codes can collide | Hash code does not replace equals |
| hashCode of 0 means the set is empty | Many non-empty sets also sum to 0 | Use `isEmpty` |
| Comparing Set toString strings | Order and display format are not the equality contract | Compare the sets directly |
| Converting every list to a Set for comparison | Discards occurrence counts and order | Choose the model based on data requirements |
| Mutating key set contents after putting into a HashMap | Can change the key's hash code and equality meaning | Use keys with stable contents |
| Using a record is enough to make all components immutable | A final field can still point to a mutable set | Protect structure and consider element stability |
| TreeSet and HashSet compare differently in two directions, so just pick the "desired" direction | There may be a Comparator inconsistent with equals | Unify the value identity rules |

When a comparison produces a surprise, check in order: whether both sides are actually `Set`s; whether contents and sizes match; what equality rules the elements use; whether there is a custom comparator; and whether any data affecting equality was mutated. Display order is only an observation, not the deciding criterion.

## 13. Self-practice and verification

### Exercise 1: compute equality and hash codes by hand

Consider sets containing `Integer`:

```text
A = {2, 5}
B = {5, 2}
C = {1, 6}
D = {2, 5, 0}
E = {}
```

Predict:

1. `A.equals(B)` and the hash codes of both sets.
2. `A.equals(C)` and the hash code of `C`.
3. `A.equals(D)` and the hash code of `D`.
4. Can hash codes be used to conclude that `A`, `C`, and `D` are the same set?

Check:

| Set | Hash code | Equal to A? |
| --- | --- | --- |
| A | `7` | Yes |
| B | `7` | Yes, only written in a different order |
| C | `7` | No, different elements |
| D | `7` | No, has an extra element 0 |
| E | `0` | No |

Adding `0` changes the set's contents and size without changing the hash code sum in this example. This is a direct reason not to use hash codes as the sole check for content changes.

### Exercise 2: distinguish subset, set equality, and sequence equality

Given `a = Set.of(1, 2)`, `b = Set.of(1, 2, 3)`, and `list = List.of(1, 2)`, explain:

```text
b.containsAll(a)  → true
b.equals(a)       → false
a.equals(list)    → false
```

A complete answer should mention the containment relationship, element counts, and structure types. Do not use "because the order is different" for the three lines above.

### Exercise 3: evaluate a key design

A class uses `Set<String> tags` as a component of a lookup key:

1. If two people add the same tags in different orders, should the keys differ?
2. If it directly accepts a `HashSet` from outside and the caller continues mutating it, what needs to be considered?
3. If replaced with `Set.copyOf(tags)`, what part is protected?
4. If the element type `String` is replaced with a mutable class, what else needs to be considered?

Verification hints:

- When tags have set semantics, insertion order should not create a value difference.
- Keys must be stable; holding a set that external code continues to mutate can change equality and hash codes.
- `Set.copyOf` provides an unmodifiable set with the corresponding contents and prevents further structural mutations of the input set from changing the key's members.
- An unmodifiable set does not automatically make element objects immutable. Data affecting each element's `equals`/`hashCode` must still remain stable.

### Exercise 4: explain the TreeSet example accurately

If you see `tree.equals(hash)` differ from `hash.equals(tree)`, do not conclude that "Set's equals depends on which side has ordering". Inspect the comparator and check whether a comparison result of `0` corresponds to element `equals`.

A correct explanation must point out the inconsistency in element identity and relate it to the symmetry of equality, rather than picking one comparison direction as the intended result.
