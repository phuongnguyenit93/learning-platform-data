# containsKey, containsValue, and Distinguishing Absent Keys from null Values

## 1. Do You Need to Ask About the Key or the Value?

`Map<K, V>` stores mappings from keys to values. The key identifies which entry you are looking up; the value is the data associated with that entry. These two questions can produce different answers:

- "Is there an entry with the key `nickname`?"
- "Is there any entry currently holding the value `nickname`?"

In a user profile, the key `nickname` might exist without a nickname having been set yet, so its stored value is `null`. Having the profile declare this entry is different from never having had the entry at all. If a program only looks at the value returned by `get`, the two situations are easily conflated.

This lesson uses `HashMap` as the main example because it allows both `null` keys and `null` values. That is not a universal rule for every `Map` implementation. When using another map type, you must check the contract of that specific type. [HashMap Documentation, Java 17](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/HashMap.html).

After this lesson, you should be able to choose the right check, read the three states of a key, and avoid equating "no mapping" with "a mapping whose value is `null`". This is foundational when handling configuration, partial input data, caches, and lookup results that may be empty.

## 2. Three Operations Answer Three Different Questions

| Operation | Primary Question | Result |
| --- | --- | --- |
| `containsKey(key)` | Is there a mapping for this key? | `boolean` |
| `containsValue(value)` | Does at least one key map to this value? | `boolean` |
| `get(key)` | What is the value for this key? | A value of type V, possibly `null` |

`containsKey` does not require the key's value to be non-`null`. `containsValue` does not tell you which key has that value, nor how many keys share it. `get` retrieves data by key, but the returned value alone may not be enough to conclude whether the key is present or absent. [Map Method Contracts, Java 17](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/Map.html).

Example:

~~~java
Map<String, String> profile = new HashMap<>();
profile.put("name", "Lan");
profile.put("nickname", null);
profile.put("empty", "");
~~~

Checks, while the map remains unchanged:

~~~text
profile.containsKey("nickname")    -> true
profile.containsValue("nickname")  -> false
profile.containsValue("Lan")       -> true
profile.containsKey("Lan")         -> false
profile.get("name")                -> "Lan"
~~~

`"Lan"` is the value of the key `"name"`, not an automatically created key. Similarly, a key's name does not automatically appear in the set of values just because it is present on the key side.

It is valid for multiple keys to map to the same value. For example, two accounts may both choose the same language. `containsValue("vi")` only needs to find one matching mapping to return `true`; it is not a uniqueness check for values.

## 3. The Three-State Model of a Key

For a map that permits `null` values, separate "is there a mapping" from "what is the value":

| State of key k | `containsKey(k)` | `get(k)` | Interpretation |
| --- | --- | --- | --- |
| Key absent | `false` | `null` | There is no mapping for k |
| Key present, `null` value | `true` | `null` | A mapping exists, but its data is currently `null` |
| Key present, non-`null` value | `true` | Stored value | A mapping exists with a value object |

The first two rows have the same `get(k)` result. Therefore:

~~~java
if (profile.get("nickname") == null) {
    // Not enough information to say that the nickname key does not exist.
}
~~~

This snippet illustrates an incomplete condition, not a way to classify the three states.

If you need to express it directly:

~~~java
if (!profile.containsKey("nickname")) {
    System.out.println("Vang khoa");
} else if (profile.get("nickname") == null) {
    System.out.println("Co khoa, gia tri null");
} else {
    System.out.println("Co khoa, gia tri khac null");
}
~~~

This snippet assumes no other party modifies the map during the check. In a full program, we wrap the result into a type that holds both a presence flag and the value so callers do not have to guess.

### Empty Values That Are Not null

The following values are distinct:

~~~text
null       Does not point to a String object.
""         Has a string of length 0.
"null"     Has a string of four characters n, u, l, l.
" "        Has a string of one space.
~~~

If `profile.put("empty", "")`, the key `empty` exists and its value is non-`null`. If business logic treats an empty or whitespace-only string as "not entered", that is an additional rule such as `isEmpty()` or `isBlank()`; it does not change the result of `containsKey`.

Do not use `String.valueOf(profile.get(k))` to determine state. That conversion turns `null` into the display string `"null"`, making it hard to distinguish from an actual `"null"` string value. The full program later uses a separate `<null>` marker and wraps string values in brackets when printing to demonstrate the difference.

## 4. containsValue(null) Does Not Determine the State of a Specific Key

Suppose the map contains:

~~~text
name     -> "Lan"
nickname -> null
~~~

Then:

~~~text
containsValue(null) -> true
get("missing")     -> null
containsKey("missing") -> false
~~~

If you write:

~~~java
boolean exists =
        profile.get("missing") != null || profile.containsValue(null);
~~~

then `exists` is `true` even though the key `missing` is absent. The `containsValue(null)` part only tells you there is a `null` value somewhere, in this case at the key `nickname`. It does not tie that information to the key being queried.

To check whether a specific key exists, call `containsKey` for that key. To know whether a key currently maps to `null`, combine:

~~~java
boolean mappedToNull =
        profile.containsKey("nickname")
        && profile.get("nickname") == null;
~~~

The `&&` ensures the value is only read after confirming existence. However, the two calls are still two separate operations; the expression is not automatically atomic in a multithreaded program.

The direction of inference must also be clear: if the map does not change and a key actually maps to `null`, `HashMap.containsValue(null)` will be `true`. However, from `containsValue(null) == true`, you cannot infer that any given key maps to `null`. This is the difference between a map-wide assertion and an assertion about a specific key.

## 5. getOrDefault Only Substitutes for an Absent Key

`getOrDefault(k, fallback)` only uses `fallback` when **there is no mapping** for key `k`. If the key is present and maps to `null`, the result is still `null`:

~~~java
Map<String, String> profile = new HashMap<>();
profile.put("nickname", null);
System.out.println(profile.getOrDefault("nickname", "Guest")); // null
System.out.println(profile.getOrDefault("missing", "Guest"));  // Guest
~~~

Therefore, when the question is **whether the key exists**, you still must use `containsKey(k)`. The default value is also not proof that the key existed or did not exist: the stored value might happen to equal `fallback`.

The next lesson on `getOrDefault` analyzes common pitfalls in depth: unboxing `null`, evaluating default expressions before the call, using collections as defaults, and policies that also replace `null` if the application truly wants that.
## 6. Optional Cannot Preserve All Three States on Its Own

`Optional.ofNullable(value)` creates an empty `Optional` when the argument is `null`, and a present one when the argument is non-`null`. It does not know whether `null` came from an absent key or a `null` mapping. [Optional.ofNullable Documentation, Java 17](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/Optional.html#ofNullable(T)).

Therefore:

~~~java
Optional<String> first =
        Optional.ofNullable(profile.get("missing"));
Optional<String> second =
        Optional.ofNullable(profile.get("nickname"));
~~~

both `first` and `second` are empty. This is correct according to the `Optional` contract, but it does not satisfy the requirement of preserving the three states of a `Map`.

You can use `Optional.ofNullable(map.get(k)).orElse("Guest")` if business logic wants to merge an absent key and a `null` value. Do not present this expression as a full replacement for `containsKey`.

A simpler result type to preserve complete information:

~~~java
record Lookup<V>(boolean present, V value) {
}
~~~

Then:

~~~text
Lookup(false, null)  -> key absent
Lookup(true, null)   -> key present, value null
Lookup(true, "Lan")  -> key present, value "Lan"
~~~

The state `Lookup(false, "Lan")` contradicts the chosen semantics. The complete program adds a check in the constructor to prevent creating this state.

The lookup method can optimize the non-`null` value case:

~~~java
V value = map.get(key);
boolean present = value != null || map.containsKey(key);
~~~

If `value` is non-`null`, we already have enough information that the key existed during that read, so `||` short-circuits and does not call `containsKey`. If `value` is `null`, we must also ask about existence. This read pattern has a precondition that the map is not modified between operations; the `record` type only makes the result explicit and does not automatically create an atomic snapshot of a map being mutated.

## 7. Complete Java 17+ Program

The following program demonstrates both key-based and value-based checks, the two kinds of `null`, default results, unboxing, operations easily misunderstood by the word "Absent" in their names, and caching a "not found" lookup result.

`lookup` and `loadCached` are intended for maps accessed sequentially in the example. They are not general-purpose thread-safe utilities for any `Map`. The cache loader function is assumed not to modify the cache map itself while loading.

Save as `MapPresenceDemo.java`:

~~~java
import java.util.HashMap;
import java.util.List;
import java.util.Map;
import java.util.Objects;
import java.util.Optional;
import java.util.concurrent.ConcurrentHashMap;
import java.util.function.Function;

public class MapPresenceDemo {
    record Lookup<V>(boolean present, V value) {
        Lookup {
            if (!present && value != null) {
                throw new IllegalArgumentException("Absent lookup cannot hold a value");
            }
        }

        String state() {
            return !present ? "ABSENT"
                    : value == null ? "PRESENT_NULL" : "PRESENT_VALUE";
        }
    }

    static <K, V> Lookup<V> lookup(Map<K, V> map, K key) {
        Objects.requireNonNull(map, "map");
        V value = map.get(key);
        boolean present = value != null || map.containsKey(key);
        return new Lookup<>(present, value);
    }

    static String display(String value) {
        return value == null ? "<null>" : "[" + value + "]";
    }

    static void printLookup(Map<String, String> map, String key) {
        Lookup<String> result = lookup(map, key);
        System.out.println("key=" + key
                + " present=" + result.present()
                + " value=" + display(result.value())
                + " state=" + result.state());
    }

    static <K, V> V loadCached(
            Map<K, V> cache, K key, Function<? super K, ? extends V> loader) {
        if (cache.containsKey(key)) {
            return cache.get(key);
        }
        V value = loader.apply(key);
        cache.put(key, value);
        return value;
    }

    static void expectNullPointer(String label, Runnable action) {
        try {
            action.run();
            throw new AssertionError("Expected NullPointerException: " + label);
        } catch (NullPointerException exception) {
            System.out.println(label + "=NullPointerException");
        }
    }

    public static void main(String[] args) {
        Map<String, String> map = new HashMap<>();
        map.put("name", "Lan");
        map.put("nickname", null);
        map.put("empty", "");
        map.put("literal", "null");
        map.put("fallback", "DEFAULT");

        for (String key : List.of("missing", "nickname", "name", "empty", "literal")) {
            printLookup(map, key);
        }
        System.out.println("contains equal nickname="
                + map.containsKey(new String("nickname")));
        System.out.println("contains value Lan="
                + map.containsValue(new String("Lan")));
        System.out.println("contains key Lan=" + map.containsKey("Lan"));
        System.out.println("contains value nickname=" + map.containsValue("nickname"));
        System.out.println("contains value null=" + map.containsValue(null));
        System.out.println("missing get is null=" + (map.get("missing") == null));
        System.out.println("missing key exists=" + map.containsKey("missing"));
        System.out.println("default missing="
                + display(map.getOrDefault("missing", "DEFAULT")));
        System.out.println("default nickname="
                + display(map.getOrDefault("nickname", "DEFAULT")));
        System.out.println("default stored fallback="
                + display(map.getOrDefault("fallback", "DEFAULT")));
        System.out.println("optional missing present="
                + Optional.ofNullable(map.get("missing")).isPresent());
        System.out.println("optional nickname present="
                + Optional.ofNullable(map.get("nickname")).isPresent());

        map.put(null, "root");
        System.out.println("null key exists=" + map.containsKey(null));
        System.out.println("null key value=" + display(map.get(null)));

        Map<String, Integer> numbers = new HashMap<>();
        numbers.put("limit", null);
        System.out.println("integer default missing="
                + numbers.getOrDefault("missing", 10));
        expectNullPointer("unbox null mapping", () -> {
            int value = numbers.getOrDefault("limit", 10);
            System.out.println("unreachable value=" + value);
        });

        Map<String, String> changes = new HashMap<>(map);
        String previous = changes.putIfAbsent("nickname", "Guest");
        System.out.println("putIfAbsent previous=" + display(previous));
        System.out.println("putIfAbsent value=" + display(changes.get("nickname")));

        changes.put("nickname", null);
        int[] computations = {0};
        String computed = changes.computeIfAbsent("nickname", key -> {
            computations[0]++;
            return "Generated";
        });
        System.out.println("compute null mapping=" + display(computed));
        System.out.println("computation count=" + computations[0]);

        changes.put("nickname", null);
        changes.computeIfAbsent("nickname", key -> null);
        System.out.println("null computation keeps null key="
                + changes.containsKey("nickname"));
        changes.computeIfAbsent("new", key -> null);
        System.out.println("null computation creates new key="
                + changes.containsKey("new"));

        String removed = changes.remove("nickname");
        System.out.println("remove null mapping returned=" + display(removed));
        System.out.println("key exists after remove="
                + changes.containsKey("nickname"));
        changes.put("nickname", null);
        System.out.println("conditional remove absent="
                + changes.remove("missing", null));
        System.out.println("conditional remove null="
                + changes.remove("nickname", null));

        Map<String, String> cache = new HashMap<>();
        int[] loads = {0};
        Function<String, String> loader = key -> {
            loads[0]++;
            return null;
        };
        System.out.println("cached first=" + display(loadCached(cache, "user-7", loader)));
        System.out.println("cached second=" + display(loadCached(cache, "user-7", loader)));
        System.out.println("cached miss key exists=" + cache.containsKey("user-7"));
        System.out.println("loader calls=" + loads[0]);

        Map<String, String> concurrent = new ConcurrentHashMap<>();
        System.out.println("concurrent missing=" + display(concurrent.get("missing")));
        expectNullPointer("concurrent put null value",
                () -> concurrent.put("x", null));
        expectNullPointer("concurrent containsKey null",
                () -> concurrent.containsKey(null));
        expectNullPointer("concurrent containsValue null",
                () -> concurrent.containsValue(null));
    }
}
~~~

Compile and run:

~~~shell
javac --release 17 -encoding UTF-8 MapPresenceDemo.java
java MapPresenceDemo
~~~

Use JDK 17 or newer supporting target version 17. The program uses Java 17-compatible syntax and APIs; the output does not depend on `HashMap` iteration order because each key is checked in a fixed list.

### Reading the Output Groups

The first five lines are the classification. Both `missing` and `nickname` print `value=<null>`, but their `present` flags differ. `empty` prints `value=[]` because an empty string is still a string value. `literal` prints `value=[null]` because those are four actual characters.

The two `new String(...)` calls demonstrate that for string keys and values in `HashMap`, equal content is sufficient; the same object reference is not required. The `contains key Lan` and `contains value nickname` lines remind us that keys and values do not swap roles.

The `default` group shows that the default is only used for absent keys. The `optional` group shows that converting only the return value of `get` to `Optional` merges two states together.

`null key exists=true` is a different story from a `null` value: the `null` key in the example maps to the string `"root"`. The unboxing group shows that a valid `getOrDefault` can still return `null`, leading to an exception when assigned to a primitive type.

The `putIfAbsent`, `compute`, and `remove` lines are explained by their state policies in a later section. Both `cached` lines return `null`, but `loader calls=1` shows that the "not found" lookup was remembered. The `concurrent` lines demonstrate that another map type has a different `null` policy.


## 8. "Absent" in a Method Name Does Not Always Mean containsKey Is false

`containsKey(k)` only checks **whether a mapping exists**. However, several methods with "Absent" in their names also treat a mapping to `null` as a case that needs a value initialized:

~~~java
Map<String, String> settings = new HashMap<>();
settings.put("theme", null);
System.out.println(settings.containsKey("theme")); // true
settings.putIfAbsent("theme", "light");
System.out.println(settings.get("theme"));         // light
~~~

`computeIfAbsent` can also invoke its function to compute a value when the key currently maps to `null`; if the function returns `null`, the method does not set a new value. Therefore, clearly decide whether your policy is "missing key" or "no non-null value yet" before choosing an API.

The lessons `putIfAbsent, Conditional replace, and Conditional remove` and `computeIfAbsent, computeIfPresent, compute` explain in detail when the function is called, return values, and adding/replacing/removing. Here, the key takeaway is that **method names do not replace an accurate presence check with `containsKey`**.
## 9. null Keys and null Values Are Two Independent Axes

A mapping has two positions: key and value. Do not see `null` in one position and infer something about the other.

With `HashMap`:

~~~java
Map<String, String> map = new HashMap<>();
map.put(null, "root");
~~~

`containsKey(null)` is `true`, whereas `containsValue(null)` is `false` if there are no other `null` mappings. The value of the `null` key here is the string `"root"`.

If we continue:

~~~java
map.put(null, null);
~~~

the `null` key is still present; only its value is replaced. Then `get(null)` returns `null` and `containsKey(null)` is still `true`.

A `HashMap` does not create multiple distinct `null` keys. Writing again with the same `null` key updates that key's mapping. Meanwhile, many different keys can share the `null` value.

In business design, the fact that a class permits `null` does not force you to permit `null` in application data. You can require every key to be a valid code and every value to be an object that explicitly describes state. In that case, enforce that rule on every write path rather than relying solely on the declared type `Map<String, V>`.

## 10. Do Not Apply HashMap's null Policy to Every Map

`Map` is an interface; whether `null` keys or `null` values are accepted depends on the implementation. An unsupported `null` query may throw an exception instead of always returning `false`.

| Map Type in Java | Can store `null` keys? | Can store `null` values? | Related consequence |
| --- | --- | --- | --- |
| `HashMap` | Yes | Yes | `get(k) == null` can represent two states |
| `ConcurrentHashMap` | No | No | `get(k) == null` indicates no mapping during that read, for a valid key |
| Maps created by `Map.of` or `Map.copyOf` | No | No | Do not use them to build maps with `null` mappings |

The factory methods `Map.of` and `Map.copyOf` also create unmodifiable maps; that is a separate property from `null` support. A map can be unmodifiable yet still originate from a structure that permits `null` values, so do not use "unmodifiable" as a synonym for "no nulls".

In `ConcurrentHashMap`, `null` keys and `null` values are prohibited. The `containsKey(null)` and `containsValue(null)` calls demonstrated in the program both throw `NullPointerException`. [ConcurrentHashMap Documentation, Java 17](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/concurrent/ConcurrentHashMap.html).

With this type, a `get(key)` returning `null` can be used as a signal that no value was stored for the key during that read. This does not mean the key will remain absent after another thread updates the map, and it does not allow passing a `null` key to query.

Do not choose `ConcurrentHashMap` merely to hide an unclear state design. If the application wants to remember "looked up but not found", it needs a non-`null` value to express that state, such as a result object or `Optional.empty()` stored as the map value.

If you only know a parameter has type `Map<K, V>` without knowing the implementation or input contract, you should not try `containsValue(null)` and assume the call is always safe. Design the accepted value policy directly in your API or read the contract of the map object passed in.

## 11. Applications: Layered Configuration and Caching

### Layered Configuration

Suppose a local configuration layer has three meanings:

~~~text
Key absent          -> inherit global configuration.
Key present -> null -> user chose to clear the inherited value.
Key present -> x    -> use value x.
~~~

If you write `Optional.ofNullable(local.get(key)).orElse(globalValue)`, both an absent key and a local `null` fall back to the global configuration. Thus the operation loses the "clear inherited value" choice.

With sequential access and existing variables, the right policy can be:

~~~java
String resolved = local.containsKey(key)
        ? local.get(key)
        : globalValue;
~~~

A `null` result here can be the right answer because the user chose it. Do not assume every `null` is an error that must be replaced by another value.

Conversely, if the business rule is that `null` means unset, reading with `get` and falling back to a default on `null` is appropriate. The same API can be used rightly or wrongly depending on how you model state.

### Caching "Not Found" Lookups

In a cache, you may need to distinguish:

- Key absent: lookup has not been performed yet, or the old result was evicted from the cache.
- Key present mapping to `null`: looked up and no result exists.
- Key present mapping to an object: looked up and a result exists.

If you use `cache.get(key) == null` to decide whether to load, the second state is treated like the first, causing the same nonexistent data to be loaded repeatedly.

The `loadCached` method in the program checks `containsKey` first. The first load returns `null` and records that mapping in the `HashMap`. The second call sees that the key already exists and returns the recorded value without calling the loader again. That is why stdout has two `<null>` results but only one loader call.

This is a simple single-threaded caching policy, not a complete expiration or refresh mechanism. When real data appears later, the old "not found" result must be invalidated or expired according to application rules. An exception from the loader does not automatically mean "not found" either: the given method does not record a result if the loader throws an exception.

A representation that avoids `null` map values:

~~~java
Map<String, Optional<String>> cache = new HashMap<>();
~~~

With the rule of never writing a `null` `Optional`:

~~~text
No mapping                       -> not looked up yet.
Mapping -> Optional.empty()      -> looked up, no data.
Mapping -> Optional.of(value)    -> looked up, has data.
~~~

Storing `Optional.empty()` still stores a non-`null` object. This differs from `Optional.ofNullable(cache.get(key))` on a string-valued map: here `Optional` is part of the data model inside the map, not an attempt to recover lost information after `get`.

If you use this approach with `ConcurrentHashMap`, `Optional.empty()` is valid because it is non-`null`. Single-flight loading, error handling, expiration, and concurrent updates still require proper design; changing the value type alone does not solve the entire problem.

## 12. Equality, Lookup Cost, and Choosing the Right Query

### Content-Based Comparison and the Key Contract

In the `HashMap<String, String>` examples, `new String("nickname")` can be used to query the stored key `"nickname"` because `String.equals` compares content. Similarly, `containsValue(new String("Lan"))` finds the string value `"Lan"`.

Key objects do not need to compare equal by `==` for `containsKey` to return `true`. For a custom key used in `HashMap`, `equals` and `hashCode` must be consistent; two equal objects must have the same hash code. A case of "looks like the same data but cannot be found" may stem from a broken key contract rather than a `null` value.

Avoid mutating fields that participate in `equals` or `hashCode` of an object while it is being used as a `HashMap` key. Looking up by a mutated key no longer has a basis for working as you expect. The examples use immutable `String` so key-design bugs are not mixed into the state problem being studied.

Specialized map classes may define key identity differently. Therefore, the practical conclusions with strings in this lesson are tied to `HashMap`, not a promise that every object of type `Map` uses the same internal lookup mechanism.

### containsValue Is Usually More Expensive Than containsKey

With `HashMap` and a well-distributed hash code, key lookup has expected constant cost. `containsValue` does not use the same hash index by value, so to conclude that a target value is absent, it may have to scan many elements.

In the OpenJDK 17 source code, `containsKey` checks the result of finding a node by key; `containsValue` iterates through the bucket table and the nodes inside it. In the not-found case on a non-empty map, traversal cost can depend on both table capacity C and number of mappings N, as O(C + N), not just the number of mappings. [HashMap Source Code, OpenJDK 17](https://raw.githubusercontent.com/openjdk/jdk/jdk-17%2B35/src/java.base/share/classes/java/util/HashMap.java).

This explains why you should not replace `containsKey(k)` with a value scan just because sample data is small. For frequent value-based queries, revisit the lookup model. You may need an additional index from values to their associated keys, though when multiple keys share the same value, a reverse index cannot assume only a single key per value.

Do not attach a single universal complexity table to all `Map` implementations. The map type, key comparison, data structure, and cost of `equals`/`hashCode` all affect the result. `containsValue` itself can also stop early when it finds a matching value; "may have to scan" does not mean every call scans everything.

### Choosing the Query That Fits Your Need

| Need | Suitable Expression |
| --- | --- |
| Only need to know if a key exists | `containsKey(key)` |
| Only need to know if value v exists somewhere | `containsValue(v)`, if data policy allows querying v |
| Need the value, okay with merging absent and `null` | `get(key)` |
| Need a default only when the key is absent | `getOrDefault(key, defaultValue)` |
| Need to distinguish all three states | Value plus presence flag, such as `Lookup` |
| Need a default for both absent and `null` | Read with `get` and check for `null`, or a clearly documented state-merging helper |
| Need to check a specific key-value pair | Read by that exact key and compare the value; handle `null` values and concurrency separately |

For the last need, `Objects.equals(map.get(k), expected)` is not enough if `expected` is `null`: an absent key also has `get` equal to `null`. When the map is unchanged, you need an existence check to distinguish `k -> null` from `k` being absent.

## 13. Two Reads Do Not Automatically Form an Atomic Snapshot

The `lookup` method illustrates the right result model for sequential access. If another thread modifies the map between `get` and `containsKey`, the combined result may not correspond to any state that ever existed.

An illustrative update schedule:

~~~text
Initially: key k is absent.
Thread A: get(k) receives null.
Thread B: put(k, "Lan").
Thread A: containsKey(k) receives true.
Thread A: combines into Lookup(true, null).
~~~

If the map never contained `k -> null`, the combined result describes a state that never existed. Even if the two separate operations are performed on a thread-safe map class, combining two observations yourself does not turn them into an atomic operation.

With `HashMap`, multiple threads must not read/write concurrently without proper coordination. If the design allows `null` values and needs to read the full state in a consistent region, all relevant readers and writers must follow the same locking mechanism or operate on an immutable snapshot.

Example of the lock-protection idea, with existing variables:

~~~java
Lookup<String> result;
synchronized (lock) {
    result = lookup(sharedMap, key);
}
~~~

The necessary condition is that every write operation affecting `sharedMap` also uses that same `lock`. Wrapping only the reader, or having each side use a different lock object, does not provide the desired guarantee.

If data is stored under a contract that forbids `null` values, a single `get` can be enough to distinguish absence from presence. `ConcurrentHashMap` enforces this policy and supports concurrent operations, but you still need to read the contract of the update operation you use. Do not treat a hand-written `containsKey -> get -> put` sequence as atomic just because each method belongs to a thread-safe map.

In the cache example, two threads both seeing an absent key and both loading is a separate problem to handle. `containsKey` solves state distinction, not duplicate loading.

## 14. Common Mistakes

| Code or Reasoning | Why It Is Incorrect | How to Handle It |
| --- | --- | --- |
| `get(k) == null` means the key is absent | `null` may have been stored | Also check `containsKey(k)` if you need to distinguish |
| `containsValue(null)` tells you k has `null` | It is only map-wide information | Check key k itself |
| `containsKey(k)` means `get(k)` is non-`null` | Presence does not determine the value | Separate the two pieces of information |
| `getOrDefault` always eliminates `null` from the result | Stored `null` is returned as-is | Choose the default policy that matches business logic |
| Comparing the result to the default tells whether the key was absent | The real value might equal the default | Keep a separate presence flag |
| Wrapping `get` in `Optional` preserves three states | Both `null` sources become empty | Use an explicit result type or data model |
| `putIfAbsent` never replaces an existing key | A `null` value can still be replaced | Check the method's policy |
| `remove(k) != null` is a "removed" flag | Removing a `null` mapping still returns `null` | Use an operation with an appropriate boolean result or check under the same synchronization |
| Every `Map` accepts `null` queries and returns `false` if absent | Some classes throw exceptions | Check the implementation's policy |
| Switching to a thread-safe map makes a check sequence atomic | Multiple calls are still multiple observations | Design atomic operations or proper critical sections |
| Using `containsValue` frequently to reverse-lookup a key | Does not tell you the key, and may scan | Design lookup directions to match your needs |
| Treating empty string, `"null"` string, and `null` as the same | They have different object states | Normalize according to explicitly stated business rules |

Do not fix every bug with a blanket "replace `null` with a default" rule. First determine whether `null` is a valid state with its own meaning. That decision governs how you look up, update, cache, and return results to callers.

## 15. Exercises and Solutions

### Exercise 1 — Reading Three States

Given `Map<String, Integer> ages = new HashMap<>()`, add `ages.put("An", null)` and `ages.put("Binh", 20)`. Fill in the results of `get` and `containsKey` for An, Binh, and Chi.

**Solution:**

| Key | get | containsKey | State |
| --- | --- | --- | --- |
| An | null | true | Key present, `null` value |
| Binh | 20 | true | Key present, non-`null` value |
| Chi | null | false | Key absent |

Looking only at the `get` column cannot distinguish An from Chi.

### Exercise 2 — Choosing the Check for the Right Side

Given `Map<String, String> roleByUser` containing `"u1" -> "ADMIN"`, what do you use to ask whether account u1 exists? What do you use to ask whether anyone currently holds the ADMIN role?

**Solution:** `containsKey("u1")` and `containsValue("ADMIN")`, respectively. The second operation does not return the list of accounts and does not tell you how many ADMIN accounts exist.

### Exercise 3 — Can containsValue(null) Rescue get?

A map has `"a" -> null`. Key b is not present. What does `map.get("b") != null || map.containsValue(null)` return, and is it valid for checking key b?

**Solution:** It returns `true`, which is incorrect. The `null` value belongs to key a; key b is still absent. Use `containsKey("b")`, which returns `false`.

### Exercise 4 — Default for a Key Mapped to null

A map has `"timeout" -> null`. What is the result of `map.getOrDefault("timeout", 30)`? What happens if you assign it directly to an `int`?

**Solution:** With a `Map<String, Integer>` that permits `null`, the result is `Integer null`. Assigning to `int` causes a `NullPointerException` during unboxing. If you want to use 30 for both an absent key and `null`, read into an `Integer` and check for `null` explicitly.

### Exercise 5 — Empty String and "null" String

A map has `"x" -> ""` and `"y" -> "null"`. Do both map to `null`? What does `containsKey` return?

**Solution:** No. Both map to non-`null` `String` objects, so `containsKey("x")` and `containsKey("y")` are both `true`. Treating them as "not entered" requires a separate business rule, not changing the semantics of `Map`.

### Exercise 6 — Optional Losing Information

A method returns `Optional.ofNullable(map.get(k))`. Can the caller tell whether k existed with `null` or never existed?

**Solution:** No; both become `Optional.empty()`. If you need to preserve that information, return a `Lookup<V>` with a presence flag, or use a data model inside the map with clearly defined states.

### Exercise 7 — Policy Against Overwriting null

The key `"color"` already exists with value `null`, and `null` means "no color used". Should you call `putIfAbsent("color", "blue")` to add only when the key does not exist yet?

**Solution:** No. That call can replace `null` with blue. Under sequential access, checking `!containsKey("color")` before inserting expresses the policy to preserve. If concurrent updates occur, you need protection covering both the decision and the write operation.

### Exercise 8 — null Result from computeIfAbsent

On a `HashMap`, the new key `"new"` does not exist yet. Does `computeIfAbsent("new", k -> null)` create a `null` mapping so the computing function is not called next time?

**Solution:** No. No non-`null` value is produced, so no new mapping is added. The next call may still invoke the computing function. If you need to remember a "not found" result, use a dedicated sentinel value such as an actually stored `Optional.empty()`, or a `null`-storing policy with proper `containsKey` checks.

### Exercise 9 — Old Value When Removing

A map has `"a" -> null`. `remove("a")` returns `null`. Can you conclude nothing was removed? What is `containsKey("a")` afterward?

**Solution:** You cannot conclude that from the return value. The `null` mapping was removed; in the sequential example, `containsKey("a")` afterward is `false`. If you want to remove only a `null` mapping and get a success flag, `HashMap.remove("a", null)` returns `true` when the matching mapping still exists.

### Exercise 10 — Two Kinds of null

A `HashMap<String, String>` has only `null -> "root"`. Fill in `containsKey(null)`, `get(null)`, and `containsValue(null)`.

**Solution:** `true`, `"root"`, and `false`, respectively. A `null` key does not have to be paired with a `null` value. Do not apply these results to `ConcurrentHashMap` because it does not accept `null` keys.

### Exercise 11 — Concurrency Check

Thread A reads `get(k)` and sees `null`. Thread B inserts `k -> "Lan"`. Thread A reads `containsKey(k)`, sees `true`, and combines them into "key present, `null` value". What is wrong?

**Solution:** The two results belong to two different points in time. Combining them does not create an atomic snapshot. You need a consistent access contract—such as a lock region respected by all relevant parties—or a `null`-forbidding model with appropriate reads on a concurrent structure.

### Exercise 12 — Designing a Configuration Field

Requirement: if the key is absent, inherit; if the key has `null`, disable the value; if the key has a string, use that string. Write an expression to select the value when the map does not change. Why is `getOrDefault` a better fit than `Optional.ofNullable(get).orElse` for this requirement?

**Solution:** You can use `local.getOrDefault(key, inheritedValue)` or `local.containsKey(key) ? local.get(key) : inheritedValue`. They preserve the stored `null`. Wrapping `get` alone with `Optional.ofNullable` and then `orElse` would replace local `null` with the inherited value as well, losing the disable option.

## 16. Self-Check for Reading Maps

When writing a condition, name the information you actually need: key existence, value occurrence, or the data attached to a key. Those three questions lead to three different operations.

If `null` values are allowed, test your condition on at least three states: key absent, key present with `null`, and key present with a real value. Also test empty strings or a default value matching real data if your business logic includes them. When multiple threads update the map, separately verify whether observations are read within the same consistent state.

`containsKey` holds information about the mapping; `get` provides the value; `containsValue` queries the value side of the entire map. Using them for the right question and deciding the meaning of `null` directly in your data model will prevent most bugs that confuse an absent key with a `null` value.
