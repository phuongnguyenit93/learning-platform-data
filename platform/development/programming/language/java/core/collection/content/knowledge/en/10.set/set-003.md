# Membership Testing and Element Removal in Set

## 1. Two Different Questions: Is the Element Present, and Can It Be Removed?

`Set<E>` represents a collection of unique elements according to the set's rules for element identity. When working with a set of tags, job IDs, or user IDs, we often need to answer two questions:

- Is a value already in the set? Use `contains`.
- After requesting to remove a value, did the set actually change? Use `remove`.

For example, a set currently contains `"java"` and `"sql"`. Calling `contains("java")` answers `true` while keeping both elements. Calling `remove("java")` on a modifiable set removes that element and returns `true`. Calling `remove("java")` again returns `false`, because there is no longer a matching element to remove.

The key point to understand before reading code is that **membership testing is not finding an index**, and **removal returns a modification flag, not the removed element**. `Set` does not provide index-based access like `List`.

There are implementations that preserve order, such as `LinkedHashSet`, but iteration order does not turn a set into a list. With `Set<Integer>`, `remove(1)` means removing the element whose `Integer` value equals `1`; it does not mean removing the element at index 1. [Set specification in Java 17](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/Set.html)

After this lesson, you should be able to explain:

1. What arguments `contains` and `remove` accept, what they return, and whether they modify the set.
2. Why a newly created object can still find and remove a stored object.
3. Why `HashSet` and a `TreeSet` with a custom comparator can produce different results.
4. How to remove a single element, multiple elements, or elements matching a condition.
5. How to remove elements during iteration without modifying the set through an invalid path.

## 2. Basic Contract of contains and remove

### 2.1. contains Only Answers Membership

Method signature:

```java
boolean contains(Object value)
```

Under the general contract, `contains(value)` returns `true` if there is an element `element` such that `Objects.equals(value, element)` is `true`. If no matching element exists, it returns `false`, noting that some implementations may reject invalid arguments by throwing an exception.

`contains` does not add, remove, or retrieve an element from the set. Its result is a `boolean` value, not an element, an index, or an occurrence count. Because a set does not store multiple equal copies, the question "how many copies of this value are there?" is not the purpose of this method.

For a stable set, with no other threads modifying it and elements not changing their equality rules while stored:

| Before the call | Call | Result | After the call |
| --- | --- | --- | --- |
| Contains an element equal to `"java"` | `contains("java")` | `true` | Set remains unchanged |
| Contains no element equal to `"xml"` | `contains("xml")` | `false` | Set remains unchanged |

The parameter has type `Object`, not `E`. Therefore, the fact that a call compiles does not prove that the query value's type matches the set's elements. A later section analyzes the `Integer` and `Long` case.

### 2.2. remove Deletes a Matching Element and Returns a Change Flag

Signature:

```java
boolean remove(Object value)
```

For a modifiable set, `remove(value)` removes the matching element if present. It returns:

- `true`: the set changed because an element was removed.
- `false`: there was no matching element to remove, so the set did not change.

Because a `Set` cannot contain two elements that are equal according to its rules, removing a value never means looping to remove multiple copies.

| State of modifiable set | Return value | Size change |
| --- | --- | --- |
| Contains an element matching the argument | `true` | Decreases by 1 |
| Contains no element matching the argument | `false` | Unchanged |
| Set is empty, valid query argument | `false` | Remains 0 |

The rows above assume the operation does not throw an exception, there is no concurrent modification, and elements have stable equality rules. They do not mean every implementation is required to accept every argument or support removal. Modification operations on `Set` are optional operations; an unmodifiable set may throw `UnsupportedOperationException`. [Contract of contains and remove](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/Set.html)

### 2.3. No Need to Call contains Before Every remove

If the goal is simply to remove an element if present and report the outcome, the return value of `remove` already provides the necessary information:

```java
// Illustrative snippet: tags is a modifiable Set<String>.
if (tags.remove("sql")) {
    System.out.println("Đã xóa thẻ sql");
} else {
    System.out.println("Không có thẻ sql để xóa");
}
```

Writing `if (tags.contains("sql")) { tags.remove("sql"); }` usually performs an extra lookup. It also does not automatically create an atomic operation: between the two calls, another thread could modify the set if the program has concurrent access.

Using `remove` directly expresses a single request cleanly, but it does not make `HashSet` or `LinkedHashSet` thread-safe for concurrent modifications. You need to choose an appropriate data structure and synchronization mechanism if the problem involves multiple threads; that is a separate requirement, not something implied by the `boolean` return type.

If you only need to check membership and want to preserve the data, use `contains`. Do not use `remove` to "test whether something is there," because such a test deletes the element.

## 3. How Is "the Same Element" Determined?

### 3.1. Value Equality Does Not Mean Reference Identity

Two variables can point to two different objects yet represent the same value:

```java
// Illustrative snippet about String, not a standalone program.
String stored = "java";
String probe = new String("java");

System.out.println(stored == probe);      // false
System.out.println(stored.equals(probe)); // true
```

A set based on value equality can recognize `probe` as an element already present. The caller is not required to keep the exact reference used when adding the element.

This is useful when query data comes from elsewhere: a user ID read from a file, a tag entered from the keyboard, or a job ID received in a message. We want to look up by the meaning of the value, not by the object's location in memory.

However, a user-defined class without a value-based `equals` rule will not automatically have that behavior. If the class simply inherits `Object`'s equality, two distinct objects remain unequal even if their fields have identical contents. You must design `equals`/`hashCode` appropriately or use a suitable value type, such as a `record` with immutable components.

### 3.2. HashSet and LinkedHashSet: hashCode Assists Lookup, equals Confirms Equality

`HashSet` uses a hash-based structure. You can think of lookup and removal in two steps:

1. Use the hash code to narrow down the search region.
2. Use equality comparison to identify the matching element.

Therefore, designing an element for use in a hash-based set must follow these rules:

- If two objects are equal according to `equals`, they must have the same `hashCode`.
- Having the same `hashCode` does not require them to be equal. A hash collision does not turn two different values into a single element.
- Data affecting `equals` and `hashCode` must remain stable while the object is in the set.

`LinkedHashSet` additionally preserves insertion order during iteration, but it still has the same hash-based lookup and equality semantics. It must not be assumed to look up by insertion index. [HashSet](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/HashSet.html), [LinkedHashSet](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/LinkedHashSet.html)

For example, `record UserId(String value)` in the second program uses component-based equality from the record. Because `String` is immutable, this is a simple, stable key for the example. Two separately created `UserId("u-1")` instances are still equal by value, so the second object can be used to check for or remove the first element.

A record does not automatically make all component types immutable. If a record holds a mutable object and that object's equality changes, you still need to consider the risk of the key changing while in the set.

### 3.3. Using the Right Query Value Type Still Matters

Consider a `HashSet<Integer>` containing the integer `1`:

```java
// Illustrative snippet; full imports and program are in a later example.
Set<Integer> numbers = new HashSet<>(Set.of(1, 2));

numbers.contains(1);   // true: 1 is boxed into Integer
numbers.contains(1L);  // false: 1L is boxed into Long
numbers.remove(1L);    // false: does not remove Integer 1
```

`Integer.valueOf(1)` and `Long.valueOf(1L)` are not equal according to `equals`. Representing the same mathematical number does not mean they are the same value under the rules of the two classes.

The calls above still compile because the parameter type is `Object`. The set's generic type does not force the query method to accept only `E` at compile time.

The `false` result here is specific to this implementation and data in the example. Do not generalize this into "a wrong-type query always returns false for every Set." The contract allows some implementations to throw `ClassCastException` when the argument type is incompatible. With `TreeSet`, the argument must also be comparable using the ordering that the set uses. [Set: optional exceptions for query and removal](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/Set.html)

### 3.4. TreeSet Determines Elements via Comparison

`TreeSet` uses natural ordering via `Comparable` or a provided `Comparator`. For lookup and removal operations, two values are considered the same element when the comparison result is `0`.

Example:

```java
// Illustrative snippet; a complete runnable version is in the second program.
Set<String> names = new TreeSet<>(String.CASE_INSENSITIVE_ORDER);
names.add("Java");

names.contains("JAVA"); // true
names.remove("java");   // true
```

The case-insensitive comparator treats `"Java"`, `"JAVA"`, and `"java"` as equivalent. However, `String.equals` is case-sensitive: `"Java".equals("JAVA")` is `false`.

This example is meant to clearly show how `TreeSet` works, while also highlighting a design point that requires care: a set's ordering should be consistent with `equals` to obey the general `Set` contract. An ordering inconsistent with `equals` still produces well-defined behavior according to `TreeSet`'s comparator, but causes the set to violate that general contract. The discrepancy in this example should not be taken as default advice for all string sets. [TreeSet specification on ordering and equals](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/TreeSet.html)

If your domain requires case-insensitive codes, define the normalization and equality rules for the code right in the design. For example, normalize upon creating a dedicated code type, then keep the same meaning for `equals`, `hashCode`, and comparison order. Do not let each lookup site pick a different rule.

### 3.5. Do Not Mutate a Key After Adding It to a Set

Suppose `User` uses `email` in `equals` and `hashCode`. After adding a `User` to a `HashSet`, the program changes that same object's `email`. Now the recomputed hash code may differ from the hash code at insertion time.

In that situation, the fact that the object is still referenced in the set does not guarantee that `contains` or `remove` will find it as the author expects. The `Set` contract does not specify behavior if an element's value is modified in a way that affects equality while the element remains in the set. There is no portable stdout across all such programs to memorize. [Set: mutable elements](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/Set.html)

With `TreeSet`, changing a field used for ordering also makes the object no longer match its position in the tree structure.

The most controllable design is to use immutable keys. If you truly need to update an identifying value, you must design an operation that removes the old value before mutating and then adds the new value, while also handling the case where the new value already exists. That sequence of operations is not inherently atomic or rollback-safe; the application must decide on an appropriate policy.

## 4. Checking Multiple Values and Bulk Removal

Not every requirement involves only a single element. `Set` inherits collection-level operations from `Collection`, so it is important to distinguish the receiver object from the argument collection.

### 4.1. containsAll: Are All Required Values in the Set?

```java
// Illustrative snippet.
Set<String> skills = new LinkedHashSet<>(List.of("java", "sql", "http"));

boolean enough = skills.containsAll(List.of("java", "http")); // true
boolean missing = skills.containsAll(List.of("java", "xml")); // false
```

`containsAll(required)` returns `true` when all elements of `required` are contained in `skills`. The method does not modify `skills`.

There are three common misconceptions:

- It does not check "whether there is at least one element in common." A single missing requirement is enough to make the result `false`.
- It does not check whether two sets are equal. `skills` may have many additional elements and the result is still `true`.
- It does not count duplicates in the argument. If the set has `"java"`, then `containsAll(List.of("java", "java"))` is still `true`.

For a normal set that supports the corresponding queries, `containsAll` with an empty required collection returns `true`: no requirement is missing. This is the same "every element of the empty set satisfies the condition" meaning, not a special bug that needs to be inverted.

### 4.2. Choosing the Right Operation for the Goal

In the table below, `current` is the receiver set and `other` is the collection used for comparison:

| Operation | Meaning for current | Return value |
| --- | --- | --- |
| `current.containsAll(other)` | Checks whether every element of other is in current; leaves current unchanged | `boolean` answering the query |
| `current.removeAll(other)` | Removes from current the elements that are in other | `true` if current changed |
| `current.retainAll(other)` | Keeps in current only the elements that are also in other | `true` if current changed |
| `current.removeIf(predicate)` | Removes elements for which the predicate returns true | `true` if any elements were removed |
| `current.clear()` | Removes all elements | `void` |

Whichever set the method is called on is the one that gets modified. Passing another collection into `removeAll` or `retainAll` does not mean requesting to delete data from the argument collection.

The `boolean` return values of modification operations are also not the count of removed elements. `true` can correspond to one or many removed elements. If you need the count, for a modifiable set with no other actor mutating it, you can subtract the size after a successful operation from the size before.

Example with sets sharing the same equality rules:

```text
Initial current: [java, sql, http, xml]

current.removeAll([sql, missing])
→ remaining: [java, http, xml]
→ true, because sql was removed; absent missing causes no error

current.retainAll([java, http])
→ remaining: [java, http]
→ true, because xml is not in the retained set

current.removeIf(s -> s.startsWith("h"))
→ remaining: [java]
→ true, because http satisfies the removal condition
```

Avoid memorizing `retainAll` as "remove the argument elements." It does the opposite: elements *not* retained by the argument collection are removed. If the argument is empty and the operation is supported, `retainAll` will empty a non-empty set.

Modification operations are still subject to the implementation's limitations. An unmodifiable set does not become modifiable just by switching from `remove` to `removeAll` or `removeIf`. [Inherited operations of Set](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/Set.html)

### 4.3. removeIf and the Removal Predicate

`removeIf` takes a `Predicate`, i.e., a condition that receives an element and returns a `boolean`. `true` means **remove** that element:

```java
// Illustrative snippet: pending is a modifiable Set<String>.
pending.removeIf(value -> value.startsWith("done:"));
```

For a set that may contain `null`, the predicate also needs to handle `null` if you want to iterate safely:

```java
// Remove null and blank strings; tags may contain null.
tags.removeIf(value -> value == null || value.isBlank());
```

In this expression, `||` short-circuits: when `value == null` is `true`, Java does not call `isBlank()` on `null`.

The predicate should only decide whether to remove the element under inspection. Do not call `add`, `remove`, or `clear` on the set itself from inside the predicate; modifying the structure while it is being traversed can cause the operation to fail or behave unexpectedly.

Exceptions thrown inside the predicate are propagated outward. Do not assume `removeIf` will restore any elements already removed before the exception occurred. If the problem requires "either remove everything matching the criteria, or leave everything intact," you must design an additional mechanism to meet that requirement. [Collection.removeIf in Java 17](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/Collection.html#removeIf(java.util.function.Predicate))

## 5. Complete Program: Observing the Result of Each Operation

The following program uses `LinkedHashSet` so that printed output follows insertion order, making stdout easy to verify. This is a choice for the example, not an ordering guarantee of the `Set` interface.

Save all the code to **SetMembershipRemovalDemo.java**:

```java
import java.util.Arrays;
import java.util.LinkedHashSet;
import java.util.List;
import java.util.Set;

public class SetMembershipRemovalDemo {
    public static void main(String[] args) {
        Set<String> tags =
                new LinkedHashSet<>(Arrays.asList("java", "sql", null));
        System.out.println("initial: " + tags);
        System.out.println("contains equal String: "
                + tags.contains(new String("java")));
        System.out.println("contains missing: " + tags.contains("xml"));
        System.out.println("contains null: " + tags.contains(null));
        System.out.println("size after contains: " + tags.size());

        System.out.println("remove sql: " + tags.remove("sql"));
        System.out.println("after removal: " + tags);
        System.out.println("remove sql again: " + tags.remove("sql"));
        System.out.println("remove null: " + tags.remove(null));
        System.out.println("remaining: " + tags);

        Set<Integer> numbers =
                new LinkedHashSet<>(List.of(1, 2, 3));
        System.out.println("Set.remove(1): " + numbers.remove(1));
        System.out.println("numbers: " + numbers);

        Set<String> skills =
                new LinkedHashSet<>(List.of("java", "sql", "http", "xml"));
        System.out.println("contains repeated requirement: "
                + skills.containsAll(List.of("java", "java")));
        System.out.println("contains empty requirement: "
                + skills.containsAll(List.of()));

        System.out.println("removeAll changed: "
                + skills.removeAll(Set.of("sql", "missing")));
        System.out.println("after removeAll: " + skills);
        System.out.println("retainAll changed: "
                + skills.retainAll(Set.of("java", "http")));
        System.out.println("after retainAll: " + skills);
        System.out.println("removeIf changed: "
                + skills.removeIf(value -> value.startsWith("h")));
        System.out.println("after removeIf: " + skills);

        skills.clear();
        System.out.println("after clear: " + skills
                + "; size = " + skills.size());
    }
}
```

Compile for Java 17 and run:

```shell
javac --release 17 -encoding UTF-8 SetMembershipRemovalDemo.java
java SetMembershipRemovalDemo
```

Stdout:

```text
initial: [java, sql, null]
contains equal String: true
contains missing: false
contains null: true
size after contains: 3
remove sql: true
after removal: [java, null]
remove sql again: false
remove null: true
remaining: [java]
Set.remove(1): true
numbers: [2, 3]
contains repeated requirement: true
contains empty requirement: true
removeAll changed: true
after removeAll: [java, http, xml]
retainAll changed: true
after retainAll: [java, http]
removeIf changed: true
after removeIf: [java]
after clear: []; size = 0
```

How to read the output:

1. `new String("java")` is a separate object but equals the stored string, so `contains` returns `true`.
2. After the queries, the size is still 3. `contains` does not take elements out of the set.
3. The first removal of `"sql"` changes the set; the next call does not find it and returns `false`.
4. The `tags` set allows `null`, so `null` can be tested and removed as a value accepted by the set.
5. `numbers.remove(1)` removes the number `1`; the result is `[2, 3]`, proving this is not an index-based removal.
6. Requesting `"java"` twice in `containsAll` does not require two copies in the set.
7. `removeAll`, `retainAll`, and `removeIf` sequentially mutate the same `skills` set; read each result relative to the preceding state.
8. `clear` has no return value. The program verifies the post-state by printing the set and `size()`.

The sets created by `Set.of(...)` in the arguments to `removeAll` and `retainAll` are only used for reading and comparison. The receiver set here is still a modifiable `LinkedHashSet`, so there is no conflict with `Set.of`'s unmodifiability.

## 6. Removing Elements During Iteration

### 6.1. Why Direct remove in a for-each Loop Is a Problem

A `for-each` loop over a set uses an iterator under the hood. If you are iterating over a regular `HashSet` or `LinkedHashSet` and call `set.remove(value)` directly, the structure is modified through a path different from the active iterator.

The following snippet illustrates what to avoid, not a program to run and rely on for a fixed exception outcome:

```java
// Do not use this approach to remove from HashSet/LinkedHashSet during for-each.
for (Integer value : values) {
    if (value % 2 == 0) {
        values.remove(value);
    }
}
```

The fail-fast iterator of these sets may throw `ConcurrentModificationException` when it detects invalid structural modification. The exception's name does not mean two threads are required; a single thread can also iterate and modify improperly at the same time.

Fail-fast detection is only best-effort. Not seeing an exception in one run does not prove the loop is correct, and that exception should never be used as an algorithm's control-flow mechanism. [HashSet: iterators and fail-fast](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/HashSet.html)

### 6.2. Iterator.remove Deletes the Element Just Returned by next

When you need explicit control over iteration and removal, use the set's iterator if it supports this operation:

```java
// Illustrative snippet; the full program appears in the next section.
Iterator<Integer> iterator = values.iterator();
while (iterator.hasNext()) {
    Integer value = iterator.next();
    if (value % 2 == 0) {
        iterator.remove();
    }
}
```

`iterator.remove()` takes no arguments. It removes the element returned by the most recent call to `next()`. Important rules:

- `next()` must be called before the corresponding removal.
- Only one `remove()` is allowed per `next()` call.
- Calling remove before `next()`, or calling remove twice in a row for the same element, can result in `IllegalStateException`.
- The iterator must also support the removal operation; not every iterator has this capability.

The rules above apply to `Iterator.remove` when this operation is supported. [Contract of Iterator.remove](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/Iterator.html#remove())

If you only need a clear removal condition, `removeIf` is usually shorter. If you need multiple processing steps per turn or need to use an explicit iterator, `Iterator.remove` makes clear which element is being removed. Do not mix both approaches by keeping an active iterator while calling `removeIf` on the same set.

## 7. null, Unmodifiable Sets, and Exceptions

### 7.1. Is null Considered an Element?

There is no single answer for every `Set`:

| Set type | What to remember when testing and removing |
| --- | --- |
| `HashSet` | Allows one `null` element; `contains(null)` and `remove(null)` work |
| `LinkedHashSet` | Also allows one `null` element |
| `TreeSet` with natural ordering | Does not accept `null` as a comparable element; do not use `contains(null)` as a universal test |
| `TreeSet` with Comparator | `null` handling depends on the comparator |
| `Set.of(...)` | Disallows `null` elements; the set is also unmodifiable |

If a set allows `null`, the uniqueness rule still applies: at most one `null`.

Do not conflate two different situations:

- A valid query value that is not in the set: normally returns `false`.
- A query value not accepted by the implementation: may throw an exception.

The specification allows `NullPointerException` when the argument is `null` and the set forbids it, and `ClassCastException` when the argument type is incompatible. Some invalid-argument queries may return `false` depending on the implementation; therefore, do not build logic assuming every set handles them identically. [Set](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/Set.html), [TreeSet](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/TreeSet.html)

### 7.2. Readable Does Not Always Mean Removable

`Set.of("java", "sql")` creates an unmodifiable set. It still permits valid queries such as `contains("java")`, but modification operations are rejected with `UnsupportedOperationException`.

A variable of type `Set<String>` only indicates the interface the caller is using. It does not prove that the actual underlying object is a modifiable set.

If you need a separate working set that allows removal, you can create a structural copy:

```java
// Illustrative snippet.
Set<String> source = Set.of("java", "sql");
Set<String> working = new LinkedHashSet<>(source);

working.remove("sql"); // modifies working
// source still contains "sql"
```

The initial order of `working` follows the iteration order of `source`, so do not predict a fixed print order for this snippet from `Set.of` alone. Copying a set is also not a deep copy of its elements: if elements are mutable objects, both sets can still hold references to the same objects.

Do not use `remove` and catch exceptions as a default way to discover whether arbitrary data is modifiable. Clearly design ownership and set types where the data is created or received.

## 8. Complete Program: Equality Rules and Removal During Iteration

Save the code to **SetLookupRulesDemo.java**:

```java
import java.util.HashSet;
import java.util.Iterator;
import java.util.LinkedHashSet;
import java.util.List;
import java.util.Set;
import java.util.TreeSet;

public class SetLookupRulesDemo {
    private record UserId(String value) {
    }

    public static void main(String[] args) {
        UserId stored = new UserId("u-1");
        UserId probe = new UserId("u-1");
        Set<UserId> ids = new HashSet<>();
        ids.add(stored);

        System.out.println("same UserId instance: " + (stored == probe));
        System.out.println("contains equal UserId: " + ids.contains(probe));
        System.out.println("remove equal UserId: " + ids.remove(probe));
        System.out.println("ids size: " + ids.size());

        Set<Integer> numeric = new HashSet<>(Set.of(1, 2));
        System.out.println("contains Integer 1: " + numeric.contains(1));
        System.out.println("contains Long 1: " + numeric.contains(1L));
        System.out.println("remove Long 1: " + numeric.remove(1L));

        Set<String> ordered = new TreeSet<>(String.CASE_INSENSITIVE_ORDER);
        ordered.add("Java");
        System.out.println("TreeSet contains JAVA: " + ordered.contains("JAVA"));
        System.out.println("String equals JAVA: " + "Java".equals("JAVA"));
        System.out.println("TreeSet remove java: " + ordered.remove("java"));
        System.out.println("TreeSet size: " + ordered.size());

        Set<Integer> values =
                new LinkedHashSet<>(List.of(1, 2, 3, 4, 5));
        Iterator<Integer> iterator = values.iterator();
        while (iterator.hasNext()) {
            Integer value = iterator.next();
            if (value % 2 == 0) {
                iterator.remove();
            }
        }
        System.out.println("after iterator removal: " + values);

        Set<String> fixed = Set.of("java", "sql");
        System.out.println("unmodifiable contains java: " + fixed.contains("java"));
        try {
            fixed.remove("java");
        } catch (UnsupportedOperationException ex) {
            System.out.println("unmodifiable remove: UnsupportedOperationException");
        }
    }
}
```

Compile and run:

```shell
javac --release 17 -encoding UTF-8 SetLookupRulesDemo.java
java SetLookupRulesDemo
```

Stdout:

```text
same UserId instance: false
contains equal UserId: true
remove equal UserId: true
ids size: 0
contains Integer 1: true
contains Long 1: false
remove Long 1: false
TreeSet contains JAVA: true
String equals JAVA: false
TreeSet remove java: true
TreeSet size: 0
after iterator removal: [1, 3, 5]
unmodifiable contains java: true
unmodifiable remove: UnsupportedOperationException
```

Points to verify while reading:

- `stored == probe` is `false`, yet `ids.contains(probe)` and `ids.remove(probe)` are both `true`: the query object has a value equal to the stored object.
- `1L` does not equal `Integer` with value `1`; querying and removing with `Long` in the `HashSet<Integer>` example both yield `false`.
- `TreeSet`'s comparator recognizes strings differing in case as the same element; `String.equals` does not. This example intentionally exposes the inconsistency to avoid when aiming for full compliance with the general `Set` contract.
- `Iterator.remove` removes even numbers during iteration, leaving `[1, 3, 5]`.
- The `fixed` set supports queries but rejects removal, even though the variable still has type `Set<String>`.

Both programs in this lesson were compiled with `--release 17` and executed to verify the exact stdout recorded above. `--release 17` checks the language/API level and generates Java 17-compatible bytecode; this option does not mean the running JVM itself is JDK 17.

## 9. Performance: Distinguishing Interface from Implementation

You cannot look at a variable of type `Set<E>` and conclude that every `contains` or `remove` call has the same complexity.

| Implementation | Basic contains/remove | Conditions and meaning |
| --- | --- | --- |
| `HashSet` | Expected constant time, often denoted O(1) | Hash codes must distribute reasonably; not a constant-time guarantee in all cases |
| `LinkedHashSet` | Similar to hash set, expected O(1) | Preserves insertion order during iteration; does not look up by index |
| `TreeSet` | O(log n) | Based on an ordered tree; each step also incurs comparison cost |
| An arbitrary `Set` | Implementation-dependent | The interface does not mandate hashing or trees |

The notations above describe basic operations in terms of element count `n`; actual cost also depends on `hashCode`, `equals`, comparator implementation, and the data. Do not infer that `containsAll`, `removeAll`, `retainAll`, or `removeIf` also take only O(1). They operate on multiple elements, may iterate, and may perform many checks. [HashSet](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/HashSet.html), [LinkedHashSet](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/LinkedHashSet.html), [TreeSet](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/TreeSet.html)

In application code, choose the right semantics first:

- Need to answer "is it already present?": `contains`.
- Need to remove if present and know whether it changed: `remove` directly.
- Need to remove by a collection of values: `removeAll`.
- Need to keep only the intersection: `retainAll`.
- Need to remove by a per-element condition: `removeIf`.
- Need controlled iteration while removing the current element: `Iterator.remove`.

Optimizing the number of lookups is only worthwhile after equality rules, mutability, and data ownership are clear.

## 10. Applying to a Small Scenario

Suppose a tag management screen has a working set `selectedTags`:

```java
// Illustrative snippet, selectedTags is a modifiable working set.
if (selectedTags.contains("java")) {
    System.out.println("Đang chọn thẻ java");
}

boolean removed = selectedTags.remove("archived");
if (removed) {
    System.out.println("Đã bỏ thẻ archived khỏi lựa chọn");
}
```

The two calls have distinct purposes:

- Check `"java"` to display selection state, so leave the set unchanged.
- Remove `"archived"` because the user actually requested to deselect it. Use the return value to know whether the operation changed the set.

There is no need to convert the set into a `List` or an array just to search for or remove a value. Such a conversion adds extra work and can obscure the set semantics of the data.

If the input is owned by another component, determine whether modifying it directly is permitted. A `Set<String>` parameter does not make this clear on its own. When the requirement is to produce a filtered result while keeping the input intact, create a separate working set and remove from that set:

```java
// Illustrative snippet; input is a Set<String> provided by the caller.
Set<String> result = new LinkedHashSet<>(input);
result.removeIf(tag -> tag.startsWith("draft:"));
// Use result as the output; do not structurally modify input.
```

The predicate in the last snippet assumes `input` does not contain `null`. If the input contract allows `null`, you must explicitly decide whether to keep or remove `null` and write the condition accordingly, rather than letting a `startsWith` call decide via an exception.

## 11. Common Mistakes and How to Self-Diagnose

| Symptom or misconception | Common cause | How to fix the mental model or code |
| --- | --- | --- |
| "remove returns the removed element" | Confusing with an API that has a different contract | Read the signature: `Set.remove` returns `boolean` |
| `Set<Integer>.remove(1)` is thought to remove the second position | Carrying List's index model over to Set | Set has no indices; the argument is the value to remove |
| Same field contents but contains returns false | Class has not defined value-based equality, or hashCode does not match equals | Design and test the equality contract |
| Changing an identifying field then failing to find/remove as expected | Element changed its equality or ordering rules while inside the set | Use immutable keys and an explicit update procedure |
| Integer set does not find a Long query | Different wrapper types; equals does not consider them equal | Standardize the query data type |
| TreeSet finds strings differing in case | Comparator returns 0 | Check the Comparator and its consistency with equals |
| Querying null throws an exception | Implementation or comparator does not accept null | Read the contract of the set type in use |
| Removing from Set.of throws an exception | The set is unmodifiable | Create a modifiable working set if appropriate |
| removeIf deletes the opposite of what you want to keep | Mistaking true for "keep" | In removeIf, true means remove |
| retainAll removes more than expected | Mistaking the argument set for the list to remove | retainAll keeps only elements present in the argument |
| Direct for-each and remove causes errors | Structural modification through a path other than the active iterator | Use Iterator.remove or removeIf as appropriate |
| Seeing no ConcurrentModificationException and assuming the loop is correct | Treating fail-fast as proof of correctness | Follow the iteration contract; do not rely on error detection |

When `contains` or `remove` yields an unexpected result, check in order: the actual set type; the argument's type; the `equals`/`hashCode` or `Comparator` rules; whether the element was mutated while in the set; and whether the set is modifiable. This sequence is usually more helpful than adding a manual loop to "search again."

## 12. Practice and Verification

### Exercise 1: Predict Results Without Using Indices

Start with:

```java
Set<Integer> values = new LinkedHashSet<>(List.of(10, 20, 30));
```

Execute sequentially and record the return value of each expression along with the set's state afterward:

```java
values.contains(20);
values.remove(1);
values.remove(20);
values.containsAll(List.of(10, 10));
values.retainAll(Set.of(30));
values.removeIf(value -> value > 25);
```

Check against:

| Expression | Result | Set after expression |
| --- | --- | --- |
| `contains(20)` | `true` | `[10, 20, 30]` |
| `remove(1)` | `false` | `[10, 20, 30]` |
| `remove(20)` | `true` | `[10, 30]` |
| `containsAll(List.of(10, 10))` | `true` | `[10, 30]` |
| `retainAll(Set.of(30))` | `true` | `[30]` |
| `removeIf(value -> value > 25)` | `true` | `[]` |

Key point to explain: `remove(1)` does not remove `20`, because a set has no concept of "the element at index 1." Requesting `10` twice in `containsAll` also does not require two copies.

### Exercise 2: Choose the Right Method

For a modifiable set of tags:

1. Check only whether the `"java"` tag is present, without changing the selection.
2. Remove the `"old"` tag if present and know whether the selection changed.
3. Remove every tag in a `blockedTags` set.
4. Keep only tags belonging to `allowedTags`.
5. Remove tags with the `"temp:"` prefix, given input guaranteed to have no `null`.

The answers are `contains`, `remove`, `removeAll`, `retainAll`, and `removeIf`, respectively. Be able to state the purpose of each return value; only the `contains` query leaves the set unchanged.

### Exercise 3: Find the Root Cause Before Fixing

A set holds `AccountKey` objects. Two objects have the same code, yet `contains` returns `false`. Ask these questions before writing fix code:

- Is this a `HashSet`, `LinkedHashSet`, `TreeSet`, or another implementation?
- Does the class define `equals` and `hashCode` according to the intended code semantics?
- If using `TreeSet`, is the comparison consistent with equality?
- Was any field involved in element identity modified after insertion?
- Do the type and normalized form of the query code match the stored data?

You cannot choose the right patch from the symptom "`contains` returns `false`" alone. You must establish the element identity rules first; only then do `contains` and `remove` have stable semantics.
