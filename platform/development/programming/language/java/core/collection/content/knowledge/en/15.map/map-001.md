# Unique Keys, Duplicate Values, and Mapping Semantics

## 1. Map Answers the Question "What Can Be Found from This Key?"

Suppose an application manages employees' teams:

```text
emp-1 → Backend
emp-2 → Backend
emp-3 → Data
```

Given the ID `emp-2`, the application wants to immediately find the corresponding team. The employee ID acts as the **key**; the team name is the **value**. Each line is a **mapping** from one key to one value.

In Java, `Map<K, V>` describes that structure:

```java
Map<String, String> teamByEmployee;
```

This is an illustrative declaration; `java.util.Map` must be imported. The first type is the key type, and the second type is the value type. Both types can be the same while still having different roles.

The first three principles:

- In a map, one key identifies at most one current mapping.
- Multiple different keys can map to equal values.
- Looking up by key does not automatically turn into a reverse lookup from a value back to a single unique key.

This lesson explains those three principles, how they appear in basic operations, and how to choose a model when a single key needs to hold a group of data.

## 2. Unique Keys Do Not Mean All Data Is Unique

### 2.1. Each Key Holds Only One Current Value

With `emp-1 → Backend`, if you then write `emp-1 → Platform` into a map that supports updates, the current result is:

```text
emp-1 → Platform
```

The map does not simultaneously hold two separate mappings `emp-1 → Backend` and `emp-1 → Platform`. If you need a history of old and new teams, you must design a separate history data structure; a simple map does not automatically retain overwritten history.

"At most one" also includes the case where the key does not yet exist. Not every possible value of type `K` is required to be present in the map.

### 2.2. Two Keys Can Have the Same Value

Two mappings:

```text
emp-1 → Backend
emp-2 → Backend
```

are completely valid. There is no requirement that a team name belongs to only one employee.

Here there are two keys, two mappings, and two occurrences of the value `Backend`. If you only count distinct team names, there is one team name, but that is a different statistic.

Do not assume `size()` equals the number of distinct values. `Map.size()` counts the number of key–value mappings.

### 2.3. Mapping Direction Matters

The structure:

```java
Map<String, String> teamByEmployee;
```

expresses "each employee has one current team." If you change it to "each team has many employees," a plain `Map<String, String>` with the team name as the key is usually not enough.

Reversing the arrow is a model change, not just a variable rename:

```text
Employee → Current team
Team     → List of employees
```

Because values can be duplicated, the original relationship is not necessarily one-to-one. Therefore, there is no single unique reverse key from just a team name.

The foundational contract of the interface and its three collection views are described in [Map Java 17](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/Map.html).

## 3. When Are Two Keys Considered the Same Key?

### 3.1. With HashMap and LinkedHashMap, It Is Not Just Reference Equality

Two different `String` objects can hold the same content:

```java
String first = "emp-1";
String second = new String("emp-1");
```

In this context:

```text
first == second       is false
first.equals(second)  is true
```

With `HashMap` or `LinkedHashMap`, those two `String` keys represent the same key under equality. Calling `put` with `second` updates the mapping whose key equals `first`; it does not create an extra employee just because the `String` object was created with `new`.

The example code below uses `new String` only to clarify the difference between reference and value, not as the usual way to create employee IDs.

### 3.2. Matching hashCode Is Not Enough to Be the Same Key

Hash-table-based maps use `hashCode` to support lookup, but they do not treat every key with the same hash code as equal.

For example, the two strings `"Aa"` and `"BB"` can have the same hash code without being equal. A `HashMap` can still hold mappings for both.

The rule for custom keys must be consistent: if two keys are equal according to `equals`, they must have the same `hashCode`. The reverse is not required.

Do not use a hash function as a "guaranteed unique identifier" just because it makes lookup fast. Hash codes can collide; keys still need an equality rule that matches the data domain.

The class properties regarding equality, `null`, and ordering are documented in [HashMap Java 17](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/HashMap.html).

### 3.3. Ordered Maps Also Require Reading the Class Rules

`TreeMap` determines key equivalence in ordering via `compareTo` or a comparator. Two keys that compare as `0` are treated as the same key in that map.

For example, a case-insensitive comparator may treat `"Code"` and `"code"` as the same key position, even though `String.equals` on the two strings is `false`. In that case, writing the second key can replace the value at the existing key.

To obey the general equality-based `Map` contract, a `TreeMap`'s ordering rule should be consistent with `equals`. See [TreeMap Java 17](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/TreeMap.html).

Therefore, the statement "unique keys" must go with "according to which key-identification rule of the structure being used?" Do not use an experiment on one class to assume every `Map` class shares the same specific policy.

### 3.4. Uniqueness Applies Only Within the Map Under Consideration

Two independent maps can both contain the key `emp-1`, each holding a different value. A `Map` does not enforce uniqueness across an entire program or a database.

If employee IDs are only unique within each organization, a map aggregating multiple organizations may need a composite key such as `(organizationId, employeeId)`. Using `employeeId` alone can accidentally overwrite data from another organization.

A `record` type with immutable identity components often helps express a composite key clearly. A key must reflect the exact domain it needs to distinguish, not just be short enough to type conveniently.

## 4. put: Adding a New Key or Replacing an Existing Key's Value

### 4.1. Two Cases That Affect size Differently

On a modifiable map:

| Before command | Command | After command | Size change |
| --- | --- | --- | --- |
| No `emp-1` | `put("emp-1", "Backend")` | Has `emp-1 → Backend` | Increases by 1 |
| Has `emp-1 → Backend` | `put("emp-1", "Platform")` | Has `emp-1 → Platform` | Unchanged |
| Has `emp-1 → Platform` | `put("emp-2", "Platform")` | Also has `emp-2 → Platform` | Increases by 1 |

An equal value in the last row does not prevent adding a new key. Conversely, a completely different new value in the middle row still does not create a second key.

### 4.2. The Return Value of put Is the Old Value

`put(key, value)` returns the previous value associated with the key, or `null` when there was no old value. For maps that allow `null` values, a `null` return value can also come from an existing mapping whose value was `null`.

Example:

```java
// Illustrative snippet; map is modifiable and initially does not contain emp-1.
String old1 = map.put("emp-1", "Backend");  // null
String old2 = map.put("emp-1", "Platform"); // "Backend"
```

Do not rely solely on `old == null` to prove that the key definitely did not exist previously, if the map class allows `null` values.

If business logic needs to distinguish "create new" from "update" in a single-threaded example, you can check key existence before writing. A check-then-write sequence does not automatically become an atomic operation for multiple threads.

### 4.3. Writing the Same Value Again Adds No History

Calling `put("emp-1", "Backend")` again when the key already maps to `Backend` still keeps one mapping for `emp-1`. It does not record that "the employee was assigned to Backend twice."

A `Map` represents the current association state. If the requirement is to record assignment events, you need a list of events or a suitable structure to store multiple occurrences.

## 5. get, containsKey, and containsValue Answer Three Different Questions

| Method | Question |
| --- | --- |
| `get(key)` | What value is currently associated with this key? |
| `containsKey(key)` | Does the map have a mapping for this key? |
| `containsValue(value)` | Is there at least one key currently mapping to a value equal to the target? |

With `emp-1 → Backend` and `emp-2 → Backend`:

- `get("emp-1")` returns `Backend`.
- `containsKey("Backend")` does not mean "find the Backend team"; `Backend` is on the value side.
- `containsValue("Backend")` can return `true`, but it does not return `emp-1`, `emp-2`, or the number of employees.

A variable name like `teamByEmployee` helps clarify the mapping direction. A variable named `data` makes it easy for readers to confuse "are we using the ID or the team name as the key?"

### Null from get Has Two Possibilities

For a map that allows `null` values:

```text
Case A: key emp-4 does not exist
Case B: key emp-4 exists, and its current value is null
```

Both can produce `get("emp-4") == null`. `containsKey("emp-4")` distinguishes them.

| State | get | containsKey | Counted by size? |
| --- | --- | --- | --- |
| Key absent | `null` | `false` | No |
| Key present mapped to null | `null` | `true` | Yes |
| Key present mapped to non-null value | That value | `true` | Yes |

Do not automatically unbox a potentially `null` result into a primitive type, such as `int count = map.get(key)` on a `Map` with `Integer` values, before deciding how to handle missing data.

`null` here is a capability of the implementation class, not a requirement that every `Map` must support it.

## 6. Runnable Program: Unique Keys and Duplicate Values

Save as **MapKeyValueDemo.java**:

```java
import java.util.LinkedHashMap;
import java.util.Map;

public class MapKeyValueDemo {
    public static void main(String[] args) {
        Map<String, String> teamByEmployee = new LinkedHashMap<>();
        teamByEmployee.put("emp-1", "Backend");
        teamByEmployee.put("emp-2", "Backend");
        teamByEmployee.put("emp-3", "Data");

        System.out.println("initial map: " + teamByEmployee);
        System.out.println("mapping count: " + teamByEmployee.size());
        System.out.println("keys: " + teamByEmployee.keySet());
        System.out.println("values: " + teamByEmployee.values());
        System.out.println("contains key Backend: " + teamByEmployee.containsKey("Backend"));
        System.out.println("contains value Backend: " + teamByEmployee.containsValue("Backend"));
        System.out.println("get emp-1: " + teamByEmployee.get("emp-1"));

        System.out.println("old team: " + teamByEmployee.put("emp-1", "Platform"));
        System.out.println("size after replacement: " + teamByEmployee.size());

        String anotherKey = new String("emp-1");
        System.out.println("same key reference: " + (anotherKey == "emp-1"));
        System.out.println("equal key value: " + anotherKey.equals("emp-1"));
        System.out.println("old team using equal key: "
                + teamByEmployee.put(anotherKey, "Security"));
        System.out.println("map after equal key: " + teamByEmployee);

        teamByEmployee.put("emp-4", null);
        System.out.println("get emp-4: " + teamByEmployee.get("emp-4"));
        System.out.println("contains emp-4: " + teamByEmployee.containsKey("emp-4"));
        System.out.println("get missing: " + teamByEmployee.get("missing"));
        System.out.println("contains missing: " + teamByEmployee.containsKey("missing"));

        System.out.println("removed emp-2 value: " + teamByEmployee.remove("emp-2"));
        System.out.println("contains Backend after removal: "
                + teamByEmployee.containsValue("Backend"));
        System.out.println("final map: " + teamByEmployee);
        System.out.println("final size: " + teamByEmployee.size());
    }
}
```

Compile and run:

```shell
javac --release 17 -encoding UTF-8 MapKeyValueDemo.java
java MapKeyValueDemo
```

Exact stdout:

```text
initial map: {emp-1=Backend, emp-2=Backend, emp-3=Data}
mapping count: 3
keys: [emp-1, emp-2, emp-3]
values: [Backend, Backend, Data]
contains key Backend: false
contains value Backend: true
get emp-1: Backend
old team: Backend
size after replacement: 3
same key reference: false
equal key value: true
old team using equal key: Platform
map after equal key: {emp-1=Security, emp-2=Backend, emp-3=Data}
get emp-4: null
contains emp-4: true
get missing: null
contains missing: false
removed emp-2 value: Backend
contains Backend after removal: false
final map: {emp-1=Security, emp-3=Data, emp-4=null}
final size: 3
```

The program uses a default `LinkedHashMap` so that print order deterministically follows key insertion order. Replacing the value of an existing key does not automatically move that key to the end in this configuration. See [LinkedHashMap Java 17](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/LinkedHashMap.html).

Do not treat this print order as a guarantee of `HashMap` or of every `Map`. Key uniqueness and ordering policy are two separate properties.

Key points to note:

- The three initial mappings have only two distinct team names.
- The value `Backend` appears twice in `values()`.
- Replacing `emp-1`'s team does not change `size()`.
- The newly created `String` key still updates `emp-1` because its content is equal.
- `emp-4` has a `null` mapping, whereas `missing` has no mapping.
- Removing `emp-2` does not remove any other employee. `Backend` no longer appears because `emp-1` was previously changed to `Security`.

The programs in this lesson were compiled with `--release 17` and run on OpenJDK 24.0.2. That flag checks the target Java 17 language/API and produces matching bytecode; the JVM used to run them is the version stated.

## 7. Three Views of the Same Set of Mappings

`Map` does not extend the `Collection` interface. It provides collection views to read keys, values, or pairs:

| View | Return type | What to remember |
| --- | --- | --- |
| `keySet()` | `Set<K>` | Keys do not repeat under the map's rule |
| `values()` | `Collection<V>` | Values can appear multiple times |
| `entrySet()` | `Set<Map.Entry<K,V>>` | Each entry pairs one key with its corresponding value |

For the example:

```text
map:      {emp-1=Backend, emp-2=Backend, emp-3=Data}
keys:     [emp-1, emp-2, emp-3]
values:   [Backend, Backend, Data]
entries:  emp-1=Backend; emp-2=Backend; emp-3=Data
```

Two entries with the same `Backend` value are still distinct because their keys differ. `entrySet()` is a set of mapping pairs; it does not mean the values must be unique.

### Views Are Not Automatically Independent Copies

On maps that support updates, these views are backed by the map's data. Changes to the map can be reflected through the view; certain supported removal operations on the view also remove the corresponding mapping.

Therefore, calling `values().remove("Backend")` does not merely remove a string from a temporary list. If supported, it can remove a mapping that carries that value. When multiple equal values exist, do not use this operation to target a specific employee; removing by key expresses the intent more clearly.

Likewise, do not use `keySet().add(key)` as a way to add a mapping: having only a key is not enough to determine the associated value. If you need a detached structure for separate processing, create an appropriate copy and remember that copying the structure does not automatically deep-copy the element objects.

## 8. Reverse Lookup Can Return Multiple Keys

If the question is "who belongs to the Backend team?", a single unique result is not guaranteed. There may be nobody, one person, or many people.

The following illustrative method is placed inside a class and requires importing `Map`, `List`, `ArrayList`, and `Objects`:

```java
static List<String> employeesInTeam(
        Map<String, String> teamByEmployee, String targetTeam) {
    List<String> result = new ArrayList<>();
    for (Map.Entry<String, String> entry : teamByEmployee.entrySet()) {
        if (Objects.equals(entry.getValue(), targetTeam)) {
            result.add(entry.getKey());
        }
    }
    return result;
}
```

The method returns all keys whose value matches. `Objects.equals` handles cases where either the value or the target is `null` in a map that allows `null`.

The result order follows the iteration order of the source map's entries. If the source is a `HashMap`, this method alone does not guarantee a fixed order of employee IDs. If the output must be sorted by ID, you must add an explicit sorting step.

For typical hash-table-based maps, looking up by key is optimized compared to scanning for an arbitrary value. Do not assume `containsValue` or a reverse-lookup function has the same lookup characteristics as `get(key)`.

If team → employee lookups happen frequently, you may need a reverse index such as a `Map` of team → list of employees. In that case, the application must keep the indexes consistent whenever an employee changes teams. A `Map` does not automatically maintain the relationship between two separate structures.

## 9. One Key Needing Multiple Data Items: Mapping to a Group

### 9.1. Calling put Twice Does Not Turn a Map into a Multimap

If you write:

```java
// Illustrative snippet:
Map<String, String> courseByStudent = new LinkedHashMap<>();
courseByStudent.put("S1", "Java");
courseByStudent.put("S1", "SQL");
```

then `S1` maps to `SQL`. `Java` is no longer `S1`'s current value in that map. Renaming the variable to `coursesByStudent` does not change the behavior of the data type.

### 9.2. A Value Can Be a Collection

If a student needs multiple courses, you can use:

```java
Map<String, List<String>> coursesByStudent;
```

`S1` still has **one value**: a single `List` object. The list inside holds multiple courses.

```text
S1 → [Java, SQL]
S2 → [Java]
```

There are two mappings, even though the total number of elements across the lists is three. This does not violate unique keys.

The proper way to update is to look up the key's list and add an element to that list, or create a new list according to application policy. Calling `put` to replace the entire list with a new list is still replacing the value of a single key.

If you want a student not to have duplicate courses, consider a `Set` value type; if you need to preserve repeated enrollments and order, `List` has different semantics. `Map` does not choose the rules inside the value collection for you.

### 9.3. Duplicate Values and Shared Objects Are Two Different Things

Two keys can hold two separate lists that have equal content. Two keys can also hold the exact same list object.

In the shared case, modifying the list through one reference changes the content seen from both keys. `Map` stores references; it does not automatically copy the payload for each key.

If business logic requires independent lists, you must create a separate object for each value or use an appropriate immutable data policy. Do not blame duplicate keys when the real issue is that multiple keys point to the same mutable payload.

## 10. Runnable Program: Single Value, List Value, and Shared Reference

Save as **MappingGroupsDemo.java**:

```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class MappingGroupsDemo {
    private static void addCourse(
            Map<String, List<String>> coursesByStudent,
            String student, String course) {
        List<String> courses = coursesByStudent.get(student);
        if (courses == null) {
            courses = new ArrayList<>();
            coursesByStudent.put(student, courses);
        }
        courses.add(course);
    }

    public static void main(String[] args) {
        Map<String, String> oneCourse = new LinkedHashMap<>();
        oneCourse.put("S1", "Java");
        System.out.println("old course when replacing: " + oneCourse.put("S1", "SQL"));
        System.out.println("single-value map: " + oneCourse);
        System.out.println("single-value mapping count: " + oneCourse.size());

        Map<String, List<String>> coursesByStudent = new LinkedHashMap<>();
        addCourse(coursesByStudent, "S1", "Java");
        addCourse(coursesByStudent, "S1", "SQL");
        addCourse(coursesByStudent, "S2", "Java");
        System.out.println("grouped map: " + coursesByStudent);
        System.out.println("grouped mapping count: " + coursesByStudent.size());
        int courseCount = 0;
        for (List<String> courses : coursesByStudent.values()) {
            courseCount += courses.size();
        }
        System.out.println("total course entries: " + courseCount);

        List<String> shared = new ArrayList<>(List.of("Java"));
        Map<String, List<String>> sharedValues = new LinkedHashMap<>();
        sharedValues.put("S1", shared);
        sharedValues.put("S2", shared);
        shared.add("SQL");
        System.out.println("shared value after change: " + sharedValues);
        System.out.println("same value reference: "
                + (sharedValues.get("S1") == sharedValues.get("S2")));

        Map<String, String> fixed = Map.of("S1", "Java", "S2", "Java");
        System.out.println("Map.of duplicate values size: " + fixed.size());
        try {
            Map.of("S1", "Java", "S1", "SQL");
        } catch (IllegalArgumentException ex) {
            System.out.println("Map.of duplicate keys: " + ex.getClass().getSimpleName());
        }
    }
}
```

Run commands:

```shell
javac --release 17 -encoding UTF-8 MappingGroupsDemo.java
java MappingGroupsDemo
```

Exact stdout:

```text
old course when replacing: Java
single-value map: {S1=SQL}
single-value mapping count: 1
grouped map: {S1=[Java, SQL], S2=[Java]}
grouped mapping count: 2
total course entries: 3
shared value after change: {S1=[Java, SQL], S2=[Java, SQL]}
same value reference: true
Map.of duplicate values size: 2
Map.of duplicate keys: IllegalArgumentException
```

The `addCourse` method in the program creates a list when one does not yet exist, then adds the course to the list. All list values managed by this method are non-null. This is a single-threaded example; the check/create/add sequence is not presented as an atomic group operation for multiple threads.

The section using `shared` creates two mappings to the same list, so after adding `SQL` both `S1` and `S2` see `Java, SQL`. This is intentional payload sharing for illustration, unlike the independent-group structure in the previous section.

The `Map.of` section shows that two situations must be distinguished:

- Two different keys with the same value `Java` is valid.
- Passing two equal `S1` keys into a single `Map.of` creation call is rejected with `IllegalArgumentException`.

`Map.of` creates an unmodifiable map, so there is no "later key overwrites earlier key's value" rule in this factory call. `put` behavior on a modifiable map and duplicate-key checking when creating an immutable map are two different contracts.

## 11. Nulls and Modifiability Depend on the Map Class

### 11.1. There Is No Single Null Policy for Every Map

`HashMap` and `LinkedHashMap` allow `null` keys and `null` values. A `null` key is still one key: writing `null` again replaces the value associated with that key; it does not create multiple independent `null` keys.

Multiple different keys can hold the value `null`, just like holding `Backend`. Each mapping is still counted by `size()`.

`Map.of` does not allow `null` keys or `null` values. Do not use a `HashMap` example to assume another factory or map class must accept `null`.

If business logic does not want a "key exists but has no value yet" state, you can forbid `null` at the data-ingestion layer. That is a design policy that simplifies lookups, not something every `Map` enforces by itself.

### 11.2. Unique Keys Do Not Mean a Map Is Always Updatable

An unmodifiable map still has unique keys and can have duplicate values. Attempting to call `put`/`remove` on a structure that does not support modification can throw `UnsupportedOperationException`.

When explaining "`put` replaces the old key's value," the contextual condition is that you are using a map that supports updates. Do not call an API with the same name while ignoring the modifiability of the actual object.

Similarly, `null` handling, iteration order, and concurrent access capability are properties you must read from the concrete class. The `K → V` interface does not decide all of those policies on its own.

## 12. Choosing Meaningful Keys and Keeping Identification Rules Stable

### 12.1. Duplicate Values Can Fit the Model Perfectly

Person names, departments, statuses, or grade levels can repeat across many records. You should not force them to be unique just to "fit a map."

For example, using a person's name as a key can cause two people with the same name to overwrite each other. If business logic needs to distinguish them, choose a proper identifier instead of concluding that `Map` cannot hold two people.

Conversely, if policy truly allows only one current configuration per configuration code, having `put` with the same key replace the value may be exactly what is intended.

Write a sentence before choosing the types:

```text
Within the scope of ..., each ... key identifies at most one ...
```

If that sentence does not hold for real data, you need to change the key, the scope, or the value structure.

### 12.2. Do Not Mutate Identifying Fields While a Key Is in a Map

For custom keys, changing a field that participates in `equals` or `hashCode` after the key has been placed into a map can prevent the map from finding the key as the author expects. The `Map` contract leaves behavior undefined if a key is mutated in a way that affects equality while it is being used as a key.

Prefer keys with stable identifying components. A `record` only helps if the identifying components inside it also retain stable semantics; a `record` containing a mutable object does not automatically create deep immutability.

If an identifier must change, perform an explicit mapping-transfer procedure with the old key and new key according to application requirements. Do not rely on mutating a field and expecting the structure to rebuild all its indexes automatically.

### 12.3. Map Does Not Enforce Business Rules on Values

Multiple keys having the same value is valid at the structural level. If business logic requires an email address to belong to only one person, `Map<Id, Email>` does not automatically forbid two `Id`s from having the same `Email`.

You may need additional validation or an index model keyed by email. You also need to decide normalization rules for emails or codes before enforcing uniqueness; `Map` does not understand domain semantics just from the type name `String`.

Do not equate "structurally allowed" with "business-accepted." Understanding keys and values helps you know which constraints already exist and which ones still need to be designed.

## 13. Common Mistakes and How to Diagnose Them

| Symptom | Wrong assumption or cause | How to fix |
| --- | --- | --- |
| Second write loses the old value | Expected `Map` to keep multiple independent values for one key | Use a collection as the value or store history separately |
| `size` is smaller than the number of `put` calls | Equivalent keys were updated | Count new keys instead of counting calls |
| Two employees in the same team treated as an error | Confused key uniqueness with value uniqueness | Allow duplicate values as modeled |
| `get` with team name does not find employees | Looked up in reverse on the key side | Iterate over entries or maintain a reverse index |
| `get` returns `null`, so concluded key is absent | Ignored stored `null` values | Use `containsKey` when distinction is needed |
| Created a new `String` but still overwrote | Confused same key with same reference | Read the key's equality rule |
| Two keys with the same hash assumed to be one | Confused hash code with unique identifier | Check `equals` and the `hashCode` contract |
| Two lists change together | Two keys share the same payload | Create separate lists when independence is needed |
| `put` on `Map.of` fails | Ignored unmodifiable map | Choose the right structure for mutability needs |
| Key mutated and then cannot be looked up | Identification rule changed after insertion | Use stable keys and update mappings explicitly |

## 14. Self-Check Exercises with Solutions

### Exercise 1: Counting Mappings

An empty modifiable map receives `A → 10`, `B → 10`, `A → 20` in order. What are the final `size` and mappings?

**Solution:** `size` is 2. `A` maps to `20`, `B` maps to `10`. The first two calls create two keys; the last call replaces the value of `A`.

### Exercise 2: New Key or New Object?

A `HashMap` contains the `String` key `"id-1"`. Does writing again with `new String("id-1")` necessarily increase `size`?

**Solution:** No. The two `String`s have equal content, so they represent the same key in the `HashMap`. A newly created key object does not mean a new logical identity.

### Exercise 3: From Value Back to Key

Given `A → Backend` and `B → Backend`. Does `containsValue("Backend")` return `A`? Can you build a reverse map `Backend → single String` that preserves both employees?

**Solution:** `containsValue` returns a `boolean`, not `A`. A reverse map with a single `String` as the value holds only one current value for `Backend`, so you need a grouped form such as `Backend → list of employees` if you want to keep both `A` and `B`.

### Exercise 4: Key Present with Null Value

A `HashMap` contains `A → null`. What are `get("A")`, `containsKey("A")`, and `size` respectively?

**Solution:** `null`, `true`, and `1`. A `null` value does not erase the existence of the mapping. An absent key `B` also gives `get` equal to `null`, but `containsKey` is `false`.

### Exercise 5: How Many Map Values Is One List?

A `Map` contains `S1 → [Java, SQL]` and `S2 → [Java]`. Does the `Map` violate one-key-one-value? What is `size`?

**Solution:** No violation. Each key maps to one list object. `size` is 2; the total number of course elements across the lists is 3 and is counted by a different calculation.

### Exercise 6: Two Keys Pointing to One List

`A` and `B` both point to the same `ArrayList` initially containing `Java`. Add `SQL` to the list via `A`. Does `B` see `SQL`?

**Solution:** Yes, because both mappings use the same value object. Key uniqueness does not automatically copy the payload. If independence is needed, separate lists must be created.

### Exercise 7: Map.of and Duplicate Values

Is `Map.of("A", 1, "B", 1)` valid? What about `Map.of("A", 1, "A", 2)`?

**Solution:** The first case is valid, having two mappings with the same value `1`. The second case is rejected due to duplicate keys. This is a factory creation-time check, unlike `put` replacing a value on a modifiable map.

### Exercise 8: Scope of Identity

Two organizations both have an employee with ID `001`. A system-wide map using only ID `001` as the key loses one record after `put`. Is `Map` behaving incorrectly?

**Solution:** The structure is correctly enforcing the one-key-one-current-value rule. The key model is missing the organization scope. You may need a composite key of organization + employee ID, or a separate map per organization.
