# computeIfAbsent, computeIfPresent, compute, and null Results

## 1. From Reading a Value to Deciding the Next Mapping

Many operations on a `Map` do more than read a value; they must decide what to store next: initialize a list for a group, increment a counter, decrement inventory, or remove an expired state.

If you manually write each step—`get`, check, compute, then `put` or `remove`—the update intent easily becomes scattered. The `compute` family of methods lets you place the rule for computing the new value into a function that the Map invokes at the appropriate time.

The three method names look very similar, but they differ on two questions:

1. When is the computation function called?
2. If the computation function returns `null`, does the map keep, add, or remove the mapping?

The second question is especially important. In these methods, `null` returned from a computation function is usually an update-control instruction; it does not simply mean "store the null value."

This lesson uses `HashMap` under sequential access to clarify the possible states, then distinguishes the concurrency guarantees of each implementation. Do not infer that a call named `compute` on any `Map` is automatically thread-safe.

## 2. Foundation: Having a Key Does Not Guarantee a Non-null Value

With a `HashMap<String, Integer>`, a key `k` can be in three states:

~~~text
A: key k is absent.
N: key k is present, stored value is null.
V: key k is present, stored value is a non-null Integer.
~~~

For example, when the non-null value is 5:

| Prior state | containsKey(k) | get(k) |
| --- | --- | --- |
| A — key absent | false | null |
| N — key present with null | true | null |
| V — key present with 5 | true | 5 |

`HashMap` allows state N. Another class such as `ConcurrentHashMap` does not allow storing null values, so it does not have that stored state. [HashMap Documentation, Java 17](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/HashMap.html).

The names "Absent" and "Present" in the two methods do not merely check `containsKey`:

- `computeIfAbsent` treats both A and N as needing a value to be computed.
- `computeIfPresent` calls the function only when in V, meaning a non-null value already exists.
- `compute` runs the computation rule in A, N, and V whenever the call is valid.

Therefore, do not mechanically translate `computeIfPresent` as "call the function whenever the key exists." A mapping currently holding null has an actual key, but it does not satisfy this method's condition of "a present, non-null value."

## 3. Signatures and the Data Received by the Computation Function

Simplified signatures showing the type contracts:

~~~java
V computeIfAbsent(
        K key,
        Function<? super K, ? extends V> mappingFunction);

V computeIfPresent(
        K key,
        BiFunction<? super K, ? super V, ? extends V> remappingFunction);

V compute(
        K key,
        BiFunction<? super K, ? super V, ? extends V> remappingFunction);
~~~

These are method signatures for reading the contract, not a standalone Java file.

`Function` takes one argument: the key. That is sufficient for creating a value from the key when no non-null value exists yet.

`BiFunction` takes two arguments: the key and the old value. With `computeIfPresent`, the function is only called when the old value is non-null. With `compute`, the old value may be null either because the key is absent or because the key is currently mapped to null.

All three methods return the post-processing value according to their contracts, rather than uniformly returning the old value as `put` does. If the return value is null, knowing whether a mapping remains requires considering the method and state, not just looking at the return value alone.

The computation function passed in must be non-null. Support for null keys, mutability, and other restrictions depend on the Map implementation. Do not use a null computation function to represent "do nothing"; choose the appropriate method or return a meaningful result from a valid function.

## 4. computeIfAbsent: Create When No Non-null Value Exists

Example of grouping items by group name:

~~~java
groups.computeIfAbsent("A", key -> new ArrayList<>()).add("first");
~~~

If A does not yet have a list, the function creates an `ArrayList` and stores it in the Map. If A already has a non-null list, the function is not called; the method returns the existing list, and `add` appends the item to that list.

For sequential data, read the rule as three branches:

| Prior state of k | Is the function called? | What does the function receive? |
| --- | --- | --- |
| k is absent | Yes | Key k |
| k is present with null | Yes | Key k |
| k is present with non-null value x | No | No invocation |

When the function is called:

- Returns a non-null value y: y is stored as the value for k and returned to the caller.
- Returns null when k was absent: no new mapping is created.
- Returns null when k already had a null value: the old null mapping remains in the HashMap example; the method does not automatically remove it.

When k already has a non-null value x, the result is x. Any "intended return value" inside the function has no effect because the function is not executed.

These rules regarding invocation conditions and null results are part of the `Map.computeIfAbsent` contract. [Map Documentation, Java 17](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/Map.html#computeIfAbsent(K,java.util.function.Function)).

### Lazy Creation and Caching Not-Found Results

The computation function only runs when the condition requires it, so it can avoid creating a new object if a value already exists. However, do not infer that it runs "exactly once for the lifetime of the key."

If the first call returns null without creating a mapping, the next call will still need to compute the key. If a computation throws an exception or the mapping is later removed, a subsequent call can also invoke the function again.

With a loader that can return null, the following chained call risks failing:

~~~java
map.computeIfAbsent(key, k -> loadList(k)).add(item);
~~~

This is an illustrative snippet where the variables and function are defined in the surrounding context. If `loadList` returns null, the result of `computeIfAbsent` can also be null; calling `add` will throw a `NullPointerException`.

If the goal is to always have a collection to add to, the factory function should always return an appropriate non-null object. If the goal is to represent "loaded but found nothing," you need a value that models that state rather than expecting `computeIfAbsent` to store a new null to remember it.

## 5. computeIfPresent: Update Only an Existing Non-null Value

Example of decrementing an existing counter:

~~~java
Integer updated = counts.computeIfPresent(
        "single", (key, old) -> old == 1 ? null : old - 1);
~~~

This illustrative snippet assumes the counters are positive. When the value is 1, the business rule in the example chooses to remove the mapping instead of keeping a 0 counter. That is the computation function's decision, not an automatic Map behavior for all zeros.

| Prior state of k | Is the function called? | Old value passed in |
| --- | --- | --- |
| k is absent | No | No invocation |
| k is present with null | No | No invocation |
| k is present with non-null x | Yes | x |

If called:

- Returns non-null y: replaces the value with y and returns y.
- Returns null: removes the mapping for k and returns null.

If not called, the state is not modified by the method. Therefore, for a key currently mapped to null, `computeIfPresent` returns null, yet the key can still remain. It does not remove keys with null values simply because the method name contains "Present."

The computation function of `computeIfPresent` receives a non-null old value, so unboxing an `Integer old` inside this function will not fail due to `old` being null in a contract-compliant call. However, the overall method's return value can still be null when the condition is not met or when the function decides to remove the entry; assigning the result directly to an `int` can still fail.

Distinguish between null as an input to the computation function, null returned by the function, and null returned by the overall method. They occur at different points in the process.

## 6. compute: A Unified Decision for Creating, Replacing, and Removing

Example of incrementing word frequency or creating a counter for the first time:

~~~java
counts.compute(word, (key, old) ->
        old == null ? 1 : Math.addExact(old, 1));
~~~

For a key that is absent or currently mapped to null, `old` is null, so the rule chooses 1. For an existing count, the rule produces the count incremented by one. `Math.addExact` prevents the increment from silently overflowing the `int` range; if it overflows, it throws an exception instead of storing an incorrect number.

State rules for `compute`:

| Prior state | `old` argument | Function returns non-null y | Function returns null |
| --- | --- | --- | --- |
| Key absent | null | Create k -> y | Remains absent |
| Present k -> null | null | Replace with k -> y | Remove k |
| Present k -> non-null x | x | Replace with k -> y | Remove k |

The most important difference is the case where a key maps to null: `compute(k, (key, old) -> null)` removes that key. It is not like `computeIfAbsent` returning null and leaving the old null mapping intact.

`compute` receives `old` as null for both an absent key and a null mapping. From the `old` parameter alone, the function cannot distinguish those two states. If business logic requires them to have different meanings, model the state with an explicit value type or design read/update operations with appropriate guarantees. Do not assume a null `old` always proves the key did not exist.

For a valid call on a map that allows updates, `compute`'s function is used to decide the result even when no value exists yet. That is not a general promise about how many times the function may be called across all concurrent implementations; a later section separates that contract clearly.

## 7. Comparison Table Focused on null

The table below applies to a sequential `HashMap`, a valid function, and no side-effect modifications to the Map during computation. `x` is a non-null old value.

| Method | Key absent | Key present -> null | Key present -> x |
| --- | --- | --- | --- |
| `computeIfAbsent` | Calls function | Calls function | Does not call, returns x |
| `computeIfPresent` | Does not call | Does not call | Calls function |
| `compute` | Calls function with old null | Calls function with old null | Calls function with old x |

If the function is configured to return null:

| Method | Initially absent | Initially null | Initially non-null x |
| --- | --- | --- | --- |
| `computeIfAbsent` | Remains absent | Keeps old null mapping | Does not call function, keeps x |
| `computeIfPresent` | Remains absent | Does not call function, keeps null mapping | Removes mapping |
| `compute` | Remains absent | Removes mapping | Removes mapping |

Do not say "all three remove the entry if they return null" while ignoring the invocation condition. With `computeIfPresent` in the null-value state, there is no invocation to return null from the function; the overall method returns null because there is no non-null value to process.

Nor should you say "returning null means there is no key after the call" for every method. The cells that keep the old null mapping are direct counterexamples.

If you intentionally want to store a new null mapping in a `HashMap`, `put(key, null)` is a different operation. Returning null from a compute function is not a general way to request storing null.

## 8. A Java 17+ Program Verifying All 18 Cases

The program creates a fresh `HashMap` for each combination so that an earlier case does not alter the input of a later case:

~~~text
3 methods
x 3 initial states
x 2 configured return results for the function: 9 or null
= 18 cases.
~~~

The stdout columns:

- `configured`: the value the function will return if called; does not assert that the function actually ran.
- `calls`: the number of times the function was actually called in this sequential case.
- `result`: the value returned by the Map method.
- `present` and `value`: the Map state after the call, read via `containsKey` and `get`.

The subsequent examples demonstrate group creation, counting, removal, a loader returning null, exceptions, and side effects on a value object. The `ConcurrentHashMap` section is run sequentially to verify null semantics, not as a multi-threaded contention test.

Save the file `MapComputeDemo.java`:

~~~java
import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;

public class MapComputeDemo {
    enum State { ABSENT, NULL_VALUE, VALUE }
    enum Operation { IF_ABSENT, IF_PRESENT, COMPUTE }

    static void runCase(Operation operation, State state, Integer replacement) {
        Map<String, Integer> map = new HashMap<>();
        if (state == State.NULL_VALUE) {
            map.put("k", null);
        } else if (state == State.VALUE) {
            map.put("k", 5);
        }
        int[] calls = {0};
        Integer result = switch (operation) {
            case IF_ABSENT -> map.computeIfAbsent("k", key -> {
                calls[0]++;
                return replacement;
            });
            case IF_PRESENT -> map.computeIfPresent("k", (key, old) -> {
                calls[0]++;
                return replacement;
            });
            case COMPUTE -> map.compute("k", (key, old) -> {
                calls[0]++;
                return replacement;
            });
        };
        System.out.println(operation + " " + state
                + " configured=" + replacement
                + " calls=" + calls[0]
                + " result=" + result
                + " present=" + map.containsKey("k")
                + " value=" + map.get("k"));
    }

    public static void main(String[] args) {
        for (Operation operation : Operation.values()) {
            for (State state : State.values()) {
                runCase(operation, state, 9);
                runCase(operation, state, null);
            }
        }

        Map<String, List<String>> groups = new HashMap<>();
        int[] creations = {0};
        groups.computeIfAbsent("A", key -> {
            creations[0]++;
            return new ArrayList<>();
        }).add("first");
        groups.computeIfAbsent("A", key -> {
            creations[0]++;
            return new ArrayList<>();
        }).add("second");
        System.out.println("group A=" + groups.get("A"));
        System.out.println("group creations=" + creations[0]);

        Map<String, Integer> counts = new HashMap<>();
        for (String word : List.of("java", "map", "java")) {
            counts.compute(word, (key, old) ->
                    old == null ? 1 : Math.addExact(old, 1));
        }
        System.out.println("counts java=" + counts.get("java")
                + " map=" + counts.get("map"));
        counts.put("single", 1);
        Integer afterDecrement = counts.computeIfPresent(
                "single", (key, old) -> old == 1 ? null : old - 1);
        System.out.println("decrement result=" + afterDecrement
                + " present=" + counts.containsKey("single"));

        Map<String, String> retry = new HashMap<>();
        int[] loads = {0};
        for (int i = 0; i < 2; i++) {
            retry.computeIfAbsent("missing", key -> {
                loads[0]++;
                return null;
            });
        }
        System.out.println("null loads=" + loads[0]
                + " present=" + retry.containsKey("missing"));

        Map<String, Integer> safeMapping = new HashMap<>();
        safeMapping.put("k", 5);
        try {
            safeMapping.compute("k", (key, old) -> {
                throw new IllegalStateException("failure");
            });
        } catch (IllegalStateException exception) {
            System.out.println("failed compute=" + exception.getMessage());
        }
        System.out.println("mapping after failure=" + safeMapping.get("k"));

        Map<String, List<String>> mutable = new HashMap<>();
        mutable.put("k", new ArrayList<>(List.of("old")));
        try {
            mutable.compute("k", (key, old) -> {
                old.add("changed");
                throw new IllegalStateException("failure after mutation");
            });
        } catch (IllegalStateException exception) {
            System.out.println("mutable compute=" + exception.getMessage());
        }
        System.out.println("value object after failure=" + mutable.get("k"));

        Map<String, Integer> concurrent = new ConcurrentHashMap<>();
        Integer noValue = concurrent.computeIfAbsent("k", key -> null);
        System.out.println("concurrent null result=" + noValue
                + " present=" + concurrent.containsKey("k"));
        concurrent.compute("k", (key, old) -> old == null ? 1 : old + 1);
        concurrent.compute("k", (key, old) -> old == null ? 1 : old + 1);
        System.out.println("concurrent sequential count=" + concurrent.get("k"));
        concurrent.computeIfPresent("k", (key, old) -> null);
        System.out.println("concurrent after removal=" + concurrent.containsKey("k"));
    }
}
~~~

### Reading Several Key Lines

`IF_ABSENT NULL_VALUE configured=null calls=1 ... present=true` proves the function ran and returned null, yet the old null mapping was not removed.

The `ConcurrentHashMap` group shows that a class that forbids storing null still accepts a function returning null with the meaning of "do not add or remove," rather than throwing an exception just because the function's result is null.


## 9. Applying the Right Method to Your Update Policy

### Initializing a Collection per Key

A familiar pattern:

~~~java
groups.computeIfAbsent(groupId, key -> new ArrayList<>()).add(item);
~~~

Each key needs its own collection. Do not pre-create a shared list outside and return that same list for every key, unless sharing is an explicit design goal. If A and B point to the same list, adding to A will also change the data read through B.

The factory function must fit the subsequent operation. Returning `List.of()` creates a list that does not allow adding elements; calling `add` afterward will fail. In the program, `new ArrayList<>()` is chosen specifically because the goal is to append elements to the group.

An existing null value at a group key will be replaced with the new list when the factory function returns non-null. If an old null carried a distinct business meaning, reconsider whether `computeIfAbsent` matches your desired policy.

### Modifying Only Objects That Already Have a Value

`computeIfPresent` is suitable when you do not want to create new data solely because an update request arrived—for example, decrementing the remaining uses of an existing item, or normalizing an existing string.

However, a stored null value will be skipped. If you want to clean up null mappings, `computeIfPresent` is not the tool that will invoke the function for them. You may need a removal or a filtering pass suited to the requirement.

### Unifying Counter Creation and Incrementing

`compute` clearly expresses the rule "start at 1 if no value exists yet, otherwise increment." The `counts` example in the program does not need a separate `containsKey` branch.

If 0 is still a valid value to keep, return 0. If you want to remove the mapping when the count runs out, return null in that specific branch. There is no general rule in `Map` that automatically turns 0, an empty string, or an empty collection into a removal.

Example of adjusting a score under a policy that does not keep a 0 result, assuming `scores`, `key`, and `delta` already exist in context:

~~~java
Integer result = scores.compute(key, (k, old) -> {
    int next = Math.addExact(old == null ? 0 : old, delta);
    return next == 0 ? null : next;
});
~~~

This snippet illustrates a specific policy. If a null `old` previously had a different meaning from an absent key, treating both as 0 intentionally merges them and must be acceptable to the business logic.

### When You Need to Remember a Not-Found Result

A cache whose loader returns null does not automatically record a failed lookup through `computeIfAbsent`. Two calls may both end up loading because no new value was stored.

You can store a non-null result object, such as `Optional.empty()` representing "loaded but no data found." In that case, the map's value type is `Optional<V>`, not a nullable `V`. The loader needs to convert the result into a non-null `Optional` object.

Do not conflate a loading error with "not found" if they have different policies. A loader exception, non-existent data, and data not yet loaded are three pieces of information that may need to be tracked separately.

## 10. Exceptions and Side Effects: No General Rollback Mechanism

When the computation function throws an exception that is not handled inside the function, the exception propagates to the caller. In a contract-compliant call, the method does not install a partially computed value as a new mapping.

Example in the program:

~~~text
Before: k -> 5.
The compute function throws IllegalStateException.
After catching the exception: k still has the value 5.
~~~

However, "the mapping was not replaced" does not mean everything the function did was rolled back.

In the second example, the old value is an `ArrayList`. The function calls `old.add("changed")` and then throws an exception. The map still points to that same old list, and the list has had an element added to it:

~~~text
Before: [old]
After the function throws: [old, changed]
~~~

The `compute` methods do not have a transaction system to revert the contents of arbitrary objects, restore external variables, erase log entries, or cancel a request already sent to another system.

Therefore, keep the computation function focused on deciding a value. If you want to avoid mutating the old object before the computation finishes, create a new object from the old data and return the new object only when the rule completes. That helps control side effects in a sequential model; safety when data is shared still needs to be designed separately.

Also distinguish two kinds of failure:

- Function returns null: a normal result meaning do not add or remove, depending on the method.
- Function throws an exception: the computation did not complete normally and the exception is propagated.

Do not catch all exceptions and return null as a habit. With `compute` or `computeIfPresent` when a value exists, that behavior can turn a computation error into a data deletion command.

## 11. Do Not Modify the Same Map from Inside the Computation Function

A common mistake is both returning a new value and writing additional entries to the Map:

~~~java
map.compute("a", (key, old) -> {
    map.put("b", 100);
    return 10;
});
~~~

This code illustrates invalid usage under the computation function contract. Instead of treating it as a two-key update operation, separate the update design according to your actual needs.

The computation function should not modify the Map currently being computed, including attempting to update another key in it. With `HashMap`, detecting certain modifications from the function can result in a `ConcurrentModificationException` on a best-effort basis. Do not treat this exception as a guarantee that every invalid modification will be detected or rolled back. [HashMap compute Methods Contract, Java 17](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/HashMap.html).

Nesting `compute` calls on the same Map is not a general workaround either. With concurrent implementations, some forms of recursive updates are forbidden or may be detected with an exception. Do not use recursion exceptions to control your algorithm.

If changes to two keys must be consistent with each other, a `compute` on one key does not automatically provide a transaction across both keys. Choose a coordination mechanism or data model suited to the consistency you need.

Mutating the old value object itself—like the list in the exception section—is a different kind of side effect from calling `Map.put`. It still needs careful consideration because it can alter shared data and affect failure handling.

## 12. Map, HashMap, ConcurrentMap, and ConcurrentHashMap Have Different Guarantees

### Do Not Infer Atomicity from the Method Name

`Map`'s default methods do not provide general synchronization guarantees across all implementing classes. Nor is `HashMap` a structure for threads to freely update concurrently without a coordination mechanism.

Replacing a `get -> compute -> put` sequence with a `HashMap.compute` call makes the intent cleaner, but it does not turn `HashMap` into a thread-safe map. If multiple threads share data, all parties must follow an appropriate access mechanism, or use a concurrent data structure with the right contract.

### ConcurrentHashMap Has a Specific Atomicity Contract

`ConcurrentHashMap` implements the compute methods with atomic guarantees for the described operation. The computation function should be short; during computation, some other updates may have to wait. Do not put long-running or interdependent work inside the function and assume the rest of the system will proceed independently. [ConcurrentHashMap Documentation, Java 17](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/concurrent/ConcurrentHashMap.html).

For a valid call on `ConcurrentHashMap`, its contract specifies how many times the function is invoked according to each method's conditions. This differs from claiming "the function runs only once across the entire application": a mapping can be removed, a computation may produce no value, and subsequent calls may still need to recompute.

`ConcurrentHashMap` does not store null keys or null values, yet it accepts **a null result from the computation function** as a control signal:

| Call on eligible state | Meaning of a null function result |
| --- | --- |
| `computeIfAbsent` for an absent key | Do not establish a new mapping |
| `computeIfPresent` for a present key | Remove the mapping |
| `compute` | Remove the mapping if present, or keep absent if not |

Do not confuse "forbids putting a null value" with "forbids a compute function from returning null." The program verified this on `ConcurrentHashMap` sequentially.

### Do Not Extend One Class's Promise to Every ConcurrentMap

Some default algorithms in `ConcurrentMap` may retry under update contention; the remapping function can be invoked multiple times within a single call. Therefore, code that accepts a general `ConcurrentMap` needs to rely on the contracts of supported implementations, not assume `ConcurrentHashMap`'s guarantees by default for all of them. [ConcurrentMap Documentation, Java 17](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/concurrent/ConcurrentMap.html).

This is another reason to minimize side effects inside the computation function. Emitting an external event or incrementing an external variable each time the function is called may not correspond one-to-one with successful mapping updates.

The `calls` counter in the program is an instrument for observing the chosen sequential cases. Do not treat those observed counts as test evidence for every contention behavior of a concurrent implementation.

### Map Safety Does Not Automatically Protect the Values Inside

The pattern:

~~~java
groups.computeIfAbsent(key, k -> new ArrayList<>()).add(item);
~~~

does not automatically make the `ArrayList` inside a thread-safe collection even when `groups` is a `ConcurrentHashMap`. The `add` operation happens on the returned list object; a `computeIfAbsent` call does not create a protective wrapper around all subsequent operations on that list.

You need to choose a value type with an appropriate concurrency mechanism or design updates using immutable values, along with a consistent access rule. Distinguish the safety of the mapping from the safety of the object the mapping points to.

## 13. Choosing the Right Method and Recognizing Common Mistakes

| Intent | Usually appropriate choice | What to verify |
| --- | --- | --- |
| Create a value when no non-null value exists | `computeIfAbsent` | Should an old null be treated as uninitialized? |
| Modify only when a non-null value already exists | `computeIfPresent` | Is skipping keys mapped to null acceptable? |
| Single rule for creating, replacing, and removing | `compute` | Does the function handle a null `old`? |
| Read only, without modifying the Map | `get` or `getOrDefault` as needed | Do not use `compute` just to return a default and accidentally create a mapping |
| Store a new null in `HashMap` | `put` with an explicit policy | Do not use null returned from `compute` as a request to store null |
| Atomic concurrent operation | Implementation with the right contract | Do not infer from the `Map` type or the name `compute` |

Common mistakes:

| Mistake | Likely consequence | How to fix |
| --- | --- | --- |
| Treating `IfPresent` as `containsKey` | Function does not run for null values as expected | Read the condition as "a non-null value already exists" |
| Assuming every null result removes | Misunderstanding null mappings kept by `IfAbsent` or skipped by `IfPresent` | Check both the state and the invocation condition |
| Returning null from `compute` to store null | Mapping is removed | Separate removal from directly storing null |
| Using `IfAbsent` to cache null | Loader gets called repeatedly | Store a non-null result state if you want to remember it |
| Chaining a method onto a possibly null result | `NullPointerException` | Require the factory function to return non-null or check the result |
| Assigning the result to a primitive type | Unboxing null fails | Keep the wrapper type and handle the null branch |
| Catching errors and returning null to "ignore" | Can delete an existing value | Choose a dedicated failure policy; do not accidentally issue a delete |
| Modifying the Map inside the computation function | Contract violation, possible exception | Separate the operations or change the update model |
| Assuming a thrown exception rolls back all changes | Side effects on objects or external systems remain | Minimize side effects; compute on new values when appropriate |
| Assuming `ConcurrentHashMap` protects all value collections | Lost updates or errors in shared objects | Design value safety separately |
| Assuming every `ConcurrentMap` calls the function the same number of times | Side effects repeated on retries | Rely on implementation contracts; keep computation functions suitable |

For Map types that do not allow updates, the `compute` methods may be rejected with `UnsupportedOperationException`. Do not use the "If" in the name to assume that calling an update method on a read-only map will always be allowed when you expect no change to occur.

## 14. Exercises and Solutions

### Exercise 1 — Distinguishing Invocation Conditions

A `HashMap` has `a -> null`, `b -> 5`, and `c` is absent. With a valid computation function, for which keys will `computeIfAbsent` consider calling the function? What about `computeIfPresent`?

**Solution:** `computeIfAbsent` calls it for `a` and `c`, not for `b`. `computeIfPresent` calls it for `b`, not for `a` or `c`. `compute` evaluates the function in all three cases when the call is valid.

### Exercise 2 — Three Ways of Returning null on a Null Mapping

Start separately each time from `a -> null`. Compare the state after `computeIfAbsent(a, k -> null)`, `computeIfPresent(a, (k,v) -> null)`, and `compute(a, (k,v) -> null)`.

**Solution:** The first two keep the mapping `a -> null`, but for two different reasons: `IfAbsent` called the function and did not write a new value; `IfPresent` did not call the function. `compute` called the function and then removed the mapping for `a`. You need `containsKey` to distinguish the resulting states when all return values are null.

### Exercise 3 — Function Does Not Run but Is Configured to Return null

A Map has `a -> 5`. The function passed to `computeIfAbsent` is written to return null. What are the method's return value and the stored value afterward?

**Solution:** The function does not run because the non-null value 5 already exists. The method returns 5 and the Map keeps 5. There is no actual null result from the function to handle in this call.

### Exercise 4 — Keep 0 or Remove?

Counter `a` is currently 1. You want to decrement it to 0 while keeping the key. Should you return null in the branch where `old` is 1?

**Solution:** No. Return 0 to store 0; returning null in `computeIfPresent` will remove the mapping. Choosing to remove a 0 counter in the example program is a business policy, not a mandatory Map rule.

### Exercise 5 — Loader Returns null Twice

A key does not exist yet. Call `computeIfAbsent` twice in a row with a loader that always returns null. How many times does the loader run in a sequential `HashMap`? Is a new mapping created?

**Solution:** Twice; no new mapping is created. The first call did not create a value for the later call to reuse. If you need to remember "not found," use a non-null value representing that state.

### Exercise 6 — The Old Value in compute

A `compute` function receives `old` equal to null. Can you conclude with certainty that the key was absent before the call?

**Solution:** No, if the Map allows storing null values. It could be either an absent key or a null mapping. The `old` parameter alone does not carry enough information to distinguish those two states.

### Exercise 7 — Does an Exception Roll Back the List?

A Map holds `k -> ArrayList["one"]`. A `compute` function adds `"two"` to `old` and then throws an exception. Can you assume the list in the Map still contains only `"one"`?

**Solution:** No. The mapping may still hold the same list reference, but that object has been mutated. There is no automatic rollback mechanism for object contents. Computing on a fresh copy helps avoid mutating the old object before success in an appropriate model.

### Exercise 8 — Why Not Modify Another Key Inside the Function?

A `compute` function for `a` calls `map.put("b", 10)` and then returns a value for `a`. Can this be treated as an atomic two-key update?

**Solution:** No. The computation function should not modify the Map currently being processed; it can violate the contract and raise an exception. A `compute` on one key does not provide a two-key transaction. You need to design a separate consistency mechanism.

### Exercise 9 — null on ConcurrentHashMap

`ConcurrentHashMap` forbids storing null values. Does `compute("a", (k,v) -> null)` necessarily throw an exception because the function returns null?

**Solution:** No. A null returned from the function means "do not add" or "remove the mapping," not "store a null value." The key passed in must still be valid and the function must still obey the other constraints.

### Exercise 10 — Group Lists Across Multiple Threads

`groups` is a `ConcurrentHashMap` whose values are `ArrayList`. Every thread uses `computeIfAbsent` and then calls `add` on the returned list. Is that alone enough to protect the list?

**Solution:** Not yet. The Map protects the mapping operation according to its contract; `ArrayList` does not automatically become thread-safe. You need a value with an appropriate access mechanism or a different update design that protects all related data.

### Exercise 11 — Do Not Transfer Promises Between Implementations

A library method accepts a `ConcurrentMap` and a computation function with side effects. Since `ConcurrentHashMap` is commonly used, can it assume every passed-in implementation invokes the function once?

**Solution:** No. Some default algorithms can retry and call the function multiple times under update contention. The library must document the supported implementation contracts or design the function not to rely on an unguaranteed invocation count.

### Exercise 12 — Reading the Verification Table

Explain the line `IF_PRESENT NULL_VALUE configured=9 calls=0 result=null present=true value=null`. Did the method try to store 9 and fail?

**Solution:** No. `configured` is only the result the function would return if called. The old value is null, so the `IfPresent` condition is not met; `calls` is 0, no computation of 9 was performed, the old null mapping is preserved, and the method returns null.

## 15. How to Self-Check a compute Rule

Before writing a lambda, identify the input states it must handle and which condition allows calling it. Then assign clear meanings to both kinds of results: a non-null value and null.

Test the rule on an absent key, a key with null if the implementation allows it, and a key with a real value. Separately observe how many times the function runs, what value the method returns, and whether the mapping exists after the call. If there are side effects or multi-threaded data, also verify the failure contract and concurrency contract of the exact `Map` class you are using.

Remember the three roles: `computeIfAbsent` creates when no non-null value exists; `computeIfPresent` modifies an existing non-null value; `compute` applies a general rule. A null returned from the function is a signal controlling whether to keep absent or remove according to each method, and it only has meaning when the function was actually called.
