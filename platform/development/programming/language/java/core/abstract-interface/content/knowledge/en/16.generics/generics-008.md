# Type erasure, bridge methods, and overriding relationships in Java

## 1. Three related concepts

Generics help the compiler check types in source code. Java implements generics primarily using **type erasure**: type parameters are erased or replaced by the erased type of their bound when generating bytecode. Generic inheritance can cause the source-code signature and the JVM descriptor to differ; the compiler generates a **bridge method** when needed so that polymorphic calls still reach the right implementation.

- **Type erasure** determines the types of type variables and generic types after compilation.
- **Overriding** is determined according to Java language rules and generic inheritance relationships.
- **Bridge method** is a synthetic method generated by the compiler to maintain compatibility between the erased signature and the concrete implementation.

Bridge methods normally do not appear in source code written by developers. Do not manually declare a bridge to fix an incorrect generic signature.

## 2. How does type erasure work?

| Source declaration | Illustrative erased type |
| --- | --- |
| List&lt;String&gt; | List |
| Map&lt;String, Integer&gt; | Map |
| T with unbounded &lt;T&gt; | Object |
| T with &lt;T extends Number&gt; | Number |
| T with &lt;T extends Number & Comparable&lt;T&gt;&gt; | Number, which is the first bound |

Example:

~~~java
class Box<T> {
    private T value;

    public void set(T value) {
        this.value = value;
    }

    public T get() {
        return value;
    }
}
~~~

For an unbounded T, the erased signatures are conceptually equivalent to set(Object) and get() returning Object. When source code uses Box&lt;String&gt;, the compiler still checks types and inserts the necessary casts at read sites. This does not mean the compiler creates a separate runtime class for Box&lt;String&gt;.

The class file can retain generic signature metadata so that Reflection and tools can read generic declarations. That metadata does not turn Box&lt;String&gt; and Box&lt;Integer&gt; into two different runtime classes.

## 3. Why does generic overriding need a bridge method?

~~~java
class Node<T> {
    public void setData(T data) {
        // Store data.
    }

    public T getData() {
        return null;
    }
}

final class IntegerNode extends Node<Integer> {
    @Override
    public void setData(Integer data) {
        System.out.println("integer=" + data);
    }

    @Override
    public Integer getData() {
        return 42;
    }
}
~~~

In source code, IntegerNode fixes T to Integer and provides setData(Integer) and getData() returning Integer. These overrides are valid after applying the type argument of Node&lt;Integer&gt;.

After erasure, Node's methods have signatures using Object, whereas IntegerNode's implementations accept or return Integer. The compiler needs to generate bridges equivalent to the entry points setData(Object) and getData() returning Object. The bridge forwards to the concrete implementation and may also cast the argument from Object to Integer.

If a call uses a valid generic type, the compiler guarantees that the argument matches. If a raw type is used to pass a value of the wrong type, the cast inside the bridge can throw a ClassCastException.

## 4. Runnable example and observation with Reflection

Save all the code to **TypeErasureBridgeDemo.java**:

~~~java
import java.lang.reflect.Method;
import java.util.Arrays;
import java.util.Comparator;
import java.util.stream.Collectors;

class Node<T> {
    private T data;

    public void setData(T data) {
        this.data = data;
    }

    public T getData() {
        return data;
    }
}

final class IntegerNode extends Node<Integer> {
    @Override
    public void setData(Integer data) {
        System.out.println("set Integer: " + data);
        super.setData(data);
    }

    @Override
    public Integer getData() {
        return super.getData();
    }
}

public class TypeErasureBridgeDemo {
    public static void main(String[] args) {
        Node<Integer> node = new IntegerNode();
        node.setData(42);
        System.out.println("value=" + node.getData());

        Arrays.stream(IntegerNode.class.getDeclaredMethods())
                .filter(Method::isBridge)
                .sorted(Comparator.comparing(Method::getName))
                .forEach(method -> {
                    String parameters = Arrays.stream(method.getParameterTypes())
                            .map(Class::getSimpleName)
                            .collect(Collectors.joining(", "));
                    System.out.println("bridge=" + method.getName()
                            + "(" + parameters + ") -> "
                            + method.getReturnType().getSimpleName());
                });
    }
}
~~~

Compile and run with JDK 17 or later:

~~~bash
javac TypeErasureBridgeDemo.java
java TypeErasureBridgeDemo
~~~

Stdout output:

~~~text
set Integer: 42
value=42
bridge=getData() -> Object
bridge=setData(Object) -> void
~~~

The variable node is declared as Node&lt;Integer&gt; but points to an IntegerNode. The call setData(42) goes through the erased dispatch path and then reaches the implementation that accepts Integer. Reflection filters by isBridge() and sorts by name for consistent output; you should not rely on the order returned by getDeclaredMethods().

## 5. Bridges and covariant return types

A bridge can also appear when the return type of an override is a more specific subtype:

~~~java
class Animal {
    public Object create() {
        return new Object();
    }
}

final class Cat extends Animal {
    @Override
    public String create() {
        return "cat";
    }
}
~~~

Java allows Cat.create() to override Animal.create() because String is a subtype of Object. The return type is part of the JVM descriptor, so the compiler can generate a bridge returning Object so that calls through Animal still reach Cat's implementation. This is not overloading: Java does not allow declaring two methods in the same class that differ only by return type.

Bridges typically carry the ACC_BRIDGE and ACC_SYNTHETIC bytecode flags. Reflection can check isBridge() and isSynthetic(); not every synthetic method is a bridge, and not every generic override requires a bridge.

## 6. Implications to keep in mind

- You cannot overload two methods that differ only in type arguments if their signatures collide after erasure. The article on name clashes analyzes the cases and how to redesign them.
- You cannot check List&lt;String&gt; with instanceof as if the runtime knew the concrete type argument; use List&lt;?&gt; if you only need to verify that it is a List.
- You cannot directly create new T() or new T[n] for a type variable whose concrete type is unknown.
- Static members cannot directly use the type parameter of the instance class; static generic methods can declare their own type parameters.
- Raw types and unchecked casts can bypass part of compile-time checking; they do not make the runtime object check type arguments on its own.

## 7. How to investigate when seeing an unfamiliar method

1. Verify the extends/implements relationship and the override signature in the source code.
2. Compute the erasure of each type variable: an unbounded T becomes Object; T extends X usually erases to X.
3. Use @Override so the compiler verifies the intended override relationship.
4. If Reflection lists an unexpected method, check isBridge() and isSynthetic().
5. You can use javap -p -c -v IntegerNode to inspect the descriptor, ACC_BRIDGE/ACC_SYNTHETIC flags, and forwarding instructions.

Type erasure is an implementation mechanism; a bridge method is a compiler-generated detail to preserve polymorphism. Design and verify contracts at the Java source level without relying on writing bridges manually.
