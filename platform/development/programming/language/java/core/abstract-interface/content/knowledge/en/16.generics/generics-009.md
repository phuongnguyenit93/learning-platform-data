# Name clash due to the same erasure and inheriting multiple type parameters in Java

## 1. What is a name clash?

A **name clash** occurs when two method declarations have the same erasure but do not form a valid override relationship. Type arguments help the compiler check types in source code, but usually do not create separate JVM descriptors.

Example that intentionally does not compile:

~~~java
import java.util.List;

class InvalidOverload {
    void handle(List<String> values) {}
    void handle(List<Integer> values) {}
}
~~~

Both signatures erase to handle(List). Java cannot distinguish them in bytecode based solely on String or Integer inside List. This is a signature design error; renaming parameter variables, changing the return type, or adding @SuppressWarnings cannot fix it.

Regular overloads with genuinely different parameter types remain valid, for example handle(String) and handle(Integer). The problem is that type arguments inside the same generic type are erased.

## 2. Two independent interfaces can conflict

~~~java
interface TextReceiver<T> {
    void accept(T value);
}

interface NumberReceiver<T> {
    void accept(T value);
}

// Intentionally does not compile:
class ConflictingReceiver
        implements TextReceiver<String>, NumberReceiver<Integer> {
    public void accept(String value) {}
    public void accept(Integer value) {}
}
~~~

After applying type arguments, one contract requires accept(String), and the other requires accept(Integer). However, both methods declared in the interfaces have the erasure accept(Object). The compiler cannot generate two different accept(Object) bridges to guess which implementation each call should go to.

If two interfaces have the same contract after substituting type arguments, a single implementation can satisfy both:

~~~java
interface First<T> {
    void accept(T value);
}

interface Second<T> {
    void accept(T value);
}

final class SharedReceiver implements First<String>, Second<String> {
    @Override
    public void accept(String value) {
        System.out.println("accepted=" + value);
    }
}
~~~

Here, both interfaces require accept(String), so SharedReceiver only needs one method. Bridges, if needed, will be generated by the compiler according to the usual rules; see the article on type erasure and bridge methods to learn how to observe them.

## 3. Cannot inherit the same generic interface with different type arguments

This is a separate error with the inheritance structure:

~~~java
interface Receiver<T> {
    void receive(T value);
}

// Intentionally does not compile:
class InvalidReceiver implements Receiver<String>, Receiver<Integer> {
}
~~~

Java does not allow a type to inherit the same generic interface with different type arguments. Do not confuse this case with two independent interfaces in the previous section: they have causes related to erasure, but the violated rules are different.

## 4. Generic methods can also have the same erasure

~~~java
class MethodClash {
    <T> void store(T value) {}
    void store(Object value) {}
}
~~~

This snippet does not compile because the erasure of **&lt;T&gt; void store(T)** is store(Object), which collides with the regular method. Keep a single signature if the purpose is to accept any object; if the operations differ in meaning, choose genuinely different names or parameters.

Similarly, you cannot create two overloads merely by changing the type arguments of List, Map, or another generic type. Wildcards also do not produce a different descriptor after erasure.

## 5. Distinguishing name clashes from valid overrides

Not all methods with the same erasure are errors. When a subclass method truly and validly overrides an inherited generic method, the compiler can generate a bridge to preserve dispatch:

~~~java
class Box<T> {
    public T echo(T value) {
        return value;
    }
}

final class StringBox extends Box<String> {
    @Override
    public String echo(String value) {
        return "echo=" + value;
    }
}
~~~

StringBox.echo(String) overrides Box&lt;String&gt;.echo(T) after T is substituted with String. A bridge accepting Object can forward to echo(String). This differs from two independent overloads handle(List&lt;String&gt;) and handle(List&lt;Integer&gt;), because that pair of overloads do not override each other.

## 6. Comparison table

| Case | Result | Reason |
| --- | --- | --- |
| f(String) and f(Integer) | Usually valid | Different parameter descriptors |
| f(List&lt;String&gt;) and f(List&lt;Integer&gt;) | Invalid | Same erasure f(List) |
| Two interfaces both requiring accept(String) | Can be valid | A single implementation satisfies both |
| Two interfaces requiring accept(String) and accept(Integer), both with erasure accept(Object) | Cannot be implemented using those two overloads | No single Object dispatch fits both |
| Inheriting Receiver&lt;String&gt; and Receiver&lt;Integer&gt; | Invalid | The same generic interface is inherited with different type arguments |
| Valid generic override in a subclass | Valid | Compiler can generate a bridge to preserve dispatch |

## 7. What to do when encountering an error

1. Find all methods with the same name in the class, superclass, and inherited interfaces.
2. Compute the erasure of each signature: List&lt;String&gt; and List&lt;Integer&gt; both become List; an unbounded T becomes Object; T extends Number becomes Number.
3. Check whether the method actually overrides or is merely an overload. Use @Override so the compiler verifies the override intent.
4. Check the type arguments of the parent interfaces and see whether a single implementation can satisfy the contracts.
5. Choose a fix based on the API's meaning: rename the methods if the operations differ; use a single generic method if the logic is shared; unify the type arguments when the contracts truly share the same type; or separate the interfaces if they describe incompatible behaviors.

Do not use raw types, unchecked casts, or @SuppressWarnings to work around a name clash. Those approaches do not produce a different JVM signature and can cause type checking to be lost in other places. When an error involves bridges, see the article on type erasure; when an error involves raw types or unchecked warnings, see the corresponding article in the chapter.

## 8. Self-check

1. Why are handle(List&lt;String&gt;) and handle(List&lt;Integer&gt;) not two valid overloads? Because both have the erasure handle(List).
2. Why can two interfaces be implemented together if both require accept(String)? Because a single method satisfies both.
3. Why is it not possible to inherit Receiver&lt;String&gt; and Receiver&lt;Integer&gt;? Because the same generic interface cannot be inherited with different type arguments.
4. Are bridge methods a way to manually fix overloads with the same erasure? No; the compiler only generates a bridge when needed to maintain a valid override relationship.
5. If two operations are different, should you rename or cast? Design signatures that accurately reflect the contract; do not use casts to hide conflicts.
