# JDBC 4.3: Phân biệt tiện ích trích dẫn với tham số hóa PreparedStatement

## 1. Vấn đề: SQL có cú pháp, giá trị và định danh

Khi xây dựng câu truy vấn SQL bằng JDBC, cần phân biệt ba loại thông tin:

- **Giá trị dữ liệu (value):** email, tên người dùng, tiền, số, ngày giờ hoặc nội dung nhập trong biểu mẫu. Giá trị có thể chứa dấu nháy hoặc ký tự đặc biệt nhưng vẫn phải được hiểu như dữ liệu.
- **Định danh SQL (identifier):** tên bảng, cột, schema, chẳng hạn `users`, `created_at` hoặc một cột thực sự có tên `"Order Detail"`.
- **Cú pháp SQL:** `SELECT`, `WHERE`, `ORDER BY`, `ASC`/`DESC`, phép toán và cấu trúc biểu thức.

**Kết luận quan trọng:** tiện ích trích dẫn của JDBC 4.3 tạo **chuỗi biểu diễn literal/identifier trong SQL**. `PreparedStatement` giữ SQL thành một cấu trúc có vị trí tham số (`?`), rồi **bind giá trị** bằng `setXxx`. Hai cơ chế giải quyết hai nhu cầu khác nhau.

JDBC 4.3 xuất hiện cùng Java 9; các API `Statement.enquoteLiteral`, `Statement.enquoteIdentifier`, `Statement.enquoteNCharLiteral` và `Statement.isSimpleIdentifier` **vẫn được hỗ trợ** trong các JDK hiện đại. Nội dung này tập trung vào cách sử dụng còn phù hợp hiện nay, đặc biệt là tránh trộn dữ liệu chưa tin cậy vào cấu trúc truy vấn.

## 2. Tiện ích trích dẫn của Statement

Từ Java 9, `java.sql.Statement` cung cấp những phương thức `default`:

| Phương thức | Mục đích | Ví dụ theo triển khai mặc định của JDK |
| --- | --- | --- |
| `String enquoteLiteral(String value)` | Đặt một chuỗi trong nháy đơn SQL và tăng đôi dấu `'` xuất hiện bên trong | `O'Reilly` → `'O''Reilly'` |
| `String enquoteNCharLiteral(String value)` | Tạo dạng national-character literal có tiền tố `N`, thường được biểu diễn bằng `N'...'` | `Hello` → `N'Hello'` |
| `String enquoteIdentifier(String name, boolean alwaysQuote)` | Tạo định danh đơn giản hoặc định danh được bao bằng dấu phân cách | `("customer_name", false)` → `customer_name`; `("Order Detail", true)` → `"Order Detail"` |
| `boolean isSimpleIdentifier(String name)` | Nhận biết tên có hình dạng identifier đơn giản theo quy tắc triển khai/driver hay không | `customer_name` → `true` |

**Literal và identifier không dùng cùng dấu trích dẫn.** Trong nhiều SQL dialect, nháy đơn `'...'` biểu diễn một giá trị chuỗi, còn nháy kép `"..."` bao tên đối tượng. Không thay thế một loại bằng loại kia.

### 2.1. enquoteLiteral không phải parameter binding

`enquoteLiteral("O'Reilly")` tạo chuỗi `'O''Reilly'`. Phương thức xử lý dấu nháy đơn trong văn bản literal, nhưng kết quả **vẫn là một đoạn String sẽ xuất hiện trong SQL**. Nó không gọi database và không truyền tham số độc lập; mã ứng dụng cần tự xác định nơi chèn kết quả.

```java
// Ví dụ biểu diễn SQL literal, chỉ để minh họa hình dạng kết quả:
String escaped = statement.enquoteLiteral("O'Reilly");
String sql = "SELECT id FROM authors WHERE name = " + escaped;
// SQL được tạo: SELECT id FROM authors WHERE name = 'O''Reilly'
```

Trong mã nhận dữ liệu từ request, **không nên** dùng cách ghép chuỗi như trên thay cho `PreparedStatement`. Ngoài quoting, JDBC binding còn giải quyết cách truyền kiểu dữ liệu và `NULL`; việc escape literal có thể phụ thuộc dialect, chế độ SQL và driver.

### 2.2. enquoteIdentifier xử lý cú pháp tên, không kiểm tra quyền

`enquoteIdentifier(name, false)` có thể giữ nguyên tên nếu là identifier đơn giản. `alwaysQuote = true` yêu cầu dấu phân cách ngay cả với tên đơn giản. Một số cơ sở dữ liệu xử lý chữ hoa/chữ thường khác đi khi định danh được quote, vì thế phải biết cách schema đã khai báo tên.

Theo triển khai mặc định của JDK, identifier đơn giản bắt đầu bằng chữ cái ASCII, sau đó chỉ gồm chữ cái ASCII, chữ số hoặc `_`, dài 1–128 ký tự, không có nháy kép bao ngoài. Đây là **quy tắc hình dạng tên**, không phải allowlist nghiệp vụ. Ví dụ `isSimpleIdentifier("users") == true` không nói rằng bảng `users` tồn tại hoặc người dùng được phép truy cập bảng đó. Driver có thể ghi đè các phương thức để phù hợp database.

Nếu datasource không hỗ trợ quoted identifier, `enquoteIdentifier` có thể ném `SQLFeatureNotSupportedException`. Tên không hợp lệ hoặc vượt giới hạn cũng có thể gây `SQLException`. Không hardcode dấu nháy kép hoặc backtick cho mọi database; nếu có nhu cầu quoting thật, kiểm tra driver và metadata database.

### 2.3. enquoteNCharLiteral là biểu diễn literal

`enquoteNCharLiteral("Hello")` tạo `N'Hello'` trong triển khai mặc định. Đây là biểu diễn dành cho database/dialect có national-character literal. Nó **không phải** cách bind dữ liệu Unicode. Khi truyền giá trị cho cột phù hợp, JDBC có `PreparedStatement.setNString` và `setString`; chọn phương thức thích hợp dựa trên loại cột và hỗ trợ của driver.

Các phương thức quote nhận chuỗi `null` có thể ném `NullPointerException` theo tài liệu API. Một giá trị SQL `NULL` không giống chuỗi ký tự `'NULL'`; với binding hãy dùng `setNull(index, sqlType)` theo kiểu SQL mong đợi.

## 3. PreparedStatement giữ giá trị tách khỏi cú pháp

Ví dụ người dùng có thể nhập tên `O'Reilly` hoặc chuỗi chứa dấu nháy và từ khóa SQL. Cách sau **nguy hiểm** vì nối dữ liệu chưa tin cậy trực tiếp vào SQL:

```java
// Sai: tên người dùng có thể ảnh hưởng đến văn bản/cú pháp SQL.
String unsafe = "SELECT id FROM users WHERE username = '" + userInput + "'";
```

Nếu input làm đóng nháy, phần còn lại có thể bị parser SQL hiểu là biểu thức hoặc điều kiện bổ sung (SQL injection). Bọc chuỗi này bằng `connection.prepareStatement(unsafe)` sau khi nối **không khắc phục** vấn đề: SQL đã chứa dữ liệu nhập trước khi được prepare.

Dùng marker `?` với `PreparedStatement`:

```java
// Đặt trong phương thức có Connection hợp lệ và khai báo throws SQLException.
String sql = "SELECT id FROM users WHERE username = ?";
try (PreparedStatement ps = connection.prepareStatement(sql)) {
    ps.setString(1, userInput);
    try (ResultSet rs = ps.executeQuery()) {
        while (rs.next()) {
            long id = rs.getLong("id");
            // Xử lý id theo nghiệp vụ.
        }
    }
}
```

Ở đây:

1. `connection.prepareStatement(sql)` tạo statement theo mẫu SQL cố định, có một parameter marker.
2. `ps.setString(1, userInput)` truyền **giá trị chuỗi** cho tham số thứ nhất; JDBC đánh số tham số từ **1**.
3. Trình điều khiển xử lý giá trị theo cơ chế parameter của database. Dấu nháy trong giá trị không biến thành điều kiện SQL do ứng dụng nối vào văn bản.
4. `ResultSet` và `PreparedStatement` được đóng qua `try-with-resources`. Mã thực tế cần một `Connection` đang hoạt động, JDBC driver và bảng có dữ liệu.

Với dữ liệu kiểu số, dùng `setInt`/`setLong`; tiền dùng `setBigDecimal` khi phù hợp; đối tượng SQL khác có thể dùng `setObject` với kiểu rõ ràng; SQL `NULL` có thể dùng `setNull`. Những lợi ích này không có được chỉ nhờ `enquoteLiteral`. Việc server có cache hoặc tái sử dụng execution plan hay không còn tùy database/driver; đừng coi hiệu năng là lý do duy nhất để dùng binding.

**Lỗi cú pháp hay gặp:** `WHERE username = '?'` chứa literal ký tự `?`, nên không có marker để `setString` gắn giá trị. Phải viết `WHERE username = ?`.

## 4. Vì sao dấu ? không áp dụng cho tên bảng, cột và ORDER BY?

`?` đại diện cho **giá trị**, không thể thay thế một đoạn ngữ pháp SQL bất kỳ. Chẳng hạn:

```sql
-- Ý định sai: chọn tên cột dựa trên giá trị được bind.
SELECT id, email FROM users ORDER BY ?;

-- Đúng về ngữ pháp: lựa chọn cột được kiểm soát trong mã nguồn.
SELECT id, email FROM users ORDER BY created_at DESC;
```

Với `ORDER BY ?`, database không thể coi một tham số String bất kỳ là từ khóa hay tên cột; một số hệ quản trị có thể coi nó là biểu thức hằng, một số có thể từ chối. Tương tự, `SELECT ? FROM users` biểu diễn một giá trị được bind, không phải một lệnh chọn cột dựa trên tên do người dùng nhập.

Nếu API cho phép người dùng chọn `sort=name` hay `sort=created`, chương trình phải dùng **allowlist**: chỉ chấp nhận tên lựa chọn có trong tập đã định nghĩa và ánh xạ sang tên cột đã biết. Không chèn chuỗi `sortKey` thô vào SQL và cũng không dùng `enquoteIdentifier(sortKey, true)` như một hình thức cấp quyền truy cập.

### Ví dụ áp dụng thực tế, Java 17+

Giả sử bảng `users` có `id`, `email`, `status`, `created_at` và `display_name`. Tệp `UserQueries.java` là lớp có thể biên dịch bằng Java 17+; ứng dụng phải truyền `Connection` thật và có bảng theo giả định khi muốn thực thi.

```java
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;
import java.util.ArrayList;
import java.util.List;

public final class UserQueries {
    private UserQueries() {}

    public static List<Long> findIds(
            Connection connection,
            String email,
            int minimumStatus,
            String sortKey,
            boolean descending) throws SQLException {

        // User chỉ chọn các khóa logic; tên cột đến từ mã của ứng dụng.
        String column = switch (sortKey) {
            case "created" -> "created_at";
            case "name" -> "display_name";
            default -> throw new IllegalArgumentException(
                    "Unknown sort key: " + sortKey);
        };
        String direction = descending ? "DESC" : "ASC";

        // Phần ghép vào cú pháp SQL chỉ gồm các token được phép.
        String sql = "SELECT id FROM users WHERE email = ? AND status >= ? "
                + "ORDER BY " + column + " " + direction;

        List<Long> ids = new ArrayList<>();
        try (PreparedStatement ps = connection.prepareStatement(sql)) {
            ps.setString(1, email);
            ps.setInt(2, minimumStatus);
            try (ResultSet rs = ps.executeQuery()) {
                while (rs.next()) {
                    ids.add(rs.getLong("id"));
                }
            }
        }
        return ids;
    }
}
```

Biên dịch:

```bash
javac -encoding UTF-8 UserQueries.java
```

Vì đây là lớp truy vấn không có `main` và không kèm DB/driver, **không có stdout cố định**. Khi một ứng dụng thật gọi `UserQueries.findIds(...)`, mọi giá trị `email` và `minimumStatus` đều được bind. `sortKey` chỉ chọn `created_at` hoặc `display_name`; chiều sắp xếp chỉ chọn token `ASC`/`DESC` do ứng dụng viết sẵn. Những lựa chọn ngoài allowlist bị từ chối.

Đây là sự kết hợp cần thiết: **parameterization cho dữ liệu + allowlist cho cấu trúc SQL động**. Nếu không cần tên cột động, giữ câu SQL tĩnh là đơn giản nhất.

## 5. Khi cần kết hợp identifier quoting với PreparedStatement

Một schema thực tế đôi khi có tên cột chứa dấu cách hoặc từ dành riêng. Nếu đã **xác nhận trước** schema có cột tên `Order Detail`, dùng tiện ích của driver để trích dẫn identifier; sau đó vẫn bind giá trị `reportId`:

```java
// Fragment trong phương thức throws SQLException, với Connection hợp lệ.
// Cần import java.sql.Statement, PreparedStatement, ResultSet.
try (Statement quoting = connection.createStatement()) {
    // Tên cột được cố định theo schema của ứng dụng.
    String columnSql = quoting.enquoteIdentifier("Order Detail", true);
    String sql = "SELECT " + columnSql + " FROM order_reports WHERE id = ?";

    try (PreparedStatement ps = connection.prepareStatement(sql)) {
        ps.setLong(1, reportId);
        try (ResultSet rs = ps.executeQuery()) {
            while (rs.next()) {
                String detail = rs.getString(1);
                // Xử lý detail theo ứng dụng.
            }
        }
    }
}
```

Ở đây `enquoteIdentifier` phụ trách **hình thức tên cột**; `setLong` phụ trách **giá trị id**. Tên `Order Detail` phải tồn tại đúng theo quy tắc đặt tên/nháy của DB, và driver phải hỗ trợ quoted identifiers. Nếu tên bảng/cột được người dùng chọn, trước hết phải ánh xạ lựa chọn của họ tới danh sách đối tượng được phép; quoting không kiểm tra quyền hay tính đúng đắn của nghiệp vụ.

Không nhất thiết phải dùng `Statement.enquoteIdentifier` trong mọi truy vấn. Với schema dùng tên đơn giản cố định (`order_detail`), SQL trực tiếp như `SELECT order_detail FROM order_reports WHERE id = ?` thường rõ ràng hơn.

## 6. Demo không cần cơ sở dữ liệu: thấy tận mắt kết quả quote

Các phương thức `enquote...` là `default methods` của `Statement`. Demo sau dùng Java dynamic proxy để gọi **triển khai mặc định của JDK**, nhằm xem kết quả tạo chuỗi mà không cần JDBC driver hoặc database. Trong chương trình thực tế, dùng `Statement` được tạo từ `Connection`; driver có thể ghi đè theo dialect.

Tạo tệp `QuoteDemo.java`:

```java
import java.lang.reflect.InvocationHandler;
import java.lang.reflect.Proxy;
import java.sql.Statement;

public final class QuoteDemo {
    public static void main(String[] args) throws Exception {
        Statement demo = (Statement) Proxy.newProxyInstance(
                Statement.class.getClassLoader(),
                new Class<?>[] { Statement.class },
                (proxy, method, argsForMethod) -> {
                    if (method.isDefault()) {
                        return InvocationHandler.invokeDefault(
                                proxy, method, argsForMethod);
                    }
                    throw new UnsupportedOperationException(
                            "This demo does not use a database");
                });

        System.out.println(demo.enquoteLiteral("O'Reilly"));
        System.out.println(demo.enquoteNCharLiteral("Hello"));
        System.out.println(demo.isSimpleIdentifier("customer_name"));
        System.out.println(demo.enquoteIdentifier("customer_name", false));
        System.out.println(demo.enquoteIdentifier("Order Detail", true));
    }
}
```

Biên dịch/chạy với Java 17+:

```bash
javac -encoding UTF-8 QuoteDemo.java
java QuoteDemo
```

Kết quả chính xác của triển khai mặc định JDK:

```text
'O''Reilly'
N'Hello'
true
customer_name
"Order Detail"
```

Dòng đầu là một *string literal* có nháy đơn; dòng cuối là một *identifier* có dấu nháy kép. Chương trình này không thực thi SQL và không tự xác nhận kiểu quoting phù hợp với mọi hệ quản trị. Việc dùng proxy chỉ phục vụ demo độc lập; không cần đem proxy vào code JDBC thông thường.

## 7. Bảng quyết định nhanh

| Nhu cầu thực tế | Cách dùng phù hợp | Tránh |
| --- | --- | --- |
| Lọc theo email, tên, ID, giá, ngày | `PreparedStatement` + `?` + `setXxx` đúng kiểu | Nối dữ liệu nhập vào SQL, hoặc chỉ escape bằng tay |
| Cần SQL `NULL` | `ps.setNull(index, Types.XXX)` đúng SQL type | Nối `"NULL"` rồi đặt nháy thành `'NULL'` |
| Lập câu SQL có literal chuỗi đặc thù từ nguồn đã kiểm soát | Cân nhắc `Statement.enquoteLiteral` đúng ngữ cảnh driver | Gọi đó là bind tham số hoặc thay thế parameterization |
| Literal `N'...'` cho dialect hỗ trợ | `enquoteNCharLiteral` nếu thật sự cần sinh văn bản SQL | Dùng nó thay `setNString` cho dữ liệu từ người dùng |
| Identifier có dấu cách/ký tự đặc biệt trong schema | `enquoteIdentifier` sau khi tên đối tượng đã được xác định hợp lệ | Cho raw user input quyết định truy cập bảng/cột |
| Người dùng chọn sort theo tên/thời gian | `switch`/map allowlist sang SQL token cố định | `ORDER BY ?` hoặc `ORDER BY ` + raw input |
| Kiểm tra tên có dạng identifier đơn giản | `isSimpleIdentifier` khi cần kiểm tra cú pháp tên | Coi kết quả `true` là đã phân quyền/allowlist |
| Nhiều giá trị trong `IN (...)` | Sinh số lượng `?` hợp lệ và bind từng giá trị | Nối chuỗi phần tử input vào danh sách SQL |

### Lỗi phổ biến và cách sửa

1. **Ghép dữ liệu trước rồi mới gọi `prepareStatement`:** vẫn có nguy cơ injection. Hãy giữ SQL template cố định và bind qua `setXxx`.
2. **Đặt marker trong dấu nháy:** `WHERE email = '?'` không chứa parameter marker thực sự. Viết `WHERE email = ?`.
3. **Dùng `enquoteIdentifier` như bộ lọc bảo mật:** một identifier có quoting hợp lệ vẫn có thể trỏ tới đối tượng không được phép. Dùng allowlist, phân quyền nghiệp vụ và quyền DB tối thiểu.
4. **Cho rằng mọi driver quote giống nhau:** ký tự phân cách tên cột/bảng và hỗ trợ national-character literal phụ thuộc DB. Chạy kiểm thử với JDBC driver và database thật khi cần quoted identifier.
5. **Cho rằng `isSimpleIdentifier` chứng minh tên không phải từ khóa, tên có tồn tại, hoặc người dùng có quyền:** phương thức chỉ giúp phân loại tên theo triển khai hiện hành.
6. **Tin rằng thay dấu `'` bằng `''` đủ xử lý mọi dữ liệu:** việc escape SQL literal có thể phụ thuộc cú pháp; binding vẫn là cách chuẩn cho giá trị động.
7. **Quên quản lý tài nguyên:** đóng `PreparedStatement`, `ResultSet` và `Statement` bằng `try-with-resources`; không coi hàm quoting là truy vấn thật.
8. **Nhầm SQL injection với authorization:** parameterization ngăn input thay đổi cú pháp; ứng dụng vẫn phải kiểm tra người dùng có được phép đọc/sửa bản ghi tương ứng hay không.

## 8. Câu hỏi ôn tập

1. `enquoteLiteral("O'Reilly")` tạo ra gì? So với `ps.setString(1, "O'Reilly")`, khác biệt quan trọng nhất là gì?
2. `enquoteIdentifier("Order Detail", true)` xử lý thành phần nào của SQL? Tại sao không nên đưa trực tiếp tên bảng do người dùng nhập vào phương thức này?
3. Vì sao `WHERE username = '?'` không hoạt động như tham số của `PreparedStatement`?
4. Tại sao `ORDER BY ?` không phải cách chuẩn để cho phép khách chọn cột sắp xếp?
5. Khi người dùng muốn sort theo `name` hoặc `created`, hãy nêu allowlist phù hợp và vị trí nào vẫn dùng `?`.
6. Nếu `isSimpleIdentifier("users")` trả `true`, còn cần kiểm tra gì trước khi cho người dùng truy cập dữ liệu?
7. Với cột national-character, khi nào cần `setNString` và khi nào mới có lý do dùng `enquoteNCharLiteral`?

**Điều cần nhớ:** `Statement.enquote...` hỗ trợ **biểu diễn SQL literal/identifier**; `PreparedStatement` hỗ trợ **tham số hóa giá trị**; allowlist bảo vệ **cấu trúc truy vấn được chọn động**. Trong ứng dụng Java hiện đại, dữ liệu đến từ bên ngoài nên được bind; việc trích dẫn identifier chỉ áp dụng khi thực sự cần và sau khi đối tượng được phép đã được xác định.
