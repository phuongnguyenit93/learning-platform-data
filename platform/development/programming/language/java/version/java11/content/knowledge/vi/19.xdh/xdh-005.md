# XECPublicKey và XECPrivateKey trong XDH — Java 11+

## 1. Tổng quan: hai kiểu khóa chuyên dụng cho X25519 và X448

Java 11 bổ sung các API **XDH** (Elliptic Curve Diffie–Hellman theo **RFC 7748**) để hai bên thỏa thuận một bí mật chung bằng **X25519** hoặc **X448**. Trong Java Cryptography Architecture (**JCA/JCE**), kết quả của quá trình tạo khóa có thể được biểu diễn bằng hai interface trong package `java.security.interfaces`:

- **`XECPublicKey`**: biểu diễn khóa công khai của X25519/X448 bằng **tọa độ `u`** của điểm trên đường cong Montgomery.
- **`XECPrivateKey`**: biểu diễn khóa riêng dưới dạng **scalar đã được mã hóa**, có thể truy cập thông qua `Optional<byte[]>` nếu provider cho phép xuất.
- Cả hai đều mở rộng **`XECKey`** để cung cấp tham số đường cong qua `getParams()`.

Các interface này xuất hiện từ **Java 11** và vẫn có hiệu lực trên các JDK hiện đại. Chúng phục vụ những thao tác như `KeyPairGenerator`, `KeyFactory` và `javax.crypto.KeyAgreement`. **Không nhầm XDH với chữ ký số:** X25519/X448 thỏa thuận khóa; không dùng `XECPublicKey` để thay thế API chữ ký RSA/ECDSA/EdDSA.

Ví dụ thường gặp: Alice và Bob mỗi người tạo một cặp X25519, trao đổi **public key**, rồi dùng private key của mình kết hợp với public key của người kia. Nếu không có can thiệp, họ tạo ra cùng một **shared secret**:

```text
Alice                              Bob
(private A, public A)               (private B, public B)
       |------ public A ----------->|
       |<----- public B ------------|
       |                             |
KeyAgreement(private A, public B)   KeyAgreement(private B, public A)
       |                             |
       +------ shared secret -------+
               (hai bên bằng nhau)
```

Không gửi **private key** hay raw scalar. **Shared secret chưa tự cung cấp xác thực đối tác** và không nên đưa trực tiếp vào thuật toán mã hóa ứng dụng; cần giao thức bắt tay có xác thực, KDF và quản lý khóa đúng thiết kế.

## 2. Quan hệ interface và kiểu dữ liệu

| Interface | Kế thừa | Phương thức đặc trưng | Mục đích |
| --- | --- | --- | --- |
| `XECKey` | Interface nền của khóa theo RFC 7748 | `AlgorithmParameterSpec getParams()` | Cho biết bộ tham số, chẳng hạn `NamedParameterSpec.X25519` hoặc `X448`. |
| `XECPublicKey` | `XECKey`, `PublicKey` | `BigInteger getU()` | Đọc tọa độ `u` của khóa công khai theo RFC 7748. |
| `XECPrivateKey` | `XECKey`, `PrivateKey` | `Optional<byte[]> getScalar()` | Lấy một **bản sao raw scalar chưa clamp** nếu khóa có thể xuất; có thể `Optional.empty()`. |
| `PublicKey` / `PrivateKey` | `java.security.Key` | `getAlgorithm()`, `getEncoded()`, `getFormat()` | Metadata chung và encoding khóa nếu provider hỗ trợ. |

Chữ ký Java 11 quan trọng:

```java
public interface XECKey {
    AlgorithmParameterSpec getParams();
}

public interface XECPublicKey extends XECKey, PublicKey {
    BigInteger getU();
}

public interface XECPrivateKey extends XECKey, PrivateKey {
    Optional<byte[]> getScalar();
}
```

Bảng trên trình bày **các chữ ký cốt lõi đã lược bớt import**, không phải khai báo interface ứng dụng cần tự tạo. Trong chương trình thật, chỉ import các interface đã có của JDK; **không** định nghĩa lại chúng.

Khóa `XECPublicKey` khác `java.security.interfaces.ECPublicKey`: XDH theo RFC 7748 sử dụng biểu diễn điểm bằng riêng **`u`**, còn kiểu EC truyền thống được thiết kế cho các tham số/điểm Weierstrass, có API khác. Khóa `XECPrivateKey` cũng khác `ECPrivateKey`. Không ép kiểu một khóa X25519 thành `ECPublicKey`, `ECPrivateKey` để dùng `getW()` hoặc `getS()`.

## 3. `XECPublicKey.getU()`: tọa độ `u` chứ không phải toàn bộ khóa đã mã hóa

`XECPublicKey.getU()` trả một `java.math.BigInteger` biểu diễn **tọa độ `u`** của điểm trên đường cong Montgomery. RFC 7748 mô tả phép nhân scalar dùng **tọa độ `u`** và cấu trúc X25519/X448; không cần một cặp tọa độ `(x, y)` như nhiều API elliptic curve khác.

```java
XECPublicKey publicKey = (XECPublicKey) pair.getPublic();
BigInteger coordinate = publicKey.getU();
AlgorithmParameterSpec params = publicKey.getParams();
```

Đây là **đoạn minh họa** đặt trong chương trình đã có biến `pair` kiểu `KeyPair` và các import phù hợp.

**Ba điểm đặc biệt quan trọng:**

1. `getU()` trả **giá trị số** của tọa độ, **không** trả byte raw public key và **không** phải ASN.1/X.509-encoded public key.
2. Hợp đồng interface cho phép `BigInteger` chứa cả giá trị **không theo biểu diễn trường canonical**; không suy ra rằng chỉ kiểm tra `getU()` khác 0 là đủ để xác minh một public key không tin cậy. Phải dùng API provider/kiểm tra hợp lệ ở đúng giao thức.
3. `BigInteger.toByteArray()` dùng **big-endian, signed two's complement, độ dài biến thiên**. Trong khi đó, wire encoding của tọa độ X25519/X448 theo RFC 7748 có dạng **little-endian, độ dài cố định** (32 byte cho X25519, 56 byte cho X448). Vì vậy **không** gửi thẳng `getU().toByteArray()` nếu bên kia chờ raw RFC 7748 public key.

Khi cần **truyền/lưu khóa công khai** bằng định dạng chuẩn giữa các Java implementation, thường dùng:

```java
byte[] subjectPublicKeyInfo = pair.getPublic().getEncoded();
```

Với provider thông dụng hỗ trợ xuất khóa, `PublicKey.getEncoded()` thường là **X.509 SubjectPublicKeyInfo (SPKI) DER**, *không* phải raw 32 byte X25519. Luôn thỏa thuận encoding với hệ thống nhận. `getEncoded()` có thể trả `null` đối với khóa/provider không hỗ trợ xuất.

## 4. `XECPrivateKey.getScalar()`: `Optional<byte[]>`, chưa clamp và cần bảo vệ

`XECPrivateKey` cho phép đọc scalar mã hóa của private key qua:

```java
Optional<byte[]> maybeScalar = privateKey.getScalar();
```

Đoạn này giả định `privateKey` có kiểu `XECPrivateKey`. **Không** có phương thức `getS()` theo kiểu `ECPrivateKey`.

### Tại sao trả `Optional<byte[]>`?

Không phải mọi private key đều xuất được. Private key có thể nằm trong **hardware security module (HSM)**, token hoặc provider đánh dấu non-extractable. Khi đó `getScalar()` có thể trả **`Optional.empty()`** dù đối tượng private key vẫn dùng được với `KeyAgreement` thông qua provider phù hợp.

Không được viết:

```java
byte[] scalar = privateKey.getScalar().get(); // Không an toàn.
```

Với khóa không cho xuất, câu lệnh sẽ ném `NoSuchElementException`. Nếu một tác vụ thực sự được cấp quyền xuất scalar, phải xử lý nhánh rỗng, bảo vệ dữ liệu, không log, không đưa vào URL, telemetry hay source control.

Theo Javadoc Java 11, **mỗi lần `getScalar()` trả dữ liệu, mảng byte là một bản sao mới**. Việc xóa mảng nhận được **không xóa private key gốc trong provider**, nhưng giảm thời gian một bản sao private data còn hiện diện trong RAM:

```java
privateKey.getScalar().ifPresent(bytes -> {
    try {
        // Chỉ xử lý scalar nếu có yêu cầu rõ ràng.
        System.out.println("scalarLength=" + bytes.length);
    } finally {
        Arrays.fill(bytes, (byte) 0);
    }
});
```

Đây là **đoạn minh họa** cho việc dọn bản sao byte, không phải hướng dẫn xuất khóa mặc định hay chương trình độc lập. In **độ dài** chỉ phục vụ học tập; **tuyệt đối không** in giá trị scalar.

### “Unpruned” hay “unclamped” là gì?

RFC 7748 quy định một bước xử lý một số bit của scalar trước phép tính mật mã, gọi là **pruning/clamping**. `XECPrivateKey.getScalar()` trả **byte được mã hóa trước khi pruning**, không phải scalar đã được điều chỉnh bit cho phép tính. `XECPrivateKeySpec` cũng biểu diễn raw scalar **unpruned**.

Bước pruning là trách nhiệm của implementation mật mã khi thực hiện X25519/X448. Không tự ý làm thay đổi bit của scalar trước khi đưa cho `KeyAgreement` hoặc `KeyFactory`, trừ khi bạn đang thực hiện một giao thức/định dạng đã được đặc tả và kiểm thử chính xác. **Không** băm `getScalar()` rồi coi đó là shared secret: private scalar và shared secret là những dữ liệu khác nhau.

## 5. `getParams()`, `NamedParameterSpec` và lựa chọn X25519/X448

`XECKey.getParams()` trả về `AlgorithmParameterSpec`, thường là `NamedParameterSpec` trong các provider hỗ trợ XDH:

```java
AlgorithmParameterSpec params = publicKey.getParams();
if (params instanceof NamedParameterSpec) {
    String curve = ((NamedParameterSpec) params).getName();
    System.out.println(curve);
}
```

Dạng khai báo:

- `NamedParameterSpec.X25519`: bộ tham số RFC 7748 cho X25519.
- `NamedParameterSpec.X448`: bộ tham số RFC 7748 cho X448.

**Không nhầm tên tham số với tên JCA service:**

| Tên | Vai trò |
| --- | --- |
| `XDH` | Tên thuật toán chung của các service key agreement, key generation và key factory hỗ trợ họ RFC 7748. |
| `X25519` | Tên service cụ thể và tên bộ tham số cho X25519. |
| `X448` | Tên service cụ thể và tên bộ tham số cho X448. |
| `NamedParameterSpec.X25519` | Đối tượng `AlgorithmParameterSpec` chọn **đường cong** X25519 khi khởi tạo service linh hoạt. |
| `NamedParameterSpec.X448` | Đối tượng chọn X448. |

Hai cách tạo cặp X25519 thông dụng:

```java
KeyPairGenerator concrete = KeyPairGenerator.getInstance("X25519");
KeyPair pair1 = concrete.generateKeyPair();

KeyPairGenerator general = KeyPairGenerator.getInstance("XDH");
general.initialize(NamedParameterSpec.X25519);
KeyPair pair2 = general.generateKeyPair();
```

Đoạn này cần import `KeyPairGenerator`, `KeyPair` và `NamedParameterSpec`; không phải chương trình độc lập. Với `XDH`, nên **chọn tham số tường minh**, không vô tình phụ thuộc curve mặc định mà provider sử dụng.

Provider **SunEC** của JDK 11 hỗ trợ `XDH`, `X25519`, `X448` cho `KeyPairGenerator`, `KeyFactory` và `KeyAgreement`. Tuy nhiên, khả năng của môi trường khác (provider tùy biến, FIPS/HSM) cần được xác minh: tên thuật toán được định nghĩa chuẩn **không bảo đảm** một provider bất kỳ thực hiện tất cả các curve.

X25519 thường dùng shared secret dài **32 byte**, X448 dài **56 byte**. Số **255** trong “X25519” là danh xưng curve/function, **không phải** yêu cầu truyền một mảng 255 byte.

## 6. Ví dụ hoàn chỉnh: inspect XEC keys, dựng lại public key, thỏa thuận X25519

Chương trình sau:

1. Tạo hai cặp X25519 (Alice và Bob) bằng `KeyPairGenerator`.
2. Ép các khóa sang `XECPublicKey` / `XECPrivateKey` và đọc `getParams()`, `getU()`.
3. Gọi `getScalar()` để minh họa `Optional`, nhưng **không in raw private scalar**; nếu có bản sao được xuất thì xóa nó.
4. Dùng `XECPublicKeySpec` và `KeyFactory` để dựng lại một public key từ `params + u`, đồng thời đọc/khôi phục encoding X.509 của public key.
5. Dùng `KeyAgreement` ở cả Alice/Bob để nhận cùng một shared secret X25519 dài 32 byte; in **kết quả so sánh**, không in giá trị bí mật.

Tạo tệp **`XecKeysDemo.java`**:

```java
import java.security.KeyFactory;
import java.security.KeyPair;
import java.security.KeyPairGenerator;
import java.security.MessageDigest;
import java.security.PublicKey;
import java.security.interfaces.XECPrivateKey;
import java.security.interfaces.XECPublicKey;
import java.security.spec.NamedParameterSpec;
import java.security.spec.X509EncodedKeySpec;
import java.security.spec.XECPublicKeySpec;
import java.util.Arrays;
import java.util.Optional;
import javax.crypto.KeyAgreement;

public class XecKeysDemo {
    public static void main(String[] args) throws Exception {
        KeyPairGenerator generator = KeyPairGenerator.getInstance("X25519");
        KeyPair alice = generator.generateKeyPair();
        KeyPair bob = generator.generateKeyPair();

        XECPublicKey alicePublic = (XECPublicKey) alice.getPublic();
        XECPrivateKey alicePrivate = (XECPrivateKey) alice.getPrivate();
        NamedParameterSpec publicParams =
                (NamedParameterSpec) alicePublic.getParams();
        NamedParameterSpec privateParams =
                (NamedParameterSpec) alicePrivate.getParams();

        System.out.println("publicInterface=" +
                (alice.getPublic() instanceof XECPublicKey));
        System.out.println("privateInterface=" +
                (alice.getPrivate() instanceof XECPrivateKey));
        System.out.println("publicCurve=" + publicParams.getName());
        System.out.println("privateCurve=" + privateParams.getName());
        System.out.println("uNonnegative=" +
                (alicePublic.getU().signum() >= 0));

        Optional<byte[]> exportedScalar = alicePrivate.getScalar();
        exportedScalar.ifPresent(bytes -> Arrays.fill(bytes, (byte) 0));
        System.out.println("scalarReturnType=Optional<byte[]>");

        KeyFactory factory = KeyFactory.getInstance("X25519");
        XECPublicKey rebuilt = (XECPublicKey) factory.generatePublic(
                new XECPublicKeySpec(alicePublic.getParams(),
                        alicePublic.getU()));
        System.out.println("publicSpecRoundTrip=" +
                rebuilt.getU().equals(alicePublic.getU()));

        PublicKey decoded = factory.generatePublic(
                new X509EncodedKeySpec(alice.getPublic().getEncoded()));
        System.out.println("x509RoundTrip=" +
                Arrays.equals(decoded.getEncoded(),
                        alice.getPublic().getEncoded()));

        KeyAgreement aliceAgreement = KeyAgreement.getInstance("X25519");
        aliceAgreement.init(alice.getPrivate());
        aliceAgreement.doPhase(bob.getPublic(), true);
        byte[] aliceSecret = aliceAgreement.generateSecret();

        KeyAgreement bobAgreement = KeyAgreement.getInstance("X25519");
        bobAgreement.init(bob.getPrivate());
        bobAgreement.doPhase(alice.getPublic(), true);
        byte[] bobSecret = bobAgreement.generateSecret();

        try {
            System.out.println("sharedLength=" + aliceSecret.length);
            System.out.println("sharedEqual=" +
                    MessageDigest.isEqual(aliceSecret, bobSecret));
        } finally {
            Arrays.fill(aliceSecret, (byte) 0);
            Arrays.fill(bobSecret, (byte) 0);
        }
    }
}
```

Biên dịch và chạy với **JDK 17+** (đã kiểm tra cú pháp bằng chế độ `--release 11`, mã chỉ dùng API Java 11):

```bash
javac --release 11 XecKeysDemo.java
java XecKeysDemo
```

**Stdout chính xác trên JDK cung cấp provider SunEC thông dụng:**

```text
publicInterface=true
privateInterface=true
publicCurve=X25519
privateCurve=X25519
uNonnegative=true
scalarReturnType=Optional<byte[]>
publicSpecRoundTrip=true
x509RoundTrip=true
sharedLength=32
sharedEqual=true
```

Đây là kết quả đã được **biên dịch với `javac --release 11` và chạy trên OpenJDK 21**. Khóa được tạo ngẫu nhiên ở mỗi lần chạy, nhưng các mệnh đề kiểm tra trong ví dụ vẫn có kết quả ổn định với provider SunEC. Nếu chạy với HSM hoặc provider tùy biến, không được giả định nó luôn cho phép `getScalar()`/`getEncoded()` hoặc trả tham số bằng đúng class `NamedParameterSpec`; cần điều chỉnh trường hợp provider đó.

### Giải thích cụ thể

- `instanceof XECPublicKey` / `XECPrivateKey` xác nhận interface phù hợp cho cặp khóa X25519.
- `getParams()` trả `NamedParameterSpec`; `getName()` là `X25519`. Hai khóa của cùng một cặp phải dùng tham số tương thích.
- `getU()` là một tọa độ số. Với cặp public key được SunEC sinh, `signum() >= 0`; câu lệnh này **không phải phép kiểm tra an toàn khóa từ đối tác**.
- `getScalar()` trả `Optional<byte[]>`; code không giả định `Optional` có dữ liệu. Chỉ xóa **bản sao** nếu có, không đưa private scalar ra stdout.
- `KeyFactory.generatePublic(new XECPublicKeySpec(...))` dựng lại khóa từ `curve + u`. `X509EncodedKeySpec` dựng lại khóa từ `SubjectPublicKeyInfo` đã mã hóa; hai cách **không dùng cùng loại input**.
- Alice dùng `alice.getPrivate()` và `bob.getPublic()`; Bob đảo lại. `MessageDigest.isEqual` xác nhận hai shared secret bằng nhau mà không in giá trị.
- `Arrays.fill` chỉ xóa **những mảng secret có trong chương trình**, không bảo đảm xóa mọi bản sao/buffer còn lại bên trong JDK/GC. Trong ứng dụng thực, hạn chế vòng đời và số bản sao bí mật.

## 7. KeyFactory và các dạng KeySpec cho XEC

Java 11 có cả hai spec:

```java
new XECPublicKeySpec(AlgorithmParameterSpec params, BigInteger u);
new XECPrivateKeySpec(AlgorithmParameterSpec params, byte[] scalar);
```

Đây là **mô tả constructor**, không phải hai lời gọi hợp lệ khi chưa có biến `params`, `u`, `scalar`. Dạng public dựa vào tọa độ `u`; dạng private dựa vào scalar **unpruned**.

Ví dụ **minh họa**, dùng khi có quyền xuất raw private key và có nhu cầu chuyển đổi provider:

```java
XECPrivateKey original = (XECPrivateKey) pair.getPrivate();
Optional<byte[]> scalarOptional = original.getScalar();

if (scalarOptional.isPresent()) {
    byte[] scalarCopy = scalarOptional.get();
    try {
        KeyFactory factory = KeyFactory.getInstance("X25519");
        XECPrivateKeySpec spec = new XECPrivateKeySpec(
                original.getParams(), scalarCopy);
        XECPrivateKey reconstructed = (XECPrivateKey)
                factory.generatePrivate(spec);
        // Dùng reconstructed trong một phạm vi được quản lý an toàn.
    } finally {
        Arrays.fill(scalarCopy, (byte) 0);
    }
}
```

Đoạn này **không phải chương trình độc lập**; cần `pair` và các import `KeyFactory`, `Optional`, `Arrays`, `XECPrivateKeySpec`. Khi tạo `XECPrivateKeySpec`, constructor **sao chép mảng** để chống thay đổi từ bên ngoài, do đó xóa `scalarCopy` không xóa bản sao bên trong `spec`. Cần quản lý cả vòng đời object/spec và bí mật còn được giữ. **Không xuất private key chỉ để kiểm tra nó hoạt động**: thực hành tốt là giao việc ký/thỏa thuận khóa cho provider/HSM và giữ khóa không thể xuất nếu có thể.

Ngoài KeySpec, cách lưu/trao đổi private key có kiểm soát giữa hệ thống thường sử dụng **PKCS#8 DER** khi provider cho phép:

```java
byte[] pkcs8 = pair.getPrivate().getEncoded();
byte[] spki = pair.getPublic().getEncoded();
```

Theo hợp đồng `Key.getEncoded()`, có thể nhận `null` nếu key không cho xuất. **Đừng coi `pkcs8` là chính raw scalar** và đừng coi `spki` là chính 32 byte raw public key. Khi khôi phục từ encoding chuẩn, dùng `PKCS8EncodedKeySpec` hoặc `X509EncodedKeySpec` tương ứng với `KeyFactory`. Đặc biệt, **không** lưu PKCS#8 private key không mã hóa ở nơi không có biện pháp bảo vệ truy cập.

## 8. Đúng định dạng byte: tại sao không gửi `getU().toByteArray()`?

X25519 và X448 quy định cách biểu diễn raw u-coordinate theo RFC 7748:

| Curve | Raw public u-coordinate | Raw private scalar input | Kết quả `generateSecret()` |
| --- | --- | --- | --- |
| X25519 | 32 byte little-endian | 32 byte | 32 byte |
| X448 | 56 byte little-endian | 56 byte | 56 byte |

Bảng này nói về **wire/raw representation theo RFC 7748**, **không** phải độ dài của `getEncoded()` dạng SPKI/PKCS#8. Giá trị private scalar theo `XECPrivateKeySpec`/`getScalar()` là bytes **trước bước pruning/clamping**. Các triển khai JCA thực hiện bước cần thiết theo thuật toán.

`BigInteger.toByteArray()` tạo mảng **big-endian có dấu**, có thể thêm byte 0 phía trước để giữ số dương hoặc trả độ dài ngắn hơn số byte cố định. Vì thế nó không phải cách xuất raw X25519/X448 đúng giao thức. Nếu cần tương tác với giao thức raw, phải triển khai/chọn serializer có kiểm soát **endianness, độ dài cố định, bit mask và các quy tắc RFC 7748**, kiểm thử bằng vector RFC; ưu tiên thư viện giao thức được thẩm định thay vì tự viết phép toán và serialization mật mã.

Khi trao đổi khóa **giữa các ứng dụng Java**, phương án dễ tránh lỗi hơn là thống nhất dùng `getEncoded()` và `X509EncodedKeySpec` cho public key; chỉ dùng raw encoding nếu hệ thống bên kia thật sự yêu cầu.

Lưu ý rằng `XECPublicKeySpec` cho phép truyền `BigInteger u`, nhưng **tạo đối tượng spec thành công** chưa chứng minh đây là public key hợp lệ/an toàn để dùng với một peer không tin cậy. `KeyFactory` và `KeyAgreement` có thể từ chối các khóa không tương thích hoặc giá trị không an toàn bằng exception; xử lý lỗi thay vì tự bỏ qua kiểm tra.

## 9. Cơ chế `KeyAgreement` và việc dùng shared secret an toàn

Với XDH hai bên:

```java
KeyAgreement agreement = KeyAgreement.getInstance("X25519");
agreement.init(myPrivateKey);
agreement.doPhase(peerPublicKey, true);
byte[] ikm = agreement.generateSecret();
```

Đoạn **minh họa** với `myPrivateKey` và `peerPublicKey` có kiểu tương thích (private/public của X25519). `doPhase(peerPublicKey, true)` báo pha cuối trong thỏa thuận khóa hai bên. `generateSecret()` tạo byte chung; nếu hai bên chọn đúng key và không có can thiệp, kết quả trùng nhau.

### Shared secret không tự cung cấp xác thực

Khi public keys trao đổi trên một kênh **không có xác thực**, kẻ tấn công có thể thay public key của từng phía, lập ra hai shared secret riêng (man-in-the-middle). XDH chỉ cung cấp thao tác **thỏa thuận bí mật**. Nếu muốn bảo mật giao tiếp end-to-end, cần giao thức đầy đủ để xác thực peer, xác thực transcript, chống replay và quản lý vòng đời khóa. TLS 1.3 là một ví dụ giao thức đã giải quyết nhiều phần của việc bắt tay an toàn, nhưng **không nên tự tái tạo TLS** bằng vài lời gọi `KeyAgreement`.

### Không dùng trực tiếp output làm AES key

`generateSecret()` trả **input keying material (IKM)** cho quá trình dẫn xuất khóa. Trong một giao thức an toàn, thường cần KDF (ví dụ **HKDF theo RFC 5869**), cùng salt và context/info thích hợp với mục đích sử dụng, để tạo khóa phiên, nonce hoặc khóa cho từng hướng truyền. Không mã hóa ngay bằng shared secret như một “AES key 32 byte” rồi mặc định đã có giao thức an toàn.

Nếu một giao thức buộc phải xử lý public keys không tin cậy, cần bảo vệ trường hợp điểm bậc nhỏ khiến shared secret trở thành toàn số 0. RFC 7748 mô tả việc kiểm tra all-zero; một số provider có thể **từ chối khóa/pha thỏa thuận không hợp lệ**, nhưng không nên thay hợp đồng giao thức chỉ bằng kỳ vọng vào một implementation cụ thể.

### Giới hạn thời gian tồn tại và logging

Không in raw private scalar, `getEncoded()` của private key hoặc shared secret ra log. Không lưu chúng trong `String` không thể xóa. Với các mảng bí mật do ứng dụng sở hữu, hạn chế bản sao và `Arrays.fill` khi đã dùng xong. Nếu thiết kế sử dụng ephemeral X25519, tạo cặp mới theo mỗi phiên/handshake cần thiết, không tái sử dụng private key không kiểm soát. Quản lý phiên và xác thực quan trọng không kém lựa chọn curve.

## 10. Lỗi thường gặp

| Sai lầm | Lý do | Cách đúng |
| --- | --- | --- |
| Ép `XECPublicKey` thành `ECPublicKey` | Khác biểu diễn curve/point và interface | Dùng `XECPublicKey.getU()` cùng `XECKey.getParams()`. |
| Nghĩ `getU()` trả `byte[]` | `getU()` trả `BigInteger` | Dùng `getU()` cho tọa độ số, dùng chuẩn encoding khi truyền dữ liệu. |
| Gửi thẳng `getU().toByteArray()` cho hệ thống chờ raw X25519 | Signed big-endian khác 32 byte little-endian | Dùng serializer RFC 7748 đã kiểm thử hoặc SPKI nếu hai bên hỗ trợ. |
| Gọi `getScalar().get()` mà không kiểm tra | `Optional` có thể rỗng | Xử lý `isPresent()` hoặc dùng khóa trực tiếp qua provider. |
| Ghi scalar ra log để debug | Rò private key | Chỉ in metadata không nhạy cảm và bảo vệ dữ liệu bí mật. |
| Nghĩ `getScalar()` trả scalar đã clamp | Javadoc nói **unpruned** | Để implementation XDH xử lý pruning đúng RFC. |
| Dùng `XECPrivateKey` để ký ECDSA/EdDSA | XDH dùng thỏa thuận khóa, không phải signature key | Chọn API chữ ký và loại khóa tương ứng. |
| Trộn X25519 private với X448 public | Không cùng bộ tham số, không thể thỏa thuận đúng | Kiểm tra `getParams()` và giao thức; xử lý `InvalidKeyException`. |
| Nhầm raw 32 byte với `getEncoded()` của public key | Encoding SPKI DER có cấu trúc ASN.1 | Dùng `X509EncodedKeySpec` cho SPKI, PKCS#8 cho private. |
| Coi shared secret là khóa AES cuối cùng | Thiếu KDF, authentication, context và quản lý khóa | Dùng HKDF/giao thức đã được thẩm định, xác thực peer. |
| Không xử lý khóa non-extractable | HSM có thể không trả scalar/encoding | Thiết kế xử lý provider key handle, không yêu cầu xuất để dùng. |
| Viết test assert tọa độ `u` hay private scalar cố định từ `generateKeyPair()` | Keypair được sinh ngẫu nhiên | Assert đường cong, độ dài, equality thỏa thuận; không dùng giá trị khóa cố định. |

## 11. Câu hỏi tự kiểm tra

**Câu 1:** `XECPublicKey.getU()` trả kiểu gì? Nó có phải ASN.1-encoded public key không?

**Đáp án:** `BigInteger` chứa tọa độ `u`; **không** phải SPKI DER hay raw RFC 7748 encoding.

**Câu 2:** Tại sao `XECPrivateKey.getScalar()` trả `Optional<byte[]>`?

**Đáp án:** Vì private key không nhất thiết có thể xuất raw scalar, chẳng hạn private key được giữ trong HSM. Nếu có dữ liệu, nó là một bản sao và ở dạng **unpruned**.

**Câu 3:** Phải dùng loại manager/factory nào để dựng lại khóa công khai từ `params + u`?

**Đáp án:** `KeyFactory` và `XECPublicKeySpec` (với các tham số đường cong tương ứng). Không dùng `KeyManagerFactory` TLS, vì đó là API quản lý định danh TLS khác mục đích.

**Câu 4:** `MessageDigest.isEqual(aliceSecret, bobSecret) == true` chứng minh những gì và không chứng minh điều gì?

**Đáp án:** Hai bên tính được cùng shared secret; **không** chứng minh public key đã được xác thực là thuộc đúng Alice/Bob. Vẫn cần xác thực peer và KDF trong giao thức thật.

**Câu 5:** Có thể dùng `getU().toByteArray()` trực tiếp làm raw public key X25519 32 byte không?

**Đáp án:** Không. `BigInteger` xuất signed big-endian độ dài biến thiên, còn raw X25519 dùng 32 byte little-endian với quy tắc RFC 7748.

**Câu 6:** Vì sao không được assume `getEncoded()` của private key luôn có dữ liệu?

**Đáp án:** Khóa non-extractable hoặc provider có thể không hỗ trợ encoding và trả `null`. Ứng dụng cần làm việc qua khóa/provider mà không xuất nó nếu có thể.

**Câu 7:** Muốn tạo XDH với tham số X448 thay vì X25519, cần thay đổi gì?

**Đáp án:** Tạo `KeyPairGenerator.getInstance("X448")` hoặc `getInstance("XDH")` rồi `initialize(NamedParameterSpec.X448)`, và dùng `KeyAgreement` tương thích curve X448 ở cả hai bên. Shared secret X448 dài 56 byte.

**Ghi nhớ:** **`XECPublicKey` = public point qua `getU(): BigInteger`**; **`XECPrivateKey` = raw private scalar qua `getScalar(): Optional<byte[]>` khi provider cho xuất**, ở dạng **unpruned**. Cả hai cung cấp `getParams()` qua `XECKey`. Dùng `KeyPairGenerator` và `KeyAgreement` cho X25519/X448, `KeyFactory` + XEC specs để dựng lại khóa, và encoding đúng chuẩn khi trao đổi. Luôn bảo vệ private scalar/shared secret, xác thực public key của peer và dùng KDF/giao thức được thiết kế an toàn.
