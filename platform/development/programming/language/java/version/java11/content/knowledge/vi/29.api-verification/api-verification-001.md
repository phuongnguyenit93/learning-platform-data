# Biên dịch với mức nguồn, API và bytecode được xác định (Java 11+)

**Chủ đề cha: Kiểm chứng API.** Một chương trình được viết trên JDK mới có thể biên dịch thành class file mà JVM Java 11 đọc được, nhưng vẫn vô tình gọi **API chỉ có ở Java 12/17/21**. Đến lúc chạy thật trên Java 11, chương trình mới thất bại với `NoSuchMethodError` hoặc lỗi liên kết khác. Muốn phát hành thư viện, dịch vụ hoặc CLI tương thích Java 11, phải kiểm chứng **ba mức tương thích riêng biệt**:

1. **Ngôn ngữ nguồn (source level):** được dùng cú pháp Java của phiên bản nào?
2. **API của nền tảng (platform API level):** được tham chiếu đến lớp, phương thức, trường và module nào của Java/JDK?
3. **Định dạng class file/bytecode (target level):** JVM phiên bản tối thiểu nào có thể nạp class?

Trong hệ sinh thái Java hiện đại, lựa chọn mặc định là **`javac --release 11`** (hoặc cấu hình tương đương trong Maven/Gradle). Một option thống nhất cả ba mức: **cú pháp Java 11, các API platform được hỗ trợ ở Java 11, và class file version 55**. Tuy nhiên, `--release` chỉ là **một lớp của hợp đồng tương thích**; vẫn cần kiểm tra dependencies, plugin, reflection và chạy test trên JVM Java 11 thật.

Bài này chỉ sử dụng kiến thức **vẫn còn áp dụng hiện nay**, không khuyến nghị hack `bootclasspath`/các gói JDK nội bộ hoặc cấu hình đã lỗi thời. Ví dụ dùng JDK 17 làm **build JDK** và JDK 11 làm **runtime tối thiểu**, nhưng có thể thay build JDK bằng một bản mới hơn nếu `javac --help` của bản đó còn hỗ trợ `--release 11`.

## 1. Tại sao phải tách ba mức?

Ví dụ một nhóm phát triển viết phần mềm trên JDK 17, muốn khách hàng dùng JVM 11.

```text
Build machine                     Production
JDK 17 javac                      Java 11 runtime
   |                                   |
   | 1) Source syntax <= Java 11       |
   | 2) Platform API <= Java 11        |
   | 3) Class major version = 55       |
   v                                   v
.class / .jar  ------------------> Load/link/execute
                     |
                     +--> còn cần dependencies tương thích
                     +--> còn cần integration/runtime tests
```

Nếu chỉ giới hạn source:

- Người viết không dùng được cú pháp `record` của Java 16, nhưng vẫn có thể gọi phương thức thư viện chuẩn mới của JDK 17.
- Class file có thể mang phiên bản mặc định mới nếu chưa chọn target.

Nếu chỉ giới hạn target:

- Compiler phải tuân ràng buộc kết hợp source/target, nhưng chỉ một mức bytecode **không** chọn API Java 11.
- Một class có major version 55 vẫn có thể chứa tham chiếu phương thức mới, dẫn đến lỗi khi JVM 11 resolve method.

Nếu đã dùng `--release 11`:

- `javac` kiểm tra cú pháp theo Java 11.
- Các API Java/JDK được compiler công bố cho release 11 là tập API có thể sử dụng.
- Generated bytecode nhắm Java 11.

**Đừng đồng nhất ba khái niệm:** “classfile 55” không tự có nghĩa “chỉ dùng API Java 11”; “không dùng cú pháp mới” không tự có nghĩa “chạy trên Java 11”.

## 2. Bảng so sánh option javac

| Lựa chọn | Hạn chế cú pháp nguồn | Hạn chế API Java/JDK tương ứng | Hạn chế class file |
| --- | --- | --- | --- |
| `javac --release 11` | **Có, Java 11** | **Có, API được hỗ trợ của Java 11** | **Có, major 55** |
| `javac -source 11` | Có | **Không tự bảo đảm** | Không đặt target độc lập |
| `javac -target 11` | Không đặt source độc lập | **Không tự bảo đảm** | Có, major 55 |
| `javac -source 11 -target 11` | Có | **Không tự bảo đảm** khi dùng system modules mới hơn | Có, major 55 |
| `javac` không option | Theo version của compiler | Theo JDK compiler đang dùng | Theo mặc định JDK compiler |

**Cú pháp thường dùng:**

```bash
javac --release 11 -encoding UTF-8 -d out Compat11.java
```

`-encoding UTF-8` giúp source tiếng Việt/Unicode được diễn giải rõ ràng, giảm khác biệt máy build; `-d out` đưa class files vào thư mục output. Thư mục `out` được tạo nếu chưa có khi `javac` có thể tạo đường dẫn, nhưng để quy trình rõ ràng có thể tạo trước.

### --release hoạt động ở mức nào?

Theo tài liệu Oracle `javac`, `--release N` kết hợp các giới hạn:

- Java Language Specification của release N;
- Java SE/JDK API được hỗ trợ, xuất bản cho release N;
- Class-file target của release N.

API được chọn **không chỉ là danh sách các package bắt đầu bằng `java.*`**: với mỗi JDK release, một số exported documented JDK APIs cũng thuộc phạm vi có thể tham chiếu. Nhưng **không được dùng `--add-exports` để mở rộng tập gói nội bộ của system modules** khi `--release` chọn một release có module system.

**Không trộn option:** `--release` **không kết hợp** với `-source` hoặc `-target` cho cùng lần biên dịch. Ví dụ dưới đây phải bị từ chối:

```bash
javac --release 11 -source 11 -target 11 Compat11.java
```

Điều này khác với việc dùng `-encoding`, `-d`, `-classpath` hoặc module path phù hợp: những option đó vẫn phục vụ compiler; chúng không thay vai trò của `--release`.

### --release không đồng nghĩa “chọn JDK chạy javac”

`javac --release 11` **không tải xuống hoặc đổi JDK hiện tại thành JDK 11**. Nếu terminal đang dùng JDK 17, javac vẫn là **javac 17** đang thực hiện cross-compilation. Phân biệt:

```bash
java -version
javac -version
javac --help
```

- `java -version`: phiên bản runtime trong PATH.
- `javac -version`: phiên bản compiler trong PATH.
- `javac --help`: xem phiên bản `--release` mà compiler đó hỗ trợ.

Các bản JDK hiện đại chỉ hỗ trợ một **tập hữu hạn** các target cũ; không giả định mọi javac ở tương lai đều còn hỗ trợ mọi release trước đó. Khi compiler báo “release version 11 not supported”, cần chọn toolchain có hỗ trợ, không tự hạ xuống source/target như một cách sửa tương đương.

## 3. Bài chạy được: chỉ sử dụng ngôn ngữ và API Java 11

Đoạn dưới dùng các API đã có tới Java 11:

- `var` cho local variable, từ Java 10;
- `String.strip()`, từ Java 11;
- `Files.writeString()` và `Files.readString()`, từ Java 11;
- `List.of()`, từ Java 9.

### Tệp `Compat11.java`

```java
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.List;

public final class Compat11 {
    public static void main(String[] args) throws Exception {
        var normalized = "   java11   ".strip();
        var items = List.of(normalized, "ready");

        Path file = Files.createTempFile("compat11-", ".txt");
        try {
            Files.writeString(file, String.join(":", items));
            System.out.println(Files.readString(file));
        } finally {
            Files.deleteIfExists(file);
        }
    }
}
```

Biên dịch với **JDK 17** (hoặc JDK mới hỗ trợ `--release 11`):

```bash
mkdir -p out
javac --release 11 -encoding UTF-8 -d out Compat11.java
java -cp out Compat11
```

Output cố định của chương trình khi thư mục tạm writable:

```text
java11:ready
```

**Vì sao output giống nhau trên JDK 11 và JDK 17?** Các APIs trên đã tồn tại trong Java 11. `String.strip()` bỏ các ký tự trắng ở hai đầu; `List.of()` tạo hai phần tử; `String.join(":", items)` tạo `java11:ready`; file tạm được xóa trong `finally`. Mục đích của demo là kiểm chứng build API + bytecode chứ không chạy benchmark.

**Kiểm chứng bắt buộc:** đổi sang terminal dùng **JDK 11 thật** và chạy:

```bash
java -version
java -cp out Compat11
```

Khi `java -version` xác nhận major **11**, câu lệnh thứ hai cũng phải in `java11:ready`. Nếu bạn chỉ chạy trên JDK 17, bạn mới chứng minh **compiler chấp nhận mã**, chưa chứng minh deployment Java 11 hoạt động trong môi trường của bạn.

## 4. Class file version: kiểm chứng bằng javap

JVM không thực thi trực tiếp các tệp `.java` đã biên dịch. Nó đọc class file có header:

```text
CAFEBABE | minor_version | major_version | constant_pool | ...
```

Class-file major version theo các bản phổ biến:

| Java SE | Major version |
| --- | ---: |
| Java 8 | 52 |
| Java 9 | 53 |
| Java 10 | 54 |
| **Java 11** | **55** |
| Java 17 | 61 |
| Java 21 | 65 |
| Java 25 | 69 |
| Java 26 | 70 |

Đừng lấy công thức “major = version + 44” làm bộ kiểm tra cho **mọi** JDK trong lịch sử; dùng bảng phiên bản theo JVMS. Với Java 11, giá trị mong đợi là **55**.

```bash
javap -verbose -classpath out Compat11
```

Trong output rất dài, tìm:

```text
minor version: 0
major version: 55
```

**Lưu ý:** `javap -v` là công cụ đọc class file, **không tự kiểm tra** mọi lời gọi API sẽ tồn tại khi chạy. Hai class cùng có major 55 vẫn có thể khác nhau ở method references, dependencies và lỗi runtime.

### Vì sao classfile 61 không chạy trên Java 11?

Khi class được tạo bởi javac 17 mà không giới hạn target, nó thường có major **61**. Java 11 chỉ hỗ trợ tới major **55**. Nếu nạp class 61 trên Java 11, JVM có thể ném `UnsupportedClassVersionError`. Thông báo đầy đủ phụ thuộc runtime, nhưng nguyên nhân là **định dạng class mới hơn JVM hỗ trợ**.

**Mặt ngược lại:** có classfile major 55 chỉ giải quyết **điều kiện định dạng**. Nó chưa khẳng định mọi method, field và dependency có thật trên Java 11. Phải kết hợp API check với runtime tests.

## 5. Tự đọc header class file bằng Java 11

Nếu viết CI tooling muốn kiểm tra nhanh major/minor mà không parse toàn bộ class file, có thể dùng Java SE APIs chuẩn.

### Tệp `ClassFileHeaderCheck.java`

```java
import java.io.DataInputStream;
import java.nio.file.Files;
import java.nio.file.Path;

public final class ClassFileHeaderCheck {
    public static void main(String[] args) throws Exception {
        if (args.length != 1) {
            throw new IllegalArgumentException(
                    "Usage: ClassFileHeaderCheck path/to/X.class");
        }

        Path path = Path.of(args[0]);
        try (DataInputStream input =
                     new DataInputStream(Files.newInputStream(path))) {
            int magic = input.readInt();
            if (magic != 0xCAFEBABE) {
                throw new IllegalArgumentException("Not a class file");
            }

            int minor = input.readUnsignedShort();
            int major = input.readUnsignedShort();

            System.out.println("major: " + major);
            System.out.println("minor: " + minor);
            System.out.println("is Java 11 class format: "
                    + (major == 55 && minor == 0));
        }
    }
}
```

```bash
javac --release 11 -encoding UTF-8 -d out ClassFileHeaderCheck.java
java -cp out ClassFileHeaderCheck out/Compat11.class
```

Stdout mong đợi:

```text
major: 55
minor: 0
is Java 11 class format: true
```

**Giới hạn:** chương trình chỉ đọc **8 byte đầu** để kiểm tra magic và version. Nó không xác nhận mọi section trong class file hợp lệ, không xác nhận API references và không kiểm tra dependencies. Với release 11 bình thường, `javac --release 11` tạo major 55, minor 0. Một class file giả/sai định dạng vẫn có thể vượt qua bộ kiểm tra 8 byte này; JVM verifier và runtime tests là các bước khác.

## 6. Lỗ hổng của -source 11 -target 11 khi build trên JDK mới

Ví dụ thực tế rất dễ mắc: mã nguồn dùng **cú pháp Java 11 hợp lệ**, nhưng gọi API **được bổ sung ở Java 12**.

`String.indent(int)` được thêm từ Java 12, không có trong Java 11.

### Tệp `ApiTooNew.java`

```java
public final class ApiTooNew {
    public static void main(String[] args) {
        String value = "core".indent(2);
        System.out.println(value.length());
    }
}
```

#### Phép thử 1: dùng --release 11

Trên JDK **17 hoặc mới hơn** còn hỗ trợ target 11:

```bash
mkdir -p safe-out
javac --release 11 -encoding UTF-8 -d safe-out ApiTooNew.java
```

**Kết quả mong đợi:** compile **FAILED** vì `String.indent(int)` không thuộc Java 11 API. Diagnostic cụ thể khác nhau giữa các bản javac, thường chứa `cannot find symbol` / `method indent(int)`. Đây là **thất bại đúng** của kiểm chứng API, không phải lý do để bỏ `--release`.

#### Phép thử 2: chỉ dùng -source/-target

Trên JDK **17**:

```bash
mkdir -p unsafe-out
javac -source 11 -target 11 -encoding UTF-8 \
  -d unsafe-out ApiTooNew.java
java -cp unsafe-out ApiTooNew
```

Dùng JDK17 như trên, compile có thể **thành công**, do compiler thấy API `String.indent` từ platform JDK17. Chạy trên JDK17 in:

```text
7
```

Giải thích: `"core".indent(2)` tạo chuỗi gồm hai dấu cách, `core` và newline, tổng **7 ký tự**. Javac có thể cảnh báo về system modules path khi chọn source/target cũ; cảnh báo **không biến build thành API-safe**.

Tiếp theo, lấy **Java 11 runtime thật** và chạy:

```bash
java -version
java -cp unsafe-out ApiTooNew
```

Khi `java -version` là **11**, JVM nạp được classfile **major 55** nhưng không tìm thấy phương thức `java.lang.String.indent(int)`. **Kết quả mong đợi:** `NoSuchMethodError`; văn bản/stack trace thay đổi tùy VM.

**Đây là ví dụ trung tâm của bài:**

```text
-source 11       -> cú pháp đúng Java 11
-target 11       -> classfile major 55
JDK 17 libraries -> compiler vẫn cho gọi String.indent
Java 11 runtime -> NoSuchMethodError

--release 11     -> chặn String.indent ngay ở compile time
```

Tài liệu Oracle giải thích khi dùng `-source/-target` cho JDK 9+ mà cần target platform API thật, có thể cấu hình `--system` trỏ tới JDK tương ứng; **nhưng `--release` là phương pháp trực tiếp và dễ kiểm tra hơn** cho Java 11 trong các công trình thông thường. Không đề xuất bootclasspath hack cho module system Java 11.

## 7. Phân biệt lỗi cú pháp mới và API mới

Hai thử nghiệm khác nhau:

### Ngôn ngữ quá mới

```java
// Tệp NewSyntax.java
record Point(int x, int y) {}
```

```bash
javac --release 11 NewSyntax.java
```

**Kỳ vọng:** bị từ chối vì `record` là cú pháp được chuẩn hóa từ Java 16. `-source 11` cũng từ chối. Vì thế demo này **không chứng minh** lợi thế API của `--release`; nó chỉ chứng minh giới hạn source level.

### Cú pháp cũ nhưng API mới

```java
// Tệp ApiTooNew.java, đã giới thiệu đầy đủ ở mục 6.
String value = "core".indent(2);
```

Đoạn này dùng cú pháp hoàn toàn hợp lệ trong Java 11, nhưng API quá mới. **`--release 11` từ chối, trong khi `-source 11 -target 11` trên JDK17 có thể chấp nhận.**

**Điểm cần nhớ:** đừng kiểm tra khả năng chạy trên Java 11 chỉ bằng việc biên dịch một class dùng `var` hoặc nhìn thấy classfile major 55. Phải kiểm tra **API surface**.

## 8. Các giới hạn của --release: vẫn cần test runtime

`--release 11` giúp ngăn vô tình gọi **platform API Java 12+** trong source được compile. Nhưng nó **không** tự đảm bảo mọi thứ bên ngoài source module của bạn tương thích:

| Tình huống | --release 11 xử lý được? | Kiểm chứng bổ sung |
| --- | --- | --- |
| Cú pháp Java 17 trong source của bạn | **Có, chặn** | Test build phải fail |
| Gọi `String.indent` Java 12 từ source của bạn | **Có, chặn** | Dùng source API regression |
| Classfile của bạn có major 61 | **Có, tránh** bằng target 55 | `javap -v` / class audit |
| Một dependency JAR chứa class major 61 | **Không tự hạ cấp** | Quét dependencies, chạy trên JDK11 |
| Thư viện third-party dùng API mới bên trong | **Không kiểm tra trọn** | Chạy integration test với libs trên Java11 |
| Reflection truy cập class/method theo tên string | **Không thể xét tĩnh đầy đủ** | Test thực tế, runtime logs |
| JNI/native library không tương thích OS/ABI | **Không** | Test trên OS/architecture production |
| ServiceLoader/plugin tải implementation muộn | **Không tự đảm bảo** | Integration tests trên JVM tối thiểu |
| Resource, config, TLS/protocol khác giữa JVMs | **Không** | Smoke và hệ thống test |
| Module exports/strong encapsulation | **Không đảm bảo mọi runtime scenario** | Module/test trên JDK11 thật |
| Chạy trên Java 17/21+ thay vì 11 | API target hợp lệ nhưng runtime behavior vẫn có thể khác | CI matrix đa JVM |

**Hợp đồng tương thích thật là “compile + dependency closure + runtime”.** Khi một thư viện công bố “supports Java 11”, đó là lời hứa về **artifact và các dependencies cần thiết**, không chỉ flag javac của source chính.

## 9. Ví dụ: dependency build bằng JDK 17 vẫn có thể làm app Java 11 thất bại

Đây là rủi ro tinh vi. Hãy tạo hai lớp Java rất đơn giản, không dùng API mới.

### Tệp `FutureLibrary.java`

```java
public final class FutureLibrary {
    public static String label() {
        return "future-lib";
    }
}
```

### Tệp `UsesLibrary.java`

```java
public final class UsesLibrary {
    public static void main(String[] args) {
        System.out.println(FutureLibrary.label());
    }
}
```

Trên **JDK 17**, lần lượt thực hiện:

```bash
mkdir -p lib17 app11

# Thư viện được build mặc định bởi javac 17 -> major 61.
javac -d lib17 FutureLibrary.java

# Ứng dụng nhắm release 11 nhưng nhìn thấy thư viện vừa build.
javac --release 11 -cp lib17 -d app11 UsesLibrary.java

# Kiểm tra classfile.
javap -verbose -classpath lib17 FutureLibrary
javap -verbose -classpath app11 UsesLibrary
```

Tìm hai dòng:

```text
FutureLibrary: major version: 61
UsesLibrary:   major version: 55
```

Đây là **tóm lược hai output**, không phải output nguyên văn của một lần `javap`.

Chạy trên JDK 17, lệnh sau thành công:

```bash
java -cp app11:lib17 UsesLibrary
```

```text
future-lib
```

**Trên Java 11**, cùng classpath có thể nạp `UsesLibrary` (major 55) nhưng **không nạp được `FutureLibrary` (major 61)**. Kết quả là `UnsupportedClassVersionError`. Tên file class và thông báo lỗi tùy runtime, nhưng nguyên nhân rõ ràng: dependency mới hơn JVM target.

**Cú pháp shell:** Dấu `:` ngăn cách classpath ở Linux/macOS. Trên Windows, dùng `;` trong classpath. Ví dụ:

```powershell
java -cp 'app11;lib17' UsesLibrary
```

Nếu dùng Java 11 compiler trực tiếp để biên dịch app và trỏ đến thư viện major61, compiler sẽ có thể từ chối ngay vì không đọc được classfile quá mới. Dùng Java17 compiler cùng `--release 11` **không tự thực hiện kiểm tra tương thích bytecode cho mọi dependency như một policy**.

**Hướng xử lý:** dùng dependency release tương thích Java 11, hoặc rebuild thư viện bằng release 11 nếu source/API của thư viện thực sự hỗ trợ. Không dùng công cụ “đổi số major 61 thành 55” để giả tương thích: các bytecode constructs, API references và verification rules khác có thể khiến file hỏng hoặc thất bại lúc chạy.

## 10. Third-party API không nằm trong --release của Java Platform

`--release 11` kiểm soát tập API **của Java SE/JDK** được javac công bố cho release 11. Nó **không tự cấm** source code bạn gọi API mới của một thư viện ứng dụng (ví dụ một bản logging/client/database library chỉ chạy trên Java 17).

Mô hình cần kiểm tra:

```text
Application (compile --release 11)
  |
  +-- Library A (claims support Java 11?)
  |      |
  |      +-- Library B (compiled for Java 17?)
  |
  +-- JDBC driver (requires Java 11?)
  +-- JSON library / HTTP SDK (may have multi-release classes)
  +-- SPI / ServiceLoader implementation
  +-- Native binding (OS and architecture)
```

Các bước thực tế:

1. Đọc **minimum Java version** trong tài liệu phát hành của tất cả dependency chính.
2. Dùng dependency management/lockfile để cố định phiên bản.
3. Kiểm tra bytecode major của JARs, đặc biệt những thư viện thay bản trong update.
4. Với multi-release JAR, cần hiểu những classes nằm dưới `META-INF/versions/N` và phiên bản runtime sẽ chọn.
5. Dùng `jdeps` tìm dependencies tĩnh và những API nội bộ, nhưng **không xem jdeps là bằng chứng đầy đủ**.
6. Chạy test/integration trên **JVM 11 thật**, với toàn bộ runtime classpath/module path.
7. Kiểm tra tình huống tải class muộn, reflection, SPI và JNI/native.

Một JAR có classes major >55 **không nhất thiết** luôn không dùng được trên Java 11 nếu đó là **multi-release JAR hợp lệ** chứa code base tương thích và version-specific classes chỉ được VM mới chọn. Vì vậy công cụ kiểm tra phải hiểu cấu trúc JAR; không chỉ tìm một byte sequence major 61 trong mọi entry rồi kết luận build fail.

## 11. jdeps, javap và giới hạn phân tích tĩnh

**`javap`** kiểm tra class file ở mức bytecode:

```bash
javap -verbose -classpath out Compat11
javap -c -p -classpath out Compat11
```

- `-verbose`: xem major/minor, constant pool, method references.
- `-c`: xem bytecode instructions.
- Không thực thi code và không mô phỏng đầy đủ API resolution.

**`jdeps`** là công cụ phân tích dependencies. Một lệnh hữu ích:

```bash
jdeps --jdk-internals --recursive app.jar
```

Đây là **lệnh minh họa** chỉ chạy nếu `app.jar` tồn tại. `--jdk-internals` tìm việc dùng các JDK internal APIs được công cụ phát hiện qua dependencies; `jdeps` có thể không thấy reflection hoặc những class names xây dựng động từ string.

Với **multi-release JAR**, dùng option `--multi-release 11` **khi phân tích multi-release artifact**. Option này chọn cách nhìn vào entries phù hợp với target release; nó **không** biên dịch hoặc tự chuyển API source sang Java 11.

**Đừng dùng `jdeps --jdk-internals` như kiểm thử duy nhất:** nó tập trung tìm internal APIs, không có nghĩa đã chứng minh không có mọi `NoSuchMethodError` khi chạy trên JDK11. Kết hợp `--release`, API/docs verification, bytecode audit và runtime integration tests.

### Trình tự ngắn trước khi phát hành

```text
1. javac --release 11
2. javap -verbose -> major 55
3. dependency tree + classfile compatibility
4. jdeps -> inspect static dependencies/internals
5. Java 11 smoke/integration tests
6. Java 17/21/25 tests nếu muốn hỗ trợ ngược chiều
7. release artifact kèm min-Java-version
```

## 12. Maven: xác định release thay vì chỉ source/target

Trong dự án Maven hiện đại, **Maven Compiler Plugin** hỗ trợ property:

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0
                             https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>
    <groupId>com.example</groupId>
    <artifactId>java11-compat</artifactId>
    <version>1.0.0</version>

    <properties>
        <maven.compiler.release>11</maven.compiler.release>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    </properties>

    <build>
        <plugins>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-compiler-plugin</artifactId>
                <version>3.16.0</version>
            </plugin>
        </plugins>
    </build>
</project>
```

Đây là **file POM độc lập**, đặt tại `pom.xml`. Với mã ở `src/main/java/Compat11.java`, build bằng một Maven/JDK có hỗ trợ plugin và release:

```bash
mvn -B clean package
javap -verbose -classpath target/classes Compat11
```

Trong output `javap`, kiểm tra major 55. Không cần song song đặt `maven.compiler.source` và `maven.compiler.target` khi đã dùng `maven.compiler.release=11`.

### Maven toolchain và compiler release không phải cùng thứ

- **Compiler release:** policy cho source/API/bytecode output.
- **Maven toolchains:** chọn compiler JDK cụ thể để build nhất quán giữa CI/dev.
- **JDK chạy Maven:** môi trường JVM của Maven/build plugins, không nhất thiết là JVM mà bạn phân phối phần mềm cho khách hàng.
- **JDK chạy tests:** phải kiểm tra riêng, vì test trên build JDK17 không thay thế test thực trên Java11.

Có thể sử dụng toolchain pin JDK17 để biên dịch `--release11`, nhưng vẫn cần test với Java11. Không hứa rằng việc cài property release sẽ tự động làm các plugin kiểm thử hoặc container chạy bằng Java11.

**Chú ý phiên bản compiler plugin:** config ở trên là một ví dụ theo tài liệu Maven Compiler Plugin hiện hành. Trong dự án thật, dùng phiên bản plugin được tổ chức kiểm thử/phê duyệt, không tự nâng mọi plugin chỉ vì bài học minh họa một version.

## 13. Gradle: kết hợp toolchain và options.release

Trong `build.gradle.kts` dùng Kotlin DSL:

```kotlin
plugins {
    java
}

java {
    toolchain {
        languageVersion.set(JavaLanguageVersion.of(17))
    }
}

tasks.withType<JavaCompile>().configureEach {
    options.release.set(11)
    options.encoding = "UTF-8"
}
```

Ý nghĩa:

- Gradle **toolchain 17** xác định JDK dùng để biên dịch, giúp reproducible builds. Nó không tự buộc generated bytecode target Java11.
- `options.release.set(11)` buộc `javac` kiểm tra **Java 11 source + API + classfile**.
- `options.encoding` cố định source encoding.
- Khi muốn test thực trên JVM11, cấu hình **test launcher/toolchain** riêng hoặc chạy test job bằng JDK11. Đừng suy rằng Gradle daemon chạy trên JVM17 sẽ tự chạy tests trên JVM11.
- Gradle có thể cần JDK để chạy daemon phù hợp phiên bản Gradle; JDK chạy Gradle và JDK toolchain có thể khác.

Với Gradle Groovy DSL:

```groovy
plugins {
    id 'java'
}

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(17)
    }
}

tasks.withType(JavaCompile).configureEach {
    options.release = 11
    options.encoding = 'UTF-8'
}
```

Gradle docs khuyến nghị **toolchains** để chọn compiler/runtime tools và **release** để ràng buộc API của target. Chỉ đặt `sourceCompatibility = 11` và `targetCompatibility = 11` không có cùng bảo đảm API.

### Dependency resolution của build tool

Maven/Gradle có thể kéo một phiên bản JAR **khác** giữa local và CI do dependency ranges, transitive upgrades hoặc dynamic versions. Nếu cần hỗ trợ Java11 dài hạn:

- Pin/lock versions.
- Chặn dependency mới đòi JVM >11 bằng metadata rules/CI checks khi phù hợp.
- Kiểm tra generated artifact sau mọi lần nâng dependency.
- Đừng chỉ xem tên `targetCompatibility` hoặc `release` rồi cho rằng dependency đã tương thích.

## 14. API ở module path và classpath

Java 11 có Java Platform Module System (JPMS). Khi biên dịch modular app, mã có thể cần `module-info.java` với `requires` module hợp lệ.

Ví dụ một module dùng HTTP Client (có từ Java 11):

```java
module com.example.httpdemo {
    requires java.net.http;
}
```

Đoạn này là nội dung **`module-info.java`**, cần file source khác trong module để thành project runnable. `java.net.http` là Java 11 API và module hợp lệ khi biên dịch với `--release 11`.

Ngược lại, cố gọi module/API được thêm sau Java 11 sẽ bị compiler chặn theo API platform của release. `--release` ngăn việc dùng các API JDK nội bộ không được export cho target, thay vì dựa vào cấu hình phá encapsulation.

**Classpath khác module path:**

- `-classpath`/`-cp` dùng cho thư viện không module hoặc ứng dụng classpath truyền thống.
- `--module-path` dùng để phân giải các module.
- `requires`, exports/opens của JPMS là **ràng buộc truy cập** riêng, không bị vô hiệu hóa bởi classfile major 55.
- Khi chạy modular app trên JDK11, phải bảo đảm toàn bộ required modules hiện diện và exports phù hợp.

Có những lỗi chỉ xuất hiện khi chạy trên runtime thật, như thiếu module, reflection bị ngăn bởi encapsulation hoặc dependency chưa được resolved. **Không bypass bằng cách thêm hàng loạt `--add-opens`/`--add-exports` mà không hiểu module boundary**.

## 15. Preview features không thuộc hợp đồng ổn định Java 11

Một compiler mới có thể hỗ trợ **preview features** của chính release đó. Nhưng preview không phải cách để viết mã Java 17 rồi phát hành một classfile Java 11.

- `--release 11` không cho cú pháp/feature chỉ có sau Java11.
- Không phối hợp `--enable-preview` của compiler Java17 với `--release 11` để lách version.
- Bytecode preview của release mới có quy tắc version/minor riêng; không phải classfile 55 thông thường.
- Một thư viện hứa Java11 support nên kiểm thử trên **JDK11 GA/stable**, không dựa vào phiên bản preview đã hết vòng đời.

Với thư viện lâu dài, ưu tiên supported language/API của minimum runtime. Nếu thật sự muốn version-specific implementation, cân nhắc modular design/multi-release JAR có kiểm thử ở từng runtime; đừng đưa preview feature vào baseline không tương thích.

## 16. Kiểm tra một JAR có chứa nhiều classfile versions

JAR là container của nhiều class files và resources. Đừng chỉ chạy `javap` trên class `Main` rồi tin mọi class đã nhắm major55.

Cần xem:

1. Classfiles trong code chính.
2. Classfiles được tạo bởi annotation processors/code generation.
3. JARs trong runtime dependency graph.
4. ServiceLoader providers, driver và plugin classes chỉ được load trên path đặc biệt.
5. Multi-release JAR entries trong `META-INF/versions/<N>`, nơi các JVM mới có thể chọn class mới hơn thay vì baseline.

**Đặc biệt với multi-release JAR**: version-specific classes major61 bên trong `META-INF/versions/17` không tự là lỗi cho Java11, **nếu base entries tương thích Java11** và packaging đúng. Java11 sẽ chọn base hoặc version-specific entry có version không vượt quá 11 khi manifest/structure hợp lệ. Do đó chính sách audit cần hiểu MRJAR, không từ chối vô điều kiện mọi classfile major >55 trong tất cả entries.

Lệnh xem nội dung JAR:

```bash
jar tf target/java11-compat-1.0.0.jar
```

Lệnh này chỉ hoạt động nếu JAR từ ví dụ Maven đã được tạo. Để kiểm tra từng class, có thể viết script phù hợp CI hoặc dùng công cụ class-file analysis đáng tin, rồi xác minh kết quả bằng `javap` trên những classes quan trọng. Không sửa trực tiếp byte major của dependency để “ép hỗ trợ Java 11”.

## 17. Trường hợp khó: reflection, code generation và annotation processing

**Reflection** có thể chuyển tên API thành chuỗi:

```java
String typeName = "some.runtime.ClassName";
Class<?> dynamicType = Class.forName(typeName);
```

Đây là đoạn **minh họa**, tên class cần tồn tại khi chạy nếu muốn thành công. Compiler không xác minh sự tồn tại của target class từ string và không thể biết mọi control flow sẽ tạo tên nào.

Cũng tương tự:

- `MethodHandles.Lookup` tạo method handles theo tên/type tại runtime.
- `ServiceLoader` tải providers trong classpath/module path.
- Framework DI/ORM/serialization dùng reflection, proxies hoặc generated bytecode.
- Annotation processor có thể phát sinh classes/resources sau khi compile.
- JNI/native libraries có yêu cầu ABI, CPU architecture và OS riêng.

**`--release 11` không tự kiểm tra tất cả các runtime-generated classes**. Khi có bytecode generators, hãy đặt target major55 trong generator configuration, kiểm tra artifact cuối và chạy smoke test Java11.

Một source class được compiler kiểm tra chặt vẫn có thể fail khi framework sinh class major61 lúc runtime rồi load trên Java11. Đây là lý do CI cần **end-to-end tests**, không chỉ unit test các methods không động đến phần tích hợp.

## 18. CI matrix: compile một lần, chạy trên minimum JVM

Một pipeline đơn giản có thể làm:

```text
BUILD (JDK17, javac --release 11)
       |
       +-- Check source/API target
       +-- Package + dependency audit
       +-- Check major version 55
       |
       +-- Test job A: Java 11
       |       integration/smoke + dependency/runtime loading
       |
       +-- Test job B: Java 17
       |       forward compatibility
       |
       +-- Test job C: Java 21/25 (nếu hỗ trợ)
               module/security/behavior compatibility
```

**Bắt buộc đặc biệt:** job chạy Java11 thật phải dùng **đúng runtime11** khi gọi `java -version`, không chỉ dùng `--release11` trong javac của job build. Nếu test runner, CI action hoặc Docker image chọn JVM17 ngầm, kiểm tra cấu hình lại.

Một quy trình POSIX minh họa khi đã có JDK11 và JDK17:

```bash
# Build sử dụng javac 17 với API/bytecode 11.
"$JDK17_HOME/bin/javac" --release 11 -encoding UTF-8 \
  -d out Compat11.java

# Audit class file với javap 17.
"$JDK17_HOME/bin/javap" -verbose -classpath out Compat11

# Kiểm tra trên runtime tối thiểu, không chạy bằng JDK17.
"$JDK11_HOME/bin/java" -version
"$JDK11_HOME/bin/java" -cp out Compat11
```

**Điều kiện:** hai biến môi trường `JDK17_HOME` và `JDK11_HOME` phải trỏ đến các thư mục JDK đã cài sẵn; file `Compat11.java` đã được tạo từ mục 3. Không dùng placeholder làm đường dẫn shell thật mà không cấu hình.

### Khi nào chạy cùng một binary trên nhiều runtimes?

Khi hỗ trợ Java 11 là **minimum**, mã đã compile thành major55 thường có thể load trên JVM mới hơn, nhưng vẫn có thể có thay đổi trong behavior, security, dependencies hoặc removed components. Test Java17/21/25 giúp phát hiện regressions. **Compile target thấp không miễn trách nhiệm xác minh chạy tốt trên JVM mới.**

## 19. Chẩn đoán lỗi theo giai đoạn

| Triệu chứng | Giai đoạn | Khả năng cao | Kiểm tra |
| --- | --- | --- | --- |
| `release version 11 not supported` | javac startup | Build JDK không còn hỗ trợ target hoặc compiler không phù hợp | `javac --help` / version |
| `records not supported in -source 11` | Compile source | Dùng cú pháp mới | Dùng Java11 syntax hoặc đổi minimum |
| `cannot find symbol: indent(int)` khi `--release11` | Compile API | Dùng Java12 API | Thay API tương đương Java11 |
| `UnsupportedClassVersionError` | JVM load class | Classfile major > runtime hỗ trợ | `javap -v` app **và deps** |
| `NoSuchMethodError` | JVM resolve/link/invoke | Có class nhưng thiếu signature method ở runtime | API version, dependency conflict |
| `NoSuchFieldError` | JVM resolve field | Field không tồn tại/khác kiểu | Linkage/dependency version |
| `NoClassDefFoundError` | Load/link | Class phụ thuộc thiếu hoặc init thất bại trước đó | Runtime classpath/module path |
| `ClassNotFoundException` | Reflection/class loading | Tên class không có trên path hoặc loader sai | Provider/loader/runtime classpath |
| `IllegalAccessError` / `InaccessibleObjectException` | Link/reflection | Encapsulation/access khác runtime | JPMS exports/opens, library compat |
| `NoSuchModuleException` | Module resolution | Required module không hiện diện | Module path/JDK version |
| Tests pass trên JDK17, fail JDK11 | Deployment | Chỉ test build-JDK, deps/API mới hoặc behavior khác | Chạy test matrix với JDK11 |

Một lỗi liên kết có thể xuất hiện **muộn**, khi JVM lần đầu nạp class/method ở nhánh logic hiếm. Vì thế cần test coverage của paths quan trọng, không chỉ chạy `main()` in startup message.

### Phân biệt hai lỗi nổi bật

**`UnsupportedClassVersionError`:** format bytecode không được JVM target hỗ trợ. Ví dụ major61 gặp JVM11.

**`NoSuchMethodError`:** class có thể đã load thành công, nhưng method được tham chiếu trong bytecode không tồn tại với signature mong đợi khi link/invoke. Ví dụ class major55 gọi `String.indent` trên JVM11.

Hai lỗi có nguyên nhân **khác nhau**, và xử lý chỉ bằng “hạ target bytecode” không giải quyết lỗi API.

## 21. Câu hỏi tự luyện

**1.** `--release 11` có kiểm tra cả cú pháp, API platform và bytecode không?

**2.** Classfile major55 có chứng minh ứng dụng không gọi API mới từ Java12 không?

**3.** Vì sao `-source 11 -target 11` với compiler JDK17 vẫn có thể cho phép `String.indent()`?

**4.** Record là ngôn ngữ Java16. Nếu viết `record Point(int x, int y){}` rồi compile release11, phải pass hay fail?

**5.** Class của app major55, dependency class major61, chạy trên JVM11 có thể gặp lỗi gì?

**6.** Maven property nào nên dùng cho compiler release? Gradle Kotlin DSL dùng thuộc tính nào?

**7.** Dùng `--release 11` trên JDK17 có nghĩa lệnh `java` đang dùng tự chuyển thành JDK11 không?

**8.** JAR chứa `META-INF/versions/17/Foo.class` major61 có nhất thiết không chạy được trên Java11 không?

**9.** `jdeps --jdk-internals` có thể tìm mọi tên lớp được tạo trong `Class.forName(userInput)` không?

**10.** Vì sao phải chạy test Java11 dù compile bằng `--release11` đã thành công?

**Đáp án:**

1. **Có**: language/source, documented supported platform APIs của Java11, classfile target11.
2. **Không**: chỉ chứng minh format, không chứng minh API.
3. `-source` kiểm cú pháp, `-target` kiểm bytecode, nhưng JDK17 platform APIs vẫn được nhìn thấy nếu không chọn target API thích hợp.
4. **Fail**: records chưa thuộc Java11 syntax.
5. `UnsupportedClassVersionError` khi JVM11 phải nạp dependency major61.
6. Maven: `maven.compiler.release=11`; Gradle: `JavaCompile.options.release=11`.
7. **Không**: chỉ thay chính sách compiler; runtime là command/env khác.
8. **Không nhất thiết**: multi-release JAR hợp lệ có base/versioned entries phù hợp JVM11.
9. **Không**: reflection/dynamic loading không được static analyzer nhìn đầy đủ.
10. Cần kiểm tra dependencies, SPI/reflective paths, runtime config, native code và integration thực trên minimum JVM.

## 22. Kết luận

Để hỗ trợ **Java 11** khi build bằng JDK mới, **`--release 11` là chuẩn mặc định**: nó ràng buộc **cú pháp Java 11**, **API Java/JDK có ở release 11**, và **class file major55**. Không dùng `-source11 -target11` một mình như bằng chứng đủ về API compatibility. Đừng quên **dependencies có thể là bytecode mới hơn**, hoặc framework có thể dùng reflection/bytecode generation ngoài phạm vi kiểm tra compiler.

Một quy trình đáng tin cậy là: **xác nhận compiler → compile `--release11` → kiểm classfiles/dependencies → chạy tests trên JDK11 thật → CI matrix các runtime được hỗ trợ**. Kết quả “build thành công trên JDK17” là điều kiện cần, không phải giấy chứng nhận hoàn chỉnh cho sản phẩm Java11.
