# XDH — Kiểm thử sai khóa, đầu vào không hợp lệ và khả năng tương tác (Java 11+)

## Mục tiêu

XDH là họ thuật toán trao đổi khóa Diffie–Hellman trên các đường cong Montgomery theo **RFC 7748**, gồm **X25519** và **X448**. Java 11 đưa các thuật toán này vào JCA/JCE chuẩn qua `KeyPairGenerator`, `KeyAgreement`, `KeyFactory` và các kiểu khóa `XEC` (OpenJDK JEP 324). Chúng **vẫn được hỗ trợ trên Java hiện đại**, không phải API đã lỗi thời.

Mục tiêu bài học là kiểm thử **đúng và an toàn**, không chỉ chứng minh hai máy có thể tính cùng một mảng byte. Bạn sẽ:

1. Phân biệt **khóa sai đường cong**, **public key sai định dạng**, **public key bậc nhỏ**, **public key hợp lệ nhưng của sai đối tác**, và **private key không được phép xuất**.
2. Viết test cho X25519/X448 bằng Java 11: sinh khóa, thỏa thuận hai chiều, round-trip X.509 SPKI, DER bị cắt, curve mismatch, low-order input và test vector RFC 7748.
3. Hiểu sự khác biệt giữa **raw public key 32/56 byte**, `XECPublicKeySpec`, `X509EncodedKeySpec` và private key dạng PKCS#8.
4. Chuẩn hóa little-endian khi kết nối Java với một SDK bên ngoài, không nhầm thông số/encoding.
5. Hiểu **XDH không xác thực danh tính**: public key hợp lệ của người khác vẫn có thể tính ra một secret; phát hiện sai peer cần authentication, transcript binding và key confirmation.
6. Phân biệt test tương thích trong **một provider** với kiểm thử interop thực sự giữa Java và thư viện/ngôn ngữ khác.

Bài học dùng kiến thức hiện còn áp dụng từ Java 11 trở lên; code đầy đủ có thể biên dịch bằng `javac --release 11`, không dùng `HexFormat` (mới có từ Java 17) và không dựa vào cách viết crypto tùy tiện.

## 1. XDH trao đổi khóa, nhưng không tự xác thực

Hai phía tạo mỗi bên một cặp `private/public`:

```text
Alice                                         Bob
  |                                             |
  | privateA -> publicA = X25519(a, base)       |
  |                        privateB -> publicB = X25519(b, base)
  |                                             |
  | ----------- publicA --------------------->  |
  | <---------- publicB ----------------------  |
  |                                             |
  | secretA = X25519(privateA, publicB)         |
  |                      secretB = X25519(privateB, publicA)
  |                                             |
  |          secretA == secretB                 |
```

Nếu phép tính hợp lệ, hai phía tạo cùng shared secret. Với X25519 secret là **32 byte**; với X448 là **56 byte**. Nhưng phép tính **không chứng minh public key nhận được thuộc đối tác mong đợi**.

Nếu Alice nhận public key của Mallory thay vì Bob:

- Public key của Mallory có thể là X25519 **hợp lệ**.
- `KeyAgreement.doPhase(...)` có thể **không ném exception**.
- Secret của Alice sẽ khác secret Alice–Bob mà Bob mong đợi.
- Chỉ **protocol authentication và key confirmation** mới khiến một buổi trao đổi không đúng đối tác bị từ chối đáng tin cậy.

Không dùng “thu được 32 byte” hay “không có exception” làm bằng chứng xác thực đối tác. Không dùng raw XDH secret trực tiếp làm AES key nếu chưa có cơ chế dẫn xuất khóa/KDF được đặc tả.

### Phân biệt các tên thuật toán

| Tên | Vai trò | Ghi nhớ |
| --- | --- | --- |
| `XDH` | Họ thuật toán key agreement RFC 7748 | Có thể sử dụng X25519 hoặc X448 |
| `X25519` | Trao đổi khóa Curve25519 | Raw public key và secret 32 byte |
| `X448` | Trao đổi khóa Curve448 | Raw public key và secret 56 byte |
| `Ed25519`, `Ed448` | Chữ ký số theo RFC 8032 | Không tráo với public key XDH |
| `ECDH` với `secp256r1` | Trao đổi khóa trên đường cong kiểu Weierstrass | Cũng là ECDH nhưng **khác XDH** |

Tuyệt đối không rút ngắn public key X448 xuống 32 byte, chèn padding vào public key X25519 để “đổi curve”, hoặc import public Ed25519 theo API X25519 mà chưa có một giao thức chuyển đổi chuẩn hóa và được đánh giá an toàn.

## 2. Các API Java 11 nên dùng

```java
KeyPairGenerator generator = KeyPairGenerator.getInstance("XDH");
generator.initialize(NamedParameterSpec.X25519);

KeyPair alice = generator.generateKeyPair();
KeyPair bob = generator.generateKeyPair();

KeyAgreement agreementA = KeyAgreement.getInstance("XDH");
agreementA.init(alice.getPrivate());
agreementA.doPhase(bob.getPublic(), true);
byte[] secretA = agreementA.generateSecret();

KeyAgreement agreementB = KeyAgreement.getInstance("XDH");
agreementB.init(bob.getPrivate());
agreementB.doPhase(alice.getPublic(), true);
byte[] secretB = agreementB.generateSecret();

boolean same = MessageDigest.isEqual(secretA, secretB);
```

Đây là **mã minh họa bên trong method**, cần import `java.security.*`, `java.security.spec.NamedParameterSpec`, `javax.crypto.KeyAgreement` và xử lý `GeneralSecurityException`. Không in các mảng secret.

**Các điểm chính:**

- Gọi `generator.initialize(NamedParameterSpec.X25519)` thay vì dựa vào curve mặc định của provider; dùng `NamedParameterSpec.X448` khi muốn X448.
- `KeyAgreement.init(...)` cần **private key**, `doPhase(otherPublic, true)` nhận **public key phía đối tác**.
- Với XDH trao đổi khóa hai bên, có **một phase**, truyền `true` vào `doPhase`.
- `generateSecret()` trả mảng byte raw. Mảng bí mật có thể tồn tại trong heap; không log hoặc chuyển thành `String`. Xóa buffer khi không còn cần nếu có thể, đồng thời cần hiểu việc GC/copy có thể làm còn các bản sao khác.
- Nếu sinh khóa và sử dụng chúng trong HSM, provider có thể không cho xuất private key và các KeySpec/encoding cần được điều chỉnh đúng chính sách.
- Dùng `getInstance("XDH")` không ép một provider cụ thể, giúp ứng dụng có thể chọn provider đã cấu hình. Oracle/OpenJDK cung cấp XDH qua SunEC, nhưng production cần kiểm tra provider thực tế.

**Đừng đánh đồng `KeyAgreement.generateSecret()` với secret đã xác thực.** XDH chỉ làm toán trao đổi khóa; authentication là trách nhiệm của giao thức bao quanh.

## 3. Những loại “khóa sai” cần tách riêng

| Loại test | Ví dụ | Giai đoạn lỗi/điều kiện |
| --- | --- | --- |
| **SPKI/DER sai** | Public key X.509 bị cắt một byte | `KeyFactory.generatePublic` có thể báo `InvalidKeySpecException` |
| **Private/public sai role** | Đưa public key vào `KeyAgreement.init` | `InvalidKeyException` hoặc lỗi nhập khóa tương ứng |
| **Khác curve** | Private X25519 + public X448 | Không tương thích; thường `InvalidKeyException` ở `doPhase` |
| **Public bậc nhỏ** | X25519 u-coordinate = 0 | Provider có thể từ chối hoặc tính all-zero shared secret; **không được tiếp tục** |
| **Public hợp lệ, sai người** | Public X25519 của Mallory thay Bob | Có thể vẫn tính secret; phải phát hiện qua xác thực giao thức |
| **Import sai format** | Raw public 32 byte truyền vào `X509EncodedKeySpec` | Không phải SPKI DER, nên parse lỗi |
| **Sai private key store** | PKCS#8/hardware key không truy cập được | Lỗi import/permission, không phải lỗi curve |
| **Khác bối cảnh KDF** | Cùng raw XDH secret nhưng khác HKDF `salt/info` | Khóa ứng dụng khác, phải đồng nhất protocol context |
| **Dữ liệu bị hỏng trên wire** | DER, raw key hoặc transcript bị biến đổi | Phải bị phát hiện ở tầng parse, key agreement hoặc authentication |

Hãy viết test **theo nguyên nhân**. Một test kiểm tra DER cắt ngắn nên assert lỗi import; không cần chờ đến key agreement. Một test wrong-peer không nên assert `InvalidKeyException` bởi public key vẫn hợp lệ toán học.

### Ngoại lệ không phải ở đâu cũng giống nhau

Các nhà cung cấp JCA/JCE có thể phân loại lỗi ở vị trí khác nhau. Các lớp cần biết:

- `InvalidKeySpecException`: `KeyFactory` không chuyển được dữ liệu/spec thành khóa phù hợp.
- `InvalidKeyException`: một key không phù hợp cho `KeyAgreement.init`/`doPhase`.
- `InvalidAlgorithmParameterException`: cấu hình tham số curve/provider không phù hợp.
- `NoSuchAlgorithmException`: provider không có thuật toán được yêu cầu.
- `IllegalStateException`: vòng đời agreement sai, ví dụ chưa init hoặc chưa đủ phase.
- `ProviderException` hoặc lỗi implementation: có thể phát sinh ở provider cụ thể.

**Không so sánh nguyên văn error message** trong CI: message và giai đoạn phát hiện có thể thay đổi theo JDK, provider, FIPS policy hoặc HSM. Test nên giữ điều kiện **không chấp nhận dữ liệu/secret không an toàn** thay vì “phải ném y hệt chuỗi tiếng Anh”.

## 4. Public key raw và X.509 SPKI khác nhau

XDH interop rất dễ sai do định dạng public key:

| Representation | X25519 | X448 | Nội dung |
| --- | --- | --- | --- |
| Raw public key theo RFC 7748 | 32 byte | 56 byte | u-coordinate little-endian |
| Raw private scalar theo RFC 7748 | 32 byte | 56 byte | Input scalar, provider xử lý clamping |
| Raw shared secret | 32 byte | 56 byte | Kết quả key agreement |
| Java `PublicKey.getEncoded()` | Dài hơn 32 byte | Dài hơn 56 byte | DER **SubjectPublicKeyInfo** với algorithm identifier |
| Java `PrivateKey.getEncoded()` | Dài hơn raw hoặc có thể không export | Tương tự | Thường **PKCS#8** khi private key export được |

**X.509 SPKI** (SubjectPublicKeyInfo) chứa cấu trúc ASN.1/DER và algorithm identifier. RFC 8410 định nghĩa OID tương ứng:

- X25519: **1.3.101.110**.
- X448: **1.3.101.111**.

Trong Java:

```java
KeyFactory factory = KeyFactory.getInstance("XDH");
byte[] encoded = bob.getPublic().getEncoded();

PublicKey decoded =
        factory.generatePublic(new X509EncodedKeySpec(encoded));
```

Đây là đoạn minh họa với biến `KeyPair bob` đã có. **Không** lấy raw public 32 byte từ một thư viện khác rồi đưa thẳng vào `X509EncodedKeySpec`. Java đòi **container SPKI đầy đủ**, không phải chỉ public coordinate.

### Raw u-coordinate little-endian và BigInteger

RFC 7748 mã hóa public u-coordinate theo **little-endian**, còn `new BigInteger(byte[])` diễn giải mảng bytes theo **big-endian có dấu**. Muốn import raw public u:

```java
BigInteger u = littleEndianUnsigned(rawBytes);

PublicKey peer = KeyFactory.getInstance("XDH")
        .generatePublic(new XECPublicKeySpec(
                NamedParameterSpec.X25519, u));
```

Đây là đoạn minh họa: `littleEndianUnsigned(...)` được định nghĩa trong chương trình đầy đủ bên dưới; `rawBytes` phải là input X25519 có độ dài/format được kiểm tra ở tầng giao thức.

**Không** bỏ qua thao tác đảo byte rồi nghĩ kết quả giống nhau. **Không** dùng `new BigInteger(rawBytes)` trực tiếp do còn sai cả dấu của BigInteger. Khi phải chuyển byte array về số nguyên, đảo thành big-endian rồi dùng `new BigInteger(1, reversed)`.

### Private scalar và clamping

`XECPrivateKeySpec(NamedParameterSpec.X25519, rawScalar)` đại diện cho một encoded scalar theo RFC 7748. Theo tài liệu Java, dữ liệu scalar trong spec **chưa được prune/clamp**; provider áp dụng thao tác đó khi thực hiện thuật toán.

Không nhầm seed, scalar, scalar đã clamp và PKCS#8: những representation này có hợp đồng riêng. Không tự biến đổi bit của private scalar mà không có lý do chuẩn hóa. Việc một provider xuất private key `getEncoded()` được không cũng phụ thuộc key type và chính sách: private key trong HSM có thể không bao giờ cho export.

## 5. Test vector RFC 7748 là phép thử độc lập

Một lỗi tinh vi: nếu chỉ kiểm tra Alice/Bob trong cùng một provider, **cả hai phía có thể cùng mắc một lỗi encoding** nhưng vẫn cho kết quả giống nhau. Vì vậy cần ít nhất một **test vector độc lập** từ RFC 7748.

Ví dụ vector chuẩn X25519:

```text
Alice private scalar (32 byte, hex):
77076d0a7318a57d3c16c17251b26645df4c2f87ebc0992ab177fba51db92c2a

Bob public u-coordinate (32 byte raw, little-endian):
de9edb7d7b7dc1b4d35b61c2ece435373f8343c85b78674dadfc7e146f882b4f

Expected shared secret (32 byte, hex):
4a5d9d5ba4ce2de1728e3bf480350f25e07e21c947d19e3376f09b3c1e161742
```

Chương trình phần sau import private scalar bằng `XECPrivateKeySpec`, chuyển raw public u-coordinate sang `BigInteger` đúng little-endian và kiểm tra secret bằng `MessageDigest.isEqual(...)`. Nếu so khớp, test giúp bảo đảm đúng thuật toán/encoding theo một vector **được công bố công khai**.

**Vector này chỉ dùng cho test**, không sử dụng private scalar công khai của RFC trong production. Không log private key/secret thật hoặc paste chúng vào issue tracker.

## 6. Ví dụ Java 11 đầy đủ: tám kiểm thử cốt lõi

Tệp **`XdhValidationDemo.java`** dùng JDK tiêu chuẩn, không cần Internet. Nó kiểm tra:

1. X25519 Alice/Bob tạo cùng 32-byte secret.
2. Public key X.509 SPKI round-trip không đổi kết quả.
3. DER bị cắt một byte bị từ chối.
4. X25519 private + X448 public bị từ chối.
5. Public u-coordinate zero/bậc nhỏ không được phép dẫn đến shared secret được chấp nhận.
6. Public key X25519 hợp lệ của người khác tạo secret khác, không tự xác thực peer.
7. Vector RFC 7748 đúng.
8. X448 sinh shared secret hai phía giống nhau và dài 56 byte.

### 6.1. Source code

```java
import java.math.BigInteger;
import java.security.GeneralSecurityException;
import java.security.InvalidKeyException;
import java.security.KeyFactory;
import java.security.KeyPair;
import java.security.KeyPairGenerator;
import java.security.MessageDigest;
import java.security.PrivateKey;
import java.security.PublicKey;
import java.security.spec.InvalidKeySpecException;
import java.security.spec.NamedParameterSpec;
import java.security.spec.XECPrivateKeySpec;
import java.security.spec.XECPublicKeySpec;
import java.security.spec.X509EncodedKeySpec;
import java.util.Arrays;
import javax.crypto.KeyAgreement;

public class XdhValidationDemo {
    private static byte[] agree(PrivateKey own, PublicKey other)
            throws GeneralSecurityException {
        KeyAgreement agreement = KeyAgreement.getInstance("XDH");
        agreement.init(own);
        agreement.doPhase(other, true);
        return agreement.generateSecret();
    }

    private static KeyPair create(NamedParameterSpec curve)
            throws GeneralSecurityException {
        KeyPairGenerator generator =
                KeyPairGenerator.getInstance("XDH");
        generator.initialize(curve);
        return generator.generateKeyPair();
    }

    private static byte[] hex(String value) {
        if ((value.length() & 1) != 0) {
            throw new IllegalArgumentException("Odd hex length");
        }
        byte[] result = new byte[value.length() / 2];
        for (int i = 0; i < result.length; i++) {
            int hi = Character.digit(value.charAt(2 * i), 16);
            int lo = Character.digit(value.charAt(2 * i + 1), 16);
            if (hi < 0 || lo < 0) {
                throw new IllegalArgumentException(
                        "Non-hex character");
            }
            result[i] = (byte) ((hi << 4) | lo);
        }
        return result;
    }

    private static BigInteger littleEndianUnsigned(byte[] bytes) {
        byte[] reversed = bytes.clone();
        for (int i = 0, j = reversed.length - 1;
                i < j; i++, j--) {
            byte temp = reversed[i];
            reversed[i] = reversed[j];
            reversed[j] = temp;
        }
        return new BigInteger(1, reversed);
    }

    private static boolean allZero(byte[] bytes) {
        int combined = 0;
        for (byte value : bytes) {
            combined |= value & 0xff;
        }
        return combined == 0;
    }

    public static void main(String[] args) throws Exception {
        KeyPair alice = create(NamedParameterSpec.X25519);
        KeyPair bob = create(NamedParameterSpec.X25519);
        byte[] ab = agree(alice.getPrivate(), bob.getPublic());
        byte[] ba = agree(bob.getPrivate(), alice.getPublic());
        if (!MessageDigest.isEqual(ab, ba) || ab.length != 32) {
            throw new IllegalStateException(
                    "X25519 exchange failed");
        }
        System.out.println("x25519Mutual=true");
        System.out.println("secretLength=32");

        KeyFactory factory = KeyFactory.getInstance("XDH");
        byte[] publicSpki = bob.getPublic().getEncoded();
        PublicKey restored = factory.generatePublic(
                new X509EncodedKeySpec(publicSpki));
        System.out.println("spkiRoundTrip="
                + MessageDigest.isEqual(ab,
                        agree(alice.getPrivate(), restored)));

        boolean malformedRejected = false;
        byte[] truncated = Arrays.copyOf(
                publicSpki, publicSpki.length - 1);
        try {
            factory.generatePublic(
                    new X509EncodedKeySpec(truncated));
        } catch (InvalidKeySpecException ex) {
            malformedRejected = true;
        }
        System.out.println(
                "malformedSpkiRejected=" + malformedRejected);

        KeyPair x448 = create(NamedParameterSpec.X448);
        boolean mixedCurveRejected = false;
        try {
            agree(alice.getPrivate(), x448.getPublic());
        } catch (InvalidKeyException ex) {
            mixedCurveRejected = true;
        }
        System.out.println(
                "mixedCurveRejected=" + mixedCurveRejected);

        PublicKey zeroPoint = factory.generatePublic(
                new XECPublicKeySpec(
                        NamedParameterSpec.X25519,
                        BigInteger.ZERO));
        boolean zeroRejected = false;
        try {
            byte[] possible =
                    agree(alice.getPrivate(), zeroPoint);
            if (allZero(possible)) {
                zeroRejected = true;
            } else {
                throw new IllegalStateException(
                        "Unexpected zero-point result");
            }
        } catch (InvalidKeyException ex) {
            zeroRejected = true;
        }
        System.out.println("lowOrderRejected=" + zeroRejected);

        KeyPair unrelated = create(NamedParameterSpec.X25519);
        byte[] wrong = agree(
                alice.getPrivate(), unrelated.getPublic());
        System.out.println(
                "unrelatedPeerProducesDifferentSecret="
                + !MessageDigest.isEqual(ab, wrong));

        PrivateKey rfcPrivate = factory.generatePrivate(
                new XECPrivateKeySpec(
                        NamedParameterSpec.X25519,
                        hex("77076d0a7318a57d3c16c17251b2664"
                          + "5df4c2f87ebc0992ab177fba51db92c2a")));
        PublicKey rfcPublic = factory.generatePublic(
                new XECPublicKeySpec(
                        NamedParameterSpec.X25519,
                        littleEndianUnsigned(hex(
                        "de9edb7d7b7dc1b4d35b61c2ece4353"
                        + "73f8343c85b78674dadfc7e146f882b4f"))));
        boolean vectorMatch = MessageDigest.isEqual(
                agree(rfcPrivate, rfcPublic),
                hex("4a5d9d5ba4ce2de1728e3bf480350f"
                  + "25e07e21c947d19e3376f09b3c1e161742"));
        System.out.println("rfc7748Vector=" + vectorMatch);

        KeyPair x448Second = create(NamedParameterSpec.X448);
        byte[] x448Ab = agree(
                x448.getPrivate(), x448Second.getPublic());
        byte[] x448Ba = agree(
                x448Second.getPrivate(), x448.getPublic());
        System.out.println("x448Mutual="
                + (x448Ab.length == 56
                && MessageDigest.isEqual(x448Ab, x448Ba)));

        Arrays.fill(ab, (byte) 0);
        Arrays.fill(ba, (byte) 0);
        Arrays.fill(wrong, (byte) 0);
        Arrays.fill(x448Ab, (byte) 0);
        Arrays.fill(x448Ba, (byte) 0);
    }
}
```

Các chuỗi hex RFC 7748 được nối bằng `+` để trình bày dễ đọc. Chúng biểu diễn đúng cùng 32 byte ở mỗi trường hợp, không có whitespace trong dữ liệu crypto. Mẫu này tạo khóa test ngẫu nhiên nhưng **không in khóa/secret**; kết quả dựa trên các bất biến và vector xác định.


Chương trình đã được biên dịch bằng `javac --release 11` và chạy thành công với JDK có provider XDH. Không cố định tên provider trong test để tránh một phụ thuộc không cần thiết. Kết quả về cách provider **ném ngoại lệ** có thể khác nhau trên JDK/provider khác; khi chuyển môi trường, điều kiện an toàn vẫn là không chấp nhận dữ liệu/key agreement không hợp lệ.

### 6.3. Giải thích các test

**Test X25519 hai chiều.** `ab = agree(alicePrivate, bobPublic)` và `ba = agree(bobPrivate, alicePublic)` phải bằng nhau và dài 32 byte. Nếu khác nhau, implementation/encoding đang sai hoặc đã dùng cặp key không tương ứng.

**Test SPKI.** `bob.getPublic().getEncoded()` trả khóa ở định dạng X.509 SubjectPublicKeyInfo của JCA. Đưa vào `X509EncodedKeySpec` và `KeyFactory.generatePublic` phải giữ nguyên public key và shared secret.

**Test malformed DER.** Cắt một byte cuối của cấu trúc SPKI rồi import. Trong provider đã thử, `InvalidKeySpecException` được ném. Không cần xác định chính xác thông báo lỗi DER vì nó có thể khác nhau.

**Test mixed curve.** Private X25519 với public X448 không thể tạo agreement hợp lệ. Provider thử nghiệm ném `InvalidKeyException`. Curve mismatch không phải lỗi cần tự “sửa” bằng truncate/padding.

**Test low order.** Public key u-coordinate zero có thể khiến XDH tạo output all-zero hoặc provider chủ động ném `InvalidKeyException`. Mẫu chấp nhận **một trong hai con đường từ chối an toàn**: provider ném lỗi, hoặc code phát hiện secret toàn zero và đánh dấu không chấp nhận. Không sử dụng all-zero secret làm key.

**Test unrelated peer.** Key X25519 của bên thứ ba có thể **hoàn toàn hợp lệ**. `KeyAgreement` tính được một secret khác, nên không có exception. Ứng dụng thật phải xác thực public key/handshake; không thể biết đây là “sai người” chỉ bằng kiểm tra độ dài hoặc curve.

**Test vector RFC 7748.** Dùng scalar Alice, raw u-coordinate Bob và expected secret của chuẩn. Helper `littleEndianUnsigned` tránh lỗi chuyển little-endian thành BigInteger. Kết quả `true` xác nhận interop với một vector chuẩn độc lập.

**Test X448.** Hai cặp X448 được tạo, mỗi bên tính chung một 56-byte secret. Điều này chứng minh code XDH hỗ trợ curve thứ hai và độ dài khác X25519.

### Lưu ý về bảo mật của demo

Chương trình là **fixture kiểm thử**, không phải authenticated key exchange protocol đầy đủ. Nó không chứa tính năng xác thực đối tác, HKDF hay mã hóa dữ liệu sản phẩm. Việc xóa một vài mảng `byte[]` cuối chương trình không thể bảo đảm xóa hết mọi bản sao secret trong JVM hay provider. Trong sản phẩm, dùng giao thức chuẩn và quản lý key material phù hợp ranh giới bảo mật.

## 7. Public key bậc nhỏ và all-zero: xử lý đúng đặc tả

RFC 7748 mô tả các input public key có bậc nhỏ có thể loại bỏ đóng góp của private scalar đối tác khỏi phép thỏa thuận và sinh shared secret toàn zero. Tiêu chuẩn cho phép implementation kiểm tra all-zero để từ chối.

**Tại sao cần quan tâm?** Nếu một giao thức coi all-zero như secret “chỉ hai bên biết”, bất kỳ bên nào cũng có thể biết giá trị đó; các tính chất bảo mật bị phá hỏng. Vì vậy với giao thức sản phẩm, không được sử dụng all-zero output như một khóa hoặc dấu hiệu đã xác thực thành công.

Cách viết kiểm tra không có phân nhánh phụ thuộc từng byte:

```java
private static boolean allZero(byte[] bytes) {
    int combined = 0;
    for (byte value : bytes) {
        combined |= value & 0xff;
    }
    return combined == 0;
}
```

Đây là helper độc lập về mặt cú pháp, nhưng muốn sử dụng phải kết hợp với kết quả `generateSecret()` và quy tắc xử lý lỗi. Một implementation có thể từ chối ở `doPhase` thay vì trả secret. **Không** bắt buộc test phải nhìn thấy đúng một exception class cho mọi provider.

**Đừng coi mọi raw public key “non-canonical” là sai.** RFC 7748 đặt quy tắc xử lý cụ thể:

- Public u-coordinate raw X25519 có định dạng little-endian và quy tắc mask bit cao.
- Giá trị non-canonical thuộc các trường hợp RFC cho phép phải được xử lý theo chuẩn thay vì tự động báo malformed.
- Cấu trúc ASN.1 DER/SPKI lỗi lại là **vấn đề format khác**, vẫn có thể bị từ chối khi import.

Vì vậy, phải phân biệt **bad DER**, **raw public coordinate không canonical nhưng thuộc phạm vi RFC**, và **low-order/all-zero**. Không áp một assertion chung “mọi public value lạ đều phải ném `InvalidKeySpecException`”.

## 8. “Sai khóa” đúng curve nhưng sai danh tính

Một nguy cơ không thể giải quyết chỉ bằng KeyFactory:

```text
Alice mong chờ publicBob
Nhưng nhận được publicMallory (X25519 hợp lệ)

X25519(alicePrivate, publicMallory) -> có thể thành công
X25519(alicePrivate, publicBob)     -> một secret khác
```

Trong mạng thật, Alice **không có sẵn secret Alice–Bob** để so sánh như unit test. Vì thế phải xác minh danh tính khóa qua:

- **Certificate / chữ ký** được kiểm tra đúng trust anchor và danh tính endpoint.
- **Pinned public key** có quy trình rotation/revocation phù hợp nếu hệ thống dùng mô hình này.
- **Transcript binding**: gắn version, client/server roles, public keys, thuật toán và context vào quá trình derivation/authentication theo protocol.
- **Key confirmation**: MAC/AEAD/Finished message chứng minh hai phía sở hữu đúng khóa phiên theo quy tắc giao thức.
- **Anti-replay / freshness**: nonce, ephemeral key và session binding theo thiết kế được đánh giá.

Không chỉ dựa vào “thành công KeyAgreement” để xác định Bob. Khi cần trao đổi khóa thực tế, ưu tiên giao thức đã được chuẩn hóa và kiểm toán như TLS 1.3 hoặc profile HPKE phù hợp yêu cầu; đừng tự ghép một ứng dụng mã hóa tùy hứng.

## 9. Từ XDH shared secret đến symmetric key

XDH raw shared secret **chưa phải khóa AES ứng dụng**. Các giao thức hiện đại thường dùng **KDF**, ví dụ HKDF theo RFC 5869, với context và thông tin ràng buộc phù hợp. KDF giải quyết việc tạo key material, phân tách mục đích và gắn thông tin phiên.

Các trường có thể phải nhất quán khi interop:

| Trường | Nếu hai bên khác nhau |
| --- | --- |
| X25519/X448 | Không cùng phép key agreement |
| Raw public key format/endianness | Tạo public key sai hoặc parse lỗi |
| Private scalar encoding/clamping | Kết quả XDH khác hoặc import thất bại |
| Raw shared secret byte order | HKDF input khác |
| HKDF hash | Output key khác |
| HKDF salt | Output key khác |
| HKDF info/context | Output key khác |
| Thứ tự client/server public keys | Transcript/KDF binding khác |
| Authentication/key confirmation | Có thể chấp nhận nhầm đối tác |
| AEAD nonce/key separation | Nguy cơ dùng sai khóa, nonce hoặc replay |

Không **tùy tiện cắt 16 byte đầu của raw secret** rồi coi đó là AES-128 key “đủ an toàn” cho mọi protocol. Hãy theo KDF/key schedule chính thức của giao thức; không invent HKDF info string giữa client và server một cách riêng rẽ.

Nếu dùng một HSM/provider chuyên dụng, private key có thể chỉ tồn tại như handle bên trong module. Đừng yêu cầu dump private bytes để debug; test bằng vector công khai hoặc cơ chế attestation/key agreement do provider hỗ trợ.

## 10. Kiểm thử khả năng tương tác: bốn cấp độ

### Cấp 1 — Cùng một JDK/provider

- X25519/X448 happy path và độ dài.
- `KeyPairGenerator`, `KeyFactory`, `KeyAgreement` nhất quán.
- SPKI round-trip không đổi kết quả.
- Khóa sai curve, SPKI bị cắt, all-zero không được chấp nhận.

**Giới hạn:** hai phía trong cùng implementation có thể cùng mắc một lỗi encoding mà test đối xứng không nhận ra.

### Cấp 2 — RFC 7748 vectors

- Scalar raw, public u-coordinate raw và expected secret khớp tài liệu.
- Kiểm tra cả test vector X25519 và X448 nếu sản phẩm thực sự dùng cả hai.
- Xác minh little-endian và raw bytes, không nhầm với text hex UTF-8.

**Lợi ích:** kiểm chứng khả năng tính đúng theo một chuẩn bên ngoài provider.

### Cấp 3 — Cùng thuật toán, khác provider/JDK

- Chạy trên JDK 11 và phiên bản JDK production.
- Dùng provider được sản phẩm hỗ trợ; ví dụ Oracle/OpenJDK SunEC hoặc HSM/crypto provider được tổ chức phê duyệt.
- Ghi metadata: provider name, version, JDK vendor/version, curve và key encoding.
- Không assert các lỗi nội bộ/exception message giống hệt nhau.
- Kiểm tra unsupported curves, key export permissions và provider restrictions.

**Lưu ý:** demo chính có test vector chuẩn, nhưng chưa gọi hai provider độc lập trong cùng một lần chạy; đừng tuyên bố nó chứng minh mọi provider liên thông.

### Cấp 4 — Cross-language/SDK thực tế

Đối với Java ↔ Go/Rust/Python hoặc API đối tác:

1. Chốt curve: X25519 hay X448.
2. Chốt wire format public key: raw 32/56-byte u-coordinate hay DER SPKI.
3. Chốt định dạng private key trong **test fixture**, không truyền private key production.
4. Chốt encoding: raw bytes/little-endian; hex/base64 chỉ là lớp vận chuyển text do API quy định.
5. Chốt HKDF salt/hash/info/transcript, role và thứ tự public keys.
6. Dùng vector RFC 7748 để kiểm tra hai implementation riêng.
7. Thử positive, malformed, mixed curve, low-order, wrong-but-valid peer.
8. Thử key rotation, transcript bị thay đổi, key confirmation và lỗi version.
9. Kiểm tra parser có **giới hạn độ dài** và không treo/crash khi input bất thường.
10. Ghi kết quả tương thích trong CI, dùng credential/test keys riêng và bảo vệ logs.

Đừng dùng một phép so sánh mảng trong cùng JVM làm thay thế cho **integration test thật sự** qua wire format và protocol handshake.

## 11. Kiểm thử đầu vào không hợp lệ mà không làm yếu crypto

Một chương trình nhận public key từ mạng nên kiểm soát:

- **Độ dài payload:** giới hạn số byte trước khi parse; raw X25519 là 32 byte, X448 là 56 byte, DER có format/size khác.
- **Loại dữ liệu:** key exchange phải sử dụng đúng curve, đúng role và chuẩn encoding.
- **Input bị cắt/sửa:** parser fail an toàn, không tạo public key ngầm định/zero fill.
- **Low-order/all-zero:** không tiếp tục sử dụng secret yếu.
- **Non-canonical raw:** tuân thủ RFC 7748, không bịa quy tắc từ chối thiếu căn cứ.
- **Sai đối tác:** xác thực danh tính và transcript ở tầng giao thức; không dựa vào API crypto tự nhận ra.
- **Lỗi provider:** xử lý lỗi crypto và không tự fallback sang một curve yếu hoặc không đúng protocol.
- **Log:** không chứa secret, private key hoặc toàn bộ thông điệp nhạy cảm.
- **Timeout/resource:** giới hạn kích thước ASN.1, thời gian parse, số handshake đồng thời và số lần retry.

**Không viết lại Montgomery ladder, curve arithmetic hoặc scalar clamping trong business code** chỉ để qua một test. Dùng provider JCA/JCE đã được kiểm thử và chuẩn hóa wire format giữa các thành phần.

### Vì sao parser không đồng nghĩa xác thực?

Một public key **đúng format và đúng curve** mới chỉ chứng minh nó có thể đi vào phép toán. Nó không chứa thông tin “người sở hữu là Bob” theo cách XDH tự xác minh. Nếu người gửi thay một public key khác cũng hợp lệ, `KeyFactory` không có lý do phải ném lỗi.

Tương tự, nếu hai bên dùng hai bộ HKDF info khác nhau, raw XDH có thể vẫn giống nhau nhưng session keys khác. Điều đó phải được phát hiện bởi **protocol key confirmation**, không phải “kiểm tra curve”.

## 13. Bài tập và đáp án

**Bài 1 — Khác curve.** Private X25519 + public X448 có được cắt public xuống 32 byte rồi tính không? **Không**. Đây là curve không tương thích; phải từ chối.

**Bài 2 — Wrong peer.** Public key X25519 của Mallory có định dạng chuẩn. `KeyAgreement.doPhase` có bắt buộc lỗi vì Alice mong Bob? **Không**. Cần xác thực public key/peer ở protocol.

**Bài 3 — Độ dài.** Shared secret X25519 dài **32 byte**; X448 dài **56 byte**. Đây là độ dài raw secret, không phải độ dài SPKI DER.

**Bài 4 — Format.** Java nhận raw X25519 32 byte từ SDK khác rồi dùng `X509EncodedKeySpec`. Vì sao lỗi? **SPKI có ASN.1 DER và OID**, còn raw key chỉ có coordinate.

**Bài 5 — Endianness.** Đoạn `new BigInteger(rawKey)` sai ở đâu? **BigInteger(byte[]) dùng big-endian có dấu**. Dùng `littleEndianUnsigned` và `new BigInteger(1, reversed)`.

**Bài 6 — Low-order.** Provider trả secret 32 byte toàn zero. Có được dùng để tạo AES key không? **Không**; phải từ chối kết quả này.

**Bài 7 — DER bị cắt.** Tệp SPKI của Bob thiếu byte cuối. Nên phát hiện ở `KeyFactory.generatePublic` hay đợi tới `generateSecret()`? **Tại bước parse/import**, ví dụ nhận `InvalidKeySpecException`.

**Bài 8 — RFC vector.** Scalar Alice bắt đầu `77076d...` và public Bob bắt đầu `de9edb...`. Expected secret bắt đầu `4a5d9d...`, nhưng bài test phải so **đủ 32 byte**, không chỉ prefix.

**Bài 9 — HKDF.** Hai bên tạo cùng raw XDH secret nhưng khác `info`; có thể tạo khóa ứng dụng khác không? **Có**. Cần thống nhất key schedule và transcript.

**Bài 10 — Interop.** Có chứng minh được Java ↔ Go interoperable bằng test SPKI roundtrip trong một JDK? **Chưa**. Phải thực sự chạy hai implementation và kiểm tra wire encoding, RFC vectors cùng KDF output.

### Checklist production

1. XDH/X25519/X448 dùng đúng, không nhầm với EdDSA hoặc ECDH khác?
2. Curve và wire format được định nghĩa rõ trong hợp đồng?
3. Có kiểm tra malformed DER, curve mismatch và low-order/all-zero?
4. Có xác thực public key của peer và key confirmation theo protocol?
5. Có RFC 7748 vector độc lập và test cross-provider/cross-language?
6. Có chuẩn hóa little-endian raw u-coordinate và SPKI/PKCS#8?
7. Có KDF và transcript binding thay vì dùng raw secret tùy tiện?
8. Private key/secret không được log hoặc export khi không được phép?
9. Test assertions không phụ thuộc message riêng của provider?
10. Đã chạy trên JDK 11 và runtime hiện đại thực tế theo đúng Special Note?
