# TLS 1.3 — Thương lượng giao thức giữa client và server (Java 11+)

## Mục tiêu

Một chương trình HTTPS không tự động đạt bảo mật mong muốn chỉ vì chạy Java 11 hoặc có chữ `TLSv1.3` trong cấu hình. **Client và server phải thương lượng** phiên bản TLS, thuật toán mật mã, tham số trao đổi khóa và cơ chế xác thực phù hợp trước khi trao đổi dữ liệu ứng dụng. Nếu không có cấu hình khả dụng chung, TLS handshake thất bại.

Từ **Java 11**, triển khai JSSE trong JDK đã hỗ trợ **TLS 1.3** (JEP 332). Các API `SSLContext`, `SSLParameters`, `SSLSocket`, `SSLServerSocket`, `SSLEngine` và `SSLSession` vẫn được dùng trên JDK hiện đại. Bài này giải thích:

- Cách client gửi `ClientHello` và server chọn phiên bản qua `ServerHello`.
- Vì sao `supported_versions` mới xác định TLS 1.3, thay vì chỉ đọc `legacy_version`.
- Phân biệt `getSupportedProtocols()`, `getEnabledProtocols()` và `SSLSession.getProtocol()`.
- Viết và chạy **chương trình Java 11 độc lập** với certificate/truststore thật cho localhost, xác minh ba tình huống: TLS 1.3 thành công, chọn TLS 1.2 khi tương thích, và thất bại khi không có phiên bản chung.
- Phân biệt TLS protocol negotiation với certificate validation, SNI và ALPN của HTTP/2.
- Chẩn đoán lỗi handshake mà **không** tắt hostname verification, dùng trust-all hoặc bật giao thức yếu.

**Đặc tả mới:** từ **tháng 7/2026**, **RFC 9846** thay thế RFC 8446 về TLS 1.3. Bản cập nhật giữ nguyên tên phiên bản TLS 1.3 và tương thích ngược với TLS 1.3 theo RFC 8446, đồng thời làm chặt một số yêu cầu. Trong tài liệu Java 11 xuất bản trước 2026 bạn có thể thấy RFC 8446; để tham khảo chuẩn hiện hành, hãy dùng RFC 9846.

## 1. TLS handshake thực hiện những gì?

TLS bảo vệ tính bí mật, toàn vẹn và xác thực peer trong kết nối. Với HTTPS, phía client thường xác minh danh tính server bằng certificate và tên host; server có thể yêu cầu chứng chỉ client nếu hệ thống sử dụng mTLS.

Quá trình thông thường của một **full TLS 1.3 handshake dựa trên certificate**:

```text
Client                                       Server
   |                                             |
   | -- ClientHello ---------------------------> |
   |    supported_versions, cipher_suites,       |
   |    supported_groups, key_share,             |
   |    signature_algorithms, SNI, ALPN ...       |
   |                                             |
   | <--------------------------- ServerHello --- |
   |    selected_version, cipher_suite, key_share|
   | <-------------------- EncryptedExtensions -- |
   | <-------------------------- Certificate* --- |
   | <-------------------- CertificateVerify* --- |
   | <----------------------------- Finished ---- |
   | -- Finished -------------------------------> |
   |                                             |
   | <=== Application data được mã hóa =========> |
```

Dấu `*` cho biết các thông điệp trong tình huống xác thực server bằng certificate thông thường; handshake PSK/resumption hoặc mTLS có thể khác. Trong TLS 1.3, phần lớn thông điệp sau `ServerHello` được bảo vệ bằng khóa handshake. Trong một số trường hợp có `HelloRetryRequest` để client gửi lại `ClientHello` với tham số key share phù hợp.

**Ba việc khác nhau cần phân biệt:**

1. **TCP connect thành công:** chỉ có kết nối vận chuyển, chưa có bảo đảm TLS hay xác thực.
2. **TLS handshake thành công:** hai phía đã thương lượng các tham số và khóa, cùng xác thực theo cấu hình trust.
3. **HTTP request thành công:** tầng ứng dụng nhận status/response phù hợp; điều này không được suy ra chỉ từ TLS handshake.

Một reverse proxy hoặc load balancer có thể kết thúc TLS và tạo một kết nối riêng tới backend. Phiên bản TLS mà client đo được ở chặng client→proxy **không tự nói** phiên bản của chặng proxy→backend.

## 2. ClientHello: client đề xuất các khả năng

Khi bắt đầu, client gửi `ClientHello`. Các thành phần quan trọng:

| Trường/extension | Mục đích | Lưu ý |
| --- | --- | --- |
| `supported_versions` | Danh sách phiên bản TLS client cho phép, ví dụ TLS 1.3 và 1.2 | **Quyết định phiên bản TLS 1.3 qua extension này** |
| `cipher_suites` | Danh sách cipher suite được hỗ trợ/cho phép | TLS 1.3 có cấu trúc suite khác TLS 1.2 |
| `supported_groups` | Các nhóm trao đổi khóa mà client hỗ trợ | Phải có nhóm khả dụng phù hợp với server |
| `key_share` | Tham số khóa tạm thời của nhóm được đưa ra | Server có thể dùng hoặc yêu cầu HelloRetryRequest |
| `signature_algorithms` | Thuật toán chữ ký có thể dùng trong handshake | Liên quan chứng chỉ/chữ ký xác thực |
| `server_name` (SNI) | Hostname đích, giúp server chọn virtual host/certificate | **Không phải thay thế hostname verification** |
| `ALPN` | Danh sách giao thức ứng dụng, ví dụ `h2`/`http/1.1` | Không phải phiên bản TLS |
| `legacy_version` | Trường tương thích trong cấu trúc handshake | **Không** dùng riêng trường này để kết luận phiên bản negotiated |

### Cảnh báo về `legacy_version`

Trong TLS 1.3, cấu trúc ClientHello/ServerHello vẫn có trường legacy mang giá trị **TLS 1.2** nhằm tương thích với các thiết bị trung gian. Phiên bản được thỏa thuận **thực tế** nằm trong extension `supported_versions`. Vì vậy:

```text
ClientHello.legacy_version = TLS 1.2
ClientHello.supported_versions = [TLS 1.3, TLS 1.2]
ServerHello.supported_versions = TLS 1.3
SSLSession.getProtocol() = TLSv1.3
```

Đây là mô hình logic, không phải output của chương trình bên dưới. **Không được kết luận** kết nối đã bị downgrade chỉ vì một dòng packet dump hiển thị `legacy_version = TLS 1.2`.

## 3. ServerHello: server lựa chọn phiên bản, thuật toán

Server kiểm tra các khả năng của client với cấu hình của mình:

- Có ít nhất một **phiên bản TLS chung** được security policy cho phép không?
- Có bộ mã hóa và nhóm trao đổi khóa phù hợp không?
- Chứng chỉ, private key, chữ ký và trust policy có cho phép hoàn tất handshake không?
- Các mở rộng như SNI và ALPN có thỏa mãn những yêu cầu của ứng dụng không?

Nếu phù hợp, server chọn phiên bản và thông số qua `ServerHello`, tiếp tục xác thực và thiết lập khóa. **Không có phiên bản/thuật toán hợp lệ chung** thì handshake thất bại, không được tự chuyển HTTPS thành HTTP để gửi tiếp dữ liệu.

| Client cho phép | Server cho phép | Kết quả khi cipher/cert hợp lệ |
| --- | --- | --- |
| TLS 1.3, TLS 1.2 | TLS 1.3, TLS 1.2 | Thường chọn **TLS 1.3** |
| TLS 1.3, TLS 1.2 | TLS 1.2 | Có thể chọn **TLS 1.2** nếu chính sách cho phép |
| Chỉ TLS 1.3 | Chỉ TLS 1.2 | **Không giao nhau → handshake thất bại** |
| Chỉ TLS 1.3 | TLS 1.3 nhưng không có certificate/algorithm phù hợp | Vẫn có thể **thất bại** |

**TLS 1.2** vẫn có thể được dùng với cấu hình an toàn trong các môi trường cần tương thích; tuy nhiên **TLS 1.3 là lựa chọn ưu tiên**. Không bật lại SSLv3, TLS 1.0 hoặc TLS 1.1 chỉ để làm một handshake lỗi trở nên thành công.

## 4. Ba lớp khả năng trong Java: supported, enabled, negotiated

Trong `javax.net.ssl`:

- **Supported protocols:** `socket.getSupportedProtocols()` — toàn bộ tên giao thức implementation biết hỗ trợ về mặt API.
- **Enabled protocols:** `socket.getEnabledProtocols()` — tập con được bật cho socket/engine. Đây vẫn chưa phải phiên bản đang chạy.
- **Negotiated protocol:** `socket.getSession().getProtocol()` — phiên bản **đã được chọn sau handshake thành công**, ví dụ `TLSv1.3`.

Các phương thức liên quan:

```java
SSLContext context = SSLContext.getInstance("TLS");

// Đoạn minh họa: context phải được init với key/trust đúng.
// host và port phải được cung cấp bởi chương trình.
SSLSocket socket = (SSLSocket)
        context.getSocketFactory().createSocket(host, port);

String[] supported = socket.getSupportedProtocols();
String[] enabled = socket.getEnabledProtocols();

socket.setEnabledProtocols(
        new String[] {"TLSv1.3", "TLSv1.2"});

socket.startHandshake();
String negotiated = socket.getSession().getProtocol();
String cipher = socket.getSession().getCipherSuite();
```

**Đây chỉ là đoạn minh họa** cần biến `host`, `port`, các import `SSLContext`/`SSLSocket`, `init(...)`, kiểm tra certificate, xử lý exception và đóng socket. Xem ví dụ đầy đủ ở phần 6.

**Supported không đồng nghĩa allowed.** Một phiên bản có tên trong `getSupportedProtocols()` vẫn có thể bị cấm bởi `jdk.tls.disabledAlgorithms` hoặc các security constraints của JDK/provider. Việc gọi `setEnabledProtocols(...)` cũng không bảo đảm server sẽ chấp nhận, cipher sẽ phù hợp hoặc chứng chỉ sẽ hợp lệ.

| API | Dùng cho | Ý nghĩa |
| --- | --- | --- |
| `SSLContext.getInstance("TLS")` | Tạo nền JSSE | Có thể bao gồm nhiều version do provider cho phép |
| `SSLContext.init(...)` | Key/trust managers | Định nghĩa danh tính và trust policy |
| `SSLSocket.setEnabledProtocols(...)` | Một kết nối TLS client | Giới hạn version trước handshake |
| `SSLServerSocket.setEnabledProtocols(...)` | TLS listener | Cấu hình version cho các socket chấp nhận |
| `SSLParameters.setProtocols(...)` | Cấu hình socket/engine | Đặt danh sách version |
| `SSLSocket.startHandshake()` | Kết nối hiện tại | Bắt đầu handshake rõ ràng |
| `SSLSession.getProtocol()` | Kết nối đã bắt tay xong | Phiên bản TLS đã chọn |
| `SSLSession.getCipherSuite()` | Kết nối đã bắt tay xong | Cipher suite đã chọn |
| `SSLSocket.getApplicationProtocol()` | Kết nối dùng ALPN | Giao thức ứng dụng, không phải TLS version |

## 5. Chứng chỉ và truststore: không dùng trust-all

Để minh họa negotiation đúng cách, ta cần một server có **private key và certificate**, và một client có **truststore** tin certificate phù hợp.

- **Server KeyStore:** chứa private key/certificate chain, được nạp vào `KeyManagerFactory`.
- **Client TrustStore:** chứa certificate hoặc CA được phép tin, được nạp vào `TrustManagerFactory`.
- **Endpoint identification:** kiểm tra tên host/IP kết nối có khớp certificate (SAN) hay không; khác với việc kiểm tra chain được trust.

Cả ba đều có ý nghĩa; một certificate được tin nhưng không khớp tên host vẫn phải bị từ chối theo chính sách HTTPS.

**Tránh tuyệt đối** cách chữa lỗi bằng một `X509TrustManager` tự viết mà bỏ qua certificate validation, hoặc tắt hostname verification. Làm vậy có thể khiến kẻ trung gian giả làm server, dù vẫn sử dụng TLS 1.3 và mã hóa.

Trong bài học, ta tạo certificate **self-signed chỉ cho localhost** và chủ động import phần certificate công khai vào truststore test. Đây không phải quy trình cấp certificate cho môi trường production.

## 6. Ví dụ Java 11 hoàn chỉnh: ba tình huống thương lượng

Chương trình dưới đây tạo một server TLS tại `127.0.0.1` với cổng ngẫu nhiên, rồi một client SSL kết nối vào nó. Server và client có SSLContext riêng:

- Server đọc private key từ `server.p12`.
- Client đọc các chứng chỉ được tin từ `trust.p12`.
- Client bật `SSLParameters.setEndpointIdentificationAlgorithm("HTTPS")` để xác minh danh tính host/IP theo certificate.
- Hai bên đặt allowed protocols **trước handshake**.
- Cả hai đầu đọc `SSLSession.getProtocol()`; chương trình so sánh chúng khi handshake thành công.

**Ba trường hợp:** TLS 1.3 được chọn, TLS 1.2 được chọn khi chỉ server hỗ trợ 1.2, và không có version chung.

### 6.1. Tạo certificate và truststore test

Trong thư mục thử nghiệm **trống**, dùng `keytool` đi kèm JDK:

```bash
keytool -genkeypair -alias local-server -keyalg RSA -keysize 2048 -sigalg SHA256withRSA -validity 2 -storetype PKCS12 -keystore server.p12 -storepass changeit -keypass changeit -dname "CN=localhost" -ext "SAN=DNS:localhost,IP:127.0.0.1" -noprompt
keytool -exportcert -rfc -alias local-server -keystore server.p12 -storetype PKCS12 -storepass changeit -file server.crt
keytool -importcert -alias local-server -file server.crt -keystore trust.p12 -storetype PKCS12 -storepass changeit -noprompt
```

Giải thích:

- `server.p12` giữ **private key** và certificate; không commit lên Git hoặc chia sẻ cho người khác.
- `server.crt` là phần certificate công khai được export.
- `trust.p12` là truststore **riêng của client test**.
- `changeit` là mật khẩu demo công khai, **không phải lựa chọn cho sản phẩm thật**.
- SAN chứa `127.0.0.1` và `localhost`, để việc xác minh endpoint của client phù hợp đúng đích.
- Certificate hiệu lực 2 ngày, phục vụ thử nghiệm ngắn hạn; production cần PKI, quản lý secret và certificate lifecycle phù hợp.

### 6.2. Tệp chạy được: `TlsNegotiationDemo.java`

```java
import java.io.InputStream;
import java.net.InetAddress;
import java.nio.file.Files;
import java.nio.file.Path;
import java.nio.file.Paths;
import java.security.KeyStore;
import java.security.SecureRandom;
import java.util.concurrent.atomic.AtomicReference;
import javax.net.ssl.KeyManagerFactory;
import javax.net.ssl.SSLContext;
import javax.net.ssl.SSLException;
import javax.net.ssl.SSLParameters;
import javax.net.ssl.SSLServerSocket;
import javax.net.ssl.SSLSocket;
import javax.net.ssl.TrustManagerFactory;

public class TlsNegotiationDemo {
    private static KeyStore loadStore(Path file, char[] password)
            throws Exception {
        KeyStore store = KeyStore.getInstance("PKCS12");
        try (InputStream in = Files.newInputStream(file)) {
            store.load(in, password);
        }
        return store;
    }

    private static SSLContext serverContext(
            KeyStore keys, char[] password) throws Exception {
        KeyManagerFactory factory = KeyManagerFactory.getInstance(
                KeyManagerFactory.getDefaultAlgorithm());
        factory.init(keys, password);
        SSLContext context = SSLContext.getInstance("TLS");
        context.init(factory.getKeyManagers(),
                null, new SecureRandom());
        return context;
    }

    private static SSLContext clientContext(KeyStore trust)
            throws Exception {
        TrustManagerFactory factory = TrustManagerFactory.getInstance(
                TrustManagerFactory.getDefaultAlgorithm());
        factory.init(trust);
        SSLContext context = SSLContext.getInstance("TLS");
        context.init(null, factory.getTrustManagers(),
                new SecureRandom());
        return context;
    }

    private static String negotiate(
            SSLContext serverContext,
            SSLContext clientContext,
            String[] serverProtocols,
            String[] clientProtocols,
            boolean expectSuccess) throws Exception {
        InetAddress loopback =
                InetAddress.getByName("127.0.0.1");

        try (SSLServerSocket server = (SSLServerSocket)
                serverContext.getServerSocketFactory()
                        .createServerSocket(0, 1, loopback)) {
            server.setEnabledProtocols(serverProtocols);
            AtomicReference<String> serverVersion =
                    new AtomicReference<>();
            AtomicReference<Throwable> serverError =
                    new AtomicReference<>();

            Thread worker = new Thread(() -> {
                try (SSLSocket peer =
                        (SSLSocket) server.accept()) {
                    peer.setSoTimeout(5000);
                    peer.startHandshake();
                    serverVersion.set(
                            peer.getSession().getProtocol());
                } catch (Throwable ex) {
                    serverError.set(ex);
                }
            });
            worker.start();

            String clientVersion = null;
            SSLException clientError = null;

            try (SSLSocket client = (SSLSocket)
                    clientContext.getSocketFactory()
                            .createSocket(
                                    loopback,
                                    server.getLocalPort())) {
                client.setSoTimeout(5000);
                SSLParameters parameters =
                        client.getSSLParameters();
                parameters.setProtocols(clientProtocols);
                parameters.setEndpointIdentificationAlgorithm(
                        "HTTPS");
                client.setSSLParameters(parameters);

                client.startHandshake();
                clientVersion =
                        client.getSession().getProtocol();
            } catch (SSLException ex) {
                clientError = ex;
            }

            worker.join(5000);
            if (worker.isAlive()) {
                throw new IllegalStateException(
                        "TLS server thread did not finish");
            }

            if (!expectSuccess) {
                if (clientError == null) {
                    throw new IllegalStateException(
                            "Expected TLS failure");
                }
                return "handshake-failed";
            }
            if (clientError != null) {
                throw clientError;
            }
            if (serverError.get() != null) {
                throw new IllegalStateException(
                        "TLS server failure",
                        serverError.get());
            }
            if (!clientVersion.equals(serverVersion.get())) {
                throw new IllegalStateException(
                        "Negotiated versions disagree");
            }
            return clientVersion;
        }
    }

    public static void main(String[] args) throws Exception {
        if (args.length != 2) {
            throw new IllegalArgumentException(
                    "Usage: java TlsNegotiationDemo"
                    + " server.p12 trust.p12");
        }

        char[] password = "changeit".toCharArray();
        KeyStore serverKeys = loadStore(
                Paths.get(args[0]), password);
        KeyStore trust = loadStore(
                Paths.get(args[1]), password);

        SSLContext server =
                serverContext(serverKeys, password);
        SSLContext client = clientContext(trust);

        System.out.println("tls13=" + negotiate(
                server, client,
                new String[] {"TLSv1.3", "TLSv1.2"},
                new String[] {"TLSv1.3", "TLSv1.2"},
                true));
        System.out.println("tls12Fallback=" + negotiate(
                server, client,
                new String[] {"TLSv1.2"},
                new String[] {"TLSv1.3", "TLSv1.2"},
                true));
        System.out.println("noOverlap=" + negotiate(
                server, client,
                new String[] {"TLSv1.2"},
                new String[] {"TLSv1.3"},
                false));
    }
}
```

### 6.3. Biên dịch/chạy

Sau khi tạo keystore:

```bash
javac -encoding UTF-8 TlsNegotiationDemo.java
java TlsNegotiationDemo server.p12 trust.p12
```

Kiểm tra biên dịch theo API **Java 11** ngay cả khi JDK hiện tại mới hơn:

```bash
javac --release 11 -encoding UTF-8 TlsNegotiationDemo.java
java TlsNegotiationDemo server.p12 trust.p12
```

**Stdout chính xác đã kiểm tra khi biên dịch `--release 11` và chạy:**

```text
tls13=TLSv1.3
tls12Fallback=TLSv1.2
noOverlap=handshake-failed
```

Đây là kết quả của thử nghiệm thực với `keytool`, `SSLServerSocket`, `SSLSocket` và truststore; không phải kết quả suy đoán. Không cố định tên cipher suite trong stdout vì provider/security policy có thể chọn cipher khác.

### 6.4. Giải thích ba dòng kết quả

**`tls13=TLSv1.3`:** hai đầu cho phép TLS 1.3/1.2, và JSSE trên JDK thử nghiệm chọn TLS 1.3. Sau handshake, cả hai `SSLSession.getProtocol()` trả cùng phiên bản.

**`tls12Fallback=TLSv1.2`:** server chỉ cho phép TLS 1.2; client có cả 1.3 và 1.2. Nếu TLS 1.2 vẫn được phép bởi security policy và các tham số khác hợp lệ, server/client chọn TLS 1.2. Đây là **thử nghiệm tương thích**, không khuyến khích hạ cấp cấu hình thật.

**`noOverlap=handshake-failed`:** server chỉ cho TLS 1.2 trong khi client chỉ cho TLS 1.3. Client nhận `SSLException` khi handshake; ví dụ in nhãn ổn định thay vì dựa vào nguyên văn message có thể thay đổi giữa JDK/provider.

Đoạn code bật xác minh danh tính bằng `setEndpointIdentificationAlgorithm("HTTPS")`, và truststore không phải một trust-all manager. **Handshake lỗi không phải lý do để bỏ xác thực**.

### 6.5. Giới hạn phạm vi demo

- Đây là **TLS handshake**, không phải HTTP server; không có REST endpoint, status code hay HTTP/2 trong demo.
- Thực hành chỉ xét version overlap; không kiểm thử mTLS, certificate rollover, nhiều server node, TLS termination hay PSK resumption.
- Nếu JDK/provider không hỗ trợ TLS 1.3 hoặc policy đã vô hiệu hóa TLS 1.2, test cần được điều chỉnh theo yêu cầu bảo mật; không được bật lại giao thức yếu tùy tiện.
- Self-signed key chỉ dùng cục bộ; phải đóng và xóa tài liệu test an toàn sau khi dùng.
- Handshake/timing phụ thuộc CPU và runtime; ví dụ không đặt một SLA cụ thể cho thời gian TLS.

## 7. TLS 1.3 khác TLS 1.2 về mật mã và key exchange

TLS 1.3 không phải chỉ là tên phiên bản mới. Nó đơn giản hóa tập cơ chế mật mã và giảm số thông điệp handshake trong trường hợp thường gặp.

| Khía cạnh | TLS 1.3 | TLS 1.2 |
| --- | --- | --- |
| Version negotiation | Extension `supported_versions` | Cơ chế version negotiation tương thích TLS 1.2 |
| Key establishment | (EC)DHE/PSK theo handshake phù hợp; loại bỏ RSA key transport cũ | Nhiều chế độ cipher/key exchange lịch sử, phải chọn an toàn |
| Record protection | AEAD hiện đại, ví dụ AES-GCM và ChaCha20-Poly1305 nếu có hỗ trợ | Có thể dùng AEAD nhưng còn legacy cipher cần tránh |
| Certificate | Xác thực với signature algorithms phù hợp | Chính sách certificate và chữ ký theo TLS 1.2 |
| Handshake confidentiality | Nhiều phần sau `ServerHello` được bảo vệ | Cấu trúc handshake khác |
| Session resumption | Ticket/PSK theo TLS 1.3 | Cơ chế tiếp tục phiên khác |
| 0-RTT early data | Tính năng tùy chọn của giao thức, có rủi ro replay | Không có 0-RTT TLS 1.3 |

**RSA certificate khác RSA key transport.** Trong ví dụ, certificate server chứa RSA public key dùng **xác thực/chữ ký**, nhưng TLS 1.3 **không** sử dụng kiểu RSA key transport cũ. Đừng nhầm thuật toán của certificate với cơ chế tạo shared secret.

Cipher suite TLS 1.3 có tên điển hình:

- `TLS_AES_128_GCM_SHA256`
- `TLS_AES_256_GCM_SHA384`
- `TLS_CHACHA20_POLY1305_SHA256` (nếu provider hỗ trợ)

Không hardcode tất cả bộ mã trên cho mọi JDK rồi cho rằng đều được bật; cần xem provider, enabled cipher suites và `jdk.tls.disabledAlgorithms`.

**0-RTT:** đừng suy rằng Java 11 hoặc mọi provider tự hỗ trợ 0-RTT; đó là khả năng tùy chọn của TLS 1.3 và early data có thể bị replay. Không đưa thao tác không idempotent (tạo đơn, thanh toán, cập nhật dữ liệu) vào early data mà không có bảo vệ chống replay theo thiết kế.

## 8. SNI và ALPN: hai extension khác TLS version

### SNI (Server Name Indication)

SNI cho server biết **hostname client muốn kết nối**, rất hữu ích khi một IP/cổng phục vụ nhiều domain. Server có thể chọn certificate phù hợp. Tuy nhiên:

- **SNI không tự kiểm tra certificate**: client vẫn phải xác thực chain và SAN/hostname.
- Tên trong SNI có thể khác với tên socket nếu code cấu hình sai; không dùng SNI để lách hostname check.
- Với Java raw TLS, có thể cấu hình server name qua `SSLParameters.setServerNames(...)` khi thật sự cần; trong HTTP Client thông thường, dùng URI HTTPS đúng đích là cơ sở quan trọng.

### ALPN (Application-Layer Protocol Negotiation)

ALPN dùng để chọn giao thức **tầng ứng dụng** như:

- `h2` — HTTP/2 qua TLS;
- `http/1.1` — HTTP/1.1;
- tên ứng dụng khác do hai đầu có hỗ trợ thực sự.

Java 11 JSSE có API:

```java
// Đoạn minh họa cho SSLSocket socket chưa handshake.
SSLParameters parameters = socket.getSSLParameters();
parameters.setApplicationProtocols(
        new String[] {"h2", "http/1.1"});
socket.setSSLParameters(parameters);

socket.startHandshake();
String alpn = socket.getApplicationProtocol();
```

Đây **không phải chương trình độc lập**: cần `SSLSocket socket` có SSLContext/trust/certificate đúng, server hỗ trợ ALPN tương ứng và phải xử lý lỗi. Giá trị `alpn` có thể là chuỗi rỗng nếu không chọn được giao thức ứng dụng; nó **không phải** `TLSv1.3`. Chỉ khai báo `h2` mà không triển khai HTTP/2 không biến một raw TLS server thành HTTP/2 server.

Một kết nối có thể là **TLS 1.3 + HTTP/1.1** hoặc **TLS 1.3 + HTTP/2**; TLS version và HTTP version là hai khái niệm độc lập.

### Java `HttpClient` kiểm tra phiên bản của cả hai tầng

```java
// Đoạn minh họa với API HTTPS thật, không phải demo cục bộ.
HttpClient client = HttpClient.newBuilder()
        .version(HttpClient.Version.HTTP_2)
        .build();
HttpRequest request = HttpRequest.newBuilder(
        URI.create("https://api.example.com/"))
        .GET()
        .build();
HttpResponse<Void> response = client.send(
        request, HttpResponse.BodyHandlers.discarding());

System.out.println(response.version());
response.sslSession().ifPresent(session ->
        System.out.println(session.getProtocol()));
```

Cần các import `URI`, `HttpClient`, `HttpRequest`, `HttpResponse`, cùng xử lý `IOException`/`InterruptedException`. `response.version()` cho biết **HTTP version thực tế**; `sslSession().getProtocol()` cho biết **TLS version** nếu response có TLS session. `HTTP_2` là lựa chọn **ưu tiên** của client chứ không ép mọi server phải hỗ trợ HTTP/2.

## 9. Cấu hình policy TLS qua JSSE và hệ thống

### Cấp socket/engine

Thiết lập trước handshake:

```java
socket.setEnabledProtocols(
        new String[] {"TLSv1.3", "TLSv1.2"});
```

Đoạn này minh họa trên `SSLSocket socket`. Nếu cấu hình một phiên bản không được provider hỗ trợ, API có thể ném `IllegalArgumentException`. Ngay cả khi API nhận cấu hình, security properties vẫn có thể chặn một version/cipher bị vô hiệu hóa.

### Cấp property khi dùng cấu hình JSSE mặc định

Có thể gặp:

```bash
java -Djdk.tls.client.protocols=TLSv1.3,TLSv1.2 App
java -Djdk.tls.server.protocols=TLSv1.3,TLSv1.2 ServerApp
```

`App`/`ServerApp` là tên lớp minh họa, **không phải tên chương trình chính**. Các property này ảnh hưởng bộ protocol mặc định ở phía client/server khi SSLContext/provider sử dụng cấu hình defaults phù hợp. Nếu code đặt `setEnabledProtocols(...)` rõ ràng, một property mặc định có thể không áp dụng theo ý bạn kỳ vọng.

Đừng nhầm `https.protocols` — chủ yếu dùng cho `HttpsURLConnection`/`URL.openStream()` — với cấu hình chung cho **mọi** stack HTTP, đặc biệt `java.net.http.HttpClient`. Với client HTTP hiện đại, cần dùng `HttpClient.Builder.sslContext(...)`/`sslParameters(...)` đúng nhu cầu, và kiểm chứng phiên bản negotiated trên runtime thực.

### Disabled algorithms và chính sách bảo mật

`jdk.tls.disabledAlgorithms` và các algorithm constraints có thể ngăn những phiên bản/cipher yếu mặc dù lớp JSSE vẫn biết tên của chúng. Đặc biệt TLS 1.0/1.1/SSLv3 không phải lựa chọn phục hồi khi TLS 1.3 bị lỗi.

Không tự sửa `java.security` để bỏ ràng buộc an toàn chỉ vì một đối tác chưa nâng cấp. Ưu tiên nâng cấp endpoint, certificate, provider và TLS termination theo chính sách. Nếu còn cần TLS 1.2, hãy kiểm tra những cipher/key/certificate phù hợp và đo mức sử dụng thực tế.

## 10. Những nguyên nhân thực tế làm handshake thất bại

| Triệu chứng | Nguyên nhân có thể | Cách xử lý |
| --- | --- | --- |
| `SSLHandshakeException: protocol_version` | Không có phiên bản dùng chung | So enabled version cả hai phía và security policy |
| `handshake_failure` | Version, cipher, signature, named group hoặc certificate không tương thích | Đọc log JSSE và tách từng giai đoạn |
| `PKIX path building failed` | Truststore/certificate chain không hợp lệ | Kiểm tra CA và chain; không tắt trust verification |
| `No subject alternative names matching...` | Certificate SAN không khớp IP/host | Cấp chứng chỉ đúng tên; giữ hostname check |
| `No available authentication scheme` | Server cert/private key không phù hợp TLS 1.3, ví dụ chỉ có DSA | Dùng cert/key và signature schemes hiện hành |
| `no cipher suites in common` | Cipher bị disable hoặc policy khác nhau | Kiểm tra suite khả dụng ở cả hai |
| SNI sai | Server chọn virtual host/certificate khác | Kiểm tra URI/hostname, SNI, TLS terminator |
| ALPN negotiation lỗi | Giao thức ứng dụng không tương thích | Kiểm tra HTTP/2 vs HTTP/1.1 độc lập TLS version |
| `ClientHello.legacy_version` là TLS 1.2 | Không hẳn là lỗi; TLS 1.3 sử dụng trường legacy | Xem `supported_versions` và SSLSession |
| Có lúc TLS 1.2, có lúc TLS 1.3 | Các endpoint/proxy/node khác cấu hình | Đo từng hop, ghi negotiated version và backend |

Thông điệp quan trọng: **ngoại lệ handshake không nói ngay nguyên nhân**. Đặc biệt, kết nối thất bại không đồng nghĩa “JDK không hỗ trợ TLS 1.3” hay “cần trust-all”.

## 11. Debug và quan sát giao thức thực tế

Bật JSSE handshake log:

```bash
java -Djavax.net.debug=ssl,handshake TlsNegotiationDemo server.p12 trust.p12
```

Đây là lệnh chỉ áp dụng sau khi đã tạo hai keystore và biên dịch. Log chi tiết thay đổi theo JDK/provider; **không dùng nó làm stdout ổn định** của bài.

Quy trình đọc log:

1. Xem `ClientHello.supported_versions`, đừng chỉ đọc `legacy_version`.
2. Xem `ServerHello.supported_versions` và cipher được chọn.
3. Kiểm tra `key_share`, `supported_groups`, signature algorithms và chứng chỉ.
4. Khi thất bại, đọc **TLS alert**/nguyên nhân ở cả client và server.
5. Sau thành công, xem `SSLSession.getProtocol()`/`getCipherSuite()`.
6. Với HTTPS, kiểm tra thêm `response.version()`, ALPN, hostname/certificate và proxy.
7. Nếu qua load balancer/CDN, xác nhận từng chặng TLS, không suy ra toàn bộ đường đi từ client.

TLS debug có thể hiển thị hostname, certificate chain và metadata kết nối; không thu private key, secret hay log chưa được ẩn thông tin nhạy cảm vào ticket công khai. Với production, chỉ bật log chi tiết trong điều kiện kiểm soát phù hợp.

## 12. Sai lầm phổ biến và cách phòng tránh

| Sai lầm | Hậu quả | Cách sửa |
| --- | --- | --- |
| `getSupportedProtocols()` có TLSv1.3 nên kết luận đang dùng TLS 1.3 | Supported ≠ negotiated | Dùng `SSLSession.getProtocol()` sau handshake |
| Thấy legacy_version TLS 1.2 rồi coi là downgrade | Hiểu sai TLS 1.3 | Đọc extension `supported_versions` |
| Chỉ bật TLS 1.3 ở client mà không xét server | Không có phiên bản chung | Đồng bộ policy hai phía, cập nhật endpoint |
| Thiết lập `setEnabledProtocols` sau handshake | Không thay version đã chọn | Cấu hình trước `startHandshake()` |
| Đọc mỗi version mà bỏ qua cipher/certificate | Có version chung nhưng handshake vẫn fail | Kiểm tra đầy đủ trust, key, signature, named group |
| Dùng TrustManager chấp nhận mọi chứng chỉ | Tạo lỗ hổng MITM | Truststore hợp lệ + endpoint identification |
| Tắt hostname verification vì lỗi SAN | Chấp nhận server không đúng danh tính | Sửa URI và certificate SAN |
| Nhầm SNI là xác thực | Chỉ chọn certificate/virtual host, chưa chứng minh nó đáng tin | Xác minh chain và hostname |
| Nghĩ TLS 1.3 tự động dùng HTTP/2 | HTTP/2 phụ thuộc ALPN/app implementation | Đọc HTTP version và ALPN riêng |
| Cho rằng TLS 1.3 tự động bật 0-RTT cho mọi request | 0-RTT tùy chọn, có replay risk | Không dùng early data cho tác vụ có side effect |
| Hạ xuống TLS 1.0/1.1 để sửa handshake | Mất chính sách bảo mật hiện hành | Nâng cấp đối tác/terminator, dùng policy chuẩn |
| Đọc một kết nối rồi kết luận cho mọi node | Proxy/load balancer có thể khác | Kiểm tra theo đích/node/hop |
| Dùng certificate demo localhost trong production | Không đáp ứng PKI/lifecycle thực | Quản lý CA, SAN, secret và rotation đúng |
| Nhầm cipher suite TLS 1.3 với TLS 1.2 | Chọn thuật toán không hợp lệ | Kiểm tra capability/constraint của provider |

## 13. Bài tập và câu hỏi ôn tập

**Bài 1 — Phiên bản chung.** Client cho phép `TLSv1.3` và `TLSv1.2`, server chỉ cho phép `TLSv1.2`. Nếu các điều kiện khác hợp lệ, kết quả? **Có thể chọn TLS 1.2**. Cần chính sách cho phép tương thích này.

**Bài 2 — Không giao nhau.** Client chỉ TLS 1.3, server chỉ TLS 1.2. Có thể tiếp tục gửi HTTP request qua HTTPS không? **Không**, handshake chưa thành công.

**Bài 3 — Supported/negotiated.** `getSupportedProtocols()` liệt kê TLS 1.3, nhưng `SSLSession.getProtocol()` là TLS 1.2. Điều đó có mâu thuẫn không? **Không**: implementation hỗ trợ nhưng kết nối này đã chọn 1.2.

**Bài 4 — Legacy field.** ClientHello.legacy_version mang TLS 1.2 trong khi supported_versions có TLS 1.3 và server chọn TLS 1.3. Phiên bản thực tế? **TLS 1.3**.

**Bài 5 — Chứng chỉ.** Client tin CA, nhưng server certificate SAN chỉ ghi `api.example.com` trong khi URI là `other.example.net`. Có được tắt hostname verification không? **Không**, phải sửa chứng chỉ hoặc tên đích.

**Bài 6 — Cipher.** Cùng TLS 1.3 nhưng hai bên không có nhóm khóa/chữ ký/cipher hợp lệ chung. Có thể kết nối không? **Không**, version overlap là điều kiện cần, chưa đủ.

**Bài 7 — ALPN.** `SSLSession.getProtocol() = TLSv1.3` và `HttpResponse.version() = HTTP_1_1`. Có sai không? **Không**, hai tầng giao thức khác nhau.

**Bài 8 — Tự chạy.** Trong demo chính, đổi case thứ ba để cả hai đầu chỉ cho phép `TLSv1.3`, đặt `expectSuccess=true`. Dự kiến dòng cuối thành `noOverlap=TLSv1.3` (nên đổi tên nhãn cho phù hợp), nếu trust/algorithm cho phép.

**Bài 9 — Downgrade.** Đối tác chỉ hỗ trợ TLS 1.0. Giải pháp có nên là tắt `jdk.tls.disabledAlgorithms` không? **Không**; đề xuất nâng cấp đầu cuối theo security policy.

**Bài 10 — Tiêu chuẩn hiện hành.** Java 11 JSSE ban đầu được phát hành theo RFC 8446. Từ tháng 7/2026 đặc tả TLS 1.3 nào thay nó? **RFC 9846**, giữ version 1.3 và tương thích ngược.

### Checklist triển khai

1. Đã xác định **TLS termination hop** muốn đo?
2. Cả client và server đã bật **version hợp lệ** tương ứng?
3. `SSLSession.getProtocol()` đã xác nhận version thực tế?
4. Cipher suite, nhóm khóa và signature algorithms được phép?
5. Server certificate/CA/truststore và SAN khớp hostname/IP đích?
6. Có giữ hostname verification và không dùng trust-all?
7. SNI, ALPN và HTTP version được kiểm tra **riêng** với TLS version?
8. Nếu vẫn cho TLS 1.2, có yêu cầu tương thích được duyệt và cipher an toàn?
9. Không bật TLS 1.0/1.1/SSLv3 hoặc xóa disabledAlgorithms khi gặp lỗi?
10. Có logging/metrics lỗi TLS theo endpoint, mask secret?
11. Có test với đúng JDK/provider/cấu hình server/proxy?
12. Có tham khảo **RFC 9846** là đặc tả TLS 1.3 hiện hành?
