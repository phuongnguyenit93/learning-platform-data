# Phân tích TLS 1.3 handshake mà không bỏ kiểm tra chứng chỉ (Java 11)

Khi kết nối HTTPS, WebSocket bảo mật (`wss://`), gRPC qua TLS hoặc một socket TLS, lỗi handshake thường bị nhầm thành “mạng lỗi” chung. Một số tình huống rất khác nhau có thể cho ra cùng loại `SSLHandshakeException`: bên kia không hỗ trợ phiên bản TLS, chứng chỉ không được tin cậy, tên miền không khớp Subject Alternative Name (SAN), chứng chỉ hết hạn hoặc hai bên không thống nhất được thuật toán xác thực.

**Cách chẩn đoán đúng không phải là tắt kiểm tra chứng chỉ.** Java 11 đã có JSSE (Java Secure Socket Extension) hỗ trợ **TLS 1.3**. Bạn có thể bật log handshake, xem phiên bản/cipher suite được chọn, phân tích chain và truststore, kiểm tra hostname, rồi sửa đúng certificate/CA/server configuration mà **vẫn duy trì xác thực peer**.

> Nguyên tắc an toàn: **Mã hóa TLS và xác thực danh tính server là hai mục tiêu liên quan nhưng không đồng nhất.** Một kết nối được mã hóa mà tin mọi chứng chỉ hoặc chấp nhận mọi hostname **không chứng minh đang nói chuyện với server đúng** và có thể bị tấn công man-in-the-middle.

Đây là bài thuộc nhóm **TLS 1.3** của Java 11. Nội dung chỉ sử dụng kiến thức và API vẫn còn giá trị trên các JDK hiện đại. Nên thực hành bằng **JDK được nhà cung cấp cập nhật và hỗ trợ**, đồng thời dùng `javac --release 11` để bảo đảm source code tương thích API Java 11.

## 1. Mục tiêu học tập

Sau bài này, bạn có thể:

1. Mô tả thứ tự các message chính trong **full TLS 1.3 handshake**: `ClientHello`, `ServerHello`, `EncryptedExtensions`, `Certificate`, `CertificateVerify`, `Finished`.
2. Phân biệt **đàm phán TLS protocol/cipher** với **xác thực certificate chain** và **hostname verification**.
3. Bật `-Djavax.net.debug=ssl,handshake,trustmanager` và đọc log một cách có hệ thống.
4. Giải thích vì sao ServerHello TLS 1.3 có trường `legacy_version` mang giá trị tương thích TLS 1.2, còn `supported_versions` mới chỉ ra TLS 1.3.
5. Dùng `SSLContext`, `TrustManagerFactory`, `SSLSocket` và `SSLParameters.setEndpointIdentificationAlgorithm("HTTPS")` trong một ví dụ JSSE.
6. Kiểm tra ba kịch bản bằng code chạy thực tế: **đúng CA và hostname**, **CA sai/không tin cậy**, **hostname sai dù CA đã tin cậy**.
7. Biết sử dụng `keytool` để tạo tài sản thử nghiệm PKCS#12, xem SAN và chain, nhưng không đưa private key/truststore lab vào production.
8. Phân loại lỗi certificate, trust path, hostname, TLS version, cipher suite, clock và mTLS để chọn biện pháp khắc phục.
9. Chẩn đoán HTTPS qua `HttpClient` mà không thay `X509TrustManager` bằng trust-all hoặc bật chế độ tắt kiểm tra tên host.
10. Hiểu giới hạn của log JSSE, TLS resumption và các cơ chế certificate revocation.

## 2. TLS handshake bảo vệ những gì?

TLS 1.3 đảm nhiệm ba chức năng chính:

- **Bí mật truyền tải:** mã hóa application data sau khi bắt tay và tạo khóa phù hợp.
- **Toàn vẹn:** phát hiện dữ liệu bị sửa đổi trong quá trình truyền.
- **Xác thực peer theo chính sách:** trong HTTPS, client thường xác thực **server certificate** và **tên máy đích**; trong mutual TLS (mTLS), server còn yêu cầu chứng chỉ của client.

Kết nối TCP được tạo thành công **không** chứng minh handshake TLS đã thành công. Handshake TLS xong **không** đồng nghĩa HTTP request có status 2xx. Server certificate hợp lệ cũng **không** bảo đảm ứng dụng backend đang khỏe.

```text
DNS / chọn IP
     |
     v
TCP connect (hoặc transport tương ứng)
     |
     v
TLS 1.3 ClientHello / ServerHello / ...
     |
     +--> Kiểm tra certificate chain + hostname
     |       |
     |       +--> Thất bại: từ chối handshake
     |
     v
TLS session đã xác thực thành công
     |
     v
HTTP request / response (hoặc protocol khác)
     |
     v
Kiểm tra HTTP status và trạng thái nghiệp vụ
```

Khi gỡ lỗi, phải xác định lỗi xảy ra **ở tầng nào**. Đừng biến lỗi certificate thành một lỗi HTTP giả: chưa hoàn thành handshake thì thường **chưa có HTTP response** để xem `statusCode()`.

## 3. Sơ đồ full TLS 1.3 handshake có chứng chỉ server

Một trường hợp điển hình với server authentication qua certificate:

```text
CLIENT                                             SERVER
  |                                                  |
  | --- ClientHello --------------------------------> |
  |      supported_versions: TLSv1.3                  |
  |      key_share, signature_algorithms, SNI ...     |
  |                                                  |
  | <----------------------------------- ServerHello  |
  |                  chọn TLSv1.3, cipher, key_share  |
  |                                                  |
  |   Từ sau ServerHello, nhiều handshake message     |
  |   đã được bảo vệ bằng handshake traffic keys.     |
  |                                                  |
  | <--------------------------- EncryptedExtensions  |
  | <---------------------------------- Certificate  |
  | <----------------------------- CertificateVerify  |
  | <------------------------------------- Finished  |
  |                                                  |
  |  Kiểm tra chain + hostname + các chữ ký/Finished  |
  |                                                  |
  | --- Finished -----------------------------------> |
  |                                                  |
  | <==== Application Data (TLS records đã mã hóa) ===>|
```

Các message có ý nghĩa:

| Bước | Nội dung cần tìm | Ý nghĩa |
| --- | --- | --- |
| `ClientHello` | `supported_versions`, `key_share`, `signature_algorithms`, có thể có SNI/ALPN | Client công bố những khả năng hỗ trợ |
| `ServerHello` | Phiên bản chọn trong `supported_versions`, cipher suite, `key_share` | Hai bên chốt các thông số mật mã cơ bản |
| `EncryptedExtensions` | Extension được server xác nhận, có thể gồm ALPN | Các tham số không gửi công khai như ServerHello |
| `Certificate` | Chứng chỉ server và chain gửi kèm | Dữ liệu đầu vào cho xác thực danh tính |
| `CertificateVerify` | Chữ ký của server trên transcript handshake | Chứng minh nắm private key tương ứng chứng chỉ |
| `Finished` | Xác thực transcript handshake | Xác nhận integrity và key schedule |
| Application data | Dữ liệu HTTP hoặc giao thức cấp trên | Chỉ xử lý khi handshake cần thiết đã hoàn tất |

**Không phải mọi handshake TLS 1.3 đều giống sơ đồ.** Có thể có `HelloRetryRequest` nếu client/server cần thống nhất lại key share, `CertificateRequest` nếu server yêu cầu mTLS, hoặc **session resumption qua PSK**, trong đó full certificate authentication flow không lặp lại y hệt. Vì thế, “không thấy Certificate trong một log resumed session” **không tự chứng minh** server đã bỏ xác thực.

### Tại sao log có `TLSv1.2` trong một handshake TLS 1.3?

TLS 1.3 giữ một số trường legacy để tương thích với thiết bị và phần mềm trung gian. Đặc biệt:

```text
ServerHello.legacy_version    = 0x0303 (TLS 1.2)
ServerHello.supported_versions = TLS 1.3
SSLSession.getProtocol()      = TLSv1.3  (khi đã chọn TLS 1.3)
```

Không kết luận “bị downgrade xuống TLS 1.2” chỉ vì thấy `legacy_version=TLSv1.2` trong cấu trúc `ServerHello`. Hãy xem giá trị được chọn trong `supported_versions` và `SSLSession.getProtocol()` sau handshake thành công.

### Vì sao Wireshark và log JSSE nhìn khác nhau?

TLS 1.3 mã hóa nhiều handshake message **sau ServerHello**. Một công cụ quan sát gói tin từ ngoài thường chỉ thấy TLS records được mã hóa, không đọc được `Certificate` hay `Finished` dưới dạng plaintext khi không có khóa giải mã hợp lệ. JSSE có thể ghi **thông tin handshake ở bên trong tiến trình** để phục vụ chẩn đoán.

**Không cần và không nên tắt certificate verification để “nhìn được” TLS handshake.** Hãy dùng trace JSSE trong môi trường thử nghiệm, hoặc một bộ công cụ phân tích có quyền truy cập dữ liệu phù hợp, tuân theo chính sách bảo mật của dự án.

## 4. Xác thực chứng chỉ gồm nhiều lớp

Để xác thực server đúng, client thường cần:

1. **Chain/path validation:** chứng chỉ server được liên kết tới một trust anchor (CA) mà client đã chấp thuận, với chữ ký và ràng buộc chính sách phù hợp.
2. **Thời hạn hiệu lực:** chứng chỉ hợp lệ tại thời điểm kiểm tra, không hết hạn hoặc chưa có hiệu lực.
3. **Mục đích và thuật toán:** các ràng buộc như key usage, extended key usage, signature algorithm, key size/algorithm constraints phải phù hợp.
4. **Hostname/endpoint identification:** tên host được kết nối phải khớp danh tính hợp lệ trong chứng chỉ, thông thường là SAN DNS/IP.
5. **Revocation theo chính sách:** nếu môi trường yêu cầu OCSP/CRL/stapling, phải cấu hình và giám sát phù hợp. Không giả định mọi cơ chế thu hồi chứng chỉ đều được bật mặc định cho mọi kiểu JSSE connection.
6. **mTLS (nếu có):** server cũng kiểm tra chứng chỉ client và quyền truy cập liên quan; không dùng truststore phía client để giải quyết nhầm lỗi certificate phía server.

**Tin CA không đồng nghĩa đúng hostname.** Một server có chứng chỉ được ký bởi CA tin cậy nhưng chỉ hợp lệ cho `service-a.example` không thể tự động dùng làm `service-b.example`.

**Đúng hostname không đồng nghĩa có trust path.** Một certificate ghi `DNS:api.example` nhưng tự ký bởi người lạ cũng không đủ để kết nối được chấp thuận.

### Subject Alternative Name và Common Name

Với xác minh danh tính HTTPS hiện đại, hãy cấu hình **Subject Alternative Name (SAN)** chính xác:

- `DNS:api.example.com` cho tên miền.
- `IP:192.0.2.10` nếu kết nối và xác minh bằng địa chỉ IP tương ứng (ví dụ địa chỉ dành cho tài liệu).
- Chứng chỉ chỉ có `DNS:localhost` **không tự xác thực** kết nối qua `127.0.0.1`.

Không dựa vào **Common Name (CN)** như cách thay thế SAN trong chứng chỉ mới. Khi tạo chứng chỉ cho hệ thống thật, dùng SAN phù hợp với tên endpoint và CA/certificate lifecycle được tổ chức quản lý.

### Truststore và keystore khác gì?

| Thành phần | Đặc điểm | Ví dụ |
| --- | --- | --- |
| **Keystore phía server** | Chứa private key và certificate chain server dùng để trình danh tính | `server.p12` |
| **Truststore phía client** | Chứa những trust anchor/certificate được phép dùng khi xác minh server | `trusted.p12` |
| Keystore phía client trong mTLS | Chứa private key và certificate của client | `client-identity.p12` |
| Truststore phía server trong mTLS | Chứa CA/certificate được phép xác minh client | Cấu hình trên server |

`KeyManagerFactory` đọc danh tính cục bộ (private key + certificate). `TrustManagerFactory` tạo các trust manager kiểm tra peer. Nếu tắt/đổi nhầm trust manager hoặc cài trust-all, kết nối không còn xác thực server đáng tin cậy.

## 5. Bật JSSE handshake debug mà không nới lỏng bảo mật

Với SunJSSE provider, dùng Java system property:

```sh
java -Djavax.net.debug=ssl,handshake,trustmanager MyApp
```

`MyApp` là **tên lớp ứng dụng đang có**, không phải chương trình hoàn chỉnh. Có thể thử `-Djavax.net.debug=help` để xem các tùy chọn debug của provider/JDK đang sử dụng; lựa chọn `help` có thể khiến chương trình kết thúc sau khi in hướng dẫn.

Một số nhóm log:

| Tùy chọn | Thông tin nhận được |
| --- | --- |
| `ssl` | Log chẩn đoán chung của JSSE |
| `handshake` | Những TLS handshake messages được tạo/tiêu thụ |
| `trustmanager` | Trust manager và certificate/truststore được xét |
| `keymanager` | Lựa chọn private key/certificate phía local khi cần |
| `record` | Chẩn đoán record layer |
| `session` / `sessioncache` | TLS session và cache/resumption |
| `data` / `packet` / `plaintext` / `keygen` | Thông tin sâu hơn, có thể làm lộ dữ liệu nhạy cảm; tránh bật trên production |

Định dạng log `javax.net.debug` **không phải một API ổn định được chuẩn hóa**. Oracle nêu rõ nội dung log có thể thay đổi giữa JDK release và giữa security provider. Hãy đọc chúng như chẩn đoán, **không viết parser nghiệp vụ dựa trên từng dòng log cố định**.

### Trình tự đọc log để khoanh vùng nhanh

1. Tìm **`ClientHello`**: client đề nghị những phiên bản TLS nào? Có `supported_versions` phù hợp không?
2. Tìm **`ServerHello`**: server chọn phiên bản/cipher nào? Có `HelloRetryRequest` không?
3. Tìm **`Certificate`** và log trust manager: server gửi những certificate nào? Chain có issuer phù hợp không?
4. Kiểm tra thông báo **PKIX/path validation**, hạn chứng chỉ, thuật toán không được cho phép và **hostname/IP mismatch**.
5. Nếu certificate validation thành công, quan sát `CertificateVerify` và `Finished` để xem handshake còn lỗi gì.
6. Chỉ sau khi handshake hoàn tất, mới xem HTTP status/response body hoặc lỗi ứng dụng.

Không phải log nào cũng có mọi message (ví dụ resumed session, HelloRetryRequest, mTLS). Không thay đổi certificate/truststore chỉ vì thiếu một dòng log mẫu.

### Thận trọng với log TLS

Log TLS có thể chứa hostname, chain chứng chỉ, SNI, metadata kết nối và thông tin nhạy cảm tùy tùy chọn. Trong môi trường xử lý dữ liệu thật:

- Chỉ bật trong **phạm vi được phép**, trên môi trường thử nghiệm hoặc theo quy trình sự cố.
- Không dùng `javax.net.debug=all` hoặc bật `plaintext/keygen` bừa bãi ở production.
- Không tải log chứa bí mật lên dịch vụ bên ngoài khi chưa kiểm tra và được phép.
- Hạn chế quyền đọc file log, thời gian lưu, và xóa log sau khi hoàn thành chẩn đoán.
- Không đưa private key hoặc passphrase vào log/chat/ticket.

## 6. Vì sao raw `SSLSocket` phải bật hostname verification?

Một lỗi rất phổ biến là dùng `SSLSocket` và `TrustManagerFactory` có truststore hợp lệ, nhưng **quên bật endpoint identification**. Với raw socket, đừng mặc định rằng certificate chain và hostname luôn được xác minh y như khi `HttpClient` gọi HTTPS.

Cấu hình đúng trong code client:

```java
SSLSocket socket = (SSLSocket)
        sslContext.getSocketFactory()
                .createSocket("api.example.com", 443);

SSLParameters parameters = socket.getSSLParameters();
parameters.setEndpointIdentificationAlgorithm("HTTPS");
socket.setSSLParameters(parameters);

socket.startHandshake();
```

Đây là **snippet**, không phải chương trình độc lập; `sslContext` là `SSLContext` được khởi tạo bằng trust manager đáng tin cậy, và ứng dụng phải xử lý ngoại lệ/đóng socket trong `try-with-resources`. Tên host chỉ là ví dụ, không thực hiện request ở đoạn mã này.

**Quan trọng:**

- `"HTTPS"` là tên endpoint identification algorithm tiêu chuẩn do JSSE hỗ trợ.
- `setEndpointIdentificationAlgorithm("HTTPS")` yêu cầu đối chiếu identity của peer trong handshake.
- `null` hoặc chuỗi rỗng **không** phải lựa chọn phù hợp để thực hiện kiểm tra hostname.
- Khi dùng HTTPS qua `java.net.http.HttpClient` với cấu hình mặc định, Java thực hiện xác thực server/host theo cơ chế chuẩn; không thay thế default trust manager bằng một callback luôn chấp thuận.

**Khác biệt các thành phần:** `HttpClient` cho HTTPS và raw `SSLSocket` không nên bị xem như cùng một layer có cấu hình endpoint identification giống hệt. Nếu dùng socket trực tiếp, hãy bật rõ ràng `"HTTPS"`.

## 7. Phòng lab hoàn chỉnh: TLS 1.3 thực tế, chứng chỉ đúng/sai đều được kiểm tra

Phần này tạo một TLS server trong máy, một truststore **chứa đúng certificate của server lab**, một truststore **chỉ tin certificate khác**, rồi chạy ba lần handshake. **Không có ví dụ nào bỏ kiểm tra certificate.**

- Case A: kết nối `localhost`, truststore tin certificate server, SAN có `DNS:localhost` → **thành công**.
- Case B: kết nối `localhost`, truststore chứa certificate không liên quan → **bị từ chối** do trust path.
- Case C: kết nối `127.0.0.1`, truststore tin certificate server nhưng SAN chỉ chứa `DNS:localhost` → **bị từ chối** do hostname/IP mismatch.

Lab dùng `PKCS12`, `keytool`, `KeyManagerFactory`, `TrustManagerFactory`, `SSLContext`, `SSLSocket` và `SSLServerSocket` thuộc Java 11. Certificate self-signed **chỉ được đưa vào truststore của lab để mô phỏng một trust anchor có chủ đích**. Điều này khác hoàn toàn với trust-all: lab vẫn từ chối certificate không có trong truststore và từ chối tên máy không khớp.

### 7.1. Chuẩn bị khóa và truststore (chỉ cho lab)

Thực hiện trong **một thư mục thực hành mới, trống**, không dùng thư mục chứa khóa production. Các lệnh sau là những lệnh đơn dòng dùng `keytool` trên PATH:

```sh
keytool -genkeypair -alias lab -keyalg RSA -keysize 2048 -sigalg SHA256withRSA -validity 30 -dname "CN=localhost" -ext "SAN=dns:localhost" -storetype PKCS12 -keystore server.p12 -storepass changeit -keypass changeit -noprompt

keytool -exportcert -alias lab -keystore server.p12 -storepass changeit -file server.cer -rfc

keytool -importcert -alias lab -file server.cer -keystore trusted.p12 -storetype PKCS12 -storepass changeit -noprompt

keytool -genkeypair -alias other -keyalg RSA -keysize 2048 -sigalg SHA256withRSA -validity 30 -dname "CN=other.example" -ext "SAN=dns:other.example" -storetype PKCS12 -keystore unrelated.p12 -storepass changeit -keypass changeit -noprompt

keytool -exportcert -alias other -keystore unrelated.p12 -storepass changeit -file unrelated.cer -rfc

keytool -importcert -alias other -file unrelated.cer -keystore untrusted.p12 -storetype PKCS12 -storepass changeit -noprompt
```

Kết quả tạo các tệp:

| Tệp | Nội dung | Vai trò |
| --- | --- | --- |
| `server.p12` | RSA private key + self-signed cert có `SAN=DNS:localhost` | Server nhận kết nối TLS |
| `server.cer` | Public certificate của server lab | Dùng để import truststore hợp lệ |
| `trusted.p12` | Truststore chỉ tin cert server lab | Client case A và C |
| `unrelated.p12` | Private key + cert của `other.example` | Chỉ để tạo CA/cert không liên quan |
| `unrelated.cer` | Public certificate không liên quan | Dùng tạo truststore case B |
| `untrusted.p12` | Truststore tin certificate không liên quan | Client case B |

**Mật khẩu `changeit` chỉ là mật khẩu công khai của bài lab**, không được dùng cho khóa production. Việc ghi password trực tiếp trên command line có thể để lộ trong lịch sử shell/process list; ở môi trường thật dùng cơ chế quản lý secret phù hợp, không commit keystore/private key. File `server.p12` có private key; không upload hoặc chia sẻ nó.

Có thể kiểm tra certificate và SAN trước khi chạy:

```sh
keytool -list -v -keystore server.p12 -storetype PKCS12 -storepass changeit
keytool -list -v -keystore trusted.p12 -storetype PKCS12 -storepass changeit
```

Hai lệnh chỉ kiểm tra nội dung tài liệu thử nghiệm. Khi nhìn thấy `SubjectAlternativeName` chứa `DNSName: localhost`, nghĩa là cert lab hợp lệ cho tên `localhost`, nhưng **không đủ cho `127.0.0.1`**.

### 7.2. Chương trình Java 11 độc lập

Tạo file **`Tls13HandshakeLab.java`** với toàn bộ nội dung:

```java
import java.io.IOException;
import java.net.InetAddress;
import java.nio.file.Path;
import java.security.KeyStore;
import java.security.SecureRandom;
import java.security.cert.Certificate;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.concurrent.TimeUnit;
import javax.net.ssl.KeyManagerFactory;
import javax.net.ssl.SSLContext;
import javax.net.ssl.SSLHandshakeException;
import javax.net.ssl.SSLParameters;
import javax.net.ssl.SSLServerSocket;
import javax.net.ssl.SSLSocket;
import javax.net.ssl.SSLSession;
import javax.net.ssl.TrustManagerFactory;

public class Tls13HandshakeLab {
    private static final char[] PASSWORD = "changeit".toCharArray();

    private static KeyStore load(Path file) throws Exception {
        KeyStore store = KeyStore.getInstance("PKCS12");
        try (java.io.InputStream in =
                     java.nio.file.Files.newInputStream(file)) {
            store.load(in, PASSWORD);
        }
        return store;
    }

    private static SSLContext serverContext(Path keyStore)
            throws Exception {
        KeyManagerFactory keys = KeyManagerFactory.getInstance(
                KeyManagerFactory.getDefaultAlgorithm());
        keys.init(load(keyStore), PASSWORD);
        SSLContext context = SSLContext.getInstance("TLSv1.3");
        context.init(keys.getKeyManagers(), null, new SecureRandom());
        return context;
    }

    private static SSLContext clientContext(Path trustStore)
            throws Exception {
        TrustManagerFactory trust = TrustManagerFactory.getInstance(
                TrustManagerFactory.getDefaultAlgorithm());
        trust.init(load(trustStore));
        SSLContext context = SSLContext.getInstance("TLSv1.3");
        context.init(null, trust.getTrustManagers(), new SecureRandom());
        return context;
    }

    private static void connect(
            SSLContext context, String host, int port,
            String label, boolean expectSuccess) throws Exception {
        try (SSLSocket socket = (SSLSocket)
                context.getSocketFactory().createSocket(host, port)) {
            socket.setEnabledProtocols(new String[] {"TLSv1.3"});
            socket.setSoTimeout(5000);
            SSLParameters parameters = socket.getSSLParameters();
            parameters.setEndpointIdentificationAlgorithm("HTTPS");
            socket.setSSLParameters(parameters);
            socket.startHandshake();

            SSLSession session = socket.getSession();
            int value = socket.getInputStream().read();
            if (!expectSuccess) {
                throw new AssertionError(
                        "Invalid certificate was unexpectedly trusted");
            }
            if (value != 42
                    || !"TLSv1.3".equals(session.getProtocol())
                    || session.getPeerCertificates().length == 0) {
                throw new AssertionError("Successful handshake mismatch");
            }
            System.out.println(label + ": verified; protocol="
                    + session.getProtocol() + "; peerCerts="
                    + session.getPeerCertificates().length);
        } catch (SSLHandshakeException rejected) {
            if (expectSuccess) {
                throw rejected;
            }
            System.out.println(label + ": rejected by certificate checks");
        }
    }

    public static void main(String[] args) throws Exception {
        if (args.length != 3) {
            throw new IllegalArgumentException(
                    "Usage: java Tls13HandshakeLab "
                    + "server.p12 trusted.p12 untrusted.p12");
        }

        SSLContext serverContext =
                serverContext(Path.of(args[0]));
        SSLContext trusted =
                clientContext(Path.of(args[1]));
        SSLContext untrusted =
                clientContext(Path.of(args[2]));
        InetAddress loopback = InetAddress.getByName("127.0.0.1");

        try (SSLServerSocket server = (SSLServerSocket)
                serverContext.getServerSocketFactory()
                        .createServerSocket(0, 5, loopback)) {
            server.setEnabledProtocols(new String[] {"TLSv1.3"});
            server.setSoTimeout(5000);

            ExecutorService executor =
                    Executors.newSingleThreadExecutor();
            try {
                Future<?> serverTask = executor.submit(() -> {
                    for (int i = 0; i < 3; i++) {
                        try (SSLSocket client =
                                (SSLSocket) server.accept()) {
                            client.setSoTimeout(5000);
                            client.startHandshake();
                            client.getOutputStream().write(42);
                            client.getOutputStream().flush();
                        } catch (IOException expectedForRejectedPeers) {
                            // Clients with failed validation abort the TLS handshake.
                        }
                    }
                });

                int port = server.getLocalPort();
                connect(trusted, "localhost", port,
                        "Trusted localhost", true);
                connect(untrusted, "localhost", port,
                        "Untrusted localhost", false);
                connect(trusted, "127.0.0.1", port,
                        "Wrong hostname", false);
                serverTask.get(6, TimeUnit.SECONDS);
                System.out.println("Connections attempted: 3");
            } finally {
                executor.shutdownNow();
            }
        }
    }
}
```

#### Chạy

Đặt file Java cùng thư mục với `server.p12`, `trusted.p12`, `untrusted.p12` đã được tạo:

```sh
javac --release 11 -encoding UTF-8 Tls13HandshakeLab.java
java Tls13HandshakeLab server.p12 trusted.p12 untrusted.p12
```

**Stdout chính xác khi loopback được phép và mọi tài sản lab được tạo đúng:**

```text
Trusted localhost: verified; protocol=TLSv1.3; peerCerts=1
Untrusted localhost: rejected by certificate checks
Wrong hostname: rejected by certificate checks
Connections attempted: 3
```

#### Đọc kết quả

**Case A — Trusted localhost**

- Client dùng `trusted.p12` chứa đúng public certificate server lab.
- Kết nối tới host `localhost`, khớp `DNS:localhost` trong SAN.
- `SSLParameters.setEndpointIdentificationAlgorithm("HTTPS")` bật xác minh hostname.
- `socket.startHandshake()` hoàn thành, `SSLSession.getProtocol()` là `TLSv1.3`.
- `getPeerCertificates()` trả certificate chain của peer; lab có một self-signed cert.
- Client nhận được byte `42`, chứng minh application data chỉ được đọc sau handshake.

**Case B — Untrusted localhost**

- Client dùng `untrusted.p12` chỉ chứa certificate của `other.example`.
- Server trình `CN=localhost` với SAN phù hợp cho hostname, **nhưng không có trust path được chấp nhận**.
- JSSE từ chối handshake bằng `SSLHandshakeException`; **không** xử lý application data.

**Case C — Wrong hostname**

- Client dùng **truststore hợp lệ** `trusted.p12`.
- Nhưng tên mà client xác minh là địa chỉ IP `127.0.0.1`, trong khi cert chỉ có `DNS:localhost`, không có `IP:127.0.0.1`.
- JSSE vẫn từ chối handshake, chứng minh **tin CA/certificate không thể thay thế kiểm tra hostname**.

**Lưu ý về tệp và vòng đời:** `try-with-resources` đóng các socket, `Future.get` chờ luồng server test hoàn tất, `ExecutorService.shutdownNow` dừng executor. Trong demo, server chấp nhận tối đa ba kết nối rồi đóng. Nếu môi trường khóa loopback hoặc JDK không cho phép cấu hình crypto cần thiết, ví dụ có thể ném ngoại lệ; không nên chữa bằng trust-all.

## 8. Những điểm cần hiểu trong code JSSE

### `SSLContext.getInstance("TLSv1.3")`

Lab yêu cầu một SSL context hỗ trợ TLS 1.3. Cùng với `socket.setEnabledProtocols(new String[] {"TLSv1.3"})`, nó đảm bảo thí nghiệm không lặng lẽ rơi sang TLS 1.2. Nếu peer không hỗ trợ TLS 1.3, handshake phải thất bại và bạn cần điều chỉnh **chính sách protocol** theo yêu cầu thực tế thay vì bỏ xác thực.

Ở ứng dụng production, có thể dùng `SSLContext.getInstance("TLS")` và để JDK chọn các TLS version còn được cho phép theo chính sách; nếu cần pin các phiên bản được hỗ trợ, phải xác định bằng configuration/SSLParameters. **Không khuyến khích bật lại TLS 1.0/1.1 hay cipher yếu để “sửa nhanh” handshake**.

### `TrustManagerFactory` thay vì trust-all

Code:

```java
TrustManagerFactory tmf = TrustManagerFactory.getInstance(
        TrustManagerFactory.getDefaultAlgorithm());
tmf.init(trustStore);
SSLContext context = SSLContext.getInstance("TLSv1.3");
context.init(null, tmf.getTrustManagers(), new SecureRandom());
```

Đây là **snippet trong phương thức** có `KeyStore trustStore` hợp lệ và xử lý các checked exception. `TrustManagerFactory` tạo trust manager từ các trust anchors đã được chấp thuận. Không tự viết `X509TrustManager` với `checkServerTrusted(...)` rỗng hoặc hàm luôn trả true — cách đó **bỏ kiểm tra danh tính server**.

### `SSLParameters.setEndpointIdentificationAlgorithm("HTTPS")`

Cấu hình:

```java
SSLParameters p = socket.getSSLParameters();
p.setEndpointIdentificationAlgorithm("HTTPS");
socket.setSSLParameters(p);
socket.startHandshake();
```

Đây cũng là **snippet** trong method đã có `SSLSocket socket`. Điều này buộc JSSE thực hiện kiểm tra endpoint identity phù hợp trong handshake. Đừng xóa dòng này chỉ vì một certificate không khớp IP; hãy sửa **certificate SAN hoặc hostname đích**.

### `SSLSession` hữu ích nhưng không thay thế validation

Sau khi handshake thành công, có thể đọc:

```java
SSLSession session = socket.getSession();
System.out.println(session.getProtocol());
System.out.println(session.getCipherSuite());
System.out.println(session.getPeerPrincipal());
```

Đây là **snippet**, không phải chương trình độc lập. Các giá trị cho biết protocol, cipher và peer identity của session. Nhưng việc `getPeerCertificates()` trả một certificate **không chứng minh server đã được xác thực**, nếu trước đó client cấu hình trust-all hoặc tắt hostname verification. Phải bảo đảm cấu hình xác thực đúng **trước khi handshake**.

## 9. Phân tích handshake của `java.net.http.HttpClient`

Với Java 11 `HttpClient` kết nối tới một HTTPS endpoint hợp lệ, bạn có thể kiểm tra TLS session sau khi nhận response.

Ví dụ `HttpsSessionInspect.java` (chương trình độc lập **cần một HTTPS endpoint thật do bạn được phép truy cập**):

```java
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.time.Duration;
import javax.net.ssl.SSLSession;

public class HttpsSessionInspect {
    public static void main(String[] args) throws Exception {
        if (args.length != 1) {
            throw new IllegalArgumentException(
                    "Provide one https:// URL");
        }

        URI uri = URI.create(args[0]);
        if (!"https".equalsIgnoreCase(uri.getScheme())) {
            throw new IllegalArgumentException("HTTPS is required");
        }

        HttpClient client = HttpClient.newBuilder()
                .connectTimeout(Duration.ofSeconds(5))
                .followRedirects(HttpClient.Redirect.NEVER)
                .build();

        HttpRequest request = HttpRequest.newBuilder(uri)
                .timeout(Duration.ofSeconds(10))
                .GET().build();

        HttpResponse<Void> response = client.send(
                request, HttpResponse.BodyHandlers.discarding());

        SSLSession tls = response.sslSession().orElseThrow(
                () -> new IllegalStateException("TLS session missing"));

        System.out.println("HTTP status: " + response.statusCode());
        System.out.println("TLS protocol: " + tls.getProtocol());
        System.out.println("Cipher suite: " + tls.getCipherSuite());
        System.out.println("Peer principal: " + tls.getPeerPrincipal());
    }
}
```

Biên dịch:

```sh
javac --release 11 -encoding UTF-8 HttpsSessionInspect.java
```

Chạy **chỉ với endpoint thực sự được phép truy cập**:

```sh
java HttpsSessionInspect https://your-authorized-host.example/
```

**Không có stdout cố định cho ví dụ này**, vì HTTP status, protocol/cipher, certificate và peer principal phụ thuộc server/cấu hình. Đây là chương trình để **quan sát**, không phải unit test có dữ liệu giả. Nếu chứng chỉ không được tin hoặc tên host không khớp, request sẽ thất bại thay vì in một phiên TLS giả.

Có thể dùng:

```sh
java -Djavax.net.debug=ssl,handshake,trustmanager HttpsSessionInspect https://your-authorized-host.example/
```

`HttpResponse.sslSession()` trả `Optional<SSLSession>`; với HTTPS hợp lệ thường có session. Chỉ có TLS session sau khi kết nối an toàn đã được thiết lập và response được nhận. `BodyHandlers.discarding()` có nghĩa không giữ response body; nó **không** làm mất HTTP status.

**Không cần sửa `HostnameVerifier` để luôn chấp nhận, không cần custom trust-all `SSLContext`, và không cần các system property nội bộ có tác dụng tắt hostname verification.** Nếu endpoint fail, phân tích certificate chain, SAN, truststore, TLS version và network path.

## 10. Bảng chẩn đoán lỗi TLS 1.3

| Triệu chứng/log | Nhóm nguyên nhân | Cách xác minh an toàn | Cách khắc phục |
| --- | --- | --- | --- |
| `PKIX path building failed` / `unable to find valid certification path` | CA/chain không được tin cậy | Xem certificate chain, issuer, truststore đang dùng | Cài đúng CA chain của tổ chức hoặc sửa server chain; không trust-all |
| `No subject alternative names matching IP address ...` | IP không có trong SAN | Xem SAN và hostname/IP thực kết nối | Kết nối bằng hostname hợp lệ hoặc cấp cert có IP SAN đúng |
| `No subject alternative DNS name matching ...` | DNS hostname mismatch | So SAN DNS, SNI, proxy/virtual host | Sửa server certificate/SNI/địa chỉ gọi |
| `certificate expired` / `not yet valid` | Thời hạn hoặc clock sai | Xem `Not Before`/`Not After` và đồng hồ hệ thống | Gia hạn cert hoặc sửa thời gian |
| `handshake_failure` / `protocol_version` | TLS version/cipher/auth không tương thích | So `supported_versions`, cipher suites, algorithm constraints | Cập nhật JDK/server và policy, tránh bật protocol yếu |
| `no suitable certificate` / `No available authentication scheme` | Server/mTLS thiếu cert/key hoặc thuật toán phù hợp | Xem key manager và cert key algorithm | Cài certificate/private key hợp lệ, thuật toán được hỗ trợ |
| `bad_certificate` hoặc `certificate_unknown` | Peer từ chối certificate | Phân biệt client/server mTLS, kiểm tra lỗi ở phía nào | Sửa client cert/CA/SAN/usage theo policy của peer |
| `unrecognized_name` | SNI/virtual host routing không hợp lệ | Kiểm tra SNI, tên host và cấu hình proxy/server | Cấu hình virtual host, certificate mapping |
| `SSLPeerUnverifiedException` | Không có danh tính peer được xác thực cho thao tác được gọi | Xem handshake state và cấu hình trust | Điều tra gốc, không in certificate như bằng chứng trust |
| `EOFException` / `connection reset` trong handshake | Peer/proxy đóng kết nối sớm | So log cả hai phía, TLS alerts/network | Sửa routing/proxy/TLS config, không tự kết luận là lỗi cert |
| Chỉ thấy `TLSv1.2` ở `legacy_version` | Trường tương thích của TLS 1.3 | Xem `supported_versions` và negotiated protocol | Không kết luận downgrade nếu negotiated TLS 1.3 |
| Không thấy `Certificate` trong log | Resumption, thiếu log hoặc phiên khác | Kiểm tra session resumption và trace chính xác | Không tự bỏ kiểm tra certificate |
| Handshake thành công nhưng HTTP `403` | Lỗi phân quyền cấp ứng dụng | Xem HTTP status và auth | Sửa authorization; không phải SSLHandshakeException |
| HTTP request treo sau handshake | Response/body/backend chậm | Phân tách TLS complete và HTTP read timeout | Kiểm tra app/proxy/response streaming |

Một lỗi handshake có thể có **nhiều nguyên nhân gốc**. Ví dụ `handshake_failure` rất chung; cần kiểm tra stack trace/cause và log hai phía. Nếu đã có certificate chain hợp lệ nhưng hostname sai, **không sửa bằng cách thay truststore** — cần sửa định danh endpoint.

## 11. Làm gì khi server dùng chứng chỉ nội bộ/self-signed?

Trong nội bộ công ty hoặc test environment, có thể không dùng public CA. Cách xử lý vẫn phải có mô hình tin cậy rõ ràng:

1. **Ưu tiên PKI/CA nội bộ đã được tổ chức phê duyệt**, cấp certificate với SAN chính xác.
2. Phân phối **CA root/intermediate được xác thực out-of-band**, hoặc pin certificate/public key theo một cơ chế có quản lý xoay vòng nếu thực sự cần.
3. Cấu hình `TrustManagerFactory` hoặc truststore tương ứng; nếu phải thay thế truststore mặc định, cân nhắc **có giữ các public trust anchors cần thiết hay không**, thay vì vô tình loại hết những CA khác.
4. Giữ **hostname verification bật** ở mọi môi trường. Trust một internal CA không có nghĩa mọi host do CA đó cấp đều được dùng thay thế cho nhau.
5. Theo dõi expiration/rotation/revocation policy và hạn chế quyền ghi truststore.
6. Không đưa certificate tự ký vừa nhận từ một endpoint không tin cậy vào truststore mà chưa **xác minh fingerprint hoặc kênh phân phối đáng tin cậy**. Nếu tự động tin mọi cert khi lỗi, sẽ mất mục đích authentication.

### Trust certificate của lab có phải “bỏ certificate check” không?

**Không.** Trong lab, truststore chỉ chứa **một certificate public cụ thể** đã được tạo có chủ đích, và việc xác minh tên host vẫn bật. Client từ chối cert khác và tên IP khác. Đây là một bài kiểm thử có trust anchor được kiểm soát.

**Không đồng nghĩa production nên trust một leaf certificate riêng rẽ mãi mãi.** Certificate thường phải xoay vòng và có thời hạn. Tùy môi trường, CA trust hoặc pinning có quản lý vòng đời tốt hơn; cần theo quy định an ninh của tổ chức.

## 12. Những cách “sửa TLS” tuyệt đối không áp dụng

Các cách sau làm mất tính xác thực của TLS và **không được dùng để khắc phục handshake failure**:

- Viết `X509TrustManager` với `checkServerTrusted(...)` rỗng.
- Tạo `TrustManager[]` tự chấp nhận mọi server certificate.
- Cài `HostnameVerifier` luôn trả `true` hoặc tắt `HTTPS` endpoint identification.
- Bật system property nội bộ làm HTTP client bỏ kiểm tra hostname.
- Chấp nhận mọi certificate mới chỉ vì “đang chạy môi trường dev”.
- Tắt xác minh chain rồi in ra `SSLSession.getCipherSuite()` như thể kết nối đã an toàn.
- Hạ TLS xuống giao thức/cipher yếu bị chính sách hiện hành vô hiệu hóa chỉ để bỏ một exception.
- Tắt kiểm tra revocation theo chính sách bảo mật hoặc chấp nhận cert đã hết hạn mà không có phê duyệt.

**Thay vì tắt validation, hãy tạo chứng chỉ đúng, sửa truststore/CA, sửa SAN/hostname, đồng bộ đồng hồ và cấu hình TLS policy.** Một handshake thất bại khi gặp certificate giả hoặc sai host là **hành vi bảo vệ đúng**, không phải bug cần né tránh.

## 13. SNI, ALPN, certificate chain và mTLS

### SNI (Server Name Indication)

SNI giúp server/proxy biết client muốn truy cập virtual host nào để chọn certificate phù hợp. Nếu kết nối tới sai IP/host hoặc proxy không chuyển SNI như mong đợi, server có thể trình **certificate của site khác**. Kiểm tra:

- URI/hostname đích ứng dụng đang dùng.
- SNI extension trong `ClientHello` (nếu có).
- Certificate trả về và SAN.
- Cấu hình virtual host/reverse proxy/load balancer.

**Không giả định SNI luôn xuất hiện** trong mọi kết nối đến IP literal hoặc `localhost`; implementation có thể không gửi SNI ở những trường hợp đó. Kết quả cert/hostname validation mới là điều kiện quan trọng khi xác thực server.

### ALPN (Application-Layer Protocol Negotiation)

ALPN thường chọn giao thức cấp ứng dụng như HTTP/2 (`h2`) hoặc HTTP/1.1. ALPN negotiation **khác** TLS protocol negotiation. Một kết nối chọn TLS 1.3 có thể dùng HTTP/1.1, và một số kết nối TLS 1.2 có thể dùng HTTP/2 tùy policy.

Không dùng `"h2"` như bằng chứng TLS là phiên bản 1.3. Quan sát riêng `SSLSession.getProtocol()` và application protocol/HTTP version.

### Intermediate chain

Server thường gửi leaf certificate và các intermediate certificate cần thiết; root CA thường đã nằm trong truststore của client và không nhất thiết được server gửi. Nếu thiếu intermediate, path building có thể thất bại dù root CA đã được tin. Sửa server chain là giải pháp phổ biến — **không** tắt certificate validation.

### mTLS

Nếu server yêu cầu client certificate, luồng TLS 1.3 có thể có `CertificateRequest`. Khi đó:

- Client cần `KeyManagerFactory` có private key/certificate phù hợp.
- Server cần truststore/CA để xác minh client.
- Client vẫn cần **xác minh certificate server và hostname**, mTLS không thay thế bước đó.
- Một lỗi `bad_certificate` có thể đến từ server từ chối **client cert**, không phải client từ chối server cert. Xem log của **cả hai phía** để xác định.

Không đưa private key client vào truststore; phân biệt rõ danh tính cục bộ và trust anchors.

## 14. TLS 1.3 resumption và ngoại lệ khi đọc handshake

TLS 1.3 có hỗ trợ **session resumption qua PSK**; một lần kết nối lại có thể không trình lại đầy đủ certificate chain như một full handshake. Điều này có thể khiến người chẩn đoán nghĩ log bị thiếu.

- Khi debug lần đầu, có thể tạo **client/context mới** và đối chiếu session cache để hiểu luồng; không cần vô hiệu hóa authentication.
- Không suy ra “CertificateVerify không có nên server không được xác thực” nếu đó là **resumed session** dựa vào thông tin tin cậy đã thiết lập trước.
- Với 0-RTT early data (một tính năng của giao thức TLS 1.3), có các rủi ro replay ở tầng ứng dụng; **không tự cho rằng Java 11 HttpClient hỗ trợ gửi 0-RTT theo mọi kết nối**.
- Thay đổi JDK/security provider và session tickets có thể làm chi tiết log khác nhau; ghi nhận version JDK, protocol và cách kết nối được tái sử dụng.

Nếu phân tích một trace trong production, nên biết session đó là **full handshake hay resumption**, trước khi kết luận một message “biến mất” là lỗi.

## 15. Quản lý cấu hình truststore trong ứng dụng thật

### Mặc định thường an toàn hơn cấu hình tự chế

Với HTTPS `HttpClient` bình thường, nên để **default trust manager và hostname verification** nếu không có yêu cầu tổ chức khác. Java runtime có tập trust anchors (ví dụ `cacerts`) và các chính sách security cập nhật theo bản JDK/vendor; cần bảo trì JDK để nhận bản vá/cập nhật CA.

Nếu sử dụng truststore riêng:

- Đảm bảo nguồn CA đáng tin, đã phê duyệt.
- Tránh lưu mật khẩu dạng plain text trong source code hoặc repository.
- Chú ý custom truststore có thể **thay thế** tập trust mặc định tùy cách khởi tạo, không tự hợp nhất.
- Xác định rõ owner của CA rotation, expiry alerts, revocation và deployment.
- Kiểm tra bằng negative tests: cert không được tin phải thất bại, hostname sai phải thất bại.

### `javax.net.ssl.trustStore` và `javax.net.ssl.keyStore`

Các system properties JSSE có thể cấu hình truststore/keystore cho default SSL context trong nhiều ứng dụng:

```sh
java -Djavax.net.ssl.trustStore=/secure/path/company-trust.p12 -Djavax.net.ssl.trustStoreType=PKCS12 MyApp
```

`MyApp` là chương trình do bạn sở hữu; command chỉ minh họa. Việc sử dụng truststore riêng có thể thay tập CA công khai được mặc định tin cậy; cần kiểm tra ảnh hưởng ứng dụng. Tránh đưa password thật qua command line: process list, log hoặc shell history có thể ghi lại. Có thể cấu hình programmatically bằng `TrustManagerFactory`/`SSLContext` và secret management của nền tảng khi thích hợp.

**Lab `Tls13HandshakeLab` không phụ thuộc system property truststore toàn JVM**, vì chương trình tự load PKCS12 và tạo context. Điều này giúp ba kịch bản độc lập, không thay cấu hình TLS của các tiến trình Java khác.

## 16. Kiểm thử certificate validation phải có cả negative tests

Một phép thử “kết nối thành công với server đúng” chưa đủ chứng minh không có trust-all. Nếu client đã bị cấu hình chấp nhận mọi cert, positive case vẫn thành công. Bộ test tối thiểu nên có:

| Kịch bản | Expected |
| --- | --- |
| CA tin cậy + hostname khớp | Handshake TLS 1.3 thành công |
| Certificate không thuộc trust anchors | **Bị từ chối** |
| Trust đúng CA nhưng hostname/IP sai | **Bị từ chối** |
| Certificate hết hạn | **Bị từ chối** theo validation policy |
| Algorithm bị security policy cấm | **Bị từ chối** |
| Certificate bị thu hồi, nếu revocation check là yêu cầu | **Bị từ chối** theo policy |
| Certificate của virtual host khác do SNI/routing sai | **Bị từ chối** do hostname |
| Server thiếu intermediate | Phát hiện path building error và sửa chain |
| Server chỉ hỗ trợ phiên bản TLS bị cấm | Handshake bị từ chối, không tự bật lại legacy protocol |
| mTLS thiếu client certificate | Phát hiện từ lỗi phía server và sửa cấu hình client identity |
| TLS hợp lệ nhưng HTTP `403` | Phân biệt lỗi authorization với handshake |

**Lab trong bài đã chạy ba case đầu**. Với những case còn lại, cần fixture/certificate test được tạo có kiểm soát hoặc integration environment có khả năng cấu hình CA, thời gian, proxy và mTLS. Không thử kết nối tới hệ thống không được phép hoặc thu thập certificate/private key của bên khác.

## 17. Checklist chẩn đoán sự cố TLS 1.3

1. Ghi **JDK/vendor/version** đang chạy và thông tin endpoint/proxy, tránh suy đoán từ version Java khi toolchain không đúng runtime.
2. Chụp lại exception **kèm cause** (và correlation ID), không chỉ phần message đầu.
3. Xác định đang ở TCP, TLS handshake hay HTTP/application layer.
4. Bật `javax.net.debug=ssl,handshake,trustmanager` **trong phạm vi an toàn**, bảo vệ log.
5. Tìm `ClientHello`, `ServerHello`, `supported_versions` và negotiated protocol.
6. Nếu có certificate flow, phân tích leaf cert, issuer/intermediate chain, trust anchors, SAN, hạn dùng và algorithm constraints.
7. Kiểm tra hostname/IP thực kết nối và SNI/virtual host, đừng chỉ xem CN.
8. Phân biệt mTLS client certificate failure với server certificate failure.
9. Kiểm tra system clock/PKI rotation nếu lỗi không ổn định theo thời gian.
10. Đối chiếu full handshake với session resumption nếu log thiếu message.
11. Sửa certificate/truststore/server config đúng nguyên nhân; **không bật trust-all, không bỏ hostname verification**.
12. Chạy lại **positive và negative tests**, xác nhận đúng host thành công còn cert/hostname sai vẫn bị từ chối.
13. Tắt debug sau khi điều tra xong, bảo vệ/xóa log theo chính sách.

## 18. Bài tập thực hành

### Bài 1 — Đọc TLS 1.3 handshake

Vẽ thứ tự message của full handshake có server authentication và chỉ ra bước nào đưa tới quyết định tin certificate, bước nào chứng minh server có private key. Giải thích vì sao CertificateVerify và Finished có chức năng khác nhau.

### Bài 2 — TLSv1.2 trong ServerHello

Tìm một đoạn JSSE log TLS 1.3 có `ServerHello.legacy_version`. Giải thích vì sao giá trị legacy có thể tương ứng TLS 1.2 nhưng `supported_versions` và `SSLSession.getProtocol()` vẫn là TLS 1.3.

### Bài 3 — Lab trust và hostname

Tạo các truststore như phần 7, chạy `Tls13HandshakeLab.java` và đối chiếu bốn dòng stdout. Thử cấp chứng chỉ mới có SAN gồm `DNS:localhost` **và** `IP:127.0.0.1` trong môi trường lab; dự đoán case “Wrong hostname” sẽ thay đổi thế nào khi client dùng truststore mới phù hợp. **Không bỏ `setEndpointIdentificationAlgorithm("HTTPS")`**.

### Bài 4 — Chẩn đoán lỗi PKIX

Thay truststore client bằng `untrusted.p12` và bật log `trustmanager`. Tìm thông báo không xây dựng được trust path. Mô tả cách kiểm tra nguồn CA đúng, không “import tất cả cert” từ một endpoint không đáng tin.

### Bài 5 — Chẩn đoán mTLS

Giả sử log server có `CertificateRequest` và báo client certificate không hợp lệ. Mô tả sự khác nhau giữa `KeyManagerFactory` phía client và `TrustManagerFactory` phía server. Nêu cách kiểm tra mTLS mà vẫn xác thực hostname của server phía client.

### Bài 6 — So sánh raw SSLSocket với HttpClient

Giải thích vì sao đoạn raw `SSLSocket` cần bật `SSLParameters.setEndpointIdentificationAlgorithm("HTTPS")`, còn HTTPS `HttpClient` bình thường đã theo đường xác thực server/host chuẩn. Viết một negative test chứng minh không được bỏ việc so hostname.

### Bài 7 — TLS và HTTP/business status

Một request nhận `SSLHandshakeException`, một request nhận HTTP `503`, một request nhận HTTP `200` với business status `REJECTED`. Phân loại lỗi ở tầng TLS, HTTP và nghiệp vụ; cách xử lý/retry của ba trường hợp có giống nhau không?

### Checklist hoàn thành

- [ ] Biết Java 11 có TLS 1.3/JSSE và không cần thư viện TLS incubator.
- [ ] Mô tả đúng full handshake, các trường legacy và message được mã hóa sau ServerHello.
- [ ] Phân biệt protocol/cipher negotiation, certificate path trust và hostname verification.
- [ ] Biết bật/tắt `javax.net.debug` an toàn và không coi format log là ổn định.
- [ ] Dùng `TrustManagerFactory` và `setEndpointIdentificationAlgorithm("HTTPS")` trong raw `SSLSocket`.
- [ ] Tạo lab PKCS12 và chạy đủ ba kịch bản, gồm hai negative tests.
- [ ] Không dùng trust-all hoặc always-true hostname verifier.
- [ ] Không coi `getPeerCertificates()` là bằng chứng trust nếu cấu hình xác thực sai.

**Kết luận:** chẩn đoán TLS 1.3 tốt nhất là **quan sát handshake, xác định chính xác điểm thất bại, kiểm tra trust path và hostname riêng biệt**, rồi sửa đúng CA/certificate/SAN/server configuration. Phòng lab đã chứng minh TLS 1.3 có thể thành công với trust anchor và hostname đúng, đồng thời **bắt buộc từ chối** truststore không đúng và hostname sai. Không vì muốn “kết nối được” mà tắt certificate validation — hành vi từ chối certificate/host giả chính là mục đích bảo mật của TLS.
