# Chứng chỉ, truststore, key manager và trust manager trong TLS 1.3 với Java 11+

## 1. Bốn khái niệm dễ bị nhầm

Java 11 hỗ trợ **TLS 1.3** thông qua Java Secure Socket Extension (**JSSE**) trong `javax.net.ssl`. Khi Java kết nối tới `https://` hoặc triển khai máy chủ TLS, ứng dụng cần biết **ai đang trình diện định danh**, **ai được tin cậy** và **thành phần nào thực hiện việc xác thực**.

| Khái niệm | Chứa / thực hiện | Trả lời câu hỏi |
| --- | --- | --- |
| **Chứng chỉ X.509** | Public key, subject/SAN, issuer, thời hạn, chữ ký CA và các extension liên quan | “Định danh/public key nào đang được trình diện?” |
| **Identity keystore** | Thường có **private key** cùng **certificate chain** của chính endpoint; Java dùng `KeyStore` để đọc | “Tôi dùng khóa và chuỗi chứng chỉ nào để chứng minh danh tính của mình?” |
| **Truststore** | Chứa **trusted certificates/trust anchors** (thường là CA mà ta chủ động tin cậy); có thể dùng định dạng PKCS12 | “Tôi tin những bên phát hành/chứng chỉ nào để kiểm tra peer?” |
| **Key manager** | `KeyManager` / `X509KeyManager`, thường lấy từ `KeyManagerFactory` | “Chọn private key và chuỗi chứng chỉ **của bên cục bộ** nào khi cần xác thực?” |
| **Trust manager** | `TrustManager` / `X509TrustManager`, thường lấy từ `TrustManagerFactory` | “Kiểm tra chuỗi chứng chỉ **của bên từ xa** có đáng tin hay không?” |

**Keystore và truststore không phải hai kiểu Java class hoàn toàn khác nhau.** Cả hai đều có thể biểu diễn bằng `java.security.KeyStore` (ví dụ định dạng `PKCS12`), nhưng **vai trò** khác nhau. Identity keystore thông thường có entry private key; truststore thường có entry chứng chỉ tin cậy. Không gọi một file “truststore” rồi suy ra nó chứa private key.

**Private key không nằm trong chứng chỉ công khai.** Chứng chỉ chỉ mang public key và metadata đã được chứng thực. Private key phải được giữ bí mật; nếu chỉ import một file `.crt` vào truststore thì không tự tạo được key manager có khả năng xuất trình định danh TLS.

TLS 1.3 **không thay thế mô hình PKI/CA**: phiên bản handshake, thuật toán trao đổi khóa và mã hóa được nâng cấp, nhưng xác thực chứng chỉ X.509 và kiểm tra định danh đầu cuối vẫn quan trọng. Không có yêu cầu phải viết một `TrustManager` riêng chỉ vì sử dụng TLS 1.3.

## 2. Luồng xác thực HTTPS một chiều và hai chiều

### HTTPS thông thường: client xác thực server

```text
Java HTTPS client                       HTTPS server
       |------ ClientHello ------------->|
       |<----- TLS handshake ------------|
       |<----- Certificate chain --------|
       |                                  |
  TrustManager kiểm tra chuỗi chứng chỉ
  + kiểm tra server hostname/SAN qua cơ chế HTTPS
       |
  Nếu hợp lệ -> tiếp tục kết nối có xác thực
  Nếu không -> handshake/HTTP request thất bại
```

Với một website công khai, client thường **không cần certificate/private key riêng**. Nó chỉ cần biết cách **kiểm tra chứng chỉ của server**, thường thông qua truststore mặc định của JVM. Đa số trường hợp **không cần** tự cấu hình `SSLContext`.

Kiểm tra certificate chain và kiểm tra hostname là **hai điều kiện khác nhau**:

- **Xác thực chuỗi chứng chỉ (trust):** kiểm tra các chữ ký, thời hạn, chính sách/thuật toán, liên kết CA/trust anchor phù hợp và những kiểm tra PKIX liên quan.
- **Xác thực danh tính hostname (endpoint identification):** tên server trong URL (ví dụ `api.example.com`) phải khớp danh tính cho phép trong chứng chỉ, thông thường qua `subjectAltName` (**SAN**). Chứng chỉ được một CA tin cậy ký **không đủ** nếu nó dành cho hostname khác.

`java.net.http.HttpClient` thực hiện HTTPS endpoint identification theo cấu hình bảo mật mặc định; **đừng tắt xác minh hostname** để “sửa” lỗi chứng chỉ.

### Mutual TLS (mTLS): hai phía xác thực nhau

Khi server yêu cầu chứng chỉ **của client**, có thêm một hướng xác thực:

```text
Java client                                  TLS server
  TrustManager -> xác minh cert server      KeyManager -> cert + key server
  KeyManager   -> cert + key client  ---->  TrustManager -> xác minh cert client
```

Ở client mTLS:

1. **Trust manager của client** kiểm tra server.
2. **Key manager của client** chọn và dùng private key + certificate chain **của client** khi server yêu cầu client authentication.
3. **Trust manager của server** kiểm tra certificate chain của client.
4. **Key manager của server** cung cấp định danh của server.

Chỉ đặt chứng chỉ client vào keystore **không ép** server bật mTLS. Phía server phải được cấu hình để **yêu cầu và tin cậy** certificate client. Tương tự, có truststore phía client không đồng nghĩa client đang gửi certificate của mình.

## 3. Các API JSSE cốt lõi

| API Java 11+ | Vai trò |
| --- | --- |
| `KeyStore.getInstance("PKCS12")` | Tạo đối tượng đọc/giữ keystore/truststore PKCS12. |
| `KeyStore.load(InputStream, char[])` | Nạp entries từ file, với password phù hợp. |
| `TrustManagerFactory.getDefaultAlgorithm()` | Lấy tên thuật toán factory mặc định theo cấu hình JDK/provider. |
| `TrustManagerFactory.getInstance(algorithm)` | Khởi tạo factory sinh trust managers. |
| `tmf.init(trustStore)` | Cấu hình các trust anchors từ `KeyStore` đã nạp. |
| `KeyManagerFactory.getDefaultAlgorithm()` | Lấy thuật toán key manager factory mặc định. |
| `kmf.init(identityStore, keyPassword)` | Cấp keystore chứa private-key entries và password giải mã khóa. |
| `SSLContext.getInstance("TLS")` | Tạo context TLS theo provider/phiên bản hỗ trợ. |
| `SSLContext.getInstance("TLSv1.3")` | Lấy context với tên thuật toán TLS 1.3 khi provider hỗ trợ (SunJSSE trong Java 11 hỗ trợ). |
| `context.init(keyManagers, trustManagers, secureRandom)` | Gắn vai trò xuất trình danh tính và kiểm tra trust vào context. |
| `HttpClient.newBuilder().sslContext(context)` | Cho HTTP client dùng context TLS đã cấu hình. |

Chữ ký quan trọng:

```java
void SSLContext.init(
    KeyManager[] keyManagers,
    TrustManager[] trustManagers,
    SecureRandom random)
```

Đối số `keyManagers` dùng cho **định danh của chính ứng dụng**; `trustManagers` dùng để **kiểm tra phía đối diện**. `random` có thể để `null` để dùng nguồn `SecureRandom` mặc định. Các tham số manager cũng có thể là `null` nhưng **không có cùng ý nghĩa**:

- `keyManagers == null`: context không được cấp một tập key manager tường minh để cung cấp định danh từ ứng dụng.
- `trustManagers == null`: JSSE có thể sử dụng trust managers mặc định của provider/JDK. Không đồng nghĩa “tin mọi chứng chỉ”.
- `trustManagers` được tạo từ một truststore **rỗng** không có nghĩa là dùng truststore mặc định: nguồn trust anchors ở đây là keystore rỗng, thường làm việc xác thực server thất bại.

Trong code ứng dụng, nếu **không** có yêu cầu tùy chỉnh, thường nên dùng `HttpClient.newHttpClient()` và trust mặc định. Chỉ tạo `SSLContext` riêng khi dự án có nhu cầu tin CA nội bộ, dùng mTLS, hoặc cấu hình TLS đã được yêu cầu và kiểm thử.

## 4. Ví dụ Java hoàn chỉnh, không mạng: khởi tạo các manager và TLS context

Ví dụ đầu tiên cố tình **không kết nối server** và không cần chứng chỉ có sẵn. Nó chứng minh cấu trúc các API và cho thấy một keystore **rỗng** không tự cung cấp client certificate. Để vẫn có trust anchors thông thường, ví dụ khởi tạo `TrustManagerFactory` bằng **trust configuration mặc định của JDK** qua `init((KeyStore) null)`.

Tạo file **`TlsManagersDemo.java`**:

```java
import java.security.KeyStore;
import javax.net.ssl.KeyManagerFactory;
import javax.net.ssl.SSLContext;
import javax.net.ssl.TrustManagerFactory;
import java.net.http.HttpClient;

public class TlsManagersDemo {
    public static void main(String[] args) throws Exception {
        // Demo-only password, không phải thông tin bảo mật thật.
        char[] demoPassword = "demo-only".toCharArray();

        // Keystore trống: KHÔNG có private key/certificate client.
        KeyStore identity = KeyStore.getInstance("PKCS12");
        identity.load(null, demoPassword);

        KeyManagerFactory kmf = KeyManagerFactory.getInstance(
                KeyManagerFactory.getDefaultAlgorithm());
        kmf.init(identity, demoPassword);

        // Dùng trust anchors mặc định của JDK thay vì truststore rỗng.
        TrustManagerFactory tmf = TrustManagerFactory.getInstance(
                TrustManagerFactory.getDefaultAlgorithm());
        tmf.init((KeyStore) null);

        SSLContext tls = SSLContext.getInstance("TLSv1.3");
        tls.init(kmf.getKeyManagers(), tmf.getTrustManagers(), null);

        HttpClient client = HttpClient.newBuilder()
                .sslContext(tls)
                .build();

        System.out.println("identityStoreType=" + identity.getType());
        System.out.println("identityEntries=" + identity.size());
        System.out.println("contextProtocol=" + tls.getProtocol());
        System.out.println("clientUsesContext=" +
                (client.sslContext() == tls));
    }
}
```

Chạy bằng **JDK 17+** (mã dùng API Java 11):

```bash
javac TlsManagersDemo.java
java TlsManagersDemo
```

**Stdout kỳ vọng trên JDK Java 11+ dùng provider SunJSSE hỗ trợ TLS 1.3:**

```text
identityStoreType=PKCS12
identityEntries=0
contextProtocol=TLSv1.3
clientUsesContext=true
```

Diễn giải:

1. `identity.load(null, password)` tạo một `KeyStore` trong bộ nhớ, chưa có entry nào. `identity.size()==0` **không phải lỗi API** nhưng nghĩa là không có private-key entry cho mTLS.
2. `kmf.init(identity, demoPassword)` khởi tạo key manager factory với nguồn khóa **rỗng**. Không nên hiểu rằng nó tạo ra certificate client.
3. `tmf.init((KeyStore) null)` sử dụng cơ chế lấy trust material mặc định của provider/JDK. Khác với `tmf.init(identity)` khi `identity` đang rỗng.
4. `SSLContext.getInstance("TLSv1.3")` chọn context có tên giao thức TLS 1.3. `getProtocol()` phản ánh tên thuật toán của **context**, không phải kết quả handshake; ví dụ **chưa gửi bất kỳ request nào**.
5. `HttpClient.Builder.sslContext(tls)` gắn context; phép so sánh object cho thấy client sử dụng context đã truyền.
6. Chương trình **không kiểm tra certificate path thực tế** vì không có máy chủ và không có peer certificate. Mục tiêu là giải thích pipeline tạo manager/context, không tuyên bố đã xác minh TLS.

**Không lấy `identity` rỗng trong bài làm cấu hình mTLS production.** Ở mục sau, ứng dụng sẽ nạp **một identity keystore thật** chứa private key và certificate chain để trình diện với server khi được yêu cầu.

## 5. Chuẩn bị truststore và identity keystore theo định dạng PKCS12

### 5.1. Truststore: tin CA/endpoint được lựa chọn

Khi phải kết nối tới một server dùng private CA hoặc PKI nội bộ, nhóm vận hành có thể cấp một **CA certificate** đã kiểm tra fingerprint/nguồn gốc. Chỉ khi đã tin rằng chứng chỉ đó đúng mới import vào truststore riêng của ứng dụng.

Ví dụ lệnh **minh họa** với certificate `internal-ca.crt` đã có:

```bash
keytool -importcert -alias internal-ca -file internal-ca.crt -keystore app-truststore.p12 -storetype PKCS12
```

`keytool` sẽ hỏi password và xác nhận nhập chứng chỉ (trừ khi có tham số tự động xác nhận). **Không** bật `-noprompt` trước khi đã kiểm tra nguồn certificate, fingerprint và các thuộc tính cần thiết.

Xem truststore:

```bash
keytool -list -v -keystore app-truststore.p12 -storetype PKCS12
```

Truststore như trên chứa trust material cho **peer authentication**. Nó **không** tự biến server certificate sai hostname thành hợp lệ, và không cấp private key cho client.

Với môi trường thực, ưu tiên trust anchor là CA được tổ chức quản lý có quy trình cấp phát/thu hồi, thay vì tùy tiện tin một certificate leaf do người không xác định gửi tới. Import leaf có thể tạo cách tin cậy hẹp cho hệ thống đặc thù, nhưng cần chính sách xoay vòng/kiểm tra danh tính rõ ràng.

### 5.2. Identity keystore: private key và chuỗi chứng chỉ

Nếu server bắt buộc **mTLS**, phía client cần một identity keystore chứa **PrivateKeyEntry**: private key và certificate chain tương ứng. Hệ thống PKI có thể cấp file `client-identity.p12` sau quy trình quản lý khóa/cấp chứng chỉ thích hợp. Ví dụ kiểm tra metadata:

```bash
keytool -list -v -keystore client-identity.p12 -storetype PKCS12
```

Thông tin cần kiểm tra gồm entry type (ví dụ `PrivateKeyEntry`), alias, certificate chain, thời hạn, SAN/Extended Key Usage theo chính sách PKI và việc chứng chỉ đáp ứng yêu cầu của server. **Truststore nhập mỗi `trustedCertEntry` không thể thay thế identity keystore có private key**.

Đối với ứng dụng server TLS, key manager cũng dùng private key/certificate chain của **server**, còn trust manager có thể kiểm tra certificate client nếu server bật mTLS.

### 5.3. Password và bảo quản file

Trong production, không đưa keystore password vào source code, git, image công khai hoặc log. Dùng secret manager, keystore phần cứng/HSM hoặc cách phân phối bí mật có kiểm soát. Đọc password từ environment variable thường dễ minh họa nhưng vẫn phải bảo vệ môi trường triển khai, audit quyền đọc file, xoay vòng chứng chỉ/khóa. Trên ví dụ `keytool`, cố tình không thêm `-storepass` dưới dạng plain text trong command history.

Chứng chỉ public (`.crt`/`.pem`) không phải secret giống private key, nhưng vẫn cần **kiểm tra nguồn gốc** trước khi đánh dấu trusted. File `.p12` có private key phải được giới hạn quyền đọc và lưu trữ an toàn.

## 6. Nạp hai store thật vào `SSLContext` cho HTTPS client/mTLS

Mã sau là một ví dụ **độc lập về chức năng**, được đặt trong class tiện ích của ứng dụng; các biến input là `Path` và mảng `char[]` nhận từ hệ thống cấu hình/secret manager. Nó cho thấy cách đọc file PKCS12 mà không dựa vào tên thuật toán của một provider cụ thể.

```java
import java.io.InputStream;
import java.nio.file.Files;
import java.nio.file.Path;
import java.security.KeyStore;
import javax.net.ssl.KeyManager;
import javax.net.ssl.KeyManagerFactory;
import javax.net.ssl.SSLContext;
import javax.net.ssl.TrustManagerFactory;

public final class TlsContextFactory {
    private TlsContextFactory() { }

    private static KeyStore loadStore(Path path, char[] password)
            throws Exception {
        KeyStore store = KeyStore.getInstance("PKCS12");
        try (InputStream in = Files.newInputStream(path)) {
            store.load(in, password);
        }
        return store;
    }

    public static SSLContext forHttps(
            Path trustPath,
            char[] trustPassword,
            Path identityPath,
            char[] identityPassword)
            throws Exception {

        KeyStore trusted = loadStore(trustPath, trustPassword);
        TrustManagerFactory trustFactory = TrustManagerFactory.getInstance(
                TrustManagerFactory.getDefaultAlgorithm());
        trustFactory.init(trusted);

        KeyManager[] identities = null;
        if (identityPath != null) {
            KeyStore identity = loadStore(identityPath, identityPassword);
            KeyManagerFactory keyFactory = KeyManagerFactory.getInstance(
                    KeyManagerFactory.getDefaultAlgorithm());
            keyFactory.init(identity, identityPassword);
            identities = keyFactory.getKeyManagers();
        }

        SSLContext context = SSLContext.getInstance("TLS");
        context.init(identities, trustFactory.getTrustManagers(), null);
        return context;
    }
}
```

Lưu thành `TlsContextFactory.java` và biên dịch bằng:

```bash
javac TlsContextFactory.java
```

Đây là một **class tiện ích biên dịch được**, không có `main`, vì vậy lệnh `java TlsContextFactory` **không** phải cách chạy chương trình. Ứng dụng khác sẽ gọi `TlsContextFactory.forHttps(...)` rồi truyền kết quả cho `HttpClient.newBuilder().sslContext(...).build()`.

**Hai trường hợp:**

- **HTTPS không có mTLS:** truyền `identityPath == null`, do đó `identities == null`. Trust manager vẫn lấy các anchors từ `trustPath`.
- **HTTPS có mTLS:** truyền `identityPath` của PKCS12 chứa private key/cert chain. Key manager có thể chọn chứng chỉ client khi server yêu cầu và chấp nhận loại chứng chỉ đó.

**Không nhầm `identityPassword` trong code với mọi loại password của PKCS12.** Nhiều store dùng chung store password/key password, nhưng hệ thống PKI/provider có thể có chính sách riêng. `KeyManagerFactory.init(identity, keyPassword)` cần password giải mã key entries, không đơn thuần là password đọc file. Ví dụ giả sử chúng giống nhau; nếu khác, tách riêng hai mảng password.

**Cảnh báo quan trọng:** `trustFactory.init(trusted)` chỉ dùng các trust anchors theo **truststore được nạp**. Nó không tự động gộp `cacerts` mặc định với `app-truststore.p12`. Nếu ứng dụng vẫn cần tin public CA **và** private CA, phải thiết kế bộ trust anchors/composite validation theo chính sách được duyệt; không tùy tiện chuyển sang “trust all”.

### Gắn vào `HttpClient`

Trong một phương thức có các biến cấu hình tương ứng:

```java
SSLContext context = TlsContextFactory.forHttps(
        trustPath, trustPassword, identityPath, identityPassword);

HttpClient client = HttpClient.newBuilder()
        .sslContext(context)
        .build();
```

Đoạn này **không độc lập** (cần `trustPath`/password/`identityPath` do ứng dụng cung cấp) và không tự gọi HTTPS. Muốn gửi request, tạo `HttpRequest` rồi gọi `send` hoặc `sendAsync`. Lúc handshake, trust manager xác minh certificate path phía server; key manager chỉ được dùng để xuất trình định danh cục bộ khi giao thức/peer yêu cầu.

`SSLContext.getInstance("TLS")` thường là lựa chọn mềm dẻo để JSSE thương lượng phiên bản TLS hiện đại theo cấu hình được bật. Nếu hệ thống **bắt buộc** TLS 1.3, cần kiểm soát các phiên bản được phép qua `SSLParameters`/TLS policy phù hợp và **xác nhận phiên bản thương lượng sau handshake**; chỉ thấy tên context không chứng minh thực tế đã dùng TLS 1.3. Trong `java.net.http.HttpClient` có `HttpClient.Builder.sslParameters(...)`, nhưng thay đổi tham số TLS phải được kiểm thử cẩn thận, giữ nguyên bảo vệ danh tính endpoint, không cho phép giao thức đã bị vô hiệu hóa.

## 7. Truststore mặc định, `cacerts` và cấu hình JVM

Đối với các HTTPS endpoint sử dụng chứng chỉ do CA tin cậy phổ biến phát hành, default trust setup của JDK thường đã đủ. Một số thiết lập JSSE của provider mặc định có thể được thay bằng JVM system properties như:

```text
-Djavax.net.ssl.trustStore=/secure/config/app-truststore.p12
-Djavax.net.ssl.trustStoreType=PKCS12
```

Có thể cần cung cấp `javax.net.ssl.trustStorePassword` bằng cơ chế an toàn của môi trường chạy. **Đừng đưa password thật vào command line mà ai cũng có thể đọc qua process listing hoặc logs**. Các property này tác động ở cấp cấu hình JVM/JSSE tùy provider và thời điểm khởi tạo, không phải cơ chế đặt trust riêng cho một `HttpClient`. Khi muốn hai client dùng hai chính sách tin cậy khác nhau trong cùng tiến trình, nên tạo `SSLContext` riêng cho từng client thay vì sửa system properties toàn cục tại runtime.

Trên SunJSSE, khi không chỉ định trustStore property, việc tìm trust material mặc định thường xét `jssecacerts` trước `cacerts` trong vùng security của JDK. Tập CA có thể thay đổi tùy bản JDK, nhà phân phối, container image và chính sách tổ chức. **Không hardcode kết luận rằng mọi JVM có cùng danh sách root CA**.

Nếu `javax.net.ssl.trustStore` trỏ tới **đường dẫn không tồn tại**, không nên kỳ vọng Java tự bỏ qua và quay về tin `cacerts`; tài liệu SunJSSE nêu trường hợp có thể dẫn đến tập trust anchors rỗng. Vì vậy, hãy kiểm tra file thực sự tồn tại, đúng quyền đọc/định dạng/password, và log lỗi cấu hình (không log secret).

`javax.net.ssl.keyStore` và các property liên quan có thể điều khiển identity mặc định theo provider. Khi bài toán dùng mTLS chuyên biệt, lựa chọn `SSLContext` riêng thường dễ kiểm soát và kiểm thử hơn so với thay đổi cả JVM.

## 8. Chứng chỉ TLS 1.3: những phần phải xác minh

**Chuỗi chứng chỉ:** server thường gửi leaf certificate và các intermediate cần thiết để client dựng đường dẫn đến một trust anchor. Không mặc nhiên import mọi certificate server gửi vào truststore. CA trust anchor nên được quản lý theo chính sách doanh nghiệp; việc tin tùy tiện một intermediate/leaf có thể thay đổi ranh giới tin cậy.

**Tên miền/SAN:** nếu URL là `https://api.example.com` thì certificate cần hợp lệ cho tên `api.example.com` theo quy tắc HTTPS, không phải chỉ có chữ ký của CA đáng tin. Trong hệ thống dùng IP trực tiếp, cần certificate có IP SAN phù hợp.

**Hiệu lực:** kiểm tra `notBefore/notAfter`, thời gian hệ thống, các extension như `KeyUsage`/`ExtendedKeyUsage` và thuật toán chữ ký được bật theo chính sách JDK.

**Thu hồi chứng chỉ:** CRL/OCSP là những cơ chế có thể được bật/cấu hình tùy môi trường và provider. Không mặc định mọi ứng dụng Java 11 luôn kiểm tra revocation trực tuyến đầy đủ chỉ vì đang dùng trust manager. Với yêu cầu compliance, thiết kế kiểm tra revocation và khả năng truy cập dịch vụ PKI đúng chính sách.

**TLS version:** TLS 1.3 hỗ trợ chứng thực server bằng certificate và có thể hỗ trợ mTLS. Chứng chỉ X.509 không mang nhãn “chỉ dùng được TLS 1.3”; khả năng tương thích còn phụ thuộc thuật toán khóa/chữ ký, key exchange, cấu hình provider và tập cipher suites. Không tự tạo khóa yếu hoặc bật protocol đã bị hạn chế chỉ để handshake thành công.

**Certificate pinning:** nếu cần pinning theo threat model được duyệt, cần thiết kế vòng đời xoay vòng và cách xử lý certificate chain; không viết custom trust manager “return true” để giả lập pinning.

## 9. Xử lý lỗi phổ biến khi handshake

| Triệu chứng | Nguyên nhân có thể | Cách điều tra/sửa |
| --- | --- | --- |
| `PKIX path building failed` / `SunCertPathBuilderException` | Không dựng được đường dẫn từ peer certificate tới trust anchor đáng tin | Kiểm tra certificate chain, intermediate, truststore được nạp và CA nội bộ chính xác. |
| `unable to find valid certification path to requested target` | Chưa có trust anchor phù hợp hoặc chain thiếu | Xác minh nguồn chứng chỉ, không tự động import tất cả certificate quan sát được. |
| `No subject alternative DNS name matching ... found` | URL hostname không khớp SAN | Dùng hostname đúng hoặc cấp lại certificate có SAN đúng. Không tắt hostname verification. |
| `Keystore was tampered with, or password was incorrect` / lỗi đọc PKCS12 | Sai password, format hoặc file hỏng (thông điệp tùy provider) | Kiểm tra định dạng file, password và quyền truy cập an toàn. |
| `bad_certificate` / `certificate_required` khi mTLS | Server yêu cầu certificate client, không có hoặc không tin chain | Kiểm tra `PrivateKeyEntry`, certificate chain, key manager, CA được server tin cậy và chính sách client authentication. |
| `No appropriate protocol` / `protocol_version` | Không có protocol chung được bật hoặc chính sách thuật toán không tương thích | Kiểm tra TLS 1.3/1.2 được bật ở hai phía, `jdk.tls.disabledAlgorithms` và khả năng provider. |
| Handshake hoạt động với client A nhưng lỗi ở client B | Mỗi client dùng SSLContext/trust anchors khác nhau | In/kiểm tra cấu hình (không để lộ secret); kiểm tra client nào dùng context nào. |

Tên exception/message có thể thay đổi theo provider, JDK, vị trí lỗi và TLS version. Đừng viết logic nghiệp vụ phụ thuộc nguyên văn một thông báo lỗi tiếng Anh.

Để hỗ trợ chẩn đoán trong môi trường phát triển có kiểm soát, SunJSSE cho phép debug TLS bằng cấu hình như:

```text
-Djavax.net.debug=ssl,handshake,trustmanager
```

**Cẩn thận:** log TLS có thể chứa thông tin nhạy cảm về certificate, hostname, giao tiếp và hoạt động ứng dụng. Chỉ bật có thời hạn, bảo vệ log và tránh đưa thông tin bí mật vào báo cáo công khai. Debug logging chỉ là công cụ điều tra, không thay việc kiểm tra trust policy và test tích hợp.

## 10. Các sai lầm phải tránh

1. **Tắt trust validation** bằng một `X509TrustManager` có `checkServerTrusted` rỗng hoặc trả về mà không kiểm tra chain. Cách này làm client dễ bị tấn công man-in-the-middle; **không** dùng cho production hay để “tạm sửa” test rồi quên.
2. **Tắt hostname verification** hoặc bỏ kiểm tra SAN vì chứng chỉ CA đã được tin. Trust chain và endpoint identity là hai điều kiện **cần** cùng nhau.
3. **Import certificate client vào truststore** rồi tưởng Java đã có private key để tham gia mTLS. Private key và cert chain phải nằm trong identity store/HSM, được key manager truy cập.
4. **Dùng truststore rỗng** rồi diễn giải như “dùng default trust”. `tmf.init(emptyStore)` khác với `tmf.init((KeyStore) null)`.
5. **Thay thế toàn bộ `cacerts` bằng một truststore nội bộ** mà quên các API công khai. Một custom `TrustManagerFactory.init(customStore)` không tự merge những CA mặc định.
6. **Dùng `SSLContext.getProtocol()=="TLSv1.3"` làm bằng chứng server đã thương lượng TLS 1.3**. Tên context là cấu hình/tên thuật toán, còn protocol thực tế xác định qua handshake/`SSLSession`.
7. **Đưa password `.p12` vào source code, git hoặc log**. Bảo vệ cả file khóa riêng, password và cơ chế cấp phát bí mật.
8. **Đặt cấu hình JSSE qua system properties sau khi client/default SSLContext đã được tạo** rồi mong mọi kết nối cập nhật ngay. Context/config có thể được cache hoặc đã được khởi tạo; hãy cấu hình trước lúc tạo client hoặc truyền context rõ ràng.
9. **Giữ certificate đã hết hạn hoặc chưa xoay vòng** và chỉ tìm cách nới lỏng thuật toán. Cần quy trình rotate, deploy, rollback, theo dõi expiry.
10. **Cho rằng mọi handshake TLS 1.3 yêu cầu client certificate**. Trong HTTPS thông thường chỉ server cần certificate; mTLS là cấu hình bổ sung ở cả server và client.

## 11. Tự kiểm tra

**Câu 1:** Trên một HTTPS client thông thường, thành phần nào kiểm tra certificate server? Thành phần nào cung cấp certificate client?

**Đáp án:** `TrustManager` kiểm tra certificate server; `KeyManager` lựa chọn client certificate/private key **nếu** cần mTLS.

**Câu 2:** Một truststore chỉ chứa `trustedCertEntry` có giúp client ký xác thực mTLS không?

**Đáp án:** Không. Client cần private key và certificate chain (hoặc nguồn khóa tương đương, ví dụ HSM) cho `KeyManager`.

**Câu 3:** `tmf.init((KeyStore) null)` có giống `tmf.init(emptyPkcs12)` không?

**Đáp án:** Không. Trường hợp đầu yêu cầu cơ chế trust mặc định của provider; trường hợp sau cung cấp một truststore rỗng, không có CA anchors.

**Câu 4:** Chứng chỉ được CA tin cậy ký nhưng chỉ có SAN `other.example.com`, trong khi request gọi `api.example.com`. Có nên bỏ qua hostname check không?

**Đáp án:** Không. Phải dùng hostname phù hợp hoặc cấp chứng chỉ có SAN đúng. Không đánh đổi xác thực danh tính để kết nối thành công.

**Câu 5:** Khi đã có `SSLContext.getInstance("TLSv1.3")` và `context.init(...)`, có thể khẳng định request HTTPS đã dùng TLS 1.3 chưa?

**Đáp án:** Chưa. Context chỉ mới được cấu hình. Cần **thực hiện handshake** rồi kiểm tra protocol negotiated của phiên TLS khi cần xác nhận.

**Câu 6:** Khi cần tin một private CA và các public CA mặc định, chỉ gọi `tmf.init(customTruststore)` có tự gộp hai tập này không?

**Đáp án:** Không. Phải xây trust configuration gồm các anchors được phê duyệt hoặc chính sách validation phù hợp; tuyệt đối không dùng trust-all.

**Ghi nhớ:** Trong Java 11+ TLS 1.3, **truststore + TrustManager** xác thực phía đối diện, còn **identity keystore + KeyManager** cung cấp định danh của chính ứng dụng. `SSLContext.init(keyManagers, trustManagers, null)` nối hai vai trò; `HttpClient.Builder.sslContext(context)` áp dụng chúng cho kết nối HTTPS. Mọi cấu hình phải giữ **certificate path validation + hostname verification**, và mTLS chỉ hoạt động khi server thực sự yêu cầu/kiểm tra client certificate.
