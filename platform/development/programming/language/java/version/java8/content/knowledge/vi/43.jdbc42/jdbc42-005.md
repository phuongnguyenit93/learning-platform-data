# OffsetTime, OffsetDateTime và giới hạn hỗ trợ của DBMS — JDBC 4.2

JDBC 4.2 đưa những kiểu thời gian thuộc `java.time` (Java 8) vào cách làm việc với cơ sở dữ liệu. Hai kiểu trọng tâm của bài là **`OffsetTime`** — giờ trong ngày kèm độ lệch UTC, **không có ngày** — và **`OffsetDateTime`** — ngày, giờ kèm độ lệch UTC, đủ để xác định một instant. JDBC công bố những kiểu tổng quát `TIME_WITH_TIMEZONE` và `TIMESTAMP_WITH_TIMEZONE`, nhưng khả năng lưu và đọc thành công còn phụ thuộc **DBMS, phiên bản JDBC driver, kiểu cột, session timezone và precision**.

Câu hỏi quan trọng không chỉ là “có thể gọi `PreparedStatement.setObject` không?” mà còn là “**đọc lại được gì**?”. Một database có thể giữ nguyên instant nhưng đổi offset từ `+07:00` về `Z`; một database khác có thể giữ offset, hoặc không hỗ trợ kiểu thời gian có offset ở mức SQL. Nếu không tách các yêu cầu, ứng dụng dễ tạo dữ liệu thời gian sai mà code vẫn chạy.

Bài học chỉ dùng API và kiến thức **hiện còn áp dụng**, minh họa cú pháp JDBC 4.2, cơ chế của các lớp thời gian, so sánh PostgreSQL/Oracle/MySQL/SQL Server, kiểm tra khả năng hỗ trợ, xử lý precision/DST/NULL/SQLException và kiểm thử roundtrip. Ví dụ Java chính chạy độc lập với **JDK 17+**, có stdout đã xác minh. Đoạn thao tác với database thật được đánh dấu là **mảnh tích hợp cần driver và DB**, không được trình bày như kết quả test đã chạy.

## 1. Chọn đúng kiểu Java trước khi truy cập SQL

| Kiểu | Thông tin chứa | Có định danh instant không? | Phù hợp khi |
|---|---|---|---|
| `LocalTime` | Giờ trong ngày | Không | “09:00 hằng ngày” |
| `OffsetTime` | Giờ + offset UTC | Không; thiếu ngày | Một giờ gắn fixed offset |
| `LocalDateTime` | Ngày + giờ, không offset | Không | Thời gian địa phương chưa gắn zone |
| `OffsetDateTime` | Ngày + giờ + UTC offset | Có | Event có ngày và offset |
| `Instant` | Điểm trên timeline UTC | Có | Thứ tự sự kiện, audit |
| `ZonedDateTime` | Ngày + giờ + ZoneId | Có | Giờ ở vùng có quy tắc DST |
| `ZoneOffset` | Fixed offset, ví dụ +07:00 | Không | Độ lệch UTC cụ thể |
| `ZoneId` | Vùng địa lý, ví dụ Europe/Berlin | Không | Quy tắc timezone theo ngày |

`OffsetTime.parse("09:30+07:00")` không cho biết **ngày nào**. Hai ngày khác nhau có cùng OffsetTime không phải một event. Ngược lại, `OffsetDateTime.parse("2026-11-06T09:30+07:00")` đủ để quy về một instant `2026-11-06T02:30:00Z`.

Một `ZoneOffset` **không phải ZoneId**. Chỉ biết `+02:00` không biết đó là vùng nào, có quy tắc mùa hè hay không. Nếu hệ thống lưu lịch lặp theo vùng địa lý, cần **LocalTime + ZoneId + quy tắc ngày/lịch**, không thể chỉ dùng OffsetTime.

### 1.1. OffsetDateTime và instant

~~~java
OffsetDateTime local =
        OffsetDateTime.parse("2026-11-06T09:30:45+07:00");
OffsetDateTime utc =
        local.withOffsetSameInstant(ZoneOffset.UTC);

System.out.println(local.toInstant());
// 2026-11-06T02:30:45Z
~~~

Đây là đoạn Java trong một method có `import java.time.*;`. `withOffsetSameInstant` đổi giờ/offset hiển thị nhưng **không đổi instant**. `withOffsetSameLocal` giữ lại trường ngày/giờ địa phương nhưng thay offset, do đó **đổi instant**; không dùng nhầm trong hệ thống lưu sự kiện.

### 1.2. OffsetTime cần thêm ngày nếu muốn instant

~~~java
OffsetTime clock = OffsetTime.parse("09:30:45+07:00");
Instant point = clock.atDate(LocalDate.of(2026, 11, 6))
                     .toInstant();
// 2026-11-06T02:30:45Z
~~~

Giá trị `point` chỉ có ý nghĩa khi **ngày 06/11/2026 là dữ liệu nghiệp vụ thật**. Không thêm một ngày giả rồi coi đó là thời điểm thật. Nếu bảng SQL lưu time-only, nó không thể tự đại diện cho toàn bộ thông tin event.

### 1.3. equals và isEqual có thể khác nhau

~~~java
OffsetDateTime hcm =
        OffsetDateTime.parse("2026-11-06T09:30:45+07:00");
OffsetDateTime utc =
        hcm.withOffsetSameInstant(ZoneOffset.UTC);

System.out.println(hcm.equals(utc)); // false
System.out.println(hcm.isEqual(utc)); // true
~~~

`equals` của OffsetDateTime xét local date/time và offset; `isEqual` xét **cùng instant**. Nếu database chuẩn hóa UTC thì original và returned có thể `equals == false` nhưng `isEqual == true`. Khi test, phải biết yêu cầu cần **giữ instant** hay **giữ nguyên offset**.

`OffsetTime.isEqual` cũng so thời điểm của một giờ theo độ lệch offset trong phạm vi ngày quy chiếu, nhưng vì thiếu ngày nên **không phải phép kiểm hai event thật trùng instant** khi chưa có ngày.

## 2. Hợp đồng JDBC 4.2 và các mã SQLType

| Java value | JDBC enum | Constants trong Types | Số JDBC |
|---|---|---|---|
| `OffsetTime` | `JDBCType.TIME_WITH_TIMEZONE` | `Types.TIME_WITH_TIMEZONE` | 2013 |
| `OffsetDateTime` | `JDBCType.TIMESTAMP_WITH_TIMEZONE` | `Types.TIMESTAMP_WITH_TIMEZONE` | 2014 |
| `LocalTime` | `JDBCType.TIME` | `Types.TIME` | 92 |
| `LocalDateTime` | `JDBCType.TIMESTAMP` | `Types.TIMESTAMP` | 93 |
| `LocalDate` | `JDBCType.DATE` | `Types.DATE` | 91 |

Đây là **mã JDBC tổng quát**, không phải SQL type name phổ quát. SQL Server có `datetimeoffset`; PostgreSQL có `timestamptz`. Không suy từ enum là DBMS hỗ trợ DDL mang đúng tên.

### 2.1. Ghi qua PreparedStatement

~~~java
OffsetTime fixed = OffsetTime.parse("09:15:00+07:00");
OffsetDateTime event =
        OffsetDateTime.parse("2026-11-06T09:30:45+07:00");

try (PreparedStatement ps = connection.prepareStatement(
        "INSERT INTO offset_probe (time_offset, event_at) VALUES (?, ?)")) {
    ps.setObject(1, fixed, JDBCType.TIME_WITH_TIMEZONE);
    ps.setObject(2, event, JDBCType.TIMESTAMP_WITH_TIMEZONE);
    ps.executeUpdate();
}
~~~

**Đây là mảnh tích hợp JDBC**, giả định `connection` đã mở, bảng và hai cột tồn tại với kiểu tương thích. `setObject(int,Object,SQLType)` có trên API JDBC 4.2, nhưng **driver có thể từ chối mapping hoặc không hỗ trợ overload mong muốn**. Một số driver hỗ trợ truyền trực tiếp `setObject(index, event)` với type inference, một số cần vendor-specific binding. Thử đúng cách trên driver cụ thể và kiểm dữ liệu sau khi insert.

### 2.2. Đọc qua ResultSet có target Class

~~~java
try (PreparedStatement ps = connection.prepareStatement(
        "SELECT time_offset, event_at FROM offset_probe WHERE id = ?")) {
    ps.setLong(1, 42L);
    try (ResultSet rs = ps.executeQuery()) {
        if (rs.next()) {
            OffsetTime time = rs.getObject(
                    "time_offset", OffsetTime.class);
            OffsetDateTime timestamp = rs.getObject(
                    "event_at", OffsetDateTime.class);
        }
    }
}
~~~

Đây cũng là **mảnh tích hợp**, yêu cầu JDBC driver hỗ trợ typed `getObject` cho cột đó. Đừng gọi `getObject(column)` rồi ép kiểu `(OffsetDateTime)` mà chưa biết default Java type: driver có thể trả một đối tượng vendor riêng.

### 2.3. SQL NULL

Khi cột SQL là NULL, typed `rs.getObject(...,OffsetDateTime.class)` có thể trả Java `null` vì đây là reference type. Với binding null:

~~~java
ps.setNull(1, Types.TIMESTAMP_WITH_TIMEZONE);
~~~

Nếu driver không hỗ trợ mã tổng quát đối với cột cụ thể, bạn phải dùng target type phù hợp với driver, không âm thầm gán timestamp không offset. Null và conversion là hai tình huống độc lập.

## 3. Bốn dạng bảo toàn cần phân biệt

Khi lưu `2026-11-06T09:30:45+07:00`, có ít nhất bốn invariant khác nhau:

1. **Instant:** vẫn là `2026-11-06T02:30:45Z`.
2. **Offset nhập vào:** vẫn `+07:00`, không đổi thành `Z`.
3. **Trường ngày và giờ tại nguồn:** vẫn là `2026-11-06 09:30:45`.
4. **ZoneId vùng:** ví dụ `Asia/Ho_Chi_Minh`; bản thân OffsetDateTime không chứa ID này.

Một DBMS có thể chỉ giữ (1), còn Java object trả về có local fields và offset khác. Muốn giữ offset/ZoneId gốc để hiển thị hoặc audit, cần **kiểu cột thực sự giữ thông tin đó** hoặc **cột bổ sung**.

~~~text
Input:    2026-11-06 09:30:45 +07:00
                |
                | cùng instant
                v
UTC:      2026-11-06 02:30:45 Z

Output đọc từ một DB chuẩn hóa UTC:
          2026-11-06T02:30:45Z
~~~

Lỗi phổ biến là dùng `assertEquals(original,returned)` khi yêu cầu chỉ là instant. Nếu nhận offset khác không có nghĩa instant bị sai. Ngược lại, khi nghiệp vụ yêu cầu giữ đúng offset gốc, chỉ test instant là chưa đủ.

## 4. PostgreSQL: timestamptz và timetz

PostgreSQL hỗ trợ hai kiểu SQL tương ứng về mặt tên:

~~~sql
CREATE TABLE offset_probe (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    event_at TIMESTAMP WITH TIME ZONE NOT NULL,
    time_offset TIME WITH TIME ZONE
);
~~~

Đây là **DDL PostgreSQL**, không portable qua mọi DBMS. `timestamptz` là alias của timestamp with time zone; `timetz` là alias của time with time zone.

### 4.1. timestamptz không lưu original offset

PostgreSQL chuyển input có timezone về UTC để lưu, **không lưu nguyên tên vùng hay offset đầu vào**. Tài liệu pgJDBC hiện hành cho biết typed `getObject(...,OffsetDateTime.class)` đối với timestamp with time zone trả OffsetDateTime ở **offset UTC 0**.

~~~text
Insert: 2026-11-06T09:30:45+07:00
Stored instant: 2026-11-06T02:30:45Z
Typed read: 2026-11-06T02:30:45Z
~~~

Đây là mô tả semantics từ tài liệu, **không phải kết quả integration test vừa chạy**. Test cần so `toInstant` để kiểm đúng event và so `getOffset` riêng khi thật sự cần bảo toàn offset.

### 4.2. timetz có giá trị hạn chế trong thiết kế mới

PostgreSQL có `TIME WITH TIME ZONE`, nhưng tài liệu PostgreSQL **không khuyến nghị dùng cho thiết kế mới** vì thiếu ngày để áp quy tắc DST theo vùng. Nó giữ **giờ và fixed offset** chứ không thay thế một lịch hẹn theo ZoneId.

Các tài liệu pgJDBC cập nhật có mô tả hỗ trợ ánh xạ `OffsetTime ↔ TIME WITH TIME ZONE`, nhưng **không được mặc định mọi driver release đều như nhau**. Kiểm đúng bản driver của hệ thống bằng test `setObject`/`getObject`. Nếu ứng dụng chỉ cần giờ mở cửa theo một khu vực, thường nên lưu `LocalTime` + `ZoneId`, rồi chọn ngày khi tính instant.

### 4.3. Timestamp precision

PostgreSQL lưu thời gian với fractional precision thường tới microsecond (6 digits), trong khi Java hỗ trợ nano (9 digits). Input `.123456789` có thể không roundtrip từng nano đúng. Phải test cách DBMS/driver làm tròn hoặc cắt và lựa chọn precision policy trước khi so exact.

## 5. Oracle Database: TIMESTAMP WITH TIME ZONE và WITH LOCAL TIME ZONE

Oracle Database có hai biến thể quan trọng:

- `TIMESTAMP WITH TIME ZONE` chứa dữ liệu timezone dưới dạng offset hoặc vùng tùy cách sử dụng, khác kiểu chỉ chứa local timestamp.
- `TIMESTAMP WITH LOCAL TIME ZONE` **chuẩn hóa** vào database timezone và trả giá trị theo session timezone. **Offset/zone đầu vào không được lưu trong column**.
- `TIMESTAMP` không có timezone không tự là OffsetDateTime.
- `DATE` không mang offset.

Nếu business phải giữ original timezone/offset, chọn nhầm WITH LOCAL TIME ZONE có thể làm mất thông tin. Nếu business chỉ cần instant đúng, lưu với conversion có kiểm soát có thể phù hợp hơn.

**Giới hạn JDBC:** kiểu SQL có timezone trong Oracle không đồng nghĩa mọi phiên bản Oracle JDBC driver đều trả một Java OffsetDateTime y hệt object đầu vào. Hãy kiểm `getObject(...,OffsetDateTime.class)` và so instant, offset, precision trên đúng driver. Những setting format và session cũng có thể ảnh hưởng text display; dùng typed value khi có thể.

## 6. MySQL: TIMESTAMP khác DATETIME

MySQL không có một kiểu timestamp-with-original-offset theo cùng semantics với một số hệ quản trị khác.

- `TIMESTAMP` chuyển giá trị từ session timezone sang UTC khi lưu, và từ UTC sang session timezone khi lấy lại. Nó nhằm biểu diễn instant nhưng **không giữ offset đầu vào**.
- `DATETIME` là local date-time; bản thân nó không có offset để xác định instant.
- Connector/J có các cấu hình như `preserveInstants`, `connectionTimeZone` và `forceConnectionTimeZoneToSession`; cách mapping còn phụ thuộc phiên bản driver và cấu hình.

Nếu nhận `OffsetDateTime` rồi tự gọi `toLocalDateTime` và lưu vào DATETIME, bạn có thể **mất instant** khi server/session khác timezone. Muốn lưu event an toàn, cần một policy UTC/instant nhất quán và integration test trên nhiều session timezone.

Nếu cần giữ original offset/zone, bổ sung cột tương ứng. Không cho rằng `TIMESTAMP` của MySQL tự giữ thông tin biểu diễn người dùng đã nhập.

## 7. SQL Server: datetimeoffset và JDBC vendor type

SQL Server cung cấp `datetimeoffset` có **ngày, giờ và offset**, có thể giữ offset gốc. Thông số hiện hành có độ chính xác phân số tới 7 digits (100 ns) và giới hạn offset theo kiểu SQL.

~~~sql
CREATE TABLE dbo.offset_probe (
    id BIGINT NOT NULL PRIMARY KEY,
    event_at DATETIMEOFFSET(7) NOT NULL
);
~~~

Đây là **SQL Server T-SQL**. Theo Microsoft JDBC documentation, một số đường `getObject` của driver trả kiểu riêng **`microsoft.sql.DateTimeOffset`** cho cột `datetimeoffset`. Không tự ép `rs.getObject(column)` sang `OffsetDateTime`. Typed `getObject(column,OffsetDateTime.class)` và `setObject` cần được kiểm theo driver/driver version.

`datetimeoffset` lưu fixed offset nhưng **không tự lưu ZoneId địa lý và các quy tắc DST**. Nếu muốn hiển thị “Europe/Berlin” với luật mùa hè, lưu tên vùng riêng.

## 8. Tóm tắt khác biệt thực tế giữa DBMS

| DBMS/kiểu | Điểm giữ được | Điểm dễ mất hoặc cần test |
|---|---|---|
| PostgreSQL `timestamptz` | Instant | Original offset; pgJDBC trả UTC |
| PostgreSQL `timetz` | Clock + fixed offset | Không có ngày/ZoneId; mapping theo driver |
| Oracle `TIMESTAMP WITH TIME ZONE` | Timezone data trong DB | JDBC mapping và precision |
| Oracle `TIMESTAMP WITH LOCAL TIME ZONE` | Instant qua session conversion | Original offset/zone |
| MySQL `TIMESTAMP` | Instant với cấu hình đúng | Original offset, session-conversion |
| MySQL `DATETIME` | Local date/time | Instant/offset không tự xác định |
| SQL Server `datetimeoffset` | Instant và offset | ZoneId và driver-specific mapping |

Đây là bảng **ngữ nghĩa kiểu cột**, không phải lời hứa mọi phép typed `setObject`/`getObject` sẽ chạy thành công trên mọi driver.

## 9. Kiểm hỗ trợ DBMS đúng cách

### 9.1. Ghi lại environment của hệ thống

~~~java
DatabaseMetaData md = connection.getMetaData();
System.out.println(md.getDatabaseProductName());
System.out.println(md.getDatabaseProductVersion());
System.out.println(md.getDriverName());
System.out.println(md.getDriverVersion());
System.out.println(md.getJDBCMajorVersion());
System.out.println(md.getJDBCMinorVersion());
~~~

Đây là **mảnh JDBC integration** với `connection` đã có. Không chỉ ghi Java version. Cần cả database version, driver version, session timezone và các connection properties. Một cập nhật driver có thể đổi conversion behavior dù Java source không đổi.

### 9.2. Tham khảo getTypeInfo

~~~java
try (ResultSet info = connection.getMetaData().getTypeInfo()) {
    while (info.next()) {
        int code = info.getInt("DATA_TYPE");
        if (code == Types.TIME_WITH_TIMEZONE
                || code == Types.TIMESTAMP_WITH_TIMEZONE) {
            System.out.println(info.getString("TYPE_NAME")
                    + " -> " + code);
        }
    }
}
~~~

`getTypeInfo` cho thấy các kiểu mà driver/DBMS quảng bá. Nhưng **không chứng minh** rằng mapping `OffsetTime` và `OffsetDateTime` hoạt động hoàn toàn. Một số hệ thống có kiểu vendor-specific được báo bằng mã khác. Hãy dùng metadata để định hướng schema rồi **thử roundtrip thật**.

### 9.3. Kiểm metadata của cột

~~~java
try (PreparedStatement ps = connection.prepareStatement(
        "SELECT event_at FROM offset_probe WHERE 1 = 0");
     ResultSet rs = ps.executeQuery()) {
    ResultSetMetaData meta = rs.getMetaData();
    System.out.println(meta.getColumnTypeName(1));
    System.out.println(meta.getColumnType(1));
    System.out.println(meta.getScale(1));
}
~~~

Đây là mảnh JDBC integration, bảng `offset_probe` phải tồn tại. `getScale` giúp xem fractional seconds scale, nhưng **không thay thế** kiểm thực tế việc rounding/truncation khi lưu.

### 9.4. Test roundtrip trên DB thật

Hãy insert với offset `+07:00`, `Z` và offset âm; sau đó đọc lại typed values. Ghi ít nhất:

- SQL type name/code của column;
- Java type thực tế trả về;
- Giá trị instant trước/sau;
- Original offset và returned offset;
- Local date/time fields;
- Fractional second precision;
- Session timezone và driver connection settings;
- NULL, lỗi unsupported và transaction boundary.

Một test chỉ đọc chuỗi hiển thị SQL không đủ, vì session timezone hoặc format string có thể thay đổi mà instant vẫn đúng.

## 10. SQLException, SQLFeatureNotSupportedException và fallback

Một method JDBC có mặt trong JDK **không bảo đảm driver triển khai tất cả conversions**. Khi unsupported, có thể có `SQLFeatureNotSupportedException` hoặc một `SQLException` khác tùy nguyên nhân: cột sai kiểu, conversion không hợp lệ, lỗi statement, precision/range.

~~~java
try (PreparedStatement ps = connection.prepareStatement(
        "INSERT INTO offset_probe (event_at) VALUES (?)")) {
    ps.setObject(1, event, JDBCType.TIMESTAMP_WITH_TIMEZONE);
    ps.executeUpdate();
} catch (SQLFeatureNotSupportedException ex) {
    // Tính năng được yêu cầu không được hỗ trợ ở driver này.
    throw ex;
} catch (SQLException ex) {
    // Ghi SQLState, vendor error code, schema và driver version.
    throw ex;
}
~~~

Đây là **mảnh tích hợp**, `connection` và `event` do ứng dụng cung cấp. Không âm thầm đổi OffsetDateTime sang LocalDateTime hoặc String khi gặp exception: việc đó có thể làm mất offset hoặc sai instant.

Nếu cần fallback portable, xây adapter có policy rõ (ví dụ lưu UTC instant + original offset/ZoneId theo cột bổ sung) và test. Đừng xem `java.sql.Time` là tương đương `OffsetTime` vì nó không chứa offset.

### 10.1. NULL và transaction

Typed `getObject` có thể trả null với SQL NULL. `setNull` phải có target type được driver/column chấp nhận. Nếu chạy batch trong transaction, một mapping error có thể khiến batch dở dang; cấu hình commit/rollback đúng nghiệp vụ. Không để một record sai timezone lọt qua do catch exception rồi skip.

### 10.2. Báo lỗi đủ dữ kiện

Ghi `SQLException.getSQLState()`, `getErrorCode()`, class Java, JDBCType, SQL column type, DB/driver versions và connection timezone. Đừng ghi mật khẩu DB hoặc dữ liệu riêng tư vào log. Không parse thông báo lỗi tiếng Anh như API ổn định.

## 11. Precision của java.time so với SQL

`OffsetTime` và `OffsetDateTime` hỗ trợ **9 chữ số nanosecond**. Cột SQL có thể chỉ giữ microsecond (6), millisecond (3) hoặc kiểu scale khác.

~~~java
OffsetDateTime original = OffsetDateTime.parse(
        "2026-11-06T09:30:45.123456789+07:00");
OffsetDateTime sixDigits =
        original.truncatedTo(ChronoUnit.MICROS);
// .123456789 thành .123456000
~~~

Đây là **phép ứng dụng chủ động truncate**, không có nghĩa mọi DBMS đều làm đúng như vậy. Một database/driver có thể **round** thay vì truncate; cần test cột và version cụ thể.

| Fraction input | Trường hợp kiểm | Rủi ro |
|---|---|---|
| `.000000000` | Giây nguyên | Ít |
| `.123000000` | Millisecond | Cột scale 0 có thể mất |
| `.123456000` | Microsecond | Cột scale 3 có thể mất |
| `.123456789` | Nanosecond 9 digits | DB scale thấp hơn |
| `.999999999` | Sát giây tiếp theo | Rounding có thể carry |
| Giá trị trước epoch | Kiểu/range khác nhau | DB có thể từ chối |

Đừng áp `assertEquals(original, actual)` trước khi xác định precision và offset normalization. Với yêu cầu cùng instant, so `toInstant` sau khi biết policy precision.

## 12. DST và ý nghĩa business

Vùng có DST có thể có **gap** (giờ địa phương không tồn tại) hoặc **overlap** (giờ địa phương xuất hiện hai lần). `OffsetDateTime` mang một offset đã được chọn, nên có instant; `OffsetTime` thiếu ngày/ZoneId nên không thể tự tính lịch theo vùng.

~~~java
ZoneId region = ZoneId.of("Europe/Berlin");
LocalDateTime ambiguous =
        LocalDateTime.of(2026, 10, 25, 2, 30);
int count = region.getRules().getValidOffsets(ambiguous).size();
// count = 2 với tzdb đang được dùng trong bản thử nghiệm.
~~~

Nếu ứng dụng lưu một lịch họp `02:30 Europe/Berlin` theo tuần hoặc mùa, cần bảo toàn tên vùng và quy tắc xử lý gap/overlap. Không dùng `OffsetTime` cố định rồi mặc định nó sẽ tự đổi offset ở các mùa.

**Phân biệt use case:** Event log đã xảy ra nên lưu instant/UTC; giờ mở cửa định kỳ nên lưu LocalTime + ZoneId; hóa đơn cần cả thời điểm và dữ liệu trình bày nguyên thủy có thể lưu thêm original offset/region ID.

## 13. Chương trình Java độc lập, đã kiểm tra bằng JDK

Lưu tên file **`JdbcOffsetTypesDemo.java`**. Chương trình chạy trên **JDK17+** và chỉ dùng thư viện JDK chuẩn. Nó có các method `bind`, `read` với chữ ký JDBC được **biên dịch**, nhưng không gọi database, vì không có Connection thật. Mục tiêu là chứng minh:

1. JDBCType codes 2013 và 2014 có trong JDK.
2. OffsetTime và OffsetDateTime chuyển offset cùng instant.
3. `equals` khác `isEqual` với OffsetDateTime.
4. OffsetTime chỉ thành instant sau khi được gắn ngày.
5. Nano 9 digits và phép minh họa chuẩn hóa microsecond.
6. ZoneId có thể gặp DST overlap.
7. JDBC syntax có thể compile nhưng **chưa chứng minh DBMS/driver runtime hỗ trợ**.

~~~java
import java.sql.*;
import java.time.*;
import java.time.temporal.ChronoUnit;

public class JdbcOffsetTypesDemo {
    static void bind(PreparedStatement ps, OffsetTime time,
                     OffsetDateTime timestamp) throws SQLException {
        ps.setObject(1, time, JDBCType.TIME_WITH_TIMEZONE);
        ps.setObject(2, timestamp, JDBCType.TIMESTAMP_WITH_TIMEZONE);
    }

    static void read(ResultSet rs) throws SQLException {
        OffsetTime time = rs.getObject(1, OffsetTime.class);
        OffsetDateTime timestamp = rs.getObject(2, OffsetDateTime.class);
        if (time == null || timestamp == null) {
            System.out.println("SQL NULL is possible");
        }
    }

    public static void main(String[] args) {
        OffsetTime time = OffsetTime.parse("09:30:45.123456789+07:00");
        OffsetDateTime timestamp =
                OffsetDateTime.parse("2026-11-06T09:30:45.123456789+07:00");

        OffsetTime utcTime = time.withOffsetSameInstant(ZoneOffset.UTC);
        OffsetDateTime utcStamp = timestamp.withOffsetSameInstant(ZoneOffset.UTC);

        System.out.println("JDBC TIME_WITH_TIMEZONE: "
                + JDBCType.TIME_WITH_TIMEZONE.getVendorTypeNumber());
        System.out.println("JDBC TIMESTAMP_WITH_TIMEZONE: "
                + JDBCType.TIMESTAMP_WITH_TIMEZONE.getVendorTypeNumber());
        System.out.println("Types constants match: "
                + (Types.TIME_WITH_TIMEZONE == JDBCType.TIME_WITH_TIMEZONE.getVendorTypeNumber()
                && Types.TIMESTAMP_WITH_TIMEZONE == JDBCType.TIMESTAMP_WITH_TIMEZONE.getVendorTypeNumber()));
        System.out.println("OffsetTime: " + time);
        System.out.println("OffsetTime UTC equivalent: " + utcTime);
        System.out.println("Same clock time: "
                + time.toLocalTime().equals(utcTime.toLocalTime()));
        System.out.println("Same offset-time point: " + time.isEqual(utcTime));
        System.out.println("Time plus date to instant: "
                + time.atDate(LocalDate.of(2026, 11, 6)).toInstant());
        System.out.println("OffsetDateTime: " + timestamp);
        System.out.println("OffsetDateTime UTC equivalent: " + utcStamp);
        System.out.println("Java equals: " + timestamp.equals(utcStamp));
        System.out.println("Same instant: " + timestamp.isEqual(utcStamp));
        System.out.println("Instant: " + timestamp.toInstant());
        System.out.println("Nanosecond fraction: " + timestamp.getNano());
        System.out.println("Microsecond normalized nanos: "
                + timestamp.truncatedTo(ChronoUnit.MICROS).getNano());

        ZoneId region = ZoneId.of("Europe/Berlin");
        LocalDateTime overlap = LocalDateTime.of(2026, 10, 25, 2, 30);
        System.out.println("Berlin DST overlap offsets: "
                + region.getRules().getValidOffsets(overlap).size());
        System.out.println("JDBC calls need a DB driver to execute");
    }
}
~~~

Biên dịch và chạy:

~~~bash
javac -encoding UTF-8 JdbcOffsetTypesDemo.java
java JdbcOffsetTypesDemo
~~~

Stdout đã chạy và đối chiếu:

~~~text
JDBC TIME_WITH_TIMEZONE: 2013
JDBC TIMESTAMP_WITH_TIMEZONE: 2014
Types constants match: true
OffsetTime: 09:30:45.123456789+07:00
OffsetTime UTC equivalent: 02:30:45.123456789Z
Same clock time: false
Same offset-time point: true
Time plus date to instant: 2026-11-06T02:30:45.123456789Z
OffsetDateTime: 2026-11-06T09:30:45.123456789+07:00
OffsetDateTime UTC equivalent: 2026-11-06T02:30:45.123456789Z
Java equals: false
Same instant: true
Instant: 2026-11-06T02:30:45.123456789Z
Nanosecond fraction: 123456789

~~~

Dòng `Java equals: false` và `Same instant: true` là điểm dễ nhầm nhất khi đọc `timestamptz` về UTC. Dòng `Microsecond normalized nanos` chỉ là phép `truncatedTo` trong Java, không phải benchmark DB precision. Dòng cuối nêu giới hạn: Java compile được JDBC method không có nghĩa đã có kết nối để thực hiện roundtrip database.

## 14. Mẫu integration test cho PostgreSQL

Với PostgreSQL và pgJDBC đã cấu hình đúng, DDL test:

~~~sql
CREATE TABLE offset_probe (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    event_at TIMESTAMP WITH TIME ZONE NOT NULL,
    time_offset TIME WITH TIME ZONE
);
~~~

DDL chỉ dùng cho test; không khuyến nghị `timetz` làm kiểu giờ đặt lịch DST mới. Cần một `Connection connection` từ driver thực.

Mảnh kiểm `OffsetDateTime`:

~~~java
OffsetDateTime sent = OffsetDateTime.parse(
        "2026-11-06T09:30:45.123456+07:00");
try (PreparedStatement ps = connection.prepareStatement(
        "INSERT INTO offset_probe (event_at) VALUES (?)")) {
    ps.setObject(1, sent);
    ps.executeUpdate();
}
try (PreparedStatement ps = connection.prepareStatement(
        "SELECT event_at FROM offset_probe ORDER BY id DESC LIMIT 1");
     ResultSet rs = ps.executeQuery()) {
    if (rs.next()) {
        OffsetDateTime got = rs.getObject(1, OffsetDateTime.class);
        if (!sent.toInstant().equals(got.toInstant())) {
            throw new AssertionError("Instant changed");
        }
    }
}
~~~

Đây **không phải một test đã chạy trên DB**. Query `ORDER BY id DESC` chỉ dùng khi bảng test riêng không có writer khác; production phải dùng ID của đúng record (generated keys) để tránh đọc nhầm. Nếu muốn kiểm `OffsetTime`, hãy insert/read cột timetz riêng và ghi rõ driver version cùng outcome, không tự gán “được hỗ trợ” chỉ từ sự có mặt của kiểu SQL.

## 15. Ma trận kiểm thử compatibility

| Case | Cần xác nhận |
|---|---|
| OffsetDateTime → timestamp with timezone | Typed bind/read và instant |
| OffsetTime → time with timezone | Có hỗ trợ trên driver/cột không |
| Different offsets cùng instant | Đúng instant dù local fields đổi |
| Yêu cầu giữ offset gốc | getOffset không đổi hoặc có cột phụ |
| Yêu cầu giữ ZoneId | Có cột lưu region ID |
| SQL NULL | Typed getObject trả null |
| Fraction 0/3/6/9 | Precision và rounding policy |
| Date crossover khi đổi offset | Ngày và instant đúng |
| DST gap/overlap | Chính sách xử lý theo ZoneId |
| Session timezone khác | Instant không thay ngoài ý muốn |
| MySQL connection settings | preserveInstants/connectionTimeZone đúng |
| PostgreSQL timestamptz | UTC-normalized read |
| Oracle LOCAL TIME ZONE | Không đòi giữ original offset |
| SQL Server datetimeoffset | Vendor JDBC mapping/precision |
| Driver từ chối SQLType | SQLException có ngữ cảnh |
| DBMS/driver upgrade | Chạy lại test trên version mới |
| Typed getObject không hỗ trợ | Không cast object không kiểm |
| Time-only recurring schedule | Không giả định có instant |
| Negative/large years | Range DBMS có thể giới hạn |

Khi chạy test, ghi **JDK version, DB product/version, JDBC driver/version, connection/session timezone, schema column type/scale, Java input, Java returned value và SQLState** nếu có lỗi. Metadata có thể hữu ích nhưng một thử nghiệm roundtrip mới là bằng chứng chính xác cho combo deployment.

## 16. Các sai lầm thường gặp

**1. Coi OffsetTime là timestamp event.** Nó thiếu ngày.

**2. Nhầm OffsetDateTime với ZonedDateTime.** Offset không chứa tên vùng hoặc quy tắc DST.

**3. Cho rằng WITH TIME ZONE luôn giữ original offset.** PostgreSQL timestamp-with-zone chuẩn hóa UTC.

**4. So equals khi chỉ cần so instant.** Dùng `toInstant` hoặc `isEqual`.

**5. Tin JDBC enum đồng nghĩa mọi DBMS/driver hỗ trợ.** Phải test actual mapping.

**6. Dùng getObject không có Class rồi cast bừa.** Có driver trả vendor type.

**7. Bỏ qua SQLException/SQLFeatureNotSupportedException.** Không được đánh dấu “đã lưu”.

**8. Fallback âm thầm OffsetDateTime→LocalDateTime.** Có thể làm mất instant.

**9. Chuyển OffsetTime thành java.sql.Time rồi tin offset vẫn còn.** Time không giữ offset.

**10. Không kiểm target SQL column type.** Driver có thể conversion khác mong muốn.

**11. Dùng MySQL DATETIME như instant.** Nó là local date/time.

**12. Quên MySQL session timezone hoặc Connector/J preserveInstants.** Có thể lệch instant.

**13. Tin Oracle LOCAL TIME ZONE giữ offset gốc.** Nó không giữ.

**14. Tin SQL Server datetimeoffset tự map Java OffsetDateTime qua mọi driver.** Cần kiểm.

**15. Dùng PostgreSQL timetz để lưu lịch giờ theo DST.** Không có ngày/region.

**16. Không test fractional second precision.** 9 digit của Java không tự có trong DB.

**17. Dựa vào String hiển thị khi session TZ khác.** Cùng instant có nhiều chuỗi.

**18. Không xử lý SQL NULL.** Typed getObject có thể null.

**19. Dựa duy nhất vào getTypeInfo.** Metadata không chứng minh conversion.

**20. Chỉ test offset +00:00.** Dễ bỏ sót lỗi đổi zone.

**21. Không test thời gian giao ngày.** Đổi +14 sang UTC có thể đổi ngày.

**22. Không test DST gap/overlap.** Không phải mọi local time đều có instant duy nhất.

**23. Không lưu ZoneId khi nghiệp vụ cần timezone region.** Offset không thể tái tạo vùng.

**24. Không ghi driver version trong bug report.** Khó tái hiện.

**25. Lẫn transaction failure và convert failure.** Cần rollback/đọc lỗi SQL.

## Tổng kết

`OffsetTime` là giờ kèm fixed UTC offset **không có ngày**; `OffsetDateTime` có ngày và xác định một instant. JDBC 4.2 định nghĩa `TIME_WITH_TIMEZONE (2013)` và `TIMESTAMP_WITH_TIMEZONE (2014)`, nhưng một API Java hợp lệ **không đảm bảo driver/database chấp nhận hoặc giữ offset gốc**. PostgreSQL timestamptz giữ instant nhưng chuẩn hóa UTC, MySQL TIMESTAMP chịu timezone conversion, Oracle có khác biệt WITH/LOCAL, SQL Server có datetimeoffset và vendor JDBC mapping. Hãy chọn invariant nghiệp vụ — instant, original offset, local fields hay ZoneId — rồi thiết kế schema và **test roundtrip trên DB/driver thật**, bao gồm precision, SQL NULL, session timezone và DST.
