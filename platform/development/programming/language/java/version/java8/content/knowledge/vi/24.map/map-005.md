# computeIfAbsent và tạo giá trị theo nhu cầu trong Map (Java 8)

Khi một ứng dụng sử dụng `Map<K,V>` để gom dữ liệu, lưu bộ đếm hoặc cache, thường có một nhu cầu rất cụ thể: **chỉ tạo giá trị khi khóa chưa có giá trị sử dụng được**. Ví dụ, chỉ tạo `ArrayList` khi phòng ban xuất hiện lần đầu, chỉ nạp cấu hình khi chưa có trong cache, hoặc chỉ dựng bộ đếm cho một loại giao dịch khi lần đầu ghi nhận loại đó.

Từ Java 8, `Map.computeIfAbsent(key, mappingFunction)` diễn đạt trực tiếp nhu cầu đó. Tuy nhiên, muốn dùng đúng cần hiểu sự khác nhau giữa **khóa không tồn tại**, **khóa đã có nhưng value bằng null**, **callback trả null**, **callback ném exception**, và tính đồng thời của từng implementation Map. `computeIfAbsent` không phải phép màu giúp mọi Map trở thành thread-safe hay tự biến nó thành cache có thời hạn.

Bài học thuộc chủ đề **Map**, dùng các API từ Java 8 **vẫn còn áp dụng trong Java hiện hành**. Các chương trình độc lập đều có thể biên dịch với `javac --release 8` và có stdout được kiểm chứng.

## 1. Mục đích của computeIfAbsent

Cách tạo giá trị thủ công:

```java
// Đoạn minh họa; giả sử cache là Map<String, Config>
// và loadConfig(String) do ứng dụng tự định nghĩa.
Config config = cache.get(key);
if (config == null) {
    config = loadConfig(key);
    if (config != null) {
        cache.put(key, config);
    }
}
```

Cách dùng Java 8:

```java
// Cùng ngữ cảnh với đoạn trên, không phải chương trình độc lập.
Config config = cache.computeIfAbsent(
    key, k -> loadConfig(k));
```

Cả hai đều có mục tiêu "nếu chưa có giá trị khác null thì tính và lưu kết quả khác null". Cách thứ hai ngắn gọn và biểu đạt rõ **lazy value initialization**: không chạy `loadConfig` khi key đã có giá trị non-null.

Nhưng **tính atomic của hai cách không giống nhau ở mọi loại Map**. Với `HashMap` bình thường, `computeIfAbsent` không mặc định bảo đảm an toàn khi nhiều luồng cùng thay đổi Map. Với `ConcurrentHashMap`, phương thức được ghi đè để có hợp đồng atomic riêng. Ta sẽ phân biệt ở mục concurrency.

### Giải thích chữ ký

```java
// Chữ ký khái quát từ Map API Java 8, không phải tệp Java độc lập:
default V computeIfAbsent(
    K key,
    Function<? super K, ? extends V> mappingFunction);
```

- `key`: khóa muốn tìm hoặc khởi tạo value.
- `mappingFunction`: hàm nhận chính key đó và tạo ra một value.
- Kết quả: value hiện tại nếu khác null, hoặc value mới được tạo; có thể là null nếu callback trả null.
- Callback chỉ được dùng khi **không có mapping tới một giá trị non-null**.

Đây là hành vi của "compute **if absent**", không phải "compute every time". Nếu muốn cập nhật giá trị đang tồn tại hoặc gộp hai giá trị, có các phương thức `compute`, `computeIfPresent` và `merge` với hợp đồng khác.

## 2. Bốn trạng thái phải phân biệt

| Trạng thái trước gọi | Có gọi mappingFunction? | Giá trị callback trả | Kết quả |
| --- | --- | --- | --- |
| Không có key | Có | Value khác null | Lưu key → value, trả value |
| Key có value khác null | **Không** | Không được tính | Giữ nguyên mapping, trả value cũ |
| Key có value null, Map cho phép null | **Có** | Value khác null | Thay null bằng value mới, trả value mới |
| Chưa có value khác null | Có | Null | Không lưu giá trị mới khác null, trả null |

Với `Map` default method, có thể hình dung như sau:

```java
// GIẢ MÃ để hiểu semantics; không tự sử dụng làm giải pháp concurrent.
V oldValue = map.get(key);
if (oldValue == null) {
    V newValue = mappingFunction.apply(key);
    if (newValue != null) {
        map.put(key, newValue);
    }
    return newValue;
}
return oldValue;
```

Những điểm không thể bỏ qua:

1. **`containsKey(key)` không phải điều kiện duy nhất.** `HashMap` có thể chứa `key → null`; lúc đó `containsKey` trả true, nhưng `computeIfAbsent` vẫn tính lại.
2. **Null từ callback không được lưu như một mapping mới.** Nếu key chưa tồn tại, sau lời gọi key vẫn không tồn tại. Nếu đang có key → null, callback trả null không biến null thành giá trị sử dụng được.
3. **Callback ném exception:** exception được truyền ra; phương thức không thêm mapping mới vì callback đó. Side effect mà callback đã làm với hệ thống bên ngoài không tự rollback.
4. **Trạng thái sau lần tính ảnh hưởng lần sau.** Một callback trả null hoặc ném lỗi có thể được gọi lại ở lần truy vấn kế tiếp; value được xóa khỏi Map cũng có thể được tính lại.

Vì thế, `computeIfAbsent` không thể dùng một mình để bảo đảm "một tác vụ bên ngoài chỉ chạy đúng một lần trong suốt vòng đời hệ thống".

## 3. So sánh với getOrDefault, putIfAbsent, compute và merge

Giả sử `makeValue()` là phương thức nặng, có thể gọi database hoặc tạo một đồ thị object.

```java
// Mã minh họa; Map và hàm makeValue() được định nghĩa bên ngoài.
V a = map.getOrDefault(key, makeValue());
V b = map.putIfAbsent(key, makeValue());
V c = map.computeIfAbsent(key, k -> makeValue());
```

**Sự khác nhau ở thời điểm đánh giá:**

- `getOrDefault(key, makeValue())` đánh giá `makeValue()` **trước khi** phương thức `getOrDefault` được gọi. Nếu key đã có value, việc tạo giá trị có thể bị lãng phí. `getOrDefault` không tự lưu default vào Map.
- `putIfAbsent(key, makeValue())` cũng nhận một đối số đã được đánh giá. Nó có thể ghi Map theo điều kiện "chưa có value khác null", nhưng giá trị mặc định vẫn được tính sớm. Ngoài ra, phương thức trả **giá trị trước thao tác**, không phải value mới.
- `computeIfAbsent(key, k -> makeValue())` nhận một Function, nên nếu key có value non-null, callback **không chạy**. Phương thức trả value có thể dùng được (cũ hoặc mới).

| API | Có thể tạo value thừa nếu key đã có? | Có thay đổi Map? | Dùng khi nào |
| --- | --- | --- | --- |
| `get(key)` | Không có hàm tạo | Không | Chỉ đọc |
| `getOrDefault(key, defaultValue)` | Có nếu `defaultValue` là kết quả gọi hàm | Không | Trả một giá trị mặc định đã có |
| `putIfAbsent(key, value)` | Có nếu phải tính đối số value | Có | Đặt value đã tính sẵn khi cần |
| `computeIfAbsent(key, fn)` | Không đối với key đã có value non-null | Có nếu callback trả non-null | Tạo/lưu value theo nhu cầu |
| `computeIfPresent(key, fn)` | Callback chỉ chạy khi key có value non-null | Có thể cập nhật/xóa | Chuyển đổi value đang có |
| `compute(key, fn)` | Callback nhận key và value hiện có/có thể null | Có thể thêm/cập nhật/xóa | Tính lại dựa trên trạng thái cũ |
| `merge(key, value, fn)` | Callback gộp khi đã có value | Có thể thêm/cập nhật/xóa | Gộp dữ liệu mới vào value cũ |

`computeIfAbsent` trả value **sau khi bảo đảm có thể sử dụng kết quả**, còn `putIfAbsent` trả value **cũ**. Việc nhầm hai kiểu trả về có thể tạo lỗi logic tinh vi khi code dùng ngay giá trị kết quả.

## 4. Ví dụ hoàn chỉnh: lazy, null, exception và eager argument

Tệp **`ComputeIfAbsentCoreDemo.java`** sử dụng `LinkedHashMap` để thứ tự key khi in được xác định và dùng bộ đếm test để kiểm tra callback có thực sự được bỏ qua khi key đã có value.

```java
import java.util.*;
import java.util.concurrent.atomic.AtomicInteger;

public class ComputeIfAbsentCoreDemo {
    static void check(boolean pass, String name) {
        if (!pass) throw new AssertionError(name);
    }

    public static void main(String[] args) {
        Map<String, String> cache = new LinkedHashMap<>();
        AtomicInteger factoryCalls = new AtomicInteger();

        String first = cache.computeIfAbsent("city", key -> {
            factoryCalls.incrementAndGet();
            return key.toUpperCase(Locale.ROOT);
        });

        String second = cache.computeIfAbsent("city", key -> {
            factoryCalls.incrementAndGet();
            return "WRONG";
        });

        check(first.equals("CITY") && second.equals("CITY"),
              "same value");
        check(factoryCalls.get() == 1,
              "factory on present key");

        cache.put("existingNull", null);
        check(cache.containsKey("existingNull"),
              "null key must exist");

        String restored = cache.computeIfAbsent(
            "existingNull", key -> "RECOVERED");
        check("RECOVERED".equals(restored),
              "treat mapped null as absent");

        String missing = cache.computeIfAbsent(
            "missing", key -> null);
        check(missing == null && !cache.containsKey("missing"),
              "null mapping result must not insert");

        boolean thrown = false;
        try {
            cache.computeIfAbsent("failed", key -> {
                throw new IllegalArgumentException("load failed");
            });
        } catch (IllegalArgumentException ex) {
            thrown = "load failed".equals(ex.getMessage());
        }
        check(thrown && !cache.containsKey("failed"),
              "exception propagates without insertion");

        AtomicInteger eagerCalls = new AtomicInteger();
        cache.putIfAbsent("city", expensive(eagerCalls));
        cache.computeIfAbsent(
            "city", key -> expensive(eagerCalls));
        check(eagerCalls.get() == 1,
              "putIfAbsent eager argument");

        System.out.println(
            "first=" + first + ", second=" + second);
        System.out.println(
            "factoryCalls=" + factoryCalls.get());
        System.out.println("restored=" + restored);
        System.out.println(
            "missingStored=" + cache.containsKey("missing"));
        System.out.println("exceptionCaught=" + thrown);
        System.out.println(
            "eagerCalls=" + eagerCalls.get());
        System.out.println("cache=" + cache);
        System.out.println("PASS");
    }

    static String expensive(AtomicInteger calls) {
        calls.incrementAndGet();
        return "EXPENSIVE";
    }
}
```

Biên dịch và chạy:

```bash
javac -encoding UTF-8 ComputeIfAbsentCoreDemo.java
java ComputeIfAbsentCoreDemo
```

Kết quả chính xác:

```text
first=CITY, second=CITY
factoryCalls=1
restored=RECOVERED
missingStored=false
exceptionCaught=true
eagerCalls=1
cache={city=CITY, existingNull=RECOVERED}
PASS
```

### Phân tích từng assertion

- `first` và `second` đều là `CITY`, nhưng `factoryCalls=1`. Callback của lần thứ hai không chạy, cho thấy tính lazy khi key có non-null value.
- `existingNull` đã có trong `LinkedHashMap` với value null. Lời gọi `computeIfAbsent` vẫn tính lại và lưu `RECOVERED`.
- Callback cho `missing` trả null, nên không tạo key mới: `missingStored=false`. Gọi lại callback trên key đó trong tương lai vẫn có thể được thực hiện.
- Callback cho `failed` ném `IllegalArgumentException`. Test xác nhận exception và không có key mới trong Map.
- `putIfAbsent("city", expensive(...))` đã tính expensive dù key có value; `computeIfAbsent("city", key -> expensive(...))` bỏ qua callback. Vì vậy bộ đếm eager chỉ tăng một lần.

`AtomicInteger` ở đây dùng để quan sát số lần gọi trong test; **không** biến `LinkedHashMap` thành thread-safe. Trong code thật, chỉ đưa Map này vào những chỗ có quy tắc đồng bộ/ownership đúng.

## 5. Khóa tồn tại nhưng value null: tại sao dễ sai?

Với `HashMap` và `LinkedHashMap`, hai phép hỏi sau có thể khác nhau:

```java
// Mã minh họa độc lập khi đặt trong một phương thức.
Map<String, String> values = new HashMap<>();
values.put("A", null);

System.out.println(values.get("A"));          // null
System.out.println(values.containsKey("A"));  // true
System.out.println(values.get("B"));          // null
System.out.println(values.containsKey("B"));  // false
```

Trong trường hợp A, key có mapping null; trong trường hợp B, key chưa tồn tại. `get` không phân biệt hai trường hợp, còn `containsKey` phân biệt được.

Tuy nhiên, `computeIfAbsent` **đều xem cả hai là chưa có một value non-null** và gọi mappingFunction. Kết quả sau đó phụ thuộc callback:

- Callback trả non-null: value mới được lưu cho key.
- Callback trả null khi key B chưa tồn tại: B vẫn không có mapping.
- Callback trả null khi key A có null: không có value khác null mới được lưu; mapping null cũ không tự trở thành một giá trị hợp lệ.
- Callback ném exception: exception được truyền ra; thao tác không tự cung cấp value thay thế.

**Map khác nhau, chính sách null khác nhau:** `ConcurrentHashMap` không cho phép key null hoặc value null. Không suy diễn từ `HashMap` rằng mọi lớp Map đều chứa được null.

Nếu nhu cầu là "đã kiểm tra nhưng không tìm thấy dữ liệu", lưu null thường không phù hợp với computeIfAbsent vì lần sau vẫn tính lại. Có thể lưu một object khác null biểu diễn kết quả không tìm thấy, ví dụ `Optional.empty()`, với chính sách hết hạn rõ ràng.

## 6. Ứng dụng thực tế: khởi tạo List theo nhóm đúng lúc

Một ứng dụng thường nhận các bản ghi:

```text
Books → Java
Games → Chess
Books → Kotlin
Books → Java
```

Mục tiêu là:

```text
Books → [Java, Kotlin, Java]
Games → [Chess]
```

Cách dùng `computeIfAbsent`:

```java
// Mã minh họa, giả sử items là Iterable<Item>
// và Item có trường department và name.
Map<String, List<String>> groups = new LinkedHashMap<>();

for (Item item : items) {
    groups.computeIfAbsent(
        item.department, key -> new ArrayList<>()
    ).add(item.name);
}
```

Giải thích:

1. Với Books lần đầu, Map chưa có value → tạo một `ArrayList` mới và đặt vào key Books.
2. Với Games lần đầu, tạo một `ArrayList` khác.
3. Khi Books xuất hiện lần nữa, lấy **chính List đã có**, rồi thêm Kotlin hoặc Java.
4. `ArrayList` giữ thứ tự chèn, không tự loại trùng. `LinkedHashMap` giữ thứ tự gặp lần đầu của các key.
5. Mỗi key có List riêng, vì lambda `key -> new ArrayList<>()` tạo instance mới khi cần.

Nếu muốn nhóm theo key rồi đếm/tính tổng bằng Stream, `Collectors.groupingBy(..., downstream)` cũng là một lựa chọn phù hợp. Nhưng trong một vòng lặp cập nhật thủ công, `computeIfAbsent` là cách diễn đạt thuận tiện và rõ ràng. Không buộc mọi trường hợp phải dùng Stream hoặc mọi trường hợp phải dùng computeIfAbsent.

**Điểm cần nhớ:** `Map<K, List<V>>` với `computeIfAbsent` chỉ là một dạng **multimap đơn giản tự xây**. Java không tự biến nó thành kiểu dữ liệu có đồng bộ, deduplication, eviction hoặc hợp đồng bất biến.

## 7. Ví dụ hoàn chỉnh: tạo nhóm và cache kết quả không tìm thấy

Tệp **`MultimapAndNegativeCacheDemo.java`** minh họa cả multimap và một kỹ thuật cache có chủ đích: lưu `Optional.empty()` **như một value khác null**, để một key đã kiểm tra nhưng không có kết quả không bị nạp lại vô ích.

```java
import java.util.*;
import java.util.concurrent.atomic.AtomicInteger;
import java.util.function.Function;

public class MultimapAndNegativeCacheDemo {
    static final class Item {
        final String department;
        final String name;

        Item(String department, String name) {
            this.department = department;
            this.name = name;
        }
    }

    static void check(boolean pass, String label) {
        if (!pass) throw new AssertionError(label);
    }

    public static void main(String[] args) {
        List<Item> data = Arrays.asList(
            new Item("Books", "Java"),
            new Item("Games", "Chess"),
            new Item("Books", "Kotlin"),
            new Item("Books", "Java")
        );

        Map<String, List<String>> groups = new LinkedHashMap<>();

        for (Item item : data) {
            groups.computeIfAbsent(
                item.department, key -> new ArrayList<>())
                .add(item.name);
        }

        check(groups.get("Books").equals(
            Arrays.asList("Java", "Kotlin", "Java")),
            "keeps duplicates and insertion order");

        AtomicInteger dbCalls = new AtomicInteger();
        Map<String, Optional<String>> lookup =
            new LinkedHashMap<>();

        Function<String, Optional<String>> loader = key -> {
            dbCalls.incrementAndGet();
            return "found".equals(key)
                ? Optional.of("VALUE")
                : Optional.empty();
        };

        Optional<String> missing1 =
            lookup.computeIfAbsent("missing", loader);
        Optional<String> missing2 =
            lookup.computeIfAbsent("missing", loader);
        Optional<String> present1 =
            lookup.computeIfAbsent("found", loader);
        Optional<String> present2 =
            lookup.computeIfAbsent("found", loader);

        check(!missing1.isPresent() && !missing2.isPresent(),
              "cache known absence");
        check(present1.equals(Optional.of("VALUE"))
              && present2.equals(present1),
              "cache value");
        check(dbCalls.get() == 2,
              "one load per key");

        System.out.println("groups=" + groups);
        System.out.println("lookup=" + lookup);
        System.out.println("dbCalls=" + dbCalls.get());
        System.out.println("PASS");
    }
}
```

```bash
javac -encoding UTF-8 MultimapAndNegativeCacheDemo.java
java MultimapAndNegativeCacheDemo
```

Stdout:

```text
groups={Books=[Java, Kotlin, Java], Games=[Chess]}
lookup={missing=Optional.empty, found=Optional[VALUE]}
dbCalls=2
PASS
```

Tại sao có bốn lời gọi `computeIfAbsent` cho cache nhưng chỉ hai lần nạp?

- Key missing: loader trả `Optional.empty()`. Đây là **value hợp lệ không-null**, nên được lưu vào Map.
- Lần thứ hai hỏi missing: Map đã có Optional rỗng, callback **không chạy lại**.
- Key found: loader trả `Optional.of("VALUE")`, được lưu.
- Lần hỏi found thứ hai: callback bị bỏ qua.

Kỹ thuật này gọi là **negative caching**: cache kết quả "không tìm thấy". Nó chỉ hợp lý khi nghiệp vụ cho phép ghi nhớ absence. Nếu dữ liệu có thể được thêm vào hệ thống sau đó, kết quả empty được cache có thể trở nên lỗi thời. Cần có chính sách xóa, hết hạn hoặc làm mới phù hợp.

`Optional` ở đây được dùng có chủ đích làm value của một Map để ghi nhớ cả kết quả âm. Không có nghĩa mọi field domain, parameter hoặc bản ghi serialized đều nên trở thành `Optional`. Ngoài ra, cache có giới hạn bộ nhớ, TTL, eviction và kiểm soát tải cần một thiết kế bổ sung; `computeIfAbsent` **không tự cung cấp** những tính năng đó.

## 8. mappingFunction nên được thiết kế như thế nào?

Hàm truyền vào `computeIfAbsent` ảnh hưởng không chỉ kết quả mà còn hiệu năng và concurrency.

**Nên:**

- Tạo ra **một value cụ thể từ key**, ví dụ `k -> new ArrayList<>()`, `k -> new LongAdder()` hoặc `k -> loadConfig(k)`.
- Trả **non-null** nếu muốn Map ghi nhớ kết quả.
- Dùng hàm tính ngắn, ít side effect, không phụ thuộc vào trạng thái Map đang được sửa trong callback.
- Trả object mới riêng cho mỗi key nếu value là cấu trúc mutable độc lập.
- Xác định rõ exception nào có thể phát sinh; đừng coi mọi lỗi loader là dữ liệu không tồn tại.
- Khi dùng ConcurrentHashMap, tránh cập nhật đệ quy chính Map từ mappingFunction.

**Không nên:**

- Trả về một `ArrayList` dùng chung cho mọi key nếu các nhóm phải độc lập.
- Dùng callback để gửi email, ghi database hoặc tạo file và mong mọi side effect được rollback nếu sau đó có lỗi.
- Đưa hàm có thời gian chờ I/O không giới hạn vào nơi các thao tác cập nhật concurrent có thể phải chặn.
- Dùng `null` làm sentinel cho "đã kiểm tra" nhưng lại kỳ vọng Map sẽ cache nó thành kết quả mới.
- Gọi `computeIfAbsent` trên cùng một Map một cách đệ quy để tạo các key phụ thuộc vòng, đặc biệt với ConcurrentHashMap.
- Dựa vào việc callback "sẽ chạy đúng một lần suốt đời ứng dụng". Tính lại vẫn có thể xảy ra nếu key bị xóa hoặc lần trước không có value được lưu.

Một value mutable sau khi được Map lưu vẫn có thể bị thay đổi: việc bảo toàn quy tắc nghiệp vụ và thread-safety của **value** là trách nhiệm riêng, không được Map tự xử lý.

## 9. ConcurrentHashMap: atomic mapping không có nghĩa mọi value đều thread-safe

Phương thức `Map.computeIfAbsent` mặc định **không có bảo đảm synchronization hoặc atomicity** cho mọi implementation. Trong môi trường đa luồng, đừng chia sẻ `HashMap` để nhiều thread sửa cùng lúc chỉ vì đã chuyển sang dùng computeIfAbsent.

`ConcurrentHashMap<K,V>` có implementation computeIfAbsent riêng, với hợp đồng **atomic** cho thao tác thiết lập mapping. Khi key chưa có mapping và hàm tạo trả non-null, ConcurrentHashMap phối hợp để tạo mapping đúng hợp đồng và không để các thread tự do thay thế kết quả theo kiểu get/put không đồng bộ.

Tuy nhiên, cần phân biệt hai lớp:

1. **Lớp Map**: việc tìm hoặc khởi tạo value theo key là một thao tác atomic theo hợp đồng ConcurrentHashMap.
2. **Lớp value**: nếu value là một object mutable dùng chung, mọi cập nhật nội bộ vào object đó vẫn phải thread-safe hoặc được đồng bộ đúng cách.

Ví dụ **nguy hiểm**:

```java
// Mã phản ví dụ: không dùng trong code nhiều writer đồng thời.
ConcurrentHashMap<String, List<String>> groups =
    new ConcurrentHashMap<>();

// Nhiều thread cùng thêm vào List có thể mất cập nhật.
groups.computeIfAbsent(
    "team", k -> new ArrayList<>()).add("member");
```

`ArrayList.add` không an toàn khi nhiều thread đồng thời ghi vào **cùng ArrayList**, dù List được lấy từ một ConcurrentHashMap. Việc map có atomic không làm thao tác add trên List atomic.

Các giải pháp hợp lệ theo mục tiêu:

- Đếm nhiều cập nhật: `ConcurrentHashMap<K, LongAdder>` và `computeIfAbsent(k, x -> new LongAdder()).increment()`.
- Thu tập giá trị phân biệt nhiều writer: `ConcurrentHashMap<K, Set<V>>` và khởi tạo bằng `ConcurrentHashMap.newKeySet()` trong Java 8.
- Thu danh sách có thứ tự: cần cấu trúc dữ liệu/chiến lược phối hợp khác theo hợp đồng thứ tự; không tự giả định việc thêm concurrent giữ đúng encounter order.
- Các thao tác update gồm nhiều bước: xác định atomicity cho **toàn nghiệp vụ**, không chỉ cho việc khởi tạo key.

**LongAdder.sum() không phải snapshot atomic trong lúc các thread đang ghi.** Nếu cần kiểm tra tổng chính xác sau một batch, hãy đợi tất cả thao tác cập nhật hoàn thành rồi đọc sum.

### Callback có thể chặn và cập nhật đệ quy

Tài liệu `ConcurrentHashMap.computeIfAbsent` yêu cầu callback tính toán ngắn, đơn giản và không cố cập nhật các mapping khác trong cùng Map. Trong thời gian computation diễn ra, một số cập nhật khác có thể bị chặn. Callback nặng, đợi I/O hoặc lấy khóa theo thứ tự phức tạp có thể gây tranh chấp hoặc bế tắc.

Một cập nhật đệ quy vào cùng Map trong callback có thể ném `IllegalStateException` nếu phát hiện tình huống không thể hoàn thành. Tránh:

```java
// Mã phản ví dụ, đừng dùng để quản lý dependencies:
cache.computeIfAbsent("A", key -> {
    cache.computeIfAbsent("B", other -> createB());
    return createA();
});
```

Hãy tách các giai đoạn xây dựng dependency hoặc dùng chiến lược caching/loading riêng. Đừng dùng computeIfAbsent để thay thế transaction, cơ chế điều phối tác vụ hay đồ thị phụ thuộc đệ quy.

## 10. Ví dụ hoàn chỉnh: đếm và thu tập hợp đồng thời

Tệp **`ConcurrentMapComputeDemo.java`** kiểm tra ba hành vi:

1. `LongAdder` đếm 5.000 số chẵn và 5.000 số lẻ trên một IntStream parallel.
2. `ConcurrentHashMap.newKeySet()` thu 500 số chẵn và 500 số lẻ không trùng vào hai Set concurrent.
3. Hai mươi tác vụ cùng hỏi một key chung và nhận cùng kết quả, callback tạo value non-null được gọi một lần theo hợp đồng ConcurrentHashMap trong kịch bản không xóa key.

```java
import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.*;
import java.util.stream.*;

public class ConcurrentMapComputeDemo {
    static void check(boolean ok, String label) {
        if (!ok) throw new AssertionError(label);
    }

    public static void main(String[] args) throws Exception {
        ConcurrentHashMap<String, LongAdder> counts =
            new ConcurrentHashMap<>();

        IntStream.range(0, 10000).parallel().forEach(i -> {
            String key = (i % 2 == 0) ? "even" : "odd";
            counts.computeIfAbsent(
                key, k -> new LongAdder()).increment();
        });

        long even = counts.get("even").sum();
        long odd = counts.get("odd").sum();
        check(even == 5000 && odd == 5000,
              "thread safe counts");

        ConcurrentHashMap<String, Set<Integer>> groups =
            new ConcurrentHashMap<>();

        IntStream.range(0, 1000).parallel().forEach(i -> {
            String key = (i % 2 == 0) ? "even" : "odd";
            groups.computeIfAbsent(
                key,
                k -> ConcurrentHashMap.<Integer>newKeySet()
            ).add(i);
        });

        check(groups.get("even").size() == 500
              && groups.get("odd").size() == 500,
              "concurrent set values");

        ConcurrentHashMap<String, String> cache =
            new ConcurrentHashMap<>();
        AtomicInteger loads = new AtomicInteger();

        ExecutorService executor =
            Executors.newFixedThreadPool(4);
        CountDownLatch start = new CountDownLatch(1);
        List<Future<String>> tasks = new ArrayList<>();

        try {
            for (int i = 0; i < 20; i++) {
                tasks.add(executor.submit(() -> {
                    start.await();
                    return cache.computeIfAbsent(
                        "shared", key -> {
                            loads.incrementAndGet();
                            return "READY";
                        });
                }));
            }

            start.countDown();
            for (Future<String> task : tasks) {
                check("READY".equals(task.get()),
                      "shared result");
            }
        } finally {
            start.countDown();
            executor.shutdown();
        }

        check(loads.get() == 1,
              "factory once for one key");

        System.out.println(
            "even=" + even + ", odd=" + odd);
        System.out.println(
            "groupSizes=" + groups.get("even").size()
            + "/" + groups.get("odd").size());
        System.out.println(
            "shared=" + cache.get("shared")
            + ", loadCalls=" + loads.get());
        System.out.println("PASS");
    }
}
```

```bash
javac -encoding UTF-8 ConcurrentMapComputeDemo.java
java ConcurrentMapComputeDemo
```

Kết quả đã kiểm chứng:

```text
even=5000, odd=5000
groupSizes=500/500
shared=READY, loadCalls=1
PASS
```

**Vì sao kết quả đúng?**

- `LongAdder.increment()` được thiết kế cho nhiều cập nhật đồng thời; sau khi `forEach` kết thúc, ta mới đọc `sum()`.
- Value `Set` do `ConcurrentHashMap.newKeySet()` tạo hỗ trợ thêm phần tử đồng thời; không kiểm tra thứ tự khi in vì Set không cam kết thứ tự.
- Các tác vụ `ExecutorService` cùng gọi computeIfAbsent cho key `shared`. Callback trả non-null, không có tác vụ xóa key, nên một lần khởi tạo mapping được chia sẻ. `Future.get()` đợi task hoàn tất.
- `CountDownLatch` chỉ giúp các task có thể bắt đầu gần nhau để test concurrency; điều bảo vệ chính là hợp đồng ConcurrentHashMap chứ không phải bản thân latch.
- Đây là test chức năng, không phải benchmark chứng minh parallel Stream nhanh hơn. Hiệu năng cần đo trên workload thật.

## 11. Cẩn thận với cache có I/O, TTL và ngoại lệ

`computeIfAbsent` là một phép khởi tạo value theo key, **không phải hệ thống cache có vòng đời hoàn chỉnh**.

Khi dùng nó để tải dữ liệu từ database hoặc service, đặt thêm các câu hỏi:

- **Thời hạn hiệu lực:** value có thể trở nên cũ sau bao lâu? Map thường không tự hết hạn.
- **Chính sách loại bỏ:** cache vô hạn có thể sử dụng quá nhiều bộ nhớ.
- **Negative caching:** có nên nhớ kết quả không tìm thấy? Nếu có, trong bao lâu?
- **Retry:** nếu loader trả null hoặc ném exception, lần gọi sau có được phép thử lại không? Có cần backoff?
- **Idempotency:** nếu loader gây side effect trước khi lỗi, thực thi lại có an toàn không?
- **Cancellation/timeout:** nếu load bị kẹt, request nào phải đợi và có cách hủy an toàn không?
- **Multi-instance:** Map nằm trong JVM này không tự chia sẻ cache với các JVM/service khác.
- **Đồng bộ:** cần khóa theo key, toàn Map, hay phối hợp Future cho các phép nạp nặng và kéo dài?
- **Lỗi nghiệp vụ so với lỗi hạ tầng:** "không có dữ liệu" khác "database không kết nối"; không nên nuốt mọi exception rồi ghi Optional.empty.

Nếu các vấn đề trên là yêu cầu thiết yếu, cân nhắc giải pháp caching có TTL/eviction/loading policy thay vì tự xây mọi thứ chỉ bằng computeIfAbsent. Không diễn giải "cache hit" như một lời hứa dữ liệu luôn mới.

## 12. Kiểm thử computeIfAbsent như thế nào cho đủ?

Một bộ kiểm thử tốt phải có cả **kết quả** và **số lần gọi callback** khi số lần gọi thuộc hợp đồng cần xác minh.

| Case | Trạng thái ban đầu | Mapping function | Kết quả mong đợi |
| --- | --- | --- | --- |
| Key chưa có | Map rỗng | Trả `NEW` | Map có key → NEW |
| Key đã có | Key → `OLD` | Đếm lời gọi | Trả OLD; callback 0 lần |
| Key có value null | HashMap cho phép null | Trả NEW | Trả NEW và thay null |
| Callback trả null | Key chưa có | `k -> null` | Trả null; không chèn key |
| Callback trả null khi key có null | Key → null | `k -> null` | Không tạo value mới |
| Callback ném exception | Key chưa có | Throw IllegalArgumentException | Exception truyền ra; không chèn key |
| Key nhiều giá trị | Group có sẵn List | Tạo new ArrayList | Callback không chạy; List cũ nhận thêm item |
| Nhiều key | Map rỗng | Tạo List riêng | Các key không dùng chung instance |
| Negative cache | Map<K,Optional<V>> | Trả Optional.empty | Lưu empty như value non-null |
| Concurrent cùng key | ConcurrentHashMap rỗng | Trả non-null | Giá trị được khởi tạo atomic |
| Concurrent nhóm mutable | ConcurrentHashMap | Tạo Set concurrent | Không mất cập nhật vào value |
| Cache bị xóa | Key có rồi bị remove | Trả non-null | Khi hỏi lại, có thể tạo mới |
| Value null trong CHM | ConcurrentHashMap | Không áp dụng | CHM từ chối key/value null |
| Callback tạo chậm | ConcurrentHashMap | Chờ I/O | Không giả định throughput cao; đo tranh chấp |

### Assertions cần kiểm rõ

Một phép test tốt cho lazy creation nên kiểm tra:

```java
// Minh họa, cache là Map<String, String> rỗng.
AtomicInteger calls = new AtomicInteger();
String value = cache.computeIfAbsent("k", k -> {
    calls.incrementAndGet();
    return "V";
});
String again = cache.computeIfAbsent("k", k -> {
    calls.incrementAndGet();
    return "OTHER";
});

// Hợp đồng: value và again đều bằng "V", calls bằng 1.
```

**Không chỉ assert Map chứa đúng một key.** Một implementation sai có thể tính value lần thứ hai rồi bỏ kết quả, khiến Map vẫn đúng về dữ liệu nhưng đã tiêu tốn chi phí tạo.

Đối với Map đồng thời, tránh kiểm thử theo thứ tự chạy thread; nên kiểm kết quả ổn định sau khi các tác vụ kết thúc. Đối với `HashMap`, không assert thứ tự in qua `toString()`; dùng các phép đọc theo key, `Map.equals` hoặc collection equality.

Nếu dùng JUnit ở dự án thật, chuyển các case thành test độc lập hoặc parameterized tests. Các chương trình Java thuần trong bài cố ý dùng `AssertionError` để có thể chạy không cần thư viện ngoài.

## 13. Các lỗi phổ biến

| Sai lầm | Vì sao sai | Giải pháp |
| --- | --- | --- |
| `putIfAbsent(k, expensive())` được cho là lazy | Hàm expensive đã được tính trước lời gọi | `computeIfAbsent(k, x -> expensive())` |
| Nghĩ key tồn tại thì callback không chạy | Map có thể lưu key → null | Kiểm tra điều kiện non-null value |
| Mapping function trả null để "cache không tìm thấy" | Null không được chèn thành mapping mới | Lưu result non-null có nghĩa và TTL phù hợp |
| Dùng `getOrDefault(k, make())` để lưu cache | Không lưu default vào Map, vẫn tính đối số | Dùng computeIfAbsent |
| Dùng shared ArrayList làm value cho nhiều key | Nhóm bị trộn dữ liệu | Khởi tạo instance riêng cho mỗi key |
| HashMap dùng chung cho nhiều writer | Default computeIfAbsent không atomic | Dùng ConcurrentHashMap hoặc đồng bộ đúng |
| ConcurrentHashMap + mutable ArrayList nhiều writer | Map an toàn, ArrayList không an toàn | Dùng value concurrent hoặc khóa bảo vệ riêng |
| Callback cập nhật đệ quy cùng CHM | Có thể vi phạm hợp đồng, ném lỗi/chặn | Tách dependency computation khỏi callback |
| Callback chờ I/O rất lâu | Các cập nhật khác có thể bị chặn | Cân nhắc cache loader, async design và timeout |
| Callback ném lỗi rồi nghĩ mọi side effect được rollback | Map không phải transaction | Thiết kế lỗi, retry và idempotency riêng |
| Đưa key/value null vào ConcurrentHashMap | Không được phép | Chuẩn hóa dữ liệu hoặc dùng biểu diễn không-null |
| Tạo cache thiếu chiến lược xóa | Bộ nhớ tăng và dữ liệu lỗi thời | Thêm giới hạn, expiry, invalidation |
| Đọc `LongAdder.sum()` giữa lúc đang update rồi gọi là snapshot chính xác | Sum không phải snapshot atomic | Đợi kết thúc hoặc định nghĩa semantics quan sát |
| Chỉ test lần tạo đầu tiên | Bỏ sót khả năng tính lại không cần thiết | Kiểm thêm key đã có, null, exception, concurrent |

## 14. Bài tập áp dụng

**Bài 1 — Gom tên theo phòng ban.** Từ danh sách nhân viên `(department, name)`, hãy gom vào `Map<String,List<String>>`, giữ thứ tự tên và giữ tên trùng.

**Gợi ý:**

```java
// Mã minh họa trong ngữ cảnh có Iterable<Employee> employees.
Map<String, List<String>> groups = new LinkedHashMap<>();
for (Employee e : employees) {
    groups.computeIfAbsent(
        e.getDepartment(), k -> new ArrayList<>())
        .add(e.getName());
}
```

Đảm bảo vòng lặp tuần tự, dữ liệu đầu vào đã có thứ tự hợp lệ và không ghi vào các List đó đồng thời từ nơi khác.

**Bài 2 — Value phải được tạo lazy.** Với `Map<String,Config>`, cấu hình chỉ được nạp khi key chưa có value. Hàm tải tốn chi phí, có bộ đếm số lần gọi. Viết test: key mới gọi một lần, key cũ không gọi thêm.

**Đáp án định hướng:** `map.computeIfAbsent(key, k -> loadConfig(k))`; test số lần gọi bằng counter/test double và xác minh value.

**Bài 3 — Cache kết quả không tìm thấy.** Loader trả null cho key "missing". Vì sao gọi computeIfAbsent trên key này có thể chạy loader lần thứ hai?

**Đáp án:** vì null không được lưu làm value mới. Nếu muốn lưu "không có", dùng value non-null như `Optional.empty()` và chính sách xóa/làm mới phù hợp.

**Bài 4 — Đếm song song.** Có 100.000 event nhiều loại, chạy nhiều task cập nhật Map. Có thể dùng `ConcurrentHashMap<String,ArrayList<Event>>` và `computeIfAbsent(...).add(e)` không?

**Đáp án:** không an toàn khi nhiều luồng cùng thêm vào cùng ArrayList. Nếu chỉ cần đếm, dùng `ConcurrentHashMap<String,LongAdder>`. Nếu cần thu event, chọn cấu trúc hoặc chiến lược đồng bộ value phù hợp và xác định yêu cầu thứ tự.

**Bài 5 — Thay lời gọi API.** Một chương trình có `putIfAbsent(key, createExpensive())`. Kết quả trả về là old value; người viết muốn nhận **new-or-existing** mà không tính thừa. Nên dùng gì?

**Đáp án:** `computeIfAbsent(key, k -> createExpensive())` khi muốn chỉ tạo nếu chưa có value non-null; nhớ rằng null hoặc exception có quy tắc riêng.

## 15. Câu hỏi tự kiểm tra

**1. Điều kiện nào khiến computeIfAbsent gọi mappingFunction?**  
Khi key chưa gắn với một giá trị non-null; bao gồm cả trường hợp key có mapping null trong Map cho phép null.

**2. Callback trả null có tạo key mới không?**  
Không. Nếu key vắng mặt thì vẫn vắng mặt; nếu đã có mapping null, không có value non-null mới được tạo.

**3. `putIfAbsent(key, create())` có bảo đảm create chỉ chạy khi key vắng không?**  
Không. Java đánh giá đối số create trước khi gọi phương thức.

**4. Vì sao ConcurrentHashMap.computeIfAbsent atomic không đồng nghĩa value thread-safe?**  
Vì tính atomic liên quan thao tác đặt mapping; việc cập nhật object mutable trong value có hợp đồng thread-safety riêng.

**5. Dùng class nào của Java 8 để đếm theo key trong nhiều luồng?**  
Một lựa chọn là `ConcurrentHashMap<K,LongAdder>`, tạo bằng computeIfAbsent rồi gọi increment.

**6. Callback ném exception thì có tự rollback thao tác gửi email trước đó không?**  
Không. computeIfAbsent không phải transaction cho side effect bên ngoài Map.

**7. Có nên dùng null để biểu diễn kết quả không tìm thấy được cache không?**  
Không nếu cần tránh tính lại. Có thể lưu một giá trị non-null biểu diễn absence, như Optional.empty, với chính sách freshness.

**8. Phải làm gì khi giá trị cache có thể thay đổi theo thời gian?**  
Xây dựng invalidation/expiration hoặc chiến lược tải lại; computeIfAbsent không tự quản lý tuổi thọ dữ liệu.

**9. Mapping function trong ConcurrentHashMap có nên cập nhật các key khác của chính Map không?**  
Không. Tài liệu yêu cầu callback không cố cập nhật mapping khác trong cùng Map trong lúc tính.

**10. Vì sao không dựa vào thứ tự duyệt HashMap khi test?**  
Vì HashMap không cam kết encounter order; test nên đối chiếu key/value qua API hoặc dùng LinkedHashMap khi bài toán thật cần thứ tự chèn.

## Tài liệu chính thức

- [Java SE 8 — Map](https://docs.oracle.com/javase/8/docs/api/java/util/Map.html): `computeIfAbsent`, `putIfAbsent`, `getOrDefault`, `compute` và `merge`.
- [Java SE 8 — ConcurrentHashMap](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/ConcurrentHashMap.html): atomic computeIfAbsent, hướng dẫn tránh recursive updates, ví dụ `LongAdder`.
- [Java SE 8 — LongAdder](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/atomic/LongAdder.html): nhiều lần cập nhật đồng thời và giới hạn `sum()` khi còn ghi.
- [Java SE 8 — Optional](https://docs.oracle.com/javase/8/docs/api/java/util/Optional.html): cách biểu diễn một kết quả có/không có khi có chủ đích lưu negative caching.
- [Java SE 8 — Function](https://docs.oracle.com/javase/8/docs/api/java/util/function/Function.html): hợp đồng hàm tạo giá trị cho mappingFunction.

**Ghi nhớ:** `computeIfAbsent` là cách diễn đạt **khởi tạo value non-null đúng lúc cần**, đặc biệt hữu ích cho nhóm dữ liệu, bộ đếm và cache đơn giản. Hãy luôn xét null, exception, giá trị được tái sử dụng, khả năng thay đổi theo thời gian, và tính thread-safe của cả Map lẫn value. Lazy creation là lợi ích về tính rõ ràng và chi phí, không phải sự thay thế cho quản lý vòng đời, caching policy hoặc đồng bộ nghiệp vụ.
