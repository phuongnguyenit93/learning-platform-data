# JDBC 4.2: executeLargeUpdate, executeLargeBatch và update count kiểu long

## 1. Tại sao JDBC cần update count kiểu long?

Trong JDBC, **update count** là số dòng mà một thao tác SQL cập nhật dữ liệu báo đã ảnh hưởng. Với `INSERT`, `UPDATE`, `DELETE` và nhiều câu DML khác, ứng dụng có thể cần biết có bao nhiêu dòng được xử lý. Các API truyền thống trả `int` hoặc `int[]`:

```java
int count = statement.executeUpdate(sql);
int[] counts = statement.executeBatch();
```

Vấn đề: `int` có dấu của Java chỉ biểu diễn số dương đến **2.147.483.647** (`Integer.MAX_VALUE`). Một lệnh cập nhật hàng loạt có thể ảnh hưởng nhiều dòng hơn giới hạn đó. Để làm việc với update count lớn mà không bị giới hạn bởi kiểu `int`, JDBC **4.2**, đi cùng **Java 8**, bổ sung các phương thức:

- `Statement.executeLargeUpdate(String sql)` trả một `long`.
- `PreparedStatement.executeLargeUpdate()` trả một `long`, sử dụng câu SQL đã chuẩn bị và tham số đã bind.
- `Statement.executeLargeBatch()` trả một **`long[]`**, tức một update count cho từng mục trong batch.
- `Statement.getLargeUpdateCount()` trả một `long` cho kết quả cập nhật hiện tại sau khi gọi `execute(...)`.
- `BatchUpdateException.getLargeUpdateCounts()` trả **`long[]`** thông tin các lệnh trong batch khi có lỗi.

`long` có dấu chứa được số dương tới **9.223.372.036.854.775.807**. Các API này vẫn hiện hành trên JDK hiện đại. Không cần thay `long` bằng `BigInteger` chỉ để nhận update count ở phạm vi JDBC chuẩn.

**Mục tiêu quan trọng:** sử dụng kiểu rộng để **bảo toàn thông tin từ driver**. Chỉ thay kiểu biến nhận từ `int` sang `long` sau khi gọi `executeUpdate()` **không thể khôi phục** một update count đã vượt khả năng biểu diễn của `int`:

```java
long tooLate = statement.executeUpdate(sql);  // int được trả trước
long correct = statement.executeLargeUpdate(sql); // API trả long trực tiếp
```

Hai dòng trên là snippet độc lập trong method có `Statement statement` và `String sql` đã hợp lệ. Dòng đầu mở rộng **kết quả int**, chứ không khiến driver trả long. Khi driver không thực sự hỗ trợ large methods, việc code compile vẫn **không bảo đảm** cập nhật số dòng cực lớn được báo chính xác.

### 1.1. Một bảng định hướng nhanh

| Tác vụ | API trước JDBC 4.2 | API large (Java 8+) | Kiểu kết quả |
| --- | --- | --- | --- |
| Chạy một SQL update trực tiếp | `Statement.executeUpdate(sql)` | `Statement.executeLargeUpdate(sql)` | `long` |
| Chạy một prepared update | `PreparedStatement.executeUpdate()` | `PreparedStatement.executeLargeUpdate()` | `long` |
| Chạy nhiều lệnh trong batch | `Statement.executeBatch()` | `Statement.executeLargeBatch()` | `long[]` |
| Đọc update count sau `execute` | `Statement.getUpdateCount()` | `Statement.getLargeUpdateCount()` | `long` |
| Đọc các count khi batch lỗi | `BatchUpdateException.getUpdateCounts()` | `BatchUpdateException.getLargeUpdateCounts()` | `long[]` |

**Chú ý:** `getLargeMaxRows()` và `setLargeMaxRows(long)` cũng là các API dùng số long trong JDBC 4.2, nhưng chúng nói về **giới hạn số dòng của ResultSet**, không phải số dòng bị thay đổi. Đừng nhầm hai khái niệm.

## 2. Hiểu chính xác update count

Khi một câu DML thực thi, driver báo **số dòng bị ảnh hưởng theo ngữ nghĩa JDBC/DBMS và câu SQL**. Không nên tự diễn giải update count thành những thông tin khác:

- Không phải **khóa chính mới được tạo**. Generated keys là một luồng kết quả riêng được lấy qua `getGeneratedKeys()` nếu driver hỗ trợ.
- Không phải **số lệnh trong batch**. Mỗi lệnh batch có một count riêng, dù một lệnh có thể cập nhật hàng triệu dòng.
- Không phải **số lần trigger chạy**, cũng không phải cam kết về tác động gián tiếp do trigger/cascade.
- Không bảo đảm `UPDATE` nào cũng trả 1: điều kiện `WHERE` có thể khớp 0, 1 hoặc nhiều dòng.
- Không nên suy ra từ `long count == 0L` rằng SQL lỗi. Trường hợp `WHERE` không khớp dòng nào là một cập nhật hợp lệ với count 0.

Với DML, `executeLargeUpdate` báo số dòng ảnh hưởng theo driver/DBMS. Với câu SQL **không tạo ResultSet** như DDL, phương thức có thể trả **0**, tùy API contract và DBMS. Đối với câu `SELECT` có ResultSet, dùng `executeQuery` hoặc `execute` — không dùng `executeLargeUpdate` như một cách “đếm số dòng SELECT”.

### 2.1. Đếm dòng không phải transaction status

Giá trị `count = 42` có nghĩa driver báo 42 dòng ảnh hưởng bởi thao tác đó. Nó **không tự chứng minh** rằng transaction đã `commit` thành công, đã được nhân bản sang mọi replica, hoặc các side effect ngoài DB được thực hiện đúng một lần.

Nếu `connection.setAutoCommit(false)` thì thao tác có thể trả count trước khi gọi `commit()`. Nếu sau đó `rollback()`, dữ liệu có thể bị hoàn nguyên theo khả năng transaction của DB; count đã trả **không tự đổi thành 0** trong biến Java.

### 2.2. Count là số dòng, không phải dung lượng dữ liệu

`long` trong các phương thức này **không** đo bytes của tệp, kích thước bảng, memory hoặc số result-set rows đang được fetch. Đó là **update count** theo ngữ nghĩa lệnh SQL. Với batch, mỗi phần tử của `long[]` còn là **một kết quả cho một lệnh**, không phải tổng.

## 3. `Statement.executeLargeUpdate(String)`

Chữ ký quan trọng:

```java
long executeLargeUpdate(String sql) throws SQLException;
```

Phương thức tồn tại trên interface `java.sql.Statement` dưới dạng **default method** từ Java 8. Nó thực thi câu DML như `INSERT`, `UPDATE`, `DELETE`, hoặc câu SQL không trả ResultSet như một số câu DDL, và nhận count kiểu long.

```java
try (Statement statement = connection.createStatement()) {
    long count = statement.executeLargeUpdate(
        "UPDATE inventory SET archived = 1 WHERE created_at < DATE '2020-01-01'");
    System.out.println("Affected rows: " + count);
}
```

Đây là **snippet cần kết nối JDBC thật**: `Connection connection` đã được ứng dụng cấp; cú pháp SQL date và tên bảng/cột có thể phụ thuộc DBMS. `try-with-resources` đóng `Statement` sau khi dùng.

**Khi nào dùng:** câu SQL tĩnh, đáng tin cậy, không nhận giá trị trực tiếp từ user và một lệnh DML có thể ảnh hưởng rất nhiều dòng. Trong code ứng dụng xử lý input, **`PreparedStatement` với tham số bind thường phù hợp hơn**, kể cả khi chưa vượt giới hạn int.

### 3.1. Không dùng API này cho `SELECT`

`executeLargeUpdate` được dùng với SQL không trả `ResultSet`. Nếu một câu SQL trả ResultSet, driver có thể ném `SQLException` theo hợp đồng API. Với `SELECT` thông thường:

```java
try (Statement statement = connection.createStatement();
     ResultSet rows = statement.executeQuery(
         "SELECT id, status FROM inventory")) {
    while (rows.next()) {
        // Xử lý từng dòng kết quả.
    }
}
```

Đây là snippet có `connection`, table/columns hợp lệ. Nếu DBMS hỗ trợ `UPDATE ... RETURNING ...` và câu SQL trả ResultSet, phải xem **hợp đồng driver và dạng thực thi phù hợp**, không tự cho rằng `executeLargeUpdate` sẽ vừa trả long vừa trả ResultSet theo ý muốn.

### 3.2. Các overload lấy generated keys

`Statement` có thêm overload:

```java
long executeLargeUpdate(String sql, int autoGeneratedKeys);
long executeLargeUpdate(String sql, int[] columnIndexes);
long executeLargeUpdate(String sql, String[] columnNames);
```

Các chữ ký trên thuộc `Statement`; flags/columns cho driver biết bạn yêu cầu thông tin về **generated keys**. Ví dụ:

```java
try (Statement st = connection.createStatement()) {
    long rows = st.executeLargeUpdate(
        "INSERT INTO audit_event(message) VALUES ('created')",
        Statement.RETURN_GENERATED_KEYS);
    try (ResultSet keys = st.getGeneratedKeys()) {
        while (keys.next()) {
            // Đọc generated key theo kiểu cột thật của DBMS.
        }
    }
}
```

Snippet sử dụng SQL tĩnh để minh họa; không nối user input vào SQL. Việc driver có hỗ trợ generated keys với loại statement hoặc cú pháp này không phụ thuộc **chỉ** vào việc trả long. `rows` là update count, **không phải generated key**.

### 3.3. `Statement.executeLargeUpdate(sql)` KHÔNG dùng trên `PreparedStatement`

Đây là một khác biệt API rất dễ nhầm. `PreparedStatement` kế thừa `Statement`, nhưng các overload `executeLargeUpdate(String sql,...)` của `Statement` **không được gọi trên đối tượng PreparedStatement/CallableStatement** theo Javadoc. Để thực thi SQL đã chuẩn bị, dùng **phiên bản không có String**:

```java
PreparedStatement ps = connection.prepareStatement(
    "UPDATE inventory SET archived = ? WHERE id = ?");
ps.setBoolean(1, true);
ps.setLong(2, 123L);
long count = ps.executeLargeUpdate(); // ĐÚNG
// ps.executeLargeUpdate("UPDATE ..."); // Không dùng.
```

Snippet chưa có `try-with-resources` cho ngắn; code thực cần đóng `ps`. `ps.executeLargeUpdate()` là phương thức được khai báo riêng ở `PreparedStatement`.

## 4. `PreparedStatement.executeLargeUpdate()`

Chữ ký:

```java
long executeLargeUpdate() throws SQLException;
```

`PreparedStatement` đại diện một SQL đã được chuẩn bị, với các dấu `?` làm placeholder. Bạn **bind parameter** rồi gọi phương thức không tham số `executeLargeUpdate()`.

```java
String sql = "UPDATE orders SET status = ? WHERE created_at < ?";

try (PreparedStatement ps = connection.prepareStatement(sql)) {
    ps.setString(1, "ARCHIVED");
    ps.setTimestamp(2, cutoffTimestamp);
    long updated = ps.executeLargeUpdate();
    System.out.println("Updated: " + updated);
}
```

Đây là **snippet cần database và biến `cutoffTimestamp`** (kiểu `java.sql.Timestamp`) từ ứng dụng. JDBC parameter indexes bắt đầu từ 1. Dữ liệu trong placeholders được driver xử lý như **giá trị**, tránh nối chuỗi SQL từ input người dùng. SQL literal, tên cột và biểu thức vẫn phải tuân thủ dialect DBMS.

### 4.1. Khi nào thật sự cần large method?

Nếu một update có thể ảnh hưởng trên 2,1 tỷ dòng, API kiểu `long` tránh giới hạn `int`. Với một update thông thường chỉ ảnh hưởng 0–vài nghìn dòng, `executeUpdate()` kiểu `int` **vẫn là API hợp lệ** và không bị coi là legacy chỉ vì có bản large.

Lựa chọn nên dựa trên:

- **Khả năng thật** số dòng có thể vượt `Integer.MAX_VALUE`.
- Driver đang triển khai có hỗ trợ large methods.
- Hệ thống thống kê/kiểm toán có dùng `long` xuyên suốt hay vẫn vô tình thu hẹp về `int`.
- Mức độ nhất quán API nếu ứng dụng quy định mọi số dòng dùng `long`.

### 4.2. Dùng cùng `PreparedStatement` cho nhiều lần chạy

Một `PreparedStatement` có thể được bind lại nhiều lần cho cùng SQL. Ví dụ:

```java
try (PreparedStatement ps = connection.prepareStatement(
        "UPDATE inventory SET quantity = quantity + ? WHERE id = ?")) {
    ps.setInt(1, 5);
    ps.setLong(2, 101L);
    long first = ps.executeLargeUpdate();

    ps.setInt(1, 8);
    ps.setLong(2, 102L);
    long second = ps.executeLargeUpdate();
}
```

Đây là snippet. Hai lần `executeLargeUpdate` trả **hai update counts riêng**, không mặc nhiên cộng dồn. Không tự giả định driver/bảng sẽ cho `first == second == 1` nếu không có dữ liệu thật.

### 4.3. CallableStatement và câu lệnh có nhiều kết quả

`CallableStatement` kế thừa `PreparedStatement` và có ngữ nghĩa stored procedures; việc có sử dụng được phương thức update nào còn phụ thuộc câu lệnh đang gọi và driver. Nếu procedure có thể trả **nhiều ResultSet hoặc update counts**, xem `execute()` kết hợp `getMoreResults()` / `getLargeUpdateCount()`, thay vì cho rằng một `executeLargeUpdate()` đơn sẽ trả tổng mọi tác động gián tiếp.

## 5. `executeLargeBatch()`: một mảng `long[]` cho nhiều lệnh

`Statement.executeLargeBatch()` trả **`long[]`**; `PreparedStatement` kế thừa phương thức này. Bạn dùng `addBatch` để gom nhiều lệnh rồi thực thi:

```java
try (Statement st = connection.createStatement()) {
    st.addBatch("UPDATE products SET active = 0 WHERE id = 101");
    st.addBatch("UPDATE products SET active = 0 WHERE id = 102");
    st.addBatch("UPDATE products SET active = 0 WHERE id = 103");

    long[] counts = st.executeLargeBatch();
    // counts[i] ứng với lệnh được addBatch ở vị trí i.
}
```

Đây là snippet cần database phù hợp. Trên đường **thành công toàn bộ**, mảng chứa một kết quả cho mỗi lệnh theo **thứ tự thêm vào batch**. Giá trị của từng phần tử có thể là số không âm hoặc `Statement.SUCCESS_NO_INFO` nếu driver xác nhận thành công nhưng không biết số dòng.

### 5.1. PreparedStatement batch: dùng `addBatch()` không truyền SQL

```java
String sql = "UPDATE products SET active = ? WHERE id = ?";

try (PreparedStatement ps = connection.prepareStatement(sql)) {
    for (long id : idsToDeactivate) {
        ps.setBoolean(1, false);
        ps.setLong(2, id);
        ps.addBatch(); // chụp bộ tham số của lần này
    }
    long[] counts = ps.executeLargeBatch();
}
```

Đây là snippet với `idsToDeactivate` do ứng dụng định nghĩa. Trên `PreparedStatement` phải dùng `addBatch()` **không truyền String SQL** để gom các bộ tham số tương ứng câu SQL đã chuẩn bị. Trái lại, `Statement.addBatch(String sql)` nhận một câu SQL riêng.

**Lưu ý quan trọng:** số phần tử trong `long[]` **không phải số dòng được ảnh hưởng**. Một phần tử có thể là `0` (lệnh không khớp dòng), `1`, `2_500_000_000L` hoặc sentinel `SUCCESS_NO_INFO`, tùy dữ liệu và driver.

### 5.2. Batch là phương tiện gửi nhiều lệnh, không phải một phép UPDATE khổng lồ

Một mảng `long[100]` không ngụ ý 100 dòng bị cập nhật. Nó chứa **100 kết quả tương ứng 100 lệnh batch**, nếu đường thực thi thành công và driver trả kết quả cho từng lệnh.

Ngược lại, **một** lệnh SQL có `WHERE` rộng có thể ảnh hưởng 3 tỷ dòng và trả `3_000_000_000L` qua `executeLargeUpdate()`.

### 5.3. Batch không tự đồng nghĩa atomic transaction

`executeLargeBatch()` không phải một giao dịch all-or-nothing chỉ vì có chữ "batch". Nếu connection đang auto-commit, chính sách commit mỗi lệnh và lỗi phụ thuộc DBMS/driver. Nếu có transaction bao quanh batch, code phải chủ động **commit** hoặc **rollback**, và kiểm tra storage engine có hỗ trợ transaction cho loại thao tác.

Khi một câu SQL trong batch lỗi, driver có thể **dừng ngay** hoặc **tiếp tục chạy các lệnh còn lại** theo quy định Javadoc. Vì vậy, mọi cách retry phải phân tích các lệnh đã có thể thực thi và trạng thái giao dịch.

## 6. Ý nghĩa các giá trị trong `long[]`: không chỉ là số dòng

Trong một mảng update counts, có ba nhóm giá trị quan trọng:

| Giá trị | Ý nghĩa | Có cộng vào tổng dòng chính xác không? |
| --- | --- | --- |
| `0L` | Lệnh thành công, driver báo 0 dòng ảnh hưởng | Có, cộng 0 |
| `1L`, `12L`, `3_000_000_000L`… | Lệnh thành công, có số dòng rõ ràng | Có, nếu cộng không tràn `long` |
| `Statement.SUCCESS_NO_INFO` = `-2` | Lệnh thành công nhưng **không biết count** | **Không**; không thể biết tổng chính xác |
| `Statement.EXECUTE_FAILED` = `-3` | Lệnh bị lỗi, thường thấy trong **BatchUpdateException** khi driver tiếp tục sau lỗi | **Không**; batch thất bại |
| `-1` từ `getLargeUpdateCount()` | Không có update count hiện tại hoặc kết quả hiện tại là `ResultSet` | **Không**; không phải số dòng `-1` |

`Statement.SUCCESS_NO_INFO` và `Statement.EXECUTE_FAILED` là **constant kiểu `int`**, nhưng có thể so sánh trực tiếp với từng phần tử kiểu `long` vì Java mở rộng int sang long khi so sánh.

### 6.1. Không nhầm `SUCCESS_NO_INFO` với lệnh thất bại

`Statement.SUCCESS_NO_INFO == -2` nghĩa là **driver báo thành công nhưng không xác định số dòng**. Không có căn cứ suy ra 0, 1 hoặc một số dòng khác.

`Statement.EXECUTE_FAILED == -3` chỉ ra một lệnh **đã thất bại**, trong thông tin batch-exception khi driver tiếp tục xử lý các mục khác. Trên đường `executeLargeBatch()` trả về bình thường, Javadoc cho phép số không âm hoặc `SUCCESS_NO_INFO`; không tự diễn giải `-3` là một kết quả thành công.

### 6.2. Không cộng thẳng cả mảng

**Sai:**

```java
long total = 0;
for (long count : counts) {
    total += count;
}
```

Nếu `counts = {3L, 2_500_000_000L, -2L}`, tổng máy tính sẽ là `2_500_000_001L`. Nhưng dữ liệu thực chỉ cho biết **ít nhất những lệnh có count rõ** đã ảnh hưởng `2_500_000_003` dòng, và **một lệnh thành công không có count chính xác**. Lấy tổng gồm `-2` là sai.

**Một chính sách có chủ đích:**

```java
long knownAffected = 0L;
boolean hasUnknown = false;

for (long count : counts) {
    if (count >= 0L) {
        knownAffected = Math.addExact(knownAffected, count);
    } else if (count == Statement.SUCCESS_NO_INFO) {
        hasUnknown = true;
    } else if (count == Statement.EXECUTE_FAILED) {
        throw new IllegalStateException("Batch item failed");
    } else {
        throw new IllegalStateException("Unexpected JDBC count: " + count);
    }
}

if (hasUnknown) {
    // Không báo knownAffected là totalAffected chính xác.
}
```

Đây là **snippet** với `long[] counts` đã được driver trả; `Math.addExact` có từ Java 8 và ném `ArithmeticException` khi tổng `long` bị tràn. Nếu cần thống kê không giới hạn tổng, dùng `BigInteger`/database count theo hợp đồng. Khi có `SUCCESS_NO_INFO`, có thể báo **known count** cùng cờ `INCOMPLETE/UNKNOWN`, không báo "tổng chính xác".

## 7. `BatchUpdateException` khi một mục trong batch thất bại

Khi batch có lỗi, JDBC dùng `java.sql.BatchUpdateException`, một subclass của `SQLException`. Exception chứa thông tin về những lệnh đã xử lý, cùng SQLState/vendor code/cause.

API cần ghi nhớ:

```java
long[] partial = exception.getLargeUpdateCounts();
String state = exception.getSQLState();
int vendorCode = exception.getErrorCode();
SQLException next = exception.getNextException();
```

Đây là snippet với `BatchUpdateException exception` trong catch. Với `executeLargeBatch`, **dùng `getLargeUpdateCounts()`** thay vì `getUpdateCounts()` vì bản `int[]` có thể mất thông tin count lớn.

### 7.1. Nếu driver dừng ở lệnh lỗi

Ví dụ batch có năm lệnh; nếu driver dừng ngay khi mục thứ ba lỗi, array trong exception **có thể chỉ có hai phần tử** cho các lệnh đã xử lý thành công trước khi lỗi:

```text
Commands:  [ A, B, C, D, E ]
Result:    [ 3, 9 ]
Meaning:   A/B có count; C gây lỗi; D/E không chạy theo đường dừng.
```

Đây là **ví dụ logic**, không phải kết quả thật của mọi driver. Không mặc định một `getLargeUpdateCounts()` ngắn là một mảng toàn bộ với các phần tử còn lại bằng 0. Thiếu phần tử không đồng nghĩa số dòng 0.

### 7.2. Nếu driver tiếp tục sau lệnh lỗi

Một driver có thể tiếp tục chạy những lệnh còn lại, và trả mảng cùng số phần tử với batch, trong đó có `EXECUTE_FAILED`:

```text
Commands: [ A, B, C ]
Counts:   [ 2500000000, -3, -2 ]
                 |       |    |
               count   FAILED SUCCESS_NO_INFO
```

Theo ví dụ, A báo 2,5 tỷ dòng; B thất bại; C được chạy thành công nhưng driver không biết count. **Không** tự tuyên bố cả batch “rollback” chỉ vì catch exception; trạng thái transaction phụ thuộc database, auto-commit và thao tác xử lý sau đó.

### 7.3. Constructor nhận `long[]` đã tồn tại từ Java 8

Javadoc khuyến nghị driver tạo `BatchUpdateException` bằng constructor chứa **`long[] updateCounts`**, thay vì `int[]`, để tránh mất count lớn:

```java
long[] partial = {
    2_500_000_000L,
    Statement.EXECUTE_FAILED,
    Statement.SUCCESS_NO_INFO
};

BatchUpdateException problem = new BatchUpdateException(
    "simulated batch failure", "23000", 7,
    partial, new SQLException("duplicate key"));

long[] recovered = problem.getLargeUpdateCounts();
```

Đây là snippet xây **exception giả lập để học API**, không hề chạy database. Lớp JDBC cung cấp constructor này từ Java 8, còn actual SQLState/error code do driver/DBMS trả.

### 7.4. Thiết kế catch batch error đúng kiểu

```java
try {
    long[] counts = ps.executeLargeBatch();
    inspectSuccessfulBatch(counts);
} catch (BatchUpdateException failure) {
    long[] partial = failure.getLargeUpdateCounts();
    recordBatchFailure(failure.getSQLState(), partial);
    throw failure;
}
```

Đây là **snippet kiến trúc** với `ps` là `PreparedStatement`, các helper do ứng dụng định nghĩa. Code production cần transaction và rollback; phần bắt exception chỉ là bước **phân loại**, chưa giải quyết dữ liệu đã bị thay đổi.

Không mặc định câu lệnh thứ ba luôn là câu bị lỗi chỉ từ `partial.length == 2` nếu driver có chính sách thực thi khác; đối chiếu theo semantics của driver và số lệnh thêm vào.

## 8. Transaction, rollback và retry an toàn

Khi batch ảnh hưởng dữ liệu quan trọng, nên có **ranh giới transaction** rõ ràng nếu DB/driver hỗ trợ. Mẫu điển hình:

```java
boolean oldAutoCommit = connection.getAutoCommit();
connection.setAutoCommit(false);
try {
    try (PreparedStatement ps = connection.prepareStatement(
            "UPDATE orders SET state = ? WHERE id = ?")) {
        for (OrderUpdate item : updates) {
            ps.setString(1, item.getState());
            ps.setLong(2, item.getId());
            ps.addBatch();
        }
        long[] counts = ps.executeLargeBatch();
        validateBatchCounts(counts);
    }
    connection.commit();
} catch (SQLException | RuntimeException failure) {
    try {
        connection.rollback();
    } catch (SQLException rollbackFailure) {
        failure.addSuppressed(rollbackFailure);
    }
    throw failure;
} finally {
    connection.setAutoCommit(oldAutoCommit);
}
```

Đây là **snippet kiến trúc**, cần `Connection connection`, `updates` và `OrderUpdate`, `validateBatchCounts` do ứng dụng định nghĩa; method chứa nó cần khai báo `throws SQLException` phù hợp. Để sản xuất, cần xử lý riêng trường hợp **khôi phục auto-commit cũng thất bại** và bảo đảm connection được trả về pool/đóng đúng lifecycle. Mẫu này không giải quyết tất cả lỗi connection bị mất hoặc transaction outcome không xác định; nó chỉ nêu luồng cơ bản.

### 8.1. Không gọi rollback khi auto-commit vẫn bật rồi mặc định an toàn

Trong auto-commit mode, từng statement thường được DB commit theo chính sách riêng. Việc catch `BatchUpdateException` **không tự đảo ngược** các lệnh trước đó. Với nhiều DB, `rollback` khi auto-commit đang bật cũng không khôi phục những thay đổi đã được commit.

Nếu muốn all-or-nothing, cần tắt auto-commit **trước khi chạy batch**, bảo đảm bảng/storage engine hỗ trợ transaction, kiểm tra transaction isolation và xử lý cả commit failure.

### 8.2. Retry phải dựa vào trạng thái thực tế và idempotency

Trường hợp lỗi mạng đúng lúc commit là bài toán khó: client có thể **không biết** DB đã commit hay chưa. Không thể quyết định retry tất cả lệnh chỉ dựa trên chiều dài `long[]`. Với thao tác tăng số dư, gửi tiền, tạo đơn hàng... cần idempotency key, unique constraints, versioned updates hoặc state reconciliation để ngăn thực hiện lặp.

### 8.3. Batch size là vấn đề vận hành khác update count

Một batch có thể chứa 500 lệnh, mỗi lệnh cập nhật từ 0 đến hàng triệu dòng. Tối ưu batch size dựa vào round trips, memory, transaction log, locks, DB limits, thời gian rollback và khả năng retry; **không** suy ra từ kiểu trả `long[]` rằng nên tăng batch vô hạn.

## 9. `getLargeUpdateCount()` sau `execute(...)`

`Statement.execute(sql)` phù hợp với SQL có thể tạo **ResultSet, update count hoặc nhiều kết quả**. Method này trả boolean:

- `true`: kết quả hiện tại là `ResultSet`.
- `false`: kết quả hiện tại là **update count hoặc không có kết quả**.

Nếu `execute(...)` trả false, bạn có thể hỏi `getLargeUpdateCount()` để biết count hiện tại:

```java
try (Statement st = connection.createStatement()) {
    boolean hasResultSet = st.execute(
        "UPDATE account SET checked = 1 WHERE active = 1");

    if (!hasResultSet) {
        long count = st.getLargeUpdateCount();
        if (count >= 0L) {
            // Đang có một update count hiện tại.
        } else {
            // -1: không có update count hiện tại.
        }
    }
}
```

Đây là snippet cần DB, với SQL chỉ minh họa. Không suy ra `hasResultSet == false` chắc chắn có count hợp lệ; **`getLargeUpdateCount() == -1L`** là sentinel **không có update count hiện tại hoặc kết quả hiện tại là ResultSet**.

### 9.1. `getLargeUpdateCount()` khác `executeLargeUpdate()`

- `executeLargeUpdate(sql)` **thực thi SQL và trả long count** ngay.
- `execute(sql)` **thực thi SQL**, có thể có nhiều dạng kết quả; sau đó dùng `getResultSet()` hoặc `getLargeUpdateCount()` theo loại kết quả.
- `getMoreResults()` chuyển tới kết quả kế tiếp nếu DBMS/driver hỗ trợ multiple results; kết hợp với `getLargeUpdateCount()` để phân biệt “update count tiếp theo” với “không còn kết quả”.

Ví dụ khung xử lý:

```java
boolean hasResults = st.execute(sql);
while (true) {
    if (hasResults) {
        try (ResultSet rs = st.getResultSet()) {
            processRows(rs);
        }
    } else {
        long count = st.getLargeUpdateCount();
        if (count == -1L) {
            break; // Không còn kết quả.
        }
        recordUpdateCount(count);
    }
    hasResults = st.getMoreResults();
}
```

Đây là **snippet kiến trúc**, cần `st`, `sql` và hai helper `processRows`/`recordUpdateCount` được ứng dụng định nghĩa. Với nhiều ResultSet, cách đóng và giữ results cần tuân thủ `getMoreResults` policy của driver; ví dụ minh họa chỉ đóng result hiện tại trước khi chuyển. Javadoc khuyến nghị gọi `getLargeUpdateCount` **một lần cho mỗi result**, không dùng nó như đồng hồ đo thường xuyên trong vòng polling.

### 9.2. Phân biệt ba sentinel âm

Đừng gộp các giá trị:

- `-1`: từ `getLargeUpdateCount`, báo **không có update count** hiện tại.
- `-2`: `Statement.SUCCESS_NO_INFO` trong **batch**, nghĩa là **thành công nhưng không biết số dòng**.
- `-3`: `Statement.EXECUTE_FAILED` trong **batch exception**, nghĩa là **lệnh bị lỗi**.

Mỗi số thuộc một **ngữ cảnh API khác nhau**, tuyệt đối không cộng chúng như row counts.

## 10. Hỗ trợ JDBC driver: compile được chưa đủ

JDBC 4.2 bổ sung các phương thức large trên interface, nhưng **driver phải hiện thực hỗ trợ** để chúng thực sự hoạt động đúng và bảo toàn số dòng lớn. Nhiều phương thức được khai báo dưới dạng **default method** vì tương thích nhị phân với driver cũ; **default implementation không nhất thiết thực hiện SQL**.

Trong Javadoc Java 8/hiện đại:

- `Statement.executeLargeBatch()`: default có thể ném `UnsupportedOperationException`.
- `Statement.executeLargeUpdate(String sql)`: default có thể ném `UnsupportedOperationException`.
- `PreparedStatement.executeLargeUpdate()`: default có thể ném `UnsupportedOperationException`.
- `Statement.getLargeUpdateCount()`: default có thể ném `UnsupportedOperationException`.
- Một số overload `executeLargeUpdate(sql, generatedKeys...)` default có thể ném `SQLFeatureNotSupportedException`.

Vì vậy **đừng giả định** mọi JDBC 4.2 interface đều đồng nghĩa mọi phiên bản driver có large update counts đúng. Kiểm tra **driver version + DBMS version + tài liệu hỗ trợ** và chạy **integration test** trên môi trường thực nếu large counts là yêu cầu quan trọng.

### 10.1. SQLFeatureNotSupportedException và UnsupportedOperationException

`SQLFeatureNotSupportedException` là một `SQLException`; `UnsupportedOperationException` là unchecked exception. Tùy method và driver, code có thể gặp một trong những lỗi hỗ trợ như vậy.

**Không biến unsupported thành 0 affected rows**. Nếu large update là yêu cầu bắt buộc, việc driver không hỗ trợ phải làm **deployment/operation fail rõ**, hoặc chuyển tới phương án xử lý đã được chứng minh an toàn, không âm thầm dùng `executeUpdate()` rồi ép `int` thành `long`.

### 10.2. `DatabaseMetaData` và xác minh trên môi trường thực

`DatabaseMetaData.getJDBCMajorVersion()`, `getJDBCMinorVersion()` và `supportsBatchUpdates()` có thể cung cấp thông tin cơ bản về JDBC driver/database, nhưng **supportsBatchUpdates() == true không khẳng định các large methods đều được hỗ trợ chính xác tới giới hạn long**.

```java
DatabaseMetaData metadata = connection.getMetaData();
System.out.println(metadata.getJDBCMajorVersion());
System.out.println(metadata.getJDBCMinorVersion());
System.out.println(metadata.supportsBatchUpdates());
```

Đây là snippet cần DB. Muốn xác minh count thật trên 2,1 tỷ, có thể cần **môi trường kiểm thử tích hợp với dữ liệu tương ứng**, hoặc một test riêng có driver-specific fixture/mock được công bố rõ; không thực hiện update hàng tỷ dòng trên production chỉ để "thử API".

### 10.3. Các framework có thể tự quyết định API nào được gọi

Spring JDBC, JPA, Hibernate hoặc các thư viện database khác có thể **không trả long counts qua interface public hiện tại**, ngay cả khi JDBC driver hỗ trợ. Khi cần giá trị > `Integer.MAX_VALUE`, kiểm tra cả **framework method type**, ORM batching policy và map từ driver sang application; không chỉ sửa code repository tự gọi JDBC.

## 11. `long[]`, tổng đếm và overflow ở lớp ứng dụng

Một lệnh có thể trả `3_000_000_000L`, nhưng ứng dụng vẫn có thể phá hỏng thông tin ở các bước sau:

```java
long count = ps.executeLargeUpdate();
int narrowed = (int) count; // Có thể mất dữ liệu.
// Long -> JSON number, DB INT, metric 32-bit... cũng cần kiểm tra.
```

`(int)count` cắt bớt bit cao theo luật Java; không ném exception mặc định. Nếu thật sự cần thu hẹp và muốn **phát hiện lỗi**, Java 8 có `Math.toIntExact(long)`:

```java
long count = 3_000_000_000L;
try {
    int safe = Math.toIntExact(count);
} catch (ArithmeticException tooBig) {
    // Count không vừa int. Đừng âm thầm chuyển sai.
}
```

Đây là snippet runnable trong method. Với dữ liệu có thể lớn, tốt hơn là **giữ long tới cuối**: lớp service, DTO, metrics, log, storage và định dạng xuất.

### 11.1. Tổng known counts có thể vượt long nếu quá nhiều batch

`long` có giới hạn hữu hạn. Nếu cộng rất nhiều update counts cực lớn trong thời gian dài, `long total += count` có thể tràn. Dùng `Math.addExact` để phát hiện overflow, hoặc `BigInteger` khi cần đếm tổng lịch sử vượt `Long.MAX_VALUE`. Đừng cố suy ra tổng chính xác khi có `SUCCESS_NO_INFO`.

### 11.2. Long[] chỉ mở rộng giá trị từng phần tử, không làm mảng vô hạn

Java array vẫn được đánh chỉ số bằng `int` và chịu giới hạn kích thước bộ nhớ. `executeLargeBatch()` trả `long[]` không có nghĩa một batch có thể chứa `Long.MAX_VALUE` lệnh. Thiết kế chunk size và bộ nhớ phù hợp, không phóng đại tên gọi "large".

### 11.3. JSON và DB cần schema phù hợp

Một `long` Java tối đa 9,22×10¹⁸; các client dùng JavaScript `Number` thông thường chỉ giữ chính xác mọi số nguyên trong khoảng **±(2⁵³−1)**. Nếu update count rất lớn cần được giao tiếp chính xác với JavaScript client, cân nhắc trả **chuỗi thập phân** hoặc schema hỗ trợ số nguyên lớn thay vì mặc định JSON number.

Database column lưu cumulative counts cũng cần đủ độ rộng, ví dụ signed `BIGINT` có miền tương ứng, hoặc `DECIMAL/NUMERIC` nếu tổng có thể vượt long. Không dùng kiểu `INT`/`INTEGER` 32-bit để lưu count lớn.

## 12. Generated keys, row limit và các con số khác trong JDBC

Ba ý niệm cần tách:

| Cái gì? | Ví dụ API | Ý nghĩa |
| --- | --- | --- |
| **Update count** | `executeLargeUpdate()`, `getLargeUpdateCount()` | Số dòng bị ảnh hưởng theo SQL/DBMS |
| **Generated keys** | `Statement.RETURN_GENERATED_KEYS`, `getGeneratedKeys()` | ID/cột do DB sinh, trả qua `ResultSet` |
| **Max rows limit** | `setLargeMaxRows(long)`, `getLargeMaxRows()` | Giới hạn dòng được trả trong `ResultSet` |
| **Fetch size** | `Statement.setFetchSize(int)` | Gợi ý số dòng fetch khi truy xuất ResultSet |
| **Batch length** | `counts.length` | Số phần tử count driver trả cho batch |
| **Tổng count đã biết** | Cộng từng `count >= 0` | Chỉ chính xác khi không có unknown/failure |

### 12.1. `setLargeMaxRows` không giới hạn update count

`setLargeMaxRows(1000L)` ảnh hưởng **giới hạn dòng trả của ResultSet**, không phải "câu UPDATE sẽ chỉ ảnh hưởng 1.000 dòng". Nếu muốn giới hạn update, phải dùng ràng buộc SQL/transaction phù hợp theo DBMS; không dùng ResultSet max rows như biện pháp an toàn cho DML.

### 12.2. `SUCCESS_NO_INFO` không nói gì về generated keys

Nếu một `INSERT` batch trả `SUCCESS_NO_INFO`, nghĩa là không có update count chính xác cho mục đó, **không** kết luận generated key thiếu hoặc tồn tại. Generated keys có API/kênh dữ liệu riêng và mức hỗ trợ riêng theo driver.

## 13. Mẫu thao tác thực với PreparedStatement

Dưới đây là **mẫu tích hợp cơ sở dữ liệu thật**. Nó chủ động đặt transaction và không coi `SUCCESS_NO_INFO` thành count 0. SQL, bảng và connection phụ thuộc ứng dụng; không thể chạy độc lập nếu thiếu JDBC driver/database.

```java
static long updateAccounts(Connection connection, List<Long> ids)
        throws SQLException {
    if (ids.isEmpty()) return 0L;

    String sql = "UPDATE accounts SET active = ? WHERE id = ?";
    boolean previous = connection.getAutoCommit();
    connection.setAutoCommit(false);
    try {
        long knownTotal = 0L;
        try (PreparedStatement ps = connection.prepareStatement(sql)) {
            for (Long id : ids) {
                ps.setBoolean(1, false);
                ps.setLong(2, id);
                ps.addBatch();
            }

            long[] counts = ps.executeLargeBatch();
            if (counts.length != ids.size()) {
                throw new SQLException("Unexpected successful batch size");
            }
            for (long count : counts) {
                if (count == Statement.SUCCESS_NO_INFO) {
                    throw new SQLException(
                        "Exact update count unavailable");
                }
                if (count < 0L) {
                    throw new SQLException(
                        "Unexpected batch status: " + count);
                }
                try {
                    knownTotal = Math.addExact(knownTotal, count);
                } catch (ArithmeticException overflow) {
                    throw new SQLException(
                        "Accumulated row count exceeds long", overflow);
                }
            }
        }
        connection.commit();
        return knownTotal;
    } catch (SQLException | RuntimeException failure) {
        try {
            connection.rollback();
        } catch (SQLException rollbackError) {
            failure.addSuppressed(rollbackError);
        }
        throw failure;
    } finally {
        connection.setAutoCommit(previous);
    }
}
```

Đây là **method snippet** yêu cầu import `java.sql.Connection`, `PreparedStatement`, `SQLException`, `Statement` và `java.util.List`. Nếu code nằm trên pooled connection, framework quản lý transaction có thể **không cho** method tự đổi auto-commit; hãy dùng transaction API mà ứng dụng đã chọn thay vì trộn hai hệ thống quản lý transaction.

**Vì sao mẫu có thể chủ động fail khi `SUCCESS_NO_INFO`?** Vì giả định nghiệp vụ cần **tổng count chính xác**. Trong một API chỉ cần biết lệnh đã được chấp nhận, có thể cho phép `SUCCESS_NO_INFO` với cờ unknown; đó là quyết định domain, không phải JDBC bắt buộc phải fail.

### 13.1. Nên kiểm tra từng hàng có count bằng 1?

Với cập nhật theo khóa duy nhất, nhiều hệ thống kỳ vọng 0 hoặc 1. Nếu câu SQL đảm bảo unique key và nghiệp vụ yêu cầu tất cả ID tồn tại, có thể kiểm tra `count == 1L` với từng phần tử. Nhưng nếu driver trả `SUCCESS_NO_INFO`, nếu update bị trigger đổi semantics, hoặc câu WHERE không phải unique, logic ấy cần được đánh giá lại.

Đừng áp kiểm tra "mọi lệnh phải bằng 1" như quy tắc JDBC toàn cục; nó chỉ hợp lý với nghiệp vụ/SQL phù hợp và driver có count đáng tin.

### 13.2. Với bảng rất lớn, thử nghiệm trước trong môi trường an toàn

Một câu `UPDATE` ảnh hưởng tỷ dòng có thể tạo transaction log khổng lồ, locks kéo dài, pressure lên replication, storage và rollback. Đừng xem `executeLargeUpdate` như “câu lệnh tối ưu cho dữ liệu lớn”; nó chỉ đổi **kiểu trả update count**, không tự batch/partition công việc hay giảm tác động DB.

Nếu cần migration hàng tỷ dòng, có thể chia công việc theo key ranges với checkpoint, kiểm soát lock/log và rollback theo kế hoạch. Update count `long` hỗ trợ **đo lường**, không thay kiến trúc migration.

## 14. Chương trình Java 8 chạy độc lập — giả lập JDBC driver có count > int

JDK không tích hợp một cơ sở dữ liệu đầy đủ có thể mặc định dùng trên mọi môi trường. Vì vậy ví dụ thực thi bên dưới dùng **Java Dynamic Proxy** để làm một **JDBC driver giả lập**, cho phép gọi thật các method interface `Statement` và `PreparedStatement` nhưng **không gửi SQL đến DB**.

Đây là khác biệt quan trọng:

- **Đã được kiểm thử thực:** cú pháp Java 8 của `executeLargeUpdate`/`executeLargeBatch`, kiểu trả `long`/`long[]`, cách code phân loại sentinel, lấy `getLargeUpdateCounts`, sử dụng `getLargeUpdateCount` và phát hiện narrowing overflow.
- **Chưa được kiểm thử bằng giả lập:** driver thật có hỗ trợ large update counts hay không, DBMS tính affected rows ra sao, transaction rollback/commit, SQL plan, generated keys, hiệu năng.
- Các con số `3_000_000_000L` và `2_500_000_000L` là **giá trị fixture của fake driver**, không phải báo cáo dữ liệu thật.

Mẫu này giúp học chính xác **API và logic xử lý kết quả** mà không phải tạo hàng tỷ record. Mẫu SQL thực ở mục 13 dành cho integration test với database có schema phù hợp.

Tạo file **JdbcLargeCountDemo.java**:

```java
import java.lang.reflect.InvocationHandler;
import java.lang.reflect.Method;
import java.lang.reflect.Proxy;
import java.sql.BatchUpdateException;
import java.sql.PreparedStatement;
import java.sql.SQLException;
import java.sql.SQLFeatureNotSupportedException;
import java.sql.Statement;
import java.util.Arrays;

public class JdbcLargeCountDemo {
    static final long HUGE = 3_000_000_000L;
    static final long[] OK = {
        3L, 2_500_000_000L, Statement.SUCCESS_NO_INFO
    };
    static final long[] FAILED = {
        2_500_000_000L, Statement.EXECUTE_FAILED,
        Statement.SUCCESS_NO_INFO
    };

    static final class FakeDriver implements InvocationHandler {
        private final boolean prepared;
        private final boolean failBatch;
        private int batched;
        private long current = -1L;
        private boolean closed;

        FakeDriver(boolean prepared, boolean failBatch) {
            this.prepared = prepared;
            this.failBatch = failBatch;
        }

        @Override
        public Object invoke(Object proxy, Method method, Object[] args)
                throws Throwable {
            String name = method.getName();
            if (name.equals("close")) {
                closed = true;
                return null;
            }
            if (name.equals("isClosed")) {
                return closed;
            }
            if (closed) {
                throw new SQLException("statement already closed");
            }
            if (name.equals("setLong") || name.equals("setString")) {
                return null;
            }
            if (name.equals("addBatch")) {
                batched++;
                return null;
            }
            if (name.equals("clearBatch")) {
                batched = 0;
                return null;
            }
            if (name.equals("executeLargeUpdate")) {
                int argCount = args == null ? 0 : args.length;
                if ((prepared && argCount != 0)
                        || (!prepared && argCount == 0)) {
                    throw new SQLException("wrong executeLargeUpdate overload");
                }
                current = HUGE;
                return current;
            }
            if (name.equals("executeLargeBatch")) {
                if (batched != 3) {
                    throw new SQLException("demo expects three batch commands");
                }
                batched = 0;
                if (failBatch) {
                    throw new BatchUpdateException(
                        "simulated batch error", "23000", 7,
                        FAILED.clone(), new SQLException("duplicate key"));
                }
                return OK.clone();
            }
            if (name.equals("execute")) {
                current = HUGE;
                return false;
            }
            if (name.equals("getLargeUpdateCount")) {
                return current;
            }
            if (name.equals("getMoreResults")) {
                current = -1L;
                return false;
            }
            throw new SQLFeatureNotSupportedException(
                "demo fake does not implement " + name);
        }
    }

    @SuppressWarnings("unchecked")
    static <T> T fake(Class<T> type, boolean failBatch) {
        return (T) Proxy.newProxyInstance(
            JdbcLargeCountDemo.class.getClassLoader(),
            new Class<?>[] {type},
            new FakeDriver(type == PreparedStatement.class, failBatch));
    }

    static long sumKnown(long[] counts) {
        long total = 0L;
        for (long count : counts) {
            if (count >= 0L) {
                total = Math.addExact(total, count);
            }
        }
        return total;
    }

    static boolean totalExact(long[] counts) {
        for (long count : counts) {
            if (count < 0L) {
                return false;
            }
        }
        return true;
    }

    public static void main(String[] args) throws SQLException {
        System.out.println("int max: " + Integer.MAX_VALUE);
        System.out.println("huge count fits long: " + (HUGE > Integer.MAX_VALUE));
        System.out.println("SUCCESS_NO_INFO: " + Statement.SUCCESS_NO_INFO);
        System.out.println("EXECUTE_FAILED: " + Statement.EXECUTE_FAILED);

        try (Statement statement = fake(Statement.class, false)) {
            long count = statement.executeLargeUpdate(
                "UPDATE demo SET processed = 1");
            System.out.println("Statement large update: " + count);
            boolean isResultSet = statement.execute(
                "UPDATE demo SET processed = 2");
            System.out.println("Execute returns ResultSet: " + isResultSet);
            System.out.println("Current large update count: "
                + statement.getLargeUpdateCount());
            statement.getMoreResults();
            System.out.println("No more updates: "
                + (statement.getLargeUpdateCount() == -1L));

            statement.addBatch("UPDATE demo SET processed = 3");
            statement.addBatch("UPDATE demo SET processed = 4");
            statement.addBatch("UPDATE demo SET processed = 5");
            long[] results = statement.executeLargeBatch();
            System.out.println("Statement batch counts: "
                + Arrays.toString(results));
            System.out.println("Batch known sum: " + sumKnown(results));
            System.out.println("Batch total exact: " + totalExact(results));
        }

        try (PreparedStatement prepared =
                fake(PreparedStatement.class, false)) {
            prepared.setLong(1, 101L);
            System.out.println("Prepared large update: "
                + prepared.executeLargeUpdate());
            for (int i = 0; i < 3; i++) {
                prepared.setLong(1, i + 1L);
                prepared.addBatch();
            }
            System.out.println("Prepared batch counts: "
                + Arrays.toString(prepared.executeLargeBatch()));
            boolean sqlTextOverloadRejected = false;
            try {
                prepared.executeLargeUpdate(
                    "UPDATE demo SET processed = 6");
            } catch (SQLException expected) {
                sqlTextOverloadRejected = true;
            }
            System.out.println("Prepared SQL-text overload rejected: "
                + sqlTextOverloadRejected);
        }

        try (Statement failing = fake(Statement.class, true)) {
            failing.addBatch("UPDATE demo SET processed = 7");
            failing.addBatch("UPDATE demo SET processed = 8");
            failing.addBatch("UPDATE demo SET processed = 9");
            try {
                failing.executeLargeBatch();
            } catch (BatchUpdateException failure) {
                long[] partial = failure.getLargeUpdateCounts();
                System.out.println("Failed batch SQLState: "
                    + failure.getSQLState());
                System.out.println("Failed batch counts: "
                    + Arrays.toString(partial));
                System.out.println("Failed batch known sum: "
                    + sumKnown(partial));
                System.out.println("Failed batch exact: "
                    + totalExact(partial));
                System.out.println("Second item failed: "
                    + (partial[1] == Statement.EXECUTE_FAILED));
            }
        }

        boolean rejectedNarrowing = false;
        try {
            Math.toIntExact(HUGE);
        } catch (ArithmeticException expected) {
            rejectedNarrowing = true;
        }
        System.out.println("int narrowing rejected: " + rejectedNarrowing);
    }
}
```

### 14.1. Giải thích từng nhóm stdout

1. **Giới hạn:** `Integer.MAX_VALUE = 2147483647`, trong khi fixture `HUGE = 3000000000` vượt int nhưng vẫn nằm trong long.
2. **Hằng số JDBC:** `SUCCESS_NO_INFO = -2` và `EXECUTE_FAILED = -3`. Đây không phải các update counts thực âm.
3. **`Statement.executeLargeUpdate`:** fake driver trả `3_000_000_000L` trực tiếp. Trên DB thật, count được lấy từ driver, không phải giá trị cố định như fixture.
4. **`execute()` + `getLargeUpdateCount()`:** fake đặt current count khi mô phỏng DML. Sau `getMoreResults()` nó đặt `-1` để biểu diễn không còn kết quả. Đây là mô phỏng chính xác **kiểu API** và nhánh của demo, không phải thử nghiệm real DB multiple results.
5. **`executeLargeBatch()`:** ba lệnh trả `[3,2500000000,-2]`. `sumKnown` chỉ cộng hai số không âm thành `2500000003`; vì có unknown `-2`, `totalExact` trả false.
6. **`PreparedStatement`:** overload không tham số thực thi fixture, còn overload truyền SQL text bị giả lập ném `SQLException` để minh họa hợp đồng không được dùng trên prepared statement.
7. **`BatchUpdateException`:** fake tạo một exception với SQLState `23000` và `long[]` gồm count lớn, một `EXECUTE_FAILED`, một `SUCCESS_NO_INFO`. Cấu trúc phản ánh ví dụ driver **tiếp tục sau lỗi**, không bảo đảm mọi DB sẽ làm thế.
8. **Kiểm tra narrowing:** `Math.toIntExact(3_000_000_000L)` ném `ArithmeticException`. Code catch để in `true`, chứng minh không thể ép an toàn về int.

### 14.2. Vì sao không tự tạo 3 tỷ bản ghi cho unit test?

Một test tạo hàng tỷ row chỉ để “kiểm tra long API” có chi phí storage, transaction log và thời gian không phù hợp với unit test. Fake driver ở đây kiểm tra **hành vi client và việc bảo toàn kiểu long**. Còn chứng minh driver/database thật có thể **báo count > Integer.MAX_VALUE** đòi hỏi integration test với phiên bản driver, database, schema và dữ liệu/fixture thích hợp; không thể suy ra từ kết quả mock.

## 15. Chiến lược kiểm thử đúng cấp

### 15.1. Unit test không DB

Nên test các phần **thuần logic**:

- `long count = 3_000_000_000L` đi qua service và DTO mà không bị ép int.
- `long[]{3,2_500_000_000,-2}` được phân loại thành known sum + unknown, không cộng `-2`.
- Mảng lỗi `{2_500_000_000,-3,-2}` không bị gọi là thành công.
- `getLargeUpdateCounts` được dùng trong catch `BatchUpdateException`.
- `Math.addExact` phát hiện tổng vượt long.
- Giá trị `-1` của `getLargeUpdateCount` không bị tính là -1 dòng cập nhật.
- Phân biệt overload `Statement.executeLargeUpdate(sql)` và `PreparedStatement.executeLargeUpdate()`.

### 15.2. Integration test trên DB thật

Cần có driver/database/schema test phù hợp:

1. Tạo bảng tạm hoặc schema test được quản lý, không dùng production.
2. Tạo `PreparedStatement` có tham số thật và thử `executeLargeUpdate()` với vài dòng để xác minh driver **không ném unsupported exception**.
3. Xác nhận `executeLargeBatch()` trả mảng đúng thứ tự các bộ tham số.
4. Kiểm tra `SUCCESS_NO_INFO` nếu driver đưa sentinel theo đường thực.
5. Tạo lỗi controlled (ví dụ vi phạm unique constraint) để xem chiều dài `getLargeUpdateCounts()` và driver có tiếp tục sau lỗi hay không.
6. Kiểm tra transaction và rollback khi `setAutoCommit(false)`.
7. Kiểm tra `getGeneratedKeys()` riêng nếu ứng dụng cần.
8. Test behavior dưới DB transaction isolation, timeouts và connection interruption theo môi trường triển khai.

**Không** giả định integration test vài hàng chứng minh large counts được báo đúng khi >2,1 tỷ. Muốn kiểm chứng giới hạn lớn cần nguồn dữ liệu/driver test đặc thù với chi phí được chấp nhận và thiết kế an toàn.

### 15.3. Test portability giữa các driver

Một driver có thể hỗ trợ `executeLargeUpdate` và `executeLargeBatch`, còn driver khác có thể không. Bộ test liên database nên phân biệt:

- **Supported behavior:** các method chạy được và trả kết quả.
- **Unsupported behavior:** ném `UnsupportedOperationException` hoặc `SQLFeatureNotSupportedException` theo hợp đồng/driver.
- **Vendor semantics:** cách đếm affected/matched rows, generated keys, batch error continuation, transaction.
- **Database/version constraints:** khả năng số dòng thực tế vượt `Integer.MAX_VALUE`.

Không catch mọi exception rồi đổi thành `count = 0` để “đồng nhất” kết quả: cách đó làm lỗi driver bị che.

## 16. Hiệu năng và giới hạn thực tế

### 16.1. Large method không làm SQL chạy nhanh hơn

`executeLargeUpdate` mở rộng **kiểu trả về**, không có bảo đảm dùng thuật toán DB nhanh hơn `executeUpdate`. Tốc độ thao tác chủ yếu do SQL plan, index, locks, transaction size, số dòng, network và I/O của DBMS.

Tương tự, `executeLargeBatch` không tự khiến mọi driver dùng một wire protocol/batching tối ưu. Một số driver rewrite batch, một số gửi từng statement; kết quả và performance phải đo theo driver/DBMS thực tế.

### 16.2. Giới hạn bộ nhớ cho batch

Một batch có nhiều bộ tham số sẽ giữ metadata và dữ liệu cho đến lúc thực thi/clear theo implementation. Với input rất lớn, xử lý theo chunks có kích thước hợp lý:

```java
for (int i = 0; i < items.size(); i += batchSize) {
    int end = Math.min(i + batchSize, items.size());
    for (int j = i; j < end; j++) {
        bindItem(ps, items.get(j));
        ps.addBatch();
    }
    long[] counts = ps.executeLargeBatch();
    recordCounts(counts);
    ps.clearBatch();
}
```

Đây là snippet kiến trúc, cần `items`, `batchSize > 0`, `ps` và helper. `clearBatch` hữu ích để chủ động xóa danh sách lệnh còn chờ, nhưng sau `executeLargeBatch` thường batch đã được xử lý theo hợp đồng; không dùng `clearBatch` như một phép rollback hoặc cách xóa dữ liệu đã commit.

### 16.3. Timeout và cancellation

`Statement.setQueryTimeout(seconds)` có thể thiết lập deadline phía JDBC/driver cho thao tác; khi timeout, driver có thể ném `SQLTimeoutException`. Hiệu lực, cách server dừng lệnh và trạng thái transaction là vấn đề **driver/DBMS**. Nếu call bị timeout hoặc mất connection, **không tự suy luận** count = 0 hay SQL chưa từng thực thi. Phải xử lý trạng thái không xác định và reconciliation khi nghiệp vụ quan trọng.

### 16.4. Connection pooling và resource management

Trong service, kết nối thường đến từ pool; dùng `try-with-resources` cho `PreparedStatement` và `ResultSet`, đồng thời đảm bảo connection được trả về pool đúng scope. Không chia sẻ một `PreparedStatement` mutable giữa các thread mà không có hợp đồng đồng bộ; mỗi invocation cập nhật parameter state và batch state.

## 17. Các lỗi phổ biến và cách tránh

1. **Dùng `long count = executeUpdate()` và tưởng đã lấy count lớn.** Sai: kết quả int được mở rộng sau khi có thể mất dữ liệu. Dùng `executeLargeUpdate` nếu cần.
2. **Gọi `ps.executeLargeUpdate(sql)` trên PreparedStatement.** Sai overload; dùng `ps.executeLargeUpdate()`.
3. **Dùng `executeLargeUpdate("SELECT ...")`.** Sai loại statement nếu câu trả ResultSet; dùng `executeQuery`/`execute`.
4. **Coi `executeLargeBatch` trả một long tổng.** Sai: trả `long[]` một phần tử theo từng lệnh.
5. **Cộng thẳng cả `long[]`.** Sai nếu chứa `SUCCESS_NO_INFO`; phân loại sentinel trước.
6. **Hiểu `SUCCESS_NO_INFO` là 0 dòng hoặc lỗi.** Sai: thành công nhưng không biết count.
7. **Hiểu `EXECUTE_FAILED` là số dòng âm.** Sai: marker thất bại trong kết quả batch exception.
8. **Dùng `BatchUpdateException.getUpdateCounts()` khi count vượt int.** Có thể overflow; dùng `getLargeUpdateCounts()`.
9. **Tưởng mọi batch exception luôn có mảng full-size.** Driver có thể dừng tại lệnh lỗi; mảng thường ngắn hơn.
10. **Tưởng driver chắc chắn dừng khi một lệnh lỗi.** Một số driver tiếp tục, có thể có `EXECUTE_FAILED`.
11. **Giả định batch là một transaction.** Phụ thuộc auto-commit, DBMS và transaction boundary.
12. **Retry batch vô điều kiện sau lỗi mạng.** Có thể tạo side effects lặp khi commit outcome không biết.
13. **Coi `getLargeUpdateCount() == -1` là -1 dòng.** `-1` là sentinel không có count hiện tại.
14. **Coi `execute(sql) == false` nghĩa count chắc chắn hợp lệ.** Còn phải gọi `getLargeUpdateCount` và xử lý -1.
15. **Gọi `getLargeUpdateCount` nhiều lần cho cùng result như một metric polling.** Javadoc khuyến nghị một lần mỗi result; dùng đúng chuỗi xử lý kết quả.
16. **Coi `getLargeMaxRows` là số dòng UPDATE đã tác động.** Đó là ResultSet max rows setting.
17. **Coi `RETURN_GENERATED_KEYS` thay cho update count.** Generated keys đi qua `getGeneratedKeys` riêng.
18. **Gọi SQL update có input bằng nối chuỗi.** Có thể SQL injection; dùng PreparedStatement bind params.
19. **Tin compile Java 8 là mọi driver đều hỗ trợ.** Default methods có thể ném unsupported; kiểm thử driver cụ thể.
20. **Im lặng fallback từ long về int.** Có thể mất count; chỉ làm khi đã chứng minh upper bound.
21. **Narrowing cast `(int)longCount`.** Có thể tràn im lặng; giữ long hoặc `Math.toIntExact` khi bắt buộc.
22. **Dùng số âm sentinel để tính số dòng.** Phân biệt -1/-2/-3 theo method và ngữ cảnh.
23. **Cho rằng SQL DDL trả 0 nghĩa không chạy.** DDL thành công có thể trả 0 theo contract.
24. **Tin update count luôn bằng số bản ghi “thật sự đổi nội dung”.** DBMS/driver có thể khác nhau về matched/changed rows.
25. **Không đóng Statement/ResultSet.** Có thể leak resource; dùng try-with-resources.
26. **Trộn transaction management của framework và JDBC thủ công.** Dễ làm sai auto-commit/rollback; thống nhất một owner.
27. **Không xử lý rollback failure.** Có thể che lỗi đầu tiên; giữ suppressed exceptions/log an toàn.
28. **Bỏ qua `SQLException.getNextException()`.** Có thể mất chẩn đoán chi tiết driver; xem cause chain trong log kỹ thuật.
29. **Benchmark bằng giả lập và kết luận DB thật nhanh.** Mock chỉ test code xử lý API; hiệu năng cần DB thật.
30. **Dùng số dòng batch để suy ra generated keys.** Không có tương ứng mặc định; kiểm tra driver riêng.

## 18. Bảng lựa chọn API theo mục tiêu

| Bạn muốn làm gì? | API phù hợp | Kiểu kết quả | Điều cần nhớ |
| --- | --- | --- | --- |
| Update tĩnh có thể ảnh hưởng > 2,1 tỷ dòng | `Statement.executeLargeUpdate(sql)` | `long` | Driver phải hỗ trợ |
| Update có tham số bind | `PreparedStatement.executeLargeUpdate()` | `long` | Không truyền SQL text ở lúc execute |
| Gửi nhiều SQL text | `Statement.addBatch(sql)` + `executeLargeBatch()` | `long[]` | Không nối user input |
| Gửi nhiều bộ tham số | `PreparedStatement.addBatch()` + `executeLargeBatch()` | `long[]` | Một count cho từng lệnh |
| Batch thất bại | `BatchUpdateException.getLargeUpdateCounts()` | `long[]` | Có thể partial/full tùy driver |
| `execute(sql)` trả cập nhật | `getLargeUpdateCount()` | `long` | `-1` nghĩa không có count |
| Cần chỉ biết zero/one vài dòng, driver không hỗ trợ large | `executeUpdate()` sau khi đánh giá yêu cầu | `int` | Không bảo toàn count > int |
| Cần generated key của INSERT | `getGeneratedKeys()` | `ResultSet` | Khác với update count |
| Muốn hạn chế ResultSet rows | `setLargeMaxRows(long)` | Không trả count DML | Không phải limit của UPDATE |
| Cần tổng count chính xác | Xử lý `count >= 0`, từ chối unknown | `long`/`BigInteger` | Không cộng sentinel |
| Chỉ cần biết batch thành công, count có thể unknown | Phân loại `SUCCESS_NO_INFO` | State + known counts | Không báo tổng chính xác |
| Batch phải all-or-nothing | Transaction + commit/rollback | Trạng thái giao dịch | Không được suy ra từ tên method |
| Cần chống SQL injection | `PreparedStatement` với bind | `long` hoặc `long[]` | Hợp đồng input riêng |

## 19. Câu hỏi ôn luyện và lời giải

**1. Vì sao JDBC 4.2 thêm `executeLargeUpdate`?**  
Vì `executeUpdate` trả int, không đủ biểu diễn một số update counts > `Integer.MAX_VALUE`. Large version trả long.

**2. `Statement.executeLargeUpdate(sql)` trả kiểu gì?**  
`long`.

**3. `PreparedStatement.executeLargeUpdate(sql)` có đúng không?**  
Không. Dùng `PreparedStatement.executeLargeUpdate()` không tham số, sau khi bind `?`.

**4. `executeLargeBatch` trả `long` hay `long[]`?**  
`long[]`, theo thứ tự thêm lệnh vào batch.

**5. Nếu `counts = {1, 3, -2}`, tổng affected rows có chính xác bằng 2 không?**  
Không. `-2` là `SUCCESS_NO_INFO`; biết hai lệnh đầu ảnh hưởng 4 dòng, lệnh thứ ba thành công nhưng count không biết.

**6. `Statement.SUCCESS_NO_INFO` có giá trị bao nhiêu?**  
`-2`, thành công nhưng count không được cung cấp.

**7. `Statement.EXECUTE_FAILED` có giá trị bao nhiêu?**  
`-3`, thường là marker lệnh lỗi trong mảng update counts của `BatchUpdateException` khi driver tiếp tục xử lý.

**8. `getLargeUpdateCount() == -1L` báo điều gì?**  
Không có update count hiện tại hoặc kết quả hiện tại là ResultSet.

**9. Tại sao không dùng `long count = ps.executeUpdate()` để lấy count cực lớn?**  
Vì driver đã trả int, phép gán long chỉ mở rộng kết quả int.

**10. JDBC driver cũ không override large methods thì sao?**  
Có thể gặp `UnsupportedOperationException` hoặc `SQLFeatureNotSupportedException` tùy method; cần kiểm thử trên driver cụ thể.

**11. Batch có năm lệnh, lỗi ở lệnh thứ ba, `getLargeUpdateCounts` chắc chắn dài năm phần tử không?**  
Không. Nếu driver dừng ở lỗi, mảng có thể chỉ ghi kết quả các lệnh trước; nếu tiếp tục có thể trả đủ phần tử với marker `EXECUTE_FAILED`.

**12. `executeLargeBatch` có tự rollback các lệnh thành công trước khi lỗi không?**  
Không được coi là bảo đảm. Transaction/auto-commit/driver và DBMS quyết định; ứng dụng cần xử lý transaction rõ.

**13. Có nên cộng mọi `long` trong array để lấy tổng không?**  
Không. Phải loại sentinel âm, phát hiện unknown/failure và kiểm tra overflow.

**14. `Math.addExact` giúp gì khi cộng update counts?**  
Phát hiện overflow của phép cộng signed long bằng `ArithmeticException`.

**15. `getLargeMaxRows` có báo số dòng UPDATE ảnh hưởng không?**  
Không, đó là cấu hình/giới hạn số dòng của ResultSet.

**16. Có thể dùng `executeLargeUpdate` cho câu SELECT trả ResultSet không?**  
Không. Câu SQL trả ResultSet nên dùng `executeQuery`/`execute` tùy trường hợp.

**17. Update count 0 luôn là lỗi không?**  
Không. Một UPDATE có `WHERE` không khớp dòng nào có thể thành công với count 0.

**18. `BatchUpdateException.getUpdateCounts` khác gì `getLargeUpdateCounts`?**  
Bản đầu trả `int[]`, bản thứ hai trả `long[]`, nên bản lớn an toàn hơn với count > int.

**19. Vì sao dùng PreparedStatement cho input người dùng?**  
Có bind parameters, tránh nối dữ liệu người dùng thành cú pháp SQL và hỗ trợ reuse/batch.

**20. Generated key có được lấy từ `long count` không?**  
Không; dùng `getGeneratedKeys()` theo hỗ trợ driver.

**21. Có thể dùng một mock driver để xác nhận driver production báo hơn 2,1 tỷ dòng chính xác không?**  
Không; mock chỉ chứng minh code client xử lý long đúng. Cần integration test trên driver/database thật với điều kiện phù hợp.

**22. Nếu auto-commit tắt và executeLargeBatch trả về counts thành công thì transaction đã commit chưa?**  
Chưa nhất thiết; cần `connection.commit()`.

**23. Nếu mất kết nối khi commit, retry toàn bộ batch có an toàn không?**  
Không tự động. Có thể đã commit nhưng client không biết; cần idempotency và reconciliation.

**24. Mảng count có một `SUCCESS_NO_INFO` thì có được báo tổng chính xác không?**  
Không. Chỉ báo được tổng các count đã biết kèm trạng thái unknown.

**25. Các large methods còn áp dụng trên Java hiện đại không?**  
Có. Chúng thuộc JDBC 4.2 / Java 8 và vẫn hiện diện trong API `java.sql` hiện hành; mức hỗ trợ thực tế vẫn do JDBC driver và DBMS.

## 20. Tài liệu chính thức vẫn áp dụng

Các nguồn dưới đây có đầy đủ chữ ký API Java 8 và mô tả contract trong JDK hiện đại:

- [`java.sql.Statement` — Java SE 25](https://docs.oracle.com/en/java/javase/25/docs/api/java.sql/java/sql/Statement.html): `executeLargeUpdate`, `executeLargeBatch`, `getLargeUpdateCount`, `setLargeMaxRows`, các sentinel và default-method behavior.
- [`java.sql.PreparedStatement` — Java SE 25](https://docs.oracle.com/en/java/javase/25/docs/api/java.sql/java/sql/PreparedStatement.html): `executeLargeUpdate()` không tham số, `addBatch()`, bind parameters và inherited JDBC methods.
- [`java.sql.BatchUpdateException` — Java SE 25](https://docs.oracle.com/en/java/javase/25/docs/api/java.sql/java/sql/BatchUpdateException.html): `getLargeUpdateCounts`, constructor nhận `long[]`, driver tiếp tục hoặc dừng khi batch lỗi.
- [`java.sql.Connection` — Java SE 25](https://docs.oracle.com/en/java/javase/25/docs/api/java.sql/java/sql/Connection.html): `setAutoCommit`, `commit`, `rollback`, transaction semantics và resource lifecycle.
- [`java.sql.DatabaseMetaData` — Java SE 25](https://docs.oracle.com/en/java/javase/25/docs/api/java.sql/java/sql/DatabaseMetaData.html): JDBC version và `supportsBatchUpdates`.
- [`java.sql.Statement` — Java 8](https://docs.oracle.com/javase/8/docs/api/java/sql/Statement.html): xác nhận API large được giới thiệu từ Java 8.
- [`java.sql.PreparedStatement` — Java 8](https://docs.oracle.com/javase/8/docs/api/java/sql/PreparedStatement.html): overload `executeLargeUpdate()` trong JDBC 4.2.
- [`java.sql.BatchUpdateException` — Java 8](https://docs.oracle.com/javase/8/docs/api/java/sql/BatchUpdateException.html): `getLargeUpdateCounts()` và `long[]` constructor, ngữ nghĩa mảng khi batch thất bại.

**Kết luận:** khi có khả năng cập nhật vượt `Integer.MAX_VALUE`, cần **gọi đúng large API**, giữ count kiểu `long` qua toàn bộ các tầng, xử lý `long[]` theo từng lệnh và **không cộng sentinel**. Đồng thời phải xác minh hỗ trợ của JDBC driver, xử lý `BatchUpdateException` và transaction rõ ràng. `long` chỉ giải quyết giới hạn kiểu dữ liệu của update count — không tự giải quyết atomicity, retry, generated keys hay hiệu năng DB.
