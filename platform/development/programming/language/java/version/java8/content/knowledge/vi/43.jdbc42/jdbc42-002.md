# SQLType, JDBCType và mã kiểu SQL trong JDBC 4.2

## 1. Vấn đề mà JDBC 4.2 giải quyết

Khi làm việc với cơ sở dữ liệu quan hệ trong Java, có ít nhất ba hệ thống kiểu cần phân biệt:

1. **Kiểu dữ liệu Java** của đối tượng trong ứng dụng: `Integer`, `String`, `BigDecimal`, `LocalDate`, `OffsetDateTime`, v.v.
2. **Kiểu dữ liệu SQL** của cột hoặc tham số: `INTEGER`, `VARCHAR`, `DECIMAL`, `DATE`, `TIMESTAMP WITH TIME ZONE` hoặc kiểu riêng của hệ quản trị.
3. **Mã kiểu JDBC** mà driver báo cáo/nhận vào: các hằng số `int` trong `java.sql.Types` hoặc các đối tượng kiểu `SQLType`.

**JDBC 4.2**, thuộc Java 8, bổ sung `java.sql.SQLType` và enum `java.sql.JDBCType`. Hai API này giúp diễn đạt **kiểu SQL bằng đối tượng có tên, vendor và mã**, thay vì chỉ truyền một số nguyên khó hiểu.

Ví dụ:

```java
// Hai cách mô tả kiểu JDBC INTEGER
int code = Types.INTEGER;
SQLType type = JDBCType.INTEGER;
```

*Đây là snippet minh họa: cần import `java.sql.Types`, `java.sql.SQLType` và `java.sql.JDBCType`. Không phải chương trình độc lập.*

Những API trên **vẫn còn áp dụng** trong JDK hiện hành. `Types` dạng `int` **không bị loại bỏ** và vẫn cần thiết vì nhiều API metadata/overload dùng số nguyên. Không coi `JDBCType` là sự thay thế hoàn toàn tất cả API nhận `int`.

### Mục tiêu

Sau bài này, bạn sẽ:

- Hiểu đúng `SQLType` (interface), `JDBCType` (enum) và `Types` (class chứa hằng số `int`).
- Dùng `getName()`, `getVendor()` và `getVendorTypeNumber()`.
- Đổi mã JDBC chuẩn sang enum bằng `JDBCType.valueOf(int)` và xử lý mã chưa biết.
- Phân biệt **enum ordinal**, **tên kiểu**, **mã kiểu**, **tên SQL của database** và **vendor-specific code**.
- Dùng overload `PreparedStatement.setObject(...,SQLType)`, `CallableStatement.registerOutParameter(...,SQLType)` và `ResultSet.updateObject(...,SQLType)`.
- Hiểu **driver compatibility**: method mặc định nhận `SQLType` có thể ném `SQLFeatureNotSupportedException`.
- Khai báo vendor-specific `SQLType` khi driver thật sự hỗ trợ.
- Chọn kiểu cho `BigDecimal`, `LocalDate`, `LocalDateTime`, `OffsetDateTime`, SQL NULL và dữ liệu JSON theo phiên bản JDK/driver.
- Đọc `ResultSetMetaData`, `ParameterMetaData` và `DatabaseMetaData` để tìm thông tin từ driver thay vì đoán.
- Viết code an toàn với parameterized SQL, resource management và unit tests không cần database; biết khi nào phải có integration tests với driver thật.

Ví dụ được viết cho **Java 17+** và chỉ dùng các hằng số chuẩn tồn tại từ JDBC 4.2. Những bổ sung mới của JDBC 4.5 trên **JDK 26** được nêu rõ, tránh để ví dụ Java 17 không biên dịch.

## 2. Sơ đồ các tầng

```text
Ứng dụng Java
    |
    |  BigDecimal("19.75"), LocalDate, String...
    v
PreparedStatement.setObject(index, value, SQLType)
    |
    |  SQLType -> JDBCType.DECIMAL / custom vendor SQLType
    |  getName / getVendor / getVendorTypeNumber
    v
JDBC Driver (kiểm tra hỗ trợ + chuyển kiểu)
    |
    |  SQL/DB protocol, mã kiểu và cấu hình riêng
    v
Database
    |
    |  DECIMAL(10,2), VARCHAR(100), DATE, ...
    v
ResultSet / ResultSetMetaData
    |
    |  getColumnType() -> int (Types code)
    |  getColumnTypeName() -> String từ DB/driver
    v
Java data model
```

**Một mã kiểu không phải dữ liệu thực.** `JDBCType.INTEGER` mô tả **loại** của giá trị, không chứa số 42. `JDBCType.NULL` là một constant đại diện generic JDBC type `NULL`, không tự thực hiện thao tác gán SQL NULL cho một tham số.

**Một kiểu JDBC generic không tương đương chính xác mọi kiểu vendor.** Ví dụ DB có thể cung cấp JSON, UUID, ARRAY, domain/UDT hoặc timestamp semantics riêng. Driver có thể ánh xạ chúng sang `Types.OTHER` hoặc mã tùy biến, hoặc sang một kiểu generic khác. Không suy luận hành vi driver chỉ từ tên SQL trông giống nhau.

## 3. Ba API cốt lõi

| API | Java declaration | Ý nghĩa | Ví dụ |
| --- | --- | --- | --- |
| `java.sql.SQLType` | Interface | Hợp đồng mô tả một kiểu JDBC hoặc vendor-specific | `SQLType type = JDBCType.INTEGER` |
| `java.sql.JDBCType` | `enum implements SQLType` | Tập kiểu JDBC generic được chuẩn hóa | `JDBCType.VARCHAR` |
| `java.sql.Types` | Class với `public static final int` | Mã kiểu JDBC dạng số, vẫn được dùng rộng rãi | `Types.VARCHAR` |

Các phương thức của `SQLType`:

```java
String getName();
String getVendor();
Integer getVendorTypeNumber();
```

*Đây là các signature rút gọn từ interface, không phải class Java độc lập.*

**`getName()`:** tên SQLType đại diện, ví dụ `"VARCHAR"`. Với custom vendor type, có thể là tên riêng như `"UUID"`.

**`getVendor()`:** tên vendor, thường dùng định danh dạng package; các hằng số `JDBCType` trả **`"java.sql"`**.

**`getVendorTypeNumber()`:** mã kiểu `Integer`. Với `JDBCType`, nó bằng hằng số `Types` tương ứng. Với custom `SQLType`, số này thuộc không gian mã và hợp đồng của vendor/driver.

**Quan trọng:** cùng giá trị `int` không chứng minh hai kiểu của hai vendor là tương đương. Muốn hiểu một custom type, phải biết **vendor** và **database/driver contract**.

## 4. Bài chạy 1: SQLType, JDBCType và Types khớp như thế nào?

Lưu `BasicJdbcTypesDemo.java`:

```java
import java.sql.JDBCType;
import java.sql.SQLType;
import java.sql.Types;
import java.util.List;

public class BasicJdbcTypesDemo {
    public static void main(String[] args) {
        List<SQLType> types = List.of(
                JDBCType.INTEGER,
                JDBCType.VARCHAR,
                JDBCType.DECIMAL,
                JDBCType.BOOLEAN,
                JDBCType.OTHER);

        for (SQLType type : types) {
            System.out.println(type.getName()
                    + " = " + type.getVendorTypeNumber()
                    + " @ " + type.getVendor());
        }

        System.out.println("integerMatches = " +
                (JDBCType.INTEGER.getVendorTypeNumber()
                        == Types.INTEGER));
        System.out.println("varcharMatches = " +
                (JDBCType.VARCHAR.getVendorTypeNumber()
                        == Types.VARCHAR));
    }
}
```

Chạy:

```bash
javac BasicJdbcTypesDemo.java
java BasicJdbcTypesDemo
```

Stdout:

```text
INTEGER = 4 @ java.sql
VARCHAR = 12 @ java.sql
DECIMAL = 3 @ java.sql
BOOLEAN = 16 @ java.sql
OTHER = 1111 @ java.sql
integerMatches = true
varcharMatches = true
```

**Giải thích:** `JDBCType` vừa là enum vừa thỏa interface `SQLType`. Giá trị kiểu `int` của `Types.INTEGER` vẫn là 4, còn kiểu được đặt tên là `JDBCType.INTEGER`.

`Integer` từ `getVendorTypeNumber()` được tự unbox khi so với `int`. Nếu viết helper cho custom `SQLType`, không nên mù quáng unbox khi contract custom có thể trả null hoặc mã không chuẩn: hãy kiểm tra đầu vào và driver support phù hợp.

## 5. Các mã kiểu JDBC phổ biến

Một số giá trị thuộc bộ mã được công nhận rộng rãi:

| SQLType/JDBCType | `Types` numeric code | Ví dụ dùng |
| --- | ---: | --- |
| `INTEGER` | 4 | Số nguyên 32-bit ở phía JDBC |
| `BIGINT` | -5 | Số nguyên lớn |
| `SMALLINT` | 5 | Số nguyên nhỏ |
| `VARCHAR` | 12 | Chuỗi text |
| `CHAR` | 1 | Chuỗi ký tự |
| `DECIMAL` | 3 | Số thập phân chính xác |
| `NUMERIC` | 2 | Số numeric chính xác |
| `DOUBLE` | 8 | Số thực floating-point |
| `BOOLEAN` | 16 | Giá trị boolean generic |
| `DATE` | 91 | Ngày |
| `TIME` | 92 | Thời gian trong ngày |
| `TIMESTAMP` | 93 | Timestamp không mang offset trong generic mapping |
| `REF_CURSOR` | 2012 | Cursor tham chiếu |
| `TIME_WITH_TIMEZONE` | 2013 | Time with timezone/offset |
| `TIMESTAMP_WITH_TIMEZONE` | 2014 | Timestamp with timezone/offset |
| `ROWID` | -8 | SQL row identifier |
| `OTHER` | 1111 | Kiểu riêng/không nằm trong các loại chuẩn khác |
| `NULL` | 0 | Generic SQL NULL type marker |

**Đừng xem bảng trên là định nghĩa DDL cụ thể cho mọi DB.** Ví dụ `DECIMAL` là một kiểu generic; kích thước `DECIMAL(10,2)` phụ thuộc column precision/scale, còn `BOOLEAN` có thể được driver ánh xạ sang loại DB cụ thể. Tên kiểu mà metadata báo cáo có thể là tên vendor khác.

Các mã `TIME_WITH_TIMEZONE` và `TIMESTAMP_WITH_TIMEZONE` là phần JDBC 4.2. Driver có thể vẫn giới hạn khả năng sử dụng hoặc chuyển đổi Java time types; kiểm tra driver/database thật.

### 5.1. Phân biệt enum ordinal và mã kiểu

`JDBCType.INTEGER.ordinal()` là vị trí enum constant trong khai báo Java, **không phải** mã 4. Enum ordinal không nên được lưu như JDBC type code hoặc gửi qua network làm schema ổn định; thứ tự enum có thể thay đổi khi thêm constants.

`JDBCType.INTEGER.name()` là tên constant, còn `JDBCType.INTEGER.getVendorTypeNumber()` mới là mã JDBC chuẩn tương ứng `Types.INTEGER`.

## 6. Chuyển mã chuẩn thành enum

`JDBCType.valueOf(int code)` là overload đặc biệt nhận **mã từ `Types`** và trả hằng số `JDBCType` tương ứng. Nó **khác** với overload sinh tự động của enum `valueOf(String name)`.

Lưu `JdbcTypeLookupDemo.java`:

```java
import java.sql.JDBCType;
import java.sql.Types;

public class JdbcTypeLookupDemo {
    public static void main(String[] args) {
        int[] codes = {
                Types.INTEGER,
                Types.VARCHAR,
                Types.ROWID,
                Types.REF_CURSOR,
                Types.TIME_WITH_TIMEZONE,
                Types.TIMESTAMP_WITH_TIMEZONE
        };

        for (int code : codes) {
            System.out.println(code + " -> " +
                    JDBCType.valueOf(code).getName());
        }

        boolean unknownRejected = false;
        try {
            JDBCType.valueOf(987_654);
        } catch (IllegalArgumentException e) {
            unknownRejected = true;
        }

        System.out.println("unknownRejected = " +
                unknownRejected);
    }
}
```

```bash
javac JdbcTypeLookupDemo.java
java JdbcTypeLookupDemo
```

```text
4 -> INTEGER
12 -> VARCHAR
-8 -> ROWID
2012 -> REF_CURSOR
2013 -> TIME_WITH_TIMEZONE
2014 -> TIMESTAMP_WITH_TIMEZONE
unknownRejected = true
```

**Tại sao phải bắt `IllegalArgumentException`?** Một `ResultSetMetaData.getColumnType()` từ vendor có thể trả mã không thuộc bộ generic JDBC; không phải số nào cũng có `JDBCType` tương ứng. Không tự chuyển mã lạ thành `JDBCType.OTHER` mà bỏ mất thông tin gốc, nếu ứng dụng cần phân biệt custom types.

Lưu `JdbcTypeNameVsCodeDemo.java`:

```java
import java.sql.JDBCType;
import java.sql.Types;

public class JdbcTypeNameVsCodeDemo {
    public static void main(String[] args) {
        JDBCType fromCode = JDBCType.valueOf(
                Types.INTEGER);
        JDBCType fromName = JDBCType.valueOf(
                "INTEGER");

        System.out.println("enumName = " +
                JDBCType.INTEGER.name());
        System.out.println("sqlTypeName = " +
                JDBCType.INTEGER.getName());
        System.out.println("typeCode = " +
                JDBCType.INTEGER.getVendorTypeNumber());
        System.out.println("fromCodeSame = " +
                (fromCode == JDBCType.INTEGER));
        System.out.println("fromNameSame = " +
                (fromName == JDBCType.INTEGER));
    }
}
```

```bash
javac JdbcTypeNameVsCodeDemo.java
java JdbcTypeNameVsCodeDemo
```

```text
enumName = INTEGER
sqlTypeName = INTEGER
typeCode = 4
fromCodeSame = true
fromNameSame = true
```

`valueOf("INTEGER")` yêu cầu tên enum constant; nó không phân tích tự động các chuỗi DDL như `"VARCHAR(255)"` hoặc tên kiểu riêng của DB. Tên kiểu SQL thực tế nên lấy từ metadata hoặc cấu hình schema.

## 7. Kiểu riêng của vendor thông qua SQLType

Interface `SQLType` được thiết kế để hỗ trợ cả kiểu JDBC chuẩn **và kiểu vendor-specific**. Ứng dụng hoặc driver có thể định nghĩa một enum/class implements `SQLType` với `getName`, `getVendor` và `getVendorTypeNumber`.

Lưu `VendorSqlTypeDemo.java`:

```java
import java.sql.SQLType;

public class VendorSqlTypeDemo {
    enum ExampleType implements SQLType {
        UUID_TOKEN(50_001),
        VECTOR(50_002);

        private final int code;

        ExampleType(int code) {
            this.code = code;
        }

        @Override
        public String getName() {
            return name();
        }

        @Override
        public String getVendor() {
            return "com.example.database";
        }

        @Override
        public Integer getVendorTypeNumber() {
            return code;
        }
    }

    public static void main(String[] args) {
        for (SQLType type : ExampleType.values()) {
            System.out.println(type.getName()
                    + " | vendor=" + type.getVendor()
                    + " | code=" + type.getVendorTypeNumber());
        }
    }
}
```

```bash
javac VendorSqlTypeDemo.java
java VendorSqlTypeDemo
```

```text
UUID_TOKEN | vendor=com.example.database | code=50001
VECTOR | vendor=com.example.database | code=50002
```

**Quan trọng:** mã `50001` và `50002` trong ví dụ **hoàn toàn giả định** để dạy cấu trúc `SQLType`, không tuyên bố một database cụ thể dùng mã này. Class implement `SQLType` thành công chỉ chứng minh Java API hoạt động; **không** khiến bất kỳ JDBC driver nào tự hiểu kiểu đó. Driver và database phải có contract riêng cho binding/reading và có thể yêu cầu Java object riêng.

### 7.1. Trùng mã kiểu giữa các vendor

Cùng một mã số có thể được nhà cung cấp tự định nghĩa theo ý nghĩa khác. Nếu một custom `SQLType` trả vendor `"vendor.custom"`, code `4`, không được dùng `JDBCType.valueOf(4)` để suy ra đó chắc chắn là generic INTEGER.

Lưu `VendorTypeCollisionDemo.java`:

```java
import java.sql.JDBCType;
import java.sql.SQLType;
import java.sql.Types;

public class VendorTypeCollisionDemo {
    static final class CustomType implements SQLType {
        @Override
        public String getName() {
            return "CUSTOM_PAYLOAD";
        }

        @Override
        public String getVendor() {
            return "vendor.custom";
        }

        @Override
        public Integer getVendorTypeNumber() {
            return 4;
        }
    }

    public static void main(String[] args) {
        SQLType custom = new CustomType();

        System.out.println("customName = " +
                custom.getName());
        System.out.println("customVendor = " +
                custom.getVendor());
        System.out.println("collidingCode = " +
                custom.getVendorTypeNumber());
        System.out.println("genericLookup = " +
                JDBCType.valueOf(
                        custom.getVendorTypeNumber()));
        System.out.println("sameVendor = " +
                JDBCType.INTEGER.getVendor()
                        .equals(custom.getVendor()));
        System.out.println("integerCode = " +
                Types.INTEGER);
    }
}
```

```bash
javac VendorTypeCollisionDemo.java
java VendorTypeCollisionDemo
```

```text
customName = CUSTOM_PAYLOAD
customVendor = vendor.custom
collidingCode = 4
genericLookup = INTEGER
sameVendor = false
integerCode = 4
```

Đây là ví dụ **chống suy luận sai về mã**, không phải kiểu database thực. Đừng tự gọi `JDBCType.valueOf(custom.getVendorTypeNumber())` để “chuẩn hóa” vendor-specific type nếu chưa biết đó thật sự là mã trong bộ `java.sql.Types`.

## 8. Chọn SQLType cho parameterized SQL

Với một database thực, `PreparedStatement` cho phép bind tham số bằng các overload:

```java
void setObject(int parameterIndex, Object value,
               SQLType targetSqlType);

void setObject(int parameterIndex, Object value,
               SQLType targetSqlType, int scaleOrLength);
```

*Đây là chữ ký rút gọn để học API, không phải một chương trình độc lập.*

Ví dụ khi đã có `Connection conn`:

```java
String sql = """
    INSERT INTO orders(customer_name, amount, ordered_on)
    VALUES (?, ?, ?)
    """;

try (PreparedStatement ps = conn.prepareStatement(sql)) {
    ps.setObject(1, "Lan", JDBCType.VARCHAR);
    ps.setObject(2, new BigDecimal("19.75"),
                 JDBCType.DECIMAL, 2);
    ps.setObject(3, LocalDate.of(2026, 11, 6),
                 JDBCType.DATE);
    int affected = ps.executeUpdate();
}
```

*Snippet minh họa: cần imports `java.sql.*`, `java.math.BigDecimal`, `java.time.LocalDate` và `conn` là connection đã mở tới DB thật. SQL/schema/driver chưa được cung cấp nên đoạn này **không phải một chương trình chạy độc lập**. Hỗ trợ các overload `SQLType` và Java time values phụ thuộc driver.*

**Index bắt đầu từ 1**, không phải 0. Kiểu SQL trong tham số là **mục tiêu chuyển đổi**, không phải kiểu compile-time của Java value. Driver chịu trách nhiệm hỗ trợ/mapping; có thể từ chối một sự kết hợp `Java class + target SQLType` bằng `SQLException` hoặc `SQLFeatureNotSupportedException`.

**Parameterized SQL** (dấu `?` cho dữ liệu) giúp tránh nối thẳng giá trị user vào câu SQL; nhưng `?` **không thay thế** tên bảng/cột/keyword SQL động. Với identifier động phải dùng allowlist/quoting theo driver, không xây SQL bằng chuỗi không tin cậy.

### 8.1. Tại sao vẫn phải dùng try-with-resources?

`PreparedStatement` và `ResultSet` là JDBC resources. Code dùng `try (...) { ... }` để đóng chúng ngay cả khi exception xảy ra. `Connection` cũng cần lifecycle phù hợp với data source/transaction/pool. Chọn `SQLType` mới không thay thế quản lý transaction, rollback hoặc xử lý exceptions.

## 9. Một chương trình chạy được: giả lập PreparedStatement, quan sát overload

Để kiểm chứng **cú pháp Java thật** của overload mà không cần server DB, có thể tạo **dynamic proxy** của `PreparedStatement`. Proxy chỉ ghi lại các lời gọi Java; **không thực hiện SQL hoặc kiểm tra driver**.

Lưu `MockPreparedStatementDemo.java`:

```java
import java.lang.reflect.Proxy;
import java.math.BigDecimal;
import java.sql.JDBCType;
import java.sql.PreparedStatement;
import java.sql.SQLType;

public class MockPreparedStatementDemo {
    public static void main(String[] args)
            throws Exception {

        PreparedStatement ps = (PreparedStatement)
                Proxy.newProxyInstance(
                        PreparedStatement.class.getClassLoader(),
                        new Class<?>[]{PreparedStatement.class},
                        (proxy, method, values) -> {
                            if ("setObject".equals(
                                    method.getName())) {
                                Object sqlType = values[2];
                                String name =
                                        sqlType instanceof SQLType t
                                                ? t.getName()
                                                : "int:" + sqlType;
                                String scale = values.length == 4
                                        ? values[3].toString()
                                        : "none";
                                System.out.println("bind "
                                        + values[0] + " type=" + name
                                        + " value=" + values[1]
                                        + " scale=" + scale);
                            }
                            return null;
                        });

        ps.setObject(1, 42, JDBCType.INTEGER);
        ps.setObject(2, new BigDecimal("19.75"),
                     JDBCType.DECIMAL, 2);
        ps.setObject(3, null, JDBCType.VARCHAR);
    }
}
```

```bash
javac MockPreparedStatementDemo.java
java MockPreparedStatementDemo
```

```text
bind 1 type=INTEGER value=42 scale=none
bind 2 type=DECIMAL value=19.75 scale=2
bind 3 type=VARCHAR value=null scale=none
```

**Điều demo chứng minh:** Java chọn được các overload `SQLType` với `JDBCType`, kể cả trường hợp có scale và value null. Proxy không nói rằng một DB đã ghi 42, đã giữ đúng số thập phân hoặc đã thực hiện NULL. Các vấn đề đó phải được integration-test với driver/database cụ thể.

### 9.1. Default method chưa chắc driver hỗ trợ

Một sự thật rất dễ bị bỏ qua: các overload `setObject(...,SQLType)` được thêm dưới dạng **default methods** của interface, và **triển khai mặc định ném `SQLFeatureNotSupportedException`**. JDBC driver muốn hỗ trợ cần có implementation phù hợp.

Vì thế:

- Java 17 compile code dùng `JDBCType` **không có nghĩa driver trong production hỗ trợ**.
- Driver cũ hoặc một wrapper/proxy không override method typed có thể ném exception.
- Chỉ dùng fallback sang overload `int` khi đó là **mã generic tương đương và driver thực sự hỗ trợ**; đừng ép custom vendor type thành `Types.OTHER` một cách mù quáng.
- Chú ý dependency phiên bản driver và test trên combination JDK + driver + database được triển khai thật.

## 10. Fallback có kiểm soát nếu driver không hỗ trợ SQLType overload

Một số hệ thống cần tương thích driver dùng overload `int`; những phương thức này **vẫn được hỗ trợ**, không phải tính năng đã lỗi thời.

Lưu `SqlTypeFallbackDemo.java`:

```java
import java.lang.reflect.Proxy;
import java.sql.JDBCType;
import java.sql.PreparedStatement;
import java.sql.SQLFeatureNotSupportedException;
import java.sql.SQLType;
import java.sql.Types;

public class SqlTypeFallbackDemo {
    public static void main(String[] args)
            throws Exception {

        PreparedStatement ps = (PreparedStatement)
                Proxy.newProxyInstance(
                        PreparedStatement.class.getClassLoader(),
                        new Class<?>[]{PreparedStatement.class},
                        (proxy, method, values) -> {
                            if ("setObject".equals(
                                    method.getName())) {
                                if (values[2] instanceof SQLType) {
                                    throw new
                                            SQLFeatureNotSupportedException(
                                                    "typed overload");
                                }
                                System.out.println("intFallback = "
                                        + values[2]);
                            }
                            return null;
                        });

        try {
            ps.setObject(1, 42, JDBCType.INTEGER);
        } catch (SQLFeatureNotSupportedException ex) {
            ps.setObject(1, 42, Types.INTEGER);
        }
    }
}
```

```bash
javac SqlTypeFallbackDemo.java
java SqlTypeFallbackDemo
```

```text
intFallback = 4
```

**Chỉ là mô phỏng** driver typed API không hỗ trợ. Trong code thật, không catch mọi `SQLException` rồi retry một update **đã có thể thực hiện một phần**: đặc biệt với DML có side effect, fallback cần dựa trên contract, lỗi driver và trạng thái transaction. `SQLFeatureNotSupportedException` từ lần bind trước execute thường là tín hiệu khác với lỗi tại lúc execute. Thiết kế điều kiện retry/idempotency rõ ràng.

## 11. `scaleOrLength` và DECIMAL/NUMERIC

Với `PreparedStatement.setObject(index, value, JDBCType.DECIMAL, scaleOrLength)`, tham số thứ tư có **ý nghĩa theo loại value/SQLType**:

- Với `DECIMAL`/`NUMERIC`: **scale** là số chữ số sau dấu thập phân.
- Với một `InputStream`: length là **số byte** stream cần cung cấp.
- Với một `Reader`: length là **số ký tự** cần cung cấp.
- Với các kiểu khác: Javadoc quy định giá trị này có thể bị bỏ qua.

**Scale khác precision.** Ví dụ `DECIMAL(10,2)` có precision 10 và scale 2. `BigDecimal("123.456")` có scale 3; chuyển sang scale 2 cần quy tắc làm tròn rõ ràng nếu không muốn mất dữ liệu.

Lưu `DecimalScaleDemo.java`:

```java
import java.math.BigDecimal;

import java.sql.JDBCType;

public class DecimalScaleDemo {
    public static void main(String[] args) {

        BigDecimal rounded = raw.setScale(
                2, RoundingMode.HALF_UP);

        boolean exactRejected = false;
        try {
            raw.setScale(2, RoundingMode.UNNECESSARY);
        } catch (ArithmeticException ex) {
            exactRejected = true;
        }

        System.out.println("raw = " + raw);
        System.out.println("rawScale = " + raw.scale());
        System.out.println("rounded = " + rounded);
        System.out.println("roundedPrecision = " +
                rounded.precision());
        System.out.println("roundedScale = " +
                rounded.scale());
        System.out.println("decimalTypeCode = " +
                JDBCType.DECIMAL.getVendorTypeNumber());
        System.out.println("exactRejected = " +
                exactRejected);
    }
}
```

## 12. Kiểu ngày giờ trong JDBC 4.2

Một thay đổi quan trọng từ JDBC 4.2 là hỗ trợ các lớp Java Date-Time API `java.time` khi driver tương thích:

| Kiểu Java | Kiểu SQL/JDBC thường phù hợp | Ý nghĩa cần xác định |
| --- | --- | --- |
| `LocalDate` | `JDBCType.DATE` | Ngày, không chứa giờ/múi giờ |
| `LocalTime` | `JDBCType.TIME` | Giờ trong ngày, không offset |
| `LocalDateTime` | `JDBCType.TIMESTAMP` | Ngày và giờ local, không tự mang offset |
| `OffsetTime` | `JDBCType.TIME_WITH_TIMEZONE` | Giờ cùng offset |
| `OffsetDateTime` | `JDBCType.TIMESTAMP_WITH_TIMEZONE` | Ngày giờ cùng offset |
| `Instant` | Phụ thuộc driver và thiết kế schema | Điểm thời gian tuyệt đối; chuyển rõ policy |

**`JDBCType.TIMESTAMP` không tự lưu múi giờ.** `OffsetDateTime` có offset, nhưng việc DB giữ nguyên offset, chỉ giữ instant, hoặc chuẩn hóa về UTC là hành vi phụ thuộc loại SQL thực và driver. Phải có hợp đồng time zone/precision nhất quán.

Lưu `TemporalSqlTypesDemo.java`:

```java
import java.sql.JDBCType;

import java.time.LocalTime;
import java.time.OffsetDateTime;
import java.time.OffsetTime;

    }

    public static void main(String[] args) {
        Plan[] columns = {
            new Plan(LocalDate.of(2026, 11, 6),
                     JDBCType.DATE),
            new Plan(LocalTime.of(9, 30),
                     JDBCType.TIME),
            new Plan(LocalDateTime.of(2026, 11, 6, 9, 30),
                     JDBCType.TIMESTAMP),
            new Plan(OffsetTime.parse("09:30:00+07:00"),
                     JDBCType.TIME_WITH_TIMEZONE),
            new Plan(OffsetDateTime.parse(
                    "2026-11-06T09:30:00+07:00"),
                     JDBCType.TIMESTAMP_WITH_TIMEZONE)
        };

        for (Plan column : columns) {
            System.out.println(
                    column.javaValue().getClass()
                            .getSimpleName() + " -> "
                    + column.sqlType().getName());
        }
    }
}
```

### 12.1. JDBCType và Java type không phải cùng một enum

## 13. Gán SQL NULL: loại của tham số vẫn quan trọng

`PreparedStatement.setNull(int parameterIndex, int sqlType)` nhận **`int` code từ `Types`**, chứ không nhận `SQLType`. Phương thức `setNull(int,SQLType)` **không** tồn tại trong API JDBC chuẩn.

Ví dụ với một cột `VARCHAR`:

```java
ps.setNull(1, Types.VARCHAR);
```

*Snippet giả định `ps` là `PreparedStatement` đã mở.*

Nếu driver hỗ trợ typed overload, cũng có thể thử:

```java
ps.setObject(1, null, JDBCType.VARCHAR);
```

*Snippet mô tả việc bind một value null với SQLType đích. Tính tương thích của driver phải kiểm tra.*

Không dùng `JDBCType.NULL` cho mọi trường hợp null rồi bỏ qua loại SQL của cột. SQL NULL là **giá trị**, còn JDBC SQL type code là **mô tả kiểu dữ liệu** của parameter.

## 14. CallableStatement: đăng ký tham số OUT bằng SQLType

`CallableStatement` đại diện lời gọi stored procedure/function. JDBC 4.2 cung cấp các overload `registerOutParameter` nhận `SQLType`:

```java
cs.registerOutParameter(1, JDBCType.INTEGER);
cs.registerOutParameter(2, JDBCType.DECIMAL, 2);
cs.registerOutParameter("result_code", JDBCType.INTEGER);
```

*Snippet giả định `cs` là `CallableStatement` và procedure hỗ trợ tham số theo index/tên đó; không phải chương trình độc lập.*

**OUT parameters phải đăng ký trước khi execute**. Với `NUMERIC`/`DECIMAL` có thể dùng overload nhận scale. Với UDT hoặc `REF`, có overload nhận **SQL type name** và yêu cầu hỗ trợ tùy driver.

Một số overload typed cũng là **default methods** có thể ném `SQLFeatureNotSupportedException` nếu driver chưa triển khai.

Lưu `MockCallableTypesDemo.java`:

```java
import java.lang.reflect.Proxy;
import java.math.BigDecimal;
import java.sql.CallableStatement;
import java.sql.JDBCType;
import java.sql.SQLType;

public class MockCallableTypesDemo {
    public static void main(String[] args)
            throws Exception {

        CallableStatement cs = (CallableStatement)
                Proxy.newProxyInstance(
                    CallableStatement.class.getClassLoader(),
                    new Class<?>[]{CallableStatement.class},
                    (proxy, method, values) -> {
                        switch (method.getName()) {
                            case "registerOutParameter" -> {
                                SQLType type = (SQLType) values[1];
                                System.out.println(
                                        "OUT " + values[0] + "="
                                        + type.getName()
                                        + (values.length == 3
                                          ? " scale=" + values[2]
                                          : ""));
                                return null;
                            }
                            case "execute" -> {
                                System.out.println("executeCalled");
                                return false;
                            }
                            case "getObject" -> {
                                return ((Integer) values[0]) == 1
                                        ? 7
                                        : new BigDecimal("19.75");
                            }
                            default -> {
                                return null;
                            }
                        }
                    });

        cs.registerOutParameter(1, JDBCType.INTEGER);
        cs.registerOutParameter(2, JDBCType.DECIMAL, 2);
        cs.execute();

        System.out.println("answer = " +
                cs.getObject(1, Integer.class));
        System.out.println("amount = " +
                cs.getObject(2, BigDecimal.class));
    }
}
```

## 15. ResultSet.updateObject và SQLType

Các overload `ResultSet.updateObject(..., SQLType)` dùng để cập nhật giá trị trong **current row hoặc insert row** của một `ResultSet` updatable. Chúng **không** tự ghi xuống bảng ngay lập tức; cần `updateRow()` hoặc `insertRow()` theo chế độ của result set.

Ví dụ khi đã có một ResultSet updatable:

```java
rs.updateObject("amount",
        new BigDecimal("19.75"),
        JDBCType.DECIMAL, 2);
rs.updateRow();
```

*Snippet không độc lập; `rs` phải là ResultSet hỗ trợ concurrency `CONCUR_UPDATABLE`, có current row hợp lệ và driver hỗ trợ typed overload.*

**Không nhầm `updateObject` với `PreparedStatement.setObject`**. Một cái thay giá trị cột trong result set updatable; một cái bind input parameter trong SQL. Với đa số ứng dụng, `PreparedStatement` và DML parameterized thường là cách cập nhật dễ kiểm soát hơn, nhưng `ResultSet.updateObject` vẫn là API hiện hành.

Lưu `MockResultSetUpdateDemo.java`:


## 16. Đọc giá trị qua ResultSet.getObject: Java type khác SQLType

Ví dụ:

```java

OffsetDateTime time = rs.getObject("event_ts",
```

## 17. ResultSetMetaData và mã kiểu do driver báo cáo

Các API metadata cốt lõi vẫn sử dụng kiểu `int`:

- `ResultSetMetaData.getColumnType(i)` → **mã JDBC** thường thuộc `Types`.
- `ResultSetMetaData.getColumnTypeName(i)` → **tên kiểu riêng được driver/database báo cáo**, không bắt buộc khớp `JDBCType.getName()`.
- `getPrecision(i)` và `getScale(i)` → thông tin về độ chính xác/scale do driver báo cáo.
- `ParameterMetaData.getParameterType(index)` → **int** type code của input parameter, nếu driver hỗ trợ metadata đó.
- `DatabaseMetaData.getTypeInfo()` → các rows type information từ driver/database, bao gồm `TYPE_NAME` và `DATA_TYPE`.

Khi nhận code **không biết**, nên giữ cả số và tên vendor:

```java
int code = meta.getColumnType(index);
String databaseName = meta.getColumnTypeName(index);

String generic;
try {
    generic = JDBCType.valueOf(code).getName();
} catch (IllegalArgumentException unknown) {
    generic = "VENDOR_SPECIFIC";
}
```

*Snippet yêu cầu `meta` thuộc `ResultSetMetaData` và `index` hợp lệ; không độc lập.*

Đừng tự đồng nhất `TYPE_NAME` với enum constant. Một DB có thể báo cáo `"NUMBER"`, `"UUID"`, `"JSONB"` hoặc tên user-defined dù generic JDBC code là `NUMERIC`/`OTHER`.

Lưu `MockResultMetadataDemo.java`:


## 18. Bảng mapping cho repository/DAO

Một hệ thống thường cần một registry khai báo mỗi cột dùng target `SQLType` và kiểu Java dự kiến. Điều này giúp kiểm tra logic binding và schema consistency mà không lặp các số magic như 12, 3, 91.

Lưu `SqlColumnPlanDemo.java`:

```java
import java.sql.JDBCType;
import java.sql.SQLType;
import java.util.List;

public class SqlColumnPlanDemo {
    record ColumnPlan(
            String name, Class<?> javaClass, SQLType sqlType) {
    }

    public static void main(String[] args) {
        List<ColumnPlan> columns = List.of(
            new ColumnPlan("id", Long.class,
                           JDBCType.BIGINT),
            new ColumnPlan("label", String.class,
                           JDBCType.VARCHAR),
            new ColumnPlan("amount",
                           java.math.BigDecimal.class,
                           JDBCType.DECIMAL),
            new ColumnPlan("createdOn",
                           java.time.LocalDate.class,
                           JDBCType.DATE)
        );

        for (ColumnPlan column : columns) {
            System.out.println(column.name()
                    + ": " + column.javaClass()
                            .getSimpleName()
                    + " -> " + column.sqlType().getName());
        }
    }
}
```

```bash
javac SqlColumnPlanDemo.java
java SqlColumnPlanDemo
```

```text
id: Long -> BIGINT
label: String -> VARCHAR
amount: BigDecimal -> DECIMAL
createdOn: LocalDate -> DATE
```

Đây là **schema plan**, không phải schema DDL hay guarantee driver mapping. Nếu có precision, scale, nullability, timezone, vendor-specific typeName và dữ liệu array/JSON, model registry nên mang thêm các thông tin đó theo nhu cầu thực.

Một lớp ORM/mapper có thể quản lý mapping này, nhưng không nên suy ra từ `SQLType` rằng nó tự thay thế Hibernate/JPA, migrations hoặc schema validation.

## 19. Kiểm tra custom type trước khi map thành generic

Trong thư viện muốn hỗ trợ nhiều vendor, một helper có thể:

1. Nếu type thuộc chính `JDBCType`, lấy mã generic tương ứng.
2. Nếu type thuộc vendor khác, **không** tự map sang `Types` chỉ vì mã tình cờ giống nhau.
3. Giao loại vendor cho adapter/driver đúng, hoặc fail với thông báo rõ ràng.
4. Không thay `OTHER` cho mọi lỗi type code mà không giữ typeName/vendor.

Lưu `SafeGenericTypeCodeDemo.java`:

```java
import java.sql.JDBCType;
import java.sql.SQLType;

public class SafeGenericTypeCodeDemo {
    static final class VendorType implements SQLType {
        @Override
        public String getName() {
            return "SPECIAL";
        }

        @Override
        public String getVendor() {
            return "vendor.example";
        }

        @Override
        public Integer getVendorTypeNumber() {
            return 4;
        }
    }

    static int requireGenericCode(SQLType type) {
        if (!(type instanceof JDBCType standard)) {
            throw new IllegalArgumentException(
                    "not a standard JDBCType");
        }
        return standard.getVendorTypeNumber();
    }

    public static void main(String[] args) {
        int code = requireGenericCode(JDBCType.INTEGER);
        boolean customRejected = false;

        try {
            requireGenericCode(new VendorType());
        } catch (IllegalArgumentException e) {
            customRejected = true;
        }

        System.out.println("genericInteger = " + code);
        System.out.println("customRejected = " +
                customRejected);
    }
}
```

```bash
javac SafeGenericTypeCodeDemo.java
java SafeGenericTypeCodeDemo
```

```text
genericInteger = 4
customRejected = true
```

Helper này cố ý nghiêm ngặt để bảo vệ code generic. Nếu ứng dụng cần hỗ trợ custom `SQLType`, hãy viết **explicit vendor adapter** thay vì từ chối tất cả. `getVendor()` là thông tin hữu ích, nhưng một string vendor có thể bị custom implementation khai báo tùy ý; đừng dùng nó làm chứng cứ bảo mật hoặc chứng thực nguồn dữ liệu.

## 20. JDBC 4.2 vẫn hiện hành; JDK 26 mở rộng loại kiểu

**Đây là phân biệt phiên bản cần đặc biệt chú ý:**

- **Java 8 / JDBC 4.2:** thêm interface `SQLType`, enum `JDBCType`, các overload typed liên quan và các loại `REF_CURSOR`, `TIME_WITH_TIMEZONE`, `TIMESTAMP_WITH_TIMEZONE`.
- **Java 17:** vẫn hỗ trợ các API JDBC 4.2 này. Mọi ví dụ runnable trong bài nhắm Java 17+ và không dùng constant chỉ có trong JDK mới.
- **Java 26 / JDBC 4.5:** JDK hiện hành đã bổ sung `JDBCType.JSON`, `JDBCType.DECFLOAT` và `Types.JSON`, `Types.DECFLOAT`. Mã generic tương ứng là **2016 (JSON)** và **2015 (DECFLOAT)**. Những constant này **không tồn tại trong Java 17 hoặc Java 24**.

Không viết code khai báo `JDBCType.JSON` trên Java 17 rồi kỳ vọng biên dịch. Với Java 17, JSON có thể được driver ánh xạ qua `OTHER` hoặc cách vendor-specific khác; dùng hướng dẫn của driver/schema. Ngay cả khi compile trên JDK 26, **database và driver vẫn phải thực sự hỗ trợ** JSON/DECFLOAT và cách Java object được bind.

Cùng một câu “JDBC 4.2” không đồng nghĩa Java 26 ngừng hỗ trợ các phương thức từ 4.2. API JDBC hiện hành phát triển tích lũy; không cần quay lại các thủ thuật driver loading cũ hay bỏ đi `Types` đang được hỗ trợ.

### 20.1. Không nhầm JDBC enum JSON với parsing JSON

`JDBCType.JSON` chỉ biểu diễn **loại SQL generic** khi được hỗ trợ. Nó **không** phải một thư viện parse/serialize JSON Java, không tự chuyển Map/POJO sang JSON đúng schema, và không bảo đảm driver nhận trực tiếp một Java `Map`. Cần Java JSON library/mapping và driver type conversion policy phù hợp.

### 20.2. DECFLOAT không đồng nghĩa BigDecimal conversion không mất dữ liệu

`DECFLOAT` mô tả loại SQL decimal floating point trong môi trường hỗ trợ. Chi tiết precision, rounding, special values, conversion và Java mapping phải theo driver/DB. `BigDecimal` là kiểu Java decimal chính xác được dùng phổ biến, nhưng không có bảo đảm chuyển đổi sang mọi DECFLOAT column mà không làm tròn hoặc mất thông tin.

## 21. Lỗi khi xử lý SQLType và JDBCType

| Sai lầm | Vì sao sai | Cách sửa |
| --- | --- | --- |
| Xem `JDBCType` là class chứa dữ liệu cột | Nó mô tả loại SQL, không giữ value | Tách Java value và target SQLType |
| Coi `Types.INTEGER` đã bị loại bỏ | Các API metadata/overload vẫn dùng `int` | Giữ cả hai API khi cần |
| Dùng `JDBCType.ordinal()` làm type code | Ordinal là vị trí enum, không phải mã JDBC | `getVendorTypeNumber()` |
| Gọi `JDBCType.valueOf(4)` cho custom vendor code | Trùng số không chứng minh cùng loại | Xét vendor và driver contract |
| Gọi `valueOf("VARCHAR(50)")` | Enum không parse DDL string | Metadata/schema parser phù hợp |
| Nghĩ `SQLType` custom là driver tự hiểu | Interface chỉ mô tả metadata | Vendor adapter/driver hỗ trợ |
| Tưởng mọi driver hỗ trợ typed default method | Có thể ném `SQLFeatureNotSupportedException` | Integration test và fallback có kiểm soát |

| Gọi `setNull(index, JDBCType.VARCHAR)` | Không có overload chuẩn `setNull(int,SQLType)` | `setNull(index, Types.VARCHAR)` |

## 22. Kiểm thử và tương thích driver

Có **hai loại kiểm thử** khác nhau:

**Unit test không cần DB**:

- Verify enum `JDBCType` và `Types` khớp những mã chuẩn được dùng.
- Verify `SQLType.getVendor`, `getName`, custom vendor type và code collisions.
- Verify logic mapping Java type → SQLType trong repository.
- Test handling unknown code từ metadata bằng mock.
- Test fallback có kiểm soát khi nhận `SQLFeatureNotSupportedException` từ một mock driver.
- Test decimal precision/scale và normalization trước khi bind.
- Test tên tham số và thứ tự index 1-based trong adapter.

**Integration test với DB thật**:

- Chạy `setObject(...,SQLType)` trên phiên bản driver và DB sẽ triển khai.
- Insert/read lại `DECIMAL` có scale/precision nhạy cảm, SQL NULL và kiểu date/time.
- Thử `OffsetDateTime` với offset khác nhau, DST, fractional-second precision và timezone DB.
- Test vendor-specific `JSON/UUID/ARRAY/STRUCT` theo tài liệu driver.
- Test `CallableStatement.registerOutParameter` nếu có stored procedure.
- Test khả năng `ResultSet.updateObject` trên updatable ResultSet thực tế.
- So metadata `getColumnType`, `getColumnTypeName`, `getPrecision`, `getScale` với DDL.
- Test transaction rollback, driver-specific exception, SQLState, timeout và resource closure.

**Không có một kết quả chung cho mọi database.** Tên `JDBCType` được chuẩn hóa về API, nhưng SQL schema và driver conversion là môi trường bên ngoài. Khi driver/version thay đổi, nên chạy lại integration tests quan trọng.

### 22.1. Cơ chế quan sát hỗ trợ driver

`DatabaseMetaData` cho biết driver+DB hỗ trợ nhiều tính năng và có `getTypeInfo()` để kiểm tra data types. Những thông tin này là **kết quả từ driver**, không phải suy ra từ `JDBCType.values()`.

`ParameterMetaData` có thể không đầy đủ ở một số driver hoặc không hỗ trợ kiểu custom chính xác; đừng tự coi metadata luôn có 100% precision. Nếu ứng dụng cần type catalog bảo đảm, kết hợp driver documentation, migration schema và test.

## 23. Bài tập thực hành

**Bài 1 — Mã kiểu:** Dùng `JDBCType.valueOf(Types.INTEGER)` và `JDBCType.valueOf(Types.TIMESTAMP_WITH_TIMEZONE)`. In `getName`/`getVendorTypeNumber`. Chứng minh `ordinal()` không phải hợp đồng lưu mã.

**Bài 2 — Kiểu vendor:** Viết enum implements `SQLType` cho một kiểu giả định `VECTOR`; vendor `"com.example.db"`, mã `50002`. Vì sao gọi `JDBCType.valueOf(50002)` không làm driver tự hỗ trợ nó?

**Bài 3 — NULL:** Với cột `VARCHAR(100)` nullable, viết hai cách gán SQL NULL khi driver hỗ trợ typed overload. Giải thích vì sao `setNull` vẫn cần `Types.VARCHAR`.

**Bài 4 — Decimal:** Tạo `BigDecimal("123.456")` và làm tròn HALF_UP đến scale 2. Giải thích khác nhau giữa `precision` và `scale`; điều gì còn phải kiểm tra ở DB?

**Bài 5 — Java time:** Chọn SQLType phù hợp với `LocalDate`, `LocalDateTime`, `OffsetTime`, `OffsetDateTime`. Khi nào phải viết policy chuẩn hóa offset/timezone rõ ràng?

**Bài 6 — Metadata unknown:** `getColumnType()` trả 50001 và `getColumnTypeName()` trả `"MY_PAYLOAD"`. Viết logic không bị crash khi `JDBCType.valueOf(50001)` ném exception và vẫn giữ mã/tên gốc.

**Bài 7 — Driver fallback:** Mock typed overload ném `SQLFeatureNotSupportedException` rồi fallback sang `setObject(index,value, Types.INTEGER)`. Vì sao không áp dụng fallback mù quáng cho JSON/UUID vendor types?

**Bài 8 — Phiên bản:** Vì sao code Java 17 không được dùng `JDBCType.JSON` dù API mới ở JDK 26 có constant này? Khi triển khai vẫn phải kiểm tra điều gì ngoài compile?

### 23.1. Lời giải Java tổng kết

Lưu `SqlTypePracticeDemo.java`:

```java
import java.math.BigDecimal;
import java.math.RoundingMode;
import java.sql.JDBCType;
import java.sql.SQLType;
import java.sql.Types;

public class SqlTypePracticeDemo {
    private static String typeOrUnknown(int code) {
        try {
            return JDBCType.valueOf(code).getName();
        } catch (IllegalArgumentException e) {
            return "UNKNOWN(" + code + ")";
        }
    }

    public static void main(String[] args) {
        SQLType id = JDBCType.INTEGER;
        BigDecimal amount = new BigDecimal("12.345")
                .setScale(2, RoundingMode.HALF_UP);

        System.out.println("idVendor = " + id.getVendor());
        System.out.println("idCode = " +
                id.getVendorTypeNumber());
        System.out.println("typeByCode = " +
                typeOrUnknown(Types.INTEGER));
        System.out.println("unknown = " +
                typeOrUnknown(50_001));
        System.out.println("amount = " + amount);
        System.out.println("amountSQLType = " +
                JDBCType.DECIMAL.getName());
    }
}
```

## 24. Checklist trước khi đưa vào production

- Tôi phân biệt **Java object type**, **SQL column type** và **JDBC type code** chưa?
- `JDBCType` dùng `getVendorTypeNumber()` thay vì enum `ordinal()`?
- Type code từ metadata có thể unknown/vendor-specific không? Đã giữ typeName?
- Custom SQLType có vendor/mã chính xác theo tài liệu driver không?
- Code Java 17 chỉ dùng constant tồn tại trong Java 17? Mọi API JDK 26 đã ghi rõ version?
- Driver thật hỗ trợ `setObject(...,SQLType)` hay còn ném `SQLFeatureNotSupportedException`?
- Với nullable column, đã bind NULL cùng target SQL type thích hợp?
- `setNull` đang nhận `int` từ `Types`, không cố dùng SQLType overload không tồn tại?
- Scale/precision và rounding `BigDecimal` được xác định theo nghiệp vụ và DDL?
- `LocalDateTime`, `OffsetDateTime` được ánh xạ theo time zone/precision contract rõ ràng?
- `CallableStatement` OUT parameters được register trước execute?
- `ResultSet.updateObject` dùng đúng updatable cursor và `updateRow()`?
- `ResultSet.getObject(..., Class<T>)` yêu cầu Java class chứ không phải JDBCType?
- `DatabaseMetaData.getTypeInfo()`/`ResultSetMetaData` được đọc trên driver thật khi cần type details?
- SQL values được bind bằng `?`, identifiers động có allowlist thay vì string concatenation?
- Resources được đóng với try-with-resources, transaction rollback được kiểm soát?
- Integration tests được chạy trên JDK + driver + DB version tương ứng production?
- Không suy từ mock proxy rằng driver/database đã xử lý SQL thật?
