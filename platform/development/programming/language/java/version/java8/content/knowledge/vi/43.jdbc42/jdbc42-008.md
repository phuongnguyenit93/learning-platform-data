# BatchUpdateException với số lượng cập nhật lớn — JDBC 4.2 (Java 8+)

`java.sql.BatchUpdateException` là một `SQLException` đặc biệt được ném khi một lệnh trong batch SQL thất bại. Ngoài SQLState, mã lỗi vendor và nguyên nhân, nó còn mang **các update count** mà JDBC driver có thể báo cho những lệnh đã được thực thi. Từ **JDBC 4.2 / Java 8**, `Statement.executeLargeBatch()` trả `long[]` khi thành công, còn `BatchUpdateException.getLargeUpdateCounts()` trả `long[]` trong nhánh lỗi, để tránh mất số khi một câu SQL tác động hơn `Integer.MAX_VALUE` dòng.

**“Batch lớn” có hai nghĩa khác nhau:** nhiều *lệnh* được add vào batch, và *một lệnh* tác động rất nhiều *dòng*. Mảng update counts có một vị trí ứng với từng command theo thứ tự add (hoặc chỉ một prefix khi driver dừng vì lỗi); mỗi giá trị không âm là số **dòng chịu tác động của command đó**. Một batch 100.000 command có thể chỉ tác động 100.000 dòng; một batch gồm 1 command lại có thể tác động hàng tỷ dòng. Do đó **không nhầm `counts.length` với tổng dòng bị cập nhật**, và không nghĩ `long[]` chỉ cần khi số lượng command vượt 2 tỷ.

Bài này áp dụng những API JDBC 4.2 vẫn được duy trì trong Java hiện đại; không dùng công nghệ lỗi thời/legacy làm lời giải. Nội dung phân biệt kỹ khả năng **tiếp tục hoặc dừng khi lỗi**, hai sentinel đặc biệt, rollback/auto-commit, quản lý chunk và an toàn retry. Một chương trình **không cần database** ở cuối bài dựng exception giả lập với count 3.000.000.000 để kiểm tra getter, phân tích kết quả và minh họa tràn `int`. Chương trình được biên dịch với JDK 17 và dùng API Java 8+.

## 1. Batch trong JDBC diễn ra thế nào?

Một `PreparedStatement` có thể chạy cùng SQL với nhiều bộ tham số mà không phải viết lại chuỗi SQL cho mỗi input:

~~~java
try (PreparedStatement ps = connection.prepareStatement(
        "UPDATE inventory SET reserved = ? WHERE product_id = ?")) {

    ps.setInt(1, 3);
    ps.setLong(2, 101L);
    ps.addBatch();

    ps.setInt(1, 5);
    ps.setLong(2, 102L);
    ps.addBatch();

    ps.setInt(1, 8);
    ps.setLong(2, 103L);
    ps.addBatch();

    long[] counts = ps.executeLargeBatch();
}
~~~

Đây là đoạn **tích hợp** trong method có `Connection connection` và policy exception phù hợp; chỉ chạy nếu có bảng, schema và quyền DB tương ứng. Mỗi lần `addBatch()` thêm một bộ tham số, nhưng **không tự thực thi ngay**. `executeLargeBatch` gửi những command đã xếp hàng theo semantics driver/database.

Nếu một lệnh sửa 0 dòng, `count == 0` là kết quả **thành công ở mức JDBC**, không mặc định SQL bị lỗi. Nếu bạn yêu cầu “mỗi product ID bắt buộc tồn tại”, ứng dụng có thể coi 0 là **lỗi nghiệp vụ** sau khi kiểm counts. Nếu command UPDATE có điều kiện khớp nhiều dòng, count có thể lớn hơn 1. Không có quy tắc JDBC “mỗi addBatch chỉ sửa một dòng”.

Phân biệt hai cách thêm batch:

- `Statement.addBatch(String sql)`: add những chuỗi SQL riêng.
- `PreparedStatement.addBatch()`: add bộ tham số đã set cho cùng SQL mẫu; không truyền chuỗi SQL vào method này.
- Cả hai đều thực thi bằng `executeBatch()` hoặc `executeLargeBatch()` khi driver hỗ trợ. Không gọi `addBatch(String)` trên `PreparedStatement`; đây không phải API đúng cho PreparedStatement.

## 2. `executeBatch` và `executeLargeBatch` khác nhau

| Tác vụ | API truyền thống | API large count của JDBC 4.2 |
| --- | --- | --- |
| Thực thi batch | `executeBatch()` | `executeLargeBatch()` |
| Kiểu trả khi thành công | `int[]` | `long[]` |
| Một lệnh update đơn | `executeUpdate()` → `int` | `executeLargeUpdate()` → `long` |
| Đọc count trong `BatchUpdateException` | `getUpdateCounts()` → `int[]` | `getLargeUpdateCounts()` → `long[]` |
| Lớn hơn 2³¹−1 dòng/lệnh | Rủi ro overflow | Có thể biểu diễn bằng `long` |

`executeLargeBatch` được khai báo ở interface `Statement` và thừa hưởng bởi `PreparedStatement`. Phần triển khai `default` có thể ném `UnsupportedOperationException`: **driver phải hỗ trợ trên thực tế**. Không giả định chỉ đổi sang JDK mới là mọi JDBC driver sẽ hỗ trợ chuẩn large API. Kiểm tra driver version và chạy integration test trên DBMS thực sự dùng.

### Vì sao một phần tử `int` là chưa đủ?

~~~java
long affectedRows = 3_000_000_000L;

boolean exceedsSignedInt = affectedRows > Integer.MAX_VALUE;
// true.
~~~

`Integer.MAX_VALUE == 2_147_483_647`. Nếu ép 3 tỷ thành int trên JDK 17:

~~~java
int narrowed = (int) 3_000_000_000L;
// -1294967296.
~~~

Giá trị âm đó **không phải update count có ý nghĩa**; nó là kết quả mất bit khi chuyển từ long sang int. Chuyển nó trở lại `long` bằng cast **không phục hồi** được 3 tỷ ban đầu.

### Luôn ghép đúng cặp API

~~~java
try {
    long[] counts = ps.executeLargeBatch();
    // xử lý long[] không cắt thành int[]
} catch (BatchUpdateException ex) {
    long[] countsAtFailure = ex.getLargeUpdateCounts();
    // xử lý long[] và transaction
}
~~~

Đừng gọi `getUpdateCounts()` trong catch của `executeLargeBatch` khi count có thể lớn. Oracle Javadoc khuyến nghị `getLargeUpdateCounts` để tránh overflow. Nếu cần cast sang int phục vụ giao diện cũ, hãy validate `0 <= c && c <= Integer.MAX_VALUE` trước; đồng thời phải tách sentinel và xử lý riêng, không ép mọi giá trị.

## 3. Những trường dữ liệu có trong `BatchUpdateException`

`BatchUpdateException extends SQLException`. Các API chẩn đoán còn được hỗ trợ:

| Method | Dữ liệu nhận được | Lưu ý |
| --- | --- | --- |
| `getMessage()` | Mô tả lỗi từ JDBC driver/DB | Không nên parse text message để quyết định retry |
| `getSQLState()` | SQLState nếu có | Có thể null; ý nghĩa theo chuẩn và vendor |
| `getErrorCode()` | Mã vendor | Không tự dùng chung giữa các DBMS |
| `getCause()` | Nguyên nhân nếu được gắn | Có thể null |
| `getNextException()` | Chuỗi SQLException bổ sung | Driver có thể gắn nhiều lỗi chi tiết |
| `getUpdateCounts()` | `int[]` update counts | Có nguy cơ overflow |
| `getLargeUpdateCounts()` | `long[]` update counts | Dùng với large batch |

Constructor `BatchUpdateException(String reason, String SQLState, int vendorCode, long[] updateCounts, Throwable cause)` được đưa vào JDBC 4.2 để có thể giữ count lớn. Oracle khuyến nghị các nhà triển khai driver dùng **constructor có `long[]`**, thay vì các constructor cũ nhận `int[]`. Đây là khuyến nghị để giữ độ chính xác, không phải lệnh buộc ứng dụng tự tạo exception cho mọi lỗi batch.

### Constructor minh họa (không phải lệnh DB)

~~~java
BatchUpdateException simulated = new BatchUpdateException(
        "simulated failure", "23000", 7001,
        new long[] {1L, 3_000_000_000L, Statement.EXECUTE_FAILED},
        new SQLException("simulated cause"));

long[] largeCounts = simulated.getLargeUpdateCounts();
~~~

Ở đây `SQLState 23000`, vendor code 7001 và thông điệp đều là **dữ liệu giả lập**; 7001 không được quảng bá là mã lỗi của một DB vendor. Mục đích là dạy cách kiểm tra ngoại lệ và số đếm, không giả vờ đã kết nối thật.

## 4. Ba trạng thái quan trọng của một count

Khi đọc `long c` từ `getLargeUpdateCounts()`:

| Giá trị | Tên | Ý nghĩa |
| --- | --- | --- |
| `c >= 0` | Count thực | Lệnh thành công và driver biết số dòng bị ảnh hưởng |
| `c == -2` | `Statement.SUCCESS_NO_INFO` | Lệnh thành công nhưng **không biết** số dòng bị ảnh hưởng |
| `c == -3` | `Statement.EXECUTE_FAILED` | Lệnh thất bại; marker xuất hiện khi driver tiếp tục sau lỗi |

`SUCCESS_NO_INFO` và `EXECUTE_FAILED` có kiểu hằng số `int`, được dùng hợp lệ trong mảng `long[]`. Hai sentinel này không có nghĩa là một số dòng âm.

**Phân biệt quan trọng:**

- `0`: command chạy thành công nhưng **không sửa dòng nào**.
- `1`: command chạy thành công, driver biết đã sửa 1 dòng.
- `3_000_000_000L`: command chạy thành công, driver báo sửa 3 tỷ dòng.
- `-2`: command thành công, **số dòng chưa biết**; không được tự đổi thành 0 hay 1.
- `-3`: command thất bại theo thông tin driver báo.

Nếu có giá trị âm khác `-2` và `-3` khi đang xử lý `long[]`, không tự gán nghĩa cho nó; kiểm tra input/driver và fail rõ theo policy. Một giá trị âm lạ có thể là dấu hiệu **đã đi qua đường int overflow** hoặc vấn đề tương thích.

### Ví dụ mảng có đủ ba loại

~~~java
long[] counts = {
        1L,
        3_000_000_000L,
        Statement.SUCCESS_NO_INFO,
        Statement.EXECUTE_FAILED,
        0L
};
~~~

Từ mảng này, biết chính xác các counts không âm có tổng `1 + 3000000000 + 0 = 3000000001`. Nhưng đây chỉ là **knownAffectedRows**, không thể khẳng định **actual total affected rows** vì một command thành công có `SUCCESS_NO_INFO`. Và nó cũng không cho biết dữ liệu đã được **commit** hay chưa.

## 5. Driver có thể dừng hoặc tiếp tục xử lý khi một command lỗi

JDBC không bắt buộc mọi driver xử lý giống hệt nhau sau khi một lệnh trong batch thất bại. Theo Javadoc, driver có thể **dừng** hoặc **tiếp tục**; hành vi của driver cần nhất quán với DBMS.

### Trường hợp A — Stop-on-error

Batch có năm command, driver trả counts cho **hai lệnh đã thành công trước khi lỗi**:

~~~text
index:       0       1       2       3       4
planned:   cmd0    cmd1    cmd2    cmd3    cmd4
returned:    1   3000000000
~~~

Mảng `getLargeUpdateCounts()` có `length == 2`. Không thêm `EXECUTE_FAILED` vào các vị trí vắng mặt để “cho đủ 5”; **unreported ≠ EXECUTE_FAILED**. Thông tin prefix chưa đủ để khẳng định lệnh chưa có entry đã chạy, chưa chạy, có side effect hay đã commit.

### Trường hợp B — Continue-on-error

Driver tiếp tục và có một entry cho mỗi command:

~~~text
index:       0       1       2       3       4
planned:   cmd0    cmd1    cmd2    cmd3    cmd4
returned:    1   3000000000  -2      -3      0
~~~

Index 2 thành công nhưng không biết count. Index 3 thất bại. Index 4 vẫn được xử lý thành công, dù một command trước lỗi. Cần xác định lệnh lỗi theo **index và thông tin SQL** chứ không dựa vào “toàn bộ batch đã thất bại nên mọi lệnh thất bại”.

**Khi driver thực hiện batch rewriting hoặc server-side batching**, việc suy ra số dòng chính xác cho từng bộ tham số có thể có giới hạn. Đọc tài liệu driver/version và kiểm thử mapping trên hệ thống dùng thực tế, không tuyên bố một bộ test synthetic chứng minh behavior của DB.

## 6. Đừng nhầm số command với số dòng và số transaction đã commit

Cùng một batch có:

~~~text
plannedCommands = 5
reportedCounts = 5
knownAffectedRows = 3_000_000_001
unknownRowCounts = 1
failedCommands = 1
~~~

Các đại lượng có ý nghĩa riêng. Cộng tất cả count như số nguyên gồm `-2`, `-3` sẽ tạo tổng vô nghĩa. `counts.length` không phải số dòng ảnh hưởng; chỉ nói về số entry counts.

Cũng không được coi count dương là bằng chứng DB đã commit. Command có thể thực thi trong transaction chưa commit, rồi `rollback()` khiến hiệu ứng bị hủy. Trái lại, với auto-commit hoặc transaction đã commit một phần ở nơi khác, retry ngay có thể tạo side effect trùng.

Vì vậy báo cáo vận hành nên tách **execution result** khỏi **transaction outcome**.

## 7. Phân loại `long[]` mà không mất số liệu

Một hàm trợ giúp có thể tách exact, unknown, failed, unreported:

~~~java
static String summarize(long[] counts, int planned) {
    long known = 0;
    int exact = 0, unknown = 0, failed = 0;

    for (long c : counts) {
        if (c >= 0) {
            known = Math.addExact(known, c);
            exact++;
        } else if (c == Statement.SUCCESS_NO_INFO) {
            unknown++;
        } else if (c == Statement.EXECUTE_FAILED) {
            failed++;
        } else {
            throw new IllegalArgumentException("Unknown count marker: " + c);
        }
    }

    return "exact=" + exact + ", unknown=" + unknown
            + ", failed=" + failed
            + ", unreported=" + (planned - counts.length)
            + ", knownAffected=" + known;
}
~~~

Đây là snippet minh họa với `import java.sql.Statement;`. Nó giả định `planned >= counts.length`; trong ứng dụng thật, kiểm tra cả mảng, count planned, tình huống driver không tuân hợp đồng, và policy khi total known bị overflow.

`Math.addExact` báo lỗi nếu **tổng counts không âm** tràn `long`. Nếu tổng nhiều lệnh có thể vượt `Long.MAX_VALUE`, dùng `BigInteger`. **BigInteger không giải quyết `SUCCESS_NO_INFO`**: một unknown count vẫn unknown dù tổng được tính bằng kiểu rộng vô hạn.

### Các metric nên lưu riêng

- `plannedCommands` và `reportedEntries`.
- `exactCountEntries`, `knownAffectedRows`.
- `successUnknownEntries` (marker `-2`).
- `failedEntries` (marker `-3`).
- `unreportedEntries` (khi mảng ngắn).
- `SQLState`, vendor code và category lỗi; không log dữ liệu cá nhân hoặc SQL parameters thô.

Không biến `knownAffectedRows` thành nhãn “confirmed committed rows” trước khi transaction outcome được xác định.

## 8. Đọc SQLState, lỗi vendor và chuỗi exception

Trong nhánh catch:

~~~java
catch (BatchUpdateException ex) {
    long[] counts = ex.getLargeUpdateCounts();
    String state = ex.getSQLState();
    int code = ex.getErrorCode();

    SQLException next = ex.getNextException();
    while (next != null) {
        // Ghi metadata an toàn; có thể có nhiều lỗi nối tiếp.
        next = next.getNextException();
    }

    // Xử lý transaction sau khi kiểm counts/metadata.
    throw ex;
}
~~~

Đây là code snippet cần method `throws SQLException` và biến transaction sở hữu ở tầng ngoài, không standalone. `SQLState` có thể cung cấp class lỗi (ví dụ nhóm `23` về integrity constraint), nhưng giá trị có thể khác theo database, có thể null, và vendor code không có mapping chung cho mọi DBMS.

Không dùng so chuỗi `getMessage().contains("duplicate")` làm điều kiện retry duy nhất. Message có thể đổi theo ngôn ngữ, driver hay bản DB. Dựa vào loại lỗi, SQLState/vendor code đã được DBMS tài liệu hóa, tính idempotent và trạng thái transaction.

## 9. Quản lý transaction: exception không tự rollback

Mặc định `Connection` mới ở chế độ auto-commit. Nếu cần **all-or-nothing** cho cả batch, ứng dụng nên chủ động dùng một transaction và commit **chỉ sau khi đã kiểm tra business invariant**:

~~~java
try (Connection con = dataSource.getConnection()) {
    con.setAutoCommit(false);

    try (PreparedStatement ps = con.prepareStatement(
            "UPDATE jobs SET status = ? WHERE id = ?")) {

        for (JobChange item : changes) {
            ps.setString(1, item.getStatus());
            ps.setLong(2, item.getId());
            ps.addBatch();
        }

        long[] counts = ps.executeLargeBatch();

        if (counts.length != changes.size()) {
            throw new SQLException("Missing update counts");
        }
        for (long count : counts) {
            if (count != 1L) {
                throw new SQLException("Expected exactly one updated row");
            }
        }
        con.commit();
    } catch (SQLException | RuntimeException original) {
        try {
            con.rollback();
        } catch (SQLException rollbackFailure) {
            original.addSuppressed(rollbackFailure);
        }
        throw original;
    }
}
~~~

Đây là **mẫu tích hợp**: `dataSource` kiểu `javax.sql.DataSource`, `changes` là `List<JobChange>`, còn `JobChange` là lớp nghiệp vụ do ứng dụng định nghĩa (getter `getStatus/getId`). Đừng biên dịch riêng snippet khi chưa định nghĩa các dependency này. SQL phải phù hợp bảng/kiểu cột ở database thực tế.

Mẫu này có **quy tắc nghiệp vụ cụ thể**: mỗi ID phải cập nhật **đúng 1 dòng**, nên cả `0` và `SUCCESS_NO_INFO` **không đủ** để xác nhận invariant, đều khiến rollback. Với nghiệp vụ chỉ yêu cầu SQL command chạy thành công, `SUCCESS_NO_INFO` có thể được chấp nhận mà không cần chính xác số row. Không áp “-2 luôn là lỗi” cho mọi sản phẩm.

### Vì sao catch cả `RuntimeException`?

`executeLargeBatch` có implementation mặc định có thể ném `UnsupportedOperationException`; các lỗi runtime khác trong quá trình kiểm kết quả cũng có thể khiến transaction chưa kết thúc. Nếu helper sở hữu transaction, việc rollback trong catch runtime là hợp lý, nhưng **không hứa rollback luôn thành công**. Không nuốt ngoại lệ rollback: dùng `addSuppressed` để giữ lỗi gốc và thông tin cleanup.

### Commit failure và trạng thái không chắc chắn

Nếu `con.commit()` thất bại vì timeout hoặc đứt mạng, client không luôn biết lệnh commit có đến DB và được áp dụng hay chưa. **Không retry mù** toàn bộ batch: các UPDATE cộng dồn, INSERT hay thao tác gọi trigger có thể chạy hai lần. Thiết kế idempotency key, reconciliation query, audit trail hoặc workflow có thể phục hồi theo yêu cầu nghiệp vụ.

### Auto-commit và DDL

Nếu transaction không được quản lý, một batch lỗi ở giữa **không bảo đảm toàn bộ tác động bị hủy**. Một số database/DDL có semantics commit riêng. Xác minh loại câu SQL, transaction isolation và tính hỗ trợ transaction của DB/storage engine. Chỉ được tuyên bố atomic khi hệ thống thực tế đáp ứng.

## 10. `Savepoint`, partial success và khi nào nên giữ kết quả trước lỗi

`Connection.setSavepoint()`, `rollback(savepoint)` và `releaseSavepoint` có thể hỗ trợ phục hồi một phần transaction, **nếu driver/DBMS hỗ trợ** và ứng dụng có chính sách partial success rõ. Không phải mọi driver đều hỗ trợ savepoints; có thể ném `SQLFeatureNotSupportedException`.

Việc giữ lệnh thành công trước lỗi là **quyết định nghiệp vụ**, không phải điều do `getLargeUpdateCounts` quyết định. Một số quy trình import cho phép hàng lỗi được chuyển sang bảng reject và phần còn lại commit; các quy trình chuyển tiền hoặc đối soát có thể đòi all-or-nothing.

Một chiến lược partial success cần biết: lệnh nào đã chạy, lệnh nào lỗi, transaction còn khả dụng không, khóa/constraint phụ thuộc lẫn nhau ra sao và khả năng thực thi lại từng command. Đừng giả định vì mảng có prefix counts nên có thể commit tùy ý mà không gây dữ liệu thiếu nhất quán.

## 11. Batch lớn về số command: chunking và index mapping

Một lệnh có count 3 tỷ và một batch có 100.000 command là **hai bài toán khác nhau**:

- Count lớn hơn 2³¹−1 đòi **`long`**.
- Rất nhiều command đòi **giới hạn kích thước batch, kiểm soát memory/packet size, timeout, transaction log và throughput**.

Ứng dụng thường chia input thành nhiều chunk có số item giới hạn, chọn ngưỡng sau benchmark trên DB/driver thực:

~~~java
int pending = 0;

for (JobChange item : changes) {
    ps.setString(1, item.getStatus());
    ps.setLong(2, item.getId());
    ps.addBatch();
    pending++;

    if (pending == batchLimit) {
        long[] counts = ps.executeLargeBatch();
        validateCounts(counts, pending);
        ps.clearBatch();
        pending = 0;
    }
}

if (pending > 0) {
    long[] counts = ps.executeLargeBatch();
    validateCounts(counts, pending);
    ps.clearBatch();
}
~~~

Đây là **pseudocode Java có thể tích hợp** sau khi định nghĩa `ps`, `changes`, `batchLimit > 0`, `JobChange` và `validateCounts`. Phải đặt vòng lặp trong transaction/error policy phù hợp. `clearBatch` chỉ xóa danh sách commands đã xếp hàng, **không rollback** những SQL đã thực thi.

Gắn vào lỗi thông tin `chunkIndex` và `offset` của dữ liệu gốc. Index 2 của chunk thứ 10 không phải index 2 của toàn job. Nếu commit mỗi chunk, các chunk trước đã commit **không bị rollback** khi chunk sau lỗi; nếu commit một lần sau mọi chunk, có thể tăng lock, transaction log và thời gian giao dịch. Phải công bố rõ SLA/semantics trước khi tối ưu.

## 12. `SUCCESS_NO_INFO` không chứng minh lệnh cập nhật đúng một dòng

Với SQL `UPDATE orders SET status = ? WHERE id = ?`, một lệnh có thể trả:

- `1`: đúng một dòng được cập nhật.
- `0`: không có row thỏa điều kiện; với optimistic locking, đây có thể là **conflict** dù JDBC không ném exception.
- `-2`: driver báo thành công nhưng **không biết row count**; không thể chắc chắn “đúng 1 dòng”.
- `-3`: failed, chỉ dùng khi driver tiếp tục sau lỗi.

Nếu hệ thống yêu cầu update đúng một bản ghi, `-2` có thể phải **fail closed** hoặc xác minh thêm trong một transaction hợp lệ; không đổi `-2` thành 1 để báo success. Nếu chỉ cần “command SQL đã chạy thành công” và không quan tâm affected rows, `-2` có thể được chấp nhận, nhưng tổng affectedRows vẫn không tính được chính xác.

Với một số driver, rewrite batch hoặc server-side optimization ảnh hưởng khả năng trả count từng lệnh. Hãy integration-test cùng các setting driver production trước khi quyết định policy.

## 13. `EXECUTE_FAILED` và các command không có entry

Ví dụ:

~~~text
planned = 5
counts  = [1, 1, -3, 1, 0]
    => index 2 failed; lệnh index 4 thành công, 0 dòng.

planned = 5
counts  = [1, 1]
    => chỉ biết prefix 2 thành công theo báo cáo.
       Không có dữ liệu count tại index 2,3,4.
~~~

Không điền `-3` cho những index vắng mặt; chúng **unreported**. Nếu lập báo cáo theo ID, trạng thái unreported phải khác failed, success-no-info và exact-count. Khi driver batch rewriting, việc nhận diện command cụ thể có thể phụ thuộc tài liệu vendor; không suy quá mức từ mảng counts.

**Mảng counts không thể thay thế truy vấn trạng thái sau commit.** Kể cả count dương không bảo đảm transaction đã commit và vẫn có thể bị rollback.

## 14. Chương trình Java độc lập mô phỏng counts lớn

Chương trình này **không kết nối cơ sở dữ liệu**. Nó tạo hai `BatchUpdateException` giả lập bằng constructor nhận `long[]`:

- Một trường hợp **continue-on-error** với count lớn 3 tỷ, success-unknown, failed marker và count 0.
- Một trường hợp **stop-on-error** chỉ có prefix gồm hai count cho năm command dự kiến.

Nhờ không phụ thuộc DB, bạn có thể chạy code để kiểm tra chính xác cách phân loại mảng và nguy cơ overflow khi dùng `getUpdateCounts()`. Kết quả **không chứng minh** driver/DB cụ thể sẽ trả đúng những mảng này trong production.

Tạo file **`LargeBatchCountsDemo.java`**:

~~~java
import java.sql.*;
import java.util.*;
import java.math.BigInteger;

public class LargeBatchCountsDemo {
    static void check(boolean ok, String message) {
        if (!ok) throw new AssertionError(message);
    }
    static String summary(long[] counts, int planned) {
        long known = 0;
        int exact = 0, unknown = 0, failed = 0;
        for (long c : counts) {
            if (c >= 0) {
                known = Math.addExact(known, c);
                exact++;
            } else if (c == Statement.SUCCESS_NO_INFO) {
                unknown++;
            } else if (c == Statement.EXECUTE_FAILED) {
                failed++;
            } else {
                throw new IllegalArgumentException("Unknown marker: " + c);
            }
        }
        return "exact=" + exact + ", unknown=" + unknown
                + ", failed=" + failed + ", unreported=" + (planned - counts.length)
                + ", knownAffected=" + known;
    }
    public static void main(String[] args) throws SQLException {
        long[] continuedCounts = {
            1L, 3_000_000_000L, Statement.SUCCESS_NO_INFO,
            Statement.EXECUTE_FAILED, 0L
        };
        BatchUpdateException continued = new BatchUpdateException(
            "simulated batch failure", "23000", 7001, continuedCounts,
            new SQLException("simulated duplicate key"));
        long[] large = continued.getLargeUpdateCounts();
        System.out.println("continued: " + Arrays.toString(large));
        System.out.println("continued summary: " + summary(large, 5));
        System.out.println("SQLState: " + continued.getSQLState());
        System.out.println("vendor code: " + continued.getErrorCode());
        System.out.println("cause: " + continued.getCause().getMessage());
        int[] narrow = continued.getUpdateCounts();
        System.out.println("legacy count[1]: " + narrow[1]);
        System.out.println("large count[1]: " + large[1]);

        BatchUpdateException stopped = new BatchUpdateException(
            "simulated early stop", "23000", 7001,
            new long[] {1L, 3_000_000_000L}, null);
        System.out.println("stopped: " +
                Arrays.toString(stopped.getLargeUpdateCounts()));
        System.out.println("stopped summary: " +
                summary(stopped.getLargeUpdateCounts(), 5));
        System.out.println("sentinels: success=" + Statement.SUCCESS_NO_INFO
                + ", failure=" + Statement.EXECUTE_FAILED);

        long known = 1L + 3_000_000_000L;
        System.out.println("known affected is not total: " + known);

        boolean badCountRejected = false;
        try {
            summary(new long[] {-4L}, 1);
        } catch (IllegalArgumentException ex) {
            badCountRejected = true;
        }
        System.out.println("unknown marker rejected: " + badCountRejected);

        check(large.length == 5, "continue length");
        check(large[1] > Integer.MAX_VALUE, "large count");
        check(narrow[1] != large[1], "legacy overflow demo");
        check(summary(large, 5).equals(
                "exact=3, unknown=1, failed=1, unreported=0, knownAffected=3000000001"),
                "continue summary");
        check(summary(stopped.getLargeUpdateCounts(), 5).equals(
                "exact=2, unknown=0, failed=0, unreported=3, knownAffected=3000000001"),
                "stop summary");
        check(known == 3_000_000_001L, "exact addition");
        check(continued.getCause() instanceof SQLException, "cause");
        check(badCountRejected, "marker validation");
        System.out.println("all checks passed");
    }
}
~~~

Biên dịch và chạy:

~~~bash
javac --release 17 -encoding UTF-8 LargeBatchCountsDemo.java
java LargeBatchCountsDemo
~~~

**Stdout chính xác đã kiểm thử với JDK 17:**

~~~text
continued: [1, 3000000000, -2, -3, 0]
continued summary: exact=3, unknown=1, failed=1, unreported=0, knownAffected=3000000001
SQLState: 23000
vendor code: 7001
cause: simulated duplicate key
legacy count[1]: -1294967296
large count[1]: 3000000000
stopped: [1, 3000000000]
stopped summary: exact=2, unknown=0, failed=0, unreported=3, knownAffected=3000000001
sentinels: success=-2, failure=-3
known affected is not total: 3000000001
unknown marker rejected: true
all checks passed
~~~

Đọc các kết quả chính:

1. Mảng `continued` có năm entry, bao gồm `-2` là success unknown, `-3` là failed và `0` là thành công 0 dòng.
2. Count `3000000000` được giữ nguyên trong `getLargeUpdateCounts` nhưng trở thành `-1294967296` khi đi qua `getUpdateCounts` trên JDK đã chạy. Đây là minh họa overflow; **không xây nghiệp vụ dựa vào con số overflow này**.
3. Mảng `stopped` chỉ có hai entry cho năm command, nên có ba entry **unreported**, không tự suy ba command đều failed.
4. Tổng `knownAffected=3000000001` chỉ là **tổng các count xác định**, không phải tổng thực khi có success-no-info, càng không phải tổng đã commit.
5. `SQLState`/vendor code/cause được đọc đúng từ exception giả lập, không đại diện driver thực tế.
6. `all checks passed` xuất hiện sau **8 phép kiểm tra** về count, sentinel, length, overflow và type của cause.

## 15. Kiểm thử thực tế trên database/driver

Synthetic exception **kiểm tra được logic Java**, nhưng không thay cho integration test JDBC:

1. Driver của môi trường có hỗ trợ `executeLargeBatch` hay không? Có ném `UnsupportedOperationException`?
2. Với 3 lệnh thành công, mảng counts có đúng 3 entry theo thứ tự add không?
3. Với lỗi constraint ở command giữa, driver **stop** hay **continue**? `getLargeUpdateCounts` có prefix hay full-length?
4. Có trường hợp `SUCCESS_NO_INFO` do batch rewrite/batching optimization?
5. Lệnh update 0 dòng được report 0 như thế nào? Với optimistic lock, ứng dụng xử lý ra sao?
6. Khi `setAutoCommit(false)` và rollback thành công, dữ liệu thực sự không còn những thay đổi?
7. Khi auto-commit bật, batch lỗi có partial commits không?
8. Nếu phải đọc count hơn `Integer.MAX_VALUE`, cơ sở dữ liệu/driver có trả đúng `long` không? Nếu tạo dataset khổng lồ không khả thi, tách synthetic test large count với integration test driver support.
9. Chained SQLExceptions có chứa mã lỗi hữu ích không?
10. Batch size tối ưu theo packet size, memory, network latency, query plan và transaction log là bao nhiêu?
11. Thay đổi cấu hình driver batch rewriting có ảnh hưởng per-item counts hoặc generated keys?
12. Với timeout, deadlock, mất kết nối khi commit, hệ thống có reconciliation/idempotency?
13. Mỗi chunk commit riêng hay toàn job commit một lần? Có biết partial outcome không?
14. Có kiểm thử rollback failure để bảo toàn suppressed exception?

Không ngụy tạo thông số benchmark hoặc khẳng định DBMS cụ thể luôn có cùng hành vi. Ghi rõ driver version, database version, SQL và transaction setting khi báo kết quả.

## 17. Bài tập có đáp án

### Bài 1 — Hai loại “lớn”

Một batch có 10 lệnh, mỗi lệnh sửa 1 dòng; một batch khác có 1 lệnh sửa 3 tỷ dòng. Trường hợp nào cần `long` để giữ **per-command count**?

**Đáp án:** Trường hợp một lệnh sửa 3 tỷ dòng. Nhiều command không mặc nhiên đòi `long` cho count từng lệnh, dù vẫn có vấn đề bộ nhớ/throughput.

### Bài 2 — Getter tương thích với `executeLargeBatch`

**Đáp án:** `BatchUpdateException.getLargeUpdateCounts()`, nhận `long[]`, không phải `getUpdateCounts()`.

### Bài 3 — `[1,-2,-3,0]` có những trạng thái nào?

**Đáp án:** Một lệnh exact 1 dòng, một success unknown, một failed, một success 0 dòng. `-2` không phải failed và `0` không phải lỗi SQL.

### Bài 4 — Có được báo affected total = 3000000001?

Counts `[1,3000000000,-2]`.

**Đáp án:** Chỉ được nói **known affected rows** là 3000000001. Vì có `-2`, total thực không xác định chính xác.

### Bài 5 — Mảng ngắn

Dự kiến 5 command nhưng counts `[1,1]`. Ba lệnh còn lại có phải `EXECUTE_FAILED`?

**Đáp án:** Không. Chỉ biết hai entry prefix được báo; những lệnh thiếu count phải giữ trạng thái **unreported**, xem driver/transaction.

### Bài 6 — Continue-on-error

Dự kiến 5 command, counts `[1,1,-3,1,0]`. Lệnh nào thất bại?

**Đáp án:** Index 2 có `Statement.EXECUTE_FAILED`. Index 4 thành công nhưng sửa 0 dòng.

### Bài 7 — Overflow

Tại sao `3000000000L` không thể lưu nguyên vẹn trong `int`?

**Đáp án:** Vì `int` signed tối đa 2147483647. Nên giữ `long` và chỉ cast khi đã validate miền phù hợp.

### Bài 8 — Transaction all-or-nothing

**Đáp án:** Quản lý `setAutoCommit(false)`, thực thi/kiểm invariant rồi `commit`; nếu lỗi thì `rollback`, bảo toàn rollback error, kiểm khả năng transaction của DB.

### Bài 9 — `SUCCESS_NO_INFO` với yêu cầu mỗi ID cập nhật đúng 1 row

**Đáp án:** Không đủ chứng cứ row count = 1. Ứng dụng có thể fail closed/rollback hoặc xác minh theo chiến lược phù hợp.

### Bài 10 — Timeout lúc commit

**Đáp án:** Không retry ngay toàn batch vì trạng thái commit có thể chưa chắc chắn. Thiết kế idempotency/reconciliation và kiểm DB.

### Bài 11 — Chunking và atomicity

**Đáp án:** Commit mỗi chunk thì lỗi chunk cuối không rollback được những chunk đã commit. Muốn all-or-nothing phải dùng một cơ chế transaction/ingestion hỗ trợ tương ứng.

### Bài 12 — Driver không hỗ trợ large API

**Đáp án:** Phần triển khai mặc định của `executeLargeBatch` có thể ném `UnsupportedOperationException`. Nếu count lớn có ý nghĩa nghiệp vụ, phải dùng driver hỗ trợ hoặc thiết kế thay thế vẫn giữ chính xác, không lặng lẽ dùng `int[]`.

## 18. Checklist production

- [ ] Đã phân biệt số command, số dòng mỗi command, số dòng đã biết và trạng thái commit?
- [ ] Có trường hợp per-command count vượt `Integer.MAX_VALUE`?
- [ ] Nếu có, dùng `executeLargeBatch` và `getLargeUpdateCounts` cùng nhau?
- [ ] Driver JDBC/DBMS thực tế hỗ trợ large-count API?
- [ ] Không ép `long` xuống `int` ở API, metrics, logging hoặc transport?
- [ ] `SUCCESS_NO_INFO` được phân loại là thành công nhưng không biết count?
- [ ] `EXECUTE_FAILED` được phân loại là command failed?
- [ ] Count `0` được xử lý theo domain (có thể là optimistic-lock conflict)?
- [ ] Mảng counts có thể là prefix ngắn hoặc toàn bộ batch?
- [ ] Đã giữ index input/chunk để mapping lỗi đúng command?
- [ ] Không biến các command unreported thành failed?
- [ ] Tổng counts chỉ cộng giá trị không âm; có xử lý overflow?
- [ ] SQLState, vendor code, cause và SQLException chain được lưu an toàn?
- [ ] Transaction policy all-or-nothing/partial-success được công bố rõ?
- [ ] Auto-commit được chọn đúng, có rollback nếu lỗi?
- [ ] Rollback failure được giữ làm suppressed exception?
- [ ] Commit failure/timeout có reconciliation và idempotency?
- [ ] `SUCCESS_NO_INFO` với invariant exactly-one-row có được fail closed/xác minh?
- [ ] Chunk size có giới hạn, được benchmark theo database driver thực?
- [ ] Commit per chunk hay after all chunks đã được thiết kế nhất quán?
- [ ] Không dựa vào synthetic exception để kết luận driver DB thực?
- [ ] Code Java/expected stdout đã được biên dịch/chạy xác minh?

**Kết luận:** Với batch JDBC có khả năng trả **row count lớn**, cặp `executeLargeBatch` + `BatchUpdateException.getLargeUpdateCounts` là lựa chọn phù hợp của JDBC 4.2 để giữ độ chính xác `long[]`. Hãy phân biệt exact count, `SUCCESS_NO_INFO`, `EXECUTE_FAILED` và unreported entries. Khi batch lỗi, counts cho biết thông tin thực thi mà driver báo, **không chứng nhận dữ liệu đã commit**. Kết hợp kiểm tra driver, quản lý transaction, chunking và cơ chế retry an toàn để tránh tràn số hoặc xử lý dữ liệu sai.

- [`Connection` — Java SE 26](https://docs.oracle.com/en/java/javase/26/docs/api/java.sql/java/sql/Connection.html): `setAutoCommit`, `commit`, `rollback`, savepoint, transaction semantics.
- [`SQLException` — Java SE 26](https://docs.oracle.com/en/java/javase/26/docs/api/java.sql/java/sql/SQLException.html): `SQLState`, vendor code và chained exceptions.
