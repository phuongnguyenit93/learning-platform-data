# JDBC 4.2 và các API tiếp tục dùng trong driver hiện đại

**JDBC 4.2 là một phần của Java SE 8 và không phải công nghệ đã hết giá trị.** Những giao diện quen thuộc như `DataSource`, `Connection`, `PreparedStatement`, `ResultSet`, `CallableStatement` tiếp tục đóng vai trò nền tảng của truy cập cơ sở dữ liệu quan hệ trong các ứng dụng Java hiện đại. Các cải tiến của JDBC 4.2 như **`SQLType` / `JDBCType`**, hỗ trợ kiểu ngày giờ của `java.time`, **`REF_CURSOR`** và **large update counts** vẫn có thể được sử dụng với các driver phù hợp.

Điều cần phân biệt là **API có mặt trong JDK** không đồng nghĩa **mọi driver, mọi database và mọi phiên bản server hỗ trợ đầy đủ tính năng đó**. Một method được khai báo trên `PreparedStatement` vẫn có thể ném `SQLFeatureNotSupportedException` hoặc `UnsupportedOperationException` từ default implementation/driver khi chức năng tương ứng không được cung cấp.

Bài học thuộc mục **JDBC 4.2** với đề tài **“JDBC 4.2 và các API tiếp tục dùng trong driver hiện đại”**. Nội dung phân biệt tính năng **được thêm ở JDBC 4.2** với các tính năng **ra đời trước nhưng vẫn là best practice**, giải thích cách dùng và giới hạn của các API, mapping `java.time`, kiểm tra khả năng hỗ trợ của driver, transactions, resources, SQL injection, cùng ví dụ Java hoàn chỉnh và checklist tích hợp.

Theo tài liệu Java SE 26, package `java.sql` mô tả **JDBC 4.5** là API hiện hành và nói rõ nó **kế thừa JDBC 4.4, 4.3, 4.2...**. Vì vậy, học đúng JDBC 4.2 là học một lớp nền tảng vẫn được sử dụng, **không phải khuyến khích quay về driver cũ hay ngừng cập nhật bảo mật**. Bài chỉ giữ những kiến thức tiếp tục áp dụng hiện nay, và ghi rõ ranh giới phiên bản của các tính năng mới hơn.

## 1. Vị trí của JDBC 4.2 trong lịch sử API Java

| Phiên bản JDBC | Phiên bản Java SE gắn với API | Một vài điểm đáng nhớ |
| --- | --- | --- |
| JDBC 4.0 | Java SE 6 | Cơ chế driver discovery qua service provider và nhiều API như `SQLXML` |
| JDBC 4.1 | Java SE 7 | `try-with-resources` cho `Connection`/`Statement`/`ResultSet`; `ResultSet.getObject(..., Class<T>)`; network timeout/abort trên `Connection` |
| **JDBC 4.2** | **Java SE 8** | `SQLType`, `JDBCType`, mappings `java.time`, `REF_CURSOR`, large-update methods, `DriverAction` |
| JDBC 4.3 | Java SE 9 | Các bổ sung như sharding keys và tiện ích quoting identifiers/literals |
| JDBC 4.4 | Java SE 24 | Các bổ sung mới hơn, **không** được gán cho Java 8 |
| JDBC 4.5 | Java SE 26 | API mới hơn, **kế thừa** các lớp JDBC 4.2 |

**Lưu ý trọng tâm:** `PreparedStatement`, `Connection`, `DataSource`, `ResultSet` và `try-with-resources` **không phải tất cả đều được tạo mới trong JDBC 4.2**. Chúng vẫn là cách viết JDBC hiện hành và cần được dạy bên cạnh những cải tiến 4.2, nhưng phải phân biệt nguồn gốc cho chính xác.

### 1.1. Phiên bản JDK khác với phiên bản driver

JDK cung cấp **các interface và class API** trong module `java.sql`. Một **JDBC driver** là implementation do vendor cung cấp để biến lời gọi API thành giao thức giao tiếp với database cụ thể.

~~~text
Ứng dụng Java
  -> javax.sql.DataSource / java.sql.*
  -> JDBC driver đã cấu hình
  -> PostgreSQL / Oracle Database / SQL Server / MySQL / ...
~~~

Nâng JDK không tự động cài đúng driver cho database. Ngược lại, driver có tên phiên bản thương mại riêng, không nhất thiết trùng “4.2” hoặc “4.3” của JDBC specification.

Ví dụ, một driver trên JDK 17/21 có thể triển khai JDBC 4.3 hoặc 4.5 tùy vendor/phiên bản, nhưng các API cốt lõi của JDBC 4.2 vẫn tiếp tục được gọi. **Luôn dùng bản driver được nhà cung cấp hỗ trợ cho JDK và database server bạn đang chạy**, và kiểm thử tính năng cụ thể.

### 1.2. API tồn tại ≠ feature được hỗ trợ

Một phương thức mới có thể được thêm vào interface Java bằng `default` method để giữ khả năng tương thích nhị phân. Vì vậy code của bạn **biên dịch** thành công nhưng đến runtime vẫn có thể nhận lỗi không hỗ trợ.

Ví dụ `PreparedStatement.setObject(index, value, JDBCType.TIMESTAMP)` là overload JDBC 4.2 có đối số `SQLType`, nhưng Javadoc mô tả default implementation có thể ném `SQLFeatureNotSupportedException`. Driver thực tế phải triển khai chức năng thì lời gọi mới chạy.

Tương tự, `PreparedStatement.executeLargeUpdate()` có chữ ký trả `long`, nhưng default implementation có thể ném `UnsupportedOperationException`. Đừng suy rằng **“method xuất hiện trong IDE” = “server chắc chắn thực hiện được”**.

## 2. Kiến trúc JDBC hiện hành: những vai trò không thay đổi

Các interface dưới đây có thể đã xuất hiện **trước JDBC 4.2**, nhưng vẫn được sử dụng hàng ngày:

| API | Vai trò | Quy tắc thực hành |
| --- | --- | --- |
| `DataSource` | Cung cấp `Connection`, thường tích hợp connection pool | Cấu hình một nơi, dùng pool được quản lý, đóng `Connection` để trả về pool |
| `Connection` | Phiên kết nối JDBC và transaction boundary | Không dùng đồng thời tùy tiện trên nhiều thread; commit/rollback/close rõ |
| `PreparedStatement` | SQL parameterized, binding các giá trị | Tránh nối chuỗi input người dùng vào SQL, reuse trong đúng phạm vi |
| `ResultSet` | Cursor đọc các dòng trả về | Duyệt bằng `next()`, xử lý SQL NULL, đóng khi xong |
| `CallableStatement` | Gọi stored procedure/function qua JDBC | Dùng khi database có stored procedure phù hợp; feature phụ thuộc vendor |
| `DatabaseMetaData` | Kiểm tra đặc tính database/driver | Probe các tính năng tùy chọn, không đoán từ tên JAR |
| `SQLException` và subclasses | Truyền lỗi từ database/driver | Quan sát SQLState, error code, cause; không nuốt lỗi |
| `JDBCType` / `SQLType` | Biểu diễn loại SQL rõ ràng | Đây là bổ sung của JDBC 4.2, hỗ trợ type-safe hơn so với chỉ dùng int constants |

**Connection không đồng nghĩa transaction:** nhiều driver bật `autoCommit` ban đầu, nên từng DML statement có thể commit riêng. Nếu một nghiệp vụ phải cập nhật nhiều bước atomically, hãy điều khiển transaction tường minh theo yêu cầu. Một `DataSource` có pool cũng không tự biến các phương thức của một `Connection` đang chia sẻ thành thread-safe.

## 3. Cải tiến JDBC 4.2: SQLType và JDBCType

### 3.1. Khác nhau giữa interface và enum

- **`java.sql.SQLType`** là interface đại diện cho một SQL type, có thể dùng cho loại chung hoặc loại đặc thù của vendor.
- **`java.sql.JDBCType`** là enum triển khai `SQLType`, chứa các SQL type chung như `VARCHAR`, `INTEGER`, `BIGINT`, `DATE`, `TIME`, `TIMESTAMP`, `DECIMAL` và các kiểu JDBC 4.2 như `TIME_WITH_TIMEZONE`, `TIMESTAMP_WITH_TIMEZONE`, `REF_CURSOR`.
- **`java.sql.Types`** chứa các hằng số kiểu `int` có từ trước. Nó vẫn còn sử dụng được; không phải “API bị bỏ” chỉ vì có `JDBCType`.

~~~java
SQLType textType = JDBCType.VARCHAR;
SQLType amountType = JDBCType.DECIMAL;
SQLType dateType = JDBCType.DATE;

System.out.println(dateType.getName()); // DATE
~~~

Đây là **mã minh họa**, cần import `java.sql.SQLType` và `java.sql.JDBCType`.

### 3.2. Tại sao type object giúp ích?

~~~java
// JDBC 4.2:
statement.setObject(1, value, JDBCType.DECIMAL);

// Cách dùng int SQL type vẫn hợp lệ:
statement.setObject(1, value, Types.DECIMAL);
~~~

Đây là **hai cách minh họa** đối với `PreparedStatement statement` và `value` do ứng dụng cung cấp. `JDBCType.DECIMAL` thường rõ nghĩa hơn một số nguyên, và interface `SQLType` cho phép vendor types.

**Nhưng tính portable không đến từ tên enum một cách tự động.** Phải xem driver có hỗ trợ overload `SQLType` và chuyển đổi kiểu được yêu cầu hay không.

### 3.3. Các phương thức SQLType quan trọng

~~~java
SQLType type = JDBCType.TIMESTAMP_WITH_TIMEZONE;

String name = type.getName();
String vendor = type.getVendor();
Integer code = type.getVendorTypeNumber();
~~~

`getName` trả tên SQL type, `getVendor` nhận diện vendor khai báo kiểu, `getVendorTypeNumber` cho mã kiểu. Với `JDBCType` chuẩn, có thể đối chiếu mã với `Types`.

Không hardcode giá trị số của type vào code khi đã có enum/hằng số có tên. Nếu cần vendor-specific JSON, UUID, ARRAY, GEOMETRY... phải xem **mapping và extension của driver**, không giả định mọi database xử lý cùng một SQL type hoặc cùng một Java class.

### 3.4. NULL có kiểu cũng cần chính sách

~~~java
ps.setNull(1, Types.VARCHAR);
~~~

Đây là ví dụ với `PreparedStatement ps` đã cấu hình. Không dùng `ps.setObject(1, null)` rồi tin mọi driver suy luận chính xác loại SQL cần thiết. Javadoc khuyến nghị dùng `setNull` hoặc `setObject` với target type để bảo đảm chuyển đổi rõ hơn.

Đối với overload `SQLType`, `ps.setObject(1, null, JDBCType.VARCHAR)` có thể hợp lệ nếu driver hỗ trợ; **`setNull(1, Types.VARCHAR)`** vẫn là lựa chọn phổ biến và rõ nghĩa khi tính tương thích driver quan trọng.

## 4. Java time và JDBC 4.2: thay đổi có giá trị lớn

Trước đây, mã JDBC thường lấy ngày giờ bằng `java.sql.Date`, `java.sql.Time` hoặc `java.sql.Timestamp`. JDBC 4.2 thiết lập mappings cho các kiểu **`java.time`** có từ Java 8; đây vẫn là cách viết tự nhiên cho ứng dụng mới khi driver hỗ trợ.

### 4.1. Bảng mapping cần ghi nhớ

| SQL type | Java type phù hợp | Ý nghĩa |
| --- | --- | --- |
| `DATE` | `java.time.LocalDate` | Ngày theo lịch, **không có giờ hoặc offset** |
| `TIME` (không time zone) | `java.time.LocalTime` | Giờ trong ngày, **không có date hoặc offset** |
| `TIMESTAMP` (không time zone) | `java.time.LocalDateTime` | Ngày + giờ địa phương, **không xác định một instant toàn cục** |
| `TIME_WITH_TIMEZONE` | `java.time.OffsetTime` | Giờ + offset; mức hỗ trợ thực tế của DB/driver có thể khác nhau |
| `TIMESTAMP_WITH_TIMEZONE` | `java.time.OffsetDateTime` | Ngày giờ + offset, diễn đạt được instant; cách DB lưu/trả offset phụ thuộc hệ quản trị |

Đây là các mappings liên quan JDBC 4.2; **không phải cam kết mọi database hỗ trợ đầy đủ năm cặp kiểu**. Cụ thể, loại SQL `TIME WITH TIME ZONE` không tồn tại hoặc không được hỗ trợ tương ứng trên một số database.

Theo tài liệu pgJDBC được cập nhật, PostgreSQL driver hỗ trợ các mapping `LocalDate`, `LocalTime`, `LocalDateTime`, `OffsetTime` và `OffsetDateTime` theo các cột tương ứng; `Instant` và `ZonedDateTime` **không được pgJDBC hỗ trợ như direct mappings**. Tài liệu cũng nêu `OffsetDateTime` đọc từ PostgreSQL `TIMESTAMP WITH TIME ZONE` có thể có offset UTC (+00:00) bởi cách backend lưu timestamp. Đừng suy rằng Javadoc của Java là tài liệu đủ cho mọi mapping vendor.

### 4.2. Ghi java.time bằng PreparedStatement.setObject

~~~java
LocalDate birthday = LocalDate.of(2000, 1, 15);

try (PreparedStatement ps = con.prepareStatement(
        "INSERT INTO people (birthday) VALUES (?)")) {
    ps.setObject(1, birthday);
    ps.executeUpdate();
}
~~~

Đây là **đoạn minh họa yêu cầu database**, với `con` là `Connection` đang mở và bảng `people` có cột `DATE` phù hợp. `setObject(index, LocalDate)` là cách đưa java.time object qua driver hỗ trợ mapping JDBC 4.2. Bất kỳ SQL schema/vendor cụ thể nào vẫn phải được kiểm thử.

Có thể yêu cầu target type tường minh:

~~~java
ps.setObject(1, birthday, JDBCType.DATE);
~~~

**Lưu ý runtime:** overload `SQLType` này có default implementation có thể ném `SQLFeatureNotSupportedException` nếu driver không triển khai; không tự fallback rồi chạy lại statement đã có side effect một cách mù quáng. Hãy probe/kiểm thử trước và chọn một chính sách đã biết phù hợp.

### 4.3. Đọc java.time bằng ResultSet.getObject(Class<T>)

~~~java
try (PreparedStatement ps = con.prepareStatement(
        "SELECT birthday FROM people WHERE id = ?")) {

    ps.setLong(1, personId);

    try (ResultSet rs = ps.executeQuery()) {
        if (rs.next()) {
            LocalDate birthday =
                rs.getObject("birthday", LocalDate.class);
        }
    }
}
~~~

Đây là đoạn minh họa cần `con` và `personId`. **Cú pháp `getObject(column, Class<T>)` được giới thiệu từ JDBC 4.1**, trong khi hỗ trợ mappings **`java.time`** được bổ sung ở JDBC 4.2. Đây là phân biệt phiên bản quan trọng.

Một `ResultSet` có thể trả `null` nếu cột SQL là `NULL` và kiểu đích là reference type. Phải xử lý bằng domain policy, không tự coi Java `null` là ngày 1970-01-01 hay một instant mặc định.

### 4.4. DATE, TIMESTAMP và offset không thể hoán đổi tùy tiện

- `LocalDate` không chứa giờ/zone.
- `LocalDateTime` chứa giờ địa phương nhưng **không xác định duy nhất một instant**.
- `OffsetDateTime` kèm offset để xác định instant; **không giữ nguyên tên zone** như `Asia/Ho_Chi_Minh`.
- `ZonedDateTime` có zone ID và zone rules, nhưng **không phải mapping JDBC 4.2 phổ quát cho mọi SQL timestamp**.
- `Instant` rất hữu ích trong domain model, nhưng không mặc định được driver hỗ trợ trực tiếp bằng `setObject/getObject(..., Instant.class)`; có thể chuyển qua `OffsetDateTime` ở UTC hoặc adapter được kiểm chứng.

~~~java
OffsetDateTime dbValue =
    rs.getObject("created_at", OffsetDateTime.class);

Instant instant =
    dbValue == null ? null : dbValue.toInstant();
~~~

Đây là mã minh họa. SQL column cần phù hợp với `TIMESTAMP WITH TIME ZONE` và driver hỗ trợ. Nếu cột chỉ là `TIMESTAMP WITHOUT TIME ZONE`, tự gắn UTC vào một `LocalDateTime` là **quyết định nghiệp vụ** phải được định nghĩa theo schema, không phải phép chuyển đổi hiển nhiên của JDBC.

### 4.5. Không nhầm TIMESTAMP WITH TIME ZONE với việc lưu zone ID

Tên SQL type có chữ `WITH TIME ZONE` không có nghĩa database chắc chắn lưu lại **tên zone** gốc hoặc bảo toàn offset người gửi dưới cùng một dạng. Một số hệ thống chuẩn hóa giá trị về UTC. Nếu ứng dụng cần lưu `Europe/Paris` hoặc `Asia/Ho_Chi_Minh` làm zone ID để tính lịch hẹn tương lai và DST, cần **lưu zone ID riêng** hoặc thiết kế schema chuyên biệt.

### 4.6. Precision và fractional seconds

Database và driver có thể cắt/làm tròn phần nanosecond theo độ chính xác cột. Ví dụ `LocalDateTime` trong Java có nanosecond, nhưng cột SQL `TIMESTAMP(3)` có thể chỉ lưu millisecond. Test round-trip phải so sánh theo precision của schema hoặc chọn cột phù hợp, không mặc định bitwise equality.

## 5. REF_CURSOR và CallableStatement

Một trong các bổ sung được Oracle liệt kê ở JDBC 4.2 là **hỗ trợ `REF_CURSOR`** — một out parameter của stored procedure có thể biểu diễn tập kết quả. Tuy nhiên, đây là tính năng **tùy database/driver**.

### 5.1. Kiểm tra driver có hỗ trợ không

~~~java
DatabaseMetaData metadata = connection.getMetaData();

boolean supported = metadata.supportsRefCursors();
~~~

Đây là mã minh họa; `connection` được mở trước. `supportsRefCursors()` giúp ứng dụng quyết định có nên sử dụng stored procedure trả cursor kiểu này hay không. Nếu database không có stored procedure với REF_CURSOR thì **không cần cố dùng API này** để “được gọi là JDBC 4.2”.

### 5.2. Gọi stored procedure trả REF_CURSOR

~~~java
try (CallableStatement cs =
         connection.prepareCall("{call find_people(?)}")) {

    cs.registerOutParameter(1, Types.REF_CURSOR);
    cs.execute();

    try (ResultSet rows =
             cs.getObject(1, ResultSet.class)) {

        while (rows.next()) {
            System.out.println(rows.getString(1));
        }
    }
}
~~~

Đây là **mã minh họa phụ thuộc stored procedure thực tế**, không phải ví dụ chạy khi không có database. Cú pháp call, thủ tục, kiểu OUT và hành vi commit có thể khác theo vendor. `registerOutParameter(1, Types.REF_CURSOR)` dùng hằng số xuất hiện ở JDBC 4.2; `cs.getObject(1, ResultSet.class)` có kiểu trả rõ ràng.

Nếu driver không hỗ trợ `REF_CURSOR`, Javadoc cho phép ném `SQLFeatureNotSupportedException`. Đừng tự mặc định stored procedure của Microsoft SQL Server, PostgreSQL hay Oracle dùng cùng dạng OUT cursor. Kiểm tra tài liệu và integration test driver thực tế.

### 5.3. REF_CURSOR không thay thế ResultSet thông thường

Đối với truy vấn dữ liệu đơn giản, `PreparedStatement.executeQuery` trả `ResultSet` vẫn là lựa chọn trực tiếp và phổ biến. `REF_CURSOR` có giá trị khi **stored procedure interface** thực sự đòi output đó.

Không chuyển mọi câu `SELECT` thành stored procedure chỉ để dùng một tính năng JDBC 4.2 tùy chọn.

## 6. Large update counts: vì sao có họ phương thức executeLarge*

Những API JDBC cũ thường dùng `int` cho số dòng cập nhật. Khi một thao tác DML/batch có thể tác động hơn **`Integer.MAX_VALUE`** dòng, `int` không đủ biểu diễn. JDBC 4.2 bổ sung các phương thức liên quan **long update counts**.

### 6.1. Các phương thức đáng nhớ

| API | Kết quả | Ý nghĩa |
| --- | --- | --- |
| `Statement.executeLargeUpdate(sql)` | `long` | Chạy DML/DDL, trả số dòng update có thể lớn |
| `PreparedStatement.executeLargeUpdate()` | `long` | Tương tự với SQL đã chuẩn bị |
| `Statement.executeLargeBatch()` | `long[]` | Số dòng/đánh dấu kết quả cho từng lệnh trong batch |
| `Statement.getLargeUpdateCount()` | `long` | Lấy số dòng DML lớn từ kết quả statement hiện tại |
| `Statement.setLargeMaxRows(long)` / `getLargeMaxRows()` | `void` / `long` | Giới hạn số hàng trong ResultSet với kiểu long |
| `DatabaseMetaData.getMaxLogicalLobSize()` | `long` | Khả năng kích thước logical LOB, theo metadata driver |

**Không hiểu sai:** `executeLargeUpdate` không khiến database chạy nhanh hơn. Chữ `Large` nói đến **kiểu trả về của row count/giới hạn**, không phải streaming tự động, bulk engine mới hoặc performance guarantee.

### 6.2. Dùng với PreparedStatement

~~~java
try (PreparedStatement ps = con.prepareStatement(
        "DELETE FROM audit_log WHERE created_at < ?")) {

    ps.setObject(1, cutoff);

    long updated = ps.executeLargeUpdate();
    System.out.println("Rows changed: " + updated);
}
~~~

Đây là **mã minh họa**, `con` là `Connection`, `cutoff` là giá trị được driver chuyển đổi phù hợp. DML có thể có ảnh hưởng lớn, cần kiểm soát transaction, lock, batch strategy và an toàn nghiệp vụ.

**Quan trọng:** default implementation của `PreparedStatement.executeLargeUpdate()` được Javadoc ghi có thể ném `UnsupportedOperationException`. Không tự cho rằng “Java 8 có method này” thì mọi driver đã override.

### 6.3. executeLargeBatch và mã sentinel

~~~java
try (PreparedStatement ps = con.prepareStatement(
        "INSERT INTO events (event_id) VALUES (?)")) {

    for (long id : eventIds) {
        ps.setLong(1, id);
        ps.addBatch();
    }

    long[] counts = ps.executeLargeBatch();
}
~~~

Đây là mã minh họa, `eventIds` và DB schema do ứng dụng cung cấp. Kết quả batch có thể chứa các sentinel như `Statement.SUCCESS_NO_INFO` hoặc `Statement.EXECUTE_FAILED`, không nhất thiết mọi phần tử là một row count dương chính xác.

Nếu batch lỗi, `BatchUpdateException` có thể kèm danh sách counts của các lệnh đã xử lý. Không đơn giản tính tổng mảng rồi xem như transaction đã commit đầy đủ; kiểm tra **transaction state** và rollback/commit đúng.

### 6.4. Khi nào vẫn dùng executeUpdate?

Nếu số dòng ảnh hưởng theo nghiệp vụ chắc chắn nhỏ hơn `Integer.MAX_VALUE`, `executeUpdate()` trả `int` vẫn là API hiện hành và phù hợp. Không phải lúc nào cũng cần chuyển sang `executeLargeUpdate` — đặc biệt khi driver không hỗ trợ overload mới.

## 7. DriverAction: tính năng JDBC 4.2 dành cho driver

`java.sql.DriverAction` được bổ sung để cho phép implementer của JDBC driver nhận callback khi driver bị deregister từ `DriverManager`. Nó liên quan đến **vòng đời driver** và cơ chế service container/hot redeploy.

**Không phải** một cơ chế thay thế `DataSource`, connection pooling hoặc transaction management ở tầng business.

~~~java
// Mô tả API ở tầng triển khai driver:
DriverManager.registerDriver(driver, driverAction);
~~~

Đây là **mã minh họa**, `driver`/`driverAction` phải được cung cấp từ code quản lý driver. Ứng dụng bình thường dùng driver JDBC theo tài liệu vendor, thay vì tự đăng ký/deregister driver ở từng request.

Một số môi trường container có classloader lifecycle cần cleanup đúng để tránh resource leak, nhưng không tự đưa logic gọi `DriverManager.deregisterDriver` vào code ứng dụng một cách tùy tiện.

## 8. DataSource tiếp tục là hướng tổ chức kết nối tốt

Trong dịch vụ Java hiện đại, `javax.sql.DataSource` thường là entrypoint cho connection pooling, cấu hình và quản lý tài nguyên theo application/framework. JDBC 4.2 không loại bỏ `DataSource`.

~~~java
public static int findCount(DataSource dataSource)
        throws SQLException {

    try (Connection con = dataSource.getConnection();
         PreparedStatement ps = con.prepareStatement(
             "SELECT COUNT(*) FROM people")) {

        try (ResultSet rs = ps.executeQuery()) {
            if (!rs.next()) {
                throw new SQLException("Missing count row");
            }
            return rs.getInt(1);
        }
    }
}
~~~

Đây là **phương thức minh họa**, cần imports `javax.sql.DataSource` và `java.sql.*`. Nó cần database có bảng `people`; không phải demo không cần driver.

### 8.1. Connection pool không phải Connection singleton

Một `DataSource` được chia sẻ giữa requests có thể cấp **một Connection khác nhau theo mỗi lần checkout**. Với pool, `Connection.close()` thường **trả logical connection về pool** thay vì nhất thiết đóng physical TCP socket ngay.

Đừng giữ một `Connection` toàn cục rồi cho nhiều request cùng gọi `prepareStatement`/`commit` trên nó. Concurrency support và thread-safety của Connection/driver cần kiểm tra riêng; cách đơn giản thường là **mỗi logical unit of work có một connection được cấp và đóng trong phạm vi rõ**.

### 8.2. DriverManager còn dùng được không?

~~~java
try (Connection con =
         DriverManager.getConnection(jdbcUrl, user, password)) {
    // ...
}
~~~

Đây là minh họa. `DriverManager` vẫn hợp lệ và có ích cho demo/tool nhỏ. Với service production có nhiều request, `DataSource` cộng pool được quản lý thường tốt hơn về connection lifecycle và cấu hình. Đừng gọi `DriverManager` là API đã bị xóa hoặc deprecated chỉ vì ứng dụng framework ưu tiên DataSource.

### 8.3. Có cần Class.forName("...Driver") không?

Từ JDBC 4.0, driver có thể được phát hiện qua service-provider mechanism. Với driver JDBC hiện đại được đóng gói đúng và có trên classpath/module path phù hợp, thường **không cần** tự `Class.forName(...)` trong từng method.

Dù vậy, một số môi trường/module/classloader đặc biệt cần cấu hình khác. Cần kiểm tra vendor documentation và deployment, thay vì tuyên bố mọi ứng dụng đều phải/không bao giờ được gọi `Class.forName`.

### 8.4. Driver không đi kèm mọi database trong JDK

JDK có các interface `java.sql` và `javax.sql`; nó **không đồng nghĩa đã đi kèm driver cho PostgreSQL, Oracle hay SQL Server**. Dự án phải khai báo dependency driver phù hợp, cấu hình JDBC URL/credentials và có database thật để chạy integration test.

Không bịa rằng chỉ với `javac App.java` là một CRUD JDBC có thể kết nối bất kỳ DB server nào.

## 9. PreparedStatement, parameter binding và SQL injection

`PreparedStatement` đã có từ lâu trước JDBC 4.2 nhưng **vẫn là nền tảng bảo mật quan trọng**.

~~~java
String sql =
    "SELECT email FROM users WHERE username = ?";

try (PreparedStatement ps = con.prepareStatement(sql)) {
    ps.setString(1, username);

    try (ResultSet rs = ps.executeQuery()) {
        while (rs.next()) {
            String email = rs.getString("email");
        }
    }
}
~~~

Đây là minh họa; `con` và `username` do ứng dụng cung cấp. Tham số `?` là **giá trị** được driver bind, giúp tránh ghép text input vào cú pháp SQL.

### 9.1. Không nối chuỗi input vào SQL

~~~java
// PHẢN VÍ DỤ:
String sql =
    "SELECT * FROM users WHERE name = '" + input + "'";
~~~

Đây là lỗi SQL injection có thể xảy ra nếu `input` từ người dùng. Dùng `PreparedStatement` với `?` thay vì tự escape dấu nháy. PreparedStatement còn giúp biểu diễn kiểu dữ liệu và tránh một số lỗi quoting/locale.

### 9.2. Placeholder không dùng cho tên bảng/cột

~~~java
// Sai ý định: '?' không đại diện cho SQL identifier.
// SELECT ? FROM users
~~~

Nếu ứng dụng cho phép chọn cột sắp xếp, phải dùng **allowlist** tên cột/tên bảng được server định nghĩa và tạo SQL từ những identifiers đã được kiểm soát. Không truyền arbitrary SQL fragments từ request để nối vào ORDER BY hoặc WHERE.

### 9.3. setObject nên có target SQL type rõ khi cần

`PreparedStatement.setObject(index, value)` có thể được driver chuyển đổi tự động theo mapping chuẩn. Nhưng với `NULL`, vendor-specific types và các cột time zone, nên xem xét `setNull`/`setObject(index, value, targetType)` và kiểm thử mapping cụ thể.

Nếu cột là `DECIMAL`/`NUMERIC` dùng cho số tiền, ưu tiên `BigDecimal` với scale/rounding policy nghiệp vụ, không tự chuyển bằng `double` rồi mong có độ chính xác thập phân tuyệt đối.

## 10. try-with-resources: có từ JDBC 4.1, vẫn cần trong JDBC 4.2+

`Connection`, `Statement` và `ResultSet` triển khai `AutoCloseable`, giúp code quản lý tài nguyên bằng `try-with-resources`.

~~~java
try (Connection con = dataSource.getConnection();
     PreparedStatement ps = con.prepareStatement(
         "SELECT id FROM users WHERE active = ?")) {

    ps.setBoolean(1, true);

    try (ResultSet rs = ps.executeQuery()) {
        while (rs.next()) {
            long id = rs.getLong("id");
            // Xử lý id tại đây.
        }
    }
}
~~~

Ví dụ cần database/schema. Thứ tự đóng resource trong try-with-resources là **ngược thứ tự khai báo**. Chọn phạm vi đủ ngắn để ResultSet và Statement không giữ cursor/connection lâu khi không cần.

**Không bao giờ dựa vào garbage collector để giải phóng connection đúng thời điểm.** Pool và database có hạn mức connection/cursor; rò tài nguyên có thể làm nghẽn dịch vụ ngay cả khi JVM còn nhiều RAM.

### 10.1. SQLException khi đóng tài nguyên

Một tài nguyên có thể ném `SQLException` khi `close`. Với try-with-resources, exception từ close có thể nằm trong **suppressed exceptions** nếu có exception chính trong body. Khi gỡ lỗi, kiểm tra `Throwable.getSuppressed()` bên cạnh `getCause()` thay vì mất thông tin gốc.

### 10.2. Không dùng một Statement và ResultSet cho nhiều thread tùy tiện

JDBC thông thường có stateful cursor, transaction và statement settings. Đừng assume một `ResultSet`/`PreparedStatement` có thể được dùng đồng thời bởi nhiều thread chỉ vì Java object được chia sẻ qua một collection thread-safe. Nếu cần concurrency, cấu trúc nhiều unit of work và checkout connections phù hợp với pool capacity.

## 11. Transaction: hiện hành, nhưng không phải tính năng “mới JDBC 4.2”

Một giao dịch có thể cần **nhiều DML statements cùng commit hoặc rollback**.

~~~java
try (Connection con = dataSource.getConnection()) {
    con.setAutoCommit(false);

    try {
        // Thực hiện các thao tác DML cần atomically.
        doFirstUpdate(con);
        doSecondUpdate(con);
        con.commit();
    } catch (SQLException ex) {
        try {
            con.rollback();
        } catch (SQLException rollbackError) {
            ex.addSuppressed(rollbackError);
        }
        throw ex;
    }
}
~~~

Đây là **mã minh họa**, `doFirstUpdate` và `doSecondUpdate` là hàm ứng dụng đã được định nghĩa riêng. Cần xác định driver/DB hỗ trợ transaction cho loại SQL đang chạy; một số DDL có implicit commit tùy DB.

### 11.1. Auto-commit cần chủ động

`Connection.getAutoCommit()` cho biết mode hiện tại; mặc định một connection mới theo JDBC thường auto-commit, nhưng pool/framework có thể cấu hình. Khi bạn gọi `setAutoCommit(false)`, ứng dụng chịu trách nhiệm commit/rollback. Sau khi trả Connection về pool, cần tin tưởng/bảo đảm pool reset trạng thái theo hợp đồng cấu hình của nó.

**Không đổi autoCommit trong khi một giao dịch đang hoạt động rồi đoán việc đó vô hại.** Đổi auto-commit có thể tác động đến transaction hiện tại; làm theo phạm vi rõ, tránh thay connection state ngoài transaction boundary.

### 11.2. Isolation không có một giá trị đúng cho mọi ứng dụng

Các mức như `TRANSACTION_READ_COMMITTED`, `TRANSACTION_REPEATABLE_READ`, `TRANSACTION_SERIALIZABLE` có semantics và hỗ trợ thực tế phụ thuộc database. Chọn theo nguy cơ dirty/nonrepeatable/phantom reads, anomaly và mục tiêu throughput, không gán “mọi ứng dụng phải SERIALIZABLE”.

Dùng `DatabaseMetaData.supportsTransactionIsolationLevel(level)` để xem driver/database công bố hỗ trợ, rồi kiểm thử các anomaly quan trọng trong DB thật. Một `Connection` có transaction không làm cho side effects ở HTTP/email nằm trong cùng database transaction.

### 11.3. Savepoint và nested behavior

`Connection.setSavepoint`, `rollback(savepoint)` có từ JDBC trước 4.2. Chúng có thể giúp rollback một phần giao dịch nơi DB/driver hỗ trợ. Đừng tự suy mọi `setSavepoint` là một nested transaction độc lập hoặc hoạt động giống nhau ở mọi database.

## 12. SQL NULL và kiểu dữ liệu: điểm hay lỗi ở driver

SQL `NULL` là trạng thái **không có giá trị** trong DB; Java có những phương thức getter trả primitive nên cần kiểm tra thêm.

~~~java
int score = rs.getInt("score");
boolean wasNull = rs.wasNull();

if (wasNull) {
    // SQL NULL, không phải số 0 thật.
}
~~~

Đây là đoạn minh họa trong phạm vi ResultSet. Getter primitive như `getInt` trả 0 nếu SQL NULL, nên `rs.wasNull()` phân biệt `NULL` với 0.

Với reference type:

~~~java
Integer score = rs.getObject("score", Integer.class);
LocalDate date = rs.getObject("planned_date", LocalDate.class);
~~~

Khi mapping được hỗ trợ, giá trị SQL NULL thường trở thành Java `null`. Driver vẫn có thể ném `SQLException` nếu conversion không hỗ trợ; không phải `getObject(..., SomeClass.class)` luôn thành công cho mọi SQL type.

### 12.1. Decimal và float

SQL `DECIMAL(18,2)` thường phù hợp với `BigDecimal`. Test phải kiểm tra scale, rounding, precision và cách driver truyền/đọc, đặc biệt với tiền. Không thay `DECIMAL` bằng `double` chỉ vì code đơn giản hơn.

### 12.2. BLOB/CLOB/SQLXML vẫn có chỗ dùng

`Blob`, `Clob`, `NClob`, `SQLXML`, `Array` và `Struct` đã có lịch sử trước JDBC 4.2. Chúng tiếp tục là API hữu ích nếu schema/driver cần kiểu đặc thù. Nhưng chúng có resource lifecycle và khả năng hỗ trợ phụ thuộc vendor. Không chọn BLOB/CLOB hoặc SQLXML chỉ để chứng minh “dùng JDBC hiện đại”; cân nhắc binary/JSON/native type và streaming khi phù hợp.

## 13. Metadata và cách kiểm tra driver thực tế

Trước khi phụ thuộc `REF_CURSOR`, large updates, `TIME_WITH_TIMEZONE` hoặc một chuyển đổi `java.time`, ứng dụng nên có **bằng chứng** từ metadata, tài liệu vendor và integration tests.

~~~java
try (Connection con = dataSource.getConnection()) {
    DatabaseMetaData meta = con.getMetaData();

    System.out.println("driver=" + meta.getDriverName());
    System.out.println("driverVersion="
        + meta.getDriverVersion());
    System.out.println("jdbcVersion="
        + meta.getJDBCMajorVersion() + "."
        + meta.getJDBCMinorVersion());
    System.out.println("refCursors="
        + meta.supportsRefCursors());
}
~~~

Đây là đoạn minh họa với DataSource có driver và server. Metadata có thể giúp biết version và capability, nhưng **không bảo đảm một conversion cụ thể chạy đúng trên schema cụ thể**. Test tính năng thực với các kiểu cột, null, timezone, precision và các phiên bản driver/database thực tế.

### 13.1. Các dấu hiệu hỗ trợ khác nhau

- **`SQLFeatureNotSupportedException`**: driver không hỗ trợ tính năng (hoặc type/overload) được yêu cầu.
- **`UnsupportedOperationException`**: một số default methods như `executeLargeUpdate` có thể dùng ngoại lệ runtime này.
- **`SQLException` khác**: lỗi schema, quyền, syntax, conversion, network, constraint, deadlock, transaction hoặc vendor state.
- **`BatchUpdateException`**: lỗi batch kèm thông tin kết quả các lệnh trước/sau tùy driver/DB.
- **`SQLTimeoutException`**: driver đã xác định vượt timeout, không có nghĩa mọi thao tác trên server chắc chắn đã bị hủy hoàn toàn.

Không tự thay một trường hợp `UnsupportedOperationException` bằng “driver hỏng hoàn toàn”; có thể chỉ một tính năng mới chưa được triển khai. Với các thao tác có side effect, tuyệt đối **không thử lại ngay sau lỗi nếu chưa hiểu liệu statement đã thực sự được thực hiện hay chưa**.

### 13.2. Không suy capability chỉ từ getJDBCMajorVersion

Một driver có thể công bố JDBC 4.2 nhưng database không hỗ trợ `REF_CURSOR`, `TIME_WITH_TIMEZONE`, một phương pháp streaming hoặc batch lớn. Ngược lại, driver có thể hỗ trợ một tính năng vendor-specific trước khi nó nằm trong mapping chuẩn.

**Kiểm chứng theo ba tầng:** (1) documentation/version support matrix, (2) metadata feature flag nơi có, (3) integration test với driver + database thật.

### 13.3. Đọc SQLState và error code có ích

~~~java
try {
    executeDatabaseOperation();
} catch (SQLException ex) {
    String sqlState = ex.getSQLState();
    int vendorCode = ex.getErrorCode();
    throw ex;
}
~~~

Đây là snippet minh họa, `executeDatabaseOperation` do ứng dụng định nghĩa. Trong thực tế log có request correlation và metadata cần thiết nhưng **không log mật khẩu, private data hoặc raw SQL chứa secret**. SQLState có convention chuẩn nhưng các thông tin chi tiết vẫn vendor-dependent; dùng error classification cẩn thận.

## 14. Timeout và connection pooling: vấn đề runtime hiện đại

Một ứng dụng có thể chạy được JDBC 4.2 về API nhưng vẫn thất bại production vì **pool cạn, câu SQL treo, transaction quá lâu**.

Các loại timeout khác nhau:

| Timeout | Ví dụ cơ chế | Điều gì được giới hạn? |
| --- | --- | --- |
| Lấy Connection từ pool | Cấu hình `connectionTimeout`/acquire timeout của pool | Thời gian chờ checkout connection |
| Login/connect | `DataSource.setLoginTimeout`/driver properties | Thời gian thiết lập kết nối theo implementation |
| Một SQL statement | `Statement.setQueryTimeout(seconds)` | Thời hạn statement do driver quản lý; attempt cancel có thể không phải hard kill |
| I/O trên Connection | `Connection.setNetworkTimeout(executor, milliseconds)` | Giới hạn network operation theo driver semantics |
| Toàn request | Deadline/cancellation ở service/framework | Tổng thời gian nhiều DB + network + xử lý ứng dụng |

**`setNetworkTimeout` và `try-with-resources` xuất hiện từ JDBC 4.1, không phải 4.2**, nhưng vẫn hiện hành. Không dùng một timeout duy nhất rồi tin nó giải quyết hết mọi tình huống hung kết nối.

### 14.1. Statement timeout là best effort theo driver

~~~java
try (PreparedStatement ps = con.prepareStatement(sql)) {
    ps.setQueryTimeout(3);
    try (ResultSet rs = ps.executeQuery()) {
        // ...
    }
}
~~~

Đây là minh họa với `sql` do ứng dụng kiểm soát. `setQueryTimeout` được đo theo giây. Khi timeout, driver có thể **thử hủy** statement; nó không tự bảo đảm transaction đã rollback hoặc server không còn thực thi bất kỳ việc gì. Phải kiểm tra semantics vendor và xử lý connection/transaction sau lỗi.

### 14.2. JDBC là blocking API truyền thống

Các lời gọi `executeQuery`/`executeUpdate` thường **block thread gọi** trong lúc chờ driver/server. Đưa chúng vào `CompletableFuture.supplyAsync(...)` chuyển blocking sang thread khác, **không biến JDBC thành non-blocking driver**. Nếu ứng dụng dùng virtual threads ở JDK mới, chúng có thể phù hợp cho blocking I/O trong một số điều kiện, nhưng **JDBC 4.2 không cam kết mọi driver tối ưu cho virtual threads**.

Không ghép kiến thức Java 21+ vào phần code tự nhận chỉ dùng Java 8; cần ghi rõ mốc phiên bản.

## 15. Batch, generated keys và performance

Batching có thể giảm round trips khi cùng thực hiện nhiều DML statements:

~~~java
try (PreparedStatement ps = con.prepareStatement(
        "INSERT INTO items (item_id, amount) VALUES (?, ?)")) {

    for (Item item : items) {
        ps.setLong(1, item.id());
        ps.setBigDecimal(2, item.amount());
        ps.addBatch();
    }

    int[] counts = ps.executeBatch();
}
~~~

Đây là **pseudocode** dùng kiểu `Item` của ứng dụng và accessor minh họa; `con`/`items` đã có từ ngoài. `addBatch/executeBatch` không mới ở JDBC 4.2. Điểm mới 4.2 là các biến thể **`executeLargeBatch`** trả `long[]` khi cần vùng row count lớn hơn.

### 15.1. Batching không thay thế transaction

Batch API không có nghĩa mỗi lệnh được rollback cùng nhau nếu lỗi. Phải dùng transaction boundary và chính sách xử lý `BatchUpdateException`/partial execution phù hợp với database. Không tự retry toàn batch nếu một số lệnh đã commit; có nguy cơ tạo bản ghi trùng.

### 15.2. Generated keys

~~~java
try (PreparedStatement ps = con.prepareStatement(
        "INSERT INTO orders (amount) VALUES (?)",
        Statement.RETURN_GENERATED_KEYS)) {

    ps.setBigDecimal(1, amount);
    ps.executeUpdate();

    try (ResultSet keys = ps.getGeneratedKeys()) {
        if (keys.next()) {
            long id = keys.getLong(1);
        }
    }
}
~~~

Đây là ví dụ phụ thuộc schema và identity strategy; feature đã có trước JDBC 4.2 nhưng vẫn được dùng. Việc trả key, định dạng và thứ tự trong batch tùy driver. Nếu hệ thống cần nhiều keys, test từng driver thay vì mặc định mỗi INSERT trả đúng một ID theo cùng thứ tự.

### 15.3. Đừng cho rằng PreparedStatement chắc được DB cache

`PreparedStatement` cho phép truy vấn tham số và driver/server có thể tận dụng chuẩn bị/caching. Nhưng policy cache, number of round trips và server-side prepare phụ thuộc driver, connection pool và cấu hình. **Không bảo đảm** mỗi lần tạo PreparedStatement đều được compile một lần vĩnh viễn hay tất cả DB dùng cùng protocol.

## 16. Code Java độc lập: nhận diện chính xác API 4.2 mà không cần database

Ví dụ này không cố kết nối DB, vì JDK không chứa sẵn driver cho mọi database. Nó giúp xác nhận:

- `JDBCType` và `SQLType` có trong Java.
- Enum SQL type khớp các constant `Types`.
- `java.time` có cách biểu diễn ngày/giờ/offset tường minh.
- Những method signatures liên quan JDBC 4.2 hiện diện trên interface Java.
- Sự hiện diện chữ ký **không chứng minh một driver có thực thi được**.

Lưu tên tệp **`Jdbc42ApiDemo.java`**. Đây là một **chương trình Java hoàn chỉnh**, dùng API có từ Java 8 và chạy được với **JDK 17+ mà không cần DB hoặc driver ngoài**.

~~~java
import java.sql.DatabaseMetaData;
import java.sql.JDBCType;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLType;
import java.sql.Statement;
import java.sql.Types;
import java.time.LocalDate;
import java.time.LocalDateTime;
import java.time.LocalTime;
import java.time.OffsetDateTime;
import java.time.ZoneOffset;

public final class Jdbc42ApiDemo {

    private Jdbc42ApiDemo() {
    }

    private static boolean hasMethod(
            Class<?> owner,
            String name,
            Class<?>... parameterTypes) {

        try {
            owner.getMethod(name, parameterTypes);
            return true;
        } catch (NoSuchMethodException ex) {
            return false;
        }
    }

    public static void main(String[] args) {
        SQLType timestamp =
                JDBCType.TIMESTAMP_WITH_TIMEZONE;

        System.out.println("sqlTypeName="
                + timestamp.getName());
        System.out.println("timestampTypeMatches="
                + (timestamp.getVendorTypeNumber()
                    == Types.TIMESTAMP_WITH_TIMEZONE));
        System.out.println("dateTypeMatches="
                + (JDBCType.DATE.getVendorTypeNumber()
                    == Types.DATE));
        System.out.println("refCursorTypeMatches="
                + (JDBCType.REF_CURSOR.getVendorTypeNumber()
                    == Types.REF_CURSOR));

        LocalDate date = LocalDate.of(2024, 2, 29);
        LocalTime time = LocalTime.of(13, 5, 9);
        LocalDateTime localTimestamp =
                LocalDateTime.of(date, time);

        OffsetDateTime offsetTimestamp =
                OffsetDateTime.of(
                    localTimestamp, ZoneOffset.ofHours(7));

        System.out.println("date=" + date);
        System.out.println("time=" + time);
        System.out.println("localTimestamp="
                + localTimestamp);
        System.out.println("offsetTimestamp="
                + offsetTimestamp);
        System.out.println("instant="
                + offsetTimestamp.toInstant());

        // Có API trong JDK != driver thực thi được.
        System.out.println("sqlTypeSetterApi="
                + hasMethod(
                    PreparedStatement.class,
                    "setObject",
                    int.class,
                    Object.class,
                    SQLType.class));

        // getObject(Class<T>) có từ JDBC 4.1;
        // java.time mapping là phần thêm ở JDBC 4.2.
        System.out.println("typedGetObjectApi="
                + hasMethod(
                    ResultSet.class,
                    "getObject",
                    String.class,
                    Class.class));

        System.out.println("largeUpdateApi="
                + hasMethod(
                    Statement.class,
                    "executeLargeUpdate",
                    String.class));

        System.out.println("refCursorMetadataApi="
                + hasMethod(
                    DatabaseMetaData.class,
                    "supportsRefCursors"));

        System.out.println("driverNotRequired=true");
    }
}
~~~

Biên dịch và chạy:

~~~bash
javac -encoding UTF-8 Jdbc42ApiDemo.java
java Jdbc42ApiDemo
~~~

**Đầu ra kỳ vọng:**

~~~text

timestampTypeMatches=true
dateTypeMatches=true
refCursorTypeMatches=true
date=2024-02-29
time=13:05:09
localTimestamp=2024-02-29T13:05:09
offsetTimestamp=2024-02-29T13:05:09+07:00
instant=2024-02-29T06:05:09Z
sqlTypeSetterApi=true
typedGetObjectApi=true
largeUpdateApi=true
refCursorMetadataApi=true
driverNotRequired=true
~~~

### Phân tích từng nhóm kết quả

1. `sqlTypeName` là tên `JDBCType.TIMESTAMP_WITH_TIMEZONE` theo interface `SQLType`.
2. Các dòng `...TypeMatches=true` xác nhận các mã kiểu chuẩn `Types` tương ứng với enum `JDBCType`, không dựa vào một mã số hard-coded.
3. `LocalDate` chứa đúng ngày nhuận 29-02-2024; `LocalTime` là 13:05:09; `LocalDateTime` không kèm offset.
4. `OffsetDateTime` với +07:00 biểu diễn cùng instant là 06:05:09 UTC. Đó là một phép tính trên `java.time`, **không chứng minh driver lưu nguyên offset khi ghi DB**.
5. Reflection kiểm tra đúng các method chữ ký có sẵn trên interface Java; không tạo `Connection`, không truy cập server và không thử conversion.
6. Các kết quả true là **tính sẵn có của API trong JDK**, không phải giấy chứng nhận driver hỗ trợ `REF_CURSOR` hoặc `executeLargeUpdate` runtime.

Vì ví dụ không cần DB, nó có thể được dùng như một bước làm quen trước khi thực hành integration test. Phần tiếp theo trình bày hai đoạn JDBC thật cần DataSource và schema tương thích.

## 17. Ví dụ thực hành có database: Date/Time và PreparedStatement

Phần này là **mã biên dịch được khi được đặt trong class có imports phù hợp**, nhưng **không chạy độc lập nếu chưa có driver, database, schema và DataSource**. Cột/tên bảng chỉ là ví dụ, không phải SQL chuẩn tương thích mọi vendor.

~~~java
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;
import java.time.LocalDate;
import javax.sql.DataSource;

public final class Jdbc42BookingRepository {

    private final DataSource dataSource;

    public Jdbc42BookingRepository(DataSource dataSource) {
        this.dataSource = dataSource;
    }

    public void saveDate(long id, LocalDate date)
            throws SQLException {

        String sql =
            "INSERT INTO bookings (id, booked_date) VALUES (?, ?)";

        try (Connection con = dataSource.getConnection();
             PreparedStatement ps = con.prepareStatement(sql)) {

            ps.setLong(1, id);
            ps.setObject(2, date);
            ps.executeUpdate();
        }
    }

    public LocalDate findDate(long id) throws SQLException {
        String sql =
            "SELECT booked_date FROM bookings WHERE id = ?";

        try (Connection con = dataSource.getConnection();
             PreparedStatement ps = con.prepareStatement(sql)) {

            ps.setLong(1, id);

            try (ResultSet rs = ps.executeQuery()) {
                if (!rs.next()) {
                    return null;
                }
                return rs.getObject(
                    "booked_date", LocalDate.class);
            }
        }
    }
}
~~~

### Lược đồ giả định

~~~sql
CREATE TABLE bookings (
    id BIGINT PRIMARY KEY,
    booked_date DATE
);
~~~

Đây là schema **minh họa**; cú pháp identity/auto-increment, reserved words, transaction và privilege có thể thay đổi theo DB. Đoạn code không cần một API Java mới hơn Java 8, nhưng **yêu cầu driver triển khai LocalDate mapping**.

### Bốn điều cần kiểm chứng bằng integration test

1. Lưu `LocalDate.of(2024,2,29)` rồi đọc lại đúng cùng ngày.
2. Cột SQL NULL: phương thức `getObject(..., LocalDate.class)` có thể trả null theo dữ liệu, logic domain cần xử lý.
3. Điều gì xảy ra khi driver không hỗ trợ mapping hoặc schema là `TIMESTAMP` thay vì `DATE`.
4. Connection được checkout/close đúng qua DataSource, không rò resources nếu query ném SQLException.

**Không tự thay `LocalDate` bằng `OffsetDateTime` chỉ vì đều thuộc java.time**. SQL type phải phù hợp ngữ nghĩa ngày/giờ.

## 18. Ví dụ thực hành: giao dịch hai cập nhật, rollback an toàn

Một use case thực tế không chỉ cần mapping mà còn cần **transaction correctness**:

~~~java
import java.math.BigDecimal;
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.SQLException;
import javax.sql.DataSource;

public final class JdbcTransferExample {

    public static void transfer(
            DataSource dataSource,
            long fromId,
            long toId,
            BigDecimal amount) throws SQLException {

        String sql =
            "UPDATE accounts SET balance = balance + ? "
          + "WHERE account_id = ?";

        try (Connection con = dataSource.getConnection()) {
            con.setAutoCommit(false);

            try (PreparedStatement ps =
                    con.prepareStatement(sql)) {

                ps.setBigDecimal(1, amount.negate());
                ps.setLong(2, fromId);
                if (ps.executeUpdate() != 1) {
                    throw new SQLException(
                        "Source account not found");
                }

                ps.setBigDecimal(1, amount);
                ps.setLong(2, toId);
                if (ps.executeUpdate() != 1) {
                    throw new SQLException(
                        "Destination account not found");
                }

                con.commit();
            } catch (SQLException ex) {
                try {
                    con.rollback();
                } catch (SQLException rollbackError) {
                    ex.addSuppressed(rollbackError);
                }
                throw ex;
            }
        }
    }
}
~~~

Đây là **mã minh họa kỹ thuật transaction**. Nó có thể biên dịch trên Java 8 nhưng **không phải implementation chuyển tiền production hoàn chỉnh**: chưa kiểm tra amount dương, khác tài khoản, số dư đủ, double-spend, concurrent transaction anomalies, idempotency, audit, journal/ledger hoặc ordering để tránh deadlock. DB phải có transaction support và schema accounts tương ứng.

**Điểm JDBC vẫn hiện hành:** prepared statements, try-with-resources, commit/rollback và SQLException suppression. Chúng không phải API mới của JDBC 4.2, nhưng là phần **bắt buộc để dùng JDBC 4.2 đúng trong ứng dụng thật**.

## 19. Driver hiện đại: ma trận kiểm thử cần thiết

Chỉ ghi version driver vào dependency là chưa đủ. Một ma trận kiểm thử tương thích có thể gồm:

| Nhóm test | Test cụ thể | Lý do |
| --- | --- | --- |
| Kết nối | Connect, close, pool checkout, invalid credentials | Xác nhận driver/server/protocol |
| Prepared values | String, long, BigDecimal, NULL | Kiểm tra SQL type mapping và precision |
| java.time | LocalDate/LocalTime/LocalDateTime round-trip | Xác nhận phần phổ biến của JDBC 4.2 |
| Offset time | OffsetTime/OffsetDateTime nếu DB hỗ trợ | Xác nhận kiểu SQL, zone/offset normalization |
| SQLType overload | `setObject(..., JDBCType.DATE)` | Phát hiện driver còn default implementation |
| REF_CURSOR | Metadata support và stored procedure test | Tính năng optional, vendor-specific |
| Large updates | `executeLargeUpdate/executeLargeBatch` | API tồn tại nhưng implementation có thể thiếu |
| Transactions | Commit, rollback, constraint violation | Tránh partial writes |
| Batch | Partial failure, generated keys, counts | Driver-specific batch behavior |
| Timeouts | Query timeout, network disconnect | Kiểm tra cancellation và recovery |
| Resource lifecycle | Statement/ResultSet/Connection close | Tránh pool exhaustion |
| Security | Parameter binding, least privilege, TLS | Tránh SQL injection và rò secrets |

### 19.1. Phải test dưới schema và timezone giống production

Một test dùng cột DATE có thể thành công nhưng production dùng `TIMESTAMP WITH TIME ZONE` hoặc cột vendor `DATETIME` lại gặp khác biệt. Cũng tương tự, mapping được driver hỗ trợ trên server version mới có thể không tồn tại trên server version cũ.

Test thêm:
- Ngày nhuận và giao thừa.
- DST gap/overlap nếu ứng dụng có zone ID.
- Offset khác UTC.
- Fractional seconds khác 0.
- SQL NULL và giá trị ranh giới.
- Precision DECIMAL và dữ liệu Unicode.
- Bảng/transaction có khóa cạnh tranh, error code và retry policy.

### 19.2. Kiểm thử driver nâng cấp

Khi nâng major driver/JDK:
1. Đọc release notes và compatibility matrix.
2. Kiểm tra supported Java version/database server version.
3. Chạy integration tests trên môi trường tương đương production.
4. So sánh java.time/offset/precision behavior.
5. Kiểm tra performance, connection pooling và TLS configuration.
6. Test lại exception classification, statement timeout, batch behavior.
7. Có rollback plan và quan sát lỗi sau deployment.

Không tuyên bố driver mới luôn giữ nguyên mọi vendor-specific behavior dù interface JDBC vẫn tương thích.

## 20. Các lỗi phổ biến khi học và dùng JDBC 4.2

### Lỗi 1 — Cho rằng JDBC 4.2 đã obsolete vì Java SE 26 mô tả JDBC 4.5

Sai. API JDBC hiện hành **kế thừa** 4.2. Những kiểu `SQLType`/`JDBCType`, java.time mapping và các interface `java.sql` tiếp tục được dùng.

### Lỗi 2 — Cho rằng chỉ cần JDK mới là có database driver

JDK chứa API; driver vendor phải được cấu hình phù hợp. Một chương trình compile thành công có thể fail vì thiếu driver/classpath, JDBC URL sai hoặc server không truy cập được.

### Lỗi 3 — Gán mọi API đang dùng cho JDBC 4.2

`PreparedStatement`, `DataSource`, `ResultSet`, `try-with-resources` đã có trước. Tính năng **mới trong 4.2** cần ghi rõ để hiểu cách tiến hóa API.

### Lỗi 4 — Dùng getObject(index, LocalDate.class) mà không kiểm tra schema/driver

Cú pháp typed `getObject` đã có từ JDBC 4.1; JDBC 4.2 cung cấp java.time mappings. Nếu column type hoặc driver không hỗ trợ conversion, có thể ném SQLException.

### Lỗi 5 — Giả định Instant/ZonedDateTime là mapping JDBC 4.2 chuẩn ở mọi database

Không nên. Mappings chuẩn trọng tâm gồm LocalDate, LocalTime, LocalDateTime, OffsetTime, OffsetDateTime. Hỗ trợ Instant/ZonedDateTime là câu chuyện driver/vendor-specific; nếu cần instant, cân nhắc `OffsetDateTime.toInstant()` với cột/time policy phù hợp.

### Lỗi 6 — Mặc định TIMESTAMP luôn là thời điểm UTC

`TIMESTAMP WITHOUT TIME ZONE` chứa local date-time, không tự xác định một instant. Chỉ dùng UTC khi schema và business contract quy định; cẩn thận chuyển sang Instant.

### Lỗi 7 — Nghĩ TIMESTAMP WITH TIME ZONE giữ tên zone ID

Nhiều DB lưu instant được chuẩn hóa và có thể trả offset UTC. Nếu cần zone ID, lưu/tái tạo từ thông tin riêng.

### Lỗi 8 — Dùng overload SQLType rồi bỏ qua khả năng not supported

Interface default method có thể ném `SQLFeatureNotSupportedException`. Kiểm thử driver hoặc chọn API tương đương được nhà cung cấp hỗ trợ, không để lỗi xuất hiện bất ngờ trên production.

### Lỗi 9 — Dùng REF_CURSOR với mọi stored procedure

Không phải DB nào cũng có kiểu OUT REF_CURSOR. Kiểm tra `supportsRefCursors` và đặc tả procedure; dùng truy vấn `SELECT` thông thường khi phù hợp.

### Lỗi 10 — Cho rằng executeLargeUpdate là một thuật toán DML nhanh hơn

Chữ Large nói về **long row count**. Performance vẫn phụ thuộc SQL plan, index, isolation, server, network và transaction.

### Lỗi 11 — Bỏ qua BatchUpdateException và partial execution

Các statement trong batch có thể đã thực thi một phần. Không auto retry toàn bộ batch mà không xét trạng thái commit và idempotency.

### Lỗi 12 — Dùng getInt cho nullable column và nhầm SQL NULL thành số 0

Sau `getInt` cần `wasNull`, hoặc dùng `getObject(..., Integer.class)` nơi mapping được hỗ trợ và xử lý null.

### Lỗi 13 — Chỉ dùng JDBCType để suy DB có kiểu mới

`JDBCType.TIME_WITH_TIMEZONE` tồn tại trong enum Java nhưng database server có thể không có SQL type tương ứng hoặc driver không hỗ trợ.

### Lỗi 14 — Nối chuỗi input vào SQL

Dùng prepared parameters cho **giá trị**. Với identifiers động, dùng allowlist để tránh SQL injection.

### Lỗi 15 — Quên đóng ResultSet, Statement hoặc Connection

JDBC resources không nên phụ thuộc GC. Dùng try-with-resources và xác nhận connection được trả về pool.

### Lỗi 16 — Dùng một Connection trên nhiều thread không có thiết kế concurrency

Connection chứa state transaction/cursor. Không tự coi nó là thread-safe chỉ vì driver chạy đa luồng. Mỗi unit of work nên checkout connection riêng theo pool.

### Lỗi 17 — Không commit hoặc rollback khi tắt autoCommit

Nếu một exception xảy ra giữa hai updates, phải rollback. Đừng bắt SQLException rồi coi transaction đã được dọn chính xác mà không quan sát failure.

### Lỗi 18 — Cho rằng JDBC 4.2 là non-blocking

JDBC API truyền thống là blocking; việc dùng CompletableFuture/virtual threads không đổi semantics của driver một cách kỳ diệu. Cần tính pool/thread/cancellation đúng.

### Lỗi 19 — Không phân biệt query timeout với network timeout/pool timeout

Mỗi cơ chế giới hạn một phạm vi khác nhau và có thể do driver/framework thực thi khác nhau. Test outage thật, không suy từ một method setTimeout thành độ bền tuyệt đối.

### Lỗi 20 — Đưa exception raw vào log chứa thông tin nhạy cảm

Một số driver có thể đưa SQL, parameter value hoặc connection details trong message. Log có redaction và correlation; không lộ password, token, key hay PII.

### Lỗi 21 — Test date-time chỉ ở UTC và không test precision

Ngay cả driver hiện đại có thể khác về normalization, DST và fractional seconds. Test với schema, session time zone, precision và driver thực tế.

### Lỗi 22 — Dùng driver quá cũ vì “bài học là JDBC 4.2”

Dùng JDBC 4.2 **không đòi** cài driver phát hành đúng thời Java 8. Nên dùng phiên bản driver đang được vendor hỗ trợ và vá bảo mật tương thích với JDK/database của bạn.

- [ ] Có kiểm tra rằng các API mới sau Java 8 không bị gán nhầm là JDBC 4.2?

**Ghi nhớ:** JDBC 4.2 tiếp tục là **nền tảng tương thích** của JDBC hiện đại. Học đúng trọng tâm là biết những bổ sung 4.2 — **`SQLType` / `JDBCType`, mappings `java.time`, `REF_CURSOR`, large update counts, `DriverAction`** — và dùng chúng cùng các thực hành bền vững đã có từ trước: **`DataSource`, `PreparedStatement`, `ResultSet`, try-with-resources, transaction, error handling và integration testing**. Khi dùng driver mới, **tin hợp đồng API cộng bằng chứng từ driver/database thực tế**, không tin vào tên phiên bản hay một lời gọi compile thành công.
