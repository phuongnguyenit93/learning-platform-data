# setObject, updateObject với SQLType trong JDBC 4.2

## 1. Mục tiêu của bài học

JDBC 4.2, đi kèm Java 8, bổ sung cách chỉ định kiểu SQL bằng đối tượng `java.sql.SQLType` thay vì chỉ dùng mã số nguyên `java.sql.Types`. Hai nhóm API cần phân biệt là:

- **`PreparedStatement.setObject(..., SQLType, ...)`**: gán giá trị Java cho tham số `?` trước khi thực thi câu SQL.
- **`ResultSet.updateObject(..., SQLType, ...)`**: gán giá trị mới cho cột của một hàng trên **ResultSet có thể cập nhật**; cần `updateRow()` hoặc `insertRow()` để gửi thay đổi vào cơ sở dữ liệu.

`SQLType` là kiểu chỉ định **kiểu SQL đích**. `JDBCType` là enum chuẩn triển khai interface ấy, với các hằng quen thuộc như `INTEGER`, `VARCHAR`, `DECIMAL`, `DATE`, `TIMESTAMP` và `TIMESTAMP_WITH_TIMEZONE`.

Hai điểm phải biết trước khi lập trình:

1. **Không phải mọi driver đều triển khai các overload nhận `SQLType`.** Javadoc quy định những default method này ném `SQLFeatureNotSupportedException`; muốn chạy thật phải dùng driver đã hỗ trợ. API tồn tại trong JDK không đồng nghĩa driver đã triển khai.
2. **`ResultSet.updateObject` không tự ghi xuống database.** Phương thức chỉ cập nhật giá trị cột trong hàng đang thao tác của result set; cần `updateRow()` hoặc `insertRow()`, sau đó xét transaction `commit/rollback` nếu tắt auto-commit.

Bài trình bày Java 8/JDBC 4.2 và kiến thức **vẫn còn áp dụng trong JDK hiện đại**, không lấy các kỹ thuật đã lỗi thời/legacy làm khuyến nghị. Ví dụ runnable dùng API Java 17+ và được kiểm thử bằng JDK 21. Các chương trình dùng mock được **ghi rõ là mock**; khi cần JDBC driver, schema và database thực, mã tích hợp được dán nhãn riêng.

## 2. `SQLType` là gì và liên quan `JDBCType` ra sao?

`SQLType` là một interface trong package `java.sql`, bổ sung từ Java 8. Nó đại diện cho mã định danh một SQL type, thuộc loại JDBC chung hoặc loại riêng của nhà cung cấp database.

Interface có ba phương thức:

```java
// Chữ ký của interface SQLType:
String getName();
String getVendor();
Integer getVendorTypeNumber();
```

Ý nghĩa:

- `getName()`: tên kiểu SQL, ví dụ `"DECIMAL"`.
- `getVendor()`: tên vendor, ví dụ `"java.sql"` đối với các type JDBC chuẩn.
- `getVendorTypeNumber()`: mã type theo vendor dưới dạng `Integer`; với `JDBCType` chuẩn, nó trùng với hằng tương ứng trong `java.sql.Types`.

`java.sql.JDBCType` là enum triển khai `SQLType`:

```java
import java.sql.JDBCType;
import java.sql.SQLType;
import java.sql.Types;

// Đoạn minh họa:
SQLType target = JDBCType.DECIMAL;

System.out.println(target.getName());             // DECIMAL
System.out.println(target.getVendor());           // java.sql
System.out.println(target.getVendorTypeNumber()); // 3
System.out.println(Types.DECIMAL);                 // 3
```

Không nhầm:

| Đối tượng | Ví dụ | Dùng để làm gì? |
| --- | --- | --- |
| `Types` | `Types.DECIMAL` | Mã số `int` của JDBC type |
| `SQLType` | Một object triển khai interface | Mô tả SQL type theo chuẩn/vendor |
| `JDBCType` | `JDBCType.DECIMAL` | Enum type chuẩn, cũng là `SQLType` |
| Java value | `new BigDecimal("12.34")` | Giá trị cần chuyển sang kiểu SQL đích |
| SQL column | `DECIMAL(12,2)` | Kiểu và ràng buộc thực sự trong schema DB |

**`JDBCType.DECIMAL` không tự tạo cột `DECIMAL(12,2)`.** Precision/scale của cột là việc của schema; `setObject` chỉ chọn conversion đích cho giá trị được bind.

### 2.1. Vì sao thêm SQLType khi đã có Types?

Trước JDBC 4.2, những overload cũ nhận `int targetSqlType`:

```java
// API cũ theo kiểu int, vẫn hợp lệ và còn sử dụng:
ps.setObject(1, new BigDecimal("12.34"), Types.DECIMAL);
```

JDBC 4.2 đưa thêm overload kiểu rõ nghĩa hơn:

```java
// API JDBC 4.2, Java 8+:
ps.setObject(1, new BigDecimal("12.34"), JDBCType.DECIMAL);
```

Ưu điểm là giá trị type có tên, có interface vendor và giảm nhầm giữa mã số nguyên ứng dụng với mã type. Nhưng **khả năng chạy thực tế** vẫn phụ thuộc JDBC driver. Các overload `int` và `SQLType` vẫn cùng tồn tại; sử dụng overload cũ không đồng nghĩa “lỗi thời” nếu đó là đường API driver hỗ trợ.

### 2.2. SQLType không phải Java class của dữ liệu

Đừng nhầm `JDBCType.DATE` là `LocalDate.class` hoặc `JDBCType.VARCHAR` là `String.class`. Một cái là **kiểu dữ liệu của phía database**, cái kia là **kiểu của object Java**. Driver cần mapping/conversion giữa hai bên.

## 4. Bốn overload setObject của PreparedStatement

Hai overload cũ nhận `int`:

```java
void setObject(int parameterIndex,
               Object x, int targetSqlType);

void setObject(int parameterIndex,
               Object x, int targetSqlType,
               int scaleOrLength);
```

Hai overload mới từ JDBC 4.2 nhận `SQLType`:

```java
default void setObject(int parameterIndex,
                       Object x,
                       SQLType targetSqlType);

default void setObject(int parameterIndex,
                       Object x,
                       SQLType targetSqlType,
                       int scaleOrLength);
```

Ví dụ bind vào `PreparedStatement`:

```java
// Đoạn minh họa bên trong try (PreparedStatement ps = ...).
ps.setObject(1, 17, JDBCType.INTEGER);
ps.setObject(2, "ACTIVE", JDBCType.VARCHAR);
ps.setObject(3, new BigDecimal("12.34"),
             JDBCType.DECIMAL, 2);
ps.setObject(4, LocalDate.of(2024, 2, 29),
             JDBCType.DATE);
```

Ở đây:

- `parameterIndex` **đếm từ 1**, không phải từ 0.
- `x` là object Java mang giá trị.
- `targetSqlType` là kiểu SQL đích.
- `scaleOrLength` dùng cho một số trường hợp đặc biệt, như `DECIMAL/NUMERIC` và streams.
- Lệnh `setObject` chỉ **gán tham số**, không tự gọi `executeUpdate`/`executeQuery` và không tự commit transaction.

### 4.1. Khi nào dùng overload không có SQLType?

`ps.setObject(index, value)` để driver suy kiểu đích theo mapping chuẩn và thông tin cột, tùy driver. Nó có thể phù hợp với giá trị rõ nghĩa nhưng dễ gặp ambiguity, chẳng hạn object có thể map theo nhiều SQL type hoặc null chưa có type. Khi cần rõ ràng, truyền `SQLType` hoặc dùng setter chuyên biệt `setInt`, `setString`, `setDate`, `setBigDecimal`.

**Đừng tự giả định một setter “đúng nhất” cho mọi driver.** Hợp đồng API, metadata của cột, driver và schema quyết định conversion được hỗ trợ.

## 5. scaleOrLength: ý nghĩa phụ thuộc giá trị/type

Tham số cuối của overload bốn đối số **không phải precision của cột** và không có nghĩa chung là “số ký tự tối đa”.

Theo Javadoc của `PreparedStatement.setObject(..., SQLType, int)`:

- Với `JDBCType.DECIMAL` hoặc `JDBCType.NUMERIC`: `scaleOrLength` là **số chữ số sau dấu thập phân** (*scale*).
- Với giá trị `InputStream`: số **byte** của stream dự kiến.
- Với giá trị `Reader`: số **ký tự** của reader dự kiến.
- Với các loại Java object khác, tham số này được bỏ qua theo contract.

Ví dụ:

```java
// Đoạn minh họa, JDBC driver phải hỗ trợ overload.
BigDecimal amount = new BigDecimal("123.45");
ps.setObject(1, amount, JDBCType.DECIMAL, 2);
```

Không có scale argument thì Javadoc nói overload ba đối số tương đương với **scale bằng 0**. Vì vậy với tiền có số lẻ, hãy chọn overload scale rõ ràng hoặc API `setBigDecimal` thích hợp, rồi kiểm tra database thực sự lưu độ chính xác cần thiết.

**Chú ý:** scale trong lời gọi không thay thế precision/scale của SQL column. Driver có thể chuyển đổi, làm tròn hoặc báo lỗi tùy cột, DB và cấu hình. Với số tiền, ứng dụng nên kiểm tra scale và chính sách làm tròn trước; không dựa vào implicit conversion để âm thầm thay đổi số tiền.

### 5.1. Phân biệt precision và scale

Ví dụ SQL `DECIMAL(10,2)` thường có precision 10 chữ số tổng cộng, scale 2 chữ số thập phân. Nhưng `setObject(..., DECIMAL, 2)` chỉ chuyển tham số **scale=2** cho conversion; nó không khai báo cột `DECIMAL(10,2)`.

Nếu business yêu cầu chính xác hai chữ số, có thể chuẩn hóa `BigDecimal` theo quy tắc xác định:

```java
// Đoạn minh họa, java.math:
BigDecimal approved = raw.setScale(
    2, RoundingMode.HALF_UP
);
// Hoặc dùng UNNECESSARY nếu tuyệt đối không được làm tròn.
```

### 5.2. Ví dụ 2 — kiểm tra scale ở Java trước khi bind

**SQLTypeScaleDemo.java**:

```java
import java.math.BigDecimal;
import java.math.RoundingMode;

public class SQLTypeScaleDemo {
    public static void main(String[] args) {
        BigDecimal raw =
            new BigDecimal("123.456");

        BigDecimal approved = raw.setScale(
            2, RoundingMode.HALF_UP
        );

        System.out.println("raw=" + raw);
        System.out.println(
            "rawScale=" + raw.scale()
        );
        System.out.println(
            "approved=" + approved
        );
        System.out.println(
            "approvedScale=" + approved.scale()
        );
        System.out.println(
            "approvedPrecision=" +
            approved.precision()
        );

        try {
            raw.setScale(
                2, RoundingMode.UNNECESSARY
            );
        } catch (ArithmeticException ex) {
            System.out.println(
                "exactScale=REJECTED"
            );
        }
    }
}
```

```bash
javac SQLTypeScaleDemo.java
java SQLTypeScaleDemo
```

Stdout:

```text
raw=123.456
rawScale=3
approved=123.46
approvedScale=2
approvedPrecision=5
exactScale=REJECTED
```

`BigDecimal` đầu vào được tạo từ chuỗi để tránh sai số nhị phân thường gặp khi khởi tạo từ `double`. `UNNECESSARY` từ chối khi cần làm tròn; lựa chọn chính sách phải được xác định theo nghiệp vụ.

## 6. Ví dụ 3 — kiểm tra chữ ký overload JDBC 4.2 bằng reflection

Các overload `SQLType` là **default methods** của interface, khác với việc JDK tự cung cấp triển khai database thực.

Tạo **SQLTypeOverloadDemo.java**:

```java
import java.lang.reflect.Method;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLType;

public class SQLTypeOverloadDemo {
    public static void main(String[] args)
            throws Exception {
        Method ps3 =
            PreparedStatement.class.getMethod(
                "setObject",
                int.class,
                Object.class,
                SQLType.class
            );

        Method ps4 =
            PreparedStatement.class.getMethod(
                "setObject",
                int.class,
                Object.class,
                SQLType.class,
                int.class
            );

        Method rs3 =
            ResultSet.class.getMethod(
                "updateObject",
                String.class,
                Object.class,
                SQLType.class
            );

        Method rs4 =
            ResultSet.class.getMethod(
                "updateObject",
                int.class,
                Object.class,
                SQLType.class,
                int.class
            );

        System.out.println(
            "ps3=" + ps3.isDefault()
        );
        System.out.println(
            "ps4=" + ps4.isDefault()
        );
        System.out.println(
            "rs3=" + rs3.isDefault()
        );
        System.out.println(
            "rs4=" + rs4.isDefault()
        );
        System.out.println(
            "psReturn=" +
            ps3.getReturnType().getSimpleName()
        );
    }
}
```

```bash
javac SQLTypeOverloadDemo.java
java SQLTypeOverloadDemo
```

Stdout:

```text
ps3=true
ps4=true
rs3=true
rs4=true
psReturn=void
```

**Tại sao quan trọng?** Một JDBC driver có thể được biên dịch với interface chứa default method nhưng chưa override chúng để hỗ trợ conversion mới. Mặc định theo Javadoc, các method này có thể ném `SQLFeatureNotSupportedException`. Đừng dùng reflection thấy chữ ký tồn tại rồi kết luận driver chạy được.

## 7. setObject với null: chỉ định kiểu SQL đích rõ ràng

Trong SQL, `NULL` không có một kiểu Java riêng để suy ra. Nếu cột có thể null, giá trị Java có thể được bind bằng:

```java
// Đoạn minh họa nếu driver hỗ trợ SQLType overload.
ps.setObject(1, null, JDBCType.VARCHAR);
ps.setObject(2, null, JDBCType.DATE);
```

Với driver không hỗ trợ overload `SQLType`, có thể sử dụng API `setNull` lâu đời và vẫn hiện hành:

```java
ps.setNull(1, Types.VARCHAR);
ps.setNull(2, Types.DATE);
```

**Không truyền `JDBCType.NULL` chỉ vì value là null.** `targetSqlType` thường cần phản ánh **kiểu cột đích thực sự** (DATE/VARCHAR/DECIMAL...), không phải một kiểu “giá trị Java null”. Với SQL UDT/vendor type, việc bind null có thể đòi cách xử lý đặc thù của driver.

Khi đọc kết quả, `ResultSet.getObject(column, LocalDate.class)` có thể trả `null` cho SQL NULL (nếu conversion được hỗ trợ); với `getInt`/`getBoolean` các primitive getter, cần `wasNull()` để phân biệt SQL NULL với giá trị mặc định 0/false. Nên thiết kế mapping null theo model nghiệp vụ thay vì đổi mọi null thành giá trị số 0.

## 8. Ánh xạ java.time của JDBC 4.2

JDBC 4.2 tích hợp các kiểu ngày giờ `java.time`, giúp tránh nhầm lẫn giữa local date/time và instant có offset. Những cặp chuẩn cần nhớ:

| Java object | JDBCType thường tương ứng | Ý nghĩa |
| --- | --- | --- |
| `LocalDate` | `DATE` | Ngày theo lịch, không có time/zone |
| `LocalTime` | `TIME` | Giờ địa phương, không có zone |
| `LocalDateTime` | `TIMESTAMP` | Ngày giờ địa phương, không có offset |
| `OffsetTime` | `TIME_WITH_TIMEZONE` | Giờ có UTC offset |
| `OffsetDateTime` | `TIMESTAMP_WITH_TIMEZONE` | Ngày giờ có UTC offset |

Ví dụ:

```java
// Đoạn minh họa, driver/schema phải hỗ trợ.
ps.setObject(
    1, LocalDate.of(2024, 2, 29),
    JDBCType.DATE
);

ps.setObject(
    2, LocalDateTime.of(2024, 2, 29, 14, 5),
    JDBCType.TIMESTAMP
);

ps.setObject(
    3, OffsetDateTime.parse(
        "2024-08-15T10:30:00+07:00"
    ),
    JDBCType.TIMESTAMP_WITH_TIMEZONE
);
```

**Cần phân biệt semantics:**

- `LocalDateTime` không xác định một instant duy nhất khi chưa có múi giờ/offset.
- `OffsetDateTime` xác định được instant, nhưng SQL database/driver có thể **chuẩn hóa offset** hoặc biểu diễn khác khi lưu/trả. Cần test round-trip và so sánh instant nếu nghiệp vụ coi đó là mốc thời gian.
- `ZonedDateTime` mang vùng quy tắc thời gian như `Europe/Paris`; `Instant` là mốc timeline. JDBC 4.2 không yêu cầu driver hỗ trợ trực tiếp mọi kiểu `java.time`. Không mặc định truyền `Instant`/`ZonedDateTime` bằng `setObject` là portable.
- `TIME_WITH_TIMEZONE`/`TIMESTAMP_WITH_TIMEZONE` có trong `JDBCType` không đồng nghĩa tất cả DB engines hỗ trợ native SQL type này giống nhau.

```java
        System.out.println(
```

## 9. Ví dụ 5 — mô phỏng PreparedStatement.setObject bằng JDBC mock

Để kiểm thử Java API ngay cả khi máy chưa có driver hoặc database, có thể tạo một `PreparedStatement` giả bằng `java.lang.reflect.Proxy`. Nó ghi nhận lời gọi thay vì gửi dữ liệu đến DB.

Tạo **MockBindingDemo.java**:

```java
import java.lang.reflect.Proxy;
import java.math.BigDecimal;
import java.sql.JDBCType;
import java.sql.PreparedStatement;
import java.sql.SQLType;
import java.time.LocalDate;
import java.util.Set;
import java.util.TreeSet;

public class MockBindingDemo {
    public static void main(String[] args)
            throws Exception {
        Set<Integer> indices = new TreeSet<>();

        PreparedStatement ps = (PreparedStatement)
            Proxy.newProxyInstance(
                PreparedStatement.class.getClassLoader(),
                new Class<?>[] { PreparedStatement.class },
                (proxy, method, callArgs) -> {
                    if (method.getName().equals(
                            "setObject")) {
                        int index = (Integer) callArgs[0];
                        indices.add(index);

                        Object value = callArgs[1];
                        String display =
                            value == null
                                ? "NULL"
                                : value.toString();

                        String sqlType =
                            ((SQLType) callArgs[2])
                                .getName();

                        String detail =
                            callArgs.length == 4
                                ? " scale=" + callArgs[3]
                                : "";

                        System.out.println(
                            "bind#" + index + "=" +
                            display + " type=" +
                            sqlType + detail
                        );
                        return null;
                    }

                    if (method.getName().equals(
                            "executeUpdate")) {
                        return 1; // Chỉ mô phỏng row count.
                    }

                    throw new UnsupportedOperationException(
                        method.getName()
                    );
                }
            );

        ps.setObject(
            1, LocalDate.of(2024, 2, 29),
            JDBCType.DATE
        );
        ps.setObject(
            2, new BigDecimal("12.34"),
            JDBCType.DECIMAL, 2
        );
        ps.setObject(
            3, null, JDBCType.VARCHAR
        );

        System.out.println(
            "affected=" + ps.executeUpdate()
        );
        System.out.println(
            "boundIndices=" + indices
        );
    }
}
```

## 10. Mã tích hợp thật: PreparedStatement với SQLType

Một ví dụ cho schema giả định:

```sql
-- DDL mang tính minh họa; cú pháp TIMESTAMP WITH TIME ZONE
-- và ID có thể khác giữa các DB engine.
CREATE TABLE purchase_events (
    event_id BIGINT PRIMARY KEY,
    event_date DATE NOT NULL,
    amount DECIMAL(12, 2) NOT NULL,
    occurred_at TIMESTAMP WITH TIME ZONE
);
```

Mã Java sau sử dụng `DriverManager` và `PreparedStatement`. Đây là **mẫu tích hợp**, cần JDBC driver trên classpath/module path, biến môi trường kết nối và schema tồn tại. Không có stdout cố định được khẳng định cho mọi DB.

**JdbcWriteTemplate.java**:

```java
import java.math.BigDecimal;
import java.sql.Connection;
import java.sql.DriverManager;
import java.sql.JDBCType;
import java.sql.PreparedStatement;
import java.sql.SQLException;
import java.time.LocalDate;
import java.time.OffsetDateTime;

public class JdbcWriteTemplate {
    public static void main(String[] args)
            throws SQLException {
        String url = System.getenv("JDBC_URL");
        String user = System.getenv("JDBC_USER");
        String password = System.getenv("JDBC_PASSWORD");

        if (url == null || url.isBlank()) {
            throw new IllegalArgumentException(
                "Missing JDBC_URL"
            );
        }

        try (Connection connection =
                 DriverManager.getConnection(
                     url, user, password
                 )) {
            connection.setAutoCommit(false);

            String sql =
                "INSERT INTO purchase_events " +
                "(event_id, event_date, amount, occurred_at) " +
                "VALUES (?, ?, ?, ?)";

            try (PreparedStatement ps =
                     connection.prepareStatement(sql)) {
                ps.setObject(
                    1, 1001L, JDBCType.BIGINT
                );
                ps.setObject(
                    2, LocalDate.of(2024, 2, 29),
                    JDBCType.DATE
                );
                ps.setObject(
                    3, new BigDecimal("12.34"),
                    JDBCType.DECIMAL, 2
                );
                ps.setObject(
                    4,
                    OffsetDateTime.parse(
                        "2024-08-15T10:30:00+07:00"
                    ),
                    JDBCType.TIMESTAMP_WITH_TIMEZONE
                );

                int affected = ps.executeUpdate();
                if (affected != 1) {
                    throw new SQLException(
                        "Expected exactly one inserted row"
                    );
                }
                connection.commit();
            } catch (SQLException ex) {
                connection.rollback();
                throw ex;
            }
        }
    }
}
```

Chạy chỉ khi đã cài driver và cấu hình DB:

```bash
# Thiết lập JDBC_URL, JDBC_USER, JDBC_PASSWORD theo môi trường.
# Thêm JAR của driver đúng phiên bản vào classpath.
javac JdbcWriteTemplate.java
java -cp ".:<jdbc-driver-jar>" JdbcWriteTemplate
```

Dòng lệnh trên là **mẫu dành cho shell Unix-like**; thay dấu phân cách classpath thành `;` trên Windows và thay `<jdbc-driver-jar>` bằng JAR thật. Nó không phải lệnh có thể chạy nguyên văn khi chưa chuẩn bị driver.

**Cân nhắc production:**

- Đừng ghi password trực tiếp trong source code hoặc log, nên dùng secret manager/cấu hình an toàn.
- Bật transaction boundary rõ; thực tế cần rollback cho cả lỗi runtime theo chính sách ứng dụng, không chỉ `SQLException`.
- Có thể kiểm tra `SQLFeatureNotSupportedException` khi driver chưa hỗ trợ overload `SQLType` hoặc `TIMESTAMP_WITH_TIMEZONE`.
- Trước khi publish vào môi trường thật, test **precision/scale**, null, offset, constraint và row count.
- Nếu chỉ cập nhật một cột, một câu `UPDATE ... WHERE id=?` qua PreparedStatement thường dễ kiểm soát hơn ResultSet updatable.

## 11. ResultSet.updateObject: sửa cột khác với gửi SQL UPDATE

`ResultSet` có các overload mới từ JDBC 4.2:

```java
// Các chữ ký của ResultSet:
default void updateObject(
    int columnIndex,
    Object x,
    SQLType targetSqlType
);

default void updateObject(
    int columnIndex,
    Object x,
    SQLType targetSqlType,
    int scaleOrLength
);

default void updateObject(
    String columnLabel,
    Object x,
    SQLType targetSqlType
);

default void updateObject(
    String columnLabel,
    Object x,
    SQLType targetSqlType,
    int scaleOrLength
);
```

Khác biệt:

- `columnIndex` **đếm từ 1** và chỉ cột trong result set hiện tại.
- `columnLabel` là nhãn cột do `AS` chỉ định hoặc tên cột nếu không dùng alias.
- `x` và `targetSqlType` mang ý nghĩa tương tự `PreparedStatement`.
- `scaleOrLength` có semantics của scale/stream length như Javadoc.
- Phải có `ResultSet` updatable, và driver/statement/SQL query phải hỗ trợ.
- `updateObject(...)` cập nhật buffer của hàng hiện tại hoặc hàng chèn; **không tự cập nhật bảng gốc**.
- Với hàng hiện tại, gọi `updateRow()` để gửi cập nhật.
- Với hàng chèn sau `moveToInsertRow()`, gọi `insertRow()` rồi xử lý cursor theo contract.
- Nếu transaction chưa commit, `updateRow` mới gửi thay đổi trong transaction, **không đồng nghĩa commit**.

### 11.1. Sự khác nhau giữa statement parameter và result-set column

| `PreparedStatement.setObject` | `ResultSet.updateObject` |
| --- | --- |
| `1` là tham số `?` đầu tiên | `1` là cột đầu tiên của result set |
| Binding trước khi execute | Stage giá trị của row/cột hiện tại |
| `executeUpdate/executeQuery` mới chạy SQL | `updateRow/insertRow` mới gửi sửa row |
| Dùng được với `INSERT/UPDATE/SELECT` có parameter | Yêu cầu updatable result set |
| Dễ định nghĩa điều kiện `WHERE`, row count | Tùy khả năng cursor/update của DB driver |
| Transaction commit là bước riêng | Transaction commit cũng là bước riêng |

## 12. ResultSet updatable cần được yêu cầu và kiểm tra

Mẫu code minh họa:

```java
// Đoạn minh họa, connection là JDBC Connection hợp lệ.
String sql =
    "SELECT event_id, amount " +
    "FROM purchase_events WHERE event_id = ?";

try (PreparedStatement ps =
        connection.prepareStatement(
            sql,
            ResultSet.TYPE_FORWARD_ONLY,
            ResultSet.CONCUR_UPDATABLE
        )) {

    ps.setLong(1, 1001L);

    try (ResultSet rs = ps.executeQuery()) {
        if (rs.getConcurrency()
                != ResultSet.CONCUR_UPDATABLE) {
            throw new SQLFeatureNotSupportedException(
                "ResultSet is read-only"
            );
        }

        if (rs.next()) {
            rs.updateObject(
                "amount",
                new BigDecimal("45.67"),
                JDBCType.DECIMAL,
                2
            );
            rs.updateRow();
        }
    }
}
```

**Ràng buộc quan trọng:**

- Không phải query nào cũng updatable. JOIN, aggregate, DISTINCT, alias, key thiếu hoặc cursor type có thể khiến driver/DB từ chối, tùy sản phẩm.
- Yêu cầu `CONCUR_UPDATABLE` không bảo đảm driver sẽ cấp quyền cập nhật. Kiểm tra `rs.getConcurrency()` và exceptions/SQL warnings thực tế.
- Không được gọi `updateObject` khi chưa đứng trên hàng thích hợp bằng `rs.next()` (hoặc chế độ insert row tương ứng).
- `updateRow` có thể ném `SQLException` nếu bị constraint, concurrency conflict, thiếu quyền hoặc database error.
- Nếu ứng dụng cần phát hiện lost update, việc dùng updatable cursor không tự thay thế optimistic locking/version check.
- Kết quả SQL và khả năng cập nhật phải được test với DB/schema thực; không coi snippet là SQL portable cho mọi engine.

### 12.1. Vì sao nhiều dự án ưu tiên PreparedStatement UPDATE?

Với bài toán nghiệp vụ như `UPDATE orders SET amount=? WHERE id=? AND version=?`, dùng `PreparedStatement` thường giúp thấy rõ:

- Cột nào được ghi;
- Điều kiện `WHERE`/version;
- Row count có bằng 1 không;
- Cách xử lý conflict và transaction;
- Giới hạn quyền truy cập DB.

`ResultSet.updateObject` vẫn là API hợp lệ và hữu ích khi driver hỗ trợ updatable cursor; nó không bị “legacy” theo nghĩa bị loại khỏi JDBC. Nhưng không nên dùng nó chỉ vì tránh viết SQL mà bỏ qua những yêu cầu concurrency/version/transaction.

## 13. Ví dụ 6 — mô phỏng updateObject → updateRow

Ví dụ sau dùng **dynamic proxy mock**, không có DB thật. Nó mô phỏng một hàng ban đầu có `amount=5.00`, vùng staged và bước `updateRow` để dễ hiểu contract.

**MockResultSetDemo.java**:

```java
import java.lang.reflect.Proxy;
import java.math.BigDecimal;
import java.sql.JDBCType;
import java.sql.ResultSet;
import java.util.HashMap;
import java.util.Map;

public class MockResultSetDemo {
    public static void main(String[] args)
            throws Exception {
        Map<String, Object> dbRow =
            new HashMap<>();

        dbRow.put(
            "amount", new BigDecimal("5.00")
        );

        Map<String, Object> staged =
            new HashMap<>();

        ResultSet rs = (ResultSet)
            Proxy.newProxyInstance(
                ResultSet.class.getClassLoader(),
                new Class<?>[] { ResultSet.class },
                (proxy, method, callArgs) -> {
                    switch (method.getName()) {
                        case "getConcurrency":
                            return ResultSet.CONCUR_UPDATABLE;

                        case "getObject":
                            return dbRow.get(
                                (String) callArgs[0]
                            );

                        case "updateObject":
                            staged.put(
                                (String) callArgs[0],
                                callArgs[1]
                            );
                            return null;

                        case "updateRow":
                            dbRow.putAll(staged);
                            staged.clear();
                            return null;

                        default:
                            throw new UnsupportedOperationException(
                                method.getName()
                            );
                    }
                }
            );

        System.out.println(
            "updatable=" +
            (rs.getConcurrency()
                == ResultSet.CONCUR_UPDATABLE)
        );

        System.out.println(
            "before=" + rs.getObject("amount")
        );

        rs.updateObject(
            "amount",
            new BigDecimal("12.34"),
            JDBCType.DECIMAL,
            2
        );

        System.out.println(
            "staged=" + staged.get("amount")
        );

        System.out.println(
            "beforeUpdateRow=" +
            rs.getObject("amount")
        );

        rs.updateRow();

        System.out.println(
            "afterUpdateRow=" +
            rs.getObject("amount")
        );

        System.out.println(
            "pending=" + staged.size()
        );
    }
}
```

**Điều mô phỏng:** Giá trị được stage riêng và được đưa vào cấu trúc giả lập `dbRow` tại `updateRow()`. Đây chỉ là cách minh họa, **không phải bảo đảm rằng getter của một driver thật sẽ luôn hiển thị giá trị cũ cho tới updateRow**; driver có thể phản ánh giá trị đang staged trên cursor. Trong database thật, `updateRow()` có thể ảnh hưởng row trong transaction nhưng còn cần `connection.commit()` nếu auto-commit đã tắt. Không gọi việc stage trong mock là transaction.

## 14. updateObject với null và cách hủy pending update

Khi muốn cập nhật một cột thành SQL NULL:

```java
// Đoạn minh họa, ResultSet updatable hợp lệ:
rs.updateObject("optional_note", null, JDBCType.VARCHAR);
rs.updateRow();
```

Có thể dùng setter chuyên dụng:

```java
rs.updateNull("optional_note");
rs.updateRow();
```

`ResultSet.cancelRowUpdates()` là API để hủy thay đổi đang chờ ở hàng hiện tại khi chưa gọi `updateRow()`; kiểm tra giới hạn cụ thể trong Javadoc/driver. Nó **không phải rollback transaction** cho những thay đổi đã được gửi vào database.

Khi cập nhật kết quả bằng `moveToInsertRow()` và `insertRow()`, thao tác khác với `updateRow()`: hàng mới được thêm, không phải thay thế hàng đang có. Luôn kiểm tra con trỏ đang đứng ở row nào và khả năng updatable của result set.

## 15. Driver không hỗ trợ SQLType: vì sao lỗi xuất hiện?

Các overload `SQLType` của `PreparedStatement` và `ResultSet` là default methods trong interface. Javadoc nói **default implementation ném `SQLFeatureNotSupportedException`**. Driver có thể hỗ trợ overload chuẩn nhưng từ chối một `targetSqlType` cụ thể hoặc một kiểu conversion.

Điều này có thể xảy ra ngay cả khi code biên dịch:

```java
// Biên dịch được với Java 8+ nhưng driver có thể ném lỗi.
ps.setObject(1, LocalDate.now(), JDBCType.DATE);
```

**Không suy từ “đang dùng JDK 21/26” rằng driver tự hỗ trợ JDBC 4.2.** JDK chứa API Java; module JDBC driver và DB engine quyết định implementation.

Những nguyên nhân lỗi cần phân biệt:

- `SQLFeatureNotSupportedException`: method hoặc target SQL type/conversion không được driver hỗ trợ.
- `SQLException`: index/cột không hợp lệ, câu SQL sai, constraint fail, kết nối đóng, DB access error, conversion failure.
- `SQLDataException` hoặc các subclass `SQLException`: dữ liệu không chuyển được/range/format.
- `SQLTimeoutException`: timeout JDBC theo điều kiện của method/driver; không phải mọi lỗi chậm đều là SQL timeout.
- `ClassCastException`/`IllegalArgumentException` của application: lỗi Java trước khi/ngoài JDBC hoặc mapping không đúng.

Đừng catch mọi `SQLException` rồi coi là “driver cũ”; làm thế che mất lỗi dữ liệu hoặc sự cố DB.

### 15.1. Đường dự phòng có kiểm soát

Nếu driver chưa có overload `SQLType`, có thể dự kiến phương án dùng overload `Types` hoặc setter chuyên dụng, sau khi **xác nhận được driver thật hỗ trợ**:

```java
// Đoạn minh họa, ps là PreparedStatement thật.
try {
    ps.setObject(
        1, localDate, JDBCType.DATE
    );
} catch (SQLFeatureNotSupportedException unsupported) {
    ps.setDate(
        1, java.sql.Date.valueOf(localDate)
    );
}
```

Hoặc:

```java
// Overload int-based vẫn còn hợp lệ:
ps.setObject(
    1, java.sql.Date.valueOf(localDate),
    Types.DATE
);
```

**Đây không phải quy tắc “hễ thất bại là dùng Types”**. Chỉ fallback cho kiểu đã định nghĩa mapping tương đương và có integration test. Với timestamp có timezone, UDT/vendor type hoặc trường không thể mất thông tin offset, một fallback sang `TIMESTAMP` có thể **đổi ngữ nghĩa**; khi ấy tốt hơn là từ chối và báo khả năng driver/DB không phù hợp.

## 16. Ví dụ 7 — mô phỏng driver từ chối overload SQLType

**UnsupportedSqlTypeDemo.java** dùng mock cố tình ném `SQLFeatureNotSupportedException` ở overload SQLType, nhưng chấp nhận overload cũ theo mã `int`. Đó là **hành vi mô phỏng có chủ đích**, không phải khẳng định một driver cụ thể luôn hoạt động như vậy.

```java
import java.lang.reflect.Proxy;
import java.sql.JDBCType;
import java.sql.PreparedStatement;
import java.sql.SQLFeatureNotSupportedException;
import java.sql.SQLType;
import java.sql.Types;
import java.time.LocalDate;

public class UnsupportedSqlTypeDemo {
    public static void main(String[] args)
            throws Exception {
        PreparedStatement ps = (PreparedStatement)
            Proxy.newProxyInstance(
                PreparedStatement.class.getClassLoader(),
                new Class<?>[] {
                    PreparedStatement.class
                },
                (proxy, method, callArgs) -> {
                    if (method.getName().equals(
                            "setObject")
                            && callArgs.length == 3) {

                        if (callArgs[2] instanceof SQLType) {
                            throw new SQLFeatureNotSupportedException(
                                "SQLType overload unavailable"
                            );
                        }

                        if (callArgs[2] instanceof Integer) {
                            System.out.println(
                                "fallbackCode=" +
                                callArgs[2]
                            );
                            System.out.println(
                                "fallbackValueClass=" +
                                callArgs[1]
                                    .getClass()
                                    .getSimpleName()
                            );
                            return null;
                        }
                    }

                    throw new UnsupportedOperationException(
                        method.getName()
                    );
                }
            );

        LocalDate date = LocalDate.of(2024, 2, 29);

        try {
            ps.setObject(
                1, date, JDBCType.DATE
            );
        } catch (SQLFeatureNotSupportedException ex) {
            System.out.println(
                "unsupported=" +
                ex.getClass().getSimpleName()
            );

            ps.setObject(
                1, java.sql.Date.valueOf(date),
                Types.DATE
            );
        }
    }
}
```

```bash
javac UnsupportedSqlTypeDemo.java
java UnsupportedSqlTypeDemo
```

Stdout của **mock**:

```text
unsupported=SQLFeatureNotSupportedException
fallbackCode=91
fallbackValueClass=Date
```

`Types.DATE` có mã `91`. Bài demo chứng minh cách **bắt đúng subclass `SQLFeatureNotSupportedException`** và phân nhánh fallback có chủ đích, không phải chứng minh rằng chuyển `LocalDate` sang `java.sql.Date` luôn bảo toàn mọi semantics ở tất cả drivers.

## 17. SQLType do vendor định nghĩa

`SQLType` được thiết kế để đại diện cả type chuẩn lẫn type nhà cung cấp. Một vendor có thể có SQL type độc quyền mà `JDBCType` chuẩn không mô tả đầy đủ.

Bạn có thể tạo một `SQLType` riêng:

```java
// Đoạn minh họa interface:
SQLType custom = new SQLType() {
    public String getName() {
        return "CUSTOM_STATUS";
    }

    public String getVendor() {
        return "com.example.db";
    }

    public Integer getVendorTypeNumber() {
        return 50001;
    }
};
```

**Nhưng:** Tạo object `SQLType` **không tự khiến driver hiểu kiểu vendor đó**. Driver phải nhận diện vendor/type number và có logic conversion. Với production, ưu tiên dùng hằng `SQLType` hoặc API do chính driver cung cấp; tránh tự chế type number khi không có tài liệu nhà cung cấp.

```text
standardByCode=VARCHAR
```

Đây chỉ là demo metadata trong JVM. Không có database và không khẳng định driver hiểu `CUSTOM_STATUS`.

**Cẩn trọng với `getVendorTypeNumber()`:** Interface trả `Integer`, có thể là `null` trong một custom implementation. Khi cần mapping về `Types`, đừng auto-unbox một giá trị có thể null hoặc giả định mọi vendor code nằm trong danh sách chuẩn của `JDBCType`.

## 18. SQLType và SQL injection

`PreparedStatement` với placeholder `?` tách **giá trị** khỏi SQL text, có lợi cho an toàn và khả năng chuyển đổi:

```java
// Đúng khi bind giá trị:
String sql =
    "UPDATE users SET status = ? WHERE id = ?";

try (PreparedStatement ps =
         connection.prepareStatement(sql)) {
    ps.setObject(1, status, JDBCType.VARCHAR);
    ps.setLong(2, userId);
    ps.executeUpdate();
}
```

**Không chèn giá trị input vào SQL string bằng nối chuỗi.** Nhưng placeholder `?` thường không dùng được cho **tên bảng/tên cột/keyword SQL**; nếu phải chọn identifier động, áp dụng allowlist ở tầng application. `SQLType` không tự bảo vệ SQL identifier động.

`ResultSet.updateObject` không phải công cụ chống SQL injection cho chuỗi SQL đã được dựng sai ở `createStatement`; an toàn vẫn phụ thuộc cách query được tạo.

## 19. Transaction và concurrency: updateRow chưa đồng nghĩa commit

Nếu `Connection.setAutoCommit(false)`:

```text
PreparedStatement.setObject(...) / ResultSet.updateObject(...)
    -> bind hoặc stage dữ liệu

PreparedStatement.executeUpdate() / ResultSet.updateRow()
    -> gửi thay đổi lên database trong transaction

Connection.commit()
    -> kết thúc transaction thành công

Connection.rollback()
    -> hủy transaction theo semantics của database
```

Đừng đánh dấu business record “đã lưu” chỉ sau `updateObject`. Với auto-commit bật, commit behavior gắn với completion của SQL statement theo JDBC/driver; những chi tiết như cursor còn mở hoặc batch nên được test rõ.

### 19.1. Optimistic concurrency control

Nếu nhiều user sửa một record, chỉ gửi một update có thể gây **lost update**. Với PreparedStatement, một chiến lược phổ biến:

```sql
UPDATE purchase_events
SET amount = ?, version = version + 1
WHERE event_id = ? AND version = ?
```

Rồi kiểm tra `executeUpdate() == 1`. Nếu 0, record không tồn tại hoặc version đã đổi, cần xử lý conflict. `ResultSet.updateRow` không tự giải quyết tất cả nhu cầu optimistic locking của domain. Cách viết câu `UPDATE` cũng phải tương thích syntax DB cụ thể.

### 19.2. Khi có lỗi giữa các bước

Sau `setObject`/`executeUpdate` hoặc `updateObject`/`updateRow` nếu phát sinh `SQLException`, caller cần áp dụng transaction policy, thường là rollback trên connection đang ở transaction thủ công, ghi log không lộ secret, đóng resources trong `try-with-resources` và phân loại lỗi theo SQLState/vendor code nếu cần.

Không bắt exception rồi tiếp tục commit khi state đã không còn hợp lệ. Không tự retry lệnh có side effect (ví dụ tạo payment) mà không có idempotency/transaction boundary.

## 20. Kiểm thử integration cho JDBC driver thật

Mock chỉ xác nhận code Java gọi overload đúng. Để kiểm chứng **JDBC 4.2 compatibility**, cần chạy trên **driver/database/version thực tế**. Ma trận test tối thiểu:

| Kiểm thử | Nội dung cần xác minh |
| --- | --- |
| SQLType overload support | `setObject(..., JDBCType.DATE)` có ném `SQLFeatureNotSupportedException` không? |
| DECIMAL scale | `12.34` có được lưu/đọc nguyên vẹn ở cột phù hợp không? |
| DECIMAL rounding | `123.456` vào cột scale 2 có lỗi/rounding theo đúng policy không? |
| Null type | `setObject(index,null,JDBCType.DATE)` hoặc `setNull` lưu được SQL NULL không? |
| LocalDate | `LocalDate` round-trip DATE đúng không? |
| LocalDateTime | TIMESTAMP không offset có giữ đúng fields không? |
| OffsetDateTime | TIMESTAMP_WITH_TIMEZONE có được hỗ trợ và giữ cùng instant không? |
| TIME_WITH_TIMEZONE | `OffsetTime` được hỗ trợ như nào? |
| Typed getters | `rs.getObject(col, LocalDate.class)`/`OffsetDateTime.class` có hỗ trợ không? |
| Updatable cursor | `CONCUR_UPDATABLE` được chấp nhận hay bị downgrade? |
| updateObject staging | Không ghi DB trước `updateRow`/`insertRow` |
| updateRow | Gửi cập nhật đúng row và xử lý constraint |
| Transaction | Commit/rollback chính xác với autoCommit=false |
| Concurrent writes | Có phát hiện lost update/version conflict không? |
| Vendor SQLType | Driver nhận type vendor-specific hay báo unsupported? |
| Error handling | Invalid index, conversion fail, connection closed, timeout |
| Resource cleanup | Đóng đúng `Connection`, `PreparedStatement`, `ResultSet` |
| Security | Dùng placeholder cho values, không nối input thành SQL |

**Chạy test trên môi trường gần production**, không suy từ demo mock hoặc một DB in-memory rằng mọi driver khác sẽ có cùng semantics. Một driver có thể hỗ trợ ba đối số nhưng không hỗ trợ target type cụ thể.

### 20.1. JDBC version và khả năng DB

Có thể đọc `DatabaseMetaData`:

```java
// Đoạn minh họa, connection hợp lệ.
DatabaseMetaData meta = connection.getMetaData();

System.out.println(
    meta.getJDBCMajorVersion() + "." +
    meta.getJDBCMinorVersion()
);
System.out.println(
    meta.getDriverName()
);
System.out.println(
    meta.getDriverVersion()
);
```

Metadata giúp ghi lại phiên bản, nhưng **không thay thế thử chính overload và loại conversion**. Driver tự báo JDBC 4.2 không đồng nghĩa mọi SQL type vendor đều được hỗ trợ, nhất là timezone type và updatable cursor.

### 20.2. Không dùng một schema test sai để kết luận API không chạy

Nếu test chỉ dùng câu `SELECT SUM(amount) ...` rồi yêu cầu `CONCUR_UPDATABLE`, một số DB không cho updatable cursor vì query tổng hợp. Hãy dùng bảng nhỏ có primary key, query đơn giản, quyền UPDATE và transaction rõ. Tách **unsupported SQLType method** khỏi **unsupported updatable query**.

## 21. Lỗi thường gặp

### Lỗi 1 — Nhầm `SQLType` với `Types`

`SQLType` là interface, `JDBCType` là enum; `Types.DECIMAL` là int. Dùng đúng overload và hiểu driver support.

### Lỗi 2 — Nghĩ Java 8/JDK mới tự bảo đảm driver hỗ trợ SQLType

Default interface method có thể ném `SQLFeatureNotSupportedException`. Kiểm tra driver thực.

### Lỗi 3 — Không truyền scale cho DECIMAL

Overload ba đối số có mặc định scale zero theo Javadoc. Với decimal có phần lẻ, cần kế hoạch rõ về scale/rounding và test DB thực.

### Lỗi 4 — Đưa precision vào tham số scaleOrLength

`DECIMAL(12,2)` có precision 12, scale 2. Giá trị truyền `scaleOrLength` cho DECIMAL là **scale**, không phải precision.

### Lỗi 5 — Dùng `new BigDecimal(double)` rồi mong số thập phân chính xác theo chuỗi

Dùng `new BigDecimal("12.34")` hoặc `BigDecimal.valueOf` khi thích hợp; kiểm soát rounding.

### Lỗi 6 — Nghĩ `setObject` đã chạy SQL

`setObject` chỉ bind value. Phải `executeUpdate`, `executeQuery` hoặc phương thức execute phù hợp.

### Lỗi 7 — Gọi `updateObject` và tin bảng đã đổi

Cần `updateRow` hoặc `insertRow`; transaction commit là bước khác.

### Lỗi 8 — Dùng ResultSet mặc định read-only để update

Yêu cầu `CONCUR_UPDATABLE` và xác nhận concurrency sau khi execute.

### Lỗi 9 — Truyền columnIndex=0 hoặc parameterIndex=0

JDBC dùng index 1-based cho parameter và result-set column.

### Lỗi 10 — Nhầm columnLabel với tên bảng

`updateObject(String columnLabel,...)` nhận **nhãn cột trong result set**, có thể bị ảnh hưởng bởi alias `AS`.

### Lỗi 11 — Dùng Instant/ZonedDateTime trực tiếp và mặc định portable

JDBC 4.2 không bắt buộc mọi loại `java.time` ngoài mapping chuẩn. Chọn kiểu/date-time semantics tương ứng và test driver.

### Lỗi 12 — Lưu OffsetDateTime rồi yêu cầu đúng offset gốc từ mọi DB

SQL TIMESTAMP_WITH_TIMEZONE có cách lưu/trả khác nhau tùy DB. Kiểm tra instant và yêu cầu offset/zone của domain.

### Lỗi 13 — Nhầm SQL NULL với JDBCType.NULL

Chọn type **của cột đích** khi bind null; với unsupported overload có thể dùng `setNull`.

### Lỗi 14 — Bắt mọi SQLException để fallback

Một conversion fail, constraint violation hoặc DB down không có nghĩa overload SQLType bị thiếu. Bắt đúng `SQLFeatureNotSupportedException` khi trường hợp tương ứng được chứng minh.

### Lỗi 15 — Tự chế vendor SQLType rồi tin driver tự hiểu

Driver phải implement mapping. Custom interface object chỉ cung cấp metadata.

### Lỗi 16 — Dùng updatable cursor cho query aggregate/join và coi DB lỗi

Không phải mọi query result set có khả năng update. Kiểm tra SQL, quyền và driver.

### Lỗi 17 — Quên commit/rollback khi autoCommit=false

`updateRow`/`executeUpdate` không tự là transaction commit trong mode thủ công.

### Lỗi 18 — Đánh dấu test mock PASS là DB integration PASS

Mock không có database, constraint, timezone normalization hoặc SQL parser. Test trên driver thật.

### Lỗi 19 — SQL injection qua nối chuỗi

Bind values bằng placeholder; không nối input vào SQL text. Với identifier động dùng allowlist.

### Lỗi 20 — Không kiểm tra số row UPDATE

Nếu business mong cập nhật đúng một record, kiểm tra row count và version để phát hiện conflict.

### Lỗi 21 — Coi metadata JDBC version là bảo đảm toàn bộ features

Feature support phụ thuộc implementation và DB type. Thử từng path cần dùng.

### Lỗi 22 — Dùng updateObject trên cursor chưa đứng ở hàng nào

Phải `rs.next()` để ở hàng hiện tại, hoặc `moveToInsertRow()` nếu chèn. Gọi update ngay sau executeQuery không có current row là sai.

### Lỗi 23 — Không đóng resources JDBC

Dùng `try-with-resources` cho Connection/Statement/ResultSet để tránh cạn connection/cursor.

### Lỗi 24 — Quên dữ liệu bị làm tròn/overflow ở DB

Integer/decimal/time precision bị giới hạn bởi cột và driver; cần validation và round-trip test.

## 23. Câu hỏi ôn tập

**1.** `SQLType` và `JDBCType` là gì?

**Đáp án:** `SQLType` là interface mô tả SQL type, `JDBCType` là enum các type JDBC chuẩn triển khai interface.

**2.** `Types.DECIMAL` khác `JDBCType.DECIMAL` như thế nào?

**Đáp án:** `Types.DECIMAL` là số nguyên `int` (3); `JDBCType.DECIMAL` là enum object `SQLType`.

**3.** `PreparedStatement.setObject(1,x,JDBCType.DATE)` có chạy SQL ngay không?

**Đáp án:** Không, chỉ bind tham số. Cần execute thích hợp.

**4.** Index tham số đầu tiên là 0 hay 1?

**Đáp án:** 1.

**5.** Tham số `scaleOrLength` của `DECIMAL` là gì?

**Đáp án:** Số chữ số sau dấu thập phân, không phải precision.

**6.** Khi không truyền scale trong overload SQLType thì Javadoc giả định bao nhiêu?

**Đáp án:** Scale 0.

**7.** `updateObject` có tự ghi ngay vào DB không?

**Đáp án:** Không. Với hàng hiện tại, cần `updateRow()`; với hàng chèn, `insertRow()`.

**8.** Sau `updateRow` với autoCommit=false, đã commit transaction chưa?

**Đáp án:** Chưa; cần `Connection.commit()` hoặc rollback theo policy.

**9.** Muốn dùng `updateObject` trên ResultSet cần loại concurrency nào?

**Đáp án:** `CONCUR_UPDATABLE`; còn cần driver/query thực sự cho phép cập nhật.

**10.** `columnIndex` đầu tiên là mấy?

**Đáp án:** 1.

**11.** `columnLabel` có thể là alias `AS` không?

**Đáp án:** Có.

**12.** Khi driver không override default SQLType overload, có thể gặp lỗi gì?

**Đáp án:** `SQLFeatureNotSupportedException`.

**13.** Có được bắt mọi SQLException rồi fallback không?

**Đáp án:** Không; dễ che lỗi DB/dữ liệu thực. Cần phân loại chính xác.

**14.** Loại Java nào tương ứng SQL DATE theo JDBC 4.2?

**Đáp án:** `LocalDate`.

**15.** Loại Java nào tương ứng TIMESTAMP_WITH_TIMEZONE?

**Đáp án:** `OffsetDateTime`, nếu DB/driver hỗ trợ type đó.

**16.** `LocalDateTime` có luôn xác định một instant không?

**Đáp án:** Không, vì không có offset/zone.

**17.** `JDBCType.TIMESTAMP_WITH_TIMEZONE` có bảo đảm mọi DB lưu nguyên offset ban đầu không?

**Đáp án:** Không; cần test semantics round-trip của DB.

**18.** `SQLType` custom có thể sử dụng ngay trên mọi driver không?

**Đáp án:** Không. Driver phải nhận diện vendor type và hỗ trợ conversion.

**19.** `getVendorTypeNumber` trả kiểu gì?

**Đáp án:** `Integer`; với custom implementation có thể null, nên không auto-unbox vô điều kiện.

**20.** MockBindingDemo kiểm chứng điều gì?

**Đáp án:** Kiểm chứng cách Java gọi overload, index/type/scale; không chứng minh driver thật hay DB đã lưu.

**21.** Vì sao cần integration test về NULL?

**Đáp án:** Để chắc chắn driver hiểu type cột, cách bind null và cách đọc lại đúng.

**22.** Vì sao dùng `new BigDecimal("12.34")` cho tiền?

**Đáp án:** Tránh lỗi biểu diễn thập phân khi tạo trực tiếp từ `double` nhị phân và kiểm soát scale rõ.

**23.** Dùng placeholder `?` có bind được tên cột/tên bảng tùy ý không?

**Đáp án:** Thông thường không; nó dùng cho giá trị. Identifier động phải được kiểm soát qua allowlist.

**24.** Nếu `executeUpdate` trả 0 trong UPDATE theo id và version, cần làm gì?

**Đáp án:** Xử lý record không có hoặc version conflict, không mặc định đã cập nhật thành công.

## 24. Tài liệu chính thức còn áp dụng

- [Oracle Java SE 26 — SQLType](https://docs.oracle.com/en/java/javase/26/docs/api/java.sql/java/sql/SQLType.html): interface, metadata kiểu SQL chuẩn và vendor.
- [Oracle Java SE 26 — JDBCType](https://docs.oracle.com/en/java/javase/26/docs/api/java.sql/java/sql/JDBCType.html): enum chuẩn, mapping tới `Types`.
- [Oracle Java SE 26 — PreparedStatement](https://docs.oracle.com/en/java/javase/26/docs/api/java.sql/java/sql/PreparedStatement.html): overload `setObject` nhận `SQLType`, `scaleOrLength`, default `SQLFeatureNotSupportedException`.
- [Oracle Java SE 26 — ResultSet](https://docs.oracle.com/en/java/javase/26/docs/api/java.sql/java/sql/ResultSet.html): `updateObject`, `updateRow`, `insertRow`, updatable cursor và typed getters.
- [Oracle Java SE 26 — Connection](https://docs.oracle.com/en/java/javase/26/docs/api/java.sql/java/sql/Connection.html): transaction, `commit`, `rollback` và auto-commit.
- [Oracle Java SE 26 — SQLFeatureNotSupportedException](https://docs.oracle.com/en/java/javase/26/docs/api/java.sql/java/sql/SQLFeatureNotSupportedException.html): báo feature JDBC driver không hỗ trợ.
- [Oracle Java SE 26 — DatabaseMetaData](https://docs.oracle.com/en/java/javase/26/docs/api/java.sql/java/sql/DatabaseMetaData.html): version/capability metadata.
- [JDBC 4.2 Maintenance Release (JSR 221)](https://jcp.org/aboutJava/communityprocess/maintenance/jsr221/JDBC4.2MR-Oct232013.pdf): thay đổi liên quan `SQLType` và các overload mới.

**Kết luận:** Trong JDBC 4.2, `SQLType`/`JDBCType` cho phép chỉ rõ kiểu SQL đích khi bind bằng `PreparedStatement.setObject` hoặc stage cột bằng `ResultSet.updateObject`. `setObject` phải đi với execute, còn `updateObject` phải đi với `updateRow`/`insertRow`; commit/rollback vẫn là vấn đề transaction. Driver có thể chưa hỗ trợ default SQLType overload, nên phải kiểm tra `SQLFeatureNotSupportedException` và test trực tiếp trên DB/driver triển khai. Null, scale, precision, offset/timezone và concurrency của ResultSet đều cần kiểm chứng theo schema và yêu cầu nghiệp vụ.
