# Map.merge và tổng hợp dữ liệu theo khóa trong Java (Java 8+)

## 1. Bài toán: nhiều bản ghi cùng một khóa, kết quả chỉ có một giá trị

Trong ứng dụng thực tế, nhiều bản ghi có thể mang **cùng một khóa**: nhiều giao dịch cùng mã sản phẩm, nhiều sự kiện cùng loại, nhiều từ giống nhau trong văn bản, hoặc nhiều kết quả tính toán cùng mã nhân viên.

Ví dụ có các dòng bán hàng:

| Sản phẩm | Số lượng |
| --- | ---: |
| apple | 2 |
| orange | 5 |
| apple | 3 |
| pear | 1 |
| orange | 2 |

Ta muốn có kết quả:

~~~text
apple  -> 5
orange -> 7
pear   -> 1
~~~

**Map<K,V>** không lưu hai mapping riêng cho cùng một khóa theo quy tắc bằng nhau của Map. Muốn tổng hợp dữ liệu, ta cần **kết hợp giá trị mới với giá trị đã có** thay vì liên tục ghi đè. Từ Java 8, phương thức **Map.merge(key, value, remappingFunction)** giải quyết trực tiếp việc này.

~~~java
Map<String, Long> totalByProduct = new HashMap<>();

for (Sale sale : sales) {
    totalByProduct.merge(
            sale.product(),
            sale.quantity(),
            Long::sum);
}
~~~

Trong đoạn minh họa trên, **Sale** là kiểu bản ghi có các phương thức **product()** và **quantity()**. Chương trình đầy đủ ở phần 9 khai báo kiểu này và chạy độc lập.

**Map.merge vẫn là API hiện hành**, không phải kỹ thuật đã lỗi thời. Bài học sẽ tập trung vào ngữ nghĩa chính xác, cách dùng để đếm và cộng dồn theo khóa, đối chiếu với các API khác, kết hợp cùng Stream/Collectors và những giới hạn khi sử dụng đa luồng.

## 2. Chữ ký và vai trò ba tham số

Định nghĩa cốt lõi:

~~~java
V merge(
        K key,
        V value,
        BiFunction<? super V, ? super V, ? extends V> remappingFunction);
~~~

Trong đó:

- **key:** khóa cần cập nhật.
- **value:** giá trị mới để thêm vào hoặc hợp nhất, **bắt buộc không null**.
- **remappingFunction:** hàm gộp hai giá trị kiểu V khi khóa **đã có giá trị khác null**; đối số thứ nhất là **oldValue**, đối số thứ hai là **value mới**.
- **Giá trị trả về:** giá trị cuối cùng gắn với khóa, hoặc **null** nếu sau thao tác không còn mapping.

Ví dụ đơn giản:

~~~java
Map<String, Integer> counts = new HashMap<>();

counts.merge("java", 1, Integer::sum); // java=1
counts.merge("java", 1, Integer::sum); // java=2
counts.merge("map", 1, Integer::sum);  // map=1
~~~

Ở lần đầu cho khóa "java", Map chưa có giá trị nên đặt **1** trực tiếp. Lần thứ hai, Map đã có **1**, nên **Integer::sum** nhận hai số (1, 1) và trả về **2**.

Hàm gộp tương đương với:

~~~java
(oldValue, incomingValue) -> oldValue + incomingValue
~~~

**Điểm dễ sai:** remappingFunction **không nhận key**. Nếu bạn cần cả key để tính giá trị mới, hãy xem **Map.compute(...)**; compute nhận hàm với đối số **(key, oldValue)**.

## 3. Cơ chế merge: ba trường hợp phải thuộc

### Trường hợp A: chưa có khóa

~~~java
Map<String, Integer> map = new HashMap<>();
Integer result = map.merge("A", 5, Integer::sum);
// result = 5; map = {A=5}
~~~

Vì **map.get("A")** là null, Map đưa giá trị mới **5** vào. Hàm Integer::sum **không được gọi** cho thao tác này.

### Trường hợp B: khóa đã gắn với một giá trị khác null

~~~java
Map<String, Integer> map = new HashMap<>();
map.put("A", 5);

Integer result = map.merge("A", 2, Integer::sum);
// result = 7; map = {A=7}
~~~

Ở đây Map lấy **oldValue=5** và **incomingValue=2**, sau đó gọi remappingFunction để thu được **7** và thay mapping cũ.

### Trường hợp C: khóa có giá trị null trong Map cho phép null

~~~java
Map<String, Integer> map = new HashMap<>();
map.put("A", null);

Integer result = map.merge("A", 5, Integer::sum);
// result = 5; map = {A=5}
~~~

**HashMap cho phép null value.** Đối với merge, "không có khóa" và "khóa đang gắn với null" đều đi vào nhánh **đặt value mới**, không gọi remappingFunction. Điều này khác với suy nghĩ rằng merge sẽ luôn gộp hai giá trị chỉ vì **containsKey("A")** trả true.

Nếu bài toán cần phân biệt **"chưa có dữ liệu"** với **"dữ liệu hiện tại bằng null"**, đừng dùng null như một con số; hãy thiết kế trạng thái riêng hoặc dùng cấu trúc thích hợp.

### Bảng quy tắc

| Trạng thái trước merge | Việc thực hiện | Trạng thái sau |
| --- | --- | --- |
| key chưa tồn tại | Đặt value mới, không gọi remapper | key -> value |
| key tồn tại nhưng đang gắn null | Đặt value mới, không gọi remapper | key -> value |
| key tồn tại với oldValue khác null | Gọi remapper(oldValue, value) | key -> kết quả, nếu kết quả khác null |
| remapper trả null | Xóa mapping của key | key không còn mapping |
| remapper ném exception | Exception được truyền ra | Mapping hiện tại không được thay bằng kết quả tính mới |

**Không nhầm hai loại null:** value truyền vào merge **không được null**; nhưng remappingFunction **có thể trả null** để xóa mapping. Nếu remapper tác động lên object mutable từ trước rồi ném lỗi, sự thay đổi bên trong object đó không nhất thiết được hoàn tác. Vì vậy hãy viết remapper thuần, tránh side effect.

## 4. Vì sao merge tốt hơn put khi cần tổng hợp?

Xét đoạn code:

~~~java
for (String word : words) {
    counts.put(word, 1);
}
~~~

Nếu từ "java" xuất hiện ba lần, Map cuối vẫn có **java=1** vì **put** ghi đè giá trị trước đó. Ta không đang đếm; ta chỉ lưu **giá trị của lần ghi gần nhất**.

Có thể sửa thủ công:

~~~java
for (String word : words) {
    counts.put(word, counts.getOrDefault(word, 0) + 1);
}
~~~

Đoạn này đơn giản và hợp lệ **khi không có value null**, Map dùng tuần tự và giá trị đếm không bị tràn. Nhưng với Map cho phép **key -> null**, **getOrDefault** trả về null khi key có mapping null, dẫn tới **NullPointerException** khi unbox để cộng 1.

Với merge:

~~~java
for (String word : words) {
    counts.merge(word, 1, Integer::sum);
}
~~~

Không cần viết nhánh kiểm tra khóa. Khi chưa có giá trị hoặc giá trị đang null, merge bắt đầu bằng 1; nếu đã có số đếm, merge cộng vào.

**Lưu ý quan trọng:** **Map.merge thay đổi chính đối tượng Map được gọi**. Nó không tạo một Map mới để trả về. Kết quả của mỗi lời gọi là một value V (hoặc null), còn Map vẫn là đối tượng ban đầu.

## 5. Mẫu 1 — Đếm tần suất xuất hiện

Dữ liệu:

~~~java
List<String> words = Arrays.asList(
        "java", "map", "java", "stream", "map", "java");
~~~

Tổng hợp bằng Map:

~~~java
Map<String, Integer> frequencies = new HashMap<>();

for (String word : words) {
    frequencies.merge(word, 1, Integer::sum);
}

// Nội dung: java=3, map=2, stream=1.
~~~

Trình tự khi xử lý "java":

~~~text
Lần 1: chưa có -> value mới là 1
Lần 2: old=1 + incoming=1 -> 2
Lần 3: old=2 + incoming=1 -> 3
~~~

Muốn hiển thị theo thứ tự khóa, dùng **TreeMap** thay vì giả định **HashMap** giữ thứ tự:

~~~java
Map<String, Integer> frequencies = new TreeMap<>();

for (String word : words) {
    frequencies.merge(word, 1, Integer::sum);
}

System.out.println(frequencies);
// {java=3, map=2, stream=1}
~~~

Nếu không cần sắp thứ tự nhưng muốn giữ thứ tự **khóa được gặp lần đầu** khi xử lý tuần tự, có thể sử dụng **LinkedHashMap**. Đây là yêu cầu về trình bày kết quả, độc lập với thuật toán cộng dồn.

### Chuẩn hóa khóa trước khi merge

~~~java
for (String word : words) {
    String key = word.trim().toLowerCase(Locale.ROOT);
    if (!key.isEmpty()) {
        frequencies.merge(key, 1, Integer::sum);
    }
}
~~~

**Locale.ROOT** giúp quy tắc viết thường không phụ thuộc locale mặc định của máy. Nhưng chuẩn hóa Unicode/locale phải tuân thủ đặc tả nghiệp vụ; đừng tự giả định **toLowerCase** giải quyết mọi trường hợp tương đương văn bản.

Nếu **word** có thể null, cần định nghĩa chính sách bỏ, báo lỗi hoặc gán mã thay thế **trước khi gọi trim()**. Một key sai/null không nên được âm thầm gộp cùng dữ liệu hợp lệ nếu điều đó làm lệch thống kê.

## 6. Mẫu 2 — Cộng số lượng, điểm hoặc doanh thu theo khóa

Giả sử một đơn hàng có **product** và **quantity**:

~~~java
Map<String, Long> totalByProduct = new TreeMap<>();

for (Sale sale : sales) {
    totalByProduct.merge(
            sale.product(),
            sale.quantity(),
            Long::sum);
}
~~~

Nếu dữ liệu "apple" có số lượng **2** và **3**, kết quả là **apple=5**. Nếu "orange" có **5** và **2**, kết quả là **orange=7**.

Đầu vào **quantity** trong ví dụ là **long**, nên Map nhận **Long** và hàm **Long::sum** làm phép gộp. Đây là tổng theo khóa, không phải số bản ghi theo khóa. Nếu mỗi Sale là một giao dịch, ta có thể đồng thời duy trì:

~~~java
Map<String, Integer> counts = new TreeMap<>();

for (Sale sale : sales) {
    counts.merge(sale.product(), 1, Integer::sum);
}
~~~

**counts** trả số giao dịch mỗi sản phẩm; **totalByProduct** trả tổng số lượng sản phẩm bán. Hai con số không giống nhau trong dữ liệu có quantity khác 1.

### Chọn kiểu số đúng

- **Integer::sum** đơn giản cho tần suất không quá lớn, nhưng int có thể tràn.
- **Long::sum** có phạm vi lớn hơn; long vẫn có thể tràn nếu số liệu vượt giới hạn.
- Với giá trị tiền tệ yêu cầu thập phân chính xác, **BigDecimal::add** phù hợp hơn cộng double nhị phân.

~~~java
Map<String, BigDecimal> revenue = new HashMap<>();

revenue.merge(
        "book",
        new BigDecimal("12.50"),
        BigDecimal::add);

revenue.merge(
        "book",
        new BigDecimal("2.25"),
        BigDecimal::add);

// Nội dung tương ứng: book -> 14.75
~~~

Mã trên cần import **java.math.BigDecimal**. Dùng constructor từ String để tránh đưa lỗi biểu diễn nhị phân của double vào dữ liệu tài chính. Nếu tính toán có quy tắc làm tròn, phải xác định quy tắc ở đúng bước nghiệp vụ.

## 7. Mẫu 3 — Ghép danh sách giá trị cùng khóa

Không phải tất cả bài toán merge đều là cộng số. Giả sử phải gộp danh sách kỹ năng của từng nhóm:

~~~text
dev: [java]
dev: [sql]
ops: [linux]

Kết quả: {dev=[java, sql], ops=[linux]}
~~~

Có thể dùng Map<String, List<String>> và một remappingFunction trả danh sách mới:

~~~java
Map<String, List<String>> tagsByTeam = new TreeMap<>();

tagsByTeam.merge("dev", List.of("java"), (oldList, newList) -> {
    List<String> result = new ArrayList<>(oldList);
    result.addAll(newList);
    return result;
});

tagsByTeam.merge("dev", List.of("sql"), (oldList, newList) -> {
    List<String> result = new ArrayList<>(oldList);
    result.addAll(newList);
    return result;
});
~~~

**List.of(...)** có từ Java 9. Với dự án chỉ dùng Java 8, thay bằng **Arrays.asList(...)** hoặc List được tạo bằng ArrayList. Ý nghĩa của **Map.merge** không thay đổi.

Vì ví dụ tạo **ArrayList mới** khi có va chạm khóa nên không sửa trực tiếp danh sách oldList. Đây là lựa chọn dễ hiểu khi đầu vào có thể là danh sách không sửa được hoặc danh sách còn được tham chiếu ở nơi khác.

Cách gộp danh sách bằng **oldList.addAll(newList); return oldList;** chỉ an toàn khi bạn **chắc chắn** oldList có thể sửa, thuộc quyền sở hữu riêng và việc mutate đó không làm thay đổi đối tượng dùng chung ngoài ý muốn.

Nếu mục tiêu là **xây danh sách phần tử theo khóa từ một luồng dữ liệu**, **Collectors.groupingBy(...)** có thể thể hiện bài toán rõ hơn việc gọi merge nhiều lần. Chọn theo cấu trúc đầu vào và yêu cầu ownership.

## 8. Mẫu 4 — Hợp nhất hai Map theo khóa

Bài toán thường gặp là nhận hai bảng tổng hợp:

~~~java
Map<String, Long> january = Map.of(
        "apple", 2L, "orange", 5L);

Map<String, Long> february = Map.of(
        "apple", 3L, "pear", 1L);
~~~

Các Map được tạo bằng **Map.of** không sửa được (Java 9+), nên không gọi merge trực tiếp lên chúng. Tạo một Map kết quả có thể sửa rồi tổng hợp:

~~~java
Map<String, Long> combined = new TreeMap<>(january);

february.forEach((key, amount) ->
        combined.merge(key, amount, Long::sum));

// combined: {apple=5, orange=5, pear=1}
~~~

Trong ví dụ này:

- **january** và **february** không bị thay đổi cấu trúc.
- **combined** là TreeMap mới. Giá trị Long là bất biến nên không có rủi ro sửa nội dung Long từ hai phía.
- Kết quả dùng cộng số, một phép phù hợp cho việc gom theo khóa.
- Giả định các key và amount đều hợp lệ, amount không null. **merge không nhận value null**.

Phân biệt cách làm này với:

~~~java
january.putAll(february);
~~~

**putAll** ghi đè giá trị của khóa chung theo Map đầu vào, chứ **không cộng dồn**. Với Map.of ở trên, lệnh còn không được phép vì january không sửa được.

Nếu dữ liệu tháng được lưu trong **Map<String, MutableValue>**, new TreeMap<>(oldMap) chỉ sao chép cấu trúc, không tự deep-copy MutableValue. Phải xác định ownership của value trước khi chỉnh sửa nội dung bên trong.

## 9. Chương trình Java 17 chạy độc lập và đầu ra chính xác

Ví dụ sau minh họa toàn bộ các nhánh quan trọng: cộng dồn theo khóa, đếm bản ghi, kết quả với Collector, xử lý oldValue null, xóa mapping bằng remapper trả null, ghép danh sách và merge trên Map an toàn khi có concurrency.

Tạo tệp **MapMergeAggregationDemo.java**:

~~~java
import java.util.*;
import java.util.concurrent.*;
import java.util.function.*;
import java.util.stream.*;

public class MapMergeAggregationDemo {
    record Sale(String product, long quantity) {}

    static <T> List<T> concatCopy(List<T> left, List<T> right) {
        List<T> result = new ArrayList<>(left);
        result.addAll(right);
        return result;
    }

    public static void main(String[] args) {
        List<Sale> sales = List.of(
                new Sale("apple", 2),
                new Sale("orange", 5),
                new Sale("apple", 3),
                new Sale("pear", 1),
                new Sale("orange", 2));

        Map<String, Long> totals = new TreeMap<>();
        Map<String, Integer> counts = new TreeMap<>();

        for (Sale sale : sales) {
            totals.merge(sale.product(), sale.quantity(), Long::sum);
            counts.merge(sale.product(), 1, Integer::sum);
        }

        System.out.println("totals: " + totals);
        System.out.println("counts: " + counts);

        Map<String, Long> collected = sales.stream()
                .collect(Collectors.toMap(
                        Sale::product,
                        Sale::quantity,
                        Long::sum,
                        TreeMap::new));

        System.out.println("collected: " + collected);

        Map<String, Integer> nullable = new LinkedHashMap<>();
        nullable.put("key", null);
        int[] calls = {0};

        int first = nullable.merge("key", 5, (oldV, newV) -> {
            calls[0]++;
            return oldV + newV;
        });
        System.out.println(
                "first: " + first + ", remap calls: " + calls[0]);

        int second = nullable.merge("key", 2, (oldV, newV) -> {
            calls[0]++;
            return oldV + newV;
        });
        System.out.println(
                "second: " + second + ", remap calls: " + calls[0]);

        Integer removed = nullable.merge(
                "key", 1, (oldV, newV) -> null);
        System.out.println("removed: " + removed
                + ", contains key: " + nullable.containsKey("key"));

        Map<String, List<String>> tags = new TreeMap<>();
        tags.merge("dev", List.of("java"),
                MapMergeAggregationDemo::concatCopy);
        tags.merge("dev", List.of("sql"),
                MapMergeAggregationDemo::concatCopy);
        tags.merge("ops", List.of("linux"),
                MapMergeAggregationDemo::concatCopy);

        System.out.println("tags: " + tags);

        ConcurrentMap<String, Integer> concurrent =
                new ConcurrentHashMap<>();

        IntStream.range(0, 1000).parallel()
                .forEach(i ->
                        concurrent.merge("hits", 1, Integer::sum));

        System.out.println(
                "concurrent hits: " + concurrent.get("hits"));
        System.out.println("sales unchanged: " + sales.size());
    }
}
~~~

Lệnh biên dịch/chạy với JDK 17+:

~~~bash
javac MapMergeAggregationDemo.java
java MapMergeAggregationDemo
~~~

**Stdout đã kiểm chứng:**

~~~text
totals: {apple=5, orange=7, pear=1}
counts: {apple=2, orange=2, pear=1}
collected: {apple=5, orange=7, pear=1}
first: 5, remap calls: 0
second: 7, remap calls: 1
removed: null, contains key: false
tags: {dev=[java, sql], ops=[linux]}
concurrent hits: 1000
sales unchanged: 5
~~~

### Đọc kết quả

1. **totals** cộng các quantity bằng Long::sum. apple có **2 + 3 = 5**, orange có **5 + 2 = 7**, pear có 1.
2. **counts** đếm số dòng Sale theo product, nên apple và orange đều có **2** dòng, pear có 1.
3. **collected** dùng **Collectors.toMap** để nhận cùng Map tổng hợp mà không tự viết vòng lặp cập nhật.
4. **first** chứng minh khi key đã có nhưng gắn null, merge đặt **5** trực tiếp và remapper được gọi **0 lần**.
5. **second** gộp old=5 với incoming=2, tạo 7; bộ đếm remapper tăng thành 1. Bộ đếm chỉ để quan sát cách gọi tuần tự trong demo.
6. **removed** trả null và key bị xóa, thể hiện **null từ remapper = remove mapping**.
7. **tags** ghép danh sách theo khóa. Mã tạo List mới trong hàm concatCopy, không dựa vào việc List cũ có sửa được.
8. **concurrent** sử dụng **ConcurrentHashMap.merge**. Cả 1.000 lần tăng cùng khóa đều góp một lần vào kết quả cuối **1000** do merge được thực hiện atomically theo hợp đồng của ConcurrentHashMap.
9. **sales unchanged** cho thấy vòng lặp và Stream chỉ đọc danh sách Sale; các Map kết quả được tạo riêng.

**Lưu ý:** Lambda **forEach** trong phần ConcurrentHashMap có chủ đích cập nhật một Map thread-safe khác với nguồn IntStream. Điều đó khác với side effect vào **HashMap** dùng chung hoặc sửa chính nguồn đang được Stream duyệt; không xem đây là mẫu mặc định cho mọi pipeline. Nếu muốn kết quả tổng hợp trực tiếp từ một Parallel Stream mà không quản lý Map chia sẻ, dùng **Collectors.toConcurrentMap** như phần sau.

## 10. Kết hợp Map.merge với Stream và Collectors.toMap

**Map.merge** là một phương thức cập nhật trên Map đã có. **Collectors.toMap(...)** là cách thu thập phần tử Stream thành một Map mới. Chúng liên quan nhưng không giống nhau về **chỗ xảy ra cập nhật** và **quyền sở hữu kết quả**.

Để tổng hợp quantity từ một Stream<Sale>:

~~~java
Map<String, Long> totals = sales.stream()
        .collect(Collectors.toMap(
                Sale::product,
                Sale::quantity,
                Long::sum,
                TreeMap::new));
~~~

Bốn tham số của Collector:

- **keyMapper**: tạo khóa, ở đây **Sale::product**.
- **valueMapper**: tạo giá trị, ở đây **Sale::quantity**.
- **mergeFunction**: xử lý nhiều phần tử tạo ra cùng khóa, ở đây **Long::sum**.
- **mapFactory**: tạo Map đích, ở đây **TreeMap::new** cho thứ tự khóa xác định.

Nếu dùng overload **toMap(keyMapper, valueMapper)** mà có hai phần tử tạo cùng khóa, Collector sẽ báo lỗi duplicate key thay vì tự hiểu rằng cần cộng các quantity.

~~~java
// Với sales có nhiều dòng apple, đoạn sau sẽ lỗi duplicate key:
// sales.stream().collect(Collectors.toMap(
//         Sale::product, Sale::quantity));
~~~

Không nhầm với **Collectors.groupingBy**:

~~~java
Map<String, Long> quantities = sales.stream()
        .collect(Collectors.groupingBy(
                Sale::product,
                TreeMap::new,
                Collectors.summingLong(Sale::quantity)));
~~~

Ở đây **groupingBy** phân nhóm theo product và downstream **summingLong** tính tổng của từng nhóm. Nó cho cùng đại lượng tổng quantity, nhưng thể hiện mô hình "phân nhóm rồi tổng hợp" thay vì "Map các giá trị rồi merge khi khóa trùng".

### Chọn cách nào?

| Trường hợp | API thường rõ ràng |
| --- | --- |
| Đang duy trì một Map tích lũy trong vòng lặp | Map.merge |
| Cần thêm một phần dữ liệu vào Map đang sở hữu | Map.merge |
| Có Stream nguồn, muốn thu một Map<K,V> mới và giải quyết khóa trùng | Collectors.toMap với mergeFunction |
| Có Stream nguồn và muốn tính count/sum/average mỗi nhóm | groupingBy với downstream collector |
| Muốn Map<K,List<T>> từ Stream | groupingBy(classifier) |
| Muốn Map concurrent từ Parallel Stream khi phù hợp | toConcurrentMap hoặc groupingByConcurrent |

Không dùng **toMap** rồi gọi **Map.merge** lại trên cùng dữ liệu chỉ vì thấy cả hai có từ "merge". Chọn đúng điểm phát sinh kết quả để tránh cộng hai lần.

## 11. Map.merge khác gì putIfAbsent, compute và computeIfAbsent?

| Phương thức | Lúc nào gọi hàm tính toán? | Dùng tốt khi |
| --- | --- | --- |
| **put(key, value)** | Không có hàm gộp | Muốn ghi đè giá trị cũ |
| **putIfAbsent(key, value)** | Không có hàm gộp | Chỉ đặt value khi key chưa có giá trị khác null |
| **merge(key, value, remapper)** | Khi oldValue khác null | Thêm mới hoặc kết hợp old và incoming |
| **compute(key, remapper)** | Gọi remapper với key và oldValue (có thể null) | Cần key để tính mới hoặc cần xử lý cả absent theo logic riêng |
| **computeIfAbsent(key, mapper)** | Khi key chưa có giá trị khác null | Khởi tạo giá trị một lần theo khóa, ví dụ tạo container |
| **computeIfPresent(key, remapper)** | Khi key đang có giá trị khác null | Chỉ cập nhật khóa đang có dữ liệu |
| **replaceAll(function)** | Áp dụng cho các entry hiện có | Biến đổi những giá trị đã có; không thêm key mới |

Ví dụ khi cần khởi tạo danh sách theo khóa:

~~~java
Map<String, List<String>> groups = new HashMap<>();

groups.computeIfAbsent("dev", key -> new ArrayList<>())
        .add("java");
groups.computeIfAbsent("dev", key -> new ArrayList<>())
        .add("sql");
~~~

Kết quả dev có List [java, sql]. Đây là cách ngắn gọn để tạo List mỗi khóa rồi bổ sung phần tử, **khi Map thuộc quyền quản lý của code, List được phép sửa và không truy cập đồng thời thiếu đồng bộ**.

Với **merge**, ta có thể chuyển một List mới vào mỗi lần và dùng remapper để ghép. Với **computeIfAbsent**, ta chủ yếu quan tâm tạo giá trị khi vắng mặt; lời gọi add xảy ra trên List nhận được, không phải trong chính Map.merge.

### Vì sao getOrDefault có thể không thay cho merge?

~~~java
Map<String, Integer> map = new HashMap<>();
map.put("A", null);

// map.getOrDefault("A", 0) là null chứ không phải 0.
// Unboxing để cộng 1 sẽ ném NullPointerException.

map.merge("A", 1, Integer::sum); // A=1
~~~

**getOrDefault** không mặc nhiên coi một mapping hiện hữu có value null là "absent". Merge có quy tắc riêng với oldValue null.

## 12. Null, hàm gộp trả null và ngoại lệ

### 12.1. value tham số thứ hai không được null

~~~java
Map<String, String> map = new HashMap<>();

// Sai: value truyền vào merge không được null.
// map.merge("key", null, String::concat);
~~~

Ngay cả HashMap có thể chứa null value, **Map.merge** vẫn yêu cầu **incoming value khác null**. Trường hợp này gây **NullPointerException**.

### 12.2. Trả null từ remapper có nghĩa là xóa khóa

~~~java
Map<String, Integer> map = new HashMap<>();
map.put("A", 10);

Integer result = map.merge(
        "A", 1,
        (oldValue, incomingValue) -> null);

// result == null, map không còn key A.
~~~

Nếu bài toán muốn **giữ khóa với value null**, không thể dùng remapper trả null để biểu diễn điều đó; hãy chọn API/phương án khác phù hợp với Map cho phép null.

### 12.3. Map không phải loại nào cũng chấp nhận null key/value

- **HashMap** cho phép một null key và các null value; merge vẫn cấm tham số incoming value null.
- **ConcurrentHashMap** không cho phép null key và null value.
- **Map.of(...)** (Java 9+) và **Map.copyOf(...)** (Java 10+) tạo Map không sửa được, cấm null key/value. Gọi merge lên chúng không phải cách hợp lệ để tích lũy.

### 12.4. Remapper ném exception

Nếu remapper ném exception không kiểm tra, **merge không cập nhật mapping thành giá trị gộp mới** theo hợp đồng. Nhưng nếu remapper tự sửa một đối tượng mutable bên trong Map rồi ném lỗi, thay đổi side effect đó không tự rollback.

Để dễ kiểm thử và an toàn hơn, viết remapper như **Integer::sum**, **Long::sum**, **BigDecimal::add**, hoặc một hàm gộp thuần trả kết quả mới.

## 13. Thread safety: Map.merge không tự động an toàn với mọi Map

**Map.merge** là phương thức của interface Map. Hợp đồng mặc định **không bảo đảm atomicity hay synchronization** khi nhiều thread thao tác đồng thời. Do đó đoạn code:

~~~java
Map<String, Integer> counts = new HashMap<>();

IntStream.range(0, 1000)
        .parallel()
        .forEach(i ->
                counts.merge("hits", 1, Integer::sum));
~~~

là **phản ví dụ không an toàn**: HashMap không hỗ trợ nhiều cập nhật đồng thời theo cách này. Có thể mất lần cập nhật, gây trạng thái không nhất quán hoặc biểu hiện lỗi khác. Đừng suy ra rằng một lời gọi merge là atomic chỉ vì nó gói gọn trong một method.

### ConcurrentHashMap.merge có hợp đồng riêng

~~~java
ConcurrentMap<String, Integer> counts =
        new ConcurrentHashMap<>();

IntStream.range(0, 1000)
        .parallel()
        .forEach(i ->
                counts.merge("hits", 1, Integer::sum));

// Sau khi terminal operation hoàn tất: counts.get("hits") == 1000.
~~~

**ConcurrentHashMap** ghi rõ thao tác merge được thực hiện **atomically** đối với mỗi lời gọi. Vì vậy ví dụ này cho tổng 1000, miễn mỗi lời gọi merge thực hiện thành công và không có code khác thay đổi cùng key theo quy tắc khác.

RemappingFunction của ConcurrentHashMap nên **ngắn, đơn giản**, không thực hiện blocking I/O và **không cố chỉnh các mapping khác của cùng Map trong lúc tính toán**. Trong khi function chạy, các thao tác cập nhật khác có thể phải chờ; đưa lời gọi chậm hoặc đệ quy vào đây là sai thiết kế.

### Một cách thu kết quả khác: toConcurrentMap

Nếu bạn đã có Parallel Stream và chỉ muốn kết quả tổng hợp, không cần quản lý một Map mutable bên ngoài:

~~~java
ConcurrentMap<String, Long> counts =
        Stream.of("java", "map", "java")
                .parallel()
                .collect(Collectors.toConcurrentMap(
                        Function.identity(),
                        word -> 1L,
                        Long::sum));
~~~

Trong đoạn minh họa này cần import **Stream**, **Collectors**, **Function**, **ConcurrentMap**. Nội dung Map cuối là java=2 và map=1; **thứ tự duyệt key không được bảo đảm**.

Nếu một khóa được cập nhật rất nhiều với mức tranh chấp cao, **ConcurrentHashMap<String, LongAdder>** cùng **computeIfAbsent** rồi **increment()** là mô hình được tài liệu ConcurrentHashMap giới thiệu cho bảng tần suất. Đây là tối ưu chuyên biệt, cần đánh giá với workload và yêu cầu snapshot/read consistency. Không cần áp dụng LongAdder cho mọi bài toán Map nhỏ.

## 14. Điều kiện của phép gộp khi xử lý song song

Khi chạy **vòng lặp tuần tự**, các lời gọi merge xảy ra theo thứ tự mà chương trình duyệt dữ liệu. Ví dụ **String::concat** sẽ nối các đoạn theo đúng chuỗi thao tác được lập trình.

Khi dùng **Collectors.toMap** trong Parallel Stream, các kết quả cục bộ có thể được gộp theo nhiều cách. Với kết quả cần ổn định bất kể cách chia, **mergeFunction phải có tính kết hợp (associative)**. Nếu yêu cầu kết quả không phụ thuộc việc hoán vị phần tử của nguồn unordered, còn cần quan tâm tới tính giao hoán hoặc quy tắc sắp thứ tự riêng.

~~~text
Kết hợp:  (a ⊕ b) ⊕ c = a ⊕ (b ⊕ c)
Giao hoán: a ⊕ b = b ⊕ a
~~~

**Long::sum** phù hợp về cách nhóm theo số học kiểu long của Java (dù vẫn có thể tràn so với tổng toán học mong muốn). **Phép trừ** không kết hợp:

~~~text
(10 - 5) - 2 = 3
10 - (5 - 2) = 7
~~~

Vì vậy không dùng **(oldValue, incoming) -> oldValue - incoming** làm mergeFunction của collector song song nếu kết quả phải độc lập với cách phân chia.

**String::concat** là phép kết hợp nhưng không giao hoán: **"ab" + "cd"** khác **"cd" + "ab"**. Nếu yêu cầu thứ tự chuỗi, hãy giữ một nguồn/collector có bảo đảm encounter order phù hợp. Với các phép collector concurrent/unordered, đừng dựa vào thứ tự ngẫu nhiên mà runtime đưa ra.

**Một kết quả đúng trong một lần chạy parallel không chứng minh mọi cách chia đều đúng.** Hãy chứng minh tính kết hợp của phép gộp trên miền dữ liệu và kiểm thử nhiều bộ dữ liệu, trong đó có các khóa trùng, mảng rỗng và lượng bản ghi lớn.

## 15. Hiệu năng, chọn loại Map và thiết kế key

### Loại Map

- **HashMap**: phù hợp cho Map có thể sửa trong luồng tuần tự hoặc khi đã có đồng bộ bên ngoài; không hứa thứ tự duyệt key.
- **LinkedHashMap**: giữ thứ tự chèn key khi dùng chế độ mặc định; phù hợp khi báo cáo phải phản ánh thứ tự gặp khóa lần đầu trong một quá trình xử lý xác định.
- **TreeMap**: sắp xếp khóa theo comparator/thứ tự tự nhiên; thao tác có đặc điểm hiệu năng khác HashMap.
- **ConcurrentHashMap**: phù hợp với cập nhật đồng thời có contract rõ, không chấp nhận null key/value và không bảo đảm thứ tự duyệt key.
- **Map.of / Map.copyOf**: Map không sửa được; tạo một Map mutable trước khi cần merge.

Không chọn TreeMap chỉ để "làm merge đúng"; lựa chọn Map liên quan tới thứ tự, concurrent access, tính sửa đổi và quy mô dữ liệu.

### Thiết kế khóa

Các khóa được Map coi là cùng khóa theo quan hệ so sánh phù hợp với implementation. Với HashMap/LinkedHashMap, cần **equals/hashCode** nhất quán. Với TreeMap, comparator quyết định thứ tự và tính tương đương của khóa trong Map.

- Không sửa các trường của một object key nếu chúng ảnh hưởng đến equals/hashCode khi object đang được dùng làm key.
- Định nghĩa chính sách chuẩn hóa mã, chữ hoa/thường, khoảng trắng và giá trị thiếu.
- Không gộp hai mã khác nhau ngoài ý muốn chỉ vì một phép normalize quá mạnh.
- Với TreeMap, comparator không nhất quán với equals có thể làm Map có hành vi khác kỳ vọng của Map tổng quát; cân nhắc điều này trong thiết kế.

### Chi phí remapping

Một phép **Integer::sum** thường rất rẻ. Ngược lại, mỗi lần gộp hai List lớn bằng cách sao chép toàn bộ có thể tạo nhiều cấp phát. Với việc gom nhiều phần tử thành danh sách theo khóa, **groupingBy** hoặc **computeIfAbsent** với container được quản lý rõ thường dễ hiểu và tiết kiệm hơn trong ứng dụng tuần tự.

Không tối ưu theo cảm giác; đo trên số khóa, số va chạm khóa, kích thước value và phân bố tải thực tế.

## 16. Checklist triển khai tổng hợp theo khóa

**Bước 1 — Xác định kết quả:** cần số lần xuất hiện, tổng quantity, tổng tiền, danh sách chi tiết hay giá trị cuối cùng?

**Bước 2 — Xác định key:** key chuẩn hóa thế nào, có null hay khóa mutable không, Map nào định nghĩa equality/order?

**Bước 3 — Xác định value đầu vào:** value có được null không? Map.merge yêu cầu **value khác null**, kể cả trên HashMap.

**Bước 4 — Xác định remapper:** hàm nhận **oldValue** trước, **incomingValue** sau; có trả null để xóa mapping không? Có side effect hoặc khả năng ném lỗi không?

**Bước 5 — Xác định quyền sửa:** đang cập nhật Map có sẵn hay tạo Map mới từ Stream? Nếu Map là view hoặc unmodifiable, đừng gọi mutator.

**Bước 6 — Xác định concurrency:** code tuần tự dùng HashMap có thể phù hợp; nhiều thread cập nhật phải dùng cấu trúc/cơ chế concurrent có contract rõ hoặc Collector phù hợp.

**Bước 7 — Xác định giới hạn số:** int/long có thể overflow; tổng tiền có yêu cầu chính xác thập phân; String nối có cần thứ tự?

**Bước 8 — Kiểm thử ca biên:** key mới, key đã có, key gắn null, remapper trả null, key trùng nhiều lần, collection rỗng, Map không sửa được, va chạm khóa trong Stream parallel.

**Bước 9 — Đo tải thực:** quan sát số khóa, mức contention vào một key, GC khi gộp List, chi phí sắp xếp TreeMap và khả năng mở rộng.

## 17. Luyện tập có lời giải

### Bài 1 — Tính tần suất từ

Đầu vào: **["a", "b", "a", "a"]**. Hãy dùng merge.

~~~java
Map<String, Integer> counts = new HashMap<>();
for (String word : Arrays.asList("a", "b", "a", "a")) {
    counts.merge(word, 1, Integer::sum);
}
// Nội dung: a=3, b=1
~~~

**Giải thích:** key mới nhận 1; key đã có nhận oldValue + 1. Không dùng put(word, 1) vì nó chỉ ghi đè.

### Bài 2 — Thêm dữ liệu vào Map nhưng không sửa Map nguồn

Giả sử **oldTotals** và **newTotals** đều là Map<String, Long> với key và value hợp lệ, khác null:

~~~java
Map<String, Long> result = new HashMap<>(oldTotals);
newTotals.forEach((key, value) ->
        result.merge(key, value, Long::sum));
~~~

**Giải thích:** result là Map mới về mặt cấu trúc. Các giá trị Long là bất biến. Hai Map đầu vào không bị gọi mutator; trường hợp value là object mutable phải đánh giá thêm shallow copy.

### Bài 3 — Xử lý key đã có nhưng value null

~~~java
Map<String, Integer> map = new HashMap<>();
map.put("x", null);
map.merge("x", 4, (oldValue, value) -> oldValue + value);
~~~

**Đáp án:** sau lời gọi, **map.get("x") == 4**. Remapper không được gọi vì oldValue là null.

### Bài 4 — Tại sao remapper trả null làm mất key?

~~~java
Map<String, Integer> map = new HashMap<>();
map.put("x", 7);
map.merge("x", 1, (oldValue, value) -> null);
~~~

**Đáp án:** Map không còn mapping "x". Theo hợp đồng merge, null từ remapper là **remove**, không phải lưu key với value null.

### Bài 5 — Dùng Stream tính tổng per key

~~~java
Map<String, Long> totals = sales.stream()
        .collect(Collectors.toMap(
                Sale::product,
                Sale::quantity,
                Long::sum,
                TreeMap::new));
~~~

**Đáp án:** keyMapper xác định product, valueMapper xác định quantity, mergeFunction xử lý key trùng, mapFactory tạo TreeMap. Nếu thiếu mergeFunction và xuất hiện cùng product nhiều lần, overload toMap hai tham số sẽ báo duplicate key.

### Bài 6 — Có nên dùng HashMap.merge trong parallelStream.forEach?

**Đáp án:** Không nếu Map được cập nhật đồng thời mà không có bảo đảm đồng bộ. HashMap không bảo đảm an toàn. Có thể chọn **ConcurrentHashMap.merge** hoặc thiết kế Stream thu kết quả qua **Collectors.toConcurrentMap** nếu đúng nhu cầu.

### Bài 7 — Tại sao không gộp bằng phép trừ trong collector song song?

**Đáp án:** Phép trừ không kết hợp. Hai cách nhóm **(10 - 5) - 2 = 3** và **10 - (5 - 2) = 7** không bằng nhau, nên không bảo đảm cùng kết quả khi runtime phân chia và ghép dữ liệu khác nhau.

### Bài 8 — Map.of có thể dùng làm Map tích lũy không?

~~~java
Map<String, Integer> map = Map.of("a", 1);
// map.merge("a", 1, Integer::sum);
~~~

**Đáp án:** không. **Map.of** tạo Map không sửa được (Java 9+); gọi merge như mutator không được hỗ trợ. Nếu cần sửa, tạo **new HashMap<>(map)** trước.

## 18. Ghi nhớ

1. **Map.merge(key, value, remapper)** thêm giá trị nếu oldValue null/absent, hoặc gộp **oldValue** và **incomingValue** khi oldValue khác null.
2. **Tham số incoming value không được null.** Nếu **remapper trả null**, mapping bị xóa.
3. **Map.merge sửa chính Map** nhận lời gọi và trả **V** mới hoặc null, không tự tạo Map kết quả khác.
4. **put chỉ ghi đè**; **putIfAbsent chỉ thêm khi chưa có giá trị**; **compute/computeIfAbsent** phục vụ những mô hình tính toán khác. Chọn API đúng ngữ nghĩa.
5. **Cộng dồn theo khóa** dùng Integer::sum, Long::sum hoặc BigDecimal::add với kiểu số phù hợp và kiểm soát tràn/làm tròn.
6. **Collectors.toMap** có mergeFunction để giải quyết key trùng khi xây Map mới từ Stream; **groupingBy** thuận tiện cho tổng hợp thống kê theo nhóm.
7. **HashMap.merge không tự động thread-safe**; **ConcurrentHashMap.merge** có bảo đảm atomic theo API. Trong Parallel Stream, có thể dùng toConcurrentMap khi cần kết quả concurrent.
8. **Phép gộp phải phù hợp với cách chia trong parallel reduction**, đặc biệt tính kết hợp. Không dùng phép trừ hay side effect để suy kết quả nhất quán.
9. Làm rõ ownership của Map/value, null, thứ tự key, tính bất biến của key, contention và yêu cầu hiệu năng.
