# Generics, Type Inference, and Cases That Only Fail When Recompiling

In a long-lived Java project, an already-compiled artifact may still run in the current environment, yet the source code fails to compile when upgrading the compiler or updating libraries. One common group of causes lies in generic types, type inference, and changes in API signatures.

Generics are checked primarily at compile time and implemented using type erasure. Therefore, two API versions may keep the same method descriptor at the JVM level while differing in the generic signature used by the compiler. An old binary may sometimes still link, while old source code is no longer valid when recompiled. Conversely, a generic change can also alter the erasure and cause an actual linkage error.

This lesson presents how to read generic signatures, understand type inference, identify situations that only surface when recompiling, and investigate root causes based on evidence. This is part of the source compatibility examination in Java Advance Compatibility Migration.

## 1. Three Compatibility Layers to Distinguish

When a library or compiler changes, answer three questions separately:

1. **Source compatibility:** does the current source code compile with the new compiler and API?
2. **Binary compatibility:** does previously generated bytecode link with the new classes and methods?
3. **Behavioral compatibility:** after linking, does the program continue to process data and produce correct results?

The answers to all three cannot be inferred from a single successful build or a single successful run.

For example, the old library declares:

```java
package com.example;

import java.util.List;

public interface Registry {
    List findAll();
}
```

Client usage:

```java
Registry registry = obtainRegistry();
List<Integer> ids = registry.findAll();
```

Because the method returns a raw `List`, the compiler may accept the assignment and emit an unchecked conversion warning. The new library version declares:

```java
public interface Registry {
    List<String> findAll();
}
```

When recompiling, `List<String>` cannot be assigned to `List<Integer>`, so the source fails. However, the JVM descriptor of the method in both versions remains:

```text
findAll:()Ljava/util/List;
```

Generic information is stored in the `Signature` attribute of the class file, while the erased descriptor is used by the JVM for method linkage. Because the descriptor has not changed, the old binary may still be able to call the new method. However, if the new library returns `String` while the old client reads elements and casts them to `Integer`, the program may encounter a `ClassCastException`.

This example shows that a generic change can break source compatibility without breaking binary linkage, yet still cause behavioral errors.

## 2. Generics and Type Erasure

### 2.1. Purpose of Generics

Generics allow expressing data types and type constraints in an API:

```java
List<String> names = new ArrayList<>();
names.add("Mai");
String first = names.get(0);
```

The compiler checks element types at compile time. `List<String>` and `List<Integer>` are not two separate runtime classes; both are backed by `java.util.List`.

### 2.2. How Type Erasure Works

During compilation, the compiler erases type parameters according to the main rules:

- An unbounded type parameter is replaced with `Object`.
- A bounded type parameter is replaced with the first bound type.
- A parameterized type such as `List<String>` is erased to the raw type `List`.
- The compiler may insert casts at the call site and generate bridge methods to preserve dispatch rules after erasure.

Example:

```java
public static <T> T identity(T value) {
    return value;
}
```

The descriptor after erasure of the method accepts and returns `Object`:

```text
identity:(Ljava/lang/Object;)Ljava/lang/Object;
```

If the method has a bound:

```java
public static <T extends Number> T normalize(T value) {
    return value;
}
```

The erased type of `T` is `Number`, so the descriptor uses `Number` instead of `Object`.

### 2.3. Descriptor and Generic Signature

In a class file, it is necessary to distinguish:

| Component | Role |
| --- | --- |
| JVM descriptor | Represents parameter types and return type after erasure; used for bytecode linkage. |
| `Signature` attribute | Preserves type parameter, wildcard, and generic type information for use by the compiler, reflection, and metadata-reading tools. |

Example:

```java
public interface Cache {
    <T> T get(String key);
}
```

The erased descriptor is:

```text
(Ljava/lang/String;)Ljava/lang/Object;
```

If the API changes to `Object get(String key)`, the descriptor stays as above, but the generic signature has changed. An old client with the statement `String value = cache.get("name");` may fail to recompile because the compiler only sees the return type `Object`.

When comparing two library versions, comparing only method names and descriptors is not enough. Both the `Signature` attribute and the type contract visible to source clients must also be examined.

### 2.4. Bridge Methods

The compiler may generate bridge methods to preserve polymorphism after erasing generic types. Example:

```java
class Node<T> {
    public void set(T value) { }
}

class IntegerNode extends Node<Integer> {
    @Override
    public void set(Integer value) { }
}
```

At the source level, `IntegerNode.set(Integer)` overrides the specialized generic method. After erasure, the superclass signature uses `Object`, while the subclass method uses `Integer`. The compiler may generate a bridge method accepting `Object`, checking/casting the type, and forwarding to `set(Integer)`.

When investigating linkage errors or override behavior, remember that bytecode may contain synthetic methods (`synthetic`) that source code does not show directly. `javap -v` helps inspect flags and compiler-generated methods.

## 3. How the Compiler Performs Type Inference

### 3.1. Inferring Type Arguments of Generic Methods

Callers do not always write type arguments explicitly. The compiler builds constraints from argument types, the target type, and the method signature, then solves for a suitable solution.

```java
static <T> T first(List<T> values) {
    return values.get(0);
}

String name = first(Arrays.asList("Lan", "Minh"));
```

The compiler infers `T` to be `String`. It can be written explicitly to clarify intent:

```java
String name = MyUtils.<String>first(Arrays.asList("Lan", "Minh"));
```

If the call fails to compile, trying an explicit type argument can help identify which constraint is not satisfied. This is a diagnostic technique; if the new API no longer has the corresponding generic method, this syntax cannot restore the old contract.

### 3.2. Target Typing

A target type is the type that an expression must conform to in its usage context. The target type can participate in the inference process:

```java
List<String> names = Collections.emptyList();
```

`Collections.emptyList()` is a generic method. The target type `List<String>` helps the compiler choose `String` as the type argument.

Target typing also appears with lambdas and method references:

```java
Function<String, Integer> length = value -> value.length();
```

The parameter type of `value` is inferred from the target functional interface. If the API changes overloads or the target type, the lambda expression may resolve differently or become ambiguous.

### 3.3. Diamond Operator

The diamond operator allows inferring type arguments when constructing a generic object:

```java
Map<String, List<Integer>> index = new HashMap<>();
```

The compiler uses the target type to infer the type of `HashMap`. If the expression is moved to another context, such as passed across multiple overloads or assigned to a variable with a broader type, the inference result may change.

### 3.4. Wildcards and Capture Conversion

Wildcards describe flexible element types:

```java
void printNumbers(List<? extends Number> values) {
    for (Number value : values) {
        System.out.println(value);
    }
}
```

`? extends Number` allows passing lists of subtypes of `Number`, but an arbitrary `Integer` cannot be added because the concrete element type is unknown.

With `? super Integer`, an `Integer` can be added to the list, but when reading, only `Object` can be guaranteed if no other information is available.

Capture conversion creates a representative type for an unknown wildcard. A generic helper often helps the compiler maintain the relationship between reads and writes:

```java
static void swapFirstTwo(List<?> values) {
    swapCaptured(values);
}

private static <T> void swapCaptured(List<T> values) {
    T first = values.get(0);
    values.set(0, values.get(1));
    values.set(1, first);
}
```

When the API's generic signature changes, the capture relationship inferred by the compiler may no longer be the same as before.

## 4. Generic Changes That Can Cause Source Compilation Failures

### 4.1. Raw Types Replaced by Parameterized Types

Old API:

```java
List findAll();
```

New API:

```java
List<String> findAll();
```

A client assigning the result to `List<Integer>` may previously have compiled with an unchecked warning, but will fail when recompiling against the new API. The descriptor is still `()Ljava/util/List;`; it is the new generic signature that causes the compiler to reject it.

### 4.2. Generic Method Changed to a Concrete Return Type

Old API:

```java
<T> T read(String key);
```

New API:

```java
Object read(String key);
```

A client may previously have called `String title = store.read("title");` without casting. After the change, the source must use another typed API or convert the type explicitly. Erasure may still produce the same descriptor returning `Object`, but the source contract has weakened.

### 4.3. Changing Type Bounds

Bounds restrict permitted types and determine erasure. Example:

```java
// Before
<T extends Number> T normalize(T value);

// After
<T extends Integer> T normalize(T value);
```

Source passing `Double` or `Long` is no longer valid. Because the first bound changes from `Number` to `Integer`, the descriptor also changes, so old binaries may encounter linkage errors.

With an intersection bound, the first bound type determines erasure. Changing the first bound can change the descriptor even if the other bounds remain unchanged.

### 4.4. Adding Overloads Changes Overload Resolution

The compiler selects an overload based on argument types, generic inference, target types, and method resolution rules. When a library adds an overload, old calls may select a different method or become ambiguous.

Example:

```java
void register(Consumer<String> handler);
void register(Function<String, String> handler);

register(text -> text.trim());
```

A lambda expression can match both a functional interface returning `void` (if the body is a statement expression) and a functional interface returning a value. The compiler may not be able to select a unique overload. The target type can be clarified:

```java
Function<String, String> normalizer = text -> text.trim();
register(normalizer);
```

When an error appears after upgrading a library, inspect all overload candidates in the compiler message and cross-reference the API release notes.

### 4.5. Raw Types and Unchecked Warnings Promoted to Errors

```java
List values = new ArrayList();
values.add("text");
List<String> names = values; // unchecked conversion
```

The source may compile but generate warnings. If the build enables `-Werror` or a warning-as-error policy, the pipeline may fail. Distinguish genuine type errors from errors caused by build policy. Prioritize fixing raw types and confining unchecked casts to small adapters; do not suppress warnings broadly.

### 4.6. Generic Varargs and Heap Pollution

```java
static <T> List<T> merge(List<T>... inputs) {
    List<T> result = new ArrayList<>();
    for (List<T> input : inputs) {
        result.addAll(input);
    }
    return result;
}
```

Generic varargs may emit heap pollution warnings because the runtime array does not preserve full type arguments. Only use `@SafeVarargs` when the method is truly safe and satisfies language requirements. This annotation is a programmer guarantee, not an automatic check.

## 5. Non-Generic Causes of Recompilation Failures

Compile errors after migration are not always caused by changes in javac. Accompanying factors need to be checked:

- **Dependency versions changed:** the current compile classpath may contain a different generic API from the version used when generating the old binary.
- **Compiler plugins changed:** Maven Compiler Plugin, Gradle compiler tasks, or annotation processors may have changed configuration and code generation behavior.
- **Different source/release levels:** JDK 11 runs a new compiler; if `--release` or source level is not locked, the project may inadvertently use new language features/APIs.
- **Generated source:** code generated by JAXB, ORM metamodel generators, Lombok, or other processors may change with tool versions.
- **Warning flags changed:** `-Xlint`, `-Werror`, or CI configuration may turn old warnings into build errors.
- **Non-reproducible builds:** unlocked snapshot dependencies, repositories, or plugin versions can cause two compilations to use different inputs.

Therefore, when comparing JDK 8 and JDK 11, keep dependencies and build configuration stable before concluding an error is caused by the compiler.

## 6. Distinguishing Compiler Changes from API Changes

### 6.1. Record the Effective Build Configuration

Collect the following values:

| Information | To record |
| --- | --- |
| Compiler JDK | Vendor, version, and actual JDK path. |
| Source level | Java syntax version accepted by the compiler. |
| Target bytecode | Version of generated class files. |
| Release API | Platform API that source code is allowed to use. |
| Compile classpath | Dependency versions visible to the compiler. |
| Annotation processor | Versions and configuration of processors generating source/classes. |
| Compiler flags | `-Xlint`, `-Werror`, encoding, and other options. |

With JDK 11, `--release 8` helps compile against Java 8 APIs and bytecode within the scope supported by JDK 11. This is helpful during a transition period, but does not turn the JDK 11 compiler into the JDK 8 compiler and does not replace checking dependencies.

### 6.2. Check the Dependency Tree

Maven:

```bash
mvn dependency:tree -Dscope=compile
```

Gradle:

```bash
./gradlew dependencies --configuration compileClasspath
```

Compare compile dependencies between the baseline and the new build. If a library changed its generic signatures, identify the exact version before adjusting source code.

### 6.3. Inspect Descriptors and Generic Signatures with `javap`

```bash
javap -classpath path/to/library.jar -p -s -v com.example.Registry
```

Compare:

- Descriptors after erasure.
- `Signature` attribute.
- New or removed overloaded methods.
- Bridge methods and `ACC_SYNTHETIC` flags if present.

If descriptors changed, investigate binary linkage. If descriptors stayed the same while signatures changed, source recompilation can still fail. In both cases, check runtime data and behavior.

## 7. How to Handle Errors by Cause

### 7.1. If the Library's Generic API Changed

Read the migration guide and choose one of these approaches:

- Update source code to follow the new contract.
- Convert data at the adapter boundary.
- Use a different dependency version if the product must maintain source compatibility.
- Synchronously update independently compiled modules/clients.

Do not cast merely to silence the compiler without verifying actual data. Casting only shifts errors from compile time to runtime.

### 7.2. If Inference Cannot Determine the Type

Try:

- Writing explicit type arguments for generic methods.
- Creating intermediate variables with concrete types.
- Declaring functional interface types for lambdas/method references.
- Splitting complex expressions into smaller steps.
- Choosing an explicit overload according to the API documentation.

Example:

```java
Function<String, Integer> parser = text -> Integer.valueOf(text);
result = converter.convert(parser);
```

The `parser` variable fixes the target type before calling the overloaded API.

### 7.3. If Raw Types or Unchecked Warnings Are the Cause

Replace raw types with parameterized types matching the data. If data comes from a legacy API, validate and convert it in a centralized place. Only use `@SuppressWarnings` on small statements or methods under clear control.

### 7.4. If the Error Comes from Generated Source

Identify the code-generating processor/plugin, the JDK version supported by the processor, and the dependency versions referenced by generated source. Delete old generated outputs in the build directory via a clean build, then regenerate using locked configuration. Do not manually edit generated source if it will be overwritten on the next build; fix the source schema, annotation, template, or plugin instead.

## 8. Testing and Managing Compatibility After Compilation

After source compilation succeeds, check:

- Unit tests for generic APIs and actual data types.
- Integration tests with implementations and dependencies used in production.
- Overload, lambda, and method reference branches with business significance.
- Serialization/deserialization if generic types participate in data schemas.
- Compatibility between old binary clients and new libraries if plugins or clients are released independently.
- Runtime on the lowest still-supported JDK and the migration target JDK.

For public API libraries, separate source compatibility and binary compatibility checks should be maintained. API comparison tools can be used to detect signature changes, while still needing to read generic signatures and test behavior.

## 9. Template for Recording a Generics Issue in Migration

| Field | Content to record |
| --- | --- |
| Module/source | Module, file, and line where the error occurred. |
| Compiler | JDK vendor/version, source/release, and compiler flags. |
| Related API | Class, method, and before/after generic signatures. |
| Dependency | Artifact, version, and compile classpath. |
| Error message | Full diagnostics, overload candidates, and warnings. |
| Classification | Source incompatibility, warning-as-error, binary linkage, or runtime behavior. |
| Resolution | Fix source, update dependency, update processor, or adjust build policy. |
| Evidence | Build logs, `javap` output, test results, and related commits. |

Record attempted changes that did not resolve the error as well if they help identify the root cause. Do not bundle multiple unrelated generic errors into a single combined ticket if each error belongs to a different API or dependency.

## 10. Examination Completion Checklist

- [ ] Identified the compiler JDK, source/release, target bytecode, and warning flags.
- [ ] Compared compile classpaths between the baseline and migration build.
- [ ] Searched for raw types, unchecked conversions/casts, and generic varargs.
- [ ] Checked changes to generic return types, parameters, bounds, and overloads.
- [ ] Compared descriptors and `Signature` attributes of changed APIs.
- [ ] Inspected target typing, wildcard capture, lambdas, and method references at compile failure locations.
- [ ] Identified related annotation processors and generated source.
- [ ] Distinguished real compile errors from warnings promoted to errors.
- [ ] Tested runtime behavior to detect cast or data contract errors after compilation succeeded.
- [ ] Documented source/binary compatibility decisions for independent clients or plugins.

## 11. Conclusion in the Context of Java Compatibility Migration

Generics and type inference errors often appear only during recompilation because the compiler checks source code against current generic signatures and APIs, whereas old binaries typically link using post-erasure descriptors. Changes in dependencies, generic bounds, overloads, target typing, annotation processors, or warning policies can also cause compilation outcomes to differ from before.

When investigating, lock down build inputs, read full diagnostics, compare generic signatures with descriptors, and verify data behavior at runtime. This approach helps pinpoint whether an error belongs to the source contract, binary linkage, compiler configuration, or runtime behavior, while avoiding casts or suppressions to mask an API change that is not yet fully understood.
