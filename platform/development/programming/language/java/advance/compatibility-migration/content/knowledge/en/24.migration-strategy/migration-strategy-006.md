# Automating Mechanical Changes and Checking Generated Code Diffs

In **Java Advance Compatibility Migration**, many changes must be applied simultaneously across dozens of modules: updating imports, swapping annotations, migrating APIs, adjusting Gradle/Maven builds, regenerating REST clients from OpenAPI, regenerating Protobuf classes, or updating mappers generated by annotation processors. Done manually, teams easily miss sites, introduce inconsistencies, and lose significant time resolving massive diffs.

Automation reduces repetitive work, yet **an automatically generated change is not automatically correct**. Rewriting packages can silence compiler errors while leaving the application unable to detect JPA entities; changing a generator can update Jakarta imports while simultaneously changing serialization defaults; a rewrite tool can touch out-of-scope files or run a recipe that keeps mutating code on every invocation.

This lesson in the **Migration Strategy** chapter explains how to design **controlled mechanical edits**, choose AST-aware and recipe-based tools, manage **generated code** as the output of a process with well-defined inputs, inspect diffs along API and data contracts, and build reproducible CI gates. The goal is a migration where reviewers understand clearly **what changed, why it changed, how it was verified, and how it can be rolled back**.

## 1. How do mechanical changes differ from semantic changes?

A **mechanical change** is a transformation following a describable rule that applies repeatably across a well-defined scope.

Examples:

- Renaming types or imports once the successor API has been identified.
- Moving packages and updating references via IDE refactorings.
- Replacing known annotation types in modules that already carry the target dependency.
- Migrating a property key according to a verified migration guide.
- Updating build configuration from Java 11 to Java 17 per chosen policy.
- Converting API calls that have an exact one-to-one mapping.
- Regenerating clients/models when the input schema or templates change.

A **semantic change** alters behavior or contracts relied upon by clients, databases, the runtime, or business logic.

Examples:

- Changing request authentication and authorization logic.
- Swapping serializers and changing null, date/time, or unknown-field representation.
- Changing database transaction boundaries.
- Altering HTTP client retry behavior.
- Changing a Protobuf field number.
- Converting a synchronous API to asynchronous execution.

Most migrations combine **both parts**: tools rewrite source matching patterns, while engineers and tests verify semantic behavior.

### 1.1. A deceptively simple-looking edit

Before:

~~~java
import javax.persistence.Entity;
~~~

After:

~~~java
import jakarta.persistence.Entity;
~~~

This mechanical step is appropriate **if** the module has moved to Jakarta Persistence. Even then, it is not enough to prove Hibernate 6 scans the entity, repository queries still run, or the database schema stays unchanged.

### 1.2. Classify changes before selecting tools

| Change category | Example | Strategy |
|---|---|---|
| Clear mechanical | Exact rename of a known type | AST-aware recipe |
| Conditional mechanical | `javax.persistence` → `jakarta.persistence` | Module- and dependency-scoped recipe |
| Build configuration | Java release, plugin version, BOM | Script or structured config edit plus review |
| Semantic | Security matchers, retries, serialization | Design review plus contract tests |
| Generated source | DTOs, mappers, stubs, DB models | Edit input/generator then regenerate |
| Generated binary | Compiler AST/bytecode transformation | Bytecode/API inspection and runtime tests |

Do not collapse all these categories into a single raw text search-and-replace operation.

## 2. Why is automation especially important in Java upgrades?

Java migrations frequently involve sweeping changes:

1. Moving from JDK 8/11 to 17 or 21.
2. Replacing APIs removed from the JDK or tightly encapsulated.
3. Upgrading Spring Boot / Spring Framework and adopting Jakarta EE APIs.
4. Updating reflection, bytecode, testing, and instrumentation libraries.
5. Updating Gradle/Maven compilers, plugins, and dependency versions.
6. Regenerating source from OpenAPI, Protobuf, Avro, or database schemas.
7. Adjusting configuration files for target framework versions.
8. Replacing source code that calls deprecated APIs.
9. Updating CI/CD workflows and container images.
10. Verifying updated Java source and bytecode on the target runtime.

Because these changes repeat across multiple services, a **verified recipe** prevents different teams from patching identical issues in inconsistent ways.

Even so, automation pays off only when the **target version matrix** is clear. Running a Jakarta recipe against a module still on Spring Framework 5 creates broken code rather than solving anything.

## 3. Golden rule: source of truth and file ownership

Before editing any file, determine **whether that file is handwritten or generated**.

~~~text
Handwritten Java source
    |
    +--> IDE / OpenRewrite / manual review
    |
    v
Updated application source

Schema / template / annotations / DB metadata
    |
    +--> Generator / annotation processor
    |
    v
Generated Java / resources / bytecode
~~~

Rules:

- **Handwritten source:** can be refactored directly with appropriate tools.
- **Generated source:** edit the **schema, template, or generator config/version** first, then re-run the generator.
- **Generated bytecode/AST:** inspect compiler or processor behavior rather than expecting `.java` files to diff.
- **Build outputs:** avoid manual edits, which subsequent builds overwrite.

If you do not know who owns a file, investigate before running any rewrite.

### 3.1. Signs of generated files

Look for indicators such as:

- A `Generated by...` file header.
- The `@Generated` annotation.
- Paths like `build/generated` or `target/generated-sources`.
- Package conventions such as `client.generated`.
- Code-generation tasks configured in Gradle or Maven.
- Comments referencing an input schema or template.
- Files rewritten on every clean build.

Do not rely on a single clue alone: some generators emit no `@Generated` annotation, and teams sometimes copy generated source into regular source packages.

## 4. Two policies for storing generated code

### 4.1. Committing generated output to Git

Example:

~~~text
api/orders.yaml               <- source of truth
src/generated/java/           <- committed generated files
build.gradle                  <- generator configuration
~~~

The advantage is that pull requests expose direct diffs of generated DTOs and clients, and developers do not necessarily have to invoke the generator just to inspect the project.

The downside is repository bloat, stale outputs, or manual edits slipping in. CI should regenerate outputs and **compare them against the committed copies**.

### 4.2. Keeping generated output only in the build directory

Example:

~~~text
src/main/openapi/orders.yaml  <- source of truth
build/generated/openapi/      <- ignored build output
~~~

The advantage is cleaner Git diffs without machine-generated implementation noise. The downside is that ordinary Git diffs **cannot see** generated code changes, and CI must reproduce generation accurately.

Here, rely on snapshot comparisons, generated API reports, schema compatibility checks, or archived build artifacts so reviewers see what changed. Never treat an empty `git diff` as proof codegen is unaffected when generated outputs are gitignored.

### 4.3. Keep each module's policy explicit

One service may commit generated DTOs while another generates them solely during builds—both approaches can work, provided each module documents:

- Where original inputs reside.
- Tool and version producing the output.
- Output directory path.
- Whether output is committed to Git.
- Who owns review approval.
- Command or build task used to regenerate.
- CI criteria for failing on stale output.

## 5. Establish a baseline before automating

Any rewrite is meaningful only relative to a known starting state.

Record:

| Item | Contents |
|---|---|
| Git baseline | Commit/tag, clean working tree status |
| Java toolchain | Vendor/version, `--release` level |
| Build tool | Gradle/Maven wrapper and plugin versions |
| Dependency graph | Direct/transitive versions, BOMs |
| Generator | Tool, plugin, templates, and versions |
| Inputs | OpenAPI/proto/schema/annotations with checksums |
| Outputs | Pre-migration generated files or build artifacts |
| Behavior | Test counts, contract fixtures, integration baselines |
| Runtime | Container image, locale, timezone where relevant |
| Ownership | Approvers for API, data, and security changes |

Useful commands for inspecting repository state before running tools:

~~~bash
git status --short
git rev-parse HEAD
git diff --stat
~~~

A dirty working tree mixes automated edits with unrelated local changes. Always start batch rewrites from a clean branch and baseline commit.

## 6. Match the right tool to the change

| Tool | Strengths | Limitations |
|---|---|---|
| IDE Rename/Move refactoring | Understands symbols and imports in project | Requires a valid resolved project model |
| OpenRewrite | Structured recipes running across modules | Depends on recipe and tool compatibility |
| JavaParser / JDT | Custom AST transformations | Requires configuring type resolution carefully |
| Error Prone / Refaster | Compiler-aware pattern rewrites | Tied to javac/plugin versions |
| Structured XML/YAML edits | Schema-respecting config edits | May alter formatting or key ordering |
| Regex / text replacement | Literal strings over tight scope | Lacks type and semantic awareness |
| OpenAPI/protoc/jOOQ generators | Regenerates source from schemas | Output shifts with generator/toolchain versions |
| Manual review | Evaluates contracts and security | Time-consuming, yet indispensable |

Not every project needs OpenRewrite. A rename inside one small module is often safer via an IDE refactoring than writing a custom recipe. Conversely, updating thousands of call sites across many repositories justifies investing in tested recipes.

## 7. Why can regex break Javax/Jakarta migrations?

Consider a naive text rule:

~~~text
Replace all "javax." with "jakarta."
~~~

That blindly corrupts Java SE imports that remain valid:

~~~java
import javax.net.ssl.SSLContext;
import javax.crypto.Cipher;
import javax.sql.DataSource;
import javax.naming.InitialContext;
import javax.management.MBeanServer;
~~~

Those packages have no wholesale migration to `jakarta.*`.

Text find-and-replace can also alter:

- Reflection string literals.
- XML metadata.
- Comments and documentation.
- Generated test fixtures.
- Code inside modules intentionally still targeting the older stack.
- Unrelated packages sharing similar prefixes whose types differ.

**Never use prefix string replacement as an API migration mechanism.** Migrate distinct API groups intentionally with explicit preconditions.

### 7.1. Surveying candidates with ripgrep

~~~bash
rg -n 'javax\.(servlet|persistence|validation)\.' src
rg -n 'WebSecurityConfigurerAdapter|antMatchers' src
rg -n 'sun\.|jdk\.internal\.' src/main/java
~~~

Search matches are **candidates to classify**, never an instruction to rewrite every matched line.

## 8. What is AST-aware refactoring?

An AST (Abstract Syntax Tree) models program structure: import declarations, type references, annotations, method invocations, lambdas, class declarations, and more.

An AST-aware tool distinguishes:

~~~java
import javax.persistence.Entity;

@Entity
public class OrderEntity {
}
~~~

from:

~~~java
String doc = "javax.persistence.Entity";
~~~

Using type attribution, a recipe targets genuine type references instead of every text occurrence matching that string.

### 8.1. Limits of AST transformations

AST rewriting alone does not prove:

- HTTP endpoints keep proper authorization.
- Database schemas stayed intact.
- Protobuf wire formats remain compatible.
- Serializers handle null/date/time identically.
- Runtime provides the expected implementation of a new interface.

Thus **clean structural source conversion** and **valid behavioral migration** remain two separate milestones.

## 9. OpenRewrite recipe: a narrow example

OpenRewrite runs recipes over Java, build, and config files. Here is a minimal declarative recipe replacing one annotation type:

~~~yaml
type: specs.openrewrite.org/v1beta/recipe
name: com.example.migration.UseJakartaEntity
displayName: Use Jakarta Persistence Entity annotation
description: Replace the known Java EE Entity type.
recipeList:
  - org.openrewrite.java.ChangeType:
      oldFullyQualifiedType: javax.persistence.Entity
      newFullyQualifiedType: jakarta.persistence.Entity
~~~

This recipe **updates only one type reference**. It does not migrate all of JPA, upgrade Hibernate 6, or prove ORM entity scanning works.

Projects configured with the OpenRewrite Gradle plugin may provide:

~~~bash
./gradlew rewriteDryRun
./gradlew rewriteRun
~~~

Projects with the Maven plugin configured may provide:

~~~bash
mvn rewrite:dryRun
mvn rewrite:run
~~~

Exact task/goal names depend on plugin versions and build config—never assume they exist in every repository.

### 9.1. Dry-run first, then apply

Workflow:

1. Select exact plugin and recipe versions.
2. Run a dry run and review affected files.
3. Confirm nothing outside target scope is touched.
4. Apply the recipe on a migration branch.
5. Inspect both source diffs and dependency graph changes.
6. Compile and run tests per project workflow.
7. Run the recipe a second time to verify idempotency.
8. Commit source alongside exact recipe/version documentation.

### 9.2. Pin recipe versions

A recipe ID can remain identical while its implementation changes across releases. To keep migrations reproducible, record:

- Build tool wrapper version.
- OpenRewrite plugin version.
- Recipe artifact version.
- Active recipe names and execution order.
- JDK running the rewrite tool.
- Module paths processed.

Never cite a vague label like "latest recipe" as review evidence.

## 10. Design small, conditional recipes

A single monolithic recipe changing Java baseline, Spring Security, Hibernate, generated OpenAPI clients, and logging in one sweep yields an unreadable diff.

Split work cleanly:

~~~text
R1: Jakarta Persistence Java imports/types
R2: Jakarta Bean Validation in modules on the upgraded stack
R3: API method renames per migration guide
R4: Build configuration / JDK toolchain
R5: Cleanup of safe deprecated constructs
Manual: Security, transactions, schema, and protocols
Generated: Regenerate from new schemas/configs
~~~

For R1, the precondition should be "modules already adopting Jakarta Persistence managed by the target stack," not "every module in the monorepo."

### 10.1. Idempotency

Applying recipe `R` to source `S` should satisfy:

\[
R(R(S)) = R(S)
\]

Re-running a recipe must not keep adding annotations, toggling formatting back and forth, or duplicating code blocks. If a second run emits fresh diffs, review match preconditions or formatting stability.

**Idempotency does not prove correctness.** A broken rewrite that stabilizes produces an idempotent yet wrong result—tests and human review remain essential.

### 10.2. Recipe ordering

Sometimes recipe B matches only after recipe A updates a type. Consequently A → B and B → A may not yield identical results. Record exact execution ordering in the build configuration or migration runbook.

## 11. Mechanical JPA entity conversion example

Before:

~~~java
package com.example.orders;

import javax.persistence.Entity;
import javax.persistence.Id;
import javax.persistence.Table;

@Entity
@Table(name = "orders")
public class OrderEntity {

    @Id
    private Long id;
}
~~~

After:

~~~java
package com.example.orders;

import jakarta.persistence.Entity;
import jakarta.persistence.Id;
import jakarta.persistence.Table;

@Entity
@Table(name = "orders")
public class OrderEntity {

    @Id
    private Long id;
}
~~~

While the diff above can be generated automatically, declaring the migration complete still requires confirming:

- Jakarta Persistence API is present in the dependency graph.
- Hibernate/framework versions align.
- Entity scanning succeeds at runtime.
- Custom converters, listeners, and query APIs were migrated.
- SQL, sequence, and schema behaviors match expectations.
- Integration tests run against a representative database.

This illustrates **automating deterministic mechanics** while preserving human verification of semantics.

## 12. Changes requiring human semantic decisions

### 12.1. Spring Security 5 to 6

Moving from `WebSecurityConfigurerAdapter` to `SecurityFilterChain` is more than syntax. Review request matchers, authorization rule ordering, CSRF, session management, CORS, method security, and OAuth/JWT validation.

Never add `permitAll()` or disable CSRF merely to make builds or tests pass.

### 12.2. Date and time handling

Migrating `SimpleDateFormat` to `DateTimeFormatter` can alter parsing strictness, locale defaults, timezones, and error behavior. Validate with golden inputs covering boundary timestamps and daylight-saving transitions where relevant.

### 12.3. HTTP clients

Switching HTTP client libraries can alter default timeouts, redirect policies, connection pooling, TLS verification, and retry behavior. Even if recipes migrate method signatures cleanly, test network and failure integration behavior separately.

### 12.4. Serialization

Swapping JSON/XML libraries or changing generated DTOs can affect field names, optional/null representation, enum mapping, and wire compatibility. Here, **a tiny diff can trigger a major breaking change**.

## 13. Modeling generated code as a function

Generation can be modeled as:

\[
G(I,T,C,E)=O
\]

Where:

- `I`: input schemas, source files, annotations, or DB metadata.
- `T`: generator implementation and version.
- `C`: configuration flags, options, and custom templates.
- `E`: environment—JDK, OS, locale, timezone, filesystem.
- `O`: generated output.

For a generated diff to be intelligible, you must know **which inputs changed**.

Simultaneously changing the OpenAPI schema, upgrading the generator, switching JDKs, and reformatting outputs produces massive diffs where business contract changes disappear inside tool noise.

### 13.1. Vary one input at a time when possible

Example:

~~~text
Baseline:
  orders.yaml checksum A
  generator version X
  JDK 17
  templates checksum T

Candidate:
  orders.yaml checksum B
  generator version X
  JDK 17
  templates checksum T
~~~

The resulting diff should isolate the schema edit. If upgrading generator X → Y too, isolate that upgrade in a separate PR or commit to inspect tool-only diffs cleanly.

## 14. Common Java code-generation sources

| Technology | Input | Output | Diff risks |
|---|---|---|---|
| OpenAPI Generator | OpenAPI YAML/JSON | API clients, DTOs, server interfaces | HTTP contracts, annotations, nullability |
| protoc / gRPC | `.proto` | Message classes, service stubs | Field numbers, wire format, method signatures |
| Avro compiler | Avro schema | Records and serializers | Schema evolution, default values |
| jOOQ | Database schema | Table, record, and DAO classes | SQL types, naming, schema metadata |
| MapStruct | Mapper interfaces | Concrete mapper implementations | Null handling, nested mappings |
| JPA metamodel processors | Entity annotations | Static metamodel types | Javax vs. Jakarta package versions |
| QueryDSL processors | Domain/JPA models | Query Q-types | Processor classifier and API compatibility |
| JAXB / XJC | XSD schemas | Java XML models | XML namespaces and javax/jakarta bindings |
| Lombok | Annotations / AST | Compiler bytecode transformations | Compiler internals and bytecode behavior |

Know **which tool owns each generated artifact**. Never assume every generator writes `.java` files into the same directory.

## 15. Generated markers and the javax.annotation pitfall

When upgrading JDKs or Jakarta stacks, generators may emit:

~~~java
import javax.annotation.Generated;
~~~

In modern Java, distinguish carefully among:

- `javax.annotation.Generated` from Java EE / legacy annotations libraries.
- `javax.annotation.processing.Generated` from the standard Java SE annotation processing API.
- `jakarta.annotation.Generated` from Jakarta Annotations API.

Do not run a blanket regex replacing every variant with a single package name. Choose based on the generator, runtime, framework, and whether any tool actually inspects the annotation beyond metadata.

### 15.1. When generated code fails to compile

~~~text
error: package javax.annotation does not exist
~~~

Investigation steps:

1. Identify the generator or plugin emitting the import.
2. Check the generator's release compatibility and Java/Jakarta target support.
3. Update generator options, templates, or plugin version to a supported release.
4. Regenerate all outputs cleanly.
5. Inspect the diff and compile.
6. Never hand-edit hundreds of generated files while leaving the old generator emitting legacy imports.

A generator may **run cleanly on JDK 17 yet still emit source tied to older frameworks**. Build runtime compatibility and generated output target are two separate checks.

## 16. Control both generator inputs and outputs

OpenAPI example:

~~~text
src/main/openapi/orders.yaml
        |
        | Generator version + config + templates
        v
build/generated/openapi/
        +-- api/OrdersApi.java
        +-- model/OrderDto.java
        +-- ApiClient.java
~~~

If a DTO field needs changing, inspect the OpenAPI schema and contract rather than patching `OrderDto.java`.

Protobuf example:

~~~text
src/main/proto/orders.proto
        |
        | protoc + Java/gRPC plugins
        v
build/generated/source/proto/main/
        +-- java/...message classes
        +-- grpc/...service stubs
~~~

Before editing fields, verify field numbers, unknown fields, and backward compatibility rules prior to regenerating.

## 17. Generator determinism and build reproducibility

A generator is **deterministic** when identical inputs, toolchain, configuration, and controlled environment produce byte-identical outputs.

Common causes of unintended output drift:

- Embedded timestamps inside header comments.
- Dynamic generator or dependency versions.
- Changing JDK or annotation processor versions.
- Differing locales or timezones.
- Non-deterministic collection iteration order.
- Differing filesystem traversal ordering.
- CRLF vs. LF line endings.
- Unspecified character encoding.
- Unpinned custom templates.
- Stale incremental build caches.
- Multiple tasks writing into the same output directory.

### 17.1. Timestamp noise example

~~~diff
-// Generated at 2026-11-10 09:15:00
+// Generated at 2026-11-12 13:05:00
~~~

Disable **timestamp emission** via generator flags where supported instead of writing broad diff filters that could mask real contract changes.

### 17.2. Standardize the generation environment

Migrations requiring strict reproducibility can pin:

- JDK toolchain.
- Locale and timezone where code generation depends on them.
- UTF-8 file encoding.
- Build tool wrapper.
- Plugin and generator versions.
- Custom template versions/checksums.
- Input schema checksums.
- Formatting and line-ending policy.

`.gitattributes` helps standardize line endings for committed generated files. Still, avoid changing line-ending rules and schema inputs in the same PR so real diffs are not drowned out.

## 18. Workflow for comparing baseline and candidate generated outputs

~~~text
Baseline commit
    |
    +--> Pinned generator version
    |
    v
Output A
    |
    | Intentional schema/template/tool change
    v
Candidate commit/config
    |
    +--> Corresponding pinned generator
    |
    v
Output B
    |
    v
Diff A vs B
    |
    +--> Expected API changes
    +--> Template/tool-only changes
    +--> Formatting/noise
    +--> Unexpected/deleted files
    |
    v
Review + contract/integration tests
~~~

If baseline outputs cannot even be reproduced cleanly from baseline inputs, resolve determinism first—otherwise A-vs-B diffs mix generator environment bugs with intended migration edits.

## 19. Inspecting Git diffs in layers

Reference commands:

~~~bash
git status --short
git diff --stat
git diff --name-status
git diff HEAD -- src/main/java
git diff HEAD -- src/generated/java
~~~

`--stat` and `--name-status` highlight added, modified, deleted, or unexpected out-of-scope files. On multi-commit PRs, select the intended baseline branch or commit carefully.

### 19.1. Whitespace checks

~~~bash
git diff --check HEAD -- src/main/java src/generated/java
~~~

Flags basic whitespace mistakes in diffs. It validates neither Java semantics nor API contracts.

### 19.2. Word diffs

~~~bash
git diff --word-diff HEAD -- src/generated/java
~~~

Useful when imports or type references shift by a few tokens. Never skip standard line diffs though, since class structure, annotations, and deletions are easy to misread in word-diff view.

### 19.3. Ignore whitespace for triage only

~~~bash
git diff --ignore-space-change HEAD -- src/generated/java
~~~

Helps gauge how much of a diff is whitespace churn; **never use it as the sole review gate**, as subtle real edits can hide next to formatting changes.

## 20. Tracked, untracked, and ignored files

`git diff --exit-code HEAD -- path` checks tracked changes relative to `HEAD` but **does not flag new untracked files**.

When generated output is committed, also check:

~~~bash
git ls-files --others --exclude-standard -- src/generated/java
~~~

This lists untracked files not ignored by `.gitignore` inside that directory.

### 20.1. Example CI freshness gate

Unix-style shell snippet on a **clean checkout**:

~~~bash
set -eu

# Illustrative task; replace with the project's generator task.
./gradlew generateClientSources

# Tracked outputs must not differ if committed properly.
git diff --check HEAD -- src/generated/java
git diff --exit-code HEAD -- src/generated/java

# No new untracked outputs should exist.
if [ -n "$(git ls-files --others --exclude-standard -- src/generated/java)" ]; then
    echo "Generated files chưa được commit"
    exit 1
fi
~~~

Key considerations:

- Ensure `generateClientSources` actually exists and is wired cleanly.
- CI must start from a clean, known checkout state.
- `git diff HEAD` detects tracked modifications, including staged edits where applicable.
- Checking untracked files must be a distinct step.
- If the generated directory is gitignored, these Git checks **are insufficient**; compare build snapshots or artifacts instead.
- This gate proves committed files match generator output—it **does not prove** new APIs are compatible.

## 21. Diffing generated output kept only in build/

When generated files are not committed, preserve snapshots or artifacts across generation runs.

Example for Unix environments with `diff`:

~~~bash
./gradlew clean generateClientSources
cp -R build/generated/client /tmp/generated-run-a

# Same inputs and same toolchain.
./gradlew --rerun-tasks generateClientSources

diff -ru /tmp/generated-run-a build/generated/client
~~~

Purpose:

- Two runs with identical inputs verify **determinism**.
- Comparing baseline vs. candidate requires generating two snapshots from **two well-defined inputs or configurations**.
- `diff -ru` exits non-zero when differences exist; handle exit status appropriately in CI.
- On Windows PowerShell, use equivalent directory comparison tooling (`cp`/`diff` flags differ).
- If a generator does not wipe stale files automatically, clean the output directory first so obsolete files do not leak into snapshots.

### 21.1. Determinism does not guarantee correctness

A generator can deterministically produce broken source every time. Conversely, valid code evolves legitimately when schemas change intentionally. Pair **reproducibility checks with contract tests**.

## 22. Classify generated diffs by risk

| Diff category | Examples | Action required |
|---|---|---|
| Jakarta imports | `javax.validation` → `jakarta.validation` | Verify target stack alignment |
| Public APIs | Added/removed methods, altered parameter/return types | API/ABI review |
| Data models | Nullable → required, changed enum values, dropped fields | Contract/schema review |
| Wire formats | Protobuf numbers, XML/JSON property names | Cross-version compatibility tests |
| Runtime dependencies | Serializers, HTTP clients, annotation libraries | Behavioral and security review |
| SQL models | Changed column, type, or primary key | Database migration review |
| Generated comments | Timestamps, tool version headers | Suppress or isolate noise |
| Formatting | CRLF/LF, indentation | Separate from semantic edits |
| Deleted/renamed files | Vanished classes or endpoints | Explicit owner sign-off |
| Security-related metadata | Changed validation or auth annotations | Security review |

Changing **one Protobuf field number** can break far more clients than 10,000 lines of formatter whitespace edits. Never gauge diff risk by line count alone.

## 23. OpenAPI: generator diffs vs. schema diffs

Suppose you have:

~~~text
api/orders.yaml
      |
      v
OpenAPI Generator
      |
      +-- OrdersApi.java
      +-- OrderDto.java
      +-- ApiClient.java
~~~

Upgrading Spring Boot 2 → 3 may require migrating from Javax to Jakarta annotations.

Expected diff:

~~~diff
-import javax.validation.Valid;
-import javax.validation.constraints.NotNull;
+import jakarta.validation.Valid;
+import jakarta.validation.constraints.NotNull;
~~~

However, if the generator simultaneously produces:

~~~diff
-public Long getOrderId()
+public String getOrderId()
~~~

investigate schema, templates, and type mappings immediately. That signals a **breaking API change**, not harmless Jakarta migration churn.

### 23.1. Separate generator upgrades from schema changes

Recommended sequence:

1. Pin the generator and confirm baseline determinism.
2. Upgrade generator version/options while holding schemas constant.
3. Review the tool-only generated diff.
4. Apply intentional schema edits and regenerate.
5. Execute API and serialization contract suites.

Projects need not enforce that exact PR count rigidly, yet every category in a generated diff must have a clear explanation.

## 24. Protobuf/gRPC: never confuse field names with wire contracts

Example:

~~~proto
syntax = "proto3";

package example.orders;

message Order {
  string id = 1;
  int64 created_at_epoch_ms = 2;
}
~~~

Adding a field:

~~~proto
message Order {
  string id = 1;
  int64 created_at_epoch_ms = 2;
  string note = 3;
}
~~~

can be wire-compatible under Protobuf evolution rules, whereas **renumbering field 2 to 8** while keeping its field name silently breaks wire compatibility.

Verification checklist:

- Pin `protoc` and Java/gRPC plugin versions.
- Compare `.proto` edits alongside generated Java source.
- Never reuse deleted field numbers casually.
- Reserve retired numbers/names when needed.
- Verify unknown-field preservation and default values.
- Test old client ↔ new server and new client ↔ old server.
- Confirm gRPC service method names and status handling.

Upgrading `protoc` can create large code diffs with zero schema change; never mistake generator churn for wire-schema evolution.

## 25. Avro, JAXB, and XML code generation

### 25.1. Avro

Generated Avro classes depend on schema fields, defaults, unions, and logical types. During schema evolution, verify reader/writer schema compatibility explicitly rather than just compiling generated Java.

### 25.2. JAXB and Java/Jakarta

With newer JDKs, JAXB is no longer bundled in the JDK by default. Projects using XJC / XML Binding must match generator and runtime library implementations intentionally.

Confirm:

- Whether `javax.xml.bind.*` or `jakarta.xml.bind.*` matches the target runtime.
- Generator/XJC and runtime dependency versions.
- XML namespaces, elements, and attributes.
- Adapter/converter behavior.
- Golden XML marshal/unmarshal fixtures.

Never hand-patch hundreds of imports inside generated JAXB classes while leaving the old generator regenerating them.

## 26. jOOQ and database-generated code

Example:

~~~text
Versioned DDL / database schema
       |
       v
jOOQ generator
       |
       +-- Tables
       +-- Records / POJOs
       +-- DAOs
~~~

Output can change when:

- The underlying database schema genuinely migrates.
- JDBC driver or metadata resolution shifts.
- jOOQ generator version changes.
- Database dialect or engine version changes.
- Naming strategy changes.
- Catalog/schema filters change.
- Metadata query ordering is unstable.

### 26.1. Generate against a deterministic schema

Avoid running code generation directly against a drifting shared production database. Build the target schema from versioned migration scripts or pinned snapshots inside a reproducible environment first.

### 26.2. Review SQL and database semantics

Column types or ID generation shifts change generated POJOs—yet you must still verify ORM/SQL mappings, query plans, transactions, and database rollback safety.

## 27. MapStruct, QueryDSL, JPA metamodels, and processors

Annotation processors typically write generated sources to paths like:

~~~text
build/generated/sources/annotationProcessor/java/main/
target/generated-sources/annotations/
~~~

MapStruct example:

~~~java
@Mapper
public interface OrderMapper {
    OrderDto toDto(OrderEntity entity);
}
~~~

Generated mapper implementations can differ when upgrading MapStruct, changing compiler/JDK versions, altering Lombok integration, or tweaking null/default mapping strategies.

Review points:

- Null input handling.
- Nested object and collection mapping.
- Enum mapping behavior.
- Field renames and defaults.
- Date/time conversions.
- Whether generated code invokes different constructors or setters.
- Component model and dependency injection annotations.

QueryDSL and JPA metamodel processors may need **Jakarta Persistence**–compatible releases once entities move from `javax.persistence.*` to `jakarta.persistence.*`. Hand-editing generated `QOrder.java` never resolves processor version mismatches.

### 27.1. Lombok does not always emit source files

Lombok transforms the compiler AST directly rather than writing plain Java files under `build/generated`. Upgrading JDKs or Lombok requires checking compiler integration, emitted bytecode/API signatures, tests, and delombok diffs if your workflow uses delombok.

## 28. Build caches and incremental code generation

Build systems can wrongly skip generator tasks when inputs are modeled incompletely.

Typical causes:

- Imported OpenAPI fragments omitted from declared task inputs.
- Custom template directories omitted from task inputs.
- Two generators writing into the same directory.
- A clean task deleting outputs belonging to another task.
- Cache keys omitting Java or generator versions.
- Misconfigured incremental annotation processing.
- Stale generated files left behind after entity deletion.
- Parallel builds overwriting outputs concurrently.

### 28.1. Compare clean vs. incremental outputs

In verification runs, compare:

~~~bash
./gradlew generateClientSources
./gradlew clean generateClientSources
~~~

If identical inputs produce different outputs, fix task input/output declarations and cache keys. **Do not permanently disable build caching** merely because a task forgot to declare an input directory.

### 28.2. Isolate output directories

Give each generator its own output folder wired into build source sets explicitly. Avoid having multiple generators emit straight into `src/main/java` or shared Git-tracked folders without strict coordination.

## 29. Generated bytecode not visible as `.java`

Several tools transform bytecode or ASTs directly without emitting Java source:

- Lombok and compiler plugins.
- Bytecode weaving (e.g., AspectJ / ORM enhancement).
- Annotation-processing metadata files.
- Class instrumentation.
- Runtime dynamic proxies.
- Generated resource descriptors.

To inspect generated class-file versions or signatures:

~~~bash
javap -verbose -classpath build/classes/java/main \
  com.example.orders.OrderMapperImpl
~~~

Do not demand **byte-for-byte identical** `.class` files across JDK/compiler upgrades: debug attributes, constant pool layouts, and code-emission sequences legitimately shift. Compare APIs and runtime behavior instead of raw bytecode hashes.

## 30. Verify generated changes inside fat JARs and final artifacts

A repo can have clean generated code in `build/generated` while the packaged artifact ships stale classes due to shading, packaging rules, or caching.

Questions to answer:

- Does the final archive contain the newly generated classes?
- Were duplicate generated classes bundled from multiple sources?
- Did fat JAR / shade relocation break package names or metadata?
- Does WAR `WEB-INF/lib` bundle matching generator runtime dependencies?
- Does the runtime container inject conflicting library versions?
- Do generated classes target bytecode major versions compatible with the deployment JDK?
- Are reflection metadata and service descriptors intact?

Reference inspection commands:

~~~bash
jar tf build/libs/orders-service.jar
jar tf target/orders-service.war
~~~

Exact paths depend on build setup. **Reviewing source diffs never replaces verifying the deployed artifact.**

## 31. Review diffs along contract boundaries

Reviewers need not read every boilerplate getter across 500 generated files, yet they must see **which contracts changed**.

Focus on:

1. Public classes, methods, and constructors.
2. HTTP routes, methods, media types, and status codes.
3. DTO fields, required/optional flags, and nullability.
4. Bean Validation constraints.
5. JSON/XML field names and serialization shapes.
6. Protobuf field numbers and enum ordinals/names.
7. DB tables, columns, types, and keys.
8. Authentication and authorization metadata.
9. Runtime dependencies and TLS/security defaults.
10. Deleted files or moved packages.

An informative diff summary looks like:

~~~text
Input diff:
  orders.yaml: added optional note field

Generator diff:
  version X -> version X (unchanged)

Generated diff:
  OrderDto.java: added field, accessor, and annotation
  OrdersApi.java: unchanged methods/paths
  ApiClient.java: unchanged

Contract checks:
  old client -> new server: verified
  new client -> old server: verified
~~~

This is solely a **reporting structure template**, not observed test results.

## 32. How should pull requests be split?

Where practical, separate distinct change drivers:

- PR A: pin build/generator toolchains and add CI freshness gates.
- PR B: apply scoped mechanical recipes.
- PR C: upgrade generators/Jakarta targets with schemas unchanged.
- PR D: apply intentional schema/API edits and verify backward compatibility.

Projects do not strictly need four PRs—the core aim is avoiding giant PRs where reviewers cannot distinguish **tool-only churn** from **semantic changes**.

Document in every PR:

- Baseline commit.
- Tool, recipe, and generator versions.
- Scoped modules and paths.
- Expected diff categories.
- Explanations for any unexpected changes.
- Build, test, and contract verification evidence.
- Owners and reviewers.
- Rollout and rollback steps where runtime behavior shifts.

### 32.1. Code owners and sign-off

Platform teams may manage codegen tooling technically, yet contract owners must review API or wire-protocol changes. Formatting-only approvals must never waive compatibility sign-off.

## 33. Verification matrix after automation

| Check | Mechanical rewrite | Generated code |
|---|---|---|
| Scope and file diff | Mandatory | Mandatory |
| Tool/recipe versions | Documented | Documented |
| Recipe idempotency | Required for recipes | Does not replace generator determinism |
| Generator determinism | Not generally applicable | Required |
| Input freshness | Required if touching codegen | Required |
| Compile & type resolution | Required | Required |
| Public API / ABI diff | When APIs change | Especially critical |
| Schema / wire compatibility | When affected | Required for models/protocols |
| Unit tests | Yes | Yes |
| Contract / integration tests | Risk-based | Risk-based |
| Security / static analysis | Yes | Yes |
| Cross-JDK verification | Per support matrix | Per support matrix |
| Performance checks | If hot paths shift | If implementations shift |
| Data / rollback safety | If state/protocols shift | If schemas/serialization shift |

Table cells guide verification scope; they are not assertions that any run passed.

### 33.1. Golden fixtures

For codecs and clients, keep curated test fixtures:

~~~text
fixtures/
  request-valid.json
  request-invalid.json
  response-legacy.json
  customer-record-v1.bin
  customer-record-v2.bin
~~~

Golden fixtures guard serialization compatibility across library and generator upgrades. Never commit secrets or real customer PII—use sanitized synthetic data.

### 33.2. Cross-version compatibility tests

During rolling deployments, test:

- Old client ↔ new server.
- New client ↔ old server.
- New writer ↔ old reader.
- Old writer ↔ new reader.
- Consumers running differing JDKs when shipping MR-JARs or multi-target bytecode.

Clean compilation of newly generated DTOs never proves wire compatibility across live versions.

## 34. Scenario: generated code still imports javax

Suppose handwritten files already migrated to:

~~~java
import jakarta.validation.Valid;
~~~

while the generated client still contains:

~~~java
import javax.validation.Valid;
~~~

Likely causes:

1. Recipes ran only on handwritten source directories.
2. An older generator version still emits Java EE imports.
3. Generator configuration has not enabled Jakarta mode.
4. Stale output or build cache reused old files.
5. Local and CI machines ran different generator versions.
6. Custom generator templates were not updated.

Remediation: locate the owning generator, update its version/options/templates, regenerate cleanly, review diffs, compile, and test validation behavior. Never manually edit generated Java files only for the next build to overwrite them.

## 35. Scenario: generator touches 300 files with zero schema change

A PR bumps the generator version and CI reports:

~~~text
300 Java files modified
25 files renamed
10 files deleted
~~~

Analysis steps:

1. Verify input schemas and template checksums remained untouched.
2. Confirm generator version/config changed intentionally.
3. Group diffs by imports, comments, formatting, types, signatures, and file renames.
4. Suppress or isolate timestamp and line-ending churn.
5. Inspect every removed class or method.
6. Diff API, wire, and schema contracts.
7. Execute test suites and client/server compatibility checks.
8. Document approved changes explicitly.
9. If diffs exceed review capacity, split generator upgrades from schema edits.

Never use `git diff --ignore-space-change` as an excuse to skip semantic review.

## 36. Scenario: CI is green yet committed generated files are stale

If a repo commits `src/generated/java`, a developer editing `orders.yaml` without regenerating leaves stale Java source that still compiles cleanly and passes unit tests.

A CI freshness gate catches this:

1. Start from a clean checkout.
2. Execute the pinned generator.
3. Compare tracked outputs against `HEAD`.
4. Flag any new untracked generated files.
5. Fail CI on mismatch.
6. Surface diffs so the author regenerates and commits cleanly.

Note that freshness proves only **outputs match current inputs and toolchains**, not that schema edits stay backward-compatible with consumers—run contract tests separately.

## 37. Migration flow from Java 11 / Spring Boot 2 to Java 17 / Spring Boot 3

Example phased plan:

### Phase A — Lock baseline

- Document JDK, framework/BOM, build tool, and generator versions.
- Save input schemas, baseline generated outputs, and test evidence.
- Freeze repository baseline state.

### Phase B — Prepare toolchain

- Upgrade compiler and test JVMs to Java 17 per support policy.
- Update annotation processors, JaCoCo, bytecode tools, and static analyzers as required.
- Verify generators run cleanly and reproduce outputs.

### Phase C — Mechanical rewrite

- Apply scoped Jakarta recipes across targeted modules.
- Preserve Java SE `javax.*` packages intact.
- Review source diffs and dependency graphs.

### Phase D — Regenerate

- Switch to Jakarta-compatible generator versions and templates.
- Hold input schemas unchanged initially where feasible.
- Inspect generator-only diffs cleanly.
- Apply intentional schema changes afterward and review contract diffs.

### Phase E — Verify

- Compilation, unit, and integration suites.
- Negative validation and security tests.
- API/serialization golden fixtures.
- Cross-version service contract suites.
- Generated freshness and CI reproducibility gates.
- Final artifact, class-file, and runtime checks.

### Phase F — Deploy

- Canary or rolling rollout where appropriate.
- Monitor logs, 4xx/5xx rates, DB errors, metrics, and distributed traces.
- Ensure binary rollback and two-way data compatibility.

Assign owners and record evidence per phase; finishing a rewrite recipe never marks the end of a Java migration.

## 38. Anti-patterns to avoid

### 38.1. Unscoped text find-and-replace

Turning every `javax.` into `jakarta.` corrupts Java SE APIs. Use type-aware refactoring rules.

### 38.2. Unpinned recipes and generators

Identical source can emit different code when floating tool versions shift. Pin exact versions in build/config files.

### 38.3. Hand-editing generated outputs

The next regeneration overwrites manual edits. Modify schemas, templates, or generator config instead.

### 38.4. Batching multiple major migrations together

Makes isolating failures across JDK, framework, serializer, and generator impossible. Decouple drivers wherever possible.

### 38.5. Treating empty Git diffs as valid codegen

Generated directories may be gitignored, generator tasks skipped, or build caches stale.

### 38.6. Ignoring untracked generated files

`git diff` misses brand-new untracked files. CI gates for committed codegen must inspect untracked files too.

### 38.7. Ignoring timestamp churn

Thousands of noisy timestamp diffs cause reviewers to skim past real API breaks. Configure deterministic formatting and timestamps.

### 38.8. Reviewing Java source diffs while ignoring schema/wire contracts

One modified Protobuf tag or field nullability rule can break external clients even when Java source diffs appear tiny.

### 38.9. Deleting tests or weakening security checks to get green builds

That removes verification safeguards rather than proving migration compatibility.

### 38.10. Lacking a data rollback strategy

Code reverts cleanly via Git, yet data written by the newer version remains in databases or queues; define compatibility windows and data rollback plans.

## 40. Checklist for completing an automation wave

- [ ] Recorded baseline commit, JDK version, and dependency graph.
- [ ] Classified mechanical, semantic, and generated changes cleanly.
- [ ] Pinned recipe, tool, and generator versions.
- [ ] Executed and reviewed scoped dry-run diffs.
- [ ] Confirmed no blanket Javax/Jakarta replacement altered Java SE APIs.
- [ ] Verified recipe idempotency where applicable.
- [ ] Identified source of truth and owner for all generated files.
- [ ] Confirmed reproducible generator inputs, configs, and templates.
- [ ] Eliminated or isolated timestamp, locale, and line-ending noise.
- [ ] For committed generated code: verified both tracked and untracked diffs.
- [ ] For ignored generated code: verified snapshots or build artifacts.
- [ ] Reviewed public APIs, schemas, and wire contracts.
- [ ] Confirmed no stale generated outputs or incremental cache errors remain.
- [ ] Ran required unit, integration, contract, and security suites.
- [ ] Verified runtime JDK and emitted class-file versions.
- [ ] Cross-checked final deployment artifacts against tested source.
- [ ] Documented expected and unexpected changes clearly in the PR.
- [ ] Covered data compatibility in rollout and rollback plans where applicable.

Checklist items serve as technical guidance, **not proof that a repository has already passed QA**.

## 41. Summary principles

- **Automate mechanical edits, never semantic judgment.** API renames can be automated; runtime behavior still requires verification.
- **AST/type-aware refactoring beats generic text replacement** for scoped Java API migrations.
- **Recipes need clear scope, preconditions, pinned versions, and idempotency** to behave reliably on repeat runs.
- **Manage generated code via schemas, templates, processors, and generator configuration**, not ad-hoc manual patches.
- **Generator determinism and behavioral correctness are distinct questions.** Consistent output is not necessarily right; changed output is not automatically a bug.
- **Git diff cannot inspect everything**: tracked, untracked, and gitignored outputs require tailored checks.
- **Small diffs can trigger huge breaking changes** across Protobuf field numbers, HTTP routes, DTO nullability, SQL types, or security annotations.
- **Javax/Jakarta migrations must verify API ownership**, keeping Java SE packages like `javax.net.ssl` and `javax.sql` untouched.
- **OpenAPI, Protobuf, Avro, jOOQ, MapStruct, and annotation processors carry distinct contracts** requiring format-appropriate tests.
- **Build caches, toolchains, locales, and generator versions shape outputs**, so CI requires controlled inputs and environments.
- **Group generated diffs by driver**—tool-only, formatting, API, and data contracts.
- **Verify through compilation, contract, integration, and security suites**, alongside explicit owners and rollback plans when runtime or data shifts.

In **Java Advance Compatibility Migration**, automation standardizes repetitive transformations and reduces manual error, rather than proving runtime compatibility on its own. Combining tightly scoped recipes, explicit sources of truth, pinned generators, diff checks across both tracked and gitignored outputs, and contract-driven testing lets teams upgrade JDKs and frameworks while knowing **where every change came from, what it affects, and how any regression will be caught**.
