# sun.misc.Unsafe: inventorying usage and choosing replacement APIs

## 1. Why is `sun.misc.Unsafe` a risk point when upgrading Java?

`sun.misc.Unsafe` is a class previously used by many Java libraries to perform low-level operations outside the language's normal safety model: reading/writing memory by offset, atomic operations, off-heap memory access, managing fences, allocating objects without going through constructors, and several other special operations. Part of these capabilities serve performance or framework implementation, yet they can also break JVM guarantees for type safety, memory lifecycle management, and encapsulation.

When moving from one JDK version to another, the issue is not merely “whether `sun.misc.Unsafe` is imported or not”. A project may encounter these situations:

- Source code directly uses fields, methods, or instances of `Unsafe`.
- Frameworks or transitive dependencies access `Unsafe` inside a JAR.
- Code uses reflection to obtain the `theUnsafe` singleton or call methods by name.
- Dynamically generated bytecode, JNI, native libraries, or class loaders rely on the JVM's internal memory layout.
- A build runs on a developer machine yet fails in CI or production due to different module access, dependency versions, or runtime images.
- An operation still runs, yet semantics for memory ordering, alignment, or lifetime are no longer suitable after migration.

`sun.misc.Unsafe` belongs to the set of APIs not recommended as an application contract. Since Java 9, certain compatibility APIs such as `sun.misc.Unsafe` are provided via the `jdk.unsupported` module, yet that does not turn them into stably guaranteed Java SE APIs. Nor should one switch to `jdk.internal.misc.Unsafe` as an “upgrade”, because it remains a JDK internal API, subject to encapsulation constraints, and is not a public, sustainable option.

The goal of this lesson is to **accurately inventory `Unsafe` usage**, classify risks by actual behavior, and then select supported Java APIs as replacements. Replacements must be verified with appropriate tests and benchmarks; one cannot assume every `Unsafe` call has an equivalent replacement call in every respect.

## 2. Distinguishing “direct use”, “indirect use”, and “actually needed”

A system may contain `Unsafe` at multiple layers. Before fixing, three separate questions need to be answered:

1. **Who uses it?** Application-written code, internal libraries, external dependencies, instrumentation agents, or runtime-generated code?
2. **What is it used for?** Field CAS, array reading, off-heap allocation, serialization, park/unpark, or other operations?
3. **Does it actually need direct replacement in the application?** Does the dependency already have a newer version using supported APIs, or does the framework's public API already provide the exact functionality?

For example, detecting `Unsafe` in a serialization library JAR does not mean the team has to rewrite the serializer themselves. The priority direction is identifying the library version that supports the target JDK, checking release notes, and upgrading to a compatible dependency. Only when the application truly owns the low-level logic or no suitable supported version exists does that usage need to be redesigned.

Conversely, if application source code calls `Unsafe.allocateMemory()` and stores the native address in a `long` field, that is the team's direct responsibility. Ownership of the memory region, deallocation rules, and thread sharing must be determined before replacing.

### 2.1. Three conclusion levels upon detection

| Finding | Example | Next step |
| --- | --- | --- |
| Direct use | `import sun.misc.Unsafe;` in application source | Inventory every call site and design a replacement API |
| Indirect use | `jdeps --jdk-internals` reports a dependency | Identify the artifact/version and find a supported upgrade |
| Trace only, execution path unproven | String `sun.misc.Unsafe` in generated code, shaded JAR, or logs | Identify loaded classes and which features actually go through this path |

A text string or analyzer warning is the starting point for investigation, not enough to decide whether to fix or ignore. You need to find the specific call path, actual runtime behavior, and impact if changed.

## 3. Inventorying `Unsafe` in source code and artifacts

### 3.1. Searching in source and build configuration

Start from imports, class names, and method names. For example, using a text search tool in the repository:

~~~bash
rg -n 'sun[.]misc[.]Unsafe|jdk[.]internal[.]misc[.]Unsafe' src
rg -n 'theUnsafe|objectFieldOffset|allocateMemory|copyMemory' src
rg -n 'compareAndSwap|compareAndSet|putOrdered|loadFence|storeFence' src
rg -n 'allocateInstance|defineClass|park\(|unpark\(' src
~~~

The commands are examples for environments with `rg` (ripgrep); not every project has this tool. In Windows PowerShell, you can use `Get-ChildItem` with `Select-String` according to repository conventions.

Besides main source code, also check:

- Test code, test utilities, and internal benchmarks.
- Generated sources and annotation processors.
- Build plugins, code generators, and tooling running in CI.
- Modules using reflection to obtain `theUnsafe` without direct imports.
- Multi-platform sources or JDK-specific source sets (if any).

Do not stop at the keyword `Unsafe`. Code may use `MethodHandles`/reflection to invoke methods by name, store class names in resources, or load classes dynamically.

### 3.2. Analyzing dependencies with `jdeps`

`jdeps` is a tool bundled with the JDK that can find static references to internal APIs. For example:

~~~bash
jdeps --jdk-internals application.jar
jdeps --jdk-internals --recursive library.jar
~~~

For multi-release JARs, it may be necessary to specify the target release level:

~~~bash
jdeps --multi-release 21 --jdk-internals library.jar
~~~

The output helps identify which classes are referencing unsupported APIs, including `sun.misc.Unsafe`. However, `jdeps` primarily analyzes linkages in class files; it cannot guarantee finding all dynamic accesses via reflection, method handles constructed from strings, runtime-generated code, or JNI. A “not detected” result therefore does not strictly prove the application does not use Unsafe.

If the application has a complex classpath, analyze the exact artifacts and dependencies packaged for runtime. Do not use an incomplete JAR to draw conclusions about the entire product.

### 3.3. Identifying the actual JAR loaded

During migration, the version declared in the build script may differ from the actual version placed into containers, shaded JARs, or the runtime classpath. Therefore, the inventory should record:

- Group/artifact/version of direct and transitive dependencies.
- Versions of frameworks, JDK, and build tools.
- Artifact type: normal JAR, fat/uber JAR, shaded JAR, agent JAR, or native image.
- Actual environment: local, CI, integration, staging, production.
- Whether an execution path triggers the `Unsafe` call.

When needed, use the corresponding dependency graph tool, for example:

~~~bash
./gradlew dependencies --configuration runtimeClasspath
./gradlew dependencyInsight --dependency target-artifact \
    --configuration runtimeClasspath
mvn dependency:tree
~~~

These are reference commands for the investigation phase, not prerequisites for editing this document. For plugins or agents, inspect separate build/runtime classpaths as well because not every dependency appears in the application's `runtimeClasspath`.

## 4. Inventory table template for a migration

Each finding should have a record complete enough for another team to receive, evaluate, and plan:

| Field | Meaning |
| --- | --- |
| Finding ID | Issue code for tracking |
| Module/artifact | Owning or dependent component |
| Current/target version | For example, Java 17 → Java 21/22 runtime |
| `Unsafe` API in use | Actual method/field name |
| Behavior to preserve | CAS, off-heap, fences, object creation, parking... |
| Usage path | Class, method, business flow, environment |
| Ownership | Application code or third-party library |
| Risks | Memory safety, module access, crash, performance, semantics |
| Candidate replacement API | VarHandle, Atomic*, FFM, ByteBuffer, LockSupport... |
| Constraints | Minimum JDK, threads, alignment, lifecycle |
| Evidence | Logs, static analysis, tests, benchmarks, upstream issues |
| Decision | Fix directly, upgrade dependency, keep temporarily under control |
| Owner/completion milestone | Responsible person and release gate |

Example of an inventory item:

~~~text
ID: JAVA-UNSAFE-014
Artifact: order-engine.jar
Call site: com.example.queue.SequenceCounter
Unsafe API: compareAndSwapLong(Object, long, long, long)
Purpose: CAS on the sequence field of an object
Current JDK: 17
Target JDK: 21
Candidate: VarHandle.compareAndSet
Compatibility requirement: atomic CAS, no lost updates under multithreading
Verification: concurrent stress test; linearizability review
Owner: Platform
~~~

Do not group every call into a single category “replace Unsafe”. An application may use `Unsafe` for CAS, off-heap memory, and object allocation; these three cases have completely different replacement mechanisms and verification criteria.

## 5. Matrix for choosing replacement APIs by purpose

| `Unsafe` usage category | Legacy method examples | Supported API options | Points to consider |
| --- | --- | --- | --- |
| Field CAS | `compareAndSwapInt`, `compareAndSwapLong`, `compareAndSwapObject` | `VarHandle.compareAndSet` or `Atomic*` classes | Field type, memory ordering, ABA, retry loop |
| Volatile read/write | `getObjectVolatile`, `putLongVolatile` | `VarHandle.getVolatile` / `setVolatile`; `volatile` field | Visibility, ordering, avoiding unintentional semantics changes |
| Release/lazy write | `putOrderedObject`, `putOrderedLong` | `VarHandle.setRelease` or `Atomic*.lazySet` | Not identical to `setVolatile` by default |
| Atomic update | `getAndAddInt`, `getAndSetObject` | `VarHandle.getAndAdd` / `getAndSet`; `AtomicInteger`/`AtomicReference` | Return type, overflow, contention level |
| Memory fences | `loadFence`, `storeFence`, `fullFence` | Corresponding fences in `VarHandle` or higher-level synchronization | Happens-before, acquire/release, proving synchronization |
| Array element access | `arrayBaseOffset`, `arrayIndexScale` combined with load/store | `MethodHandles.arrayElementVarHandle`, normal array access | Do not calculate byte offsets manually |
| Byte buffer views | Reading/writing byte regions by offset | `ByteBuffer`, `byteBufferViewVarHandle` | Endianness, alignment, bounds |
| Off-heap allocation/access | `allocateMemory`, `freeMemory`, `getLong(long)`, `putLong(long, ...)` | Foreign Function & Memory API (`Arena`, `MemorySegment`, `ValueLayout`) on appropriate JDKs | Ownership, lifetime, thread scope, alignment |
| Copying heap arrays | `copyMemory` for arrays | `System.arraycopy`, `Arrays.copyOf` | Overlap, array type, element count vs bytes |
| Copying memory segments | `copyMemory` between native regions | `MemorySegment.copy` | Bounds and lifetime checks |
| Thread park/unpark | `park`, `unpark` | `LockSupport`, `Lock`, `Condition`, `Semaphore` | Permits, timeouts, interrupts, spurious wakeups |
| Creating objects without running constructors | `allocateInstance` | Constructors, factories, builders, supported serialization APIs | Object invariants; no universal direct replacement |
| Dynamic class definition | Legacy/unsupported class-definition APIs | `MethodHandles.Lookup.defineClass`, `defineHiddenClass`, public class loading mechanisms | Package/lookup access, lifetime, class identity |
| Bypassing checked exceptions | `throwException` | Explicit exception contracts and appropriate wrappers/translation | No general reason to bypass the compiler |

The matrix is a routing guide. Never replace by method name with a “similar-looking” operation without fully understanding visibility, ordering, lifetime, and error behavior.

## 6. Replacing field CAS operations with `VarHandle`

### 6.1. Why is `VarHandle` suitable?

`VarHandle`, available since Java 9, provides a public API to access and perform atomic operations on fields, array elements, or certain buffer views. Instead of taking raw memory offsets and using `Unsafe` to read/write, code can create a handle bound to a specific type and access location.

Example of a sequence counter using CAS on a field:

~~~java
import java.lang.invoke.MethodHandles;
import java.lang.invoke.VarHandle;

public final class SequenceCounter {
    private volatile long sequence;

    private static final VarHandle SEQUENCE;

    static {
        try {
            SEQUENCE = MethodHandles.lookup()
                    .findVarHandle(
                            SequenceCounter.class,
                            "sequence",
                            long.class);
        } catch (ReflectiveOperationException ex) {
            throw new ExceptionInInitializerError(ex);
        }
    }

    public long next() {
        while (true) {
            long current = (long) SEQUENCE.getVolatile(this);
            long updated = current + 1;
            if (SEQUENCE.compareAndSet(this, current, updated)) {
                return updated;
            }
        }
    }
}
~~~

In the example:

- `findVarHandle` identifies the field by class, name, and type; `objectFieldOffset` is unnecessary.
- `getVolatile` reads with volatile semantics.
- `compareAndSet` attempts to swap the value atomically if the current value matches the expectation.
- Failed CAS can retry because another thread updated it.
- The `volatile` field and using appropriate access modes make the synchronization model easier to read compared to raw offsets.

If only an atomic counter is needed and there is no requirement to keep the old object structure, `AtomicLong` is usually simpler:

~~~java
import java.util.concurrent.atomic.AtomicLong;

public final class SequenceCounter {
    private final AtomicLong sequence = new AtomicLong();

    public long next() {
        return sequence.incrementAndGet();
    }
}
~~~

`AtomicLong` expresses intent clearly, yet may differ in object layout, serialization, allocation, and binary compatibility compared to the old `long` field. For libraries required to preserve fields or class layout, `VarHandle` may be more suitable; for normal application code, atomic classes are usually easier to maintain.

### 6.2. No CAS loop is needed if the API already provides atomic updates

The example above can be shortened if the goal is incrementing the counter:

~~~java
public long next() {
    return (long) SEQUENCE.getAndAdd(this, 1L) + 1L;
}
~~~

`getAndAdd` returns **the value before updating**, so adding is needed if the `next()` method commits to returning the new value. A wrong “old value vs new value” swap can cause business logic errors even though the operation is atomic.

### 6.3. Private fields and the Java Module System

`MethodHandles.lookup()` inside the class owning the field itself can look up private fields according to that class's access permissions. For a class in another module, creating a private lookup may require `MethodHandles.privateLookupIn` and the package must be opened to the calling module.

Do not automatically replace:

~~~java
field.setAccessible(true);
~~~

with `privateLookupIn` expecting to bypass all encapsulation boundaries. Supported APIs still must respect access control and module boundaries. When designing a library, prioritize providing public/protected APIs or placing `VarHandle` creation inside the module owning the state.

## 7. Memory ordering: `plain`, `opaque`, `acquire/release`, and `volatile`

The hardest part when replacing `Unsafe` is usually not syntax, but synchronization semantics.

`VarHandle` provides multiple access modes:

| Access mode | General meaning | Situations to consider |
| --- | --- | --- |
| `get` / `set` | Plain access | Only safe when synchronized by another mechanism or not unsafely shared |
| `getOpaque` / `setOpaque` | Opaque access, with ordering guarantees weaker than volatile | Certain proven lock-free structures |
| `getAcquire` | Reads with acquire semantics | Receiving state published with a matching release |
| `setRelease` | Writes with release semantics | Publishing state under release/acquire rules |
| `getVolatile` / `setVolatile` | Volatile semantics | Communicating between threads with stronger ordering |
| `compareAndSet` | CAS with VarHandle-defined semantics | Conditional, atomic update |
| `getAndSet` / `getAndAdd` | Atomic read-modify-write | Counters, state transitions |

Example:

~~~java
// Release write.
STATE.setRelease(this, READY);

// Acquire read.
int observed = (int) STATE.getAcquire(this);
~~~

When used properly, a release/acquire pair can support publishing data between threads. However, one cannot look only at those two lines and conclude the entire algorithm is thread-safe. You must examine the order of surrounding writes/reads, shared objects, and which conditions confirm data has been published.

Do not change `Unsafe.getObjectVolatile` to `VarHandle.get` just because the result is the same type. Weakening ordering can create rare races, especially on hardware or optimization configurations that regular tests struggle to reproduce.

Conversely, replacing everything with the strongest volatile does not prove an algorithm correct either. It can alter performance, contention, and still fail to fix atomicity issues when an operation consists of multiple steps.

### 7.1. CAS, ABA, and retry

`compareAndSet` atomically checks whether the current value equals expected before updating. However, CAS does not automatically solve every **ABA** case: a value transitioning from A → B → A can make a thread think the state has not changed.

If the algorithm needs to know change history, version/stamp mechanisms such as `AtomicStampedReference` can be used, or an appropriate state machine designed. Do not treat switching from Unsafe CAS to VarHandle CAS as proof that a lock-free algorithm is safe.

### 7.2. Fences and high-level synchronization

`Unsafe.loadFence`, `storeFence`, and `fullFence` have public fence options in `VarHandle`, including `acquireFence`, `releaseFence`, `fullFence`, and appropriate load/store fence variants.

Example:

~~~java
VarHandle.releaseFence();
// Publish data according to a designed synchronization protocol.
~~~

A standalone fence does not turn arbitrary normal accesses into thread-safe ones. It must be placed in a valid synchronization protocol. In many cases, using `synchronized`, `ReentrantLock`, `Atomic*`, or supported concurrent queues is easier to verify and maintain than managing fences manually.

## 8. Accessing array elements and buffers without calculating raw offsets

### 8.1. Array element `VarHandle`

Legacy Unsafe code might calculate offsets by base offset plus index multiplied by index scale. For Java arrays, prefer direct array access or `arrayElementVarHandle` if CAS/volatile on elements is needed.

~~~java
import java.lang.invoke.MethodHandles;
import java.lang.invoke.VarHandle;

public final class ArraySlots {
    private static final VarHandle SLOT =
            MethodHandles.arrayElementVarHandle(int[].class);

    public static boolean replaceIfEqual(
            int[] values, int index, int expected, int update) {
        return SLOT.compareAndSet(values, index, expected, update);
    }
}
~~~

This code makes the array and index explicit, avoiding dependence on JVM object header size, base offset, or layout. Out-of-bounds access and data type issues are expressed through a better-defined API.

### 8.2. Buffer views by type and byte order

When data consists of bytes in a `ByteBuffer`, buffer APIs or a view VarHandle can be used:

~~~java
import java.lang.invoke.MethodHandles;
import java.lang.invoke.VarHandle;
import java.nio.ByteBuffer;
import java.nio.ByteOrder;

public final class PacketReader {
    private static final VarHandle LONG_VIEW =
            MethodHandles.byteBufferViewVarHandle(
                    long[].class,
                    ByteOrder.LITTLE_ENDIAN);

    public static long readLong(ByteBuffer buffer, int byteOffset) {
        return (long) LONG_VIEW.get(buffer, byteOffset);
    }
}
~~~

With a byte-buffer view, the offset is interpreted in bytes, not as an index of a `long[]` array. You must verify alignment, bounds, byte order, and which access modes the view supports. Do not assume atomic operations can execute at arbitrary unaligned addresses.

If only reading/writing sequentially, `ByteBuffer.order(...).getLong(...)` or `putLong(...)` is usually easier to understand.

## 9. Replacing `allocateMemory` and off-heap access with the Foreign Function & Memory API

### 9.1. Support scope by JDK

The Foreign Function & Memory API (FFM) was standardized in JDK 22, with main public APIs in the `java.lang.foreign` package, including `MemorySegment`, `Arena`, and `ValueLayout`. Earlier JDKs had incubator/preview phases with varying syntax and stability levels; do not copy JDK 22 examples verbatim into a JDK 17 or JDK 21 project expecting them to run immediately.

If the target runtime does not yet support standard FFM, you can consider `ByteBuffer.allocateDirect` for off-heap byte storage needs, or continue relying on a low-level library with a vendor-supported version under a time-bound plan. The choice depends on whether native pointers, memory lifetime, and layout are needed or only a data buffer.

### 9.2. Example replacing allocation and reading/writing memory

An old Unsafe pattern (illustrating usage to replace):

~~~java
// Legacy pseudocode; assume an Unsafe instance already exists.
long address = unsafe.allocateMemory(Long.BYTES);
try {
    unsafe.putLong(address, 123L);
    long value = unsafe.getLong(address);
} finally {
    unsafe.freeMemory(address);
}
~~~

With JDK 22+ and standard FFM, a memory region with a clear lifecycle can be used:

~~~java
import java.lang.foreign.Arena;
import java.lang.foreign.MemorySegment;
import java.lang.foreign.ValueLayout;

public final class OffHeapSample {
    public static long readWrite() {
        try (Arena arena = Arena.ofConfined()) {
            MemorySegment segment =
                    arena.allocate(ValueLayout.JAVA_LONG);

            segment.set(ValueLayout.JAVA_LONG, 0, 123L);
            return segment.get(ValueLayout.JAVA_LONG, 0);
        }
    }
}
~~~

Here:

- `Arena` determines the segment's lifetime.
- `try-with-resources` closes the confined arena when leaving scope.
- `MemorySegment` provides access checks based on bounds, lifetime, and threading constraints.
- `ValueLayout.JAVA_LONG` describes the corresponding type and alignment.

This model is better than scattering raw `long` addresses across multiple classes and trying to remember to call `freeMemory` in the right place. However, it still requires ownership and concurrency design: a segment from a confined arena must not be arbitrarily shared for access from other threads.

### 9.3. Layout, byte order, and alignment

When reading binary structures, byte order and field sizes must be determined. For example:

~~~java
import java.lang.foreign.Arena;
import java.lang.foreign.MemorySegment;
import java.lang.foreign.ValueLayout;
import java.nio.ByteOrder;

try (Arena arena = Arena.ofConfined()) {
    MemorySegment segment = arena.allocate(16);
    ValueLayout.OfLong littleEndianLong =
            ValueLayout.JAVA_LONG.withOrder(ByteOrder.LITTLE_ENDIAN);

    segment.set(littleEndianLong, 0, 0x0102030405060708L);
    long decoded = segment.get(littleEndianLong, 0);
}
~~~

When porting from Unsafe, you must cross-check:

1. Byte order of the format and of the legacy operation.
2. Alignment and offsets in the struct or packet.
3. Sizes and types (`int`, `long`, pointers, platform words).
4. Lifetime of the memory region; who creates and who closes it.
5. Which threads are allowed to access it.
6. Whether copies can overlap, and bounds rules.

A mechanical translation from `getLong(address + offset)` to `segment.get(...)` that picks the wrong layout/offset can still corrupt data.

### 9.4. Copying data

If Unsafe is only used to copy elements of heap arrays, consider:

~~~java
System.arraycopy(source, 0, target, 0, length);
~~~

`length` here is the **number of elements** of the array, not the number of bytes. Semantics regarding overlap, element types, and the copied sub-region must be preserved.

For memory segments, the memory-region copy API can be used:

~~~java
MemorySegment.copy(source, sourceOffset, target, targetOffset, bytes);
~~~

The value `bytes` is the number of bytes, and the operation must satisfy the bounds/lifetime/access restrictions of the segments. Do not mistakenly swap units when moving from arrays to memory regions.

### 9.5. Native interop is not always the requirement

Not every application using `allocateMemory` needs a native linker or arbitrary addresses. If only a buffer for sending to files/network or holding bytes is needed, `ByteBuffer` and public I/O APIs can be simpler than FFM.

If native code calls are needed, FFM provides native interoperability mechanisms appropriate to supported JDKs. Some native access operations are controlled by runtime policies and may require configuring appropriate access permissions; check the official guide for the exact target JDK version rather than adding flags arbitrarily.

## 10. `ByteBuffer.allocateDirect`: when it fits and its limitations

`ByteBuffer.allocateDirect` can provide a byte region outside the Java heap depending on implementation. The buffer API supports reading/writing typed values without using `Unsafe`:

~~~java
import java.nio.ByteBuffer;
import java.nio.ByteOrder;

ByteBuffer buffer = ByteBuffer.allocateDirect(16)
        .order(ByteOrder.LITTLE_ENDIAN);

buffer.putLong(0, 123L);
long value = buffer.getLong(0);
~~~

Suitable when:

- The need is reading/writing bytes and primitive values with clear bounds.
- I/O APIs already work well with `ByteBuffer`.
- There is no need to pass a native address directly to a C library.
- Lifecycle is managed via standard buffer mechanisms and does not require freeing immediately at an exact moment.

Limitations:

- Direct buffers do not provide the same deterministic lifetime model as an `Arena` that can be actively closed.
- Do not access private cleaners or internal addresses of a direct buffer to free it manually with Unsafe.
- Sharing across threads, byte order, alignment, and ownership still need to be designed.

If the application needs scoped control over memory deallocation, FFM on a supported JDK is usually a clearer choice.

## 11. Replacing `park` / `unpark` with public synchronization tools

`Unsafe.park` and `Unsafe.unpark` are used in some concurrent structures. Java provides `LockSupport` for park/unpark operations without accessing Unsafe:

~~~java
import java.util.concurrent.locks.LockSupport;

// Current thread pauses (may return due to unpark,
// interrupt, or spurious wakeup).
LockSupport.park();

// In another thread, grant a permit so the thread can continue.
LockSupport.unpark(workerThread);
~~~

Points to preserve when replacing:

- `LockSupport` permits do not accumulate infinitely like the number of messages in a queue.
- `park` can return upon interrupt or spurious wakeup.
- Wait conditions must be checked in an appropriate loop; do not treat “park returning” as the condition already being true.
- `parkNanos` and `parkUntil` differ in how time is interpreted; do not confuse relative/absolute timing.
- Do not ignore interruption or block a thread without a valid wakeup path.

In most business code, `BlockingQueue`, `Semaphore`, `CountDownLatch`, `ReentrantLock`, or `Condition` are more suitable than building a low-level park/unpark protocol manually.

Example using a condition instead of manual parking:

~~~java
import java.util.concurrent.ArrayBlockingQueue;
import java.util.concurrent.BlockingQueue;

BlockingQueue<String> queue = new ArrayBlockingQueue<>(100);

// Producer:
queue.put("event");

// Consumer:
String event = queue.take();
~~~

The queue class takes responsibility for most synchronization and wakeup details. Do not reimplement concurrent structures just to replace an Unsafe call if the standard library already meets the requirement.

## 12. `allocateInstance` and creating objects without calling constructors

`Unsafe.allocateInstance(Class<?>)` can create an object without going through a normal constructor. Some serialization, proxy, or object mapper frameworks used this mechanism to construct objects when no suitable constructor existed.

The risk is not only the internal API; it also bypasses invariants established by the constructor:

~~~java
public final class Session {
    private final String token;

    public Session(String token) {
        this.token = java.util.Objects.requireNonNull(token);
    }

    public String token() {
        return token;
    }
}
~~~

If the object is allocated without running the constructor, `token` may not be initialized according to the application's rules. Calling `token()` afterward could receive `null` even though the API expects it to always be non-null.

Priority replacement directions:

1. Provide an explicit constructor or factory that checks invariants.
2. For deserialization, use mechanisms supported by the library/framework and configure appropriate constructor/builder/record mappings.
3. For traditional Java serialization, use public serialization APIs if truly needed and understand the specific rules of that mechanism.
4. If a third-party framework depends on `allocateInstance`, prioritize upgrading to a framework version confirmed to support the target JDK.

There is no single universal public API that directly replaces `allocateInstance` with the same meaning of “creating any object without calling a constructor”. This is usually a sign that the contract must be redesigned or framework-level tooling upgraded, rather than merely changing imports.

## 13. Dynamic class generation and loading

Some paths using Unsafe or internal APIs serve to define classes from bytecode. In appropriate cases, Java provides APIs such as:

- `MethodHandles.Lookup.defineClass(byte[])`: defines a class within an appropriate package/lookup scope.
- `MethodHandles.Lookup.defineHiddenClass(...)`: creates a hidden class for certain dynamic implementation code generation cases.
- Public `ClassLoader` mechanisms to load normal classes according to Java rules.

Illustrative example in API-call form, not complete code generating bytecode itself:

~~~java
import java.lang.invoke.MethodHandles;

// bytes is a valid class file and satisfies package/access conditions.
Class<?> generated =
        MethodHandles.lookup().defineClass(bytes);
~~~

Things to evaluate:

- Which package and module does the new class belong to?
- Does the lookup object have the required permissions?
- Is the class designed to be looked up externally by name or only used internally?
- Do class lifecycle, class loader identity, and garbage collection eligibility change?
- Does the bytecode generator support the target JDK's class-file version?

`defineHiddenClass` is not a one-to-one replacement for every regularly named class. Hidden classes have different identity/discovery semantics than classes loaded by name. For proxy/bytecode generation frameworks, prioritize using a framework version that already supports the target JDK rather than replacing class-definition internals yourself.

## 14. Why is `--add-opens` not a long-term replacement option?

In the Java Module System, deep reflective access into unopened packages can be blocked. Some teams add flags like `--add-opens` so legacy libraries continue running. This flag is a **temporary compatibility measure** where applicable and approved, not a replacement API for Unsafe.

It is necessary to distinguish:

- `--add-opens` can open packages to allow certain deep reflective accesses.
- `--add-exports` relates to exporting packages across module boundaries.
- Neither flag guarantees the existence or stability of internal methods.
- A new JDK can still change/remove behavior that code relies on.

If a workaround is truly needed:

1. Clearly record which library and method are being blocked.
2. Apply the smallest scope to controlled environments.
3. Have an owner, deadline, and target dependency version that will remove the workaround.
4. Check related tests and security/operational issues.
5. Do not extend the workaround into a system-wide configuration indefinitely.

In particular, switching from `sun.misc.Unsafe` to `jdk.internal.misc.Unsafe` and then opening the module with flags merely moves the problem from one internal point to another internal point.

## 15. JDK compatibility changes to anticipate

A migration plan should clearly state the baseline and target runtime:

| JDK milestone | Relevance to this lesson | Notes |
| --- | --- | --- |
| Java 8 | Lots of legacy code used `sun.misc.Unsafe` directly | No `VarHandle` yet |
| Java 9+ | Has `VarHandle` and JPMS; `sun.misc.Unsafe` remains in the context of unsupported APIs | Module access and dependencies must be checked |
| Java 17 | Has `VarHandle`, `Atomic*`, `LockSupport`, and `ByteBuffer` | FFM in pre-final standard API period |
| Java 21 | Has standard concurrent APIs; FFM in preview stage | Do not assume JDK 22 FFM code runs verbatim |
| Java 22+ | Standard FFM (`java.lang.foreign`) can replace many off-heap operations | Check runtime vendor/version, native access policy |

Do not decide to replace based solely on “whether the JDK has that API”. A library may have a minimum Java level lower than the application's runtime or need to compile artifacts for use by older Java consumers.

For example: if a library must continue supporting Java 17, it cannot directly publish an API using JDK 22's `java.lang.foreign.Arena` in an artifact with a Java 17 baseline. It may be necessary to keep interfaces independent of the runtime implementation, choose ByteBuffer, or split modules by supported JDK level.

### 15.1. Source, binary, and behavioral compatibility

Some changes when removing Unsafe can have different impacts:

- **Source compatibility:** a public method changing from taking `long address` to `MemorySegment` forces consumers to fix source code.
- **Binary compatibility:** JVM descriptors change, so old client bytecode may fail to link.
- **Behavioral compatibility:** freeing segments earlier, forbidding out-of-scope thread access, or stricter bounds checks can make old bugs surface clearly.
- **Performance compatibility:** different layouts, access modes, and synchronization can alter latency/throughput.

If a public API exposes raw addresses or `Unsafe`, treat the replacement process as a planned API evolution, not merely an internal refactoring.

## 16. Controlled migration strategy

### Step 1: Lock down the baseline

Record the JDK, vendor, JVM flags, build tools, dependency versions, architecture, OS, runtime image, and key tests/benchmarks. Identify flows using Unsafe.

### Step 2: Complete the inventory

Combine source scans, `jdeps`, dependency graphs, and runtime evidence. Record call sites, owners, and purposes; do not conclude based solely on imports or scanners.

### Step 3: Choose APIs by purpose

- CAS/field access → `VarHandle` or `Atomic*`.
- Queue/waiting → `LockSupport` or concurrency abstractions.
- Heap arrays → standard access/`System.arraycopy`.
- Byte buffers → `ByteBuffer` or buffer views.
- Off-heap memory → FFM on supported JDKs.
- Object creation/class definition → constructors/factories, official serializers/frameworks, and `MethodHandles.Lookup` when appropriate.

### Step 4: Separate low-level changes from large framework upgrades

If possible, replace each Unsafe API group separately. Keep old/new comparison tests to identify regressions. Changing memory ordering and upgrading an entire framework in one commit makes finding causes difficult.

### Step 5: Verify semantics, not only compilability

Check:

- Return values and side effects.
- Atomicity, memory visibility, and concurrency.
- Buffer bounds, byte order, and alignment.
- Lifetime and native memory deallocation.
- Exceptions, failure behavior, and cancellation.
- Thread confinement and shareability.

### Step 6: Review performance on the right workload

Unsafe was sometimes chosen for specific latency or allocation goals. After replacement, benchmark on representative workloads; inspect warmup, throughput, tail latency, contention, and memory footprint. Optimize deeply only when data shows it is necessary.

Do not use a microbenchmark that does not reflect production as a reason to keep internal APIs indefinitely. Conversely, do not claim the replacement is always faster just because it is a new API.

### Step 7: Rollout, observe, and remove workarounds

Test on staging/canary; monitor crashes, native memory, GC, latency, error rates, and logs for illegal/restricted access. Verify the production container/JDK has the right artifacts. Remove module-opening flags and legacy configurations no longer needed after successful replacement.

## 17. Integrated example: from raw native address to a lifecycle-managed segment

Suppose a legacy cache module manages a record consisting of `long id` and `int flags` in native memory. Unsafe code might allocate a block of bytes, calculate offsets manually, write data, and store the native address in a registry.

The risks:

- Failing to free `address` when an exception occurs.
- Double freeing when multiple owners hold the same address.
- Use-after-free causing hard-to-diagnose errors.
- Wrong offsets or alignment when changing layout/architecture.
- One thread using the memory region while another thread frees it.

With JDK 22+ and FFM, the design direction is describing layout and ownership:

~~~java
import java.lang.foreign.Arena;
import java.lang.foreign.MemoryLayout;
import java.lang.foreign.MemorySegment;
import java.lang.foreign.ValueLayout;

public final class RecordBuffer implements AutoCloseable {
    private static final MemoryLayout LAYOUT =
            MemoryLayout.structLayout(
                    ValueLayout.JAVA_LONG.withName("id"),
                    ValueLayout.JAVA_INT.withName("flags"),
                    MemoryLayout.paddingLayout(4));

    private final Arena arena = Arena.ofConfined();
    private final MemorySegment segment = arena.allocate(LAYOUT);

    public void setId(long id) {
        segment.set(ValueLayout.JAVA_LONG, 0, id);
    }

    public long id() {
        return segment.get(ValueLayout.JAVA_LONG, 0);
    }

    public void setFlags(int flags) {
        segment.set(ValueLayout.JAVA_INT, 8, flags);
    }

    public int flags() {
        return segment.get(ValueLayout.JAVA_INT, 8);
    }

    @Override
    public void close() {
        arena.close();
    }
}
~~~

Usage example:

~~~java
try (RecordBuffer record = new RecordBuffer()) {
    record.setId(1001L);
    record.setFlags(2);

    System.out.println(record.id());
}
~~~

This is an example illustrating a specific layout: `long` at offset 0, `int` at offset 8, plus padding for a sensible total size. With real data, the layout must be matched accurately against the format/protocol/native ABI. If a struct from C has different alignment or packing rules, do not assume offsets blindly.

`Arena.ofConfined()` is appropriate if the object is accessed only by the owning thread. If cache logic needs to be shared across multiple threads, a different arena model and synchronization must be chosen. Simply “having a MemorySegment” does not automatically make a cache design thread-safe.

Compared to raw addresses, the `RecordBuffer` wrapper expresses lifecycle via `AutoCloseable`; when closing the arena, memory is managed by scope. In return, API consumers take on the responsibility of not using the object after `close()` and not holding references beyond its lifetime.

## 18. Common mistakes when removing `Unsafe`

**Merely changing the import to another internal API.** `jdk.internal.misc.Unsafe` is not a sustainable public choice.

**Assuming `--add-opens` solves the long-term problem.** Module flags can support certain reflective accesses, yet do not provide a stable API contract.

**Using `VarHandle.get()` to replace every `getVolatile()`.** Method names and data types may look similar, yet memory ordering has changed.

**Changing CAS yet ignoring return values.** `compareAndSet` returns boolean; `getAndAdd` returns the old value; the caller's contract must be preserved.

**Ignoring ABA and data races.** An atomic primitive operation does not make an entire concurrent algorithm automatically correct.

**Replacing raw memory with `ByteBuffer` and then trying to obtain the internal native address.** That approach can lead code back to unsupported APIs and does not solve ownership.

**Ignoring byte order and alignment.** Reading a `long` with the wrong endianness or offset can still return a valid-looking number with the wrong meaning.

**Using a confined arena for multithreaded shared data.** Lifetime and thread access rules must be chosen according to design.

**Keeping raw pointers in a `long` field without a clear owner.** If the question of who closes/frees and when has not been solved, changing the API class does not eliminate the risk.

**Replacing `allocateInstance` by bypassing constructors another way.** Bypassing invariants is a design risk; the usual approach is an appropriate factory/serialization contract.

**Evaluating dependencies via source search while ignoring runtime JARs.** Application code that does not import Unsafe can still execute through dependencies that use it.

**Treating every static analysis finding as an equal blocker.** An untriggered code path and a direct off-heap memory manager in production require different plans, yet both must be recorded.

**Claiming better performance without representative measurements.** Throughput, tail latency, and memory management overhead all need checking.

## 19. Checklist before finalizing the plan to replace `Unsafe`

- [ ] Identified accurately which artifact/module uses `sun.misc.Unsafe`.
- [ ] Searched source code, dependencies, shaded JARs, and possibly related reflective accesses.
- [ ] Recorded Unsafe methods, purposes, call sites, and critical execution paths.
- [ ] Checked library/framework versions supported on the target JDK.
- [ ] Did not treat `jdk.internal.misc.Unsafe` as a supported replacement API.
- [ ] CAS/atomic operations have appropriate `VarHandle` or `Atomic*` choices.
- [ ] Old/new memory ordering is explicitly documented, without silently weakening visibility.
- [ ] Evaluated data races, ABA, and correctness of concurrency algorithms.
- [ ] Array/buffer operations replaced raw offsets with APIs having clear bounds/types when possible.
- [ ] For off-heap, ownership, lifetime, alignment, byte order, and thread-safety are clearly defined.
- [ ] Chose APIs compatible with the minimum supported JDK, especially for FFM.
- [ ] Serialization/object creation flows preserve invariants and failure semantics.
- [ ] Dynamic class generation uses appropriate lookup/class loading mechanisms.
- [ ] Recorded exceptions if workarounds must remain, with an owner and removal milestone.
- [ ] Have a testing, benchmarking, and rollout plan on the target runtime image.
- [ ] Release notes and migration documentation clearly indicate which consumers need source edits or rebuilds.

## 21. Conclusion

`sun.misc.Unsafe` is not an issue that can be solved merely by changing imports. It is a collection of multiple low-level mechanisms with different risks: memory access, atomic operations, fences, thread parking, object allocation, and class generation. A sustainable migration requires **inventorying by actual usage purpose**, identifying accurately who owns the code, and choosing supported APIs suitable for the target JDK version.

For concurrent state, prioritize `VarHandle` and `Atomic*` classes or high-level concurrency abstractions. For arrays and buffers, prioritize Java APIs with explicit bounds and types. For off-heap memory on supported JDKs, FFM provides the `Arena`/`MemorySegment` model to manage access rights and lifetime. For serialization, object creation, and dynamic class generation, re-evaluate invariants, lookup permissions, and framework capabilities instead of seeking an equivalent “bypass controls” operation.

A successful migration does not only compile on the new JDK: it also preserves atomicity, visibility, layout, lifetime, exceptions, and runtime behavior while gradually reducing dependence on internal APIs that the organization does not control.
