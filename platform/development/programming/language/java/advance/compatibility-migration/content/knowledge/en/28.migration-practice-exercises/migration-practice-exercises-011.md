# Detecting Charset, Locale, or Serialized Data Regressions

In **Java Advance Compatibility Migration**, an application can pass compilation, ordinary unit tests, and startup smoke tests yet still misprocess data previously written by an older version. Three easily overlooked problem areas are **charset**, **locale**, and **serialization** (data serialization). For example, an old file written in ISO-8859-1 gets read by a newer Java runtime as UTF-8 by default; an identifier has its case converted according to the CI machine's locale; or data stored via `ObjectOutputStream` can no longer be restored after changing class/package/`serialVersionUID`.

This lab belongs to the **Practice Exercises** chapter of **Java Advance Compatibility Migration**. Learners will build a small laboratory consisting of **producer V1** and **reader V2**, generate test data with the old version, save immutable fixtures, and then write regression tests to catch bugs before release. The example picks JDK 17 as baseline and JDK 21 as target for easy illustration, yet the process applies to any JDK pair officially supported by a project. All sample data is synthetic data, requiring no secrets or production systems.

**Expected outcome:** knowing how to distinguish encoding regressions from locale data and serialization regressions; knowing how to design *old writer → new reader* tests; knowing how to use fixtures with provenance, negative tests, and multi-environment execution matrices; knowing when to fix source code, data, configuration, or format contracts.

## 1. Objectives, Prerequisites, and Deliverables

Upon completion, learners can:

1. Explain why `new String(bytes)` and text APIs using the default charset are risky for long-term stored data.
2. Use `CharsetDecoder` in `REPORT` mode to detect invalid bytes instead of silently substituting characters.
3. Distinguish user locale from locales used for **machine identifiers**, number formatting, and dates/times.
4. Reproduce differences between `Locale.ROOT` and locales such as `tr-TR` during case conversion.
5. Read a V1 object stream on a V2 binary that has class changes while preserving a valid compatibility contract.
6. Recognize `InvalidClassException`, `ClassNotFoundException`, post-deserialization default fields, and risks of native Java serialization.
7. Use golden fixtures, checksums, and regression tests to avoid validating broken behavior.
8. Clearly report which compatibility dimensions were verified and which are not yet guaranteed.

**Prerequisites:** permitted baseline and target JDKs (illustrated with 17 and 21), `javac`/`java`, a dedicated working directory, and JUnit 5 if running automated tests. Maven or Gradle is only used to orchestrate tests; the core knowledge lies in standard Java APIs. No database, Docker, or external data downloads are needed to follow the lesson.

**Lab deliverables**:
- Fixture set `customer-v1.ser`, `name-v1-latin1.txt`, `name-v1-utf8.txt` generated by V1.
- Metadata for producer version, charset, schema/class identity, and SHA-256.
- JUnit tests for charset, locale, serialization, and negative cases.
- Execution results on baseline/target JDKs, with environment details recorded.
- Decision report: PASS, FAIL, or BLOCKED for each contract.

## 2. Failure Context to Detect

Suppose Customer service V1 stored three kinds of data:

| Data | How V1 wrote it | What V2 must guarantee |
|---|---|---|
| Legacy customer name | Text bytes in ISO-8859-1 | Decodes `Café` accurately |
| Identifier | String normalized to uppercase | Code `id` must become `ID`, independent of machine locale |
| Customer snapshot | Java `Serializable` class V1 | V2 reads ID, name, balance, and assigns default for new field |

**Intentional bugs introduced in the lab**:
- V2 uses `new String(bytes)` on Latin-1 bytes → can produce replacement characters on JDKs defaulting to UTF-8.
- V2 uses `raw.toUpperCase()` → result depends on `Locale.getDefault()`.
- V2 changes `serialVersionUID` or the class package → V1 object stream is no longer compatible.
- V2 adds a new field yet forgets to handle the default value when reading old streams → downstream code hits `null`.

This lesson does not aim to prove JDK 21 has a bug. These failures are **application data contract bugs** exposed when changing the Java environment, runtime defaults, or source code.

### 2.1. Testing lifecycle

~~~text
Producer V1 (JDK baseline)
       |
       +-- write byte fixtures and metadata
       |
       v
Immutable golden fixtures
       |
       v
Reader V2 (JDK target)
       |
       +-- Test decode charset
       +-- Test locale-independent identifiers
       +-- Test native serialized object
       +-- Test semantic invariants
       |
       v
PASS / FAIL + root cause + evidence
~~~

Most importantly: **do not generate fixtures using V2 and feed them back to V2**. That is merely a round-trip test of the new version and does not catch compatibility regressions.

A usable structure:

charset-locale-serialization-lab/

  output/

~~~

**Reason for separating V1 and V2 sources:** both may define the same fully-qualified class name `org.example.lab.model.SavedCustomer`, yet bytecode must be compiled separately. Do not put both class files with the same name into one source set and expect the classpath to distinguish versions automatically.

### 3.1. Fixture rules

- Fixtures are created by **V1 source/tag/release**, never automatically regenerated when V2 tests fail.
- Filenames express format/version/charset; do not use generic names like `sample.dat`.
- Original bytes must be preserved, especially when Git line-ending conversion could alter text files.
- Independently reviewed expected business values exist.
- Manifest/hashes exist to detect whether data was altered.
- Fixtures must be **synthetic/trusted input**. Do not deserialize object streams grabbed randomly from the network.

If real data is needed to increase coverage, only use copies processed through masking and data governance procedures. Do not commit raw production snapshots/PII/secrets.

## 4. Part A — Creating the V1 Model for Native Serialization

Create `v1-producer/src/org/example/lab/model/SavedCustomer.java`:

~~~java
package org.example.lab.model;

import java.io.Serial;
import java.io.Serializable;
import java.math.BigDecimal;

public final class SavedCustomer implements Serializable {
    @Serial
    private static final long serialVersionUID = 1L;

    private String customerId;
    private String displayName;
    private BigDecimal credit;

    public SavedCustomer(
            String customerId,
            String displayName,
            BigDecimal credit) {
        this.customerId = customerId;
        this.displayName = displayName;
        this.credit = credit;
    }

    public String getCustomerId() {
        return customerId;
    }

    public String getDisplayName() {
        return displayName;
    }

    public BigDecimal getCredit() {
        return credit;
    }
}
~~~

The class implements `Serializable` and has an **explicit `serialVersionUID = 1L`**. Choosing `1L` is only for illustration, not a rule to apply to every class. For real classes with historical streams, the UID value must match the already-written format; do not reset it arbitrarily just to look "clean".

### 4.1. Why use BigDecimal?

Credit is a business decimal number. `BigDecimal("10.25")` preserves the exact value to assert; using `double` and comparing directly can introduce binary representation inaccuracies into a test focused on serialization.

### 4.2. Why do class and package matter?

Java object serialization is tied to **class identity, stream class descriptor, UID, and field descriptors**. If V2 arbitrarily changes `org.example.lab.model.SavedCustomer` to `org.example.app.Customer`, `ObjectInputStream` does not automatically deduce it is the same schema. An explicit migration reader/compatibility adapter or a Java-class-independent format solution may be required.

## 5. Part A — Writing the V1 Fixture Generator Program

Create `v1-producer/src/org/example/lab/fixture/WriteFixtures.java`:

~~~java
package org.example.lab.fixture;

import java.io.ObjectOutputStream;
import java.math.BigDecimal;
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.Path;
import org.example.lab.model.SavedCustomer;

public final class WriteFixtures {
    private WriteFixtures() {}

    public static void main(String[] args) throws Exception {
        if (args.length != 1) {
            throw new IllegalArgumentException(
                    "Usage: WriteFixtures <output-directory>");
        }

        Path output = Path.of(args[0]);
        Files.createDirectories(output);

        // Four bytes: 43 61 66 E9. Character é is U+00E9.
        Files.write(
                output.resolve("name-v1-latin1.txt"),
                "Café".getBytes(StandardCharsets.ISO_8859_1)
        );

        // Vietnamese text data is stored as UTF-8 per a separate contract.
        Files.write(
                output.resolve("name-v1-utf8.txt"),
                "Đặng Ánh".getBytes(StandardCharsets.UTF_8)
        );

        SavedCustomer legacy = new SavedCustomer(
                "000042",
                "Café",
                new BigDecimal("10.25")
        );

        try (ObjectOutputStream out = new ObjectOutputStream(
                Files.newOutputStream(
                        output.resolve("customer-v1.ser")))) {
            out.writeObject(legacy);
        }

        System.out.println(
                "Created V1 fixtures in " + output.toAbsolutePath()
        );
    }
}
~~~

The code intentionally uses **explicit encodings right in V1** so fixtures have deterministic bytes. This is a data compatibility exercise, not relying on luck regarding which default charset the V1 machine happens to use.

### 5.1. Compiling and running V1 on the baseline JDK

POSIX/Git Bash shell example:

~~~bash
mkdir -p output/v1-classes output/generated-fixtures

javac --release 17 \
  -d output/v1-classes \
  v1-producer/src/org/example/lab/model/SavedCustomer.java \
  v1-producer/src/org/example/lab/fixture/WriteFixtures.java

java -cp output/v1-classes \
  org.example.lab.fixture.WriteFixtures \
  output/generated-fixtures
~~~

In this step, set `JAVA_HOME` or select the executable so **both `javac` and `java` are genuinely the baseline JDK**. Use `java -version` and the executable path to confirm, rather than inferring from IDE settings.

On PowerShell, create directories with `New-Item -ItemType Directory -Force` and pass the same two source paths using PowerShell syntax; the `\` in the example above is a line-continuation character for POSIX shells, **not** PowerShell's line-continuation character.

### 5.2. Evidence to save

Verify the three files exist, record checksums:

~~~bash
sha256sum output/generated-fixtures/*
~~~

If the environment lacks `sha256sum`, use the OS's built-in hash tool. PowerShell provides `Get-FileHash -Algorithm SHA256`. Hashes help detect if fixtures were altered during checkout, transfer, or inadvertent "snapshot updates".

For the Latin-1 fixture, expected bytes:

~~~text
43 61 66 E9
 C  a  f  é
~~~

In UTF-8, `é` is normally bytes `C3 A9`. This is the difference used to test the decoder.

### 5.3. Freezing fixtures

Copy the three generated files to `v2-reader/src/test/resources/legacy/`. Save a text manifest/README:

~~~text
Fixture set: customer-v1
Producer application: lab V1
Producer JDK: baseline 17 (specific vendor/build during actual run)
Producer class: org.example.lab.model.SavedCustomer
Serialization UID: 1
Latin-1 file: ISO-8859-1, expected text "Café"
UTF-8 file: UTF-8, expected text "Đặng Ánh"
Serialized customer: id="000042", name="Café", credit="10.25"
SHA-256: record actual hash of each file, do not commit placeholders
Change control: do not regenerate using reader V2
~~~

For text files if the repository performs line-ending normalization, appropriate Git attributes rules can be configured to preserve fixture bytes. Binary `.ser` files must be marked as binary so tools do not alter their contents.

## 6. Part B — Reproducing Charset Regression

### 6.1. Incorrect reading code

In Java, the constructor:

~~~java
String decoded = new String(bytes);
~~~

uses the JVM's **default charset**. If V1 wrote `0xE9` in ISO-8859-1 while V2 uses UTF-8, that lone byte **is not a valid UTF-8 sequence**. Depending on the API, the decoder may replace the character with `�` or throw an error.

A test checking only "no exception thrown" can pass even when the user sees garbled accents in the name.

### 6.2. Correct reading code per storage contract

~~~java
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.Path;

byte[] bytes = Files.readAllBytes(
        Path.of("src/test/resources/legacy/name-v1-latin1.txt")
);

String decoded = new String(
        bytes,
        StandardCharsets.ISO_8859_1
);
~~~

If the file was written in ISO-8859-1, switching the JVM default to UTF-8 does not change the decoded value.

### 6.3. Using a strict decoder to detect invalid data

`new String(bytes, StandardCharsets.UTF_8)` can substitute malformed byte sequences with replacement characters, hiding data corruption instead of surfacing an exception. For data streams requiring integrity, use a decoder:

~~~java
import java.nio.ByteBuffer;
import java.nio.charset.CharacterCodingException;
import java.nio.charset.CodingErrorAction;
import java.nio.charset.StandardCharsets;

static String strictUtf8(byte[] bytes)
        throws CharacterCodingException {

    return StandardCharsets.UTF_8
            .newDecoder()
            .onMalformedInput(CodingErrorAction.REPORT)
            .onUnmappableCharacter(CodingErrorAction.REPORT)
            .decode(ByteBuffer.wrap(bytes))
            .toString();
}
~~~

With `name-v1-latin1.txt`, strict UTF-8 decoding must **fail with an error**. With `name-v1-utf8.txt`, it must return `Đặng Ánh`.

Key takeaway: "bytes are not UTF-8" **does not automatically mean the data is corrupt**; if the V1 contract is Latin-1, attempting to decode as UTF-8 is the reader's bug. Conversely, if the contract is UTF-8, encountering malformed bytes must follow a fail/quarantine/log policy, not assume falling back to Latin-1 is safe.

## 7. Part B — Writing Charset Tests

A JUnit 5 test can be used:

~~~java
import static org.junit.jupiter.api.Assertions.*;

import java.io.InputStream;
import java.nio.ByteBuffer;
import java.nio.charset.CodingErrorAction;
import java.nio.charset.StandardCharsets;
import org.junit.jupiter.api.Test;

class CharsetRegressionTest {

    private byte[] fixture(String path) throws Exception {
        try (InputStream in = getClass().getResourceAsStream(path)) {
            assertNotNull(in, "Missing legacy fixture: " + path);
            return in.readAllBytes();
        }
    }

    @Test
    void latin1FixtureMustDecodeAsLatin1() throws Exception {
        byte[] bytes = fixture("/legacy/name-v1-latin1.txt");

        assertArrayEquals(
                new byte[]{0x43, 0x61, 0x66, (byte) 0xE9},
                bytes
        );

        String decoded = new String(
                bytes, StandardCharsets.ISO_8859_1
        );
        assertEquals("Café", decoded);
    }

    @Test
    void latin1FixtureIsNotValidUtf8() throws Exception {
        byte[] bytes = fixture("/legacy/name-v1-latin1.txt");

        var decoder = StandardCharsets.UTF_8
                .newDecoder()
                .onMalformedInput(CodingErrorAction.REPORT)
                .onUnmappableCharacter(CodingErrorAction.REPORT);

        assertThrows(
                java.nio.charset.MalformedInputException.class,
                () -> decoder.decode(ByteBuffer.wrap(bytes))
        );
    }

    @Test
    void utf8FixtureKeepsVietnameseCharacters() throws Exception {
        byte[] bytes = fixture("/legacy/name-v1-utf8.txt");

        String decoded = StandardCharsets.UTF_8
                .newDecoder()
                .onMalformedInput(CodingErrorAction.REPORT)
                .onUnmappableCharacter(CodingErrorAction.REPORT)
                .decode(ByteBuffer.wrap(bytes))
                .toString();

        assertEquals("Đặng Ánh", decoded);
    }
}
~~~

Example uses `InputStream.readAllBytes()` (Java 9+) and `var` (Java 10+), fitting the Java 17/21 lab. When used on older JDKs, adjust the API or Java source level.

**Note:** the second test intentionally asserts a UTF-8 error. This is a **negative test that PASSES when receiving the expected exception**, not a bug in the decoder.

### 7.1. Regression symptoms to record

| Symptom | Conclusion |
|---|---|
| Latin-1 decodes properly to `Café` | Reader uses the right codec |
| Latin-1 decodes to `Caf�` | Reader decodes with wrong charset or replaces malformed bytes |
| UTF-8 Vietnamese loses diacritics | Incorrect encoding or fixture pipeline |
| One OS passes, another OS fails | Likely relying on default charset/source conversion |
| Test file hash changes after checkout | Fixture artifact bytes were not preserved |

### 7.2. Do not test only with ASCII

The string `Hello123` has identical bytes in many common charsets; a test using only ASCII **does not detect charset mismatches**. Include non-ASCII characters, Vietnamese characters, Unicode combining marks, emoji if supported by the format, and bytes invalid under the contract.

## 8. Part C — Reproducing Locale Regression

**Locale** describes language/region rules for case conversion, sorting, number formatting, date formatting, resource bundles, and display text. It is **not** a charset: a Unicode string can decode properly yet still be normalized wrongly because of locale.

### 8.1. Bug: toUpperCase() without specifying locale

~~~java
String key = "id".toUpperCase();
~~~

The result depends on `Locale.getDefault()`. For instance, under the Turkish locale `tr-TR`, the character `i` uppercases to **`İ`** (Latin capital letter I with dot above), not `I`. An identifier used as a key or field name can fail to match another system.

### 8.2. Fix: use Locale.ROOT for language-independent identifiers

~~~java
import java.util.Locale;

String canonical = "id".toUpperCase(Locale.ROOT);
// "ID" following a stable rule for language-independent identifiers.
~~~

Do not apply `Locale.ROOT` to every case: Turkish UIs may need `tr-TR` rules; personal names or multilingual text have their own policies. Distinguish **machine keys** from **human-facing text**.

### 8.3. Writing tests without mutating global Locale

Some tests change `Locale.setDefault(...)` and forget to restore it, causing flakiness when JUnit runs in parallel. Instead of mutating global state, test with explicit locales:

~~~java
import static org.junit.jupiter.api.Assertions.*;
import java.util.Locale;
import org.junit.jupiter.api.Test;

class LocaleRegressionTest {

    @Test
    void identifierIsStableAcrossLocale() {
        String raw = "id";

        assertEquals(
                "ID",
                raw.toUpperCase(Locale.ROOT)
        );

        assertEquals(
                "İD",
                raw.toUpperCase(
                        Locale.forLanguageTag("tr-TR"))
        );
    }

    @Test
    void machineIdentifierUsesRootLocale() {
        String raw = "invoice-id";
        String canonical = raw.toUpperCase(Locale.ROOT);

        assertEquals("INVOICE-ID", canonical);
    }
}
~~~

The first test shows that **different locale rules are valid**; it does not prove the Turkish locale is wrong. A regression occurs when code **omits the locale** for data requiring a stable contract.

### 8.4. How to create a "fail first" test

1. Write a temporary implementation using `raw.toUpperCase()`.
2. Run under a different default locale (for example Turkish) in a separate process.
3. Observe the key mismatch.
4. Fix the implementation to `toUpperCase(Locale.ROOT)` if the field is a machine identifier.
5. Re-run under multiple locales.

In CI, you can run the test JVM with `-Duser.language=tr -Duser.country=TR` to proactively expose bugs; this affects **only the configured process**. If the build tool forks the test JVM, pass the flags to the exact test fork, not just the shell/daemon.

## 9. Locale in Decimal Numbers: Format for Parsing or for Display?

Monetary amounts:
- `1,234.50` typically follows US English conventions.
- `1.234,50` typically follows German conventions.

If a machine protocol commits only to a decimal dot and no grouping, use **canonical decimal format**, such as `BigDecimal.toPlainString()` and an explicit parser. Do not use locale-less `NumberFormat.getInstance()` for long-term stored data.

### 9.1. Testing with explicit DecimalFormatSymbols

~~~java
import static org.junit.jupiter.api.Assertions.*;
import java.math.BigDecimal;
import java.text.DecimalFormat;
import java.text.DecimalFormatSymbols;
import java.text.ParsePosition;
import java.util.Locale;
import org.junit.jupiter.api.Test;

class DecimalLocaleTest {

    @Test
    void germanNumberHasExpectedDisplayFormat() {
        DecimalFormat format = new DecimalFormat(
                "#,##0.00",
                DecimalFormatSymbols.getInstance(Locale.GERMANY)
        );

        String displayed = format.format(
                new BigDecimal("1234.50")
        );

        assertEquals("1.234,50", displayed);
    }

    @Test
    void parseLegacyGermanDecimalFully() {
        DecimalFormat format = new DecimalFormat(
                "#,##0.00",
                DecimalFormatSymbols.getInstance(Locale.GERMANY)
        );
        format.setParseBigDecimal(true);

        String raw = "1.234,50";
        ParsePosition position = new ParsePosition(0);
        Number parsed = format.parse(raw, position);

        assertNotNull(parsed);
        assertEquals(raw.length(), position.getIndex());
        assertEquals(-1, position.getErrorIndex());
        assertInstanceOf(BigDecimal.class, parsed);
        assertEquals(
                0,
                ((BigDecimal) parsed).compareTo(
                        new BigDecimal("1234.50"))
        );
    }
}
~~~

**Why use ParsePosition?** A parser can read only a valid prefix and silently discard the rest. Full-string tests must verify the number of characters consumed, not just the return value.

### 9.2. UI formatting and wire format should have different policies

- **UI:** format appropriate to the user's locale, though test outputs may require controlled updates when locale data/CLDR changes across JDKs.
- **Wire/data storage:** locale-independent format, explicit schema, independent of defaults.
- **Money:** prefer `BigDecimal`/minor units with currency/scale/rounding policy.
- **Identifiers:** never apply number formatting with grouping to IDs.

Avoid asserting that every JDK-formatted string must match byte-for-byte across all releases. If it is a file export contract, freeze the format and test specifically; if it is solely UI display, consider user goals and the updated locale data.

## 10. Locale in Dates/Times and Timezones

Timezone and locale are **two different things**:
- `Locale` affects language-specific presentation of month names, weekdays, and separators.
- `ZoneId` affects how an instant is converted into a date/time in a region.
- `Instant` is a point on the timeline and carries no local timezone.
- `LocalDateTime` does not represent an instant without a zone/offset.

### 10.1. Machine data needs a stable timestamp format

~~~java
import java.time.Instant;
import java.time.format.DateTimeFormatter;

Instant timestamp = Instant.parse(
        "2024-10-26T14:30:00Z"
);

String encoded = DateTimeFormatter.ISO_INSTANT
        .format(timestamp);
~~~

If the protocol uses ISO instant, test against the exact contract `2024-10-26T14:30:00Z`. If the data represents a local appointment, do not automatically convert everything to UTC and lose timezone region/business semantics.

### 10.2. Using explicit locales for month names

~~~java
import java.time.LocalDate;
import java.time.format.DateTimeFormatter;
import java.util.Locale;

LocalDate date = LocalDate.of(2024, 10, 26);

String english = date.format(
        DateTimeFormatter.ofPattern(
                "d MMM yyyy", Locale.ENGLISH
        )
);
~~~

String output can be affected by the JDK's locale data version. If display formatting is part of a public contract, tests against the target JDK and backward compatibility decisions are needed. For machine protocols, use ISO formats or formatters with fixed symbols/schema.

### 10.3. Do not depend on the current date

A test like:

~~~java
assertEquals(
        "2026-11-12",
        java.time.LocalDate.now().toString()
);
~~~

will fail depending on the date or timezone. Inject `Clock`:

~~~java
import java.time.Clock;
import java.time.Instant;
import java.time.LocalDate;
import java.time.ZoneId;

Clock clock = Clock.fixed(
        Instant.parse("2026-11-12T00:00:00Z"),
        ZoneId.of("Asia/Ho_Chi_Minh")
);

LocalDate date = LocalDate.now(clock);
~~~

This is how to fix test inputs, not advice to freeze time in production.

## 11. Part D — Defining the V2 Model to Read Old Java Serialization

V2 keeps the fully-qualified name `org.example.lab.model.SavedCustomer` yet adds a new field `segment`.

Create `v2-reader/src/main/java/org/example/lab/model/SavedCustomer.java`:

~~~java
package org.example.lab.model;

import java.io.Serial;
import java.io.Serializable;
import java.math.BigDecimal;

public final class SavedCustomer implements Serializable {
    @Serial
    private static final long serialVersionUID = 1L;

    private String customerId;
    private String displayName;
    private BigDecimal credit;

    // New field that does not exist in the V1 stream.
    private String segment;

    public String getCustomerId() {
        return customerId;
    }

    public String getDisplayName() {
        return displayName;
    }

    public BigDecimal getCredit() {
        return credit;
    }

    public String getSegment() {
        // New field deserialized from a V1 stream will be null.
        return segment == null ? "LEGACY" : segment;
    }
}
~~~

**Note:** `ObjectInputStream` restores fields according to the Java serialization protocol; it **does not invoke the serializable class's normal constructor** when restoring its serializable state. Therefore, putting defaults in a new constructor is not a reliable way to populate fields absent from a V1 stream.

In the example, the getter applies the default policy `LEGACY`. Real systems may require a migration adapter or `readObject` depending on semantics; do not silently give a new field a default if it affects authorization or transaction state.

### 11.1. What conditions allow a V1 stream to be read by V2?

- Class name/package still matches.
- `serialVersionUID` is compatible.
- Field changes do not violate serialization compatibility rules.
- Referenced classes in the object graph can still be loaded.
- Classloader/module/security policy permits the required read path.
- Meanings of old business fields were not changed.
- New fields absent in old streams have a handling policy.

Keeping `serialVersionUID` does not guarantee every class change is compatible; it is only **one part of the verification mechanism**.

## 12. Part D — Testing V2 Reading the V1 Stream

Create test `v2-reader/src/test/java/org/example/lab/LegacyCompatibilityTest.java`:

~~~java
package org.example.lab;

import static org.junit.jupiter.api.Assertions.*;

import java.io.InputStream;
import java.io.ObjectInputStream;
import java.math.BigDecimal;
import org.example.lab.model.SavedCustomer;
import org.junit.jupiter.api.Test;

class LegacyCompatibilityTest {

    @Test
    void readsSerializedCustomerFromV1() throws Exception {
        try (InputStream raw = getClass().getResourceAsStream(
                "/legacy/customer-v1.ser")) {

            assertNotNull(raw, "Missing immutable V1 fixture");

            try (ObjectInputStream input =
                    new ObjectInputStream(raw)) {

                Object decoded = input.readObject();

                assertInstanceOf(SavedCustomer.class, decoded);
                SavedCustomer customer = (SavedCustomer) decoded;

                assertEquals(
                        "000042",
                        customer.getCustomerId()
                );
                assertEquals(
                        "Café",
                        customer.getDisplayName()
                );
                assertEquals(
                        0,
                        customer.getCredit().compareTo(
                                new BigDecimal("10.25"))
                );
                assertEquals(
                        "LEGACY",
                        customer.getSegment()
                );
            }
        }
    }
}
~~~

This test reads only a **trusted binary fixture generated by V1 of the lab itself**. Native deserialization must not be applied indiscriminately to bytes arriving from networks/partners; see the security section below.

### 12.1. An intentional negative test

Try editing a **copy** of V2:

~~~java
@Serial
private static final long serialVersionUID = 2L;
~~~

Re-run the reader on `customer-v1.ser`. Normally `InvalidClassException` will occur because the local class UID differs from the stream. This proves compatibility conditions were broken, **not** a reason to mechanically change UIDs of all classes.

After observing, restore `1L` and re-test. Do not edit the V1 fixture to make the test pass.

### 12.2. Another negative test: changing the package

If the V2 model is changed to `org.example.lab.v2.SavedCustomer` without migration code, the V1 stream still references `org.example.lab.model.SavedCustomer`. When the old class is no longer available, the reader may report `ClassNotFoundException`. Renaming a package is a class-structure change, not an ordinary field change.

In real systems a clearly designed migration reader/class resolver can be used, yet arbitrary class-name aliases should not be used for untrusted bytes.

## 13. Security: Java Deserialization Only with Trusted Data

`ObjectInputStream` has a history of risk when reading untrusted object graphs: the classpath may contain unexpected object types, and several gadget chains have led to exploits. Therefore:

- In the lab, read only **checksum-verified synthetic V1 fixtures**.
- Do not place native Java serialization on new public input boundaries.
- For systems that must keep reading old streams, review the threat model, data source, sizes, types, and filter policy.
- Java has `ObjectInputFilter` (JEP 290) and related filter context mechanisms (JEP 415) for supported cases.
- Build an allowlist matching the object graph, limiting depth/references/bytes where possible.
- Verify that filters are actually applied in the runtime/reader.
- Do not treat filters as the sole solution instead of reducing the deserialization surface.
- Prefer formats with explicit schemas and stable identity when designing long-term storage.

### 13.1. Testing corrupt data differs from testing untrusted data

A truncated byte stream can cause `EOFException` or `StreamCorruptedException`. Testing this case verifies error handling, yet **does not prove the application is safe against all malicious payloads**.

For important stored data:
- When parsing fails, log record ID/format version in a controlled way without logging the full payload.
- Quarantine for investigation rather than replacing with a default success object.
- Do not perform side effects or update state before validating correctness.
- Provide metrics for failure counts and migration progress.

- The test fork's JDK.

## 15. Execution Matrix Between Baseline and Target JDK

An illustrative plan:

| Producer | Reader | File/source | Expected |
|---|---|---|---|
| V1 / JDK 17 | V1 / JDK 17 | Generated fixtures | Baseline control |
| V1 / JDK 17 | V2 / JDK 17 | Latin-1, UTF-8, `.ser` | PASS if V2 still supports Java 17 |
| V1 / JDK 17 | V2 / JDK 21 | Same fixtures, **do not regenerate** | **Mandatory PASS** |
| V2 / JDK 21 | V2 / JDK 21 | New V2 data | Normal regression |
| V2 / JDK 21 | V1 / JDK 17 | V2 data | Mandatory only if rollback/mixed version required |

**Do not force testing combinations unsupported by frameworks/libraries.** If V2 only supports JDK 21, omit the V2-on-JDK-17 cell and record the reason. If the project still needs rollback to V1 during a rolling deployment, test **old reader/new writer** as well; V2 reading V1 alone is insufficient to prove safe rollback.

### 15.1. Must distinguish three outcome types

- **PASS:** executed and asserted the exact business contract.
- **FAIL:** confirmed a regression or data no longer compatible.
- **BLOCKED:** could not run due to unmet environment/test infrastructure; no compatibility evidence yet.

Do not report PASS if fixtures are missing, the test runner executed 0 tests, or tests were skipped.

## 16. Practicing "Fail First, Fix, Lock"

To understand why regression tests are valuable, follow an intentional sequence.

### Exercise 1: Charset error

1. Use V1 to create `name-v1-latin1.txt` with bytes `43 61 66 E9`.
2. In V2, test the buggy code `new String(bytes)`.
3. Observe under a UTF-8 default JDK: the result is no longer `Café` or contains replacement characters.
4. Write a test requiring `Café` to be returned.
5. Fix the reader to use `ISO_8859_1` for the known legacy format.
6. Add a negative test with strict UTF-8 on Latin-1 bytes.
7. Re-run on the target JDK and record the fixture checksum.

**Criteria:** proper code does not depend on the running machine's default charset.

### Exercise 2: Locale error

1. Choose identifier `id`.
2. Test upper-casing with English and Turkish locales.
3. Create a failing case when the application relies on the default locale.
4. Define machine canonicalization using `Locale.ROOT`.
5. Test `ID` across multiple locales.
6. Separate UI formatting tests from machine protocols.

**Criteria:** stored/exchanged identifiers have a stable format; display text still uses the user-requested locale.

### Exercise 3: Serialization UID error

1. Generate `customer-v1.ser` from V1 with UID 1.
2. V2 reads and asserts ID, name, credit, and the default new field.
3. In a copy of V2, change the UID to 2.
4. Observe the `InvalidClassException` error.
5. Restore UID 1.
6. Try renaming the package to see that class identity matters.
7. Write down conclusions on compatibility boundaries.

**Criteria:** V2 reads the V1 stream without regenerating; adding a new field does not break business semantics.

### Exercise 4: Adding unknown/invalid inputs

1. Create a corrupt byte-sequence fixture or truncated file separately in the test suite.
2. Assert the reader returns a controlled error.
3. Do not fall back to a fake "valid" object.
4. Do not log the full raw serialized payload.
5. If using a filter, write a test proving the filter is applied.

**Criteria:** corrupt data is detected and creates no business side effects.

## 17. Extension: Detecting Regressions When the Format Is JSON

Not every application uses native `Serializable`; many systems use JSON/Jackson to store objects. JSON does not use Java's `serialVersionUID`, yet can still change between versions due to:
- Naming strategy converting camelCase to snake_case.
- Including/excluding null fields.
- Default values and missing fields.
- Enum representation.
- Numeric precision.
- Date/time formatting and timezone.
- Polymorphic type information.
- Jackson module registration and framework auto-configuration.

A V1 fixture:

~~~json
{
  "customerId": "000042",
  "displayName": "Café",
  "credit": "10.25",
  "status": "ACTIVE",
  "createdAt": "2024-10-26T21:30:00+07:00"
}
~~~

When V2 reads, assert:
- ID `000042` remains a string without losing leading zeros.
- Unicode name is accurate.
- Credit uses decimal semantics, not rounded by `double`.
- Status maps accurately.
- Timestamp preserves the instant/offset contract.
- V1 fields missing in V2 schema are handled per policy.

If V2 reads old JSON and writes it back, and V1 must still be able to read that record during a rollback window, test **old reader/new writer** separately.

### 17.1. Do not regenerate "golden JSON" with V2

A common mistake: when snapshot tests fail, running "update snapshots" and committing the new values. That approach can legitimize dropped fields or altered timezones.

To change a contract:
- Version the new format.
- Keep V1 fixtures for the support window.
- Have reviewed expected semantics.
- Test the V1→V2 adapter.
- Retire the old contract only when retention/rollback policies permit.

## 18. Distinguishing Charset, Locale, and Serialization When Investigating

The three categories have overlapping symptoms yet different root-cause layers.

| Symptom | Charset | Locale | Serialization |
|---|---|---|---|
| `Café` becomes `Caf�` | **Very likely** | Unlikely | Possible if stream/string layer changed |
| `id` becomes `İD` | No | **Case conversion under tr-TR** | Only if code converts after reading |
| `InvalidClassException` | Not primary cause | No | **UID/class compatibility** |
| JSON parses yet amount is wrong | Possible if bytes corrupt | Possible from number parsing | Business mapper/codec may be involved |
| Date displays differently | Possible if text encoding wrong | Locale and timezone | Post-deserialization formatter |
| `ClassNotFoundException` reading `.ser` | No | No | Class identity/classpath |
| Fails only on Linux CI | Default charset/bytes | Locale/timezone | Classpath/JDK/config also possible |
| Returns null in new field | Not typical | Not typical | Absent field on deserialize or JSON mapping |

**Do not fix every error by changing the JVM-wide default charset or locale.** Identify what bytes the original data has, which reader interprets it, and which business contract must be preserved.

## 19. Collecting Empirical Evidence for Diagnosis

A failure report should include:
- Producer tag, commit, JDK vendor/build.
- Reader tag, JDK vendor/build.
- Fixture name, hash, format, and declared charset.
- Test name, stack trace, or actual/expected values.
- Locale ID/timezone/charset of the test process.
- Serializer provider/dependency versions.
- Class/package/`serialVersionUID` if a Java stream.
- Whether running locally, in CI, or in a container.
- Did any regeneration/normalization alter bytes?

Example of a short report:

~~~text
TEST: legacyLatin1MustDecode
PRODUCER: customer-v1, JDK baseline
READER: customer-v2, JDK target
FIXTURE: name-v1-latin1.txt
DECLARED CHARSET: ISO-8859-1
EXPECTED: "Café"
ACTUAL: "Caf�"
ROOT CAUSE: decoder used default UTF-8 instead of ISO-8859-1
FIX: explicit charset per format
REGRESSION: strict decode + golden fixture SHA-256
~~~

If the failure happens only in CI, also inspect `java -version` of the **test fork** and whether fixture bytes were converted by Git/process encoding.

## 20. Testing Data Integrity and Semantic Invariants

Testing does not just verify that the parser can read:

| Invariant | Verification |
|---|---|
| ID | `000042` retains leading zeros |
| Name | `Café` and `Đặng Ánh` do not lose diacritics |
| Money | `BigDecimal("10.25")` keeps exact value |
| Segment | V1 data lacking new field has defined default |
| Status | Unknown enum does not silently map to success |
| Date/time | Preserves instant or local semantics per contract |
| Format version | Decoder selects the right format/charset |
| Class identity | Java stream loads compatible class |
| Integrity | Invalid bytes do not construct fake business objects |
| Security | Does not open deserialization of arbitrary classes |
| Retention | Can read generations still within support window |

Especially for financial and identity data, **"no exception" is not PASS** if the decoded value is wrong.

## 21. When to Use a Migration Adapter Instead of Keeping the Old Format?

V2 should not always keep reading legacy V1 native Java serialization directly forever. When multi-year support is needed, formats tied to Java class names/UIDs create difficulties when changing packages, modules, and dependencies.

A controlled direction:

~~~text
Legacy V1 stream
       |
       v
Dedicated trusted migration reader
       |
       v
Stable domain data transfer object
       |
       v
Versioned JSON/Avro/Protobuf/DB representation
       |
       v
New application readers
~~~

To migrate safely:
1. Identify all objects and versions needing to be read.
2. Read using a runtime/classpath supporting V1 with trusted data.
3. Normalize into a neutral domain model.
4. Write the new format with explicit schema/version.
5. Assert business invariants before/after.
6. Record provenance, checksums, and error counts.
7. Rehearse rollback/forward-only strategy.
8. Retire the V1 reader only when retention ends or migration is complete.

If the old stream carries deserialization risks, the migration reader must be properly isolated/permission-managed; do **not** expose a general-purpose deserializer on a public input boundary.

## 22. When Running in CI or Containers

A lab that passes locally can fail in CI because:
- Tests run on a different JDK.
- Fixture files were not copied into test resources.
- Default charset/locale differs.
- Filename case differs on Linux.
- Git line endings altered bytes.
- Maven/Gradle test JVM is configured differently.
- CI has cached stale generated fixtures.
- Tests call `Locale.setDefault` causing races with other tests.
- Docker image does not contain resources.
- Jackson/serializer versions differ due to dependency resolution.

### 22.1. Environment control matrix

| Variable | How to verify |
|---|---|
| JDK | Print vendor/runtime version of test JVM |
| Charset | `Charset.defaultCharset()` for diagnostics, without making tests depend on it |
| Locale | `Locale.getDefault()` and locale used in code |
| Timezone | `ZoneId.systemDefault()` and business ZoneId |
| Fixture bytes | SHA-256 compared against manifest |
| Test resources | `getResourceAsStream` is non-null |
| Classpath | `SavedCustomer.class.getName()` and dependency versions |
| Test execution | JUnit reports show the right number of tests |
| Docker image | Digest, JDK, copied resources |
| Build tool | Maven/Gradle wrapper + resolved dependency graph |

### 22.2. Do not fix bugs by forcing JVM-wide defaults

Flags such as `-Dfile.encoding=UTF-8`, `-Duser.language=en`, or `-Duser.timezone=UTC` can be useful to standardize environments, yet **do not replace reading legacy formats using the right charset/locale/timezone contract**. If the real data source is ISO-8859-1, forcing UTF-8 for the entire JVM does not turn the original bytes into UTF-8.

A locale/timezone matrix can be used to **expose bugs**, then fix code using explicit encoding/Locale/Clock where appropriate.

## 23. Advanced Lab: Separating Tests into Three Layers

A good test suite may include:

**Layer 1 – Byte-level:**
- Fixture hashes.
- Signature bytes `E9`, UTF-8 `C3 A9`.
- Strict decoder malformed input.

**Layer 2 – Type-level:**
- Java `SavedCustomer` deserializes accurately.
- UID/class identity remains compatible.
- JSON DTO maps typed fields accurately.
- BigDecimal/date/time do not lose precision.

**Layer 3 – Business-level:**
- Customer ID unchanged.
- Customer data with diacritics not corrupted.
- Credit remains accurate.
- Missing V1 field is not misinterpreted as "privileged" or an invalid state.
- Erroneous inputs are rejected or quarantined per policy.

With only layer 1, bytes may be right yet business mapping wrong. With only layer 3, failures make it hard to tell codec errors from logic bugs. **All three layers enable evidence-backed diagnosis**.

## 24. Advanced Lab: Old Reader/New Writer

Suppose V2 adds `segment` while rollback to V1 is still required. New question: can V1 read streams written by V2?

In Java serialization, adding a field with the same `serialVersionUID` may allow an old reader to ignore the new field per corresponding compatibility rules, **yet is not enough to guarantee business semantics or that every class change is safe**.

How to verify:
1. Write a V2 writer generating `customer-v2.ser` from an object containing the new field.
2. Launch the V1 reader with the real V1 classpath/runtime.
3. Read the V2 fixture.
4. Assert the fields V1 uses.
5. Evaluate whether there are V2 semantics V1 does not understand.
6. If a new semantic field/cost is mandatory for correctness, do not declare rollback safe merely because `ObjectInputStream` throws no exception.

The rollback window should be defined by the rollout plan. If V2 data cannot be read by V1, an approved **forward-only cutover or migration plan** is needed instead of promising full rollback.

## 25. Troubleshooting for Common Failures

| Error/symptom | Diagnosis | Remediation |
|---|---|---|
| Latin-1 outputs `�` | Read with wrong charset | Explicit legacy charset |
| `MalformedInputException` | Bytes invalid for chosen encoding | Read per format contract or quarantine |
| `UnmappableCharacterException` | Decoder cannot map byte sequence | Identify data charset/source |
| Key differs on Turkish CI | Default locale | Machine keys use `Locale.ROOT` |
| Number `1.234,50` parses wrongly | Locale/decimal symbols | Explicit parser + full consumption |
| Month names differ across JDKs | Locale data/CLDR changed | Lock UI policy or canonical wire format |
| Date off by one day | Timezone/default clock | Explicit ZoneId/Clock |
| `InvalidClassException` | UID/field/class incompatibility | Analyze V1–V2 stream/class |
| `ClassNotFoundException` | Old class/package no longer exists | Versioned reader/adapter |
| New field returns null | Field absent in V1 stream | Explicit default/migration semantics |
| Missing serialized fixture | Test resource not copied | Check `src/test/resources` |
| Fixture hash changed | Text conversion/regeneration | Restore immutable fixture |
| Build passes with 0 tests | Test runner/discovery failure | Check Surefire/Gradle/JUnit |
| Parse passes yet balance wrong | Business mapping/precision | BigDecimal/invariant assertions |
| Native deserialize unknown input | Security risk | Trusted source, filters, isolation |
| V2 reads V1, V1 cannot read V2 | Rollback not guaranteed | Cross-version matrix/forward-only policy |

Do not handle a data-reading error by deleting the failing fixture. Often that is the very sample valuable for catching regressions.

## 26. Common Mistakes When Doing the Lab

- Generating the golden fixture with V2 and calling it a legacy fixture.
- Changing fixtures whenever tests fail without reviewing the contract.
- Testing only with ASCII and concluding charset compatibility.
- Using `new String(bytes)` with default charset for files with long-lived formats.
- Using a lossy decoder and asserting only "no exception".
- Using `String.toUpperCase()` without locale for identifiers.
- Forcing `Locale.ROOT` onto all UI text without considering user languages.
- Using `double` for amounts and losing decimal precision.
- Testing `LocalDate.now()` against a fixed date without injecting Clock.
- Treating timezone and locale as the same concept.
- Keeping the same `serialVersionUID` and assuming arbitrary class changes remain readable.
- Changing UID to "fix" `InvalidClassException` without understanding the schema.
- Renaming a class's package and expecting the object stream to map automatically.
- Reading native Java serialization of untrusted bytes.
- Asserting only that the object is non-null without checking business fields.
- Ignoring null new fields when reading V1 streams.
- Treating V2-reads-V1 PASS as proof of V1-reads-V2 PASS.
- Failing to store fixture hashes/provenance.
- Forgetting to check which JDK actually runs the test fork.
- Ignoring skipped tests or pipelines running 0 tests.
- Fixing CI by changing system-wide default charset without understanding legacy formats.
- Neglecting retention/replay/rollback windows when removing legacy readers.

## 31. Conclusion

**Detecting charset, locale, and serialized data regressions requires testing in the right direction: the old version writes, the new version reads and preserves business meaning.** A V2 round-trip alone is not enough. Create immutable V1 fixtures with checksums, test with non-ASCII bytes, set explicit charsets/locales for machine formats, and verify serialization class identity, `serialVersionUID`, old/new fields, and deserialization safety.

The lab workflow is **generate data from V1 → freeze fixtures → write negative/positive tests → run V2 reader on target JDK → classify failures at bytes/locale/schema layers → fix code and re-verify → record compatibility/rollback matrix**. When those tests run regularly in CI, changing JDKs, frameworks, or serializers carries much less risk of turning historical data into wrong values that the system still silently accepts.
