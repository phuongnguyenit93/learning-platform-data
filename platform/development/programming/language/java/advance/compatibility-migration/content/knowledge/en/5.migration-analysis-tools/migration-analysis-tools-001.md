# Using java, javac, and javap to Verify Runtime and Class Files

In a Java migration, knowing “JDK 21 is installed on the machine” is not enough to prove the application actually runs on JDK 21 or that class files were compiled for the right version. A machine can have multiple JDKs installed; the shell, service manager, container, and pipeline can select different executables. The compiler can also generate bytecode for a release different from the compiler's own version.

The three tools `java`, `javac`, and `javap` help verify three related yet distinct parts:

- **`java`** launches the application and reveals the runtime executing the program.
- **`javac`** compiles source code into class files; source, target, and release options determine the target language, APIs, and bytecode.
- **`javap`** reads class files or packaged classes to inspect class-file version, class structure, descriptors, and bytecode.

Combining these three tools answers key questions: which executable is actually selected; which JDK the running JVM belongs to; which compiler produced the class files; which runtime level the class files require; where the application is loading classes from; and whether a compatibility failure occurs at compile, link, or runtime.

## 1. Distinguishing Runtime, Compiler, and Class Files

The JDK is the Java development kit, typically including the Java launcher/runtime, compiler, and diagnostic tools. In an environment with multiple JDKs, the three commands can come from three different locations if `PATH`, `JAVA_HOME`, or configuration scripts are inconsistent.

| Component | Role | Question to Verify |
|---|---|---|
| `java` | Runs classes, modules, or executable JARs | Which runtime vendor/version is the process using? |
| `javac` | Compiles `.java` into `.class` | Which JDK does the compiler belong to and what is the target release? |
| `javap` | Analyzes class files/bytecode | What major version, descriptors, and instructions does the class file have? |

The compiler version does not necessarily equal the generated bytecode version. For example, `javac` from JDK 21 can compile with `--release 17`, producing class files compatible with Java 17 if source and dependencies also meet that constraint. Conversely, `javac` can generate Java 21 class files that a Java 17 runtime cannot load.

Therefore, distinguish:

1. **JDK used to compile:** version and vendor of `javac`.
2. **Target source/API level:** the language level and Java SE APIs the compiler is allowed to use.
3. **Class-file version:** the bytecode format version written into `.class` files.
4. **JVM used to run:** the actual runtime of the process.

These are four related yet non-interchangeable pieces of information.

## 2. Identifying Which Java Executable the System Selects

Before running version checks, determine which files the commands `java`, `javac`, and `javap` resolve to. Looking only at `JAVA_HOME` is insufficient because the shell may find another executable before it in `PATH`, scripts may use absolute paths, or services/containers may have their own environments.

### 2.1. On Windows PowerShell

```powershell
Get-Command java -All
Get-Command javac -All
Get-Command javap -All
where.exe java
where.exe javac
where.exe javap
$env:JAVA_HOME
```

`Get-Command` shows which command PowerShell will pick and lists all matches found. `where.exe` searches for executables along `PATH`. Both commands can return multiple locations if the machine has multiple JDKs installed.

### 2.2. On Linux or macOS

```bash
command -v java
command -v javac
command -v javap
type -a java
type -a javac
type -a javap
printf '%s\n' "$JAVA_HOME"
readlink -f "$(command -v java)"
readlink -f "$(command -v javac)"
```

`command -v` shows how the shell resolves the command; `type -a` can show aliases, functions, or multiple executables; `readlink -f` on Linux finds the true target of a symlink. On macOS, `readlink -f` is not available by default; you can check symlinks with `ls -l` and trace paths using OS tools.

If the shell was opened before changing `PATH`, open a new shell or refresh the environment before re-checking. For services, containers, or pipelines, inspect inside the exact environment creating that process; results from a personal terminal do not represent production.

### 2.3. Invoking Tools via JAVA_HOME to Remove Ambiguity

When wanting to check a specific JDK, invoke the executable using an explicit path.

PowerShell:

```powershell
& "$env:JAVA_HOME\bin\java.exe" --version
& "$env:JAVA_HOME\bin\javac.exe" --version
& "$env:JAVA_HOME\bin\javap.exe" --version
```

Linux/macOS:

```bash
"$JAVA_HOME/bin/java" --version
"$JAVA_HOME/bin/javac" --version
"$JAVA_HOME/bin/javap" --version
```

This invocation verifies the toolset in the `JAVA_HOME` directory. It does not prove the production application also uses that directory; inspect the command line and executable of the runtime process separately.

## 3. Using java to Verify the Runtime

### 3.1. Checking the Java Version

```bash
java -version
java --version
```

`java -version` is the familiar invocation compatible with many JDK generations. `java --version` displays the modern version format on supported JDKs starting in JDK 9. Output usually identifies the version, vendor, or build of the runtime.

Illustrative example:

```text
openjdk version "21.0.5" 2024-10-15
OpenJDK Runtime Environment Temurin-21.0.5+11
OpenJDK 64-Bit Server VM Temurin-21.0.5+11
```

The output above shows that the `java` command just invoked is an OpenJDK 21 build from the Temurin distribution. It does not yet prove the application process is running the same binary, nor does it show which release the application class files were compiled for.

### 3.2. Checking System Properties of a New Runtime

```bash
java -XshowSettings:properties -version
```

This command creates a new JVM, prints several system properties, and exits. Useful properties when inspecting include:

| Property | Meaning |
|---|---|
| `java.version` | Java runtime version |
| `java.vendor` | Runtime vendor |
| `java.home` | Runtime directory used by the JVM |
| `java.vm.name` | VM name |
| `java.vm.version` | VM version |
| `java.class.version` | Class-file version supported by the runtime per the VM specification |
| `os.name`, `os.arch` | Operating system and architecture |
| `file.encoding` | Default charset of the JVM |
| `user.timezone` | Default timezone if determined |

You can filter output per OS to find properties of interest, yet should not save the full output into a ticket if it contains internal paths or sensitive information.

Note: `java -XshowSettings:properties -version` observes the new JVM created by that command. It does not read properties of an already-running application process. To inspect an existing process, use an attach tool such as `jcmd`, JMX, or a suitably protected diagnostic endpoint exposed by the application.

### 3.3. Checking Runtime Modules

On JDK 9 and newer, you can list the modules present in the runtime image:

```bash
java --list-modules
```

The output helps confirm whether the runtime has the required platform modules. This is useful if the application runs on a custom runtime image created via `jlink`, because a trimmed image may not contain all modules of a full JDK.

When running a modular application, you can use:

```bash
java --show-module-resolution --module-path mods --module com.example.app/com.example.Main
```

`--show-module-resolution` prints module resolution details. It is helpful when migration changes the module path, module descriptors, or `requires` relationships. Module syntax must match the application's actual module structure.

### 3.4. Verifying the Runtime of a Running Process

The `java -version` command only reports the runtime of the command just invoked. To verify a running application, identify its PID and query that exact process. On HotSpot/OpenJDK, you can use:

```bash
jps -lv
jcmd <pid> VM.version
jcmd <pid> VM.command_line
jcmd <pid> VM.system_properties
```

These commands identify the JVM, VM version, command line, and system properties of the process at query time. `jcmd` requires appropriate attach permissions; it may fail across different users, different container namespaces, when attach is disabled on the process, or if the runtime does not support the tool.

If attaching is not possible, record the version from the application's startup logs or a controlled diagnostic endpoint. Do not infer the production runtime from the version installed on the build machine.

## 4. Using javac to Verify the Compiler and Target Compatibility Level

### 4.1. Identifying the Compiler Version

```bash
javac -version
javac --version
```

Both forms are supported depending on JDK version; `--version` is the modern syntax. Output tells you which compiler was invoked, not which release the compiler emits class files for. The target level is determined by compilation options such as `--release`, `-source`, and `-target`.

If `java --version` and `javac --version` yield different major versions, the machine is resolving runtime and compiler from different JDKs or using a dedicated toolchain config. This may be intentional, yet must be documented and controlled.

### 4.2. Distinguishing source, target, and release

Compilation options have different meanings:

| Option | What It Controls | Limitation |
|---|---|---|
| `-source N` | Accepted Java syntax/language features | Does not automatically restrict which JDK APIs are used |
| `-target N` | Generated class-file version | Does not automatically guarantee code only uses APIs from release N |
| `--release N` | Source level, target class file, and public Java SE APIs of release N | Available since JDK 9; supports only releases for which the current compiler has data |

When using JDK 9 or newer to compile for an older release, prefer `--release`. Setting only `-source 17 -target 17` on a JDK 21 compiler, for example, can still accidentally reference new JDK 21 APIs; the resulting class files may fail on JDK 17 due to missing methods or API classes.

Do not combine `--release` with `-source` or `-target` in the same command. Choose one consistent configuration method.

### 4.3. Compiling for the Target Release

Suppose the application needs to run on Java 17 while the build environment uses JDK 21:

```bash
mkdir -p out
javac --release 17 -d out src/main/java/com/example/Main.java
```

`--release 17` instructs the compiler to use Java 17 language and Java SE API levels while emitting class files in the format compatible with Java 17. `-d out` places `.class` files in the output directory.

Run with the target runtime to check:

```bash
/path/to/jdk-17/bin/java -cp out com.example.Main
```

In practice, compile the entire source set with the right classpath/module path and dependencies, not just a single file. When using external libraries, `--release` controls only Java SE APIs; it does not guarantee third-party libraries are also compatible with the target runtime.

### 4.4. Checking Compiler Configuration When Building a Project

With build tools, inspect the actual compiler configuration rather than checking only the default `javac` in the terminal. Gradle may use Java toolchains, `options.release`, `sourceCompatibility`, `targetCompatibility`, compiler forks, or task-specific settings. Maven may configure `maven-compiler-plugin` with `release`, `source`, and `target`.

These configurations can differ between main source, test source, generated source, or submodules. Confirm which task ran and which compiler that task used. `javac -version` in the terminal does not prove Gradle/Maven invoked the right compiler if the build tool selects its own toolchain.

## 5. Using javap to Read Class Files

`javap` is the Java class-file disassembler. It can display class structure, methods, fields, descriptors, constant pool, annotations, and bytecode. This tool is very useful when you need to know at what level a `.class` file was generated and what the compiled code contains.

### 5.1. Viewing the Tool Version

```bash
javap -version
```

This command prints the version of `javap` being run. That is the analysis tool's version, not the version of the class file under inspection. To know the class-file version, use `-verbose` on a specific class.

### 5.2. Viewing Class Structure

```bash
javap -classpath build/classes/java/main com.example.Main
```

The command searches for class `com.example.Main` in the class output directory and displays public/protected members and signatures in Java-like form. `-classpath` specifies where to search for classes; the class name is passed as a fully qualified name without `.class`.

To view private members as well:

```bash
javap -p -classpath build/classes/java/main com.example.Main
```

To view JVM descriptors of methods and fields:

```bash
javap -s -classpath build/classes/java/main com.example.Main
```

Descriptors help verify signatures at the bytecode level, including parameter types, return types, and primitive/reference representations. This is useful when investigating linkage errors between compiled libraries and runtime APIs.

### 5.3. Viewing Class-File Version and Metadata

```bash
javap -verbose -classpath build/classes/java/main com.example.Main
```

In the output, look for lines such as:

```text
minor version: 0
major version: 61
```

`major version` is the major version field in the class-file header. Some common milestones:

| Java release | Class-file major version |
|---|---:|
| Java 8 | 52 |
| Java 11 | 55 |
| Java 17 | 61 |
| Java 21 | 65 |
| Java 25 | 69 |

These numbers are class-file version milestones, not `javap` version numbers. Seeing major version 65 means the class file was generated in Java 21 format; it does not by itself prove the compiler was JDK 21 because newer compilers can also target Java 21.

For classes using preview features, `minor version` can have the special value `65535`. Preview class files can only run on the same runtime release with preview enabled, typically via `--enable-preview`; preview class files cannot be treated as bytecode portable to the next release.

### 5.4. Reading Bytecode

```bash
javap -c -classpath build/classes/java/main com.example.Main
```

`-c` displays the JVM instructions of each method. For instance, a method call in source can become `invokevirtual`, `invokestatic`, `invokeinterface`, or `invokespecial`. Bytecode helps inspect which calls and control flow the compiler generated, especially when investigating bridge methods, lambdas, method references, boxing/unboxing, or compiler differences.

Combining options:

```bash
javap -p -s -c -verbose -classpath build/classes/java/main com.example.Main
```

Detailed output can include:

- Access flags, superclass, and interfaces.
- Fields, methods, and JVM descriptors.
- Constant pool and symbolic references.
- Bytecode instructions and operands.
- Line number table and local variable table if the class was compiled with debug information.
- Annotations and attributes stored in the class file.

Not all metadata is always present. For example, local variable names may not be stored if the compiler did not emit corresponding debug information. `javap` inspects compiled artifacts and does not fully reconstruct original source code.

### 5.5. Analyzing Classes in a JAR

You can specify a JAR as the classpath:

```bash
javap -verbose -classpath app.jar com.example.Main
javap -c -classpath app.jar com.example.service.OrderService
```

This checks the class packaged inside the artifact rather than looking only at pre-packaging output directories. Two files with the same name can exist in multiple directories or JARs; `javap` resolves according to the provided classpath. Specify the artifact and classpath explicitly to avoid inspecting the wrong copy.

For a multi-release JAR, you can instruct `javap` to select a view by release:

```bash
javap --multi-release 17 -verbose -classpath library.jar com.example.LibraryType
```

This is important because a multi-release JAR can contain a base class and alternative class versions under `META-INF/versions/<N>/`. The runtime selects the copy matching the running release; inspecting the wrong view can lead to wrong conclusions about actual bytecode.

## 6. Verifying Whether Class Files Run on the Target Runtime

A regular class file can only be supported by a JVM when its class-file version does not exceed what that JVM understands. If the application loads a class file newer than the runtime, `UnsupportedClassVersionError` typically occurs.

For example: Java 21 produces major 65 class files; a Java 17 runtime supports only up to major 61. Running a major 65 class on Java 17 prevents the JVM from loading that class. Renaming the JAR, increasing heap, or adding dependencies will not solve this bytecode format error.

### 6.1. Quick Check with javap and java

Suppose the class resides in `build/classes/java/main`:

```bash
javap -verbose -classpath build/classes/java/main com.example.Main
java -version
java -cp build/classes/java/main com.example.Main
```

Read `major version` from `javap`, then cross-check the actual runtime. The final execution command is the direct verification, because beyond class-file version, the application can still fail due to missing classes, missing methods, module access, or runtime dependencies.

### 6.2. Distinguishing Version Errors from Linkage and Classpath Errors

| Error | Common Meaning | Investigation Direction |
|---|---|---|
| `UnsupportedClassVersionError` | JVM does not support the class's class-file version or preview metadata | Check major/minor version with `javap -verbose`, verify actual runtime |
| `ClassNotFoundException` | Code requests loading a class yet the class loader cannot find it | Check classpath/module path and artifacts |
| `NoClassDefFoundError` | Required class unavailable at link/runtime, or earlier class initialization failed | Check dependencies, class loaders, and root exception |
| `NoSuchMethodError` | Bytecode references a method not provided by the class loaded at runtime | Check library versions and descriptors with `javap -s` |
| `NoSuchFieldError` | Bytecode references a field absent from the runtime class | Check APIs and the actually loaded artifact |
| `IllegalAccessError` | Bytecode/module-level access permissions are not met | Check access flags, modules, and dependencies |
| `InaccessibleObjectException` | Reflection blocked by the module system | Check reflective access, `--add-opens`, and related libraries |

Do not lump every runtime error into “wrong Java version”. `UnsupportedClassVersionError` indicates a class-file format issue; `NoSuchMethodError` is usually an API version mismatch between compile time and runtime; `ClassNotFoundException` usually involves classpath or module path. Diagnosing the exact error class leads to the right fix.

## 7. Verifying Which Class the JVM Actually Loads

A project may contain multiple copies of a class with the same fully qualified name: in stale build directories, multiple JARs, plugin folders, or libraries provided by an application server. `javap` checks the class on the classpath you specify; that does not yet prove the runtime loaded that exact file.

With HotSpot/OpenJDK on JDK 9 and newer, you can enable unified logging:

```bash
java -Xlog:class+load=info -cp app.jar com.example.Main
```

Class-loading logs usually show the class name and loading source, helping identify which JAR or directory the class came from. On older JDKs, `-verbose:class` is the familiar option:

```bash
java -verbose:class -cp app.jar com.example.Main
```

Logging options generate substantial output; in production, choose an appropriate log level, duration, and storage location. Do not leave class-loading logs enabled long-term on high-load systems without evaluating cost and log volume.

Once the class source is found, inspect that exact artifact:

```bash
javap -verbose -classpath path/to/the-loaded-library.jar com.example.LibraryType
```

If the runtime uses custom class loaders, plugin loaders, or module layers, loading sources can be more complex than a simple classpath. In that case, combine logs, class loader configs, and runtime evidence from the application.

## 8. Checking the Classpath and Module Path

Even when class files have a compatible major version, the runtime can still load the wrong dependency or fail to locate a needed class.

### 8.1. Classpath

Example running an application with a class directory and libraries:

```bash
java -cp "build/classes/java/main:lib/*" com.example.Main
```

On Windows, the classpath separator is a semicolon:

```powershell
java -cp "build/classes/java/main;lib/*" com.example.Main
```

Classpath order can determine which class is found first when multiple copies with the same name exist. Check the order and actual contents of directories/JARs, especially when migration changes dependency resolution or packaging.

### 8.2. Module Path

Modular applications use a module path and module name:

```bash
java --module-path mods --module com.example.app/com.example.Main
```

`javac` also has module path options like `--module-path` and `--module-source-path`; `javap` can inspect modules via `--module-path` and `--module`. When migrating an application from classpath to module path, verify module descriptors, exported packages, required modules, and reflective access.

### 8.3. Classes in Multi-Release JARs

A multi-release JAR can provide different implementations for different JDKs. Thus, a `javap` command without specifying a release may display a different view from the class chosen by a specific runtime. Use `javap --multi-release N` to inspect the corresponding view and check JAR structure when needed.

## 9. A Practical Verification Workflow for Java Migration

You can use the following workflow for each application or module moving to a new JDK.

### Step 1: Record the Current and Target Runtime

Run `java --version` in the respective environment, recording vendor, version, build, and `java.home`. Identify the executable the service/container actually invokes. Record current JDK and target JDK separately; do not infer from a developer machine.

### Step 2: Record the Actual Compiler

Run `javac --version` and inspect the executable path. With Gradle/Maven, verify the toolchain/compiler each task uses. Record the target release in the build configuration, including any differences across main, test, and generated sources.

### Step 3: Inspect Generated Class Files

After a clean build, run `javap -verbose` on representative classes in the output and packaged artifacts. Check `major version`, preview markers if any, descriptors, and APIs/methods referenced by bytecode when needed.

### Step 4: Run the Artifact on the Target Runtime

Use an explicit `java` path of the target JDK and a classpath/module path matching deployment. Run smoke tests and representative functional flows. Save the runtime identity and execution results.

### Step 5: Verify the Runtime Class Source

If linkage errors occur or a wrong dependency is suspected, enable class-loading logs in a test environment. Identify the JAR/directory supplying the class and inspect that exact artifact with `javap`.

### Step 6: Cross-Check Differences and Resolve

Classify differences as runtime version, class-file version, compiler target, Java SE APIs, dependency linkage, classpath/module path, or module access. Adjust build/toolchain/dependency or runtime configuration per the actual cause and re-run relevant checks.

### Step 7: Store Evidence

Save executed commands, tool versions, target release, major version of representative classes, artifact checksum or build id, runtime used, and test results. Redact sensitive paths or parameters before sharing logs.

## 10. End-to-End Example: Compiling with a Newer JDK, Running on an Older JDK

Suppose the development team uses JDK 21 to build, yet the product needs to support Java 17. You can run:

```bash
# 1. Confirm compiler
javac --version

# 2. Compile with Java 17 API and class-file target
javac --release 17 -d out src/main/java/com/example/Main.java

# 3. Inspect class file
javap -verbose -classpath out com.example.Main

# 4. Run with Java 17 runtime
/opt/jdk-17/bin/java -version
/opt/jdk-17/bin/java -cp out com.example.Main
```

The expected `javap` output is major version 61 for regular Java 17 classes. A Java 17 runtime can load that class if dependencies, modules, and other runtime conditions are also compatible.

If you replace `--release 17` with `-source 17 -target 17` when the compiler is JDK 21, the compiler can still permit references to APIs that exist only in JDK 21. When running on Java 17, the class file can pass the major-version check yet fail with `NoSuchMethodError` or `NoClassDefFoundError`. This is why both API target and bytecode target must be controlled.

## 11. Checklist for Verifying Runtime and Class Files

- [ ] Identified actual paths of `java`, `javac`, and `javap`.
- [ ] Recorded vendor, version, build, and `java.home` of the runtime under inspection.
- [ ] Verified the runtime of the running process, not just the terminal runtime.
- [ ] Identified the actual compiler used by the build tool or pipeline.
- [ ] Explicitly recorded source level, API release, and target class-file version.
- [ ] Used `javap -verbose` to inspect representative classes from output and packaged artifacts.
- [ ] Checked preview class files if the project enables preview features.
- [ ] Executed the artifact with the exact target runtime.
- [ ] Checked classpath/module path and JVM class-loading sources when in doubt.
- [ ] Distinguished class-file version errors from API linkage, class loading, and module access errors.
- [ ] Saved evidence by build id/release and redacted sensitive data.

## 12. Conclusion

`java`, `javac`, and `javap` provide three complementary perspectives for verifying a Java application: the runtime actually selected, the compiler and target release, and the format and content of generated class files. During migration, identify the exact executables in the deployment environment, use `--release` to constrain both APIs and bytecode when appropriate, inspect artifacts with `javap`, and run that exact artifact on the target runtime. If errors occur, classify by class-file version, linkage, classpath, or module access to fix the right root cause.
