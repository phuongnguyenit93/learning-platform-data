# `--release`: synchronizing language rules, bytecode, and API of the target version

When compiling an application with a newer JDK while still needing to run on an older JDK, setting only the source and target versions is not enough. For example, a team might use JDK 21 to compile while wanting the artifact to run on Java 17. If only `-source 17 -target 17` is used, the compiler can still see the JDK 21 API and allow the source code to call methods that do not yet exist in Java 17. When running on Java 17, the artifact can encounter linkage errors even though the bytecode was generated at the Java 17 level.

The `--release` option of `javac` solves this problem by synchronizing three factors according to a target Java version: accepted language rules, generated bytecode format, and the Java SE API set that source code is allowed to reference at compile time. This is an important tool for defining a module's Java baseline and maintaining compatibility when upgrading the JDK used during the build process.

## 1. Three factors that need to be synchronized during compilation

A Java compilation has at least three independent aspects:

1. **Language rules (source language level):** which Java version's syntax and language features the compiler accepts.
2. **Bytecode version (class-file target):** which Java version's JVM can read the `.class` file format generated by the compiler.
3. **Platform API:** which standard JDK classes and methods the source code is allowed to call.

These three factors must align with the baseline that the module declares it supports. If only the first two factors are synchronized, source code can still reference APIs newer than the target runtime.

For example, an application wants to support Java 17 while building on JDK 21:

| Factor | Required value |
|---|---|
| Language rules | Java 17 |
| Bytecode | Java 17 (class-file major version 61) |
| Java SE API | Java 17 API set |
| JDK running the compiler | Can be JDK 21 |
| Minimum JDK to run the artifact | Java 17, provided dependencies and the environment are also compatible |

The JDK running the compiler does not necessarily have to match the minimum JDK used to run the application. `--release` allows using a newer compiler to generate an artifact targeting an older release within the range of releases supported by that compiler.

## 2. How do `-source`, `-target`, and `--release` differ?

### 2.1. `-source` specifies the language rules

`-source N` instructs the compiler to apply the language rules of Java N. It controls which syntax and language features are accepted.

For example, the compiler may reject `record` syntax when the source level is lower than the Java version that introduced this feature into the language. However, `-source` does not by itself restrict the APIs that the compiler sees.

### 2.2. `-target` specifies the bytecode format

`-target N` instructs the compiler to generate class files in the format of Java N. The JVM may reject loading a class file if the bytecode version is higher than what the JVM supports.

`-target` does not by itself restrict the APIs of the JDK being used to compile. If the compiler runs on JDK 21, source code can still see Java 21 APIs even if the target bytecode is set lower.

### 2.3. `--release` synchronizes all three factors

`--release N` instructs the compiler to:

- Apply the language rules of Java N.
- Generate bytecode compatible with Java version N.
- Allow using only Java SE APIs provided in release N.

The compiler uses per-release platform API description data distributed with the JDK (typically via `ct.sym` data) to check API references. As a result, source code cannot accidentally call a Java SE API that only appeared after the target version.

Example:

```bash
javac --release 17 -d out src/main/java/com/example/App.java
```

This command uses the invoked compiler to compile according to Java 17 rules, generate Java 17 bytecode, and restrict the Java SE API to the Java 17 level.

| Option | Language rules | Bytecode | Platform API |
|---|---|---|---|
| `-source 17` | Java 17 | Per separate target/default configuration | Can see the API of the JDK running the compiler |
| `-target 17` | Per separate source/default configuration | Java 17 | Can see the API of the JDK running the compiler |
| `-source 17 -target 17` | Java 17 | Java 17 | Can still see newer APIs of the compiler JDK |
| `--release 17` | Java 17 | Java 17 | Java SE API of Java 17 |

`--release` is not a post-compilation bytecode conversion step. It takes effect directly during compiler checking and class file generation.

## 3. Why can using only `-source` and `-target` cause errors?

Suppose a team uses JDK 21 to build a library, but the library must run on Java 17. In the source code, there is a call to `Files.mismatch`, an API added after Java 17.

```java
import java.nio.file.Files;
import java.nio.file.Path;

public final class FileComparator {
    public long compare(Path left, Path right) throws Exception {
        return Files.mismatch(left, right);
    }
}
```

If only configured as:

```bash
javac -source 17 -target 17 FileComparator.java
```

the compiler running on JDK 21 can accept the API call because that API exists in JDK 21. Bytecode is generated at the Java 17 level, but the class still contains a symbolic reference to a method that does not exist in Java 17. When running on Java 17, the JVM may throw `NoSuchMethodError` when the code path calls that method.

If using:

```bash
javac --release 17 FileComparator.java
```

the compiler rejects the `Files.mismatch` call because this method does not belong to the Java SE API of release 17. The error is detected immediately during the build process, before the artifact is released.

This is an important difference between "bytecode can be read by an older JVM" and "source code only uses APIs provided by the older JVM". An artifact truly matches the baseline only when both conditions are met, along with dependencies and other runtime requirements.

## 4. How to use `javac --release`

### 4.1. Determine which releases the compiler supports

```bash
javac --help
```

In the standard options section, look at the `--release` description and supported releases. The compiler can only compile for the current release or a certain number of older releases for which that JDK still provides compatibility data. A Java 17 compiler cannot be used to target Java 21.

Check the actual JDK:

```bash
java -version
javac -version
```

`java` and `javac` can come from different JDKs if `PATH` or `JAVA_HOME` is configured inconsistently. When investigating build errors, verify both and their actual executable paths.

### 4.2. Compile a single source file

```bash
mkdir -p out
javac --release 17 -d out src/main/java/com/example/App.java
```

`-d out` specifies the directory containing the class files. The `--release 17` option controls the source level, target bytecode, and platform API.

### 4.3. Compile multiple source files

On Linux/macOS, you can use:

```bash
mkdir -p out
find src/main/java -name '*.java' -print0 \
  | xargs -0 javac --release 17 -d out
```

Or use a build tool such as Gradle/Maven to manage source sets, dependencies, annotation processors, and incremental compilation. In real-world projects, the build tool is usually the appropriate place to set a consistent baseline.

### 4.4. Do not combine `--release` with `-source` or `-target`

Do not configure simultaneously:

```bash
javac --release 17 -source 17 -target 17 App.java
```

`--release` already specifies both source and target. `javac` does not allow combining `--release` with the `-source` or `-target` options; choose one clear configuration method.

## 5. Configuring `--release` in Gradle

In the Gradle Java plugin, `JavaCompile.options.release` is the way to declare the target release for the compiler. You can use a newer JDK toolchain to run the compiler and set a lower release for the artifact.

Kotlin DSL example (`build.gradle.kts`):

```kotlin
java {
    toolchain {
        languageVersion.set(JavaLanguageVersion.of(21))
    }
}

tasks.withType<JavaCompile>().configureEach {
    options.release.set(17)
}
```

In this example:

- The toolchain requires a Java 21 compiler.
- `options.release` requires compiling according to the Java 17 baseline.
- Source code must not use syntax or Java SE APIs introduced only in Java 18 or later.
- Class files are generated in the Java 17 format.

With Groovy DSL (`build.gradle`):

```groovy
java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)
    }
}

tasks.withType(JavaCompile).configureEach {
    options.release = 17
}
```

It is best to place the configuration in a convention plugin or shared build management location if multiple modules must adhere to the same baseline. If each module has a different Java target, configure it per module and clearly document the reason.

### 5.1. Distinguishing toolchain, `options.release`, and test runtime

The following three configurations answer three different questions:

| Configuration | Role |
|---|---|
| Java toolchain | Which JDK/compiler is used to execute the compilation task or related tasks. |
| `options.release` | Which release's language rules, bytecode, and platform API the source code is compiled against. |
| Java launcher for test/app | Which JVM actually runs the tests or application. |

Setting a Java 21 toolchain and `options.release = 17` does not automatically make tests run on Java 17. If you need to prove the application runs on the Java 17 baseline, configure a Java 17 test launcher and run integration/smoke tests on that runtime.

Kotlin DSL example for a test task running on Java 17:

```kotlin
tasks.withType<Test>().configureEach {
    javaLauncher.set(javaToolchains.launcherFor {
        languageVersion.set(JavaLanguageVersion.of(17))
    })
}
```

Ensure JDK 17 is available or that the environment's toolchain resolver can provision it. In a real pipeline, check the JVM version output of the test worker to confirm the runtime matches expectations.

### 5.2. Apply to all necessary source sets

`tasks.withType<JavaCompile>()` typically covers Java compilation tasks such as main and test. If the project has custom source sets, generated sources, or submodules with their own plugins, verify that the corresponding tasks actually receive `options.release`.

For builds combining Java, Kotlin, Scala, Android, or annotation processors, do not assume a single `JavaCompile` configuration automatically controls every compiler. Each language/plugin has its own options to set the language/API target and toolchain. They must be synchronized to the same baseline.

## 6. Using Maven Compiler Plugin

With Maven, you can configure the release in `maven-compiler-plugin`:

```xml
<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-compiler-plugin</artifactId>
            <version>3.13.0</version>
            <configuration>
                <release>17</release>
            </configuration>
        </plugin>
    </plugins>
</build>
```

The plugin version in the example only illustrates the configuration structure; projects need to choose a plugin version compatible with Maven, the JDK, and managed dependency policies. With modern Maven Compiler Plugin, `release` is passed as the `--release` option of `javac` when supported by the compiler.

You should not declare only `source` and `target` when the goal is to guarantee the Java SE API of the target version. If you need to support a JDK too old to have `--release`, you must apply the dedicated compatibility approach in the next section.

## 7. When can `--release` not solve full compatibility?

`--release` restricts the Java SE platform API portion that the compiler uses to check source code. It is not a checker for all dependencies or the runtime.

### 7.1. Does not control dependency bytecode

Suppose the team's application is compiled with `--release 17`, but a third-party library was compiled only for Java 21. The application source code may compile successfully if the dependency has APIs compatible with the compiler, but when running on Java 17, the JVM may reject loading the dependency's classes with an error such as `UnsupportedClassVersionError`.

Therefore, it is necessary to check the bytecode baseline of all runtime dependencies, plugins, agents, and internal modules. `--release` only controls class files generated by the configured compiler tasks.

### 7.2. Does not control third-party library APIs

`--release 17` restricts the Java SE API; it does not know whether an external dependency requires Java 21. A library can declare Java 8 bytecode yet call Java 21 APIs at runtime, or a newer version can have metadata requiring a higher JDK. You need to read metadata, support documentation, and test dependencies on the target runtime.

### 7.3. Does not choose the JDK running the application

An artifact compiled with `--release 17` can run on Java 17 or later provided dependencies and the environment are compatible. This option does not bundle a JVM, select a vendor distribution, or configure containers/production.

### 7.4. Does not guarantee behavioral compatibility

The compiler checks syntax, class-file target, and API reference validity. It does not prove that the program produces the same results, performance, processing order, concurrency behavior, or error handling across every JDK.

### 7.5. Does not cover all internal APIs and dynamic access

`--release` can prevent many references to JDK APIs outside the target release, but it does not replace checking dependencies, reflection, JNI, dynamic loading, or accesses performed via string configuration. Additionally use `jdeps --jdk-internals`, source search, and tests on the target runtime.

## 8. When the project must build on JDK 8

`--release` was introduced in JDK 9. JDK 8's `javac` does not have this option. If you must maintain builds using JDK 8, you can use `-source` and `-target` for language rules and bytecode, but you need to control Java 8 APIs through another mechanism.

Example:

```bash
javac -source 8 -target 8 -bootclasspath /path/to/jdk8/jre/lib/rt.jar \
  -d out src/main/java/com/example/App.java
```

The `rt.jar` path is an example for a standard JDK 8; the specific installation layout may vary by vendor. You must use a boot class path matching the exact target version. You cannot take an equivalent `rt.jar` from JDK 21 because the runtime structure has changed.

Another approach is to use a JDK 8 compiler/toolchain to compile Java 8 sources and APIs, or use an API signature checking tool like Animal Sniffer with the corresponding signature. You must verify how it integrates into the build and the tool's coverage.

If the target is Java 8 but the organization can upgrade the JDK used for building to 9 or higher, using `--release 8` from a modern compiler is usually clearer and less risky than manually maintaining an old boot class path.

## 9. `--release` and preview features

Preview features are provided for experimentation in a specific feature release. They should not be treated as stable APIs/language features that can be carried over to another release unchanged. Enabling preview requires a compiler and runtime matching the release providing the feature; class files using a preview feature must be run with the corresponding preview mechanism.

If a module uses a preview feature, clearly document the experimental feature release, how to enable preview during compilation/execution, and the plan to remove it or migrate to a stable API. Read the compatibility rules of the exact target `javac` because preview has specific restrictions when combined with source/release options.

For modules that need to release libraries or applications with a long-term baseline, avoid letting preview features become an unmanaged part of the public contract.

## 10. Verifying bytecode and APIs after compilation

### 10.1. Check class-file version

`javap -verbose` displays the major version of a class file:

```bash
javap -verbose -classpath build/classes/java/main com.example.App
```

Some common major version values:

| Java release | Class-file major version |
|---|---:|
| Java 8 | 52 |
| Java 11 | 55 |
| Java 17 | 61 |
| Java 21 | 65 |
| Java 25 | 69 |

If the baseline is Java 17, the source code's class files need to be at major version 61. This check confirms the bytecode format, but does not confirm the API set used by the source code. Therefore, it must be combined with configuring `--release` and testing on Java 17.

### 10.2. Check for APIs newer than the baseline

Create a small test that uses an API available only in a newer version, for example `Files.mismatch` when targeting Java 17. When the compiler is properly configured with `--release 17`, that code snippet must be rejected at compile time.

This test helps confirm that the build actually passes `--release` to the compiler. Do not rely solely on looking at the configuration in the build file; inspect compiler logs or execute a compile test in CI.

### 10.3. Run tests on the minimum JDK

Compiling with `--release 17` while only running tests on JDK 21 does not prove the Java 17 runtime works. Run at least smoke tests and integration tests on the minimum supported JDK, along with critical tests on the chosen production runtime.

### 10.4. Check dependencies

For each runtime dependency:

- Determine the artifact's class-file major version.
- Read the minimum JDK requirement in the library's metadata/documentation.
- Check transitive dependencies and native libraries.
- Run the application on the minimum JDK to detect class loading errors or calls to non-existent APIs.

Do not infer the compatibility level of the entire application solely from the class files of the main module.

## 11. Establishing a consistent baseline in CI

To avoid situations where a local build succeeds while CI or production yields a different result, record the baseline across the following layers:

| Configuration layer | Values to manage |
|---|---|
| Gradle/Maven runtime | JDK running the build tool and compatible build tool version. |
| Compiler toolchain | Vendor and feature release of the compiler. |
| Compiler release | `--release` value applied to each source set/module. |
| Test launcher | JDK used to run unit/integration tests. |
| Runtime artifact | Minimum supported JDK and production distribution. |
| Dependencies | Java baseline of each library, plugin, and agent. |
| Container/OS | Image, digest, OS, architecture, and native packages. |

Use build conventions or centralized configuration so every module sharing a baseline receives consistent settings. If modules have different baselines, clearly express this in the module's metadata or documentation to avoid scattered configurations that are hard to trace.

CI should include these steps:

1. Print the JDK version, vendor, and Gradle/Maven version before building.
2. Verify that compiler tasks receive the correct `--release` value.
3. Build and test on the selected compiler toolchain.
4. Run runtime tests on the minimum supported JDK.
5. Check dependency bytecode/APIs and the final artifact.
6. Save logs, artifacts, and environment information so results can be reproduced.

## 12. Checklist when setting up or changing `--release`

- [ ] Clearly identified the minimum JDK that the module commits to supporting.
- [ ] Selected a compiler JDK new enough to support the target release.
- [ ] Used `--release` instead of the `-source`/`-target` pair when supported by the compiler.
- [ ] Verified all related JavaCompile tasks and source sets receive the same configuration.
- [ ] Synchronized Kotlin/Scala/Android compilers or other plugins if used by the project.
- [ ] Verified runtime tests on the minimum JDK, not only on the compiler JDK.
- [ ] Checked bytecode and API baselines of runtime dependencies.
- [ ] Verified the artifact's class-file major version.
- [ ] Added a compile test proving APIs newer than the release are rejected.
- [ ] Documented limitations with preview features, annotation processors, and native dependencies if applicable.
- [ ] Saved JDK version, vendor, build tool, and CI logs.

## Conclusion

`--release N` is the direct way to synchronize language rules, bytecode, and Java SE APIs to release N. It helps a newer compiler detect early when source code accidentally uses APIs available only in a newer JDK, which `-source` and `-target` alone do not guarantee. However, `--release` only controls source code compiled by the configured compiler; it does not automatically check dependency bytecode/APIs, choose the production runtime, or prove behavioral compatibility. A reliable Java baseline requires combining compiler release, toolchain, tests on the minimum JDK, dependency checks, and consistent CI configuration.
