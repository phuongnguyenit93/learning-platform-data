# Gradle Java Toolchains và cấu hình options.release

## 1. Mục tiêu trong Java Advance Compatibility Migration

Khi nâng phiên bản Java, một dự án có thể cần dùng JDK mới cho build tool hoặc compiler nhưng vẫn cam kết ứng dụng/thư viện chạy trên Java cũ. Ví dụ, hệ thống CI chuyển sang JDK 21, trong khi thư viện đang phát hành vẫn phải hoạt động trên Java 17. Nếu không phân biệt rõ **JDK dùng để build** và **mức Java tối thiểu khi chạy**, developer dễ vô tình dùng API JDK mới, sinh bytecode không phù hợp hoặc kiểm thử sai runtime.

Gradle cung cấp hai cơ chế bổ sung cho nhau:

- **Java Toolchains:** lựa chọn JDK có các công cụ được task cần sử dụng, như compiler javac, Java launcher để chạy test và Javadoc tool.
- **JavaCompile.options.release:** chỉ định Java release mà source Java được phép sử dụng ở mức ngôn ngữ, định dạng class file và API Java SE có trong release đó.

Kết hợp hai cơ chế giúp định nghĩa chính sách nhất quán. Chẳng hạn, compiler lấy từ JDK 21 nhưng dùng --release 17 để biên dịch artifact hướng tới Java 17, sau đó chạy kiểm thử bằng JVM Java 17 để chứng minh khả năng sử dụng thực tế.

Đây là bài học thuộc nhóm **Maven và Gradle** của module **Java Advance Compatibility Migration**, tập trung vào cách thiết kế cấu hình Gradle, kiểm tra kết quả và xử lý những lỗi thường gặp khi đổi JDK.

Sau bài học, người đọc có thể:

1. Phân biệt Gradle daemon JVM, Java compiler toolchain, Java release target và test/runtime JVM.
2. Viết cấu hình Toolchains trong build.gradle.kts và build.gradle.
3. Hiểu vì sao options.release đáng tin cậy hơn source/target khi cross-compile Java.
4. Tạo artifact bằng compiler mới nhưng còn tương thích với Java release thấp hơn.
5. Kiểm thử bằng runtime tối thiểu và runtime mục tiêu.
6. Phát hiện rủi ro từ dependency, generated bytecode, build plugin và multi-module.
7. Chẩn đoán lỗi thiếu JDK, unsupported release, class-file version hoặc CI sử dụng nhầm Java.

## 2. Bốn lớp phiên bản Java khác nhau

Một câu hỏi như “Project đang dùng Java bao nhiêu?” là không đủ chính xác. Cần hỏi ở lớp nào.

| Lớp | Vai trò | Ví dụ |
|---|---|---|
| Gradle runtime JVM | JVM chạy Gradle launcher/daemon, build scripts và plugins. | Gradle chạy trên JDK 21. |
| Java compiler toolchain | Bộ JDK cung cấp javac để biên dịch source. | JavaCompile sử dụng javac JDK 21. |
| Java release target | Mức cú pháp, bytecode và Java SE API mà class được phép dùng. | options.release = 17. |
| Test/production runtime JVM | JVM chạy ứng dụng, test worker, service hoặc CLI sau khi compile. | Test trên JDK 17; production chạy Java 17. |

Một cấu hình hợp lệ:

~~~text
Gradle daemon              JDK 21
Compiler JavaCompile       JDK 21
Compiler --release         17
Test launcher              JDK 17
Production runtime         Java 17
~~~

Compiler từ JDK 21 có thể tạo class file cho Java 17 qua --release 17, miễn là compiler đó hỗ trợ target và các thành phần khác của build phù hợp. Nhưng sử dụng JDK 21 để chạy Gradle không có nghĩa mọi class được compile cho Java 21; và options.release=17 không tự bảo đảm toàn bộ dependency runtime tương thích Java 17.

### 2.1. Vai trò của JAVA_HOME

Trong nhiều môi trường, biến JAVA_HOME hoặc Java được Gradle launcher chọn ảnh hưởng đến JVM chạy Gradle. Tuy nhiên, Java Toolchains cho phép các task Java sử dụng một JDK khác. Vì vậy:

- java -version trong terminal có thể phản ánh JDK của PATH.
- ./gradlew --version hiển thị phiên bản Gradle và JVM mà Gradle đang sử dụng.
- ./gradlew javaToolchains cho biết các JDK mà Gradle phát hiện cho việc chọn toolchain.
- javac mà compileJava thực sự sử dụng còn phụ thuộc Java Toolchains và cấu hình task.
- JVM chạy Test task còn phụ thuộc javaLauncher và conventions của Test.

Không nên suy ra tất cả chỉ từ JAVA_HOME hoặc lệnh java -version.

### 2.2. Runtime triển khai nằm ngoài toolchain

Toolchains trong Gradle không tự sửa Docker image, Kubernetes manifest, systemd service hoặc cấu hình application server. Có thể build đúng --release 17 nhưng triển khai nhầm lên Java 11 và gặp UnsupportedClassVersionError. Cần kiểm tra runtime của môi trường thật bằng thông tin process/image, không chỉ build script.

## 3. Java Toolchains hoạt động như thế nào?

Java Toolchains là cơ chế của Gradle để yêu cầu một JDK đáp ứng specification. Java toolchain specification thường gồm:

- languageVersion: phiên bản Java.
- vendor: nhà cung cấp JDK khi có ràng buộc.
- implementation: loại triển khai nếu cần.

Gradle sẽ chọn installation phù hợp trong những JDK nó biết hoặc dùng cơ chế provisioning nếu đã cấu hình đúng cho phiên bản Gradle và môi trường đó.

Ví dụ Kotlin DSL:

~~~kotlin
plugins {
    java
}

java {
    toolchain {
        languageVersion.set(JavaLanguageVersion.of(21))
    }
}
~~~

Đoạn này biểu thị ý định: project muốn sử dụng Java toolchain 21. Nó không đồng nghĩa “mọi task tùy chỉnh gọi java đều tự động chạy JDK 21”; plugin tự viết hoặc task Exec/ProcessBuilder có thể sử dụng executable riêng.

### 3.1. Compiler, launcher và Javadoc tool

Các vai trò của toolchain:

| Tool | Thường được sử dụng bởi | Lưu ý |
|---|---|---|
| JavaCompiler | JavaCompile và task/plugin cần compiler Java | Có thể chọn JDK khác Gradle daemon. |
| JavaLauncher | Test, JavaExec và task chạy JVM tương thích | Có thể chỉ định riêng JDK dùng để chạy test. |
| JavadocTool | Javadoc tasks | Không phải kiểm chứng runtime Java tối thiểu. |

Một project có thể yêu cầu compiler JDK 21 nhưng Test launcher JDK 17 để xác minh compatibility. Nếu JavaCompile phát sinh bytecode Java 21 trong lúc test chạy Java 17, sẽ lỗi. Đó là lý do cần đặt options.release phù hợp.

### 3.2. Gradle tìm JDK ở đâu?

Gradle có cơ chế dò tìm JDK cài sẵn qua những vị trí được hỗ trợ và có cấu hình thêm các Java installations. Khả năng tải/provision JDK còn phụ thuộc phiên bản Gradle, repository/resolver đã thiết lập và kết nối mạng.

Điểm quan trọng:

1. Không giả định khai báo toolchain sẽ luôn tự tải JDK.
2. Nếu CI bị cô lập mạng, cần cài sẵn JDK hoặc chuẩn bị provisioning được chấp thuận.
3. Nếu khóa vendor/implementation cụ thể, Gradle có thể không tìm được installation phù hợp dù máy có một JDK cùng major.
4. JDK chạy Gradle daemon vẫn phải được Gradle Wrapper và các plugin hỗ trợ.

Việc thay JAVA_HOME chỉ để build “chạy được” có thể che khuất cấu hình toolchain sai. Nên ghi rõ yêu cầu trong build và CI.

## 4. Ví dụ chuẩn bằng Gradle Kotlin DSL

Giả sử thư viện có các yêu cầu:

- Dùng JDK 21 để chạy compiler.
- Source Java chỉ được dùng Java SE API và cú pháp trong Java 17.
- Class file Java phải có định dạng tương thích với JVM Java 17.

Trong build.gradle.kts:

~~~kotlin
plugins {
    java
}

java {
    toolchain {
        languageVersion.set(JavaLanguageVersion.of(21))
    }
}

tasks.withType<JavaCompile>().configureEach {
    options.release.set(17)
}
~~~

Đây là cấu hình tường minh cho JavaCompile tasks trong project đó. Giá trị 17 được chuyển thành --release 17 khi javac thực thi. Nếu code sử dụng API Java SE chỉ có ở Java 21, compilation sẽ bị từ chối ở những tình huống mà --release kiểm soát.

### 4.1. Nếu sản phẩm chỉ hỗ trợ Java 21

Với major release mới có minimum Java 21:

~~~kotlin
java {
    toolchain {
        languageVersion.set(JavaLanguageVersion.of(21))
    }
}

tasks.withType<JavaCompile>().configureEach {
    options.release.set(21)
}
~~~

Đây có thể là cấu hình đúng khi product contract chính thức đã nâng mức Java tối thiểu lên 21. Không nên đổi 17 thành 21 chỉ vì developer mới cài JDK 21; đó là thay đổi có thể ảnh hưởng consumer còn chạy Java 17.

### 4.2. Nếu muốn compiler và target cùng là Java 17

~~~kotlin
plugins {
    java
}

java {
    toolchain {
        languageVersion.set(JavaLanguageVersion.of(17))
    }
}

tasks.withType<JavaCompile>().configureEach {
    options.release.set(17)
}
~~~

Kiểu cấu hình này phù hợp với nhánh maintenance cần giữ Java 17 khi không có lý do dùng compiler cao hơn. Vẫn cần lưu ý Gradle daemon có thể chạy trên một JDK khác được Wrapper hỗ trợ.

### 4.3. Public API và Java Library plugin

Khi phát hành thư viện, nên xem xét Java Library plugin để phân biệt API dependencies và implementation dependencies. Ví dụ build.gradle.kts:

~~~kotlin
plugins {
    id("java-library")
}

java {
    toolchain {
        languageVersion.set(JavaLanguageVersion.of(21))
    }
}

tasks.withType<JavaCompile>().configureEach {
    options.release.set(17)
}

dependencies {
    api("org.example:contract-api:1.0.0")
    implementation("org.example:internal-runtime:2.0.0")
}
~~~

Các tọa độ org.example chỉ là ví dụ mô hình. Một thư viện public API dùng --release 17 vẫn có thể kéo dependency chỉ chạy Java 21; do đó phải kiểm tra dependency graph thực tế của artifact.

## 5. Cấu hình tương tự bằng Gradle Groovy DSL

Trong build.gradle:

~~~groovy
plugins {
    id 'java'
}

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)
    }
}

tasks.withType(JavaCompile).configureEach {
    options.release = 17
}
~~~

Với Java Library plugin:

~~~groovy
plugins {
    id 'java-library'
}

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)
    }
}

tasks.withType(JavaCompile).configureEach {
    options.release = 17
}
~~~

Hai DSL có cú pháp setter khác nhau nhưng cùng mục tiêu kỹ thuật: lựa chọn JDK compiler và giới hạn Java release cho task JavaCompile. Các ví dụ giả định Gradle và Java plugin được dùng có hỗ trợ Java Toolchains/options.release.

## 6. options.release, sourceCompatibility và targetCompatibility

Ba thiết lập này rất dễ nhầm lẫn.

### 6.1. sourceCompatibility

sourceCompatibility liên quan mức cú pháp/ngôn ngữ Java được compiler chấp nhận. Nó có thể ngăn source viết cú pháp mới hơn mức được chọn, nhưng khi đứng riêng thì không phải giới hạn đầy đủ cho class-file format hoặc Java SE APIs.

### 6.2. targetCompatibility

targetCompatibility yêu cầu class-file target cho code được compile. Ví dụ Java 17 tương ứng class-file major version 61. Tuy nhiên, khi dùng compiler JDK 21, chỉ đặt targetCompatibility=17 không nhất thiết ngăn compiler cho phép tham chiếu method Java 21 có mặt trong platform APIs của JDK đang compile.

### 6.3. options.release

Trong JavaCompile, options.release được truyền thành javac --release. Nó đồng thời giới hạn:

- Source language level.
- Class-file target version.
- Java SE API surface khả dụng tại release mục tiêu.

Ví dụ:

~~~kotlin
tasks.withType<JavaCompile>().configureEach {
    options.release.set(17)
}
~~~

Với compiler JDK 21, --release 17 là biện pháp quan trọng để tránh vô tình gọi API nền tảng Java 21 trong mã mà vẫn muốn chạy trên Java 17.

| Thiết lập | Source syntax | Bytecode target | Java SE API theo target |
|---|---|---|---|
| sourceCompatibility=17 | Có giới hạn | Chưa đủ khi đứng riêng | Không đủ |
| targetCompatibility=17 | Không tự quyết định source policy | Có giới hạn | Không đủ |
| Cả source/target=17 | Có giới hạn | Có giới hạn | Vẫn chưa đủ với compiler JDK mới |
| options.release=17 | Có giới hạn | Có giới hạn | Có giới hạn trong phạm vi javac --release |
| toolchain=21 | Chọn compiler JDK 21 | Không tự đặt target 17 | Không tự giới hạn Java SE API xuống 17 |
| toolchain=21 + release=17 | Compiler JDK 21 | Bytecode 17 | Giới hạn Java SE API xuống mức 17 |

Tránh kết hợp các giá trị sourceCompatibility/targetCompatibility mâu thuẫn với options.release; nên có một policy rõ cho mỗi JavaCompile task.

### 6.4. Ví dụ phát hiện API Java 21

Giả sử code:

~~~java
import java.util.List;

class FirstItem {
    static String get(List<String> items) {
        return items.getFirst();
    }
}
~~~

List.getFirst được giới thiệu cùng Sequenced Collections ở Java 21. Nếu source được compile bằng JDK 21 nhưng sản phẩm hứa Java 17, đây là rủi ro. Khi cấu hình --release 17, compiler sẽ không cho phép sử dụng API đó theo platform Java 17.

Một bản viết tương thích Java 17 có thể dùng:

~~~java
static String get(List<String> items) {
    return items.get(0);
}
~~~

Ví dụ chỉ minh họa sự khác biệt API. Không phải mọi API Java mới đều có thay thế tương đương trên Java cũ; đôi khi cần thay thiết kế hoặc công bố nâng minimum Java.

## 7. options.release không hạ được bytecode của dependency

Một hạn chế quan trọng: --release tác động đến việc biên dịch **source của task**, không biên dịch lại tất cả thư viện bên ngoài.

~~~text
Project source --release 17
          │
          ▼
Application classes: major 61 (Java 17)

Dependency A: major 61 (Java 17)
Dependency B: major 65 (Java 21)
                  │
                  ▼
Ứng dụng chưa thể được coi là Java 17-compatible
~~~

Trong ví dụ này, dependency B có thể gây UnsupportedClassVersionError trên Java 17. Việc phần source của chính project được compile cho Java 17 không xử lý được dependency B.

### 7.1. Trực tiếp và bắc cầu

Không chỉ kiểm tra những dependency đã khai báo trong build.gradle. Cần kiểm tra cả thư viện được kéo vào gián tiếp:

~~~text
my-service
  ├── web-framework (direct)
  │     └── json-core (transitive)
  └── db-driver (direct)
        └── native-helper (transitive)
~~~

Khi một dependency bắc cầu nâng minimum Java, toàn bộ tổ hợp runtime có thể không còn đáp ứng Java tối thiểu.

### 7.2. Lệnh Gradle để quan sát dependency graph

Trong project dùng Java plugin:

~~~bash
./gradlew dependencies --configuration compileClasspath
./gradlew dependencies --configuration runtimeClasspath
./gradlew dependencies --configuration testRuntimeClasspath
~~~

Với module riêng:

~~~bash
./gradlew :service:dependencies --configuration runtimeClasspath
~~~

Tìm đường kéo vào một thư viện:

~~~bash
./gradlew :service:dependencyInsight \
    --dependency library-name \
    --configuration runtimeClasspath
~~~

Trên Windows PowerShell:

~~~powershell
.\gradlew.bat :service:dependencies --configuration runtimeClasspath
~~~

Những lệnh trên là hướng dẫn người đọc thực hiện trong project của họ, không phải thao tác cần chạy khi viết bài này.

### 7.3. Variant metadata và Java compatibility

Gradle Module Metadata có thể chứa các thuộc tính compatibility, trong đó có mức Java mà một variant yêu cầu. Trong một số tình huống, Gradle có thể từ chối chọn variant không phù hợp với consumer.

Nhưng không phải mọi JAR có metadata đầy đủ hoặc chính xác:

- Artifact được publish chỉ với Maven POM có thể thiếu Java variant attributes chi tiết.
- Metadata có thể không phản ánh các shaded classes hoặc native code.
- Các class chỉ được nạp động hoặc thông qua reflection vẫn có thể gặp lỗi.
- Một dependency có bytecode phù hợp nhưng gọi API không tồn tại trên runtime tối thiểu.

Vì vậy, metadata hỗ trợ chọn variant nhưng **không thay thế runtime compatibility tests**.

## 8. Chạy Test task bằng JDK tối thiểu

Trong migration, một cấu hình quan trọng là compiler JDK 21, --release 17 và Test launcher JDK 17:

~~~kotlin
plugins {
    java
}

java {
    toolchain {
        languageVersion.set(JavaLanguageVersion.of(21))
    }
}

tasks.withType<JavaCompile>().configureEach {
    options.release.set(17)
}

tasks.withType<Test>().configureEach {
    javaLauncher.set(javaToolchains.launcherFor {
        languageVersion.set(JavaLanguageVersion.of(17))
    })
}
~~~

Theo cấu hình này:

1. Gradle dùng compiler JDK 21 cho JavaCompile.
2. Các JavaCompile tasks được yêu cầu --release 17.
3. Test JVM chạy bằng Java 17 khi toolchain phù hợp có sẵn.
4. Những thư viện được test sử dụng ở runtime phải hỗ trợ Java 17.

Đây là ví dụ cho Gradle Java project với Test task thông thường. Nếu có custom integrationTest hoặc JavaExec, cần xác nhận task đó dùng launcher mong muốn.

### 8.1. Kiểm thử trên hai JDK bằng project property

Để tái sử dụng cùng script cho nhiều job CI:

~~~kotlin
val testJavaVersion =
    providers.gradleProperty("testJavaVersion").orElse("17").get().toInt()

tasks.withType<Test>().configureEach {
    javaLauncher.set(javaToolchains.launcherFor {
        languageVersion.set(JavaLanguageVersion.of(testJavaVersion))
    })
}
~~~

Sau khi giữ cấu hình JavaCompile như trên, CI có thể gọi:

~~~bash
./gradlew clean test -PtestJavaVersion=17
./gradlew clean test -PtestJavaVersion=21
~~~

Hai lệnh là hai lượt test riêng; có thể chạy ở những CI jobs độc lập. Không nên cho hai job đồng thời ghi vào cùng một build directory chưa được cô lập.

### 8.2. Thực tế cần kiểm tra điều gì?

Tối thiểu, test bằng Java thấp nhất sản phẩm cam kết để phát hiện:

- UnsupportedClassVersionError từ project hoặc dependency.
- NoSuchMethodError, NoClassDefFoundError do thiếu API/runtime dependency.
- Vấn đề với class loader, reflection hoặc module encapsulation.
- Khác biệt về TLS, security providers, locale, charset, timezone.
- Thư viện native hoặc instrumentation agent không hỗ trợ runtime đích.

Nên có integration tests, không chỉ unit tests thuần logic. Nếu thư viện được phân phối cho consumer, có thể biên dịch một binary client với API cũ rồi chạy nó với artifact mới khi chính sách yêu cầu binary compatibility.

## 9. JavaLauncher cho JavaExec và task tùy chỉnh

Một số tác vụ Gradle tự tạo cần Java launcher riêng:

~~~kotlin
val minimumRuntime = javaToolchains.launcherFor {
    languageVersion.set(JavaLanguageVersion.of(17))
}

tasks.register<JavaExec>("runCompatibilitySmoke") {
    group = "verification"
    description = "Run CLI on the minimum supported Java runtime"
    classpath = sourceSets["main"].runtimeClasspath
    mainClass.set("com.example.cli.Main")
    javaLauncher.set(minimumRuntime)
}
~~~

Ví dụ giả định project có Java plugin và class com.example.cli.Main. JavaExec được chọn JVM 17 riêng. Gradle daemon và JavaCompile vẫn có thể sử dụng JDK khác.

### 9.1. JavaCompiler Provider

Nếu custom task cần compiler, Gradle JavaToolchainService cung cấp Provider<JavaCompiler>:

~~~kotlin
val compilerFor17 = javaToolchains.compilerFor {
    languageVersion.set(JavaLanguageVersion.of(17))
}
~~~

Điều này tốt hơn hard-code đường dẫn javac trên máy phát triển. Task custom cần sử dụng provider đúng với Gradle task APIs và configuration-cache requirements nếu có.

### 9.2. Vendor specification

Khi tổ chức có yêu cầu vendor cụ thể:

~~~kotlin
java {
    toolchain {
        languageVersion.set(JavaLanguageVersion.of(21))
        vendor.set(JvmVendorSpec.ADOPTIUM)
    }
}
~~~

Ràng buộc này có thể khiến Gradle không tìm được toolchain trên runner nếu chỉ cài JDK 21 của vendor khác. Nếu không có lý do yêu cầu một vendor, nên tránh khóa quá chặt vì làm giảm khả năng tái sử dụng cấu hình ở các môi trường.

### 9.3. Plugin bên thứ ba có tự dùng Toolchains không?

Không nhất thiết. Một plugin có thể chạy Java bằng:

- Gradle daemon JVM.
- JavaLauncher lấy từ Toolchain APIs.
- ProcessBuilder hoặc Exec lấy java từ PATH.
- Đường dẫn executable được cấu hình riêng.

Vì vậy, khi kiểm tra build, không nên mặc định mọi task Java được plugin tạo đều sử dụng java.toolchain. Phải xem tài liệu plugin, logs hoặc task configuration thực tế.

## 10. Kiểm tra Gradle đang dùng JDK nào

### 10.1. Gradle Wrapper

~~~bash
./gradlew --version
~~~

Trên Windows:

~~~powershell
.\gradlew.bat --version
~~~

Thông tin này cho biết Gradle version/JVM được báo cáo, nhưng không phải bằng chứng cho compiler/test launcher trong mọi task. Nên dùng Gradle Wrapper của repository, không dùng bản Gradle toàn cục tùy ý.

### 10.2. Liệt kê các JDK được Gradle phát hiện

~~~bash
./gradlew javaToolchains
~~~

Tác vụ này giúp xem các Java installations mà Gradle nhận diện và metadata như version/vendor. Nếu toolchain yêu cầu không tồn tại, cần giải quyết việc cài đặt/provisioning trước khi đổi target một cách tùy tiện.

### 10.3. Quan sát JavaCompile

~~~bash
./gradlew compileJava --info
~~~

Thông tin log tùy phiên bản Gradle có thể hiển thị compiler toolchain hoặc đường dẫn liên quan. Với multi-module, kiểm tra đúng task, ví dụ :library:compileJava.

### 10.4. Xác định JVM bên trong test

Ví dụ JUnit test:

~~~java
import org.junit.jupiter.api.Test;

class JavaRuntimeInfoTest {
    @Test
    void printRuntime() {
        System.out.println(System.getProperty("java.version"));
        System.out.println(System.getProperty("java.vendor"));
    }
}
~~~

Đây là minh họa; cần khai báo JUnit trong test dependencies. Trong CI thật, có thể assert major version mong muốn để tránh trường hợp tên job là Java 17 nhưng Test task thực tế chạy JDK 21.

## 11. Xác nhận class-file version

Có thể xem class metadata của artifact:

~~~bash
javap -verbose -classpath build/libs/my-library.jar com.example.LibraryEntry
~~~

Tìm major version trong output:

| Java release | Class-file major |
|---|---:|
| Java 8 | 52 |
| Java 11 | 55 |
| Java 17 | 61 |
| Java 21 | 65 |

Đối với JavaCompile --release 17, Java class do javac tạo thường có major 61. Nhưng không nên xem một class đại diện cho mọi class trong artifact.

Cần xem:

- Các class khác trong cùng JAR.
- Classes sinh bởi annotation processor hoặc bytecode generator.
- Kotlin/Scala/Groovy classes nếu project hỗn hợp.
- Shaded/fat JAR dependencies có class version cao hơn.
- Multi-release JAR và thư mục META-INF/versions.

Kiểm chứng cuối phải bao gồm chạy artifact thực sự trên Java tối thiểu.

### 11.1. Multi-release JAR

Ví dụ:

~~~text
my-library.jar
  com/example/Feature.class
  META-INF/versions/17/com/example/Feature.class
  META-INF/versions/21/com/example/Feature.class
~~~

Một multi-release JAR hợp lệ có thể chứa các implementation khác nhau theo Java runtime. Phần base phải phù hợp với mức Java tối thiểu đã cam kết; class trong thư mục version cao chỉ được chọn trong điều kiện tương ứng.

Do đó, có một class major 65 bên trong META-INF/versions/21 không tự chứng minh toàn bộ JAR chỉ chạy Java 21; nhưng cũng không nên chỉ nhìn base class rồi kết luận mọi phần đều tương thích Java 17.

## 12. Cấu hình nhiều module trong Gradle

Một repository có thể có:

~~~text
root
  ├── api-contract
  ├── domain
  ├── service
  └── cli
~~~

Giả sử policy:

| Module | Compiler | --release | Runtime tối thiểu |
|---|---|---|---|
| api-contract | JDK 21 | 17 | Java 17 |
| domain | JDK 21 | 17 | Java 17 |
| service | JDK 21 | 21 | Java 21 |
| cli | JDK 21 | 21 | Java 21 |

Đây là ví dụ một sản phẩm có library lõi hỗ trợ Java 17 nhưng các ứng dụng cụ thể yêu cầu Java 21. Tùy quan hệ module, cần kiểm tra dependency và public API để bảo đảm api-contract không tham chiếu kiểu chỉ có trong artifact Java 21.

### 12.1. Root project không tự áp dụng mọi cấu hình cho subproject

Đoạn:

~~~kotlin
tasks.withType<JavaCompile>().configureEach {
    options.release.set(17)
}
~~~

chỉ tác động các task phù hợp thuộc project nơi cấu hình đó có hiệu lực. Nếu đặt ở root nhưng không cấu hình các subproject, không nên giả định mọi module sẽ được compile cho Java 17.

Đối với repo nhiều module, nên dùng Gradle convention plugin hoặc cách cấu hình có phạm vi rõ, được áp dụng nhất quán cho từng loại module. Điều này còn giúp thêm module mới mà không quên policy về toolchain/release.

### 12.2. Tránh một mức Java duy nhất cho mọi artifact

Nếu cùng repo chứa thư viện public Java 17, service Java 21 và plugin build chạy trên JDK 21, ba thứ đó có ràng buộc khác nhau. Bắt tất cả dùng --release 21 sẽ phá cam kết của thư viện; bắt tất cả dùng --release 17 có thể hạn chế chức năng chính đáng của service Java 21.

Phân nhóm theo contract của từng artifact, sau đó kiểm tra liên kết giữa chúng.

## 13. Annotation processors và generated bytecode

Một dự án có thể compile bằng javac --release 17 nhưng sử dụng:

- Annotation processors.
- Protobuf/OpenAPI/JAXB code generators.
- Proxy/ORM bytecode enhancers.
- Code coverage và instrumentation agents.
- Plugin sinh class trực tiếp.

Những công cụ này có các ràng buộc riêng:

1. Processor phải chạy được với javac/JDK được chọn.
2. Generated Java source phải không vượt Java release target.
3. Công cụ sinh bytecode trực tiếp cần tự đặt class-file target đúng.
4. Runtime dependencies của generated classes cần phù hợp Java tối thiểu.
5. Tooling có thể sử dụng compiler internals và bị ảnh hưởng khi nâng JDK.

Với generated code, hãy xem class-file output và test runtime, không chỉ file Java viết tay.

### 13.1. Kotlin, Groovy, Scala

Trong dự án hỗn hợp, các compiler khác có thể có setting JVM target riêng. Một số Gradle plugins hỗ trợ Java Toolchains, nhưng mức tích hợp phụ thuộc plugin/version.

Ví dụ Kotlin Gradle Plugin có thể có kotlin.jvmToolchain và compilerOptions.jvmTarget. Cần kiểm tra tài liệu theo plugin version thực tế để dùng cú pháp chính xác và bảo đảm Kotlin bytecode target phù hợp Java target.

Nếu JavaCompile tạo major 61 nhưng KotlinCompile sinh major 65, toàn bộ artifact chưa thể được coi là Java 17-compatible.

## 14. Gradle Wrapper và tương thích JDK chạy Gradle

Toolchains không sửa được trường hợp Gradle Wrapper quá cũ để chạy trên JDK mới.

Khi nâng JDK 17 → 21, nên kiểm tra:

- Gradle Wrapper version có hỗ trợ JDK 21 để **chạy Gradle** không?
- Java Toolchains API và options.release có sẵn ở version Gradle đang dùng không?
- Plugins của framework hoặc code generation có tương thích Wrapper/JDK mới không?
- CI image có các JDK mà Toolchains yêu cầu không?
- Toolchain provisioning có resolver phù hợp và được phép kết nối repository không?

Một trình tự hợp lý:

~~~text
Kiểm kê JDK / Gradle Wrapper hiện tại
              │
              ▼
Chọn Gradle Wrapper tương thích với JDK launcher
              │
              ▼
Nâng build plugins cần thiết
              │
              ▼
Khai báo java.toolchain và options.release
              │
              ▼
Kiểm chứng compiler/test launcher và runtime tests
~~~

Không sửa sự cố “Gradle không khởi động trên JDK 21” bằng cách chỉ đặt options.release=21; đó là hai lớp khác nhau.

## 15. Xử lý lỗi phổ biến

### 15.1. No matching toolchains found

Một thông báo điển hình:

~~~text
No matching toolchains found for requested specification
~~~

Khả năng:

- JDK mong muốn chưa được cài.
- Gradle không dò thấy JDK đã cài.
- Vendor constraint quá chặt.
- Provisioning chưa được cấu hình, resolver thiếu hoặc môi trường không có mạng.
- Architecture/OS hiện tại chưa có bản phân phối thỏa yêu cầu.

Hướng xử lý: xem ./gradlew javaToolchains, xác định installation paths, xem CI provisioning và vendor constraints; cài/configure JDK đúng, rồi thử lại task.

### 15.2. error: release version X not supported

Khi javac quá cũ không hỗ trợ target, chẳng hạn compiler JDK 17 nhưng options.release=21, javac sẽ không thể tạo release đó.

Giải pháp: chọn compiler JDK có hỗ trợ --release tương ứng, không chỉ đổi JVM chạy Gradle. Kiểm tra toolchain thực tế của JavaCompile.

### 15.3. UnsupportedClassVersionError

Ví dụ:

~~~text
class file version 65.0; runtime recognizes up to version 61.0
~~~

Java 17 không thể nạp class file Java 21. Nguyên nhân có thể là một module build sai release, shaded dependency, generated code hoặc test library chỉ hỗ trợ Java 21.

Hãy xác định class đầu tiên gây lỗi, artifact/JAR chứa nó, major version và đường dependency kéo vào. Không mặc định đây là lỗi của chính JavaCompile task chính.

### 15.4. NoSuchMethodError trên runtime tối thiểu

Một nguyên nhân là code sử dụng API Java SE mới, compile bằng JDK mới với source/target cũ nhưng không --release. Khi runtime cũ không có API, lời gọi thất bại.

Nguyên nhân khác là conflict giữa các version của dependency bên ngoài. Cần phân biệt bằng stack trace, class source và resolved runtime graph.

### 15.5. Test vẫn dùng JDK 21 dù CI job tên là Java 17

Có thể Test.javaLauncher đang bị override, hoặc task custom chạy Java qua PATH. Nên kiểm tra property java.version ngay trong test JVM, kết hợp logs và test launcher task configuration.

### 15.6. Thư viện hoặc plugin dùng API nội bộ JDK

Reflection và Java module encapsulation có thể làm thư viện cũ lỗi khi JDK mới. Toolchain chỉ chọn JDK, không tự nâng dependency hoặc thay implementation. Cần nâng/thay thư viện tương thích, dùng jdeps hoặc integration tests để tìm vấn đề.

### 15.7. Không có matching variant của dependency

Nếu Gradle báo variant không phù hợp mức Java consumer yêu cầu, xem Java compatibility metadata, version artifact và target của module. Nếu vẫn cam kết Java 17, không nên tự nâng release lên 21 chỉ để dependency resolution hết lỗi; hãy chọn version dependency còn hỗ trợ Java 17 hoặc đưa ra thay đổi baseline có kiểm soát.

## 16. CI matrix theo Java runtime được hỗ trợ

Một pipeline có thể chia:

~~~text
Source + dependency locks
          │
          ▼
Gradle Wrapper / compiler toolchain JDK 21
          │
          ▼
JavaCompile --release 17
          │
          ▼
Artifact + checksum
          │
      ┌───┴──────┐
      ▼          ▼
Run Java 17   Run Java 21
      │          │
      └───┬──────┘
          ▼
Compatibility report
~~~

Đối với project library phát hành public, điều này có thể bao gồm binary client fixture build ở version cũ và chạy trên artifact mới mà không biên dịch lại.

### 16.1. Khung CI minh họa

~~~yaml
strategy:
  matrix:
    java_runtime: [17, 21]

steps:
  - name: Checkout and prepare JDKs
    # Thiết lập runtime Java và toolchains phù hợp với CI.
  - name: Run compatibility tests
    run: ./gradlew clean test -PtestJavaVersion=17
~~~

Đây chỉ là khung mô tả ý tưởng, không phải workflow hoàn chỉnh: cần checkout, setup JDK, cách ánh xạ matrix vào property, cache và artifact management theo CI platform. Trong cấu hình thật, project property cần lấy giá trị từ ô matrix thay vì hard-code 17.

Điều cốt yếu là Test task chạy JVM thực sự tương ứng ô matrix. Bước setup Java ở CI không tự bảo đảm điều đó nếu Test.javaLauncher đã cố định sang JDK khác.

### 16.2. Kiểm thử artifact thực tế

Test task chỉ kiểm tra những classpath mà test sử dụng. Với executable JAR hoặc ứng dụng Spring Boot, nên thử khởi động artifact đã được đóng gói bằng Java tối thiểu.

Cách làm:

1. Build artifact một lần theo toolchain và release policy.
2. Lưu checksum/version và resolved runtime dependency graph.
3. Triển khai/chạy artifact trên Java 17.
4. Thực hiện health, API hoặc CLI smoke tests.
5. Chạy lại trên Java 21 nếu cũng công bố hỗ trợ.
6. So sánh kết quả và lưu evidence cho release.

Tránh build hai artifact khác nhau trong hai job rồi coi chúng là bằng chứng cùng một binary tương thích nhiều JDK.

## 17. Cấu hình Java baseline và chính sách phát hành

Một support matrix nội bộ minh họa:

| Thành phần | Cấu hình | Chủ sở hữu |
|---|---|---|
| Gradle Wrapper | Bản hỗ trợ JDK launcher đã chọn | Build/platform team |
| Gradle runtime JVM | JDK 21 | CI daemon |
| Compiler toolchain | JDK 21 | java.toolchain |
| Java source/API/bytecode target | Java 17 | options.release |
| Test runtimes | Java 17, Java 21 | Test.javaLauncher và CI |
| Production minimum runtime | Java 17 | Product support policy |
| Dependency versions | Bộ được kiểm chứng cho Java 17 | BOM/dependency management |
| Container runtime | Java 17 hoặc Java được công bố hỗ trợ | Deployment team |

Không chỉ đổi options.release=17 thành 21 khi sản phẩm nâng mức Java tối thiểu. Cần cập nhật test matrix, dependency policy, release notes, deployment image, build pipeline và migration guide.

### 17.1. Thay compiler không nhất thiết thay baseline

Một module từng được compile với JDK 17 có thể chuyển sang compiler JDK 21 + --release 17, giữ minimum Java 17 nếu dependency và hành vi phù hợp. Đây là cơ sở để hiện đại hóa build pipeline mà không buộc consumer nâng JVM ngay.

### 17.2. Thay baseline phải là quyết định công bố

Nếu dependency/framework mới buộc Java 21, không nên âm thầm nâng output bytecode. Cần thông báo mức Java tối thiểu mới ở đúng product version, hỗ trợ consumer lập kế hoạch migration và cân nhắc duy trì nhánh cũ trong khoảng thời gian hỗ trợ đã cam kết.

## 19. Quy trình triển khai cấu hình Gradle khi nâng JDK

**Bước 1 — Kiểm kê.** Ghi Gradle Wrapper, JDK launcher, JavaCompile toolchain, source/target/release, Test launcher, dependencies và Java runtime tối thiểu đang cam kết.

**Bước 2 — Nâng Gradle Wrapper nếu cần.** Dựa vào compatibility matrix để chọn Wrapper và plugin build có thể chạy trên JDK launcher mới.

**Bước 3 — Khai báo Java Toolchains.** Chọn compiler JDK cho từng project hoặc convention plugin; chỉ khóa vendor khi cần.

**Bước 4 — Đặt options.release.** Dùng minimum Java target thực tế, không lấy mặc định từ compiler JDK.

**Bước 5 — Đồng bộ các compiler khác.** Xem generated code, annotation processors, Kotlin/Groovy/Scala, bytecode enhancer và packaging.

**Bước 6 — Kiểm tra dependency.** Đánh giá trực tiếp và bắc cầu, Gradle variant metadata, native/JDK internals, framework BOM và minimum Java của runtime graph.

**Bước 7 — Chạy trên JDK tối thiểu.** Cấu hình Test launcher hoặc CI jobs và xác minh JVM thực tế. Kết hợp integration tests và smoke tests.

**Bước 8 — Kiểm tra artifact.** Xem class-file version, shaded dependencies, multi-release JAR, Docker image hoặc application-server runtime.

**Bước 9 — Lưu bằng chứng.** Ghi Wrapper version, JDK/toolchain selection, release target, dependency graph, artifact checksum, CI test results và các giới hạn chưa kiểm chứng.

**Bước 10 — Phát hành.** Nếu baseline thay đổi, cập nhật compatibility matrix, release notes và migration guide; triển khai có kiểm soát và theo dõi lỗi.

## 20. Checklist cho dự án thật

- [ ] options.release được khai báo rõ theo minimum Java.
- [ ] Không có sourceCompatibility/targetCompatibility mâu thuẫn.
- [ ] JavaCompile task của từng module tuân thủ convention.
- [ ] Test.javaLauncher chạy đúng runtime của CI matrix.

Checklist là hướng dẫn kiểm tra trong dự án, không phải bằng chứng hoàn thành nếu các bước chưa thực sự chạy.

## 21. Kết luận

**Gradle Java Toolchains** giúp kiểm soát *JDK dùng để chạy công cụ Java của build*, còn **JavaCompile.options.release** giúp kiểm soát *mức source, bytecode và Java SE API mà artifact được phép phụ thuộc*. Cấu hình compiler JDK 21 với --release 17 là một kỹ thuật hữu ích để hiện đại hóa pipeline mà vẫn nhắm tới Java 17.

Tuy nhiên, tính tương thích không dừng ở một dòng build.gradle. Dependency trực tiếp và bắc cầu, generated code, framework/plugin, module path, native libraries và artifact đóng gói đều có thể áp đặt mức Java cao hơn. Vì vậy, cần kiểm tra compiler và Test launcher thực tế, chạy test trên runtime tối thiểu, so sánh class-file versions, kiểm tra dependency graph và lưu bằng chứng của release.

Khi phân biệt rõ Gradle runtime, compiler toolchain, --release target và production Java, nhóm có thể nâng JDK có kiểm soát, tránh vô tình phá hợp đồng Java tối thiểu và tạo build dễ tái lập trên máy phát triển lẫn CI.
