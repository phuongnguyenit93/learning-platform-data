# Source language, class file version, and target platform API set

When compiling a Java project for multiple JDK versions, three choices that are often conflated must be separated: **source language version**, **class file format version**, and **permitted Java platform API set**. These three factors are related yet answer three different questions.

- Source language version determines which syntax and Java language features the compiler accepts.
- Class file version determines the generated bytecode format and the minimum JVM level capable of reading that format.
- Target platform API set determines which Java platform classes, methods, and fields source code is permitted to reference.

A project can use older Java syntax, emit older class files, yet still reference an API present only in a newer JDK. In that case, the build may succeed on a developer machine while the application fails when running on the target JDK. To avoid this situation, configure and inspect all three factors, while also verifying external libraries and the actual runtime.

## 1. Three concepts to separate

### 1.1. Source language level

Source language level governs which syntactic constructs and language features the compiler allows in source code.

For example, Java features appeared in different releases:

- Lambda expressions and method references exist since Java 8.
- **var** for local variables exists since Java 10.
- Text blocks were standardized in Java 15.
- Records were standardized in Java 16.
- Pattern matching for **instanceof** was standardized in Java 16.

If the project's source level is Java 8, source code cannot use records or text blocks as standard language features. The compiler can report syntax or source-version errors even when the installed JDK is a newer version.

Source level answers the question: **Which release's language feature set is the source code written in?**

It does not itself answer the question: which Java APIs are allowed to be called. An old source-level configuration does not necessarily restrict the platform APIs visible to the compiler.

### 1.2. Class-file target

After compiling, the Java compiler generates bytecode stored in **.class** files. Class files have their own structure and format version. The JVM reads this format to load classes and execute bytecode.

Each Java release is associated with a class-file major version. For example:

| Java release | Class-file major version |
|---|---:|
| Java 8 | 52 |
| Java 11 | 55 |
| Java 17 | 61 |
| Java 21 | 65 |
| Java 25 | 69 |

When the compiler generates a class file with major version 65, the JVM must support that format, corresponding to Java 21 or newer for ordinary class files. A Java 17 JVM cannot read major version 65 class files and can report **UnsupportedClassVersionError**.

Class-file target answers the question: **Which JVM release's format is the generated bytecode readable by?**

It does not guarantee that every API invoked in the bytecode exists on that JVM. A class file with major version 52 can still contain a reference to a method added only in Java 11 if the compiler was permitted to compile that reference from a newer JDK.

### 1.3. Platform API release

The Java platform provides APIs such as **java.lang**, **java.util**, **java.time**, **java.sql**, standard modules, and many other APIs. These APIs evolve across releases: new APIs are added, while older APIs are deprecated, modified, or removed.

For example:

- **List.of(...)** exists since Java 9.
- **String.isBlank()** exists since Java 11.
- Some older APIs or internal APIs may be restricted or no longer exist in newer JDKs.

If an application must run on Java 8, source code and bytecode must avoid calling APIs introduced in Java 9 or later. Otherwise, the class file may be readable by a Java 8 JVM yet the API call will still fail at execution time.

Platform API release answers the question: **Which release's Java SE APIs is the source code allowed to use?**

### 1.4. Summary comparison table

| Factor | Controls | Example error if misconfigured |
|---|---|---|
| Source language level | Language syntax and features | Using records when source level is too low |
| Class-file target | Output bytecode format | Java 17 cannot load Java 21 class files |
| Platform API release | Java platform APIs source code is permitted to call | Java 8 lacks String.isBlank() |
| Compiler JDK/toolchain | Actual compiler version used | Local and CI compile with different JDKs |

A compatible configuration usually must clarify compiler JDK, source level, class-file target, and platform API release. With modern JDKs, **--release** is the direct way to align the first three choices to the same target release.

## 2. Distinguishing javac options

The Java compiler has related options that are not interchangeable.

### 2.1. -source

The **-source** option selects the source language version the compiler uses to parse Java code. For example, **-source 8** instructs the compiler to process source code at the Java 8 language level.

This option does not itself restrict the output class-file version and does not fully restrict the Java platform API set.

### 2.2. -target

The **-target** option selects the generated class file version. For example, **-target 8** emits class files in Java 8 format.

This option does not itself prevent source code from calling newer APIs from the JDK used to compile. Therefore, setting only **-target 8** is not enough to prove the artifact runs on Java 8.

### 2.3. --release

The **--release N** option was introduced in JDK 9 to compile for a target Java release. It combines three requirements:

1. Use source language rules matching that release.
2. Emit class files matching that release.
3. Restrict usable Java SE APIs according to that release.

Example:

~~~bash
javac --release 8 -d out src/com/example/App.java
~~~

The command above compiles code according to Java 8, produces Java 8 class files, and restricts Java SE platform APIs to Java 8, even when the compiler runs from a newer JDK that supports **--release 8**.

Do not combine **--release** with **-source** or **-target** in the same javac invocation. They are different ways of configuring targets, and javac does not allow using them simultaneously.

### 2.4. Option comparison table

| Configuration | Source language | Class file | Platform APIs |
|---|---|---|---|
| -source 8 only | Java 8 | Per default/compiler target | Can see APIs of the compiler JDK |
| -target 8 only | Per default/compiler source | Java 8 | Can see APIs of the compiler JDK |
| -source 8 -target 8 | Java 8 | Java 8 | Not fully restricted to Java 8 |
| --release 8 | Java 8 | Java 8 | Java SE APIs of Java 8 |
| --release 17 | Java 17 | Java 17 | Java SE APIs of Java 17 |

When using JDK 9 or newer, prefer **--release** if the goal is compiling an application for a specific Java platform release.

## 3. Why can old source and target still call new APIs?

Suppose a developer uses JDK 17 to compile a project that needs to run on Java 8. The project sets **-source 8 -target 8**, without restricting platform APIs.

The following source uses **String.isBlank()**, added in Java 11:

~~~java
public class ApiCompatibilityExample {

    public static void main(String[] args) {
        String value = "   ";

        if (value.isBlank()) {
            System.out.println("Blank value");
        }
    }
}
~~~

The snippet's syntax is compatible with Java 8, and the class file can be generated in Java 8 format. However, the JDK 17 compiler sees **isBlank()** in JDK 17's API and can compile that call when only **-source 8 -target 8** is used.

When running this class file on Java 8, the JVM can load the class file format yet cannot find **String.isBlank()**. The error may be:

~~~text
java.lang.NoSuchMethodError:
  java.lang.String.isBlank()Z
~~~

This is a case where both source language level and class-file target look right, yet the platform API target is wrong.

If the configuration is replaced with:

~~~bash
javac --release 8 -d out src/com/example/ApiCompatibilityExample.java
~~~

the compiler will report an error because **isBlank()** does not exist in the Java 8 API. The error is caught at compile time instead of waiting until runtime.

Another example is **List.of(...)**, available since Java 9:

~~~java
List<String> names = List.of("An", "Binh", "Chi");
~~~

This snippet cannot be used when the target platform API is Java 8. If the application must run on Java 8, a compatible API such as **Arrays.asList(...)** can be chosen depending on collection mutability requirements and program semantics.

## 4. Understanding class-file version and JVM errors

A class file begins with the magic number **CAFEBABE**, followed by minor version and major version. The JVM checks the format version when loading a class.

Some common major versions:

| Major version | Java release |
|---:|---|
| 52 | Java 8 |
| 55 | Java 11 |
| 61 | Java 17 |
| 65 | Java 21 |
| 69 | Java 25 |

If a class is compiled for Java 21 yet run on a Java 17 JVM, the error message usually states class file version 65.0 while the runtime only supports up to 61.0. This is a bytecode format error, not a missing API method error.

Distinguish two error groups:

- **UnsupportedClassVersionError**: the JVM does not support the class-file version of the class being loaded.
- **NoSuchMethodError**, **NoSuchFieldError**, or **NoClassDefFoundError**: the class file may load, yet a required reference cannot be resolved or a required class cannot be used.

Therefore, when seeing a runtime error, read the exact error type and inspect both class-file versions and dependencies/APIs. Do not conclude every Java-version-related error is due to overly new bytecode.

### 4.1. Newer JVMs and older class files

Newer JVMs can generally execute class files from older releases within compatible format and API boundaries. However, that does not mean every legacy application runs properly on a new JDK: removed APIs, module access changes, reflection, TLS, default charsets, GC, or library behaviors can still cause problems.

The reverse direction is much more strictly bounded: older JVMs cannot read class files emitted in newer formats they do not yet support.

### 4.2. Minor version and preview features

Java preview features are released for experimentation within a release. When compiling with preview enabled, class files can use a special minor version of 65535. Running preview class files requires enabling preview on the JVM and using the exact Java release that generated that class file.

Example:

~~~bash
javac --enable-preview --release 21 -d out src/com/example/PreviewApp.java
java --enable-preview -cp out com.example.PreviewApp
~~~

Do not use preview class files as standard deployment artifacts if production environments are not configured and controlled for that exact release. During migration, check whether the project or dependencies use any preview features.

## 5. Java platform APIs and external library APIs

**--release** helps restrict Java SE APIs, yet does not govern every API an application uses.

A project typically depends on:

- Java SE platform APIs such as **java.util**, **java.time**, **java.net**.
- Framework APIs such as Spring Framework or Spring Boot.
- Third-party library APIs such as Jackson, Hibernate, Netty, or HTTP clients.
- JDK internal APIs or implementation-specific APIs.
- APIs provided by application servers, containers, or deployment platforms.

**--release 17** does not mean every third-party library in the dependency graph is Java 17 compatible. Nor does it guarantee a dependency was compiled for Java 17; an external JAR may contain Java 21 class files and cause a Java 17 runtime to fail upon class loading.

Similarly, **--release** does not prove reflection APIs, service providers, native libraries, framework configurations, or data protocols still work. Those aspects require separate verification.

### 5.1. Java SE APIs and JDK internal APIs

Do not rely on internal packages such as **sun.*** or APIs not guaranteed by Java SE. They can change or have access blocked across JDK releases.

You can use **jdeps** to detect some dependencies on JDK internal APIs:

~~~bash
jdeps --jdk-internals app.jar
~~~

This is a useful static analysis step, yet does not detect every access constructed via reflection, class names in configs, or native code. Combine with runtime testing.

### 5.2. Third-party library APIs

Suppose source code uses Spring APIs or a JSON library. The compiler checks signatures against the JAR on the compile classpath. If runtime loads a different JAR version, calls may no longer be compatible.

For external libraries, check:

- Version resolved at build time.
- Actual version packaged or provided by the environment.
- Class-file versions of classes inside the dependency.
- Java baseline supported by the library publisher.
- API and behavioral changes in release notes/migration guides.
- Whether transitive dependencies were unexpectedly upgraded/downgraded.

A build using **--release 17** can still produce an artifact that fails to run on Java 17 if a dependency contains newer bytecode or requires runtime APIs absent from Java 17.

## 6. Intentionally choosing compiler JDK and runtime target

The compiler JDK is the JDK actually running javac. The runtime target is the platform the artifact must support. These two values can differ.

For example, a team can use JDK 21 as the compiler while producing an artifact targeting Java 17:

| Component | Value |
|---|---|
| Compiler JDK | 21 |
| Source language level | 17 |
| Class-file target | 17 |
| Java SE API target | 17 |
| Expected minimum runtime | Java 17 |
| Verified runtime | Java 17 and supported environments |

This approach allows the team to use a newer compiler in CI while controlling the output platform. The condition is that all source code and dependencies comply with the chosen baseline.

Do not confuse **JAVA_HOME** with the deployment runtime. **JAVA_HOME** in a pipeline may point to the compile JDK, while production containers or servers use another JRE/JDK. Inspect both separately.

## 7. Configuring with Gradle

With the Gradle Java plugin, use a Java toolchain to select the compiler JDK and **options.release** to specify the target Java platform release.

Example using JDK 21 to compile for Java 17:

~~~groovy
java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)
    }
}

tasks.withType(JavaCompile).configureEach {
    options.release = 17
}
~~~

In this configuration:

- The toolchain selects JDK 21 to run the compiler.
- **options.release = 17** restricts source language, class-file target, and Java SE APIs to Java 17.
- The produced artifact has class-file major version 61.
- Source code cannot use language features or Java SE APIs introduced after Java 17.

If the application must run on Java 17, test tasks and the artifact execution environment on Java 17. Configuring a toolchain for compile/test can cause tests to run on the newer toolchain JDK; compiling with release 17 alone does not prove tests ran on JVM 17.

You can configure the test launcher explicitly:

~~~groovy
def java17 = javaToolchains.launcherFor {
    languageVersion = JavaLanguageVersion.of(17)
}

tasks.withType(Test).configureEach {
    javaLauncher = java17
}
~~~

Variable names and organization can be adjusted to fit the build script. What matters is separately identifying the compiler JDK and test JVM when they differ.

### 7.1. sourceCompatibility and targetCompatibility

Gradle also has **sourceCompatibility** and **targetCompatibility** properties. They represent the source and bytecode target levels for Java compilation. They do not themselves select an installed JDK to run the compiler and do not fully restrict the Java SE API set like **options.release**.

Example:

~~~groovy
java {
    sourceCompatibility = JavaVersion.VERSION_1_8
    targetCompatibility = JavaVersion.VERSION_1_8
}
~~~

If the build runs on a newer JDK, this configuration may still allow source code to reference newer APIs. With JDK 9 or newer, if the goal is enforcing Java SE APIs by release, prefer **options.release**.

Do not declare **options.release** and source/target options together in conflicting ways. Choose one consistent target configuration method and verify actual compile tasks.

### 7.2. Multi-module Gradle

In a multi-module project, do not configure only one module and assume all other modules follow the same baseline. Check:

- All Java modules use the same Java toolchain or have documented exceptions.
- Every **JavaCompile** task uses the appropriate release target.
- Test, integration test, and generated source modules have matching configs.
- Build plugins, annotation processors, and code generators run on the selected compiler JDK.
- Internal dependencies do not publish class files newer than the consuming application's runtime target.

Configuration can be applied centrally in convention plugins or shared build logic, allowing modules with special requirements to declare them explicitly. Avoid having root configs and child module configs silently override one another.

## 8. Configuring with Maven

With Maven Compiler Plugin, the **maven.compiler.release** property is a concise way to select the target release on JDKs supporting **--release**.

Example:

~~~xml
<properties>
    <maven.compiler.release>17</maven.compiler.release>
</properties>
~~~

Or declare directly in plugin configuration:

~~~xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-compiler-plugin</artifactId>
    <configuration>
        <release>17</release>
    </configuration>
</plugin>
~~~

Configuring release 17 requires the compiler to use Java SE APIs and class-file targets matching Java 17. The JDK used to run Maven/compiler still needs to be determined via environment or Maven toolchains if the project manages multiple JDKs.

The **maven.compiler.source** and **maven.compiler.target** properties are legacy settings. They do not provide full API protection like **release**. If compiling for Java 8 using JDK 9 or newer, use release 8 when supported by the compiler.

## 9. Cases where the compiler is too old or too new

**--release** can only pick a release within the range supported by the compiler. For example, a JDK 17 compiler cannot produce Java 21 class files and API targets. To compile for Java 21, a JDK 21 or newer compiler supporting release 21 is required.

Conversely, if using JDK 8 to compile for Java 8, the **--release** option does not yet exist because it was introduced in JDK 9. In that case, the JDK 8 compiler already sees Java 8 APIs, or appropriate boot class path configuration can be used in legacy workflows. For new projects, upgrade compilers/build tools to versions supporting **--release** for clearer configuration.

Also check Gradle, Maven Compiler Plugin, and related plugin versions. A newer JDK may be incompatible with an older build tool even if application source code does not change. Build tool compatibility is part of migration, independent of the application's source/class-file/API targets.

## 10. Multi-release JAR is not --release

A multi-release JAR is a mechanism for packaging multiple class versions for different Java releases inside the same JAR file. Classes intended for a specific release reside under **META-INF/versions/N**, and the manifest must declare **Multi-Release: true**.

Example structure:

~~~text
library.jar
├── META-INF/
│   ├── MANIFEST.MF
│   └── versions/
│       ├── 9/
│       │   └── com/example/FastFormatter.class
│       └── 17/
│           └── com/example/FastFormatter.class
└── com/
    └── example/
        └── FastFormatter.class
~~~

A JVM supporting multi-release JARs will pick the class best matching the running Java release. This mechanism allows a library to provide a more optimal implementation for newer JDKs while preserving a baseline implementation for older JDKs.

It differs from **--release**:

- **--release** is an option when compiling one source set for one Java platform release.
- Multi-release JAR is an artifact structure containing multiple implementations by release.
- A multi-release JAR must still ensure base classes and versioned classes have appropriate formats, APIs, and semantics.
- Not every library or packaging method automatically produces a multi-release JAR.

If a dependency is a multi-release JAR, inspect its manifest, **META-INF/versions** contents, and how dependency analysis tools are configured. When checking with jdeps, specify the release to analyze using **--multi-release**.

## 11. Checking actual configuration and artifacts

Do not read only build.gradle or pom.xml and conclude the artifact was built correctly. Inspect compiler, class files, and runtime.

### 11.1. Inspecting compiler and runtime JDK

~~~bash
java -version
javac -version
~~~

The two commands can return different versions if **PATH**, **JAVA_HOME**, toolchains, or shell environments are configured differently. In Gradle, inspect the JDKs recognized by Gradle:

~~~bash
./gradlew -q javaToolchains
~~~

If the project uses Maven Toolchains, check toolchain configuration and compiler plugin logs to identify the JDK actually used.

### 11.2. Inspecting class-file major version

Use **javap -verbose** to read class file metadata:

~~~bash
javap -verbose -classpath build/classes/java/main com.example.App
~~~

In the output, locate the line:

~~~text
major version: 61
~~~

Major version 61 corresponds to Java 17. Inspect multiple representative classes, especially auto-generated classes or classes packaged from internal modules. An artifact can contain class files from different releases if dependencies or modules are built separately.

You can run **javap** with JARs on the classpath to inspect a dependency class. Do not inspect just one application class and infer the entire JAR shares the same bytecode version.

### 11.3. Inspecting artifact contents

Use the command:

~~~bash
jar tf app.jar
~~~

With Spring Boot executable JARs, inspect application classes and libraries residing in the expected packaging layout, such as **BOOT-INF/classes** and **BOOT-INF/lib**. Cross-check against the dependency graph to detect missing libraries or unexpected versions.

### 11.4. Inspecting APIs and dependencies

With Gradle:

~~~bash
./gradlew dependencies --configuration compileClasspath
./gradlew dependencies --configuration runtimeClasspath
./gradlew dependencyInsight --dependency jackson-databind --configuration runtimeClasspath
~~~

With Maven:

~~~bash
mvn dependency:tree
~~~

You can use:

~~~bash
jdeps --multi-release 17 --jdk-internals app.jar
~~~

to check JDK internal API dependencies when analyzing an artifact for Java 17. Adjust the release to the actual target. Static analysis tools do not replace running the artifact on the target JVM.

### 11.5. Running the artifact with the target runtime

Finally, run the packaged artifact on the exact Java runtime planned for deployment:

~~~bash
java -version
java -jar app.jar
~~~

In pipelines, use images/containers containing the target JDK or JRE. Confirm startup, health checks, business flows, and service connections. If the application must run on multiple Java releases, test on each release declared as supported.

## 12. Common error scenarios

| Scenario | Cause | How to handle |
|---|---|---|
| Compiler reports unsupported source version | Compiler JDK is too old for requested source level | Use an appropriate compiler JDK |
| Syntax error with record/text block | Source level is lower than the release introducing the feature | Choose the right source release or rewrite using older syntax |
| UnsupportedClassVersionError | Class file is newer than the running JVM | Lower class-file target or upgrade runtime |
| NoSuchMethodError on older Java | Class file references an API absent from runtime | Use --release matching target and inspect dependencies |
| NoClassDefFoundError | Missing class or prior class initialization failed | Inspect runtime classpath and initialization cause |
| Error appears only inside container | Container uses a different JRE/JDK or libraries than local | Check image, runtime version, and artifact |
| Only one module fails | That module has a different release target or dependencies | Check per-module tasks and configuration |
| Fails when running tests while compilation passes | Test JVM or test dependencies differ from compile environment | Identify test launcher and runtime classpath |
| Reflection error on new JDK | Module access rights or internal APIs changed | Use supported APIs, update libraries, and test |

Read the stack trace to pinpoint the involved class, method, and class loader. A **NoSuchMethodError** may stem from a JDK API or a third-party library; the class name in the stack trace and dependency graph help distinguish them.

## 13. Multi-version verification matrix

For systems that must support multiple Java releases, build a matrix to clearly record configurations and test results.

Example project supporting Java 17 and Java 21:

| Component | Target Java 17 build | Target Java 21 build |
|---|---|---|
| Compiler JDK | 21 | 21 |
| Source level | 17 | 21 |
| Class-file major | 61 | 65 |
| Java SE API | Release 17 | Release 21 |
| Verification runtime | Java 17 | Java 21 |
| Unit/integration tests | Run on Java 17 | Run on Java 21 |
| Functional checks | Main flows and data | Main flows and data |
| Performance checks | Matching baseline | Matching baseline |

If publishing only one artifact for Java 17, you can run that artifact on both Java 17 and Java 21 to verify both old and new runtimes if that is the support scope. If publishing separate artifacts per release, each artifact must be built, verified, and clearly identified.

A matrix should record each cell's status such as PASS, FAIL, BLOCKED, or NOT RUN, along with logs and artifact checksums. Do not fill in PASS just because a build task succeeded; clearly state which steps ran.

## 14. Controlling source level and API target in multi-module projects

Multi-module projects can encounter module A compiling for Java 17, module B emitting Java 21 class files, and module C using Java 21 APIs while packaged alongside a Java 17 application. Each module may build individually, yet the combined application fails to run on the target runtime.

Standardize a baseline policy:

1. Determine the minimum Java runtime the product commits to supporting.
2. Select matching source/API release for application modules.
3. Select the compiler toolchain used by CI and developers.
4. Apply **options.release** to all relevant JavaCompile tasks.
5. Check internal modules and external dependencies for compatible bytecode/APIs.
6. Test test sources, integration tests, annotation processors, and generated sources.
7. Inspect the final artifact, not only individual modules in isolation.

If a module intentionally requires newer Java, express that in metadata, the dependency graph, and release documentation. Do not allow newer modules to be pulled into an application with a lower runtime without control.

For annotation processors or code generators, distinguish the JDK used to run the processor from the release generated code must obey. Generated sources must be compiled with the exact target **--release**. Build plugins may require a newer JDK than the application, yet application bytecode must still conform to the defined target.

## 15. What --release does not guarantee

**--release** is an important mechanism for controlling Java SE APIs and class-file targets, yet it is not a system-wide compatibility certification.

It does not automatically verify:

- Third-party dependencies have suitable class-file versions.
- Runtime classpath matches compile classpath.
- Spring beans, reflection, service loaders, or framework configs initialize successfully.
- Database drivers, native libraries, or application servers are compatible.
- Database schemas and payloads between services do not change semantics.
- The application meets latency, throughput, and resource targets.
- The application runs properly across all OSes, containers, and production configurations.

Therefore, after compiling with **--release**, dependency analysis, artifact inspection, runtime testing, and functional testing are still necessary.

## 16. Workflow for selecting and verifying targets

The following workflow can be applied when preparing multi-version builds:

### Step 1: Identify minimum runtime

Clarify the lowest Java release the application must support, based on deployment platforms, libraries, frameworks, and product policy.

### Step 2: Select compiler JDK

Choose a JDK capable of compiling the chosen source release and API target. Explicitly record vendor and version in CI so local machines and pipelines do not use different compilers.

### Step 3: Configure source, class file, and APIs

For JDK 9 and newer, use **--release N** or equivalent Gradle/Maven configuration. Do not rely solely on **sourceCompatibility** and **targetCompatibility** if restricting Java SE APIs is required.

### Step 4: Inspect dependencies

Verify internal libraries, third-party libraries, annotation processors, and build plugins. Read release notes and Java compatibility for selected versions.

### Step 5: Inspect artifacts

Check class-file major versions, JAR contents, and packaged dependencies. Review multi-release JARs and preview features if used by the project.

### Step 6: Run on target runtime

Run the artifact in the target JDK/JRE, executing startup tests, unit/integration tests, and critical business flows. With multiple targets, test every target declared as supported.

### Step 7: Save evidence

Save build logs, JDK versions, release configurations, dependency reports, artifact checksums, and test results. When errors occur, explicitly record the related release, module, class, or API.

## 17. Principles to remember

- Source language level controls syntax and language features.
- Class-file target controls the bytecode format the JVM must read.
- Platform API release controls which Java SE APIs source code is permitted to use.
- Compiler JDK/toolchain determines the actual compiler, not the deployment runtime.
- Standalone **-source** and **-target** do not fully restrict platform APIs.
- **--release** synchronizes source, class file, and Java SE API targets on supporting JDKs.
- External dependencies, reflection, native code, and configurations still require separate verification.
- Only running the artifact on the target runtime provides direct evidence of loading and initialization capability on that platform.

A reliable cross-version compilation configuration must make clear which language version source uses, which JVM bytecode is generated for, and which platform APIs may be referenced. When these three choices are controlled together with dependencies and the real runtime, the team can catch compatibility errors early and make evidence-based migration conclusions.

- APIs provided by application servers, containers, or deployment platforms.

**--release 17** does not mean every third-party library in the dependency graph is Java 17 compatible. Nor does it guarantee a dependency was compiled for Java 17; an external JAR may contain Java 21 class files and cause a Java 17 runtime to fail upon class loading.

Similarly, **--release** does not prove reflection APIs, service providers, native libraries, framework configurations, or data protocols still work. Those aspects require separate verification.

### 5.1. Java SE APIs and JDK internal APIs

Do not rely on internal packages such as **sun.*** or APIs not guaranteed by Java SE. They can change or have access blocked across JDK releases.

You can use **jdeps** to detect some dependencies on JDK internal APIs:

~~~bash
jdeps --jdk-internals app.jar
~~~

This is a useful static analysis step, yet does not detect every access constructed via reflection, class names in configs, or native code. Combine with runtime testing.

### 5.2. Third-party library APIs

Suppose source code uses Spring APIs or a JSON library. The compiler checks signatures against the JAR on the compile classpath. If runtime loads a different JAR version, calls may no longer be compatible.

For external libraries, check:

- Version resolved at build time.
- Actual version packaged or provided by the environment.
- Class-file versions of classes inside the dependency.
- Java baseline supported by the library publisher.
- API and behavioral changes in release notes/migration guides.
- Whether transitive dependencies were unexpectedly upgraded/downgraded.

A build using **--release 17** can still produce an artifact that fails to run on Java 17 if a dependency contains newer bytecode or requires runtime APIs absent from Java 17.

## 6. Intentionally choosing compiler JDK and runtime target

The compiler JDK is the JDK actually running javac. The runtime target is the platform the artifact must support. These two values can differ.

For example, a team can use JDK 21 as the compiler while producing an artifact targeting Java 17:

| Component | Value |
|---|---|
| Compiler JDK | 21 |
| Source language level | 17 |
| Class-file target | 17 |
| Java SE API target | 17 |
| Expected minimum runtime | Java 17 |
| Verified runtime | Java 17 and supported environments |

This approach allows the team to use a newer compiler in CI while controlling the output platform. The condition is that all source code and dependencies comply with the chosen baseline.

Do not confuse **JAVA_HOME** with the deployment runtime. **JAVA_HOME** in a pipeline may point to the compile JDK, while production containers or servers use another JRE/JDK. Inspect both separately.

## 7. Configuring with Gradle

With the Gradle Java plugin, use a Java toolchain to select the compiler JDK and **options.release** to specify the target Java platform release.

Example using JDK 21 to compile for Java 17:

~~~groovy
java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)
    }
}

tasks.withType(JavaCompile).configureEach {
    options.release = 17
}
~~~

In this configuration:

- The toolchain selects JDK 21 to run the compiler.
- **options.release = 17** restricts source language, class-file target, and Java SE APIs to Java 17.
- The produced artifact has class-file major version 61.
- Source code cannot use language features or Java SE APIs introduced after Java 17.

If the application must run on Java 17, test tasks and the artifact execution environment on Java 17. Configuring a toolchain for compile/test can cause tests to run on the newer toolchain JDK; compiling with release 17 alone does not prove tests ran on JVM 17.

You can configure the test launcher explicitly:

~~~groovy
def java17 = javaToolchains.launcherFor {
    languageVersion = JavaLanguageVersion.of(17)
}

tasks.withType(Test).configureEach {
    javaLauncher = java17
}
~~~

Variable names and organization can be adjusted to fit the build script. What matters is separately identifying the compiler JDK and test JVM when they differ.

### 7.1. sourceCompatibility and targetCompatibility

Gradle also has **sourceCompatibility** and **targetCompatibility** properties. They represent the source and bytecode target levels for Java compilation. They do not themselves select an installed JDK to run the compiler and do not fully restrict the Java SE API set like **options.release**.

Example:

~~~groovy
java {
    sourceCompatibility = JavaVersion.VERSION_1_8
    targetCompatibility = JavaVersion.VERSION_1_8
}
~~~

If the build runs on a newer JDK, this configuration may still allow source code to reference newer APIs. With JDK 9 or newer, if the goal is enforcing Java SE APIs by release, prefer **options.release**.

Do not declare **options.release** and source/target options together in conflicting ways. Choose one consistent target configuration method and verify actual compile tasks.

### 7.2. Multi-module Gradle

In a multi-module project, do not configure only one module and assume all other modules follow the same baseline. Check:

- All Java modules use the same Java toolchain or have documented exceptions.
- Every **JavaCompile** task uses the appropriate release target.
- Test, integration test, and generated source modules have matching configs.
- Build plugins, annotation processors, and code generators run on the selected compiler JDK.
- Internal dependencies do not publish class files newer than the consuming application's runtime target.

Configuration can be applied centrally in convention plugins or shared build logic, allowing modules with special requirements to declare them explicitly. Avoid having root configs and child module configs silently override one another.

## 8. Configuring with Maven

With Maven Compiler Plugin, the **maven.compiler.release** property is a concise way to select the target release on JDKs supporting **--release**.

Example:

~~~xml
<properties>
    <maven.compiler.release>17</maven.compiler.release>
</properties>
~~~

Or declare directly in plugin configuration:

~~~xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-compiler-plugin</artifactId>
    <configuration>
        <release>17</release>
    </configuration>
</plugin>
~~~

Configuring release 17 requires the compiler to use Java SE APIs and class-file targets matching Java 17. The JDK used to run Maven/compiler still needs to be determined via environment or Maven toolchains if the project manages multiple JDKs.

The **maven.compiler.source** and **maven.compiler.target** properties are legacy settings. They do not provide full API protection like **release**. If compiling for Java 8 using JDK 9 or newer, use release 8 when supported by the compiler.

## 9. Cases where the compiler is too old or too new

**--release** can only pick a release within the range supported by the compiler. For example, a JDK 17 compiler cannot produce Java 21 class files and API targets. To compile for Java 21, a JDK 21 or newer compiler supporting release 21 is required.

Conversely, if using JDK 8 to compile for Java 8, the **--release** option does not yet exist because it was introduced in JDK 9. In that case, the JDK 8 compiler already sees Java 8 APIs, or appropriate boot class path configuration can be used in legacy workflows. For new projects, upgrade compilers/build tools to versions supporting **--release** for clearer configuration.

Also check Gradle, Maven Compiler Plugin, and related plugin versions. A newer JDK may be incompatible with an older build tool even if application source code does not change. Build tool compatibility is part of migration, independent of the application's source/class-file/API targets.

## 10. Multi-release JAR is not --release

A multi-release JAR is a mechanism for packaging multiple class versions for different Java releases inside the same JAR file. Classes intended for a specific release reside under **META-INF/versions/N**, and the manifest must declare **Multi-Release: true**.

Example structure:

~~~text
library.jar
├── META-INF/
│   ├── MANIFEST.MF
│   └── versions/
│       ├── 9/
│       │   └── com/example/FastFormatter.class
│       └── 17/
│           └── com/example/FastFormatter.class
└── com/
    └── example/
        └── FastFormatter.class
~~~

A JVM supporting multi-release JARs will pick the class best matching the running Java release. This mechanism allows a library to provide a more optimal implementation for newer JDKs while preserving a baseline implementation for older JDKs.

It differs from **--release**:

- **--release** is an option when compiling one source set for one Java platform release.
- Multi-release JAR is an artifact structure containing multiple implementations by release.
- A multi-release JAR must still ensure base classes and versioned classes have appropriate formats, APIs, and semantics.
- Not every library or packaging method automatically produces a multi-release JAR.

If a dependency is a multi-release JAR, inspect its manifest, **META-INF/versions** contents, and how dependency analysis tools are configured. When checking with jdeps, specify the release to analyze using **--multi-release**.

## 11. Checking actual configuration and artifacts

Do not read only build.gradle or pom.xml and conclude the artifact was built correctly. Inspect compiler, class files, and runtime.

### 11.1. Inspecting compiler and runtime JDK

~~~bash
java -version
javac -version
~~~

The two commands can return different versions if **PATH**, **JAVA_HOME**, toolchains, or shell environments are configured differently. In Gradle, inspect the JDKs recognized by Gradle:

~~~bash
./gradlew -q javaToolchains
~~~

If the project uses Maven Toolchains, check toolchain configuration and compiler plugin logs to identify the JDK actually used.

### 11.2. Inspecting class-file major version

Use **javap -verbose** to read class file metadata:

~~~bash
javap -verbose -classpath build/classes/java/main com.example.App
~~~

In the output, locate the line:

~~~text
major version: 61
~~~

Major version 61 corresponds to Java 17. Inspect multiple representative classes, especially auto-generated classes or classes packaged from internal modules. An artifact can contain class files from different releases if dependencies or modules are built separately.

You can run **javap** with JARs on the classpath to inspect a dependency class. Do not inspect just one application class and infer the entire JAR shares the same bytecode version.

### 11.3. Inspecting artifact contents

Use the command:

~~~bash
jar tf app.jar
~~~

With Spring Boot executable JARs, inspect application classes and libraries residing in the expected packaging layout, such as **BOOT-INF/classes** and **BOOT-INF/lib**. Cross-check against the dependency graph to detect missing libraries or unexpected versions.

### 11.4. Inspecting APIs and dependencies

With Gradle:

~~~bash
./gradlew dependencies --configuration compileClasspath
./gradlew dependencies --configuration runtimeClasspath
./gradlew dependencyInsight --dependency jackson-databind --configuration runtimeClasspath
~~~

With Maven:

~~~bash
mvn dependency:tree
~~~

You can use:

~~~bash
jdeps --multi-release 17 --jdk-internals app.jar
~~~

to check JDK internal API dependencies when analyzing an artifact for Java 17. Adjust the release to the actual target. Static analysis tools do not replace running the artifact on the target JVM.

### 11.5. Running the artifact with the target runtime

Finally, run the packaged artifact on the exact Java runtime planned for deployment:

~~~bash
java -version
java -jar app.jar
~~~

In pipelines, use images/containers containing the target JDK or JRE. Confirm startup, health checks, business flows, and service connections. If the application must run on multiple Java releases, test on each release declared as supported.

## 12. Common error scenarios

| Scenario | Cause | How to handle |
|---|---|---|
| Compiler reports unsupported source version | Compiler JDK is too old for requested source level | Use an appropriate compiler JDK |
| Syntax error with record/text block | Source level is lower than the release introducing the feature | Choose the right source release or rewrite using older syntax |
| UnsupportedClassVersionError | Class file is newer than the running JVM | Lower class-file target or upgrade runtime |
| NoSuchMethodError on older Java | Class file references an API absent from runtime | Use --release matching target and inspect dependencies |
| NoClassDefFoundError | Missing class or prior class initialization failed | Inspect runtime classpath and initialization cause |
| Error appears only inside container | Container uses a different JRE/JDK or libraries than local | Check image, runtime version, and artifact |
| Only one module fails | That module has a different release target or dependencies | Check per-module tasks and configuration |
| Fails when running tests while compilation passes | Test JVM or test dependencies differ from compile environment | Identify test launcher and runtime classpath |
| Reflection error on new JDK | Module access rights or internal APIs changed | Use supported APIs, update libraries, and test |

Read the stack trace to pinpoint the involved class, method, and class loader. A **NoSuchMethodError** may stem from a JDK API or a third-party library; the class name in the stack trace and dependency graph help distinguish them.

## 13. Multi-version verification matrix

For systems that must support multiple Java releases, build a matrix to clearly record configurations and test results.

Example project supporting Java 17 and Java 21:

| Component | Target Java 17 build | Target Java 21 build |
|---|---|---|
| Compiler JDK | 21 | 21 |
| Source level | 17 | 21 |
| Class-file major | 61 | 65 |
| Java SE API | Release 17 | Release 21 |
| Verification runtime | Java 17 | Java 21 |
| Unit/integration tests | Run on Java 17 | Run on Java 21 |
| Functional checks | Main flows and data | Main flows and data |
| Performance checks | Matching baseline | Matching baseline |

If publishing only one artifact for Java 17, you can run that artifact on both Java 17 and Java 21 to verify both old and new runtimes if that is the support scope. If publishing separate artifacts per release, each artifact must be built, verified, and clearly identified.

A matrix should record each cell's status such as PASS, FAIL, BLOCKED, or NOT RUN, along with logs and artifact checksums. Do not fill in PASS just because a build task succeeded; clearly state which steps ran.

## 14. Controlling source level and API target in multi-module projects

Multi-module projects can encounter module A compiling for Java 17, module B emitting Java 21 class files, and module C using Java 21 APIs while packaged alongside a Java 17 application. Each module may build individually, yet the combined application fails to run on the target runtime.

Standardize a baseline policy:

1. Determine the minimum Java runtime the product commits to supporting.
2. Select matching source/API release for application modules.
3. Select the compiler toolchain used by CI and developers.
4. Apply **options.release** to all relevant JavaCompile tasks.
5. Check internal modules and external dependencies for compatible bytecode/APIs.
6. Test test sources, integration tests, annotation processors, and generated sources.
7. Inspect the final artifact, not only individual modules in isolation.

If a module intentionally requires newer Java, express that in metadata, the dependency graph, and release documentation. Do not allow newer modules to be pulled into an application with a lower runtime without control.

For annotation processors or code generators, distinguish the JDK used to run the processor from the release generated code must obey. Generated sources must be compiled with the exact target **--release**. Build plugins may require a newer JDK than the application, yet application bytecode must still conform to the defined target.

## 15. What --release does not guarantee

**--release** is an important mechanism for controlling Java SE APIs and class-file targets, yet it is not a system-wide compatibility certification.

It does not automatically verify:

- Third-party dependencies have suitable class-file versions.
- Runtime classpath matches compile classpath.
- Spring beans, reflection, service loaders, or framework configs initialize successfully.
- Database drivers, native libraries, or application servers are compatible.
- Database schemas and payloads between services do not change semantics.
- The application meets latency, throughput, and resource targets.
- The application runs properly across all OSes, containers, and production configurations.

Therefore, after compiling with **--release**, dependency analysis, artifact inspection, runtime testing, and functional testing are still necessary.

## 16. Workflow for selecting and verifying targets

The following workflow can be applied when preparing multi-version builds:

### Step 1: Identify minimum runtime

Clarify the lowest Java release the application must support, based on deployment platforms, libraries, frameworks, and product policy.

### Step 2: Select compiler JDK

Choose a JDK capable of compiling the chosen source release and API target. Explicitly record vendor and version in CI so local machines and pipelines do not use different compilers.

### Step 3: Configure source, class file, and APIs

For JDK 9 and newer, use **--release N** or equivalent Gradle/Maven configuration. Do not rely solely on **sourceCompatibility** and **targetCompatibility** if restricting Java SE APIs is required.

### Step 4: Inspect dependencies

Verify internal libraries, third-party libraries, annotation processors, and build plugins. Read release notes and Java compatibility for selected versions.

### Step 5: Inspect artifacts

Check class-file major versions, JAR contents, and packaged dependencies. Review multi-release JARs and preview features if used by the project.

### Step 6: Run on target runtime

Run the artifact in the target JDK/JRE, executing startup tests, unit/integration tests, and critical business flows. With multiple targets, test every target declared as supported.

### Step 7: Save evidence

Save build logs, JDK versions, release configurations, dependency reports, artifact checksums, and test results. When errors occur, explicitly record the related release, module, class, or API.

## 17. Principles to remember

- Source language level controls syntax and language features.
- Class-file target controls the bytecode format the JVM must read.
- Platform API release controls which Java SE APIs source code is permitted to use.
- Compiler JDK/toolchain determines the actual compiler, not the deployment runtime.
- Standalone **-source** and **-target** do not fully restrict platform APIs.
- **--release** synchronizes source, class file, and Java SE API targets on supporting JDKs.
- External dependencies, reflection, native code, and configurations still require separate verification.
- Only running the artifact on the target runtime provides direct evidence of loading and initialization capability on that platform.

A reliable cross-version compilation configuration must make clear which language version source uses, which JVM bytecode is generated for, and which platform APIs may be referenced. When these three choices are controlled together with dependencies and the real runtime, the team can catch compatibility errors early and make evidence-based migration conclusions.
