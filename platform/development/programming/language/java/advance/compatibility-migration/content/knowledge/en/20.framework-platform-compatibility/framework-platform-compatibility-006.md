# Hibernate, JPA, and Query or Data-Mapping Changes

During a **Java Advance Compatibility Migration**, an application using Hibernate/JPA may compile and start cleanly yet still query wrong data, write data differently than before, emit suboptimal SQL, or fail only when processing records created years ago. Changing the JDK, changing the Hibernate ORM version, changing Spring Data JPA, changing the JDBC driver, and upgrading the database can all expose these differences.

For example: an entity using `@GeneratedValue(strategy = AUTO)` is mapped by a new provider to a different sequence; an enum stored by ordinal shifts order; an HQL query that previously relied on implicit type coercion is now rejected by a new parser; or a fetch join multiplies intermediate rows and distorts pagination. Because these bugs differ in nature, they cannot be solved by merely editing imports or upgrading one dependency.

This lesson teaches how to distinguish the **JDK – JPA/Jakarta Persistence – Hibernate – framework – JDBC – database** layers, verify entity mappings and HQL/JPQL, safeguard existing data, design integration tests, and deploy with rollback capability.

## 1. Recognizing Hibernate and JPA as distinct layers

A Java persistence system typically follows this architecture:

~~~text
Service / Business Logic
            |
            v
Repository (Spring Data JPA or custom code)
            |
            v
JPA / Jakarta Persistence API
            |
            v
Hibernate ORM provider
            |
            v
JDBC Driver + Connection Pool
            |
            v
Database Engine + Schema + Persisted Data
~~~

**JPA/Jakarta Persistence** is the API specification and behavioral contract. **Hibernate ORM** is a provider implementing the specification, also offering HQL, caching, bytecode enhancement, custom types, and extensions. Spring Data JPA sits as an additional repository framework layer on top.

Change layers:

| Layer | Example | Migration risk |
|---|---|---|
| JDK | Java 8 → Java 17/21 | Reflection, class loading, JVM flags, security, bytecode |
| Persistence API | `javax.persistence` → `jakarta.persistence` | Namespaces, annotations, binary API |
| Hibernate ORM | Old major → new major | Mappings, query parser, SQL generation, type SPI |
| Spring Data JPA | New repository framework | Derived queries, projections, pagination |
| JDBC driver | New driver | Parameter binding, SQL types, timezones |
| Database | Engine/dialect/schema | Constraints, functions, collations, locking |
| Migration tool | Flyway/Liquibase | DDL, data backfills, and rollback |

Do not conclude "the new JDK made Hibernate emit different SQL" if a framework BOM simultaneously changed Hibernate, the driver, or the dialect. Record **the actual resolved artifact versions** rather than reading only POM version properties.

## 2. Establishing a support matrix before making changes

Information to capture:

- JDK vendor, feature/update release, and OS/CPU.
- Exact Hibernate ORM version.
- JPA API version and namespace in use.
- Spring Boot, Spring Data, Jakarta EE container, or other frameworks.
- JDBC driver, database engine, and versions.
- Hibernate Validator, Envers, Search, custom type libraries, and cache providers.
- Maven/Gradle Wrapper, compiler target, and annotation processors.
- Hibernate bytecode enhancer, agents, and proxy frameworks.
- Schema migration tool and currently deployed schema state.

A baseline/target table:

| Component | Current | Target | Evidence |
|---|---|---|---|
| JDK | JDK X | JDK Y | Vendor/framework matrix |
| Persistence API | `javax` or `jakarta` | Target API | Dependency tree |
| Hibernate | Version H1 | Version H2 | Exact-version migration guide |
| Spring Data | Release train R1 | R2 | BOM and support matrix |
| JDBC | Driver D1 | D2 | Database compatibility |
| Database | Engine E | May remain unchanged | Schema, SQL, query plans |
| Cache | Provider C1 | C2 or retain | Binary/cache-entry compatibility |

Whenever possible, separate JDK upgrades from ORM/framework major upgrades to isolate causes. If no intermediate supported combination exists, upgrade them together under control rather than trying to force an old framework onto a new runtime with unsupported JVM flags.

## 3. Locking down a baseline with real data, not code alone

Before migrating, pick key business flows and record:

1. Input queries and expected results.
2. Entity classes, table/column mappings, and relationships.
3. SQL generated by Hibernate and statement counts per request.
4. Actual schema, indexes, constraints, sequences, and triggers.
5. Historical data with `NULL`s, legacy enums, timezones, and large values.
6. Transaction boundaries, lock modes, and flush behavior.
7. p95/p99 latency, query plans, and connection pool metrics.
8. Actual loaded binary/version of the driver and ORM.

~~~text
App v1 + Hibernate v1 + Schema S1
                  |
                  +--> Golden fixtures
                  +--> Expected business results
                  +--> SQL count / execution plans
                  +--> Transaction/locking behavior
                  |
                  v
App v2 + Hibernate v2 + Schema S1/S2
                  |
                  v
Compare values, cardinality, constraints, performance
~~~

A test creating an empty database from new entities may pass while millions of existing rows are incompatible. Therefore, you must **test the new reader against data written by the old writer**.

## 4. Migrating the javax.persistence namespace to jakarta.persistence

Moving from `javax.persistence` generations of the Java Persistence API to `jakarta.persistence` generations of Jakarta Persistence affects source and binary APIs.

Example:

~~~java
// Legacy API generation
import javax.persistence.Entity;
import javax.persistence.Id;
import javax.persistence.Table;

@Entity
@Table(name = "orders")
public class OrderEntity {
    @Id
    private Long id;
}
~~~

For providers/frameworks using Jakarta Persistence:

~~~java
// Jakarta Persistence generation
import jakarta.persistence.Entity;
import jakarta.persistence.Id;
import jakarta.persistence.Table;

@Entity
@Table(name = "orders")
public class OrderEntity {
    @Id
    private Long id;
}
~~~

**Changing the namespace is not an automatic result of upgrading the JDK.** The JDK does not convert `javax.persistence.Entity` into `jakarta.persistence.Entity`. The change stems from Jakarta Persistence releases and associated frameworks/providers.

Check:

- Entity annotations, lifecycle callbacks, and `EntityManager`.
- Query API, Criteria API, and static metamodel classes.
- Annotations inside generated code.
- Hibernate Validator / Jakarta Validation if used.
- Spring Data repositories, converters, and query DSLs.
- Third-party starters/extensions still using the old namespace.
- Test entities and test configuration.

An application can accidentally pull in both `javax.persistence-api` and `jakarta.persistence-api`, yet the target provider will not recognize annotations from the other namespace. Errors can show up as "not a managed type", "unknown entity", or missing metadata.

**Version note:** transitional artifacts/modes exist across older Hibernate lines; do not infer compatibility from major version numbers alone while ignoring actual artifact namespaces and migration guides.

## 5. Entity mapping: table names, column names, and naming strategies

Mappings depend on both explicit declarations and implicit naming strategies.

~~~java
@Entity
@Table(name = "purchase_order")
public class PurchaseOrder {

    @Id
    @Column(name = "order_id")
    private Long id;

    @Column(name = "created_at")
    private Instant createdAt;
}
~~~

Factors that can change when upgrading providers/frameworks:

- Implicit naming strategy.
- Physical naming strategy.
- Quoting and case folding of database identifiers.
- Reserved words in a new dialect.
- Naming of join tables, foreign keys, and indexes.
- Attribute access by field or getter.
- Inheritance/discriminator mappings.

If a new provider looks for `purchase_order` while the schema has `PurchaseOrder` or `purchase_orders`, table-not-found errors can arise; worse, an auto-schema mode could **create a new empty table**, making old data appear to vanish.

Never enable DDL auto-update in production solely to "patch" mismatches. Inspect the actual schema and decide explicitly whether the mapping or the database must change.

### 5.1. JPQL uses entity/property names, not table/column names

JPQL query:

~~~java
select o
from PurchaseOrder o
where o.createdAt >= :from
order by o.id
~~~

Here `PurchaseOrder` is the entity name and `createdAt` is the Java persistent property. If field `createdAt` is renamed to `createdOn` while keeping column `created_at`, JPQL still must be updated to the new property name; native SQL referencing the real column name may need no change.

Do not mix HQL/JPQL rules with native SQL rules when debugging query parser errors.

## 6. Field access, property access, and inheritance

In JPA, placement of the `@Id` annotation and related metadata usually helps determine **field access** or **property access**.

Field access:

~~~java
@Entity
public class Customer {
    @Id
    private Long id;

    private String displayName;

    public String getDisplayName() {
        return displayName;
    }
}
~~~

Property access:

~~~java
@Entity
public class Customer {
    private Long id;

    @Id
    public Long getId() {
        return id;
    }
}
~~~

If refactoring moves annotations from fields onto getters without intending to change the access type, the provider may see a different set of persistent properties. Related issues:

- Getters containing business logic or side effects.
- `@Transient` placed in the wrong location.
- Lombok/generated getters causing unexpected behavior.
- Embedded types or mapped superclasses with different access rules.
- Inheritance strategies and discriminator fields changing.

When upgrading Hibernate, avoid mixing entity access-strategy refactors with provider upgrades. If a change is unavoidable, test read/write against legacy data and inspect actual SQL.

## 7. Primary key generation: SEQUENCE, IDENTITY, and AUTO

Common annotations:

~~~java
@Id
@GeneratedValue(
    strategy = GenerationType.SEQUENCE,
    generator = "order_id_generator"
)
@SequenceGenerator(
    name = "order_id_generator",
    sequenceName = "order_id_seq",
    allocationSize = 50
)
private Long id;
~~~

Important properties:

- `sequenceName` is the sequence name in the database.
- `allocationSize` can affect how the provider optimizes ID allocation.
- The database sequence increment/start value must align with the generator's assumptions.
- `IDENTITY` has different semantics from `SEQUENCE` and affects insert batching.
- `AUTO` delegates selection to the provider/dialect, so defaults can change across versions.

When upgrading ORM major versions, check implicit sequence naming and generator behavior in the exact version's migration guide. Never assume `@GeneratedValue(AUTO)` picks the same sequence/table across every Hibernate version.

### 7.1. Typical failures

- Hibernate looks for a new sequence name that does not exist.
- Sequence increment disagrees with ORM configuration.
- Duplicate IDs generated during rolling deploys because two versions use different strategies.
- New rows get IDs from another sequence while writing to the same table.
- Schema tools propose creating unexpected sequences rejected by operations.

**Never reset sequences manually in production** without knowing existing IDs and active writers. Test concurrent inserts on a schema containing historical data before rolling out.

## 8. Java ↔ JDBC ↔ SQL data types

An ORM maps between Java types and database types. When Hibernate or the JDBC driver changes, the same field may bind or read using a different JDBC type.

| Java type | Considerations |
|---|---|
| `BigDecimal` | Precision, scale, rounding, overflow |
| `Boolean` | BOOLEAN, BIT, SMALLINT, CHAR representation |
| `UUID` | Native UUID, CHAR, BINARY |
| `Instant` | Timestamp, UTC normalization, precision |
| `LocalDateTime` | Timezone-less semantics |
| `OffsetDateTime` | Offset storage and normalization |
| `Enum` | STRING, ORDINAL, SQL enum |
| `byte[]` | VARBINARY, BLOB, LOB streaming |
| JSON/arrays | Dialects and custom JDBC types |
| Custom value objects | `AttributeConverter`, `UserType`, provider SPI |

A mapping that previously used `CHAR(36)` to store UUIDs may not match a new target default type. When schema validation reports an expected type differing from the actual type, determine:

1. How is real data currently stored?
2. Which JDBC/SQL type does the target provider expect?
3. Are custom converters or dialects involved?
4. Do other services read the same column?
5. Is changing the ORM mapping or changing the database schema lower risk?

Never alter DDL before checking the migration guide and all other consumers.

## 9. Converters and custom Hibernate types

An `AttributeConverter` decouples Java representations from database representations:

~~~java
@Converter(autoApply = false)
public class CurrencyCodeConverter
        implements AttributeConverter<CurrencyCode, String> {

    @Override
    public String convertToDatabaseColumn(CurrencyCode code) {
        return code == null ? null : code.name();
    }

    @Override
    public CurrencyCode convertToEntityAttribute(String stored) {
        return stored == null
                ? null
                : CurrencyCode.valueOf(stored);
    }
}
~~~

However, converters do not solve everything on their own:

- Legacy data contains enum/code values that no longer exist.
- Query parameters may follow different binding paths when providers handle custom types.
- Native query projections may bypass converters differently.
- Custom JSON/array/UUID types may rely on changed Hibernate SPIs.
- `autoApply` may apply more broadly than intended.
- A `null` or invalid string can fail when materializing entities.

When using `UserType`, `BasicType`, `CompositeUserType`, custom dialects, or third-party Hibernate type libraries, verify the new major version's extension API. **Merely updating imports so code compiles does not prove type descriptors and SQL bindings still behave correctly.**

## 10. Enum mapping and legacy data

An entity may declare:

~~~java
@Enumerated(EnumType.STRING)
private OrderStatus status;
~~~

or:

~~~java
@Enumerated(EnumType.ORDINAL)
private OrderStatus status;
~~~

### 10.1. ORDINAL risks changing meaning

Initially:

~~~java
enum OrderStatus {
    CREATED, PAID, CANCELLED
}
~~~

If the database stores ordinals, `1` means `PAID`. After inserting a new constant in the middle of the enum, the stored value `1` silently maps to another status. This is **semantic data corruption** even without Hibernate throwing an exception.

### 10.2. STRING still needs migration on renames

If the database stores `PAID` while the new enum renames it to `COMPLETED`, readers may fail to recognize the legacy value. Mitigations:

- Keep storage codes stable.
- Support legacy codes via converters when needed.
- Backfill data via controlled migrations.
- Do not delete legacy parsers while backups/replay streams still contain old codes.
- Test unknown values explicitly rather than silently assigning wrong defaults.

Depending on the dialect/version, string enum mappings may interact differently with native SQL enums or DDL. Verify against the specific provider release.

## 11. Timestamps and timezones must not shift silently

Distinguish:

- `Instant`: a point in time on the UTC timeline.
- `LocalDateTime`: date-time without timezone attachment.
- `OffsetDateTime`: date-time with an offset.
- `LocalDate`: date without time-of-day.
- Legacy `Timestamp`/`Date`: semantics differ from `java.time` types.

During migration, inspect:

- SQL `TIMESTAMP` vs. `TIMESTAMP WITH TIME ZONE`.
- JDBC timezone configuration.
- Default JVM timezone.
- Database session timezone.
- Precision and rounding.
- Records near midnight boundaries, month ends, and DST transitions.
- Range query conditions.

Example half-open time-interval filter:

~~~java
List<OrderEntity> result = entityManager
        .createQuery(
            "select o from OrderEntity o " +
            "where o.createdAt >= :start " +
            "and o.createdAt < :end",
            OrderEntity.class)
        .setParameter("start", startInstant)
        .setParameter("end", endInstant)
        .getResultList();
~~~

Bind `startInstant` and `endInstant` using the exact data type supported by the mapping. Switching from `LocalDateTime` to `Instant` requires understanding the historical data's meaning, not just changing class names.

## 12. Relationships: owning side, cascade, and orphanRemoval

Example:

~~~java
@Entity
public class Customer {

    @Id
    private Long id;

    @OneToMany(mappedBy = "customer")
    private List<OrderEntity> orders;
}

@Entity
public class OrderEntity {

    @Id
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "customer_id")
    private Customer customer;
}
~~~

`mappedBy = "customer"` points to the Java persistent attribute name on the opposite entity, not the `customer_id` column name.

Factors to check:

- Owning side of the association.
- Join columns, nullability, and FK constraints.
- `CascadeType.PERSIST`, `MERGE`, `REMOVE`.
- `orphanRemoval`, especially on collections.
- Bidirectional consistency in the Java object graph.
- Nullable relationships, orphaned rows, and historical data.
- Fetch types and bytecode enhancement.
- `equals/hashCode` behavior with proxies or generated IDs.

A change to cascade or orphan removal can delete real database rows even when sources still compile cleanly. Test adding and removing links against existing data, inspecting actual SQL `DELETE` statements and foreign-key behavior.

## 13. Lazy loading, proxies, and N+1 queries

Hibernate can lazy-load associations via proxies or bytecode enhancement. After migration, the exact same repository call may emit a different number of SQL statements due to changes in fetch plans, framework defaults, or query handling.

N+1 example:

~~~java
List<OrderEntity> orders = entityManager
        .createQuery(
            "select o from OrderEntity o",
            OrderEntity.class)
        .getResultList();

for (OrderEntity order : orders) {
    System.out.println(order.getCustomer().getName());
}
~~~

If `customer` has not been fetched and customers differ across orders, the loop triggers many extra queries. This is a performance regression and does not necessarily throw an exception.

### 13.1. Fetch join

~~~java
List<OrderEntity> orders = entityManager
        .createQuery(
            "select o from OrderEntity o " +
            "join fetch o.customer " +
            "where o.status = :status",
            OrderEntity.class)
        .setParameter("status", OrderStatus.PAID)
        .getResultList();
~~~

Fetch joins are helpful, yet not a universal default for every query:

- Joining a to-many association can multiply SQL result rows.
- Pagination combined with collection fetch joins can be restricted or fall back to in-memory pagination depending on provider/config.
- Fetching multiple collections/bags simultaneously can fail or create huge Cartesian products.
- `inner join fetch` drops records lacking the association; `left join fetch` may be needed instead.

### 13.2. EntityGraph

When controlling fetch plans per use case:

~~~java
EntityGraph<OrderEntity> graph =
        entityManager.createEntityGraph(OrderEntity.class);
graph.addAttributeNodes("customer");

List<OrderEntity> orders = entityManager
        .createQuery(
            "select o from OrderEntity o where o.status = :status",
            OrderEntity.class)
        .setParameter("status", OrderStatus.PAID)
        .setHint("jakarta.persistence.fetchgraph", graph)
        .getResultList();
~~~

This example uses the Jakarta namespace; in `javax` API generations, the corresponding hint namespace differs. Read documentation for the exact provider version before copying.

### 13.3. LazyInitializationException

Accessing a lazy association outside an active persistence context can throw `LazyInitializationException`. Do not blindly enable Open Session in View or turn every association into `EAGER` to mask the error. Define transaction boundaries, fetch plans, and DTOs/projections per use case.

## 14. HQL/JPQL: parser and semantic validation

Hibernate HQL extends standard JPQL. Across major upgrades, the parser and semantic query model can change, invalidating legacy queries.

JPQL:

~~~java
select o
from OrderEntity o
where o.customer.id = :customerId
order by o.createdAt desc
~~~

Native SQL:

~~~sql
SELECT *
FROM purchase_order
WHERE customer_id = ?
ORDER BY created_at DESC;
~~~

**JPQL uses entity names and Java persistent properties.** Native SQL uses database table/column names.

### 14.1. Implicit type coercion

Failing query example:

~~~java
select o from OrderEntity o
where o.createdAt = :dateAsText
~~~

If `createdAt` is an `Instant` while the parameter is a `String`, older providers or databases might convert implicitly while newer providers fail early. Rather than relying on arbitrary casts, bind the proper type:

~~~java
Instant time = Instant.parse("2026-11-12T08:00:00Z");

List<OrderEntity> results = entityManager
        .createQuery(
            "select o from OrderEntity o where o.createdAt = :time",
            OrderEntity.class)
        .setParameter("time", time)
        .getResultList();
~~~

If legacy data is not truly stored in UTC, type binding alone is not the entire fix; handle timezone semantics explicitly.

### 14.2. HQL-specific functions

Some queries invoke Hibernate-specific or database-specific syntax or functions:

~~~java
select function('normalize_name', c.displayName)
from Customer c
~~~

Type inference and function registration can vary across Hibernate major versions. Custom dialects and functions must be migrated to extension APIs supported by the target release, not merely renamed.

### 14.3. Named and dynamic queries

Queries can live in:

- `@NamedQuery` / `@NamedNativeQuery`.
- Spring Data `@Query`.
- Query strings constructed in services.
- Criteria API / Specifications.
- Reporting/batch queries.
- Stored procedure calls.

Named queries may be validated at bootstrap time, whereas dynamic queries fail only when their code path executes. Therefore, startup tests alone are not enough to verify query parser migration.

## 15. Joins, DISTINCT, ORDER BY, and pagination

### 15.1. Join semantics

JPQL:

~~~java
select o
from OrderEntity o
join o.customer c
where c.enabled = true
~~~

is an inner join. Even if you use `left join` while putting `c.enabled = true` in the `where` clause, rows without a customer are filtered out despite the `left join` syntax.

When switching ORMs, do not confuse SQL rendering differences with preexisting logic bugs. Test with rows containing `null` associations to confirm expected behavior.

### 15.2. Duplicate rows and DISTINCT

Fetch joins on to-many associations can produce multiple SQL rows for a single entity. How Hibernate deduplicates entity references can change across versions and query shapes.

Distinguish:

- Duplicate SQL rows.
- Duplicate Java entity references in the result list.
- `distinct` on scalar projections.
- Ordering and pagination after joins.

Do not add or drop `distinct` solely because generated SQL text changed; check cardinality and outputs against fixtures.

### 15.3. Deterministic pagination

~~~java
List<OrderEntity> page = entityManager
        .createQuery(
            "select o from OrderEntity o " +
            "order by o.createdAt desc, o.id desc",
            OrderEntity.class)
        .setFirstResult(offset)
        .setMaxResults(limit)
        .getResultList();
~~~

Include a deterministic tie-breaker such as ID in `ORDER BY` so records do not jump across pages when timestamps match. Target dialects/providers can emit different pagination SQL; verify against a real database engine with sufficient rows.

## 16. Projections, aggregates, and return types

In JPQL, `count` typically returns `Long`:

~~~java
Long count = entityManager
        .createQuery(
            "select count(o) from OrderEntity o",
            Long.class)
        .getSingleResult();
~~~

Do not assume every native SQL `count` returns identical `Integer` or `BigInteger` types across all JDBC drivers and dialects. DTO constructor projections must also match types:

~~~java
select new com.acme.report.OrderSummary(
    o.status, count(o)
)
from OrderEntity o
group by o.status
~~~

When upgrading Hibernate, changes in type inference or constructor resolution can cause query validation or materialization failures.

For `sum`, `avg`, and numeric calculations, pay close attention to precision/scale and overflow risks. Never "fix" mismatches by calling `intValue()` everywhere.

## 17. Criteria API and static metamodel

Jakarta Persistence Criteria example:

~~~java
CriteriaBuilder cb = entityManager.getCriteriaBuilder();

CriteriaQuery<OrderEntity> query =
        cb.createQuery(OrderEntity.class);

Root<OrderEntity> root = query.from(OrderEntity.class);

ParameterExpression<OrderStatus> status =
        cb.parameter(OrderStatus.class, "status");

query.select(root)
     .where(cb.equal(root.get("status"), status));

List<OrderEntity> results = entityManager
        .createQuery(query)
        .setParameter("status", OrderStatus.PAID)
        .getResultList();
~~~

When using a generated static metamodel:

~~~java
root.get(OrderEntity_.status)
~~~

upgrade the annotation processor to match the target `jakarta.persistence` namespace. A clean rebuild is essential so stale generated sources or classfiles from `javax` are never picked up.

Also inspect Spring Data `Specification`, QueryDSL, criteria joins, and dynamic sorting, as these queries do not always look like searchable raw strings.

## 18. Native SQL and result mapping

Native queries depend less on the JPQL parser yet depend heavily on the database, JDBC, and result mapping.

~~~java
List<?> rows = entityManager
        .createNativeQuery(
            "select order_id, total_amount " +
            "from purchase_order where status = :status")
        .setParameter("status", "PAID")
        .getResultList();
~~~

Verify:

- Column names and aliases.
- Scalar return types such as `Long`, `BigInteger`, `BigDecimal`.
- Column ordering and duplicate column labels.
- `@SqlResultSetMapping`.
- JSON/array/UUID bindings.
- SQL functions, casts, and vendor syntax.
- `IN` parameters, including empty collections.
- Native pagination, locking, and stored procedures.

If code casts every row to `Object[]` while a new provider returns a scalar or different mapping, `ClassCastException` can happen. Use explicit result mappings where appropriate.

Do not rewrite every native SQL query into JPQL within the same migration simply because "you should use the ORM"; that is a separate semantics and performance change requiring dedicated testing.

## 19. Database dialects govern more than syntax

A Hibernate dialect can affect:

| Feature | SQL behavior that may change |
|---|---|
| ID generators | SEQUENCE, IDENTITY, `RETURNING` |
| Pagination | `LIMIT/OFFSET` or vendor syntax |
| Locking | `FOR UPDATE`, lock timeouts/hints |
| Boolean/UUID/enum | JDBC/SQL types and literals |
| Timestamps | Casts, timezone normalization |
| Aggregates/functions | SQL rendering and return types |
| JSON/arrays | Native operators and bindings |
| DDL | Indexes, constraints, column types |

A new provider may rename dialect classes or infer dialects from JDBC metadata differently. Do not keep an obsolete dialect class name without checking the migration guide.

Crucially, separate failures caused by **Hibernate generating different SQL** from failures caused by **different JDBC driver or database versions**. Compare SQL text, bind types, execution plans, and actual database error codes rather than looking only at wrapper exceptions.

## 20. Schema validation differs from schema migration

Some Spring Boot projects use:

~~~properties
spring.jpa.hibernate.ddl-auto=validate
~~~

Validation checks mappings against the schema within the provider's rules, yet does not verify full data/query/transaction semantics. Automatic schema creation or update modes are not reliable production data-migration tools.

Prefer Flyway/Liquibase or controlled SQL migration workflows:

~~~text
schema S1
   |
   | Expand: add compatible structures
   v
schema S1+ (readable by both v1 and v2)
   |
   | Backfill and switch writers
   v
schema S2-compatible
   |
   | Wait out old versions and rollback window
   v
Contract: drop old columns/contracts
~~~

Example adding a new `status_code` column:

1. Add the nullable column without dropping the existing `status` column.
2. Have reader v2 support both representations.
3. Backfill historical rows using a controlled mapping.
4. Switch writers once relevant readers are ready.
5. Drop the old column only when no v1 instances remain and backup/replay policy permits.

Never use `hibernate.hbm2ddl.auto=update` in production to "auto-fix" mapping differences after a major migration.

## 21. Transactions, flushing, and dirty checking

A managed entity can sync changes to the DB via dirty checking on flush/commit:

~~~java
@Transactional
public void markPaid(Long orderId) {
    OrderEntity order = entityManager.find(
            OrderEntity.class, orderId);

    order.setStatus(OrderStatus.PAID);
}
~~~

This requires proper transaction and persistence-context management; a detached object is not updated automatically just because a setter was called.

Test:

- Flush mode and when SQL statements are sent.
- Transaction propagation and isolation.
- `persist`, `merge`, and `remove` behavior.
- Bulk JPQL updates/deletes.
- Whether constraint violations occur at flush or commit.
- Batch insert ordering.
- Exception translation and rollback rules.

### 21.1. Bulk updates and stale state

~~~java
int changed = entityManager
        .createQuery(
            "update OrderEntity o " +
            "set o.status = :newStatus " +
            "where o.status = :oldStatus")
        .setParameter("newStatus", OrderStatus.PAID)
        .setParameter("oldStatus", OrderStatus.CREATED)
        .executeUpdate();
~~~

Bulk JPQL updates do not automatically sync already-loaded managed entities in the persistence context the way setters plus dirty checking do. In long transactions, clearing or refreshing appropriately may be necessary to avoid stale state.

An update returning success does not guarantee all subsequent Java objects reflect the updated state.

## 22. Optimistic and pessimistic locking

Optimistic locking:

~~~java
@Entity
public class Inventory {
    @Id
    private Long id;

    @Version
    private long version;

    private int quantity;
}
~~~

Test two concurrent transactions updating the same row, verifying version increments and exception/retry behavior. Bulk updates or direct SQL can bypass versioning unless carefully designed.

Pessimistic locking:

~~~java
Inventory item = entityManager.find(
        Inventory.class,
        id,
        LockModeType.PESSIMISTIC_WRITE);
~~~

Generated SQL locks depend on the database dialect and provider. When upgrading Hibernate, verify transaction timeouts, deadlocks, `NOWAIT`/`SKIP LOCKED` if used, and lock acquisition order in concurrent flows.

Never use H2 mocks as final proof of PostgreSQL/Oracle/MySQL locking semantics.

## 23. Hibernate caches can retain legacy state

Hibernate's first-level cache lives inside the persistence context. Second-level and query caches can span multiple Sessions and even survive across deployments depending on the backend.

Risks:

- Cache entry formats change between Hibernate major versions.
- Region names or key strategies change.
- Serializers fail to read entries written by a prior version.
- Invalidation falls out of sync during rolling deployments.
- Query caches hold older result shapes.

Mitigation strategies may include:

- Versioning cache namespaces/regions.
- Allowing cache rebuilds if the backing DB tolerates load.
- Disabling caches temporarily after measuring impact.
- Separating regions between v1 and v2 when incompatible.
- Verifying cache provider/integration versions against target Hibernate.

Never flush an entire Redis cluster blindly if the same store holds sessions, distributed locks, or idempotency keys.

## 24. Spring Data JPA and derived queries

With Spring Data JPA:

~~~java
public interface OrderRepository
        extends JpaRepository<OrderEntity, Long> {

    List<OrderEntity> findByStatusOrderByCreatedAtDesc(
            OrderStatus status);

    Page<OrderEntity> findByCustomerId(
            Long customerId, Pageable pageable);
}
~~~

The framework translates these methods into queries based on entity properties. Major upgrades can affect:

- Derived query method-name parsing.
- Nested properties and join traversal.
- Generated count queries for `Page`.
- Sorting, pagination, and projections.
- `@Query`, `@EntityGraph`, and native queries.
- Repository transaction defaults.
- Entity scanning and persistence unit setup.

Do not test only CRUD `save/findById`. Named and reporting queries may only trigger on rare business paths.

## 25. SQL logs and performance must be governed

Observability tools:

- Hibernate SQL logging.
- JDBC data source proxies in tests.
- Hibernate statistics.
- Database slow-query logs and explain plans.
- APM/tracing with sensitive fields masked.
- Query counts per request and p95/p99 latency.

Illustrative Spring configuration:

~~~properties
spring.jpa.show-sql=false
logging.level.org.hibernate.SQL=DEBUG
logging.level.org.hibernate.orm.jdbc.bind=TRACE
~~~

Bind-value logging categories vary across Hibernate major versions. Bind logging can expose PII, tokens, or customer data, so enable it only in authorized, controlled environments.

Do not merely diff SQL strings. Also compare:

1. Business outputs and row counts.
2. Statement counts and round trips.
3. Query plans and index usage.
4. Bytes transferred and row multiplication.
5. Locking and transaction behavior.
6. Response latency and database CPU.

Syntactically different SQL can still be accurate and fast; nearly identical SQL can pick a bad plan due to parameter types or a missing index.

## 26. Testing against a production-like database

H2 is handy for lightweight tests yet does not fully represent real databases. Common divergences:

- SQL types `BOOLEAN`, `UUID`, `JSON`, `ARRAY`.
- Identifier quoting, case sensitivity, and collations.
- Timezone handling and sub-second precision.
- Sequences and identity columns.
- Locking, isolation levels, and deadlocks.
- Vendor functions and casts.
- Pagination syntax and execution plans.
- Foreign keys, triggers, and generated columns.

Use a database engine and version close to production for persistence integration tests, via Testcontainers or dedicated test environments.

A golden-test matrix:

| Test | Data | What to verify |
|---|---|---|
| Load legacy entity | v1 rows | Mapping, nulls, and enums |
| Insert v2 | Real schema | IDs/sequences, constraints |
| Update relations | Legacy associations | Cascade, FK, orphanRemoval |
| JPQL/HQL | Fixtures with joins | Cardinality, sorting, return types |
| Native SQL | Real driver/database | Scalar mappings and functions |
| Timestamps | Boundary values | Timezones, precision |
| Pagination | Rows with duplicate sort keys | No duplicated or skipped rows |
| Concurrency | Concurrent transactions | Versioning/locking |
| Cache | Entries written by v1 | Readability and isolation |
| Rollback | v2 rows read by v1 reader | Bidirectional if rollout requires |

### 26.1. Fixtures should protect sensitive data

A layout like:

~~~text
fixtures/
  schema/baseline.sql
  data/legacy-order-status.sql
  data/null-and-foreign-key.sql
  data/timezone-boundary.sql
  expected/report-summary.json
~~~

Never copy customer-identifying records or secrets straight from production into repositories. Synthetic or anonymized datasets must still retain edge cases needed for testing.

## 27. Rolling deployments and backward data compatibility

During rolling deployments, old and new versions can hit the same database concurrently:

~~~text
App v1 + Hibernate H1 ----+
                          +---- Schema S ---- Persisted data
App v2 + Hibernate H2 ----+
~~~

If v2 immediately requires a renamed column, running v1 instances break. If v2 writes new enum/format values, v1 may fail to read them even when the schema stays compatible.

Test all of:

- **V1 writer → V2 reader:** new version reads legacy rows.
- **V2 writer → V1 reader:** required for rollbacks or mixed-version clusters.
- V1 and v2 concurrently inserting/updating the same table.
- Sequence/identity generation producing no ID collisions.
- Shared caches/sessions having no format conflicts.
- Transaction/locking invariants holding across versions.

Without bidirectional compatibility, adjust rollout order, introduce a bridge release, or use an approved maintenance window; never assume rolling deployment is automatically safe.

## 28. Rollback is more than downgrading the Hibernate dependency

Once v2 runs, the database or cache may already contain:

- New columns, types, or sequences.
- New enum values.
- Differently normalized timestamps.
- New query result/cache formats.
- Irreversible data backfills.
- Altered constraints or indexes.
- Data serialized by the new framework.

Simply reverting `hibernate-core` to an older version does not restore the prior database state. Rollback plans must cover application artifacts, ORM providers, schema states, persisted data, and active consumers.

Identify the **point of no return** before dropping columns, rotating keys irreversibly, or emitting data formats unreadable by prior versions.

## 29. End-to-end order migration example

Suppose an existing entity has:

~~~text
OrderEntity
  id              @GeneratedValue(AUTO)
  status          EnumType.ORDINAL
  createdAt       LocalDateTime
  customer        @ManyToOne(LAZY)
  total           BigDecimal
~~~

Issues that can surface when upgrading Hibernate:

1. Target provider selects a different implicit sequence name or allocation behavior.
2. Ordinal enum semantics break after adding a status.
3. Timestamps get read under a different timezone assumption.
4. Legacy HQL reports fail due to invalid implicit type comparisons.
5. DTO projections expect `Integer` while `count` returns `Long`.
6. Pagination combined with join fetches multiplies SQL rows.
7. Spring Data generated count queries miscount custom joins.
8. Schema validation/auto-update complains about column types.
9. Old and new nodes write simultaneously using conflicting ID or schema assumptions.

Migration path:

- **Step 1:** Preserve an anonymized database snapshot with legacy rows and baseline SQL/query outputs.
- **Step 2:** Inventory actual providers, frameworks, drivers, and dialects.
- **Step 3:** Inspect ID generators and schema sequence metadata.
- **Step 4:** Verify enum, timestamp, and converter semantics on legacy rows.
- **Step 5:** Upgrade dependencies on a separate branch without unrelated feature changes.
- **Step 6:** Run schema validation, then every critical named, dynamic, Criteria, and native query.
- **Step 7:** Compare query counts, execution plans, transactions, and locking.
- **Step 8:** Design expand–migrate–contract migrations for any required DDL changes.
- **Step 9:** Test mixed-version operation if rolling deployments are used.
- **Step 10:** Canary release, monitor DB/errors/p99, and verify actual rollback readiness.

A migration step is complete only when **query results, persisted data, and business invariants** hold—not merely when `EntityManagerFactory` starts up.

## 30. Quick diagnostic table

| Symptom | Likely cause | Where to start checking |
|---|---|---|
| `Not a managed type` | Entity scan/namespace/provider mismatch | `javax`/`jakarta`, dependency tree |
| Missing table/column | Naming strategy or schema drift | Mappings and database metadata |
| Sequence not found | Generator implicit naming changed | `@GeneratedValue`, sequence SQL |
| `SemanticException` / invalid HQL | Query parser and type mismatch | JPQL/HQL source, bound parameter types |
| `ClassCastException` reading results | Projection/scalar JDBC type changed | Result mappings and JDBC driver |
| `LazyInitializationException` | Persistence context/fetch plan | Transactions and lazy access |
| N+1 / increased DB load | Fetch plan/query shape | SQL count and EntityGraph/fetch joins |
| `ConstraintViolationException` | FK, unique, nullable, or DDL | Database constraints and SQL root cause |
| `OptimisticLockException` | Version conflict | Concurrency and `@Version` |
| Time/enum decoded wrong silently | Semantic data compatibility | Golden fixtures |
| Rollback fails | V2 wrote schema/data unreadable backwards | Expand–contract and rollback tests |
| Query passes H2, fails production DB | Dialect/driver behavior | Integration tests on real engine |

Exception messages vary by provider and framework version. Always inspect the root cause, emitted SQL, and concrete data rather than only the outermost exception type.

## 31. Checklist before finalizing migration

- [ ] Recorded actual versions of JDK, Hibernate, JPA, Spring Data, JDBC, and the database.
- [ ] Confirmed the compatibility matrix across those components.
- [ ] Separated JDK upgrades from ORM/framework major upgrades.
- [ ] Updated `javax.persistence` / `jakarta.persistence` namespaces for the target.
- [ ] Rebuilt generated metamodel/query sources cleanly.
- [ ] Checked entity scanning, annotations, and access strategies.
- [ ] Verified naming strategies and table/column/foreign-key names.
- [ ] Verified sequence/identity/UUID generators under concurrency.
- [ ] Verified numeric precision, `Boolean`, `UUID`, and JSON/array type mappings.
- [ ] Checked converters/custom type SPIs against historical rows.
- [ ] Checked ordinal/string enums, including retired values.
- [ ] Checked timezone and precision handling on legacy timestamps.
- [ ] Checked association owning sides, cascade, and `orphanRemoval`.
- [ ] Compared SQL counts, N+1 patterns, proxies, fetch joins, and entity graphs.
- [ ] Executed named queries, HQL/JPQL, Criteria, Spring Data, and native SQL queries.
- [ ] Verified projections, count/sum types, pagination, and deterministic ordering.
- [ ] Verified transactions, flushing, bulk updates, and optimistic/pessimistic locks.
- [ ] Verified caching behavior under concurrent multi-version operation.
- [ ] Tested migrations on schemas containing legacy rows.
- [ ] Tested against a production-like database engine rather than H2 alone.
- [ ] Preserved golden fixtures, SQL counts, and performance baselines.
- [ ] Verified V1→V2 and V2→V1 where rolling deploys or rollbacks require it.
- [ ] Identified the point of no return alongside backup/restore plans.
- [ ] Masked PII/secrets when capturing SQL and bind logs.

## 32. Conclusion

Hibernate/JPA migration changes a contract spanning the **Java object model, persistence API, provider-generated SQL, database schema, and existing data**. Syntactically valid queries do not guarantee right answers; persisting an entity does not guarantee right enum/timezone semantics; clean startup does not prevent N+1 or locking regressions in production.

A grounded approach captures a baseline using real SQL and historical rows, upgrades a supported JDK/framework/provider/JDBC stack, tests mappings and every query category, governs schema updates with controlled migrations, and deploys with bidirectional data compatibility whenever rolling upgrades or rollbacks are needed.

**The ultimate goal is not merely "getting the new Hibernate running", but "reading, writing, querying, and preserving the exact same data contract on the new release".**
