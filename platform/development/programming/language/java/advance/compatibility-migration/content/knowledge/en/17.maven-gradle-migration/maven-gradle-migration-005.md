# Gradle Java Toolchains and Configuring options.release

## 1. Goals in Java Advance Compatibility Migration

When upgrading the Java version, a project may need to use a newer JDK for the build tool or compiler while still committing that the application/library runs on an older Java version. For example, the CI system switches to JDK 21, while the released library must continue working on Java 17. Without clearly distinguishing between the **JDK used to build** and the **minimum Java level at runtime**, developers can easily accidentally use new JDK APIs, generate incompatible bytecode, or test against the wrong runtime.

Gradle provides two complementary mechanisms:

- **Java Toolchains:** selects the JDK containing the tools that tasks need to use, such as the javac compiler, the Java launcher for running tests, and the Javadoc tool.
- **JavaCompile.options.release:** specifies the Java release that Java source is permitted to use in terms of language level, class-file format, and Java SE APIs present in that release.

Combining the two mechanisms helps define a consistent policy. For instance, taking the compiler from JDK 21 while using --release 17 to compile an artifact targeting Java 17, and then running tests on a Java 17 JVM to prove practical usability.

This lesson belongs to the **Maven and Gradle** group of the **Java Advance Compatibility Migration** module, focusing on designing Gradle configurations, verifying results, and handling common errors when changing JDKs.

After this lesson, readers can:

1. Distinguish the Gradle daemon JVM, Java compiler toolchain, Java release target, and test/runtime JVM.
2. Write Toolchains configuration in build.gradle.kts and build.gradle.
3. Understand why options.release is more reliable than source/target when cross-compiling Java.
4. Produce artifacts with a newer compiler that remain compatible with a lower Java release.
5. Test with the minimum runtime and target runtime.
6. Detect risks from dependencies, generated bytecode, build plugins, and multi-module setups.
7. Diagnose missing JDK, unsupported release, class-file version errors, or CI using the wrong Java version.

## 2. Four Distinct Layers of Java Versions

A question like "What Java version is the project using?" is not precise enough. You need to ask at which layer.

| Layer | Role | Example |
|---|---|---|
| Gradle runtime JVM | The JVM running the Gradle launcher/daemon, build scripts, and plugins. | Gradle runs on JDK 21. |
| Java compiler toolchain | The JDK providing javac to compile sources. | JavaCompile uses JDK 21 javac. |
| Java release target | The syntax level, bytecode, and Java SE APIs classes are allowed to use. | options.release = 17. |
| Test/production runtime JVM | The JVM running the application, test workers, services, or CLI after compilation. | Tests on JDK 17; production runs Java 17. |

A valid configuration:

~~~text
Gradle daemon              JDK 21
Compiler JavaCompile       JDK 21
Compiler --release         17
Test launcher              JDK 17
Production runtime         Java 17
~~~

The compiler from JDK 21 can produce class files for Java 17 via --release 17, provided that compiler supports the target and other parts of the build are compatible. However, using JDK 21 to run Gradle does not mean every class is compiled for Java 21; and options.release=17 does not automatically guarantee all runtime dependencies are Java 17 compatible.

### 2.1. Role of JAVA_HOME

In many environments, the JAVA_HOME variable or the Java chosen by the Gradle launcher affects the JVM running Gradle. However, Java Toolchains allows Java tasks to use a different JDK. Therefore:

- java -version in the terminal may reflect the JDK on PATH.
- ./gradlew --version shows the Gradle version and the JVM Gradle is currently using.
- ./gradlew javaToolchains shows the JDKs Gradle discovered for toolchain selection.
- The javac actually used by compileJava also depends on Java Toolchains and task configuration.
- The JVM running the Test task also depends on javaLauncher and Test conventions.

Do not infer everything solely from JAVA_HOME or the java -version command.

### 2.2. Deployment runtime lies outside toolchains

Toolchains in Gradle do not automatically change Docker images, Kubernetes manifests, systemd services, or application server configurations. You can build properly with --release 17 yet accidentally deploy onto Java 11 and hit UnsupportedClassVersionError. Verify the real environment's runtime via process/image information, not only the build script.

## 3. How Do Java Toolchains Work?

Java Toolchains is Gradle's mechanism for requesting a JDK that satisfies a specification. A Java toolchain specification typically includes:

- languageVersion: Java version.
- vendor: JDK vendor when constrained.
- implementation: implementation type if needed.

Gradle will choose a matching installation among the JDKs it knows about or use a provisioning mechanism if properly configured for that Gradle version and environment.

Kotlin DSL example:

~~~kotlin
plugins {
    java
}

java {
    toolchain {
        languageVersion.set(JavaLanguageVersion.of(21))
    }
}
~~~

This snippet expresses intent: the project wants to use Java toolchain 21. It does not mean "every custom task invoking java automatically runs JDK 21"; custom plugins or Exec/ProcessBuilder tasks may use their own executable.

### 3.1. Compiler, launcher, and Javadoc tool

Roles of toolchain tools:

| Tool | Typically Used By | Notes |
|---|---|---|
| JavaCompiler | JavaCompile and tasks/plugins needing a Java compiler | Can choose a different JDK from the Gradle daemon. |
| JavaLauncher | Test, JavaExec, and compatible JVM execution tasks | Can separately specify the JDK used to run tests. |
| JavadocTool | Javadoc tasks | Not a verification of minimum Java runtime. |

A project can request a JDK 21 compiler while requesting a JDK 17 Test launcher to verify compatibility. If JavaCompile emits Java 21 bytecode while tests run on Java 17, it will fail. That is why setting options.release appropriately is necessary.

### 3.2. Where does Gradle find JDKs?

Gradle has a mechanism to auto-detect pre-installed JDKs across supported locations and supports additional configuration for Java installations. The ability to download/provision JDKs depends on the Gradle version, configured repositories/resolvers, and network connectivity.

Key points:

1. Do not assume declaring a toolchain will always auto-download a JDK.
2. If CI is network-isolated, pre-install JDKs or set up approved provisioning.
3. If locking a specific vendor/implementation, Gradle may fail to find a matching installation even if the machine has a JDK of the same major version.
4. The JDK running the Gradle daemon must still be supported by the Gradle Wrapper and plugins.

Changing JAVA_HOME merely to make the build "work" can mask a misconfigured toolchain. Explicitly document requirements in the build and CI.

## 4. Standard Example in Gradle Kotlin DSL

Suppose a library has the following requirements:

- Use JDK 21 to run the compiler.
- Java source may only use Java SE APIs and syntax from Java 17.
- Java class files must have a format compatible with a Java 17 JVM.

In build.gradle.kts:

~~~kotlin
plugins {
    java
}

java {
    toolchain {
        languageVersion.set(JavaLanguageVersion.of(21))
    }
}

tasks.withType<JavaCompile>().configureEach {
    options.release.set(17)
}
~~~

This is an explicit configuration for JavaCompile tasks in that project. The value 17 is passed as --release 17 when javac executes. If the code uses Java SE APIs only present in Java 21, compilation will be rejected in the cases controlled by --release.

### 4.1. If the product only supports Java 21

For a new major release with a minimum of Java 21:

~~~kotlin
java {
    toolchain {
        languageVersion.set(JavaLanguageVersion.of(21))
    }
}

tasks.withType<JavaCompile>().configureEach {
    options.release.set(21)
}
~~~

This can be the right configuration when the product contract has officially raised the minimum Java level to 21. Do not change 17 to 21 merely because developers installed JDK 21; that change can impact consumers still running Java 17.

### 4.2. If you want compiler and target both to be Java 17

~~~kotlin
plugins {
    java
}

java {
    toolchain {
        languageVersion.set(JavaLanguageVersion.of(17))
    }
}

tasks.withType<JavaCompile>().configureEach {
    options.release.set(17)
}
~~~

This configuration suits a maintenance branch that needs to stay on Java 17 when there is no reason to use a higher compiler. Keep in mind that the Gradle daemon may still run on another JDK supported by the Wrapper.

### 4.3. Public API and the Java Library plugin

When publishing a library, consider the Java Library plugin to separate API dependencies from implementation dependencies. Example build.gradle.kts:

~~~kotlin
plugins {
    id("java-library")
}

java {
    toolchain {
        languageVersion.set(JavaLanguageVersion.of(21))
    }
}

tasks.withType<JavaCompile>().configureEach {
    options.release.set(17)
}

dependencies {
    api("org.example:contract-api:1.0.0")
    implementation("org.example:internal-runtime:2.0.0")
}
~~~

The org.example coordinates are merely illustrative examples. A library whose public API uses --release 17 can still pull in a dependency that only runs on Java 21; therefore, you must inspect the artifact's actual dependency graph.

## 5. Equivalent Configuration in Gradle Groovy DSL

In build.gradle:

~~~groovy
plugins {
    id 'java'
}

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)
    }
}

tasks.withType(JavaCompile).configureEach {
    options.release = 17
}
~~~

With the Java Library plugin:

~~~groovy
plugins {
    id 'java-library'
}

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)
    }
}

tasks.withType(JavaCompile).configureEach {
    options.release = 17
}
~~~

The two DSLs differ in setter syntax but share the same technical goal: selecting the compiler JDK and restricting the Java release for JavaCompile tasks. The examples assume the Gradle and Java plugins used support Java Toolchains/options.release.

## 6. options.release, sourceCompatibility, and targetCompatibility

These three settings are very easy to confuse.

### 6.1. sourceCompatibility

sourceCompatibility governs the Java syntax/language level accepted by the compiler. It can prevent source from using syntax newer than the chosen level, but on its own it is not a complete constraint on class-file format or Java SE APIs.

### 6.2. targetCompatibility

targetCompatibility requests the class-file target for compiled code. For example, Java 17 corresponds to class-file major version 61. However, when using a JDK 21 compiler, setting only targetCompatibility=17 does not necessarily stop the compiler from allowing references to Java 21 methods present in the compiling JDK's platform APIs.

### 6.3. options.release

In JavaCompile, options.release is passed as javac --release. It simultaneously constrains:

- Source language level.
- Class-file target version.
- The Java SE API surface available at the target release.

For example:

~~~kotlin
tasks.withType<JavaCompile>().configureEach {
    options.release.set(17)
}
~~~

With a JDK 21 compiler, --release 17 is an important safeguard to avoid accidentally calling Java 21 platform APIs in code intended to run on Java 17.

| Setting | Source Syntax | Bytecode Target | Target Java SE API |
|---|---|---|---|
| sourceCompatibility=17 | Constrained | Insufficient on its own | Insufficient |
| targetCompatibility=17 | Does not determine source policy by itself | Constrained | Insufficient |
| Both source/target=17 | Constrained | Constrained | Still insufficient with a newer JDK compiler |
| options.release=17 | Constrained | Constrained | Constrained within javac --release scope |
| toolchain=21 | Selects JDK 21 compiler | Does not set target 17 automatically | Does not restrict Java SE APIs down to 17 |
| toolchain=21 + release=17 | JDK 21 compiler | Bytecode 17 | Constrains Java SE APIs down to level 17 |

Avoid combining conflicting sourceCompatibility/targetCompatibility values with options.release; keep one clear policy per JavaCompile task.

### 6.4. Example detecting a Java 21 API

Suppose the code:

~~~java
import java.util.List;

class FirstItem {
    static String get(List<String> items) {
        return items.getFirst();
    }
}
~~~

List.getFirst was introduced with Sequenced Collections in Java 21. If source is compiled with JDK 21 while the product promises Java 17, this is a risk. When configured with --release 17, the compiler will reject using that API against the Java 17 platform.

A Java 17 compatible version can use:

~~~java
static String get(List<String> items) {
    return items.get(0);
}
~~~

This example only illustrates an API difference. Not every new Java API has an equivalent replacement on older Java; sometimes a design change or an announced minimum Java upgrade is required.

## 7. options.release Cannot Downgrade Dependency Bytecode

An important limitation: --release affects compiling **the task's own source**, not recompiling all external libraries.

~~~text
Project source --release 17
          │
          ▼
Application classes: major 61 (Java 17)

Dependency A: major 61 (Java 17)
Dependency B: major 65 (Java 21)
                  │
                  ▼
The application cannot yet be considered Java 17-compatible
~~~

In this example, dependency B can cause UnsupportedClassVersionError on Java 17. Compiling the project's own source for Java 17 cannot resolve dependency B.

### 7.1. Direct and transitive

Do not inspect only the dependencies declared in build.gradle. You must also inspect libraries pulled in transitively:

~~~text
my-service
  ├── web-framework (direct)
  │     └── json-core (transitive)
  └── db-driver (direct)
        └── native-helper (transitive)
~~~

When a transitive dependency raises its minimum Java version, the entire runtime combination may no longer satisfy the minimum Java requirement.

### 7.2. Gradle commands to observe the dependency graph

In a project using the Java plugin:

~~~bash
./gradlew dependencies --configuration compileClasspath
./gradlew dependencies --configuration runtimeClasspath
./gradlew dependencies --configuration testRuntimeClasspath
~~~

For a specific module:

~~~bash
./gradlew :service:dependencies --configuration runtimeClasspath
~~~

Find the paths pulling in a library:

~~~bash
./gradlew :service:dependencyInsight \
    --dependency library-name \
    --configuration runtimeClasspath
~~~

On Windows PowerShell:

~~~powershell
.\gradlew.bat :service:dependencies --configuration runtimeClasspath
~~~

The commands above are instructions for readers to execute in their own projects, not actions to run while writing this article.

### 7.3. Variant metadata and Java compatibility

Gradle Module Metadata can include compatibility attributes, including the Java level a variant requires. In some situations, Gradle can reject selecting a variant unsuitable for the consumer.

However, not every JAR has complete or accurate metadata:

- Artifacts published only with a Maven POM may lack detailed Java variant attributes.
- Metadata may not reflect shaded classes or native code.
- Classes loaded only dynamically or via reflection can still fail.
- A dependency may have compatible bytecode yet call an API absent on the minimum runtime.

Therefore, metadata assists variant selection but **does not replace runtime compatibility tests**.

## 8. Running the Test Task with the Minimum JDK

In migration, an important configuration is a JDK 21 compiler, --release 17, and a JDK 17 Test launcher:

~~~kotlin
plugins {
    java
}

java {
    toolchain {
        languageVersion.set(JavaLanguageVersion.of(21))
    }
}

tasks.withType<JavaCompile>().configureEach {
    options.release.set(17)
}

tasks.withType<Test>().configureEach {
    javaLauncher.set(javaToolchains.launcherFor {
        languageVersion.set(JavaLanguageVersion.of(17))
    })
}
~~~

Under this configuration:

1. Gradle uses the JDK 21 compiler for JavaCompile.
2. JavaCompile tasks are instructed to use --release 17.
3. The Test JVM runs on Java 17 when a suitable toolchain is available.
4. Libraries used by tests at runtime must support Java 17.

This is an example for a Gradle Java project with a standard Test task. If there are custom integrationTest or JavaExec tasks, confirm they use the intended launcher.

### 8.1. Testing on two JDKs using a project property

To reuse the same script across multiple CI jobs:

~~~kotlin
val testJavaVersion =
    providers.gradleProperty("testJavaVersion").orElse("17").get().toInt()

tasks.withType<Test>().configureEach {
    javaLauncher.set(javaToolchains.launcherFor {
        languageVersion.set(JavaLanguageVersion.of(testJavaVersion))
    })
}
~~~

After keeping the JavaCompile configuration above, CI can invoke:

~~~bash
./gradlew clean test -PtestJavaVersion=17
./gradlew clean test -PtestJavaVersion=21
~~~

The two commands are two separate test runs; they can run in independent CI jobs. Two jobs should not concurrently write into the same unisolated build directory.

### 8.2. What actually needs checking?

At minimum, test with the lowest Java version committed by the product to catch:

- UnsupportedClassVersionError from the project or dependencies.
- NoSuchMethodError, NoClassDefFoundError due to missing APIs/runtime dependencies.
- Issues with class loaders, reflection, or module encapsulation.
- Differences in TLS, security providers, locale, charset, or timezone.
- Native libraries or instrumentation agents not supporting the target runtime.

You should have integration tests, not only pure logic unit tests. If the library is distributed to consumers, you can compile a binary client against the old API and run it against the new artifact when policy requires binary compatibility.

## 9. JavaLauncher for JavaExec and Custom Tasks

Some custom Gradle tasks need their own Java launcher:

~~~kotlin
val minimumRuntime = javaToolchains.launcherFor {
    languageVersion.set(JavaLanguageVersion.of(17))
}

tasks.register<JavaExec>("runCompatibilitySmoke") {
    group = "verification"
    description = "Run CLI on the minimum supported Java runtime"
    classpath = sourceSets["main"].runtimeClasspath
    mainClass.set("com.example.cli.Main")
    javaLauncher.set(minimumRuntime)
}
~~~

The example assumes the project has the Java plugin and class com.example.cli.Main. JavaExec gets a dedicated Java 17 JVM. The Gradle daemon and JavaCompile can still use different JDKs.

### 9.1. JavaCompiler Provider

If a custom task needs a compiler, Gradle's JavaToolchainService provides Provider<JavaCompiler>:

~~~kotlin
val compilerFor17 = javaToolchains.compilerFor {
    languageVersion.set(JavaLanguageVersion.of(17))
}
~~~

This is better than hard-coding a javac path from a developer machine. Custom tasks must use the provider properly according to Gradle task APIs and configuration-cache requirements where applicable.

### 9.2. Vendor specification

When the organization has a specific vendor requirement:

~~~kotlin
java {
    toolchain {
        languageVersion.set(JavaLanguageVersion.of(21))
        vendor.set(JvmVendorSpec.ADOPTIUM)
    }
}
~~~

This constraint can prevent Gradle from finding a toolchain on a runner if only a JDK 21 from another vendor is installed. If there is no reason to require a specific vendor, avoid locking it too tightly because it reduces configuration portability across environments.

### 9.3. Do third-party plugins automatically use Toolchains?

Not necessarily. A plugin might run Java using:

- The Gradle daemon JVM.
- A JavaLauncher obtained from Toolchain APIs.
- ProcessBuilder or Exec invoking java from PATH.
- A separately configured executable path.

Therefore, when auditing a build, do not assume every Java task created by a plugin uses java.toolchain. Check plugin documentation, logs, or actual task configuration.

## 10. Checking Which JDK Gradle Is Using

### 10.1. Gradle Wrapper

~~~bash
./gradlew --version
~~~

On Windows:

~~~powershell
.\gradlew.bat --version
~~~

This output shows the reported Gradle version/JVM, but it is not proof of the compiler/test launcher in every task. Use the repository's Gradle Wrapper rather than an arbitrary global Gradle installation.

### 10.2. Listing JDKs detected by Gradle

~~~bash
./gradlew javaToolchains
~~~

This task shows the Java installations Gradle detects along with metadata such as version/vendor. If the requested toolchain does not exist, resolve installation/provisioning before arbitrarily changing the target.

### 10.3. Observing JavaCompile

~~~bash
./gradlew compileJava --info
~~~

Depending on the Gradle version, the log information can show the compiler toolchain or related paths. For multi-module builds, inspect the right task, such as :library:compileJava.

### 10.4. Identifying the JVM inside tests

Example JUnit test:

~~~java
import org.junit.jupiter.api.Test;

class JavaRuntimeInfoTest {
    @Test
    void printRuntime() {
        System.out.println(System.getProperty("java.version"));
        System.out.println(System.getProperty("java.vendor"));
    }
}
~~~

This is illustrative; JUnit must be declared in test dependencies. In real CI, you can assert the expected major version to prevent cases where the job is named Java 17 while the Test task actually runs on JDK 21.

## 11. Verifying Class-File Version

You can inspect class metadata in the artifact:

~~~bash
javap -verbose -classpath build/libs/my-library.jar com.example.LibraryEntry
~~~

Look for major version in the output:

| Java release | Class-file major |
|---|---:|
| Java 8 | 52 |
| Java 11 | 55 |
| Java 17 | 61 |
| Java 21 | 65 |

For JavaCompile --release 17, Java classes produced by javac generally have major 61. However, do not treat one class as representative of every class in the artifact.

You should inspect:

- Other classes in the same JAR.
- Classes generated by annotation processors or bytecode generators.
- Kotlin/Scala/Groovy classes in mixed projects.
- Shaded/fat JAR dependencies with a higher class version.
- Multi-release JARs and the META-INF/versions directory.

Final verification must include running the actual artifact on the minimum Java version.

### 11.1. Multi-release JAR

For example:

~~~text
my-library.jar
  com/example/Feature.class
  META-INF/versions/17/com/example/Feature.class
  META-INF/versions/21/com/example/Feature.class
~~~

A valid multi-release JAR can contain different implementations per Java runtime. The base portion must match the committed minimum Java level; classes in higher version folders are only selected under matching conditions.

Therefore, having a major 65 class inside META-INF/versions/21 does not by itself prove the entire JAR only runs on Java 21; conversely, you should not inspect only the base classes and conclude every part is Java 17 compatible.

## 12. Multi-Module Configuration in Gradle

A repository may have:

~~~text
root
  ├── api-contract
  ├── domain
  ├── service
  └── cli
~~~

Suppose the policy is:

| Module | Compiler | --release | Minimum Runtime |
|---|---|---|---|
| api-contract | JDK 21 | 17 | Java 17 |
| domain | JDK 21 | 17 | Java 17 |
| service | JDK 21 | 21 | Java 21 |
| cli | JDK 21 | 21 | Java 21 |

This is an example of a product whose core libraries support Java 17 while specific applications require Java 21. Depending on module relationships, verify dependencies and public APIs to ensure api-contract does not reference types only available in Java 21 artifacts.

### 12.1. The root project does not automatically apply all configurations to subprojects

The snippet:

~~~kotlin
tasks.withType<JavaCompile>().configureEach {
    options.release.set(17)
}
~~~

only affects matching tasks belonging to the project where that configuration is in effect. If placed in root without configuring subprojects, do not assume every module will be compiled for Java 17.

For multi-module repos, use Gradle convention plugins or a well-scoped configuration approach applied consistently to each module category. This also helps when adding new modules without forgetting toolchain/release policies.

### 12.2. Avoid forcing a single Java level for every artifact

If the same repo contains a public Java 17 library, a Java 21 service, and a build plugin running on JDK 21, those three have different constraints. Forcing all of them to use --release 21 breaks the library's contract; forcing all of them to use --release 17 can unnecessarily restrict legitimate features of the Java 21 service.

Group modules according to each artifact's contract, then verify the links between them.

## 13. Annotation Processors and Generated Bytecode

A project may compile with javac --release 17 yet use:

- Annotation processors.
- Protobuf/OpenAPI/JAXB code generators.
- Proxy/ORM bytecode enhancers.
- Code coverage and instrumentation agents.
- Plugins that generate classes directly.

These tools have their own constraints:

1. The processor must be able to run on the chosen javac/JDK.
2. Generated Java source must not exceed the Java release target.
3. Direct bytecode generators must set the right class-file target themselves.
4. Runtime dependencies of generated classes must suit the minimum Java version.
5. Tooling may use compiler internals and be affected when upgrading the JDK.

For generated code, inspect the class-file output and test runtime, not only handwritten Java files.

### 13.1. Kotlin, Groovy, Scala

In mixed projects, other compilers may have their own JVM target settings. Some Gradle plugins support Java Toolchains, though the degree of integration depends on the plugin/version.

For example, the Kotlin Gradle Plugin may provide kotlin.jvmToolchain and compilerOptions.jvmTarget. Check documentation for the actual plugin version to use the exact syntax and ensure the Kotlin bytecode target matches the Java target.

If JavaCompile produces major 61 while KotlinCompile emits major 65, the overall artifact cannot yet be considered Java 17-compatible.

## 14. Gradle Wrapper and JDK Compatibility for Running Gradle

Toolchains cannot fix cases where the Gradle Wrapper is too old to run on a new JDK.

When upgrading JDK 17 → 21, check:

- Does the Gradle Wrapper version support JDK 21 for **running Gradle**?
- Are the Java Toolchains API and options.release available in the Gradle version in use?
- Are framework or code generation plugins compatible with the new Wrapper/JDK?
- Do CI images contain the JDKs required by Toolchains?
- Does toolchain provisioning have a suitable resolver and permission to reach repositories?

A sensible sequence:

~~~text
Inventory current JDK / Gradle Wrapper
              │
              ▼
Select a Gradle Wrapper compatible with the JDK launcher
              │
              ▼
Upgrade necessary build plugins
              │
              ▼
Declare java.toolchain and options.release
              │
              ▼
Verify compiler/test launchers and runtime tests
~~~

Do not try to fix "Gradle fails to start on JDK 21" merely by setting options.release=21; those are two different layers.

## 15. Handling Common Errors

### 15.1. No matching toolchains found

A typical message:

~~~text
No matching toolchains found for requested specification
~~~

Possibilities:

- The desired JDK is not installed yet.
- Gradle did not detect the installed JDK.
- The vendor constraint is too strict.
- Provisioning is unconfigured, a resolver is missing, or the environment lacks network access.
- No distribution satisfying the requirements exists for the current architecture/OS.

Resolution approach: inspect ./gradlew javaToolchains, identify installation paths, check CI provisioning and vendor constraints; install/configure the right JDK, then retry the task.

### 15.2. error: release version X not supported

When javac is too old to support the target, for example a JDK 17 compiler with options.release=21, javac cannot generate that release.

Solution: select a compiler JDK supporting the corresponding --release, rather than only changing the JVM running Gradle. Inspect the actual toolchain of JavaCompile.

### 15.3. UnsupportedClassVersionError

For example:

~~~text
class file version 65.0; runtime recognizes up to version 61.0
~~~

Java 17 cannot load Java 21 class files. Causes may be a module built with the wrong release, a shaded dependency, generated code, or a test library that only supports Java 21.

Identify the first class causing the error, the artifact/JAR containing it, its major version, and the dependency path pulling it in. Do not assume this is a bug in the main JavaCompile task itself.

### 15.4. NoSuchMethodError on the minimum runtime

One cause is code using new Java SE APIs compiled with a new JDK using old source/target without --release. When the older runtime lacks the API, the call fails.

Another cause is a conflict between versions of an external dependency. Distinguish them using the stack trace, class source, and resolved runtime graph.

### 15.5. Tests still use JDK 21 even though the CI job is named Java 17

Test.javaLauncher may be getting overridden, or a custom task invokes Java via PATH. Check the java.version property directly inside the test JVM, combined with logs and test launcher task configuration.

### 15.6. Libraries or plugins using internal JDK APIs

Reflection and Java module encapsulation can break older libraries on a newer JDK. Toolchains only select the JDK; they do not upgrade dependencies or change implementations. Upgrade/replace with compatible libraries, and use jdeps or integration tests to locate the issues.

### 15.7. No matching variant of a dependency

If Gradle reports no variant matches the Java level requested by the consumer, inspect Java compatibility metadata, artifact version, and module target. If still committed to Java 17, do not unilaterally raise release to 21 merely to silence dependency resolution errors; pick a dependency version still supporting Java 17 or make a controlled baseline change.

## 16. CI Matrix by Supported Java Runtimes

A pipeline can split into:

~~~text
Source + dependency locks
          │
          ▼
Gradle Wrapper / compiler toolchain JDK 21
          │
          ▼
JavaCompile --release 17
          │
          ▼
Artifact + checksum
          │
      ┌───┴──────┐
      ▼          ▼
Run Java 17   Run Java 21
      │          │
      └───┬──────┘
          ▼
Compatibility report
~~~

For publicly released library projects, this can include binary client fixtures built at an older version and run against the new artifact without recompiling.

### 16.1. Illustrative CI skeleton

~~~yaml
strategy:
  matrix:
    java_runtime: [17, 21]

steps:
  - name: Checkout and prepare JDKs
    # Set up Java runtimes and toolchains appropriate for CI.
  - name: Run compatibility tests
    run: ./gradlew clean test -PtestJavaVersion=17
~~~

This is only a conceptual skeleton, not a complete workflow: it still needs checkout, JDK setup, mapping the matrix to the property, caching, and artifact management tailored to the CI platform. In a real configuration, the project property should take its value from the matrix cell rather than hard-coding 17.

The essential point is that the Test task runs on the actual JVM corresponding to the matrix cell. The CI Java setup step alone does not guarantee that if Test.javaLauncher is already fixed to another JDK.

### 16.2. Testing the actual artifact

The Test task only tests the classpaths used by tests. For executable JARs or Spring Boot applications, try starting the packaged artifact on the minimum Java version.

Workflow:

1. Build the artifact once according to the toolchain and release policy.
2. Record checksum/version and the resolved runtime dependency graph.
3. Deploy/run the artifact on Java 17.
4. Execute health, API, or CLI smoke tests.
5. Run again on Java 21 if support is also declared.
6. Compare results and store evidence for the release.

Avoid building two different artifacts in two jobs and treating them as proof that one binary works across multiple JDKs.

## 17. Java Baseline Configuration and Release Policy

An illustrative internal support matrix:

| Component | Configuration | Owner |
|---|---|---|
| Gradle Wrapper | Version supporting the chosen JDK launcher | Build/platform team |
| Gradle runtime JVM | JDK 21 | CI daemon |
| Compiler toolchain | JDK 21 | java.toolchain |
| Java source/API/bytecode target | Java 17 | options.release |
| Test runtimes | Java 17, Java 21 | Test.javaLauncher and CI |
| Production minimum runtime | Java 17 | Product support policy |
| Dependency versions | Set verified for Java 17 | BOM/dependency management |
| Container runtime | Java 17 or announced supported Java | Deployment team |

Do not merely change options.release=17 to 21 when the product raises its minimum Java level. You must update the test matrix, dependency policy, release notes, deployment images, build pipeline, and migration guide.

### 17.1. Changing the compiler does not necessarily change the baseline

A module previously compiled with JDK 17 can switch to a JDK 21 compiler + --release 17, keeping the Java 17 minimum if dependencies and behavior permit. This is the basis for modernizing the build pipeline without forcing consumers to upgrade their JVMs immediately.

### 17.2. Changing the baseline must be an announced decision

If a new dependency/framework forces Java 21, do not silently raise output bytecode. Announce the new minimum Java level in the appropriate product version, support consumers in planning migration, and consider maintaining the older branch for the committed support window.

## 18. Misconceptions to Avoid

| Misconception | Explanation |
|---|---|
| JAVA_HOME is always JavaCompile's JDK. | Toolchains can select a compiler different from the JVM running Gradle. |
| java.toolchain=21 means the application only runs on Java 21. | options.release can target Java 17 classes and APIs. |
| sourceCompatibility and targetCompatibility suffice to lock Java SE APIs. | A newer compiler can still see newer JDK APIs without an appropriate --release. |
| --release 17 makes every dependency JAR run on Java 17. | It does not downgrade bytecode in external dependencies. |
| Build passing on JDK 21 proves Java 17 compatibility. | You must run tests on Java 17 and inspect the runtime graph. |
| Gradle auto-downloads a JDK if the toolchain is missing. | Depends on version, resolvers, configuration, and network. |
| Configuring in root is enough for all subprojects. | Must be applied and verified in each project/convention. |
| The Test task always uses the Gradle daemon JVM. | It can use a separate launcher. |
| Every Java-related plugin uses Toolchains. | Plugins can execute binaries from PATH. |
| One major 61 class means the whole fat JAR is Java 17 compatible. | Other classes, shaded dependencies, or generated code may have higher major versions. |
| Toolchains adjust Java in the production image. | The build tool does not automatically change deployment runtime. |
| Using a newer JDK fixes all JDK internals errors. | You must still address libraries, reflection, JPMS, or runtime APIs. |

## 19. Workflow for Rolling Out Gradle Configuration When Upgrading the JDK

**Step 1 — Inventory.** Record the Gradle Wrapper, JDK launcher, JavaCompile toolchain, source/target/release, Test launcher, dependencies, and committed minimum Java runtime.

**Step 2 — Upgrade the Gradle Wrapper if needed.** Based on the compatibility matrix, pick a Wrapper and build plugins capable of running on the new JDK launcher.

**Step 3 — Declare Java Toolchains.** Select the compiler JDK for each project or convention plugin; lock vendor only when needed.

**Step 4 — Set options.release.** Use the actual minimum Java target rather than defaulting to the compiler JDK.

**Step 5 — Align other compilers.** Check generated code, annotation processors, Kotlin/Groovy/Scala, bytecode enhancers, and packaging.

**Step 6 — Check dependencies.** Evaluate direct and transitive ones, Gradle variant metadata, native/JDK internals, framework BOMs, and the runtime graph's minimum Java.

**Step 7 — Run on the minimum JDK.** Configure the Test launcher or CI jobs and verify the actual JVM. Combine integration tests and smoke tests.

**Step 8 — Inspect the artifact.** Check class-file versions, shaded dependencies, multi-release JARs, Docker images, or application-server runtimes.

**Step 9 — Record evidence.** Save the Wrapper version, JDK/toolchain selection, release target, dependency graph, artifact checksum, CI test results, and untested boundaries.

**Step 10 — Release.** If the baseline changes, update the compatibility matrix, release notes, and migration guide; roll out in a controlled manner and monitor for errors.

## 20. Checklist for a Real Project

- [ ] Gradle Wrapper runs on the selected JVM launcher.
- [ ] Java Toolchains finds the right compiler JDK.
- [ ] options.release is explicitly declared according to minimum Java.
- [ ] No conflicting sourceCompatibility/targetCompatibility exists.
- [ ] Each module's JavaCompile task complies with the convention.
- [ ] Test.javaLauncher runs on the right CI matrix runtime.
- [ ] Custom Test/JavaExec tasks and necessary plugins have been verified.
- [ ] The runtime dependency graph does not require a newer Java than announced.
- [ ] Generated bytecode and other language compilers have matching targets.
- [ ] Packaged artifacts, fat JARs, and multi-release entries have been inspected.
- [ ] Integration/smoke tests run on the actual minimum Java version.
- [ ] Docker/container/application-server runtime is explicitly documented.
- [ ] Build evidence, checksums, and support policy are stored with the release.

The checklist is a project verification guide, not proof of completion if the steps have not actually been run.

## 21. Conclusion

**Gradle Java Toolchains** controls *the JDK used to run the build's Java tools*, while **JavaCompile.options.release** controls *the source level, bytecode, and Java SE APIs an artifact is permitted to depend on*. Configuring a JDK 21 compiler with --release 17 is a useful technique to modernize pipelines while still targeting Java 17.

However, compatibility does not stop at a single line in build.gradle. Direct and transitive dependencies, generated code, frameworks/plugins, module path, native libraries, and packaged artifacts can all impose a higher Java level. Therefore, you must verify the actual compiler and Test launcher, run tests on the minimum runtime, compare class-file versions, inspect the dependency graph, and store release evidence.

By clearly separating Gradle runtime, compiler toolchain, --release target, and production Java, teams can upgrade the JDK under control, avoid accidentally breaking the minimum Java contract, and create reproducible builds across both developer machines and CI.
