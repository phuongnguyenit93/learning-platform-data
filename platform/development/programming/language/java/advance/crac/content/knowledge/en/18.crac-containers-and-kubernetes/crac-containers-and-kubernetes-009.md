# Rolling Updates, Autoscaling, and Per-Pod Identity

When deploying CRaC-enabled Java applications on Kubernetes, a checkpoint can help a new Pod restore pre-initialized JVM state and reach readiness faster. However, a checkpoint created from an old Pod does not carry a valid identity for the new Pod. The new Pod has its own UID, IP, hostname, node, tokens, and lifecycle; it must also participate properly in Kubernetes rolling updates, readiness, draining, and autoscaling.

What must be designed clearly is that **application state can be reused, while identity and resources tied to a Pod must be refreshed**. If a checkpoint contains the Pod UID, IP address, leases, subscriptions, or connections of an old replica, multiple Pods created from the same checkpoint may start with duplicated or stale state.

This article explains how to combine checkpoint/restore with Deployment rolling updates, Horizontal Pod Autoscaler (HPA), readiness probes, and per-Pod identity. The goal is for each new replica to restore quickly, refresh resources for its current environment, and receive traffic only after it is ready.

## 1. Distinguishing Container Images and CRaC Checkpoint Images

In Kubernetes environments, the term *image* usually refers to an OCI/container image stored in a registry. In CRaC, a *checkpoint image* is process state data generated by the runtime to restore the JVM. The two artifact types play different roles:

| Artifact | Contents | Lifecycle |
|---|---|---|
| OCI image | JRE/JDK, application, libraries, default configuration, and entrypoint | Pulled from registry to create containers |
| CRaC checkpoint | Running process state, heap, and runtime state needed for restore | Created, stored, verified, and used to restore the process |
| Pod runtime identity | UID, name, IP, node, service account, and volume mounts of the current Pod | Assigned by Kubernetes to each Pod |

An OCI image may contain a pre-built checkpoint, or the container may read the checkpoint from a volume/object storage at startup. Either way, a checkpoint remains the state of a specific process. Do not treat it as a generic configuration bundle capable of carrying all runtime values verbatim across every replica.

A checkpoint also does not create Pods itself or participate in rollouts. Kubernetes still creates Pods according to the Pod template of a Deployment or StatefulSet. The container's entrypoint and CRaC-enabled runtime must execute the proper restore mode; readiness is reached only after the application restores required dependencies.

## 2. A Pod Is a Unit with Its Own Identity and Short Lifecycle

A Pod is the smallest deployable unit in Kubernetes. Pods can be deleted and replaced during rollouts, autoscaling, node failures, or rescheduling. A new Pod may run the same container image and the same checkpoint as an old Pod, yet remains a distinct entity.

Important identifying attributes:

| Attribute | Source | Characteristics |
|---|---|---|
| Pod UID | `metadata.uid` | Unique identifier for a single Pod creation; replacement Pods have new UIDs |
| Pod name | `metadata.name` | Name within the namespace; may be reused after the old Pod is deleted |
| Namespace | `metadata.namespace` | Scope for names and many Kubernetes resources |
| Pod IP | `status.podIP` | Network address of the Pod; replacement Pods usually get different IPs |
| Hostname | `spec.hostname` or Pod name by default | May change across Pods |
| Node name | `spec.nodeName` | Node chosen by the scheduler; a new Pod may run on another node |
| Service account | `spec.serviceAccountName` | Workload identity used when accessing the Kubernetes API or integrated services |
| Labels/annotations | `metadata.labels`, `metadata.annotations` | Metadata controlling routing, rollouts, policies, and observability |

Do not use Pod IP or Pod name as a durable identifier for business data. If a replica needs to be identified in logs or telemetry, Pod UID is a better choice than Pod name because UIDs do not collide when names are reused.

For business logic, distinguish:

- **Service identity:** stable service name such as `orders-api`, used in configuration, metrics, and discovery.
- **Workload identity:** identity of the workload or service account, used for authentication and authorization.
- **Pod identity:** UID and metadata of a specific Pod, used to distinguish replicas.
- **Process/run identity:** identifier for a single JVM run or restore, which can be regenerated after each restore.

Do not merge these identity types into a single UUID stored on the heap before checkpoint. When multiple Pods restore the same checkpoint, the UUID value in the heap may be duplicated, causing multiple replicas to claim to be the same instance.

## 3. Why Do Old Identities in a Checkpoint Cause Failures?

Suppose Pod `orders-api-7f8d9` takes a checkpoint with Pod UID `uid-A`, Pod IP `10.2.1.17`, and node `worker-1`. Later, a Deployment rolling update creates a new Pod `orders-api-9c4ab`, with UID `uid-B`, IP `10.2.3.24`, and node `worker-3`. If the JVM restores from the checkpoint yet keeps using values stored in the heap, the application may log under the old UID, register with service discovery using the old IP, or use a lease belonging to the deleted Pod.

Common errors:

- Multiple Pods emit telemetry with the same `instanceId` stored in the checkpoint.
- Clients or connection pools hold sockets to old endpoints.
- Service discovery registers the old Pod address or fails to deregister expired addresses.
- Old leases or leader-election state cause multiple replicas to think they are still the leader.
- Consumers keep subscriptions, consumer IDs, or sessions tied to the old replica.
- Tokens, certificates, or credentials have expired or were issued for another workload identity.
- Caches hold configuration, DNS results, or data valid only in the old environment.

The design rule is: pure Java data may be reused if still valid; state tied to a Pod, node, socket, credential, or lease must be verified or recreated after restore.

## 4. How Do Deployment Rolling Updates Work?

When a Deployment's Pod template changes, Kubernetes creates a new ReplicaSet and gradually replaces old Pods according to `strategy.rollingUpdate`. The Deployment orchestrates how many new Pods are created and how many old Pods may be unavailable during the rollout.

Two key parameters:

- `maxSurge`: number of Pods that can be created above the desired replica count during a rollout.
- `maxUnavailable`: maximum number of Pods that can be unavailable during a rollout.

For example, with `replicas: 4`, `maxSurge: 1`, and `maxUnavailable: 1`, the Deployment can temporarily have up to 5 Pods and allow at most 1 Pod unavailable per rollout rules. Actual values also depend on readiness and Pod progress.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders-api
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 1
  selector:
    matchLabels:
      app: orders-api
  template:
    metadata:
      labels:
        app: orders-api
    spec:
      containers:
        - name: app
          image: registry.example.com/orders-api:2.4.0
          ports:
            - name: http
              containerPort: 8080
```

In a rollout with CRaC, new Pods can restore from a checkpoint of a compatible version. However, the Deployment only cares whether the new Pod becomes Ready; Kubernetes does not automatically verify whether the checkpoint matches the application version or runtime. The release pipeline must bind the checkpoint to the corresponding image, JDK/CRaC runtime, architecture, and configuration.

### 4.1. How a New Pod Participates in a Rollout

A deployment sequence can include:

1. Deployment creates a new Pod from the new ReplicaSet's Pod template.
2. Container image is pulled, and volumes and Downward API are mounted.
3. Entrypoint checks the checkpoint artifact and selects restore mode.
4. CRaC-enabled JVM restores process state.
5. The `afterRestore` callback refreshes identity, connections, tokens, leases, and environment-dependent resources.
6. The application runs health checks and reports Ready only when mandatory dependencies operate.
7. Service/EndpointSlice begins routing traffic to the new Pod once the Pod is Ready.
8. The old Pod is marked terminating, stops receiving traffic, drains requests, and shuts down safely.

If restore fails, the new Pod must not report Ready. Kubernetes may restart the container per restart policy, or the Deployment continues waiting until the rollout progresses or exceeds `progressDeadlineSeconds`. Do not automatically fall through to running the new application in an indeterminate state if checkpointing errors; provide an explicit, observable cold-start fallback.

## 5. Readiness, Startup, and Liveness Probes

Probes determine how Kubernetes interprets container state:

| Probe | Question | Behavior on failure |
|---|---|---|
| Startup | Has the application finished its initial startup phase? | Kubernetes does not run liveness/readiness until startup probe succeeds; if timed out, container is restarted |
| Readiness | Can the Pod accept traffic right now? | Pod is removed from traffic-serving Service endpoints while unready |
| Liveness | Does the process need to be restarted because it is no longer functioning normally? | Kubelet restarts the container once probe failures hit threshold |

With CRaC, readiness should check post-restore state rather than only whether the JVM process exists. For example, the JVM may have restored while the database pool has not reconnected, consumers have not subscribed, or Pod identity has not been refreshed.

A startup probe is suitable when restore times vary. It allows setting a long enough startup window without letting the liveness probe restart the container prematurely. The readiness probe must reflect actual prerequisites to receive traffic. The liveness probe should check whether the process is hung or incapable of recovering; do not fail liveness merely because a dependent service is temporarily unavailable if doing so causes Pods to restart continuously and add load.

Example configuration:

```yaml
containers:
  - name: app
    image: registry.example.com/orders-api:2.4.0
    ports:
      - name: http
        containerPort: 8080
    startupProbe:
      httpGet:
        path: /actuator/health/liveness
        port: http
      periodSeconds: 5
      failureThreshold: 60
    readinessProbe:
      httpGet:
        path: /actuator/health/readiness
        port: http
      periodSeconds: 3
      timeoutSeconds: 2
      failureThreshold: 2
    livenessProbe:
      httpGet:
        path: /actuator/health/liveness
        port: http
      periodSeconds: 10
      timeoutSeconds: 2
      failureThreshold: 3
```

The endpoints in the example must be configured to accurately reflect CRaC restore and dependency state. `failureThreshold` and `periodSeconds` are illustrative values only; measure restore times on real infrastructure to choose suitable bounds.

## 6. Graceful Termination and Draining Old Pods

During a rolling update, old Pods transition to terminating status. Kubernetes runs the `preStop` hook if present, sends the termination signal to the container per configuration, and waits up to `terminationGracePeriodSeconds` before forcefully terminating the process.

The application needs to coordinate multiple steps:

1. Stop readiness so the Pod is no longer selected for new traffic.
2. Stop accepting new work from listeners, consumers, and schedulers.
3. Drain in-flight requests and finish required transactions.
4. Close connections and resources via CRaC lifecycle or normal shutdown.
5. Exit before the termination grace period expires.

Do not assume setting readiness to false immediately eliminates all requests en route to the Pod. EndpointSlice, kube-proxy, ingress controllers, and load balancers may take time to update. `preStop` can be used to start quiescing or coordinate draining, though hook execution time counts inside the termination grace period.

Example configuration:

```yaml
spec:
  terminationGracePeriodSeconds: 60
  containers:
    - name: app
      lifecycle:
        preStop:
          httpGet:
            path: /internal/quiesce
            port: 8080
```

The `/internal/quiesce` endpoint is an application-implemented API. It should switch readiness to false, stop admission, and await drain within a deadline. A `preStop` hook does not create a checkpoint automatically. Nor does Kubernetes automatically invoke a CRaC checkpoint merely because a Pod is terminating; checkpointing on shutdown requires a separate workflow with suitable privileges, time, and conditions. For standard rollouts, use a pre-prepared checkpoint for new Pods and graceful shutdown for old Pods.

`terminationGracePeriodSeconds` must exceed the total budget for quiescing, draining, and closing resources. If draining takes longer than this period, the kubelet may forcefully kill the container before the application finishes.

## 7. Autoscaling: Each New Replica Is a Separate Restore

Horizontal Pod Autoscaler adjusts replica counts based on metrics such as CPU, memory, or custom/external metrics. When load increases, HPA can add Pods; each new Pod goes through scheduling, image pull, volume setup, restore, resource refresh, and readiness.

CRaC can reduce JVM and framework initialization time, yet does not eliminate all Pod creation latency. Steps that can still take time include:

- Scheduler finding a node matching CPU, memory, affinity, taints, and topology.
- Pulling the OCI image if the node lacks the image.
- Attaching/mounting volumes containing the checkpoint or application data.
- Reading and restoring the checkpoint from storage.
- Recreating sockets, pools, tokens, leases, and subscriptions.
- Running health checks and waiting for endpoint updates.

Therefore, when designing autoscaling, measure from the moment HPA decides to scale until the Pod is Ready and receives its first request. Measure restore duration separately to see which phase CRaC reduces.

### 7.1. HPA and Example Configuration

Example HPA using CPU utilization:

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: orders-api
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: orders-api
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 65
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0
      policies:
        - type: Pods
          value: 4
          periodSeconds: 60
    scaleDown:
      stabilizationWindowSeconds: 300
```

This is an illustrative configuration, not a fixed recommendation for every workload. HPA requires metrics server or a corresponding adapter; resource requests must be configured for CPU utilization to be meaningful. `behavior` limits scaling speed and reduces oscillation when load changes rapidly.

### 7.2. Concurrent Scale-Out and Thundering Herds

When HPA creates many Pods simultaneously, all may read the same checkpoint artifact, open connections to the same database, and load the same cache data. If the checkpoint is large, storage may become a bottleneck. If all Pods connect immediately after restore, the database or service discovery may get overwhelmed.

Measures to reduce load peaks:

- Use appropriate scale-up limits so too many Pods are not created in a single cycle.
- Cap concurrency of restore or refresh steps if storage/dependencies have limits.
- Use retries with exponential backoff and jitter for external connections.
- Start consumers and warm caches in batches if the workload permits.
- Size connection pools based on total expected replicas, not just a single Pod.
- Monitor restoring Pod count, Ready Pod count, and dependency recovery time.

Connection retry jitter does not replace HPA policies. A cluster can still spawn many Pods at once; tune both scale speed and per-Pod startup behavior.

## 8. Assigning New Pod Identity via the Downward API

Kubernetes Downward API lets you inject Pod metadata into a container as environment variables or file volumes. With CRaC, be careful when using environment variables for identity: values are injected when the container is created, whereas the heap and process state restored from a checkpoint may hold values captured in the old Pod. Do not assume creating a new Pod automatically replaces all identity values stored inside the JVM.

A clean approach is mounting identity fields through a Downward API volume and re-reading them after restore:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: orders-api-example
  labels:
    app: orders-api
spec:
  containers:
    - name: app
      image: registry.example.com/orders-api:2.4.0
      volumeMounts:
        - name: pod-identity
          mountPath: /etc/pod-identity
          readOnly: true
  volumes:
    - name: pod-identity
      downwardAPI:
        items:
          - path: uid
            fieldRef:
              fieldPath: metadata.uid
          - path: name
            fieldRef:
              fieldPath: metadata.name
          - path: namespace
            fieldRef:
              fieldPath: metadata.namespace
          - path: pod-ip
            fieldRef:
              fieldPath: status.podIP
          - path: node-name
            fieldRef:
              fieldPath: spec.nodeName
```

Each Pod has a volume populated from that Pod's own metadata. After restore, the application re-reads the files from the current mount instead of using pre-checkpoint cached values. Identity fields immutable for the Pod's lifetime such as UID do not change by themselves; a new Pod gets a new UID. Some metadata may change over time and Downward API volumes are updated per Kubernetes semantics. Check documentation on supported fields and do not assume every field shares the same update mechanism.

If using environment variables from `fieldRef`, such as `POD_NAME`, `POD_UID`, `POD_NAMESPACE`, treat them as values tied to container creation. Do not rely on them as the sole source to refresh identity inside a JVM restored from another process's checkpoint.

## 9. Reading Current Identity in Java After Restore

Downward API files can be grouped into a provider and re-read in the `afterRestore` callback:

```java
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;

public record PodIdentity(
        String uid,
        String name,
        String namespace,
        String podIp,
        String nodeName) {
}

public final class PodIdentityProvider {
    private final Path root;

    public PodIdentityProvider(Path root) {
        this.root = root;
    }

    public PodIdentity readCurrent() throws IOException {
        return new PodIdentity(
                read("uid"),
                read("name"),
                read("namespace"),
                read("pod-ip"),
                read("node-name"));
    }

    private String read(String file) throws IOException {
        return Files.readString(root.resolve(file)).trim();
    }
}
```

A Resource updates identity ahead of resources depending on it:

```java
import org.crac.Context;
import org.crac.Core;
import org.crac.Resource;

public final class PodIdentityResource implements Resource {
    private final PodIdentityProvider provider;
    private volatile PodIdentity current;

    public PodIdentityResource(PodIdentityProvider provider) throws Exception {
        this.provider = provider;
        this.current = provider.readCurrent();
        Core.getGlobalContext().register(this);
    }

    @Override
    public void beforeCheckpoint(Context<? extends Resource> context) {
        // Identity is read-only; no need to close resources.
    }

    @Override
    public void afterRestore(Context<? extends Resource> context)
            throws Exception {
        current = provider.readCurrent();
    }

    public PodIdentity current() {
        PodIdentity value = current;
        if (value == null) {
            throw new IllegalStateException("Pod identity is not initialized");
        }
        return value;
    }
}
```

The example assumes the `/etc/pod-identity` mount is present in the filesystem accessible to the restoring process. In a containerized CRaC deployment, confirm the actual restore mechanism preserves the new Pod's mounts and runs callbacks after volumes are ready. If the runtime or platform does not guarantee that, move identity acquisition into the appropriate entrypoint/restore integration and open readiness only after verification.

Register `PodIdentityResource` before resources that create clients, register service discovery, or emit telemetry. With the global context, `afterRestore` runs in registration order; identity is refreshed before consumers. `beforeCheckpoint` runs in reverse order, so consumers stop first.

This holds true only when the new Pod's volume mounts are genuinely present in the mount namespace used by the runtime to restore. Verify that behavior with your specific CRaC/container integration; if the runtime restores an old mount namespace, a platform-specific step must supply current metadata before opening readiness.

## 10. Generating a New Process Identity After Every Restore

Pod UID distinguishes Pods, yet sometimes the application also needs an identifier per JVM launch or restore. For example, a Pod may restart its container several times while the Pod UID stays unchanged. A new `processRunId` helps distinguish each run in logs and traces.

Do not store `processRunId` as a static final initialized before checkpoint if you want it to distinguish restores. Regenerate the value in `afterRestore` or in a post-restore bootstrap step, then update MDC/tracing/metrics context in a thread-safe manner.

Example:

```java
import java.util.UUID;

public final class ProcessRunIdentity {
    private volatile String runId = UUID.randomUUID().toString();

    public void refreshAfterRestore() {
        runId = UUID.randomUUID().toString();
    }

    public String current() {
        return runId;
    }
}
```

The `runId` value can be refreshed inside a `Resource.afterRestore`. Use Pod UID as the dimension to identify the Pod and process run ID to identify the run; do not use the two concepts interchangeably.

## 11. Refreshing Tokens and Workload Identity

Pods may use a Kubernetes ServiceAccount to access the API server or use cloud platform workload identity. Mounted tokens may rotate; certificates and credentials may have expiration times. If the application holds a token in the heap before checkpoint, that token may expire or become invalid after restore.

Principles:

- Do not bake long-lived tokens or secrets into a checkpoint if they can be fetched again from a secret manager or projected volume.
- After restore, re-read tokens from the projected ServiceAccount token volume or use a supported credential provider.
- Do not cache tokens indefinitely; respect expiration and provider refresh mechanisms.
- If using mTLS, recreate or refresh the TLS context when certificates change.
- Do not write tokens, private keys, or credentials to logs or metrics.
- Confirm permissions of the new service account match the current Pod template.

Projected ServiceAccount tokens can be rotated by the kubelet. Applications must re-read the file or use credential libraries capable of reloading tokens; holding old token contents in the heap can cause post-restore requests to receive authentication failures.

## 12. Leases, Leader Election, and Distributed Locks

A checkpoint may contain leader state, lease owner, or distributed locks in the heap. When multiple Pods restore from the same checkpoint, this state can be duplicated. Never assume the new Pod is still the leader merely because the pre-checkpoint snapshot held `isLeader = true`.

After restore:

1. Clear or invalidate old leadership state in memory.
2. Reconnect to the coordination backend.
3. Acquire/renew the lease according to the current protocol.
4. Use lease expiration and fencing tokens to prevent old owners from continuing to write.
5. Run leader tasks only after the lease is confirmed.

If using the Kubernetes Lease API for leader election, each Pod needs its own identity as `holderIdentity`, such as Pod UID plus process run ID. Do not copy holder identity from the checkpoint. The Lease in the API server is the source of truth; the snapshot is merely potentially stale local state.

For distributed locks outside Kubernetes, a fencing token or monotonically increasing version is required. Relying solely on "already acquired the lock before checkpoint" is insufficient because another process may have acquired the lock while the old Pod was stopped.

## 13. Deployment or StatefulSet?

Choose the controller based on application semantics:

| Controller | Identity | Storage/network | Suitable for |
|---|---|---|---|
| Deployment | Replicas have no stable ordinal; new Pod UID on replacement | Typically uses shared or ephemeral storage | Stateless APIs, web services, horizontally scalable workers |
| StatefulSet | Pods have stable ordinals like `orders-0`, `orders-1` | Can attach dedicated PVCs per ordinal and headless Services | Workloads needing stable ordinal identity and storage |

StatefulSets provide stable ordinal identity, yet Pod UID and Pod IP still change when a Pod is recreated. Do not confuse the name `orders-0` with the UID of a specific Pod creation. PVCs bound to an ordinal can preserve data across Pod replacement, though checkpoints must still be compatible with the runtime and volume; ensure two processes never restore and write to the same PVC simultaneously.

If the workload is a stateless API, Deployment usually fits better. Business state should live in a database, object storage, or durable queue. CRaC checkpoints accelerate startup and should not become the sole source of truth for a replica's business state.

## 14. PodDisruptionBudget and Capacity Maintenance

PodDisruptionBudget (PDB) sets a budget for how many Pods may be disrupted by voluntary disruptions such as node drains. PDB helps protect availability during certain administrative operations, yet does not replace Deployment rollout strategies. Deployment rolling updates are governed primarily by `maxSurge` and `maxUnavailable` in the Deployment strategy; PDB is not a mechanism that locks all Pods during a rollout.

Example:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: orders-api
spec:
  minAvailable: 3
  selector:
    matchLabels:
      app: orders-api
```

A PDB only takes effect if its selector matches Pods and replica counts/capacity allow maintaining `minAvailable`. A PDB does not guarantee sufficient capacity if multiple Pods fail outside voluntary disruptions, nor does it fix faulty readiness. When using a PDB, design it in sync with replicas, rollout strategy, autoscaling, and topology spread.

## 15. Shared Checkpoints and Per-Pod Data

A pre-built checkpoint can serve as a base for multiple Pods if the runtime and platform support that model. The ability to restore the same checkpoint on another Pod or another node depends on the runtime, kernel, CPU architecture, namespaces, filesystems, and CRaC/CRIU integration constraints. Do not assume an arbitrary checkpoint can migrate freely across every node in a cluster. Before rollout, test restoring on the exact node pools and container runtime used in production. Classify state inside the checkpoint:

| State | Can be shared? | Post-restore action |
|---|---|---|
| Class metadata and immutable object graphs | Usually yes | Can be reused if compatible |
| Public, rarely changing data caches | Yes | Check freshness and invalidate if needed |
| Pod UID, Pod IP, node name | No | Read current Pod identity |
| Process run ID or random instance ID | No | Regenerate per restore |
| Sockets, connection pools, TLS sessions | Should not assume | Close/reopen or refresh per library |
| Service discovery registration | No | Register current address, deregister old state if needed |
| Leader leases/distributed locks | No | Acquire/renew using new identity |
| Short-lived credentials/tokens | Should not keep as sole source | Read/refresh current credentials |
| In-memory queues or running tasks | Depends on semantics | Drain, persist durably, or recover with idempotency |

If multiple Pods restore from the same checkpoint, each Pod starts with a copy of the heap snapshot. Mutable objects in the heap are not synchronized across Pods, yet identical state can produce duplicate behavior. For example, two replicas both holding a local counter `nextOrderId = 100` cannot guarantee unique IDs on their own. Business IDs must be issued by a database, sequence, or central coordination service.

## 16. Protecting Checkpoints and Sensitive Data

Checkpoints may contain heap state, tokens, sessions, user data, and authentication credentials. If stored in an OCI image or object storage, anyone with permission to read the artifact can access the captured data.

Apply these measures:

- Restrict read permissions on checkpoints and manifests using RBAC/ACLs.
- Encrypt artifacts at rest and in transit.
- Do not bake long-lived secrets into a checkpoint if they can be fetched again after restore.
- Verify artifact checksums and signatures before restoring.
- Bind checkpoints to application and runtime versions; do not use unverified-source artifacts.
- Have retention policies and delete old checkpoints when no longer needed.
- Avoid sharing checkpoints across dev, staging, and production environments if they contain different data or credentials.

Checksums only detect modifications relative to a manifest. Signatures on manifests or authenticated artifact sources verify provenance; encryption protects confidentiality. These three mechanisms solve three different problems.

## 17. Example Pod Template with Checkpoint and Identity Volume

The following example illustrates a Deployment using a checkpoint from a mounted directory while providing each Pod its own identity. The exact restore command depends on the CRaC-enabled runtime and project packaging; the `restore-entrypoint` script is an application component that must be implemented.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders-api
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  selector:
    matchLabels:
      app: orders-api
  template:
    metadata:
      labels:
        app: orders-api
    spec:
      serviceAccountName: orders-api
      terminationGracePeriodSeconds: 60
      containers:
        - name: app
          image: registry.example.com/orders-api:2.4.0
          command: ["/opt/app/restore-entrypoint"]
          ports:
            - name: http
              containerPort: 8080
          volumeMounts:
            - name: checkpoint
              mountPath: /opt/checkpoint
              readOnly: true
            - name: pod-identity
              mountPath: /etc/pod-identity
              readOnly: true
          startupProbe:
            httpGet:
              path: /actuator/health/liveness
              port: http
            periodSeconds: 5
            failureThreshold: 60
          readinessProbe:
            httpGet:
              path: /actuator/health/readiness
              port: http
            periodSeconds: 3
            failureThreshold: 2
          lifecycle:
            preStop:
              httpGet:
                path: /internal/quiesce
                port: http
      volumes:
        - name: checkpoint
          persistentVolumeClaim:
            claimName: orders-api-checkpoint
        - name: pod-identity
          downwardAPI:
            items:
              - path: uid
                fieldRef:
                  fieldPath: metadata.uid
              - path: name
                fieldRef:
                  fieldPath: metadata.name
              - path: namespace
                fieldRef:
                  fieldPath: metadata.namespace
              - path: pod-ip
                fieldRef:
                  fieldPath: status.podIP
              - path: node-name
                fieldRef:
                  fieldPath: spec.nodeName
```

This is an architectural example, not a production manifest to use verbatim. A shared PVC across multiple Pods is suitable only if access modes and storage semantics permit multiple readers; the checkpoint payload must be published immutably. The read-only mount example works only when the runtime can restore from a read-only payload. If the runtime needs to write metadata or temporary files, copy the verified artifact to a separate writable working directory keyed by Pod UID. Do not let multiple Pods write to the same checkpoint directory. If each Pod needs to write its own checkpoint, use separate paths/versions per Pod UID or an appropriate snapshot/coordination mechanism.

`maxUnavailable: 0` preserves existing Ready Pods during a rollout at maximum capacity, yet requires sufficient resources to create surge Pods. If the cluster lacks CPU/memory or quota for new Pods, the rollout may stall. Check capacity and node pool autoscalers.

## 18. Restore Entrypoint and Controlled Fallback

The entrypoint should verify the artifact and runtime before requesting a JVM restore. A general flow:

```bash
#!/usr/bin/env bash
set -euo pipefail

CHECKPOINT_DIR="/opt/checkpoint/current"

/opt/app/bin/verify-checkpoint "$CHECKPOINT_DIR"

exec java "-XX:CRaCRestoreFrom=$CHECKPOINT_DIR"
```

This illustrates how to pass options; with CRaC, restoring usually resumes the captured process and is not a normal `-jar` run from scratch. The exact command depends on the runtime, launcher, and how the checkpoint was created. Use the restore command required by your CRaC distribution; do not add `-jar` or application arguments if the runtime does not expect them. The purpose of the example is to emphasize that verification must finish before the JVM reads the checkpoint.

If cold-start fallback is desired when a checkpoint is incompatible, define fallback conditions clearly. For example, `MISSING_FILE`, `HASH_MISMATCH`, or runtime version mismatch errors should mark the Pod unready and emit alerts; a pipeline can deploy a new image with a normal startup path or generate a new checkpoint. Do not edit manifests automatically or skip checksums to force a restore.

## 19. Observing Rolling Updates and Autoscaling

To know whether rollouts truly become faster thanks to CRaC, measure distinct milestones:

- Time when Deployment creates a new Pod.
- Scheduling and image pull duration.
- Volume/checkpoint artifact mount duration.
- Checksum/signature verification duration.
- JVM restore duration.
- `afterRestore` identity and resource refresh duration.
- Time to readiness.
- Time when EndpointSlice updates and first request reaches the Pod.
- Old Pod drain and termination duration.

Metrics can include:

| Metric | Meaning |
|---|---|
| `pod_restore_duration_seconds` | JVM restore duration |
| `pod_restore_failures_total` | Failed restore count by cause |
| `pod_identity_refresh_duration_seconds` | Time to read and apply current identity |
| `pod_ready_duration_seconds` | Time from container start to Ready |
| `pod_drain_duration_seconds` | Quiesce/drain duration before termination |
| `checkpoint_verify_failures_total` | Count of artifacts failing verification |
| `post_restore_reconnect_attempts_total` | Post-restore reconnect attempt count |
| `replicas_restoring` | Number of Pods currently in restore phase |

Use Pod UID as a log/trace attribute to distinguish replicas, yet avoid putting UID or Pod name into metric labels if cardinality is high across workload lifecycles. For metrics, use deployment name, namespace, version, and bounded-cardinality outcomes.

## 20. Common Errors

| Symptom | Possible cause | Resolution |
|---|---|---|
| New Pod Ready but logs show old UID | Identity cached in heap before checkpoint | Read Downward API volume after restore and refresh logging context |
| Multiple replicas share `instanceId` | UUID created before checkpoint then duplicated | Generate a new process run ID after each restore |
| Pod not Ready after restore | Dependency, token, or lease not yet recovered | Inspect `afterRestore`, readiness conditions, and reconnect logs |
| Restore uses old IP or endpoint | Socket, DNS, or config cache retained | Recreate connections and refresh endpoints/discovery |
| Duplicate leader | Leadership state restored from heap across multiple Pods | Acquire a new lease using Pod identity and fencing token |
| Rolling update stalled | New Pod not Ready or insufficient capacity for `maxSurge` | Check events, resource requests, quota, storage, and restore failures |
| HPA scales out yet service remains overloaded | New Pods restore concurrently and all reconnect/warm caches | Limit scale-up, concurrency, and use backoff/jitter |
| Old Pod killed before draining finishes | `terminationGracePeriodSeconds` too short or preStop uncoordinated | Set matching drain deadline and grace period |
| Checkpoint readable yet restore fails | Runtime/OS/architecture incompatible | Attach compatibility metadata and test on target node pool |
| Multiple Pods write to same checkpoint directory | Shared artifact is not immutable | Use read-only/versioned checkpoints or per-Pod directories |

## 21. Recommended Deployment Workflow

A suitable workflow for a stateless API Deployment can be structured as follows:

1. Build an OCI image containing the exact application and CRaC-enabled runtime.
2. Create a checkpoint from an initialized and warmed-up application version in a compatible environment.
3. Generate a manifest, checksum, and signature for the checkpoint; bind the checkpoint to application version, JDK/CRaC version, OS, and architecture.
4. Publish the immutable checkpoint alongside release metadata.
5. Update the Deployment Pod template to use the new image and checkpoint version.
6. New Pods are created, mounting the checkpoint and Downward API identity.
7. The entrypoint verifies the artifact and then restores the JVM.
8. `afterRestore` refreshes Pod identity, process run ID, credentials, sockets, connection pools, discovery registration, and leases.
9. Readiness is reached only when mandatory resources are ready.
10. Deployment shifts traffic to new Pods and then drains old Pods via graceful termination.
11. HPA adjusts replicas based on metrics; scaled-out Pods use the same immutable artifact while initializing their own identities and resources.
12. Monitor restore duration, Ready latency, reconnect load, rollout progress, and verify errors.

If the application has stateful workloads, separate durable state from the checkpoint and clearly define PVC/lease ownership. StatefulSets can preserve ordinals and PVCs, yet do not make Pod UID or network identity immutable.

## 22. Design Checklist

- [ ] OCI images are distinguished from CRaC checkpoint images.
- [ ] Checkpoints are bound to compatible application and runtime versions.
- [ ] Checkpoint artifacts are verified and published immutably before rollout.
- [ ] New Pods report Ready only after successful restore and resource refresh.
- [ ] Readiness, startup, and liveness probes serve distinct purposes.
- [ ] Old Pods stop accepting new work and drain within the termination grace period.
- [ ] Do not assume Kubernetes automatically creates a checkpoint when a Pod terminates.
- [ ] `maxSurge`/`maxUnavailable` match cluster capacity.
- [ ] HPA scale-up is bounded to avoid piling load onto storage/dependencies.
- [ ] Pod UID, IP, node name, and process run ID are refreshed per Pod/restore.
- [ ] Current identity is read from a Downward API volume or a reliable runtime source.
- [ ] Tokens, certificates, sockets, pools, subscriptions, and DNS are refreshed when needed.
- [ ] Leader leases/distributed locks are re-acquired using new identity and fencing.
- [ ] Shared checkpoint artifacts are immutable; each Pod has a separate working copy if the runtime needs to write during restore.
- [ ] Stateful workloads have a clear PVC and single-writer strategy.
- [ ] Metrics exist for restore, identity refresh, readiness, drain, and reconnect.
- [ ] Rolling updates, concurrent scale-out, Pod replacement, and restore failures have been tested.
