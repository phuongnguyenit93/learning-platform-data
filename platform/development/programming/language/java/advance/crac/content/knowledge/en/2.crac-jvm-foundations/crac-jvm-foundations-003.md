# Profiling Information and the Impact of JIT on Post-Restore Performance

When a Java application is restored from a checkpoint using CRaC (Coordinated Restore at Checkpoint), the process resumes from the saved state instead of starting a new JVM from scratch. Therefore, post-restore performance depends on the state the JVM had accumulated before the checkpoint. An important part of that state is profiling data and machine code generated by the JIT compiler.

This explains why two checkpoints of the same application can yield different performance results: a checkpoint created immediately after application startup typically contains little warmed-up JIT state; a checkpoint created after the application has processed a representative workload can retain many compiled methods and useful profiling data.

## 1. What State Is the JVM Holding at Checkpoint Time?

CRaC coordinates with the JVM to bring the process to a checkpointable state, handle resources requiring preparation, and then save the process state image according to the mechanism supported by the platform. Upon successful restore, the process continues from that state image. Performance-critical components include:

| Component | Role | Significance after restore |
| --- | --- | --- |
| Java heap | Stores objects, in-memory caches, application data, and runtime structures | Existing objects can continue to be used; the application does not have to recreate all heap state as on a cold start. |
| Class metadata and class-loading state | Stores loaded class information, method metadata, constant pools, and related data | Classes already loaded before checkpoint normally do not need to be reloaded from scratch. Lazily loaded classes can still incur work after restore. |
| Thread stacks and execution state | Stores execution contexts of threads at a valid checkpoint point | The JVM can continue from the saved state according to CRaC and platform rules. Thread-bound resources must still follow the checkpoint/restore lifecycle. |
| JIT code cache | Contains native machine code generated by the JIT compiler for compiled methods | If the JVM build and CRaC platform support restoring this memory region, compiled machine code can be used immediately after restore. |
| Profiling data and runtime counters | Records method hotness, loops, object types at call sites, and branch behavior | The JIT can continue using accumulated data to decide which methods need compiling or re-optimizing. |

The JIT code cache is the memory area holding machine code executed directly on the CPU. It differs from bytecode in `.class` files: bytecode is the JVM's input, whereas JIT code is compilation output dependent on the JVM and CPU architecture. Profiling data is also important because the JIT uses runtime-observed data to select optimization strategies.

In compatible HotSpot CRaC builds, the code cache and profiling data are part of the process memory state and may be retained in the checkpoint image. However, preserving all JIT code should not be treated as a universal guarantee across every JDK build, operating system, and CRaC implementation. Verify behavior on the exact JVM build, operating system, and CPU architecture being deployed. Compiled machine code is also suitable only for compatible CPU environments; restoring to an environment with a different instruction set or hardware characteristics may not be supported.

A checkpoint does not save physical CPU state such as L1/L2/L3 caches, branch predictors, or the TLB. These hardware states will be rebuilt as the process continues running. Similarly, do not assume external resources such as database connections, sockets, or file handles can be used as-is; the application must manage them via CRaC lifecycle hooks.

## 2. How Does the JIT Compiler Generate Executable Code?

The JVM can execute bytecode using the interpreter before deciding to compile a method into machine code. With HotSpot tiered compilation enabled, the process typically progresses through several tiers:

1. **Interpreter:** executes bytecode and collects information about program behavior. Infrequently called methods usually stay at this stage.
2. **C1 compiler:** compiles faster, typically used at intermediate optimization levels. Certain C1 levels focus on gathering profiling data.
3. **C2 compiler:** performs deeper optimizations for methods identified as hot, based on collected profiling data.

The JVM does not merely count method invocations. It also observes loops, object types frequently appearing at a call site, conditional branches, and other runtime behaviors. When a loop becomes hot, the JVM can use On-Stack Replacement (OSR) to switch ongoing loop execution into compiled code without waiting for the method to be invoked again from the beginning.

Profiling helps the JIT make informed assumptions. For example, if a call site consistently receives objects of the same type, the compiler can optimize the execution path for that type and place a guard to check the assumption. If the workload changes so the assumption no longer holds, the JVM can deoptimize the optimized code, fall back to a less optimized execution level, update the profile, and recompile when needed.

Thus, JIT state is not just the answer to "which methods have been compiled?". It also includes compilation levels, profiling data, optimization assumptions, and code cache state. Together, these factors determine how fast the JVM will execute after restore.

## 3. Why Does JIT Affect Post-Restore Performance?

### 3.1. Checkpoint Created While the Application Is Still Cold

If a checkpoint is created right after the application finishes initialization, most business methods may not yet be hot enough for JIT compilation. After restore, the application can accept requests sooner than a normal JVM startup because much of the application state is already saved, yet unwarmed methods still have to go through the interpreter or initial compilation tiers.

As traffic increases, the JVM continues gathering profiling data and compiling hot methods. During this phase, the first request or initial group of requests can be slower than steady-state requests. CPU usage may also rise as compiler threads work concurrently with request-handling threads.

### 3.2. Checkpoint Created After a Representative Workload Has Warmed the Application

If the application has processed representative business flows before checkpoint, hot methods may already be compiled and the code cache may contain the corresponding machine code. When that state is restored successfully, these methods have the opportunity to continue running in compiled code right from the very first requests.

Retained profiling data also saves the JVM from having to re-observe all behavior from scratch before making certain compilation decisions. This is why a post-warm-up checkpoint can reduce initial latency and shorten the time to reach steady throughput.

However, the benefit applies only to the portion of the workload that was warmed up and the JIT state actually retained. A simple readiness endpoint may only check that the application is alive without traversing key business methods, data queries, serialization, or template rendering. Calling a readiness endpoint many times therefore does not mean the entire application has been warmed up.

### 3.3. Post-Restore Workload Differs From Pre-Checkpoint Workload

The JIT optimizes based on observed behavior. If warm-up runs only one kind of request while production after restore receives many other kinds of requests, the pre-checkpoint profile may not represent the real workload. The JVM may need to update profiles, deoptimize certain methods, or recompile to adapt.

For example, a method before checkpoint almost always receives `ArrayList`, but after restore frequently receives multiple `List` implementations. Code optimized under the narrow type assumption may no longer perform as efficiently as before. Guards can detect the mismatch and trigger deoptimization; the JVM can then compile another version based on the new data.

### 3.4. Code Cache and Compilation Queues Have Limits

The code cache has finite capacity. If an application has many hot methods or produces many compiled code versions, the code cache can experience pressure. The JVM may then have to sweep old code, halt some compilation activity, or fail to emit additional code as desired. A checkpoint created after a long warm-up is not automatically better if warm-up generates too much low-value code.

Compilation queues and the number of compiler threads also affect when new code becomes ready. Sending many warm-up requests over a short period does not prove all necessary methods have finished compiling. Observe compilation logs and actual performance before deciding when to checkpoint.

### 3.5. The Post-Restore Execution Environment Can Alter Outcomes

Even when the code cache is preserved, performance still depends on CPU, container resource limits, machine load, GC, application caches, network connections, and external services. CPU caches and branch predictors must warm up again; resource connections may have to reopen via restore hooks; external data may have changed.

Therefore, if requests are slow after restore, do not immediately conclude that JIT state was lost. Separate the effects of JIT from class loading, GC, I/O, resource reconnection, CPU throttling, and external cache state.

## 4. Comparing the Two Checkpoint Creation Strategies

| Criterion | Early checkpoint, minimal warm-up | Checkpoint after representative warm-up |
| --- | --- | --- |
| Checkpoint preparation time | Usually shorter | Longer due to running warm-up workload and waiting for JVM stabilization |
| JIT state | Many methods may still be in the interpreter or lower compilation tiers | Many critical methods may already be compiled with useful profiles |
| Requests right after restore | May exhibit a gradual ramp-up phase as JIT continues working | Chance to achieve good performance earlier for warmed paths |
| Post-restore CPU | May increase due to ongoing profiling and compilation | May reduce initial compilation work; may still compile if new workloads appear |
| Main risk | Post-restore warm-up increases initial latency | Unrepresentative or overly long warm-up can waste resources and build unsuitable profiles |

There is no single best strategy for every application. If the primary goal is reducing time to bring a service to readiness, an early checkpoint may fit. If the goal is lowering first-request latency after restore, a checkpoint after representative warm-up is usually more worth testing. The decision should be based on SLOs and measurements from realistic workloads.

## 5. Designing Pre-Checkpoint Warm-Up

Warm-up should exercise execution paths meaningful to production traffic. For a Java service, consider the following groups of operations:

- Invoke key business endpoints with representative data, including both success paths and common branches.
- Execute serialization/deserialization, object mapping, validation, and data-processing flows with significant CPU cost.
- Run common queries or data-access operations if they need to warm application caches or prepare runtime state. Connection resources must still follow the CRaC lifecycle.
- Exercise flows creating templates, expressions, regexes, or lazily initialized processing structures if they lie on critical request paths.
- Use data distributions and request ratios close to production so profiling data reflects expected post-restore behavior.

Warm-up must avoid creating unintended side effects. If a business flow writes data, sends notifications, or creates transactions, use test data and appropriate isolation mechanisms. Do not invoke a production flow just for JIT compilation if that operation alters real data.

A practical workflow may include these steps:

1. Start the application and complete necessary state preparation steps.
2. Run a representative warm-up request suite, with volume and concurrency close to the initial post-restore traffic phase.
3. Observe JIT compilation to determine whether critical methods are still actively being compiled.
4. Measure latency and throughput over a stable interval. Do not choose the checkpoint moment solely by warm-up invocation count.
5. Bring the application to a checkpoint-safe state, handle resources per the application's CRaC guidelines, and create the checkpoint.
6. Restore repeatedly in a compatible environment and re-measure the same workload to confirm benefits are repeatable.

There is no need to try compiling every method in the application. Rarely executed methods may not affect SLOs. Overly broad or overly long warm-up increases preparation time, CPU usage, and may enlarge the state needing to be saved without commensurate benefit.

## 6. Observing JIT State

HotSpot tools can be used to see when the JVM compiles methods and how the code cache is being used. Depending on the JDK build, some options or diagnostic commands may vary; verify support on the exact running runtime.

### Monitoring Compilation Logs

Unified logging can be enabled when launching the JVM:

```bash
java -Xlog:jit+compilation=debug -jar application.jar
```

Logs help identify which methods are compiled and when compilation occurs. When more detail is needed on HotSpot, you can use:

```bash
java -XX:+PrintCompilation -jar application.jar
```

Log lines typically show the compile ID, compilation level, and method name. When comparing pre-checkpoint and post-restore, focus on methods on critical processing paths. If those methods were compiled before checkpoint and do not experience a large wave of recompilation after restore, that is an indication that JIT state was retained; still combine this with latency and throughput measurements.

### Inspecting the Code Cache

On HotSpot builds supporting the corresponding diagnostic command, run:

```bash
jcmd <pid> Compiler.codecache
```

The output shows code cache capacity and usage at the time of inspection. You can compare before checkpoint and after restore to spot signs of major code cache changes or pressure. If the command is unavailable on your runtime build, check the command list with `jcmd <pid> help` and choose an equivalent tool supported by that JDK build.

### Using Java Flight Recorder

Java Flight Recorder (JFR) can record compilation-related events alongside CPU, GC, class loading, and thread events. With appropriate events enabled, JFR helps determine whether post-restore latency coincides with a period of heavy JIT compilation. This is a useful way to distinguish compiler work from other causes such as GC pauses or slow I/O.

Do not rely solely on a single metric such as compiled method count. A method may be compiled yet not lie on a critical request path; conversely, some uncompiled methods may remain negligible for overall performance.

## 7. Measuring to Determine Real Impact

A useful test should separate restore time, first-request time, post-restore warm-up phase, and steady-state performance. Three cases can be designed:

| Case | Preparation method | Question to answer |
| --- | --- | --- |
| Fresh JVM startup | Start application normally and send traffic | What is the baseline without checkpoint/restore? |
| Early CRaC checkpoint | Create checkpoint right after application finishes initialization, without business warm-up | How much readiness time does CRaC save, and how much JIT cost remains after restore? |
| Warmed CRaC checkpoint | Run representative workload, observe compilation, then create checkpoint | Does preserving JIT state improve first-request latency and time to steady performance? |

In each case, record:

- Time from starting restore until the application successfully accepts requests.
- p50, p95, and p99 latency of the initial request batch, during transition, and once stabilized.
- Throughput and CPU usage across the same intervals.
- Count and timing of JIT compilations, and at which tiers critical methods are compiled.
- Code cache status, GC, class loading, and external resource recovery time.

Keep the JDK version, JVM flags, CPU or machine type, container limits, input data, concurrency, and dependent service configurations identical across measurement runs. Repeat multiple times to avoid drawing conclusions from a single restore with abnormal background load. If possible, run the same post-restore workload on the same host and compare per time window.

In particular, do not lump restore duration together with first-request latency. Restore can be fast while the first request remains slow due to JIT, class initialization, or resource reconnection. Conversely, JIT state may be preserved while requests remain slow because CPU is throttled or external services respond slowly.

## 8. How to Interpret Common Symptoms

| Observed symptom | Potentially related JIT cause | What to inspect further |
| --- | --- | --- |
| First requests slow, subsequent requests get faster | Methods were not compiled before checkpoint; JIT continues warming up after restore | Compilation logs, hot methods, and compiler thread CPU |
| Many compilation events after restore | Checkpoint was created before warm-up finished, new workload appeared, or old code was deoptimized | Compare methods and compilation levels pre/post-restore; check whether workload changed |
| Methods already compiled yet latency remains high | JIT is not the main bottleneck, or pre-checkpoint profile no longer fits | GC, I/O, resource reconnection, CPU throttling, caches, and dependent services |
| Code cache nearly full or signs unable to compile more | Code cache pressure may restrict further optimization | Code cache statistics, compilation logs, and JVM configuration |
| Only certain endpoints are slow after restore | Warm-up did not traverse those endpoints' paths or endpoints use different data/object types | Trace endpoint methods, class loading, and call-site profiles |

The symptoms above are only investigation leads. To conclude that JIT is the cause, correlate compilation logs with request measurements and rule out other runtime factors.

## 9. Misconceptions to Avoid

**"CRaC completely eliminates JIT warm-up."** Incorrect. CRaC can restore existing JIT state, yet methods that were not hot before checkpoint may still require profiling and compilation after restore. Results also depend on the JVM build and platform.

**"After restore you must re-warm the entire application."** Not necessarily. If the code cache and profiling data are validly restored, many already hot methods can continue using pre-checkpoint state. Additional warm-up is needed only when the workload changes, optimization assumptions shift, or runtime state indicates it is required.

**"Once warmed up, every request after restore is fast."** Incorrect. Warm-up represents only the paths and data distributions that were executed. Rarely used endpoints, uncommon branches, or new data types can still incur cost after restore.

**"A checkpoint saves CPU cache state as well."** Incorrect. The checkpoint image saves process state per platform mechanisms; hardware caches, branch predictors, and TLBs are not preserved process memory state.

**"The longer the warm-up, the better the checkpoint."** Incorrect. Warm-up must represent the workload and produce measurable benefits. Overly long warm-up wastes CPU, prolongs preparation, and can build profiles unsuited to real traffic.

## 10. Conclusion

JIT performance after CRaC restore depends primarily on the compilation and profiling state existing at checkpoint time, the JVM build's ability to retain that state, and how closely the pre-checkpoint workload matches the post-restore workload. Early checkpoints typically reduce application initialization overhead but may leave JIT warm-up costs for the post-restore phase. Checkpoints after representative warm-up can help critical requests achieve good performance sooner, provided JIT code is validly restored and actual workloads align.

Therefore, choose warm-up based on SLOs, observe compilation and code cache behavior on the exact CRaC runtime in use, and verify with separate measurements for first requests and steady state. Real measurements reveal how much improvement comes from JIT, from restored application state, or from other runtime factors.
