# TLS Protects Confidentiality, Integrity, and Peer Authentication

## Lesson Objectives

When an application uses `https://` or an `SSLSocket` connection, what matters is not merely that "the data is encrypted." TLS (Transport Layer Security) is designed to protect **confidentiality**, **integrity**, and **peer authentication** over a communication channel; however, the level of authentication achieved **depends on identity verification configuration and trust policies**.

After this lesson, you will be able to:

- Distinguish the three properties **confidentiality**, **integrity**, and **authentication**; recognize the limits that TLS does **not** guarantee.
- Explain the high-level flow of the **TLS 1.3 handshake**, the roles of ephemeral key exchange, X.509 certificates, `CertificateVerify`, `Finished`, and symmetric encryption keys.
- Understand the difference between **standard server authentication** and **mutual authentication (mTLS)**; avoid confusing a valid certificate with business-level authorization for a peer.
- Know why you must verify the **certificate chain, hostname/SAN, and trust anchor**, and never use `trust-all` or disable hostname verification.
- Identify the roles of `KeyStore`, `TrustStore`, `SSLContext`, `SSLSocket`, and `SSLParameters` in Java 17+.
- Run a **TLS 1.3 client–server loopback** yourself with an intentionally trusted test certificate, and observe errors when trust or hostname is wrong.
- Understand TLS termination, forward secrecy, TLS resumption/0-RTT, metadata privacy limits, and common implementation mistakes.

**Scope:** TLS over TCP connections, illustrated with TLS 1.3 and Java Secure Socket Extension (JSSE). Local examples do not require Internet access and do **not** disable certificate validation. This content does not treat TLS as a user authorization mechanism or protection for data after it has left the TLS endpoint.

## 1. Where Does TLS Sit in Network Communication?

A typical HTTPS connection follows these layers:

~~~text
Browser / Java HTTP client                  HTTPS server
  HTTP request/response                       HTTP application
           │                                       ▲
           ▼                                       │
      TLS records  ─────── encrypt/authenticate ──► TLS records
           │                                       ▲
           ▼                                       │
          TCP ────────────────────────────────────► TCP
           │                                       ▲
           ▼                                       │
       IP / network ──────────────────────────────► IP / network
~~~

- **TCP** provides an ordered byte stream; it does not guarantee that bytes remain confidential or unmodified by a man-in-the-middle.
- **TLS** establishes an authenticated encrypted session layered **on top of** TCP, so application data is protected **in transit between two TLS endpoints**.
- **HTTPS** is HTTP transported over TLS. The URL `https://example.org` tells the client to establish an appropriate TLS connection and verify the server identity `example.org`.
- **The application** remains responsible for login, authorization, content validation, and handling input and decrypted data.

TLS does not turn TCP into a message-framed protocol. Even when communicating over `SSLSocket`, Java still reads a **byte stream**; a single `InputStream.read()` call does not guarantee receiving exactly one business message. You must define framing such as newline, length-prefix, or the HTTP protocol.

TLS is also **not a default kind of "special port"**: port 443 is the convention for HTTPS, but TLS can operate on other ports when both sides agree. Likewise, not every byte on port 443 is necessarily valid HTTPS.

## 2. Three Core Security Properties

| Property | Threat to defend against | How does TLS help? | What not to infer |
|---|---|---|---|
| **Confidentiality** | Eavesdroppers observing exchanged content | Negotiating session keys and encrypting application-data records | Hiding IP addresses, transmission timing, all metadata, or data at rest on a machine |
| **Integrity** | Man-in-the-middle modifying/injecting data undetected | Authenticated encryption (AEAD), record verification; cryptographic verification of handshake transcript | That source data was originally truthful, free of business bugs, or that the connection cannot drop |
| **Authentication** | Client being directed to an impostor server or wrong peer identity | Certificates, proof of key possession, and name/trust-chain verification; or configured authentication mechanism | That the server automatically knows the client's identity, that a certificate proves business trustworthiness, or that authorization is granted |

### Confidentiality

If an attacker only **observes the network** and does not possess the session keys, application data content is protected by proper TLS encryption. For example, a request containing a cookie, token, or JSON payload does not appear as plaintext inside the application-data portion of TLS records on the wire.

However, TLS **does not hide all metadata**. Source/destination IP addresses, timing, and data volume are typically still observable at outer layers. In many deployments, the hostname in SNI inside ClientHello is visible unless a mechanism like ECH is deployed. TLS does not hide the URL/path from the **server receiving the request**, nor does it protect plaintext in logs, RAM, disk, or at a proxy that has terminated TLS.

### Integrity

If an intermediary modifies the ciphertext, the authentication tag of the AEAD-encrypted record will not match, and the receiver cannot accept that record as valid data. The handshake also verifies that key parameters were not silently altered.

This is **integrity within the TLS channel**, not a guarantee that the application will receive all data. An on-path attacker can still **block, drop, or delay** packets, or tear down the connection. Both sides must handle EOF, timeouts, and detect incomplete responses according to the application protocol.

### Authentication

In standard HTTPS, the **client authenticates the server** via certificate and hostname. The server may **not authenticate the client at the TLS layer**; the client may log in using a token, cookie, password, or another application-layer mechanism. For the server to authenticate the client at the TLS layer, mTLS (client certificate and requirement/verification configuration) is needed.

**Key takeaway:** "encryption succeeded" is not enough to trust a peer. An encrypted channel to the **wrong server** still exposes data to that server; therefore, identity verification must be part of channel establishment.

## 3. How Does TLS 1.3 Establish a Channel?

A simplified **TLS 1.3 full handshake with a server certificate**:

~~~text
Client                                       Server
  │                                            │
  ├─ ClientHello ──────────────────────────────►│
  │   proposed versions/algorithms, key_share, │
  │   SNI/ALPN when used                       │
  │                                            │
  │◄───────────────────────────── ServerHello ─┤
  │   selected parameters, key_share           │
  │      (both sides have key material)        │
  │◄────────── EncryptedExtensions ────────────┤
  │◄────────── Certificate ────────────────────┤
  │◄────────── CertificateVerify ──────────────┤
  │◄────────── Finished ───────────────────────┤
  │                                            │
  │  verify chain + hostname and transcript    │
  │                                            │
  ├─ Finished ────────────────────────────────►│
  │                                            │
  ╞══════════ TLS application data ═══════════╡
  │  encrypted/authenticated application data  │
~~~

The flow above describes **one common full handshake configuration**; it does not apply verbatim to every PSK resumption, mTLS, or 0-RTT session.

1. **ClientHello:** the client proposes protocol versions, cipher suites, and key exchange parameters, and may include SNI to select a virtual host. Not the entire handshake is hidden from the very first byte.
2. **ServerHello:** the server selects parameters and sends an appropriate ephemeral public key. With `(EC)DHE`-style key exchange, both sides derive a shared secret without transmitting that secret in plaintext.
3. **Key schedule:** TLS 1.3 uses a key derivation mechanism (including HKDF) to generate separate handshake and application traffic keys. The keys used to encrypt regular traffic are **symmetric keys**.
4. **Certificate:** the server provides its certificate/certificate chain so the client has data to verify the public key and expected identity.
5. **CertificateVerify:** in a full certificate handshake, the server proves possession of the private key corresponding to the certificate by signing the transcript contents according to protocol rules.
6. **Finished:** both sides cryptographically verify that the handshake transcript and derived secrets match, preventing many kinds of handshake tampering.
7. **Application data:** after successful negotiation and verification, application data is sent in encrypted and authenticated TLS records.

**Do not** interpret TLS 1.3 as "the client takes the RSA public key from the certificate and encrypts all HTTP data with RSA." In modern TLS 1.3, record encryption uses **symmetric AEAD**; the certificate/private key primarily serves **authentication** in a full certificate handshake. Ephemeral keys for key exchange and traffic keys serve a different role from the private key that signs/matches the certificate.

### Cipher Suites and Key Exchange Mechanisms

In TLS 1.3, a cipher suite name such as `TLS_AES_128_GCM_SHA256` specifies the AEAD algorithm and the hash used in the key schedule; key exchange groups and signature algorithms are negotiated in other extensions. For example, **ECDHE** can be used to establish the shared secret, **RSA or ECDSA** for signing certificates/`CertificateVerify`, and **AES-GCM or ChaCha20-Poly1305** to protect records.

You should not apply TLS 1.2 cipher suite naming conventions directly to TLS 1.3. Normal Java applications should let JSSE choose supported/permitted algorithms according to security policy, rather than hard-coding an incompatible cipher suite.

## 4. Confidentiality: TLS Records and Session Keys

After the handshake, the sender:
1. Takes the application bytes.
2. Constructs the appropriate TLS record and derives the nonce/sequence counter according to protocol rules.
3. Encrypts with **AEAD** using the appropriate traffic key.
4. Transmits the ciphertext record and authentication tag.

The receiver verifies the authentication tag before returning plaintext to the application layer. Invalid tags result in a protocol error rather than "attempting to decrypt modified data."

TLS records and application messages are **not synonymous**:
- One application message may span multiple TLS records.
- One TLS record may contain data that the application still needs to assemble into frames.
- `SSLSocket.getInputStream().read(...)` only returns decrypted bytes; it does not promise to return exact application message boundaries.
- Network packet/fragmentation limits still exist; TLS only hides the encrypted content from the application protocol.

### Forward Secrecy Requires Understanding the Conditions

With a TLS 1.3 full handshake using **ephemeral (EC)DHE**, traffic keys do not derive solely from the server's long-term private key. Therefore, **later compromise of the certificate's private key** does not automatically allow an attacker to decrypt previously recorded traffic, **provided** the ephemeral/session secrets were not compromised. That property is called *forward secrecy*.

However, **do not** state "every TLS 1.3 mode and every byte is always forward secret":
- TLS 1.3 has a **PSK-only** mode without (EC)DHE, which does not provide the same forward secrecy property for that session's traffic.
- **0-RTT early data** has weaker security properties and does not provide forward secrecy guarantees in the usual way.
- An attacker who compromises the endpoint itself, the running session, or the traffic keys can read plaintext/data even if long-term keys remain safe.
- TLS does not replace proper key erasure, limiting sensitive logging, and host security.

## 5. Integrity: Authenticated Records, Not "The Network Cannot Fail"

TLS 1.3 uses AEAD, so **encryption and integrity checking** are bound together. An eavesdropper cannot forge valid modified content without the appropriate traffic key. The record sequence also uses nonce/sequence-related state to prevent reordering records within the same connection per TLS structure.

The handshake also protects the integrity of parameter negotiation through authenticated messages, especially `Finished`. Thus, handshake-tampering attacks that try to force mismatched choices can be detected in a compliant flow.

**Important limitations:**

- TLS does not guarantee that an HTTP response is business-accurate, free of false data sent by the server itself, or that the original data source was not altered before entering TLS.
- TLS does not guarantee **availability**: packets can be dropped and connections can be reset, preventing the application from receiving a complete response.
- Standard TLS does not automatically prevent **replay of an application action**, such as a payment retried twice by a client. The application needs an idempotency key/transaction ID when appropriate.
- The protocol/application must know how to detect **truncation** or mid-stream connection closure, rather than treating an abrupt stream end as complete data.
- TLS protects each **TLS hop**; when a reverse proxy decrypts and forwards a plaintext request to a backend, the outer TLS at the proxy no longer protects the internal hop.

For example, if a response consists of a 10 MB file but the peer disconnects after 2 MB, the 2 MB received earlier may have valid TLS integrity; the application must still check **Content-Length, content hash/signature**, or protocol semantics to know the file is incomplete.

## 6. Authentication: How Does the Client Know Which Server It Is Talking To?

Secure server authentication requires both **trust** and **identity**.

### X.509 Certificates and Trust Chains

A server certificate typically contains:
- **Subject** and related identifying information.
- **Subject Alternative Name (SAN)**: the DNS names or IP addresses to which the certificate applies.
- The server's **public key** and signature details, validity period, and key usage/extended key usage.
- Issuer information to build a **certificate chain** from the leaf to intermediate CAs and a trust anchor configured on the client.

The client must use a trusted **TrustManager** to validate the certificate path against policy, validity period, intended usage, and related constraints. A truststore typically stores **trusted certificates/CAs**, not the server's private key.

Passing "valid certificate chain" is **not enough** if the client does not verify the **hostname**. For example, if the client requests `api.example.org` and the server presents a valid certificate for `shop.example.org`, it must not be accepted merely because both hosts use certificates from a valid public CA.

### SAN and Hostname

The identity verifier must match the name **the client intended to connect to** against the certificate's SAN according to appropriate rules. For modern HTTPS, SAN is central; do not write naive checks such as `certificate.getSubjectDN().toString().contains(host)`.

- The URL `https://api.example.org` expects identity `api.example.org`.
- Connecting to an IP literal requires a corresponding IP SAN; having a DNS SAN does not automatically cover every IP.
- For IDNs, hostnames must be handled consistently according to IDNA rules when Unicode domain names are present.
- SNI helps the server select a certificate by hostname when hosting multiple virtual hosts, but **SNI is not an authentication step**: the client must still verify the certificate and hostname.
- A valid certificate does not prove the peer is authorized to perform a business operation or that a website is "safe in every respect."

In Java, when using **raw `SSLSocket`** directly, do not assume the library automatically checks hostnames like an HTTPS client does. You must set `SSLParameters.setEndpointIdentificationAlgorithm("HTTPS")` on the client socket, or use a higher-level API such as `java.net.http.HttpClient` with proper TLS/HTTPS defaults. **Never install a `HostnameVerifier` that always returns true**, and never replace the TrustManager with a trust-all implementation to bypass handshake errors.

### Does the Server Authenticate the Client?

**One-way TLS:** the client authenticates the server, while the server does not necessarily authenticate the client at the TLS layer. On typical HTTPS websites, the server identifies the user via login, session cookie, bearer token, or application-layer authentication.

**mTLS (mutual TLS):** the server **requires** a client certificate and verifies it. With JSSE `SSLServerSocket` or `SSLEngine`, the server typically needs `setNeedClientAuth(true)` and a TrustManager/truststore containing trusted client CAs or certificates. The client must have an appropriate private key/certificate (KeyManager) and send it when requested.

mTLS answers "the peer possesses the key bound to a certificate trusted by policy"—it **does not automatically determine access permissions**. Map the certificate identity to a principal/role/service account in the application and perform authorization separately. Do not use certificates with invalid client-auth attributes or skip certificate path validation.

## 7. JSSE in Java: KeyStore, TrustStore, and SSLContext

Java Secure Socket Extension (JSSE) provides the core classes:

| API / Concept | Responsibility |
|---|---|
| `KeyStore` | Storage for key/certificate entries; commonly PKCS12 |
| `KeyManagerFactory` | Creates a KeyManager from a keystore to present certificates and use local private keys |
| `TrustManagerFactory` | Creates a TrustManager from a truststore to verify peer certificate chains |
| `SSLContext` | Bundles key/trust managers, protocol provider, and randomness configuration for TLS connections |
| `SSLServerSocket` / `SSLSocket` | TCP sockets with TLS handshake and record protocol |
| `SSLParameters` | Configures endpoint identification, protocols, SNI/ALPN, client-auth, and related policies |
| `SSLSession` | Negotiated session information, such as protocol, cipher suite, and peer principal when available |
| `SSLEngine` | Transport-independent TLS state machine, useful in frameworks/NIO |

A **server keystore** holds the server's own private key and certificate. A **client truststore** holds the trust anchors/certificates the client accepts when verifying the server. They are not the same configuration and their roles are not interchangeable.

For an HTTPS client using standard `HttpClient`:
- You typically **do not need** to construct an `SSLContext` manually, because Java uses the environment's default truststore/provider.
- Do not disable hostname verification just to test against a mismatched certificate.
- If a private enterprise CA is required, add the permitted CA to an appropriate truststore; scope trust to the application if needed.
- Only programs requiring mTLS need to configure a client keystore/certificate.
- Never log private keys, keystore passwords, bearer tokens, or sensitive plaintext when enabling TLS debugging.

**The demo below** intentionally creates a client truststore that trusts only the **localhost server's self-signed certificate**, rather than disabling verification. This is a test-environment trust anchor, **not** how certificates are issued for public Internet systems.

## 8. Runnable Java 17+ TLS 1.3 Loopback Example Without Internet

We generate a test keypair/certificate for `localhost`; the server keeps its private key in `server.p12`, and the client stores only the trusted certificate in `client-trust.p12`. Both sides open TLS 1.3 over loopback, the client verifies the **certificate chain/trust anchor and hostname**, sends a `PING` line, and receives `PONG`.

~~~text
server.p12 (private key + certificate)
             │
             ▼
      SSLServerSocket
             │    TLS 1.3 handshake
             ▼
         SSLSocket ◄────────────── client SSLContext
                                       │
                                       ▼
                         client-trust.p12 (trusts only test certificate)
                         + HTTPS endpoint identity = localhost
~~~

### 8.1. Generating a Test Key/Certificate with `keytool`

Run the commands below in a **separate practice directory**, outside the repository, and do not commit generated files to Git. Requires a JDK with `keytool` and `javac`.

~~~bash
keytool -genkeypair -alias server -keyalg RSA -keysize 2048 -keystore server.p12 -storetype PKCS12 -storepass changeit -keypass changeit -validity 2 -dname "CN=localhost" -ext "SAN=DNS:localhost,IP:127.0.0.1" -noprompt

keytool -exportcert -rfc -alias server -keystore server.p12 -storepass changeit -file server.crt

keytool -importcert -noprompt -alias server -file server.crt -keystore client-trust.p12 -storetype PKCS12 -storepass changeit
~~~

Explanation:

1. `-genkeypair` creates an RSA keypair and a self-signed certificate **for testing only**, with SAN DNS `localhost` and IP `127.0.0.1`; validity is only two days.
2. `-exportcert` exports the **public certificate**, not the private key.
3. `-importcert` imports the certificate into the **client truststore**. The client has only the certificate's public data, not the server's private key.
4. The password `changeit` is written explicitly so the exercise runs; it is **completely unsuitable for production use**. Do not put passwords in CLI history, source code, or real logs; production requires secure secret management, standard certificate issuance, and rotation.

### 8.2. Complete `TlsLoopbackDemo.java` File

~~~java
import java.io.*;
import java.net.*;
import java.nio.charset.StandardCharsets;
import java.nio.file.*;
import java.security.KeyStore;
import java.util.concurrent.*;
import javax.net.ssl.*;

public class TlsLoopbackDemo {
    private static final char[] PASSWORD = "changeit".toCharArray();

    static SSLContext serverContext(Path keyStoreFile) throws Exception {
        KeyStore store = KeyStore.getInstance("PKCS12");
        try (InputStream in = Files.newInputStream(keyStoreFile)) {
            store.load(in, PASSWORD);
        }
        KeyManagerFactory factory = KeyManagerFactory.getInstance(
            KeyManagerFactory.getDefaultAlgorithm());
        factory.init(store, PASSWORD);

        SSLContext context = SSLContext.getInstance("TLS");
        context.init(factory.getKeyManagers(), null, null);
        return context;
    }

    static SSLContext clientContext(Path trustStoreFile) throws Exception {
        KeyStore store = KeyStore.getInstance("PKCS12");
        try (InputStream in = Files.newInputStream(trustStoreFile)) {
            store.load(in, PASSWORD);
        }
        TrustManagerFactory factory = TrustManagerFactory.getInstance(
            TrustManagerFactory.getDefaultAlgorithm());
        factory.init(store);

        SSLContext context = SSLContext.getInstance("TLS");
        context.init(null, factory.getTrustManagers(), null);
        return context;
    }

    public static void main(String[] args) throws Exception {
        if (args.length != 2) {
            System.out.println(
                "Usage: java TlsLoopbackDemo <server.p12> <client-trust.p12>");
            return;
        }

        SSLContext serverTls = serverContext(Path.of(args[0]));
        SSLContext clientTls = clientContext(Path.of(args[1]));

        ExecutorService workers = Executors.newSingleThreadExecutor();
        try (SSLServerSocket server = (SSLServerSocket)
                serverTls.getServerSocketFactory().createServerSocket(
                    0, 10, InetAddress.getLoopbackAddress())) {
            server.setEnabledProtocols(new String[] {"TLSv1.3"});

            Future<?> serverTask = workers.submit(() -> {
                try (SSLSocket peer = (SSLSocket) server.accept()) {
                    peer.setSoTimeout(5_000);
                    peer.startHandshake();

                    BufferedReader in = new BufferedReader(
                        new InputStreamReader(peer.getInputStream(),
                            StandardCharsets.UTF_8));
                    OutputStream out = peer.getOutputStream();
                    if (!"PING".equals(in.readLine())) {
                        throw new IOException("Unexpected request");
                    }
                    out.write("PONG\n".getBytes(StandardCharsets.UTF_8));
                    out.flush();
                } catch (IOException e) {
                    throw new UncheckedIOException(e);
                }
            });

            try (SSLSocket client = (SSLSocket)
                    clientTls.getSocketFactory().createSocket(
                        "localhost", server.getLocalPort())) {
                client.setSoTimeout(5_000);
                client.setEnabledProtocols(new String[] {"TLSv1.3"});

                SSLParameters parameters = client.getSSLParameters();
                parameters.setEndpointIdentificationAlgorithm("HTTPS");
                client.setSSLParameters(parameters);
                client.startHandshake();

                if (!"TLSv1.3".equals(client.getSession().getProtocol())) {
                    throw new SSLException("Unexpected TLS version");
                }
                System.out.println("TLS 1.3 handshake: OK");

                OutputStream out = client.getOutputStream();
                out.write("PING\n".getBytes(StandardCharsets.UTF_8));
                out.flush();
                BufferedReader in = new BufferedReader(
                    new InputStreamReader(client.getInputStream(),
                        StandardCharsets.UTF_8));
                System.out.println("Reply: " + in.readLine());
            }
            serverTask.get(5, TimeUnit.SECONDS);
        } finally {
            workers.shutdownNow();
        }
    }
}
~~~

### 8.3. Compiling and Running

~~~bash
javac -encoding UTF-8 TlsLoopbackDemo.java
java TlsLoopbackDemo server.p12 client-trust.p12
~~~

Stdout when the environment supports TLS 1.3, the certificate/truststore are valid, and the loopback connection succeeds (**verified by actual execution**):

~~~text
TLS 1.3 handshake: OK
Reply: PONG
~~~

The program uses port `0` so the OS picks an available port, avoiding fixed-port collisions. Timing, loopback address behavior, and the TLS provider still depend on the platform; if the JDK or security policy does not allow TLS 1.3, the program will fail with an error rather than **silently** downgrading to a weaker protocol.

### 8.4. What Does Each Step Show?

- **`serverContext`:** reads `server.p12` and configures `KeyManager`. The server can present its certificate and use its **private key** during the handshake.
- **`clientContext`:** reads `client-trust.p12`, configures `TrustManager`, and has **no** client-certificate KeyManager. The client has a basis to trust the test certificate; the server **does not authenticate the client with mTLS**.
- **`SSLServerSocket`:** creates a listening socket on loopback, enabling only TLS 1.3. The underlying TCP networking is handled by JSSE.
- **Client `SSLSocket`:** opens a connection to `localhost`; `parameters.setEndpointIdentificationAlgorithm("HTTPS")` requires identity verification against the target name during the handshake. This step is **mandatory** when using raw `SSLSocket` directly for connections with HTTPS-style identity verification.
- **`startHandshake()`:** server and client complete the TLS handshake; both the chain and hostname must be accepted. If trust or the name mismatches, the client will not print `TLS 1.3 handshake: OK`.
- **`client.getSession().getProtocol()`:** checks that the negotiated session is actually TLS 1.3, rather than assuming from the `SSLContext` name.
- **Application data:** the client writes a `PING\n` line, the server reads it from the JSSE-decrypted `InputStream`, and then the server writes `PONG\n`. This is **newline framing in the demo**, not TLS guaranteeing one read equals one message.
- **Resource management:** `try-with-resources` closes sockets, `Future.get` waits for the server worker, and `finally` shuts down the executor. This is a single-connection demo; it does not include production shutdown or connection-pooling policies.

**Why doesn't the example use trust-all?** To demonstrate **peer authentication**, the server's certificate must be explicitly trusted by the client; if replaced by a TrustManager that unconditionally accepts any certificate, a man-in-the-middle could stand up its own TLS endpoint and read the data.

**Security limits of the demo:** self-signed certificates, hard-coded passwords, and manual truststores are only for local learning. In production, you need separate key/certificate management, file and secret protection, policy-compliant CAs/trust anchors, and proper rotation/revocation.

## 9. Testing Meaningful Failure Cases

### 9.1. Truststore Does Not Trust the Server Certificate

If the client lacks the matching certificate in `client-trust.p12` (or uses another truststore), chain validation fails. In JSSE, you typically receive an exception in the `SSLHandshakeException` family, with details depending on the provider/trust path (e.g., PKIX errors). **Do not** fix this by skipping validation. Inspect the certificate chain, trust anchor, validity period, and keystore in use.

### 9.2. Certificate Is Trusted, but Hostname Is Wrong

If the server certificate has SAN `other.example` while the client connects to `localhost`, a TrustManager may accept the certificate chain, yet `HTTPS` hostname verification will fail. This clearly shows that **trusting a public key ≠ trusting the identity you intended to connect to**.

A trick like `setEndpointIdentificationAlgorithm(null)` or a `HostnameVerifier` that always returns true might "make the test pass," but it removes name verification and creates a MITM vulnerability. Instead, issue a certificate whose SAN matches the real hostname, or fix the URL/connection name to match the expected identity.

### 9.3. Server Has No Client Certificate Verification

In the demo, the server does **not** call `setNeedClientAuth(true)` and does not configure a trust policy for client certificates. Outputting `TLS 1.3 handshake: OK` proves **the client authenticated the server as configured**; it does **not** prove the server authenticated the client via TLS. If the application requires mTLS, you must add:
- A client keystore containing the permitted client's private key + certificate.
- A server truststore/TrustManager that verifies client certificates.
- Server socket configuration requiring client authentication during the handshake.
- Application logic mapping the certificate principal to specific permissions/roles.

Do not assume everyone holding a certificate from a valid CA has the same business permissions.

### 9.4. Cipher/Version Mismatch or Expired Certificate

When client and server share no compatible protocol/cipher/group/signature algorithm, the handshake fails. The program intentionally requires `TLSv1.3` on both sides, so it does not silently downgrade.

The demo certificate is valid for only `2` days from creation; re-running after expiration may fail. In practice, monitor expiry, prepare certificate rotation ahead of time, ensure intermediate chains are present, and keep system clocks synchronized.

### 9.5. Socket Errors Are Not Authentication Errors

`ConnectException`, timeouts, connection refusals, bad DNS, or firewall blocks can occur **before** the handshake or during transmission. Distinguish TCP/connectivity errors, TLS protocol/version/certificate errors, and HTTP/application errors; do not blame every failure on a "certificate problem."

## 10. TLS Alone Does Not Protect the Entire System

### Termination and Plaintext Paths

A common architecture:

~~~text
Client ─── TLS ───► Load Balancer / Reverse Proxy
                        │ decrypt
                        ▼
                     HTTP/plain ───► Application Server
~~~

Here **TLS terminates at the proxy**, leaving no encryption on the proxy → backend hop if that hop uses HTTP/plain. If the internal hop must be secured, you need **separate TLS or mTLS for proxy → backend**, rather than relying solely on Internet-facing TLS.

Even when both hops are encrypted, the proxy still sees plaintext between the two TLS sessions: that is a **trust boundary** that must be governed. TLS does not automatically protect logs containing tokens, databases, caches, stored files, crash dumps, or data in process memory.

### Attacks That TLS Does Not Directly Prevent

| Scenario | Does TLS solve it? |
|---|---|
| Man-in-the-middle reading or modifying TLS application data after a properly authenticated handshake | TLS is designed to protect against eavesdropping/tampering in transit |
| Phishing website with its own domain and a valid certificate for that domain | **No**; the certificate proves domain identity per PKI, not that the business content is safe |
| Java client disabling validation and connecting to an impostor | **No**; the configuration removed identity verification |
| Server with a SQL injection bug or data leak via API | **No**; application-level protection is required |
| Unauthorized user calling an endpoint after the TLS handshake | **No**; business authentication/authorization is required |
| Data read from RAM/logs after TLS decryption | **No**; it is already at the endpoint |
| Attacker dropping connections or launching DDoS | TLS does **not** guarantee availability |
| Proxy terminating TLS and forwarding internal HTTP | Front-end TLS does not protect the plaintext hop |
| Private password printed to debug logs | TLS does not protect local logs |
| Client resending a transaction after a timeout | TLS does not guarantee **exactly-once** execution |

### 0-RTT and Replay

TLS 1.3 can support **session resumption**, typically based on PSK/tickets, to reduce handshake overhead. Some configurations also allow sending **0-RTT early data** before the full handshake completes.

**0-RTT has weaker security properties**: it lacks the forward secrecy guarantees of proper 1-RTT traffic and carries **cross-connection replay risk**. Therefore, do not send non-idempotent actions (such as "deduct funds" or "create order" without deduplication keys) in early data unless explicit anti-replay policies/protocols are in place.

Do not assume every Java `SSLSocket` enables 0-RTT; it is a TLS 1.3 capability depending on stack, API, and configuration. In this lesson's demo, `PING` is sent **after** `startHandshake()`, with no early data.

## 11. Checklist for Implementing TLS Correctly in Java

| Step | What to verify |
|---|---|
| 1. Use supported TLS APIs | `HttpsURLConnection` / `java.net.http.HttpClient` for HTTPS; `SSLSocket` or `SSLEngine` when building custom protocols |
| 2. Choose secure versions | Prefer TLS 1.3, keep TLS 1.2 when required by policy; never downgrade to SSLv3/TLS 1.0/TLS 1.1 |
| 3. Never create a trust-all TrustManager | Use proper truststores/CAs; verify the certificate path |
| 4. Verify hostnames | With raw `SSLSocket`, enable `SSLParameters.setEndpointIdentificationAlgorithm("HTTPS")` for clients needing hostname verification |
| 5. Manage private keys | Protect server keystores and passwords with a secret manager, restrict access, and rotate |
| 6. Client certificates only with mTLS policy | Server `setNeedClientAuth(true)` and trust policy; app maps identity → permissions |
| 7. Do not abuse debug logging | TLS debugging can expose certificates/sensitive metadata; never log access tokens or plaintext |
| 8. Timeouts and quotas | Connect timeout, handshake/read timeout, message size limits, connection limits |
| 9. Never ignore TLS errors | Distinguish trust/hostname/version/transport errors; fail closed when authentication fails |
| 10. Audit TLS termination | Identify which endpoint decrypts and whether the hop behind a proxy uses TLS |
| 11. Monitor expiry | Certificate renewal, trust updates, and accurate system clocks |
| 12. Negative testing | Wrong truststore, wrong SAN, expired certificate, TLS version mismatch, invalid client cert |

**Versions/ciphers:** TLS 1.3 is usually preferred, but merely calling `SSLContext.getInstance("TLS")` does not prove the actual session uses TLS 1.3. Check `SSLSession.getProtocol()` after the handshake and rely on JDK policy, security properties, and peer negotiation. Disable obsolete versions per organizational requirements; never pick cipher suites by "trying things until errors go away" at the expense of weaker security.

**Passwords and key files:** when operating Java applications, do not hard-code them as in the demo; use secret management, proper chmod/ACLs, backup controls, and rotation. An expired certificate must be replaced validly, never worked around by relaxing validation.

## 12. Common Misconceptions

| Misconception | Accurate explanation |
|---|---|
| "`https://` means the server is definitely trustworthy in every way." | TLS authenticates domain/certificate per policy; it does not guarantee page content is safe |
| "Once data is encrypted, server authentication isn't needed." | If connected to an attacker, that attacker can decrypt data for the TLS session they terminate |
| "TLS always authenticates both client and server." | HTTPS usually does server auth only; client auth requires mTLS or the application layer |
| "Checking the certificate chain is enough; hostname isn't needed." | You must bind the certificate to the **expected server name** |
| "If `SSLHandshakeException` happens, use trust-all." | Diagnose the CA/truststore/SAN/expiry/protocol issue; never disable validation |
| "The certificate's public key encrypts the entire HTTP body with RSA." | TLS 1.3 uses symmetric AEAD traffic keys; the cert key participates in authentication |
| "With TLS, nobody can see IP addresses or metadata." | IP, timing, and size remain visible; SNI can leak unless ECH is used |
| "TLS guarantees the server will return a complete and correct response." | TLS integrity ≠ availability/business correctness; handle truncation/timeouts |
| "TLS 1.3 always guarantees all data is forward secret." | PSK-only and 0-RTT have important exceptions |
| "TLS into a reverse proxy means the whole system is encrypted." | The proxy → backend hop needs its own protection |
| "One `SSLSocket.read()` equals one message." | TLS over TCP is still a byte stream; the app must frame messages |
| "A valid mTLS certificate means permission to call every API." | Mapping client identity and authorization still belong to the application |
| "TLS solves protecting data stored on disk." | TLS protects data in transit, not encryption/secure storage at rest |

## 14. Summary

- **Confidentiality:** TLS protects application data content on the channel with authenticated encryption, but does not hide all metadata or data after decryption.
- **Integrity:** TLS records detect invalid ciphertext/handshake tampering; they do not guarantee delivery, correctness, or business-level anti-replay.
- **Authentication:** trust the certificate/key **and** verify the hostname matches the intended target. HTTPS typically **authenticates the server**; mTLS is required to authenticate the client by certificate.
- **TLS 1.3:** uses a key schedule and symmetric AEAD traffic keys; with ephemeral (EC)DHE it provides conditional forward secrecy. Resumption/0-RTT have exceptions regarding replay and forward secrecy.
- **Java JSSE:** use `SSLContext`/`KeyManagerFactory`/`TrustManagerFactory` in their proper roles, enable endpoint identification when using raw `SSLSocket` directly; never install trust-all or disable hostname verification.
- **Proper security boundaries:** encryption is per hop; proxies, logs, endpoints, and applications still need authorization, secret management, timeouts, and validation.
