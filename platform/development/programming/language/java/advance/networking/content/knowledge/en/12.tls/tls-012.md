# Diagnosing Certificates, Hostnames, and Algorithms While Preserving Verification

## 1. Objective of This Lesson

When a Java application connects over HTTPS/TLS, handshake errors can stem from the **certificate chain**, **truststore**, **hostname mismatch**, **validity period**, **TLS protocol**, **cipher suite**, **signature/key**, or **mTLS**. Diagnosis must pinpoint the specific cause while preserving two mandatory conditions: **the certificate must be verified against an appropriate trust source** and **the server identity must match the endpoint being accessed**.

If the only goal is to make the request go through, developers can easily and inadvertently drop one of the two checks. Such a connection no longer guarantees that data is being exchanged with the right server. The approach in this lesson is to **fix the chain, SAN, server, truststore, or algorithm configuration**, not to replace the certificate verifier with a trust-all mechanism and not to disable hostname checking.

### Three Distinct Condition Groups

| Group | Question | Example Failure |
| --- | --- | --- |
| **Path/PKIX** | Can the certificate chain up to a trust anchor trusted by the JVM and satisfy usage constraints? | Missing intermediate or internal CA not yet configured |
| **Endpoint identity** | Does the certificate represent the exact DNS name/IP the application uses to connect? | URL calls api.example.com, SAN only contains www.example.com |
| **TLS/cryptography policy** | Are the protocol, cipher, signature, key size, and algorithms still permitted by the JDK? | Server only supports legacy protocols or signatures |

A chain signed by a trusted CA **does not automatically prove the hostname is right**. Conversely, a certificate containing the right name but lacking a trust path is still rejected. A certificate satisfying both conditions can still violate algorithm or validity period requirements.

## 2. Model of the TLS Verification Process

~~~text
Application calls api.example.com:443
            |
     DNS / proxy / route
            |
         ClientHello
   TLS version, ciphers,
   SNI and other extensions
            |
          Server
    certificate chain
            |
    +-------+--------------------------+
    |                                  |
PKIX/path validation          Endpoint identification
CA/chain, validity,          DNS/IP SAN compared against
key usage, algorithms        the requested name
    |                                  |
    +---------------+------------------+
                    |
        If all mandatory checks PASS
                    |
       Handshake completes successfully
                    |
         Application data flows over TLS
~~~

This diagram is a logical model, not the full message sequence of TLS 1.2 or TLS 1.3. Before sending sensitive application data, the program must ensure that the handshake of the **right peer** has been successfully verified.

In Java, **JSSE** provides SSLContext, TrustManager, KeyManager, SSLSocket, SSLEngine, and SSLParameters. **HttpsURLConnection** is an HTTPS client with a default hostname verification mechanism. With **SSLSocket or SSLEngine directly**, you must actively enable appropriate endpoint identification, for example:

~~~java
SSLParameters p = tlsSocket.getSSLParameters();
p.setEndpointIdentificationAlgorithm("HTTPS");
tlsSocket.setSSLParameters(p);
tlsSocket.startHandshake();
~~~

The code above is a snippet placed where an **SSLSocket tlsSocket** already exists. It is not a standalone Java file. Configuring endpoint identification **before the handshake** is critical; merely inspecting SSLSession.getCipherSuite() is not proof that the hostname was checked.

## 3. Step-by-Step Diagnostic Workflow

### Step 1 — Pin Down the Exact Endpoint and Environment

Record the **hostname from the application configuration**, port, JDK vendor/version, running container/VM, proxy, DNS, and TLS termination point. The IP address returned by DNS is not necessarily the name to use for certificate verification: if the request targets api.example.com, endpoint identity must match api.example.com.

On a gateway with multiple virtual hosts, the certificate received also depends on **SNI** in ClientHello. Accessing by IP or setting the wrong SNI name can cause the gateway to return the **default certificate**, even when the desired virtual host's certificate is actually valid.

With a proxy, service mesh, reverse proxy, or load balancer, Java may perform the TLS handshake with an intermediary layer instead of the origin. Diagnose the certificate of the **exact TLS termination point** that the program actually sees.

### Step 2 — Capture the Exception and Cause Chain

Do not read only the outermost **SSLHandshakeException**. Inspect nested causes and handshake/PKIX logs:

| Message or Exception | Where to Check |
| --- | --- |
| **PKIX path building failed** / **unable to find valid certification path** | CA/trust anchor, missing intermediate, truststore loaded by the JVM |
| **CertificateExpiredException** | NotAfter, system clock, expired certificate |
| **CertificateNotYetValidException** | NotBefore or host clock skew |
| **No subject alternative DNS name matching** | Hostname from URL/socket compared against DNS SAN |
| **No subject alternative names present** | Certificate lacks the SAN required for the endpoint |
| **Algorithm constraints check failed** | Signature algorithm, key size, certpath/TLS policy |
| **protocol_version** | TLS versions permitted by both sides |
| **handshake_failure** | Incompatible protocol/cipher/signature, or other authentication error |
| **certificate_required** / **bad_certificate** | Possibly the server's mTLS requirement/policy |

**One SSLHandshakeException can have multiple causes**, so do not jump to conclusions from the outermost exception name. If the root cause involves CertPathValidatorException, read the path validation details carefully. If there is a fatal alert, inspect both client and server logs when you have access.

### Step 3 — Enable Selective Logging in Java

~~~bash
java -Djavax.net.debug=ssl:handshake:trustmanager -Djava.security.debug=certpath TlsVerifiedProbe api.example.com 443
~~~

- **javax.net.debug=ssl:handshake:trustmanager**: view TLS phases, presented certificates, and trust manager selection.
- **java.security.debug=certpath**: add details on certificate path checking and algorithm constraints.
- Log output can vary by vendor/JDK/provider; do not treat a single log string as a rigid assumption across every Java 17 patch.

**Enable logging only temporarily in an appropriate environment.** Endpoint and certificate metadata can be sensitive. Avoid writing private keys, keystore passwords, application data, or plaintext dumps into shared logs.

### Step 4 — Observe the Certificate Returned by the Server

~~~bash
# Print the certificate presented by the endpoint; this is not the app's PKIX/SAN check.
keytool -printcert -sslserver api.example.com:443 -rfc
~~~

If you need to observe with the exact DNS SNI using OpenSSL:

~~~bash
openssl s_client -connect api.example.com:443 -servername api.example.com -verify_hostname api.example.com -verify_return_error -showcerts
~~~

OpenSSL has **its own trust store and security policy**, which do not necessarily match Java's. A successful OpenSSL result **does not automatically prove** the JVM uses the right CA or endpoint identification. The final confirmation test is still running the Java client with verification enabled.

### Step 5 — Inspect the Actual Truststore

Check which **JDK** the process runs on, the **JAVA_HOME** value, the **javax.net.ssl.trustStore** configuration, the store type, and the trust anchors inside. Do not assume the browser, OS, and JVM share the same root CAs.

If the app specifies a custom truststore, it can **replace the default CA set** used by the JVM. A file containing only internal CAs can cause previously working public endpoints to fail with PKIX errors. Verify the exact truststore being loaded, not just whether the file exists.

### Step 6 — Check the Certificate, Hostname, and Algorithms

Compare the leaf, intermediates, and trust anchor; check validity period, DNS/IP SANs, issuer, signature, key strength, Extended Key Usage, and the certification path. Inspect the active security policy from the actual JDK installation. Do not disable any check just to temporarily get a successful connection.

### Step 7 — Fix at the Source and Test Negative Cases Too

After fixing the certificate/server/truststore, re-run the same Java client with the right hostname. In addition to a valid PASS case, an untrusted certificate or mismatched hostname case **must still FAIL**. This is proof that identity checking has not been disabled.

## 4. Diagnosing Certificate Chains and PKIX

### Leaf, Intermediate, Root/Trust Anchor

~~~text
Leaf: SAN api.example.com, public key used for the TLS server
  |
Intermediate CA: certifies the leaf, has appropriate CA constraints
  |
Root CA/trust anchor: trusted by the JVM or a scoped truststore
~~~

The server must usually send the complete **leaf + required intermediates**; the root already trusted by the client typically does not need to be sent. Java must be able to build a valid path to an allowed **trust anchor**, enforcing signature/key length/BasicConstraints/KeyUsage, validity period, and other constraints.

**A missing intermediate** can cause PKIX path building failed even when the root CA is already in the truststore. The durable fix is to deploy the server/gateway with the **correct certificate chain**. Do not rely on the client happening to have the intermediate from another source.

**Untrusted private CA:** obtain the organization's CA public certificate verified through an **independent trust source**, then add that CA to a **properly scoped truststore**. Never automatically grab a certificate from a failing connection and turn it into a trusted CA.

**Validity and clocks:** CertificateExpiredException relates to NotAfter; CertificateNotYetValidException relates to NotBefore. A container with clock skew can cause a valid certificate to be rejected. Fix the system time or renew/reissue the certificate; do not disable time checking.

**KeyUsage/EKU:** a TLS server leaf certificate must be suitable for server authentication under Java's validation rules. A client certificate with an EKU intended for mTLS cannot by default be used in place of a server certificate. CA certificates must also have valid CA constraints.

**Revocation:** OCSP/CRL policies depend on the environment and may not be enabled by default in every JSSE configuration. If security policy requires revocation checking, configure and test it explicitly; do not assume all Java handshakes always perform online revocation checks.

### Scoped Truststore Without Skipping Path Validation

When an internal CA has been pre-verified by an administrator, a dedicated truststore can be created for the application:

~~~bash
# Example with a public CA certificate file verified out-of-band.
keytool -importcert -alias approved-corp-root -file corp-root-ca.pem -keystore app-trust.p12 -storetype PKCS12

# Check alias, fingerprint, and issuer; keytool prompts for a password.
keytool -list -v -keystore app-trust.p12 -storetype PKCS12
~~~

Run the client with the organization-managed truststore:

~~~bash
java -Djavax.net.ssl.trustStore=app-trust.p12 -Djavax.net.ssl.trustStoreType=PKCS12 TlsVerifiedProbe service.corp.example 443
~~~

The filenames and hostname above are illustrative only; to run this you must have a real public CA certificate whose fingerprint has been verified. Never put passwords in source code, command lines, or logs. **Importing a CA does not replace SAN/hostname checking**. If you need to trust both public CAs and internal CAs, design a managed set of trust anchors rather than assuming Java automatically merges a custom store with all default sources.

## 5. Diagnosing Hostname, SAN, and SNI

### 5.1. Hostname Must Match SAN

For example, if the application calls **https://api.example.com** but the leaf certificate only has:

~~~text
Subject Alternative Name:
  DNS:www.example.com
  DNS:static.example.com
~~~

then **api.example.com** does not appear in the SAN, and a client with proper hostname verification must reject it. A certificate that is unexpired and signed by a reputable CA **cannot fix a wrong name**.

**How to fix:** deploy a cert with a **dNSName SAN** matching api.example.com, fix the virtual host/SNI so it selects the right certificate, or fix the URL if the application is using the wrong endpoint. Do not use a HostnameVerifier that accepts unconditionally.

**CN (Common Name)** should not be treated as a fallback for a missing SAN; modern certificates should declare SANs for the DNS/IP names in use. Wildcards have strict rules: **\*.example.com** does not automatically cover **v2.api.example.com** or arbitrary subdomain levels. Do not relax wildcard rules yourself.

### 5.2. DNS Names and IPs Are Two Distinct Identifier Types

| What the Client Actually Requests | What the Certificate Should Have |
| --- | --- |
| api.example.com | A **dNSName** SAN matching api.example.com |
| 192.0.2.10 | An **iPAddress** SAN matching the IP address |
| IPv6 literal | An **iPAddress** SAN for that IPv6 address |

If the client requests **api.example.com**, DNS resolving to 192.0.2.10 does not require the certificate to have an IP SAN. Conversely, switching the URL to an IP just to avoid a hostname mismatch usually causes a new mismatch because the certificate only covers DNS names.

### 5.3. SNI Selects the Cert; Endpoint Identification Checks the Cert

**SNI (Server Name Indication)** is sent in the client's ClientHello so a multi-virtual-host TLS endpoint can select the corresponding certificate:

~~~text
ClientHello SNI = api.example.com
       |
    TLS gateway selects cert with SAN api.example.com
       |
    Java checks chain + hostname
       |
    PASS if all conditions are met

If SNI is wrong or omitted:
    gateway may send default cert with a different SAN
    Java checks hostname -> FAIL
~~~

Some errors that look like a "certificate mismatch" are actually caused by the client passing the wrong host to SSLSocket, a misconfigured gateway, or a corporate proxy returning a different certificate. Always inspect the certificate on the application's **actual connection path**, not just on the origin.

## 6. Diagnosing TLS Protocol, Ciphers, and Algorithms

### 6.1. Algorithms Belong to Different Layers

- **TLS version**: e.g., TLS 1.2, TLS 1.3; both sides must share a version permitted by policy.
- **Cipher suite**: describes the data-protection algorithm suite and related mechanisms; negotiation differs between TLS 1.2 and TLS 1.3.
- **Certificate signature algorithm**: the signature on the certificate, e.g., SHA256withRSA or ECDSA; must be valid under CertPath policy.
- **Public key size and key type**: RSA/EC and corresponding key length/curve; overly weak keys can be rejected.
- **Signature schemes/named groups**: authentication/key-exchange capabilities during the handshake, which can also cause incompatibility.

The **handshake_failure** message does not by itself state which item is wrong. You must compare ClientHello/ServerHello and the certificate chain, along with both sides' mTLS and trust configurations.

### 6.2. Two Important Java Security Properties

- **jdk.certpath.disabledAlgorithms**: constrains signature algorithms, public keys, and chain-checking conditions.
- **jdk.tls.disabledAlgorithms**: constrains TLS protocol versions, cipher suites, key agreement, or implementation-specific TLS algorithm mechanisms.

Defaults vary by **JDK vendor, patch level, and policy**. Check **JAVA_HOME/conf/security/java.security** and logs in the exact JVM being run; do not copy lists from a different Java version.

If you see **Algorithm constraints check failed**, upgrade the server, reissue an appropriate certificate/key, or configure modern algorithms approved by your organization. **Do not remove security constraints** to "fix" an error, as that can re-enable weak protocols or signatures across many connections.

### 6.3. mTLS

When the server requires **mutual TLS**, the client must have an appropriate **client certificate and private key** from a KeyManager/keystore, and the server must trust the client CA. Adding the server CA to the **client truststore** does not replace providing a client identity. Conversely, providing a client certificate does not remove the obligation to verify the server chain and hostname.

## 7. Standalone Java 17+ Example Without Disabling Verification

**TlsVerifiedProbe.java** creates a TCP connection and wraps it in an SSLSocket using the JVM's **default SSLSocketFactory**. It sets **HTTPS endpoint identification before startHandshake()**, uses the CA/trust policy configured on the JVM, and **only prints session/certificate details after a successful handshake**. Errors are printed with their cause chain and **rethrown**, so a test step does not accidentally turn FAIL into PASS.

The **--self-test** mode makes no network connection: it checks that SSLParameters has "HTTPS" set and that enabled protocols exist. That is a local configuration check and **does not replace a real handshake against a real hostname**.

### File TlsVerifiedProbe.java

~~~java
import java.net.InetSocketAddress;
import java.net.Socket;
import java.security.cert.X509Certificate;
import java.util.Collection;
import java.util.List;
import javax.net.ssl.SSLParameters;
import javax.net.ssl.SSLSession;
import javax.net.ssl.SSLSocket;
import javax.net.ssl.SSLSocketFactory;

public class TlsVerifiedProbe {
    static final int CONNECT_TIMEOUT_MS = 5000;
    static final int READ_TIMEOUT_MS = 8000;

    static void selfTest() throws Exception {
        try (SSLSocket socket =
                (SSLSocket) SSLSocketFactory.getDefault().createSocket()) {
            SSLParameters settings = socket.getSSLParameters();
            settings.setEndpointIdentificationAlgorithm("HTTPS");
            socket.setSSLParameters(settings);
            check("HTTPS".equals(socket.getSSLParameters()
                    .getEndpointIdentificationAlgorithm()),
                    "HTTPS endpoint identification missing");
            check(socket.getEnabledProtocols().length > 0,
                    "No enabled TLS protocols");
            System.out.println("PASS: HTTPS endpoint identification configured");
            System.out.println("PASS: TLS protocols enabled");
            System.out.println("PASS: self-test made no network connection");
        }
    }

    static void check(boolean valid, String message) {
        if (!valid) throw new IllegalStateException(message);
    }

    static void probe(String host, int port) throws Exception {
        try (Socket transport = new Socket()) {
            transport.connect(new InetSocketAddress(host, port),
                    CONNECT_TIMEOUT_MS);
            transport.setSoTimeout(READ_TIMEOUT_MS);

            SSLSocketFactory factory =
                    (SSLSocketFactory) SSLSocketFactory.getDefault();
            try (SSLSocket tls = (SSLSocket) factory.createSocket(
                    transport, host, port, false)) {
                tls.setUseClientMode(true);
                tls.setSoTimeout(READ_TIMEOUT_MS);

                SSLParameters settings = tls.getSSLParameters();
                settings.setEndpointIdentificationAlgorithm("HTTPS");
                tls.setSSLParameters(settings);
                tls.startHandshake();

                SSLSession session = tls.getSession();
                X509Certificate leaf =
                        (X509Certificate) session.getPeerCertificates()[0];
                leaf.checkValidity();

                System.out.println("VERIFIED: " + host + ":" + port);
                System.out.println("Protocol: " + session.getProtocol());
                System.out.println("Cipher suite: " + session.getCipherSuite());
                System.out.println("Subject: " +
                        leaf.getSubjectX500Principal().getName());
                System.out.println("Issuer: " +
                        leaf.getIssuerX500Principal().getName());
                System.out.println("Not before: " +
                        leaf.getNotBefore().toInstant());
                System.out.println("Not after: " +
                        leaf.getNotAfter().toInstant());

                Collection<List<?>> names =
                        leaf.getSubjectAlternativeNames();
                if (names != null) {
                    for (List<?> san : names) {
                        int type = (Integer) san.get(0);
                        if (type == 2 || type == 7) {
                            System.out.println("SAN " +
                                    (type == 2 ? "DNS" : "IP") + ": " +
                                    san.get(1));
                        }
                    }
                }
            }
        }
    }

    public static void main(String[] args) throws Exception {
        if (args.length == 1 && "--self-test".equals(args[0])) {
            selfTest();
            return;
        }
        if (args.length < 1 || args.length > 2 || args[0].isBlank()
                || args[0].contains("/") || args[0].contains(":")) {
            throw new IllegalArgumentException(
                    "Usage: java TlsVerifiedProbe dns-host [port]");
        }
        int port = args.length == 2 ? Integer.parseInt(args[1]) : 443;
        if (port < 1 || port > 65535) {
            throw new IllegalArgumentException("Port out of range");
        }

        try {
            probe(args[0], port);
        } catch (Exception ex) {
            System.err.println("NOT VERIFIED: " +
                    ex.getClass().getSimpleName() + ": " + ex.getMessage());
            for (Throwable cause = ex.getCause(); cause != null;
                    cause = cause.getCause()) {
                System.err.println("Caused by " +
                        cause.getClass().getSimpleName() + ": " +
                        cause.getMessage());
            }
            throw ex;
        }
    }
}
~~~

### Compiling and Running

Save the code to **TlsVerifiedProbe.java** and use **JDK 17 or later**:

~~~bash
javac --release 17 -encoding UTF-8 TlsVerifiedProbe.java
java TlsVerifiedProbe --self-test
~~~

**Exact stdout of self-test mode (tested on a Java runtime):**

~~~text
PASS: HTTPS endpoint identification configured
PASS: TLS protocols enabled
PASS: self-test made no network connection
~~~

Run against a real DNS hostname you are authorized to test:

~~~bash
java TlsVerifiedProbe api.example.com 443
~~~

**api.example.com is only an illustrative hostname**; use a real endpoint in your exercise. When TLS is verified, the program prints **VERIFIED: host:port**, protocol, cipher suite, certificate subject/issuer, validity period, and DNS/IP SANs. On failure, it prints **NOT VERIFIED**, lists the causes, and still throws the exception; there is no automatic fallback or trust-all toggle.

The example's input handling is kept minimal for a DNS hostname or IPv4 address and port; it does not accept full URLs or IPv6 literals containing colons. A production API should parse URIs/hosts properly if multiple address formats are supported.

**Why is verification preserved?** The code does not replace TrustManager, passes the expected hostname to the layered socket, sets **HTTPS** endpoint identification, and requires startHandshake to complete before reading the session/cert. Both the transport and SSLSocket are closed via try-with-resources. **However**, if the JVM environment has been configured by operators with a truststore broader than the intended policy, the app must still control that CA configuration; no self-test replaces reviewing the actual trust policy.

## 8. Three Correct Remediation Scenarios

### A. Browser Works, but Java Reports PKIX

**Likely causes:** Java and the browser use different trust anchors; Java's trustStore override is wrong; the server is not sending the intermediate; a private CA is not yet allowed.

**How to fix:** inspect the chain/truststore in use, verify the CA fingerprint out-of-band, deploy the full chain, and configure the approved CA into a properly scoped truststore. Retry Java with verification enabled.

**Do not:** make the client trust all certificates or blindly import an unverified leaf certificate just to make the error temporarily disappear.

### B. Java Reports No subject alternative DNS name matching

**Likely causes:** wrong hostname in URL, SAN does not cover that name, SNI not sent properly, TLS gateway returning a different virtual host's cert, or a proxy interfering.

**How to fix:** issue a cert with the right SAN, fix the URL/SNI/gateway. Use DNS names intentionally; do not switch to an IP and drop hostname checking.

**Do not:** use an unconditional HostnameVerifier.

### C. Java Reports Algorithm constraints check failed or handshake_failure

**Likely causes:** certificate signature/key is too old, server lacks a common cipher/protocol, incompatible signature schemes, or mTLS is missing a client key/cert.

**How to fix:** inspect handshake logs and security properties in the exact JVM, and upgrade the TLS server, certificate/key, JDK, or mTLS configuration to match policy. Keep insecure algorithm restrictions disabled.

**Do not:** relax jdk.tls.disabledAlgorithms or jdk.certpath.disabledAlgorithms just to let a request pass.

## 9. Testing After Fixing to Prove Verification Still Works

| Test | Expected Result |
| --- | --- |
| Valid certificate, trusted chain, matching hostname | Handshake succeeds |
| CA not in truststore | Handshake is rejected |
| Hostname does not match SAN | Handshake is rejected |
| Leaf certificate expired / not yet valid | Handshake is rejected |
| Certificate/key violates policy | Handshake is rejected |
| No common TLS version | Handshake fails until both sides use an allowed configuration |
| mTLS required but client lacks an appropriate cert | Fails to authenticate |
| Fix the valid configuration for each case | Only qualifying endpoints are accepted |

A **missing intermediate** case may not always FAIL if the JVM already has another valid trust path; check the actual PKIX path logs when building test fixtures. A single HTTP 200 **is not enough** to prove the connection verified the right peer if the code tampered with TLS validation.

In CI or staging, keep negative tests with untrusted certificates or intentionally wrong hostnames. If they start passing after a configuration change, that is a red flag for identity verification.

### Checklist Before Closing an Incident

1. Identified the actual hostname, port, and TLS termination point.
2. Saved the exception/cause chain, JDK version, and timestamp of the error.
3. Checked the chain, SAN, validity period, key usage, algorithm constraints, and mTLS if applicable.
4. Confirmed which truststore Java loaded; verified the CA fingerprint independently.
5. Checked SNI, DNS, and proxy when the returned certificate did not match expectations.
6. Re-ran the client **with verification enabled** against the real endpoint.
7. Proved that an endpoint with a wrong SAN or untrusted chain is still rejected.
8. Turned off sensitive debug logging after diagnosis, leaving no secrets in logs.

## 10. Self-Check Questions

**Question 1.** Why can an unexpired certificate signed by a trusted CA still be rejected?  
**Answer:** The SAN does not match the hostname, EKU/KeyUsage or the algorithm/key does not satisfy policy, or another PKIX constraint is invalid.

**Question 2.** Does PKIX path building failed prove that the URL has the wrong hostname?  
**Answer:** No. It usually relates to the certificate chain/trust anchor path. Hostname checking is a separate identity verification step.

**Question 3.** Why should a raw SSLSocket set the HTTPS endpoint identification algorithm?  
**Answer:** To verify the certificate against the **expected peer name** during the handshake, rather than merely trusting any CA-signed chain.

**Question 4.** Should a hostname mismatch be handled by having HostnameVerifier always return true?  
**Answer:** No. That drops the peer authentication requirement; you must fix the SAN, URL, SNI, or gateway.

**Question 5.** Why can an OpenSSL probe succeed while Java still reports an error?  
**Answer:** Java has a different truststore/provider/security policy, so you need to run a Java client to verify directly.

**Question 6.** When connecting by IP, is a dNSName SAN that looks like the IP string sufficient?  
**Answer:** You should not rely on that. An IP literal needs an appropriate iPAddress SAN, while a DNS name needs a dNSName SAN.

**Question 7.** Should an algorithm constraints error be resolved by removing the policy that disables algorithms?  
**Answer:** No. Update the certificate, server, TLS configuration, or runtime to use permitted algorithms.

**Question 8.** Does a PASS from TlsVerifiedProbe --self-test prove that a remote certificate is valid?  
**Answer:** No. It only checks local configuration; a live handshake with the real hostname and truststore is required.

**Question 9.** If the server requires mTLS, is adding the server's root CA to the client truststore enough?  
**Answer:** No. The client needs an appropriate certificate and private key; the server side must also verify the client.

**Question 10.** What conditions prove that a TLS fix is safe?  
**Answer:** Valid endpoints PASS, endpoints with a wrong chain/SAN/algorithm still FAIL, and no verification step has been disabled.

## Conclusion

**Never fix TLS errors by weakening verification.** Identify the exact endpoint, read the cause chain and JSSE/CertPath logs, and inspect the chain/truststore, SAN/SNI, algorithms, and mTLS. After updating the configuration, re-run the Java client with the right hostname, keep PKIX and HTTPS endpoint identification enabled, and test that invalid connections are still rejected.
