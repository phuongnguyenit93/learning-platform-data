# Xác thực hai chiều bằng chứng chỉ máy khách (mTLS) trong Java

**Mutual TLS (mTLS)** là TLS có **xác thực chứng chỉ ở cả hai chiều**: client kiểm tra danh tính máy chủ, đồng thời máy chủ yêu cầu và kiểm tra chứng chỉ X.509 của client. Đây là một cơ chế xác thực ở **lớp kênh truyền**; nó không tự quyết định client được phép gọi API nào, đọc dữ liệu của tenant nào hoặc thực hiện nghiệp vụ nào. Sau khi TLS xác thực một certificate identity, ứng dụng vẫn cần **authorization** và chính sách truy cập dựa trên danh tính đáng tin cậy.

Trong Java 17, mTLS có thể triển khai qua **JSSE** (Java Secure Socket Extension) với **SSLContext**, **KeyManagerFactory**, **TrustManagerFactory**, **SSLServerSocket/SSLSocket** hoặc **SSLEngine**. Những thành phần này giải quyết các việc khác nhau: giữ khóa và chứng chỉ của chính mình, xác định certificate authority/peer nào được tin, yêu cầu chứng chỉ client, kiểm tra tên máy chủ và chỉ chuyển dữ liệu ứng dụng sau khi handshake hợp lệ.

Bài này thuộc phần **TLS** của Java Advance — networking. Nội dung bao gồm cơ chế handshake, kho khóa và kho tin cậy, thuật ngữ X.509, mã Java 17 chạy trên loopback, các thao tác **keytool** để tạo môi trường thực hành, kiểm tra lỗi khi thiếu/sai chứng chỉ, những điểm bảo mật bắt buộc khi đưa mTLS vào production và cách kiểm chứng đúng.

## 1. TLS một chiều khác mTLS ở đâu?

TLS thông thường cho HTTPS thực hiện **server authentication**: máy chủ đưa ra chứng chỉ, client kiểm tra chuỗi tin cậy và danh tính của địa chỉ muốn kết nối. Client sau đó có thể xác thực ở tầng HTTP bằng cookie, token, OAuth hoặc phương thức khác.

Với mTLS, máy chủ **còn yêu cầu client gửi chứng chỉ**, kiểm tra chứng chỉ được tin cậy và client sở hữu private key tương ứng. Việc xác thực này nằm trong TLS handshake; sau đó application có thể ánh xạ client certificate identity thành một principal và áp đặt chính sách quyền.

| Câu hỏi | TLS có xác thực server | mTLS yêu cầu xác thực client |
|---|---|---|
| Client kiểm tra server certificate và tên máy chủ? | Có, nếu client cấu hình xác minh đúng | Có, vẫn bắt buộc |
| Server yêu cầu client certificate? | Thông thường không | Có, bằng policy **needClientAuth** hoặc cấu hình tương đương |
| Server xác minh chain/certificate của client? | Không bắt buộc | Có, theo trust anchors và quy tắc kiểm tra |
| Client chứng minh sở hữu private key tương ứng? | Không cần ở TLS thông thường | Có, thông qua bằng chứng mật mã trong handshake |
| Kết nối có được mã hóa và bảo vệ tính toàn vẹn? | Có, với TLS được cấu hình an toàn | Có |
| Tự cấp quyền truy cập tài nguyên nghiệp vụ? | Không | **Không** — vẫn cần authorization |
| Có loại bỏ yêu cầu kiểm tra server hostname/SAN? | Không | **Không** |

**Hai chiều không có nghĩa hai bên trao private key.** Mỗi bên chỉ giữ private key của mình và đưa public certificate/chain cần thiết cho peer; quá trình handshake chứng minh sở hữu private key mà không gửi bí mật ấy qua mạng.

**mTLS không nhất thiết thay thế token người dùng.** Trong kiến trúc service-to-service, certificate thường đại diện cho **service/workload**, còn JWT/session có thể đại diện cho **end user**. Hai lớp danh tính này có thể cần cùng tồn tại.

## 2. Cơ chế TLS 1.3 mTLS ở mức khái niệm

Trong TLS 1.3, trao đổi handshake và thông điệp cụ thể phụ thuộc cipher suites, certificate setup và session resumption. Luồng khái quát của một phiên mới có client certificate authentication:

~~~text
      Java client                               Java server
          |                                         |
          | ------------ ClientHello ------------> |
          | <----------- ServerHello ------------- |
          | <------ EncryptedExtensions ---------- |
          | <-------- CertificateRequest --------- | (server yêu cầu cert client)
          | <------ Server Certificate ----------- |
          | <------ Server CertificateVerify ----- |
          | <----------- Server Finished --------- |
          |                                         |
          |  Client kiểm tra server chain, SAN,    |
          |  policy; chọn client certificate       |
          |                                         |
          | -------- Client Certificate ---------> |
          | ------ Client CertificateVerify -----> |
          | --------- Client Finished -----------> |
          |                                         |
          |  Server kiểm tra client certificate,  |
          |  chain/trust, chứng minh private key   |
          |                                         |
          | <======= Dữ liệu ứng dụng qua TLS =====>|
~~~

Sơ đồ **cố ý đơn giản hóa** thứ tự và các nhánh (ví dụ CertificateRequest có thể tùy cấu hình, TLS 1.2 khác TLS 1.3, session resumption khác full handshake). Một số handshake messages được bảo vệ bằng khóa đã thương lượng. Điều cần ghi nhớ là:

1. **Server authentication:** client xác minh certificate chain và ràng buộc certificate với địa chỉ đích mong đợi (DNS/IP SAN). Client không được chỉ kiểm tra “certificate được một CA nào đó ký” rồi bỏ hostname validation.
2. **CertificateRequest:** khi server yêu cầu client authentication, client chọn chứng chỉ thích hợp và gửi chuỗi certificate được phép gửi.
3. **Client authentication:** server kiểm tra chain, thời hạn, mục đích sử dụng, constraints, trust policy và bằng chứng sở hữu private key. Nếu **client authentication là bắt buộc** mà client không cung cấp chứng chỉ hợp lệ, handshake phải thất bại.
4. **Application authentication/authorization:** sau TLS handshake, server ánh xạ danh tính trong certificate sang service account/role/tenant theo một quy tắc độc lập và quyết định tài nguyên được phép dùng.

**Không tự xây giao thức xác thực bằng cách gửi PEM certificate qua HTTP rồi so chuỗi** nếu mục tiêu là mTLS. Certificate trong một request body không tự chứng minh bên gửi nắm private key; TLS handshake mới cung cấp phần chứng minh ấy.

## 3. X.509 certificate đại diện cho điều gì?

Một certificate X.509 thường có:

- **Subject/Issuer:** thông tin chủ thể và tổ chức phát hành; không nên coi CN tự do là định danh ủy quyền tuyệt đối.
- **Subject Alternative Name (SAN):** danh tính được cấp trong certificate, ví dụ **DNS name**, **IP address**, **URI** hoặc kiểu khác; là nguồn quan trọng cho kiểm tra server hostname và identity policy.
- **Public key:** khóa công khai liên kết với private key được giữ an toàn ở endpoint.
- **Validity window:** **Not Before / Not After**; cert hết hạn hoặc chưa hiệu lực thường không được chấp nhận theo chính sách PKIX.
- **Extended Key Usage (EKU):** ví dụ **serverAuth** cho TLS server, **clientAuth** cho TLS client; policy/provider có thể kiểm tra mục đích dùng.
- **Key Usage, Basic Constraints, signature algorithm, certificate chain:** ràng buộc loại khóa, vai trò CA/leaf và độ tin cậy của chứng chỉ.

Một CA root hoặc intermediate có thể ký certificate cho server/client. **Trust anchor** trên bên xác minh cho phép kiểm tra đường chain, chứ không đồng nghĩa tin mọi client được CA ấy cấp trong mọi ứng dụng. Cần hạn chế cấp phát, yêu cầu EKU thích hợp, có namespace/identity constraints và ánh xạ quyền thật.

**Ví dụ định danh có thể có ý nghĩa khác nhau:**

- Server cert có SAN DNS **api.example.internal**, phù hợp client kết nối tới host đó.
- Server cert có SAN IP **127.0.0.1**, phù hợp demo kết nối tới IPv4 loopback qua IP.
- Client cert có URI SAN **spiffe://example.org/ns/orders/sa/worker**, biểu diễn một workload nếu PKI/policy quy định như vậy.
- Client cert chỉ có **CN=lab-client** trong bài lab: dễ xem trong keytool nhưng **không nên tự động coi CN đó là service identity đủ mạnh cho authorization production**.

**Certificate được tin cậy không có nghĩa tự động có quyền cao.** Một CA có thể phát hành hàng nghìn certificate. Server cần xác định certificate identity cụ thể và ánh xạ vào whitelist/RBAC/ABAC hoặc policy engine; từ chối identity không phù hợp dù handshake thành công.

## 4. KeyStore, TrustStore, KeyManager và TrustManager

Đây là bốn khái niệm dễ nhầm nhất khi cấu hình JSSE.

**KeyStore (identity store)** lưu **private key** của endpoint cùng certificate chain tương ứng. Java **KeyManager** chọn credentials để endpoint **xuất trình danh tính của chính mình**.

**TrustStore** lưu các **chứng chỉ hoặc CA trust anchors mà endpoint đồng ý tin cậy** khi kiểm tra người đối diện. Java **TrustManager** thực hiện việc xác minh chứng chỉ peer.

| Thành phần | Java server | Java client |
|---|---|---|
| Identity KeyStore | Server private key + server certificate chain | Client private key + client certificate chain |
| KeyManagerFactory | Chọn khóa/certificate **server** để xuất trình | Chọn khóa/certificate **client** khi server yêu cầu |
| TrustStore | Tin cậy CA/certificate **client** được phép | Tin cậy CA/certificate **server** |
| TrustManagerFactory | Kiểm tra chain của **client** | Kiểm tra chain của **server** |
| Endpoint identification | Thường là ứng dụng riêng kiểm tra client identity/policy sau handshake | Kiểm tra server DNS/IP SAN tương ứng địa chỉ gọi |
| Quy tắc phân quyền | Map authenticated client identity sang role/quyền | Có thể áp policy đối với server đích nếu cần |

~~~text
SERVER:
  server.p12        -> KeyManager -> Server cert + server private key
  server-trust.p12  -> TrustManager -> Tin client certificate/CA

CLIENT:
  client.p12        -> KeyManager -> Client cert + client private key
  client-trust.p12  -> TrustManager -> Tin server certificate/CA

PRIVATE KEY KHÔNG ĐƯỢC CHÉP VÀO TRUSTSTORE CỦA PEER.
~~~

**KeyStore và TrustStore đều có thể là tệp PKCS#12 (.p12).** Sự khác biệt ở **loại entry và vai trò**, không nhất thiết ở extension: KeyStore thường có **PrivateKeyEntry**, TrustStore thường có **trustedCertEntry**.

**Sai lầm nghiêm trọng:** ghi **server private key** sang client truststore hoặc đưa **client private key** cho server. Bên xác minh chỉ cần certificate/trust anchors phù hợp, không cần sở hữu private key của peer.

### Khi dùng CA thật

Trong lab bên dưới, chúng ta nhập trực tiếp **hai self-signed leaf certificates** vào hai truststores: đó là cách xây một môi trường tin cậy nhỏ, được xác định trước. Trong production, thường nhập **CA trust anchor**, quản lý chain và certificate issuance/rotation/revocation theo PKI của tổ chức. Không copy một self-signed cert tùy ý rồi coi nó là CA được phép cấp certificate vô hạn.

### Trust theo CA có giới hạn phạm vi

Một client certificate có chain hợp lệ và thuộc CA tin cậy **chưa đủ** để được toàn quyền. Có thể cần kiểm tra thêm issuer policy, EKU, URI SAN identity, cluster/namespace, tenant, thời hạn hoạt động của service và trạng thái revoke. **TrustManager bảo đảm phần TLS certificate validation theo cấu hình**, còn application authorization xác định việc thực sự được phép.

## 5. Các lớp Java 17 cần biết

| Lớp/API | Công việc |
|---|---|
| **KeyStore.getInstance("PKCS12")** | Đọc private-key/certificate entries hoặc trust anchors |
| **KeyManagerFactory** | Tạo các KeyManager từ identity KeyStore |
| **TrustManagerFactory** | Tạo các TrustManager từ truststore |
| **SSLContext.getInstance("TLS")** | Khởi tạo cấu hình TLS với key/trust managers và SecureRandom |
| **SSLServerSocketFactory** | Tạo SSLServerSocket đã dùng SSLContext của server |
| **SSLServerSocket.setNeedClientAuth(true)** | Bắt buộc accepted SSLSocket đòi chứng chỉ client hợp lệ |
| **SSLServerSocket.setWantClientAuth(true)** | Chỉ **đề nghị** client certificate; không bắt buộc cung cấp |
| **SSLSocketFactory** | Tạo SSLSocket phía client từ SSLContext của client |
| **SSLSocket.startHandshake()** | Bắt đầu TLS handshake, báo lỗi khi xác thực thất bại |
| **SSLParameters.setEndpointIdentificationAlgorithm("HTTPS")** | Yêu cầu kiểm tra server endpoint name trong TLS handshake theo thuật toán HTTPS |
| **SSLSession.getPeerPrincipal()/getPeerCertificates()** | Lấy peer certificate identity/certificates sau handshake hợp lệ |
| **SSLEngine** | TLS engine dùng với non-blocking/async transport, không tự làm I/O TCP |

**SSLSocket là blocking I/O TLS socket.** Nếu ứng dụng dùng SocketChannel/Selector, đừng bọc thô SocketChannel bằng SSLSocket và kỳ vọng hoạt động non-blocking. Với NIO, thường dùng **SSLEngine** (hoặc framework TLS đã được kiểm thử) để mã hóa/giải mã byte buffers và điều phối handshake.

**TLSv1.3** và **TLSv1.2** là các lựa chọn hiện đại tùy chính sách và interoperability. Ví dụ lab chủ động chỉ cho TLS 1.3 để kết quả cấu hình rõ ràng. Không cần tự chọn cipher suite bằng tay nếu không có yêu cầu; để JSSE và chính sách bảo mật hiện hành chọn từ các suite được cho phép.

### needClientAuth và wantClientAuth khác nhau

~~~java
serverSocket.setNeedClientAuth(true);  // Bắt buộc certificate client.
serverSocket.setWantClientAuth(true);  // Chỉ yêu cầu nếu client có.
~~~

Đây là **hai lựa chọn loại trừ nhau**, không gọi nối tiếp để “tăng bảo mật”. Theo Java 17, gọi setter sau ghi đè cài đặt của setter trước. Để thực thi mTLS **bắt buộc** cho endpoint đang xét, dùng **setNeedClientAuth(true)** trên listener hoặc cấu hình tương đương trước TLS handshake.

Không chỉ gọi **setWantClientAuth(true)** rồi tuyên bố endpoint đã bắt buộc mTLS: client không trình certificate vẫn có thể hoàn tất handshake nếu không có lỗi khác.

### Kiểm tra tên server bằng SSLParameters

Khi dùng raw **SSLSocket** trong Java, không mặc nhiên dựa vào truststore để bảo vệ chống **kết nối nhầm đến một server khác vẫn được CA tin**. Bật endpoint identification trước **startHandshake**:

~~~java
SSLParameters parameters = clientSocket.getSSLParameters();
parameters.setEndpointIdentificationAlgorithm("HTTPS");
clientSocket.setSSLParameters(parameters);
clientSocket.startHandshake();
~~~

Đây là **đoạn API minh họa**, giả định clientSocket đã tạo; mã đầy đủ nằm ở phần demo. Khi kết nối tới IP, cert cần IP SAN tương ứng; khi kết nối tới DNS hostname, cert cần DNS SAN phù hợp. **Không tắt hostname verification chỉ để làm handshake “xanh”**.

## 6. Thực hành: tạo certificate và PKCS#12 stores bằng keytool

Phần này tạo hai identity keystores và hai truststores, hoàn toàn trên máy của bạn. **Chỉ dùng cho lab loopback.** Các cert được **self-sign**, thời hạn 30 ngày, RSA 2048; password **changeit** xuất hiện rõ trong command để thao tác dễ lặp lại, **không được dùng thực tế cho credential production**.

Yêu cầu: **JDK 17+** có **keytool**, **javac**, **java** trên PATH. Tạo một **thư mục thực hành mới, trống** rồi chạy lần lượt các lệnh dưới đây từ chính thư mục ấy. Không chạy đè lên keystores thật. Lệnh được viết mỗi dòng riêng để dùng thuận tiện trong Bash, PowerShell hoặc terminal đã cài JDK; không dùng Bash-only line continuation.

### Bước 1: tạo identity certificate cho server

~~~bash
keytool -genkeypair -alias server -keyalg RSA -keysize 2048 -sigalg SHA256withRSA -validity 30 -dname "CN=localhost, OU=Lab, O=Demo, C=VN" -ext SAN=ip:127.0.0.1 -ext EKU=serverAuth -keystore server.p12 -storetype PKCS12 -storepass changeit -keypass changeit -noprompt
~~~

File **server.p12** chứa private key và self-signed server cert. SAN IP **127.0.0.1** là cần thiết vì demo client sẽ kết nối đến IP này và bật endpoint identification **HTTPS**. **serverAuth** nêu mục đích certificate dùng để xác thực TLS server.

### Bước 2: tạo identity certificate cho client

~~~bash
keytool -genkeypair -alias client -keyalg RSA -keysize 2048 -sigalg SHA256withRSA -validity 30 -dname "CN=lab-client, OU=Lab, O=Demo, C=VN" -ext EKU=clientAuth -keystore client.p12 -storetype PKCS12 -storepass changeit -keypass changeit -noprompt
~~~

File **client.p12** chứa private key và self-signed client cert. **clientAuth** phân biệt mục đích sử dụng chứng chỉ máy khách. Demo xác thực certificate bằng truststore; định danh CN chỉ để nhận biết trong lab, không phải cơ chế authorization production.

### Bước 3: export public certificates, không export private keys

~~~bash
keytool -exportcert -rfc -alias server -keystore server.p12 -storepass changeit -file server.crt
keytool -exportcert -rfc -alias client -keystore client.p12 -storepass changeit -file client.crt
~~~

**server.crt và client.crt** là public certificates (PEM) có thể chia sẻ để thiết lập trust cho lab; **server.p12 và client.p12** chứa private key nên không gửi cho peer. Đừng đưa private keys vào source control hoặc chat/log.

### Bước 4: cho client tin server và server tin client

~~~bash
keytool -importcert -noprompt -alias server -file server.crt -keystore client-trust.p12 -storetype PKCS12 -storepass changeit
keytool -importcert -noprompt -alias client -file client.crt -keystore server-trust.p12 -storetype PKCS12 -storepass changeit
~~~

Lưu ý **hướng nhập** rất quan trọng:

- **client-trust.p12** chứa public certificate của **server**: client dùng nó để xác minh máy chủ.
- **server-trust.p12** chứa public certificate của **client**: server dùng nó để xác minh máy khách.
- Không import ngược rồi bù bằng cách tắt PKIX/TrustManager: nếu trust cấu hình sai, handshake **phải báo lỗi**.

### Bước 5: kiểm tra nội dung và loại entry

~~~bash
keytool -list -v -keystore server.p12 -storetype PKCS12 -storepass changeit
keytool -list -v -keystore client.p12 -storetype PKCS12 -storepass changeit
keytool -list -v -keystore server-trust.p12 -storetype PKCS12 -storepass changeit
keytool -list -v -keystore client-trust.p12 -storetype PKCS12 -storepass changeit
~~~

Kỳ vọng **server.p12/client.p12** có **PrivateKeyEntry**, còn hai truststores có **trustedCertEntry**. Trong server certificate cần thấy **IPAddress: 127.0.0.1** trong SubjectAlternativeName và EKU cho serverAuth; trong client certificate có EKU clientAuth.

**Không sử dụng self-signed leaves và password changeit cho production.** Tạo cert từ CA được quản trị, có chain và SAN/KeyUsage/EKU theo policy, private key không thể trích xuất tùy tiện nếu có HSM/keystore bảo vệ, certificate rotation và revocation. Mã lab bên dưới cố ý hardcode password để tập trung vào JSSE; đó là điều cần thay ngay khi áp dụng hệ thống thật.

## 7. Chương trình Java 17 hoàn chỉnh: server và client đều xác minh chứng chỉ

Demo chạy **một JVM**, tạo **mTLS server** và **mTLS client** trên **127.0.0.1/cổng động**, dùng **hai SSLContext độc lập**:

- SSLContext của **server** nạp **server.p12** làm identity và **server-trust.p12** làm trust.
- SSLContext của **client** nạp **client.p12** làm identity và **client-trust.p12** làm trust.
- Server **setNeedClientAuth(true)** nên từ chối client không trình một certificate có thể kiểm tra hợp lệ.
- Client bật **HTTPS endpoint identification** để xác minh server IP SAN **127.0.0.1**.
- Cả hai chỉ bật **TLSv1.3** để thống nhất thí nghiệm; TLS 1.3 có sẵn trên JDK 17 thông thường.
- Sau handshake, client gửi dòng **PING**, server gửi **ACK:PING**; main in kết quả và xác nhận cả hai session đều có peer certificate.

Ví dụ sử dụng **Future** để chờ phía server, nhưng đây là **SSLServerSocket/SSLSocket blocking**, không phải NIO.2 AsynchronousSocketChannel.

Tạo tệp **MtlsLoopbackDemo.java** với nội dung đầy đủ:

~~~java
import java.io.BufferedReader;
import java.io.BufferedWriter;
import java.io.IOException;
import java.io.InputStream;
import java.io.InputStreamReader;
import java.io.OutputStreamWriter;
import java.net.InetAddress;
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.Path;
import java.security.KeyStore;
import java.security.SecureRandom;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.concurrent.TimeUnit;
import javax.net.ssl.KeyManagerFactory;
import javax.net.ssl.SSLContext;
import javax.net.ssl.SSLParameters;
import javax.net.ssl.SSLServerSocket;
import javax.net.ssl.SSLSocket;
import javax.net.ssl.TrustManagerFactory;

public class MtlsLoopbackDemo {
    private record ServerResult(String message, boolean clientCert) {}

    private static SSLContext context(String keyFile, String trustFile)
            throws Exception {
        char[] password = "changeit".toCharArray(); // LAB ONLY

        KeyStore keys = KeyStore.getInstance("PKCS12");
        try (InputStream in = Files.newInputStream(Path.of(keyFile))) {
            keys.load(in, password);
        }
        KeyManagerFactory kmf = KeyManagerFactory.getInstance(
                KeyManagerFactory.getDefaultAlgorithm());
        kmf.init(keys, password);

        KeyStore trust = KeyStore.getInstance("PKCS12");
        try (InputStream in = Files.newInputStream(Path.of(trustFile))) {
            trust.load(in, password);
        }
        TrustManagerFactory tmf = TrustManagerFactory.getInstance(
                TrustManagerFactory.getDefaultAlgorithm());
        tmf.init(trust);

        SSLContext result = SSLContext.getInstance("TLS");
        result.init(kmf.getKeyManagers(),
                tmf.getTrustManagers(), new SecureRandom());
        return result;
    }

    public static void main(String[] args) throws Exception {
        if (args.length != 4) {
            throw new IllegalArgumentException(
                    "Usage: java MtlsLoopbackDemo server.p12 "
                    + "server-trust.p12 client.p12 client-trust.p12");
        }

        SSLContext serverContext = context(args[0], args[1]);
        SSLContext clientContext = context(args[2], args[3]);
        InetAddress loopback = InetAddress.getByName("127.0.0.1");
        ExecutorService worker = Executors.newSingleThreadExecutor();

        try (SSLServerSocket listener = (SSLServerSocket)
                serverContext.getServerSocketFactory()
                        .createServerSocket(0, 50, loopback)) {
            listener.setEnabledProtocols(new String[] { "TLSv1.3" });
            listener.setNeedClientAuth(true);
            listener.setSoTimeout(7_000);

            Future<ServerResult> served = worker.submit(() -> {
                try (SSLSocket peer = (SSLSocket) listener.accept()) {
                    peer.setSoTimeout(7_000);
                    peer.startHandshake();
                    boolean clientCert =
                            peer.getSession().getPeerCertificates().length > 0;

                    BufferedReader input = new BufferedReader(
                            new InputStreamReader(peer.getInputStream(),
                                    StandardCharsets.UTF_8));
                    String message = input.readLine();
                    if (!"PING".equals(message)) {
                        throw new IOException("Unexpected request");
                    }

                    BufferedWriter output = new BufferedWriter(
                            new OutputStreamWriter(peer.getOutputStream(),
                                    StandardCharsets.UTF_8));
                    output.write("ACK:PING\n");
                    output.flush();
                    return new ServerResult(message, clientCert);
                }
            });

            boolean serverCert;
            String reply;
            try (SSLSocket client = (SSLSocket)
                    clientContext.getSocketFactory().createSocket(
                            "127.0.0.1", listener.getLocalPort())) {
                client.setSoTimeout(7_000);
                client.setEnabledProtocols(new String[] { "TLSv1.3" });

                SSLParameters parameters = client.getSSLParameters();
                parameters.setEndpointIdentificationAlgorithm("HTTPS");
                client.setSSLParameters(parameters);
                client.startHandshake();
                serverCert =
                        client.getSession().getPeerCertificates().length > 0;

                BufferedWriter output = new BufferedWriter(
                        new OutputStreamWriter(client.getOutputStream(),
                                StandardCharsets.UTF_8));
                output.write("PING\n");
                output.flush();

                BufferedReader input = new BufferedReader(
                        new InputStreamReader(client.getInputStream(),
                                StandardCharsets.UTF_8));
                reply = input.readLine();
            }

            ServerResult serverResult = served.get(8, TimeUnit.SECONDS);
            System.out.println("Client received: " + reply);
            System.out.println("Server received: "
                    + serverResult.message());
            System.out.println("Server saw client certificate: "
                    + serverResult.clientCert());
            System.out.println("Client saw server certificate: "
                    + serverCert);
        } finally {
            worker.shutdownNow();
        }
    }
}
~~~

Trong **chính thư mục** có đủ bốn tệp .p12, chạy:

~~~bash
javac --release 17 MtlsLoopbackDemo.java
java MtlsLoopbackDemo server.p12 server-trust.p12 client.p12 client-trust.p12
~~~

Khi mọi certificate hợp lệ và không bị môi trường chặn kết nối loopback, stdout là:

~~~text
Client received: ACK:PING
Server received: PING
Server saw client certificate: true
Client saw server certificate: true
~~~

**Đã biên dịch ví dụ với chế độ tương thích Java 17 và thực thi thành công trên một OpenJDK hỗ trợ TLS 1.3** trong môi trường kiểm thử tách biệt. Kết quả trên không phải số đo hiệu năng hay khẳng định mọi máy đều hỗ trợ cùng provider/cert cấu hình; nếu handshake lỗi, chương trình ném exception thay vì in đủ bốn dòng.

### Phân tích chính xác mã demo

**context(keyFile, trustFile)** đọc **hai KeyStore riêng**. **KeyManagerFactory.init(keys, password)** nạp private key và cert chain của endpoint. **TrustManagerFactory.init(trust)** nạp trust anchors dùng để kiểm tra **peer**. **SSLContext.init(keyManagers, trustManagers, SecureRandom)** tạo môi trường bảo mật cho sockets, không có cơ chế “tin tất cả” nào trong demo.

**ServerSocketFactory.createServerSocket(0, 50, loopback)** bind tại IP **127.0.0.1** và cổng động; tham số **50** là backlog yêu cầu của listener, **không** giới hạn số lượng request nghiệp vụ hay mức độ tin cậy của client. **setNeedClientAuth(true)** được gọi **trước accept**, nên accepted SSLSocket nhận policy yêu cầu client certificate. **peer.startHandshake()** diễn ra ở server thread.

**Client** dùng **createSocket("127.0.0.1", port)**, đặt **SSLParameters.setEndpointIdentificationAlgorithm("HTTPS")** trước **startHandshake()**. Demo server cert có IP SAN thích hợp. TrustManager xác minh server certificate/chain, còn HTTPS endpoint identification ràng buộc nó với địa chỉ **127.0.0.1**; hai kiểm tra khác nhau, đều cần thiết.

**Sau handshake** server và client gọi **getSession().getPeerCertificates()**. Việc thấy certificate không phải là một phép xác minh thủ công thay thế TrustManager; validation đã được thực hiện trong handshake, và accepted peer certificate là dữ liệu để application cân nhắc identity/policy tiếp theo. Demo in hai cờ boolean sau khi handshake đã thành công, **không** tuyên bố đã phân quyền người dùng.

**Input/OutputStream** truyền **hai dòng UTF-8 có ký tự xuống dòng**. **BufferedReader.readLine()** dựa trên delimiter newline; **BufferedWriter.flush()** đẩy dữ liệu của Java writer xuống TLS stream. Nếu thiếu newline hoặc flush, ví dụ có thể đợi lẫn nhau; tương tự khi thiếu message framing trong ứng dụng thật.

**Future.get(8, SECONDS)** làm main đợi server worker, không dùng thread-unsafe log đa luồng để xây stdout. **try-with-resources** đóng accepted socket, client socket và listener, còn ExecutorService được shutdown trong finally. Các timeout 7–8 giây dành cho lab; production cần deadline end-to-end cho toàn request, lifecycle shutdown có kiểm soát và tài nguyên connection pool.

## 8. Chương trình Java 17 thứ hai: chứng minh KeyStore không phải TrustStore

Một bài kiểm tra đơn giản nhưng hữu ích là mở bốn file được tạo ở phần lab và đếm **private-key entries** so với **trusted-certificate entries**. Không kết nối mạng, không cần server chạy. Đây là cách kiểm tra độc lập rằng bạn **không nhầm hai kho** trong cấu hình.

Tạo tệp **StoreEntriesDemo.java**:

~~~java
import java.io.InputStream;
import java.nio.file.Files;
import java.nio.file.Path;
import java.security.KeyStore;
import java.util.Enumeration;

public class StoreEntriesDemo {
    public static void main(String[] args) throws Exception {
        String[] paths = {
            "server.p12", "server-trust.p12",
            "client.p12", "client-trust.p12"
        };

        for (String path : paths) {
            KeyStore store = KeyStore.getInstance("PKCS12");
            try (InputStream in = Files.newInputStream(Path.of(path))) {
                store.load(in, "changeit".toCharArray());
            }

            int privateKeys = 0;
            int trustedCerts = 0;
            Enumeration<String> aliases = store.aliases();
            while (aliases.hasMoreElements()) {
                String alias = aliases.nextElement();
                if (store.isKeyEntry(alias)) privateKeys++;
                if (store.isCertificateEntry(alias)) trustedCerts++;
            }

            System.out.println(path + ": privateKeys=" + privateKeys
                    + ", trustedCerts=" + trustedCerts);
        }
    }
}
~~~

~~~bash
javac --release 17 StoreEntriesDemo.java
java StoreEntriesDemo
~~~

Stdout khi bốn .p12 được tạo đúng và chưa có thêm entries:

~~~text
server.p12: privateKeys=1, trustedCerts=0
server-trust.p12: privateKeys=0, trustedCerts=1
client.p12: privateKeys=1, trustedCerts=0
client-trust.p12: privateKeys=0, trustedCerts=1
~~~

**Giải thích:** isKeyEntry true cho entry giữ private key; isCertificateEntry true cho entry chỉ chứa trusted certificate. File thực tế có thể có nhiều alias, nhiều CA và certificate chains, nên số đếm không buộc là một. **Không dùng hàm đếm này để quyết định cert nào được phép authenticate**; vẫn cần TrustManager/PKIX và policy.

Hai tệp Java trong bài đã được kiểm tra biên dịch tương thích Java 17 và chạy bằng JDK hỗ trợ TLS 1.3 trong môi trường kiểm thử. Mã demo cố định password chỉ để học; không dùng để mở khóa bí mật production.

## 9. Các thí nghiệm thất bại: phải thấy handshake từ chối đúng

Một bài mTLS không hoàn chỉnh nếu chỉ kiểm tra tình huống thành công. Đặc biệt, **cấu hình bảo mật sai đôi khi vẫn “chạy được” khi vô tình tắt xác minh**; đó là thất bại về bảo mật, không phải thành công.

### 9.1. Client không tin server certificate

Giữ server và client identity như cũ nhưng truyền **sai truststore phía client**. Ví dụ server-trust.p12 trong lab chứa cert **client**, không chứa server cert:

~~~bash
java MtlsLoopbackDemo server.p12 server-trust.p12 client.p12 server-trust.p12
~~~

**Kỳ vọng:** client không thể xác minh server certificate qua truststore này, handshake thất bại với exception bảo mật/TLS. Chi tiết exception, alert và thứ tự thread báo lỗi có thể khác giữa JDK/OS; **không giả định một chuỗi stdout chính xác** cho kịch bản lỗi. Đây là phép thử âm, không phải cách dùng chính thức.

### 9.2. Server không tin client certificate

Thay **server-trust.p12** bằng **client-trust.p12** (chỉ chứa server cert):

~~~bash
java MtlsLoopbackDemo server.p12 client-trust.p12 client.p12 client-trust.p12
~~~

**Kỳ vọng:** handshake không thể chấp nhận client certificate theo server trust policy và thất bại. Việc lỗi được quan sát bên nào trước có thể khác, nhưng điều phải kiểm chứng là **không có phiên mTLS được chấp nhận để làm nghiệp vụ**.

### 9.3. Client không có certificate

Tạo một SSLContext phía client với **không có KeyManager**, chỉ có TrustManager hợp lệ, rồi thử kết nối vào server vẫn **setNeedClientAuth(true)**. Trên các provider TLS thông thường, server yêu cầu certificate, client không thể đáp ứng và handshake thất bại. Cần **đóng connection**, không tự hạ xuống setWantClientAuth(true) để chạy được.

Đây là **kịch bản thiết kế test**, không phải lệnh chạy trực tiếp từ hai tệp demo trên. Nếu muốn hiện thực, thay client-side SSLContext trong code bằng một context chỉ có trust managers và đảm bảo cùng policy endpoint identification; **không** giả mạo chứng chỉ hoặc tắt kiểm tra trust để “chữa” lỗi.

### 9.4. Mismatch hostname/IP SAN

Với raw SSLSocket đã bật HTTPS endpoint identification, nếu server certificate chỉ có DNS SAN **localhost** mà client kết nối tới **127.0.0.1**, việc kiểm tra IP SAN có thể thất bại. Cách sửa là **cấp certificate có SAN phù hợp với endpoint thực** hoặc kết nối đến đúng hostname được cấp; **không** tắt hostname verification.

### 9.5. Certificate hết hạn, EKU không phù hợp, CA không tin cậy

Kiểm tra lần lượt certificate đã hết hạn, không nằm trong trust chain được phép, EKU thiếu mục đích thích hợp hoặc bị revoke theo policy. Một hệ thống an toàn phải fail-closed theo chính sách đã đặt. Hãy lưu ý **revocation checking có thể cần bật/cấu hình riêng**; không mặc định cho rằng mọi JSSE TrustManager tự truy vấn OCSP/CRL và chặn tất cả cert bị thu hồi.

## 10. Xác thực transport và authorization nghiệp vụ phải tách biệt

mTLS thường đặc biệt phù hợp **service-to-service** (một workload gọi API của workload khác). Nhưng câu hỏi “đây là chứng chỉ hợp lệ” không giống câu hỏi “service này được gọi operation này”.

Ví dụ:

~~~text
API caller presents client certificate
     |
TLS: chain + signature + purpose + time + peer trust policy hợp lệ?
     |
     +-- NO --> handshake fail, không cho xử lý request
     |
     +-- YES --> authenticated certificate identity
                    |
             map SAN URI/DNS -> service principal
                    |
             verify authorization policy:
                    endpoint, method, tenant, scope
                    |
                    +-- DENY --> 403 / ứng dụng từ chối
                    +-- ALLOW --> xử lý request có audit
~~~

**Một hướng ánh xạ có thể phù hợp:** một CA/workload identity platform phát hành cert chứa **URI SAN** theo namespace/service account, server kiểm tra certificate chain/issuer cho đúng trust domain, sau đó dùng URI SAN có cấu trúc chặt chẽ để lookup service principal. **Không tự parse CN và cấp quyền admin** chỉ vì CN chứa chuỗi quen thuộc.

**Xác minh certificate ở tầng TLS thường do TrustManager làm; kiểm tra quyền có thể ở tầng ứng dụng hoặc API gateway**. Nếu server phải từ chối certificate identity không thuộc một tập được phép *ngay trong handshake*, có thể dùng một TrustManager được kiểm soát chặt hoặc sản phẩm gateway có identity policy phù hợp; đừng thay TrustManager chuẩn bằng lớp tùy biến luôn return true.

### Các trường hợp không nên coi mTLS đủ cho authorization

- Hai service được cùng CA cấp cert nhưng chỉ một service được phép gọi chức năng thanh toán.
- Client đã mTLS thành công nhưng đang gọi một tenant hoặc resource không thuộc quyền.
- Máy trạm được cấp client cert có quyền kết nối, nhưng user trên máy cần quyền riêng.
- Gateway xác thực service phía trước, backend còn phải phân biệt **gateway identity** với **end-user identity**.
- Cùng một cert được tái sử dụng giữa nhiều workload làm mất khả năng truy vết và thu hồi quyền chính xác.

Cần một chính sách **least privilege**: định danh cụ thể, scope tối thiểu, kiểm soát thời hạn và rotation, audit có correlation ID, mapping rõ ràng khi cert thay mới.

## 11. Khi TLS kết thúc ở proxy hoặc service mesh

Một kiến trúc điển hình:

~~~text
client workload
      |
      | mTLS giữa client và gateway
      v
[ reverse proxy / ingress / service mesh ]
      |
      | HTTP hoặc một TLS connection MỚI
      v
Java backend
~~~

Nếu **proxy terminate mTLS**, Java backend **không trực tiếp thực hiện TLS handshake với client gốc**. Backend có thể chỉ thấy danh tính proxy ở kênh sau hoặc nhận metadata do proxy chuyển tiếp. **Đừng đọc header tự khai như X-Client-Cert rồi coi là chứng chỉ đã xác minh** nếu client bên ngoài có thể tự đặt header đó.

Muốn ủy quyền dựa vào danh tính client ban đầu khi có proxy:

1. Gateway/sidecar phải thật sự **xác minh client cert** và áp dụng trust policy.
2. Kết nối proxy → backend cần được bảo vệ (ví dụ mTLS nội bộ) và backend chỉ tin proxy được chỉ định.
3. Proxy phải **xóa/ghi đè** mọi header identity do client tự gửi rồi tạo header hoặc signed assertion mới theo hợp đồng tin cậy.
4. Backend phải kiểm tra nguồn metadata, policy và tenant mapping. Tốt hơn là dùng cơ chế identity chuẩn của mesh/gateway khi sẵn có.
5. Xác định rõ **mTLS ở hop nào**: chỉ edge mTLS hay end-to-end mTLS qua nhiều hop khác nhau; không tuyên bố “mTLS end-to-end” khi backend chỉ thấy kết nối từ proxy.

**TLS passthrough** là một mô hình khác: proxy định tuyến byte được mã hóa mà không terminate TLS, backend có thể thấy client certificate trực tiếp trong handshake. Điều này ảnh hưởng khả năng routing/inspection và cần thiết kế riêng.

## 12. Certificate rotation, thu hồi và quản trị bí mật

mTLS production là một **quy trình vận hành PKI** chứ không chỉ một dòng setNeedClientAuth(true).

### 12.1. Vòng đời issuance/rotation

- Phát hành certificate từ CA đã quản lý, subject/SAN/EKU rõ ràng; cấp private key vào vị trí bảo vệ thích hợp.
- Tách môi trường production/test/staging bằng trust domain/certificate policy phù hợp. Không tin CA testing trên production.
- Dùng certificate sống ngắn khi nền tảng hỗ trợ tự động xoay vòng; đồng bộ thời gian hệ thống để tránh lỗi Not Before/Not After.
- Trong giai đoạn đổi CA hoặc đổi cert, chuẩn bị **overlap trust anchors** có kiểm soát để tránh outage, nhưng loại bỏ CA/cert cũ đúng kế hoạch.
- Giám sát ngày hết hạn và thử handshake trước khi cert hết hạn; tính đến session resumption và kết nối dài đang mở.
- Private keys không gửi lên Git, image, log hoặc bucket public. Ưu tiên secrets manager, volume được quản lý chặt, keystore/HSM theo yêu cầu tổ chức; giới hạn quyền đọc file.

**Trong demo, SSLContext đọc keystore/truststore một lần lúc khởi tạo.** Thay file .p12 trên đĩa **không đồng nghĩa mọi SSLContext đang chạy lập tức tải lại cert/trust mới**. Hệ thống cần một cơ chế reload/rebuild SSLContext, thay socket factory/connection theo lifecycle và kiểm thử rotation trước khi deploy.

### 12.2. Revocation: không chỉ chờ certificate hết hạn

Nếu private key của client bị lộ hoặc workload mất quyền, chỉ kiểm tra thời hạn cert là chưa đủ. Các chính sách có thể gồm CRL, OCSP, certificate lifetime ngắn, truststore allowlist, workload identity rotation và cách vô hiệu hóa principal/application access.

**Không khẳng định JSSE mặc định luôn thực hiện online revocation check.** Cấu hình PKIX/CRL/OCSP phụ thuộc provider, security properties và TrustManager setup. Cần định nghĩa yêu cầu fail-open/fail-closed của revocation và kiểm tra thực tế. Nếu revocation service không truy cập được, policy phải rõ ràng thay vì rơi vào trạng thái không nhất quán.

### 12.3. Điều gì xảy ra với connection đã mở?

mTLS kiểm tra identity trong handshake. Nếu cert hết hạn hoặc bị revoke **sau khi** một connection/session đã được thiết lập, không nên giả định socket ngay lập tức bị đóng theo mọi policy. Với long-lived connections, cần chiến lược giới hạn tuổi kết nối, re-authentication/session refresh hoặc server-side authorization check theo request khi đặc thù an ninh yêu cầu.

TLS 1.3 session resumption có semantics riêng; không coi mỗi resumed session đều lặp toàn bộ certificate exchange theo cách giống full handshake. Nếu chính sách đòi hỏi xác thực mới cho mỗi khoảng thời gian/operation, hãy thiết kế session lifetime và renewal rõ ràng.

## 13. Cách đọc lỗi mTLS trong Java

| Dấu hiệu lỗi | Nguyên nhân cần kiểm tra | Không nên làm |
|---|---|---|
| **PKIX path building failed / unable to find valid certification path** | Thiếu CA/peer certificate trong truststore, chain thiếu intermediate, sai trust domain | Không dùng trust-all TrustManager |
| **No subject alternative names matching IP address** | Server SAN không khớp IP kết nối | Không vô hiệu endpoint identification |
| **certificate_unknown / bad_certificate** | Peer không chấp nhận certificate, chain, policy hoặc mục đích sử dụng | Không tự đổi need thành want để vượt lỗi |
| **Empty client certificate chain / certificate_required** | Client không xuất trình chứng chỉ khi server yêu cầu; KeyManager thiếu/không chọn được alias | Không giả định truststore có private key |
| **handshake_failure / no available authentication scheme** | Phiên bản TLS, thuật toán, cert type/strength, key manager, EKU hoặc policy không tương thích | Không hạ xuống giao thức cũ không an toàn |
| **Keystore was tampered with, or password was incorrect** | Sai mật khẩu/store, file hỏng hoặc format không khớp | Không log private key/password |
| **Connection reset / EOF during handshake** | Kết nối bị cắt, peer reject, proxy/network/timeout | Không suy ra một nguyên nhân duy nhất từ reset |
| **Handshake thành công nhưng API trả 403** | TLS identity đã được xác minh nhưng application authorization từ chối | Không nới trust CA để “sửa” permission |
| **Lỗi chỉ sau rotation** | Caching SSLContext, trust anchor cũ, SAN/EKU thay đổi, sync/clock | Không tự mở trust cho mọi CA |

Thông báo exception cụ thể có thể khác Java provider, TLS version và OS; **SSLHandshakeException** thường bọc các chi tiết. Hãy kiểm tra **getCause()**, server và client logs cùng lúc, phiên bản Java, loại cert và endpoint host thật.

### Debug handshake trong môi trường được kiểm soát

Có thể bật JSSE debug cho một lần thử:

~~~bash
java -Djavax.net.debug=ssl,handshake,trustmanager MtlsLoopbackDemo server.p12 server-trust.p12 client.p12 client-trust.p12
~~~

Lệnh có thể tạo **rất nhiều log**. Không bật lâu trong production nếu log có thể tiết lộ thông tin cấu trúc hệ thống, certificate identities hoặc metadata nhạy cảm. Không paste log chứa secrets vào nơi công khai.

Đối chiếu hướng trust: lỗi phía **client** thường liên quan kiểm tra **server**; lỗi phía **server** thường liên quan kiểm tra **client**. Tuy nhiên handshake failure sẽ lan đến cả hai bên, nên cần xem nguyên nhân gốc và điểm phát sinh chứ không kết luận chỉ dựa vào alert quan sát ở một đầu.

### Checklist khi chẩn đoán

1. Đúng certificate/key pair trong keystore của endpoint?
2. Đúng CA/peer cert trong truststore của phía xác minh?
3. Có intermediate chain cần gửi và policy BasicConstraints hợp lệ?
4. Certificate còn hiệu lực, clock đúng và key size/signature algorithm được phép?
5. EKU **serverAuth/clientAuth** và KeyUsage phù hợp?
6. SAN của server khớp **DNS/IP thực client dùng**?
7. **setNeedClientAuth(true)** được áp dụng trước handshake trên đúng listener/endpoint?
8. TLS 1.3/TLS 1.2 và cipher suites tương thích?
9. Certificate có bị revoke hoặc vượt identity policy không?
10. TLS kết thúc ở ứng dụng Java hay ở proxy; backend thực sự nhận được identity nào?
11. Ứng dụng đã ánh xạ authenticated certificate identity thành principal/quyền đúng chưa?
12. Có exception đồng bộ, SSLHandshakeException, timeout hoặc close từ network/peer?

## 14. Hiệu năng, connection pooling và lỗi bảo mật dễ gặp

**mTLS thường tăng công việc handshake ban đầu** do trao đổi thêm certificate chain và kiểm tra chữ ký/chain, nhưng không biến mọi byte sau đó thành hai lần mã hóa. Dữ liệu ứng dụng vẫn dùng các khóa phiên TLS được thương lượng. Hiệu năng phụ thuộc cipher suites, chain length, CPU, session resumption, network latency và policy revocation.

**Không thiết kế hệ thống mở kết nối mới cho từng request** nếu có thể dùng keep-alive/connection pooling an toàn: handshake cho mỗi kết nối có chi phí. Tuy nhiên, pooling cũng cần tôn trọng **client identity**; không tái dùng connection mTLS được xác thực bằng certificate của tenant A cho request tenant B nếu ranh giới tin cậy không cho phép.

**Không dùng một keystore client chung vô hạn cho mọi service.** Làm vậy khiến mất khả năng cấp quyền tối thiểu, audit chính xác và thu hồi theo workload. Tách certificate identities theo service/role/trust domain theo chính sách PKI.

**Không lưu private key trong code hoặc hardcode password thực tế**. Các chuỗi trong demo là cố ý cho lab và không được sao chép vào production. Không giải quyết lỗi handshake bằng **X509TrustManager.checkServerTrusted() không làm gì**, **HostnameVerifier luôn true**, hoặc tắt mọi TLS validation. Làm vậy phá mục đích xác thực của TLS/mTLS.

**Không tin vào ClientHello, CN hay HTTP header một cách đơn lẻ.** ClientHello có metadata do phía gọi tự gửi; CN từ một chứng chỉ chưa được xác minh hoặc header bị spoof không tạo ra principal tin cậy. Chỉ dùng danh tính sau khi handshake đúng policy và sau bước mapping/authorization được xác định.

**Đừng lẫn thuật ngữ certificate pinning và CA trust.** Nhập trực tiếp một self-signed leaf certificate trong demo gần với việc tin một certificate cụ thể; trust một CA root trong production cho phép chain khác được CA ấy phát hành được xem xét, nhưng vẫn phải kiểm tra identity/mục đích. Pinning cứng từng leaf có thể gây outage khi rotate nếu không có kế hoạch chuyển đổi.

## 15. mTLS với HTTP, Java HTTP Client và các framework

Chương trình trong phần trước dùng **raw SSLSocket**, nhưng thực tế mTLS thường chạy trên HTTPS hoặc gRPC:

- **HTTPS client:** cần **SSLContext** với client identity **KeyManager** và server trust **TrustManager**. Java 17 **java.net.http.HttpClient** hỗ trợ cấu hình SSLContext qua builder. Còn HTTPS endpoint verification do HTTP stack xử lý theo tiêu chuẩn; không tự hạ chính sách xác minh khi chuyển framework.
- **HTTPS server/container:** cấu hình connector/gateway cần **require client certificate** trên đúng endpoint và trust CA client; chỉ khai báo keystore server chưa phải mTLS. API cụ thể phụ thuộc server/framework, nhưng khái niệm KeyManager/TrustManager giữ nguyên.
- **gRPC:** TLS credentials và server/client certificate policy thường được cấu hình qua framework; tránh tự thay low-level SSLContext nếu framework đã có cơ chế chuẩn.
- **Service mesh:** có thể terminate mTLS ở sidecar; phần backend phải hiểu ranh giới identity và trusted metadata như đã phân tích.

Một đoạn code minh họa **Java 17 HttpClient** (không phải chương trình độc lập vì chưa khởi tạo clientContext/URI):

~~~java
HttpClient http = HttpClient.newBuilder()
        .sslContext(clientContext)
        .connectTimeout(Duration.ofSeconds(5))
        .build();
~~~

**clientContext** cần chứa certificate/key managers và trust managers phù hợp như đã trình bày. **connectTimeout** không phải tổng deadline cho TLS handshake và toàn bộ HTTP exchange; khi gửi request có thể thêm request timeout, cancellation và circuit breaker theo yêu cầu. Không coi việc gắn SSLContext là quyền truy cập tự động vào mọi API của server.

## 16. Bài tập thực hành có tiêu chí rõ ràng

### Bài tập A — Giải thích hướng trust

Không nhìn bảng có sẵn, hãy tự vẽ: private key của server nằm ở đâu, client nên giữ gì để tin server, server nên giữ gì để tin client, thành phần nào dùng **KeyManager**, thành phần nào dùng **TrustManager**. Kiểm tra bằng **StoreEntriesDemo.java** và keytool -list.

### Bài tập B — Chạy mTLS thành công

Tạo bốn .p12 bằng lệnh keytool, biên dịch/chạy **MtlsLoopbackDemo.java**. Giải thích từng dòng stdout, đặc biệt vì sao cờ **Server saw client certificate: true** cho thấy peer có certificate trong session sau handshake nhưng **không tự chứng minh authorization cho mọi API**.

### Bài tập C — Đảo truststore

Chạy hai lệnh sai truststore ở phần thí nghiệm âm. Chứng minh handshake từ chối kết nối; nêu khác biệt giữa client không tin server và server không tin client. Không thay certificate hoặc trust policy để “bỏ qua” kiểm tra.

### Bài tập D — Need và want

Trong một server thử nghiệm của bạn, so sánh **setNeedClientAuth(true)** và **setWantClientAuth(true)** khi client không có KeyManager. Viết test assertion: ở **need**, handshake không được phép hoàn tất thành một kênh application tin cậy; ở **want**, một client không có certificate có thể vẫn hoàn tất handshake nếu các điều kiện TLS khác hợp lệ. Nêu rủi ro khi ứng dụng tưởng want là bắt buộc.

### Bài tập E — Hostname mismatch

Tạo server certificate chỉ có DNS SAN **localhost** rồi cố kết nối tới IP **127.0.0.1** với endpoint identification HTTPS. Ghi nhận lỗi mismatch; thử lại bằng certificate có đúng SAN. Không tắt hostname verification.

### Bài tập F — Ánh xạ identity sang authorization

Giả sử có ba client certificates hợp lệ thuộc cùng CA: **orders-service**, **billing-service**, **analytics-service**. Định nghĩa bảng quyền sao cho chỉ billing-service được thực hiện một operation tài chính, orders-service chỉ gửi yêu cầu hợp lệ và analytics-service chỉ được đọc báo cáo; kiểm tra certificate identity đúng với policy, không cấp quyền theo CA đơn thuần.

### Bài tập G — Proxy terminate TLS

Thiết kế chuỗi client → gateway → Java backend. Vẽ rõ tại hop nào TLS handshake xác minh client cert, ai được phép tạo identity header, backend xác minh gateway bằng cách nào và làm sao ngăn client gửi header giả.

### Bài tập H — Rotation và revocation

Thiết kế kế hoạch đổi CA/leaf certificate không downtime gồm trust overlap có kiểm soát, SSLContext reload, canary handshake, session lifetime, thu hồi cert cũ và rollback. Giải thích vì sao thay một file .p12 không tự động cập nhật SSLContext đang sống.

### Bài tập I — Vận hành nhiều services

Đo TLS handshake latency, tỷ lệ lỗi chứng chỉ, số cert sắp hết hạn và số kết nối đã thiết lập. Giải thích ưu/nhược điểm của mTLS end-to-end so với terminate ở gateway khi cần phân quyền theo workload identity.

## 17. Câu hỏi ôn tập

**1. mTLS là mã hóa hai lần?** Không. Nó là TLS với **hai chiều xác thực bằng certificate**, không nhân đôi lớp mã hóa payload.

**2. Client có đưa private key cho server trong handshake?** Không. Private key luôn phải giữ ở endpoint; chỉ trao chứng chỉ và chứng minh sở hữu khóa qua handshake.

**3. Tại sao server cần truststore chứa client CA/certificate?** Để TrustManager có cơ sở kiểm tra client certificate được cấp từ nguồn tin cậy.

**4. Tại sao client cần cả identity keystore và truststore?** Identity keystore cho client xuất trình certificate/private key của mình khi server yêu cầu; truststore cho client kiểm tra server certificate.

**5. setWantClientAuth(true) có bắt buộc mTLS?** Không. Nó chỉ yêu cầu certificate nhưng không bắt buộc client có cert; **setNeedClientAuth(true)** mới yêu cầu.

**6. Client trust server cert rồi có cần hostname/SAN check?** Có. Trust chain và endpoint identity là hai điều kiện khác nhau.

**7. Handshake thành công có tự cấp quyền làm admin không?** Không. TLS xác thực danh tính chứng chỉ; authorization phải do ứng dụng/policy quyết định.

**8. Vì sao raw SSLSocket thường cần setEndpointIdentificationAlgorithm("HTTPS")?** Để gắn peer certificate với DNS/IP endpoint khi dùng TLS socket trực tiếp, tránh tin nhầm một host khác cũng có cert thuộc CA tin cậy.

**9. TrustManager và KeyManager khác gì?** TrustManager đánh giá **peer có đáng tin hay không**; KeyManager chọn **credentials của chính mình** để đưa cho peer.

**10. Có thể truyền nguyên server.p12 cho client thay cho server.crt không?** Không nên; server.p12 chứa private key bí mật. Client chỉ cần public certificate/trust anchor.

**11. Certificate client được CA tin rồi có còn cần kiểm tra URI SAN/role không?** Có, nếu ứng dụng có các quyền khác nhau theo service/tenant. Tin CA không đồng nghĩa có mọi quyền.

**12. Lỗi mTLS bị sửa bằng TrustManager “accept all” có an toàn không?** Không. Nó phá xác minh certificate và mở cơ hội tấn công man-in-the-middle.

**13. Future.get timeout hoặc socket read timeout có hủy mọi request phía server?** Không. Timeout phía caller không bảo đảm remote chưa nhận/đã ngừng xử lý.

**14. Khi reverse proxy terminate mTLS, Java backend trực tiếp xác thực cert client ban đầu?** Không. Backend chỉ có thể tin identity được chuyển tiếp nếu ranh giới proxy → backend và metadata được xác thực, bảo vệ đúng.

**15. mTLS có kiểm tra certificate bị revoke tự động ở mọi Java deployment không?** Không thể mặc định như vậy; revocation là chính sách PKIX/CA/TrustManager cần cấu hình và kiểm chứng.

**16. Vì sao certificate rotation có thể cần restart hoặc SSLContext reload?** Vì SSLContext/KeyManager/TrustManager thường đã được khởi tạo từ kho khóa tại thời điểm tạo; thay file trên đĩa không đảm bảo context đang chạy tải lại.
