# Reusing DatagramPacket and Properly Resetting the Receive Buffer Region

## 1. The Problem: DatagramPacket Is Both the Receive Buffer and the Receive Result

In Java, `DatagramSocket.receive(DatagramPacket)` uses a `DatagramPacket` object to receive **one UDP datagram**. TCP is a byte stream and does not preserve message boundaries, whereas UDP preserves datagram boundaries: a single `receive` call retrieves at most one datagram and does not append any remaining portion to subsequent receives.

`DatagramPacket` holds multiple pieces of information at once: the `byte[]` array, the starting position in the array (`offset`), the length (`length`), and the sender's IP address and port. When receiving completes, Java updates the number of bytes just received and the source metadata. This object can be reused multiple times to avoid continuously allocating new arrays and packets.

Reusing is useful when a server receives many packets, but it is essential to understand accurately that **length has two roles depending on timing**:

- **Before receiving:** the length/window that the application allows `receive` to use.
- **After receiving:** `packet.getLength()` indicates **the number of bytes actually stored** from the datagram just received.

If code uses **the length of the previous datagram** to set the limit for the **new datagram**, subsequent packets may be truncated. If the entire array is processed instead of the actual data slice, stale bytes at the tail of the buffer may be read along with it.

Objectives of this lesson: create a packet with an accurate receive region, process according to `getOffset()`/`getLength()`, proactively restore the receive capacity using `setLength(...)` or `setData(...)` when needed, and avoid assuming capabilities beyond what UDP provides.

## 2. The Receive Region Consists of Buffer, Offset, and Capacity

For example, suppose you choose a 20-byte array, but reserve the first 4 bytes for another purpose and only allow UDP to write into the last 16 bytes:

~~~text
byte[] buffer with 20 elements:
index:   0   1   2   3  |  4   5 ... 18  19
         outside region |<--- 16 bytes --->|

Receive region: [offset, offset + receiveCapacity) = [4, 20)

After datagram "A":
getOffset() = 4
getLength() = 1
Valid new byte range = [4, 5)

The tail [5, 20) does not belong to datagram "A".
~~~

Code defining the initial region:

~~~java
byte[] buffer = new byte[20];
int offset = 4;
int receiveCapacity = 16;
DatagramPacket packet =
        new DatagramPacket(buffer, offset, receiveCapacity);
~~~

*The snippet above only illustrates the API and must be inside a class with `import java.net.DatagramPacket`.*

Different values must not be conflated:

| Component | Meaning |
| --- | --- |
| `buffer.length` | Physical size of the array, e.g. 20 bytes |
| `packet.getData()` | The original buffer array, **not a copy** |
| `packet.getOffset()` | Starting position holding the data, e.g. 4 |
| `receiveCapacity` | The application's receive-region limit policy, e.g. 16 |
| `packet.getLength()` after `receive` | Number of bytes **stored from the datagram just received** |
| `packet.getAddress()` / `getPort()` | IP and port of the **sender** of the datagram just received |

Valid data after receive always lies in the range:

~~~text
[packet.getOffset(), packet.getOffset() + packet.getLength())
~~~

When offset is non-zero, reading from index 0 is wrong. When a datagram is shorter than the previous packet, bytes outside the valid range may retain old values because `receive` does not clear the entire array. If processing binary data, read only that exact slice; if decoding a String, decode only the exact offset/length.

The receive region must satisfy `offset >= 0`, `receiveCapacity >= 0`, and `receiveCapacity <= buffer.length - offset` after verifying that offset is within the array. The application limit may even be **smaller** than the remaining physical bytes available.

## 3. How setLength and setData Work

### `setLength(int)`: setting the usable length for sending/receiving

~~~java
packet.setLength(receiveCapacity); // Reset the maximum region before receive.
socket.receive(packet);
int bytesReceived = packet.getLength(); // Actual number of bytes just received.
~~~

*The illustration snippet uses existing variables from the application.*

`setLength(n)` updates the length that the packet uses in the next send or receive operation; it does **not** clear the array and does **not** change the offset. A negative `n` or `n + offset > buffer.length` throws `IllegalArgumentException`. For example, with a 20-byte buffer and offset 4, `setLength(20)` is invalid; `setLength(16)` is the maximum allowed by the physical size.

When reusing a packet for receiving, you should store `receiveCapacity` in a **separate variable**, rather than computing it from the previous `getLength()`. The easiest sequence to verify:

1. Before each `receive`, call `packet.setLength(receiveCapacity)`.
2. Call `socket.receive(packet)`; if a timeout or error occurs, handle the exception.
3. Immediately read `packet.getOffset()`, `packet.getLength()`, `packet.getAddress()`, and `packet.getPort()`, then process/copy the current payload.
4. Only after processing is complete, return to step 1.

**Do not reset before processing the just-received message:** calling `setLength(receiveCapacity)` at that point changes `getLength()`, losing the actual byte count of the previous message.

### `setData(buffer)` and `setData(buffer, offset, length)`

- `packet.setData(newBuffer)` replaces the array, setting **offset = 0** and **length = newBuffer.length**.
- `packet.setData(buffer, offset, receiveCapacity)` simultaneously sets **the array, starting position, and region length**. The same old array can be used to re-establish the receive region if needed.
- Neither is a payload-clearing operation, nor do they turn UDP into a TCP data stream.

If you have configured offset 4 to reserve the front of the buffer, do **not** accidentally call `setData(buffer)` because it will reset the offset configuration to 0. When keeping the same buffer and offset, `setLength(receiveCapacity)` alone is sufficient.

### `receive(packet)` updates the length and sender

After a successful receive, `getLength()` is the number of bytes **stored into the receive region** of the current datagram, and `getAddress()` and `getPort()` are the source of that datagram. If the actual datagram is larger than the allowed window, the excess is **truncated**: the trailing portion will not be received on the next `receive` call.

## 4. Wrong Reset: Using the Previous Message's getLength() as the New Capacity

Suppose after receiving `"A"` we have `packet.getLength() == 1`. A seemingly harmless call:

~~~java
packet.setLength(packet.getLength()); // WRONG: fixes the receive region to 1 byte.
socket.receive(packet);
~~~

*The snippet above is a bug example inside a receive loop, not a standalone runnable program.*

This is an **explicit** operation that sets the receive window to 1 byte. The next datagram `"SECOND"` (6 bytes) can only store its first byte `"S"`; the remaining five bytes **are no longer on the socket to be read later**.

Solution:

~~~java
final int receiveCapacity = 16; // Fixed application policy.
byte[] buffer = new byte[20];
DatagramPacket packet = new DatagramPacket(buffer, 4, receiveCapacity);

while (receiving) {
    packet.setLength(receiveCapacity); // Always restore max 16 bytes.
    socket.receive(packet);
    process(packet.getData(), packet.getOffset(), packet.getLength());
}
~~~

*This is Java pseudocode to explain the algorithm; `receiving`, `socket`, and `process` are defined by the application. Two complete examples are below.*

One detail to state accurately: **simply calling `receive(packet)` again without calling `setLength` can still receive longer datagrams in full on many JDK versions**. Some implementations store the receive-region capacity separately from the resulting `length`. Therefore, one should not claim that "forgetting to reset always causes truncation in every Java/JDK". The easily reproducible bug is calling **`setLength(packet.getLength())`**, `setData(buffer, offset, packet.getLength())`, or accidentally shrinking the receive region. Resetting with the original capacity before each `receive` keeps the rule clear, consistent, and prevents prior operations from skewing the limit.

## 5. Java 17+ Example: Demonstrating Wrong Reset and Correct Reset

The program uses two `DatagramSocket` instances on loopback, requiring no Internet access. The receiver has a 20-byte array, offset 4, and initial capacity 16. It receives `"A"`, then intentionally resets **wrongly** to length 1 and receives `"SECOND"` truncated, then resets **correctly** to 16 and receives `"THIRD"` intact.

Create `PacketReuseDemo.java`:

~~~java
import java.io.IOException;
import java.net.DatagramPacket;
import java.net.DatagramSocket;
import java.net.InetAddress;
import java.net.InetSocketAddress;
import java.nio.charset.StandardCharsets;

public class PacketReuseDemo {
    private static void send(DatagramSocket sender, InetAddress target,
                             int port, String value) throws IOException {
        byte[] data = value.getBytes(StandardCharsets.US_ASCII);
        sender.send(new DatagramPacket(data, data.length, target, port));
    }

    private static String text(DatagramPacket packet) {
        return new String(packet.getData(), packet.getOffset(),
                packet.getLength(), StandardCharsets.US_ASCII);
    }

    public static void main(String[] args) throws IOException {
        InetAddress loopback = InetAddress.getLoopbackAddress();
        try (DatagramSocket receiver =
                     new DatagramSocket(new InetSocketAddress(loopback, 0));
             DatagramSocket sender = new DatagramSocket(0, loopback)) {
            receiver.setSoTimeout(2_000);

            byte[] buffer = new byte[20];
            int offset = 4;
            int receiveCapacity = 16;
            DatagramPacket packet =
                    new DatagramPacket(buffer, offset, receiveCapacity);

            send(sender, loopback, receiver.getLocalPort(), "A");
            receiver.receive(packet);
            System.out.println("first: " + text(packet)
                    + " / " + packet.getLength());

            packet.setLength(packet.getLength()); // Wrong: shrinks receive region to 1.
            send(sender, loopback, receiver.getLocalPort(), "SECOND");
            receiver.receive(packet);
            System.out.println("wrong reset: " + text(packet)
                    + " / " + packet.getLength());

            packet.setLength(receiveCapacity); // Correct: restores 16 bytes.
            send(sender, loopback, receiver.getLocalPort(), "THIRD");
            receiver.receive(packet);
            System.out.println("correct reset: " + text(packet)
                    + " / " + packet.getLength());
            System.out.println("offset retained: " + (packet.getOffset() == offset));
            System.out.println("source port updated: "
                    + (packet.getPort() == sender.getLocalPort()));
        }
    }
}
~~~

Run:

~~~bash
javac PacketReuseDemo.java
java PacketReuseDemo
~~~

Output when the environment allows UDP loopback and datagrams arrive intact:

~~~text
first: A / 1
wrong reset: S / 1
correct reset: THIRD / 5
offset retained: true
source port updated: true
~~~

Note two points: `setLength(packet.getLength())` after the first datagram **sets the new limit to 1**, so `"SECOND"` is truncated. Meanwhile, `setLength(receiveCapacity)` restores 16, so `"THIRD"` is read in full (5 bytes). `getOffset()` remains 4, and `getPort()` after receive is the **sender's** port (different from `receiver.getLocalPort()`, which is the **receiving** port).

`StandardCharsets.US_ASCII` is chosen because the strings in the example contain only ASCII, so the byte count equals the character count and UTF-8 character boundaries do not need to be considered. For Vietnamese strings, use UTF-8 while still checking sizes and decoding according to **actual received bytes**.

## 6. When a Datagram Is Too Large: Using a MAX + 1 Receive Region to Detect It

A datagram of exactly `MAX_PAYLOAD_BYTES` bytes and a datagram **longer than MAX but truncated to MAX** can both result in `packet.getLength() == MAX`. If the application needs to be certain it rejects oversized datagrams, it can allocate **1 extra byte** in the receive region, and then reject when `getLength() > MAX`.

With `MAX = 8`: create a 9-byte receive region. An 8-byte datagram is valid; 9 bytes or more will store at most 9 bytes and be classified as "exceeding 8" for rejection. This approach **does not determine the exact original length** if the datagram is longer than 9 bytes, but it is sufficient to detect a violation of the 8-byte limit.

The application limit is distinct from the physical buffer. If offset is 2 and receiveCapacity is 9, the array must contain at least `2 + 9 = 11` bytes. Do not blindly add 1 if MAX is already near the available limit or if there is a risk of integer overflow when summing.

Create `PacketResetLoopDemo.java`:

~~~java
import java.io.IOException;
import java.net.DatagramPacket;
import java.net.DatagramSocket;
import java.net.InetAddress;
import java.net.InetSocketAddress;
import java.nio.charset.StandardCharsets;

public class PacketResetLoopDemo {
    private static final int MAX_PAYLOAD_BYTES = 8;

    private static void send(DatagramSocket sender, InetAddress address,
                             int port, String message) throws IOException {
        byte[] body = message.getBytes(StandardCharsets.US_ASCII);
        sender.send(new DatagramPacket(body, body.length, address, port));
    }

    public static void main(String[] args) throws IOException {
        InetAddress loopback = InetAddress.getLoopbackAddress();
        try (DatagramSocket receiver =
                     new DatagramSocket(new InetSocketAddress(loopback, 0));
             DatagramSocket sender = new DatagramSocket(0, loopback)) {
            receiver.setSoTimeout(2_000);
            int offset = 2;
            int receiveCapacity = MAX_PAYLOAD_BYTES + 1;
            byte[] buffer = new byte[offset + receiveCapacity];
            DatagramPacket packet =
                    new DatagramPacket(buffer, offset, receiveCapacity);

            for (String outgoing : new String[] {"A", "LONGER", "TOO-LARGE", "B"}) {
                packet.setLength(receiveCapacity);
                send(sender, loopback, receiver.getLocalPort(), outgoing);
                receiver.receive(packet);

                int receivedLength = packet.getLength();
                if (receivedLength > MAX_PAYLOAD_BYTES) {
                    System.out.println("rejected size: " + receivedLength);
                    continue;
                }
                String received = new String(packet.getData(),
                        packet.getOffset(), receivedLength,
                        StandardCharsets.US_ASCII);
                System.out.println("accepted: " + received
                        + " / " + receivedLength);
            }
        }
    }
}
~~~

Run:

~~~bash
javac PacketResetLoopDemo.java
java PacketResetLoopDemo
~~~

Output when loopback packets are delivered in full in turn:

~~~text
accepted: A / 1
accepted: LONGER / 6
rejected size: 9
accepted: B / 1
~~~

`"TOO-LARGE"` has 9 bytes, exceeding MAX 8, so it is rejected. Even if a datagram has 100 bytes, the receive region stores only 9 bytes, and `getLength() == 9` is still enough to reject it. Remember to check `receivedLength` before processing the data and **before handing the shared array off to other tasks**. In real applications, account for memory resources and network datagram limits when choosing MAX.

## 7. Do Not Read the Entire Array: Avoid Stale Data, Wrong Offsets, and Decoding Errors

After the same buffer receives `"LONGER"` (6 bytes) and then receives `"B"` (1 byte), stale bytes may still remain after the `"B"` byte. `receive` does not guarantee clearing the remaining elements in the array.

Wrong way:

~~~java
String wrong = new String(packet.getData(), StandardCharsets.UTF_8);
// Reads the entire array, including the region outside offset and leftover data.
~~~

Correct way:

~~~java
String correct = new String(
        packet.getData(), packet.getOffset(), packet.getLength(),
        StandardCharsets.UTF_8
);
~~~

*These are illustrative snippets inside a class with a `packet` variable; not a standalone program.*

If you need to store the message for later processing, you must copy **the exact slice**:

~~~java
byte[] ownCopy = java.util.Arrays.copyOfRange(
        packet.getData(),
        packet.getOffset(),
        packet.getOffset() + packet.getLength()
);
~~~

`packet.getData()` returns the shared array; when the next `receive` runs, old data is overwritten. If a direct reference to this array is passed to an asynchronous worker without an ownership transfer mechanism, the worker may read mutated data.

Binary payloads should not be converted to a String just for convenient inspection. With UTF-8, a truncated datagram can cut through the middle of a multi-byte character sequence and produce a corrupted decoding result; check framing/length before decoding.

## 8. Separating Receive Information from Buffer Ownership and Sender Address

After `receiver.receive(packet)` succeeds, `packet.getAddress()` and `packet.getPort()` are the **source** of the datagram, not the local socket. On the receiver:
- `receiver.getLocalPort()` is the listening port.
- `packet.getPort()` is the port of the sender that just sent the datagram.
- `packet.getSocketAddress()` is the corresponding source endpoint.

When receiving consecutively from two senders A and B, the same `DatagramPacket` can hold A's metadata and then B's. If processing message A runs asynchronously and reads `packet.getAddress()/getPort()` **after receive B**, it may send the reply to the wrong sender.

For systems with concurrent processing, snapshot **the payload bytes, address, port, and required information** for each message before reusing the packet. When sending a reply, typically create another `DatagramPacket` with a send buffer and the exact destination address/port, avoiding directly reusing the receive packet that still holds old data.

A packet should not have its data region, offset, or length modified concurrently by multiple threads while a receive operation is active. Have one thread own the receive loop, then copy or explicitly transfer ownership of the data to processing threads.

## 9. Common Mistakes When Resetting the Receive Region

| Mistake | Consequence | Fix |
| --- | --- | --- |
| `setLength(packet.getLength())` after receiving a short packet | Limits the next receive to the previous packet's length | `setLength(receiveCapacity)` with an independent capacity |
| `setData(buffer, offset, packet.getLength())` | Resets the receive region too small | Use `setData(buffer, offset, receiveCapacity)` |
| `setData(buffer)` with a non-zero offset | Receive region resets to the start of the array | Use the overload with offset or just `setLength` |
| `setLength(buffer.length)` when `offset > 0` | `IllegalArgumentException` for exceeding the array | Verify `length <= buffer.length - offset` |
| `setLength(receiveCapacity)` before processing the previous result | Overwrites the actual received `getLength` info | Read/copy the result first, reset before the new receive |
| `new String(packet.getData())` | Mixes in stale bytes and bytes outside the receive region | Use `getOffset()` + `getLength()` |
| Enqueueing `packet.getData()` while continuing to receive | Worker sees the array overwritten | Copy the payload or transfer buffer ownership |
| Receiving a packet longer than capacity then calling receive again for the tail | Excess of the datagram was already discarded | Choose sufficient capacity and handle oversize at the protocol level |
| Treating `getLength() == capacity` as proof of truncation | The packet might fit exact capacity | Use a spare byte or additional framing |
| Using `socket.setReceiveBufferSize(...)` to reset the packet | Socket receive queue is not the `DatagramPacket` window | Restore using `setLength`/`setData` |

In particular, do not turn "clearing" a packet into calling `setLength(0)` and forgetting to reset it; then the receive region cannot hold the payload of a non-empty datagram. There is no need to zero out the array before each packet if the application always processes the exact valid range. Clearing the array may only be needed if security policies or avoiding exposure of sensitive contents require it, but it does not replace offset/length control.

## 10. Timeouts, Network Limits, and UDP Testing

`DatagramSocket.receive(packet)` is a **blocking** operation until a datagram arrives or an error occurs. Set `receiver.setSoTimeout(milliseconds)` to avoid waiting indefinitely; expiration throws `SocketTimeoutException`. `IOException`/`SocketException` must be handled, especially when the socket is closed or network issues occur.

UDP **does not guarantee** that datagrams will arrive, arrive in order, be free of duplicates, or be free of errors due to network constraints. The two examples use loopback, sending and then receiving at each step to observe the API; in real systems, datagrams can be lost and the program can time out. If business logic requires reliable delivery, you must design sequence numbers, retries, idempotency, or use an appropriate protocol.

When receiving a datagram larger than `DatagramPacket` allows, data can be truncated **without a dedicated exception reporting the original size**. Do not treat `getLength()` as the true on-the-wire length if the packet may have been truncated. Additionally, `DatagramSocket.setReceiveBufferSize` is only a hint to configure the socket's OS-level receive buffer; it does not alter `packet.getLength()` and does not automatically allocate a large enough array for the application.

Reusing packets helps reduce object allocations, but if processing each datagram is expensive, you still need limits on the number of queued messages, bytes in flight, and receive rate. Optimizing allocation does not automatically guarantee overload protection for the system.

## 11. General Pattern and Principles for Code Review

Skeleton example of a receive loop that processes immediately or passes copied data:

~~~java
final int receiveCapacity = 1024;
byte[] buffer = new byte[receiveCapacity];
DatagramPacket packet = new DatagramPacket(buffer, buffer.length);

for (;;) {
    packet.setLength(receiveCapacity);
    socket.receive(packet);

    int start = packet.getOffset();
    int length = packet.getLength();
    byte[] ownedPayload = java.util.Arrays.copyOfRange(
            packet.getData(), start, start + length
    );
    InetAddress sourceIp = packet.getAddress();
    int sourcePort = packet.getPort();

    handle(ownedPayload, sourceIp, sourcePort);
}
~~~

*This is an illustrative template; `socket`, `handle(...)`, imports, loop termination, exception management, and size controls are needed according to the application. The two examples in sections 5–6 are standalone runnable programs.*

Invariants to maintain:

1. Receive capacity is an **independent configuration value**, not `packet.getLength()` from the previous message.
2. Before receiving, the data region must lie completely within the array and satisfy the protocol maximum.
3. After receiving, only the slice `getOffset()..getOffset()+getLength()` is considered the current payload.
4. Payload and source metadata must be processed/copied before the packet is used for the next receive.
5. Do not infer the original datagram length from a truncated packet, and do not expect the next receive to fetch the remainder.

## 12. Self-Check and Practice

**Question 1.** Buffer of 20 bytes, offset 4, capacity 16. After receiving `"A"`, what are `getLength()` and `getOffset()`? Can you call `setLength(20)`?

Answer: length 1, offset 4; `setLength(20)` is invalid because 4 + 20 > 20. The maximum limit for this region is 16, if policy permits.

**Question 2.** After receiving a 1-byte datagram, you call `packet.setLength(packet.getLength())` and then receive a 6-byte datagram. What happens?

Answer: the explicit call sets the new receive window to 1 byte. The 6-byte datagram is truncated to at most 1 byte, and the remainder cannot be read on a subsequent `receive`.

**Question 3.** Can we state that every JDK will automatically truncate long packets if we simply reuse a packet without calling `setLength`?

Answer: **no**. Some implementations maintain capacity separately from the resulting length. To make intent explicit and avoid accidental changes to the receive region, set the desired capacity before each receive, especially after `setLength`/`setData`.

**Question 4.** Why can decoding `new String(packet.getData())` be wrong when reusing a buffer?

Answer: the method decodes the entire array, including the region outside the offset and leftover bytes from previous datagrams. You must use the actual received offset and length.

**Question 5.** An application accepts at most 8 bytes. Why does a 9-byte receive region help detect datagrams over 8 bytes?

Answer: if 9 bytes are received, we know the datagram exceeded 8; even if the original datagram was longer than 9 and truncated, a result of 9 is still sufficient to reject it. A capacity of 8 cannot distinguish an exact 8-byte packet from a larger one truncated to 8.

**Practice:** modify `PacketReuseDemo` to replace the wrong call with `packet.setLength(receiveCapacity)` and observe `"SECOND"` being read in full (6 bytes). Try changing offset from 4 to 2, set capacity according to the array, and then intentionally call `setLength(buffer.length)` to understand the exception. In `PacketResetLoopDemo`, replace `"LONGER"` with a 20-byte datagram and verify it is still rejected thanks to the 9-byte receive region. Finally, try receiving two consecutive messages, copying the payload before the next receive, and compare that with keeping a reference to `getData()`.
