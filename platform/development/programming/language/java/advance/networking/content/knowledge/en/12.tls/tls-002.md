# Handshake, Certificates, Trust Chains, and TLS Sessions in Java

**Topic:** Java Advance - networking  
**Group:** TLS

When a Java application connects to a service over **TLS** (such as HTTPS or a custom TCP protocol protected by TLS), the two ends cannot simply send application bytes right after the TCP connection is established. They need a **TLS handshake** to negotiate the version and algorithms, authenticate the appropriate identity, derive secret keys, and establish the encryption state. The most common authentication step on the client is verifying the **X.509 certificate**, the **certificate chain** leading to a **trust anchor**, and the **hostname** of the service. After the handshake, a connection has a **TLS state/session** tied to the negotiated protocol and cipher suite; subsequent connections can use **session resumption** if both sides support it.

Four core questions of the lesson:

1. **How does the handshake work?** Client and server negotiate keys, prove possession of the private key, and determine when protected application data exchange begins.
2. **What is a certificate used for?** It binds a public key to an identity and usage permissions, but a certificate appearing in the handshake is **not enough** for the client to trust the server.
3. **How is a certificate chain verified?** The client needs to build a valid certification path to a trust anchor it already trusts, while checking the hostname, validity period, intended usage, and related policies.
4. **What is a TLS session?** It is not synonymous with a TCP socket or an HTTP cookie; a session/connection that has negotiated keys can be continued or resumed according to the mechanisms specific to each TLS version.

**Scope:** explains TLS over TCP with a focus on TLS 1.3, some still-encountered TLS 1.2 differences, and how Java **JSSE** represents handshakes/certificates/sessions. Do not implement cryptographic algorithms yourself and do not disable certificate verification just to "make it work."

## 1. Placing TLS Properly in the Stack

~~~text
Application: HTTP, RPC, or custom TCP protocol
           │   application text / messages / bytes
           ▼
TLS: handshake, peer authentication, key generation, record encryption + integrity
           │   TLS records
           ▼
TCP: byte stream, ordering, and retransmission when needed
           ▼
IP / network / Internet
~~~

TCP by itself does **not** encrypt content and does **not** authenticate the identity of the service. TLS, when configured and verified properly, provides:

- **Confidentiality:** an eavesdropper passively listening on the wire cannot read plaintext application data.
- **Integrity:** application records are protected against undetected modification by the algorithms in use.
- **Authentication:** in the common configuration, the **client authenticates the server**; if using **mutual TLS (mTLS)**, the server also authenticates the client using a certificate.

TLS does not automatically protect data before/after it leaves the TLS endpoint: the application still needs authorization, validation, log control, in-memory secret handling, and other security layers. TLS protects the channel **between two TLS endpoints**, which may be client–reverse proxy rather than client–backend if TLS terminates at the proxy.

A TCP stream can carry TLS via **SSLSocket** or via **SSLEngine** on NIO; **SSLSocket.getInputStream()** and **getOutputStream()** provide application bytes after the TLS layer processes records. Plaintext must not be sent on the same channel before negotiating a TLS upgrade unless a **STARTTLS protocol** defines it very clearly, because an improper upgrade can create a downgrade risk.

## 2. TLS Handshake: Looking at a Full TLS 1.3 Session

This is the **full, certificate-based server authentication** handshake without PSK resumption; many details can change when the server requests a client certificate, when a HelloRetryRequest occurs, or when resumption is used.

~~~text
CLIENT                                               SERVER
   |                                                  |
   | --- ClientHello --------------------------------> |
   |      supported_versions, cipher_suites, key_share,
   |      SNI (if used), ALPN (if used), extensions...
   |                                                  |
   | <--- ServerHello -------------------------------- |
   |        selects TLS 1.3, cipher suite, key_share
   |       [compute shared secret, derive handshake keys]
   |                                                  |
   | <--- EncryptedExtensions ------------------------ |
   | <--- Certificate -------------------------------- |
   | <--- CertificateVerify -------------------------- |
   | <--- Finished ----------------------------------- |
   |                                                  |
   |  [client verifies certificate chain, hostname,    |
   |   signature, Finished, and related policies]     |
   |                                                  |
   | --- Finished -----------------------------------> |
   |                                                  |
   | ===== Application Data (TLS records) <=========> |
   |                                                  |
   | <--- NewSessionTicket (optional, post-handshake)- |
~~~

**Note:** this is a conceptual diagram, not a packet dump containing every extension and state. In TLS 1.3, most handshake messages **after ServerHello are encrypted** with handshake traffic keys. Application data keys are derived according to a separate key schedule. A typical full handshake uses **(EC)DHE** key agreement combined with a signature/certificate algorithm for authentication.

### ClientHello

The client proposes supported TLS versions, cipher suites, and key exchange groups, and sends an appropriate key share. It may also send:

- **SNI (Server Name Indication):** the hostname the client wants to access so the server can select the appropriate certificate/virtual host configuration.
- **ALPN (Application-Layer Protocol Negotiation):** a list of application protocols such as **h2**, **http/1.1**.
- Extensions for signature algorithms, supported groups, key_share, supported_versions, and (if resuming) PSK information.

**ClientHello is not a confirmation that the server is trustworthy.** Unauthenticated information in the handshake needs to be evaluated in the proper context.

### ServerHello and Key Derivation

The server selects a compatible version and algorithms and provides its key share. In a TLS 1.3 full handshake, the two sides compute a shared secret using ephemeral key exchange, then use the TLS 1.3 key schedule (HKDF and intermediate secrets) to derive **traffic keys**. This differs from the misconception that "the server encrypts all content with the RSA public key in the certificate." **The certificate primarily serves authentication**, while traffic is protected by the negotiated/derived symmetric keys.

With ephemeral (EC)DHE, appropriate ephemeral keys provide **forward secrecy** for past session data if the server's long-term key is later compromised, within the security assumptions of the protocol and algorithms. This does not mean every storage/session ticket mistake is harmless.

### Certificate, CertificateVerify, Finished

- **Certificate:** the server sends the appropriate certificate chain (typically **leaf + intermediates**; the root trust anchor usually does not need to be sent).
- **CertificateVerify:** the server signs the relevant transcript data with the private key corresponding to the certificate (in a TLS 1.3 full handshake), thereby proving possession of the matching private key and binding authentication to the handshake.
- **Finished:** both ends verify the consistency/integrity of the handshake transcript based on the derived secrets. These steps prevent handshake tampering and confirm what both ends agreed upon.

The client must **verify the certificate chain and target identity**; simply receiving Certificate or CertificateVerify must not be interpreted as "the server is already trusted." An attacker can generate their own certificate and sign with their own private key; that does not make the certificate trusted by a CA or match the service's hostname.

### When Is Application Data Safe to Use?

With Java **SSLSocket.startHandshake()**, when the call returns normally, the corresponding handshake has completed according to JSSE. The application can read/write through the SSLSocket. Some I/O paths may **automatically initiate the handshake** if startHandshake was not called beforehand, but calling it explicitly helps set validation/timeout configurations before the handshake and handle errors clearly.

TLS 1.3 may have **post-handshake NewSessionTicket** and other mechanisms; "handshake completed" does not mean the connection will never receive further TLS protocol messages.

## 3. How Does TLS 1.2 Differ from TLS 1.3 at a Need-to-Know Level?

| Aspect | TLS 1.3 | TLS 1.2 |
| --- | --- | --- |
| Steps and content | Streamlined handshake on the common path; many handshake messages are encrypted after ServerHello | Has other steps/messages such as ServerKeyExchange, ChangeCipherSpec depending on the cipher suite |
| Common key exchange | Uses (EC)DHE for full handshake with forward secrecy; resumption via PSK | Depends on the cipher suite; historically included RSA key transport and (EC)DHE |
| Cipher suite | Primarily describes AEAD and hash used in the key schedule, e.g., **TLS_AES_128_GCM_SHA256** | Cipher suite typically also encodes key exchange/authentication choices, e.g., names starting with TLS_ECDHE_... |
| Certificate authentication | Certificate + CertificateVerify in a full certificate-based handshake | Depends on the cipher suite's key exchange/authentication type; do not copy the TLS 1.3 diagram verbatim |
| Session resumption | PSK and **NewSessionTicket**; optional 0-RTT mechanism depending on implementation | Session ID or session ticket and abbreviated handshake |
| Security | Removes many weak/obsolete mechanisms | Requires strict protocol/cipher controls if legacy systems must still be supported |

Do **not** configure SSLv3 or TLS 1.0/1.1 for new systems. In modern environments, prefer TLS 1.3; support TLS 1.2 when compatibility is required and policy permits. Using TLS 1.3 does not automatically guarantee correct truststore, domain name, and certificate configuration.

## 4. X.509 Certificates: What Information Is Verified?

A server certificate is typically an **X.509 certificate** signed by the private key of a CA or appropriate issuer. It contains important fields/extensions:

| Attribute | Role | What to Check |
| --- | --- | --- |
| **Subject** | Identity/metadata of the subject, may contain CN | Do not default to using CN instead of SAN for hostname checking |
| **Subject Alternative Name (SAN)** | List of DNS names or IP addresses represented by the certificate | The host/IP of the URL or connected endpoint must match |
| **Subject Public Key Info** | Public key and algorithm of the certificate owner | This public key relates to the signature/proof of private key possession in the handshake |
| **Issuer** | Identity of the entity that issued the certificate | Verify the signature and path to the real issuer, not just string comparison of names |
| **Validity: Not Before / Not After** | Time range during which the certificate is valid | System clock and validity dates must align |
| **Signature Algorithm / Signature** | Issuer's signature over the certificate data | Must verify with the issuer's public key and an algorithm permitted by policy |
| **Basic Constraints** | CA vs. end-entity, path length constraints | Intermediates must be permitted to issue certificates |
| **Key Usage** | Permitted usages of the key | Appropriate for signing/certificate signing per role |
| **Extended Key Usage (EKU)** | Specific purposes such as **serverAuth**, **clientAuth** | Check against the peer and application policy |
| **Serial Number** | Certificate identifier assigned by the issuer | Helps management/tracking/revocation; does not replace hostname verification |

A certificate can be:

- **Leaf/end-entity:** the certificate of the HTTPS/TLS service; typically **CA=false** and has a SAN for the target host.
- **Intermediate CA:** a CA certificate issued by a higher-level CA; signs certificates below it, constrained by Basic Constraints/Key Usage/path length.
- **Root CA:** typically self-signed and selected by the **client's truststore** as a **trust anchor**. The client must trust the root beforehand via a secure distribution/configuration path; the server sending the root does not create trust on its own.

A **public key** is public for anyone to know; the server's **private key** must be protected. Java typically stores the server's private key and certificate chain in a **keystore** (PKCS#12) used by a **KeyManager**. Do not embed private keys in responses, logs, repositories, or public container images.

## 5. Certificate Chain and Trust Path (PKIX)

Example chain:

~~~text
[Leaf] api.example.com
   issuer = Example Intermediate CA
        │ verify leaf signature
        ▼
[Intermediate] Example Intermediate CA
   issuer = Example Root CA
        │ verify intermediate signature
        ▼
[Root] Example Root CA
   trust anchor already present in the client's truststore
~~~

The server usually sends **leaf + necessary intermediates**; the client may already hold the trust anchor and not need the server to send the root. The PKIX verifier checks a valid **certification path** to a configured trust anchor. **Matching Issuer/Subject names are only part of it**: it must check signatures, constraints, key usage, permitted algorithms, validity period, and corresponding policies.

**A certificate chain sent by the server does not mean the chain has been verified.** An untrusted chain is data from the peer; it may be missing an intermediate, have a non-standard order, or contain a certificate not trusted by the client. Verification software may build/validate a path from available certificates, but you should not rely on the system always fetching missing intermediates from the network automatically.

### Example of Two Different Outcomes

- **Client A** has the trust anchor **Example Root CA** and connects to **api.example.com**. The server presents the right leaf + intermediate, signatures/constraints/validity are valid, and SAN contains **api.example.com**: the path can be accepted.
- **Client B** only trusts a different CA or connects using **10.0.0.5** while SAN only contains **api.example.com**: the handshake can fail due to no trust anchor or target name mismatch, even if the server has the right private key.

**A truststore is not "a list of certificates just seen."** It is the explicit selection of trust points that the client accepts. Mixing unverified certificates into the truststore to work around connection errors is **changing the trust policy**, not fixing a protocol error.

### What PKIX/Hostname Verification Does Not Replace

- Checking whether the application actually intends to connect to that endpoint.
- Authorizing the user or client after the handshake succeeds.
- Whether the certificate/service belongs to the expected tenant or deployment environment required by business logic.
- **Revocation** checking policy. CRL/OCSP handling depends on configuration, provider, and environment; do **not** assume by default that JSSE always performs online revocation checking.
- Security of trust anchors, private keys, secrets used to create session tickets, and the certificate issuance/rotation process.

## 6. Trust Anchor, Truststore, Keystore, and Hostname Identity

The most commonly confused concepts are these:

| Concept | What does it hold/provide? | Which side uses it? |
| --- | --- | --- |
| **Keystore** | Private key + certificate chain of the **endpoint itself** (may contain other entries) | Server when presenting its identity; client when using mTLS |
| **Truststore** | Certificates/trust anchors that the endpoint **decides to trust** | Client to verify the server; server when verifying mTLS clients |
| **KeyManager/KeyManagerFactory** | Selects the key pair and certificate chain of **oneself** | JSSE authenticating the local endpoint's identity |
| **TrustManager/TrustManagerFactory** | Verifies the peer's certificate chain against trust policy | JSSE authenticating the peer |
| **SSLContext** | Configures key manager, trust manager, random, and creates TLS sockets/engines | Both sides |
| **SSLParameters** | Configures protocols, ciphers, endpoint identification, SNI/ALPN, and TLS options | Per socket/engine before handshake |

A server having a valid keystore does **not** mean the client will trust it. The client needs a truststore that trusts the appropriate issuer/trust anchor and must verify identity.

### Why Is SAN More Important Than CN?

Suppose a certificate has:

~~~text
Subject: CN=api.example.com
Subject Alternative Name:
  DNS: api.example.com
  DNS: service.internal.example
~~~

A client connecting to **api.example.com** can verify the hostname if the trust chain is valid. A client connecting to **127.0.0.1** will fail validation if the certificate **does not have IP SAN 127.0.0.1**, even if TCP connects and the certificate has a CN naming a service. The fact that Java may have fallback behaviors depending on provider/algorithm is **not** a reason to rely on CN; issuing certificates with the **correct SAN** is the standard approach for new systems.

**Distinguish DNS SAN and IP SAN:** the DNS name **localhost** and the IP address **127.0.0.1** are not the same identity in hostname verification. Include both SANs in the demo certificate if clients may use either access method.

### SNI Is Not Hostname Verification

**SNI** is the name the client sends to the server so the server knows which certificate/virtual host to select. **Hostname verification** is the client's action of comparing the **expected target name** against the identity confirmed by the certificate. SNI can help the server pick the right certificate, but **sending SNI does not mean the certificate has been verified**.

When a client connects by IP literal, some stacks do not send a DNS name in SNI; if the server needs SNI to select a virtual host, you must use the proper hostname or design the architecture accordingly. With HTTPS, the URL host, SNI, SAN, and Host header have distinct roles; never replace certificate verification with setting a header.

### How Is ALPN Different?

**ALPN** is used during the handshake for both sides to negotiate the **application-layer protocol**, such as HTTP/2 (**h2**) or HTTP/1.1. ALPN does not choose a trust anchor and does not verify domain names. **A TLS session can complete its handshake successfully yet the application still fails to find a common protocol**, in which case application-layer negotiation must be handled per contract. In Java JSSE, **SSLParameters.setApplicationProtocols(...)** and **SSLSocket.getApplicationProtocol()** are available when needed; the demo below transfers raw PING/PONG so it does not need ALPN.

## 7. What Is a TLS Session and What Does SSLSession in Java Represent?

A **TLS session** is the negotiated security state/information associated with a handshake: protocol version, cipher suite, peer authentication, and information needed for the connection or resumption depending on version/implementation. Do not equate:

- **TCP connection:** a byte stream with address/port, which can be closed and reopened.
- **TLS connection:** the record layer + keys/traffic secrets of an established handshake over TCP (in this lesson).
- **TLS session/resumption state:** information/mechanisms allowing new TLS connections to be established more efficiently per policy.
- **HTTP session:** cookies/tokens and login state of a web application; not a TLS session.

In Java:

~~~java
// Snippet: socket is an SSLSocket that has completed its handshake.
SSLSession session = socket.getSession();
String version = session.getProtocol();       // Example: TLSv1.3
String cipher = session.getCipherSuite();      // Example: TLS_AES_128_GCM_SHA256
Certificate[] peer = session.getPeerCertificates();
~~~

The snippet above **does not run standalone**; it requires importing **javax.net.ssl.SSLSession**, **javax.net.ssl.SSLSocket**, and **java.security.cert.Certificate**, as well as having an active connected **socket**. **getPeerCertificates()** can throw **SSLPeerUnverifiedException** if the peer has not been authenticated in that context. The **SSLSession** API also provides **getPeerHost()**, **getPeerPort()**, **getId()**, creation/last-accessed timestamps, and other information.

**SSLSession.getId() is not an API that guarantees "this connection was resumed."** Especially with TLS 1.3, session tickets, PSKs, and session objects managed by JSSE/providers should not be inferred by naively comparing session IDs or creation times. If you need to determine resumption for performance analysis, use TLS/provider debug and appropriate metrics, and do not tie business logic to a session ID.

**SSLSession.invalidate()** relates to session/cache reusability according to the provider; it is not equivalent to **SSLSocket.close()** and is not a command that forces all active connections to stop immediately. Managing connection lifecycle and session/cache lifecycle are two separate tasks.

## 8. TLS Session Resumption: Faster, but Understand the Limits

A full handshake requires key exchange and certificate/authentication as configured. **Session resumption** allows client/server to use state established in a previous connection to reduce cost or round trips for a new connection, if the ticket/PSK is still valid and both sides allow it.

### TLS 1.3

1. After a suitable handshake, the server **may** send one or more **NewSessionTicket** messages.
2. The client stores ticket/PSK information according to policy and lifetime.
3. On the next connection, the client can propose **PSK resumption** in ClientHello.
4. The server may accept or reject it. If rejected, a full handshake can still be performed.
5. If accepted, the handshake may **skip resending certificates as in a full handshake**, because authentication is inherited per resumption logic/binding. This does not mean "skipping all security checks" or that a ticket from another service is automatically accepted.

In TLS 1.2, there is **session ID** or **session ticket** with an abbreviated handshake. Message/resumption details differ from TLS 1.3; do not apply the TLS 1.3 diagram directly.

### Does TLS 1.3 Always Use 0-RTT?

**No.** TLS 1.3 defines an **early data (0-RTT)** mechanism under suitable resumption conditions, but it is a separate feature and is not automatically enabled just because an application uses TLS 1.3. Early data carries **replay risks** and different authentication/freshness guarantees than normal application data; do not use it for non-idempotent operations (money transfers, order creation, state mutations) unless the application and server are specifically designed with appropriate anti-replay protections.

### Resumption and Real-World Performance

- Secure policies are needed for storing session tickets/PSKs, key rotation, and lifetime limits.
- Caching is often tied to **SSLContext** or the provider; creating a new SSLContext per connection can reduce opportunities to reuse state, though reusing the same context does **not** guarantee a session will definitely be resumed.
- The client must verify the right endpoint before treating it as a trusted source; resumption must not become a way to bypass endpoint identity policy.
- When the server changes certificates, key material, session ticket policy, or restarts, resumption behavior can change.
- **Connection pooling** and **TLS session resumption** are two different optimizations: reusing **the same TLS connection** avoids creating a new connection altogether; resumption optimizes the **handshake of a new connection**.

## 9. Java JSSE: Which APIs Are Used to Build the Handshake?

The Java ecosystem provides **Java Secure Socket Extension (JSSE)**. Core components:

~~~text
                              KeyStore server.p12
                       (private key + certificate)
                                    │
                           KeyManagerFactory
                                    │
                                    ▼
Server code ─────────────── SSLContext(server) ──► SSLServerSocket/SSLSocket
                                                                    │
                                                         TLS handshake
                                                                    │
Client code ─────────────── SSLContext(client) ──► SSLSocket  ◄───────┘
                                    ▲
                           TrustManagerFactory
                                    │
                            client-trust.p12
                           (trusted certificate)
~~~

- **KeyStore** can be **PKCS12** (commonly used in modern Java). The KeyStore API manages entries; truststores can also use the KeyStore format.
- **KeyManagerFactory** reads the identity key and chain for the endpoint you control.
- **TrustManagerFactory** uses the client/server's trust anchors/policy to verify the peer's chain. For applications with advanced requirements, an appropriate TrustManager can be configured, but **do not write an "accept all" TrustManager**.
- **SSLContext** creates **SSLSocketFactory / SSLServerSocketFactory** or **SSLEngine**.
- **SSLParameters** configures TLS protocols, cipher suites, hostname/endpoint identification, ALPN, etc.
- **SSLSession** exposes metadata after a successful handshake.

### Important: Raw SSLSocket Should Not Be Assumed to Verify Hostnames Automatically

When creating a raw **SSLSocket**, you need to set appropriate **endpoint identification** **before the handshake**:

~~~java
// Snippet: client is a new SSLSocket, not yet handshaked.
SSLParameters params = client.getSSLParameters();
params.setEndpointIdentificationAlgorithm("HTTPS");
client.setSSLParameters(params);
client.startHandshake();
~~~

This enables JSSE to verify the endpoint identity according to HTTPS rules, suitable for checking DNS names or IP SANs in a TLS-over-TCP example. For custom TLS protocols, you must choose the proper peer identification rule required by the protocol (never omit it). High-level HTTP APIs like **java.net.http.HttpClient** manage many HTTPS steps for you according to their configuration; raw SSLSocket is lower-level and requires more careful implementation.

**Do not** resolve domain name errors using **setEndpointIdentificationAlgorithm(null)** or a TrustManager that always trusts certificates. Doing so allows an attacker with any certificate to perform a MITM attack even though the data is still "encrypted."

## 10. Java 17+ Demo: Creating Test Certificates, Truststore, and a Real TLS 1.3 Handshake

This is a **self-contained loopback example** runnable on JDK 17+. It uses **keytool** to generate a **self-signed certificate for the demo**, exports the public certificate, imports that certificate into a **client truststore**, and then creates two separate **SSLContext** instances for server/client. The client enables **HTTPS endpoint identification** and connects to IP **127.0.0.1**, which is present in the certificate's **SAN**. Both sides complete a TLS 1.3 handshake, then exchange PING/PONG over the encrypted channel.

**Important limitation:** the demo configuration **does not simulate a multi-tier public CA chain**. The client's truststore explicitly trusts the server's self-signed certificate directly. That illustrates an **explicit trust anchor** and **hostname verification**, whereas real systems should use certificates issued by an appropriate CA/PKI, send the full intermediate chain, manage keys, and test the lifecycle. The password **changeit** is only for learning environments—**do not use it in production, and do not commit private keys/keystores**.

### 10.1. Creating Server Identity and Client Trust

In an empty directory, use the JDK's **keytool**. The commands below are written one per line so they can run in any shell with keytool on PATH (Windows PowerShell or Linux/macOS shell; keytool argument syntax is the same):

~~~bash
keytool -genkeypair -alias server -keyalg RSA -keysize 2048 -sigalg SHA256withRSA -validity 30 -dname "CN=localhost, OU=Demo, O=Learning, C=VN" -ext "SAN=DNS:localhost,IP:127.0.0.1" -storetype PKCS12 -keystore server.p12 -storepass changeit -keypass changeit -noprompt
keytool -exportcert -rfc -alias server -keystore server.p12 -storepass changeit -file server-cert.pem
keytool -importcert -noprompt -alias demo-server -file server-cert.pem -keystore client-trust.p12 -storetype PKCS12 -storepass changeit
~~~

Meaning:

- Command 1 generates a 2048-bit RSA key pair and **server.p12** containing the **private key + self-signed certificate** (30 days), with **DNS SAN:localhost** and **IP SAN:127.0.0.1**. RSA and this short validity are for demo purposes only; real systems choose appropriate algorithms/PKI policies.
- Command 2 exports the **public certificate** in PEM format. This is **not the private key**.
- Command 3 creates/imports **client-trust.p12**: the client will trust the imported certificate because we **explicitly distributed** it out-of-band. This is not something to do automatically with certificates from untrusted servers.
- Knowing the keystore password does **not** verify the certificate. The client uses the trust manager **and** endpoint identification to decide whether to trust the peer.

You can inspect the certificates:

~~~bash
keytool -printcert -file server-cert.pem
keytool -list -v -keystore client-trust.p12 -storepass changeit
~~~

When inspecting, look for Subject, Issuer, **SubjectAlternativeName**, validity period, and fingerprint. Do not share **server.p12** or passwords protecting private keys on public channels.

### 10.2. TlsHandshakeDemo.java Program

~~~java
import java.io.DataInputStream;
import java.io.InputStream;
import java.net.InetAddress;
import java.net.InetSocketAddress;
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.Path;
import java.security.KeyStore;
import java.security.cert.X509Certificate;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.concurrent.TimeUnit;
import javax.net.ssl.*;

public class TlsHandshakeDemo {
    private static KeyStore loadStore(Path path, char[] password) throws Exception {
        KeyStore store = KeyStore.getInstance("PKCS12");
        try (InputStream in = Files.newInputStream(path)) {
            store.load(in, password);
        }
        return store;
    }

    private static SSLContext serverContext(Path path, char[] password) throws Exception {
        KeyManagerFactory kmf = KeyManagerFactory.getInstance(
                KeyManagerFactory.getDefaultAlgorithm());
        kmf.init(loadStore(path, password), password);
        SSLContext context = SSLContext.getInstance("TLS");
        context.init(kmf.getKeyManagers(), null, null);
        return context;
    }

    private static SSLContext clientContext(Path path, char[] password) throws Exception {
        TrustManagerFactory tmf = TrustManagerFactory.getInstance(
                TrustManagerFactory.getDefaultAlgorithm());
        tmf.init(loadStore(path, password));
        SSLContext context = SSLContext.getInstance("TLS");
        context.init(null, tmf.getTrustManagers(), null);
        return context;
    }

    public static void main(String[] args) throws Exception {
        if (args.length != 3) {
            throw new IllegalArgumentException(
                    "Use: java TlsHandshakeDemo server.p12 client-trust.p12 password");
        }
        char[] password = args[2].toCharArray();
        SSLContext serverContext = serverContext(Path.of(args[0]), password);
        SSLContext clientContext = clientContext(Path.of(args[1]), password);

        InetAddress loopback = InetAddress.getByName("127.0.0.1");
        SSLServerSocketFactory factory = serverContext.getServerSocketFactory();
        try (SSLServerSocket listener = (SSLServerSocket)
                factory.createServerSocket(0, 10, loopback)) {
            listener.setEnabledProtocols(new String[] {"TLSv1.3"});
            int port = listener.getLocalPort();
            ExecutorService executor = Executors.newSingleThreadExecutor();
            try {
                Future<String> serverRead = executor.submit(() -> {
                    try (SSLSocket peer = (SSLSocket) listener.accept()) {
                        peer.setEnabledProtocols(new String[] {"TLSv1.3"});
                        peer.setSoTimeout(5_000);
                        peer.startHandshake();
                        byte[] incoming = new byte[4];
                        new DataInputStream(peer.getInputStream()).readFully(incoming);
                        peer.getOutputStream().write(
                                "PONG".getBytes(StandardCharsets.US_ASCII));
                        peer.getOutputStream().flush();
                        return new String(incoming, StandardCharsets.US_ASCII);
                    }
                });

                try (SSLSocket client = (SSLSocket)
                        clientContext.getSocketFactory().createSocket(
                                "127.0.0.1", port)) {
                    client.setEnabledProtocols(new String[] {"TLSv1.3"});
                    client.setSoTimeout(5_000);
                    SSLParameters parameters = client.getSSLParameters();
                    parameters.setEndpointIdentificationAlgorithm("HTTPS");
                    client.setSSLParameters(parameters);
                    client.startHandshake();

                    SSLSession session = client.getSession();
                    X509Certificate leaf =
                            (X509Certificate) session.getPeerCertificates()[0];
                    System.out.println("protocol=" + session.getProtocol());
                    System.out.println("endpointIdentification=" +
                            client.getSSLParameters().getEndpointIdentificationAlgorithm());
                    System.out.println("peerCertificatePresent=" + (leaf != null));
                    System.out.println("peerSubjectLocalhost=" +
                            leaf.getSubjectX500Principal().getName().contains("CN=localhost"));

                    client.getOutputStream().write(
                            "PING".getBytes(StandardCharsets.US_ASCII));
                    client.getOutputStream().flush();
                    byte[] response = new byte[4];
                    new DataInputStream(client.getInputStream()).readFully(response);
                    System.out.println("clientReceived=" +
                            new String(response, StandardCharsets.US_ASCII));
                }
                System.out.println("serverReceived=" +
                        serverRead.get(5, TimeUnit.SECONDS));
            } finally {
                executor.shutdownNow();
            }
        }
    }
}
~~~

The code above uses **one JVM with two endpoints** over TCP loopback. In a real application, the server and client are usually two separate processes/machines. **TlsHandshakeDemo** accepts **two paths to PKCS12 files** and a **demo password** via arguments; for simplicity, command-line passwords can appear in process listings/shell history, so do not use this approach to pass production secrets.

### 10.4. Reading the Results Accurately

1. **Server SSLContext** uses **KeyManagerFactory** to load the key pair + certificate from **server.p12**. The certificate must have its **matching private key** for the server to prove its identity during the handshake.
2. **Client SSLContext** uses **TrustManagerFactory** initialized from **client-trust.p12**, meaning the client only trusts the trust anchors configured there. If client-trust.p12 lacks the matching certificate, the demo will fail at certificate verification.
3. **SSLServerSocket** binds to **127.0.0.1:0**; the OS assigns an ephemeral port, and the client uses that actual port. This is only for the loopback demo; port 0 is not a special TLS feature.
4. Both sides enable **TLSv1.3** and call **startHandshake()** explicitly. If the environment does not support the protocol or the certificate/policy is incompatible, the handshake throws an exception instead of printing all the success lines.
5. The client enables **setEndpointIdentificationAlgorithm("HTTPS")** before the handshake. The demo certificate has SAN **IP:127.0.0.1**, matching the address the client connects to; **peerSubjectLocalhost=true** only checks Subject CN to demonstrate the getter and is **not** the primary hostname verification step.
6. **session.getProtocol()** returns **TLSv1.3**. **session.getPeerCertificates()** shows the chain presented by the peer; calling the getter does not replace the TrustManager and endpoint identification that ran during the handshake.
7. The client only sends **PING** after the handshake succeeds; both read **exactly 4 bytes** using **DataInputStream.readFully(...)** and the server replies **PONG** over the **SSLSocket** stream (already protected by TLS).
8. **try-with-resources** closes the sockets. A correct handshake does not automatically solve framing for every protocol; real requests still need length prefixes, delimiters, or an appropriate parser.

**Why not print a fixed cipher suite and fingerprint?** The cipher suite can vary by JDK and configuration, and the certificate fingerprint changes whenever keytool generates a new key pair. The demo only prints values that are stable under the test configuration. You can also inspect **session.getCipherSuite()**, **leaf.getNotAfter()**, SAN, and protocol when studying further, but do not treat variable values as fixed expected stdout.

## 11. Experiencing Errors to Understand Trust and Identity

You can experiment in a **private learning environment** and observe:

### Case A: Client Does Not Trust the Certificate

Keep **server.p12** but use an empty client-trust.p12 or one containing an unrelated CA/certificate. The client cannot find a valid trust path; the handshake fails, typically with an **SSLHandshakeException**-family error and a cause involving trust path / validator / trust anchor. The exact message depends on the JDK/provider and actual failure.

**Proper fix:** issue certificates from an appropriate PKI, install the verified trust anchor, or configure the truststore properly. **Do not** create a TrustManager that always returns success.

### Case B: Hostname/IP Mismatch

Regenerate the certificate with only **DNS SAN:localhost**, while the client still connects to **127.0.0.1** and keeps endpoint identification enabled. The client may reject it with a message like **No subject alternative names matching IP address...** or similar.

**Proper fix:** use a valid hostname present in SAN and connect via that hostname, or issue a certificate with the right **IP SAN** if an IP literal is genuinely required. Do not remove endpoint identification to bypass the error.

### Case C: Expired Certificate or Skewed Clock

If the system time falls outside **Not Before / Not After**, the certificate may be invalid under verification policy. Adding the certificate to the truststore does not automatically fix all expiration issues; depending on how trust anchors are configured and path validation policy, understand the exact error reported. Rotate certificates on schedule and synchronize system clocks.

### Case D: Server Sends a Chain Missing an Intermediate

In a multi-tier CA deployment, if the server only sends the leaf and the client lacks the intermediate needed to build the path, verification can fail even if the root CA is trusted. The server needs to configure the **appropriate full chain**, not just the leaf. Do not assume the client will always fetch/read intermediates from the Internet.

### Case E: Server and Client Have No Common Version/Cipher

The handshake can fail with errors like **protocol_version**, **handshake_failure**, or **no cipher suites in common** depending on the situation. Check TLS versions, cipher suites, signature algorithms, key types, and security policies on both ends; do not enable weak protocols just to fix an error.

## 12. Mutual TLS (mTLS): When the Server Also Authenticates the Client

In common one-way TLS, the **client authenticates the server**, while the server may authenticate the user via cookies/tokens or another application mechanism. With **mTLS**, the server requests a **client certificate** and verifies it using a trust manager/trust anchors for client identities.

~~~text
One-way TLS:
client -- verifies server certificate --> server
server -- does not necessarily verify client certificate

mTLS:
client -- verifies server certificate --> server
client <-- server requests and verifies client certificate -- server
~~~

With **SSLServerSocket**:

~~~java
// Snippet: listener is an SSLServerSocket with an appropriate SSLContext and trust manager.
listener.setNeedClientAuth(true); // Server requires the client to present a certificate.
~~~

**setNeedClientAuth(true)** differs from **setWantClientAuth(true)**: need requires client authentication by policy, whereas want only requests it when possible. The server must have a **TrustManager** for client certificates and the client must have a **KeyManager** with the appropriate private key/certificate. If the server enables needClientAuth without the right trust anchor/policy, or the client lacks an appropriate certificate, the handshake can fail.

**A client certificate does not automatically grant access to every API.** After TLS authentication, the application still needs to map the authenticated identity to a service account, tenant, role, or scope and perform authorization for each operation. Issuing any certificate from a shared CA should not default to admin privileges.

## 13. SSLEngine and Asynchronous Handshake in NIO

With **SSLSocket**, JSSE performs the handshake and record I/O over streams. With **SSLEngine**, the application must manage **ByteBuffer**, **wrap()/unwrap()**, network I/O, and the state machine. This is especially important when combined with **Selector**, because an OP_READ or OP_WRITE event only indicates **socket** readiness, not "TLS handshake completed."

Common handshake states from **SSLEngineResult.HandshakeStatus**:

| State | Practical Meaning |
| --- | --- |
| **NEED_WRAP** | The engine needs to produce TLS records; the application calls **wrap()**, then writes network bytes |
| **NEED_UNWRAP** | The engine needs more network TLS bytes; the application calls **unwrap()** to process them |
| **NEED_TASK** | Delegated tasks need to run, such as cryptographic/certificate work by the provider |
| **FINISHED** | A wrap/unwrap call reports that the handshake process has just completed |
| **NOT_HANDSHAKING** | The engine is currently not performing a handshake |

Wrap/unwrap results also have a **Status** such as **OK**, **BUFFER_UNDERFLOW**, **BUFFER_OVERFLOW**, or **CLOSED**. For example, when the network delivers only half of a TLS record, **BUFFER_UNDERFLOW** is normal; the application must retain unprocessed bytes and read more. **BUFFER_OVERFLOW** requires sufficient capacity in the output/application buffer. **NEED_TASK** must not be skipped; continuing to wrap/unwrap in the wrong state can stall the handshake.

~~~text
SocketChannel + Selector
  ├─ OP_READ ready → attempt to read encrypted bytes into netIn
  │                     → SSLEngine.unwrap(netIn, appOut)
  │                     → check status, handshake status, buffers
  ├─ NEED_WRAP → SSLEngine.wrap(appIn, netOut)
  │                → OP_WRITE when netOut has pending encrypted bytes
  └─ delegated tasks / handshake transitions / close_notify
~~~

**This is a conceptual diagram, not complete SSLEngine code.** A production-ready implementation must manage record boundaries, buffer resources, close_notify, timeouts, partial reads/writes, delegated tasks, ALPN/identity policy, and application message framing. Do not treat **SocketChannel.isConnected()** or **SelectionKey.isWritable()** as successful TLS authentication. Handshake completion is determined by the TLS state machine and policy.

## 14. TLS Records, close_notify, and Session Lifecycle

After the handshake, application data is sent as **TLS records**. TCP remains a byte stream: a single read may receive a partial TLS record or multiple TLS records; JSSE handles TLS framing at the lower layer, but does **not** automatically handle application message framing.

TLS has a **close_notify** message to signal a controlled end of TLS traffic. Closing TCP abruptly is not necessarily a proper TLS close; if a protocol needs to detect truncated data, it must handle close_notify/EOF and message boundaries appropriately. In particular, do not assume **TCP EOF** by default means "the final message was complete and valid" for every protocol.

**Do not confuse:**

- **TLS close** with **SSLSession.invalidate()**.
- **NewSessionTicket** with an application login token.
- **CertificateVerify** in TLS 1.3 with an application confirming a business transaction.
- **Successful handshake** with the business response definitely having been processed.
- **Resumption** with keys/certificates always being re-verified via a full handshake on every connection: authentication and policy are inherited according to TLS/provider mechanisms, so ticket/cache lifecycles must be controlled.

## 15. Safe Operations: Chains, Time, Policies, and Observability

### Checklist for Servers

1. Have the matching **private key + leaf certificate + intermediate chain**, and verify the keystore/chain file and alias?
2. Does the certificate have the **correct SAN** for the hostname/IP clients use? Does it have **EKU serverAuth**, appropriate Key Usage, and signature policy?
3. Are the private key and keystore stored securely, with restricted read permissions, and not committed to Git or logged?
4. Does the server enable only TLS versions/cipher suites matching the security baseline, ensuring intentional compatibility?
5. Does the server return the right certificate for **SNI** and virtual host configuration?
6. Is the certificate unexpired, with rotation/renewal and trust path error monitoring in place?
7. If using mTLS, is there a TrustManager and a policy mapping client identity → authorization?
8. Are handshake/idle timeouts, resource limits, concurrent connection limits, and cleanup configured?
9. If TLS termination happens at a reverse proxy, is it clear which TLS endpoint is responsible for identity/authentication?

### Checklist for Clients

1. Using the **actually expected** hostname/IP of the service, not an arbitrary name taken from an untrusted source?
2. Have the right truststore/trust anchors, without adding an unfamiliar certificate just because a handshake failed?
3. Is endpoint identification enabled when using **raw SSLSocket**? Does SAN match the DNS/IP the client connects to?
4. Do you distinguish **PKIX trust path**, **hostname mismatch**, **certificate expired**, **protocol/cipher mismatch**, and **I/O timeout** errors?
5. Never configure a TrustManager that trusts every peer or a HostnameVerifier that always returns true?
6. Have data size limits, timeouts, EOF/TLS close handling, and protocol framing?
7. When using mTLS, does the KeyManager have the right client identity, and does the server trust the client's issuer?
8. Does the session ticket/resumption policy align with security requirements, key rotation, and observability?

### Observing Errors with JSSE Debug

In a test environment you control, Java can emit TLS logs:

~~~bash
java -Djavax.net.debug=ssl,handshake -cp . TlsHandshakeDemo server.p12 client-trust.p12 changeit
~~~

Logs can show ClientHello, ServerHello, certificate chains, TLS alerts, algorithms/extensions, and failure points. **Do not enable verbose debug logging indiscriminately in production**: logs can contain sensitive information about systems, certificates, server names, and connection behavior; use controlled logging and redaction. You can use **keytool -printcert** to inspect public certificate contents without needing the private key.

**Common errors:**

| Symptom | Possible Cause | Diagnostic Direction |
| --- | --- | --- |
| **PKIX path building failed** | Missing trust anchor or missing intermediate | Inspect peer chain, truststore, issuer, and path validation |
| **No subject alternative names matching...** | Accessed host/IP is not in SAN | Compare target endpoint with SAN; check SNI separately |
| **CertificateExpiredException** | Certificate expired, or skewed clock | Check NotAfter, system time, and renewal schedule |
| **handshake_failure / protocol_version** | Incompatible version, cipher, signature algorithm, or auth config | Check negotiated parameters and JSSE debug |
| **bad_certificate / certificate_required** | Peer certificate rejected or missing when mTLS is required | Check client/server cert chains, truststore, needClientAuth |
| **SSLException after TCP connect** | TCP connected but TLS handshake/record failed | Do not equate TCP connect with TLS ready |
| **Session not resumed** | Incompatible ticket/PSK, changed policy/provider/cache/timeout | Check TLS debug/metrics; do not infer from SSLSession.getId alone |

## 16. Misconceptions to Avoid

- **"Having the padlock icon means the server's business logic is definitely trustworthy."** No. TLS authenticates the endpoint and protects the channel as configured; a valid server can still be buggy/compromised or serve unwanted content.
- **"Every self-signed certificate is trustworthy because it has a valid signature on itself."** No. Self-signing only proves the corresponding private key signed the certificate; the client needs an independent trust decision.
- **"If the server sends the root CA, the client will trust that root."** No. The root must already be in the client's trust policy (or securely distributed through another trusted process).
- **"The certificate has the right CN, so SAN doesn't matter."** Do not rely on CN; issue a SAN matching the DNS/IP the client actually uses.
- **"With SNI present, hostname verification isn't needed."** Wrong. SNI is for certificate selection; the client still needs to verify identity.
- **"Adding every seen certificate to the truststore is the right way to fix PKIX errors."** Wrong. That expands the set of trust anchors and can break trust boundaries.
- **"The certificate is used to encrypt every application byte with the server's public key."** Wrong model for TLS 1.3; traffic keys are primarily symmetric keys derived from the key schedule.
- **"TLS 1.3 session resumption always sends a new certificate on every connection."** Not necessarily when PSK resumption is accepted.
- **"TLS 1.3 always enables 0-RTT automatically."** No. 0-RTT is a separate capability with replay risks and activation conditions.
- **"Equal SSLSession.getId() values are sufficient proof that resumption occurred."** There is no portable guarantee for that inference.
- **"A successful startHandshake() call means API authorization is complete."** No. TLS authentication and application authorization are two separate layers.
- **"A successful handshake means the response has already been processed."** No. The application protocol needs independent confirmation and timeouts.

## 17. Self-Check Exercises

1. Draw the message order of a **TLS 1.3 full handshake with certificate-based server authentication** from ClientHello to application data. At which step do handshake traffic keys begin to be derived? Why can Certificate/CertificateVerify be sent and yet the client still rejects them?
2. Distinguish **leaf certificate**, **intermediate CA**, and **root trust anchor**. If the server only sends the leaf while the client has the root, can a chain always be built? Why or why not?
3. A certificate has SAN **DNS:api.example.com** while the client connects to **192.0.2.10**. Does importing the right root CA into the truststore automatically solve the hostname mismatch?
4. State the differences between **SNI**, **ALPN**, **hostname verification**, and **PKIX path validation**. In Java raw SSLSocket, where is endpoint identification configured?
5. Run the demo, then remove the trusted certificate from the client truststore. Observe the handshake failure. Next, regenerate the certificate with a SAN that excludes **127.0.0.1** and keep endpoint identification enabled to inspect the identity error.
6. Why are **SSLSession.getProtocol()**, **getCipherSuite()**, and **getPeerCertificates()** useful when debugging, while **getId()** is not a reliable rule to conclude TLS 1.3 resumption?
7. If the server requires mTLS, what roles must the **client keystore** and **server truststore** play? Does a valid client certificate automatically grant admin privileges?
8. For a money-transfer application, why can't 0-RTT be enabled solely to reduce latency while ignoring replay risks? What safer solutions exist, such as idempotency keys and server-side replay protection?
9. When using **SSLEngine** on a SocketChannel, why does an **OP_READ** not mean the handshake is finished? List NEED_UNWRAP, NEED_WRAP, NEED_TASK, and the BUFFER_UNDERFLOW status.
10. A certificate will expire in a few days. What factors must renewal and deployment coordinate: SAN, chain, private key, trust anchors, server restart/hot reload, and monitoring?

**Summary:** The **handshake** negotiates protocol/keys and authenticates identity; an **X.509 certificate** carries a public key along with identity/intended usage; the **certificate chain** must be verified to a **trust anchor** trusted by the client **and** match the endpoint's hostname; a **TLS session** reflects security state and may support **resumption** depending on version/policy. In Java, coordinate **SSLContext + KeyManager/TrustManager + SSLParameters + SSLSocket/SSLEngine + SSLSession**, never disable peer verification, and never confuse TLS authentication with business-level authorization.
