# Datagram Boundaries vs. TCP Byte Streams

## 1. Learning Objectives

In Java networking, one of the most important differences between UDP and TCP lies not in the syntax of �DatagramSocket� or �Socket�, but in the **unit of application data received**:

- **UDP is a datagram-oriented (message-oriented) protocol.** A single datagram send produces a distinct message unit. If the datagram is delivered to the application, the receive operation retrieves **one datagram**, with its boundary intact; it does not automatically merge the payloads of two datagrams into a stream.
- **TCP is a byte-stream protocol.** TCP provides an ordered sequence of bytes over a connection, **without preserving the boundaries of �write(...)� calls**. A single �read(...)� may receive fewer, the same number of, or more bytes than a single write on the other side, within the buffer limit and the bytes currently available.

This distinction determines how you design protocols, buffers, parsers, timeouts, error handling, and tests. In this lesson, we will practice Java 17+ with UDP datagrams, demonstrate truncated buffers, and then build framing for TCP using a length field.

After this lesson, you should be able to explain:
1. Why �send(A)� followed by �send(B)� in UDP is not equivalent to �write(A)� followed by �write(B)� in TCP.
2. Why �DatagramPacket.getLength()� differs from �getData().length� and what happens when the receive buffer is too small.
3. Why TCP requires **application-level framing** such as length-prefix, delimiter, or fixed-size records.
4. How to handle **partial reads**, EOF, binary payloads, UTF-8, and the risks when a connection is slow or drops mid-message.
5. Why datagram boundaries **do not** guarantee that UDP delivers messages reliably, in order, or without duplicates.

| Question | UDP (datagram) | TCP (byte stream) |
| --- | --- | --- |
| Unit the app sends via API | One datagram containing a byte payload | Bytes appended to the stream |
| Is the boundary between two sends preserved? | Yes, at the datagram level if delivered | No, protocol framing is required |
| What does a typical receive retrieve? | One datagram, up to the buffer capacity | An available amount of bytes, not message-aligned |
| What if the receive buffer is too small? | The datagram is **truncated**; the excess of that datagram is discarded | Unread bytes **remain in the stream** for subsequent reads |
| Is ordering guaranteed? | No | Yes, by byte order within an active connection |
| Is complete, duplicate-free delivery guaranteed? | No | TCP detects and retransmits losses to provide a reliable byte stream within the connection; the application must still handle connection failures |
| Is there an EOF concept? | No stream-style EOF; a 0-byte datagram can be received | �read() == -1� when the peer closes its sending side and all bytes have been read |
| Typical Java APIs | �DatagramSocket�, �DatagramPacket�, �DatagramChannel� | �Socket�, �InputStream�, �OutputStream�, �SocketChannel� |

**Note:** "one datagram = one message" only holds at the **UDP transport layer**. An application protocol may intentionally place multiple records into **a single** datagram or split one large message across **multiple** datagrams; in that case, the application must format and decode them itself.

## 3. How Are Datagram Boundaries Actually Preserved?

UDP has a header containing source port, destination port, length, and checksum. The length field tells the receiver which payload belongs to **the same** UDP datagram.

Suppose the sender calls:

���text
send([0x41, 0x42])      # datagram 1 = "AB"
send([0x43, 0x44, 0x45])# datagram 2 = "CDE"
���

If both reach the receiver, the application gets two separate datagrams with two payloads, �AB� and �CDE�. UDP **does not** merge them into a single �ABCDE� datagram just because they share the same source/destination port. Conversely, a single datagram is not spread across two �receive� calls to fetch the remaining bytes. Note that the operating system may use multiple IP packets (fragments) to carry **one** large UDP datagram; if IP reassembly succeeds, the application still receives **one** datagram, not individual IP fragments.

A UDP datagram can:
- **Arrive exactly once:** the common case.
- **Be lost:** the receiver has no data to read; only a timeout or higher-level logic detects the missing packet.
- **Arrive out of order:** the receiver must not assume the �send� order at endpoints.
- **Be duplicated:** a message ID must be used if the application needs deduplication.
- **Be truncated at the receive buffer:** the datagram arrived, but the part of the payload that does not fit in the buffer is discarded; there is no subsequent �receive� call to fetch the "second half."

**There is no UDP stream buffer holding the remainder of a truncated datagram.** Treat this as the most important design property when porting code from TCP to UDP or vice versa.

## 4. Java �DatagramSocket� and �DatagramPacket�

Java 17 provides �java.net.DatagramSocket� to send/receive datagrams and �java.net.DatagramPacket� to describe both the buffer and the endpoint.

On the sending side:

���java
byte[] payload = "CAT".getBytes(StandardCharsets.UTF_8);
DatagramPacket packet = new DatagramPacket(
        payload, payload.length, destination);
socket.send(packet);
���

This is a **code snippet**, requiring an existing �DatagramSocket socket� and �InetSocketAddress destination�; import �java.net.*�, �java.nio.charset.StandardCharsets�. Each �send(packet)� call requests sending one datagram containing �payload.length� bytes, with no guarantee that it will reach the peer.

On the receiving side:

���java
byte[] buffer = new byte[1024];
DatagramPacket packet = new DatagramPacket(buffer, buffer.length);
socket.receive(packet);

int offset = packet.getOffset();
int length = packet.getLength();
String message = new String(packet.getData(),
        offset, length, StandardCharsets.UTF_8);
���

Distinguish three pieces of information:
- �packet.getData().length� is the **capacity of the entire buffer array** (here 1024), not the number of bytes received.
- �packet.getOffset()� is the starting position of the payload in the array.
- �packet.getLength()� **after receiving** is the length of the data placed into the packet/buffer; for a datagram longer than the allowed capacity, this is the **truncated** length, not the original datagram size.

Therefore, **do not** decode the entire �new String(packet.getData())�. The remainder of the array may be all zeros or contain stale data, which will cause the parser to misinterpret the message.

After �receive�, the packet also provides �getAddress()� and �getPort()� of the sender. A single UDP socket can receive datagrams from **multiple** different senders unless restricted by �connect� or another policy; you should distinguish which peer a message belongs to and avoid mixing messages together.

## 5. Runnable Java 17+ Example: Each Datagram Is One Receive

This example uses the IPv4 loopback �127.0.0.1� and an OS-assigned ephemeral port (bind port �0�). It does not require an external Internet server. The sender sends packets one by one, and the receiver calls �receive� immediately after each send to demonstrate boundaries.

Save as �UdpBoundaryDemo.java�:

���java
import java.io.IOException;
import java.net.DatagramPacket;
import java.net.DatagramSocket;
import java.net.InetAddress;
import java.net.InetSocketAddress;
import java.nio.charset.StandardCharsets;

public class UdpBoundaryDemo {
    private static void send(DatagramSocket socket,
                             InetSocketAddress target, String message)
            throws IOException {
        byte[] bytes = message.getBytes(StandardCharsets.UTF_8);
        socket.send(new DatagramPacket(bytes, bytes.length, target));
    }

    private static void receive(DatagramSocket socket, int capacity)
            throws IOException {
        byte[] buffer = new byte[capacity];
        DatagramPacket packet = new DatagramPacket(buffer, buffer.length);
        socket.receive(packet);
        String text = new String(packet.getData(), packet.getOffset(),
                                 packet.getLength(), StandardCharsets.UTF_8);
        System.out.println("bytes=" + packet.getLength() + " text=" + text);
    }

    public static void main(String[] args) throws Exception {
        InetAddress loopback = InetAddress.getByName("127.0.0.1");
        try (DatagramSocket receiver =
                     new DatagramSocket(new InetSocketAddress(loopback, 0));
             DatagramSocket sender = new DatagramSocket()) {
            receiver.setSoTimeout(2000);
            InetSocketAddress target =
                    new InetSocketAddress(loopback, receiver.getLocalPort());

            send(sender, target, "cat");
            receive(receiver, 32);
            send(sender, target, "dog");
            receive(receiver, 32);
            send(sender, target, "abcdef");
            receive(receiver, 4);
            send(sender, target, "Z");
            receive(receiver, 32);
        }
    }
}

���text

bytes=3 text=dog
bytes=4 text=abcd

**Reading the output step by step:**

1. �cat� is 3 ASCII bytes and fits in the 32-byte buffer → receives the exact 3 bytes.
2. �dog� is a separate datagram; receives the exact 3 bytes. It is not concatenated into �catdog�.
3. The sender sends �abcdef� (6 bytes), but the receiver allocates a **4-byte** buffer → only �abcd� is retrieved. The two bytes �ef� **are discarded** and do not wait for the next receive.
4. The sender sends a new datagram �Z� → the next receive returns �Z� on its own. This confirms that �ef� is no longer in the receive queue as a "continuation of the previous packet."

Each call to �receive(receiver, capacity)� in the example creates a new �DatagramPacket�. The socket has a timeout to avoid blocking indefinitely if a datagram does not arrive. On a machine with special network configuration or under heavy load, a �SocketTimeoutException� may occur; UDP **does not guarantee** this stdout in all environments, though loopback is usually very stable.

### Lesson from the 4-Byte Buffer Case

If �getLength() == buffer.length�, **you cannot conclude with certainty** that the datagram was truncated: the datagram could be an exact fit of 4 bytes or larger than 4 bytes. When you need to know that a message is complete, design a payload limit and allocate a sufficiently large buffer, or add a length field/check in the payload according to the protocol. If a packet exceeds the limit, the parser should reject it rather than silently treating truncated content as a valid message.

### Encoding Note

The strings �cat�, �dog�, and �abcdef� are all ASCII, so the byte count equals the character count. With UTF-8, a Vietnamese character can occupy multiple bytes. Truncating a buffer in the middle of a UTF-8 sequence can produce the replacement character �� when decoded. Because a UDP datagram is a **byte unit**, compute the byte size with �getBytes(StandardCharsets.UTF_8).length� and decode using exact �offset/length�, rather than measuring network size with �String.length()�.

## 6. Reusing �DatagramPacket�: You Must Reset the Receive Capacity

Creating a new packet for each receive is easy to understand, but it can cause many allocations under high traffic. If you reuse the same �DatagramPacket�, remember that **�receive� updates �getLength()� to the number of bytes received**, so you must reset the length to the receive capacity before the next iteration.

Pattern inside a receiver loop:

���java
byte[] buffer = new byte[2048];
DatagramPacket packet = new DatagramPacket(buffer, buffer.length);

while (running) {
    packet.setLength(buffer.length); // reset receive capacity
    socket.receive(packet);          // receive one datagram
    handleMessage(packet.getData(),
                  packet.getOffset(),
                  packet.getLength(),
                  packet.getAddress(),
                  packet.getPort());
}
���

This is an **illustrative code snippet**, assuming �socket�, �running�, and �handleMessage(...)� are already declared. Note for asynchronous processing: �packet.getData()� references a **mutable array**; if the receive loop overwrites it before a worker finishes, the old message data is corrupted. **Copy the exact �offset/length�** into a worker-owned buffer or manage a buffer pool with clear ownership.

Key takeaway: one �receive� call must correspond to one **delivered** datagram; there is no concept of receiving "the remaining 400 missing bytes" of the same datagram by calling �receive� a second time.

## 7. TCP Is a Byte Stream; �write� Boundaries Are Not Preserved

Suppose the sender performs two writes:

���java
out.write("cat".getBytes(StandardCharsets.UTF_8));
out.write("dog".getBytes(StandardCharsets.UTF_8));
out.flush();
���

This is a **code snippet**, with �OutputStream out�. If the client receiver calls:

���java
byte[] buffer = new byte[1024];
int n = in.read(buffer);
���

with �InputStream in�, valid outcomes include receiving �catdog� in one �read�, or receiving �c� first and then �atdog�, or any other split that **preserves byte order**.

How the mechanism works:
- �write(...)� appends bytes to the socket output stream; TCP buffers them, splits them into segments, retransmits when needed, and reassembles them in order.
- �read(...)� retrieves **the currently available bytes** (up to the requested buffer size). It has no knowledge of how many times the sender called �write� or how long the application considers a message to be.
- TCP segmentation/MSS, Nagle's algorithm, delayed ACK, coalescing, receive buffering, network scheduling, and the relative speeds of the two processes can all affect how many bytes each read returns. Do not design a protocol based on a segmentation pattern accidentally observed during testing.
- �flush()� requests flushing at the appropriate stream/buffer layer; �setTcpNoDelay(true)� changes Nagle behavior on the socket. **Neither creates message boundaries at �InputStream.read�.**
- TLS running over TCP also does not cause the application to naturally receive "one message per send"; SSL/TLS records are a different structure from the application protocol's message framing.

**Do not confuse "TCP has packets" with "TCP is message-oriented."** TCP uses segments on the wire, but the application's socket API provides an ordered sequence of bytes. RFC 9293 explicitly states that there is no guaranteed correspondence between segment boundaries and the buffer boundaries of write/read calls.

### What Happens When the TCP Buffer Is Too Small?

If the peer sends 6 bytes �abcdef� and the receiver calls �read(new byte[4])�, the receiver can get at most 4 bytes on the first call; the remaining bytes **stay in the stream** for subsequent �read� calls to retrieve (unless the connection fails or the application closes it). This is the exact contrast with UDP: a small buffer does not discard the "remainder" of the stream.

If �read(buffer)� returns:
- �n > 0�: process **exactly �n� bytes** in the buffer.
- �n == -1�: EOF (the peer has closed its sending side after all available bytes have been consumed).
- For a 0-length request, �read� may return 0; in non-blocking NIO, �SocketChannel.read� may also return 0 when no bytes are available yet.

Never rely on a single �read� call to obtain "a full message"; always read according to a framing rule or process the stream incrementally.

## 8. TCP Requires Application-Layer Framing

If a protocol wants to send two messages �cat� and �dog� over one TCP connection, the **application** itself must represent the boundaries.

Common strategies:

| Framing | On the wire | Pros | Things to watch out for |
| --- | --- | --- | --- |
| Fixed-size record | Every record is exactly N bytes | Simple, read full N bytes | Wastes padding, unsuitable for variable-length payloads |
| Delimiter | �cat\n�, �dog\n� | Fits line-based text protocols | Escape delimiters in data; cap max bytes per line |
| Length-prefix | �[len=3][cat][len=3][dog]� | Fits variable-length binary/UTF-8 | Agree on endianness, prefix size, max length |
| Self-describing structured framing | Header, length, type, checksum, or parser format | Extensible protocol | Complex parser; validate both header and payload |
| EOF-delimited | Read until peer closes sending side | Fits a single final response | Unsuitable for long-lived multi-message connections |

Example of a **4-byte length-prefix** wire format:

���text
00 00 00 03 | 63 61 74 | 00 00 00 03 | 64 6F 67
-----------   --------   -----------   --------
 length = 3    "cat"      length = 3     "dog"

Definition: 4-byte unsigned/signed integer per protocol convention,
big-endian, followed by exact length bytes of UTF-8 payload.
���

In the Java example in the next section, we use �DataOutputStream.writeInt�/�DataInputStream.readInt� (signed Java �int�, 4-byte big-endian network representation), and **reject negative lengths or lengths exceeding the protocol limit**. Do not allocate an array based on an unvalidated length; a malicious or buggy sender could declare a huge length and cause the server to run out of memory or block indefinitely.

**Length is measured in bytes, not in Java characters.** For example, �"đ"� is 1 UTF-16 code unit but occupies multiple UTF-8 bytes. The right workflow: encode first, take �bytes.length�, write the length then write the bytes; on the receiving side, read that exact number of bytes before decoding.

## 9. Runnable Java 17+ Example: TCP with Explicit Framing

This standalone program creates a �ServerSocket� and �Socket� on loopback, sends two messages over **one TCP connection**, and reads them using a length-prefix. It does not assume each �read� call returns the full payload: �DataInputStream.readFully� keeps reading until it has enough bytes or encounters EOF.

Save as �TcpFramingDemo.java�:

���java
import java.io.DataInputStream;
import java.io.DataOutputStream;
import java.io.IOException;
import java.net.InetAddress;
import java.net.ServerSocket;
import java.net.Socket;
import java.nio.charset.StandardCharsets;

public class TcpFramingDemo {
    private static void writeFrame(DataOutputStream out, String message)
            throws IOException {
        byte[] bytes = message.getBytes(StandardCharsets.UTF_8);
        out.writeInt(bytes.length); // 4-byte big-endian length
        out.write(bytes);
    }

    private static String readFrame(DataInputStream in) throws IOException {
        int length = in.readInt();
        if (length < 0 || length > 1024) {
            throw new IOException("Invalid length: " + length);
        }
        byte[] bytes = new byte[length];
        in.readFully(bytes);
        return new String(bytes, StandardCharsets.UTF_8);
    }

    public static void main(String[] args) throws Exception {
        InetAddress loopback = InetAddress.getByName("127.0.0.1");
        try (ServerSocket listener = new ServerSocket(0, 50, loopback);
             Socket sender = new Socket(loopback, listener.getLocalPort());
             Socket receiver = listener.accept();
             DataOutputStream out = new DataOutputStream(sender.getOutputStream());
             DataInputStream in = new DataInputStream(receiver.getInputStream())) {
            writeFrame(out, "cat");
            writeFrame(out, "elephant");
            out.flush();

            System.out.println("frame1=" + readFrame(in));
            System.out.println("frame2=" + readFrame(in));
        }
    }
}

### Why Is This Example Correct Regardless of How TCP Splits Segments?

- The sender turns each message into **4 length bytes + payload**; that is the application's own convention.
- �readInt()� reads exactly 4 length bytes (or reports EOF if insufficient). �readFully(bytes)� waits until �length� bytes are retrieved (or throws �EOFException� if the peer closes early). There is no assumption that �read� corresponds to �write�.
- Whether TCP carries both frames in a single segment or splits them across multiple segments, the parser reconstructs the exact same two frames.
- Because both sender and receiver run in the same process and close their sockets with �try-with-resources�, the example actively releases resources. The listener port is dynamically assigned by the OS, helping avoid conflicts with other services.
- The �1024� limit protects the example from invalid lengths, though real applications must define max frame size per business requirements and add timeouts, connection management, interruption handling, and authorization.

**Caveat to remember:** TCP preserves bytes **if the connection transmits successfully**, but a connection can drop after only part of a frame has been sent. In that case, �readInt� or �readFully� may hit EOF/IOException; the application must decide whether to retry the whole message or report an error. You cannot infer that "the peer has processed a transaction" merely because �writeFrame� returned successfully.

## 10. Pitfalls When Writing Your Own TCP Parser

### 10.1. Do Not Read the Payload with a Single �read�

The following code is **incorrect** if it assumes it receives the full message:

���java
int expected = in.readInt();
byte[] payload = new byte[expected];
int n = in.read(payload); // may be less than expected!
���

This is a buggy snippet with no length validation before allocation. �n� may be only a partial read because TCP is a stream. Fix it by validating �expected� and calling �readFully(payload)� (�DataInputStream�), or looping until enough bytes are read.

### 10.2. Do Not Delimit Messages by Idle Pauses

"If no more bytes arrive for 50ms, the message has ended" is an error-prone heuristic: the network can be slow, the scheduler can pause, or a busy machine can delay delivery. Timeouts should be used to detect **taking too long to complete**; message boundaries must be declared by the protocol.

### 10.3. Do Not Use �readAllBytes� on an Open Connection

�InputStream.readAllBytes()� reads until EOF; a server may keep a connection open long-term to exchange multiple requests/responses. If the protocol needs to process each message as soon as it is complete, reading until EOF will wait unnecessarily and may hang or consume excessive memory.

### 10.4. Do Not Rely on �flush� or �TCP_NODELAY�

Calling �flush()� is right when there is Java-level buffering, but **flush does not create a delimiter**. Enabling �TCP_NODELAY� changes the coalescing of some small segments in TCP; the receiver still sees a byte stream.

### 10.5. Do Not Decode UTF-8 by Arbitrary Chunks

A UTF-8 character can be split across two �read� calls. Decoding each chunk independently can produce the replacement character ��. Read the complete frame as bytes before decoding; or use an incremental charset decoder properly if the stream protocol is genuinely line- or chunk-based.

### 10.6. Do Not Treat �writeUTF/readUTF� as Standard UTF-8

�DataOutputStream.writeUTF� and �DataInputStream.readUTF� are a Java API pair that uses **modified UTF-8** with its own length format. If you need a cross-language standard UTF-8 protocol, explicitly define the encoding and length-prefix like �writeFrame/readFrame� instead of assuming the two formats are equivalent.

## 11. When One UDP Datagram Contains Multiple Business Messages

Preserving UDP boundaries does **not** mean the protocol needs no format. Suppose a datagram contains three sensor readings:

���text
UDP datagram #7 payload:
  [count=3][reading A][reading B][reading C]
���

The receiver only knows that **the entire payload belongs to one datagram**. It still must use �count�/length or a structured format to separate the three readings. In another case, a file is split into multiple datagrams:

���text
message id = 42
datagram A: [id=42][index=0][total=3][part...]
datagram B: [id=42][index=1][total=3][part...]
datagram C: [id=42][index=2][total=3][part...]
���

UDP itself does not reassemble A/B/C into one large business message. The app must itself:
- Track �message id�, sender endpoint, and �index/total�.
- Collect fragments **regardless of arrival order**.
- Detect missing, duplicate, and expired fragments; bound memory and timeouts to prevent resource exhaustion.
- If needed, implement retransmission, acknowledgment, and rate/congestion control.

Building a reliable protocol on top of UDP is complex. For ordered, reliable stream needs, TCP is usually a better fit; for protocols that need datagrams and loss control, UDP has advantages but requires handling network conditions. QUIC uses UDP underneath and provides its own mechanisms such as reliable streams, so you cannot deduce all properties of a protocol built on top of raw TCP/UDP from the raw transport alone.

## 12. UDP Buffer Size, MTU, and IP Fragmentation

**Do not conflate these three things:**
1. **UDP payload:** the data a single �send(DatagramPacket)� requests to send.
2. **IP packet/fragment:** the IP unit transmitted across the network; a UDP datagram may have to be fragmented under some configurations.
3. **Application receive buffer:** the bytes Java allocates for �DatagramPacket� or �ByteBuffer� when reading.

For example, with typical IPv4, an Ethernet MTU of 1500 bytes, and no IPv4 options, a UDP payload that avoids fragmentation usually does not exceed **1472 bytes** (1500 − 20-byte IPv4 header − 8-byte UDP header). This number is **not a safe default for every path**: VPNs, tunnels, IPv6 extension headers, other links, and middleboxes can make the Path MTU smaller. IPv6 has a minimum 40-byte header, though practical rules also depend on the environment.

The theoretical maximum IPv4 payload of a standard UDP datagram with the minimum 20-byte IP header is **65,507 bytes** (65,535 − 20 − 8). This is not a size you should choose in a real application. Large datagrams easily exceed the MTU, causing fragmentation; losing just one IP fragment usually causes reassembly to fail, and the entire UDP datagram is not delivered to the receiver.

Therefore:
- Design an explicit **maximum datagram payload**, typically small and aligned with Path MTU.
- Do not wait until �DatagramSocket.send� fails to consider message size limits.
- Do not assume �socket.setReceiveBufferSize(...)� defines the sole limit of each datagram. The socket receive buffer option mainly relates to kernel queue capacity; **�DatagramPacket� still needs a buffer large enough to hold the payload**.
- For large messages that require application-layer fragmentation, include message ID/fragment index/total count and a recovery policy; or choose a more suitable transport.

RFC 8085 recommends that applications using UDP actively consider message size, congestion control, sending limits, and behavior under packet loss. UDP being "lightweight" does not mean you can send unboundedly at arbitrary rates.

## 13. Java NIO: �DatagramChannel� and �SocketChannel� Keep the Same Semantics

Switching from �java.net� to NIO does not change the transport model:
- �DatagramChannel.send(ByteBuffer src, SocketAddress target)� sends the remaining bytes of the buffer as **one datagram** if sent successfully; in non-blocking mode, it may return �0� when it cannot send immediately. �DatagramChannel.receive(ByteBuffer dst)� retrieves **one datagram** and returns the source endpoint, or �null� in non-blocking mode when no datagram is available.
- �SocketChannel.write(ByteBuffer src)� writes bytes to the **TCP stream**; �SocketChannel.read(ByteBuffer dst)� reads available bytes from the stream, which may be part of a frame. In non-blocking mode, �read� may return �0�; �-1� indicates EOF.

A pattern for receiving one UDP datagram with �DatagramChannel�:

���java
ByteBuffer buffer = ByteBuffer.allocate(2048);
SocketAddress sender = channel.receive(buffer);
if (sender != null) {
    buffer.flip();
    int receivedBytes = buffer.remaining();
    // Decode exactly receivedBytes and handle sender.
}
���

This is a code snippet, assuming �DatagramChannel channel� is already opened/bound and �java.nio.ByteBuffer�, �java.net.SocketAddress� are imported. �flip()� switches the buffer from write mode to read mode. If the datagram is larger than �buffer.remaining()� at receive time, NIO also **discards the data that does not fit**; you cannot read the second half in the next �receive� call.

With �SocketChannel�, a length-prefix parser must **accumulate bytes across multiple reads**, maintaining state such as "need 4 header bytes," then "need N payload bytes," and then moving on to the next frame. You should not parse a newly received �ByteBuffer� as a complete frame before the full header or payload has arrived.

## 14. Mistakes and Misconceptions to Avoid

1. **"Two UDP sends can merge into one receive."** Not under UDP datagram semantics: each �receive� retrieves at most **one** delivered datagram; the network can drop/reorder/duplicate datagrams.
2. **"If the UDP receive buffer is small, the next receive gets the rest."** False: truncated data is gone and cannot be read subsequently like a stream.
3. **"�getData().length� is the UDP message length."** False: that is the array size; use �getOffset/getLength� on the packet after receive.
4. **"�getLength()==capacity� definitely means truncation."** False: the datagram may be an exact fit. Proper protocol size limits/length checks are needed.
5. **"One TCP write produces one TCP read."** False: application framing is required.
6. **"TCP has ACK/retransmit, so a business transaction definitely runs once."** False: TCP provides a transport byte stream; on connection errors/retries, systems need request IDs, idempotency, and application-layer acknowledgments.
7. **"�read(buffer)� always fills the buffer."** False: it can return fewer bytes than requested; when you need N bytes, use �readFully� or a read loop.
8. **"�flush� or �TCP_NODELAY� fixes TCP message coalescing/splitting."** False: they do not create message boundaries.
9. **"No UDP data means the socket hit EOF."** False: UDP can lose datagrams or receive a **0-byte** datagram; a timeout is not equivalent to EOF.
10. **"�DatagramSocket.connect()� turns UDP into TCP."** False: connecting a UDP socket usually only sets a default peer/filters endpoints; it does not perform a TCP handshake, retransmission, flow control, or create a byte stream.
11. **"Having datagram boundaries makes UDP safe against oversized payloads."** False: you still must limit sizes, authenticate/validate sources, parse payloads carefully, apply rate limits, and handle overload.
12. **"A TCP read always comes from a single write on the remote side."** False: it can contain bytes from many writes, or even a single write split across multiple reads.

## 15. Choosing a Transport by Scenario

| Scenario | How boundaries are interpreted | Practical decision |
| --- | --- | --- |
| Telemetry: small sensor samples, losing a few samples is acceptable | One record in one UDP datagram | UDP can fit; add sequence numbers and measure loss |
| Traditional DNS query/response over UDP | Each request/response sits in a datagram per DNS protocol | UDP fits with size limits and standard retry/fallback handling |
| Chat commands over a long-lived TCP connection | Multiple messages share one TCP byte stream | Need delimiter or length-prefix; manage partial reads |
| File transfer requiring all bytes in order | TCP byte stream or another reliable protocol | Use framing or explicit file length, integrity checks, and resume if needed |
| Sending images/large structures over UDP | One app message may exceed useful datagram size | Need application-level fragmentation and recovery, or switch transport |
| Short-lived game state updates | Can prioritize newer data and drop stale data | UDP with sequence numbers/timeouts can be useful |
| Sending payment processing requests | Must delimit business requests and outcomes | Even over TCP/HTTP, need request IDs, confirmation, and idempotency beyond transport |

The UDP/TCP decision is not just about "fast/slow" or "connectionless/connection-oriented." Start from the **unit of data**, reliability requirements, ordering, latency, security, backpressure, congestion control, and payload size.

## 16. Checklist When Writing a Message Receiver

**UDP receiver:**
- Use �receive�/�DatagramChannel.receive� and process exactly **one datagram** per receive.
- Choose a buffer sized to the **business datagram limit**; if oversized messages must be rejected, design explicit detection instead of silently accepting truncated payloads.
- Use �offset/length� properly; reset �DatagramPacket.setLength� when reusing; manage ownership in multithreaded processing.
- Do not assume datagrams arrive completely, in order, or without duplicates; design sequence numbers, timeouts, and deduplication if needed.
- Limit size, rate, senders, and resource consumption; use �setSoTimeout� or controlled asynchronous I/O.

**TCP receiver:**
- Define framing upfront: fixed-size, length-prefix, delimiter, or a specific protocol.
- Loop reading until **one full frame** is assembled, preserving state when data is incomplete; handle multiple frames arriving in the same buffer.
- Validate length before allocating; bound memory, timeouts, frame counts, and payload sizes.
- Distinguish EOF from normal data chunks; report an error if EOF occurs mid-header or mid-payload.
- Decode UTF-8 only after obtaining the exact bytes for the message; do not tie message boundaries to �write�, �flush�, or TCP segments.

## 17. Self-Check Questions

**Q1.** A UDP sender sends two datagrams �"abc"� and �"def"�. Can the receiver get a single �"abcdef"� datagram due to UDP merging them?  
**Answer:** No. If both are delivered, they keep separate boundaries. UDP can drop/reorder/duplicate them, but it does not merge two datagrams into one payload.

**Q2.** A 10-byte datagram arrives at �DatagramSocket.receive� with a �DatagramPacket� that has a 6-byte receive buffer. What is �getLength()� after receiving, and where are the remaining 4 bytes?  
**Answer:** Typically �getLength()==6�; the remaining 4 bytes are discarded. They cannot be retrieved in the next �receive�.

**Q3.** A TCP sender calls �write("hello")� then �write("world")�. The receiver calls �read(byte[20])�. Can you rely on receiving exactly 5 bytes each time?  
**Answer:** No. TCP is a stream; the receiver might get 10 bytes at once or various splits. Framing is required to identify the two messages.

**Q4.** When TCP has received 3 out of 8 payload bytes, what should you do?  
**Answer:** Keep the 3 bytes and continue reading the remaining 5 bytes; if EOF occurs mid-frame, treat the frame as incomplete and handle the error.

**Q5.** Does �setTcpNoDelay(true)� guarantee one �read� per �write�?  
**Answer:** No. It only affects Nagle's algorithm; it does not change the TCP byte-stream contract.

**Q6.** Why can �new String(packet.getData())� be wrong?  
**Answer:** Because the array may be larger than the received bytes and contain zeros or stale data; decode using �getOffset()� and �getLength()�.

**Q7.** A large datagram undergoes IP fragmentation; does a Java receiver receive each IP fragment separately?  
**Answer:** Not via the standard UDP API. IP handles reassembly; if incomplete, the datagram is typically not delivered to the socket. Fragmentation increases the risk of losing the entire datagram.

**Q8.** What is the role of �DataInputStream.readFully(payload)� in TCP framing?  
**Answer:** It reads until the requested number of bytes is obtained or EOF is encountered; it fixes the false assumption that "one read gets a full frame," though you still need length validation, timeouts, and resource limits.
