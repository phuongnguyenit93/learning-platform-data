# SSLEngine Separates TLS Processing from the Transport Mechanism in Java

**`javax.net.ssl.SSLEngine` is a byte-buffer-level TLS/DTLS protocol processing engine, not a socket.** It performs encryption, decryption, record authentication/protection, and coordinates TLS handshake messages; the **application** must receive and send those encrypted bytes itself using TCP, NIO `SocketChannel`, or an appropriate transport mechanism. This is the fundamental difference compared to `SSLSocket`, which ties TLS processing to the data stream from a socket.

For example, when sending a `"hello"` message over TLS:
1. The application prepares **plaintext** in a `ByteBuffer`.
2. `engine.wrap(plaintext, networkBuffer)` produces **TLS records** into the output buffer; during the handshake phase it can also produce handshake bytes without consuming plaintext.
3. The application sends **networkBuffer** over the transport and ensures proper ordering, handling partial writes.
4. On the receiving end, the application reads TLS record bytes from the transport into a buffer.
5. `engine.unwrap(networkBuffer, plaintextBuffer)` processes the handshake or recovers plaintext.
6. The application processes the message only when both TLS and application framing are valid.

This lesson belongs to the **TLS** topic in Java Advance - networking. The content progresses from the engine architecture, how `wrap/unwrap` work, the handshake state machine, `SSLEngineResult`, buffer handling, and TLS security, to two **standalone runnable Java 17+** programs demonstrating how the TLS engine produces and receives record bytes in memory **without a network connection**.

## 1. What Problem Does SSLEngine Solve?

A regular TCP socket transfers bytes between two hosts; it **does not protect the content itself**. TLS brings peer authentication (depending on mode), confidentiality, and integrity checking to the transport channel. If using `SSLSocket`, the API bundles multiple layers together:

~~~text
Application
    |
    v
SSLSocket  ── TLS handshake / encrypt / decrypt
    |
    v
Socket I/O ── TCP, IP address, port, blocking read/write
~~~

This approach is convenient for simple blocking I/O code, but it does not directly give nonblocking server authors control over every TLS record byte in their own buffer queues.

With `SSLEngine`, the boundary is clearer:

~~~text
                           OUTBOUND
              Plaintext (application bytes)
                             |
                             v
                  +----------------------+
                  | SSLEngine.wrap(...)  |
                  | TLS record encoder   |
                  +----------------------+
                             |
                             v
                    TLS record bytes
                             |
             application-managed transport
               (SocketChannel, queue, ...)
                             |
                             v
                   network / remote peer


                           INBOUND
                    TLS record bytes
                             |
             application-managed transport
                             |
                             v
                  +----------------------+
                  | SSLEngine.unwrap(...)|
                  | TLS record decoder   |
                  +----------------------+
                             |
                             v
              Plaintext (application bytes)
~~~

**`SSLEngine` does not open a TCP connection, does not bind a port, does not call `read()` on a `SocketChannel`, does not send ciphertext over the network, and does not create a selector/event loop.** Calling `wrap()` can produce hundreds of handshake bytes right in RAM, yet the remote peer receives nothing until the application sends those bytes over the transport.

This allows combining TLS with:
- Nonblocking `SocketChannel` and `Selector` to manage multiple TLS clients using an event loop.
- Blocking I/O if the application wants to manage the stream itself.
- Asynchronous I/O and custom output queues, as long as the application guarantees the order of TLS records.
- Simulated buffers or transports in tests without needing a network.

**“Transport-independent” must not be misunderstood as TLS naturally running correctly over any kind of network.** Standard TLS requires a reliable, ordered record stream, typically TCP; DTLS is the variant for datagrams and has its own processing rules.

## 2. Who Is Responsible for What?

| Aspect | `SSLEngine` | Application/transport |
| --- | --- | --- |
| Negotiating TLS version, cipher suite, and keys | Participates in TLS handshake via wrap/unwrap | Delivers handshake records to the peer |
| Encrypting and protecting data | `wrap()` produces network bytes | Sends all bytes over the socket in the exact order |
| Processing received data | `unwrap()` reads TLS records and produces plaintext | Reads records from transport, retains fragments until complete |
| Certificates and trust | Relies on `SSLContext`, key/trust managers, and parameters | Configures identity/trust policy/hostname verification |
| Waiting for socket readiness | Does not perform this | `Selector`/event loop, `read()`/`write()`, timeouts |
| Buffering and backpressure | Reports sizes and status via result/session | Allocates/grows bounded buffers, queues ciphertext/plaintext |
| Application protocol | Does not understand your HTTP requests/frames | Parses length-prefix, delimiters, JSON/HTTP/RPC, etc. |
| Closing TLS | Generates/reads `close_notify` and tracks engine state | Flushes close records then manages socket close/half-close |
| Retries, reconnects, logging | Not a network connection manager | Retry limits, cleanup, metrics, error policy |

`SSLSocket` performs many I/O actions for you, whereas `SSLEngine` lets you **design your own transport processing loop**. The trade-off is that you must handle the state machine and buffers with precision.

## 3. Two Key Methods: wrap and unwrap

### `wrap()` — from application buffer to TLS network buffer

Typical API:

~~~java
SSLEngineResult result = engine.wrap(appOut, netOut);
~~~

This is a **snippet** (requires `engine`, `appOut`, `netOut` variables and imports). Depending on TLS state:
- During the **handshake**, `wrap` may produce ClientHello, ServerHello, or handshake/alert records without **consuming app bytes**.
- After the handshake, `wrap` can consume plaintext from `appOut` and produce one or more TLS records into `netOut`.
- If there is not enough space for a TLS record, it may return `BUFFER_OVERFLOW`; the application must prepare an appropriate destination.
- The `bytesConsumed()` result reflects the **number of plaintext bytes actually taken from appOut**. `bytesProduced()` reflects the **number of record bytes written to netOut**.

**Crucial:** `bytesConsumed() == 0` **does not mean an error** during a handshake. The engine can produce network bytes even when the application has not sent any message.

### `unwrap()` — from TLS network buffer to plaintext buffer

Typical API:

~~~java
SSLEngineResult result = engine.unwrap(netIn, appIn);
~~~

Depending on state:
- When `netIn` contains a handshake record, the engine processes the TLS message, updates handshake state, and **may produce no plaintext**.
- When it contains protected application data and the handshake is complete, the engine decrypts/authenticates and writes plaintext into `appIn`.
- If there are not enough bytes to form **a complete TLS record**, `unwrap` may return `BUFFER_UNDERFLOW`.
- If `appIn` does not have enough space for the expected result, it may return `BUFFER_OVERFLOW`.
- TLS authentication/decryption/syntax errors can lead to `SSLException`, and the channel must be failed according to policy.

`unwrap()` only understands **TLS records**. Do not pass a plaintext HTTP string or random bytes directly into `unwrap` expecting it to auto-detect and encrypt them. Conversely, do not send plaintext directly over `SocketChannel` after TLS is established: doing so bypasses TLS protection.

### One call does not equal one message

TLS records have their own boundaries; TCP, however, is a **byte stream**, and a single `SocketChannel.read()` call may:
- Receive only part of a TLS record.
- Receive exactly one record.
- Receive multiple consecutive records.
- Return 0 in nonblocking mode or -1 on EOF.

Therefore, the application needs a **network input buffer** to retain incomplete bytes across multiple reads, and an `unwrap` loop to process each record once enough data arrives. A single `wrap` call does not send all data either: `SocketChannel.write(netOut)` may only write a partial amount.

## 4. Initializing SSLContext, SSLEngine, and Client/Server Roles

Java pattern to create a client engine:

~~~java
SSLContext context = SSLContext.getDefault();
SSLEngine engine = context.createSSLEngine("api.example.com", 443);
engine.setUseClientMode(true);
engine.beginHandshake();
~~~

The above is a **snippet**, requiring `import javax.net.ssl.*;` and `throws Exception` or error handling. `createSSLEngine(host, port)` **does not connect to the host**. The two peer host/port parameters provide metadata for the session/TLS mechanisms; they are not an actual connected socket address. The application must still create and connect the transport itself.

When implementing a server:

~~~java
SSLEngine serverEngine = serverContext.createSSLEngine();
serverEngine.setUseClientMode(false);
serverEngine.beginHandshake();
~~~

A real server-side `SSLContext` **needs a key manager/private key and an appropriate certificate chain**, or a supported authentication mechanism. Creating a server engine from the default context **does not automatically provide certificates** sufficient to complete a TLS handshake.

Before starting the handshake, configure:
- Client/server mode via `setUseClientMode(true/false)`.
- Allowed protocol versions and cipher suites via `SSLParameters`/corresponding APIs, matching product policy.
- Trust store / `TrustManager` and server `KeyManager` via `SSLContext`.
- Endpoint identification for TLS clients according to the protocol, such as `"HTTPS"` when using HTTPS.
- SNI/ALPN if the application needs server name selection or HTTP/2, etc.

**Security note:** Even though the engine can verify the certificate chain via a trust manager, using a raw `SSLEngine` does not mean the hostname in the URL is verified. On an HTTPS client, you must set the appropriate endpoint identification algorithm before the handshake.

## 5. The TLS Handshake Does Not Happen Automatically Over the Network

Calling `beginHandshake()` **starts the state machine**, but it does not block until the handshake completes and does not transmit bytes itself. The application author must drive the `wrap/unwrap` calls, transfer records between both sides, and execute any required delegated tasks.

Conceptual flow example:

~~~text
Client SSLEngine                         Server SSLEngine
      |                                        |
      | NEED_WRAP                              | NEED_UNWRAP
      | wrap(empty) --> ClientHello bytes      |
      |---------------- transport ------------>|
      |                                        | unwrap(ClientHello)
      |                                        | NEED_TASK / NEED_WRAP
      |                          <-------------| wrap(handshake bytes)
      | unwrap(server handshake bytes)         |
      | NEED_TASK / NEED_WRAP / NEED_UNWRAP    |
      |--------------- ... ------------------->|
      |                                        |
      +----------- handshake complete ---------+
      |                                        |
      | wrap(plaintext) -> TLS app data        |
      |---------------- transport ------------>|
      |                                        | unwrap -> plaintext
~~~

This is a **diagram**: TLS 1.2 and TLS 1.3 differ in sequence and number of records; each `wrap`/`unwrap` call does not correspond to a fixed step. The TLS engine may produce multiple records, process internal handshake state, or require running delegated tasks. Never hard-code “handshake is done after one ClientHello”.

While the handshake is incomplete, **do not send application plaintext over the transport**. Some `wrap` calls at this stage consume no app bytes because they must generate handshake records first.

## 6. HandshakeStatus States and How to Respond

Read the status via `engine.getHandshakeStatus()`, or obtain it after each operation via `result.getHandshakeStatus()`. The main values in Java 17:

| `SSLEngineResult.HandshakeStatus` | Meaning | Application responsibility |
| --- | --- | --- |
| `NEED_WRAP` | The engine needs to generate handshake/alert bytes | Prepare netOut, call `wrap`, send **all** produced bytes to the peer |
| `NEED_UNWRAP` | Needs to receive a TLS record from the peer | Read more network data from the transport, `unwrap` when sufficient |
| `NEED_TASK` | Needs delegated tasks before the handshake can progress | Call `getDelegatedTask()`, run tasks, handle results, then continue |
| `FINISHED` | The just-completed `wrap/unwrap` finished the handshake | This is the completion signal in the operation's **result** |
| `NOT_HANDSHAKING` | Currently not in a handshake | Can process application data if the session is actually established |
| `NEED_UNWRAP_AGAIN` | Needs to continue unwrapping data still buffered inside the engine | Handle per provider contract; in Java 17 this status is for **DTLS** |

Distinguish carefully:
- `FINISHED` is returned in `SSLEngineResult.getHandshakeStatus()` of the `wrap/unwrap` call that finishes the handshake; **`engine.getHandshakeStatus()` does not return `FINISHED`**.
- Callbacks or network I/O are not automatically executed by the engine when the status changes.
- `NEED_UNWRAP_AGAIN` belongs to DTLS in Java 17; you should not design a TLS/TCP loop expecting to always see this status.
- When handling delegated tasks, do not keep calling `wrap/unwrap` waiting for progress while ignoring `NEED_TASK`; the engine may fail to advance.

Example snippet for running delegated tasks (not a complete TLS driver):

~~~java
Runnable task;
while ((task = engine.getDelegatedTask()) != null) {
    task.run();
}
~~~

`getDelegatedTask()` returns `null` when no tasks remain. Some tasks such as certificate validation or key selection can **block** or be CPU-intensive; with a selector/event-loop, consider offloading tasks to a worker executor and **only resuming the engine once the tasks complete**. Do not use `Thread.sleep()` in place of running tasks.

## 7. SSLEngineResult: Status, bytesConsumed, and bytesProduced

After **every** `wrap/unwrap`, you must read **two dimensions of information**:
- `result.getStatus()`: the status of the operation with respect to buffers/engine.
- `result.getHandshakeStatus()`: which TLS step the engine needs next.

In addition, `result.bytesConsumed()` and `result.bytesProduced()` determine actual progress.

| `Status` | Meaning | Typical handling |
| --- | --- | --- |
| `OK` | Operation processed normally, can make progress | Track consumed/produced and handshake status; continue I/O if needed |
| `BUFFER_OVERFLOW` | Destination lacks space for the output record/plaintext | Allocate/grow an appropriate buffer, flush existing output, retry |
| `BUFFER_UNDERFLOW` | `unwrap` lacks enough network bytes for a TLS record | Retain partial bytes, ensure network input has capacity, read more |
| `CLOSED` | The relevant direction of the engine has closed or is closing | Perform TLS close procedure, flush remaining records, cleanup |

**Example combining both statuses:**

~~~text
getStatus() = OK
getHandshakeStatus() = NEED_UNWRAP
bytesConsumed() = 0
bytesProduced() > 0
~~~

This can happen when `wrap` produces handshake bytes without consuming plaintext. The application must send those bytes, then receive the next TLS record to `unwrap`.

**Do not equate `Status.OK` with “TLS handshake completed”**: an operation can be OK while the handshake still requires `NEED_WRAP` or `NEED_UNWRAP`. Also do not treat the number of bytes produced as the number of plaintext bytes: ciphertext is longer due to the record header, authentication tag, and TLS framing.

## 8. Buffer Sizing: Packet, Application, Underflow, and Overflow

SSLEngine works with **ByteBuffer** on both sides:

~~~text
appOut    -- wrap() -->    netOut
plaintext                  TLS records

netIn     -- unwrap() -->  appIn
TLS records                plaintext
~~~

To allocate buffers, Java provides guidelines from `SSLSession`:

~~~java
SSLSession session = engine.getSession();
int packetCapacity = session.getPacketBufferSize();
int applicationCapacity = session.getApplicationBufferSize();

ByteBuffer netIn = ByteBuffer.allocate(packetCapacity);
ByteBuffer netOut = ByteBuffer.allocate(packetCapacity);
ByteBuffer appIn = ByteBuffer.allocate(applicationCapacity);
~~~

This is a snippet; it requires importing `javax.net.ssl.SSLSession`, `java.nio.ByteBuffer`, and an existing `engine`. Allocating the suggested sizes does not eliminate all overflow/underflow cases; the session or provider can change requirements after negotiation, and the application must check statuses at runtime.

### BUFFER_UNDERFLOW when receiving an incomplete record

For example, a TLS record has a **5-byte header + payload data**, but the transport has only delivered the first 5 header bytes:

~~~text
TCP read #1:  [TLS record header (5 bytes)]
TCP read #2:  [remaining record bytes ...]

netIn after read #1:
    16 03 03 01 52
    ^-- only header so far, no payload yet

unwrap(netIn, appIn)
    --> BUFFER_UNDERFLOW, typically bytesConsumed = 0

Keep 5 bytes; read more network bytes; retry unwrap.
~~~

The hex bytes here **illustrate** the record structure, not the mandatory version/length that every JDK will generate. On underflow, you must `compact()` the input buffer to preserve the remaining bytes and switch to write mode, then read more. Do not `clear()` if the buffer still holds unprocessed TLS bytes.

### BUFFER_OVERFLOW when output lacks space

If `netOut` is too small to hold the TLS record `wrap` wants to produce, you may get `BUFFER_OVERFLOW`. Because the TLS engine processes complete records, you should not rely on the engine “outputting half a record” when the destination is small. You need a buffer with sufficient capacity (refer to `getPacketBufferSize()`) or flush already-encoded bytes to the transport before retrying.

On the `unwrap` side, `BUFFER_OVERFLOW` can occur because `appIn` lacks space for the expected plaintext; consume/deliver existing plaintext or grow `appIn` within application limits and retry.

**Do not grow buffers unboundedly based on peer data**: the application must cap memory usage and defend against peers sending malformed data, excessive records, or protocol-level DoS.

### Managing ByteBuffer modes accurately

A network receiving pattern (illustrative only, not a complete program):

~~~java
int n = socketChannel.read(netIn); // netIn in write mode
if (n == -1) {
    // EOF: handle TLS close / truncation according to policy.
}
netIn.flip();                      // switch to read mode

SSLEngineResult result = engine.unwrap(netIn, appIn);
// Check result.getStatus() and getHandshakeStatus().
// May need to loop unwrap if more records remain in netIn.

netIn.compact();                   // retain unconsumed bytes
~~~

**Incomplete:** This snippet omits branch handling for overflow and tasks, so it cannot be used directly as a TLS server; its purpose is only to illustrate switching buffer modes. A complete implementation must perform multiple `unwrap`/network read passes depending on progress and prepare `appIn` at the right time.

The corresponding sending side:

~~~java
SSLEngineResult result = engine.wrap(appOut, netOut);
// Check Status/HandshakeStatus, handle buffer overflow.

netOut.flip();                     // ready to read TLS bytes
while (netOut.hasRemaining()) {
    int written = socketChannel.write(netOut);
    if (written == 0) {
        // Nonblocking transport: register OP_WRITE, keep netOut
        // until writable, DO NOT spin infinitely here.
        break;
    }
}
netOut.compact();                  // retain unsent ciphertext
~~~

In this example, if unsent ciphertext remains, the application must keep `netOut` for the next writable event and **must not overwrite a buffer containing an unflushed record**. Never mix the order of ciphertext from multiple `wrap` calls.

## 9. Java 17+ Example: Generating a TLS ClientHello Purely in RAM

The first example **opens no sockets**, performs no DNS queries, and sends no bytes over the network. We initialize a client engine, request TLS 1.3, enable endpoint identification using the HTTPS algorithm (which matters when encountering a certificate in a real handshake), and call `wrap` to generate ClientHello.

Create the file **`ClientHelloWithoutSocket.java`**:

~~~java
import java.nio.ByteBuffer;
import java.security.SecureRandom;
import javax.net.ssl.SSLContext;
import javax.net.ssl.SSLEngine;
import javax.net.ssl.SSLEngineResult;
import javax.net.ssl.SSLParameters;

public class ClientHelloWithoutSocket {
    public static void main(String[] args) throws Exception {
        SSLContext ctx = SSLContext.getInstance("TLS");
        ctx.init(null, null, new SecureRandom());

        // peerHost/port are metadata only, DOES NOT open a socket.
        SSLEngine engine = ctx.createSSLEngine("example.test", 443);
        engine.setUseClientMode(true);
        engine.setEnabledProtocols(new String[]{"TLSv1.3"});

        SSLParameters options = engine.getSSLParameters();
        options.setEndpointIdentificationAlgorithm("HTTPS");
        engine.setSSLParameters(options);

        engine.beginHandshake();
        System.out.println("Initial handshake: "
                + engine.getHandshakeStatus());

        ByteBuffer empty = ByteBuffer.allocate(0);

        // One byte is too small to hold a TLS handshake record.
        SSLEngineResult tooSmall =
                engine.wrap(empty, ByteBuffer.allocate(1));
        System.out.println("Tiny output: " + tooSmall.getStatus());

        // Allocate according to SSLSession hint.
        ByteBuffer network =
                ByteBuffer.allocate(engine.getSession().getPacketBufferSize());
        SSLEngineResult generated = engine.wrap(empty, network);

        System.out.println("Valid wrap: " + generated.getStatus());
        System.out.println("Application bytes consumed: "
                + generated.bytesConsumed());
        System.out.println("Handshake bytes produced: "
                + (generated.bytesProduced() > 0));

        network.flip();
        System.out.println("Bytes ready to send: "
                + (network.remaining() > 0));
    }
}
~~~

Compile and run on Java 17+ with a standard TLS 1.3 provider:

~~~bash
javac -encoding UTF-8 ClientHelloWithoutSocket.java
java ClientHelloWithoutSocket
~~~

**Verified output on OpenJDK supporting TLS 1.3:**

~~~text
Initial handshake: NEED_WRAP
Tiny output: BUFFER_OVERFLOW
Valid wrap: OK
Application bytes consumed: 0
Handshake bytes produced: true
Bytes ready to send: true
~~~

Explanation:
- `beginHandshake()` transitions the engine to a state needing to generate handshake bytes (`NEED_WRAP`), with zero network I/O.
- `ByteBuffer.allocate(1)` cannot hold a TLS record → `BUFFER_OVERFLOW`.
- Using `getPacketBufferSize()` to prepare a larger buffer, `wrap` returns `OK`.
- `bytesConsumed() == 0` because the source app buffer is empty; `bytesProduced() > 0` because `wrap` generates the handshake record.
- `network.flip()` readies the TLS bytes for the application to **subsequently** write to the transport. The example intentionally stops here: **there is no remote peer, no authenticated TLS session, and no full app-data encryption yet**.
- The exact byte count of ClientHello and cipher list can vary by provider/JDK/configuration, so the program only prints booleans and expected states in the described environment.

This is direct proof that **the TLS engine and network I/O are two separate concerns**.

## 10. Java 17+ Example: A Split TLS Record Causing BUFFER_UNDERFLOW

TCP can split a single TLS record across multiple reads. The second example simulates that **in memory**:

1. A client engine generates a ClientHello (TLS record).
2. Only the **first 5 bytes** are copied into `fragment`, simulating TCP having read only the header so far.
3. Another server engine receives `fragment` via `unwrap`.
4. Because there is no complete record yet, the result is `BUFFER_UNDERFLOW` and zero bytes are consumed.

**This is only a parser/BufferStatus probe.** The server uses the default context **without a configured server certificate/private key**, so this example does not perform a complete TLS handshake. To build a real TLS server, you must configure identity and trust policy according to your goals.

Create the file **`PartialTlsRecordDemo.java`**:

~~~java
import java.nio.ByteBuffer;
import java.security.SecureRandom;
import javax.net.ssl.SSLContext;
import javax.net.ssl.SSLEngine;
import javax.net.ssl.SSLEngineResult;

public class PartialTlsRecordDemo {
    public static void main(String[] args) throws Exception {
        SSLContext context = SSLContext.getInstance("TLS");
        context.init(null, null, new SecureRandom());

        SSLEngine client =
                context.createSSLEngine("example.test", 443);
        client.setUseClientMode(true);
        client.setEnabledProtocols(new String[]{"TLSv1.3"});
        client.beginHandshake();

        ByteBuffer produced = ByteBuffer.allocate(
                client.getSession().getPacketBufferSize());
        SSLEngineResult result =
                client.wrap(ByteBuffer.allocate(0), produced);

        if (result.getStatus() != SSLEngineResult.Status.OK
                || result.bytesProduced() < 5) {
            throw new IllegalStateException("No ClientHello");
        }
        produced.flip();

        // Simulate transport having delivered only the 5-byte TLS header.
        ByteBuffer fragment = ByteBuffer.allocate(5);
        for (int i = 0; i < 5; i++) {
            fragment.put(produced.get());
        }
        fragment.flip();

        SSLEngine server = context.createSSLEngine();
        server.setUseClientMode(false);
        server.setEnabledProtocols(new String[]{"TLSv1.3"});
        server.beginHandshake();

        SSLEngineResult partial = server.unwrap(
                fragment,
                ByteBuffer.allocate(
                        server.getSession().getApplicationBufferSize()));

        System.out.println("Fragment bytes: " + fragment.limit());
        System.out.println("Unwrap status: " + partial.getStatus());
        System.out.println("Bytes consumed: " + partial.bytesConsumed());
        System.out.println("More network data needed: "
                + (partial.getStatus()
                == SSLEngineResult.Status.BUFFER_UNDERFLOW));
    }
}
~~~

Run:

~~~bash
javac -encoding UTF-8 PartialTlsRecordDemo.java
java PartialTlsRecordDemo
~~~

Output on OpenJDK with TLS 1.3:

~~~text
Fragment bytes: 5
Unwrap status: BUFFER_UNDERFLOW
Bytes consumed: 0
More network data needed: true
~~~

**Why is `bytesConsumed() == 0`?** In this case, 5 bytes are only enough for the header to determine the record size, not the payload. The engine does not consume an incomplete record as observed; the caller must retain the fragment and supply more bytes.

In a real application, you should use `netIn.compact()` to retain remaining bytes and append data on the next `SocketChannel.read(netIn)` call. Do not read a record assuming “one TCP read is guaranteed to contain a full TLS record”. Every underflow and provider is not required to return the same consumed count; always use the actual ByteBuffer positions/result to decide which data to retain.

## 11. Integrating with SocketChannel/Selector: One Event Loop Controlling Two Layers

To build a nonblocking TLS server, you can use this model:

~~~text
TCP SocketChannel  (transport)
    |
    | OP_READ / OP_WRITE provided by Selector
    v
ConnectionState:
    netIn     : ByteBuffer   // received TLS bytes, may be an incomplete record
    netOut    : ByteBuffer   // unsent TLS bytes
    appIn     : ByteBuffer   // decrypted plaintext
    appOut    : ByteBuffer   // plaintext awaiting encryption
    engine    : SSLEngine
    handshake : state machine
    queues    : bounded queues
    |
    +-- READABLE  --> socket.read(netIn)
    |                --> flip(netIn)
    |                --> engine.unwrap(netIn, appIn)
    |                --> compact(netIn)
    |                --> handle status / plaintext
    |
    +-- WRITABLE  --> socket.write(netOut)
    |                --> keep remaining ciphertext if partial write
    |
    +-- APP DATA  --> engine.wrap(appOut, netOut)
    |                --> enable OP_WRITE if netOut contains bytes
    |
    +-- NEED_TASK --> run delegated tasks (can offload)
    |
    +-- CLOSE     --> closeOutbound, wrap close_notify, flush, close
~~~

**Selector tracks TCP channel readiness, while SSLEngine tracks TLS protocol state.** These states are not interchangeable:
- `OP_READ` means the socket is ready for the application to call `SocketChannel.read`; it does **not** guarantee a complete TLS record is available.
- `BUFFER_UNDERFLOW` means `unwrap` needs more TLS bytes; the socket is not necessarily readable right now.
- `NEED_WRAP` means the engine must produce TLS records; it does not mean the socket is writable.
- `OP_WRITE` means the socket can accept more bytes; it does not guarantee all of `netOut` will be written in one call.

If the engine requires `NEED_WRAP` while `netOut` still holds unflushed ciphertext, you must **preserve ordering**: do not overwrite partial bytes. You can place newly generated records into a bounded queue or wait for `netOut` to drain before calling `wrap` again.

Example **pseudocode** for each event loop iteration:

~~~text
while connection_open:
    if TCP socket readable:
        read network bytes into netIn

    while netIn has complete consumable TLS records:
        r = engine.unwrap(netIn, appIn)
        handle r.status and r.handshakeStatus
        if r is BUFFER_UNDERFLOW: read more when socket ready
        if r is BUFFER_OVERFLOW: grow/flush appIn within limits
        if progress == 0 and state unchanged: stop loop / wait

    if handshake needs delegated tasks:
        run tasks, resume when finished

    if engine needs wrap OR appOut has plaintext:
        r = engine.wrap(appOut, netOut)
        handle r.status and r.handshakeStatus
        preserve produced TLS bytes

    if netOut has bytes AND socket writable:
        write as many network bytes as possible
        retain unsent bytes for next OP_WRITE

    update Selector interestOps according to pending I/O

    if TLS closing:
        flush close_notify and finish transport cleanup
~~~

This is **illustrative logic, not compilable Java**. A real TLS driver needs additional conditions to avoid busy loops, starvation, premature closing, or dropped bytes. Especially when a `wrap/unwrap` call makes no progress, do not loop infinitely.

### Do not leave OP_WRITE enabled continuously when no bytes are waiting

With nonblocking TCP, a socket is usually writable whenever the kernel send buffer has space. If you keep `OP_WRITE` in the interest set even with no ciphertext to send, the Selector can wake up continuously and waste CPU.

Common pattern:
- **Enable `OP_WRITE`** when there are bytes in `netOut` or the TLS output queue.
- **Disable `OP_WRITE`** after draining all bytes.
- When `NEED_WRAP`, drive the engine to produce TLS bytes while also ensuring destination space.
- If ciphertext is missing because you are waiting for a remote handshake, prioritize `OP_READ` and do not spin calling `wrap`.

## 12. Record Ordering, Concurrency, and Buffer Ownership

According to Oracle documentation, `SSLEngine.wrap()` and `SSLEngine.unwrap()` **can run concurrently in opposite directions**, but **two threads must not concurrently call `wrap` on the same engine, or two threads concurrently call `unwrap` on the same engine** in a way that leaves record ordering uncontrolled.

**Important invariants:**
1. Have **one logical owner for the outbound wrap direction** so generated TLS records are sent in exact order.
2. Have **one logical owner for the inbound unwrap direction** to process received bytes in transport order.
3. Do not modify `ByteBuffer.position/limit/content` while the buffer is being operated on by the engine or network I/O on another thread.
4. If the handshake needs tasks/callbacks, synchronize state transitions; do not let another thread arbitrarily continue the engine before a delegated task finishes.
5. Queues for ciphertext, app data, and pending writes must be **bounded** to prevent OOM when a client reads slowly.

**Do not use a single `ByteBuffer` for both netIn and appIn**, or for both `netOut` and `appOut` in a way that overlaps memory. `SSLEngine.unwrap` requires not using the same underlying memory for src/dst; moreover, it makes mode and lifetime management error-prone.

Faulty example:

~~~java
// ANTI-PATTERN: app plaintext and TLS ciphertext share the same buffer.
ByteBuffer shared = ByteBuffer.allocate(4096);
engine.wrap(shared, shared);
~~~

Do not do this. Source and destination buffers must be independent, and `wrap/unwrap` can modify positions.

**Security when logging:** `netOut/netIn` contains TLS record bytes, whereas `appIn/appOut` contains plaintext data. Do not accidentally log plaintext, retain buffers past their lifetime, or reuse buffers containing sensitive data without a clear policy. Although TLS protects the wire, application memory buffers still hold directly readable information.

## 13. Trust, Hostname Verification, SNI, and ALPN

Separating TLS from the transport does not mean skipping verification. A TLS client can accept a trusted certificate chain with the **wrong hostname** if the application does not configure proper endpoint identification.

Configuration pattern for an HTTPS client (snippet):

~~~java
SSLContext context = SSLContext.getDefault();
SSLEngine engine = context.createSSLEngine("api.example.com", 443);
engine.setUseClientMode(true);

SSLParameters parameters = engine.getSSLParameters();
parameters.setEndpointIdentificationAlgorithm("HTTPS");
parameters.setApplicationProtocols(new String[]{"h2", "http/1.1"});
engine.setSSLParameters(parameters);
~~~

Requires importing `javax.net.ssl.*;`. `"api.example.com"` is an illustrative hostname, with no actual connection. For the code to actually complete TLS:
- The transport must connect to the right network endpoint.
- `SSLContext` must have trusted trust managers per policy.
- The server must send a valid certificate chain for the target hostname.
- The application must **not** disable certificate verification using trust-all managers in production.
- HTTP/2 requires additional HTTP-layer protocol semantics; calling `setApplicationProtocols(...)` alone does not create an HTTP/2 codec.
- SNI (Server Name Indication) lets the server select the appropriate certificate/virtual host; it can be configured via `SSLParameters.setServerNames(...)` when needed. Do not treat SNI as proof of identity; it is a routing hint during the handshake.

Creating an `SSLEngine` with `createSSLEngine(host, port)` does not perform a DNS lookup or HTTP request and is not enough to authenticate the peer; only after a real handshake, with an appropriate policy, can the session/certificate/endpoint be evaluated.

**Server-side context** needs a certificate + private key managed by a `KeyManager` (or equivalent valid source). Simply calling `SSLContext.init(null, null, random)` and expecting a server TLS handshake to complete usually lacks the required server identity. The two demo programs above intentionally **do not** complete a handshake, so they do not need a dummy keystore or truststore for testing.

## 14. Closing TLS Properly: close_notify vs. Socket EOF

Closing a TCP socket and closing a TLS session are **not completely synonymous**.

TLS has a `close_notify` closure alert to signal that the sending direction has ended in an orderly manner. With `SSLEngine`:
1. When the application will no longer send plaintext, call `engine.closeOutbound()`.
2. Continue calling `wrap` (an empty source app buffer can be used) to collect TLS closure record bytes.
3. **Send all** generated bytes to the peer in order, handling partial writes.
4. Monitor `result.getStatus() == CLOSED` or `engine.isOutboundDone()` and queue states.
5. On the receiving side, `unwrap` processes the peer's close notification; `engine.isInboundDone()` can indicate the inbound direction is closed.
6. Close the underlying transport according to the protocol lifecycle and application requirements.

**`closeOutbound()` does not automatically send `close_notify` over the network**, because the engine does not own the socket. Closing TCP immediately after `closeOutbound()` without flushing the record will lose the TLS shutdown message.

If transport EOF arrives **without a TLS close notification per the contract**, `closeInbound()` may throw `SSLException` to warn of possible abnormal data termination/truncation. The application must apply its protocol policy (e.g., if the application has explicit length-framing) and handle failure/cleanup; do not arbitrarily treat every EOF as a graceful TLS close.

A closed engine **cannot be reused for a new TLS connection**. To reconnect, create a new transport and a new `SSLEngine` from an appropriate context. `SSLContext` can be reused according to session policy, but an engine holds per-connection state.

## 15. What Are the Limits of TLS, DTLS, and Transport-Independence?

In the `SSLEngine` documentation, the abstraction is designed to support **TLS and DTLS** depending on provider/protocol. However:

| Characteristic | TLS typically over TCP | DTLS typically over UDP |
| --- | --- | --- |
| Network model | Reliable, ordered byte stream | Datagrams may be lost or arrive out of order |
| Record/data handling | Buffers bytes when TCP read has a partial record | Preserves datagram boundaries, supports DTLS loss/reorder handling |
| Timeout/retransmit control | Typically handled by TCP and appropriate TLS handshake semantics | Application must support DTLS handshake timers/retransmit per contract |
| HandshakeStatus `NEED_UNWRAP_AGAIN` in Java 17 | Not a required state for normal TLS streams | May appear in DTLS processing |
| Socket I/O | `SocketChannel`, TCP stream | Datagram transport, DTLS-capable provider/engine, and additional logic |

**Do not take TLS 1.3 records from the examples, push them arbitrarily over UDP, and call it DTLS.** Stream TLS has no built-in mechanism to recover lost/reordered UDP datagrams. To use datagrams, configure DTLS properly along with appropriate transport/retransmission handling.

Another system using TLS over TCP might want to write its own engine driver with `AsynchronousSocketChannel` instead of `Selector`; the principle remains the same: network I/O belongs to the caller, TLS encoding/decoding belongs to the engine, ensuring ordering and proper buffer sizing.

## 16. Common Error Diagnosis Table

| Symptom / error | Common cause | How to handle |
| --- | --- | --- |
| Called `beginHandshake()` but remote sees nothing | Engine does not send bytes itself | Call `wrap`, flush netOut over transport |
| `wrap` consumes 0 app bytes yet produces network bytes | Currently in handshake/alert | Check handshake status, send records in order |
| `BUFFER_OVERFLOW` after `wrap` | `netOut` too small or unflushed bytes remain | Flush/grow packet buffer within limits |
| `BUFFER_OVERFLOW` after `unwrap` | `appIn` lacks space | Consume/grow application buffer within limits |
| `BUFFER_UNDERFLOW` after `unwrap` | TLS record lacks enough bytes | Keep fragment via compact, read more network data |
| `Status.OK` yet still `NEED_UNWRAP` | TLS handshake incomplete | Keep reading/unwrapping records, do not send raw app plaintext |
| `NEED_TASK` repeats with no progress | Delegated tasks not run/still pending | Fetch tasks, run/await, then resume engine |
| `OP_WRITE` continuously ready with no bytes to send | Selector interestOps not cleared | Enable only when netOut or output queue has data |
| Send buffer containing TLS record overwritten | Partial write not flushed, buffer reused early | Preserve ciphertext/positions and serialize wraps |
| Certificate valid but peer hostname wrong | Endpoint identification not enabled | Configure algorithm for protocol, use trust managers |
| Server TLS handshake fails due to missing certificate | Server context lacks appropriate key manager | Provide server identity/certificate chain |
| Socket closed right after `closeOutbound()` | `close_notify` not sent | `wrap` closure bytes then flush |
| `closeInbound()` throws `SSLException` | EOF without proper TLS close procedure | Treat as abnormal/truncation per policy |
| TLS records read/written out of order | Two threads calling wrap/unwrap concurrently in same direction | One owner per I/O direction, bounded queues |
| Code runs TLS directly over UDP and drops packets | Confusing TLS with DTLS | Choose the right protocol/transport |
| Network thread blocked by delegated task | Validation/key tasks can be expensive | Offload tasks when needed, track completion |

## 17. Self-Check Exercises

**Q1.** Does calling `SSLEngine.wrap()` automatically send data over TCP?  
**Answer:** No. `wrap` only converts plaintext/handshake into TLS record bytes in a `ByteBuffer`; the application must send them over the transport.

**Q2.** Is it normal for `wrap(emptyApp, netOut)` to consume 0 bytes yet produce 300 bytes?  
**Answer:** Yes. During a handshake, the engine can generate ClientHello or control records without application data.

**Q3.** `unwrap` returns `BUFFER_UNDERFLOW`; should you `clear()` the network buffer and discard the partial data?  
**Answer:** No. Keep unconsumed bytes, typically via `compact()`, then read more until a complete TLS record is available.

**Q4.** How does `BUFFER_OVERFLOW` from `unwrap` differ from `BUFFER_UNDERFLOW`?  
**Answer:** Overflow: lack of space in the **destination app buffer**. Underflow: lack of bytes in the **source network buffer** for the incoming record.

**Q5.** Does `getStatus() == OK` prove the TLS handshake is complete?  
**Answer:** No. You must also check `getHandshakeStatus()` and state; it could still be `NEED_WRAP/NEED_UNWRAP/NEED_TASK`.

**Q6.** Why are `getPacketBufferSize()` and `getApplicationBufferSize()` needed?  
**Answer:** To size buffers for TLS records and plaintext respectively. You still need to handle dynamic statuses and memory bounds.

**Q7.** When `NEED_TASK` occurs, can you ignore it and keep calling `unwrap`?  
**Answer:** No. Fetch and run the delegated tasks; with an event loop, consider a worker pool and wait for tasks to finish before resuming the TLS state machine.

**Q8.** Does the TLS engine automatically verify that the URL host matches the certificate if `createSSLEngine(host,port)` is used?  
**Answer:** Do not assume so. Configure trust and endpoint identification (e.g., `"HTTPS"`) when using an HTTPS client.

**Q9.** Why is `closeOutbound()` alone not enough to close TLS properly?  
**Answer:** It only marks TLS outbound as closing; you must also `wrap` to produce `close_notify`, and the application must send those TLS records over the transport before closing the socket.

**Q10.** Can you call `wrap` from two threads on the same engine concurrently to increase throughput?  
**Answer:** You should not: record ordering must be preserved; Oracle warns against two threads calling the same method concurrently. One wrap and one unwrap can run concurrently with proper ownership and synchronization.

**Q11.** If a TLS record is split by TCP across three `read()` calls, how should it be handled?  
**Answer:** Accumulate bytes in `netIn`, handle `BUFFER_UNDERFLOW`, do not treat one TCP read as one TLS record; only `unwrap`/parse when enough input is present.

**Q12.** Why does sending TLS records over UDP not automatically make it DTLS?  
**Answer:** Stream TLS and DTLS have different framing, loss/reordering, and timeout/retransmission semantics. Use the proper DTLS provider and datagram driver if choosing UDP.
