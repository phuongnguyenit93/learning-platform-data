# Orderly TLS Closure and Distinguishing Handshake Errors from Application I/O Errors

## 1. Understanding the TLS Connection Lifecycle

TLS protects the application byte stream transmitted over TCP through key negotiation, peer authentication, encryption, and integrity verification. **A successful TCP connection does not mean the TLS handshake has succeeded**, and **the end of a TLS stream does not mean a business message has finished processing**.

A typical connection goes through:

~~~text
TCP connect
    ↓
TLS handshake: ClientHello / ServerHello / certificate / Finished ...
    ↓
Application data: HTTP, RPC, custom frames, ...
    ↓
Application decides not to send more, finishes accepted data
    ↓
TLS close_notify: notification of closing the outbound direction
    ↓
Peer processes remaining data and closes its outbound direction
    ↓
Close socket and release resources
~~~

If the connection is lost at each stage, the meaning of the error differs. For example:

- During the **handshake**, the client rejects an untrusted server certificate: typically `SSLHandshakeException` is received, and there is no valid TLS session yet to send application data.
- After a **successful handshake**, the server closes TLS validly without sending the full required response: `DataInputStream.readFully(...)` may throw `EOFException`. This is **insufficient application protocol bytes**, not a broken handshake.
- At **shutdown**, one side terminates TCP abruptly before properly exchanging TLS close notifications: the system may detect a TLS/transport error or an EOF signal depending on the API and policy; do not assume by default that it was a clean close.

Two guiding principles throughout this lesson: **orderly TLS closure** and **classifying errors by actual phase + exception + application context**, rather than relying on a generic error message string.

## 2. What is `close_notify` and Why is It Needed?

TLS uses a **`close_notify` close alert** to notify that the sender will not transmit any more protected application data on the corresponding direction. It is a control message belonging to the **TLS protocol**, distinct from:

- **TCP FIN/RST:** close/termination events at the transport layer.
- **Application-level END/ACK:** meaningful messages defined by the business logic, such as `"COMMIT_OK"` or `"END_OF_RESPONSE"`.
- **`OutputStream.flush()`:** a request to push buffered application bytes, **not** a notification of the end of a TLS session.
- **`InputStream.read() == -1`:** an EOF state observed through the API; if you need to distinguish a valid TLS close from a transport loss, you must consider the context and JSSE semantics.

**`close_notify` does not guarantee that the peer has saved the transaction or processed the request**. It only signals the end of application data transmission on one TLS direction. An application that needs commit guarantees must use business-layer ACKs and have an idempotency/retry strategy.

In `SSLSocket`, Java JSSE handles sending/receiving TLS records and alerts. With `SSLEngine`, the application **transfers ciphertext itself** to the transport, so it must call `wrap()` to generate and **send all** close messages before closing the transport.

If a connection is cut without the alert required by the protocol, the risk of **truncation** arises: the application might mistakenly think it has received all data when the tail was lost. Protect with both valid TLS closure **and** application framing/length/checksum/ACK.

## 3. TLS 1.2 Duplex-Close and TLS 1.3 Half-Close

This is an important distinction when designing the closure order:

| Concept | What to know |
| --- | --- |
| **Duplex-close** in TLS 1.2 and earlier | Both directions are typically closed as a duplex closing process; you should not assume normal exchange can continue after a close notification |
| **Half-close** in TLS 1.3 | Both directions can close **independently**; the client can send `close_notify` on the outbound direction while still receiving data from the server |
| `jdk.tls.acknowledgeCloseNotify` | JSSE has a configuration for handling `close_notify` responses; do not enable it arbitrarily without understanding the protocol and application |
| Java `SSLSocket.shutdownOutput()` | Useful when the TLS protocol/session supports stopping sending while **continuing to read** |
| `SSLSocket.close()` | Useful when half-close is not needed and you want to close resources completely |

For example: the client sends `"HELLO"`, then closes the outbound direction while still waiting for the server to return `"OK"`. **TLS 1.3 half-close** allows this model. If an application is deployed across multiple TLS versions/providers, do not mechanically assume "outbound is shut down so a response can always still be received" without testing the semantics.

The two full runnable demos below **explicitly select TLSv1.3** to intentionally demonstrate half-close. The actual environment must use a JDK/provider that supports TLS 1.3.

## 4. Clean TLS Closure Sequence via SSLSocket

For request-response protocols that allow half-close, the order-safe procedure is:

1. **Stop accepting new requests to send.** Complete the accepted application data frames, preserve order, process the queue, and `flush()` any pending application bytes.
2. **End the outbound direction:** call `socket.shutdownOutput()`. In a supported model, JSSE emits the corresponding TLS close signal; after that, do not send any more application data on that direction.
3. **Receive remaining data to be read from the peer:** apply protocol framing. If expecting a response, continue reading until **the full response is received** or an error/timeout occurs.
4. **Observe the peer closing its outbound direction:** in a cleanly closed TLS session, reads after the final data may return `-1` once JSSE has processed the closure. If the app still needs required bytes, EOF at this point is a **missing application message error**.
5. **Close the inbound direction** with `shutdownInput()` **after** the peer has validly ended its outbound direction if using the half-close API; then `close()`. Or simply use `close()` when the protocol does not need to split the two directions.
6. **Bound the wait time:** an uncooperative peer or interrupted transport can cause read/closure to hang. Use timeouts and cleanup, without holding threads or connections indefinitely.

TLS 1.3 example diagram:

~~~text
CLIENT                                         SERVER
startHandshake() <--------------------------> startHandshake()
write("HELLO") ------------------------------> readFully(5) -> "HELLO"
shutdownOutput() ------ TLS close_notify ----> read() -> -1
read response <------------------------------- write("OK")
read response <-------- TLS close_notify ----- shutdownOutput()
read("OK") and read() -> -1                   shutdownInput(); close()
shutdownInput(); close()
~~~

**Order matters:** do not call `shutdownInput()` before receiving closure from the peer. The `SSLSocket` documentation warns that closing inbound too early can cause an exception. Do not completely close the socket before reading the response required by the application.

## 5. APIs and Their Respective Responsibilities

| Java API | What it does | What it does not do |
| --- | --- | --- |
| `SSLContext` | Holds key manager/trust manager/TLS provider configuration | Does not automatically verify all hostnames if the client does not enable the required endpoint policy |
| `SSLSocket.startHandshake()` | Initiates/waits for the initial TLS handshake | Does not prove the application has sent/received any frame |
| `SSLSocket.shutdownOutput()` | Ends the TLS outbound direction, sending no more application data | Not a business ACK |
| `SSLSocket.shutdownInput()` | Ends the inbound direction | Not a way to ignore a missing `close_notify` or app data |
| `SSLSocket.close()` | Closes resources; the socket cannot be reused | Does not guarantee the peer has processed/committed all requests |
| `SSLSocket.setSoTimeout(ms)` | Bounds a single blocking read operation | Not a total deadline for a request or the entire TLS lifecycle |
| `DataInputStream.readFully(byte[])` | Reads the **exact** number of requested bytes, throwing EOF if short | Does not know whether those bytes are a valid HTTP/RPC/TLS response |
| `SSLEngine.closeOutbound()` | Signals the engine not to send more app data | Does not send the alert to the transport itself; must `wrap/flush` |
| `SSLEngine.closeInbound()` | Signals end-of-input; checks TLS closure per policy | Cannot fix a missing application frame |

Once an `SSLSocket` has been closed, **do not reuse that socket**. If the handshake fails, JSSE documentation also states that the session/socket cannot continue communicating: you must clean up, log the cause, and reconnect when appropriate.

## 6. Distinguishing Errors by Phase Instead of Only Looking at Exception Names

| Phase | Scenario | Possible symptoms | How to classify |
| --- | --- | --- | --- |
| **TCP connect** | Host/port unreachable or timed out | `ConnectException`, `SocketTimeoutException` | Transport, **before TLS handshake** |
| **TLS handshake** | Server certificate not in truststore, wrong hostname/SAN | `SSLHandshakeException`, cause related to certificate/trust | TLS authentication/negotiation failure |
| **TLS handshake** | Incompatible TLS protocol/cipher, peer abort | `SSLHandshakeException`, `SSLException`, or `IOException` | Check TLS alerts **and phase**; server/client may report differently |
| **App I/O after handshake** | Frame declared n bytes, but peer closed before enough bytes | `EOFException` from `readFully` | Application missing data; do not treat as handshake fail |
| **App I/O after handshake** | Waiting for response timed out | `SocketTimeoutException` | Application read timeout even though TLS was previously valid |
| **App I/O** | Malformed TLS record, fatal alert, abnormal connection loss | `SSLException`, `SSLProtocolException`, or I/O error | TLS/transport error occurring during the app phase |
| **Shutdown** | Peer sends `close_notify` after full message | Valid EOF read, closure handled | Normal termination per protocol |
| **Shutdown** | Peer disappears without sending closure, link error | `SSLException`, I/O error, or EOF depending on the case | Check JSSE semantics, do not automatically mark as clean |

**Abbreviated inheritance tree:**

~~~text
IOException
├── SSLException
│   ├── SSLHandshakeException
│   └── SSLProtocolException
├── EOFException
├── SocketTimeoutException
└── other IOExceptions
~~~

`SSLHandshakeException` is an **`SSLException`**, and both are **`IOException`**. When writing `catch` blocks, catch from **specific to general types**. If you only have `catch(IOException)` and lump every error into a single "network error" label, you lose critical information for diagnosing TLS.

An **`EOFException` does not directly state whether the peer sent `close_notify`**. It usually only indicates that a method trying to read enough data could not do so. You must examine whether the handshake succeeded, what frame was expected, how many bytes were received, and whether the data is complete.

## 7. Explicit Handshake and Phase-Based Logging

In JSSE, the handshake can be started with `startHandshake()`, but **the first application data read/write can also trigger an implicit handshake**. Therefore, an `SSLHandshakeException` sometimes appears when code is calling `getInputStream().read()`.

To classify easily, you can track state:

~~~java
enum Phase { TCP_CONNECT, TLS_HANDSHAKE, APP_IO, TLS_SHUTDOWN }
Phase phase = Phase.TCP_CONNECT;

try {
    // Create TCP/SSLSocket and configure endpoint.
    phase = Phase.TLS_HANDSHAKE;
    sslSocket.startHandshake();

    phase = Phase.APP_IO;
    // Read/write messages per application framing, with a deadline.

    phase = Phase.TLS_SHUTDOWN;
    // Close TLS in the order defined by the protocol.
} catch (SSLHandshakeException e) {
    // TLS handshake did not meet the required security level.
} catch (SSLException e) {
    // Other TLS error: inspect phase, alert, and cause.
} catch (SocketTimeoutException e) {
    // Timeout in which phase? Handshake, app read, or shutdown?
} catch (IOException e) {
    // Transport or other read/write/EOF error.
} finally {
    // Clean up socket if still open.
}
~~~

*This is **illustrative pseudocode**; the `sslSocket` variable, imports, logging, and handling policies must be fully implemented. The two standalone programs below run on JDK 17+.*

Fields that should be logged in a controlled manner: connection/session ID, phase, operation (`connect`/`startHandshake`/`readFully`/`shutdownOutput`), exception class, cause chain, expected vs. actual application bytes received, negotiated TLS protocol/cipher if any, and total duration. **Do not log private keys, passwords, raw plaintext, or full sensitive handshake data.**

Trust errors typically involve CA chains, SAN/hostname, expired certificates, key usage, ciphers, or mTLS policies. Do not "fix" them with an `X509TrustManager` that returns true for all certificates or by disabling endpoint verification.

## 8. Preparing the Test Environment: Role-Separated Keystore and Truststore

The next two demos create a TLS server/client on **127.0.0.1** in the same JVM, using JDK 17+ with `keytool`. They need two **different** self-signed certificates to demonstrate the cases where the client trusts and does not trust the server.

In a separate practice directory, run the following commands in order (each `keytool` command written on **one line**):

~~~bash
keytool -genkeypair -alias localhost -keyalg RSA -keysize 2048 -validity 1 -storetype PKCS12 -keystore loopback.p12 -storepass changeit -keypass changeit -dname "CN=localhost" -ext "SAN=IP:127.0.0.1,DNS:localhost" -noprompt
keytool -genkeypair -alias unrelated -keyalg RSA -keysize 2048 -validity 1 -storetype PKCS12 -keystore unrelated.p12 -storepass changeit -keypass changeit -dname "CN=unrelated" -noprompt
javac TlsOrderlyCloseDemo.java TlsErrorStageDemo.java
java TlsOrderlyCloseDemo loopback.p12 changeit
java TlsErrorStageDemo loopback.p12 unrelated.p12 changeit
~~~

**Explanation:**

- `loopback.p12` contains the server's self-signed private key/certificate; the certificate has a SAN for IP `127.0.0.1` and DNS `localhost`.
- `unrelated.p12` contains the certificate of a **different** entity, which cannot serve as a trust anchor for the demo server. A client using this store will reject the server certificate during the handshake.
- `changeit`, self-signed certificates, RSA 2048-bit, and 1-day validity are **for demo purposes only**, not for production security. Do not put the server's private key on the client in a real deployment.
- The demo can read the certificate from `loopback.p12` to build a trust manager in the **same JVM**. In practice, the server keeps the private key, and the client only needs to trust the public certificate/CA. A self-signed certificate not in a public truststore will be rejected as expected.
- The client enables `SSLParameters.setEndpointIdentificationAlgorithm("HTTPS")`. This causes endpoint matching against the SAN to be performed, rather than just "seeing a trusted certificate is enough."

If testing on a machine that does not allow TCP loopback or a Java/provider without TLS 1.3, do not work around it with trust-all. Check the environment error or use a suitable JDK.

## 9. Complete Java 17+ Example: Orderly TLS Closure Across Both Directions

The first program has two endpoints in the same JVM. The client completes the handshake, sends `HELLO`, and calls `shutdownOutput()`. The server reads the full request, observes TLS EOF on the client's outbound direction, sends `OK`, and also calls `shutdownOutput()`. The client receives `OK` and EOF. Both sides call `shutdownInput()` after receiving the read-direction close.

Create the file `TlsOrderlyCloseDemo.java`:

~~~java
import java.io.DataInputStream;
import java.io.IOException;
import java.io.InputStream;
import java.net.InetAddress;
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.Path;
import java.security.KeyStore;
import java.security.SecureRandom;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.concurrent.TimeUnit;
import javax.net.ssl.KeyManagerFactory;
import javax.net.ssl.SSLContext;
import javax.net.ssl.SSLParameters;
import javax.net.ssl.SSLServerSocket;
import javax.net.ssl.SSLSocket;
import javax.net.ssl.TrustManagerFactory;

public class TlsOrderlyCloseDemo {
    static SSLContext context(Path storePath, char[] password) throws Exception {
        KeyStore store = KeyStore.getInstance("PKCS12");
        try (InputStream file = Files.newInputStream(storePath)) {
            store.load(file, password);
        }
        KeyManagerFactory keys = KeyManagerFactory.getInstance(
                KeyManagerFactory.getDefaultAlgorithm());
        keys.init(store, password);
        TrustManagerFactory trust = TrustManagerFactory.getInstance(
                TrustManagerFactory.getDefaultAlgorithm());
        trust.init(store); // Only share the store in this local demo.
        SSLContext context = SSLContext.getInstance("TLS");
        context.init(keys.getKeyManagers(), trust.getTrustManagers(),
                new SecureRandom());
        return context;
    }

    public static void main(String[] args) throws Exception {
        if (args.length != 2) {
            throw new IllegalArgumentException("keystore.p12 password");
        }
        SSLContext tls = context(Path.of(args[0]), args[1].toCharArray());
        ExecutorService worker = Executors.newSingleThreadExecutor();
        try (SSLServerSocket listener = (SSLServerSocket) tls
                .getServerSocketFactory().createServerSocket(
                        0, 8, InetAddress.getByName("127.0.0.1"))) {
            listener.setEnabledProtocols(new String[] {"TLSv1.3"});
            listener.setSoTimeout(5_000);
            Future<Boolean> serverReadEof = worker.submit(() -> {
                try (SSLSocket peer = (SSLSocket) listener.accept()) {
                    peer.setSoTimeout(5_000);
                    peer.setEnabledProtocols(new String[] {"TLSv1.3"});
                    peer.startHandshake();

                    byte[] request = new byte[5];
                    new DataInputStream(peer.getInputStream()).readFully(request);
                    if (!"HELLO".equals(new String(request, StandardCharsets.US_ASCII))) {
                        throw new IOException("unexpected request");
                    }
                    boolean receivedClose = peer.getInputStream().read() == -1;
                    peer.getOutputStream().write(
                            "OK".getBytes(StandardCharsets.US_ASCII));
                    peer.getOutputStream().flush();
                    peer.shutdownOutput();
                    peer.shutdownInput();
                    return receivedClose;
                }
            });

            try (SSLSocket client = (SSLSocket) tls.getSocketFactory()
                    .createSocket("127.0.0.1", listener.getLocalPort())) {
                client.setEnabledProtocols(new String[] {"TLSv1.3"});
                client.setSoTimeout(5_000);
                SSLParameters parameters = client.getSSLParameters();
                parameters.setEndpointIdentificationAlgorithm("HTTPS");
                client.setSSLParameters(parameters);
                client.startHandshake();

                client.getOutputStream().write(
                        "HELLO".getBytes(StandardCharsets.US_ASCII));
                client.getOutputStream().flush();
                client.shutdownOutput();

                byte[] response = new byte[2];
                new DataInputStream(client.getInputStream()).readFully(response);
                boolean responseEof = client.getInputStream().read() == -1;
                client.shutdownInput();

                System.out.println("handshake completed: true");
                System.out.println("server received TLS EOF: "
                        + serverReadEof.get(5, TimeUnit.SECONDS));
                System.out.println("response: "
                        + new String(response, StandardCharsets.US_ASCII));
                System.out.println("client received TLS EOF: " + responseEof);
            }
        } finally {
            worker.shutdownNow();
        }
    }
}
~~~

Run commands:

~~~bash
javac TlsOrderlyCloseDemo.java
java TlsOrderlyCloseDemo loopback.p12 changeit
~~~

Output if the platform supports TLS 1.3 and loopback:

~~~text
handshake completed: true
server received TLS EOF: true
response: OK
client received TLS EOF: true
~~~

**Points to observe:**

1. `SSLSocket.startHandshake()` performs an explicit handshake, so the program can distinguish the TLS phase before application I/O.
2. `client.shutdownOutput()` is called only **after** writing `HELLO`. After that, the server reads `-1` when the client's outbound direction ends, yet can still send `OK` in TLS 1.3.
3. The server sends and flushes the response, then calls `shutdownOutput()`; the client reads the two bytes and reads to EOF, then calls `shutdownInput()`.
4. `try-with-resources` closes the socket last. `setSoTimeout` bounds blocking reads and `Future.get(5, SECONDS)` bounds how long the test thread waits for the result.
5. Because the demo uses the **same SSLContext on both sides in the same JVM**, it simplifies credential management; this is **not a model for distributing server private keys to clients in production**.
6. The `-1` result is the end of stream handled by JSSE in this orderly TLS close test case; it is **not** itself a business ACK. Here the `OK` response is application data, separate from the TLS close alert.

All response-reading steps are performed **before** closing input. If the entire socket were closed immediately after sending `HELLO`, the client would have no chance to receive `OK`, even though the server might have processed the request.

## 10. Complete Java 17+ Example: Handshake Trust Error vs. Application EOF

The second example creates two different TLS connections:

- **Run 1:** the client uses the `unrelated.p12` truststore. Because the server's certificate is not trusted by the trust manager, the client receives **`SSLHandshakeException` from `startHandshake()`**. The server side may receive a TLS alert **or** an `IOException`/`SocketException` due to the client aborting the connection during the handshake; do not hardcode a specific error type on the server side.
- **Run 2:** the client uses a truststore that accepts the server certificate, so the handshake **succeeds**. The server actively sends a TLS `close_notify` **without sending response data**. The client requires reading 4 application bytes, so `DataInputStream.readFully(new byte[4])` throws **`EOFException`**; this is an **application framing failure** despite a clean TLS close.

Create the file `TlsErrorStageDemo.java`:

~~~java
import java.io.DataInputStream;
import java.io.EOFException;
import java.io.IOException;
import java.io.InputStream;
import java.net.InetAddress;
import java.nio.file.Files;
import java.nio.file.Path;
import java.security.KeyStore;
import java.security.SecureRandom;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.concurrent.TimeUnit;
import javax.net.ssl.KeyManagerFactory;
import javax.net.ssl.SSLContext;
import javax.net.ssl.SSLHandshakeException;
import javax.net.ssl.SSLParameters;
import javax.net.ssl.SSLServerSocket;
import javax.net.ssl.SSLSocket;
import javax.net.ssl.TrustManagerFactory;

public class TlsErrorStageDemo {
    static KeyStore load(Path file, char[] password) throws Exception {
        KeyStore store = KeyStore.getInstance("PKCS12");
        try (InputStream input = Files.newInputStream(file)) {
            store.load(input, password);
        }
        return store;
    }

    static SSLContext context(Path serverStore, Path trustStore, char[] password,
                              boolean includeServerKey) throws Exception {
        KeyStore trusted = load(trustStore, password);
        TrustManagerFactory trust = TrustManagerFactory.getInstance(
                TrustManagerFactory.getDefaultAlgorithm());
        trust.init(trusted);
        javax.net.ssl.KeyManager[] keys = null;
        if (includeServerKey) {
            KeyStore server = load(serverStore, password);
            KeyManagerFactory manager = KeyManagerFactory.getInstance(
                    KeyManagerFactory.getDefaultAlgorithm());
            manager.init(server, password);
            keys = manager.getKeyManagers();
        }
        SSLContext tls = SSLContext.getInstance("TLS");
        tls.init(keys, trust.getTrustManagers(), new SecureRandom());
        return tls;
    }

    static SSLSocket client(SSLContext tls, int port) throws Exception {
        SSLSocket socket = (SSLSocket) tls.getSocketFactory()
                .createSocket("127.0.0.1", port);
        socket.setEnabledProtocols(new String[] {"TLSv1.3"});
        socket.setSoTimeout(5_000);
        SSLParameters parameters = socket.getSSLParameters();
        parameters.setEndpointIdentificationAlgorithm("HTTPS");
        socket.setSSLParameters(parameters);
        return socket;
    }

    public static void main(String[] args) throws Exception {
        if (args.length != 3) {
            throw new IllegalArgumentException(
                    "server-keystore.p12 wrong-truststore.p12 password");
        }
        Path serverStore = Path.of(args[0]);
        Path wrongStore = Path.of(args[1]);
        char[] password = args[2].toCharArray();
        SSLContext serverTls = context(serverStore, serverStore, password, true);
        SSLContext trustedClient = context(serverStore, serverStore, password, false);
        SSLContext untrustedClient = context(serverStore, wrongStore, password, false);
        ExecutorService worker = Executors.newSingleThreadExecutor();
        try (SSLServerSocket listener = (SSLServerSocket) serverTls
                .getServerSocketFactory().createServerSocket(
                        0, 8, InetAddress.getByName("127.0.0.1"))) {
            listener.setEnabledProtocols(new String[] {"TLSv1.3"});
            listener.setSoTimeout(5_000);
            Future<Boolean> firstServer = worker.submit(() -> {
                try (SSLSocket peer = (SSLSocket) listener.accept()) {
                    peer.setEnabledProtocols(new String[] {"TLSv1.3"});
                    peer.setSoTimeout(5_000);
                    try {
                        peer.startHandshake();
                    } catch (IOException expected) {
                        // Peer rejected the server cert; the peer-side error
                        // may arrive as a TLS alert or a transport abort.
                    }
                    return true;
                }
            });

            boolean handshakeRejected;
            try (SSLSocket socket = client(untrustedClient, listener.getLocalPort())) {
                try {
                    socket.startHandshake();
                    handshakeRejected = false;
                } catch (SSLHandshakeException expected) {
                    handshakeRejected = true;
                }
            }
            if (!handshakeRejected || !firstServer.get(5, TimeUnit.SECONDS)) {
                throw new AssertionError("expected untrusted certificate failure");
            }

            Future<Boolean> secondServer = worker.submit(() -> {
                try (SSLSocket peer = (SSLSocket) listener.accept()) {
                    peer.setEnabledProtocols(new String[] {"TLSv1.3"});
                    peer.setSoTimeout(5_000);
                    peer.startHandshake();
                    peer.shutdownOutput();
                    return peer.getInputStream().read() == -1;
                }
            });
            boolean applicationEof;
            try (SSLSocket socket = client(trustedClient, listener.getLocalPort())) {
                socket.startHandshake();
                try {
                    new DataInputStream(socket.getInputStream())
                            .readFully(new byte[4]);
                    applicationEof = false;
                } catch (EOFException expected) {
                    applicationEof = true;
                }
                socket.shutdownOutput();
                socket.shutdownInput();
            }
            if (!applicationEof || !secondServer.get(5, TimeUnit.SECONDS)) {
                throw new AssertionError("expected clean TLS EOF but incomplete app frame");
            }
            System.out.println("untrusted handshake: SSLHandshakeException");
            System.out.println("trusted handshake: succeeded");
            System.out.println("application readFully: EOFException");
        } finally {
            worker.shutdownNow();
        }
    }
}
~~~

Run commands:

~~~bash
javac TlsErrorStageDemo.java
java TlsErrorStageDemo loopback.p12 unrelated.p12 changeit
~~~

Output:

~~~text
untrusted handshake: SSLHandshakeException
trusted handshake: succeeded
application readFully: EOFException
~~~

**Important explanations:**

1. The demo uses **two different self-signed certificates**, without using "trust-all" or creating an empty truststore that triggers a `trustAnchors` error. The path from `startHandshake()` to `SSLHandshakeException` reflects real certificate verification.
2. During a failed handshake phase, the server side may report `SSLException`, `SocketException`, or another I/O error depending on timing. The demo does **not** require receiving the same exception type at both ends.
3. In the second run, the handshake succeeds with the trusted certificate, and the server calls `shutdownOutput()` to send the TLS direction-close signal. The client's `readFully(4)` hits EOF before receiving any bytes, so `EOFException` reflects **missing required application data**.
4. After observing EOF, the client can close its outbound direction (`shutdownOutput`), then close its inbound direction (`shutdownInput`); the server also waits to see EOF from the client to complete a clean half-close.
5. Do not conclude that `EOFException` means "TLS is under attack" or "TLS handshake failed." To detect a missing close alert, you must inspect JSSE/TLS and framing, such as `SSLEngine.closeInbound()` in a self-managed transport model.

## 11. Application Protocols Still Need Framing and an EOF Policy

TLS protects bytes; it **does not delimit business messages**. One `OutputStream.write` on the client does not necessarily correspond to one `InputStream.read` on the server. With a length-prefixed protocol, a frame might look like:

~~~text
[4 byte length big-endian][length byte payload]
00 00 00 05              48 45 4C 4C 4F
   length = 5               "HELLO"
~~~

The reader is responsible for:

1. Reading the **complete header** or detecting a shortfall.
2. Checking `length >= 0` and `length <= MAX_PAYLOAD_BYTES` **before allocating** a buffer for that length.
3. Reading the complete payload, handling short reads/timeouts/EOF.
4. Passing the message up to business logic only when the data is complete and valid.
5. If TLS closes cleanly before the header/body is complete, **reporting an application protocol error**. If the app expects a response/ACK that has not arrived, do not treat `close_notify` as a substitute ACK.

Example code for handling the result after the handshake:

~~~java
DataInputStream in = new DataInputStream(sslSocket.getInputStream());
int length = in.readInt();
if (length < 0 || length > MAX_PAYLOAD_BYTES) {
    throw new IOException("invalid application frame length");
}
byte[] body = new byte[length];
in.readFully(body); // EOFException if the TLS stream ends before the full body arrives.
~~~

*This illustrative snippet sits inside a class with `sslSocket`, `MAX_PAYLOAD_BYTES`, and imports; it is not a standalone program.*

Do not treat `SSLException` and `EOFException` as a single type of "network fail" and unconditionally retry the request. If the server already processed the request and only the response was lost, retrying could cause **duplicate processing**. You need an idempotency key or an explicit result-confirmation protocol.

## 12. Closing TLS with SSLEngine Requires Actively Sending close_notify

`SSLEngine` differs from `SSLSocket` because it **does not read/write the socket itself**. The application transfers encrypted data between the engine and the transport (usually a `SocketChannel`).

To close **outbound** cleanly:

~~~java
engine.closeOutbound();
while (!engine.isOutboundDone()) {
    // Call engine.wrap(emptyApplicationBuffer, networkOutputBuffer)
    // to generate TLS records, including close_notify.
    // Handle SSLEngineResult.Status and HandshakeStatus;
    // FLIP networkOutputBuffer and write all ciphertext to the transport.
}
~~~

*This is **pseudocode describing the algorithm**, not a standalone program: `engine`, buffers, delegated tasks, and transport I/O are initialized by the application.*

`closeOutbound()` **only changes the engine state**; you must continue calling `wrap()` and **send all** TLS bytes out to the network. If you close TCP immediately without sending the close alert, the peer may observe a truncated transport.

For **inbound**, receive ciphertext into the network buffer and call `engine.unwrap(...)`. Once a valid close alert is received/decrypted, the engine may report `SSLEngineResult.Status.CLOSED` or `isInboundDone()==true`. If the transport hits EOF, call `engine.closeInbound()` per JSSE guidelines to confirm closure; in cases where the peer did not send the required alert, this method may throw `SSLException`. Do not ignore `BUFFER_UNDERFLOW`, `BUFFER_OVERFLOW`, or delegated tasks in a real implementation.

TLS 1.3 allows closing inbound/outbound independently; do not assume calling `closeOutbound` alone will automatically close both outbound **and** inbound. Follow JSSE details and test against the deployed version/provider.

## 13. Timeouts and Handling an Uncooperative Peer

To avoid hanging while waiting for a peer response or close alert:

- `SSLSocket.setSoTimeout(5_000)` bounds **a single blocking read**, not the total duration of the entire TLS session.
- If a total request/shutdown deadline is required, use monotonic time (`System.nanoTime()`) or a deadline-aware coordinator; after the deadline, close/cancel the operation per policy.
- `Future.get(5, TimeUnit.SECONDS)` in the demo only bounds how long **the test thread waits**. It does not automatically stop the running operation; combine it with close/cancellation.
- If the peer does not send `close_notify` and the transport is cut, classify it as a TLS/transport error—do not lump it into "received EOF successfully" if the protocol requires closure.
- If a fatal TLS alert occurs, do not try to continue reusing the `SSLSocket` to process application data.
- If a timeout occurs in `startHandshake()`, log it in the handshake phase. If a timeout occurs while waiting for a response after `startHandshake()`, log it in the APP_IO phase. **Same `SocketTimeoutException`, different nature.**

In a multi-connection server, bound threads, socket count, output queues, and buffer capacity. Waiting indefinitely for a close alert can exhaust resources even when handshake and encryption are completely correct.

## 14. Security: Trust, Hostname, Certificates, and Error Observability

Practices to maintain:

- The server has a private key and certificate chain. The client has appropriate trust anchors and **does not need the server's private key**.
- Enable endpoint identification/hostname verification matching the application protocol. The demo uses `SSLParameters.setEndpointIdentificationAlgorithm("HTTPS")` and SAN IP `127.0.0.1`.
- Do not use an `X509TrustManager` that trusts all certificates, and do not disable SAN/hostname checking to "fix" a handshake.
- Certificates can be expired, have the wrong SAN, lack an intermediate CA, be untrusted, or use an unacceptable key/protocol/cipher; `SSLHandshakeException` is a signal to investigate TLS policy.
- If the environment has TLS 1.3 post-handshake messages, TLS errors can also occur after the initial `startHandshake()`; therefore, you need both the phase **and** the cause chain.
- Do not equate TLS close with the application completing a transaction. If business logic needs to know the server committed data, it must receive an **application-level ACK** before deciding to retry/close.
- Do not put demo keystores or the password `changeit` into production; keystores containing private keys must be protected. Public certificates and a separate truststore for the client are the right architecture.

In a **controlled test** environment, JSSE supports TLS logging:

~~~bash
java -Djavax.net.debug=ssl,handshake,record TlsErrorStageDemo loopback.p12 unrelated.p12 changeit
~~~

Logs may contain certificate chains, cipher/protocol details, record metadata, and sensitive operational information. Do not enable verbose logging across an entire production system. When inspecting stack traces, follow `getCause()` instead of relying on a `getMessage()` string that may vary across JDKs/providers.

## 15. Common Misconceptions to Avoid

| Misconception | Why is it wrong? | How to fix |
| --- | --- | --- |
| "TCP connected means TLS authenticated." | The TLS handshake has not occurred or completed yet | Call `startHandshake()` and verify the peer |
| "Every error in `read` is an application I/O error." | The first read can trigger an **implicit handshake** | Classify by phase, use an explicit handshake |
| "`SSLHandshakeException` is also an application EOF." | The handshake failed to establish a secure session | Do not use the socket; check trust/cert/protocol |
| "`SSLException` only happens during the handshake." | Malformed TLS records/alerts can appear afterward | Inspect phase, cause, and alert |
| "`EOFException` always means an improper TLS close." | `readFully` missing a frame can happen after a clean TLS close | Check how many bytes the application expected |
| "Just calling `flush` sends `close_notify`." | Flush does not signal the end of application data | Use JSSE's closure API |
| "You can call `shutdownInput` before the peer closes its outbound direction." | Can cause a closure exception | Read the appropriate closure first |
| "`shutdownOutput` and then continue to `write`." | The outbound direction is already closed | Stop sending, create a new session if needed |
| "TLS 1.2/1.3 handle half-close identically." | Version semantics differ | Choose the closing protocol and test |
| "`SSLEngine.closeOutbound()` sends all TLS records automatically." | The engine does not own the transport | `wrap` and flush network bytes |
| "TLS `close_notify` is an application ACK." | It only signals no more data will be sent | Design business responses/ACKs |
| "If the cert isn't trusted, use trust-all to make it work." | Defeats peer authentication | Fix truststore/CA/SAN properly |
| "A clean close guarantees the peer committed the request." | Transport does not confirm business logic | Use idempotency and ACKs |
| "If `Future.get` timed out, the operation has stopped." | Timeout only limits the caller's wait | Cancel/close and manage state |
| "Catch `IOException` before `SSLHandshakeException`." | The specific branch is shadowed | Catch subclasses before superclasses |

## 16. Self-Check and Practice Exercises

**Question 1.** The client sends `HELLO`, calls `shutdownOutput()`, yet still wants to receive `OK`. Why does this make sense with TLS 1.3?

*Answer:* TLS 1.3 supports half-close, where ending the outbound direction does not require ending the inbound direction. Both sides still need to respect closure and application conditions.

**Question 2.** The client receives `SSLHandshakeException` because the certificate is not in the truststore. Should it send data on that socket and close afterward?

*Answer:* No. The TLS session did not meet the required security level, and the socket is no longer usable. You must clean up and fix trust/certificate/hostname/policy before attempting a new session.

**Question 3.** After `startHandshake()` succeeds, the server sends `close_notify` without a 4-byte response. What will the client's `readFully(new byte[4])` do?

*Answer:* It throws `EOFException` because the **application frame is missing bytes**, not as evidence of a failed handshake. This is the scenario in `TlsErrorStageDemo`.

**Question 4.** `SSLEngine.closeOutbound()` has finished executing; why is it not guaranteed that the peer has received `close_notify`?

*Answer:* The engine only generates TLS records; the application must continue calling `wrap()` and write all ciphertext to the transport.

**Question 5.** A Java service logs every `IOException` as "TLS handshake failed." What is wrong with this?

*Answer:* It conflates connect, handshake, app read, shutdown, and framing errors. It should log phase, operation, type, cause, and bytes expected/received.

**Question 6.** The client sees the server send a close alert and the full response; can it be certain the server committed to the database?

*Answer:* No, unless the application protocol defines a response/ACK that means commit confirmation. TLS close only marks the end of protected data transmission.

**Practice:**

1. Run `TlsOrderlyCloseDemo` and trace the order of `HELLO`, client `shutdownOutput()`, server EOF, `OK`, server `shutdownOutput()`, and client EOF.
2. In `TlsErrorStageDemo`, replace the untrusted truststore with one that trusts the server; verify that the handshake succeeds without disabling endpoint verification.
3. Have the server in the second run send **exactly 4 bytes** before `shutdownOutput()`; observe `readFully(4)` succeeding. Change it to send only 2 bytes to demonstrate an incomplete application frame despite a clean TLS close.
4. Try creating a read timeout scenario after the handshake to see why `SocketTimeoutException` is not necessarily a certificate negotiation error.
5. Add a phase enum in production code and an error metric table separating `HANDSHAKE_FAILURE`, `APP_FRAME_INCOMPLETE`, `APP_TIMEOUT`, and `TLS_SHUTDOWN_ERROR`.
6. If you have a separate test environment, try configuring TLS 1.2 to observe shutdown semantics different from TLS 1.3; do not carry half-close assumptions into production before testing.
