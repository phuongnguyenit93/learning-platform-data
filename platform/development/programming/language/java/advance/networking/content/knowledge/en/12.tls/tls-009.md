# The wrap, unwrap, NEED_TASK Cycle and Handling Insufficient Data or Buffer Space with SSLEngine (Java TLS)

When using `javax.net.ssl.SSLEngine` to implement TLS over TCP/NIO, the programmer is **personally responsible for moving encrypted TLS bytes onto the network and feeding bytes received from the network into the engine**. `SSLEngine` does not own a `Socket` or perform `read/write` on behalf of the application like `SSLSocket`. The two core methods are `wrap()` and `unwrap()`; each call returns an `SSLEngineResult` containing **two independent statuses**: the buffer processing status and the TLS handshake progress status.

A correct cycle must accomplish **all** of the following:

1. Put buffers into the correct read/write mode and preserve unconsumed bytes.
2. Call `wrap()` to obtain outbound TLS data (handshake or application data) and **send all of that ciphertext** over the transport.
3. Call `unwrap()` to decrypt inbound TLS bytes, obtain plaintext, or advance the handshake.
4. When `HandshakeStatus.NEED_TASK`, retrieve and run all **delegated tasks**, then continue the state machine; do not wait for new I/O instead of running tasks.
5. When `BUFFER_UNDERFLOW`, **keep the already-received bytes**, read more TLS data, and retry (grow the inbound packet buffer if capacity is insufficient).
6. When `BUFFER_OVERFLOW`, **drain or grow the destination buffer**, do not discard data that still needs processing, and then retry.
7. Handle `NEED_WRAP`, `NEED_UNWRAP`, `NEED_UNWRAP_AGAIN`, handshake completion, TLS `close_notify`, and errors/timeouts.

This is advanced content under the **TLS** topic. The Java 17+ example uses an in-memory client and server `SSLEngine` to verify `BUFFER_OVERFLOW`, `BUFFER_UNDERFLOW`, and `NEED_TASK` **without needing a network or test certificates**. The example stops before the TLS handshake completes: it is **not** an authenticated secure connection and must not be used to transmit secrets.

## 1. Data model: application bytes and TLS network bytes

`SSLEngine` separates application bytes from TLS bytes on the network:

~~~text
SENDING APPLICATION                  SSLEngine                  TCP TRANSPORT
  appOut [plaintext] ---- src ----> wrap() ---- dst ----> netOut [TLS records]
                                                              |
                                                SocketChannel.write(...)
                                                              |
                                                              v
                                               (TCP network, partial read/write possible)
                                                              |
                                                SocketChannel.read(...)
                                                              |
  appIn  [plaintext] <--- dst ---- unwrap() <---- src ---- netIn  [TLS records]
RECEIVING APPLICATION
~~~

Typically, **four separate ByteBuffers** are managed, though some libraries choose an equivalent queue structure:

| Buffer | What does it hold? | Common state transitions |
| --- | --- | --- |
| `appOut` | Plaintext waiting to be sent | Application fills data → `flip()` → `wrap(appOut, netOut)` |
| `netOut` | TLS records/ciphertext produced by the engine, waiting for socket send | `wrap` writes to buffer → `flip()` → transport writes until empty → `clear()`/`compact()` |
| `netIn` | TLS records/ciphertext read from TCP, may only have received a **partial record** | Transport reads in write mode → `flip()` → `unwrap(netIn, appIn)` → `compact()` if bytes remain |
| `appIn` | Plaintext decrypted from TLS | `unwrap` writes to buffer → `flip()` → application consumes → `clear()` or `compact()` |

In TLS over TCP, **a single `SocketChannel.read()` does not correspond to one TLS record**: it may receive the first 3 bytes of a header, a partial record, a complete record, or multiple records. An `unwrap()` call processes according to TLS record boundaries; never assume that a single socket read is sufficient.

Similarly, a single `wrap()` call does not guarantee that all application bytes in `appOut` are processed. It may consume partial plaintext, produce ciphertext, or during a handshake **consume no plaintext at all while still producing a TLS handshake record**.

**Both directions must progress independently yet in coordination:** an inbound `unwrap` can cause the engine to transition to `NEED_WRAP`; an outbound `wrap` can cause the engine to require reading `NEED_UNWRAP`. You cannot implement “call wrap once and then unwrap once” to complete a TLS session.

## 2. Preparing SSLEngine for the right role

Initialize with an appropriate `SSLContext` and set the role **before the handshake**:

~~~java
// Java 17+ fragment: omits TLS credentials/trust configuration and TCP transport.
SSLContext context = SSLContext.getInstance("TLS");
context.init(keyManagers, trustManagers, secureRandom);

SSLEngine engine = context.createSSLEngine(peerHost, peerPort);
engine.setUseClientMode(true); // TLS client side

// For HTTPS, hostname identification must be configured if using SSLEngine directly.
SSLParameters parameters = engine.getSSLParameters();
parameters.setEndpointIdentificationAlgorithm("HTTPS");
engine.setSSLParameters(parameters);

engine.beginHandshake(); // Initiates handshake, does not wait for completion.
~~~

The snippet above is a **fragment**; `keyManagers`, `trustManagers`, `secureRandom`, `peerHost`, and `peerPort` must be defined according to the environment. Do not use a “trust all certificates” TrustManager to simplify production labs. The **server** side needs appropriate key material/certificates to actually complete the handshake with the required protocol/cipher suite; default initialization alone does not replace that configuration.

`setUseClientMode(false)` is used for the server; the role must not be changed after the handshake starts. `beginHandshake()` can be called explicitly; if not called, the initial `wrap()/unwrap()` can also trigger the handshake automatically. `beginHandshake()` **does not wait for the entire TLS negotiation to finish**.

Depending on the application protocol, configure endpoint identification, SNI, ALPN, and the trust store appropriately. For example, `"HTTPS"` is only suitable for HTTPS-style hostname verification; other protocols must have corresponding peer validation rules. Evaluating `SSLEngineResult.Status.OK` does not mean the certificate has been verified and the session is secure if the handshake has not finished.

## 3. Understanding the two status types returned by SSLEngineResult

After each operation:

~~~java
SSLEngineResult result = engine.wrap(appOut, netOut);

SSLEngineResult.Status status = result.getStatus();
SSLEngineResult.HandshakeStatus handshake =
        result.getHandshakeStatus();

int consumed = result.bytesConsumed();
int produced = result.bytesProduced();
~~~

**`getStatus()`** describes the condition of the **`wrap()/unwrap()` call just performed**; **`getHandshakeStatus()`** indicates the next TLS action to take. **Both** must be examined. An `unwrap()` call can return `Status.OK` alongside `HandshakeStatus.NEED_TASK` or `NEED_WRAP`, and if you only handle `OK`, the state machine can stall.

### 3.1. SSLEngineResult.Status — data/buffer status

| Status | Meaning | Proper handling |
| --- | --- | --- |
| `OK` | The call processed validly and did not need to report insufficient buffer space this time | Check `bytesConsumed/Produced`, handle output bytes and handshake status |
| `BUFFER_UNDERFLOW` | For `unwrap`, the input TLS bytes are **not enough to process a record** | Keep unused bytes, `compact()`/grow network buffer if needed, read more then `flip()` and `unwrap` again |
| `BUFFER_OVERFLOW` | The **destination buffer** does not have enough space to hold the result | For `wrap`: drain/grow `netOut`; for `unwrap`: drain/grow `appIn`; then retry |
| `CLOSED` | The engine/corresponding direction has been closed or is finishing TLS close | Send any remaining close records generated, handle `close_notify`, and clean up |

A note: **`BUFFER_UNDERFLOW` does not mean the connection was cut**. It usually just means TCP has only delivered a partial record. Nor does it mean “grow the app buffer”: for `unwrap`, underflow is **insufficient source ciphertext**, so first keep unused bytes and receive more. Only `BUFFER_OVERFLOW` requires handling an insufficient **destination** space.

### 3.2. HandshakeStatus — what TLS step does the engine need next?

| Handshake status | Action required | Do not confuse with |
| --- | --- | --- |
| `NEED_WRAP` | Call `wrap()`, often with empty plaintext during the handshake phase; send `netOut` data over TCP | Not “need a new app request” |
| `NEED_UNWRAP` | Read inbound TLS or use existing bytes, call `unwrap()`; if underflow, wait for more network bytes | Not “call unwrap repeatedly with 0 bytes” |
| `NEED_UNWRAP_AGAIN` | **Call `unwrap()` again** so JSSE processes internally buffered data; do not assume waiting for a new network read | Does not mean `BUFFER_UNDERFLOW` |
| `NEED_TASK` | Run all delegated tasks returned by the engine; only after completion continue deciding wrap/unwrap | Do not ignore because there is no socket event |
| `FINISHED` | The handshake **just finished** on this `wrap/unwrap` result | Do not write a loop that only waits for `engine.getHandshakeStatus() == FINISHED` |
| `NOT_HANDSHAKING` | Currently there is no handshake waiting to progress | Does not mean all application messages have finished processing |

`FINISHED` is a transient status, typically appearing in the `SSLEngineResult` of the operation that just completed the handshake; afterward, the engine status may return to `NOT_HANDSHAKING`. Key updates or TLS 1.3 post-handshake events may require further TLS steps later, so code must still check result statuses while transferring app data.

### 3.3. The two counters as proof of progress

- For `wrap(appOut, netOut)`, `bytesConsumed()` is the **number of plaintext bytes taken from `appOut`**, and `bytesProduced()` is the **number of TLS record bytes placed into `netOut`**.
- For `unwrap(netIn, appIn)`, `bytesConsumed()` is the **number of TLS record bytes consumed from `netIn`**, and `bytesProduced()` is the **number of plaintext bytes placed into `appIn`**.

During a handshake, a `wrap` call can have `consumed=0, produced>0`; an `unwrap` call can have `consumed>0, produced=0`. Do **not** treat `produced=0` as a general error: it may be processing TLS control messages, needing a delegated task, or needing to send the next handshake record.

Conversely, a loop that repeatedly gets `consumed=0, produced=0` and **has no change in state, buffers, or I/O readiness** risks a busy-loop. You must wait for more data, drain buffers, run tasks, or report an error/close instead of spinning.

## 4. ByteBuffer and TLS record sizes

Three important properties:

~~~text
0 <= position <= limit <= capacity
remaining() = limit - position

WRITE mode (receiving bytes from socket / engine writing output):
  position = number of bytes placed in the buffer
  limit usually = capacity

flip(): WRITE -> READ
  limit = position; position = 0

READ mode (engine consuming bytes from buffer / socket sending):
  [0 .. position)    = already-read portion
  [position .. limit)= unread bytes remaining

compact(): READ -> WRITE
  keeps bytes from [position .. limit) at the start of the buffer,
  position = number of unread bytes; limit = capacity

clear(): sets position=0, limit=capacity;
  DOES NOT physically erase old bytes and DOES NOT preserve unsent data.
~~~

For the engine:

~~~java
SSLSession session = engine.getSession();
ByteBuffer netIn = ByteBuffer.allocate(session.getPacketBufferSize());
ByteBuffer netOut = ByteBuffer.allocate(session.getPacketBufferSize());
ByteBuffer appIn = ByteBuffer.allocate(session.getApplicationBufferSize());
~~~

This is a reasonable initialization according to the API. `SSLSession.getPacketBufferSize()` indicates the recommended size to hold a TLS/DTLS packet, while `getApplicationBufferSize()` is for plaintext/application data that may be produced. The required sizes **can change** as TLS negotiation progresses or the session changes, so if the engine reports insufficient buffer space, re-read the current session sizes. Do not assume a fixed 16 KB/17 KB or assume `getPacketBufferSize()` is the maximum TCP read size.

**Consider remaining space, not just capacity.** An 18 KB buffer that already holds 17 KB of unsent ciphertext only has 1 KB left, which can overflow on the next wrap. Before increasing capacity, you may need to **drain** the data already held.

Note that `SSLEngine` **does not hold application data on behalf of the application between wrap/unwrap calls**: the app must preserve source/destination buffers and consumed/unconsumed bytes. Do not rely on the engine to recover plaintext you accidentally `clear()`ed.

## 5. The wrap cycle: plaintext into TLS bytes

During the handshake, `NEED_WRAP` means the engine needs to output TLS messages. There does not necessarily have to be any application plaintext to send:

~~~java
// Fragment: netOut is in WRITE mode and has space.
ByteBuffer emptyAppData = ByteBuffer.allocate(0);
SSLEngineResult r = engine.wrap(emptyAppData, netOut);

// r.bytesProduced() can be > 0 even though emptyAppData has no bytes.
// Next step: flip netOut, pass ciphertext to transport.
~~~

When the session is ready to send application data:

~~~java
// Fragment: outboundPlaintext is in READ mode, e.g., already flip()ped.
SSLEngineResult r = engine.wrap(outboundPlaintext, netOut);
// r.bytesConsumed() may be < outboundPlaintext.remaining() BEFORE the call.
// Do not clear outboundPlaintext if r has not consumed all of it.
~~~

Standard flow:

~~~text
appOut (READ mode) -> wrap(appOut, netOut WRITE mode)
                          |
                          v
                  handle result.status
                    OK / OVERFLOW / CLOSED
                          |
                          v
             if netOut has bytes: netOut.flip()
                          |
                          v
              TCP write until netOut is empty
                          |
                          v
               netOut.clear() for next wrap
                 (or compact if bytes remain)
~~~

**A single `SocketChannel.write(netOut)` may send only part of the ciphertext.** If a non-blocking `write()` returns `0`, you must keep the buffer and wait for `OP_WRITE` or the corresponding readiness mechanism; never `clear()` and lose an in-flight TLS record. If ciphertext is truncated or reordered, the TLS peer will typically reject the connection.

### BUFFER_OVERFLOW in wrap

`wrap` returns `BUFFER_OVERFLOW` when `netOut` does not have enough **remaining space** for the TLS output. How to handle it:

1. If `netOut` already contains **unsent** encrypted bytes, `flip()` and flush/queue them over the transport, preserving any portion the socket has not written yet.
2. If the buffer is already empty and its capacity is smaller than `engine.getSession().getPacketBufferSize()`, allocate a larger buffer according to the new size.
3. Retry `wrap` **only once the destination buffer has space**, while keeping unconsumed `appOut` intact.
4. Do not clear `appOut`/`netOut` to “solve overflow”; the error is insufficient destination space, not malformed TLS.

Example helper to grow a **buffer currently in WRITE mode**, while preserving existing bytes:

~~~java
// Java 17+ fragment: returns a new buffer in WRITE mode.
// Used for netOut when the buffer holds bytes from index 0 to position.
static ByteBuffer growWriteBuffer(
        ByteBuffer old, int minimumCapacity) {
    int target = Math.max(minimumCapacity, old.capacity() * 2);
    target = Math.max(target, old.position() + 1);

    ByteBuffer bigger = ByteBuffer.allocate(target);
    old.flip();             // prepare to read bytes already written
    bigger.put(old);        // preserve bytes, bigger stays in WRITE mode
    return bigger;
}
~~~

This is a **fragment**; it must be placed in a class that imports `java.nio.ByteBuffer`. Do not allocate unbounded buffers on abnormal parameters; a real system needs memory limits and integer overflow handling. Once ciphertext is placed into an outbound queue or TCP write completes, manage ownership so it is not sent twice.

### FINISHED does not mean ciphertext has left the machine

Even when a `wrap` call reports the handshake is finished, `netOut` may still contain TLS handshake bytes waiting to be sent. They must be flushed over the transport in order. A client cannot allow application data exchange just because it sees the FINISHED flag while dropping the final packet that needs to be delivered to the peer.

## 6. The unwrap cycle: TLS bytes into plaintext

Inbound TCP must be placed into `netIn` in **WRITE mode**; after reading from the network, `flip()` so the engine can consume it:

~~~java
// Illustrative fragment in an event loop, netIn in WRITE mode.
// TCP channel is connected; read may return 0 or -1.
int n = channel.read(netIn);

if (n > 0) {
    netIn.flip();  // Switch received bytes to READ region.
    SSLEngineResult result = engine.unwrap(netIn, appIn);
    // Handle Status/HandshakeStatus, keep unused bytes.
    netIn.compact();  // Preserve bytes from position to limit.
}
~~~

This fragment intentionally does not contain a full state machine: if `unwrap` processes one record but `netIn` still has more records, a proper loop is needed to continue processing while progress is made, rather than always calling `compact` immediately after one call and waiting for a new network event. If TCP read returns `-1`, EOS/TLS close must be handled separately (see section 11), not ignored.

### BUFFER_UNDERFLOW in unwrap

If only the first 4 bytes of a large TLS record are received, `unwrap(netIn, appIn)` typically returns `BUFFER_UNDERFLOW`. **Those bytes are still important** and must be kept.

~~~text
netIn (READ mode) has first 4 TLS bytes:
  position=0, limit=4, capacity=16 KB
                |
        unwrap -> BUFFER_UNDERFLOW
                |
        netIn.compact()
                |
  write mode: position=4, limit=capacity
  first bytes are preserved at [0 .. 4)
                |
        socket.read(netIn) more bytes
                |
        netIn.flip()
                |
        unwrap again on both old + new bytes
~~~

If the packet buffer is too small to hold a record, just calling `compact` and reading can create a wait loop that never has enough space: you must **increase capacity** according to `getPacketBufferSize()` and protect the unconsumed bytes.

Helper to move **`netIn` currently in READ mode** to a larger buffer, preserving the remaining bytes and returning in **WRITE mode**:

~~~java
// Java 17+ fragment: call when netIn still has unused bytes.
static ByteBuffer growUnreadNetwork(
        ByteBuffer readMode, int packetBufferSize) {
    int unread = readMode.remaining();
    int target = Math.max(packetBufferSize, readMode.capacity() * 2);
    target = Math.max(target, unread + 1);

    ByteBuffer bigger = ByteBuffer.allocate(target);
    bigger.put(readMode); // Copy only unconsumed bytes.
    return bigger;        // position=unread, limit=capacity -> WRITE
}
~~~

After choosing `compact()` or this helper, **read more network bytes**, then `flip()` before unwrapping. Do not call `unwrap` in an endless loop with the exact same 4 old bytes; the engine cannot synthesize the missing part of the TLS record.

### BUFFER_OVERFLOW in unwrap

With `unwrap(netIn, appIn)`, overflow means **`appIn` does not have enough remaining space** for the plaintext. You must:

1. If `appIn` contains decrypted plaintext, `flip()` and pass it to the parser/consumer (or another queue), discarding bytes **only after** the application has retained/processed them.
2. `clear()` or `compact()` `appIn` according to remaining data; if still insufficient, allocate a larger buffer according to `engine.getSession().getApplicationBufferSize()` and remaining demand.
3. Retry `unwrap` with **`netIn` in read state containing unconsumed bytes**; do not automatically read a new packet instead of processing pending data.

Unlike underflow, **overflow is not cured by reading more ciphertext**. If `netIn` already has a complete record but `appIn` has no room, reading more can increase memory pressure while the core issue remains unresolved.

### Note on plaintext after unwrap

Even when the result is `OK` and `bytesProduced()>0`, `appIn` may contain **a partial** application message. Application-level framing still requires a length prefix/delimiter/header (for example, HTTP). One TLS record does not correspond exactly to one request, one TCP read, or one business `ByteBuffer` frame.

## 7. NEED_TASK: delegated tasks must run before the handshake proceeds

Some TLS steps may involve computation or checks that take significant time: certificate verification, key management, cryptographic calculations, or trust policy interactions. Instead of doing everything inside `wrap/unwrap`, the provider can return `HandshakeStatus.NEED_TASK`. The application must call `getDelegatedTask()` **until no tasks remain**, and run those tasks to completion.

Synchronous pattern **suitable for illustration or use outside a latency-sensitive event loop**:

~~~java
// Java 17+ fragment, engine returned/is in NEED_TASK.
Runnable task;
while ((task = engine.getDelegatedTask()) != null) {
    task.run();
}
// After tasks complete, re-read engine.getHandshakeStatus()
// and continue NEED_WRAP/NEED_UNWRAP/NEED_UNWRAP_AGAIN ...
~~~

**Do not skip tasks** or assume that merely calling `getDelegatedTask()` has executed them. When the engine needs delegated task results, subsequent engine calls cannot progress properly until the required tasks complete.

**Do not run long tasks on a non-blocking event loop:** `task.run()` can be CPU-intensive or invoke blocking components. In a `Selector`/Netty-like design, you can offload them to a bounded executor. When running asynchronously:

- Retrieve the delegated tasks returned by the engine and maintain a “waiting for task” state for the session.
- Dispatch to a bounded executor and guard against errors from `run()`.
- Only **after all relevant tasks have completed**, wake/resume the engine state machine on the appropriate thread/serial context.
- Do not call `wrap/unwrap` concurrently from a task callback and another event loop without synchronizing ownership/state.
- Have a deadline and overload policy; if the executor rejects, errors, or shuts down, stop/close the TLS session in a controlled manner.

Anti-pattern example:

~~~java
// Wrong for handshake progress:
if (engine.getHandshakeStatus()
        == SSLEngineResult.HandshakeStatus.NEED_TASK) {
    // Retrieves no tasks and just waits for OP_READ from TCP.
    // There may be no more network events to drive the handshake forward.
}
~~~

And do not spawn an **unbounded** thread per task per client either. Delegated tasks can occur across many connections; the worker pool needs bounds and backpressure.

## 8. The full handshake cycle at the state-machine level

A TLS event loop is typically triggered by these events:

- Session start: `beginHandshake()`.
- `OP_READ`: the socket has new encrypted bytes.
- `OP_WRITE`: the socket can accept more ciphertext from the queue.
- Task completion: delegated tasks have finished.
- Application output has plaintext waiting to be sent after TLS is ready.
- Deadline/close/failure: need to abort the session or send `close_notify`.

Decision diagram:

~~~text
                 beginHandshake()
                        |
                        v
               getHandshakeStatus()
                        |
          +-------------+------------------------+
          |             |                        |
      NEED_TASK     NEED_WRAP               NEED_UNWRAP
          |             |                        |
  getDelegatedTask  wrap(empty,netOut)       does netIn have enough bytes?
  run all tasks     handle Status                 |
  and wait          flush ciphertext         +----+----+
          |             |                   |         |
          |             v                   no        yes
          |        check status             |         |
          |             |                read more   unwrap(netIn,appIn)
          |             |                network      |
          |             |                     |       v
          +-------------+---------------------+---- handle status
                        |                             |
                        +----------<------------------+
                        |
             NEED_UNWRAP_AGAIN
                 unwrap again,
             do not wait for new network
                        |
                        v
            FINISHED / NOT_HANDSHAKING
                        |
                  TLS session ready
                        |
                 app data wrap/unwrap
                        |
              may produce tasks or
              post-handshake TLS messages
~~~

**Do not treat the diagram as runnable code.** The result status can change after every call. In addition to handshake status, you must always handle `BUFFER_UNDERFLOW`, `BUFFER_OVERFLOW`, and `CLOSED` to avoid infinite loops.

### NEED_UNWRAP versus NEED_UNWRAP_AGAIN

- `NEED_UNWRAP` typically requires TLS data from the peer; if `netIn` does not yet have a full record, you must wait for more network data or process existing bytes.
- `NEED_UNWRAP_AGAIN` indicates that JSSE has **already-received data that has not been fully interpreted yet**; you need to call `unwrap` again **without waiting for the socket to send more**. This status is significant for specific TLS 1.3 and JSSE cases; code that only handles `NEED_WRAP/NEED_UNWRAP/NEED_TASK` will miss a valid branch.

When entering `NEED_UNWRAP_AGAIN`, do not clear the inbound buffer or assume this is `BUFFER_UNDERFLOW`. After the next `unwrap` call, **read the new result** and decide based on the current status pair.

### FINISHED and NOT_HANDSHAKING

`FINISHED` marks that the handshake has just completed, whereas `NOT_HANDSHAKING` is the state when no handshake is pending. Handshake handling needs its own state (“TLS established”) and verification of required protocol/peer conditions; do not write:

~~~java
// Anti-pattern: waiting solely for FINISHED from the engine is unsafe.
while (engine.getHandshakeStatus()
        != SSLEngineResult.HandshakeStatus.FINISHED) {
    // No buffer/task/I/O logic, and FINISHED can be very transient.
}
~~~

In practice, the handshake can return to `NOT_HANDSHAKING` after completion, and handshake status only needs to be handled properly within events. Session state can also continue to change when TLS uses key updates/post-handshake messages.

## 9. Java 17+ example that actually tests OVERFLOW, UNDERFLOW, and NEED_TASK

The example below **does not require opening a TCP port or certificate files**. It uses two in-memory engines:

1. The client starts the TLS handshake.
2. The client attempts `wrap` with a `netOut` of **only 1 byte**, resulting in `BUFFER_OVERFLOW` in the tested default JSSE provider.
3. Grow the buffer according to `getPacketBufferSize()`, and `wrap` again to produce ClientHello.
4. The server receives **only 4 bytes** of ClientHello → `unwrap` returns `BUFFER_UNDERFLOW`.
5. Combine the 4 retained bytes with the remaining ciphertext (simulating `compact/receive-more/flip`), and the server calls `unwrap` again.
6. If the server requests `NEED_TASK`, run all `getDelegatedTask().run()` calls and inspect the status after tasks.

Because the server is not configured with a private key/certificate, this exercise **only observes the initial steps of the TLS handshake**, does not send application data, and does not verify mutual client/server trust. On other Java providers, the number of delegated tasks/status sequence may vary; proper handling relies on the returned status, not on a fixed sequence.

Save under the filename **`EngineBufferProbe.java`**:

~~~java
import java.nio.ByteBuffer;
import java.security.SecureRandom;
import javax.net.ssl.SSLContext;
import javax.net.ssl.SSLEngine;
import javax.net.ssl.SSLEngineResult;

public class EngineBufferProbe {

    private static void runDelegatedTasks(SSLEngine engine) {
        Runnable task;
        int count = 0;
        while ((task = engine.getDelegatedTask()) != null) {
            task.run();
            count++;
        }
        System.out.println("delegatedTasksRun=" + count);
    }

    public static void main(String[] args) throws Exception {
        SSLContext tls = SSLContext.getInstance("TLS");
        tls.init(null, null, new SecureRandom());

        SSLEngine client = tls.createSSLEngine("localhost", 443);
        client.setUseClientMode(true);

        SSLEngine server = tls.createSSLEngine();
        server.setUseClientMode(false);

        // ClientHello is TLS handshake data, not plaintext.
        client.beginHandshake();
        ByteBuffer emptyApp = ByteBuffer.allocate(0);

        SSLEngineResult tiny = client.wrap(
                emptyApp, ByteBuffer.allocate(1));
        System.out.println(
                "wrapTinyStatus=" + tiny.getStatus());

        // netOut has enough room for the TLS packet suggested by JSSE.
        ByteBuffer clientHello = ByteBuffer.allocate(
                client.getSession().getPacketBufferSize());
        SSLEngineResult hello = client.wrap(
                emptyApp, clientHello);

        System.out.println(
                "wrapNormalStatus=" + hello.getStatus());
        System.out.println(
                "producedHandshakeBytes="
                        + (hello.bytesProduced() > 0));

        clientHello.flip(); // Produced bytes in WRITE mode -> READ.

        // Server starts handshake and receives only 4 bytes first.
        server.beginHandshake();
        ByteBuffer partial = ByteBuffer.allocate(4);
        for (int i = 0; i < 4; i++) {
            partial.put(clientHello.get());
        }
        partial.flip();

        ByteBuffer peerApp = ByteBuffer.allocate(
                server.getSession().getApplicationBufferSize());

        SSLEngineResult underflow = server.unwrap(
                partial, peerApp);
        System.out.println(
                "unwrapPartialStatus=" + underflow.getStatus());
        System.out.println(
                "partialStillAvailable=" + partial.remaining());

        // Combine unconsumed bytes with newly arrived TLS bytes.
        ByteBuffer full = ByteBuffer.allocate(
                server.getSession().getPacketBufferSize());
        full.put(partial);    // Keep the first 4 bytes, do not drop them.
        full.put(clientHello);
        full.flip();          // READ mode for unwrap.

        SSLEngineResult decoded = server.unwrap(full, peerApp);
        System.out.println(
                "unwrapFullStatus=" + decoded.getStatus());
        System.out.println(
                "fullConsumedPositive="
                        + (decoded.bytesConsumed() > 0));
        System.out.println(
                "serverHandshakeAfterUnwrap="
                        + decoded.getHandshakeStatus());

        // If NEED_TASK, execute tasks then continue state machine.
        runDelegatedTasks(server);
        System.out.println(
                "serverHandshakeAfterTasks="
                        + server.getHandshakeStatus());

        // Just end the demo, do not pretend to be TLS-authenticated.
        client.closeOutbound();
        server.closeOutbound();
    }
}
~~~

Compile/run:

~~~bash
javac EngineBufferProbe.java
java EngineBufferProbe
~~~

**Output observed on a JDK 24 build using the default JSSE:**

~~~text
wrapTinyStatus=BUFFER_OVERFLOW
wrapNormalStatus=OK
producedHandshakeBytes=true
unwrapPartialStatus=BUFFER_UNDERFLOW
partialStillAvailable=4
unwrapFullStatus=OK
fullConsumedPositive=true
serverHandshakeAfterUnwrap=NEED_TASK
delegatedTasksRun=1
serverHandshakeAfterTasks=NEED_WRAP
~~~

Across JDK 17, different TLS providers, cipher suites, enabled algorithms, session policies, and JSSE configurations, **the number of tasks or handshake status after unwrap may change**. What does not change is the meaning of each status per the API, how bytes are preserved, and the requirement to run delegated tasks when the engine reports `NEED_TASK`. If the environment does not allow initializing the TLS provider or desired algorithm, an exception may occur instead of the lines above.

### Deep dive into the output

- `wrapTinyStatus=BUFFER_OVERFLOW`: the ciphertext buffer is too small; the engine cannot output a TLS record into a 1-byte space. **Not a certificate error**.
- `wrapNormalStatus=OK` and `producedHandshakeBytes=true`: the client produced ClientHello into `netOut` with sufficient space, even though `emptyApp` had no plaintext.
- `unwrapPartialStatus=BUFFER_UNDERFLOW`: the first 4 bytes are not enough to parse a record; `partialStillAvailable=4` illustrates that those bytes **still need to be kept**. In a real event loop, use `compact()` and wait for the next TCP read, rather than feeding ClientHello from another engine as in the demo.
- `unwrapFullStatus=OK` and `fullConsumedPositive=true`: once enough of the record arrived, the server consumed TLS bytes to advance the handshake. This does not mean the server is authenticated or has decrypted application data.
- `serverHandshakeAfterUnwrap=NEED_TASK`: JSSE requests processing a delegated task; the demo runs tasks synchronously to make the result easy to see.
- `serverHandshakeAfterTasks=NEED_WRAP`: after the task, the server needs to generate an outbound TLS handshake message. **The demo stops here**, because completing a real TLS server handshake requires credentials, bidirectional communication, and trust policy verification.

## 10. Buffer error handling examples with proper state and ownership

The following snippets are **component patterns**, not a standalone runnable server class. They are useful when integrating into a TCP `SocketChannel` or an existing event loop.

### 10.1. On unwrap UNDERFLOW, keep bytes and read more

~~~java
// Fragment: netIn is in READ mode after an unwrap returned UNDERFLOW.
int desiredPacketSize = engine.getSession().getPacketBufferSize();

if (netIn.capacity() < desiredPacketSize) {
    netIn = growUnreadNetwork(netIn, desiredPacketSize);
} else {
    netIn.compact(); // netIn switches to WRITE mode.
}

// Do not call unwrap again immediately with the exact same old bytes:
// register OP_READ (non-blocking) or read more from TCP.
int n = socketChannel.read(netIn);
if (n > 0) {
    netIn.flip(); // Only now can unwrap be called again.
} else if (n == 0) {
    // Non-blocking: wait for read event, do not busy-spin.
} else {
    // n == -1: TCP EOF, transition to TLS close/truncation handling.
}
~~~

The snippet above requires the `engine/netIn/socketChannel` variables and the `growUnreadNetwork` helper from section 6. With a non-blocking socket, never assume a single `read` will be enough; keep accumulating data until `unwrap` can make progress.

### 10.2. On unwrap OVERFLOW, process plaintext first

~~~java
// Fragment: appIn is in WRITE mode and already holds prior plaintext.
appIn.flip(); // READ mode
consumePlaintext(appIn); // Application function: reads as much as framing allows.
appIn.compact(); // Retain unconsumed plaintext; WRITE mode

if (appIn.remaining()
        < engine.getSession().getApplicationBufferSize()) {
    appIn = growWriteBuffer(
            appIn,
            Math.max(engine.getSession().getApplicationBufferSize(),
                     appIn.position() + 1));
}

// Ensure appIn has room; keep netIn in READ mode and retry unwrap.
~~~

Note: `consumePlaintext` is a helper provided by the application protocol; there must be a policy when the application **cannot** consume data (backpressure). If holding unprocessed plaintext and out of capacity, do not grow the buffer infinitely: pause network reads or apply resource limits.

### 10.3. On wrap OVERFLOW, transfer ciphertext first

~~~java
// Fragment: netOut is in WRITE mode, holding unsent ciphertext.
netOut.flip(); // READ mode for SocketChannel.write().
while (netOut.hasRemaining()) {
    int n = socketChannel.write(netOut);
    if (n == 0) {
        // For a non-blocking channel:
        // save netOut, register OP_WRITE, then RETURN to event loop.
        break;
    }
}
netOut.compact(); // Keep unwritten bytes, back to WRITE mode.

if (netOut.remaining()
        < engine.getSession().getPacketBufferSize()) {
    // Can drain netOut further or grow with a memory budget guard.
    netOut = growWriteBuffer(
            netOut,
            netOut.position()
                    + engine.getSession().getPacketBufferSize());
}
~~~

The fragment only illustrates safe handling of remaining bytes. If `write` returns `0` or `netOut` has not flushed completely, you must **retain the buffer and connection state** across the next `OP_WRITE` event; do not loop continuously on the event loop thread, and do not report the TLS handshake as completed on the network side before all ciphertext is sent. Each `wrap` result is only valid if record order is preserved.

### 10.4. Handling NEED_TASK in the control loop

~~~java
// Fragment: used when status/engine reports NEED_TASK.
Runnable delegated;
while ((delegated = engine.getDelegatedTask()) != null) {
    delegated.run(); // May block; avoid calling directly on the event loop.
}
// Then retrieve current status and continue with the appropriate wrap/unwrap step.
SSLEngineResult.HandshakeStatus next =
        engine.getHandshakeStatus();
~~~

If offloading delegated tasks to an executor, do **not** use the exact code above to treat submission as equivalent to completion. You need a callback/future to collect task results before resuming the TLS state machine.

## 11. TLS EOF, close_notify, and Status.CLOSED

TLS data must terminate according to the protocol. Simply seeing TCP `read() == -1` does not mean the peer sent TLS `close_notify`. An abnormally severed channel can lose the final message, which has security implications (truncation).

Standard outbound close procedure:

1. The application has finished sending plaintext or decides to stop sending.
2. Call `engine.closeOutbound()`.
3. Continue calling `wrap()` to obtain TLS close messages (e.g., `close_notify`), possibly with an empty app buffer.
4. **Send all bytes generated by wrap** over TCP, preserving order and handling partial writes.
5. Close the transport when policy/protocol and inbound close state align; do not discard unflushed data.

On the inbound side, when `unwrap` processes a TLS close notification, the engine may report `Status.CLOSED` or `isInboundDone() == true`. When TCP EOF arrives **without a proper TLS close**, calling `engine.closeInbound()` can throw an `SSLException` to signal an ungraceful session termination. The application must distinguish a valid close from an abrupt close according to protocol guarantees; do not ignore all close exceptions by default.

**Do not reuse a closed SSLEngine** for a new TCP connection. Each session needs an engine and buffer state with a proper lifecycle. `closeOutbound()` does not automatically flush bytes to the socket, and `closeInbound()` is not equivalent to receiving `close_notify` from the peer.

## 12. TLS over non-blocking SocketChannel and Selector coordination

`SSLEngine` performs transformations on `ByteBuffer`s supplied by the application; `wrap/unwrap` calls themselves **do not perform blocking socket I/O**. However, delegated tasks can be long-running or blocking; additionally, `SocketChannel.read/write` still has partial/readiness states.

An event loop typically has at least these state groups:

| Component | What to track |
| --- | --- |
| TCP channel | Connecting/open/EOF; `OP_READ`/`OP_WRITE` readiness; write queue |
| netIn | WRITE mode waiting for TCP read or READ mode waiting for unwrap; remaining bytes |
| netOut | Unsent ciphertext; current buffer + outbound record queue |
| appIn | Decrypted plaintext not yet consumed by parser; backpressure |
| appOut | Plaintext waiting for TLS wrap; not yet fully consumed |
| SSLEngine | HandshakeStatus, CLOSED, delegated task count, session buffer sizes |
| Session policy | Overall deadline, max frame, trust/hostname verification, shutdown |

**Rules to avoid spinning:**

- `NEED_UNWRAP + BUFFER_UNDERFLOW` → if no new bytes are available, wait for `OP_READ`.
- `NEED_WRAP + BUFFER_OVERFLOW` → drain/grow `netOut`; if TCP cannot write, wait for `OP_WRITE`.
- `NEED_TASK` → run delegated tasks, only resume after completion; do not wait for `OP_READ` instead of tasks.
- `NEED_UNWRAP_AGAIN` → try unwrapping to process JSSE buffered state, but if there is no progress, check result status and avoid spinning.
- `FINISHED/NOT_HANDSHAKING` → handle app data and still-pending TLS outbound data; do not drop write interest while ciphertext remains.
- In cases with no `bytesConsumed/Produced`, no state change, and no I/O progress → must **yield the event loop** or report an error, do not run a hot wait loop.

`Selector.OP_WRITE` on many operating systems is ready very frequently. Do not keep `OP_WRITE` interest enabled at all times when **there is no ciphertext waiting to be sent**, as it can cause useless CPU wakeup loops. Register it when a write is blocked or data is pending, and clear it once the queue is drained by design.

### Ordering and concurrency

The `SSLEngine` Javadoc allows `wrap()` and `unwrap()` to be called concurrently in an appropriate manner, but do **not** let two threads call `wrap()` concurrently, or two threads call `unwrap()` concurrently, because TLS records are ordered. If using multiple executors, protect the outbound queue, inbound feed, and the entire handshake state.

A state machine that owns the engine in **a single serial context** is usually easier to reason about and debug than letting multiple callbacks call wrap/unwrap arbitrarily. Whichever design is chosen, do not reorder ciphertext generated by wrap, do not re-ingest old records, and do not let task completions race and cause two duplicate wraps.

## 13. Diagnosing common errors

| Symptom | Common cause | Inspection action |
| --- | --- | --- |
| Handshake stuck at `NEED_TASK` | Not calling/running all delegated tasks, or task waiting on worker | Drain `getDelegatedTask`, track task completion and resume |
| Repeated `BUFFER_UNDERFLOW` | `netIn` always has only a partial record, not reading more; or capacity too small | `compact` to keep unread bytes, read more, resize packet buffer |
| `BUFFER_OVERFLOW` on `wrap` | `netOut` has unflushed ciphertext or is too small | Flush queue, keep partial write, grow by packet size |
| `BUFFER_OVERFLOW` on `unwrap` | `appIn` lacks space or parser has not consumed old plaintext | Drain `appIn`, keep unread plaintext, resize by app size |
| `NEED_UNWRAP_AGAIN` but loop stalls | Only waiting for new socket `OP_READ`, ignoring JSSE pending data | Call `unwrap` again and check new status |
| Engine reports OK but peer receives nothing | New ciphertext sits in `netOut`, not written fully; record order lost | Check flip/write/compact and outbound queue |
| Some bytes “disappear” | Accidentally `clear()`ing a buffer with data; wrong flip/compact usage | Log position/limit/remaining before and after every step |
| `bytesConsumed=0, produced=0` forever | No new events, wrong buffer state, needs task or I/O | Coordinate by handshake status, avoid busy-loop |
| Handshake fails cert | KeyManager/TrustManager, hostname, cipher/protocol, certificate chain | Check TLS configuration; do not disable verification |
| Unexpected TCP EOF | Peer closed transport without `close_notify` or network error | Handle `closeInbound`/`SSLException`, truncation policy |
| Fails only with multiple clients | Shared buffers across sessions, callback/task race, concurrent wrap | Keep state separate per connection, serialize/synchronize |
| High CPU in selector | `OP_WRITE` always active, retrying on error without new bytes | Only register `OP_WRITE` when data remains, wait for readiness/tasks |

**The most dangerous mistake is “fixing” underflow/overflow with arbitrary `clear()` calls.** Even one lost TLS byte can render an entire record undecryptable; even one dropped decrypted plaintext byte causes the application layer to misparse messages. Always specify **who owns the buffer**, its READ/WRITE state, and which bytes have been consumed.

### Debug checklist for each wrap/unwrap

Log a controlled single line (without logging secrets) with the following fields:

~~~text
connId=<id> operation=wrap|unwrap
status=OK|BUFFER_UNDERFLOW|BUFFER_OVERFLOW|CLOSED
hs=NEED_WRAP|NEED_UNWRAP|NEED_UNWRAP_AGAIN|NEED_TASK|FINISHED|NOT_HANDSHAKING
consumed=<n> produced=<n>
appInPosLim=<position>/<limit>
appOutPosLim=<position>/<limit>
netInPosLim=<position>/<limit>
netOutPosLim=<position>/<limit>
socketRead=<n> socketWritten=<n>
pendingTasks=<n> pendingCiphertextBytes=<n>
~~~

This is an **illustrative log pattern**, not output from a program. In production, do not log plaintext, private keys, session secrets, or full TLS records containing sensitive data. You can use `javax.net.debug=ssl,handshake` when testing is permitted, but TLS debugging also requires managing data exposure and noise.

## 14. Misconceptions to avoid

1. **“`wrap()` automatically sends TLS records over the network.”** False: it only produces ciphertext in a ByteBuffer; the application must send all of it in order.
2. **“`unwrap()` automatically reads more bytes from the socket if short.”** False: underflow requires the application to keep bytes and fetch more data.
3. **“`Status.OK` means the handshake is done.”** False: it can be `OK + NEED_TASK` or `OK + NEED_WRAP`.
4. **“`NEED_TASK` is just a hint and can be skipped.”** False: delegated tasks must be executed before the handshake can continue properly.
5. **“Whenever `BUFFER_UNDERFLOW` occurs, grow `appIn`.”** False: **source TLS bytes** are missing; first read more into `netIn`, and grow the packet buffer if capacity is small.
6. **“Whenever `BUFFER_OVERFLOW` occurs, read more from the socket.”** False: the destination is insufficient; you must drain/grow the operation's destination.
7. **“After `flip()` if data is short, call `clear()` and read again.”** False: `clear` loses the range of unconsumed TLS bytes; use `compact` or copy unread bytes.
8. **“`NEED_UNWRAP_AGAIN` is a normal `NEED_UNWRAP`.”** False: JSSE buffered state must be processed without assuming you should wait for the peer to send more.
9. **“`FINISHED` is a value that stays forever in `engine.getHandshakeStatus()`.”** False: it marks the event that the handshake just ended; afterward it is usually `NOT_HANDSHAKING`.
10. **“One TLS record equals one TCP read.”** False: TCP is a stream; a socket read can split or coalesce records.
11. **“`closeOutbound()` automatically sends `close_notify`.”** False: you must call `wrap` and send the generated bytes.
12. **“The probe's handshake output proves secure TLS is established.”** False: the probe has not completed the handshake or authenticated the peer.
13. **“All delegated tasks are always non-blocking.”** False: certificate verification, key manager tasks, and some operations can be long-running.
14. **“One `netOut` buffer can be shared across multiple `SSLEngine`s simultaneously.”** False unless ownership/data is protected; each session's TLS bytes are tied to its own state.

## 15. Self-check questions

**Question 1:** Can `engine.wrap(empty, netOut)` produce `bytesProduced()>0`?  
**Answer:** Yes. Handshake or TLS control records do not necessarily consume application plaintext.

**Question 2:** `unwrap(netIn, appIn)` reports `BUFFER_UNDERFLOW`, and `netIn` in READ mode has 7 bytes left. What should you do before calling again?  
**Answer:** Keep the 7 bytes using `compact()` or copy unread bytes to a larger buffer, read more TCP ciphertext, then `flip()` and `unwrap` again. Check `packetBufferSize` if capacity is insufficient.

**Question 3:** `wrap` reports `BUFFER_OVERFLOW` while `netOut` still has 1 KB of unsent ciphertext. Can you `clear()` `netOut` and retry?  
**Answer:** No. You must transfer/retain the unsent 1 KB and ensure the transport sends all of it in the correct order; only then is there room for the next record or buffer growth.

**Question 4:** `unwrap` reports `BUFFER_OVERFLOW`. Should you read more from TCP?  
**Answer:** That is not the primary fix. You must drain/grow **`appIn`** to hold plaintext, keep unconsumed `netIn`, and retry.

**Question 5:** `getStatus()==OK`, `getHandshakeStatus()==NEED_TASK`. Is the handshake finished?  
**Answer:** No. You must retrieve and run all delegated tasks, wait for completion if dispatched to an executor, and then continue the state machine.

**Question 6:** Why is handling `NEED_UNWRAP_AGAIN` necessary in TLS 1.3?  
**Answer:** JSSE may hold received TLS data internally that has not been fully processed yet; `unwrap` must be called again without necessarily having a new network read.

**Question 7:** When can the application be allowed to send plaintext?  
**Answer:** When the handshake/security policy allows it; the engine no longer requires the relevant handshake steps and prior mandatory TLS data has been properly sent/received. Do not use `Status.OK` alone as proof.

**Question 8:** Why does `getSession().getPacketBufferSize()` need to be re-read?  
**Answer:** TLS packet/application sizes can change depending on the negotiation stage and session; the engine reports statuses so the application can adjust.

**Question 9:** A single network read receives two TLS records at once. What should be done?  
**Answer:** After unwrapping the first record, if `netIn` still has bytes, continue processing properly when the engine is ready, without discarding remaining bytes with `clear`; if the next record is incomplete, `compact` and read more.

**Question 10:** Can two `wrap()` calls be made concurrently on the same `SSLEngine`?  
**Answer:** No / invalid for preserving TLS record order. Serialize `wrap` per session; `unwrap` may run in parallel with `wrap` under proper synchronization and engine state rules, but never two `wrap`s or two `unwrap`s at the same time.

**Question 11:** Why is TCP EOF not automatically considered a valid TLS close?  
**Answer:** The peer may have closed the transport without sending `close_notify`; the application must handle `closeInbound`/`SSLException` and potential truncation according to the protocol.

**Question 12:** When must a handshake loop stop and wait for a network event instead of continuing to run?  
**Answer:** When `netIn` lacks bytes and needs `OP_READ`, `netOut` has unwritten ciphertext and needs `OP_WRITE`, delegated tasks are still running, or there is no progress and no new trigger. Do not busy-spin.
