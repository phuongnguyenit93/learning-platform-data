# KeyManager, TrustManager, keystore, and truststore have different responsibilities

In Java TLS (JSSE), **`KeyManager` manages local credentials to prove your own identity**, whereas **`TrustManager` verifies the peer's certificate**. **Keystore** and **truststore** are the data repositories that the managers use; they **are not two necessarily different file formats**. Both can be loaded via `java.security.KeyStore` and both can use the `PKCS12` format.

Misunderstanding these four concepts easily leads to configurations missing a private key, clients failing to verify the certificate chain, mTLS not actually requiring a client certificate, or the most dangerous mistake: writing a "trust all" manager to bypass verification. This lesson belongs to the **TLS** section in Java Advance - networking, uses Java 17+, and explains the roles, configuration, errors, testing, and operational management.

## 1. Division of responsibilities table

| Component | Object type | Function | Not primarily responsible for |
| --- | --- | --- | --- |
| `KeyManager` | Runtime JSSE manager | Selects the **local endpoint's private key and certificate chain** when TLS needs to present a certificate | Does not decide whether the peer is trusted |
| `TrustManager` | Runtime JSSE manager | **Verifies the remote peer's certificate chain** according to trust material/policy | Does not provide your own private key |
| *Keystore* (identity store) | Data source, usually a file | Contains your own **private key** and corresponding certificate chain | Does not authenticate the peer on its own |
| *Truststore* | Data source, usually a file | Contains **trusted certificates/CAs** as appropriate trust anchors | Does not prove that you possess a private key |

More specifically, `KeyManagerFactory` reads key material in `KeyStore` and creates `KeyManager[]`; `TrustManagerFactory` reads trust material and creates `TrustManager[]`. Both arrays are configured into `SSLContext` to create `SSLSocket`, `SSLServerSocket`, or `SSLEngine`.

```text
  LOCAL IDENTITY                            VERIFY REMOTE PEER
  identity.p12                              trust.p12
      |                                        |
      v                                        v
  KeyStore.load()                         KeyStore.load()
      |                                        |
  KeyManagerFactory                       TrustManagerFactory
      |                                        |
  getKeyManagers()                         getTrustManagers()
      \                                        /
       \                                      /
                SSLContext.init(...)
                       |
             SSLSocket / SSLEngine
                       |
                  TLS handshake
```

A **Store** holds data. A **Manager** uses data according to policy during the handshake. A **Context** combines the managers and serves as the factory for TLS objects. Do not interchange their names or roles.

## 2. Who proves identity, who verifies?

Consider a TLS client `A` connecting to a TLS server `B`:

- `B` must **present the server certificate** and prove possession of the corresponding private key per the TLS handshake. The JSSE server uses a local **`KeyManager`**, usually read from the **server identity keystore**.
- `A` must **verify the server certificate**: is the chain trusted against an accepted trust anchor, still valid, used for the right purpose/policy, and matching the service's **hostname/IP**? The JSSE client uses a **`TrustManager`** along with appropriate endpoint identification configuration.
- For standard server-authenticated TLS, `A` **does not need to possess a client certificate**. Not having a local client identity does not mean `A` cannot authenticate `B`.

```text
                       A: CLIENT                       B: SERVER
                  client-truststore                server-keystore
                  [CA / server cert]               [server private key]
                           |                               |
                  TrustManager verifies            KeyManager selects
                           |                               |
  TLS client <-------------+------- certificate chain -----+-- TLS server
             Verify chain + endpoint identity
             Verify server proof-of-possession
```

Sharing a **public certificate** for the proper purpose does not mean sharing the **private key**. The server private key must stay on the server or in authorized secret storage; do not copy the entire `server.p12` containing the private key to the client side just so the client "trusts the server".

## 3. One-way TLS and mutual TLS (mTLS)

| Case | Server KeyManager | Server TrustManager checking client | Client KeyManager | Client TrustManager checking server |
| --- | --- | --- | --- | --- |
| Common server-authenticated TLS | Needs server identity | Does not need to check client certificate if server does not require it | Not required | Needs to trust server |
| Two-way certificate-based mTLS | Needs server identity | **Needs** to trust client | **Needs** client identity | Needs to trust server |

With mTLS, **both client and server simultaneously have "present" and "verify" roles**:

```text
Server                                               Client
======                                               ======
server-keystore.p12                                  client-keystore.p12
  server private key                                   client private key
  server certificate chain                             client certificate chain
         |                                                      |
   KeyManager                                        KeyManager
     presents server cert                              presents client cert

server-trust.p12                                     client-trust.p12
  trusted client CA/cert                               trusted server CA/cert
         |                                                      |
   TrustManager                                     TrustManager
     verifies client                                   verifies server
```

In particular:

1. `KeyManager` **is not only for servers**. When an mTLS client presents a certificate, the client uses it too.
2. `TrustManager` **is not only for clients**. When a server wants to verify the client's cert, the server uses it too.
3. Simply providing a client keystore does not make the server automatically demand a cert: the server must configure client authentication requirements. With `SSLServerSocket` or `SSLEngine`, use `setNeedClientAuth(true)` when a client certificate is **mandatory**. `setWantClientAuth(true)` is **optional**, not equivalent.
4. Even after the client certificate is accepted by the trust manager, the server still needs to decide **authorization**: which client identity is allowed to access which endpoints/data?

## 4. Keystore and truststore: same format, different entries

Java does not define a separate `TrustStore` class to replace `KeyStore`. In practice, both are `KeyStore` instances organized for different purposes.

For example:

```text
server.p12
  alias server
  Entry type: PrivateKeyEntry
    private key: kept secret by server
    certificate chain: server leaf + intermediate if any

client-trust.p12
  alias server-cert
  Entry type: TrustedCertificateEntry
    public certificate: lab self-signed server cert
    private key: NONE
```

- **`PrivateKeyEntry`** contains a secret/private key and chain; `KeyManager` needs it when your side must prove key possession.
- **`TrustedCertificateEntry`** contains a certificate considered trust material; `TrustManager` uses these entries according to the provider's algorithm to decide whether a chain is trusted.
- **Alias** is just a name inside the store. The alias `server` is not the DNS hostname that TLS validates. Address names are verified via certificate information such as **Subject Alternative Name (SAN)**.
- **`PKCS12`, `JKS`** are store types; `.p12`/`.jks` are just file naming conventions, insufficient to determine the role. In modern JDKs, PKCS#12 is typically the default choice, but use `KeyStore.getInstance("PKCS12")` for explicit code.
- A truststore can contain trusted CAs or a pinned leaf certificate according to policy. **The trust scope differs**: trusting a root CA can accept many leaf certs issued by that CA, whereas trusting a specific self-signed leaf is only appropriate when there is a specific trust design.

## 5. What can a private key and certificate chain do?

An X.509 certificate contains a **public key**, subject/SAN, validity period, issuer, and extensions such as key usage/EKU. The corresponding private key in the local identity store enables the proof-of-possession step during the TLS handshake. It **must not and need not be shared** with the peer.

```text
        ROOT CA (trust anchor)
             |
             | signs
             v
        Intermediate CA
             |
             | signs
             v
       Leaf certificate (server)
             |
             | corresponding public key
             v
       Server PRIVATE KEY  <--- controlled only by server side
```

The server typically presents **leaf + necessary intermediates**. The client builds/evaluates the chain up to a trust anchor according to PKIX/configured algorithm. The Root CA that the client already trusts usually does not need to be sent in the chain. Validation may account for signatures, validity periods, constraints, key usage, algorithm restrictions, and revocation policies.

Note two independent levels:

- **Certificate path trust**: can the chain be built up to an allowed trust anchor?
- **Endpoint identity**: is that trusted certificate valid for the hostname/IP the application intends to connect to?

If you only solve "the chain is signed by a trusted CA" while skipping hostname verification, a certificate for `alpha.example` could be misused when connecting to `beta.example` in a custom client that doesn't check names. **Valid trust does not automatically prove the right destination**.

## 6. KeyManager and KeyManagerFactory

`KeyManagerFactory` creates a `KeyManager` from the loaded key material source. For X.509, `X509KeyManager` or `X509ExtendedKeyManager` selects the alias/private key/chain matching the certificate type, issuer, algorithm, and TLS context.

**Illustrative snippet, not a standalone class**:

```java
KeyStore identity = KeyStore.getInstance("PKCS12");
// ... identity.load(input, storePassword) ...
KeyManagerFactory kmf = KeyManagerFactory.getInstance(
        KeyManagerFactory.getDefaultAlgorithm());
kmf.init(identity, keyPassword);
KeyManager[] keyManagers = kmf.getKeyManagers();
```

**Meaning of each step:**

1. `KeyStore.load` opens the store data; if the file is wrong/unreadable or the password is incorrect, it fails right at the load step.
2. `kmf.init(identity, keyPassword)` prepares access to the **private key** at the appropriate alias.
3. `getKeyManagers()` returns runtime managers. They are responsible for choosing local credentials when the handshake needs to present a certificate.
4. A server may have multiple aliases/certificates to serve different hostnames or key algorithms; there must be an alias/cert/chain that is genuinely compatible.
5. `X509ExtendedKeyManager` supports selecting credentials in an `SSLEngine` context for NIO/TLS applications.

A successfully configured `KeyManager` **has no authority to decide whether the peer trusts that cert**. The client may still reject it due to a missing CA, wrong SAN, expiry, or policy. Furthermore, if the certificate and private key do not match, the handshake can fail even if the store opens successfully.

## 7. TrustManager and TrustManagerFactory

`TrustManagerFactory` creates a `TrustManager` from the appropriate source of trust anchors/policy. For X.509, `X509TrustManager` and `X509ExtendedTrustManager` verify the certificate chain presented by the peer.

**Illustrative snippet, not a standalone class**:

```java
KeyStore trustedPeers = KeyStore.getInstance("PKCS12");
// ... trustedPeers.load(input, storePassword) ...
TrustManagerFactory tmf = TrustManagerFactory.getInstance(
        TrustManagerFactory.getDefaultAlgorithm());
tmf.init(trustedPeers);
TrustManager[] trustManagers = tmf.getTrustManagers();
```

`checkServerTrusted(...)` typically handles evaluating the server's cert on the client side; `checkClientTrusted(...)` handles evaluating the client's cert on the mTLS server side. `X509ExtendedTrustManager` variants with a `Socket` or `SSLEngine` parameter allow incorporating connection context.

**Important:** a trust manager **does not issue private keys**, and simply placing a certificate in the truststore does not mean the application has the corresponding identity. The truststore must maintain integrity, because if an attacker can add a root CA to the truststore, they can expand the set of trusted peers.

When a custom policy is needed, consider **delegating to a valid PKIX trust manager and then tightening conditions**. Do not write an empty `checkServerTrusted` that accepts every certificate. Replacing the default trust manager with a flawed custom implementation breaks an essential part of TLS.

## 8. Creating demo identity and truststore with keytool (JDK 17+)

The two runnable examples below use a **self-signed certificate strictly for a loopback lab**. The machine must have `java`, `javac`, and `keytool` from JDK 17+ in PATH. Run the commands in **a dedicated lab directory**; do not use production files/credentials.

### Step 1: create server PKCS#12 identity

```sh
keytool -genkeypair -alias server -keyalg RSA -keysize 2048 -validity 30 -dname "CN=localhost, OU=Learning, O=Example, C=US" -ext "SAN=dns:localhost,ip:127.0.0.1" -storetype PKCS12 -keystore server.p12 -storepass changeit -keypass changeit -noprompt
```

The `server.p12` file contains the **private key + self-signed server certificate**. `-alias server` only sets the internal alias. `SAN=dns:localhost,ip:127.0.0.1` assigns the target identity so the raw `SSLSocket` client in the demo can verify the `127.0.0.1` address using the `HTTPS` endpoint identification algorithm. Do not rely on Common Name `CN=localhost` instead of SAN.

### Step 2: export the public certificate, not the private key

```sh
keytool -exportcert -alias server -keystore server.p12 -storepass changeit -rfc -file server.crt
```

The `server.crt` file contains the certificate in PEM format; there is no private key. You can provide this public certificate to the party that needs to configure the lab's trust material.

### Step 3: import into the client's truststore

```sh
keytool -importcert -alias server-cert -file server.crt -keystore client-trust.p12 -storetype PKCS12 -storepass changeit -noprompt
```

The `client-trust.p12` truststore holds the public certificate as a `TrustedCertificateEntry`, **without holding the server private key**. Importing a self-signed leaf as a trust anchor is a specific lab trust setup, not a production CA/PKI model.

### Step 4: check entry types

```sh
keytool -list -keystore server.p12 -storetype PKCS12 -storepass changeit
keytool -list -keystore client-trust.p12 -storetype PKCS12 -storepass changeit
```

Expect alias `server` to be `PrivateKeyEntry` and alias `server-cert` to be `trustedCertEntry` (capitalization in output may vary). Do not send `server.p12` to the client; that file has the private key.

The password `changeit` is a **fixed password used for learning examples**, never use it for real systems. Command-line arguments and shell history can expose passwords; in production use secret management, file permissions, and proper credential input mechanisms. Lab private keys also need to be cleaned up after use.

## 9. Java 17+ demo #1: distinguishing entry types and initializing SSLContext

Save the **`TlsRolesInspect.java`** file below into the exact lab directory just created. The program reads the two PKCS#12 stores, checks aliases/entries, and then initializes `KeyManagerFactory`, `TrustManagerFactory`, and a custom `SSLContext`.

```java
import java.io.InputStream;
import java.nio.file.Files;
import java.nio.file.Path;
import java.security.KeyStore;
import java.security.SecureRandom;
import java.util.Arrays;
import javax.net.ssl.KeyManagerFactory;
import javax.net.ssl.SSLContext;
import javax.net.ssl.TrustManagerFactory;

public class TlsRolesInspect {
    static KeyStore load(Path file, char[] pass) throws Exception {
        KeyStore store = KeyStore.getInstance("PKCS12");
        try (InputStream in = Files.newInputStream(file)) {
            store.load(in, pass);
        }
        return store;
    }

    public static void main(String[] args) throws Exception {
        if (args.length != 2) {
            throw new IllegalArgumentException(
                    "Usage: TlsRolesInspect server.p12 client-trust.p12");
        }
        char[] pass = "changeit".toCharArray(); // LAB ONLY!
        try {
            KeyStore identity = load(Path.of(args[0]), pass);
            KeyStore trusted = load(Path.of(args[1]), pass);

            System.out.println("Server identity has private key: "
                    + identity.isKeyEntry("server"));
            System.out.println("Client trusts certificate: "
                    + trusted.isCertificateEntry("server-cert"));
            System.out.println("Truststore holds private key: "
                    + trusted.isKeyEntry("server-cert"));

            KeyManagerFactory kmf = KeyManagerFactory.getInstance(
                    KeyManagerFactory.getDefaultAlgorithm());
            kmf.init(identity, pass);
            TrustManagerFactory tmf = TrustManagerFactory.getInstance(
                    TrustManagerFactory.getDefaultAlgorithm());
            tmf.init(trusted);

            SSLContext context = SSLContext.getInstance("TLS");
            context.init(kmf.getKeyManagers(),
                    tmf.getTrustManagers(), new SecureRandom());
            System.out.println("Custom TLS context ready: "
                    + (context.getSocketFactory() != null));
        } finally {
            Arrays.fill(pass, '\0');
        }
    }
}
```

Compile and run:

```sh
javac -encoding UTF-8 TlsRolesInspect.java
java TlsRolesInspect server.p12 client-trust.p12
```

Stdout when stores are created per step 8:

```text
Server identity has private key: true
Client trusts certificate: true
Truststore holds private key: false
Custom TLS context ready: true
```

Why is this right?

- Both files are in PKCS12 format, but `identity.isKeyEntry("server")` returns `true` because the entry contains a private key.
- `trusted.isCertificateEntry("server-cert")` returns `true`, while `trusted.isKeyEntry("server-cert")` is `false`. The client-side store only holds a certificate to trust the peer.
- `kmf.init(identity, pass)` supplies local key material to the manager; `tmf.init(trusted)` supplies trust material to the manager. `SSLContext.init(kms,tms,random)` combines both responsibilities.
- `Custom TLS context ready: true` **only confirms that the context could be initialized**, not that an actual handshake with a peer succeeded or that the hostname matches. That is a separate test.

`Arrays.fill(pass, '\0')` reduces the time the password array stays in memory after use, but the demo code contains the literal `"changeit"`, which is not how production credentials should be secured.

## 10. Java 17+ demo #2: TLS loopback, server identity, and client trust

The **`TlsLoopback.java`** program creates a server context with a `KeyManager` reading `server.p12`, and a client context with a `TrustManager` reading `client-trust.p12`. The client **has no local certificate** because this is one-way server-authenticated TLS, not mTLS.

In the code, the raw `SSLSocket` client enables `SSLParameters.setEndpointIdentificationAlgorithm("HTTPS")` before the handshake, to verify that `127.0.0.1` matches the server certificate's **IP SAN**. Both sides exchange a `PING` request and an `ACK:PING` response over loopback TLS.

```java
import java.io.BufferedReader;
import java.io.BufferedWriter;
import java.io.InputStream;
import java.io.InputStreamReader;
import java.io.OutputStreamWriter;
import java.net.InetAddress;
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.Path;
import java.security.KeyStore;
import java.security.SecureRandom;
import java.util.Arrays;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.concurrent.TimeUnit;
import javax.net.ssl.KeyManagerFactory;
import javax.net.ssl.SSLContext;
import javax.net.ssl.SSLParameters;
import javax.net.ssl.SSLServerSocket;
import javax.net.ssl.SSLSocket;
import javax.net.ssl.TrustManagerFactory;

public class TlsLoopback {
    static KeyStore load(Path file, char[] pass) throws Exception {
        KeyStore store = KeyStore.getInstance("PKCS12");
        try (InputStream in = Files.newInputStream(file)) {
            store.load(in, pass);
        }
        return store;
    }

    static SSLContext forServer(Path identityPath, char[] pass)
            throws Exception {
        KeyManagerFactory kmf = KeyManagerFactory.getInstance(
                KeyManagerFactory.getDefaultAlgorithm());
        kmf.init(load(identityPath, pass), pass);
        SSLContext context = SSLContext.getInstance("TLS");
        context.init(kmf.getKeyManagers(), null, new SecureRandom());
        return context;
    }

    static SSLContext forClient(Path trustPath, char[] pass)
            throws Exception {
        TrustManagerFactory tmf = TrustManagerFactory.getInstance(
                TrustManagerFactory.getDefaultAlgorithm());
        tmf.init(load(trustPath, pass));
        SSLContext context = SSLContext.getInstance("TLS");
        context.init(null, tmf.getTrustManagers(), new SecureRandom());
        return context;
    }

    public static void main(String[] args) throws Exception {
        if (args.length != 2) {
            throw new IllegalArgumentException(
                    "Usage: TlsLoopback server.p12 client-trust.p12");
        }
        char[] pass = "changeit".toCharArray();
        try {
            SSLContext serverTls = forServer(Path.of(args[0]), pass);
            SSLContext clientTls = forClient(Path.of(args[1]), pass);
            InetAddress local = InetAddress.getByAddress(
                    new byte[] {127, 0, 0, 1});

            try (SSLServerSocket listener = (SSLServerSocket)
                    serverTls.getServerSocketFactory()
                            .createServerSocket(0, 10, local)) {
                listener.setSoTimeout(10_000);
                int port = listener.getLocalPort();
                ExecutorService workers = Executors.newSingleThreadExecutor();
                try {
                    Future<String> future = workers.submit(() -> {
                        try (SSLSocket peer = (SSLSocket) listener.accept()) {
                            peer.setSoTimeout(10_000);
                            peer.startHandshake();
                            BufferedReader in = new BufferedReader(
                                    new InputStreamReader(
                                            peer.getInputStream(),
                                            StandardCharsets.UTF_8));
                            BufferedWriter out = new BufferedWriter(
                                    new OutputStreamWriter(
                                            peer.getOutputStream(),
                                            StandardCharsets.UTF_8));
                            String request = in.readLine();
                            out.write("ACK:" + request);
                            out.newLine();
                            out.flush();
                            return request;
                        }
                    });

                    try (SSLSocket client = (SSLSocket)
                            clientTls.getSocketFactory()
                                    .createSocket("127.0.0.1", port)) {
                        client.setSoTimeout(10_000);
                        SSLParameters parameters = client.getSSLParameters();
                        parameters.setEndpointIdentificationAlgorithm("HTTPS");
                        client.setSSLParameters(parameters);
                        client.startHandshake();

                        BufferedWriter out = new BufferedWriter(
                                new OutputStreamWriter(
                                        client.getOutputStream(),
                                        StandardCharsets.UTF_8));
                        BufferedReader in = new BufferedReader(
                                new InputStreamReader(
                                        client.getInputStream(),
                                        StandardCharsets.UTF_8));
                        out.write("PING");
                        out.newLine();
                        out.flush();

                        String reply = in.readLine();
                        System.out.println("TLS handshake success: true");
                        System.out.println("Peer certificate available: "
                                + (client.getSession()
                                        .getPeerCertificates().length > 0));
                        System.out.println("Client reply: " + reply);
                    }
                    System.out.println("Server request: "
                            + future.get(15, TimeUnit.SECONDS));
                } finally {
                    workers.shutdownNow();
                }
            }
        } finally {
            Arrays.fill(pass, '\0');
        }
    }
}
```

Compile and run:

```sh
javac -encoding UTF-8 TlsLoopback.java
java TlsLoopback server.p12 client-trust.p12
```

Stdout of a valid connection:

```text
TLS handshake success: true
Peer certificate available: true
Client reply: ACK:PING
Server request: PING
```

Key takeaways:

1. The server `KeyManagerFactory` has the private key/cert chain in the identity store. The client `TrustManagerFactory` trusts the exact imported public certificate.
2. The client's `context.init(null, tmf.getTrustManagers(),...)` does not pass local key material, **nor does it turn the process into mTLS**.
3. `setEndpointIdentificationAlgorithm("HTTPS")` causes the client to check the endpoint's name/IP in the certificate via the supporting provider. IP `127.0.0.1` requires an **IP SAN**, not just a DNS SAN `localhost`.
4. `client.startHandshake()` performs the handshake; if the client does not trust the certificate or the endpoint identity does not match, the connection is rejected instead of proceeding with application exchange.
5. `getPeerCertificates()` returns peer certificates after the handshake. It **does not replace** the trust manager and hostname checking; an app calling the method and counting certs is not a validation process.
6. The server worker thread and client thread run concurrently to avoid circular waiting during handshake, reading, and writing. The listener binds **only to 127.0.0.1**, not listening on the Internet.
7. The TLS `ACK:PING` in the demo is an **application response**, not proof that data was saved to a DB or that access was authorized.

For real-world testing, certificates need to be issued by an appropriate PKI, rather than using self-signed certs and hardcoded passwords like in the lab.

## 11. SSLContext: where identity and trust are combined, not a store

`SSLContext` provides factories for `SSLSocket`, `SSLServerSocket`, and `SSLEngine`, along with the necessary TLS state. You configure **runtime managers**:

```java
// Snippet: kmf and tmf have already been initialized.
SSLContext context = SSLContext.getInstance("TLS");
context.init(
        kmf.getKeyManagers(),     // local identity
        tmf.getTrustManagers(),   // peer verification
        new SecureRandom()
);
```

An initialized `SSLContext` does not create keystores, does not sign certificates, and does not verify chains/hostnames on its own. Actual identity verification checks take place during the handshake for each connection.

**Important `null` semantics:** with SunJSSE, `KeyManager[] = null` normally means no local key credentials are provided, while `TrustManager[] = null` makes the provider use its default according to its mechanism. That **is not "trust all"**. If policy requires a dedicated truststore, explicitly provide managers initialized by `TrustManagerFactory` with that store, rather than relying on an implicit fallback.

Do not assume `SSLContext.getInstance("TLS")` uses TLS 1.0: `TLS` is a context name supporting negotiation of TLS versions per JDK/provider/policy; avoid re-enabling obsolete protocols/ciphers just because an old peer cannot connect.

## 12. Default truststore and custom-configured truststore

Java has a default trust material mechanism via provider/JDK settings; in SunJSSE, configuration may inspect `javax.net.ssl.trustStore` and installed truststore files like `jssecacerts` and `cacerts` according to version/provider rules.

| How trust managers are created | What to remember |
| --- | --- |
| `tmf.init((KeyStore) null)` | Asks the provider to load default trust material according to its rules |
| `tmf.init(customTrust)` | Uses trust material from the **explicitly passed store**, not implicitly merged with the default CA set |
| `tmf.init(emptyKeyStore)` | Has no desired trust anchors; may cause all chain validations under this mechanism to fail |
| `SSLContext.init(km, null, rng)` | The provider determines default trust managers; must not be interpreted as disabling checks |

A truststore containing only an internal private CA may allow a client to connect to internal APIs but **no longer trust public HTTPS endpoints** if the application only uses that custom truststore. If two different trust groups are needed, consider **separate `SSLContext` instances per service** or a deliberately designed combined policy, rather than adding "every CA" to a global truststore.

Common JVM properties:

```text
-Djavax.net.ssl.keyStore=/path/identity.p12
-Djavax.net.ssl.keyStoreType=PKCS12
-Djavax.net.ssl.trustStore=/path/trust.p12
-Djavax.net.ssl.trustStoreType=PKCS12
```

They affect how the appropriate **default managers/context** are obtained, and do not automatically override an `SSLContext` explicitly initialized with custom managers. Password JVM properties/arguments also carry the risk of exposing secrets through process configuration or logs. For multi-tenant/multi-service applications, prefer scoping trust/identity explicitly rather than making a JVM-wide change.

## 13. Hostname verification is a separate verification layer

For example, a client wants to call `service-a.example`. The certificate has a valid chain to a trusted CA, but its SAN only contains `service-b.example`. If the application only checks the chain without **verifying the target name**, it can trust the wrong service.

In raw JSSE using `SSLSocket`:

```java
// Illustrative snippet: socket created from SSLSocketFactory.
SSLParameters parameters = socket.getSSLParameters();
parameters.setEndpointIdentificationAlgorithm("HTTPS");
socket.setSSLParameters(parameters);
socket.startHandshake();
```

`HTTPS` here is the name of the endpoint identification algorithm supported by JSSE; it does not mean you are forced to use HTTP over the socket. With an HTTP client that has a built-in hostname verification layer, use the client's policy instead of layering a context-unaware custom verifier on top.

**SAN vs CN:** for hostnames or IPs, certificate design must include the corresponding SAN. Do not rely on `CN` as a way to "patch" a certificate missing a SAN. When connecting by IP, a matching **IP SAN** is required; a DNS SAN containing `localhost` does not automatically verify `127.0.0.1`.

In other words: **the truststore decides which CAs/certs are trusted**; **endpoint identification decides whether that cert matches the expected host/IP**. Both are essential.

## 14. Handling mTLS properly in both directions

In mTLS, the server presents `server.p12`, and the client presents `client-identity.p12`; at the same time, the client trusts the server CA/cert and the server trusts the client CA/cert.

An **API illustration snippet, not standalone**, with factories already initialized from proper sources:

```java
SSLContext serverContext = SSLContext.getInstance("TLS");
serverContext.init(
        serverKeyManagerFactory.getKeyManagers(),
        serverClientTrustFactory.getTrustManagers(),
        new SecureRandom()
);

SSLServerSocket listener = (SSLServerSocket)
        serverContext.getServerSocketFactory().createServerSocket(port);
listener.setNeedClientAuth(true);

SSLContext clientContext = SSLContext.getInstance("TLS");
clientContext.init(
        clientKeyManagerFactory.getKeyManagers(),
        clientServerTrustFactory.getTrustManagers(),
        new SecureRandom()
);
```

If the server configures `setWantClientAuth(true)`, the client may omit presenting a certificate and the handshake can still be accepted depending on policy. If the business logic genuinely requires client authentication, use `setNeedClientAuth(true)`. Attention must be paid to whether the certificate uses the right **Extended Key Usage** (e.g., serverAuth/clientAuth when required by policy), issuer/trust anchor, validity period, and how the identity maps to business permissions.

Do not confuse client certificate authentication with login/authorization. A client certificate signed by an internal CA does not automatically prove it has permission to modify data across all tenants.

## 15. Never use trust-all to fix handshake errors

A dangerous anti-pattern is implementing a custom `X509TrustManager` with empty `checkServerTrusted` and `checkClientTrusted`:

```java
// Only to recognize the security flaw: DO NOT USE.
X509TrustManager unsafe = new X509TrustManager() {
    public void checkServerTrusted(X509Certificate[] c, String a) {}
    public void checkClientTrusted(X509Certificate[] c, String a) {}
    public X509Certificate[] getAcceptedIssuers() {
        return new X509Certificate[0];
    }
};
```

This snippet is missing imports and is only to **identify an anti-pattern**, not a runnable guide. Leaving checks empty removes the certificate validation layer. If combined with a hostname verifier that always returns true, the app easily becomes a target for man-in-the-middle attacks.

The right approach: find the root cause of `SSLHandshakeException`/`CertPathValidatorException`, provide the correct trust anchors, chain, and SAN, ensure the server has a valid private key and certificate, and re-test **rejection cases**. If a custom trust policy is needed, consider delegating to a standard PKIX trust manager and only adding stricter constraints; do not skip checks.

In particular, never automatically import every encountered certificate into the truststore in an untrusted environment. Doing so is equivalent to granting any new peer the right to designate whom to trust.

## 16. Isolating errors by authentication direction

| Symptom | What to investigate | Do not react by |
| --- | --- | --- |
| `PKIX path building failed` on client | Client truststore, root/intermediate CA, chain sent by server | Trust-all |
| `No subject alternative names matching IP address` | IP SAN in server cert, connected IP, endpoint ID | Disabling hostname checking |
| `No name matching ...` | DNS SAN and actual host name of the request | Just renaming the alias in the store |
| `no suitable certificate` | Local identity store, `PrivateKeyEntry`, chain, key type, password | Copying private key to peer |
| `unknown_ca` / `bad_certificate` in mTLS | Server trusting client certificate/CA, whether client presented a cert | Turning off needClientAuth if mTLS is still required |
| `UnrecoverableKeyException` | Key entry password and provider/type | Removing passwords/security |
| `certificate_expired` | Clock, validity period, and chain/policy | Relaxing trust manager for expired certs |
| HTTP 403 after successful TLS | App authorization, principal mapping | Blaming the truststore |

Message strings vary by provider/TLS version, and the side receiving an alert may only see a generic message. Reading logs on **both ends** reveals which side rejected the certificate.

In a lab environment, debug logging can be enabled:

```text
-Djavax.net.debug=ssl,handshake,trustmanager,keymanager
```

Depending on the provider/JDK, logs may contain certificate chains, hostnames, or sensitive metadata. Enable only temporarily when compliant with internal logging policies, then turn it off. Do not post full logs containing internal info/secrets to public forums.

## 17. Managing passwords, private keys, rotation, and integrity

Do not confuse two types of passwords:

- **Store password:** protects/verifies access to open the entire store, depending on provider/store type.
- **Key password:** used to recover the private key of a key entry; `KeyManagerFactory.init(identity, keyPassword)` accesses key material with the appropriate password.

Many PKCS12 implementations on the JDK use the same password for both store and key, but the two concepts are not completely synonymous across all providers. A store can load successfully yet fail to retrieve the key if the key password is wrong.

Important measures:

1. **Private keys are secrets:** do not commit them to Git, do not put them into client truststores, do not bake them into public build/container images, and do not write them to logs.
2. **Protect truststore integrity:** even though certificates are public, anyone with permission to add a CA to the truststore can alter the application's trust scope.
3. **Do not hardcode production secrets:** `changeit` in the demo is only for learning the API. Real secrets require a vault/KMS/HSM or equivalent protected deployment mechanism.
4. **File permissions:** the TLS service process should only have read access to the exact identity/trust material it needs; avoid unnecessary write access as well.
5. **Prepare for rotation:** replace certs/keys before expiration, verify chain/SAN/EKU, plan trust overlap phases when needed, and have a clear rollback policy.
6. **Intentional reload:** replacing `.p12` on disk **does not guarantee** an already-initialized `SSLContext` will automatically detect it. Managers/contexts/factories must be recreated according to lifecycle, while managing old connections/sessions.
7. **Certificate revocation:** depending on policy and provider, configure CRL/OCSP and monitor certificate status; do not assume every Java application automatically performs online revocation checks.
8. **HSM/PKCS#11:** key material may be managed by a token/provider instead of a PKCS12 file; the `KeyManager` role remains local identity.

## 18. Common misconceptions

1. **“KeyManager verifies the server certificate.”** Not as its primary responsibility: KeyManager selects local credentials; TrustManager verifies the peer.
2. **“TrustManager provides the private key for the server to sign the handshake.”** False: that is the identity/key manager.
3. **“Just having the public certificate in the server keystore is enough for the server to run TLS.”** Server certificate authentication usually requires the matching private key.
4. **“The client must have a copy of the server private key to trust the server.”** Completely wrong from a security standpoint.
5. **“A keystore must be JKS while a truststore must be P12.”** Both stores can be PKCS12 or another suitable type.
6. **“The keystore alias must equal the hostname.”** An alias is an entry name; SAN/endpoint identification determines host matching.
7. **“A truststore with a valid root CA means hostname verification is unnecessary.”** Chain trust does not prove the right hostname.
8. **“mTLS only requires the server to have a truststore.”** mTLS requires client identity, server identity, and trust on both sides.
9. **“Using wantClientAuth forces every client to have a cert.”** To make it mandatory, you must use needClientAuth.
10. **“Every PKIX error can be fixed with an empty checkServerTrusted.”** Doing so disables authentication.
11. **“SSLContext.init succeeding means the handshake is complete.”** Init configures; the handshake happens when a connection is active.
12. **“Once TLS is in place, every client is allowed to access the API.”** TLS authentication does not replace business authorization.
13. **“A truststore file is public so anyone can edit it.”** Trust anchor integrity is critical.
14. **“Replacing the keystore file automatically updates certs for all connections.”** Reloading and session lifecycle must be designed.
15. **“A custom truststore automatically adds to the default CAs.”** Not by default; it depends on the policy/tmfactory initialized.
16. **“Setting JVM properties overrides every explicit SSLContext.”** No; a context managing its own managers has its own scope.
17. **“Using trust-all only briefly in production is harmless.”** It is an authentication vulnerability; fix the actual root cause.
18. **“A client certificate issued by a valid CA automatically grants access to all tenants.”** Identity/authorization must be mapped separately.

## 19. Self-check questions

**1.** A server has `server.crt` but no private key. Is that enough for TLS server authentication? **No.** KeyManager needs local credentials with the corresponding private key.

**2.** A client wants to trust a self-signed server in a lab. Should you copy `server.p12` or import the public `server.crt` into the truststore? **Only import the public cert** (or CA per trust policy); do not copy the private key.

**3.** A server needs to authenticate clients using mTLS. Does the server also need a TrustManager? **Yes.** The server must validate the client certificate chain, while also requiring a client cert via `setNeedClientAuth(true)`.

**4.** A client uses `TrustManagerFactory.init(customTrustStore)`; are default public CAs guaranteed to still be trusted? **No.** Custom trust material can replace the CA set in the context.

**5.** The signing CA of a certificate is trusted, but the connected host differs from the SAN. Is the connection valid? **No**, under proper endpoint identification policy: the name/IP must match.

**6.** Both files are `.p12`; which file is the keystore and which is the truststore? **It depends on the entry contents and how the managers use them**, not on the file extension.

**7.** Does `setWantClientAuth(true)` require the client to send a certificate? **No**, unlike `setNeedClientAuth(true)`.

**8.** You received an `unknown_ca` alert; should you disable the trust manager to keep running? **No.** Check the CA, chain, store, and proper trust mapping.

## 20. Pre-deployment configuration checklist

1. **Identify who is the TLS server/client and whether mTLS is used.** Do not confuse roles based on HTTP class names.
2. **Identify local identity stores:** the side presenting a cert must have the right private key and chain; alias, SAN, EKU, and algorithm must match.
3. **Identify peer truststores:** who is trusted per CA/cert/policy; trust scope should be the minimum needed for business requirements.
4. **Initialize manager factories according to responsibility:** `KeyManagerFactory.init(identity, password)` and `TrustManagerFactory.init(trust)`.
5. **Assemble `SSLContext` with the right scope:** avoid a global context that accidentally trusts overly broad CAs for all services.
6. **Verify endpoint identity:** raw TLS clients enable hostname/IP checking when needed; SAN matches the called address.
7. **If mTLS:** server requires client cert, client has identity, both have trust anchors for the other side.
8. **Test both success and failure cases:** wrong CA, wrong SAN, expired cert, missing private key, client missing certificate, wrong password.
9. **Protect secrets and truststore integrity:** permissions, vault/KMS/HSM, no keys/passwords leaked in source or logs.
10. **Plan rotation/reload:** monitor expiry, overlap CAs when needed, set up new SSLContext/engine/socket and rollback.
11. **Maintain authorization after authentication:** a valid cert does not automatically grant permission to operate on every resource.
12. **Never disable certificate validation as a "quick fix":** resolve the actual PKIX/endpoint root cause.

**Summary:** `KeyManager` answers **"Which private key/certificate do I use to prove who I am?"**. `TrustManager` answers **"Do I trust this peer's certificate?"**. A *keystore* usually holds a local private key + chain; a *truststore* holds public trust anchors/certificates. Both stores can be PKCS#12; what matters are the **data, factories, TLS roles, and endpoint identity policy**.
