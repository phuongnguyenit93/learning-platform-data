# Class Identity by Binary Name Combined with Defining Loader in the JVM

## 1. Core Idea: Same Name Does Not Necessarily Mean Same Type

In Java source, when seeing `com.example.Service`, we often think of it as a single class. However, the JVM can run multiple applications, plugins, modules, or isolated environments, each having its own way of loading class files. Therefore, the JVM cannot identify a **runtime class/interface** solely by a name string.

According to the **Java Virtual Machine Specification (JVMS §5.3)**, a class or interface at runtime is identified by a **pair**:

> **(Binary name, defining class loader)**

This can be notated as:

```text
Runtime type identity = (N, Ld)

N  = binary name of the class/interface
Ld = defining class loader that defined that class/interface
```

Extremely important consequences:

- **Same binary name + same defining loader** → same runtime class/interface represented by the same `Class` object in a JVM, according to valid class loading rules.
- **Same binary name + different defining loader** → can be **two different runtime classes/interfaces**, even if the `.class` bytecode is read from the same file and the source declarations are completely identical.
- **Different binary name** → two different class/interface identities, even if using the same loader.
- The fact that a loader **requests to load** a class does not necessarily mean that loader itself **defined** the class, because the request can be **delegated (delegation)** to another loader.

Logical example:

```text
("com.example.Plugin", loader A) ≠ ("com.example.Plugin", loader B)

("com.example.Plugin", loader A) = ("com.example.Plugin", loader A)
```

This is **type identity** in the JVM, not string comparison, not `equals()` of instances, and does not depend on whether two class files have identical contents or not.

**Learning objectives:** distinguish binary name from other name forms, defining loader from initiating loader, explain `ClassCastException` "class X cannot be cast to class X", know how to isolate plugins and share APIs properly, understand impacts on packages, array types, reflection, and class loading diagnostics.

## 2. What Exactly Is a Binary Name?

A **binary name** is the name of a class/interface according to Java rules used in class files and binary linking, not every friendly name display form in Java source. For a top-level class, the name usually consists of the package name and class name joined by a dot:

```java
package com.example;
public class Account { }
```

Binary name: `com.example.Account`.

For a nested member class:

```java
package com.example;

public class Outer {
    public static class Inner { }
}
```

Binary name of the member class: **`com.example.Outer$Inner`**. In Java source, we usually write `Outer.Inner`; the `$` in the binary name reflects the binary naming rule, not a new package.

### 2.1. Name Forms to Distinguish

| Name form | Example | Used in context |
| --- | --- | --- |
| Source/canonical name | `com.example.Outer.Inner` | Readable type name syntax in Java source; `Class.getCanonicalName()` when a canonical name exists |
| **Binary name** | `com.example.Outer$Inner` | Loading a class by name, runtime identity of a nonarray class/interface |
| Internal form in class file | `com/example/Outer$Inner` | Constant pool structures and many JVM descriptors |
| Class resource path | `com/example/Outer$Inner.class` | Locating class bytecode according to classpath/JAR resource conventions |
| Reference field descriptor | `Lcom/example/Outer$Inner;` | Reference type descriptor in the JVM |
| Array class name | `[Lcom.example.Outer$Inner;` | `Class.getName()` form of a reference array |

**Do not type `com.example.Outer.Inner` into `ClassLoader.loadClass` when wanting the member class `Outer.Inner`** if its binary name is `com.example.Outer$Inner`. For `Class.forName` and `ClassLoader.loadClass`, use the name form matching the API contract.

Some local and anonymous classes have binary names generated by the compiler according to rules involving sequence numbers and `$`. Do not build APIs assuming any `$1`-style name will remain stable when changing source code or compiler versions.

### 2.2. Do Not Mistake the File Name for Runtime Identity

A file `Plugin.class` does not mean it is a class named `Plugin` in the default package. The binary name may be `com.example.Plugin`, and the class loader must find/define the class with the exact name the JVM expects. If using `defineClass(name, bytes,...)` where the passed name does not match the binary name declared in the bytecode, an error related to class name/format may occur.

Similarly, **same binary name does not prove same class**: the loader is also part of the identity.

## 3. Defining Loader and Initiating Loader: Two Different Roles

A class loader can:

1. **Read bytecode itself and define the class**, through mechanisms such as `defineClass`.
2. **Delegate to another loader** to find and define the class.
3. Participate in a loading request chain where the actual class is ultimately defined by another loader.

The JVMS uses two concepts:

- **Defining class loader (`Ld`):** the loader that directly defines a runtime class/interface from an appropriate binary representation, or the loader that the specification associates with defining an array class according to specific rules.
- **Initiating class loader (`Li`):** the loader that initiates a loading operation for a class/interface name and is recorded by the JVM according to loading rules, even when definition is delegated to another loader.

A class has **one defining loader** but can have **many initiating loaders**.

### 3.1. Delegation Example

```text
Caller requests loader PluginLoader to load java.lang.String
                       |
                       v
                 PluginLoader
                       |
                   delegate
                       v
               Parent / Platform ...
                       |
                       v
                Bootstrap loader
                       |
                       v
             defines java.lang.String
```

When the request succeeds, `PluginLoader` participated in **initiating loading**, but the **bootstrap loader** is the defining loader of `java.lang.String`. If the same `PluginLoader` requests `java.lang.String` again, loading does not create a new String class belonging to PluginLoader.

**Do not take the loader passed to `loadClass` or `Class.forName` and assume it is the defining loader**. That loader may delegate.

### 3.2. What Does `Class.getClassLoader()` Return?

For an ordinary nonarray class, `Class.getClassLoader()` provides the **defining class loader** of that class. If the class was defined by the bootstrap loader, the standard API typically returns **`null`** to represent bootstrap (not "class not yet loaded").

```java
System.out.println(String.class.getClassLoader() == null); // true on standard JDK
```

The line above is an example observing the bootstrap definition of `String` on common JDKs. Do not compare loaders by the name printed from `toString()`; to know whether it is the same loader object, check loader object identity.

### 3.3. Parent-First Is a Convention of Common Loaders, Not the Definition of Class Identity

`ClassLoader.loadClass` by default uses a model prioritizing delegation to parent (*parent-first delegation*) for eligible classes. This helps applications share Java platform classes and avoid creating unnecessary copies.

However, **parent-first is not a mandatory law for every custom loader**. There are child-first or name-selective designs for plugin isolation. Regardless of which loading strategy is used, the JVM still identifies a runtime class by **binary name and actual defining loader**.

One should not arbitrarily reload platform classes or classes in the `java.*` package using a custom loader; Java has constraints protecting packages, type linkage, and security. The experiment below **only redefines an application-owned class**, while platform classes are delegated.

## 4. Visual Example: Two Loaders Defining the Same Bytecode

Consider a class file with binary name `com.example.Plugin`.

```text
                      Plugin.class (same bytecode)
                               |
             +-----------------+-----------------+
             |                                   |
        ByteArrayLoader A                    ByteArrayLoader B
             |                                   |
       defineClass(...)                    defineClass(...)
             |                                   |
             v                                   v
    Class A: (Plugin, A)                 Class B: (Plugin, B)
             |                                   |
             +-----------------X-----------------+
                     Not the same runtime type
```

The two copies can:

- Have the same `Class.getName()` as `com.example.Plugin`.
- Have the same method signatures, field names, and bytecode.
- Still be **different `Class` objects**: `classA == classB` is false.
- Cannot cast an instance of `classA` to `classB` via a normal cast just because the names are identical.
- Can cause `ClassCastException` at runtime, or other linkage errors when types from the two loaders conflict.

This characteristic is used in plugin isolation, application servers, hot deployment, test runners, and systems that allow multiple library versions to coexist.

**Separation does not equal absolute security:** loaders still live in the same JVM process and can access shared resources if APIs, permissions, and protection mechanisms allow. ClassLoader is a tool for separating **namespace/type identity**, not creating a complete security sandbox on its own.

## 5. Complete Java 17+ Experiment: Same Name, Different Defining Loader

This example uses **a single source file** for easy execution. We will use two custom `ClassLoader` instances reading **the same class file of a nested class**, then calling `defineClass` separately in each loader. Both loaders still delegate other classes to the parent, so as not to conflict with `java.lang.*`.

Create file **`ClassIdentityDemo.java`**:

```java
import java.io.IOException;
import java.io.InputStream;
import java.lang.reflect.Array;

public class ClassIdentityDemo {
    public static class Payload {
        public Payload() {}

        public String say() {
            return "payload";
        }
    }

    static final class SelectiveLoader extends ClassLoader {
        private final String target;

        SelectiveLoader(ClassLoader parent, String target) {
            super(parent);
            this.target = target;
        }

        @Override
        protected Class<?> loadClass(String name, boolean resolve)
                throws ClassNotFoundException {
            synchronized (getClassLoadingLock(name)) {
                Class<?> result = findLoadedClass(name);

                if (result == null) {
                    if (name.equals(target)) {
                        String resource = name.replace('.', '/') + ".class";

                        try (InputStream in =
                                getParent().getResourceAsStream(resource)) {
                            if (in == null) {
                                throw new ClassNotFoundException(name);
                            }

                            byte[] bytes = in.readAllBytes();
                            result = defineClass(name, bytes, 0, bytes.length);
                        } catch (IOException e) {
                            throw new ClassNotFoundException(name, e);
                        }
                    } else {
                        result = super.loadClass(name, false);
                    }
                }

                if (resolve) {
                    resolveClass(result);
                }
                return result;
            }
        }
    }

    public static void main(String[] args) throws Exception {
        String binaryName = Payload.class.getName();
        ClassLoader parent = ClassIdentityDemo.class.getClassLoader();

        SelectiveLoader one = new SelectiveLoader(parent, binaryName);
        SelectiveLoader two = new SelectiveLoader(parent, binaryName);

        Class<?> first = one.loadClass(binaryName);
        Class<?> second = two.loadClass(binaryName);
        Object value = first.getDeclaredConstructor().newInstance();

        System.out.println("same binary name: "
                + first.getName().equals(second.getName()));
        System.out.println("same Class object: " + (first == second));
        System.out.println("loader one cache: "
                + (one.loadClass(binaryName) == first));
        System.out.println("defining loader one: "
                + (first.getClassLoader() == one));
        System.out.println("defining loader two: "
                + (second.getClassLoader() == two));

        System.out.println("first.isInstance(value): "
                + first.isInstance(value));
        System.out.println("second.isInstance(value): "
                + second.isInstance(value));
        System.out.println("app Payload.isInstance(value): "
                + Payload.class.isInstance(value));

        System.out.println("shared String by delegation: "
                + (one.loadClass("java.lang.String")
                    == two.loadClass("java.lang.String")));

        Class<?> arrayOne = Array.newInstance(first, 0).getClass();
        Class<?> arrayTwo = Array.newInstance(second, 0).getClass();

        System.out.println("array binary names equal: "
                + arrayOne.getName().equals(arrayTwo.getName()));
        System.out.println("array runtime types equal: "
                + (arrayOne == arrayTwo));
        System.out.println("array defining loader one: "
                + (arrayOne.getClassLoader() == one));

        try {
            Payload.class.cast(value);
            System.out.println("cast succeeded");
        } catch (ClassCastException exception) {
            System.out.println("cross-loader cast: ClassCastException");
        }
    }
}
```

### 5.1. Compile and Run

Place the file in the working directory, then run with **JDK 17 or newer**:

```bash
javac --release 17 ClassIdentityDemo.java
java ClassIdentityDemo
```

The `javac` command normally generates class files, including:

```text
ClassIdentityDemo.class
ClassIdentityDemo$Payload.class
ClassIdentityDemo$SelectiveLoader.class
```

The nested class names above are binary names using the `$` form. Do not delete the `ClassIdentityDemo$Payload.class` file because the loader needs to read the corresponding resource bytes.

### 5.2. Exact Stdout

```text
same binary name: true
same Class object: false
loader one cache: true
defining loader one: true
defining loader two: true
first.isInstance(value): true
second.isInstance(value): false
app Payload.isInstance(value): false
shared String by delegation: true
array binary names equal: true
array runtime types equal: false
array defining loader one: true
cross-loader cast: ClassCastException
```

The lines above do not print PID, identity hash code, or loader implementation name, so the result **does not depend on loader allocation order**. The example chose only one target class to redefine; other classes still follow delegation.

### 5.3. Explaining How the Loader Works

`SelectiveLoader` overrides `loadClass(String, boolean)`. For the exact name `Payload`:

1. `getClassLoadingLock(name)` synchronizes the class loading operation according to the loader's locking rules.
2. `findLoadedClass(name)` checks for an already-loaded version so as **not to define the same name twice in the same loader**.
3. `getParent().getResourceAsStream(resource)` reads the `Payload.class` bytes from the classpath accessible by the parent.
4. `defineClass(name, bytes, 0, bytes.length)` creates a **new runtime definition** belonging to the calling loader.
5. `resolveClass(result)` is called if the `resolve` flag requests it.

For any name other than `Payload`, the loader uses `super.loadClass(name, false)`, i.e. the parent's class-finding mechanism. Therefore, both loaders still share `java.lang.String` from the platform runtime.

**The experiment intentionally chose child-definition for a single name.** This is a learning tool, not a general-purpose class loader safe enough for all plugins, libraries, modules, resources, and operational lifecycles.

### 5.4. Explaining Each Group of Results

**`same binary name: true`:** both `Class` objects return the same name string `ClassIdentityDemo$Payload`.

**`same Class object: false`:** `first` and `second` have **different defining loaders**, so different class identities.

**`loader one cache: true`:** when loader one requests the same binary name again, it does not define a new copy; `findLoadedClass` returns the existing copy.

**`defining loader one/two: true`:** `Class.getClassLoader()` returns the loader object that actually defined the class. They are two different loaders, not just two name strings.

**`first.isInstance(value): true`:** `value` is an object instance of the class defined by loader one.

**`second.isInstance(value): false`:** even though loader two's class has the same name, the object does not belong to that runtime class.

**`app Payload.isInstance(value): false`:** even `Payload.class` known to the application itself via the classpath is a **third class** with the same binary name but defined by the parent/app loader; it is not the same class as the one created by loader one.

**`shared String by delegation: true`:** the two custom loaders delegate loading `java.lang.String` and receive the same standard class back.

**Two array lines:** an array class of a reference component has identity tied to the component type and defining loader; each array class here is also a different runtime class.

**`cross-loader cast: ClassCastException`:** casting loader one's instance to the app loader's `Payload` is a runtime type mismatch. `Class.cast` detects this and throws an exception, which the program catches to print a stable message.

## 6. Why Can Two Classes with the Same Bytecode Still Not Be Cast?

Java performs type checking at **compile-time** and at **runtime**. The compiler verifies operations according to the types the code references, but the JVM at execution time needs to know **which runtime class the actual object belongs to**.

Example:

```text
classA = ("demo.Plugin", loaderA)
classB = ("demo.Plugin", loaderB)

Object x = new instance of classA

classA.isInstance(x) → true
classB.isInstance(x) → false
```

There is no rule saying "if two classes define the same fields/methods, the JVM treats them as the same type" in class identity. Java does not apply automatic **structural typing** like some other languages. Interface/superclass compatibility is still based on validly loaded and linked type relationships.

In practice, stack traces are sometimes confusing:

```text
java.lang.ClassCastException:
  class demo.Plugin cannot be cast to class demo.Plugin
```

This is just a **condensed message pattern**, not the stdout of the example program. Modern JVMs may include module, loader, and class identity in the message. Do not conclude the runtime is "confused": **the two occurrences of `demo.Plugin` may be two different classes by defining loader**.

### 6.1. `Class.getName()` Is Not an Identity Check

Do not use:

```java
if (a.getClass().getName().equals(b.getClass().getName())) {
    // conclude a and b have the same runtime type
}
```

This is **illustrative code that can lead to a false conclusion**. Equal name strings only compare **half** of the identity. When wanting to know the exact same runtime class, compare:

```java
boolean sameRuntimeClass = a.getClass() == b.getClass();
```

If wanting to know whether an object is compatible with the type represented by `Class<?> clazz`, use:

```java
boolean compatible = clazz.isInstance(a);
```

If `a` is null, `getClass()` causes `NullPointerException`; `clazz.isInstance(null)` returns false by the API contract. Use the right check according to the business meaning.

### 6.2. Why Can `instanceof` Also Be False?

An expression such as:

```java
boolean ok = value instanceof SomeType;
```

is checked against the **runtime type** and assignability relationship with `SomeType` as seen by the class executing the statement. If `SomeType` comes from a different loader than the runtime class of `value`, the check can be false even if `getName()` has the same name.

## 7. An Initiating Loader Does Not Automatically Become a Defining Loader

Suppose `L1` calls `loadClass("java.util.List")` and delegation goes to the standard loader `L0`. At this point:

```text
Request from L1
    |
    +→ parent/delegation
             |
             v
         L0 defines java.util.List
```

`L1` may be recorded as an **initiating loader** for the class `java.util.List`, but `List.class.getClassLoader()` reflects the actual defining loader, not necessarily `L1`.

**A class can have many initiating loaders**, whereas the defining loader is a fixed component of identity.

### 7.1. When Does the Distinction Affect Design?

- **Plugin system:** the plugin loader asks the parent for a shared interface; the plugin loader **initiates** loading the interface while the **parent defines** it, so the host and plugin agree on the API.
- **Web application server:** multiple applications have separate loaders but share Java platform classes from the parent.
- **Dependency isolation:** the plugin loader defines internal implementations/dependencies itself to avoid version conflicts with other plugins.

Do not require every loader to define every class it sees itself. Doing so can accidentally split **APIs that need to be shared**, preventing objects from communicating through interfaces as intended.

### 7.2. Class Initialization Does Not Determine the Defining Loader

The concept of class loading/definition is different from **class initialization** (running `static initializer`). A class can be loaded and linked before it is initialized. That does not change the existing identity pair.

Example:

```java
Class<?> type = Class.forName("java.lang.String", false,
        ClassIdentityDemo.class.getClassLoader());
```

This is an **illustrative code snippet inside a method**, using the `Class.forName` overload with the `initialize=false` flag. This flag affects the initialization request, not the identity of the class. The passed loader may still delegate to another defining loader.

## 8. Built-in Loaders and Impact on Class Identity

On HotSpot/JDK 17 there are typically **bootstrap** (usually represented by `null` in the `getClassLoader()` API), **platform**, and **application/system** loaders. Custom loaders may continue to delegate or define bytecode themselves; there is no guarantee that all loaders use parent-first.

A point to remember **specifically for class identity**: a custom loader is an **object**. Two `PluginLoader` instances of the same Java class are still two different defining loaders if each instance calls `defineClass` on the same binary name; whereas two loaders that only delegate to one parent can both return the exact same `Class<?>`. Do not use the loader's implementation name instead of comparing object identity.

## 9. Array Classes: An Exception to Understand Properly

The JVM specification distinguishes creating a **nonarray class/interface** and creating an **array class**:

- A nonarray class/interface is created by loading a binary representation through a class loader.
- **Array classes are created directly by the JVM**, with no ordinary `.class` file corresponding to each array type.
- When the component type is a **reference type**, the defining loader of the array class is the **defining loader of the component type**.
- When the component type is a **primitive**, the defining loader of the array class is the **bootstrap loader**.

Example:

```java
String[] strings = new String[2];
int[] numbers = new int[2];
```

- `String[]` is an array type associated with `java.lang.String`; on a typical JDK the component class is defined by bootstrap.
- `int[]` has primitive component `int`; the array class is created by the JVM and associated with the bootstrap loader.
- `Plugin[]` has an array class associated with the defining loader of the component class `Plugin`.

### 9.1. Demonstration in the Executed Program

```java
Class<?> arrayOne = Array.newInstance(first, 0).getClass();
Class<?> arrayTwo = Array.newInstance(second, 0).getClass();
```

These two array classes have:

- The same `Class.getName()` because the component classes have the same binary name.
- **Different `Class` objects** because the component classes belong to two different defining loaders.
- Each array class has a defining loader corresponding to its component class.

Therefore **array class identity is also affected by component type identity**, even though an array class is not defined from a separate `.class` file.

### 9.2. Array Class Names Look Unusual but Follow Rules

Example:

| Java type | `Class.getName()` |
| --- | --- |
| `int[]` | `[I` |
| `String[]` | `[Ljava.lang.String;` |
| `String[][]` | `[[Ljava.lang.String;` |
| `Payload[]` of nested class | `[LClassIdentityDemo$Payload;` |

`Class.getName()` of an array class uses a form starting with `[` per the specified descriptor, not the source type name `java.lang.String[]`. Do not confuse this array name string with a class file path. Loading array types via reflection APIs has its own contract.

## 10. Runtime Package and Access Checking

At the Java source level, a package is usually seen as a name string:

```java
package com.example.plugins;
```

But at runtime, according to the JVMS, the **runtime package** of a nonarray class/interface is determined by **package name and defining loader**.

Therefore:

```text
com.example.plugins.PluginA    defined by loader A
com.example.plugins.PluginB    defined by loader B
```

Even though both classes have the same string package name **`com.example.plugins`**, they **do not automatically belong to the same runtime package**. This affects package-based access permissions in JVM checks, such as package-private members and certain constraints related to class accessibility.

**Common mistake:** creating two independent loaders, defining two classes "in the same package", and expecting to be able to call each other's package-private methods as if they were loaded by a single loader.

### 10.1. Package in Name Does Not Automatically Create a Trust Relationship

A plugin cannot just put a class in `com.host.internal` and automatically have all package-private access rights to the host's classes if the plugin class was created by a different defining loader. Loader identity is an important part of the runtime package boundary.

In Java 9+ there is also the **module system (JPMS)**, which adds rules for module readability, exports, and opens. Thus, when investigating `IllegalAccessError` or reflective access failures, it may be necessary to check **defining loader, runtime package, and module**. Do not blame every access error solely on the class loader.

## 11. Shared API, Isolated Implementation: Practical Plugin Design

A plugin architecture often needs to **isolate implementations** while **sharing contracts** with the host:

```text
              Host / Parent loader
               defines api.Task
                       |
        +--------------+--------------+
        |                             |
   Plugin loader A                Plugin loader B
   defines impl.A                 defines impl.B
   delegates api.Task             delegates api.Task
        |                             |
        +------ executes via ---------+
                same api.Task
```

If the parent defines `api.Task` and both plugin A and plugin B delegate loading it, the JVM sees **one shared runtime interface**. Implementations can be used via the interface on the host if the related methods/types link successfully.

Conversely, if each plugin defines its own copy of `api.Task`:

```text
("api.Task", loader A) ≠ ("api.Task", loader B)
("api.Task", loader A) ≠ ("api.Task", host loader)
```

then an object that "implements api.Task" according to loader A **does not become an instance of api.Task according to the host**. Even though the interface name is the same, the runtime type is different.

### 11.1. Shared API Contract Example

```java
// Example split into a shared module/library:
package api;

public interface Task {
    String run();
}
```

This illustrative source class **is not a standalone program**; it needs to be placed at `api/Task.java` and built with an appropriate classpath/module path. Importantly, the `api` package and `Task` class/interface should be **defined by a shared loader**, and each plugin's implementation simply references it.

When an API accepts/returns values, one must also consider the types in **method descriptors**. If two loaders see a parameter/return type under different class identities, linking across loaders can produce errors or mismatches.

### 11.2. Do Not Turn Every Library into a Shared Dependency

Isolating separate dependencies can be useful if two plugins need two incompatible versions of a library. However, if a library type appears in **API signatures communicating across the boundary**, the parties must have a unified type design. Types shared in interfaces are the key point for deciding **what to delegate** versus **what to isolate**.

A practical rule of thumb:

- **Share** API contracts, public DTOs, or classes used to exchange across the boundary when unified type identity is desired.
- **Isolate** internal implementations/dependencies that do not need direct exchange if there are version or lifecycle reasons.
- Design a serialization/message-passing mechanism when wanting to communicate between regions with different namespaces that cannot share the same runtime types.

Do not apply "child-first for all packages" just to solve one dependency name collision and thereby cause cast errors for shared interfaces.

## 12. Loading Constraints and Type Safety During Linking

JVMS §5.3.4 specifies **loading constraints** to ensure type safety when classes from different defining loaders have symbolic references to fields/methods whose types appear in descriptors.

Conceptual example:

```text
Host method:    api.Result process(api.Request request)
Plugin method:  api.Result process(api.Request request)
```

If the host and plugin need to link a method/type relationship across the boundary, the runtime must not arbitrarily treat the two `api.Request` types as equivalent when they are actually defined by two different loaders.

Therefore:

- Some simple mismatches appear as `ClassCastException` or `instanceof` returning false.
- Certain **loading constraint** violations can cause linking to fail with `LinkageError`.
- There is no single mandatory exception for every class-loader mismatch scenario; one must look at whether casting, accessing, resolving, or overriding/implementing an interface method is occurring.

**Do not try to fix this by disabling the verifier or bypassing type checks.** If class identities truly conflict, delegation, API boundaries, and dependency visibility must be redesigned.

### 12.1. Why Is `LinkageError` Different from `ClassNotFoundException`?

`ClassNotFoundException` typically arises when a class-loading-by-name API (such as `loadClass` or `Class.forName`) cannot find a suitable binary representation. Other linkage errors can occur when the class has been found but **cannot be verified, resolved, defined, or validly linked** with existing classes.

`NoClassDefFoundError` can occur when the runtime needs a class but cannot locate its definition or a prior class initialization failed. Do not lump all of them together as "the JVM couldn't find the JAR".

## 13. Common Pitfalls with Custom Class Loaders

### 13.1. Defining the Same Binary Name Twice in the Same Loader

A properly designed loader should return the already-defined class for the same name when loaded again. If calling `defineClass` twice for the same binary name in the same loader, a `LinkageError` related to duplicate class definition can occur.

In the example, `findLoadedClass(name)` prevents this error for loader one when calling `loadClass(name)` again.

### 13.2. Not Synchronizing When Multiple Threads Load the Same Name

Two threads requesting the same class simultaneously can race to the `defineClass` step if the loader does not handle locking/caching properly. Using locking/APIs according to the class loading contract is necessary. The example uses `getClassLoadingLock(name)`; any real-world custom loader also needs to carefully plan concurrent loading strategies, especially when opting into parallel-capable loaders.

### 13.3. Bypassing the Parent Causes Standard APIs to Be Duplicated

Redefining too many classes yourself can break object compatibility. Parent delegation helps share core classes and API contracts by design, while still needing to distinguish **requested class** from **defined class**.

### 13.4. Passing a `ClassLoader` Without Knowing Whether It Delegates

`Class.forName(name, false, loader)` and `loader.loadClass(name)` do not mean the returned class was definitely defined by the passed loader. Also check `result.getClassLoader()` to know the defining loader.

### 13.5. A Pretty Loader Object Name Does Not Make Two Classes Equivalent

Two loaders of the same class and with the same `toString()` can still be two different loaders. If an exact check is needed, use the identity of the loader object and class object; do not rely on friendly names in logs.

### 13.6. Using the Right Classpath or JAR but Still Getting Cast Errors

A class file sitting in the right JAR on disk does not sufficiently explain runtime identity: **which loader used the bytecode to define the class** is what matters. The same JAR opened by two independent `URLClassLoader` instances can create two runtime classes for the same binary name if both define them themselves.

### 13.7. Holding onto Old Class Loaders Prevents Class Unloading

Class unloading depends on reachability and GC/runtime behavior. If the host accidentally retains references to the loader/plugin classes/objects or components like thread/context class loader, static caches, listeners, `ThreadLocal`, etc., the old class loader may remain reachable and class metadata will not be reclaimed as expected.

Do not assume "deleting the JAR file or closing `URLClassLoader` immediately unloads all classes". The plugin lifecycle must release related references; whether and when GC occurs is a separate matter.

## 14. Thread Context Class Loader Is Not the Defining Loader

Java provides the API `Thread.currentThread().getContextClassLoader()`, often used by frameworks or service-loading mechanisms to find resources/classes through a context-appropriate loader.

Example:

```java
ClassLoader contextLoader =
        Thread.currentThread().getContextClassLoader();
```

This is an **illustrative code snippet inside a method**. The context loader is not a direct identifying property of every running class; it can change by thread or framework. One should not assume `contextLoader == SomeType.class.getClassLoader()` is always true.

Three questions to separate when debugging:

1. **Who initiated the load request?** It could be class/module code, a framework, or the context loader.
2. **Which loader ultimately defined the class?** Check `Class.getClassLoader()`.
3. **Which class is being used at the boundary?** Compare exact `Class` objects, method parameter types, and interface identity.

A thread context loader is only a **contextual lookup/delegation hint**; it does not change the defining loader of an existing class.

## 15. Module System and Class-Loader Identity

Since Java 9, **JPMS** adds the module graph, readability, exports/opens, and module layers. It affects finding, encapsulating, and accessing classes. However, it does not change the core conclusion: **a runtime class/interface is still identified by binary name and defining loader**, while also having to satisfy relevant module rules.

Do not conflate:

- **Module name** such as `com.example.app`.
- **Package name** such as `com.example.service`.
- **Binary class name** such as `com.example.service.Worker`.
- **Defining class loader object** of a runtime class.

For example, two module layers can lead to different class loader structures. Identical artifact contents do not prove two runtime classes are shared, if the class loader arrangement produces independent definitions.

To debug JPMS, inspect both `Class.getModule()` and `Class.getClassLoader()`; the two APIs return different information. Do not use module name as a substitute for loader identity.

## 16. Inspection Tools and How to Read Logs

### 16.1. Printing Name and Defining Loader in a Controlled Way

```java
static void describe(Class<?> type) {
    System.out.println("name: " + type.getName());
    System.out.println("loader: " + type.getClassLoader());
    System.out.println("module: " + type.getModule().getName());
}
```

This is **illustrative method code**, not a standalone program. `getClassLoader() == null` typically corresponds to bootstrap; `getModule().getName()` may return null for an unnamed module.

Loader names only assist log reading; to know whether two loaders are the same object, compare with `==`. In environments with different `toString()` implementations, one should not interpret loader output as a system-wide stable ID.

### 16.2. Tracing the Cause of a Bad Cast

When seeing a strange `ClassCastException`:

1. Get the **Class object** of the actual object via `value.getClass()` (if value is non-null).
2. Get the **Class object** of the target API type via `Target.class` or appropriate reflection.
3. Compare the **binary names** of the two `Class` objects.
4. Compare the **defining loaders** via `getClassLoader()`, then compare the `Class` objects themselves.
5. Check the loader delegation policy and dependency JAR/version mapping.
6. If the boundary crosses an interface, check whether the interface `Class` used by the host and plugin have the same identity.

`value.getClass().getName().equals(Target.class.getName())` returning true **does not end the investigation**; the loaders must be checked.

### 16.3. Logging Class Loading When Needed

Many modern JDKs have Unified Logging:

```bash
java -Xlog:class+load=info ClassIdentityDemo
```

Log syntax and output details may vary by JVM/version. The illustrative command fits common HotSpot/JDKs; do not treat every `-Xlog` option as part of every Java implementation.

Logs can show class names and bytecode sources, but to determine identity in code, the **`Class` object and defining loader** are more direct evidence. If class loading logs are too verbose, use levels/tags appropriate for the target JVM.

### 16.4. Inspecting a Class File Does Not Reveal Full Runtime Loader Identity

`javap -v` shows the binary name, constant pool, descriptors, and class file contents, but a file on disk **does not inherently have a single runtime defining loader**. A bytecode file can be read by multiple loaders and produce multiple runtime classes.

This is why one cannot use only `javap` or the SHA-256 hash of a `.class` file to conclude "that is the same `Class` in the JVM". Class file data must be combined with runtime class loading information.

## 17. Common Misconceptions

| Misconception | Correct understanding |
| --- | --- |
| "Binary name is enough to identify a class." | Must consider **(binary name, defining loader)**. |
| "Two byte-for-byte identical `.class` files are the same type." | Two loaders defining them separately can still create two different runtime types. |
| "Whichever loader calls `loadClass` is the defining loader." | It may **delegate** and only be an initiating loader. |
| "Two loaders of the same class `URLClassLoader` have the same identity." | Each loader **instance** is a separate object. |
| "`Class.getName()` is the same so casting is possible." | Casting must check runtime class/assignability, not just the name string. |
| "Same package name means same runtime package." | Also depends on **defining loader**. |
| "Array classes have their own `.class` files defined by a loader." | Array classes are created by the JVM; defining loader follows the component type. |
| "`int[]` is defined by a custom loader if plugin code creates it." | Primitive array types are associated with bootstrap, not defined by the plugin loader. |
| "Class loading is also running `static`." | Loading/linking and initialization are different phases. |
| "The context class loader is always the defining loader." | They serve different purposes. |
| "Closing the loader/JAR unloads classes immediately." | Class unloading depends on reachability/GC, with no guaranteed immediate timing. |
| "Completely removing parent-first makes independent plugins safer." | Can duplicate APIs, cause `ClassCastException`/`LinkageError`, and does not create a security sandbox. |
| "JPMS completely replaces class loaders." | Modules and loaders both participate in runtime organization/checks; it does not replace the JVMS pair identity. |

## 18. Self-Check Exercises with Answers

**Question 1.** Two separate loaders `A` and `B` both read a `Task.class` file with binary name `app.Task`. If both directly call `defineClass` successfully, do the two classes have the same identity?

**Answer:** No. The pairs `(app.Task, A)` and `(app.Task, B)` are different, even if the bytes are identical.

**Question 2.** Plugin loader `P` delegates loading `java.lang.String` to bootstrap. Who is the defining loader of String?

**Answer:** The bootstrap loader in standard JDKs. `P` may be an initiating loader, not the defining loader of String.

**Question 3.** Why is `Class.getName()` not enough to prove an object can be cast?

**Answer:** It does not contain defining loader identity. Runtime class and assignability relationships must be considered.

**Question 4.** What can the binary name of member class `Outer.Inner` be?

**Answer:** Typically `Outer$Inner` (with the corresponding package). The source dot between Outer and Inner is not a dot in the binary name.

**Question 5.** Can two custom loaders of the same class and with the same parent define two different copies of `Plugin`?

**Answer:** Yes, if each **loader instance** defines the same binary name itself. Having the same parent does not force sharing every class.

**Question 6.** With the same package name, are two classes created by two different defining loaders automatically in the same runtime package?

**Answer:** No. Runtime package involves **package name and defining loader**.

**Question 7.** Can two array types `Plugin[]` have different identities when their component classes have the same binary name?

**Answer:** Yes. If the component classes have different defining loaders, the corresponding array classes also have different identities.

**Question 8.** Is `int[].class.getClassLoader()` the custom loader of the class that wrote `new int[3]`?

**Answer:** No. Primitive array classes are created by the JVM and associated with the bootstrap loader.

**Question 9.** If the host and plugin need to share `api.Task`, how should the API normally be loaded?

**Answer:** Let a shared loader (usually the parent/host loader) define `api.Task`, and plugin loaders delegate that API type. Implementations can still be defined separately.

**Question 10.** Does `Class.forName(name, false, loader)` make the passed loader the defining loader?

**Answer:** Not necessarily. The loader may delegate; the `false` flag is about not requesting initialization, not changing the defining loader.

**Question 11.** Do `ClassCastException` and `LinkageError` in a multi-loader system have the exact same single cause?

**Answer:** No. Cast mismatch and loading/linking constraint failure are different issues, even though both sometimes involve types with the same binary name but different loaders.

**Question 12.** Two plugins use the same class file but are both defined independently. Can one plugin directly call a package-private member of the other plugin just because the package strings match?

**Answer:** That cannot be assumed. Runtime package includes the defining loader, and the JVM also checks access permissions/modules when appropriate.

## 19. Summary

```text
                     Binary name
                         +
                Defining class loader
                         |
                         v
                Runtime class identity
                         |
              +----------+----------+
              |                     |
         Class checks           Linkage checks
      cast / instanceof      method / field / API
              |                     |
              +----------+----------+
                         |
              Class loading policy
             (delegation, isolation, APIs)
```

Key takeaways:

1. **Do not identify a Java runtime class by name alone.** The pair **(binary name, defining loader)** determines class/interface identity.
2. **Initiating loader differs from defining loader.** Delegation can cause multiple loaders to use the same runtime definition.
3. **Same bytecode does not mean same type.** Two independent loaders can create two different `Class` objects and cause casts to fail.
4. **Array classes have special rules:** the JVM directly creates array classes, and the defining loader of an array class is determined from its component type.
5. **Runtime package and linking also depend on the loader.** Plugin design needs to share API contracts appropriately and isolate implementations in a controlled manner.
6. **Debugging must look at name, Class object, loader, and module when needed.** This is the basis for resolving type mismatch errors that look baffling on the surface.
