# `<init>` and `<clinit>`: two special methods with different roles in the JVM

In a Java ClassFile, **`<init>`** and **`<clinit>`** are the internal names of two types of *special methods*, but they serve two different purposes:

- **`<init>` — instance initialization method:** corresponds to a class's constructor. It is invoked during the initialization process of **each object** via a special invocation mechanism, typically the `invokespecial` bytecode. A class can have multiple `<init>` methods with different descriptors because constructors can be overloaded.
- **`<clinit>` — class/interface initialization method:** if present, contains the static initialization work that the compiler generates from static field initializers and static initializer blocks. It is **automatically executed by the JVM when the class or interface is initialized according to JVM rules**, typically only once per successful class/interface definition, not once per `new`.

When reading `javap` output, remember that `<init>` is not synonymous with **the entire object initialization**, and `<clinit>` is not synonymous with **loading a class file**. Class loading, linking, initialization, and constructor invocation are related but distinct steps.

## 1. Quick comparison of `<init>` and `<clinit>`

| Criterion | `<init>` | `<clinit>` |
| --- | --- | --- |
| Purpose | Initialize an **instance** through a constructor | Initialize the **static** state of a class/interface |
| Where does it come from? | Constructor written in source or default constructor generated by the compiler | Executable static initialization synthesized by the compiler |
| How many methods? | Can be multiple, distinguished by parameter descriptors | At most one method named `<clinit>` in a valid ClassFile |
| Descriptor | Form `(parameters)V`, returns `void` at the JVM level | **`()V`**: no parameters, returns no value |
| How it is invoked | Usually uses `invokespecial` with an uninitialized instance reference or within a constructor chain | Triggered by the JVM according to the class/interface initialization process; not called directly like a Java method |
| Relation to `new` | Constructor call occurs when creating an object via a `new` expression in a normal Java program | If the class is not yet initialized, a `new` operation may cause the class to require initialization before proceeding |
| Frequency | Every time there is a corresponding constructor call during object creation | Once per successfully initialized class/interface definition, except for a different definition from another class loader |
| Inherited / overridden? | Constructors are not inherited or overridden; a constructor chain may call `super(...)` or `this(...)` | Static initialization of the superclass occurs before the subclass according to rules; there is no overriding `<clinit>` |
| Callable from Java source by the name `<init>`/`<clinit>`? | No; use `new`, constructor chaining, or an appropriate reflection API | No; only write static field initializers/static blocks or let the JVM trigger it |
| Can it cause errors? | Exceptions from the constructor and the instance initialization process | Exceptions/Errors during class initialization, which can affect all subsequent uses |

**Mnemonic:** `<init>` is tied to **an object** and a constructor; `<clinit>` is tied to **class state**. Although their names contain angle brackets, these are special names in the ClassFile/JVM, **not Java source method declaration syntax**.

## 2. Placing the two methods properly in the JVM lifecycle

A conceptual model:

```text
      JVM needs to use a class
                 │
                 ▼
       Loading: load class definition
                 │
                 ▼
       Linking: verify, prepare, resolve
                 │
                 ▼
     Initialization when required
       ┌──────────────────────────┐
       │ Execute <clinit> if any  │
       │ (when conditions are met)│
       └──────────────────────────┘
                 │
                 ▼
          new an instance
                 │
                 ▼
     Constructor chain / <init>
                 │
                 ▼
        Use the created object
```

The diagram is the conceptual flow of **creating an object for the first time**; not every class loading operation immediately triggers initialization, and during execution many more classes may be loaded. Once a class has been initialized successfully, subsequent object creations **do not run `<clinit>` again**, but still run the appropriate constructor process.

### Distinguishing three notions of “initialization”

1. **Preparation:** The JVM prepares static fields with default values or `ConstantValue` values according to ClassFile rules, before executing static initializer code.
2. **Class/interface initialization:** The JVM performs class/interface initialization work, including `<clinit>` if the compiler generated one.
3. **Instance initialization:** After the object is allocated and instance fields have default values, the constructor chain and instance field initializers/instance initializer blocks establish the initial state of each object.

`static int total = compute();` usually requires executable code in `<clinit>`; `int value = compute();` is an instance field initializer and is usually inserted by the compiler into the `<init>` constructor at the appropriate location. There is no generic opcode named “execute every initializer” in bytecode that every case goes through.

## 3. `<init>`: instance initialization method

### 3.1. What does a Java constructor become in a class file?

Given the source:

```java
class Point {
    int x;

    Point() {
        this(0);
    }

    Point(int value) {
        x = value;
    }
}
```

This is an **illustrative class**; it can compile when placed in `Point.java` without needing `public`. In the ClassFile, the two constructors correspond to two `<init>` methods with different descriptors:

```text
Point.<init>:()V
Point.<init>:(I)V
```

- `()V` means it takes no parameters and completes normally without returning a value.
- `(I)V` means it takes one `int` and returns `void` at the method descriptor level.
- Both are seen by the JVM under the special name `<init>`, **not as two regular Java methods named `Point` that can be overridden**.

In Java source, a constructor **does not declare a return type**, not even `void`; the `V` notation in the descriptor is a JVM convention for how this method completes, and does not allow writing `void Point()` to declare a constructor.

### 3.2. `new` does not automatically call all constructors

When compiling the expression:

```java
Point point = new Point(5);
```

the bytecode typically has the pattern:

```text
new           Point
dup
iconst_5
invokespecial Point."<init>":(I)V
astore_1
```

This is an **illustrative bytecode snippet**, in which offsets, how the number `5` is pushed, and local variable indices may differ depending on context/compiler. Interpretation:

1. `new` requests instance creation; the reference on the stack is in an **uninitialized** state according to JVM verification rules.
2. `dup` duplicates the **reference value**, not creating a second object.
3. `iconst_5` pushes the argument `5` onto the operand stack.
4. `invokespecial` calls the exact instance initialization method `Point.<init>(int)`.
5. After initialization succeeds, the reference can be stored and used.

**Do not use an object invalidly before initialization completes.** The bytecode verifier tracks *uninitialized reference* forms and constructor invocation conditions. `<init>` is a special invocation kind, not a method that can be called arbitrarily with `invokevirtual`.

### 3.3. `this(...)`, `super(...)`, and constructor chaining

In Java 17, a normal constructor must begin with an appropriate constructor invocation:

- `this(...)` transfers to **another constructor of the same class**.
- `super(...)` transfers to a constructor of the **superclass**.
- If not written explicitly, `javac` inserts a `super()` call when valid.

For example, `Point()` calls `this(0)`, so when executing `new Point()`, the no-arg constructor does **not** run all instance field initializers on its own and then run the `Point(int)` constructor a second time. The object's initializers are arranged into the constructor flow so that they run the exact right number of times and in the right order according to Java semantics.

For an object of a subclass:

```text
new Child(...)
  → invoke the appropriate Child constructor
    → constructor chain to super(...)
      → constructor chain of ancestors
      → instance initialization part of superclass
    → instance initialization part of Child
    → body of Child constructor
  → object is ready to be returned if no exception occurs
```

This is a semantic diagram; in actual bytecode, **`<init>` calls are nested** and Java source has rules for argument evaluation, instance initializers, and constructor body ordering. See the runnable example in section 6 for the exact output.

### 3.4. Default values, instance field initializers, and constructor body

When an object is allocated, instance fields start with **default values** such as `0`, `false`, `null`. Then constructors and instance initializers can overwrite them. For a subclass, the superclass constructor runs before the subclass's instance initialization part according to Java rules.

Example:

```java
class Example {
    int count = 3;

    {
        count += 2;
    }

    Example() {
        count += 4;
    }
}
```

If we create `new Example()`, the final `count` field is **9**: default `0`, initializer sets `3`, instance initializer block adds `2`, constructor body adds `4`. This is a valid illustrative class; there is no need to declare `main` if it is only used to observe structure when compiled.

### 3.5. `<init>` is not inherited or called like a regular method

A subclass does not “inherit” the constructors of its superclass. A `super(...)` call initializes the superclass portion through a chosen constructor, but that is **not overriding or dynamic dispatch of a constructor**. You cannot call a constructor like `obj.Point()` after the object has already been created.

Reflection has the `Constructor.newInstance(...)` API to create an object via the appropriate constructor; it does not turn `<init>` into a public Java method named `<init>`. Using reflection must still obey access and class initialization rules.

## 4. `<clinit>`: class/interface initialization method

### 4.1. Compiler synthesizes static initializers

Example:

```java
class Settings {
    static int port = readDefaultPort();

    static {
        port += 10;
    }

    static int readDefaultPort() {
        return 8000;
    }
}
```

In the ClassFile, the compiler may generate:

```text
Settings.<clinit>:()V
  // port = readDefaultPort();
  // port += 10;
  // return
```

This is **pseudocode** of the operations performed by `<clinit>`, not syntax for creating a method in Java source. If class initialization succeeds, `Settings.port` becomes **8010**. Normal static field initializer and static block operations are executed **in source appearance order**, with special rules for constant variables and forward references.

If a class **has no static work requiring initialization code**, the compiler **is not required** to generate `<clinit>`. For example, a class with only regular methods or `static final int MAX = 10;` may not need a separate `<clinit>` body; this kind of constant can be represented via `ConstantValue`.

### 4.2. `<clinit>` has a fixed descriptor

Unlike constructor overloading:

```text
<init>:()V           // no-arg constructor
<init>:(I)V          // constructor taking int
<init>:(Ljava/lang/String;)V
<clinit>:()V         // class/interface initialization, no parameters
```

The methods in the listing use **special names and method descriptors**. `<clinit>` takes no parameters and is not declared as a Java source method. In modern class files, it is `static` according to ClassFile version rules; you cannot choose to call it with `someClass.<clinit>()` or by putting the name `<clinit>` into a Java statement.

### 4.3. When does the JVM trigger class initialization?

According to the JVM/JLS model, a class is usually initialized immediately before certain **active uses**, for example:

- Creating an instance of the class with `new` (if not yet initialized).
- Calling a static method declared in the class, e.g., `Service.run()`.
- Reading a static field that does not fall under the constant variable case allowed to be accessed without initialization.
- Writing a static field according to static access rules.
- Certain reflection/MethodHandle operations or specific runtime requirements.

Example:

```java
class Counter {
    static int value = init();

    static int init() {
        System.out.println("Counter static init");
        return 7;
    }

    static void show() {
        System.out.println(value);
    }
}
```

If another class calls `Counter.show()` for the first time, the JVM must ensure `Counter` is initialized according to the rules before the body of `show()` executes. However, merely **loading** the class or obtaining a class literal like `Counter.class` usually **does not** by itself trigger initialization.

### 4.4. A static initializer is not necessarily run even when using a class

A `static final` **compile-time constant** is a case that must be distinguished:

```java
class Constants {
    static final int LIMIT = 100;
    static int runtimeValue = compute();

    static int compute() {
        System.out.println("Constants initialized");
        return 2;
    }
}
```

When the Java compiler can replace `Constants.LIMIT` with the literal `100` according to constant variable rules, reading `Constants.LIMIT` **does not by itself require initializing `Constants`**. However, accessing `Constants.runtimeValue` normally triggers initialization.

Do not generalize this to “every `static final` does not trigger `<clinit>`”: `static final Object VALUE = new Object();` is not a compile-time constant variable, so the object creation work belongs to class initialization. Distinguish **compile-time constants** from **`static final` variables that require evaluating an expression at runtime**.

### 4.5. Are interfaces and classes different?

An interface can also require initialization, especially when it has static fields with initializers that produce side effects under valid semantics. The compiler can generate `<clinit>` for an interface if needed.

Do not infer that “when a class implements an interface, all superinterfaces are initialized just like the entire superclass chain.” **The initialization rules for superclasses and superinterfaces with default methods** differ from assuming the entire interface graph is initialized at once. In practice, read *JLS §12.4* and *JVMS §5.5* when predicting complex ordering.

## 5. Order and uniqueness of class initialization

### 5.1. Once per class definition, not once across the entire application

Within a JVM, a class's identity depends on its **binary name** and **defining class loader**. Two different class loaders can define two classes with the same binary name that are **two distinct runtime classes**, with their own static state and their own initialization process.

Therefore, the statement “`<clinit>` only runs once” should be stated accurately: **each runtime class/interface definition that is initialized successfully performs its initialization process only once**. If an independent definition is loaded through another loader, that is a separate case. There is no guarantee of running only once across all Java processes in every system.

### 5.2. Superclass initialized before subclass

When initialization of a subclass is requested, the JVM ensures the relevant superclass is initialized first according to the applicable rules. Thus:

```text
First active use of Child
  → Parent class initialization (<clinit> if any)
  → Child class initialization (<clinit> if any)
  → object constructor chain:
      Parent.<init> ...
      Child.<init> ...
```

**Class initialization** is static-level work, whereas the **constructor chain** is per-instance work. These two sequences are related because `new Child()` needs the class initialized before the object can be fully created/initialized, but they should not be merged into a single `<init>`.

### 5.3. Thread safety and error state

The JVM has a coordination mechanism for initializing a class so that concurrent threads do not simultaneously run the `<clinit>` body as two independent tasks on the same runtime class. Other threads may have to wait for the initialization result; the JVM has rules for the initializing, initialized, and **erroneous** states.

If `<clinit>` completes abruptly, using the class can fail with `ExceptionInInitializerError` (when an appropriate exception is wrapped) or the corresponding error; subsequent active uses typically receive `NoClassDefFoundError` for a class in the failed-initialization state. The case of an `Error` has its own rules; not every error is always wrapped in the same way.

Catching the error and “calling `<clinit>` again” by name **does not exist** in Java semantics. The fix is usually to resolve the cause of the initialization failure, change the design structure, or in an appropriate application environment load a new definition through a new loader/process; do not attempt to call `<clinit>` directly.

## 6. Runnable Java 17+ example: order of `<clinit>`, `<init>`, and constructor chaining

Create the file **`InitLifecycleDemo.java`**:

```java
public class InitLifecycleDemo {
    static int log(String text) {
        System.out.println(text);
        return 1;
    }

    static class Parent {
        static int staticValue = log("Parent static initializer");

        int parentValue = log("Parent instance initializer");

        Parent() {
            System.out.println("Parent constructor");
        }
    }

    static class Child extends Parent {
        static int staticValue = log("Child static field initializer");

        static {
            System.out.println("Child static block");
        }

        int childValue = log("Child instance initializer");

        Child() {
            System.out.println("Child constructor");
        }

        Child(int number) {
            this();
            System.out.println("Child constructor(int): " + number);
        }
    }

    public static void main(String[] args) {
        System.out.println("start");

        System.out.println("first new");
        Child first = new Child(7);

        System.out.println("second new");
        Child second = new Child();

        System.out.println("different objects: " + (first != second));
    }
}
```

From the directory containing the source, using JDK 17 or later:

```bash
javac -encoding UTF-8 InitLifecycleDemo.java
java InitLifecycleDemo
```

**Exact standard output:**

```text
start
first new
Parent static initializer
Child static field initializer
Child static block
Parent instance initializer
Parent constructor
Child instance initializer
Child constructor
Child constructor(int): 7
second new
Parent instance initializer
Parent constructor
Child instance initializer
Child constructor
different objects: true
```

### Stage-by-stage explanation

**First object creation:**

1. `main` prints `start`, then `first new`.
2. The active use `new Child(7)` requires initialization of `Child`; `Parent` is initialized first → `Parent static initializer`.
3. `Child` is initialized → static field initializer prints `Child static field initializer`, static block prints `Child static block`. The two static members of **Child** execute in source order.
4. `Child(int)` calls `this()`, and `Child()` has an implicit `super()` call. The constructor flow reaches **Parent** first.
5. `Parent`'s instance field initializer prints `Parent instance initializer`, then the body of `Parent()` prints `Parent constructor`.
6. `Child`'s instance field initializer prints `Child instance initializer`, then the body of `Child()` prints `Child constructor`.
7. Returning to the body of `Child(int)` → prints `Child constructor(int): 7`.

**Second object creation:**

- `Parent` and `Child` are already successfully initialized, so the three static initializer lines are **not printed** again.
- The new object still executes the superclass/subclass instance initializers and constructor bodies as normal.
- `first != second` is `true` because `new` creates separate objects; `<clinit>` running once does not mean the program can only create one instance.

**Precision note:** `Parent static initializer` and `Child static field initializer` in the example are *log strings*, not bytecode instruction names. The instructions that perform the printing are placed by the compiler into `<clinit>` according to the source structure, while constructors/instance initializers are compiled into bytecode in the corresponding `<init>` methods.

## 7. Separate experiment: `static final`, `T.class`, and active use

To distinguish class loading/referencing from initialization, create the file **`ActiveUseDemo.java`**:

```java
public class ActiveUseDemo {
    static class Lazy {
        static final int LIMIT = 100;

        static int result = init();

        static int init() {
            System.out.println("Lazy initialized");
            return 25;
        }

        static void work() {
            System.out.println("Lazy.work()");
        }

        Lazy() {
            System.out.println("Lazy constructor");
        }
    }

    public static void main(String[] args) {
        System.out.println("begin");
        System.out.println("constant: " + Lazy.LIMIT);
        System.out.println("class literal: " + (Lazy.class != null));
        System.out.println("before active use");
        System.out.println("runtime field: " + Lazy.result);
        Lazy.work();
        new Lazy();
        System.out.println("end");
    }
}
```

Compile/run:

```bash
javac -encoding UTF-8 ActiveUseDemo.java
java ActiveUseDemo
```

**Standard output:**

```text
begin
constant: 100
class literal: true
before active use
Lazy initialized
runtime field: 25
Lazy.work()
Lazy constructor
end
```

Meaning:

- `Lazy.LIMIT` is a **compile-time constant variable**; the compiler can inline `100`, so this operation does not cause initialization of `Lazy`.
- `Lazy.class != null` uses a class literal; this operation is not an active use requiring `<clinit>`. It may cause the system to obtain the `Class` object of the type, but does **not** mean initializing static state.
- Reading **`Lazy.result`** triggers `Lazy` initialization, printing `Lazy initialized` once.
- Calling `Lazy.work()` and `new Lazy()` afterward does not re-initialize static fields. However, **`new Lazy()` still calls the constructor**, producing `Lazy constructor`.
- If the order is reversed so that `new Lazy()` happens first, class initialization will occur before the constructor body runs.

The program does not use reflection or custom class loaders, so the stdout order above can be verified consistently.

## 8. Reading bytecode with `javap`

The following commands use the `.class` output from the example in section 6:

```bash
javap -c -p InitLifecycleDemo
javap -c -p 'InitLifecycleDemo$Parent'
javap -c -p 'InitLifecycleDemo$Child'
javap -v -p 'InitLifecycleDemo$Child'
```

In Bash/PowerShell, single quotes protect the `$` character in the nested class's binary name. With Windows `cmd.exe`, use double quotes around `InitLifecycleDemo$Child`.

### 8.1. Finding the `<init>` constructors

In the output of `javap -c -p 'InitLifecycleDemo$Child'`, constructors may be displayed using the **class name**:

```text
InitLifecycleDemo$Child();
InitLifecycleDemo$Child(int);
```

Do not infer that in the class file the constructors are actually named `Child`; **the constant pool and method references** will show the special name `<init>`. A typical snippet in the no-arg constructor:

```text
aload_0
invokespecial InitLifecycleDemo$Parent."<init>":()V
aload_0
invokestatic InitLifecycleDemo.log:(Ljava/lang/String;)I
putfield ... childValue:I
...
return
```

This is a simplified pattern for explanation, **not a `javap` listing that needs to match every offset**. The `Child(int)` constructor will call `Child.<init>:()V` via `invokespecial` before printing the line that receives the parameter.

### 8.2. Finding `<clinit>`

In the output of the **Child** class, `javap` typically presents the class initialization method with the label:

```text
static {};
```

The body contains bytecode for:

```java
static int staticValue = log("Child static field initializer");
static {
    System.out.println("Child static block");
}
```

That is the `<clinit>:()V` body generated by the compiler. The instructions typically involve calling `log`, `putstatic`, printing to the console, and then `return`.

In `javap -v -p`, observe the **method descriptor `()V`** and the constant pool entries or the names `<clinit>`, `<init>` where they appear. `javap` may display constructors using the class name and the static initializer as `static {}`, so do not look for a line printed literally as `void <clinit>()` in the Java-like signatures section.

### 8.3. Comparing instance initialization code with static code

| Java source | Typical bytecode information |
| --- | --- |
| `static int staticValue = log(...);` | In `<clinit>`: call `log`, then `putstatic` |
| `static { System.out.println(...); }` | In `<clinit>`: instructions from the static block |
| `int childValue = log(...);` | In constructor `<init>`, after the appropriate superclass constructor call |
| `Child()` | An `<init>:()V` |
| `Child(int)` | An `<init>:(I)V` calling `this()` |
| `new Child(7)` | `new`, push arguments, `invokespecial <init>` at the call site |
| `Child.staticValue` | `getstatic`, which may trigger class initialization if the class is not yet initialized |

Instruction details may vary when changing compilers, but the boundary between **static state initialized once** and **instance state initialized per object** still follows Java semantics.

## 9. Confusing questions when debugging programs

### 9.1. “There is a constructor, so why don’t I see the static log line yet?”

If you only write the class without actively using it, **class initialization may not have happened yet**. Actions such as compiling, inspecting the class file with `javap`, getting the class name from metadata, or using a class literal do not mean the static initializer has run. Conversely, the first time a static method is actually called or an instance is created can trigger initialization.

### 9.2. “Which constructor runs when `this(...)` appears?”

The constructor called via `this(...)` runs on the **same object**. This does not create a second object. The process proceeds to a constructor that has a `super(...)` call, and then returns sequentially through the constructors in the chain. The class's instance initialization blocks do not run repeatedly once for each same-class constructor in the chain.

### 9.3. “Do static fields have default values before `<clinit>`?”

Yes. The JVM performs **preparation** and applies the rules for static fields/constant values. When `<clinit>` runs, code can read those default values or pre-initialized values according to the rules, and then write further values. Do not equate a field initially having `0` with `<clinit>` having already run.

### 9.4. “Does calling `super()` initialize the superclass’s static fields?”

Superclass initialization is ensured by the JVM according to the appropriate class initialization process when a subclass needs to be initialized. However, **`super()` is a constructor invocation**, used to initialize the superclass portion of the instance. These are two different concepts; do not use the name `super()` in place of `<clinit>`.

### 9.5. “Is `<clinit>` executed again by the JVM when creating a second object?”

No, if the runtime class has already been initialized successfully. Each new object still goes through its own constructor process. If another class definition is loaded through a different loader or a new JVM, that is a different runtime class.

### 9.6. “Why does a failing static initializer make the entire class hard to use?”

An error occurring during class initialization can put the runtime class into an **erroneous** state. Subsequent active uses do not simply retry the initializer like a normal function call. Static initializer design should avoid unstable, hard-to-recover work such as network access, uncontrolled configuration reading, and operations depending on resources that are not ready yet.

### 9.7. “Is `<clinit>` present in every class that contains `static`?”

No. A class with `static` methods or compile-time constants does not necessarily need `<clinit>`; the compiler only generates it when class/interface initialization work must be executed as bytecode. Conversely, a class without an explicit static block can **still** have `<clinit>` because a static field initializer has an expression that needs to be evaluated.

### 9.8. “Can `<init>` return a different object instead of `this`?”

Java constructors have no return value and `<init>` has a descriptor returning `V`. A factory method can return an object of its choosing, but that is a **normal method**, not an `<init>` constructor. The result of a `new` expression is a reference to the newly created/successfully initialized object.

## 10. Practice exercises

### Exercise 1 — Count the number of times

Consider:

```java
class Service {
    static {
        System.out.println("S");
    }

    {
        System.out.println("I");
    }

    Service() {
        System.out.println("C");
    }
}
```

If another `main` sequentially calls `new Service(); new Service();` and there was no prior active use, the output includes:

```text
S
I
C
I
C
```

Explanation: static initialization only happens the first time; the instance initializer and constructor body run for **each object**.

### Exercise 2 — Constructor chaining

Consider:

```java
class Sample {
    {
        System.out.println("I");
    }

    Sample() {
        this(1);
        System.out.println("A");
    }

    Sample(int n) {
        System.out.println("B");
    }
}
```

If `new Sample()`, the output is:

```text
I
B
A
```

The instance initializer **only runs once** on the object. `Sample()` delegates to `Sample(int)`, initializes the instance and runs the body of the constructor taking `int`, and only then returns to print `A`.

### Exercise 3 — Compile-time constants

Consider:

```java
class Marks {
    static final int LIMIT = 50;
    static {
        System.out.println("initialized");
    }
}
```

If `main` only prints `Marks.LIMIT` from a class compiled together with the code, the JVM may simply execute the code that inlined `50`; it is not required to print `initialized`. If a definite active use is added, such as calling an executable static method of `Marks` or creating `new Marks()`, initialization will occur before the corresponding operation.

### Exercise 4 — Predicting `javap`

From `InitLifecycleDemo.java`:

1. What descriptor does `Child()` have? **`()V`**.
2. What descriptor does `Child(int)` have? **`(I)V`**.
3. Which method contains `Child static block`? **`<clinit>` of Child**.
4. Which process does `Child instance initializer` belong to? **Constructor `<init>`**, not `<clinit>`.
5. Is the line `Child constructor(int): 7` printed before or after `Child constructor`? **After**, because `Child(int)` calls `this()`.
6. How many `Child` objects are created in `main`? **Two**, even though the static initializer only runs once.

### Self-check questions

**1.** Do `<init>` and `<clinit>` share the same purpose of “setting default values for all fields”?  
**No.** Default values have their own process during preparation/object allocation; `<init>` executes constructor logic on an instance, and `<clinit>` executes static initialization logic if present.

**2.** Can `<clinit>` be overloaded into `<clinit>(int)` in a class file?  
**No.** The class/interface initialization method has a prescribed descriptor `()V`; it is not a user-overloadable API.

**3.** When creating 100 instances of the same already-initialized class, how many times do `<init>` and `<clinit>` run?  
Each instance is initialized through the appropriate constructor chain; **`<clinit>` does not run again** because the class has already been initialized successfully. The actual number of `<init>` calls may be greater than 100 because each object has a superclass/subclass constructor chain.

**4.** Why does `javap` sometimes only print `static {}` without showing the exact string `<clinit>` in the method header line?  
`javap` displays a readable representation close to Java syntax; the special method name `<clinit>` is represented as a static initializer.

**5.** Is `<init>` called with `invokevirtual` like an overridden method?  
**No.** Constructors are called using the `invokespecial` mechanism; they are not regular methods to be overridden.

**6.** When a class has `static final String CODE = "OK";`, does reading `CODE` definitely trigger the static block?  
**No.** If `CODE` is a compile-time constant variable and is inlined according to Java rules, merely reading it is not an active use that initializes the class.

**7.** Is class loading synonymous with class initialization?  
**No.** A class can be loaded/linked without running `<clinit>` yet; initialization is triggered at the appropriate time according to JVM rules.

**8.** If a static initializer fails, does calling `new` again guarantee the initializer will be run again?  
**No.** The class may be in an erroneous state within the current class loader, so active uses continue to fail.

## 11. Key takeaways and official references

- **`<init>`**: the JVM name for a constructor; can be overloaded by descriptor; participates in instance initialization, typically seen via `invokespecial`.
- **`<clinit>`**: compiler-synthesized method for class/interface initialization work; descriptor `()V`; the JVM manages when it executes.
- **Static initialization is not instance initialization**: `<clinit>` handles static state, while the constructor chain/`<init>` handles per-object state.
- **Loading is not initialization**: examine the sequence of loading, linking, preparation, and initialization instead of assuming everything happens immediately after reading the class file.
- **Verify with `javap -c -p` and `javap -v`**: predict program output, then read the relevant methods, descriptors, and instructions.

Official references: *The Java Virtual Machine Specification*, Chapter 2 (*instance initialization methods* and *class/interface initialization methods*), Chapter 4 (*ClassFile*), Section 5.5 (*Initialization*), and Section 6.5 (`new`, `invokespecial`), Java 17 edition: https://docs.oracle.com/javase/specs/jvms/se17/html/ . Language-level initializer and constructor ordering rules are explained in the *Java Language Specification*, sections **§8.8** and **§12.4**.

**Conclusion:** Ask the question at the right level: “Has the JVM **initialized the class** yet?” to understand `<clinit>`; and “Which **object is the JVM initializing, and through which constructor chain**?” to understand `<init>`. When these two questions are clearly separated, static/instance log ordering, initialization errors, and `javap` output become consistent and easier to predict.
