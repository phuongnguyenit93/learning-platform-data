# Early Resolution, Lazy Resolution, and When Linkage Errors Appear

## 1. Goal: When Is the JVM Allowed to Resolve References?

When Java source code calls `lib.Library.version()`, the caller's class file does not usually contain a fixed native address pointing directly to that method's code. Instead, bytecodes such as `invokestatic`, `getfield`, `new`, `checkcast`, etc. may use **symbolic references** in the run-time constant pool. The JVM must **resolve** these references into the appropriate runtime class, field, method, or value before performing the operation that needs them.

**The main question of this lesson** is not "Does the JVM resolve references?" but rather:

- Can the JVM perform **early resolution (eager resolution)** during linking, before the program actually calls a method?
- Can the JVM perform **late resolution (lazy resolution)** right when the related bytecode is used?
- If a reference is invalid—for example, a method is removed from a library after the client has been compiled—**at what point is the error allowed to appear**?
- Why does seeing the application print a few lines or `main` run successfully **not prove** that every symbolic reference in the application has been successfully resolved?

According to **JVMS `5.4** and **`5.4.3**, the JVM is allowed to choose certain points at which to perform resolution, but **it must not arbitrarily throw a linkage error at a point completely unrelated to a program action that might require linkage**. There are stricter rules for **dynamically-computed constants** and **dynamically-computed call sites**, which will be discussed separately.

### A High-Level Map

~~~text
Java source
   |
   | javac
   v
ClassFile
   |    constant pool: Methodref, Fieldref, Class, NameAndType, ...
   |    Code: invokestatic #N, getstatic #M, new #K ...
   v
JVM class loading
   v
Linking
   +-- Verification (validity checking)
   +-- Preparation (preparing static storage/default values)
   +-- Resolution (resolving symbolic refs) <-- flexible in timing*
   v
Initialization (static field initializers / <clinit> when needed)
   v
Execution of methods / instructions
      \-- may continue to resolve unused refs*

* Subject to limits and special cases according to the JVMS.
* Errors detected during linkage must be thrown at a point in the program where an action
  may directly or indirectly require the corresponding linkage.
~~~

Do not read the diagram as a strict order of "must resolve everything before initialization." **Loading completes, and verification and preparation complete before initialization**, but some symbolic references may only be resolved **after the class has been initialized and when the related method runs**.

## 2. Distinguishing Loading, Linking, Resolution, and Initialization

| Concept | What the VM does | Not synonymous with |
| --- | --- | --- |
| **Loading** | Finds/creates a runtime class or interface from its binary definition and loader | Running `static {}` |
| **Verification** | Checks binary structure, bytecode constraints, and type-safety rules | Executing every branch of Java code |
| **Preparation** | Creates storage and default values for static fields; handles appropriate constant rules | Executing every `static int x = f()` expression |
| **Resolution** | Converts a **symbolic reference** into a concrete runtime entity/value and performs related checks | Invoking the resolved method body |
| **Initialization** | Executes initialization logic of the class/interface when required | Resolving all constant-pool entries |
| **Execution** | Executes bytecode, creates objects, calls methods, reads fields, etc. | Merely reading `.class` |

At the class-file level, references may look like:

~~~text
#11 = Class        #12                // lib/Library
#12 = Utf8         lib/Library
#13 = NameAndType  #14:#15            // version:()Ljava/lang/String;
#16 = Methodref    #11.#13            // lib/Library.version:()Ljava/lang/String;

Code:
   ... invokestatic #16              // Method lib/Library.version:()Ljava/lang/String;
~~~

This is an **illustrative constant-pool diagram**: the indices `#11`, `#16` may differ in an actual class generated by the compiler. A **Methodref** contains the owner, method name, and descriptor, **not a machine address fixed at source compilation time**. Resolution needs to determine whether an appropriate method exists at runtime and whether the access requirements and invocation kind are valid.

A method that has a symbolic reference to `lib.Library.version()` **does not need to actually invoke that method** just because the VM has recognized the class file containing the call. Conversely, when executing the invoke bytecode, resolution requirements and instruction-specific linking checks must be satisfied.

## 3. What Is Early/Eager Resolution?

**Eager resolution** means the JVM chooses to **resolve in advance** one or more symbolic references of a class being linked, such as during verification, instead of waiting for the first time a bytecode instruction directly uses that reference.

For example: a class has a `run()` method containing a symbolic reference to `A.m:()V`, but the branch calling `A.m()` may not have been taken by the program yet. An implementation may resolve the related reference early within the limits of the specification.

Potential benefits:

- Detecting some linkage issues before the code path actually runs.
- Preparing/caching resolution results, leaving less work to do on subsequent uses.
- Fitting a specific implementation/verifier strategy or runtime optimization.

Limitations:

- **Cannot arbitrarily throw an early-detected error at an unrelated place.** The JVMS constrains the **throw** point for linkage errors.
- Not every reference is allowed to be eager in the same way; **`CONSTANT_Dynamic` and `invokedynamic`** have their own restrictions.
- "Eager" here refers to **when symbolic references are resolved**, not **eager loading of every class on the classpath**, running every `static initializer`, or calling methods early.
- One should not label "HotSpot is always eager" or "every JVM is always eager" based solely on a short log; a JVM may use different strategies depending on the reference type and context.

## 4. What Is Late/Lazy Resolution?

**Lazy resolution** means the VM leaves a symbolic reference in an unresolved state until a specific action actually needs it, such as when an `invokestatic`, `getstatic`, `new`, or `checkcast` bytecode using that reference is executed.

~~~text
Caller's constant pool:
  #A = Methodref lib/Library.version:()Ljava/lang/String;

Caller's code:
  if (someCondition) {
      invokestatic #A
  }

If the branch is not entered:
  Some JVMs may not have resolved #A yet (lazy).
  Some JVMs may have attempted to resolve #A early (eager),
  but must obey the rule of throwing the error at the relevant point of use.

If the branch is entered:
  The invoke instruction must have successful resolution and valid checks,
  or the call will fail according to linkage rules.
~~~

**Do not equate "lazy resolution" with "no resolution needed."** Bytecodes that use a symbolic reference cannot skip type, access, and correctness checks. Some actual behaviors may be optimized and cached by the VM, but the observable result must preserve the contract.

### Which References Typically Involve Resolution?

JVMS `5.4.3 lists instructions such as:

- **Class/interface**: `new`, `anewarray`, `checkcast`, `instanceof`, `multianewarray`…
- **Field**: `getfield`, `putfield`, `getstatic`, `putstatic`.
- **Methods**: `invokevirtual`, `invokespecial`, `invokestatic`, `invokeinterface`.
- **Constants and dynamic linkage**: `ldc`, `ldc_w`, `ldc2_w`, and `invokedynamic` in appropriate cases.

In addition, a symbolic reference in the constant pool used by a method handle, method type, or bootstrap machinery has its own resolution rules.

It is necessary to distinguish **resolution of a symbolic method reference** from **dynamic method dispatch**: after a method reference is resolved, `invokevirtual` still needs to find the appropriate method body based on the receiver's runtime class and lookup/selection rules. Meanwhile, `invokedynamic` creates and links a call site via its own bootstrap mechanism. These three operations are not the same thing.

## 5. Key Rule: When Are Linkage Errors Thrown?

JVMS `5.4 states the conditions an implementation must uphold when choosing the timing of linking activities:

1. A class/interface must be **completely loaded** before it is linked.
2. A class/interface must be **completely verified and prepared** before it is initialized.
3. **Errors detected during linkage** must be thrown at a **point in the program where an action is taken** that may directly or indirectly require linkage to the class/interface involved in the error.
4. For certain dynamic constant/call-site references, the specification restricts **when resolution is allowed to begin**.

For resolution, JVMS `5.4.3 further states: regardless of whether the JVM resolves references early or late under any strategy, a resolution error must appear **at a point in the program that may directly or indirectly use the failing symbolic reference**.

### "Early Detection" Does Not Mean "Throw Anytime"

Suppose the bytecode has a Methodref that does not exist in the runtime version of the library:

- The VM may **know the reference is invalid** before the application code line actually calls that method.
- However, the VM must preserve the condition of throwing the error when the program performs an action **that is related and may require** resolution.
- One must not conclude that "if eager, then as soon as the JVM process starts it must throw `NoSuchMethodError` for every unused method."
- Nor must one conclude that "if lazy, the error always appears at the exact Java line where the call is written." The JVM has loading/verification/inlining, indirect linking requirements, and startup activities; the observed location can be more complex than an imagined source line.

Therefore, the phrasing to use is **"a point where a program action may directly or indirectly require linkage"**, not "guaranteed that an error can only be reported when the specific opcode is executed" for every form of linkage.

### Contrasting Examples

| Wrong conclusion | Understanding according to the JVMS |
| --- | --- |
| "Eager resolution forces throwing errors at class load." | The VM may detect early but must defer the **throw** point according to the rules. |
| "Lazy resolution means there are no errors during linking." | Errors can still appear when the reference is used. |
| "Since `main` ran, all constant-pool method/field references are valid." | Some refs may not have been used yet; errors can appear on a later execution path. |
| "A Methodref error only occurs when the target method body starts running." | Resolution/instruction checks can fail **before** the target method is invoked. |
| "The stack trace line number is the only time the JVM actually resolves." | A stack trace helps locate error exposure; it does not necessarily reflect when the VM internally detected/resolved it. |

## 6. Runnable Java 17+ Example: Observing Used and Unused Reference Paths

Create the file **`ResolutionBasics.java`**:

~~~java
public class ResolutionBasics {
    static class Helper {
        static int twice(int n) {
            return n * 2;
        }
    }

    static int execute(boolean useHelper) {
        if (!useHelper) {
            return -1;
        }
        return Helper.twice(21);
    }

    public static void main(String[] args) {
        System.out.println("skip=" + execute(false));
        System.out.println("call=" + execute(true));
    }
}
~~~

Commands:

~~~bash
javac -g ResolutionBasics.java
java ResolutionBasics
javap -c -v -p ResolutionBasics
~~~

**Stdout printed by the Java program before the `javap` command runs:**

~~~text
skip=-1
call=42
~~~

Why? `execute(false)` returns `-1` without going through the branch that calls `Helper.twice`; `execute(true)` calls `Helper.twice(21)` and receives 42. In `javap -c -v -p`, look for the Methodref or link to `ResolutionBasics$Helper.twice:(I)I` and the `invokestatic` opcode inside the `execute` method.

**Limitation of the example:** this shows **control-flow behavior of source and bytecode**, not a sufficient experiment to know **when** the JVM resolved this Methodref. The output does not contain a "resolution timestamp" and does not force the JVM to be lazy rather than eager. The accurate conclusion is that the program **only invokes the body of `twice` on the true branch**; internal resolution still follows the JVMS.

## 7. Core Example: Changing the Binary API After the Client Is Compiled

This is an intuitive way to demonstrate that a client class can contain a symbolic reference that is valid **at compile time** but can no longer be resolved **against a different runtime library**. This lesson uses Java 17+ and standard JDK tools; create three files with paths matching this structure:

~~~text
resolution-lab/
  src/
    v1/
      lib/
        Library.java
    v2/
      lib/
        Library.java
    client/
      LinkageDemo.java
  out/                 (output directory, initially empty)
~~~

### 7.1. Library Version 1: Has the `version()` Method

File **`src/v1/lib/Library.java`**:

~~~java
package lib;

public class Library {
    public static String version() {
        return "v1";
    }
}
~~~

File **`src/client/LinkageDemo.java`**:

~~~java
public class LinkageDemo {
    public static void main(String[] args) {
        System.out.println("start");

        if (args.length == 0) {
            System.out.println("skipped");
            return;
        }

        try {
            System.out.println("value=" + lib.Library.version());
        } catch (NoSuchMethodError error) {
            System.out.println("linkage=NoSuchMethodError");
        }
    }
}
~~~

Compile **v1 and client together** (from inside the `resolution-lab` directory):

~~~bash
mkdir -p out
javac -g -d out src/v1/lib/Library.java src/client/LinkageDemo.java

java -cp out LinkageDemo
java -cp out LinkageDemo call
~~~

**Stdout of the first run, with no arguments:**

~~~text
start
skipped
~~~

**Stdout of the second run:**

~~~text
start
value=v1
~~~

`LinkageDemo` was compiled against `lib.Library.version:()Ljava/lang/String;`. When v1 is present on the classpath, method resolution succeeds and the invocation returns the string `v1`.

**Windows PowerShell:** you can replace `mkdir -p out` with `New-Item -ItemType Directory -Force out`; the remaining three `javac`/`java` commands have the same meaning. Do not keep two versions of `Library` simultaneously in one output directory when comparing; the next step **intentionally replaces** `Library.class`.

### 7.2. Library Version 2: Removing `version()` from the API

File **`src/v2/lib/Library.java`**:

~~~java
package lib;

public class Library {
    public static String release() {
        return "v2";
    }
}
~~~

Now **compile only v2 into the same output directory**, without recompiling the client:

~~~bash
javac -g -d out src/v2/lib/Library.java

java -cp out LinkageDemo
java -cp out LinkageDemo call
~~~

`out/lib/Library.class` is overwritten with the v2 version, but `out/LinkageDemo.class` still contains the Methodref **`lib/Library.version:()Ljava/lang/String;`** from when it was compiled with v1.

**Stdout in a typical JDK 17+ environment (with the exact files and classpath as described), run without arguments:**

~~~text
start
skipped
~~~

**Stdout when entering the branch that calls the method:**

~~~text
start
linkage=NoSuchMethodError
~~~

Explanation:

1. **`start`** is printed by client code that does not require calling `Library`.
2. The no-argument branch **does not use `Library.version()`**; there is no call to this method.
3. The branch with an argument attempts to invoke the v1 Methodref. At runtime, version 2 of class `lib.Library` **does not declare** a `version()` method with the matching descriptor. Method resolution fails with **`NoSuchMethodError`**.
4. `catch (NoSuchMethodError error)` catches the error and intentionally prints a fixed line, so the example avoids depending on stack trace messages that vary across JDKs.

**Important rule:** the example is only meant to illustrate a **code path that uses a failing reference** and the typical practical outcome; it does not prove that HotSpot performs "all Methodref resolution lazily." The JVMS allows choosing eager/lazy for eligible references, provided the error is thrown at a point of action that may require resolution. Do not infer from `start` being printed that the JVM "never saw" the constant-pool reference.

### 7.3. Why Can Recompiling the Client Change the Kind of Error?

If you run:

~~~bash
javac -g -cp out -d out src/client/LinkageDemo.java
~~~

when `out` only contains Library v2 (without `version()`), the Java compiler will recognize that `version()` cannot be found in `lib.Library` and report a **compile-time error**. This is **not** a `NoSuchMethodError` at runtime.

Two different cases:

- **Compile-time error:** the compiler has the new API information and detects that the client source calls a non-existent method.
- **Runtime linkage error:** the client **was compiled** against the old API, while the runtime class file of the library no longer satisfies the reference recorded in the client binary.

In production, this type of error is often caused by a dependency/JAR version mismatch or a deployment classpath with inconsistent library versions.

### 7.4. Inspecting with `javap` to Verify

~~~bash
javap -v -p -classpath out LinkageDemo
javap -c -p -classpath out LinkageDemo
javap -p -classpath out lib.Library
~~~

What to look for:

- `LinkageDemo.class` still has a Methodref of the form `lib/Library.version:()Ljava/lang/String;`.
- In the branch that uses the library, the client bytecode contains an `invokestatic` referencing that Methodref.
- `lib.Library` in v2 only declares `release()` and **does not have `version()`**.
- Constant-pool indices `#N`, BCI offsets, and line numbers in `javap` depend on the compiler; **read the symbolic content**, rather than memorizing numbers like `#17`.

## 8. Why Should You Not Measure Resolution Timing Using Stdout Alone?

Every `System.out.println` line only proves that an **observable Java action** took place. It does not record all internal VM events. To study early vs. late resolution, one must distinguish:

| Question | Can it be deduced from the example's stdout? |
| --- | --- |
| Was the branch containing `Library.version()` executed? | Yes, from the output and the code |
| With v2, is that method call still valid? | No; `NoSuchMethodError` when the branch uses the reference |
| Did the JVM scan the constant pool at load time? | Cannot be concluded |
| Was the symbolic reference eagerly resolved and the error held to be thrown at use? | Cannot be concluded from stdout alone |
| Does the JVM cache resolution results? | This is a mechanism governed by JVMS rules; not measured by simple stdout |
| Could a different configuration/module/loader fail at a different action? | Possibly; the runtime context must be investigated |

There is no need to build a microbenchmark that "counts lines before the error" and claim the specification requires the VM to be lazy. The point to grasp is **the flexibility in processing timing and the constraint on error manifestation timing**.

## 9. Resolution/Linkage Error Types Worth Recognizing

| Error / exception | Classification | Typical scenario |
| --- | --- | --- |
| **`NoSuchMethodError`** | `IncompatibleClassChangeError` → `LinkageError` | Compiled client calls a method, but the runtime class lacks the matching method |
| **`NoSuchFieldError`** | `IncompatibleClassChangeError` → `LinkageError` | The referenced field name/descriptor cannot be found |
| **`IllegalAccessError`** | `IncompatibleClassChangeError` → `LinkageError` | Access check fails during linking/execution |
| **`IncompatibleClassChangeError`** | `LinkageError` | Runtime class/interface/member shape does not match bytecode expectations, including static/instance mismatch |
| **`AbstractMethodError`** | `IncompatibleClassChangeError` → `LinkageError` | A method is invoked, but no suitable implementation exists at the point of selection/invocation per the rules |
| **`NoClassDefFoundError`** | `LinkageError` | The VM cannot find/define a required class at runtime, or the class has been marked as initialization-erroneous |
| **`VerifyError`** | `LinkageError` | Bytecode violates verifier requirements |
| **`ClassFormatError`** | `LinkageError` | Binary class file has an invalid format |
| **`BootstrapMethodError`** | `LinkageError` | Error related to bootstrapping dynamic constants/`invokedynamic` |
| **`ExceptionInInitializerError`** | `LinkageError` | A static initializer fails during **initialization**, not a normal method resolution error |

Also worth knowing:

- **`ClassNotFoundException`** is a **checked exception** from certain explicit class-loading APIs such as `Class.forName`/`ClassLoader.loadClass`, **not** a subclass of `LinkageError`.
- **`ClassCastException`** is a runtime type-check failure, which may involve two class loaders defining the same name, but **does not by itself prove** a loader constraint violation.
- **`OutOfMemoryError`** during linking/allocation is a separate possibility, not by default a "missing method in the constant pool."

### Method Errors vs. Class Initialization

If the method **does exist** and resolution succeeds, but when the JVM needs to initialize the owner class a `static { ... }` block throws an exception, the caller may see **`ExceptionInInitializerError`**. This is an **initialization-phase** error, different from `NoSuchMethodError` caused by resolution failing to find the method.

Do not lump "every error appearing when calling a method" into "resolution failure." An invocation transaction can involve resolution, access checks, class initialization, dynamic method selection, and body execution; errors can come from different layers.

## 10. Sticky Resolution Failures: For the Same Reference, Is the Result Retried?

According to **JVMS `5.4.3**, for the ordinary symbolic references described in that section:

- If **resolution succeeds**, subsequent resolutions of **the same symbolic reference** succeed with the recorded result; re-searching everything from scratch is not required.
- If **resolution fails**, subsequent resolutions of **the same symbolic reference** continue to fail with **the same error** according to the specification rules.
- Do not assume an application can "fix the classpath" or change access configuration and have the JVM automatically re-link a failed symbolic reference in an existing class.

This is an important property of **binary linkage stability**. In many plugin/hot-reload systems, to switch to a new generation of types, one may have to use a **new class loader** or restart the appropriate runtime region rather than hoping the JVM will automatically refresh all linkages of already-loaded classes.

**Exception to state clearly:** `invokedynamic` has its own **instruction-site-specific** result rules, even when multiple instructions point to the same constant-pool entry. Dynamic constants and dynamic call sites also have their own bootstrap/caching semantics. Do not take the caching rule of one kind of symbolic reference and apply it mechanically to every kind of reference.

## 11. Specific Restrictions: Dynamic Constants and `invokedynamic`

Not every symbolic reference can be eagerly resolved arbitrarily. According to JVMS `5.4:

1. **Dynamically-computed constant** (`CONSTANT_Dynamic`): must not be resolved before an `ldc`/`ldc_w`/`ldc2_w` instruction that uses it is executed, **or** it is used as a static argument to a bootstrap method being invoked.
2. **Dynamically-computed call site** (`CONSTANT_InvokeDynamic`): must not be resolved before a bootstrap method that needs that call site as a static argument is invoked (per the specification's conditional wording). For the `invokedynamic` opcode itself, resolution of the call site occurs via the bootstrap mechanism when the instruction requires it.
3. A bootstrap method may involve `MethodHandle`, `MethodType`, static bootstrap arguments, and produce a `CallSite` or constant value.
4. Bootstrap errors may be wrapped in **`BootstrapMethodError`** under specified conditions; one should not assume that whenever `invokedynamic` is present, every error is a `NoSuchMethodError`.

**Java source example:** string concatenation on modern JDKs is commonly compiled by `javac` using `invokedynamic` and `StringConcatFactory`. Lambdas also commonly use the `invokedynamic` bootstrap mechanism, though how the compiler generates bytecode is a JDK-version-dependent detail.

~~~java
public class DynamicExample {
    public static void main(String[] args) {
        int count = 3;
        System.out.println("count=" + count);
    }
}
~~~

~~~bash
javac DynamicExample.java
java DynamicExample
javap -v -c -p DynamicExample
~~~

**Program stdout:**

~~~text
count=3
~~~

In a typical Java 17+ `javac` disassembly, you can see `invokedynamic` for string concatenation and the `BootstrapMethods` attribute. Do not use this output to infer that all constant-pool entries are eagerly resolved at startup; how bootstrap is invoked must follow specific call-site rules.

## 12. Resolution, Access Rights, and Class Loaders: Errors Can Appear Late

Symbolic references do not store only the method name. Resolution must consider the **exact runtime class identity**, loader, and access rights. A class `api.Message` defined by loader A is **not automatically identical** to a class of the same name defined by loader B.

When two classes belonging to different loaders interact through method/field signatures, **loading constraints** may bind interpretations of class/interface names to protect type safety. If a constraint fails, the JVM may throw **`LinkageError`** during linking. Do not confuse:

- **`NoSuchMethodError`**: the method name and descriptor expected by the client no longer exist in the runtime type being resolved.
- **`IllegalAccessError`**: the symbolic reference can identify the member, but the access check is invalid.
- **Loader constraint violation**: type names across loaders must agree, yet lead to incompatible runtime class identities.
- **`ClassCastException`**: the runtime object type is incompatible with a type cast, which can happen after both classes were validly loaded.

**Error timing depends on the resolution/linkage action and deployment.** From an error message, one should start investigating **the owner class, loader, name, descriptor, and binary version**, rather than guessing "definitely due to lazy resolution" merely because the error occurred after a few minutes of running.

### A Practical Plugin Scenario

The host is compiled with `api.Service.send(Message)` v1. A runtime plugin uses `api.Service` v2 with a changed descriptor, or accidentally defines its own `api.Message` using its own loader. The classes may load, but an invocation/interface-resolution path or override checks will fail.

How to analyze:

1. Read `Class.getClassLoader()` and `Class.getModule()` of the involved runtime classes.
2. Check `javap -s -p` to compare method descriptors between client and library.
3. Check JAR versions on the runtime classpath/module path and the delegation policy.
4. Use a shared loader for API types appearing in signatures, avoiding bundling duplicate APIs in a child-first plugin.
5. Reproduce in a reproducible test environment; do not "fix" it with forced casts.

## 13. Linkage Error Diagnosis Workflow: From Stack Trace to Bytecode

A workflow you can apply when seeing `NoSuchMethodError` or a late linking error:

### Step A — Collect Environment Details

~~~bash
java -version
javac -version
java -cp out LinkageDemo call
~~~

Record the Java **compile version**, Java **runtime version**, classpath/module path, class loader context, and the first stack trace/cause. A newer compiler and older runtime can cause `UnsupportedClassVersionError`; that is a **class-file version compatibility** issue, not Methodref resolution missing a method.

### Step B — Identify the Caller and Failing Reference

~~~bash
javap -s -p -classpath out LinkageDemo
javap -c -v -p -classpath out LinkageDemo
~~~

Find the `invokestatic #N` instruction or other opcode in the failing method, then look up `#N` in the constant pool. Read the **owner/name/descriptor**, for example:

~~~text
Methodref lib/Library.version:()Ljava/lang/String;
~~~

`#N` is a constant-pool index, **not** a heap address or line number. The bytecode index (BCI) is different from the constant-pool index. Stack trace line numbers are mapped via `LineNumberTable` if the class retains debug metadata.

### Step C — Inspect the Actual Loaded Binary

~~~bash
javap -s -p -classpath out lib.Library
javap -v -p -classpath out lib.Library
~~~

Compare the actual method list and descriptors. If the client expects `version:()Ljava/lang/String;` but v2 only has `release:()Ljava/lang/String;`, this is a **binary API mismatch** that explains `NoSuchMethodError`.

### Step D — Distinguish the Error Phase

| Question | How to determine |
| --- | --- |
| Unreadable or unsupported class file? | Check `ClassFormatError`, `UnsupportedClassVersionError` |
| Invalid bytecode? | Check `VerifyError` |
| Owner class not found? | Check `NoClassDefFoundError` and its cause; identify the loader |
| Field/method missing with exact descriptor? | Check `NoSuchFieldError` / `NoSuchMethodError` |
| Field/method wrong static/instance or owner shape? | Check `IncompatibleClassChangeError` and the instruction |
| Insufficient permissions? | Check `IllegalAccessError`, module exports/runtime package |
| Static initializer threw an exception? | Check `ExceptionInInitializerError` and `Caused by` |
| `invokedynamic`/constant bootstrap failed? | Check `BootstrapMethodError` and the cause chain |

### Step E — Prove the Usage Path

Record the input/code path that causes the method reference to be **used**, for example `LinkageDemo call` versus `LinkageDemo` with no arguments. When reporting, phrase it as:

> "The client binary contains a reference to the old method; the path calling that method can no longer be resolved against library v2, so the error appears when the program reaches the action requiring linkage."

**Do not assert on your own** that "the JVM definitely only started resolution at that instruction" if you have not measured the internal resolution behavior of the specific JVM.

### Additional Logging (HotSpot)

On modern HotSpot, you can try:

~~~bash
java -Xlog:class+load=info -cp out LinkageDemo call
java -Xlog:help
~~~

Logging helps observe class loading, but **class loaded ≠ symbolic reference resolved**. Do not infer that the load log line for `lib.Library` is the moment the `version` Methodref was resolved. Unified logging tags vary by JVM version; consult `-Xlog:help` and enable only the logging level needed.

## 14. Interview Questions and Misconceptions to Avoid

| Statement | True or false, and why? |
| --- | --- |
| "The JVM always resolves the entire constant pool before `main`." | **False.** The JVMS allows eager/lazy for eligible references; dynamic exceptions also have their own restrictions. |
| "The JVM must only resolve a method right when the `invoke` opcode is executed." | **Not generally.** It can be eager, but the error must be thrown at the relevant action point. |
| "Eager resolution can throw all missing-method errors as soon as the JVM starts." | **False.** It cannot arbitrarily throw at a point that cannot require the corresponding linkage/reference. |
| "Lazy resolution means skipping access checks." | **False.** When resolution/instruction checks are needed, access control must still be satisfied. |
| "Having initialized a class means all of its references succeeded." | **False.** Resolution may still continue later. |
| "`NoSuchMethodError` is the same as the compiler error `cannot find symbol`." | **False.** One is a runtime binary linkage error; the other is a compile-time source error. |
| "Replacing a JAR on the path without loading new classes updates already-resolved method references." | **Cannot be assumed.** Class identities and resolution results are retained by the VM according to the rules. |
| "A linkage error appearing late proves the JVM uses lazy resolution." | **False.** The JVM may detect early and defer the throw point per the JVMS. |
| "Every time a method is invoked, its reference must be resolved again from scratch." | **False.** Resolution outcomes have caching/stability rules. |
| "`invokedynamic` allows bootstrapping any call site arbitrarily at class loading." | **False.** There are restrictions on resolution/bootstrap timing. |
| "A class can load successfully yet break when using a library method." | **True,** as in the example of a client compiled against v1 and run with library v2. |
| "`ExceptionInInitializerError` is another kind of `NoSuchMethodError`." | **False.** It belongs to initialization errors, not ordinary method-lookup errors. |

## 15. Self-Check with Answers

**Question 1.** Does a `ClassFile` containing `Methodref lib/Library.version:()Ljava/lang/String;` mean `Library.version` has already been invoked?  
**Answer:** No. That is a symbolic reference describing the owner/name/descriptor; invocation still depends on the execution path.

**Question 2.** Is the JVM allowed to resolve an ordinary reference early before the call path runs?  
**Answer:** Yes, within the limits of the JVMS; however, a resolution error must be thrown at a point of action that may use the corresponding reference.

**Question 3.** Is the JVM allowed to resolve lazily after the class has already been initialized?  
**Answer:** Yes. Linking and resolution are not required to resolve everything before initialization.

**Question 4.** In the Library v1/v2 example, why does recompiling `LinkageDemo` against v2 report a compiler error, whereas running the old binary with v2 causes `NoSuchMethodError`?  
**Answer:** The new compiler sees that the API no longer has the method; the old binary still contains the v1 Methodref and runtime resolution cannot find the method on Library v2.

**Question 5.** Once `NoSuchMethodError` occurs when using a reference, is the JVM required to automatically try reloading a new JAR on the second use?  
**Answer:** No. `JVMS `5.4.3` specifies that the resolution failure result is retained for the same symbolic reference under the applicable conditions.

**Question 6.** Do `NoClassDefFoundError` and `ExceptionInInitializerError` always indicate the same phase?  
**Answer:** No. One error may involve loading/linking or a class in an erroneous state, while the other is usually caused by static initialization failing.

**Question 7.** From `java -Xlog:class+load=info`, can you confirm which Methodref was resolved at which timestamp?  
**Answer:** No. A class-loading log is not a per-symbolic-reference resolution log.

**Question 8.** Why does `CONSTANT_Dynamic` need its own timing rules?  
**Answer:** It involves bootstrap computation, and the specification forbids resolving it too early before the related `ldc` actions or its use as a static argument in a bootstrap.

**Question 9.** Can a loading constraint violation occur when two loaders disagree on a type name in a method descriptor?  
**Answer:** Yes, if the constraints require the same runtime class identity and the two loaders cannot satisfy that.

**Question 10.** When a linking error appears "late," what is the most accurate conclusion to state?  
**Answer:** The program reached **an action related to the failing linkage**; one cannot yet conclude whether the JVM started resolution at that exact moment or detected it earlier.

**Key takeaway to remember:** **Early/lazy resolution** is the VM's flexibility regarding when to turn symbolic references into runtime entities; **error timing**, on the other hand, is constrained by the JVMS to **program actions that may require linkage**. To diagnose an error that appears late, find the exact **constant-pool reference, the bytecode using it, the binary version, and the class loader**, rather than inferring from the number of printed lines that the VM definitely resolved early or late.
