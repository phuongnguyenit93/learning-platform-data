# `athrow`, exception tables, and frame unwinding when a call fails

Java does not handle exceptions like a normal return value. When a method encounters an error and cannot catch it, the JVM removes that call's frame from the call stack and continues searching for a matching handler in the caller's frame. The mechanism combining **`athrow`**, **`Code.exception_table`**, and **frame unwinding** ensures an exception can propagate through multiple methods until it is handled or the thread terminates.

This article belongs to the **Frames and calls** topic, explaining the bytecode rules, how `try/catch/finally` and `try-with-resources` are represented, the difference between exceptional completion and normal return, as well as how to read `javap`. Examples run on **Java 17+**. Class-file details and JVM behavior are based on JVMS Java SE 17.

## 1. Distinguishing normal completion from abrupt completion

| Path | What happens in the callee | What does the caller receive? |
| --- | --- | --- |
| **Normal** | Instruction `ireturn`, `lreturn`, `freturn`, `dreturn`, `areturn`, or `return` completes the call | Non-`void` has a return value on the caller's operand stack; `void` has no value |
| **Abrupt** | An exception is thrown and the callee has no matching handler | **No normal return value**; the exception propagates to the caller and handler search continues |

Example:

```java
static int divide(int x, int y) {
    return x / y;
}
```

With `divide(10, 2)`, integer division returns `5`. With `divide(10, 0)`, the integer division opcode `idiv` causes `ArithmeticException`; `ireturn` does not complete, so the caller does not receive an integer `0` or a fake `null` as a result.

**Not every exception originates from the `throw` keyword in source code.** Instructions such as `idiv`, `aaload`, `getfield`, `invokevirtual`, array access operations, or class linking can cause exceptions according to runtime rules. Both explicit and implicit exceptions can be caught by `exception_table`.

```text
main frame
   └── caller frame (invoke callee)
         └── callee frame
               ├── normal return → caller continues with result
               └── exception E
                    ├── handler directly in callee → run corresponding catch
                    └── no handler
                           ↓
                       pop callee frame
                           ↓
                   search handler in caller, at invoke location
                           ↓
              caught → run handler | not caught → pop caller
```

## 2. What is the `athrow` opcode?

`athrow` has opcode **191** (hexadecimal **`0xbf`**), used to throw an object of class `java.lang.Throwable` or a subclass, such as `Exception`, `RuntimeException`, or `Error`.

Before `athrow`, the frame's operand stack has a reference value to the exception object on top:

```text
operand stack before: [..., exceptionRef]
                           │
                           ▼
                         athrow
                           │
                search handler or unwind
```

If thrown in Java:

```java
static void fail() {
    throw new IllegalStateException("bad state");
}
```

Bytecode generated by `javac` typically contains the pattern:

```text
new           java/lang/IllegalStateException
dup
ldc           "bad state"
invokespecial java/lang/IllegalStateException.<init>:(Ljava/lang/String;)V
athrow
```

`new` creates an object that has not completed initialization according to the JVM model; `dup` keeps the reference while the constructor receives the receiver via `invokespecial`; finally `athrow` uses the initialized reference. This is an **opcode illustration** snippet, because `javap -c` output also has offsets/constant-pool indexes.

### 2.1. `athrow` differs from `areturn`

- `areturn` completes the method **normally**, returning a reference matching the return descriptor to the caller.
- `athrow` transitions the method to **exceptional control flow**, searching for a handler; it does not use a return descriptor and does not return the exception object as a normal result.
- `athrow` can throw `Error`; the JVM does not have a separate opcode named `throwerror`.
- Both checked and unchecked exceptions can be thrown through the same bytecode mechanism; the checked/unchecked difference lies mainly in Java compilation rules.

### 2.2. What if the operand of `athrow` is `null`?

`athrow` with `objectref = null` throws **`NullPointerException`**, rather than throwing an "objectless exception".

```java
static void throwNull() {
    RuntimeException problem = null;
    throw problem;
}
```

If the caller catches `NullPointerException` around the call, it can handle it. The method snippet above is an illustrative example; the full program is in section 7.

### 2.3. Exceptions where bytecode has no `athrow` at the failure site

In `return 100 / value;`, the `idiv` operation with `value = 0` raises an exception according to the semantics of `idiv`. No explicit `athrow` instruction following `idiv` is needed. From that point on, the JVM still searches for a handler using the same mechanism.

Conversely, a `catch` can `throw ex;`, which typically generates `aload` followed by `athrow` to **rethrow** the same reference, without necessarily creating a new exception object.

## 3. Structure of `Code.exception_table`

The Java bytecode of a method resides in the **`Code` attribute** of `method_info`. Besides `code[]`, `max_stack`, and `max_locals`, `Code` also has `exception_table_length` and the **`exception_table[]`** array.

An entry consists of four `u2` fields:

```text
exception_table entry
├─ start_pc     // start of protected code region
├─ end_pc       // open end point of the region
├─ handler_pc   // offset where handler starts
└─ catch_type   // class reference in constant pool, or 0
```

| Field | Exact meaning |
| --- | --- |
| **`start_pc`** | Offset of the first instruction to which the handler can apply, **inclusive** |
| **`end_pc`** | End boundary offset, **exclusive** |
| **`handler_pc`** | Offset of the instruction starting the handler code |
| **`catch_type`** | Constant-pool class index to match exception type, or **0** to match any Throwable |

The protected region is **`[start_pc, end_pc)`**. If `start_pc=2, end_pc=10`, then an exception at an opcode starting at offset **2 up to before 10** can be handled by the entry; at an opcode at offset **10**, it cannot be handled by that entry.

`handler_pc` must point to the **start of a valid instruction** within the same `code[]`, and must not point to an operand byte in the middle of an instruction. `end_pc` can point to the start of an instruction or exactly `code_length` according to class-file structure constraints.

### 3.1. How to read the table from `javap`

Suppose the tool displays a sample:

```text
Exception table:
   from    to  target type
       0     4       5 Class java/lang/NumberFormatException
```

- `from 0` is `start_pc`.
- `to 4` is `end_pc` **exclusive**.
- `target 5` is `handler_pc`.
- The `type` column is the caught class via `catch_type`.

If `invokestatic` at offset 1 calls a method that throws `NumberFormatException`, the entry can match because 1 is in `[0,4)`. It does not matter which bytecode offset in the **callee** the exception originated from; when propagating back to the **caller**, the position to check is the offset of the **call instruction in the caller**.

### 3.2. `catch_type = 0` is not type `Object`

The value `0` is a **catch-all** sentinel: it matches any throwable being handled at a pc within the protected region. `javap` usually prints `any`.

It is **different from**:

- `catch (Throwable t)`: a handler catching the specific type `java/lang/Throwable`, usually having a non-zero `catch_type` pointing to the constant pool.
- `catch (Exception e)`: does not catch `Error` types that only inherit from `Throwable`.
- `catch (RuntimeException e)`: only catches RuntimeException and its subclasses.

`catch_type=0` is often used in cleanup bytecode such as `finally` or monitor handling paths. You cannot conclude that a method "swallows every exception" just by seeing an `any` entry: the handler may finish cleanup and **`athrow` again**.

### 3.3. The `Exceptions` attribute differs from `exception_table`

`void work() throws IOException` declares part of the checked exception contract in Java source. The class file can store this declaration via the method's **`Exceptions` attribute**.

`exception_table`, on the other hand, is the **actual handler table** of `Code`, describing runtime catch/cleanup. A method that only declares `throws` may **have no** exception table; a method that does not declare `throws` can still have try/catch/finally and a handler table.

## 4. Handler lookup rules: order and exception type

The JVM searches for an exception handler in the current frame according to the algorithm:

1. Determine the offset `pc` of the instruction where the exception occurred (or the invoke position in the caller frame when the exception has propagated up).
2. Iterate through each `exception_table[]` entry **in the order recorded in the table**.
3. Check `start_pc <= pc < end_pc`.
4. Check the type: the exception is an instance of the class in `catch_type` or a subclass; `catch_type=0` always matches the type.
5. Select the **first entry that satisfies both the range and the type**. Set pc to `handler_pc`.
6. No entry matches → the method completes abruptly, the frame is unwound, and lookup continues in the caller.

### 4.1. The JVM does not automatically pick the "narrowest handler"

Suppose a method's bytecode has entries for the same range:

```text
from to target type
0    15  25     Class java/lang/RuntimeException
0    15  35     Class java/lang/IllegalArgumentException
```

If `IllegalArgumentException` is thrown at pc 9, the JVM picks **target 25**, because RuntimeException in the first entry already matched. It **does not skip** an earlier handler to find a more specific subtype.

The Java source compiler checks reachable catch clauses: placing a broad catch before a narrow catch in the same try can cause `javac` to report an error. However, when reading a **class file**, the JVM rule remains **first matching entry**; bytecode generators must preserve the exact order so semantics do not change.

### 4.2. What if there are multiple overlapping protected regions?

A method with nested try/catch/finally can have multiple overlapping `[start_pc,end_pc)` entries. The JVM **does not** pick the shortest range using an independent algorithm. It scans the table in order and picks the first matching entry.

That is why arbitrarily **sorting the exception table by offset or by class name** during bytecode instrumentation can alter behavior. If an executing handler throws an exception again, the JVM consults the table once more using the handler's new pc.

## 5. What is the state of the handler's stack?

When a matching handler is found:

- The JVM sets pc to `handler_pc`.
- **Clears all previous values in the operand stack** of the handling frame.
- Pushes **a single reference to the exception object itself** being thrown onto the operand stack.
- Executes the first instruction of the handler.

```text
Before the exception occurs:
  operand stack: [..., temporary1, temporary2, ...]

When transferring to the handler:
  operand stack: [exceptionRef]      // one logical element

Common handler:
  astore_1                           // store exceptionRef into local 1
  ...                                // handle, return, or rethrow
```

**No normal return value** is pushed onto the caller stack when an exception propagates across a callee. If the caller frame has a handler catching the exception, the operand stack **of the caller frame at the handler** is cleared and then receives a single exception reference.

The local-variable array of the **handling frame** remains its own local array and must satisfy the verifier/StackMapTable. Meanwhile, local variables of **unwound frames** cannot be accessed from the caller's handler.

### 5.1. Why do handlers often start with `astore`?

Java source `catch (IllegalArgumentException e)` needs to use the variable `e`. Because upon entering the handler the operand stack contains the exception reference, the compiler usually uses `astore` to move the reference into a local slot. However, `astore_1` is just an example; the index varies depending on layout. A cleanup handler can also store the exception temporarily, do other work, and then load it back for `athrow`.

## 6. Frame unwinding across method calls

Consider the chain `top() → middle() → leaf()`:

```java
static int leaf() {
    throw new IllegalArgumentException("negative");
}

static int middle() {
    return leaf();
}

static void top() {
    try {
        System.out.println(middle());
    } catch (IllegalArgumentException ex) {
        System.out.println("handled=" + ex.getMessage());
    }
}
```

Sequence in the JVM:

```text
1. leaf() runs, athrow E.
2. Search leaf's exception_table: no matching handler.
3. Pop leaf frame, do not return int.
4. Restore middle frame at the call site of leaf().
5. Search middle's exception_table for the pc of the leaf invoke instruction.
6. No handler → pop middle frame, still do not return int.
7. Restore top frame at the call site of middle().
8. Search top's exception_table for the pc of the middle invoke instruction.
9. Handler catching IllegalArgumentException exists → top enters handler.
10. Top operand stack at handler = [E]; handler prints message.
```

**Subtle point:** when searching `top`'s handler, the JVM uses the offset of the **instruction calling `middle` in `top`**, not the `athrow` offset of `leaf`. Each method has its own code array; offsets are not shared.

If no frame has a handler, the thread terminates due to an uncaught exception. The thread's or runtime's uncaught exception handler may report the error. Other threads **do not necessarily die together**, and a JVM with other non-daemon threads can continue running.

### 6.1. A stack trace differs from the live call stack

The stack trace on an exception can record information about the methods involved at the time the error occurred. However, after unwinding, the callee frames have been removed from the running call stack. Those stack trace lines are diagnostic information, and **do not** keep local variables alive for a caller's handler to read back.

## 7. Complete Java 17+ program: return, implicit and explicit `athrow`

Create file **`ExceptionFlowDemo.java`**:

```java
public class ExceptionFlowDemo {

    static int leaf(int value) {
        if (value < 0) {
            throw new IllegalArgumentException("negative");
        }
        return 100 / value;
    }

    static int middle(int value) {
        try {
            return leaf(value);
        } finally {
            System.out.println("middle finally (" + value + ")");
        }
    }

    static void run(int value) {
        try {
            int result = middle(value);
            System.out.println("result=" + result);
        } catch (IllegalArgumentException ex) {
            System.out.println("argument=" + ex.getMessage());
        } catch (ArithmeticException ex) {
            System.out.println("arithmetic=" + ex.getMessage());
        }
    }

    public static void main(String[] args) {
        run(2);
        run(-1);
        run(0);
    }
}
```

Run:

```bash
javac --release 17 ExceptionFlowDemo.java
java ExceptionFlowDemo
```

**Exact stdout:**

```text
middle finally (2)
result=50
middle finally (-1)
argument=negative
middle finally (0)
arithmetic=/ by zero
```

Three execution paths:

| Input | `leaf` | `middle` | `run` |
| --- | --- | --- | --- |
| `2` | Returns `50` via `ireturn` | Runs `finally` then returns `50` | Prints `result=50` |
| `-1` | Creates IllegalArgumentException then `athrow` | Runs `finally` and propagates throw | Catches IllegalArgumentException, prints message |
| `0` | `idiv` throws ArithmeticException implicitly | Runs `finally` and propagates throw | Catches ArithmeticException, prints `/ by zero` |

The line `middle finally (...)` appears on both the **normal path** and the **exceptional path**. When throwing an error, `middle` does not return a dummy `int` and "report an error in parallel"; it **does not normal-complete** and the exception searches for a handler in `run`.

### 7.1. Inspecting bytecode with `javap`

```bash
javap -c -p ExceptionFlowDemo
javap -v -p ExceptionFlowDemo
```

What to look for in each place:

- `leaf` has `new`, `dup`, `invokespecial`, **`athrow`** in the negative branch, and `idiv` in the division path.
- `middle` has code ensuring `finally` runs on both paths. The compiler typically generates a **catch-all handler** along with cleanup code and an `athrow` to rethrow.
- `run` has entries in the **Exception table** for `IllegalArgumentException` and `ArithmeticException`.
- The `catch` code typically has `astore` to save the exception reference before calling `getMessage()`.
- `main` calls `run` three times.

A sample table illustrating the structure (offsets are not taken from a fixed build):

```text
Exception table:
  from   to   target   type
     0   12       20   Class java/lang/IllegalArgumentException
     0   12       35   Class java/lang/ArithmeticException
```

Do not use example offsets to debug a real file. `javap` from the class you compiled gives the exact positions.

## 8. How `try/catch/finally` is lowered to bytecode by the compiler

### 8.1. `catch` is not a separate method

`catch (NumberFormatException e)` is lowered to one or more entries in `exception_table` and **handler bytecode** within the same `Code` attribute of the method containing try/catch. A handler is not a method named `catch`.

```java
static int parse(String text) {
    try {
        return Integer.parseInt(text);
    } catch (NumberFormatException ex) {
        return -1;
    }
}
```

Conceptual structure:

```text
try code:
   aload_0
   invokestatic Integer.parseInt
   ireturn
handler:
   astore_1
   iconst_m1
   ireturn
exception_table:
   [try code range) -> handler, catch_type NumberFormatException
```

### 8.2. `finally` is not a JVM opcode

The Java compiler generates enough code so that `finally` executes along every exit path from `try`/`catch`:

- On normal return, run cleanup then return the normal value to the caller.
- When throwing an exception, the handler may temporarily store the exception, run cleanup, and then **`athrow` again**.
- With `break`, `continue`, or multiple exits, the compiler organizes branches and may duplicate cleanup code.

Catch-all model example:

```text
Exception table:
  from  to  target  type
     0  10      18  any

18: astore_2
19: ... cleanup code ...
24: aload_2
25: athrow
```

`any` usually represents `catch_type=0`. You should not look at the word `any` alone and conclude the method swallowed all errors: in the example, the handler **rethrows the exception after cleanup**.

**Do not assume modern compilers always use `jsr` / `ret` for finally.** That is a historical mechanism, not the default scheme of Java 17 `javac`.

### 8.3. Exceptions or `return` inside `finally` itself

Java `finally` can alter the completion path:

```java
static int unsafe() {
    try {
        throw new IllegalStateException("first");
    } finally {
        return 99;
    }
}
```

In this case, `return` in `finally` can **replace** throwing the exception from `try`, causing `unsafe()` to return `99` normally. This is why `return` inside `finally` should be avoided: it hides the exception that needs investigation.

If cleanup itself throws another exception, that error can also replace the propagating exception under standard Java rules. Try-with-resources handles the simultaneous two-exception situation using **suppressed exceptions**, unlike a simple hand-written `finally`.

## 9. `try-with-resources` and `getSuppressed()`

Create file **`SuppressedDemo.java`**:

```java
public class SuppressedDemo {
    static final class Resource implements AutoCloseable {
        @Override
        public void close() {
            throw new IllegalStateException("close failed");
        }
    }

    static void work() throws Exception {
        try (Resource resource = new Resource()) {
            throw new Exception("body failed");
        }
    }

    public static void main(String[] args) {
        try {
            work();
        } catch (Exception ex) {
            System.out.println("primary=" + ex.getMessage());
            System.out.println("suppressed=" + ex.getSuppressed().length);
            System.out.println("suppressed-message=" +
                    ex.getSuppressed()[0].getMessage());
        }
    }
}
```

Compile and run:

```bash
javac --release 17 SuppressedDemo.java
java SuppressedDemo
```

Stdout:

```text
primary=body failed
suppressed=1
suppressed-message=close failed
```

Because the `try` body threw `body failed` first and `close()` also threw `close failed`, Java keeps the body error as the **primary exception** and attaches the close error as a **suppressed exception**. The compiler may use handlers, locals, and calls to `Throwable.addSuppressed` to guarantee this behavior.

`getCause()` and `getSuppressed()` are two different concepts: cause describes the causal chain, whereas suppressed stores secondary errors occurring during cleanup or applicable circumstances.

**Practice:** do not rely on GC to close files/sockets/DB connections; use `try-with-resources` or explicit cleanup when resources must be closed according to their lifecycle.

## 10. `synchronized` and monitor release when throwing an error

For a **synchronized instance/static method**, the JVM manages the monitor when method invocation begins. When the method completes abruptly, the monitor entered for this call must be exited according to JVM rules.

For a `synchronized (lock)` block, the compiler typically uses `monitorenter` / `monitorexit` and a handler to exit the monitor on the exception path:

```java
static void guarded(Object lock) {
    synchronized (lock) {
        throw new IllegalStateException("inside lock");
    }
}
```

Even if a statement inside the block throws an error, Java still requires exiting the synchronized block properly. A bytecode generator that manually inserts `monitorenter` while forgetting the `monitorexit` path when an exception occurs can break validity/correctness.

**Do not equate** monitor management with `finally` automatically closing every kind of resource. Monitors have their own JVM rules; file handles and network sockets require explicit close operations.

## 11. Checked and unchecked exceptions use the same runtime propagation path

The Java compiler checks checked exceptions like `IOException` according to `catch` or `throws` rules. However, at JVM runtime:

- `athrow` does not have one opcode for checked and another opcode for unchecked.
- Handlers match **exception object type** against `catch_type` and `pc` position.
- The `Exceptions` attribute from `throws` differs from `exception_table` used for catching.
- `Error` and `RuntimeException` can also be thrown/caught by the JVM, although application design generally should not catch `Throwable` broadly.

Example:

```java
static void checked() throws java.io.IOException {
    throw new java.io.IOException("cannot read");
}
```

The `throws` clause enables checking at the source/caller level, while the actual throwing path of the body still ends with `athrow`. There is no special typed return for checked exceptions.

### 11.1. Asynchronous libraries can wrap errors

If a task on another thread throws an error, `Future.get()` may throw `ExecutionException` wrapping the task's error; `CompletableFuture.join()` may throw `CompletionException`. This is a **library mechanism for passing error state across tasks/threads**, and does not mean `athrow` directly jumps from thread A's stack to thread B's stack.

Each thread has its own call stack; frame unwinding operates along the call chain of the current thread itself.

## 12. Reading stack traces and exception handlers with the right tools

- **`javap -c -v ClassName`**: inspect bytecode, `Code`, `Exception table`, types, handler offsets, and `StackMapTable`.
- **Stack trace**: call chain information when a Throwable captures a stack trace; does not directly display the handler table or local-variable array.
- **Debugger**: can break at exception throw/catch, and inspect frames and live variables depending on debug info.
- **`javac -g`**: provides additional debug information such as `LocalVariableTable` to help find variable names; does not turn `exception_table` into source-level data.

Stack trace example **for illustration only**:

```text
java.lang.IllegalArgumentException: negative
    at ExceptionFlowDemo.leaf(ExceptionFlowDemo.java:6)
    at ExceptionFlowDemo.middle(ExceptionFlowDemo.java:12)
    at ExceptionFlowDemo.run(ExceptionFlowDemo.java:21)
```

The example program in section 7 **catches the exception**, so it does not automatically print this stack trace to stdout. Line numbers do not necessarily match your file.

## 13. When editing bytecode, where do handler bugs usually come from?

If writing ASM/Byte Buddy or instrumenting class files, you must preserve these invariants:

1. **`start_pc < end_pc`**, both `start_pc` and `handler_pc` point to the start of a valid instruction, and `end_pc` points to the start of a valid instruction or equals `code_length`.
2. **Valid `catch_type`**: 0 or a constant-pool index to an appropriate `CONSTANT_Class_info`.
3. **Table order preserves semantics**: the first matching entry wins; changing order can change which handler executes.
4. **Stack at handler** has a Throwable reference consistent with the verification state. The handler must not assume the old operand stack still exists.
5. **`StackMapTable` and locals** must be valid at converging control-flow paths according to the class-file version.
6. **Monitor cleanup** for synchronized blocks and `finally` logic must work on every exit path defined by Java.
7. **Do not use wrong typed returns** to hide exceptions or fabricate normal values.

Violations can lead to `ClassFormatError`, `VerifyError`, or errors during linking/execution depending on their nature. There is no single fixed error message for every invalid exception table.

### 13.1. Example of the exclusive `end_pc` bug

```text
bytecode offsets:
  0 ...  first protected instruction
  8 ...  last protected instruction
 11 ...  next instruction (outside try)
```

If you want to protect the instruction at 8 but not the instruction at 11, use `start_pc=0, end_pc=11`. Using `end_pc=8` **excludes the instruction at 8 itself** from the protected region.

### 13.2. Frame unwinding does not mean losing all heap objects

An unwound frame is no longer active; local refs in that frame are no longer a source keeping objects alive in logical state. However, objects on the heap **may still be reachable** from the caller, static fields, collections, the exception object, or other sources. GC is not required to run immediately when a frame is unwound.

Do not confuse **frame unwinding** with **garbage collection** or operating system resource cleanup.

## 14. Common misconceptions

1. **"`athrow` is like `areturn` except it returns an exception."** False. `athrow` triggers exceptional flow, while `areturn` is a normal return.
2. **"Every exception in Java has the `throw` keyword on the exact failing line."** False. Runtime can throw from opcodes like `idiv` or field access.
3. **"The `exception_table` contains the list of exceptions written in `throws`."** False. `throws` and the runtime handler table serve different purposes.
4. **"`end_pc` includes the bytecode at that exact offset."** False. The handler range is `[start_pc,end_pc)`.
5. **"The JVM picks the most specific catch subtype."** False. It picks the **first entry** that satisfies both range and type.
6. **"`catch_type=0` is type `Object`."** False. It is a catch-all sentinel.
7. **"The handler receives the entire operand stack from right before the throw."** False. The stack is cleared, leaving only a single exception reference.
8. **"Without a catch in the callee, the caller receives `null`."** False. There is no normal return value; the exception propagates to the caller.
9. **"Unwinding always removes all frames."** False. It stops when a valid handler is found.
10. **"`finally` is a bytecode instruction."** False. The compiler generates the appropriate code paths and handlers.
11. **"`try-with-resources` always replaces the primary exception with the `close` error."** False. In many cases the close exception is suppressed.
12. **"An uncaught exception in one worker always kills the entire JVM."** False. Threads can continue according to independent lifecycles.
13. **"Unwinding automatically closes all streams and sockets."** False. Use explicit cleanup/try-with-resources.
14. **"The exception object is recreated each time it crosses a frame."** False. Rethrow can keep the same reference; a new wrapper exception is a code choice.
15. **"A stack trace is a snapshot of live frames that remain long after catching."** False. It is diagnostic information; many frames have already been unwound.

## 15. Self-check with answers

**Question 1.** An entry has `start_pc=3, end_pc=10, handler_pc=20`. Does an exception at bytecode offset 10 match this entry?

**Answer:** No; `end_pc` is **exclusive**. An exception at offset 9 can match if the type fits.

**Question 2.** A `RuntimeException` handler appears before an `IllegalArgumentException` handler for the same range. If `IllegalArgumentException` is thrown, which handler is selected?

**Answer:** The `RuntimeException` entry that comes first, because `IllegalArgumentException` inherits from `RuntimeException`.

**Question 3.** What happens when `athrow` encounters `null`?

**Answer:** The JVM throws `NullPointerException`; a matching handler can catch it.

**Question 4.** When catching an exception in the caller, what does the caller's operand stack contain at the handler?

**Answer:** A single exception reference; other operand values are cleared.

**Question 5.** `leaf` throws at offset 30, while caller `top` calls `leaf` at offset 5. Which pc does `top`'s handler table use?

**Answer:** The pc of the **invoke instruction in `top`**, which is 5.

**Question 6.** Why does the `middle` example print the `finally` line even when `leaf` throws an error?

**Answer:** The compiler uses code branches/handlers to execute finally on both normal and exceptional exits according to Java semantics, then continues to return or rethrow.

**Question 7.** In `SuppressedDemo`, which error is primary and which is suppressed?

**Answer:** `body failed` is primary; `close failed` is suppressed.

**Question 8.** You see an `exception_table` entry with `type any`. Can you conclude the method swallowed every error?

**Answer:** No. The handler may perform cleanup and execute `athrow` to rethrow; you need to read the bytecode at `handler_pc` itself.

**Question 9.** If an uncaught exception occurs in a request-handling thread, must all other threads die with it?

**Answer:** No; that thread itself may terminate abruptly, while other threads and the process depend on the application/runtime lifecycle.

## 16. Brief summary via control flow

```text
instruction raises Throwable E
           │
           ▼
   athrow or implicit exception
           │
           ▼
consult current frame's exception_table:
  [start_pc, end_pc) contains pc?
  catch_type matches type E?
  take the FIRST matching entry
           │
     ┌─────┴─────────┐
     │ Has handler   │ No
     ▼               ▼
handler_pc         unwind frame
stack = [E]        no normal return
run handler        restore caller at invoke
                   └─ consult caller's handler, repeat
```

**Remember:** `athrow` is used to throw a `Throwable` object; `exception_table` specifies **which pc is protected by which handler** and **which type is allowed to be caught**. On a match, the operand stack is set up with **one exception reference**. When there is no match, the JVM unwinds the frame and continues searching in the caller **without going through a typed return**. `finally`, monitor cleanup, and try-with-resources work with this mechanism to enforce Java semantics.
