# The Code Attribute in a Class File: `max_stack`, `max_locals`, Bytecode, and Exception Table

A compiled Java method normally no longer stores source code in the `.class` file. Instead, the method has a **`Code` attribute** that describes the JVM instruction code, the maximum number of slots of the operand stack, the number of local variable slots to allocate for the frame, exception-catching regions, and some auxiliary metadata. Reading this structure accurately helps explain why a Java call works, why casts/branches/`try-catch` appear as multiple bytecode instructions, and why a `.class` file can be rejected during verification.

This article uses **Java SE 17 (class-file major version 61)** as its baseline. The structural rules are taken from the Java Virtual Machine Specification (JVMS), mainly `4.7.3, `2.6, `4.10, `6.5. Other JDK releases may generate different bytecode sequences while remaining semantically valid; do not assume a snapshot from `javap` is the only structure a compiler is allowed to generate.

## 1. Where Is the `Code` Attribute Located?

A `.class` file consists of a header, constant pool, class information, fields, methods, and attributes. In the `methods[]` table, each `method_info` has an `attributes[]` table. For a method with a body that the JVM executes, one element of that table is **`Code`**.

```text
ClassFile
├── magic, minor_version, major_version
├── constant_pool
├── access_flags, this_class, super_class, interfaces
├── fields[]
├── methods[]
│   └── method_info of a specific method
│       ├── access_flags, name_index, descriptor_index
│       └── attributes[]
│           └── Code_attribute
│               ├── max_stack
│               ├── max_locals
│               ├── code_length + code[] (bytecode)
│               ├── exception_table[]
│               └── attributes[] of Code itself
└── attributes[] of class
```

Points to distinguish:

- **`method_info`** describes a method by its name, descriptor (parameter types/return type in JVM format), flags, and attributes.
- **`Code_attribute`** describes the code and execution-support information **for one method**, not for the entire class, an individual call, or the entire JVM.
- **Each method invocation** has its own JVM frame with an operand stack and local variables; each frame uses the limits from `max_stack` and `max_locals` of the corresponding method. Multiple recursive calls to the same method create multiple frames, sharing the same metadata template but with different local values.
- **`abstract` or `native`** methods do not have a `Code` attribute in `method_info`. A normal method with code must have **exactly one** `Code` attribute according to class file rules.
- A constructor is the `<init>` method; a class/interface initializer is `<clinit>` if generated by the compiler. They can also contain `Code`. An interface `default` method with a body also belongs to the group that has code.
- `Code` is not synonymous with `SourceFile` or `SourceDebugExtension`: those metadata items have different roles.

If a class has ten methods with bodies, you will typically see multiple `Code:` sections, each attached to one method. Reading one section does not allow applying its `max_stack` or `exception_table` to another method.

## 2. Standard Binary Structure of `Code_attribute`

JVMS `4.7.3` defines the following structure. This is **pseudocode specifying the class file format**, not a standalone Java program:

```text
Code_attribute {
    u2 attribute_name_index;
    u4 attribute_length;
    u2 max_stack;
    u2 max_locals;
    u4 code_length;
    u1 code[code_length];
    u2 exception_table_length;
    {
        u2 start_pc;
        u2 end_pc;
        u2 handler_pc;
        u2 catch_type;
    } exception_table[exception_table_length];
    u2 attributes_count;
    attribute_info attributes[attributes_count];
}
```

`u1`, `u2`, `u4` are respectively **unsigned integers** encoded in 1, 2, and 4 bytes in the class file; multi-byte values in the class file format use big-endian byte order.

| Field | Size/Meaning | How to Read |
| --- | --- | --- |
| `attribute_name_index` | `u2`, constant pool index | Points to `CONSTANT_Utf8_info` with value `Code` |
| `attribute_length` | `u4` | Number of bytes of the attribute's content, **excluding the first 6 bytes** for name index and length |
| `max_stack` | `u2` | **Maximum** operand stack depth that the method needs, measured in slots |
| `max_locals` | `u2` | Number of slots in the local-variable array of each method frame |
| `code_length` | `u4` | Number of **bytes** in the instruction array, not the number of instructions and not the number of Java lines |
| `code[]` | `u1[code_length]` | Opcodes along with operand bytes, branch offsets, switch data, etc. |
| `exception_table_length` | `u2` | Number of exception handler entries |
| `exception_table[]` | Each entry consists of 4 `u2` fields | Protected bytecode range, handler target, and exception type |
| `attributes_count` | `u2` | Number of attributes **nested inside Code**, for example `StackMapTable` or `LineNumberTable` |
| `attributes[]` | Variable length | Verification and debug metadata attached to the method's code |

Important limit: `code_length` is **greater than 0 and less than 65536**, meaning a `Code` attribute can contain at most **65535 bytes** of bytecode. A multi-byte instruction is still counted byte by byte. `javap -c` shows the **bytecode offset**, not the instruction's ordinal number by source line.

Do not confuse the `Code` attribute name with a constant pool entry containing the string literal `Code`: `attribute_name_index` only **identifies the attribute type**; the actual code resides in `code[]`.

## 3. `max_stack`: Maximum Number of Operand Stack Slots in a Frame

Each JVM frame has its own **operand stack**. Bytecode typically pushes values onto the stack with `iload`/`lload`/`iconst_*`, pops operands with addition or method invocation, and pushes the result back. `max_stack` indicates the **maximum depth measured in stack slots** needed for this method.

Example of adding two `int`s in a method:

```text
Operand stack state (bottom → top):
initial             []
iload_0             [a]        // 1 slot
iload_1             [a, b]     // 2 slots
iadd                [a+b]      // 1 slot
ireturn             []         // return value to caller
```

The maximum depth of this snippet is **2 slots**, so a method executing only this sequence can have `max_stack = 2`. `max_stack` is **not** the number of opcodes, the number of Java variables, the byte size of the class file, the RAM allocated for all stacks of the process, or the actual value at every point in time.

### Category 1 and Category 2 Value Types

In the JVMS model:

- `int`, `float`, reference, and computational values of **category 1** occupy **1 slot** of the operand stack.
- `long` and `double` belong to **category 2** and occupy **2 slots**.
- Java `byte`, `short`, and `char` values are typically represented/computed as `int` on the operand stack; there is no completely independent `byte` addition opcode set.

For example, the method `sumLong(long a, long b)` may have the sequence:

```text
lload_0             [a(long)]              // 2 slots
lload_2             [a(long), b(long)]     // 4 slots
ladd                [a+b(long)]           // 2 slots
lreturn             []                    // end frame
```

Because two `long`s are needed simultaneously, the maximum depth here is **4 slots**. Counting "there are two numbers so max_stack equals 2" is wrong. A `long` value is still **one logical value**, but contributes **two units** to the stack depth.

### `max_stack` Is a Static Maximum, Not a Runtime Stack Trace

- It is **method** metadata filled in by the compiler/class-file generator to support execution layout and validity verification.
- `max_stack = 4` does not promise there are always four slots of data on the stack; some branches may use fewer.
- Do not use `max_stack` to infer the **call stack** depth, how many recursions can be performed, or the `-Xss` value. Each method call creates its own frame.
- If bytecode attempts to push more slots than declared on a valid execution path, the class file fails verification requirements; the JVM may reject it with `VerifyError` or an appropriate format/linkage error depending on the violation.

## 4. `max_locals`: Number of Slots Reserved for Parameters and Local Variables

Each frame contains an array of **local variables** indexed `0, 1, 2, ...`. `max_locals` specifies the total number of **slots** allocated for this array. It includes slots for parameters passed into the method and temporary variables generated by the compiler when needed.

Table of rules:

| Situation | Local Variables Layout |
| --- | --- |
| Instance method | Slot `0` normally holds `this`, followed by parameters |
| `static` method | No implicit `this`; the first parameter starts at slot `0` |
| `int`/`float`/reference parameter | Occupies one slot |
| `long`/`double` parameter | Occupies **two consecutive slots** |
| Variables in non-overlapping scopes | The compiler may reuse a slot |
| Exception local in `catch` | The compiler normally uses an extra slot to hold the `Throwable` received by the handler |

For the method `public static long sumLong(long left, long right)`, `left` occupies slots **0–1**, `right` occupies slots **2–3**; the method only needs these two parameters, so it can have **`max_locals = 4`**.

For the method `public int increment(int value)`, slot **0** holds `this`, slot **1** holds `value`; it can have **`max_locals = 2`**.

A `static void run()` method that takes no parameters and uses no local variables can have `max_locals = 0`. Do not assume every method has `this`.

### Two Notes on Indices and Variable Names

1. A local variable index is a **slot in the frame**, not the declaration ordinal in the source. A `double` or `long` parameter creates a two-slot gap; the compiler may also add slots for intermediate values or exceptions.
2. `max_locals` does not store variable names like `left` or `right`. Variable names/scope boundaries may appear in the optional `LocalVariableTable` attribute when compiled with debug info, but without that table, the JVM still understands and executes bytecode via **index** and **type**.

In `javap`, the `locals=4` field comes from `max_locals`; the `LocalVariableTable` section (if present) shows some variable names and lifetimes attached to slots, **not** an alternative size for `max_locals`.

## 5. `code_length` and `code[]`: Where the Actual Bytecode Resides

`code[]` is the **byte** sequence of JVM instructions. Some opcodes have no operands; some opcodes read one or more additional bytes. Variable-length instructions such as `tableswitch` and `lookupswitch` also have alignment requirements and additional data sections. Therefore:

- `code_length` measures the **number of bytes**; from the length you cannot immediately deduce the number of instructions.
- The **Bytecode index/offset (BCI)** of `javap -c` is the **byte position where the opcode starts** in `code[]`. It is not the Java line number.
- `goto`/`if_*`/`tableswitch` jump to a valid bytecode index; the jump target must land at the **beginning of an instruction**, never in the middle of an instruction's operands.
- `ireturn`, `lreturn`, `areturn`, `return` normally terminate method execution corresponding to the result type.
- `athrow` throws a `Throwable` reference, which may cause the JVM to search for an exception handler in the same method or outer calling frames.

Example of reading output:

```text
  0: iload_0
  1: iload_1
  2: idiv
  3: ireturn
  4: astore_2
  5: iconst_m1
  6: ireturn
```

The numbers `0, 1, 2, 3, 4, 5, 6` here are **byte offsets**. They are consecutive because each opcode in the example occupies exactly one byte; in another method, the bytecode index may increase by 2, 3, or more between two printed instructions.

### Common Bytecode Instructions in This Article

| Group | Example Opcodes | Role |
| --- | --- | --- |
| Load local onto stack | `iload_0`, `iload_1`, `lload_0`, `aload_0` | Read local slot with appropriate type |
| Store stack to local | `istore`, `astore_2`, `lstore` | Save value into local slot |
| Simple constants | `iconst_m1`, `iconst_1`, `bipush` | Push integer value |
| Arithmetic | `iadd`, `idiv`, `ladd` | Pop operands from stack, push result onto stack |
| Type conversion | `i2l`, `l2i`, `i2b` | Change representation/width according to JVM semantics |
| Control flow | `ifeq`, `if_icmpge`, `goto` | Change execution BCI |
| Call/return | `invokestatic`, `invokevirtual`, `ireturn`, `lreturn` | Interact between frames |
| Exception | `athrow` | Throw exception, may transfer to handler |

The `code[]` field contains all opcodes and their corresponding operand bytes, rather than storing symbolic names like `iload_0` as text. `javap` is a **disassembler** tool that converts binary code into readable mnemonics.

## 6. `exception_table[]`: Defining Handlers for Bytecode Regions

An entry in the exception table consists of four fields:

```text
start_pc  end_pc  handler_pc  catch_type
```

| Field | Meaning |
| --- | --- |
| `start_pc` | Starting BCI **inclusive** in the protected code region |
| `end_pc` | Ending BCI **exclusive**; may equal `code_length` |
| `handler_pc` | BCI of the first instruction in the handler |
| `catch_type` | Index of `CONSTANT_Class_info` describing the caught exception type, or `0` if the handler catches all |

A handler applies when an exception occurs at an instruction with offset `pc` satisfying **`start_pc <= pc < end_pc`**. `start_pc` must be a valid instruction offset; `end_pc` must be a valid instruction offset or equal to `code_length`, and `start_pc < end_pc`. `handler_pc` must point to the start of a valid instruction in `code[]`.

Important: **`end_pc` is exclusive**. If the table says `from 0 to 3 target 4`, instructions starting at BCI `0, 1, 2` belong to the protected region; the instruction at BCI `3` does not belong to that region.

### What Does the JVM Do When an Exception Occurs?

1. When an instruction throws an exception (for example `idiv` dividing by 0) or when code executes `athrow`, the JVM identifies the method and instruction where the exception was thrown.
2. The JVM inspects the entries **in order in `exception_table[]`**, looking for an entry whose BCI lies in the protected region and whose exception type matches.
3. If a handler is found, control transfers to `handler_pc`. **The frame's operand stack is cleared**, leaving only the exception object on top for the handler to process, typically starting with `astore` to save the exception into a local variable.
4. If no matching handler exists in the current method, the exception propagates to the caller; the handler search continues in outer frames, with appropriate unwinding effects. An unhandled exception may terminate the thread according to the uncaught exception handling mechanism.

At an entry with `catch_type != 0`, the JVM checks whether the exception's type is compatible with the class indicated by the constant pool. If `catch_type == 0`, the handler applies to all exceptions (catch-all). The compiler uses catch-all in constructs like `finally` or cleanup code; do not infer that every catch-all handler was written by the programmer using `catch (Throwable ...)`.

### Why Does Handler Order Matter?

`try` regions and catch types may overlap or both apply; **the first matching entry** in the table determines the handler. The Java compiler generates an order consistent with source rules; tools that modify class files must not arbitrarily reorder entries because doing so can change semantics.

Do not confuse the **exception table** of `Code` with:

- **`Exceptions` attribute** at the `method_info` level: describes the **checked exception types declared** in `throws`, not the list of handlers for `try/catch`.
- **`LineNumberTable`**: maps BCI to source line numbers, does not handle exceptions.
- **`StackMapTable`**: helps the verifier check value types on the stack/locals at points in control flow; does not replace the exception handler table.
- **Exception stack trace** printed at runtime: describes the call chain when an error occurred, not the `exception_table[]` stored in the class.

## 7. Runnable Java 17 Example: From `try/catch` to `Code`

Create the file **`CodeAttributeDemo.java`** matching the class name:

```java
public class CodeAttributeDemo {

    public static int divideOrMinusOne(int dividend, int divisor) {
        try {
            return dividend / divisor;
        } catch (ArithmeticException error) {
            return -1;
        }
    }

    public static long sumLong(long left, long right) {
        return left + right;
    }

    public int increment(int value) {
        return value + 1;
    }

    public static void main(String[] args) {
        System.out.println("normal=" + divideOrMinusOne(12, 3));
        System.out.println("fallback=" + divideOrMinusOne(12, 0));
        System.out.println("sum=" + sumLong(20L, 22L));
        System.out.println("increment=" + new CodeAttributeDemo().increment(4));
    }
}
```

Compile with a JDK 17+ compiler supporting `--release 17` and requesting full debug metadata:

```bash
javac --release 17 -g CodeAttributeDemo.java
java CodeAttributeDemo
javap -c -v -p CodeAttributeDemo
```

**Stdout of `java CodeAttributeDemo` alone** (excluding the long output of `javap`):

```text
normal=4
fallback=-1
sum=42
increment=5
```

In `divideOrMinusOne(12, 3)`, the `idiv` instruction succeeds. When `divisor == 0`, `idiv` throws `ArithmeticException`, and the handler returns `-1`. Both calls execute **the same Code attribute** but follow two different control flow paths.

### Reading `javap -c -v -p` Part by Part

In the output of the `divideOrMinusOne(int,int)` method typically generated by `javac` version 17, the relevant part looks like:

```text
Code:
  stack=2, locals=3, args_size=2
     0: iload_0
     1: iload_1
     2: idiv
     3: ireturn
     4: astore_2
     5: iconst_m1
     6: ireturn
  Exception table:
     from    to  target type
        0     3     4   Class java/lang/ArithmeticException
```

**Note:** this is a typical disassembly from `javac`, not a guarantee that every compiler/version will choose the same offsets or handler layout. `LineNumberTable`, `LocalVariableTable`, `StackMapTable`, and the constant pool may appear interspersed or below in `javap -v` output.

Explanation of each field:

- **`stack=2`:** when preparing for `idiv`, the stack simultaneously holds `dividend` and `divisor`, each `int` occupying one slot. In the handler only one slot is needed to receive the exception; the maximum depth remains **2**.
- **`locals=3`:** `dividend` is at slot 0, `divisor` is at slot 1, and the `error` variable in `catch` is at slot 2. The program has two parameters but needs three local slots.
- **`args_size=2`:** `javap` summarizes the two declared parameters; this is **not** an independent field named `args_size` in `Code_attribute`.
- **`0–3`:** the handler protects instructions starting at BCI 0, 1, 2; `idiv` at BCI 2 is protected. `ireturn` at BCI 3 is **outside** the range because `to` is exclusive.
- **`target 4`:** when dividing by 0, the JVM jumps to `astore_2` to store the exception object into slot 2, then pushes `-1` and returns via `ireturn`.
- **`type Class java/lang/ArithmeticException`:** `catch_type` points to a constant pool class entry; it only catches exceptions matching this type.

Do not interpret `stack=2` as "the method has two statements" or `locals=3` as "there are three variables declared in source"; they are **slots** used in the frame.

### Reading `long` and Instance Methods

For `sumLong(long,long)`, typical output:

```text
Code:
  stack=4, locals=4, args_size=2
     0: lload_0
     1: lload_2
     2: ladd
     3: lreturn
```

This is a `static` method: `left` occupies local slots 0 and 1, `right` occupies 2 and 3. Placing two `long`s onto the operand stack uses **4 slots** before `ladd`. The value `args_size=2` counts **two logical arguments**, not meaning only two local slots are needed.

For `increment(int)` which is an **instance** method, typical output:

```text
Code:
  stack=2, locals=2, args_size=2
     0: iload_1
     1: iconst_1
     2: iadd
     3: ireturn
```

`this` occupies slot 0 even though the body does not use it; `value` is in slot 1. `args_size=2` in `javap`'s printout counts the `this` receiver and one parameter passed to the method invocation.

### Self-Checking Assumptions

If you use another compiler and see different instructions or offsets, check the values it prints and apply the corresponding **JVMS rules**. Do not write tests requiring bytecode to match an example verbatim, unless the project is specifically testing a pinned version of that tool/compiler.

## 8. StackMapTable and Attributes Nested Inside Code

After `exception_table[]`, `Code` also has its own `attributes[]` table. Some common attributes:

| Attribute | Purpose | Is It an Opcode or Handler List? |
| --- | --- | --- |
| `StackMapTable` | Stores stack map frames to help check types of locals/operand stack at points in control flow | No; used for verification |
| `LineNumberTable` | Maps bytecode offsets to source line numbers (supports debugging/stack traces) | No |
| `LocalVariableTable` | Name, descriptor, index, and lifetime of some local variables | No |
| `LocalVariableTypeTable` | Additional generic signature info for locals when present | No |
| Other appropriately defined attributes | Other standard metadata and permitted extensions | Must not arbitrarily alter the core semantics of the code |

**`StackMapTable` is not the running operand stack.** It describes the **expected type state** at certain BCIs so the verifier can confirm control flow paths are valid. For example, an exception handler must receive a reference compatible with `Throwable` and cannot arbitrarily be treated as an `int` and fed into `iadd`.

In class-file major version 50 and above, if no explicit `StackMapTable` appears, the specification has an **implicit stack map** mechanism equivalent to an empty table; this does not mean the JVM skips verification. A class file with complex branches/handlers must have valid verification information according to the rules applicable to that class file version.

When `javac -g` is enabled, `LineNumberTable` and `LocalVariableTable` are usually more complete; when compiled without debug info, variable names may be absent even though the code still runs. Do not rely on the presence of `LocalVariableTable` to determine whether a class file is valid.

### Why Can Reading and Modifying a Class File Cause `VerifyError`?

If you write bytecode using a library or modify a `.class` file, you must ensure:

- Control flow paths use the operand stack with **the right types and the right number of slots**; merge branches are valid.
- `max_stack` and `max_locals` are sufficient for all valid execution paths.
- BCIs in branches, exception-table bounds, handler targets, and stack map frames are all valid.
- Instructions receive the correct operand/local types; do not read slots that do not yet have a valid type.
- `StackMapTable` (if required) matches the frame state at control targets.

Verification errors usually occur before the JVM runs the corresponding method; this differs from a runtime `ArithmeticException` created by the example and caught with `catch`. When debugging, read **the error message and BCI**, use `javap -v`, and cross-check descriptors, locals, the exception table, and stack map frames.

## 9. Exception Handling Across Multiple Methods

`exception_table[]` only contains handlers **of the method being examined**. When method A calls B:

```text
A calls B
  └── B executes an instruction that throws an exception
      ├── Does B have a matching handler within the BCI range? → run B's handler
      └── If not:
          └── exception propagates to A at the call site
              ├── Does A have a matching handler? → run A's handler
              └── No → continue to higher caller
```

Therefore, a `try/catch` in A can catch an exception arising deep inside B even though A's exception table only protects the BCI containing the invocation and does **not** list every instruction inside B.

At the bytecode level, `try-with-resources`, `finally`, synchronized code, and compiler-generated synthetic paths can make the exception table have more entries than the source shows. Do not assume "one `catch` in source always equals one entry", or see `catch_type=0` and assume the source author intended to catch every `Throwable`.

When an exception is transferred to a handler, the frame's operand stack is set to hold the exception object. The handler's code usually stores it into a local with `astore`; if the exception handler rethrows, you may see `aload` followed by `athrow`. The `astore` and `athrow` instructions reside in **`code[]`**, while the exception table only describes **the region and control transfer target**.

## 10. Common Limits and Misconceptions

| Misconception | Correct Understanding |
| --- | --- |
| "`max_stack` is the JVM thread stack size" | It is only the maximum **operand stack** depth of **one method frame**; `-Xss` is a different concept |
| "`max_stack` = number of live variables" | It counts temporary slots on the operand stack; locals have their own limit `max_locals` |
| "`max_locals` = number of named variables in source" | Counts local **slots**, including parameters, `this`, and compiler-created/reused variables; `long/double` require two slots |
| "Every method has `this` at slot 0" | Only instance methods; `static` methods have no receiver slot |
| "Two `long` parameters so `locals=2`" | Two `long`s occupy **4 slots** in total |
| "`code_length` = number of instructions in method" | It is the **number of bytes**; JVM instructions vary in length |
| "`Exception table` is the same as `throws`" | The exception table holds handlers in Code; the `Exceptions` attribute describes declared checked exceptions |
| "`end_pc` is still inside the `try` range" | `end_pc` is **exclusive**, protecting only BCIs in `[start_pc,end_pc)` |
| "Every handler has a non-zero `catch_type`" | A value of **0** is a catch-all handler |
| "The JVM searches handlers without order" | **The first matching entry** in the exception table determines handling |
| "`StackMapTable` is a runtime operand stack snapshot" | It is **verification types** information at BCIs |
| "Removing debug info makes the JVM lose exception-handling logic" | The logic resides in bytecode and the exception table; debug metadata serves a different function |
| "`javap` prints the Java source bytecode verbatim" | `javap` disassembles `code[]` into mnemonics; source has undergone compiler transforms/optimizations |
| "An abstract method has an empty `Code`" | `abstract`/`native` methods have no Code attribute |
| "Just increasing `max_stack` makes broken bytecode run" | Types, control flow, stack map frames, locals, and all other constraints must also be satisfied |

## 11. Workflow for Inspecting `Code` When Debugging a Class File

1. **Confirm the JDK and class-file version**: use `java -version`, `javac -version`; `javap -v MyClass` prints the file's `major version`. Java 17 is typically major 61.
2. **Select the right method**: distinguish name, descriptor, static/instance, constructor, and overloads. A class has multiple `Code` attributes.
3. **Read `stack=..., locals=..., args_size=...`**: calculate the needed slots, remembering `long/double` occupy two; receiver is at slot 0 only for instance methods.
4. **Trace `code[]` by BCI**: note operand stack/local inputs for each instruction on key branches.
5. **Read the exception table**: mark each `[from,to)` range and `target` on the disassembly. At `target`, the stack receives the exception object.
6. **Read `StackMapTable` and debug metadata when needed**: check verification states, line numbers, and local variable lifetimes; avoid treating them as source business logic.
7. **Distinguish error types**: `VerifyError`/`ClassFormatError` are class file validity/linking issues; exceptions thrown by running code like `ArithmeticException` are runtime logic issues.
8. **Cross-check with the right edition of the spec**: do not infer something is mandatory just because `javac` of one release prints that exact sequence.

## 12. Review Questions

**Question 1:** Does `max_stack=4` in `sumLong(long,long)` mean there are four Java variables?

No. There are two `long` arguments, each occupying two slots on the operand stack; when both operands are present simultaneously, the depth is four **slots**.

**Question 2:** The instance method `increment(int value)` has one parameter variable, so is the minimum `max_locals` equal to 1?

No. Local slot 0 holds `this`, and slot 1 holds the `value` parameter; at least two slots are needed.

**Question 3:** Does the handler `from=0,to=3,target=4` catch an exception occurring at BCI 3?

No. BCI 3 is outside the range because `to` is exclusive; it catches instructions with BCI in `[0,3)`.

**Question 4:** Does `catch_type=0` mean no exception is caught?

No. On the contrary, it is a **catch-all handler**, which the compiler can use for cleanup/`finally`.

**Question 5:** If `LocalVariableTable` is not present, does the method have no local variables?

No. `max_locals` and load/store instructions are sufficient for execution. `LocalVariableTable` is only optional name/type/lifetime metadata.

**Question 6:** When `idiv` throws an exception, must there be an `athrow` right after `idiv` to use the exception table?

No. The JVM itself throws `ArithmeticException` for integer division by 0; the exception table is evaluated by the location of the instruction that raised the exception.

**Key Takeaway:** `Code_attribute` is the description of **one method** containing frame limits (`max_stack`, `max_locals`), bytecode (`code[]`), handlers (`exception_table[]`), and nested metadata. Reading the **slot** counts, **BCI**, **[start_pc,end_pc)** range, and handler order accurately connects Java source, JVM execution, and verification errors on a solid basis.
