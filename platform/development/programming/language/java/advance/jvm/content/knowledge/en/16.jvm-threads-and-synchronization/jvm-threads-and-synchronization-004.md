# `monitorenter`, `monitorexit`, and Methods with the `ACC_SYNCHRONIZED` Flag

## 1. The Big Picture: How Does the JVM Execute Java `synchronized`?

Java provides two forms of intrinsic synchronization syntax:

- **Block:** `synchronized (lock) { ... }` — locks the monitor associated with **the object reference produced by the `lock` expression** for the duration of the block.
- **Method:** `synchronized void method() { ... }` or `static synchronized void method() { ... }` — the monitor lock is implicitly determined by **the receiver `this`** (instance method) or **the `Class` object** of the declaring class (static method).

Both follow a single **monitor model**: one thread owns the monitor at a time, it is **reentrant**, and an unlock–lock on the **same monitor** has memory-ordering effects according to the Java Memory Model (JMM).

However, they **differ in how they are represented in the class file**:

| Java source | Typical bytecode/class file representation | Who handles enter/exit? |
| --- | --- | --- |
| `synchronized (obj) { body(); }` | `monitorenter`, `monitorexit`, and appropriate exception handlers in `Code` | Instructions and control-flow generated by `javac` |
| `public synchronized void action()` | `method_info.access_flags` contains `ACC_SYNCHRONIZED`; usually **no** `monitorenter`/`monitorexit` just for the method declaration itself | The JVM automatically enters on invoke and exits when the method completes |
| `public static synchronized void action()` | Also `ACC_SYNCHRONIZED` | The JVM uses the monitor of the `Class` object representing the declaring class |
| `new ReentrantLock()` and `lock()/unlock()` | Ordinary library method calls; **no** `monitorenter` just because it is a lock | The `java.util.concurrent.locks` library and the JVM/OS primitives it uses |

This is the key point when reading `javap`: **not seeing the `monitorenter` opcode in a `synchronized` method does not mean the method is unsynchronized**. The `ACC_SYNCHRONIZED` flag itself is how the JVM recognizes and applies the implicit lock.

This article follows **JVMS Java SE 17**, along with specific notes on HotSpot Java 17. Java/JVMS defines the effects and class file structure; how HotSpot optimizes monitors using fast paths, spinning, inflation, JIT lock elimination, etc., are implementation details that can change across versions.

## 2. What Is a Monitor?

A monitor is a synchronization mechanism associated with an object, which can be modeled via:

- **Owner:** the thread currently owning the monitor, or no owner.
- **Entry count (reentrancy depth):** the number of times the owner has entered minus the number of matching exits.
- **Entry contention:** other threads attempting to acquire the monitor must wait until the monitor can be acquired.
- **Wait set:** threads that have validly called `Object.wait()` on the monitor and are waiting to be notified/reacquire the lock according to the `wait` condition.

```text
                 Object L / monitor(L)
                 +--------------------+
Thread A ------> | owner = A          |
                 | entry count = 2    |
Thread B --X-->  | B is waiting to enter |
                 | wait set: ...      |
                 +--------------------+

A has entered twice => must exit twice to release ownership.
B cannot enter while the monitor is still owned by A.
```

The fields in the diagram are a **semantic model**, not a literal Java object with `owner` and `entryCount` fields that applications are allowed to read. The JVM can manage monitor objects/metadata in various ways.

### Monitor Ownership Is by Object Identity, Not Variable Name

```java
Object first = new Object();
Object alias = first;
synchronized (first) {
    synchronized (alias) {
        // Reentering the same monitor.
    }
}
```

This is a **Java fragment** that can be placed inside a method. The two references have different names, but `first == alias`, so the two synchronized statements are a reentry into **the same monitor**.

Conversely, two different objects, even if `equals` returns `true`, still have **separate monitors**, because intrinsic locking is based on **reference identity**, not `equals` or `hashCode`. `System.identityHashCode` is also not the monitor address or raw memory address.

## 3. The `monitorenter` Mechanism

In JVMS 17, `monitorenter` is a JVM instruction opcode:

| Property | Details |
| --- | --- |
| Mnemonic | `monitorenter` |
| Opcode | `194`, hexadecimal `0xC2` |
| Operand stack before | `..., objectref` |
| Operand stack after | `...` |
| Effect | Attempts to acquire the monitor of `objectref`; pops the reference from the operand stack |

Operational model:

1. If `objectref == null`, the instruction throws `NullPointerException`.
2. If the monitor currently has no owner, the current thread acquires it; entry count becomes 1.
3. If the current thread **already** owns that monitor, this is a reentrant enter; entry count is incremented.
4. If another thread is currently the owner, the current thread must wait until it can acquire the monitor according to the VM mechanism; there is no FIFO guarantee.

```text
Operand stack before:
  [..., objectref L]
                  ^
                  top

monitorenter

Operand stack after:
  [...]

Monitor(L):
  entry count 0 -> owner T, count 1
  or T already owner -> count incremented
  or another thread owner -> T waits to acquire
```

You should not interpret "bytecode pops `objectref`" as meaning GC no longer holds a reference to the lock during the synchronized block. The compiler/JVM must properly manage **roots/lifetimes** and exception exit paths; `javac` typically stores the lock reference in a **hidden local variable** before `monitorenter` to reuse it at `monitorexit`.

## 4. The `monitorexit` Mechanism

`monitorexit` is the counterpart opcode:

| Property | Details |
| --- | --- |
| Mnemonic | `monitorexit` |
| Opcode | `195`, hexadecimal `0xC3` |
| Operand stack before | `..., objectref` |
| Operand stack after | `...` |
| Effect | Pops the reference, decrements the entry count of the monitor owned by the thread |

If the decrement brings the entry count to 0, the thread **is no longer the owner** and other threads can attempt to acquire the monitor.

Important exceptions according to JVMS:

- `monitorexit` with `objectref == null` → `NullPointerException`.
- If the executing thread **does not own the monitor** of that object → `IllegalMonitorStateException`.
- A JVM that enforces **structured locking** checks may throw `IllegalMonitorStateException` when structured locking rules are violated in the cases described by the specification.

```text
Thread T has entered L twice:
  owner = T, entryCount = 2

monitorexit(L):
  owner = T, entryCount = 1
  (monitor not yet released for other threads)

monitorexit(L):
  entryCount = 0
  owner = none
  (other threads can acquire)
```

**You cannot exit "once to be done with it"** when nested synchronized blocks have entered the same monitor multiple times. The compiler and VM must preserve reentrancy depth along all valid execution paths.

### Structured Locking

JVMS `2.11.10` describes **structured locking**: within an invocation, monitor exits must match monitor enters, with no more exits than enters; the state must be balanced when the invocation completes normally or abruptly. A JVM **is permitted, but not required**, to enforce all of these rules in the manner stated by the specification for general bytecode.

In valid Java source, `synchronized` blocks/methods have matching enter/exit guarantees provided by the compiler and JVM. **Do not hand-write bytecode that performs `monitorexit` on an unowned monitor**; doing so can throw `IllegalMonitorStateException` and is not a valid "advanced" lock management technique.

## 5. Why Must the Compiler Generate Bytecode-Level `try/finally`?

Suppose:

```java
void work(Object lock) {
    synchronized (lock) {
        doWork();
    }
}
```

This is a **method fragment**, depending on `doWork()` defined externally. Java semantics require the monitor to be released **whether `doWork()` completes normally or throws an exception**. Therefore, the bytecode of a synchronized block has:

1. Reading and holding the reference of the object used as the lock.
2. `monitorenter` before the body.
3. `monitorexit` on the normal path.
4. An **exception handler** to execute `monitorexit` and then rethrow the throwable on the abrupt path.

Illustrative diagram (BCIs are not real `javap` offsets of a specific file):

```text
aload lock
dup
astore monitorLocal
monitorenter

  [protected region]
  invoke doWork

aload monitorLocal
monitorexit
goto NORMAL_END

CATCH_ALL:
  astore thrown
  aload monitorLocal
  monitorexit
  aload thrown
  athrow

NORMAL_END:
  return
```

The exception table in the class file routes throwables from the body to the appropriate handler. `javac` may also emit an additional handler for exceptions occurring in the cleanup path depending on bytecode version/control flow.

### Why Isn't "Putting One `monitorexit` at the End of the Method" Enough?

Because the body can:

- `return` early.
- `break` or `continue` out of the block.
- `throw` directly.
- Encounter an exception from a method call, array access, field access, cast, etc.
- Complete through a different conditional branch.

Every valid exit path must preserve monitor exit semantics. At the class-file level, the compiler solves this with appropriate branches, handlers, and exit instructions; you cannot just look at a single `return` line in Java source and assume the lock gets stuck.

## 6. `synchronized` Methods: The `ACC_SYNCHRONIZED` Flag, No Explicit Opcode Needed

A method declared as:

```java
public synchronized int read() {
    return count;
}
```

This is a **fragment** inside a class with a field `count`.

Typically `javac` does not insert `monitorenter` or `monitorexit` into `Code` solely because of the method's `synchronized` modifier. Instead, `method_info.access_flags` has the bit:

```text
ACC_SYNCHRONIZED = 0x0020
```

When invoking a method carrying this flag, the JVM **automatically** enters the monitor before executing the method and **automatically** exits when the method completes **normally or abruptly**. If the method throws an exception out to the caller, the monitor is still released when the invocation ends.

### Method Flag vs. Field or Class Flag

- `ACC_SYNCHRONIZED` is a **method access flag** in `method_info` (JVMS §4.6), not a Java annotation.
- `ACC_SYNCHRONIZED` does not mean "every method in the class shares a single global monitor."
- This flag does not make nested object fields thread-safe.
- The JVM has certain flags/locking mechanisms outside the class file; they do not change the public bytecode meaning of the method flag.

### Which Monitor Is Used?

| Declaration | Monitor associated with | Equivalent in meaning |
| --- | --- | --- |
| `synchronized void inc()` | `this` receiver object | `synchronized (this) { body }` |
| `static synchronized void reset()` | `Class` object representing the declaring class | `synchronized (Counter.class) { body }` |

**Difference:** two instances `Counter a` and `Counter b` have separate monitors for `a.inc()` and `b.inc()`. Meanwhile, `Counter.reset()` uses the monitor of `Counter.class`, and does not acquire the monitor of `a` or `b`.

If a non-`final` class is subclassed, be careful when writing `getClass()` yourself: the runtime class object can be a different subclass than the class **declaring the static synchronized method**. Do not arbitrarily substitute `getClass()` for `Counter.class` when interpreting static monitor semantics.

## 7. Runnable Java 17 Example: Inspecting Block, Instance Method, and Static Method

Create the file **`MonitorBytecodeDemo.java`**:

```java
public class MonitorBytecodeDemo {
    private int count;

    public synchronized void incrementMethod() {
        count++;
    }

    public void incrementBlock() {
        synchronized (this) {
            count++;
        }
    }

    public synchronized int getCount() {
        return count;
    }

    public static synchronized String staticMarker() {
        return "class-monitor";
    }

    public static void main(String[] args) {
        MonitorBytecodeDemo counter = new MonitorBytecodeDemo();

        counter.incrementMethod();
        counter.incrementBlock();

        boolean holds;
        synchronized (counter) {
            holds = Thread.holdsLock(counter);
            counter.incrementMethod(); // Reentrant: same thread already holds the monitor.
        }

        System.out.println("count=" + counter.getCount());
        System.out.println("holdsInside=" + holds);
        System.out.println("holdsOutside=" + Thread.holdsLock(counter));
        System.out.println("static=" + staticMarker());
    }
}
```

Compile/run:

```bash
javac --release 17 MonitorBytecodeDemo.java
java MonitorBytecodeDemo
```

**Exact stdout:**

```text
count=3
holdsInside=true
holdsOutside=false
static=class-monitor
```

Explanation:

- `incrementMethod` and `incrementBlock` both protect the same field `count` using the receiver's monitor.
- Upon entering `synchronized(counter)`, the thread holds `counter`'s monitor; calling `counter.incrementMethod()` is still valid because intrinsic locks are **reentrant**.
- `Thread.holdsLock(counter)` returns `true` inside the region where the current thread holds the monitor, and `false` after exiting the region (with no other locks held by that thread).
- `staticMarker` is a static synchronized method, so it uses `MonitorBytecodeDemo.class`; it does not participate in `counter`'s own lock.

### Inspecting with `javap`

```bash
javap -c -v -p MonitorBytecodeDemo
```

In `incrementMethod`, `getCount`, and `staticMarker`, look for the method flags line containing **`ACC_SYNCHRONIZED`**. In `incrementBlock`, look for the **`monitorenter`**, **`monitorexit`** instructions and the **Exception table** section.

A **structural excerpt, not verbatim output with measured offsets/indices**:

```text
public synchronized void incrementMethod();
  flags: (0x0021) ACC_PUBLIC, ACC_SYNCHRONIZED
  Code:
    ... getfield count ...
    ... putfield count ...
    return

public void incrementBlock();
  flags: (0x0001) ACC_PUBLIC
  Code:
    ... aload_0 ...
    ... monitorenter ...
    ... getfield count ...
    ... putfield count ...
    ... monitorexit ...
    ... monitorexit ...
    ... athrow ...
  Exception table:
    ... any ...
```

The `...` are **omission markers**, not valid Java opcodes or a complete dump. Class-file constant pool indexes, BCI offsets, stack map frames, and exception-table boundaries must be viewed directly with `javap`. What is reliable here is **the pattern distinguishing flag versus opcodes**.

## 8. Reading `method_info` and the `Code` Attribute in the Right Order

A method in a class file has information like:

```text
method_info:
  access_flags: ACC_PUBLIC | ACC_SYNCHRONIZED
  name_index
  descriptor_index
  attributes:
    Code {
      max_stack, max_locals
      code[]
      exception_table
      ...
    }
```

This is a diagram, not actual decoded binary class file data. Things to check:

1. `ACC_SYNCHRONIZED` resides in **`method_info.access_flags`**.
2. `Code` contains the business bytecode, but does not need to contain `monitorenter`/`monitorexit` corresponding to the method-level lock.
3. For a `synchronized` block, the compiler emits explicit instructions **in `code[]`**.
4. Exception handlers in the block's `Code.exception_table` guard monitor release when the body throws an exception.
5. If a method both has `ACC_SYNCHRONIZED` and contains a `synchronized(other)` block, **two different monitors** may be held (the method monitor + the block monitor).

### Opcodes and Flags Are Not the Same

- `monitorenter = 0xC2`, `monitorexit = 0xC3` are **1-byte opcodes** in the JVM instruction stream.
- `ACC_SYNCHRONIZED = 0x0020` is a **bitmask in the method's metadata structure**.
- Do not look for bit `0x0020` in `Code` and conclude it is a lock instruction.
- Do not look for `monitorenter` in every method marked synchronized and report the bytecode as broken.

## 9. Exceptions in a Synchronized Block: Why Is the Lock Still Released?

Create the file **`MonitorExceptionDemo.java`**:

```java
public class MonitorExceptionDemo {
    private final Object lock = new Object();

    public void failInBlock() {
        synchronized (lock) {
            throw new IllegalStateException("block");
        }
    }

    public synchronized void failInMethod() {
        throw new IllegalStateException("method");
    }

    public synchronized String recover() {
        return "recovered";
    }

    public static void main(String[] args) {
        MonitorExceptionDemo demo = new MonitorExceptionDemo();

        try {
            demo.failInBlock();
        } catch (IllegalStateException e) {
            System.out.println("caughtBlock=" + e.getMessage());
        }

        synchronized (demo.lock) {
            System.out.println("blockReentered="
                    + Thread.holdsLock(demo.lock));
        }

        try {
            demo.failInMethod();
        } catch (IllegalStateException e) {
            System.out.println("caughtMethod=" + e.getMessage());
        }

        System.out.println("methodReentered=" + demo.recover());
    }
}
```

```bash
javac --release 17 MonitorExceptionDemo.java
java MonitorExceptionDemo
```

**Deterministic stdout:**

```text
caughtBlock=block
blockReentered=true
caughtMethod=method
methodReentered=recovered
```

The code demonstrates two mechanisms:

- `failInBlock` has its monitor acquired via a block; the compiler generates a release path even when `IllegalStateException` escapes.
- `failInMethod` carries the `ACC_SYNCHRONIZED` method flag; the VM guarantees implicit exit when the method terminates abruptly.
- The monitor can be reacquired after the exception; it does not stay permanently stuck because of that exception.

**Testing limitation:** the example runs on a single thread, so `blockReentered=true` by itself does not prove another thread will never be blocked if there is a bug. The primary proof of release on every control path is **the language/JVMS rules and bytecode cleanup logic**. Do not use "it ran once" to claim concurrent code is always free of races/deadlocks.

## 10. How Do `athrow`, `return`, and Implicit Release Differ?

For a method with `ACC_SYNCHRONIZED`:

- Before the method body runs, the VM enters the corresponding monitor.
- On **normal return**, the VM ensures the invocation's monitor is exited.
- On **abrupt completion** due to an unhandled exception in the method, the VM ensures exit before propagating the exception to the caller.
- The body bytecode may contain `ireturn`, `areturn`, `return`, or `athrow`, yet **the method lock does not need to be represented by an explicit `monitorexit` opcode at each point**.

For a synchronized block:

- There is `monitorenter` before the body.
- `monitorexit` on normal exit.
- `monitorexit` via a bytecode exception-handling path on abrupt exit.
- The Java compiler must ensure **the right lock object** is released; if the `lock` expression's value is reassigned in a Java variable outside/inside the block, the monitor object acquired is still the object saved at enter time.

Example:

```java
Object lock = new Object();
Object original = lock;
synchronized (lock) {
    lock = new Object();
    System.out.println(Thread.holdsLock(original)); // true
}
```

This is a **fragment** inside a method. The `lock` variable now points to a different object, but the block still owns the monitor of **`original`** until it finishes. It does not mean "reassigning the reference unlocks immediately."

## 11. Reentrancy in Detail: One Thread Entering the Same Monitor Multiple Times

Java's intrinsic locks are **reentrant**. Suppose:

```java
class Nested {
    synchronized void outer() {
        inner();
    }

    synchronized void inner() {
        // Same receiver this, so reentering the same monitor.
    }
}
```

This is an illustrative class, without `main`.

Timeline:

```text
T calls outer() on obj
  enter monitor(obj): depth 0 -> 1

outer() calls inner() on the same obj
  enter monitor(obj): depth 1 -> 2

inner() returns
  implicit exit: depth 2 -> 1

outer() returns
  implicit exit: depth 1 -> 0

Monitor of obj is available for other threads.
```

**Reentrancy is not fairness.** Java intrinsic monitors do not guarantee which waiting thread will be chosen next, do not provide `tryLock(timeout)` like `ReentrantLock`, and entering a monitor via `synchronized` syntax does not provide an interruptible lock acquisition mechanism like `lockInterruptibly()`.

Avoid writing code that assumes a thread in `BLOCKED` waiting for an intrinsic monitor will automatically stop waiting because the thread was `interrupt()`ed. **Interrupting `Object.wait` is a different matter**: a waiting thread can throw `InterruptedException` after reacquiring the monitor.

## 12. Instance `synchronized` vs. `static synchronized`: They Do Not Lock Each Other by Default

Consider:

```java
class Ledger {
    private int instanceCount;
    private static int globalCount;

    synchronized void incrementInstance() {
        instanceCount++;
    }

    static synchronized void incrementGlobal() {
        globalCount++;
    }
}
```

This is a class fragment. The monitor of `ledger.incrementInstance()` is the object `ledger`; the monitor of `Ledger.incrementGlobal()` is **`Ledger.class`**.

Two threads can:

- Thread A owns the monitor of `ledger`.
- Thread B simultaneously owns the monitor of `Ledger.class`.
- Both execute their respective methods without blocking each other **because the monitors are different**, if there is no other synchronization.

Do not use an instance synchronized method to protect a static shared mutable field that other threads can modify through a static synchronized method — they **do not automatically use the same lock**.

### Two Different Instances Are Also Two Monitors

```text
Ledger a     -> monitor(a)
Ledger b     -> monitor(b)
Ledger.class -> monitor(Ledger.class)

a.incrementInstance() and b.incrementInstance() can run in parallel.
a.incrementInstance() and Ledger.incrementGlobal() can run in parallel.
```

To protect shared state, choose **one consistent locking strategy** and ensure all relevant reads/writes follow that strategy.

## 13. Java Memory Model: Monitor Exit Has Visibility Meaning

`synchronized` does not only protect **mutual exclusion**. It also establishes memory-ordering relationships according to the JMM.

For **the same monitor M**, an **unlock of M** in thread A **synchronizes-with** a subsequent **lock of M** in thread B; from the happens-before rules, writes in A before the unlock can become properly visible to reads in B after the lock when data accesses are properly synchronized.

```text
Thread A                          Thread B

lock(M)
sharedValue = 42
unlock(M) -------- sync-with ----> lock(M)
                                  read sharedValue => sees writes
                                  unlock(M)

Condition: same M and proper ordering.
```

**It is not "every unlock in A synchronizes-with every lock in B"**. The monitor identity must be the same, and the order of synchronization actions must match. Locking does not fix **a data race** if another thread reads/writes the same mutable state outside that synchronization mechanism.

### `volatile` vs. `synchronized`

- `volatile` provides visibility/ordering semantics on a specific variable; an expression like `count++` does not automatically become atomic just because `count` is volatile.
- `synchronized` provides mutual exclusion **and** monitor-based happens-before if threads use the same lock.
- `AtomicInteger` performs atomic operations via its own API.
- `ReentrantLock` has memory synchronization effects defined by the Java concurrency API, but is not implemented using the two bytecode opcodes `monitorenter`/`monitorexit` for that lock API.

Do not equate GC write barriers/JIT memory barriers with Java source `synchronized` statements: they have different purposes/semantics.

## 14. Java 17: Two Threads Incrementing a Counter Safely

Create the file **`MonitorCounterDemo.java`**:

```java
public class MonitorCounterDemo {
    private int counter;

    public synchronized void increment() {
        counter++;
    }

    public synchronized int value() {
        return counter;
    }

    public static void main(String[] args)
            throws InterruptedException {
        MonitorCounterDemo shared = new MonitorCounterDemo();

        Runnable job = () -> {
            for (int i = 0; i < 10_000; i++) {
                shared.increment();
            }
        };

        Thread a = new Thread(job, "worker-A");
        Thread b = new Thread(job, "worker-B");

        a.start();
        b.start();
        a.join();
        b.join();

        System.out.println("expected=20000");
        System.out.println("actual=" + shared.value());
    }
}
```

```bash
javac --release 17 MonitorCounterDemo.java
java MonitorCounterDemo
```

**Exact stdout if threads complete normally:**

```text
expected=20000
actual=20000
```

Each `increment` call must acquire/release the monitor of **the same object `shared`**; therefore `counter++` (read, add, write) is inside a mutually exclusive critical section. `value` also uses that monitor, even though in this example `join()` already ensures the workers finish before main reads.

If `synchronized` is removed from `increment`, `counter++` is no longer atomic and can suffer **lost updates**; however, **there is no guarantee** every run will print less than 20,000 — a race might not manifest on a single trial. What is true is that the program then lacks proper synchronization to guarantee always getting 20,000.

### Code Review Checklist

- Guard **both reads and writes** of shared mutable state with the same monitor or a valid synchronization strategy.
- Do not call `counter++` "atomic" just because Java has an add opcode; bytecode typically separates load/compute/store.
- If a lock is held for a long time, throughput can drop due to contention; choose an appropriate granularity.
- Do not manually optimize away `synchronized` on shared state.

## 15. How Do `Object.wait`, `notify`, and `notifyAll` Relate to Monitors?

Beyond enter/exit, Java monitors involve **wait sets**. When a thread owns the monitor of object `lock`, it can call:

- `lock.wait()`: temporarily **relinquishes ownership of `lock`'s monitor**, waits for notification/interruption/timeout according to the overload/semantics; before returning or throwing as appropriate, the thread **reacquires the monitor**.
- `lock.notify()`: selects one thread waiting on **the same `lock`'s** wait set to wake up according to VM rules; **does not release the monitor immediately**.
- `lock.notifyAll()`: wakes up all threads in that object's wait set so they contend to reacquire.
- These operations require the current thread to own the appropriate monitor; otherwise → `IllegalMonitorStateException`.

**There is no separate `wait` or `notify` JVM opcode**. They are methods of `java.lang.Object` whose implementation coordinates with the JVM's monitor support.

### Why Always Use `while` Instead of `if` Around `wait`?

A thread being woken up does not mean the business condition has become true: there can be a **spurious wakeup**, another thread may have changed the state, or `notifyAll` may have woken multiple threads at once. Always check the condition in a loop **while holding the monitor**.

```java
synchronized (lock) {
    while (!ready) {
        lock.wait();
    }
    // ready is true at the moment the lock is held
}
```

This is a fragment inside a method that declares/propagates `InterruptedException`, with an appropriate `ready` field and `lock` object.

### `Thread.sleep` vs. `Object.wait`

`Thread.sleep(...)` **does not release monitors** currently owned by the thread. Sleeping for 1 second inside a `synchronized` block can keep other threads waiting for the same monitor for that entire duration. `Object.wait()` releases **the monitor being waited on**, then reacquires it before continuing; it does not automatically release any other monitors the thread also holds.

## 16. Java 17: A `wait`/`notifyAll` Example Independent of Startup Order

Create the file **`MonitorWaitDemo.java`**:

```java
public class MonitorWaitDemo {
    static final class Gate {
        private boolean open;

        synchronized void await() throws InterruptedException {
            while (!open) {
                wait();
            }
        }

        synchronized void signal() {
            open = true;
            notifyAll();
        }
    }

    public static void main(String[] args)
            throws InterruptedException {
        Gate gate = new Gate();
        Thread worker = new Thread(() -> {
            try {
                gate.await();
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                return;
            }
            System.out.println("worker=passed");
        }, "waiter");

        worker.start();
        gate.signal();
        worker.join();

        System.out.println("main=done");
    }
}
```

```bash
javac --release 17 MonitorWaitDemo.java
java MonitorWaitDemo
```

**Stdout when there is no external interruption:**

```text
worker=passed
main=done
```

- If the worker has not yet entered `await()` when main calls `signal()`, the `open` field has already been set to true; the worker entering later still passes through, **no signal is lost**.
- If the worker is already in `wait()`, main can acquire `Gate`'s monitor after the waiter releases it, set `open=true`, and call `notifyAll()`; the worker must reacquire the monitor before returning from `wait()`.
- `signal()` and `await()` are instance synchronized methods; the monitor is `gate` (the receiver).
- `join()` causes the main line to print **after** the worker line on the normal execution path.

**Note:** this is a synchronization correctness demo; do not use it to argue that a `notifyAll` event corresponds to a specific JVM opcode. Thread scheduling can vary while the two output lines still have a deterministic order thanks to `join()`.

## 17. `IllegalMonitorStateException` and `NullPointerException`

Two commonly confused errors:

### Calling `wait`/`notify` Without Holding the Monitor

```java
Object lock = new Object();
try {
    lock.notify();
} catch (IllegalMonitorStateException expected) {
    System.out.println("not-owner");
}
```

This fragment is runnable when placed in `main`. The result is `not-owner` because the caller does not hold `lock`'s monitor. To do it properly, call:

```java
synchronized (lock) {
    lock.notifyAll();
}
```

### Null Lock Expression

```java
Object lock = null;
synchronized (lock) {
    System.out.println("never");
}
```

This is a fragment. Upon monitor enter on null, the runtime throws `NullPointerException`; the body does not execute. There is no special monitor representing `null`.

### `IllegalMonitorStateException` vs. Lock Contention

A valid thread waiting to acquire a monitor held by another thread **does not by default throw `IllegalMonitorStateException`** just for waiting. This exception is related to invalid monitor operations/ownership, such as `notify()` outside synchronized and `monitorexit` when not the owner.

## 18. A Synchronized Method Does Not Mean Locking All State Inside the Object Graph

Suppose the class:

```java
class Basket {
    private final java.util.List<String> items =
            new java.util.ArrayList<>();

    synchronized void add(String item) {
        items.add(item);
    }

    java.util.List<String> rawItems() {
        return items;
    }
}
```

This is a class fragment. Even though `add` is synchronized, the `rawItems` method directly returns a mutable list. A caller can modify the list **without holding the Basket monitor**, corrupting data or creating a race.

**A monitor lock only protects actions that coordinate using that exact monitor.** It does not automatically change the thread-safety of every object referenced inside, nor does it prevent external code from holding a mutable reference and misusing it.

A good API can:

- Not expose mutable internal representations directly.
- Return an appropriate immutable snapshot/copy.
- Require all operations on state to be properly synchronized.
- Use appropriate collections or concurrent abstractions instead of overcomplicating the monitor protocol.

## 19. Deadlock: Two Monitors Locked in Opposite Order

Each `synchronized` can be locally correct, yet the system can still **deadlock** if two threads hold locks in opposite orders:

```text
Thread A:
  synchronized(L1) {
    synchronized(L2) { ... }
  }

Thread B:
  synchronized(L2) {
    synchronized(L1) { ... }
  }

A holds L1, waits for L2.
B holds L2, waits for L1.
=> cycle of wait-for dependencies.
```

This is a conceptual example, **not a program built to intentionally hang the JVM**.

Mitigations:

- Define and follow a consistent **global lock ordering**.
- Keep critical sections short; avoid calling callbacks, external code, or long I/O while holding locks.
- Do not lock on public objects such as interned strings/class literals unless the ownership policy is explicit.
- Use `ReentrantLock.tryLock` or higher-level abstractions if the problem requires timeouts/interruptible acquisition.
- Use thread dumps to verify owners and blocked dependencies.

**Reentrant does not mean "cannot deadlock"**. Reentrancy only allows the same thread to re-enter **the same monitor**; it does not resolve cycles between **two different monitors**.

## 20. Thread Dumps: How Does `BLOCKED` Differ from `WAITING`?

When a Java thread attempts to enter an intrinsic monitor already held by another thread, it can appear in the **`BLOCKED`** state. When it has called `Object.wait()` and is waiting on the wait set, it is typically seen in **`WAITING`** (or **`TIMED_WAITING`** with a timeout), depending on the situation.

Summary table:

| Situation | Typical state | Monitor role |
| --- | --- | --- |
| Waiting to enter `synchronized(lock)` because another thread holds the lock | `BLOCKED` | Waiting to acquire ownership |
| Calling `lock.wait()` without timeout | `WAITING` | Has released `lock`'s monitor and is waiting to reacquire per rules |
| Calling `lock.wait(timeout)` | `TIMED_WAITING` | Timed wait |
| Calling `Thread.sleep(timeout)` | `TIMED_WAITING` | **Does not release** held locks |
| `LockSupport.park` | `WAITING` | Parking differs from monitor wait set |
| Running code not waiting on a monitor | Possibly `RUNNABLE` | Do not conclude there is no contention from a single snapshot |

Thread state is a **snapshot**; a thread can change state very quickly. Use multiple thread dumps and a timeline when investigating production.

### Java 17 Tools

```bash
jcmd <PID> Thread.print -l
jstack -l <PID>
```

`<PID>` is a placeholder for a real running Java process to which you have attach permission. `jcmd`/`jstack` can print monitor ownership, blocked/waiting threads, and deadlock information depending on build/options. A thread dump typically displays `- locked <...>` or `- waiting to lock <...>`; object IDs in diagnostic output **are not stable Java API identities** to use in application logic.

If you encounter a **Java-level deadlock**, take multiple snapshots, inspect which threads are holding and waiting on which monitors, and look for opposite acquisition orders in the source. Do not conclude every `WAITING` thread is deadlocked; idle thread pools, valid `Object.wait`, and `LockSupport.park` also show `WAITING`.

## 21. Why Can `synchronized` Be Faster Than Expected?

HotSpot has various optimizations and implementation techniques depending on the release:

- Fast paths for uncontended monitor acquisition.
- JIT inlining and compiler optimizations around monitor regions.
- **Escape analysis / lock elimination** when the compiler proves a lock object cannot be observed by another thread in the compiled graph.
- Mechanisms for managing monitor metadata, inflation/deflation, and slow paths under contention.
- Optimizations for nested/reentrant locking or code motion while preserving Java semantics.

On **HotSpot Java 17**, do not copy locking descriptions from JDK 8 or JDK 25 as a guaranteed layout: biased locking was **disabled by default in releases prior to Java 17**, and monitor algorithms and object headers can change between versions.

### Lock Elimination Is Different from Removing `synchronized` from Source

```java
static int localOnly(int a) {
    Object privateLock = new Object();
    synchronized (privateLock) {
        return a + 1;
    }
}
```

This method fragment has a private lock that does not escape in source; C2 **may** eliminate the monitor operations and even the allocation if eligible. However, the compiler must still preserve semantics; **there is no guarantee** the lock will be eliminated on every path/JDK build.

This does not grant permission to manually remove `synchronized` in application shared-state logic. For genuinely shared objects, removing the monitor can cause a data race.

## 22. Does `monitorenter`/`monitorexit` in Bytecode Mean the JIT Always Executes a Physical Lock/Unlock?

No. Bytecode defines **JVM semantics**; the HotSpot interpreter/JIT is allowed to optimize the implementation:

- The interpreter may perform entry/exit via appropriate VM/runtime mechanisms.
- C1/C2 generate behaviorally equivalent machine code, not always a runtime call for every `monitorenter`.
- C2 can eliminate a monitor if proven thread-confined/no observable synchronization effect, or use a fast path.
- Some monitors may be inflated under contention/special operations; internal lock state is not something Java source is allowed to depend on.
- Deoptimization must preserve logical monitor ownership/state when switching execution representations.

Therefore, `javap -c` showing `monitorenter` does not prove the actual native instructions always include a hardware lock instruction at that exact BCI. To inspect machine code, you need appropriate JIT diagnostics, profiling, and builds—not `javap` as a native disassembler.

### Do Not Confuse `monitorexit` with Memory Reclamation

`monitorexit` only concerns monitor ownership/synchronization. It **does not delete the object, does not trigger GC, does not close files/sockets**, and does not automatically release resources inside the critical section. `synchronized` does not replace `try-with-resources` for I/O resources.

## 23. Why Can Holding a Lock While Calling Another Method Be Dangerous?

Example:

```java
synchronized (lock) {
    callback.run();
}
```

This is a fragment. You still own `lock`'s monitor during `callback.run()`. If the callback:

- Waits on another lock in a dangerous order.
- Performs blocking I/O or a network call.
- Calls code that may re-enter the same object under a complex protocol.
- Calls `wait` on another monitor while still holding `lock`.
- Holds the lock for a long-running task.

then contention or deadlock risk increases. **A callback re-entering the same lock** is itself valid due to reentrancy, but a protocol with multiple locks can still deadlock.

Good design typically:

1. Collects a snapshot under the lock.
2. Releases the lock.
3. Invokes external callbacks outside the protected region if business invariants allow.
4. Uses immutable messages/queues for async processing when appropriate.

Do not automatically "move every callback outside `synchronized`" if state invariants require an atomic operation; identify the exact atomicity contract first, then refactor.

## 24. Java 17: Static Monitor and Instance Monitor Are Truly Independent

Create the file **`ClassMonitorDemo.java`**:

```java
public class ClassMonitorDemo {
    private int instanceValue;
    private static int classValue;

    public synchronized void updateInstance() {
        instanceValue++;
    }

    public static synchronized void updateClass() {
        classValue++;
    }

    public static void main(String[] args) {
        ClassMonitorDemo obj = new ClassMonitorDemo();

        boolean instanceHeld;
        boolean classHeld;
        synchronized (obj) {
            instanceHeld = Thread.holdsLock(obj);
            classHeld = Thread.holdsLock(ClassMonitorDemo.class);
        }

        obj.updateInstance();
        updateClass();

        System.out.println("instanceHeld=" + instanceHeld);
        System.out.println("classHeld=" + classHeld);
        System.out.println("instanceValue=" + obj.instanceValue);
        System.out.println("classValue=" + classValue);
    }
}
```

```bash
javac --release 17 ClassMonitorDemo.java
java ClassMonitorDemo
```

**Stdout:**

```text
instanceHeld=true
classHeld=false
instanceValue=1
classValue=1
```

Inside `synchronized(obj)`, the thread holds `obj`'s monitor, but **does not** thereby own `ClassMonitorDemo.class`. The two `update...` methods then update separate fields respectively. This example helps distinguish monitors; it **is not a concurrency stress test**, nor does it prove that all fields/static state are inherently thread-safe when accessed by multiple unsynchronized methods.

## 25. Not Every Method Can Be Declared `synchronized` Arbitrarily

The Java language has rules regarding modifiers:

- **Constructors cannot be declared `synchronized`** in Java source. A synchronized block can be used inside a constructor when truly appropriate, but constructor escape/`this` publication must be carefully examined.
- Abstract methods have no body to execute a monitor in the normal synchronized-method manner; declaring `abstract synchronized` is invalid in Java source.
- Interface default/static methods with bodies have restrictions on the `synchronized` modifier in Java source, though they can contain synchronized blocks inside.
- A method with the `synchronized` modifier is a class-file method with `ACC_SYNCHRONIZED`; do not view it as an auto-generated `synchronized(this)` wrapper in source-level metadata.

**Do not hand-craft/mutate invalid class file flags** and assume the JVM must accept them. Flag constraints follow JVMS §4.6, language rules, and the verifier for the specific class file version.

## 26. Comparing `synchronized`, `ReentrantLock`, and Atomic Operations

| Requirement | `synchronized` | `ReentrantLock` | `AtomicInteger` |
| --- | --- | --- | --- |
| Mutual exclusion for a critical section | Yes, via intrinsic monitor | Yes, via explicit lock API | Only atomic operations on its own value/type |
| Reentrancy | Yes | Yes, per class implementation | Not applicable as a monitor lock |
| Auto unlock when block/method completes | Yes | Requires `unlock()` in `finally` | No unlock needed |
| Timeout on acquire | No `synchronized` timeout syntax | Has `tryLock(timeout, unit)` | Not applicable |
| Interruptible acquisition API | No equivalent to `lockInterruptibly` | Yes | Not applicable |
| Condition waiting | `wait/notify/notifyAll` | `Condition.await/signal` | Does not provide Condition itself |
| Configurable fairness policy | No | Has fair-mode constructor (with semantic limits) | Not applicable |
| JVM `monitorenter`/`monitorexit` bytecode | Block has it; method uses method flag | Not the primary representation of the API | No |
| Protect multiple invariants atomically | Yes, if using the same monitor properly | Yes, if using the same lock properly | Requires different design or CAS protocol |

Do not choose an API just because you think "bytecode `monitorenter` is slower than the lock API." Performance depends on contention, JDK, fast paths, operating system, workload, and critical section length. Choose the right contract (timeout, fairness, interruptibility, composability) and then measure.

## 27. Common Mistakes When Reading `javap`

| Misconception | Correct understanding |
| --- | --- |
| "There is no `monitorenter` in a synchronized method, so it doesn't lock" | `ACC_SYNCHRONIZED` causes the JVM to handle implicit enter/exit |
| "A block must have only one `monitorexit`" | The compiler can have normal and exception cleanup paths, hence multiple instruction sites |
| "Every `monitorexit` in the file executes on every block entry" | Only the actual control-flow path taken is executed |
| "`ACC_SYNCHRONIZED` = opcode 0x20" | It is a method access flag; the opcodes are 0xC2/0xC3 |
| "Static synchronized uses the monitor of any instance" | Uses the corresponding `Class` object |
| "`javap` doesn't show a lock object local so there's no reference" | The compiler can store the monitor reference in a hidden local |
| "A block exception handler means the exception is swallowed" | The handler typically cleans up the monitor and then rethrows via `athrow` |
| "`return` inside a block skips release" | The compiler must route every normal exit through valid cleanup |
| "Nested synchronized on the same object causes self-deadlock" | Intrinsic monitors are reentrant |
| "Synchronized protects every field even if external code bypasses the lock" | Accesses must be synchronized consistently |
| "Monitor exit only lets another thread enter, no visibility effect" | Unlock/lock on the same monitor establishes appropriate JMM happens-before |
| "`notify()` releases the monitor immediately" | The thread calling notify still holds the monitor until it exits |
| "`wait()` does not release the lock" | Wait releases the monitor of the waited-on object and reacquires it before continuing |
| "`sleep()` releases all locks" | Sleep does not release intrinsic monitors |
| "`IllegalMonitorStateException` happens just because the lock is busy" | It reports invalid monitor ownership/operation |
| "`Thread.State.BLOCKED` is the same as `WAITING`" | Blocked for monitor entry differs from waiting on wait set/park |
| "Triggering GC will free a monitor that has an owner" | GC must not break synchronization semantics of live objects |
| "Lock elimination means `synchronized` in source is unnecessary" | The JIT only removes it when proven safe in a specific context |

## 28. Practical Workflow for Explaining a Synchronized Snippet on HotSpot

**Step 1 — Pin down the goal.** Are you asking which opcodes the compiler emits, why a thread is `BLOCKED`, or why synchronized code is slow? Each question uses different tools.

**Step 2 — Check the source form.** Is it a `synchronized(lock)` block or a method `synchronized` modifier? Instance or static?

**Step 3 — Identify the lock identity.** The lock can be `this`, `SomeClass.class`, a `private final Object lock` field, or a passed-in object. Variable name matters less than **reference identity**.

**Step 4 — Compile with Java 17:**

```bash
javac --release 17 MonitorBytecodeDemo.java
javap -v -c -p MonitorBytecodeDemo
```

**Step 5 — For a block:** locate `monitorenter`, `monitorexit` on the normal path, and the exception handler. Do not confuse the number of opcode sites with runtime lock/unlock counts.

**Step 6 — For a method:** check method flags for `ACC_SYNCHRONIZED`. The JVM handles implicit monitor enter/exit at invocation/return, without requiring `Code` to have explicit monitor opcodes.

**Step 7 — Read Java semantics:** every control flow must release the monitor; same-thread reentry is allowed; a null lock throws NPE; the caller must own the monitor if calling `wait/notify`.

**Step 8 — Verify JMM:** do the threads reading/writing shared state actually use **the same monitor**? Is there any code reading outside `synchronized` that breaks happens-before?

**Step 9 — Investigate runtime contention:** inspect `jcmd <PID> Thread.print -l`, JFR Java Monitor Blocked events when available on the build/settings, and CPU/latency timelines. A single thread dump is a snapshot, not long-term statistics.

**Step 10 — If tuning is needed:** shorten the critical section, avoid blocking I/O and external callbacks inside the lock, and review lock ordering. Do not remove `synchronized` just because a profiler reports contention.

**Step 11 — Only when studying codegen:** use compiler diagnostics/assembly tools appropriate for the exact JDK/CPU, and remember that the JIT can replace bytecode monitor operations with fast paths or lock elimination while preserving semantics.

## 29. Self-Check Questions

**Q1.** Through which instructions does a `synchronized(obj)` block appear in bytecode?

**Answer:** `monitorenter` and `monitorexit`, with an exception-handling path ensuring exit.

**Q2.** An instance method has `ACC_SYNCHRONIZED`, yet `javap -c` does not print `monitorenter`. Is that a bug?

**No.** Method monitor enter/exit is handled implicitly by the JVM through invocation/return semantics.

**Q3.** Whose monitor does a static synchronized method use?

**The `Class` object representing the class declaring the method**, e.g., `Counter.class`, not an instance's monitor.

**Q4.** What operand does `monitorenter` take and what does it leave behind?

It pops `objectref` from the operand stack and performs the acquire; preceding stack elements remain.

**Q5.** A thread has entered the same object twice; after one `monitorexit`, can another thread enter yet?

**Not yet** if the entry count is still 1; the current thread still owns the monitor.

**Q6.** When the body of a synchronized block throws an exception, what happens?

The compiler/JVM performs cleanup to exit the monitor before the exception is propagated out (aside from exceptional VM termination semantics outside normal application flow).

**Q7.** Why does `lock.notifyAll()` need to be inside `synchronized`?

The caller must own `lock`'s monitor; otherwise `IllegalMonitorStateException` can be thrown.

**Q8.** How do `lock.wait()` and `Thread.sleep()` differ regarding monitors?

`wait` releases `lock`'s monitor and reacquires it before continuing; `sleep` does not release monitors.

**Q9.** Why is `if (!ready) wait()` not safe enough?

There are spurious wakeups and the condition can change before reacquire; use `while (!ready) wait()`.

**Q10.** A thread enters `synchronized(a)` and then calls an instance synchronized method on `b`, where `a != b`. Is this reentry of the same lock?

**No.** Two different monitors; the thread can hold two locks **simultaneously**, introducing deadlock risk if lock order is inconsistent.

**Q11.** Does `monitorexit` automatically delete the object from the heap?

**No.** It releases ownership/reentrancy depth and produces synchronization effects; it does not directly reclaim memory.

**Q12.** What does `synchronized` using the same monitor in two threads provide besides mutual exclusion?

The memory ordering relationship **unlock synchronizes-with later lock**, establishing happens-before for properly protected reads/writes.

**Q13.** If a method is optimized by the JIT to eliminate monitor operations, does the class file's `ACC_SYNCHRONIZED` disappear?

**Not necessarily, and do not assume so.** The JIT can eliminate runtime work when proven safe without modifying the Java-level method declaration/class-file flag.

**Q14.** Which command helps inspect method flags and bytecode on Java 17?

`javap -v -c -p ClassName`. `-v` shows flags, `-c` shows bytecode; compiler/native machine code is the scope of other tools.
