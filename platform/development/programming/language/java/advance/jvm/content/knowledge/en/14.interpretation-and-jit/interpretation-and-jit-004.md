# Tiered Compilation in HotSpot and the Role of C1, C2

**Tiered compilation** is a **HotSpot JVM** strategy that combines the **interpreter** and levels of **JIT compilation** to balance two somewhat conflicting goals:

- **Fast startup and warm-up:** avoiding spending too much CPU deeply optimizing every method right from the start.
- **Sustained long-term performance:** once the JVM has observed enough of how the program runs, it can generate more optimal machine code based on actual runtime information.

In the common HotSpot model of **JDK 17**, two compilers play the central roles:

- **C1** (*client compiler*): compiles relatively quickly, with code generation modes featuring **no profiling**, **limited profiling**, or **full profiling**. C1 helps hot methods transition from the interpreter to native code without yet paying the full optimization cost of C2.
- **C2** (*server compiler*): a more powerful optimizer that uses collected runtime information to optimize methods, inlining, loops, speculative type optimizations, and many other transformations; typically produces **level 4** code.

**Important:** the description of C1/C2 and the five compilation levels is **HotSpot** architecture, not a mandatory part of the Java Language Specification or JVM Specification. Another JVM, a specialized HotSpot build, or another JIT backend may differ. Learn the levels to understand the runtime, but **do not write applications relying on a method definitely being JIT-compiled at a specific level**.

## 1. From Java source to interpreter and JIT machine code

```text
           javac (before runtime)
   MyApp.java ─────────────────────► MyApp.class
                                     JVM bytecode
                                          │
                                  class loading/linking
                                          │
                                          ▼
                          HotSpot interpreter (level 0)
                          reads/executes bytecode
                          and collects information
                                          │
                                is method "hot" enough?
                                          │
                          ┌───────────────┴───────────────┐
                          ▼                               ▼
                   C1 compiler                       C2 compiler
                  levels 1,2,3                         level 4
                  fast compilation               deep optimization
                          │                               │
                          └──────────┬────────────────────┘
                                     ▼
                            native machine code
                           in HotSpot code cache
                                     │
                                     ▼
                               CPU execution
```

The diagram only illustrates **the components**, without imposing a single path “interpreter → C1 → C2” for every method. A method can:

- Run in the interpreter for the entire lifetime of the process if rarely used.
- Be compiled by C1 and never move up to C2.
- Have multiple code versions at different levels and/or for OSR.
- Be compiled directly by C2 in certain situations.
- Be deoptimized, falling back to the interpreter or lower-level code and then recompiled.

### Three different kinds of code

| Component | Stored where / role | Easily confused with |
| --- | --- | --- |
| **Java source** | `.java` file, input to `javac` | Not what the CPU executes directly |
| **JVM bytecode** | `.class` / runtime class metadata | `javap -c` inspects bytecode, **not** JIT machine code |
| **JIT machine code** | Native executable code generated by the VM, in the code cache | Can be replaced, invalidated, re-optimized |

The `javac` command runs **before** JVM execution when building the application. **C1 and C2 are not two backend options replacing `javac` during source compilation**; they operate when code is already running under the JVM.

## 2. Why not use C2 for every method immediately?

Deep optimization is CPU-intensive work and usually requires a **profile of the actual program**:

- How many times is the method called?
- How many backedges/iterations does the loop run?
- Which runtime types commonly appear at a call site?
- Which `if` branches are commonly taken?
- Which values or states allow reducing checks?
- Should a call be inlined?
- Can loops be transformed, bounds checks eliminated, or code hoisted?

**If optimized too early:** the JVM wastes compiler time/CPU on code that may not even be used; startup and early-stage throughput can suffer. **If never optimized:** hot methods run slowly long-term even though the JVM has had plenty of opportunities to do better.

Tiered compilation uses **C1 as a fast bridge**, while collecting enough profile data so **C2 has useful input**. In practice, the policy also considers **compile queues**, compiler thread availability, call/backedge rates, method size, code cache, class loading, and many other limits.

### Hot code is not only repeated method calls

A method may be called **only once** yet contain a huge loop. Backedge counters help the runtime detect hotness within a single execution and can use **on-stack replacement (OSR)** to switch to a compiled loop. Conversely, a method called repeatedly that is very short/trivial can be inlined into the caller, leaving the final code without a standalone method call as in source.

## 3. Five execution levels in HotSpot tiered policy

In HotSpot JDK 17 under the commonly used tiered scheme, there are **five levels** numbered 0–4:

| Level | Engine/compiler | Profiling | Main goal |
| ---: | --- | --- | --- |
| **0** | **Interpreter** | Can record invocation/backedge counters and method data | Early execution, runtime observation |
| **1** | **C1 simple** | **Does not generate full profiling instrumentation** | Relatively lightweight C1 compiled code; suitable for code paths needing no further profiling |
| **2** | **C1 limited profile** | Mainly invocation/backedge counting; less than level 3 | Runs code faster than level 3 when the C2 queue is under load, while still tracking hotness |
| **3** | **C1 full profile** | Collects rich profiles, with relevant method data | Prepares information for level 4 decisions and optimizations |
| **4** | **C2 full optimization** | Leverages existing profiles, typically without instrumentation like C1 level 3 | Optimized code for hot paths |

**Do not misunderstand the name “full optimization”:** level 1 can use **C1** optimizations but **is not equivalent to C2 level 4 optimization capabilities**. Level 3 does not necessarily run faster than level 2, because profiling instrumentation also has overhead. Level 4 does not mean the VM will definitely use this code forever from now on.

### 3.1. Level 0 — interpreter

- Lets the program **run immediately** without needing to compile each method first.
- Can record invocation counters, backedge events, and method profiles according to runtime policy.
- Does not yet place a corresponding JIT-compiled nmethod for every method.
- Has bytecode interpretation overhead, but cold code may not be worth compiling.

### 3.2. Level 1 — C1 without profiling

- Generates C1 code with appropriate optimizations but **without attaching full profile collection**.
- Can be chosen for methods that the policy sees do not need to proceed to C2, or when C2 is not suitable.
- **Not a mandatory checkpoint** before level 2 or 3; transitions can go 0 → 3 directly.

### 3.3. Level 2 — C1 limited profiling

- Mainly maintains invocation/backedge information for policy decisions.
- Can be chosen when the C2 queue is long, making the level 3 full profiling option unattractive while waiting.
- Does not itself generate as many call-site profile kinds as level 3 in the same model.
- Level 2 is also not a mandatory tier every method must pass through.

### 3.4. Level 3 — C1 full profiling

- Executes C1 compiled code while collecting more runtime profiles.
- **MethodData / historical MethodDataOop, MethodData in modern HotSpot** can store statistics used for adaptive optimization.
- Can provide branch/type profiles useful for C2.
- Incurs extra instrumentation/metadata overhead, so one should not claim level 3 is always the fastest compiled code while waiting.

### 3.5. Level 4 — C2 deep optimization

- Leverages profiles such as commonly seen call-site types, branch probabilities, and hot loops.
- Can generate speculative optimizations accompanied by guards/deoptimization fallback.
- Higher compilation cost, aiming for good **steady-state performance** when code is genuinely hot.
- Not guaranteed to always beat C1 in every microbenchmark; effectiveness depends on method shape, target CPU, workload, profiling, and compile budget.

## 4. Level transitions are not linear

Common transition model:

```text
                          ┌───────────────────┐
                          │ Level 0           │
                          │ Interpreter       │
                          └──────┬────────────┘
                                 │ hot method
                  ┌──────────────┼─────────────────────┐
                  ▼              ▼                     ▼
        ┌────────────────┐ ┌────────────────┐  ┌────────────────┐
        │ C1 level 3     │ │ C1 level 2     │  │ C1 level 1     │
        │ full profiling │ │ limited profile│  │ no profiling   │
        └────────┬───────┘ └────────┬───────┘  └────────────────┘
                 │                  │
                 ▼                  ▼
          ┌────────────────────────────┐
          │ C2 level 4                 │
          │ full optimization          │
          └────────────────────────────┘

Deoptimization can transfer execution back to the interpreter/
other compiled code, to later recompile if policy warrants.
```

Examples of paths in tiered policy:

- **0 → 3 → 4:** the commonly used path when the profiler needs to accumulate data at level 3 and then C2 compiles.
- **0 → 2 → 3 → 4:** can be used when the C2 queue is high and the VM wants to reduce full profiling cost while waiting.
- **0 → 3 → 1**, or **0 → 2 → 1:** some methods may receive C1 code with less instrumentation because the compiler/policy judges C2 is not needed.
- **0 → 4:** can occur in appropriate cases, for example when C1 compilation fails or code/profile is already available.
- **3 → 4 → deopt → 0/3/...:** optimized assumptions can become invalid, and the JVM restores the correct execution state and recompiles.

Paths are affected by version and policy. **The transition arrows above are HotSpot examples**, not an immutable state machine for every application run. Do not assert that a method passes through all 5 levels in order.

## 5. Profiling: what data drives JIT decisions?

### 5.1. Invocation counters and backedge counters

- **Invocation counter:** signal that a method is called many times.
- **Backedge counter:** signal that a backward branch in a loop runs many times.
- **Rate / event frequency:** the policy can care about the number of events per unit of time, not just total counters.
- **Method Data Object (MDO):** metadata containing profiling information for applicable bytecode sites.

```java
static long sum(int n) {
    long result = 0;
    for (int i = 0; i < n; i++) {
        result += i;
    }
    return result;
}
```

This is an **illustrative method**, without a `main`. Calling the method once with a very large `n` can still increment the backedge counter enough for the runtime to consider OSR. Calling the method repeatedly with `n=0` creates a large invocation count even though the loop body does not run.

### 5.2. Type profiles and inlining

A virtual call:

```java
interface Worker { int work(int x); }

static int apply(Worker w, int x) {
    return w.work(x);
}
```

This is an **illustrative snippet** that needs to be placed inside complete types to run. If at runtime most `w` instances have exactly one concrete class, the VM can record a **monomorphic call site**, inline the appropriate method, and add guards to preserve correctness.

If later more types appear or a new subclass is loaded making the assumption no longer valid, the optimized code can **deoptimize**. This does not mean the JIT compiled incorrectly; speculative optimization is valid if the VM has a proper fallback mechanism.

### 5.3. Branch profiles and loop optimizations

Suppose:

```java
if (x >= 0) {
    fastPath();
} else {
    rarePath();
}
```

This is **Java pseudocode**; `fastPath` and `rarePath` must be defined to compile. When one branch is rare, the JIT can place the hot path more favorably in machine code. However, one **cannot** infer from that that the rare branch is deleted and never needs to execute. The VM must still preserve correctness when conditions change.

### 5.4. Profiles are not immutable

Profiles are recorded from actual inputs and can differ between warm-up and production workloads. Behaviors that change profiles:

- Input data no longer has the same distribution.
- Caches warm up, request traffic changes.
- Dynamic proxies or new subclasses are loaded.
- Different class loaders increase polymorphism.
- Hot code shifts with workload phases.
- Recompilation, code cache pressure, or compilation limits.

Therefore, do not predict final machine code solely from Java source; it depends on **runtime evidence**.

## 6. How C1 and C2 differ in cost and optimizations

| Aspect | C1 | C2 |
| --- | --- | --- |
| Orientation | Relatively fast compilation, supporting tiered warm-up | Deep optimization for hot code |
| Compilation cost | Usually lower | Usually higher |
| Runtime profiling | Levels 2/3 have instrumentation by level | Leverages profiles; optimized output has less profiling |
| Compilation levels | 1, 2, 3 in the HotSpot scheme | 4 |
| Optimizations | Appropriate C1 optimizations, geared toward fast compile time | Deep inlining, loop optimization, speculative optimizations, vectorization when applicable |
| Startup | Can bring hot methods to native code early | Can cause compile latency/CPU if used too early |
| Steady-state | Good enough for many methods | Can achieve higher throughput on hot paths |
| Code cache | Produces C1 compiled nmethods, including profiled variants | Produces C2 compiled nmethods, usually non-profiled |
| Misconception risk | C1 level 3 is always faster than level 2 | C2 is always fastest for every method |

The term “C1” is historically tied to **client compiler** and “C2” to **server compiler**, but in modern HotSpot tiered compilation can use both **within the same Server VM**. Do not think you need to run `-client` to get C1 on 64-bit JDK 17.

### C2 does not turn Java into unsafe code

Optimizations can eliminate physical allocations, inline virtual calls, transform loops, or remove checks proven redundant **as long as observable semantics are preserved**: exceptions, synchronization, Java Memory Model, class initialization, safepoints, and required conditions.

If a speculative assumption is wrong, the VM can deopt and restore method/frame state at a valid point. **Speculation does not allow the JIT to return arbitrary wrong results**.

## 7. Compilation policy, thresholds, and compile queues

HotSpot does not JIT a method as soon as its invocation count hits a single fixed “magic” number across all JVMs.

The policy may consider:

- Invocation count and backedge count.
- Rate of events, how fast the method becomes hot.
- Whether profile data is useful enough yet.
- Compiler queue length and compiler threads.
- Method size/bytecode complexity.
- Code cache space.
- Compilation exclusions and compiler failure cases.
- JVM flags, tiered policy, and version.

### The compile queue is not a simple FIFO list

Compile requests can enter C1/C2 queues, be prioritized by hotness/estimated benefit, and a request can become **stale** when the workload changes. The VM can adjust thresholds when the compiler is busy to avoid compiling batches of methods that are no longer hot.

```text
Method A is being called heavily ─► C1 queue ─► C1 worker
                                       │
                                       ▼
                                  C1 nmethod
                                       │ profiling
                                       ▼
                                    C2 queue ─► C2 worker
                                                   │
                                                   ▼
                                              C2 nmethod
```

The diagram is a model, not a guarantee that every method always has exactly one request in each queue.

### Compiler threads are runtime resources

C1/C2 compilation uses CPU and memory; they can run **asynchronously with respect to application threads**. The application continues running interpreted/C1 code while C2 is compiling. Compile activity affects:

- CPU during the warm-up phase.
- Startup/readiness speed.
- Code cache occupancy.
- Long-term throughput after hot methods are optimized.

Therefore, “the JVM is still slow in the first 10 seconds” may be due to not being warmed up yet, but can also be due to I/O, class loading, cache misses, GC, allocations, or external services. Multi-dimensional measurement is needed.

## 8. On-Stack Replacement (OSR) for running loops

When a method is called **once** but a loop runs for a long time, it would be inefficient if the VM had to wait for the method to return to use compiled code on the next call. **OSR** allows compiling an entry corresponding to a **loop/backedge bytecode index** and transferring execution from the interpreter/C1 to appropriate optimized code while the method is still running.

```text
Method called first time in interpreter
              │
              ▼
        very long loop
              │
       backedge hot enough
              │
              ▼
         OSR compile
              │
              ▼
         OSR nmethod
       (entry at loop BCI)
              │
              ▼
    continue loop in compiled code
```

- OSR compiled code can **differ** from normal-entry compiled code of the same method.
- `PrintCompilation` can mark OSR with the `%` symbol; other codes/notations depend on the HotSpot version.
- OSR is not simply “moving the entire Java stack into the code cache” — it is transferring **execution state** at a valid point.
- A JVM may choose not to perform OSR in a specific run; a hot loop does not guarantee seeing an exact OSR compile event.

### OSR and tiered levels

An OSR nmethod can be generated at an appropriate level per VM policy, without necessarily waiting for all compilation levels. When reading logs, distinguish a method's **OSR compile** from a **normal-entry compile** rather than adding them together as two different source methods.

## 9. Deoptimization: when optimized assumptions no longer hold

C2 can optimize based on type/branch profiles and **guards**. If it needs to fall back to a general execution path, HotSpot can perform **deoptimization**.

```text
C2 optimized method
      │
      ├─ assumptions still valid ──► continue optimized code
      │
      └─ guard failed/class changed
                    │
                    ▼
            deoptimization
                    │
                    ▼
         interpreter frame state
         or another execution path
                    │
                    ▼
           profile/recompile if needed
```

Examples:

- A call site previously only received class `Dog` but later receives `Cat`.
- The class hierarchy changes when a new subclass is loaded.
- Rare branches/exceptions occur more frequently.
- Optimized code depends on assumptions about synchronization or reference state checked by the VM.

**Deoptimization does not mean an exception or JVM crash.** It is the mechanism for **maintaining correctness when speculative optimization has been used**.

### Uncommon traps and recompilation

HotSpot can route a “rare” path through an **uncommon trap** to return to general execution. If that path later becomes common, the profile can change and the JVM recompiles code with fewer assumptions or re-optimizes according to the new data.

When reading printed JIT code, pay attention to **each compile ID/level/BCI and version state**, rather than asserting a method forever has only one compiled body.

## 10. The code cache holds C1/C2 compilation results

Machine code generated by C1 or C2 is managed in the **HotSpot code cache**, usually in the form of **nmethods**. The code cache resides in native executable memory, **separate from the Java heap**, metaspace, and stack frames.

A HotSpot configured with **segmented code cache** can have:

| CodeHeap | Purpose |
| --- | --- |
| **non-nmethods** | VM-generated runtime stubs, adapters, and code that is not a compiled Java method |
| **profiled nmethods** | C1 code with profiling, typically serving the warm-up phase and level transitions |
| **non-profiled nmethods** | Code with little/no profiling, including many long-term optimized compiled methods |

Do not equate a CodeHeap with an absolute compilation level; actual placement depends on version/mode. C1 level 1 can reside in the non-profiled region, while C1 level 3 carries instrumentation suited to the profiled region.

### When the code cache is full

If the code cache no longer has enough space for a new nmethod, HotSpot can **reduce/stop compilation** and print a warning such as:

```text
CodeCache is full. Compiler has been disabled.
```

This is a **common message pattern**, not a guaranteed string across every release. The application can continue running in the interpreter/existing code but loses opportunities for further optimization. Do not conclude with certainty that a full code cache is the cause just because throughput is low; check code heap statistics, queues, and logs.

Operations like **code sweeping**, **not entrant/zombie nmethods**, **class unloading**, and **deoptimization** help manage the lifecycle of compiled code. JIT-compiling a method does not mean its native code persists forever until the process exits.

## 11. Enabling/disabling tiered compilation on HotSpot JDK 17

The following commands are examples specifically for **HotSpot**, not standard Java SE flags across all JVMs:

| Option | Meaning | Caution |
| --- | --- | --- |
| `-XX:+TieredCompilation` | Enables tiered compilation if the JVM/build supports it | Enabled by default in many modern Server VMs |
| `-XX:-TieredCompilation` | Disables the tiered compilation policy | **Does not mean interpreter-only**; the JVM can still JIT |
| `-XX:TieredStopAtLevel=1` | Caps compilation level, typically keeping C1 no-profiling | Does not prove every method is compiled |
| `-XX:TieredStopAtLevel=3` | Allows levels up to 3, not using level 4 of the standard scheme | Compiler/mode/runtime flags can affect behavior |
| `-Xint` | **Interpreted-only** mode for Java methods | Suitable for correctness/perf experiments, usually slow |
| `-Xcomp` | Prioritizes aggressively compiling methods early | Has startup cost; does not reflect normal execution |
| `-XX:+PrintCompilation` | Prints compilation events | Output varies by runtime |
| `-XX:+PrintCodeCache` | Prints code cache statistics | VM/build dependent |
| `-XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining` | Diagnoses inlining decisions (if supported) | Very verbose output, do not enable indiscriminately in production |

**A common pitfall:** `-XX:-TieredCompilation` is **not** a long way to write `-Xint`. `-Xint` is clearer when the goal is an interpreter-only comparison.

### Note on `CompileThreshold`

One cannot claim “on every HotSpot, calling a method exactly 10,000 times gets it compiled by C2.” In tiered mode, thresholds are affected by counters, rates, compile queues, tier transitions, and other JVM flags; `CompileThreshold` alone does not describe the entire policy.

If you want to learn the meaning of each threshold flag, read the exact **JDK version/source** and use compiler logs. Changing thresholds can cause insufficient profiles, overloaded compile queues, or altered warm-up; do not use them to optimize production without benchmarking.

## 12. Java 17+ Lab: hot method and OSR-eligible loop

Create a single file **`TieredCompilationDemo.java`**:

```java
public class TieredCompilationDemo {
    private static volatile long lastValue;

    static long score(int n) {
        long sum = 0;
        for (int i = 0; i < n; i++) {
            sum += (i & 7);
        }
        return sum;
    }

    static long longLoop(int n) {
        long sum = 0;
        for (int i = 0; i < n; i++) {
            sum += i % 13;
        }
        return sum;
    }

    public static void main(String[] args) {
        long checksum = 0;
        int repeats = 80;

        for (int j = 0; j < repeats; j++) {
            long result = score(1_000_000);
            checksum += result;
            lastValue = result;
        }

        long osrCandidate = longLoop(1_300_000);

        System.out.println("score: " + lastValue);
        System.out.println("iterations: " + repeats);
        System.out.println("checksum: " + checksum);
        System.out.println("long loop: " + osrCandidate);
        System.out.println("done");
    }
}
```

Compile and run on JDK 17+:

```bash
javac -encoding UTF-8 TieredCompilationDemo.java
java TieredCompilationDemo
```

**Exact standard output when run without compiler/GC logging enabled:**

```text
score: 3500000
iterations: 80
checksum: 280000000
long loop: 7800000
done
```

### Explaining why the result is fixed

- `i & 7` produces the repeating sequence `0,1,2,3,4,5,6,7`, summing to **28** per 8 values.
- `1_000_000 / 8 = 125_000` cycles, so each `score(1_000_000) = 125_000 × 28 = 3_500_000`.
- Repeated `80` times and accumulated, so `checksum = 80 × 3_500_000 = 280_000_000`.
- `i % 13` produces a cycle from 0 to 12, summing to **78**. `1_300_000 / 13 = 100_000` cycles, so `longLoop = 7_800_000`.
- Using `long` for sums avoids overflow confusion when exercises change iteration counts.
- `lastValue` is `volatile`: writing/reading the value is designed to have an observable effect, preventing the assumption that the source loop is definitely eliminated completely; even so, the VM can still optimize execution paths while preserving semantics.

**No JIT guarantee:** loops with many iterations create an **opportunity** for profiling/OSR, without guaranteeing a fixed level or number of compilation events across all CPUs/JVMs/configs.

## 13. Observing method levels with `PrintCompilation`

On HotSpot:

```bash
java -XX:+PrintCompilation TieredCompilationDemo
```

Besides the five lines of program output, the JVM can print many compiler events, including for **JDK library methods**. A log might look like:

```text
...  3   TieredCompilationDemo::score (N bytes)
...  4   TieredCompilationDemo::score (N bytes)
...  %   4   TieredCompilationDemo::longLoop @ BCI (N bytes)
```

This is a **structural pattern**, not a measured log and not lines guaranteed to appear. `N bytes` is the bytecode/method size reported by the VM, and **BCI** is the bytecode index at the OSR entry. Actual output has compile ID, timestamp, flags, and other version-specific information.

### How to read it properly

- **Compile ID:** identifier of the compilation event within the VM process.
- **Level** such as 1,2,3,4: compilation level according to tiered policy (when that column is shown).
- **Method name:** `Class::method` being compiled or related to the event.
- **`%`:** typically indicates an **OSR compilation** event.
- **`made not entrant`:** the compiled code version no longer accepts new calls in the marked situation.
- **`made zombie`:** internal state of compiled code no longer in use according to the VM lifecycle.

**Do not infer that every method must print 3 then 4.** If the interpreter or C1 policy differs, the process finishes before C2 compiles, the compile queue is not drained, or the JVM optimizes differently, the log may lack level 4.

### Trying different modes

```bash
java -Xint TieredCompilationDemo
java -XX:TieredStopAtLevel=1 -XX:+PrintCompilation TieredCompilationDemo
java -XX:TieredStopAtLevel=3 -XX:+PrintCompilation TieredCompilationDemo
java -XX:+PrintCompilation TieredCompilationDemo
java -XX:-TieredCompilation -XX:+PrintCompilation TieredCompilationDemo
```

These commands run **five separate JVM processes**. **The computed program output must remain identical** across all runtime-supported commands; however, compilation logs and execution times differ.

**The goal of the exercise** is to see **execution paths change**, not to assert that level 1 must have exactly X events or that level 4 definitely appears in a single short run.

## 14. `javap` only shows bytecode, not C1/C2 output

The command:

```bash
javap -c -p TieredCompilationDemo
```

shows bytecode opcodes such as `iload`, `iand`, `i2l`, `ladd`, `iinc`, conditional branches, `lreturn`, and the appropriate `invokestatic` calls. `javap` reads the class file, **not a snapshot of the running JVM's code cache**.

### If you want to see native assembly generated by the JIT

HotSpot has diagnostic mechanisms such as:

```bash
java -XX:+UnlockDiagnosticVMOptions -XX:+PrintAssembly TieredCompilationDemo
```

However, `PrintAssembly` usually requires the **hsdis** library matching the OS/architecture/JDK build, and the output can be huge or contain no assembly if the disassembler is unavailable. **Do not treat not seeing assembly as proof that C2 is not working.** Use `PrintCompilation` or a profiler before diving into assembly.

Some builds/tooling can use `CompileCommand=print` to restrict methods, but syntax and requirements must be checked on the exact HotSpot version; do not copy a long configuration into production without testing.

## 15. Observing compile queues and code cache with `jcmd`

On a JDK/HotSpot supporting the `jcmd` tool, a running JVM process can provide JIT diagnostics:

```bash
jcmd -l
jcmd PID help
jcmd PID Compiler.queue
jcmd PID Compiler.codelist
jcmd PID Compiler.codecache
```

`PID` is a **placeholder** and must be replaced with the actual process ID. Do not type literal `<PID>` brackets in the shell because it may be interpreted as redirection syntax.

| Command | Usage |
| --- | --- |
| `Compiler.queue` | Observe methods waiting to be compiled |
| `Compiler.codelist` | List compiled methods/code currently live in the VM |
| `Compiler.codecache` | Statistics on code cache layout/capacity |
| `VM.flags` | Check effective JVM flags |
| `help` | Verify whether a diagnostic command is supported by the build |

**Note:** the `TieredCompilationDemo` program may finish too fast for you to type `jcmd` in time. Use a long-lived test process or a running service with appropriate access permissions.

### Full code cache and overloaded compile queue are different

- **Long C2 queue:** C2 has not yet processed all compilation requests; the JVM can continue running interpreter/C1 code.
- **Full code cache:** no suitable space left for new code blobs, compilation may be restricted.
- **Insufficient profile:** the policy has not yet sent the method to compile or chosen level 4.
- **Method excluded from compilation:** compiler exclusion/limit/failure exists, or `-Xint` mode.
- **CPU throttled:** compiler threads struggle to get CPU, making warm-up slow.

Do not immediately increase code cache size just upon seeing low throughput. Measure **queue lengths, effective flags, code cache use, CPU throttling, and load**.

## 16. Compilation MXBean and monitoring tools

The Java Management API has `java.lang.management.CompilationMXBean`, **if exposed by the JVM**. It can report the JIT compiler name and `totalCompilationTime`, but does not provide a standardized log of every compilation level:

```java
import java.lang.management.CompilationMXBean;
import java.lang.management.ManagementFactory;

public class CompilerInfoDemo {
    public static void main(String[] args) {
        CompilationMXBean bean =
                ManagementFactory.getCompilationMXBean();

        if (bean == null) {
            System.out.println("compiler bean: unavailable");
            return;
        }

        System.out.println("compiler: " + bean.getName());
        if (bean.isCompilationTimeMonitoringSupported()) {
            System.out.println("time(ms): "
                    + bean.getTotalCompilationTime());
        } else {
            System.out.println("time(ms): unsupported");
        }
    }
}
```

Run:

```bash
javac -encoding UTF-8 CompilerInfoDemo.java
java CompilerInfoDemo
```

**Well-structured output but variable values:** compiler name and compilation time depend on the JVM/mode, and may print `compiler bean: unavailable` or `time(ms): unsupported`. Do not assume a fixed ms number, because VM startup timing, workload, and JIT threads differ.

### Why JMX does not replace compiler logs

`CompilationMXBean` helps show overall JIT status, but **does not** directly prove method `score` reached level 4. To analyze individual methods, use `PrintCompilation`, JIT logs, JFR compiler events, or a supported profiler; to analyze machine instructions, use the proper VM decoding tool.

## 17. Performance trade-offs

### Startup vs steady state

A 2-second CLI application may **finish before benefiting much from C2**. Spending CPU to profile/compile methods that are not reused enough times can worsen startup or total time. A server running for days with stable hot methods can benefit significantly from C2.

**Tiered compilation exists to find a balance**, not because C2 is always “strongest” so you should always turn on a mode that compiles all methods immediately.

### Warm-up and flawed benchmarks

If measuring:

```java
long start = System.nanoTime();
for (int i = 0; i < 100; i++) {
    targetMethod();
}
long elapsed = System.nanoTime() - start;
```

This is **Java pseudocode** with an undefined `targetMethod()`. Results are easily skewed by class loading, interpreter, C1/C2 transitions, code cache, GC, CPU scheduling, and dead-code elimination. Do not use a single measurement to choose flags.

For microbenchmarks, use **JMH**, sufficient warm-up, multiple forks, avoid constant folding/dead-code elimination, and observe JVM flags. However, **also do not warm up indefinitely** if startup latency itself is what you need to measure. Define the goal first.

### When to consider `TieredStopAtLevel=1`?

On some serverless/short-lived workloads, capping at C1 can reduce compilation overhead, improve readiness, or save code cache. However, steady-state throughput may drop. Do not choose by gut feeling; measure request latency/warm-up/CPU with the real application.

### When might disabling tiered be considered?

Only when there is a specific benchmark/tuning reason and the trade-off has been proven. `-XX:-TieredCompilation` can cause the compiler policy to take a different path (not `-Xint`). Do not try to use it to “disable JIT” when what needs testing is interpreter-only.

## 18. Troubleshooting common scenarios

| Symptom | Possibility | Check |
| --- | --- | --- |
| Hot method does not reach level 4 | Insufficient profile, C2 queue, exclusions, stop level, C2 inactive, code cache | `PrintCompilation`, `Compiler.queue`, effective flags |
| Log only has level 1 | `TieredStopAtLevel=1` or policy chose C1 no-profiling | `VM.flags` / startup command |
| No JIT events | `-Xint`, JVM/tooling does not support logging, workload too short | VM mode, logger, run command |
| Throughput increases gradually after startup | JVM warm-up/profile/JIT; could also be cache/app effects | JIT logs, metrics, warm-up phase |
| CPU spikes at startup | JIT compilation, class loading, GC, or app initialization | CPU profiles, compiler events |
| Compile time too large | C2 queue/compilation cost, too many hot methods | CompilationMXBean, JFR, method-level logs |
| Code cache warning | Native code region out of capacity/fragmentation | `Compiler.codecache`, flags, code cache logs |
| Method `made not entrant` | Compiled code version replaced/no longer suitable | Deopt/recompilation, class loading |
| `PrintAssembly` shows no assembly | Missing hsdis or missing diagnostic setup | JDK architecture/build and hsdis |
| Same source has different compile levels | Profile, inputs, CPU quota, JDK build, timing | Compare environments/runs |
| Long loop shows no OSR | Loop not hot enough per policy or mode unsupported | Backedge/workload, `PrintCompilation` |
| `-XX:-TieredCompilation` still JITs | That changes policy, not interpreter-only | Use `-Xint` when wanting to disable JIT |

### JVM versions and distributions

The levels and flags described here illustrate **HotSpot JDK 17**. Newer HotSpot releases may change policies, code cache, compiler internals, or add AOT mechanisms. Some JVMs have other compilers such as the **Graal compiler** at the optimizing level in appropriate configurations. **OpenJ9** also has a JIT but does not directly map to these five HotSpot C1/C2 levels.

If a flag is reported as unrecognized, do not automatically conclude the Java installation is broken: check the implementation, JDK version, and release docs of that binary.

## 19. Table distinguishing easily confused concepts

| Misconception | Reality |
| --- | --- |
| “`javac` is C1 or C2.” | `javac` compiles source into bytecode before running; C1/C2 generate native code at runtime |
| “The JVM always interprets, never runs native code.” | HotSpot has both an interpreter and JIT-compiled native code |
| “C1 only runs on Client VM, C2 only on Server VM.” | HotSpot tiered mode can use both in Server VM |
| “Every method must go level 0→1→2→3→4.” | Policy chooses different paths depending on profile and queue |
| “Level 1 means C1 with no optimization.” | It has C1 optimizations, just without full profiling instrumentation |
| “Level 3 is always faster than level 2.” | Profiling has runtime cost, depending on the method |
| “Level 4 code will never change.” | Deopt, recompilation, unloading/code sweeping can occur |
| “Calling a method many times is the only condition for hotness.” | Backedge counters for long loops are also important |
| “A method only has one compiled version.” | C1/C2/OSR/recompile can produce multiple code versions |
| “C2 optimizes deeper so every program starts faster.” | C2 compile cost/profiling can slow startup |
| “`javap -c` is native assembly after C2.” | It is JVM bytecode in the class file |
| “`-XX:-TieredCompilation` disables JIT.” | Not necessarily; `-Xint` is interpreter-only |
| “`TieredStopAtLevel=1` guarantees every method has C1 code.” | Cold methods can remain interpreted |
| “An empty C2 queue means every hot method is optimized.” | Compilation could be disabled, profile insufficient, or stop level set |
| “`PrintCompilation` event count is always deterministic.” | Depends on JDK, CPU, workload, timing, and compiler state |
| “HotSpot tiered levels are a standard feature of every JVM.” | It is an implementation detail |
| “Code cache is Java heap.” | Native code resides in the HotSpot code cache region, outside heap objects |
| “Deoptimization proves the compiler was wrong.” | It is a valid fallback mechanism from a speculative assumption |

## 20. Exercises with answers

**Exercise 1.** What is HotSpot level 0?  
**Answer:** Interpreter; the JVM can execute bytecode before the method is JIT-compiled.

**Exercise 2.** At which levels does C1 typically produce compiled code?  
**Answer:** 1, 2, 3; differing in profiling level.

**Exercise 3.** Which level does C2 typically correspond to in the HotSpot tiered model?  
**Answer:** Level 4, aiming for full optimization.

**Exercise 4.** Is level 3 “deepest optimization” because 3 is greater than 2?  
**Answer:** No. It is C1 with full profiling; level 4 is C2 with deeper optimization.

**Exercise 5.** Why can level 2 be useful when the C2 queue is long?  
**Answer:** It avoids part of level 3's profiling overhead while waiting, while still tracking invocation/backedge counters.

**Exercise 6.** Can a method called exactly once with a very long loop be JIT-compiled while still running?  
**Answer:** Possibly, via OSR if backedges and policy are suitable.

**Exercise 7.** What does the `%` sign in `PrintCompilation` usually indicate?  
**Answer:** An OSR compilation event in the common HotSpot format.

**Exercise 8.** If an optimized call site previously only saw one type and later sees another type, what can happen?  
**Answer:** Deoptimization, profile update, and recompilation; the program must still preserve correct semantics.

**Exercise 9.** Does `-XX:TieredStopAtLevel=1` force the JVM to compile every method?  
**Answer:** No; it caps the level if compiled, while cold methods can stay interpreted.

**Exercise 10.** Does disabling tiered with `-XX:-TieredCompilation` mean disabling JIT?  
**Answer:** No; use `-Xint` when wanting interpreter-only.

**Exercise 11.** Does `javap -c` tell whether C2 has inlined a method?  
**Answer:** No. It displays bytecode; JIT logs/profiler/native code diagnostics are needed.

**Exercise 12.** Why is level 4 not permanent code?  
**Answer:** Assumptions can change, and deoptimization or the compiled-code lifecycle causes the VM to replace versions.

**Exercise 13.** What can a long C2 queue cause?  
**Answer:** Longer warm-up, with methods continuing to run interpreter/C1 code while waiting for C2.

**Exercise 14.** What does `TieredCompilationDemo.score(1_000_000)` return?  
**Answer:** 3,500,000 because `i & 7` has a period of 8 with a sum of 28.

**Exercise 15.** What total checksum does `TieredCompilationDemo` print for 80 iterations?  
**Answer:** 280,000,000.

**Exercise 16.** What is the sum of `longLoop(1_300_000)` when adding `i % 13`?  
**Answer:** 7,800,000.

**Exercise 17.** If a CLI app finishes in two seconds, is forcing earliest possible JIT always beneficial?  
**Answer:** No. Compilation cost can outweigh benefits if code is not reused enough.

**Exercise 18.** If the code cache is full, is the Java heap out of space?  
**Answer:** Not necessarily. The code cache is a separate native region, though both contribute to total resource footprint.

**Exercise 19.** What is used to inspect compile events of a method in HotSpot JDK 17?  
**Answer:** `-XX:+PrintCompilation`, compilation logs/JFR, and appropriate diagnostic tools; cross-check flags and workload.

**Exercise 20.** Can the HotSpot 0–4 scheme be applied directly to OpenJ9?  
**Answer:** No. This is HotSpot's tiered JIT organization, not a JVM-spec requirement.

## 21. Checklist when investigating JIT warm-up

- [ ] Have you confirmed vendor, JVM implementation, version, and architecture?
- [ ] Have you verified `TieredCompilation`, `TieredStopAtLevel`, and effective flags?
- [ ] Have you distinguished interpreter-only (`-Xint`) from tiered disabled?
- [ ] Did you observe compile events by **method + level + OSR status**?
- [ ] Did you measure C1/C2 compile queues, code cache, and compiler threads when needed?
- [ ] Did you warm up and measure multiple times to reduce noise?
- [ ] Did you distinguish startup latency from steady-state throughput?
- [ ] Did you check inlining, profiles, and deoptimization when performance changes unexpectedly?
- [ ] Did you avoid concluding every method must reach level 4?
- [ ] Did you distinguish Java bytecode from machine code in the HotSpot code cache?
- [ ] Did you avoid arbitrarily tuning tier thresholds/compilers before having a baseline?
- [ ] Did you pay attention to CPU quota, GC, I/O, class loading, and memory footprint?
- [ ] Did you record runtime flags in benchmark reports?
- [ ] Did you verify code after changes still produces correct output per Java semantics?
- [ ] Did you check JDK release notes when a flag/log format changes?

## 22. Summary and reference documentation

Useful mental model:

```text
INTERPRETER (level 0)
  │ runs bytecode + detects hotness
  ▼
C1 (levels 1–3)
  │ fast compiled code, profiling by level
  ▼
C2 (level 4)
  │ uses runtime profile for deep optimization
  ▼
CODE CACHE holds compiled machine code
  │
  └─ deopt/OSR/recompile when runtime needs

Not every method has to go through every box in the diagram.
```

**C1** produces compiled code relatively early and provides multiple profiling collection modes; **C2** uses profiles to deeply optimize parts worth investing in. **Tiered policy** decides **when, at what level, and whether it is worth compiling** based on invocation/backedge counters, call/type profiles, compiler queues, and compilation cost. **OSR** handles hot loops in currently executing methods; **deoptimization** maintains correctness when speculative assumptions change; **code cache** manages compiled nmethods across the JVM lifecycle.
