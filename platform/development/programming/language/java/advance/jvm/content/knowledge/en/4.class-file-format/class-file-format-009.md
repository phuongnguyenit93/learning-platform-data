# Signature, annotation, synthetic, and bridge: additional data beyond the ClassFile descriptor

A `.class` file does not only contain bytecode and the **descriptor** of fields/methods. It also has **attributes**, access flags, and metadata that help compilers, analysis tools, reflection libraries, and frameworks understand more information at the Java language level. Four important concepts in this group are **`Signature`**, **annotation**, **`synthetic`**, and **bridge method**.

These pieces of information are related but not identical:

- **Descriptor** is the JVM-level type representation describing a field or a method's parameter list and return type. It serves the ClassFile structure, type checking, and call linking at runtime.
- **`Signature` attribute** supplements generic type descriptions: type parameters `<T>`, type bounds, parameterizations such as `List<String>`, wildcards, and `implements Interface<String>` relationships. Descriptors usually only retain types after **type erasure**.
- **Annotation attributes** store annotations that the compiler decides to write into the class file according to retention/target, including annotations that can be read by Java reflection at runtime.
- **`ACC_SYNTHETIC`** marks a component generated by a tool that does not appear as a corresponding direct declaration in source; **`ACC_BRIDGE`** marks a method serving a bridge role. Many bridge methods generated by `javac` have **both flags**, but the two concepts are not synonymous.

This lesson is under the **class file** topic: what needs to be understood is where metadata is stored, what it is used for, and how it differs from the data that the JVM directly needs during execution. The examples use JDK **17 or later**; bytecode details and constant pool ordering may differ between compilers.

## 1. What question does a descriptor answer?

In a ClassFile, `field_info` and `method_info` reference a **field descriptor** or **method descriptor** via entries in the constant pool. Some common notations:

| Java type | Corresponding descriptor |
| --- | --- |
| `int` | `I` |
| `boolean` | `Z` |
| `long` | `J` |
| `double` | `D` |
| `String` | `Ljava/lang/String;` |
| `int[]` | `[I` |
| `List` | `Ljava/util/List;` |
| `void` as a method result | `V` |

A method descriptor has the form `(param_1param_2...)return_type`:

```text
Java:       int sum(int a, long b)
Descriptor: (IJ)I

Java:       String get()
Descriptor: ()Ljava/lang/String;

Java:       void accept(String[] values)
Descriptor: ([Ljava/lang/String;)V
```

Descriptors use **internal names** with `/` such as `java/lang/String`, not `.` as in Java source syntax. They do not store the full generic types written in source. For example, both `List<String>` and `List<Integer>` have the **raw descriptor** `Ljava/util/List;`; the JVM still distinguishes fields by name and descriptor, rather than distinguishing the two generic type arguments in this descriptor.

For methods, **the return type is also part of the JVM method descriptor**. This is a difference to remember compared to overloading rules in Java source, where two methods cannot be created with the same name and parameters differing only in return type.

## 2. `Signature`: preserving generic information after type erasure

### 2.1. Why is a separate attribute needed?

Java generics help `javac` perform static type checking, but the traditional JVM mechanism runs with descriptors that have undergone **erasure**. The code:

```java
java.util.List<String> names;
```

can be represented in the ClassFile as:

```text
descriptor: Ljava/util/List;
Signature:  Ljava/util/List<Ljava/lang/String;>;
```

These lines illustrate information that can be seen with `javap -v`, not a standalone Java program.

The descriptor `Ljava/util/List;` indicates the reference type handled at runtime. `Signature` preserves the **parameterization with `String`** so tools/reflective APIs can analyze it. If you only read the descriptor, you cannot tell whether the source field declared `List<String>` or `List<Integer>`.

### 2.2. Where can `Signature` be attached?

In the ClassFile, `Signature` is an attribute that can appear on a **class**, **field**, and **method** when a generic signature needs to be recorded.

| Location | Java source example | Generic content that `Signature` can preserve |
| --- | --- | --- |
| Class | `class Box<T> {}` | Declaration of type parameter `T`, its bounds, generic superclass/interfaces |
| Field | `List<String> names;` | Type argument `String` of the field |
| Method | `<T> T identity(T input)` | Type parameters of the method, parameters, result, and generic thrown types when relevant |

Example at the class level:

```java
class TextBox implements java.util.function.Supplier<String> {
    @Override
    public String get() {
        return "hello";
    }
}
```

This class can carry a `Signature` for the `implements Supplier<String>` relationship, even though the descriptor on the implementing method is `()Ljava/lang/String;`. If a method has a type parameter `T`, erasure typically replaces `T` with the appropriate bound, defaulting to `Object` when there is no tighter bound.

### 2.3. How to read a generic signature

A few common expressions:

| Java source | Illustrative signature representation |
| --- | --- |
| `List<String>` | `Ljava/util/List<Ljava/lang/String;>;` |
| `List<? extends Number>` | `Ljava/util/List<+Ljava/lang/Number;>;` |
| `List<? super Integer>` | `Ljava/util/List<-Ljava/lang/Integer;>;` |
| `List<?>` | `Ljava/util/List<*>;` |
| Type variable `T` | `TT;` |

The symbols `+`, `-`, `*`, `T...;` belong to the **generic signature grammar**, not bytecode instructions for addition, subtraction, or multiplication.

**Important limitation:** `Signature` adds metadata so tools understand **generic type declarations**; by itself, it does not turn `List<String>` and `List<Integer>` into two different runtime classes. The checking and casting mechanism of Java generics is subject to type erasure; for example, after retrieving an element through an erased generic interface, the compiler may emit `checkcast`.

### 2.4. When `Signature` is missing or malformed

Not every class, field, or method has a `Signature`: a declaration with no generic information to preserve may only need a descriptor. Reflection libraries have APIs for reading raw types (`Field.getType`, `Method.getReturnType`) and APIs for reading generic types (`Field.getGenericType`, `Method.getGenericReturnType`, `Class.getGenericInterfaces`). Generic APIs can read the `Signature` attribute when present.

For class files modified by bytecode tools, an invalid `Signature` may cause some generic reflection operations to throw errors such as `GenericSignatureFormatError` or `TypeNotPresentException`; this is different from concluding that "every method needs a `Signature` for the JVM to invoke it."

## 3. Annotation: metadata stored as attributes

Annotations in Java are declared with `@interface` and can be attached to classes, fields, methods, parameters, type uses, etc., depending on `@Target`. ClassFile has attributes for several kinds of annotations:

| Common attribute | Role |
| --- | --- |
| `RuntimeVisibleAnnotations` | Annotations on declarations stored so they can be observed through the corresponding reflection APIs |
| `RuntimeInvisibleAnnotations` | Annotations kept in the class file but typically **not** returned directly by Java reflection |
| `RuntimeVisibleParameterAnnotations`, `RuntimeInvisibleParameterAnnotations` | Annotations attached to parameters indexed according to the method structure |
| `RuntimeVisibleTypeAnnotations`, `RuntimeInvisibleTypeAnnotations` | Annotations on **type uses** or type parameters/bounds with positions encoded in the class file |
| `AnnotationDefault` | Default value of an element in an **annotation type** |

These attributes are encoded using JVM data structures (constant pool references, element-value pairs, target/path of type annotations, etc.). They are **not** literal `@MyAnnotation(...)` text inserted verbatim into bytecode.

### 3.1. Retention determines how long an annotation persists

| `@Retention` | After compilation | Standard Java reflection |
| --- | --- | --- |
| `RetentionPolicy.SOURCE` | The compiler discards the annotation per SOURCE policy; not written as a corresponding annotation in ClassFile | Not visible |
| `RetentionPolicy.CLASS` | Written into the class file; typically as a runtime-invisible annotation | Not visible via standard annotation-reading APIs |
| `RetentionPolicy.RUNTIME` | Written as metadata queryable at runtime | Can be read according to the appropriate location and API |

If an annotation type **does not declare `@Retention`**, the default is **`CLASS`**. `@Target` restricts where the annotation can be used (class declaration, method, parameter, `TYPE_USE`, etc.); it does **not** determine retention by itself.

Do not infer that every annotation with `RUNTIME` is visible through the same reflection call: declaration annotations and type-use annotations use different APIs. Inherited annotations also have their own rules; `@Inherited` only applies to certain annotation lookups on **classes**, and does not arbitrarily make method/field annotations inherited.

### 3.2. `AnnotationDefault` is not a runtime object value

Example:

```java
@interface Status {
    String value() default "new";
}
```

The value `"new"` is recorded as `AnnotationDefault` on **the method representing the `value` element of the annotation type**. It does not require every use of the annotation to store a copy of the default value. Reflection can look it up using `Method.getDefaultValue()`.

### 3.3. Annotations only add metadata, they do not execute logic on their own

Writing `@Transactional`, `@Test`, `@Deprecated`, or a custom annotation **does not by default cause the JVM to perform a special action** every time the method is called. Additional behavior is typically implemented by a compiler, annotation processor, framework, agent, or tooling that reads the metadata. Some standard annotations are handled by the compiler/VM according to specific rules; one should not generalize that all annotations are purely comments or that all of them self-execute.

## 4. `synthetic`: trace of generated components

Some components of a class file do not have a corresponding Java source declaration in the usual way, because the compiler or a tool generated them to support program semantics. ClassFile has the **`ACC_SYNTHETIC`** flag for appropriate components and, in historical formats, an attribute named **`Synthetic`**. The flag and the attribute are two representation forms to distinguish by class file version.

Situations you may encounter:

- A **bridge method** generated by the compiler to preserve dispatch after generic erasure or to support covariant returns.
- An auxiliary method generated by the compiler from certain language constructs, such as a lambda implementation method on certain compiler versions/strategies.
- A field or method supporting internal compiler access/representation in certain source translation strategies.

**Not every component not clearly visible in source is marked `synthetic`.** For example, a default constructor generated by the compiler does not necessarily carry the synthetic flag. Java records, enums, and nested classes also have specification-defined components with their own rules. You need to inspect the actual flag in the class file, rather than guessing solely from names like `lambda$...` or `access$...`.

A synthetic element is still a component that **actually exists in the class file** and can contain bytecode invoked by the JVM. Reflection can list it, and APIs like `Method.isSynthetic()` and `Field.isSynthetic()` help identify it from metadata. Synthetic is **not synonymous** with private, invisible, uncallable, or a compilation error.

## 5. Bridge method: why does an erased descriptor need an extra method?

### 5.1. The problem that arises when using generics

Consider the interface and class:

```java
interface Provider<T> {
    T get();
}

class StringProvider implements Provider<String> {
    @Override
    public String get() {
        return "OK";
    }
}
```

This is an **illustrative snippet** and must be placed in an appropriate file to compile. In Java source, `StringProvider.get()` fulfills the `Provider<String>.get()` contract. However, after type erasure:

```text
Provider<T>.get()            → method descriptor: ()Ljava/lang/Object;
StringProvider.get()         → method descriptor: ()Ljava/lang/String;
```

At the JVM level, the two descriptors **differ in return type**. So that a call through `Provider` still finds the right implementation after erasure, `javac` may generate an additional method in `StringProvider` roughly like:

```java
// Pseudocode illustrating the purpose, DO NOT copy into the source class.
// Generated by the compiler as bytecode in StringProvider:
public Object get() {
    return this.get(); // calls the get() version returning String
}
```

This is **not valid Java source** when placed alongside `String get()` in a class because Java does not overload by return type alone. In the **ClassFile**, the two methods have different descriptors and the method returning `Object` is marked **`ACC_BRIDGE`** by the compiler, typically also having **`ACC_SYNTHETIC`**. The bridge forwards the call to the primary implementation, allowing polymorphism to work properly.

At the illustrative bytecode level:

```text
StringProvider.get():Ljava/lang/String;   // original method
StringProvider.get():Ljava/lang/Object;   // bridge method
    aload_0
    invokevirtual StringProvider.get:()Ljava/lang/String;
    areturn
```

The constant pool indices and instruction offsets depend on the actual `javap` output.

### 5.2. Bridges are not only tied to generic `T`

Java allows **covariant return types** in overrides (a subclass method returns a more specific reference type). Example:

```java
class Parent {
    Object value() {
        return "parent";
    }
}

class Child extends Parent {
    @Override
    String value() {
        return "child";
    }
}
```

In compilations that need compatibility with calls via `Parent.value():Object`'s descriptor, the compiler can generate a bridge method on `Child`. **You should not infer that whenever there is a bridge, the source must declare generics.** The conditions and manner of bridge generation are up to the compiler to ensure appropriate dispatch semantics and binary compatibility.

### 5.3. `ACC_BRIDGE` and `ACC_SYNTHETIC` are different

| Field/flag | Meaning | How to inspect |
| --- | --- | --- |
| `ACC_BRIDGE` | Method serving a bridge role generated by the compiler | `Method.isBridge()`, `javap -v` |
| `ACC_SYNTHETIC` | Synthetic component, not corresponding to a normal source declaration | `Member.isSynthetic()` on appropriate members, `javap -v` |
| `Signature` | Metadata describing a generic signature | `javap -v`, generic reflection APIs |
| `RuntimeVisibleAnnotations` | Annotations observable at runtime via appropriate APIs | `javap -v`, Java reflection |

The `ACC_BRIDGE` flag is only meaningful for **methods**, not fields or classes. A bridge is usually synthetic, but **a synthetic method is not necessarily a bridge**; `Method.isSynthetic()` alone does not determine a method's purpose.

## 6. Complete Java 17+ practice: observing all four concepts

Create a file **`ClassMetadataDemo.java`**, saved as UTF-8:

```java
import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;
import java.lang.reflect.Field;
import java.lang.reflect.Method;
import java.util.List;

public class ClassMetadataDemo {
    @Retention(RetentionPolicy.RUNTIME)
    @Target(ElementType.TYPE)
    @interface RuntimeTag {
        String value() default "default";
    }

    @Retention(RetentionPolicy.CLASS)
    @Target(ElementType.TYPE)
    @interface ClassTag {}

    @Retention(RetentionPolicy.SOURCE)
    @Target(ElementType.TYPE)
    @interface SourceTag {}

    interface Provider<T> {
        T get();
    }

    @RuntimeTag("demo")
    @ClassTag
    @SourceTag
    static final class TextProvider implements Provider<String> {
        @Override
        public String get() {
            return "xin chào";
        }
    }

    static final class Holder {
        List<String> names = List.of("An", "Bình");
    }

    public static void main(String[] args) throws Exception {
        Field names = Holder.class.getDeclaredField("names");
        System.out.println("raw field: " + names.getType().getTypeName());
        System.out.println("generic field: "
                + names.getGenericType().getTypeName());

        RuntimeTag tag = TextProvider.class.getAnnotation(RuntimeTag.class);
        System.out.println("runtime annotation: " + tag.value());
        System.out.println("annotation default: "
                + RuntimeTag.class.getDeclaredMethod("value").getDefaultValue());
        System.out.println("class-retention via reflection: "
                + TextProvider.class.isAnnotationPresent(ClassTag.class));
        System.out.println("source-retention via reflection: "
                + TextProvider.class.isAnnotationPresent(SourceTag.class));

        int bridges = 0;
        boolean bridgeIsSynthetic = false;
        for (Method method : TextProvider.class.getDeclaredMethods()) {
            if (method.isBridge()) {
                bridges++;
                bridgeIsSynthetic = method.isSynthetic();
            }
        }
        System.out.println("bridge methods: " + bridges);
        System.out.println("bridge is synthetic: " + bridgeIsSynthetic);

        Provider<String> provider = new TextProvider();
        System.out.println("interface dispatch: " + provider.get());
    }
}
```

In a terminal in the directory containing the file:

```bash
mkdir out
javac -encoding UTF-8 -d out ClassMetadataDemo.java
java -cp out ClassMetadataDemo
```

**Expected standard output from typical JDK 17+ `javac`:**

```text
raw field: java.util.List
generic field: java.util.List<java.lang.String>
runtime annotation: demo
annotation default: default
class-retention via reflection: false
source-retention via reflection: false
bridge methods: 1
bridge is synthetic: true
interface dispatch: xin chào
```

Exact explanation of each part:

1. `names.getType()` returns the raw type of the field, corresponding to the descriptor `Ljava/util/List;`.
2. `names.getGenericType()` reads the generic information `List<String>` preserved in `Signature`.
3. `RuntimeTag` is a declaration annotation marked with `RUNTIME` retention, so `getAnnotation` can return the annotation instance; `value()` returns `"demo"`.
4. The `"default"` value of the annotation element is held via `AnnotationDefault` in the annotation type. The value recorded when using `@RuntimeTag("demo")` is `"demo"`, so do not confuse the two value sources.
5. `ClassTag` has `CLASS` retention: it can be observed in the ClassFile with metadata-reading tools, but **does not** appear via standard `isAnnotationPresent`. `SourceTag` only exists during the source processing phase.
6. `TextProvider` provides `String get()`, whereas `Provider<T>.get()` has an erased descriptor returning `Object`. The compiler generates a **bridge method** `Object get()` so calls through the interface still dispatch properly, and this bridge usually also has the synthetic flag.
7. The variable `provider` has type `Provider<String>`; calling `provider.get()` through the interface still returns the string `"xin chào"`.

Output containing Vietnamese characters depends on the terminal displaying UTF-8 properly; the file is required to be compiled with `-encoding UTF-8` to specify the source encoding.

### 6.1. Using `javap -v` to inspect the actual components

After compiling, run:

```bash
javap -classpath out -v -p ClassMetadataDemo
javap -classpath out -v -p 'ClassMetadataDemo$Holder'
javap -classpath out -v -p 'ClassMetadataDemo$TextProvider'
javap -classpath out -v -p 'ClassMetadataDemo$RuntimeTag'
```

Single quotes for nested class names work for Bash and PowerShell; if using Windows `cmd.exe`, you can replace them with double quotes to protect the `$` character. The main file/class name is `ClassMetadataDemo`; nested types have binary names containing `$`.

**In `ClassMetadataDemo$Holder`**, look for information roughly like:

```text
java.util.List<java.lang.String> names;
  descriptor: Ljava/util/List;
  Signature: ... // Ljava/util/List<Ljava/lang/String;>;
```

The `...` symbols here are **illustrative output with constant pool indices omitted**, not an exact line of output for character-by-character comparison. The key point is that `descriptor` represents raw `List`, while `Signature` preserves `<String>`.

**In `ClassMetadataDemo$TextProvider`**, look for both `get` methods:

```text
public java.lang.String get();
  descriptor: ()Ljava/lang/String;
  flags: ... ACC_PUBLIC ...

public java.lang.Object get();
  descriptor: ()Ljava/lang/Object;
  flags: ... ACC_PUBLIC, ACC_BRIDGE, ACC_SYNTHETIC ...
```

This is a **descriptive excerpt of the lines to compare**, not a verbatim copy of a `javap` listing. You can also see the class `Signature` for `Provider<String>`, `RuntimeVisibleAnnotations` for `RuntimeTag`, and `RuntimeInvisibleAnnotations` for `ClassTag`. `SourceTag` is not retained as an annotation in the class file.

**In `ClassMetadataDemo$RuntimeTag`**, look for `AnnotationDefault` of the `value` element; you can read the content `default_value: s#...` with a constant pool entry corresponding to the string `"default"`.

### 6.2. Looking at bridge bytecode

```bash
javap -classpath out -c -p 'ClassMetadataDemo$TextProvider'
```

In the bridge method returning `Object`, `javap -c` typically shows a behavior pattern equivalent to:

```text
aload_0
invokevirtual ... get:()Ljava/lang/String;
areturn
```

Meaning:

- `aload_0` pushes the `this` reference onto the operand stack.
- `invokevirtual` calls the actual implementation method `get():String`.
- `areturn` returns the `String` reference under the bridge's JVM return type `Object`.

`String` is a subtype of `Object`, so bytecode can return that same reference without copying the object. In override scenarios with generic parameters, a bridge may also need a `checkcast` before delegating, because parameter types are also erased. Do not assume every bridge has the same three instructions above.

## 7. How much metadata does reflection see?

Java reflection allows reading **part of the metadata recorded in the class file**, not fully reconstructing the original Java source.

| Need | Example API | Data read |
| --- | --- | --- |
| Raw type of a field | `Field.getType()` | Class representing the erased type |
| Generic type of a field | `Field.getGenericType()` | `Type`, which may be based on `Signature` |
| Raw return type | `Method.getReturnType()` | `Class<?>` |
| Generic return type | `Method.getGenericReturnType()` | `Type` |
| Type parameters of a class | `Class.getTypeParameters()` | `TypeVariable<?>[]` |
| Generic interfaces | `Class.getGenericInterfaces()` | `Type[]` |
| Runtime annotations on a class | `Class.getAnnotation(...)` | Annotations visible per retention/API |
| Default value of an annotation element | `Method.getDefaultValue()` | `AnnotationDefault` value |
| Is a method a bridge? | `Method.isBridge()` | `ACC_BRIDGE` flag |
| Is a method synthetic? | `Method.isSynthetic()` | Synthetic metadata |
| Type-use annotations | Appropriate `AnnotatedType` APIs | Runtime type annotation metadata supported by the API |

**Limitation of reflection:** `RetentionPolicy.CLASS` is designed so it can be stored in the class file but is not returned as a runtime-visible annotation by standard reflection APIs. To analyze that kind of information, you need a ClassFile-reading tool like `javap` or a bytecode library. Some local variable names, debugging information, or generic metadata may be absent depending on compiler flags and input structure.

When reflection lists `getDeclaredMethods()`, you may see **bridge/synthetic methods**, making the method count larger than the number of method declarations in source. Frameworks scanning methods should have rules for handling bridges if they need to identify logic-implementing methods, avoiding unintended double invocation or registration. However, one should not blindly **discard all synthetic methods**: synthetic does not mean "has no runtime effect."

## 8. Common misconceptions

| Misconception | Accurate understanding |
| --- | --- |
| "The descriptor of `List<String>` contains `String`." | The descriptor typically only has `Ljava/util/List;`; generic information is in `Signature` when preserved |
| "`Signature` by itself prevents putting an `Integer` into a raw `List` at runtime." | Generic checking mainly happens at compile time; erasure and appropriate `checkcast` instructions help protect semantics at use sites |
| "Every annotation in `.class` can be read via reflection." | `CLASS` retention can be stored in the class file but is not exposed by standard reflection |
| "If `@Retention` is omitted, an annotation defaults to `RUNTIME`." | The default is `CLASS` |
| "`@Target` determines whether an annotation persists at runtime." | `@Target` restricts usage locations; `@Retention` determines the retention level |
| "`synthetic` means non-executable." | A synthetic method can contain bytecode that is actually invoked, such as a bridge |
| "Every synthetic method is a bridge." | A bridge is just one case of a generated method; you must check `isBridge()` |
| "Bridges only appear when programming with generics." | Covariant return types can also cause the compiler to generate a bridge |
| "The JVM cannot have two methods with the same name and parameters differing in return type." | In ClassFile, the method descriptor **includes the return type**, so the compiler can generate a bridge with a different descriptor; Java source does not overload this way |
| "`javap -v` always reconstructs the exact original `.java` file." | It displays bytecode and metadata present in `.class`, not lost source code |

### Self-check questions

**1. Why is `Signature` needed when descriptors already exist?**  
Descriptors indicate the JVM types needed to organize/verify calls; `Signature` preserves richer generic metadata after erasure for compilers and tooling.

**2. Can a `RetentionPolicy.CLASS` annotation exist in a class file while `getAnnotation` returns `null`?**  
Yes. It belongs to the runtime-invisible annotation group according to the appropriate storage rules.

**3. Are `ACC_SYNTHETIC` and `ACC_BRIDGE` the same flag?**  
No. The synthetic flag marks a compiler-generated origin, while the bridge flag identifies a method's bridge role.

**4. Is an `Object get()` bridge method a compiler bug that creates duplicate methods?**  
No. Java source does not allow overloading by return type alone, but JVM method descriptors include the return type; the compiler generates a bridge with a different descriptor to ensure polymorphic calls after erasure.

**5. Do annotations automatically make the JVM invoke an interceptor?**  
Not by default. Framework behavior such as interceptors/proxies requires another mechanism that reads and processes annotations.

**6. Why can `getDeclaredMethods()` see more methods than source?**  
Because the class file contains compiler-generated methods as well, including bridges and other synthetic methods.

When reading a ClassFile with `javap`, separately identify **descriptors (execution types)**, **`Signature` (generic metadata)**, **annotation attributes (metadata by retention/location)**, and **`ACC_SYNTHETIC`/`ACC_BRIDGE` flags (roles of generated components)**. These four groups explain why the JVM still executes under type erasure, while reflection/tools can observe additional generic declarations, annotations, and methods that do not appear as ordinary Java source declarations.
