# Compiling Dependencies Built by a Newer JDK

In a Java project, application source code may **not use new Java syntax**, yet still fail to compile or run on an older Java version because a **dependency library (`.class` or `.jar`)** was built by a newer JDK. For example, an application aiming to support Java 17 whose library on the classpath contains Java 21 class files will encounter bytecode compatibility issues. If you switch the JDK running the compiler from 17 to 21, the compile step may pass, but the application **still cannot run on Java 17 by default**.

This article clearly distinguishes between **the compiler's ability to read class files**, **new class files generated by the application**, **platform APIs and library APIs**, and **the JVM runtime's ability to load bytecode**, then guides you through identifying the root cause and choosing the right solution. The examples focus on Java 17 and 21.

## 1. First, Distinguish Four Versions

When debugging a compilation involving dependencies, note four independent components:

| Component | Example | Meaning |
| --- | --- | --- |
| **JDK running `javac`** | JDK 17 or JDK 21 | Determines the highest class file version the compiler can normally read and which `--release` targets are supported |
| **Target release of application source** | `--release 17` | Specifies the source syntax, class-file target, and Java 17 platform APIs that the application code itself is allowed to use |
| **Class file version of dependency** | Library `.class` with major `65` | Indicates the dependency was emitted in the Java 21 class file format, regardless of what the application code aims to target |
| **JVM running the application** | Java 17 runtime | Must be able to load **every class actually used**, including dependencies, not just `Main.class` |

A common scenario:

```text
Application source
    |
    | javac JDK 21 --release 17
    v
Application.class  (major 61 = Java 17)
    |
    +-- uses Library.class (major 65 = Java 21)
                         |
                         v
                Java 17 runtime cannot load this class
```

The diagram above describes **a real risk for the application**, even when the JDK 21 compiler is able to read the major 65 library and successfully compile the application code to major 61. Targeting 17 for the new class **does not downgrade** classes already present inside a dependency JAR.

**Short definition:** *Compile-time compatibility* answers "Can `javac` read, link, and check the dependency?"; *runtime compatibility* answers "Can the target JVM load and execute every required class/dependency?". The two conclusions can differ.

## 2. Major/Minor Version of Java Class Files

Each `.class` begins with a header consisting of the magic number `CAFEBABE`, `minor_version`, and `major_version`. The JVM uses these versions to determine whether the class file is in a format it supports. Some common milestones:

| Java release | Class-file major version | Example |
| --- | --- | --- |
| Java 8 | 52 | `52.0` |
| Java 11 | 55 | `55.0` |
| Java 17 | 61 | `61.0` |
| Java 18 | 62 | `62.0` |
| Java 20 | 64 | `64.0` |
| Java 21 | 65 | `65.0` |
| Java 22 | 66 | `66.0` |
| Java 23 | 67 | `67.0` |
| Java 24 | 68 | `68.0` |

For the modern Java releases in the table, the major version increases by one when the release increases by one. Do not extrapolate a simple formula to all historical Java 1.x releases.

**Example:** A `65.0` class file is generated in the Java 21 format. A standard JDK 17 `javac` **cannot read** that format as a dependency. A Java 17 JVM also **cannot load** a major 65 class file. A Java 21 JVM can load a Java 17 major 61 class under normal compatibility conditions; the reverse is not guaranteed.

### Preview features and minor version `65535`

A class file using **preview features** can carry minor version `65535` (with the major version corresponding to the Java release using preview). This is a special case: preview classes are only supported by a JVM of the **exact Java release** when run with the appropriate preview configuration; even a newer JVM release is not permitted by default to load old preview classes. When seeing `65.65535`, investigate preview settings separately instead of simply concluding "the JVM needs major at least 65".

## 3. Inspecting Versions with `javap` and Identifying the Right Artifact

To view the major version of a class file, use `javap` from a JDK **new enough to understand the file format to be inspected**:

```sh
javap -verbose -classpath build/lib library.Library
```

Look for the section:

```text
minor version: 0
major version: 65
```

This is **an example output to look for when the class is compiled for Java 21**, not the default result for every `Library.class` file.

If the dependency is a JAR:

```sh
jar --list --file libs/vendor.jar
javap -verbose -classpath libs/vendor.jar library.Library
```

`jar --list` shows the entries; `javap` reads the class based on the classpath and type name. With complex JARs, make sure you are viewing **the entry actually selected by the compiler/runtime**. Multiple versions of the same class name can exist in a multi-release JAR.

**Do not use the JAR filename to infer the Java release.** `my-lib-2.0.jar` or a manifest having a field recording the build JDK **is not sufficient proof** that all class files have the same major version. A library can contain mixed class files, shaded classes, generated code, or versioned entries.

Before analyzing an issue, you should record:

```sh
java -version
javac -version
```

The two commands can point to two different JDKs if `PATH`, `JAVA_HOME`, the IDE, or the build tool are not configured consistently. For projects with multiple Java toolchains, you must inspect **the compiler and runtime actually used in each task**.

## 4. Complete Example: Java 21 Library, Java 17 Application

Prepare two JDKs (17 and 21) along with the project source. Each command block requires **selecting the JDK noted in the heading as the active JDK** via `JAVA_HOME`/`PATH` or calling the path to that JDK's executable directly. Do not assume the OS has a program named `javac21`.

Structure:

```text
project/
├── src/
│   ├── library/
│   │   └── library/
│   │       └── Library.java
│   └── app/
│       └── client/
│           └── Main.java
└── build/                   # output generated after compilation
```

File `src/library/library/Library.java`:

```java
package library;

public final class Library {
    private Library() {
    }

    public static int answer() {
        return 42;
    }
}
```

File `src/app/client/Main.java`:

```java
package client;

import library.Library;

public final class Main {
    public static void main(String[] args) {
        System.out.println("Thư viện: " + Library.answer());
    }
}
```

Both files use syntax available in Java 17. **What determines the error in this experiment is the class-file version of `Library.class`**, not new Java syntax inside the library source.

### 4.1. Building the dependency with JDK 21

Select **JDK 21**, verify:

```sh
javac -version
javac --release 21 -encoding UTF-8 -d build/lib21 src/library/library/Library.java
javap -verbose -classpath build/lib21 library.Library
```

The class file is created at:

```text
build/lib21/library/Library.class
```

`javap -verbose` reports `major version: 65`. A successful compiler run typically prints no stdout. Keep in mind that **the directory name `lib21` is only a convention**; the real evidence lies in the class-file header and the toolchain that built it.

### 4.2. Using JDK 17 `javac` to compile the application

Select **JDK 17**, verify `javac -version` is 17.x, then run:

```sh
javac --release 17 -encoding UTF-8 -cp build/lib21 -d build/app17 src/app/client/Main.java
```

This compilation **fails** because `javac` 17 must read `library.Library` major 65 to resolve `Library.answer()`, whereas it only understands class-file versions compatible with JDK 17 and earlier. Typical diagnostics:

```text
bad class file: .../library/Library.class
class file has wrong version 65.0, should be 61.0
```

This is **a commonly seen message excerpt**, with no guarantee of exact verbatim paths, positions, punctuation, or line numbers across all JDKs. A compiler may print "cannot access Library" or "bad class file"; read the entire cause section, especially **wrong version 65.0 / 61.0**.

**Conclusion at this point:** The error occurs at **compile-time**, before running `Main`. Adding `--release 17` does not enable `javac` 17 to read a future class file.

### 4.3. How to fix it to genuinely support Java 17: recompile the dependency

Select **JDK 21** and recompile the library source itself targeting 17:

```sh
javac --release 17 -encoding UTF-8 -d build/lib17 src/library/library/Library.java
javap -verbose -classpath build/lib17 library.Library
```

This time the library output is `build/lib17/library/Library.class`, which has **major version 61**. The library source is compatible with Java 17, so it compiles with this target.

Select **JDK 17**, compile the app with the new dependency:

```sh
javac --release 17 -encoding UTF-8 -cp build/lib17 -d build/app17 src/app/client/Main.java
```

Run with **Java 17 JVM**. On Linux/macOS, the classpath is separated by colons:

```sh
java -cp build/app17:build/lib17 client.Main
```

On Windows PowerShell/cmd, the classpath is separated by semicolons and should be enclosed in quotes:

```powershell
java -cp "build/app17;build/lib17" client.Main
```

**Exact stdout** of the program when using the two class files compiled for Java 17:

```text
Thư viện: 42
```

Result after fixing:

```text
build/
├── lib17/
│   └── library/Library.class    # major 61
└── app17/
    └── client/Main.class        # major 61
```

With this example having no other external dependencies, both the application and the library have a version that Java 17 understands. This is a more meaningful verification than merely making `Main.class` reach major 61.

### 4.4. Important warning: a newer compiler can still produce a misleading build

Keep `build/lib21` as the major 65 dependency. Select **JDK 21** and compile the app as follows:

```sh
javac --release 17 -encoding UTF-8 -cp build/lib21 -d build/app17 src/app/client/Main.java
```

In this situation, `javac` 21 **understands** the library's major 65 class, and can compile the application into `Main.class` major 61. **`--release 17` does not check or convert all class files of third-party libraries on the classpath into major 61.**

If you run those two outputs with **Java 21**, the simple program above runs and prints:

```text
Thư viện: 42
```

But if run with **Java 17**, when the JVM tries to load `library.Library` major 65, it throws `UnsupportedClassVersionError`. In the output of a Java 17 JVM, the error might state:

```text
java.lang.UnsupportedClassVersionError: library/Library has been compiled by a more recent version of the Java Runtime (class file version 65.0), this version of the Java Runtime only recognizes class file versions up to 61.0
```

This is **an illustrative message**: the wording/stack trace depends on the JVM version and class loading time. What is certain is that the Java 17 runtime does not support the major 65 class format.

**Lesson:** "Compilation succeeded with `--release 17`" **does not prove** all dependencies can run on Java 17. You must check the version and APIs of the **entire runtime dependency graph**.

## 5. What Does `--release` Guarantee and What Does It Not Guarantee?

For **the source currently being compiled by `javac`**, `--release N` controls:

1. Accepted syntax and language features according to Java `N`.
2. Class-file target version corresponding to `N`.
3. **Public Java/JDK platform APIs** in release `N` that the source can reference.

For example, JDK 21 + `--release 17` does not allow normal source code to call a JDK API that only appeared in Java 21. That is the advantage of `--release` over using only `-source` and `-target` on a newer JDK.

However, `--release` **is not a compatibility analyzer for every JAR**:

- Does not recompile existing dependencies on the classpath/module path.
- Does not require all dependency class files to have a major version less than or equal to the target release.
- Does not verify that all depended-upon methods/fields at runtime exist and work on Java `N`.
- Does not prevent a dependency from being packaged with the wrong version, shadowed classes, or a JAR with an invalid multi-release layout.
- Does not upgrade an older compiler to read a newer class-file format.
- Does not convert new Java syntax into old Java syntax if the source itself is incompatible with `--release`.

### Why are `-source` / `-target` also not the solution?

`-source 17` restricts the source language; `-target 17` selects the class-file format of **the output being compiled**. They do not alter class files inside `vendor.jar` and do not automatically restrict all JDK platform APIs when the compiler is newer.

Therefore, changing `--release 17` to `-source 17 -target 17` **does not fix a major 65 dependency error**. The effective approach is to choose the right library version or build the library for Java 17, and then run verification on Java 17.

## 6. Distinguishing Compiler Errors and Runtime Errors

| Symptom | Phase where it occurs | Common cause | Investigation direction |
| --- | --- | --- | --- |
| `bad class file: ... wrong version 65.0, should be 61.0` | Older `javac` reading dependency | Compiler does not support the newer class-file version | Check `javac -version` and the dependency's class files |
| `UnsupportedClassVersionError` | JVM loading class | Runtime JVM does not support the class's major/minor version | Check `java -version`, the class actually being loaded, and all runtime dependencies |
| `NoSuchMethodError` | Linkage / method invocation | Compiled against a different library ABI/version than at runtime | Compare method signatures and the packaged/executed JARs |
| `NoClassDefFoundError` | Class loading / linkage | Missing runtime dependency or class load/init failed | Check runtime classpath/module path and cause logs |
| `ClassNotFoundException` | Loading class by name via an API that can throw a checked exception | Class absent from load path, wrong name, or wrong loader | Check the class loader and class name |
| `package ... does not exist` | `javac` resolving dependency | Wrong/missing classpath, module path, package, or JAR | Check paths and artifact contents |
| `cannot access ...` + version mismatch | `javac` resolving type | Dependency has unreadable class format or corrupted file | Read the nested diagnostic, not just the first line |

**`UnsupportedClassVersionError`** is a `LinkageError` (`ClassFormatError` branch), raised when the VM reads a class with an unsupported major/minor version. It is not a `.java` syntax error. Conversely, the `bad class file` message from `javac` is an error during dependency analysis **before runtime**.

Sometimes multi-step builds mix logs together: Gradle/Maven may use a JDK 21 compiler and then run unit tests with JDK 17. Therefore, a successful `compileJava` command gives no certainty about `test` or the production JVM.

## 7. Appropriate Solutions by Situation

### Option A — Choose a library version supporting the target Java

If the application **must run on Java 17**, prefer a library version declared by its author to support Java 17 and whose artifact is genuinely compiled compatibly. Specify the version explicitly in dependency management, run output verification, and confirm that transitive dependencies are also compatible.

Cross-check:

- **Release notes/compatibility matrix** of the library: what is the minimum Java runtime?
- Artifact downloaded in the Maven/Gradle cache: which version is it, and from which repository?
- Actual class-file major version of the classes to be used.
- Transitive dependencies and plugins/agents loaded at runtime.

Do not infer "library source can be written for Java 17" from "the current JAR was built by the author with JDK 21": the source may be rewritable/recompilable, but **the specific distributed artifact** still has major 65 class files.

### Option B — Rebuild the library with a lower target

If you own the library source and it is compatible with Java 17, use the appropriate toolchain:

```sh
javac --release 17 -encoding UTF-8 -d build/lib17 src/library/library/Library.java
```

For real-world libraries, Maven/Gradle can manage source sets, the dependency graph, annotation processors, and packaging. If the library's source or dependencies **require APIs/features only present in Java 21**, adding `--release 17` will cause compilation to fail. That is a signal that you must **replace the implementation**, **choose another library version**, or **raise the minimum Java** of the product.

Do not edit the major byte 65 to 61 with a hex editor: newer classes can contain constant-pool entries, attributes, bootstrap instructions, or API dependencies that Java 17 does not understand. Changing the header is not a valid semantic/bytecode conversion.

### Option C — Upgrade both the compiler JDK and runtime when permitted

If the product **accepts Java 21 or newer**, upgrading the toolchain and runtime accordingly is a valid option. In that case, use `--release 21` to clearly express the application's minimum Java 21 requirement, when truly aligned with platform APIs/dependencies.

Note: Upgrading **only the compiler** to read a major 65 dependency while still deploying to production on Java 17 will create runtime issues as in section 4.4. The decision should be stated in the deployment contract (base image, CI/JDK, container runtime, client machines).

### Option D — Multi-release JAR when supporting multiple JVMs is required

A **multi-release JAR** can contain a compatible class version at the root and implementations specific to newer Java releases under `META-INF/versions/N/`. The manifest needs:

```text
Multi-Release: true
```

Example diagram (illustrative structure only):

```text
example-mr.jar
├── META-INF/MANIFEST.MF
├── library/Library.class                 # base, Java 17 compatible
└── META-INF/versions/21/
    └── library/Library.class             # Java 21-specific implementation
```

A Java 17 JVM selects the compatible root version; a Java 21 JVM can select the `versions/21` entry if the JAR is validly marked as multi-release. Compilation/packaging tools must properly handle versioned entry selection rules and API compatibility. You cannot arbitrarily drop a major 65 class into a regular JAR and hope Java 17 ignores it automatically.

**A multi-release JAR does not automatically solve arbitrary public API changes.** Versioned classes must obey specific rules of the JAR File Specification to preserve the contract across versions. If an external bytecode analysis tool scans the entire JAR without understanding the multi-release layout, it can still trip over higher-version entries; you need to update the tool or configure it properly.

## 8. JPMS and Annotation Processor Cases

### Dependencies on the module path

If the dependency is a named module, you use `--module-path`/`module-info.java` instead of a plain classpath. The compiler still has to read `module-info.class` and the required classes. A module built by a newer JDK can cause a **version mismatch**, or contain metadata/module declarations/APIs that an older JDK does not yet understand.

Do not confuse this with **module readability** and **exports**: an error like "module does not read ..." or "package not exported" is a **JPMS access relationship** issue, not automatically a class-file version mismatch. Always read the actual diagnostic.

### Annotation processors and compiler plugins

A JAR used as an **annotation processor** also contains class files and **is executed during compilation**. A processor built with JDK 21 may not run inside the JDK 17 JVM used to run the compiler, even when the main source uses `--release 17`. Depending on the environment, an error may appear when the compiler attempts to load the processor, such as `UnsupportedClassVersionError`, or a "bad service configuration" message because the processor class could not be loaded.

Here we should distinguish:

- **Compile dependency:** A JAR whose types/ABI the source needs to read.
- **Processor/plugin dependency:** A JAR containing code executed inside/alongside the compiler and needing compatibility with the JVM running the compiler.
- **Runtime dependency:** A JAR packaged/executed with the application and needing compatibility with the deployment JVM.

An artifact can belong to multiple groups, but the way errors arise is not the same. In Maven/Gradle, inspect each configuration (`compileClasspath`, `annotationProcessor`, `runtimeClasspath`, or equivalent configurations) instead of drawing conclusions from just a single JAR file with a matching name.

## 9. Maven, Gradle, and CI: Controlling Toolchain/Target

Configuring **the Java release of the generated code** and **the JDK executing the compiler** are two dimensions that need to be examined separately.

### Maven

With a sufficiently recent `maven-compiler-plugin`, an example declaration is:

```xml
<properties>
  <maven.compiler.release>17</maven.compiler.release>
</properties>
```

This configures compilation for the current Maven module. It **does not retroactively affect** already-published dependency JARs. Maven may use toolchains or the JDK running Maven depending on the project configuration, so you need to verify the actual compiler, resolved dependencies, and surefire/failsafe runtime.

A dependency requiring Java 21 can still slip into the dependency graph if there is no separate minimum runtime check. Use version management mechanisms, build rules, and tests to lock in compatibility.

### Gradle

In a Gradle JVM project, two concepts are commonly used:

```groovy
java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(17)
    }
}

tasks.withType(JavaCompile).configureEach {
    options.release = 17
}
```

This is **a Gradle Groovy DSL configuration snippet**, not a standalone Java file. The toolchain configuration selects JDK 17 for Java compilation in appropriately managed tasks; `options.release` selects target 17 for `javac`. Toolchains, Gradle version, and specific tasks may require separate configuration; do not assume every external plugin or test process uses the right toolchain without verifying.

If JavaCompile genuinely uses **JDK 17**, a major 65 dependency on the compile classpath will cause the compiler to reject it as in section 4.2. That **helps detect errors early**, but ensuring the entire runtime dependency graph is compatible still requires testing/inspecting the artifacts.

### CI: minimum meaningful verification

A pipeline targeting Java 17 should:

1. **Define the minimum runtime** the product promises to support; for example, Java 17.
2. Use a compatible toolchain or compile with `--release 17` on a capable newer compiler.
3. Scan the dependency graph and class-file versions, including transitive dependencies and artifacts with multi-release layouts.
4. **Run integration/smoke tests using the Java 17 JVM itself** after packaging. Testing only with JDK 21 does not prove it runs on JDK 17.
5. Verify that the image/container/server runtime is actually Java 17; a base image accidentally bumped to Java 21 can mask errors until deployed in another environment.
6. Log `java -version`, `javac -version`, and dependency versions to reproduce issues.

**Testing on the minimum Java version is an essential complementary step.** Checking the major version is important but not sufficient: a major 61 class file can still reference APIs/libraries that are absent or have a different ABI at runtime.

## 10. Practical Ordered Investigation Checklist

When encountering an error compiling with a dependency built by a newer JDK:

**Step 1 — Read the error in full.** Is there `wrong version N.0`? Distinguish whether this is a compiler error, linker error, or runtime exception.

**Step 2 — Check the tools.**

```sh
javac -version
java -version
```

If the build tool has its own toolchain, check the task log or configuration instead of trusting only `java` in the terminal.

**Step 3 — Identify the exact JAR/class being selected.** Inspect compile classpath/module path, runtime classpath/module path, transitive dependencies, shaded packages, and class loaders if multiple library versions exist.

**Step 4 — Inspect the actual class header.** Use `javap -verbose` from an appropriate JDK to read major/minor. For a multi-release JAR, identify which entry is selected.

**Step 5 — Compare three numbers.** What does the compiler JDK support up to? What is the dependency major version? What major version does the target JVM support? Remember that `--release` does not change dependencies.

**Step 6 — Choose a maintainable fix.** Downgrade the library version, rebuild with the appropriate `--release`, choose the right MR-JAR, or raise the application's minimum Java version. Do not modify raw class file bytes.

**Step 7 — Recompile and rerun from a managed clean output.** Avoid mixing up old classes or old JARs. Only clean **build output directories owned by the project**; do not delete source files or unidentified data.

**Step 8 — Test the final packaged artifact.** A class in `build/classes` does not reliably represent the contents of the final JAR/container. Inspect the published/deployed artifact and run it on the target JVM.

## 11. Misconceptions to Eliminate

**"`--release 17` turns every dependency into Java 17."** False. It applies to the source code being compiled by the compiler and the target platform API; it does not rewrite JARs.

**"A library built with JDK 21 is definitely Java 21-only."** Not necessarily. If the author used `--release 17`, the resulting class files can be major 61. Inspect the actual artifact.

**"The app code has major 61, so the application can run on Java 17."** Not sufficient. A major 65 dependency, a new ABI, or Java 21 APIs can still cause failures.

**"Upgrading `javac` fixes the Java 17 error completely."** It only resolves the step where the compiler cannot understand newer class files. If the runtime is still Java 17, the newer classes still cannot be loaded.

**"Changing minor/major bytes in `.class` is downcompiling."** False. It can corrupt the class file or encounter unsupported instructions/metadata/APIs.

**"Every `UnsupportedClassVersionError` occurs at startup."** Not necessarily. A class may only be loaded when the relevant code branch executes, so the error can appear late.

**"A low class-file version proves all APIs are compatible."** No. `NoSuchMethodError`/`NoClassDefFoundError` can still occur due to differing runtime APIs/ABIs, even when the major version is valid.

**"A newer JDK can always run every older class in all circumstances."** Upward compatibility is a general goal, but preview class files, changed APIs, security/module encapsulation, and runtime changes have specific conditions. Testing on the actual JVM remains necessary.

## 12. Quick Decision Table

| Current state | Can compile? | Can run on Java 17? | Action |
| --- | --- | --- | --- |
| JDK 17 compiler + major 65 dependency | No, if that class needs to be read | No | Use a Java 17 dependency or rebuild |
| JDK 21 compiler `--release 17` + major 65 dependency | Possibly | **No** if runtime must load class 65 | Do not rely on compile-pass; fix dependency/runtime |
| JDK 21 compiler `--release 17` + major 61 dependency | Possibly | Possibly, if APIs and other dependencies match | Test with Java 17 |
| JDK 17 compiler + major 61 dependency | Possibly, if API/ABI is valid | Possibly, if runtime graph is compatible | Test from packaged artifact |
| JDK 21 compiler/runtime + major 65 dependency | Possibly | Not applicable for Java 17 target | Declare minimum Java 21 if the product accepts it |

The word **"possibly"** is intentional: class-file version is only a necessary condition. Module graph, visibility, APIs, annotation processors, JNI/native code, and build realities can also affect the outcome.

**Key takeaway:** Whether an application **compiles for Java 17** and whether **all bundled libraries genuinely support Java 17** are two separate checks. Verify versions from artifacts, lock toolchains/dependencies, and run the final packaged artifact on the **minimum JVM** the product commits to support.
