# Using -proc to Select the Annotation Processing Mode by Active JDK

**Annotation processing** is the step in which the Java compiler can execute **annotation processors** to read annotations, check source code conventions, emit diagnostics, or generate additional source files. For **javac**, the **-proc** option decides whether the compiler only compiles, only runs annotation processing, or performs both.

The easiest mistake to make is that **the default policy has changed across JDK versions**. A command that does not declare processor configuration might automatically run annotation processors on an older JDK yet fail to do so on JDK 23+. Therefore, when a project suddenly lacks generated code after a JDK upgrade, check **which version of javac actually runs** and **the exact options passed to the compilation**.

This lesson focuses on the three modes **-proc:none**, **-proc:only**, and **-proc:full**, differences in defaults across JDKs, how processors are located, self-contained compilable examples, build upgrade strategies, and common errors.

## 1. First: Annotations Differ from Annotation Processors

An annotation is metadata in Java source code, for example:

~~~java
package demo;

import java.lang.annotation.ElementType;
import java.lang.annotation.Target;

@Target(ElementType.TYPE)
public @interface Mark {
}
~~~

Merely writing or using **@Mark** does not mean some program runs automatically. The compiler can handle annotation syntax and types as a regular part of Java, whereas **annotation processing** under the **javax.annotation.processing** API is a separate mechanism: a class implementing the **Processor** interface (commonly extending **AbstractProcessor**) is loaded and invoked by javac across processing rounds.

A processor can:

- Read type, declaration, and annotation information using **javax.lang.model**.
- Emit warnings or errors via **Messager**.
- Generate new source code via **Filer**; generated code can be fed into subsequent compilation rounds.
- Generate resource or metadata files according to the processor's contract.
- Check build conventions such as a required annotation on a certain kind of class.

For example, an annotation processing tool can generate implementations of a mapper or data-related classes. This is completely different from runtime reflection: the processor runs **during the build**, before the final program is run with the **java** command.

**Note:** an annotation having RUNTIME retention does not mean an annotation processor is always present. And an annotation with SOURCE retention can still be read by a processor while javac compiles source code. The **-proc:none** mode does not strip annotations from source code and does not disable all annotation-related language checks; it only **skips running annotation processing executed by processors**.

## 2. The Three Values of -proc

Standard javac syntax:

~~~bash
javac -proc:none ...
javac -proc:only ...
javac -proc:full ...
~~~

The **colon** is part of the option name: use **-proc:full**, do not substitute **-proc full** or **--proc=full**. Before using a value, verify that the specific JDK supports it with **javac --help**.

| Mode | Runs annotation processors? | Compiles sources to class files? | Use case |
| --- | --- | --- | --- |
| **-proc:none** | No | Yes, when code is valid without processor-generated sources | Intentionally disabling processors; checking code in isolation; builds without processors |
| **-proc:only** | Yes, when a processor is found and has matching work | **No** final compilation performed to emit classes for the processed sources | Checking annotations, testing a processor, generating sources before another build step |
| **-proc:full** | Yes, when processors are available | Yes, including appropriate compilation of original and generated sources | Builds needing processors and runnable artifacts afterward |

**-proc:full does not require annotations on every class** and does not automatically download processors from the network. If the configuration has no processor to execute, the command can still compile normally without code-generation effects. **-proc:only** also does not guarantee that files will be created: a processor might only inspect and emit notes, or generate nothing.

### 2.1. -proc:none: Compile Without Running Processors

~~~bash
javac -proc:none -d out src/demo/App.java
~~~

When sources are complete and required dependencies are present, javac still parses, checks, and generates **.class** files. What is turned off is invoking annotation processors. If source code references a class **only generated by a processor** and that class is not already available, compilation can fail with errors such as **cannot find symbol**. This is the expected outcome when disabling a needed code-generation step.

### 2.2. -proc:only: Run Processors Without Emitting Final Classes

~~~bash
javac -proc:only -processor demo.MarkProcessor ...
~~~

Used when you want to verify that a processor emits diagnostics or generates code as expected without proceeding to final compilation. If the processor uses **Filer**, created sources/resources can still appear depending on **-s** or output configuration; **-proc:only does not mean creating no files at all**. What it skips is **the step of compiling sources into class files after annotation processing**.

Do not call **java demo.App** based solely on a **-proc:only** command in a fresh output directory. To run, a full compilation producing class files is required.

### 2.3. -proc:full: Processors and Compilation

~~~bash
javac -proc:full -processor demo.MarkProcessor ...
~~~

This mode matches the common cycle: javac finds or uses the specified processors, runs processing rounds, and then compiles original sources along with generated sources (if any), writing class files to the directory selected with **-d**.

**Version distinction:** the explicit value **-proc:full** was introduced in newer JDK lines and backported to some older JDKs. **Do not assume every early JDK 17.0.x release accepts -proc:full.** The next section provides a version table to choose accurately.

## 3. Defaults by Version: The Key Point of This Lesson

**Having no -proc option** does not always mean the same policy.

| javac version | When no explicit annotation processing configuration option is given | Recommended practice |
| --- | --- | --- |
| **JDK 8–20** | Legacy policy: may discover and run processors on the classpath by default | To disable: **-proc:none**; to process: choose **-processor**/processor path or the mechanism supported by that JDK |
| **JDK 21–22** | Release javac docs describe processing annotations by default when processors are found; some versions print a note warning of the upcoming change | Declare specific processors, processor path, or **-proc:full** instead of relying on implicit behavior |
| **JDK 23+** | **Does not automatically scan and run processors merely because they appear on the classpath**; requires explicit processing request or configuration | Configure **-processor**, **--processor-path**, **--processor-module-path**, or **-proc:only/full** |

According to the official change announcement for **JDK 23**, javac stops proactively running annotation processors discovered incidentally on the classpath if the user does not supply an annotation-processing-related option. Consequently, long-lived builds relying on implicit discovery can miss generated code after a JDK upgrade.

**JDK 21 and 22:** Javac used to emit a note when a processor ran purely via implicit discovery, advising explicit configuration. Some articles/early JDK 22 builds have a history of experimenting with the policy change; when evaluating a specific environment, prioritize **javac --help**, the installed build, and actual execution results, rather than guessing solely from major version numbers.

**JDK 23+ disabling implicit processing by default** does not mean every command omitting **-proc:full** skips processors. If the user passes **-processor** or a processor path/module path to enable processing explicitly, javac can still run processors and compile as described in the javac 23+ documentation.

### 3.1. Which JDK Releases Support -proc:full?

What must be distinguished is **legacy default behavior** from **the recognized -proc:full syntax**:

- **-proc:none** and **-proc:only** have existed since Java 6.
- **-proc:full** is available in **JDK 21+** and was backported in security updates, notably including **JDK 17.0.11+** and **11.0.23+** of the corresponding OpenJDK/Oracle distributions.
- **JDK 17.0.0** or an un-updated 17u release should not be assumed to accept **-proc:full**. Run **javac --help** to confirm rather than inferring solely from the Java 17 label.

A project using both an older JDK 17 and JDK 23 may need to update the minimum environment before using a unified configuration flag. If you cannot upgrade an old javac, you can enable annotation processing using an explicit **-processor** or appropriate processor path, after testing on that exact JDK.

### 3.2. -proc Is Not --release

For example:

~~~bash
javac --release 17 -proc:full -d out ...
~~~

**--release 17** selects the language level, platform APIs, and target bytecode. It **does not turn JDK 23 javac into JDK 17 javac regarding annotation processing policy**. The processing policy is still governed by **the running compiler version and the actual options**.

Similarly, **java -version** shows the runtime invoked by that command; you must also check **javac -version** because the shell may locate binaries from different JDK installations.

## 4. Identifying the Exact javac in Use

Run:

~~~bash
java -version
javac -version
javac --help
~~~

If the environment has multiple JDKs, determine the path to the compiler:

~~~bash
# Linux/macOS
which javac
~~~

~~~powershell
# Windows CMD/PowerShell
where.exe javac
~~~

Details to record:

1. **Vendor and full version** of the JDK, for example 17.0.11, 21.0.x, or 24.0.x.
2. **Supported -proc values** in javac --help.
3. **Actual compile command** passed by IDE/Maven/Gradle to javac, especially -processor, processor path, and -proc.
4. **Classpath/module path of processors** and of the sources to compile.
5. **Generated class/source outputs** in a clean build directory.

A command run in a terminal does not necessarily match the JDK toolchain that Gradle or Maven uses; CI may have a separate JDK for the compile step.

## 5. Selecting Processors: -processor, --processor-path, and Classpath

**-proc** selects the *execution mode*. The following options help javac find *which processor*:

| Option | Role |
| --- | --- |
| **-processor com.example.MyProcessor** | Specifies the processor class name to run, instead of relying on auto-discovery |
| **--processor-path path** or **-processorpath path** | Specifies where to locate annotation processors on a classpath-style path |
| **--processor-module-path path** | Locates annotation processors packaged as modules under JPMS |
| **-cp path** | Classpath for compiling sources; in some configurations also searched for processors when no separate processor path is given |
| **-Akey=value** | Passes an option to a processor; **not a directive replacing processor selection** |
| **-d out** | Class output directory |
| **-s generated-sources** | Directory receiving sources generated by processors via Filer |

**A processor JAR present on the classpath does not mean the processor runs automatically on JDK 23+.** An explicit activation option is needed. In modern builds, prefer a **separate processor path** and explicitly specify trusted processors.

### 5.1. Two Processor Discovery Methods

**Direct specification:**

~~~bash
javac -processor com.example.MyProcessor --processor-path processor.jar ...
~~~

This approach requires class **com.example.MyProcessor** to exist and be executable on the processor path. This is a highly intentional choice, suitable when the exact processors to run are known.

**Discovery via service provider:**

A JAR can contain the file:

~~~text
META-INF/services/javax.annotation.processing.Processor
~~~

The content can be the fully qualified name of the processor class, one name per line:

~~~text
com.example.MyProcessor
~~~

When processing is enabled and the processor sits on an appropriate search path, javac can discover it via this service-provider configuration. With JDK 23+, **configuring --processor-path** is one of the explicit ways to enable processing; merely having a service file in a classpath dependency without an activation option is not enough.

**Security note:** An annotation processor is Java code executed during the build, not merely statically checked metadata. Do not arbitrarily add untrusted JARs to the processor search path. The default change in JDK 23 helps prevent the compiler from unexpectedly executing a processor present on the classpath when the user has not explicitly requested it.

### 5.2. Processor Path Differs from Application Class Search Path

A processor may need to be loaded from **processor-classes** or **processor.jar**, while application source needs annotation types and other dependencies on the **compile classpath**.

In a small example, both can point to the same directory for ease of learning. In real projects, separating processor dependencies from runtime dependencies avoids unnecessarily bundling processor implementations into the final program.

Using named modules also has **--processor-module-path**, requiring the processor module to conform to JPMS's service/provider mechanism. Do not take the short classpath example below as the only model for module builds.

## 6. Complete Example: Observing -proc:none, -proc:only, -proc:full

This example set can compile on **JDK 21+** and **JDK 17 updates that support -proc:full**. The example uses **--release 17** to avoid source-version warnings from the processor. It does not rely on external processors or IDEs.

We create:

- Annotation **@Mark**.
- Processor **MarkProcessor**, printing a **NOTE** when seeing @Mark.
- Application **App**, normally printing one line when run.
- Two independent output layers: processor compilation directory and application compilation directory.

### 6.1. File Structure

~~~text
demo/
└── src/
    └── demo/
        ├── Mark.java
        ├── MarkProcessor.java
        └── App.java
~~~

From the **demo** directory, create the files below.

**src/demo/Mark.java**

~~~java
package demo;

import java.lang.annotation.ElementType;
import java.lang.annotation.Target;

@Target(ElementType.TYPE)
public @interface Mark {
}
~~~

**src/demo/MarkProcessor.java**

~~~java
package demo;

import java.util.Set;
import javax.annotation.processing.AbstractProcessor;
import javax.annotation.processing.RoundEnvironment;
import javax.annotation.processing.SupportedAnnotationTypes;
import javax.annotation.processing.SupportedSourceVersion;
import javax.lang.model.SourceVersion;
import javax.lang.model.element.TypeElement;
import javax.tools.Diagnostic;

@SupportedAnnotationTypes("demo.Mark")
@SupportedSourceVersion(SourceVersion.RELEASE_17)
public class MarkProcessor extends AbstractProcessor {
    @Override
    public boolean process(
            Set<? extends TypeElement> annotations,
            RoundEnvironment roundEnv) {
        if (!annotations.isEmpty()) {
            processingEnv.getMessager().printMessage(
                Diagnostic.Kind.NOTE, "PROCESSOR_RAN"
            );
        }
        return false;
    }
}
~~~

Notable points:

- **AbstractProcessor** provides the base building blocks for an annotation processor.
- **@SupportedAnnotationTypes("demo.Mark")** tells javac which annotation type the processor supports.
- **@SupportedSourceVersion(RELEASE_17)** states the source level the processor is designed to handle. In the example, the javac command compiles application source with **--release 17**.
- **process(...)** can be invoked across multiple rounds; the **!annotations.isEmpty()** condition only emits the NOTE when matching annotations are present in the round, avoiding printing the message on the final round that has no annotations.
- **return false** says the processor does not exclusively claim these annotations. That does not affect observing the three modes in the example.

**src/demo/App.java**

~~~java
package demo;

@Mark
public class App {
    public static void main(String[] args) {
        System.out.println("APP_RAN");
    }
}
~~~

### 6.2. Compile the Annotation and Processor First

From the demo directory:

~~~bash
javac --release 17 -d processor-classes src/demo/Mark.java src/demo/MarkProcessor.java
~~~

After this command, the **processor-classes** directory contains **demo/Mark.class** and **demo/MarkProcessor.class**. There is no service metadata in this example; we will use **-processor demo.MarkProcessor** to select the processor directly by name.

**Why are two steps needed?** The compiler must locate and load the compiled processor before using it to process another source file. This exercise intentionally separates the processor build step from the App build step to clarify the flow.

### 6.3. none Mode: Do Not Run Processor, Still Compile App

On a clean output directory:

~~~bash
javac --release 17 -proc:none -cp processor-classes -processorpath processor-classes -processor demo.MarkProcessor -d out-none src/demo/App.java
~~~

In this command:

- **-cp processor-classes** lets App see the **demo.Mark** annotation.
- **-processorpath processor-classes** allows javac to find the processor implementation.
- **-processor demo.MarkProcessor** explicitly specifies the processor name.
- Yet **-proc:none** takes effect and disables annotation processing.

Result:

- **Does not emit NOTE PROCESSOR_RAN**.
- **out-none/demo/App.class exists**.
- The application can run:

~~~bash
java -cp out-none demo.App
~~~

**Standard output:**

~~~text
APP_RAN
~~~

The presence of **-processor** in the command does not turn **-proc:none** into full processing. This is intentionally the mode that does not run processors.

### 6.4. only Mode: Run Processor, Do Not Compile App.class

Use a completely empty new output directory:

~~~bash
javac --release 17 -proc:only -cp processor-classes -processorpath processor-classes -processor demo.MarkProcessor -d out-only src/demo/App.java
~~~

In the example, the compiler emits the message:

~~~text
Note: PROCESSOR_RAN
~~~

This is **javac diagnostic output**, not stdout from the App application (App has not run). After the command, **out-only/demo/App.class is not created** by this compilation. If this processor used **Filer** to generate sources/resources, corresponding output could still appear; in the current example the processor only writes a NOTE, so no files are generated.

Do not run **java -cp out-only demo.App** and expect success: the App class has not been created.

### 6.5. full Mode: Run Processor Then Compile

~~~bash
javac --release 17 -proc:full -cp processor-classes -processorpath processor-classes -processor demo.MarkProcessor -d out-full src/demo/App.java
~~~

This time:

- Javac emits **Note: PROCESSOR_RAN**.
- Javac generates **out-full/demo/App.class**.
- The application can be run with:

~~~bash
java -cp out-full demo.App
~~~

Stdout:

~~~text
APP_RAN
~~~

Results table for the three test runs, assuming initially clean output directories:

| Command | NOTE PROCESSOR_RAN emitted? | App.class exists? | Can run App? |
| --- | --- | --- | --- |
| **-proc:none** | No | Yes | Yes |
| **-proc:only** | Yes | No | No, unless class exists from another build |
| **-proc:full** | Yes | Yes | Yes |

**Verified in practice on JDK 21** with all three commands using **--release 17**: none completes and generates App.class; only prints NOTE and does not generate App.class; full prints NOTE and generates App.class. This is the verification set for the exact difference -proc makes.

### 6.6. Avoid Wrong Conclusions When Old Class Files Exist

If you run multiple times into **the same out directory** without cleaning beforehand, **App.class** created by an earlier full run may remain. Then after **-proc:only**, seeing App.class in the directory does not prove only created the class.

For a fair verification, use separate **out-none**, **out-only**, and **out-full** directories as in the commands above, or delete **only the test's output directory** before each run. Do not carelessly run clean operations on project or other build directories.

## 7. Example When a Processor Actually Generates Code

The processor in section 6 only writes a NOTE so output is easy to observe. In real projects, a processor can call **processingEnv.getFiler().createSourceFile(...)** and write a new class, for example **demo.GeneratedMapper**. Then the difference is much more significant:

~~~text
- proc:none
    → Processor does not create GeneratedMapper.java.
    → If source calls GeneratedMapper without an existing class/source beforehand:
      javac reports cannot find symbol.

- proc:only
    → Processor can create GeneratedMapper.java in source output (-s).
    → Does not perform the final compilation step generating all class files.

- proc:full
    → Processor generates GeneratedMapper.java across processing rounds.
    → Javac continues compiling original sources and generated code when valid.
~~~

**This is a conceptual diagram**, not stdout of a complete program. Different processors can generate **.java** files, resources, or merely emit errors; not every processor generates code.

If you want to separate generated sources clearly, you can use:

~~~bash
javac -proc:full -processor com.example.MapperProcessor --processor-path mapper-processor.jar -s generated-src -d out -cp dependency.jar src/MyService.java
~~~

This is a **configuration template**; the processor, JAR, and source file names are illustrative placeholders, not claimed to exist. **-s generated-src** specifies the generated source directory, while **-d out** specifies class output. They have a different role from **-proc**.

### 7.1. Annotation Processors Run in Rounds

Javac can run processors across multiple rounds:

1. First, the processor receives annotations present in the initial sources.
2. The processor generates new sources if needed.
3. The compiler feeds the new sources into the next processing round.
4. When no more sources are generated, javac has a final round signaled by **processingOver()**.
5. If the policy is full, appropriate compilation proceeds to generate class files.

To observe, javac supports:

~~~bash
javac -XprintRounds -XprintProcessorInfo -proc:full -processor demo.MarkProcessor -cp processor-classes -processorpath processor-classes --release 17 -d out-full src/demo/App.java
~~~

Detailed output depends on version and processor. **-XprintRounds** and **-XprintProcessorInfo** are diagnostic tools; they do not replace **-proc:full** or an option enabling processing on newer JDKs.

## 8. Choosing the Right Configuration in Each Situation

| Situation | Suitable Mode | Why |
| --- | --- | --- |
| Project has no processors and wants predictable builds | **-proc:none** | Does not execute unintended processors |
| Project needs code generation then class creation to run | **-proc:full** with explicitly configured processors | Performs annotation processing and compilation |
| Need to check annotation rules without needing class output | **-proc:only** | Runs processors separately to inspect diagnostics or generated sources |
| JDK 23+ where sources lack generated classes after upgrade | Configure processor path / -processor or **-proc:full** | Default implicit discovery changed |
| Want to specify a single trusted processor | **-processor** with explicit processor path | Controls specifically which class executes |
| Want to compile while excluding processor generation step | **-proc:none** | Used to isolate root causes or build parts independent of generation |
| Project still uses an older JDK 17 | Check -proc:full support, update patch release, or choose appropriate -processor config | Do not assume every 17u accepts the full flag |

**There is no single best -proc option for every project**. The right policy depends on: whether the project truly needs processors; whether processors are trustworthy; when generated code is used; which JDK runs the compiler; where dependencies are placed; and whether CI checks clean outputs.

A long-lasting choice is to configure processors and processor search paths **explicitly**, so that JDK upgrades do not depend on implicit defaults.

## 9. Upgrading JDK 21/22 to 23+: How to Diagnose Missing Generated Code Errors

Suppose a project uses an annotation processor that generates a class **UserMapperImpl**. Before the JDK upgrade, the build worked; afterward javac reports:

~~~text
error: cannot find symbol
  symbol:   class UserMapperImpl
~~~

The cause **might** be that the newer JDK no longer runs processors implicitly. Yet do not jump to conclusions solely because the class name has an Impl suffix: other causes include a wrong processor JAR, unfound annotation, processor reporting an error, stale generate directory, or build configuration excluding the new source.

The right workflow:

1. Check **javac -version** in the exact failing task, not just java -version opened in a terminal.
2. Open the actual compile command and check whether **-proc:none** is present and whether **-processor**, **--processor-path**, **--processor-module-path**, or **-proc:only/full** is present.
3. Verify the processor JAR is actually present on the **processor path**, not merely inside compile/runtime dependencies.
4. Confirm the processor supports the source version, annotation type, and can be loaded.
5. Check the generated source output of a clean build.
6. Try enabling processing deliberately, for example using **-processor com.example.MyProcessor**, and recompile.
7. Conclude it is fixed only when generated sources/classes are actually created and tests pass on the exact CI JDK.

If **-proc:only** creates sources successfully yet the program still fails to run, it is very likely because you have not performed the full compile step (or have not compiled generated sources in a later step).

If **-proc:full** produces no generated sources/classes, check whether the processor was loaded or matching annotations exist; **-proc:full does not guarantee that a processor exists**.

If **-proc:none** compiles successfully yet the application probably needs code generation, it may be using **old** class files. Check with a clean build and manage output separately to avoid masking errors.

### 9.1. Checking the Java 21/22 Implicit-Processing Note

In JDK 21 and some transitional configurations, javac can print a note like **annotation processing is enabled because one or more processors were found on the class path**. This is not a message that code is wrong, but a sign that the build **is relying on the automatic processor-discovery policy**.

Fix by configuring the **processor path and required processors**, or enabling explicit processing according to the supported version. Do not just use **-Xlint:-options** to hide the note and skip upgrading the configuration, because future compilers may behave differently.

## 10. Maven, Gradle, IDE, and Java Toolchain

In Maven or Gradle, you usually do not type the javac command directly. The plugin/build tool configures compiler arguments based on dependency configuration, annotation-processor configuration, and the Java toolchain version.

**Gradle with the Java plugin** has a dependency configuration dedicated to annotation processors:

~~~groovy
plugins {
    id 'java'
}

dependencies {
    annotationProcessor 'org.example:demo-processor:1.0'
}
~~~

This is only a **syntax template** with illustrative artifact coordinates; replace with actual dependencies and appropriate repositories. The build tool can pass an explicit processor path when seeing an annotationProcessor dependency. Do not treat this snippet as a standalone runnable project example.

**Maven Compiler Plugin** has configurations for processors, processor paths/dependencies, and depending on version, the **proc** property. The plugin version and JDK determine the generated javac CLI; check the documentation of the plugin in use. Do not assume **maven.compiler.proc** or processor configuration of every Maven Compiler Plugin version has the same default.

**IDEs** can enable annotation processing for a project, yet settings often differ among javac CLI, IntelliJ, and the Eclipse compiler. Results succeeding only in the IDE while failing on CI usually mean the actual configurations of the two places differ.

### 10.1. Toolchain Changes Compiler Policy

For example, the shell uses **javac 24**, yet the Gradle toolchain selects **JDK 21** for the compileJava task. In that case, processor policy is determined by the javac/JDK executing the corresponding task, not by the java version you happened to open in the terminal.

A reliable check is to record the **compiler command/toolchain**, **processor configuration**, **generated source output**, and **build logs** of the same task.

## 11. Common Warnings and Errors

### 11.1. "Invalid flag: -proc:full"

A javac version that is too old may not understand the **full** value. Check **javac -version** and **javac --help**, then update to a newer patch release if possible. Older releases may still support **-proc:none** and **-proc:only**, yet that does not mean **-proc:full** exists.

Do not change it to **-proc:none** to "get rid of the option error" if the project needs a processor. Doing so may just turn the error into missing generated classes.

### 11.2. "Annotation processor ... not found"

Javac was asked to run a processor yet could not find the class or could not load the processor. Check:

- The fully qualified name in **-processor**.
- The location containing the processor class/JAR on **-processorpath** or appropriate module path.
- Dependencies that the processor itself needs for initialization.
- Bytecode compatibility: a processor compiled with a newer JDK may not load on an older JVM running javac.
- With JPMS: provider declaration and module visibility.

**Do not solve this by merely adding an import in application source**. Imports serve type references in the application, whereas processor loading happens in the compiler environment.

### 11.3. Processor Runs Yet No Class File Exists

If using **-proc:only**, this is **by design**. If class output is desired, switch to **-proc:full** or run the subsequent compilation step.

If using full, check compiler errors, the **-d** path, output from generated source rounds, and completion of compilation. Do not conclude solely from the existence of a generated .java file.

### 11.4. Processor Does Not Run on JDK 23+

Check that the invocation has **at least one appropriate processing-enabling option**. Merely having a processor appear on the classpath is no longer sufficient without a requesting option. Configuring **-processor** with the explicit name together with the processor search path is the easiest way to verify.

### 11.5. "Supported source version ... less than -source ..."

A processor declaring a supported source level lower than the compilation target can emit a warning. In the example, the annotation processor declares **RELEASE_17**, so **--release 17** makes results easy to compare. In Java 21/25 projects, update the processor to support the appropriate source level instead of always lowering **--release** just to avoid warnings.

### 11.6. No Processor Executes Even With -proc:full

When **-proc:full** is set yet the classpath contains no discoverable processor (or the wrong processor is selected), javac can still compile normal code without any processor actually running. Use **-processor** to select explicitly and try **-XprintProcessorInfo** when diagnostics are needed.

## 12. Checklist to Configure Once and Use Reliably

Before accepting an annotation processing configuration for the main build:

- [ ] Identified **the actual javac and JDK update version**.
- [ ] Chosen the **none / only / full** policy based on build purpose.
- [ ] If processors are needed, explicitly specified **processor names or processor path** properly.
- [ ] Processor dependencies are properly separated from runtime dependencies.
- [ ] No implicit reliance on processors appearing accidentally on the classpath.
- [ ] Source-generated and class-generated outputs are verified with a **clean build**.
- [ ] Distinguished **--release** from **javac's processing policy**.
- [ ] Verified whether older JDKs support the **-proc:full** value.
- [ ] Ran tests on the exact JDK used in CI and production builds.
- [ ] Annotation processors and their dependencies come from trusted sources.

**Remember:** **-proc:none** compiles without running annotation processors; **-proc:only** only processes annotations; **-proc:full** both processes and compiles. More importantly, since **JDK 23**, annotation processing requires an explicit request/configuration and no longer runs by default merely because a processor is on the classpath. Always verify the **actual javac**, select a trusted processor, check clean output, and do not confuse **--release** with the **-proc** option.
