# Bridge methods and synthetic members in Java compilation output

## 1. Lesson objectives

Java source code does not always correspond one-to-one with the methods and fields stored in the .class file. The compiler may generate additional members to preserve language semantics after translating into bytecode. Two notable cases to study are:

- **Bridge method**: an intermediate method generated by the compiler to maintain overriding and dynamic dispatch when a method at the bytecode level has a different descriptor from the specialized method in source. Commonly encountered with generic type erasure and covariant returns.
- **Synthetic member**: a member marked as compiler-generated, not corresponding directly to a normal source declaration. Many methods/fields carry the **ACC_SYNTHETIC** flag in the class file.

A bridge method is usually also a synthetic method in javac output, but synthetic members have a broader scope. Not every compiler-generated method is a bridge; nor is every compiler-generated member marked synthetic.

After this lesson, you will be able to compile Java 17+ yourself, find bridges with javap, inspect ACC_BRIDGE and ACC_SYNTHETIC flags, compare with Reflection, explain generic erasure and covariant returns, and understand the limitations when analyzing output from different compilers.

## 2. From Java source signature to JVM descriptor

In Java source, overriding is evaluated by method name, parameters, type relationships, generic bounds, return-type substitutability, and visibility/static/final rules. On the JVM, a method is stored with a **descriptor** describing its parameter type list **and return type**.

~~~text
String process(String input)
    descriptor: (Ljava/lang/String;)Ljava/lang/String;

Object process(Object input)
    descriptor: (Ljava/lang/Object;)Ljava/lang/Object;

Number read()
    descriptor: ()Ljava/lang/Number;

Integer read()
    descriptor: ()Ljava/lang/Integer;
~~~

Some notations:

| Notation | Meaning |
| --- | --- |
| Ljava/lang/String; | Reference to java.lang.String |
| Ljava/lang/Object; | Reference to java.lang.Object |
| I | int |
| V | void |
| (I)V | Takes int, returns void |
| ()Ljava/lang/Number; | No parameters, returns Number |

In Java source, it is not possible to overload solely by differing return types. However, the bytecode descriptor includes the return type; the compiler can create two methods with the same name and parameters but different return types in the .class file, something a programmer cannot declare as two ordinary Java methods.

**Key point:** reading a javap line displaying generic type T is not enough to know the JVM descriptor. You need to inspect javap -v to observe the descriptor after type erasure and Signature metadata.

## 3. Why does generic type erasure need a bridge?

Suppose the superclass defines:

~~~java
public class Processor<T> {
    public T process(T input) {
        return input;
    }
}
~~~

With T having no specific upper bound, type erasure replaces T with Object in the JVM descriptor:

~~~text
Processor.process:
(Ljava/lang/Object;)Ljava/lang/Object;
~~~

The subclass specializes T to String:

~~~java
public final class StringProcessor extends Processor<String> {
    @Override
    public String process(String input) {
        return input.strip();
    }
}
~~~

The Java compiler confirms process(String) is a valid override of the method inherited from Processor<String>. However, the source method in the subclass is compiled with the descriptor:

~~~text
(Ljava/lang/String;)Ljava/lang/String;
~~~

With only that method, the JVM would not see the same descriptor as Processor's process(Object):Object method when executing a call through the erased superclass type. To preserve dispatch, javac generates an intermediate method in StringProcessor with descriptor process(Object):Object. The equivalent logic is:

~~~text
StringProcessor.process(Object):Object   [bridge]
        |
        v
checkcast parameter to String
        |
        v
StringProcessor.process(String):String   [method from source]
        |
        v
Return String as Object
~~~

That is the bridge method. It ensures client code calling through a Processor<String> reference still executes the StringProcessor implementation. Generics do not create additional runtime copies for every type T: specialization in this context is tied to erasure and bridge rules.

**Not every generic method has a bridge**; the compiler only generates one when needed to maintain the proper method relationship in bytecode. For example, merely declaring List<String> or a generic method that does not require overriding with a different descriptor does not automatically generate a corresponding bridge.

## 4. Complete Java 17 example: generic override and Reflection

Create the structure:

~~~text
bridge-lab/
├── src/
│   └── demo/
│       └── bridge/
│           ├── Processor.java
│           ├── StringProcessor.java
│           └── BridgeDemo.java
└── out/                      # Will be created before the compile step
~~~

### File src/demo/bridge/Processor.java

~~~java
package demo.bridge;

public class Processor<T> {
    public T process(T input) {
        return input;
    }
}
~~~

### File src/demo/bridge/StringProcessor.java

~~~java
package demo.bridge;

import java.util.Locale;

public final class StringProcessor extends Processor<String> {
    @Override
    public String process(String input) {
        return input.strip().toUpperCase(Locale.ROOT);
    }
}
~~~

The strip() method has existed since Java 11; toUpperCase(Locale.ROOT) makes uppercase normalization consistent across the example. @Override is an annotation confirming the override relationship at the source level; it does not directly instruct javac to generate a bridge.

### File src/demo/bridge/BridgeDemo.java

~~~java
package demo.bridge;

import java.lang.reflect.Method;
import java.util.Arrays;
import java.util.Comparator;

public final class BridgeDemo {
    private BridgeDemo() {
    }

    public static void main(String[] args) {
        Processor<String> processor = new StringProcessor();
        System.out.println("Call: " + processor.process("  java  "));

        Method[] methods = StringProcessor.class.getDeclaredMethods();
        Arrays.sort(methods,
                Comparator.comparing(m ->
                        m.getParameterTypes()[0].getSimpleName()));

        for (Method method : methods) {
            if (method.getName().equals("process")) {
                System.out.printf(
                        "%s -> %s | bridge=%s | synthetic=%s%n",
                        method.getParameterTypes()[0].getSimpleName(),
                        method.getReturnType().getSimpleName(),
                        method.isBridge(),
                        method.isSynthetic());
            }
        }
    }
}
~~~

These are three complete source files, each public class placed in a file of the same name. Reflection getDeclaredMethods() retrieves methods belonging specifically to the StringProcessor class, including compiler-generated methods. Arrays.sort fixes the order as Object then String; the default order of the Reflection array is **not guaranteed**. Because the example only uses process methods that each have one parameter, getParameterTypes()[0] is valid.

### Compiling from the bridge-lab root directory

On Bash:

~~~bash
mkdir -p out
~~~

On Windows PowerShell:

~~~powershell
New-Item -ItemType Directory -Path out -Force | Out-Null
~~~

After creating out, run:

~~~sh
javac -encoding UTF-8 --release 17 -d out src/demo/bridge/Processor.java src/demo/bridge/StringProcessor.java src/demo/bridge/BridgeDemo.java
java -cp out demo.bridge.BridgeDemo
~~~

**Exact stdout on JDK 17+:**

~~~text
Call: JAVA
Object -> Object | bridge=true | synthetic=true
String -> String | bridge=false | synthetic=false
~~~

Line-by-line explanation:

1. Through a variable of type Processor<String>, calling process still uses the StringProcessor implementation, with the result stripped and uppercased to JAVA.
2. Method process(Object) has flags bridge=true and synthetic=true: this is the method added to the class file by javac.
3. Method process(String) has both flags false: this is the method written by the author in StringProcessor.java.

In the source of StringProcessor there is only **one** declaration of process(String); the second method should not be called an intentional overload by the programmer.

## 5. Reading javap output at each level

From the bridge-lab root, run:

~~~sh
javap -classpath out -p demo.bridge.StringProcessor
~~~

Notable lines:

~~~text
public final class demo.bridge.StringProcessor extends demo.bridge.Processor<java.lang.String> {
  public demo.bridge.StringProcessor();
  public java.lang.String process(java.lang.String);
  public java.lang.Object process(java.lang.Object);
}
~~~

This command shows two methods with the same name in the class file, but does not list all flags. To see the descriptor and flags:

~~~sh
javap -classpath out -v -p demo.bridge.StringProcessor
~~~

Find the section corresponding to the bridge (below is an intentionally abbreviated excerpt; constant-pool indexes and offsets may differ):

~~~text
public java.lang.Object process(java.lang.Object);
  descriptor: (Ljava/lang/Object;)Ljava/lang/Object;
  flags: (...) ACC_PUBLIC, ACC_BRIDGE, ACC_SYNTHETIC
  Code:
    ...
    checkcast     ... // class java/lang/String
    invokevirtual ... // Method process:(Ljava/lang/String;)Ljava/lang/String;
    areturn
~~~

Important instructions:

- **checkcast**: verifies that the Object parameter can be used as a String when forwarding. If incompatible, ClassCastException may occur at runtime.
- **invokevirtual**: invokes the subclass's implementation method process(String).
- **areturn**: returns the result reference to the caller according to the bridge's Object descriptor.

In the class file generated by javac in this example, the bridge is marked with both ACC_BRIDGE and ACC_SYNTHETIC. Flags are clearer evidence than guessing from the method name. Javap -p reveals non-public methods as well; javap -v allows inspecting code and metadata.

Compare with the superclass:

~~~sh
javap -classpath out -p demo.bridge.Processor
javap -classpath out -v -p demo.bridge.Processor
~~~

In the human-readable display, javap may present the generic signature T, but the actual descriptor of Processor.process is Object -> Object. The Signature metadata stores generic information for tools and does not change the descriptor used for JVM dispatch.

## 6. Two call paths and the runtime role of the bridge

Consider the illustrative snippet placed inside a valid method:

~~~java
Processor<String> parentView = new StringProcessor();
StringProcessor childView = new StringProcessor();

String first = parentView.process(" one ");
String second = childView.process(" two ");
~~~

The compiler may encode the call through parentView using the descriptor of Processor.process(Object):Object, and then cast the result to String to match the source expression type. Thus the JVM needs the bridge in StringProcessor to dispatch to the typed process(String).

With childView, the compiler directly sees the process(String):String method and can call the specialized descriptor. Both call paths still have the same business semantics.

A bridge is not an API meant to be called directly in source. It is an implementation detail that keeps the override contract valid even after generics are erased.

### Intentional experiment: raw type causes ClassCastException

The following snippet is an **unsafe illustrative method**, not a standalone class:

~~~java
@SuppressWarnings({"rawtypes", "unchecked"})
static void unsafeCall() {
    Processor raw = new StringProcessor();
    raw.process(123);
}
~~~

Because the raw type bypasses part of compile-time generic checking, the compiler allows the call with Integer matching the descriptor taking Object (usually producing raw/unchecked warnings if not suppressed). At runtime, the bridge StringProcessor.process(Object) must cast Integer to String, leading to **ClassCastException**. This is a useful example for understanding checkcast inside a bridge, not a programming practice to follow.

One should not think the compiler inserts bridges to "automatically fix" wrong parameter types. Bridges preserve dispatch and required runtime checks; generic type safety still depends on using proper source types instead of raw types.

## 7. Covariant returns can also generate bridges

Generic erasure is not the only cause. Java allows an override to return a **subtype reference type** relative to the superclass's return type; that is a covariant return type. However, the JVM descriptor includes the return type, so the compiler may generate a bridge to maintain compatibility with calls using the old descriptor.

Create the file **src/demo/covariant/CovariantDemo.java** with the complete contents:

~~~java
package demo.covariant;

class NumberSource {
    Number read() {
        return 5;
    }
}

class IntegerSource extends NumberSource {
    @Override
    Integer read() {
        return 7;
    }
}

public final class CovariantDemo {
    public static void main(String[] args) {
        NumberSource source = new IntegerSource();
        System.out.println("Value: " + source.read());
    }
}
~~~

Three classes are in the same file; only CovariantDemo is public, so naming the file CovariantDemo.java is valid.

From the project root where out already exists, compile and run:

~~~sh
javac -encoding UTF-8 --release 17 -d out src/demo/covariant/CovariantDemo.java
java -cp out demo.covariant.CovariantDemo
~~~

**Stdout:**

~~~text
Value: 7
~~~

Inspect bytecode:

~~~sh
javap -classpath out -p demo.covariant.IntegerSource
javap -classpath out -v -p demo.covariant.IntegerSource
~~~

Notable methods in class IntegerSource:

~~~text
java.lang.Integer read();
java.lang.Number read();
~~~

Method Integer read() is the override declared by the author. Method Number read() is the bridge generated by javac, carrying flags **ACC_BRIDGE, ACC_SYNTHETIC** in the example output. Both methods have the same name and no parameters, but **different return types in the JVM descriptor**. Writing two such methods directly in Java source would be invalid because Java does not allow overloading by return type.

Distinguish this from bridges caused by generics: in this covariant return case, no parameter is erased from T to Object; the mismatch that needs bridging lies in the return type Number versus Integer.

## 8. Synthetic members are broader than bridge methods

A synthetic member is a member marked by class file metadata. Certain members generated by the compiler to implement lambdas, enums, nested classes, or other source constructs can be synthetic; their count, names, and bytecode form depend on the compiler/JDK.

### Lambda example: synthetic but not a bridge

Create **src/demo/synthetic/LambdaDemo.java**:

~~~java
package demo.synthetic;

public final class LambdaDemo {
    private LambdaDemo() {
    }

    public static void main(String[] args) {
        Runnable task = () -> System.out.println("task");
        task.run();
    }
}
~~~

Compile and run with out already created:

~~~sh
javac -encoding UTF-8 --release 17 -d out src/demo/synthetic/LambdaDemo.java
java -cp out demo.synthetic.LambdaDemo
javap -classpath out -v -p demo.synthetic.LambdaDemo
~~~

**Stdout:**

~~~text
task
~~~

With the javac used in this exercise, javap -p shows a helper named like **lambda$main$0**, and javap -v marks this helper **ACC_SYNTHETIC** but not ACC_BRIDGE. This is a method serving the lambda body; it does not exist because an overridden method with a different descriptor needs bridging.

With the modern lambda mechanism, the compiler typically uses **invokedynamic** and a bootstrap related to LambdaMetafactory. One should not assume every lambda must create a fixed class file with a predictable name. A helper name like lambda$main$0 is a **compiler detail**, not an API name for business code to depend on.

### Other cases

- **Enum**: the compiler provides methods such as values() and valueOf(String). However, do not infer that every compiler-provided method carries the synthetic flag. Javac may also generate an internal field storing the array of enum values, marked synthetic; commonly seen field names like $VALUES are not part of the language contract.
- **Nested classes**: older compilers could generate access$... helpers to cross certain private boundaries. Since Java 11, the **nestmates** mechanism allows many accesses to be represented directly in the JVM, so the same source may no longer produce such helpers.
- **Bytecode transformation tools**: instrumentation libraries, proxies, AOP, or code generators can create their own members. To know for sure, read the actual class file and metadata; do not assume a fixed list of synthetic names across all compilers.

**Not every compiler-generated member has the ACC_SYNTHETIC flag.** There are methods generated by the compiler to intentionally provide Java APIs. And not every synthetic method has the ACC_BRIDGE flag. This is the most important distinction when reading a class file that has more methods than source.

## 9. Distinguishing related concepts

| Concept | Nature | Indicators |
| --- | --- | --- |
| Overload | Same name, different parameters according to Java rules | Can be declared in source |
| Override | Subclass replaces inherited method implementation | Can be checked with @Override |
| Generic type erasure | Removes/replaces generic type parameters in runtime representation | Descriptor is Object or upper bound |
| Bridge method | Forwards calls to preserve proper overriding in bytecode | ACC_BRIDGE, usually ACC_SYNTHETIC |
| Synthetic member | Member marked as generated by the compiler | ACC_SYNTHETIC or related metadata |
| Covariant return | Override returns a more specific reference type | May need a bridge to change the return descriptor |
| Normal helper | Method written by the author to split logic | Not automatically synthetic |
| Lambda helper | A form of code transformation for a lambda body | May be synthetic, not a bridge |

Points not to confuse:

- Using generics **does not mean every generic class generates a bridge**.
- Using @Override **does not automatically create a bridge**; it verifies the overriding relationship according to the language.
- A bridge method is usually synthetic with javac in the examples, but a synthetic helper is not necessarily a bridge.
- A method with the synthetic flag may still be needed at runtime. **Synthetic does not mean it can be safely removed**.
- Bytecode can contain two descriptors with different return types even when Java source does not allow you to write two such overloads.

## 10. Reflection: identifying compiler-generated methods

Java Reflection has two important methods:

~~~java
boolean bridge = method.isBridge();
boolean synthetic = method.isSynthetic();
~~~

These APIs read information about methods actually loaded by the class loader. To inspect methods directly in a class, use **Class.getDeclaredMethods()**. It returns both public and private methods declared in the class file, including bridge/synthetic ones if present; it does not aggregate all inherited methods.

There is also **Class.getMethods()** to get accessible public methods, including public inherited methods. If you are looking for a private helper or all methods added by the compiler in a specific class, getDeclaredMethods() is the more appropriate choice.

Technical notes:

1. Do not rely on the ordering of Method[]; if stable output is needed, sort it.
2. Do not use method name alone to distinguish bridges. Two methods can have the same name; check parameter types, return type, and flags.
3. isSynthetic() by itself does not tell you **why** the compiler generated the method; you need to inspect the bytecode.
4. For other member types, there are Field.isSynthetic(), Constructor.isSynthetic(), and Class.isSynthetic() where applicable; not every field/constructor touched by the compiler is synthetic.
5. Reflection and javap answer two complementary questions: Reflection tells you how runtime members are seen; javap -v tells you the descriptors, flags, and instructions of the class file.

### What should a method-scanning framework do?

A framework using Reflection to discover endpoints, serializers, AOP advice, or method handlers may encounter both the bridge and the source method at the same time. If it registers each entry as an independent business action, there is a risk of **duplicate methods**, wrong parameter types, or double processing.

The solution depends on the framework: it usually needs to identify bridges, cross-reference the original declaration, and select the method representing the API contract to expose. However, **you should not strip out all synthetic members from every task**; when analyzing JVM dispatch or bytecode, bridges are an essential part of the call path.

## 11. Binary impact and library upgrades

After compilation, client bytecode stores method references with name, target class, and descriptor. When upgrading a library, changing generic hierarchies, generic bounds, covariant returns, or override forms can alter the generated methods/compiler bridges.

Therefore, three questions should be separated:

1. **Source compatibility**: does the client source code still compile against the new API?
2. **Binary compatibility**: do previously compiled client classes still link with the new classes?
3. **Behavioral compatibility**: do dispatch and casts at runtime still return the correct results?

The Processor/StringProcessor example shows that the compiler needs a bridge so a call to process(Object):Object via the superclass type can execute the typed process(String):String in the subclass.

You should not remove bridges yourself when optimizing bytecode or writing instrumentation tools. An incompatible set of classes/JARs can lead to wrong dispatch or linkage errors such as AbstractMethodError or NoSuchMethodError in specific configurations. Removing a bridge does not guarantee getting the exact same error every time: the outcome depends on descriptors, class hierarchy, and caller bytecode.

In large projects:

- Keep artifacts built consistently with one another.
- When changing a public generic API, check both source and binary compatibility.
- When reading bytecode processed by proxies/instrumentation, verify actual flags instead of guessing based on the source compiler.
- Do not depend on synthetic helper names such as lambda$main$0 or $VALUES in business logic.
- Do not directly invoke bridges via Reflection as an official API path unless there is a clear tooling need.

## 12. Investigation workflow for unfamiliar methods in .class files

1. **Confirm the right artifact**: locate the .class/JAR file actually being run by the application; avoid accidentally reading an old build.
2. **List methods**: use javap -classpath out -p package.Class.
3. **Inspect descriptors**: use javap -classpath out -v -p package.Class, checking descriptor, flags, Signature, and Code.
4. **Cross-check source**: inspect superclass/interfaces, generic bounds, overrides, and return types.
5. **Read the delegation target**: the bridge may cast and then call the specialized method; not every bridge has the exact same instructions.
6. **Verify via Reflection**: Method.isBridge()/isSynthetic(), parameters, return type.
7. **Test dynamic dispatch**: call the same object through the superclass type and subclass type and compare behavior.

| Observation | Common wrong conclusion | How to verify |
| --- | --- | --- |
| Javap shows an extra process(Object) | The author wrote an Object overload | Check source, ACC_BRIDGE, and Code |
| Generics are present | There must be a bridge | Check whether an override needs descriptor bridging |
| Method is marked synthetic | Can be removed without runtime impact | Check whether it serves dispatch/code transformation |
| access$000 is not seen | No private access between nested classes | Check nestmates and the compiler in use |
| getDeclaredMethods() has two methods with the same name | Reflection is buggy | Check descriptors and bridge flag |
| Java source only has process(String) | Bytecode also has only one method | Use javap -p/-v |
| Covariant return without generics | Cannot have a bridge | Check the return type in the descriptor |
| lambda$... seen in javap | The name can be used as a long-term public API | It is an implementation detail that can change |

## 14. Knowledge checklist

- Distinguish Java source signatures from JVM descriptors.
- Explain why unbounded T is erased to Object.
- Understand process(String) is the source method, and process(Object) is the bridge generated by javac.
- Compile/run the example yourself and observe the expected Reflection output.
- Read ACC_BRIDGE, ACC_SYNTHETIC, and instructions via javap -v.
- Understand covariant returns can also generate bridges.
- See that synthetic lambda helpers are not bridges.
- Know that not everything compiler-generated is synthetic, and not every synthetic member is a bridge.
- Know the significance of bridges for polymorphism, binary compatibility, and Reflection tools.

### Further reading

- **Java Language Specification (JLS)**: *Type Erasure*, *Method Signature*, *Overriding*, and *Return-Type-Substitutability*.
- **Java Virtual Machine Specification (JVMS)**: method descriptors, method_info format, ACC_BRIDGE, ACC_SYNTHETIC, Signature, and Code.
- **Reflection API**: java.lang.reflect.Method.isBridge(), isSynthetic(), and Class.getDeclaredMethods().

A bridge method is a bytecode adapter for polymorphic calls whose descriptors must be preserved after compiler transformations. A synthetic member is a broader concept denoting compiler-generated markers. When you understand **source code, descriptors, flags, and bytecode instructions**, you can accurately explain why compilation output contains members not written in source.
