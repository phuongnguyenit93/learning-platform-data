# Reading Major and Minor Versions and UnsupportedClassVersionError in Java

A `.class` file is bytecode in the Java Virtual Machine (JVM) format, with its own **class-file version**. When `javac` generates bytecode at a language/compilation target level, the class file has a **major version** and **minor version** in its header. The JVM must support that class-file format to load and link the class.

If an older runtime receives a class built for a newer Java version, it may throw **`java.lang.UnsupportedClassVersionError`**. This error relates to the ability to read the **bytecode format**; it is different from missing method/API errors, different from compile-time syntax errors, and does not mean “the Maven/Gradle library version is too new” in terms of artifact version number.

This lesson explains how to read major/minor numbers, identify the corresponding Java release, use `javap` or a standalone Java program to read the header, understand preview class files, diagnose errors, and choose compilation configurations that ensure the application runs on the target JDK/JRE.

## 1. Java Source, javac, Class File, and JVM Are Four Layers of Information

For example, a project has:

~~~text
HelloVersion.java   -- javac -->   HelloVersion.class   -- JVM -->   execution
      |                               |                       |
 Java source code                  bytecode                Java runtime
  syntax/APIs needed              major/minor             version limit
~~~

Easily confused pieces of information:

| Information | What does it describe? | How to check |
| --- | --- | --- |
| Source language level | Syntax/semantics accepted by the compiler, e.g., Java 17 | `javac --release 17` or build configuration |
| Compiler version | The `javac` binary actually running | `javac -version` |
| Class file major/minor | Generated bytecode format | `javap -verbose` or reading the first 8 bytes |
| Runtime version | The JVM actually launched by the `java` command | `java -version` |
| Runtime libraries/APIs | Classes and methods actually present on the runtime classpath/module path | JDK APIs and actual dependencies |

**JDK 21 can produce class files for Java 17** when properly configured with `--release 17`. Therefore, you cannot deduce the major number solely from `javac -version`. Conversely, a class having a compatible major version does not prove that all dependencies and APIs used by the program are also runtime compatible.

## 2. Class File Header: magic, minor, and major

According to the class file structure, the first fields are:

~~~text
Offset (byte)   Length   Field
0–3             4        magic          = 0xCAFEBABE
4–5             2        minor_version
6–7             2        major_version
8...                     constant_pool_count, constant pool, ...
~~~

Both version fields are **unsigned 16-bit** integers stored in **big-endian** order (high byte first). The four magic bytes `CA FE BA BE` identify the class-file format.

For example, a normal Java 17 file begins with:

~~~text
CA FE BA BE 00 00 00 3D ...
| magic     |minor|major|
             0x0000 0x003D
                     0x3D = 61
~~~

This means:

- `major_version = 61`: the class file corresponds to Java 17.
- `minor_version = 0`: the typical value of a class file created by a Java 17 compiler without using preview features.
- `0xCAFEBABE`: magic number; it is **not** a version number.
- Bytecode after the header also contains the constant pool, class info, fields, methods, attributes, etc. Reading only the first 8 bytes identifies the header, **it does not verify the entire file**.

Another example:

~~~text
CA FE BA BE 00 00 00 34
~~~

`0x34` in the two major bytes is 52 in decimal, which is the Java 8 class-file level. Do not misread `00 34` as decimal 34.

**Major and minor are two independent fields**, not a floating-point version notation. For example, `61.0` means major = 61, minor = 0; `61.65535` means major = 61, minor = 65535, **not** Java 61 patch 65535.

For releases from Java 5 onward in the table, a convenient mnemonic is **major = release number + 44**. For instance, 17 + 44 = 61, 21 + 44 = 65. Older Java 1.x versions must be looked up separately: do not apply the formula to Java 1.1.

The table gives the **class file format version**; it does not by itself tell whether a runtime supports a specific API or which JDK distribution is installed. A typical Java 17 runtime supports class files up to major 61; a typical Java 11 runtime supports up to 55. When encountering a major version above the limit, the JVM may throw `UnsupportedClassVersionError`.

If you have to decode a major version not in the table and know it follows the modern Java rule, you can compute the release as `major - 44`; you still need to check the specification and actual runtime support, especially when preview features are involved.

## 4. Inspecting major/minor with javap -verbose

The `javap` tool is included in the JDK and can display class-file metadata. Create the file **`HelloVersion.java`**:

~~~java
public final class HelloVersion {
    public static void main(String[] args) {
        System.out.println("Hello, bytecode!");
    }
}
~~~

On a machine with JDK 17, run from the directory containing the file:

~~~bash
javac -encoding UTF-8 --release 17 HelloVersion.java
javap -verbose HelloVersion
java HelloVersion
~~~

`javac` normally prints nothing to stdout on successful compilation. The full output of `javap -verbose` also includes the constant pool and attributes; the important part to look for is:

~~~text
  minor version: 0
  major version: 61
~~~

**Exact stdout of `java HelloVersion`:**

~~~text
Hello, bytecode!
~~~

You can also specify the compiled file directly:

~~~bash
javap -verbose HelloVersion.class
~~~

`javap` reads the class file contents or the class found on the classpath. If multiple JARs contain the same binary name, provide **the specific path to the file** or an appropriate `-classpath`; otherwise, you may accidentally read a different copy of the class.

### Reading a class inside a JAR

Suppose the file `app.jar` actually contains `com/example/app/Main.class`. Use:

~~~bash
javap -verbose -classpath app.jar com.example.app.Main
~~~

This command line is a **method example**, running only when that JAR and class exist. When inspecting a class with `javap`, look for `major version` and `minor version` of the specific class. **A JAR does not have a single major version** if it contains multiple classes compiled at different levels.

If you want to examine all class files inside, list them first:

~~~bash
jar --list --file app.jar
~~~

Then check the necessary classes (especially program entry classes and dependencies likely to fail).

## 5. Reading Header Bytes with a Standalone Java 17 Program

`javap` is the most convenient tool, but you can verify the header yourself without external libraries. Create the file **`ClassVersionReader.java`** in the same directory as `HelloVersion.java`:

~~~java
import java.io.DataInputStream;
import java.io.FileInputStream;
import java.io.IOException;

public final class ClassVersionReader {
    public static void main(String[] args) throws IOException {
        if (args.length != 1) {
            System.err.println("Usage: java ClassVersionReader <file.class>");
            return;
        }

        try (DataInputStream in =
                     new DataInputStream(new FileInputStream(args[0]))) {
            int magic = in.readInt();
            int minor = in.readUnsignedShort();
            int major = in.readUnsignedShort();

            System.out.printf("magic: 0x%08X%n", magic);
            System.out.printf("minor version: %d%n", minor);
            System.out.printf("major version: %d%n", major);

            if (magic != 0xCAFEBABE) {
                System.err.println("Not a Java class file");
            }
        }
    }
}
~~~

Place both files in the same directory and run with JDK 17:

~~~bash
javac -encoding UTF-8 --release 17 HelloVersion.java ClassVersionReader.java
java ClassVersionReader HelloVersion.class
~~~

**Exact stdout:**

~~~text
magic: 0xCAFEBABE
minor version: 0
major version: 61
~~~

Explanation: `DataInputStream.readInt()` reads 4 big-endian bytes, `readUnsignedShort()` reads 2 unsigned bytes so minor = 0 or 65535 are both represented accurately. `try-with-resources` ensures the stream is closed. A file that is too short will cause `EOFException`; this is a **minimal header reader** program, not a complete class-file validator.

### Compiling the same code for Java 8

With a JDK supporting target `--release 8` (such as JDK 17), run:

~~~bash
javac -encoding UTF-8 --release 8 HelloVersion.java ClassVersionReader.java
java ClassVersionReader HelloVersion.class
~~~

**Exact stdout once both sources have just been recompiled successfully:**

~~~text
magic: 0xCAFEBABE
minor version: 0
major version: 52
~~~

The source code did not change, yet the class file major changed **61 → 52** because the target release changed. The `ClassVersionReader` program is also compiled as a major 52 class, so it can run on a Java 8 runtime if the runtime has the required dependencies/APIs. The examples above use APIs available in Java 8.

If a build has multiple modules or JARs, you must check **all relevant classes**, not just the class with `main`. A major 52 `Main.class` can still depend on a library containing major 61 classes, causing an error when the Java 8 JVM needs to load that class.

## 6. When Does UnsupportedClassVersionError Occur?

`java.lang.UnsupportedClassVersionError` is a kind of `LinkageError` (specifically a subclass of `ClassFormatError`), thrown by the JVM when a class-file version is unsupported.

Typical example:

- `javac --release 17` creates `HelloVersion.class` major 61.
- Run `java HelloVersion` with a **Java 11** JVM (limit major 55).
- The Java 11 JVM does not understand the major 61 class-file format and refuses to load the class.

The error message may look roughly like this (illustrative; path/class names and wording depend on the JDK):

~~~text
java.lang.UnsupportedClassVersionError:
  HelloVersion has been compiled by a more recent version of the Java Runtime
  (class file version 61.0),
  this version of the Java Runtime only recognizes class file versions up to 55.0
~~~

Reading the message part by part:

| Component | Meaning |
| --- | --- |
| `HelloVersion` | The class the runtime could not load at the time of the error |
| `class file version 61.0` | The bytecode requires Java 17 or higher to support major 61, unless specially constrained by preview |
| `up to 55.0` | The runtime supports up to major 55, corresponding to Java 11 |
| `UnsupportedClassVersionError` | An issue with **class-file format version**, not an `import` error |

A class in a dependency can also be the cause. For example, a major 55 `Main` runs on Java 11, yet calls a major 61 `LibraryService`; the application may start up and only throw the error when it needs to load `LibraryService`. Hence, **the class named in the exception** is the right starting point for investigation.

### Is it always a newer JDK than the JRE?

The common case is **the compiler producing newer bytecode than the JVM runtime**. However, there are also variants such as preview class files with a special minor version that the runtime disallows, or class files with an unsupported version pair. Therefore, read **both major and minor** and check the actual runtime, rather than assuming every error just requires upgrading the JDK.

## 7. Normal Minor Version and Preview Features

In most modern Java class files **not using preview**, `minor_version = 0`.

For class files with **major version 56 or higher (Java 12+)**, the class-file format specifies that minor must be **0 or 65535**. When minor = **65535** (`0xFFFF`), the class file marks a **dependency on a preview feature** of the corresponding Java release.

Example:

| Major.minor | Interpretation |
| --- | --- |
| `61.0` | Normal Java 17 class file |
| `61.65535` | Java 17 class file using a preview feature |
| `65.0` | Normal Java 21 class file |
| `65.65535` | Java 21 class file using a preview feature |

For preview classes:

- The compiler usually needs `--enable-preview` enabled and the exact `--release N` or `--source N` for which the compiler supports preview.
- The runtime needs to support **the exact Java release** corresponding to the preview class and usually must run with `--enable-preview`.
- A newer Java runtime **does not automatically run preview classes from an older release**, even if it supports a higher major version.
- `--enable-preview` does **not** make an older JVM understand a class-file major version newer than it supports.

### Preview example on JDK 17

Java 17 had **pattern matching for switch** in preview status. Create **`PreviewDemo.java`**:

~~~java
public final class PreviewDemo {
    static String describe(Object value) {
        return switch (value) {
            case String text -> "String:" + text;
            default -> "Other";
        };
    }

    public static void main(String[] args) {
        System.out.println(describe("Java"));
    }
}
~~~

Run **with JDK 17**:

~~~bash
javac --enable-preview --release 17 PreviewDemo.java
javap -verbose PreviewDemo
java --enable-preview PreviewDemo
~~~

The `javap` command will display the version section:

~~~text
  minor version: 65535
  major version: 61
~~~

**Stdout of the program:**

~~~text
String:Java
~~~

`javac` and `java` may print additional notices about preview features to stderr; those notice lines depend on the JDK and are not part of the program's stdout. If you omit `--enable-preview` in the run command, the JVM does not allow loading the preview class as an ordinary class. This snippet uses preview syntax **specific to JDK 17**; with another JDK, choose a preview example and flags suitable for that Java version.

**Note:** Only when the compiler actually generates a class depending on a preview feature under `--enable-preview` does the corresponding class carry minor = 65535. Do not infer that every class in a build with that flag enabled is guaranteed to have minor = 65535.

## 8. Using --release to Generate Compatible Bytecode

If you develop with a newer JDK yet need to run the application on older Java, you should use `javac --release N` when that compiler version supports the target.

JDK 17 example:

~~~bash
javac --release 8 -encoding UTF-8 -d out8 HelloVersion.java
javac --release 17 -encoding UTF-8 -d out17 HelloVersion.java
javap -verbose out8/HelloVersion.class
javap -verbose out17/HelloVersion.class
~~~

The two `javap` commands will show, respectively:

~~~text
out8/HelloVersion.class  -> major version: 52, minor version: 0
out17/HelloVersion.class -> major version: 61, minor version: 0
~~~

**The lines above are a summary** of the results, not verbatim `javap` output. Before running, create `out8` and `out17` or let the compiler create the directories depending on toolchain capability; an explicit way in Bash is `mkdir -p out8 out17`. Depending on the JDK version, not every older target release is supported.

### --release differs from -source and -target

| Option | Adjusts |
| --- | --- |
| `--source N` | Syntax version and source language rules accepted by the compiler |
| `--target N` | Target bytecode/class-file version to generate |
| `--release N` | Coordinates source language, target class file, and **Java platform APIs** available in release N |

If using only `-source 8 -target 8` with a newer JDK, you can accidentally compile code that calls **APIs of a newer Java platform**, while the class file still carries major 52. When running on Java 8, the error may be `NoSuchMethodError` or another linkage error, even though major 52 is accepted by the JVM.

`--release 8` helps the compiler check code against Java 8's platform APIs and prevents relying on newer JDK APIs. However, **`--release` does not automatically check whether every third-party library** on your classpath is compatible with the target runtime. You must still control dependency versions and test using the target runtime.

For example, the following code uses `String.repeat(int)` (an API available since Java 11):

~~~java
public final class RepeatDemo {
    public static void main(String[] args) {
        System.out.println("A".repeat(3));
    }
}
~~~

When using a compiler with target Java 8:

~~~bash
javac --release 8 RepeatDemo.java
~~~

The compiler will **reject** it because the `String.repeat` API does not exist in Java 8. With JDK 17 and `-source 8 -target 8` without proper platform API restrictions, the code can compile to major 52, yet when run on Java 8 it will lack the corresponding method. This illustrates why **a compatible major version is not enough to prove API compatibility**.

## 9. Identifying the Actual javac and java

Multiple JDKs/JREs can be installed on a development machine. You run `javac` from JDK 21 while `java` on PATH is a Java 11 runtime; hence errors appear even though the IDE reports everything is fine.

Check:

~~~bash
javac -version
java -version
~~~

These commands show the tool versions selected by the terminal. If you need to check executable paths:

**Linux/macOS:**

~~~bash
command -v javac
command -v java
~~~

**Windows PowerShell:**

~~~powershell
Get-Command javac
Get-Command java
~~~

**Windows CMD:**

~~~bat
where javac
where java
~~~

There is no fixed output because paths depend on the machine. In build/CI environments, the `JAVA_HOME` variable and `PATH` ordering can determine which Java toolchain is used; IDEs or Gradle/Maven can choose a different JDK from the terminal. When encountering errors, record the **compile toolchain**, **deployment runtime**, and **actual class versions in the artifact**.

### Deployment: do not look only at the build machine's JDK

A pipeline using JDK 21 to compile and then deploying to a Java 17 server will need class-file major versions not exceeding the runtime limit (Java 17 supports normal major 61), and must also use compatible APIs/dependencies.

Places to inspect include:
- The CI worker's JDK.
- The build's `--release`/toolchain configuration and Java compiler plugin.
- The JRE/JDK provided by the Docker image or the application host machine.
- Libraries packaged into the artifact.
- Classes generated by annotation processors, code generation, bytecode manipulation, or other plugins.

An application can contain classes generated by multiple compilers or build tasks; do not infer every class file uses the same major version merely from one global setting.

## 10. UnsupportedClassVersionError vs. Related Errors

| Error/symptom | Phase | Initial diagnosis |
| --- | --- | --- |
| `UnsupportedClassVersionError` | JVM class loading/definition | Read major.minor of the failing class and compare with runtime |
| `NoSuchMethodError` | Runtime linking/invocation | Runtime class API differs from compile-time API; check method signature |
| `NoClassDefFoundError` | Runtime loading/linking/initialization | Required class could not be provided or failed initialization |
| `ClassNotFoundException` | Loading class by name API | Class loader could not find the requested class |
| `ClassFormatError` | Runtime class format validation | Invalid bytecode; note `UnsupportedClassVersionError` is a subtype |
| `Unsupported major.minor version X.Y` | Message on some older JVMs | Class-file version is not supported by the runtime |
| `invalid source release: N` | Compile | Compiler version does not support the requested source release |
| `release version N not supported` | Compile | Compiler version does not support target `--release N` |
| `cannot find symbol` with platform API | Compile | API missing in configured release, or wrong dependency/import |
| `Preview features are not enabled` or equivalent message | Compile/runtime | Missing preview flag for matching release or improper use of preview class |

**Do not try to fix `UnsupportedClassVersionError` by adding `import` or changing package names:** the compiler and JVM can find the class, yet its format is not accepted. Nor should you attempt to downgrade the major version by editing the two header bytes: bytecode bodies, constant pools, and attributes may depend on newer version features; manually editing the header does not convert bytecode into a valid version.

## 11. How to Handle When the Runtime Is Too Old

Suppose the log reports class file `65.0`, while the runtime only supports up to `61.0`.

**Step 1: Read the message.** Major 65 is Java 21, major 61 is Java 17. The class was compiled at Java 21 level, whereas the current runtime supports normal class files up to Java 17.

**Step 2: Find the offending class.** If the log says `com.example.lib.Parser`, locate the JAR/directory containing that class rather than checking only the `Main` class. Identify the class with `javap -verbose -classpath path/to/library.jar com.example.lib.Parser`.

**Step 3: Confirm the actual runtime.** Run `java -version` in **the exact environment where the error occurs**: the container, service, pipeline, or terminal used to launch. A machine with multiple JDKs can cause the terminal and application to pick two different executables.

**Step 4: Choose the appropriate fix:**

1. **Upgrade the runtime** to a sufficiently new JDK/JRE, if deployment policy allows and the whole system is compatible.
2. **Recompile with `--release 17`** if the source code and APIs actually support targeting Java 17. Build all required modules with a consistent toolchain/configuration.
3. **Select a dependency version** supporting Java 17 if a third-party library only distributes major 65 classes. You usually do not have the rights or sufficient information to recompile vendor bytecode.
4. **Isolate/replace the component** if a library strictly requires Java 21 and the application must stay on Java 17; this is an architectural change that requires evaluation.
5. **If minor = 65535**, check preview status, specific release, and runtime flags instead of comparing only the major version.

**Step 5: Re-verify the artifact and run on the target runtime.** Check the class versions of relevant classes and run integration/smoke tests in an environment of the exact version. Simply having `javac` return exit code 0 on the build machine does not prove the target runtime can execute the entire dependency graph.

### If the compiler reports an error because source uses newer features

For example, source contains a record:

~~~java
public record Point(int x, int y) {
}
~~~

`record` is a standard feature since Java 16. Compiling with `javac --release 8` is invalid because Java 8 source target does not support records. To run the application on Java 8, you need to redesign the source using Java 8 syntax and APIs; you cannot just change flags while keeping newer language features.

## 12. When One JAR Contains Multiple Class Version Levels

There is no mandatory rule that every `.class` inside a JAR carries the same major version. It can happen that:

- A project bundles class files built from modules with different target levels.
- A library has classes compatible with an older Java baseline along with classes built for a newer release.
- A **Multi-release JAR** has special paths `META-INF/versions/N/...` and a manifest declaring `Multi-Release: true`, allowing a supporting runtime to pick the class/resource version matching the release.

Conceptual structure example:

~~~text
example.jar
├── META-INF/MANIFEST.MF                 (Multi-Release: true)
├── com/example/Feature.class            (base version)
└── META-INF/versions/17/
    └── com/example/Feature.class        (version for Java 17)
~~~

This is an **illustrative** structure, not a sample JAR created in this lesson. The base class version may have major 52, while the Java 17 version has major 61. A JVM supporting multi-release JARs can select the version matching the runtime release, following manifest conditions and JAR format versioning rules.

When diagnosing, identify **the specific entry being loaded**, not just any arbitrary class file in the JAR. `javap` has the `--multi-release N` option to inspect the entry corresponding to a version in a multi-release JAR if the tool/JAR supports it; the result still needs to be cross-checked against actual class loading behavior.

## 13. Preview Class Files Are Not Multi-Version Java

Suppose a class has header `61.65535`:

- Java 17 with `--enable-preview` can accept it **if** the class is valid and the corresponding preview is supported.
- Java 17 without preview enabled will not accept it as a normal class.
- Java 18 does not treat `61.65535` as a Java 18 preview class, even though Java 18 understands many lower-major class files. Preview is bound to **the exact release**.
- Java 11 does not support major 61, so enabling preview cannot resolve it.

Therefore, for errors mentioning preview, read **minor** alongside **major**, and ensure compile/runtime share the same preview release. It is best to avoid packaging preview classes into shared libraries needing long-term compatibility unless explicitly required.

## 14. Review Questions and Answers

**Question 1.** `javap -verbose` prints `major version: 52` and `minor version: 0`. Which release does the class file target?

**Answer:** The Java 8 class-file format. However, APIs and runtime dependencies still must be checked to conclude the application is fully Java 8 compatible.

**Question 2.** Why does `major 61` not necessarily mean the developer ran `javac` from JDK 17?

**Answer:** A newer compiler can produce a Java 17 target using `--release 17` or an appropriate configuration. Major reflects **the class-file target**, not directly the compiler executable version.

**Question 3.** A Java 11 JVM reports “class file version 61.0, runtime recognizes up to 55.0”. What do the two numbers say?

**Answer:** The class requires the Java 17 format; the runtime only supports up to the Java 11 format. Either a newer runtime or recompiling the class with a compatible target is needed.

**Question 4.** Looking at the first eight bytes `CA FE BA BE 00 00 00 41`, what is the major version?

**Answer:** `0x0041 = 65`, corresponding to Java 21; minor = 0. The data uses big-endian.

**Question 5.** What does `minor = 65535` with major 61 indicate?

**Answer:** A Java 17 class file marked with a preview feature. It requires preview support conditions for the exact Java 17 release; it is not Java version “61.65535”.

**Question 6.** Can you lower the major version from 65 to 61 with a hex editor so a Java 17 JVM can run it?

**Answer:** There is no guarantee and it is not a valid solution. Bytecode/attributes/APIs may be incompatible. You must recompile with the appropriate source and target or upgrade the runtime.

**Question 7.** Why can a major 52 `Main.class` still fail on Java 8?

**Answer:** A dependent class may have a higher major version, or the program calls an API missing from the Java 8 runtime. The major version of a single individual class does not guarantee the entire application will run.

**Question 8.** Are `--release 8` and `-target 8` completely equivalent?

**Answer:** No. `--release 8` also constrains Java platform APIs to Java 8, helping detect calls to APIs added after Java 8. Setting only the bytecode target does not provide the same level of platform API checking.

## 15. Checklist When Investigating Errors in a Real Project

1. Record the **class name** in `UnsupportedClassVersionError` and the reported **major.minor**.
2. Use the major table to deduce the minimum Java release corresponding to the **class file**.
3. Determine **`java -version` of the failing process**, not just the terminal or IDE.
4. Use `javap -verbose` or a header reader tool to verify the class file **actually deployed**.
5. Check whether that class resides in application output, a dependency JAR, generated bytecode, or a multi-release JAR.
6. Check `javac -version`, `--release`, compiler toolchain, Gradle/Maven configuration, and target version of each module.
7. If **minor 65535** is seen, determine the preview flag and corresponding release at both compile and runtime.
8. Decide to upgrade the runtime, validly lower the compilation target, or swap the dependency; do not manually edit bytecode headers.
9. Re-run on the actual target runtime, verify all classes and APIs used, and save build/deployment evidence so the error does not recur.

## Takeaway

- A `.class` header begins with **magic = 0xCAFEBABE**, followed by **minor (2 bytes)** then **major (2 bytes)**, all big-endian.
- Class files normally use **minor 0**; starting from **Java 12/major 56**, **minor 65535** marks a class depending on a preview feature of the corresponding release.
- Useful milestones: **Java 8 → 52**, **Java 11 → 55**, **Java 17 → 61**, **Java 21 → 65**.
- `UnsupportedClassVersionError` occurs when the JVM does not support the version of the loaded class file; the message states the class version and runtime limit.
- Use **`javap -verbose`** to inspect the version, **`java -version`** to check the actual runtime, and **`javac --release N`** when building for a target Java version.
- A matching bytecode major version is a **necessary, not sufficient, condition** for API/dependency compatibility; test on the actual runtime.
