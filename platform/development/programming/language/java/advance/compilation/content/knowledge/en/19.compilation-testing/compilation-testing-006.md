# Testing Generated Code with a Real Consumer Compilation

## 1. Why Must Generated Code Be Compiled?

In Java, *generated code* is source code or bytecode automatically created from annotations, schemas, templates, DSLs, or a build step. For example: an annotation processor generating data-access classes, an API client generator generating models and endpoints, or a tool generating adapters for an interface.

**Having a file created** is not enough to conclude the generator is right. A `.java` file may have valid syntax yet use the wrong package name, miss imports, have wrong generic types, wrong visibility, wrong methods, or depend on a library absent from the application's classpath. Merely comparing source strings with a *golden file* also easily misses compatibility errors with real code.

A stronger criterion is:

> Have **user code that actually calls the generated API** participate in a clean compilation, with the exact Java compiler, Java version, and classpath expected to be used; check whether the entire compilation succeeds or fails.

In this lesson, "a real consumer compilation" means **a single `javac` invocation compiling application source that references the class generated by an annotation processor**, so the compiler itself runs annotation processing rounds and checks the client in the same compilation. Beforehand we still need to compile the processor into a runnable tool — this is a preparation step, not a second compilation used to patch generated code.

## 2. The Contract to Verify

A valuable compilation test must simultaneously confirm these relationships:

| Component | What to Verify |
|---|---|
| **Generator input** | Annotations/schemas and configuration are valid and actually trigger the generator |
| **Generated code** | Files are created with the right package, class, members, return types, modifiers, and generics |
| **Real consumer** | A Java class outside the generator can import, instantiate, or call that API |
| **Java compiler** | `javac` checks all real sources with the target `--release`/toolchain |
| **Classpath** | Contains the exact required dependencies, without "accidentally" seeing test classes or stale artifacts |
| **Output** | `.java` and `.class` files are created in a clean directory; compilation errors fail the build |

For example, if a generator is supposed to create `HelloGenerated.greet(String): String` yet generates `greet(Object): int`, a test that only counts files or searches class names can still pass. A consumer assigning the result to a `String` variable forces the compiler to verify the expected signature and catch the type error.

This kind of test has a clear scope: it proves **the compilation contract** with the constructed scenarios, without automatically proving runtime logic, performance, thread stability, security, or every possible configuration.

## 3. Annotation Processing Mechanism of `javac`

With a standard Java annotation processor (JSR 269), the compiler can execute multiple **processing rounds within a single compilation invocation**:

1. `javac` reads user sources and identifies annotations to process.
2. The processor observes annotated elements and uses `Filer` to create new source files.
3. The compiler feeds new files into the next round; another processor may process annotations on them.
4. When no new sources remain, processing rounds end and the compiler checks/compiles both original sources and generated sources.
5. If the client uses the generated API with wrong types, wrong visibility, or missing symbols, the entire `javac` command fails.

Therefore, with a `Filer`-based generator, **there is no need and you should not manually compile generated files in a second `javac` command just to prove this smoke test**. Compiling separately a second time can accidentally pick up old classes and miss issues in the real flow.

Two paths must be clearly distinguished:

- **Processor path** (`-processorpath`): where `javac` looks for classes executing the annotation processor.
- **Compilation classpath** (`-classpath` or `-cp`): where application sources look for annotations, libraries, and APIs they reference.

Processors can be supplied explicitly with `-processor lab.GreetingProcessor`; when using this approach, the example does not need service loader registration. In real projects, Gradle/Maven can configure processor discovery via dependencies/`META-INF/services/javax.annotation.processing.Processor` or corresponding support mechanisms.

## 4. Complete Example with Java 17+: Generating an API and Compiling the Client

We build an annotation processor creating class `lab.generated.HelloGenerated` from annotation `@GenerateGreeting`. The consumer will call `HelloGenerated.greet("Lan")` and require the result to be `String`.

File structure:

~~~text
src/
├── processor/
│   └── lab/
│       ├── GenerateGreeting.java
│       └── GreetingProcessor.java
└── app/
    └── demo/
        ├── GreeterSpec.java
        └── Demo.java
~~~

### 4.1. Defining the annotation

File `src/processor/lab/GenerateGreeting.java`:

~~~java
package lab;

import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

@Target(ElementType.TYPE)
@Retention(RetentionPolicy.SOURCE)
public @interface GenerateGreeting {
}
~~~

`RetentionPolicy.SOURCE` is sufficient for the processor to read the annotation during compilation; it does not require the annotation to appear in runtime bytecode.

### 4.2. Writing the processor generating source via Filer

File `src/processor/lab/GreetingProcessor.java`:

~~~java
package lab;

import java.io.IOException;
import java.io.Writer;
import java.util.Set;
import javax.annotation.processing.AbstractProcessor;
import javax.annotation.processing.RoundEnvironment;
import javax.annotation.processing.SupportedAnnotationTypes;
import javax.annotation.processing.SupportedSourceVersion;
import javax.lang.model.SourceVersion;
import javax.lang.model.element.Element;
import javax.lang.model.element.TypeElement;
import javax.tools.Diagnostic;

@SupportedAnnotationTypes("lab.GenerateGreeting")
@SupportedSourceVersion(SourceVersion.RELEASE_17)
public final class GreetingProcessor extends AbstractProcessor {
    @Override
    public boolean process(
            Set<? extends TypeElement> annotations,
            RoundEnvironment roundEnv) {
        for (Element element :
                roundEnv.getElementsAnnotatedWith(GenerateGreeting.class)) {
            try (Writer writer = processingEnv.getFiler()
                    .createSourceFile("lab.generated.HelloGenerated", element)
                    .openWriter()) {
                writer.write("""
                    package lab.generated;

                    public final class HelloGenerated {
                        private HelloGenerated() {}

                        public static String greet(String name) {
                            return "Xin chào, " + name + "!";
                        }
                    }
                    """);
            } catch (IOException exception) {
                processingEnv.getMessager().printMessage(
                    Diagnostic.Kind.ERROR,
                    "Không tạo được HelloGenerated: " + exception.getMessage(),
                    element
                );
            }
        }
        return true;
    }
}
~~~

Notable points:

- `@SupportedAnnotationTypes` declares the exact annotation processed by the processor; `@SupportedSourceVersion` indicates the supported language version.
- `roundEnv.getElementsAnnotatedWith(...)` selects only sources with the annotation, avoiding generating files when not requested.
- `Filer.createSourceFile(...)` registers the file with the compiler for processing in the next round; `element` is the **originating element**, useful for source-generation tracking mechanisms.
- `Diagnostic.Kind.ERROR` turns code-generation errors into compilation errors, instead of swallowing errors and returning a green build.
- The example has **exactly one annotated class**. Generators producing a fixed class name like this need their own rules to avoid conflicts if multiple elements are annotated simultaneously; this practical exercise intentionally keeps scope simple.

### 4.3. Creating input and real consumer

File `src/app/demo/GreeterSpec.java`:

~~~java
package demo;

import lab.GenerateGreeting;

@GenerateGreeting
public final class GreeterSpec {
}
~~~

File `src/app/demo/Demo.java`:

~~~java
package demo;

import lab.generated.HelloGenerated;

public final class Demo {
    public static void main(String[] args) {
        String greeting = HelloGenerated.greet("Lan");
        System.out.println(greeting);
    }
}
~~~

`Demo.java` **does not depend on the processor's source code**; it depends on **the generated API**. Assigning the result to a `String` variable actively verifies the return type. If the generator makes an incompatible signature change, the consumer's own compiler will catch it.

### 4.4. Compiling the processor once to prepare

Using JDK 17 or newer, in the directory containing `src`. Create three clean output directories; on macOS/Linux:

~~~bash
mkdir -p verify-out/processor verify-out/generated verify-out/classes
javac --release 17 -d verify-out/processor   src/processor/lab/GenerateGreeting.java   src/processor/lab/GreetingProcessor.java
~~~

On Windows PowerShell, you can create the directories with `New-Item -ItemType Directory -Force verify-out/processor,verify-out/generated,verify-out/classes`; then pass both filenames on the same line to `javac` (do not use the Unix shell line-continuation character `\`).

This command only **bootstraps** the annotation and processor. The processor's classes reside in `verify-out/processor`; do not include processor sources in the application's compilation command in the next step.

### 4.5. A single compilation containing both consumer and generated code

On macOS/Linux:

~~~bash
javac --release 17   -cp verify-out/processor   -processorpath verify-out/processor   -processor lab.GreetingProcessor   -s verify-out/generated   -d verify-out/classes   src/app/demo/GreeterSpec.java   src/app/demo/Demo.java
java -cp verify-out/classes demo.Demo
~~~

`-cp` helps the compiler see annotation `lab.GenerateGreeting`; `-processorpath` helps locate and load the processor; `-processor` instructs it to run the exact processor; `-s` specifies where to place **generated sources**; `-d` specifies where to place **class files**. Using `--release 17` helps catch generated code calling APIs absent in the Java 17 platform when the build runs on a newer JDK.

The single `javac` command in this section checked **both the annotated input and the consumer referencing the generated class**, thanks to the compiler handling the rounds. After succeeding, you can check:

~~~text
verify-out/generated/lab/generated/HelloGenerated.java
verify-out/classes/lab/generated/HelloGenerated.class
verify-out/classes/demo/GreeterSpec.class
verify-out/classes/demo/Demo.class
~~~

Correct application run output is:

~~~text
Xin chào, Lan!
~~~

The `java` command here is an **additional runtime smoke test** after compilation; API interface verification was performed by `javac` immediately before. If there are compilation errors, do not run the application and interpret classes from a previous run as new results.

## 5. Ensuring the Test Does Not Produce a "False Green"

Successful execution is valuable only when the environment is isolated:

1. **Use clean output:** delete or recreate the test's own `verify-out` directory before running. Do not leave `HelloGenerated.class` from an old build sitting on the application classpath.
2. **Do not pass old generated source as explicit input:** `src/app/demo/Demo.java` imports the generated class, yet the application command does not list `verify-out/generated/lab/generated/HelloGenerated.java` as a pre-existing source file.
3. **Force processor activation:** for example using `-processor lab.GreetingProcessor`. If the processor is not loaded, the command must fail because the consumer cannot find `lab.generated.HelloGenerated`.
4. **Do not make the classpath "too rich":** a JAR containing an old version of `HelloGenerated` can let the consumer compile even if the current run generates no file.
5. **Confirm the code-generation event:** besides exit code `0`, verify the right new file in `-s`, package, API signature, and new class in `-d`.
6. **Inspect full diagnostics:** do not ignore compiler stderr, and do not count a run as successful when only the generator ran while `javac` failed.
7. **Lock release/toolchain:** use the same target Java and dependency versions that the application will use; a newer compiler or development environment classpath can mask compatibility errors in production.

A useful control test is running application compilation with `-proc:none` into a **clean output**. Because the processor is disabled, `Demo.java` cannot find `lab.generated.HelloGenerated` and the command must error. If it still succeeds, old generated classes/sources may have accidentally leaked into the classpath or sourcepath — fix isolation before trusting the test.

Note: `-proc:none` is only a **negative control** to prove the test truly needs generated code; not the configuration of the main compilation.

## 6. Testing Contract-Breaking Changes

Example where the generator changes the method:

~~~java
// Illustrates an invalid change in generated code; this is not a standalone runnable file.
public static int greet(String name) {
    return 42;
}
~~~

The consumer in section 4 still expects:

~~~java
String greeting = HelloGenerated.greet("Lan");
~~~

A clean compilation will produce the type error **`int cannot be converted to String`** and a non-zero exit code. This is a meaningful finding that checks looking solely at filenames cannot perform.

Other changes worth testing in a real test suite:

| Generator change | Consumer helps detect |
|---|---|
| Changing `lab.generated` to another package | Import does not resolve |
| Renaming `greet` to `hello` | Method does not exist |
| Changing `public` to package-private | Not accessible from package `demo` |
| Turning `static` into an instance method | Static call fails |
| Changing `String` to `int` | Incompatible assignment type |
| Generating source using a Java API higher than release | Compilation with `--release 17` fails |
| Generating wrong generic bounds or checked exceptions | Compiler catches it at consumers having corresponding constraints |

Even so, compilation does not prove the text result `Xin chào, Lan!` matches business logic. That is why the example runs `Demo.main` after compilation; in real products separate unit/integration tests are needed for behavior.

## 7. When Should It Be Separated into an Automated Test?

In CI, you should rerun **consumer compilation** whenever the generator or a generator dependency changes. It can be implemented via a build/test script in a temporary directory, via `javax.tools.JavaCompiler` in a Java test, or via a fixture module dedicated to compiling application sources. Whichever approach is chosen, what is tested must be a **real compilation task/command** against the generated API, not merely checking file existence.

With a Gradle project having processor module `:generator` and application module `:consumer-fixture`, the dependency declaration idea is:

~~~groovy
// In build.gradle of :consumer-fixture (illustrative configuration snippet)
dependencies {
    compileOnly project(":generator")       // Annotation API used at compile time
    annotationProcessor project(":generator") // Processor execution
}
~~~

The snippet above illustrates the roles of the two classpaths, not a complete project. Module `:generator` must provide both the annotation and processor, and the processor needs to be registered so Gradle discovers it (such as via service registration). If the annotation is split into a separate API module, `compileOnly` should depend on the API module; `annotationProcessor` depends on the processor module and its dependencies. Source in `:consumer-fixture` must contain code **using the generated API** so the compile task detects incompatible signatures.

Scenarios to include in the fixture when the generator becomes more complex:

- Consumers in **different packages** to check visibility and imports.
- Consumers with realistic **generics, overloads, nested types, checked exceptions, and annotation usage**.
- Fixtures with multiple inputs of the same kind to detect **generated filename collisions** and processing rounds.
- Fixtures compiled on the **lowest supported release** and minimum dependency classpath.
- Fixtures using both **generated sources** and generated resources when required by the product, while remembering the compiler does not verify runtime resource semantics.

For processors generating sources across multiple rounds, do not try to add generated files into the source set via hardcoded paths upfront; let the compiler/Gradle track processor output via standard tasks. Generators running before compilation (for example OpenAPI codegen) have a different flow: the generate step creates sources, followed by **one real consumer compile** on application sources plus generated sources; task dependencies and generated source directories must be wired properly in the build tool.

## 8. Distinguishing Generator Errors from Build Configuration Errors

A failing smoke test can come from multiple layers:

| Symptom | Cause to Inspect |
|---|---|
| `Annotation processor '...' not found` | Wrong `-processorpath`, processor not built yet, or wrong fully qualified name |
| `package lab does not exist` | Missing annotation API on compilation classpath |
| `package lab.generated does not exist` | Processor did not activate, annotation did not match, output not generated, or old classes removed |
| `cannot find symbol` at generated method call | Generator generated wrong name, parameter count, visibility, or signature |
| `FilerException: Attempt to recreate a file` | Generator created duplicate file across multiple annotated elements/rounds |
| Build succeeds only when removing `--release 17` | Generated code or dependencies require newer API/language level |
| Test passes locally, fails on CI | Different classpath, JDK/toolchain, filesystem case sensitivity, stale output, or task dependencies |
| Test passes when processor is disabled | Usually old generated classes/sources leaked into test inputs |

Preserve original compiler diagnostics, generated sources in the test directory, and classpath/toolchain information. A `cannot find symbol` message is usually a **symptom**; the root cause may be that the processor did not run or generated the wrong API, not necessarily a missing application dependency.

## 9. Checklist for Evaluating a Reliable Compilation Test

- [ ] Test identifies generator inputs and a Java consumer using the real generated API.
- [ ] Processor code is built beforehand; the consumer needs only **one `javac` invocation** to generate and then use the generated class (for annotation processing).
- [ ] Compiler/toolchain, `--release`, and dependencies match the supported Java contract.
- [ ] Source output and class output reside in clean directories, without mixing generated artifacts from a previous run.
- [ ] Processor is explicitly activated or via verified registration; compilation fails if generation is disabled.
- [ ] Consumer makes calls specific enough to catch required type, package, visibility, method signature, and generic errors.
- [ ] Exit code, diagnostics, generated files, and class output are verified; runtime smoke tests are added when behavioral verification is needed.
- [ ] CI runs the check when generator/dependencies change, and broken artifacts cannot be masked by caches or stale outputs.

**Remember:** the best way to test generated code is putting a **representative consumer** into a **real compilation process**. File existence proves the generator wrote text; successful compilation from a clean directory proves at least one real Java program **can use the generated API contract**.
