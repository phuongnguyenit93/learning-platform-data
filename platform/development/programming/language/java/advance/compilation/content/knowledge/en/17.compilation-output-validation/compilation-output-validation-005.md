# Inspecting Bridge Methods, Synthetic Members, and Auxiliary Generated Classes After javac Compilation

When `javac` compiles a `.java` file, the output does not necessarily contain only the classes and methods explicitly written in source. The compiler can add **bridge methods**, **synthetic members**, and **auxiliary class files** for generics, overriding, nested/local/anonymous classes, and Java language rules. This is not by default a sign of abnormal bytecode tampering: many components are necessary compatibility mechanisms between Java source and the JVM.

When **validating outputs**, learners should not only ask “did the code compile successfully?”. You need to know which methods and classes actually appear in `.class`, why they are present, how to distinguish author-written methods from compiler-generated support methods, and how to avoid misidentifying them when using reflection, bytecode analyzers, coverage tools, or method-scanning frameworks.

This lesson uses Java 17+, `javac`, `javap`, and reflection. Complete examples can be run independently, along with stdout, bytecode inspection commands, and notes on which parts are **language/JVM contracts** and which are only **`javac` implementation choices**.

## 1. Three Concepts Often Lumped Together

| Concept | Nature | Verification Signal |
| --- | --- | --- |
| **Bridge method** | Auxiliary method generated by the compiler to preserve overriding/polymorphism when JVM signatures differ from source signatures, especially with **type erasure** or **covariant return types** | `ACC_BRIDGE` in `javap -v`; `Method.isBridge()` |
| **Synthetic member** | Field/method/member generated by the compiler or a tool, not directly corresponding to a source declaration in the ordinary sense | `ACC_SYNTHETIC` / synthetic metadata; `Member.isSynthetic()` via reflection where applicable |
| **Auxiliary generated class** | Another `.class` file created from the same source, e.g., member class, non-static inner class, local class, or anonymous class | List output files, inspect `InnerClasses`, `EnclosingMethod`, `NestHost`/`NestMembers` if present |

**The relationship among them is not one-to-one:**

- A bridge method generated by `javac` usually **carries both `ACC_BRIDGE` and `ACC_SYNTHETIC`**.
- A synthetic field such as a reference to the outer class instance of an inner class **is not a bridge method**.
- A nested class having its own `.class` file **is not necessarily a synthetic class**: source explicitly declares that nested class.
- Methods generated by the compiler yet specified by the language as members usable in source, such as certain enum/record methods, **do not necessarily carry the synthetic flag**.
- Lambdas can be implemented using `invokedynamic` and classes generated at runtime; it does **not** mean an `Outer$1.class` file for the lambda always exists on disk.

Cross-check **source-level declarations**, **JVM method descriptors**, **access flags**, and **output files** instead of merely counting method names by intuition.

## 2. Why Do Bridge Methods Appear?

Java generics normally use **type erasure** in bytecode. For example, an interface declares:

~~~java
interface Holder<T> {
    T get();
}
~~~

After erasing the type variable `T` without an explicit bound, the method descriptor of `Holder.get` corresponds to `()Ljava/lang/Object;`. When a class implements it:

~~~java
final class TextHolder implements Holder<String> {
    @Override
    public String get() {
        return "text";
    }
}
~~~

The implementation has descriptor `()Ljava/lang/String;`. The JVM distinguishes methods by name and descriptor, where the descriptor includes the return type. So that calls through `Holder<String>` still execute the right implementation in `TextHolder`, `javac` generates a forwarding method conceptually taking the form:

~~~java
// Equivalent ILLUSTRATIVE code, NOT source allowed to be copied
// into TextHolder: return type overloading is invalid in Java source.
public Object get() {
    return get(); // Delegates to String get() at the bytecode level.
}
~~~

In source, you **cannot** manually declare two methods with the same name and same parameters differing only in return type as above. That is precisely where a bridge is needed **at the JVM level**, not an ordinary source overload. The synthetic bridge method retains the descriptor expected by code calling through the interface/supertype.

Diagram:

~~~text
Source:
  Holder<T>.get(): T
  TextHolder.get(): String

Erasure / JVM descriptors:
  Holder.get()      ()Ljava/lang/Object;
  TextHolder.get()  ()Ljava/lang/String;

javac additionally generates in TextHolder:
  get()Ljava/lang/Object;    [ACC_BRIDGE | ACC_SYNTHETIC]
       |
       +--> calls TextHolder.get()Ljava/lang/String;
~~~

The running program still sees only the `String` value. The bridge is an implementation piece making JVM dispatch/resolution compatible with the subtype contract.

## 3. Complete Java 17 Example: Bridge, Synthetic Field, and Inner Class

Create **one** file `GeneratedMembersDemo.java` in an empty directory:

~~~java
import java.lang.reflect.Method;
import java.lang.reflect.Field;
import java.util.Arrays;
import java.util.Comparator;

interface Holder<T> {
    T get();
}

final class TextHolder implements Holder<String> {
    @Override
    public String get() {
        return "text";
    }
}

final class Envelope {
    private final int base;

    Envelope(int base) {
        this.base = base;
    }

    final class Inner {
        int plus(int value) {
            return value + base;
        }
    }
}

public final class GeneratedMembersDemo {
    public static void main(String[] args) {
        Method[] methods = TextHolder.class.getDeclaredMethods();

        Arrays.sort(
                methods,
                Comparator.comparing(
                        method -> method.getReturnType().getName()
                )
        );

        for (Method method : methods) {
            if (method.getName().equals("get")) {
                System.out.println(
                        method.getName()
                        + " -> " + method.getReturnType().getSimpleName()
                        + ", bridge=" + method.isBridge()
                        + ", synthetic=" + method.isSynthetic()
                );
            }
        }

        Holder<String> holder = new TextHolder();
        System.out.println("value: " + holder.get());

        Envelope outer = new Envelope(5);
        Envelope.Inner inner = outer.new Inner();
        System.out.println("inner result: " + inner.plus(2));

        boolean syntheticOuterField = Arrays.stream(
                Envelope.Inner.class.getDeclaredFields()
        ).anyMatch(field ->
                field.isSynthetic()
                && field.getType() == Envelope.class
        );

        System.out.println(
                "synthetic outer field: " + syntheticOuterField
        );
    }
}
~~~

Compile and run with JDK 17:

**Linux/macOS (Bash):**

~~~bash
mkdir -p out
javac --release 17 -encoding UTF-8 -d out GeneratedMembersDemo.java
java -cp out GeneratedMembersDemo
~~~

**Windows PowerShell:**

~~~powershell
New-Item -ItemType Directory -Force out | Out-Null
javac --release 17 -encoding UTF-8 -d out GeneratedMembersDemo.java
java -cp out GeneratedMembersDemo
~~~

**Exact stdout with the lab's Java 17 javac/JVM:**

~~~text
get -> Object, bridge=true, synthetic=true
get -> String, bridge=false, synthetic=false
value: text
inner result: 7
synthetic outer field: true
~~~

Explanation:

1. `getDeclaredMethods()` returns methods **declared directly in `TextHolder` bytecode**, including the bridge. This is **not** an API returning “only programmer-written methods”.
2. Reflection **does not guarantee method order**. The example sorts by qualified name of the return type, so `java.lang.Object` appears before `java.lang.String` to give deterministic output order.
3. `get(): Object` is compiler-generated, having `isBridge() == true` and `isSynthetic() == true`.
4. `get(): String` is the implementation written in source, carrying neither flag in the example.
5. `Holder<String> holder` calls via the generic contract; result `text` proves the bridge supports dispatching to the right implementation.
6. `Envelope.Inner` is a **non-static inner class** accessing instance field `base` of `Envelope`. With Java 17 `javac`, `Inner`'s bytecode has a synthetic field holding a reference to the enclosing instance; `Field.isSynthetic()` detects it.
7. Using `anyMatch` instead of printing a field name like `this$0` avoids relying on **internal field names** chosen by the compiler. Synthetic field names are not part of the class's public API.

### Generated Class Files

After compiling the single source file, `out` normally contains:

~~~text
out/
├── Holder.class
├── TextHolder.class
├── Envelope.class
├── Envelope$Inner.class
└── GeneratedMembersDemo.class
~~~

`Envelope$Inner.class` is generated because source declares `Envelope.Inner` as a member class with its own definition. The `$` sign is the common binary name form for member classes in class files, differing from the `Envelope.Inner` reference syntax in source. That file **does not mean the Inner class itself is “absent from source”**.

File names of member classes follow stable syntax in the example, whereas more complex numbering forms for local/anonymous classes can depend on the compiler and declaration positions.

## 4. Inspecting Bytecode with javap -v, -p, and -c

No need to infer from reflection output: open the class file directly with `javap`.

~~~bash
javap -classpath out -p -v TextHolder
~~~

Key parts commonly seen with Java 17 `javac`, omitting the constant pool and keeping only the lines needing inspection:

~~~text
public java.lang.String get();
  descriptor: ()Ljava/lang/String;
  flags: ... ACC_PUBLIC

public java.lang.Object get();
  descriptor: ()Ljava/lang/Object;
  flags: ... ACC_PUBLIC, ACC_BRIDGE, ACC_SYNTHETIC
~~~

The lines above are **illustrative excerpts**, not verbatim output (constant pool indices and detailed ordering are decided by `javap`). Hex numbers `0x....` of flags may be displayed alongside flag names.

Inspect bytecode:

~~~bash
javap -classpath out -p -c TextHolder
~~~

Bridges usually have instructions calling the actual implementation method, for example:

~~~text
public java.lang.Object get();
  Code:
     aload_0
     invokevirtual ... // Method get:()Ljava/lang/String;
     areturn
~~~

This is an **abbreviated sample**; addresses, reference names, and instruction order numbers may differ. What is essential is that the bridge descriptor returns `Object` while the implementation returns `String`.

To inspect the inner class (both Bash and PowerShell support single-quoted strings):

~~~bash
javap -classpath out -p -v 'Envelope$Inner'
~~~

Look for a field of type `Envelope` with `ACC_SYNTHETIC` and nested class information in attributes. Note:

- In **Bash**, writing `Envelope$Inner` unquoted can cause the shell to expand `$Inner` as an environment variable.
- In **PowerShell**, double quotes can interpolate `$Inner`; single quotes keep it literal.
- In **CMD**, you can use `"Envelope$Inner"` to pass the class name intact.

List class files on Linux/macOS:

~~~bash
find out -type f -name '*.class' -print | sort
~~~

In PowerShell:

~~~powershell
Get-ChildItem -Path out -Recurse -Filter *.class |
    Select-Object -ExpandProperty FullName
~~~

**Do not use `javap -c` alone to conclude synthetics:** it mainly prints instructions; to verify flags use `-v` (verbose), and to see non-public members use `-p`.

## 5. Reflection: Detecting Bridges and Synthetics Properly

The reflection API has the methods:

| API | Meaning |
| --- | --- |
| `Method.isBridge()` | Method has the bridge flag per class-file metadata |
| `Method.isSynthetic()` | Method is marked synthetic |
| `Field.isSynthetic()` | Field is marked synthetic |
| `Constructor.isSynthetic()` | Constructor is marked synthetic if present |
| `Class.isSynthetic()` | Checks the synthetic flag of a runtime class |
| `Class.getDeclaredMethods()` | Direct methods of the class, including compiler-generated methods |
| `Class.getMethods()` | Public methods visible per reflection rules, including inherited methods |
| `Class.getDeclaredFields()` | Directly declared fields, including compiler-generated fields |

Note `isBridge()` is a method of **`Method`**, not of every `Member`. A synthetic field does not have a bridge flag. An auxiliary class created from a source declaration can still return `Class.isSynthetic() == false`.

### Filtering Bridges When Tools Scan Methods

Suppose a framework builds a list of actions based on public methods. Iterating `getDeclaredMethods()` and treating every method name as a distinct endpoint might register `TextHolder`'s `get()` twice:

~~~java
for (Method method : TextHolder.class.getDeclaredMethods()) {
    if (method.isBridge() || method.isSynthetic()) {
        continue;
    }
    // Process methods matching framework policy.
}
~~~

This is a **fragment**; you must import `java.lang.reflect.Method` and place it inside an appropriate method.

This filter is an **application policy**, not a mandatory rule for every framework. For example, bytecode coverage tools, serialization frameworks, or proxy systems sometimes need to analyze synthetic/bridge methods too. An annotation processor analyzing source via `javax.lang.model` also does not necessarily expose the same list of methods that runtime reflection sees in bytecode.

**Do not filter only by name** such as `get` or `$` characters. Author-written methods can legitimately use `$` in identifiers; conversely, compiler-generated methods can carry ordinary names. Rely on metadata and analysis goals.

### Why Can Signatures in Reflection Be Misleading?

Java source does not allow overloads differing only in return type, yet reflection can see two methods:

~~~text
get() -> java.lang.String
get() -> java.lang.Object
~~~

This is not source violating Java. **Class files** and the **source language** have different rules for representing methods; compiler-generated bridges translate between those two systems.

In verification code, read **`getReturnType()`**, **`getParameterTypes()`**, **`isBridge()`**, **`isSynthetic()`**, and generic signatures if needed. `getGenericReturnType()` helps analyze generic types where class files still store matching metadata; it does not turn a bridge method into an independent source declaration.

## 6. Bridge Methods from Generic Erasure with Parameters: checkcast in Bytecode

The `Holder<T>.get()` example created a bridge differing in return type. With **generic parameters**, the bridge may have to cast arguments before calling the implementation.

Create standalone file **`BridgeCastDemo.java`**:

~~~java
interface Sink<T> {
    void put(T value);
}

final class StringSink implements Sink<String> {
    @Override
    public void put(String value) {
        System.out.println("stored:" + value);
    }
}

public final class BridgeCastDemo {
    @SuppressWarnings({"rawtypes", "unchecked"})
    public static void main(String[] args) {
        Sink<String> typed = new StringSink();
        typed.put("ok");

        Sink raw = new StringSink();
        try {
            raw.put(Integer.valueOf(7));
        } catch (ClassCastException ex) {
            System.out.println("bridge rejected Integer");
        }
    }
}
~~~

Compile and run:

~~~bash
mkdir -p out-cast
javac --release 17 -encoding UTF-8 -d out-cast BridgeCastDemo.java
java -cp out-cast BridgeCastDemo
~~~

**Exact stdout:**

~~~text
stored:ok
bridge rejected Integer
~~~

In `Sink<T>`, the method erases to `put(Object)`, while the implementation declares `put(String)`. The compiler generates a semantically equivalent bridge:

~~~java
// Only to explain bytecode, NOT a valid source method
public void put(Object value) {
    put((String) value);
}
~~~

Calling `raw.put(Integer.valueOf(7))` at runtime goes through bridge `put(Object)`; the cast to `String` fails, so `ClassCastException` occurs **before** the body of `put(String)` executes. `@SuppressWarnings` is only used to silence unchecked/raw warnings in the **snippet intentionally illustrating dropping type safety**; it does not make that call safe.

Inspect bytecode:

~~~bash
javap -classpath out-cast -p -c -v StringSink
~~~

On the synthetic bridge method `put(java.lang.Object)`, look for flags `ACC_BRIDGE, ACC_SYNTHETIC` and an instruction like `checkcast java/lang/String` before the call to `put(java.lang.String)`. This exact detail explains why a bridge is not merely a “duplicated method”, and can contain necessary conversion bytecode.

### Avoiding Misunderstandings About Raw Types

Properly typed generic Java code cannot pass `Integer` to `Sink<String>` at compile time. Raw types drop generic type checking at the call site, yet the bridge/runtime cast still protects the typed implementation. This is a **runtime ClassCastException caused by using a raw reference**, not `javac` picking the wrong overload.

## 7. Covariant Return Types Can Also Generate Bridges

Bridges are not tied exclusively to generics. When a subclass overrides a method with a **narrower** return type (covariant return), the JVM method descriptor can differ between superclass and subclass.

Example file **`CovariantBridgeDemo.java`**:

~~~java
class ParentValue {
    Number value() {
        return 1;
    }
}

final class IntegerValue extends ParentValue {
    @Override
    Integer value() {
        return 2;
    }
}

public final class CovariantBridgeDemo {
    public static void main(String[] args) {
        ParentValue value = new IntegerValue();
        System.out.println(value.value());
    }
}
~~~

Run:

~~~bash
mkdir -p out-covariant
javac --release 17 -encoding UTF-8 -d out-covariant CovariantBridgeDemo.java
java -cp out-covariant CovariantBridgeDemo
~~~

**Exact stdout:**

~~~text
2
~~~

The compiler can generate a bridge in `IntegerValue` with a descriptor returning `Number`, forwarding to the implementation returning `Integer`. Inspect:

~~~bash
javap -classpath out-covariant -p -v IntegerValue
~~~

With Java 17 `javac`, the bridge has `ACC_BRIDGE` and `ACC_SYNTHETIC`. It maintains proper overriding behavior when code calls through the compile-time type `ParentValue`.

**Remember:** the JVM can distinguish descriptors having different return types, yet Java source-level overriding is not implemented by writing two overloads differing only in return type. Bridges are the compiler's bytecode generation work.

## 8. Synthetic Field of Non-Static Inner Classes

A **non-static inner class** has permission to access the outer class's instance. To perform this access at runtime, `javac` can store the outer instance reference in a compiler-generated field.

In `GeneratedMembersDemo`:

~~~java
final class Envelope {
    private final int base;

    Envelope(int base) {
        this.base = base;
    }

    final class Inner {
        int plus(int value) {
            return value + base;
        }
    }
}
~~~

Source declares only `base` in `Envelope`, not an `outer` field in `Inner`. However, `Inner.plus()` must know **which Envelope instance** to read `base` from. When writing `outer.new Inner()`, the compiler passes the outer reference into the inner class's initialization mechanism.

Use `javap -p -v 'Envelope$Inner'` to inspect the synthetic field referencing `Envelope`. With Java 17 `javac`, this field usually has an internal name like `this$0` and the `ACC_SYNTHETIC` flag.

### Synthetics and Outer References Are Not the Same

Do not assume every inner class has a field named exactly `this$0` across **all JDKs/compilers**. How outer reference capture is implemented can differ and be optimized under certain conditions. The lab example directly uses `base` to create a clear scenario on Java 17.

Also do not treat this synthetic field as business data needing serialization. When a framework scans fields to generate JSON or SQL schemas, failing to filter properly can pull the outer reference into the model, causing object graph cycles or unintended data leaks.

### Why Doesn't Private Access Necessarily Create access$000 Anymore?

Some older articles describe compilers having to generate synthetic accessors such as `access$000` so inner classes could access private fields/methods in the outer class. In older class files, that was a common technique.

Since Java 11, the JVM supports **nest-based access control** and class files have attributes like `NestHost` and `NestMembers`. When compiling for Java 17, `javac` usually leverages nestmates so inner/outer classes access private members **without needing to generate old-style accessors in many cases**.

Therefore, do not use the question “is there an `access$000` method or not?” as a mandatory test for every compiler/JDK. Inspect the actual class file with `javap -v -p`, reading both **nest attributes** and synthetic methods if they appear.

## 9. Member Classes, Local Classes, and Anonymous Classes: One Source, Multiple .class Files

Java has different kinds of type declarations:

| Kind | Example | Additional Class File |
| --- | --- | --- |
| Static nested class | `static class Helper` inside outer class | Usually has `Outer$Helper.class` |
| Non-static inner member class | `class Inner` inside outer class | Usually has `Outer$Inner.class` |
| Local class | `class LocalTask` declared inside a method | Has separate class file; numbering/binary naming decided by compiler |
| Anonymous class | `new Runnable() { ... }` | Has separate class file; internal name usually contains `$` and numbers |
| Lambda expression | `() -> ...` | Does not necessarily have a matching class file on disk; usually uses `invokedynamic` and runtime machinery |

Example program **`GeneratedClassesDemo.java`**:

~~~java
public final class GeneratedClassesDemo {
    interface Task {
        String run();
    }

    public static void main(String[] args) {
        class LocalTask implements Task {
            @Override
            public String run() {
                return "local";
            }
        }

        Task anonymous = new Task() {
            @Override
            public String run() {
                return "anonymous";
            }
        };

        Task lambda = () -> "lambda";

        System.out.println(new LocalTask().run());
        System.out.println(anonymous.run());
        System.out.println(lambda.run());
    }
}
~~~

Run:

~~~bash
mkdir -p out-classes
javac --release 17 -encoding UTF-8 -d out-classes GeneratedClassesDemo.java
java -cp out-classes GeneratedClassesDemo
~~~

**Exact stdout:**

~~~text
local
anonymous
lambda
~~~

Run:

~~~bash
find out-classes -type f -name '*.class' -print | sort
javap -classpath out-classes -p -v GeneratedClassesDemo
~~~

Normally you will see files for outer, member interface `Task`, local class `LocalTask`, and the anonymous class. **Do not hardcode** numbered names like `GeneratedClassesDemo$1` or `GeneratedClassesDemo$1LocalTask` into tests running across multiple compilers/versions: names can change when adding/removing declarations or changing compilers.

### Distinguishing “Auxiliary Generated Classes” and “Synthetic Classes”

Both local classes and anonymous classes originate from **valid Java source syntax**; separate class files are simply how their definitions are stored. A file with `$` in its name **does not prove** the whole class is synthetic.

When checking with reflection:

- `Class.isMemberClass()` identifies member classes per API rules.
- `Class.isLocalClass()` identifies local classes.
- `Class.isAnonymousClass()` identifies anonymous classes.
- `Class.getEnclosingMethod()` can point to the method containing a local/anonymous class declaration.
- `Class.isSynthetic()` is a **different** check from the three classifications above.

Do not filter all files containing `$` and label them “not author-written”, because static nested classes also have `$` files yet are explicitly declared in source.

## 10. Lambdas: No Outer$1.class by Default

Looking at source:

~~~java
Runnable action = () -> System.out.println("run");
~~~

A beginner might imagine `javac` always creates `Outer$1.class` like an anonymous class. With Java 17, lambdas are normally compiled based on **`invokedynamic`** and appropriate bootstrap machinery; how runtime implementations are created differs from traditional anonymous classes.

Inspect a class with lambdas using:

~~~bash
javap -classpath out-classes -p -c -v GeneratedClassesDemo
~~~

Look for:
- `invokedynamic` instructions in bytecode of methods containing lambdas.
- `BootstrapMethods` attribute describing the relevant bootstrap method.
- Compiler-generated helper methods, which may have names like `lambda$main$0` and be marked synthetic in some cases.

**There is no guarantee** helper methods are named strictly `lambda$main$0` in every compiler release or that every lambda has a separate synthetic method. JVMs and compilers are allowed to use different implementation strategies as long as language semantics are obeyed.

At runtime, lambda implementations can also use **hidden classes**. They are not required to be emitted as `.class` files on disk when `javac` runs. Therefore, “not seeing auxiliary lambda files” is **not** a build error.

### Anonymous Classes and Lambdas Differ Regarding this

In an anonymous class, `this` refers to that anonymous class's instance. In a lambda, `this` (in an instance context) is the enclosing class's `this`. This difference in source semantics explains why compilers are not forced to implement both using the same class-file structure.

Do not infer a lambda's runtime class name by calling `lambda.getClass().getName()` and building business logic on that string. Implementation names/identifiers can change across JVMs/JDKs and are not stable APIs.

## 11. Other Synthetic Members: Avoid Over-Inferring

Some forms of compiler-generated bytecode also include:

- Synthetic fields storing captured values in certain local/anonymous classes.
- Synthetic fields holding the outer instance of a non-static inner class in certain cases.
- Bridge methods bridging descriptors for generic erasure/covariant returns.
- Helper methods supporting lambdas, switches, or constructs lowered by javac into auxiliary bytecode, depending on version/strategy.
- Certain helper fields/methods serving enums or compiler-generated classes.

However, watch out for pitfalls:

1. **Synthetic is not synonymous with private.** Compilers can create **public** bridges; synthetic fields can carry different access flags.
2. **Not every automatically generated member is synthetic.** Certain methods mandated by the Java language play public API roles, e.g., `values()` and `valueOf(String)` on enums. Do not assume they have `Method.isSynthetic() == true`.
3. **Not every anonymous/local class is synthetic.** The existence of a separate class file is not enough to prove `ACC_SYNTHETIC`.
4. **Not every auxiliary bytecode instruction has a corresponding synthetic member.** Compilers can use direct instructions, `invokedynamic`, constant pool entries, or attributes.
5. **Do not use prefixes `access$`, `lambda$`, or `this$` as the sole criterion.** Internal names are implementation details. Class-file flags and metadata, together with compiler context, hold diagnostic value.

This distinction matters when writing long-lived bytecode validation suites: tests based on **behavior and contracts** are more durable than tests requiring a unique set of internal names not guaranteed by the specification.

## 12. Validating Class Output as an Artifact

After each compilation pass, validate across three layers:

### 12.1. Confirm Successful Compilation and List Files

On Linux/macOS:

~~~bash
javac --release 17 -encoding UTF-8 -d out GeneratedMembersDemo.java
find out -type f -name '*.class' -print | sort
~~~

In PowerShell:

~~~powershell
javac --release 17 -encoding UTF-8 -d out GeneratedMembersDemo.java
Get-ChildItem -Path out -Recurse -Filter *.class |
    Select-Object -ExpandProperty FullName
~~~

Before running, the `out` directory must exist; earlier sections gave creation commands. Verify files are present and re-read metadata if needed, while remembering class-file counts can change when source changes or the compiler changes implementation strategies.

### 12.2. Inspect Method Flags, Descriptors, Attributes

~~~bash
javap -classpath out -p -v TextHolder
javap -classpath out -p -v 'Envelope$Inner'
javap -classpath out -p -c TextHolder
~~~

Items to record:

- Binary name/superclass/interfaces.
- Method descriptors alongside generic `Signature` attributes if present.
- `ACC_BRIDGE` and `ACC_SYNTHETIC` on methods.
- Synthetic field used by inner classes to point to outer.
- `InnerClasses` and nest attributes (if present).
- Dispatch bytecode, `invokevirtual`, or `checkcast` inside bridges.
- Class file major version matching the targeted release.

### 12.3. Run Behavioral Verification

~~~bash
java -cp out GeneratedMembersDemo
~~~

Reflection and stdout from the lab help verify flags/behavior, not just file counts. For multi-module/JAR projects, ensure runtime classpath and class loaders use the exact freshly compiled artifact; if runtime accidentally loads a different class with the same binary name, conclusions from `javap` on your output may not describe the running class.

## 13. Testing via Reflection Without Depending on Method Order

When building automated tests, avoid:

~~~java
Method first = TextHolder.class.getDeclaredMethods()[0];
// Wrong verification approach if expecting first is always String get().
~~~

The Reflection API does not guarantee the return order of method arrays. Also avoid checking only `getDeclaredMethods().length == 2` on complex classes: compilers may emit additional helper members, or bytecode enhancement frameworks may instrument classes.

A better strategy is filtering by properties:

~~~java
long bridgeCount = Arrays.stream(
        TextHolder.class.getDeclaredMethods()
).filter(Method::isBridge).count();

long syntheticBridgeCount = Arrays.stream(
        TextHolder.class.getDeclaredMethods()
).filter(m -> m.isBridge() && m.isSynthetic()).count();

System.out.println(bridgeCount);
System.out.println(syntheticBridgeCount);
~~~

This is a **fragment** needing placement in a method and imports for `java.lang.reflect.Method`, `java.util.Arrays`. With `TextHolder` from the Java 17 lab, the two lines print:

~~~text
1
1
~~~

In test frameworks, verify both the **exact descriptor** and that the real method gets dispatched to the implementation, if ABI assurance is a goal. Seeing `isBridge() == true` alone does not prove the bridge has valid bytecode or right behavior after bytecode rewriting.

A detailed bytecode test can use `javap -v` or a class-file reading library supporting the target class version, while keeping the boundary between checking flags and checking behavior.

## 14. ABI Compatibility: Bridges Can Affect Pre-Compiled Code

Bridge methods help preserve the ability to call methods through erased interfaces/superclasses. If a bytecode optimizer, obfuscator, or transformer removes an `ACC_BRIDGE` method solely because it is synthetic, previously compiled code can fail when runtime has to resolve expected descriptors.

For instance, a caller compiled against interface `Holder<T>` expects method `Holder.get(): Object`. In `TextHolder`, bridge `get(): Object` ensures dispatch to `get(): String`. Removing a bridge in a hierarchy lacking the needed matching method can break virtual dispatch or cause runtime linkage/dispatch errors, depending on the exact class layout.

**Never conclude:** “Synthetics are always junk and can be deleted to shrink JAR size.” Synthetic/bridge flags are metadata explaining a member's **origin and role**; compiler-generated members can be **mandatory prerequisites** for a program to still satisfy overriding after erasure.

Shrink/obfuscate tools must preserve:
- Method descriptors required for ABI.
- Bridge methods and dispatch relations per the bytecode specification.
- Reflection entry points used by applications/frameworks.
- Metadata/attributes needed for semantics of configured language features or frameworks.

Changing generic signatures only alters compile-time type checking, whereas JVM descriptors and bridges decide actual binary invocation. When debugging `NoSuchMethodError` or `AbstractMethodError` after bytecode optimization, check whether bridges survived or were altered.

## 15. Auxiliary Classes in JARs and Packaging Issues

Suppose you package:

~~~bash
jar --create --file app.jar -C out .
jar --list --file app.jar
~~~

If `out` contains `GeneratedMembersDemo.class`, `TextHolder.class`, and `Envelope$Inner.class`, the JAR must include all class files needed for runtime loading. Packaging **only the class with main** and dropping inner/helper classes can cause `NoClassDefFoundError` when code first uses them.

Conversely, do not identify every `Outer$X.class` file as redundant artifact junk. It may be a public member type defined by source; deleting it breaks the API.

### Even a Single Source File Can Create Multiple Classes

The lab has five class files from one `GeneratedMembersDemo.java` file. That is valid. In build systems, when source changes or deletes a local/anonymous class, corresponding stale class files from prior compilations must be deleted; otherwise, the JAR may retain bytecode no longer belonging to current source.

**Clean build** and **incremental build** capabilities are therefore separate concerns beyond `javac` emitting valid bytecode. When discovering an auxiliary class “no longer in source”, check whether the output directory was properly cleaned/invalidated before blaming the compiler.

### Classfile Versions and How javac Implements Things Can Change

When using `--release 8` versus `--release 17` (if the compiler supports both), the compiler may generate different synthetic accessors and nest metadata. To compare properly:

1. Compile the same source into two **separate** output directories.
2. Check the `major version` of each class.
3. Use `javap -v -p` to compare flags/attributes.
4. Do not change the runtime target across test runs when testing a specific property.
5. Treat only specified differences as mandatory requirements; helper method details can depend on compiler version.

## 16. Mistakes When Reading javap or Reflection Output

| Claim / Mistake | Correct Understanding |
| --- | --- |
| “One source file must create exactly one .class” | Nested/local/anonymous types can generate multiple class files |
| “Two get() methods differing in return type prove a bad source overload” | One method may be a **bridge** generated by the compiler at the bytecode level |
| “Every bridge method is an author-written method” | `ACC_BRIDGE` indicates a compiler-generated bridge; in javac it usually pairs with `ACC_SYNTHETIC` |
| “Every synthetic member can be deleted” | May be required for dispatch, capture, runtime access, or ABI |
| “getDeclaredMethods only returns source methods” | It can return bridge/synthetic methods present in the class file |
| “getDeclaredMethods order always matches source order” | Reflection does not guarantee order |
| “Files with $ are definitely synthetic” | May be explicit member classes, local, or anonymous classes |
| “Every lambda has Outer$1.class” | Lambdas usually rely on `invokedynamic` and runtime implementations |
| “Using Java 17 always produces access$000” | Nest-based access control can eliminate old-style accessor needs |
| “isSynthetic() == false means the user wrote the method” | Some generated/mandated methods do not carry the synthetic flag |
| “If the compiler generated a helper, that's a build error” | It can be mandatory bytecode to implement Java semantics |
| “The class file on disk and runtime class are definitely identical” | Runtime classpath/loaders can load another copy with the same binary name |

## 17. Repeatable Output Review Process

When encountering bridge/synthetic questions in a real project:

1. **Pin source and JDK**: record `javac -version`, `--release`, processor/plugin options, and compile classpath.
2. **Compile into clean output**: remove stale classes from prior builds; do not edit a running project's outputs directly.
3. **List all .class files**: identify nested/member/local/anonymous classes and auxiliary classes.
4. **Run `javap -p -v -c`** on suspect classes; read method descriptors, access flags, `Signature`, `InnerClasses`, and nest attributes.
5. **Cross-check generic/covariant inheritance**: if an overriding method has a different descriptor after erasure/covariance, a bridge may be needed to maintain polymorphism.
6. **Use reflection properly**: filter methods by `isBridge`/`isSynthetic` if targeting source-like APIs; do not skip them by default when testing ABI.
7. **Test virtual dispatch and casts**: invoke through interface/superclass types to verify bridge behavior.
8. **Package completely**: retain required helper classes and resources in artifacts, inspecting the JAR rather than only the main class.
9. **Verify runtime loader**: classes can come from a different JAR; check CodeSource/class loader if results diverge from bytecode on disk.
10. **Mark compiler-dependent details clearly**: never turn synthetic field names, anonymous class numbering, or internal lambda structures into permanent API contracts.

## 18. Self-Check Questions and Answers

**Question 1.** `TextHolder` implements `Holder<String>`, declaring `String get()`. Why does bytecode also have `Object get()`?

**Answer:** Because erasure of `Holder<T>.get` gives a descriptor returning `Object`. The bridge keeps runtime dispatch contracts compatible with the interface method; the source implementation returns `String`.

**Question 2.** In Java 17 `javac`'s `TextHolder`, what are `Method.isBridge()` and `isSynthetic()` for `get():Object`?

**Answer:** Both `true`. For source method `get():String`, both are `false` in the lab.

**Question 3.** An inner class uses a field of the outer instance. Reflection sees a synthetic field of the outer type. Did source declare that field?

**Answer:** No. The compiler creates a helper field referencing the outer instance. The exact name is an implementation detail and should not be used as a business API.

**Question 4.** Why does `Envelope$Inner.class` not mean `Envelope.Inner` is a synthetic type?

**Answer:** Source explicitly declared `Inner`; the separate file is the compiled form of the member class. A name with `$` is not the `ACC_SYNTHETIC` flag.

**Question 5.** When calling `raw.put(Integer.valueOf(7))` via raw `Sink`, why does `ClassCastException` occur?

**Answer:** Bridge `put(Object)` forwards to `put(String)` and must `checkcast String`; the Integer argument is incompatible, so it throws an error before the body of the method receiving String.

**Question 6.** Does a lambda `() -> "hello"` always create an `Outer$1.class` file when javac compiles?

**Answer:** No. Java 17 typically uses `invokedynamic` and bootstrap/runtime implementation; the class can be created at runtime instead of being an auxiliary file on disk.

**Question 7.** Why must API-scanning tools be careful with `getDeclaredMethods()`?

**Answer:** The result includes methods present in the class file, which can contain compiler-generated bridge/synthetic methods; order is also not guaranteed. Tools must filter/group by purpose.

**Question 8.** Can all synthetic methods be deleted from a JAR to save space?

**Answer:** No. Bridge/capture/helper members can be required for runtime behavior and binary compatibility. Optimization must preserve semantics and necessary method descriptors.

**Question 9.** Why can `access$000` disappear after upgrading the JDK?

**Answer:** With nest-based access control in modern class files, the compiler can allow nestmates to access private members without needing old-style helper access methods.

**Question 10.** Does checking `Method.isBridge()` replace running the program?

**Answer:** No. The flag confirms metadata, yet bytecode may have been modified or depend on another runtime. To verify behavior, you must call through interface/superclass types, run tests, and cross-check the actually loaded artifact.

## Takeaways

- A **bridge method** is an auxiliary method at the bytecode level for generic erasure or covariant return; with `javac` it usually carries **`ACC_BRIDGE` and `ACC_SYNTHETIC`**.
- A **synthetic member** is metadata about compiler/tool origin, not redundant by default, not synonymous with private, and not synonymous with deletable.
- **One .java file can generate multiple .class files**; nested/local/anonymous classes and lambdas have different implementation mechanisms.
- Use **`javap -p -v -c`** to read flags, descriptors, and bytecode; use **`Method.isBridge()` / `Member.isSynthetic()`** to verify via reflection.
- **Do not depend on internal names** like `this$0`, `access$000`, `lambda$...`, or anonymous class numbering as an API contract across every JDK/compiler.
- Good output validation requires **compiling into clean output, checking class files/flags, running dispatch tests, and keeping necessary auxiliary classes when packaging**.
