# Output Isolation and Avoiding Stale Class Files Masking Missing Dependency Errors

## Learning Objectives

By the end of this lesson, you will be able to:

- Explain why a `javac` command can compile successfully thanks to an old `.class` file, even though the source set or dependencies declared for the current build are incomplete.
- Distinguish between **source path**, **compiler classpath**, **output directory**, and **runtime classpath**.
- Reproduce the “works on my machine, fails on a clean environment” scenario using a Java 17+ example that can be run from the terminal.
- Use separate output directories for each step/module, rebuild from scratch in a new directory, and verify the exact artifacts used.
- Recognize when `javac` reports a missing symbol error, and when the program compiles but the JVM encounters a class linking/loading error at runtime.
- Build a checklist to avoid **stale class files** in manual workflows or Gradle/Maven/CI.

The scope of this lesson is **the classpath and the reliability of compilation results**. No framework or IDE is needed to practice.

## 1. Why Can an Old `.class` File Be Dangerous?

Imagine that previously the project had two classes:

- `dep.Greeter` provides the functionality of an internal library.
- `app.Main` uses `dep.Greeter`.

In the first build, you compile both into `build/classes`. Afterwards, the source set that you **want** to include in the new build only has `app.Main` left; the dependency `dep.Greeter` has not been declared or has not been built in the intended inputs.

If you run:

~~~bash
javac -cp build/classes -d build/classes src/app/Main.java
~~~

`javac` still finds `build/classes/dep/Greeter.class` generated earlier. The compiler can therefore successfully check the call to `Greeter` even though **there is no Greeter source/library in the new input set that you want to verify**.

This leads to the false conclusion: “I verified that the project builds independently.” In reality, you have only proven that the code compiles **in an environment that still has old artifacts**.

Compiling into a **completely new output**, with a classpath containing only allowed dependencies, will expose the missing dependency error.

### 1.1 Step-by-Step Mechanism

~~~text
Run 1: old build
src/dep/Greeter.java ─┐
                       ├─ javac -d build/classes ─> build/classes/dep/Greeter.class
src/app/Main.java ────┘                       └──> build/classes/app/Main.class

Run 2: specify compiling Main.java
                                       +----------------------------------+
javac -cp build/classes ... ---------->| classpath has old Greeter.class  |
                                       | compiler resolves dep.Greeter OK |
                                       +----------------------------------+
                                                      |
                                                      v
                                       Result "compile successful"
                                       but the intended dependency is missing

Run 3: build in clean output
javac -cp build/clean -d build/clean src/app/Main.java
                                                      |
                                                      v
                                        package dep does not exist
                                        / cannot find symbol
~~~

**The compiler does not ignore the error.** The compiler checks accurately against the classes that you allow it to see on the classpath. The problem is that **the classpath contains unintended inputs**.

In real-world work, old classes can be left behind due to renaming/deleting source files, moving packages, changing dependencies, removing a module from the build, or performing partial builds while keeping the same output directory.

## 2. Distinguishing Four Related Paths

| Component | Example | Role |
| --- | --- | --- |
| **Source files** | `src/app/Main.java` | The source files you ask the compiler to process |
| **Compile classpath** | `javac -cp build/lib ...` | Where `javac` looks for compiled classes/libraries needed to check the source |
| **Output directory** | `javac -d build/app ...` | The directory receiving the class files generated by the current compile command |
| **Runtime classpath** | `java -cp build/app:build/lib app.Main` on Linux/macOS | Where the JVM looks for classes when running the program |

Key points:

- `-d` **is not synonymous** with `-cp`. `-d` specifies where to write; `-cp` specifies where to read compiled dependencies.
- If you pass the same old output directory into `-cp`, it can itself become an **input** to the next compile.
- `javac` typically compiles the specified sources, and also has a mechanism to search for related sources/classes via the source path and classpath. Therefore, you must control all search paths, not just look at the list of files written on the command line.
- The runtime classpath can differ from the compile classpath. Having a library at compile time does not guarantee that the library is present at runtime.
- The `src/` and `build/` paths in the examples are project-defined conventions; the JVM itself does not mandate these names.

### 2.1 Implicit Source Discovery Mechanism of `javac`

If a referenced class is not passed directly as source, `javac` may search for a class file or source file along the configured search paths. The default source path and its combination with the classpath depend on compile options; therefore, a “still builds” issue can stem from **implicitly discovered sources** or from **old class files**.

In this lesson, the commands use `-cp` explicitly and each source is placed in its own directory. Thus, the experiment shows that it is the old class file acting as a dependency that makes the compilation succeed. In a complex pipeline, you should also configure `-sourcepath` when you need to control source discovery.

The `-implicit:none` option controls **generating class files** for sources implicitly discovered by the compiler, but it **does not automatically delete old classes and does not make a dirty classpath clean**. Do not use `-implicit:none` as a substitute for isolating inputs.

## 3. Preparing a Java 17+ Example to Reproduce the Issue

You need JDK 17 or higher and a terminal. Check with:

~~~bash
javac -version
java -version
~~~

The program uses two independent Java files organized by package:

~~~text
classpath-isolation-demo/
├── src/
│   ├── dep/
│   │   └── Greeter.java
│   └── app/
│       └── Main.java
└── build/
    └── ... (will be created during the exercise)
~~~

Create a new project and two directories `src/dep`, `src/app` using your file manager or your operating system's directory creation command. Open a terminal at the root directory `classpath-isolation-demo`.

### 3.1 Library Source: `src/dep/Greeter.java`

~~~java
package dep;

public final class Greeter {
    private Greeter() {
    }

    public static String message() {
        return "Hello from Greeter";
    }
}
~~~

The `message()` method is `static` and returns a fixed string. The class resides in package `dep`; after compilation, it will correspond to the path `dep/Greeter.class` under the classpath root.

### 3.2 Application Source: `src/app/Main.java`

~~~java
package app;

import dep.Greeter;

public final class Main {
    public static void main(String[] args) {
        System.out.println("App: " + Greeter.message());
    }
}
~~~

`app.Main` needs `dep.Greeter` to compile the `Greeter.message()` call. An import lets you write shorter class names in source code, but `import` **does not automatically add JARs or class files to the classpath**.

### 3.3 Creating the Output Directories

In **PowerShell**, from the project directory:

~~~powershell
New-Item -ItemType Directory -Force build/classes, build/clean, build/lib, build/app | Out-Null
~~~

In **Bash/Zsh**:

~~~bash
mkdir -p build/classes build/clean build/lib build/app
~~~

You must create or verify the output directory before running `javac -d`. This lesson uses four different directories to clearly observe which classes are generated in each run, avoiding accidentally overwriting artifacts from another test.

## 4. Experiment A: Old Compilation Hiding a Missing Dependency Error

### Step A1 — Compile Both the Library and Application into a Shared Directory

~~~bash
javac -encoding UTF-8 -d build/classes src/dep/Greeter.java src/app/Main.java
java -cp build/classes app.Main
~~~

Stdout when running:

~~~text
App: Hello from Greeter
~~~

After compiling, the `build/classes` directory contains:

~~~text
build/classes/
├── dep/
│   └── Greeter.class
└── app/
    └── Main.class
~~~

Both classes are valid, and the runtime classpath contains the same `build/classes` root, so the JVM finds them.

### Step A2 — Simulate a Compile with Only the Application Source

Now suppose the new pipeline **is only allowed to build the application**, while the dependency on `dep.Greeter` is omitted in the new configuration. We intentionally **do not include** `src/dep/Greeter.java` in the list of files to compile, yet we use a classpath containing the output of the previous run:

~~~bash
javac -encoding UTF-8 -cp build/classes -d build/classes src/app/Main.java
~~~

This command still compiles successfully. `Main.java` sees `dep.Greeter` through **`build/classes/dep/Greeter.class`**, the old class file that still exists from step A1.

The condition causing the false conclusion here is not that `Greeter.java` was deleted from the machine. Even when the source still sits in `src/dep`, it **does not belong to the intended source/dependency set of step A2**. The classpath accidentally brought the dependency into the check.

You might think “there are no errors, so the dependencies are complete,” but a build from a completely clean state is not guaranteed to reproduce this result.

### Step A3 — Compile into a Clean Output to Verify Independently

Still compiling from `src/app/Main.java`, but without letting the classpath see `build/classes`:

~~~bash
javac -encoding UTF-8 -cp build/clean -d build/clean src/app/Main.java
~~~

The experiment uses `build/clean`, which was just created and **contains no class files yet**. There is no `dep.Greeter` on the classpath of this compile command; therefore, the compiler will report an error. Diagnostics may include lines such as:

~~~text
package dep does not exist
cannot find symbol
~~~

Line numbers, carets, and diagnostic ordering may vary by JDK version. What needs to be verified is a **non-zero exit code** and that the compiler does not produce a valid `app.Main` from that compile run.

Why didn't `javac` automatically pick up `src/dep/Greeter.java`? Because in command A3 we only passed the file `src/app/Main.java` and explicitly set the compile classpath to `build/clean`. The source of `dep.Greeter` is in a different path and is not included in the sources the compiler is searching.

### Step A4 — Fix Properly by Declaring the Dependency in the Clean Build

If both sources are allowed to belong to the same output/module, pass both sources:

~~~bash
javac -encoding UTF-8 -d build/clean src/dep/Greeter.java src/app/Main.java
java -cp build/clean app.Main
~~~

Stdout:

~~~text
App: Hello from Greeter
~~~

The clean build now succeeds because **the inputs are truly complete**. If the two parts are two independent modules/libraries, follow experiment B below: compile the library separately and then pass the library's output onto the application's compile classpath.

### What Has Been Proven

- **A2 succeeded:** only proves that `Main.java` compiles when it sees the old `Greeter.class`.
- **A3 failed:** proves that a clean input set containing only `Main.java` is not sufficient to compile the application.
- **A4 succeeded:** proves that when the actual dependency is added, the clean build works.

This is reproducible evidence of how a stale artifact masks a missing dependency error. Do not interpret this as a type-checking bug in `javac`: the compiler always treats classes present on the specified classpath as valid sources of information.

## 5. Experiment B: Isolating Outputs by Module

In a multi-module project, a clear approach is for each module to have its own output:

~~~text
build/
├── lib/
│   └── dep/Greeter.class
└── app/
    └── app/Main.class
~~~

### Step B1 — Build the Library

~~~bash
javac -encoding UTF-8 -d build/lib src/dep/Greeter.java
~~~

At this point, `build/lib` contains `dep/Greeter.class`. This is the library artifact allowed to be used as a dependency when compiling the application.

### Step B2 — Build the Application with an Explicitly Declared Dependency

~~~bash
javac -encoding UTF-8 -cp build/lib -d build/app src/app/Main.java
~~~

Here:

- `-cp build/lib` tells the compiler where to find `dep.Greeter`.
- `-d build/app` writes **only the classes generated by the application compilation** into the application output.
- There is no need to mix `Greeter.class` into `build/app`.
- This separation makes missing dependencies easier to detect and helps trace the origin of each artifact.

### Step B3 — The Runtime Classpath Must Contain Both Parts

On **Linux/macOS**:

~~~bash
java -cp "build/app:build/lib" app.Main
~~~

On **Windows (PowerShell/CMD)**:

~~~powershell
java -cp "build/app;build/lib" app.Main
~~~

Stdout for both:

~~~text
App: Hello from Greeter
~~~

The separator for multiple classpath entries is **`:` on Linux/macOS** and **`;` on Windows**. On both operating systems, the package names remain `app.Main` and `dep.Greeter`; do not replace the package names with slashes or backslashes when running.

### Step B4 — Compiles Successfully but Fails at Runtime Due to Missing Dependency

Run the application with only the application output:

~~~bash
java -cp build/app app.Main
~~~

The JVM can find `app.Main`, but when it reaches the `Greeter.message()` call, the `dep.Greeter` class is not on the runtime classpath. With this example, the error is typically `NoClassDefFoundError: dep/Greeter`, often accompanied by a cause such as `ClassNotFoundException` from the class loader. The detailed stack trace depends on the JVM, so do not treat it as fixed output.

The takeaway is that **the compile classpath and runtime classpath serve two different phases**. A class can be present during the compile step yet absent during the execution step. That error differs from case A3, where the compiler could not find the symbol from the start.

### Step B5 — Avoid Accidentally Using the Application's Output as a Dependency

When compiling the application, the option:

~~~bash
javac -cp build/lib -d build/app src/app/Main.java
~~~

is clearer than passing a combined directory containing lots of old classes into `-cp`. In a large project, each module should have its own output, and dependencies should be described by a dependency graph or specific entries.

Output isolation is not an absolute guarantee: if you still reference a wrong JAR version or a polluted directory, the build can still produce wrong results. You need to combine **the right input set**, **the right dependency versions**, and **clean build proof**.

## 6. Real-World Scenarios That Create Stale Class Files

### 6.1 Deleting or Renaming Source Files While Old Class Files Remain

Previously the project had `src/dep/Legacy.java` and `build/classes/dep/Legacy.class`. After the source is deleted or moved to `NewApi.java`, if the compile process only writes new classes without **cleaning up old output**, `Legacy.class` may still remain.

If another source references `dep.Legacy` and the compiler classpath points to the old output, the build may still pass even though the source `Legacy.java` has disappeared. When packaging from the entire old output, unwanted artifacts can also slip into the JAR.

One way to verify is to compare the list of classes in the output after a clean build with the incremental output; if you see classes that no longer have valid sources/dependencies, you need to review the build cleanup or lifecycle.

### 6.2 Moving Packages

Changing `package old;` to `package newer;` causes the compiler to generate the class at a different path. If `old/Thing.class` is not cleaned up, places that still import `old.Thing` can continue compiling from the old binary.

Do not assume that changing a package in source code will automatically delete classes belonging to the old package in every custom script. Deleting obsolete outputs is the responsibility of the build process.

### 6.3 Building Only Part of the Project

A developer just built a library module, then modified the configuration so that the module is no longer a dependency of the application. If output from the previous build still remains on the classpath, compiling just the application may continue to succeed.

A clean CI machine or a teammate's machine without the old artifacts will report an error. “Only fails on CI” is sometimes a signal that **the local machine is relying on undeclared data**.

### 6.4 Class Files from Old Versions and Confusing Runtime Errors

An old `.class` file does not merely mask a missing class error; it can also provide an old API signature. Later, when the runtime loads a different library version, the application may encounter linkage errors such as `NoSuchMethodError` or `NoSuchFieldError` when code calls an incompatible API.

Not every `NoSuchMethodError` is caused by a stale build. When encountering this error, check the actual loaded class, library version, and classpath; avoid diagnosing solely by exception name.

## 7. How to Organize Compilation for Easy Verification

### 7.1 Do Not Use a Shared Output Directory as a “Dependency Warehouse”

One anti-pattern is:

~~~bash
javac -cp build/classes -d build/classes src/app/Main.java
~~~

when `build/classes` contains the results of previous compiles without any mechanism to manage obsolete files.

Instead, prefer:

~~~bash
javac -cp build/lib -d build/app src/app/Main.java
~~~

where `build/lib` holds the dependency artifacts built from valid inputs, and `build/app` contains only the application's output.

This is a **build design convention**; it is not an absolute prohibition against an output directory appearing in the compile classpath. Some pipelines need classes compiled from a previous stage. What matters is that reuse must be controlled, have a clear dependency graph, and be verified with clean build tests.

### 7.2 Distinguish Clean Output from Clean Dependency Set

“Clean build” has at least two layers of meaning:

1. **Clean output:** the destination directory receiving `.class` files initially contains no old artifacts.
2. **Clean input:** the compiler does not read sources or binaries outside the declared dependencies.

Merely creating `build/clean` while still passing `-cp build/classes` will **not** prove the dependency set is clean, because old classes are still read from `build/classes`. To verify, provide the compiler with a classpath consisting strictly of the intended dependencies.

For example A3, `-cp build/clean` was chosen to intentionally **exclude** `Greeter.class`. If the real application needs `Greeter`, declare/enforce building this dependency instead of trying to use an empty classpath in production.

### 7.3 Output Directory Names Should Reflect Their Purpose

A useful structure:

~~~text
build/
├── isolated-lib/
├── isolated-app/
├── test-classes/
├── generated-sources/
└── packaged-artifacts/
~~~

These directories are naming examples. The goal is to avoid mixing sources, generated sources, application classes, test classes, and library dependencies in one place where you can no longer tell what is acting as **input** versus **output**.

### 7.4 Do Not Use Previous Compile Results to Prove Reproducibility

When reviewing dependency changes, running CI, or doing release builds, a compile result relying solely on incremental artifacts has limited value. You should be able to run a build from a fresh checkout and fresh output, with explicitly declared dependencies, without relying on binaries outside the build system.

That does not mean incremental compilation is wrong. Incremental compilation is very useful for speed; a reliable build system must know which inputs changed and clean up or invalidate outputs that are no longer valid. Periodic clean builds serve as an **independent verification check**.

## 8. Inspecting Actual Artifacts and Classpaths

### 8.1 Inspecting Generated Class Files

After step A1, use the JDK tool:

~~~bash
javap -classpath build/classes dep.Greeter
javap -classpath build/classes app.Main
~~~

`javap` disassembles class file information; it does not need to run `main`. You can verify that the class exists and inspect the member signatures seen by the compiler. To view the bytecode as well:

~~~bash
javap -c -classpath build/classes app.Main
~~~

Look for the instruction calling `dep.Greeter.message`. Seeing the reference in bytecode **does not guarantee** that the target class is present on the runtime classpath.

### 8.2 Inspecting Which Class Version Is Loaded

With HotSpot/JDK 17+, you can observe class loading via unified logging:

~~~bash
java -Xlog:class+load=info -cp build/classes app.Main
~~~

The output will include multiple lines of JVM information; if `dep.Greeter` is loaded, the log typically shows the source of the class. Detailed log lines depend on the implementation, JDK version, and configuration; you should not hardcode the entire log as expected output.

This diagnostic command belongs to HotSpot/unified logging; it is not guaranteed that every JVM vendor accepts the exact same syntax.

### 8.3 Inspecting the Classpath at Runtime

You can print the `java.class.path` system property inside a Java program:

~~~java
System.out.println(System.getProperty("java.class.path"));
~~~

This is **an illustrative statement** that can be placed inside `main`, not a standalone program. It helps show the launcher classpath entries in typical configurations, but it does not list every source that may be used by custom class loaders or the module system.

### 8.4 Do Not Infer Class Origin Solely from File Name

Two `dep/Greeter.class` files in two different directories/JARs can contain different bytecode. If multiple entries share the same name on the classpath, the class loader typically searches according to the loader's order and rules; the result can depend on configuration.

When investigating “why is this machine running an old version,” check the **loaded class path**, classpath, JAR versions, and appropriate logs. Do not just inspect the file you assume is right in the currently open folder.

## 9. Common Errors and How to Handle Them

| Symptom | Possible Cause | Resolution |
| --- | --- | --- |
| Local build succeeds, clean CI reports `cannot find symbol` | Local still has old dependency binaries on the compile classpath | Build into a new directory, review the compile classpath and dependency declarations |
| Source file deleted but application still runs | Old `.class` file still resides in output/JAR/classpath | Identify the loaded artifact, create clean output, and inspect packaging |
| `package dep does not exist` during compile | Compiler does not see `dep` in allowed sources/classpath | Compile the dependency or add the correct version of the artifact to `-cp` |
| `NoClassDefFoundError: dep/Greeter` at runtime | Runtime cannot find the required class even though the app may have compiled | Add the dependency to the runtime classpath / package properly |
| `NoSuchMethodError` after replacing a JAR | Compile/runtime may be using different API versions | Check versions, classpath order, and binary compatibility |
| Running produces old results after editing source | Running the wrong output or forgot to recompile | Check `java -cp ...`, artifacts, and build logs |
| `Could not find or load main class app.Main` | Wrong runtime classpath root or main class not generated yet | Check `build/app/app/Main.class` and the fully qualified name |
| `error: directory not found` when using `-d` | Output directory does not exist or is inaccessible | Create the proper output directory and check permissions |
| Old package is still found after changing package | Old binaries were not removed | Rebuild into an empty output directory and inspect the class tree |
| `Greeter.class` exists yet compiler still reports an error | File is outside `-cp` or class is incompatible/misnamed | Check classpath root, package, major version, permissions, and detailed diagnostics |

### 9.1 Reading Errors by Phase

- `cannot find symbol`, `package ... does not exist`: usually **compile-time**, the compiler cannot resolve the symbol.
- `NoClassDefFoundError`, `ClassNotFoundException`: related to finding/loading/initializing classes at **runtime**, though the two error types are not completely synonymous; examine the stack trace and cause.
- `UnsupportedClassVersionError`: the runtime does not support the loaded class-file version.
- `NoSuchMethodError`: usually a binary API mismatch between compile-time and runtime artifacts, though other causes are possible.

Do not try to “fix” every error by haphazardly adding more directories to the classpath. That approach may make the build run again immediately, but it continues to hide missing dependencies and creates version conflicts.

## 10. Applying This with Gradle, Maven, and CI

Build tools manage the classpath, dependency graph, and outputs for you; however, some issues still arise if you write custom scripts or misconfigure tasks/packaging.

### 10.1 Gradle

In Java projects using Gradle, compile tasks have their own **destination directory** and **classpath**. The build tool tracks inputs/outputs and incremental compilation, but not every artifact created manually outside Gradle conventions will be tracked properly if custom task configuration lacks information.

To re-verify from a clean build output state when needed:

~~~bash
./gradlew clean classes
~~~

On Windows, using the batch wrapper:

~~~powershell
.\gradlew.bat clean classes
~~~

`clean` is Gradle's task that deletes build outputs managed according to configuration; it does not delete stray JARs in a directory outside the build directory if scripts/applications still point there. Do not assume a single `clean` command is enough to verify that all input dependencies are correct.

In multi-project applications, each project must declare its actual dependencies in build logic. A conceptual example of a Gradle Java module, in `build.gradle`:

~~~groovy
dependencies {
    implementation project(':library')
}
~~~

This snippet only illustrates **declaring a relationship between two appropriately named and configured Gradle projects**, not a standalone runnable project. When the dependency graph is declared properly, the build tool has the basis to compile the library before the application and place the correct dependency output onto the classpath.

### 10.2 Maven

In a Maven project with an appropriate compiler configuration, you can perform a clean build:

~~~bash
mvn clean compile
~~~

For multi-module Java projects, dependencies must be declared in the POM and reactor/module setup; Maven's `clean` removes managed outputs and does not automatically fix a wrong JAR referenced elsewhere.

An illustrative Maven dependency declaration in `pom.xml`:

~~~xml
<dependency>
    <groupId>com.example</groupId>
    <artifactId>greeter-lib</artifactId>
    <version>1.0.0</version>
</dependency>
~~~

This is a **configuration snippet**; the coordinates are only meaningful if the corresponding artifact actually exists in the dependency system. Do not add a dummy dependency to a build just to make an example run.

### 10.3 CI Is a Useful Reproducibility Test

CI with a clean checkout and fresh build output often catches issues that local incremental builds miss. However, CI also uses caches, so you need to distinguish between **valid dependency caches** and **old class outputs from another build**.

A good workflow needs to:

1. Accurately declare source sets and the dependency graph.
2. Avoid reading output directories outside configuration.
3. Build modules according to their dependency relationships.
4. Verify the final artifacts rather than relying solely on the exit code of a single compiler invocation.
5. Be capable of running a clean build in CI or when validating dependency changes.

Cached build outputs can be safe if cache keys, input tracking, and invalidation are correct. The problem is treating results of **unknown origin** as valid dependencies.

## 11. Self-Practice Exercises

### Exercise 1 — Predict the Outcome of Three Tests

With the same sources from section 3, predict the outcome:

~~~bash
javac -d build/classes src/dep/Greeter.java src/app/Main.java
javac -cp build/classes -d build/classes src/app/Main.java
javac -cp build/clean -d build/clean src/app/Main.java
~~~

Assume `build/classes` and `build/clean` are initially empty.

**Answer:** The first command succeeds and creates two classes; the second command succeeds thanks to `Greeter.class` generated in the first command; the third command fails because package `dep` is not visible on the clean compile classpath.

### Exercise 2 — Separating Compile Time from Runtime

From step B2, choose the correct run command on Linux/macOS:

~~~bash
java -cp "build/app:build/lib" app.Main
~~~

If you omit `build/lib`, what happens?

**Answer:** `app.Main` can be loaded, but when referencing `dep.Greeter` there will be an error related to a missing class at runtime, typically `NoClassDefFoundError` for `dep/Greeter`. The program will no longer print the normal result line.

### Exercise 3 — Changing a Dependency's Package

Suppose you rename `dep.Greeter` to `newdep.Greeter`, while also updating `app.Main`. If `build/classes/dep/Greeter.class` is still kept, why can an un-updated source still compile?

**Answer:** The old source still references `dep.Greeter`, and the old binary with the same name still exists on the classpath. Clean output will help detect the outdated reference if no corresponding dependency is declared.

### Exercise 4 — Checking Completeness of the Dependency Graph

If a build only compiles `Main.java` yet wants to be considered successful **without relying on old artifacts**, what is required?

**Answer:** `Greeter` must be included as a valid input: compile the dependency source in the appropriate source set or build the library module/JAR and point the classpath to the right artifact. An independent output must be used, without reading a directory containing leftover binaries outside the declared dependencies.

### Exercise 5 — Distinguishing `-d` and `-cp`

Why can the following command mask errors?

~~~bash
javac -cp build/classes -d build/classes src/app/Main.java
~~~

**Answer:** `-cp build/classes` allows the compiler to read binaries already existing there; `-d build/classes` also writes new classes to the same location. If the directory is not cleaned and contains an old `dep/Greeter.class`, the `Main.java` source can compile even though the current dependency has not been provided as intended.

## 12. Checklist Before Concluding a Build Is Clean

- [ ] Compiling **the exact source set** to be verified, without picking up unintended extra sources.
- [ ] Each module or test has its own output directory, which can be created fresh.
- [ ] Compile classpath contains only legitimately declared binaries and JARs.
- [ ] Not accidentally referencing the output directory from a previous build.
- [ ] Verified the result in a **fresh output**, without reusing old `.class` files.
- [ ] Checked for obsolete class files after changing packages / deleting sources / changing dependencies.
- [ ] Runtime classpath contains the exact dependencies needed at runtime.
- [ ] Inspected the fully qualified class name, loaded class path, and appropriate version when encountering errors.
- [ ] Build tool/CI properly manages inputs, outputs, caches, and the dependency graph.
- [ ] Observed real errors, without arbitrarily adding classpath entries just to make compilation pass.

## Conclusion

When the compiler sees an old `.class` file on the compile classpath, **it is entitled to use that file to resolve symbols**, even when the current source or dependency is missing. Therefore, a “compile successful” message is only meaningful for **the actual set of inputs** that the compiler read. To know whether a build is reproducible, **isolate outputs, declare dependencies explicitly, and verify with a compile from clean inputs**. This skill helps pinpoint the root causes of confusing discrepancies between personal machines, CI, and Java deployment environments.
