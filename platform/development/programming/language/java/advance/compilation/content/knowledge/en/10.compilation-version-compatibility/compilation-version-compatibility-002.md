# Meaning and Limitations of -source and -target When Compiling Java

## 1. The Problem: Compiling with a Newer JDK but Needing to Run on Older Java

When a project uses JDK 17, 21, or newer to compile, we may need to deliver the application to an environment that only has Java 8, 11, or 17. However, the statement “the program is Java 8 compatible” has at least **three independent meanings**:

1. **Source language:** which syntax constructs does the compiler accept? For example, lambdas belong to Java 8, `record` is a standard feature since Java 16.
2. **Bytecode format:** which class-file major version does the `.class` file use so that the target JVM can load it?
3. **Platform APIs:** which Java SE version do the classes/methods/fields referenced by the program belong to? An API present in a newer JDK may not exist in an older JDK.

Two traditional `javac` options control the first two layers:

- `--source N` or `-source N`: selects the accepted **source language level**.
- `--target N` or `-target N`: selects the **class-file version** generated by the compiler.

Importantly: **setting only `-source` and `-target` does not guarantee the program only uses APIs available on Java N**. To check all three layers when using JDK 9+, you should usually use `--release N`.

~~~text
                    Compile with a newer JDK
                                |
          +---------------------+---------------------+
          |                     |                     |
    Source language       Output bytecode         Platform API
       --source N            --target N         Not locked by
          |                     |               two flags alone
          +---------------------+---------------------+
                                |
                 --release N (usually preferred)
                  source + class version + API N
                                |
                          Test on JDK N
~~~

The word “usually” here is very important: `--release` checks the **public and supported platform APIs** of the target release; it does not replace checking third-party dependencies, runtime behavior, deployment configuration, or data compatibility.

## 2. -source: Controlling Syntax and Language Rules

Example:

~~~bash
javac --source 8 Main.java
~~~

Instructs `javac` to parse source code according to the Java 8 rules supported by the current compiler. With source code using `record`, Java 8 did not have that syntax yet, so the compiler must report an error instead of treating this as valid Java 8.

Typical milestones:

| Feature | Java version where it became standard | Remark when `--source` is lower |
| --- | --- | --- |
| Lambda and method reference | 8 | Invalid if the language level does not support it |
| Local-variable type inference with `var` | 10 | Invalid with `--source 8` |
| Switch expression | 14 | Invalid with `--source 11` |
| Text block | 15 | Invalid with `--source 11` |
| Record | 16 | Invalid with `--source 11` |
| Sealed classes/interfaces | 17 | Invalid with `--source 11` |

The table uses **finalized** versions; many features had a preview phase in earlier versions. Do not assume preview features will be supported merely by setting a lower `--source` on a newer compiler.

`-source` affects how the parser/type checker applies language rules, but **does not automatically select the system libraries of the older version**. This is the most common compatibility configuration mistake.

### Example A: a valid Java 17 program

Create the file `RecordDemo.java`:

~~~java
public record RecordDemo(int x, int y) {
    public static void main(String[] args) {
        RecordDemo p = new RecordDemo(2, 3);
        System.out.println(p.x() + p.y());
    }
}
~~~

Compile and run with JDK 17+:

~~~bash
javac --source 17 --target 17 RecordDemo.java
java RecordDemo
~~~

Stdout:

~~~text
5
~~~

The file declares `public record RecordDemo`, so the file name `RecordDemo.java` must match. With JDK 17, the program can also be compiled with `javac --release 17 RecordDemo.java`.

If you change the command to:

~~~bash
javac --source 8 --target 8 RecordDemo.java
~~~

the compiler rejects it because `record` does not belong to the Java 8 language. This is a **source language error**, without even needing to consider the output class file.

Note: using `--target 8` **cannot arbitrarily “backport” a Java 17 feature into Java 8 constructs**. `javac` is not a tool that transpiles every new syntax into older bytecode.

## 3. -target: Controlling Class-File Version, Not Checking APIs

The JVM reads class files according to a versioned format. The header begins with the magic `CAFEBABE`, followed by the minor version and major version; the major version increases across Java releases.

Some common milestones:

| Java SE | Class-file major version |
| --- | ---: |
| Java 8 | 52 |
| Java 11 | 55 |
| Java 17 | 61 |
| Java 21 | 65 |

With a compiler supporting the corresponding values, `javac --target 8` produces a major version 52 class file. A Java 8 JVM can understand this bytecode **format**, while a JVM older than the supported level may report `UnsupportedClassVersionError`.

However, being able to **read the class-file format** does not mean **the program can run**: the bytecode may reference methods that do not exist on a Java 8 runtime, external libraries may require a higher version, or the system may lack resources/native code.

`-target` specifies the version of class files generated by *that compilation pass*. It **does not automatically recompile** dependency JARs; a dependency with class-file version 61 still cannot run on Java 8 just because the application is compiled with target 8.

### Verifying with javap

From the `RecordDemo.java` example, run:

~~~bash
javap -verbose RecordDemo
~~~

In the header, you can see:

~~~text
major version: 61
~~~

This is the information to cross-check after compiling with target 17; the constant pool lines, timestamp, entry names, and remaining details may differ between compilers. Use `javap -verbose` or `javap -v` to read the generated file, rather than inferring from the JAR file name.

If compiling into the `build/classes` directory, you can use:

~~~bash
javap -classpath build/classes -verbose com.example.Main
~~~

This command is a **template**; it only runs when the directory actually contains `com/example/Main.class`.

## 4. Why Can -source 8 -target 8 Still Call Post-Java 8 APIs?

Suppose you use JDK 17 (or a newer JDK that supports `--source 8`/`--target 8`). Create `ApiTrap.java`:

~~~java
import java.util.List;

public class ApiTrap {
    public static void main(String[] args) {
        System.out.println(List.of("A", "B").size());
    }
}
~~~

`List.of` is an API added in Java 9. The static method call and generic method invocation syntax here is still **valid at the Java 8 language level**.

Compile with the newer JDK:

~~~bash
mkdir -p out/legacy
javac --source 8 --target 8 -d out/legacy ApiTrap.java
java -cp out/legacy ApiTrap
~~~

On JDK 17, `javac` can compile successfully while using the current platform APIs; it may emit a warning about bootstrap/platform classpath because it is compiling for an older release. Stdout of the command **running on JDK 17+**:

~~~text
2
~~~

The generated class file still has major version **52**. However, when taking that class to a **Java 8 runtime**, `java.util.List` in Java 8 **does not have** the static method `of`. By the time the method is linked/invoked, the program may fail with `NoSuchMethodError` instead of `UnsupportedClassVersionError`.

This is the core difference:

- `UnsupportedClassVersionError`: the JVM does not support the required **class-file format**.
- `NoSuchMethodError` or `NoClassDefFoundError`: the class file can be read, but the **API or dependent class** is not present/compatible at runtime.
- `-source 8`: the compiler only checks whether code follows **Java 8 language** rules; it does not automatically forbid calling `List.of`.
- `-target 8`: the compiler can produce a major 52 class file, which does not mean it has sufficiently verified Java 8 APIs.

In particular, code can compile successfully with `-source 8 -target 8` and run fine on the build machine's JDK; that is **not proof** that the application can run on real Java 8.

## 5. --release Combines the Three Necessary Layers for Compatibility

Starting in JDK 9, `javac` has the option:

~~~bash
javac --release 8 ApiTrap.java
~~~

This option directs the compiler to achieve these goals simultaneously:

1. Apply Java 8 language rules.
2. Generate class files compatible with Java 8 (major 52).
3. Allow code to reference only **supported public Java SE/JDK APIs of release 8**, according to the platform API information built into the compiler.

Because `List.of` did not exist yet in Java 8, the command `javac --release 8 ApiTrap.java` will be rejected at compile time. The error message may take the form `cannot find symbol` for method `List.of`; do not assume the verbatim error lines are identical across JDKs.

Comparison:

| Command (with a newer JDK supporting Java 8) | Language | Class version | APIs restricted to Java 8? |
| --- | --- | --- | --- |
| `javac --source 8 --target 8 ApiTrap.java` | Java 8 | 52 | No, unless old platform APIs are configured |
| `javac --release 8 ApiTrap.java` | Java 8 | 52 | Yes, for documented/supported platform APIs |
| `javac --release 17 RecordDemo.java` | Java 17 | 61 | Yes, for Java 17 platform APIs |
| `javac RecordDemo.java` on JDK 17 | JDK 17 default | JDK 17 default | Uses current platform |

The values of `N` accepted by `--release`, `--source`, and `--target` **depend on the `javac` version**. Do not assume the current compiler supports every Java release that ever existed. Check:

~~~bash
javac -version
javac --help
~~~

In `javac --help`, there is a list of supported releases for each option. With JDK 8, `--release` did not exist yet; to cross-compile, you had to use the options and platform classes appropriate for JDKs of that era.

### Example B: a valid Java 8 program from source to API

Create standalone file `CompatibleEight.java`:

~~~java
import java.util.Arrays;
import java.util.List;

public class CompatibleEight {
    public static void main(String[] args) {
        List<String> words = Arrays.asList("Java", "8");
        System.out.println(String.join("-", words));
    }
}
~~~

`Arrays.asList` and `String.join` both exist in Java 8. Use JDK 17+ that supports release 8:

~~~bash
mkdir -p out/release8
javac --release 8 -d out/release8 CompatibleEight.java
javap -classpath out/release8 -verbose CompatibleEight
java -cp out/release8 CompatibleEight
~~~

Observations:

- `javac --release 8` compiles successfully on an appropriate toolchain.
- The output of `javap -verbose` has `major version: 52`.
- Running `java` prints to stdout exact output:

~~~text
Java-8
~~~

Because it does not rely on APIs newer than Java 8, this program has a better basis for compatibility with a Java 8 runtime than `ApiTrap`. However, **to confirm deployment readiness**, it is still necessary to test on an actual Java 8 runtime, not just infer from the compile result and class major version.

### Example C: new syntax is blocked even with familiar APIs

The `RecordDemo.java` file in section 2 uses a record. Even though the body only performs very simple integer arithmetic, the command `javac --release 8 RecordDemo.java` still fails because `record` syntax is not yet in the Java 8 language. `--release` checks **both syntax and APIs**, not just the class-file format.

## 6. Cannot Arbitrarily Combine -source, -target, and --release

Configuration cases to avoid:

~~~bash
# Wrong: --release and the two source/target flags are mutually exclusive mechanisms.
javac --release 8 --source 8 CompatibleEight.java
javac --release 8 --target 8 CompatibleEight.java
~~~

The compiler refuses to use `--release` together with `--source` or `--target`. Choose one compatibility strategy intentionally.

`--source` and `--target` must be **compatible with each other**. For example, you cannot expect the compiler to accept all Java 17 syntax and generate Java 8 bytecode:

~~~bash
# Wrong/unsupported by the compiler: source is invalidly newer than target.
javac --source 17 --target 8 RecordDemo.java
~~~

`-target` is not a comprehensive *desugaring* tool capable of downgrading all language features and runtime semantics. Even in cases where the compiler permits a combination, you must still control platform APIs and test at runtime.

In addition:

- If specifying `--source N` while omitting `--target`, or vice versa, check the behavior of **the javac version in use** rather than assuming every JDK has the same default value. A more reliable approach is to use `--release N` or declare both with appropriate platform classes.
- A Java release can be **dropped from support** as a target/source in later compilers. In that case, a command that used to run on an older JDK may fail; this does not mean the source code is wrong.
- `--enable-preview` only serves preview features of **the release supported by the current compiler under current preview rules**. You cannot use `--enable-preview` as a workaround to compile new preview source into an arbitrary older Java release.
- If compiling code with `module-info.java`, module support belongs to Java 9+. You cannot produce a Java 8 deployment simply by setting `--target 8` on a module descriptor.

## 7. Cross-Compilation with -source/-target and Platform Classes

In principle, to cross-compile **without using `--release`**, you must supply the **platform classes** of the exact target version; otherwise, the compiler may see newer APIs from the running JDK.

When targeting **JDK 8 and earlier**, JDK tools of the appropriate era use a *boot class path* for older Java platform classes, through an option such as `-bootclasspath`. Specifying only `-source 8 -target 8` without providing Java 8 platform classes is insufficient to verify API compatibility.

When targeting **JDK 9 and later**, the Java platform uses system modules; modern compilers have the `--system` option to select the appropriate JDK platform classes location in manual cross-compilation scenarios. Do not use `-bootclasspath` to configure system platform modules of JDK 9+.

Explanation (this is **illustrative syntax**, not a standalone runnable command because a valid JDK path must be supplied):

~~~text
# Target Java 8 with the right older platform classes, on a still-supported toolchain:
javac -source 8 -target 8 -bootclasspath <java8-platform-classes> ...sources...

# Target Java 11 with the corresponding JDK system modules:
javac -source 11 -target 11 --system <path-to-jdk11> ...sources...
~~~

Do not replace placeholders with application library paths, because these options are meant for **platform classes/modules**. Each compiler restricts which combinations of options are allowed; check `javac --help` and the corresponding JDK documentation.

`--release N` is designed to simplify this, using platform API data bundled in the compiling JDK. By rule, `--release` does not allow arbitrary combinations of options that override platform classes or break encapsulation (for example, `--add-exports` to bypass access restrictions to JDK internals). If a project depends on unsupported internal APIs, safe cross-compilation requires **removing/replacing the internal APIs** or specifying explicit runtime constraints, rather than relying on the compiler accidentally letting it through.

## 8. What --release Does Not Guarantee Either

`--release 8` is a strong check, but it is not a certificate that the program will work in every Java 8 environment. There are several layers outside the scope of javac:

### 8.1. Third-party libraries

`--release 8` does not automatically guarantee that every dependency JAR can run on Java 8 or that every library version has compatible APIs. A dependency with a major 61 class file can break the application on Java 8, even if the main class is compiled with major 52.

For dependencies with multiple versions, you need to check **the dependency's minimum Java version**, class-file versions, dependency graph, and behavior. The build tool must choose the right library version; the compiler does not automatically download/resolve versions just because of `--release`.

### 8.2. APIs outside Java SE/JDK

The compiler checks the Java platform of the target release, but an external JAR can change or disappear between the build machine and the runtime machine. `--release` does not bundle external libraries into the output. You must distinguish compile classpath from runtime classpath.

### 8.3. Runtime behavior, environment, and patch updates

Two runtimes with the same major release name can still differ in update level, security policies, trust store, TLS settings, fonts, locale database, OS/CPU architecture, native libraries, and JVM configuration. A program using an API that exists in Java 8 can still fail to run if the environment lacks resources or encounters platform-dependent behavior.

Syntax/API/bytecode compatibility is an **important necessary condition**, but deployment testing remains a separate verification step.

### 8.4. Reflection, ServiceLoader, and dynamic loading

Reflection calls such as `Class.forName("...")` or looking up methods by string are not resolved like normal static Java calls. `--release` cannot prove that every class/method name the program constructs dynamically exists at runtime. Service providers, plugin JARs, or custom class loaders can also load incompatible code.

### 8.5. Java modules

With `--release 9` and above, you can use the corresponding module structure if the target supports it. However, the compiler still does not validate the entire deployment configuration on your behalf: you must consider the module path, `requires`, `exports`, service providers, runtime module arguments, and dependency modules present in the actual environment.

### 8.6. Preview features and new formats

A class built from a preview feature has special constraints regarding compiler/runtime and preview version. Do not use `--target` to assume that preview code can run on an older JVM. For applications needing long-term compatibility, prefer finalized Java features of the target release.

## 9. Distinguishing Source Compatibility, Binary Compatibility, and Behavioral Compatibility

| Question | Error example | How to verify |
| --- | --- | --- |
| Source compatibility: can code compile under language N? | `record` does not exist in Java 8 | `--release N` or check `--source N` |
| Class-file compatibility: does the JVM understand the bytecode? | Major 61 on a JVM supporting only major 52 | `--target N`, `javap -verbose` |
| Platform API compatibility: does Java N have the called method? | `List.of` missing in Java 8 | `--release N`, run on Java N |
| Dependency compatibility: can libraries/JARs also run? | Major 61 JAR in a Java 8 app | Check all JARs and test runtime |
| Linkage/binary compatibility: do class and method signatures match? | `NoSuchMethodError` when changing dependency | Check version/binary API and integration tests |
| Behavioral compatibility: same behavior when running? | Different locale, TLS, timezone, native code | Run integration tests on target runtime/OS |

Do not conflate the first three concepts. `--source 8` answers the syntax question; `--target 8` handles class-file readability; `--release 8` simultaneously adds a guardrail checking the platform APIs available in Java 8.

## 10. Gradle: Selecting the Right Toolchain and Release for the Target

With the Gradle `java` plugin, if the build runs on a newer JDK but needs a Java 8 artifact, you should configure the **toolchain** for the chosen compiler and `options.release` for the target platform. Example `build.gradle` in Groovy DSL:

~~~groovy
plugins {
    id 'java'
}

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(17)
    }
}

tasks.withType(JavaCompile).configureEach {
    options.release = 8
    options.encoding = 'UTF-8'
}
~~~

Meaning:

- Toolchain requests using the **JDK 17 compiler** for the JavaCompile task when Gradle finds a matching toolchain; that is the *compiler JDK version*.
- `options.release = 8` passes the equivalent of `javac --release 8` to control **Java 8 source language, class version, and platform APIs**.
- `options.encoding = 'UTF-8'` makes explicit how the compiler reads source files.

**JDK 17 toolchain and Java 8 target are two independent decisions.** Setting only `sourceCompatibility = '8'` and `targetCompatibility = '8'` on a newer JDK does not provide the full platform API guardrail like `options.release`. Similarly, setting only Java toolchain 17 does not mean the output will be Java 8 compatible.

If the project must use an API available only in a newer JDK, you need to decide to raise the minimum runtime or design a compatibility approach, rather than removing the `--release` check so the build passes and deployment fails.

To verify in practice on a project with Gradle Wrapper, use the compile/test tasks:

~~~bash
./gradlew clean compileJava test
~~~

On Windows, use `gradlew.bat`. This command is a **project command**, not a standalone command from the two example files above; the result depends on build.gradle, test framework, dependencies, and the configured environment.

If the project uses Java test code that requires newer syntax/APIs than production, you must configure the corresponding task/source set/toolchain intentionally; do not silently alter the production artifact or pull test classes into runtime.

## 11. Maven: Using maven.compiler.release Instead of Only source/target

In Maven's `pom.xml`, the snippet below is a **fragment inside the `project` element**:

~~~xml
<properties>
    <maven.compiler.release>8</maven.compiler.release>
</properties>
~~~

With a Maven Compiler Plugin version that supports this property and an appropriate JDK 9+ compiler, it configures compilation according to `--release 8`. This differs from setting:

~~~xml
<properties>
    <maven.compiler.source>8</maven.compiler.source>
    <maven.compiler.target>8</maven.compiler.target>
</properties>
~~~

The source/target pair controls language and class files, but does not automatically resolve the new platform APIs issue. The specific plugin/toolchain configuration still needs to be compatible with the JDK in use. Older versions of Maven Compiler Plugin or JDK 8 have different support capabilities, since `--release` was introduced in JDK 9.

Test/build plugins and dependency JARs can also have their own JDK requirements. Therefore, check the compiler toolchain, plugin versions, and the actual runtime used by CI/deployment.

## 12. Common Errors and How to Read Messages

| Symptom | Possible cause | How to investigate |
| --- | --- | --- |
| Compiler reports `record` syntax unsupported | Source language level is too low | Choose a sufficiently new release or change syntax |
| `invalid source release` / `invalid target release` | Compiler does not support the configured value | `javac -version`, `javac --help`; change toolchain |
| Compiler reports `source release ... requires target release ...` | `--source` and `--target` conflict | Align options to the target release |
| Bootstrap classpath warning when using source 8 | Newer compiler is using platform classes not locked to Java 8 | Use `--release 8` or the proper bootclasspath |
| `List.of` compiles but fails on Java 8 | Source/target does not block new APIs | Use `--release 8`, test on Java 8 |
| `UnsupportedClassVersionError` | Class file/JAR requires a newer JVM | Run `javap -verbose` for app and dependencies |
| `NoSuchMethodError` | Runtime binary API differs from compile time | Verify the exact JDK/API/JAR versions |
| `--release` cannot be used with `--source` or `--target` | Mutually exclusive options | Use only `--release N` |
| `--release` disallows calling JDK internal APIs | Internal APIs are not public/supported in the release | Replace with supported APIs |
| Compiles successfully but integration tests fail on older runtime | Checked source only, lacked runtime/environment testing | Run CI matrix on target JDK |
| Using Java 17 toolchain but JAR still requires Java 17 | Desired `options.release`/target not yet set | Separate compiler JDK from target artifact |

**Note:** the exact wording and ordering of `javac` messages may differ across JDK versions. Use error categories and explanations for diagnosis, rather than writing tests that depend on a fixed stderr string.

## 13. Verification Workflow for Compatibility from Source to Runtime

A project claiming to “run on Java 8” should have multi-layered evidence:

1. **Lock down the minimum runtime:** does the project require Java 8, 11, 17, or another version? Document it clearly in docs and CI.
2. **Select the compiler toolchain:** a tested JDK version supporting the corresponding `--release N`. Do not assume every new javac supports every old N.
3. **Compile with `--release N`:** control language, bytecode, and public platform APIs.
4. **Inspect class version:** run `javap -verbose` on product classes and check binary dependencies; the artifact must have an appropriate JVM version.
5. **Check the dependency graph:** every runtime JAR has a compatible minimum Java version, method/class availability, and dependency configuration.
6. **Run on the actual target JDK:** smoke/functional/integration tests using Java N, including execution paths that use reflection or service loading.
7. **Test the deployment environment:** OS/CPU, encoding, locale, timezone, TLS, certificates/trust store, native libraries, and JVM flags where relevant.
8. **Ensure reproducible builds:** pin toolchain and dependency versions; CI builds from a clean checkout, without relying on leftover class/JAR files.

### Control Experiment

Create the two standalone files `ApiTrap.java` and `CompatibleEight.java` as in sections 4 and 5. Use a newer JDK that supports Java 8:

~~~bash
# Experiment: plain source/target can accept newer Java APIs.
javac --source 8 --target 8 -d out/legacy ApiTrap.java

# Real compatibility check with Java 8 APIs: this line must be rejected.
javac --release 8 -d out/release8 ApiTrap.java

# A program valid for Java 8 APIs can be compiled successfully.
javac --release 8 -d out/release8 CompatibleEight.java

# Observe major version 52 and the Java-8 output.
javap -classpath out/release8 -verbose CompatibleEight
java -cp out/release8 CompatibleEight
~~~

**Do not put the entire sequence above into a shell script assuming all commands exit 0**: the command compiling `ApiTrap` with `--release 8` is designed to **fail**, proving that the compiler blocked the newer API.

Finally, if a Java 8 runtime is available, run `CompatibleEight` on that JVM and observe `Java-8`. If the target runtime is not available, you can only assert that it passed static compiler checks, not that runtime testing succeeded.

## 14. Principles to Remember

- `--source N` controls the **language level**; it does not automatically restrict Java platform APIs to N.
- `--target N` controls the **class-file version**; it does not rewrite library dependencies or guarantee the runtime has the required APIs.
- `--release N` is usually the right choice when compiling from a newer JDK for Java N, because it combines source, target, and API compatibility on the **supported Java N platform**.
- `--release` does not replace checking third-party libraries, runtime environment, reflection/native code, or behavior across versions.
- Supported values of N vary by compiler version; check `javac --help` on the actual toolchain.
- Avoid conflicting configurations between `--release` and `--source`/`--target`; do not expect `-target` to automatically lower new Java features into older bytecode.
- Inspect `major version` with `javap -verbose`, then **run tests on the lowest JVM declared as supported**.
