# Handling `processingOver`, `errorRaised`, and state across rounds in annotation processors

An annotation processor's job is not just reading an annotation and creating a file. In **JSR 269**, a single `javac` invocation can perform multiple **processing rounds**: new sources/classes created by a processor in a previous round become targets for analysis in the next round, and participating processors continue receiving `process(...)` calls, including the **final round**. To build a reliable processor, you must manage **state across multiple rounds**, properly handle **`RoundEnvironment.processingOver()`** and **`RoundEnvironment.errorRaised()`**, avoid creating duplicate files, and not treat the final round as an opportunity to generate new code.

This lesson explains the conditions in detail, provides a complete Java 17 processor that both generates source and records observed types across multiple rounds, and then demonstrates an intentional diagnostic error case to prove `errorRaised()` is not the same as `processingOver()`.

## 1. Processing rounds and three distinct kinds of state

During a compiler invocation:

1. `javac` has the initial set of source/class files, root elements, and processable annotation types.
2. Selected processors are invoked via `process(annotations, roundEnv)` for the current round.
3. New `.java`/`.class` files created via `Filer` whose writers/streams are properly closed are examined in the **next round**.
4. A round that creates no further new source/class types to process leads to the **final round**. Processors called in prior rounds receive a final call to summarize.
5. If the build has not halted due to errors and is not in processing-only mode, the tool proceeds to complete compilation.

Example diagram:

```text
Input: demo.Main @Tracked("root")
             |
             v
       Round 1: process(Main)
       state = {"demo.Main"}
       Filer generates demo.Generated
             |
             v
       Round 2: process(Generated)
       state = {"demo.Main","demo.Generated"}
       no further files generated
             |
             v
       Final round: processingOver() == true
       no additional source/class generated
       summarizes state and prior errors
             |
             v
       Compiler completes or reports failure
```

In the diagram, **state** persists across multiple `process` invocations on the **same processor instance**. However, the `RoundEnvironment` object reflects a **specific round**, not the entire history.

| What to check | Source | Meaning |
| --- | --- | --- |
| Does the current round end processing? | `roundEnv.processingOver()` | `true` in the final round; types generated in this round are not passed to a new processing round |
| Did the previous round report an error? | `roundEnv.errorRaised()` | `true` if an error occurred in the **prior round**, not “overall build status” |
| What are the root elements of the current round? | `roundEnv.getRootElements()` | Root declarations fed into that round |
| Which elements carry matching annotations? | `roundEnv.getElementsAnnotatedWith(...)` | Matching elements within the current round's scope |
| Which types has the processor seen from the start? | **Processor-maintained state** | E.g. `Set<String> observedTypes`, not available from a single `RoundEnvironment` |
| Has a specific type already been generated? | **Processor state + `Filer`** | Prevents duplicate output creation within the same invocation |

**Common confusion:** `getElementsAnnotatedWith(...)` returning an empty set **does not prove the final round has been reached**. A generated type might not carry annotations the processor cares about; processors that participated earlier continue being invoked.

## 2. `processingOver()`: the final-round handling branch

The `RoundEnvironment.processingOver()` API states: returns `true` if types generated by this round **will not be subject to a subsequent round of annotation processing**. This is the criterion to identify the final round in a processor.

A recommended handling pattern:

```java
@Override
public boolean process(
        Set<? extends TypeElement> annotations,
        RoundEnvironment roundEnv) {
    if (roundEnv.processingOver()) {
        // Final summary or checks.
        // Do not generate class/source files that need further processor handling.
        return true;
    }

    // Analyze elements and optionally create sources/classes.
    return true;
}
```

This is a **method fragment** inside an `AbstractProcessor`, not yet a class with complete imports.

### What is allowed in the final round?

- Read **accumulated state** stored from previous rounds.
- Print diagnostics via `Messager` to report results or missing data when there is a sound reason.
- Check invariant conditions, such as ensuring an annotation group produced an expected recorded type.
- Release or close resources managed by the processor, if any.
- Inspect `errorRaised()` from the **immediately preceding round** to avoid falsely reporting success.

### What should not be done in the final round?

- Create `.java`/`.class` files that another processor must handle in a new round: **there is no next round to do that**.
- Use `createSourceFile` in the final round to build a type that application sources will import; doing so may trigger compiler warnings and fail to process the new file as expected.
- Treat `processingOver() == true` as proof the compiler succeeded. The final round can also happen during an error flow.
- Assume the final round is always round 2 or round 3. The number of rounds depends on generated files and actual processing.

**Subtle note:** A processor can create a **resource** at an appropriate stage, yet resources created via `Filer.createResource` do not count as new sources/classes to trigger another annotation round. For new source/class code, generate **before** the final round. If a final aggregated `.java` artifact is needed, design it so content is decided in a normal round with sufficient data, or use a separate build mechanism for the aggregation step; do not expect “final round generates source and the compiler reruns”.

## 3. `errorRaised()`: strictly errors of the *prior round*

According to Java SE 17 documentation, `RoundEnvironment.errorRaised()` returns `true` **if an error was raised in the prior round of processing**. Therefore:

- In the first round, when no actual processing round preceded it, there is normally no prior-round error to report.
- If a processor emits `Diagnostic.Kind.ERROR` in round 1, the **next round** will receive the signal `errorRaised() == true`.
- If a round has warnings without errors, `errorRaised()` is not set merely because of warnings.
- `errorRaised() == false` **does not guarantee** final compilation will succeed; for instance, type-checking/resolution errors may still be discovered after processing.

Suppose:

```text
Round 1:
  processingOver=false
  errorRaised=false
  processor emits ERROR

Subsequent final round:
  processingOver=true
  errorRaised=true
  processor knows prior round raised an error
```

This is a **typical state progression** for an error detected by a processor in the initial round. A complex case with many rounds may need tracking **historical** errors, because `errorRaised()` directly refers only to the previous round.

### Tracking errors across multiple rounds

A processor wanting to know “have any prior rounds ever reported an error” can maintain state:

```java
private boolean observedPriorRoundError;

@Override
public boolean process(
        Set<? extends TypeElement> annotations,
        RoundEnvironment roundEnv) {
    observedPriorRoundError |= roundEnv.errorRaised();
    if (roundEnv.processingOver()) {
        // Can use observedPriorRoundError to avoid reporting success.
        return true;
    }
    return true;
}
```

This is an **illustrative fragment**, not a standalone file. This value accumulates only errors exposed by the `errorRaised` API as the processor receives corresponding rounds. If **the processor itself** emits an error in the current round and needs an immediate aggregate flag, set `hasReportedError = true` right when calling `Messager.printMessage(ERROR, ...)`; do not wait for `errorRaised` to update within the same call.

Table of three key states:

| State | Accurate interpretation |
| --- | --- |
| `processingOver=false, errorRaised=false` | Normal round; previous round reported no errors per API; can continue processing/generating files |
| `processingOver=true, errorRaised=false` | Final round; no error signal from previous round; **does not** prove compilation will succeed |
| `processingOver=true, errorRaised=true` | Final round, prior round reported an error; do not keep generating to “rescue” the build |

Do not treat the table above as a promise that the compiler will **always** produce every state combination on every program. It is an interpretation table for the two flags when the processor receives them.

## 4. Where is state stored across rounds?

Under the `Processor` contract, the compiler **does not instantiate a new processor object each round**. After `init(ProcessingEnvironment)` is called, the same processor instance receives all `process` invocations belonging to that compilation invocation.

State example:

```java
private final Set<String> seenTypeNames = new TreeSet<>();
private final Set<String> emittedTypeNames = new HashSet<>();
private int calls;
private boolean emittedAnySource;
private boolean hasReportedError;
```

The fields above are **declaration fragments** that must be placed in a class with appropriate imports; not a standalone `.java` file.

Meaning:

- `seenTypeNames` stores **stable String type names** across multiple rounds for use in the final round.
- `emittedTypeNames` records names of types already generated, avoiding calling `Filer.createSourceFile` twice for the same name.
- `calls` counts how many times the processor received `process` in the running invocation; **not** the compiler's total round count if the processor was selected late.
- `emittedAnySource` is for processors permitted to generate only one artifact per invocation.
- `hasReportedError` helps recognize self-reported errors immediately when emitting a diagnostic.

### Why store names instead of keeping `Element`/`TypeMirror` too long?

`Element` and `TypeMirror` are supplied by the compiler in the processing environment and tied to the program model currently being processed. As new code appears across rounds, the model can evolve and model objects follow specific rules. Storing **Strings, primitives, immutable DTOs, or small summary data** is generally easier to understand and test than holding model references and reusing them arbitrarily across rounds.

Do not treat a processor instance or state across **two separate compilation invocations** as a source of truth. Even though a build system may use a long-lived JVM daemon, the standard API does not guarantee processor instance fields serve as persistent memory across two builds. For accurate incremental builds, rely on build-tool-managed inputs/outputs and `Filer`'s **originating elements**.

### State must be deterministic

The set returned by `getElementsAnnotatedWith(...)` may not have an order suitable for output ordering or serialization. If you want deterministic logs/outputs, **sort names** (e.g., `TreeSet`) before aggregating. If two rounds provide the same type name (or the processor is invoked again in special circumstances), use a `Set` to avoid double-counting under the chosen policy.

For an **aggregating processor** generating one artifact from multiple source parts, clearly define when sufficient data has been collected. `processingOver()` is suitable for **checking/summarizing**, yet not a valid moment to create a new Java source needing further processing. Complex generators need a multi-round protocol structure or must offload aggregation to another build task.

## 5. Complete Java 17 example: keeping state, generating a type, and summarizing in final

This example consists of annotation `@Tracked`, processor `TrackingProcessor`, and application `Main`. The processor performs:

1. Receives `demo.Main` annotated `@Tracked("root")` in round 1.
2. Records `demo.Main` and **generates source** `demo.Generated` (also annotated `@Tracked("generated")`).
3. In round 2, receives `demo.Generated`, accumulates into the same `Set<String>`; does not regenerate the file.
4. In the final round, reads `processingOver` and `errorRaised`, prints a `NOTE` diagnostic with the observed names, and returns. Generates no code in final.
5. The application calls `Generated.message()` after the compiler compiles the newly generated source file.

### 5.1. Project structure

```text
project/
└── src/
    ├── demo/
    │   ├── Tracked.java
    │   └── Main.java
    └── processor/
        └── TrackingProcessor.java
```

Contents of **`src/demo/Tracked.java`**:

```java
package demo;

import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

@Retention(RetentionPolicy.SOURCE)
@Target(ElementType.TYPE)
public @interface Tracked {
    String value();
}
```

`RetentionPolicy.SOURCE` is sufficient for the processor to inspect sources; no requirement for the annotation to appear in runtime class files. `Target(TYPE)` limits the annotation to type declarations.

Contents of **`src/processor/TrackingProcessor.java`**:

```java
package processor;

import demo.Tracked;
import java.io.IOException;
import java.io.Writer;
import java.util.Set;
import java.util.TreeSet;
import javax.annotation.processing.AbstractProcessor;
import javax.annotation.processing.RoundEnvironment;
import javax.annotation.processing.SupportedAnnotationTypes;
import javax.annotation.processing.SupportedSourceVersion;
import javax.lang.model.SourceVersion;
import javax.lang.model.element.Element;
import javax.lang.model.element.ElementKind;
import javax.lang.model.element.TypeElement;
import javax.tools.Diagnostic;
import javax.tools.JavaFileObject;

@SupportedAnnotationTypes("demo.Tracked")
@SupportedSourceVersion(SourceVersion.RELEASE_17)
public final class TrackingProcessor extends AbstractProcessor {
    private final Set<String> observedTypes = new TreeSet<>();
    private boolean generated;
    private boolean sawPriorError;
    private boolean reportedOwnError;
    private int calls;

    @Override
    public boolean process(
            Set<? extends TypeElement> annotations,
            RoundEnvironment roundEnv) {

        calls++;
        sawPriorError |= roundEnv.errorRaised();

        if (roundEnv.processingOver()) {
            processingEnv.getMessager().printMessage(
                    Diagnostic.Kind.NOTE,
                    "calls=" + calls
                    + ", types=" + String.join(",", observedTypes)
                    + ", priorError=" + sawPriorError
                    + ", ownError=" + reportedOwnError);
            return true;
        }

        Element mainOrigin = null;

        for (Element element :
                roundEnv.getElementsAnnotatedWith(Tracked.class)) {
            if (element.getKind() != ElementKind.CLASS) {
                continue;
            }

            TypeElement type = (TypeElement) element;
            String fullName = type.getQualifiedName().toString();
            observedTypes.add(fullName);

            String label = element.getAnnotation(Tracked.class).value();
            if ("reject".equals(label)) {
                processingEnv.getMessager().printMessage(
                        Diagnostic.Kind.ERROR,
                        "Rejected @Tracked value on " + fullName,
                        element);
                reportedOwnError = true;
            }

            if ("demo.Main".equals(fullName) && !reportedOwnError) {
                mainOrigin = element;
            }
        }

        if (!generated && mainOrigin != null) {
            try {
                JavaFileObject output = processingEnv.getFiler()
                        .createSourceFile("demo.Generated", mainOrigin);
                try (Writer writer = output.openWriter()) {
                    writer.write(
                            "package demo;\n"
                            + "@Tracked(\"generated\")\n"
                            + "public final class Generated {\n"
                            + "  private Generated() {}\n"
                            + "  public static String message() {\n"
                            + "    return \"Hello across rounds\";\n"
                            + "  }\n"
                            + "}\n");
                }
                generated = true;
            } catch (IOException exception) {
                processingEnv.getMessager().printMessage(
                        Diagnostic.Kind.ERROR,
                        "Cannot generate demo.Generated: "
                                + exception.getMessage(),
                        mainOrigin);
                reportedOwnError = true;
            }
        }

        return true;
    }
}
```

**Processor analysis:**

- The two `@Supported...` annotations describe the annotation type and source version supported by the processor.
- `observedTypes` is a `TreeSet<String>` keeping **type names** across rounds in stable ascending order; does not retain `Element` past its round.
- `generated` is flipped to `true` **after the writer closes successfully**; the processor does not try creating `demo.Generated` multiple times.
- `calls` counts how many times **this processor** is called during the invocation, not the round counts of other processors.
- `sawPriorError |= roundEnv.errorRaised()` accumulates **prior-round error signals**.
- `reportedOwnError` is set right when the processor calls `printMessage(ERROR, ...)`. That is processor-managed state; it differs from the flag provided by `RoundEnvironment`.
- `mainOrigin` is the originating element passed to `Filer.createSourceFile`, useful for incremental build systems.
- `try (Writer ...)` closes the output stream, enabling the compiler to recognize generated source for the next round.
- `roundEnv.processingOver()` is checked **before** the loop and `Filer` operations; final only prints the summary.
- `return true` means the processor **claims** the annotation types it is asked to process, not a control signal to stop processing.

In a small example with a single `Main`, a boolean flag `generated` suffices. If generating classes per annotated element in a real project, use a `Set<String> generatedTypeNames` and a naming/idempotency strategy to avoid omissions or duplicates.

Contents of **`src/demo/Main.java`**:

```java
package demo;

@Tracked("root")
public final class Main {
    public static void main(String[] args) {
        System.out.println(Generated.message());
    }
}
```

`Generated` **does not yet exist in the initial source tree**. This is an intentional example letting `javac` pick up a class created by the processor during annotation processing.

### 5.2. Compile the annotation and processor first

From directory `project`, with JDK 17+ supporting target 17:

```sh
javac --release 17 -encoding UTF-8 -proc:none -d build/processor src/demo/Tracked.java src/processor/TrackingProcessor.java
```

This step outputs at least:

```text
build/processor/
├── demo/Tracked.class
└── processor/TrackingProcessor.class
```

Uses `-proc:none` because the processor does not need to run during bootstrap. When `javac` succeeds, it normally prints no messages.

### 5.3. Compile the application and run the processor

```sh
javac --release 17 -encoding UTF-8 -cp build/processor -processorpath build/processor -processor processor.TrackingProcessor -s build/generated -d build/classes -XprintRounds -XprintProcessorInfo src/demo/Main.java
```

Meaning:

| Option | Role |
| --- | --- |
| `-cp build/processor` | Lets app and generated source look up annotation class `demo.Tracked` during compilation |
| `-processorpath build/processor` | Lets the tool locate and load the processor class |
| `-processor processor.TrackingProcessor` | Selects processor explicitly; no service file required |
| `-s build/generated` | Location of generated `.java` from `Filer.createSourceFile` |
| `-d build/classes` | Directory for class files of the application and generated types |
| `-XprintRounds` | Prints root elements and annotations per round |
| `-XprintProcessorInfo` | Prints invoked processors / claimed annotations |

When compilation succeeds, the output structure looks like:

```text
build/
├── processor/
│   ├── demo/Tracked.class
│   └── processor/TrackingProcessor.class
├── generated/
│   └── demo/Generated.java
└── classes/
    └── demo/
        ├── Generated.class
        └── Main.class
```

### 5.4. Running the program and interpreting logs

```sh
java -cp build/classes demo.Main
```

**Exact stdout of the program:**

```text
Hello across rounds
```

The `-XprintRounds` and `-XprintProcessorInfo` flags emit diagnostics during compilation, **not stdout of program `Main`**. Because formatting and ordering can vary by JDK, do not write tests by comparing the entire compiler log character by character.

Expected processing flow:

| Round | Involved roots | Annotations | What does the processor handle? |
| --- | --- | --- | --- |
| 1 | `demo.Main` | `demo.Tracked` | Records `demo.Main`, generates `demo.Generated.java` |
| 2 | `demo.Generated` | `demo.Tracked` | Records `demo.Generated`; `generated` flag blocks recreation |
| 3, final | No new roots | None | `processingOver() == true`; emits result NOTE only |

The final `NOTE` diagnostic normally has the **core content**:

```text
calls=3, types=demo.Generated,demo.Main, priorError=false, ownError=false
```

This is **the message text assembled by the processor source**, not a guaranteed verbatim copy of the full `javac` log line (which may have a `Note:` prefix, whitespace, or different position). `TreeSet` sorts `demo.Generated` before `demo.Main`.

The processor does not need to create files in final and wait for “round 4”; code created in round 1 is recognized by the compiler in round 2 and compiled within the same invocation.

## 6. Testing `errorRaised()` with an intentional compile failure case

To observe how the processor reacts to errors, create **a standalone source** `src/demo/Rejected.java`:

```java
package demo;

@Tracked("reject")
public final class Rejected {
}
```

`TrackingProcessor` has the branch:

```java
if ("reject".equals(label)) {
    processingEnv.getMessager().printMessage(
            Diagnostic.Kind.ERROR,
            "Rejected @Tracked value on " + fullName,
            element);
    reportedOwnError = true;
}
```

This is an **actual excerpt from the full processor class**, not a separate file. When `Rejected` is processed, the processor emits an `ERROR`. Use separate output directories to avoid colliding with `Main`'s successful build:

```sh
javac --release 17 -encoding UTF-8 -cp build/processor -processorpath build/processor -processor processor.TrackingProcessor -s build/rejected-generated -d build/rejected-classes -XprintRounds src/demo/Rejected.java
```

**Expected result:** Compilation fails (non-zero exit code), diagnostic contains `Rejected @Tracked value on demo.Rejected`. No `demo.Generated` output is produced from this negative example, because the processor only generates `Generated` when encountering `demo.Main`.

In the typical flow:

- Round 1 has `processingOver=false`, `errorRaised=false` before the processor emits `ERROR`.
- When the compiler invokes the processor in the next/final round, `errorRaised()` reports `true` due to the error in the prior round.
- `reportedOwnError` becomes `true` **right in round 1**, because the processor updates it itself before returning from `process`.
- `sawPriorError` becomes `true` when the compiler reports the previous round error.
- The final round still **must not** be interpreted as “the build succeeded cleanly”.

The summary NOTE message may contain:

```text
calls=2, types=demo.Rejected, priorError=true, ownError=true
```

This is a **common scenario** when a processor is called in round 1 and then final; exact log details and call counts may vary if the tool adds extra rounds or triggers additional errors. Do not use `calls == 2` as a hard assertion across all JDKs or source sets.

### If a processor emits `ERROR`, must it throw an exception?

**No.** `Messager.printMessage(Diagnostic.Kind.ERROR, ...)` is the standard way to report a source issue via diagnostics. Throwing an unhandled exception from `process` can cause the tool to abort other processors and make errors harder to read; throw only when there is truly no way to recover or report an error cleanly.

At the same time, if an error was raised in a round, processor code should not try creating types meant as success artifacts and then report `“success”` in final. The processor can gather additional diagnostics, yet must respect the fact that compilation will fail.

## 7. Preserving data across multiple rounds without generating duplicate code

A practical processor design usually maintains **two data sets**:

- **Input-derived state**: observed types/fields/methods, validation state, relationships to aggregate.
- **Output-derived state**: set of file names requested for creation, files whose writers closed cleanly, file creation errors.

Suggested structure:

```java
private final Set<String> seen = new TreeSet<>();
private final Set<String> emitted = new HashSet<>();
private boolean hadValidationError;
```

This is a **declaration fragment**. Import `java.util.Set`, `TreeSet`, and `HashSet` when placing it in a complete processor.

For each element:

1. Retrieve a **stable name** such as `((TypeElement) e).getQualifiedName().toString()`.
2. Validate annotations/options and record state.
3. If type `pkg.GeneratedX` needs to be generated, check that name in `emitted` or the managed set.
4. Call `Filer.createSourceFile` with the exact name; write valid code and close the writer.
5. Record the successful file creation result.
6. In the next round, handle new roots without self-generating duplicates.
7. In final, perform only data checking/summarization; do not generate new sources/classes.

### Why does `FilerException` matter?

`Filer` enforces a rule prohibiting creating **the same pathname/type multiple times in a single invocation**, including collisions with an input type or between source/class files of the same name. If a processor creates `demo.Generated` in round 1 and tries calling `createSourceFile("demo.Generated")` again in round 2, the tool typically throws `FilerException` like “Attempt to recreate a file for type ...”.

**Do not solve this by arbitrarily deleting files** while the compiler is running. Fix type-generation conditions, ownership between processors, and the naming scheme. Files lingering from an older invocation and recreating the same file **within one invocation** are two distinct issues; distinguish old/stale outputs from `Filer`'s recreate rule.

Generated **resources** from `Filer.createResource` do not themselves trigger another processing round like sources/classes. Merely creating a `.java` file via `Files.write` outside `Filer` is also not guaranteed by the compiler to enter the subsequent round.

## 8. `return true`/`false` is not directly tied to ending rounds

`process(...)` returns a boolean confirming whether the processor **claims the assigned annotation types**.

- `true`: the processor takes responsibility for the annotation types; downstream processors are no longer asked to process these exact claimed annotations under discovery.
- `false`: does not claim, leaving them for other processors to process.
- Does not mean `true = compilation success` or `false = ERROR`.
- Does not mean `false = compiler creates a new round` or `true = final round`.

A `@SupportedAnnotationTypes("*")` processor (universal processor) only auditing/validating should usually `return false`; returning `true` with `"*"` can swallow annotation types and prevent other processors from running as expected.

For the `@Tracked` processor in the example, `return true` is a choice to claim the annotation it controls. Round counts still come from generated code and termination conditions, **not** from `process`'s boolean return value.

## 9. Pitfalls in holding onto `Element` and compiler models

A new processor often wants to put round 1 `Element`s into a `List<Element>` and reuse them directly in the final round. Be cautious:

- `Element`, `TypeMirror`, and `AnnotationMirror` are **model objects** bound to the processing environment, not compiler-independent immutable DTOs.
- The compiler can add generated types in later rounds; global state lookups can shift.
- When needing only **type names, field names, textual types, enum constants, or verified annotation info**, extract them into small suitable data to retain across rounds.
- When needing to analyze types of the current round, use `processingEnv.getElementUtils()`/`getTypeUtils()` and `roundEnv.getRootElements()` within supported API bounds.
- Do not use Java runtime reflection like `Class.forName` to load application classes being compiled expecting to always find new classes; those classes may not yet exist in the processor's runtime.
- Do not retain state across two compiler invocations because a daemon/build tool may alter how processor instances are created.

### Aggregated data and incremental builds

A generated file can come from a single annotated class (**isolating**) or from aggregating multiple annotated classes (**aggregating**). These are terms commonly used by build tools; **they are not two new JSR 269 processor API types**. Build tools may require dedicated metadata/configuration to support incremental annotation processing.

Passing `originatingElements` to `Filer` lets the tool know the origin creating a file. If a processor depends on undeclared resources or unstable set ordering, a clean build may succeed while an incremental build produces stale/wrong artifacts. Test both build types with outputs managed by the build tool.

## 10. Not every error condition appears immediately via `errorRaised()`

When processor code hits errors, there can be three signal sources:

| Source | Where is it observed? | Handling |
| --- | --- | --- |
| Processor self-validates and emits `Diagnostic.Kind.ERROR` | Immediately in the current round, known by processor upon emitting | Set internal flag `reportedOwnError`, do not generate success artifacts |
| Compiler notifies of error from previous round | `roundEnv.errorRaised()` in the next round | Store cumulative flag if history is needed |
| Compiler detects error after processors finished running | Other compile/type/link phases, not necessarily reflected back to the processor | Do not conclude compilation succeeded merely because final saw no error |

This explains why **the final round is not an "onSuccess" callback**. It is only the final callback of the annotation-processing lifecycle. A processor can print summary logs, yet the build tool/`javac` decides the exit status after full compilation.

If designing an artifact representing “build succeeded”, do not create it prematurely based on `!errorRaised()`; instead let the **build system** manage marker/success artifacts after the compiler returns a successful exit code.

## 11. An example of data across multiple processors

Suppose two processors coordinate:

- `ModelProcessor` sees `@Model` on class A and generates `generated.DescriptorA` annotated with `@Descriptor`.
- `DescriptorProcessor` sees `@Descriptor` on the generated source and generates an additional mapper.

Key point: `DescriptorProcessor` should not rely on **being called after `ModelProcessor` in the same round** to immediately discover `DescriptorA`. Generated source enters **the next round** under the `Filer` contract. If each processor keeps intentionally generating new files endlessly, the entire invocation will not converge and can become an abnormally long processing loop.

Coordination rules:

1. **Orthogonality:** one processor should not change its result merely because an unrelated processor is present.
2. **Consistency:** same input → same output.
3. **Commutativity:** processing order of independent inputs does not change the final result.
4. **Independence:** avoid requiring another processor's output to appear immediately within the same round.
5. **No duplicate generation:** every generated type has a single owner.
6. **Finite progression:** chains of generated types must have a clear termination condition.
7. **Clear diagnostics:** validation errors are reported attached to specific source elements when possible.

These principles match sustainability guidelines for the `Processor` API, especially when different IDEs, compilers, and build tools execute the same processor.

| `javac` option | Effect |

| `-processor processor.TrackingProcessor` | Explicitly specify the processor to run |
| `-processorpath path` | Path to load processors |
| `-cp path` | Classpath used to look up annotations/dependencies in source |
| `-s path` | Generated **source** output directory |
| `-d path` | Compiled **class** output directory |
| `-XprintRounds` | Prints round number, roots, and annotation types in `javac`'s format |
| `-XprintProcessorInfo` | Prints invoked processors and related annotation types |
| `-proc:only` | Runs only annotation processing, skipping normal class file compilation |
| `-proc:none` | Disables annotation processing |
| `-Akey=value` | Passes an option declared supported by the processor |

When inspecting `-XprintRounds`:

- Do not treat **round numbers** as persistent IDs across incremental builds.
- Do not test exact ordering/contents of every compiler stderr line across JDKs.
- Confirm a type created by the processor in round n appears in **round n+1**.
- Confirm the final round reports `processingOver() == true` if the processor logs info.
- Confirm generated files in `-s` and compiled classes in `-d` match expectations.
- Do not confuse `-XprintProcessorInfo` with `System.out.println` written by program `Main`.

When only wanting to inspect generated sources:

```sh
javac --release 17 -encoding UTF-8 -cp build/processor -processorpath build/processor -processor processor.TrackingProcessor -s build/only-sources -d build/only-classes -proc:only -XprintRounds src/demo/Main.java
```

This is a **separate command**, using different output directories from the full run example. `-proc:only` does not perform the normal final application class compilation step; do not expect `Main.class` to be emitted as in `-proc:full`/normal compile. With processors creating class files directly via `Filer.createClassFile`, custom outputs still exist; distinguish source processing from the final compilation step.

## 13. Common bugs and how to fix them

| Symptom | Possible cause | Resolution |
| --- | --- | --- |
| `process` is called again with empty `annotations` | Processor participated in an earlier round; current round has no supported annotations | Handle empty sets safely; use `processingOver` to detect final |
| State only sees types from the last round | Overwriting state or reading `getRootElements` from a single round | Use a Set/Map on the processor instance to accumulate |
| `processingOver()` is true yet code still calls `createSourceFile` | Missing final guard | Return early in final; do not generate new classes/sources |
| `errorRaised()` stays false right after the processor called ERROR | It only reports the **prior round** | Store an internal flag when reporting error; observe next round |
| Final round saw no errors yet compilation failed | Errors occurred in another phase or status only checked prior round | Rely on compiler exit code, do not treat final as success |
| `FilerException: Attempt to recreate a file` | Created the same type/path twice in an invocation | Record created names, fix naming/conditions |
| Type generated properly yet missing in next round | Did not use Filer, writer unclosed, source error, or compilation broken | Call `createSourceFile` properly, close writer, read diagnostics |
| Processor runs only when invoked explicitly | Service discovery/processor path differs from expectation | Specify `-processor` or declare service/module provider properly |
| Infinite generation of generated sources | Generator lacks a fixed point or fails to block recreation | Design finite generation, check naming and cycles |
| Clean build works, incremental build fails | Stale outputs, undeclared origins, or missing input tracking | Check originating elements, build tool, and outputs |

### Ordered debugging workflow

1. Verify `javac -version`, `-processor`, `-processorpath`, `-s`, `-d`, `-proc`.
2. Enable `-XprintRounds` and `-XprintProcessorInfo`; confirm the processor is loaded.
3. Inspect each round: what do `getRootElements()` and `getElementsAnnotatedWith(...)` contain?
4. Check whether the processor guards `processingOver` before creating files.
5. When hitting ERROR, compare the **error-emitting round** against `errorRaised` in the **subsequent round**, not within the same round.
6. Check whether instance state is accidentally cleared/overwritten on every `process`.
7. Check generated filename/package and whether the writer is closed.
8. If a file does not appear in the next round, check whether a resource was created instead of a source/class.
9. Check the exit code and generated sources/classes before running the application.
10. Compare clean builds and incremental builds if the bug reproduces only across multiple builds.

## 14. Checklist before releasing a processor

- [ ] Does the processor have a public no-argument constructor and declare supported annotations/source version properly?
- [ ] Does it handle **every invocation** of `process`, including empty annotation sets and the final round?
- [ ] Is `processingOver()` checked before code-generation operations?
- [ ] Is `errorRaised()` understood as a **prior-round error**, not a success flag?
- [ ] Does the processor track errors it emits itself immediately in the current round?
- [ ] Is state across rounds kept in the instance using stable names/DTOs, avoiding inadvertent reliance on old `Element`s?
- [ ] Are generated types created with `Filer`, streams closed, and without duplicates?
- [ ] Does aggregated data have deterministic ordering without depending on set iteration order?
- [ ] Is the annotation-claiming `return true/false` rule kept distinct from round termination?
- [ ] Were normal single-round, multi-round codegen, final non-generating, and negative ERROR cases tested?
- [ ] Was the processor tested when the same annotations are also observed by other processors?
- [ ] Were clean and incremental builds tested without implicitly retaining state across invocations?
- [ ] Were application class files and the final exit code verified, not merely relying on a NOTE in final?

**Remember:** `processingOver()` indicates **this is the final round, with no subsequent annotation processing round to handle new code**. `errorRaised()` indicates **the prior round reported an error**, not “build failed/succeeded” in the complete sense. Accumulated state across rounds must be stored by the processor on the **same instance**, alongside rules to avoid duplicates and control errors. Under those conditions, the processor generates code at the right time and summarizes meaningfully without inadvertently prolonging compilation.
