# Retaining Parameter Names with `-parameters` and the Limits of This Metadata

## Objectives

After this lesson, you will be able to:

- Explain why parameter names `left` and `right` in Java source code do not automatically appear when read via Reflection at runtime.
- Use `javac -parameters` to store formal parameter names of **methods** and **constructors** into class files, then verify them with `java.lang.reflect.Parameter` and `javap`.
- Distinguish `MethodParameters` metadata from debug information (`LocalVariableTable`, `-g`), generic types, annotations, and local variable names.
- Enable the compiler option in Gradle/Maven projects and inspect the actual class files used by the application.
- Recognize cases where metadata is missing, transformed, or differs between interface/implementation; handle safely when a framework relies on parameter names for binding.

This lesson covers **compilation configuration and parameter-name metadata**, not an exhaustive guide to all Reflection techniques.

## 1. Why can Java forget parameter names?

Consider a snippet inside a Java class:

~~~java
public static int multiply(int left, int right) {
    return left * right;
}
~~~

Reading the source, you see two names `left` and `right`. However, to invoke the method at the JVM level, the method name, parameter types, and parameter order are what identify the method descriptor. The parameter names chosen by the author **are not needed** for the virtual machine to execute multiplication.

Therefore, under default compilation, a `.class` file retains the method structure and `int` types without metadata reflecting the two source names. Java Reflection still returns a two-element `Parameter` array, yet `getName()` typically synthesizes placeholder names:

~~~text
arg0
arg1
~~~

The names `arg0` and `arg1` are synthetic names derived from parameter indices; they do not prove the source declared those two names.

Since Java 8, `javac` provides the `-parameters` option to preserve **formal parameter names** in class files. It is especially useful for libraries/frameworks reading method/constructor signatures at runtime, such as mapping input names to parameters.

Processing flow:

~~~text
Source:
  int multiply(int left, int right)
                  |
                  | javac -parameters
                  v
Class file:
  method descriptor: (II)I
  MethodParameters: left, right
                  |
                  | JVM loads class / Java Reflection
                  v
  Method.getParameters()
                  |
                  +--> getName(): "left", "right"
                  +--> isNamePresent(): true, true
~~~

`(II)I` represents two `int` parameters and one `int` return value in the JVM descriptor. The names `left` and `right` are auxiliary metadata; they do not alter this descriptor.

## 2. What does `-parameters` actually record?

In class files emitted by `javac` with:

~~~bash
javac -parameters Example.java
~~~

the compiler writes **`MethodParameters`** metadata for method/constructor declarations. This attribute can contain the name and flags of each parameter, including special cases like `synthetic` or `mandated`.

Standard Java APIs for reading it:

| API | Role |
| --- | --- |
| `Method.getParameters()` | Returns `Parameter[]` objects for the reflected method |
| `Constructor.getParameters()` | Returns `Parameter[]` for the reflected constructor |
| `Parameter.getName()` | Returns the name from class-file metadata; if no real name exists, returns a placeholder like `arg0` |
| `Parameter.isNamePresent()` | Confirms whether real parameter-name metadata was stored |
| `Parameter.getType()` | Returns the parameter's `Class<?>` type, independent of name-storage flags |
| `Parameter.getParameterizedType()` | Reads parameter type info, including generics when matching generic metadata exists |
| `Parameter.isImplicit()` / `isSynthetic()` | Helps identify certain parameters generated by language rules or the compiler |

**Key point:** names in source code are not a promise of runtime presence. Conversely, the presence of `MethodParameters` does not mean that metadata alone explains every method semantic.

### 2.1 Why not check using the name `arg0`?

Do not write logic like “if `getName()` starts with `arg`, metadata is definitely missing”. The source author could genuinely name a parameter `arg0`. When compiled with the flag, `getName()` still returns `arg0` and `isNamePresent()` returns `true`.

Always use `isNamePresent()` if your system requires exact declared names. A library with optional support can also provide an explicit fallback when metadata is absent.

### 2.2 Not information about a specific call

Suppose code declares:

~~~java
public void send(String recipient, int attempts)
~~~

the stored names can be `recipient` and `attempts`. It **does not record concrete values** of any invocation, such as `"An"` or `3`. A `Parameter` object belongs to the **method declaration**; it is not a window into an executing stack frame.

Similarly, `-parameters` does not indicate whether a parameter may be null, adds no validation, stores no JavaDoc descriptions, and does not turn Java into a named-arguments language.

## 3. Hands-on comparison with Java 17+

You need JDK 17+ and a terminal; no IDE or framework is required. Check the commands:

~~~bash
java -version
javac -version
~~~

Output depends on the JDK/vendor installed on your machine. Ensure `java` and `javac` point to compatible versions; on Windows you can use `Get-Command java` and `Get-Command javac` in PowerShell, and on Bash/Zsh use `command -v`.

### 3.1 Create a complete Reflection example

Create **`src/ParameterNamesDemo.java`** (UTF-8 encoding):

~~~java
import java.lang.reflect.Method;
import java.lang.reflect.Parameter;

public class ParameterNamesDemo {
    public static int multiply(int left, int right) {
        return left * right;
    }

    public static void main(String[] args) throws Exception {
        Method method = ParameterNamesDemo.class
                .getDeclaredMethod("multiply", int.class, int.class);

        for (Parameter parameter : method.getParameters()) {
            System.out.println(parameter.getName()
                    + " | present=" + parameter.isNamePresent()
                    + " | type=" + parameter.getType().getSimpleName());
        }

        System.out.println("Tich = " + multiply(6, 7));
    }
}
~~~

This is a standalone program. `getDeclaredMethod` looks up the method by **name and parameter types**, not searching for `left` or `right`. The loop reads metadata for each `Parameter`, then the program executes the multiplication logic.

### 3.2 Separate compilation directories to avoid running the wrong class

From the project directory containing `src/ParameterNamesDemo.java`, create two output directories:

**PowerShell:**

~~~powershell
New-Item -ItemType Directory -Force out/without, out/with | Out-Null
~~~

**Bash/Zsh:**

~~~bash
mkdir -p out/without out/with
~~~

The purpose of two outputs is keeping **both class builds created with different configurations** at the same time. Building both passes into a single directory easily causes confusion because the second build overwrites the first.

### 3.3 Compile without `-parameters`

~~~bash
javac -encoding UTF-8 -d out/without src/ParameterNamesDemo.java
java -cp out/without ParameterNamesDemo
~~~

Because `javac` compiles by default without storing parameter names via `MethodParameters`, the program's stdout is:

~~~text
arg0 | present=false | type=int
arg1 | present=false | type=int
Tich = 42
~~~

The compiler normally prints nothing when successful. The three lines above are printed by the Java program at **runtime**, not reported by `javac`.

### 3.4 Compile with `-parameters`

~~~bash
javac -parameters -encoding UTF-8 -d out/with src/ParameterNamesDemo.java
java -cp out/with ParameterNamesDemo
~~~

Stdout:

~~~text
left | present=true | type=int
right | present=true | type=int
Tich = 42
~~~

Both builds return product `42`; only parameter-name reflection metadata differs. `-parameters` does not require changing method signatures, does not alter how Java calls `multiply(6, 7)`, and does not make the JVM create an extra argument.

Verify this step yourself by running with `-cp out/without` and `-cp out/with` in turn. If both builds show real names, check whether you accidentally ran the same artifact or another tool modified the class files.

### 3.5 Inspecting class files with `javap`

`javap` is a JDK tool for reading class file contents:

~~~bash
javap -v -p -classpath out/without ParameterNamesDemo
javap -v -p -classpath out/with ParameterNamesDemo
~~~

Locate the `multiply` method description. In the build with `-parameters`, `javap -v` displays a section like:

~~~text
MethodParameters:
  Name                           Flags
  left
  right
~~~

`javap -v` also prints the constant pool, bytecode, offsets, and other info; the excerpt above focuses only on the relevant attribute. Full output can vary across JDK versions.

In the build lacking the flag, `multiply`'s `MethodParameters` section may be absent. **Do not verify merely by searching for the string `left` across the whole class file:** some names can appear in other debug attributes. A human finding a string inside a class file does not guarantee `Parameter.getName()` reads that name.

### 3.6 Directory structure after building

~~~text
project/
├── src/
│   └── ParameterNamesDemo.java
└── out/
    ├── without/
    │   └── ParameterNamesDemo.class
    └── with/
        └── ParameterNamesDemo.class
~~~

`java -cp out/with ParameterNamesDemo` picks the `.class` with metadata. `java -cp out/without ParameterNamesDemo` picks the build lacking metadata. Using the wrong classpath causes reflection calls to reflect whichever class the JVM actually loaded, not what the builder intended.

### 3.7 Successful compilation is not enough to prove names were stored

Even when `javac` exits with code 0, a configuration may still omit `-parameters`. When business logic requires parameter names, checks should include:

1. Identify the **actual running** `.class` file or JAR.
2. Inspect `MethodParameters` with `javap -v`.
3. Run Reflection code checking `Parameter.isNamePresent()`.
4. Test an actual method/constructor analyzed by your framework.

Reading only “BUILD SUCCESSFUL” logs does not answer whether the metadata exists.

## 4. Constructors also receive parameter-name metadata

`-parameters` does not apply only to methods. Create **`src/ConstructorNamesDemo.java`**:

~~~java
import java.lang.reflect.Constructor;
import java.lang.reflect.Parameter;

public class ConstructorNamesDemo {
    private final String title;
    private final int count;

    public ConstructorNamesDemo(String title, int count) {
        this.title = title;
        this.count = count;
    }

    public static void main(String[] args) throws Exception {
        Constructor<ConstructorNamesDemo> constructor =
                ConstructorNamesDemo.class.getConstructor(String.class, int.class);

        for (Parameter parameter : constructor.getParameters()) {
            System.out.println(parameter.getName()
                    + " | present=" + parameter.isNamePresent());
        }

        ConstructorNamesDemo item = constructor.newInstance("Sách", 3);
        System.out.println(item.title + ": " + item.count);
    }
}
~~~

Compile and run with the flag:

~~~bash
javac -parameters -encoding UTF-8 -d out/with src/ConstructorNamesDemo.java
java -cp out/with ConstructorNamesDemo
~~~

Stdout:

~~~text
title | present=true
count | present=true
Sách: 3
~~~

Compile and run without the flag:

~~~bash
javac -encoding UTF-8 -d out/without src/ConstructorNamesDemo.java
java -cp out/without ConstructorNamesDemo
~~~

Stdout:

~~~text
arg0 | present=false
arg1 | present=false
Sách: 3
~~~

Constructing `ConstructorNamesDemo` follows **parameter order and constructor code**. Stored parameter names are not what makes `this.title = title` work.

### When there are “hidden” constructors or compiler-generated parameters

Certain class kinds can cause the compiler to emit extra parameters in bytecode not directly visible in source, such as non-`static` inner classes or enums. In those cases, elements in `Constructor.getParameters()` may differ from what you expect from reading source. Flags `isImplicit()` or `isSynthetic()`, together with type information and actual class files, help analyze these cases.

Do not assume every constructor has the exact parameter count visible in the source signature, nor that every reflected parameter was author-written. For mappers or dependency-injection containers, compiler-added parameters can affect constructor selection or binding logic.

## 5. Do not confuse `-parameters` with `-g`

`javac` has different debug information options. Formal parameter names in `MethodParameters` and variable names in debuggers are stored through **different mechanisms**.

| Mechanism | Related Metadata | Purpose | Readable via `Parameter.getName()`? |
| --- | --- | --- | --- |
| `-parameters` | `MethodParameters` | Stores formal parameter names of executables | Yes, if metadata exists |
| `-g` | Debug attributes, including source, line, and local variables when applicable | Debuggers and bytecode analysis | Not a sufficient guarantee |
| `-g:vars` | Local variable info, typically `LocalVariableTable` | Reading variable names in debugging tools | Does not replace `MethodParameters` |
| `-g:none` | Omits optional debug information per that option | Reduces debug data | Can still store `MethodParameters` via `-parameters` |
| Runtime annotations | `RuntimeVisibleAnnotations` or matching annotation metadata | Parameters/methods with annotations | Does not automatically store formal parameter names |
| Generic signature | `Signature` when needed | Lets Reflection read generic types | Not directly related to names |

Example build **both saving names and omitting debug information**:

~~~bash
javac -parameters -g:none -encoding UTF-8 -d out/with src/ParameterNamesDemo.java
java -cp out/with ParameterNamesDemo
~~~

Stdout for names is still:

~~~text
left | present=true | type=int
right | present=true | type=int
Tich = 42
~~~

Conversely, try:

~~~bash
javac -g -encoding UTF-8 -d out/without src/ParameterNamesDemo.java
java -cp out/without ParameterNamesDemo
~~~

`-g` does not guarantee `isNamePresent()` becomes `true`. Tools reading `LocalVariableTable` might infer some names when bytecode permits, yet **standard Java Reflection does not use `-g` as a substitute for `-parameters`**.

### Formal parameters are not arbitrary local variables

Consider a snippet inside a class:

~~~java
static int square(int value) {
    int result = value * value;
    return result;
}
~~~

`value` is a formal parameter; `result` is a local variable. The `-parameters` flag targets the method's parameter name `value`; it provides no Reflection API to list all local variables like `result`. Viewing variable names in a debugger is the domain of debug metadata.

### Annotations on parameters are also independent data

Illustrative signature example:

~~~java
void update(@Deprecated String identifier) {
    // This snippet is placed inside a class, not a standalone program.
}
~~~

An annotation does not automatically put `identifier` into `MethodParameters`. Whether an annotation appears at runtime depends on the annotation type's `@Retention` and compiler config; parameter names remain a separate aspect. Similarly, generic type metadata and parameter names are distinct axes of information.

## 6. Limits to understand accurately

### 6.1 Stores only declared names, not runtime values

`getParameters()` reads the **method or constructor definition**. It does not know whether calls passed `"customer-01"`, `42`, or `null`; it holds no call history and cannot read variables on the stack of a running thread.

Observing executing arguments is the job of debuggers, instrumentation, logging, or other runtime observability tools, with their own constraints and requirements.

### 6.2 No named arguments in Java syntax

Having parameter-name metadata does **not** make the following syntax valid:

~~~java
// This is an example of INVALID SYNTAX in Java.
multiply(left: 6, right: 7);
~~~

The valid Java call to the example method is:

~~~java
// Illustrates a statement inside a class having the multiply(int, int) method.
int product = multiply(6, 7);
~~~

`-parameters` does not add default arguments, does not change argument passing order, and does not make the compiler validate input names under any framework's rules.

### 6.3 Does not generate validation or parameter descriptions

If a parameter is named `email`, the compiler does not validate email addresses. If named `amount`, metadata does not express whether it must be positive or represent currency. Names include no JavaDoc comments, nullability contracts, or business rules.

If a framework wants data validation, it needs another rule source: annotations, schemas, code validators, or explicit configuration.

### 6.4 Cannot modify precompiled dependencies

An application can combine your own sources, code-generator-created classes, and many library JARs. Enabling the flag for your module's sources **does not inject metadata into JARs built elsewhere**.

For example:

~~~text
application.jar: built with -parameters
library.jar: built without -parameters
~~~

Reflection on methods of `application.jar` can see real names, whereas methods of `library.jar` still return `arg0`. For a library to have metadata, it must be compiled/packaged appropriately at its source or processed by a tool capable of reliably adding metadata.

### 6.5 Bytecode transformers can strip or alter names

Some build pipelines also run obfuscators, shrinkers, optimizers, bytecode instrumentation, or packaging tools. Depending on configuration, they can keep, rename, or strip `MethodParameters`. Therefore, **`javap` results right after `javac` might not match the final deployed artifact**.

If a framework requires metadata, inspect the **class files in the final JAR** or classes actually loaded by the JVM. Certain systems use custom class loaders or dynamic class generation that require care when tracing method sources.

### 6.6 Parameter names are not part of binary method signatures

Changing:

~~~java
void publish(String topic)
~~~

to:

~~~java
void publish(String channel)
~~~

does not alter parameter types or the JVM method descriptor. Other precompiled code can still call that method as before. However, a framework using names as keys can change behavior from binding `topic` to `channel`.

Parameter names can thus **become a contract at the framework layer** even when not governing binary compatibility. If names are used in API routes, query mappings, or constructor binding, treat renames like data-contract changes.

### 6.7 Compiler-generated, implicit, and synthetic parameters

In some Java constructs, the compiler generates extra parameters or methods for execution. `Parameter[]` may include parameters not obvious from the source signature. `isImplicit()` and `isSynthetic()` flags help inspect corresponding metadata when present, yet do not build logic assuming every compiler/transformer creates and preserves identical metadata.

This matters when reflecting constructors of non-static inner classes, enums, or compiler/framework-generated methods. When building a binder, examine the **declaring class**, executable kind, parameter types, parameter count, and flags, not just names.

### 6.8 Present names can reveal business structure

Names like `customerNumber`, `transactionLimit`, or `internalFlag` can expose part of an application's vocabulary through distributed class files. `-parameters` is not a security feature. Do not place secrets in source/metadata and do not rely on the absence of metadata to keep secrets safe in distributed products.

Obfuscation tools can rename identifiers, yet if a framework relies on names, appropriate keep/mapping rules must be configured. Do not expect both full-name obfuscation and intact name-based runtime binding simultaneously.

## 7. Interfaces, inheritance, and reflected methods

Formal parameter names are tied to **each individual method declaration**, not inherited in the sense that overriding methods must keep the same parameter names.

Create **`src/DeclarationNamesDemo.java`**:

~~~java
import java.lang.reflect.Method;

interface Processor {
    void process(String input);
}

class UpperProcessor implements Processor {
    @Override
    public void process(String text) {
        System.out.println(text.toUpperCase());
    }
}

public class DeclarationNamesDemo {
    public static void main(String[] args) throws Exception {
        Method onInterface =
                Processor.class.getMethod("process", String.class);
        Method onClass =
                UpperProcessor.class.getMethod("process", String.class);

        System.out.println(onInterface.getParameters()[0].getName());
        System.out.println(onClass.getParameters()[0].getName());
    }
}
~~~

Compile and run:

~~~bash
javac -parameters -encoding UTF-8 -d out/with src/DeclarationNamesDemo.java
java -cp out/with DeclarationNamesDemo
~~~

Stdout:

~~~text
input
text
~~~

Both declarations are valid overrides because Java override rules rely on compatible method signatures, without requiring `input` and `text` to match.

A framework reflecting `Processor.class` may see `input`, whereas reflecting `UpperProcessor.class` sees `text`. If a framework uses proxies, bridge methods, or dynamically generated classes, the returned name also depends on **the specific method being reflected**. Do not look only at method name while ignoring `Method.getDeclaringClass()` and the implementing class's method.

If you build a binding library yourself and want to read names from interfaces, define explicit rules for where names come from and how to handle interface/implementation differences. `-parameters` does not merge those names automatically.

## 8. How do frameworks use parameter names?

Many libraries can use runtime parameter names to:

- Map query, path, or command argument names to handler method parameters.
- Select values for constructors when instantiating objects from named data.
- Generate error messages, documentation, or metadata for developer tooling.
- Wire inputs in dependency injection or serializers per custom contracts.

However, **not every framework enables this feature automatically**. A framework might prefer names declared in annotations, read names via Reflection, read custom metadata, or ignore parameter names altogether.

Conceptual example: when a handler defines `find(String orderId)`, a framework supporting name inference can bind input key `orderId` based on `MethodParameters`. Another framework may require annotations explicitly specifying names, or use a different mechanism. Always check the contract of the framework in use.

For public APIs, explicit names in annotations/configs usually keep behavior stable if Java variable names change later. If choosing name inference via Reflection, ensure the compilation pipeline **retains metadata across all relevant modules** and include tests for binding behavior.

### Do not use metadata to infer types or default values

If `Parameter.getName()` returns `timeout`, you still need to inspect the parameter type via `getType()`, annotations, and rules to know how to parse inputs. `timeout` could be `int`, `long`, or `Duration`. Names do not change types and do not establish default values.

## 9. Practical configuration with compilers and build tools

One general rule: the flag must be passed to the **compiler processing sources containing the methods/constructors you inspect**, and then the class files actually loaded at runtime must retain that metadata.

### 9.1 Direct `javac` command

~~~bash
javac -parameters -encoding UTF-8 -d out/with src/ParameterNamesDemo.java
~~~

When Java 17 compatibility is needed and using a JDK supporting that option:

~~~bash
javac --release 17 -parameters -encoding UTF-8 -d out/with src/ParameterNamesDemo.java
~~~

`--release 17` sets the language level, Java platform APIs, and class-file target for Java 17; `-parameters` stores parameter-name metadata. The two options solve **two different needs**. Do not use `--release` in place of `-parameters`.

### 9.2 Gradle Groovy DSL

In `build.gradle` of a module applying the Java plugin, you can add:

~~~groovy
tasks.withType(org.gradle.api.tasks.compile.JavaCompile).configureEach {
    options.compilerArgs.add('-parameters')
}
~~~

This applies to `JavaCompile` tasks configured in that module, provided the compiler/toolchain supports it. Multi-module projects may need settings in multiple places or via a shared convention plugin.

With **Gradle Kotlin DSL** in `build.gradle.kts`:

~~~kotlin
tasks.withType<org.gradle.api.tasks.compile.JavaCompile>().configureEach {
    options.compilerArgs.add("-parameters")
}
~~~

This is a build configuration example, not a Java source snippet. If the project has separate compile tasks for tests or generated sources, verify whether they receive the flag. After changing configuration, rebuild the relevant classes.

### 9.3 Maven

In the module's `pom.xml`, the compiler plugin configuration can include:

~~~xml
<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-compiler-plugin</artifactId>
            <configuration>
                <parameters>true</parameters>
            </configuration>
        </plugin>
    </plugins>
</build>
~~~

This is an **XML snippet to place inside a valid Maven configuration**, not an entire standalone `pom.xml` file. Use a suitable plugin version supporting `<parameters>`; actual versions may be governed by the project's `pluginManagement`.

If modules use different compiler configurations, enabling `parameters` in module A does not automatically emit names for classes in module B. When consuming a third-party library JAR, Maven/Gradle flags in the current project also do not alter metadata inside that JAR.

### 9.4 Verifying after build instead of trusting config on paper

To verify the effective configuration:

1. Rebuild the module using the actual build tool you run.
2. Locate the final class output directory or built JAR, avoiding running stale classes.
3. Open that exact class file with `javap -v -p`; inspect `MethodParameters` on a recognizable method.
4. Run a Reflection snippet calling `isNamePresent()` directly on the final runtime classpath.
5. If the application goes through obfuscation/instrumentation, perform checks **after that step**.

Example for the practice layout:

~~~bash
javap -v -p -classpath out/with ParameterNamesDemo
java -cp out/with ParameterNamesDemo
~~~

With Gradle/Maven, replace `out/with` with the actual output path produced by the tool; do not assume every tool uses the example's directory.

### 9.5 Do not confuse compiler flags with JVM options

`-parameters` is a **`javac` option**. Running `java -parameters ...` does not magically add metadata to class files that lack names. The JVM reads pre-built classes; names must exist in the artifacts loaded by the JVM. Similarly, the JVM can run class files containing `MethodParameters` without needing `-parameters` at launch.

Easy-to-remember summary:

~~~text
javac -parameters ...  -> creates name metadata in .class
java -cp ...          -> loads .class and reads metadata via Reflection
~~~


## 10. Writing safe code when names may be missing

If your logic requires real parameter names, handle missing metadata explicitly. Create **`src/RequireNamesDemo.java`**:

~~~java
import java.lang.reflect.Method;
import java.lang.reflect.Parameter;

public class RequireNamesDemo {
    public static void greet(String person) {
        System.out.println("Hello, " + person);
    }

    public static void main(String[] args) throws Exception {
        Method method =
                RequireNamesDemo.class.getDeclaredMethod("greet", String.class);

        Parameter parameter = method.getParameters()[0];
        if (!parameter.isNamePresent()) {
            System.out.println("Missing parameter-name metadata");
            return;
        }

        System.out.println("Parameter name = " + parameter.getName());
        greet("An");
    }
}
~~~

Without flag:

~~~bash
javac -encoding UTF-8 -d out/without src/RequireNamesDemo.java
java -cp out/without RequireNamesDemo
~~~

Stdout:

~~~text
Missing parameter-name metadata
~~~

With flag:

~~~bash
javac -parameters -encoding UTF-8 -d out/with src/RequireNamesDemo.java
java -cp out/with RequireNamesDemo
~~~

Stdout:

~~~text
Parameter name = person
Hello, An
~~~

This example prints a message and returns when metadata is missing. A real system can **fail fast** with an exception and instructions to enable the compiler flag, or fall back to names declared explicitly in annotations. Crucially, avoid silently treating `arg0` as a business input name unless defined by contract.

**Do not infer:** “`isNamePresent()` returning `true` means framework binding succeeded.” That result confirms only one part: parameter names are available. You still must verify whether inputs match names, types, validation, data sources, and framework rules.

## 11. Common errors and how to verify

| Symptom | Possible Cause | How to Verify |
| --- | --- | --- |
| `getName()` returns `arg0` and `isNamePresent()` is `false` | Class lacks formal parameter-name metadata | Rebuild module with `-parameters`, run `javap` on final class |
| Enabled `-g` yet still cannot read names | Debug metadata does not substitute for `MethodParameters` | Use `-parameters` |
| Old names appear after editing source | Stale class/JAR still loaded | Inspect `-cp`, build outputs, deployed artifacts, and classpath |
| Build tool has configuration yet names are still missing | Flag on wrong module/task or compile cache has not updated running artifact | Verify compiler arguments, class files, and final artifact |
| Interface method has different name from implementation | Metadata belongs per declaration | Check `getDeclaringClass()` and which declaration the framework inspects |
| Constructor has unexpected parameter count | Compiler may emit implicit/synthetic parameters | Inspect `getParameters()`, flags, and actual bytecode |
| Framework fails to bind despite names being present | Framework uses different mapping/annotation rules | Check framework docs/config, inspect inputs/types |
| Reflection works locally yet fails when deployed | Packaging, transformers, obfuscation, or runtime classpath differs | Compare deployed artifact and actually loaded classes |
| `Parameter.getName()` returns `arg0` yet `isNamePresent()` is `true` | Actual parameter name in source may literally be `arg0` | Trust flags and metadata, do not guess from strings alone |
| Library A has metadata, B does not | JARs were built with different configurations | Inspect individual methods/constructors on respective classes |

### Do not mix up compile-time and runtime

`javac` can produce completely valid classes without the `-parameters` flag. Those classes still run, the JVM still knows parameter counts/types, and methods and constructors can still be called. Only APIs/frameworks requiring source names observe a difference.

Conversely, the compiler can record complete metadata while runtime binding still fails due to mismatched input names, missing annotations, unconvertible types, or invalid runtime data. Those are application-contract errors, not a failure of `-parameters`.

Compile `DeclarationNamesDemo` with the flag, explaining why the interface returns `input` and the implementing class returns `text`.

**Answer:** Names attach to each declaration and do not participate in JVM signature-based override rules.

### Exercise 5 — Detecting missing metadata

Run `RequireNamesDemo` without the flag. Why does the code not call `greet("An")`?

**Answer:** `isNamePresent()` returns `false`, so the missing-metadata branch prints a message and exits `main`. This is an explicit choice by application code, not automatic JVM behavior.

### Exercise 6 — Multi-module project

Module `api` contains an interface with method `handle(String requestId)`; module `impl` contains an implementation declaring `handle(String id)`. Only `impl` enables the flag. Will a framework reflecting `api`'s method be guaranteed to see `requestId`?

**Answer:** No. You must check whether `api`'s classes were compiled/packaged with metadata. Implementation names do not transfer automatically to interface methods.

## 13. Self-check questions

**Does `-parameters` affect binary method signatures?** It adds name metadata; parameter names do not become part of a Java method's JVM descriptor.

**Can you read the names of every local variable with `Parameter.getName()`?** No; only formal parameters of reflected methods/constructors are exposed.

**Is `arg0` always a JVM-synthesized name?** No; check `isNamePresent()`. A programmer might actually choose the name `arg0`.

**Does enabling the flag on a project modify external library JARs?** No; check how those classes/JARs were compiled and packaged.

**Can parameter names become part of a framework contract?** Yes. Even though they do not govern binary signatures, frameworks may use them as binding key names.

**Is using `-parameters` enough to guarantee valid inputs?** No. It is only name metadata, while validation, types, defaults, annotations, and input data belong to other mechanisms.

## 14. Key takeaways

`javac -parameters` preserves **formal parameter names in `MethodParameters`** so Java Reflection can read them at runtime. Compare `Parameter.getName()` alongside `Parameter.isNamePresent()`, distinguish it from `-g` and local variables, and inspect the final artifact in the right module. Whenever a framework relies on parameter names to map inputs, the presence and stability of this metadata become items requiring verification during build and deployment pipelines.
