# Packaging, registering, and testing an annotation processor from a consuming project

An annotation processor does not run automatically just because its class has been compiled. For another project to use it, you must **package the processor with appropriate dependencies**, **register it so the compiler discovers it or select it explicitly by name**, **configure the processor path and compile classpath properly**, and then **verify both generated sources and compiled classes/runtime outputs**. This is an essential lifecycle when turning a processor into a reusable tool.

This lesson illustrates everything completely with **Java 17+**, without needing external frameworks: a processor-providing project is packaged into a JAR, an application project places an annotation on a class, the processor generates additional Java source, `javac` compiles the generated source, and the application calls the generated class. Afterward, we examine the service registration mechanism, selecting processors via `-processor`, the effects of options, and build system integration.

## 1. Architectural picture: two roles and three artifact sets

~~~text
PROCESSOR PROJECT (built first)
  Annotation API: @GenerateGreeting
  Processor implementation: GreetingProcessor implements Processor
  META-INF/services/javax.annotation.processing.Processor
                   |
                   v
       greeting-processor.jar
                   |
             +-----+-------------------+
             |                         |
             v                         v
CONSUMER PROJECT (javac)    Compiler locates/loads processor
  @GenerateGreeting         via -processorpath and SPI
  Trigger.java                          |
  App.java                              v
             +----------> processing rounds
                             |
               Filer.createSourceFile(...)
                             |
                   -s build/generated/
                     GeneratedHello.java
                             |
                             v
                   compile generated source
                             |
                   -d build/classes/
          App.class, Trigger.class, GeneratedHello.class
                             |
                             v
                     java -cp build/classes ...
~~~

Three groups must be distinguished:

1. **Annotation declaration**: the Java type representing the annotation, so *consumer* source code can use `@GenerateGreeting`. The consumer needs to see this type on the compile classpath or module path.
2. **Processor implementation**: code running **during compilation**, operating on the compiler's elements/types model and producing outputs. The compiler must be able to load the processor from the appropriate *processor path* or *processor module path*.
3. **Generated code and runtime classes**: sources generated by the processor can be compiled by the compiler into classes; the running application needs the generated classes and appropriate runtime dependencies, **not necessarily the processor implementation** once compilation finishes.

The compact example below packages the annotation API and processor in **the same JAR** for easy testing. In real products, splitting into two artifacts is usually better: a lightweight annotation API artifact for consumers to compile against, and a processor artifact for build tools to use during annotation processing. This is a design choice, not a mandatory Java rule.

## 2. What contract must a processor fulfill?

An annotation processor is written with the `javax.annotation.processing` API, typically extending `AbstractProcessor` and overriding `process(...)`.

Key components:

| Component | Role |
| --- | --- |
| `javax.annotation.processing.Processor` | Processor contract invoked by the compiler |
| `AbstractProcessor` | Base class supporting lifecycle/metadata declarations |
| `@SupportedAnnotationTypes` | Names the annotations the processor handles |
| `@SupportedSourceVersion` | Declares the source version the processor supports |
| `process(Set<? extends TypeElement>, RoundEnvironment)` | Processes annotations and elements per *round* |
| `processingEnv.getFiler()` | Creates generated sources, classes, or resources via compiler-managed mechanism |
| `processingEnv.getMessager()` | Emits diagnostics (NOTE, WARNING, ERROR) to the compiler |
| `RoundEnvironment.processingOver()` | Indicates the final round when processing is about to finish |

**Do not directly call the `process(...)` method from an application at runtime**. Consumers do not turn a processor into a business object to run manually; the compiler/build system sets up `ProcessingEnvironment` and invokes the processor during compilation.

**Finding the processor does not mean the processor generates code.** The processor must support the matching annotation, have elements to process, encounter no errors during processing, and actually call an output-creating method like `Filer.createSourceFile(...)`.

## 3. Sample project: two separate source structures

Create the following directory tree. Compile commands are run from the root directory `sample`, containing two branches `processor` and `consumer`:

~~~text
sample/
├── processor/
│   ├── src/
│   │   └── com/acme/
│   │       ├── annotations/
│   │       │   └── GenerateGreeting.java
│   │       └── processor/
│   │           └── GreetingProcessor.java
│   └── resources/
│       └── META-INF/
│           └── services/
│               └── javax.annotation.processing.Processor
├── consumer/
│   └── src/
│       └── com/acme/app/
│           ├── Trigger.java
│           └── App.java
└── build/
    ├── processor-classes/
    ├── greeting-processor.jar
    ├── generated/
    └── classes/
~~~

The `build` directory will be created when running commands. **Do not mistakenly place the service descriptor in `processor/src/META-INF/...` if the packaging step only copies compiled classes**: it is a *resource* that must be placed into the JAR at the exact right location. In the example, the resource lives in `processor/resources` and is added to the JAR in a separate step.

### 3.1. Annotation API

**File `processor/src/com/acme/annotations/GenerateGreeting.java`:**

~~~java
package com.acme.annotations;

import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

@Retention(RetentionPolicy.SOURCE)
@Target(ElementType.TYPE)
public @interface GenerateGreeting {
}
~~~

`RetentionPolicy.SOURCE` fits because the annotation only needs to be present in source for the compiler/processor to handle; the application does not need to read this annotation via reflection at runtime. This is **not** a mandatory condition for every processor: some annotations need `CLASS` or `RUNTIME` for other reasons.

### 3.2. Processor generating a fixed class for the demo

**File `processor/src/com/acme/processor/GreetingProcessor.java`:**

~~~java
package com.acme.processor;

import com.acme.annotations.GenerateGreeting;
import java.io.IOException;
import java.io.Writer;
import java.util.Set;
import javax.annotation.processing.AbstractProcessor;
import javax.annotation.processing.RoundEnvironment;
import javax.annotation.processing.SupportedAnnotationTypes;
import javax.annotation.processing.SupportedSourceVersion;
import javax.lang.model.SourceVersion;
import javax.lang.model.element.TypeElement;

@SupportedAnnotationTypes("com.acme.annotations.GenerateGreeting")
@SupportedSourceVersion(SourceVersion.RELEASE_17)
public final class GreetingProcessor extends AbstractProcessor {
    private boolean generated;

    @Override
    public boolean process(Set<? extends TypeElement> annotations,
                           RoundEnvironment round) {
        if (generated
                || round.processingOver()
                || round.getElementsAnnotatedWith(GenerateGreeting.class).isEmpty()) {
            return true;
        }

        generated = true;
        try {
            var file = processingEnv.getFiler()
                    .createSourceFile("com.acme.generated.GeneratedHello");

            try (Writer writer = file.openWriter()) {
                writer.write("package com.acme.generated;\n"
                        + "public final class GeneratedHello {\n"
                        + "  private GeneratedHello() {}\n"
                        + "  public static String message() {\n"
                        + "    return \"hello-from-processor\";\n"
                        + "  }\n"
                        + "}\n");
            }
        } catch (IOException ex) {
            throw new IllegalStateException("Source generation failed", ex);
        }
        return true;
    }
}
~~~

Detailed explanation:

- `@SupportedAnnotationTypes` must point to the exact **fully qualified name** of the annotation; do not substitute the processor name, module name, or generated class name.
- `@SupportedSourceVersion(SourceVersion.RELEASE_17)` informs the compiler that the processor declares support for source level 17. It does not **itself** set the consumer's target release; the command `javac --release 17` does that.
- `getElementsAnnotatedWith(GenerateGreeting.class)` checks whether the current round has classes marked with the annotation. If none exist, the processor emits no file.
- `generated` avoids calling `createSourceFile` a second time in subsequent rounds; creating a duplicate name causes `Filer` to typically throw `FilerException`.
- `createSourceFile("com.acme.generated.GeneratedHello")` takes the **canonical name** of the new class; `Filer` maps it to `com/acme/generated/GeneratedHello.java` in the source output location.
- `openWriter()` writes **valid Java source content**, including package and class; once the writer is closed, the compiler can proceed to process that source.
- `return true` indicates the processor *claims* the annotations it handled; in a multi-processor project, the claim decision affects which processors are still invited to process corresponding annotations in the round.
- This is an **illustrative processor generating a single fixed class per compilation**. A production tool typically generates per annotated type, constructs non-colliding deterministic names, and passes *originating elements* to `Filer`.

Do not use `FileWriter` directly into a guessed directory inside a processor: creating sources via `Filer` helps the compiler track generated files and process them in subsequent rounds.

## 4. Registering the processor via Java Service Provider Interface (SPI)

When `-processor <class>` is not specified, `javac` can discover processors through a **service provider configuration file** located in a JAR on the processor search path.

**Exact entry name inside the JAR:**

~~~text
META-INF/services/javax.annotation.processing.Processor
~~~

This is a **text file without a `.txt` extension**, not a decorative directory, nor a file named `META-INF/services/com.acme.processor.GreetingProcessor`.

**Contents of file `processor/resources/META-INF/services/javax.annotation.processing.Processor`:**

~~~text
com.acme.processor.GreetingProcessor
~~~

One line is the fully qualified processor class name. Multiple providers can be registered across multiple lines, and service configurations can use comments per ServiceLoader syntax. For this example, a single uncommented line is clearest.

Important requirements:

1. The service file must reside at the **exact entry path in the JAR** used by the compiler to discover processors.
2. The contents must point to a real class, in the right package, loadable from the processor path with required dependencies.
3. The processor class must implement `Processor` (here via `AbstractProcessor`), with a constructor suitable for service provider instantiation; for example, an implicit public no-argument constructor.
4. Avoid packaging only `GreetingProcessor.class` while forgetting `GenerateGreeting.class`: the implementation references the annotation class when running.
5. The service file name does not change based on annotation name or application name. The SPI interface remains `javax.annotation.processing.Processor`.

A missing service file usually prevents **auto-discovery from finding the processor**. Conversely, using `-processor com.acme.processor.GreetingProcessor` can run the processor even **without a service descriptor**, because it is an explicit selection bypassing default discovery. The two mechanisms must be tested separately.

## 5. Packaging a JAR from the processor project

### 5.1. Create output directories

In **Bash or a Linux/macOS shell**:

~~~bash
mkdir -p build/processor-classes build/generated build/classes
~~~

In **PowerShell**:

~~~powershell
New-Item -ItemType Directory -Force -Path build/processor-classes,build/generated,build/classes
~~~

### 5.2. Compile the annotation and implementation

From `sample/`:

~~~bash
javac --release 17 -d build/processor-classes processor/src/com/acme/annotations/GenerateGreeting.java processor/src/com/acme/processor/GreetingProcessor.java
~~~

Success normally prints no stdout. Class output:

~~~text
build/processor-classes/
└── com/acme/
    ├── annotations/GenerateGreeting.class
    └── processor/GreetingProcessor.class
~~~

**Processing is not run on any consumer yet** at this step. Only the processor class and annotation class are built. Because the service descriptor file sits separately in `processor/resources`, it is not yet inside `build/processor-classes` after running `javac`.

### 5.3. Package the JAR with both classes and resources

~~~bash
jar --create --file build/greeting-processor.jar -C build/processor-classes . -C processor/resources .
~~~

Explanation: `-C build/processor-classes .` places the entire class output contents at the **JAR root**; `-C processor/resources .` places resources at the **JAR root**. Thus the service descriptor is stored precisely at `META-INF/services/...` rather than nested under `processor/resources` inside the JAR.

Check the entry listing:

~~~bash
jar --list --file build/greeting-processor.jar
~~~

The listing must show the key entries:

~~~text
com/acme/annotations/GenerateGreeting.class
com/acme/processor/GreetingProcessor.class
META-INF/services/javax.annotation.processing.Processor
~~~

Entries such as `META-INF/`, `META-INF/MANIFEST.MF`, and intermediate directories may also appear; display order does not matter.

**Verify the service file content** by inspecting the entry from the JAR with an archive viewer, or extracting to a separate QA directory and reading the file. Merely seeing the entry name does not prove the class name inside is spelled accurately; confirm the content `com.acme.processor.GreetingProcessor`.

### 5.4. Packaging errors to guard against

- **Wrong root:** JAR contains `processor/resources/META-INF/services/...` instead of `META-INF/services/...`, preventing SPI recognition.
- **Wrong class name:** service file lists `GreetingProcessor` instead of the full name.
- **Missing dependencies:** processor class is present, yet at load time an auxiliary class is missing, causing failures in service loading or processor execution.
- **Adding service descriptor to compile output before compiling the processor:** the compiler may try loading a provider **not yet compiled**, causing a service configuration error. Building processor classes first and packaging resources into the JAR afterward keeps a clean separation.
- **JAR missing the annotation API:** if a demo uses a single shared JAR yet omits `GenerateGreeting.class`, the consumer compiler cannot recognize the annotation.
- **Using the wrong JAR version:** the pipeline might execute an old processor no longer matching current annotations/sources.

## 6. Consumer project: referencing the generated class

Create two new Java files:

**File `consumer/src/com/acme/app/Trigger.java`:**

~~~java
package com.acme.app;

import com.acme.annotations.GenerateGreeting;

@GenerateGreeting
public final class Trigger {
}
~~~

**File `consumer/src/com/acme/app/App.java`:**

~~~java
package com.acme.app;

import com.acme.generated.GeneratedHello;

public final class App {
    public static void main(String[] args) {
        System.out.println(GeneratedHello.message());
    }
}
~~~

At the time of writing these two files, `GeneratedHello.java` or `GeneratedHello.class` **does not yet exist** in the consumer source tree. The processor will generate the missing source when invoked.

Dependency diagram:

~~~text
Consumer source:
  Trigger.java --> annotation API GenerateGreeting
  App.java     --> generated type GeneratedHello

Compile:
  annotation API --> compile classpath (visible to consumer)
  processor implementation --> processor path (javac loads processor)
  processor output --> generated source root (-s)
  java bytecode --> classes output (-d)

Run:
  App.class + GeneratedHello.class --> runtime classpath
  processor JAR is usually not needed at runtime
~~~

## 7. Most important test: auto-discovering the processor from the JAR

Run from root `sample/` once `build/greeting-processor.jar` exists:

~~~bash
javac --release 17 -cp build/greeting-processor.jar -processorpath build/greeting-processor.jar -s build/generated -d build/classes consumer/src/com/acme/app/Trigger.java consumer/src/com/acme/app/App.java
~~~

This is an invocation **without `-processor`**. It uses the service descriptor inside the JAR to locate `GreetingProcessor`.

Each option has a specific role:

| Option | Meaning in the demo |
| --- | --- |
| `--release 17` | Sets Java 17 source/API/bytecode level |
| `-cp build/greeting-processor.jar` | Allows consumer source to see `com.acme.annotations.GenerateGreeting` |
| `-processorpath build/greeting-processor.jar` | Specifies where `javac` locates the implementation and service descriptor |
| `-s build/generated` | Where `Filer.createSourceFile` places `GeneratedHello.java` |
| `-d build/classes` | Where `javac` places class files of both handwritten and generated sources |
| `consumer/src/...` | The input source files to compile |

Supplying `-processorpath` is **explicit annotation processing configuration**. It also avoids relying on the compiler accidentally finding the processor on the compile classpath. Starting from JDK 23, `javac` no longer automatically enables annotation processing solely because a processor is detected on the classpath **if no annotation processing configuration option is chosen**; therefore builds should proactively supply a processor path or processor names, or `-proc:full` on supporting JDKs. The example uses an explicit processor path and is compatible with Java 17+.

**Result after successful compilation:**

~~~text
build/
├── generated/
│   └── com/acme/generated/GeneratedHello.java
└── classes/
    ├── com/acme/app/
    │   ├── Trigger.class
    │   └── App.class
    └── com/acme/generated/GeneratedHello.class
~~~

The generated source contains a class with package `com.acme.generated` and a static method `message()` returning `"hello-from-processor"`. `javac` processes the new source through annotation processing rounds and compiles it in the same normal compilation.

### Running the consumer

~~~bash
java -cp build/classes com.acme.app.App
~~~

**Exact stdout:**

~~~text
hello-from-processor
~~~

At runtime, a classpath containing `App.class` and `GeneratedHello.class` suffices in the demo. `SOURCE` annotation retention and the processor serving only compile time mean the processor JAR **is not needed on the runtime classpath**. This can differ for real processors whose generated sources depend on a separate runtime library.

**Evidence that auto-discovery succeeded**: `-processor` was **not** specified in the compile command; generated source appeared; classes compiled; and the app ran with the expected output. When needing to view which processor name was invoked, add `-XprintProcessorInfo` for diagnostics.

## 8. Selecting the processor explicitly with `-processor`

If you want to test the implementation **without depending on service-discovery**, explicitly specify the full processor class name:

~~~bash
javac --release 17 -cp build/greeting-processor.jar -processorpath build/greeting-processor.jar -processor com.acme.processor.GreetingProcessor -s build/explicit-generated -d build/explicit-classes consumer/src/com/acme/app/Trigger.java consumer/src/com/acme/app/App.java
~~~

Create the two new output roots `build/explicit-generated` and `build/explicit-classes` beforehand if they do not exist; do not mix with outputs from the prior compile run.

Run:

~~~bash
java -cp build/explicit-classes com.acme.app.App
~~~

Stdout remains:

~~~text
hello-from-processor
~~~

**Two test forms uncover two different groups of errors:**

- **Auto-discovery** uses `META-INF/services/javax.annotation.processing.Processor`. If the processor class runs with `-processor` yet does not run in auto mode, inspect the service file path/content and processor path.
- **Explicit selection** uses `-processor`. If even the explicit form fails, inspect classes/dependencies, processor code, annotation matching, exceptions, and output paths.

`-processor` **is not synonymous** with `-processorpath`: one option sets **the name of the selected implementation**, while the other sets **where to look for implementations**.

## 9. Trying `-proc:only` and `-proc:none` modes

### `-proc:only`: run annotation processing, skip normal class compilation

~~~bash
javac --release 17 -cp build/greeting-processor.jar -processorpath build/greeting-processor.jar -proc:only -s build/only-generated -d build/only-classes consumer/src/com/acme/app/Trigger.java consumer/src/com/acme/app/App.java
~~~

Use clean output roots `build/only-generated` and `build/only-classes` for comparison. Result of the demo:

~~~text
build/only-generated/
└── com/acme/generated/GeneratedHello.java

build/only-classes/
    (no application .class files present)
~~~

`-proc:only` runs annotation processing **without proceeding to normal class compilation**. This mode is useful when needing to inspect generated code before compiling it in a separate step.

### `-proc:none`: compile without running annotation processors

With a fresh output and without supplying the generated type on the classpath, the command:

~~~bash
javac --release 17 -proc:none -cp build/greeting-processor.jar -d build/no-processing-classes consumer/src/com/acme/app/Trigger.java consumer/src/com/acme/app/App.java
~~~

will **intentionally fail** because `App.java` imports `com.acme.generated.GeneratedHello`, yet the processor did not generate that class. Compiler errors may state package `com.acme.generated` does not exist or cannot find symbol; diagnostic text varies by JDK.

This is a useful test to determine whether the consumer **genuinely depends** on generated code. When testing, avoid accidentally leaving an old `GeneratedHello.class` on the compile classpath, as it can mask the fact that the processor did not run.

### If wanting to compile generated source separately

After `-proc:only`, an explicit compile can be run, **disabling processors** to avoid duplicate generation:

~~~bash
javac --release 17 -proc:none -cp build/greeting-processor.jar -d build/manual-classes consumer/src/com/acme/app/Trigger.java consumer/src/com/acme/app/App.java build/only-generated/com/acme/generated/GeneratedHello.java
~~~

Now `App.java` compiles because the generated source is listed directly. This is a **build-orchestrated two-step pipeline**, distinct from the single-pass `javac` pipeline in Section 7. In a normal single-pass pipeline, there is no need to manually recompile `GeneratedHello.java`.

## 10. Diagnosing processor discovery and processing rounds

Add observation options:

~~~bash
javac --release 17 -cp build/greeting-processor.jar -processorpath build/greeting-processor.jar -XprintRounds -XprintProcessorInfo -s build/debug-generated -d build/debug-classes consumer/src/com/acme/app/Trigger.java consumer/src/com/acme/app/App.java
~~~

With fresh/clean output roots, the compiler can print about processing rounds:

- First round sees `@GenerateGreeting` on `Trigger`; processor is called and generates `GeneratedHello.java`.
- Next round has new source `GeneratedHello.java`, so an extra round can be observed.
- Final round has `processingOver() == true`; the processor in the example creates no further files.

**Do not include `javac` diagnostics in the application's stdout table**. `-XprintRounds` and `-XprintProcessorInfo` produce compiler-dependent output, typically over diagnostic streams, and formatting can change. When automating checks, prefer verifying concrete artifacts and program outputs rather than comparing entire logs character by character.

### Automatable test checklist

| Check | Expected observation |
| --- | --- |
| JAR has service descriptor | `jar --list --file ...` shows exact `META-INF/services/javax.annotation.processing.Processor` |
| Service file points to exact FQCN | Content is `com.acme.processor.GreetingProcessor` |
| Auto-discovery | Even without `-processor`, `GeneratedHello.java` is created |
| Source creation | `build/generated/com/acme/generated/GeneratedHello.java` exists |
| Class creation | `build/classes/com/acme/generated/GeneratedHello.class` exists |
| Running application | Exact stdout `hello-from-processor` |
| Explicit selection | `-processor com.acme.processor.GreetingProcessor` yields the same result |
| Processing only | `-proc:only` creates Java source, does not create app classes |
| Processor disabled | `-proc:none` on clean output leaves consumer missing generated type |
| Editing annotation/processor scenario | Clean build retains no stale classes/sources from previous version |

You can use `javap -p build/classes/com/acme/generated/GeneratedHello.class` to verify the method exists in bytecode. This checks class output, not just generated source.

## 11. Bringing the JAR into a real project: classpath, Gradle, and Maven

### 11.1. Processor path is not compile classpath

In the demo, the same JAR appears on **both** paths because the JAR contains both the annotation API and the processor:

~~~text
-cp build/greeting-processor.jar
-processorpath build/greeting-processor.jar
~~~

The two options serve two distinct purposes:

- **Compile classpath** lets the consumer read classes/annotations that its source directly references.
- **Processor path** lets the compiler load the processor implementation and processor dependencies, as well as locate service providers.

In a real codebase, consider separating:

~~~text
greeting-annotations.jar   -> compileOnly / compile classpath
greeting-processor.jar     -> annotationProcessor / processor path
generated-runtime.jar      -> add only if generated classes truly require this runtime API
~~~

If the processor implementation uses other dependencies such as a code-generation library, those dependencies must be provided to the processor classloader. If **generated** source imports a runtime API, consumer compile/runtime must also have that API in the appropriate place. Do not mix up the two dependency sets.

### 11.2. Gradle Java plugin

An illustrative configuration once the two artifacts are published:

~~~kotlin
// Consumer's build.gradle.kts - illustrating dependency coordinates
plugins {
    java
}

dependencies {
    compileOnly("com.acme:greeting-annotations:1.0.0")
    annotationProcessor("com.acme:greeting-processor:1.0.0")
}
~~~

The coordinates above are **hypothetical examples**; they work only after you actually publish corresponding artifacts to a configured repository. `annotationProcessor` tells Gradle the dependency is for compile-time processing, not runtime. `compileOnly` can fit a SOURCE-retained annotation if runtime does not need it; if code/runtime needs the annotation API, choose a more suitable scope.

Gradle normally manages the generated-source root and classes root in the build directory. No need to manually apply `-s`/`-d` if the plugin is properly configured; when debugging, inspect compiler arguments and `compileJava` task outputs.

For the **single unpublished JAR** demo, a Gradle consumer can use a file dependency after copying the JAR to the `libs` directory:

~~~kotlin
dependencies {
    compileOnly(files("libs/greeting-processor.jar"))
    annotationProcessor(files("libs/greeting-processor.jar"))
}
~~~

This is a local file configuration example; the file `libs/greeting-processor.jar` must exist. Do not copy both approaches simultaneously unless genuinely needed.

### 11.3. Maven Compiler Plugin

With the separated artifact structure, an illustrative configuration:

~~~xml
<dependencies>
  <dependency>
    <groupId>com.acme</groupId>
    <artifactId>greeting-annotations</artifactId>
    <version>1.0.0</version>
    <scope>provided</scope>
  </dependency>
</dependencies>

<build>
  <plugins>
    <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-compiler-plugin</artifactId>
      <configuration>
        <release>17</release>
        <annotationProcessorPaths>
          <path>
            <groupId>com.acme</groupId>
            <artifactId>greeting-processor</artifactId>
            <version>1.0.0</version>
          </path>
        </annotationProcessorPaths>
      </configuration>
    </plugin>
  </plugins>
</build>
~~~

This is an **illustrative `pom.xml` snippet**, not a complete standalone POM. In real projects, use an appropriate plugin version, artifacts must exist in repositories, and the dependency graph must include every library the processor needs. With modern Maven/compiler plugins, processor dependency configuration can take a different form; the goal remains **separating compile dependencies and processor dependencies**.

Do not manually add the generated-source directory to compile source roots in the same task if the compiler/plugin already manages generated sources. Doing so can cause duplicate classes or generate sources multiple times.

## 12. Packaging processors for JPMS: do not confuse with classpath SPI

The example above uses **a JAR on the processor path**, so it registers via:

~~~text
META-INF/services/javax.annotation.processing.Processor
~~~

If deploying the processor as a **named module**, the module descriptor can declare a service provider:

~~~java
module com.acme.processor {
    requires java.compiler;
    provides javax.annotation.processing.Processor
        with com.acme.processor.GreetingProcessor;
}
~~~

This snippet is a **`module-info.java` illustration** for the modular processor approach. Appropriate exports/requires must be added if the annotation API and processor reside in different modules; you cannot simply paste the descriptor into the sample project above and expect it to compile automatically.

When using module-based processor discovery, the relevant option is `--processor-module-path` instead of `-processorpath`. For unmodularized classpath JARs, use the `META-INF/services` service file as in the main example. Understand clearly whether you are using **classpath-service registration** or **module-provides registration**; they have different resolution and packaging rules.

## 13. Notes on differences across JDK 17, JDK 21, and JDK 23+

On older JDKs, `javac` could perform annotation processing implicitly if a processor service descriptor appeared on the classpath. Starting with **JDK 23**, annotation processing is disabled by default when **no explicit configuration exists** for processing. This change helps curb unintended processor execution.

To make builds easy to verify and reduce risks:

- Place processor dependencies on a dedicated processor path/module path; do not rely on a JAR accidentally sitting on the runtime/compile classpath.
- Use `-processor FQCN` when wanting to verify an implementation explicitly, **or** use a service descriptor with `-processorpath` to verify discovery.
- `-proc:full` requests processing followed by compilation on JDKs supporting the option. This option was introduced in JDK 21 and backported to certain update releases such as JDK 17.0.11; do not assume every older JDK 17 build understands it. The main example avoids needing this option via an explicit processor path.
- `-proc:only` still serves generated-source inspection; `-proc:none` explicitly disables processing.
- Run both `javac -version` and `java -version` when diagnosing environments: the compiler may not match the runtime version used for deployment.

At build time, **an annotation processor is executable code** capable of reading resources and creating files with the permissions of the compilation process. Use processor artifacts only from trusted sources, manage versions, and inspect the dependency supply chain; do not treat them as harmless “passive annotations”.

## 14. Common mistakes when packaging and using processors

| Symptom | Common cause | How to check |
| --- | --- | --- |
| Compile does not see generated class | Processor did not run, missing annotation, or source generation failed | Check processor path, service file, `-XprintProcessorInfo`, `-s` |
| `Annotation processor ... not found` | Wrong class name or missing implementation/dependencies | Check `-processor`, `jar --list`, processor path |
| `Bad service configuration file` / `Provider ... not found` | Wrong FQCN in service entry, class not public/loadable, or missing dependency | Verify service file content and JAR |
| Runs with `-processor`, auto-discovery does not run | Missing/wrong `META-INF/services` or processor search path | Use two separate test modes, inspect JAR entries |
| Consumer does not recognize `@GenerateGreeting` | Annotation API missing from compile classpath/module path | Add appropriate annotation API artifact |
| `FilerException: Attempt to recreate a file...` | Processor creates same file across rounds or collides with existing source | Prevent duplicate creation, choose stable output names, clean build |
| Generated source exists yet class is missing | `-proc:only`, compilation failed, or wrong `-d` | Check `-proc`, compiler diagnostics, and class output |
| Class exists yet app does not run | Runtime classpath/module path missing generated class or runtime API | Check class directory and deployment dependencies |
| Java source generated in wrong package | Wrong canonical name passed to `Filer.createSourceFile` or mismatched package written | Check both file creation name and `package` in generated source |
| Processor is called yet emits no file | `getElementsAnnotatedWith(...)` empty; different annotation type; `generated` guard blocks; wrong processor picked | Check annotation names/rounds and generation conditions |
| Works on one JDK version, fails on another | Default discovery changes; processor source-version support; API/compiler options | Configure processing explicitly and test JDK matrix |
| Generated class from prior run masks errors | Stale files on compile classpath or uncleaned outputs | Run with fresh output roots and lock search paths |
| Build succeeds yet packaged JAR lacks generated class | Packaged wrong directory or task ordering | Inspect application artifact and `jar --list` |

### Effective ordered debugging approach

1. **Inspect the processor artifact:** Does the JAR exist? Is the service descriptor at the right path? Are the implementation class and annotation/dependencies included?
2. **Inspect compiler arguments:** Does the compile classpath have the annotation API? Does the processor path have the implementation? Does the JDK enable processing?
3. **Inspect rounds:** Was the processor called? Did it see `@GenerateGreeting`? Were there any exceptions/diagnostics?
4. **Inspect source output:** Does `GeneratedHello.java` exist in the `-s` directory with the right package?
5. **Inspect bytecode:** Does `GeneratedHello.class` exist in `-d`? Did App.class compile cleanly?
6. **Inspect runtime/deployment:** Are generated classes and dependencies actually on the runtime classpath/module path?
7. **Inspect reproducibility:** From clean outputs, does compiling recreate artifacts matching expectations, or did it only work due to stale files?

Do not fix discovery issues by **dumping every JAR indiscriminately onto the runtime classpath**. Locate the exact compiler/processor/runtime boundaries.

## 15. Serious processor testing strategies

The runnable example above is a *smoke test*, whereas reusable processors need additional test groups:

### 15.1. Positive compilation tests

Given one or more validly annotated declarations, verify:

- Processor executes without `Diagnostic.Kind.ERROR`.
- Generated files have the right canonical/package names.
- Generated sources are syntactically valid, compile cleanly, and runtime outputs are correct when applicable.
- With multiple annotation targets, generated names do not collide; files are created once per compilation.
- Generated code conforms to `--release` and does not call APIs newer than the target.

### 15.2. Negative compilation tests

Intentionally feed invalid inputs and assert **intentional compiler diagnostics**, not merely exception stack traces. For example, a processor supports only public classes yet a user marks an interface: use `Messager.printMessage(Diagnostic.Kind.ERROR, "...", element)` to pinpoint why it is wrong.

Error cases to test: missing required annotations, annotations used on unsupported element kinds, generated type name already exists, incompatible compiler API level, processor path missing dependency, and broken generated source.

### 15.3. Service-discovery integration tests

Package the JAR **identical to the release build**, then compile a consumer project using **that exact JAR**, **without `-processor`**, to verify SPI. Next, run explicit selection with `-processor` to separate packaging/discovery errors from implementation errors.

A test that only directly invokes the processor class or instantiates it **without running actual `javac`** is insufficient to prove JAR service registration works.

### 15.4. Cross-version and clean builds

Using the minimum published JDK and newer target JDKs, run from clean outputs first. Verify both `-s`/`-d` paths and check for regressions when upgrading the processor version. If using incremental compilation, verify removing an annotation deletes old artifacts per build policy, and task ordering does not consume stale generated sources.

## 16. Self-check questions

**1. Why does auto-discovery fail to run when only `GreetingProcessor.class` is in the JAR?**  
It may be missing the service descriptor at the right path or have an incorrect FQCN inside; a lone processor class does not guarantee compiler discovery.

**2. What is the path to the service file?**  
`META-INF/services/javax.annotation.processing.Processor` at the root of the JAR on the processor path (for classpath-service registration).

**3. There is a valid service file, yet the implementation class is absent from the processor path; what happens?**  
The compiler cannot load the provider and may report a service configuration error or fail to compile as expected.

**4. Why does the example use the same JAR in `-cp` and `-processorpath`?**  
The demo JAR combines the annotation API and processor. `-cp` serves consumer source, `-processorpath` lets the compiler load the processor. In practice, the two artifacts can be separated.

**5. If `-processor` is omitted and processing still runs, what has been verified?**  
The service discovery portion of the JAR has been verified, provided the compiler is configured to look for processors on the right processor path.

**6. Does `-proc:only` make the `App` program runnable immediately?**  
No. It only runs processing; a compile step is needed to emit class outputs.

**7. What is `-proc:none`?**  
Disables annotation processing. The consumer in the demo will fail to compile unless the generated type already comes from other source/bytecode.

**8. Should the processor implementation be deployed together with the application?**  
Usually not needed after generated sources are compiled, unless there is an independent runtime requirement; generated code may need its own runtime library.

**9. Why is a test suite that only selects the processor explicitly insufficient for release?**  
It skips testing the service descriptor/auto-discovery, which is an essential step if users expect automatic discovery.

**10. On a newer JDK, the processor fails to run when only adding the JAR to the classpath; what should be inspected?**  
Check the default annotation processing change starting in JDK 23; declare `-processorpath`, `-processor`, or `-proc:full` as appropriate, and confirm the JDK version.

## 17. Release checklist

- [ ] Annotation API and processor code compile for the exact supported Java release.
- [ ] Processor declares supported annotations/source version and produces no duplicate outputs.
- [ ] JAR contains processor class, required dependencies, and service descriptor with accurate FQCN.
- [ ] Service descriptor sits precisely at `META-INF/services/javax.annotation.processing.Processor`.
- [ ] Consumer sees the annotation API on the compile classpath/module path.
- [ ] Compiler loads the processor explicitly from processor path/module path; does not rely on implicit auto-processing.
- [ ] Automated integration test **without `-processor`** proves SPI works.
- [ ] Explicit `-processor` test separates discovery bugs from implementation bugs.
- [ ] Generated `.java` appears in `-s`; generated `.class` exists in `-d`.
- [ ] `-proc:only` and `-proc:none` are properly understood when splitting build pipelines.
- [ ] Consumer application actually runs with the appropriate classpath/module path and runtime dependencies.
- [ ] Clean build and target JDK version tests do not depend on stale artifacts.
- [ ] Processor is treated as an executable build dependency with controlled provenance, versioning, and security.
