# 11.9. Limitations of Java Source Code: Calling Bootstrap Directly and Inspecting Real `invokedynamic` Bytecode

Java has two concepts that sound very similar but are **not synonymous**:

1. **Calling a Java method named `bootstrap`**, manually creating a `CallSite`, obtaining a `MethodHandle` via `dynamicInvoker()`, and invoking it with `invokeExact()`.
2. **Executing an `invokedynamic` instruction in JVM bytecode**, where the JVM relies on the constant pool and the `BootstrapMethods` attribute of the class file to link the call site with a bootstrap method.

Only **the second case** is a *dynamic call site* of the `invokedynamic` opcode according to the Java Virtual Machine Specification (JVMS). `javac` has no Java source syntax that lets you directly specify a custom bootstrap method and emit an arbitrary `invokedynamic` opcode as when writing in an assembler. You **can** declare and call a Java method with a signature like a real bootstrap; however, that call alone does not make the JVM attach this method to the `BootstrapMethods` table.

This lesson proves the difference using **two standalone runnable Java 17+ programs**, then uses `javap -p -c -v` to inspect the bytecode directly. The expected results are:

- `ManualBootstrapOnly.class`: has `invokestatic ... bootstrap`, `CallSite.dynamicInvoker`, and `MethodHandle.invokeExact`; **no `invokedynamic` opcode** and **no `BootstrapMethods` attribute**.
- `CompilerIndyDemo.class`: has **two real `invokedynamic` opcodes**, generated by `javac` for a method reference and runtime string concatenation; the `BootstrapMethods` table points to **`LambdaMetafactory.metafactory`** and **`StringConcatFactory.makeConcatWithConstants`**, **not** to the `ManualBootstrapOnly.bootstrap` method.

This is the fundamental difference between **writing code that calls a bootstrap manually** and **producing a class file containing a dynamic call site managed by the JVM**.

## 1. Three Layers to Separate: Java Source, Bytecode, and JVM Linkage

Imagine the process in three layers:

```text
Layer 1: Java source code
    |
    | javac compiles
    v
Layer 2: class file (instructions + constant pool + attributes)
    |  - invokestatic, invokevirtual, invokeinterface, ...
    |  - invokedynamic if the compiler chooses to emit it
    |  - CONSTANT_InvokeDynamic + BootstrapMethods when there is a dynamic call site
    |
    | JVM loads, verifies, and links when needed
    v
Layer 3: runtime
    |  - for invokedynamic: JVM resolves the bootstrap specifier
    |  - invokes the bootstrap method handle to obtain a CallSite
    |  - uses the CallSite's target for the dynamic call
    v
Return value or exception
```

A method named `bootstrap` at **the source layer** is just a Java method. For it to become *the bootstrap method of an `invokedynamic` instruction*, **the class file layer** must have a `CONSTANT_InvokeDynamic` referencing the corresponding bootstrap entry, and the instruction must point to that symbolic reference.

Both situations can use `MethodHandle` and `CallSite`, but the linking flows differ:

| Question | Calling bootstrap directly in Java | Real dynamic call site |
| --- | --- | --- |
| Who calls bootstrap? | Java code itself calls the method like any other method | The JVM invokes the bootstrap method handle when linking the instruction |
| Bytecode instruction at the bootstrap call point | Usually `invokestatic` if it is a static method | An **`invokedynamic` instruction** pointing into the constant pool |
| Who provides `Lookup`, name, `MethodType`? | Java code creates/passes them manually | The JVM obtains caller info, name, and descriptor from the call site specifier |
| How is `CallSite` used? | Code receives the object and manually calls `getTarget()` or `dynamicInvoker()` | The JVM links the `CallSite` with the dynamic call site |
| Is the `BootstrapMethods` attribute required? | **No**, just for calling a helper | **Yes**, if the class file contains `CONSTANT_InvokeDynamic` |
| Is it linked per opcode occurrence? | No; there are only normal Java calls | Yes, the JVM caches the linkage result for the dynamic call site |
| Can plain Java source alone specify a custom opcode? | No | Requires a bytecode compiler/generator/transformer to create the class file structure |

This explains why a program printing `"bootstrap-called"` still **does not prove** there is an `invokedynamic`. The log line proves the Java method ran, not that the JVM invoked it itself while processing an opcode.

## 2. `invokedynamic` Is an Instruction, Not Regular Java Syntax

The JVM has several method invocation opcodes, among which:

| Instruction | Typical meaning | Characteristics |
| --- | --- | --- |
| `invokestatic` | Calls a static method | Mainly based on class and method reference |
| `invokevirtual` | Calls a virtual instance method, or the opcode for signature-polymorphic calls to `MethodHandle.invoke`/`invokeExact` | Does not automatically turn into `invokedynamic` because the callee is dynamic |
| `invokeinterface` | Calls a method dispatched via an interface | Still different from `invokedynamic` |
| `invokespecial` | Constructors, certain private/super method calls | JVM-specific rules |
| **`invokedynamic`** | Calls through a dynamically computed call site that is bootstrapped | Linked according to the bootstrap specifier in the class file |

The `MethodHandle.invokeExact` symbol sounds "dynamic", and in fact the JVM has a special mechanism for signature-polymorphic method invocation. However, **the opcode at an `invokeExact` call is still `invokevirtual`**. That is an important reason to look at the bytecode rather than guessing from Java API names.

In Java code, many high-level constructs **can** lead to `invokedynamic` bytecode at the compiler's choice, for example:

- Lambda expressions or method references, typically linked by `javac` via `LambdaMetafactory`.
- String concatenation with runtime data, typically using `StringConcatFactory` in modern `javac` versions.
- Certain compiler-generated methods for `record`, which may go through `ObjectMethods.bootstrap`.

**Not every expression that looks "dynamic" emits `invokedynamic`.** A normal interface call uses `invokeinterface`; a Java method named `bootstrap` can still be just `invokestatic`; a constant string concatenation such as `"Hello, " + "Java"` can be folded into a constant by the compiler and **does not need** a dynamic concat site.

The bytecode shape is a detail of the actual compiler and class file. The `--release 17` flag specifies the API/target release and corresponding class file, but **does not force every compiler version to choose the exact same code generation strategy** in all situations.

## 3. Example A: Calling Bootstrap Manually, but the Class Has No `invokedynamic`

Create the file **`ManualBootstrapOnly.java`**. The program intentionally avoids lambdas, method references, and runtime `+` string concatenation to provide an easily observable "negative" piece of evidence.

```java
import java.lang.invoke.CallSite;
import java.lang.invoke.ConstantCallSite;
import java.lang.invoke.MethodHandle;
import java.lang.invoke.MethodHandles;
import java.lang.invoke.MethodType;

public final class ManualBootstrapOnly {
    public static String decorate(String text) {
        return "[".concat(text).concat("]");
    }

    public static CallSite bootstrap(
            MethodHandles.Lookup caller, String name, MethodType type)
            throws NoSuchMethodException, IllegalAccessException {
        System.out.println("manual-bootstrap-entered");
        MethodHandle target = caller.findStatic(
                ManualBootstrapOnly.class, "decorate",
                MethodType.methodType(String.class, String.class));
        return new ConstantCallSite(target.asType(type));
    }

    public static void main(String[] args) throws Throwable {
        MethodType signature =
                MethodType.methodType(String.class, String.class);
        CallSite site = bootstrap(
                MethodHandles.lookup(), "apply", signature);
        MethodHandle invoker = site.dynamicInvoker();
        String value = (String) invoker.invokeExact("Ada");
        System.out.printf("manual=%s%n", value);
    }
}
```

### 3.1. Why Does the `bootstrap` Method Look Valid?

It takes the three parameters commonly found in a bootstrap method for a dynamic call site:

```text
(MethodHandles.Lookup, String, MethodType) -> CallSite
```

For a real bootstrap, the JVM provides a `Lookup` bound to **the class containing the instruction**, the symbolic call site name, and the `MethodType` corresponding to the descriptor. If the class file declares additional static bootstrap arguments, the JVM also passes those values according to the bootstrap protocol.

In **Example A**, `main` passes them manually:

```java
bootstrap(MethodHandles.lookup(), "apply", signature)
```

`MethodHandles.lookup()` is called from code inside `ManualBootstrapOnly.main`, `"apply"` is just a string chosen by the author, and `signature` is also created via the Java API. No step requires the JVM to read a `CONSTANT_InvokeDynamic` to derive those values.

Inside the body of `bootstrap`:

1. `caller.findStatic(...)` finds a handle to `decorate(String)`.
2. `target.asType(type)` ensures the handle has the type requested by the caller, when the conversion is valid.
3. `new ConstantCallSite(...)` creates a `CallSite` whose target cannot be changed after initialization.
4. `main` obtains `site.dynamicInvoker()`, then invokes the handle like a normal Java object.

**Creating a `ConstantCallSite` does not automatically emit an `invokedynamic` opcode.** Likewise, `CallSite.dynamicInvoker()` is a Java API; it does not automatically register an entry in `BootstrapMethods`.

### 3.2. Execution Result

After compiling in section 5, run:

```bash
java ManualBootstrapOnly
```

Stdout:

```text
manual-bootstrap-entered
manual=[Ada]
```

This is the verified result on the program compiled with `javac --release 17`.

The line `manual-bootstrap-entered` appears because **`main` directly called the Java method `bootstrap`**, not because the runtime linked an `invokedynamic` opcode.

### 3.3. Why Intentionally Use `String.concat`?

The `decorate` method uses:

```java
return "[".concat(text).concat("]");
```

instead of:

```java
return "[" + text + "]";
```

If `+` is used with the variable `text`, modern `javac` may automatically emit `invokedynamic` for string concatenation. In that case, the manual class would have `invokedynamic` **due to string concatenation**, easily leading learners to mistake that opcode as related to the `bootstrap` helper. Writing it with `String.concat` keeps Example A focused on comparing **direct bootstrap call** and **real indy**.

Similarly, the example uses `System.out.printf("manual=%s%n", value)` instead of `"manual=" + value` to avoid creating an additional dynamic string-concat site in the class being inspected.

## 4. Example B: No Manual Bootstrap Call, but the Compiler Actually Emits `invokedynamic`

Create the second file **`CompilerIndyDemo.java`** in the same directory as the first file:

```java
public final class CompilerIndyDemo {
    @FunctionalInterface
    interface Task {
        String apply(String text);
    }

    public static void main(String[] args) {
        Task task = ManualBootstrapOnly::decorate;
        System.out.printf("reference=%s%n", task.apply("Bob"));

        String input = args.length == 0 ? "Java" : args[0];
        String message = "Hello, " + input;
        System.out.printf("concat=%s%n", message);
    }
}
```

There are only two constructs to note:

1. **Method reference** `ManualBootstrapOnly::decorate`: in the tested compiler configuration, `javac` generates an `invokedynamic` whose bootstrap belongs to `LambdaMetafactory`. This dynamic call site creates an implementation of the functional interface `Task`. After the object is created, `task.apply("Bob")` is a normal interface call (`invokeinterface`).
2. **String concatenation** `"Hello, " + input`: `input` is a runtime variable, so the tested compiler emitted `invokedynamic` linked to `StringConcatFactory.makeConcatWithConstants`.

**Program B does not call `ManualBootstrapOnly.bootstrap` at all.** The actual bootstraps of the two instructions are bootstraps provided by the JDK. `ManualBootstrapOnly.decorate` is referenced as the **implementation method** of the method reference, not the bootstrap method.

Subtle point: *the method reference pointing to `decorate`* and *the bootstrap pointing to `LambdaMetafactory.metafactory`* are two different method handles in the constant pool. You should not see the name `decorate` in the `BootstrapMethods` section and conclude it is the bootstrap method.

Keep **both files in the same directory** and run:

```bash
javac --release 17 ManualBootstrapOnly.java CompilerIndyDemo.java
java ManualBootstrapOnly
java CompilerIndyDemo
```

Stdout of the first program:

```text
manual-bootstrap-entered
manual=[Ada]
```

Stdout of the second program:

```text
reference=[Bob]
concat=Hello, Java
```

These values were verified using `javac --release 17` and `java`. If you want to change the runtime string concatenation value, you can run `java CompilerIndyDemo JVM` to get `concat=Hello, JVM`; that is an optional variation, not part of the standard stdout above.

### 5.1. Exact Disassembly Command

Run:

```bash
javap -p -c -v ManualBootstrapOnly
javap -p -c -v CompilerIndyDemo
```

Flag explanations:

- `-c`: prints instructions in method code, such as `invokestatic`, `invokevirtual`, `invokedynamic`.
- `-v`: prints detailed class file information, including the constant pool, version, and `BootstrapMethods`.
- `-p`: shows all members, including private ones; useful when investigating compiler-generated methods.

You can also write the output to two text files for inspection:

```bash
javap -p -c -v ManualBootstrapOnly > manual.txt
javap -p -c -v CompilerIndyDemo > compiler.txt
```

Bash/Linux/macOS, filter notable lines:

```bash
grep -nE 'invokedynamic|invokestatic.*bootstrap|invokeExact|BootstrapMethods|LambdaMetafactory|StringConcatFactory' manual.txt compiler.txt
```

PowerShell on Windows:

```powershell
Select-String -Path manual.txt,compiler.txt -Pattern 'invokedynamic|invokestatic.*bootstrap|invokeExact|BootstrapMethods|LambdaMetafactory|StringConcatFactory'
```

**Be careful when counting opcodes:** the word `invokedynamic` can appear in both **constant pool comments** and **instructions**. To count the actual number of opcodes in the disassembly, count only the *Code* lines that have a numeric offset and opcode, such as `0: invokedynamic ...` or `45: invokedynamic ...`; do not count every occurrence of the string `InvokeDynamic`.

### 5.2. Bytecode Result in `ManualBootstrapOnly`

In `main`, the notable instructions of the inspected compilation are:

```text
14: invokestatic  #66   // Method bootstrap:(Lookup;String;MethodType)CallSite;
19: invokevirtual #70   // Method java/lang/invoke/CallSite.dynamicInvoker:()MethodHandle;
26: invokevirtual #78   // Method java/lang/invoke/MethodHandle.invokeExact:(String)String;
```

For readability, the `//` portion above **shortens the descriptors** with friendly type names; the actual `javap` output prints full JVM descriptors such as `Ljava/lang/invoke/CallSite;`. The offset positions and `#66`, `#70`, `#78` numbers belong to one specific compilation and **may change** if the JDK/compiler/source changes. The opcodes and their meanings are what should be compared.

Conclusion from the inspected disassembly:

```text
ManualBootstrapOnly:
  number of invokedynamic instructions = 0
  number of BootstrapMethods attribute entries = 0
  number of invokestatic calls to bootstrap = 1
  number of invokevirtual calls to MethodHandle.invokeExact = 1
```

This is exact proof that **`MethodHandles.lookup()` + `CallSite` + `invokeExact` is not synonymous with an `invokedynamic` instruction**.

Note: this class file still has constant-pool entries to call the `bootstrap` helper and `java.lang.invoke` methods. The existence of those Methodrefs is **different** from a `CONSTANT_InvokeDynamic` referencing a bootstrap specifier.

### 5.3. Bytecode Result in `CompilerIndyDemo`

In `main`, the inspected compilation has two instructions:

```text
0:  invokedynamic #7,  0   // InvokeDynamic #0:apply:()LCompilerIndyDemo$Task;
45: invokedynamic #34, 0   // InvokeDynamic #1:makeConcatWithConstants:(Ljava/lang/String;)Ljava/lang/String;
```

The constant pool numbers and bytecode offsets **are not required to be identical** on another machine; the caller/factory names and opcodes are the focus. In this class, inspection confirmed:

```text
CompilerIndyDemo:
  number of invokedynamic instructions = 2
  number of BootstrapMethods attributes = 1
  number of bootstrap entries = 2
```

Notice the method reference:

```java
Task task = ManualBootstrapOnly::decorate;
```

is performed with `invokedynamic` to create the functional object; after that:

```java
task.apply("Bob");
```

uses `invokeinterface`, **not the second `invokedynamic` instruction itself**. The second instruction comes from the string concatenation expression `"Hello, " + input`.

A method reference does not turn **every subsequent call** into a bootstrap pass. The dynamic call site typically handles linking the method/instantiating the functional object, while the subsequent call to the functional interface has its own dispatch bytecode.

## 6. Reading `BootstrapMethods` and Tracing Back to the Instruction

In `javap -v CompilerIndyDemo`, after the code and other sections, there is the `BootstrapMethods` attribute. The two bootstrap entries from the inspection have the shortened form:

```text
BootstrapMethods:
  0: REF_invokeStatic java/lang/invoke/LambdaMetafactory.metafactory:...
     Method arguments:
       ... REF_invokeStatic ManualBootstrapOnly.decorate:(Ljava/lang/String;)Ljava/lang/String;
  1: REF_invokeStatic java/lang/invoke/StringConcatFactory.makeConcatWithConstants:...
     Method arguments:
       ... Hello, \u0001
```

The `...` in this snippet represents **descriptors/constant-pool indices omitted for readability**; to see the full bytecode, run `javap -v` directly on the actual class. `\u0001` in the recipe is the placeholder where the dynamic argument is inserted during string concatenation; it is not a character you have to type yourself in Java source.

In the constant pool section, there are also corresponding entries such as:

```text
#7  = InvokeDynamic  #0:...   // call site using bootstrap entry 0
#34 = InvokeDynamic  #1:...   // call site using bootstrap entry 1
```

When looking at an instruction:

```text
0: invokedynamic #7, 0
```

`#7` is the **constant pool entry index** of type `CONSTANT_InvokeDynamic`. The comment `InvokeDynamic #0:apply` carries the index of **bootstrap method entry 0**, not "constant pool index 0".

The tracing procedure that applies to any class file:

1. Find the **`invokedynamic` instruction** in the `Code` section.
2. Take the constant pool index that the instruction uses.
3. Find the corresponding `CONSTANT_InvokeDynamic` entry in the constant pool.
4. From that entry, take **bootstrap_method_attr_index**; this is a zero-based index into the `BootstrapMethods` array, not a bytecode offset.
5. Find the corresponding entry in the `BootstrapMethods` attribute.
6. Read the bootstrap method handle (`REF_invokeStatic ...`) and the **bootstrap arguments**.
7. Read the `NameAndType`/method descriptor of the dynamic call site to understand the signature the JVM will require the `CallSite` to serve.

In Example B, both bootstrap method handles point to JDK APIs, because the Java compiler chose bootstraps for the method reference and string concat. There is no `BootstrapMethods` entry pointing to `ManualBootstrapOnly.bootstrap`, even though the name `bootstrap` appeared in Program A.

### Warning: Having `BootstrapMethods` Alone Is Not Enough to Confirm an `invokedynamic` Opcode Exists

In modern class files, the `BootstrapMethods` attribute can also serve **dynamically-computed constants** (`CONSTANT_Dynamic`, or *condy*). Therefore, if you need to prove that a piece of code **used the `invokedynamic` opcode**, there must be a **real `invokedynamic` instruction** in `Code` and a matching mapping.

Strict verification rule: **instruction -> constant pool `InvokeDynamic` -> bootstrap entry**, not just searching for the word `BootstrapMethods`.

## 7. What Does the JVM Actually Do When Linking an `invokedynamic`?

General overview for a dynamic call site:

```text
class file:
  Code: invokedynamic #callSiteEntry, 0
  constant pool: name + method descriptor + bootstrap entry index
  BootstrapMethods: bootstrap handle + static bootstrap arguments
                                      |
                                      v
JVM resolution / linkage:
  resolve the bootstrap handle and arguments
  create a Lookup for the class containing the instruction
  create String name + MethodType from the call site specifier
  invoke the bootstrap method handle
  verify the result is a valid CallSite
  verify target.type() == descriptor of the call site
  link the instruction with the chosen CallSite
                                      |
                                      v
runtime invocation:
  each time the instruction runs: execute the CallSite's target
  according to the associated signature and CallSite state
```

### 7.1. Three Common Parameters: caller, name, type

A common bootstrap pattern:

```java
public static CallSite bootstrap(
        MethodHandles.Lookup caller,
        String name,
        MethodType type) throws Throwable {
    // find/construct an appropriate target MethodHandle
    // return a CallSite whose target.type() matches type
}
```

This is an **API pattern**, not a standalone program, and it does not mean `javac` will automatically link to this method.

- **`caller`**: lookup bound to the class containing the `invokedynamic` instruction. It carries the lookup privileges of the caller context according to the specification, not an arbitrary lookup declared by a consumer.
- **`name`**: the symbolic call site name recorded in the constant pool, chosen by the compiler or generator; it does not automatically determine the target member if the bootstrap code does not use it.
- **`type`**: the `MethodType` of the call site, expressing the types of the arguments passed through the dynamic call and the return type.

A bootstrap can receive additional **static bootstrap arguments** from the constant pool (such as method handles, types, strings, or other permitted constants). These arguments serve **linking**, unlike the **dynamic arguments** passed when the instruction is executed.

For example, `LambdaMetafactory.metafactory` receives additional metadata about the functional interface and implementation handle. `StringConcatFactory.makeConcatWithConstants` receives an additional recipe/constants. That is why the `BootstrapMethods` entry has a `Method arguments` section.

### 7.2. `CallSite` and Type Checking

For linkage to succeed, the bootstrap must return a valid result resolving to a non-null `CallSite`, and **the type of the target MethodHandle must match** the method descriptor of the dynamic call site **exactly**. `target.asType(type)` can help create a compatible adapter inside the bootstrap when the conversions are supported; however, the compiler/generator must still provide a matching descriptor.

Three common `CallSite` categories:

- `ConstantCallSite`: the target is set once and cannot be changed after creation.
- `MutableCallSite`: the target can be changed, with its own visibility/synchronization rules.
- `VolatileCallSite`: access to the target follows volatile visibility rules.

`CallSite.dynamicInvoker()` creates a `MethodHandle` whose behavior is to invoke the call site's current target, which is very useful when manipulating a `CallSite` as a Java object. However, **that API does not emit an `invokedynamic` opcode** into the compiled class.

### 7.3. When Does Linkage Occur, and Does Bootstrap Run Exactly Once?

Under Java SE/JVMS rules, a dynamic call site is linked when the JVM needs to execute the instruction for the first time. After successful linkage, the instruction uses the chosen `CallSite` **without repeating the bootstrap on every call**.

However, you should not write a bootstrap with side effects and rely on the assumption **"the Java bootstrap method can only run strictly once"**. Multiple threads may simultaneously try to link an unlinked site; the runtime may execute the bootstrap method handle on multiple threads concurrently, then **select one result** to install for the dynamic call site. The other results are discarded.

If a bootstrap writes global state, creates resources, or registers side effects, it must handle concurrency and idempotency according to the application context. This differs from a manually called helper: the number of direct helper calls depends entirely on the Java code controlling it.

### 7.4. Errors When Bootstrap/Linkage Fails

If the bootstrap cannot be resolved/invoked validly, the result is not an appropriate `CallSite`, or the target method type does not match, the JVM may throw a **`BootstrapMethodError`** during linking. The error may have a cause to help trace the origin. Certain `Error`s thrown directly during the bootstrap/resolution step are propagated according to JVMS rules.

This is **not the same** as calling `bootstrap(...)` yourself in Java and receiving a `NoSuchMethodException` or `IllegalAccessException` per the method signature. Errors in a direct helper call follow normal Java invocation rules; errors in `invokedynamic` linkage are handled by the JVM according to the bootstrap/linkage protocol.

Therefore, when debugging, you need to confirm whether the exception occurred while **manually creating a `CallSite`**, or while **the JVM was linking the `invokedynamic` opcode**.

## 8. Why Are `invokeExact`, `LambdaMetafactory`, and `invokedynamic` Easily Confused?

An easy misconception:

```java
MethodHandle handle = ...;
handle.invokeExact(arg);
```

If the handle's target is chosen dynamically, does the code above use `invokedynamic`?

**Not based on that syntax alone.** `invokeExact` is a signature-polymorphic method. The JVM uses a special type-checking mechanism for it, but the bytecode of the call from Java still has the **`invokevirtual`** opcode. The disassembly of Example A proves this.

Another picture:

```java
Task task = ManualBootstrapOnly::decorate;
```

With the tested `javac`, **the expression that creates the method-reference object** uses `invokedynamic` via `LambdaMetafactory`. In the `BootstrapMethods` table, the implementation handle points to `ManualBootstrapOnly.decorate`, whereas **the bootstrap handle** points to `LambdaMetafactory.metafactory`. Having the method reference lead to `decorate` does not turn `decorate` into a bootstrap method.

For string concatenation:

```java
String message = "Hello, " + input;
```

the compiler may choose `invokedynamic` and `StringConcatFactory`; however, a purely constant expression `"Hello, " + "Java"` may just be an `ldc` pointing to the concatenated string. Do not use a constants-only example to conclude the compiler does not support dynamic string concat.

### Distinction Table by Layer

| Code or artifact | Mechanism/privilege type | Evidence to look for |
| --- | --- | --- |
| Calling a static helper named `bootstrap` | Java method invocation | `invokestatic` |
| `CallSite site = new ConstantCallSite(handle)` | Java object/API | Constructor call + MethodHandle references |
| `site.dynamicInvoker().invokeExact(...)` | Signature-polymorphic MethodHandle invocation | `invokevirtual ... invokeExact` |
| Lambda/method reference compiled by `javac` | Compiler chooses dynamic linkage | `invokedynamic` + `LambdaMetafactory` bootstrap entry |
| Runtime string concat compiled by `javac` | Compiler chooses dynamic linkage | `invokedynamic` + `StringConcatFactory` bootstrap entry |
| Defining a custom dynamic call site in bytecode | Bytecode generation/transform | `invokedynamic` + bootstrap entry pointing to the exact custom bootstrap |

## 9. What If You Really Want an `invokedynamic` Calling a Custom Bootstrap?

**Regular Java source code has no statement or expression that lets you write:**

```text
invokedynamic "apply" (String)String bootstrap=ManualBootstrapOnly.bootstrap
```

The line above is an **illustrative idea**, not Java syntax, and cannot be fed to `javac` expecting it to emit the opcode. To specify a **custom bootstrap method** for an instruction, you need a tool that **generates or modifies class files**, such as a compiler for another language running on the JVM, a bytecode generation framework, or the ASM library.

A logical sketch of the operation using ASM is:

```java
// Illustrative ASM snippet, NOT a standalone program.
// mv is a MethodVisitor from org.objectweb.asm.
// Requires ASM dependency, class writer, method body, and an appropriate class loader.
Handle bsm = new Handle(
        Opcodes.H_INVOKESTATIC,
        "ManualBootstrapOnly",
        "bootstrap",
        "(Ljava/lang/invoke/MethodHandles$Lookup;"
                + "Ljava/lang/String;"
                + "Ljava/lang/invoke/MethodType;)"
                + "Ljava/lang/invoke/CallSite;",
        false
);

// There must be a String argument on the operand stack matching the descriptor.
mv.visitInvokeDynamicInsn(
        "apply",
        "(Ljava/lang/String;)Ljava/lang/String;",
        bsm
);
```

This is only an **illustration of the structure of a bytecode generator using ASM**, not a complete Java program, and not code tested in the two runnable examples in sections 3–5. The names `Handle`, `Opcodes`, and `MethodVisitor` belong to **the external ASM library**, not the Java standard library. You need the corresponding imports, dependency library, a valid method visitor, proper stack-map/max-stack, pushing the argument onto the operand stack, storing the result, and loading the class successfully.

The key point is that `visitInvokeDynamicInsn` requires:

1. **Call-site name**, e.g. `"apply"`.
2. **Call-site descriptor**, e.g. `(Ljava/lang/String;)Ljava/lang/String;`.
3. **Bootstrap method handle**, here referencing `ManualBootstrapOnly.bootstrap`.
4. **Additional static bootstrap arguments** if the bootstrap design requires them.

When the properly generated class file is loaded and the instruction executes, the JVM can invoke the bootstrap through the linkage protocol and use the returned `CallSite`. Then `javap -v` must show **the bootstrap entry actually pointing to `ManualBootstrapOnly.bootstrap`** and the `Code` section containing the `invokedynamic` instruction. Only then is there grounds to say **the custom bootstrap was used by the JVM to link the dynamic call site**.

If using ASM in a real project, choose an ASM version compatible with the class file version, declare the official dependency, and verify with the bytecode verifier; **you should not rely on the JDK's internal `jdk.internal.*` ASM packages** because they are not a stable supported API.

## 10. When Can the Two Ways of Calling Bootstrap Yield the Same Result via Different Mechanisms?

A direct source helper can return the exact same `String` as a custom indy site:

```text
direct Java:
  bootstrap(...) -> CallSite -> dynamicInvoker() -> "result"

real invokedynamic:
  [bootstrap specifier] -> JVM linkage -> CallSite -> instruction -> "result"
```

The same final value **does not prove the same path**.

Differences with practical impact:

- **Runtime specification**: `invokedynamic` stores linkage on the opcode occurrence, without requiring Java source to hold a `CallSite` variable.
- **Bootstrap arguments**: the JVM constructs the parameters from class-file metadata; a direct call constructs arguments itself and can pass a different `Lookup`.
- **Access privileges**: the `Lookup` provided by the JVM is bound to the instruction's caller class. Direct Java can pass `MethodHandles.lookup()` from another class or a reduced-privilege lookup; the `findStatic` result can differ.
- **Timing**: a manual call runs right where source calls it; real indy links when the runtime needs to execute the site, and may face concurrent linking contention.
- **Descriptor checking**: real indy requires the `CallSite` target type to match the descriptor recorded in bytecode. A direct call can obtain a `CallSite` and invoke it with a mismatched type, receiving a `MethodHandle` call-site error.
- **Bytecode reading**: a direct call resides in `invokestatic`; real indy resides in `invokedynamic` and has bootstrap metadata in the class file.

A test that only verifies `"manual=[Ada]"` or `"reference=[Bob]"` is a functional result test. To test **the mechanism** taught in this lesson, there must be a separate bytecode/constant pool test.

## 11. Verification Checklist on a Real Java Project

When you encounter the claim "this framework uses `invokedynamic`", follow this process:

1. **Identify the actual class and method** containing the intended call site. Having only a `bootstrap` helper in source is not enough.
2. **Compile in the actual configuration** (JDK, `--release`, flags, and dependencies), avoiding conclusions from source that differs from the running class.
3. **Run `javap -c -v -p`** on the actual class; confirm the major version when appropriate (`--release 17` usually produces major version 61).
4. **Find the instruction offset containing `invokedynamic`**, not just searching for the string `InvokeDynamic` in the constant pool.
5. **Read the `CONSTANT_InvokeDynamic`** of the instruction to know the name, descriptor, and bootstrap index.
6. **Read the corresponding `BootstrapMethods` entry** to know the bootstrap method handle and static arguments.
7. **Verify the bootstrap owner**: `LambdaMetafactory`, `StringConcatFactory`, `ObjectMethods`, or a framework's custom method?
8. **Compare with Java source**: a method reference or string concatenation can create indy; a direct helper call does not prove a custom bootstrap.
9. **Check runtime**: is the call site executed, are there any linkage errors, and are the arguments of the right types?
10. **If `BootstrapMethodError` appears**, inspect the cause and the descriptor/target type. For a direct Java helper, inspect the exception where the method itself throws.
11. **If using generated/transformed classes**, make sure you disassemble **the exact final class file that runs**, not just the `.class` compiled before the transform step.
12. **Do not use bootstrap stdout as the sole proof**: the log could be triggered by Java code calling it directly, or by another compiler-generated site.

The concrete shell commands in section 5 work with a normal classpath. For multi-module projects, add the appropriate `--module-path`/classpath for compiling and running; `javap` still needs to point to the generated class file/module.

### Counting Opcodes Without Confusing Them with the Constant Pool

In `javap -c -v` output, an instruction has a numeric offset form:

```text
45: invokedynamic #34, 0
```

while the constant pool has the form:

```text
#34 = InvokeDynamic #1:#35
```

Both refer to `InvokeDynamic`, but they are **not two instructions**. If a parser/test script simply searches for the string `"invokedynamic"` without distinguishing context, it can easily double-count. Filter lines that have a **bytecode offset** and cross-reference them with the constant pool index.

## 12. Typical Mistakes and How to Fix Them

| Claim / symptom | Why it is not quite right | How to verify or fix |
| --- | --- | --- |
| "I have a `bootstrap` method so I am using `invokedynamic`" | Method names do not create opcodes | `javap -c -v`; find the instruction and the right bootstrap entry |
| "`MethodHandle.invokeExact` is an `invokedynamic` opcode" | `invokeExact` uses signature-polymorphic `invokevirtual` | Check the opcode at the call site |
| "There is a `CallSite` object so the JVM linked a dynamic call site" | `CallSite` is also a manually created Java object | Check `CONSTANT_InvokeDynamic` and `BootstrapMethods` |
| "The class has `BootstrapMethods` so it must have `invokedynamic`" | It might only be using `CONSTANT_Dynamic` | Find the actual opcode in the `Code` section |
| "The method `decorate` appears in bootstrap arguments so it is the bootstrap" | It may just be the lambda's implementation method | Check the entry's bootstrap method handle, do not confuse it with static arguments |
| "A string `+` operation always emits indy" | Constant folding or compiler strategy may differ | Use a runtime variable and inspect the class after compilation |
| "Using `--release 17` means every compiler produces identical offsets/CP indexes" | Code generation strategy/ordering may differ | Compare opcodes, descriptors, and logical links; do not hardcode `#7`/offsets |
| "Java source calling bootstrap and JVM bootstrap pass the exact same `Lookup` in all cases" | Direct Java chooses lookup itself; JVM takes the instruction's caller | Verify the lookup class/module in the exact context |
| "Bootstrap is guaranteed to run strictly once across all threads" | Linkage contention can occur and multiple bootstrap invocations can run concurrently | Make bootstrap idempotent/thread-safe if it has side effects |
| "`BootstrapMethodError` is an exception from the target method" | It usually relates to bootstrap linkage/validation | Inspect the cause and bootstrap entry |
| "`task.apply` in a lambda is always indy" | Creating the functional object may be indy; calling `apply` is usually `invokeinterface` | Disassemble each method individually, do not lump them together |
| "For custom indy, calling `LambdaMetafactory` directly is enough" | Calling the factory directly creates a CallSite but does not emit the instruction | Use a bytecode emitter/transformer to create the custom opcode |
| "Having the opcode guarantees the right bootstrap owner" | The CP entry may point to a different factory than expected | Trace back `CONSTANT_InvokeDynamic` -> `BootstrapMethods` |

A very common mistake when trying to write a custom bootstrap in Java is running directly:

```java
CallSite site = bootstrap(
        MethodHandles.lookup(), "apply",
        MethodType.methodType(String.class, String.class));
```

This snippet is **valid Java code in a context that has a matching `bootstrap` method**, but it only proves you **can use the `CallSite` API by hand**, not that you have affected an `invokedynamic` opcode.

## 13. Self-Check Questions with Answers

1. **Does a Java method named `bootstrap` register itself with the JVM?** No. To become the bootstrap of an indy site, the class file must have a matching symbolic reference and bootstrap entry.
2. **Is `MethodHandles.lookup()` called in `main` and passed into a helper completely identical to the `Lookup` created by the JVM for every indy site?** No. Privileges and the lookup class depend on the caller context; the JVM takes it from the class containing the site.
3. **Does `new ConstantCallSite(handle)` emit indy bytecode?** No. This is Java object creation.
4. **What opcode does `dynamicInvoker().invokeExact(...)` compile to?** The `invokeExact` call uses `invokevirtual`, not `invokedynamic`.
5. **Why must the two examples be in separate files?** So that the manual class can genuinely be verified to contain no `invokedynamic`, while the compiler class has two opcodes with clear origins.
6. **Does `ManualBootstrapOnly.bootstrap` run when running `CompilerIndyDemo`?** Not in this example. The method reference uses `decorate`; JDK factories handle the bootstrap.
7. **Where does the `BootstrapMethods` entry of the method reference point?** `LambdaMetafactory.metafactory`; the implementation handle is what points to `ManualBootstrapOnly.decorate`.
8. **What did the tested compiler turn the string concatenation `"Hello, " + input` into?** An `invokedynamic` to `StringConcatFactory.makeConcatWithConstants`.
9. **If `input` is replaced with the literal `"Java"` right in the string concatenation, is it still guaranteed to create indy?** No. The compiler may constant-fold it.
10. **Why use `javap -c -v` instead of just running the program?** Because identical output does not reveal opcodes or bootstrap specifiers.
11. **Can `BootstrapMethods` be treated as the sole proof of indy?** No; the attribute can also be for dynamic constants.
12. **Are `#7` in `invokedynamic #7` and `#0` in `InvokeDynamic #0:apply` the same index?** No; the first index points to the constant pool, the second points to the bootstrap method entry.
13. **What happens if an indy bootstrap returns a `CallSite` whose target type does not match the descriptor?** The JVM fails to link and may report `BootstrapMethodError`.
14. **If a dynamic call site is invoked multiple times, does the bootstrap run every time?** No. After successful linking, the site uses the linked result; however, there may be parallel bootstrap invocations while resolving first-time contention.
15. **What do you do if you want to specify `ManualBootstrapOnly.bootstrap` as the real bootstrap of a custom site?** Generate or transform a class file containing `invokedynamic` with a matching `BootstrapMethods` entry, for example using ASM or a bytecode compiler.
16. **Why is `task.apply("Bob")` not proof of the second indy opcode?** Because an interface call can be `invokeinterface`; in this lesson the second indy opcode belongs to string concatenation.

**Key takeaway:** **A method name, a `CallSite` object, or a `MethodHandle.invokeExact` call does not determine whether `invokedynamic` is present.** The proof must lie in the **actual class file**: an `invokedynamic` instruction, a `CONSTANT_InvokeDynamic` entry, and `BootstrapMethods` pointing to the right bootstrap owner. Calling a bootstrap helper in Java only simulates creating a target/call site; real custom bytecode linkage must be emitted by a compiler or bytecode generator.
