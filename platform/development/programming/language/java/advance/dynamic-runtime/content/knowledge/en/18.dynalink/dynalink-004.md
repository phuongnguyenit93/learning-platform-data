# 18.4 RelinkableCallSite, SimpleRelinkableCallSite and ChainedCallSite

## 1. Topic and objectives

`Dynalink` is a Java library in the `jdk.dynalink` module that supports dynamic linking of operations on objects such as reading/writing properties, getting elements, invoking functions, or creating objects. When the receiver type is only known at runtime, a method handle linked for class A may no longer be suitable for class B. Dynalink supports updating the linkage of **the same call site** without having to treat the entire expression as a fixed call.

The three APIs of this lesson consist of one **protocol** and two **cache policies**:

- **`RelinkableCallSite`** is an interface describing a call site that `DynamicLinker` can manage. It provides the descriptor and receives `initialize`, `relink`, and `resetAndRelink` commands.
- **`SimpleRelinkableCallSite`** is a monomorphic implementation (*monomorphic inline cache*), holding **one `GuardedInvocation`** at a time. If the guard no longer applies, it takes the fallback path to be relinked.
- **`ChainedCallSite`** is a polymorphic implementation (*polymorphic inline cache*, PIC), holding **a chain of `GuardedInvocation`s**. By default it is limited to 8 entries, with the most recently linked at the head of the chain, and the oldest may be evicted when full.

Both Simple and Chained can return **the same business result**. They differ in how they reuse specializations, the number of guards to test, relink frequency, and resource pressure. No strategy is optimal for every workload.

After this lesson, you should be able to distinguish initial linking from relinking, understand `GuardedInvocation` and `relinkAndInvoke`, know how to choose Simple/Chained based on receiver shapes, determine when `resetAndRelink` clears cache history, and implement a Java 17+ demo.

## 2. Why does relink occur?

Suppose a dynamic language has the operation:

~~~text
result = receiver.color
~~~

An expression at a single source location can encounter multiple receivers:

~~~text
Call 1: FieldBean   → read public field color
Call 2: GetterBean  → call getColor()
Call 3: FieldBean   → read field color
Call 4: GetterBean  → call getter
~~~

In bytecode generated by a language runtime, similar logic can be represented as:

~~~text
aload_1
invokedynamic GET:PROPERTY:color (Object)Object
astore_2
~~~

This is a **bytecode diagram**, not verbatim `javap` output, nor is every runtime required to encode operation names this way. The important point is that the call site takes an `Object` receiver and returns `Object`. For the concrete class of the receiver, the linker selects the right target.

A specialization typically consists of two method handles:

~~~text
guard(receiver)    → does the receiver match this type/shape?
invoke(receiver)   → specialized operation for that type/shape
~~~

A changing receiver can cause the guard to fail. To avoid throwing `ClassCastException` or performing the wrong operation, the call site goes to a fallback capable of requesting another specialization. That is relinking.

**Not every relink re-runs the `invokedynamic` bootstrap method.** The bootstrap creates/links the `CallSite`, while relinking changes/composes the target of the already existing call site.

~~~

Core API table:

| API | Meaning |
| --- | --- |
| `CallSiteDescriptor` | Fixed metadata for a site: lookup, operation, method type |
| `Operation` | Abstract operation, such as `GET:PROPERTY:color` |
| `DynamicLinkerFactory` | Configures and creates `DynamicLinker` |
| `DynamicLinker.link(site)` | Attaches the linker to a relinkable site, setting up the initial linkage path |
| `GuardingDynamicLinker` | Where a `GuardedInvocation` can be found for the current operation and receiver |
| `GuardedInvocation` | Invocation handle plus guard and optional invalidation conditions |
| `RelinkableCallSite` | Protocol for receiving/installing new linkages |
| `SimpleRelinkableCallSite` | Caches one guarded invocation |
| `ChainedCallSite` | Caches multiple guarded invocations as a chain |

`DynamicLinkerFactory` by default integrates `BeansLinker` to handle many operations on regular Java objects. When implementing a language with its own object model, custom guarding linkers can be added to describe the exact access rules of that language.

### Type identity of a call site

A site with `MethodType` `(Object)Object` still has that type after encountering `String`, `Map`, `FieldBean`, and `GetterBean`. **The runtime receiver class can change; the call-site signature does not change by itself.** The internal method handles must be adapted to be compatible with the descriptor when updating the target.

## 4. RelinkableCallSite: the exact protocol

Key Java 17 signatures:

~~~java
// Methods of interface jdk.dynalink.RelinkableCallSite:
CallSiteDescriptor getDescriptor();
void initialize(MethodHandle relinkAndInvoke);
void relink(
        GuardedInvocation guardedInvocation,
        MethodHandle relinkAndInvoke);
void resetAndRelink(
        GuardedInvocation guardedInvocation,
        MethodHandle relinkAndInvoke);
~~~

This is an **API excerpt** for learning names and roles, not a standalone program. `GuardedInvocation` is in package `jdk.dynalink.linker`; `MethodHandle` is in `java.lang.invoke`.

The methods address different tasks:

**`getDescriptor()`:** provides the metadata needed for relinking. It **does not** return a business value or a receiver.

**`initialize(relinkAndInvoke)`:** installs the initial `MethodHandle` that knows how to ask the linker for a new target and immediately invoke that target. When `DynamicLinker.link(site)` is called, it prepares the site with this callback; finding a suitable specialization can be deferred until **the first call with actual arguments**.

**`relink(guardedInvocation, relinkAndInvoke)`:** notifies of a new specialization. The site **may keep old specializations that are still valid** depending on the cache policy. Simple typically replaces; Chained can append.

**`resetAndRelink(guardedInvocation, relinkAndInvoke)`:** requests forgetting previous linkage state and then creating a target from the new specialization. This is a different operation from `relink`, especially for PIC.

**`relinkAndInvoke`:** fallback callback provided by the linker, having the same `MethodType` as the site. It is neither a user argument nor the bootstrap method itself.

The `RelinkableCallSite` interface is not declared as a subclass of `java.lang.invoke.CallSite`. The built-in implementations inherit from `AbstractRelinkableCallSite extends MutableCallSite`, so in practice they also have the `CallSite` API such as `type()` and `dynamicInvoker()`.

## 5. Inheritance between the two implementations

~~~text
java.lang.Object
   └── java.lang.invoke.CallSite
        └── java.lang.invoke.MutableCallSite
             └── AbstractRelinkableCallSite
                  ├── SimpleRelinkableCallSite
                  └── ChainedCallSite

AbstractRelinkableCallSite implements RelinkableCallSite
~~~

`AbstractRelinkableCallSite` holds `CallSiteDescriptor` and supports initializing the fallback with the right type. The two subclasses define how `relink` and `resetAndRelink` are performed. They are provided out of the box, so when writing a runtime you are not required to assemble the entire guard chain from scratch.

Both constructors take a descriptor:

~~~java
new SimpleRelinkableCallSite(descriptor);
new ChainedCallSite(descriptor);
~~~

This is an **illustrative snippet**; the `descriptor` variable must contain a valid `Lookup`, `Operation`, and `MethodType`.

## 6. What assumptions does GuardedInvocation hold?

`jdk.dynalink.linker.GuardedInvocation` is an immutable value holder, consisting of:

- **Invocation MethodHandle:** executes a specialized operation.
- **Guard MethodHandle (optional):** determines whether this specialization applies to the current arguments.
- **SwitchPoint(s) (optional):** allows invalidation when an external assumption no longer holds.
- **Invalidating exception type (optional):** a designated exception that can invalidate the specialization.

Example:

~~~text
Operation: GET:PROPERTY:color
Guard:     receiver instanceof FieldBean
Invoke:    read public field FieldBean.color
Fallback:  ask the linker to find another specialization
~~~

If the guard returns `true`, the invocation runs. If `false`, the site tries another branch (in PIC) or transfers to the fallback. A guard usually **checks applicability**, not necessarily comparing property values. Two `FieldBean` instances with `color="red"` and `color="blue"` can still share the same specialization without relinking.

**Do not assume a guard is `getClass()==X`.** It can be based on class, object structure, version, switch point, or language rules. `ChainedCallSite` is a chain of **conditions and targets**, not a publicly guaranteed Map<Class,MethodHandle>.

`GuardedInvocation` has the constructor:

~~~java
new GuardedInvocation(invocationHandle, guardHandle);
~~~

In this example, the guard has type `(Object)boolean`, and the invocation has type `(Object)Object`. The two handles must be compatible for composition with `MethodHandles.guardWithTest` and with the call-site signature.

## 7. SimpleRelinkableCallSite is a monomorphic cache

Simple holds **one** `GuardedInvocation` at a time. When the guard does not match, a switch point is invalidated, or an invalidating exception occurs, the current specialization cannot be used; the fallback finds a new one and the site replaces its state.

~~~text
Receivers: A, A, B, B, A

Simple:
  A → link A
  A → reuse A
  B → guard A miss; replace with B
  B → reuse B
  A → guard B miss; replace with A
~~~

This approach fits when a site almost always receives **the same receiver shape**. The guard chain is short, state is small, and there is no need to store multiple specializations.

The main drawback is *thrashing* if traffic alternates A/B: each shape change can require a relink, even though both shapes were seen before. The cost of linker lookup, creating adapters, and invalidation can exceed a few guard checks.

An example site suitable for Simple:

~~~text
95% A, 5% A-subclass that the guard still accepts
  → usually reuses one specialization
~~~

An example unsuitable site:

~~~text
A, B, A, B, A, B continuously
  → single-entry cache must replace continuously
~~~

Even so, **a fixed number of relinks is not guaranteed** from the receiver list alone: the actual guard is chosen by the linker, and a guard may accept more than one class or be invalidated between calls.

## 8. ChainedCallSite is a polymorphic inline cache

Chained holds **multiple** `GuardedInvocation`s at the same time. When invoked, it tests the previously linked guards first before falling back if no branch matches.

~~~text
Receivers: A, B, A, B, C

Chained (illustrative):
  A → cache [A]
  B → cache [B,A]
  A → B guard fail, A guard pass
  B → B guard pass
  C → cache [C,B,A]
~~~

Per the JDK 17 contract:

- `getMaxChainLength()` **defaults to 8**.
- The limit can be overridden in a subclass.
- When adding a new specialization and the chain is full, the **oldest entry** is evicted.
- The **most recently linked entry** is at the head, and the oldest is at the tail.
- Entries **do not automatically reorder on every hit**; this is not an LRU cache in the per-access sense.
- Specializations invalidated via switch points/invalidating exceptions can be removed from the chain.
- Concurrent relinking from multiple threads has contention resolution; a guarded invocation created by a losing thread may not be integrated, causing repeated linking.

### Changing the limit via a subclass

~~~java
static class TwoEntryChain extends ChainedCallSite {
    TwoEntryChain(CallSiteDescriptor descriptor) {
        super(descriptor);
    }

    @Override
    protected int getMaxChainLength() {
        return 2;
    }
}
~~~

This is an **illustrative class**, requiring imports and placement in a valid Java class/file. The API requires `getMaxChainLength()` to return a number **1 or greater**. Do not use `0` to represent “no cache”; a number less than 1 leads to a runtime error.

If A, B, C are linked sequentially in a two-entry cache:

~~~text
[A] → [B,A] → [C,B]
                 ^
             A evicted
~~~

When A returns, the guard may miss and the linker relinks A back at the head of the chain. “Evicted from the cache” is different from “never able to handle type A”.

## 9. Comparing caching capabilities

| Characteristic | SimpleRelinkableCallSite | ChainedCallSite |
| --- | --- | --- |
| Cache style | Monomorphic | Polymorphic |
| Number of `GuardedInvocation`s remembered | One | Multiple, default maximum 8 |
| Guard miss | Usually relinks, replaces old entry | Tries remaining entries; only relinks if all fail |
| Alternating A/B | Prone to continuous cache replacement | Can reuse both A and B |
| One dominant type | Fewer branches, simple | May add unnecessary guard overhead |
| Many distinct types | Links continuously | Has eviction/guard chain overhead |
| Capacity customization | No PIC-size hook | `getMaxChainLength()` |
| Reset | To a single new entry | Drops the entire chain and starts over |
| Small polymorphic stream | Usually less suitable | Can reduce number of relinks |

One should not conclude that Chained is always faster. With a long chain, checking many guards can cost CPU and affect JIT optimization. Conversely, continuous relinking in Simple also has a cost. The choice should be based on shape distribution, guard hit-rate, linker cost, and benchmarks.

## 10. Complete Java 17+ Example 1: Real Dynalink with two JavaBeans

The program has two object types:

- `FieldBean` with public field `color`;
- `GetterBean` with private field and public getter `getColor()`.

`DynamicLinkerFactory` by default creates a linker capable of handling JavaBeans. Both Simple and Chained read `GET:PROPERTY:color`, but cache according to two different policies. The code uses `dynamicInvoker()` directly, so **there is no need to generate the `invokedynamic` opcode** in the example file.

Create file **DynalinkCallSitesDemo.java**:

~~~java
import java.lang.invoke.CallSite;
import java.lang.invoke.MethodHandle;
import java.lang.invoke.MethodHandles;
import java.lang.invoke.MethodType;
import java.util.ArrayList;
import java.util.List;

import jdk.dynalink.CallSiteDescriptor;
import jdk.dynalink.DynamicLinker;
import jdk.dynalink.DynamicLinkerFactory;
import jdk.dynalink.Operation;
import jdk.dynalink.StandardNamespace;
import jdk.dynalink.StandardOperation;
import jdk.dynalink.support.ChainedCallSite;
import jdk.dynalink.support.SimpleRelinkableCallSite;

public class DynalinkCallSitesDemo {
    public static class FieldBean {
        public final String color;

        public FieldBean(String color) {
            this.color = color;
        }
    }

    public static class GetterBean {
        private final String color;

        public GetterBean(String color) {
            this.color = color;
        }

        public String getColor() {
            return color;
        }
    }

    private static String run(
            CallSite site, Object[] receivers) throws Throwable {
        MethodHandle invoker = site.dynamicInvoker();
        List<String> values = new ArrayList<>();

        for (Object receiver : receivers) {
            Object color = invoker.invokeWithArguments(receiver);
            values.add(String.valueOf(color));
        }
        return String.join(" | ", values);
    }

    public static void main(String[] args) throws Throwable {
        DynamicLinkerFactory factory = new DynamicLinkerFactory();
        DynamicLinker linker = factory.createLinker();

        Operation operation = StandardOperation.GET
                .withNamespace(StandardNamespace.PROPERTY)
                .named("color");

        MethodType type = MethodType.methodType(
                Object.class, Object.class);

        CallSiteDescriptor descriptor = new CallSiteDescriptor(
                MethodHandles.lookup(), operation, type);

        SimpleRelinkableCallSite simple = linker.link(
                new SimpleRelinkableCallSite(descriptor));

        ChainedCallSite chained = linker.link(
                new ChainedCallSite(descriptor));

        Object[] receivers = {
                new FieldBean("red"),
                new GetterBean("green"),
                new FieldBean("blue"),
                new GetterBean("yellow")
        };

        System.out.println("simple: " +
                run(simple, receivers));
        System.out.println("chained: " +
                run(chained, receivers));
        System.out.println("site type: " + simple.type());
        System.out.println("same type: " +
                simple.type().equals(chained.type()));
    }
}
~~~

Compile/run with **JDK 17+**, enabling the `jdk.dynalink` module when using classpath:

~~~bash
javac --add-modules jdk.dynalink DynalinkCallSitesDemo.java
java --add-modules jdk.dynalink DynalinkCallSitesDemo
~~~

Expected stdout:

~~~text
simple: red | green | blue | yellow
chained: red | green | blue | yellow
site type: (Object)Object
same type: true
~~~

### Flow explanation

**Operation:** `StandardOperation.GET.withNamespace(StandardNamespace.PROPERTY).named("color")` describes reading a fixed property. Because the name `color` is already attached to `NamedOperation`, the call-site signature only takes the receiver, without needing a runtime name argument.

**MethodType:** `(Object)Object` allows the same site to accept different Java classes. The return type in the descriptor is `Object` even though the actual getter may return `String` or a primitive, because the linker can adapt the handle accordingly.

**Descriptor:** `CallSiteDescriptor` holds lookup, operation, and type so the linker knows what to do when a new receiver appears. It does not contain the specific receiver of each call.

**Linking:** `linker.link(site)` sets up the initial relink-and-invoke method handle, typically deferring specialization until the actual call. Afterward, the site can relink throughout its lifetime.

**Invocation:** `site.dynamicInvoker()` creates a MethodHandle that uses the site's current target, unlike capturing a target that does not follow subsequent relinks. Each `invokeWithArguments(receiver)` executes the operation for the actual receiver.

**Result:** the two sites return the same colors according to the object data. However, Simple only keeps one specialization at a time, whereas Chained can remember the matching branches for both classes. The demo does not print the relink count because that number depends on the runtime's guard and linking policy, not an API constant.

`FieldBean` and `GetterBean` are declared public static so `BeansLinker` can use the public members under the appropriate access mechanism. If changed to private inner classes or used in a module that does not export the package, lookup permissions and accessibility during linking must be reviewed.

### Module jdk.dynalink

`jdk.dynalink` is a JDK module that is not always resolved by default for applications running on the classpath; therefore the example specifies both `javac --add-modules` and `java --add-modules`. If the project is a named module, it can declare:

~~~java
module example.runtime {
    requires jdk.dynalink;
}
~~~

This is an **illustrative module-info.java**, not a file that needs to be added to the classpath demo above. For a named module, sources/build must also be placed in the proper JPMS layout.

## 11. Complete Java 17+ Example 2: Clearly simulating relink, reset, and eviction

In the following program, we **supply guarded invocations ourselves**:

- `isText` only accepts `String`;
- `isNumber` accepts `Integer`;
- `isLong` accepts `Long`.

The three targets return different strings. The fallback `miss` intentionally returns the string `"<miss>"` instead of calling the linker. Thus the program directly tests the property of **what the cache retains after relink**.

**Limitation to understand:** because `DynamicLinker.link(site)` is not called, this is only a **simulation of the call site protocol**, not a full self-linking Dynalink runtime. When a guard fails, the dummy callback only prints miss and does not attempt to find a new target. In production, Dynalink supplies an appropriate `relinkAndInvoke` fallback to relink automatically.

Create file **RelinkProtocolDemo.java**:

~~~java
import java.lang.invoke.MethodHandle;
import java.lang.invoke.MethodHandles;
import java.lang.invoke.MethodType;

import jdk.dynalink.CallSiteDescriptor;
import jdk.dynalink.StandardNamespace;
import jdk.dynalink.StandardOperation;
import jdk.dynalink.linker.GuardedInvocation;
import jdk.dynalink.support.ChainedCallSite;
import jdk.dynalink.support.SimpleRelinkableCallSite;

public class RelinkProtocolDemo {
    static class TwoEntryChain extends ChainedCallSite {
        TwoEntryChain(CallSiteDescriptor descriptor) {
            super(descriptor);
        }

        @Override
        protected int getMaxChainLength() {
            return 2;
        }
    }

    public static boolean isText(Object x) {
        return x instanceof String;
    }

    public static Object text(Object x) {
        return "text:" + x;
    }

    public static boolean isNumber(Object x) {
        return x instanceof Integer;
    }

    public static Object number(Object x) {
        return "int:" + x;
    }

    public static boolean isLong(Object x) {
        return x instanceof Long;
    }

    public static Object longValue(Object x) {
        return "long:" + x;
    }

    public static Object miss(Object x) {
        return "<miss>";
    }

    private static GuardedInvocation guarded(
            MethodHandles.Lookup lookup,
            String invocationName,
            String guardName) throws ReflectiveOperationException {

        MethodHandle action = lookup.findStatic(
                RelinkProtocolDemo.class,
                invocationName,
                MethodType.methodType(Object.class, Object.class));

        MethodHandle guard = lookup.findStatic(
                RelinkProtocolDemo.class,
                guardName,
                MethodType.methodType(boolean.class, Object.class));

        return new GuardedInvocation(action, guard);
    }

    private static String call(
            java.lang.invoke.CallSite site, Object argument)
            throws Throwable {
        Object result = site.dynamicInvoker()
                .invokeWithArguments(argument);
        return String.valueOf(result);
    }

    public static void main(String[] args) throws Throwable {
        MethodHandles.Lookup lookup = MethodHandles.lookup();
        MethodType type = MethodType.methodType(
                Object.class, Object.class);

        CallSiteDescriptor descriptor = new CallSiteDescriptor(
                lookup,
                StandardOperation.GET
                    .withNamespace(StandardNamespace.PROPERTY)
                    .named("value"),
                type);

        MethodHandle fallback = lookup.findStatic(
                RelinkProtocolDemo.class, "miss", type);

        GuardedInvocation text = guarded(
                lookup, "text", "isText");
        GuardedInvocation integer = guarded(
                lookup, "number", "isNumber");
        GuardedInvocation longValue = guarded(
                lookup, "longValue", "isLong");

        SimpleRelinkableCallSite simple =
                new SimpleRelinkableCallSite(descriptor);
        simple.initialize(fallback);
        simple.relink(text, fallback);

        System.out.println("simple text: " +
                call(simple, "Ada"));

        simple.relink(integer, fallback);
        System.out.println("simple text after relink: " +
                call(simple, "Ada"));
        System.out.println("simple int: " +
                call(simple, 7));

        ChainedCallSite chain = new ChainedCallSite(descriptor);
        chain.initialize(fallback);
        chain.relink(text, fallback);
        chain.relink(integer, fallback);

        System.out.println("chain text: " +
                call(chain, "Ada"));
        System.out.println("chain int: " +
                call(chain, 7));

        chain.resetAndRelink(integer, fallback);
        System.out.println("chain text after reset: " +
                call(chain, "Ada"));
        System.out.println("chain int after reset: " +
                call(chain, 7));

        TwoEntryChain limited = new TwoEntryChain(descriptor);
        limited.initialize(fallback);
        limited.relink(text, fallback);
        limited.relink(integer, fallback);
        limited.relink(longValue, fallback);

        System.out.println("limited old text: " +
                call(limited, "Ada"));
        System.out.println("limited int: " +
                call(limited, 7));
        System.out.println("limited long: " +
                call(limited, 9L));
    }
}
~~~

Compile/run:

~~~bash
javac --add-modules jdk.dynalink RelinkProtocolDemo.java
java --add-modules jdk.dynalink RelinkProtocolDemo
~~~

Expected stdout (single-thread):

~~~text
simple text: text:Ada
simple text after relink: <miss>
simple int: int:7
chain text: text:Ada
chain int: int:7
chain text after reset: <miss>
chain int after reset: int:7
limited old text: <miss>
limited int: int:7
limited long: long:9
~~~

### Why does each line appear?

**Matching types:** Invocation MethodHandles are all `(Object)Object`; guards are all `(Object)boolean`; fallback is `(Object)Object`. Therefore, no adapters are needed in the demo.

**Initial Simple:** `simple.relink(text,fallback)` installs a text branch. When running `"Ada"`, guard `isText` passes, and the target returns `text:Ada`.

**Simple after relink:** `simple.relink(integer,fallback)` replaces the text branch with the integer branch. `isNumber("Ada")` fails so the fallback returns `<miss>`; integer 7 is handled by the integer branch as `int:7`.

**Chained after two relinks:** `chain.relink(text,fallback)` then `chain.relink(integer,fallback)` keeps both branches. `"Ada"` can pass past the failing integer guard and use the text guard; `7` uses the integer guard.

**Chained after reset:** `chain.resetAndRelink(integer,fallback)` requests dropping the old branches. Text no longer has a matching branch so it returns `<miss>`; integer still returns `int:7`.

**TwoEntryChain:** after linking text, integer, and long, the 2-entry chain retains the 2 recent linkages, causing the old text to be evicted. At this point 7 and `9L` still have specialized handles.

**Why is the operation named `value` when no class contains a `value` property?** Because the example intentionally constructs guarded invocations via MethodHandles and **does not call DynamicLinker to resolve that operation**. The descriptor is used to hold the call-site type and illustrate the API. In demo 1, the operation is actually resolved by `BeansLinker`.

**Why not use a dummy fallback in production?** Because when a new shape appears, the runtime must ask `DynamicLinker` to select a new specialization and invoke it, rather than returning `"<miss>"` as a normal business result if language semantics require property access.

## 12. MethodType must remain consistent after every update

Distinguish the signatures involved:

~~~text
Site (fixed):      (Object)Object
Invocation:        (Object)Object
Guard:             (Object)boolean
Relink fallback:   (Object)Object
~~~

In demo 2, the types already match. With a real language linker, the raw target may carry a more specific type, for example `(FieldBean)String`, and then be adapted to fit the `(Object)Object` call site through the `LinkerServices` mechanism.

**A call site does not change its signature because of relinking.** If the initial descriptor is `(Object)Object`, it remains so after being linked to a getter returning String, int, or another object. Do not confuse changing the target with changing the bytecode `MethodType`.

Debug pattern:

~~~java
MethodType siteType = site.type();
MethodType targetType = site.getTarget().type();
System.out.println("site: " + siteType);
System.out.println("target: " + targetType);
~~~

This is an **illustrative snippet**; `site` must be of type `CallSite` and already initialized. With `MutableCallSite`, a valid target needs to have a method type matching the site type. A guard has a boolean return type, so do not compare the guard type directly as if it were the target method.

If writing a custom call site and constructing a guard chain incorrectly, you may encounter `WrongMethodTypeException`, `ClassCastException`, or errors when setting the target. Always check parameter/return types and conversions at the linker boundary.

## 13. ResetAndRelink is not just another name for relink

Consider the state:

~~~text
Before:
  chain = [Integer, String, Boolean]

After relink(Double):
  chain = [Double, Integer, String, Boolean]
  (if not yet at limit and entries are still valid)

After resetAndRelink(Double):
  chain = [Double]
~~~

In `SimpleRelinkableCallSite`, both calls may look similar because Simple only holds one entry. In `ChainedCallSite`, the difference is significant: reset erases the accumulated PIC advantage.

Do not call reset on every guard miss in application code. Normally **DynamicLinker** decides when to request `resetAndRelink`, for example according to instability policies or linker state. For a call site that needs to retain multiple shapes, calling reset indiscriminately turns the cache into a “forget everything” strategy that causes excessive relinking.

`resetAndRelink` does not mean re-running the `invokedynamic` bootstrap. It is a request to **update the target of the same site**.

## 14. Two number 8s that are easy to confuse

There are two APIs with a default value of 8 but different roles.

### A. ChainedCallSite.getMaxChainLength()

This is the **limit on the number of guarded invocations** in the PIC. Default is 8; a subclass can override it to choose 2, 4, 16... depending on the workload. Choosing too large a value increases guard probing cost and code size.

### B. DynamicLinkerFactory.setUnstableRelinkThreshold(int)

This is the **threshold for the number of relinks** after which a call site may be marked unstable and subsequent link requests receive this signal. Per the JDK 17 API, default is 8, and a value of 0 means not marking unstable via that threshold.

~~~java
DynamicLinkerFactory factory = new DynamicLinkerFactory();
factory.setUnstableRelinkThreshold(8);
DynamicLinker linker = factory.createLinker();
~~~

This is an **illustrative snippet**, requiring imports and used before `createLinker()`. The value 8 here **does not** control the number of branches in `ChainedCallSite`. A site with maxChainLength 2 can still relink more than 8 times across many shapes; a site with maxChainLength 8 might relink only once.

Do not set the threshold to 0 or an excessively large number just to “eliminate relinks”: guard misses and invalidation still exist, and the unstable threshold mainly informs the linker policy of the site's status.

## 15. SwitchPoint and invalidating exceptions

A specialization can become invalid **even when the receiver is still the same class**. For example, a runtime allows changing a prototype or property definition after an optimized handle has been created.

`GuardedInvocation` can use `java.lang.invoke.SwitchPoint` to mark that an assumption is still true. When the runtime invalidates the switch point, the corresponding guarded invocation is no longer valid.

~~~text
Before:
  guard shape X + switchpoint valid
  → fast getter is applicable

Runtime:
  property definition changes
  SwitchPoint.invalidateAll(...)

After:
  old assumption invalid
  → fallback/relink for updated semantics
~~~

This is a diagram, not a complete program. If the application only changes the value of a field and the old getter is still valid, it is not necessary to invalidate the specialization. Invalidation is for changes to assumptions about **how the operation works**, not every data change.

`GuardedInvocation` can also declare an exception class that triggers invalidation. When the specialized invocation throws that exception type, the linking mechanism can discard the specialization and re-select. Do not mark an overly broad `RuntimeException` as an “invalidating exception” if you still want to distinguish real business errors; this can cause confusing relinks and mask the root cause.

## 16. Chained is not a per-access LRU cache

The chained cache order is **most recently linked first**. Per the API, invocations do not reorder themselves when a guard is hit.

~~~text
Chain: [C, B, A]

Input C:
  guard C → true          (1 guard)

Input B:
  guard C → false
  guard B → true          (2 guards)

Input A:
  guard C → false
  guard B → false
  guard A → true          (3 guards)
~~~

Therefore, if A is extremely “hot” but was linked very early and sits at the end of the chain, it can return the right result while having to go through several checks. Chained helps reduce relinks in small polymorphic workloads, without guaranteeing O(1) lookup like a hash map.

When the chain is full, an old evicted type can reappear and be newly linked at the head. PIC is a **bounded optimization policy**, not a closed-set type support capability.

## 17. Concurrency and MutableCallSite visibility

`ChainedCallSite` has a relink mechanism that is safe under concurrent updates from multiple threads. When a race occurs, a specialization linked by a “losing” thread may be discarded, leading to re-linking a similar type in the future. Do not require a relink counter to equal exactly 1 across all multithreaded execution schedules.

However, there is another problem: **visibility of target changes**. Both implementations inherit from `MutableCallSite`, where target updates must obey the Java memory model. `DynamicLinkerFactory` provides an option:

~~~java
DynamicLinkerFactory factory = new DynamicLinkerFactory();
factory.setSyncOnRelink(true);
DynamicLinker linker = factory.createLinker();
~~~

This is an illustrative snippet. `setSyncOnRelink(true)` instructs the linker to perform `MutableCallSite.syncAll(...)` after relinking, supporting visibility rules for threads sharing the site. It has its own cost, so a multithreaded runtime needs to configure and measure accordingly.

**Do not infer** that concurrency-safe relinking means the target object being called, custom linker, guard, or mutable application state are automatically thread-safe. Those are separate synchronization scopes.

## 18. When to choose Simple vs. Chained?

Metrics should be collected **per call site**, rather than choosing a single policy by intuition alone.

| Traffic pattern | Initial guess |
| --- | --- |
| Site only sees A | Simple is usually reasonable |
| Site sees A/A/A and very rarely B | Simple may suffice |
| A, B alternate frequently | Chained usually reduces relinks |
| Stable A/B/C/D | Chained can keep PIC effective |
| Dozens/hundreds of shapes | Both will miss; measure and consider another strategy |
| Links invalidated frequently | Check switchpoints/reset and link cost |
| Shared by many threads | Check synchronization along with relink cost |
| A “hot” type sits at the end of the chain | Guard check cost may be disadvantageous |

Metrics to measure: invocation count, link requests, guard misses, reset events, chain eviction, invalidation, cost per link, JIT warm-up, p95 latency, and memory cost. For benchmarks, separate *cold linkage* (first time) and *steady state* (after warm-up). Do not compare the speed of a single initial call and declare Simple/Chained absolutely optimal.

If you need to build a custom call-site policy, consider a custom subclass of `ChainedCallSite` to change max chain before writing a full `RelinkableCallSite` implementation; that preserves the existing guard/invalidation semantics.

## 19. When implementing RelinkableCallSite yourself

A custom implementation outside the two built-ins must fully satisfy:

1. Has a `CallSiteDescriptor` and does not arbitrarily alter the `Operation`/`MethodType` of the call site.
2. `initialize(relinkAndInvoke)` sets up an initial target with the right signature.
3. `relink(...)` attaches the new linkage without breaking guards, switchpoints, and exception invalidation.
4. `resetAndRelink(...)` discards old state as requested; does not silently retain cleared assumptions.
5. The final fallback of the chain is the linker callback with the matching `MethodType`.
6. Method handles must be adapted to match the call-site type, not just match parameter count.
7. Chain/cache does not grow unboundedly; has eviction and memory lifecycle policies.
8. Updating the call site and reading the cache under concurrency requires proper memory consistency.
9. Do not hold references to generated classloaders too long if the runtime needs to unload plugins.
10. Test guard pass/miss, re-entry, invalidation, reset, multi-shape, and thread contention.

You should not create a `GuardedInvocation` without a guard when the target only handles one class: the site could apply that handle to a different receiver and throw an error instead of falling back properly.

## 20. Dynalink and MethodHandles.guardWithTest

At the low level, `MethodHandles.guardWithTest(test, target, fallback)` creates a conditional branching handle:

~~~text
if test(argument):
    return target(argument)
else:
    return fallback(argument)
~~~

This is **pseudocode**, not complete Java source. Dynalink builds a framework around this primitive:

~~~text
Operation (GET:PROPERTY:color)
            |
CallSiteDescriptor
            |
DynamicLinker + GuardingDynamicLinker
            |
GuardedInvocation
            |
RelinkableCallSite (policy)
            |
CallSite.dynamicInvoker()
~~~

With `ChainedCallSite`, multiple guarded branches can be arranged into a chain. With `SimpleRelinkableCallSite`, only one guarded branch is active at a time. Thus Dynalink does not replace `MethodHandle`; it **selects, adapts, and updates** method handles for high-level operations.

If you only need to call a fixed method with a known type, a Java method call or `MethodHandles.Lookup.findVirtual` is usually simpler than creating a Dynalink pipeline. Dynalink is useful when receiver shapes and operations are only decided at runtime.

## 21. Integrating with invokedynamic bootstrap

When a language runtime compiles dynamic source into a JVM classfile, the `invokedynamic` bootstrap can create the call site:

~~~java
// Illustrative snippet; dynamicLinker and parseOperation
// must be provided by the runtime.
public static java.lang.invoke.CallSite bootstrap(
        MethodHandles.Lookup lookup,
        String name,
        MethodType type) {
    Operation op = parseOperation(name);
    CallSiteDescriptor desc =
            new CallSiteDescriptor(lookup, op, type);

    return dynamicLinker.link(new ChainedCallSite(desc));
}
~~~

**Does not run standalone:** the `dynamicLinker` variable/field and `parseOperation` method are not defined in the snippet. Dynalink does not automatically parse the string `"GET:PROPERTY:color"` if the runtime has not defined how names are encoded/decoded.

Once the JVM has the call site, calls with new receivers can cause guards to fail and relink. This updates **the target of the existing site**, which does not mean the bootstrap must re-execute on every type change.

It is also possible to use Dynalink in an interpreter without generating bytecode by creating a `SimpleRelinkableCallSite` or `ChainedCallSite` in Java source, calling `DynamicLinker.link`, and then using `dynamicInvoker()`, as in demo 1.

## 22. Common error matrix

| Symptom | Common reason | Check |
| --- | --- | --- |
| `package jdk.dynalink does not exist` | Module not resolved | `--add-modules jdk.dynalink` or `requires jdk.dynalink` |
| Site does not run when called | Forgot `DynamicLinker.link(site)` or wrong initial callback | Check initialize and target |
| Simple relinks continuously | Alternating A/B or overly narrow guard | Receiver distribution, guard miss count |
| Chained still relinks frequently | Chain overflow, reset, invalidation, or guard mismatch | `getMaxChainLength()`, assumptions |
| Old type missing after reset | Reset literally discards prior linkage | Distinguish from `relink` |
| `WrongMethodTypeException` | Method types between target/site do not match | Print `site.type()`, `getTarget().type()` |
| `ClassCastException` on receiver switch | Missing guard or wrong adapter cast | Check runtime class, LinkerServices |
| Property name not found | Wrong namespace/member visibility | Use proper `GET:PROPERTY`, check getter/field access |
| Used `named("color")` but still passing name argument | Confusing fixed name with dynamic-name slot | Fixed getter descriptor usually only needs receiver |
| Assuming PIC is an unbounded cache | Default 8, eviction, invalidation | Monitor number of shapes |
| Seeing old target in another thread | MutableCallSite visibility, linker synchronization | Check `setSyncOnRelink` |
| Plugin loader retained forever | Handles/cache still reference class/loader | Manage lifecycle of site and linker |
| Benchmark slow despite few misses | Long guard chain, cold JIT | Measure warm-up, guard cost, and profile |

Do not catch every exception and “relink” as a universal solution. Business operation errors, operation resolution errors, and designated invalidation exceptions have different meanings.

## 23. Self-check questions with answers

**1. Is `RelinkableCallSite` a specific cache type or an interface?**  
**Answer:** A protocol interface for `DynamicLinker` to manage call sites; Simple and Chained are two implementations.

**2. How many guarded invocations can Simple hold at the same time?**  
**Answer:** One, following the monomorphic inline cache strategy.

**3. How many entries does Chained hold by default?**  
**Answer:** 8; `getMaxChainLength()` can be overridden in a subclass.

**4. Does Chained automatically move a just-hit branch to the head?**  
**Answer:** No; ordering is based on **link** time, newest linked first, not reordered on hit.

**5. Why can A,B,A,B traffic be disadvantageous for Simple?**  
**Answer:** When A's guard does not apply to B, the single-entry cache must replace with B; when A returns, it usually has to relink.

**6. If Chained already holds A and B, is the next A guaranteed to hit?**  
**Answer:** Only if the guard and assumptions are still valid and the branch has not been evicted/reset; it cannot be unconditionally guaranteed.

**7. Who supplies `relinkAndInvoke` for a normal Dynalink site?**  
**Answer:** `DynamicLinker`, during `link(site)` and relinking.

**8. What is `initialize` for?**  
**Answer:** Installs the initial callback target for the call site, allowing specialization to be deferred until the call with actual arguments.

**9. How does `relink` differ from `resetAndRelink`?**  
**Answer:** Relink may keep valid old linkages; resetAndRelink requests discarding prior linkage state and rebuilding with the new linkage.

**10. Why does the fallback in demo 2 only return `<miss>`?**  
**Answer:** It is a simulated fallback, not a DynamicLinker callback; the demo is used to observe the cache, not to auto-link on miss.

**11. Why doesn't `CallSiteDescriptor` contain the value `color="red"`?**  
**Answer:** It holds the operation, lookup, and type; the field value belongs to the receiver instance and is read at invocation time.

**12. Does `(Object)Object` automatically change to `(FieldBean)String` after linking?**  
**Answer:** No, the call-site type is fixed. The internal handle can be adapted to that type.

**13. When does a switch point cause a relink even though the receiver class has not changed?**  
**Answer:** When an assumption outside the class type is no longer valid, such as a modified layout/prototype.

**14. Do the PIC limit of 8 and the unstable relink threshold of 8 have the same meaning?**  
**Answer:** No. One is the number of cached guarded invocations; the other is the relink count threshold for marking instability.

**15. Does adding `setSyncOnRelink(true)` solve application-wide thread safety?**  
**Answer:** No; it relates to the visibility of MutableCallSite target updates, and does not automatically protect receiver/linker state.

**16. If a target has a type that does not match the descriptor, what must be done?**  
**Answer:** Adapt it properly via LinkerServices/MethodHandle adapters, checking method types before installation.

**17. Is it mandatory to generate invokedynamic bytecode to learn Dynalink?**  
**Answer:** No. Demo 1 uses `DynamicLinker.link` and `CallSite.dynamicInvoker()` directly in Java.

**18. Why isn't a long PIC necessarily faster?**  
**Answer:** It may have to test many guards per invocation, incurring CPU/JIT cost; many shapes also cause eviction.

**19. Does `GuardedInvocation` contain only an invocation handle or something else?**  
**Answer:** It can contain an optional guard, switch points, and an invalidating exception class.

**20. When should `ChainedCallSite` be chosen?**  
**Answer:** When a site frequently sees a small, repeating set of shapes, and the benefit of avoiding relinks outweighs the guard chain cost.

## 24. Implementation checklist

- [ ] Identify the right operation (`GET:PROPERTY`/`GET:ELEMENT`/`CALL`/`NEW`).
- [ ] Create the proper `CallSiteDescriptor` with lookup, operation, and MethodType.
- [ ] Create `DynamicLinker` before linking the site.
- [ ] Use `link(site)` so the initial target knows how to relink when receiving arguments.
- [ ] Choose Simple for nearly monomorphic sites; Chained for small, repeating polymorphism.
- [ ] If subclassing Chained, keep `getMaxChainLength() >= 1`.
- [ ] Clearly understand guard, invocation, invalidation, and fallback.
- [ ] Do not conflate guard misses with business exceptions.
- [ ] Do not call `resetAndRelink` when wanting to keep old branches.
- [ ] Verify that the site type does not change across relinks.
- [ ] Measure relink counts, guard misses, eviction, and latency instead of comparing stdout alone.
- [ ] For multithreading, check `setSyncOnRelink` and synchronization in custom linkers/receivers.
- [ ] Provide the `jdk.dynalink` module properly at compile/runtime.
- [ ] Check classloader lifecycle if linking to dynamically generated classes.
- [ ] Test the cache with A/A, A/B/A/B inputs, more types than chain length, invalidation, and reset.

## 26. Conclusion

`RelinkableCallSite` defines the **update protocol** that `DynamicLinker` uses for a dynamic call site. `SimpleRelinkableCallSite` holds one guarded specialization, suitable when a site almost only sees one shape; `ChainedCallSite` holds multiple guarded invocations as a PIC, default maximum 8, to reuse specializations across multiple shapes.

The most important distinction is **keeping or forgetting old linkages**. `relink` can append to the chain, whereas `resetAndRelink` requests discarding accumulated state. When a guard misses, DynamicLinker's fallback is responsible for finding and installing a new specialization, not running the bootstrap indefinitely or changing the call-site signature.

Understanding **descriptor → initial fallback → GuardedInvocation → guard pass/miss → relink/reset → cached target** will help you design, read, and debug runtime dispatch properly, while choosing a cache strategy based on real data.
