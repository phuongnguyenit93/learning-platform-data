# 13.8. Observing javap and Separating Language Contracts from javac-Generated Details

## Lesson Objectives

After this lesson, you can:

- Use `javac` and `javap` to observe bytecode, the constant pool, compiler-generated methods, and the `BootstrapMethods` table of a class containing **lambdas**, **method references**, and **string concatenation with the + operator**.
- Explain why a test compilation may contain `invokedynamic`, `LambdaMetafactory`, `StringConcatFactory`, methods named `lambda$...`, or `StringBuilder`, yet **specific bytecode names and shapes are not the Java source contract**.
- Read the descriptor of an `invokedynamic` to distinguish **captured variables** at lambda creation time from **SAM parameters** when invoking the lambda.
- Distinguish what is guaranteed by the Java Language Specification (JLS) (functional interface target type, capture rules, expression evaluation order, concatenation result) from compiler/JDK/JVM choices.
- Perform repeatable checks, compare `--release 8` and `--release 17` fairly, and avoid drawing conclusions about performance or object identity from `javap` alone.

**Context:** Java Advance – dynamic-runtime; parent topic is **Lambdas and String Concatenation**. Examples use Java 17+ and only read class files generated by the examples themselves. When working with another Java version, some bytecode details may change.

## 1. Three Layers to Separate

The reason to learn `javap` is to see that **the compiler made a specific choice**, not to turn that choice into the definition of the Java language.

~~~text
Java source:     () -> expr, Type::method, "x=" + value
      |
      | javac --release <version>
      v
Class file:      constant pool, Code, BootstrapMethods, invokedynamic...
      |
      | JVM verifier, linkage, runtime optimization / JIT
      v
Runtime behavior: invoking lambda, creating String, optimizing, garbage collection...
~~~

| Layer | Right question | Type of evidence |
| --- | --- | --- |
| **Java language (JLS)** | What target type does the lambda have? How are locals captured? What value does `+` with String produce? What is the operand evaluation order? | JLS rules, behavioral tests |
| **Class file (JVMS + javac output)** | What bytecode does this compiler emit? Is there `invokedynamic`? Where does `BootstrapMethods` point? | `javap -c -p -v`, `javap -s`, class file |
| **Runtime and JIT** | Which runtime object/class implements the lambda? Is there allocation, inlining, or constant folding at runtime? | Profiling/JFR/JMH tools, relevant JVM specs |

**Do not conflate:** `javap` is a **class file** disassembler, not a tool for displaying actual JIT machine code. An `invokedynamic` line in a class file does not prove the JVM executes a bootstrap method on every call. A `new StringBuilder` line does not prove the runtime must allocate a physical `StringBuilder` object on every execution.

### 1.1. What does “language contract” mean?

It is the behavior that a valid Java program must exhibit according to the specification, regardless of how the compiler chooses to lower source to bytecode. For example:

- A lambda is **typed according to a functional interface** in an appropriate context.
- A local variable from the enclosing scope used by a lambda must be `final` or **effectively final** (for locals/parameters that need to be captured).
- String concatenation with `+` must produce the **String value corresponding to the string conversion** of the operands and preserve Java's evaluation rules.
- A String expression that is a **compile-time constant expression** when meeting JLS conditions has the corresponding compile-time constant behavior.

Conversely, the private helper name `lambda$makeAdder$0`, index `#19` in the constant pool, the character recipe for `StringConcatFactory`, or the runtime's use of a hidden class are all **not source APIs** for applications to rely on.

### 1.2. What do “javac-generated details” mean?

Given a specific `javac` version, a specific target version, and a specific piece of source code, the compiler emits a specific class file. The details may include:

- One or more `invokedynamic` instructions and `CONSTANT_InvokeDynamic` entries.
- A bootstrap method handle to `java/lang/invoke/LambdaMetafactory.metafactory`, `altMetafactory`, or `StringConcatFactory.makeConcatWithConstants`.
- An auxiliary private method to hold the lambda body.
- How a chain of `+` concatenations is split or merged into call sites.
- Bytecode choices such as `ldc`, `invokevirtual`, `invokestatic`, `StringBuilder.append`.
- Constant-pool indices, synthetic method names, bootstrap entry order, synthetic flags, and bytecode offsets.

Observing them is useful when debugging, auditing bytecode, learning JVM mechanisms, and studying performance. However, application APIs should not require `javap` output to remain identical line-for-line across JDK versions.

## 2. Minimal javac / javap Toolkit

`javac` compiles source into `.class`; `javap` reads that class file. You can check versions:

~~~bash
java -version
javac -version
javap -version
~~~

The commands below assume **JDK 17 or later**, and we explicitly select Java 17 for the test run:

~~~bash
javac --release 17 -encoding UTF-8 LambdaConcatObservation.java EvaluationOrderDemo.java
java LambdaConcatObservation
java EvaluationOrderDemo
javap -c -p LambdaConcatObservation
javap -v -p LambdaConcatObservation
javap -c -p EvaluationOrderDemo
~~~

Meaning of the options:

| Option | Effect | Notes |
| --- | --- | --- |
| `javac --release 17` | Selects source semantics, target classfile, and public platform APIs corresponding to release 17 | Does not mean the compiler executes the exact algorithm of `javac` version 17 |
| `javac -encoding UTF-8` | Reads source as UTF-8 | Keeps behavior consistent when comments/text contain Vietnamese characters |
| `javap -c` | Displays instructions of methods that have a Code attribute | Does not automatically show full BootstrapMethods |
| `javap -p` | Displays private members as well | Useful to see `lambda$...` helpers |
| `javap -v` | Displays verbose information: constant pool, flags, BootstrapMethods... | Long output; index numbers may change |
| `javap -s` | Prints JVM descriptors | Useful when it is hard to distinguish source types from descriptors |
| `javac -g` and `javap -l` | Adds/views line and local-variable debug information | Debug metadata does not define semantics |

If classes are in a separate output directory:

~~~bash
# Shell command fragment: class compiled into out17.
javap -c -p -classpath out17 LambdaConcatObservation
~~~

Avoid accidentally disassembling a class with the same name located elsewhere on the classpath. In projects with multiple modules, jars, or classloaders, verify which class file is being read before drawing conclusions.

### 2.1. Why fix the release and record the actual JDK?

Two variables affect comparisons:

1. **Target release**: for example `--release 8` versus `--release 17`. It affects the classfile target and may affect the bytecode emission strategy.
2. **Running compiler version**: `javac 17`, `javac 21`, `javac 24`... They may select the same target 17 yet still be allowed to change detailed emission within the specification's limits.

A responsible observation report should record: **compiler version, `--release`, source, javap command, and the inspected classfile snippet**. Do not write “Java 17 must generate the exact method `lambda$...`” just because you saw it in one test run.

## 3. Runnable Example 1: Lambdas, Method References, and String Concatenation

Save the following verbatim as **LambdaConcatObservation.java**.

~~~java
import java.util.Locale;
import java.util.function.Function;
import java.util.function.IntUnaryOperator;
import java.util.function.Supplier;

public class LambdaConcatObservation {
    private static String shout(String text) {
        return text.toUpperCase(Locale.ROOT);
    }

    static IntUnaryOperator makeAdder(int step) {
        return input -> input + step;
    }

    static IntUnaryOperator makeDoubler() {
        return input -> input * 2;
    }

    static String format(String name, int count) {
        return "item=" + name + ", count=" + count;
    }

    public static void main(String[] args) {
        IntUnaryOperator doubleIt = makeDoubler();
        IntUnaryOperator addFive = makeAdder(5);
        Function<String, String> ref = LambdaConcatObservation::shout;
        Supplier<String> greeting = () -> "hello";
        String constant = "ab" + "cd";
        String missing = null;

        System.out.println("double=" + doubleIt.applyAsInt(7));
        System.out.println("addFive=" + addFive.applyAsInt(7));
        System.out.println("ref=" + ref.apply("java"));
        System.out.println("supplier=" + greeting.get());
        System.out.println("concat=" + format("A", 3));
        System.out.println("constant=" + constant);
        System.out.println("missing=" + ("value=" + missing));
    }
}
~~~

Compile and execute:

~~~bash
javac --release 17 -encoding UTF-8 LambdaConcatObservation.java
java LambdaConcatObservation
~~~

**Exact stdout**:

~~~text
double=14
addFive=12
ref=JAVA
supplier=hello
concat=item=A, count=3
constant=abcd
missing=value=null
~~~

First things to verify **without looking at bytecode**:

- `makeDoubler` returns an `IntUnaryOperator` that applies multiplication by two.
- `makeAdder(5)` returns an `IntUnaryOperator` whose body uses the captured value `step=5`.
- `LambdaConcatObservation::shout` is a method reference matching the functional type `Function<String,String>`.
- `"ab" + "cd"` is a constant expression; the program prints `abcd`.
- `"value=" + missing` converts the `null` reference into the four characters `null` via string conversion.

**This is the behavior that must be preserved when changing compilers**, even if the classfile implementation differs.

## 4. Reading javap -c: Where invokedynamic Appears and Where It Is Not Needed

Run:

~~~bash
javap -c -p LambdaConcatObservation
~~~

In a test compilation targeting release 17, `makeAdder` typically has this shape:

~~~text
static java.util.function.IntUnaryOperator makeAdder(int);
  Code:
     0: iload_0
     1: invokedynamic #19,  0  // InvokeDynamic #0:applyAsInt:(I)Ljava/util/function/IntUnaryOperator;
     6: areturn
~~~

Whereas `makeDoubler` typically has:

~~~text
static java.util.function.IntUnaryOperator makeDoubler();
  Code:
     0: invokedynamic #23,  0  // InvokeDynamic #1:applyAsInt:()Ljava/util/function/IntUnaryOperator;
     5: areturn
~~~

**The numbers `#19`, `#23`, `#0`, `#1`, and offsets `0/1/6` are illustrative from one build, not fixed numbers of Java 17.** Looking at instruction names, descriptors, and bootstrap mappings is what is meaningful.

### 4.1. Capturing lambda: signs in the descriptor

With source:

~~~java
// Fragment taken from makeAdder(int step):
return input -> input + step;
~~~

`step` comes from outside the lambda body. When creating the lambda, the compiler must arrange for the **captured value** to reach the implementation. In the sample javap:

~~~text
invokedynamic ... applyAsInt:(I)Ljava/util/function/IntUnaryOperator;
~~~

The descriptor `(I)Ljava/util/function/IntUnaryOperator;` at the **factory site** means:

- `(I)`: at the time of creating the functional object, the call site receives **one captured int** (`step`).
- `L...IntUnaryOperator;`: the result of the factory site is a reference of type `IntUnaryOperator`.

**Do not misread** `(I)` in the factory descriptor as “the `input` parameter of `applyAsInt`”. The SAM `IntUnaryOperator.applyAsInt(int)` still takes an `int input` when the lambda is invoked later. There are two different moments:

~~~text
Create lambda:   makeAdder(5)     -> factory invokedynamic(step = 5)
Invoke lambda:   op.applyAsInt(7) -> body uses input=7 and step=5
Result:          12
~~~

A `javac` version may generate a private helper of the form:

~~~text
private static int lambda$makeAdder$0(int, int);
  Code:
     0: iload_1
     1: iload_0
     2: iadd
     3: ireturn
~~~

The helper receives both the captured `step` and the invocation parameter `input`. However, **the name `lambda$makeAdder$0` and the order of helper-generated methods are javac details**, not something an application should call via reflection by name.

### 4.2. Non-capturing lambda: descriptor may have no capture input

`makeDoubler` has the body:

~~~java
// Fragment from the program:
return input -> input * 2;
~~~

It uses no local variable from the enclosing method. Therefore the observed build has the factory descriptor:

~~~text
()Ljava/util/function/IntUnaryOperator;
~~~

There is no `int step` to pass to the factory. In the test, javac generated the helper:

~~~text
private static int lambda$makeDoubler$0(int);
~~~

However, **do not infer from an empty descriptor that every call to `makeDoubler()` must return the same object instance**. The JLS allows implementations to reuse or create functional objects; reference equality `==` of two lambda objects **is not a tool** to determine whether they have the same behavior.

If the semantic requirement is “two identical operations”, compare the business contract rather than using the identity of a lambda expression.

### 4.3. Method reference: seeing a different linkage

Source:

~~~java
// Fragment from main:
Function<String, String> ref = LambdaConcatObservation::shout;
~~~

In one build, `javap` for `main` shows an `invokedynamic` creating a `Function`; `BootstrapMethods` may point directly to `LambdaConcatObservation.shout` via a `MethodHandle`.

There does not necessarily have to be a new method named `lambda$main$...()` just to forward this call. **Method references are still subject to Java's target typing rules**, but the compiler may choose to encode the implementation handle differently from a lambda expression containing a body.

What must be learned is **the selected method and the functional interface contract**, not “method references never have a helper” or “are always faster than lambdas”.

### 4.4. Why is there lambda$main$0?

In the example, the expression:

~~~java
// Fragment from main:
Supplier<String> greeting = () -> "hello";
~~~

has a lambda body. The test javac generated a separate method to hold the body:

~~~text
private static java.lang.String lambda$main$0();
  Code:
     0: ldc  // String hello
     2: areturn
~~~

The helper name here **depends on the compiler**, and may change with method ordering or optimizations. Do not write APIs that depend on this method, do not hardcode `Class.getDeclaredMethod("lambda$main$0")`, and do not assume helpers always have a strict one-to-one correspondence with lambdas.

Furthermore, seeing a private helper with `javap -p` does not mean the source directly declared it. To inspect synthetic flags, use `javap -v -p` and check the relevant flags; when reading compiled bytecode, distinguish source methods from compiler-generated artifacts.

## 5. Reading javap -v: BootstrapMethods, the Constant Pool, and Two Kinds of Bootstraps

`javap -c` tells you an `invokedynamic` instruction exists. To know **where the linkage goes**, run:

~~~bash
javap -v -p LambdaConcatObservation
~~~

Look in three places:

1. **Constant pool:** the `InvokeDynamic` line points to a bootstrap method index and a `NameAndType`.
2. **Method's Code:** the `invokedynamic` instruction uses that constant-pool entry.
3. **BootstrapMethods:** the entry specifies a bootstrap method handle and static bootstrap arguments, which typically include an implementation handle or a concat recipe.

In the test build's output, the bootstrap names appear in this pattern:

~~~text
BootstrapMethods:
  ... REF_invokeStatic java/lang/invoke/LambdaMetafactory.metafactory:...
  ... REF_invokeStatic java/lang/invoke/StringConcatFactory.makeConcatWithConstants:...
~~~

The `...` in the block above **omits output for readability of the structure**; this is not a verbatim full dump and should not be used as golden test text. Run `javap -v` yourself to see the actual indices, descriptors, and static arguments of your build.

### 5.1. What does LambdaMetafactory do in the observed build?

When `javac` chooses the strategy of linking lambdas via `invokedynamic`, the bootstrap is usually `java.lang.invoke.LambdaMetafactory.metafactory` or a variant such as `altMetafactory`. It receives the linkage information: caller lookup, invokedynamic site name/type, SAM type, and implementation method handle; from that it produces a call site capable of producing an appropriate functional object.

It helps to distinguish:

~~~text
invokedynamic at the lambda CREATION site
    -> Bootstrap LambdaMetafactory
    -> strategy for creating the functional object

invokeinterface IntUnaryOperator.applyAsInt at the lambda INVOCATION site
    -> executes the SAM through the created object
~~~

Seeing `invokedynamic` at the factory site **does not mean every `applyAsInt` executes an `invokedynamic` instruction at the call site.** In the sample bytecode, `applyAsInt` appears as `invokeinterface` when the caller uses the object.

`LambdaMetafactory` is a standard JDK API/mechanism and is very important for understanding modern javac. However, the **lambda contract in Java source** does not require a compiled program to contain a `LambdaMetafactory.metafactory` entry, nor does it require a runtime class with a stable name.

### 5.2. What does StringConcatFactory do in the observed build?

The method:

~~~java
// Fragment from the program:
static String format(String name, int count) {
    return "item=" + name + ", count=" + count;
}
~~~

is lowered by a `javac --release 17` build to:

~~~text
static java.lang.String format(java.lang.String, int);
  Code:
     0: aload_0
     1: iload_1
     2: invokedynamic #26,  0  // InvokeDynamic #2:makeConcatWithConstants:(Ljava/lang/String;I)Ljava/lang/String;
     7: areturn
~~~

Here `aload_0` pushes `name`, `iload_1` pushes `count` onto the operand stack; the `invokedynamic` instruction has a signature taking `(String,int)` and returning `String`.

The name `makeConcatWithConstants` indicates that the bootstrap can receive a **recipe** combining fixed parts and placeholders for runtime operands. The recipe may contain special marker characters such as `\u0001` (runtime argument) and `\u0002` (bootstrap constant). This is the **protocol of StringConcatFactory**, not Java source syntax or characters the program prints itself.

Some cases may use `StringConcatFactory.makeConcat` or another approach, depending on how the compiler lowers the source. Do not treat `makeConcatWithConstants` as a mandatory rule of the `+` operator across all compilers.

### 5.3. Two invokedynamics with Different Purposes

| Aspect | Lambda factory site | String concat site |
| --- | --- | --- |
| Typical source | `n -> n * 2`, `Type::method` | `"item=" + name + count` |
| Observed behavior | Creates a functional value with a target type | Produces the concatenated String value |
| Sample bootstrap from javac | `LambdaMetafactory.metafactory` | `StringConcatFactory.makeConcatWithConstants` |
| Sample descriptor | `()IntUnaryOperator` or `(int)IntUnaryOperator` when capturing | `(String,int)String` |
| Exact bootstrap name guaranteed by JLS? | **No** | **No** |
| Observable with javap? | **Yes**, in classfiles with that form | **Yes**, in classfiles with that form |

What they share is the JVM's dynamic linkage mechanism via the `invokedynamic` instruction; what differs is the result type and language purpose. Do not equate “lambdas are StringConcatFactory” just because both use the same opcode.

## 6. What the JLS Actually Guarantees for Lambdas and Method References

### 6.1. Functional interfaces and target typing

A lambda like `x -> x + 1` **does not have an arbitrary context-independent object type**: Java uses *target typing* to identify an interface with a single abstract functional method (functional interface). For example:

~~~java
// Fragment, requires importing java.util.function.IntUnaryOperator.
IntUnaryOperator inc = x -> x + 1;
int answer = inc.applyAsInt(6); // 7
~~~

The contract is that `inc` can be used as an `IntUnaryOperator` with SAM `applyAsInt(int)`; there is no contract that the compiler must generate a private method named `lambda$...` with some exact descriptor.

### 6.2. Captured locals must be effectively final

In `makeAdder`, the parameter `step` is not reassigned after being received, so it is valid for the lambda to capture.

~~~java
// Valid fragment:
int step = 5;
IntUnaryOperator add = x -> x + step;
// step is not reassigned.
~~~

The snippet below **intentionally does not compile**, only to illustrate the rule:

~~~java
// INVALID fragment: local step is not effectively final.
int step = 5;
IntUnaryOperator add = x -> x + step;
step = 6; // compiler rejects the lambda capturing this variable
~~~

When mutable state is needed, you must choose an explicit state model (for example, a field of a captured object) and handle concurrency appropriately. Do not assume a lambda holds a “reference to a reassignable local stack slot”; that is not Java local capture semantics.

### 6.3. Lambda object identity is not a business contract

Two evaluations of the same lambda expression may produce the same or different objects depending on runtime/implementation choices. Therefore, do not build caching logic on:

~~~java
// Fragment that should not be used to determine semantics:
boolean same = ((Supplier<String>) () -> "hello")
        == ((Supplier<String>) () -> "hello");
~~~

Two separate lambda expressions in source are even less guaranteed to use the same object; comparing with `==` only reflects actual reference identity at runtime. Use the functional interface API or business keys if you need to determine equivalence.

**Similarly, the runtime class name of a lambda** may change. In modern JDKs, implementations may use hidden classes, and `getClass().getName()` is not a stable representation for serialization, whitelisting, or compatibility checks.

### 6.4. Method references are not guaranteed to be faster than lambdas

`LambdaConcatObservation::shout` and `s -> LambdaConcatObservation.shout(s)` can have the same behavior within an appropriate scope, but how javac wires the implementation handle and how the JVM optimizes them are not necessarily byte-for-byte equivalent. Do not draw performance conclusions from whether a method reference in an observed build has or lacks a `lambda$...` method.

Choose the form that expresses intent clearly, check null/receiver behavior for method reference forms that have a receiver, and use benchmarks for real bottlenecks.

## 7. What the JLS Guarantees for the + String Concatenation Operator

In Java, the `+` operator can be numeric addition or string concatenation. When one operand has type `String`, the operands are converted to the necessary String representation, and the result is concatenation according to the language rules.

### 7.1. Order and associativity

`+` is left-associative, so:

~~~java
// Expression-standalone fragment:
String first = 1 + 2 + "x"; // "3x": computes 1+2 numerically first
String second = "x" + 1 + 2; // "x12": concatenates from left to right
~~~

Do not apply a model where “all elements are converted to String and then concatenated” to cases where numeric additions appear before a String operand. Parentheses and operand types determine the semantics.

### 7.2. Null and string conversion

A null reference in string concatenation is represented by the four characters `null`:

~~~java
// Fragment:
String missing = null;
String result = "value=" + missing; // "value=null"
~~~

It does not throw `NullPointerException` merely because an operand is null, although calling a method on null yourself (for example `missing.toString()`) will fail. Converting arbitrary objects to strings may invoke `toString()` and is subject to that implementation's behavior; do not assume objects are immutable or that `toString` has no side effects.

### 7.3. Operand evaluation order still matters

Java evaluates operands in the specified order, even when the compiler folds the result into a single `invokedynamic` concat site. If operands have side effects, the call order must be preserved; a compiler cannot arbitrarily reorder method calls just because the concat bytecode uses a single bootstrap.

The second program in section 8 shows that `text("left")` is executed before `number("right",7)` and then produces the string `left:7`.

### 7.4. Constant folding is a separate case

`"ab" + "cd"` consists only of literals belonging to a constant expression, so the compiler can represent the value `"abcd"` directly; for String constant expressions, the JLS specifies compile-time evaluation. In the demo's `javap`, we see:

~~~text
ldc  #... // String abcd
~~~

This **does not prove that concatenations with runtime operands must also be folded**. When `name` and `count` are runtime variables, the output must still be correct, but the bytecode may use `StringConcatFactory`, `StringBuilder`, or another strategy.

## 8. Runnable Example 2: Evaluation Order, null, and Captured Locals

Save as **EvaluationOrderDemo.java**:

~~~java
public class EvaluationOrderDemo {
    private static String text(String name) {
        System.out.println("eval=" + name);
        return name;
    }

    private static int number(String name, int value) {
        System.out.println("eval=" + name);
        return value;
    }

    static String combine() {
        return text("left") + ":" + number("right", 7);
    }

    public static void main(String[] args) {
        System.out.println("combined=" + combine());
        String constant = "Java" + "17";
        System.out.println("folded=" + constant);
        String nullable = null;
        System.out.println("null=" + ("item=" + nullable));
        int captured = 3;
        java.util.function.IntUnaryOperator multiply = n -> n * captured;
        System.out.println("captured=" + multiply.applyAsInt(4));
    }
}
~~~

Compile and run:

~~~bash
javac --release 17 -encoding UTF-8 EvaluationOrderDemo.java
java EvaluationOrderDemo
~~~

**Exact stdout**:

~~~text
eval=left
eval=right
combined=left:7
folded=Java17
null=item=null
captured=12
~~~

Explanation:

1. The first operand calls `text("left")`, causing the line `eval=left`.
2. The last operand calls `number("right",7)`, causing the line `eval=right`.
3. The concatenation result must preserve the value `left:7`.
4. The constant expression `"Java" + "17"` yields `Java17`.
5. `nullable` is null, yet string concatenation still yields `item=null`.
6. `multiply` captures the local `captured=3` (effectively final), so `4*3=12`.

You can inspect the bytecode:

~~~bash
javap -c -p EvaluationOrderDemo
~~~

Observation may show `invokestatic text` before `invokestatic number`, then `invokedynamic` for concat, but **do not use instruction offset numbers as semantic assertions**. Better assertions are the listed stdout lines: order and values must still hold.

## 9. Controlled Experiment: javac --release 8 and --release 17

To see differences caused by **target release**, use the same simple source and compile **twice into different output directories**, avoiding overwriting each other's classfiles.

Save the file **ConcatTargetCompare.java**:

~~~java
public class ConcatTargetCompare {
  static String format(String name, int count) {
    return "item=" + name + ", count=" + count;
  }
  public static void main(String[] args) {
    System.out.println(format("A", 3));
  }
}
~~~

On a JDK recent enough to support both targets:

~~~bash
javac --release 8 -d out8 ConcatTargetCompare.java
javac --release 17 -d out17 ConcatTargetCompare.java

java -cp out8 ConcatTargetCompare
java -cp out17 ConcatTargetCompare

javap -c -classpath out8 ConcatTargetCompare
javap -c -classpath out17 ConcatTargetCompare
~~~

If your shell does not create folders when using `-d`, create `out8` and `out17` before running. On some very recent JDKs, `--release 8` may print deprecation/obsolete option warnings or drop support; **do not hardcode stderr as a contract**.

**Stdout of both runs**:

~~~text
item=A, count=3
~~~

In the controlled test with the available javac, `javap -c` produces typical output:

| Build | How concatenation is lowered in method format |
| --- | --- |
| `--release 8` | `new java/lang/StringBuilder`, multiple `append` calls, `toString` |
| `--release 17` | `invokedynamic` with linkage name `makeConcatWithConstants` |

Two illustrative excerpts:

~~~text
# Release 8 example — offsets and constant pool indices omitted:
new           ... // class java/lang/StringBuilder
invokespecial ... // StringBuilder.<init>
...
invokevirtual ... // StringBuilder.append
...
invokevirtual ... // StringBuilder.toString
~~~

~~~text
# Release 17 example — constant pool indices omitted:
aload_0
iload_1
invokedynamic ... // makeConcatWithConstants:(Ljava/lang/String;I)Ljava/lang/String;
areturn
~~~

**Right conclusion:** The same source can be lowered by javac using different classfile strategies when the target release changes, while **the meaning of the Java expression and the output are identical**.

**Wrong conclusions:** “Java 8 forces the JVM to always allocate StringBuilder”, “Java 17 definitely has no intermediate objects”, “StringConcatFactory is always faster than StringBuilder in every workload”. These are runtime/JIT hypotheses that must be measured, not concluded from opcodes alone.

### 9.1. Why is this better than comparing two uncontrolled .class files?

If you compile only once and then switch JDKs to run, the classfile **is still the same compiled file**; bytecode does not rewrite itself to the new version. If you want to compare javac output, you must actually **recompile**.

Nor should you change source, compiler, target, JVM, and input all in one run and attribute every difference to `--release`. Record each variable explicitly and keep the rest identical.

## 10. Bytecode Descriptors and Constant Pool: What Is Useful to Read?

When viewing `javap`, distinguish:

- **Source method names**: `makeAdder`, `format`, `shout`.
- **NameAndType** in the constant pool: the symbolic name of the dynamic call site and its descriptor.
- **JVM type descriptors**: for example `(I)Ljava/util/function/IntUnaryOperator;` (factory taking a captured int) or `(Ljava/lang/String;I)Ljava/lang/String;` (concat taking String and int).
- **BootstrapMethods index**: reference to a bootstrap record with a method handle and static arguments.
- **Synthetic method**: a helper added by the compiler to implement source, not automatically a public API.
- **Opcodes**: `invokedynamic`, `invokeinterface`, `invokevirtual`, `ldc`, `aload`, `iload`, `areturn`...

Useful descriptor table:

| Symbol | Meaning |
| --- | --- |
| `I` | Java `int` |
| `V` | `void` |
| `Z` | `boolean` |
| `Ljava/lang/String;` | Reference to `java.lang.String` |
| `Ljava/util/function/IntUnaryOperator;` | Reference to functional interface |
| `(I)I` | Takes int, returns int |
| `(I)Ljava/util/function/IntUnaryOperator;` | Takes int, returns functional object |
| `(Ljava/lang/String;I)Ljava/lang/String;` | Takes String and int, returns String |

`javap -s -p LambdaConcatObservation` helps inspect descriptors quickly without reading the entire constant pool.

**Be careful about two places with different descriptors:** For a capturing lambda, the descriptor of the **factory invokedynamic** is not the descriptor of the **SAM method**. The SAM `IntUnaryOperator.applyAsInt` is `(I)I`; the factory site can be `(I)IntUnaryOperator` because it receives captured data and then creates the functional object.

## 11. An invokedynamic Instruction Does Not Describe Full Semantics by Itself

When you see the instruction:

~~~text
invokedynamic #N, 0 // InvokeDynamic #M:...
~~~

read further to find out:

1. **Call site descriptor**: inputs/outputs on the operand stack.
2. **Bootstrap method**: who establishes the linkage? LambdaMetafactory, StringConcatFactory, or a custom bootstrap?
3. **Static bootstrap arguments**: implementation method handle, SAM type, concat recipe/constants... when present.
4. **Caller location**: which method of the class invokes `invokedynamic`? Creating a functional object or creating a String?
5. **Actual runtime result**: does the program run according to the contract?

One instruction using a common opcode can be linked to many different behaviors. Beyond lambdas/string concat, the JVM allows custom bootstraps in appropriate bytecode cases. Therefore, seeing `invokedynamic` is **not enough** to conclude “this is a lambda” or “this is String concat”.

### 11.1. The bootstrap does not necessarily run on every call

`invokedynamic` has a **linking** step with the bootstrap method. Once a call site is successfully linked, repeated calls use that linkage according to JVM rules. With an optimizing runtime, actual cost depends on many factors, but do not describe it as “every concat calls `StringConcatFactory.makeConcatWithConstants` like an ordinary Java function”.

This is also why you cannot use the bootstrap name in `javap` alone to measure object creations, number of allocations, or warmup time.

### 11.2. Is StringConcatFactory a Java call in source?

No. The source has the `+` operator; the compiler may choose to represent it with `invokedynamic` bytecode and the StringConcatFactory bootstrap. A reader of `javap` sees the consequence of compilation, not source code that directly called the factory.

For debugging/optimization, knowing the factory name helps investigate the mechanism; for source compatibility guarantees, what matters is **correct String values and evaluation order**.

## 12. Claims Allowed and Not Allowed from javap

| Observation | Can conclude | Cannot conclude from that observation alone |
| --- | --- | --- |
| Seeing `invokedynamic` in `makeAdder` | This classfile has a dynamic call site at that location | Every compiler/version must emit the same bytecode |
| Seeing `LambdaMetafactory.metafactory` | This classfile's bootstrap references LambdaMetafactory | Every SAM call runs the bootstrap or allocates |
| Seeing method `lambda$makeAdder$0` | This compiler generated a helper method | The helper name is an API or always exists |
| Seeing `StringConcatFactory.makeConcatWithConstants` | This compiler links concat via that factory | Every `+` uses the factory; no intermediate objects exist |
| Seeing `new StringBuilder` | The bytecode contains an instruction to create a builder | The runtime must allocate a builder object after JIT |
| Seeing `ldc "abcd"` | The classfile carries the constant `"abcd"` | All String concats, including runtime operands, can be folded |
| Two javac versions give the same stdout | Specific behavior for the tested input is identical | All semantics/edge cases have been verified |
| `javap -p` prints a private helper | There is a member in the classfile | It is a source method declared by the author |
| There is an `invokedynamic` site | There is an instruction with dynamic linkage | How many times the bootstrap runs in every runtime per call |

This table is a way to avoid the mistake of “seeing one bytecode output and elevating it to a language rule”.

## 13. Practical Verification Procedure When Suspecting a javac Detail

A good experiment can be repeated by others:

1. **Write a specific question.** For example “when a lambda captures an int, what descriptor does the call site have?”, not just “what does lambda javap look like?”.
2. **Create minimal source with two comparison paths.** Use one capturing lambda and one non-capturing lambda, or concat with constant operands and concat with runtime operands.
3. **Record the JDK and target release.** `javac -version`, `java -version`, `--release`.
4. **Compile into a separate directory.** Do not let old classes shadow the new build.
5. **Run the program and check stdout first.** This is the actual behavior of the test build.
6. **Use `javap -c -p` to locate instructions.** If it is `invokedynamic`, read `javap -v -p` to look up `BootstrapMethods`.
7. **Cross-check with JLS/JVMS.** What is mandatory, and what is allowed to vary?
8. **Compare only one variable at a time.** For example `--release 8` vs 17, keeping source and compiler identical.
9. **Do not claim performance from bytecode.** When optimization is needed, use a profiler or a benchmark like JMH with warm-up and a plan to avoid dead-code elimination.
10. **Write scoped conclusions.** “In test javac X, target 17, method format uses invokedynamic...” differs from “Java always uses invokedynamic for +”.

### 13.1. When your build differs from the examples

If javap shows extra methods, different indices, or concat using `makeConcat` instead of `makeConcatWithConstants`, do not rush to treat it as an error. Verify that:

- Running the program produces the right output.
- The class file is genuinely the newly built one with the right release.
- The BootstrapMethods output links properly to the invokedynamic site.
- The differing details do not violate language rules.

If the class was produced by another compiler (ECJ, Kotlin compiler, Scala compiler...), a description written for `javac` does not necessarily apply. This lesson makes no claim about how other compilers must emit bytecode.

## 14. Common Mistakes

### Mistake 1 — Reading LambdaMetafactory as a business method

LambdaMetafactory is used to link **how to create a functional object** in one implementation. It is not the lambda body `x -> x + step`; the body may reside in a helper, a referenced method, or another target. To understand the result, you must read the implementation handle and the body's code.

### Mistake 2 — Concluding a lambda has a fixed class

The runtime lambda class name, which may contain `$$Lambda` markers or hidden-class behavior, is not a stable API. Do not serialize by that class name, do not bind Reflection to synthetic names, and do not build logic depending on a lambda's `getClass().toString()`.

### Mistake 3 — Confusing captured input with SAM input

The factory `invokedynamic:(I)IntUnaryOperator` receives the captured `step`, whereas `applyAsInt(int)` receives `input` when invoked later. These are two different stages and two different signature interfaces.

### Mistake 4 — Assuming every String concat appears in javap as invokedynamic

Constant expressions may be compiled into `ldc` of a String constant; target release 8 may use StringBuilder; another compiler is free to choose differently. `+` is language syntax, not a single opcode.

### Mistake 5 — Equating StringBuilder in bytecode with runtime allocation

The JIT can perform escape analysis and other optimizations. `javap` only reflects the classfile before runtime optimization. If you need allocation/throughput numbers, you must measure the real application.

### Mistake 6 — Comparing constant-pool indices as permanent identifiers

Numbers like `#19`, `#26`, `#141` change when the compiler adds/removes constants or changes emission order. When writing bytecode tests, normalize/match **meaningful structure** rather than hardcoding indices.

### Mistake 7 — Using javap output as proof of JLS-valid source

Bytecode can even be generated by other tools, not Java source. A valid classfile does not prove that corresponding source can be written and compiled by `javac` with valid Java syntax.

### Mistake 8 — Ignoring String conversion of null and operands with side effects

Even if the compiler uses `invokedynamic`, the expression `"x=" + nullReference` must produce a String containing `null`; operands with side effects must be evaluated according to the rules. Do not rewrite source as an “optimization” in a way that alters method call order.

### Mistake 9 — Assuming --release 17 means running javac 17

A newer `javac` can target Java 17 classfiles. The bytecode lowering of a newer javac is not guaranteed to match `javac 17` line-for-line. Record both `javac -version` and `--release`.

### Mistake 10 — Looking at javap while ignoring BootstrapMethods

The `invokedynamic` line and its name/descriptor are not enough to determine the entire mechanism. Use `-v` to connect the constant-pool entry, bootstrap method handle, and arguments.

## 15. Self-Check with Answers

**Question 1.** `javap -c` shows `invokedynamic` in `makeAdder(int step)` with descriptor `(I)IntUnaryOperator`. What does the `I` represent?

**Answer:** The `int step` data that needs to be captured **when creating the functional object**, not the `input` of `applyAsInt(int)` when invoked later.

**Question 2.** `javap` shows a private method `lambda$makeDoubler$0`. Can it be treated as an API method to call via Reflection?

**Answer:** No. This is a helper generated by the current `javac` version; its name may change or it may not exist in another compiler.

**Question 3.** Does `"ab" + "cd"` necessarily create a `StringBuilder` at runtime?

**Answer:** No. This is a constant expression; the test javac emits an `ldc` of `"abcd"`. Even bytecode using a builder in other cases does not prove the JIT must allocate an object.

**Question 4.** Are `"x" + 1 + 2` and `1 + 2 + "x"` the same?

**Answer:** No. `"x12"` versus `"3x"`, because `+` is left-associative and operand types determine addition versus concatenation.

**Question 5.** Seeing `StringConcatFactory.makeConcatWithConstants` in BootstrapMethods means every call to `format` runs the factory from scratch, right?

**Answer:** No. The bootstrap participates in the linking step of the dynamic call site; subsequent calls use the established linkage according to JVM rules and do not necessarily invoke the factory again.

**Question 6.** Given the same `format` source, `--release 8` uses StringBuilder while `--release 17` uses invokedynamic. What must still remain true?

**Answer:** The resulting String and the semantics of the `+` operator according to the JLS. Classfile generation may differ.

**Question 7.** Can we deduce that `makeDoubler() == makeDoubler()` is always true because the lambda captures nothing?

**Answer:** No. Functional object identity is not business semantics guaranteed by the JLS. Implementations may reuse or create objects.

**Question 8.** Why is `javap -v` more important than `javap -c` when studying invokedynamic?

**Answer:** It shows the constant pool and `BootstrapMethods`, allowing you to trace from the invokedynamic site to the bootstrap handle and static arguments. `-c` mainly shows instructions.

**Question 9.** To measure string concatenation allocation, is looking only at `new StringBuilder` in `javap` enough?

**Answer:** No. You need runtime measurement with JIT using an appropriate profiler/benchmark; bytecode does not prove allocation actually occurs after optimization.

**Question 10.** How do you distinguish what Java guarantees from an incidental build detail?

**Answer:** Use the JLS/JVMS as the authority for semantics and classfile format, use `javap` to record a specific compiler output, and avoid turning index numbers, helper names, or concat strategies into API contracts.

## Key Takeaways

- **`javap` shows what the compiler emitted, not everything the JLS requires.**
- A lambda/method reference is a **functional interface value**; a modern javac may use `invokedynamic` and `LambdaMetafactory`, though helper names/runtime identity are unstable.
- `+` string concatenation is defined by **language semantics**; one build may use `StringConcatFactory`, another `StringBuilder`, or constant-fold directly in the classfile.
- When inspecting `invokedynamic`, read all of **descriptor + constant pool + BootstrapMethods**.
- **Capture at lambda creation time** is distinct from **SAM parameters at lambda invocation time**.
- Every conclusion should record **JDK, `--release`, source, classfile**; to conclude anything about performance, measure at runtime rather than only reading disassembly.
