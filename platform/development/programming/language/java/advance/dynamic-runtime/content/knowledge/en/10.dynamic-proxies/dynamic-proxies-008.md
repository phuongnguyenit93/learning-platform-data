# 10.8. Designing equals, hashCode, and toString Behavior for Dynamic Proxies

## Objectives

After this lesson, you will be able to:

- Explain why `equals(Object)`, `hashCode()`, and `toString()` on a **JDK dynamic proxy** are all routed to `InvocationHandler.invoke` instead of automatically behaving like a regular `Object` instance.
- Accurately recognize Object method calls using the `Method` object, even when the proxy's interface **redeclares** these three signatures.
- Design two clear policies: **proxy identity** (each proxy is a separate entity) and **logical/key equality** (proxies with the same business identity are considered equal).
- Keep `equals`–`hashCode` contracts consistent for proper use in `HashMap`, `HashSet`, and hash-based data structures.
- Write a useful `toString()` without causing recursion, leaking sensitive information, or performing unintended operations.
- Detect `method.invoke(proxy, ...)` loop bugs, "forward everything to target", returning the wrong type, and symmetry issues when comparing against the target or proxies from other libraries.

**Scope:** This lesson covers standard JDK dynamic proxies created with `java.lang.reflect.Proxy`. Libraries that generate subclass proxies via bytecode (e.g., subclass-based interceptors) may have different Object method mechanisms; do not automatically equate them with JDK dynamic proxies.

## 1. Why do equals, hashCode, and toString need dedicated design?

A JDK dynamic proxy is an object created at runtime that implements one or more interfaces of our choice. Instead of directly containing the logic of each interface method, the proxy routes calls into an `InvocationHandler`:

~~~text
Application calls: proxy.execute("A")
            |
            v
Proxy class generated by JDK
            |
            v
handler.invoke(proxy, Method, Object[] {"A"})
            |
            v
Handler decides whether to return data, delegate, or throw an error
~~~

The following three calls also go through the handler:

~~~java
// Fragment: proxy is an initialized JDK dynamic proxy.
boolean same = proxy.equals(other);
int code = proxy.hashCode();
String description = proxy.toString();
~~~

**Special point:** According to the `java.lang.reflect.Proxy` contract (Java 17), calls to `equals`, `hashCode`, and `toString` are encoded and dispatched to the handler **just like interface method calls**. The `Method` object passed to `invoke` has `getDeclaringClass() == Object.class` for those three signatures.

Even if the interface **redeclares** one of the three methods, the `Method` received in the handler is still declared by `java.lang.Object`. This is a special precedence rule for the three Object methods in JDK proxies.

| Call | Method received in `invoke` | `args` | Handler should return |
| --- | --- | --- | --- |
| `proxy.equals(x)` | `Object.equals(Object)` | One element, which may be `null` | `Boolean`, unboxed to `boolean` |
| `proxy.hashCode()` | `Object.hashCode()` | No arguments; `args` is usually `null` | `Integer`, unboxed to `int` |
| `proxy.toString()` | `Object.toString()` | No arguments; `args` is usually `null` | `String` |

Not every method inherited from `Object` is dispatched to the handler. For example, `getClass()`, `wait()`, `notify()`, and `notifyAll()` still behave as public final methods of `Object`; the proxy does not override them using the mechanism of the three methods above.

### 1.1. Identifying Object methods safely

In a handler serving normal interfaces, you can branch as follows:

~~~java
// Fragment: inside InvocationHandler.invoke(...).
if (method.getDeclaringClass() == Object.class) {
    return switch (method.getName()) {
        case "equals" -> proxy == args[0];
        case "hashCode" -> System.identityHashCode(proxy);
        case "toString" -> "ServiceProxy";
        default -> throw new UnsupportedOperationException(method.getName());
    };
}
~~~

This is a **fragment**, not a standalone program; the variables `method`, `proxy`, and `args` are parameters of `InvocationHandler.invoke`. For the `equals` method, `args` contains one argument, even when the argument is `null`. For `hashCode` and `toString`, do not assume `args` is always an empty array; it may be `null`.

Matching `getDeclaringClass() == Object.class` here is a well-founded decision under the JDK proxy specification. Checking only `method.getName().equals("equals")` without considering the signature/context can cause confusion if the code handles multiple method types or custom-designed adapters.

### 1.2. Is there a "Java default"?

If you write `class X {}` without overriding Object methods, a regular class inherits identity equality behavior from `Object`. However, a JDK dynamic proxy **generates overrides** for the three methods mentioned above and delegates them to the handler. Therefore, the handler **must decide** the semantics.

If the handler does not distinguish Object methods and immediately calls `method.invoke(target, args)`, the `equals` result can violate Java's contract. If the handler returns `null` for `hashCode`, the primitive return call will fail with an unboxing error. Do not leave these three methods as an "accidental case" in a generic delegation branch.

## 2. The equals, hashCode, and toString contracts that must be upheld

### 2.1. The equals(Object) contract

A valid equality comparison requires:

1. **Reflexive:** For any non-null object `x`, `x.equals(x)` must be `true`.
2. **Symmetric:** `x.equals(y)` and `y.equals(x)` must have the same value.
3. **Transitive:** If `x.equals(y)` and `y.equals(z)`, then `x.equals(z)`.
4. **Consistent:** If the information used in the comparison has not changed, multiple invocations return the same result.
5. **Non-null:** `x.equals(null)` is always `false`.

You must decide on the **definition of identity** before writing code. For proxies, common choices are **proxy object** identity, **target object** identity, or **business key** identity. There is no single rule that applies to every system.

### 2.2. The hashCode() contract

Key invariant:

~~~text
If x.equals(y) == true
=> x.hashCode() == y.hashCode()
~~~

The converse is **not required**: two different objects can still have the same hash code. A hash code value is also **not** a unique identifier that can be stored in a database or transmitted across different JVM sessions.

If a proxy is used as a `HashMap` key or a `HashSet` element, the hash and the fields affecting equals must remain **stable for as long as the object is in the collection**. If the hash changes after being added to the set, looking up the key again may fail.

### 2.3. The role of toString()

`toString()` is not required to be a global ID; the goal is usually a representation that is **meaningful enough for debugging**, stable by design, and free of side effects. Restrictions:

- Do not call `proxy.toString()` from inside the handler that handles `toString()` for that same proxy (recursion).
- Do not rely on the generated proxy class name as a stable API.
- Do not automatically print secrets, tokens, passwords, private request contents, or the entire target data.
- Avoid network/DB queries in `toString()`, because debuggers, loggers, or IDEs may invoke it unexpectedly.
- The format can use the interface name + filtered key, e.g. `ServiceProxy[id=order-7]`, if security policy allows displaying that ID.

## 3. Choose the equality policy before coding

| Policy | When two proxies are equal | Reasonable `hashCode` | Use case |
| --- | --- | --- | --- |
| **Proxy identity** | Only when `proxyA == proxyB` | `System.identityHashCode(proxy)` | Interceptors, independent adapters, where each wrapper is a separate entity |
| **Stable business key** | Two proxies of the same **contract type** and same immutable key | `key.hashCode()` or a combination of the key's immutable fields | Client proxies for resources, service handles with IDs, caches |
| **Target identity** | Two proxies reference the **same target instance** under an agreed rule | `System.identityHashCode(target)` if equality is truly based on `target == otherTarget` | Certain internal wrappers |
| **Target value equality** | Two targets are equal per `target.equals(otherTarget)`, within **a uniform comparison domain** | Hash corresponding to the target's value equality | Value-like adapters if the target has stable equality/hashing |

**Caution:** The last two rows require an algorithm that handles **two wrappers** and decides whether a non-proxy object is considered equal. Blindly calling `target.equals(other)` does not automatically produce a valid target equality policy. This lesson will illustrate in detail the two most controllable options: identity and stable key.

**Design recommendation:** Choose the policy based on the API contract. If callers invoke a proxy factory multiple times for the same target and expect equivalent proxies, the identity policy may be **unsuitable**; instead, consider reusing/canonicalizing a single proxy or implementing equality by a stable key/target.

## 4. Complete example 1: equality by the proxy instance itself

The example below creates two different proxies wrapping the same target. The chosen policy: **the two proxies remain distinct**, because each wrapper is a separate entity.

Save file **IdentityProxyDemo.java**:

~~~java
import java.lang.reflect.InvocationHandler;
import java.lang.reflect.InvocationTargetException;
import java.lang.reflect.Method;
import java.lang.reflect.Proxy;
import java.util.HashSet;
import java.util.Set;

public class IdentityProxyDemo {
    interface Greeter {
        String greet(String name);
        boolean equals(Object other);
        int hashCode();
        String toString();
    }

    static final class GreeterImpl implements Greeter {
        public String greet(String name) {
            return "Hello, " + name;
        }
    }

    static final class IdentityHandler implements InvocationHandler {
        private final Greeter target;
        private final String label;
        boolean sawObjectMethod;

        IdentityHandler(Greeter target, String label) {
            this.target = target;
            this.label = label;
        }

        @Override
        public Object invoke(Object proxy, Method method, Object[] args)
                throws Throwable {
            if (method.getDeclaringClass() == Object.class) {
                sawObjectMethod = true;
                return switch (method.getName()) {
                    case "equals" -> proxy == args[0];
                    case "hashCode" -> System.identityHashCode(proxy);
                    case "toString" -> "GreeterProxy[" + label + "]";
                    default -> throw new UnsupportedOperationException(
                            method.getName());
                };
            }

            try {
                return method.invoke(target, args);
            } catch (InvocationTargetException ex) {
                throw ex.getCause();
            }
        }
    }

    static Greeter newProxy(IdentityHandler handler) {
        return (Greeter) Proxy.newProxyInstance(
                Greeter.class.getClassLoader(),
                new Class<?>[]{Greeter.class},
                handler);
    }

    public static void main(String[] args) throws Exception {
        Greeter target = new GreeterImpl();
        IdentityHandler first = new IdentityHandler(target, "first");
        IdentityHandler second = new IdentityHandler(target, "second");
        Greeter a = newProxy(first);
        Greeter b = newProxy(second);

        System.out.println("greeting=" + a.greet("Mai"));
        System.out.println("reflexive=" + a.equals(a));
        System.out.println("sameTargetEquals=" + a.equals(b));
        System.out.println("nullEquals=" + a.equals(null));
        System.out.println("symmetric=" + (a.equals(b) == b.equals(a)));
        System.out.println("identityHash="
                + (a.hashCode() == System.identityHashCode(a)));
        Set<Greeter> set = new HashSet<>();
        set.add(a);
        set.add(b);
        set.add(a);
        System.out.println("setSize=" + set.size());
        System.out.println("toString=" + a.toString());
        System.out.println("ObjectDeclaringClass=" + first.sawObjectMethod);
        System.out.println("interfaceRedeclares="
                + (Greeter.class.getMethod("equals", Object.class)
                    .getDeclaringClass() == Greeter.class));

        InvocationHandler blindForwarder =
                (proxy, method, actual) -> method.invoke(target, actual);
        Greeter broken = (Greeter) Proxy.newProxyInstance(
                Greeter.class.getClassLoader(),
                new Class<?>[]{Greeter.class},
                blindForwarder);
        System.out.println("brokenReflexive=" + broken.equals(broken));
        System.out.println("brokenProxyEqualsTarget=" + broken.equals(target));
        System.out.println("targetEqualsBrokenProxy=" + target.equals(broken));
    }
}
~~~

Compile and run on **JDK 17+**:

~~~bash
javac -encoding UTF-8 IdentityProxyDemo.java
java IdentityProxyDemo
~~~

Stdout:

~~~text
greeting=Hello, Mai
reflexive=true
sameTargetEquals=false
nullEquals=false
symmetric=true
identityHash=true
setSize=2
toString=GreeterProxy[first]
ObjectDeclaringClass=true
interfaceRedeclares=true
brokenReflexive=false
brokenProxyEqualsTarget=true
targetEqualsBrokenProxy=false
~~~

### 4.1. Why is identity equality appropriate here?

The handler does not ask "do two proxies wrap the same target?" but rather **"do two references point to the same proxy object?"**:

~~~java
// Fragment: expression returned in the equals branch of the handler.
proxy == args[0]
~~~

For `a.equals(a)`, the result is true; for `a.equals(b)` (two different proxy instances), the result is false, even though both point to the same `GreeterImpl`. Comparing with `null` returns false. This rule is naturally reflexive, symmetric, and transitive.

`System.identityHashCode(proxy)` retrieves an identity-based hash **without going through `proxy.hashCode()`**, so it does not call back into the handler. Hashes may collide between two different objects, which does not violate the contract. The test result intentionally compares booleans rather than printing a random hash number that is unstable across JVMs.

A `HashSet` containing the two proxies `a` and `b` yields size 2; adding `a` again does not create a new element. `toString()` returns the deterministic string `GreeterProxy[first]`, independent of the class name format generated by the JVM.

### 4.2. Why is ObjectDeclaringClass=true when the interface redeclares equals?

The `Greeter` interface in the example **declares its own signature `boolean equals(Object)`**, as well as `hashCode` and `toString`. The reflection check on the interface itself returns:

~~~text
interfaceRedeclares=true
~~~

Yet at runtime, calls to `a.equals(...)`, `a.hashCode()`, and `a.toString()` still pass a `Method` whose declaring class is **`Object.class`** to the handler. Therefore `ObjectDeclaringClass=true`.

This is a special rule documented by `java.lang.reflect.Proxy`; do not replace it with an assumption that the method is always declared by the first interface.

### 4.3. Why must InvocationTargetException be unwrapped in the business method branch?

The call `a.greet("Mai")` is dispatched to the handler, and then `method.invoke(target, args)` invokes the implementation on `GreeterImpl`. When a business method throws an exception, `Method.invoke` wraps the original exception in an `InvocationTargetException`. The handler in the example rethrows the **actual cause** so the proxy handles exceptions according to the interface method's contract.

This is necessary when using reflection to delegate. A checked exception not declared in the interface may still be wrapped by the proxy in an `UndeclaredThrowableException`; do not use unwrapping as a way to bypass the method's checked exception rules.

## 5. Executed counterexample: forwarding all Object methods to the target is wrong

In the same program above, a third proxy uses the handler:

~~~java
// Fragment from IdentityProxyDemo.java, illustrating WRONG:
InvocationHandler blindForwarder =
        (proxy, method, actual) -> method.invoke(target, actual);
~~~

With `target` using `Object.equals` based on identity, what happens?

- `broken.equals(broken)` actually calls `target.equals(broken)` and returns **false** because the target is not the proxy. Thus, the object is not equal to itself: **violating reflexivity**.
- `broken.equals(target)` calls `target.equals(target)` and returns **true**.
- However, `target.equals(broken)` returns **false**. Thus **violating symmetry**.

The stdout of the counterexample printed all three cases:

~~~text
brokenReflexive=false
brokenProxyEqualsTarget=true
targetEqualsBrokenProxy=false
~~~

This means **"delegate every method" is not an equality design**. The target might have great `equals` and `hashCode` with other targets, but the handler still needs to understand **whether the proxy and target belong to the same equality domain**.

`toString()` should also not be blindly forwarded if the target's default prints a class name/hash that is unhelpful to users, or if the target contains sensitive data. The handler needs to design the proxy's own format separately.

## 6. Complete example 2: equality by an immutable business key

Some proxies represent **a logical resource**; two wrappers created at different times with the same ID may need to be treated as equivalent. For example, a service proxy for resource `order-7` from a registry.

The design below deliberately restricts equality to **the same proxy type created by KeyedHandler**, the same `Service` interface, and the same key. It **does not automatically treat the proxy as equal to the underlying target object**. Every instance created through this factory uses the same rule, so it is symmetric within that domain.

Save file **KeyedProxyDemo.java**:

~~~java
import java.lang.reflect.InvocationHandler;
import java.lang.reflect.InvocationTargetException;
import java.lang.reflect.Method;
import java.lang.reflect.Proxy;
import java.util.HashMap;
import java.util.HashSet;
import java.util.Map;
import java.util.Objects;
import java.util.Set;

public class KeyedProxyDemo {
    interface Service {
        String read();
    }

    static final class KeyedHandler implements InvocationHandler {
        private final String key;
        private final Service target;

        KeyedHandler(String key, Service target) {
            this.key = Objects.requireNonNull(key);
            this.target = Objects.requireNonNull(target);
        }

        @Override
        public Object invoke(Object proxy, Method method, Object[] args)
                throws Throwable {
            if (method.getDeclaringClass() == Object.class) {
                return switch (method.getName()) {
                    case "equals" -> equalsProxy(proxy, args[0]);
                    case "hashCode" -> key.hashCode();
                    case "toString" -> "ServiceProxy[id=" + key + "]";
                    default -> throw new UnsupportedOperationException(
                            method.getName());
                };
            }
            try {
                return method.invoke(target, args);
            } catch (InvocationTargetException ex) {
                throw ex.getCause();
            }
        }

        private boolean equalsProxy(Object self, Object other) {
            if (self == other) {
                return true;
            }
            if (!(other instanceof Service)
                    || !Proxy.isProxyClass(other.getClass())) {
                return false;
            }
            InvocationHandler otherHandler = Proxy.getInvocationHandler(other);
            return otherHandler instanceof KeyedHandler matching
                    && key.equals(matching.key);
        }
    }

    static Service wrap(String key, Service target) {
        return (Service) Proxy.newProxyInstance(
                Service.class.getClassLoader(),
                new Class<?>[]{Service.class},
                new KeyedHandler(key, target));
    }

    public static void main(String[] args) {
        Service target = () -> "payload";
        Service first = wrap("order-7", target);
        Service second = wrap("order-7", target);
        Service third = wrap("order-8", target);

        System.out.println("sameKey=" + first.equals(second));
        System.out.println("reverse=" + second.equals(first));
        System.out.println("differentKey=" + first.equals(third));
        System.out.println("nullEquals=" + first.equals(null));
        System.out.println("rawTargetEquals=" + first.equals(target));
        System.out.println("hashConsistent="
                + (first.hashCode() == second.hashCode()));
        Set<Service> set = new HashSet<>();
        set.add(first);
        set.add(second);
        set.add(third);
        System.out.println("setSize=" + set.size());
        Map<Service, String> cache = new HashMap<>();
        cache.put(first, "cached");
        System.out.println("mapLookup=" + cache.get(second));
        System.out.println("toString=" + first);
        System.out.println("read=" + first.read());
    }
}
~~~

Compile and run:

~~~bash
javac -encoding UTF-8 KeyedProxyDemo.java
java KeyedProxyDemo
~~~

Stdout:

~~~text
sameKey=true
reverse=true
differentKey=false
nullEquals=false
rawTargetEquals=false
hashConsistent=true
setSize=2
mapLookup=cached
toString=ServiceProxy[id=order-7]
read=payload
~~~

### 6.1. Meaning of the comparison logic

`first.equals(second)` and `second.equals(first)` are both true because both have a `KeyedHandler` and the key `order-7`. `first.equals(third)` is false because `order-8` is a different resource.

`Proxy.isProxyClass(other.getClass())` ensures the object being checked is a **JDK proxy class**. `Proxy.getInvocationHandler(other)` returns the handler attached to that proxy; in this example, we further accept only `KeyedHandler` to avoid misinterpreting an unfamiliar proxy created by another framework.

Writing only `other instanceof Service` is not enough: the real target can also be a `Service` without using the same equality policy. The `rawTargetEquals=false` case reflects an **intentional decision**: "service proxy with ID" is distinct from "raw target object".

**Design limitation:** The comparison rule guarantees the contract **within the proxy family controlled by this factory**. If *another* class or proxy handler proactively reports itself as equal to a `KeyedProxy` while `KeyedProxy` returns false, system-wide symmetry can break. Therefore, implementers participating in the same equality domain must agree on a shared contract; a single handler cannot force every other class to behave symmetrically.

### 6.2. HashMap and HashSet based on the key

Two wrappers with equal keys return the same hash because `hashCode` is based on the **immutable String key** itself. As a result:

- `HashSet` had three proxies created but only two logical elements: `setSize=2`.
- `cache.put(first, "cached")` followed by `cache.get(second)` returns `cached`. The keys share the same equality policy and the same hash.
- `first.read()` still calls the business target and returns `payload`; proxy equality does not alter business method delegation.

If requests can point to different targets that share `order-7`, this equality style means both proxies are still considered **the same logical resource**. You must confirm that this is the right business rule. If the ID is only meaningful within a tenant, environment, or type, the key needs to include tenant/type to avoid accidental merging.

### 6.3. Why should the key be immutable?

Consider two objects `a` and `b` with the same key `order-7`. If `a`'s key were allowed to change after being added to a `HashMap`, `a.hashCode()` would change and the `HashMap` might fail to find the entry again. The same applies to a target whose `hashCode` depends on mutable fields.

In the sample code, `key` is `private final String` and required to be non-null. `String` is immutable, so equality/hashing stays stable for the data used. For a composite key, use an immutable value object—such as a record containing `tenant`, `resourceType`, and `resourceId`—and ensure its components are stable.

### 6.4. toString reflects the proxy, not the entire target

`ServiceProxy[id=order-7]` is a proxy-specific format, easily distinguished from the target object and independent of the runtime class name. In a real system, the ID might contain information that needs to be hidden; consider a format like `ServiceProxy[type=Order, state=ready]` or a shortened/masked ID, depending on logging policy.

In particular, never make network calls just to build `toString`. If the proxy is an RPC client, a logger accidentally printing the proxy must not trigger new network requests.

## 7. Four bug patterns when implementing the three Object methods

### 7.1. Calling back into the proxy itself, causing recursion

Wrong snippet:

~~~java
// WRONG fragment inside handler:
if (method.getName().equals("toString")) {
    return proxy.toString(); // proxy.toString() calls the handler itself again!
}
~~~

Execution path:

~~~text
proxy.toString()
  -> handler.invoke(proxy, Object.toString, ...)
      -> proxy.toString()
          -> handler.invoke(...)
              -> ... repeats until StackOverflowError
~~~

Similarly, `proxy.equals(other)` inside the `equals` branch or `proxy.hashCode()` inside the `hashCode` branch can both call the handler infinitely. Do not use `Objects.hash(proxy)` if it leads to `proxy.hashCode()` in the same branch. Use `proxy == other`, `System.identityHashCode(proxy)`, or immutable fields of the handler according to your design policy.

**Logging is also an indirect recursion path.** For example, `System.out.println("handling " + proxy)` inside the handler will trigger `proxy.toString()`. If that log line sits inside the `toString` handler itself, the program can enter an infinite loop. When debugging, log the method type and handler label instead of interpolating the proxy directly.

### 7.2. Returning the wrong type for the signature

According to `InvocationHandler.invoke`, the return value must be compatible with the return type of the invoked method:

| Method | Java return type | Correct handler return | Wrong return tends to cause |
| --- | --- | --- | --- |
| `equals(Object)` | `boolean` | `Boolean.TRUE` / `Boolean.FALSE` | `NullPointerException` if null; `ClassCastException` if another type |
| `hashCode()` | `int` | An `Integer` | Unbox/cast error if null or wrong wrapper |
| `toString()` | `String` | An appropriate `String` | Cast error if returning a non-String object |

The fact that `InvocationHandler.invoke` declares its return type as `Object` **does not mean** you can return any object. The generated proxy code must convert the result to the method's type. For `equals`/`hashCode`, return a boolean/int directly in Java source so autoboxing produces the right wrapper.

### 7.3. Letting inappropriate exceptions escape Object methods

`InvocationHandler.invoke` can throw `Throwable`, but the proxied method still has its own checked exception contract. The three methods `Object.equals/hashCode/toString` declare no checked exceptions. If the handler throws a checked exception not permitted by the signature, the generated proxy typically wraps it in an `UndeclaredThrowableException`.

Therefore, equality/`toString` should be **lightweight, non-I/O** operations with deterministic semantics. Do not let `equals` call a database, RPC, or external class loader and unexpectedly throw a checked exception while `HashMap` is looking up a key.

When a business method is delegated via `Method.invoke(target, args)`, you usually need to unwrap `InvocationTargetException.getCause()` so the proxy sees the original error. However, unwrapping must still respect the interface's `throws` clause; an incompatible checked exception cannot be "legalized" by the handler.

### 7.4. Choosing a hashCode that does not match equals

Wrong example:

~~~java
// WRONG fragment: two proxies with the same ID are considered equal...
case "equals" -> id.equals(idOfOtherProxy);
// ...but hash takes the separate identity of each wrapper.
case "hashCode" -> System.identityHashCode(proxy);
~~~

If `a.equals(b)` is true while their hashes differ, using them as keys in a `HashMap`/`HashSet` will be unstable under the contract. This code example is an **error-illustrating snippet**, not a standalone program; `id` and `idOfOtherProxy` must be defined by application logic.

If you want equality by ID, the hash must also be based on that same ID (and any other components used in `equals`). If you want equality by proxy identity, hash by proxy identity. Do not mix the two policies.

## 8. Distinguishing comparisons between proxies, targets, and proxies from other frameworks

### 8.1. Two proxies wrapping the same target

You cannot automatically infer that they are equal. Three options are commonly valid:

- **Wrapper identity:** `a.equals(b) == false` if `a != b`; clearly each wrapper is a separate instance.
- **Same-target identity:** `a.equals(b) == true` if both handlers reference the same target via `==`; hash is based on the target's identity.
- **Same logical resource:** `a.equals(b) == true` if they share the same immutable business key; target instances may differ.

Pick one rule, document it on the factory, and keep it consistent across `equals`, `hashCode`, caches, collections, and tests.

### 8.2. Should a proxy equal the real target object?

It is usually **safer** to specify that a proxy **only compares equal to proxies with the same contract**, not automatically to the target object. If you want equality between proxy and target, both directions of comparison must be coordinated: the target must also be designed so that `target.equals(proxy)` returns the same result. This is difficult if the target is an existing class using `Object.equals` or strict `getClass()` checks.

The counterexample in Section 5 is concrete proof: `broken.equals(target)` is true, while `target.equals(broken)` is false.

### 8.3. Multiple interfaces, class loaders, and proxy classes

A proxy can implement multiple interfaces; the class generated by `Proxy` depends on the loader and interface list according to API rules. You should not rely on names like `$Proxy0`, on whether two proxies share the same generated class, or on arbitrary `Method` ordering to decide equality.

For **regular interfaces with overlapping signatures**, `Proxy` has rules to determine the `Method` based on interface order. For the three Object method signatures specifically, `Object.class` takes precedence. If a handler needs to branch across multiple business methods with the same name, identify them by signature, parameter types/declaring class, and interface rules per the API; do not select by method name alone while ignoring parameters.

In plugin/multiple class loader environments, two interfaces with the same **string name** loaded by different loaders are not necessarily the same `Class`. When comparing objects or handlers across loaders, avoid blind casts; test the specific loader environment. A proxy belonging to a different classloader may prevent the expected configuration contract from applying.

### 8.4. You cannot "fix" symmetry from one side alone

Suppose `KeyedHandler` returns false for an object outside the factory, yet that other object returns true when compared with `KeyedProxy`. Symmetry is violated even though `KeyedHandler` followed its local policy correctly. To achieve equality across multiple classes/frameworks, you need:

- A shared contract on which types of objects are considered equivalent.
- The same definition of keys/comparison and hashing.
- Agreement on handling `null`, subtypes, proxy classes, and edge cases.
- Bidirectional and transitivity tests across implementers.

If you do not control all implementers, **restricting the equality domain** is usually much easier to maintain than trying to force a proxy to equal every target with "the same content".

## 9. Practical design for real applications

### 9.1. Recommended workflow

1. **Identify what the proxy is used for.** For example, a temporary logging/interceptor wrapper, an RPC resource handle, or an entity identity representative.
2. **Choose a clear equality policy.** If identity, compare `proxy == other`; if logical, define an immutable key and comparison domain.
3. **Write equals first, hashCode immediately after.** Prove "equals true ⇒ equal hashes", then verify null/reflexivity/symmetry/transitivity.
4. **Design toString separately.** Include only metadata allowed in logs, make no external service calls, and do not interpolate the proxy inside the handler itself.
5. **Handle Object methods before business methods.** Use `Method.getDeclaringClass() == Object.class` per the JDK proxy API, then delegate the rest.
6. **Ensure return types.** `equals` → `boolean`, `hashCode` → `int`, `toString` → `String`.
7. **Review the exception boundary.** Unwrap errors from `Method.invoke(target, args)`, but do not throw checked exceptions outside the interface signature.
8. **Test in HashMap/HashSet.** Verify lookups with equivalent proxies, not just direct `equals` calls.
9. **Test with multiple factory calls.** Multiple proxies around the same target, multiple targets with the same ID, different IDs, null, foreign proxies, and the real target.
10. **Document and preserve compatibility.** Changing the equality policy in a new release can alter cache behavior, set membership, and application dependencies.

### 9.2. Should you cache a single proxy to preserve reference identity?

If the requirement is that **the same resource always returns the exact same proxy instance** (for `==`), an equality policy alone cannot satisfy it. A factory may need **interning/canonicalization**—a map from stable ID to reused proxy, plus a lifecycle/weak-reference strategy if needed. In that case, `System.identityHashCode` still fits identity semantics.

However, if the application cannot guarantee a single proxy instance (for instance, a distributed client recreating wrappers multiple times), identity equality can cause surprises. Consider a stable-key policy and separate caching proxy instances from defining resource equality.

### 9.3. Do not turn equals into a heavy business operation

`HashMap.get` may call `hashCode` and `equals` multiple times. If every proxy comparison triggers an RPC, loads metadata, or acquires multi-layered mutexes, seemingly lightweight collection operations can become slow or fail. `equals`, `hashCode`, and `toString` should use **local, immutable, cheap state** whenever feasible.

For lazy proxies, avoid initializing the target just to answer `hashCode` or `toString`. Identity/key equality can be determined without touching the real target, so logging and collections do not cause side effects.

## 10. QA checklist before delivering a proxy factory

| Test question | Expected result per policy |
| --- | --- |
| `p.equals(p)`? | **Always true** |
| `p.equals(null)`? | **Always false** |
| `p.equals(q)` vs `q.equals(p)`? | **Same value** within the defined equality domain |
| If `p.equals(q)` is true, what about the two hashes? | **Equal** |
| Are three proxies `p, q, r` transitive? | If `p=q` and `q=r`, then `p=r` |
| Insert then retrieve from `HashMap` with an equivalent key? | Retrieves the stored value |
| Does the hash change when the target mutates? | No, if the equality policy has not changed |
| Does `p.toString()` recurse? | No |
| Does `p.toString()` leak secrets or perform I/O? | No |
| Interface redeclares `equals/hashCode/toString`? | Handler still receives `Method` belonging to `Object.class` |
| `p.equals(target)` and `target.equals(p)`? | Policy-aligned or **both false** |
| Handler returns `null` for `hashCode`? | **Not allowed** |
| Foreign proxy or different loader? | Do not cast blindly; handle by explicit domain |

A property-based test suite can generate many proxies from different IDs and verify reflexivity/symmetry/transitivity. Tests using `HashSet` and `HashMap` directly catch hash/equality inconsistencies that tests calling only `equals` might miss.

## 11. Self-check questions

**1.** Why can `proxy.hashCode()` end up calling `InvocationHandler`?

**Answer:** The JDK proxy generates an override of `Object.hashCode()` and dispatches it to `InvocationHandler.invoke`, just like `equals` and `toString`. The handler must decide the proxy's hash.

**2.** An interface declares its own `boolean equals(Object)`. What declaring class does the `Method` received by the handler have for that call?

**Answer:** `java.lang.Object.class`, per the special JDK proxy rule, even though the interface redeclared it.

**3.** To make each proxy independent, even when wrapping the same target, what should `equals` and `hashCode` be based on?

**Answer:** `proxy == other` and `System.identityHashCode(proxy)`. Do not call `proxy.hashCode()` from the handler handling `hashCode`, as that will recurse.

**4.** Two proxies with the same ID are considered equal. Can `System.identityHashCode(proxy)` be used as the hash for each instance?

**Answer:** No. Two proxies can have different identity hashes even when equality returns true, violating the contract. You must compute the hash from the same immutable key data.

**5.** Why can `method.invoke(target, args)` for all methods cause `broken.equals(broken)` to return false?

**Answer:** The call ends up executing `target.equals(broken)` instead of comparing `broken` with itself. If the target uses Object identity equality, `target` is not `broken`, so it returns false.

**6.** Why can `System.out.println(proxy)` be dangerous inside a handler?

**Answer:** It can call `proxy.toString()`, which dispatches back into the same handler; if done inside the `toString` branch or unguarded common logging, it can cause infinite recursion.

**7.** Is it valid for a handler to return `null` for `hashCode()` because `invoke` returns `Object`?

**Answer:** No. The proxy must convert the result to a primitive `int`; `null` cannot be unboxed and can cause a `NullPointerException`.

**8.** A `KeyedProxy` has key `order-7`, and another proxy has key `order-7` but a different target object. Should `equals` return true?

**Answer:** It depends on the contract. If the key identifies **the same logical resource** within the same namespace, true is reasonable; if the key is only local or target identity matters more, a different policy is needed.

**9.** Does `getClass()` on a JDK proxy go into the handler like `toString()`?

**Answer:** No. `getClass()` is a final method inherited from `Object`, not one of the three Object methods overridden and dispatched by the proxy.

## Key takeaways

- **JDK dynamic proxies route `equals`, `hashCode`, and `toString` to `InvocationHandler.invoke`.** The `Method` passed has `Object` as its declaring class, even if the interface redeclares the corresponding signature.
- **Equality is a design decision.** Proxy identity, target identity, and stable key produce different behaviors; do not delegate blindly.
- **Equals and hashCode must be consistent**, especially when proxies serve as `HashMap` keys or `HashSet` elements.
- **toString must be clear, safe, and non-recursive**, without logging secrets or triggering unintended I/O.
- **Avoid `method.invoke(proxy, ...)` or calling back into the proxy's Object methods from within the handler.** For business methods, if delegating via reflection, handle `InvocationTargetException` properly.
- **Test bidirectionally and with multiple instances**: proxy against itself, against the target, against proxies with the same ID, different IDs, and foreign proxies. Do not rely on just a single simple example.
