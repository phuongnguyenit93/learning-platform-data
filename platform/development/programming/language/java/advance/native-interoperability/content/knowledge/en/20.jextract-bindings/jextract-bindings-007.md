# Regenerating jextract When Headers Change and Verifying Against the Distributed Binary Library

## 1. Why Is Regenerating Bindings Not Enough?

`jextract` is an OpenJDK tool that reads **C headers** using Clang and generates **Java bindings** using the Foreign Function & Memory API (FFM). It can generate classes containing `MemoryLayout`, `FunctionDescriptor`, `MethodHandle`, and wrappers for Java to call C functions. However, jextract **does not** reverse-read machine code to prove that the binary has the same ABI as the header.

In a release workflow, there are at least three independent entities:

- **Public header (.h):** the specification that the C compiler and jextract rely on to understand function names, parameters, structs, typedefs, macros, and preprocessor conditions.
- **Generated Java bindings:** Java code generated by jextract from the header **for a specific toolchain and target**.
- **Distributed native binary:** the actual `.so`, `.dylib`, or `.dll` file packaged, loaded into the JVM, and executed.

```text
  [Release header + included headers]
                  |
                  v
      jextract + JDK + libclang
      -I / -D / target platform
                  |
                  v
        Generated Java sources
                  |
                 javac
                  |
                  v
             Java application
                  |
                  v
     Load actual distributed .so/.dylib/.dll
                  |
                  v
         ABI + semantic smoke tests
```

If the header changes but the bindings remain old, Java may create wrong descriptors. If the bindings are regenerated from the new header but the application still loads the old binary, the Java code **can still compile successfully**, even resolve a symbol with the same name, and then read the wrong field or call the native function with the wrong ABI.

**Core rule:** **when the header contract or code generation inputs change, regenerate jextract from the exact release header set; then verify against the exact binary that will be distributed to customers.** Do not treat `jextract` succeeding, `javac` succeeding, or "the symbol exists" as comprehensive proof of compatibility.

This lesson focuses on the **regeneration and binary verification** workflow, rather than stopping at the command to run jextract. We will build a sample C library with ABI-version/size/offset probes, a Java integration test that directly calls the generated bindings, and two independent gates for hashes and exported symbols.

**Java version:** Standard FFM was finalized in **JDK 22** (JEP 454). `jextract` is a **separate** tool, not bundled by default with every JDK; you need to choose a build compatible with the target JDK and libclang/OS. The `jextract`/FFM examples use JDK 22+, while the two file-checking programs are written for JDK 17+ (`BinaryExportGate` uses FFM so it requires JDK 22+).

## 2. Three Different Compatibility Layers

| Layer | What needs to match | Typical verification |
| --- | --- | --- |
| **Source API** | Headers, declarations, macros, and generated Java types | Run jextract, compile all generated code and handwritten wrappers |
| **Binary ABI** | Symbols, calling convention, C type widths, layout, alignment, field offsets, pointer width | Export check, correct architecture, native `sizeof`/`offsetof` probes, ABI major |
| **Behavior/semantic** | Return values, error reporting, memory ownership, callback behavior, thread safety | Smoke tests with actual binary, negative/integration tests, release notes |

Two headers can use the same function names but have different struct layouts. For example, v2 and v3 structs are both 16 bytes long, but the `total` field changes its offset from 8 to 0. Checking the `demo_sum_record` symbol or `sizeof == 16` alone does not detect the difference. Specifically for C, an exported symbol name usually **does not encode the full prototype**.

Conversely, a binary can keep the same ABI while changing semantics: a function that previously returned milliseconds now returns microseconds, or a `borrowed` pointer becomes `owned`. jextract does not infer those business or lifecycle rules.

**Do not conflate conclusions:** source-compatible does not necessarily mean ABI-compatible; ABI-compatible does not necessarily mean semantic-compatible; having a sha256 matching some file does not prove it is the right release artifact if the expected hash source is not trustworthy.

## 3. When Is Regeneration Needed?

A direct or indirect change can make the generated Java incorrect:

1. The public `.h` changes functions, parameters, return types, constants, enums, typedefs, structs/unions, or callback signatures.
2. A `#include`d **transitive header** changes even though the root header did not change.
3. `-D` macros or `#ifdef` select a different declaration; `-I` include order finds a different file.
4. Compiler flags/ABI change such as `#pragma pack`, `-fpack-struct`, MSVC `/Zp`, calling convention, or visibility.
5. Target OS or CPU changes: x86/x64/arm64, LP64 vs. LLP64, `long`, `size_t`, pointer width.
6. JDK/jextract/libclang changes can generate different code or layouts.
7. SDK/sysroot/target headers, build compiler, and ABI settings change.
8. The native binary is upgraded: **always re-run binary verification**; regeneration is not necessarily required if headers/toolchain/ABI truly have not changed.
9. The semantic contract changes even though prototypes remain unchanged: update handwritten wrappers/tests and verify release notes.

Merely changing a header's mtime without changing tokens/configuration does not necessarily require regeneration. It should be based on **content and dependency closure**, not just timestamps. However, a new binary—even when headers remain identical—must still be smoke tested.

The official jextract guide notes that generated code **can be platform-dependent**: preprocessing takes different branches and some built-in types like C `long` have different sizes on Windows and Linux. If you want to release a single set of bindings for multiple OSes, you must inspect the generated layout on each platform and then prove portability.

## 4. Pin All Inputs for Reproducible Regeneration

| Subject | Information to pin |
| --- | --- |
| Public headers | Git tag/commit, SHA-256, entire transitive header closure |
| Native ABI | OS, architecture, toolchain, C compiler, target triple, packing, calling convention |
| Preprocessor | Exact list of `-I`, `-D`, sysroot, platform macros, and include order |
| jextract | Generator version/build, libclang version, output/filter configuration |
| Java toolchain | JDK compiler and runtime version compatible with generated FFM API |
| Native binary | Release candidate file, version/SONAME, SHA-256, shared dependencies |
| Testing | Required symbols, `sizeof`, `offsetof`, ABI major, primitive/struct behavior |
| Distribution | Final package/container, exact file downloaded by users |

Simply writing "run jextract demoabi.h" is insufficient. For example, the same `demoabi.h` name, if one run resolves `stdint.h` from a different SDK or one run has `-D FEATURE_X`, can produce different output.

**The expected digest must come from an independent signed or trusted release manifest.** Computing sha256 on the file being checked and comparing it against itself only confirms the hash calculation, not that the artifact is the right release.

## 5. Sample C Project with Self-Describing ABI

We create the `demoabi` library with the following exported native functions:

- `demo_abi_major()`: the ABI version implemented by **the running binary**.
- `demo_record_size()`: `sizeof(struct DemoRecord)` as computed by the C compiler.
- `demo_total_offset()`: actual `offsetof(struct DemoRecord,total)`.
- `demo_add(int64_t,int64_t)`: checks primitive arguments and return value.
- `demo_sum_record(const struct DemoRecord*)`: checks pointer passing and field layout.

Directory layout:

```text
example/
  include/demoabi.h
  native/demoabi.c
  smoke/AbiSmoke.java
  smoke/BinaryExportGate.java
  smoke/ArtifactShaGate.java
  dist/include/demoabi.h           # actual release header
  dist/native/libdemoabi.so        # Linux; macOS .dylib; Windows demoabi.dll
  build/generated/                # contains only jextract-generated code
  build/classes/
```

### 5.1. File `include/demoabi.h`

```c
#ifndef DEMOABI_H
#define DEMOABI_H

#include <stdint.h>

#if defined(_WIN32)
#  if defined(DEMOABI_BUILD)
#    define DEMOABI_API __declspec(dllexport)
#  else
#    define DEMOABI_API __declspec(dllimport)
#  endif
#else
#  define DEMOABI_API __attribute__((visibility("default")))
#endif

#ifdef __cplusplus
extern "C" {
#endif

#define DEMO_ABI_MAJOR 2

struct DemoRecord {
    int32_t id;
    int32_t flags;
    int64_t total;
};

DEMOABI_API int32_t demo_abi_major(void);
DEMOABI_API int32_t demo_record_size(void);
DEMOABI_API int32_t demo_total_offset(void);

DEMOABI_API int64_t demo_add(int64_t a, int64_t b);
DEMOABI_API int64_t demo_sum_record(
        const struct DemoRecord *record);

#ifdef __cplusplus
}
#endif

#endif
```

**Why `int32_t`/`int64_t` instead of `int`/`long`?** Fixed-width types reduce differences between LP64 (typically Linux x64) and LLP64 (Windows x64). However, alignment, padding, and calling convention still need to be tested. `DEMO_ABI_MAJOR` is a header constant for the generated Java to compare against **the native runtime function**.

### 5.2. File `native/demoabi.c`

```c
#include "demoabi.h"
#include <stddef.h>
#include <stdint.h>

DEMOABI_API int32_t demo_abi_major(void) {
    return DEMO_ABI_MAJOR;
}

DEMOABI_API int32_t demo_record_size(void) {
    return (int32_t)sizeof(struct DemoRecord);
}

DEMOABI_API int32_t demo_total_offset(void) {
    return (int32_t)offsetof(struct DemoRecord, total);
}

DEMOABI_API int64_t demo_add(int64_t a, int64_t b) {
    return a + b;
}

DEMOABI_API int64_t demo_sum_record(
        const struct DemoRecord *record) {
    if (record == NULL) {
        return INT64_MIN;
    }

    return (int64_t)record->id
            + (int64_t)record->flags
            + record->total;
}
```

On common 64-bit ABIs, the sample struct consists of two 32-bit integers followed by one 64-bit integer; `sizeof(DemoRecord)=16` and `offsetof(total)=8` are expected. But **do not replace the probes with predicted numbers**: tests must query the compiled native binary itself to detect wrong compiler flags/packing.

`INT64_MIN` for null is just a sample function convention; a production library needs clearly defined error semantics, ownership, and value bounds.

## 6. Compiling the Sample Native Binary Across Platforms

These are **illustrative** commands to build the native artifact yourself if you have a C compiler. In a real release workflow, the distributed binary may come from a vendor or an independent release system; you must test **that file**, not substitute it with a fresh build from local headers.

**Linux (GCC):**

```bash
mkdir -p dist/native dist/include build/generated build/classes
cp include/demoabi.h dist/include/demoabi.h

gcc -std=c11 -O2 -fPIC -shared \
  -DDEMOABI_BUILD -Iinclude \

```

**macOS (Clang):**

```bash
mkdir -p dist/native dist/include build/generated build/classes
cp include/demoabi.h dist/include/demoabi.h

clang -std=c11 -O2 -dynamiclib \
  -DDEMOABI_BUILD -Iinclude \
  -o dist/native/libdemoabi.dylib native/demoabi.c
```

**Windows (Visual Studio Developer Command Prompt):**

```bat
mkdir dist

mkdir dist\include
mkdir build

copy include\demoabi.h dist\include\demoabi.h
```

Make sure to use the right **C compiler/architecture** for the release; for example, an x64 DLL will not run in an x86 JVM. If a directory already exists, `mkdir` may warn; organize an idempotent pipeline according to your actual build tool.

## 7. Running jextract with the Release Header and Clean Output

### 7.1. Checking the toolchain

```bash
java -version
javac -version
jextract --version
```

`jextract` is a program external to the base JDK; obtain a compatible build from the OpenJDK project and check libclang requirements. Generator versions can change the FFM API and generated class structure depending on the target JDK; do not arbitrarily mix the current JDK with bindings generated by an incompatible generator.

### 7.2. Command supported by the official guide

```bash
jextract \
  --include-dir dist/include \
  --output build/generated \
  --target-package edu.demoabi \
  --library demoabi \
  --use-system-load-library \
  dist/include/demoabi.h
```

Explanation:

- `--include-dir`: where Clang searches for dependent headers.
- `--output`: directory where generated Java source files are written.
- `--target-package`: package of the generated classes.
- `--library demoabi`: native library with logical name `demoabi`.
- `--use-system-load-library`: generated code loads the main library via `System.loadLibrary`/`java.library.path`; the library's dependencies still follow the OS loader.
- Final argument: **the actual header of the distributed release**.

Current versions typically generate the class `edu.demoabi.demoabi_h`, along with `edu.demoabi.DemoRecord` for the tagged struct. Before writing handwritten wrappers, inspect the newly generated output files to see the accessor names.

**Clean generation requirement:** create a fresh `build/generated` or delete only the **pipeline-owned generated directory** before each regeneration. Otherwise, a class generated from a removed symbol could linger and cause a false passing build. Do not delete handwritten files or release artifacts.

### 7.3. If you need to filter symbols

You can use options:

```bash
jextract \
  --include-dir dist/include \
  --output build/generated \
  --target-package edu.demoabi \
  --library demoabi \
  --use-system-load-library \
  --include-function demo_abi_major \
  --include-function demo_record_size \
  --include-function demo_total_offset \
  --include-function demo_add \
  --include-function demo_sum_record \
  --include-struct DemoRecord \
  dist/include/demoabi.h
```

The `--include-*` options restrict output by symbol/struct name. For complex projects, if filtering omits a dependent declaration, jextract may report an error. For full-sample ABI smoke testing, the **unfiltered** command in section 7.2 is simpler and less prone to omissions.

`jextract --dump-includes` is useful if you want to export the symbol list and manage filters via a version-controlled argfile. However, do not filter only new symbols and omit a dependent struct.

### 7.4. Version control and reproducibility

There are two reasonable strategies:

- **Commit generated Java:** PRs that change headers include the regeneration diff; CI regenerates with the same toolchain and confirms the output has no unexpected differences.
- **Do not commit generated Java:** CI must generate from the pinned toolchain/headers in every build and store generated sources in an artifact; caches must be invalidated whenever any generator input changes.

In both cases, **do not manually edit a generated file and treat it as the source of truth**. Put advanced rules, validations, or abstractions in a handwritten Java wrapper; if you need to improve how code is generated, change the headers/configuration/tooling accordingly.

## 8. Checking the ABI from Generated Java Before Calling Native Code with Structs

Four preflight layers:

1. Compiled header ABI major == binary runtime ABI major.
2. `DemoRecord.sizeof()` == `demo_record_size()`.
3. `DemoRecord.total$offset()` == `demo_total_offset()`.
4. Exported symbols are present and primitive/struct smoke tests return expected results.

### 8.1. File `smoke/AbiSmoke.java`

The jextract guide describes a generated header class `demoabi_h` with accessors for functions/macros and a generated struct class `DemoRecord` with `sizeof()`, `total$offset()`, and field getters/setters. The code below targets those API conventions; verify the actual names in **the generated Java of the exact jextract version you use**.

```java
import java.lang.foreign.Arena;
import java.lang.foreign.MemorySegment;

import edu.demoabi.DemoRecord;
import static edu.demoabi.demoabi_h.*;

public class AbiSmoke {
    public static void main(String[] args) {
        int expectedMajor = DEMO_ABI_MAJOR();
        int actualMajor = demo_abi_major();

        if (actualMajor != expectedMajor) {
            throw new IllegalStateException(
                    "ABI version mismatch: header=" + expectedMajor
                    + ", binary=" + actualMajor);
        }

        long generatedSize = DemoRecord.sizeof();
        int binarySize = demo_record_size();

        if (generatedSize != binarySize) {
            throw new IllegalStateException(
                    "Size mismatch: header=" + generatedSize
                    + ", binary=" + binarySize);
        }

        long generatedOffset = DemoRecord.total$offset();
        int binaryOffset = demo_total_offset();

        if (generatedOffset != binaryOffset) {
            throw new IllegalStateException(
                    "Offset mismatch: header=" + generatedOffset
                    + ", binary=" + binaryOffset);
        }

        long add = demo_add(7L, 9L);
        if (add != 16L) {
            throw new IllegalStateException(
                    "Primitive ABI mismatch: " + add);
        }

        long sum;
        try (Arena arena = Arena.ofConfined()) {
            MemorySegment record = DemoRecord.allocate(arena);
            DemoRecord.id(record, 5);
            DemoRecord.flags(record, 2);
            DemoRecord.total(record, 11L);

            sum = demo_sum_record(record);
        }

        if (sum != 18L) {
            throw new IllegalStateException(
                    "Struct ABI mismatch: " + sum);
        }

        System.out.println("ABI major: " + actualMajor);
        System.out.println("Record sizeof: " + binarySize);
        System.out.println("Total offset: " + binaryOffset);
        System.out.println("Add: " + add);
        System.out.println("Sum: " + sum);
    }
}
```

**Important design point:** `AbiSmoke` checks ABI major/size/offset **before** allocating and passing `DemoRecord` across the native boundary. If the header and binary are already known to differ, fail immediately in Java rather than risking reading wrong bytes.

**Expected stdout** when the sample binary is built exactly as the C source, with ABI major 2 and matching fields:

```text

Total offset: 8

```

**Distinguishing verification from expectation:** the `AbiSmoke` integration test requires both `jextract` **and the demoabi native binary**. If a machine only has the JDK without jextract/C compiler, the full demo cannot be run. The output above is the **expected result based on the C implementation**; it must be confirmed in CI for each release/platform and must not be described as an execution that already happened if it has not been run.

### 8.3. Three probes do not prove every ABI contract

ABI probes themselves must also have stable prototypes/ABIs, and they only compare what is measured:

- They do not automatically detect every enum width, bitfield packing, nested structure, callback calling convention, or error semantics.
- A native binary may export the right probe names while the prototypes of the probes themselves have changed; therefore, you must use a manifest version and check the baseline first.
- A different library version can have the same `sizeof` and `offsetof` while business logic has changed.
- An ABI mismatch can cause a crash before probes run if an imported prototype is severely wrong.
- For APIs with pointers and ownership, you need to smoke test release handles and error paths in addition to layout checks.

ABI checks help fail fast and reduce risk; **they do not turn every FFM downcall into memory-safe code if the C contract is wrong**.

## 9. Ensuring the Right Binary File Is Being Loaded

### 9.1. Loading the wrong version

Testing against `dist/native/libdemoabi.so` is worthless if production loads an old `/usr/local/lib/libdemoabi.so`. Conversely, if generated code uses `--library demoabi` without `--use-system-load-library`, native OS lookup may not follow `java.library.path`.

You need to know the exact loading mechanism:

- According to the OpenJDK jextract guide, `--library name` normally uses the native loader / `SymbolLookup.libraryLookup` mechanism; dependency lookup depends on the OS.
- `--use-system-load-library` switches the main library to `System.loadLibrary` and searches via `java.library.path`. **Dependent libraries** may still have to be resolved via OS PATH/RPATH/LD_LIBRARY_PATH.
- `--library :/absolute/path/libdemoabi.so` can request a specific path, suitable for test environments but not portable if a dev path is hardcoded.
- Use `-Xlog:library` on HotSpot when you need to investigate the actual load. Logs are only supporting evidence; combine them with SHA-256/hash manifests.
- When packaging, re-verify hashes **after** copying/compression/extraction or before publishing and in the installation test environment.

### 9.2. Inspecting exports and dependencies with OS tools

**Linux/ELF:**

```bash
nm -D --defined-only dist/native/libdemoabi.so
readelf -h dist/native/libdemoabi.so
readelf -d dist/native/libdemoabi.so
```

**macOS/Mach-O:**

```bash
nm -gU dist/native/libdemoabi.dylib
otool -L dist/native/libdemoabi.dylib
file dist/native/libdemoabi.dylib
```

**Windows/PE (MSVC Developer Command Prompt):**

```bat
dumpbin /exports dist\native\demoabi.dll
dumpbin /headers dist\native\demoabi.dll

```

Exports of the sample library:

```text

```

On macOS, `nm` may display a leading underscore per Mach-O conventions. Beyond symbol names, check architecture, linking dependencies, soname/install name, and version.

**Limitation:** having a symbol does not guarantee the right prototype. Under some C ABIs, symbol names do not encode parameter types, so changing `int32_t` to `int64_t` can still keep the old export and cause errors when called.

## 10. Standalone Java: BinaryExportGate Checking Exports of the Exact File

This is a **JDK 22+** program that inspects a library at **a specified path**, without needing jextract-generated code. It only checks export availability and does not call those functions.

### 10.1. File `smoke/BinaryExportGate.java`

```java
import java.lang.foreign.Arena;
import java.lang.foreign.SymbolLookup;
import java.nio.file.Path;

public final class BinaryExportGate {
    public static void main(String[] args) {
        if (args.length < 2) {
            throw new IllegalArgumentException(
                    "Usage: BinaryExportGate absoluteLibraryPath "
                    + "export1 [export2 ...]");
        }

        Path library = Path.of(args[0]).toAbsolutePath();

        try (Arena arena = Arena.ofConfined()) {
            SymbolLookup lookup = SymbolLookup.libraryLookup(
                    library, arena);

            for (int i = 1; i < args.length; i++) {
                String symbol = args[i];

                if (lookup.find(symbol).isEmpty()) {
                    throw new IllegalStateException(
                            "Missing export: " + symbol);
                }

                System.out.println("Export present: " + symbol);
            }
        }
    }
}
```

**Build/run on Linux with the exact distributed library:**

```bash
javac -d build/classes smoke/BinaryExportGate.java

java --enable-native-access=ALL-UNNAMED \
  -cp build/classes \
  BinaryExportGate "$(pwd)/dist/native/libdemoabi.so" \
  demo_abi_major demo_record_size demo_total_offset demo_add demo_sum_record
```

On macOS/Windows, use the corresponding `.dylib`/`.dll` path. If an export is missing, the gate throws `IllegalStateException` and CI exits with a non-zero code. If the library fails to load due to wrong architecture/dependency, lookup fails early.

**Test performed on JDK 24 Windows:** the program compiled/ran against `kernel32.dll`, confirming real exports `GetCurrentProcessId`, `GetFileAttributesW`; intentionally looking up a non-existent symbol produced the expected failure. Because the test machine had no C compiler, **BinaryExportGate has not been run on the sample demoabi.dll itself**. This gate is an additional safeguard; `AbiSmoke` remains mandatory.

## 11. Standalone Java: Checking SHA-256 of Header and Binary

`ArtifactShaGate` runs on **JDK 17+** and does not depend on jextract or FFM. It only confirms that the bytes of two files match SHA-256 values from a **trusted manifest**.

### 11.1. File `smoke/ArtifactShaGate.java`

```java
import java.io.InputStream;
import java.nio.file.Files;
import java.nio.file.Path;
import java.security.MessageDigest;
import java.util.HexFormat;

public final class ArtifactShaGate {
    private static String sha256(Path path) throws Exception {
        MessageDigest hash = MessageDigest.getInstance("SHA-256");

        try (InputStream in = Files.newInputStream(path)) {
            byte[] buffer = new byte[8192];
            int n;

            while ((n = in.read(buffer)) != -1) {
                hash.update(buffer, 0, n);
            }
        }

        return HexFormat.of().formatHex(hash.digest());
    }

    private static void check(
            String label, String file, String expected) throws Exception {
        String actual = sha256(Path.of(file));

        if (!actual.equalsIgnoreCase(expected)) {
            throw new IllegalStateException(
                    label + " SHA-256 mismatch");
        }

        System.out.println(label + " hash: OK");
    }

    public static void main(String[] args) throws Exception {
        if (args.length != 4) {
            throw new IllegalArgumentException(
                    "Usage: ArtifactShaGate header expectedHeaderSha256 "
                    + "library expectedLibrarySha256");
        }

        check("Header", args[0], args[1]);
        check("Binary", args[2], args[3]);
    }
}
```

**In Linux CI**, the two environment variables come from a trusted release manifest, not from computing hashes on the same files right before:

```bash
javac -d build/classes smoke/ArtifactShaGate.java

java -cp build/classes ArtifactShaGate \
  dist/include/demoabi.h "$EXPECTED_HEADER_SHA256" \
  dist/native/libdemoabi.so "$EXPECTED_LIBRARY_SHA256"
```

**Stdout when both checksums match:**

```text
Header hash: OK
Binary hash: OK
```

If either digest is wrong, the gate throws `IllegalStateException` and returns a non-zero exit code. **Actual test run on JDK 24:** both positive (both hashes correct) and negative (header hash altered to wrong value) cases were verified using independent fixture files. Do not interpret fixture testing as having verified the vendor's demoabi set.

### 11.2. SHA-256 does not mean ABI compatibility

Two files whose hashes match the manifest can still be a **mismatched release pair** if the manifest is wrong or unauthenticated. Hashes check **the exact bytes**, not function signatures, compiler ABI, export semantics, or runnability. Combine them with signatures/provenance, proper native binary loading, export inspection, ABI probes, and behavior tests.

## 12. Breaking Change Example: v3 Header with v2 Binary

v2 has:

```c
#define DEMO_ABI_MAJOR 2
struct DemoRecord {
    int32_t id;
    int32_t flags;
    int64_t total;   /* offset 8 */
};
```

v3 (different ABI) might change to:

```c
#define DEMO_ABI_MAJOR 3
struct DemoRecord {
    int64_t total;  /* offset 0 */
    int32_t id;
    int32_t flags;
};
```

On common 64-bit ABIs, both structs can still be **16 bytes** long, and the v2 binary can still export all the same function names. The outcome can be:

- `jextract` generates `DemoRecord.total$offset() == 0` from the v3 header.
- `javac` compiles Java using the v3 generated class successfully.
- The v2 binary executes `demo_abi_major() == 2` and `demo_total_offset() == 8`.
- `AbiSmoke` hits an **ABI major mismatch** before dereferencing the struct.
- If the vendor forgot to bump the version macro, the **offset** comparison still detects the mismatch even though `sizeof` is identical.

This is why **export-only** and **size-only** tests are not enough. If Java tries to call `demo_sum_record` with the new layout on the old binary, native code can read the wrong fields, return wrong results, and in severe cases cause memory corruption.

What about **unchanged header, changed binary**? You do not necessarily have to regenerate bindings when inputs truly have not changed, but you must re-run export checks, digest checks, and native behavior smoke tests on the new binary. Bugs that change semantics do not show up in a header diff.

## 13. ABI Hazards to Audit When Reviewing Regeneration

### 13.1. Struct packing and alignment

`#pragma pack`, GCC/Clang attributes, and MSVC `/Zp` can change offsets or alignment even when field names remain unchanged. For structs with nested fields, unions, or pointers, checking only `sizeof` of the outer struct can also be insufficient. Use `sizeof`/`_Alignof`/`offsetof` probes on key type fields and compare against jextract-generated layouts.

### 13.2. Native type widths by OS/architecture

On x64 Windows, C `long` is typically 32-bit (LLP64), whereas on x64 Linux it is typically 64-bit (LP64). `size_t`, `wchar_t`, and pointer width also differ by platform. Using `int32_t`/`int64_t` can improve portability, but **does not replace** ABI testing.

### 13.3. C++ mangled symbols and calling convention

If a library is written in C++, provide a C-compatible exported wrapper layer with `extern "C"` when jextract needs to process C headers. On some ABIs such as Windows x86, `__stdcall`/`__cdecl` and symbol decoration differ. Do not assume that a `demo_add` with the same name has the same calling convention and parameter passing.

### 13.4. Opaque pointers and ownership

A C function that keeps the prototype `void* get_resource()` but changes its contract from "borrowed pointer" to "caller must free" will not automatically cause jextract to report an error. The Java wrapper needs to be updated to call **the right destructor**, avoiding double-free and use-after-free. Tests that only check returned numbers do not detect lifecycle bugs.

### 13.5. Callbacks and function pointers

A callback that changes signature or thread rules can crash the JVM even while the main native function symbol still exists. CI needs to test callback upcalls/downcalls and the lifetime of the `Arena` holding the stub, as well as the error policy.

### 13.6. Unsupported C constructs

jextract currently does not fully support all C constructs; the guide describes cases such as function-like macros, bitfields, opaque declarations, and some uncommon types. You must review warnings and generated API coverage. When needed, create exported C wrapper functions or handwritten Java/FFM glue instead of silently dropping declarations.

## 14. Recommended CI/CD Workflow

One pipeline for **each supported OS/architecture**:

```text
1. Fetch headers + binaries + dependencies from a trusted release.
2. Verify signed manifest / checksums of exact staged artifacts.
3. Record JDK, jextract, Clang, compiler flags, OS and CPU ABI.
4. Regenerate bindings from the release header set in a CLEAN dir.
5. Compare generated output against expected API/layout baseline.
6. Compile all generated Java and handwritten wrappers.
7. Inspect native binary format, arch, deps and required symbols.
8. Run ABI major/sizeof/offsetof checks on staged binary.
9. Run primitive and struct smoke calls, then ownership/error tests.
10. Package the same tested binary + bindings/dependencies.
11. Recheck hashes of packaged artifact before release.
12. Publish only if all gates pass.
```

**Why this order?** If the ABI is wrong, you should not call complex native functions before probing; if the binary hash is wrong, smoke testing it should not be treated as evidence for an official release; if packaging copies the wrong DLL/so, pre-package testing does not prove end users will receive the right binary.

With a CI matrix, you can split by platform:

| Platform | Library | Tools for exports / deps | Risks |
| --- | --- | --- | --- |
| Linux x86_64 / arm64 | `libdemoabi.so` | `nm -D`, `readelf` | ELF architecture, glibc/deps, LP64 |
| macOS x86_64 / arm64 | `libdemoabi.dylib` | `nm -gU`, `otool -L` | Mach-O slices/install name |
| Windows x64 | `demoabi.dll` | `dumpbin /exports`, `/dependents` | PE architecture, CRT, LLP64 |

If a project supports only one platform, test that exact platform and state the support matrix honestly; do not claim portability if it has not been verified.

### Guarding against stale generated files

If generated Java is committed, CI can run regeneration with the same toolchain and diff against the committed version. If not committed, the build must invalidate caches on header closure/generator flags/JDK. Avoid mixing old and new classes in the same output directory.

A warning from jextract due to a missing typedef or unsupported declaration must not be ignored just because compilation still succeeds. Compare the list of intended exported functions against the list of generated methods and baseline tests.

### Valuable negative tests

- Intentionally pair the v3 header with the v2 binary: the ABI major or offset test **must fail**.
- Remove a required symbol from a test fixture binary: `BinaryExportGate` **must fail**.
- Alter one byte in a header fixture or binary fixture: `ArtifactShaGate` **must fail**.
- Test the loader in an environment with **two versions of the same name** and ensure only the exact packaged binary is loaded.
- Change a `-D` macro affecting a struct to ensure the build detects that generated output/layout changed.
- Switch to an incompatible arch/ABI and ensure the release pipeline rejects it.

Do not create a test that executes a pointer with the wrong layout **after already knowing an ABI mismatch** just to see if the JVM crashes; failing fast is the safer testing approach.

## 15. Troubleshooting

| Symptom | Cause to check | How to fix |
| --- | --- | --- |
| `jextract` command not found | External tool not installed / wrong PATH | Install the right build and check `jextract --version` |
| Generated code fails to compile on current JDK | jextract targets a different FFM API / JDK mismatch | Pin a compatible generator + JDK |
| Root header unchanged but generated code changed | Different transitive header, macros, Clang/SDK/target | Compare preprocessor inputs and toolchain |
| Old Java symbol still compiles even though C header removed function | Generated directory was not cleaned | Generate into a fresh output, clean compile |
| `NoSuchElementException` when resolving function | Missing symbol or wrong version loaded | Inspect exports and exact loaded library |
| `UnsatisfiedLinkError`/load failure | Wrong OS/architecture/dependency/path | Check ELF/PE/Mach-O and OS search paths |
| `ABI major mismatch` | Header/binary release pair does not match | Block launch, fetch the right artifact version |
| Struct size matches but offset is wrong | Reordered fields, packing, or compiler flags | Compare offset probes and generated layout |
| Exports present but call returns wrong value | ABI types, calling convention, or semantic regression | Check descriptor, native function behavior |
| JVM crash | Wrong native pointer/layout/prototype/lifetime | Stop, analyze crash log + native sanitizer |
| Local smoke passes but package fails | Wrong binary/dependency copied or dynamic lookup path | Verify packaged hashes and actual loader behavior |
| Windows CI passes, Linux fails | LLP64/LP64, preprocessing, different lib version | Run jextract + smoke per platform |

**Remember:** being able to load a library does not mean the ABI is right. The OS loader does not validate struct field offsets, function return conventions, or memory ownership. Do not fix a mismatch by disabling bounds checks or blindly casting pointers.

## 16. Self-Check Exercises

**Question 1.** `jextract` runs successfully and `javac` reports no errors. Why do we still need to smoke test with the binary?

**Answer:** jextract generates bindings from the header, and javac checks Java source; neither guarantees the actual binary has the same symbols, ABI/layout, or semantics. You need to run against the exact distributed binary.

**Question 2.** A header adds a field to a struct without changing any exported function name. Do we need to regenerate?

**Answer:** Yes if it changes the public ABI; you must regenerate, check layout offsets, and release a matching binary. Function names alone are not enough.

**Question 3.** Why is `demo_total_offset` needed alongside `demo_record_size`?

**Answer:** v2/v3 structs can both have `sizeof == 16` while the `total` field moves from offset 8 to 0. Testing size alone cannot detect that.

**Question 4.** With a new binary and unchanged headers, do we always need to regenerate bindings?

**Answer:** Not necessarily when all generator inputs/ABI are unchanged, but it is mandatory to test the new binary, exported symbols, dependencies, and semantics.

**Question 5.** Does `--library demoabi` guarantee loading the binary in `dist/native`?

**Answer:** No. The loader depends on the OS and jextract configuration; with `--use-system-load-library`, you can specify `java.library.path` for the main library, but dependencies still follow OS rules.

**Question 6.** The hashes of the header/binary match a manifest that the machine just created from those same files being checked. Does that prove the release is right?

**Answer:** No. Expected hashes must come from an independent trusted manifest/signature; comparing a file against a hash just computed from itself does not verify provenance.

**Question 7.** `DemoRecord.sizeof() == demo_record_size()`. Can we skip the other tests?

**Answer:** No. You need version, offset, symbol, signature, semantics, and ownership checks; matching size does not guarantee matching offsets.

**Question 8.** Windows x64 and Linux x64 are both 64-bit. Can we always share the same C `long` layout?

**Answer:** No. Windows x64 is typically LLP64, while Linux x64 is LP64. C `long` and `size_t` must be verified against the target ABI; use fixed-width types where appropriate.

**Question 9.** Does storing generated sources in the repo mean we no longer need jextract on CI?

**Answer:** To verify that source regeneration is accurate, CI should still run the pinned generator and check the diff. If you choose not to regenerate on every build, you at least need a gate that regenerates when inputs change.

**Question 10.** Why is `BinaryExportGate` not enough to prove the ABI?

**Answer:** It only confirms the file can be loaded and contains the symbol names. C function prototypes/layouts can be wrong even with the same names.

**Question 11.** When encountering `NoSuchElementException` in a generated binding, should you catch the exception and continue calling native code via another pointer?

**Answer:** No. Check the binary version, exported symbols, and load path. That could be a release mismatch, so fail fast instead of guessing function names/addresses.

**Question 12.** Are ownership tests necessary if ABI major/offset/size all match?

**Answer:** Yes. `void*`/callbacks can keep the same signature while changing borrowed/owned semantics, threading requirements, or lifetimes; jextract cannot verify this.

## 17. Summary

- **Regenerate jextract** when public headers, transitive includes, macros, compiler ABI, target platform, or generator inputs change.
- **Verify the native binary** for every release artifact, even when headers have not changed.
- **Verify the exact file:** trusted SHA-256, right OS/arch/loader/dependencies, without accidentally loading another library of the same name.
- **Do not check only compilation or exports:** compare header vs. runtime ABI major, `sizeof`, `offsetof`, calling convention, and function results.
- **Generate code into a clean directory**, pin jextract/JDK/libclang, and review diffs/generated warnings.
- **Catch errors before dereferencing** structs or using pointers whose ABI has not been verified.
- **Smoke test on the exact binary being shipped**, then re-verify the package. This connects the public header, Java bindings, and binary into a verifiable release unit.
