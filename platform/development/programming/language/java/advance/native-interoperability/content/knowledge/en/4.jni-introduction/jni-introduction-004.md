# Role of `jni.h`, platform-specific headers, `JNIEXPORT`, and `JNICALL`

> **Topic:** Java Advance — Native Interoperability · **Section:** First JNI. This lesson explains four components that commonly appear right when writing JNI for the first time: what `jni.h` provides, why there is an OS-dependent header, why `javac -h` generates a separate header for the Java class, and what `JNIEXPORT`/`JNICALL` guarantee at the Java–C/C++ boundary.

## 1. Looking at the full path of a JNI call

**Java Native Interface (JNI)** is the standard interface for code running in the JVM to call native code (usually written in C/C++) and for native code to interact back with Java classes, objects, arrays, strings, exceptions, and methods.

For example, when Java declares:

```java
package demo.jni;

public class NativeMath {
    public static native int add(int left, int right);
}
```

The `native` modifier tells the JVM that the method has no Java body; when the method is linked and called, the JVM searches for the corresponding native implementation in a loaded library. The implementation must conform to the **ABI (Application Binary Interface)** and the JNI contract: symbol name or manual registration, data types, parameter order, calling convention, and how to interact with the JVM.

```text
Java Code (.java)
    |
    | javac -h ...                (generates class + native declaration header)
    v
NativeMath.class        demo_jni_NativeMath.h
    |                            |
    | System.loadLibrary(...)    | #include <jni.h>
    v                            | #include "jni_md.h" (indirectly)
JVM/JNI linker <-----------------+----------------+
    |                                             |
    | find JNI symbol                             | C compiler + linker
    v                                             v
Java_demo_jni_NativeMath_add(...)   <----   libnative_math.so / .dylib / native_math.dll
                      (called inside the JVM process itself)
```

Here are **the three header layers to distinguish**:

1. **`jni.h`:** the common JNI header provided by the JDK. It declares JNI types, `JNIEnv`, `JavaVM`, the JNI function table, and the necessary macros/structures.
2. **`jni_md.h`:** the platform header provided by the JDK, included by `jni.h` to get machine/ABI-dependent definitions, such as certain platform integer types and export decoration.
3. **`demo_jni_NativeMath.h`:** the **application's** header, generated by `javac -h` from the `native` methods of a specific class. It contains the exact prototypes of the Java ↔ native functions.

`jni.h` is not a per-project header; and the header generated by `javac -h` is **not** a copy of `jni.h`. Both work together so that native code has declarations matching the JVM and the Java class.

## 2. Role of `jni.h`: the common contract with the JVM

Typically, C code can write:

```c
#include <jni.h>
```

This header (and the headers it includes) provides:

| Component | Example | Role |
|---|---|---|
| JNI primitive types | `jboolean`, `jbyte`, `jchar`, `jshort`, `jint`, `jlong`, `jfloat`, `jdouble` | Accurately represent Java data types across the JNI ABI |
| Reference types | `jobject`, `jclass`, `jstring`, `jarray`, `jintArray` | JNI references to object/class/string/array managed by the JVM |
| JNI environment | `JNIEnv`, `JNIEnv *env` | Access JVM functions on the current thread: read fields, call methods, create strings, handle exceptions, etc. |
| Virtual machine interface | `JavaVM` | Access JVM-related operations, such as attaching/detaching native threads |
| Auxiliary types and values | `jsize`, `jmethodID`, `jfieldID`, `JNI_OK`, `JNI_VERSION_1_8` | Sizes, IDs for methods/fields, status, and version |
| Declaration helper macros | `JNIEXPORT`, `JNICALL` | Export symbols and standardize the calling convention per platform/JDK |

**Do not replace JNI types with C types by intuition.** For example, Java `int` maps to `jint`, Java `long` to `jlong`; C `long` has different sizes across ABIs, especially Windows x64 and Linux x64. Java `char` is a 16-bit UTF-16 unit, so JNI uses `jchar` rather than simply using C `char`. A Java String does not automatically turn into `char *`: JNI passes `jstring`, and to get bytes/characters you use API functions with the appropriate release rules.

### `JNIEnv` is not an ordinary Java object

A native method written in **C** can call a JNI function:

```c
/* Illustrative fragment; only use inside a valid native method. */
jstring result = (*env)->NewStringUTF(env, "Hello JNI");
```

In **C++**, the `JNIEnv` wrapper supports a different syntax:

```cpp
// Illustrative fragment; only use inside a valid native method.
jstring result = env->NewStringUTF("Hello JNI");
```

Both syntaxes use the same JNI function table. The difference lies in the definition of `JNIEnv` for C/C++, not in the Java method signature.

**Thread rule:** `JNIEnv*` is only valid on the thread that received it. Do not store `env` and carry it to another native thread to use; a self-created native thread must attach to the JVM according to JNI rules and detach appropriately. Similarly, a JNI local reference usually only lives within the corresponding thread/native call context; if you want to keep an object longer, you must understand global references and their lifecycle.

## 3. Why does `jni.h` need the platform header `jni_md.h`?

The JNI API surface is quite consistent across operating systems, but how it compiles into machine code still depends on **OS, CPU architecture, ABI, compiler/toolchain**. Therefore, the JDK is usually organized as:

```text
<JDK_HOME>/
  include/
    jni.h                 # common JNI interface
    jvmti.h               # another API, not needed for this JNI example
    linux/
      jni_md.h            # ABI configuration of the Linux JDK build
    darwin/
      jni_md.h            # ABI configuration of the macOS JDK build
    win32/
      jni_md.h            # ABI configuration of the Windows JDK build
```

The diagram shows **three different JDK installations** for comparison, not a single JDK directory containing all three platforms. Depending on the JDK vendor, some platform subdirectories may differ. When building on Linux, take the Linux header of the corresponding JDK; on macOS take the `darwin` header; on Windows take `win32`, even when the Windows machine is 64-bit.

`jni.h` contains a simple include directive by name:

```c
#include "jni_md.h"
```

Therefore, the compiler must be pointed to **both include directories**. For Linux:

```bash
-I"$JAVA_HOME/include" -I"$JAVA_HOME/include/linux"
```

The equivalent on macOS:

```bash
-I"$JAVA_HOME/include" -I"$JAVA_HOME/include/darwin"
```

And on Windows with the MSVC Developer Command Prompt:

```bat
/I"%JAVA_HOME%\include" /I"%JAVA_HOME%\include\win32"
```

`jni_md.h` typically specifies some machine-dependent types, visibility/export, and platform details matching the ABI. **Do not edit `jni_md.h` directly** to fix build errors. Choose the right JDK/target platform/toolchain, then configure the include path; editing JDK headers will easily create wrong bindings that are hard to debug.

### Do not mix incompatible headers and binaries

For example, a project compiles native code for the Linux x86-64 ABI but deploys a Windows x64 DLL: both are "64-bit", yet the binary format, calling convention, system libraries, and linking method are completely different. You need to align **JDK headers + compiler target + OS/CPU + native library**. When cross-compiling, you must have the appropriate target headers/toolchain rather than grabbing the host's `jni_md.h` arbitrarily.

If the compiler reports `fatal error: jni.h: No such file or directory`, the `include` path is usually missing or pointing to the wrong JRE/JDK. If it reports `fatal error: jni_md.h: No such file or directory`, `jni.h` was usually found, but **the platform-specific include path is missing**.

## 4. `JNIEXPORT` and `JNICALL` have two different responsibilities

The familiar template:

```c
JNIEXPORT jint JNICALL Java_demo_jni_NativeMath_add(
    JNIEnv *env,
    jclass clazz,
    jint left,
    jint right
);
```

Reading from left to right:

| Component | Meaning |
|---|---|
| `JNIEXPORT` | Tells the compiler/linker to **export** the function across the dynamic library boundary in a platform-appropriate way |
| `jint` | Native return value type, corresponding to Java `int` |
| `JNICALL` | Selects the **calling convention** that JNI/JVM expects for the native function |
| `Java_demo_jni_NativeMath_add` | Symbol corresponding to class `demo.jni.NativeMath`, method `add` according to JNI name mapping rules |
| `JNIEnv *env` | Pointer to the JNI interface of the current thread |
| `jclass clazz` | The class declaring the method, because `add` is `static native` |
| `jint left, jint right` | Two Java `int` parameters mapped to JNI `jint` |

### `JNIEXPORT`: the function must be present in the symbol table

On Windows, DLL exports typically use a mechanism like `__declspec(dllexport)`. On Unix-like systems, the compiler/linker has a symbol visibility mechanism; some JDKs implement `JNIEXPORT` with an appropriate visibility attribute, while some implementations leave it empty when symbols are exported by default. **The exact expansion is a platform/JDK-version detail**, which is why code authors use the macro provided by the JDK instead of hard-coding it themselves.

Without proper export, C code may **compile/link successfully**, but the JVM will not find the symbol when linking the native method. On Windows, `JNIEXPORT` is especially important when building a DLL. Even on Linux, building with `-fvisibility=hidden` can hide the function if the appropriate export annotation is missing.

### `JNICALL`: caller and callee must agree on the ABI

The **calling convention** specifies how parameters are placed (registers/stack), return rules, and ABI-level details. Historically on Win32 x86, JNI used a `__stdcall`-style convention; on many modern ABIs, the default convention already matches and the macro may expand to empty. There is no need to guess what `JNICALL` expands to on your machine.

If caller and callee disagree on the calling convention, the application may handle parameters incorrectly or corrupt the stack; such bugs are particularly hard to trace on older 32-bit configurations. `JNICALL` does **not** mean a Java callback, async call, fast call, or thread management mechanism. It only ensures that the native function declaration adheres to the required convention.

### The two macros are not interchangeable

- `JNIEXPORT` handles **symbol visibility from outside the library**.
- `JNICALL` handles **how machine code performs the function call**.
- The `Java_...` name handles **which native method the JVM finds**.

All three elements are needed to form a proper static binding according to the naming convention. Besides using the `Java_...` name, JNI also supports `RegisterNatives` to register function pointers, but in a first practical exercise you should use the header generated by `javac -h` to avoid mapping errors.

## 5. Writing and running a JNI example from scratch: Java 17+

The following example intentionally has **one `static native` method and one `instance native` method** to compare `jclass` and `jobject`. All numbers are small, so there is no need to discuss overflow in this hands-on section.

Requirements: JDK 17+, a platform-compatible C compiler, `JAVA_HOME` set to point to the JDK directory in use; the main command examples use Linux with GCC.

### Step 1 — Write the Java class

Create `src/demo/jni/NativeMath.java`:

```java
package demo.jni;

public final class NativeMath {
    static {
        System.loadLibrary("native_math");
    }

    public static native int add(int left, int right);

    public native int doubleValue(int value);

    public static void main(String[] args) {
        System.out.println("add=" + add(20, 22));
        System.out.println("double=" + new NativeMath().doubleValue(21));
    }
}
```

- `System.loadLibrary("native_math")` takes the **logical library name**, not a filename with `.so`, `.dll`, or `.dylib`.
- `native` declares a method without a Java body. Native implementations can reside in the same shared library.
- `static native` receives `jclass` as the second JNI argument; instance native receives `jobject` (the `this` object).

### Step 2 — Use `javac -h` to generate prototypes

In the project root directory:

```bash
mkdir -p build/classes build/headers
javac -d build/classes -h build/headers src/demo/jni/NativeMath.java
```

Since JDK 17, `javac -h` is the official way to generate JNI native headers. The command above creates:

```text
build/classes/demo/jni/NativeMath.class
build/headers/demo_jni_NativeMath.h
```

The key content of `build/headers/demo_jni_NativeMath.h` looks like:

```c
/* DO NOT EDIT THIS FILE - it is machine generated */
#include <jni.h>
/* Header for class demo_jni_NativeMath */

#ifndef _Included_demo_jni_NativeMath
#define _Included_demo_jni_NativeMath

#ifdef __cplusplus
extern "C" {
#endif

/*
 * Class:     demo_jni_NativeMath
 * Method:    add
 * Signature: (II)I
 */
JNIEXPORT jint JNICALL Java_demo_jni_NativeMath_add
  (JNIEnv *, jclass, jint, jint);

/*
 * Class:     demo_jni_NativeMath
 * Method:    doubleValue
 * Signature: (I)I
 */
JNIEXPORT jint JNICALL Java_demo_jni_NativeMath_doubleValue
  (JNIEnv *, jobject, jint);

#ifdef __cplusplus
}
#endif
#endif
```

Some whitespace, comments, or include guards may vary across compiler versions; **the prototypes and parameter types are the contract that must match**. In `(II)I`, the two `I`s inside the parentheses mean two Java `int` parameters, and the `I` after the parentheses is the `int` return type. `(I)I` means one `int` parameter and an `int` return value.

Note that this header is **generated from Java code** and includes `jni.h` itself. Do not hand-write or edit symbol names in the header; when Java declarations change, re-run `javac -h` and rebuild the C library.

### Step 3 — Write the implementation in C

Create `native/NativeMath.c`:

```c
#include "demo_jni_NativeMath.h"

JNIEXPORT jint JNICALL Java_demo_jni_NativeMath_add(
        JNIEnv *env, jclass clazz, jint left, jint right) {
    (void) env;
    (void) clazz;
    return left + right;
}

JNIEXPORT jint JNICALL Java_demo_jni_NativeMath_doubleValue(
        JNIEnv *env, jobject self, jint value) {
    (void) env;
    (void) self;
    return value * 2;
}
```

This is a complete C file (linked into a dynamic library). `(void) env` and `(void) clazz/self` are only to prevent the compiler from warning about **unused parameter**; the JVM still passes all of those arguments.

The generated header protects consistency through prototypes. If the C implementation has the wrong return type, is missing `JNIEnv*`, or swaps `jclass`/`jobject`, the compiler has a chance to catch **conflicting types** at build time, instead of waiting for the JVM to fail at runtime.

### Step 4 — Compile the Linux library

```bash
gcc -std=c11 -fPIC -shared \
  -I"build/headers" \
  -I"$JAVA_HOME/include" \
  -I"$JAVA_HOME/include/linux" \
  -o libnative_math.so native/NativeMath.c
```

Flag explanations:

- `-Ibuild/headers`: finds the `demo_jni_NativeMath.h` header that `javac` just generated.
- `-I$JAVA_HOME/include`: finds the JDK's `jni.h`.
- `-I$JAVA_HOME/include/linux`: finds `jni_md.h` for the Linux target.
- `-fPIC`: generates position-independent code suitable for a shared library.
- `-shared -o libnative_math.so`: creates the dynamic library for Linux, whose name is mapped by `System.loadLibrary("native_math")`.

### Step 5 — Run Java and verify

JDK 17–23:

```bash
java -Djava.library.path=. -cp build/classes demo.jni.NativeMath
```

With JDK 24+, you should grant native access to the application on the classpath:

```bash
java --enable-native-access=ALL-UNNAMED \
  -Djava.library.path=. -cp build/classes demo.jni.NativeMath
```

**Expected stdout (excluding tool diagnostics):**

```text
add=42
double=42
```

`-Djava.library.path=.` tells the JVM to look for JNI libraries in the current working directory. If you do not want to depend on the current directory, you can use `System.load(absolutePath)` and manage the absolute path; `System.loadLibrary` still takes a logical name. Do not confuse `java.library.path` with the classpath: `-cp build/classes` is for finding `.class` files, while `java.library.path` is for finding native libraries.

### Corresponding names and commands on macOS

The Java source/header are compiled similarly. Use the Clang/Xcode command-line tools compiler:

```bash
clang -std=c11 -dynamiclib -fPIC \
  -I"build/headers" \
  -I"$JAVA_HOME/include" \
  -I"$JAVA_HOME/include/darwin" \
  -o libnative_math.dylib native/NativeMath.c
```

Then run Java with the same classpath and `-Djava.library.path=.`; pass `--enable-native-access=ALL-UNNAMED` for JDK 24+. The macOS library has the `.dylib` extension instead of Linux `.so`.

### Corresponding names and commands on Windows

In the **Developer Command Prompt for Visual Studio** with MSVC and `JAVA_HOME` pointing to the Windows JDK:

```bat
mkdir build\classes
mkdir build\headers
javac -d build\classes -h build\headers src\demo\jni\NativeMath.java
cl /LD /I"build\headers" /I"%JAVA_HOME%\include" /I"%JAVA_HOME%\include\win32" native\NativeMath.c /link /OUT:native_math.dll
java --enable-native-access=ALL-UNNAMED -Djava.library.path=. -cp build\classes demo.jni.NativeMath
```

The run command above is for JDK 24+; if using JDK 17–23, omit `--enable-native-access=ALL-UNNAMED`. `mkdir` may report that the directories already exist if re-run; you can keep the existing directories. The DLL is `native_math.dll`, without a `lib` prefix. The MSVC toolchain may also produce `.obj` and `.lib` files; those are toolchain artifacts. Linux/macOS and Windows shell commands are not directly interchangeable.

## 6. Why is the auto-generated header better than guessing function names?

Traditional JNI dynamic linking maps Java names to C symbols. For class `demo.jni.NativeMath`, the non-overloaded `add` method has the short form:

```text
Java_demo_jni_NativeMath_add
```

The `demo_jni` part is the package transformed according to JNI name mangling. Underscores appearing in Java source names have their own escaping rules; you must not assume that every `_` in a Java name is merely a package separator.

With two overloaded `native` methods:

```java
// Illustrative fragment, not a standalone class to run.
native int scale(int value);
native long scale(long value);
```

The long name in JNI usually has a parameter suffix:

```text
Java_demo_jni_Scale_scale__I
Java_demo_jni_Scale_scale__J
```

`I` is the Java `int` parameter descriptor; `J` is `long`. This example assumes both methods are in class `demo.jni.Scale`. Mangling also has rules for objects/arrays, dots, underscores, and Unicode characters. **Use `javac -h`** to get the right prototypes, especially when there are overloads; do not concatenate strings or rename prototypes by guesswork.

`javac -h` generates **compile-time-checked prototypes**; it does not generate the C implementation and does not automatically build `.so`/`.dylib`/`.dll`. When changing Java signatures, package names, or modifiers, you must regenerate the header and the corresponding library.

## 7. C and C++: keeping the right linkage

A C++ compiler performs **name mangling** to support overloads and namespaces. The JVM, however, searches for a symbol following the JNI naming convention; a C++-mangled symbol will not match the name.

The header generated by `javac -h` usually wraps prototypes with:

```cpp
#ifdef __cplusplus
extern "C" {
#endif
// JNI prototypes
#ifdef __cplusplus
}
#endif
```

The `extern "C"` construct tells the compiler that the declarations inside use **C linkage**. If you write the native implementation in `.cpp`, include the generated header and ensure the definition has the same C linkage. Illustrative example for the `add` method above:

```cpp
// C++ fragment: replaces the C definition of add when building with C++.
#include "demo_jni_NativeMath.h"

extern "C" JNIEXPORT jint JNICALL Java_demo_jni_NativeMath_add(
        JNIEnv *env, jclass clazz, jint left, jint right) {
    (void) env;
    (void) clazz;
    return left + right;
}
```

This fragment does not have the `doubleValue` implementation yet, so it is not a complete library for the exercise's Java class. When writing the entire binding in C++, define both methods with the right prototypes. Using `extern "C"` does **not** mean JNI only runs C: the implementation can still use C++ features internally; only the ABI/exported symbol is restricted to C linkage.

## 8. Distinguishing compile, load, and native method link errors

The execution flow has **three different error stages**:

| Stage | Typical symptom | How to check |
|---|---|---|
| **Compile native code** | `jni.h: No such file or directory` | Missing `-I<JDK>/include` or wrong `JAVA_HOME` |
| **Compile native code** | `jni_md.h: No such file or directory` | Missing corresponding `-I<JDK>/include/linux`, `darwin`, or `win32` |
| **Compile native code** | `conflicting types for 'Java_...'` | `javac -h` header and C definition have different signatures, missing/extra types |
| **Load library** | `UnsatisfiedLinkError: no native_math in java.library.path` | Wrong logical name, directory, file extension, permissions |
| **Load library** | Reports wrong architecture, missing dependent DLL/`.so`, loader error | Wrong bitness/OS/CPU, dependent libraries, toolchain runtime |
| **Link method** | `UnsatisfiedLinkError` mentioning the Java native method/signature | The library may have loaded, but lacks the exact symbol, export is hidden, wrong name, or missing function |

### Commands to inspect exported symbols

On Linux, after building:

```bash
nm -D --defined-only libnative_math.so | grep Java_
```

With Windows and the MSVC Developer Command Prompt:

```bat
dumpbin /EXPORTS native_math.dll
```

On macOS, you can use `nm -gU libnative_math.dylib` to view global external symbols; names may show an extra leading underscore per the Mach-O tool convention. What matters is that **the JNI symbol has the right name and is exported**, not just that the file exists.

When debugging, separate three questions: (1) did the compiler find the right headers? (2) did the JVM load the right library? (3) did the library export the right native symbol? Lumping them into one "JNI doesn't work" error turns troubleshooting into guesswork.

## 9. Common misconceptions about macros and headers

1. **“Just including `jni.h` lets the compiler find everything automatically.”** Not enough: the compiler must also find the target's `jni_md.h` and the application header generated by `javac -h` if the code includes it.
2. **“`jni.h` is the header generated from the Java class.”** False: `jni.h` is the common API from the JDK; `javac -h` generates prototypes for your class.
3. **“`JNIEXPORT` and `JNICALL` are just for pretty code.”** False: they express symbol export / calling convention requirements; omitting them incorrectly can cause load/link or ABI errors.
4. **“`JNIEXPORT` always expands the same on every OS/JDK.”** False: how symbols are exported depends on the toolchain and header version; use the macro from the JDK instead of copying an expansion manually.
5. **“`JNICALL` always makes JNI calls faster.”** False: it determines the required calling convention, not guaranteed latency or throughput.
6. **“A `static` native method receives `jobject this`.”** False: static receives `jclass`; instance receives `jobject`; both have `JNIEnv*` before it.
7. **“Java `long` is always C `long`.”** False: use `jlong`; C primitives can differ in size across ABIs.
8. **“`System.loadLibrary` takes `libnative_math.so`.”** Incorrect in the example: pass the logical name `native_math`, letting the JVM map it to the OS-specific library name.
9. **“C++ exports functions with the same name as C if the function name looks identical.”** Not always true: you must control C linkage, usually via the `javac -h` header with `extern "C"`.
10. **“Having the right header guarantees the library runs safely.”** False: JNI runs native code in the same JVM process; invalid pointer access, use-after-free, or native crashes can still bring down the JVM.

## 10. Native access on newer JDKs, compatibility, and maintenance

Starting with **JDK 24 (JEP 472)**, using sensitive JNI operations such as loading native libraries and linking native methods is governed by the **native access** policy. For modules not granted permission, JDK 24 issues a warning by default; handling behavior can be adjusted with `--illegal-native-access` and will be tightened in future JDK releases.

- Running on the **classpath**: `--enable-native-access=ALL-UNNAMED`.
- Running a **named module** application: grant permission specifically, e.g., `--enable-native-access=my.module`, to the module using native access.
- To detect missing permissions early, on supported JDKs you can test with `--illegal-native-access=deny`.
- `JNIEXPORT`, `JNICALL`, and headers do not replace declaring native access permission for the Java runtime.
- Granting native access does not make native code memory-safe; input validation, ownership, and JNI error checking are still required.

When releasing, you should:

1. Bundle native libraries matching **OS/CPU**, along with required toolchain runtime/dependencies.
2. Build on CI for each target and verify exported symbols.
3. Keep Java native declarations, generated headers, and C/C++ implementations synchronized through the build pipeline.
4. Avoid committing/hand-editing generated headers if the build can regenerate them; if the project stores generated headers for review, have a process to regenerate them and check for drift.
5. Document the minimum JDK, how to configure `JAVA_HOME`, `java.library.path`, native access policy, and how to rebuild the binaries.
6. Use the JNI API properly: do not share `JNIEnv*` across threads, do not hold local refs past their lifetime, and balance array and string acquire/release calls when used.
7. Note that native bugs can crash the JVM; test unfamiliar native code in an isolated environment.

## 11. Self-check questions

**Question 1.** The compiler finds `jni.h` but fails on `jni_md.h`. What should you check first?  
**Answer:** The platform-specific include path, such as `$JAVA_HOME/include/linux` on Linux, and ensure `JAVA_HOME`/target JDK is correct.

**Question 2.** Why must the C function be declared `JNIEXPORT jint JNICALL ...`?  
**Answer:** `JNIEXPORT` handles symbol export, `jint` matches the Java `int` return type, and `JNICALL` applies the calling convention matching the JNI ABI.

**Question 3.** The same class has `static native int f()` and `native int g()`. How do the two native functions differ in their second parameter?  
**Answer:** Both have `JNIEnv*` first; `f` receives `jclass`, while `g` receives `jobject`.

**Question 4.** Where is `demo_jni_NativeMath.h` located and who creates it?  
**Answer:** In the directory specified by `javac -h` (e.g., `build/headers`); `javac` generates it from the `native` declarations, and developers should not edit it manually.

**Question 5.** The JVM loads the DLL, but throws `UnsatisfiedLinkError` when calling `add`. What should you check?  
**Answer:** Whether the prototype/symbol matches the naming convention and mangling, whether export is hidden, whether the method is overloaded, and whether C++ has C linkage; inspect with `dumpbin /EXPORTS` or `nm` depending on the platform.

**Question 6.** Can `JNIEXPORT` be replaced with `JNICALL`?  
**Answer:** No; they handle two different aspects of the ABI. Use both properly according to the JDK headers to avoid wrong platform assumptions.

### Summary of key takeaways

`jni.h` defines the common JNI interface; `jni_md.h` adds target-dependent details; `javac -h` generates headers matching the Java methods. In the prototype `JNIEXPORT <type> JNICALL Java_...(...)`, each part has its own job: **symbol export**, **JNI type**, **calling convention**, **mangled method name**, **`JNIEnv*`/`jclass` or `jobject`, and parameters**. For JNI to work reliably, headers, toolchain/ABI, library name, loading mechanism, and native access policy must all be aligned.
