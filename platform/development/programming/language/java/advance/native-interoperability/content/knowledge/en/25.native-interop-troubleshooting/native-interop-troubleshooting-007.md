# Reading `hs_err_pid`, Problematic Frames, and Java or Native Stack Traces

When Java HotSpot encounters a **fatal error** (a serious error that prevents the JVM from continuing safely), the JVM attempts to generate a text report typically named `hs_err_pid<PID>.log`. Unlike a regular Java `Exception` stack trace, this report can record **the OS signal/error, program counter (`pc`), the failing instruction frame (`Problematic frame`), the current thread, Java/native stack chains, JVM state, loaded library list, and system information**. This document helps identify where the JVM failed, how execution crossed the Java ↔ JNI/Foreign Function & Memory API (FFM) boundary, and what evidence is needed to find the root cause.

**Goal:** know how to find the right log, read the header and `Problematic frame`, decode `C/j/J/V/v` frames, correlate `Native frames` with `Java frames` of the right thread, distinguish the error detection site from the root cause, and choose the next investigation step.

## 1. When Is `hs_err_pid` Generated and When Is It Not?

The report is written by HotSpot when the fatal error handler has a chance to run—for example, when the process hits `SIGSEGV` on Linux, `EXCEPTION_ACCESS_VIOLATION` on Windows, `SIGBUS`/`SIGILL` in certain situations, or when the JVM detects an `Internal Error`. This can be caused by native code/JNI/FFM accessing invalid memory, drivers/system libraries, JVM/JIT/GC, or the effects of earlier memory corruption.

| Symptom | Is `hs_err_pid` generated by default? | Appropriate source of evidence |
| --- | --- | --- |
| `NullPointerException`, `IOException`, a regular Java exception | No | Application log and Java exception stack trace |
| Common `OutOfMemoryError` in the Java heap | Not guaranteed | Application log; heap dump if `-XX:+HeapDumpOnOutOfMemoryError` is enabled |
| JVM encounters a fatal native error and the crash handler runs | HotSpot attempts to create the log, completeness not guaranteed | `hs_err_pid`, stderr, core/minidump if available |
| Linux OOM killer sends `SIGKILL`, container is forcibly stopped | Usually no: no chance to run the handler | Kernel/container/pod events, OOMKilled/exit status |
| JVM exits normally, `System.exit` | No | Application logs and exit status |

`hs_err_pid` is a **snapshot at the moment the error was detected**, not a complete prior history. If the stack or heap is severely corrupted, HotSpot may only write a partial log or report `error occurred during error reporting`. Therefore, "no log" or "no stack" does not rule out a native error.

## 2. Finding the Right File and JVM Version

The default filename is usually `hs_err_pid4242.log` (PID `4242` is just an example). If `-XX:ErrorFile` is not set, HotSpot tries to write in the **working directory of the process**; if it cannot write there, it may fall back to the OS temporary directory (for example `/tmp` on Linux). For services/containers, the working directory may differ from the project directory.

You can explicitly specify the location (e.g., Linux):

~~~bash
java -XX:ErrorFile=/var/log/myapp/hs_err_pid%p.log -jar myapp.jar
~~~

In `-XX:ErrorFile`, `%p` is replaced by the PID, and `%%` is replaced by a literal `%` character. Ensure the directory exists, the service account has write permission, and the disk has free space. On Windows, you can use `C:/logs/myapp/hs_err_pid%p.log`.

The stderr output at crash time sometimes prints the report path:

~~~text
# An error report file with more information is saved as:
# /var/log/myapp/hs_err_pid4242.log
~~~

Before reading the contents, verify:

1. **Right incident:** the timestamp, PID, host/container/pod, and deployment match the incident under investigation.
2. **Right JVM:** the `JRE version`/`Java VM`, OS, and architecture lines match the actual runtime; avoid using a report from an older JDK as evidence for a new run.
3. **Right binary:** libraries with the same name may differ in version/build; save the corresponding application build, native libraries, and runtime configuration.
4. **Protect evidence:** copy the original file for investigation; redact or control access to sensitive information in command lines, environment variables, internal paths, and memory snapshots before sharing.

If the file is not found at the expected location, check stderr, temporary directories, supervisor/container logs, write permissions, disk space exhaustion, and whether the process was killed externally.

## 3. Map of Sections in a Fatal Error Log

Layout and label spelling vary by HotSpot version, operating system, and degree of data corruption. Common landmarks include:

| Section/string | Information to extract |
| --- | --- |
| `A fatal error has been detected`, `SIGSEGV`, or `Internal Error` | Fatal error type, code, `pc`, PID, TID |
| `JRE version`, `Java VM` | JVM build, architecture, operating system |
| `Problematic frame` | Frame containing the instruction where the error was recorded |
| `THREAD`, `Current thread` | Failing thread, thread type, thread name, native thread id, and state |
| `siginfo`, `Registers`, `Stack`, `Instructions` | Faulting address, registers, and readable CPU/stack evidence |
| `Native frames` | Native, VM, and Java calls reconstructed by HotSpot |
| `Java frames` | Java methods appearing in the call path |
| `PROCESS`, `VM state`, `VM Arguments` | VM state, JVM flags, agents, and runtime parameters |
| `Dynamic libraries` or `Loaded libraries` | List of loaded libraries/paths if available |
| `SYSTEM`, `Memory`, `CPU` | Resources, OS, CPU, and environment |

**Effective reading order:** header → `Problematic frame` → `Current thread` → `Native frames` and `Java frames` → fault address/registers → libraries/build/JVM state → reproduce and verify. Do not stop at a single `SIGSEGV` line.

## 4. Simulated Log Example and Interpretation

The following is a **simulated log for learning**, written in a format commonly seen on Linux/x86-64. Addresses, versions, and library names are illustrative only; it is not an excerpt from a real JVM. You can copy the entire block into `sample-hs_err.log` to run the Java program in section 8.

~~~text
#
# A fatal error has been detected by the Java Runtime Environment:
#
#  SIGSEGV (0xb) at pc=0x00007f0012341abc, pid=4242, tid=4250
#
# JRE version: OpenJDK Runtime Environment (21.0.x+example)
# Java VM: OpenJDK 64-Bit Server VM (21.0.x+example, linux-amd64)
# Problematic frame:
# C  [libnativecodec.so+0x1abc]  native_decode+0x2b
#
---------------  T H R E A D  ---------------

Current thread (0x00007f0022001000): JavaThread "import-worker" [_thread_in_native, id=4250, stack(0x00007f0030000000,0x00007f0030100000)]

siginfo: si_signo: 11 (SIGSEGV), si_code: 1, si_addr: 0x0000000000000000

Native frames: (J=compiled Java code, j=interpreted, Vv=VM code, C=native code)
C  [libnativecodec.so+0x1abc]  native_decode+0x2b
C  [libnativebridge.so+0x0200]  Java_com_acme_NativeDecoder_decode0+0x20
j  com.acme.NativeDecoder.decode0([B)I+0
j  com.acme.Worker.process()V+15

Java frames: (J=compiled Java code, j=interpreted, Vv=VM code)
j  com.acme.NativeDecoder.decode0([B)I+0
j  com.acme.Worker.process()V+15
~~~

### Header: signal, `pc`, PID, TID

`SIGSEGV (0xb)` indicates that the OS reported a memory access error. `pc=0x00007f0012341abc` is the **machine instruction address** at the time the error was reported, not the data address being accessed; `pid=4242` is the process id; `tid=4250` is the **native/OS thread id**, which is not necessarily equal to `Thread.getId()` or `Thread.threadId()` on the Java side.

`siginfo.si_addr=0x0` is the address associated with the access fault in the simulated log. It suggests a null pointer hypothesis, but only registers/instructions and the native code can distinguish between null, a dangling/expired pointer, a miscalculated address, or other scenarios. This is **not** a regular Java `NullPointerException`.

### `Problematic frame`: error detection site

`C [libnativecodec.so+0x1abc] native_decode+0x2b` means HotSpot identified a native frame belonging to `libnativecodec.so` at the offset shown in the log, with a suggested symbol `native_decode` if symbol information is available. This is the **location where the failing instruction was recorded**, not proof that the `native_decode` function itself is the root cause.

If you see `C [libc.so... memcpy]`, the issue might be that the caller passed an invalid buffer or length. Similarly, a frame in `libjvm.so` may be where the JVM detected native data that had been corrupted earlier.

### `Current thread`: who is executing?

The line `JavaThread "import-worker" [_thread_in_native, id=4250, ...]` confirms that the Java thread named `import-worker` was in the native state and its OS thread id matches the faulting TID. `stack(start,end)` describes the thread stack range, not the Java heap size. If the thread is in `_thread_in_vm`, it is running VM code; `_thread_in_Java` means in Java code; the states only indicate **what it was doing when it crashed**, without assigning absolute blame.

### Two stacks tell the same call path

The simulated frames show the call path:

~~~text
Worker.process()
    -> NativeDecoder.decode0(byte[])
        -> JNI bridge Java_com_acme_NativeDecoder_decode0
            -> native_decode()  [crash recorded here]
~~~

`Native frames` has a mixed chain of `C`/`j`; `Java frames` shows the Java callers. The print order is usually from **the frame closest to the executing instruction at the top**, followed by deeper callers below. A stack is a **call snapshot**, not a timeline log of events.

From the example, you can only conclude: "Process 4242 hit SIGSEGV in thread 4250 while executing native code in `libnativecodec.so`, with a call path from `Worker.process` through JNI." There is not enough evidence to say `Worker.process` definitely passed null or that the code in `libnativecodec` definitely has a bug.

## 5. Decoding `C`, `j`, `J`, `V`, `v` Symbols

| Frame | Meaning in HotSpot | How to use during investigation |
| --- | --- | --- |
| `C` | Native C/C++ or native library | `C [libfoo.so+offset]`, `C [foo.dll+offset]`. May belong to JNI, FFM, OS, JDK, or a driver |
| `j` | Java interpreted frame | Example: `j com.acme.Worker.process()V+15` |
| `J` | Compiled Java/compiled frame recognized by HotSpot | Suggests checking the compiled method or JIT, but does not prove a JIT bug |
| `V` | HotSpot VM frame | Example: `V [libjvm.so+offset]` or `V [jvm.dll+offset]` |
| `v` | VM-generated stub | Example: `v ~StubRoutines::call_stub`; a runtime bridge step |

The frame legend usually appears right after `Native frames:`; prefer the legend present in the file itself because formatting can differ across JDK versions.

Reading a `J` frame does not mean Java code directly manipulated a bad native address; native memory corruption could have happened earlier and then manifested in compiled code. A `V` frame does not by itself prove a HotSpot bug: check the callers in the native stack and the history of JNI/FFM calls. A `C` frame in `libc` does not by itself prove a libc bug: you must check the arguments passed by the caller.

For Java method descriptor notation such as `decode0([B)I`: `[B` is `byte[]`, `I` is the `int` return type, `V` is `void`, `J` is `long`, and `Ljava/lang/String;` is `String`. A suffix like `+15` in a frame line is **not a Java source line number**; source/build mapping is required to trace the exact source location.

## 6. Distinguishing Java Stack, Native Stack, and the JNI/FFM Boundary

**`Native frames`** can represent C/C++, JVM (`V/v`), and Java (`j/J`) frames in the mixed call stack that the crash handler managed to reconstruct. With JNI, there is often an exported symbol like `Java_com_acme_NativeDecoder_decode0`, though the exact name depends on the registration/binding style and symbol availability. With FFM, Java can go through `Linker`/`MethodHandle`/generated stubs to a C function; not every native frame is JNI.

**`Java frames`** help find the application method that led the thread to the native call. When reading alongside the native stack:

1. Confirm the **exact current thread**; do not mix stacks from different threads.
2. Find the Java method closest to the JNI/FFM boundary and its Java callers.
3. In `Native frames`, identify the bridge/library, the native-side functions, and the faulting frame.
4. Compare the C/JNI signature or FFM `FunctionDescriptor`; inspect pointers, buffer lengths, alignment, ownership, thread confinement, `Arena/MemorySegment` lifetime, and the actual ABI.
5. Verify the loaded library path, version, symbols, and debug symbols against the build that actually ran.

**Important limitations:** JIT may inline or optimize frames; native stack unwinding can fail due to missing frame pointers/debug symbols or stack corruption; the crash handler can abort partway through. Therefore, **a missing frame does not prove that the call did not happen**. In particular, if you see `error occurred during error reporting`, treat the stack as incomplete.

`jstack`/`jcmd <PID> Thread.print` can only be collected directly from a **live** process. Once the process has died, you need the crash report and any recorded core/minidump; you cannot attach to take a new thread dump from the old PID.

## 7. Detection Evidence and Root Cause Are Two Different Things

Commonly misattributed situations:

- `Problematic frame` is `C [libc.so... memcpy]`: libc may be using a bad pointer/length from the caller; the code that corrupted memory may be elsewhere.
- `Problematic frame` is `V [libjvm.so...]`: the JVM may be operating on memory/references corrupted earlier by JNI or native code; it could also be a JVM bug.
- `Problematic frame` is `J ...`: could be a compiled code/JIT issue, JVM bug, hardware fault, or earlier corruption.
- Thread named `CompilerThread...`: can help point toward JIT; not enough to conclude a compiler bug. `VMThread`/`VM_Operation` may involve GC, but prior corruption remains a possibility.
- `si_addr=0x0`: consistent with a null dereference hypothesis in some cases; requires checking instructions/registers rather than jumping to a Java `NullPointerException` conclusion.

Record three distinct layers of information:

**Observation:** "`SIGSEGV`, `Problematic frame=C libnativecodec.so`, `_thread_in_native`, Java caller `NativeDecoder.decode0`."

**Hypothesis:** "The pointer passed to the library might be null/expired; or the length is wrong; or the binary and descriptor have an ABI mismatch."

**Verification:** "Cross-check C source/headers, ABI, inputs, `.so` version, registers/core, and run a reproducer test under ASan/UBSan if you control the library."

A native buffer overflow can happen long before the JVM crashes in `free`/GC. `hs_err_pid` tells you the time of **detection** and the crash scene, and cannot by itself deduce the historical cause.

## 8. Safe Practice: Java 17 Reading a Simulated Log

You do not need to—and should not—crash a JVM to learn. Create `sample-hs_err.log` from **the entire simulated log block in section 4**. Save the following code to `HsErrReader.java`. It only reads text and extracts a few key landmarks; it makes no native calls.

~~~java
import java.io.IOException;
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.List;

public final class HsErrReader {
    private static String crashLine(List<String> lines) {
        for (String line : lines) {
            String s = line.strip();
            if (s.startsWith("#") &&
                (s.contains(" at pc=") || s.contains("Internal Error ("))) {
                return s;
            }
        }
        return "(not found)";
    }

    private static String problematicFrame(List<String> lines) {
        boolean afterLabel = false;
        for (String line : lines) {
            String s = line.strip();
            if (s.equals("# Problematic frame:")) {
                afterLabel = true;
                continue;
            }
            if (afterLabel) {
                if (s.isEmpty() || s.equals("#")) {
                    continue;
                }
                if (s.startsWith("# ")) {
                    return s.substring(2).strip();
                }
                break;
            }
        }
        return "(not found)";
    }

    private static String currentThread(List<String> lines) {
        for (String line : lines) {
            if (line.strip().startsWith("Current thread ")) {
                return line.strip();
            }
        }
        return "(not found)";
    }

    private static void printFrames(
            List<String> lines, String header, int maxFrames) {
        for (int i = 0; i < lines.size(); i++) {
            if (lines.get(i).strip().startsWith(header)) {
                System.out.println(header);
                int printed = 0;
                for (int j = i + 1; j < lines.size() &&
                        printed < maxFrames; j++) {
                    String line = lines.get(j).strip();
                    if (line.isEmpty()) {
                        break;
                    }
                    System.out.println("  " + line);
                    printed++;
                }
                if (printed == 0) {
                    System.out.println("  (no data)");
                }
                return;
            }
        }
        System.out.println(header + " (not found)");
    }

    public static void main(String[] args) throws IOException {
        if (args.length != 1) {
            System.err.println("Usage: java HsErrReader <hs_err_file>");
            return;
        }

        List<String> lines = Files.readAllLines(
                Path.of(args[0]), StandardCharsets.UTF_8);

        System.out.println("Crash: " + crashLine(lines));
        System.out.println("Problematic: " + problematicFrame(lines));
        System.out.println("Thread: " + currentThread(lines));
        printFrames(lines, "Native frames:", 8);
        printFrames(lines, "Java frames:", 8);
    }
}
~~~

Compile and run with JDK 17+:

~~~bash
javac HsErrReader.java
java HsErrReader sample-hs_err.log
~~~

Expected output when using the exact example file from section 4:

~~~text
Crash: #  SIGSEGV (0xb) at pc=0x00007f0012341abc, pid=4242, tid=4250
Problematic: C  [libnativecodec.so+0x1abc]  native_decode+0x2b
Thread: Current thread (0x00007f0022001000): JavaThread "import-worker" [_thread_in_native, id=4250, stack(0x00007f0030000000,0x00007f0030100000)]
Native frames:
  C  [libnativecodec.so+0x1abc]  native_decode+0x2b
  C  [libnativebridge.so+0x0200]  Java_com_acme_NativeDecoder_decode0+0x20
  j  com.acme.NativeDecoder.decode0([B)I+0
  j  com.acme.Worker.process()V+15
Java frames:
  j  com.acme.NativeDecoder.decode0([B)I+0
  j  com.acme.Worker.process()V+15
~~~

This is only a **quick reader for learning**, not a general-purpose parser for all HotSpot versions. Real logs may lack sections, be incomplete, use different encodings, or require recovery via a debugger. `Files.readAllLines` can consume significant RAM on large files; when processing very large logs, read them in a streaming fashion. Do not treat a "not found" result returned by this parser as proof that the corresponding section is definitely absent.

## 9. Locating Sections via Shell

Example on Linux:

~~~bash
grep -nE 'SIGSEGV|SIGBUS|SIGILL|Internal Error|Problematic frame|Current thread|Native frames|Java frames|siginfo|VM state|VM Arguments|Dynamic libraries|Loaded libraries' hs_err_pid4242.log
~~~

Read the beginning of the file:

~~~bash
sed -n '1,70p' hs_err_pid4242.log
~~~

In PowerShell (one-liner):

~~~powershell
Select-String -Path .\hs_err_pid4242.log -Pattern 'Problematic frame','Current thread','Native frames','Java frames' -Context 2,8
~~~

When comparing multiple incidents, group by **signal + frame/library/function + JDK build + OS/architecture + native library version**, not by an absolute `pc` address: ASLR makes base addresses differ between runs.

## 10. When Do You Need a Native Debugger, Core/Minidump, and Symbols?

`hs_err_pid` is a useful starting point. To prove pointer behavior or an ABI error, you usually need a **core dump/minidump**, the **exact build** of `java` and the libraries, along with debug symbols. For example, if you are on Linux and have a core file:

~~~bash
gdb /opt/jdk-21/bin/java /var/crash/core.4242
~~~

In GDB you can inspect:

~~~text
(gdb) info threads
(gdb) thread apply all bt
(gdb) info sharedlibrary
(gdb) disassemble
~~~

These are illustrative commands; you need the matching binary, core, debug symbols, and OS architecture. On Windows you can use WinDbg and a minidump; on macOS, use the appropriate crash report/debugger.

To map `[libnativecodec.so+0x1abc]` back to a function/source:

1. Find the actual loaded library, its path, version, and build ID; do not use a file with the same name from a different build.
2. Determine the base/load bias and how offsets are represented in the log. Do not feed every offset directly into `addr2line` without understanding ELF/PE addresses, ASLR, and layout.
3. Combine symbol information, disassembly, registers, and stack to see the exact instruction accessing the bad address, where it was called from, and whether the arguments satisfy the contract.
4. If you own the C/C++ code, reproduce it in a test environment and try AddressSanitizer/UndefinedBehaviorSanitizer; for JNI, `-Xcheck:jni` catches **some** incorrect JNI API usages.
5. For FFM, check `FunctionDescriptor` and layouts against the C ABI, `Arena`/`MemorySegment` lifetimes, callbacks, struct alignment, and ownership. `-Xcheck:jni` does not prove an FFM downcall is safe.

When the log states `error occurred during error reporting` or is missing stack sections, clearly note that the evidence is **incomplete**; a core dump and reproduction can help more than guessing from the remaining fragments.

## 11. Incident Triage Guide Table

| Observation | Hypotheses to prioritize | Useful verification |
| --- | --- | --- |
| `SIGSEGV`, `C [libapp.so+...]`, `_thread_in_native` | Invalid pointer, use-after-free, overflow, ABI mismatch | C source, ABI, binary version, core, sanitizer |
| `C [libc.so+...] memcpy` | Caller passed wrong pointer/length, prior corruption | Native caller frames, registers, buffer lifetime |
| `V [libjvm.so+...]` near JNI wrapper | JNI corrupted reference/state; could also be a HotSpot bug | `-Xcheck:jni`, core, compare JDK build |
| `J ...` in problematic frame | Compiled-code/JIT issue, or prior native corruption | Repro, flags/JDK version, check native dependencies |
| `CompilerThread...` as current thread | Need to inspect JIT compilation path | Compiler info, JDK build, isolated test |
| `VMThread`, `VM_Operation` related to GC | GC/heap corruption | GC logs, native writes, core |
| Missing stack, `error occurred during error reporting` | Crash handler lacked data or stack/memory corruption | Dump, symbols, reproducible test |
| No `hs_err_pid`, OS reports OOMKilled | Kernel killed the process | Kernel/pod metrics, memory limits, and events |

**Frame letters indicate where the JVM noticed the error, not an absolute root-cause classifier.** `C` does not automatically mean a C bug, `V` does not automatically mean a definite JVM bug, and `J` does not automatically mean bad Java source.

## 12. 10-Step Workflow for an Incident

1. **Identify the incident type:** fatal JVM crash, Java exception, or OOM kill; cross-check PID/time/OS/exit reason.
2. **Record the raw facts:** signal/error, `pc`, `pid`, `tid`, `JRE version`, `Java VM`, and `Problematic frame`.
3. **Read `Current thread`:** Java thread name, thread type, state, OS thread id; confirm it matches the crashing thread.
4. **Correlate the stacks:** find the native frames near the failing instruction; trace back to the Java caller across JNI/FFM from the **same thread**.
5. **Analyze memory info:** `siginfo`, fault address, registers, `Stack`/`Instructions` if present; avoid guessing from `si_addr` alone.
6. **Check runtime:** `VM state`, `VM Arguments`, loaded libraries, JDK/OS/CPU, agents, and related GC/concurrency logs.
7. **Check the native contract:** parameter types/sizes, `sizeof`, struct layout/alignment, buffer length, pointer lifetime, thread confinement, ABI, JNI references, FFM descriptor.
8. **Form falsifiable hypotheses:** e.g., JNI passed a length larger than the buffer; native code retained a pointer after the arena closed; incompatible library version. Record supporting and missing evidence.
9. **Reproduce in isolation:** exact build/JDK/input, test native code separately in a process/container, use `-Xcheck:jni`/sanitizers/debugger/core as appropriate; never intentionally crash a production process to "verify."
10. **Conclude and prevent:** state the **proven** cause and any remaining uncertainties, add a valuable regression test, and record a versioned crash signature to check after fixing.

Example of a standard incident report distinguishing evidence:

> "`hs_err_pid4242.log` records `SIGSEGV` in `libnativecodec.so` while thread `import-worker` was `_thread_in_native`. Native and Java stacks show the call `Worker.process → NativeDecoder.decode0 → native_decode`. This is evidence of **the crash location and call path**. It is not yet enough to confirm a null pointer or library bug; we still need to verify the buffer contract, binary version, and core/sanitizer."

## 13. Self-Check

**Q1.** How do `hs_err_pid` and a Java exception stack trace differ? — Regular exceptions do not terminate the JVM and do not generate a fatal error log; `hs_err_pid` reflects HotSpot's state during a fatal error.

**Q2.** Does `Problematic frame: C [libc.so+...]` prove libc is at fault? — No. The caller may have passed an invalid pointer/length, or memory corruption may have occurred earlier.

**Q3.** Is the header `tid` the Java thread id? — Not by default; in the sample report it is the native thread id. Cross-check `Current thread` to identify the exact thread and Java name.

**Q4.** Does `J` prove a JIT bug? — No. It helps identify compiled code; you still need to rule out native corruption and inspect the JVM/compiler further.

**Q5.** Does the absence of `Java frames` mean there is no Java caller? — No. The handler or stack unwinding may have failed to reconstruct it completely.

**Q6.** What is needed to see which source line `libfoo.so+offset` corresponds to? — The exact library/build, debug symbols, offset/load bias mapping, and a debugger; having the same filename is not enough.

**Q7.** Does `-Xcheck:jni` validate all FFM and native binaries? — No. It helps detect some JNI API violations in test environments, not guarantee native safety.
