# Chọn phiên bản jextract phù hợp với API FFM và JDK mục tiêu

## 1. Vấn đề cần giải quyết

**jextract** là công cụ của dự án OpenJDK Code Tools, đọc **C header (.h)** qua Clang/libclang rồi sinh **Java source bindings** sử dụng **Foreign Function & Memory API (FFM)**. Các binding thường chứa **MemorySegment**, **MemoryLayout**, **Arena**, **SymbolLookup**, **Linker**, **FunctionDescriptor**, **MethodHandle**, helper truy cập C struct/union và wrapper cho native function. Chúng không phải code Java thông thường độc lập với phiên bản JDK.

Vì FFM API đã trải qua các giai đoạn **incubator → preview → final**, và tiếp tục được phát triển sau khi final, phiên bản jextract dùng để sinh source **phải tương thích với JDK dự định dùng để biên dịch và chạy source đó**. Không nên tải jextract bản mới nhất mà không nhìn JDK mục tiêu: bản mới có thể sinh lời gọi API mà target JDK chưa có.

**Quy tắc ngắn gọn:**

> Chọn **JDK ứng dụng sẽ chạy** trước; chọn **bản jextract được phát hành hoặc build để nhắm tới FFM API của JDK ấy**; sinh binding từ đúng header/ABI; rồi **biên dịch và smoke-test trên chính JDK mục tiêu**.

Bài học hướng dẫn kiểm tra version thực tế, chọn branch/binary, chạy một ví dụ C → jextract → Java, khoanh vùng lỗi, quản lý phiên bản trong CI/CD và quyết định nâng cấp. Ví dụ mặc định dùng **JDK 25** vì đây là một JDK LTS có FFM API chuẩn và có các bản jextract hướng JDK 25 được phân phối; tuy vậy câu lệnh phụ thuộc gói jextract cụ thể và cần kiểm tra **jextract --version**, không coi một số build là chuẩn vĩnh viễn.

**Phạm vi:** jextract tự động hóa liên kết **C ABI**, không phải bộ biên dịch chuyển trực tiếp C++ class/templates sang Java. Với C++, Rust hoặc ngôn ngữ khác, hãy dùng một C-compatible wrapper/API/header đã được xuất hợp lệ trước khi chạy jextract.

## 2. Vì sao có bài toán version compatibility?

Hãy tách bốn lớp tương tác:

~~~text
    C headers  ---------  ABI/native library
        |                         |
        v                         v
  Clang/libclang            .so / .dylib / .dll
        |
        v
     jextract (phiên bản công cụ)
        |
        v
    Java bindings (source sử dụng API FFM cụ thể)
        |
        +--> javac/JDK mục tiêu  --- biên dịch thành .class
                                       |
                                       v
                                 java/JDK runtime
                                       |
                                       v
                           native Linker + thư viện C
~~~

**jextract tool** có thể chạy nhờ một JDK riêng hoặc runtime được đóng gói cùng bộ công cụ. **Bindings generated by jextract** phải được biên dịch với phiên bản JDK cung cấp đủ lớp/phương thức FFM mà generated source tham chiếu. **Native library** lại phải tương thích hệ điều hành, CPU architecture, calling convention và C ABI.

Một file C header có thể được jextract parse thành công nhưng Java binding không biên dịch với target JDK. Ngược lại, Java binding có thể biên dịch thành công nhưng runtime nạp nhầm native library hoặc dùng C ABI không tương thích. Vì vậy “jextract chạy được” là **chưa đủ** để kết luận “ứng dụng Java chạy được”.

Bốn loại compatibility cần kiểm tra riêng:

| Lớp | Câu hỏi quyết định | Ví dụ lỗi |
| --- | --- | --- |
| **Tool → host JDK** | Bản jextract binary chạy được trên JDK/OS của máy build không? | Tool không khởi động, thiếu Java runtime hoặc libclang |
| **Generated source → JDK API** | Các class/method FFM được sinh có tồn tại trong JDK target không? | package/class/method không tồn tại khi javac |
| **Generated bytecode → runtime JDK** | Classfile level và linked methods tương thích runtime không? | UnsupportedClassVersionError, NoSuchMethodError |
| **Binding → native ABI** | Header, compiler flags và .so/.dll thực tế có tương ứng không? | UnsatisfiedLinkError, sai sizeof/offset, crash |

Đây là bốn quyết định liên quan nhưng **không thể dùng một con số version duy nhất thay cho tất cả**.

## 3. Lịch sử FFM API và ý nghĩa chọn jextract

| Nhóm JDK | Trạng thái FFM | Tác động đến jextract |
| --- | --- | --- |
| **JDK 17** | Foreign API đời đầu thuộc incubator, ví dụ package **jdk.incubator.foreign** | Phải dùng công cụ/binding tương ứng API cũ; source sinh cho java.lang.foreign hiện đại không dùng trực tiếp |
| **JDK 19–21** | FFM ở giai đoạn preview; các package/chữ ký trải qua thay đổi | Cần bản jextract gắn với **đúng JDK preview target**; có thể cần --enable-preview trong compile/run |
| **JDK 22** | FFM trở thành **final API** (JEP 454) trong **java.lang.foreign** | Có thể dùng jextract tương thích JDK 22; không còn yêu cầu preview chỉ vì sử dụng FFM |
| **JDK 23–24** | FFM tiếp tục có thay đổi/bổ sung theo JDK | Chọn bản jextract phù hợp; kiểm tra generated source trên đúng runtime thay vì giả định tương thích ngược |
| **JDK 25 LTS** | FFM đã là API chuẩn; có bản jextract nhắm JDK 25 | Phù hợp cho một ví dụ pipeline build có pin JDK 25 + jextract 25 |
| **JDK 26–27** | JDK mới hơn (JDK 27 phát hành tháng 9/2026) | Kiểm tra binary/branch jextract và FFM API của đúng bản target; **không suy ra** bản binary JDK 27 luôn có sẵn hoặc bản JDK 25 chạy nguyên vẹn |

**Cần phân biệt:** **FFM API trở thành final ở JDK 22** không có nghĩa **jextract đã trở thành lệnh mặc định trong mọi JDK**. jextract là **công cụ phát hành riêng**; bộ cài JDK thông thường không bảo đảm có **bin/jextract**. Cũng không có quy tắc “version jextract N chỉ chạy trên JDK N, không thể chạy JDK khác” áp dụng tuyệt đối: **khả năng chạy tool** và **API mà source nó sinh ra cần** là hai hợp đồng khác nhau, đều phải đo/kiểm.

**Với Java 17/21 còn đang vận hành:** Không nâng jextract lên master rồi hy vọng generated code mới tự tương thích incubator/preview cũ. Hãy chọn branch hoặc bản phát hành nhắm JDK lịch sử, giữ lại generated source đã kiểm thử, hoặc cân nhắc một kế hoạch nâng cấp JDK ứng dụng trước. OpenJDK jextract README giải thích nhánh **master** theo API FFM mới, còn branch phiên bản như **jdk21** dành cho mục tiêu cũ. Nhánh nào thực sự tồn tại và build được phải kiểm tra từ repository ở thời điểm sử dụng.

## 4. Quy trình chọn phiên bản theo thứ tự đúng

**Bước 1: Chốt JDK mục tiêu.** Ghi chính xác **major**, bản cập nhật nếu quan trọng, vendor, OS và architecture. Ví dụ “OpenJDK 25 LTS x64 Linux”, không chỉ “Java mới”. Xem JDK đang dùng để **compile** và **runtime**; nếu khác nhau phải xác minh chiến lược cross-compilation.

**Bước 2: Tra jextract release/branch hỗ trợ target JDK.** Ưu tiên binary phát hành chính thức hoặc được nhà cung cấp đáng tin cậy xây cho target JDK. Dự án OpenJDK đăng hướng dẫn tại **https://github.com/openjdk/jextract** và các bản đóng gói được liên kết từ **https://jdk.java.net/jextract/**. Các bản prebuilt được phát hành theo đợt, có thể **không khớp** bản JDK GA mới nhất.

**Bước 3: Đọc metadata thực tế của tool.** Chạy **jextract --version** và so khớp thông tin tool/JDK, cộng thêm **jextract --help** để xác nhận option của bản đó. Không đoán syntax từ một blog viết cho jextract đời trước.

**Bước 4: Chốt C header và compiler/ABI.** Bản C header phải tương ứng native library được dùng lúc chạy. Vị trí include, các macro -D, target OS và compiler flags có thể thay đổi khai báo và layout. **jextract cùng version** nhưng chạy trên Windows và Linux có thể tạo source khác do C long/pointer/layout khác.

**Bước 5: Sinh binding vào một thư mục sạch, cố định package.** Ghi lại tool build, OS, JDK, libclang version và CLI arguments. So sánh output sau mỗi lần nâng tool/header.

**Bước 6: Biên dịch generated source bằng JDK mục tiêu.** Đây là kiểm chứng API FFM hiệu quả nhất: lỗi ngay ở javac là chỉ dấu target JDK không cung cấp class/method mà binding cần, hoặc có một sai khác source-generation khác.

**Bước 7: Chạy smoke test với native library thực.** Biên dịch thành công chưa đủ; cần nạp đúng .so/.dll/.dylib và gọi ít nhất một hàm để phát hiện loader, symbol và ABI issues.

**Bước 8: Ghi pin version và test vào CI.** Khi thay target JDK hoặc jextract, regenerate/test có chủ đích. Không silently kéo binary “latest” vào mỗi lần CI chạy.

Tóm lại, ưu tiên:

~~~text
Chốt target JDK
      |
      v
Tìm jextract được tài liệu ghi tương thích target
      |
      v
jextract --version / --help
      |
      v
Sinh Java bindings từ header/ABI đúng
      |
      v
javac target JDK -> PASS?
      |
    NO: kiểm tra API mismatch, tool version, source
      |
    YES
      v
java target JDK + native lib -> PASS?
      |
    NO: classfile, native access, linker/loader, ABI
      |
    YES
      v
Pin phiên bản và lưu artifacts/CI test
~~~

## 5. Phân biệt ba số version không được trộn

### 5.1. Version của tool jextract

**jextract --version** in thông tin version của tool và có thể kèm phiên bản JDK mà nó được build/nhắm tới cùng **libclang**. Output cụ thể khác giữa release, platform và vendor. Chẳng hạn một gói jextract nhắm JDK 25 có thể in mã build theo mẫu **25-jextract+...** hoặc **JDK version 25...**.

**Không** dùng số đó để suy ra tự động:

- phiên bản JDK mà production đang chạy;
- phiên bản bytecode của generated classes;
- phiên bản libclang native của máy;
- phiên bản C header hoặc libfoo.so trong hệ thống.

Tool version là một dòng chứng cứ, không phải phép kiểm toàn bộ end-to-end.

### 5.2. Version của javac và Java runtime

**javac --version** kiểm tra compiler phát hành cùng JDK nào; **java --version** kiểm tra JVM khởi chạy. Có thể lệnh **javac** và **java** được resolve từ hai JDK khác nhau do **PATH**, **JAVA_HOME**, IDE/Gradle toolchains hoặc cấu hình CI.

Ví dụ chạy rõ ràng bằng binary trong một JDK:

~~~bash
"$JAVA_HOME/bin/java" --version
"$JAVA_HOME/bin/javac" --version
"$JAVA_HOME/bin/javac" -d classes MyApp.java
"$JAVA_HOME/bin/java" -cp classes MyApp
~~~

**Đây là command minh họa**, phải có file MyApp.java và thư mục classes đúng. Không tự khẳng định **JAVA_HOME** sẽ thay đổi executable mà build tool khác sử dụng; Gradle/Maven IDE có thể dùng toolchain riêng.

### 5.3. Version/API được generated source gọi

Trong generated .java, xem **imports** và API usages:

- **import java.lang.foreign...** là dấu hiệu dùng FFM package hiện đại (từ giai đoạn preview và final).
- **import jdk.incubator.foreign...** là dấu hiệu hướng incubator API đời cũ.
- Những method như **Arena.allocate(...)**, **SymbolLookup.libraryLookup(...)**, **Linker.nativeLinker().downcallHandle(...)**, **MemorySegment.reinterpret(...)** hoặc các layout factories có chữ ký đổi theo phiên bản.
- Generated helper classes/fields/methods có thể thay đổi cách tổ chức khi jextract thay đổi ngay cả khi cùng tên C header.

**Không chỉ tìm tên package.** Java 21 preview cũng có **java.lang.foreign** nhưng không đồng nghĩa generated code của JDK25/26 tương thích API Java21.

## 6. Lấy binary jextract và xác minh từ nguồn tin cậy

Tham khảo công khai:

- Dự án OpenJDK jextract: **https://github.com/openjdk/jextract**
- Trang các bản jextract được liên kết chính thức: **https://jdk.java.net/jextract/**
- Hướng dẫn sử dụng: **https://github.com/openjdk/jextract/blob/master/doc/GUIDE.md**
- Bài hướng dẫn trên dev.java: **https://dev.java/learn/ffm/jextract/**

Cách chọn gói:

1. Xem release được mô tả dành cho **JDK N** nào; tránh chọn chỉ vì ngày upload mới nhất.
2. Xác minh OS/CPU: Linux x64/AArch64, macOS x64/AArch64, Windows x64... Bản dành cho macOS ARM64 không chạy trên Windows x64.
3. Kiểm tra **SHA-256**, chữ ký/nguồn phân phối nếu được cung cấp. Không lấy một binary tên **jextract** từ trang không rõ provenance rồi dùng để parse C headers trong CI.
4. Giải nén riêng (ví dụ **/opt/tools/jextract25**); đừng overwrite bản cũ rồi mất khả năng tái lập.
5. Gọi executable bằng absolute path hoặc môi trường được pin; tránh dựa vào một bản jextract cũ nằm trước trong **PATH**.

Ví dụ kiểm tra sau khi cài trên Linux:

~~~bash
/opt/tools/jextract25/bin/jextract --version
/opt/tools/jextract25/bin/jextract --help

"$JAVA_HOME/bin/java" --version
"$JAVA_HOME/bin/javac" --version
uname -m
~~~

Mọi đường dẫn trong đoạn trên là **minh họa**, phải thay cho đúng chỗ bạn cài. **Output của --version** phụ thuộc gói, nên không có một chuỗi stdout cố định cho mọi JDK/tool vendor. Dùng **--version** để ghi lại chính xác phần này trong build logs.

**Điểm cần nhớ:** bản **master** trong repo thường theo FFM API của JDK mới nhất mà dự án đang phát triển; nếu target là JDK 25/22/21, đừng chỉ build master mà không kiểm tra README/branch tương ứng. Ngay cả khi tool master có thể khởi chạy với JDK cài trên máy, bindings mới sinh vẫn có thể đòi FFM API quá mới so với deployment target.

## 7. Khi không có binary phù hợp: build từ branch tương ứng

OpenJDK jextract README mô tả cách build từ source và cho ví dụ checkout branch **jdk21** để dùng với JDK cũ. Quy trình định hướng:

~~~bash
git clone https://github.com/openjdk/jextract.git
cd jextract

git branch -a
git tag -l

# Ví dụ *nếu target là JDK 21* và branch còn tồn tại:
git checkout jdk21
~~~

**Không tự áp một branch name cho mọi JDK**. Kiểm tra **git branch -a** và release notes; một số phiên bản có thể dùng tag/binary khác. Nếu công cụ cho JDK mục tiêu không còn được hỗ trợ, hãy dùng release archive đã kiểm chứng hoặc lên kế hoạch nâng target JDK. Việc build một branch cũ trên compiler/JDK quá mới có thể vấp lỗi Gradle, Clang, toolchain — không phải do mã C của ứng dụng.

Lệnh build theo README OpenJDK hiện dùng Gradle wrapper và tham số tách biệt cho toolchain JDK với libclang:

~~~bash
# Đang ở thư mục source jextract checkout đúng branch.
sh ./gradlew \
  -Pjdk_home=/opt/jdks/jdk-target \
  -Pllvm_home=/opt/llvm \
  clean verify

build/jextract/bin/jextract --version
~~~

**Đường dẫn là ví dụ**, và mỗi branch có thể có build script/toolchain prerequisites riêng: **phải đọc README của đúng commit/branch** trước khi chạy. JDK sử dụng để **chạy Gradle** có thể khác JDK cung cấp qua **-Pjdk_home**; README nói rõ cần tham khảo **Gradle Java compatibility matrix**.

jextract dùng **libclang C API**, nên ngoài JDK bạn còn cần bản LLVM/libclang hỗ trợ của branch. Nếu tool không load được **libclang** hoặc parse header thất bại, phải kiểm tra clang availability, ABI và include paths; lỗi đó không được kết luận ngay là “FFM của JDK sai version”.

Để tái lập: pin **jextract Git commit/tag**, **JDK distribution/version**, **LLVM/libclang version** và build flags. Một bản sinh ở master ngày hôm nay có thể khác master ngày mai.

## 8. Ví dụ Linux end-to-end với JDK 25 và jextract phù hợp

Ví dụ này thể hiện toàn bộ lựa chọn version, không cần tính năng C phức tạp. Giả định bạn có:

- **JDK 25** là Java compiler + runtime dùng trong demo;
- **jextract** có bản phát hành/commit nhắm tới API FFM của JDK 25, đã cài đúng OS/CPU;
- GCC hoặc Clang C compiler trên Linux x64, cùng ABI với Java process;
- Native access được phép khi chạy Java.

Ví dụ C function:

~~~c
int add_ints(int left, int right);
~~~

Trên Linux x64 thông dụng, **int** C có 4 byte, tương ứng **int** Java. Trong dự án native thực, xác nhận độ rộng với ABI/toolchain, không khái quát cho mọi C ABI.

### 8.1. Cấu trúc thư mục

~~~text
ffm-version-lab/
├── native/
│   ├── adder.h
│   ├── adder.c
│   └── libadder.so       (được build)
├── generated/             (jextract output)
├── classes/               (javac output)
└── App.java
~~~

**Tất cả nội dung sau là file mẫu riêng biệt.** Thư mục generated và classes là outputs, không phải file nguồn viết tay.

### 8.2. File native/adder.h

~~~c
#ifndef DEMO_ADDER_H
#define DEMO_ADDER_H

#ifdef __cplusplus
extern "C" {
#endif

int add_ints(int left, int right);

#ifdef __cplusplus
}
#endif

#endif
~~~

Header này khai báo đúng một exported C ABI function. Block **extern "C"** chỉ có tác dụng khi header được include trong C++ source; ví dụ implementation biên dịch bằng C11.

### 8.3. File native/adder.c

~~~c
#include "adder.h"

int add_ints(int left, int right) {
    return left + right;
}
~~~

Đây là mã C11 đầy đủ của một hàm thư viện, không có main. Với input 20 và 22 không xảy ra signed overflow.

Build Linux shared library:

~~~bash
mkdir -p generated classes

cc -std=c11 -Wall -Wextra -Wpedantic \
  -fPIC -shared native/adder.c \
  -o native/libadder.so
~~~

Lệnh sử dụng native compiler của máy và tạo file library tại **native/libadder.so**. Kiểm tra có symbol **add_ints** nếu cần bằng công cụ như **nm -D native/libadder.so**.

### 8.4. Kiểm tra tool trước khi generate

~~~bash
jextract --version
jextract --help

"$JAVA_HOME/bin/java" --version
"$JAVA_HOME/bin/javac" --version
~~~

Chỉ tiếp tục khi:

- jextract đang dùng là bản **được chọn để nhắm JDK25**;
- JAVA_HOME chỉ JDK25 đúng CPU/OS;
- CLI options **--output**, **--target-package**, **--library** có trong **--help** của bản tool.

Không coi lệnh **jextract --version** chỉ hiện số 25 là bằng chứng mọi generated source sẽ chạy ngay. Phép thử thật bắt đầu ở bước sau.

### 8.5. Sinh Java bindings

~~~bash
jextract \
  --output generated \
  --target-package demo.bindings \
  --library adder \
  native/adder.h
~~~

**Giải thích:**

- **--output generated**: root của source files được sinh.
- **--target-package demo.bindings**: package Java; jextract tạo thư mục tương ứng.
- **--library adder**: binding sẽ tìm native library tên **adder** theo cơ chế platform; Linux thường là **libadder.so**.
- **native/adder.h**: header chính, chứa C declaration cần sinh.

Theo convention của hướng dẫn jextract hiện hành, header **adder.h** tạo lớp chính **adder_h** trong package **demo.bindings**, với method static **add_ints(int,int)**. Nếu bản jextract đã pin sinh tên/code khác, **xem trực tiếp output** và điều chỉnh chương trình caller theo API thực tế. Không sao chép lớp được generate bởi jextract bản khác rồi giả định tên luôn không đổi; có thể dùng option **--header-class-name** khi cần cố định tên.

### 8.6. File App.java

~~~java
import static demo.bindings.adder_h.add_ints;

public class App {
    public static void main(String[] args) {
        int result = add_ints(20, 22);
        System.out.println("native result = " + result);
    }
}
~~~

Đây là chương trình Java độc lập dùng wrapper jextract sinh từ C header. Nó **không** gọi JNI native method, không tự viết FunctionDescriptor và không tự khai báo downcall handle; những phần đó thuộc generated binding.

### 8.7. Biên dịch bằng đúng target JDK

Dùng các lệnh sau từ thư mục **ffm-version-lab/**:

~~~bash
# Lưu ý: generated là nguồn .java, không chỉ một JAR sẵn có.
find generated -type f -name '*.java' -print0 \
  | xargs -0 "$JAVA_HOME/bin/javac" -d classes

"$JAVA_HOME/bin/javac" -cp classes -d classes App.java
~~~

Điểm kiểm tra:

- **javac** phải là binary của **target JDK 25**.
- Nếu lỗi ở import/method trong **java.lang.foreign**, nghi **jextract ↔ FFM API target** không tương thích.
- Nếu lỗi không tìm thấy **demo.bindings.adder_h**, xem generated class/package thực, không vội kết luận do JDK.
- Nếu jextract không sinh hàm **add_ints**, xem header path, Clang diagnostics và symbol filters.
- Nếu compilation vượt qua, tiến hành runtime smoke test; compiler success chưa chứng minh native symbol sẽ load được.

### 8.8. Chạy và kiểm tra kết quả

~~~bash
LD_LIBRARY_PATH="$PWD/native" \
  "$JAVA_HOME/bin/java" --enable-native-access=ALL-UNNAMED \
  -cp classes App
~~~

**--enable-native-access=ALL-UNNAMED** cho phép native FFM operations từ classpath code trong unnamed module. Cơ chế/diagnostics có thể thay đổi theo JDK; nếu dùng named modules, phải cấp native access cho tên module thay vì ALL-UNNAMED.

**LD_LIBRARY_PATH** ở đây giúp loader tìm **libadder.so** cho demo. Quy trình đóng gói production nên quản lý library location rõ ràng và an toàn hơn việc cho phép load bất kỳ library cùng tên từ đường dẫn có thể bị thao túng.

Với bản toolchain/JDK đã xác minh tương thích, trên Linux stdout chính:

~~~text
native result = 42
~~~

Có thể xuất hiện log hoặc cảnh báo môi trường trên stderr/stdout tùy JVM, nhưng phép kiểm trọng tâm là **wrapper thật sự gọi hàm C và trả 42**. Nếu native library không được load, thường thấy **UnsatisfiedLinkError** hoặc lỗi lookup liên quan; đó khác lỗi API FFM khi javac compile.

**Không nên coi việc công cụ jextract khởi chạy thành công mà không có compile/run là đã kiểm thử compatibility.** Đây là lý do ví dụ đi đủ cả ba bước: generate → compile → invoke.

## 9. Test không cần jextract để xác định target JDK có API FFM chuẩn

Trước khi dùng tool, bạn có thể chạy một smoke test FFM đơn giản trên **JDK 22+**. Đoạn này chỉ kiểm chứng **java.lang.foreign** cơ bản có thể biên dịch/chạy, không kiểm chứng chính jextract.

### File FfmApiCheck.java

~~~java
import java.lang.foreign.MemorySegment;
import java.lang.foreign.ValueLayout;

public class FfmApiCheck {
    public static void main(String[] args) {
        byte[] data = {10, 20, 30};
        MemorySegment segment = MemorySegment.ofArray(data);

        byte middle = segment.get(ValueLayout.JAVA_BYTE, 1);
        System.out.println("FFM byte = " + middle);
        System.out.println("FFM package available");
    }
}
~~~

~~~bash
javac FfmApiCheck.java
java FfmApiCheck
~~~

Stdout với **JDK 22+**:

~~~text
FFM byte = 20
FFM package available
~~~

Ví dụ sử dụng memory trong Java heap nên không đòi native access, không cần libclang hay file .so. Nếu **JDK 17** báo không tìm thấy package **java.lang.foreign**, nguyên nhân là phiên bản JDK chưa có package FFM chuẩn, không phải do jextract hỏng.

**Giới hạn của test:** JDK22+ có package không chứng minh mọi symbol mà jextract25/26 sinh đều có trong API đó. Phải tiếp tục biên dịch generated source thật.

## 10. Bản jextract mới có chắc chạy với JDK cũ hơn không?

**Không có bảo đảm chung.** FFM API thay đổi từ thời incubator/preview; dù đã final ở 22, các overload và hạn chế native access vẫn được phát triển. Mã generator mới có thể tham chiếu API chỉ có ở JDK mới.

Một số trường hợp:

| Tình huống | Kết luận hợp lý |
| --- | --- |
| jextract gắn JDK21 preview sinh code rồi compile trên JDK21 tương ứng | Có thể tương thích nếu đúng preview level và flags; phải chạy test |
| jextract gắn JDK25 sinh code rồi compile trên JDK21 | Không được mặc định tương thích; 21 còn preview, 25 dùng API chuẩn; thường cần dùng bản phù hợp 21 |
| jextract gắn JDK25 sinh code rồi compile trên JDK22 | Phụ thuộc symbols/overloads được sinh; không có lời hứa source luôn tương thích ngược |
| jextract gắn JDK25 sinh code rồi compile trên JDK25 | Đây là cặp hợp lý để bắt đầu, vẫn phải kiểm tra tool, Clang, native ABI |
| jextract gắn JDK25 sinh code rồi compile/chạy trên JDK27 | Có thể hoạt động nếu compatibility vẫn giữ; không khẳng định nếu chưa compile và runtime test |
| jextract từ nhánh master sinh code rồi compile trên JDK25 | Có nguy cơ API mới hơn; dùng release/branch target JDK25 hoặc kiểm thử thực tế |

**Suy nghĩ đúng:** “Có thể vẫn chạy” không đồng nghĩa “được kiểm chứng”. Với production, pin một cặp tool/JDK có kết quả compile/test tốt hơn tin vào số version hoặc quy tắc “mới hơn luôn tốt hơn”.

### Java classfile version khác FFM source compatibility

Một file **.class** được biên dịch bằng JDK mới có thể gây **UnsupportedClassVersionError** trên Java runtime cũ. Ví dụ xây classfile mặc định bằng JDK25 rồi deploy lên JDK21 sẽ không tương thích classfile level, bất kể source Java có dùng FFM hay không.

Dùng **javac --release N** kiểm soát Java language/API/classfile target ở compile time, nhưng **không sửa được** trường hợp generated code yêu cầu **FFM method không có ở N**. Nếu generated Java do jextract25 sử dụng API chỉ có ở JDK25 thì **--release 22** không biến method đó thành tồn tại trong JDK22. Tốt nhất dùng **javac của chính target JDK**, hoặc kiểm soát **--release** và biên dịch/test trên runtime target.

## 11. Phải pin native ABI cùng với phiên bản jextract

jextract phân tích header qua Clang. Kết quả phụ thuộc C preprocessor, platform, compiler flags, OS và data model.

Ví dụ C:

~~~c
struct NativePair {
    long first;
    void *second;
};
~~~

- Trên **Linux x64 LP64**, **long** thường 8 byte và pointer 8 byte.
- Trên **Windows x64 LLP64**, **long** thường 4 byte nhưng pointer 8 byte; struct có thể chèn padding.
- Trên 32-bit ABI, pointer và alignment lại khác.

Vì vậy cùng bản jextract25 nhưng chạy trên hai platform có thể tạo **MemoryLayout**, Java carrier và offsets khác nhau. jextract guide khuyến nghị sinh theo từng platform rồi so generated output trước khi chia sẻ một bộ binding duy nhất cho nhiều platform.

Còn những yếu tố khác:

- **#ifdef _WIN32**, **#if defined(__linux__)** chọn declarations khác nhau;
- **-D** macro flags thay đổi struct/feature selection;
- **-I / --include-dir** quyết định header nào được parse;
- clang target triple và compiler-specific attributes có thể ảnh hưởng layout;
- phiên bản **libfoo.so** khác phiên bản **foo.h** có thể đổi ABI nhưng cùng tên symbol.

Trong repository, pin tối thiểu:

~~~text
TARGET_JDK       = 25 (vendor/build được ghi rõ)
JEXTRACT_RELEASE = bản nhắm JDK25, pin build/commit
LLVM_LIBCLANG    = version được jextract distribution hỗ trợ
TARGET_OS_ARCH   = linux-x64 hoặc matrix theo platform
HEADER_VERSION   = revision/tag của native SDK
NATIVE_LIBRARY   = version/ABI tương ứng với header
JEXTRACT_FLAGS   = include dirs, macros, package, library
~~~

Đây là *mẫu cấu hình minh họa*, không phải nội dung chuẩn của một công cụ cụ thể. Để tái lập, các phiên bản và checksum phải được ghi thành giá trị thật trong project.

Nếu bất kỳ **C header, compiler flags, native library, jextract version hoặc target JDK** nào thay đổi, cần đánh giá sinh lại bindings và chạy ít nhất smoke test.

## 12. CI/CD: làm thế nào để tránh “máy tôi chạy được”?

Một pipeline thực tế nên có các bước tách biệt:

~~~text
Setup target JDK (pin major/vendor/build)
        |
Install/pin jextract release + checksum
        |
Install/verify LLVM/libclang and C compiler
        |
Compile native library against pinned headers
        |
Run jextract to a clean generated/ directory
        |
Compile generated .java with target javac
        |
Compile smoke test against generated classes
        |
Run java with native access + correct library path
        |
Record versions, logs, generated diff, test result
~~~

Một script Linux minh họa kiểm tra chặt (giả định các file ở mục 8 đã có):

~~~bash
#!/usr/bin/env bash
set -euo pipefail

: "$JAVA_HOME"
: "$JEXTRACT_HOME"

"$JAVA_HOME/bin/java" --version
"$JAVA_HOME/bin/javac" --version
"$JEXTRACT_HOME/bin/jextract" --version

rm -rf generated classes
mkdir -p generated classes native

cc -std=c11 -Wall -Wextra -Wpedantic -fPIC -shared \
  native/adder.c -o native/libadder.so

"$JEXTRACT_HOME/bin/jextract" \
  --output generated \
  --target-package demo.bindings \
  --library adder \
  native/adder.h

find generated -type f -name '*.java' -print0 \
  | xargs -0 "$JAVA_HOME/bin/javac" -d classes

"$JAVA_HOME/bin/javac" -cp classes -d classes App.java

LD_LIBRARY_PATH="$PWD/native" \
  "$JAVA_HOME/bin/java" --enable-native-access=ALL-UNNAMED \
  -cp classes App
~~~

**Điều kiện dùng script:** Chỉ chạy trong **thư mục lab/sandbox đã xác minh**, vì **rm -rf generated classes** xóa hai thư mục output này. Đây là **một script mẫu** phục vụ CI, không yêu cầu chạy trên working tree quan trọng; trên dự án thực nên dùng output directory riêng của build tool và tránh lệnh dọn thư mục chưa xác minh.

Khi CI chạy trên nhiều OS/ABI, **không tái sử dụng generated bindings từ Linux x64 cho Windows x64 theo mặc định**. Có thể generate mỗi target trong pipeline hoặc kiểm chứng rằng declarations/ABI thật sự portable rồi mới dùng chung output.

### Sinh tại build time hay commit generated code?

Có hai chiến lược đều hợp lệ:

- **Commit generated Java source:** build chính không cần libclang/jextract mỗi lần; review diff dễ hơn và dễ pin output. Cần quy trình regenerate có kiểm soát khi nâng header/tool/JDK.
- **Generate trong build pipeline:** luôn đồng bộ với C headers được pin; nhưng cần đảm bảo binary jextract, libclang, compiler environment và flags được cố định để kết quả reproducible.

OpenJDK jextract guide mô tả cách dùng phổ biến là generate từ header rồi đưa sources đã tạo vào dự án, chỉ regenerate khi native library hoặc jextract thay đổi. Không có yêu cầu bắt buộc phải chạy jextract lúc khởi động Java application.

## 13. Kiểm chứng generated bindings thay vì tin tên class qua ví dụ cũ

Tên lớp và các helpers generated có thể đổi giữa các thế hệ jextract. Với guide hiện hành, một header **adder.h** thường tạo **adder_h** và method tĩnh **add_ints**. Nhưng nếu bạn lấy code hướng dẫn từ blog cũ hoặc dùng một JDK-target branch khác:

1. Mở generated source để xác nhận **package** và tên lớp chính.
2. Kiểm tra **--header-class-name** có được tool hỗ trợ không nếu cần cố định tên.
3. Xem chữ ký static wrappers cho C function, không giả định Java carrier type.
4. Biên dịch toàn bộ generated source trước khi viết client.
5. Có thể kiểm tra class sau compile bằng **javap** để thấy signature thực.

Ví dụ với lớp đã compile:

~~~bash
"$JAVA_HOME/bin/javap" -classpath classes demo.bindings.adder_h
~~~

Nếu bản tool khác tạo method name hay carrier khác, hãy làm theo generated class thật. **Sửa code Java caller** cho phù hợp; không sửa C ABI hoặc giả mạo wrapper signature để ép compile.

Một số code generated có helper như **Point.layout()**, **Point.sizeof()**, **Point.x(segment)**, **foo$address()**, **foo$descriptor()**, **foo$handle()** tùy version. Đây là tiện ích do jextract tạo, **không phải các method chuẩn của MemorySegment**; khi migrate giữa bản jextract, chính phần này cũng cần kiểm thử source compatibility.

## 14. JDK17/JDK21: nên làm gì với hệ thống không nâng được?

### JDK17 (incubator-era)

JDK17 có Foreign Function & Memory API ở giai đoạn thí nghiệm, khác đáng kể với **java.lang.foreign** chuẩn từ JDK22. Không thể bảo đảm generated source từ jextract25 chạy với JDK17 chỉ bằng cách thêm **--add-modules jdk.incubator.foreign**. Khi buộc chạy JDK17:

- tìm binary/tag jextract được phát hành cho đúng incubator API của JDK17;
- giữ toolchain JDK17 + required flags nhất quán;
- kiểm tra branch cũ thực sự còn build được;
- cân nhắc tiếp tục JNI/JNA hoặc cập nhật runtime nếu không có tool/binding phù hợp.

Không nên hứa một cờ compile duy nhất sẽ backport API từ JDK25 về JDK17.

### JDK21 LTS (preview-era)

JDK21 có **java.lang.foreign** dạng preview. Để compile/chạy source thực sự tương thích với preview JDK21, có thể cần:

~~~bash
javac --enable-preview --release 21 MyApp.java
java --enable-preview MyApp
~~~

Đây là **mẫu lệnh dành cho source được viết đúng API JDK21 preview**, không phải cách “ép” binding do jextract25 sinh về JDK21. Trong dự án thực cần thêm classpath/module path, generated sources, native access flags và tên class chính như appropriate.

OpenJDK jextract README đưa ví dụ branch **jdk21** cho bản công cụ nhắm JDK21. Nếu dùng branch đó, phải kiểm tra build prerequisites của **chính branch**, không sao chép nguyên lệnh Gradle từ master đang tiến hóa.

### JDK22 và JDK25 (final-era)

JDK22 là mốc FFM final; JDK25 là LTS mới hơn. Khi target JDK22, có thể tìm jextract release/branch sinh code tương thích 22. Khi target JDK25, ưu tiên release/binary được ghi là **JDK25**; không phải cứ jextract master ở một thời điểm bất kỳ đều bảo đảm target25.

**Không cần --enable-preview chỉ để dùng FFM final trên JDK22/25.** Nhưng native access có restrictions riêng: khi downcall/load library, sử dụng **--enable-native-access** hoặc cấu hình module tương ứng theo chính JDK mục tiêu. Preview flag và native access flag giải quyết **hai vấn đề khác nhau**.

## 15. Khi nâng version: đánh giá source compatibility, binary compatibility và ABI

Giả sử dự án đang dùng JDK25 + jextract25 và muốn nâng lên JDK27.

Đừng thay cùng lúc cả ba thành phần mà không có checkpoint. Quy trình an toàn:

1. **Giữ** bản generated bindings và native SDK/library hiện tại trong source control.
2. **Nâng JDK runtime/compiler** trước ở một nhánh thử nghiệm; biên dịch generated code cũ và chạy native integration tests.
3. Nếu compiler/runtime có vấn đề hoặc cần tính năng mới, chọn **jextract được tài liệu hỗ trợ target JDK27**; kiểm tra binary có thực sự tồn tại và tương thích OS/CPU.
4. Sinh lại bindings vào một output directory **mới**, không overwrite phiên bản cũ ngay.
5. Diff generated source: package/class names, field accessors, var handles, memory layouts, SymbolLookup, Linker callsites, C macro processing.
6. Compile, run smoke test và native regression suite trên target runtime; kiểm tra native access permissions.
7. Cập nhật lockfile/build instructions và code caller nếu generated API thay đổi.
8. Sau khi QA, thay output cũ có chủ đích.

Một bảng kiểm chuyển đổi:

| Thành phần thay | Những gì cần kiểm tra |
| --- | --- |
| Chỉ JDK patch 25.0.x | JDK compatibility/runtime/native access diagnostics, hồi quy |
| JDK25 → JDK27 | FFM methods, classfile, native access policy, generated bindings |
| Chỉ jextract release | Tên/lược đồ generated helpers, layout code, wrapper implementation |
| Chỉ native SDK/header | Function signatures, macros, struct offsets, enum, pointer ownership |
| Chỉ architecture Linux x64 → ARM64 | Pointer width, C ABI, alignment, calling convention |
| Chuyển OS Linux → Windows | DLL loading, LLP64 vs LP64, C long, wchar_t, compiler headers |

Điểm then chốt: **có thể biên dịch lại generated source để dùng trên một JDK mới** mà chưa cần regenerate, nhưng chỉ được chấp nhận khi compile/runtime/integration tests chứng minh. Ngược lại, **regenerate không tự bảo đảm** tương thích binary C library nếu header/ABI sai.

## 16. Các lỗi thường gặp và cách chẩn đoán đúng lớp

| Triệu chứng | Nghi ngờ chính | Hành động |
| --- | --- | --- |
| **jextract: command not found** | Chưa cài hoặc PATH sai | Gọi binary bằng absolute path; kiểm tra --version |
| Tool jextract không khởi chạy vì Java version | Host runtime của tool không phù hợp | Xem release yêu cầu JDK nào, chọn tool/binary đúng |
| **Unable to load libclang** | Thiếu/sai LLVM libclang hoặc architecture | Kiểm tra libclang phụ thuộc tool, native library loader |
| **fatal error: 'foo.h' file not found** | Include path hoặc header SDK sai | Dùng --include-dir và xác minh exact header |
| Generated code gọi **java.lang.foreign** nhưng JDK17 không thấy | API chưa có ở JDK17 | Dùng target JDK22+ hoặc đúng bản generator incubator |
| Preview error trên JDK21 | Chưa bật preview hoặc source khác level | Dùng target21 preview flags và generator21 phù hợp |
| **cannot find symbol / no suitable method** ở javac | Binding sinh API FFM khác target | So imports/methods với JDK docs và jextract --version |
| **class file has wrong version** | Compiler mới, runtime cũ | Align javac/java target; kiểm tra --release |
| **NoSuchMethodError/NoClassDefFoundError** runtime | Compile/runtime mismatch hoặc classpath sai | Đồng bộ JDK, dependency, rebuild generated classes |
| **IllegalCallerException** / native access warning | Chưa cấp quyền native access phù hợp | --enable-native-access cho module/classpath đúng |
| **UnsatisfiedLinkError** khi load .so/.dll | Native library không thấy, symbol thiếu, ABI/arch sai | Kiểm tra library path, export symbols, dependency, bitness |
| Native call trả sai hoặc crash | C ABI khác header được parse | Kiểm tra sizeof/offsetof, calling convention, macros |
| Generated wrapper class name đổi | Tool version hoặc CLI changes | --header-class-name nếu hỗ trợ; compile + review diff |
| Source Java thiếu struct/bitfield/macro | Jextract limitation hoặc symbol filter | Xem warnings, unsupported features, viết C wrapper |
| Mã Java chạy Linux nhưng lỗi Windows | Platform-dependent layout/data model | Generate và test theo OS/ABI, không share mù quáng |

**Đừng xử lý tất cả bằng cách nâng JDK.** Lỗi libclang xảy ra trước Java binding compilation; lỗi native loader có thể xảy ra sau khi Java compilation hoàn toàn đúng. Chẩn đoán đúng giai đoạn tiết kiệm thời gian và tránh thay đổi không cần thiết.

### Lỗi header và feature không được jextract hỗ trợ

jextract guide lưu ý các giới hạn có thể gồm **function-like macros**, **C bitfields**, **opaque incomplete types**, một số scalar C không được hỗ trợ đầy đủ theo ABI, hay linker options đặc biệt. Ví dụ muốn chụp **errno** qua **captureCallState**, có thể phải viết/điều chỉnh binding thủ công hoặc tạo helper tương ứng thay vì trông chờ mọi bản jextract tự sinh linker option đó.

Nếu jextract in warning bỏ qua một C declaration, đó **không nhất thiết là do chọn sai JDK**. Đối chiếu unsupported features của đúng tool version, hiểu header và thiết kế C façade khi cần.

## 17. Những câu hỏi quan trọng khi pin jextract ở doanh nghiệp

### Có bắt buộc pin jextract bằng đúng major JDK không?

**Không có luật một-một phổ quát cho mọi binary và release.** Nhưng cặp **jextract nhắm API FFM JDK N ↔ JDK target N** là điểm xuất phát an toàn. Quyết định cuối dựa vào **release notes, --version, generated source compilation và runtime tests**. Đặc biệt với preview/incubator, sự khác biệt thường lớn nên việc ghép sai version có rủi ro cao.

### Có thể tải jextract mới nhất rồi dùng để sinh binding cho JDK21 không?

Không nên giả định. **Master** thường theo mainline JDK mới; JDK21 dùng preview FFM API. Tìm bản lịch sử dành cho 21, ví dụ branch jdk21 khi còn khả dụng, hoặc nâng runtime.

### Có thể dùng jextract25 generated source trên JDK27 không?

**Có thể** nếu generated code chỉ dùng API còn tương thích và runtime/native ABI đáp ứng yêu cầu, nhưng phải kiểm bằng **javac/java trên JDK27**. Không bảo đảm từ nhãn version.

### Có cần jextract trên server production không?

**Không nếu bạn deploy generated Java classes hoặc JAR đã build.** jextract là công cụ **code-generation/build-time**. Production cần Java runtime phù hợp, các native libraries và OS dependencies, cùng cấu hình native access; không cần chạy generator tại runtime trừ khi ứng dụng của bạn có một workflow rất đặc biệt.

### Có thể chạy jextract cho C++ header trực tiếp không?

jextract chủ yếu parse **C headers**. C++ source có thể cung cấp **extern "C" façade** chứa ABI C rồi sinh binding từ header façade đó. C++ overloads/templates/name mangling không được giải quyết chỉ bằng việc trỏ jextract vào header C++ phức tạp.

### jextract có tự sửa ABI khác giữa LP64 và LLP64 không?

Nó parse header và sinh layout theo platform, nhưng output phụ thuộc **đúng target ABI**. Điều cần đảm bảo là **máy generate tương ứng nền tảng đích** hoặc có phương án cross-generation/test chứng minh layout đúng. Không lấy generated source Linux với C long 8 byte dùng trên Windows với C long 4 byte mà bỏ qua thử nghiệm.

### Có nên xóa generated sources và regenerate mỗi lần CI?

Có thể, nếu jextract binary, JDK, clang, headers và flags đều pin và build reproducible. Nhưng OpenJDK guide cũng chấp nhận workflow generate một lần, đưa generated sources vào codebase và regenerate khi có version/header changes. Chọn chính sách rõ ràng thay vì phụ thuộc artifact latest thay đổi hàng ngày.

## 18. Checklist ra quyết định và tiêu chí PASS

### Chọn tool

- [ ] Có **target JDK major, vendor/build, OS và architecture** rõ ràng.
- [ ] jextract release/branch có tài liệu hỗ trợ **FFM API target**.
- [ ] Chạy được **jextract --version** trên host, kiểm tra binary/platform.
- [ ] **jextract --help** xác nhận CLI flags đang dùng.
- [ ] libclang tương thích, header include paths và macros đúng native SDK.
- [ ] Tool binary/commit, JDK, LLVM, native SDK được pin và kiểm tra nguồn tải.

### Generate/compile

- [ ] Sinh source vào thư mục sạch, package/header class name xác định.
- [ ] Không có Clang warnings quan trọng bị bỏ qua.
- [ ] Generated imports/methods tương ứng **java.lang.foreign** của JDK mục tiêu.
- [ ] **javac target JDK** biên dịch tất cả generated .java.
- [ ] Caller Java biên dịch đúng generated wrappers.
- [ ] Không dùng **--release** để che giấu API thiếu trên target JDK.

### Runtime/ABI

- [ ] Runtime java thực tế đúng JDK mục tiêu.
- [ ] Có native access cho đúng module/classpath.
- [ ] Native library được tìm thấy và đúng CPU/OS/ABI.
- [ ] Chạy **một downcall thật**, kiểm tra return value hoặc side effects.
- [ ] Nếu có structs, đối chiếu **sizeof/offsetof/alignment** bằng C compiler.
- [ ] Smoke/integration tests chạy trên mọi OS/arch có hỗ trợ.
- [ ] Generated bindings/lịch sử version được review và ghi lại.

Chỉ khi cả **tool, generated source, javac, JVM runtime và native library** vượt qua các kiểm thử tương ứng mới có cơ sở gọi một bộ jextract/JDK “phù hợp” cho dự án cụ thể.

## 19. Bài tập và tình huống thực hành

**Câu 1.** Vì sao cài jextract25 trên máy JDK25 rồi chạy thành công **jextract --version** chưa đủ?

**Đáp án:** Version command chỉ chứng minh tool khởi động. Generated binding còn phải compile trên JDK25 và gọi native function thật trên đúng ABI.

**Câu 2.** Generated source import **jdk.incubator.foreign** nhưng project dùng JDK25. Có nên chỉ đổi dòng import thành java.lang.foreign?

**Đáp án:** Không. API classes/method signatures/semantics đã khác, cần regenerate từ jextract phù hợp target25 hoặc migrate code có kiểm thử.

**Câu 3.** Generated source import **java.lang.foreign** và target là JDK21. Đã chắc chắn tương thích chưa?

**Đáp án:** Chưa. JDK21 cũng dùng package đó ở giai đoạn preview, nhưng các API giữa 21 và final JDK22+/JDK25 có thể khác. Cần generator/flags phù hợp và compile/run target21 thực tế.

**Câu 4.** JDK25 có cần **--enable-preview** chỉ để dùng FFM không?

**Đáp án:** Không. FFM đã final từ JDK22. Tuy nhiên native linker calls là restricted operations và có thể cần **--enable-native-access** theo chính sách runtime.

**Câu 5.** Mã binding compile được với JDK25 nhưng khi chạy báo **UnsatisfiedLinkError**. Có chắc do jextract version sai không?

**Đáp án:** Không. Kiểm tra .so/.dll loading, library path, symbol exports, OS/arch và ABI; đây là lỗi xuất hiện ở giai đoạn runtime native link.

**Câu 6.** Dùng generated binding Linux x64 trên Windows x64 có an toàn nếu cùng JDK25 không?

**Đáp án:** Chưa chắc. C long thường 8 byte trên LP64 Linux x64 nhưng 4 byte trên LLP64 Windows x64; macros, pointer handling, calling convention và library names cũng khác.

**Câu 7.** Dùng **javac --release 22** có làm một jextract25 binding tự tương thích với JDK22 không?

**Đáp án:** Không. Nếu code dùng FFM APIs không có trên JDK22, compiler sẽ báo lỗi khi kiểm tra API target, hoặc ứng dụng fail nếu cố bypass.

**Câu 8.** Vì sao nên pin phiên bản Clang/libclang, dù Java runtime đã được pin?

**Đáp án:** jextract parse C headers bằng Clang. Different parser/compiler/target flags có thể tạo output khác nhau hoặc warnings, không phụ thuộc trực tiếp vào Java FFM.

**Câu 9.** Project có code C++ template library, jextract chỉ nhìn header C-compatible. Nên làm gì?

**Đáp án:** Xây C ABI wrapper rõ ràng, dùng extern "C" phù hợp và generated bindings từ các C declarations được export. Không coi jextract là trình dịch toàn bộ C++ sang Java.

**Câu 10.** Khi nâng từ JDK25 lên JDK27, có phải regenerate toàn bộ bindings lập tức?

**Đáp án:** Không bắt buộc nếu generated bindings cũ compile/run/integration-test được trên 27. Nhưng nếu cần tính năng mới hoặc tool/API mismatch, chọn jextract target27 phù hợp nếu có, regenerate trong nhánh kiểm thử, review diff và thử lại native integration.

**Bài tập A:** Với cùng header **adder.h**, lưu hai bộ generated sources từ hai releases jextract (chọn hai bản có thể build). So sánh **imports**, class name, wrapper signature, linker calls. Ghi khác biệt thay vì chỉ so số dòng source.

**Bài tập B:** Dùng **javac của JDK cũ hơn** để compile binding được sinh cho JDK mới hơn. Phân loại lỗi thành: package/class không có, signature không tồn tại, preview flag thiếu hay carrier/overload khác.

**Bài tập C:** Đổi **int** trong header C thành **long**, generate trên Linux x64 và Windows x64. So differences trong Java carrier/layout, rồi đo **sizeof(long)** bằng C compiler từng OS. Không dùng kết quả của một máy làm đại diện cho cả hai.

**Bài tập D:** Tạo hai CI profiles: **JDK25 + jextract target25** và **JDK27 + jextract được chứng minh tương thích27**. Cả hai phải compile generated bindings và chạy trả **native result = 42**. Nếu profile thứ hai không có bản tool phù hợp, đánh dấu blocker cụ thể thay vì tự tải binary “latest” không rõ target.
