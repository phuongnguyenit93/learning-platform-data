# Running a Minimal Example and Checking Types, Results, Load Errors, and Linking Errors (JNI)

## 1. Lesson Purpose and Scope

In the **First JNI** group of Java Native Interoperability, this lesson takes a Java `native` method through four stages: **Java compilation → C compilation into a dynamic library → JVM loading and finding the native method → Java checking the result**. The goal does not stop at "the program runs", but rather knowing how to prove that data types and signatures on both sides match, identifying which step an error occurs at, and handling the root cause properly.

You will create a program with `public static native int add(int, int)` implemented in C. The program calls it with two datasets, checks the results, and then prints `RESULT: PASS`. All source files are presented in full and can run on **JDK 17 or higher** with an appropriate C compiler.

After completing this, the learner must be able to explain:
- How `javac -h` generates a header from a Java signature; why you should not guess C function names yourself.
- What `jint`, `JNIEnv *`, `jclass`, `JNIEXPORT`, and `JNICALL` are used for.
- Why the library name in `System.loadLibrary` differs from the `.so/.dylib/.dll` filename.
- The difference between a **C compile** error, a **C library link** error, a **library load error in the JVM**, a **native method linking** error, a **type/ABI** error, and an **incorrect result**.
- How to inspect the Java descriptor, exported symbol, library path, CPU architecture, and dependent libraries without trial-and-error edits in multiple places at once.

### The Big Picture

~~~text
src/demo/jni/FirstJni.java
    |
    | javac --release 17 -h native -d out
    +--> out/demo/jni/FirstJni.class
    +--> native/demo_jni_FirstJni.h
                |
native/firstjni.c + generated header
    |
    | C compiler + native linker
    +--> libfirstjni.so (Linux)
    |    libfirstjni.dylib (macOS)
    |    firstjni.dll (Windows)
    |
    | java -Djava.library.path=. -cp out demo.jni.FirstJni
    v
  static initializer: System.loadLibrary("firstjni")   <- LOAD error
    |
  call add(12, 30): find Java_demo_jni_FirstJni_add    <- METHOD LINKING error
    |
  C executes: jint + jint -> jint                      <- TYPE/ABI or LOGIC error
    |
  Java assert: 42, -3                                  <- RESULT error
    |
  RESULT: PASS
~~~

**Three layers commonly misnamed as "link":** the native linker creates `.so`/`.dylib`/`.dll`; the system loader opens the file and its dependent libraries; the JVM resolves the native method with a symbol in the binary. Both of the latter two stages can report `UnsatisfiedLinkError`, but the causes are completely different.

## 2. Prerequisites and Directory Structure

Requires JDK **17+** (with `java`, `javac`, and `include/jni.h`), a C compiler for the corresponding platform, and a terminal. Maven, Gradle, Spring Boot, JNA, or FFM are not needed for this example.

Check beforehand:

~~~sh
java -version
javac -version
~~~

Name the practice directory `jni-first`; create three subdirectories and the Java file in the correct package:

~~~text
jni-first/
├── src/
│   └── demo/
│       └── jni/
│           └── FirstJni.java      # Created manually
├── native/
│   ├── demo_jni_FirstJni.h        # Generated by javac -h
│   └── firstjni.c                 # Created manually
├── out/
│   └── demo/jni/FirstJni.class    # Generated by javac
└── libfirstjni.so                 # Linux; name varies depending on OS
~~~

In a Linux/macOS terminal, run from the `jni-first` directory:

~~~sh
mkdir -p src/demo/jni native out
~~~

In Windows **Developer Command Prompt (CMD)**:

~~~bat
mkdir src\demo\jni
mkdir native
mkdir out
~~~

If the three directories already exist, simply reuse them. `JAVA_HOME` in the native build steps must point to the **JDK root**, i.e., where `include/jni.h` and `include/linux` / `include/darwin` / `include/win32` are located. The native binary architecture must be compatible with the running JVM architecture (for example, x86-64 with x86-64, arm64 with arm64); "Java running on a 64-bit machine" is not enough to infer that the compiler is outputting the right architecture.

## 3. Creating the Java Class and a Deterministic Test

Full contents of **`src/demo/jni/FirstJni.java`**:

~~~java
package demo.jni;

public final class FirstJni {
    static {
        System.loadLibrary("firstjni");
    }

    private FirstJni() {}

    public static native int add(int left, int right);

    public static void main(String[] args) {
        int first = add(12, 30);
        int second = add(-5, 2);

        if (first != 42 || second != -3) {
            throw new AssertionError(
                    "Wrong JNI result: " + first + ", " + second);
        }

        System.out.println("JNI loaded");
        System.out.println("add(12, 30) = " + first);
        System.out.println("add(-5, 2) = " + second);
        System.out.println("RESULT: PASS");
    }
}
~~~

`add` is declared as `native` so it **has no Java method body**. `javac` checks types in Java; when the JVM runs, it will need a corresponding native definition in the library. The `static` modifier on `add` determines that the second hidden parameter on the C side is `jclass`; if changed to an instance method, the C side receives `jobject`.

The `static` block loads the library when the class initializes; in this program, initialization occurs before the body of `main`. Therefore, a load error prevents the program from printing `JNI loaded`. The value-checking block is intentional: the library might load and the C function might be called correctly, yet compute the wrong result. `RESULT: PASS` only appears after **both** calls return the right numbers. Neither addition in the example causes overflow for the `jint` type.

**Library name:** `System.loadLibrary("firstjni")` takes the **logical name `firstjni`**, do not write `libfirstjni.so`, `firstjni.dll`, file extensions, or paths. The path is specified via the library search mechanism (this lesson uses `-Djava.library.path=.`), while `System.load` is a different API that can take an absolute path.

## 4. Compiling Java and Generating the Exact JNI Header

At the `jni-first` root:

~~~sh
javac --release 17 -h native -d out src/demo/jni/FirstJni.java
~~~

Meaning:
- `--release 17`: compiles compatible with Java 17 API/bytecode; runnable with JDK 17+.
- `-d out`: generates `out/demo/jni/FirstJni.class` according to the package.
- `-h native`: generates `native/demo_jni_FirstJni.h` from the `native` methods seen by the Java compiler. This is the **type contract**, so do not edit this file by hand.

In the generated header, the following snippet will appear (along with comments and include guards generated by `javac`):

~~~c
#include <jni.h>

/*
 * Class:     demo_jni_FirstJni
 * Method:    add
 * Signature: (II)I
 */
JNIEXPORT jint JNICALL Java_demo_jni_FirstJni_add
  (JNIEnv *, jclass, jint, jint);
~~~

At the same time, inspect the descriptor in the Java bytecode:

~~~sh
javap -s -p -classpath out demo.jni.FirstJni
~~~

The output includes the constructor/`main`/static initializer; the important part must be:

~~~text
public static native int add(int, int);
  descriptor: (II)I
~~~

**Reading `(II)I`:** the two `I`s inside the parentheses are two `int` inputs; the `I` after the parentheses is the `int` result. The descriptor belongs to the JVM and is not the same as the "C function name". The native symbol name in the example is `Java_demo_jni_FirstJni_add`, consisting of the package, class, and method name (escaped according to JNI rules). For overloaded native methods, the JVM also has a long JNI name form containing signature information; let `javac -h` generate the prototype instead of manually adding suffixes.

### Decoding the C Signature

| Prototype part | Meaning |
|---|---|
| `JNIEXPORT` | Ensures appropriate export/visibility declaration so the dynamic loader/JVM sees the symbol |
| `jint` at return position | JNI type for Java `int`, 32-bit signed integer |
| `JNICALL` | Calling convention per JNI/ABI, especially required on Windows |
| `Java_demo_jni_FirstJni_add` | The Java-native function name that the JVM must resolve for the class/package/method |
| `JNIEnv *` | Pointer to the JNI interface for the current thread, provided by the JVM when calling native |
| `jclass` | Second argument for a **static** Java method; an instance method will receive `jobject` |
| `jint, jint` | The two Java integers `left` and `right`, after the two hidden JNI parameters |

Do not omit `JNIEnv *` or `jclass` to create a C function that only takes two numbers. `JNIEnv *` is not a self-managed pointer; JNI defines its usage scope as tied to the thread and the call. You should also not replace `jint` with C `long`: the size of `long` varies by ABI, for instance 64-bit Windows typically uses a 32-bit `long` whereas Java `long` is 64-bit (JNI `jlong`).

## 5. Implementing C to Match the Generated Header

Create the file **`native/firstjni.c`** with the following full contents:

~~~c
#include "demo_jni_FirstJni.h"

JNIEXPORT jint JNICALL Java_demo_jni_FirstJni_add(
        JNIEnv *env, jclass declaring_class, jint left, jint right) {
    (void)env;
    (void)declaring_class;
    return left + right;
}
~~~

This is the **complete C code for the native library**. The header generated by `javac` already includes `jni.h`, so it contains the `jint`, `jclass` types and JNI macros. The two `(void)` lines avoid unused-parameter warnings: `env` and `declaring_class` are mandatory ABI parameters even though the addition method does not need to use them yet.

You must keep the function name, return type, and number and order of parameters matching the generated header. A change from `static` to an instance method in Java requires regenerating the header and reviewing the native code. For C++ (`.cpp`) files, the `extern "C"` mechanism from the generated header must be used; do not let C++ name mangling cause the JNI symbol to differ from what the JVM expects.

## 6. Building the Shared Library and Running End-to-End

Choose the branch **for the same OS as the JVM that will run**. Commands are run from the `jni-first` directory, after creating the source and header as above.

### Linux: GCC or Clang

On Linux with `readlink -f`, you can derive the JDK path from `javac`; if `JAVA_HOME` already points to the right JDK, keep that value:

~~~sh
export JAVA_HOME="$(dirname "$(dirname "$(readlink -f "$(command -v javac)")")")"

cc -std=c11 -Wall -Wextra -fPIC -shared \
  -I"$JAVA_HOME/include" \
  -I"$JAVA_HOME/include/linux" \
  -Inative \
  -o libfirstjni.so native/firstjni.c

java -Djava.library.path=. -cp out demo.jni.FirstJni
~~~

`-fPIC` generates position-independent code, `-shared` builds the shared object `libfirstjni.so`; `-I` locates `jni.h`, `jni_md.h`, and the generated header. For an example that only receives `JNIEnv *` passed in by the JVM, there is no need to link `libjvm` or call `JNI_CreateJavaVM`.

### macOS: Clang

In Terminal with Xcode Command Line Tools and JDK:

~~~sh
export JAVA_HOME="$(/usr/libexec/java_home)"

cc -std=c11 -Wall -Wextra -fPIC -dynamiclib \
  -I"$JAVA_HOME/include" \
  -I"$JAVA_HOME/include/darwin" \
  -Inative \
  -o libfirstjni.dylib native/firstjni.c

java -Djava.library.path=. -cp out demo.jni.FirstJni
~~~

The output file is `libfirstjni.dylib`. On Apple Silicon, an arm64 JVM needs an arm64 native binary; if the JVM runs in x86-64/Rosetta mode, the native binary must be x86-64 compatible.

### Windows: MSVC Developer Command Prompt (CMD)

`JAVA_HOME` needs to point to the JDK of the right architecture, for example in a CMD shell that has `cl.exe` from x64 Native Tools when using an x64 JVM:

~~~bat
javac --release 17 -h native -d out src\demo\jni\FirstJni.java

cl /nologo /W4 /LD ^
  /I"%JAVA_HOME%\include" ^
  /I"%JAVA_HOME%\include\win32" ^
  /Inative ^
  native\firstjni.c /Fe:firstjni.dll

java -Djava.library.path=. -cp out demo.jni.FirstJni
~~~

`/LD` creates a DLL, `/Fe:firstjni.dll` chooses the name matching `loadLibrary("firstjni")`. The `^` character continues lines in **CMD**; do not copy these lines verbatim into PowerShell. If the terminal lacks `cl.exe`, open the appropriate Developer Command Prompt or use a suitable alternative C toolchain.

### Exact Output of the Standard Program

~~~text
JNI loaded
add(12, 30) = 42
add(-5, 2) = -3
RESULT: PASS
~~~

This output was verified using **JDK 21 (`javac --release 17`), GCC C11, and a Linux shared library** with these exact two source files. The macOS/Windows branches use their respective native tools; the expected output is the same given the same signature and behavior. Run from the directory containing the shared library, because `.` in `java.library.path` is the **working directory of the Java process**.

To further check JNI usage in HotSpot:

~~~sh
java -Xcheck:jni -Djava.library.path=. -cp out demo.jni.FirstJni
~~~

This example does not make additional calls through `JNIEnv`, so the standard output is unchanged. `-Xcheck:jni` helps detect certain incorrect JNI usages when expanding further, but it does not replace C testing for memory overflows or incompatible ABI types.

## 7. Type Checking: Java Types Cannot Be Arbitrarily Inferred from C

Java bytecode checks types according to Java; in C you must keep **JNI types** instead of substituting C types that might happen to match in size.

| Java type | JNI type | Risk when bound incorrectly |
|---|---|---|
| `boolean` | `jboolean` | Not interchangeable with an arbitrary `int` or C `bool`; JNI uses an 8-bit representation |
| `byte` | `jbyte` | 8-bit signed integer |
| `short` | `jshort` | 16-bit signed integer |
| `char` | `jchar` | 16-bit unsigned UTF-16 code unit, not a regular C `char` |
| `int` | `jint` | 32-bit signed integer; the `add` example uses this type |
| `long` | `jlong` | 64-bit signed integer; not equal to C `long` by default |
| `float` | `jfloat` | 32-bit float per JNI |
| `double` | `jdouble` | 64-bit float per JNI |
| `String` | `jstring` | JVM object reference; do not cast to `char *` |
| `int[]` | `jintArray` | JVM array reference; access via JNI API |
| `void` | `void` | No return value |

For `static native int add(int,int)`:
- The Java compiler recognizes `(II)I`.
- The C header generates the prototype `JNIEXPORT jint JNICALL ... (JNIEnv *, jclass, jint, jint)`.
- The C implementation must keep `jint` for the parameters and return value.
- The Java caller receives an `int` value and compares it via tests. Correct results for 42 and -3 verify the data flow **for these inputs**, not that the implementation is correct for all inputs.

In JNI, **the right symbol name does not guarantee the right ABI**. If C declares the wrong number or types of parameters but still exports the JNI name that the JVM finds, garbage values, crashes, or undefined behavior can occur. Therefore, always include the generated header in C so the compiler cross-checks the prototype, and **rebuild** whenever the Java declaration changes.

### Checking the Exported Native Symbol

On Linux, after building:

~~~sh
nm -D --defined-only libfirstjni.so | grep Java_demo_jni_FirstJni_add
~~~

The name `Java_demo_jni_FirstJni_add` must appear as a defined symbol (usually marked with `T`). The hex address changes per build and is not an expected output to match exactly. You can view symbol details with:

~~~sh
readelf -Ws libfirstjni.so | grep Java_demo_jni_FirstJni_add
~~~

On macOS there is `nm -gU libfirstjni.dylib` (symbols may have a leading `_` per tool convention). Windows has `dumpbin /EXPORTS firstjni.dll`. Symbol not found? Check whether the C source was compiled into the binary, the version of the generated header, the package/method name, `JNIEXPORT/JNICALL`, C++ name mangling, and the actual library file being loaded.

## 8. Which Stage Failed: Diagnostic Table

| Common error / symptom | Classification | How to handle |
|---|---|---|
| `javac: file not found`, `package ... does not exist` | Java compile | Source path, package, working directory |
| `Could not find or load main class demo.jni.FirstJni` | JVM classpath | `-cp out`, `out/demo/jni/FirstJni.class` file, full class name |
| `fatal error: jni.h: No such file or directory` | C compile | `JAVA_HOME`, `-I` to JDK and platform headers |
| `conflicting types for Java_demo_jni_FirstJni_add` | C compile / wrong prototype | Fix C to match generated header, do not edit header by hand |
| `undefined reference` / `LNK2019` during build | Native link | Missing native definition/import; resolve linker before running JVM |
| `UnsatisfiedLinkError: no firstjni in java.library.path: ...` | **Load:** JVM cannot find library file | Check filename, working directory, `-Djava.library.path=.` |
| `cannot open shared object file` / `Library not loaded` | **Load/dependency:** OS loader missing dependent library | Check `ldd`, `otool -L`, or `dumpbin /DEPENDENTS` |
| `wrong ELF class` / `not a valid Win32 application` / `wrong architecture` | **Load:** wrong OS/CPU/ABI | Check 32/64-bit build, arm64/x86-64, right native toolchain |
| `UnsatisfiedLinkError: 'int demo.jni.FirstJni.add(int, int)'` | **Method linking:** cannot resolve JNI symbol | Check `javap -s`, generated header, export, and stale binary |
| `AssertionError: Wrong JNI result: ...` | **Logic/result:** native method returned but wrong | Check C formula, input/output data, conversion |
| JVM crashes upon entering C | **Native/ABI/memory:** not a Java compile error | Cross-check prototype/ABI, pointers, stack, crash log; try `-Xcheck:jni` |

Messages may vary depending on the JDK and operating system. For `UnsatisfiedLinkError`, check whether it appears at **`System.loadLibrary`** or at the **`add` call**. A load error in the static initializer can cause subsequent attempts to use the class to report a class initialization error instead of the original stack trace.

### Three Types of Paths to Keep Separate

1. `-cp out` finds **Java classes**. Changing the classpath does not help find DLL/SO files.
2. `-Djava.library.path=.` helps the JVM find **the library requested by `loadLibrary`**. Place this option before the main class name and run in the correct working directory.
3. The OS loader finds **libraries that the native binary depends on**. Linux has `LD_LIBRARY_PATH` and RPATH/RUNPATH; macOS has loader paths and `DYLD_*` policies; Windows has DLL search order/PATH. These are distinct from `java.library.path`, and adding only the Java path may not resolve a missing dependency.

To view dependencies of a trusted Linux binary:

~~~sh
ldd libfirstjni.so
readelf -d libfirstjni.so
~~~

On macOS use `otool -L libfirstjni.dylib`; on Windows use `dumpbin /DEPENDENTS firstjni.dll`. If a dependency is listed as "not found", identify the missing library and fix the deployment/search path. The `ldd` tool should only be used on trusted binaries on a test machine.

## 9. Reproducing Two Errors to Understand the Difference and Fix

Only perform the following two experiments **after the standard program has PASSED**. After each experiment, restore the Java/C sources to a synchronized state, rebuild, and run to PASS.

### A. Intentionally Using the Wrong Library Path (Load Error)

On Linux/macOS, try a path without the library:

~~~sh
java -Djava.library.path=/definitely/not/a/jni/library -cp out demo.jni.FirstJni
~~~

Typically, the JVM throws an error like:

~~~text
java.lang.UnsatisfiedLinkError: no firstjni in java.library.path: ...
~~~

The stack trace points to `System.loadLibrary`/`FirstJni.<clinit>`. There is no `JNI loaded` line. This error happens **before** the JVM calls native `add`; do not edit the addition code. Fix the path to the directory containing the binary file with the right name, e.g., `-Djava.library.path=.` from the `jni-first` directory.

### B. Library Present but Native Symbol Does Not Match (Method Linking Error)

Keep the built `libfirstjni.so` file that has the symbol `Java_demo_jni_FirstJni_add`. In `FirstJni.java`, change **the method name in the declaration and both calls** from `add` to `addV2`, but **do not rebuild the C/shared library**. Re-run **only**:

~~~sh
javac --release 17 -h native -d out src/demo/jni/FirstJni.java
java -Djava.library.path=. -cp out demo.jni.FirstJni
~~~

This time the library may load successfully, but the JVM needs `Java_demo_jni_FirstJni_addV2`. Because the binary still only exports the old symbol, the error will look like:

~~~text
java.lang.UnsatisfiedLinkError: 'int demo.jni.FirstJni.addV2(int, int)'
~~~

The stack trace is at `FirstJni.addV2(Native Method)`. This experiment was verified on JDK 21/Linux; error formatting may differ on other platforms. The fix is to **synchronize the Java declaration + generated header + C implementation + native binary** and rebuild; do not edit `java.library.path` because the library was already found.

**Additional test to distinguish a result error:** with the standard Java `add` and properly named library, change only the C body from `return left + right;` to `return left - right;` and rebuild. The native method can still link and be called, but `main` throws `AssertionError` because 12−30 differs from 42. Restore the addition after observing. This proves that **the absence of `UnsatisfiedLinkError` is not enough to conclude the computation is correct**.

## 10. Effective Debugging Workflow for Real-World JNI

When encountering an error, follow this exact order to avoid fixing the wrong layer:

1. **Freeze the inputs:** record the Java and JDK versions, compiler/architecture, Java class/package, native filename, and **run command**. Find the first stack trace that appears.
2. **Verify the Java build:** run `javac -h`, check the `.class` file, `javap -s`, and the generated header. Compare each Java type with `jint/jlong/...` on the C side.
3. **Verify the C build:** check the compiler/linker return code and the existence of the new binary. Errors for `jni.h`, `conflicting types`, or linker errors are all in this stage.
4. **Verify exported symbols + dependencies:** check `nm/readelf/dumpbin` and `ldd/otool/dumpbin`; confirm the architecture and that the file found by the JVM is **the build you just created**, not an old file with the same name.
5. **Verify the loader:** run Java with an explicit `-Djava.library.path` and the right `-cp`. If the error is in `<clinit>`, focus on name/path/platform/dependencies.
6. **Verify native method lookup:** if the error occurs when calling `add`, compare `Java_demo_jni_FirstJni_add`, the generated header, the `(II)I` descriptor, and the native binary currently being loaded.
7. **Verify the logic:** run inputs with expected results, catching discrepancies with assertions/tests. Only after the entire chain has PASSED should you expand to `String`, arrays, object refs, callbacks, or native memory.

### Common Mistakes to Avoid

- Typing JNI names from memory, or changing package/class without regenerating the header and native binary.
- Using C `long` instead of `jlong`, using `jint` instead of `jlong`, or swapping the positions of `JNIEnv *`/`jclass`/Java parameters.
- Writing `System.loadLibrary("libfirstjni.so")` or adding a file extension on Windows.
- Assuming `java.library.path` replaces `classpath` or all OS dependency search paths.
- Compiling native for x86 while running an x64/arm64 JVM.
- Editing C source and forgetting to rebuild the shared library, causing the JVM to keep loading the old binary.
- Only testing the happy path without checking returned values.
- Rushing to convert Java `String` to C `char *` or Java arrays to C pointers; JNI reference types require their corresponding APIs and lifetimes.

## 11. Acceptance Checklist and Review Questions

| Step | Passing indicator |
|---|---|
| Java compile | `out/demo/jni/FirstJni.class` exists, no compile errors |
| Header | `native/demo_jni_FirstJni.h` exists with `(II)I` and symbol `Java_demo_jni_FirstJni_add` |
| C compile/link | Fresh `libfirstjni.so`/`libfirstjni.dylib`/`firstjni.dll` file exists with the right ABI |
| Export | Symbol tool displays `Java_demo_jni_FirstJni_add` |
| Load | `System.loadLibrary("firstjni")` does not throw `UnsatisfiedLinkError` |
| Native lookup | Both `add` calls resolve and return `jint` |
| Logic | Values `42` and `-3` are correct, stdout ends with `RESULT: PASS` |

**1. `javac` compiles successfully, yet `java` still reports `UnsatisfiedLinkError`. Why?**  
Because `javac` only compiles Java and generates the header; it does not guarantee that the native binary exists, has the right architecture, is on the right path, has all dependencies, or contains the symbol the JVM needs.

**2. Why are there two "hidden" arguments in the C function when Java `add` only takes two `int`s?**  
`JNIEnv *` is provided by the JVM to call the JNI API on the current thread, and `jclass` is the class reference because `add` is `static`. Only after those come the two `jint`s from Java.

**3. When should you check `java.library.path`, and when should you check exported symbols?**  
A load error at `System.loadLibrary` points to checking the file/dependencies/path/architecture. An error at the `add` call after the library has loaded points to the native method name, export, and signature.

**4. Why do types and results need to be tested separately?**  
C might export the right name and the method might be called, yet misinterpret ABI types, pass wrong numbers, or compute incorrectly. Compatible signatures are a necessary condition; output assertions verify the behavior of the test cases.

**5. Is seeing `RESULT: PASS` enough to prove all JNI calls are safe?**  
No. It confirms the path, symbol, and addition for the two inputs in this lesson; to work with Java arrays, `String`, JNI references, threads, or native memory, you must verify the corresponding JNI rules as well.

## 12. Conclusion and Reference Documentation

For your first JNI, keep a repeatable chain of evidence: **Java declaration → `javac -h` → C function with matching prototype → platform-specific shared library → successful load → resolved symbol → asserted result**. When an error occurs, identify which stage it stands at before fixing it.
