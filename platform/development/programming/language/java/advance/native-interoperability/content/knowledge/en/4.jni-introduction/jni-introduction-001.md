# Flow from a `native` Method to Its C or C++ Implementation with JNI

## 1. Objectives and the Big Picture

**JNI (Java Native Interface)** is an interface that allows Java code running in the JVM to call native functions compiled into machine libraries, typically written in C or C++. This lesson traces **a complete call**: from the `native` declaration, header generation, building and loading the library, symbol linking, the JVM passing arguments to JNI, C/C++ processing, and returning the result to Java.

After this lesson, you will be able to:

- Write a Java class containing `native` methods and load the library via `System.loadLibrary`.
- Use `javac -h` to generate a JNI header that matches the Java declarations exactly.
- Build a shared library `.so`, `.dylib`, or `.dll` containing a C **or** C++ implementation.
- Understand why native functions take extra `JNIEnv *` and `jclass`/`jobject` parameters, and how `jint` and `jstring` cross the boundary.
- Distinguish library loading from method linking; diagnose `UnsatisfiedLinkError` and lifetime/ABI errors.

Overview diagram:

~~~text
Java source                      Build native                    At runtime
JniJourney.java  --javac -h--> JniJourney.h
     |                                |
     |                           jni_journey.c/.cpp
     |                                |
     v                                v
JniJourney.class                 libjnijourney.so / .dylib / jnijourney.dll
     |                                ^
     | JVM initializes class          | System.loadLibrary("jnijourney")
     v                                |
Java calls add(20,22) --> JVM finds/links JNI entry point
                                |
                                v
                Java_JniJourney_add(JNIEnv *, jclass, jint, jint)
                                |
                                v
                         C/C++ returns jint 42
                                |
                                v
                       Java receives int 42
~~~

**Distinguish three tasks:** (1) `javac` compiles Java and generates the header; (2) the C/C++ compiler builds the native library; (3) the **JVM** loads the library and transfers control into the JNI function when the application runs. `javac` does not compile C/C++ code, and the JVM does not automatically generate a native implementation from the `native` keyword alone.

JNI appears in applications that need to integrate OS libraries, existing C/C++ code, devices/drivers, native technologies, or specialized computations. JNI allows accessing memory and APIs outside Java's normal safety mechanisms: a single native bug can crash the entire JVM.

## 2. Preparing the Project and Environment

The example uses **JDK 17 or later** and C11 or C++17. To get deterministic results across all platforms, the example only adds two small numbers and processes the ASCII string `"Java"`.

Requirements: `javac` and `java` from the **same JDK**, a C/C++ compiler matching the operating system (GCC/Clang or MSVC), and the `JAVA_HOME` environment variable pointing to the **JDK root directory containing `include/jni.h`**. The JDK and the native library must have the same architecture, for example both x64 or both ARM64.

Directory structure **after building** on Linux for illustration:

~~~text
jni-first/
├── JniJourney.java
├── JniJourney.class          # generated by javac
├── JniJourney.h              # generated by javac -h
├── jni_journey.c             # choose C
├── libjnijourney.so          # generated by compiler/linker
└── ...                       # on macOS/Windows the library name differs
~~~

All commands below run from the `jni-first` directory. Only **one** implementation is needed: use `jni_journey.c` **or** `jni_journey.cpp`. Do not link both because they export the same two JNI symbols.

## 3. Step 1 — Declaring `native` Methods in Java

Create **`JniJourney.java`** (without a `package` declaration so the JNI names are easy to observe):

~~~java
public final class JniJourney {
    static {
        System.loadLibrary("jnijourney");
    }

    private JniJourney() {
    }

    public static native int add(int left, int right);

    public static native String greet(String name);

    public static void main(String[] args) {
        int result = add(20, 22);
        String greeting = greet("Java");

        System.out.println("add(20, 22) = " + result);
        System.out.println(greeting);
    }
}
~~~

Key points to understand:

1. `native` tells the compiler/JVM that **the method body is implemented outside Java bytecode**. Therefore, the Java declaration ends with `;` and has no `{ ... }` block.
2. `static` is chosen in this example to call the methods directly on the class. An **instance** native method is also valid; in that case, the JNI function receives `jobject` instead of `jclass`.
3. The `static` initializer block runs when the JVM initializes the class before using `main`/static methods; it calls `System.loadLibrary("jnijourney")` to load the platform-appropriate library.
4. `"jnijourney"` is the **logical name** of the library: on Linux it typically maps to `libjnijourney.so`, on macOS to `libjnijourney.dylib`, and on Windows to `jnijourney.dll`. Do not pass a path or the `lib` prefix/`.dll` extension to `loadLibrary`.
5. `int` and `String` in Java are **not yet** ordinary C parameters: the JVM converts them to the JNI types `jint` and `jstring` according to the specification.

This Java code **compiles without the native library**, but if you run it right away, the library loading or symbol linking step will fail. Java compilation and native building are independent steps.

## 4. Step 2 — Generating the JNI Header with the JDK

In the `jni-first` directory, run:

~~~bash
javac -h . JniJourney.java
~~~

The `-h .` option tells `javac` to generate the native header in the current directory. The output includes `JniJourney.class` and **`JniJourney.h`**. Do not hand-edit the generated header: if you change the class name, package, method name, overloads, or Java types, **re-run `javac -h`** and recompile the native code.

The key part of the header will contain two declarations equivalent to:

~~~c
#include <jni.h>

/* Excerpt of generated prototypes; not the entire header */
JNIEXPORT jint JNICALL Java_JniJourney_add(
    JNIEnv *, jclass, jint, jint);

JNIEXPORT jstring JNICALL Java_JniJourney_greet(
    JNIEnv *, jclass, jstring);
~~~

Meaning:

- `JNIEXPORT` marks how the symbol is exported so the JVM can locate the function in the dynamic library (macro details depend on the platform).
- `JNICALL` specifies the calling convention required by JNI on the corresponding platform.
- `JNIEnv *` gives native code access to JNI functions to manipulate JVM objects/state on the **current thread**.
- `jclass` is the implicit argument for a `static` native method; for an instance native method, the second argument is `jobject` (the `this` object).
- The Java arguments appear **after the two implicit parameters** in the exact order declared.
- `jint` is the JNI type for Java `int`; `jstring` is a JNI reference to a Java `String` object. Do not interpret `jstring` as `char *`.

The names `Java_JniJourney_add` and `Java_JniJourney_greet` are **JNI entry point** names, not arbitrary Java names. The JVM links them to `native` methods using JNI naming rules (or an explicit registration mechanism, see below).

## 5. Step 3 — Implementing the Two JNI Entry Points in C

Create **`jni_journey.c`** with the full contents:

~~~c
#include "JniJourney.h"
#include <stdio.h>

JNIEXPORT jint JNICALL Java_JniJourney_add(
        JNIEnv *env, jclass clazz, jint left, jint right) {
    (void) env;
    (void) clazz;

    return left + right;
}

JNIEXPORT jstring JNICALL Java_JniJourney_greet(
        JNIEnv *env, jclass clazz, jstring name) {
    (void) clazz;

    if (name == NULL) {
        jclass type = (*env)->FindClass(
                env, "java/lang/NullPointerException");
        if (type != NULL) {
            (*env)->ThrowNew(env, type, "name must not be null");
        }
        return NULL;
    }

    const char *chars = (*env)->GetStringUTFChars(env, name, NULL);
    if (chars == NULL) {
        return NULL;  /* JVM already has a pending exception, usually OOME */
    }

    char buffer[128];
    int count = snprintf(buffer, sizeof(buffer), "Hello, %s!", chars);

    (*env)->ReleaseStringUTFChars(env, name, chars);

    if (count < 0 || (size_t) count >= sizeof(buffer)) {
        jclass type = (*env)->FindClass(
                env, "java/lang/IllegalArgumentException");
        if (type != NULL) {
            (*env)->ThrowNew(env, type, "name is too long");
        }
        return NULL;
    }

    return (*env)->NewStringUTF(env, buffer);
}
~~~

**`add`: Java → C → Java**

- Java passes `20` and `22` as two `int` values; upon entering JNI they have type `jint`.
- The JVM prepends `JNIEnv *env` and `jclass clazz`; `add` does not need these two parameters, so it casts them to `void` to avoid compiler warnings.
- C computes `left + right` for two small numbers and returns `jint 42`.
- The JVM receives the `jint` value and converts it back to the `int` result of the Java call.

**`greet`: Java `String` → JNI → Java `String`**

- `name` is a **JNI reference** to a `String` object. You must not cast it directly to `char *` or read the object's internal layout directly.
- `GetStringUTFChars` obtains a NUL-terminated **Modified UTF-8** byte string; the JVM may allocate a copy or use pinned memory. Therefore, the code must call `ReleaseStringUTFChars` when finished.
- `snprintf` writes the name into a fixed buffer and returns the number of bytes needed (excluding NUL); the code checks this to avoid returning a truncated string. The example limits total output length to 127 bytes.
- `NewStringUTF` creates a **new Java `String`** from Modified UTF-8. For the ASCII input `"Java"`, the exact result is `"Hello, Java!"`.
- If `name == NULL` or the string is too long, native code creates a Java exception via `FindClass`/`ThrowNew` and returns `NULL`. When returning to Java, the JVM propagates the pending exception. `GetStringUTFChars` returns `NULL` on failure (such as out of memory), so it must be checked before use.

**Encoding note:** JNI's Modified UTF-8 **differs in some cases from standard UTF-8**, especially for U+0000 and surrogate pairs. The runnable example uses ASCII to keep stdout deterministic; when integrating Unicode strings or APIs requiring standard UTF-8, handle transcoding properly instead of treating the two formats as identical.

## 6. Step 4 — Compiling the Native Library

Choose only one command group for your operating system. `JAVA_HOME` must point to the JDK currently used to compile/run Java.

### Linux with GCC or Clang

~~~bash
cc -std=c11 -Wall -Wextra -fPIC -shared \
  -I"$JAVA_HOME/include" \
  -I"$JAVA_HOME/include/linux" \
  jni_journey.c -o libjnijourney.so
~~~

### macOS with Clang

~~~bash
cc -std=c11 -Wall -Wextra -fPIC -dynamiclib \
  -I"$JAVA_HOME/include" \
  -I"$JAVA_HOME/include/darwin" \
  jni_journey.c -o libjnijourney.dylib
~~~

### Windows x64 with MSVC

Open **x64 Native Tools Command Prompt for Visual Studio** and run:

~~~bat
cl /nologo /W4 /LD /I "%JAVA_HOME%\include" /I "%JAVA_HOME%\include\win32" jni_journey.c /link /OUT:jnijourney.dll
~~~

Note: the shell command examples are **three platform options**, not meant to be run sequentially. On Windows, `JAVA_HOME` must be a CMD environment variable, not Bash variable syntax. You must use an MSVC x64 build if the JVM is x64.

Common options:

- `-I` or `/I`: specifies the JDK header directories containing `jni.h` and the OS-dependent header.
- `-fPIC`: generates position-independent code suitable for shared objects on applicable platforms.
- `-shared`/`-dynamiclib`/`/LD`: builds a shared library for the JVM to load.
- The output name must match how the JVM maps `"jnijourney"` on the actual platform.

A JNI library uses the exact ABI of the running process. You cannot load a Windows `.dll` into a Linux JVM, an x86-64 library into an ARM64 process, or mix 32-bit and 64-bit. For any other native dependencies, the OS loader must also be able to locate those dependent libraries.

## 7. Step 5 — Running and Observing the Output

From the directory containing `JniJourney.class` and the built native library, run:

~~~bash
java -Djava.library.path=. JniJourney
~~~

Successful stdout output:

~~~text
add(20, 22) = 42
Hello, Java!
~~~

`-Djava.library.path=.` adds the current directory to the JVM's library search path in this example. It is configured at JVM startup; if you reconfigure the search path, **start a new Java process**. `java.library.path` and OS dependency search path variables (such as `PATH`/`LD_LIBRARY_PATH`) serve related roles but are not identical.

### 7.1. Actual Timeline of `add(20, 22)`

1. The JVM loads/initializes `JniJourney`; the `static` block requests loading `jnijourney`. The OS loader opens the library file with matching architecture; JNI/VM records the library in the class loader's context.
2. Java code calls `JniJourney.add(20, 22)`. Bytecode describes a call to a method marked `native`; the method has no bytecode body generated by the Java compiler.
3. The JVM **resolves the native entry point**. With the name-based linking in this example, the JVM looks up the exported symbol `Java_JniJourney_add` in the loaded library. The exact **timing** of resolution can depend on the JVM; do not assume every call looks up the symbol from scratch.
4. The JVM prepares the transition from Java to native code, passing `JNIEnv *`, `jclass`, and two `jint` values according to the platform's JNI/ABI.
5. The C function runs, computes `20 + 22`, places the `jint 42` result according to the calling convention, and returns control to the JVM.
6. The JVM completes the return to Java, converting the value to `int 42`. Java prints the first line.

For `greet("Java")`, replace the scalar step with a **`jstring` JNI reference**. Native code must use APIs on `JNIEnv` to read/create the String; the JVM still manages Java objects and the garbage collector.

This model helps distinguish **two interfaces**: Java ↔ JNI runtime ↔ C/C++ library. The JVM and native code must agree on the JNI signature, ABI, data types, and lifetime of borrowed data.

## 8. Implementing in C++ Instead of C

C++ uses the same `JniJourney.h` header and the same Java class; the visible difference is how JNI functions are called: **C** uses `(*env)->NewStringUTF(env, ...)`, while **C++** uses `env->NewStringUTF(...)`. JNI provides different syntactic interfaces to support both languages.

To replace C with C++, **do not build `jni_journey.c`**. Replace it with the entire file **`jni_journey.cpp`**:

~~~cpp
#include "JniJourney.h"
#include <cstddef>
#include <cstdio>

extern "C" JNIEXPORT jint JNICALL Java_JniJourney_add(
        JNIEnv *env, jclass clazz, jint left, jint right) {
    (void) env;
    (void) clazz;
    return left + right;
}

extern "C" JNIEXPORT jstring JNICALL Java_JniJourney_greet(
        JNIEnv *env, jclass clazz, jstring name) {
    (void) clazz;

    if (name == nullptr) {
        jclass type = env->FindClass("java/lang/NullPointerException");
        if (type != nullptr) {
            env->ThrowNew(type, "name must not be null");
        }
        return nullptr;
    }

    const char *chars = env->GetStringUTFChars(name, nullptr);
    if (chars == nullptr) {
        return nullptr;
    }

    char buffer[128];
    int count = std::snprintf(buffer, sizeof(buffer), "Hello, %s!", chars);
    env->ReleaseStringUTFChars(name, chars);

    if (count < 0 || static_cast<std::size_t>(count) >= sizeof(buffer)) {
        jclass type = env->FindClass(
                "java/lang/IllegalArgumentException");
        if (type != nullptr) {
            env->ThrowNew(type, "name is too long");
        }
        return nullptr;
    }

    return env->NewStringUTF(buffer);
}
~~~

Compile the **replacement C++ file** on Linux:

~~~bash
c++ -std=c++17 -Wall -Wextra -fPIC -shared \
  -I"$JAVA_HOME/include" \
  -I"$JAVA_HOME/include/linux" \
  jni_journey.cpp -o libjnijourney.so
~~~

On macOS:

~~~bash
c++ -std=c++17 -Wall -Wextra -fPIC -dynamiclib \
  -I"$JAVA_HOME/include" \
  -I"$JAVA_HOME/include/darwin" \
  jni_journey.cpp -o libjnijourney.dylib
~~~

On Windows x64 (MSVC Native Tools CMD):

~~~bat
cl /nologo /EHsc /W4 /LD /I "%JAVA_HOME%\include" /I "%JAVA_HOME%\include\win32" jni_journey.cpp /link /OUT:jnijourney.dll
~~~

After building, re-run the exact Java command from Section 7. **Stdout is identical to the C version** because both versions export the same JNI names/types and implement the same logic.

**Why is `extern "C"` needed?** C++ normally *name-mangles* symbols to represent overloads. JNI looks up exported names according to JNI rules; using C linkage keeps the exported name in the form `Java_JniJourney_add`. The header generated by `javac -h` also guards C++ prototypes with `extern "C"`; writing it explicitly on the definition makes the intent clear. Never let a C++ exception escape across the JNI boundary: handle it in C++ and report the error using the appropriate JNI mechanism (such as `ThrowNew`). Declaring `extern "C"` alone does not give a C++ class a stable C layout.

## 9. Native Signatures: How the JVM Finds the Right Function

For the packageless class in the example:

| Java | C/C++ JNI |
| --- | --- |
| `public static native int add(int, int);` | `Java_JniJourney_add(JNIEnv *, jclass, jint, jint)` returning `jint` |
| `public static native String greet(String);` | `Java_JniJourney_greet(JNIEnv *, jclass, jstring)` returning `jstring` |

When there is a package, the exported name includes the package name. For example, class `com.example.NativeMath` with method `add` typically has the prefix `Java_com_example_NativeMath_add`. Underscores in names, Unicode, special characters, and overloads also have **escaping rules**; do not construct names by guesswork.

For **overloaded native methods**, the long JNI name may require a `__` suffix followed by the encoded parameter signature. The JVM tries short/long name lookup according to the JNI specification; if overloads require disambiguation, symbols must be unambiguous. The header generated by `javac -h` is the authoritative source to avoid writing the wrong name. If Java changes a signature and you forget to rebuild the native code, symbol lookup or the call ABI can fail.

Besides linking by exported name, JNI provides **`RegisterNatives`** to register a method name, JNI signature, and C/C++ function pointer. Example info structure declaration (illustrative snippet, not a standalone program):

~~~c
/* Example describing a native method registration entry */
JNINativeMethod entry = {
    "add",        /* Java method name */
    "(II)I",      /* (int, int) -> int per JNI descriptor */
    (void *) native_add_impl
};

/* After obtaining the correct env and jclass, check the result: */
// (*env)->RegisterNatives(env, clazz, &entry, 1);
~~~

When using `RegisterNatives`, the code must provide `native_add_impl` with the exact JNI ABI prototype and register it against the appropriate `jclass`. This mechanism is useful when controlling initialization yourself, but is **not necessary** for the exported-name `Java_JniJourney_add` example. A wrong registration entry can lead to undefined behavior, so use the exact signature and only register methods you control.

### 9.1. How Do `static` and Instance Methods Differ?

~~~java
// Illustration of declarations in a class, not a standalone runnable example:
public static native int staticSum(int a, int b);
public native int instanceSum(int a, int b);
~~~

Conceptual prototypes after `javac -h`:

~~~c
JNIEXPORT jint JNICALL Java_Example_staticSum(
        JNIEnv *env, jclass clazz, jint a, jint b);

JNIEXPORT jint JNICALL Java_Example_instanceSum(
        JNIEnv *env, jobject self, jint a, jint b);
~~~

In this example, `Example` is a hypothetical class name used to illustrate the signature; if a real class has a package or a different name, the header changes accordingly. **The second parameter** is a class reference for a static native method, whereas an instance native method receives a reference to the current object. A Java method with two parameters corresponds to a C function with four parameters, not two.

## 10. What Types Do Java and JNI Pass?

| Java Type | Typical C/C++ JNI Type | Notes |
| --- | --- | --- |
| `boolean` | `jboolean` | Use `JNI_TRUE`/`JNI_FALSE` when needed; do not assume C `bool` has the same ABI |
| `byte` | `jbyte` | 8-bit signed per Java |
| `char` | `jchar` | 16-bit unsigned UTF-16 code unit, not C `char` |
| `short` | `jshort` | 16-bit signed |
| `int` | `jint` | 32-bit signed |
| `long` | `jlong` | 64-bit signed; do **not** assume C `long` is 64-bit on Windows |
| `float` | `jfloat` | 32-bit floating-point |
| `double` | `jdouble` | 64-bit floating-point |
| `String` | `jstring` | Opaque reference to a Java String |
| `int[]` | `jintArray` | Reference to a Java array; requires JNI APIs to access |
| `Object`/Java class | `jobject`/appropriate JNI reference type | Must not be dereferenced as a pointer to a C struct |
| `void` | `void` | Native method returns no result |

**Primitives** are passed by corresponding value; Java objects/arrays are passed via **JNI references** managed by the JVM. Do not assume a `jobject` pointer address is a stable heap object address: the GC may move objects, while the JNI handle remains managed by the JVM through the reference mechanism.

A JNI reference returned from a JNI function is usually a **local reference**. For a native call initiated by Java, local references are valid for the duration of that call on that thread and are reclaimed by the JVM when the native method returns. If native code needs to keep an object across multiple calls, it must create a **global reference** via `NewGlobalRef` and call `DeleteGlobalRef` at the appropriate time. Do not store a local reference in a global variable and reuse it on another thread.

### 10.1. Receiving an `int[]` Array

Illustrative **JNI pattern** example for a `jintArray` argument, not the standalone runnable `JniJourney` program:

~~~c
JNIEXPORT jint JNICALL Java_Example_firstElement(
        JNIEnv *env, jclass clazz, jintArray values) {
    (void) clazz;

    if (values == NULL) {
        return 0;  /* Simplified example: a real API needs an error contract */
    }

    jsize length = (*env)->GetArrayLength(env, values);
    if (length == 0) {
        return 0;
    }

    jint value = 0;
    (*env)->GetIntArrayRegion(env, values, 0, 1, &value);
    return value;
}
~~~

`GetIntArrayRegion` **copies** the requested elements into a C buffer, allowing code that only needs the first value to avoid holding a pointer to the entire array. This pattern is only valid after null and length checks. If working via `GetIntArrayElements`, you must account for possible copies and **call `ReleaseIntArrayElements`** properly; many JNI-returned data regions must be released and must not be used after release.

## 11. What Happens When There Is an Error or Java Exception?

JNI does not automatically convert every `errno`, C return code, C++ exception, or allocation failure into a Java exception. You must define an error-reporting contract:

- **Pending Java exception:** `ThrowNew` marks an exception for the JVM to throw when control returns to Java; native code must return a compatible type and avoid continuing disallowed JNI calls while an exception is pending.
- **Failed JNI operation:** `GetStringUTFChars` or `NewStringUTF` may return `NULL` on failure; many JNI APIs set a pending exception. Check the result before using it.
- **C++ exception:** catch it on the C++ side, clean up resources, and then create an appropriate Java exception. Letting a C++ exception unwind across a JNI frame is unsafe integration.
- **Native crash:** dereferencing an invalid pointer, use-after-free, ABI mismatch, or buffer overflow can terminate the entire JVM; Java `try/catch` cannot repair corrupted native memory.
- **Normal native function return:** a value like `jint 0` does not automatically mean “success”. Error/result semantics must be defined by the API design.

For example, instead of just returning `NULL` on null input, `greet` calls `FindClass("java/lang/NullPointerException")` and then `ThrowNew`; Java will observe the Java exception. Returning `NULL` here **does not replace creating the exception**—it is simply an appropriate return value when exiting a native function with a pending exception.

### 11.1. `JNIEnv *` and Thread Safety

`JNIEnv *` is bound to the **current thread**; do not save it to pass to another OS thread. If a native thread created by the C/C++ application itself needs to call into the JVM, it must attach via the Invocation API (such as `AttachCurrentThread`) and detach per the contract. JNI local references also have corresponding thread/call scope. Memory from `GetStringUTFChars`, array elements, and native buffers must remain valid for the entire duration of use.

JNI does not automatically make C/C++ functions thread-safe. If multiple Java threads call `add` concurrently, the example has no shared mutable state; if native code uses global variables, shared buffers, or library state, you must synchronize as required.

## 12. Common Errors and How to Fix Them

| Symptom | Common Explanation | What to Check |
| --- | --- | --- |
| `UnsatisfiedLinkError: no jnijourney in java.library.path` | The JVM cannot find the library with logical name `jnijourney` | Output name `libjnijourney.so`/`.dylib`/`jnijourney.dll`, working directory, `-Djava.library.path=.`, case-sensitive name on the relevant OS |
| `UnsatisfiedLinkError: ... add(II)I` | The library was loaded, but the JVM could not link the native method | Check `javac -h` header, exported symbol name, `extern "C"`, overloads, package; rebuild native |
| `wrong ELF class`/architecture error | JVM and library have different architectures or formats | Check x86/x64/ARM64, compiler target, 32/64-bit, OS |
| `jni.h: No such file or directory` | Missing JDK include path | Verify `JAVA_HOME/include/jni.h`, add OS-specific header |
| `NoClassDefFoundError: Could not initialize class ...` | Class failed during earlier initialization, possibly because `loadLibrary` threw an error | Check the **first exception** in the stack trace and fix the root cause |
| Java String produces garbage/truncated text | Casting `jstring` to `char *`, Modified UTF-8 mismatch, or overflow | Use JNI APIs, check sizes, and release resources |
| JVM crashes after several calls | JNI reference/buffer outlived its lifetime; wrong signature; memory corruption | Check `hs_err_pid...log`, ABI, local/global references, ownership, and debug builds |
| Fails only in apps with multiple class loaders | The JNI library is already bound to another class loader | Check library loading strategy per class loader and which library copy is used |

To inspect exported symbols, you can use the appropriate tool:

~~~bash
# Linux / ELF
nm -D libjnijourney.so

# macOS / Mach-O
nm -gU libjnijourney.dylib
~~~

Windows (Developer Command Prompt):

~~~bat
dumpbin /exports jnijourney.dll
~~~

Look for `Java_JniJourney_add` and `Java_JniJourney_greet` (on some platforms, disassembly/symbol utilities may show an extra prefix or platform-specific decoration). On 32-bit x86, name decoration rules and calling conventions can differ from x64; always use the **JNI header and the right target compiler**.

**Minimal diagnostic workflow:** check `java -version` and `javac -version` → verify JDK headers → compile Java and regenerate header → verify library file architecture → inspect exports → re-run with library path configured at startup → only then investigate data/exception handling.

## 13. JNI Flow Pitfalls to Avoid

1. **Thinking `native` already contains an implementation.** The keyword only declares the contract; the native library must be built and linked.
2. **Thinking `System.loadLibrary` immediately invokes JNI functions.** It mainly loads the library and triggers related hooks if any; `add` only runs when Java calls `add`.
3. **Writing prototypes manually instead of using `javac -h`.** It is easy to forget `JNIEnv *`, `jclass`, or get the symbol name wrong when packages/overloads are present.
4. **Using C `int/long` arbitrarily instead of JNI types.** Use `jint`, `jlong`, `jstring`; in particular, C `long` can be 32-bit on Windows x64.
5. **Treating `jstring` like a C string.** It is an opaque reference requiring `GetStringUTFChars`/`ReleaseStringUTFChars` or equivalent APIs.
6. **Forgetting `extern "C"` in C++.** Name mangling breaks JNI linking if the wrong name is exported; always follow the generated header.
7. **Keeping `JNIEnv *` or local references on the wrong thread or past their lifetime.** This is a source of hard-to-reproduce bugs and can crash the JVM.
8. **Mixing up `System.load` and `System.loadLibrary`.** `System.load` typically takes an absolute path to the library file, whereas `loadLibrary` takes a logical name without path/extension.
9. **Treating JNI as FFM.** The Foreign Function & Memory API has a different symbol/descriptor model; `Linker.downcallHandle` for pure C ABI does not automatically prepend `JNIEnv *` and `jclass` like a JNI entry point.
10. **Assuming build commands are OS-independent.** File extensions, platform-specific headers, and calling conventions must all match the JVM.

## 14. Check Your Understanding

1. After writing `public static native int add(int, int);`, what build/run steps remain before the Java program calls it successfully?
2. Why does the C function receive four parameters when Java calls `add(20, 22)`?
3. If you rename the Java class from `JniJourney` to `com.acme.JniJourney` without rebuilding the native code, what error typically occurs?
4. Why must `GetStringUTFChars` be paired with `ReleaseStringUTFChars`, and why does `NewStringUTF` require valid Modified UTF-8?
5. Distinguish between a **library not found** error and a **native method symbol not found** error.
6. If using C++ instead of C, what stays the same and what changes in the signature and JNI API call syntax?

**Answer hints:** (1) `javac -h` → create C/C++ JNI implementation matching the header → compile into a library for the right target → load the library and call it; (2) two implicit parameters `JNIEnv *` and `jclass`; (3) typically `UnsatisfiedLinkError` when the matching symbol is not found; (4) the byte region must be released, and Modified UTF-8 is not identical to standard UTF-8; (5) one occurs when loading the library, the other occurs when linking the method; (6) JNI types/symbols/contract stay the same, while C++ uses `env->...` and requires C linkage.
