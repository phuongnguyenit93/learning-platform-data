# Do not assume the input byte array is always identical to the class on disk

When writing a Java agent, the `classfileBuffer` parameter of `ClassFileTransformer.transform(...)` contains the **class file bytes at the current step in the transformation chain**. There is no general guarantee that this byte array is identical to the `.class` file you open from the build directory or a JAR on disk. During a class definition pass, a preceding transformer may have already modified the bytes; during a `redefineClasses` or `retransformClasses` pass, the source and reconstruction of the bytes also depend on prior instrumentation requests. Some classes are also generated directly in memory, with no corresponding `.class` file to compare against.

**Working principle:** Treat `classfileBuffer` as the **actual, authoritative input for that callback invocation**. When you want to transform it, read and parse the exact array passed in, create a new array, and return it. Only use "bytes on disk" as reference data when you can verify that they come from the exact same class, class loader, version, and processing stage.

## 1. Why does this topic matter?

Suppose an application uses two agents:

- Agent A inserts timing measurements into a method.
- Agent B inserts logging or collects coverage in the same method.

If B assumes the class file being processed is always the version unmodified by A and searches for an opcode sequence or offset that only existed in the original version, B may misidentify the insertion point, corrupt stack map frames, or produce invalid bytecode. The result can be a `VerifyError`, `ClassFormatError`, or an observability tool reporting inaccurate metrics.

The right mental model:

```text
Bytecode at the time the JVM requests definition/redefine/retransform
                  |
                  v
          Transformer A
        inputA -> outputA
                  |
                  v
          Transformer B
        inputB = outputA (if A returns a new byte[])
                  |
                  v
          Transformer C ...
                  |
                  v
      JVM verifies and applies the resulting class bytes
```

If A returns `null`, the JVM forwards the current bytes to B; if A returns a new `byte[]` array, that array becomes B's input content. Transformers compose in a **chain**, rather than operating independently by default on separate copies of an original `.class` file.

This is not only about content changes. Even when the Java logic is equivalent, the bytes may differ due to the constant pool, attributes, ordering of non-significant parts, or data generated by the compiler/agent/class loader.

## 2. What does `classfileBuffer` actually represent?

The full signature commonly used in Java 17:

```java
@Override
public byte[] transform(
        Module module,
        ClassLoader loader,
        String className,
        Class<?> classBeingRedefined,
        java.security.ProtectionDomain protectionDomain,
        byte[] classfileBuffer) {
    // Read the bytes of the current transformation step.
    return null;
}
```

This is an **illustrative method body placed inside a class implementing ClassFileTransformer**, not a standalone Java program. `className` typically uses the **internal name** such as `demo/pipeline/Target`; `classBeingRedefined == null` during a new definition and is non-`null` during a redefine or retransform.

According to the Java 17 contract, the input to the **first transformer in the chain** depends on the case:

| Scenario | Initial byte source per the contract |
| --- | --- |
| **Defining a new class** | The bytes passed to `ClassLoader.defineClass(...)` or an equivalent JVM definition mechanism. |
| **Redefining a loaded class** | The bytes supplied by the `Instrumentation.redefineClasses(...)` call in `ClassDefinition`. |
| **Retransforming a loaded class** | The JVM starts from the initial definition bytes or the most recent redefine per the contract; the effects of transformers that do not support retransformation are reapplied, while transformers that support it are called again. |
| **Second and subsequent transformers in a chain** | The input bytes are the **current result** left by the preceding transformer, which may already differ from the request's source bytes. |

In the table above, "first transformer" means the first transformer in the **actual execution chain**, not necessarily the first agent named on the `java` command line in all cases. The JVM groups transformers by retransformation capability and by Java/native category before applying registration order within each group.

### 2.1. The name "class file" does not require a file on the filesystem

The specification uses the term **class file** to refer to a valid byte sequence conforming to the JVM ClassFile format; this sequence **can exist entirely in memory**. Classes can be generated by code generators, custom class loaders, frameworks, proxies, or other runtime mechanisms without any standalone `.class` file on disk.

With standard class loaders, the source file may reside in a JAR or module image rather than an `out` directory. With a custom loader, the bytes passed to `defineClass` may have been decompressed, decrypted, or synthesized from another source. Therefore, "reading the class file on disk and comparing" may be impossible or may compare **the wrong object**.

### 2.2. Do not assume `getResourceAsStream` returns the exact bytes the JVM is using

`loader.getResourceAsStream("pkg/Type.class")` returns **the classpath resource that the loader finds at the time of reading**. It is not a standard API for retrieving the active class definition. There are several reasons they may differ: the class loader does not expose a corresponding resource, the resolved resource differs from the definition source, multiple JARs contain the same name, the class was generated in memory, or transformers have already modified the class after the resource was read.

In the hands-on example below, we **deliberately use a simple classpath** so that the `Target.class` file on disk serves as a reliable reference point. Do not generalize that result as a guarantee for all production applications.

## 3. Rules for coordinating multiple transformers

There are two common registration patterns:

```java
// Snippet inside premain/agentmain:
instrumentation.addTransformer(transformerA, false);
instrumentation.addTransformer(transformerB, false);
```

Both A and B belong to the same **Java retransformation-incapable transformer** group. If A is registered before B, then on a new class definition, the JVM calls A before B. B receives the bytes processed by A if A returns a new `byte[]`.

In Java 17, the order of **groups** is:

1. Java transformers **that do not support retransformation** (`canRetransform=false`).
2. Native transformers that do not support retransformation.
3. Java transformers **that support retransformation** (`canRetransform=true`).
4. Native transformers that support retransformation.

Within a group, registration order determines execution order. Thus, with A `canRetransform=true` and B `false`, B can run before A **even when A was registered first**. Do not infer transform order solely from the order agents are listed on the command line.

Return values:

| A returns | Bytes B receives |
| --- | --- |
| `null` | Keeps the current bytes of the chain unchanged. |
| A valid new `byte[]` array | Passes the new byte array to B. |
| Throws an uncaught exception | Per the contract, the JVM still continues calling subsequent transformers; the effect is equivalent to A returning `null`. |
| Invalid bytes | The JVM still attempts to verify/apply them; a class format/verification error may occur. There is no automatic mechanism to repair malformed bytes. |

**Mandatory:** `classfileBuffer` is an **input array that must not be modified in place**. When transforming, create another array, such as `byte[] output = classfileBuffer.clone()`, modify `output`, and return `output`. Return `null` when no transformation is needed.

## 4. Runnable experiment: transformer B sees bytes already modified by A

We use **Java 17+** with no external libraries. The agent registers two transformers in the same group in the order A → B:

- **A** modifies a short string literal by replacing an exact constant-length ASCII string in the constant pool: `FROM_DISK` → `FROM_LIVE`.
- **B** reads the `classfileBuffer` passed by the JVM, separately reads `Target.class` from the class loader's resource, and compares them. B does not modify the bytes.
- **The application** loads `Target` after `premain` has registered A and B, and invokes `Target.message()` via reflection to avoid a static reference beforehand.
- We will observe that **B receives `FROM_LIVE`**, while the `Target.class` resource still contains `FROM_DISK`.

The experiment deliberately replaces an exact ASCII literal of the **same 9-byte length** so as not to shift the class file structure. This "search and patch raw bytes" technique is only for small verification demos where the exact input content is known. In real systems, use a dedicated parser/bytecode library and handle constant pool structure, stack maps, and the class model properly.

### 4.3. `src/demo/pipeline/Agent.java`

```java

    private Agent() {}

    public static void premain(String options, Instrumentation inst) {
        inst.addTransformer(new FirstTransformer(), false);

    }
}
```

Because A and B are registered with `false`, both are in the same Java retransformation-incapable group. The JVM calls A then B when `Target` is first defined after registration.

### 4.4. `src/demo/pipeline/FirstTransformer.java`

```java
package demo.pipeline;

import java.lang.instrument.ClassFileTransformer;
import java.nio.charset.StandardCharsets;
import java.security.ProtectionDomain;

public final class FirstTransformer implements ClassFileTransformer {
    @Override
    public byte[] transform(
            Module module,
            ClassLoader loader,
            String className,
            Class<?> classBeingRedefined,
            ProtectionDomain protectionDomain,
            byte[] classfileBuffer) {

        if (!"demo/pipeline/Target".equals(className)) {
            return null;
        }

        byte[] from = "FROM_DISK".getBytes(StandardCharsets.US_ASCII);
        byte[] to = "FROM_LIVE".getBytes(StandardCharsets.US_ASCII);
        byte[] result = classfileBuffer.clone();

        int matches = 0;
        int foundAt = -1;

        for (int i = 0; i <= result.length - from.length; i++) {
            boolean equal = true;
            for (int j = 0; j < from.length; j++) {
                if (result[i + j] != from[j]) {
                    equal = false;
                    break;
                }
            }
            if (equal) {
                matches++;
                foundAt = i;
            }
        }

        if (matches != 1 || from.length != to.length) {
            throw new IllegalStateException(
                    "Expected exactly one fixed-length marker, got "
                            + matches);
        }

        System.arraycopy(to, 0, result, foundAt, to.length);
        System.out.println("[A] replaced FROM_DISK -> FROM_LIVE");
        return result;
    }
}
```

Explanation:

1. A processes only `Target`; internal JVM names use `/`.
2. A **clones** `classfileBuffer` and modifies the resulting array; it does not mutate the array passed by the JVM.
3. It searches for exactly one occurrence of the ASCII literal `FROM_DISK` and verifies that both strings have equal length before writing. In the sample class, that location is the payload of the UTF-8 constant-pool entry for the literal.
4. When A returns `result`, the JVM passes the **modified bytes** to the next transformer.
5. If the sample class is altered so the marker no longer appears exactly once, A throws an error to report the issue in logs; per the contract, this exception does not by itself stop class definition. Therefore, do not use this strategy in production.

Java 17 defines `ClassFileTransformer` with default `transform` methods; **you cannot use a lambda directly** as a functional interface. The class above overrides the six-parameter form, so it compiles cleanly.

### 4.5. `src/demo/pipeline/SecondTransformer.java`

```java
package demo.pipeline;

import java.io.IOException;
import java.io.InputStream;
import java.lang.instrument.ClassFileTransformer;
import java.nio.charset.StandardCharsets;
import java.security.ProtectionDomain;
import java.util.Arrays;

public final class SecondTransformer implements ClassFileTransformer {
    @Override
    public byte[] transform(
            Module module,
            ClassLoader loader,
            String className,
            Class<?> classBeingRedefined,
            ProtectionDomain protectionDomain,
            byte[] classfileBuffer) {

        if (!"demo/pipeline/Target".equals(className)) {
            return null;
        }

        byte[] resourceBytes;
        try (InputStream input = loader.getResourceAsStream(
                "demo/pipeline/Target.class")) {
            if (input == null) {
                throw new IllegalStateException("Target resource missing");
            }
            resourceBytes = input.readAllBytes();
        } catch (IOException e) {
            throw new IllegalStateException("Reading class resource failed", e);
        }

        // ISO-8859-1 maps bytes 1:1 to Unicode characters 0..255,
        // sufficient to detect ASCII strings in this experiment.
        String incoming = new String(
                classfileBuffer, StandardCharsets.ISO_8859_1);
        String resource = new String(
                resourceBytes, StandardCharsets.ISO_8859_1);

        System.out.println("[B] inputHasFROM_LIVE="
                + incoming.contains("FROM_LIVE"));
        System.out.println("[B] resourceHasFROM_DISK="
                + resource.contains("FROM_DISK"));
        System.out.println("[B] inputEqualsResource="
                + Arrays.equals(classfileBuffer, resourceBytes));

        return null;
    }
}
```

B does not take the "original from disk" to overwrite the input array. B only uses the resource as a **proof baseline**; the authoritative value for the current instrumentation step is `classfileBuffer`. B returns `null` to preserve the result already applied by A.

**Limitation of the comparison:** In the sample program, the classpath is the `out` directory and the resource returns the bytes of `out/demo/pipeline/Target.class`, so we know the reference baseline. Outside this setup, the same resource path may not reflect the bytes passed to `defineClass`; do not use resource reading as a general oracle.

Step-by-step explanation:

1. The JVM calls `Agent.premain`; A/B are registered before application `main`.
2. App prints its first line and then asks the JVM to define `Target`.
3. A receives the bytes of the new definition, replaces the literal `FROM_DISK` with `FROM_LIVE` in a **cloned array**, and returns the new bytes.
4. B is called after A, so B's `classfileBuffer` contains the literal `FROM_LIVE`. Meanwhile, B reads the unmodified `Target.class` resource on disk, which still contains `FROM_DISK`. Therefore `Arrays.equals(...)` returns `false`.
5. The JVM defines `Target` from the final bytes. Calling `message()` returns `FROM_LIVE` even though the compiler wrote `FROM_DISK` into the class file on disk.

## 5. When do the first transformer's bytes also differ from the class content on disk?

The example above proves that **transformer B** receives bytes different from the resource version. Even the **first** transformer should not assume its input is the "original file on disk":

| Definition source | Why comparing directly against a file is unreliable |
| --- | --- |
| Custom `ClassLoader` | The loader may read bytes from a network, database, encrypted package, or synthesize/modify bytes before calling `defineClass`. |
| Runtime bytecode generation | Proxies/classes generated at runtime may have no `.class` file on disk. |
| Classes in a JAR or module | Data comes from the selected entry in the archive/module, not necessarily from an `out/Type.class` path that a tool guesses. |
| Multi-release JAR | The JVM may select an entry version based on the runtime version; the root-level entry is not necessarily the one loaded. |
| Multiple classpath/module path entries | Duplicate class names across different sources; the **defining loader** and search order determine which source is used. |
| Redefined class | The runtime definition may be based on bytes passed to `ClassDefinition`, not matching the old deployed artifact. |
| Retransformation | The JVM uses the base bytes of the most recent definition and reapplies transformations from incapable transformers; the bytes may differ from both the disk version and the previous call's output. |

The key anchor is **class identity**: in the JVM, a class's identity is bound to its **binary name + defining class loader**. Two different class loaders can define two classes with the same name from different bytes; finding a `com/acme/Foo.class` file does not guarantee those are the bytes of the exact class being transformed.

If you genuinely need to verify class provenance, you can record the defining loader, module, code source when available, resource URL (for reference only), a checksum of the bytes **right at the callback**, and build metadata. Do not treat a resource lookup result as a guarantee that all bytes in `classfileBuffer` are a copy of that file.

## 6. Retransformation: the risk of assuming "next time I will see the original bytes again"

`Instrumentation.retransformClasses(Class<?>...)` is a separate capability that may not be supported by a given JVM or configuration. For loaded classes and transformers with different retransformation capabilities, the JVM follows a special rule:

```text
Base bytes of the most recent definition/redefine
        |
        v
Automatically reapply effects from canRetransform=false transformers
        |    (without re-invoking transform() on false transformers)
        v
Invoke canRetransform=true transformers
        |    (receiving bytes that already include the reapplied effects)
        v
Verify and install the retransformed definition
```

Here, `canRetransform=false` does **not** mean prior effects are necessarily discarded during retransformation. Instead, the JVM may reuse the old transformation results from the incapable group **without invoking their callbacks again**.

Conceptual example, **not standalone runnable code**:

```text
At class load time:
  A (false): adds marker A to the bytes
  B (true):  receives bytes containing marker A, adds marker B
  JVM installs the class after A and B

At retransform time:
  A (false): is not called again
  JVM reapplies A's transformation from the previous load/redefine
  B (true):  is called again, may receive bytes already containing marker A
  JVM installs the new result
```

In Java 17, the *initial class file bytes* used as the basis for retransformation **may not be byte-for-byte identical** to the bytes from the earlier `defineClass`/`redefineClasses`: the constant pool may be laid out differently, have entries added/removed, or be reordered; some attributes may be absent; structures without ordering significance may be swapped. Therefore, **never treat the checksum or offsets of the load-time buffer as invariant across retransformations**.

Several consequences follow:

- Transformers supporting retransformation must tolerate **multiple callbacks for the same class**.
- Avoid inserting the same helper or marker twice if the bytes already contain it; perform idempotence checks at the **bytecode structure level**, not merely by comparing against a file on disk.
- For a class transformed multiple times, you cannot deduce the origin of the bytes from a single `retransformClasses` call without understanding the entire active transformer chain.
- Retransformation and redefinition restrict class schema changes; you cannot arbitrarily add/remove fields/methods or change inheritance. The definition must remain valid for the running JVM.
- `isRetransformClassesSupported()` and `isModifiableClass(clazz)` should be checked before relying on class re-processing.

## 7. Redefinition: the caller supplies the bytes, not necessarily from disk

In `Instrumentation.redefineClasses(ClassDefinition...)`, the API caller passes in the **new class definition** via `ClassDefinition.getDefinitionClassFile()`. These bytes may be read from a file, fetched elsewhere, or generated in memory by an instrumentation tool. Transformers are invoked according to redefinition rules before the bytes are verified and installed.

Thus, even the first transformer must parse the **array supplied by the JVM**; do not open `Foo.class` on disk and assume it is the input. A redefinition can change method bodies without altering the old artifact file, because applying it at runtime does not write back to the JAR.

Transformations during a redefinition pass are also chained. When handling `classBeingRedefined != null`, the transformer must ensure the output satisfies **redefinition semantics**, meaning it is a legal replacement for the existing class.

## 8. How to write resilient transformers when you do not control the entire chain

1. **Filter the right targets.** Check `className` in internal form (`/`), `loader`, `module`, and `classBeingRedefined` where meaningful. Do not rely solely on a basename like `Service.class`.
2. **Parse `classfileBuffer` itself.** Use a class file parser/ASM/Byte Buddy compatible with the version, constant pool, and attributes of the current bytes. Do not rely on opcode offsets, constant pool entry order, or checksums from the original artifact.
3. **Do not mutate the input buffer.** When making changes, create and return a new output array. If making no changes, return `null`; do not return a garbage array or retain a mutable reference outside the callback for later modification.
4. **Ensure validity.** Properly handle stack map frames, max stack, branches, exception handlers, the constant pool, descriptors, and class version. A preceding transformer may have added code that invalidates original offsets.
5. **Idempotence.** Detect existing markers/structural patterns before instrumenting; do not stack wrappers/helpers infinitely across retransformations.
6. **Cooperate with multiple agents.** Do not assume transform order from JVM argument order alone; check `canRetransform`, Java/native groups, and actual registration order.
7. **Instrument diagnostics appropriately.** When comparison is needed, record the hash of the **bytes received by the callback**, the hash of the bytes **returned**, the class name, defining loader, and event type. The hash of a resource on disk is a separate piece of data.
8. **Handle errors cleanly.** If class bytes are invalid, you may throw `IllegalClassFormatException` for logging/debugging, but do not rely on exceptions to block class loading: the JVM will still attempt to proceed as if the transformer returned `null`.
9. **Keep callbacks short and safe.** Class loading can occur concurrently on multiple threads. Avoid heavy I/O inside `transform`, dependencies prone to recursive class loading, deadlocks, and loggers that require unloaded classes.
10. **Verify results at runtime.** Success means the JVM accepts the bytes and application behavior is correct. Having an input hash that differs from disk **alone** is not sufficient proof that instrumentation is correct.

### Diagnostic workflow when A and B conflict

A practical workflow is to run A alone, run B alone, and then run both together with the same JDK/classpath; log registration order and transformer types; capture class identity at the callback; compare before/after hashes at each step; and save a dump **when authorized to do so** for inspection with `javap -v` or an appropriate verifier. Then test loading new classes and retransform/redefine separately when those features are supported.

If B only works without A, first check whether B depends on original bytecode, fixed offsets, or the constant pool order of the file on disk. Changing agent order may expose the bug, but it will not solve the design issue if B still assumes a fixed byte source.

## 9. Common misconceptions and symptoms

| Claim or symptom | Correct understanding |
| --- | --- |
| "`classfileBuffer` is always the bytes of `out/Foo.class`." | False. The buffer belongs to the current transform step; the initial source is the bytes the JVM was asked to define/redefine/retransform. |
| "Both transformers see the same class version from disk." | False when a preceding transformer returns new bytes; the subsequent transformer receives the previous result. |
| "If A returns `null`, the JVM gives B the original bytes from disk." | No. `null` keeps the **current bytes**, which may have already passed through other transformers. |
| "A runs first if `-javaagent:a.jar` precedes B in all cases." | Insufficient: registration order, Java/native groups, and `canRetransform` also matter. |
| "`getResourceAsStream` is a snapshot of the runtime class." | No. It is a resource lookup, which may match or differ from the definition source. |
| "If the file is not on disk, the callback cannot run." | False. A class can be generated from bytes in memory. |
| "`classBeingRedefined != null` means a new class is being loaded." | The opposite: it indicates redefinition/retransformation of an existing class. |
| "Retransform will re-invoke every transformer, including false ones." | No. The `canRetransform=false` group is not called again; prior effects are reapplied per the rules. |
| "Retransform bytes are always byte-for-byte identical to the initial `defineClass` bytes." | No. Java 17 explicitly notes they may differ in constant pool, attributes, and ordering of some components. |
| "Modifying `classfileBuffer` in place saves memory." | Violates the contract. Create a new output byte array. |
| "If A throws an exception, class loading definitely stops." | No. The JVM treats it equivalently to A returning `null` and continues to subsequent transformers. |
| "`javap -v` on the JAR shows the transformed class bytes in the JVM." | No. It reads the provided artifact and does not access the transformed runtime class definition. |

## 10. Self-check questions

**Question 1.** A returns a new `byte[]` with added logging; B is registered after A in the same group. Which bytes does B see?

**Answer:** B receives the new bytes returned by A via the `classfileBuffer` parameter. It does not default to receiving the bytes of the original `.class` file on disk.

**Question 2.** B returns `null` after A has modified the bytes. Does the JVM discard A's transformation?

**Answer:** No. B's `null` only means B makes no further changes; the bytes after A remain the input to the next stage.

**Question 3.** Why does `Target.message()` return `FROM_LIVE` in the lab while the `Target.class` resource still contains `FROM_DISK`?

**Answer:** A modified the bytes in the class definition pipeline **in memory**, without writing back to the file. B saw the bytes after A, and the JVM installed the class from the transformed bytes.

**Question 4.** If a custom loader generates class bytes in memory, where should you get the original version from disk?

**Answer:** There may be no disk version. Process the bytes the JVM actually passes through the callback and, if provenance is needed, instrument the class generation/definition source according to the loader's design.

**Question 5.** Initially A is registered with `canRetransform=false` and B with `true`. When retransform is called, does A receive the callback again?

**Answer:** No. The JVM reapplies A's effect from the previous load/redefine without calling A, and then calls B as part of the retransformation-capable group.

**Question 6.** Can you compute the SHA-256 of `Foo.class` on disk and require that `classfileBuffer`'s hash always match it?

**Answer:** No. The hash on disk measures a specific artifact; the callback hash measures bytes at a point in the runtime chain. The two can both be valid yet different.

**Question 7.** A transformer only works well when it is the sole agent. Can you fix it by forcing B to always run before A?

**Answer:** Changing the order can help isolate the bug, but the durable solution is to make B understand and properly process the input bytes of the **actual transformation chain**, respect class structure constraints, and verify compatibility.

## 11. Key takeaways and primary references

**Five key points:**

1. `classfileBuffer` is the **bytes at the current step of the pipeline**, with no guarantee that it is the `.class` file sitting on disk.
2. In a chain, **the bytes A returns are the input B receives**; returning `null` preserves the current bytes.
3. Input sources differ across **class definition**, **redefinition**, and **retransformation**; classes can also be created without a file on disk.
4. Retransformation has rules for **reusing incapable transformations**, and base bytes may change constant pool/attribute layouts.
5. Writing a transformer properly means **reading the passed-in bytes, not mutating the input array, producing valid output bytes, and verifying the result when the JVM applies it**.
