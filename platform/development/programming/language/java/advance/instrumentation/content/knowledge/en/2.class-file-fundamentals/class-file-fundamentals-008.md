# Annotations, synthetic, bridge, lambda, and compiler-generated code in Java class files

> **Goal:** When looking at a `.class` file, distinguish structures actually declared by the programmer from metadata and code generated by the compiler/runtime; understand the role of annotations, the `ACC_SYNTHETIC` and `ACC_BRIDGE` flags, generic bridge methods, and lambdas using `invokedynamic`; and from there choose the right instrumentation points, avoiding missed or duplicate event recording.

## 1. Why doesn't the code in `.class` look identical to the Java code written?

Java source is not executed directly by the JVM. `javac` translates source into class, field, method, bytecode, and **attributes** definitions in a `.class` file. During this process, the compiler must fulfill language obligations that the source does not state as a specific method: preserving polymorphism after generic erasure, implementing lambdas, storing annotations with appropriate retention, generating constructors or helper methods when needed.

For example, the source only has one method `String convert(String)`, but the class file may also have an `Object convert(Object)` method to maintain compatibility with the erased generic type. A lambda `x -> x.trim()` may correspond to an `invokedynamic` instruction, an implementation method with a compiler-chosen name, and a functional interface object created at runtime. An annotation `@Tag` may remain only as metadata, never appearing as an executed instruction at all.

This is a practical problem for **instrumentation**:

- If an agent counts every method entry, a single business call may be counted twice because it passes through both the **bridge method** and the original method.
- If filtering out all `synthetic` methods, the agent may miss code that **actually executes** inside a lambda body.
- If using only Java Reflection to find annotations, the agent will not see annotations with `CLASS` retention.
- If looking for a `SomeClass$$Lambda...class` file on disk, it may not be found because the lambda implementation is generated at runtime and may be a **hidden class**.
- If believing that every `invokedynamic` is a lambda, the agent easily misinterprets call sites used for other purposes, such as string concatenation.

**Principle:** Each structure in a class file has a different role: descriptive metadata, executable method bytecode, access flags describing method properties, and bootstrap/call sites participating in behavior linkage. You must know which kind you are reading before deciding where to insert a probe.

## 2. Map of components to identify

| Component | Typical manifestation in a class file | Main meaning | Impact on instrumentation |
| --- | --- | --- | --- |
| **Annotation** | `RuntimeVisibleAnnotations`, `RuntimeInvisibleAnnotations`, parameter/type annotation attributes | Metadata on declarations or type-use locations | Select components to monitor; not executable code by default |
| **Synthetic** | `ACC_SYNTHETIC` flag or `Synthetic` attribute on the corresponding class/member | Component that does not appear directly as a declaration in source | Avoid treating all of them as user API; may still contain important bytecode |
| **Bridge method** | Method flag `ACC_BRIDGE`, usually accompanied by `ACC_SYNTHETIC` with `javac` | Preserves polymorphism when the descriptor changes due to generic erasure or covariant return | May create an extra call layer leading to duplicate statistics |
| **Lambda / method reference** | `invokedynamic`, `BootstrapMethods` entries, method handles, possibly `lambda$...` methods | Creates functional interface behavior through dynamic linkage | Cannot just scan methods declared by Java source name |
| **Other compiler-generated components** | Constructors, accessors, auxiliary fields, instructions inside methods, special attributes | Implements Java language rules | Not all generated code has a distinct name or the `synthetic` flag |

These manifestations depend on the compiler, target bytecode, and JDK version. **Specified behavior** must be separated from **how `javac` implements it**.

## 3. Annotations: where is metadata stored and how long does it live?

An annotation is metadata attached to a declaration or, when allowed by `@Target`, to a type-use location. It can be read by the compiler, annotation processors, frameworks, class file analysis tools, or Reflection. Having an annotation **does not cause the JVM to automatically run an interceptor**. A framework only changes behavior when it actually looks for and processes that annotation.

### 3.1. `@Retention`: SOURCE, CLASS, and RUNTIME

| Retention | Present in `.class` under standard Java compilation? | Readable via Java Reflection at runtime? | Example purpose |
| --- | --- | --- | --- |
| `SOURCE` | No; discarded during compilation | No | Guiding compiler/IDE, source-level checks |
| `CLASS` | Yes | Not via standard Reflection | Bytecode analysis, build tools; this is the **default value** if `@Retention` is not declared |
| `RUNTIME` | Yes | Yes, if reading the right element and API | Framework or runtime tool looking up metadata |

Example:

```java
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;

@Retention(RetentionPolicy.RUNTIME)
@interface RuntimeTag {}

@Retention(RetentionPolicy.CLASS)
@interface ClassTag {}

@Retention(RetentionPolicy.SOURCE)
@interface SourceTag {}
```

When a class uses these annotations, the class file may contain the first two annotations; the `SOURCE` annotation is not retained in the target artifact. `ClassTag` does not appear in `Class.isAnnotationPresent(...)` via the standard Reflection API, even though a bytecode parser can see its attribute.

In a class file, the names `RuntimeVisibleAnnotations` and `RuntimeInvisibleAnnotations` describe **visibility via Reflection**, not that an "invisible" annotation is useless. Bytecode-reading tools like ASM can observe both sets. Corresponding attributes also exist for annotations on parameters or type-use, such as `RuntimeVisibleParameterAnnotations` and `RuntimeVisibleTypeAnnotations`.

### 3.2. `@Target` determines placement, not retention

`@Target(ElementType.METHOD)` allows the annotation on a method declaration. `@Target(ElementType.TYPE_USE)` allows the annotation at a type-use location, such as:

```java
// Structural example (not a standalone runnable file):
@Target(ElementType.TYPE_USE)
@Retention(RetentionPolicy.RUNTIME)
@interface NonNull {}

List<@NonNull String> names;
```

The annotation on `String` here is a **type-use annotation**, not identical to an annotation on the declaration of field `names`. A scanner that only looks for `RuntimeVisibleAnnotations` on the field may miss `RuntimeVisibleTypeAnnotations`. Similarly, annotations on parameters require reading the proper parameter table, and parameter names are not automatically available if the compiler does not emit the appropriate metadata.

Annotations such as `@Override` and `@SuppressWarnings` are typically useful at compile time, not as a mechanism for placing runtime probes. Conversely, a custom annotation with `RUNTIME` retention can be scanned by a framework during initialization.

### 3.3. Annotation processors vs. runtime instrumentation

An **annotation processor** operates at compile time, reads the source/element model, and can generate additional source/resource files. It is not the same as a Java agent intervening in bytecode when the JVM loads classes.

Distinction example:

```text
Source + annotation
      ├─ compiler/annotation processor → files generated at build time
      └─ compiler → .class + retained annotation metadata
                                              ↓
                                JVM / Reflection / Java agent
```

An annotation is just a data signal. Not every `RUNTIME` annotation is scanned by a framework, and not every `CLASS` annotation is meaningless to an agent. To decide on instrumentation by annotation, clearly identify whether the tool reads source, bytecode, or Reflection.

### 3.4. Be careful when moving or modifying annotations

A bytecode transformer must preserve relevant annotations unless it intentionally modifies them. That includes attributes at the class, method, field, parameter, and type-use levels. Specifically, `AnnotationDefault` stores default values on methods of an annotation type; `Signature`, `MethodParameters`, or debug attributes are different metadata, **not annotations**.

If an agent creates a wrapper method and copies annotations thoughtlessly, the result may cause a framework to see the annotation on multiple methods or on a different method than intended. Even retrieving annotations via `getDeclaredAnnotations()` vs. `getAnnotations()` differs due to class-level annotation inheritance; `@Inherited` does not mean every method annotation is automatically inherited by overrides.

## 4. Synthetic: compiler-generated, but not synonymous with "ignore"

`ACC_SYNTHETIC` is an access flag describing a component that **does not appear directly as a declaration in source**. In the class file format there is also a `Synthetic` attribute for compatibility with relevant cases/versions. With Java Reflection:

- `Class.isSynthetic()` indicates whether a class is synthetic.
- `Method.isSynthetic()` indicates whether a method is synthetic.
- `Field.isSynthetic()` indicates whether a field is synthetic.
- `Method.isBridge()` asks **a different thing**: whether the method has the bridge flag.

For example, a compiler may generate a separate method to hold a lambda body; that method usually carries `ACC_SYNTHETIC`. Yet that method can execute real business logic. If an agent unconditionally excludes all synthetic methods, it may miss processing written in lambdas.

Conversely, there are components that appear in `.class` even though the source has no corresponding declaration, which are **not guaranteed** to have the `synthetic` flag: default constructors, methods required by records/enums, instructions to implement `try-with-resources`, transformations inside methods, etc. `isSynthetic()` cannot be used as a complete classifier of "compiler-generated code".

### 4.1. Which signals are reliable?

Some naming patterns are commonly seen in `javac` output: `lambda$...`, `$VALUES`, `$SwitchMap...`, `access$...`. **Do not rely on these names as a stable contract.** They are implementation details that can differ across JDKs/compiler versions/source structures, and some no longer appear in newer versions. For instance, the JVM has supported *nestmates* since Java 11, so many accesses between classes in the same nest no longer require synthetic accessors the way older compilers used to generate them.

For an agent, it is necessary to combine access flags, method descriptors, owner/class loader, annotations, instructions, and call sites. A `synthetic` method may be an "internal detail to avoid exposing as API", while still being a useful measurement point when wanting to understand execution paths.

### 4.2. What counts as "not declared in source"?

- **Synthetic member:** marked appropriately by class-file flags/metadata; Reflection API can inspect it.
- **Compiler-generated instruction:** bytecode added by the compiler inside a method, **not necessarily existing as a new member**.
- **Generated source:** an annotation processor or generator outputs `.java`; when `javac` compiles it, members from that generated source **do not automatically have `ACC_SYNTHETIC`**.
- **Generated runtime class:** a proxy/lambda implementation created when the program runs; requires looking at class-definition mechanisms and separate runtime information.

The four cases above are easily lumped together as "generated code", but how to find and instrument them differs.

## 5. Bridge methods: why can one call pass through two methods?

### 5.1. Generic erasure changes the descriptor

Consider two classes:

```java
class Parent<T> {
    public T convert(T value) {
        return value;
    }
}

class Child extends Parent<String> {
    @Override
    public String convert(String value) {
        return value.trim();
    }
}
```

In Java source, `Child.convert(String)` overrides `Parent<String>.convert(String)`. However, generics **are erased in bytecode**: the method in `Parent<T>` has an equivalent descriptor `(Ljava/lang/Object;)Ljava/lang/Object;`. Meanwhile, the actual method declared by `Child` has the descriptor `(Ljava/lang/String;)Ljava/lang/String;`.

So that a polymorphic call through a `Parent<String>` reference still reaches `Child`, `javac` typically generates a **bridge method** in `Child`:

```java
// PSEUDOCODE to illustrate the bridge, not Java source allowed to be declared
// alongside convert(String) in this way:
public Object convert(Object value) {
    return convert((String) value);
}
```

In the class file, the bridge method has the `ACC_BRIDGE` flag, usually along with `ACC_SYNTHETIC`. It performs a cast and then forwards to the specific method. Therefore:

```text
Parent<String> p = new Child();
p.convert("  hi  ");
       │
       ▼
Child.convert(Object)     [bridge, erased descriptor]
       │ cast to String
       ▼
Child.convert(String)     [logic written by the programmer]
```

Entering a method twice does not mean there are two business operations. If you instrument both entries and record `business.operation.count++`, the same call may be counted twice. If you measure the duration of both and sum them as independent tasks, you may double-count nested intervals.

### 5.2. Bridges can also appear outside generic examples

Beyond generic erasure, a **covariant return type** can also require a bridge to preserve polymorphism at the JVM descriptor level. For example, a subclass returns `String` while the superclass has a method returning `Object`. The Java specification defines overriding semantics; the compiler is responsible for generating bytecode that preserves them.

Not all bridges follow the same naming rule; you must check `ACC_BRIDGE`, bytecode signatures, and actual call paths. Also do not confuse a method's `ACC_BRIDGE` in a class file with the `LambdaMetafactory.FLAG_BRIDGES` constant used in a lambda linkage case: they belong to **two different interfaces/levels**.

### 5.3. When raw types or Reflection are involved

Because a bridge accepts `Object`, a call through raw `Parent` can reach the bridge and throw a `ClassCastException` if an invalid type is passed. That is part of runtime type safety, not a bug introduced by instrumentation. Java Reflection with `getDeclaredMethods()` can also return both the bridge method and the actual method; when iterating automatically via Reflection, you must filter or deduplicate so as not to repeat the same logical operation.

## 6. Lambdas: `invokedynamic`, bootstrap, and the executed body

A lambda is a Java expression that creates an object implementing a **functional interface**. Source:

```java
Function<String, String> formatter = s -> s.trim().toUpperCase();
String result = formatter.apply("  java  ");
```

With modern `javac`, bytecode at the point where the lambda expression is evaluated typically contains **`invokedynamic`**, paired with a bootstrap method provided by `LambdaMetafactory`. The API specification describes three meaningful phases:

1. **Linkage:** The first time the call site is linked, the `LambdaMetafactory` bootstrap builds an appropriate `CallSite`; the strategy for creating/reusing classes is a runtime detail.
2. **Capture:** When evaluating the lambda expression, the call site's target creates or obtains a functional interface object, possibly holding captured values (if any). Do not rely on the identity of these objects as a contract.
3. **Invocation:** When calling `formatter.apply(...)`, the implementation described by a `MethodHandle` executes with the received arguments and the captured values.

Conceptual diagram:

```text
Source: s -> s.trim().toUpperCase()
          │ javac
          ▼
caller bytecode: invokedynamic   → bootstrap: LambdaMetafactory
          │                                     │
          │                             links CallSite
          ▼                                     │
  Function instance  ◀──────────────────────────┘
          │
       apply("  java  ")
          │
          ▼
  implementation method/handle
          │
          ▼
       "JAVA"
```

`javac` typically places the lambda body into a method named like `lambda$...` in the enclosing class; this method is usually synthetic. However, a **method reference** such as `String::trim` can link directly to an existing method and need not generate a corresponding `lambda$...`. A lambda can also capture `effectively final` local variables or `this`; the number of parameters in the method handle may differ from the apparent functional-interface method because of captured arguments.

### 6.1. Where is the lambda object's class?

The lambda implementation can be generated dynamically and have no separate `.class` file in a JAR. Modern JDKs can use **hidden classes** for implementations. Do not assume you can obtain all lambda implementations by scanning the classpath or relying on class names like `$$Lambda`. Some basic runtime/agent APIs have limitations regarding hidden classes, retransformation, or visibility of runtime-generated classes.

At the same time, `invokedynamic` is **not exclusive** to lambdas. In modern Java, string concatenation with `+` also commonly uses a call site whose bootstrap belongs to `StringConcatFactory`. To identify call sites meant for lambdas, inspect `BootstrapMethods`, the bootstrap method handle, and how it links to the functional interface, rather than just searching for the `invokedynamic` opcode.

### 6.2. Where should instrumentation place probes?

There are three different kinds of locations:

| Location | What is captured? | Points requiring caution |
| --- | --- | --- |
| Where the lambda is **created** (`invokedynamic` call site) | When the expression is evaluated / object is captured | Does not mean the body has run; a lambda may be created without being called |
| Implementation method or `lambda$...` | When the body executes | May be compiler-dependent; must handle synthetic, method handles, class loaders |
| Functional interface method boundary (e.g., `Function.apply`) | When the object is invoked | Select only the right implementations; avoid instrumenting every `apply` too broadly or duplicating measurements |

With asynchronous lambdas, the time a lambda is created, the time the task is submitted, and the time the task actually runs can be far apart; a span may need context propagation and appropriate completion rules. Measuring only lambda expression creation does not reflect callback execution time.

## 7. Java 17+ experiment: observing annotations, bridge, synthetic, and lambda

Create **a single file** named `ClassFileArtifactsDemo.java`:

```java
import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;
import java.lang.reflect.Method;
import java.util.Arrays;
import java.util.function.Function;

public class ClassFileArtifactsDemo {

    @Retention(RetentionPolicy.RUNTIME)
    @Target(ElementType.TYPE)
    @interface RuntimeTag {}

    @Retention(RetentionPolicy.CLASS)
    @Target(ElementType.TYPE)
    @interface ClassTag {}

    @Retention(RetentionPolicy.SOURCE)
    @Target(ElementType.TYPE)
    @interface SourceTag {}

    static class Parent<T> {
        public T convert(T input) {
            return input;
        }
    }

    @RuntimeTag
    @ClassTag
    @SourceTag
    static final class Child extends Parent<String> {
        @Override
        public String convert(String input) {
            return input.trim();
        }
    }

    public static void main(String[] args) {
        Parent<String> throughParent = new Child();
        System.out.println("bridge call: " + throughParent.convert("  hi  "));

        Method[] methods = Child.class.getDeclaredMethods();
        long bridgeCount = Arrays.stream(methods)
                .filter(Method::isBridge)
                .count();
        long syntheticBridgeCount = Arrays.stream(methods)
                .filter(m -> m.isBridge() && m.isSynthetic())
                .count();
        System.out.println("bridge methods: " + bridgeCount);
        System.out.println("bridge synthetic: " + syntheticBridgeCount);

        System.out.println("runtime annotation: "
                + Child.class.isAnnotationPresent(RuntimeTag.class));
        System.out.println("class annotation at runtime: "
                + Child.class.isAnnotationPresent(ClassTag.class));
        System.out.println("source annotation at runtime: "
                + Child.class.isAnnotationPresent(SourceTag.class));

        String prefix = "value=";
        Function<String, String> formatter =
                value -> prefix + throughParent.convert(value);
        System.out.println("lambda: " + formatter.apply(" ok "));
    }
}
```

Run with JDK 17 or later, using the JDK's `javac` (not an alternative compiler):

```bash
javac -encoding UTF-8 ClassFileArtifactsDemo.java
java ClassFileArtifactsDemo
```

**Expected stdout with JDK 17+ `javac`:**

```text
bridge call: hi
bridge methods: 1
bridge synthetic: 1
runtime annotation: true
class annotation at runtime: false
source annotation at runtime: false
lambda: value=ok
```

Explanation of results:

- `throughParent.convert(...)` uses the static type `Parent<String>` but dispatches to `Child`. `javac` provides the `convert(Object)` bridge to preserve this dispatch path.
- Reflection sees one bridge method on `Child`, and `javac` marks it synthetic.
- `RuntimeTag` is visible to Reflection; `ClassTag` still exists in the class file but is not returned via standard Reflection; `SourceTag` is discarded during compilation.
- The lambda captures both `prefix` and `throughParent`. When `apply` is called, the body executes `convert`, producing `"value=ok"`. The output line does not reveal in what class form the lambda implementation was generated.

### 7.1. Reading the class file with `javap`

Use the following commands (names with `$` are placed in single quotes for Bash/PowerShell):

```bash
javap -c -p ClassFileArtifactsDemo
javap -v -p ClassFileArtifactsDemo
javap -v -p 'ClassFileArtifactsDemo$Child'
```

In Windows `cmd.exe`, use double quotes around class names containing `$` instead of single quotes. `javap -p` displays private members; `-c` prints instructions; `-v` also prints flags, descriptors, attributes, and bootstrap entries.

Things **to look for**, independent of specific constant pool indices:

1. In `Child`, there are two descriptors related to `convert`: one taking/returning `String`, one taking/returning `Object`. The latter has `ACC_BRIDGE`, `ACC_SYNTHETIC`; its body forwards to the `String`-typed method.
2. In `Child`'s metadata, `RuntimeTag` is in `RuntimeVisibleAnnotations` and `ClassTag` is in `RuntimeInvisibleAnnotations`. There is no annotation instance of `SourceTag`.
3. In the main class, find the `invokedynamic` associated with `Function`. In `BootstrapMethods`, find the entry referencing `java/lang/invoke/LambdaMetafactory` and the method handle pointing to the implemented body.
4. With JDK 17+ `javac`, you can see a private synthetic method named something like `lambda$main$0` in the main class. The structure/naming is not an API for tools to depend on long-term.
5. Another `invokedynamic` may appear due to string concatenation; a `StringConcatFactory` bootstrap is **not** a lambda.

The goal of `javap` is **confirming artifacts**, not inferring from source or from method names. If another compiler/JDK produces a different shape, inspect the actual output and explain it by descriptors, flags, and bootstrap owners.

### 7.2. Two different checks

**Checking via Reflection** answers: *At runtime, which metadata/members does the public API see?*

```java
// Illustrative snippet must be placed in a program that has Child:
for (Method method : Child.class.getDeclaredMethods()) {
    System.out.println(method.getName()
            + " bridge=" + method.isBridge()
            + " synthetic=" + method.isSynthetic());
}
```

Output **may vary in order** because `getDeclaredMethods()` does not guarantee element ordering. Therefore, the complete example above counts rather than printing everything to keep stdout stable.

**Checking via `javap` or a bytecode parser** answers: *Which instructions, flags, descriptors, and attributes are contained in the `.class` file?* The two checks do not replace each other: Reflection does not show instructions and does not return `CLASS`-retention annotations through the standard path.

## 8. Other forms of compiler-generated code to distinguish

The lesson is not limited to synthetic methods. The Java compiler can also create or modify:

| Case | What the compiler/JVM needs to do | Right perspective |
| --- | --- | --- |
| **Default constructor** | Add a constructor if the class qualifies under Java rules | A constructor can have bytecode without being declared in source; not automatically synonymous with `synthetic` |
| **Enum** | Provide members and initialization according to the enum model | Some auxiliary methods/fields may be compiler-generated; do not assume every member has the synthetic flag |
| **Record** | Generate accessors, constructors/canonical methods per record rules when not explicitly declared | Public members required by the language cannot be dismissed simply by a "compiler generated" heuristic |
| **Try-with-resources** | Ensure resource closing, preserve primary/suppressed exceptions | Can generate multiple exception branches within **the same method**; does not necessarily have a separate helper method |
| **Enhanced for** | Translate loop syntax into an iterator or index-based loop depending on type | More bytecode instructions than source statements; source line mapping may not be direct |
| **Nested/inner classes** | Store nest/outer info, capture enclosing instance or needed variables | Auxiliary fields and constructor parameters depend on compiler/JDK; do not rely on names like `this$0` as API |
| **String concatenation** | May use `invokedynamic` with `StringConcatFactory` | Not a lambda even though the opcode is the same |
| **Switch, pattern matching, assertions** | Generate branches, helpers, or control structures to preserve semantics | Evaluate by actual bytecode, do not infer from source syntax |

In addition, metadata such as `LineNumberTable`, `LocalVariableTable`, `MethodParameters`, `Signature`, `NestHost`/`NestMembers`, and `Record` can help map back to source, but their nature and presence vary. `javac -g` adds debug information, `javac -parameters` adds parameter names for Reflection; do not confuse these two options with annotation retention.

## 9. Concrete implications for instrumentation tools

### 9.1. Define the unit of measurement before choosing filters

One **logical business operation** can pass through multiple bytecode methods:

```text
call site
   → generic bridge         (type conversion/forwarding)
       → user method        (business logic)
           → lambda body    (when invoked)
```

If you need a metric of "once per business call", place the probe at the chosen boundary and avoid recording the same event at every layer. If you need detailed bytecode traces, you can observe both bridges and lambdas, but you must clearly represent them as nested frames/layers, not independent operations.

A starting filter set often includes: excluding bridges from certain metric types, selecting only synthetic methods with specific roles, avoiding agent-internal packages, maintaining class-loader allowlists/blacklists. These are **goal-dependent policies**, not a law of "drop all bridge/synthetic".

### 9.2. Use real flags from the class file, do not guess by name

With a class-file reading library, a tool can check the corresponding bits such as `ACC_BRIDGE` and `ACC_SYNTHETIC`; with Reflection there are `Method.isBridge()` and `Method.isSynthetic()`. When transforming bytecode, use the actual (erased) descriptor and generic `Signature` info in their proper roles. Matching only by the name `convert` can select both the bridge and the override; matching only `(String)->String` can miss calls at the erased method boundary.

Similarly, `lambda$` is a `javac` hint, not a standard for identifying all lambdas. The bootstrap method owner and method handles at the call site provide better information for bytecode analysis, though the runtime may use multiple implementation strategies.

### 9.3. Annotations: read the right metadata layer

An agent operating on `ClassFileTransformer` can read both `CLASS` and `RUNTIME` retention annotations from raw bytecode. An interceptor relying only on Reflection typically sees `RUNTIME` annotations. For type-use annotations, you must look up the proper `...TypeAnnotations` attribute instead of fetching declaration annotations.

Do not assume annotations on a bridge are identical to those on the overriding method. Some compilers may copy annotations to the bridge or generate metadata in their own way; inspect the actual artifact before building rules. If the agent adds annotations itself, it must consider where and how frameworks might read them.

### 9.4. Lambdas and asynchronous work

Instrumenting `invokedynamic` where a callback is created differs from instrumenting the callback body when it runs. For example, a callback is created during HTTP request A but runs on an executor later; if you only capture context at creation without proper propagation/execution hooks, spans may be attached to the wrong parent. Choose the submit/start/complete boundary according to the semantics to measure and the observability library in use.

If the runtime generates hidden classes, a transformer should not assume it can freely retransform every implementation. When wanting to observe all callbacks, another option is instrumenting executor boundaries, framework callbacks, or existing methods with stable contracts.

### 9.5. Valid bytecode and preserving semantics

Inserting code inside a method must preserve the order and results of returns/throws, exception tables, verifier stack map frames, local variables, class-file version, and other required information. Do not accidentally turn a bridge into a public method exposed as a new API, strip framework-required annotations, or lose generic signatures.

For production bytecode transformers, use libraries like ASM or Byte Buddy to manage bytecode structure and test across target JVM versions. After transformation, verify that classes load, code runs correctly, errors are not swallowed, stack traces/line numbers remain useful, and probe overhead is acceptable.

## 10. Investigation workflow for a "strange" method during instrumentation

**Step 1 — Look at runtime/source context.** Record the JDK, compiler, target release, class name, class loader, method descriptor, and call path. Same name with different descriptors are different methods.

**Step 2 — Inspect the class file.** Use `javap -v -p` to view flags (`ACC_SYNTHETIC`, `ACC_BRIDGE`), descriptors, `Signature`, annotation attributes, `BootstrapMethods`. Use `javap -c -p` to view instructions and which method actually calls which.

**Step 3 — Compare with Reflection.** `Method.isBridge()`/`isSynthetic()` show flags visible via Reflection; `isAnnotationPresent(...)` only checks runtime metadata via the appropriate API. Do not infer that a `CLASS`-retention annotation has vanished just because Reflection returns false.

**Step 4 — Determine the measurement point.** To count logical requests, measure a stable boundary. To diagnose generics dispatch, observe the bridge. To measure callback duration, measure invocation rather than only lambda creation.

**Step 5 — Verify before/after.** Run the same inputs with and without the agent; compare outputs, exceptions, call counts, span/metric counts, and timings. Also test error paths, overloads, generic raw calls, concurrent callbacks, and different class loadings if they fall within scope.

## 11. Common misconceptions

1. **"Every annotation can be used via Reflection."** False. `SOURCE` is not kept in the class file; `CLASS` is not returned by standard Reflection; only `RUNTIME` has retention suitable for runtime lookup.
2. **"Annotations directly inject behavior into methods."** False. Metadata does not execute on its own. A processor, framework, transformer, or runtime component must actively handle it.
3. **"Synthetic means dead code."** False. A synthetic method can be a lambda body or a component needed for the program to run correctly.
4. **"A bridge is just a redundant overload."** False. It preserves overriding and dispatch after erasure or when changing to a compatible return type.
5. **"Counting method entries equals total business operations."** Not necessarily. Bridges and wrappers/proxies can cause one logical call to pass through multiple frames.
6. **"Every lambda generates a class file pre-packaged in the JAR."** False. Part of the implementation is generated/linked at runtime; hidden classes may appear.
7. **"If there is `invokedynamic`, it is definitely a lambda."** False. Many features use `invokedynamic`; you must check the bootstrap.
8. **"The name `lambda$main$0` always exists and is stable."** False. This is a compiler detail, not a standard contract.
9. **"Because there is a generic `Signature`, the JVM dispatches by generic type."** False. The JVM links methods based on the erased descriptor; `Signature` holds generic info for relevant tools/APIs.
10. **"Filtering out all bridge and synthetic methods is always optimal."** False. That may suit a business-level metric, but causes missing data when analyzing bridges or lambdas themselves.

## 12. Self-check

**Q1:** `@Retention(CLASS)` is visible to `javap` but `isAnnotationPresent` returns `false`. Is this a contradiction?  
**A:** No. Metadata in the class file does not mean runtime Reflection must return it.

**Q2:** Why might `Parent<String>.convert` and `Child.convert(String)` also need `Child.convert(Object)`?  
**A:** Generic erasure gives `Parent.convert` a descriptor taking/returning `Object`; the bridge preserves dispatch to the override taking/returning `String`.

**Q3:** Should all `synthetic` methods be excluded from traces?  
**A:** It depends on the goal. Avoiding double-counting bridges for business metrics can make sense, but synthetic lambda bodies may still contain logic needing diagnosis.

**Q4:** A lambda is created at 10:00 but the callback runs at 10:05. What does a probe at `invokedynamic` measure?  
**A:** It observes linkage/capture activity when the expression is evaluated; it does not by default measure the body's execution time at 10:05.

**Q5:** Why not rely entirely on `lambda$` or `$$Lambda` when designing an agent?  
**A:** Names and implementation generation strategies are unstable across compilers/JDKs; a method reference can even point to an existing method.
