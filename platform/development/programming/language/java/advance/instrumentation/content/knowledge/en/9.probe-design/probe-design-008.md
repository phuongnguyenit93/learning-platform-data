# Abstract, Native, Synchronized Methods and Cases Without Code

## 1. Why must probe design distinguish method kinds?

In Java Instrumentation, a Java agent often inserts hooks at the **entry** and **exit** of a method (*method-entry/method-exit advice*) to measure latency, trace, coverage, or metrics. This approach only works when the method has **Java bytecode** in the **`Code`** attribute of the class file.

Three cases are very easy to confuse:

- **`abstract`**: only declares a contract; **has no `Code`** to insert instructions into. Must measure the real implementation or another boundary.
- **`native`**: the implementation does not reside in Java bytecode; **has no `Code`**. Can be measured at a Java wrapper/call site or by using a specialized native/JVMTI mechanism.
- **`synchronized`**: is a JVM monitor management flag; if the method has a Java body, it **still has `Code`**. However, a **`synchronized native`** method has both the synchronized and native flags, so it still **has no `Code`**.

Therefore, you cannot rely on the name, source declaration, or a single flag alone to decide whether to insert advice. Check **the existence of `Code` in the actual method_info**, then apply the appropriate probe policy.

Lesson objectives:

1. Identify valid methods **without Code** according to the JVM Specification.
2. Understand the mechanism of synchronized methods and synchronized blocks at the JVM level.
3. Choose the right probe points for abstract, native, synchronized, constructors, class initializers, and compiler-generated methods.
4. Use `javap` on Java 17 and the Java Class-File API on JDK 24+ to verify in practice.

## 2. `method_info`, access flags, and `Code` rules

In a class file, a method is represented by:

```text
method_info {
    u2 access_flags;
    u2 name_index;
    u2 descriptor_index;
    u2 attributes_count;
    attribute_info attributes[attributes_count];
}
```

`Code` is an attribute of `method_info`. It contains JVM instructions along with `max_stack`, `max_locals`, the exception table, and sub-attributes such as `StackMapTable`.

According to **JVMS `4.7.3**:

- If a method is **`ACC_ABSTRACT` or `ACC_NATIVE`**, that method **must not have a `Code` attribute**.
- For remaining methods, a valid `method_info` **must have exactly one `Code`**.

Common flags:

| Flag in class file | Value | Meaning | Has `Code`? |
| --- | --- | --- | --- |
| `ACC_ABSTRACT` | `0x0400` | Does not provide an implementation | **No** |
| `ACC_NATIVE` | `0x0100` | Implementation is outside Java bytecode | **No** |
| `ACC_SYNCHRONIZED` | `0x0020` | Invocation uses a JVM monitor | **Yes if not abstract/native** |
| `ACC_STATIC` | `0x0008` | Method belongs to the class | Yes if not abstract/native |
| `ACC_FINAL` | `0x0010` | Cannot be overridden per JVM rules | Yes if not abstract/native |
| `ACC_BRIDGE` | `0x0040` | Bridge generated by the compiler | Usually yes; check in practice |
| `ACC_SYNTHETIC` | `0x1000` | No direct source method | Depends on method; does not decide alone |
| `ACC_VARARGS` | `0x0080` | Has varargs parameter | Yes if not abstract/native |

Flag combination rules are also important:

- An `abstract` method **must not** simultaneously be `private`, `static`, `final`, `synchronized`, or `native`.
- A **`native synchronized` method is valid** in a class. `ACC_SYNCHRONIZED` does not make `Code` appear if `ACC_NATIVE` is already set.
- Interface methods must not carry `ACC_NATIVE` or `ACC_SYNCHRONIZED`; an interface method without a body is abstract, whereas a `default` method or a private method with a body has Code.

**A method with an empty body still has `Code`**: for example, `void f() {}` usually has a `return` instruction. Do not confuse "doing nothing" with "having no `Code`".

## 3. `abstract`: declaration is not implementation

Consider the example:

```java
abstract class Job {
    public abstract String execute();
}

final class Worker extends Job {
    @Override
    public String execute() {
        return "done";
    }
}
```

In `Job.class`, the `execute` method is marked `ACC_ABSTRACT` and has no `Code`. In `Worker.class`, the overriding `execute` method has Java code.

**Implications when instrumenting:**

- Cannot insert instructions into an **abstract declaration**; there is no instruction stream, label, return instruction, or exception handler.
- If you want to measure **execution logic**, choose the **concrete implementation** that the call actually dispatches to.
- If you want to measure **every call to an API contract**, you can instrument the **call site**, a Java proxy, a decorator, or a controlled gateway. However, a call-site transformer only covers callers that have been transformed.
- For interfaces, check each method individually. **`default` methods with a body** and **interface private methods with a body** have `Code`; do not skip an entire interface just because it has abstract declarations.

### Inherited methods and non-overridden methods

A subclass can inherit a concrete method without creating an additional `method_info` for that method. If you only read `ClassModel.methods()` of the subclass, you **will not see the inherited method**, yet calls to the method still execute the body defined in the superclass.

Therefore, the scope must be clearly defined:

- **Declared methods** of a class file;
- **Inherited methods** whose implementation is in an ancestor;
- **Actual override** during JVM dispatch;
- **Proxy/bridge** that may add an intermediate layer.

Confusing these scopes can lead to missed measurements or duplicate metric recording.

## 4. `native`: method has a signature but no Java bytecode

Example:

```java
class NativeService {
    public native int readValue();

    public synchronized native int readLocked();
}
```

Both methods **have no `Code`** because the execution logic is not written as JVM instructions in this method. `readLocked` carries both `ACC_NATIVE` and `ACC_SYNCHRONIZED`, but the JVM synchronization **does not generate a Code attribute**.

**Note when testing:** if the corresponding native implementation has not been loaded or registered yet, do not call these two methods; calling them may throw `UnsatisfiedLinkError`. A class containing native declarations does not mean the JVM cannot load the class.

### Where to place hooks when you need to measure native?

| Goal | Viable probe point | Limitations to state clearly |
| --- | --- | --- |
| Latency of a Java API calling native | Java **wrapper** or service boundary before/after the native call | Only covers call paths going through the wrapper |
| Call count of a native API from Java bytecode | `invoke...` **call sites** | Does not guarantee coverage of reflection/JNI/uninstrumented call sites |
| Processing time inside the native library | Native profiler or appropriate **JVMTI/JNI** | Tools, permissions, and capabilities depend on the VM/OS |
| Changing the native binding mechanism | Specialized APIs such as native method prefix (if supported) | Not ordinary `Code` insertion; requires capability design and verification |

**Do not modify `ACC_NATIVE` yourself to add a Java body during retransformation** and think of it as a valid method-entry advice. Redefinition/retransformation of loaded classes is subject to constraints on modifiers and structure; converting native to non-native may not be accepted by the JVM. Choose another measurement boundary instead of corrupting the class file.

## 5. `synchronized`: has `Code`, but locking is usually outside the instruction stream

Example:

```java
public synchronized int increase() {
    return ++counter;
}
```

This method has **`ACC_SYNCHRONIZED`** and **`Code`**. The JVM uses the method flag to automatically acquire/release the monitor on invocation/return, **without needing** `monitorenter` and `monitorexit` instructions in the body of the synchronized method.

- **Instance synchronized method:** monitor of the receiver object (`this`).
- **Static synchronized method:** monitor of the `Class` object representing the class.
- The JVM releases the monitor when the method completes normally **or** exits due to an exception.
- **Synchronized native method:** still has monitor semantics, but **has no Code**, because it is native.

### Difference from synchronized block

```java
public int getValue() {
    synchronized (lock) {
        return value;
    }
}
```

Here the method does not necessarily have the `ACC_SYNCHRONIZED` flag. `javac` generates `monitorenter`/`monitorexit` directly **inside `Code`**, along with the exception handling needed to balance the monitor on abnormal exit paths.

| Source code | `ACC_SYNCHRONIZED` | `Code` | Monitor management |
| --- | --- | --- | --- |
| `synchronized void work() { ... }` | Yes | Yes | Implicit JVM invocation/return |
| `static synchronized void work() { ... }` | Yes | Yes | JVM, locks on `Class` |
| `void work() { synchronized (lock) { ... } }` | Usually no | Yes | `monitorenter`/`monitorexit` in code |
| `synchronized native void work();` | Yes | No | JVM/native invocation path |
| `abstract void work();` | No | No | No implementation yet |

### Be careful with measured time

With a synchronized method, advice inserted at the **start of the body** only runs **after the JVM has acquired the monitor**:

```text
Caller
  |
  |  waiting for monitor on contention
  v
JVM acquire monitor
  |
  v
[entry advice]  -> start timer
  |
  |  business logic + instrumentation under monitor
  v
[exit advice]   -> stop timer
  |
JVM release monitor
  |
  v
Caller
```

If the goal is to measure **lock wait time**, method-entry advice **cannot measure the wait before acquire**. Consider caller-side timing or JVM monitor events/profiling (for example JFR) with well-defined measurement semantics.

Advice inside a synchronized method increases **monitor hold time**; logging, blocking I/O, other locks, or reentrant code can cause contention, overhead, and deadlock. Prefer a fast path, limit side effects, and separate data collection from export.

## 6. Normal return, exceptions, and preserving semantics

A Java method with Code can have multiple `return`s or throw exceptions. If you only insert a hook before the return instruction, you will miss exceptional exits. If you insert a `try/finally` or handler, you must preserve control semantics, exception handlers, stack/locals, and frames.

Illustrated with Java source code (not an automatic bytecode rewrite algorithm):

```java
public synchronized String process() {
    long started = System.nanoTime();
    try {
        return businessLogic();
    } finally {
        long duration = System.nanoTime() - started;
        metrics.record(duration);
    }
}
```

Because the method is synchronized, `metrics.record` also runs **while the monitor is still held**. If the recorder fails, it can mask the original exception; production design must have a fault-tolerance policy for measurement.

When instrumenting, you need to check:

- All normal/abrupt exit paths are covered according to the contract.
- Return values, thrown exceptions, and the exception table are preserved.
- Do not break `monitorenter`/`monitorexit` of synchronized blocks.
- Do not inadvertently change/remove `ACC_SYNCHRONIZED` of the method.
- Regenerate or properly maintain stack map frames according to the class-file version/JVM.
- Do not make modifier/schema changes that retransform/redefine does not support.

If a constructor `<init>` or class initializer `<clinit>` is instrumented, it is even more critical to preserve initialization order and avoid accessing `this` before the constructor chain/super initialization is valid.

## 7. "No Code" cases and easily confused exceptions

| Case | `Code` status | What to remember |
| --- | --- | --- |
| Abstract method in a class | **No** | Body resides in another implementation |
| Interface abstract method | **No** | Implementation may be in an implementing class |
| Native method | **No** | Implementation outside Java bytecode |
| Synchronized native | **No** | Synchronized flag does not create Code |
| Concrete synchronized | **Yes** | Implicit JVM lock, Code still exists |
| Method containing a synchronized block | **Yes** | Monitor instructions are inside Code |
| Interface `default` method | **Yes** | Has a Java body |
| Interface private/static method with body | **Yes** | Not abstract by default |
| Constructor `<init>` if present | **Yes** | Special method sensitive to the verifier |
| Class initializer `<clinit>` if present | **Yes** | Not every class has `<clinit>` |
| Class without `<clinit>` | **No corresponding method_info** | Different from having method_info but missing Code |
| Bridge/synthetic concrete method | Usually **yes** | May only forward to another method |
| Empty body `void f() {}` | **Yes** | Usually consists of a `return` instruction |

Do not confuse **"the class does not declare that method"** with **"the method exists but has no Code"**. Do not treat a class file missing `Code` on an ordinary concrete, non-native method as a valid case: that is a sign of a class file that does not comply with the JVMS.

## 8. Java 17 practice: observing bytecode and flags with `javap`

Create the file **`MethodKinds.java`**:

```java
public abstract class MethodKinds {
    private static int counter = 7;

    public abstract String abstractWork();

    // Two native methods are declared but not called.
    public native int nativeWork();
    public synchronized native int nativeSync();

    public synchronized String synchronizedWork() {
        return "synchronized";
    }

    public String blockWork() {
        synchronized (this) {
            return "block";
        }
    }

    public String plainWork() {
        return "plain";
    }

    public static synchronized int staticSync() {
        return counter;
    }

    public static void main(String[] args) {
        MethodKinds target = new Concrete();

        System.out.println("[main] abstract="
                + target.abstractWork());
        System.out.println("[main] synchronized="
                + target.synchronizedWork());
        System.out.println("[main] block="
                + target.blockWork());
        System.out.println("[main] plain="
                + target.plainWork());
        System.out.println("[main] static="
                + staticSync());
    }

    static final class Concrete extends MethodKinds {
        @Override
        public String abstractWork() {
            return "implemented";
        }
    }
}

interface Contract {
    String required();

    default String defaultWork() {
        return "default";
    }
}
```

Compile and run using JDK 17 or later:

```bash
javac --release 17 MethodKinds.java
java MethodKinds
```

**Exact stdout of `java MethodKinds`:**

```text
[main] abstract=implemented
[main] synchronized=synchronized
[main] block=block
[main] plain=plain
[main] static=7
```

The `native` declarations do not cause an error when merely loading the class; the demo does not call them. The JVM dispatches `abstractWork` to `Concrete.abstractWork`, which has a Java body.

### Using `javap`

```bash
javap -v -p MethodKinds
javap -c -p MethodKinds
javap -v -p Contract
javap -v -p 'MethodKinds$Concrete'
```

Commands with `-v` display flags and the `Code:` header; `-c` displays instructions. The last line uses single quotes to preserve the `$` character in the nested class name on POSIX shell/PowerShell.

Indicators to look for, not the entire fixed output (constant-pool indexes/offsets may differ):

- `abstractWork` in `MethodKinds`: `ACC_ABSTRACT`, **no `Code:`**.
- `nativeWork`: `ACC_NATIVE`, **no `Code:`**.
- `nativeSync`: both `ACC_NATIVE` and `ACC_SYNCHRONIZED`, **no `Code:`**.
- `synchronizedWork`: `ACC_SYNCHRONIZED`, **has `Code:`**.
- `staticSync`: `ACC_STATIC` and `ACC_SYNCHRONIZED`, **has `Code:`**.
- `blockWork`: does not carry the synchronized flag, but `javap -c` displays `monitorenter` and `monitorexit`.
- `Contract.required`: abstract, no Code. `Contract.defaultWork`: concrete/default, has Code.
- `MethodKinds$Concrete.abstractWork`: has Code; it is the implementation of the abstract contract.

Observe the `<init>` constructor and `<clinit>` class initializer in the output if you want to distinguish a method with Code from a nonexistent method; `counter = 7` is not a `static final` constant, so the sample class has static field initialization code.

## 9. Class-File API practice on JDK 24+: `MethodModel.code()`

**`java.lang.classfile` is standardized starting in JDK 24**. If you only have JDK 17, this API cannot be used: use `javap` or an appropriate ASM/Byte Buddy library instead.

Create the file **`CodeAudit.java`** in the directory containing `MethodKinds.class` and `Contract.class`:

```java
import java.io.IOException;
import java.lang.classfile.ClassFile;
import java.lang.classfile.ClassModel;
import java.lang.classfile.MethodModel;
import java.lang.reflect.AccessFlag;
import java.nio.file.Path;
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

public final class CodeAudit {
    private CodeAudit() {
    }

    private static void inspect(Path path) throws IOException {
        ClassModel model = ClassFile.of().parse(path);
        List<String> rows = new ArrayList<>();

        for (MethodModel method : model.methods()) {
            String name = method.methodName().stringValue();

            // Focus on the methods being compared.
            if (name.equals("<init>")
                    || name.equals("<clinit>")
                    || name.equals("main")) {
                continue;
            }

            boolean isAbstract =
                    method.flags().has(AccessFlag.ABSTRACT);
            boolean isNative =
                    method.flags().has(AccessFlag.NATIVE);
            boolean isSynchronized =
                    method.flags().has(AccessFlag.SYNCHRONIZED);
            boolean hasCode = method.code().isPresent();

            rows.add(name
                    + " abstract=" + isAbstract
                    + " native=" + isNative
                    + " synchronized=" + isSynchronized
                    + " code=" + hasCode);
        }

        Collections.sort(rows);
        System.out.println("[" + path.getFileName() + "]");
        rows.forEach(System.out::println);
    }

    public static void main(String[] args) throws IOException {
        for (String arg : args) {
            inspect(Path.of(arg));
        }
    }
}
```

Commands using **JDK 24+**:

```bash
javac --release 24 CodeAudit.java
java CodeAudit MethodKinds.class Contract.class
```

**Expected stdout:**

```text
[MethodKinds.class]
abstractWork abstract=true native=false synchronized=false code=false
blockWork abstract=false native=false synchronized=false code=true
nativeSync abstract=false native=true synchronized=true code=false
nativeWork abstract=false native=true synchronized=false code=false
plainWork abstract=false native=false synchronized=false code=true
staticSync abstract=false native=false synchronized=true code=true
synchronizedWork abstract=false native=false synchronized=true code=true
[Contract.class]
defaultWork abstract=false native=false synchronized=false code=true
required abstract=true native=false synchronized=false code=false
```

`method.code()` returns `Optional<CodeModel>`; `isPresent()` checks the **Code attribute** directly, while `method.flags().has(AccessFlag...)` provides the metadata. This is clearer than inferring from modifiers or method names.

**Example limitation:** the program reads class files on disk, does not rewrite bytecode, and does not load `MethodKinds` via reflection. In a real agent, you must use **the exact `classfileBuffer`** received by the callback rather than assuming the file on disk matches the class version the JVM is defining.

## 10. Writing a method-body instrumentation filter

In JDK 24+, a helper can determine whether a method has a body to consider for advice:

```java
static boolean hasInstrumentableBody(MethodModel method) {
    return method.code().isPresent()
            && !method.flags().has(AccessFlag.ABSTRACT)
            && !method.flags().has(AccessFlag.NATIVE);
}
```

**This snippet is an illustrative helper, not a standalone Java file**; it uses the `MethodModel` and `AccessFlag` imports like the `CodeAudit` program. `code().isPresent()` already expresses the main condition; the two flag checks help express intent and detect abnormal metadata.

With ASM on Java 17, the equivalent preliminary logic (the snippet uses **ASM Opcodes** constants, not standalone Java SE):

```java
boolean hasJavaBody =
        (access & (ACC_ABSTRACT | ACC_NATIVE)) == 0;
```

In both approaches, **eligible for method-body instrumentation** is only the first step. Next, you need a policy for:

- `<init>`: choose an entry point after the valid constructor initialization phase; do not access `this` too early.
- `<clinit>`: code runs during class initialization, risking recursion and class-initialization failure.
- Bridge/synthetic methods: if both the bridge and implementation are measured, one call can emit multiple events.
- Synchronized methods: advice is executed when the monitor is already acquired; very sensitive to overhead and deadlock.
- Methods generated by proxies or frameworks: the class loader and definition time may differ from source code.
- Methods belonging to Java core, agent helpers, or recorders: avoid instrumenting the agent's own logging/tracing mechanism and causing recursion.

## 11. Probe selection workflow in a transformer

```text
MethodModel / method_info
         |
         v
Does Code exist?
    |
    +-- NO
    |     |
    |     +-- ACC_ABSTRACT -> find concrete override,
    |     |                    proxy/API boundary or call site
    |     |
    |     +-- ACC_NATIVE   -> measure Java wrapper/call site,
    |     |                    JVMTI/native profiler
    |     |
    |     +-- otherwise    -> invalid class file?
    |
    +-- YES
          |
          +-- <init>/<clinit>/bridge/synthetic?
          |          -> apply separate policy
          |
          +-- ACC_SYNCHRONIZED?
          |          -> minimize overhead because monitor is held
          |
          +-- has monitorenter/monitorexit?
          |          -> preserve synchronized block/handlers
          |
          v
    Instrument entry / normal + exceptional exits
          |
          v
    Check frames / exception / monitor
          |
          v
    Verify class file + integration tests
```

Important testing requirements:

1. **Abstract and native:** do not arbitrarily generate `Code`; have another measurement strategy instead of silently claiming "instrumented".
2. **Synchronized:** test normal execution, exceptions, monitor contention, tracing recursion, and overhead. Compare inside/outside monitor to understand latency accurately.
3. **Constructor/initializer:** check during class initialization, exceptions, and circular initialization.
4. **Bridge/synthetic:** check for double-counting when called via generics/interfaces.
5. **Bytecode integrity:** use the verifier, check `StackMapTable`, try/catch, return/throw paths, and class-file version.
6. **Retransform:** do not assume permission to change method flags/schema of loaded classes. Only make changes supported by the target JVM.
7. **Class-loader scope:** two loaders can define the same class name; do not filter by name alone when the agent has a special scope.

## 12. Common errors and fixes

| Symptom | Common cause | How to fix |
| --- | --- | --- |
| `MethodModel.code()` is empty on an abstract method | Abstract has no bytecode implementation | Skip body and instrument the concrete implementation |
| Native method has no body | `ACC_NATIVE` forbids the Code attribute | Use wrapper/call site/native instrumentation |
| Synchronized Java method is skipped | Confusing `ACC_SYNCHRONIZED` with "no Code" | Check actual Code; method body can still be instrumented |
| `synchronized native` gets Code inserted | Checking synchronized flag without checking native | Prioritize checking Code and `ACC_NATIVE` |
| `javap -c` does not show monitorenter in synchronized method | JVM applies monitor implicitly based on the flag | Use `javap -v` to see `ACC_SYNCHRONIZED` |
| Method has monitorenter without synchronized flag | Code contains a synchronized block | Analyze instructions and exception handlers |
| Tracing measures less than lock contention | Method-entry advice runs after acquiring monitor | Place caller-side timer or measure JVM monitor events |
| Metrics double-count | Hooking both bridge and implementation | Clearly define ownership and method filtering |
| `VerifyError` after rewrite | Wrong frames, schema, exception, or monitor pairing | Verify bytecode, use a tool matching the class version |
| Constructor crashes when instrumented | Hook uses `this` before valid constructor chain | Move hook to a safe point |
| `UnsatisfiedLinkError` when testing native demo | No native implementation | Do not call native declarations if JNI is not linked |
| Class initialization fails due to hook | Recursion/exception in `<clinit>` | Reduce dependencies, prevent recursion, have an error policy |
| Java 17 does not recognize `java.lang.classfile` | Class-File API is official from JDK 24 | Use JDK 24+ or ASM/Byte Buddy for JDK 17 |

## 13. Pre-release checklist

1. Read flags **and** `Code` in the actual artifact, not just by looking at source.
2. **Skip no-Code** for method-body advice; decide separately how to measure abstract/native.
3. Do not exclude synchronized methods wholesale: many synchronized methods **have Code**.
4. Distinguish synchronized method (implicit monitor) from synchronized block (explicit monitor instructions).
5. Define target latency: **execution under lock** differs from **wait-to-acquire lock**.
6. Preserve normal/exception exits, stack maps, monitor balance, and return values.
7. Define policies for constructors, initializers, bridge, and synthetic methods.
8. Limit blocking work in synchronized advice; avoid recursion/deadlock.
9. Test on the target JVM and class loaders, including retransform if applicable.
10. Ensure metrics accurately reflect the method/time actually instrumented.

## 14. Self-check

**Question 1:** Can bytecode be inserted into the `abstract void run();` method itself?

**Answer:** No. An abstract method has no Code. Choose the concrete override or a call boundary.

**Question 2:** Does `public synchronized void run() { ... }` have Code?

**Answer:** Yes, because synchronized is only a monitor flag; the Java body still has bytecode.

**Question 3:** Does `public synchronized native void run();` have Code?

**Answer:** No, because it is a native method; synchronized does not make Code appear.

**Question 4:** Does `void run() { synchronized(lock) { action(); } }` require the `ACC_SYNCHRONIZED` flag?

**Answer:** No. Code contains `monitorenter`/`monitorexit` for the synchronized block.

**Question 5:** Does method-entry advice in a synchronized method also measure monitor wait time?

**Answer:** No. Advice starts after the monitor has already been acquired by the JVM.

**Question 6:** Are modifiers provided by reflection sufficient to know whether a method has Code?

**Answer:** No. To confirm the Code attribute, you need to read the class file with `javap`, the Class-File API, or a bytecode parser.

**Takeaway:** **`abstract` and `native` have no `Code`; `synchronized` can have `Code` and the JVM manages the monitor implicitly.** Check the actual method before inserting advice, then choose the appropriate probe point to preserve semantics and measure the right target.
