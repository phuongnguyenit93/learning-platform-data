# Maintaining Compatibility When Multiple Java Agents Modify the Same Method

When an application runs with two Java agents—for example, agent A recording traces and agent B measuring duration—**both can transform the bytecode of the same class and the same method**. The modifications do not work as two independent patches applied to the original `.class` file: the JVM invokes **ClassFileTransformer** instances in a defined order, and the `byte[]` returned by the previous transformer becomes the input to the next transformer. If B rebuilds the method from bytes on disk, removes instructions added by A, or assumes the method structure is always in its original state, A's features may disappear, be inserted twice, or the JVM may reject the final class file.

This lesson explains how the JVM chains multiple transformers; how to write transformations that preserve prior valid modifications; risks with **retransform/redefine**, class loaders, modules, and concurrency; and a runnable Java 17+ example in which **two `-javaagent` passes modify the result of the same method** to clearly show the impact of ordering.

## 1. Objectives and High-Level Model

After completing this lesson, you should be able to:

1. Explain why transformer B may receive bytes **already modified by A**, rather than the original bytes B0.
2. Know the **four transformer groups** in the order applied by the JVM and distinguish group order from registration order.
3. Know when to **return null**, when to return a **new byte array**, and why not to mutate **classfileBuffer** directly.
4. Preserve method semantics: returns, exceptions, stack/frames, synchronization, annotations, and metadata.
5. Design transformations to be **idempotent** so advice is not inserted twice after transform/retransform.
6. Test A, B, A+B, B+A, repeated registration, late-loaded classes, and retransform.
7. Identify cases where two agents are **business-logic incompatible** without a coordination mechanism.

~~~text
Class bytes B0 (before transformers)
        │
        ▼
Transformer A ── return B1 = add invocation-counting advice
        │
        ▼
Transformer B receives B1, not the original B0
        │
        └── return B2 = keep A + add duration-measuring advice
        ▼
Subsequent transformers (if any)
        │
        ▼
JVM verifies/links/defines class from final bytes
        │
        ▼
Application executes method according to the accepted definition
~~~

**Core principle:** a transformer that does not want to modify a class must **return null** on its turn; a transformer that wants to modify it processes the **current bytes in the chain** and returns a new array containing a valid class file. Callback return values alone do not prove the JVM accepted the class or that the application exhibits the intended effect.

## 2. Chaining Contract for Multiple ClassFileTransformers

### 2.1. Each Result Becomes the Next Step's Input

Given two transformers A and B:

| A returns | B returns | Result of the A → B segment |
| --- | --- | --- |
| **null** | **null** | Keep B0 unchanged |
| B1 | **null** | Continue with B1 |
| **null** | B2 | B2 is built from B0 |
| B1 | B2 | B2 must be built from B1 |
| B1 | Invalid B2 | The JVM may reject the final definition |

If A **returns null**, that does not mean "no agent has transformed the class". If A returns B1, B cannot validly assume that every instruction in B1 was generated by the original application. In a method observed by multiple agents, it is critical that B **analyzes the existing code as well**, preserves valid properties, and only modifies what B owns.

### 2.2. Order of the Four Transformer Groups in Java 17

According to the **ClassFileTransformer** Javadoc, the JVM processes transformers by group:

1. **Java transformers that do not support retransformation**: registered with **addTransformer(t)** or **addTransformer(t, false)**.
2. **Native transformers that do not support retransformation**.
3. **Java transformers that support retransformation**: registered with **addTransformer(t, true)**.
4. **Native transformers that support retransformation**.

**Within each group**, transformers are invoked in registration order. Native transformers correspond to the JVM Tool Interface **ClassFileLoadHook** event. For startup agents via **-javaagent**, the JVM invokes **premain** methods in the order declared on the command line, but **you cannot assume the first JAR's transformer always runs before the second JAR's transformer** if they are registered in different groups.

Example:

~~~text
-javaagent:agent-a.jar -javaagent:agent-b.jar

premain A: addTransformer(A, true)   → retransformation-capable Java group
premain B: addTransformer(B, false)  → non-retransformation-capable Java group

When defining a new class:
    B is called before A due to GROUP order.
~~~

If both A and B call **addTransformer(t, false)**, they belong to the same group and run in registration order. If agent B is attached after startup or a framework removes and re-adds a transformer, the actual order may differ from what you assumed when designing the pipeline.

### 2.3. Do Not Assume All Transformations Commute

Let A(x) be the bytes after A's transformation, and B(x) be the bytes after B's transformation:

- **B(A(B0))** is the result when A runs before B.
- **A(B(B0))** is the result when B runs before A.

The two expressions can differ even when each transformer is valid on its own. For logging, tracing, timeout, or security advice, the difference can change what is measured, the order of exception handling, or the events recorded. Deployment documentation should clearly state: **which order is supported, what the expected result is, and whether the order can be reversed**.

## 3. Rules for Writing Transformers Without Breaking Other Agents

### 3.1. Always Use the Current classfileBuffer

~~~java
// Illustrative snippet inside ClassFileTransformer.transform(...).
if (!"com/example/Service".equals(className)) {
    return null;
}
byte[] next = applyOnlyMyChanges(classfileBuffer);
return next; // null if no modification needed, new byte[] if modified.
~~~

This is pseudocode because **applyOnlyMyChanges** depends on the transformation library. However, the meaning is clear: the input is the **classfileBuffer passed by the JVM into the current callback**.

Incorrect design:

~~~java
// Conceptual anti-pattern, not runnable Java.
byte[] pristine = readClassBytesFromOriginalJar("com/example/Service");
byte[] replacement = instrument(pristine);
return replacement; // Discards instructions inserted by earlier agents.
~~~

An agent may read bytes from disk for analysis or comparison, but it must not silently **replace the entire transformation chain** with a version it just built from the original file. Doing so easily wipes out metrics/logging/tracing from earlier agents.

### 3.2. Return null When Unchanged; Do Not Mutate Input

~~~java
// Correct buffer ownership pattern:
if (!shouldTransform(className, loader)) {
    return null;
}
byte[] copy = classfileBuffer.clone();
modifyCopyAsValidClassFile(copy);
return copy;
~~~

This is also pseudocode. **classfileBuffer must not be mutated directly**, even when ultimately returning null. If actual processing determines no transformation is needed, return **null** and avoid cloning/recomputing bytecode. Do not use **new byte[0]** to mean "no change".

Returning a **new byte[]** from a transformer only proves that it supplied replacement data. The JVM and subsequent transformers must still verify and process it; an array with a different reference but identical content is not evidence of a new effect.

### 3.3. Preserve All Instructions and Metadata You Do Not Own

When modifying a method, you must consider:

- Exact method name and **descriptor**; do not filter by name alone because of overloads.
- Existing instructions, including callsites added by other agents.
- **Max stack, local variables, StackMapTable**, branch targets, and try/catch/finally handlers.
- **Annotations, generic signatures, line numbers, and local-variable tables** if other consumers rely on them.
- **Access flags**, method semantics, constructors, `synchronized`, and ABI characteristics.
- The class loader and module of the transformed class; the same FQCN in two different defining loaders represents two distinct runtime classes.

With ASM, you need to understand the **ClassReader → ClassVisitor/MethodVisitor → ClassWriter** pipeline and forward visitor calls whenever you are not intentionally replacing them. With Byte Buddy, you need to understand method matching, transformer ordering, and advice/delegation behavior, avoiding "replace method body" configurations that make code added by earlier agents vanish.

Do not assume that enabling **COMPUTE_MAXS** will automatically fix all stack-map frame issues; frame computation and common superclass resolution have their own conditions. You must test on the real JVM/JDK and with the appropriate class loaders.

### 3.4. Intentional Idempotency

If the same agent is loaded twice, or the same class is retransformed multiple times, advice can be inserted multiple times. Ways to prevent this:

- Before inserting, check whether the method already has **your agent's own identifying marker** (for example, a callsite to a helper in your own namespace).
- Do not use generic, meaningless markers like **INSTRUMENTED** shared across agents; avoid name collisions and wrong ownership.
- If the code already carries your agent's advice, **return null** for the current callback.
- When caching state, use a sufficiently strict class identity (class name + defining loader/module as needed); do not rely solely on a string name.
- Do not assume you can add fields/methods during **retransform/redefine**, because the JVM typically forbids that kind of class schema change.

Idempotency of individual transformations **does not mean** A and B can be reordered arbitrarily; a transformation that does not double-insert can still depend on another agent's output.

## 4. Runnable Java 17+ Example: Two Agent Passes Modifying the Same Target.value()

This example uses **one agent JAR declared twice** on the command line with options A and B. Per the Java Instrumentation specification, multiple **-javaagent** arguments may point to the same jarpath; the JVM invokes `premain` in declaration order. Each `premain` call creates **a separate transformer instance**, giving us two transformers and demonstrating chaining without having to deal with dependency conflicts between two separate JARs.

The focus of the example is how they both modify **Target.value()**. A changes the string literal **ORIG000 → STEP100**, and B changes **STEP100 → STEP200**. All three are **7 ASCII bytes**, allowing us to patch a single constant pool entry in the demo class without changing the class file length. This is an exercise for observing chaining, **not a general-purpose method weaving mechanism**.

### 4.1. File DemoApp.java

~~~java
// File: DemoApp.java
public final class DemoApp {
    public static void main(String[] args) throws Exception {
        // Actively load Target after all premain methods have run.
        Class<?> target = Class.forName("Target");
        java.lang.reflect.Method method =
                target.getDeclaredMethod("value");
        System.out.println("VALUE=" + method.invoke(null));
    }
}

class Target {
    static String value() {
        return "ORIG000";
    }
}
~~~

**DemoApp** and **Target** belong to the same default package and application class loader in this example. **Class.forName("Target")** provides a clear point where the class is used after the JVM installs the agents. A package-private method can be called from `DemoApp` in the same package/module. Real projects should use clearly named packages and manage access permissions appropriately.

### 4.2. File ChainAgent.java

~~~java
// File: ChainAgent.java
import java.lang.instrument.ClassFileTransformer;
import java.lang.instrument.Instrumentation;
import java.nio.charset.StandardCharsets;
import java.security.ProtectionDomain;

public final class ChainAgent implements ClassFileTransformer {
    private final String mode;

    private ChainAgent(String mode) {
        this.mode = mode;
    }

    public static void premain(String options, Instrumentation inst) {
        if (!"A".equals(options) && !"B".equals(options)) {
            throw new IllegalArgumentException("Use mode A or B");
        }

        inst.addTransformer(new ChainAgent(options), false);
        System.out.println("REGISTER " + options);
    }

    @Override
    public byte[] transform(
            ClassLoader loader,
            String className,
            Class<?> classBeingRedefined,
            ProtectionDomain protectionDomain,
            byte[] classfileBuffer) {

        if (!"Target".equals(className)) {
            return null;
        }

        String from = "A".equals(mode) ? "ORIG000" : "STEP100";
        String to = "A".equals(mode) ? "STEP100" : "STEP200";

        byte[] result = swapUtf8(classfileBuffer, from, to);
        System.out.println("TRANSFORM " + mode + " "
                + (result == null ? "SKIP" : "CHANGED"));
        return result;
    }

    private static byte[] swapUtf8(byte[] original,
                                   String from, String to) {
        byte[] oldValue = from.getBytes(StandardCharsets.US_ASCII);
        byte[] newValue = to.getBytes(StandardCharsets.US_ASCII);
        if (oldValue.length != newValue.length || original.length < 10
                || (original[0] & 0xff) != 0xca
                || (original[1] & 0xff) != 0xfe
                || (original[2] & 0xff) != 0xba
                || (original[3] & 0xff) != 0xbe) {
            return null;
        }

        int count = u2(original, 8);
        int p = 10;

        for (int i = 1; i < count; i++) {
            int tag = original[p++] & 0xff;
            switch (tag) {
                case 1 -> { // CONSTANT_Utf8
                    int size = u2(original, p);
                    p += 2;
                    if (size == oldValue.length
                            && matches(original, p, oldValue)) {
                        byte[] copy = original.clone();
                        System.arraycopy(newValue, 0, copy,
                                         p, newValue.length);
                        return copy;
                    }
                    p += size;
                }
                case 3, 4, 9, 10, 11, 12, 17, 18 -> p += 4;
                case 5, 6 -> {
                    p += 8;
                    i++; // long/double occupy two slots.
                }
                case 7, 8, 16, 19, 20 -> p += 2;
                case 15 -> p += 3;
                default -> throw new IllegalArgumentException(
                        "Unknown constant-pool tag: " + tag);
            }
        }
        return null;
    }

    private static int u2(byte[] bytes, int index) {
        return ((bytes[index] & 0xff) << 8)
                | (bytes[index + 1] & 0xff);
    }

    private static boolean matches(byte[] bytes, int p,
                                   byte[] sought) {
        if (p + sought.length > bytes.length) {
            return false;
        }
        for (int i = 0; i < sought.length; i++) {
            if (bytes[p + i] != sought[i]) {
                return false;
            }
        }
        return true;
    }
}
~~~

Key points:

1. **premain** creates **new ChainAgent(options)**; two `-javaagent` flags mean two independent transformer instances registered in the same **canRetransform=false** group.
2. Only the internal class named **Target** is inspected; other classes **return null** without being parsed or copied.
3. A only changes **ORIG000** to **STEP100**, and then B can read those modified bytes and change **STEP100** to **STEP200**.
4. When B runs before A, it does not find **STEP100**, so it **returns null**. A still finds **ORIG000** afterward and modifies it once.
5. **original.clone()** creates a separate array to replace the exact same-length UTF8 entry; **classfileBuffer is not mutated**.
6. **TRANSFORM ... CHANGED** logs the supplied array; the **VALUE=...** output in `DemoApp` confirms the class actually uses the new literal.

**Technical limitations:** The constant pool parser helper above is only for **valid class files generated by `javac` in this example**; it lacks full bounds checking for malformed/forged input, does not handle arbitrary Modified UTF-8, does not support complex multi-edit transformations, and does not manage branches/StackMapTable. Do not use it to modify arbitrary classes. In production, use a bytecode library, preserve unrelated metadata, validate inputs, and respect retransform/redefine constraints.

### 4.3. File agent.mf

Create a text file **agent.mf** with a trailing newline:

~~~text
Manifest-Version: 1.0
Premain-Class: ChainAgent
~~~

This example only handles newly loaded classes, so **Can-Retransform-Classes** is not needed. The manifest contains the binary name of the agent class, not a `.class` file path.

### 4.4. Compiling, Packaging, and Running

Place **DemoApp.java**, **ChainAgent.java**, and **agent.mf** in the same directory. Use JDK 17+:

~~~bash
javac --release 17 DemoApp.java ChainAgent.java
jar cfm chain-agent.jar agent.mf ChainAgent.class
java -javaagent:chain-agent.jar=A -javaagent:chain-agent.jar=B -cp . DemoApp
~~~

Expected output on HotSpot Java 17:

~~~text
REGISTER A
REGISTER B
TRANSFORM A CHANGED
TRANSFORM B CHANGED
VALUE=STEP200
~~~

A returns bytes containing **STEP100**; B receives those bytes and changes them to **STEP200**; the JVM defines **Target** with the final literal. Reversing the order:

~~~bash
java -javaagent:chain-agent.jar=B -javaagent:chain-agent.jar=A -cp . DemoApp
~~~

Output:

~~~text
REGISTER B
REGISTER A
TRANSFORM B SKIP
TRANSFORM A CHANGED
VALUE=STEP100
~~~

B skipped because `STEP100` was not present yet. A ran afterward and produced `STEP100`, but there was no subsequent B pass to turn it into `STEP200`. Running without agents:

~~~bash
java -cp . DemoApp
~~~

~~~text
VALUE=ORIG000
~~~

Running A alone:

~~~bash
java -javaagent:chain-agent.jar=A -cp . DemoApp
~~~

~~~text
REGISTER A
TRANSFORM A CHANGED
VALUE=STEP100
~~~

Running A twice to verify it does not duplicate the result:

~~~bash
java -javaagent:chain-agent.jar=A -javaagent:chain-agent.jar=A -cp . DemoApp
~~~

~~~text
REGISTER A
REGISTER A
TRANSFORM A CHANGED
TRANSFORM A SKIP
VALUE=STEP100
~~~

The second A pass does not see `ORIG000`, so it returns `null`. This illustrates idempotency **for this string-replacement rule**; an agent that inserts instructions is not automatically idempotent.

Running **javap -c -p Target** shows that the class on disk still returns **ORIG000**: this example transforms the class definition **inside the JVM**, without modifying the `.class` file on disk.

### 4.5. When Two Agents Are Two Real JARs

In real systems, A and B usually have **two Premain-Classes, two JARs, and different dependencies**. If they are in the same group, the chaining mechanism above still applies. The difference is that each agent may register multiple transformers, belong to different capability groups, load helpers from different loaders/modules, or use conflicting bytecode library versions. Therefore, you must observe the **actual registration order** and test compatibility on the exact version combination.

## 5. Ensuring Two Advices on the Same Method Do Not Break Semantics

The constant pool example is easy to follow because it adds no control flow. In real methods, A wants to count requests and B wants to record duration, so both may insert entry/exit advice:

~~~java
// Source-level example to illustrate semantics; not source code
// that a transformer is allowed to swap directly inside the JVM.
Result process(Request request) {
    return service.handle(request);
}
~~~

A desired semantic outcome:

~~~text
process(request):
    Agent A: incrementCallCounter()
    Agent B: startTimer()
    try:
        return originalProcess(request)
    finally:
        Agent B: recordDuration()
~~~

This is a **conceptual model**, not a list of JVM instructions. The implementation must preserve the return type, operand stack, exception table, `synchronized` semantics, and all execution paths. If A also writes an exit log or B only records metrics on normal return, **advice ordering** will affect the measured results.

| Method characteristic | Risk when multiple agents modify | How to verify |
| --- | --- | --- |
| **Method descriptor/overload** | Attaching advice to the wrong overloaded method | Match name + descriptor + class identity |
| **Primitive/reference return** | Wrong boxing/unboxing or stack type mismatch | Test void, primitive, object, and null |
| **Exception** | Advice swallows exceptions, alters cause, or skips cleanup | Test normal and exceptional exits |
| **try/catch/finally** | Inserting branches corrupts the exception table | Inspect control-flow graph and handlers |
| **Synchronized** | Advice alters lock order or monitor hold duration | Concurrency tests and thread dumps |
| **Constructor** | Using `this` before the object is initialized | Check uninitialized-this / verifier |
| **StackMapTable** | Invalid frames after multiple insertions | Verify with the JVM and bytecode library |
| **Locals/max_stack** | Two agents collide on slots or miscompute maxes | Evaluate layout and recomputation |
| **Annotations/attributes** | Dropping metadata added by A or frameworks | Compare class metadata before/after |
| **Helper linkage** | New bytecode calls an invisible class | Test classloader/module and API visibility |

A transformation that is valid in isolation can become invalid when combined with another if B accidentally drops local slots, exception branches, or metadata introduced by A.

### 5.1. onEnter/onExit Ordering Must Be Defined

If A opens a span and B opens a child span, nesting order affects the parent-child relationship. If B measures duration around the entire method already containing A's logging, the metric may include logging overhead; if B wraps only the original body, it will not. Both can be valid bytecode, but only one matches the business specification. Therefore, you must test **metric values and event relationships**, not just confirm that the JVM loads the class successfully.

### 5.2. Avoid Adding Members to Already-Loaded Classes

Some agents try to add fields to store counters or synthetic methods to call helpers. If two agents use the same name, they can collide even at initial class load. With **retransform/redefine**, the JVM generally forbids adding/removing fields or methods, changing the class hierarchy, and similar schema changes. Instead of relying on new fields when modifying running classes, store state in an external helper or use JVM-supported instrumentation within the method body with an appropriate lifecycle strategy.

### 5.3. Each Agent Must Maintain Ownership of Its Own Marker

Before adding advice, A should detect **A's own marker**, rather than treating any call to B's helper as a sign of "already instrumented". Use sufficiently distinctive identifiers, avoid overly generic field/helper names, and inspect instruction structure rather than just matching a collision-prone class name. If no stable marker representation is available, establish an explicit policy for retransforming from baseline bytes rather than guessing when to insert.

## 6. Modules, Class Loaders, and Internal Libraries of Two Agents

### 6.1. Two Classes with the Same Name Are Not Necessarily the Same Class

A runtime type is identified by **binary name + defining class loader**. For example, an application server may have two versions of **com.example.Service** defined by two different plugin loaders. Agent A modifies plugin 1's copy; agent B might modify both if it filters only by class name string. Compatibility must account for the **exact Class instance**, loader, and module—not just the FQCN.

If an agent caches transformation results keyed by **String className**, it may feed plugin 1's class bytes into plugin 2, causing class format/linkage errors or unexpected behavior. Key caches by proper class identity and use an eviction policy so you do not hold strong references to unloaded class loaders.

### 6.2. Helpers Inserted by Agent A Must Resolve at Runtime

A transformation may succeed during serialization yet fail at runtime when the modified method calls **com.agentA.Helper.enter()** and the target's class loader cannot find the helper. With named modules, you must also consider **readability, exports/opens, and access modifiers**. **ClassFileTransformer** only produces bytes; it does not automatically resolve class loader/module relationships for auxiliary code.

When multiple agents bundle ASM/Byte Buddy or utilities with the same FQCN but different versions, you can hit **NoSuchMethodError**, **LinkageError**, or behavioral drift because a loader defines only one version. Shading/relocation or dependency isolation is a common implementation approach, though you must also verify helper code referenced **from transformed classes**.

### 6.3. Do Not Arbitrarily Call loader.loadClass Inside Callbacks

Transformers typically run inside the class loading path. If A is transforming X and calls **loader.loadClass(Y)**, Y may trigger B, and B may try to load X or hold another lock. This can cause recursion, class circularity errors, or deadlocks. Callbacks should be short and avoid blocking I/O, global locks, and heavy dependencies. If you need to resolve a common superclass during frame computation, use a controlled resolution mechanism rather than eagerly loading application classes inside the transformer.

## 7. Retransform: Where Agents Often Think Advice Was "Lost"

Initial class loading and **Instrumentation.retransformClasses(...)** do not follow the same callback pattern. According to the Java 17 documentation:

- A transformer registered with **canRetransform=false** is called on class load/redefine, but **is not called again** on retransform; the JVM **automatically reapplies the saved result** from that group's previous load/redefine pass.
- A transformer with **canRetransform=true** is called again on retransform; it must produce a result that remains a **valid redefinition** of the running class.
- The input bytes during retransform may differ byte-for-byte from the bytes supplied at initial load, because constant-pool layout and attributes may differ.
- **Active stack frames** of running methods may continue executing the old definition, while new invocations use the new code. Retransform does not automatically re-run static initializers.
- If the final bytes violate schema rules or fail verification, **retransformClasses** may throw an error; a `TRANSFORMED` log inside the callback cannot be treated as proof of completion.

~~~text
Initial load:
    Original bytes → A (non-retransform-capable)
                   → B (retransform-capable)
                   → installed definition

Subsequent retransform:
    JVM reconstructs baseline bytes
        → reapplies A's saved output, DOES NOT call A again
        → calls B again on the bytes already transformed by A
        → verifies/installs new definition if valid
~~~

**Consequence:** B must not discard A's result during retransform. Likewise, A cannot just change configuration inside its own object and expect a retransform pass to invoke A again if A registered with **false**. If you want to dynamically reconfigure transformations on already-loaded classes, design the capability flag and update path from the start.

### 7.1. Redefine Is a Different Path

**redefineClasses(...)** accepts class definition bytes supplied by the caller; transformers apply to redefine according to the contract. It differs from **retransformClasses(...)**, which re-runs the chain from JVM-reconstructed baseline bytes with previous results automatically reapplied based on capability. If one agent redefines a class from bytes without accounting for another agent, the two agents may interact differently than during retransform alone.

Do not use **removeTransformer(A)** as an undo command; removing a transformer does not automatically revert already-installed bytecode. Rolling back requires a semantically sound class update plan that is compatible with active agents and JVM schema limits.

### 7.2. Concurrent Events and Shutdown

**removeTransformer(instance)** may return while an already-started callback is still running. Multiple threads can also define classes concurrently. Avoid sharing mutable `byte[]` across callbacks; if you have caches/counters, use proper synchronization and explicit lifecycles. Do not close resources that an in-flight callback might still access immediately after `removeTransformer` without a coordination mechanism.

## 8. Pragmatic Coexistence Guidelines

To reduce the likelihood of conflicts when two agents modify the same method:

1. **Modify only the necessary scope:** filter by class loader/module and name + descriptor; do not blanket-transform the entire JDK or application.
2. **Transform on the current input:** do not rebuild methods from original bytes and overwrite what earlier agents added.
3. **Preserve code and metadata:** use a bytecode library with a tested visitor/writer strategy; compute frames and exception tables accurately.
4. **Recognize your own transformations:** avoid duplicate advice insertion during retransform or when a startup agent is declared twice.
5. **Keep naming and dependencies independent:** avoid colliding on synthetic helpers, static fields, packages, or shared libraries.
6. **Minimize side effects:** avoid calling application code, network, blocking file I/O, or complex locks inside `transform`.
7. **Verify behavior:** do not rely solely on callback counts or `byte[]` return counts.
8. **Document compatibility clearly:** state supported versions of A, B, JDK, app frameworks, loading modes, modules/classloaders, and ordering.

In a system controlled by a single team, **a central coordinator** can accept requirements from A and B and build **a single unified pipeline**; this helps when transformations depend tightly on ordering or share instrumentation metadata. For independent third-party agents, there is no default guarantee that every combination/version is compatible; you must test and publish specific limitations.

## 9. Compatibility Test Matrix

| Scenario | Purpose | What to verify |
| --- | --- | --- |
| No agent | Baseline | Original behavior |
| A only | A works standalone | A's metrics/traces/returns/exceptions are correct |
| B only | B works standalone | B's metrics/traces/returns/exceptions are correct |
| A before B | Chain order 1 | B preserves A's result; class is valid |
| B before A | Chain order 2 | Result and ordering are supported |
| A appears twice | Idempotency | No unexpected duplicate advice |
| B appears twice | Idempotency | No unexpected duplicate advice |
| Different A/B versions | Dependency conflicts | No class shadowing or linkage errors |
| Class loaded after premain | Coverage | Callback runs for the right class/loader |
| Retransform loaded class | Reapplication | No lost or duplicated advice |
| Redefine from new bytes | Schema limits | Methods and metadata remain valid |
| Two loaders, same class name | Scope | Only target runtime class is modified |
| Method throws exception | Cleanup semantics | Exception not swallowed, context cleaned up |
| Concurrent class loading | Thread safety | No races or deadlocks |
| Shutting down one agent | Lifecycle | In-flight callbacks do not crash |

### 9.1. Essential Logs for Investigation

~~~text
Agent=A event=LOAD class=com/example/Service
loader=<identity> module=<name> method=process(Ljava/lang/String;)V
group=JAVA_NO_RETRANSFORM action=REPLACEMENT_SUPPLIED

Agent=B event=LOAD class=com/example/Service
loader=<identity> module=<name> method=process(Ljava/lang/String;)V
group=JAVA_NO_RETRANSFORM action=REPLACEMENT_SUPPLIED

Class accepted by JVM; new invocation verified; both features observed.
~~~

This is an **illustrative log format**, not something the JVM prints automatically. If needed, also log hashes of input/output bytes to verify whether B actually saw A's bytes. However, **different hashes do not prove the JVM applied the result**; you must verify the target's methods/behavior after the class is defined or retransformed.

Do not log or copy the entire `classfileBuffer` on every production call unnecessarily: CPU cost, heap usage, startup time, and sensitive data exposure can increase significantly.

## 10. Common Failure Modes and Fixes

| Symptom | Possible cause | Action |
| --- | --- | --- |
| A works alone, A+B loses A's metrics | B rewrites method from old bytes | Use current `classfileBuffer`, check visitor/writer |
| A+B causes VerifyError | Mismatched frames/stack/exception handlers | Inspect end-of-pipeline bytecode and verifier output |
| Swapping agent order changes output | Non-commutative transforms or different groups | Check `canRetransform` and registration order |
| CHANGED logged, but runtime still fails | Invalid final bytes or wrong target | Check `ClassFormatError`/`LinkageError` and class identity |
| Same log appears multiple times | Advice inserted repeatedly | Check markers and idempotency |
| Retransform does not call A | A registered with `canRetransform=false` | Understand old output is reapplied; fix capability policy |
| Removing A still executes A's code | Class already has A's code, or callback running | Do not treat `remove` as rollback; manage lifecycle |
| New agent causes NoSuchMethodError | Conflicting helper/library versions | Isolate/shade dependencies and test |
| Only one plugin fails | Same FQCN but different loaders | Log defining loader/module and filter properly |
| JVM hangs during class loading | Re-entrant callback / lock cycle | Take thread dump; reduce I/O and locks in transformer |

**Distinguishing transformer exceptions from invalid final bytecode:** According to the Javadoc, when a transformer throws an uncaught exception, the JVM still calls the remaining transformers and attempts to define the class; for that transformer, the effect is similar to **returning null**. However, if a transformer returns an **invalid class file**, verification/definition may fail. Therefore, do not use `throw` as a normal skip mechanism; **return null** when no modification is needed.

## 11. Diagnostic Workflow When a New Agent Breaks an Existing One

Suppose enabling tracing alone produces all spans, but adding a profiler causes spans to disappear. Proceed as follows:

1. Identify the **exact class and method**, along with the defining loader/module.
2. Record **transformer group order + registration order**, not just manifest/JAR order.
3. Verify that A is called, returns bytes, and that B receives bytes containing A's changes.
4. Inspect B's bytecode writer: does it reload bytes from the JAR, drop instructions, omit metadata, or compute wrong frames?
5. Confirm the JVM accepted the post-chain definition, then invoke the modified method to verify both tracing and profiling.
6. Check runtime support: helper class access, module readability, dependency versions, and class loaders.
7. Re-run baseline, A, B, A+B, and B+A on the exact JDK/app build; classify as an ordering conflict, schema conflict, semantic conflict, or dependency error.
8. If a coordination protocol is needed, define explicit ownership and ordering or coordinate through a shared instrumentation pipeline.

Do not conclude "transformer B overwrote A" just because A's logs disappeared; A might still be in the bytecode while its helper fails to resolve, the method is not called, an old active stack frame is still running, or trace context is cleared prematurely. Evidence must tie back to a specific step.

## 12. Self-Check Questions

1. **Does A returning null cancel B's output?** No. B can still modify the class.
2. **If A runs before B, which bytes does B receive?** The bytes returned by A if A modified the class, or the existing bytes if A returned null.
3. **If JAR A precedes JAR B, does A's transformer always run first?** Not if they belong to different capability groups.
4. **Why does the B→A demo yield STEP100 instead of STEP200?** B looks for STEP100 while the bytes still contain ORIG000; B returns null, and A later changes ORIG000 to STEP100.
5. **Can you always read the original class file from the JAR to instrument it?** You should not; it can wipe out prior agents' modifications.
6. **Why must exception paths be tested?** Advice from two agents can alter exceptions or skip cleanup when a method throws.
7. **Does retransform guarantee calling every transformer again?** No. Transformers with `canRetransform=false` are not called again; their prior output is reapplied automatically.
8. **Does removeTransformer automatically revert inserted code?** No.
9. **Can you add new fields to an already-loaded class via retransform by default?** No. Schema changes are generally restricted and must obey JVM limits.
10. **How do you prove compatibility?** Valid final bytecode, right class/method, and both features working properly on new invocations across supported orders and configurations.

## 13. Pre-Release Checklist

- I know the **transformer groups** and actual registration order.
- Each `transform` processes the **current bytes**, without erasing valid prior results.
- All no-op cases use **return null**; all modifications return a **valid new byte[]**, leaving the input immutable.
- Scope is identified by **class name + defining loader/module + method descriptor** as needed.
- Transformation code preserves return, exception, `synchronized`, stack/frame, and metadata semantics.
- Advice has duplicate-insertion protection, its own marker, and no helper/dependency collisions.
- I have tested both **A+B** and **B+A**, and documented any required ordering.
- For already-loaded classes, `retransform/redefine` capabilities, schema limits, and active frames have been checked.
- Removing a transformer or shutting down an agent is managed separately, without promising automatic bytecode rollback.
- Key tests include **behavioral evidence**, not just callback/return-byte logs.
