# Verifying Structure with `ClassFile.verify`, Then Testing Loading and Execution on the JVM

> **Goal:** Understand the testing workflow for classfiles generated by Java instrumentation: **static verification** using the Java Class-File API `ClassFile.verify(...)`, followed by **loading the exact verified bytes into the JVM**, triggering initialization, checking linkage, and running test cases for return values, exceptions, and dependencies. Know why an empty verification result does not equate to correct behavior, why testing on the actual class loader/module/JDK is necessary, and how to classify errors when releasing a Java agent. This lesson includes a complete **JDK 24+** Java example featuring all three `verify` overloads, an isolated load, and a fresh JVM run.

This lesson belongs to the **Testing and Diagnostics** group. `ClassFile` in the title refers to `java.lang.classfile.ClassFile`, part of the **standard Class-File API since JDK 24 (JEP 484)**. Java 17 does not include this standard package; if a production application runs on JDK 17, you can place the verification tooling on JDK 24+ and run integration tests on the **target JDK 17** with classfiles of a compatible version. **Do not** copy the lab using `java.lang.classfile` directly to `javac 17` and expect it to compile.

## 1. Why Are There Two Testing Layers?

A `ClassFileTransformer` or bytecode generator can return a byte array that the JVM will use to define or redefine a class. There are two distinct questions:

1. **Are the bytes valid according to the classfile format and bytecode verification rules?**
2. **Can the class be loaded, linked, initialized, and executed with correct business logic by a real JVM?**

These two questions require two types of evidence:

```text
source .class
     │
     ▼
parse → transform / build
     │
     ▼
candidate byte[]
     │
     ├── ClassFile.verify(candidate)
     │       └── structural/verification error → fix output
     │
     ▼
verification finds no errors
     │
     ▼
write exact .class/.jar artifact
     │
     ▼
target JVM + defining ClassLoader + JPMS graph
     │
     ├── load/link/initialize → runtime error?
     │
     ▼
invoke methods, test branches/exceptions/state
     │
     ├── wrong business result or too slow?
     │
     ▼
CI / integration / canary evidence
```

**`verify PASS` does not mean `runtime PASS`**, and runtime PASS on a single method does not prove all classes, dependencies, and paths are correct. Record three separate statuses: `verification_passed`, `load_link_passed`, `behavior_tests_passed`.

A classfile may be accepted by the verifier yet use `invokestatic` to call a helper missing from the target loader; the JVM may throw `NoClassDefFoundError` or `NoSuchMethodError` when that instruction is executed. Another class may load and run without error yet return `x * 3` instead of `x * 2`. That is a logic error, not a stack map error.

## 2. What Exactly Does `ClassFile.verify` Provide?

The standard JDK 24+ API provides three overloads:

```java
import java.lang.VerifyError;
import java.lang.classfile.ClassFile;
import java.lang.classfile.ClassModel;
import java.nio.file.Path;
import java.util.List;

// The bytes and path variables must be provided by the program beforehand.
ClassFile cf = ClassFile.of();
ClassModel model = cf.parse(bytes);

List<VerifyError> modelErrors = cf.verify(model);
List<VerifyError> byteErrors = cf.verify(bytes);
List<VerifyError> diskErrors = cf.verify(path);
```

**This is an illustrative snippet, not a standalone Java file**, as `bytes` and `path` are assumed to already exist. The lab section will provide the complete program.

| API | Input | Use in Pipeline |
| --- | --- | --- |
| `verify(ClassModel model)` | Parsed class model | Verify the readable model, e.g., before transformation |
| `verify(byte[] bytes)` | Candidate bytes | Verify the **final bytes** returned by a transformer/builder |
| `verify(Path path)` | Written `.class` file | Verify the physical artifact before packaging/deployment |

The return value is **`List<java.lang.VerifyError>`**: an empty list means no verification errors were found during that check. A non-empty list must be printed/included in the error report and cause the test to **fail**, not merely log a warning.

`verify(Path)` can throw `IOException` when the file cannot be read; the parser or hierarchy resolver can also throw exceptions due to invalid input or an incomplete environment. Do not assume all malformed data will always be returned as a list element.

Check pattern:

```java
// Place inside a method that has a byte[] candidateBytes variable.
List<VerifyError> errors =
        ClassFile.of().verify(candidateBytes);

if (!errors.isEmpty()) {
    for (VerifyError error : errors) {
        System.err.println(error);
    }
    throw new AssertionError("Candidate verification failed");
}
```

This is an example snippet with `candidateBytes` supplied externally. In CI, the process must exit with a non-zero exit code if errors are detected. Logging `"verification failed"` while letting the build produce a release artifact can allow bugs to slip into production.

### `VerifyError` in the List vs. `VerifyError` in the JVM Differ in the Reporting Phase

Both are `java.lang.VerifyError`, however:

- In `List<VerifyError>`, it is a **data result** of the Class-File API verification check.
- When the JVM throws `VerifyError`, it is an **actual exception/error** during class loading, verification, or linking.

Simply observing an empty list does not prove that a JVM in a different deployment, with different loaders or modules, cannot throw `VerifyError` or other `LinkageError`s.

## 3. Successful Parsing Is Not Full Verification

`ClassFile.of().parse(bytes)` creates a `ClassModel`, an immutable model describing the classfile. However, the Class-File API uses **lazy parsing**: some attributes and instructions are only interpreted when the application traverses or accesses them. The Javadoc warns that `IllegalArgumentException` may occur at an accessor due to malformed bytes.

Therefore:

```text
parse(bytes) reports no error
      ≠
verify(bytes) returns an empty list
      ≠
JVM executes every method without error
```

In an instrumentation tool, you might parse to read class and method names, transform some elements, and serialize into new bytes. **The verify step must be performed on the new bytes**, not just the original model.

### Verification Error Classes of Interest

- Invalid header and classfile version.
- Incorrect constant pool entries, tags, or indexes.
- Invalid internal class names, type descriptors, or method descriptors.
- Corrupted instructions or invalid operand usage.
- Branch targets not pointing to a valid instruction boundary.
- Invalid exception handler table or bytecode ranges.
- Inconsistent operand stack, local variable types, and data-flow.
- Mismatched `StackMapTable` and frame type constraints.
- Attributes/metadata corrupted during rewriting.

This is a grouping of **format/JVMS** errors; it does not mean every error is always represented by `ClassFile.verify` with a fixed message. `IllegalArgumentException`, `List<VerifyError>`, and JVM-side errors must all be recorded separately.

### Errors Outside the Scope of Static Verification

- Business logic returning the wrong number or mis-evaluating a condition.
- Helper class located in a different class loader and thus unable to link.
- Method/field name present in the constant pool, but no corresponding method/field exists at runtime.
- Named module unable to read another module, or package not properly exported/opened.
- Static initializer throwing an exception or deadlocking.
- Concurrent invocations causing race conditions or lost metrics data.
- Probe being called twice instead of once on an exception path.
- Thread/blocking/network overhead exceeding the SLO budget.
- Transformer chain differing between local tests and production.
- Target JDK not supporting the candidate's major/minor version.

`ClassFile.verify` is **a quality gate**, not a tool that proves absolute system correctness.

## 4. Verify the Exact Candidate, Not a Similar Copy

Data flowing through a transformer chain may look like:

```text
B0 original bytes
    │
    ▼
T1 → B1
    │
    ▼
T2 → B2
    │
    ▼
T3 → B3 (final candidate)
```

If you verify **B1** but deploy **B3**, the result is insufficient to prove B3 is valid. In the JVM, Java/native transformers are applied in sequence; the output of one transformer can become the input of the next. No single agent always knows the final output after all other agents have run.

Therefore, tests should track the **exact candidate**:

1. Identify which source, tool/version, and JDK generated the bytes.
2. Run `ClassFile.verify(candidateBytes)`.
3. Write the bytes to the final artifact (`.class` or `.jar`) at the exact internal path.
4. Read and verify that artifact again; record its SHA-256 hash when needed.
5. On the test JVM, load **that exact artifact**, not a same-named class from the system classpath.
6. Test runtime semantics, exceptions, concurrency, and performance.
7. Upon release, use the exact verified artifact or compare hashes before deployment.

**Do not** conclude "verified" just because a `.class` file in a source directory shares the name of the one passed through `ClassDefinition`; `redefineClasses` may receive new bytes or pass through registered transformers.

### Explaining `ClassTransform.ACCEPT_ALL`

In the lab, we use:

```java
byte[] output =
        ClassFile.of().transformClass(
                model, ClassTransform.ACCEPT_ALL);
```

`ClassTransform.ACCEPT_ALL` is a transform that **preserves elements** and lets the builder reconstruct the classfile. It is a **no-op transform in terms of business intent**; it does not inject probes. The reason for using it is to demonstrate the pipeline `parse → transformClass → verify output → JVM load`, not to teach how to inject method calls into bytecode.

To perform real transformations, provide an appropriate `ClassTransform`/`MethodTransform`/`CodeTransform`, ensure valid stack maps/frames, and verify the output afterward. `transformClass` may produce bytes that are not byte-for-byte identical to the original binary while still preserving semantics; hence, comparing file size or hash alone is not a check for logical equivalence.

## 5. Hierarchy Resolver: A Common Blind Spot for Verification in Agents

For stack-map verification and type merges, the Class-File API may require inheritance and interface hierarchy information. JDK 24 provides `ClassFile.ClassHierarchyResolverOption`.

The default resolver uses the **system class loader and reflection**. This may be insufficient if:

- The target class is defined by a plugin, servlet, or custom loader.
- Two classes with the same name exist in different loaders.
- A class name exists only in newly generated bytes, not yet on the system classpath.
- Modules or layers control visibility differently than in the test environment.
- The agent wants to avoid triggering any class loading inside a callback.

According to the Javadoc, `ClassHierarchyResolver.ofClassLoading(loader)` looks up classes via loading/reflection. `ofResourceParsing(loader)` reads the corresponding classfile resources instead of relying entirely on loading classes. `ClassHierarchyResolver.of(...)` can use pre-known metadata about interfaces and supertypes.

Illustrative configuration snippet:

```java
import java.lang.classfile.ClassFile;
import java.lang.classfile.ClassHierarchyResolver;

// targetLoader is provided beforehand by the test environment.
ClassFile cf = ClassFile.of(
        ClassFile.ClassHierarchyResolverOption.of(
                ClassHierarchyResolver.ofResourceParsing(targetLoader))
);
```

**The snippet above is not standalone runnable** because `targetLoader` must be declared by the test harness. For specialized loaders, you may need a composite resolver or metadata for generated classes not yet present in resources.

**Caution when calling from `ClassFileTransformer`:** If the verifier or resolver attempts `Class.forName` or loads a class currently being defined, recursive loading, `ClassCircularityError`, `LinkageError`, or deadlocks on class-loading locks can occur. Therefore, running intensive verification in **CI/integration tests** or using a metadata-based resolver is a more practical choice than verifying every class while the JVM is loading under heavy load.

### Caching and Concurrency

`ClassHierarchyResolver.cached()` is **not thread-safe** by default. If sharing the same resolver across multiple callback threads, appropriate synchronization must be considered; furthermore, caching by name without considering loader or version can retain stale information after a redefine or redeploy.

**Do not conflate two issues:** A misconfigured resolver can cause incomplete verification results or report errors even when the input is valid in the target loader. Conversely, a correct resolver cannot save bytecode with invalid branch targets or stack maps.

## 6. JVM Phases and Potential Error Types

| Phase | What to Check | Common Error Types |
| --- | --- | --- |
| **Loading/definition** | Can the loader define the class from the bytes with the right binary name? | `ClassFormatError`, `UnsupportedClassVersionError`, `NoClassDefFoundError` |
| **Verification** | Are types, stack, frames, and bytecode rules valid on the JVM? | `VerifyError` |
| **Resolution/linking** | Do method/field/class references actually exist and are they accessible? | `NoSuchMethodError`, `NoClassDefFoundError`, `IllegalAccessError`, `IncompatibleClassChangeError` |
| **Initialization** | Does `<clinit>` complete properly? | `ExceptionInInitializerError`, deadlock |
| **Execution** | Are return values, exceptions, and side effects correct? | Business errors, `AssertionError`, timeout |
| **Deployment** | Do artifact, JDK, agent, modules, and config match the real environment? | Bugs not reproducible in unit tests |

The JVM may perform **lazy symbolic resolution**; `ClassLoader.defineClass(...)` is not required to resolve every method reference in unexecuted code. A class can be loaded, `Class.forName(..., true, loader)` can initialize it, yet a rarely taken branch that has not been called can still cause `NoSuchMethodError` later.

Therefore, you must **execute critical code paths**, not just obtain a `Class<?>` and print `"PASS"`.

### `defineClass`, `Class.forName`, and `Method.invoke` Serve Different Checks

- `defineClass(name, bytes, 0, bytes.length)` defines the specific class under a **defining loader** you control.
- `Class.forName(name, true, loader)` forces lookup through that loader and requires **initialization**.
- `getMethod` checks that the public method exists with the required name and parameter types.
- `Method.invoke` runs the method and lets you test the return value. If the target method throws an exception, reflection wraps it in `InvocationTargetException`, so you must inspect `getCause()`.
- Running a **fresh JVM process** with `-cp` pointing strictly to the target artifact is an additional deployment check: it ensures you do not accidentally use a `Class<?>` already loaded in the old test runner.

A single load in a custom loader does not replace testing with the **actual defining loader and module graph of production**. The lab is only a runnable foundation.

## 7. Java 24+ Lab: source → verify → load → run → fresh JVM

The lab requires only the JDK—no ASM, Byte Buddy, or agent. It builds a candidate classfile using the Class-File API and verifies it in three ways:

1. Compile the `Calculator` class with `javac`.
2. Parse and `verify(ClassModel)` the source model.
3. `transformClass(model, ClassTransform.ACCEPT_ALL)` to produce a new candidate.
4. `verify(byte[])` the candidate.
5. Write the actual `.class` file and `verify(Path)`.
6. Corrupt the magic header of a copy to verify the parser rejects malformed input.
7. Load the candidate into an isolated loader, initialize it, and run success/edge/exception paths.
8. Launch a fresh JVM with `-Xverify:all`, load the written file, and test the return value.

### 7.1. File Structure

```text
verify-then-run/
├── src/
│   ├── demo/sample/Calculator.java
│   ├── demo/run/FreshJVM.java
│   └── VerifyAndRun.java
└── out/                    # created by build commands
    ├── original/
    ├── verifier/
    ├── runner/
    └── checked/
```

**Important:** When running `VerifyAndRun`, the runtime classpath **must not contain `out/original`**. If you accidentally put both versions of `Calculator.class` on the classpath, parent delegation or classpath order may cause the test to load the wrong version.

### 7.2. `src/demo/sample/Calculator.java`

```java
package demo.sample;

public final class Calculator {
    private Calculator() {
    }

    public static int twice(int number) {
        if (number < 0) {
            throw new IllegalArgumentException("negative input");
        }
        return number * 2;
    }
}
```

Two success cases to check:

- `twice(21) == 42`.
- `twice(0) == 0`.

For `twice(-1)`, the method must throw `IllegalArgumentException` with the message `"negative input"`. Do not rely on the verifier to infer this business contract: the verifier only analyzes classfile/bytecode structure, whereas the meaning of `twice` must be defined by tests.

### 7.3. `src/VerifyAndRun.java`

```java
import java.lang.VerifyError;
import java.lang.classfile.ClassFile;
import java.lang.classfile.ClassModel;
import java.lang.classfile.ClassTransform;
import java.lang.reflect.InvocationTargetException;
import java.lang.reflect.Method;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.List;

public final class VerifyAndRun {
    private static final String NAME = "demo.sample.Calculator";

    private static final class IsolatedLoader extends ClassLoader {
        IsolatedLoader() {
            super(ClassLoader.getPlatformClassLoader());
        }

        Class<?> define(String name, byte[] bytes) {
            return defineClass(name, bytes, 0, bytes.length);
        }
    }

    private static void assertVerified(
            String stage, List<VerifyError> errors) {
        if (!errors.isEmpty()) {
            for (VerifyError error : errors) {
                System.err.println(stage + ": " + error);
            }
            throw new AssertionError(
                    stage + ": verification failed");
        }
        System.out.println(stage + ": verify=PASS");
    }

    private static void assertNegativePath(Method method)
            throws Exception {
        try {
            method.invoke(null, -1);
            throw new AssertionError(
                    "Expected IllegalArgumentException");
        } catch (InvocationTargetException wrapper) {
            Throwable cause = wrapper.getCause();
            if (!(cause instanceof IllegalArgumentException)
                    || !"negative input".equals(cause.getMessage())) {
                throw new AssertionError(
                        "Unexpected target exception", cause);
            }
        }
        System.out.println(
                "runtime: twice(-1)=IllegalArgumentException");
    }

    public static void main(String[] args) throws Exception {
        if (args.length != 2) {
            throw new IllegalArgumentException(
                    "Usage: VerifyAndRun <source.class> <output-root>");
        }

        Path source = Path.of(args[0]);
        Path outputRoot = Path.of(args[1]);

        ClassFile cf = ClassFile.of();
        byte[] input = Files.readAllBytes(source);

        // 1. Verify the parsed model.
        ClassModel model = cf.parse(input);
        assertVerified("source", cf.verify(model));

        // 2. Reconstruct class bytes via the Class-File API.
        byte[] candidate =
                cf.transformClass(model, ClassTransform.ACCEPT_ALL);
        assertVerified("generated", cf.verify(candidate));

        // 3. Verify the exact artifact written to disk.
        Path output = outputRoot.resolve(
                "demo/sample/Calculator.class");
        Files.createDirectories(output.getParent());
        Files.write(output, candidate);
        assertVerified("disk", cf.verify(output));

        // 4. Negative control: corrupt the magic header.
        byte[] broken = candidate.clone();
        broken[0] = 0;
        try {
            cf.parse(broken);
            throw new AssertionError(
                    "Malformed input should have failed");
        } catch (IllegalArgumentException expected) {
            System.out.println(
                    "negative: malformed-header=rejected");
        }

        // 5. Load the EXACT candidate into an isolated loader.
        IsolatedLoader loader = new IsolatedLoader();
        Class<?> defined = loader.define(NAME, candidate);
        if (defined.getClassLoader() != loader) {
            throw new AssertionError("Wrong defining loader");
        }

        Class<?> initialized = Class.forName(NAME, true, loader);
        if (initialized != defined) {
            throw new AssertionError("Wrong class identity");
        }
        System.out.println("runtime: loader=isolated");

        // 6. Invoke the actual method and verify logic.
        Method method = defined.getMethod("twice", int.class);
        Object answer = method.invoke(null, 21);
        if (!Integer.valueOf(42).equals(answer)) {
            throw new AssertionError("Wrong result: " + answer);
        }
        System.out.println("runtime: twice(21)=42");

        Object zero = method.invoke(null, 0);
        if (!Integer.valueOf(0).equals(zero)) {
            throw new AssertionError("Wrong zero result: " + zero);
        }
        System.out.println("runtime: twice(0)=0");

        assertNegativePath(method);
        System.out.println("integration: PASS");
    }
}
```

**Explanation of key points:**

- `ClassFile.of()` uses default options, suitable for the lab's very simple class with no external hierarchy.
- `cf.parse(input)` can throw `IllegalArgumentException` if the classfile is malformed or its version is unsupported by the current JDK.
- `ClassTransform.ACCEPT_ALL` passes elements to the builder and does **not** inject probes; the candidate is a classfile reconstructed from the model.
- `assertVerified` takes the error list and **fails the test** if the list is non-empty, rather than continuing with invalid bytes.
- `Files.write` writes the classfile to the exact path derived from its binary name, then `verify(Path)` checks the **data on disk**.
- The negative control creates a copy and alters the first magic byte; `cf.parse` is expected to reject the corrupted header with `IllegalArgumentException`. Do not treat this negative test as a `verify` overload.
- `IsolatedLoader` uses the platform loader as its parent, so there is no `Calculator` in the application/system loader; `defineClass` receives the **exact candidate**.
- `Class.forName(NAME,true,loader)` forces class initialization and checks identity; if called on a class already loaded in another loader, the identity check will catch it.
- `Method.invoke` wraps business exceptions in `InvocationTargetException`. The negative path test must inspect `wrapper.getCause()`.
- `Integer.valueOf(42).equals(answer)` checks the actual return value, not just the method signature.
- The program prints `integration: PASS` only if all preceding steps succeed. If `NoSuchMethodError`, `VerifyError`, or `AssertionError` occurs, the process does not pretend to succeed.

### 7.4. `src/demo/run/FreshJVM.java`

```java
package demo.run;

import demo.sample.Calculator;

public final class FreshJVM {
    public static void main(String[] args) {
        int value = Calculator.twice(21);
        if (value != 42) {
            throw new AssertionError(
                    "Wrong result: " + value);
        }
        System.out.println(
                "fresh-jvm: twice(21)=" + value);
    }
}
```

This file compiles against the **original class's API**, but at runtime it uses the `.class` verified by `verify(Path)` in `out/checked`. Because it runs in a fresh JVM process, there is no risk that a same-named `Calculator` class was already loaded by the test runner. You can add exception-path tests in the fresh JVM if needed; the goal here is to confirm **fresh classpath resolution**.

### 7.5. Build/Run on Bash (Linux/macOS/Git Bash)

In the `verify-then-run` directory, using JDK 24+:

```bash
mkdir -p out/original out/verifier out/runner out/checked

javac -encoding UTF-8 -d out/original \
    src/demo/sample/Calculator.java

javac -encoding UTF-8 -d out/verifier \
    src/VerifyAndRun.java

javac -encoding UTF-8 -cp out/original -d out/runner \
    src/demo/run/FreshJVM.java

java -cp out/verifier VerifyAndRun \
    out/original/demo/sample/Calculator.class out/checked

java -Xverify:all -cp out/runner:out/checked \
    demo.run.FreshJVM
```

Order matters: the runner needs `Calculator` at **compile time**, but the runtime classpath only contains `out/runner` and `out/checked`, **not** `out/original`. Unix paths use `:` to separate multiple classpath entries.

```powershell
New-Item -ItemType Directory -Force `
```

### 7.7. Expected Stdout

With JDK 24+ able to read the compiled classfile and no other environment/agent interference:

```text
source: verify=PASS
generated: verify=PASS
disk: verify=PASS
negative: malformed-header=rejected
runtime: loader=isolated
runtime: twice(21)=42
runtime: twice(0)=0
runtime: twice(-1)=IllegalArgumentException
integration: PASS
fresh-jvm: twice(21)=42
```

The first three lines test the `ClassFile.verify` overloads. The negative line confirms the parser rejects a corrupted header. The four runtime lines check loader identity, success, zero, and failure paths; the integration line appears only when all assertions pass. The `fresh-jvm` line comes from the **second java command**, i.e., a separate JVM.

If the runner encounters an error, you will see stderr and a non-zero exit code instead of the expected output; preserve the stack trace to fix the root cause. Do not use "sample stdout" as proof that the program ran successfully when it has not actually been executed.

## 8. Why Is `-Xverify:all` Still Not Enough?

`-Xverify:all` instructs the JVM to verify classes within the scope of what gets loaded. However:

- It does not force the application to execute all methods or branches.
- Certain dependency errors only surface when a symbolic reference is resolved along a specific code path.
- It has no knowledge of the business contract `twice(x)==2*x`.
- It does not test overhead or concurrency side effects.
- It does not guarantee the file on the classpath is the same verified build artifact if deployment replaced the artifact.

Therefore, run the **JVM verifier** and **functional tests** together. In CI, you can separate static verification and JVM smoke tests into two stages to catch errors earlier. For large systems, integration tests should use the same JDK vendor/version and the same agent/classloader/module graph as production.

### What Negative Tests Should Be Added?

Do not test only a corrupted magic header; add safe fixtures in the test environment:

- A classfile with a `StackMapTable` inconsistent with control flow.
- A branch offset not aligned on an instruction boundary.
- `invokestatic` to a non-existent method (bytecode may parse, but runtime resolution fails).
- A helper package invisible via a custom loader (to catch `NoClassDefFoundError`).
- A method with `try/finally` that throws an exception, to detect probes swallowing the original exception.
- A class to redefine where the replacement makes a forbidden schema change.
- A generated class major version too new for the target runtime.
- Tests inside a named module missing `requires`/`exports`/`opens` edges.

**Note:** Negative test cases must be created in a test environment; never intentionally feed corrupted classfiles into a production JVM. A test can assert the exact error type or at least assert that the process **fails**, though exact JVM error messages may vary across vendors/versions.

## 9. For a Real Java Agent, What Else Should Be Tested Beyond the Lab?

### 9.1. Instrumentation Helper Resolution

Transformers often inject instructions such as:

```text
invokestatic com/example/agent/bridge/ProbeBridge.hit:()V
```

This is a **method reference descriptor**, not Java source. The JVM class loader of the instrumented class must be able to find the helper. If the helper resides in the system loader while the target class only delegates to bootstrap/platform, a classfile can pass `verify`, yet invocation fails with `NoClassDefFoundError`.

For named modules, JPMS read edges and visibility are also required. Test across **real** loaders and modules; do not just run the application on the system classpath in a lab.

### 9.2. Runtime Semantic Preservation

In instrumented methods, test:

- Normal returns and early returns.
- Checked/unchecked exceptions preserve their type and message.
- `finally` executes exactly once.
- Return values and side effects are unaltered.
- Probes are not invoked twice for a single request.
- Control flow is not altered when a method has synchronized blocks/monitors.
- Heavy network I/O is not introduced into the hot path.
- Class-loading recursion is not triggered when helpers, loggers, or exporters are instrumented.
- Sensitive data is not written into unauthorized event payloads.

A valid stack map cannot prove these business invariants.

### 9.3. Bytecode Integrity Across Multiple Transformers

Multiple Java agents, native JVMTI hooks, or redefinitions can form a chain:

```text
source bytes → A → B → C → JVM
```

A direct unit test of A does not know whether B or C will re-insert instructions or corrupt metadata. You must integrate with the **exact order of agents and JVM**. If a transformer returns `null`, it means "leave the current output unchanged," not "roll back the previous transformer's output."

### 9.4. Redefinition / Retransformation

A classfile eligible for **fresh loading** is not necessarily eligible to **redefine** an existing class:

- `Instrumentation.isRedefineClassesSupported()` and `isModifiableClass(target)` must align.
- The replacement must not arbitrarily add/remove fields or methods, change descriptors, or alter the superclass/interfaces.
- Registered Java transformers may still be invoked during redefine.
- `retransformClasses` does not accept replacement `byte[]` directly like redefine does.
- Active method frames may continue executing old bytecode; only new invocations use the new version.
- Static state does not automatically reset, and class initializers do not automatically re-run.

Thus, testing `ClassFile.verify(candidate)` is only the opening step; you must still invoke the actual API on a test JVM and inspect responses, errors, and runtime behavior afterward.

## 10. Diagnosing Verification or Runtime Failures

| Symptom | Common Cause | Resolution |
| --- | --- | --- |
| `parse(...)` throws `IllegalArgumentException` | Malformed classfile or unsupported version | Inspect source bytes, header/version, parser |
| `verify(...)` returns a non-empty list | Invalid stack types, frames, instructions, or attributes | Print all errors, compare `javap -v`, check method offset |
| `verify(Path)` throws `IOException` | Incorrect file path or permissions | Fix test artifact; do not misattribute as a bytecode bug |
| Verify reports hierarchy-related errors | Default resolver cannot see custom loader classes | Supply an appropriate hierarchy resolver |
| `UnsupportedClassVersionError` | Runtime JVM is older than the classfile major version | Compile/generate with the appropriate `--release` |
| `ClassFormatError` | Classfile format rejected by the JVM | Compare final bytes hash, check constant pool/attributes |
| JVM `VerifyError` | Invalid stack-map, dataflow, or type safety | Dump exact bytes, run `-Xverify:all`, inspect frames |
| `NoClassDefFoundError` | Missing dependency/helper or resolution failure | Check loader, module, JAR, and load timing |
| `NoSuchMethodError` | Helper method descriptor/ABI changed | Run `javap -p -s`, compare against runtime JAR |
| `IllegalAccessError` | Package, module, or access flags forbid access | Check exports/reads/opens and defining loader |
| `ExceptionInInitializerError` | Static initializer failed | Test `Class.forName(...,true,loader)` |
| `InvocationTargetException` | Invoked method threw an exception | Inspect cause, verify against contract |
| Tests pass on CI but fail on server | Different JDK, classpath, custom loader, or agent order | Reproduce exact deployment and artifact |
| Bytecode tests pass but logic is wrong | Branch/return/side-effect semantics bug | Add golden tests covering multiple code paths |
| JVM is slow despite passing verify | Allocation, locking, or exporter blocking | JFR/profile/benchmark with vs. without instrumentation |
| Fails only on redeploy | Class-loader leak or stale cache | Log defining loader and lifecycle |

### How Should `javap` Be Used?

For example, after writing the candidate:

```bash
javap -v -p out/checked/demo/sample/Calculator.class
```

`javap -v` displays the constant pool, bytecodes, `StackMapTable`, exception tables, and metadata. When an error belongs to a specific method, compare the versions **before and after** transformation, rather than looking only at Java source. To view method descriptors:

```bash
javap -p -s out/checked/demo/sample/Calculator.class
```

Preserve class-loader/module/runtime context when comparing, because a symbolic reference can be valid in loader A yet fail to resolve in loader B.

## 11. Where to Place Verification in an Agent Product?

**Best in build/test:** Collect classfile fixtures, run the transform, verify the output, and spin up test JVMs with real versions. This catches bugs before deployment and avoids slowing down production startup.

**Possible in integration tests:** When multiple agents or classloaders are involved, launch a separate JVM with the real `-javaagent` and test the final output. Diagnostics can be enabled and debug artifacts saved in a protected area.

**Use caution in production callbacks:** `ClassFileTransformer.transform(...)` runs during class loading and can execute concurrently on multiple threads. `ClassFile.verify` with the default hierarchy resolver may attempt reflection or load additional classes while the JVM holds locks. Invoking a heavy verifier for every class can increase latency, GC pressure, or cause recursion/deadlock.

An agent running on JDK 17 also **cannot** rely on the standard JDK 24 Class-File API inside its callback; when needed, use tooling appropriate for that JDK, or run verification on JDK 24+ in CI while still testing the bytecode under the target JVM.

### CI Checklist

1. Generate class bytes from the exact source and transformer version.
2. Confirm the classfile major version is compatible with the target JDK.
3. Parse/verify inputs when needed.
4. Verify the **generated bytes**, not just the source.
5. Write the artifact and verify the saved file.
6. Attach the hash/artifact identifier to the test report.
7. Test `defineClass` in an isolated/target loader.
8. Test `Class.forName(...,true,loader)` and method/exception paths.
9. Run a fresh JVM with the exact artifact.
10. Test with the deployment's agent/loader/module graph.
11. Test counters, probe call frequency, and exception propagation.
12. Benchmark startup, CPU, memory/GC, and latency.
13. Check policies for PII/secrets and output data.
14. If the runtime/JVM reports an error, CI must fail rather than merely log warnings.
15. Do not release a new artifact if verifier or runtime regression steps were skipped.

## 12. Common Misconceptions

**1. “`ClassFile.verify` returning an empty list means the class runs correctly.”**  
No. It only indicates no verification errors were detected in the context used.

**2. “`parse(bytes)` returning a `ClassModel` means every attribute is valid.”**  
No. The Class-File API parses lazily; accessors or verification may uncover errors later.

**3. “The verifier catches all missing dependencies.”**  
No. Loader/module visibility and runtime symbolic resolution still require JVM tests.

**4. “`ClassFile.verify` is available in JDK 17.”**  
No. The standard API was introduced in JDK 24; that is the minimum requirement for the lab.

**5. “`ClassTransform.ACCEPT_ALL` already injects instrumentation.”**  
No. It preserves elements and is used in the lab to reconstruct bytes.

**6. “Loading a class means all method references have been resolved.”**  
No. The JVM uses lazy resolution; an uncalled branch can still fail.

**7. “`-Xverify:all` tests business logic.”**  
No. It is a JVM verification option; assertions are still required.

**8. “The class in the runtime JAR is always identical to the file I just verified.”**  
Not automatically. Check artifacts/hashes and avoid duplicate classes on the classpath.

**9. “The default hierarchy resolver always works with plugin loaders.”**  
No. It relies on the system loader and reflection, so it may miss plugin-specific class metadata.

**10. “A classfile valid for loading can definitely be redefined.”**  
No. Redefinition has its own schema and capability restrictions.

**11. “`NoSuchMethodError` proves `ClassFile.verify` is broken.”**  
Not necessarily. It may be due to a runtime ABI/helper version mismatch.

**12. “A single test run on Java 24 is enough for a JDK 17 server.”**  
No. JDK 17 has different classfile limits and class loader/module/dependency environments.

**13. “An exception thrown by a method means a JVM VerifyError.”**  
No. `IllegalArgumentException` from a business method is a business exception; the verifier does not eliminate it.

**14. “Writing direct unit tests for the transformer alone is enough.”**  
No. Integration tests with the actual chain, JVM, helpers, and loaders are needed before release.

**15. “JVM verification should be disabled to avoid VerifyError.”**  
No. That hides bytecode bugs and introduces risk; fix the classfile and stack maps instead.

## 13. Self-Check Questions

**1.** What do the overloads of `ClassFile.verify` accept?  
**Answer:** `ClassModel`, `byte[]`, and `Path`, returning `List<VerifyError>`.

**2.** When should you verify `Path` instead of only `byte[]`?  
**Answer:** After writing the artifact, to avoid checking a byte array that differs from the deployed file.

**3.** Why can `parse` succeed while `verify` still reports errors?  
**Answer:** Parsing is lazy and does not perform full verification upfront.

**4.** Does `ClassFile.verify` execute `Calculator.twice(21)`?  
**Answer:** No. You must load the class and invoke the method.

**5.** Why does the lab use an isolated loader?  
**Answer:** To prove the verified candidate bytes are actually defined, rather than accidentally loading a copy from the system classpath.

**6.** What check does `Class.forName(...,true,loader)` add?  
**Answer:** It forces initialization in the chosen loader.

**7.** Why must `Method.invoke` catch `InvocationTargetException`?  
**Answer:** It is the wrapper around exceptions thrown by the target method.

**8.** Why does the lab use an additional fresh JVM?  
**Answer:** To test the artifact loaded from disk/classpath in an independent process, without reusing classes already loaded in the previous runner.

**9.** Can `NoClassDefFoundError` occur even when the static verifier passes?  
**Answer:** Yes, because the runtime loader may fail to locate a dependency or helper.

**10.** What issue does the default hierarchy resolver have with plugin loaders?  
**Answer:** It uses the system loader and reflection, so it may not see plugin-private classes.

**11.** Does `redefineClasses` accept every classfile that passes verify?  
**Answer:** No. Schema restrictions, class modifiability, and capabilities also apply.

**12.** Why not verify every class directly inside a transformer callback?  
**Answer:** Cost and the risk of class-loading recursion/deadlock, especially when hierarchy resolution is needed.

**13.** If JDK 24 generates a new classfile, can a JDK 17 JVM run it?  
**Answer:** Only if the classfile version and features are compatible with JDK 17; typically you must build with `--release 17` and test on JDK 17.

**14.** Why is `ClassTransform.ACCEPT_ALL` insufficient to prove code injection?  
**Answer:** It adds no bytecode; proving instrumentation requires a real transformer and runtime tests.

**15.** What details should be recorded when diagnosing a classfile failure?  
**Answer:** Exact candidate hash, JDK version, loader/module, transform chain, verify errors, JVM stack trace, and runtime test outcome.
