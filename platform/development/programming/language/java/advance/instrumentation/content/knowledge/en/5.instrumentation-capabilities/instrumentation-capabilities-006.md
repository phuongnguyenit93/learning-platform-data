# Primitive classes, array classes, and unmodifiable classes in Java Instrumentation

When building a Java agent to observe, profile, or modify the bytecode of a running JVM, you cannot assume that every `Class<?>` object can be **retransformed** or **redefined**. Two groups are always excluded: **primitive classes** (including the `Class` object representing `void`) and **array classes**. In addition, the JVM may have other special classes that cannot be modified.

This lesson belongs to the **Instrumentation Capabilities** topic, focusing on accurately identifying those kinds of classes, checking them with `Instrumentation.isModifiableClass(Class<?>)`, and distinguishing the modifiability of a **class** from support for a **bytecode modification operation**. After this lesson, you will know why `int[].class` cannot be retransformed yet you can still instrument a Java method that performs operations on arrays; how to handle `UnmodifiableClassException`; and how to filter targets before calling the instrumentation API.

## 1. A “Class” in Java is not always a .class file

`java.lang.Class<?>` can represent a class defined by bytecode, an interface, a primitive type, `void`, or an array class generated by the JVM. All of them have a `Class` object, but they do not share the same creation mechanism:

| Expression | `isPrimitive()` result | `isArray()` result | Nature |
| --- | --- | --- | --- |
| `int.class` | `true` | `false` | `Class` object representing primitive `int` |
| `Integer.TYPE` | `true` | `false` | Same `Class` object as `int.class` |
| `void.class` / `Void.TYPE` | `true` | `false` | `Class` object representing the pseudo-type `void` |
| `Integer.class` | `false` | `false` | Regular wrapper class `java.lang.Integer` |
| `int[].class` | `false` | `true` | One-dimensional array class with `int` elements |
| `int[][].class` | `false` | `true` | Two-dimensional array class with `int` elements |
| `String[].class` | `false` | `true` | Array class holding `String` references |
| `String.class` | `false` | `false` | Regular class, has a class file in the JDK |
| `Runnable.class` | `false` | `false` | Regular interface |

In the expression `int[].class`, the word `class` does not mean there is an `int[].class` file generated by `javac`. The JVM creates array classes according to its own rules. Similarly, the primitive type `int` does not have the bytecode of a regular class that an agent can replace.

Easily confused pairs:

- `int.class == Integer.TYPE` is `true`, whereas `int.class == Integer.class` is `false`.
- `Integer[].class` is also an array class, even though its element type `Integer` is a regular class.
- `String.class` and `String[].class` are **two** different `Class` objects. Whether the `String` class is modifiable does not determine whether the `String[]` array class is modifiable.
- The types `byte`, `short`, `int`, `long`, `float`, `double`, `char`, `boolean`, and `void` are all identified by `Class.isPrimitive()`.

## 2. The contract of Instrumentation.isModifiableClass()

The method:

~~~java
boolean isModifiableClass(Class<?> theClass)
~~~

answers the question: **“Is this class considered modifiable by the JVM for retransformation or redefinition?”** No bytecode transformation or attachment is performed when merely calling this check method.

Important rules in the Java Instrumentation API:

1. If it returns `false`, that class **cannot** be retransformed or redefined via the corresponding APIs.
2. If it returns `true`, the class **passes the modifiability check**, but there is still no guarantee that the actual operation will succeed.
3. For **primitive classes** and **array classes**, the result is **always `false`** by API contract, regardless of JVM configuration.
4. `isModifiableClass(null)` throws `NullPointerException`; you must check for `null` in input-filtering code.
5. This value **does not depend** on whether the JVM currently supports retransformation or redefinition. Those two capabilities must be checked **separately**.

You can picture the two required verification steps as follows:

~~~text
Target class C
    |
    v
inst.isModifiableClass(C)?
    | false
    +----------> Do not attempt to modify C
    |
    | true
    v
What operation do you want to perform?
    |
    +--> retransform -> inst.isRetransformClassesSupported()?
    |
    +--> redefine ----> inst.isRedefineClassesSupported()?
                              |
                              v
                       Check bytecode modification
                       constraints before proceeding
~~~

**`isModifiableClass(C) == true` is not equivalent to `retransformClasses(C)` being guaranteed to succeed.** Having the capability, valid class bytes, and the kind of change permitted by the JVM are independent conditions.

### Distinguishing three questions

| Question | API | Meaning |
| --- | --- | --- |
| Can class `C` be modified by these two mechanisms in principle? | `isModifiableClass(C)` | Capability of **a specific class** |
| Does the JVM/agent currently support retransform? | `isRetransformClassesSupported()` | Capability **of the environment and agent** |
| Does the JVM/agent currently support redefine? | `isRedefineClassesSupported()` | Capability **of the environment and agent** |

For a Java agent, the two capabilities usually need to be declared in the manifest with `Can-Retransform-Classes: true` and `Can-Redefine-Classes: true`, and the JVM must actually support them. Manifest declarations cannot “unlock” the ability to modify primitive or array classes.

## 3. Primitive classes and array classes: two groups that are always unmodifiable

### 3.1. Primitive classes

The objects `boolean.class`, `byte.class`, `char.class`, `short.class`, `int.class`, `long.class`, `float.class`, `double.class`, and `void.class` do not represent regular classes with method bytecode to replace.

Example:

~~~java
boolean a = inst.isModifiableClass(int.class);       // false
boolean b = inst.isModifiableClass(Integer.TYPE);    // false
boolean c = inst.isModifiableClass(void.class);      // false
~~~

Instructions such as `iadd`, `iload`, or `ireturn` appear **inside a method of another class**. To measure `int` addition, an agent needs to instrument the **method performing the addition**, not modify `int.class`.

**Distinguishing from wrappers:** `java.lang.Integer` is a class with regular bytecode, so `Integer.class.isPrimitive()` returns `false`. However, you must not immediately conclude that `inst.isModifiableClass(Integer.class)` will be `true` on every JVM: you must query it at runtime. Even more importantly, you must not treat every JDK class as safe to modify.

### 3.2. Array classes

Array classes are created by the JVM based on element type and number of dimensions; they do not correspond to a standalone class file that an agent can retransform.

~~~java
boolean a = inst.isModifiableClass(int[].class);       // false
boolean b = inst.isModifiableClass(String[].class);    // false
boolean c = inst.isModifiableClass(long[][].class);    // false
boolean d = inst.isModifiableClass(Object[][][].class);// false
~~~

This applies to **all** array classes, including primitive arrays, object arrays, multidimensional arrays, and arrays whose element type is an interface. Even though `int[].class.isPrimitive()` is `false`, `int[].class.isArray()` is `true`, so it is still excluded. For `String[].class`, the determining factor is the **array class**, not whether `String.class` is modifiable.

Methods that perform operations on arrays still have bytecode that can be an instrumentation target:

| Operation | Commonly involved bytecode | Class the agent should target |
| --- | --- | --- |
| Create primitive array | `newarray` | Class containing the array creation instruction |
| Create object array | `anewarray` | Class containing the array creation instruction |
| Create multidimensional array | `multianewarray` | Class containing the array creation instruction |
| Read `int[]` element | `iaload` | Class containing the array read method |
| Write reference element | `aastore` | Class containing the array write method |
| Read array length | `arraylength` | Class containing the array access method |

Java example:

~~~java
public int total(int[] values) {
    int result = 0;
    for (int value : values) {
        result += value;
    }
    return result;
}
~~~

When instrumenting the `total` method, an agent can add timing measurement to the **bytecode of the class declaring `total`**, if that class is eligible. The agent does not need and cannot redefine `int[].class`. This is a crucial distinction between **instrumenting an operation that uses a type** and **instrumenting the class representing that type**.

## 4. What other classes might be unmodifiable?

In addition to the two always-excluded groups, the JVM TI Specification also mentions **a number of implementation-dependent classes** (*implementation-defined classes*) that cannot be modified. There is no fixed, portable list of class names that applies across all JDKs/JVMs. Therefore, **checking each `Class<?>` with `isModifiableClass` on the target JVM itself** is the right approach.

### 4.1. Hidden classes

JDK 15+ has hidden classes, created via `MethodHandles.Lookup.defineHiddenClass(...)`; Java 17+ provides `Class.isHidden()` to identify them. They commonly appear in the implementation of dynamic runtime features. On modern HotSpot, hidden classes **cannot be redefined or retransformed**. That is an important example of an unmodifiable class even though both `isPrimitive()` and `isArray()` are `false`.

~~~java
if (clazz.isHidden()) {
    // Do not include in the redefine/retransform target list.
}
~~~

The snippet above is a **candidate-filtering illustration**, not a standalone runnable program; `clazz` must be supplied by class-discovery code. Do not assume that **every** `synthetic` class is a hidden class or that every dynamically generated class is unmodifiable. For example, a class name containing `$$Lambda` is not a stable API contract for checking modifiability; use `isHidden()` and `isModifiableClass()`.

### 4.2. Final, record, enum, interface, and JDK library classes

Certain characteristics **do not automatically mean** unmodifiable:

- `final class`: `final` forbids inheritance in Java; it does not automatically mean `isModifiableClass == false`.
- `record`, `enum`, `sealed class`: have their own structural rules, but relying on these keywords alone is not enough to conclude retransform/redefine capability.
- Interface or abstract class: the JVM may support instrumenting eligible methods; each class must be checked individually.
- Classes loaded by the bootstrap class loader, such as `java.lang.String`: belonging to `java.*` does not automatically cause the API to mark them `false`; on a specific JVM they may be modifiable. Modifying core classes still carries wide-ranging risks and must be weighed independently of the boolean result.

You should separate three concepts: **class modifiability**, **class file structural rules**, and **module or system access permissions**. For instance, `Instrumentation.isModifiableModule(Module)` is a different API for querying whether module relationships can be expanded; it does not replace `isModifiableClass` and does not allow modifying primitive/array classes.

## 5. Java 17+ example: running an agent and verifying directly on the JVM

To call `Instrumentation.isModifiableClass`, you need an **Instrumentation instance** provided by the JVM to a Java agent via `premain` or `agentmain`. There is no public constructor for a regular application to create an instance itself. The following example uses `-javaagent` at startup, **only inspects metadata and triggers a controlled error on an array class**, without modifying application bytecode.

### 5.1. Create ModifiabilityProbe.java

~~~java
import java.lang.instrument.Instrumentation;
import java.lang.instrument.UnmodifiableClassException;

public final class ModifiabilityProbe {
    private static volatile Instrumentation instrumentation;

    public static void premain(String arguments, Instrumentation inst) {
        instrumentation = inst;
    }

    public static void main(String[] args) {
        Instrumentation inst = instrumentation;
        if (inst == null) {
            throw new IllegalStateException(
                    "Run with -javaagent:modifiability-probe.jar");
        }

        Class<?>[] examples = {
            int.class, void.class, int[].class, String[][].class
        };

        for (Class<?> type : examples) {
            System.out.printf(
                    "%s | primitive=%b | array=%b | modifiable=%b%n",
                    type.getTypeName(),
                    type.isPrimitive(),
                    type.isArray(),
                    inst.isModifiableClass(type));
        }

        System.out.println("ownClassModifiable="
                + inst.isModifiableClass(ModifiabilityProbe.class));
        System.out.println("retransformSupported="
                + inst.isRetransformClassesSupported());
        System.out.println("redefineSupported="
                + inst.isRedefineClassesSupported());

        if (inst.isRetransformClassesSupported()) {
            try {
                inst.retransformClasses(int[].class);
                System.out.println("arrayRetransform=unexpected-success");
            } catch (UnmodifiableClassException expected) {
                System.out.println(
                        "arrayRetransform=UnmodifiableClassException");
            }
        } else {
            System.out.println("arrayRetransform=not-attempted");
        }
    }
}
~~~

The program uses `getTypeName()` so array names are displayed as `int[]` or `java.lang.String[][]`, which is more readable than JVM names such as `[I`, `[[Ljava.lang.String;`.

### 5.2. Create the agent.mf file

Manifest contents:

~~~text
Manifest-Version: 1.0
Premain-Class: ModifiabilityProbe
Can-Retransform-Classes: true
Can-Redefine-Classes: true
~~~

Note that you must **end the manifest file with a blank line**. The two `Can-...: true` lines request capabilities for the agent; the JVM still decides whether it can satisfy them. The `ModifiabilityProbe` class has both `premain` and `main` so the same program serves as both the agent and the sample application, avoiding the need for a separate project.

### 5.3. Compile, package, and run

Place `ModifiabilityProbe.java` and `agent.mf` in the same directory. Run with JDK 17+:

~~~bash
javac ModifiabilityProbe.java
jar --create --file modifiability-probe.jar --manifest agent.mf ModifiabilityProbe.class
java -javaagent:modifiability-probe.jar -cp . ModifiabilityProbe
~~~

**Example stdout from a successful run on HotSpot JDK 24:**

~~~text
int | primitive=true | array=false | modifiable=false
void | primitive=true | array=false | modifiable=false
int[] | primitive=false | array=true | modifiable=false
java.lang.String[][] | primitive=false | array=true | modifiable=false
ownClassModifiable=true
retransformSupported=true
redefineSupported=true
arrayRetransform=UnmodifiableClassException
~~~

**The first four lines** with `modifiable=false` are the normative part for primitive/array types. **The three capability/`ownClassModifiable` lines** depend on the JVM and agent configuration, so do not treat the entire output above as fixed across all environments. If the JVM does not support retransformation, the program will print `arrayRetransform=not-attempted`. The `catch` block catches specifically `UnmodifiableClassException`; it does not mask other unexpected errors.

You can remove the `retransformClasses(int[].class)` block entirely to turn the example into a **read-only** tool, because `isModifiableClass(int[].class)` returning `false` already proves that the array class is not allowed to be modified.

### 5.4. Why must it be run with -javaagent?

The line:

~~~java
public static void premain(String arguments, Instrumentation inst)
~~~

is the entry point that the JVM calls when processing `Premain-Class` in the manifest. The JVM supplies the `Instrumentation` parameter before running `main`. If you only run `java ModifiabilityProbe` without `-javaagent`, the static field is not initialized and the program intentionally throws an error. Running the code in an IDE also requires configuring the corresponding VM options.

## 6. Filtering eligible classes before retransforming

When an agent wants to process many classes, do not blindly pass `inst.getAllLoadedClasses()` to `retransformClasses(...)`. The list of loaded classes **is not a list of modifiable classes**.

In Java 21, `Instrumentation.getAllLoadedClasses()` is documented as returning all loaded classes/interfaces, **including array classes and hidden classes**. According to the JVM TI Specification, primitive classes are not included in that loaded classes list; the absence of primitives from the list **does not mean** `isModifiableClass(int.class)` will return `true`.

The filtering pattern below is a **logic snippet running inside an agent that already has `Instrumentation inst`**, not a standalone Java class:

~~~java
if (!inst.isRetransformClassesSupported()) {
    System.out.println("JVM/agent does not support retransformation");
    return;
}

java.util.List<Class<?>> accepted = new java.util.ArrayList<>();
for (Class<?> candidate : inst.getAllLoadedClasses()) {
    if (candidate == null) {
        continue;
    }
    if (candidate.isPrimitive() || candidate.isArray()) {
        continue;
    }
    if (!inst.isModifiableClass(candidate)) {
        continue;
    }

    // Practical target filtering conditions should go here:
    // package, class loader, class name, application scope...
    accepted.add(candidate);
}

System.out.println("Candidates allowed by preflight: "
        + accepted.size());
~~~

Meaning:

1. Check the operation capability **before** preparing retransformation.
2. Exclude special types guaranteed by contract to be unmodifiable.
3. Still check `isModifiableClass` for **every** remaining class, because the JVM may have other unmodifiable classes.
4. Filter further by **application scope**: select only classes you need to observe, avoiding touching the entire runtime.
5. If actual retransformation is needed, register an appropriate transformer, then call `inst.retransformClasses(...)` on the selected list and handle errors. The example above only **counts candidates** and does not retransform any class yet.

Filtering `isHidden()` and `isArray()` alone is not enough; even regular classes can be marked unmodifiable by the JVM. Conversely, there is no need to guess upfront by package name which classes are strictly unmodifiable: use the runtime result to decide.

## 7. Further hurdles: a modifiable class can still fail to be modified

Suppose `inst.isModifiableClass(MyService.class)` returns `true` and the retransformation capability is also `true`. Bytecode replacement can still fail if the transformation violates the JVM TI contract.

### 7.1. Retransformation and redefinition are two different operations

| Operation | API | Role |
| --- | --- | --- |
| Retransformation | `retransformClasses(Class<?>...)` | Re-runs the transformer chain on already-loaded classes, following rules for reusing/applying existing transformations |
| Redefinition | `redefineClasses(ClassDefinition...)` | Supplies new class bytecode to replace the definition of already-loaded classes |
| Load-time transformation | `addTransformer(...)` | Can process bytecode when the JVM **defines a new class**, before the class is created |

Primitive and array classes are not regular classes with bytecode files fed into the redefinition/retransformation mechanism; **there is no valid way to use `redefineClasses` to “add a method to `int[].class`”**.

Note that load-time transformation and retransform/redefine **are not the same check**. `isModifiableClass` describes whether an **already existing** class can be modified via retransform or redefine; it is not a blanket toggle for all transformers at class load time.

### 7.2. You cannot arbitrarily change class structure

According to Java 21 JVM TI, common restrictions on retransformation/redefinition include:

- You can change **method bodies**, the constant pool, and attributes within permitted limits.
- You cannot add, remove, or rename fields/methods; you cannot change method signatures, modifiers, or inheritance relationships.
- You cannot change `NestHost`, `NestMembers`, `Record`, or `PermittedSubclasses` attributes.
- The resulting bytecode must still be well-formed and pass JVM verification; instructions and stack frames must be compatible.

For example, adding logging to the **body** of `OrderService.process()` can be a valid target if the class is modifiable and the transformer produces valid bytecode. Trying to add a new field `private int counter;` to an **already-loaded** class via retransform is a structural change disallowed under the limits above, even when `isModifiableClass(OrderService.class)` returned `true`.

If a method currently has an active execution frame, a redefinition change does not necessarily alter the bytecode of that frame immediately; new calls use the new version according to JVM rules. Redefining a class also does not automatically re-run its static initializer. These issues are distinct from the modifiability question.

## 8. Exceptions and diagnostic workflow

| Observation or error | Possible cause | Resolution step |
| --- | --- | --- |
| `isModifiableClass(int.class) == false` | Primitives are always unmodifiable | Instrument the class containing the operation using `int` |
| `isModifiableClass(String[].class) == false` | Array classes are always unmodifiable | Instrument where the array is created/read/written |
| `isModifiableClass(SomeClass.class) == false` | The JVM marks the class as unmodifiable | Exclude from the list; find another instrumentation point |
| `isModifiableClass(null)` throws `NullPointerException` | Input is `null` | Validate input before calling |
| `isRetransformClassesSupported() == false` | JVM/agent capability is missing | Check manifest, JVM implementation, load-time strategy |
| `UnmodifiableClassException` | A class requested for modification is unmodifiable | Check each target with `isModifiableClass` |
| `UnsupportedOperationException` | Missing capability or change exceeds permitted limits | Check capability flags and class structure changes |
| `ClassFormatError` | Class bytes are malformed | Inspect output of the transformer/bytecode generator |
| `NoClassDefFoundError` during redefine/retransform | Class name in bytecode does not match the target class | Preserve the exact internal name and target definition |
| `isModifiableClass == true` but transformer changes nothing | Transformer returns `null`, is not registered properly, or is not invoked in the current step | Check transformer logic, `canRetransform`, load/retransform timing |

When calling `retransformClasses` or `redefineClasses` for multiple classes and one class is unmodifiable, the method throws an exception per contract; if a retransform/redefine call fails, no class **in that call** is successfully modified. Ensure the target list is valid before calling, while still preparing error handling because classes/configuration and runtime state can change.

**Do not treat the result of `isModifiableClass` as a license to modify just any class.** It is only a technical check of the target's modifiability; whether you should instrument core classes, security-sensitive classes, or third-party library classes also depends on purpose, compatibility, and testability.

## 9. Target selection decision diagram

~~~text
Have Class<?> target?
    |
    +-- null -----------------> Skip / report invalid input
    |
    +-- target.isPrimitive() -> Cannot modify primitive class
    |
    +-- target.isArray() ----> Cannot modify array class
    |
    v
inst.isModifiableClass(target)?
    |
    +-- false ---------------> Exclude; may be hidden/VM-defined...
    |
    +-- true ----------------> Check capability for the operation
                                  |
                                  v
                            Choose valid transformer/bytecode
                                  |
                                  v
                            Modify only classes within scope
                                  |
                                  v
                            Execute, handle errors, measure results
~~~

The key takeaway is to select the right **class containing the bytecode you want to observe**. When the target involves integers or arrays, you usually must instrument the method operating on that data; `int.class` or `String[].class` is not an object to put into a retransformation list.

## 10. Self-check exercises

**Question 1.** Are `Integer.TYPE` and `Integer.class` the same `Class<?>`? Which one is guaranteed to be unmodifiable?

**Question 2.** `String.class` on a JVM returns `isModifiableClass == true`. Can you deduce from this that `String[].class` is also modifiable?

**Question 3.** `inst.isModifiableClass(MyService.class) == true`, but `inst.isRetransformClassesSupported() == false`. Can `retransformClasses(MyService.class)` be called successfully?

**Question 4.** When you want to add a check before the operation `values[i] = 10` in an already-loaded Java method, should you modify `int[].class` or the class declaring the method that contains the `iastore` instruction?

**Question 5.** Is a class marked `final` or `record` inherently impossible to retransform? What if you want to add a new field via retransform when the class is already loaded?

**Question 6.** Why can the following code fail even when the list contains all classes currently loaded by the JVM?

~~~java
inst.retransformClasses(inst.getAllLoadedClasses());
~~~

**Answers:**

1. They are different. `Integer.TYPE == int.class`, which is a primitive class and **guaranteed to be unmodifiable**; `Integer.class` is a wrapper class and must be queried with `isModifiableClass`.
2. **No.** `String[].class` is an array class, so the result is always `false`.
3. **No.** The retransformation capability is required; the class's modifiability boolean alone is not enough.
4. Instrument the **class containing the method** that uses the `iastore` instruction, after checking conditions; do not modify the array class.
5. `final`/`record` does not automatically mean `false`. Even if the class is modifiable, **adding a new field** to an already-loaded class is a structural change beyond the retransform/redefine limits described above.
6. `getAllLoadedClasses()` can contain array/hidden classes and many unmodifiable classes; additionally, capabilities may be missing, the scope is too broad, and bytecode safety is not guaranteed. You must filter and select targets before operating.
