# Output of the Previous Transformer Becomes Input to the Next Transformer

In Java Instrumentation, when multiple `ClassFileTransformer` instances process **a single class definition**, the JVM applies the transformations as a **sequential chain** (*transformation chain*). Each transformer receives a byte array representing the class file in its current state. If a transformer returns a new byte array, **that result becomes the logical input to the next transformer**. Therefore, execution order, `null` handling, and class file format errors all directly affect the final bytecode that the JVM verifies and uses.

This lesson explains the exact API contract, transformer ordering during load/redefine/retransform, how to avoid mutating the input in place, and a runnable Java agent on JDK 17+ demonstrating two consecutive transformers transforming `SEED → NEXT → DONE`. The goal is to understand the **transformation chain**, without needing ASM or Byte Buddy yet.

## 1. General Model: Data Flow of a Class File

Suppose the JVM needs to define the class `LessonTarget` with initial bytecode `B0`. Two transformers are registered in the same group, in the order `T1` then `T2`:

~~~text
Class-file bytes B0
       |
       v
   T1.transform(...)
       |
       | return B1
       v
   T2.transform(..., classfileBuffer = B1)
       |
       | return B2
       v
 JVM verifies and defines class from B2
~~~

This can be expressed as: `B1 = T1(B0)`, `B2 = T2(B1)`. This is **function composition**: `T2(T1(B0))`; generally it cannot be replaced with `T1(T2(B0))` because transformations can be order-dependent.

For example:

- `T1` finds a string constant `"SEED"` in the constant pool and changes it to `"NEXT"`.
- `T2` finds `"NEXT"` in **the bytes already transformed by T1** and changes it to `"DONE"`.
- The class is defined with the final constant `"DONE"`.

If `T2` runs before `T1`, it does not see `"NEXT"` yet and replaces nothing; the class may end up with `"NEXT"` instead of `"DONE"`. Ordering is a **design constraint** when a later transformer depends on the output of an earlier one.

Important: the API guarantees that **the contents of the transformed bytes** are passed to the next step; it does not require two transformers to see the same `byte[]` object in the `==` sense. Do not rely on array identity.

## 2. The ClassFileTransformer.transform(...) Contract

On Java 17+, a common override is:

~~~java
@Override
public byte[] transform(
        Module module,
        ClassLoader loader,
        String className,
        Class<?> classBeingRedefined,
        ProtectionDomain protectionDomain,
        byte[] classfileBuffer)
        throws IllegalClassFormatException {
    // Read current bytes, optionally produce new bytes.
    return null;
}
~~~

This is an **illustrative API signature**, inside a class implementing `ClassFileTransformer`; the `return null` body only illustrates the no-change case. The parameters have the following meanings:

| Parameter | Meaning in chain processing |
| --- | --- |
| `module` | Module of the class being defined |
| `loader` | Class loader defining/having defined the class; may be `null` for the bootstrap loader |
| `className` | Internal name in the form `java/lang/String`; do not assume it is always non-`null` |
| `classBeingRedefined` | The `Class<?>` object on redefine/retransform; may be `null` for a new definition |
| `protectionDomain` | Protection domain associated with the class |
| `classfileBuffer` | **Input bytes at this step**, which may already have been modified by an earlier transformer |
| Return value | Output bytes for the next transformer, or `null` to keep the current input unchanged |

According to the specification, a transformer **must not modify** the `classfileBuffer` array in place. If you need to change the bytecode, create a new array (e.g., `classfileBuffer.clone()` or bytes generated by a class-file generation tool) and return that array.

### What does returning null mean?

If `T1` returns `null`, the JVM passes **the exact bytes that entered T1** onward to `T2`. It does not mean restoring the original bytecode.

~~~text
B0 --T1 returns B1--> B1 --T2 returns null--> B1 --T3 returns B3--> B3
B0 --T1 returns null--> B0 --T2 returns B2  --> B2
~~~

Similarly, if a transformer does not care about the current `className`, it should return `null` to preserve the transformation chain for that class.

### Exceptions in a transformer

If a transformer throws an uncaught exception, **the JVM still continues calling the remaining transformers** per the contract; for the transformation chain, throwing an exception has the same effect as the transformer returning `null`. Throwing `IllegalClassFormatException` helps express or diagnose malformed input bytes, but **it does not automatically stop subsequent steps**.

Distinguish clearly: **an error inside a transformer** can be ignored to continue, whereas **an invalid new byte array** returned by another transformer can cause the JVM to reject defining, redefining, or retransforming the class after the verification phase. Do not rely on throwing an exception in a transformer as a rollback mechanism.

## 3. Actual Ordering: By Capability Group, Then Registration Order

Common registration calls:

~~~java
inst.addTransformer(transformerA);          // equivalent to canRetransform=false
inst.addTransformer(transformerB, false);   // not called on retransform
inst.addTransformer(transformerC, true);    // can be called on retransform
~~~

With `canRetransform=true`, the JVM/agent must actually support retransformation; otherwise, `addTransformer(..., true)` may throw `UnsupportedOperationException`. Check `inst.isRetransformClassesSupported()` first if that capability is needed.

It is **incorrect** to say all transformers always run purely in the order you call `addTransformer`. Java Instrumentation defines four **priority-ordered processing groups**:

| Group order | Transformer kind |
| --- | --- |
| 1 | Java transformers **without** retransformation capability |
| 2 | Native transformers **without** retransformation capability |
| 3 | Java transformers **with** retransformation capability |
| 4 | Native transformers **with** retransformation capability |

Within **each group**, transformers run in the order they were registered. Native transformers come from the JVM Tool Interface (JVMTI) `ClassFileLoadHook` mechanism; when using a pure Java agent, you usually care most about **the Java non-retransformation group** and **the Java retransformation group**.

For example, if a Java agent calls:

~~~java
inst.addTransformer(transformerB, true);   // group 3, registered early
inst.addTransformer(transformerA, false);  // group 1, registered late
~~~

then when a class is newly defined, `transformerA` still runs **before** `transformerB` because it belongs to a higher-priority group. To guarantee `T1 → T2` solely through registration order, place both transformers in the **same group** or explicitly design around cross-group ordering.

A single transformer instance can be registered multiple times, but the API **recommends avoiding this** because it easily causes repeated transformations; create separate instances with clear responsibilities instead.

## 4. Complete Example: Two Transformers Depending on Each Other's Output

The following example is a self-contained Java agent. It uses two transformers on a single class:

- `T1` changes the ASCII UTF-8 constant `SEED` to `NEXT`.
- `T2` only recognizes `NEXT`, changing it to `DONE`.
- `LessonTarget.message()` is defined by the JVM **after** the agent has registered both transformers and returns `DONE`.

To keep the demo runnable with pure JDK, the code manipulates a `CONSTANT_Utf8` entry in the constant pool of **equal ASCII length**. This is a technique to illustrate byte flow; it is not a general-purpose bytecode modifier. In real systems, use ASM/Byte Buddy or a spec-compliant class file parser.

### 4.1. Create TransformerChainDemo.java

Save the entire snippet below in **a single file** named `TransformerChainDemo.java`:

~~~java
import java.lang.instrument.ClassFileTransformer;
import java.lang.instrument.IllegalClassFormatException;
import java.lang.instrument.Instrumentation;
import java.nio.ByteBuffer;
import java.nio.charset.StandardCharsets;
import java.security.ProtectionDomain;

public final class TransformerChainDemo {
    public static void premain(String options, Instrumentation inst) {
        inst.addTransformer(new MarkerTransformer("T1", "SEED", "NEXT"));
        inst.addTransformer(new MarkerTransformer("T2", "NEXT", "DONE"));
    }

    public static void main(String[] args) {
        System.out.println("main=" + new LessonTarget().message());
    }

    private static final class MarkerTransformer implements ClassFileTransformer {
        private final String label;
        private final String from;
        private final String to;

        MarkerTransformer(String label, String from, String to) {
            this.label = label;
            this.from = from;
            this.to = to;
        }

        @Override
        public byte[] transform(Module module, ClassLoader loader,
                String className, Class<?> classBeingRedefined,
                ProtectionDomain domain, byte[] classfileBuffer)
                throws IllegalClassFormatException {
            if (!"LessonTarget".equals(className)) {
                return null;
            }

            byte[] changed = replaceUtf8Constant(classfileBuffer, from, to);
            if (changed == null) {
                throw new IllegalClassFormatException(
                        label + ": expected exactly one " + from);
            }
            System.out.printf("%s input=%s output=%s%n", label, from, to);
            return changed;
        }
    }

    private static byte[] replaceUtf8Constant(
            byte[] original, String from, String to) {
        if (from.length() != to.length()) {
            throw new IllegalArgumentException("Equal-length ASCII only");
        }
        byte[] bytes = original.clone();
        ByteBuffer cp = ByteBuffer.wrap(bytes);
        if (cp.getInt() != 0xCAFEBABE) {
            throw new IllegalArgumentException("Not a class file");
        }
        cp.position(8);
        int count = Short.toUnsignedInt(cp.getShort());
        byte[] source = from.getBytes(StandardCharsets.US_ASCII);
        byte[] replacement = to.getBytes(StandardCharsets.US_ASCII);
        int matches = 0;
        for (int index = 1; index < count; index++) {
            int tag = Byte.toUnsignedInt(cp.get());
            switch (tag) {
                case 1 -> {
                    int length = Short.toUnsignedInt(cp.getShort());
                    int at = cp.position();
                    if (length == source.length
                            && equalsBytes(bytes, at, source)) {
                        System.arraycopy(replacement, 0, bytes, at, length);
                        matches++;
                    }
                    cp.position(at + length);
                }
                case 3, 4, 9, 10, 11, 12, 17, 18 ->
                        cp.position(cp.position() + 4);
                case 5, 6 -> {
                    cp.position(cp.position() + 8);
                    index++;
                }
                case 7, 8, 16, 19, 20 ->
                        cp.position(cp.position() + 2);
                case 15 -> cp.position(cp.position() + 3);
                default -> throw new IllegalArgumentException(
                        "Unknown constant-pool tag: " + tag);
            }
        }
        return matches == 1 ? bytes : null;
    }

    private static boolean equalsBytes(byte[] bytes, int at, byte[] needle) {
        for (int i = 0; i < needle.length; i++) {
            if (bytes[at + i] != needle[i]) {
                return false;
            }
        }
        return true;
    }
}

final class LessonTarget {
    String message() {
        return "SEED";
    }
}
~~~

**Explanation of key details:**

1. `premain` is called by the JVM before `main` when the agent is loaded with `-javaagent`. Thus, both transformers are registered before `LessonTarget` is defined.
2. Both are registered with `addTransformer(transformer)`, meaning `canRetransform=false`. They belong to the **same group**, so `T1` runs before `T2`.
3. `"LessonTarget".equals(className)` filters for the target class; for other classes, it returns `null`. Putting the literal on the left also safely handles the `className == null` case.
4. `replaceUtf8Constant` copies `original.clone()`. It reads the `CAFEBABE` header, walks each constant pool entry by `tag`, and replaces only a single `CONSTANT_Utf8` string matching the exact four ASCII bytes.
5. `CONSTANT_Long`/`CONSTANT_Double` (tag 5/6) occupy two constant pool indices, so the loop increments `index++` an extra time. Do not omit this rule, as it would misread the position of the next entry.
6. `T1` sees `SEED` and returns bytes containing `NEXT`. When `T2` receives `classfileBuffer`, it finds `NEXT` **only because the bytes already passed through T1**.
7. If the target class does not contain **exactly one** expected marker, the demo throws `IllegalClassFormatException` to expose the invalid test condition. Because the contract can still continue calling subsequent transformers, check stdout and actual behavior rather than treating an exception as a mechanism to halt the entire pipeline.

### 4.2. Create agent.mf

Create an `agent.mf` file in the same directory:

~~~text
Manifest-Version: 1.0
Premain-Class: TransformerChainDemo
~~~

Ensure the manifest file **ends with a trailing blank line**. This example only demonstrates **load-time transformation** flow, so there is no need to declare retransformation or redefinition capabilities.

### 4.3. Compile, Package the Agent JAR, and Run

Use JDK 17 or later. The following commands use single-quoted shell syntax that works in both Bash and PowerShell:

~~~bash
javac TransformerChainDemo.java
jar --create --file transformer-chain-agent.jar --manifest agent.mf TransformerChainDemo.class 'TransformerChainDemo$MarkerTransformer.class'
java -javaagent:transformer-chain-agent.jar -cp . TransformerChainDemo
~~~

`javac` produces `TransformerChainDemo.class`, `TransformerChainDemo$MarkerTransformer.class`, and `LessonTarget.class`. The agent JAR contains the two classes needed for `premain` and the transformer to run; `LessonTarget.class` sits on the application classpath so the JVM reads it and applies the transformation at load time.

**Exact stdout verified when running the example on JDK 24:**

~~~text
T1 input=SEED output=NEXT
T2 input=NEXT output=DONE
main=DONE
~~~

This is **execution proof**: if `T2` had received the original bytes without passing through `T1`, it could not have found the `NEXT` UTF-8 entry that only exists after `T1` replaces `SEED`. The actual chain caused `LessonTarget.message()` to return `DONE`.

The code uses `switch ->` syntax and Instrumentation APIs available since Java 17. You can re-run in a clean directory to avoid stale `.class` or JAR files masking test results.

### 4.4. Limitations of the Constant Pool Editing Technique in the Example

The demo only replaces **a single** equal-length ASCII UTF-8 entry. Do not use it as a general modifier for arbitrary strings or methods:

- Class files use **modified UTF-8** for `CONSTANT_Utf8` entries; short ASCII strings in the demo have no difference, whereas Unicode characters or `NUL` must be encoded properly.
- Changing string length requires updating the constant pool entry length and can shift offsets of subsequent bytes; same-length `System.arraycopy` is not enough.
- A constant in the constant pool can be referenced by multiple places; changing it may affect other behaviors unintentionally.
- When adding/modifying real method bytecode, you must maintain valid constant pool entries, offsets, exception tables, stack frames, and class-file validation.
- If you only want to observe without modifying, the transformer should **return `null`**, avoiding unnecessary byte array copies.

For transforming production code, prefer ASM or Byte Buddy. Regardless of the library used, **the chaining contract across transformers remains the same**.

## 5. Null, New byte[], Exceptions: What Does the Next Transformer Receive?

Suppose there are three Java transformers in the same group, registered in order `T1, T2, T3`:

| Behavior | Bytes received by the next step | Consequence |
| --- | --- | --- |
| `T1` returns new array `B1` | `B1` | T1's transformation enters the chain |
| `T2` returns `null` | `B1` | Preserves all accumulated modifications |
| `T2` returns new array `B2` | `B2` | T3 sees T2's output |
| `T2` throws an exception | `B1` | Per the contract, subsequent transformers are still called |
| `T3` returns malformed bytes | Final bytes may be rejected by the JVM | Having the chain run does not guarantee the class loads successfully |

**A transformer has no API to "skip all subsequent transformers."** If you need centralized filtering, register a single coordinator transformer that dispatches steps internally, or have each transformer check `className` and byte state according to a clear contract.

### Do not mutate the input array in place

The following code is an **example of a contract violation**:

~~~java
classfileBuffer[100] = 42; // WRONG: mutating JVM's input directly
return classfileBuffer;
~~~

To switch to a valid pattern, copy first:

~~~java
byte[] modified = classfileBuffer.clone();
modified[100] = 42; // Illustrates writing to a copy only; index 100 has no class-file meaning
return modified;
~~~

Both snippets are **illustrative code fragments**, not standalone class-file transformations. In practice, never modify a byte at an arbitrary offset; locate the proper class-file structure and produce valid output. The core rule is that **the input belongs to the JVM and the transformer must treat it as immutable**.

## 6. Retransformation: When Some Transformers Are Not Called Again

This is the most common source of confusion if you are used to load-time flow:

- A transformer registered with `canRetransform=false` is called when a class is **first loaded** or **redefined**, but is **not called again** on each `retransformClasses(...)`.
- On retransform, the JVM **reapplies verbatim the previous transformation result** of transformers that lack retransformation capability.
- A transformer registered with `canRetransform=true` is **called again** during retransformation and receives the bytes after those reapplied steps.

For example, given `A` without capability and `B` with capability; at initial class definition, the chain produces:

~~~text
Initial load:
B0 --A(false)--> B1 --B(true)--> B2 [class defined]

Subsequent retransform:
B0' --reapplies A's previous result--> B1' --calls B(true) again--> B2'
       A.transform does NOT run            B.transform DOES run
~~~

`B0'` is the original bytes suitable for retransformation from the initial definition or the most recent redefine. They **may differ in binary representation** from `B0` in details such as constant pool layout, even though logically equivalent; do not design transformers around fixed byte offsets. The prime in `B0'`/`B1'` does not imply reloading the class from a physical file.

Example of mixed-group registration:

~~~java
if (!inst.isRetransformClassesSupported()) {
    throw new IllegalStateException("Retransformation unsupported");
}
inst.addTransformer(transformerA, false);
inst.addTransformer(transformerB, true);
~~~

The snippet above is a **code fragment requiring `Instrumentation inst` and two pre-created transformers**, only illustrating capabilities; it is not a standalone program. The agent manifest must include `Can-Retransform-Classes: true` and the JVM must support it. If you only need load-time transformation like the example in section 4, do not declare or use this capability.

### Why doesn't B necessarily accumulate B's previous result?

Each retransform starts again from the appropriate original bytes, then applies non-retransformable transformations per the API rules and invokes retransform-capable transformers. It does not by default take **the final B2 from the previous retransform** as input to the next B. This distinguishes valid, idempotent transformations from accidentally injecting the same code on every retransform.

For a retransform-capable transformer, design the transformation to be **correct when run multiple times**, paying attention to classes that have also been redefined. If you need to mark a class as transformed, do not assume the next invocation will receive the exact byte array returned previously.

## 7. Initial Bytes Source Varies by JVM Operation

Each event type has its own defined starting point:

| Operation | Initial bytes fed into the chain |
| --- | --- |
| New class definition | Bytes received by `ClassLoader.defineClass` or equivalent mechanism |
| Redefinition | Bytes in `ClassDefinition.getDefinitionClassFile()` supplied by the `redefineClasses(...)` call |
| Retransformation | Bytes from the initial definition or most recent redefine, combined with reapplying non-retransformable transformations |

Transformers are called **before** the JVM verifies/applies the final class bytes. If `T1` produces a valid class file but `T2` generates broken bytes, the JVM can reject the definition after the entire chain runs. Therefore, logging `T1 success` does not prove the entire final class is valid.

When retransforming/redefining an already-loaded class, bytecode changes must obey class-structure restrictions (for example, typically you cannot add/remove fields or methods). A transformer that modified a class at load time must ensure that its output during a later retransform/redefine remains a valid transformation under JVM rules.

## 8. Designing Multiple Interdependent Transformers in Practice

In a complex agent, you might need:

1. `T1` adds appropriate markers/metadata to a method.
2. `T2` uses this marker to insert timing logic.
3. `T3` validates or normalizes the result for the final class file.

This is only an example of **how to organize responsibilities**. There is no guarantee that third-party library transformers will produce or recognize each other's markers. When such dependencies exist, verify the output format between steps, determine group ordering, and have tests running on the target JDK.

Design principles:

- **Order by capability intentionally.** Only within the same group is order directly controlled by registration order; across groups, account for the API-defined ordering.
- **Define clear input/output contracts.** For example, `T2` only acts when it sees the pattern produced by `T1`; if absent, return `null` or log a diagnostic error.
- **Do not assume exclusive ownership of the class file.** Other agents may register transformers, including native ones. Your input bytecode may already differ from the class file on disk.
- **Treat `classfileBuffer` as read-only.** Parse the bytes and return a separate array when transforming.
- **Process only the classes you need.** Filter by `className`, `loader`, or module as appropriate to avoid interfering with bootstrap/runtime classes.
- **Avoid unsynchronized global state.** Multiple threads can load multiple classes concurrently; a transformer can be invoked concurrently on different classes.
- **Design transformers to be repeatable.** When a class is redefined or retransformed, do not infinitely stack instructions/markers based on false assumptions about the input.
- **Inspect the final bytes.** Use class-file inspection tools and run the actual class; comparing transformer logs alone is not enough.

### Can you reorder transformers after registration?

`Instrumentation` provides `removeTransformer(transformer)`. Removing affects **future** class definitions, but the API warns that a transformer may still receive callbacks after being removed due to concurrent class loading. Re-registering can affect position within a group, but it should not be treated as a safe orchestration mechanism on a running JVM.

If a multi-step chain requires an invariant order, it is usually easier to control by having **one transformer orchestrate the steps internally**. Then the steps can be called sequentially through an API you own, while still obeying the contract of not mutating `classfileBuffer` in place.

## 9. Diagnosing Unexpected Results

| Symptom | Causes to check |
| --- | --- |
| Only `T1` log appears, no `T2` | Was T2 registered before the class loaded? Was it filtered out by `className`? Was it a retransform event it doesn't support? |
| `T2` sees bytes without T1's edits | Did T1 return new bytes or `null`? Was there an error/exception? Are T1/T2 in capability groups with the reverse of the expected order? |
| Application still returns `SEED` | Was the class already loaded before registration? Did the transformer miss the internal name? Was the output not applied by the JVM? |
| Application returns `NEXT` instead of `DONE` | Step T2 failed or was not called; check the marker in T2's input |
| `ClassFormatError` / `VerifyError` | One of the transformers produced malformed bytes; inspect the class file **after each step**, frames, and stack |
| Same transformation appears multiple times | Duplicate instance registration, or transformer is not safe under redefine/retransform |
| Transformer logs appear but retransform fails | Class is not modifiable, capability is missing, or bytes violate redefine/retransform rules |
| Callbacks still arrive after `removeTransformer` | Concurrent class loading may be in progress; the API warns about this |
| Works on one JDK but fails on another | Check class-file version, JVMTI capabilities, bytecode library, and transformer contract |

To debug systematically, log (at an appropriate log level) the **internal class name**, class loader/module, transformer name, callback order, define/redefine/retransform event, and the size and checksum of the **before/after** byte arrays; do not log full bytecode in production. Hashes/digests show that bytes differ, but **do not prove** that the transformation is semantically right or that the final class is valid.

## 10. Self-Check Exercises

**Exercise 1.** `T1` returns `B1`, `T2` returns `null`, `T3` returns `B3`. What is the input to `T3`?

**Exercise 2.** You register `T2` with `canRetransform=true` first, then register `T1` with `canRetransform=false`. On a new class definition, which Java transformer does the JVM call first?

**Exercise 3.** `T1` turns marker `SEED` into `NEXT`; `T2` depends on marker `NEXT`. If you reverse the order to `T2` then `T1` in the same group, what value will the class return in the demo model?

**Exercise 4.** A non-retransform-capable transformer changed `SEED` to `NEXT` at load time. When `retransformClasses(...)` occurs, is its `transform(...)` called again? How is its previous result handled?

**Exercise 5.** Why is the following incorrect: `classfileBuffer[10] = 0; return classfileBuffer;`?

**Exercise 6.** `T1` throws `IllegalClassFormatException`. Is it guaranteed that the JVM stops completely and does not call `T2`?

**Exercise 7.** Both `T1` and `T2` log "changed", yet the JVM throws `VerifyError`. Do the logs prove both transformations are valid?

### Answers

1. `B1`, because `T2`'s `null` preserves **the current bytes**, not restoring `B0`.
2. `T1` (non-retransform group) before `T2` (retransform group), even though `T2` was registered earlier.
3. Typically `NEXT`: `T2` does not find `NEXT` in the pre-`T1` bytes so it makes no change, and then `T1` changes `SEED → NEXT`.
4. **Not called again**; the JVM **reapplies the saved transformation result** per the contract, then calls retransform-capable transformers.
5. It violates the contract **not to modify the input array**, and mutating an arbitrary offset can corrupt the class file.
6. **No**; a transformer exception is equivalent to returning `null` for chain purposes; subsequent transformers are still called.
7. **No**; logs only prove callbacks ran. The JVM still has to verify and accept the final class bytes.
