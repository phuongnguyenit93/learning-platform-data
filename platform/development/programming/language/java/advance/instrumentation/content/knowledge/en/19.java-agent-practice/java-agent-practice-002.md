# Listing Loaded Classes Along with Their Loaders and Per-Class Modifiability

## 1. Objectives and Expected Output

In Java agent experiments, a fundamental diagnostic question is: **which classes is the JVM currently holding, which class loader defined each class, and does the JVM consider that class modifiable via redefinition or retransformation?** The three calls to know are:

~~~java
Class<?>[] classes = inst.getAllLoadedClasses();
ClassLoader definingLoader = clazz.getClassLoader();
boolean modifiable = inst.isModifiableClass(clazz);
~~~

These are three **illustrative** lines placed in code that already has an `Instrumentation inst` object and a `Class<?> clazz` variable; the complete runnable version is in a later section.

The goal of the lab **“Listing Loaded Classes Along with Their Loaders and Per-Class Modifiability”**, under the **Agent Practice** group, is to build a real Java agent on Java 17+ with two modes:

- `demo.app.`: still takes a JVM-wide snapshot, but only **prints** classes whose names start with this prefix. This mode is small and easy to test with concrete output.
- `all`: iterates over the **entire `getAllLoadedClasses()` snapshot** and prints **one line per class**, including the class name, defining class loader, and `isModifiableClass`.

We also use two different URLClassLoaders to define **the same binary class name** to see why reporting based solely on `Class.getName()` is insufficient.

**Scope limitation:** this is a **read-only** JVM inspection activity. The agent does not add a transformer, does not modify class bytes, does not call `redefineClasses` or `retransformClasses`, and does not grant additional module access. Printing reports still consumes CPU, memory, and I/O, so it must be controlled in production.

## 2. Official API: Instrumentation.getAllLoadedClasses

Java SE 17 defines:

~~~java
Class<?>[] snapshot = inst.getAllLoadedClasses();
~~~

According to the Javadoc, the API returns an array of all classes currently loaded in the JVM, including classes, interfaces, **hidden classes/interfaces**, and **array classes of all types**. Each element is a `Class<?>` object, not a text-based class name.

### 2.1. It Is a Snapshot, Not a Live List

The array is captured at a point in time. The JVM may load more classes or unload a class loader afterward. Do not treat `snapshot.length` as an always-accurate global counter. Even running sorting code, creating a formatter, or logging may cause the JVM to load additional classes after the snapshot has been created.

There is no guarantee on element ordering. If readable output is needed, **sort a copy/filtered list** by name and loader identity. Do not infer class loading chronology from the initial order in the array.

### 2.2. Class Types That Can Be Surprising

| Type | Observable Name | Notes |
|---|---|---|
| Regular class | `demo.app.Main` | Java binary name |
| Interface | `java.lang.Runnable` | Is a Class object even though Java calls it an interface |
| Primitive array | `[I` | Runtime/descriptor name, not `int[]` in source syntax |
| Reference array | `[Ljava.lang.String;` | May appear in the snapshot if loaded |
| Hidden class | Name may contain a JVM suffix like `/0x...` | Not necessarily findable via standard `Class.forName` |
| Proxy/lambda/generated | Name generated by tools/JVM | Count depends on runtime and timing |

The table only explains the types; it **does not assert that every one of these rows must appear on all JVMs**. An important point is that `getAllLoadedClasses` is not limited to classes on the application classpath.

### 2.3. Do Not Use Class.forName to Re-scan Every Class

We already have the `Class<?>` object from the JVM; there is no need to use `Class.forName(c.getName())` to “verify” it. Doing so may fail to find hidden classes, may trigger class initialization, or may trigger additional loading through an inappropriate loader. Retrieve metadata directly from the `Class<?>` object.

## 3. Class.getClassLoader: Which Loader Is Being Queried?

~~~java
ClassLoader loader = clazz.getClassLoader();
~~~

This method returns the **defining class loader** of the class. Under JVM semantics, a class name **alone is not enough** to uniquely determine class identity: the same binary name created by **two different defining loaders** produces two distinct classes.

Reporting cases in the lab:

| Condition | Short Label | Explanation |
|---|---|---|
| `loader == null` | `bootstrap` | Class defined by the bootstrap loader |
| `loader == ClassLoader.getSystemClassLoader()` | `system` | Class defined by the system class loader |
| `loader == ClassLoader.getPlatformClassLoader()` | `platform` | Class defined by the platform class loader |
| Otherwise | `custom:<loader-type>@<identity-hash>` | Another class loader, e.g., URLClassLoader |

**`null` is not an error.** The bootstrap class loader is not represented by a regular Java `ClassLoader` object returned by `Class.getClassLoader()`.

The labels `system`/`platform` describe **the role in that JVM**, and do not guarantee a fixed class loader class name across all vendors/JDKs. For custom loaders, using the class name and `System.identityHashCode(loader)` helps distinguish two instances. The hash is only **reference information within a single run**, can rarely collide, and is not stable across processes; when a guaranteed ID is needed, map directly by **object identity** and manage a dedicated ID lifecycle.

### 3.1. Which Loader Loads Array Classes?

For an array type of a reference class, the defining loader is tied to the component type according to JVM rules; primitive array types are defined by the bootstrap loader. Therefore, do not lump every class with `getName().startsWith("[")` into the system loader.

### 3.2. getInitiatedClasses Does Not Have the Same Meaning

`Instrumentation.getInitiatedClasses(loader)` returns the classes for which `loader` is recorded as an **initiating loader**, meaning it can be found via `ClassLoader.loadClass`, `Class.forName`, or linkage. With parent delegation, the initiating loader is not necessarily the **defining loader**. According to Java SE 17, the initiated list also does not include hidden classes/interfaces in the way `getAllLoadedClasses` does.

~~~java
Class<?>[] initiated =
        inst.getInitiatedClasses(
                ClassLoader.getSystemClassLoader());
~~~

This is a **secondary API example**. If the requirement is “for every class in the entire JVM, record the exact loader that defined it”, the correct approach in this lab is `getAllLoadedClasses()` followed by `Class.getClassLoader()` for **each element** — do not call `getInitiatedClasses(system)` and label all of them “system”.

## 4. isModifiableClass: Class-Level Modifiability

~~~java
boolean modifiable = inst.isModifiableClass(clazz);
~~~

The API returns `true` if the JVM considers the class modifiable by `retransformClasses` or `redefineClasses` considering **the class itself**; it returns `false` if the class is not modifiable.

Two controls guaranteed by the Java SE 17 Javadoc:

~~~java
inst.isModifiableClass(int.class);     // false
inst.isModifiableClass(int[].class);   // false
~~~

Classes representing **primitive types** and **array types** are always **unmodifiable**. For other classes, do not guess by package name: call the actual API.

### 4.1. Modifiable True Is Not Enough to Perform Code Modification

The Javadoc explicitly states that the result of `isModifiableClass` is **independent** of:

~~~java
inst.isRetransformClassesSupported();
inst.isRedefineClassesSupported();
~~~

A class may report `modifiable=true` in the report while the agent **did not request** `Can-Retransform-Classes` or `Can-Redefine-Classes` via the manifest. To actually perform retransformation, you need the capability supported by the JVM, a modifiable class, an appropriate transformer, valid class bytes, and adherence to class schema rules.

Therefore:

- `isModifiableClass(c) == false`: do not use `c` as a target for retransform/redefine.
- `isModifiableClass(c) == true`: a **necessary condition**, not a promise that every modification operation will succeed.
- `isRetransformClassesSupported() == false`: even a class reporting `modifiable=true` does not make `retransformClasses` available.
- The VM may still reject schema changes such as adding fields/methods or changing the superclass on current HotSpot/JVM TI.

In the main example, the manifest **does not** request any code-modification capability because this lab only observes. Therefore, do not use the modifiable flag as a basis to claim “patched successfully”.

### 4.2. Modifiable Is Not a User Permission

This flag is not an ACL, not a check of whether the user has permission to modify bytecode, and does not replace attach/OS/JVM policies. It describes a VM property of the class, whereas the concrete operation has many other operational and technical conditions.

## 5. Demo Architecture

Structure:

~~~text
loaded-class-lab/
├── agent.mf
├── src/
│   ├── agent/demo/agent/LoadedClassAgent.java
│   └── app/demo/app/
│       ├── Main.java
│       └── Helper.java
└── out/
    ├── agent/
    ├── app/
    └── loaded-class-agent.jar
~~~

`LoadedClassAgent.premain` receives the `Instrumentation` object from the JVM and retains a reference. `Main` creates an instance of `Helper`, then calls `LoadedClassAgent.dump(...)` to output the snapshot **after Main and Helper have been loaded**.

~~~text
JVM starts -javaagent
          |
          v
Agent.premain -> Instrumentation granted -> agent:ready
          |
          v
Main.main
  |
  +-- new Helper().ping()     -> app:helper=ok
  |
  +-- LoadedClassAgent.dump("demo.app.")
       |
       +-- getAllLoadedClasses()
       +-- filter/sort
       +-- each Class: getName(), getClassLoader(), isModifiableClass()
       +-- print two app classes and primitive/array probes
~~~

Having `Main` import the agent class is only to provide a deterministic trigger in the **lab**. In a production app, choose an independent trigger from `agentmain`, JMX, or an access-controlled administrative channel, rather than coupling business source code with the agent.

## 6. Complete Java Agent Source

File **`src/agent/demo/agent/LoadedClassAgent.java`**:

~~~java
package demo.agent;

import java.lang.instrument.Instrumentation;
import java.util.ArrayList;
import java.util.Comparator;
import java.util.List;

public final class LoadedClassAgent {
    private static volatile Instrumentation instrumentation;
    private LoadedClassAgent() {}

    public static void premain(String options, Instrumentation inst) {
        instrumentation = inst;
        System.out.println("agent:ready");
    }

    public static void dump(String scope) {
        Instrumentation inst = instrumentation;
        if (inst == null) {
            throw new IllegalStateException("Run with -javaagent");
        }

        Class<?>[] snapshot = inst.getAllLoadedClasses();
        boolean all = "all".equals(scope);

        List<Class<?>> selected = new ArrayList<>();
        for (Class<?> type : snapshot) {
            if (all || type.getName().startsWith(scope)) {
                selected.add(type);
            }
        }

        selected.sort(Comparator
                .comparing((Class<?> c) -> c.getName())
                .thenComparingInt(c ->
                        System.identityHashCode(c.getClassLoader())));

        System.out.println("snapshot:scope=" + scope);
        for (Class<?> type : selected) {
            ClassLoader loader = type.getClassLoader();
            System.out.println(
                    "loaded=" + type.getName()
                    + " | loader=" + describe(loader)
                    + " | modifiable="
                    + inst.isModifiableClass(type));
        }

        System.out.println("snapshot:selected=" + selected.size());
        System.out.println(
                "probe:int=" + inst.isModifiableClass(int.class));
        System.out.println(
                "probe:int-array=" + inst.isModifiableClass(int[].class));
        System.out.println("snapshot:end");
    }

    private static String describe(ClassLoader loader) {
        if (loader == null) return "bootstrap";
        if (loader == ClassLoader.getSystemClassLoader()) {
            return "system";
        }
        if (loader == ClassLoader.getPlatformClassLoader()) {
            return "platform";
        }
        return "custom:" + loader.getClass().getName()
                + "@"
                + Integer.toHexString(
                        System.identityHashCode(loader));
    }
}
~~~

This is **complete, runnable code on Java 17+**. Neither OW2 ASM, Byte Buddy, nor `jdk.internal.*` is needed because the task **does not modify bytes**.

### 6.1. Detailed Explanation

**`static volatile Instrumentation instrumentation`:** holds the VM-provided object passed to `premain`. `volatile` ensures reference visibility across threads in the lab, but does not create an atomic snapshot with respect to all concurrent class loading.

**`dump("demo.app.")`:** still calls `getAllLoadedClasses` with **JVM-wide** scope, then filters classes whose names start with `demo.app.` to reduce output. There is no overload of `getAllLoadedClasses` to ask the JVM to scan only one package.

**`dump("all")`:** removes the name filter condition, adds all array elements to the list, and prints each class. This is the full mode that satisfies the requirement to list every class, though it can produce many lines.

**`Comparator`:** sorts by `Class.getName()` then loader identity hash for readable output. Sorting by hash may not break ties definitively in the event of a collision and is not stable across runs; this is a demonstration technique, not a persistent ID system.

**`describe(loader)`:** distinguishes bootstrap/system/platform/custom. For custom loaders, it prints the Java type and identity hash; it does not print only `loader.getClass().getName()` because multiple instances of the same loader type can define classes with identical names.

**`isModifiableClass(type)`:** called **once per displayed class**; do not infer a class's modifiability from its package name or loader.

**`int.class`/`int[].class` probes:** control checks for two cases guaranteed to be false, independent of whether primitive classes appear in the snapshot.

### 6.2. Why Is There No ClassFileTransformer?

None is needed. `Instrumentation` provides `getAllLoadedClasses` directly, so there is no need to hook class loading to discover previously loaded classes. Adding a transformer just to list a snapshot makes the lab harder, may alter class loading order, and increases overhead.

### 6.3. Why Must the Loader Record Be Kept for Each Class?

If you only print:

~~~text
demo.app.Helper=true
~~~

then it is impossible to tell which loader defined the class. If two independent loaders both load the name `demo.isolated.Widget`, the two records will have the same name and may have the same modifiable flag, but they are **not the same Class object**. Therefore, the report line must include the **loader identity/role**.

## 7. Java Application Used for Verification

File **`src/app/demo/app/Helper.java`**:

~~~java
package demo.app;

public final class Helper {
    public String ping() {
        return "ok";
    }
}
~~~

File **`src/app/demo/app/Main.java`**:

~~~java
package demo.app;

import demo.agent.LoadedClassAgent;

public final class Main {
    public static void main(String[] args) {
        System.out.println("app:start");
        System.out.println(
                "app:helper=" + new Helper().ping());
        System.out.println("app:before-snapshot");

        LoadedClassAgent.dump(
                args.length == 0 ? "demo.app." : args[0]);

        System.out.println("app:end");
    }
}
~~~

`Main` intentionally instantiates `Helper` before taking the snapshot; `Main` itself has also been loaded by the JVM to run the entry point. Thus, when filtering `demo.app.`, we expect **Main** and **Helper**.

The line `LoadedClassAgent.dump` creates a **compile-time dependency** between the sample app and the agent, compiled using `-cp out/agent`. When running with `-javaagent`, the JDK places the agent classes onto the system class loader search path per the Java agent contract, and `Main` can find the agent class. Do not run this `Main` as a standalone application without the agent JAR: it attempts to call `LoadedClassAgent` and may fail with `NoClassDefFoundError` or `IllegalStateException` depending on the classpath. This is an **intentional limitation of the test harness**, not a production architecture.

## 8. Manifest, Compilation, and Packaging

File **`agent.mf`** must contain:

~~~text
Manifest-Version: 1.0
Premain-Class: demo.agent.LoadedClassAgent

~~~

Keep the trailing newline and rebuild the JAR whenever the manifest changes. `Premain-Class` is a dot-separated **binary name**, not a slash-separated internal JVM name.

Create output directories:

~~~bash
mkdir -p out/agent out/app
~~~

If using Windows PowerShell:

~~~powershell
New-Item -ItemType Directory -Force out/agent, out/app
~~~

Compile and create the agent JAR using JDK 17+:

~~~bash
javac --release 17 -d out/agent src/agent/demo/agent/LoadedClassAgent.java

javac --release 17 -cp out/agent -d out/app src/app/demo/app/Main.java src/app/demo/app/Helper.java

jar --create --file out/loaded-class-agent.jar --manifest agent.mf -C out/agent .
~~~

Explanation:

1. `javac --release 17` produces Java 17 target classfiles (major version 61), without using newer Java APIs.
2. `out/agent` contains the class `demo.agent.LoadedClassAgent`.
3. `-cp out/agent` in the app compile command lets the compiler resolve `Main`'s import.
4. `out/app` contains the two app classes; they do **not** need to be packaged into the agent JAR.
5. The `jar` command writes the manifest and agent classes; afterward, inspect the **final artifact**.

Inspect the JAR:

~~~bash
jar --list --file out/loaded-class-agent.jar
jdeps --jdk-internals out/loaded-class-agent.jar
~~~

The `jar --list` output must include `META-INF/MANIFEST.MF` and `demo/agent/LoadedClassAgent.class`. `jdeps --jdk-internals` should report no dependencies on JDK internal APIs since the source only uses public APIs. If `Premain-Class` is missing in the actual JAR, the JVM will fail before the app `main` is called; editing the source manifest file without rebuilding the JAR will not fix it.

**`Can-Retransform-Classes: true` or `Can-Redefine-Classes: true` is not needed** in this lab's manifest, because no retransformation/redefinition is performed—only observation APIs are called. This is also an opportunity to learn the difference between the `isModifiableClass` flag and agent-wide capabilities.

## 9. Filtered Mode: Tested Exact Output

Run:

~~~bash
java -Xverify:all -javaagent:out/loaded-class-agent.jar -cp out/app demo.app.Main
~~~

**Measured stdout from an actual test run on JDK 24.0.2 (bytecode compiled with `--release 17`):**

~~~text
agent:ready
app:start
app:helper=ok
app:before-snapshot
snapshot:scope=demo.app.
loaded=demo.app.Helper | loader=system | modifiable=true
loaded=demo.app.Main | loader=system | modifiable=true
snapshot:selected=2
probe:int=false
probe:int-array=false
snapshot:end
app:end
~~~

How to read it:

- `agent:ready`: `premain` received and stored `Instrumentation` before app `main`.
- `app:helper=ok`: `Helper` was used before the snapshot.
- `snapshot:scope=demo.app.`: the program **filters the display**, not claiming the JVM only has two classes.
- `loaded=demo.app.Helper` and `loaded=demo.app.Main`: the two `Class` objects defined by the `system` loader in the test.
- `modifiable=true`: the VM reports both classes as modifiable on a per-class basis; this does not mean the agent requested the capability to perform modifications.
- `snapshot:selected=2`: the number of elements **after filtering**, not the total number of loaded classes in the JVM.
- `probe:int=false` and `probe:int-array=false`: results conforming to the Java SE 17 contract.
- `app:end`: the program continues running after printing the snapshot.

### 9.1. What Should Not Be Tested with Exact-Match

On another machine, the number of loaded classes may vary. If the app is extended with more classes in package `demo.app.`, `snapshot:selected` will no longer be 2. If the system class loader is customized, labels/behavior may change. Therefore, the stdout above is the **exact result of the isolated lab run**, not a universal standard for every runtime.

### 9.2. Why Doesn't the Program Display Source Code or Bytecode?

`getAllLoadedClasses` returns `Class<?>` objects for observing **runtime metadata**. It does not provide classfile bytes, does not indicate whether a method body has been instrumented, and does not measure invocation counts. Viewing class bytes or measuring method execution requires different APIs/designs that are outside the scope of this lab.

## 10. All Mode: Listing Every Class in the Entire JVM

Command:

~~~bash
java -Xverify:all -javaagent:out/loaded-class-agent.jar -cp out/app demo.app.Main all
~~~

Because `scope` equals `all`, the code:

~~~java
boolean all = "all".equals(scope);

for (Class<?> type : snapshot) {
    if (all || type.getName().startsWith(scope)) {
        selected.add(type);
    }
}
~~~

adds **every element of `getAllLoadedClasses()`** to the list, then prints:

~~~text
loaded=class.name | loader=defining-loader | modifiable=true-or-false
~~~

The line above is a **format template**, not an exact log from the JVM. Actual output can be very long; the entire output should not be shown in the article.

To save to a file when running in the lab with Bash:

~~~bash
java -Xverify:all -javaagent:out/loaded-class-agent.jar -cp out/app demo.app.Main all > loaded-classes.txt
~~~

With PowerShell:

~~~powershell
java -Xverify:all -javaagent:out/loaded-class-agent.jar -cp out/app demo.app.Main all | Out-File -Encoding utf8 loaded-classes.txt
~~~

### 10.1. Actual Experimental Results

In a run of the Java 17-target agent on JDK 24.0.2:

- `snapshot:scope=all` appeared.
- There were **1,282** class lines in the selected snapshot.
- There were many records with `loader=bootstrap`.
- Both hidden class records and array class records were present.
- There were **167** `modifiable=false` lines in that run.
- Both `demo.app.Helper` and `demo.app.Main` were still in the output, both with `loader=system | modifiable=true`.

The numbers **1,282** and **167** are only measurements from **one run** on **one JVM**; class loading depends on JDK/version/options/timing and the libraries in use. **Do not assert these numbers in CI on a different runtime.** Assert stable properties instead: output exists for each class in the snapshot, the bootstrap loader is handled, primitive/array probes are false, and the app classes that the test actively loaded are present.

### 10.2. Verifying Output Count for a Specific Run

In the source, the loop displays each selected `Class<?>` as **one line** starting with `loaded=...`, then prints `snapshot:selected=<size>`. You can filter lines starting with `loaded=` and count them in the output file itself. Other logs such as `agent:ready` or `app:start` must be ignored.

If class-loading logs are printed from multiple threads/agents simultaneously to stdout, parsing becomes more complex. Production tools should write structured reports with dedicated timestamps/correlation IDs instead of mixing everything into service stdout.

## 11. Second Experiment: Two Defining Loaders, One Class Name

A common pitfall: seeing two lines with the same name `demo.isolated.Widget` from `getAllLoadedClasses` and assuming it is a meaningless duplicate. In reality, the pair **(binary name, defining class loader)** forms class identity in the JVM.

We intentionally define a `Widget` class from **two separate `URLClassLoader` instances**.

File **`src/plugin/demo/isolated/Widget.java`**:

~~~java
package demo.isolated;

public final class Widget {
    public String id() {
        return "widget";
    }
}
~~~

Compile into a **separate** directory:

~~~bash
mkdir -p out/plugin
javac --release 17 -d out/plugin src/plugin/demo/isolated/Widget.java
~~~

Do not add `out/plugin` to the runtime application classpath. The two URLClassLoaders will read the same `Widget.class` from this path.

File **`src/app/demo/app/LoaderMain.java`**:

~~~java
package demo.app;

import java.net.URL;
import java.net.URLClassLoader;
import java.nio.file.Path;
import demo.agent.LoadedClassAgent;

public final class LoaderMain {
    public static void main(String[] args) throws Exception {
        URL root = Path.of("out/plugin")
                .toAbsolutePath().toUri().toURL();

        try (URLClassLoader first =
                     new URLClassLoader(new URL[] {root}, null);
             URLClassLoader second =
                     new URLClassLoader(new URL[] {root}, null)) {

            Class<?> a = Class.forName(
                    "demo.isolated.Widget", false, first);

            Class<?> b = Class.forName(
                    "demo.isolated.Widget", false, second);

            System.out.println(
                    "same-name=" + a.getName().equals(b.getName()));

            System.out.println("same-class=" + (a == b));

            LoadedClassAgent.dump("demo.isolated.");
        }
    }
}
~~~

The `null` parent of the two URLClassLoaders in the lab ensures they **do not delegate defining `Widget` to the application loader**, while bootstrap classes remain available. This is test isolation, not a default production plugin pattern.

Compile and run:

~~~bash
javac --release 17 -cp out/agent -d out/app src/app/demo/app/LoaderMain.java

java -Xverify:all -javaagent:out/loaded-class-agent.jar -cp out/app demo.app.LoaderMain
~~~

**Two behavior lines verified on JDK 24.0.2:**

~~~text
same-name=true
same-class=false
~~~

In the subsequent snapshot, `demo.isolated.Widget` has **two records with different custom URLClassLoader identity hashes**, and each class reports `modifiable=true` in the tested JVM. If you see two `loaded=demo.isolated.Widget` lines and `snapshot:selected=2`, that is the expected result.

Do not assert exact identity hashes: they change between runs and may differ across JDK vendors. If two records have the same class name but different loaders, they are **two distinct Class objects**. Do not build a JVM-wide `Map<String, Boolean>` using only the class name as the key, because it will erroneously merge these two classes.

### 11.1. Do Not Hold Strong References Indefinitely

Holding `Class<?>`/`ClassLoader` objects long-term in agent static fields can prevent class unloading. For diagnostic snapshots, release references after printing or writing the needed data; if building long-term metrics, use appropriate loader IDs and lifecycle policies, and consider weak references instead of an unbounded strong cache.

## 12. What a Modifiable Result Does Not Prove

A line:

~~~text
loaded=demo.app.Main | loader=system | modifiable=true
~~~

**does not** prove:

1. A transformer has been registered.
2. `Can-Retransform-Classes` or `Can-Redefine-Classes` is enabled.
3. The VM allows changing the entire schema of the class.
4. The class has ever been redefined or retransformed.
5. The agent has permission to intervene in every module or classloader.
6. Installed bytecode will be valid and business behavior will be preserved.
7. The user or tool has permission to attach to another JVM.
8. There is no class with the same binary name in another custom loader.

If you want to **actually modify**, first check:

~~~java
boolean classIsModifiable =
        inst.isModifiableClass(clazz);
boolean canRetransform =
        inst.isRetransformClassesSupported();
boolean canRedefine =
        inst.isRedefineClassesSupported();
~~~

This is only a **precondition check snippet**. Afterward, you still must check schema restrictions, transformer code, bytecode verification, helper visibility, thread safety, and deployment policy. Do not use the snapshot lab output as proof that “the agent patched successfully”.

## 13. How Is a Snapshot Different from Class Loading Events?

`getAllLoadedClasses()` is a snapshot of the state at the time of the call. It does not state **when the class was loaded**, does not tell **who requested the load**, does not measure the memory footprint of all instances, and cannot count how many times a method was called.

| Goal | Better-Suited Tool |
|---|---|
| List of all currently loaded classes | `getAllLoadedClasses()` |
| Defining loader of each class | `Class.getClassLoader()` |
| Is a class retransformable/redefinable per the VM? | `isModifiableClass(clazz)` |
| Which class was just defined? | `ClassFileTransformer`, JFR/ClassLoading events, or JVM logging |
| Execution time of each method | Appropriate bytecode probes/profiler/JFR |
| Which classes were initiated by a loader? | `getInitiatedClasses(loader)` in the strict initiating sense |
| Which classes were loaded before agent startup? | Loaded snapshot; do not expect transformers to replay automatically |
| Is a class loader leaking? | Snapshots over time + heap/jcmd/JFR/class unloading analysis |

Do not conclude from **a single** snapshot that a class has leaked. Class unloading and GC depend on the reference graph, threads, caches, and time. Running a diagnostic tool itself can also cause new classes to be loaded.

## 14. How to Extend to agentmain to Observe a Running JVM

The main lab chooses `premain` to avoid dynamic attach complexity. However, in real applications, the need is often to **list classes after the JVM has been running for a long time**. If the JVM allows agent loading after startup, you can add an entry point:

~~~java
public static void agentmain(
        String options, Instrumentation inst) {

    instrumentation = inst;
    System.out.println("agent:attached");

    dump(options == null || options.isBlank()
            ? "all" : options);
}
~~~

**This is an illustrative extension snippet** that must be placed in `LoadedClassAgent` and declared via `Agent-Class` in the JAR manifest before use. It **is not part of the startup-agent test in Section 9**.

Things to verify:

- Whether the JVM and vendor support dynamic attach.
- OS/container permissions, PID ownership, and dynamic agent loading flags/policies.
- JDK 21+ has specific warnings/recommendations regarding dynamic agent loading; check the target runtime.
- `agentmain` must not print tens of thousands of records unboundedly to production JVM stdout.
- If the operator requests `all`, consider record limits, redaction, and secure log storage.
- Successful dynamic attach does not mean every class is modifiable; still query each `Class<?>`.

**Strength of the snapshot:** it includes classes loaded **before the agent attached**, without depending on a transformer having observed that class at load time.

## 15. Mitigating Risks When Listing a Large JVM

### 15.1. CPU, Heap, and Logging Costs

Calling `getAllLoadedClasses` allocates an array of class references; the demo code also creates an `ArrayList`, sorts, and prints each record. In a JVM with many class loaders or frameworks generating a large number of classes, this can consume CPU/heap and cause log flooding.

- Filter early by name/module/loader on the snapshot to reduce the **printed list**.
- Do not call `Class.forName` to “verify” each element.
- Do not store snapshots in an infinitely lived static map.
- Do not make network/database calls from the loop if this is a hot diagnostic tool.
- Do not run `all` repeatedly in an unbounded loop without rate limiting.
- Do not write raw classfile bytes, secrets, or sensitive paths to public logs.
- Do not automatically call `System.gc()` to “normalize” the snapshot; it does not guarantee class unloading.

### 15.2. Classpath Information Security

Lists of class/module names, class loader types, and plugin names can expose system architecture. Collect and share them only with authorized personnel under clear output retention and access policies.

### 15.3. Results Varying Between Runs

Class counts and identity hashes can change across JDK builds/vendors, flags, app dependencies, class loading timing, or thread scheduling. Compare by essential invariants: expected target classes are present, loader role/identity is consistent within the **same run**, and classes are not confused with instances.

## 16. Common Errors

| Symptom | Cause / Check |
|---|---|
| JVM does not find `Premain-Class` | Manifest in the final JAR is wrong, JAR was not rebuilt, or binary class name is wrong |
| `NoClassDefFoundError` for `LoadedClassAgent` | Sample app calls the agent class, but the JVM did not load the agent JAR/search path as expected |
| `snapshot:scope=demo.app.` does not show `Helper` | Was `Helper` instantiated before the snapshot? Does the class use the right package/loader? |
| Prints `loader=null` and treated as an error | `null` is the bootstrap defining loader |
| Two records with the same name | Check if there are two different defining class loader identities |
| `modifiable=false` for `int[].class` | Standard behavior; array classes are not modifiable |
| `modifiable=true` but retransform fails | Global capability/manifest, VM support, schema, and class eligibility |
| `getInitiatedClasses(system)` differs from JVM-wide list | The two APIs serve different purposes; initiated is not defining |
| `snapshot:selected` differs between runs | Snapshot timing/JDK version/app classloading changed |
| `all` produces too many lines | Use a filter or redirect output to a secure file |
| Custom loader hash differs | Identity hash is not persistent |
| Duplicate class names merged in a map | Do not use name alone as class identity |
| Keeping snapshot cache long-term prevents class unloading | Strong references to Class/loader can prevent unloading |
| JVM reports `UnsupportedClassVersionError` | Compiled without `--release 17` or runtime is too old |
| Class appears in snapshot but method cannot be called | Loading does not guarantee linkage/invocation of every code path |
| `Class.forName(name)` cannot find a hidden class | Hidden classes are not discoverable like normal classes |

### 16.1. Do Not Infer the Loader from the Package Name

Do not assume all `java.*` classes are bootstrap and all `com.example.*` classes are system. Plugins, module layers, generated classes, or custom class loaders can break this heuristic. **Call `clazz.getClassLoader()` on the actual `Class` object**.

### 16.2. Do Not Confuse Array Classes and Primitive Classes

An array class `int[].class` and a primitive type `int.class` are both unmodifiable, but their runtime/display names differ; the fact that `getAllLoadedClasses` may list array classes does not mean every primitive type will also appear as an element with a similar naming style. This lab uses probes to verify them explicitly.

### 16.3. Do Not Treat the Loader Hash as an Absolute Unique Key

`System.identityHashCode` can have collisions. If a tool needs an exact ID table for two loader instances within the same snapshot, use `IdentityHashMap<ClassLoader, Integer>` and assign dedicated IDs, rather than mapping by `ClassLoader.getClass().getName()`.

## 17. Practice Exercises and Answers

### A. Record All Three Pieces of Information per Class

For each `Class<?> c`, how do you obtain its name, defining loader, and modifiability?

**Answer:** `c.getName()`; `c.getClassLoader()` (handling `null` as bootstrap); `inst.isModifiableClass(c)`.

### B. Why Doesn't getAllLoadedClasses Sort Automatically?

The specification does not guarantee ordering; for a readable report, you must sort it yourself and keep loader identity as a tie-breaker. **Do not infer from array position that a class was loaded earlier or later.**

### C. Creating 100 Helper Instances

Create 100 `new Helper()` objects in the same class loader. Are there 100 `demo.app.Helper` records? **No**. The snapshot contains class identities, not object instances.

### D. Adding String[].class to Probes

Predict `isModifiableClass(String[].class)`. **Answer:** `false` because it is an array class.

### E. Two URLClassLoaders with the Same Widget Name

Why is `a.getName().equals(b.getName())` true while `a == b` is false? **Answer:** two different defining class loaders create two independent class identities.

### F. Comparing getInitiatedClasses and getAllLoadedClasses

Can you use `getInitiatedClasses(system)` to state that all returned classes were defined by the system loader? **No.** Initiating loader and defining loader differ under parent delegation.

### G. Modifiable True and Capability False

A class reports `modifiable=true`, but the agent does not have `Can-Retransform-Classes: true`. Is calling `retransformClasses` guaranteed to work? **No**, you must check the global capability; class eligibility and valid bytes are also required.

### H. Adding a Module Column

Add `c.getModule().getName()` to the report, handling unnamed modules where `getName() == null`. Does it replace loader identity? **No**.

### I. Warning About Caching

If you keep `Class<?>[]` in an agent static field for days, what can the consequence be? **Strong references can keep classes/classloaders reachable**, impeding class unloading.

### J. Predicting Full Output

Run `all` on two different JVM/JDK versions. Why do the line counts differ? **Because snapshot timing, the class loading graph, generated/hidden classes, and runtime vendor/configuration differ.**

### Quick Questions

1. API to get the list of loaded classes? — `getAllLoadedClasses()`.
2. API to get the defining loader of a class? — `Class.getClassLoader()`.
3. What does a `null` loader mean? — Bootstrap.
4. API to query per-class modifiability? — `isModifiableClass(clazz)`.
5. Are primitive/array classes modifiable? — No.
6. Does `modifiable=true` mean the redefine capability is enabled? — No.
7. Can two classes with the same name be different? — Yes, when their defining loaders differ.
8. Does the snapshot include hidden classes? — Yes, per Java SE 17.
9. Does `getInitiatedClasses` mean defining loader? — No.
10. Does listing the snapshot modify bytecode? — No.
11. Should you hard-match total loaded classes in CI? — No.
12. Can you use `Class.forName` to find every hidden class by name? — No.
13. Does a snapshot update automatically as the JVM loads more classes? — No.
14. Can `all` output be large? — Yes, it needs limiting/redirection.
15. Can an agent from `premain` capture classes loaded before it ran? — Yes, the snapshot API captures the classes currently loaded in the JVM at the time of the call.

## 19. Summary and References

The lab **“Listing Loaded Classes Along with Their Loaders and Per-Class Modifiability”** has a very small core:

~~~java
for (Class<?> c : inst.getAllLoadedClasses()) {
    ClassLoader loader = c.getClassLoader();
    boolean modifiable = inst.isModifiableClass(c);
    // Record c.getName(), loader, and modifiable.
}
~~~

From those three calls, understanding the exact semantics is the key takeaway:

- `getAllLoadedClasses` is a JVM-wide snapshot, including hidden and array classes, with no stable ordering.
- `getClassLoader` returns the **defining loader**, not necessarily the initiating loader. `null` means bootstrap.
- `isModifiableClass` is a **per-class** answer, not whether the agent has retransform/redefine capabilities. Primitive/array classes are not modifiable.
- Class identity depends on **name and loader**, so two classes with the same name from two URLClassLoaders are two distinct classes.

The lab suite was compiled for **Java 17 target** and run on **JDK 24.0.2 with `-Xverify:all`**: filtered output has `demo.app.Helper` and `demo.app.Main` with `loader=system | modifiable=true`, and false primitive/array probes; `all` mode displays bootstrap, hidden, array, and nonmodifiable classes; the two-URLClassLoader test confirms same-name true and same-class false. **Preserve the read-only spirit of this inspection** before expanding into actual instrumentation.
