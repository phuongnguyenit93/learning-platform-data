# A class file is a binary representation that can exist as bytes in memory

## 1. Does a `.class` file have to be a file on disk?

**No.** In Java, the core of the **class-file format** is **a structured sequence of bytes defined by the Java Virtual Machine Specification**. The `.class` extension is a common way to **store** that byte sequence as a file on the filesystem, not the sole condition for representing or loading a class.

For example, the same class definition can pass through different storage forms:

~~~text
Java code                       class-file-format bytecode
   |                                     |
   v                                     v
javac / compiler             CA FE BA BE 00 00 00 3D ...
   |                                     |
   +------> on disk: MyType.class        |
   +------> in a JAR/ZIP entry           |
   +------> in a byte[] on the heap      |
   +------> in ByteArrayOutputStream     |
   +------> bytes from network/cache/DB  |
   +------> bytes generated by library   |
                                         v
                           ClassLoader.defineClass(...)
                                         |
                                         v
                              Class<?> in the JVM
~~~

You should not phrase this as "the JVM runs `.class` files on disk." The JVM defines a class from a **valid representation in the class-file format** supplied by the class-loading mechanism; that representation may originate from disk, a JAR, the network, dynamically generated data, or memory. The final step produces a `Class<?>` object and runtime information managed by the JVM; they **are not the original `byte[]` array itself**.

**Distinguish three concepts right from the start:**

- **`class-file bytes`:** binary content in a defined format, which can reside in a `byte[]`.
- **`Something.class` file:** a **container on the filesystem** whose content is the aforementioned bytes; the file may not exist.
- **JVM-defined class:** a runtime type created by a defining class loader, represented via `Class<?>`; not identical to a copy of the bytes or a file.

This definition applies to classes, interfaces, and related representations described by the JVMS, not only ordinary `public class` declarations.

## 2. What does a class file actually contain?

According to the **Java Virtual Machine Specification, Chapter 4**, a class file is a stream of 8-bit bytes. Multi-byte quantities are stored in **big-endian** order (most significant byte first). The standard notations are `u1`, `u2`, `u4`: unsigned values occupying 1, 2, and 4 bytes.

General structure of `ClassFile`:

~~~text
ClassFile {
    u4 magic;
    u2 minor_version;
    u2 major_version;
    u2 constant_pool_count;
    cp_info constant_pool[constant_pool_count - 1];
    u2 access_flags;
    u2 this_class;
    u2 super_class;
    u2 interfaces_count;
    u2 interfaces[interfaces_count];
    u2 fields_count;
    field_info fields[fields_count];
    u2 methods_count;
    method_info methods[methods_count];
    u2 attributes_count;
    attribute_info attributes[attributes_count];
}
~~~

This is a **descriptive structure in the specification**, not a compilable C or Java declaration. Items are encoded sequentially according to the class-file format, not as a native struct with operating system alignment.

| Part | Role |
| --- | --- |
| `magic` | First four bytes identifying the format: `CA FE BA BE` |
| `minor_version`, `major_version` | Class-file version that the JVM must support |
| `constant_pool_count` / `constant_pool` | Constant table and symbolic references: classes, names, descriptors, strings, method handles... |
| `access_flags` | Access/characteristic flags of the type |
| `this_class`, `super_class` | Constant-pool references for the current class and superclass, subject to JVMS constraints |
| `interfaces` | Declared interfaces |
| `fields` | Fields and their metadata |
| `methods` | Methods and attributes; method bytecode is usually in the `Code` attribute |
| `attributes` | Class metadata, such as source info, annotations, nest/record/module... when present |

**Header section with fixed offsets** when reading from the start of the array:

| 0-based offset | Length | Item | Java 17 class example |
| --- | --- | --- | --- |
| 0–3 | 4 bytes | `magic` | `CA FE BA BE` |
| 4–5 | 2 bytes | `minor_version` | `00 00` |
| 6–7 | 2 bytes | `major_version` | `00 3D` (61 decimal) |
| 8–9 | 2 bytes | `constant_pool_count` | Varies with class content |
| From 10 | Variable | `constant_pool` then subsequent sections | No general fixed offset |

Do not assume `methods_count` is always at a fixed offset: entries in the constant pool have different sizes, and intermediate tables also have variable lengths. For example, `CONSTANT_Long_info` and `CONSTANT_Double_info` take up **two indices** in the constant pool. Therefore, `constant_pool_count - 1` **should not be mechanically interpreted** as the number of Java objects or the number of bytecode instructions.

### 2.1. Why is `CA FE BA BE` important but not sufficient?

The four bytes `CA FE BA BE` at the beginning are the **magic number**. It helps quickly identify data that may belong to the class-file format. However:

- An array containing only the four magic bytes **is not** a valid class file.
- A valid header with an invalid constant pool, invalid method descriptor, or code that fails verifier rules can still be rejected by the JVM.
- Checking `major_version` alone does not replace checking the entire structure and constraints of the class file.
- A byte stream from an untrusted source must be treated as input requiring validation, not as "safe" just because it has the right magic number.

### 2.2. What does the major version indicate?

Some common milestones:

| Java release | Class-file major |
| --- | --- |
| Java 8 | 52 |
| Java 11 | 55 |
| Java 17 | 61 |
| Java 21 | 65 |
| Java 24 | 68 |

The table above shows the **corresponding default version** when the compiler emits a class file for that release. For example, running `javac --release 17` on a JDK that supports that option will output class-file **major 61**, even though the JDK running the compiler may be newer.

If you feed a class with a major version higher than what the JVM supports into an older JVM, you may get `UnsupportedClassVersionError`. This is a **format/runtime capability** issue, not something that can be fixed by simply renaming the file from `.class` to `.bin`. Some preview feature cases also have specific minor version rules that should not be ignored when building general-purpose class-file readers.

## 3. Bytecode, class file, `Class<?>`, and machine code are not the same thing

A common conceptual mistake is calling everything related to a class "bytecode in RAM." There are at least four layers:

~~~text
Java source
    | javac / compiler
    v
Class-file bytes: header + constant pool + fields/methods/attributes
    | ClassLoader + JVM loading/linking
    v
Runtime class metadata + Class<?> mirror
    | execution / interpreter / JIT when needed
    v
Runtime activity: objects, stack frames, JIT machine code (if any)
~~~

- **Java source** is text such as `public class Greeting { ... }`.
- **Class-file bytes** are a structured binary representation. In many methods, the `Code` section contains **JVM instructions**; the entire class file also contains metadata, not just instructions.
- **`Class<?>`** is a Java object reflecting a type defined in the JVM. It is not a "`byte[]` view" of the class file.
- **JIT machine code** is the result of optimization depending on the runtime and timing, not the `.class` content. A JVM can execute bytecode using an interpreter without requiring a separate `.class` file stored on disk for each class.

**Example:** When `ClassLoader#defineClass` receives a valid `byte[]`, it creates a runtime type; calling a static method of that type can trigger class initialization. Dropping the reference to the source array **does not mean** the runtime class will automatically disappear immediately, nor does it force the JVM to JIT-compile it right away.

The term "class file" in the specification can refer to **a representation in the class-file format**, even if it has never been written to the filesystem. That is the core point of this topic.

## 4. Where can class-file bytes come from?

| Source | Data at the point the JVM/tool receives it | Usage example |
| --- | --- | --- |
| Physical `.class` file | Read the file into a byte array or stream | `Files.readAllBytes(path)` |
| JAR/JMOD and suitable package formats | Read entry/resource into bytes | Classpath or module mechanism |
| Compiler running inside the application | Byte array returned by `javax.tools.JavaCompiler` via a custom file manager | Plugins, rule engines, code generation |
| Bytecode generation library | A complete `byte[]` conforming to the JVMS | Proxies/codegen and build tools |
| Another system supplying data | Bytes transferred over IPC, network, cache, or database | Custom loader/plugin with validation |
| Java agent/transformer | `classfileBuffer` supplied by the JVM in the callback | Observing or producing transformed bytes |

One of the simplest ways to get bytes is:

~~~java
byte[] classBytes = java.nio.file.Files.readAllBytes(
        java.nio.file.Path.of("Example.class"));
~~~

This is just a **code snippet that can be placed in a method declaring/handling `IOException`**. It still **reads from disk**, then puts the contents into a `byte[]`. To prove that **the generated class file does not need to be written to disk**, the example in the next section compiles in memory, intercepting the output path with a custom file manager.

Conversely, do not assume that **every** running class can retrieve the exact original `byte[]` from when it was loaded. `Class<?>` does not provide a standard "getOriginalClassFileBytes()" method. A class may have been transformed, dynamically generated, hidden behind a class loader, or lack a resource on disk.

## 5. Standalone Java 17+ example: compiling a class into a `byte[]` without writing its `.class` to disk

This exercise uses the **JavaCompiler API** (`java.compiler` module) and a custom `ForwardingJavaFileManager`. The Java source of the target class is held in a `String`, compiler output is captured into a `ByteArrayOutputStream`, and the `byte[]` is then passed to a custom `ClassLoader#defineClass`.

**Purpose of the example:** to show that the class `demo.MemoryHello` can be compiled and loaded in a **single JVM run**, even without creating the file `demo/MemoryHello.class` on the filesystem. `InMemoryClassDemo.class` itself—the runner program—is still compiled with `javac` in the usual way to launch. You should not claim that "the entire JDK does not read any files at all."

### 5.1. Full source code

**File: `InMemoryClassDemo.java`**

~~~java
import java.io.ByteArrayOutputStream;
import java.io.IOException;
import java.io.OutputStream;
import java.net.URI;
import java.nio.ByteBuffer;
import java.nio.ByteOrder;
import java.nio.charset.StandardCharsets;
import java.util.HashMap;
import java.util.List;
import java.util.Locale;
import java.util.Map;
import javax.tools.DiagnosticCollector;
import javax.tools.FileObject;
import javax.tools.ForwardingJavaFileManager;
import javax.tools.JavaCompiler;
import javax.tools.JavaFileManager;
import javax.tools.JavaFileObject;
import javax.tools.SimpleJavaFileObject;
import javax.tools.StandardJavaFileManager;
import javax.tools.ToolProvider;

public final class InMemoryClassDemo {
    private static final class Source extends SimpleJavaFileObject {
        private final String source;
        Source(String name, String source) {
            super(URI.create("string:///" + name.replace('.', '/')
                    + Kind.SOURCE.extension), Kind.SOURCE);
            this.source = source;
        }
        @Override
        public CharSequence getCharContent(boolean ignoreEncodingErrors) {
            return source;
        }
    }

    private static final class ByteCode extends SimpleJavaFileObject {
        private final ByteArrayOutputStream bytes = new ByteArrayOutputStream();
        ByteCode(String name, Kind kind) {
            super(URI.create("memory:///" + name.replace('.', '/')
                    + kind.extension), kind);
        }
        @Override
        public OutputStream openOutputStream() {
            return bytes;
        }
        byte[] toByteArray() {
            return bytes.toByteArray();
        }
    }

    private static final class MemoryFiles
            extends ForwardingJavaFileManager<JavaFileManager> {
        private final Map<String, ByteCode> compiled = new HashMap<>();
        MemoryFiles(JavaFileManager base) {
            super(base);
        }
        @Override
        public JavaFileObject getJavaFileForOutput(
                Location location, String className,
                JavaFileObject.Kind kind, FileObject sibling) throws IOException {
            ByteCode code = new ByteCode(className, kind);
            compiled.put(className, code);
            return code;
        }
        byte[] bytesFor(String name) {
            ByteCode code = compiled.get(name);
            if (code == null) {
                throw new IllegalStateException("No compiled class: " + name);
            }
            return code.toByteArray();
        }
    }

    private static final class MemoryLoader extends ClassLoader {
        MemoryLoader() {
            super(ClassLoader.getPlatformClassLoader());
        }
        Class<?> define(String binaryName, byte[] bytes) {
            return defineClass(binaryName, bytes, 0, bytes.length);
        }
    }

    public static void main(String[] args) throws Exception {
        JavaCompiler compiler = ToolProvider.getSystemJavaCompiler();
        if (compiler == null) {
            throw new IllegalStateException(
                    "Run with a JDK, not a minimal JRE");
        }
        String binaryName = "demo.MemoryHello";
        String source = "package demo; public class MemoryHello { "
                + "public static String message() { "
                + "return \"Hello from RAM\"; } }";
        DiagnosticCollector<JavaFileObject> diagnostics =
                new DiagnosticCollector<>();
        byte[] classBytes;

        try (StandardJavaFileManager standard =
                     compiler.getStandardFileManager(
                             diagnostics, Locale.ROOT, StandardCharsets.UTF_8);
             MemoryFiles memory = new MemoryFiles(standard)) {
            boolean success = Boolean.TRUE.equals(compiler.getTask(
                    null, memory, diagnostics, List.of("--release", "17"),
                    null, List.of(new Source(binaryName, source))).call());
            if (!success) {
                throw new IllegalStateException("Compilation failed: "
                        + diagnostics.getDiagnostics());
            }
            classBytes = memory.bytesFor(binaryName);
        }

        ByteBuffer header = ByteBuffer.wrap(classBytes)
                .order(ByteOrder.BIG_ENDIAN);
        long magic = Integer.toUnsignedLong(header.getInt());
        int minor = Short.toUnsignedInt(header.getShort());
        int major = Short.toUnsignedInt(header.getShort());
        int cpCount = Short.toUnsignedInt(header.getShort());
        System.out.printf("magic=%08X%n", magic);
        System.out.println("minor=" + minor);
        System.out.println("major=" + major);
        System.out.println("constantPoolCountPositive=" + (cpCount > 1));
        System.out.println("byteArrayNonEmpty=" + (classBytes.length > 0));

        MemoryLoader loader = new MemoryLoader();
        Class<?> type = loader.define(binaryName, classBytes);
        System.out.println("name=" + type.getName());
        System.out.println("customLoader=" + (type.getClassLoader() == loader));
        System.out.println("message="
                + type.getMethod("message").invoke(null));
    }
}
~~~

### 5.2. Compiling and running

A **full JDK** is required (not a runtime image stripped of the compiler module). On Java 17 or a newer JDK that supports `--release 17`:

~~~bash
javac --release 17 InMemoryClassDemo.java
java InMemoryClassDemo
~~~

**Exact stdout of the example**, tested when compiled with `--release 17` and run with a JDK containing the compiler:

~~~text
magic=CAFEBABE
minor=0
major=61
constantPoolCountPositive=true
byteArrayNonEmpty=true
name=demo.MemoryHello
customLoader=true
message=Hello from RAM
~~~

In this example, `major=61` is a consequence of `--release 17`; `minor=0` indicates a version without preview features. Constant pool contents can vary by compiler and optimizations, so the example **does not print the specific numeric value** of `cpCount`, only verifying that it is a non-empty table.

If the environment lacks the compiler module or `ToolProvider.getSystemJavaCompiler()` returns `null`, this is a **limitation of the runtime environment**, not proof that "class files must reside on disk."

### 5.3. Step-by-step analysis of the example

**Step 1 — `Source`:** `SimpleJavaFileObject` with `Kind.SOURCE` supplies Java source from a `String` via `getCharContent`. The `string:///...` URI serves as a **logical identifier** for the source, without creating a file on the filesystem.

**Step 2 — `ByteCode`:** A `JavaFileObject` of kind `CLASS` accepts output via `openOutputStream()` and stores the bytes in a `ByteArrayOutputStream`. The `memory:///...` URI is also only an output-identifying URI. There is no `FileOutputStream` or `Files.write` for the generated class.

**Step 3 — `MemoryFiles`:** By overriding `getJavaFileForOutput(...)`, we instruct the compiler to write compilation output into an in-memory object. The `compiled` map associates the **binary class name** with its bytes. In a real system, if one source produces multiple classes/nested classes, the file manager needs to retain and handle loading/reading **each output** appropriately.

**Step 4 — `JavaCompiler.getTask`:** The compiler receives the `JavaFileObject` source, file manager, diagnostics, and the `--release 17` option. `call()` performs compilation and returns a `Boolean`; do not infer success merely because the map already contains some bytes. The example checks for failure and reports diagnostics.

**Step 5 — reading the header:** `ByteBuffer.wrap(classBytes)` allows reading bytes already on the heap without opening a file. `getInt()` and `getShort()` read in **big-endian** order; `Integer.toUnsignedLong` and `Short.toUnsignedInt` preserve the unsigned semantics of the JVMS fields. The four magic bytes are printed in hex using `%08X`.

**Step 6 — `defineClass`:** `MemoryLoader` is a custom class loader that passes `binaryName` and the byte array to `ClassLoader#defineClass` (which is `protected`). The JVM defines the `demo.MemoryHello` type from that data. Setting the parent to the platform class loader allows the new class to still reference Java platform classes and avoids depending on a `demo/MemoryHello.class` file on the application classpath.

**Step 7 — execution:** `type.getMethod("message").invoke(null)` invokes the static method of the newly defined class, producing `Hello from RAM`. At this point the JVM has a runtime type and executes the method; that is a **different step** from merely possessing a `byte[]` in the class-file format.

**Experimental conclusion:** the main program may appear as an `InMemoryClassDemo.class` file, but **the target class `demo.MemoryHello` does not need a `demo/MemoryHello.class` file**. The compiler and loader exchange class-file bytes directly in memory.

## 6. Simple header checking is not the same as writing a complete class-file parser

The following snippet shows the idea of reading the first 10 bytes:

~~~java
if (bytes.length < 10) {
    throw new IllegalArgumentException("Too short for class-file header");
}
java.nio.ByteBuffer header = java.nio.ByteBuffer.wrap(bytes)
        .order(java.nio.ByteOrder.BIG_ENDIAN);
int magic = header.getInt();
int minor = Short.toUnsignedInt(header.getShort());
int major = Short.toUnsignedInt(header.getShort());
int cpCount = Short.toUnsignedInt(header.getShort());
if (magic != 0xCAFEBABE) {
    throw new IllegalArgumentException("Wrong class-file magic");
}
~~~

This is a **code snippet inside a method that already has `byte[] bytes`**. The hex literal `0xCAFEBABE` is a signed Java `int`, but bit-pattern comparison still works; the full example uses `Integer.toUnsignedLong` to print an unsigned hex string for readability.

**Checking only the header is a preliminary check**: a complete parser must also understand constant-pool entry types, variable lengths, field/method descriptors, attributes, code structure, and version-specific constraints. Manually "slicing bytes at some offset" without knowing the JVMS can easily corrupt a class file.

When you only want to inspect the structure from a compiled file, you can use the JDK tool:

~~~bash
javap -verbose InMemoryClassDemo
~~~

`javap` lets you view the constant pool, major version, methods, and attributes supported by the tool. However, note that it is reading the **demo program's class** from the classpath. To inspect the bytes of `demo.MemoryHello` generated in RAM, you must explicitly save those bytes to a file for `javap` to read **or** use an appropriate parser API directly on the `byte[]`.

Starting in **JDK 24**, Java has the standardized `java.lang.classfile` API for reading/generating/transforming class-file structures (JEP 484); on Java 17, this standard package does not exist yet. If you want a parser on Java 17, you can use a suitable library or implement a clearly scoped subset yourself, rather than assuming `ClassFile.of()` compiles on every JDK.

## 7. Loading a class from `byte[]`: loading, linking, and initialization are distinct phases

For a class with valid bytes, defining and using it in the JVM involves these activities:

~~~text
Class-file bytes
      |
      v
Loading / defining       -> ClassLoader#defineClass(...)
      |
      v
Linking                  -> verification + preparation + resolution when needed
      |
      v
Initialization           -> executing class initializer when triggered
      |
      v
Invocation/instantiation -> calling methods / creating objects per JVM rules
~~~

These phases have points that can be **deferred** according to the JVMS; the diagram shows logical boundaries, not a claim that the JVM always performs every operation in one sequential pass at the moment `defineClass` is called.

- **Loading** creates/defines a class from its class-file representation. A class loader may use a file mechanism, resource, dynamic compiler, or self-generated bytes.
- **Verification** ensures the format, data-type, and instruction constraints required by the JVM. An invalid byte array can lead to errors.
- **Preparation** allocates/initializes default values for static fields in runtime structures according to JVM rules.
- **Resolution** converts symbolic references into runtime references, which may be deferred.
- **Initialization** executes `<clinit>` when usage triggers it. `defineClass` by itself does not mean all static initializers of all related types have already run.

The example in Section 5 calls a public static method via reflection after `defineClass`, going beyond "merely having bytes in an array." If you only read the `CA FE BA BE` header, you **have not loaded the class yet**; if you already have `Class<?>`, you **do not automatically have an exact copy of the original file's bytes**.

### 7.1. Class identity is not just its name

The JVM distinguishes runtime types by **binary name** and **defining class loader**. Two different class loaders can define two types with the same binary name, yet they are **not the same `Class<?>`**.

~~~text
Loader A + "demo.MemoryHello" -> Class<?> A
Loader B + "demo.MemoryHello" -> Class<?> B

Same name; different runtime identities.
~~~

This matters when using an in-memory loader for plugins or generated code: an instance created from a class defined by loader A **cannot naturally be cast** to a class of the same name defined by loader B. A normal class loader also has **delegation** and security policies; you should not bypass the parent loader mechanism without a deliberate reason.

When using `defineClass(binaryName, bytes, ...)`, the passed binary name must match the name described in the class file. You cannot validly rename a class merely by changing the `binaryName` string in the call; that metadata lives inside the class-file bytes themselves.

## 8. In-memory byte scenarios in instrumentation

This is the direct connection to the **Java Advance - instrumentation** module. A Java agent can receive `ClassFileTransformer` callbacks when the JVM defines or transforms a class.

**Code snippet** example, not a standalone program:

~~~java
@Override
public byte[] transform(
        ClassLoader loader,
        String className,
        Class<?> classBeingRedefined,
        java.security.ProtectionDomain domain,
        byte[] classfileBuffer) {

    // classfileBuffer contains the bytes for the transformation currently being processed.
    if (className == null || !className.startsWith("example/app/")) {
        return null;
    }

    // Analyze classfileBuffer when needed, but do not mutate the input array.
    // Return null if not transforming this class.
    return null;
}
~~~

This snippet lives in a class implementing `java.lang.instrument.ClassFileTransformer`. A transformer **does not necessarily receive a `.class` file path**; it receives the class-file representation as a `byte[]` from the JVM. This is why a Java agent can observe classes generated dynamically in memory.

Under the transformer contract:

- `return null`: the transformer **does not modify** the class bytes for that invocation.
- Returning a new `byte[]`: proposes transformed class-file content, which must still be valid according to the JVMS and the corresponding redefinition/retransformation restrictions.
- **Do not mutate** the `classfileBuffer` passed in by the JVM. When using ASM/Byte Buddy/Class-File API on supported versions, create new bytes and preserve the input data per the contract.
- **Exclude agent/helper/logger classes** and filter class names early, avoiding instrumenting the instrumentation mechanism itself.
- `className` in the callback is typically in internal form `example/app/Service`, differing from the dot-separated binary name of `Class#getName()`.

Classes can be transformed by the JVM/agent without a `Service.class` file existing on disk at an accessible location. Therefore, finding the "original file path" is not a required part of the transformer contract.

### 8.1. Bytes of a defined class do not equal "source code"

An agent sees class-file bytes, **not necessarily Java source**. What can be analyzed includes method descriptors, the constant pool, code attributes, and metadata retained after compilation; Java comments and much source-level information are usually gone. `SourceFile` or line-number metadata (if emitted by the compiler) does not fully reconstruct the original source code.

A decompiler is a tool that **reconstructs** Java-like source from bytecode, not a "verbatim decoder" of every character in a `.java` file. This also holds true when a class file exists only as bytes in memory.

## 9. The `byte[]` array is still mutable: ownership and consistency

**The class-file format is a binary standard; `byte[]` is a mutable Java data type.** Do not confuse "compiled class" with "its byte array is immutable."

Example:

~~~java
byte[] safeSnapshot = originalBytes.clone();
java.nio.ByteBuffer header =
        java.nio.ByteBuffer.wrap(safeSnapshot)
                .order(java.nio.ByteOrder.BIG_ENDIAN);
~~~

This is a code snippet in a method that has `originalBytes`. Cloning creates a **copy**, but assumes the caller ensures no writes occur to `originalBytes` during the clone. `ByteBuffer.wrap` **does not copy** the array; if someone still holds `safeSnapshot` and modifies it, the buffer will see the changed content.

Operational principles:

1. **Clear ownership:** which thread creates/modifies the bytes; when it is permitted to publish them to another worker.
2. **Do not hold uncontrolled mutable references:** bytes received from a library/plugin may be reused or mutated under its own contract.
3. **Do not share a builder/stream while writing:** wait until compilation/transformation completes before taking a snapshot.
4. **Cache by content/version when needed:** the same binary class name can correspond to different versions of bytes; the class loader also affects runtime identity.
5. **Monitor resources:** keeping thousands of large arrays alive simultaneously can increase heap/GC pressure; use appropriate bounding/release mechanisms.
6. **Do not assume dropping bytes will unload the class:** runtime class unloading depends on the class loader, reachability, and JVM decisions, not just local variable scope.

When multiple threads need to read headers independently, you can copy the bytes or ensure a snapshot is not mutated after publication using proper Java Memory Model visibility mechanisms. A `ByteBuffer.asReadOnlyBuffer()` only creates a **read-only view through that buffer**; if another mutable reference to the backing array exists, the data can still be modified.

## 10. Conditions and errors when loading invalid bytes

A class loader should not accept bytes from an untrusted source and define a class without a control policy. The JVM checks format/bytecode, but **valid bytecode can still execute unsafe behavior for the application**, such as reading files or calling network APIs under runtime permissions.

| Symptom | Common cause | How to check |
| --- | --- | --- |
| `UnsupportedClassVersionError` | Major/minor version not supported by the JVM | Check `major_version` and target JVM version |
| `ClassFormatError` | Invalid class-file structure / constant pool / attribute | Validate bytes against the JVMS, parser/verifier |
| `VerifyError` | Invalid verifier constraint or bytecode data types | Inspect verifier message, transformer/generator bug |
| `NoClassDefFoundError` | Name in bytes does not match requested name or missing dependency class at link time | Check binary name and classpath/loader |
| `LinkageError` | Definition conflict, dependency, name, or linking constraint violation | Check defining loader and specific cause |
| `ClassNotFoundException` | Loader was asked but could not find or create the class | Distinct from invalid-bytes errors inside `defineClass` |
| `IllegalAccessError`/`IncompatibleClassChangeError` | Incompatible access constraints or runtime structure | Compare class versions and dependencies |
| `ToolProvider.getSystemJavaCompiler() == null` | Runtime does not provide the system compiler | Run with a full JDK or use another available compiler |

**A valid magic number does not rule out the errors above.** The JVM verifier helps protect instruction-level format correctness, but **does not replace** source authentication policies, access control, and compatibility testing for externally supplied code.

With code generation, you must actively manage the volume of generated classes: each defining loader/type can consume runtime metadata; if many classes are generated and loaders are kept alive for a long time, the memory footprint can grow. Do not design a mechanism that "generates a new class per request" without understanding class/loader reclamation.

## 11. Mental model for choosing tools

| Practical goal | Approach and rationale |
| --- | --- |
| Only check the version of a class file on disk | `javap -verbose` or read the 10-byte header |
| Analyze an unloaded class file | Read `byte[]` with an appropriate class-file parser; no `Class.forName` needed |
| Create a runtime class without writing the target class file | In-memory `JavaCompiler` + file manager + `defineClass`, as in the example |
| Generate dynamic proxies/helpers | Bytecode generator and class-loader/lookup suited to the security model |
| Instrument a class as it is being loaded | Java agent `ClassFileTransformer` receives class bytes, returns new bytes or `null` |
| Replace an already-loaded class | `Instrumentation` with retransform/redefine when supported; cannot just call `defineClass` again with the same loader and name |
| Use the same name for multiple class versions | Separate class loaders; design proper isolation/caching/versioning |
| Analyze multiple byte arrays across multiple threads | Clear byte ownership or copying; avoid concurrent writes and shared mutable parsing state |

Note that `ClassLoader#defineClass` **defines a new type in the loader**, not an API to "overwrite an existing class." Attempting to redefine the same binary name in the same loader typically causes a `LinkageError`; to instrument/redefine a running class, you must use the proper JVM mechanism and satisfy its corresponding constraints.

## 12. Misconceptions to avoid

1. **"Without a `.class` file on disk, the JVM cannot run it."** False: the class-file format can reside in a byte array or another source supplied by a loader.
2. **"A `byte[]` array is a `Class<?>` object."** False: before and after loading are two different concepts.
3. **"A class file only contains instructions."** False: it also contains the header, constant pool, fields, methods, and attributes.
4. **"The four bytes `CAFEBABE` are enough to define a class."** False: the entire structure and verification are also required.
5. **"`major=61` means the current machine is definitely running Java 17."** False: it indicates the class was compiled for the Java 17 format; the runtime JVM can be newer.
6. **"`ByteBuffer.wrap` copies the bytes."** False: it uses the provided backing array.
7. **"Changing the `defineClass` parameter renames the class inside the bytes."** False: the class-file content must describe the matching name.
8. **"Two classes with the same name are always the same type."** False: the defining class loader is part of the identity.
9. **"The JVM must store original bytes as a file and a public API lets you retrieve them."** False: neither that mechanism nor access to original bytes is guaranteed.
10. **"A valid class file is automatically safe to run."** False: valid bytecode is still code that can perform dangerous actions under the application's permissions.
11. **"An agent can modify the `classfileBuffer` array directly."** False: per the transformer contract, a new array must be returned when transforming.
12. **"Calling `defineClass` definitely runs the static initializer."** False: initialization has its own conditions and timing according to the JVM.
13. **"Not creating a class file means the compiler cannot use JDK/modules from disk."** False: only the generated output class in the example is kept in memory; the compiler may still need to access JDK components.

## 13. Self-check questions and exercises

1. If an application receives a `byte[]` from the network, what conditions are needed before `defineClass` can be called successfully?
2. What do the four bytes at offsets 0–3 and the two bytes at offsets 6–7 mean respectively?
3. Why can't `methods_count` be read using a fixed offset across all class files?
4. When running the example on JDK 21 with `--release 17`, what is `major`? Why?
5. Why does `type.getMethod("message").invoke(null)` prove more than just printing the header bytes?
6. At which step does `MemoryFiles.getJavaFileForOutput` help avoid creating the `demo/MemoryHello.class` file?
7. Why is `type.getClassLoader() == loader` worth checking when loading a dynamically generated class?
8. If you create a second `MemoryLoader` and define `demo.MemoryHello` from the same bytes, are the two `Class<?>` objects equal by identity?
9. If you modify a random byte in the constant pool, will the JVM definitely reject it at `defineClass`, or could the error appear during linking/usage? Why should you follow the JVM contract instead of guessing?
10. Why must you not write into the `classfileBuffer` passed to `ClassFileTransformer`?
11. Does `Class<?>` provide a method to retrieve the exact bytes emitted by the compiler?
12. For a class-file byte array that exists only in RAM, must a corresponding `Path` necessarily exist?

**Key takeaway:** "`.class`" is a common storage format, whereas **the class-file format is a binary structure that can be fully represented by a `byte[]`**. The JVM needs **valid byte content and an appropriate loading/defining mechanism**, not necessarily a physical file for that class. The Java compiler, class loader, and Java agent all have interfaces that work directly with bytes; distinguish bytes, runtime classes, and machine code, while controlling version, class loader, mutability, and data origin.
