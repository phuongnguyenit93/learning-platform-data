# Phân biệt chuẩn SQL, phần mở rộng và mức hỗ trợ theo phiên bản

Hai hệ quản trị có thể cùng được gọi là “database SQL” nhưng không nhất thiết chạy cùng một câu lệnh. Một câu SELECT đơn giản thường dễ chuyển đổi; đến lúc dùng kiểu dữ liệu JSON, cú pháp tạo ID tự tăng, UPSERT, hàm ngày giờ, phân trang, khóa, transaction hoặc DDL thì khác biệt xuất hiện.

Muốn viết SQL chạy được trên nhiều hệ quản trị, cần phân biệt ba lớp:

1. **Chuẩn SQL:** cú pháp và ngữ nghĩa được mô tả trong tiêu chuẩn quốc tế.
2. **Phần mở rộng của nhà cung cấp:** cú pháp hoặc tính năng riêng của PostgreSQL, MySQL, SQL Server, Oracle, SQLite hoặc một sản phẩm cụ thể.
3. **Mức hỗ trợ theo phiên bản:** một tính năng chuẩn hoặc mở rộng có thể chỉ xuất hiện từ một phiên bản, bị giới hạn, có hành vi thay đổi hoặc phụ thuộc cấu hình/edition.

Ví dụ cùng một mục đích tạo bảng có ID tự sinh:

~~~sql
-- PostgreSQL
CREATE TABLE orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
);

-- MySQL
CREATE TABLE orders (
    id BIGINT AUTO_INCREMENT PRIMARY KEY
);

-- SQL Server
CREATE TABLE orders (
    id BIGINT IDENTITY(1,1) PRIMARY KEY
);

-- SQLite
CREATE TABLE orders (
    id INTEGER PRIMARY KEY
);
~~~

Các câu lệnh trên không giống nhau về cú pháp và cũng không hoàn toàn đồng nhất về semantics. Chúng đều có thể tạo ID tự sinh, nhưng quy tắc sequence, giá trị được phép chèn tường minh, kiểu lưu trữ, transaction và cách lấy ID vừa tạo khác nhau.

Bài học thuộc module **Database SQL**, chương **SQL đa hệ quản trị**, chủ đề **“Phân biệt chuẩn SQL, phần mở rộng và mức hỗ trợ theo phiên bản”**. Nội dung lấy các hệ quản trị phổ biến làm ví dụ, hướng đến cách thiết kế ứng dụng có khả năng chuyển đổi và vận hành lâu dài.

## 1. Mục tiêu học tập

Sau bài này, bạn có thể:

1. Giải thích chuẩn SQL là gì và vì sao “có hỗ trợ SQL” không có nghĩa mọi DBMS thực thi cùng một cú pháp.
2. Phân biệt cú pháp chuẩn, optional feature, vendor extension, implementation-defined behavior và giới hạn của phiên bản.
3. Hiểu vì sao SQL conformance không phải một nhãn đơn giản “đạt chuẩn/không đạt chuẩn”.
4. Nhận diện các khác biệt về identifier, kiểu dữ liệu, NULL, hàm, ngày giờ, phân trang, DML, transaction và DDL.
5. So sánh cách tạo ID, UPSERT, RETURNING/OUTPUT, JSON, CTE, window function, generated columns và temporal tables.
6. Hiểu một số mốc phiên bản quan trọng của PostgreSQL, MySQL/MariaDB, SQL Server, Oracle và SQLite.
7. Phân biệt phiên bản database server, compatibility level, JDBC driver, client và cấu hình session.
8. Chọn cách viết SQL portable hoặc cô lập dialect-specific SQL trong tầng truy cập dữ liệu.
9. Thiết kế kiểm thử tương thích trên nhiều DBMS và phiên bản thực tế.
10. Biết cách kiểm tra feature/capability thay vì chỉ suy đoán theo tên sản phẩm.
11. Tránh những lỗi chuyển đổi âm thầm làm thay đổi kết quả, nullability, độ chính xác hoặc tính nguyên tử.
12. Hoàn thành bài tập nhận diện chuẩn, extension và giới hạn phiên bản.

## 2. Chuẩn SQL là gì?

SQL được chuẩn hóa trong họ tiêu chuẩn quốc tế **ISO/IEC 9075**, thường được gọi chung là SQL Standard. Các phiên bản tiêu chuẩn được phát triển qua nhiều năm; ví dụ các thế hệ thường được nhắc đến gồm SQL-92, SQL:1999, SQL:2003, SQL:2008, SQL:2011, SQL:2016 và các bản sửa đổi/ấn bản sau đó.

Chuẩn mô tả nhiều phần của ngôn ngữ:

- Data Definition Language (DDL): tạo, sửa, xóa đối tượng.
- Data Manipulation Language (DML): SELECT, INSERT, UPDATE, DELETE và các thao tác dữ liệu.
- Kiểu dữ liệu và chuyển đổi kiểu.
- Constraint và integrity.
- Transaction và isolation.
- Routine, trigger, dynamic SQL.
- JSON, temporal, analytics và các nhóm tính năng được bổ sung qua các thế hệ chuẩn.

### 2.1. Chuẩn không phải một bộ cú pháp nhỏ bất biến

SQL Standard phát triển theo phiên bản. Một tính năng có thể:

- Chưa tồn tại trong một edition cũ.
- Được thêm vào edition mới.
- Là optional feature mà DBMS có thể chọn hỗ trợ hoặc không.
- Có cú pháp chuẩn nhưng sản phẩm chỉ hỗ trợ một phần.
- Có quy định chuẩn nhưng implementation có giới hạn do kiến trúc hoặc sản phẩm.

Vì thế, khi nói “câu lệnh này là SQL chuẩn”, cần hỏi thêm: **chuẩn phiên bản nào, tính năng nào, DBMS nào và phiên bản sản phẩm nào?**

### 2.2. SQL chuẩn không có nghĩa mọi sản phẩm đều giống nhau

Một hệ quản trị có thể tuân theo nhiều phần quan trọng của SQL Standard, nhưng vẫn cung cấp hàng trăm tính năng riêng. Một sản phẩm khác có thể hỗ trợ cùng tính năng với cú pháp hoặc giới hạn khác.

Không nên kết luận:

- “DBMS A hỗ trợ SQL, vậy câu lệnh DBMS B chạy được.”
- “Cú pháp có trong tài liệu SQL chuẩn, vậy tất cả phiên bản đều có.”
- “Hai câu lệnh cho cùng kết quả trên một bộ dữ liệu nhỏ, vậy semantics giống nhau.”

Cần xét cả **cú pháp, kiểu dữ liệu, NULL, transaction, concurrency, lỗi và quyền**.

## 3. Các mức hỗ trợ và tính phù hợp với chuẩn

### 3.1. Core features và optional features

Một tiêu chuẩn lớn có thể chia thành nhiều phần và tính năng. Một sản phẩm thường hỗ trợ một tập con. Một tính năng được mô tả trong tiêu chuẩn không nhất thiết bắt buộc phải có ở mọi implementation.

Ví dụ, một DBMS có thể hỗ trợ:

- SELECT, JOIN, GROUP BY, ORDER BY.
- CTE và recursive query.
- Window functions.
- JSON functions.
- Temporal features.
- Routines và triggers.

Nhưng mức hỗ trợ, cú pháp, giới hạn và phiên bản xuất hiện khác nhau.

### 3.2. SQL conformance không phải điểm số duy nhất

Một DBMS không đơn giản được xếp loại “chuẩn 100%” hoặc “không chuẩn”. Tính phù hợp thường được xét theo các phần, tính năng và quy định cụ thể của tiêu chuẩn.

Khi đọc tài liệu nhà cung cấp, hãy tìm:

- SQL conformance statement.
- Feature support matrix.
- Những optional features được hỗ trợ.
- Những phần không hỗ trợ hoặc hỗ trợ một phần.
- Khác biệt semantics và implementation limits.

### 3.3. Implementation-defined và implementation-dependent

Hai khái niệm này giúp hiểu vì sao cùng một chuẩn vẫn có thể có khác biệt.

- **Implementation-defined:** tiêu chuẩn để implementation lựa chọn một chi tiết, và implementation phải công bố lựa chọn đó.
- **Implementation-dependent:** kết quả phụ thuộc implementation theo một khía cạnh được tiêu chuẩn cho phép, không nhất thiết có cùng một lựa chọn bắt buộc công bố như trường hợp trên.

Trong thực tế ứng dụng, điều cần làm là tìm tài liệu của sản phẩm, kiểm tra cấu hình và viết test cho các hành vi ảnh hưởng dữ liệu.

### 3.4. Extension không tự động là sai

Vendor extension là phần mở rộng của nhà cung cấp. Nó có thể đem lại:

- Tính năng hiệu năng cao.
- Khả năng thao tác dữ liệu đặc thù.
- Cấu trúc kiểu dữ liệu phong phú.
- Công cụ vận hành, giám sát và bảo mật.
- Cú pháp tiện lợi mà SQL chuẩn chưa có hoặc sản phẩm chưa triển khai.

Vấn đề không phải “extension luôn xấu”. Vấn đề là **biết rõ nơi nào phụ thuộc extension và kiểm soát sự phụ thuộc ấy**.

## 4. Ba câu hỏi trước khi dùng một tính năng SQL

Khi gặp một cú pháp mới, hãy phân loại theo ba bước:

~~~text
Câu lệnh / tính năng cần dùng
             │
             ▼
Có trong SQL Standard không?
       ┌─────┴─────┐
       │           │
      Có          Không / chưa rõ
       │           │
       ▼           ▼
DBMS có hỗ trợ?   Vendor extension?
       │           │
       └─────┬─────┘
             ▼
Phiên bản tối thiểu nào?
             │
             ▼
Có phụ thuộc edition, config,
compatibility level, driver,
extension hoặc storage engine?
             │
             ▼
Test cú pháp + semantics + lỗi
~~~

Ví dụ: `RETURNING` có thể được hỗ trợ trong PostgreSQL, SQLite và MariaDB ở các ngữ cảnh phù hợp; SQL Server dùng `OUTPUT` cho mục đích tương tự; MySQL không nên được giả định có cùng cú pháp RETURNING như PostgreSQL. Một câu lệnh có thể cùng mục đích nhưng không cùng grammar.

## 5. Cú pháp chuẩn, extension và khác biệt implementation

| Nhóm | Đặc điểm | Ví dụ |
|---|---|---|
| SQL chuẩn | Được mô tả trong tiêu chuẩn SQL | SELECT, JOIN, CASE, CAST, GROUP BY |
| Optional feature | Có trong chuẩn nhưng implementation có thể không hỗ trợ | Một số tính năng temporal, routine hoặc advanced analytics |
| Vendor extension | Cú pháp/tính năng riêng của sản phẩm | PostgreSQL `ILIKE`, MySQL `AUTO_INCREMENT`, SQL Server `TOP` |
| Khác biệt implementation | Cùng ý tưởng nhưng giới hạn/hành vi khác | Kiểu số, collation, transaction DDL |
| Version-gated feature | Chỉ xuất hiện từ một phiên bản | PostgreSQL MERGE từ 15 |
| Configuration-gated feature | Phụ thuộc cấu hình hoặc chế độ | SQL mode MySQL, SQL Server compatibility level |
| Extension/module-gated | Cần cài extension/module | PostgreSQL PostGIS, SQLite extension tùy build |

Một tính năng có thể thuộc nhiều nhóm. Ví dụ JSON có thể có cú pháp chuẩn SQL/JSON, nhưng các hàm, toán tử, kiểu lưu trữ và khả năng index của mỗi DBMS vẫn có khác biệt.

## 6. Identifier, tên bảng và quy tắc quote

SQL Standard sử dụng dấu ngoặc kép cho delimited identifier:

~~~sql
SELECT "OrderId"
FROM "Sales"."Orders";
~~~

Nhưng mỗi DBMS có các quy tắc riêng.

| DBMS | Cách quote identifier thường gặp | Ghi chú |
|---|---|---|
| PostgreSQL | `"identifier"` | Không quote được chuẩn hóa về lowercase |
| MySQL | Backtick identifier | Double quote phụ thuộc SQL mode |
| MariaDB | Backtick identifier | Có chế độ SQL ảnh hưởng cách dùng quote |
| SQL Server | `[identifier]` hoặc `"identifier"` | Double quote phụ thuộc QUOTED_IDENTIFIER |
| Oracle | `"identifier"` | Unquoted identifier thường được chuẩn hóa uppercase |
| SQLite | `"identifier"`; có cú pháp tương thích khác | Nên dùng double quotes cho tính rõ ràng |

### 6.1. PostgreSQL

~~~sql
CREATE TABLE orders (
    order_id BIGINT
);
~~~

Tên không quote được lưu theo quy tắc lowercase. `OrderId` không quote sẽ được xử lý như `orderid`.

Nếu tạo:

~~~sql
CREATE TABLE "OrderItems" (
    "itemId" BIGINT
);
~~~

thì mọi lần tham chiếu cần quote chính xác `"OrderItems"` và `"itemId"`. Điều này có thể làm query khó portable và dễ lỗi.

### 6.2. SQL Server

SQL Server hỗ trợ bracket identifiers:

~~~sql
SELECT [OrderId]
FROM [Sales].[Orders];
~~~

Double quote cũng có thể dùng làm delimited identifier khi cấu hình `QUOTED_IDENTIFIER` phù hợp. Bracket syntax là đặc trưng T-SQL.

### 6.3. MySQL

MySQL thường dùng backticks:

~~~sql
SELECT `order_id`
FROM `orders`;
~~~

Double quote có thể được hiểu khác tùy `ANSI_QUOTES`. Đừng dùng dấu quote tùy tiện khi muốn query chạy trên nhiều DBMS.

### 6.4. Quy tắc portable

- Tên bảng/cột đơn giản, tránh reserved words.
- Dùng chữ thường và underscore nếu có thể.
- Tránh identifier có khoảng trắng hoặc ký tự đặc biệt.
- Nếu phải quote, dùng quy tắc phù hợp DBMS và cô lập trong migration/dialect.
- Không nối identifier từ input người dùng mà không allowlist.

## 7. Phân trang: LIMIT, TOP và FETCH FIRST

Một nhu cầu thường gặp là lấy 20 hàng đầu.

### 7.1. PostgreSQL, MySQL, SQLite

~~~sql
SELECT id, amount
FROM orders
ORDER BY id
LIMIT 20 OFFSET 40;
~~~

`LIMIT/OFFSET` được nhiều DBMS hỗ trợ, nhưng không phải cú pháp portable cho tất cả.

### 7.2. SQL Server

~~~sql
SELECT id, amount
FROM dbo.Orders
ORDER BY id
OFFSET 40 ROWS
FETCH NEXT 20 ROWS ONLY;
~~~

T-SQL cũng có `TOP`:

~~~sql
SELECT TOP (20) id, amount
FROM dbo.Orders
ORDER BY id;
~~~

TOP không biểu diễn OFFSET trực tiếp như câu đầu.

### 7.3. Oracle và cú pháp FETCH FIRST

Các phiên bản Oracle hiện đại hỗ trợ:

~~~sql
SELECT id, amount
FROM orders
ORDER BY id
OFFSET 40 ROWS
FETCH NEXT 20 ROWS ONLY;
~~~

Cú pháp row limiting này được bổ sung trong Oracle 12c. Với phiên bản cũ hơn, thường gặp truy vấn dùng ROWNUM hoặc analytic functions.

### 7.4. FETCH FIRST và LIMIT không thay thế semantics ORDER BY

Không có ORDER BY thì “20 hàng đầu” không có thứ tự được đảm bảo. Ngay cả khi có ORDER BY nhưng khóa không duy nhất, thứ tự giữa các hàng bằng nhau có thể không ổn định. Nên thêm khóa phụ:

~~~sql
ORDER BY created_at DESC, id DESC
~~~

### 7.5. Pagination sâu

OFFSET lớn có thể khiến DBMS phải đọc/bỏ qua nhiều hàng. Keyset pagination có thể phù hợp hơn:

~~~sql
SELECT id, created_at, amount
FROM orders
WHERE (created_at, id) < (?, ?)
ORDER BY created_at DESC, id DESC
FETCH FIRST 20 ROWS ONLY;
~~~

Row-value comparison và cú pháp FETCH cần kiểm tra theo DBMS; có thể viết điều kiện tương đương bằng OR/AND khi cần portable.

## 8. Tạo ID tự tăng: IDENTITY, AUTO_INCREMENT và SEQUENCE

SQL Standard có cú pháp identity:

~~~sql
CREATE TABLE orders (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    amount NUMERIC(12,2) NOT NULL
);
~~~

Nhưng sản phẩm có thể hỗ trợ khác nhau hoặc có cơ chế lịch sử riêng.

| DBMS | Cách phổ biến |
|---|---|
| PostgreSQL | `GENERATED ... AS IDENTITY`; trước đó thường dùng SERIAL/sequence |
| MySQL | `AUTO_INCREMENT` |
| MariaDB | `AUTO_INCREMENT` |
| SQL Server | `IDENTITY(seed, increment)` |
| Oracle | Identity column từ Oracle 12c; trước đó thường dùng sequence |
| SQLite | `INTEGER PRIMARY KEY` gắn với rowid; `AUTOINCREMENT` có nghĩa riêng |

### 8.1. PostgreSQL identity và SERIAL

~~~sql
CREATE TABLE orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
);
~~~

Identity columns được hỗ trợ từ PostgreSQL 10. `SERIAL` là shorthand lịch sử tạo sequence và default; nó không phải kiểu dữ liệu độc lập như BIGINT.

Hai chế độ identity quan trọng:

- `GENERATED ALWAYS`: thông thường không cho chèn giá trị tường minh trừ khi dùng cú pháp override thích hợp.
- `GENERATED BY DEFAULT`: cho phép cung cấp giá trị tường minh; nếu bỏ qua thì sequence cấp giá trị.

### 8.2. MySQL AUTO_INCREMENT

~~~sql
CREATE TABLE orders (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    amount DECIMAL(12,2) NOT NULL
);
~~~

Cú pháp này là MySQL/MariaDB extension. Quy tắc cấp số, reset, concurrency và cách lấy ID vừa tạo phụ thuộc engine/driver.

### 8.3. SQL Server IDENTITY

~~~sql
CREATE TABLE dbo.Orders (
    Id BIGINT IDENTITY(1,1) PRIMARY KEY,
    Amount DECIMAL(12,2) NOT NULL
);
~~~

IDENTITY là đặc trưng SQL Server. Nó không đảm bảo không có khoảng trống; rollback hoặc cache/khởi động lại có thể làm dãy số không liên tục.

### 8.4. Oracle

~~~sql
CREATE TABLE orders (
    id NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    amount NUMBER(12,2) NOT NULL
);
~~~

Identity column được bổ sung trong Oracle 12c. Với hệ thống cũ hơn, sequence và trigger là cách phổ biến.

### 8.5. SQLite

~~~sql
CREATE TABLE orders (
    id INTEGER PRIMARY KEY,
    amount NUMERIC NOT NULL
);
~~~

INTEGER PRIMARY KEY là alias cho rowid trong bảng rowid thông thường. `AUTOINCREMENT` có thể thay đổi quy tắc tái sử dụng rowid và thêm chi phí; không thêm nó chỉ vì nghĩ rằng mọi bảng tự tăng đều phải có từ khóa này.

## 9. UPSERT: MERGE, ON CONFLICT và ON DUPLICATE KEY

UPSERT là thao tác insert nếu chưa có, hoặc xử lý khi vi phạm unique key. Mục đích tương tự nhưng cú pháp và semantics khác nhau.

### 9.1. PostgreSQL

~~~sql
INSERT INTO inventory (sku, quantity)
VALUES ('A-100', 5)
ON CONFLICT (sku)
DO UPDATE SET quantity = EXCLUDED.quantity;
~~~

`ON CONFLICT` là PostgreSQL syntax. `EXCLUDED` đại diện hàng đề xuất trong nhánh conflict.

### 9.2. SQLite

SQLite hỗ trợ UPSERT với cú pháp gần PostgreSQL:

~~~sql
INSERT INTO inventory (sku, quantity)
VALUES ('A-100', 5)
ON CONFLICT(sku)
DO UPDATE SET quantity = excluded.quantity;
~~~

UPSERT được bổ sung trong SQLite 3.24.0. Cần kiểm tra phiên bản runtime SQLite thực sự đi kèm ứng dụng.

### 9.3. MySQL

~~~sql
INSERT INTO inventory (sku, quantity)
VALUES ('A-100', 5)
ON DUPLICATE KEY UPDATE
    quantity = VALUES(quantity);
~~~

MySQL dùng `ON DUPLICATE KEY UPDATE`, không phải `ON CONFLICT`. Cách tham chiếu hàng đề xuất đã thay đổi theo các phiên bản MySQL 8.0; `VALUES(column)` trong ngữ cảnh này bị đánh dấu deprecated từ MySQL 8.0.20, vì vậy code mới nên theo cú pháp alias hàng được tài liệu phiên bản hiện hành khuyến nghị.

### 9.4. SQL Server và Oracle: MERGE

SQL Server và Oracle hỗ trợ `MERGE` theo cú pháp riêng:

~~~sql
MERGE INTO target_table AS t
USING source_table AS s
ON t.id = s.id
WHEN MATCHED THEN
    UPDATE SET t.value = s.value
WHEN NOT MATCHED THEN
    INSERT (id, value)
    VALUES (s.id, s.value);
~~~

Đây là hình dạng khái quát, không phải một câu lệnh portable nguyên xi cho mọi DBMS. Cú pháp alias, điều kiện, nhánh DELETE, hạn chế concurrency và lỗi duplicate có khác biệt.

PostgreSQL bổ sung `MERGE` từ phiên bản 15. Không giả định các bản PostgreSQL cũ hơn hỗ trợ.

### 9.5. Không phải mọi UPSERT đều có cùng semantics concurrency

Cần kiểm tra:

- Unique constraint nào quyết định conflict?
- Có thể conflict trên nhiều unique keys không?
- UPDATE branch có kích hoạt trigger không?
- Giá trị hàng đề xuất được tham chiếu bằng cú pháp nào?
- Có trả lại hàng bị insert/update không?
- Hành vi khi hai transaction đồng thời upsert cùng key?
- Có nguy cơ lost update hoặc deadlock không?

Hai câu lệnh nhìn giống nhau có thể khác hành vi ở concurrency và trigger.

## 10. Lấy hàng vừa INSERT: RETURNING, OUTPUT và generated keys

### 10.1. PostgreSQL

~~~sql
INSERT INTO orders (amount)
VALUES (100000)
RETURNING id, amount;
~~~

`RETURNING` trả các giá trị của hàng được tác động. Hỗ trợ RETURNING cho DML là điểm mạnh của PostgreSQL.

### 10.2. SQLite

SQLite hỗ trợ RETURNING từ phiên bản 3.35.0:

~~~sql
INSERT INTO orders (amount)
VALUES (100000)
RETURNING id, amount;
~~~

Kiểm tra SQLite library version; JDBC driver có thể đóng gói hoặc liên kết một runtime khác với CLI trên máy.

### 10.3. MariaDB và MySQL

MariaDB hỗ trợ một số dạng DML RETURNING từ các phiên bản 10.5 trở lên, tùy loại statement và phiên bản. **Không suy luận MariaDB RETURNING có nghĩa MySQL hỗ trợ cú pháp tương tự.** MySQL 8.x thường dùng cơ chế khác như generated keys từ driver để lấy ID insert.

### 10.4. SQL Server OUTPUT

~~~sql
INSERT INTO dbo.Orders (Amount)
OUTPUT inserted.Id, inserted.Amount
VALUES (100000);
~~~

T-SQL dùng `OUTPUT` và các bảng giả `inserted`/`deleted` tùy thao tác.

### 10.5. Oracle RETURNING INTO

Oracle có cú pháp `RETURNING ... INTO` trong những ngữ cảnh DML phù hợp, thường bind vào biến PL/SQL hoặc host variable theo driver.

### 10.6. JDBC getGeneratedKeys

JDBC có API chung:

~~~java
PreparedStatement ps = connection.prepareStatement(
    "INSERT INTO orders(amount) VALUES (?)",
    Statement.RETURN_GENERATED_KEYS
);

ps.setBigDecimal(1, new BigDecimal("100000"));
ps.executeUpdate();

try (ResultSet keys = ps.getGeneratedKeys()) {
    if (keys.next()) {
        long id = keys.getLong(1);
    }
}
~~~

Khả năng và metadata generated keys phụ thuộc driver/DBMS. Kiểm tra tài liệu driver, đặc biệt khi insert nhiều hàng hoặc lấy nhiều cột sinh tự động.

## 11. Kiểu Boolean: BOOLEAN, BIT và TINYINT

SQL Standard có BOOLEAN, nhưng các DBMS triển khai khác nhau:

| DBMS | Biểu diễn thường gặp |
|---|---|
| PostgreSQL | BOOLEAN thực |
| MySQL | `BOOLEAN`/`BOOL` là alias của TINYINT(1) |
| MariaDB | `BOOLEAN`/`BOOL` là alias của TINYINT(1) |
| SQL Server | `BIT` |
| Oracle trước 23c/23ai | Không có SQL BOOLEAN column thông thường; PL/SQL có BOOLEAN |
| Oracle 23c/23ai | Có kiểu SQL BOOLEAN |
| SQLite | Dynamic typing; TRUE/FALSE được biểu diễn như số nguyên 1/0 |

### 11.1. Không giả định mọi DBMS có TRUE/FALSE giống nhau

Trong MySQL, BOOLEAN là alias số. Trong SQL Server, BIT có thể biểu diễn 0/1/NULL. Trong SQLite, storage class và affinity linh hoạt.

Nếu code Java cần Boolean nullable, dùng wrapper `Boolean` và test NULL. Nếu DBMS lưu số, kiểm tra driver conversion.

### 11.2. Điều kiện portable

Các điều kiện:

~~~sql
WHERE is_active = TRUE
~~~

có thể được hỗ trợ khác nhau. Nếu phải hỗ trợ nhiều hệ, adapter có thể sinh predicate tương ứng hoặc dùng dạng so sánh được DBMS hỗ trợ. Không ép mọi DBMS thành TINYINT mà bỏ qua semantics.

## 12. String concatenation và hàm chuỗi

### 12.1. Toán tử nối chuỗi

SQL Standard có toán tử `||`:

~~~sql
SELECT first_name || ' ' || last_name AS full_name
FROM customers;
~~~

PostgreSQL, Oracle và SQLite hỗ trợ cách này trong các phiên bản phổ biến.

MySQL dùng `CONCAT` phổ biến:

~~~sql
SELECT CONCAT(first_name, ' ', last_name) AS full_name
FROM customers;
~~~

SQL Server thường dùng `+`:

~~~sql
SELECT first_name + ' ' + last_name AS full_name
FROM dbo.Customers;
~~~

SQL Server cũng có CONCAT ở các phiên bản hiện đại.

### 12.2. NULL khi nối chuỗi

Ngữ nghĩa nối với NULL có thể khác theo DBMS và hàm. MySQL CONCAT trả NULL nếu có đối số NULL; SQL Server CONCAT chuyển NULL thành chuỗi rỗng; các toán tử có thể có quy tắc riêng.

Nếu cần contract ổn định, viết rõ:

~~~sql
SELECT
    COALESCE(first_name, '') || ' ' ||
    COALESCE(last_name, '') AS full_name
FROM customers;
~~~

Nhưng cú pháp || không portable tới mọi DBMS mặc định. Có thể dùng adapter hoặc CONCAT/COALESCE theo dialect.

### 12.3. ILIKE là extension

PostgreSQL có:

~~~sql
SELECT *
FROM customers
WHERE name ILIKE 'an%';
~~~

`ILIKE` là extension PostgreSQL để so khớp không phân biệt hoa thường theo locale/collation. MySQL thường dùng collation không phân biệt case; SQL Server phụ thuộc collation; Oracle có thể dùng UPPER/LOWER hoặc collation phù hợp.

Đừng thay ILIKE bằng LOWER ở mọi nơi mà không xét index, collation và Unicode semantics.

## 13. Hàm ngày giờ và timezone

Cùng một khái niệm “thời gian hiện tại” có thể dùng cú pháp khác nhau:

| DBMS | Ví dụ |
|---|---|
| PostgreSQL | `CURRENT_TIMESTAMP`, `now()`, `clock_timestamp()` |
| MySQL | `CURRENT_TIMESTAMP`, `NOW()` |
| SQL Server | `CURRENT_TIMESTAMP`, `GETDATE()`, `SYSDATETIME()` |
| Oracle | `CURRENT_TIMESTAMP`, `SYSTIMESTAMP`, `SYSDATE` |
| SQLite | `CURRENT_TIMESTAMP`, hàm `datetime('now')` |

`CURRENT_TIMESTAMP` là biểu thức SQL chuẩn phổ biến; các hàm còn lại có semantics và độ chính xác riêng.

### 13.1. Transaction timestamp và wall-clock timestamp

PostgreSQL:

- `CURRENT_TIMESTAMP`/`transaction_timestamp()` phản ánh thời điểm bắt đầu transaction.
- `statement_timestamp()` phản ánh thời điểm bắt đầu statement.
- `clock_timestamp()` đọc đồng hồ tại lúc hàm được gọi.

MySQL/SQL Server/Oracle có các quy tắc khác. Không thay NOW() bằng CURRENT_TIMESTAMP rồi cho rằng mọi hệ thống giữ nguyên semantics transaction.

### 13.2. Time zone type

- PostgreSQL phân biệt TIMESTAMP WITHOUT TIME ZONE và TIMESTAMP WITH TIME ZONE.
- MySQL có DATETIME và TIMESTAMP với các quy tắc chuyển đổi timezone riêng.
- SQL Server có datetime2 và datetimeoffset.
- Oracle có DATE, TIMESTAMP, TIMESTAMP WITH TIME ZONE và LOCAL TIME ZONE.
- SQLite không có một kiểu temporal storage nghiêm ngặt như các DBMS trên; thường lưu TEXT/REAL/INTEGER theo convention.

### 13.3. Quy tắc portable

Chốt rõ domain cần lưu:

- Ngày lịch: DATE/LocalDate.
- Giờ địa phương: TIME/LocalTime.
- Ngày giờ địa phương chưa có timezone: LocalDateTime.
- Thời điểm tuyệt đối: instant/UTC hoặc timestamp có offset.
- Vùng timezone người dùng chọn: lưu thêm ZoneId nếu cần.

Đừng chỉ đổi kiểu SQL cho query chạy được mà thay đổi ý nghĩa dữ liệu.

## 14. NULL, phép so sánh và xử lý khác biệt

SQL dùng logic ba giá trị: TRUE, FALSE, UNKNOWN. So sánh với NULL bằng `= NULL` không cho kết quả TRUE; phải dùng IS NULL.

~~~sql
SELECT *
FROM orders
WHERE shipped_at IS NULL;
~~~

Một số DBMS có toán tử so sánh NULL-safe riêng:

- PostgreSQL: `IS DISTINCT FROM` và `IS NOT DISTINCT FROM`.
- MySQL: `<=>` là NULL-safe equality.
- SQL Server từ SQL Server 2022 hỗ trợ `IS [NOT] DISTINCT FROM`.
- Các hệ khác có thể dùng biểu thức CASE/OR phù hợp.

Ví dụ PostgreSQL:

~~~sql
WHERE old_value IS DISTINCT FROM new_value
~~~

Nếu muốn portable rộng, viết biểu thức rõ cho hai trạng thái NULL:

~~~sql
WHERE old_value <> new_value
   OR (old_value IS NULL AND new_value IS NOT NULL)
   OR (old_value IS NOT NULL AND new_value IS NULL)
~~~

Không dùng `COALESCE(value, sentinel)` nếu sentinel có thể là giá trị hợp lệ.

## 15. CTE và recursive query

CTE với `WITH` là phần của SQL hiện đại:

~~~sql
WITH paid_orders AS (
    SELECT id, customer_id, amount
    FROM orders
    WHERE status = 'PAID'
)
SELECT customer_id, SUM(amount) AS total_amount
FROM paid_orders
GROUP BY customer_id;
~~~

CTE giúp chia query thành các bước logic, nhưng semantics tối ưu hóa/materialization có thể khác theo DBMS và version.

### 15.1. Recursive CTE

~~~sql
WITH RECURSIVE descendants AS (
    SELECT id, parent_id, 0 AS depth
    FROM categories
    WHERE id = 1

    UNION ALL

    SELECT c.id, c.parent_id, d.depth + 1
    FROM categories AS c
    JOIN descendants AS d
        ON c.parent_id = d.id
)
SELECT *
FROM descendants;
~~~

PostgreSQL, MySQL 8.0+, SQLite và các DBMS hiện đại hỗ trợ recursive CTE theo cú pháp có khác biệt. SQL Server dùng `WITH ... AS` nhưng không viết từ khóa RECURSIVE trong cùng cách của PostgreSQL. Cần kiểm tra giới hạn recursion và syntax của sản phẩm.

### 15.2. CTE materialization không đồng nhất

Một số DBMS có keyword hoặc hint điều khiển materialization; hành vi mặc định có thể thay đổi theo version và optimizer. Đừng dùng CTE với giả định luôn tạo bảng tạm vật lý hoặc luôn inline.

## 16. Window functions

Window functions cho phép tính toán trên một cửa sổ hàng mà không gộp hàng như GROUP BY:

~~~sql
SELECT
    customer_id,
    id AS order_id,
    amount,
    ROW_NUMBER() OVER (
        PARTITION BY customer_id
        ORDER BY amount DESC, id
    ) AS order_rank
FROM orders;
~~~

Các hàm như ROW_NUMBER, RANK, DENSE_RANK, LAG, LEAD, SUM OVER và AVG OVER xuất hiện trong nhiều DBMS hiện đại.

### 16.1. Phiên bản hỗ trợ

- PostgreSQL hỗ trợ window functions từ PostgreSQL 8.4.
- MySQL hỗ trợ window functions từ MySQL 8.0.
- SQLite hỗ trợ window functions từ 3.25.0.
- SQL Server đã hỗ trợ nhiều window functions từ các thế hệ trước, với cú pháp và tập hàm theo version.
- Oracle hỗ trợ analytics từ lâu, nhưng từng hàm/khung cửa sổ có giới hạn riêng.

### 16.2. ORDER BY trong window khác ORDER BY cuối query

`ORDER BY` trong OVER quyết định thứ tự tính cửa sổ; `ORDER BY` ở cuối SELECT quyết định thứ tự hàng trả ra. Nếu ứng dụng cần kết quả ổn định, thường phải có ORDER BY cuối query.

### 16.3. Frame semantics

`ROWS BETWEEN ...`, `RANGE BETWEEN ...` và mặc định window frame có thể tạo kết quả khác nhau. Đừng chỉ chuyển cú pháp; hãy kiểm tra frame, peer rows và thứ tự tie.

## 17. JSON: kiểu dữ liệu, hàm và toán tử khác nhau

JSON là một ví dụ điển hình về tiêu chuẩn và extension cùng tồn tại.

### 17.1. PostgreSQL JSON và JSONB

~~~sql
CREATE TABLE events (
    id BIGINT PRIMARY KEY,
    payload JSONB NOT NULL
);
~~~

JSONB là kiểu PostgreSQL riêng với cách lưu trữ, toán tử và index đặc thù. Nó không tương đương hoàn toàn với một cột JSON của MySQL hay văn bản JSON trong SQLite.

~~~sql
SELECT payload ->> 'event_type' AS event_type
FROM events;
~~~

`->` và `->>` là toán tử PostgreSQL; cú pháp không portable sang mọi DBMS.

### 17.2. MySQL JSON

MySQL có kiểu JSON và các hàm như JSON_EXTRACT/JSON_VALUE tùy version. Ví dụ:

~~~sql
SELECT
    JSON_UNQUOTE(JSON_EXTRACT(payload, '$.event_type'))
        AS event_type
FROM events;
~~~

Không dùng toán tử PostgreSQL `->>` trong query MySQL mặc định.

### 17.3. SQL Server JSON

SQL Server thường lưu JSON trong NVARCHAR và cung cấp các hàm như `JSON_VALUE`, `JSON_QUERY`, `OPENJSON`:

~~~sql
SELECT
    JSON_VALUE(payload, '$.event_type') AS event_type
FROM dbo.Events;
~~~

Khả năng index và JSON features phụ thuộc version/edition.

### 17.4. Oracle JSON

Oracle hỗ trợ JSON trong các cột phù hợp, với khả năng type/constraint và JSON SQL functions theo version. Các kiểu lưu trữ và cú pháp JSON có thể khác giữa các đời Oracle.

### 17.5. SQLite JSON

SQLite có JSON functions; từ SQLite 3.38.0, JSON functions được tích hợp mặc định trong các bản build chuẩn (trừ khi compile option tắt), trước đó có thể phụ thuộc build/extension. SQLite 3.45.0 bổ sung định dạng JSONB nội bộ của riêng SQLite; **không tương thích binary format với PostgreSQL JSONB**.

### 17.6. SQL/JSON Standard không làm mọi API giống nhau

SQL/JSON đưa ra cú pháp và hàm tiêu chuẩn, nhưng từng DBMS triển khai theo phiên bản và phạm vi khác nhau. Cần kiểm tra JSON_TABLE, JSON_VALUE, JSON_QUERY, JSON_EXISTS, constructors và path semantics trên DBMS cụ thể.

## 18. Generated columns và computed columns

Một cột được tính từ cột khác có thể có cú pháp khác:

~~~sql
-- PostgreSQL
CREATE TABLE products (
    price NUMERIC(12,2),
    tax NUMERIC(12,2),
    gross NUMERIC(12,2)
        GENERATED ALWAYS AS (price + tax) STORED
);
~~~

SQL Server dùng `AS (expression) PERSISTED` cho computed column trong nhiều trường hợp:

~~~sql
CREATE TABLE dbo.Products (
    Price DECIMAL(12,2),
    Tax DECIMAL(12,2),
    Gross AS (Price + Tax) PERSISTED
);
~~~

MySQL:

~~~sql
CREATE TABLE products (
    price DECIMAL(12,2),
    tax DECIMAL(12,2),
    gross DECIMAL(12,2)
        GENERATED ALWAYS AS (price + tax) STORED
);
~~~

SQLite hỗ trợ generated columns từ 3.31.0, với VIRTUAL/STORED và giới hạn riêng.

Oracle cũng có virtual columns và các cơ chế generated expression theo version.

**Không giả định** mọi hệ thống cho phép cùng expression, cùng kiểu volatility, index hoặc lưu trữ. Một expression hợp lệ trên PostgreSQL có thể bị giới hạn trong computed column của SQL Server/MySQL.

## 19. Constraints và CHECK theo phiên bản

CHECK constraint là một khái niệm SQL quen thuộc:

~~~sql
CREATE TABLE products (
    price NUMERIC(12,2) NOT NULL,
    CONSTRAINT positive_price CHECK (price >= 0)
);
~~~

Nhưng khả năng enforcement và giới hạn khác nhau.

### 19.1. MySQL CHECK

MySQL trước 8.0.16 chấp nhận một số cú pháp CHECK nhưng không thực thi theo cách mong đợi; từ 8.0.16, CHECK constraints được thực thi. Khi nâng cấp từ bản cũ, không giả định constraint từng khai báo đã bảo vệ dữ liệu lịch sử.

### 19.2. PostgreSQL

PostgreSQL hỗ trợ CHECK, NOT NULL, UNIQUE, PRIMARY KEY, FOREIGN KEY và exclusion constraints (đặc thù). CHECK không phải cơ chế thay thế mọi constraint liên bảng; không nên dựa vào CHECK để truy vấn dữ liệu hàng khác.

### 19.3. SQLite

SQLite có CHECK, nhưng dynamic typing và các quy tắc affinity cần được hiểu rõ. Có thể dùng STRICT tables từ SQLite 3.37.0 để có kiểm soát kiểu nghiêm ngặt hơn trong phạm vi kiểu SQLite hỗ trợ.

### 19.4. Deferrable constraints

PostgreSQL và Oracle hỗ trợ các loại constraint DEFERRABLE theo những quy tắc nhất định; MySQL và SQL Server không cung cấp cùng cơ chế deferred constraint tổng quát. Nếu logic transaction phụ thuộc việc kiểm tra constraint cuối transaction, đây là một khác biệt kiến trúc, không chỉ khác cú pháp.

## 20. MERGE, RETURNING và DML extensions

Ngoài UPSERT, DML output cũng có các dạng khác nhau:

| Mục đích | PostgreSQL | SQL Server | Oracle | MySQL | SQLite |
|---|---|---|---|---|---|
| Insert/update khi trùng | ON CONFLICT; MERGE từ 15 | MERGE hoặc logic khác | MERGE | ON DUPLICATE KEY UPDATE | ON CONFLICT |
| Trả hàng DML tác động | RETURNING | OUTPUT | RETURNING INTO | Generated keys; không cùng cú pháp PostgreSQL | RETURNING từ 3.35 |
| Cập nhật theo source | UPDATE ... FROM | UPDATE ... FROM | UPDATE/MERGE theo cú pháp riêng | UPDATE JOIN | UPDATE FROM từ 3.33 |
| Xóa có kết quả | DELETE ... RETURNING | DELETE ... OUTPUT | RETURNING INTO | MariaDB có hỗ trợ theo version; MySQL khác | DELETE ... RETURNING |

Bảng là định hướng, không thay tài liệu cụ thể. Cần xét số hàng, trigger, output columns, transaction và concurrency.

## 21. MERGE không tự bảo đảm cùng semantics giữa DBMS

MERGE có trong SQL Standard nhưng từng DBMS triển khai theo grammar, giới hạn và lịch sử lỗi riêng.

### 21.1. PostgreSQL

PostgreSQL hỗ trợ MERGE từ phiên bản 15. Cần xem giới hạn và semantics của từng version; các bản trước đó không thể chạy cú pháp này.

### 21.2. SQL Server

SQL Server có MERGE, nhưng việc sử dụng trong môi trường đồng thời và tương tác trigger/constraint cần được thiết kế, kiểm thử cẩn thận. Một số hệ thống chọn tách INSERT/UPDATE hoặc dùng locking/transaction logic để kiểm soát rõ hơn.

### 21.3. Oracle

Oracle hỗ trợ MERGE từ nhiều thế hệ trước; cú pháp và nhánh điều kiện có các quy tắc riêng.

### 21.4. MySQL

MySQL không dùng MERGE theo cú pháp PostgreSQL/SQL Server/Oracle; thường dùng `INSERT ... ON DUPLICATE KEY UPDATE`.

**Bài học:** nếu application repository cần upsert trên nhiều DBMS, tạo một API nghiệp vụ chung nhưng triển khai query theo từng dialect, rồi test concurrency riêng.

## 22. Transaction và DDL khác nhau

Nhiều người nghĩ mọi DDL đều rollback được như DML. Điều này không đúng trên mọi DBMS.

| DBMS | DDL transaction behavior khái quát |
|---|---|
| PostgreSQL | Nhiều DDL có thể chạy trong transaction và rollback; có một số lệnh bị hạn chế |
| MySQL | Nhiều DDL gây implicit commit; atomic DDL có giới hạn/version/engine riêng |
| MariaDB | Nhiều DDL có implicit commit; hỗ trợ atomic DDL tùy loại/version |
| SQL Server | Nhiều DDL có thể tham gia transaction, nhưng không phải mọi thao tác đều như nhau |
| Oracle | DDL thường implicit commit trước/sau theo quy tắc Oracle |
| SQLite | Nhiều DDL hỗ trợ transaction, nhưng cần kiểm tra loại lệnh/version |

### 22.1. Ví dụ rủi ro migration

~~~sql
BEGIN;

ALTER TABLE orders ADD COLUMN source TEXT;

INSERT INTO migration_log(version)
VALUES ('v2');

ROLLBACK;
~~~

Trên PostgreSQL, ALTER TABLE thường transactional và có thể rollback cùng INSERT trong các điều kiện thông thường. Trên MySQL hoặc Oracle, DDL có thể tạo implicit commit; câu lệnh ROLLBACK không nhất thiết hoàn tác ALTER TABLE như kỳ vọng.

**Không thiết kế migration portable dựa trên giả định mọi DBMS có transactional DDL.**

### 22.2. Kế hoạch migration đa DBMS

- Chạy migration trên database đúng loại/version.
- Không gộp DDL và DML vào một transaction khi DBMS có implicit commit nếu chưa hiểu hệ quả.
- Dùng migration scripts/dialect theo DBMS.
- Có kiểm tra trạng thái schema trước/sau.
- Chuẩn bị rollback script hoặc forward-fix phù hợp; không giả định ROLLBACK SQL có thể khôi phục mọi DDL.

## 23. Transaction isolation và locking

Tên isolation level có thể giống nhau nhưng implementation khác nhau.

Các mức phổ biến theo SQL:

- READ UNCOMMITTED
- READ COMMITTED
- REPEATABLE READ
- SERIALIZABLE

Nhưng snapshot, locking, phantom prevention, serialization failure và MVCC behavior khác theo DBMS.

Ví dụ:

- PostgreSQL READ COMMITTED thường dùng snapshot mới cho mỗi statement.
- PostgreSQL REPEATABLE READ dùng snapshot transaction và có thể phát serialization anomaly ở mức mà tên isolation gợi ý khác cách hiểu đơn giản.
- MySQL InnoDB có các quy tắc consistent read và gap/next-key locking.
- SQL Server có locking-based READ COMMITTED hoặc READ_COMMITTED_SNAPSHOT tùy cấu hình.
- Oracle dùng multi-version consistency và các mức isolation riêng theo mô hình Oracle.
- SQLite có locking/transaction modes và journal/WAL behavior riêng.

Không chỉ đổi chuỗi `SET TRANSACTION ISOLATION LEVEL REPEATABLE READ` rồi kết luận hai DBMS có cùng khả năng chống anomaly. Hãy test các lịch giao dịch đồng thời thực tế.

## 24. Collation, Unicode và so sánh chuỗi

Cùng câu:

~~~sql
SELECT *
FROM customers
WHERE name = 'An';
~~~

có thể cho kết quả khác nhau tùy collation:

- Phân biệt hoa/thường hay không.
- Phân biệt dấu/diacritics hay không.
- Quy tắc sắp xếp Unicode.
- Locale và collation version.
- Chuẩn hóa Unicode và ký tự tương đương.

PostgreSQL có collation libc/ICU và các tùy chọn theo version; MySQL thường dùng collation theo charset; SQL Server có collation cấp server/database/column; Oracle có NLS/collation; SQLite có BINARY/NOCASE/RTRIM và custom collations.

### 24.1. Không tự giả định LOWER() portable tuyệt đối

`LOWER(name)` có thể hỗ trợ rộng, nhưng xử lý Unicode, locale và index vẫn khác. Một tìm kiếm không phân biệt dấu/case cần định nghĩa nghiệp vụ cụ thể và cấu hình collation/normalization phù hợp.

### 24.2. ORDER BY cũng chịu collation

Hai DBMS có thể sắp xếp cùng tập chuỗi theo thứ tự khác nhau. Nếu kết quả phân trang hoặc pagination token dựa trên thứ tự chuỗi, khác biệt collation có thể làm thiếu/lặp hàng.

## 25. Kiểu số, tiền và giới hạn miền giá trị

Các kiểu cùng tên không luôn có miền giá trị/rounding giống nhau:

- PostgreSQL NUMERIC có precision linh hoạt trong giới hạn sản phẩm.
- MySQL DECIMAL có giới hạn precision/scale theo phiên bản.
- SQL Server DECIMAL/NUMERIC có precision tối đa riêng.
- Oracle NUMBER có precision/range riêng.
- SQLite dùng dynamic storage classes và affinity; khai báo DECIMAL không tạo hành vi cố định giống PostgreSQL DECIMAL.

Khi chuyển DBMS:

1. Kiểm tra precision/scale tối đa.
2. Kiểm tra rounding và overflow.
3. Kiểm tra cách bind/return qua JDBC.
4. Test giá trị âm, 0, biên, số chữ số lớn và NULL.
5. Chọn BigDecimal cho ứng dụng cần số thập phân chính xác.

## 27. Phiên bản server chưa phải toàn bộ môi trường

Một ứng dụng có thể kết nối database thông qua nhiều lớp:

~~~text
Ứng dụng
   │
   ▼
JDBC driver / ORM / SQL client
   │
   ▼
Connection settings / SQL mode / compatibility level
   │
   ▼
Database server version
   │
   ▼
Extensions / plugins / storage engine / build options
~~~

Một câu lệnh có thể thất bại vì:

- Server quá cũ.
- JDBC driver không hiểu kiểu mới hoặc không triển khai API tương ứng.
- ORM sinh SQL theo dialect khác.
- SQL mode thay đổi grammar/semantics.
- SQL Server database compatibility level thấp hơn khả năng engine.
- Extension PostgreSQL chưa cài hoặc chưa bật.
- SQLite runtime trong ứng dụng cũ hơn CLI trên máy.
- MySQL engine/table configuration khác.
- Feature chỉ có trong edition hoặc cấu hình đặc biệt.

### 27.1. Database version và driver version khác nhau

Ví dụ máy dev cài PostgreSQL mới, nhưng ứng dụng production dùng JDBC driver cũ hoặc kết nối đến server phiên bản thấp hơn. Không thể suy ra khả năng từ phiên bản driver hoặc công cụ SQL client.

### 27.2. Compatibility level của SQL Server

SQL Server engine có thể là một phiên bản mới nhưng database đặt compatibility level cũ. Một số cú pháp, optimizer behavior và feature có thể bị ảnh hưởng. Kiểm tra cả engine version lẫn compatibility level.

### 27.3. SQLite version trong ứng dụng

Ứng dụng Android, desktop hoặc embedded có thể đóng gói SQLite library riêng. Kết quả `sqlite3 --version` trên máy phát triển không nhất thiết là version mà JDBC/native driver trong ứng dụng dùng.

## 28. Kiểm tra phiên bản và capability

### 28.1. PostgreSQL

~~~sql
SELECT version();
SHOW server_version;
SHOW server_version_num;
~~~

`server_version_num` hữu ích cho kiểm tra version có cấu trúc. Trong ứng dụng, có thể dùng DatabaseMetaData của JDBC và query server version khi cần.

### 28.2. MySQL/MariaDB

~~~sql
SELECT VERSION();
SELECT @@version_comment;
SELECT @@sql_mode;
~~~

Kiểm tra server product, version và SQL mode. Không chỉ dựa vào chuỗi version nếu cần biết tính năng hoặc behavior do mode ảnh hưởng.

### 28.3. SQL Server

~~~sql
SELECT
    @@VERSION AS full_version,
    SERVERPROPERTY('ProductVersion') AS product_version,
    SERVERPROPERTY('Edition') AS edition;

SELECT compatibility_level
FROM sys.databases
WHERE name = DB_NAME();
~~~

Cần xem product version, edition và database compatibility level.

### 28.4. Oracle

~~~sql
SELECT banner
FROM v$version;
~~~

Quyền đọc dynamic performance views có thể bị hạn chế; trong môi trường quản trị, dùng view phù hợp với quyền được cấp và tài liệu phiên bản.

### 28.5. SQLite

~~~sql
SELECT sqlite_version();
PRAGMA compile_options;
~~~

`sqlite_version()` cho version của library đang thực thi câu query. Compile options cho biết một số build features, nhưng không phải mọi capability đều được suy ra chỉ từ danh sách này.

### 28.6. JDBC DatabaseMetaData

~~~java
DatabaseMetaData md = connection.getMetaData();

System.out.println(md.getDatabaseProductName());
System.out.println(md.getDatabaseProductVersion());
System.out.println(md.getDriverName());
System.out.println(md.getDriverVersion());
System.out.println(md.getSQLKeywords());
~~~

DatabaseMetaData có thể cung cấp thêm thông tin về supportsTransactions, supportsBatchUpdates, supportsResultSetType và các capability khác. Không phải mọi driver khai báo chính xác mọi tính năng; hãy test hành vi thực tế.

### 28.7. Feature detection tốt hơn so sánh chuỗi tùy tiện

Tránh:

~~~java
if (versionString.compareTo("10.0") >= 0) {
    // assume feature
}
~~~

So sánh chuỗi version có thể sai thứ tự. Nếu bắt buộc version gating, parse thành các thành phần số và biết product family. Tốt hơn nữa là capability probe hoặc cấu hình dialect rõ ràng.

## 29. Chiến lược viết SQL portable

Không phải mọi query đều cần chạy trên mọi DBMS. Hãy xác định phạm vi portability trước.

### 29.1. Dùng phần giao nhau khi có thể

Các cấu trúc thường dễ portable hơn:

- SELECT/WHERE/GROUP BY/HAVING.
- INNER JOIN/LEFT JOIN.
- CASE.
- CAST theo cú pháp chuẩn.
- COALESCE.
- EXISTS.
- UNION ALL.
- Common expressions đơn giản.
- Prepared statements với parameter binding.

Nhưng ngay cả các cấu trúc này vẫn có khác biệt về kiểu, collation, NULL, precision và optimizer.

### 29.2. Cô lập dialect-specific SQL

Ví dụ interface Java:

~~~java
public interface OrderSqlDialect {
    String upsertInventorySql();
    String insertReturningSql();
    String paginationSql();
}
~~~

Các implementation:

~~~text
PostgresOrderSqlDialect
MySqlOrderSqlDialect
SqlServerOrderSqlDialect
OracleOrderSqlDialect
SqliteOrderSqlDialect
~~~

Service gọi interface chung; phần SQL đặc thù nằm trong adapter/repository tương ứng.

Không nên rải kiểm tra `if (isPostgres)` khắp business service.

### 29.3. Tách schema migration theo DBMS

Một migration có thể cần các file riêng:

~~~text
db/migration/
  postgres/
    V001__create_orders.sql
    V002__add_status_index.sql
  mysql/
    V001__create_orders.sql
    V002__add_status_index.sql
  sqlserver/
    V001__create_orders.sql
    V002__add_status_index.sql
~~~

Công cụ migration có thể hỗ trợ placeholder hoặc dialect, nhưng schema semantics, identity, JSON, index và transaction DDL vẫn cần thiết kế theo DBMS.

### 29.4. Dùng view làm compatibility layer khi phù hợp

Có thể tạo view cùng alias/cấu trúc ở mỗi DBMS để ứng dụng nhận một contract chung:

~~~sql
CREATE VIEW app_order_summary AS
SELECT
    id AS order_id,
    amount AS total_amount
FROM orders;
~~~

Mỗi DBMS có migration tạo view tương ứng. Cần xem updatability, owner/security và hiệu năng của view; view không tự giải quyết mọi khác biệt.

## 30. Chiến lược kiểm thử đa hệ quản trị

Một câu SQL portable không chỉ cần parse được. Nó cần cho kết quả và lỗi đúng theo hợp đồng ứng dụng.

### 30.1. Ma trận kiểm thử

| Lớp kiểm thử | Nội dung |
|---|---|
| Syntax | Query có parse/execute trên DBMS/version không? |
| Result shape | Alias, số cột, kiểu, precision/scale có đúng không? |
| Nullability | SQL NULL được map đúng không? |
| Semantics | Kết quả JOIN, GROUP BY, CASE, date/time có cùng nghĩa không? |
| Constraints | CHECK/FK/UNIQUE có được thực thi như yêu cầu không? |
| Transactions | Rollback, DDL và isolation có đúng kỳ vọng không? |
| Concurrency | Upsert, locking, lost update và deadlock |
| Permissions | Role, schema, sequence, RLS và routine |
| Performance | Index, query plan và độ trễ trên dữ liệu đại diện |
| Migration | Nâng cấp schema, rollback/forward-fix và dữ liệu cũ |

### 30.2. Test trên server thật của từng DBMS

Không thay database bằng mock để xác minh SQL dialect. Mock có thể kiểm tra service logic nhưng không kiểm tra parser, transaction, locking, type conversion hoặc constraint thật.

Dùng test environment/containers hoặc database test service cho từng engine và version mục tiêu.

### 30.3. Test version tối thiểu và version mục tiêu

Nếu sản phẩm hỗ trợ PostgreSQL 14, 15, 16 và 17, cần xác định tính năng tối thiểu trong code. Không chỉ test bản mới nhất.

Ví dụ `MERGE` chỉ có từ PostgreSQL 15; query có MERGE không thể được coi là tương thích với PostgreSQL 14.

### 30.4. Test dữ liệu biên

Tối thiểu gồm:

- SQL NULL và giá trị rỗng.
- Số sát precision/scale.
- Unicode và collation.
- Timestamp quanh DST/offset.
- Hàng trùng key khi upsert đồng thời.
- Hàng không khớp JOIN.
- Result set rỗng.
- Transaction rollback.
- Constraint violation.
- Dữ liệu lớn và pagination sâu.

### 30.5. Test semantics, không chỉ test syntax

Hai query đều chạy được nhưng có thể khác:

- SUM trả NULL hay 0.
- NULL concatenation.
- Thứ tự hàng khi ORDER BY không duy nhất.
- So sánh chuỗi case/accent.
- DDL có implicit commit hay không.
- Trigger có chạy trong upsert branch không.
- Sequence có rollback không.
- RLS có lọc hàng không.

## 31. Ví dụ compatibility adapter cho pagination

Một service muốn API:

~~~java
List<Order> findPage(int offset, int pageSize);
~~~

Không nhất thiết mọi DBMS phải dùng cùng một SQL string.

PostgreSQL/MySQL/SQLite:

~~~sql
SELECT id, amount
FROM orders
ORDER BY id
LIMIT ? OFFSET ?;
~~~

SQL Server/Oracle hiện đại:

~~~sql
SELECT id, amount
FROM orders
ORDER BY id
OFFSET ? ROWS
FETCH NEXT ? ROWS ONLY;
~~~

Adapter:

~~~java
String paginationSql(DatabaseProduct product) {
    return switch (product) {
        case POSTGRES, MYSQL, SQLITE ->
            "SELECT id, amount FROM orders "
            + "ORDER BY id LIMIT ? OFFSET ?";
        case SQL_SERVER, ORACLE ->
            "SELECT id, amount FROM orders "
            + "ORDER BY id OFFSET ? ROWS "
            + "FETCH NEXT ? ROWS ONLY";
    };
}
~~~

Đây là ví dụ minh họa. Driver enum, placeholder order và hỗ trợ version cần được triển khai theo sản phẩm thật. Không để input offset/pageSize âm hoặc quá lớn; validate ở application.

### 31.1. Portable semantics

Dù syntax khác, contract phải giữ:

- Cùng cột output và alias.
- Cùng thứ tự ổn định.
- Cùng cách hiểu offset và page size.
- Cùng xử lý giá trị biên.
- Cùng kiểu Java.

Nếu chỉ đổi cú pháp mà thứ tự tie khác nhau, ứng dụng có thể nhận trang bị lặp hoặc thiếu hàng.

## 32. Ví dụ compatibility adapter cho UPSERT

API chung:

~~~java
void saveInventory(String sku, int quantity);
~~~

Các dialect có thể triển khai:

- PostgreSQL: INSERT ... ON CONFLICT ... DO UPDATE.
- SQLite: INSERT ... ON CONFLICT ... DO UPDATE (nếu version hỗ trợ).
- MySQL: INSERT ... ON DUPLICATE KEY UPDATE.
- SQL Server/Oracle: MERGE hoặc chiến lược UPDATE rồi INSERT với concurrency control phù hợp.

**Không** tạo một query string duy nhất rồi thay vài từ khóa bằng replace. Mỗi dialect cần xử lý:

- Unique constraint mục tiêu.
- Giá trị hàng mới.
- Hành vi trigger.
- Cập nhật cột nào.
- Kết quả trả về.
- Lock/concurrency và retry.
- Duplicate key ngoài constraint mục tiêu.

### 32.1. Tính nguyên tử và race condition

Mẫu naïve:

~~~sql
SELECT id FROM inventory WHERE sku = ?;
-- Nếu không thấy:
INSERT INTO inventory ...
~~~

có race condition: hai transaction cùng SELECT không thấy rồi cùng INSERT. Unique constraint sẽ bảo vệ tính duy nhất nhưng một transaction có thể lỗi; cần upsert/locking/retry đúng DBMS.

### 32.2. MERGE cũng cần test concurrency

Dùng MERGE không tự xóa mọi race condition hoặc đảm bảo giống semantics giữa DBMS. Kiểm tra locking, unique constraints, trigger, error handling và retry trên engine/version thực tế.

## 33. Quản lý tính năng theo phiên bản trong ứng dụng

Có ba chiến lược:

### 33.1. Chọn baseline thấp nhất

Nếu ứng dụng phải chạy PostgreSQL 14+, chỉ dùng những tính năng có trên PostgreSQL 14 hoặc có fallback. Đây là cách đơn giản nhất để kiểm soát hỗ trợ.

### 33.2. Capability-based implementation

Khi ứng dụng hỗ trợ nhiều database, có thể khai báo capability:

~~~java
record SqlCapabilities(
    boolean supportsReturning,
    boolean supportsMerge,
    boolean supportsJsonTable,
    boolean supportsWindowFunctions
) {}
~~~

Khởi tạo capability theo product/version/config đã xác nhận. Đừng chỉ set true vì version string lớn hơn một số tự đoán.

### 33.3. Capability probe

Có thể kiểm tra bằng metadata, catalog hoặc một câu thử trong schema test. Probe phải tránh thay đổi dữ liệu production; nếu cần DDL, thực hiện trong transaction/temporary schema khi DBMS hỗ trợ.

### 33.4. Fallback phải giữ semantics

Ví dụ database không hỗ trợ RETURNING:

- PostgreSQL: INSERT ... RETURNING id.
- JDBC generic: getGeneratedKeys nếu driver hỗ trợ.
- Một số DBMS: sequence preallocation hoặc API đặc thù.

Fallback phải xử lý insert nhiều hàng, rollback, generated key và concurrency. Không thay bằng SELECT MAX(id), vì đó không phải cách lấy ID của transaction hiện tại an toàn.

## 34. Những bẫy portability cần ghi nhớ

| Bẫy | Vì sao nguy hiểm |
|---|---|
| Dùng LIMIT trên mọi DBMS | SQL Server/Oracle có cú pháp khác tùy version |
| Dùng SERIAL ở mọi nơi | SERIAL là shorthand PostgreSQL, không phải kiểu chuẩn phổ quát |
| Dùng BOOLEAN | Một số DBMS biểu diễn bằng BIT/TINYINT hoặc chỉ hỗ trợ từ version mới |
| Dùng ON CONFLICT | PostgreSQL/SQLite, không phải MySQL |
| Dùng ON DUPLICATE KEY UPDATE | MySQL/MariaDB, không phải PostgreSQL |
| Dùng MERGE mà không kiểm tra version | PostgreSQL chỉ có từ 15; cú pháp/semantics khác |
| Dùng RETURNING | SQL Server dùng OUTPUT; MySQL không cùng cú pháp |
| Dùng JSONB | Là kiểu PostgreSQL riêng; SQLite JSONB khác binary format |
| Dùng ILIKE | Extension PostgreSQL |
| Dùng || nối chuỗi | MySQL mode mặc định có thể hiểu || là logical OR |
| Dùng quote identifier tùy tiện | Double quote/backtick/bracket khác semantics |
| Giả định DDL rollback | MySQL/Oracle có implicit commit với nhiều DDL |
| Giả định mọi DBMS hỗ trợ deferred constraints | Phạm vi hỗ trợ khác |
| Giả định collation giống nhau | Case/accent/Unicode sorting khác |
| Giả định TIMESTAMP cùng timezone semantics | Mỗi DBMS có kiểu và conversion riêng |
| Dùng SELECT MAX(id) lấy ID mới | Race condition với transaction khác |
| Dùng version string so sánh từ điển | "10" có thể được sắp trước "9" theo chuỗi |
| Chỉ test trên SQLite | Không đại diện semantics PostgreSQL/MySQL/SQL Server |
| Chỉ test trên DBMS mới nhất | Bỏ sót phiên bản tối thiểu được hỗ trợ |
| Coi driver version là server version | Hai phiên bản độc lập |
| Coi syntax parse được là tương thích | Result types, NULL, transaction và concurrency vẫn có thể khác |

## 35. Bài tập thực hành có lời giải

### Bài 1. Chuẩn SQL có nghĩa là mọi DBMS chạy cùng câu không?

**Lời giải:** không. Tiêu chuẩn có nhiều phần/optional features, implementation hỗ trợ theo mức và phiên bản; sản phẩm còn có extension và giới hạn riêng.

### Bài 2. PostgreSQL ILIKE là gì?

**Lời giải:** extension PostgreSQL cho so khớp không phân biệt hoa thường theo semantics/collation của hệ thống; không phải cú pháp portable mặc định.

### Bài 3. SQL Server dùng cú pháp nào cho top-N?

**Lời giải:** TOP (n) hoặc OFFSET/FETCH với ORDER BY, tùy mục đích và version. Không mặc định dùng LIMIT.

### Bài 4. PostgreSQL identity column xuất hiện từ phiên bản nào?

**Lời giải:** PostgreSQL 10 hỗ trợ identity columns. SERIAL là shorthand lịch sử khác.

### Bài 5. PostgreSQL MERGE có từ phiên bản nào?

**Lời giải:** PostgreSQL 15. PostgreSQL 14 không hỗ trợ MERGE.

### Bài 6. MySQL có hỗ trợ CTE và window functions từ thế hệ nào?

**Lời giải:** MySQL 8.0. Kiểm tra phiên bản server thực tế nếu ứng dụng hỗ trợ MySQL 5.7.

### Bài 7. CHECK trong MySQL trước 8.0.16?

**Lời giải:** cú pháp CHECK có thể được chấp nhận nhưng chưa được thực thi như CHECK constraint; enforcement bắt đầu từ MySQL 8.0.16.

### Bài 8. SQLite UPSERT bắt đầu từ phiên bản nào?

**Lời giải:** SQLite 3.24.0.

### Bài 9. SQLite RETURNING có từ phiên bản nào?

**Lời giải:** SQLite 3.35.0.

### Bài 10. SQLite JSONB có giống PostgreSQL JSONB không?

**Lời giải:** không. Đây là định dạng nội bộ riêng của SQLite từ 3.45.0, không tương thích binary với PostgreSQL JSONB.

### Bài 11. Oracle có SQL BOOLEAN column từ trước 23c không?

**Lời giải:** Oracle Database trước 23c/23ai không có SQL BOOLEAN column thông thường, dù PL/SQL có BOOLEAN. SQL BOOLEAN được bổ sung ở thế hệ 23c/23ai.

### Bài 12. MySQL BOOLEAN là kiểu độc lập như PostgreSQL BOOLEAN?

**Lời giải:** không; BOOLEAN/BOOL là alias của TINYINT(1) trong MySQL.

### Bài 13. SQL Server lấy hàng vừa INSERT bằng gì?

**Lời giải:** T-SQL hỗ trợ OUTPUT, ví dụ OUTPUT inserted.Id. JDBC còn có getGeneratedKeys tùy driver.

### Bài 14. PostgreSQL và MySQL nối chuỗi có giống nhau không?

**Lời giải:** PostgreSQL hỗ trợ ||; MySQL thường dùng CONCAT. Trong MySQL, || mặc định có thể là logical OR, trừ khi SQL mode phù hợp thay đổi semantics.

### Bài 15. DDL có thể rollback giống DML trên mọi DBMS không?

**Lời giải:** không. PostgreSQL hỗ trợ transaction cho nhiều DDL; MySQL/Oracle có implicit commit với nhiều DDL; từng loại lệnh cần kiểm tra.

### Bài 16. Tại sao ORDER BY phải có khóa phụ khi phân trang?

**Lời giải:** nếu giá trị sắp xếp không duy nhất, thứ tự giữa các hàng đồng hạng không ổn định; các trang có thể lặp hoặc bỏ sót hàng.

### Bài 17. Cùng tên REPEATABLE READ có nghĩa semantics giống nhau?

**Lời giải:** không. MVCC, locking, snapshot, phantom và serialization behavior khác theo DBMS/config.

### Bài 18. SQLite version trong ứng dụng lấy ở đâu?

**Lời giải:** truy vấn SELECT sqlite_version() trên connection thực tế; CLI trên máy có thể là runtime khác với library ứng dụng đóng gói.

### Bài 19. SQL Server compatibility level có cần kiểm tra không?

**Lời giải:** có. Engine version và database compatibility level là hai thông tin riêng; một số grammar/optimizer behavior phụ thuộc compatibility level.

### Bài 20. Có nên dùng SELECT MAX(id) để lấy ID vừa tạo?

**Lời giải:** không. Transaction khác có thể insert sau đó, khiến MAX(id) không phải ID của hàng hiện tại. Dùng RETURNING, OUTPUT, RETURNING INTO hoặc JDBC generated keys phù hợp.

### Bài 21. JSONB SQLite và PostgreSQL

**Đề:** Ứng dụng dùng PostgreSQL JSONB, chuyển sang SQLite 3.45 rồi đọc binary JSONB cũ được không?

**Lời giải:** không thể giả định. Hai định dạng JSONB khác nhau; chuyển qua JSON text hoặc serialization được định nghĩa rõ.

### Bài 22. Feature detection

**Đề:** Vì sao không dùng so sánh chuỗi `version >= "10"`?

**Lời giải:** so sánh từ điển không phải so sánh phiên bản số; cần parse thành phần số hoặc dùng capability probe/tài liệu product version.

### Bài 23. Query chạy được nhưng kết quả sai

**Đề:** Hai DBMS cùng chấp nhận query nối chuỗi nhưng một hệ trả NULL khi một thành phần NULL, hệ kia trả chuỗi có phần rỗng. Có portable không?

**Lời giải:** chưa. Phải quy định semantics NULL và dùng COALESCE/adapter phù hợp, rồi test trên từng DBMS.

### Bài 24. Nên viết một query UPSERT cho mọi DBMS?

**Lời giải:** không nhất thiết. Dùng một API repository chung, triển khai SQL theo dialect và kiểm thử unique conflict, concurrency, trigger và returned values.

### Bài 25. Một ứng dụng hỗ trợ PostgreSQL 14 và 16

**Đề:** Có thể dùng MERGE trong code chung không?

**Lời giải:** không nếu không có fallback; MERGE chỉ có từ PostgreSQL 15. Chọn baseline thấp nhất hoặc dùng implementation khác cho PostgreSQL 14.

## 36. Checklist trước khi đưa SQL vào ứng dụng đa hệ quản trị

1. Query dùng phần nào của SQL Standard, phần nào là extension?
2. Chuẩn/feature được nhắm tới thuộc edition nào?
3. DBMS cụ thể có hỗ trợ tính năng đó không?
4. Phiên bản tối thiểu của server là gì?
5. Có compatibility level, SQL mode, edition hoặc build option ảnh hưởng không?
6. JDBC driver/ORM có hỗ trợ kiểu hoặc cú pháp này không?
7. Có extension/module/storage engine cần cài không?
8. Identifier/quote/case có portable không?
9. Data type, precision, scale, nullability có cùng semantics không?
10. Date/time/timezone có được chuyển đổi đúng không?
11. NULL, string concatenation và collation có khác không?
12. Pagination có ORDER BY ổn định không?
13. UPSERT/MERGE có cùng concurrency và trigger semantics không?
14. RETURNING/OUTPUT/generated keys có phù hợp driver không?
15. DDL có implicit commit hoặc giới hạn transaction không?
16. Isolation/locking có đáp ứng yêu cầu nghiệp vụ không?
17. Constraint có thực sự được enforce trên version đó không?
18. JSON/ARRAY/ENUM có định dạng riêng không?
19. Có test trên DBMS/version thấp nhất được hỗ trợ không?
20. Có test semantics, edge cases và concurrency, không chỉ parse syntax không?
21. Dialect-specific SQL đã được cô lập chưa?
22. Migration có script theo DBMS và kế hoạch forward/rollback phù hợp không?
23. Capability detection có đáng tin hơn việc so sánh chuỗi version không?
24. Tài liệu vendor/release notes đã được kiểm tra trước khi triển khai chưa?

## 38. Tổng kết

Khi làm việc với nhiều hệ quản trị, không nên chia SQL thành hai loại đơn giản “chuẩn” và “không chuẩn”. Cần biết chính xác **tính năng, phiên bản và semantics**:

- **SQL Standard** mô tả ngôn ngữ và các nhóm tính năng, nhưng implementation có thể hỗ trợ theo từng phần/optional feature.
- **Vendor extensions** có thể rất hữu ích; hãy đánh dấu và cô lập chúng để kiểm soát phụ thuộc.
- **Version support** không chỉ nằm ở server: còn có driver, ORM, compatibility level, SQL mode, extension, edition và build options.
- **Cú pháp giống nhau không đảm bảo hành vi giống nhau** về NULL, collation, kiểu dữ liệu, transaction, DDL, locking, concurrency và error handling.
- **PostgreSQL, MySQL/MariaDB, SQL Server, Oracle và SQLite** có nhiều mốc tính năng khác nhau; xác nhận bản tối thiểu trước khi sử dụng.
- **Portable SQL** nên dùng phần giao nhau khi phù hợp; tính năng đặc thù nên được đặt trong dialect adapter hoặc migration riêng.
- **Kiểm thử đa DBMS** phải kiểm tra syntax, result shape, semantics, transaction, concurrency, permissions và dữ liệu biên.
- **Capability detection** và release documentation đáng tin cậy hơn suy đoán từ tên sản phẩm hoặc so sánh chuỗi version.

Thiết kế tốt là xác định baseline hỗ trợ, dùng SQL chung cho phần nghiệp vụ phổ biến, cô lập extension ở tầng truy cập dữ liệu, và kiểm chứng hành vi trên đúng DBMS/version triển khai.
