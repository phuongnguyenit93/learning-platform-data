# Mô phỏng đặt hàng đồng thời và bảo vệ số lượng tồn kho trong PostgreSQL

Một hệ thống bán hàng có thể nhận nhiều yêu cầu mua cùng một sản phẩm trong cùng thời điểm. Nếu hai transactions cùng đọc số lượng tồn kho trước khi cập nhật, cả hai có thể tin rằng hàng vẫn đủ và cùng xác nhận đơn. Kết quả là bán vượt số lượng thực tế, tồn kho âm hoặc trạng thái đơn hàng không khớp với số hàng đã giữ.

Đây là bài toán đồng thời (concurrency) ở cấp database. Việc kiểm tra tồn kho trong application trước khi gửi INSERT không đủ, vì giữa lần đọc và lần ghi có thể có transaction khác thay đổi dữ liệu. PostgreSQL cần thực hiện kiểm tra và cập nhật theo một thao tác nguyên tử, hoặc khóa đúng rows trong suốt transaction.

Bài **“Mô phỏng đặt hàng đồng thời và bảo vệ số lượng tồn kho”**, thuộc chương **Thực hành tổng hợp** của module **Database Engine Relational PostgreSQL**, xây dựng một mô hình bán hàng nhỏ và thực hành:

- Tái hiện race condition khi hai khách cùng mua lượng hàng gần bằng tồn kho.
- Phân biệt lost update và overselling.
- Dùng conditional UPDATE và CHECK constraints để bảo vệ invariant.
- Dùng SELECT FOR UPDATE để khóa tồn kho khi xử lý đơn nhiều sản phẩm.
- Thiết kế transaction all-or-nothing, idempotency và reservation lifecycle.
- Hiểu READ COMMITTED, REPEATABLE READ, SERIALIZABLE, deadlock và retry.
- Mô phỏng bằng nhiều psql sessions, kiểm tra locks và xác minh kết quả cuối.

> **Nguyên tắc:** kiểm tra điều kiện tồn kho và thay đổi tồn kho phải được phối hợp ở phía database trong cùng transaction. Application không được quyết định dựa trên một giá trị đã đọc từ trước rồi ghi đè lại trạng thái mới hơn.

## 1. Mục tiêu của bài thực hành

Sau khi hoàn thành, bạn có thể:

1. Giải thích vì sao hai yêu cầu mua hàng có thể cùng vượt qua một lần kiểm tra tồn kho.
2. Tạo schema inventory và orders có constraints phù hợp.
3. Chạy hai transactions đồng thời trên cùng một sản phẩm.
4. Sửa race condition bằng một UPDATE có điều kiện.
5. Giữ invariant tồn kho không âm.
6. Khóa nhiều sản phẩm theo thứ tự ổn định.
7. Đảm bảo một order không bị trừ kho hai lần khi request retry.
8. Thiết kế giữ hàng, xác nhận thanh toán và giải phóng reservation.
9. Phân biệt transaction abort, insufficient stock và lỗi kết nối.
10. Thu thập bằng chứng từ pg_stat_activity và pg_locks.

## 2. Bài toán và invariant

Giả sử một cửa hàng có sản phẩm và tồn kho theo kho hàng.

Ta cần duy trì các điều kiện:

- Số lượng hàng thực có không âm.
- Số lượng đang giữ không âm.
- Số lượng đang giữ không vượt quá số lượng thực có.
- Một đơn chỉ được xác nhận nếu mọi dòng hàng đều được đáp ứng.
- Một request retry không tạo đơn hoặc trừ kho lần thứ hai.
- Mọi thay đổi tồn kho phải có thể giải thích và đối soát.

Nếu dùng mô hình đơn giản không có reservation, invariant chính là:

\[
available \geq 0
\]

Nếu tách hàng thực có và hàng đang giữ:

\[
available = on\_hand - reserved
\]

và:

\[
0 \leq reserved \leq on\_hand
\]

Invariant phải được bảo vệ bằng constraints và transaction logic, không chỉ bằng validation ở application.

## 3. Mô hình dữ liệu

Mô hình thực hành gồm:

- products: danh mục sản phẩm.
- inventory: số lượng theo warehouse và product.
- orders: đơn hàng và idempotency key.
- order_items: các dòng sản phẩm trong đơn.
- inventory_reservations: lượng hàng đang giữ cho đơn, nếu dùng reservation workflow.
- inventory_movements: lịch sử thay đổi tồn kho.

Một order có thể chứa nhiều products; cùng một product có thể tồn kho ở nhiều warehouses.

## 4. Tạo schema lab

Tạo schema và bảng:

~~~sql
CREATE SCHEMA IF NOT EXISTS shop;

CREATE TABLE shop.products (
    product_id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    sku text NOT NULL UNIQUE,
    product_name text NOT NULL,
    active boolean NOT NULL DEFAULT true
);

CREATE TABLE shop.inventory (
    warehouse_id bigint NOT NULL,
    product_id bigint NOT NULL
        REFERENCES shop.products(product_id),
    on_hand integer NOT NULL,
    reserved integer NOT NULL DEFAULT 0,
    updated_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (warehouse_id, product_id),
    CONSTRAINT inventory_nonnegative
        CHECK (on_hand >= 0 AND reserved >= 0),
    CONSTRAINT inventory_reserved_within_on_hand
        CHECK (reserved <= on_hand)
);

CREATE TABLE shop.orders (
    order_id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    idempotency_key text NOT NULL UNIQUE,
    status text NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT orders_status_valid
        CHECK (status IN (
            'pending', 'reserved', 'confirmed',
            'cancelled', 'rejected'
        ))
);

CREATE TABLE shop.order_items (
    order_id bigint NOT NULL REFERENCES shop.orders(order_id),
    product_id bigint NOT NULL REFERENCES shop.products(product_id),
    quantity integer NOT NULL CHECK (quantity > 0),
    unit_price numeric(12, 2) NOT NULL CHECK (unit_price >= 0),
    PRIMARY KEY (order_id, product_id)
);
~~~

Primary key của inventory là cặp warehouse/product. Điều này cho phép một sản phẩm có số lượng khác nhau ở nhiều kho.

## 5. Nạp dữ liệu ban đầu

~~~sql
INSERT INTO shop.products (product_id, sku, product_name)
VALUES
    (1, 'SKU-COFFEE', 'Coffee'),
    (2, 'SKU-TEA', 'Tea'),
    (3, 'SKU-MUG', 'Mug')
ON CONFLICT (product_id) DO NOTHING;

INSERT INTO shop.inventory
    (warehouse_id, product_id, on_hand, reserved)
VALUES
    (10, 1, 5, 0),
    (10, 2, 8, 0),
    (10, 3, 20, 0)
ON CONFLICT (warehouse_id, product_id)
DO UPDATE SET
    on_hand = EXCLUDED.on_hand,
    reserved = EXCLUDED.reserved,
    updated_at = now();
~~~

Fixture ban đầu có 5 đơn vị Coffee ở warehouse 10. Ta sẽ mô phỏng hai khách cùng mua 4 đơn vị.

Chạy seed trong database lab riêng. Không chạy reset tồn kho này trên môi trường đang có giao dịch thật.

## 6. Kiểm tra trạng thái ban đầu

~~~sql
SELECT
    warehouse_id,
    product_id,
    on_hand,
    reserved,
    on_hand - reserved AS available
FROM shop.inventory
ORDER BY warehouse_id, product_id;
~~~

Kết quả mong đợi cho Coffee:

| warehouse_id | product_id | on_hand | reserved | available |
|---:|---:|---:|---:|---:|
| 10 | 1 | 5 | 0 | 5 |

Đây là baseline để so sánh sau mỗi thí nghiệm.

## 7. Vì sao kiểm tra tồn kho ở application chưa đủ?

Một flow ngây thơ thường làm:

1. SELECT available.
2. Application kiểm tra available có đủ không.
3. Nếu đủ, application INSERT order.
4. Application UPDATE inventory.

Giữa bước 1 và bước 4 có thể có transaction khác làm thay đổi cùng row.

Ví dụ cả hai khách đọc được available = 5. Mỗi khách muốn mua 4. Cả hai đều thấy 4 <= 5 và tiếp tục.

Đây là race condition: kết quả phụ thuộc vào cách các transactions xen kẽ.

## 8. Mô phỏng race condition bằng hai sessions

Mở hai terminal độc lập và kết nối cùng database:

~~~bash
psql -X -d inventory_lab
~~~

Nếu database có tên khác, thay inventory_lab bằng tên database lab của bạn.

Trong cả hai sessions, xác nhận:

~~~sql
SELECT pg_backend_pid();
~~~

Hai PID phải khác nhau.

## 9. Thí nghiệm A: hai sessions cùng đọc tồn kho

Trong Session A:

~~~sql
BEGIN;

SELECT on_hand - reserved AS available
FROM shop.inventory
WHERE warehouse_id = 10
  AND product_id = 1;
~~~

Trong Session B, trước khi A cập nhật:

~~~sql
BEGIN;

SELECT on_hand - reserved AS available
FROM shop.inventory
WHERE warehouse_id = 10
  AND product_id = 1;
~~~

Cả hai sessions đều có thể đọc giá trị 5 vì SELECT thông thường không khóa row để ngăn transaction khác cập nhật.

Đây là điểm bắt đầu của race condition.

## 10. Thí nghiệm B: ghi đè bằng giá trị cũ

Giả sử application đọc available = 5 và tự tính số dư mới là 1.

Trong Session A:

~~~sql
UPDATE shop.inventory
SET on_hand = 1,
    updated_at = now()
WHERE warehouse_id = 10
  AND product_id = 1;
~~~

Trong Session B, application cũng dùng giá trị đã đọc trước đó:

~~~sql
UPDATE shop.inventory
SET on_hand = 1,
    updated_at = now()
WHERE warehouse_id = 10
  AND product_id = 1;
~~~

Sau khi cả hai transactions commit, on_hand có thể là 1 dù hai đơn đã được chấp nhận, tổng số lượng bán là 8.

Đây là lost update: transaction sau ghi một giá trị tính từ snapshot cũ và làm mất tác động logic của transaction trước.

Trong lab, rollback và nạp lại baseline trước thí nghiệm tiếp theo.

## 11. Phân biệt lost update và overselling

Hai vấn đề có liên quan nhưng không giống nhau:

- **Lost update:** một cập nhật dựa trên giá trị cũ ghi đè kết quả cập nhật khác.
- **Overselling:** hệ thống chấp nhận tổng số lượng bán lớn hơn số lượng có thể cung cấp.

Ví dụ nếu hai transactions cùng trừ 4 từ 5 bằng biểu thức đọc-cập nhật riêng, chúng có thể ghi kết quả 1 thay vì -3. Database nhìn thấy 1 nhưng hệ thống đã xác nhận bán 8.

Nếu dùng phép trừ nguyên tử mà không có constraint, kết quả có thể thành -3. Nếu có CHECK constraint, cập nhật khiến tồn kho âm sẽ bị từ chối. Cần cả cách cập nhật đúng lẫn invariant ở database.

## 12. Phép trừ nguyên tử có điều kiện

Cách đơn giản và hiệu quả là gộp kiểm tra và cập nhật trong cùng một statement:

~~~sql
UPDATE shop.inventory
SET on_hand = on_hand - 4,
    updated_at = now()
WHERE warehouse_id = 10
  AND product_id = 1
  AND on_hand - reserved >= 4
RETURNING on_hand, reserved;
~~~

Kết quả:

- Một row được trả về: đã trừ được hàng.
- Không có row nào: không có inventory row hoặc số lượng khả dụng không đủ.

Application không cần đọc số lượng trước rồi tính giá trị mới. Điều kiện và phép trừ được PostgreSQL thực hiện trên row được cập nhật.

## 13. Vì sao conditional UPDATE an toàn dưới READ COMMITTED?

Khi hai transactions cùng UPDATE một row, PostgreSQL dùng row-level lock để tuần tự hóa các thay đổi trên row đó.

Nếu transaction thứ hai phải chờ transaction thứ nhất, PostgreSQL kiểm tra lại điều kiện WHERE trên phiên bản row mới nhất theo semantics của READ COMMITTED trước khi cập nhật.

Vì vậy, nếu A trừ 4 từ 5 và commit, B sẽ đánh giá lại điều kiện available >= 4. Giá trị còn lại chỉ là 1, nên B không cập nhật row.

Điểm quan trọng là điều kiện phải nằm trong chính UPDATE, không chỉ nằm trong một SELECT trước đó.

## 14. Thí nghiệm C: chạy conditional UPDATE đồng thời

Nạp lại baseline:

~~~sql
UPDATE shop.inventory
SET on_hand = 5, reserved = 0
WHERE warehouse_id = 10 AND product_id = 1;
~~~

Trong Session A:

~~~sql
BEGIN;

UPDATE shop.inventory
SET on_hand = on_hand - 4,
    updated_at = now()
WHERE warehouse_id = 10
  AND product_id = 1
  AND on_hand - reserved >= 4
RETURNING on_hand;
~~~

A nhận được on_hand = 1. Chưa commit.

Trong Session B:

~~~sql
BEGIN;

UPDATE shop.inventory
SET on_hand = on_hand - 4,
    updated_at = now()
WHERE warehouse_id = 10
  AND product_id = 1
  AND on_hand - reserved >= 4
RETURNING on_hand;
~~~

B sẽ chờ row lock.

Quay lại Session A:

~~~sql
COMMIT;
~~~

Sau khi A commit, B tiếp tục. Điều kiện được kiểm tra lại và B nhận zero rows.

Trong Session B:

~~~sql
ROLLBACK;
~~~

Chỉ một transaction thành công. Tổng số hàng còn lại là 1.

Kết quả phải là:

## 16. CHECK constraint là lớp bảo vệ cuối

Bảng inventory đã có:

~~~sql
CHECK (on_hand >= 0 AND reserved >= 0)
~~~

và:

~~~sql
CHECK (reserved <= on_hand)
~~~

Nếu code có lỗi và cố ghi on_hand âm hoặc reserved lớn hơn on_hand, PostgreSQL từ chối statement.

Constraint không thay thế logic xử lý insufficient stock. Nó bảo vệ tính đúng đắn của dữ liệu khi một code path khác quên điều kiện.

Không bắt lỗi constraint rồi vẫn xác nhận đơn. Nếu cập nhật tồn kho thất bại, transaction tạo order phải rollback.

## 17. Đóng gói thao tác trừ kho trong function

Có thể tạo function để mọi callers dùng cùng một quy tắc:

~~~sql
CREATE OR REPLACE FUNCTION shop.take_stock(
    p_warehouse_id bigint,
    p_product_id bigint,
    p_quantity integer
)
RETURNS integer
LANGUAGE plpgsql
AS $$
DECLARE
    v_on_hand integer;
BEGIN
    IF p_quantity <= 0 THEN
        RAISE EXCEPTION 'quantity must be positive';
    END IF;

    UPDATE shop.inventory
    SET on_hand = on_hand - p_quantity,
        updated_at = now()
    WHERE warehouse_id = p_warehouse_id
      AND product_id = p_product_id
      AND on_hand - reserved >= p_quantity
    RETURNING on_hand INTO v_on_hand;

    IF NOT FOUND THEN
        RAISE EXCEPTION USING
            ERRCODE = 'P0001',
            MESSAGE = 'insufficient stock or inventory row missing';
    END IF;

    RETURN v_on_hand;
END;
$$;
~~~

Function này raise exception nếu không đủ hàng. Caller phải xử lý transaction failure và không tạo order thành công.

Function chạy trong transaction của caller; nó không tự commit transaction.

## 18. Tạo order và trừ kho trong cùng transaction

Không được commit phần trừ kho rồi mới tạo order ở transaction khác. Nếu INSERT order thất bại sau khi đã trừ kho và transaction đầu đã commit, inventory bị thiếu mà không có order tương ứng.

Một flow đơn giản:

~~~sql
BEGIN;

SELECT shop.take_stock(10, 1, 2);

INSERT INTO shop.orders (idempotency_key, status)
VALUES ('checkout-2025-0001', 'confirmed')
RETURNING order_id;

-- Insert order_items using the returned order_id.

COMMIT;
~~~

Trong ứng dụng, lấy order_id và insert order_items trong cùng transaction. Nếu bất kỳ bước nào thất bại, rollback cả order và inventory change.

## 19. Đảm bảo quantity hợp lệ

Không chấp nhận quantity bằng 0 hoặc số âm.

Có thể kiểm tra ở hai lớp:

- Application validation để trả lỗi sớm, dễ hiểu.
- Database CHECK/function validation để bảo vệ mọi code paths.

Ví dụ constraint:

~~~sql
ALTER TABLE shop.order_items
ADD CONSTRAINT order_items_quantity_positive
CHECK (quantity > 0);
~~~

Không dùng quantity âm để biểu diễn hoàn hàng. Return/refund nên là một nghiệp vụ riêng với movement type và audit record rõ ràng.

## 20. Đặt hàng nhiều sản phẩm

Một order có thể gồm nhiều dòng:

| Product | Requested quantity |
|---|---:|
| Coffee | 2 |
| Tea | 3 |
| Mug | 1 |

Yêu cầu all-or-nothing: hoặc giữ/trừ đủ mọi dòng, hoặc không thay đổi tồn kho nào.

Nếu xử lý từng dòng và commit sau mỗi dòng, một order có thể chỉ trừ được một phần. Toàn bộ các thao tác cần nằm trong một transaction.

## 21. Gộp dòng trùng sản phẩm

Request có thể chứa cùng product nhiều lần. Ví dụ Coffee xuất hiện ở hai dòng với quantity 2 và 3.

Trước khi khóa/cập nhật inventory, aggregate thành một dòng Coffee quantity 5. Nếu không, cùng một transaction có thể xử lý cùng inventory row nhiều lần theo thứ tự khó dự đoán.

Ví dụ request staging table:

~~~sql
CREATE TEMP TABLE requested_items (
    product_id bigint NOT NULL,
    quantity bigint NOT NULL CHECK (quantity > 0)
) ON COMMIT DROP;

INSERT INTO requested_items (product_id, quantity)
VALUES (1, 2), (2, 3), (1, 3);
~~~

Tổng yêu cầu là Coffee 5 và Tea 3.

## 22. Khóa nhiều inventory rows theo thứ tự ổn định

Khi một transaction cần nhiều products, các transactions khác có thể khóa cùng rows theo thứ tự khác nhau và tạo deadlock.

Khóa theo product_id tăng dần:

~~~sql
WITH requested AS (
    SELECT product_id, sum(quantity) AS required_qty
    FROM requested_items
    GROUP BY product_id
)
SELECT
    i.product_id,
    i.on_hand,
    i.reserved,
    r.required_qty
FROM shop.inventory AS i
JOIN requested AS r USING (product_id)
WHERE i.warehouse_id = 10
ORDER BY i.product_id
FOR UPDATE OF i;
~~~

Các rows được khóa đến khi transaction kết thúc. Ứng dụng phải kiểm tra số rows trả về bằng số product IDs duy nhất được yêu cầu và available của từng row đủ lớn.

Nếu thiếu inventory row hoặc một sản phẩm không đủ hàng, rollback transaction trước khi tạo order.

## 23. Vì sao thứ tự khóa quan trọng?

Giả sử transaction A cần product 1 rồi product 2, còn transaction B cần product 2 rồi product 1.

- A khóa product 1.
- B khóa product 2.
- A chờ product 2.
- B chờ product 1.

Hai transactions chờ nhau tạo deadlock. PostgreSQL sẽ phát hiện và hủy một transaction.

Nếu mọi code paths khóa theo cùng thứ tự product_id tăng dần, tình huống vòng chờ này được giảm đáng kể.

Dùng thứ tự ổn định cho cả inventory rows, account rows và các resources khác mà transaction có thể khóa.

## 24. Cập nhật nhiều sản phẩm sau khi đã khóa

Sau khi khóa và xác minh tất cả rows, có thể cập nhật tồn kho:

~~~sql
WITH requested AS (
    SELECT product_id, sum(quantity) AS required_qty
    FROM requested_items
    GROUP BY product_id
)
UPDATE shop.inventory AS i
SET on_hand = i.on_hand - r.required_qty::integer,
    updated_at = now()
FROM requested AS r
WHERE i.warehouse_id = 10
  AND i.product_id = r.product_id
  AND i.on_hand - i.reserved >= r.required_qty
RETURNING i.product_id, i.on_hand;
~~~

Ứng dụng cần xác nhận số rows cập nhật bằng số product IDs duy nhất. Nếu không khớp, rollback toàn transaction.

Vì các rows đã được khóa và kiểm tra trước đó, transaction giữ quyền kiểm soát cho đến commit. Không bỏ qua kết quả RETURNING.

## 25. Tạo order sau khi xác minh inventory

Trình tự trong một transaction:

1. Nhận request và kiểm tra quantity.
2. Gộp dòng trùng product.
3. Khóa inventory rows theo thứ tự ổn định.
4. Xác minh mọi sản phẩm tồn tại và đủ available.
5. Cập nhật inventory.
6. Tạo order.
7. Tạo order_items.
8. Ghi inventory movement/audit rows.
9. Commit.

Nếu bất kỳ bước nào thất bại, rollback toàn bộ. Không gửi email, gọi payment provider hoặc thực hiện side effect ngoài database trước khi transaction commit; dùng outbox pattern cho công việc cần phát đi sau commit.

## 26. Idempotency khi client retry

Client có thể gửi request, server xử lý thành công nhưng response bị mất. Client retry và gửi cùng một đơn lần nữa.

Nếu chỉ dựa vào request mới, hệ thống có thể tạo order thứ hai và trừ stock lần thứ hai.

Dùng idempotency key duy nhất cho mỗi ý định checkout:

~~~sql
CREATE UNIQUE INDEX orders_idempotency_key_uq
ON shop.orders (idempotency_key);
~~~

Bảng orders trong lab đã có UNIQUE constraint tương ứng. Cùng một key phải trả về kết quả của operation đã xử lý, không chạy lại side effects.

## 27. Xử lý idempotency key trong transaction

Một pattern:

1. Thử tạo order với idempotency key.
2. Nếu insert thành công, transaction sở hữu request và tiếp tục reserve stock.
3. Nếu key đã tồn tại, đọc order hiện có và trả trạng thái đã lưu.
4. Không trừ stock lần nữa cho request đã xử lý.
5. Nếu xử lý thất bại, rollback cả idempotency record và inventory changes, hoặc lưu trạng thái failure theo policy riêng.

Ví dụ:

~~~sql
INSERT INTO shop.orders (idempotency_key, status)
VALUES ('checkout-2025-0002', 'pending')
ON CONFLICT (idempotency_key) DO NOTHING
RETURNING order_id;
~~~

Nếu không trả về row, application phải lấy order hiện có và quyết định response theo status. Không tiếp tục tạo order_items hoặc trừ kho như một request mới.

## 28. Reservation khác với bán hàng ngay

Nhiều hệ thống không muốn trừ on_hand ngay khi checkout. Chúng giữ hàng trong một khoảng thời gian để chờ payment.

Trong mô hình này:

- on_hand: số lượng thực có trong kho.
- reserved: số lượng đã giữ cho orders chưa hoàn tất.
- available = on_hand - reserved.

Khi tạo reservation, tăng reserved. Khi thanh toán thành công, giảm cả on_hand và reserved. Khi đơn hết hạn/hủy, chỉ giảm reserved.

## 29. Tạo bảng reservations

~~~sql
CREATE TABLE shop.inventory_reservations (
    reservation_id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id bigint NOT NULL REFERENCES shop.orders(order_id),
    warehouse_id bigint NOT NULL,
    product_id bigint NOT NULL,
    quantity integer NOT NULL CHECK (quantity > 0),
    status text NOT NULL
        CHECK (status IN ('reserved', 'consumed', 'released', 'expired')),
    expires_at timestamptz NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now(),
    FOREIGN KEY (warehouse_id, product_id)
        REFERENCES shop.inventory(warehouse_id, product_id),
    UNIQUE (order_id, warehouse_id, product_id)
);
~~~

Unique constraint ngăn cùng order tạo nhiều reservations cho cùng một product ở cùng warehouse.

## 30. Tạo reservation nguyên tử

~~~sql
UPDATE shop.inventory
SET reserved = reserved + 2,
    updated_at = now()
WHERE warehouse_id = 10
  AND product_id = 1
  AND on_hand - reserved >= 2
RETURNING on_hand, reserved;
~~~

Nếu trả về một row, có thể tạo reservation record trong cùng transaction.

Nếu không trả về row, không đủ hàng. Rollback transaction tạo order/reservation.

CHECK constraint reserved <= on_hand là lớp bảo vệ bổ sung.

## 31. Xác nhận reservation sau khi thanh toán

Khi payment provider xác nhận thành công, cần chuyển reservation sang consumed và giảm số hàng thực có.

Trong cùng transaction:

1. Khóa reservation row.
2. Chỉ chuyển status từ reserved sang consumed.
3. Giảm on_hand và reserved cùng quantity.
4. Ghi inventory movement.
5. Đổi order status thành confirmed.
6. Commit.

Ví dụ cập nhật inventory:

~~~sql
UPDATE shop.inventory
SET on_hand = on_hand - 2,
    reserved = reserved - 2,
    updated_at = now()
WHERE warehouse_id = 10
  AND product_id = 1
  AND on_hand >= 2
  AND reserved >= 2;
~~~

Chỉ thực hiện sau khi transaction đã xác minh và chuyển đúng reservation state. Nếu reservation đã consumed trước đó, retry không được trừ kho lần nữa.

## 32. Giải phóng reservation khi hủy

Khi khách hủy hoặc payment thất bại:

~~~sql
UPDATE shop.inventory
SET reserved = reserved - 2,
    updated_at = now()
WHERE warehouse_id = 10
  AND product_id = 1
  AND reserved >= 2;
~~~

Trong thực tế, không chỉ dựa vào quantity. Trước tiên khóa reservation row và chỉ chuyển từ status reserved sang released/expired đúng một lần. Chỉ transaction đổi được status mới được giảm reserved.

Điều này ngăn hai workers cùng giải phóng một reservation và làm reserved bị giảm hai lần.

## 33. Hết hạn reservation

Một worker có thể tìm các reservations đã hết hạn:

~~~sql
SELECT reservation_id
FROM shop.inventory_reservations
WHERE status = 'reserved'
  AND expires_at <= now()
ORDER BY expires_at, reservation_id
FOR UPDATE SKIP LOCKED
LIMIT 100;
~~~

SKIP LOCKED cho phép nhiều workers xử lý các rows khác nhau mà không chờ nhau trên cùng reservation.

Trong một transaction, worker khóa batch, đổi status sang expired, giảm reserved tương ứng và commit. Nếu xử lý thất bại, rollback để worker khác có thể thử lại.

## 34. Không giữ row locks trong lúc gọi payment provider

Gọi external payment service có thể mất nhiều giây hoặc timeout. Không nên giữ transaction và row locks trong suốt thời gian network call.

Một flow tốt hơn:

1. Transaction ngắn tạo order và reservation.
2. Commit.
3. Worker gọi payment provider.
4. Transaction khác xác nhận hoặc giải phóng reservation dựa trên kết quả.
5. Timeout/retry được xử lý qua trạng thái và idempotency.

Dùng outbox để ghi event cần gửi trong cùng transaction với order/reservation; worker đọc outbox sau commit.

## 35. State machine cho order

Định nghĩa trạng thái hợp lệ:

~~~text
pending
   |
   v
reserved
   |
   +------> confirmed
   |
   +------> cancelled
   |
   +------> expired
~~~

Không cho phép chuyển trạng thái tùy ý. Ví dụ confirmed không nên chuyển ngược thành pending chỉ vì client retry.

Dùng UPDATE có điều kiện theo trạng thái hiện tại:

~~~sql
UPDATE shop.orders
SET status = 'confirmed'
WHERE order_id = 100
  AND status = 'reserved'
RETURNING order_id;
~~~

Nếu không có row trả về, trạng thái đã thay đổi hoặc order không tồn tại. Application cần đọc lại và xử lý idempotently.

## 36. READ COMMITTED

READ COMMITTED là isolation level mặc định của PostgreSQL.

Mỗi statement nhìn thấy snapshot mới tại thời điểm statement bắt đầu. Một transaction có thể thấy kết quả commit mới ở statement sau.

Conditional UPDATE trên cùng inventory row thường là cách đơn giản để bảo vệ decrement dưới READ COMMITTED.

Không nên thay bằng SELECT rồi quyết định ở application, vì statement sau có thể làm việc trên trạng thái đã thay đổi.

## 37. REPEATABLE READ

REPEATABLE READ giữ snapshot ổn định hơn trong transaction. Nếu transaction cố cập nhật row đã bị transaction khác thay đổi sau snapshot của nó, PostgreSQL có thể abort với serialization failure.

Application phải retry toàn bộ transaction khi gặp SQLSTATE 40001 nếu operation có thể retry an toàn.

Không retry riêng statement cuối vì các quyết định trước đó dựa trên snapshot cũ.

## 38. SERIALIZABLE

SERIALIZABLE yêu cầu các transactions có kết quả tương đương một thứ tự tuần tự. PostgreSQL dùng Serializable Snapshot Isolation để phát hiện các dependency patterns có thể tạo anomaly.

Transaction có thể bị hủy với serialization failure dù không có deadlock.

Dùng SERIALIZABLE khi invariant nghiệp vụ liên quan nhiều rows/predicates khó bảo vệ bằng khóa tường minh hoặc atomic updates. Cần có retry loop và đo tỷ lệ abort.

## 39. Retry serialization failure

SQLSTATE quan trọng:

| SQLSTATE | Ý nghĩa | Xử lý |
|---|---|---|
| 40001 | serialization_failure | Retry toàn transaction |
| 40P01 | deadlock_detected | Retry toàn transaction nếu operation idempotent |
| 55P03 | lock_not_available | Xem xét retry/backoff hoặc trả busy |
| 23514 | check_violation | Lỗi invariant/validation; không retry mù |
| 23505 | unique_violation | Xử lý duplicate/idempotency theo constraint |

Retry cần có giới hạn số lần, exponential backoff có jitter và log correlation ID. Không retry vô hạn.

## 40. Deadlock là gì?

Deadlock xảy ra khi các transactions giữ locks mà transactions còn lại cần, tạo thành vòng chờ.

Ví dụ:

~~~text
Transaction A                Transaction B
-------------                -------------
Lock inventory row 1         Lock inventory row 2
Wait for row 2               Wait for row 1
       |                            |
       +---------- cycle -----------+
~~~

PostgreSQL phát hiện deadlock và abort một transaction để phá vòng chờ.

## 41. Phòng tránh deadlock

- Khóa rows theo thứ tự ổn định.
- Giữ transactions ngắn.
- Không gọi network khi đang giữ locks.
- Tránh lock thêm rows không cần thiết.
- Dùng index phù hợp để giảm phạm vi scan/lock.
- Dùng cùng thứ tự khóa trong mọi code paths.
- Xử lý deadlock bằng retry toàn transaction khi an toàn.

Thứ tự khóa phải thống nhất giữa checkout, cancel, payment confirmation và inventory adjustment.

## 42. Lock timeout và statement timeout

Có thể giới hạn thời gian chờ lock trong transaction:

~~~sql
SET LOCAL lock_timeout = '2s';
SET LOCAL statement_timeout = '10s';
~~~

SET LOCAL chỉ áp dụng trong transaction hiện tại.

Lock timeout giúp request không chờ quá lâu. Statement timeout giới hạn thời gian thực thi statement. Chọn giá trị theo latency budget và workload, không copy một con số chung cho mọi hệ thống.

Khi timeout, transaction thường cần rollback trước khi connection được tái sử dụng.

## 43. Optimistic locking bằng version column

Nếu xung đột hiếm và application cần phát hiện stale reads, có thể dùng version:

~~~sql
ALTER TABLE shop.inventory
ADD COLUMN version bigint NOT NULL DEFAULT 0;
~~~

Update:

~~~sql
UPDATE shop.inventory
SET on_hand = on_hand - 1,
    version = version + 1,
    updated_at = now()
WHERE warehouse_id = 10
  AND product_id = 1
  AND version = 7
  AND on_hand - reserved >= 1
RETURNING version, on_hand;
~~~

Nếu không có row, version đã thay đổi hoặc không đủ hàng. Application đọc lại và quyết định retry hoặc trả conflict.

Optimistic locking không thay thế CHECK constraints.

## 44. Advisory locks

PostgreSQL có transaction-level advisory locks để khóa một logical resource không tương ứng trực tiếp với một row.

Ví dụ:

~~~sql
SELECT pg_advisory_xact_lock(9001, 10);
~~~

Lock được giữ đến hết transaction.

Advisory lock hữu ích khi cần serialize một workflow theo key nghiệp vụ, nhưng mọi code paths liên quan phải tuân thủ cùng lock protocol. Nó không tự bảo vệ inventory nếu một code path khác bỏ qua advisory lock.

Ưu tiên row locks/constraints khi resource có row đại diện rõ ràng.

## 45. Queue workers và SKIP LOCKED

Nếu nhiều workers xử lý orders/reservations, có thể claim công việc bằng SKIP LOCKED:

~~~sql
WITH next_jobs AS (
    SELECT order_id
    FROM shop.orders
    WHERE status = 'pending'
    ORDER BY created_at, order_id
    FOR UPDATE SKIP LOCKED
    LIMIT 20
)
UPDATE shop.orders AS o
SET status = 'reserved'
FROM next_jobs AS j
WHERE o.order_id = j.order_id
RETURNING o.order_id;
~~~


Mỗi worker nhận một tập rows khác nhau. SKIP LOCKED phù hợp cho queue-like processing, nhưng không cung cấp fairness tuyệt đối; một row liên tục bị khóa có thể bị trì hoãn.

## 46. Inventory movement ledger

Chỉ lưu số dư hiện tại khiến việc điều tra sai lệch khó khăn. Có thể ghi mọi thay đổi vào movement ledger:

~~~sql
CREATE TABLE shop.inventory_movements (
    movement_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    warehouse_id bigint NOT NULL,
    product_id bigint NOT NULL,
    order_id bigint,
    movement_type text NOT NULL,
    quantity_delta integer NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now(),
    reference_key text
);
~~~

Ví dụ movement types: receipt, reservation, release, sale, return, adjustment.

Ghi movement cùng transaction với inventory update. Không ghi ledger sau commit bằng một request độc lập có thể thất bại.

## 47. Đối soát inventory và ledger

Có thể kiểm tra số dư âm hoặc reservation vượt on_hand:

~~~sql
SELECT
    warehouse_id,
    product_id,
    on_hand,
    reserved
FROM shop.inventory
WHERE on_hand < 0
   OR reserved < 0
   OR reserved > on_hand;
~~~

Đối soát movement cần một opening balance và quy tắc rõ về loại movement nào tác động đến on_hand hoặc reserved. Ledger không tự đúng nếu code ghi sai; cần reconciliation job và audit trail.

## 48. Tồn kho theo nhiều warehouses

Một product có thể có hàng ở nhiều warehouses. Checkout cần chọn warehouse theo business rule:

- Kho gần địa chỉ giao hàng.
- Kho đủ toàn bộ quantity.
- Kho có chi phí vận chuyển thấp.
- Ưu tiên một kho để tránh split shipment.

Khi một order lấy hàng từ nhiều warehouses, transaction phải khóa inventory rows theo thứ tự toàn cục, ví dụ warehouse_id rồi product_id, để giảm deadlocks.

Không chỉ khóa theo product_id nếu cùng product xuất hiện ở nhiều warehouses.

## 49. Backorder và overselling policy

Không phải hệ thống nào cũng cấm bán vượt available stock. Một số business hỗ trợ backorder hoặc preorder.

Nếu cho phép backorder, biểu diễn trạng thái rõ:

- Available stock.
- Reserved stock.
- Backordered quantity.
- Expected replenishment date.

Không dùng giá trị âm để ngầm biểu diễn backorder nếu invariant của inventory yêu cầu nonnegative. Tách business promise khỏi physical stock.

## 50. Xử lý cancellation và refund

Cancel order cần kiểm tra state transition và inventory movement.

- Nếu order mới reserved, release reservation.
- Nếu order đã confirmed và chưa giao, có thể restock theo policy.
- Nếu hàng đã ship, quy trình return/receipt phải ghi nhận khi hàng thực sự quay lại.
- Refund payment là một workflow riêng với idempotency key riêng.

Không tự động cộng stock chỉ vì payment refund thành công; hàng có thể chưa quay về kho.

## 51. Xác minh với nhiều sessions

Sau mỗi thí nghiệm, query:

~~~sql
SELECT
    i.warehouse_id,
    p.sku,
    i.on_hand,
    i.reserved,
    i.on_hand - i.reserved AS available
FROM shop.inventory AS i
JOIN shop.products AS p USING (product_id)
ORDER BY i.warehouse_id, p.sku;
~~~

Kiểm tra số orders, order_items và reservation statuses:

~~~sql
SELECT status, count(*)
FROM shop.orders
GROUP BY status
ORDER BY status;

SELECT status, count(*)
FROM shop.inventory_reservations
GROUP BY status
ORDER BY status;
~~~

Đừng chỉ nhìn response của application. Database state là bằng chứng cuối cùng về transaction outcome.

## 52. Quan sát lock waits

Xem sessions đang chờ lock:

~~~sql
SELECT
    pid,
    usename,
    state,
    wait_event_type,
    wait_event,
    now() - query_start AS query_age,
    left(query, 160) AS query_text
FROM pg_stat_activity
WHERE wait_event_type = 'Lock'
ORDER BY query_start;
~~~

Xem locks và session:

~~~sql
SELECT
    a.pid,
    a.application_name,
    a.state,
    l.locktype,
    l.mode,
    l.granted,
    l.relation::regclass AS relation_name
FROM pg_locks AS l
JOIN pg_stat_activity AS a USING (pid)
ORDER BY a.pid, l.granted;
~~~

Các views này giúp nhận diện blocking sessions. Để tìm blocker trực tiếp, có thể dùng pg_blocking_pids(pid).

## 53. Tìm blocking relationships

~~~sql
SELECT
    blocked.pid AS blocked_pid,
    blocker.pid AS blocker_pid,
    blocked.query AS blocked_query,
    blocker.query AS blocker_query
FROM pg_stat_activity AS blocked
JOIN LATERAL unnest(pg_blocking_pids(blocked.pid)) AS b(pid)
  ON true
JOIN pg_stat_activity AS blocker
  ON blocker.pid = b.pid;
~~~

Cần quyền xem thông tin session phù hợp. Trong production, bảo vệ query text vì có thể chứa dữ liệu nhạy cảm.

## 54. Kiểm tra invariant định kỳ

Một query kiểm tra dữ liệu bất thường:

~~~sql
SELECT *
FROM shop.inventory
WHERE on_hand < 0
   OR reserved < 0
   OR reserved > on_hand;
~~~

Nếu CHECK constraints luôn được bật và không bị bypass, query không nên trả rows. Vẫn hữu ích trong operational monitoring và sau migration/import.

Có thể thêm checks cho reservations không khớp order status, orders thiếu order_items hoặc duplicate external references.

## 55. Mô phỏng tải bằng pgbench

Tạo file workload, ví dụ reserve.sql:

~~~sql
UPDATE shop.inventory
SET on_hand = on_hand - 1,
    updated_at = now()
WHERE warehouse_id = 10
  AND product_id = 1
  AND on_hand - reserved >= 1;
~~~

Chạy nhiều clients:

~~~bash
pgbench -n -c 20 -j 4 -T 30 -f reserve.sql inventory_lab
~~~

Đây là bài test tải đơn giản. Nó đo contention và throughput trên một inventory row nóng; không tự xác minh nghiệp vụ order/rollback. Dùng test harness ở application level để đếm success, insufficient-stock outcomes và duplicate requests.

Reset baseline trước mỗi lượt và giới hạn tổng số giao dịch để không làm cạn stock trước khi đo xong.

## 56. Test cases bắt buộc

Một bộ test concurrency nên bao gồm:

1. Hai buyers cùng mua 4 từ stock 5: chỉ một thành công.
2. Hai buyers cùng mua 2 từ stock 5: cả hai có thể thành công, còn 1.
3. Request quantity bằng 0: bị từ chối.
4. Request quantity âm: bị từ chối.
5. Product không có inventory row: bị từ chối.
6. Multi-item order thiếu một product: rollback mọi thay đổi.
7. Hai orders cùng idempotency key: chỉ một lần trừ kho.
8. Payment callback gửi hai lần: reservation chỉ consume một lần.
9. Cancel callback gửi hai lần: reservation chỉ release một lần.
10. Hai orders khóa nhiều products theo thứ tự ngược: xác minh deadlock prevention.
11. Transaction bị timeout: không để order nửa chừng.
12. Client mất response sau commit rồi retry: trả kết quả cũ.
13. Hai warehouses cùng có hàng: chọn đúng kho theo policy.
14. Reservation hết hạn trong lúc payment callback đến: state transition chỉ có một winner.

## 57. Những lỗi thường gặp

### 57.1. SELECT rồi UPDATE theo giá trị application giữ

Tạo stale write và race condition. Đưa predicate vào UPDATE hoặc khóa row trước khi quyết định.

### 57.2. Không có CHECK constraint

Một code path khác có thể ghi tồn kho âm. Dùng constraint để bảo vệ invariant.

### 57.3. Commit từng order item

Có thể tạo order chỉ trừ một phần hàng. Xử lý mọi dòng trong một transaction.

### 57.4. Khóa rows theo thứ tự khác nhau

Làm tăng nguy cơ deadlock. Dùng thứ tự ổn định trên mọi code paths.

### 57.5. Không dùng idempotency key

Client retry có thể tạo order và trừ kho lần hai.

### 57.6. Giữ transaction khi gọi payment API

Tạo lock waits dài và giữ connection. Commit reservation trước, gọi external service ngoài transaction, rồi finalize bằng transaction mới.

### 57.7. Retry mọi lỗi

Constraint violation hoặc insufficient stock không phải serialization failure. Chỉ retry lỗi transient được xác định và phải retry toàn transaction.

### 57.8. Dùng SKIP LOCKED mà không theo dõi backlog

Một số jobs có thể bị trì hoãn. Theo dõi oldest pending age và retry/dead-letter policy.

### 57.9. Chỉ dựa vào application cache

Cache có thể stale. Quyết định cuối về inventory phải được xác nhận bằng transaction ở database.

### 57.10. Không đối soát movement ledger

## 61. Checklist triển khai thực tế

**Dữ liệu và invariant**

- Inventory có key theo warehouse/product.
- Quantity được kiểm tra dương.
- CHECK constraints bảo vệ số dư.
- Có movement/audit trail.
- Có reconciliation query.

**Concurrency**

- Conditional UPDATE hoặc row locking được dùng cho mọi stock changes.
- Multi-row locks có thứ tự ổn định.
- Transactions ngắn.
- Lock/statement timeout phù hợp.
- Deadlock và serialization retry có giới hạn.

**Order workflow**

- Inventory và order changes cùng transaction.
- Multi-item order là all-or-nothing.
- Idempotency key có unique constraint.
- Order state transitions được kiểm tra.
- Reservation consume/release chỉ chạy một lần.
- External calls nằm ngoài transaction dài.

**Vận hành**

- Lock waits và hot rows được theo dõi.
- Insufficient stock khác database failure.
- Retry và backoff có metrics.
- Load test dùng dữ liệu đại diện.
- Restore/reconciliation có runbook.
- Alerts không tiết lộ dữ liệu nhạy cảm.

## 62. Câu hỏi thường gặp

### Tại sao application SELECT available rồi UPDATE không an toàn?

Vì một transaction khác có thể thay đổi inventory sau SELECT và trước UPDATE. Giá trị application giữ có thể đã stale.

### UPDATE số học có tự an toàn không?

Phép trừ như on_hand = on_hand - quantity tránh ghi đè một giá trị cũ, nhưng cần thêm predicate đủ hàng và CHECK constraints để ngăn số âm.

### Vì sao cần cả conditional UPDATE và CHECK?

Conditional UPDATE trả lời nghiệp vụ đủ hàng hay không. CHECK là lớp bảo vệ cuối chống mọi code path ghi trạng thái vi phạm invariant.

### READ COMMITTED có đủ cho đặt hàng không?

Với một inventory row, conditional UPDATE có điều kiện thường đủ. Multi-row workflow cần transaction và lock ordering; invariant phức tạp hơn có thể cần explicit locks hoặc SERIALIZABLE.

### SELECT FOR UPDATE làm gì?

Nó khóa rows được chọn để transactions khác không thể cập nhật/xóa các rows đó cho đến khi transaction kết thúc.

### Khi nào dùng SKIP LOCKED?

Khi nhiều workers claim jobs từ một queue và có thể bỏ qua rows đang được worker khác xử lý.

### Deadlock có phải dữ liệu bị hỏng không?

Không nhất thiết. PostgreSQL abort một transaction để phá vòng chờ. Application cần xử lý và retry toàn transaction khi operation an toàn.

### Có nên retry insufficient stock không?

Không retry ngay như lỗi database. Đây là kết quả nghiệp vụ; trả response hết hàng hoặc chạy lại theo policy sau khi có stock mới.

### Tại sao cần idempotency key?

Để request retry sau timeout/mất response không tạo order hoặc inventory movement lần hai.

### Có nên giữ transaction trong khi gọi payment provider?

Không nên. Network calls có latency và failure không dự đoán được. Commit reservation trước, gọi provider ngoài transaction rồi finalize bằng transaction mới.

### Khi nào dùng reservation thay vì trừ on_hand ngay?

Khi cần giữ hàng trong lúc chờ thanh toán hoặc xác nhận đơn. Reservation cần expiration, consume và release transitions rõ.

### Hai order có thể cùng mua phần tồn kho còn lại không?

Có thể nếu tổng quantity không vượt available. Row locking sẽ tuần tự hóa cập nhật; conditional predicate quyết định transaction nào đủ điều kiện.

### Vì sao khóa product_id theo thứ tự tăng dần?

Để mọi transactions lấy locks cùng thứ tự, giảm khả năng tạo vòng chờ deadlock.

### SERIALIZABLE có loại bỏ mọi lỗi nghiệp vụ không?

Không. Nó phát hiện một số serialization anomalies và có thể abort transactions. Application vẫn cần constraints, validation, retry và state machine đúng.

### Làm sao biết Session nào đang chờ?

Dùng pg_stat_activity với wait_event_type = Lock, pg_locks và pg_blocking_pids().

### Inventory ledger có thay thế bảng inventory không?

Ledger lưu lịch sử movement; bảng inventory thường lưu balance hiện tại để truy vấn nhanh. Cần transaction ghi đồng thời và reconciliation để hai nguồn nhất quán.

### Backorder có phải tồn kho âm không?

Không nhất thiết. Backorder là cam kết cung cấp trong tương lai và nên được biểu diễn riêng với physical on_hand/reserved.

### Khi nào bài toán concurrency được xử lý đúng?

Khi các concurrent tests chứng minh số lượng không vượt stock policy, mọi order là all-or-nothing, retries không nhân đôi side effects và database invariants luôn đúng.

## 63. Tổng kết

Các câu lệnh cốt lõi:

~~~sql
-- Trừ kho nguyên tử, chỉ khi còn đủ hàng.
UPDATE shop.inventory
SET on_hand = on_hand - 4,
    updated_at = now()
WHERE warehouse_id = 10
  AND product_id = 1
  AND on_hand - reserved >= 4
RETURNING on_hand, reserved;

-- Giữ hàng để chờ thanh toán.
UPDATE shop.inventory
SET reserved = reserved + 2,
    updated_at = now()
WHERE warehouse_id = 10
  AND product_id = 1
  AND on_hand - reserved >= 2
RETURNING on_hand, reserved;

-- Khóa các inventory rows theo thứ tự ổn định.
SELECT product_id, on_hand, reserved
FROM shop.inventory
WHERE warehouse_id = 10
  AND product_id IN (1, 2, 3)
ORDER BY product_id
FOR UPDATE;

-- Đặt timeout trong transaction.
SET LOCAL lock_timeout = '2s';
SET LOCAL statement_timeout = '10s';

-- Kiểm tra các invariant.
SELECT *
FROM shop.inventory
WHERE on_hand < 0
   OR reserved < 0
   OR reserved > on_hand;

-- Quan sát các sessions đang chờ lock.
SELECT
    pid,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE wait_event_type = 'Lock';
~~~

Những nguyên tắc cần nhớ:

1. Race condition xuất hiện khi nhiều transactions đọc rồi quyết định trên cùng trạng thái cũ.
2. Lost update có thể làm kết quả ghi không phản ánh tổng tác động nghiệp vụ.
3. Đặt predicate đủ hàng trong cùng conditional UPDATE với phép trừ.
4. Dùng CHECK constraints để bảo vệ on_hand và reserved.
5. Tạo order, order_items và inventory changes trong cùng transaction.
6. Multi-item order phải all-or-nothing.
7. Aggregate các dòng trùng product trước khi khóa hoặc cập nhật.
8. Khóa nhiều inventory rows theo thứ tự ổn định.
9. Dùng idempotency key để request retry không tạo side effects lần hai.
10. Reservation tách hàng thực có khỏi hàng đang được giữ.
11. Consume/release reservation phải là state transition chỉ xảy ra một lần.
12. Không giữ transaction locks khi gọi payment/network services.
13. READ COMMITTED kết hợp conditional UPDATE phù hợp với nhiều inventory operations.
14. REPEATABLE READ/SERIALIZABLE có thể abort transaction và cần retry toàn bộ.
15. Deadlock cần được giảm bằng lock ordering và xử lý bằng retry có giới hạn.
16. SKIP LOCKED hữu ích cho queue workers nhưng cần theo dõi backlog.
17. Inventory ledger giúp giải thích thay đổi và đối soát balances.
18. Monitoring locks và wait events giúp tìm contention.
19. Test nhiều sessions là cách chứng minh concurrency behavior.
20. Kết quả cuối phải thỏa inventory invariants và order state machine.

          |

          |
       +--+--+
       |     |
      No    Yes
       |     |
       v     v
    Rollback Update inventory/reservations
             |

             |

**Kết luận:** bảo vệ tồn kho là bài toán transaction và concurrency. PostgreSQL cung cấp row locks, conditional UPDATE, constraints và isolation levels để đảm bảo nhiều requests cùng chạy vẫn không phá invariant. Thiết kế cần kết hợp các cơ chế này với order state machine, idempotency và reservation lifecycle; sau đó chứng minh bằng nhiều sessions và kiểm tra trạng thái cuối trong database.
