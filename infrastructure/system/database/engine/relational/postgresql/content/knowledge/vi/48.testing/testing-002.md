# Dữ liệu mẫu, seed và khả năng tái lập trong PostgreSQL

Kiểm thử database chỉ có giá trị khi dữ liệu đầu vào đủ đại diện, có thể tạo lại và không phụ thuộc vào trạng thái còn sót lại từ lần chạy trước. Trong PostgreSQL, **test data** là dữ liệu phục vụ kiểm thử; **fixture** là tập dữ liệu nhỏ có cấu trúc và kết quả mong đợi đã biết; **seed** là quá trình nạp dữ liệu ban đầu vào môi trường; còn **reproducibility** là khả năng tái tạo cùng điều kiện và cùng kết quả kiểm thử khi chạy lại.

Một bộ seed tốt cần trả lời được các câu hỏi:

- Dữ liệu được tạo từ nguồn nào và có được phép dùng trong test không?
- Mỗi lần chạy có tạo cùng một baseline không?
- Script có chạy lại an toàn không?
- Quan hệ khóa ngoại và sequence có nhất quán không?
- Các test chạy song song có ảnh hưởng lẫn nhau không?
- Thời gian, timezone, locale, collation và random values có ổn định không?
- Khi test thất bại, có thể tái tạo đúng dữ liệu và trạng thái đã gây lỗi không?

Bài **“Dữ liệu mẫu, seed và khả năng tái lập”**, thuộc chương **Kiểm thử** của module **Database Engine Relational PostgreSQL**, trình bày cách thiết kế fixture, seed scripts có thể lặp lại, tạo dữ liệu tổng hợp, kiểm soát random values, quản lý identity/sequence, cô lập test, chuẩn bị dữ liệu CI và ghi lại điều kiện để tái hiện lỗi.

> **Nguyên tắc:** một test phải có thể tạo ra dữ liệu đầu vào mà nó cần, không dựa vào thứ tự chạy test hoặc dữ liệu còn sót lại. Seed nên có phiên bản, có thể chạy lặp lại theo chủ đích, và có thể tái tạo trên một database sạch.

---

## 1. Dữ liệu mẫu trong kiểm thử database

Dữ liệu mẫu là dữ liệu được tạo hoặc chọn để kiểm tra behavior của schema, SQL queries, constraints, transactions, stored procedures và ứng dụng.

Ví dụ một hệ thống bán hàng có thể cần customer và địa chỉ, product và category, order và order items, payment và shipment, trạng thái đơn hàng, cùng các trường hợp thiếu dữ liệu, dữ liệu biên và dữ liệu không hợp lệ.

Dữ liệu test không nhất thiết phải lớn. Một fixture nhỏ có thể kiểm tra logic join, aggregation và constraints dễ hiểu hơn một bản sao production hàng triệu rows.

## 2. Fixture, seed và test data khác nhau thế nào?

| Khái niệm | Mục đích | Ví dụ |
|---|---|---|
| Fixture | Mô tả tập dữ liệu đã biết cho một test | 3 customers và 4 orders |
| Seed | Nạp dữ liệu ban đầu cho môi trường | Countries, roles, product catalog |
| Synthetic data | Dữ liệu giả được sinh theo quy tắc | 100.000 orders giả lập |
| Anonymized data | Dữ liệu nguồn đã được xử lý để giảm khả năng nhận diện | Bản sao đã masking |
| Snapshot | Trạng thái database được lưu tại một thời điểm | Database template hoặc dump |

Các khái niệm có thể giao nhau. Seed có thể nạp fixture; fixture có thể được tạo bằng synthetic data; snapshot có thể là cách phân phối một baseline.

## 3. Vì sao cần dữ liệu có thể tái lập?

Nếu mỗi lần chạy test có dữ liệu khác nhau, lỗi có thể xuất hiện ngẫu nhiên và khó tái hiện.

Tính tái lập giúp so sánh kết quả giữa các lần chạy, phát hiện regression, tái hiện bug từ CI, chạy test song song có kiểm soát, xác định thay đổi do code hay do dữ liệu, debug query plans và đảm bảo migration không làm mất dữ liệu quan trọng.

Một lỗi chỉ xảy ra với tập dữ liệu ngẫu nhiên nhưng không lưu seed, generator version và test parameters sẽ khó điều tra.

## 4. Phân loại dữ liệu kiểm thử

Một test suite thường cần nhiều loại dữ liệu:

1. **Reference data:** quốc gia, đơn vị tiền tệ, trạng thái cố định.
2. **Baseline fixtures:** records nhỏ để kiểm tra logic nghiệp vụ.
3. **Boundary data:** giá trị min/max, empty, NULL và giới hạn.
4. **Negative data:** dữ liệu vi phạm constraints để xác minh lỗi.
5. **Volume data:** dữ liệu lớn để đo hiệu năng.
6. **Concurrency data:** nhiều sessions cùng đọc/ghi.
7. **Historical data:** timestamps và trạng thái qua nhiều giai đoạn.
8. **Migration data:** dữ liệu đại diện cho schema/version cũ.

Không nên dùng một seed duy nhất cho mọi mục đích nếu các test có yêu cầu khác nhau.

## 5. Thiết kế fixture theo business scenario

Fixture nên mô tả tình huống nghiệp vụ, không chỉ là một danh sách rows. Ví dụ: customer mới chưa có order; customer có order đã thanh toán; order có nhiều items; order bị hủy trước khi thanh toán; payment thất bại rồi retry thành công; product hết hàng; order chứa discount và tax; hai transactions cùng cập nhật inventory.

Một fixture có tên rõ ràng giúp người đọc hiểu tại sao dữ liệu tồn tại và test nào sử dụng nó.

## 6. Fixture nhỏ và dễ đọc

Ví dụ schema đơn giản:

~~~sql
CREATE SCHEMA IF NOT EXISTS app;

CREATE TABLE IF NOT EXISTS app.customer (
    customer_id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_key text NOT NULL UNIQUE,
    display_name text NOT NULL,
    created_at timestamptz NOT NULL
);

CREATE TABLE IF NOT EXISTS app.orders (
    order_id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id bigint NOT NULL
        REFERENCES app.customer(customer_id),
    status text NOT NULL,
    total_amount numeric(12, 2) NOT NULL CHECK (total_amount >= 0),
    created_at timestamptz NOT NULL
);
~~~

Fixture có thể dùng IDs cố định:

~~~sql
INSERT INTO app.customer
    (customer_id, customer_key, display_name, created_at)
VALUES
    (101, 'cust-alice', 'Alice Test', '2025-01-10 09:00:00+00'),
    (102, 'cust-bob',   'Bob Test',   '2025-01-11 09:00:00+00');

INSERT INTO app.orders
    (order_id, customer_id, status, total_amount, created_at)
VALUES
    (1001, 101, 'paid',      125.50, '2025-01-12 10:00:00+00'),
    (1002, 101, 'cancelled',   0.00, '2025-01-13 10:00:00+00'),
    (1003, 102, 'pending',    49.99, '2025-01-14 10:00:00+00');
~~~

Dùng IDs cố định giúp assertions dễ đọc và không phụ thuộc vào sequence state. Sau khi insert explicit identity values, cần đồng bộ sequence nếu test tiếp tục insert rows bằng default identity.

## 7. Chọn khóa ổn định cho fixture

Có thể dùng natural key có unique constraint, UUID cố định được định nghĩa trong fixture, integer IDs cố định trong database test riêng hoặc composite key phản ánh business identity.

Tránh dựa vào thứ tự insert hoặc giả định row đầu tiên luôn có ID 1. ID sequence có thể thay đổi do test trước, rollback hoặc parallel workers.

## 8. Idempotent seed là gì?

Một seed idempotent có thể chạy lại mà không tạo duplicate hoặc làm trạng thái trở nên không xác định.

Ví dụ dùng unique natural key:

~~~sql
INSERT INTO app.customer
    (customer_key, display_name, created_at)
VALUES
    ('cust-alice', 'Alice Test', '2025-01-10 09:00:00+00')
ON CONFLICT (customer_key) DO NOTHING;
~~~

Chạy lại script không tạo thêm customer có cùng key.

Idempotent không nhất thiết có nghĩa chạy lại luôn reset dữ liệu về trạng thái ban đầu. Nếu test đã thay đổi row, DO NOTHING giữ thay đổi đó. Cần chọn behavior phù hợp với mục đích seed.

## 9. DO NOTHING và DO UPDATE

Hai cách xử lý conflict có semantics khác nhau.

| Cách | Kết quả khi key đã tồn tại | Phù hợp khi |
|---|---|---|
| DO NOTHING | Giữ nguyên row hiện tại | Seed reference data, không ghi đè |
| DO UPDATE | Đưa các cột được chỉ định về baseline | Muốn seed-owned fields được đồng bộ |
| Delete rồi insert | Thay mới row, có thể ảnh hưởng FK | Chỉ dùng trong database test cô lập |
| TRUNCATE rồi seed | Xóa toàn bộ dữ liệu trong phạm vi | Reset environment chuyên dụng |

Ví dụ upsert:

~~~sql
INSERT INTO app.customer
    (customer_key, display_name, created_at)
VALUES
    ('cust-alice', 'Alice Test', '2025-01-10 09:00:00+00')
ON CONFLICT (customer_key)
DO UPDATE SET
    display_name = EXCLUDED.display_name,
    created_at = EXCLUDED.created_at;
~~~

Chỉ update các cột do seed quản lý. Nếu update cả trạng thái nghiệp vụ, có thể vô tình xóa dấu vết mà test cần kiểm tra.

## 10. Tách baseline data và mutable test data

Reference data như country codes hoặc status definitions thường ổn định. Dữ liệu nghiệp vụ trong test thường bị thay đổi.

Nên phân biệt baseline seed, per-test fixture, generated workload và test output. Không dùng cùng một row mutable cho nhiều test nếu chúng có thể chạy song song hoặc thay đổi trạng thái của nhau.

## 11. Seed có version

Khi seed thay đổi theo thời gian, ghi nhận version hoặc checksum để biết database test đang dùng baseline nào.

~~~sql
CREATE SCHEMA IF NOT EXISTS test_support;

CREATE TABLE IF NOT EXISTS test_support.seed_version (
    seed_name text PRIMARY KEY,
    version integer NOT NULL,
    applied_at timestamptz NOT NULL
);

INSERT INTO test_support.seed_version
    (seed_name, version, applied_at)
VALUES
    ('core-fixtures', 3, '2025-02-01 00:00:00+00')
ON CONFLICT (seed_name)
DO UPDATE SET
    version = EXCLUDED.version,
    applied_at = EXCLUDED.applied_at;
~~~

Trong dự án thực tế, seed version nên được quản lý bởi migration/seed runner để không vô tình đánh dấu version đã chạy khi một phần script thất bại.

## 12. Chạy seed trong transaction

Một seed SQL thuần thường nên chạy trong transaction để nếu có lỗi thì dữ liệu seed không bị áp dụng một phần.

~~~sql
BEGIN;

INSERT INTO app.customer
    (customer_key, display_name, created_at)
VALUES
    ('cust-alice', 'Alice Test', '2025-01-10 09:00:00+00')
ON CONFLICT (customer_key) DO NOTHING;

INSERT INTO app.orders
    (order_id, customer_id, status, total_amount, created_at)
SELECT
    1001,
    customer_id,
    'paid',
    125.50,
    '2025-01-12 10:00:00+00'
FROM app.customer
WHERE customer_key = 'cust-alice'
ON CONFLICT (order_id) DO NOTHING;

COMMIT;
~~~

Nếu statement thất bại, transaction có thể rollback toàn bộ phần seed đã thực hiện.

Một số lệnh không chạy được trong transaction block, ví dụ CREATE DATABASE, VACUUM và CREATE INDEX CONCURRENTLY. Giữ các thao tác đó ở bước setup riêng.

## 13. Thứ tự nạp dữ liệu theo foreign keys

Nếu table con tham chiếu table cha, cần nạp parent trước child.

~~~text
country
   |
   v
customer
   |
   v
orders
   |
   v
order_item
   |
   v
payment
~~~

Thứ tự seed cần tôn trọng dependency graph. Nếu có quan hệ vòng, xem xét thiết kế constraints deferrable, tạo records theo workflow phù hợp hoặc tách bước cập nhật foreign key sau insert.

Không vô hiệu hóa constraints chỉ để seed chạy dễ hơn; điều đó có thể che giấu lỗi dữ liệu.

## 14. Foreign keys và deferrable constraints

Một số schema cho phép kiểm tra foreign key vào cuối transaction:

~~~sql
ALTER TABLE app.child
ADD CONSTRAINT child_parent_fk
FOREIGN KEY (parent_id)
REFERENCES app.parent(parent_id)
DEFERRABLE INITIALLY DEFERRED;
~~~

Khi đó, transaction có thể insert các rows theo thứ tự khác nhau nếu mọi references hợp lệ lúc commit.

Chỉ dùng DEFERRABLE khi semantics nghiệp vụ cho phép. Nó không phải giải pháp mặc định cho mọi fixture.

## 15. Cleanup bằng TRUNCATE

Trong một database test cô lập, có thể reset bảng:

~~~sql
TRUNCATE TABLE
    app.order_item,
    app.payment,
    app.orders,
    app.customer
RESTART IDENTITY;
~~~

TRUNCATE nhanh hơn delete nhiều rows, có thể reset owned sequences với RESTART IDENTITY, nhưng lấy lock mạnh và không chạy row-level DELETE triggers.

Nếu dùng CASCADE, PostgreSQL có thể truncate thêm các tables tham chiếu. Chỉ sử dụng khi đã hiểu toàn bộ phạm vi.

Không chạy reset command này trên database dùng chung hoặc production.

## 16. Cleanup bằng DELETE

DELETE phù hợp khi cần chạy triggers hoặc chỉ xóa records thuộc fixture:

~~~sql
DELETE FROM app.orders
WHERE customer_id IN (
    SELECT customer_id
    FROM app.customer
    WHERE customer_key LIKE 'test-%'
);
~~~

Xóa child rows trước parent rows nếu foreign keys không cascade. Cleanup phải có predicate chính xác và không được xóa dữ liệu của test khác.

## 17. Transaction rollback để cô lập test

Một pattern phổ biến là chạy test trong transaction rồi rollback:

~~~sql
BEGIN;

INSERT INTO app.customer
    (customer_key, display_name, created_at)
VALUES
    ('test-one', 'Test One', now());

-- Assertions and test operations.

ROLLBACK;
~~~

Cách này phù hợp với test chạy tuần tự trên cùng connection và không cần quan sát kết quả từ session khác.

Nhưng không phải mọi thứ đều rollback: sequence values từ nextval() không được trả lại; một số external side effects và actions bên ngoài database cũng không được hoàn tác. Các test cần nhiều connections hoặc commit thật có thể cần database/schema riêng.

## 18. Sequence và identity columns

Identity column dùng sequence để sinh giá trị.

~~~sql
CREATE TABLE app.ticket (
    ticket_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title text NOT NULL
);
~~~

Với GENERATED ALWAYS, explicit value thường bị từ chối trừ khi dùng OVERRIDING SYSTEM VALUE. Với GENERATED BY DEFAULT, caller có thể cung cấp explicit value.

Khi seed IDs cố định, phải đảm bảo sequence tiếp tục từ giá trị phù hợp để insert sau đó không đụng primary key.

## 19. Đồng bộ sequence sau explicit IDs

Có thể lấy sequence gắn với cột bằng pg_get_serial_sequence():

~~~sql
SELECT setval(
    pg_get_serial_sequence('app.customer', 'customer_id')::regclass,
    COALESCE((SELECT max(customer_id) FROM app.customer), 1),
    EXISTS (SELECT 1 FROM app.customer)
);
~~~

Tham số thứ ba cho biết giá trị đã được gọi hay chưa. Nếu bảng rỗng, is_called = false để lần nextval() tiếp theo trả về giá trị đã đặt. Nếu bảng có rows, is_called = true để lần tiếp theo tăng theo sequence increment.

setval() và nextval() có semantics không rollback như thay đổi bảng thông thường. Đừng dựa vào transaction rollback để đưa sequence về đúng trạng thái cũ.

## 20. Tránh phụ thuộc vào sequence hiện tại

Test không nên giả định last_value của sequence là một giá trị cố định. Sequence có thể tăng do test khác, rollback, cache hoặc concurrent sessions.

Nếu cần xác định row, hãy query bằng natural key hoặc fixture ID đã biết. Nếu cần kiểm tra behavior của sequence, tạo test riêng với sequence riêng và assertions phù hợp.

## 21. Dữ liệu sinh bằng generate_series

PostgreSQL có generate_series() để tạo nhiều rows mà không cần vòng lặp ở application.

~~~sql
INSERT INTO app.metric_sample
    (sample_id, metric_value, recorded_at)
SELECT
    n,
    (n::numeric * 7919 % 100000) / 100.0,
    timestamptz '2025-01-01 00:00:00+00'
        + n * interval '1 minute'
FROM generate_series(1, 10000) AS g(n);
~~~

Công thức tạo giá trị theo n nên deterministic: cùng range đầu vào sẽ tạo cùng values. Chọn kiểu dữ liệu và phép toán để tránh integer overflow.

Dùng generate_series() cho volume tests, partitioning, index tests và time-series workloads.

## 22. Tạo dữ liệu tổng hợp có cấu trúc

Dữ liệu volume không nên chỉ lặp lại một giá trị. Query planner và index behavior phụ thuộc phân phối dữ liệu.

Có thể tạo phân phối uniform, skewed, sparse, time-correlated, high-cardinality, NULL-heavy và boundary-heavy.

Ví dụ phân phối đơn giản:

~~~sql
INSERT INTO app.event_log
    (event_id, tenant_id, event_type, occurred_at)
SELECT
    n,
    CASE
        WHEN n % 10 = 0 THEN 1
        ELSE 2 + (n % 500)
    END,
    CASE
        WHEN n % 20 = 0 THEN 'payment'
        WHEN n % 5 = 0 THEN 'login'
        ELSE 'view'
    END,
    timestamptz '2025-01-01 00:00:00+00'
        + n * interval '1 second'
FROM generate_series(1, 100000) AS g(n);
~~~

Dữ liệu này tạo tenant 1 có tỷ trọng cao hơn các tenant khác để kiểm tra skew.

## 23. Random data và setseed()

PostgreSQL cung cấp random() để tạo pseudo-random values. Có thể đặt seed cho PRNG của session bằng setseed():

~~~sql
SELECT setseed(0.42);

SELECT random()
FROM generate_series(1, 5);
~~~

Với cùng PostgreSQL implementation, cùng seed và cùng thứ tự gọi trong một session, chuỗi kết quả có thể được tái tạo.

Tuy nhiên, không nên coi chuỗi random() là contract ổn định xuyên mọi major versions, implementations hoặc thay đổi thứ tự thực thi query. Parallelism và việc gọi random ở các vị trí khác nhau có thể làm sequence values thay đổi.

## 24. Khi nào không nên dùng random() cho fixture?

Không dùng random values khi test cần expected result cố định, ví dụ tổng tiền phải bằng một con số cụ thể, một customer phải có đúng ba orders, một row phải nằm trong partition cụ thể, query phải trả đúng nhóm records hoặc bug cần tái hiện chính xác.

Trong những trường hợp đó, dùng values được định nghĩa rõ hoặc generator deterministic theo input key.

Random data phù hợp hơn cho fuzzing, property-based tests hoặc load tests khi lưu lại seed và parameters để tái hiện.

## 25. Deterministic pseudo-random values

Có thể tạo variation từ một key bằng hàm hash deterministic như md5() thay vì dựa vào trạng thái PRNG session.

Ví dụ lấy bucket từ hai ký tự hex đầu của hash:

~~~sql
SELECT
    n,
    get_byte(
        decode(substr(md5('tenant:' || n::text), 1, 2), 'hex'),
        0
    ) AS bucket
FROM generate_series(1, 10) AS g(n);
~~~

Cùng input key sẽ tạo cùng bucket. Dùng bucket để chọn category hoặc tỷ lệ phân phối.

Hash không phải nguồn random mật mã. Không dùng cách này để sinh passwords, tokens hoặc secrets.

## 26. Lưu seed và generator version

Nếu test dùng random/fuzzing, log tối thiểu seed value, generator version/commit, PostgreSQL version, test name, parameters và dataset size, worker count/parallelism, timezone và locale, cùng environment variables liên quan.

Seed number một mình có thể chưa đủ nếu generator code hoặc call order thay đổi.

Khi test thất bại, lưu minimized failing input nếu framework hỗ trợ.

## 27. UUID và reproducibility

UUID ngẫu nhiên như gen_random_uuid() tạo ID mới ở mỗi lần gọi. Điều đó phù hợp khi uniqueness là yêu cầu, nhưng không phù hợp nếu test cần ID cố định để so sánh kết quả.

Với fixtures, có thể dùng UUID literal đã định nghĩa:

~~~sql
INSERT INTO app.customer (customer_id, customer_key, display_name)
VALUES
(
    '11111111-1111-4111-8111-111111111111',
    'cust-alice',
    'Alice Test'
);
~~~

Nếu cần UUID xác định từ namespace và name, có thể dùng UUID v5 qua extension hỗ trợ, nhưng cần quản lý package/version dependency. Không tạo IDs dựa vào random nếu assertion cần giá trị ổn định.

## 28. Timestamp và timezone

Dữ liệu thời gian là nguồn gây flaky tests phổ biến.

Nên dùng timestamptz cho thời điểm tuyệt đối và ghi literal có timezone rõ ràng:

~~~sql
INSERT INTO app.audit_event (event_time)
VALUES ('2025-03-08 10:00:00+00');
~~~

Đặt timezone test rõ ràng:

~~~sql
SET TIME ZONE 'UTC';
~~~

Tránh dựa vào now() nếu expected result phụ thuộc thời điểm chạy. now()/CURRENT_TIMESTAMP trong PostgreSQL trả về transaction start time, còn clock_timestamp() thay đổi theo thời gian thực.

## 29. Freeze time trong test

Có thể truyền timestamp cố định vào application hoặc function thay vì để code tự đọc clock.

Ví dụ function nhận thời điểm tham chiếu:

~~~sql
CREATE OR REPLACE FUNCTION app.is_expired(
    p_expires_at timestamptz,
    p_as_of timestamptz
)
RETURNS boolean
LANGUAGE sql
IMMUTABLE
AS $$
    SELECT p_expires_at <= p_as_of;
$$;
~~~

Test:

~~~sql
SELECT app.is_expired(
    '2025-01-01 00:00:00+00',
    '2025-01-02 00:00:00+00'
);
~~~

Inject clock/reference time giúp test boundary conditions và tránh phụ thuộc wall clock.

## 30. DateStyle, timezone và locale

Session settings có thể ảnh hưởng parsing và formatting.

~~~sql
SET DateStyle = 'ISO, YMD';
SET TIME ZONE 'UTC';
~~~

Tránh nhập ngày dạng mơ hồ như 01/02/2025. Dùng ISO format và timezone tường minh.

Locale, collation và ICU/libc versions có thể ảnh hưởng sort order, case conversion và comparison. Một test dựa vào thứ tự text phải xác định collation environment.

## 31. Collation và thứ tự kết quả

SQL không đảm bảo thứ tự rows nếu query không có ORDER BY.

Không viết test:

~~~sql
SELECT customer_key
FROM app.customer;
~~~

rồi giả định row đầu tiên luôn là Alice.

Viết rõ:

~~~sql
SELECT customer_key
FROM app.customer
ORDER BY customer_key;
~~~

Nếu thứ tự phụ thuộc locale/collation, khai báo collation phù hợp hoặc so sánh kết quả theo tập hợp khi thứ tự không phải behavior cần kiểm tra.

## 32. Numeric và floating-point

Với tiền tệ và giá trị cần so sánh chính xác, dùng numeric(p,s) thay vì real/double precision nếu semantics nghiệp vụ yêu cầu decimal exactness.

Ví dụ:

~~~sql
CREATE TABLE app.invoice (
    invoice_id bigint PRIMARY KEY,
    amount numeric(12, 2) NOT NULL
);
~~~

Floating-point dùng biểu diễn nhị phân gần đúng. Test nên dùng tolerance khi kiểm tra kết quả floating-point, hoặc dùng numeric cho các phép tính tài chính.

## 33. NULL, empty string và boundary values

Fixture cần phân biệt NULL, chuỗi rỗng, chuỗi có whitespace, số 0, boolean false, ngày ở biên tháng/năm, giá trị ngay dưới/bằng/trên giới hạn, Unicode và chuỗi dài, duplicate keys và missing references.

Đừng chỉ seed dữ liệu “đẹp”. Negative và boundary fixtures giúp kiểm tra constraints, validation và error handling.

## 34. Kiểm thử constraints bằng negative fixtures

Một test có thể xác minh database từ chối dữ liệu không hợp lệ:

~~~sql
INSERT INTO app.orders
    (customer_id, status, total_amount, created_at)
VALUES
    (999999, 'paid', 10.00, now());
~~~

Nếu customer không tồn tại, foreign key phải từ chối insert.

Có thể dùng PL/pgSQL exception block trong test:

~~~sql
DO $$
BEGIN
    BEGIN
        INSERT INTO app.orders
            (customer_id, status, total_amount, created_at)
        VALUES
            (999999, 'paid', 10.00, now());

        RAISE EXCEPTION 'Expected foreign key violation';
    EXCEPTION
        WHEN foreign_key_violation THEN
            RAISE NOTICE 'Expected error observed';
    END;
END;
$$;
~~~

Đảm bảo exception handler chỉ bắt lỗi mong đợi; nếu code có thể ném lỗi khác, test phải phát hiện.

## 35. Seed dữ liệu lớn và ANALYZE

Sau khi nạp nhiều rows, planner statistics có thể chưa phản ánh phân phối mới.

Chạy:

~~~sql
ANALYZE app.event_log;
~~~

Với nhiều bảng:

~~~sql
ANALYZE;
~~~

Sau đó dùng EXPLAIN hoặc EXPLAIN (ANALYZE, BUFFERS) trên query test.

Nếu test performance phụ thuộc statistics, seed process phải quy định rõ khi nào chạy ANALYZE và có dùng autovacuum hay không.

## 36. Bulk loading bằng COPY

Với fixture lớn, COPY thường hiệu quả hơn nhiều lệnh INSERT riêng lẻ.

Ví dụ client-side bằng psql:

~~~text
psql meta-command: copy app.customer(customer_key, display_name, created_at) from customers.csv using CSV format with header
~~~

Meta-command copy của psql đọc file từ máy chạy psql. SQL COPY FROM với filename truy cập file trên server và có yêu cầu quyền khác.

Đối với test automation, kiểm soát encoding, delimiter, header, NULL representation và file path để seed có kết quả ổn định.

## 37. Dữ liệu phụ thuộc vào thứ tự nạp

Khi dùng CSV hoặc nhiều seed files, ghi rõ dependency order và format contract.

Ví dụ: reference data, customers, products, orders, order items, payments.

Nếu IDs được sinh tự động, mapping giữa parent/child cần được xác định ổn định. Tránh phụ thuộc vào thứ tự row trong file nếu không có explicit key.

## 38. Test data và migrations

Schema migration và data seed có vòng đời khác nhau.

- Migration thay đổi schema hoặc dữ liệu theo phiên bản ứng dụng.
- Seed tạo baseline/reference/test data.
- Fixture tạo dữ liệu cho một test case.
- Production reference data có thể được quản lý như migration nếu cần versioning.

Không đưa hàng triệu rows benchmark vào migration production. Không đặt test-only fixture vào schema production nếu không có lý do và kiểm soát rõ.

## 39. Seed sau migration

Một workflow phổ biến:

~~~text
Create empty test database
          |
          v
Apply schema migrations
          |
          v
Install required extensions
          |
          v
Load baseline seed
          |
          v
Create per-test fixtures
          |
          v
Run tests
          |
          v
Cleanup / discard database
~~~

Test phải chạy trên schema được tạo bởi migrations hiện tại, không dựa vào một dump cũ có thể lệch schema.

## 40. Test database riêng

Cách an toàn và dễ tái lập là tạo database riêng cho mỗi test run hoặc worker.

Ví dụ:

~~~bash
createdb app_test_001
psql -X -v ON_ERROR_STOP=1 -d app_test_001 -f schema.sql
psql -X -v ON_ERROR_STOP=1 -d app_test_001 -f seed.sql
~~~

Tên database nên bao gồm build/run/worker identifier để tránh collisions. Cleanup database sau test chỉ khi chắc chắn database thuộc run đó.

Không dùng chung database test với developer khác hoặc service có dữ liệu quan trọng.

## 41. Dùng schema riêng cho test

Nếu tạo database mới quá tốn kém, có thể tạo schema riêng cho từng test worker và cấu hình search_path.

~~~sql
CREATE SCHEMA test_worker_01;
SET search_path TO test_worker_01, public;
~~~

Tuy nhiên, schema isolation không hoàn toàn tương đương database isolation: extensions, database-level objects, shared sequences, advisory locks và một số catalog/settings vẫn ở phạm vi database.

Tránh để test workers dùng chung mutable tables hoặc objects.

## 42. Parallel tests và collisions

Các test chạy song song có thể va chạm nếu dùng chung primary keys cố định, unique natural keys, shared rows, sequence reset, temporary object names, advisory lock keys, global configuration hoặc external service identifiers.

Giải pháp gồm database/schema riêng mỗi worker, namespace prefix cho fixture keys, transaction isolation phù hợp, deterministic ID space theo worker, cleanup có ownership và không reset sequence dùng chung khi worker khác đang chạy.

## 43. Temporary tables

Temporary table thuộc session hiện tại:

~~~sql
CREATE TEMP TABLE test_result (
    item_id bigint,
    result text
) ON COMMIT DROP;
~~~

Nó hữu ích cho dữ liệu trung gian của test và tự biến mất khi session kết thúc.

Nhưng temporary tables không thay thế fixtures cần được truy cập từ nhiều connections. Nếu application mở connection pool, mỗi connection có temporary table riêng.

## 44. Transaction isolation và test concurrency

PostgreSQL mặc định dùng READ COMMITTED. Test concurrency cần chỉ rõ isolation level nếu đang kiểm tra behavior phụ thuộc snapshot hoặc serialization.

Ví dụ:

~~~sql
BEGIN ISOLATION LEVEL REPEATABLE READ;

SELECT balance
FROM app.account
WHERE account_id = 1;

COMMIT;
~~~

Với test SERIALIZABLE, cần kiểm tra cả khả năng transaction bị abort do serialization failure và logic retry của ứng dụng.

Seed data phải tạo đúng preconditions để hai sessions cùng tranh chấp một row hoặc resource.

## 45. Test race conditions có thể tái hiện

Để tái hiện concurrency bug:

1. Dùng hai connections độc lập.
2. Nạp fixture có IDs và trạng thái cố định.
3. Điều khiển thứ tự statements bằng test barriers.
4. Ghi lại isolation level.
5. Ghi transaction boundaries.
6. Lưu SQL logs hoặc trace.
7. Xác minh final state.

Không dùng pg_sleep() làm synchronization chính nếu có thể dùng barrier trong test harness; sleep chỉ tạo timing gần đúng và dễ flaky.

## 46. Seed cho performance tests

Performance seed cần đại diện cho workload: row counts, data skew, index selectivity, foreign-key relationships, NULL ratios, hot keys, time distribution, update/delete ratios, partition sizes và concurrent clients.

Một bảng có 10 triệu rows nhưng mọi value giống nhau không đại diện cho production nếu production có cardinality và skew khác.

Ghi rõ generator parameters và dataset checksum.

## 47. Synthetic data và privacy

Synthetic data được sinh từ quy tắc hoặc generator, không sao chép trực tiếp thông tin cá nhân thật. Đây thường là lựa chọn tốt cho development và CI.

Nếu dùng production-derived data, cần phê duyệt theo policy, mask/anonymize identifiers và quasi-identifiers, loại bỏ credentials/tokens/secrets, bảo vệ free-text fields có thể chứa PII, kiểm tra khả năng re-identification, giới hạn quyền truy cập/retention và ghi rõ nguồn/quá trình xử lý.

Hash email hoặc số điện thoại không luôn đủ để anonymize vì không gian giá trị có thể đoán được.

## 48. Masking cần bảo toàn quan hệ

Khi anonymize dữ liệu có quan hệ:

- Cùng source identifier phải map thành cùng masked identifier.
- Foreign keys phải tiếp tục khớp.
- Unique constraints vẫn phải được bảo đảm.
- Referential integrity không bị phá.
- Distribution và skew quan trọng nên được giữ ở mức cần thiết.
- Thông tin nhạy cảm không được giữ trong logs hoặc CSV phụ.

Dùng deterministic mapping có secret key nếu cần tính nhất quán giữa nhiều datasets; quản lý key riêng và không commit vào repository.

## 49. Seed trong CI pipeline

Một pipeline điển hình:

~~~text
Start PostgreSQL service
          |
          v
Create isolated test database
          |
          v
Apply migrations
          |
          v
Install extensions
          |
          v
Load deterministic baseline
          |
          v
Run unit/integration tests
          |
          v
Collect logs and artifacts
~~~

Pin PostgreSQL image/tag, extension packages và locale. Không dùng latest nếu cần tái hiện cùng môi trường giữa các CI runs.

## 50. Docker và Testcontainers

Container giúp kiểm soát PostgreSQL major version, configuration và package set.

Khi dùng Docker/Testcontainers:

- Pin image tag hoặc digest.
- Cài extension packages trong image/build step.
- Chờ health/readiness, không chỉ chờ container process.
- Tạo database và roles riêng.
- Chạy migrations và seeds theo thứ tự.
- Expose logs khi test fail.
- Dùng volume tạm hoặc database disposable.
- Cleanup container và volume đúng ownership.

Nếu extension cần shared_preload_libraries, cấu hình trước khi PostgreSQL khởi động.

## 51. Snapshot và template database

PostgreSQL cho phép tạo database từ template:

~~~sql
CREATE DATABASE app_test_worker_01
WITH TEMPLATE app_test_template;
~~~

Template có thể được chuẩn bị sẵn schema, extensions và baseline fixtures để giảm thời gian setup.

Lưu ý:

- Không có active sessions trên template database khi copy theo các điều kiện PostgreSQL yêu cầu.
- Template phải được refresh khi migrations/seed thay đổi.
- Database clone là snapshot baseline tại thời điểm tạo.
- Mỗi test vẫn cần dữ liệu riêng và cleanup.
- Template không thay thế package inventory trên server.

Một template cũ có thể khiến test chạy trên schema hoặc seed không còn khớp source code.

## 52. pg_dump/pg_restore làm baseline snapshot

Có thể tạo custom-format dump từ database test đã chuẩn bị:

~~~bash
pg_dump -Fc -f test_baseline.dump app_test_template
~~~

Mỗi run restore vào database mới:

~~~bash
createdb app_test_run
pg_restore --dbname=app_test_run --exit-on-error test_baseline.dump
~~~

Cách này phù hợp khi baseline lớn và setup tốn thời gian. Tuy nhiên, phải version snapshot cùng migration/seed commit và extension package inventory.

## 53. Kiểm tra seed đã nạp đủ

Đừng chỉ kiểm tra exit code của seed script. Có thể thêm assertions:

~~~sql
DO $$
BEGIN
    IF (SELECT count(*) FROM app.customer) < 2 THEN
        RAISE EXCEPTION 'Customer fixture is incomplete';
    END IF;

    IF NOT EXISTS (
        SELECT 1
        FROM app.customer
        WHERE customer_key = 'cust-alice'
    ) THEN
        RAISE EXCEPTION 'Required customer fixture is missing';
    END IF;
END;
$$;
~~~

Assertions nên kiểm tra preconditions mà test suite thực sự cần, không hardcode tổng row count nếu seed được phép mở rộng.

## 54. Ghi lại môi trường để tái hiện bug

Khi test fail, lưu Git commit hoặc build identifier, PostgreSQL version và image digest, extension versions, schema migration version, seed version/checksum, random seed và generator version, database settings liên quan, timezone/locale/collation, test name và worker ID, SQL parameters hoặc minimized fixture, logs và error details đã loại secrets.

Nếu chỉ lưu stack trace mà không lưu data fixture và environment, việc tái hiện có thể thất bại.

## 55. Flaky tests do phụ thuộc trạng thái

Các nguyên nhân thường gặp:

- Test phụ thuộc test chạy trước.
- Seed chỉ chạy một lần trên database dùng chung.
- Sequence state không reset.
- now() làm expected values thay đổi.
- Query thiếu ORDER BY.
- Random values không được cố định.
- Parallel tests dùng chung rows.
- Cleanup bỏ sót dữ liệu.
- External service state không được reset.
- Locale/timezone khác giữa local và CI.

Giải quyết bằng isolation, explicit inputs, deterministic fixtures và evidence có thể tái tạo.

## 56. Các anti-pattern thường gặp

### 56.1. Dùng production dump làm test data mặc định

Có thể chứa dữ liệu nhạy cảm và làm test phụ thuộc vào snapshot không được version hóa.

### 56.2. Dùng một database chung cho mọi tests

Dễ gây race conditions, collisions và test order dependency.

### 56.3. Dùng random() mà không lưu seed

Không thể tái hiện chính xác failing case.

### 56.4. Dùng TRUNCATE CASCADE trên database dùng chung

Có thể xóa dữ liệu ngoài phạm vi test.

### 56.5. Giả định sequence rollback

Sequence values không được hoàn tác như row changes.

### 56.6. Không ANALYZE sau bulk seed

Planner có thể dùng statistics cũ hoặc thiếu.

### 56.7. Dựa vào thứ tự rows mặc định

Không có ORDER BY thì thứ tự không được bảo đảm.

### 56.8. Gộp migration và seed không phân biệt

Khó biết lỗi thuộc schema evolution hay test data setup.

### 56.9. Chỉ kiểm tra seed command exit code

Script có thể hoàn tất nhưng thiếu fixtures mà test cần.

### 56.10. Dùng dữ liệu giả nhưng format không thực tế

Query performance và application validation có thể không đại diện production.

## 57. Ví dụ workflow seed bằng psql

Một shell workflow đơn giản:

~~~bash
createdb app_test

psql -X \
  -v ON_ERROR_STOP=1 \
  -d app_test \
  -f db/schema.sql

psql -X \
  -v ON_ERROR_STOP=1 \
  -d app_test \
  -f db/seed/reference_data.sql

  -v ON_ERROR_STOP=1 \
~~~

Có thể dùng psql --single-transaction cho một nhóm scripts tương thích với transaction. Không dùng khi scripts chứa commands không được chạy trong transaction block.

## 58. Ví dụ seed deterministic hoàn chỉnh

~~~sql
BEGIN;

CREATE SCHEMA IF NOT EXISTS test_data;

CREATE TABLE IF NOT EXISTS test_data.customer (
    customer_id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_key text NOT NULL UNIQUE,
    display_name text NOT NULL,
    created_at timestamptz NOT NULL
);

CREATE TABLE IF NOT EXISTS test_data.orders (
    order_id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id bigint NOT NULL
        REFERENCES test_data.customer(customer_id),
    status text NOT NULL,
    total_amount numeric(12, 2) NOT NULL
        CHECK (total_amount >= 0),
    created_at timestamptz NOT NULL
);

INSERT INTO test_data.customer
    (customer_id, customer_key, display_name, created_at)
VALUES
    (101, 'cust-alice', 'Alice Test', '2025-01-10 09:00:00+00'),
    (102, 'cust-bob', 'Bob Test', '2025-01-11 09:00:00+00')
ON CONFLICT (customer_key) DO NOTHING;

INSERT INTO test_data.orders
    (order_id, customer_id, status, total_amount, created_at)
VALUES
    (
        1001,
        (SELECT customer_id
         FROM test_data.customer
         WHERE customer_key = 'cust-alice'),
        'paid',
        125.50,
        '2025-01-12 10:00:00+00'
    ),
    (
        1002,
        (SELECT customer_id
         FROM test_data.customer
         WHERE customer_key = 'cust-bob'),
        'pending',
        49.99,
        '2025-01-13 10:00:00+00'
    )
ON CONFLICT (order_id) DO NOTHING;

-- Explicit IDs require sequence synchronization before later generated inserts.
SELECT setval(
    pg_get_serial_sequence(
        'test_data.customer',
        'customer_id'
    )::regclass,
    COALESCE(
        (SELECT max(customer_id) FROM test_data.customer),
        1
    ),
    EXISTS (SELECT 1 FROM test_data.customer)
);

SELECT setval(
    pg_get_serial_sequence(
        'test_data.orders',
        'order_id'
    )::regclass,
    COALESCE(
        (SELECT max(order_id) FROM test_data.orders),
        1
    ),
    EXISTS (SELECT 1 FROM test_data.orders)
);

COMMIT;
~~~

Ví dụ dùng natural keys và explicit IDs để fixtures dễ nhận biết. Trong một hệ thống thật, seed script cần xử lý trường hợp key đã tồn tại nhưng ID khác, và cần quyết định rõ DO NOTHING hay DO UPDATE cho từng cột.

5. Chuyển sang namespace/database riêng.
6. Kiểm tra cleanup của từng worker.
7. Dừng một worker bất thường và xác minh worker còn lại không mất dữ liệu.
8. Ghi lại isolation strategy.

## 62. Checklist dữ liệu test có thể tái lập

**Nguồn và cấu trúc**

- Dataset được phân loại là fixture, seed, synthetic hay anonymized.
- Business scenarios và edge cases được mô tả.
- Natural keys hoặc IDs ổn định.
- Foreign-key order rõ.
- Sensitive data được loại bỏ/masking phù hợp.

**Seed lifecycle**

- Script được version control.
- Có policy cho DO NOTHING/DO UPDATE.
- Có transaction và error handling.
- Có cleanup/reset an toàn.
- Identity sequences được xử lý.
- Seed có thể chạy trên database sạch.

**Reproducibility**

- Random seed/generator version được ghi.
- Timestamps có timezone rõ.
- Time reference được cố định khi cần.
- Locale/collation và PostgreSQL image được pin.
- Query assertions có ORDER BY khi thứ tự quan trọng.
- Failing fixture và environment được lưu.

**Isolation và CI**

- Database/schema/namespace riêng cho worker.
- Parallel tests không dùng chung mutable state.
- Extension packages và migrations được chuẩn bị.
- CI logs có đủ evidence.
- Test database được cleanup theo ownership.
- Performance dataset có distribution đại diện.

## 63. Câu hỏi thường gặp

### Seed có giống migration không?

Không. Migration thay đổi schema hoặc dữ liệu theo phiên bản ứng dụng; seed nạp baseline/reference/test data. Hai quy trình có thể chạy trong cùng pipeline nhưng nên có mục đích và versioning riêng.

### Seed script có nhất thiết phải idempotent không?

Với baseline automation, thường nên có khả năng chạy lại an toàn. Tuy nhiên, DO NOTHING, DO UPDATE và reset strategy có behavior khác nhau; phải chọn theo mục tiêu.

### Có nên dùng fixed IDs trong fixture không?

Có thể dùng trong database test cô lập vì dễ đọc và assertion ổn định. Cần đồng bộ sequence sau explicit identity values và tránh collisions giữa workers dùng chung database.

### Vì sao sequence tăng sau ROLLBACK?

nextval() không được thiết kế để hoàn tác cùng transaction. Gaps trong sequence là bình thường và không thể dùng sequence value như số đếm transaction chính xác.

### setseed() có đảm bảo kết quả giống nhau ở mọi PostgreSQL version không?

Không nên dựa vào bảo đảm đó. Nó giúp tái tạo PRNG sequence trong cùng implementation và call order, nhưng không phải contract cross-version cho test fixtures.

### Có nên dùng random() cho mọi dữ liệu test không?

Không. Dữ liệu cần expected result cố định nên được khai báo rõ hoặc tạo deterministic từ key. Random phù hợp hơn với fuzzing/load tests khi lưu seed và generator details.

### TRUNCATE khác DELETE thế nào?

TRUNCATE nhanh, lấy lock mạnh, có thể reset identity và không chạy row-level DELETE triggers. DELETE xử lý từng row, có thể chạy triggers và hỗ trợ predicate.

### Vì sao không nên dùng chung database cho parallel tests?

Các workers có thể va chạm keys, sequences, rows và cleanup. Dùng database/schema riêng hoặc namespace isolation.

### Rollback transaction có dọn mọi thứ test tạo ra không?

Không. Sequence state không rollback như row changes; external side effects và actions ngoài transaction cũng không được hoàn tác.

### Vì sao cần ANALYZE sau seed lớn?

Planner cần statistics phù hợp với phân phối dữ liệu mới để chọn query plans có ý nghĩa.

### Có thể dùng production dump làm test fixture không?

Chỉ khi policy cho phép và dữ liệu đã được bảo vệ phù hợp. Synthetic data thường an toàn và dễ tái lập hơn. Nếu dùng anonymized data, vẫn cần đánh giá re-identification risk.

### Làm sao tái hiện một bug từ CI?

Lưu commit, PostgreSQL/image version, extensions, migration/seed version, random seed, timezone/locale, test parameters và fixture tối thiểu gây lỗi.

### Snapshot template có luôn mới nhất không?

Không. Template chỉ phản ánh schema và seed tại thời điểm tạo. Version snapshot cùng migration/seed commit và refresh khi baseline thay đổi.

### Khi nào dùng COPY thay vì INSERT?

Khi cần bulk load dataset lớn. Kiểm soát encoding, delimiter, NULL representation, file location và quyền server/client.

### Làm sao kiểm tra seed đầy đủ?

Thêm assertions cho required natural keys, row counts hoặc business invariants mà test phụ thuộc. Không chỉ dựa vào exit code của loader.

## 64. Tổng kết

Các câu lệnh và pattern quan trọng:

~~~sql
-- Tạo dữ liệu từ một range xác định.
INSERT INTO app.metric_sample (sample_id, metric_value)
SELECT
    n,
    (n::numeric * 7919 % 100000) / 100.0
FROM generate_series(1, 10000) AS g(n);

-- Seed idempotent theo natural key.
INSERT INTO app.customer (customer_key, display_name, created_at)
VALUES ('cust-alice', 'Alice Test', '2025-01-10 09:00:00+00')
ON CONFLICT (customer_key) DO NOTHING;

-- Đặt timezone rõ ràng trong session.
SET TIME ZONE 'UTC';

-- Đặt pseudo-random seed cho session.
SELECT setseed(0.42);

-- Đồng bộ identity/serial sequence sau explicit IDs.
SELECT setval(
    pg_get_serial_sequence('app.customer', 'customer_id')::regclass,
    COALESCE((SELECT max(customer_id) FROM app.customer), 1),
    EXISTS (SELECT 1 FROM app.customer)
);

-- Cập nhật planner statistics sau bulk seed.
ANALYZE app.metric_sample;
~~~

~~~bash
# Tạo database test riêng.
createdb app_test

# Chạy schema và seed với lỗi dừng ngay.
psql -X -v ON_ERROR_STOP=1 -d app_test -f db/schema.sql
psql -X -v ON_ERROR_STOP=1 -d app_test -f db/seed.sql

# Tạo baseline archive khi cần.
pg_dump -Fc -f test_baseline.dump app_test

# Restore baseline vào một database run riêng.
createdb app_test_run
pg_restore --dbname=app_test_run --exit-on-error test_baseline.dump
~~~

Những nguyên tắc cần nhớ:

1. Fixture mô tả dữ liệu cho test cụ thể; seed nạp baseline; synthetic data phục vụ volume và distribution tests.
2. Mỗi test phải khai báo preconditions và không phụ thuộc test chạy trước.
3. Dùng natural keys hoặc IDs ổn định để assertions dễ tái lập.
4. Seed idempotent cần policy rõ cho DO NOTHING, DO UPDATE và reset.
5. Chạy seed trong transaction khi scripts tương thích.
6. Nạp parent rows trước child rows hoặc dùng constraints deferrable có chủ đích.
7. TRUNCATE chỉ dùng trong database/schema được kiểm soát; hiểu lock, cascade và trigger behavior.
8. Sequence values không rollback cùng transaction; đồng bộ sequence sau explicit identity values.
9. generate_series() tạo volume data có thể tái lập; thiết kế distribution giống workload cần kiểm thử.
10. setseed() không phải contract cross-version; lưu generator version và call order.
11. Dùng deterministic mapping từ input key khi expected values phải ổn định.
12. Dùng timestamp có timezone rõ và inject reference time để tránh flaky tests.
13. Locale/collation và query ordering phải được xác định khi ảnh hưởng kết quả.
14. Dùng numeric cho decimal exactness; dùng tolerance với floating-point.
15. Kiểm tra NULL, empty, boundary và negative cases.
16. Chạy ANALYZE sau bulk loading khi test phụ thuộc planner statistics.
17. Dùng database/schema/namespace riêng cho parallel workers.
18. Phân biệt migration, seed, fixture và performance dataset.
19. Pin PostgreSQL image, extension packages, seed version và generator.
20. Chỉ dùng production-derived data khi được phép và đã xử lý privacy.
21. Lưu seed, environment và failing fixture để tái hiện lỗi.
22. Test CI phải có cleanup theo ownership và logs đủ để điều tra.
23. Snapshot/template cần được version cùng schema và seed commit.
24. Một test data setup tốt phải có thể chạy từ database sạch và cho kết quả xác định.

Sơ đồ seed và test lifecycle:

~~~text
             Empty test database
                     |
                     v
             Apply migrations
                     |
                     v
          Install required extensions
                     |
                     v
             Load baseline seed
                     |
                     v
          Create per-test fixtures
                     |
                     v
          Run isolated test cases
                     |
              +------+------+
              |             |
              v             v
           Passed         Failed
              |             |
              v             v
          Cleanup       Save seed, fixture,
          test state    environment and logs
              |             |
              +------+------+
                     |
                     v
            Reset/discard database
                     |
                     v
             Reproducible next run
~~~

**Kết luận:** dữ liệu mẫu và seed là một phần của thiết kế kiểm thử database. Muốn tái lập kết quả, cần version hóa fixture, tạo seed deterministic và idempotent, quản lý sequence/time/random state, cô lập các test chạy song song và ghi lại môi trường. Khi một test thất bại, bộ dữ liệu cùng điều kiện chạy phải đủ để tái tạo lỗi trên một database sạch.
