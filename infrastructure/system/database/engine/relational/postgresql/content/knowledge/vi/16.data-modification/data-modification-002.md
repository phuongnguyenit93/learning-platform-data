# Giá trị mặc định, cột identity và cột sinh tự động trong PostgreSQL

Khi thêm một bản ghi, ứng dụng không nhất thiết phải cung cấp mọi giá trị. PostgreSQL có thể tự điền **trạng thái ban đầu**, **thời điểm tạo**, **số lượng mặc định**, **mã định danh dạng số** hoặc **giá trị được tính từ các cột khác**. Tuy trông giống nhau ở chỗ “database tự tạo giá trị”, đây là những cơ chế khác nhau về cú pháp, thời điểm tính, khả năng cập nhật và quy tắc toàn vẹn dữ liệu.

Ví dụ, khi tạo một đơn hàng:

- `status` có thể mặc định là `'draft'`.
- `created_at` có thể nhận thời điểm bắt đầu transaction.
- `order_id` có thể lấy số tiếp theo từ một sequence qua cột **identity**.
- `line_total` có thể được tính từ `quantity * unit_price` bằng một **generated column**.

Ba khái niệm cốt lõi của bài học thuộc chương **Thay đổi dữ liệu** là:

1. **`DEFAULT`**: điền giá trị khi câu lệnh ghi không cung cấp giá trị cho cột hoặc yêu cầu `DEFAULT`.
2. **`GENERATED ... AS IDENTITY`**: tạo giá trị định danh bằng sequence, có hai chế độ quản lý dữ liệu nhập tường minh là `ALWAYS` và `BY DEFAULT`.
3. **Generated/computed column**: cột có giá trị phụ thuộc một biểu thức từ các cột của cùng hàng, chẳng hạn `quantity * unit_price`.

Bài này giải thích đầy đủ từng cơ chế, đưa ra các trường hợp `INSERT`, `UPDATE`, `RETURNING`, `OVERRIDING`, `ALTER TABLE`, `ON CONFLICT`, những vấn đề về `NULL`, thứ tự sequence, đồng thời và migration, cùng bài lab PostgreSQL có thể thực hành trên database thử nghiệm.

## 1. Bức tranh tổng quan: ba kiểu “tự điền” không giống nhau

| Cơ chế | Ví dụ khai báo | Khi nào PostgreSQL tính? | Có thể nhập giá trị trực tiếp? |
|---|---|---|---|
| Giá trị mặc định | `status TEXT DEFAULT 'draft'` | Khi INSERT dùng mặc định | Có, giá trị nhập thay DEFAULT |
| Giá trị mặc định bằng hàm | `created_at TIMESTAMPTZ DEFAULT now()` | Khi giá trị mặc định được dùng | Có |
| Identity BY DEFAULT | `id BIGINT GENERATED BY DEFAULT AS IDENTITY` | Khi không cung cấp ID | Có |
| Identity ALWAYS | `id BIGINT GENERATED ALWAYS AS IDENTITY` | Khi không cung cấp ID | INSERT thủ công cần cú pháp override thích hợp |
| Generated stored | `total NUMERIC GENERATED ALWAYS AS (qty * price) STORED` | Khi ghi/cập nhật hàng | Không tự đặt giá trị tùy ý |
| Generated virtual (phiên bản hỗ trợ) | `... GENERATED ALWAYS AS (...) VIRTUAL` | Khi đọc giá trị | Không tự đặt giá trị tùy ý |

Một điểm rất quan trọng: **identity column và generated computed column đều có từ `GENERATED` nhưng không cùng ý nghĩa**.

- Identity dùng sequence để sinh giá trị khi cần.
- Generated computed column phụ thuộc biểu thức theo dữ liệu của chính hàng.
- DEFAULT là giá trị hoặc biểu thức thay thế khi người ghi không cung cấp giá trị.

### 1.1. Cột nào cần cơ chế nào?

Hãy hỏi:

- “Giá trị ban đầu hợp lý nếu ứng dụng không gửi gì?” → `DEFAULT`.
- “Mỗi hàng cần một mã số được database cấp phát?” → `IDENTITY` kết hợp khóa duy nhất/khóa chính.
- “Giá trị này luôn được tính từ các cột khác trong cùng hàng?” → **Generated column** nếu biểu thức phù hợp và được PostgreSQL hỗ trợ.
- “Giá trị chỉ thay đổi khi có sự kiện từ service hoặc trigger?” → Có thể cần logic cập nhật riêng, không chỉ DEFAULT/generated column.

## 2. DEFAULT là gì?

`DEFAULT` xác định một biểu thức PostgreSQL dùng để tạo giá trị khi thao tác INSERT không cung cấp giá trị của cột đó.

~~~sql
CREATE TABLE customer_preferences (
    preference_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    newsletter_enabled BOOLEAN NOT NULL DEFAULT FALSE,
    preferred_language TEXT NOT NULL DEFAULT 'vi',
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
~~~

Nếu ghi:

~~~sql
INSERT INTO customer_preferences (preferred_language)
VALUES ('en')
RETURNING *;
~~~

PostgreSQL có thể tự điền:

- `preference_id` từ sequence của identity.
- `newsletter_enabled = false`.
- `preferred_language = 'en'` vì đã nhập cụ thể.
- `created_at` theo biểu thức mặc định.

### 2.1. DEFAULT không đồng nghĩa bắt buộc

~~~sql
CREATE TABLE defaults_only (
    nickname TEXT DEFAULT 'Khách',
    status TEXT DEFAULT 'new'
);
~~~

Hai cột vẫn cho phép `NULL` nếu không có `NOT NULL`.

Nếu nghiệp vụ cấm NULL:

~~~sql
CREATE TABLE defaults_not_null (
    nickname TEXT NOT NULL DEFAULT 'Khách',
    status TEXT NOT NULL DEFAULT 'new'
);
~~~

**DEFAULT** quyết định giá trị khi thiếu đầu vào. **NOT NULL** bảo vệ dữ liệu sau khi được xác định.

### 2.2. DEFAULT có thể là hằng hoặc biểu thức

~~~sql
CREATE TABLE default_examples (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    active BOOLEAN NOT NULL DEFAULT TRUE,
    retry_count INTEGER NOT NULL DEFAULT 0,
    category TEXT NOT NULL DEFAULT 'general',
    created_on DATE NOT NULL DEFAULT CURRENT_DATE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
~~~

Không nên coi `DEFAULT 'general'` là một kiểu “cột không đổi”. Người ghi vẫn có thể cung cấp giá trị khác:

~~~sql
INSERT INTO default_examples (
    active,
    retry_count,
    category
)
VALUES (FALSE, 3, 'custom');
~~~

Nếu chỉ một tập giá trị được phép, cần `CHECK`, foreign key hoặc mô hình dữ liệu thích hợp.

## 3. Giá trị mặc định được áp dụng khi nào?

Xem một bảng:

~~~sql
CREATE TABLE default_semantics (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    status TEXT DEFAULT 'draft',
    quantity INTEGER DEFAULT 1
);
~~~

### 3.1. Bỏ qua cột trong INSERT

~~~sql
INSERT INTO default_semantics (quantity)
VALUES (5)
RETURNING id, status, quantity;
~~~

Cột `status` nhận `'draft'`.

### 3.2. Ghi rõ DEFAULT

~~~sql
INSERT INTO default_semantics (status, quantity)
VALUES (DEFAULT, DEFAULT)
RETURNING id, status, quantity;
~~~

Cả hai cột dùng mặc định tương ứng.

### 3.3. Gửi NULL tường minh

~~~sql
INSERT INTO default_semantics (status, quantity)
VALUES (NULL, NULL)
RETURNING id, status, quantity;
~~~

Khi các cột không có `NOT NULL`, hai giá trị được lưu là NULL. **PostgreSQL không tự thay NULL tường minh bằng DEFAULT**.

| Dữ liệu trong INSERT | `status DEFAULT 'draft'` nhận gì? |
|---|---|
| Không ghi cột status | `'draft'` |
| Ghi `status = DEFAULT` | `'draft'` |
| Ghi `status = 'paid'` | `'paid'` |
| Ghi `status = NULL` | NULL nếu cột cho phép |
| Ghi `status = ''` | Chuỗi rỗng, không phải default |

Điều này đặc biệt quan trọng khi API gửi JSON `null` cho mọi trường bị bỏ trống. Nếu backend đưa NULL vào câu INSERT, mặc định của database sẽ không được áp dụng.

### 3.4. Khi không có DEFAULT

Một cột thông thường không có giá trị mặc định sẽ nhận NULL nếu được bỏ qua trong INSERT, trừ khi constraint như `NOT NULL` từ chối.

Không có `DEFAULT` không có nghĩa PostgreSQL tự điền 0, chuỗi rỗng hay thời điểm hiện tại.

## 4. INSERT ... DEFAULT VALUES

Khi tất cả cột có thể được sinh hoặc nhận giá trị mặc định:

~~~sql
CREATE TABLE empty_request_events (
    event_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    event_type TEXT NOT NULL DEFAULT 'created',
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);

INSERT INTO empty_request_events
DEFAULT VALUES
RETURNING *;
~~~

Câu `DEFAULT VALUES` không chỉ định cột nào; database dùng giá trị mặc định cho tất cả cột. Nếu một cột bắt buộc không có default, INSERT có thể bị từ chối.

### 4.1. DEFAULT VALUES khác VALUES(NULL)

~~~sql
-- Dùng toàn bộ mặc định.
INSERT INTO empty_request_events DEFAULT VALUES;

-- Không giống: ghi NULL tường minh vào cột event_type.
INSERT INTO empty_request_events (event_type)
VALUES (NULL);
~~~

Lệnh thứ hai vi phạm `NOT NULL`; nó không nhận `'created'`.

### 4.2. DEFAULT trong VALUES nhiều hàng

~~~sql
INSERT INTO empty_request_events (event_type)
VALUES
    (DEFAULT),
    ('processed'),
    (DEFAULT)
RETURNING event_id, event_type;
~~~

Mỗi hàng có thể dùng default hoặc giá trị tường minh ở vị trí tương ứng.

## 5. DEFAULT được tính theo từng hàng

Giá trị mặc định có thể là hàm, không chỉ hằng:

~~~sql
CREATE TABLE random_samples (
    sample_id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    sampled_value DOUBLE PRECISION NOT NULL DEFAULT random()
);

INSERT INTO random_samples DEFAULT VALUES;
INSERT INTO random_samples DEFAULT VALUES;
~~~

`random()` được tính khi giá trị mặc định được sử dụng. Các hàng khác nhau có thể nhận các giá trị khác nhau.

### 5.1. DEFAULT không tham chiếu trực tiếp cột khác của cùng hàng

Ý tưởng sau không hợp lệ cho một default thông thường:

~~~sql
-- Cú pháp sai về nguyên tắc:
-- CREATE TABLE line_items (
--     quantity INTEGER,
--     unit_price NUMERIC,
--     total NUMERIC DEFAULT (quantity * unit_price)
-- );
~~~

Biểu thức `DEFAULT` của một cột không được phụ thuộc trực tiếp vào giá trị cột khác trong cùng hàng theo cách này.

Nếu cần `total = quantity * unit_price`, hãy dùng **generated column** khi phù hợp, hoặc tính trong ứng dụng/transaction với thiết kế nhất quán.

### 5.2. DEFAULT không tự tính lại khi cột khác đổi

Nếu `unit_price</BT> được cập nhật, một cột thông thường đã nhận DEFAULT trước đó **không tự thay đổi** theo giá mới. DEFAULT phục vụ việc tạo giá trị khi lệnh ghi yêu cầu default, không phải một quan hệ tính toán liên tục.

## 6. DEFAULT cho thời gian: now(), CURRENT_TIMESTAMP và clock_timestamp()

Một ví dụ quen thuộc:

~~~sql
CREATE TABLE activity_log (
    activity_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    action_name TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
~~~

### 6.1. CURRENT_TIMESTAMP và now()

Trong PostgreSQL, `CURRENT_TIMESTAMP</BT>, `now()</BT> và `transaction_timestamp()</BT> lấy **thời điểm bắt đầu transaction**.

~~~sql
BEGIN;

SELECT now() AS first_read;
SELECT pg_sleep(1);
SELECT now() AS second_read,
       clock_timestamp() AS actual_clock;

COMMIT;
~~~

Hai lần `now()</BT> trong cùng transaction trả cùng instant. `clock_timestamp()</BT> đọc thời gian tại lúc gọi và có thể thay đổi.

`pg_sleep()</BT> chỉ dùng ở môi trường thử nghiệm; không nên giữ transaction ngủ trên production.

### 6.2. DEFAULT CURRENT_TIMESTAMP không có nghĩa thời điểm COMMIT

Nếu transaction bắt đầu lúc 10:00 nhưng INSERT xảy ra lúc 10:05, `CURRENT_TIMESTAMP</BT> vẫn phản ánh mốc bắt đầu transaction.

Nếu nghiệp vụ yêu cầu “thời điểm câu lệnh” hoặc “thời gian đồng hồ thực tại lúc gọi”, cần xét `statement_timestamp()</BT> hoặc `clock_timestamp()</BT> thay vì dùng `now()</BT> mà không suy nghĩ.

### 6.3. Chọn TIMESTAMPTZ cho instant

Một event thực sự xảy ra tại một thời điểm nên thường dùng:

~~~sql
created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
~~~

`TIMESTAMPTZ` biểu diễn instant, hiển thị theo timezone của session. PostgreSQL không lưu riêng timezone gốc người dùng đã nhập.

Nếu cột chỉ là ngày nghiệp vụ theo một timezone, có thể cần `DATE` và quy tắc xác định ngày, không tự dùng CURRENT_DATE của session mà bỏ qua timezone nghiệp vụ.

### 6.4. DEFAULT created_at không tự động cập nhật updated_at

~~~sql
CREATE TABLE profiles_time (
    profile_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    display_name TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
~~~

Khi UPDATE `display_name</BT>, cột `updated_at</BT> **không tự thay đổi** chỉ vì nó có DEFAULT.

Ứng dụng có thể cập nhật:

~~~sql
UPDATE profiles_time
SET display_name = 'Tên mới',
    updated_at = clock_timestamp()
WHERE profile_id = 1;
~~~

Nếu mọi đường ghi phải cập nhật `updated_at</BT>, có thể cân nhắc trigger được kiểm thử và quản lý. Không dùng generated column `now()</BT> cho mục đích này vì biểu thức generated column có các giới hạn khác.

## 7. DEFAULT với UUID và chuỗi mã định danh

Một hệ thống có thể cần UUID thay vì ID số liên tiếp:

~~~sql
CREATE TABLE external_requests (
    request_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    status TEXT NOT NULL DEFAULT 'pending'
);
~~~

`gen_random_uuid()</BT> được hỗ trợ trong PostgreSQL hiện đại; khả năng có sẵn phụ thuộc phiên bản và môi trường cài đặt, còn những phiên bản cũ có thể cần extension phù hợp.

### 7.1. UUID default khác identity

- UUID được tạo bởi một hàm sinh UUID.
- Identity được PostgreSQL quản lý bằng sequence, thường trên kiểu số nguyên.
- UUID không bảo đảm thứ tự liên tiếp như số đếm.
- Identity không tự bảo đảm khóa duy nhất nếu thiếu constraint thích hợp.
- Cả hai đều cần cân nhắc PRIMARY KEY hoặc UNIQUE.

### 7.2. Vì sao không tạo “ID bằng cách SELECT MAX(id)+1”?

~~~sql
-- Không nên dùng làm cơ chế cấp ID đồng thời:
-- SELECT COALESCE(MAX(order_id), 0) + 1 FROM orders;
~~~

Hai transaction có thể cùng nhìn thấy cùng `MAX(id)` rồi chọn trùng ID. Identity/sequence được thiết kế để cấp số an toàn hơn dưới concurrency, dù vẫn cần primary key bảo vệ tính duy nhất.

## 8. Giá trị mặc định với ALTER TABLE

Bạn có thể thay đổi default mà không định nghĩa lại bảng:

~~~sql
CREATE TABLE shipping_jobs (
    job_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    priority INTEGER NOT NULL DEFAULT 1,
    status TEXT NOT NULL DEFAULT 'waiting'
);
~~~

Đổi mức ưu tiên mặc định:

~~~sql
ALTER TABLE shipping_jobs
ALTER COLUMN priority SET DEFAULT 3;
~~~

Bỏ default:

~~~sql
ALTER TABLE shipping_jobs
ALTER COLUMN priority DROP DEFAULT;
~~~

### 8.1. SET DEFAULT thường chỉ ảnh hưởng những lần ghi tương lai

Đổi default từ 1 sang 3 **không tự cập nhật mọi hàng cũ đang có priority=1**.

Nếu muốn sửa dữ liệu đã tồn tại, cần câu UPDATE riêng với điều kiện rõ:

~~~sql
UPDATE shipping_jobs
SET priority = 3
WHERE priority = 1;
~~~

Lệnh này chỉ là ví dụ; trên hệ thống thật, phải phân biệt hàng có giá trị 1 do default cũ với hàng mà người dùng chủ động chọn 1. Nếu không lưu nguồn gốc giá trị, bạn **không thể tự biết** mọi giá trị 1 nên được thay.

### 8.2. Khi thêm một cột có DEFAULT vào bảng lớn

~~~sql
ALTER TABLE shipping_jobs
ADD COLUMN retry_count INTEGER NOT NULL DEFAULT 0;
~~~

PostgreSQL có các tối ưu để tránh rewrite toàn bảng cho nhiều default không volatile trong những phiên bản hiện đại, nhưng không phải mọi biểu thức default và mọi thao tác ALTER TABLE đều có cùng chi phí. Với bảng lớn, cần xem phiên bản server, lock, dung lượng và kế hoạch migration.

### 8.3. Thêm default khác thêm constraint

~~~sql
ALTER TABLE shipping_jobs
ALTER COLUMN status SET DEFAULT 'waiting';
~~~

Chỉ xác định trạng thái mặc định. Nó **không cấm** giá trị `'invalid'</BT> nếu không có CHECK/FK tương ứng.

~~~sql
ALTER TABLE shipping_jobs
ADD CONSTRAINT chk_shipping_status
CHECK (status IN ('waiting', 'running', 'done', 'failed'));
~~~

Bất biến tập trạng thái là trách nhiệm của constraint, không phải DEFAULT.

## 9. Identity column là gì?

Cột **identity** dùng một sequence liên kết với cột để tạo số định danh theo cơ chế PostgreSQL.

~~~sql
CREATE TABLE departments_identity (
    department_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    department_name TEXT NOT NULL
);
~~~

Khi thêm hàng:

~~~sql
INSERT INTO departments_identity (department_name)
VALUES ('Engineering')
RETURNING department_id, department_name;
~~~

PostgreSQL lấy một số từ sequence để điền `department_id`. Ứng dụng không cần tự chọn ID.

### 9.1. Tại sao identity thường đi cùng PRIMARY KEY?

Identity sinh số nhưng **không tự thay thế PRIMARY KEY hoặc UNIQUE constraint**. Quy tắc “không trùng ID” phải được bảo vệ bằng constraint thích hợp.

Cách phổ biến:

~~~sql
id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY
~~~

Trong mô hình này:

- Identity cấp giá trị.
- PRIMARY KEY bảo đảm không NULL và không trùng trong bảng.
- Quyền và transaction của ứng dụng quản lý vòng đời bản ghi.

### 9.2. Identity không phải “số thứ tự liên tục không thiếu”

Sequence có thể bị tiêu thụ khi transaction thất bại, khi INSERT xung đột hoặc khi cơ chế cache cấp số. Vì vậy dãy ID có thể có khoảng trống.

**Không dùng identity làm số lượng đơn đã xử lý**, thứ tự sự kiện tuyệt đối hay số hóa đơn pháp lý bắt buộc liên tục.

## 10. GENERATED ALWAYS AS IDENTITY

Cú pháp:

~~~sql
CREATE TABLE inventory_categories (
    category_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    category_name TEXT NOT NULL UNIQUE
);
~~~

Thêm dữ liệu thông thường:

~~~sql
INSERT INTO inventory_categories (category_name)
VALUES ('Books'), ('Office')
RETURNING category_id, category_name;
~~~

Database cấp `category_id`.

### 10.1. ALWAYS hạn chế người ghi nhập ID

Ví dụ sau không hợp lệ khi không có cú pháp override thích hợp:

~~~sql
-- Cố tình minh họa thao tác bị từ chối:
-- INSERT INTO inventory_categories (category_id, category_name)
-- VALUES (500, 'Special');
~~~

`GENERATED ALWAYS</BT> thể hiện rằng ID thông thường do database quyết định, không phải do client.

### 10.2. Khi cần nhập ID cụ thể: OVERRIDING SYSTEM VALUE

Một trường hợp migration hoặc import đã kiểm soát có thể cần giữ ID cũ:

~~~sql
INSERT INTO inventory_categories (
    category_id,
    category_name
)
OVERRIDING SYSTEM VALUE
VALUES (500, 'Imported category')
RETURNING category_id;
~~~

`OVERRIDING SYSTEM VALUE</BT> cho phép cung cấp ID tường minh với identity ALWAYS trong INSERT.

**Không nên dùng override làm đường ghi mặc định của ứng dụng.** Nó phù hợp với các thao tác có mục đích rõ và cần kiểm tra trùng khóa, sequence state, audit và phân quyền.

### 10.3. ALWAYS không có nghĩa giá trị không bao giờ đổi

Identity ALWAYS chủ yếu quản lý cách cấp giá trị khi INSERT và các quy tắc ghi vào identity column. Nó **không phải** cơ chế chống mọi thay đổi dữ liệu hay bảo vệ quyền truy cập. Quy tắc sửa ID, trách nhiệm tham chiếu FK và role permissions vẫn phải được thiết kế riêng.

## 11. GENERATED BY DEFAULT AS IDENTITY

Cột identity ở chế độ `BY DEFAULT` linh hoạt hơn:

~~~sql
CREATE TABLE external_categories (
    category_id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    category_name TEXT NOT NULL UNIQUE
);
~~~

Không cung cấp ID:

~~~sql
INSERT INTO external_categories (category_name)
VALUES ('Standard')
RETURNING category_id;
~~~

Database cấp ID.

Có thể cung cấp ID tường minh:

~~~sql
INSERT INTO external_categories (
    category_id,
    category_name
)
VALUES (900, 'Imported')
RETURNING category_id;
~~~

PostgreSQL chấp nhận giá trị 900 nếu thỏa các constraints.

### 11.1. BY DEFAULT vẫn không tự dò ID đã dùng

Sau khi nhập `category_id=900` trực tiếp, sequence của identity **không tự nhảy đến 901** chỉ vì có hàng đó.

Nếu lần tự sinh sau này đi tới số đã nhập, primary key có thể phát hiện trùng và câu INSERT thất bại. Khi import IDs, phải lập kế hoạch đồng bộ sequence với tập dữ liệu hiện tại.

### 11.2. Chọn ALWAYS hay BY DEFAULT?

| Trường hợp | Lựa chọn thường cân nhắc |
|---|---|
| Ứng dụng tạo mọi bản ghi mới, ID do DB quản lý | `ALWAYS` |
| Import dữ liệu cần giữ ID tường minh thường xuyên | `BY DEFAULT` hoặc ALWAYS + override có kiểm soát |
| Migration một lần từ hệ thống cũ | `ALWAYS` + `OVERRIDING SYSTEM VALUE` có thể phù hợp |
| Muốn cấm client tùy ý chọn ID | `ALWAYS` cùng quyền/đường ghi thích hợp |

Không có chế độ nào thay thế thiết kế security: nếu ứng dụng có quyền cao hoặc trực tiếp xây SQL từ client thiếu kiểm soát, cần khắc phục quyền và boundary.

## 12. OVERRIDING USER VALUE

`OVERRIDING USER VALUE</BT> yêu cầu PostgreSQL **bỏ qua giá trị identity do người ghi cung cấp** và dùng giá trị được sinh bởi sequence.

Ví dụ với `BY DEFAULT`:

~~~sql
INSERT INTO external_categories (
    category_id,
    category_name
)
OVERRIDING USER VALUE
VALUES (9999, 'New generated category')
RETURNING category_id;
~~~

Giá trị 9999 ở phần VALUES được bỏ qua cho cột identity; `category_id` được cấp theo sequence.

### 12.1. Mục đích phổ biến: sao chép dữ liệu nhưng cấp ID mới

Giả sử bảng có các cột thông thường như tên, địa chỉ, trạng thái và cột identity. Khi copy dữ liệu thành bản ghi mới, không nên dùng lại identity cũ nếu hai hàng cùng tồn tại.

Cú pháp override có thể cho phép giữ cấu trúc SELECT/INSERT mà yêu cầu database sinh ID mới, thay vì phải thay toàn bộ thao tác nhập dữ liệu.

### 12.2. Không nhầm hai OVERRIDING

| Cú pháp | Tác dụng |
|---|---|
| `OVERRIDING SYSTEM VALUE` | Cho phép giá trị ID tường minh thay chế độ ALWAYS |
| `OVERRIDING USER VALUE` | Bỏ qua giá trị ID tường minh, dùng sequence |

Hai câu có ý nghĩa **ngược nhau**. Một câu dùng để giữ ID từ dữ liệu nguồn, câu kia dùng để cấp ID mới.

## 13. Sequence đứng sau identity

Identity dựa trên **sequence object** trong PostgreSQL. Sequence cung cấp số theo thiết lập như giá trị bắt đầu, bước tăng, min/max, chu kỳ và cache.

~~~sql
CREATE TABLE ticket_numbers (
    ticket_id BIGINT GENERATED ALWAYS AS IDENTITY (
        START WITH 1000
        INCREMENT BY 1
    ) PRIMARY KEY,
    title TEXT NOT NULL
);
~~~

Thêm hàng:

~~~sql
INSERT INTO ticket_numbers (title)
VALUES ('First'), ('Second')
RETURNING ticket_id, title;
~~~

Trong một lab mới không có tác động trước đó, các giá trị đầu tiên thường là 1000 và 1001.

### 13.1. Sequence có thể có cấu hình khác

Có các tùy chọn như `START WITH`, `INCREMENT BY`, `MINVALUE`, `MAXVALUE`, `CACHE` và `CYCLE` tùy định nghĩa phù hợp.

Không nên cấu hình `CYCLE` cho ID khóa chính mà chưa hiểu nguy cơ lặp lại số sau khi quay vòng và tương tác với uniqueness.

### 13.2. Sequence không rollback số đã cấp

Mô hình:

~~~text
Transaction A:
    nextval -> 1000
    INSERT xảy ra lỗi
    ROLLBACK

Transaction B:
    nextval -> 1001
    INSERT thành công
~~~

ID 1000 có thể bị bỏ trống. Điều này bình thường.

### 13.3. Sequence không bảo đảm thứ tự COMMIT

Transaction A có thể lấy ID 1000 trước nhưng commit sau transaction B lấy ID 1001. Vì vậy **ID nhỏ hơn không chứng minh giao dịch hoàn tất trước**.

Nếu cần xác định thứ tự sự kiện, phải thiết kế dữ liệu và semantics tương ứng; timestamp cũng cần hiểu transaction vs commit time.

### 13.4. Sequence không phải bộ đếm số hàng

Khi xóa bản ghi, sequence không tự giảm. Khi rollback, số có thể đã bị tiêu thụ. Khi import thủ công, bảng có thể chứa ID không tương ứng thứ tự sequence.

Để đếm hàng:

~~~sql
SELECT COUNT(*) FROM ticket_numbers;
~~~

Không sử dụng `MAX(ticket_id)</BT> hay giá trị sequence làm số lượng ticket thực đã lưu.

## 14. INSERT RETURNING: cách lấy ID đã tạo

Một kiểu lỗi ở ứng dụng là:

1. INSERT bản ghi.
2. Đọc “ID cuối cùng” theo một nguồn chung.
3. Dùng ID đó để tạo bản ghi con.

Cách đáng tin và gọn trong PostgreSQL là **`RETURNING`**:

~~~sql
INSERT INTO ticket_numbers (title)
VALUES ('Issue from app')
RETURNING ticket_id;
~~~

### 14.1. RETURNING trả giá trị thực sau INSERT

Với bảng có DEFAULT/identity/generated column:

~~~sql
INSERT INTO ticket_numbers (title)
VALUES ('Another issue')
RETURNING *;
~~~

Client thấy ID được cấp thực sự, không cần tự đoán sequence và không phụ thuộc những transaction khác.

### 14.2. RETURNING trong JDBC

~~~java
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.ResultSet;

String sql = """
    INSERT INTO ticket_numbers (title)
    VALUES (?)
    RETURNING ticket_id
    """;

try (PreparedStatement ps = connection.prepareStatement(sql)) {
    ps.setString(1, "Issue from Java");

    try (ResultSet rs = ps.executeQuery()) {
        if (rs.next()) {
            long ticketId = rs.getLong("ticket_id");
            // Sử dụng ticketId cho các thao tác tiếp theo.
        }
    }
}
~~~

Đây là ví dụ Java/JDBC; giả định `connection` là kết nối PostgreSQL hợp lệ. Trong code thật, quản lý transaction và rollback phù hợp.

### 14.3. Không dùng SELECT MAX(id) để tìm ID vừa thêm

~~~sql
-- Không nên suy ra ID của INSERT hiện tại:
-- SELECT MAX(ticket_id) FROM ticket_numbers;
~~~

Hàng có ID lớn nhất có thể đến từ transaction khác hoặc import. Dùng `RETURNING` cho câu INSERT cụ thể.

## 15. currval(), lastval() và nextval()

PostgreSQL có các hàm sequence:

- `nextval(sequence)</BT>: cấp giá trị tiếp theo.
- `currval(sequence)</BT>: đọc giá trị đã được `nextval</BT> cấp gần nhất **cho sequence đó trong session hiện tại**.
- `lastval()</BT>: đọc giá trị được cấp gần nhất trong session từ một sequence bất kỳ.

### 15.1. currval không phải “ID cuối cùng của cả database”

Nếu session hiện tại chưa gọi `nextval</BT> trên sequence tương ứng, `currval</BT> có thể báo lỗi. Nó không truy vấn hàng có ID lớn nhất.

### 15.2. lastval có thể gây nhầm khi nhiều sequence được dùng

Một thao tác có trigger hoặc thêm bản ghi khác có thể tiêu thụ thêm sequence. Khi đó `lastval()</BT> không nhất thiết là ID của bảng bạn đang quan tâm.

### 15.3. Ưu tiên RETURNING

Ngay khi có thể:

~~~sql
INSERT INTO ticket_numbers (title)
VALUES ('New ticket')
RETURNING ticket_id;
~~~

`RETURNING</BT> làm rõ ID được trả thuộc câu lệnh nào và có thể trả nhiều cột sau default/generated.

## 16. SERIAL và IDENTITY: khác nhau thế nào?

Trước khi có identity theo chuẩn SQL, PostgreSQL thường dùng `SERIAL`, `BIGSERIAL` và `SMALLSERIAL`.

Ví dụ legacy:

~~~sql
CREATE TABLE legacy_serial_tickets (
    ticket_id BIGSERIAL PRIMARY KEY,
    title TEXT NOT NULL
);
~~~

`SERIAL</BT> là một **cách khai báo tiện ích**, không phải một kiểu dữ liệu số độc lập có đầy đủ semantics như tên gọi gợi ý. Nó tạo một cột số, sequence liên quan và default gọi `nextval</BT> theo cơ chế tương ứng.

### 16.1. So sánh

| Đặc điểm | SERIAL/BIGSERIAL | GENERATED AS IDENTITY |
|---|---|---|
| Cấp số bằng sequence | Có | Có |
| Cú pháp khai báo | Pseudo-type | Thuộc tính cột theo SQL standard |
| Chế độ ALWAYS/BY DEFAULT | Không cùng cơ chế | Có |
| Default nextval hiển thị như default thường | Có | Metadata identity riêng |
| Dùng làm PK tự động | Không; cần PRIMARY KEY | Không; cần PRIMARY KEY |
| Khoảng trống sequence có thể xảy ra | Có | Có |
| Dùng cho hệ thống cũ | Rất phổ biến | Phù hợp với schema mới khi muốn quản lý identity tường minh |

### 16.2. Khi nào vẫn gặp SERIAL?

Nhiều dự án cũ hoặc ORM có migration dùng `SERIAL</BT>. Đây không phải lý do phải thay toàn bộ ngay lập tức. Khi thiết kế bảng mới, identity thường thể hiện ý định rõ hơn và có cú pháp quản lý được PostgreSQL hỗ trợ.

### 16.3. Không dùng SERIAL và IDENTITY chồng nhau cho cùng cột

Một cột nên có một cơ chế cấp ID được thiết kế rõ. Không tự gắn thêm DEFAULT `nextval</BT> cho cột đã có thuộc tính identity nếu không có mục đích migration và đã hiểu giới hạn cú pháp.

## 17. Điều chỉnh sequence khi import dữ liệu có ID

Giả sử một bảng identity BY DEFAULT nhận một loạt ID cũ từ hệ thống khác. Dãy số cấp phát tự động có thể vẫn đang ở mức thấp hơn ID lớn nhất đã import.

### 17.1. Lấy tên sequence của cột

PostgreSQL hỗ trợ:

~~~sql
SELECT pg_get_serial_sequence(
    'public.external_categories',
    'category_id'
);
~~~

Ví dụ này giả định bảng ở schema `public`. Nếu đối tượng nằm ở schema khác, cần dùng tên đầy đủ đúng trường hợp. Hàm được dùng để xác định sequence gắn với cột serial/identity theo metadata phù hợp.

### 17.2. Đồng bộ sequence bằng setval khi đã kiểm soát writer

Một mẫu thường gặp trong migration đã xác nhận bảng không rỗng:

~~~sql
SELECT setval(
    pg_get_serial_sequence(
        'public.external_categories',
        'category_id'
    ),
    (SELECT MAX(category_id) FROM public.external_categories),
    TRUE
);
~~~

Với `is_called = TRUE`, lần `nextval</BT> kế tiếp tiến theo bước cấu hình sau giá trị đã set. Mẫu này giả định sequence tăng bước 1 thông thường và MAX không NULL.

**Không sao chép câu này chạy bừa trên hệ thống đang có writer đồng thời.** Nếu có INSERT giữa lúc tính MAX và setval, có thể làm sequence quay về số đã cấp hoặc tạo xung đột. Migration cần kiểm soát đường ghi/khóa và hiểu trạng thái sequence thật.

### 17.3. Bảng rỗng, INCREMENT âm và sequence khác cấu hình

Mẫu `MAX(id)` không tự phù hợp với mọi trường hợp:

- Bảng rỗng → MAX là NULL.
- Sequence giảm bước âm → logic “giá trị kế tiếp” khác.
- Sequence có MIN/MAX/CYCLE.
- Bảng có ID nhập tay rất lớn.
- Sequence đã cấp số trước nhưng chưa commit.

Cần viết quy trình setval/restart phù hợp **cấu hình cụ thể**, không coi một biểu thức MAX là công thức vạn năng.

### 17.4. ID pháp lý và số thứ tự liên tục

Nếu số hóa đơn bắt buộc không có khoảng trống, không dùng sequence thông thường làm bằng chứng không thiếu số. Cần cơ chế phát hành số riêng với quy tắc pháp lý, transaction và audit thích hợp.

## 18. Identity có thể thay đổi bằng ALTER TABLE

Với một cột số thông thường đã tồn tại và phù hợp điều kiện:

~~~sql
CREATE TABLE imported_users (
    user_id BIGINT PRIMARY KEY,
    display_name TEXT NOT NULL
);
~~~

Có thể xét thêm thuộc tính identity trong migration:

~~~sql
ALTER TABLE imported_users
ALTER COLUMN user_id
ADD GENERATED BY DEFAULT AS IDENTITY;
~~~

Nhưng việc thêm identity **không tự đảm bảo sequence khớp với ID đã có**. Nếu dữ liệu cũ chứa user_id 1..10000, sequence mới có thể bắt đầu từ một số thấp gây xung đột về sau.

### 18.1. Chuyển BY DEFAULT sang ALWAYS

~~~sql
ALTER TABLE imported_users
ALTER COLUMN user_id
SET GENERATED ALWAYS;
~~~

Ngược lại:

~~~sql
ALTER TABLE imported_users
ALTER COLUMN user_id
SET GENERATED BY DEFAULT;
~~~

Những lệnh trên chỉ phù hợp khi cột hiện đã là identity và migration được lên kế hoạch đúng.

### 18.2. Restart identity sequence

~~~sql
ALTER TABLE imported_users
ALTER COLUMN user_id
RESTART WITH 20000;
~~~

Ví dụ minh họa thay điểm bắt đầu cho các giá trị cấp phát tiếp theo. Chỉ làm khi đã phân tích dữ liệu hiện có, thứ tự sequence và writer đồng thời.

### 18.3. Bỏ identity

~~~sql
ALTER TABLE imported_users
ALTER COLUMN user_id
DROP IDENTITY;
~~~

Bỏ thuộc tính identity không đồng nghĩa xóa dữ liệu trong cột. Tuy nhiên, sau đó các INSERT bỏ qua ID có thể bị từ chối nếu cột vẫn NOT NULL mà không có default mới.

### 18.4. Migration phải xem phụ thuộc

Trước khi thay identity:

- Xem foreign key và các bảng tham chiếu.
- Xem mã ứng dụng có nhập ID trực tiếp không.
- Xem ETL/replication/import.
- Xem sequence state và quyền.
- Chuẩn bị rollback và kiểm thử trên dữ liệu đại diện.

## 19. Generated column: cột tính từ các cột khác

Trong PostgreSQL, **generated column** thường dùng cho một giá trị được tính từ biểu thức trên cùng hàng.

Ví dụ:

~~~sql
CREATE TABLE sales_line_calculation (
    line_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    quantity INTEGER NOT NULL CHECK (quantity > 0),
    unit_price NUMERIC(12, 2) NOT NULL CHECK (unit_price >= 0),
    line_total NUMERIC(14, 2)
        GENERATED ALWAYS AS (quantity * unit_price) STORED
);
~~~

Khi INSERT:

~~~sql
INSERT INTO sales_line_calculation (
    quantity,
    unit_price
)
VALUES (3, 125000.00)
RETURNING line_id, quantity, unit_price, line_total;
~~~

Kết quả `line_total = 375000.00`.

### 19.1. Generated column khác DEFAULT

`DEFAULT</BT> cung cấp một giá trị ban đầu khi cột bị bỏ qua. Generated column là **hàm của dữ liệu cùng hàng** theo một biểu thức quy định.

| Câu hỏi | DEFAULT | Generated column |
|---|---|---|
| Có thể phụ thuộc trực tiếp vào cột khác cùng hàng? | Không | Có, theo giới hạn biểu thức |
| Được tự tính lại khi UPDATE cột nguồn? | Không | Có |
| Có thể ghi đè bằng giá trị thủ công? | Có, nếu constraints cho phép | Không viết tùy ý |
| Có thể dùng hàm thời gian biến động? | Có, khi default biểu thức hợp lệ | Không, biểu thức phải thỏa yêu cầu immutable |
| Có thể dùng cho tổng `quantity * unit_price`? | Không như default phụ thuộc cột | Có |

### 19.2. Tính lại khi cột nguồn đổi

~~~sql
UPDATE sales_line_calculation
SET quantity = 4
WHERE line_id = 1
RETURNING quantity, unit_price, line_total;
~~~

Nếu hàng line_id=1 được tạo bởi INSERT đầu tiên trong bảng thử nghiệm, `line_total` trở thành `4 * 125000 = 500000`.

Không cần service tự gửi một giá trị line_total mới. Điều này giảm nguy cơ service quên cập nhật tổng khi quantity thay đổi.

### 19.3. Không trực tiếp gán giá trị tùy ý cho generated column

~~~sql
-- Dự kiến bị PostgreSQL từ chối:
-- INSERT INTO sales_line_calculation
--     (quantity, unit_price, line_total)
-- VALUES (3, 125000, 1);
~~~

PostgreSQL quản lý giá trị `line_total` theo biểu thức. Nếu cần tổng có thể điều chỉnh thủ công vì chiết khấu, thuế hoặc quy tắc đặc biệt, hãy cân nhắc mô hình cột khác chứ không ép generated column nhận số tùy ý.

## 20. STORED và VIRTUAL: khác biệt theo phiên bản PostgreSQL

Các ví dụ trong bài dùng:

~~~sql
GENERATED ALWAYS AS (expression) STORED
~~~

Đây là cách phổ biến và tương thích với các phiên bản PostgreSQL đã hỗ trợ generated columns dạng lưu trữ.

### 20.1. STORED

**Stored generated column** được tính khi hàng được INSERT hoặc UPDATE, rồi **lưu giá trị trên đĩa** như một cột thông thường.

Ưu điểm:

- Truy vấn đọc có thể lấy giá trị đã tính.
- Có thể hữu ích khi biểu thức được đọc thường xuyên.
- Có thể tạo index phù hợp trên cột stored generated.

Đổi lại:

- Tốn dung lượng lưu trữ cho giá trị.
- Có chi phí tính toán khi ghi/cập nhật.
- Migration thêm/đổi biểu thức có thể đắt trên bảng lớn.

### 20.2. VIRTUAL

Các phiên bản PostgreSQL mới có thêm khả năng **virtual generated columns**: giá trị được tính khi đọc thay vì lưu sẵn. PostgreSQL 18 hỗ trợ loại cột này; với các phiên bản cũ hơn không có, chỉ có dạng STORED trong phạm vi generated columns.

Ví dụ cú pháp chỉ dành cho phiên bản hỗ trợ:

~~~sql
-- PostgreSQL 18+:
CREATE TABLE generated_virtual_demo (
    quantity INTEGER NOT NULL,
    unit_price NUMERIC(12, 2) NOT NULL,
    line_total NUMERIC
        GENERATED ALWAYS AS (quantity * unit_price) VIRTUAL
);
~~~

Lưu ý: loại VIRTUAL có những giới hạn riêng về biểu thức/hàm và khả năng sử dụng; phải tham khảo tài liệu đúng **phiên bản server đang chạy** trước khi triển khai.

### 20.3. Chọn STORED hay VIRTUAL?

| Tiêu chí | STORED | VIRTUAL |
|---|---|---|
| Thời điểm tính chính | Ghi/cập nhật hàng | Đọc giá trị |
| Chi phí lưu cột kết quả | Có | Không lưu giá trị cột như stored |
| Tải tính toán | Nghiêng về ghi | Nghiêng về đọc |
| Hỗ trợ phiên bản | Rộng hơn | Cần phiên bản mới hỗ trợ |
| Ví dụ trong bài lab | Dùng STORED | Chỉ là tùy chọn bổ sung |

Đừng mặc định virtual luôn tốt hơn vì tiết kiệm dung lượng; cũng đừng mặc định stored luôn nhanh hơn vì tính sẵn. Cần đo workload và xem giới hạn phiên bản.

## 21. Giới hạn biểu thức của generated column

Generated columns không phải nơi để chạy mọi logic tùy ý. PostgreSQL áp dụng các giới hạn để giá trị có thể được tính ổn định từ hàng.

### 21.1. Biểu thức phải phù hợp tính bất biến

Ví dụ hợp lý:

~~~sql
line_total NUMERIC
    GENERATED ALWAYS AS (quantity * unit_price) STORED
~~~

Ví dụ không phù hợp:

~~~sql
-- Không được dùng hàm thời gian biến động như sau:
-- calculated_at TIMESTAMPTZ
--     GENERATED ALWAYS AS (now()) STORED
~~~

`now()</BT> không bất biến theo đầu vào của hàng. Generated expression yêu cầu các hàm thỏa tính chất immutable theo quy tắc PostgreSQL.

### 21.2. Không truy vấn bảng khác từ generated expression

Một ý tưởng sai:

~~~sql
-- Không phù hợp làm generated expression:
-- total_value GENERATED ALWAYS AS (
--     SELECT SUM(...) FROM order_items
-- ) STORED
~~~

Generated column chỉ có thể dùng dữ liệu phù hợp trong cùng hàng theo giới hạn expression, không thay thế aggregate liên quan nhiều hàng hoặc query sang bảng khác.

### 21.3. Không tham chiếu generated column khác

Trong PostgreSQL, một generated column không được dựa trực tiếp vào một generated column khác theo cách tạo chuỗi phụ thuộc tính toán trong khai báo. Nếu cần nhiều bước, có thể lặp/ghép biểu thức trên các cột gốc hoặc cân nhắc mô hình khác.

### 21.4. Không trộn DEFAULT và GENERATED cho cùng cột

Cột có generated expression không đồng thời là cột mặc định có thể ghi tay theo cách thông thường. Khi giá trị phải được tính từ các cột khác, chỉ định rõ generated expression; khi muốn giá trị ban đầu linh hoạt, dùng default.

### 21.5. Hàm tự định nghĩa cần được đánh giá nghiêm túc

Một hàm PostgreSQL được khai báo `IMMUTABLE` phải thực sự trả cùng kết quả với cùng input trong những điều kiện yêu cầu. Không chỉ đánh dấu một hàm đọc bảng khác hoặc phụ thuộc thời gian là IMMUTABLE để vượt qua giới hạn generated expression; điều đó có thể gây dữ liệu không nhất quán.

## 22. Generated column và NULL

Giả sử:

~~~sql
CREATE TABLE totals_nullable (
    quantity INTEGER,
    unit_price NUMERIC(12, 2),
    total NUMERIC(14, 2)
        GENERATED ALWAYS AS (quantity * unit_price) STORED
);
~~~

Nếu `quantity</BT> hoặc `unit_price</BT> là NULL, phép nhân thường trả NULL.

~~~sql
INSERT INTO totals_nullable (quantity, unit_price)
VALUES (NULL, 100000)
RETURNING quantity, unit_price, total;
~~~

Kết quả total là NULL, không phải 0.

### 22.1. Muốn cấm NULL

~~~sql
CREATE TABLE totals_required (
    quantity INTEGER NOT NULL CHECK (quantity > 0),
    unit_price NUMERIC(12, 2) NOT NULL CHECK (unit_price >= 0),
    total NUMERIC(14, 2)
        GENERATED ALWAYS AS (quantity * unit_price) STORED
);
~~~

Lúc này hai giá trị nguồn đều bắt buộc và hợp lệ theo constraints.

### 22.2. COALESCE thay đổi ngữ nghĩa

~~~sql
-- Ví dụ ý tưởng tính NULL thành 0, chỉ khi nghiệp vụ yêu cầu:
-- GENERATED ALWAYS AS (COALESCE(quantity,0) * unit_price) STORED
~~~

Nếu quantity NULL nghĩa là “chưa biết”, biến nó thành 0 sẽ che giấu dữ liệu thiếu. Không áp dụng COALESCE chỉ để tránh NULL khi chưa hiểu nghiệp vụ.

### 22.3. CHECK trên generated column

Có thể đặt constraint phù hợp cho kết quả tính:

~~~sql
CREATE TABLE computed_limits (
    quantity INTEGER NOT NULL,
    unit_price NUMERIC(12,2) NOT NULL,
    total NUMERIC(14,2)
        GENERATED ALWAYS AS (quantity * unit_price) STORED,
    CONSTRAINT chk_total_nonnegative
        CHECK (total >= 0)
);
~~~

Nhưng nếu đã yêu cầu quantity dương và unit_price không âm, có thể bảo vệ logic rõ hơn trực tiếp ở các cột nguồn. Constraint thêm trên total cần có lý do thực tế.

## 23. Generated column có thể giúp tạo khóa chuẩn hóa

Một nhu cầu khác ngoài tính tiền là chuẩn hóa trường để tìm kiếm.

~~~sql
CREATE TABLE customer_emails_generated (
    customer_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email_raw TEXT NOT NULL,
    email_key TEXT
        GENERATED ALWAYS AS (lower(btrim(email_raw))) STORED,
    CONSTRAINT chk_email_nonblank
        CHECK (btrim(email_raw) <> ''),
    CONSTRAINT uq_email_key
        UNIQUE (email_key)
);
~~~

Khi thêm:

~~~sql
INSERT INTO customer_emails_generated (email_raw)
VALUES ('  Alice@Example.COM  ')
RETURNING customer_id, email_raw, email_key;
~~~

Kết quả khóa so sánh có thể là `alice@example.com` theo quy tắc đã chọn.

### 23.1. Unique trên khóa so sánh

Nếu thêm `'alice@example.com'</BT> lần nữa, `UNIQUE(email_key)` sẽ từ chối khi biểu thức chuẩn hóa cho cùng khóa.

### 23.2. Không nhầm normalized key với xác thực email

Biểu thức `lower(btrim(email_raw))` chỉ thực hiện biến đổi chuỗi đơn giản. Nó không chứng minh email tồn tại, chủ sở hữu đã xác minh, hoặc quy tắc canonicalization thích hợp với mọi hệ thống email.

Ngoài ra, case conversion có thể phụ thuộc collation/locale. Chính sách canonicalization cần được xác định trước khi dùng làm khóa unique.

### 23.3. Khi nào dùng expression index thay vì generated column?

Có thể tạo index trực tiếp trên:

~~~sql
CREATE UNIQUE INDEX uq_customer_emails_expr
ON some_customer_table (lower(btrim(email_raw)));
~~~

Ví dụ trên là cấu trúc yêu cầu bảng nguồn tồn tại. Nếu chỉ cần so sánh/index mà không cần truy cập `email_key` như cột riêng, expression index có thể đơn giản hơn.

Generated column hữu ích khi muốn thể hiện phép tính như một cột rõ ràng cho truy vấn hoặc ứng dụng, với các chi phí và giới hạn tương ứng.

## 24. Generated column có thể được dùng trong truy vấn và RETURNING

~~~sql
SELECT
    line_id,
    quantity,
    unit_price,
    line_total
FROM sales_line_calculation
ORDER BY line_id;
~~~

Nếu created `sales_line_calculation</BT> và đã chèn các hàng, PostgreSQL trả `line_total` như một cột.

### 24.1. ORDER BY kết quả tính

~~~sql
SELECT
    line_id,
    line_total
FROM sales_line_calculation
ORDER BY line_total DESC;
~~~

### 24.2. Index phù hợp với STORED

~~~sql
CREATE INDEX idx_sales_line_total
ON sales_line_calculation (line_total);
~~~

Với stored generated column, chỉ mục trên kết quả tính có thể hữu ích cho truy vấn lọc/sắp xếp, tùy workload.

### 24.3. Không tự coi computed column là bản sao bất biến của dữ liệu nguồn

Giá trị generated STORED được cập nhật khi hàng nguồn bị ghi lại theo cơ chế tính của PostgreSQL. Nó thể hiện dữ liệu hiện hành trong hàng, **không phải snapshot lịch sử** nếu giá/số lượng được sửa.

Đối với hóa đơn đã phát hành, có thể cần ghi giá bán lịch sử cố định và khóa sửa theo workflow. Generated column không tự giải quyết yêu cầu kế toán/audit đó.

## 25. Lab tổng hợp: schema cho sản phẩm và đơn hàng

Phần thực hành này được thiết kế cho **database PostgreSQL thử nghiệm** có quyền CREATE SCHEMA. Không chạy trên production. Nếu schema `generated_lab</BT> đã tồn tại, chọn database hoặc tên schema khác để tránh xung đột; không xóa dữ liệu thật.

### 25.1. Tạo schema

~~~sql
CREATE SCHEMA generated_lab;
~~~

### 25.2. Bảng sản phẩm với identity và default

~~~sql
CREATE TABLE generated_lab.products (
    product_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    sku TEXT NOT NULL UNIQUE,
    product_name TEXT NOT NULL,
    price NUMERIC(12, 2) NOT NULL
        CHECK (price >= 0),
    stock INTEGER NOT NULL DEFAULT 0
        CHECK (stock >= 0),
    is_active BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
~~~

Phân tích:

| Cột | Cơ chế |
|---|---|
| `product_id` | Identity ALWAYS, PK |
| `sku` | Bắt buộc, duy nhất |
| `product_name` | Bắt buộc |
| `price` | Bắt buộc, CHECK không âm |
| `stock` | Default 0, CHECK không âm |
| `is_active` | Default TRUE |
| `created_at` | Default transaction time |
| `updated_at` | Default lúc INSERT, không auto-update |

### 25.3. INSERT không điền các cột default/identity

~~~sql
INSERT INTO generated_lab.products (
    sku, product_name, price
)
VALUES
    ('BOOK-001', 'PostgreSQL căn bản', 150000.00),
    ('BOOK-002', 'SQL thực hành', 99000.00)
RETURNING
    product_id,
    sku,
    stock,
    is_active,
    created_at;
~~~

PostgreSQL cấp `product_id`, `stock = 0`, `is_active = TRUE` và các timestamp.

### 25.4. Ghi rõ DEFAULT cho vài cột

~~~sql
INSERT INTO generated_lab.products (
    sku, product_name, price, stock, is_active
)
VALUES (
    'BOOK-003', 'Sổ tay PostgreSQL', 49000.00,
    DEFAULT,
    DEFAULT
)
RETURNING product_id, stock, is_active;
~~~

### 25.5. Gửi NULL tường minh vào cột NOT NULL

-- Dự kiến bị PostgreSQL từ chối:

~~~

DEFAULT 0 **không thay** NULL tường minh. Kết quả vi phạm NOT NULL.

## 26. Lab: bảng đơn hàng và dòng hàng generated STORED

### 26.1. Bảng đơn hàng

~~~sql
CREATE TABLE generated_lab.orders (
    order_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_code TEXT NOT NULL,
    status TEXT NOT NULL DEFAULT 'draft'
        CHECK (status IN (
            'draft', 'submitted', 'paid', 'cancelled'
        )),
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
~~~

### 26.2. Bảng dòng hàng

~~~sql
CREATE TABLE generated_lab.order_items (
    order_item_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL
        REFERENCES generated_lab.orders(order_id),
    product_id BIGINT NOT NULL
        REFERENCES generated_lab.products(product_id),
    quantity INTEGER NOT NULL DEFAULT 1
        CHECK (quantity > 0),
    unit_price NUMERIC(12, 2) NOT NULL
        CHECK (unit_price >= 0),
    line_total NUMERIC(14, 2)
        GENERATED ALWAYS AS (quantity * unit_price) STORED,
    CONSTRAINT uq_order_product
        UNIQUE (order_id, product_id)
);
~~~

**Giá trị đơn giá ở dòng hàng** được lưu riêng, không luôn truy vấn giá hiện tại của bảng products để tính tiền lịch sử. Nếu giá sản phẩm thay đổi sau khi đặt, line_total của đơn đã có vẫn dựa trên `unit_price` snapshot trong order_items.

### 26.3. Tạo đơn rồi dùng RETURNING lấy ID

~~~sql
INSERT INTO generated_lab.orders (customer_code)
VALUES ('CUST-001')
RETURNING order_id, status, created_at;
~~~

Trong môi trường lab mới, `order_id` đầu có thể là 1, nhưng không nên xây quy trình dựa trên giả định đó.

### 26.4. Tạo đơn và item trong một câu dùng CTE

~~~sql
WITH new_order AS (
    INSERT INTO generated_lab.orders (customer_code)
    VALUES ('CUST-002')
    RETURNING order_id
)
INSERT INTO generated_lab.order_items (
    order_id,
    product_id,
    quantity,
    unit_price
)
SELECT
    o.order_id,
    p.product_id,
    2,
    p.price
FROM new_order AS o
JOIN generated_lab.products AS p
    ON p.sku = 'BOOK-001'
RETURNING
    order_item_id,
    order_id,
    quantity,
    unit_price,
    line_total;
~~~

Trong bảng lab, câu lệnh này tạo một đơn và một dòng hàng, trả identity ID cùng tổng tiền sinh tự động.

### 26.5. Thử quantity mặc định bằng cách bỏ cột

Với `INSERT ... SELECT`, cách rõ ràng để dùng DEFAULT là **bỏ cột quantity khỏi danh sách INSERT** và không đưa biểu thức cho cột đó vào SELECT. Ví dụ với order có mã CUST-002 vừa tạo:

~~~sql
INSERT INTO generated_lab.order_items (
    order_id, product_id, unit_price
)
SELECT
    o.order_id,
    p.product_id,
    p.price
FROM generated_lab.orders AS o
JOIN generated_lab.products AS p
    ON p.sku = 'BOOK-002'
WHERE o.customer_code = 'CUST-002'
RETURNING quantity, unit_price, line_total;
~~~

Kết quả quantity nhận mặc định 1. Khác với cú pháp `VALUES(DEFAULT, ...)`, từ khóa `DEFAULT` không thể được đặt như một biểu thức trong danh sách SELECT. Việc phân biệt **VALUES(... DEFAULT ...)** và **INSERT ... SELECT** là chi tiết quan trọng khi viết SQL tạo hàng.

### 26.6. Tính lại line_total khi UPDATE quantity

~~~sql
UPDATE generated_lab.order_items
SET quantity = 3
WHERE order_id IN (
    SELECT order_id
    FROM generated_lab.orders
    WHERE customer_code = 'CUST-002'
)
AND product_id IN (
    SELECT product_id
    FROM generated_lab.products
    WHERE sku = 'BOOK-001'
)
RETURNING
    order_item_id,
    quantity,
    unit_price,
    line_total;
~~~

`line_total` được tính lại theo quantity mới.

### 26.7. Tổng đơn là aggregate nhiều hàng

Nếu muốn tổng tiền của một đơn:

~~~sql
SELECT
    order_id,
    SUM(line_total) AS order_total
FROM generated_lab.order_items
GROUP BY order_id
ORDER BY order_id;
~~~

Không nên cố đưa `SUM(line_total)</BT> qua nhiều hàng vào generated column của bảng orders: generated expression có giới hạn theo một hàng, không tham chiếu các hàng khác.

Nếu cần lưu `orders.total_amount</BT> vì audit hoặc hiệu năng, phải chọn giao thức transaction, trigger hoặc cơ chế duy trì dữ liệu dẫn xuất phù hợp, có kiểm soát concurrency.

## 27. Lab: UPDATE SET column = DEFAULT

PostgreSQL cho phép yêu cầu dùng default trong UPDATE trên một cột thông thường.

Ví dụ phục hồi stock theo default đã khai báo:

~~~sql
UPDATE generated_lab.products
SET stock = DEFAULT
WHERE sku = 'BOOK-003'
RETURNING sku, stock;
~~~

Nếu default của stock đang là 0, giá trị được đặt về 0.

### 27.1. DEFAULT trong UPDATE có thể thay dữ liệu đang có

`SET stock = DEFAULT` không phải “giữ stock như hiện tại”. Nó **ghi giá trị default mới** vào hàng theo cú pháp UPDATE. Hãy dùng cẩn thận.

### 27.2. Reset status bằng DEFAULT

~~~sql
UPDATE generated_lab.orders
SET status = DEFAULT
WHERE customer_code = 'CUST-002'
RETURNING order_id, status;
~~~

Nếu default là `'draft'`, thao tác đưa những đơn khớp điều kiện về draft. Nhưng nếu đơn đã paid, đó có thể vi phạm workflow dù constraint cho phép.

**DEFAULT không thay business transition validation.**

### 27.3. Generated column không phải trường để reset tùy ý

Một generated column nhận giá trị từ biểu thức và không được cập nhật bằng một giá trị tùy ý như `line_total = 1</BT>. Nếu giá trị cần thay đổi, cập nhật các cột nguồn hoặc thay thiết kế dữ liệu.

## 28. Lab: INSERT ... ON CONFLICT và các giá trị tự sinh

PostgreSQL hỗ trợ upsert bằng `INSERT ... ON CONFLICT</BT>.

~~~sql
INSERT INTO generated_lab.products (
    sku, product_name, price
)
VALUES ('BOOK-001', 'PostgreSQL căn bản', 155000.00)
ON CONFLICT (sku) DO UPDATE
SET
    product_name = EXCLUDED.product_name,
    price = EXCLUDED.price,
    updated_at = CURRENT_TIMESTAMP
RETURNING product_id, sku, price, updated_at;
~~~

### 28.1. DEFAULT được dùng trong nhánh INSERT

Nếu SKU chưa tồn tại, các cột `stock</BT>, `is_active</BT> và timestamp có default sẽ được điền theo quy tắc INSERT.

### 28.2. Nhánh UPDATE không tự áp lại toàn bộ DEFAULT

Nếu SKU đã tồn tại, nhánh `DO UPDATE</BT> thực hiện những phép gán được nêu. `updated_at` ở ví dụ được **gán tường minh** vì DEFAULT của nó không tự chạy lại theo mọi UPDATE.

### 28.3. Sequence có thể tăng ngay cả khi xảy ra conflict

Việc cấp giá trị sequence cho hàng thử INSERT có thể xảy ra trước khi PostgreSQL xác định conflict và chuyển sang nhánh DO UPDATE. Vì vậy một câu UPSERT có thể tiêu thụ số identity ngay cả khi không tạo hàng mới.

Đừng dựa vào identity IDs liên tiếp để suy ra “mỗi câu INSERT tạo đúng một hàng”.

### 28.4. Unique constraint bảo vệ SKU

`ON CONFLICT (sku)</BT> ở đây dựa trên unique constraint/index tương ứng của SKU. Identity không liên quan trực tiếp tới việc phát hiện sản phẩm đã có cùng SKU.

## 29. Identity và COPY/import

PostgreSQL có công cụ `COPY FROM</BT> để nạp dữ liệu hàng loạt. Khi nhập dữ liệu có cột identity tường minh, cần đặc biệt thận trọng: hành vi `COPY FROM</BT> đối với giá trị identity được cung cấp **không giống mặc định của INSERT ALWAYS** trong mọi trường hợp; COPY có thể ghi giá trị ID từ dữ liệu đầu vào bất kể chế độ identity.

### 29.1. Hai chiến lược import

**Chiến lược A: giữ ID cũ**

- Chỉ làm khi cần giữ tham chiếu từ hệ thống nguồn.
- Đảm bảo không trùng primary key.
- Đồng bộ sequence sau import có kiểm soát.
- Kiểm tra foreign keys giữa các bảng đã nhập.

**Chiến lược B: cấp ID mới**

- Để database cấp identity mới.
- Lưu bảng mapping từ old_id → new_id.
- Chuyển foreign keys theo mapping.
- Không cố suy ra quan hệ bằng “số thứ tự import”.

### 29.2. Import không phải quyền tự do bỏ qua constraints

Dù dùng `COPY</BT>, constraints và transaction vẫn cần được xem xét. Không tắt constraints hoặc quyền bảo vệ chỉ vì muốn nhập nhanh hơn mà không có kế hoạch integrity và phục hồi.

## 30. Identity, concurrency và gaps

Giả sử hai request cùng chèn:

~~~sql
INSERT INTO generated_lab.orders (customer_code)
VALUES ('CUST-A')
RETURNING order_id;
~~~

và:

~~~sql
INSERT INTO generated_lab.orders (customer_code)
VALUES ('CUST-B')
RETURNING order_id;
~~~

Sequence cấp giá trị theo cơ chế riêng, tránh việc cả hai request tự tính cùng `MAX(id)+1</BT>.

### 30.1. Số ID không nhất thiết phản ánh thời gian nghiệp vụ

Một request có thể nhận số nhỏ trước rồi commit sau request có số lớn. Nếu một thao tác thất bại, số cũng có thể bị bỏ.

### 30.2. Vì sao không thể mặc định ID là số hóa đơn?

Ở nhiều nghiệp vụ kế toán, số hóa đơn có yêu cầu phát hành, hủy, audit và tính liên tục riêng. Identity sequence có thể có khoảng trống, nên cần cơ chế đánh số pháp lý riêng nếu luật/quy trình yêu cầu.

### 30.3. UUID cũng không tự quyết định thứ tự

Nếu dùng `gen_random_uuid()</BT>, giá trị phù hợp làm định danh nhưng không mặc định thể hiện thứ tự theo thời gian. Chọn kiểu ID phải dựa trên nhu cầu: uniqueness, kích thước, phân tán, index locality, khả năng import và expose qua API.

## 31. Chọn kiểu dữ liệu cho identity

Identity thường được khai báo trên kiểu số nguyên hỗ trợ, ví dụ:

~~~sql
id SMALLINT GENERATED ALWAYS AS IDENTITY
id INTEGER GENERATED ALWAYS AS IDENTITY
id BIGINT GENERATED ALWAYS AS IDENTITY
~~~

Đây là những dòng cú pháp minh họa cho một định nghĩa cột, không phải ba lệnh SQL độc lập.

### 31.1. SMALLINT, INTEGER hay BIGINT?

| Kiểu | Phạm vi số nguyên có dấu (xấp xỉ) | Cân nhắc |
|---|---|---|
| `SMALLINT` | ±32 nghìn | Chỉ dùng khi số lượng giá trị rất hạn chế |
| `INTEGER` | ±2,1 tỷ | Phù hợp nhiều bảng vừa |
| `BIGINT` | ±9,22 × 10¹⁸ | Biên rộng cho ID dài hạn |

Sequence có thể dùng giá trị trong phạm vi được cấu hình. Hệ thống có tốc độ ghi cao nhiều năm thường ưu tiên BIGINT cho primary key số để giảm nguy cơ cạn phạm vi, tùy tính toán thực tế.

### 31.2. Dùng BIGINT không có nghĩa tối ưu mọi trường hợp

BIGINT chiếm nhiều không gian hơn INTEGER trong index/hàng. Nên chọn dựa trên khả năng mở rộng và tài nguyên. Với một danh mục chỉ có vài trăm trạng thái cố định, INTEGER hoặc một khóa nghiệp vụ có thể phù hợp.

### 31.3. Identity không tự che giấu ID

ID số liên tiếp có thể khiến người dùng đoán ID của tài nguyên khác. Nếu API dùng `/orders/123</BT>, vẫn phải kiểm tra authorization. Dùng UUID cũng không thay thế bảo vệ quyền truy cập.

## 32. Metadata: làm sao biết cột có default, identity hay generated?

PostgreSQL đưa metadata cột ra `information_schema.columns`.

~~~sql
SELECT
    table_schema,
    table_name,
    column_name,
    data_type,
    column_default,
    is_identity,
    identity_generation,
    is_generated,
    generation_expression
FROM information_schema.columns
WHERE table_schema = 'generated_lab'
  AND table_name IN ('products', 'orders', 'order_items')
ORDER BY table_name, ordinal_position;
~~~

Các cột thông tin có ý nghĩa:

- `column_default`: biểu thức default nếu được khai báo theo dạng thông thường.
- `is_identity`: có phải identity column không.
- `identity_generation`: ALWAYS hay BY DEFAULT khi là identity.
- `is_generated`: thông tin về generated column theo phiên bản.
- `generation_expression`: biểu thức tính khi metadata được cung cấp.

### 32.1. Không suy luận identity chỉ từ column_default

Identity có metadata riêng, không cần hiển thị hệt một default `nextval(...)</BT> như cột SERIAL legacy. Để nhận biết đúng, dùng các trường identity.

### 32.2. Sử dụng psql \d

Trong công cụ `psql`, có thể dùng:

~~~text
\d generated_lab.products
\d generated_lab.order_items
~~~

Đây là lệnh meta của `psql`, **không phải SQL chuẩn gửi trực tiếp qua JDBC**.

### 32.3. Xem định nghĩa thực tế trước migration

Một schema có thể đã được ORM tạo ra theo phiên bản khác. Đừng chỉ dựa trên tên cột như `id` hay `total</BT> để đoán nó là identity/generated. Hãy đọc metadata.

## 33. Constraint vẫn cần thiết khi có DEFAULT và generated column

Giả sử:

~~~sql
CREATE TABLE stock_defaults (
    product_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    quantity INTEGER DEFAULT 0
);
~~~

Câu này không cấm:

~~~sql
INSERT INTO stock_defaults (quantity)
VALUES (-100);
~~~

Muốn cấm âm:

~~~sql
CREATE TABLE stock_safe (
    product_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    quantity INTEGER NOT NULL DEFAULT 0
        CHECK (quantity >= 0)
);
~~~

### 33.1. DEFAULT là ý định ban đầu, CHECK bảo vệ phạm vi

- `DEFAULT 0`: nếu không nhập quantity, bắt đầu từ 0.
- `NOT NULL`: không lưu giá trị thiếu.
- `CHECK (quantity >= 0)`: không lưu số âm.
- `PRIMARY KEY`: product_id không trùng.

Không có một cơ chế riêng lẻ thay toàn bộ các cơ chế khác.

### 33.2. Generated result vẫn phải phù hợp nghiệp vụ

`line_total = quantity * unit_price` chỉ đúng nếu total của dòng được định nghĩa đúng bằng tích đó.

Nếu có giảm giá, coupon, thuế và phí:

\[
\text{total} \ne \text{quantity} \times \text{unit_price}
\]

trừ khi các thành phần khác không áp dụng.

Không biến một công thức tiện lợi thành generated column nếu nghiệp vụ thực cần nhiều quy tắc hơn.

## 34. DEFAULT và thiết kế API

Một API tạo sản phẩm có thể nhận:

~~~json
{
  "sku": "BOOK-010",
  "productName": "Sổ tay dữ liệu",
  "price": 75000
}
~~~

Nếu hợp đồng API cho phép bỏ qua stock và isActive, backend có thể **không đưa hai cột vào INSERT** để PostgreSQL áp dụng DEFAULT.

### 34.1. JSON null khác không có trường

Hai request:

~~~json
{"sku":"BOOK-010","stock":null}
~~~

và:

~~~json
{"sku":"BOOK-010"}
~~~

có thể được backend xử lý khác nhau:

- Có trường stock với giá trị null → nếu bind NULL tường minh, DB không dùng default.
- Thiếu trường stock → SQL có thể bỏ cột, DB dùng default.

Đây là quyết định ở hợp đồng API/mapper, không chỉ là chi tiết SQL.

### 34.2. Không cho client truyền created_at tùy ý khi không có lý do

Nếu thời điểm tạo phải phản ánh sự kiện hệ thống, API không nên tin giá trị `created_at` do client gửi, dù database có default. Bởi vì default **không áp dụng khi người ghi cung cấp giá trị cụ thể**.

Có thể:

- Không expose created_at trong request DTO.
- Giới hạn quyền và đường ghi.
- Dùng trigger/logic DB đặc biệt nếu yêu cầu tính toàn vẹn xuyên nhiều writer.

### 34.3. Identity cũng cần kiểm soát API

Một request tạo bản ghi mới thường không nên có trường `id` người dùng được chọn. Identity ALWAYS có thể giúp phòng vệ ở DB, nhưng authorization/mass-assignment ở API vẫn phải được thiết kế.

## 35. Gắn DEFAULT vào thời điểm tạo có rủi ro timezone

~~~sql
created_at TIMESTAMP WITHOUT TIME ZONE DEFAULT now()
~~~

Đây là lựa chọn khác với:

~~~sql
created_at TIMESTAMPTZ DEFAULT now()
~~~

Ở trường hợp đầu, một instant từ `now()</BT> cần được chuyển thành timestamp không timezone và cách diễn giải chịu ảnh hưởng timezone của session. Nếu bạn lưu event instant, `TIMESTAMPTZ` thường rõ hơn.

### 35.1. CURRENT_DATE phụ thuộc ngày theo session

~~~sql
SELECT CURRENT_DATE;
~~~

Giá trị ngày hiện tại của session chịu ảnh hưởng TimeZone. Một hệ thống báo cáo cần “ngày nghiệp vụ ở Việt Nam” phải xác định rõ timezone nghiệp vụ thay vì mặc định ngày ở kết nối database luôn tương ứng vị trí người dùng.

### 35.2. Mặc định không đồng nghĩa bất biến lịch sử

`created_at</BT> có DEFAULT nhưng vẫn là cột thông thường có thể bị UPDATE nếu writer được phép. Nếu cần bất biến “không thay đổi sau khi tạo”, phải bổ sung chính sách quyền/đường ghi hoặc cơ chế bảo vệ phù hợp.

## 36. Migration giữa SERIAL và IDENTITY

Một schema legacy có thể có:

~~~sql
CREATE TABLE legacy_items (
    item_id BIGSERIAL PRIMARY KEY,
    title TEXT NOT NULL
);
~~~

Muốn thay bằng identity, không thể chỉ đổi chữ `BIGSERIAL` thành `BIGINT GENERATED ...` trong file migration rồi cho rằng đối tượng đang chạy tự thay đổi.

Cần xem:

- Sequence cũ đã được tạo và gắn ownership ra sao.
- Default `nextval(...)</BT> trên cột.
- Các quyền cấp trên sequence.
- Tình trạng bảng đã có dữ liệu.
- ORM có kỳ vọng JDBC generated key theo cách cũ không.
- Lịch sử import ID tường minh.
- Giới hạn khóa/transaction trong ALTER TABLE.

### 36.1. Không bỏ sequence cũ khi chưa kiểm tra phụ thuộc

Sequence legacy có thể được code gọi trực tiếp bằng tên. Một migration xóa/thay sequence mà không cập nhật ứng dụng có thể gây lỗi runtime.

### 36.2. Cập nhật ứng dụng trước và sau migration

Kiểm thử:

- INSERT bỏ qua id.
- INSERT RETURNING id.
- Batch INSERT.
- Upsert.
- COPY/import.
- Quyền role của writer.
- Sequence state sau restore.
- Hành vi ORM.

Đây là phần của migration dữ liệu, không chỉ sửa DDL.

## 37. Generated column và migration schema lớn

Thêm generated STORED trên bảng lớn có thể yêu cầu tính biểu thức cho dữ liệu hiện có và gây chi phí rewrite/lock theo thao tác/phiên bản.

~~~sql
ALTER TABLE existing_order_items
ADD COLUMN line_total NUMERIC(14,2)
    GENERATED ALWAYS AS (quantity * unit_price) STORED;
~~~

Câu này là ví dụ cấu trúc; chỉ chạy khi bảng và cột nguồn tồn tại. Không chạy trực tiếp trên production mà không đánh giá.

### 37.1. Kiểm tra dữ liệu cũ trước

Nếu quantity hoặc unit_price có NULL, kết quả generated có thể NULL. Nếu giá vượt giới hạn của `numeric(14,2)</BT>, migration có thể lỗi ở bước tính.

Cần đánh giá:

- Kiểu dữ liệu và giới hạn kết quả.
- NULL semantics.
- Độ chính xác và làm tròn.
- Tính bất biến của biểu thức.
- Tải đọc/ghi và index liên quan.
- Rollback nếu ALTER TABLE thất bại.

### 37.2. Khi công thức nghiệp vụ thay đổi

Nếu sau này total phải tính thêm chiết khấu, công thức generated ban đầu không còn đủ. Cần xem sửa schema/expression, loại dữ liệu đã lưu và khả năng khôi phục lịch sử.

Không dùng generated column cho những phép tính phụ thuộc trạng thái nhiều bảng hoặc luật thuế thay đổi theo từng kỳ nếu không được mô hình hóa thành các cột nguồn thích hợp.

### 37.3. Generated column không phải công cụ duy nhất để tránh dư thừa

Nếu biểu thức rất đơn giản và chỉ được đọc thỉnh thoảng, có thể tính trực tiếp trong SELECT:

~~~sql
SELECT quantity * unit_price AS line_total
FROM generated_lab.order_items;
~~~

Trong trường hợp bảng đã có generated column, phép tính này chỉ minh họa lựa chọn khác. Hãy cân nhắc chi phí tính khi đọc, ghi, nhu cầu index và tính đúng trước khi thêm cột sinh tự động.

## 38. Generated column và trigger: khi nào dùng cơ chế nào?

| Tình huống | DEFAULT | Generated column | Trigger/service |
|---|---|---|---|
| Trạng thái lúc tạo là draft | Rất phù hợp | Không cần | Có thể nhưng thường thừa |
| created_at khi thêm hàng | Phù hợp | Không phù hợp với now() | Có thể trong tình huống đặc biệt |
| line_total = qty × price | Không vì phụ thuộc hàng | Phù hợp | Có thể, nhưng phức tạp hơn |
| updated_at đổi mỗi UPDATE | Không tự đủ | Không phù hợp với now() | Service hoặc trigger |
| Tổng order từ nhiều order_items | Không | Không phù hợp biểu thức khác hàng | Transaction/service/trigger có kiểm soát |
| Cấp ID số | Identity/sequence thay vì DEFAULT thủ công | Không | Hiếm khi cần cơ chế riêng |
| Ghi audit log khi status đổi | Không | Không | Trigger/service/eventing |
| Giá theo API bên ngoài | Không | Không | Service hoặc workflow |

### 38.1. Generated expression phải có cùng kết quả với cùng cột nguồn

Nếu giá trị phải gọi API, đọc bảng khác hay phụ thuộc thời gian, nó không còn là một biểu thức local immutable đơn giản. Dùng service/transaction hoặc mô hình dữ liệu có trạng thái được lưu phù hợp.

### 38.2. Trigger không tự an toàn hơn

Trigger có thể gây tác động phụ ẩn, khó debug và vẫn phải được thiết kế đúng trước concurrency. Không thay mọi DEFAULT/generated bằng trigger chỉ để “gom logic về database”.

## 39. Thao tác đồng thời với computed totals

Một ví dụ:

~~~sql
UPDATE generated_lab.order_items
SET quantity = quantity + 1
WHERE order_item_id = 1
RETURNING quantity, line_total;
~~~

Nếu hàng tồn tại, PostgreSQL cập nhật quantity theo cơ chế transaction/row locking và tính lại stored generated line_total.

### 39.1. Generated total không tự ngăn overselling

Dù line_total đúng công thức, hai người vẫn có thể cùng mua vượt tồn kho nếu ứng dụng không kiểm soát giao dịch cấp phát.

Một mẫu tồn kho an toàn hơn là:

~~~sql
UPDATE generated_lab.products
SET stock = stock - 2,
    updated_at = clock_timestamp()
WHERE sku = 'BOOK-001'
  AND stock >= 2
RETURNING product_id, stock;
~~~

Nếu trả 0 hàng, không đủ điều kiện cấp phát hoặc SKU không tồn tại.

### 39.2. Generated column không thay transaction nhiều bảng

Khi đặt hàng, cần tạo order, items và trừ kho trong transaction phù hợp. Cột computed total chỉ đảm bảo phép nhân trên từng hàng, không chứng minh toàn bộ workflow đã hoàn tất.

### 39.3. Đừng tự gán ID để “giữ thứ tự giao dịch”

Identity phục vụ cấp ID và uniqueness. Muốn kiểm soát thứ tự nghiệp vụ, cần một cơ chế rõ và có khả năng chịu tải; cấp ID trước không đồng nghĩa commit trước.

## 40. Xử lý lỗi phổ biến

PostgreSQL trả SQLSTATE giúp backend phân biệt những lỗi khi dùng default/identity/generated.

| SQLSTATE phổ biến | Tình huống | Hướng xử lý |
|---|---|---|
| `23502` | NULL ở cột NOT NULL | Xem trường nhập hoặc thiếu DEFAULT |
| `23505` | Trùng PRIMARY KEY/UNIQUE | Kiểm tra import ID, sequence, key nghiệp vụ |
| `23514` | CHECK không thỏa | Kiểm tra dữ liệu/logic nghiệp vụ |
| `23503` | Vi phạm FOREIGN KEY | Kiểm tra quan hệ và thứ tự ghi |
| `22003` | Numeric value out of range | Cột ID/total vượt phạm vi |
| `428C9` | Generated always column violation | Ghi giá trị không hợp lệ vào cột generated/identity ALWAYS theo ngữ cảnh |

Mã lỗi chi tiết cần được xác nhận theo thao tác và phiên bản PostgreSQL. Không ánh xạ mọi `23505` thành “sequence lỗi”: nó có thể là SKU, email, mã đơn hoặc unique key khác.

### 40.1. Đừng trả nguyên lỗi DB cho người dùng cuối

Lỗi có thể chứa tên bảng/cột và giá trị nhạy cảm. API nên chuyển lỗi thành thông báo ổn định, dễ hiểu và không lộ dữ liệu nội bộ.

### 40.2. Nếu import ID xung đột, đừng tự retry vô hạn

Phải kiểm tra: import có trùng key nghiệp vụ không, sequence đang ở đâu, có concurrent writers không và chiến lược mapping ID như thế nào.

### 40.3. Nếu total tính ra NULL

Xem cột nguồn có NULL không, vì phép nhân với NULL có thể cho NULL. Không tự `COALESCE(...,0)</BT> nếu “không biết giá” khác “giá bằng 0”.

## 41. Bài tập thực hành

### Bài 1 — DEFAULT cơ bản

Tạo bảng `tasks</BT> có cột `status TEXT NOT NULL DEFAULT 'new'`.

**Gợi ý:**

~~~sql
CREATE TABLE exercise_tasks (
    task_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title TEXT NOT NULL,
    status TEXT NOT NULL DEFAULT 'new'
);
~~~

### Bài 2 — Bỏ qua cột so với NULL

Với `status DEFAULT 'new'`, kết quả khác nhau ra sao khi INSERT không có status và khi INSERT status=NULL?

**Gợi ý:** Bỏ qua dùng default; NULL tường minh không dùng default và sẽ bị từ chối nếu NOT NULL.

### Bài 3 — DEFAULT VALUES

Viết một bảng có mọi cột đều có giá trị tự sinh/default rồi dùng `INSERT ... DEFAULT VALUES`.

**Gợi ý:** Bảng có identity ID và timestamp mặc định.

### Bài 4 — DEFAULT thời gian

`DEFAULT now()</BT> trả thời điểm INSERT thực tại hay thời điểm bắt đầu transaction?

**Gợi ý:** Thời điểm bắt đầu transaction.

### Bài 5 — updated_at

Vì sao khai báo `updated_at DEFAULT now()</BT> chưa đủ để nó thay đổi khi UPDATE?

**Gợi ý:** DEFAULT không tự chạy lại cho mọi UPDATE.

### Bài 6 — ID do PostgreSQL cấp

Viết `GENERATED ALWAYS AS IDENTITY PRIMARY KEY` cho BIGINT.

**Gợi ý:**

~~~sql
id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY
~~~

### Bài 7 — ALWAYS vs BY DEFAULT

Một ứng dụng luôn để database chọn ID nên cân nhắc ALWAYS hay BY DEFAULT?

**Gợi ý:** ALWAYS biểu đạt ý định quản lý ID chặt hơn; vẫn cần quyền/PK.

### Bài 8 — Import ID cũ

Muốn chèn ID=500 vào identity ALWAYS, cần cú pháp gì?

**Gợi ý:** `INSERT ... OVERRIDING SYSTEM VALUE ...`.

### Bài 9 — Bỏ qua ID người nhập

Muốn copy một dòng nhưng cấp identity mới thay vì giữ ID nguồn, dùng loại OVERRIDING nào?

**Gợi ý:** `OVERRIDING USER VALUE`.

### Bài 10 — Sequence gaps

Một INSERT thất bại sau khi cấp ID. Vì sao lần INSERT tiếp có thể không dùng lại ID vừa cấp?

**Gợi ý:** Sequence không rollback số đã cấp.

### Bài 11 — Thứ tự COMMIT

ID=100 có chắc commit trước ID=101 không?

**Gợi ý:** Không.

### Bài 12 — MAX(id)+1

Vì sao hai transaction cùng tính MAX(id)+1 có thể chọn trùng ID?

**Gợi ý:** Race condition; dùng identity/sequence.

### Bài 13 — Lấy ID an toàn

Cách lấy ID do INSERT vừa tạo trong PostgreSQL?

**Gợi ý:** `INSERT ... RETURNING id`.

### Bài 14 — SERIAL khác identity

Nêu khác nhau giữa BIGSERIAL và BIGINT GENERATED ALWAYS AS IDENTITY.

**Gợi ý:** BIGSERIAL là pseudo-type tiện ích với default nextval; identity có metadata và chế độ ALWAYS/BY DEFAULT.

### Bài 15 — Cấp ID thủ công

Sau khi nhập ID=900 vào BY DEFAULT identity, sequence có tự nhảy qua 900 không?

**Gợi ý:** Không nhất thiết; cần đồng bộ trong migration có kiểm soát.

### Bài 16 — Đồng bộ sequence

Nêu rủi ro của `setval(..., MAX(id), true)</BT> khi có nhiều writers đồng thời.

**Gợi ý:** Dữ liệu/sequence có thể thay đổi giữa lúc đọc MAX và setval, gây xung đột.

### Bài 17 — Thêm identity cho bảng có dữ liệu

Sau khi ALTER cột user_id ADD GENERATED BY DEFAULT AS IDENTITY, cần kiểm tra gì?

**Gợi ý:** Sequence state so với IDs hiện có, quyền và writers.

### Bài 18 — Generated total

Tạo cột `line_total` bằng `quantity * unit_price`.

**Gợi ý:**

~~~sql
line_total NUMERIC(14,2)
    GENERATED ALWAYS AS (quantity * unit_price) STORED
~~~

### Bài 19 — UPDATE cột nguồn

Nếu quantity tăng từ 2 lên 3, line_total STORED thay đổi thế nào?

**Gợi ý:** PostgreSQL tính lại từ expression khi cập nhật hàng.

### Bài 20 — Nhập line_total thủ công

Có thể INSERT line_total=1 để bỏ qua generated expression không?

**Gợi ý:** Không. Generated column không nhận giá trị thủ công tùy ý.

### Bài 21 — DEFAULT phụ thuộc cột khác

Vì sao `total DEFAULT (quantity * unit_price)</BT> không phù hợp?

**Gợi ý:** DEFAULT thông thường không tham chiếu các cột khác cùng hàng; dùng generated column.

### Bài 22 — now() trong generated

Có thể khai báo `GENERATED ALWAYS AS (now()) STORED` không?

**Gợi ý:** Không, generated expression cần thỏa tính bất biến và không dùng hàm phụ thuộc thời gian.

### Bài 23 — Tổng order

Tại sao không thể tính `SUM(line_total)</BT> từ nhiều order_items trực tiếp bằng generated column của hàng orders?

**Gợi ý:** Giới hạn cùng hàng; cần aggregate/query hoặc transaction/trigger phù hợp.

### Bài 24 — NULL nhân số

Nếu quantity=NULL và unit_price=100, phép nhân trong generated total thường cho gì?

**Gợi ý:** NULL.

### Bài 25 — STORED vs VIRTUAL

Sự khác nhau chính về thời điểm tính và lưu trữ?

**Gợi ý:** STORED tính lúc ghi và lưu; VIRTUAL tính lúc đọc ở phiên bản hỗ trợ.

### Bài 26 — Kiểm tra phiên bản

Nếu PostgreSQL cũ không hỗ trợ VIRTUAL, ví dụ tương thích thường dùng loại nào?

**Gợi ý:** `STORED`.

### Bài 27 — Kiểm tra metadata

Truy vấn `information_schema.columns` có những trường nào giúp nhận diện identity và generated?

**Gợi ý:** `is_identity`, `identity_generation`, `is_generated`, `generation_expression`.

### Bài 28 — DEFAULT không thay CHECK

Một cột stock DEFAULT 0 có chặn stock=-5 không?

**Gợi ý:** Không. Cần CHECK (stock >= 0).

### Bài 29 — UPSERT

Nếu ON CONFLICT DO UPDATE, DEFAULT updated_at có tự làm mới không?

**Gợi ý:** Không. Cần SET updated_at=... hoặc cơ chế khác.

### Bài 30 — Sequence khi UPSERT conflict

Vì sao ID mới có thể bị tiêu thụ dù nhánh DO UPDATE được chạy?

**Gợi ý:** Sequence có thể được lấy trong giai đoạn thử INSERT trước khi phát hiện conflict.

### Bài 31 — Identity và bảo mật

Vì sao một API dùng ID liên tiếp vẫn phải xác thực quyền truy cập?

**Gợi ý:** Đoán ID không được phép đồng nghĩa truy cập hợp pháp; phải kiểm tra authorization.

### Bài 32 — Giá bán thay đổi

Bảng products.price đã tăng, nhưng line_total của đơn cũ dùng unit_price đã lưu. Vì sao đây có thể là thiết kế đúng?

**Gợi ý:** Giá tại thời điểm mua là snapshot lịch sử, không phải giá hiện hành của danh mục.

### Bài 33 — Công thức total có chiết khấu

Nếu cần total=quantity*unit_price-discount, cần kiểm tra gì trước khi sửa generated expression?

**Gợi ý:** Discount là dữ liệu cùng hàng hay từ hệ thống ngoài, NULL/constraints, migration và lịch sử hóa đơn.

### Bài 34 — COPY import

Vì sao COPY dữ liệu có identity IDs tường minh cần thận trọng ngay cả khi cột là ALWAYS?

**Gợi ý:** COPY có quy tắc ghi giá trị identity được cung cấp khác INSERT thông thường; có thể ghi ID và cần kiểm soát trùng/sequence.

### Bài 35 — JSON null

API không gửi stock và API gửi `"stock": null` có thể tạo kết quả DB khác nhau như thế nào?

**Gợi ý:** SQL bỏ cột dùng default; SQL bind NULL tường minh không dùng default.

### Bài 36 — BIGINT

Khi nào chọn BIGINT cho identity thay INTEGER?

**Gợi ý:** Dự báo số hàng dài hạn, tốc độ ghi, phạm vi kiểu và chi phí lưu trữ.

### Bài 37 — Dữ liệu hiển thị vs mã ID

Tại sao không nên dùng identity để tạo số đơn có yêu cầu pháp lý “không có khoảng trống”?

**Gợi ý:** Sequence có thể bỏ số do rollback/conflict, nên cần quy trình đánh số riêng.

### Bài 38 — Cột email chuẩn hóa

Đề xuất generated column lưu `lower(btrim(email_raw))` và unique constraint nếu nghiệp vụ cho phép.

**Gợi ý:** `email_key TEXT GENERATED ALWAYS AS (lower(btrim(email_raw))) STORED UNIQUE` và chính sách canonicalization thống nhất.

### Bài 39 — ALTER DEFAULT

Sau khi SET DEFAULT status='new', các hàng cũ có status='draft' có tự đổi không?

**Gợi ý:** Không. DEFAULT chỉ áp dụng khi các thao tác ghi dùng default.

### Bài 40 — Thiết kế hệ thống

Chọn cơ chế phù hợp:

- `created_at</BT> lúc tạo.
- `updated_at</BT> khi sửa.
- `id</BT> số được DB cấp.
- `line_total</BT> cùng hàng.
- `order_total</BT> tổng từ nhiều dòng.

**Gợi ý:** DEFAULT; service/trigger; IDENTITY; generated column; aggregate/transaction/thiết kế đồng bộ.

## Kết luận

PostgreSQL có ba cơ chế thường bị gọi chung là “tự sinh giá trị”, nhưng **giải quyết ba nhiệm vụ khác nhau**:

- **`DEFAULT`** giúp điền trạng thái, số lượng hoặc thời điểm ban đầu khi một câu INSERT không cung cấp giá trị. Nó **không thay NULL tường minh**, không tự cập nhật khi hàng thay đổi và không bảo đảm giá trị luôn đúng nếu thiếu constraint.
- **`GENERATED ALWAYS/BY DEFAULT AS IDENTITY`** sử dụng sequence để cấp ID số. `ALWAYS` hạn chế việc nhập ID tường minh trong INSERT, còn `BY DEFAULT` cho phép linh hoạt hơn. Sequence an toàn cho cấp số đồng thời nhưng **có thể có khoảng trống, không rollback số đã cấp và không bảo đảm thứ tự COMMIT**.
- **Generated columns** tính dữ liệu từ biểu thức trên cùng hàng, như `quantity * unit_price`. Với `STORED`, giá trị được tính khi ghi và lưu lại; phiên bản PostgreSQL mới còn hỗ trợ `VIRTUAL`. Biểu thức phải tuân thủ các giới hạn như tính immutable và không thể thay một truy vấn tổng hợp nhiều hàng.

Trong thao tác thay đổi dữ liệu, hãy ưu tiên `INSERT ... RETURNING` để lấy ID thực, dùng `DEFAULT` có chủ đích thay vì truyền NULL tràn lan, kiểm soát `OVERRIDING</BT> và sequence khi import, đồng thời tách việc tính cùng hàng khỏi workflow nhiều bảng. Constraints, transaction, authorization và kế hoạch migration vẫn cần thiết ngay cả khi database đã tự điền nhiều giá trị.

Chọn đúng cơ chế giúp câu INSERT gọn hơn, giảm lỗi đồng bộ giữa ứng dụng và PostgreSQL, đồng thời giữ dữ liệu có ý nghĩa và có khả năng mở rộng trong hệ thống thực tế.
