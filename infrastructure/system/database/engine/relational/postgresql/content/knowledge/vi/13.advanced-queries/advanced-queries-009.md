# CTE thay đổi dữ liệu và luồng dữ liệu qua RETURNING trong PostgreSQL

Một truy vấn PostgreSQL không chỉ dùng `WITH` để tạo bảng kết quả tạm cho `SELECT`. Bên trong *common table expression* (CTE), PostgreSQL còn cho phép chạy các lệnh **`INSERT`, `UPDATE`, `DELETE`** và ở những phiên bản hỗ trợ, các dạng thay đổi dữ liệu khác. Khi kết hợp với **`RETURNING`**, kết quả của bước thay đổi trước có thể được chuyển trực tiếp cho bước kế tiếp **trong cùng một câu lệnh SQL**.

Các bài toán thực tế thường gặp:

- Tạo một khách hàng rồi dùng ngay `customer_id` vừa sinh để tạo đơn hàng.
- Chuyển đơn từ `pending` sang `paid` và ghi lịch sử cho **đúng những đơn thực sự đã đổi trạng thái**.
- Xóa những bản ghi đủ điều kiện và chuyển nội dung đã xóa sang bảng lưu trữ.
- Giảm số lượng tồn kho với điều kiện an toàn, sau đó ghi một dòng biến động kho.
- Thay đổi dữ liệu nghiệp vụ và tạo sự kiện **transactional outbox** trong cùng một thao tác nguyên tử.

Tuy nhiên, data-modifying CTE có những quy tắc rất quan trọng: **các bước thay đổi dữ liệu chạy đến hết**, **thứ tự thực thi của các nhánh cùng cấp không được cam kết**, các bước dùng **cùng snapshot của câu lệnh**, và **không được cố tác động cùng một hàng hai lần trong một statement**. Hiểu rõ các quy tắc đó là điều kiện để viết SQL vừa ngắn gọn vừa đúng về giao dịch.

## 1. Nhắc lại CTE và RETURNING

Một CTE được khai báo bằng `WITH`:

~~~sql
WITH active_customers AS (
    SELECT customer_id, full_name
    FROM customers
    WHERE is_active = true
)
SELECT *
FROM active_customers;
~~~

Ở ví dụ này, CTE `active_customers` là nguồn hàng tạm để truy vấn ngoài đọc. Nó **không sửa dữ liệu**.

Với data-modifying CTE, thân CTE là một lệnh thay đổi dữ liệu:

~~~sql
WITH changed AS (
    UPDATE orders
    SET status = 'paid'
    WHERE order_id = 101
    RETURNING order_id, status
)
SELECT order_id, status
FROM changed;
~~~

Ở đây:

1. `UPDATE` tìm hàng đơn 101 và thay đổi trạng thái nếu có hàng khớp.
2. `RETURNING` trả về các giá trị từ hàng thực sự được cập nhật.
3. Tên CTE `changed` trở thành **nguồn dữ liệu dạng bảng** cho câu `SELECT` bên ngoài.
4. Nếu không có hàng nào được cập nhật, `changed` trả **0 hàng**.

Khác biệt then chốt là `changed` **không phải một bản sao của bảng `orders`**. Nó chỉ chứa những cột và những hàng mà `RETURNING` tạo ra.

### Các lệnh có RETURNING

PostgreSQL hỗ trợ `RETURNING` trên các lệnh thay đổi dữ liệu như:

| Lệnh | Ý nghĩa của dữ liệu trả về |
| --- | --- |
| `INSERT ... RETURNING` | Giá trị của hàng đã chèn, gồm cả ID/default được sinh |
| `UPDATE ... RETURNING` | Giá trị hàng sau cập nhật cho các biểu thức được trả về |
| `DELETE ... RETURNING` | Giá trị của hàng bị xóa, hữu ích để ghi lưu trữ/audit |
| `MERGE ... RETURNING` | Khả năng tùy phiên bản PostgreSQL; phải kiểm tra server và cú pháp tài liệu tương ứng |

Bài học dùng `INSERT`, `UPDATE` và `DELETE` để tránh phụ thuộc những khác biệt `MERGE` giữa các major version.

## 2. Sơ đồ luồng dữ liệu qua RETURNING

~~~mermaid
flowchart TD
    A["Bảng nghiệp vụ hiện tại"] --> B["UPDATE / INSERT / DELETE"]
    B --> C["RETURNING các hàng đã thay đổi"]
    C --> D["CTE: changed_rows"]
    D --> E["INSERT vào audit / archive / outbox"]
    D --> F["SELECT trả kết quả cho ứng dụng"]
    E --> G["Một statement nguyên tử"]
    F --> G
~~~

Điểm cần hiểu là mũi tên từ `changed_rows` sang bước sau **đi qua dữ liệu `RETURNING`**, không đi qua việc đọc lại bảng gốc trong cùng câu SQL.

Ví dụ:

~~~sql
WITH newly_inserted AS (
    INSERT INTO customers (full_name)
    VALUES ('An')
    RETURNING customer_id, full_name
)
SELECT customer_id, full_name
FROM newly_inserted;
~~~

Nếu `customer_id` được sinh tự động, CTE trả ID mới trực tiếp. Không phải gọi `SELECT MAX(customer_id)` hoặc thực hiện một truy vấn phỏng đoán hàng nào “vừa được tạo”.

## 3. Dựng bộ dữ liệu thực hành

Các ví dụ còn lại sử dụng schema riêng `dml_cte_lab` trong **database PostgreSQL dành cho học tập**. Script tạo lại schema và xóa dữ liệu cũ bằng `DROP SCHEMA ... CASCADE`, vì vậy **chỉ chạy khi đã xác nhận đúng database lab và không có dữ liệu cần giữ**.

### 3.1. Tạo schema và các bảng

~~~sql
-- CHỈ CHẠY TRONG DATABASE LAB SỞ HỮU RIÊNG.
DROP SCHEMA IF EXISTS dml_cte_lab CASCADE;
CREATE SCHEMA dml_cte_lab;

CREATE TABLE dml_cte_lab.customers (
    customer_id bigint GENERATED BY DEFAULT
        AS IDENTITY (START WITH 1000) PRIMARY KEY,
    email text NOT NULL UNIQUE,
    full_name text NOT NULL
);

CREATE TABLE dml_cte_lab.orders (
    order_id bigint GENERATED BY DEFAULT
        AS IDENTITY (START WITH 2000) PRIMARY KEY,
    customer_id bigint NOT NULL
        REFERENCES dml_cte_lab.customers(customer_id),
    status text NOT NULL
        CHECK (status IN ('pending', 'paid', 'cancelled')),
    total numeric(12, 2) NOT NULL
        CHECK (total >= 0),
    created_at timestamptz NOT NULL DEFAULT now(),
    paid_at timestamptz
);

-- Cố ý KHÔNG đặt FK từ audit.order_id tới orders:
-- thông tin audit cần tồn tại ngay cả khi đơn được xóa.
CREATE TABLE dml_cte_lab.order_audit (
    audit_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_id bigint NOT NULL,
    action text NOT NULL,
    previous_status text,
    new_status text,
    amount numeric(12, 2),
    recorded_at timestamptz NOT NULL DEFAULT now()
);

-- Transactional outbox: sự kiện được ghi cùng dữ liệu nghiệp vụ.
CREATE TABLE dml_cte_lab.outbox_events (
    event_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    aggregate_type text NOT NULL,
    aggregate_id bigint NOT NULL,
    event_name text NOT NULL,
    payload jsonb NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now(),
    published_at timestamptz
);

-- Bảng lưu lịch sử đơn đã xóa/được chuyển đi.
CREATE TABLE dml_cte_lab.orders_archive (
    order_id bigint PRIMARY KEY,
    customer_id bigint NOT NULL,
    status text NOT NULL,
    total numeric(12, 2) NOT NULL,
    created_at timestamptz NOT NULL,
    paid_at timestamptz,
    archived_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE dml_cte_lab.inventory (
    product_id integer PRIMARY KEY,
    quantity integer NOT NULL CHECK (quantity >= 0)
);

CREATE TABLE dml_cte_lab.inventory_movements (
    movement_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    product_id integer NOT NULL
        REFERENCES dml_cte_lab.inventory(product_id),
    delta integer NOT NULL CHECK (delta <> 0),
    quantity_after integer NOT NULL CHECK (quantity_after >= 0),
    recorded_at timestamptz NOT NULL DEFAULT now()
);
~~~

Thiết kế này phục vụ nhiều ví dụ độc lập:

- `customers` và `orders`: tạo dữ liệu cha–con, cập nhật trạng thái.
- `order_audit`: lưu bằng chứng thay đổi trạng thái.
- `outbox_events`: lưu sự kiện để một worker khác phát đi sau khi transaction commit.
- `orders_archive`: nhận các hàng bị xóa khỏi bảng hoạt động.
- `inventory` và `inventory_movements`: giảm tồn kho, đồng thời ghi biến động.

Cột ID dùng `GENERATED BY DEFAULT AS IDENTITY` cho phép nạp một số ID cố định ở phần seed, còn ID tự sinh về sau bắt đầu ở một dải khác để ví dụ có kết quả dễ kiểm tra. Với hệ thống production, cần kiểm soát sequence và tránh việc chèn ID thủ công không có chính sách rõ ràng.

### 3.2. Seed dữ liệu cố định

~~~sql
INSERT INTO dml_cte_lab.customers
    (customer_id, email, full_name)
VALUES
    (1, 'an@example.test',   'An'),
    (2, 'binh@example.test', 'Binh'),
    (3, 'chi@example.test',  'Chi');

INSERT INTO dml_cte_lab.orders
    (order_id, customer_id, status, total, created_at, paid_at)
VALUES
    (101, 1, 'pending',   120.00, '2026-11-01 08:00:00+00', NULL),
    (102, 1, 'paid',       75.00, '2026-11-02 08:00:00+00',
                                '2026-11-02 08:30:00+00'),
    (103, 2, 'pending',   200.00, '2026-11-03 08:00:00+00', NULL),
    (104, 3, 'cancelled',  40.00, '2026-11-04 08:00:00+00', NULL);

INSERT INTO dml_cte_lab.inventory
    (product_id, quantity)
VALUES
    (501, 8),
    (502, 0);
~~~

Kết quả ban đầu:

| order_id | customer_id | status | total |
| ---: | ---: | --- | ---: |
| 101 | 1 | pending | 120.00 |
| 102 | 1 | paid | 75.00 |
| 103 | 2 | pending | 200.00 |

Bảng `order_audit`, `outbox_events`, `orders_archive` và `inventory_movements` lúc đầu rỗng.

**Cách chạy bài:** trừ khi được ghi rõ là tạo dữ liệu mới, mỗi thí nghiệm thay đổi dữ liệu sẽ được bọc trong `BEGIN ... ROLLBACK` để không làm ảnh hưởng tới ví dụ tiếp theo. Khi muốn giữ kết quả thật trong lab, có thể thay `ROLLBACK` bằng `COMMIT` một cách có chủ đích; không làm điều đó với dữ liệu production.

## 4. INSERT ... RETURNING: lấy ID mới sinh

Bước cơ bản nhất là chèn một bản ghi và nhận khóa chính ngay trong cùng câu SQL.

~~~sql
INSERT INTO dml_cte_lab.customers
    (email, full_name)
VALUES
    ('dung@example.test', 'Dung')
RETURNING customer_id, email, full_name;
~~~

PostgreSQL trả về ID được sinh bởi identity column cùng email, tên. **Giá trị ID cụ thể có thể khác giữa các lần chạy** do sequence không bị rollback như dữ liệu bảng trong những trường hợp thông thường.

Nếu chỉ muốn thử:

~~~sql
BEGIN;

INSERT INTO dml_cte_lab.customers
    (email, full_name)
VALUES
    ('dung@example.test', 'Dung')
RETURNING customer_id, email;

ROLLBACK;
~~~

Sau rollback, hàng khách hàng được hoàn tác, nhưng giá trị sequence đã cấp có thể vẫn bị tiêu thụ. Không kỳ vọng lần INSERT sau phải tái sử dụng đúng số đó.

### Vì sao không dùng MAX(id) để tìm hàng vừa tạo?

Cách sau không đáng tin cậy trong hệ nhiều phiên:

~~~sql
-- KHÔNG dùng để suy ra ID vừa sinh.
SELECT MAX(customer_id)
FROM dml_cte_lab.customers;
~~~

Một transaction khác có thể vừa thêm bản ghi có ID lớn hơn; hoặc ID được cấp không phản ánh thứ tự commit. `RETURNING` lấy ID **từ chính thao tác INSERT** nên chính xác với những hàng mà lệnh của bạn đã chèn.

## 5. Data-modifying CTE đầu tiên: tạo khách hàng rồi tạo đơn

Kết hợp hai bước trong **một câu lệnh SQL**:

~~~sql
BEGIN;

WITH new_customer AS (
    INSERT INTO dml_cte_lab.customers
        (email, full_name)
    VALUES
        ('dung@example.test', 'Dung')
    RETURNING customer_id
)
INSERT INTO dml_cte_lab.orders
    (customer_id, status, total)
SELECT
    customer_id,
    'pending',
    0.00
FROM new_customer
RETURNING order_id, customer_id, status, total;

ROLLBACK;
~~~

Giải thích:

1. CTE `new_customer` thực hiện `INSERT` vào `customers`.
2. `RETURNING customer_id` tạo một luồng gồm ID của đúng khách hàng vừa thêm.
3. Câu `INSERT INTO orders ... SELECT ... FROM new_customer` lấy ID đó để tạo đơn.
4. `RETURNING` ở **lệnh INSERT chính** trả ID đơn và thông tin liên quan.
5. Nếu một ràng buộc hoặc thao tác nào đó gây lỗi, statement không được commit một nửa.
6. `ROLLBACK` giúp đưa dữ liệu trong lab về trước thử nghiệm.

### Luồng dữ liệu rõ ràng, không phải đọc lại bảng gốc

~~~mermaid
flowchart LR
    A["INSERT customers"] --> B["RETURNING customer_id"]
    B --> C["CTE new_customer"]
    C --> D["INSERT orders ... SELECT FROM new_customer"]
    D --> E["RETURNING order_id"]
~~~

Khóa mới chuyển trực tiếp từ `RETURNING`. Đây là cách quan trọng khi lệnh đầu sinh dữ liệu mà lệnh tiếp cần dùng.

Không cần viết:

~~~sql
-- Không nên đọc lại để phỏng đoán khách hàng vừa tạo.
SELECT customer_id
FROM dml_cte_lab.customers
ORDER BY customer_id DESC
LIMIT 1;
~~~

Cách đó có thể đọc nhầm khách hàng khác và không biểu diễn quan hệ nhân quả giữa hai thao tác.

## 6. UPDATE ... RETURNING: chỉ nhận những hàng thực sự được đổi

Khi chuyển trạng thái đơn hàng, ta thường muốn biết **đơn nào thực sự đã đi qua trạng thái cho phép**.

~~~sql
BEGIN;

UPDATE dml_cte_lab.orders
SET
    status = 'paid',
    paid_at = now()
WHERE order_id = 101
  AND status = 'pending'
RETURNING
    order_id,
    customer_id,
    status,
    total,
    paid_at;

ROLLBACK;
~~~

Với seed, đơn 101 đủ điều kiện và `RETURNING` trả **một hàng**.

Ngược lại:

~~~sql
UPDATE dml_cte_lab.orders
SET status = 'paid'
WHERE order_id = 102
  AND status = 'pending'
RETURNING order_id;
~~~

trả **0 hàng**, vì đơn 102 vốn đã là `paid`. Việc lọc bằng trạng thái hiện tại hữu ích để tránh ghi lịch sử “chuyển sang paid” khi thật ra không có chuyển trạng thái phù hợp.

### RETURNING không tự chứng minh “giá trị đã khác”

Nếu viết:

~~~sql
UPDATE dml_cte_lab.orders
SET status = 'paid'
WHERE order_id = 102
RETURNING order_id, status;
~~~

lệnh vẫn có thể cập nhật một hàng, dù giá trị `status` trước và sau đều là `paid`. `RETURNING` trả **những hàng mà UPDATE xử lý**, không có nghĩa mọi cột bắt buộc đã thay đổi giá trị.

Nếu nghiệp vụ cần phát sự kiện đúng lúc chuyển trạng thái, hãy thêm điều kiện chuyển trạng thái vào `WHERE`, ví dụ `status = 'pending'`, cùng chính sách xử lý concurrency thích hợp.

## 7. UPDATE CTE rồi INSERT vào bảng audit

Bài toán: khi đơn 101 chuyển từ `pending` sang `paid`, lưu một dòng audit cho **chính đơn đã được cập nhật**.

~~~sql
BEGIN;

WITH changed_orders AS (
    UPDATE dml_cte_lab.orders AS o
    SET
        status = 'paid',
        paid_at = now()
    WHERE o.order_id = 101
      AND o.status = 'pending'
    RETURNING
        o.order_id,
        o.customer_id,
        o.status,
        o.total
)
INSERT INTO dml_cte_lab.order_audit
    (order_id, action, previous_status, new_status, amount)
SELECT
    c.order_id,
    'status_changed',
    'pending',
    c.status,
    c.total
FROM changed_orders AS c
RETURNING
    audit_id,
    order_id,
    previous_status,
    new_status,
    amount;

SELECT order_id, status
FROM dml_cte_lab.orders
WHERE order_id = 101;

SELECT audit_id, order_id, action, new_status
FROM dml_cte_lab.order_audit
ORDER BY audit_id;

ROLLBACK;
~~~

**Kết quả trong transaction trước rollback:**

- Đơn 101 có `status = 'paid'`.
- Một hàng mới trong `order_audit` có `order_id = 101`, `previous_status = 'pending'` và `new_status = 'paid'`.
- Câu `INSERT INTO order_audit` sẽ chèn **0 hàng** nếu CTE `changed_orders` không trả hàng nào.

### Tại sao ví dụ ghi previous_status = 'pending'?

Điều kiện `WHERE o.status = 'pending'` đảm bảo mọi hàng được cập nhật đã ở trạng thái `pending` ngay trước thao tác hợp lệ này, nên ta có thể ghi giá trị đó như một quy tắc nghiệp vụ xác định.

Với thao tác đổi từ **nhiều trạng thái đầu vào**, không được ghi cứng `'pending'` cho mọi hàng. Cần cơ chế lấy giá trị trước thay đổi phù hợp phiên bản PostgreSQL và thiết kế concurrency, hoặc tách audit vào trigger được thiết kế đúng. `UPDATE ... RETURNING o.status` thông thường cho giá trị **sau cập nhật**, không tự cung cấp một cột old_status theo tên đó.

### Sự liên kết được bảo đảm bởi hàng trả về

Một thiết kế hai statement ở application:

~~~text
UPDATE orders ...
INSERT INTO order_audit ...
~~~

cũng có thể đúng nếu nằm trong một transaction với logic kiểm tra row count/returning phù hợp. Nhưng nếu ứng dụng chỉ cập nhật rồi **chèn audit một cách vô điều kiện**, nó có thể ghi sai lịch sử cho bản ghi đã ở trạng thái đích hoặc không tồn tại.

Data-modifying CTE giúp biểu diễn rõ: **chỉ audit những hàng thực sự đi ra từ UPDATE ... RETURNING**.

## 8. Kết hợp hai INSERT phụ thuộc cùng một UPDATE

Một tình huống thực tế: khi đơn chuyển `paid`, ta muốn đồng thời:

- Ghi lịch sử vào `order_audit`.
- Ghi sự kiện vào `outbox_events` để worker bên ngoài xử lý sau.
- Trả về ID audit và ID event cho ứng dụng.

~~~sql
BEGIN;

WITH transitioned AS (
    UPDATE dml_cte_lab.orders AS o
    SET
        status = 'paid',
        paid_at = now()
    WHERE o.order_id = 103
      AND o.status = 'pending'
    RETURNING
        o.order_id,
        o.customer_id,
        o.status,
        o.total
),
audit_written AS (
    INSERT INTO dml_cte_lab.order_audit
        (order_id, action, previous_status, new_status, amount)
    SELECT
        t.order_id,
        'status_changed',
        'pending',
        t.status,
        t.total
    FROM transitioned AS t
    RETURNING audit_id, order_id
),
event_written AS (
    INSERT INTO dml_cte_lab.outbox_events
        (aggregate_type, aggregate_id, event_name, payload)
    SELECT
        'order',
        t.order_id,
        'order.paid',
        jsonb_build_object(
            'order_id', t.order_id,
            'customer_id', t.customer_id,
            'status', t.status,
            'total', t.total
        )
    FROM transitioned AS t
    RETURNING event_id, aggregate_id
)
SELECT
    a.order_id,
    a.audit_id,
    e.event_id
FROM audit_written AS a
JOIN event_written AS e
    ON e.aggregate_id = a.order_id;

ROLLBACK;
~~~

Trường hợp seed có một đơn 103 hợp lệ:

1. `transitioned` trả một hàng của đơn 103.
2. `audit_written` nhận dữ liệu đó và chèn một hàng audit.
3. `event_written` nhận **cùng luồng RETURNING của transitioned** và chèn một hàng outbox.
4. Câu `SELECT` cuối ghép hai ID vừa tạo qua `order_id`.
5. Nếu một bước ghi thất bại, không có trạng thái commit một phần của statement.

**Điểm tinh tế:** `audit_written` và `event_written` không cần chạy theo thứ tự tuyến tính “audit trước, event sau”; chúng đọc cùng nguồn `transitioned` và ghi vào **hai bảng khác nhau**. Không dựa vào thứ tự vật lý của hai nhánh. Nếu cần dữ liệu chỉ có sau khi ghi audit (ví dụ `audit_id`), cho nhánh tiếp theo **đọc trực tiếp `audit_written RETURNING`** để thể hiện phụ thuộc thực sự.

### Ví dụ phụ thuộc nhiều tầng

~~~sql
WITH inserted_audit AS (
    INSERT INTO dml_cte_lab.order_audit
        (order_id, action)
    VALUES
        (101, 'manual_review')
    RETURNING audit_id, order_id
),
inserted_event AS (
    INSERT INTO dml_cte_lab.outbox_events
        (aggregate_type, aggregate_id, event_name, payload)
    SELECT
        'order',
        a.order_id,
        'audit.created',
        jsonb_build_object('audit_id', a.audit_id)
    FROM inserted_audit AS a
    RETURNING event_id, payload
)
SELECT event_id, payload
FROM inserted_event;
~~~

Ở đây `inserted_event` nhận `audit_id` vừa sinh **qua `RETURNING` của inserted_audit**, không đoán ID bằng một truy vấn `MAX(audit_id)`. Khi tự chạy lab, bọc statement này bằng `BEGIN ... ROLLBACK` để giữ nguyên seed.

## 9. DELETE ... RETURNING: lấy chính hàng vừa xóa

`DELETE ... RETURNING` trả dữ liệu của **những hàng bị xóa**. Đây là nền tảng cho thao tác chuyển dữ liệu từ bảng hoạt động sang bảng lưu trữ.

Ví dụ đơn giản:

~~~sql
BEGIN;

DELETE FROM dml_cte_lab.orders
WHERE order_id = 104
  AND status = 'cancelled'
RETURNING
    order_id,
    customer_id,
    status,
    total,
    created_at,
    paid_at;

ROLLBACK;
~~~

Trong transaction, đơn 104 không còn trong `orders` và các cột của nó xuất hiện trong output `RETURNING`. Sau rollback, hàng lại tồn tại.

**Không nhầm `RETURNING` với một truy vấn `SELECT` đọc dữ liệu sau khi đã xóa.** `DELETE` là thao tác thay đổi; `RETURNING` là output của chính thao tác đó.

## 10. Chuyển dữ liệu sang archive trong một câu lệnh

Ví dụ: chuyển các đơn `cancelled` sang `orders_archive` rồi xóa khỏi bảng hoạt động.

~~~sql
BEGIN;

WITH moved AS (
    DELETE FROM dml_cte_lab.orders
    WHERE status = 'cancelled'
    RETURNING
        order_id,
        customer_id,
        status,
        total,
        created_at,
        paid_at
)
INSERT INTO dml_cte_lab.orders_archive
    (order_id, customer_id, status, total, created_at, paid_at)
SELECT
    order_id,
    customer_id,
    status,
    total,
    created_at,
    paid_at
FROM moved
RETURNING order_id, status, archived_at;

-- Quan sát sau khi câu chuyển hoàn tất:
SELECT order_id
FROM dml_cte_lab.orders
WHERE order_id = 104;

SELECT order_id, status, total
FROM dml_cte_lab.orders_archive
WHERE order_id = 104;

ROLLBACK;
~~~

Với seed, `moved` có một hàng (đơn 104). Câu INSERT chính nhận hàng từ `moved` và ghi sang archive.

### Tại sao dùng DELETE ... RETURNING thay cho SELECT rồi DELETE?

Một quy trình ngây thơ:

~~~text
SELECT * FROM orders WHERE status = 'cancelled';
INSERT INTO orders_archive ...;
DELETE FROM orders WHERE status = 'cancelled';
~~~

có thể gặp các vấn đề nếu được chạy thành nhiều statement riêng không được phối hợp:

- Hàng có thể bị đổi trạng thái giữa bước SELECT và DELETE.
- INSERT archive có thể thành công nhưng DELETE lỗi hoặc ngược lại nếu thiếu transaction.
- Điều kiện ở các câu SQL có thể khác nhau, khiến số hàng archive không khớp số hàng xóa.
- Có thể đọc nhầm tập hàng không còn đủ điều kiện ở thời điểm xóa thực tế.

Với `DELETE ... RETURNING`, **tập hàng chuyển đi chính là tập hàng DELETE đã xử lý**. Nếu INSERT archive vi phạm unique/constraint, toàn bộ statement lỗi và thao tác DELETE không được commit riêng lẻ.

### Cần chú ý foreign key và vòng đời dữ liệu

Ví dụ lab không có bảng con tham chiếu `orders.order_id`. Trong hệ thống thật, xóa đơn có thể bị FK của `order_items` chặn, hoặc cascade xóa nhiều dữ liệu khác. Một thao tác archive phải tính tới **toàn bộ quan hệ tham chiếu**, chính sách lưu trữ và yêu cầu tuân thủ. Không coi CTE là cách bỏ qua FK.

## 11. Điều kiện cập nhật an toàn khi giảm tồn kho

Giả sử sản phẩm 501 còn `quantity = 8`, cần xuất kho 3 đơn vị.

Một cách không an toàn là:

~~~text
SELECT quantity FROM inventory WHERE product_id = 501;
-- Ứng dụng thấy 8 rồi quyết định trừ 3.
UPDATE inventory SET quantity = 5 WHERE product_id = 501;
~~~

Giữa hai statement, một transaction khác có thể đã đổi tồn kho. Nếu không đồng bộ đúng, ứng dụng có thể ghi đè hoặc đưa ra quyết định dựa trên giá trị cũ.

Thay bằng cập nhật **có điều kiện ngay trên hàng**:

~~~sql
BEGIN;

UPDATE dml_cte_lab.inventory
SET quantity = quantity - 3
WHERE product_id = 501
  AND quantity >= 3
RETURNING product_id, quantity AS quantity_after;

ROLLBACK;
~~~

Ở dữ liệu ban đầu, `quantity_after = 5`.

Nếu số lượng còn lại nhỏ hơn 3, `WHERE quantity >= 3` không khớp và `RETURNING` trả 0 hàng. Cộng với `CHECK(quantity >= 0)`, thiết kế này thể hiện rõ quy tắc không xuất kho âm.

### Tại sao hiệu quả khi có ghi đồng thời?

PostgreSQL quản lý khóa hàng và tính nhất quán của UPDATE. Với các mức isolation thông dụng, khi hai transaction cùng tìm cách cập nhật một hàng, PostgreSQL phối hợp việc chờ khóa/kiểm tra điều kiện theo cơ chế MVCC. Điều kiện `quantity >= 3` trong chính `UPDATE` đáng tin cậy hơn quy trình **đọc số lượng rồi ghi đè một giá trị tính từ bản đọc cũ**.

Không nên suy rằng mọi trường hợp concurrency phức tạp đều được giải quyết chỉ bởi một câu UPDATE: mức isolation, deadlock, serialization failure, nhiều sản phẩm và quy tắc xuyên hàng vẫn cần được thiết kế riêng.

## 12. UPDATE tồn kho và ghi movement qua RETURNING

Mở rộng bước giảm kho: chỉ ghi biến động khi cập nhật tồn kho đã thành công.

~~~sql
BEGIN;

WITH stock_changed AS (
    UPDATE dml_cte_lab.inventory AS i
    SET quantity = i.quantity - 3
    WHERE i.product_id = 501
      AND i.quantity >= 3
    RETURNING
        i.product_id,
        i.quantity AS quantity_after
)
INSERT INTO dml_cte_lab.inventory_movements
    (product_id, delta, quantity_after)
SELECT
    s.product_id,
    -3,
    s.quantity_after
FROM stock_changed AS s
RETURNING
    movement_id,
    product_id,
    delta,
    quantity_after;

ROLLBACK;
~~~

Kết quả trong transaction: một hàng movement có `product_id = 501`, `delta = -3`, `quantity_after = 5`.

Nếu thử với sản phẩm 502, vốn có `quantity = 0`:

~~~sql
WITH stock_changed AS (
    UPDATE dml_cte_lab.inventory AS i
    SET quantity = i.quantity - 3
    WHERE i.product_id = 502
      AND i.quantity >= 3
    RETURNING i.product_id, i.quantity
)
INSERT INTO dml_cte_lab.inventory_movements
    (product_id, delta, quantity_after)
SELECT product_id, -3, quantity
FROM stock_changed
RETURNING movement_id;
~~~

`stock_changed` không trả hàng, do đó INSERT movement **cũng không chèn hàng**.

Tuy nhiên, đây chỉ là ví dụ về **một lần xử lý yêu cầu**. Nếu cùng yêu cầu được gửi lại hai lần, hệ thống có thể trừ kho hai lần. Cần thêm idempotency key/unique constraint theo thiết kế nghiệp vụ để chống xử lý trùng, không coi `WITH` hay `RETURNING` tự động cung cấp idempotency.

## 13. RETURNING có thể trả biểu thức, không chỉ cột

`RETURNING` nhận danh sách biểu thức tương tự `SELECT`.

~~~sql
BEGIN;

UPDATE dml_cte_lab.orders
SET
    total = total + 10.00
WHERE order_id = 101
RETURNING
    order_id,
    total,
    total * 0.10 AS ten_percent_reference,
    status,
    now() AS statement_time;

ROLLBACK;
~~~

`total` trong ví dụ `UPDATE ... RETURNING` là giá trị **sau cập nhật**, nên thành 130.00 với seed. `total * 0.10` được tính từ giá trị 130.00. Cột `ten_percent_reference` chỉ minh họa biểu thức, không phải công thức thuế/phí có thể áp dụng cho mọi sản phẩm.

Có thể tạo JSON:

~~~sql
BEGIN;

UPDATE dml_cte_lab.orders AS o
SET status = 'paid', paid_at = now()
WHERE o.order_id = 101
  AND o.status = 'pending'
RETURNING
    o.order_id,
    jsonb_build_object(
        'order_id', o.order_id,
        'customer_id', o.customer_id,
        'status', o.status,
        'total', o.total
    ) AS event_payload;

ROLLBACK;
~~~

Khi output được ứng dụng hoặc CTE khác sử dụng, việc trả JSON có thể giảm bước tự dựng payload không nhất quán ở application. Tuy nhiên dữ liệu trong JSON phải có schema sự kiện và quy tắc versioning phù hợp.

## 14. Quy tắc cốt lõi: data-modifying CTE luôn chạy đến hết

Đây là điểm khác quan trọng với nhiều `SELECT` CTE.

Ví dụ:

~~~sql
BEGIN;

WITH inserted AS (
    INSERT INTO dml_cte_lab.order_audit (order_id, action)
    VALUES
        (101, 'sample_a'),
        (102, 'sample_b')
    RETURNING audit_id, order_id
)
SELECT audit_id
FROM inserted
LIMIT 1;

SELECT COUNT(*) AS audit_rows
FROM dml_cte_lab.order_audit;

ROLLBACK;
~~~

Câu `SELECT ... LIMIT 1` chỉ **trả một hàng**, nhưng CTE `INSERT` vẫn thực hiện **toàn bộ hai hàng**. Trong transaction, số hàng audit tăng 2, không phải 1.

Điều này khác với một số tình huống `SELECT` CTE, nơi PostgreSQL có thể chỉ tính những hàng mà truy vấn cha cần dùng.

**Không dùng `LIMIT` ngoài để kiểm soát số hàng bị UPDATE/DELETE/INSERT bởi CTE.** Muốn giới hạn số hàng thay đổi, phải xây điều kiện chọn hàng một cách có chủ đích **trong nguồn của thao tác DML**, với thứ tự và cơ chế concurrency rõ ràng.

### CTE thay đổi dữ liệu không có RETURNING

PostgreSQL cho phép một data-modifying CTE không có `RETURNING`:

~~~sql
BEGIN;

WITH touched AS (
    UPDATE dml_cte_lab.orders
    SET total = total + 1.00
    WHERE order_id = 101
)
SELECT 'executed' AS result;

ROLLBACK;
~~~

Lệnh `UPDATE` vẫn thực thi dù `SELECT` ngoài không đọc dữ liệu của `touched`. Nhưng vì không có `RETURNING`, `touched` **không hình thành một bảng kết quả để các bước sau tham chiếu**.

Do đó, khi muốn nối luồng dữ liệu giữa các bước, `RETURNING` là thành phần cần thiết, không phải trang trí.

## 15. Quy tắc snapshot: CTE cùng câu lệnh không thấy thay đổi của nhau qua bảng gốc

Đây là chỗ dễ hiểu sai nhất khi mới dùng data-modifying CTE.

Các thành phần thay đổi dữ liệu trong một câu `WITH` và truy vấn chính chạy dưới **cùng snapshot của câu lệnh**. Vì vậy, không nên kỳ vọng một `SELECT` khác trong cùng statement đọc lại bảng gốc và tự nhìn thấy những thay đổi do CTE cùng statement thực hiện.

Hãy xem:

~~~sql
BEGIN;

WITH changed AS (
    UPDATE dml_cte_lab.orders AS o
    SET status = 'paid'
    WHERE o.order_id = 101
      AND o.status = 'pending'
    RETURNING o.order_id, o.status
)
SELECT
    changed.order_id,
    changed.status AS status_from_returning,
    (
        SELECT original.status
        FROM dml_cte_lab.orders AS original
        WHERE original.order_id = changed.order_id
    ) AS status_from_base_table
FROM changed;

ROLLBACK;
~~~

Theo cơ chế snapshot của PostgreSQL, ví dụ này có thể trả:

| order_id | status_from_returning | status_from_base_table |
| ---: | --- | --- |
| 101 | paid | pending |

- `status_from_returning` là giá trị sau UPDATE do DML trả trực tiếp.
- `status_from_base_table` là giá trị từ snapshot của bảng gốc trong **cùng statement**, vốn không thấy thay đổi của DML CTE qua cách đọc bảng đó.

Nếu chạy **một statement SELECT riêng sau khi statement UPDATE đã kết thúc**, bên trong cùng transaction, phiên của bạn sẽ thấy những thay đổi của chính mình theo quy tắc giao dịch thông thường:

~~~sql
BEGIN;

WITH changed AS (
    UPDATE dml_cte_lab.orders
    SET status = 'paid'
    WHERE order_id = 101
      AND status = 'pending'
    RETURNING order_id
)
SELECT COUNT(*) AS rows_changed
FROM changed;

-- Đây là CÂU LỆNH KHÁC, sau câu UPDATE.
SELECT order_id, status
FROM dml_cte_lab.orders
WHERE order_id = 101;

ROLLBACK;
~~~

Câu SELECT thứ hai thấy `paid` trong transaction vì statement cập nhật trước đó đã hoàn tất.

### Quy tắc thiết kế

**Trong cùng một statement: nếu bước sau cần dữ liệu vừa thay đổi, đọc `RETURNING` của bước trước.** Không thiết kế pipeline bằng cách sửa bảng rồi hy vọng nhánh khác đọc lại bảng sẽ thấy trạng thái mới.

## 16. Thứ tự chạy giữa các CTE thay đổi dữ liệu không được cam kết

Nếu viết hai nhánh cùng cấp:

~~~sql
WITH first_change AS (
    UPDATE dml_cte_lab.orders
    SET status = 'paid'
    WHERE order_id = 101
    RETURNING order_id
),
second_change AS (
    INSERT INTO dml_cte_lab.order_audit (order_id, action)
    VALUES (101, 'logged')
    RETURNING audit_id
)
SELECT ...
~~~

việc một nhánh được **viết trước** nhánh kia không có nghĩa PostgreSQL hứa sẽ chạy nhánh trước rồi mới chạy nhánh sau theo thứ tự hiệu ứng mà bạn mong đợi. Các data-modifying CTE cùng statement được thực hiện với quy tắc snapshot chung; **thứ tự các thao tác thực tế là không nên dựa vào**.

Ngoài ra, nhánh `second_change` ở ví dụ chỉ ghi audit **vô điều kiện**; kể cả khi `first_change` cập nhật 0 hàng, audit vẫn có thể được chèn. Đây là lỗi nghiệp vụ.

### Cách đúng khi nhánh sau phụ thuộc kết quả nhánh trước

~~~sql
WITH first_change AS (
    UPDATE dml_cte_lab.orders
    SET status = 'paid'
    WHERE order_id = 101
      AND status = 'pending'
    RETURNING order_id, status
),
second_change AS (
    INSERT INTO dml_cte_lab.order_audit
        (order_id, action, new_status)
    SELECT
        order_id,
        'status_changed',
        status
    FROM first_change
    RETURNING audit_id, order_id
)
SELECT audit_id, order_id
FROM second_change;
~~~

Vì `second_change` đọc **`first_change RETURNING`**, dữ liệu được truyền một cách minh bạch. Không cần giả định về thứ tự vật lý giữa hai nhánh độc lập.

## 17. Không tác động cùng một hàng hai lần trong một statement

PostgreSQL cảnh báo rõ: **cố cập nhật cùng một hàng hai lần trong cùng một statement không được hỗ trợ theo cách có kết quả dự đoán đáng tin cậy**. Điều này gồm trường hợp vừa UPDATE vừa DELETE cùng một hàng ở các nhánh thay đổi dữ liệu.

Ví dụ **không nên viết hoặc chạy**:

~~~sql
-- PHẢN VÍ DỤ: hai nhánh UPDATE cùng order_id=101.
WITH a AS (
    UPDATE dml_cte_lab.orders
    SET total = total + 10
    WHERE order_id = 101
    RETURNING order_id
),
b AS (
    UPDATE dml_cte_lab.orders
    SET status = 'paid'
    WHERE order_id = 101
    RETURNING order_id
)
SELECT * FROM a;
~~~

Không thể dựa vào thứ tự viết `a` rồi `b` để có kết quả cuối cùng gồm cả hai thay đổi. **Tránh tác động trùng hàng**, kể cả khi điều kiện giữa hai CTE nhìn có vẻ độc lập về mặt cột.

### Gộp thành một UPDATE

~~~sql
BEGIN;

WITH changed AS (
    UPDATE dml_cte_lab.orders
    SET
        total = total + 10,
        status = 'paid',
        paid_at = now()
    WHERE order_id = 101
      AND status = 'pending'
    RETURNING order_id, status, total
)
SELECT * FROM changed;

ROLLBACK;
~~~

Mỗi hàng chỉ được UPDATE một lần; `RETURNING` mang cả trạng thái lẫn số tiền sau cập nhật.

Nếu hai thao tác thực sự cần diễn ra **tuần tự**, có thể dùng **hai statement riêng trong một transaction**, kiểm tra kết quả statement trước khi chạy statement sau. Một transaction không đồng nghĩa bắt buộc gộp mọi thao tác vào một statement.

## 18. Data-modifying CTE cần gắn với WITH của lệnh top-level

Một giới hạn cú pháp/ngữ nghĩa quan trọng: các lệnh thay đổi dữ liệu bên trong `WITH` được PostgreSQL hỗ trợ khi `WITH` thuộc **statement top-level**.

Hợp lệ:

~~~sql
WITH changed AS (
    DELETE FROM dml_cte_lab.orders
    WHERE order_id = 9999
    RETURNING order_id
)
SELECT order_id
FROM changed;
~~~

Hoặc:

~~~sql
WITH created AS (
    INSERT INTO dml_cte_lab.order_audit
        (order_id, action)
    VALUES
        (101, 'sample')
    RETURNING audit_id
)
SELECT audit_id
FROM created;
~~~

Không nên giả định có thể đặt tùy ý một CTE sửa dữ liệu sâu trong **subquery lồng nhau** như một bảng tạm thường. Các ràng buộc của PostgreSQL với data-modifying CTE khác với `SELECT` CTE, và DML trong `WITH` phải gắn với top-level statement theo quy tắc hỗ trợ.

Nếu chỉ cần bảng tạm để lọc hoặc tổng hợp, dùng `SELECT` CTE. Nếu cần sửa dữ liệu, tổ chức lệnh `WITH` ở tầng ngoài phù hợp.

## 19. Tính nguyên tử: một statement, một kết quả commit

Trong PostgreSQL, một câu SQL thay đổi dữ liệu chạy dưới transaction. Khi data-modifying CTE kết hợp UPDATE với INSERT audit:

~~~text
UPDATE orders
  → RETURNING
  → INSERT order_audit
~~~

các thao tác là một **statement nguyên tử**. Nếu một bước gây lỗi ràng buộc, không thể có trạng thái “UPDATE đã commit nhưng INSERT audit thất bại” chỉ vì chúng ở hai CTE của cùng statement.

Ví dụ:

~~~sql
BEGIN;

WITH changed AS (
    UPDATE dml_cte_lab.orders
    SET status = 'paid'
    WHERE order_id = 101
      AND status = 'pending'
    RETURNING order_id, status
)
INSERT INTO dml_cte_lab.order_audit
    (order_id, action, new_status)
SELECT order_id, 'status_changed', status
FROM changed;

ROLLBACK;
~~~

Toàn bộ ví dụ được rollback để giữ dữ liệu lab. Trong ứng dụng thật, muốn lưu kết quả phải commit transaction phù hợp.

### Atomicity không có nghĩa nghiệp vụ luôn đúng

Một statement có thể nhất quán về giao dịch nhưng vẫn sai logic:

- UPDATE không có điều kiện `status = 'pending'` và ghi sự kiện không đúng.
- INSERT vào outbox có payload sai khóa/tenant.
- Một nhánh INSERT không sử dụng hàng RETURNING nên ghi lịch sử dù UPDATE 0 hàng.
- Bảng audit thiếu constraint ngăn event trùng trong trường hợp retry.
- Một hành động xóa theo cascade ảnh hưởng nhiều bảng ngoài dự kiến.

**Atomicity bảo đảm không commit một nửa một statement bị lỗi; nó không thay thế việc mô tả đúng quy tắc nghiệp vụ.**

## 20. CTE thay đổi dữ liệu không thay thế transaction nhiều statement

Có lúc pipeline cần:

1. Kiểm tra quyền người dùng.
2. Khóa các hàng nghiệp vụ.
3. Cập nhật nhiều bảng theo điều kiện phức tạp.
4. Đọc lại/trả kết quả hoặc gọi logic ứng dụng.
5. Commit hoặc rollback đồng bộ.

Nếu khó biểu diễn đúng bằng một statement, dùng nhiều câu SQL trong một transaction vẫn là phương án hợp lệ:

~~~sql
BEGIN;

-- 1. Chọn hoặc khóa những hàng cần xử lý.
SELECT order_id, status
FROM dml_cte_lab.orders
WHERE order_id = 101
FOR UPDATE;

-- 2. Cập nhật với điều kiện nghiệp vụ.
UPDATE dml_cte_lab.orders
SET status = 'paid', paid_at = now()
WHERE order_id = 101 AND status = 'pending'
RETURNING order_id, status;

-- 3. Ứng dụng hoặc stored procedure kiểm tra row count,
-- rồi ghi audit/outbox nếu việc chuyển trạng thái thành công.

COMMIT;
~~~

Đây là **minh họa quy trình**, chưa phải một workflow hoàn chỉnh vì phần ghi audit/outbox cần được cài đặt để sử dụng đúng output và xử lý lỗi.

Điểm mạnh của transaction là các statement **chạy tuần tự theo chương trình** và có thể đọc kết quả từ các statement trước trong cùng transaction. Ngược lại, data-modifying CTE trong một statement có quy tắc snapshot chung và không nên được hiểu là chuỗi DML tuần tự theo thứ tự văn bản.

## 21. Xử lý 0 hàng RETURNING trong ứng dụng

Một điều kiện như:

~~~sql
UPDATE dml_cte_lab.orders
SET status = 'paid'
WHERE order_id = 101
  AND status = 'pending'
RETURNING order_id;
~~~

có thể trả:

- **1 hàng:** chuyển trạng thái thành công cho đơn 101.
- **0 hàng:** đơn không tồn tại hoặc trạng thái hiện tại không phải pending.
- **Lỗi:** có vấn đề constraint, lock, deadlock, quyền, serialization, kết nối...

Không được coi mọi trường hợp 0 hàng đều là lỗi database. Đó có thể là kết quả hợp lệ của điều kiện `WHERE`.

Một API có thể cần phân biệt:

- Không có đơn (`404` theo thiết kế API).
- Đơn đã thanh toán (`409` hoặc phản hồi idempotent, tùy nghiệp vụ).
- Đơn bị hủy, không được thanh toán.
- Một giao dịch khác vừa xử lý đơn, cần đọc lại trạng thái hoặc trả kết quả phù hợp.

Muốn phân biệt các trường hợp, thường cần **thêm truy vấn** hoặc cơ chế xử lý trạng thái ứng dụng; không suy từ số hàng 0 rằng tất cả đều là “không tồn tại”.

## 22. Kết hợp RETURNING với JDBC

Với PostgreSQL JDBC, dữ liệu trả về từ statement có `RETURNING` có thể được đọc qua `ResultSet`. Ví dụ Java:

~~~java
import java.math.BigDecimal;
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;

public static boolean markPaid(
    Connection connection,
    long orderId
) throws SQLException {
    String sql = """
        WITH changed AS (
            UPDATE dml_cte_lab.orders
            SET status = 'paid', paid_at = now()
            WHERE order_id = ?
              AND status = 'pending'
            RETURNING order_id, total
        )
        INSERT INTO dml_cte_lab.order_audit
            (order_id, action, previous_status, new_status, amount)
        SELECT
            order_id, 'status_changed', 'pending', 'paid', total
        FROM changed
        RETURNING order_id, amount
        """;

    try (PreparedStatement ps =
             connection.prepareStatement(sql)) {
        ps.setLong(1, orderId);

        try (ResultSet rs = ps.executeQuery()) {
            if (!rs.next()) {
                return false;
            }

            long updatedOrderId = rs.getLong("order_id");
            BigDecimal amount = rs.getBigDecimal("amount");

            // Thực tế nên trả DTO/kết quả nghiệp vụ thay vì in console.
            System.out.println(
                "Paid order " + updatedOrderId +
                " amount=" + amount
            );

            return true;
        }
    }
}
~~~

Đây là phương thức minh họa cho **một đơn** và không tự quản lý `commit`/`rollback` của connection. Trong ứng dụng thật, transaction boundary phải do lớp service quản lý nhất quán; không tự bật/tắt autocommit ngẫu nhiên khi connection đang được chia sẻ.

### Tại sao executeQuery()?

Mặc dù câu SQL có cả `UPDATE` và `INSERT`, lệnh top-level là `INSERT ... RETURNING` tạo một tập kết quả. Với pgJDBC thông dụng, `executeQuery()` cho phép đọc những hàng trả về. Nếu viết câu top-level không có result set, có thể dùng `executeUpdate()` hoặc `execute()` theo hợp đồng JDBC.

### Dùng parameter binding

Không nối `orderId` hoặc dữ liệu từ request trực tiếp vào câu SQL. `PreparedStatement` đưa giá trị qua tham số `?` và tránh lỗi injection từ dữ liệu được người dùng cung cấp. Tuy nhiên việc bind không thay thế kiểm tra quyền: lệnh SQL còn phải được giới hạn theo user/tenant đã xác thực ở lớp phù hợp.

## 23. Transactional outbox: thay đổi dữ liệu và ghi sự kiện cùng nhau

Bài toán phổ biến trong kiến trúc hướng sự kiện: đơn được thanh toán trong PostgreSQL, rồi một service muốn gửi thông báo tới message broker.

Nếu ứng dụng làm:

~~~text
1. UPDATE orders rồi COMMIT
2. Gửi event tới message broker
~~~

thì có thể gặp lỗi **đã commit đơn nhưng chưa gửi được event**.

Nếu đảo lại:

~~~text
1. Gửi event
2. UPDATE orders rồi COMMIT
~~~

thì có thể gặp lỗi **đã gửi event nhưng transaction database rollback**.

Mẫu **transactional outbox** đặt event vào một bảng trong cùng database/transaction với thay đổi nghiệp vụ:

~~~mermaid
flowchart TD
    A["UPDATE orders"] --> B["RETURNING order_id/status"]
    B --> C["INSERT outbox_events"]
    C --> D{"COMMIT transaction"}
    D -->|"Thành công"| E["Worker đọc outbox sau commit"]
    E --> F["Publish tới broker"]
    F --> G["Đánh dấu published_at"]
    D -->|"Rollback"| H["Không có thay đổi đơn hay event được commit"]
~~~

Ví dụ data-modifying CTE:

~~~sql
BEGIN;

WITH paid_orders AS (
    UPDATE dml_cte_lab.orders AS o
    SET
        status = 'paid',
        paid_at = now()
    WHERE o.order_id = 101
      AND o.status = 'pending'
    RETURNING
        o.order_id,
        o.customer_id,
        o.status,
        o.total
)
INSERT INTO dml_cte_lab.outbox_events
    (aggregate_type, aggregate_id, event_name, payload)
SELECT
    'order',
    p.order_id,
    'order.paid',
    jsonb_build_object(
        'order_id', p.order_id,
        'customer_id', p.customer_id,
        'total', p.total,
        'status', p.status
    )
FROM paid_orders AS p
RETURNING event_id, aggregate_id, event_name;

ROLLBACK;
~~~

Nếu muốn phát sự kiện thật, một worker độc lập phải đọc những event **đã commit**, gửi tới broker và quản lý retry/đánh dấu đã gửi.

### Outbox có bảo đảm exactly-once delivery không?

**Không mặc nhiên.** Một worker có thể gửi event thành công nhưng chết trước khi cập nhật `published_at`; lần chạy lại có thể gửi trùng. Vì vậy consumer thường cần **idempotency/deduplication** và thiết kế xử lý ít nhất một lần (*at-least-once*).

Điểm mà CTE giúp bảo đảm là **thay đổi nghiệp vụ và bản ghi outbox cùng nằm trong một statement/transaction nguyên tử**, không phải toàn bộ giao thức truyền tin bên ngoài có exactly-once.

## 24. UPDATE nhiều hàng và RETURNING như một tập dữ liệu

`RETURNING` không giới hạn một hàng. Nó trả **mỗi hàng** mà DML đã tác động theo điều kiện.

Ví dụ chuyển tất cả đơn pending thành cancelled trong lab:

~~~sql
BEGIN;

WITH cancelled AS (
    UPDATE dml_cte_lab.orders AS o
    SET status = 'cancelled'
    WHERE o.status = 'pending'
    RETURNING o.order_id, o.customer_id, o.status, o.total
)
INSERT INTO dml_cte_lab.order_audit
    (order_id, action, previous_status, new_status, amount)
SELECT
    order_id,
    'status_changed',
    'pending',
    status,
    total
FROM cancelled
RETURNING audit_id, order_id, new_status;

ROLLBACK;
~~~

Theo seed, có hai đơn pending (101 và 103). CTE `cancelled` trả **hai hàng**, và bảng audit nhận **hai hàng**.

Không nên giả định thứ tự các hàng trong `RETURNING` là thứ tự khóa chính hoặc thứ tự UPDATE/INSERT vật lý. Nếu cần output ổn định để đối chiếu, dùng một `SELECT` ngoài với `ORDER BY`.

Ví dụ:

~~~sql
WITH changed AS (
    UPDATE dml_cte_lab.orders
    SET status = 'cancelled'
    WHERE status = 'pending'
    RETURNING order_id, status
)
SELECT order_id, status
FROM changed
ORDER BY order_id;
~~~

Câu `SELECT` ngoài sắp các hàng RETURNING, nhưng không đổi thứ tự vật lý mà PostgreSQL dùng để cập nhật hàng.

## 25. DML CTE và SELECT CTE khác nhau ở điều gì?

| Tính chất | SELECT CTE | Data-modifying CTE |
| --- | --- | --- |
| Thân CTE | `SELECT` | `INSERT` / `UPDATE` / `DELETE` |
| Tác động dữ liệu | Không trực tiếp | Có |
| Tạo bảng kết quả | Kết quả SELECT | Chỉ thông qua `RETURNING` nếu có |
| Chạy nếu output không được đọc | Có thể phụ thuộc tối ưu/nhu cầu truy vấn cha | **Vẫn thực thi đến hết** |
| Chỉ lấy một phần với LIMIT bên ngoài | Có thể giới hạn số hàng cần tính trong một số kế hoạch | Không giới hạn số hàng DML thực hiện |
| Truyền dữ liệu giữa nhánh | Qua hàng SELECT | Qua hàng `RETURNING` |
| Gắn trong nested query | Linh hoạt hơn | Có giới hạn top-level cho data-modifying WITH |
| Thứ tự giữa các nhánh DML | Không liên quan nếu chỉ đọc | **Không được dựa vào thứ tự văn bản** |

Một nhầm lẫn phổ biến là coi `WITH a AS (UPDATE ...)` như “chạy UPDATE xong, rồi các CTE sau có thể SELECT bảng đã cập nhật”. Đúng hơn, nó tạo ra **một thao tác DML và một tập RETURNING** trong statement dùng chung snapshot.

## 26. Khóa, concurrency và những giới hạn cần hiểu

Data-modifying CTE không bypass hệ thống giao dịch của PostgreSQL. Các hàng bị UPDATE/DELETE vẫn chịu lock, MVCC, foreign key, trigger, unique constraint, RLS và các quy tắc isolation.

### Hai phiên cùng thanh toán một đơn

Giả sử hai phiên cùng chạy:

~~~sql
WITH paid AS (
    UPDATE dml_cte_lab.orders
    SET status = 'paid', paid_at = now()
    WHERE order_id = 101
      AND status = 'pending'
    RETURNING order_id
)
INSERT INTO dml_cte_lab.order_audit
    (order_id, action, new_status)
SELECT order_id, 'paid', 'paid'
FROM paid;
~~~

Trong tình huống thông thường ở mức `READ COMMITTED`, một phiên thực hiện cập nhật trước; phiên còn lại có thể phải chờ khóa hàng, sau đó kiểm tra lại điều kiện trên phiên bản hàng mới và nhận **0 hàng**, nên không chèn audit thêm.

Đây là ưu điểm của việc ràng buộc logic vào **điều kiện UPDATE** và **hàng RETURNING**. Tuy nhiên tại các mức isolation cao hơn, hệ thống có thể cần xử lý serialization failure/retry. Nếu nghiệp vụ phức tạp hoặc nhiều bảng liên quan, hãy thiết kế rõ transaction/locking/idempotency.

### Không tự bảo đảm không deadlock

Nếu một workflow cập nhật hai bảng theo thứ tự khác với một workflow khác, deadlock vẫn có thể xảy ra. Một statement dài không đồng nghĩa miễn nhiễm với deadlock. Ứng dụng phải phát hiện và xử lý các lỗi có thể retry theo chính sách an toàn.

### RETURNING không bypass quyền

Role dùng câu DML cần quyền INSERT/UPDATE/DELETE tương ứng, và muốn dùng `RETURNING` trên những cột cụ thể thường còn cần quyền `SELECT` thích hợp trên các cột đó. Row-level security có thể giới hạn những hàng mà DML được phép tác động/trả về. Đừng coi `RETURNING *` là cách lấy dữ liệu mà role vốn không được đọc.

## 27. Thao tác DELETE nhiều hàng có thể lan truyền

Khi một CTE dùng:

~~~sql
WITH removed AS (
    DELETE FROM some_parent_table
    WHERE ...
    RETURNING parent_id
)
INSERT INTO audit_table (...)
SELECT ...
FROM removed;
~~~

nó chỉ trả các hàng bị xóa bởi `DELETE` trên **bảng đích** `some_parent_table`. Nếu có `ON DELETE CASCADE` làm xóa tiếp hàng con ở bảng khác, `RETURNING` của parent **không tự chứa mọi hàng con bị xóa**.

Nếu cần lưu cả dữ liệu con để audit/archive, phải thiết kế quy trình riêng: cascade có được cho phép không, cần trigger audit ở bảng con không, dữ liệu có phải chuyển lưu trữ theo khóa cha hay không. Không kết luận “đã có RETURNING ở cha nên đã backup toàn bộ cây dữ liệu”.

### Không lẫn với TRUNCATE

`TRUNCATE` không cung cấp cùng luồng `DELETE ... RETURNING` theo từng hàng. `TRUNCATE ... CASCADE` là cơ chế khác, có thể tác động **toàn bảng phụ thuộc**, không phù hợp để thay thế một thao tác archive có kiểm soát theo hàng.

## 28. Những lỗi thường gặp

### 28.1. Dùng WITH nhưng quên RETURNING

~~~sql
WITH updated AS (
    UPDATE dml_cte_lab.orders
    SET status = 'paid'
    WHERE order_id = 101
)
SELECT * FROM updated;
~~~

Không có tập hàng `updated` để tham chiếu. Data-modifying CTE có thể vẫn chạy dù thiếu RETURNING, nhưng không thể truyền dữ liệu tiếp như một bảng.

### 28.2. Nghĩ LIMIT 1 chỉ làm DML chạy một hàng

`LIMIT` ở truy vấn ngoài có thể giới hạn số hàng **trả về**, không giới hạn hàng mà data-modifying CTE sửa. Phải giới hạn điều kiện DML theo cách phù hợp.

### 28.3. Đọc lại bảng gốc trong cùng statement để thấy trạng thái mới

Các nhánh DML và truy vấn chính dùng snapshot chung. Muốn nhận dữ liệu vừa sửa, dùng **`RETURNING`**, không dựa vào `SELECT` đọc lại bảng gốc cùng statement.

### 28.4. Nghĩ thứ tự viết CTE là thứ tự thực thi DML

Các nhánh DML cùng cấp không có thứ tự thực thi được bảo đảm. Hãy tạo phụ thuộc qua `RETURNING`; nếu cần thay đổi cùng hàng theo hai bước tuần tự, dùng **hai statement trong transaction**.

### 28.5. Cố cập nhật cùng hàng ở hai CTE

PostgreSQL không bảo đảm kết quả đúng theo ý định khi cùng hàng bị sửa hai lần trong một statement. Gộp các cột cần đổi vào một UPDATE hoặc tách statement.

### 28.6. Ghi audit vô điều kiện

Nếu `INSERT audit` dùng `VALUES` cố định, nó có thể chạy dù UPDATE 0 hàng. Dùng `INSERT ... SELECT FROM changed RETURNING` để số hàng audit đi theo số hàng cập nhật.

### 28.7. Coi RETURNING là hàng trước UPDATE

`UPDATE ... RETURNING` thường trả giá trị mới. Nếu cần cả giá trị trước và sau, phải dùng phương án phù hợp ngữ nghĩa/phiên bản, không đặt alias `old_status` lên cột mới rồi giả đó là giá trị cũ.

### 28.8. Nghĩ data-modifying CTE tự cung cấp idempotency

Một lệnh `UPDATE inventory SET quantity=quantity-3` có thể trừ tiếp khi request bị gửi lại. Cần idempotency key và unique constraint/transaction phù hợp.

### 28.9. Dùng SELECT MAX(id) sau INSERT

Không đáng tin trong môi trường nhiều phiên hoặc identity sequence. Dùng `INSERT ... RETURNING id`.

### 28.10. Tin rằng INSERT audit luôn thành công nếu UPDATE thành công

Nếu bảng audit có constraint vi phạm hoặc hết dung lượng, **toàn statement lỗi**. Ứng dụng cần xử lý transaction và lỗi, không bỏ qua.

### 28.11. Coi outbox có exactly-once publication

Outbox bảo đảm giao dịch dữ liệu–event tại database, không tự bảo đảm broker/consumer không thấy event trùng. Cần idempotency và retry.

### 28.12. Archive bằng DELETE mà bỏ qua foreign key

Xóa hàng cha có thể bị RESTRICT chặn hoặc CASCADE xóa hàng con. Cần xem mô hình dữ liệu và chính sách lưu trữ.

### 28.13. Không phân biệt 0 hàng với lỗi SQL

`RETURNING` rỗng thường là kết quả của điều kiện `WHERE`; lỗi constraint/deadlock/serialization là tình huống khác, cần xử lý riêng.

### 28.14. Không kiểm tra tính phá hủy của EXPLAIN ANALYZE

`EXPLAIN (ANALYZE)` thực sự chạy statement, kể cả UPDATE/DELETE/INSERT. Không dùng trên dữ liệu thật chỉ để “xem plan” mà không có biện pháp an toàn. Dùng `EXPLAIN` không `ANALYZE` để xem kế hoạch ước lượng.

## 29. Quan sát execution plan và kết quả

Một statement có DML CTE vẫn có thể được PostgreSQL giải thích bằng `EXPLAIN`:

~~~sql
EXPLAIN
WITH changed AS (
    UPDATE dml_cte_lab.orders
    SET status = 'paid'
    WHERE order_id = 101
      AND status = 'pending'
    RETURNING order_id
)
SELECT order_id
FROM changed;
~~~

`EXPLAIN` không `ANALYZE` chỉ cung cấp kế hoạch ước lượng, không thực thi DML.

Nếu muốn đo thời gian thực thi trong database lab:

~~~sql
BEGIN;

EXPLAIN (ANALYZE, BUFFERS)
WITH changed AS (
    UPDATE dml_cte_lab.orders
    SET status = 'paid'
    WHERE order_id = 101
      AND status = 'pending'
    RETURNING order_id
)
SELECT order_id
FROM changed;

ROLLBACK;
~~~

Ở đây `EXPLAIN ANALYZE` **có thực thi UPDATE**, vì vậy phải rollback sau đó nếu chỉ đo trong lab. Sequence, thao tác bên ngoài database hoặc một số tác động không transaction có thể không được đảo ngược như dữ liệu bảng, nên không coi rollback là “máy quay thời gian” cho mọi side effect.

### Những điều nên đo

- Số hàng thực tế được UPDATE/DELETE/INSERT.
- Chỉ mục trên điều kiện `WHERE`, ví dụ `orders.order_id`.
- Chi phí foreign key, trigger và index trên bảng nhận dữ liệu.
- Thời gian chờ khóa khi nhiều phiên cùng xử lý.
- Số hàng trong output `RETURNING`.
- WAL, throughput và thời gian transaction khi xử lý hàng loạt.

Khi xử lý số lượng lớn, cân nhắc chia batch có khóa/điều kiện ổn định, giới hạn công việc và chiến lược retry. Đừng dùng `LIMIT` ở SELECT ngoài để tưởng rằng DML đã tự chia batch.

## 30. Bài tập thực hành có đáp án

Các bài sau dựa vào seed ở mục 3. Với lệnh thay đổi dữ liệu, nên bọc trong `BEGIN ... ROLLBACK` để giữ trạng thái ban đầu.

### Bài 1. Tạo khách hàng và nhận ID

Viết `INSERT` thêm khách hàng `duong@example.test` và trả ID sinh tự động.

~~~sql
INSERT INTO dml_cte_lab.customers (email, full_name)
VALUES ('duong@example.test', 'Duong')
RETURNING customer_id, email;
~~~

**Đáp án:** Một hàng có ID mới sinh cùng email đã chèn. Không dự đoán số ID cụ thể nếu sequence đã được dùng trước đó.

### Bài 2. Tạo khách hàng rồi tạo đơn trong một statement

~~~sql
WITH created AS (
    INSERT INTO dml_cte_lab.customers (email, full_name)
    VALUES ('mai@example.test', 'Mai')
    RETURNING customer_id
)
INSERT INTO dml_cte_lab.orders
    (customer_id, status, total)
SELECT customer_id, 'pending', 50.00
FROM created
RETURNING order_id, customer_id;
~~~

**Đáp án:** Đơn mới trỏ đúng khách hàng vừa được tạo; cả hai thao tác thuộc cùng statement.

### Bài 3. Chỉ audit khi đơn pending chuyển paid

~~~sql
WITH changed AS (
    UPDATE dml_cte_lab.orders
    SET status = 'paid', paid_at = now()
    WHERE order_id = 101 AND status = 'pending'
    RETURNING order_id, status, total
)
INSERT INTO dml_cte_lab.order_audit
    (order_id, action, previous_status, new_status, amount)
SELECT order_id, 'status_changed', 'pending', status, total
FROM changed
RETURNING audit_id, order_id;
~~~

**Đáp án:** Với seed, một audit được chèn. Nếu cùng câu chạy lại trên dữ liệu đã commit với status paid, lần sau cập nhật 0 hàng và audit cũng 0 hàng.

### Bài 4. Vì sao SELECT bảng gốc trong cùng statement có thể vẫn thấy pending?

**Đáp án:** Các bước cùng statement dùng snapshot chung; thay đổi của data-modifying CTE không được nhánh khác nhìn qua cách đọc lại bảng gốc. `RETURNING` chuyển giá trị mới trực tiếp giữa các nhánh.

### Bài 5. Xóa đơn cancelled và chép vào archive

~~~sql
WITH moved AS (
    DELETE FROM dml_cte_lab.orders
    WHERE order_id = 104 AND status = 'cancelled'
    RETURNING
        order_id, customer_id, status, total, created_at, paid_at
)
INSERT INTO dml_cte_lab.orders_archive
    (order_id, customer_id, status, total, created_at, paid_at)
SELECT order_id, customer_id, status, total, created_at, paid_at
FROM moved
RETURNING order_id;
~~~

**Đáp án:** Đơn 104 được chuyển sang archive và không còn ở bảng orders khi statement commit. Nếu archive INSERT lỗi, DELETE không được commit riêng.

### Bài 6. Giảm kho an toàn

~~~sql
WITH stock_changed AS (
    UPDATE dml_cte_lab.inventory
    SET quantity = quantity - 3
    WHERE product_id = 501
      AND quantity >= 3
    RETURNING product_id, quantity
)
INSERT INTO dml_cte_lab.inventory_movements
    (product_id, delta, quantity_after)
SELECT product_id, -3, quantity
FROM stock_changed
RETURNING movement_id, quantity_after;
~~~

**Đáp án:** Tồn kho 501 từ 8 xuống 5, movement ghi `delta = -3` và `quantity_after = 5`.

### Bài 7. Nếu kho còn 0 thì sao?

Đổi `product_id = 501` thành `502` trong truy vấn bài 6.

**Đáp án:** Điều kiện `quantity >= 3` không khớp; UPDATE 0 hàng, INSERT movement 0 hàng.

### Bài 8. LIMIT 1 ở ngoài có giới hạn số hàng INSERT không?

~~~sql
WITH a AS (
    INSERT INTO dml_cte_lab.order_audit (order_id, action)
    VALUES (101, 'A'), (102, 'B'), (103, 'C')
    RETURNING audit_id
)
SELECT audit_id
FROM a
LIMIT 1;
~~~

**Đáp án:** Không. `INSERT` vẫn chèn ba hàng; SELECT chỉ trả một hàng. Dùng transaction/rollback nếu thử lab.

### Bài 9. Vì sao hai UPDATE cùng order_id trong hai CTE là sai?

**Đáp án:** PostgreSQL không hỗ trợ việc tác động cùng hàng hai lần trong một statement với kết quả được cam kết theo thứ tự mong muốn. Gộp thành một UPDATE hoặc dùng nhiều statement trong transaction.

### Bài 10. Phát event outbox khi thanh toán

~~~sql
WITH transitioned AS (
    UPDATE dml_cte_lab.orders
    SET status = 'paid', paid_at = now()
    WHERE order_id = 103
      AND status = 'pending'
    RETURNING order_id, customer_id, status, total
)
INSERT INTO dml_cte_lab.outbox_events
    (aggregate_type, aggregate_id, event_name, payload)
SELECT
    'order',
    order_id,
    'order.paid',
    jsonb_build_object(
        'order_id', order_id,
        'status', status,
        'total', total
    )
FROM transitioned
RETURNING event_id, event_name;
~~~

**Đáp án:** Một event được chèn khi đơn 103 được cập nhật; event không được chèn nếu điều kiện UPDATE không khớp. Worker bên ngoài sẽ gửi event sau commit; phải xử lý retry/trùng lặp.

### Bài 11. Khi nào cần nhiều statement thay vì một DML CTE?

**Đáp án gợi ý:** Khi cần kiểm tra nhiều bước với thứ tự thực sự, đọc thay đổi từ bảng ở statement tiếp theo, gọi logic ứng dụng giữa các bước, hoặc cùng một hàng cần được sửa theo các pha tuần tự. Có thể dùng transaction để giữ atomicity mà không gộp mọi bước thành một statement.

### Bài 12. DML CTE thiếu RETURNING có chạy không?

**Đáp án:** Có, data-modifying CTE vẫn thực thi đến hết. Nhưng nếu không có RETURNING, nó không tạo bảng kết quả để CTE khác hoặc câu SELECT chính đọc qua tên CTE.

### Bài 13. Vì sao chỉ audit đơn cha chưa đủ cho cascade?

**Đáp án:** `DELETE ... RETURNING` trên bảng cha chỉ trả các hàng bị DELETE khỏi bảng cha. Nếu FK cascade xóa dữ liệu ở bảng con, muốn giữ lịch sử hàng con phải có cơ chế audit/archive riêng.

### Bài 14. Phân biệt 0 hàng RETURNING và lỗi

**Đáp án:** 0 hàng có thể do WHERE không khớp; lỗi là trường hợp PostgreSQL không thực hiện statement thành công (constraint, quyền, deadlock, serialization...). Ứng dụng phải phân biệt hai tình huống.

## 31. Checklist khi dùng data-modifying CTE trong dự án

1. **Xác định thay đổi nghiệp vụ:** INSERT, UPDATE hay DELETE, theo khóa/điều kiện nào?
2. **Xác định hàng thực sự được tác động:** ghi điều kiện `WHERE` rõ ràng, tránh UPDATE/DELETE quá rộng.
3. **Chọn dữ liệu cần truyền:** ghi danh sách cột trong `RETURNING` thay vì luôn dùng `RETURNING *`.
4. **Chỉ dẫn dữ liệu qua RETURNING:** các nhánh sau dùng `SELECT FROM cte_name`.
5. **Không kỳ vọng đọc lại bảng gốc thấy thay đổi cùng statement:** tôn trọng snapshot chung.
6. **Không dựa vào thứ tự viết nhánh DML:** tạo phụ thuộc dữ liệu khi cần.
7. **Không cập nhật/xóa cùng một hàng hai lần:** gộp thay đổi hoặc tách statement.
8. **Xử lý 0 hàng:** phân biệt không khớp điều kiện với lỗi SQL.
9. **Kiểm tra FK, trigger, constraint và RLS:** DML vẫn chịu đầy đủ luật của database.
10. **Thiết kế transaction boundary:** statement nguyên tử, nhưng nhiều bước nghiệp vụ có thể cần transaction lớn hơn.
11. **Xử lý concurrency:** row lock, isolation, retry và idempotency nếu có nhiều writer.
12. **Đánh giá audit/outbox:** bảo đảm event đi theo hàng đã thay đổi; worker phát event phải hỗ trợ retry.
13. **Quan sát execution plan an toàn:** `EXPLAIN` để xem kế hoạch; `EXPLAIN ANALYZE` chỉ trong môi trường kiểm soát.
14. **Thử lại trên dữ liệu biên:** 0 hàng, một hàng, nhiều hàng, status không hợp lệ, duplicate key và tác động FK.
15. **Dùng database lab riêng khi học:** không chạy script reset/archive/xóa trên dữ liệu thật.

## 32. Tổng kết

**Data-modifying CTE** cho phép PostgreSQL biến `RETURNING` thành một luồng hàng có thể dùng bởi phần còn lại của câu SQL:

~~~sql
WITH changed_rows AS (
    UPDATE some_table
    SET some_column = some_value
    WHERE some_condition
    RETURNING id, some_column
)
INSERT INTO audit_table (entity_id, new_value)
SELECT id, some_column
FROM changed_rows;
~~~

Mẫu này hữu ích vì **bảng audit nhận dữ liệu từ chính những hàng UPDATE đã tác động**, thay vì một tập hàng được đoán hoặc truy vấn lại.

Những quy tắc cần nhớ nhất:

- `INSERT/UPDATE/DELETE ... RETURNING` là kênh lấy dữ liệu đã chèn, sửa hoặc xóa.
- Data-modifying CTE **thực thi đầy đủ**, không bị giới hạn bởi `LIMIT` ở SELECT bên ngoài.
- Những nhánh trong cùng statement chia sẻ snapshot; **không dùng SELECT lại bảng gốc** để truyền trạng thái mới giữa các nhánh.
- Thứ tự thực thi giữa các DML CTE cùng cấp **không được bảo đảm**; hãy diễn đạt phụ thuộc bằng `RETURNING`.
- Tránh tác động **cùng một hàng nhiều lần trong một statement**.
- Mọi thao tác vẫn chịu transaction, khóa, FK, trigger, RLS và constraint bình thường.
- Audit, archive và transactional outbox là những ứng dụng thực tế; atomicity không tự thay thế authorization hay idempotency.

Khi mô hình hóa đúng luồng dữ liệu qua `RETURNING`, bạn có thể viết những thao tác PostgreSQL phức tạp nhưng vẫn rõ ràng: **hàng nào thay đổi thì chỉ hàng đó tạo ra lịch sử, dữ liệu liên quan hoặc sự kiện tiếp theo**.
