# Planning Migration of Remotes, Refs, Tags, LFS, and Submodules

When moving a Git repository to a new server or hosting platform, simply copying the source code directory is not enough. A repository can contain multiple branches, tags, notes, signed commits, Git LFS contents, and submodules pointing to other repositories. In addition, remote URLs, default branches, access permissions, branch protections, CI, and webhooks are usually stored in local configuration or the hosting service rather than inside the Git object database.

A safe migration requires a plan for inventorying, backing up, transferring objects and refs, transferring LFS objects separately, handling each submodule, performing a final sync, and verifying on the target remote. This lesson covers choosing between `git push --all`/`--tags` and mirroring, preserving data, and transitioning users to the new remote with controlled downtime.

## 1. Defining migration scope

Before running commands, identify exactly what needs to be transferred and what needs to be reconfigured. A Git repository and a hosting platform do not store the same types of data.

| Component | Primary storage | How to handle during migration |
|---|---|---|
| Commits, trees, blobs, annotated tag objects | Git object database | Transfer via clone/fetch/push or mirror |
| Branch and tag refs | Git refs | Transfer via `push --all`, `push --tags`, or `push --mirror` depending on scope |
| Notes and custom refs | `refs/*` namespaces | Inventory separately; mirror can transfer more refs |
| Git LFS content | LFS object storage | Fetch/push LFS objects separately, not just Git refs |
| Submodule repositories | Independent repositories | Migrate each child repository and verify gitlink commits |
| Remote URLs, fetch/push refspecs | Local `.git/config` configuration | Reconfigure on clones or new machines |
| Default branch, protections, permissions, webhooks | Hosting/server | Recreate or reconfigure on the target platform |
| Pull/merge requests, issues, reviews, discussions | Hosting/server | Use platform migration tools/APIs if preservation is needed |
| CI secrets, variables, runners, release assets | Hosting/CI | Inventory and migrate via separate workflows |

Git transfer preserves history and objects, but does not automatically migrate platform settings or project management data. Define the project scope to retain before scheduling the cutover.

## 2. Inventorying the source repository

Before copying, gather information about the source repository. Perform this from a clone with full read access or from the appropriate repository server.

### Checking remotes and local state

```bash
git status --short --branch
git remote -v
git branch --all --verbose
git tag --list --sort=version:refname
```

Check whether the current clone has uncommitted changes. A normal working clone may not hold every ref on the server, especially if fetch refspecs are restricted or some branches were never fetched.

### Listing refs and object IDs

To inventory local refs:

```bash
git for-each-ref --format='%(refname) %(objectname)' refs
```

To see refs advertised by the remote:

```bash
git ls-remote --refs origin
```

Check the symbolic HEAD and default branch of the remote:

```bash
git ls-remote --symref origin HEAD
```

`git ls-remote` only shows refs advertised by the remote. Some hosting platforms have internal or hidden refs that do not appear through this command. If all internal refs must be transferred, verify server access permissions and policies.

### Checking important namespaces

Common namespaces:

- `refs/heads/`: local branches or server branches.
- `refs/tags/`: tags.
- `refs/notes/`: Git notes.
- `refs/replace/`: replace refs used to override how Git views objects.
- `refs/remotes/`: remote-tracking refs in a normal clone.
- Custom namespaces created by workflows or hosting platforms.

Not every ref belongs on the target remote. For example, `refs/remotes/origin/*` is typically local remote-tracking state, while `refs/pull/*` or `refs/merge-requests/*` may be internal refs generated by the hosting platform. Decide which namespaces should be migrated and which belong solely to the source platform.

### Checking the object database and integrity

```bash
git count-objects -vH
git fsck --full
```

`git count-objects` estimates object storage size; `git fsck --full` checks the object database. If the source has object errors or missing data, fix them before migrating to avoid carrying corruption over to the target.

## 3. Backing up and preparing the target remote

Before migrating, create a recoverable backup. For a bare or mirror repository, back up the entire repository directory following your organization's backup procedures; for a working clone, preserve uncommitted changes and required configuration as well.

Verify the target remote:

- Target repository has been created and push permission is granted.
- Object format and Git version are compatible with source clients.
- Storage capacity, quotas, and retention policies accommodate Git objects and LFS objects.
- Target service has Git LFS enabled if the repository uses LFS.
- Accounts or deploy keys have read access to submodules after migration.
- Default branch and branch protection rules have been defined.

If you plan to use `git push --mirror`, create an empty target repository and dedicate a mirror clone for the job. Do not use an active development clone to mirror all refs without verifying scope.

## 4. Choosing how to transfer branches and tags

There are two common ways to transfer Git refs. They are not equivalent and must be chosen according to requirements.

### Option A: pushing required branches and tags

In a regular clone, add the target remote:

```bash
git remote add new-origin https://git.example.com/team/project.git
git fetch --all --tags --prune
```

Push all local branches:

```bash
git push new-origin --all
```

Push all local tags:

```bash
git push new-origin --tags
```

`--all` pushes local branches under `refs/heads/`; it does not push every remote-tracking branch and does not automatically include all custom namespaces. `--tags` pushes local tags under `refs/tags/`. If notes or custom refs are needed, push the corresponding namespace explicitly after inventorying, for example:

```bash
git push new-origin 'refs/notes/*:refs/notes/*'
```

Only use a specific refspec after confirming that namespace makes sense on the target remote. If the target remote already has a branch with the same name but different history, a normal push may be rejected as non-fast-forward. Do not automatically use `--force` to bypass it; determine whether the target history must be kept.

After pushing main branches, set upstreams for working branches if needed:

```bash
git push --set-upstream new-origin main
```

This configures tracking for the current local branch or the specified branch so subsequent `pull`/`push` operations use the right remote and default branch.

### Option B: mirroring all refs

If the requirement is copying nearly the entire ref namespace of the repository, use a bare mirror clone:

```bash
git clone --mirror https://git.example.com/old/project.git project.git
cd project.git
git remote add target https://git.example.com/new/project.git
git push --mirror target
```

`git clone --mirror` creates a bare repository and configures fetch refspecs to pull all refs advertised by the source. `git push --mirror` instructs the target to mirror local refs: new refs are created, changed refs may be force-updated, and refs no longer present in the local mirror may be deleted on the target.

Therefore, mirror only into an empty target repository or a target confirmed as safe to overwrite/delete according to plan. This command is destructive to refs on the target if they do not exist in the source mirror. Do not use `--mirror` to "see what happens" against a remote containing data that must be preserved.

A mirror clone has no working tree for editing source code. It is suited for repository migration at the refs/objects level, not for daily working clones.

## 5. Understanding what --mirror can transfer

Mirroring has a broader scope than `--all` and `--tags`, but that does not mean it transfers all hosting platform data.

| Method | Primary scope | Things to note |
|---|---|---|
| `git push --all` | Local branches | Does not automatically push tags, notes, or custom refs |
| `git push --tags` | Local tags | Does not push branches |
| Pushing a specific refspec | Specified namespace/ref | Requires precise control over source and destination |
| `git push --mirror` | All local refs within mirror scope | Can force-update and delete refs on the target remote |

Mirroring can include notes, replace refs, or custom namespaces if they were fetched into the local mirror. However, the target remote may reject protected namespaces or refs users are not permitted to create. Hosting platforms may also hide internal refs from clients. Review push output and re-verify refs after transferring.

Do not expect a mirror to preserve:

- Pull requests or merge requests along with discussions/reviews.
- Issues, or wikis if the wiki is stored in a separate repository.
- Branch protections, rulesets, member permissions, and groups.
- Webhooks, deploy keys, CI secrets, variables, runners, and schedules.
- Release assets, package registries, artifacts, and integration settings.

That data must be migrated using platform tools/APIs or reconfigured on the target platform.

## 6. Final sync and controlling cutover timing

If the source repository continues receiving commits during copying, the initial mirror can quickly become stale. The safe approach is splitting migration into an initial copy and a final sync.

A common schedule:

1. Announce the migration time and ask the team to avoid making changes during the cutover window.
2. Perform the initial mirror while the source remains active or write-restricted as platform capabilities allow.
3. At the cutover window, set the source repository to read-only or pause pushes.
4. Re-fetch all refs from source into the mirror and run the final mirror push.
5. Sync any missing LFS objects.
6. Verify branches, tags, LFS, submodules, and target configurations.
7. Update URLs in documentation, CI, bots, and member clones; enable writes on the target.
8. Keep the source read-only for an agreed rollback period.

For a mirror clone with source remote `origin` and target remote `target`, the final sync can look like:

```bash
git fetch --prune origin
git push --mirror target
```

In a mirror clone, fetch refspecs normally cover refs per the mirror configuration. Check `git config --get-all remote.origin.fetch` and local refs before syncing. `--prune` removes local refs no longer advertised by the source under the refspec; the subsequent `push --mirror` can delete the corresponding refs on the target. This is necessary for accurate mirroring, but must be anticipated.

If writes cannot be locked on the source, an iterative sync workflow and a clear cutoff time are needed. Avoid letting both remotes accept independent writes for long periods: both sides can gain commits on the same branch, move tags, or diverge in history, making reconciliation difficult to control.

## 7. Migrating Git LFS objects separately

A Git repository may transfer commits and pointer files successfully, yet users still fail to download large files if LFS objects have not been transferred. Pointers in Git contain only an OID and size; the actual content resides in LFS storage.

### Inventorying LFS

In a clone containing the refs to transfer, inspect LFS files:

```bash
git lfs ls-files --all
git lfs env
```

Check `.gitattributes` and `.lfsconfig` if used by the repository. `.lfsconfig` can declare an LFS endpoint; local or remote configuration can override endpoints. Never put tokens or credentials in committed files.

### Fetching all LFS objects from source

After fetching all refs and tags:

```bash
git lfs fetch --all origin
```

`--all` requests downloading LFS objects referenced by the refs considered by Git LFS in the repository, suited for migration instead of fetching only the current branch's objects. If the mirror clone lacks the LFS client or source access, install Git LFS and authenticate first.

### Pushing all LFS objects to target

```bash
git lfs push --all target
```

This command pushes the LFS objects needed for refs in the local repository to the target remote's endpoint. Run it after fetching all LFS objects from the source and before opening the new remote to team members.

A safe cutover sequence:

1. Fetch latest refs from the source.
2. Run `git lfs fetch --all origin` to pull required LFS objects.
3. Push Git refs to the target.
4. Run `git lfs push --all target` to ensure target LFS storage has corresponding contents.
5. Test cloning from the target and downloading LFS objects with `git lfs pull`.

If the hosting platform requires LFS objects to exist before refs are published, you can push LFS objects to the target before pushing refs. Whichever order you choose, open cutover only once both refs and LFS contents are complete.

### Verifying LFS after migration

Create a test clone from the target remote:

```bash
git clone https://git.example.com/new/project.git verify-project
cd verify-project
git lfs pull
git lfs ls-files
```

Open several representative large files and check their contents, sizes, or checksums per project procedures. If the working tree contains only pointer text, check the LFS endpoint, access permissions, and whether `git lfs pull` successfully downloads objects.

## 8. Migrating submodules and updating URLs

A submodule is a separate Git repository. The superproject does not store full submodule contents; it stores a gitlink (mode `160000`) pointing to a specific commit in the child repository. Therefore, migrating the superproject does not automatically migrate submodule repositories.

### Inventorying submodules

Inspect configuration:

```bash
git config --file .gitmodules --get-regexp 'submodule\..*\.path'
git config --file .gitmodules --get-regexp 'submodule\..*\.url'
git submodule status --recursive
```

Check each submodule and nested submodules. Record the URLs, configured branches if any, the gitlink commits currently referenced by the superproject, and LFS files if child repositories use LFS.

### Migrating each submodule repository

Each submodule must have its branches, tags, refs, LFS, and nested submodules transferred using the corresponding workflow. Ensure the commit referenced by the superproject's gitlink exists on the new submodule remote. If you transfer only branch tips without older commits referenced by gitlinks, checking out the superproject can fail.

For each submodule repository, you can use a dedicated clone/mirror, inspect refs, and verify the target commit. If the submodule uses LFS, transfer LFS objects separately as shown earlier.

### Updating URLs in the superproject

Once the new submodule remote is ready, update the URL in `.gitmodules` using the appropriate command or by editing the file and committing:

```bash
git config -f .gitmodules submodule.shared-lib.url https://git.example.com/team/shared-lib.git
git add .gitmodules
git commit -m "chore: update submodule remote URLs"
```

The name `shared-lib` must match the submodule section in `.gitmodules`. If relative URLs are used, verify the namespace layout between the superproject and submodules on the new host; relative URLs can continue working if relative repository paths are preserved.

On existing clones, sync URLs from `.gitmodules` into local config:

```bash
git submodule sync --recursive
git submodule update --init --recursive
```

`sync` updates URLs in local submodule config to match `.gitmodules`; it does not migrate child repository contents. `update --init --recursive` initializes and checks out the exact gitlink commits, including nested submodules.

### Verifying submodules

```bash
git submodule status --recursive
git -C path/to/shared-lib rev-parse HEAD
```

In `git submodule status` output, the leading character is meaningful: a normal space indicates the submodule is at the exact commit recorded in the superproject; `-` indicates uninitialized; `+` indicates submodule HEAD differs from the gitlink; `U` indicates a gitlink conflict. Verify actual commits and clone access for each submodule before cutover.

## 9. Tags, annotated tags, and signatures

Tags are usually transferred alongside refs when using `git push --tags` or `git push --mirror`. An annotated tag is a separate object containing the tagger, message, and optionally a signature; if the object is transferred intact, metadata and signatures remain inside the tag object.

After transferring, inspect the list and key tags:

```bash
git ls-remote --tags target
git verify-tag v2.0.0
git show --show-signature v2.0.0
```

Preserving a signature in the object does not mean the new machine already trusts the signing key. The verifying machine needs the public key/certificate, allowed signers, or trust store per policy. Lightweight tags have no separate tag object or tag signature.

If the target remote already has a tag with the same name pointing to a different object, a normal push may be rejected. Do not force-update shared release tags without an explicit decision; tags are generally treated as immutable milestones in release workflows.

## 10. Remote configuration does not automatically travel with Git objects

When pushing commits and refs to a new remote, remote URLs and local clone settings do not transfer automatically. After migration, each clone must update its remote accordingly.

Inspect:

```bash
git remote -v
git branch -vv
```

Change the existing remote URL:

```bash
git remote set-url origin https://git.example.com/new/project.git
```

Or add a new remote and keep the old remote during verification:

```bash
git remote add new-origin https://git.example.com/new/project.git
git fetch new-origin --prune --tags
```

If you need to view refspecs or push URLs, use appropriate config inspection commands:

```bash
git config --get-regexp '^remote\.'
git config --get-regexp '^branch\.'
```

These commands can expose internal URLs or sensitive details improperly embedded in URLs. Review output before sharing. Prefer credential helpers or an SSH agent rather than storing tokens directly in remote URLs.

After changing the remote, check branch upstreams. If a branch still tracks the old remote, update upstream with:

```bash
git branch --set-upstream-to=new-origin/main main
```

Run this with an existing branch and a fetched remote-tracking ref. You can use `git push -u new-origin main` when pushing a branch for the first time to set upstream in the same step.

## 11. Verifying the target repository

Do not treat a migration as finished simply because the push command returned exit code `0`. Compare refs, verify objects, and perform an independent test clone from the target.

### Comparing refs

Check branches/tags on the target remote:

```bash
git ls-remote --heads target
git ls-remote --tags target
git ls-remote --symref target HEAD
```

Compare against the list recorded from the source. With a mirror, you can compare all advertised refs:

```bash
git ls-remote --refs origin
git ls-remote --refs target
```

Differences can stem from server namespaces users cannot create, hidden refs, or hosting rules. Classify every discrepancy rather than ignoring all differences.

### Checking integrity and test cloning

```bash
git clone --recurse-submodules https://git.example.com/new/project.git verify-project
cd verify-project
git fsck --full
git submodule update --init --recursive
git lfs pull
```

Verify the default branch, release tags, critical commits, LFS files, and every submodule. Run a basic build/test to confirm clones from the new remote can reproduce the working environment.

### Checking hosting configuration

Confirm on the target platform:

- Default branch points to the desired branch.
- Branch protections/rulesets are properly enabled.
- Members, teams, deploy keys, and bots have appropriate permissions.
- CI workflows, secrets, variables, runners, and webhooks operate properly.
- Releases, packages, wikis, and project docs have been migrated if in scope.

## 12. Rollback plan

Before cutover, define the conditions for reverting to the source and how to handle changes made after opening the target remote.

A rollback plan should answer:

1. Who has authority to decide to roll back to the source?
2. Is the source still read-only with its refs intact?
3. If new commits have already landed on the target, how will they be transferred back to the source?
4. Do newly created LFS objects on the target exist on the source yet?
5. How will URLs in submodules, CI, bots, and member clones be switched back?
6. How long will the old remote and backups be retained?

Avoid letting both source and target accept pushes for an extended period. If rollback is necessary after the target received new commits, sync any newly created refs and LFS objects before reopening the source. Do not force-push or reverse-mirror without inventorying changes on both sides.

## 13. Reference migration checklist

### Before migration

- [ ] Inventoried remotes, refs, branches, tags, notes, and custom namespaces.
- [ ] Recorded default branch and critical commits.
- [ ] Ran `git fsck --full` and measured object/LFS size.
- [ ] Inventoried `.gitattributes`, `.lfsconfig`, and the LFS object list.
- [ ] Inventoried `.gitmodules`, nested submodules, and gitlink commits.
- [ ] Created a recoverable backup.
- [ ] Created target repository, verified quota, LFS, and access permissions.
- [ ] Listed hosting/CI data requiring separate migration.

### During migration

- [ ] Selected individual branch/tag pushing or mirroring in a bare clone.
- [ ] Avoided `--mirror` onto a target holding data to preserve unless approved.
- [ ] Fetched all refs and ran final sync during the freeze window.
- [ ] Transferred LFS objects for all retained refs.
- [ ] Migrated each submodule and updated URLs in `.gitmodules`.
- [ ] Kept source read-only during verification.

### After migration

- [ ] Compared refs and tags between source and target.
- [ ] Verified tag/commit signatures against the new environment's trust store.
- [ ] Test-cloned from target, ran `git fsck --full`, `git lfs pull`, and updated submodules.
- [ ] Verified default branch, protections, permissions, CI, webhooks, and secrets.
- [ ] Updated remote URLs/upstreams in clones, bots, and documentation.
- [ ] Ran representative builds/tests and confirmed the team can work.
- [ ] Retained backups and rollback plan for the agreed duration.

## 14. Common misconceptions

| Misconception | Accurate understanding |
|---|---|
| `git push --all` transfers the entire repository | It pushes local branches; tags and other namespaces require separate commands |
| `git push --tags` also pushes branches | It pushes only local tags |
| `git push --mirror` is safe for every remote | It can force-update and delete refs on the target; use only with controlled scope |
| Mirroring Git also transfers Git LFS | LFS objects reside in separate storage and require separate fetch/push |
| The superproject contains full submodule source | The superproject stores only gitlinks to child repository commits |
| Pushing Git refs automatically changes remote URLs in team clones | Remote URLs and upstreams are local config that must be updated |
| Valid tag signatures mean new machines automatically trust the signer | Public keys, fingerprints, allowed signers, or trust stores must be configured |
| Git migration transfers PRs, issues, and branch protections | Hosting/CI data must be migrated with separate tools or configurations |
| The new remote can open right after the first push | Final sync, LFS/submodule checks, and a test clone from the target are required |

## 15. Key takeaways

A complete remote migration plan must separately manage Git objects/refs, Git LFS, submodules, and hosting configuration. For regular clones, `git push --all` transfers local branches and `git push --tags` transfers tags; when mirroring refs is required, use a bare mirror clone and `git push --mirror` only after confirming the target remote can be force-updated or have refs deleted.

Git LFS requires `git lfs fetch --all` from the source and `git lfs push --all` to the target. Each submodule must have a target repository containing the gitlink commit, URLs in `.gitmodules` must be updated, and clones must run `git submodule sync --recursive` followed by `git submodule update --init --recursive`.

Finally, freeze writes on the source, perform a final sync, verify refs/LFS/submodules with a test clone, configure default branches and permissions on the host, and only then transition users to the new remote. Keep the source and backups during the rollback window so discrepancies can be addressed without losing critical history.
