# Checking a Patch Before Applying and Handling Context Errors

Patches are a way to exchange changes without sending the entire repository. A patch file usually contains deleted lines, added lines, and some context so Git can locate the exact spot to modify. When code on the receiving machine has changed, the patch may no longer match the original content. Applying it immediately without checking can create partial changes, miss hunks, or make root-cause diagnosis difficult.

In the **Sharing and Migrating Changes** chapter of the **SOURCE_CONTROL_GIT** module, this lesson covers how to read a patch, check applicability before modifying the working tree, diagnose context errors, and choose the right resolution. You will distinguish git apply from git am, know when to use three-way merge, when to handle .rej files, and how to verify the result after a patch is applied.

After this lesson, you will be able to:

- Read unified diff structure and understand the role of context lines.
- Check a patch with git apply --check before applying it.
- Inspect statistics, paths, and metadata that a patch will modify.
- Diagnose errors caused by wrong base, modified files, path prefix, whitespace, or an already-applied patch.
- Use --3way when the patch has the required blob info and the original object is available.
- Understand the risks of --reject and how to handle .rej files.
- Distinguish git apply from git am when receiving patches from git format-patch.
- Inspect the diff, index, and repository status after applying.

## 1. What does a patch contain?

A text patch usually uses the unified diff format. It describes the differences between the old version and the new version of a file.

Example:

~~~diff
diff --git a/src/greeting.js b/src/greeting.js
index 1a2b3c4..5d6e7f8 100644
--- a/src/greeting.js
+++ b/src/greeting.js
@@ -10,4 +10,5 @@
 function greeting(name) {
-  return "Hello " + name;
+  if (!name) return "Hello guest";
+  return "Hello " + name;
 }
~~~

Components:

- **diff --git**: file paths in the old and new versions.
- **index**: object IDs of the old and new blobs along with file mode; this information can assist with three-way merge.
- **---**: old file.
- **+++**: new file.
- **@@**: indicates the line offset and line counts of the hunk in both versions.
- Lines starting with a space: context, which must match the current content.
- Lines starting with a minus sign: removed content.
- Lines starting with a plus sign: added content.

A hunk can have several context lines before and after the change. Git uses them to locate where to apply the change, rather than relying solely on the line numbers in the header. When context lines have changed, Git may report that the patch cannot be applied.

A patch can also include file renames, executable permissions, new files, deleted files, or binary content. Therefore, do not read only the plus/minus lines; inspect the patch headers and metadata as well.

## 2. Distinguishing git apply and git am

Both commands are commonly used to receive patches, but they serve different goals.

| Command | Typical input | Result |
| --- | --- | --- |
| git apply | Diff patch such as a file generated by git diff | Applies content changes to working tree or index; does not automatically create commits |
| git am | Mailbox patch generated by git format-patch | Applies each patch and creates a commit, preserving author, timestamp, and commit message |

If you receive a .patch file containing a plain diff, git apply is usually appropriate. If you receive a .patch or .mbox file from git format-patch and want to preserve commit metadata, use git am.

Example creating a plain diff:

~~~bash
git diff main..feature/login > login.patch
~~~

Applying:

~~~bash
git apply login.patch
~~~

Example creating a mailbox patch:

~~~bash
git format-patch -1 <commit>
~~~

Applying and creating a commit:

~~~bash
git am 0001-feature-change.patch
~~~

git apply does not recreate the author, date, and commit message from a mailbox. If those details must be preserved, do not substitute git apply for git am.

## 3. Preparing before checking a patch

Before applying a patch from someone else, verify the repository, branch, and file status.

~~~bash
git rev-parse --show-toplevel
git status -sb
git branch --show-current
git log -1 --oneline --decorate
~~~

Steps to take:

1. Confirm you are in the right repository and working directory.
2. Check whether the current branch is the base from which the patch was created.
3. Check for uncommitted changes in the working tree and index.
4. Back up or commit in-progress changes if you need to keep them.
5. Determine whether the patch is a plain diff or a mailbox patch.
6. Read the filenames and scope of changes in the patch before applying.

If the working tree has changes, the patch may touch the same files or lines. Do not use reset --hard just to clean the state before testing a patch. Preserve current work using a commit, stash, or appropriate copy.

Run commands from the repository root so paths in the patch are predictable. If run from a subdirectory, Git may apply the patch relative to the current working directory; confirm paths before proceeding.

## 4. Checking a patch without modifying files

The most important command is:

~~~bash
git apply --check change.patch
~~~

--check asks Git to verify whether the patch can apply without modifying the working tree or index. If the command succeeds, the patch can be applied under current conditions. If it fails, Git typically identifies the mismatched file and hunk.

You can request more detailed output:

~~~bash
git apply --check --verbose change.patch
~~~

Check statistics before applying:

~~~bash
git apply --stat change.patch
git apply --numstat change.patch
git apply --summary change.patch
~~~

- --stat displays changed line counts per file.
- --numstat displays added and deleted line counts in a script-friendly format.
- --summary displays information such as new files, deleted files, renames, or mode changes.

Statistics commands help catch patches affecting unexpected files or paths. They do not replace --check; a patch with valid statistics can still fail to match the current working tree.

## 5. Applying a patch after checking

If --check succeeds, apply the patch:

~~~bash
git apply change.patch
~~~

By default, git apply modifies the working tree and does not automatically stage content into the index. Verify:

~~~bash
git status --short
git diff --check
git diff
~~~

git diff --check looks for certain whitespace errors in current changes, such as trailing whitespace. It does not test patch applicability; that is handled by git apply --check.

After reviewing, stage the required files:

~~~bash
git add -- src/greeting.js
git diff --cached
~~~

Only commit once the content has been properly reviewed and tested.

### Applying simultaneously to the index and working tree

If you want Git to update both the index and the working tree:

~~~bash
git apply --index change.patch
~~~

--index requires the index and working tree for affected paths to match each other, then applies the change to both. If they already differ, Git may refuse.

You can check beforehand with:

~~~bash
git apply --check --index change.patch
~~~

### Applying only to the index

~~~bash
git apply --cached change.patch
~~~

--cached applies the patch to the index without modifying the working tree. This is useful in workflows that build a controlled staging area, though you must understand that the index and working tree will then differ. Inspect using:

~~~bash
git diff --cached
git diff
git status --short
~~~

## 6. Understanding context errors

A context error occurs when Git cannot find a matching block of content to apply a hunk. Example:

~~~text
error: patch failed: src/greeting.js:10
error: src/greeting.js: patch does not apply
~~~

This message does not necessarily mean the patch is corrupted. It may have been created from a different version of the code than the current one.

Common causes:

| Cause | Symptom | What to check |
| --- | --- | --- |
| Wrong base commit | Multiple hunks fail to match, file changed significantly | Compare base commit and file history |
| File was modified | Only some hunks in the file fail | Read current context lines and diff |
| Patch partially or fully applied | Some old blocks no longer exist | Try reverse check and compare content |
| Wrong path prefix | Git reports file not found or applies to wrong path | Check headers and adjust -p |
| Whitespace differences | Text matches but spaces or tabs differ | Compare whitespace and consider ignore options |
| Different line endings | File has CRLF/LF or mixed line endings | Check EOL status and file bytes |
| Patch truncated or edited incorrectly | Hunk header and line counts mismatch, missing end | Inspect patch file and sender source |
| File renamed or moved | Patch references old path | Identify new path and regenerate patch against current base |

Do not immediately force Git to ignore whitespace or use --reject. First identify the cause, because those two options can mask a patch generated from the wrong base.

## 7. Diagnosing base commit and file contents

A patch is normally created between two states of a file. If the receiving machine is on a different commit, context lines may no longer match.

### See which files the patch wants to modify

~~~bash
git apply --stat change.patch
git apply --summary change.patch
~~~

Read the diff --git, ---, and +++ headers to identify old/new filenames. Then inspect current contents:

~~~bash
git diff -- src/greeting.js
git log --oneline --follow -- src/greeting.js
~~~

If you know the base commit the patch author used:

~~~bash
git show <base-commit>:src/greeting.js
~~~

Compare the base version with the current file to determine which change shifted the context.

### Determine whether the patch was already applied

You can try a reverse check:

~~~bash
git apply --reverse --check change.patch
~~~

If the reverse check succeeds, it indicates the patch contents may already be present in the working tree. This is not absolute proof that the entire patch was applied properly; compare diffs and history before concluding.

If a patch was partially applied, check each file and each hunk. Do not blindly re-run the entire patch, as that can cause further errors or duplicate changes.

## 8. Checking and fixing the path prefix

Patches usually contain paths such as:

~~~text
diff --git a/src/greeting.js b/src/greeting.js
--- a/src/greeting.js
+++ b/src/greeting.js
~~~

git apply normally strips one leading path component by default, so a/ and b/ become src/greeting.js.

The -p<n> option controls how many leading path components are stripped:

~~~bash
git apply --check -p1 change.patch
git apply --check -p0 change.patch
~~~

- -p1 strips the first component, such as a/.
- -p0 preserves the paths in the patch as-is.
- -p2 strips the first two components.

If a patch lacks a/ and b/ prefixes, determine the exact number of components to strip by reading the headers rather than guessing randomly.

You can prepend a target directory after stripping the prefix:

~~~bash
git apply --check --directory=vendor/library change.patch
~~~

--directory prepends a path to the file paths after -p processing. This example applies patch paths underneath vendor/library. Check --stat and --check first to be sure you do not write to the wrong location.

## 9. Handling whitespace differences

A patch may fail to match because context lines differ in spaces or tabs. Git provides options to relax whitespace matching in context lines:

~~~bash
git apply --check --ignore-space-change change.patch
git apply --check --ignore-whitespace change.patch
~~~

These two options let Git ignore certain whitespace differences in context lines when finding the target location. They do not mean all whitespace in newly added lines is automatically stripped. Inspect the content after applying.

### Whitespace in added lines

The --whitespace option controls how whitespace errors are handled in lines added or modified by the patch:

~~~bash
git apply --whitespace=warn change.patch
git apply --whitespace=fix change.patch
git apply --whitespace=error change.patch
~~~

- warn: warns about whitespace errors.
- fix: attempts to fix whitespace errors in added content.
- error: raises an error when encountering whitespace errors.
- error-all: like error, but displays all detected whitespace errors instead of stopping at the first one.
- nowarn: suppresses whitespace warnings.

The default behavior can also be influenced by core.whitespace. Whitespace errors commonly include trailing whitespace or spaces before tabs in certain contexts. Do not use fix if that whitespace is meaningful to the project's format or data.

Note: --ignore-space-change and --ignore-whitespace adjust how context lines are matched; --whitespace controls how whitespace errors in patch content are detected or fixed. These are two distinct groups of behavior.

## 10. When to use --3way?

If a patch does not apply directly because the file has changed, Git can attempt a three-way merge:

~~~bash
git apply --3way change.patch
~~~

Git requires the patch to record the original blob's object ID and requires that blob to be available in the object database. If enough information is present, Git can use the base version, current version, and patch-proposed version to merge.

--3way implies --index. Therefore, Git updates the index along with the working tree and may leave unmerged entries if conflicts arise. Do not assume a non-zero exit code means nothing changed; check status immediately afterward.

~~~bash
git status
git ls-files -u
git diff
~~~

If there are conflicts:

1. Open the file and locate conflict regions.
2. Compare base, ours, and theirs if needed.
3. Edit the content to the desired outcome.
4. Stage resolved files with git add.
5. Check git diff --cached and run tests.

Unlike git am, git apply --3way has no --continue command to finish an application sequence. After resolving, you stage and commit yourself if your workflow requires a commit.

### Creating patches with enough info for three-way

When generating a diff to share, you can preserve full blob IDs and binary data:

~~~bash
git diff --full-index --binary base..topic > change.patch
~~~

--full-index writes full blob object IDs in the index header; --binary generates data needed for binary changes. The recipient still needs the base blobs in their object database for three-way merge to work.

If you only have a manually edited text patch and no original objects, Git may lack enough information to perform three-way. In that case, obtain the proper base or resolve manually.

## 11. When to use --reject?

By default, git apply handles patches atomically: if one part fails to apply, Git does not apply the other parts of the patch. The --reject option changes this behavior:

~~~bash
git apply --reject change.patch
~~~

Git applies matching hunks and writes rejected hunks into corresponding .rej files. This is useful when you intentionally want to take independent hunks that apply cleanly and manually handle the rest.

However, the result can be a partial change. After running:

~~~bash
git status --short
git diff
~~~

Find the .rej files and read each hunk:

~~~text
src/greeting.js.rej
~~~

Open the .rej file, compare against current content, and edit manually. After resolving, delete the processed .rej files and inspect the diff. Do not stage or commit while rejected hunks remain unaddressed.

Do not combine --reject with --3way; these are two different failure-handling strategies. Use --3way when base blobs are available for Git to attempt a merge; use --reject when intentionally accepting partial application and handling remaining hunks yourself.

## 12. Edited or malformed patches

If a patch was edited manually, line counts in the hunk header may no longer be accurate. Example:

~~~diff
@@ -10,4 +10,5 @@
~~~

yet the body after the header has a different number of lines than the declared counts. You can try:

~~~bash
git apply --check --recount change.patch
~~~

--recount tells Git to recalculate hunk line counts instead of trusting the counts written in the header. This option only handles count mismatches; it does not repair missing patch content or wrong context.

If a patch is truncated, missing lines, has wrong encoding, or lost binary data, obtain the original file from the sender or regenerate the patch. Do not use --recount to mask a corrupted patch file.

## 13. Handling mailbox patches with git am

When receiving patches from git format-patch, git am is the appropriate tool because it recreates commits from the information in the email patch.

Applying a single patch:

~~~bash
git am 0001-fix-login.patch
~~~

If the patch does not match cleanly but has sufficient base blobs, try:

~~~bash
git am --3way 0001-fix-login.patch
~~~

If a conflict occurs, inspect the patch currently being processed:

~~~bash
git am --show-current-patch=diff
git status
git ls-files -u
~~~

Resolve conflicts in the files, then stage:

~~~bash
git add -- src/login.js
git am --continue
~~~

Commands to control an am series:

| Command | Effect |
| --- | --- |
| git am --continue | Continue after resolving and staging conflicts |
| git am --skip | Skip the current patch and move to the next patch |
| git am --abort | Cancel the entire in-progress am session and return to the state before the session began |
| git am --show-current-patch=diff | Display the diff of the patch currently being processed |

Unlike git apply, git am maintains state for the commit series being applied. Therefore, after resolving conflicts, use --continue; to drop a patch, use --skip; to stop the entire series, use --abort.

## 14. Complete workflow when receiving a mismatched patch

Suppose you receive change.patch, but git apply --check reports an error on two hunks in src/greeting.js.

### Step 1: protect current work

~~~bash
git status -sb
git diff
git diff --cached
~~~

Save any uncommitted changes you need to keep before retrying. Do not wipe the working tree just to make a patch apply.

### Step 2: read patch scope and headers

~~~bash
git apply --stat change.patch
git apply --summary change.patch
~~~

Identify files, renames, modes, and change scope. Open the patch to read context lines around the failing hunks.

### Step 3: inspect base and current file

~~~bash
git log --oneline --follow -- src/greeting.js
git diff -- src/greeting.js
~~~

If the sender provided a base commit, inspect the file at the base:

~~~bash
git show <base-commit>:src/greeting.js
~~~

Compare current content with context lines in the patch. Determine whether the file was modified, renamed, or the patch was previously applied.

### Step 4: check path and whitespace

~~~bash
git apply --check -p1 change.patch
git apply --check -p0 change.patch
git apply --check --ignore-space-change change.patch
~~~

Only test options supported by evidence from patch headers and file content. Do not apply all options at once just to "make it run", as it will hide the true cause.

### Step 5: choose a strategy

- If the patch was created from an old base but base blobs still exist in the repository, try --3way.
- If the patch only differs in whitespace on context lines and the logic still fits, consider --ignore-space-change or --ignore-whitespace.
- If some independent hunks apply and you accept handling the rest manually, use --reject.
- If the patch is already applied, do not re-apply it; verify using reverse check and diff.
- If the patch is missing or has wrong content, request regeneration from the proper base.

### Step 6: review and verify

~~~bash
git status --short
git diff --check
git diff
~~~

If applied to the index or using three-way:

~~~bash
git diff --cached
git ls-files -u
~~~

Ensure no unresolved conflicts or .rej files remain. Run appropriate tests and stage the right files before committing.

## 15. Checking patches for binary, mode, or sensitive path changes

A patch does not contain only text edits. It can:

- Add or delete files.
- Rename or copy files.
- Change file modes, such as toggling executable permissions.
- Contain binary patches.
- Modify configuration files, scripts, or automation workflows.

Before applying a patch from an unfamiliar source, inspect --stat and --summary, then read each file header. Pay attention to paths outside project scope, security configuration files, CI scripts, and auto-executed files.

git apply protects against unsafe paths by default. Do not enable --unsafe-paths just to make a patch apply without verifying the source and all target paths. Do not run patch application with higher administrative privileges than necessary.

For binary patches, the patch must contain corresponding binary data, usually generated with git diff --binary. A text patch without binary content cannot accurately recreate binary file changes.

## 16. Making patches easier to apply

Senders can reduce context errors by generating patches from the right base and keeping required metadata.

### Create a diff between two commits

~~~bash
git diff --full-index --binary <base>..<topic> > change.patch
~~~

The patch represents changes from base to topic. The recipient should have the matching base or the objects needed for three-way merge.

### Create mailbox patches preserving commit metadata

~~~bash
git format-patch -o ../outgoing-patches <base>..<topic>
~~~

Each commit in the range is created as a separate patch file. The recipient uses git am to preserve author, timestamp, and commit message.

### Check patches before sending

~~~bash
git diff --check <base>..<topic>
git diff --stat <base>..<topic>
~~~

Check whitespace and change scope before sharing. State the base commit or branch from which the patch was created, any required dependencies, and application order if the patch has multiple parts.

Do not generate a patch from a working tree mixing multiple unrelated changes if the recipient needs to apply them independently. Splitting patches by purpose makes reviewing, testing, and conflict handling easier.

## 17. Common misconceptions

### Does git apply --check succeeding mean the patch is safe?

No. It only confirms the patch can apply in the current state. You still must review paths, content, file modes, and the impact of the changes.

### Is git diff --check the same as git apply --check?

No. git apply --check verifies whether a patch can apply without modifying files. git diff --check checks an existing diff for certain whitespace errors.

### Does git apply create commits automatically?

No. It applies changes to the working tree or index. To create a commit, you must stage and run git commit.

### Does --3way always solve context errors?

No. Git needs the patch to record original blob IDs and those blobs must exist in the object database. If the base is missing or changes conflict too heavily, you still must resolve manually or obtain a patch against the right base.

### Does --reject keep the entire repository untouched if one hunk fails?

No. It tries to apply matching hunks and writes rejected hunks into .rej files. The outcome can be a partial change; you must review and handle every file.

### Are git apply and git am interchangeable?

Not entirely. git apply is suited for plain diffs and does not create commits. git am processes mailbox patches, creates commits, and preserves the sender's metadata.

### If a patch fails to apply, should you just increase context lines?

No. More context can make a patch harder to apply when code has changed, even though increasing context when creating a patch often helps pinpoint locations and detect base mismatches. The right approach is to identify the base and differences, then regenerate or intentionally merge.

## 18. Self-check

You receive change.patch from a colleague. Running git apply --check reports errors on two hunks in src/api.js. The current file already has a commit renaming a function; the patch was generated from an earlier commit. The patch header has an index line containing old and new blob IDs. Your repository still has the base blob.

Answer:

1. Which command checks a patch without modifying files?
2. Why might a patch fail to match even when the change content still makes sense?
3. Which command can attempt a three-way merge based on the base blob?
4. After --3way produces conflicts, which commands do you use to inspect and resolve them?
5. How does --reject differ from --3way in handling failed hunks?
6. If the patch file is a mailbox from git format-patch and you need to keep author/commit message, which command do you use?
7. Why should you review the diff and run tests after a patch applies successfully?

**Hint:** Use git apply --check change.patch to check first. Hunks may drift because the current file changed relative to the base. Use git apply --3way change.patch if the patch has blob IDs and the base object is available. Check git status, git ls-files -u, resolve conflicts, git add, then review the diff. --reject applies matching parts and creates .rej for failed parts; --3way attempts a merge using the base and may leave conflicts in the index. For mailbox patches, use git am or git am --3way. Finally, verify content, paths, whitespace, and actual behavior.

## Conclusion

Always read a patch and check its scope before applying. git apply --check verifies applicability without modifying files; only then run git apply and review the diff. When facing context errors, inspect the base commit, file contents, path prefix, whitespace, and whether the patch was already applied. Use --3way when base blobs are available for Git to attempt a merge, or --reject when intentionally accepting partial application and handling .rej files. For mailbox patches from git format-patch, use git am to preserve commit metadata. Regardless of which application method succeeds, verify status, diff, conflicts, whitespace, and tests before committing.
