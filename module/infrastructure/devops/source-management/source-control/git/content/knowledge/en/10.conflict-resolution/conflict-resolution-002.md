# Reading Conflict Markers with merge, diff3, and zdiff3

When Git cannot automatically combine two changes, it preserves the contents of each side and marks the region where the developer must decide. Lines such as **<<<<<<<**, **=======**, and **>>>>>>>** are conflict markers. They show which parts of the content disagree, but they do not indicate which part is correct from a business perspective.

In the **Conflict Resolution** chapter of the **SOURCE_CONTROL_GIT** module, this lesson focuses on how to read the three conflict presentation styles: **merge**, **diff3**, and **zdiff3**. Understanding these markers helps you trace each branch's changes, look back at the original content before edits, and produce an intentional merge result.

After this lesson, you will be able to:

- Identify changes from the current branch, the merged branch, and the original version.
- Explain the differences among the three conflict marker styles.
- Choose an appropriate display style and configure Git for a single repository or machine-wide.
- Inspect the versions stored in the index when investigating a difficult conflict.
- Complete conflict resolution and properly continue a merge, rebase, or cherry-pick operation.

## 1. Why Does Git Create Conflict Markers?

Git typically combines changes by comparing three versions:

1. **Base (merge base)**: the closest common ancestor version from which both branches developed.
2. **Ours**: the version on the checked-out side, i.e., the current side of the merge operation.
3. **Theirs**: the version on the incoming side, such as the branch being merged in.

Git can combine changes automatically when they do not overlap or when the outcome can be inferred unambiguously. A conflict occurs when both sides modify the same region in ways that cannot be automatically reconciled, or when structural changes prevent Git from determining a safe result.

For example, the base has a fee calculation rule:

~~~java
return amount * 0.03;
~~~

The current branch changes it to:

~~~java
return amount * 0.05;
~~~

While the merged branch changes the same line to:

~~~java
return amount * 0.04;
~~~

Git does not know whether the 5% or 4% rule reflects the product decision. It marks the conflict region for the developer to review. Choosing one side, combining both, or writing a third implementation must be based on the application's requirements.

Conflict markers are written into the text file in the working tree. At the same time, the index holds the unmerged versions in separate stages. Thus, markers are how Git presents the conflict for human handling; they are not a decision already made by Git.

## 2. The Default merge Style: Reading Both Changed Sides

The **merge** style is concise and is typically the default. A conflict region looks like this:

~~~text
<<<<<<< HEAD
return amount * 0.05;
=======
return amount * 0.04;
>>>>>>> feature/minimum-fee
~~~

Reading from top to bottom:

| Marker | Meaning |
| --- | --- |
| **<<<<<<< HEAD** | Starts the content from the ours side. In a standard merge, this is the content from HEAD, i.e., the current branch. |
| Lines before **=======** | Content of the ours side. |
| **=======** | Boundary between the two sides. |
| Lines after **=======** | Content of the theirs side. |
| **>>>>>>> feature/minimum-fee** | Ends the conflict region; the label identifies the theirs side in this example. |

The names after the opening and closing markers can be branch names, commit hashes/messages, or labels generated by Git. Do not rely solely on the label string to infer the entire history; combine it with the operation in progress and the repository state.

The **merge** style shows the two disagreeing versions but **does not display the base version**. If you only need to choose between two well-understood changes, this short form is often easy to read. If it is unclear why both sides arrived at different results, lacking the base section may force you to open the history or retrieve the original version using other commands.

## 3. The diff3 Style: Viewing the Original Content as Well

The **diff3** style adds the base section between the two sides. Using the same fee calculation example, the conflict region can be presented as follows:

~~~text
<<<<<<< HEAD
return amount * 0.05;
||||||| <merge-base>
return amount * 0.03;
=======
return amount * 0.04;
>>>>>>> feature/minimum-fee
~~~

The **|||||||** marker opens the original content. The label following this marker may identify the merge base or the original version Git used for comparison. This section sits between ours and theirs:

- From **<<<<<<<** to before **|||||||**: content from the ours side.
- From **|||||||** to before **=======**: content from the base.
- From **=======** to before **>>>>>>>**: content from the theirs side.

The base answers an important question: **before the two branches changed, what was the content in this region?** In the example above, we see both branches changed the fee rate from 3%, one to 5% and the other to 4%. That helps distinguish new changes from pre-existing behavior.

Use the base information to understand the intent of the changes, not as a default answer to pick. The base is the shared historical state; it may already be outdated or be the very behavior both branches are trying to replace.

A multi-line example makes this clearer:

**Base**

~~~java
if (enabled) {
    return legacyPolicy();
}
~~~

**Ours**

~~~java
if (enabled) {
    audit();
    return fastPolicy();
}
~~~

**Theirs**

~~~java
if (enabled) {
    return safePolicy();
}
~~~

A conflict region in **diff3** style can show all three versions:

~~~text
<<<<<<< HEAD
if (enabled) {
    audit();
    return fastPolicy();
}
||||||| <merge-base>
if (enabled) {
    return legacyPolicy();
}
=======
if (enabled) {
    return safePolicy();
}
>>>>>>> feature/safe-policy
~~~

Looking at the three sections, we see ours added the audit call and changed the policy to fast; theirs changed the policy to safe. The resolver needs to check the actual requirements: is auditing still needed, which policy is correct, and should the two changes be combined into a new implementation.

## 4. The zdiff3 Style: Keeping Base While Compacting the Conflict Region

The **zdiff3** style also displays the base like **diff3**, while moving common lines at the beginning or end of the conflict region outside the markers when possible. As a result, the section you need to focus on is usually shorter and identical context lines are not repeated inside each side.

With the policy example above, the presentation following the idea of **zdiff3** can look like this:

~~~text
if (enabled) {
<<<<<<< HEAD
    audit();
    return fastPolicy();
||||||| <merge-base>
    return legacyPolicy();
=======
    return safePolicy();
>>>>>>> feature/safe-policy
}
~~~

The two common structural lines **if (enabled) {** and **}** sit outside the marker region. The marked section focuses on the lines that differ across the three versions. This illustrates how compaction works; exact boundaries depend on the content and how Git analyzes the diff region.

Key points to remember:

- **zdiff3** still provides all three perspectives: ours, base, and theirs.
- Common lines moved outside the markers are still part of the file and usually still need to remain in the result.
- Compaction only changes how the conflict region is displayed; it does not automatically choose a policy or resolve disagreements.

## 5. Comparing the Three Conflict Marker Styles

| Style | Shows ours | Shows base | Shows theirs | Characteristics |
| --- | --- | --- | --- | --- |
| **merge** | Yes | No | Yes | Concise, easy to read when both sides are already clear. |
| **diff3** | Yes | Yes | Yes | Shows the content before both sides changed; the displayed block can be longer. |
| **zdiff3** | Yes | Yes | Yes | Includes base information and compacts common lines at the boundaries of the conflict region when possible. |

You can choose based on your needs:

- Use **merge** when conflicts are small, both changes are straightforward, and you do not need to revisit the original state.
- Use **diff3** when you need to investigate why both sides conflict or compare all three versions explicitly.
- Use **zdiff3** when you want to retain base information while reducing repetition, especially for changed blocks with many shared boundary lines.

For frequent conflict resolution work, **zdiff3** is a helpful choice if your installed Git version supports it. Within a team, it is good practice to agree on a display style so members can easily discuss the same conflict region. Regardless of the style chosen, the final outcome must still be based on the intent of the changes and project tests.

## 6. Configuring the Display Style in Git

You can set the conflict marker style at multiple scopes.

**Apply only to the current repository**

~~~bash
git config --local merge.conflictStyle zdiff3
~~~

**Apply by default for all repositories of the current user**

~~~bash
git config --global merge.conflictStyle zdiff3
~~~

**Check the value and configuration source**

~~~bash
git config --show-origin --get merge.conflictStyle
~~~

If the command returns no value, the repository may be using Git's default. You can check the Git version with:

~~~bash
git --version
~~~

To specify a style for a single merge, use the option:

~~~bash
git merge --conflict=diff3 feature/minimum-fee
~~~

Or set a temporary configuration for that single command:

~~~bash
git -c merge.conflictStyle=zdiff3 merge feature/minimum-fee
~~~

The **--conflict** flag lets you choose the presentation style for that merge. The **merge.conflictStyle** setting sets the default for applicable future operations. If you already have a conflict and want to re-examine the same content in a different style, check the file status before asking Git to re-checkout the conflicted version; restoring the file can overwrite your unsaved edits.

## 7. Inspecting Conflicted Versions in the Index

When markers are not enough to explain a complex situation, you can read the unmerged stages in the index.

~~~bash
git ls-files -u -- src/Fee.java
~~~

For a typical conflicted file, Git can store three versions:

| Stage | Content |
| --- | --- |
| **1** | Base, the shared version before both sides changed. |
| **2** | Ours, the version on the current side of the merge operation. |
| **3** | Theirs, the version on the incoming side. |

You can inspect each version using:

~~~bash
git show :1:src/Fee.java
git show :2:src/Fee.java
git show :3:src/Fee.java
~~~

If the file was added independently on both sides, stage 1 may not exist because there is no corresponding base version. Conflict types such as modify/delete or renames can also cause the stage layout to differ from the single-file edit case. Therefore, do not assume all three stages are always present.

The following diff commands help compare the file being resolved against each version:

~~~bash
git diff --base -- src/Fee.java
git diff --ours -- src/Fee.java
git diff --theirs -- src/Fee.java
git diff --cc -- src/Fee.java
~~~

**--base**, **--ours**, and **--theirs** show the differences relative to the base version, the current side, and the incoming side, respectively. **--cc** displays the combined diff for the conflicted content. These commands are useful when the file is long or when markers have already been edited during resolution.

## 8. Workflow for Reading and Resolving a Conflict Region

Handle each file and each conflict region using a verifiable workflow.

### Step 1: Identify the Paused Operation

~~~bash
git status
git diff -- src/Fee.java
~~~

Read Git's output to see whether a merge, rebase, or cherry-pick is in progress. This matters because the meaning of ours and theirs changes depending on the operation.

### Step 2: Read All Three Parts If Available

With **diff3** or **zdiff3**, read ours, base, and theirs in turn. Ask yourself:

- What was the original content doing?
- What did each side change?
- Do both changes share the same goal, or do they follow two different business rules?
- Are there common lines sitting outside the marker region that must be kept?

If the repository uses **merge** style, use commit history, **git show**, or stage inspection commands to check the base when needed.

### Step 3: Decide the Result Based on Intent

Do not pick ours just because it comes first, nor theirs just because it comes last. Valid outcomes may include:

- Keeping one side's change because the other side is outdated.
- Combining both changes if they complement each other.
- Rewriting the code block according to a new design while preserving necessary behaviors from both sides.

For example, if one side adds auditing and the other changes the fee policy, the result may need to keep auditing and use the policy agreed upon by the team. Markers only help reveal the differences; product requirements, API contracts, and tests determine the right outcome.

### Step 4: Edit the File

After deciding, edit the file into its final content. Remove all remaining marker lines:

- **<<<<<<< ...**
- **||||||| ...** if using **diff3** or **zdiff3**
- **=======**
- **>>>>>>> ...**

Do not accidentally delete code lines outside the markers. With **zdiff3**, common lines moved outside the conflict region may still be essential parts of the program.

### Step 5: Verify and Mark as Resolved

~~~bash
git diff -- src/Fee.java
git add -- src/Fee.java
git status
git diff --cached -- src/Fee.java
git diff --cached --check
~~~

**git add** informs Git that the file is resolved and puts the current content into the index. Git does not verify that you removed every marker string or chose the right business logic; therefore, re-read the staged diff and run relevant tests. **git diff --cached --check** helps detect certain whitespace issues in the staged changes.

### Step 6: Continue or Abort the Operation When Needed

Once all files are resolved and verified, continue according to the operation in progress:

~~~bash
git merge --continue
git rebase --continue
git cherry-pick --continue
~~~

Run only the command matching the paused operation. If you decide to return to the state before the operation, the corresponding abort commands are:

~~~bash
git merge --abort
git rebase --abort
git cherry-pick --abort
~~~

Aborting restores the state prior to that process as far as Git can; inspect the repository status and protect any independent edits before running it.

## 9. Common Misconceptions

### Do ours and theirs always mean the same thing?

No. In a standard merge, ours is the current branch and theirs is the branch being merged in. In a rebase, the perspective is easy to confuse: Git is replaying commits from your working branch onto a new base, so the ours side is typically the new base being rebased onto, while the theirs side is the commit being replayed. When encountering a conflict, read the operation message and inspect the index stages instead of guessing from the labels **ours** or **theirs** alone.

### Is the base section the answer you should pick?

No. The base only shows the shared state before the two branches changed. If both sides fixed a bug or implemented a new requirement, the base may be an unsuitable version.

### Does zdiff3 cause fewer Git conflicts?

No. **zdiff3** makes the marker block more compact by moving common boundary lines outside the marked region. It does not change the intent of either branch and does not turn a logical conflict into a safe automatic result.

### Do all conflicts appear as markers in a file?

No. Text markers apply to content that Git can represent as text. Binary conflicts, rename conflicts, or certain path-level situations require different handling. Start with **git status** to see what kind of conflict Git is asking you to resolve.

### Does git add prove the file is correct?

No. **git add** only stages the current content into the index and marks the path as resolved. Git can still create a commit containing leftover markers or broken logic if the developer does not verify. Review the diff, run tests, and check expected behavior before continuing.

## 10. Self-Check on Reading Markers

Suppose a configuration file has three versions:

**Base**

~~~text
retry = 2
~~~

**Ours**

~~~text
retry = 3
~~~

**Theirs**

~~~text
retry = 5
~~~

A marker block in **diff3** style:

~~~text
<<<<<<< HEAD
retry = 3
||||||| <merge-base>
retry = 2
=======
retry = 5
>>>>>>> feature/retry-policy
~~~

Answer for yourself:

1. Which value belongs to base?
2. Which values belong to ours and theirs?
3. Do the markers tell Git it can decide the retry count automatically?
4. If the team wants to retry according to a new policy, can you resolve it by writing a value different from the three above?

**Hint:** base is 2, ours is 3, and theirs is 5. The markers show that both sides changed the same value, but do not indicate which retry count is right. If the new requirement specifies another value, the resolver can write the result according to that policy, then check related configuration, tests, and documentation.

## Conclusion

Read conflict markers as a short narrative of three versions of the same content region. **merge** shows the two changed sides; **diff3** adds the original state; **zdiff3** keeps the original information while compacting common lines at the conflict boundaries. Once you understand each part properly, you can decide which changes to keep, combine, or rewrite, then verify the result with diffs and tests before continuing Git history.
