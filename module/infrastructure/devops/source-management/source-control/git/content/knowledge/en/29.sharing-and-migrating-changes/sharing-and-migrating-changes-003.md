# Distinguishing Patch Application with git apply and git am

When you need to transfer changes between two repositories or two machines that do not share a remote, Git can package the changes into a patch. A patch is data describing which lines are added, modified, or deleted in files. The recipient can use git apply to apply the changes to the working tree or index, or use git am to apply email-formatted patches and create corresponding commits.

The two commands may seem similar, yet they serve two different goals. git apply focuses on applying a diff; it does not automatically create commits. git am reads mail-formatted patch messages, applies each patch, and creates a commit while preserving the author information and commit message packaged in the patch. Choosing the right command helps you retain the necessary history and precisely control which changes enter the repository.

After this lesson, you will be able to:

- Distinguish a standard diff patch from an email-formatted patch.
- Choose git apply when you only need to apply content changes.
- Choose git am when you want to import one or more commits from patch mail.
- Inspect a patch before applying it.
- Understand the impact of the --index, --cached, and --3way options.
- Resolve conflicts when applying a patch or running git am.
- Create patches using git diff and git format-patch.
- Choose the appropriate workflow when sharing changes without pushing directly.

## 1. What is a patch?

A patch is a description of the differences between two content states. For text files, a patch typically includes filenames, context regions, and the lines added or removed. Git can create patches from changes in the working tree, from the staging area, or from commits.

Simple diff example:

~~~diff
diff --git a/src/Search.java b/src/Search.java
index 1234567..89abcde 100644
--- a/src/Search.java
+++ b/src/Search.java
@@ -10,7 +10,7 @@ public class Search {
-    return query;
+    return normalize(query);
 }
~~~

Lines starting with a minus sign are old content that was removed; lines starting with a plus sign are new content that was added. Context lines help Git find the exact location to apply the change.

Patches can be transferred via email, chat, file attachments, or a shared folder. The recipient does not necessarily need a shared remote, but must have a compatible version of the source code for the patch to apply.

## 2. Core differences between git apply and git am

| Criterion | git apply | git am |
| --- | --- | --- |
| Typical input | Diff/patch file | Email-formatted patch or mbox, usually generated by git format-patch |
| Purpose | Modify working tree or index | Apply patch and create commit |
| Creates commit | No | Yes, usually one commit per mail patch |
| Preserves author and commit message | No commit metadata to preserve in a standard diff | Can preserve author, author date, and message from patch mail |
| Creator of new commit | User commits manually after applying | User running git am becomes the committer |
| Handling a series of changes | Apply diff, then stage/commit manually | Process patch series in sequence |
| On conflict | Command stops; user resolves content and commits manually | Pauses mail patch series; resolve then continue, skip, or abort |

Remember:

- git apply puts changes into the working tree or index, depending on options.
- git am imports a series of changes with commit metadata and creates new commits in the current repository.

A patch created by git diff typically describes only content changes. A patch created by git format-patch also packages author details, the commit message, and the mail headers needed for git am to recreate commits.

## 3. Using git diff to create a patch for git apply

Suppose you have edited a file without staging it. Create a patch from working tree changes:

~~~bash
git diff > search-fix.patch
~~~

This patch contains unstaged changes. If the changes are already in the staging area, use:

~~~bash
git diff --cached > search-fix.patch
~~~

If you want to create a patch from all tracked changes in the working tree and staging area relative to HEAD, you can use:

~~~bash
git diff HEAD > all-changes.patch
~~~

Default text patches cannot fully represent binary content. When binary changes need to be included, create the patch with:

~~~bash
git diff --binary HEAD > all-changes.patch
~~~

The --binary option adds the data needed for Git to apply binary changes. The recipient still needs Git apply to process that patch.

A patch from git diff does not carry an author, commit message, or commit structure. It only describes content changes relative to a baseline state.

## 4. Checking a patch before applying

Before modifying the working tree, inspect the patch:

~~~bash
git apply --stat search-fix.patch
git apply --summary search-fix.patch
git apply --check search-fix.patch
~~~

- --stat displays file statistics and the number of changed lines.
- --summary displays high-level summary information such as creations, deletions, renames, or file modes if the patch contains that data.
- --check checks whether the patch can apply cleanly without actually modifying files.

Visually inspecting the patch is also important. A patch may modify the wrong file, contain out-of-scope changes, or have been generated from an incompatible source version.

If a patch comes from an untrusted source, read its full contents and verify file paths before applying. A patch could add scripts or executable code; applying the patch does not run that code automatically, but committing or running a build afterward may execute the newly added content.

## 5. Applying a patch with git apply

Once the patch has been checked, apply it:

~~~bash
git apply search-fix.patch
~~~

By default, git apply updates the working tree, does not automatically stage changes, and does not create a commit. Check:

~~~bash
git status --short
git diff
~~~

After reviewing the changes, you can stage and commit following your normal workflow:

~~~bash
git add src/Search.java
git diff --cached
git commit -m "Normalize search query"
~~~

This is useful when you only want the content of the changes and want to decide yourself how to commit, write the commit message, or combine it with other work.

### Applying directly to the staging index with --cached

If you want the patch to update only the index without modifying the working tree:

~~~bash
git apply --cached search-fix.patch
~~~

Then inspect the staged changes:

~~~bash
git diff --cached
git status --short
~~~

The --cached option affects only the index. Contents in the working tree are not updated to match the patch, so files may differ from their staged versions. This is intentional behavior when you want to prepare a commit snapshot while keeping the working tree in a separate state.

### Updating both the working tree and index with --index

~~~bash
git apply --index search-fix.patch
~~~

The --index option tells Git to update both the index and the working tree. For affected paths, the initial index and working tree states must match; if they already differ, the command may reject the operation to avoid losing separately staged state.

Comparison:

| Command | Working tree | Index |
| --- | --- | --- |
| git apply patch | Updated | Unchanged |
| git apply --cached patch | Unchanged | Updated |
| git apply --index patch | Updated | Updated |

Do not confuse git apply --cached with standard git apply. Choose based on where you want the patch to appear.

## 6. Useful git apply options

### Checking and reversing a patch

Check a patch without applying:

~~~bash
git apply --check search-fix.patch
~~~

If you need to undo the exact patch you just applied, you can use:

~~~bash
git apply --reverse search-fix.patch
~~~

--reverse reverses the changes described in the patch. The command only succeeds if the current contents match the state expected by the patch. Do not use it as a general undo command for arbitrary changes; inspect diff and status first.

### Adjusting paths with -p

Patches usually contain paths like a/src/Search.java and b/src/Search.java. By default, git apply strips one leading path component. The -p<n> option changes the number of stripped components:

~~~bash
git apply -p1 search-fix.patch
git apply -p2 search-fix.patch
~~~

If a patch was created from a different directory or the target repository has a different structure, -p can help map paths correctly. Use --directory to prepend a directory prefix to paths after stripping leading components:

~~~bash
git apply --directory=vendor/shared search-fix.patch
~~~

Before applying with -p or --directory, use --stat or read the patch to confirm the target paths.

### Handling whitespace

Patches may contain trailing whitespace differences. The --whitespace option controls how Git handles them:

~~~bash
git apply --whitespace=warn search-fix.patch
git apply --whitespace=fix search-fix.patch
~~~

- warn warns about whitespace errors.
- fix attempts to fix whitespace errors recognized by Git while applying.

This option does not replace a formatter or project formatting rules. If whitespace is significant in a file or the patch was created by another tool, inspect the result after applying.

### Applying successful hunks and writing rejected ones

~~~bash
git apply --reject search-fix.patch
~~~

With the --reject option, Git attempts to apply hunks that match and writes non-matching hunks into .rej files. You must open the .rej files, manually apply the rejected parts, and inspect the diff afterward. This option cannot be combined with --3way.

## 7. Applying a patch with the three-way mechanism

Patches generated from diff can record OIDs of old and new blobs. If the corresponding base object is available in the repository, Git can use the blob contents to perform a three-way merge instead of looking only for exact context matches.

With git apply:

~~~bash
git apply --3way search-fix.patch
~~~

--3way instructs Git to attempt applying the patch via a three-way merge when sufficient object information is available. This option implies updating the index, unless used with --cached in a Git-supported manner. If conflicts arise, paths may enter an unmerged state.

Check:

~~~bash
git status --short
git diff
git diff --cached
~~~

Open the conflicted files, locate the conflict markers, edit to the desired content, and stage:

~~~bash
git add src/Search.java
git diff --cached
~~~

git apply does not create a commit after resolving conflicts. You inspect, stage the necessary files, and commit according to your workflow.

Three-way can only work when the patch has enough information to identify the base blob and the necessary objects are accessible locally. If the patch only contains an abbreviated diff or the repository lacks the base object, Git may be unable to perform a three-way merge.

## 8. How does git am use email-formatted patches?

git am is designed to apply email messages containing patches, typically created with git format-patch. A patch mail includes email headers, the commit message, and the diff section. Because of this, Git can create commits with the packaged author metadata.

Example creating a patch for the current commit:

~~~bash
git format-patch -1 HEAD
~~~

The command creates a file like:

~~~text
0001-normalize-search-query.patch
~~~

Transfer this file to the receiving repository. On the target branch, verify a clean state and run:

~~~bash
git am 0001-normalize-search-query.patch
~~~

Git reads the mail patch content, applies the changes, and creates a commit. The new commit typically retains the author, author date, and commit message from the patch. The user running git am becomes the committer, and a new commit hash is generated because the commit is attached to the current parent along with new commit metadata.

### Importing a series of commits

If you want to send a series of commits not yet present on the target branch, use git format-patch with a commit range:

~~~bash
git format-patch -o ../patches origin/main..HEAD
~~~

The range origin/main..HEAD selects commits reachable from HEAD that are not in origin/main. The patches are numbered to indicate order.

In the receiving repository, apply the patches sequentially in the order they were generated:

~~~bash
git am ../patches/0001-first-change.patch ../patches/0002-second-change.patch
~~~

Replace the filenames with the actual files in the patch directory. If there is a single mbox file containing multiple messages, you can pass that mbox file directly to git am.

Do not pass a plain diff created by git diff to git am and expect Git to reconstruct the author and commit message. For plain diffs, use git apply. If you want to preserve commit structure, generate patches with git format-patch.

## 9. git am and commit metadata

A mail patch created by git format-patch typically contains:

- From: author of the original commit.
- Date: timestamp when the author created the commit.
- Subject: commit message, usually prefixed with [PATCH].
- Commit description body.
- Commit diff.

git am uses that information to create a new commit. The user running the command becomes the committer. The new commit ID usually differs from the original commit ID because the parent, committer, or part of the metadata may differ.

If you need to add a Signed-off-by line for the person importing the patch:

~~~bash
git am --signoff 0001-normalize-search-query.patch
~~~

This option appends a sign-off line to the generated commit message. A sign-off is an attestation under project workflow rules and is not automatically equivalent to a cryptographic commit signature.

If you want to keep the [PATCH] prefix in the subject instead of letting Git strip it per default rules:

~~~bash
git am --keep 0001-normalize-search-query.patch
~~~

Only use this option when your team's workflow requires preserving the subject prefix.

## 10. Three-way merge with git am

When a mail patch does not apply cleanly because code on the target branch has changed, you can ask Git to attempt a three-way merge:

~~~bash
git am --3way 0001-normalize-search-query.patch
~~~

Git uses blob information in the patch and available objects to try merging the changes. If a conflict occurs, git am pauses the patch series and preserves the current processing state.

View the patch currently being applied:

~~~bash
git am --show-current-patch=diff
~~~

Check conflicted files:

~~~bash
git status --short
~~~

Open the files, resolve conflict markers, then stage the result:

~~~bash
git add src/Search.java
~~~

Continue the patch series:

~~~bash
git am --continue
~~~

If there are remaining patches, Git continues processing them in order. If the current patch is no longer needed, you can skip it:

~~~bash
git am --skip
~~~

If you want to abort the entire in-progress git am session and return to the state before starting:

~~~bash
git am --abort
~~~

--continue finishes the in-progress patch after resolving and staging; --skip drops the current patch; --abort cancels the entire series being processed. Inspect status and the current patch before choosing.

## 11. Troubleshooting when git apply fails to apply

If git apply reports errors such as patch failed or file not found, common causes include:

- The target repository is not at the base version from which the patch was created.
- Files have been renamed or moved.
- Context region contents have changed.
- The patch is missing lines, has corrupted encoding, or had whitespace altered by an email client.
- Paths in the patch do not match the current repository structure.

Inspection workflow:

~~~bash
git status --short --branch
git apply --stat search-fix.patch
git apply --check search-fix.patch
~~~

If the patch cannot apply, determine the branch and base commit the sender used. You can check out the exact base in a separate worktree, or try --3way if the patch has blob IDs and the base objects exist. Avoid repeatedly applying a patch onto a working tree that has already been partially modified.

If using --reject, inspect every .rej file and compare against the original file. Do not ignore rejected hunks just because the command applied the remaining parts.

## 12. Troubleshooting when git am stops

When git am fails due to a conflict or unapplicable patch:

1. Run git status --short to identify conflicted files.
2. Use git am --show-current-patch=diff to view the current patch.
3. Inspect changes in the working tree and index.
4. Resolve conflicts and stage files with git add.
5. Run git am --continue to create the commit and continue the series.

If the patch is unnecessary or cannot apply on this branch, consider --skip after verification. If you want to abandon the entire patch import process, use --abort.

Do not manually delete Git's state directory while am is running. Use continue, skip, or abort so Git closes the session cleanly.

## 13. Choosing the tool based on your goal

| Need | Appropriate tool | Outcome |
| --- | --- | --- |
| Transfer only content changes | git diff and git apply | Working tree or index modified; no automatic commit |
| Stage patch without modifying working tree | git apply --cached | Index updated |
| Apply patch that may require three-way | git apply --3way | Changes applied or conflicts left to resolve |
| Transfer one commit with author and message | git format-patch and git am | New commit created from mail patch |
| Transfer a commit series | git format-patch range and git am | Commit series recreated in order |
| Import mail patch and add sign-off | git am --signoff | New commit with Signed-off-by line |

If you only need the content and want to write a new commit yourself, apply is usually simpler. If you want to transfer commit history via email or patch files, format-patch combined with am is more suitable.

## 14. Practical workflow: transferring changes without commits

The sender creates a patch from staged changes:

~~~bash
git diff --cached --binary > search-change.patch
~~~

Transfer the patch file to the recipient. The recipient runs:

~~~bash
# Check repository status
git status --short --branch

# View statistics and check applicability
git apply --stat search-change.patch
git apply --check search-change.patch

# Apply to the working tree
git apply search-change.patch

# Inspect changes
git diff
git status --short

# Stage and create commit per local workflow
git add src/Search.java
git diff --cached
git commit -m "Apply search improvement"
~~~

The recipient chooses the commit content and metadata for the new commit. The patch does not carry the original commit.

## 15. Practical workflow: transferring commits while preserving author metadata

The sender has a completed commit:

~~~bash
git format-patch -1 HEAD
~~~

Transfer the patch file to the recipient. The recipient switches to the target branch and checks:

~~~bash
git status --short --branch
git log --oneline -n 5
~~~

After confirming a clean working tree and the right branch:

~~~bash
git am 0001-normalize-search-query.patch
~~~

Inspect the new commit:

~~~bash
git log -1 --format=fuller
git show --stat --oneline HEAD
~~~

The fuller output shows Author, AuthorDate, Commit, and CommitDate. You can compare the metadata with the original commit provided by the sender.

If patches were created from multiple commits, use git format-patch with a range and apply all files in order. After importing, check git log to confirm the count, order, and commit contents.

## 16. Common mistakes

### Using git apply and seeing no new commit

This is expected behavior. git apply only modifies the working tree or index. Stage and commit manually if you want to create a commit.

### Using git am with a patch created by git diff

Plain diffs do not contain full mail commit metadata. Use git apply to apply a diff, or ask the sender to generate patches with git format-patch if commit metadata needs to be preserved.

### git apply reports patch does not match

Check the base version, paths, and context. Run --check first, inspect the patch, and consider --3way when base objects are available.

### git am stops mid-series

Check conflicted files and the current patch. Resolve, then git add and git am --continue; use --skip or --abort as decided.

### Commit after git am has a different hash from the original commit

This is normal. The new commit may have a different parent and committer. Git preserves author info and message but creates a new commit object in the target history.

### Applying a patch multiple times

A patch normally applies only when the baseline content matches. Run --check and check git status each time. If partially applied, do not re-run the entire patch without determining the state of each file.

### Using --reject and forgetting .rej files

Rejected hunks are written to .rej files. Open and handle all of these files, then inspect the diff before committing.

## 17. Key takeaways

- A patch describes differences; a standard diff patch is not a commit.
- git apply applies a diff to the working tree by default and does not automatically create a commit.
- git apply --cached updates only the index; --index updates both the index and the working tree.
- git apply --check helps verify a patch before modifying files; --3way can use blob IDs and base objects to merge.
- git am reads email/mbox patches and creates new commits, typically preserving author, author date, and commit message.
- git format-patch is the standard way to export commits as mail patches for git am.
- When git am encounters conflicts, resolve and stage files, then run --continue; use --skip or --abort when needed.
- Commits created by git am usually have a different hash than the original commits because parent or committer metadata differs.
- Choose apply when you need content; choose format-patch/am when you need to transfer commits with metadata.

Both git apply and git am help transfer changes without pushing directly between two repositories, but the results they produce differ. Understanding the boundary between diff content and commit metadata helps you choose the right tool, handle conflicts in a controlled manner, and maintain history aligned with your team's collaboration workflow.
