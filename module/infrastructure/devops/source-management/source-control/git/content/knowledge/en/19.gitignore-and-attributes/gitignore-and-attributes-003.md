# Path Patterns, /, **, and Negation Rules in .gitignore

When working with Git, a repository often contains files meant only for the development machine or the build process, such as output directories, log files, caches, temporary files, and private configurations. You can declare patterns in <code>.gitignore</code> so Git does not suggest those untracked files during normal operations. However, a pattern with a misplaced <code>/</code>, an improper wildcard, or a negation missing parent directory access can cause Git to ignore more files than intended or fail to bring a needed file back.

This lesson explains how Git interprets path patterns in <code>.gitignore</code>, the difference between patterns with and without <code>/</code>, the meaning of <code>*</code> and <code>**</code>, the precedence order between rules, and how to use <code>!</code> to handle exceptions. This is part of the **Ignore and attributes** chapter of the **SOURCE_CONTROL_GIT** module, helping you keep project files tidy while ensuring shared content is tracked properly.

## 1. What Is .gitignore Used For?

A <code>.gitignore</code> file contains path patterns that Git uses to identify untracked files that should be ignored. When a new file matches an ignore rule, <code>git status</code> usually does not list it under untracked files. This is useful for auto-generated files such as:

- Build and output directories.
- Log files and temporary files.
- IDE or build tool caches.
- Dependency directories reinstalled from a package manager.
- Local configurations containing machine-specific paths or settings.

Example:

~~~gitignore
# Build output
build/
out/

# Log files
*.log

# Local environment settings
.env.local
~~~

The patterns above ignore the <code>build</code> and <code>out</code> directories, any file ending in <code>.log</code> within the ignore file's scope, and the <code>.env.local</code> file.

Point to remember: <code>.gitignore</code> primarily governs paths not yet tracked by Git. If a file has already been committed or is already in the index as a tracked file, adding the filename to <code>.gitignore</code> does not automatically stop tracking that file. To keep the file on disk while stopping tracking, you must remove it from the index with the appropriate command, for example:

~~~bash
git rm --cached -- config/local-settings.json
~~~

Then commit the index removal along with the appropriate ignore rule. The file's content remains on the current machine, but Git stops tracking changes to that file in subsequent commits.

## 2. Where Is a .gitignore File Applied?

A repository can have multiple <code>.gitignore</code> files. The file in the root directory applies to paths across the entire directory tree below it. You can also place a <code>.gitignore</code> file in a subdirectory so that rules apply only from that directory downward.

Example structure:

~~~text
project/
|-- .gitignore
|-- src/
|   |-- .gitignore
|   |-- app.log
|   |-- main.java
|-- build/
|   |-- app.jar
|-- docs/
|   |-- draft.tmp
~~~

Rules in <code>project/.gitignore</code> are evaluated relative to the <code>project</code> directory. Rules in <code>project/src/.gitignore</code> are evaluated relative to <code>src</code>, not from the repository root.

Git also has other ignore rule sources:

1. Patterns passed directly via certain Git commands.
2. <code>.gitignore</code> files in the directory containing the path and parent directories.
3. The repository-specific exclude file at <code>.git/info/exclude</code>.
4. The global ignore file configured by <code>core.excludesFile</code>.

Rules in <code>.gitignore</code> are shared with the repository when that file is committed. <code>.git/info/exclude</code> is suited for rules applying only to the current clone, while the global ignore file is suited for files generated by personal tools that you do not want to put into every project.

## 3. Pattern Structure and Special Characters

Each non-empty line in <code>.gitignore</code> is a pattern. Git interprets certain characters according to glob rules, not regular expressions.

| Symbol | Meaning |
|---|---|
| <code>*</code> | Matches zero or more characters, without crossing the directory separator <code>/</code> |
| <code>?</code> | Matches any single character except <code>/</code> |
| <code>[abc]</code> | Matches one character from the listed character set |
| <code>[0-9]</code> | Matches one character within the declared range |
| <code>**</code> | In positions supported by Git, matches across multiple directory levels |
| <code>!</code> at start of line | Negates a previous ignore rule to bring matching paths back |
| <code>#</code> at start of line | Starts a comment line |
| <code>\</code> | Escapes a special character in a pattern |

Example:

~~~gitignore
*.log
report-?.csv
image-[0-9].png
~~~

The patterns respectively match files ending in <code>.log</code>, files with any single character between <code>report-</code> and <code>.txt</code>, and image files with a single digit in the specified position.

### Blank Lines, Comments, and Whitespace

- Blank lines create no rules.
- Lines starting with <code>#</code> are comments.
- A leading <code>#</code> in a name must be escaped if meant as a literal character.
- Trailing spaces on a line are ignored unless escaped with a backslash.
- A leading <code>!</code> at the start of a line means negation; if a path name actually starts with <code>!</code>, escape that character.

Example:

~~~gitignore
# Ignore generated reports
*.report

\#notes.txt
\!important.txt
name-with-space\ 
~~~

In this example, <code>\#notes.txt</code> is a filename starting with a hash, <code>\!important.txt</code> is a filename starting with an exclamation mark, and the trailing space in the last pattern is preserved by escaping.

## 4. Meaning of / in .gitignore

The <code>/</code> character determines where a pattern is anchored and whether directory levels are considered. This is the most common source of confusion when writing ignore rules.

### Patterns Without a Middle /

If a pattern contains no <code>/</code>, except for a trailing <code>/</code> indicating a directory, the pattern can match at any level beneath the location of the <code>.gitignore</code> file.

Example in a <code>.gitignore</code> file at the repository root:

~~~gitignore
temp
*.log
~~~

The <code>temp</code> rule can match a file or directory named <code>temp</code> at the root, inside <code>src/temp</code>, <code>docs/temp</code>, or deeper levels. If it matches a directory, the contents inside that directory are also ignored.

The <code>*.log</code> rule can match log files in multiple subdirectories, for example:

~~~text
app.log
src/debug.log
src/test/integration.log
~~~

### Patterns With a Leading /

A leading <code>/</code> anchors the pattern to the directory containing the <code>.gitignore</code> file. If the file is at the repository root, a pattern starting with <code>/</code> applies only from that root.

~~~gitignore
/TODO
/build/
~~~

In the root ignore file:

- <code>/TODO</code> matches a file or directory named <code>TODO</code> right at the root.
- <code>/build/</code> matches the <code>build</code> directory right at the root and its contents.
- <code>src/TODO</code> does not match <code>/TODO</code>.
- <code>src/build/</code> does not match <code>/build/</code>.

### Patterns With a Middle /

If a pattern contains a <code>/</code> in the middle, the pattern is evaluated relative to the directory containing the <code>.gitignore</code> file. Example:

~~~gitignore
doc/frotz
logs/archive/
~~~

In the root <code>.gitignore</code>, <code>doc/frotz</code> matches the path <code>doc/frotz</code> beneath the root. It does not mean matching every file named <code>frotz</code> in any directory. Similarly, <code>logs/archive/</code> targets the <code>archive</code> directory directly inside <code>logs</code>.

### Trailing / Indicates a Directory

A pattern ending with <code>/</code> matches only directories:

~~~gitignore
cache/
~~~

This rule matches a directory named <code>cache</code> and its contents, not a regular file named <code>cache</code>. When Git ignores a directory, its child files are also not listed individually in untracked status.

If you omit the <code>/</code>:

~~~gitignore
cache
~~~

the pattern can match both files and directories named <code>cache</code> at any level under the ignore file's location.

### Quick Comparison

Assume all patterns are in a <code>.gitignore</code> file at the root:

| Pattern | Matching examples | Non-matching examples |
|---|---|---|
| <code>build</code> | <code>build</code>, <code>src/build</code>, <code>src/a/build</code> | Not restricted by level if the component name is build |
| <code>/build</code> | <code>build</code> at root | <code>src/build</code> |
| <code>build/</code> | Directory <code>build</code> at any applicable level | Regular file named <code>build</code> |
| <code>/build/</code> | Directory <code>build</code> at root | <code>src/build/</code> |
| <code>src/build/</code> | Directory <code>src/build/</code> | <code>other/build/</code> |
| <code>*.log</code> | <code>app.log</code>, <code>src/app.log</code> | Files without the <code>.log</code> extension |
| <code>/logs/*.log</code> | Log files directly inside <code>logs/</code> at root | <code>logs/archive/app.log</code> |

Always evaluate paths from the location of the <code>.gitignore</code> file containing the pattern. If the pattern is inside a subdirectory, a leading <code>/</code> anchors to that subdirectory, not the repository root.

## 5. Wildcards * and ?

Wildcards help group many filenames into one rule. However, <code>*</code> does not cross <code>/</code>; to match multiple directory levels, you need to understand the <code>**</code> syntax.

Example:

~~~gitignore
*.tmp
report-?.csv
backup-[0-9].zip
~~~

With these patterns:

- <code>*.tmp</code> matches files with the <code>.tmp</code> extension at any level applicable to the ignore file's location.
- <code>report-?.csv</code> matches <code>report-1.csv</code> or <code>report-a.csv</code>, but does not match <code>report-12.csv</code> because <code>?</code> represents only a single character.
- <code>backup-[0-9].zip</code> matches a single digit at the bracketed position.

The pattern <code>src/*.log</code> matches only log files directly inside <code>src</code>, such as <code>src/app.log</code>. It does not match <code>src/test/app.log</code>, because <code>*</code> does not cross directory separators.

If you want to ignore log files at every level, use a pattern without <code>/</code> such as <code>*.log</code>. If you want to scope to a directory tree, use <code>/</code> and <code>**</code> intentionally.

## 6. Special Meaning of **

Git supports <code>**</code> in certain pattern constructs to match across multiple directory levels. The key forms are:

### Leading **/

~~~gitignore
**/cache
~~~

Matches a path component named <code>cache</code> at any directory level. For a simple pattern with no <code>/</code> like <code>cache</code>, the result is usually equivalent.

### Trailing /**

~~~gitignore
logs/**
~~~

Matches all contents inside the <code>logs</code> directory, at any depth. Example:

~~~text
logs/app.log
logs/2026/11/app.log
logs/archive/old/server.log
~~~

This pattern targets the contents inside <code>logs</code>. If you want to ignore the <code>logs</code> directory itself along with all its contents, you can use <code>logs/</code>.

### Middle /**/

~~~gitignore
a/**/b
~~~

Matches paths:

~~~text
a/b
a/x/b
a/x/y/b
~~~

The <code>**/</code> segment can represent zero or more directory levels. Thus, the pattern still matches when there is no intermediate directory between <code>a</code> and <code>b</code>.

### Practical Examples

~~~gitignore
# Ignore node_modules directories at every level
**/node_modules/

# Ignore contents inside the generated directory at root
/generated/**

# Ignore any file named secrets.json in the project tree
**/secrets.json

# Ignore cache files at every level
**/*.cache
~~~

The <code>**/node_modules/</code> pattern catches dependency directories nested across multiple packages. The <code>/generated/**</code> pattern limits scope to the <code>generated</code> directory at the root. The <code>**/secrets.json</code> pattern applies to files of that name at any level.

Do not overuse <code>**</code>. When a pattern without <code>/</code> already expresses the exact intent, use the simpler pattern so it is easier for readers to understand and avoids hard-to-maintain rules.

## 7. Negation Rules Using !

A leading <code>!</code> negates an earlier ignore rule. It allows bringing a specific path back into the set tracked by Git, even if that path matches a broader ignore pattern.

For example, ignore all log files but keep a sample log file:

~~~gitignore
*.log
!examples/sample.log
~~~

In this example, <code>examples/sample.log</code> is brought back, provided its parent directories are not excluded from traversal.

### Rule Order Matters

Within the same precedence level, the last matching rule determines the outcome. Therefore, a negation rule is usually placed after the ignore rule it needs to reverse:

~~~gitignore
*.log
!important.log
~~~

<code>important.log</code> is not ignored, while other log files remain ignored.

If you reverse the order:

~~~gitignore
!important.log
*.log
~~~

the ignore rule on the later line matches that file again, so the file remains ignored.

### Cannot Re-Allow Files Inside an Already-Ignored Parent Directory

This is the most important limitation of negation rules. If Git has already ignored a directory, Git does not traverse the paths inside that directory to look for negation patterns. Therefore, merely writing:

~~~gitignore
build/
!build/keep.txt
~~~

is usually not enough to bring <code>build/keep.txt</code> back. The <code>build</code> directory has already been excluded from traversal.

An appropriate way to write this is to ignore the child items instead of ignoring the entire parent directory:

~~~gitignore
build/*
!build/keep.txt
~~~

Here <code>build/</code> is still traversed by Git, its immediate entries are ignored by <code>build/*</code>, and then <code>keep.txt</code> is negated on the next line.

### Re-Allowing a Subdirectory and a Specific File

Suppose you want to ignore most contents inside <code>build</code>, while keeping <code>build/keep/important.txt</code>. You can write:

~~~gitignore
build/*
!build/keep/
build/keep/*
!build/keep/important.txt
~~~

Explanation:

1. <code>build/*</code> ignores immediate entries inside <code>build</code>.
2. <code>!build/keep/</code> re-allows the <code>keep</code> directory so Git can traverse inside it.
3. <code>build/keep/*</code> ignores immediate entries inside the <code>keep</code> directory.
4. <code>!build/keep/important.txt</code> re-allows the file to keep.

If the file to keep is nested deeper, each parent directory along the path must also be re-allowed so Git can traverse down. Verify rules with <code>git check-ignore</code> rather than relying solely on filename reasoning.

## 8. Which Rules Have Higher Precedence?

When multiple sources provide ignore rules, Git applies a precedence order. From highest to lowest:

1. Patterns passed on the command line to commands that support them.
2. <code>.gitignore</code> files in the directory containing the path and parent directories. A file in a deeper directory can override a file in a parent directory.
3. The <code>$GIT_DIR/info/exclude</code> file of the current repository.
4. The global ignore file specified by <code>core.excludesFile</code>.

Within the same file or same precedence level, the last matching rule takes effect. A rule in a deeper <code>.gitignore</code> file can override a rule in a parent file, allowing a subdirectory to have its own exceptions.

Example:

~~~text
project/
|-- .gitignore
|-- logs/
|   |-- .gitignore
|   |-- important.log
|   |-- debug.log
~~~

Root file:

~~~gitignore
*.log
~~~

<code>logs/.gitignore</code> file:

~~~gitignore
!important.log
~~~

The rule in the <code>logs</code> directory can bring <code>logs/important.log</code> back, while <code>logs/debug.log</code> remains ignored by the root rule. The parent directory <code>logs</code> is not ignored in this example, so Git can read the ignore file inside it.

## 9. Paths in .gitignore on Windows and Linux

In <code>.gitignore</code> patterns, directory separators must be written with a forward slash <code>/</code>, even when working on Windows.

Example:

~~~gitignore
build/
src/generated/
logs/**/*.log
~~~

Do not write path patterns in Windows style with backslashes as directory separators:

~~~text
build\
src\generated\
~~~

In Git patterns, the backslash serves to escape special characters, not as a directory separator to use in <code>.gitignore</code>. Use <code>/</code> so patterns behave consistently across operating systems.

## 10. Checking Why a File Is Ignored

When <code>git status</code> does not show a file you think should be tracked, do not rush to add more negation rules. Ask Git which rule is matching.

### Using git check-ignore -v

~~~bash
git check-ignore -v -- build/app.jar
~~~

The <code>-v</code> option displays the rule source, line number, and matched pattern. The output may look like:

~~~text
.gitignore:4:/build/    build/app.jar
~~~

The output shows that line 4 in the root <code>.gitignore</code> file is ignoring this path. You can fix the exact rule instead of adding an exception in an unrelated location.

### Checking Tracked Paths as Well

Normally, <code>git check-ignore</code> does not report a path already tracked by Git in the index. If you want to check whether an ignore pattern matches a tracked path, use <code>--no-index</code>:

~~~bash
git check-ignore -v --no-index -- config/application.yml
~~~

This option is useful when you have just added a pattern to <code>.gitignore</code> and want to confirm whether it matches an already-tracked file. A match does not mean the file has automatically stopped being tracked; you still need to act on the index if you want to untrack it.

### Listing Ignored Files

~~~bash
# Show ignored paths in status as well
git status --ignored

# Short form, easier to scan
git status --short --ignored
~~~

This command helps inspect the actual ignore scope. Repositories with many build directories can produce long output; you can specify paths when checking with <code>git check-ignore</code>.

## 11. When You Need to Add an Ignored File

Sometimes you want to add a template or configuration file that is ignored by a general rule. There are two approaches depending on your goal.

### Force-Adding a File

~~~bash
git add -f examples/sample.env
~~~

The <code>-f</code> option forces Git to add the path even though it matches an ignore rule. This fits a one-off exception, but does not change the rules in <code>.gitignore</code>. If the file continues to need sharing, the team should consider having an explicit negation rule so other members can add that file normally as well.

### Writing an Exception in .gitignore

~~~gitignore
*.env
!examples/sample.env
~~~

Then verify:

~~~bash
git check-ignore -v -- examples/sample.env
git status --short
~~~

If the path is still ignored, check parent directories and rule order. A negation pattern cannot re-allow a file if a parent directory is still ignored.

## 12. Common Practical Patterns

### Ignore Build Output but Keep Documentation

~~~gitignore
/build/*
!/build/README.md
~~~

This pattern ignores items inside the <code>build</code> directory at the root while keeping the documentation file. Since the <code>build</code> directory itself is not directly ignored, Git can traverse it to apply the exception.

### Ignore Log Files at All Levels, Keep Sample Log

~~~gitignore
*.log
!examples/sample.log
~~~

This pattern is suitable when generated logs should not be committed, yet the team wants to keep a sample file illustrating the log format. If the <code>examples</code> directory is ignored by another rule, that directory must be re-allowed first.

### Ignore Caches at All Levels

~~~gitignore
**/.cache/
**/*.tmp
~~~

The first rule ignores <code>.cache</code> directories at every level; the second ignores temporary files ending in <code>.tmp</code>.

### Ignore Local Configs but Keep Template File

~~~gitignore
.env
.env.*
!.env.example
~~~

This example ignores environment files and variants, while allowing the template file <code>.env.example</code> to be committed. Make sure the template file contains no real passwords, tokens, or secrets.

### Ignore Only the Root generated Directory

~~~gitignore
/generated/
~~~

The <code>generated</code> directory at the root is ignored, whereas a directory of the same name inside <code>src/generated</code> is unaffected by this rule.

## 13. Workflow for Designing and Testing Rules

When writing or modifying <code>.gitignore</code>, follow this workflow:

1. Identify the exact paths to ignore and the exception paths to keep.
2. Determine where the <code>.gitignore</code> file is placed to calculate relative scope.
3. Choose the simplest pattern possible: no slash if matching all levels, with slash if restricting paths.
4. Use <code>*</code> for a single name component and <code>**</code> when you genuinely need to cross multiple directory levels.
5. Place negation rules after the ignore rules they need to reverse.
6. Ensure every parent directory of an exception path can be traversed by Git.
7. Verify with <code>git check-ignore -v</code> and <code>git status --ignored</code>.
8. Confirm tracked files are not mistakenly assumed to be untracked.

Example of testing a new rule:

~~~bash
# Check which rule is ignoring the file
git check-ignore -v -- logs/app.log

# Check file statuses, including ignored files
git status --short --ignored

# If needed, test patterns against an already-tracked file
git check-ignore -v --no-index -- config/application.yml
~~~

Test both the cases that should be ignored and the cases that should be kept. A good rule not only ignores generated files accurately, it also avoids hiding source files, template configs, or documentation that the team needs to commit.

## 14. Common Errors

| Symptom | Possible cause | Resolution |
|---|---|---|
| <code>*.log</code> does not match as expected | Ignore file is inside a subdirectory or file is already tracked | Check the location of <code>.gitignore</code>; use <code>git check-ignore -v</code> |
| <code>/build/</code> does not ignore <code>src/build/</code> | Leading slash anchors pattern to directory containing ignore file | Use <code>build/</code> or a pattern matching the directory tree |
| <code>src/*.log</code> does not match logs in subdirectories | <code>*</code> does not cross slashes | Use <code>src/**/*.log</code> if multiple levels are needed |
| Exception file is still ignored | Parent directory is ignored or ignore rule appears after negation rule | Re-allow parent directory and place exception after ignore rule |
| Added pattern to .gitignore but tracked file still shows changes | Ignore does not affect already-tracked files | Use <code>git rm --cached</code> if intentionally stopping tracking |
| Files on Windows do not match | Pattern uses backslashes as separators | Use <code>/</code> in patterns |
| Unknown where a rule comes from | Multiple ignore files or config sources exist | Use <code>git check-ignore -v</code> to see source and line |

## 15. Self-Check Exercises

Practice in a test repository:

1. Create paths <code>app.log</code>, <code>src/debug.log</code>, and <code>src/test/result.log</code>. Add pattern <code>*.log</code> and inspect status.
2. Replace the pattern with <code>/app.log</code>. Explain why files in subdirectories no longer match.
3. Try <code>src/*.log</code> and <code>src/**/*.log</code>. Compare the result with log files in deeper subdirectories.
4. Create <code>build/keep.txt</code>. Write rules to ignore items inside build while keeping this file.
5. Try directly ignoring <code>build/</code> and then negating the child file. Observe why the exception does not take effect if the parent directory remains ignored.
6. Create a tracked file, then add a pattern matching the file. Confirm the file is still tracked by Git.
7. Use <code>git check-ignore -v</code> to find the rule line matching a file.
8. Create a <code>.gitignore</code> file inside a subdirectory and check the scope of a pattern anchored with <code>/</code>.
9. Explain the difference between <code>*</code>, <code>**/</code>, and <code>/**</code>.

When you can predict which files a pattern matches, calculate scope accurately from the <code>.gitignore</code> file's location, and re-allow exceptions without ignoring parent directories, you have mastered the most important parts of ignore syntax. Favor clear patterns, verify with Git, and keep necessary rules in the repository so the whole team gets consistent behavior.
