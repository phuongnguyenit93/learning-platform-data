# Introducing Build Provenance and Software Bills of Materials

A successfully built artifact does not by itself answer critical questions before release: which source code produced it, which pipeline and builder ran, which dependencies were used, whether the artifact was modified after the build, and how those details can be verified?

Two types of data help answer these questions: **build provenance** and a **Software Bill of Materials (SBOM)**. Provenance describes how an artifact was built and from which inputs. An SBOM describes the software components contained inside the artifact. When both are bound to the artifact's immutable digest and protected by signatures/attestations, teams can trace and inspect the software supply chain before deployment.

This falls under **DEVOPS_CI_CD_FUNDAMENTALS**: building CI/CD from Git events and pipeline-as-code through builds, testing, artifact management, environments, quality gates, secrets protection, post-deploy verification, and rollback. Provenance and SBOMs add verifiable evidence so release decisions rest on inspectable data.

## 1. Artifacts Need a Stable Identity

An artifact is an output generated by a build process, such as:

- A Java application JAR, WAR, or package.
- A binary, executable, or installer package.
- A container image.
- A static site or frontend bundle.
- A Helm chart, manifest, or deployment bundle.
- Test reports, SBOMs, and release metadata.

Human-readable filenames or tags help people recognize versions, but they can be overwritten or repointed to different content. To pinpoint exact contents, use a **cryptographic digest** computed over the artifact, typically SHA-256.

Example:

~~~text
Artifact: registry.example.com/orders/api:1.8.0
Digest:   sha256:7b2d...e91a
Commit:   4f9a1c2...
Build:    ci-run-1842
~~~

Tag `1.8.0` is a reference label. The digest identifies the exact contents. If the tag is updated to point to a different image, the new image's digest will differ. Therefore, testing, provenance verification, security scanning, and deployment steps should reference the same digest.

For a JAR file, the digest can be computed with:

~~~bash
sha256sum build/libs/orders-api.jar
~~~

For container images, registries typically provide the digest of the manifest or image index. Use the digest published by the registry for the specific platform and manifest being deployed. A multi-architecture image may have an image index digest alongside separate digests for each platform manifest; understand which digest is being verified and deployed.

A stable identity links together the artifact, provenance, SBOM, scan reports, signatures, releases, and deployment records. If these records link only by mutable tag names, the traceability chain becomes unreliable.

## 2. What Is Build Provenance?

Build provenance is a structured record of the process that created an artifact. It describes details such as:

- Which artifact was emitted by the build run.
- Which builder or CI system executed the build.
- Which workflow, job, or build process ran.
- Which source code and revision were used.
- Which dependencies or input materials were resolved.
- Build parameters and configurations affecting the output.
- Start time, completion time, and run identifier.

Good provenance lets an artifact recipient verify: was this artifact built from the official repository? Was it the exact reviewed commit? Is the builder on the trusted list? Did the build use unexpected dependencies or parameters?

Provenance is not merely a "build succeeded" log line. Logs are optimized for troubleshooting and can be hard to standardize, aggregate, or verify automatically. Provenance uses a schema-backed data structure bound to the subject digest and can be signed or issued as an attestation.

### 2.1. Core Components of Provenance

| Component | Meaning | Example |
| --- | --- | --- |
| Subject | The artifact being described, typically with digest | `orders-api` image with SHA-256 |
| Builder identity | System or service that produced the artifact | CI workflow running on a trusted builder |
| Build type | Process or build type used | Container image build following standard workflow |
| Source/materials | Source code, revision, and input dependencies | Repository, commit SHA, base image digest |
| Parameters | Parameters influencing the build | Target, publicly allowed build arguments |
| Invocation | Execution run identifier | Pipeline run ID, workflow run ID |
| Timing | Build start and completion times | UTC timestamp |
| Metadata | Additional schema-defined details | Builder version, log or run links |

Provenance must describe the actual resolved inputs, not merely a floating reference. For instance, recording `base-image:latest` does not tell you which exact image was used. Recording the base image's digest pinpoints the input content.

Never put secrets into provenance. You may record parameter names or indicate that a credential came from a secret manager, but never put tokens, passwords, private keys, or secret values into metadata.

## 3. Attestations and Digital Signatures

An **attestation** is a structured statement about an object, issued by an identified party. For build provenance, an attestation asserts that an artifact with a specific digest was built following a particular process and from the recorded inputs.

An attestation typically has three distinct parts:

1. **Content:** what is claimed about the artifact, such as build provenance or an SBOM.
2. **Issuer:** which system or identity produced the statement.
3. **Integrity and authenticity:** which signature or protection mechanism detects tampering and verifies the issuing origin.

A digital signature does not prove every claim is academically true or that the artifact is bug-free. It proves the signed data was not altered after signing and was signed by the identity corresponding to the verified key/certificate. Consumers must still decide whether that identity is trusted, whether the builder was authorized to build the repository, and whether the process satisfies policy.

### 3.1. Verification Chain

A typical verification flow:

1. Compute or retrieve the digest of the artifact being inspected.
2. Fetch the attestation associated with that exact digest.
3. Verify the signature or envelope against the configured trust root.
4. Verify the publisher identity, issuer, and builder.
5. Verify the repository, source revision, workflow, and build type.
6. Check materials, parameters, and policy conditions.
7. Cross-reference the SBOM and scan results against the same artifact digest.
8. Permit deployment only if all mandatory conditions pass.

Never check only that "a signature exists" and assume trust. A valid signature from a workflow not authorized for production releases still violates policy. Verify both signature validity and authorized publisher identity/origin.

### 3.2. in-toto and SLSA

**in-toto** provides a model for describing steps and materials in a software supply chain, along with an attestation mechanism to record statements about those activities. An in-toto Statement binds a subject to a predicate containing specific data, such as provenance or an SBOM.

**SLSA (Supply-chain Levels for Software Artifacts)** is a framework for evaluating and improving the assurance level of build processes. SLSA provenance describes build origin under a defined schema; requirements on builders, build processes, and provenance protection help consumers assess artifact trustworthiness.

These concepts are related but not synonymous:

- in-toto defines the attestation structure and how subjects bind to predicates.
- SLSA defines supply chain requirements and assurance levels, including provenance.
- Signatures protect integrity and authenticate the attestation issuer.
- Organizational policy decides which builders, sources, and workflows are accepted.

Do not label a build as achieving a SLSA level merely because a provenance file was generated. Assurance levels depend on meeting specific requirements of the standard version, including how the builder and build process are controlled.

## 4. Example Provenance Structure

An in-toto Statement can use a SLSA provenance predicate. The abbreviated example below illustrates only the key fields; full schemas and field names must conform to the declared predicate version:

~~~json
{
  "_type": "https://in-toto.io/Statement/v1",
  "subject": [
    {
      "name": "registry.example.com/orders/api",
      "digest": {
        "sha256": "7b2d...e91a"
      }
    }
  ],
  "predicateType": "https://slsa.dev/provenance/v1",
  "predicate": {
    "buildDefinition": {
      "buildType": "https://example.com/ci/container-build/v1",
      "externalParameters": {
        "sourceRepository": "https://example.com/org/orders-api",
        "sourceRef": "refs/heads/main"
      },
      "resolvedDependencies": [
        {
          "uri": "git+https://example.com/org/orders-api",
          "digest": {
            "gitCommit": "4f9a1c2..."
          }
        },
        {
          "uri": "oci://registry.example.com/base/java",
          "digest": {
            "sha256": "base-image-digest"
          }
        }
      ]
    },
    "runDetails": {
      "builder": {
        "id": "https://ci.example.com/builders/trusted-linux"
      },
      "metadata": {
        "invocationId": "ci-run-1842"
      }
    }
  }
}
~~~

This example shows the subject is an artifact identified by digest; the predicate records build type, repository, revision, resolved dependencies, and builder. Real data must conform to the schema, including required fields and data types of the predicate version. Never invent arbitrary field names and claim SLSA compliance.

`externalParameters` are inputs supplied by the build caller and must be governed by policy. `resolvedDependencies` describes resolved dependencies or materials. `builder.id` identifies the actual builder; it should never be an arbitrary string self-reported by a job without verification.

## 5. What Is an SBOM?

An SBOM is an inventory of software components inside a product or artifact. It may list:

- Direct packages and libraries.
- Transitive dependencies.
- Modules, frameworks, and runtime components.
- Versions, suppliers, and package identifiers.
- Hashes or component identification details.
- Licenses or copyright information.
- Dependency relationships among components.

SBOMs help development, security, and operations teams know what software contains. When a new vulnerability is disclosed, the organization can search for artifacts containing the affected package/version rather than manually inspecting every repository.

An SBOM does not by itself prove software is secure, replace testing, or guarantee every dependency was detected. SBOM quality depends on tooling, artifact type, package detection accuracy, and when it was generated.

### 5.1. Direct and Transitive Dependencies

Suppose an application declares:

~~~text
orders-api
  ├── spring-web
  │    ├── spring-core
  │    └── jackson-databind
  └── postgres-driver
~~~

`spring-web` and `postgres-driver` are direct dependencies of the application. `spring-core` and `jackson-databind` are transitive dependencies in this example. Recording only direct dependencies would omit many packages that may carry vulnerabilities or license terms requiring review.

A useful SBOM should reflect the dependency graph resolved by the tooling, including inter-component relationships. For container images, include OS packages, runtimes, and application libraries if supported by the tooling.

### 5.2. Common Fields

| Field | Meaning |
| --- | --- |
| Component name | Package or component name |
| Version | Detected version |
| Package URL (PURL) | Ecosystem-standard package identifier |
| Hash | Package or component hash when available |
| Supplier/origin | Package supplier or origin |
| License | Declared or detected license |
| Relationship | Dependency relationship between components |
| Timestamp | Time when the SBOM was generated |
| Subject/artifact identity | Artifact described by the SBOM |

Not every tool populates every field. Inspect the schema, data quality, and scan scope rather than merely checking that an SBOM file exists.

## 6. Common SBOM Formats

Two widely used formats are SPDX and CycloneDX:

| Format | Focus | When Appropriate |
| --- | --- | --- |
| SPDX | Exchanging software component, license, copyright, and relationship metadata | License management, compliance, and inventory |
| CycloneDX | Describing BOMs for software, services, and supply chain components | Security analysis, dependencies, and inventory |

SPDX is standardized by the Linux Foundation and has versioned specifications. CycloneDX is an OWASP BOM standard. Choose the format matching your consuming systems, partner requirements, and organizational policy. Some platforms support both.

### 6.1. Abbreviated CycloneDX SBOM Example

~~~json
{
  "bomFormat": "CycloneDX",
  "specVersion": "1.5",
  "version": 1,
  "metadata": {
    "component": {
      "type": "application",
      "name": "orders-api",
      "version": "1.8.0"
    }
  },
  "components": [
    {
      "type": "library",
      "name": "spring-web",
      "version": "6.1.8",
      "bom-ref": "pkg:maven/org.springframework/spring-web@6.1.8",
      "purl": "pkg:maven/org.springframework/spring-web@6.1.8"
    },
    {
      "type": "library",
      "name": "jackson-databind",
      "version": "2.17.1",
      "bom-ref": "pkg:maven/com.fasterxml.jackson.core/jackson-databind@2.17.1",
      "purl": "pkg:maven/com.fasterxml.jackson.core/jackson-databind@2.17.1"
    }
  ],
  "dependencies": [
    {
      "ref": "pkg:maven/org.springframework/spring-web@6.1.8",
      "dependsOn": [
        "pkg:maven/com.fasterxml.jackson.core/jackson-databind@2.17.1"
      ]
    }
  ]
}
~~~

This is a simplified example illustrating structure, not a complete production SBOM. Real SBOMs require schema-mandated fields, generation timestamp metadata, and the full list of detected components/relationships; a serial number is a useful document identifier when supported by the format/version. Values in `dependencies` must accurately reference component `bom-ref` identifiers. Validate with tooling supporting the exact CycloneDX version before publishing.

## 7. Generating SBOMs from the Exact Releasable Object

An SBOM can be generated from a source tree, package manager dependency graph, package file, or container image. Each approach has different visibility:

- Generating from source or lockfiles lists dependencies declared/resolved during development.
- Generating from binaries/packages detects components actually packaged into the artifact.
- Generating from container images captures OS packages and runtimes inside the image.

For products released as container images, generate or verify the SBOM from the built image itself. An SBOM built solely from source can miss OS packages or components added inside the Dockerfile. Conversely, image scanning may not recover complete license details or dependency relationships available in the package manager. You can combine multiple sources and merge them using appropriate tooling.

Example using Syft to generate a CycloneDX SBOM for an image:

~~~bash
syft registry.example.com/orders/api:1.8.0 \
  -o cyclonedx-json=orders-api.cdx.json
~~~

In release pipelines, scan the pushed image identified by digest rather than relying on mutable tags. Exact tool flags may vary by version; pin the Syft version and verify outputs before adopting it in pipelines.

For Java applications, you can use build-ecosystem SBOM plugins or package scanning tools. Ensure the SBOM includes transitive dependencies and matches the packaged artifact. If the build performs shading, repackaging, or dependency exclusion, verify that the SBOM accurately reflects the final contents.

## 8. Linking Provenance and SBOMs to Artifacts

Provenance and SBOMs answer two different questions:

| Evidence | Core Question |
| --- | --- |
| Build provenance | Where, by whom, from which source/materials, and by what process was the artifact created? |
| SBOM | Which software components does the artifact contain, and how do they relate? |
| Vulnerability scan | Which known components have security issues according to data at scan time? |
| Signature | Was the artifact or attestation altered, and is the signing origin authenticated? |

These records should be linked by the artifact's digest. An SBOM does not always have a dedicated standard field for the full artifact digest; it can be bound via an attestation whose subject is the artifact digest and whose predicate holds the SBOM, or via external metadata managed alongside the release. For example, a release may include:

~~~text
orders-api@sha256:7b2d...e91a
  ├── provenance.intoto.jsonl
  ├── sbom.cdx.json
  ├── vulnerability-report.json
  ├── signature / attestation
  └── deployment-record
~~~

When promoting an artifact from staging to production, preserve the digest and all evidence bound to that digest. If rebuilt, even from the same source commit, the artifact digest may change due to timestamps, toolchains, dependencies, or environment factors. In that case, generate fresh provenance and a fresh SBOM for the new artifact.

Never attach an SBOM from an earlier build to a new artifact merely because they share a version string. An SBOM must describe the exact object it claims to represent.

## 9. Integrating Provenance and SBOMs into Pipelines

A typical pipeline can follow this sequence:

1. **Checkout:** fetch the exact commit SHA and record repository/ref.
2. **Resolve dependencies:** use lockfiles, configured repositories, and verification mechanisms.
3. **Build and test:** run builds, tests, and quality gates on that commit.
4. **Package:** produce an immutable artifact and compute its digest.
5. **Generate SBOM:** analyze the final artifact or published image, recording format and schema version.
6. **Generate provenance:** record builder identity, workflow, source revision, materials, and build invocation.
7. **Attest/sign:** sign or issue attestations using a trusted workload identity, preferring short-lived credentials.
8. **Publish:** store the artifact, SBOM, and attestations in a controlled registry/repository.
9. **Verify:** validate digest, signature, builder, source, policy, and SBOM before promotion.
10. **Deploy:** deploy the exact verified digest; record release/deployment IDs.

Diagram:

~~~mermaid
flowchart TD
    A["Specific Git commit"] --> B["Dependency resolution and verification"]
    B --> C["Build, tests, and quality gates"]
    C --> D["Create immutable artifact"]
    D --> E["Compute digest"]
    E --> F["Generate SBOM from artifact"]
    E --> G["Generate build provenance"]
    F --> H["Attest and sign with builder identity"]
    G --> H
    H --> I["Publish artifact + SBOM + attestations"]
    I --> J["Verify digest, signature, and policy"]
    J --> K{"Eligible for release?"}
    K -- "No" --> L["Block promotion and retain evidence"]
    K -- "Yes" --> M["Promote same digest"]
    M --> N["Record deployment and release record"]
~~~

If SBOM or provenance generation fails, decide explicitly whether policy treats this as a mandatory blocker or a warning. For critical production artifacts, organizations may require both to exist and be verifiable before release. Never silently skip the step just because a metadata tool errored out.

### 9.1. Platform-Neutral Pipeline Example

The snippet below illustrates logical steps rather than a specific CI product's syntax:

~~~yaml
pipeline:
  source:
    checkout: exact_commit_sha

  build:
    steps:
      - resolve: locked_dependencies
      - verify: dependency_checksums
      - run: unit_and_integration_tests
      - run: quality_gates
      - package: immutable_artifact
      - calculate: sha256_digest

  evidence:
    steps:
      - generate: sbom_from_final_artifact
      - generate: provenance_from_trusted_builder
      - attest: artifact_digest_and_evidence
      - sign: with_short_lived_workload_identity

  publish:
    steps:
      - upload: artifact_by_digest
      - upload: sbom_and_attestations

  release:
    steps:
      - verify: signature_builder_source_and_policy
      - verify: sbom_and_vulnerability_policy
      - promote: same_artifact_digest
      - record: deployment_identity_and_result
~~~

Separating build, evidence, publish, and release steps makes pipelines easier to audit. In real implementations, jobs can be combined or split depending on the platform, provided dependencies prevent publishing or promoting an artifact that lacks required evidence.

## 10. Verifying Provenance Before Deployment

Artifact consumers need policies defining which builders and sources are authorized. For example, accept an artifact only if:

- The verified digest matches the artifact being deployed.
- The attestation has a valid signature and accepted chain of trust.
- The issuer is a trusted CI system/workload identity.
- The source repository is on the approved list.
- The revision is a reviewed/merged commit per policy.
- The workflow or build type matches the standard release pipeline.
- The builder is not an arbitrary runner controlled by untrusted users.
- Materials and dependencies comply with organizational rules.
- The SBOM has a valid format, describes the exact digest, and was generated within an appropriate window.

A valid signature from an unauthorized builder does not qualify. Valid provenance pointing to an unreleasable branch also does not qualify. Verification must check both claim contents and issuing identity.

Policy-as-code can express these rules. Example pseudo-policy:

~~~text
allow deployment only if:
  artifact.digest == attestation.subject.digest
  signature.valid == true
  signer.identity in trusted_builders
  provenance.source.repository in approved_repositories
  provenance.source.revision is approved_revision
  provenance.build_type in approved_build_types
  sbom.subject_digest == artifact.digest
  sbom.schema is supported
  vulnerability_policy == passed
~~~

This is illustrative logic. Real systems must validate schemas, signatures, trust roots, issuers, subject digests, and each field according to the attestation standard in use.

## 11. How Do SBOMs Support Vulnerability and License Management?

SBOMs feed into risk management activities:

- Matching packages/versions against vulnerability databases.
- Identifying affected artifacts when a new CVE emerges.
- Tracking end-of-life dependencies or licenses requiring review.
- Analyzing direct and transitive components.
- Supporting supply chain incident investigations.
- Preparing data for audits and customer inquiries.

Vulnerability scan results must record the scan timestamp and vulnerability data source. An SBOM generated today can be re-scanned tomorrow when the CVE database updates without rebuilding the artifact. Therefore, distinguish:

- **SBOM:** which components exist inside the artifact.
- **Scan result:** which components have issues according to data and policy at scan time.
- **Exception/risk decision:** which findings are temporarily accepted and why.

An SBOM with zero findings does not mean zero vulnerabilities exist. A package may be unrecognized, a version unknown, an advisory not yet published, or the ecosystem unsupported by the scanner. Reports should state detection scope and limitations.

Licenses also require careful interpretation. An SBOM can record license identifiers or package declarations, yet compliance decisions typically require evaluating license text, distribution models, modifications, and legal obligations. Never automatically conclude a product is legally compliant from a single license field in an SBOM.

## 12. Protecting Provenance, SBOMs, and Supply Chain Information

Provenance and SBOMs increase transparency, yet they can also expose internal details:

- Repository, project, and branch names.
- Internal dependency and tool versions.
- Private package names or private registries.
- Product architecture and component relationships.
- Service addresses, environment names, or operational metadata.

Protective practices:

- Never include secrets, tokens, private keys, or credentials in metadata.
- Publish SBOMs/provenance only to authorized audiences.
- Enforce proper read permissions on registries and attestation stores.
- Sign with workload identities or managed keys; never store private keys in repositories.
- Prefer short-lived credentials and job-scoped permissions.
- Record and protect trust roots, certificates, and verification policies.
- Maintain immutable attestation history or audit trails.
- Never let untrusted pull requests control builders authorized to sign release artifacts.

For public artifacts, SBOMs and provenance can be published for user verification. For internal software or products carrying sensitive information, apply dedicated sharing policies. Transparency must go hand in hand with access control.

## 13. How Do Reproducible Builds and Provenance Differ?

These concepts complement each other without replacing one another:

| Concept | Goal |
| --- | --- |
| Reproducible build | Identical source and deterministic build conditions produce identical or equivalent artifacts per defined criteria |
| Build provenance | Records where, by which builder, from which materials, and by which process an artifact was produced |
| SBOM | Describes components contained inside the artifact |
| Attestation/signature | Protects and authenticates claims made about the artifact |

A build with provenance may still be non-reproducible if the environment contains non-deterministic inputs. A reproducible build still needs provenance so consumers know who built the artifact and which process ran.

To improve reproducibility:

- Pin toolchains and dependencies.
- Pin base image versions.
- Normalize timezones, locales, and timestamps where supported by tools.
- Avoid depending on uncontrolled network data.
- Declare all task inputs and outputs explicitly.
- Record build parameters and materials.

Never claim a build is reproducible simply because two builds share a version string. Compare digests or apply defined equivalence criteria.

## 14. Common Mistakes

| Mistake | Risk | Remediation |
| --- | --- | --- |
| Using tags instead of digests for verification | Tags can point to different content | Bind provenance, SBOM, and deployments to digests |
| Provenance recording only a branch name | Cannot identify the exact source revision | Record commit SHA and resolved materials |
| Trusting any valid signature | Unauthorized builders can still sign | Verify issuer, identity, workflow, and policy |
| SBOM listing only direct dependencies | Misses transitive dependencies | Export the full dependency graph as supported by tooling |
| Generating SBOM from source when shipping containers | Misses OS packages or runtime components in the image | Scan the final artifact/image and combine sources when needed |
| SBOM not bound to a specific artifact | Risk of using an SBOM from another version | Bind subject digest and validate at publish time |
| Treating a clean SBOM as absolute security | Scanners may lack data or miss packages | Combine scans, tests, policies, and risk assessment |
| Writing secrets into provenance | Leaks credentials via metadata | Strip secrets and use workload identity |
| Rebuilding in production and reusing staging provenance | Actual artifact differs from verified artifact | Promote the same verified digest |
| Claiming SLSA compliance merely from a JSON file | Fails builder/process requirements | Evaluate against the exact SLSA version and requirements |
| Not retaining attestation history | Hard to investigate when artifacts or policies change | Retain metadata, signatures, and audit trails per release |

## 15. Traceable Artifact Checklist

**Artifact**

- [ ] Artifact has an immutable identifier or digest.
- [ ] Human-readable tag/version links to the actual digest.
- [ ] Artifact is stored in a controlled registry/repository.
- [ ] Environments promote the exact same digest.

**Build Provenance**

- [ ] Provenance binds to the exact subject digest.
- [ ] Source repository and commit SHA are explicitly recorded.
- [ ] Builder identity and build type are verifiable.
- [ ] Materials/dependencies and key parameters are recorded.
- [ ] Invocation ID and build timestamp are traceable.
- [ ] Schema/predicate version is explicitly declared.

**SBOM**

- [ ] SBOM is generated from the final artifact or image.
- [ ] Direct and transitive dependencies are listed per tooling capability.
- [ ] Version, PURL, hash, license, and relationships are included where supported.
- [ ] SPDX or CycloneDX format is validated.
- [ ] SBOM binds to the corresponding artifact digest.
- [ ] Generation timestamp and tool details are recorded.

**Attestation and Verification**

- [ ] Attestations are signed or protected by a trusted mechanism.
- [ ] Trust root, issuer, and signer identity are verified.
- [ ] Policy checks repository, revision, builder, and build type.
- [ ] Scan results bind to the exact artifact and scan timestamp.
- [ ] No secrets appear in metadata.
- [ ] Audit trails exist for publish, verify, and deployment events.

## Conclusion

Build provenance and SBOMs provide two essential perspectives on an artifact: provenance explains how the artifact was created, while an SBOM reveals what components it contains. When both bind to an immutable digest, are issued as signed attestations, and are verified against policy, organizations gain end-to-end traceability from source commit to artifact and deployment.

Provenance, signatures, or SBOMs should never be treated as absolute proof that software is safe. You must verify builder identity, source revision, materials, schemas, components, vulnerability scans, and quality gates. Carrying the exact same digest across testing and release eliminates version confusion, supports incident investigation, and builds a verifiable software supply chain.
