# style-src

> **Chương:** CSP  
> **Học phần:** Application Security — Browser Security (`SECURITY_APPLICATION_SECURITY_BROWSER_SECURITY`)

CSS quyết định cách nội dung web được trình bày, nhưng stylesheet và style inline cũng là đầu vào mà browser phải phân tích. Nếu ứng dụng cho phép tải CSS từ nguồn không đáng tin hoặc chấp nhận style inline tùy ý, kẻ tấn công có thể thay đổi giao diện, che giấu cảnh báo, tạo lớp phủ đánh lừa người dùng hoặc lợi dụng một số hành vi tải tài nguyên của CSS. **Content Security Policy (CSP) với `style-src`** giúp giới hạn nguồn stylesheet và cách style được áp dụng.

`style-src` là một directive trong CSP. Nó kiểm soát nguồn style khi các directive chi tiết hơn chưa được khai báo, đồng thời làm fallback cho `style-src-elem` và `style-src-attr`. Khi cần kiểm soát riêng stylesheet element và style attribute, có thể dùng hai directive chuyên biệt này. `style-src` là một lớp phòng vệ; nó không thay thế việc kiểm soát dữ liệu, tránh CSS injection và bảo vệ các directive khác như `img-src`, `font-src` hay `script-src`.

## 1. Mục tiêu học tập

Sau bài học, bạn có thể:

1. Giải thích vai trò của `style-src` trong CSP và quan hệ fallback với `default-src`.
2. Phân biệt stylesheet bên ngoài, thẻ `<style>` và thuộc tính `style`.
3. Hiểu khi nào cần `style-src-elem` và `style-src-attr`.
4. Cấu hình nguồn CSS bằng `'self'`, host source, nonce và hash.
5. Đánh giá rủi ro khi bật `'unsafe-inline'` hoặc `'unsafe-hashes'`.
6. Phân biệt việc cho phép stylesheet với việc cho phép tài nguyên mà CSS tham chiếu.
7. Triển khai CSP Report-Only, đọc violation và chuyển dần sang enforcement.
8. Kiểm chứng policy trong browser và xử lý các lỗi thường gặp.

## 2. `style-src` kiểm soát điều gì?

`style-src` xác định những nguồn mà browser được phép sử dụng cho stylesheet và style inline theo phạm vi của directive. Một policy cơ bản:

```http
Content-Security-Policy: default-src 'self'; style-src 'self'
```

Policy này cho phép stylesheet từ cùng origin. Inline `<style>` và style attribute không được cho phép chỉ vì chúng nằm trong HTML cùng origin; inline style cần cơ chế cho phép riêng như nonce/hash hoặc `'unsafe-inline'` theo thiết kế.

Các nguồn thường gặp:

| Source expression | Ý nghĩa khái quát | Lưu ý |
| --- | --- | --- |
| `'self'` | Cùng origin với tài liệu | Scheme, host và port phải phù hợp |
| `https://cdn.example.com` | Nguồn CSS trên host chỉ định qua HTTPS | Chỉ mở cho CDN thực sự cần thiết |
| `https:` | Nguồn HTTPS nói chung | Rộng hơn nhiều so với một host cụ thể |
| `'nonce-{giá-trị}'` | Cho phép style element có nonce khớp | Nonce phải ngẫu nhiên và thay đổi theo response |
| `'sha256-...'` | Cho phép nội dung style khớp hash | Thay đổi một ký tự/whitespace có thể làm hash không còn khớp |
| `'unsafe-inline'` | Cho phép inline style trong phạm vi directive | Làm giảm đáng kể khả năng CSP ngăn CSS injection |
| `'unsafe-hashes'` | Cho phép áp dụng hash source cho một số inline attribute | Chỉ nên dùng khi có nhu cầu rõ và hash cụ thể |

Không nên thêm `https:` hoặc `*` chỉ để hết lỗi giao diện. Hãy xác định stylesheet thực sự đến từ đâu, vì sao cần nguồn đó và liệu có thể self-host hoặc giới hạn bằng host cụ thể hay không.

## 3. Ba cách CSS đi vào trang

Một trang có thể sử dụng CSS theo nhiều cách. Chúng chịu các quy tắc CSP liên quan nhưng không hoàn toàn giống nhau.

### 3.1 Stylesheet bên ngoài

Ví dụ:

```html
<link rel="stylesheet" href="/assets/site.css">
<link rel="stylesheet" href="https://cdn.example.com/ui.css">
```

Browser kiểm tra URL stylesheet theo source list của `style-src-elem` nếu có, nếu không thì dùng `style-src`, rồi fallback về `default-src`. Nếu chỉ cho phép `'self'`, stylesheet trên cùng origin được tải; stylesheet từ CDN khác origin bị chặn cho tới khi policy cho phép host đó.

### 3.2 Thẻ `<style>` trong HTML

Ví dụ:

```html
<style>
  .notice { color: #2457a7; }
</style>
```

Đây là inline style element. Nó không phải file CSS được tải từ `'self'`; browser kiểm tra inline style theo `style-src-elem` hoặc fallback tương ứng. Có thể cho phép một block cụ thể bằng nonce hoặc hash thay vì bật tất cả inline style.

### 3.3 Thuộc tính `style`

Ví dụ:

```html
<p style="color: #2457a7">Thông báo</p>
```

Đây là style attribute. Browser kiểm tra theo `style-src-attr` nếu có, nếu không thì fallback `style-src` rồi `default-src`. Nonce không áp dụng trực tiếp cho thuộc tính `style`; khi cần cho phép một attribute cụ thể, có thể đánh giá hash cùng `'unsafe-hashes'`, hoặc tốt hơn là chuyển style sang class/CSSOM theo thiết kế phù hợp.

## 4. `style-src`, `style-src-elem` và `style-src-attr`

CSP Level 3 cung cấp các directive chi tiết hơn:

| Directive | Kiểm soát | Ví dụ |
| --- | --- | --- |
| `style-src` | Nguồn style nói chung và làm fallback | `style-src 'self'` |
| `style-src-elem` | Nguồn stylesheet element, gồm `<style>` và `<link rel="stylesheet">` | `style-src-elem 'self'` |
| `style-src-attr` | Style attribute trên element | `style-src-attr 'none'` |

Nếu khai báo directive chi tiết, chúng sẽ được ưu tiên cho loại tài nguyên tương ứng. Nếu thiếu `style-src-elem`, browser fallback về `style-src`, rồi `default-src`. `style-src-attr` cũng fallback theo thứ tự tương tự. Do đó, policy sau có thể cho stylesheet bên ngoài nhưng chặn style attribute:

```http
Content-Security-Policy: default-src 'self'; style-src 'self'; style-src-attr 'none'
```

Và policy sau kiểm soát hai loại riêng biệt:

```http
Content-Security-Policy: default-src 'self'; style-src-elem 'self' https://cdn.example.com; style-src-attr 'none'
```

Trong ví dụ thứ hai, CSS file từ origin ứng dụng và CDN được phép; style attribute bị chặn. Inline `<style>` element cũng thuộc `style-src-elem`, nên nếu cần một block inline, phải cấp quyền bằng nonce/hash phù hợp.

Các directive chuyên biệt được hỗ trợ tùy browser. Hãy kiểm tra browser mục tiêu; policy có fallback `style-src` giúp duy trì hành vi hợp lý ở môi trường chưa hỗ trợ directive Level 3.

## 5. Fallback và `default-src`

`default-src` là fallback chung cho nhiều directive tải tài nguyên. Nếu không có `style-src`, `style-src-elem` hoặc `style-src-attr`, browser có thể dùng `default-src` theo chuỗi fallback của directive tương ứng.

Ví dụ:

```http
Content-Security-Policy: default-src 'self'
```

Policy này giới hạn stylesheet về cùng origin thông qua fallback. Tuy nhiên, khi policy lớn dần, nên khai báo rõ `style-src` để reviewer nhìn thấy ý định đối với CSS thay vì phải suy ra từ directive mặc định.

Ví dụ rõ hơn:

```http
Content-Security-Policy: default-src 'self'; style-src 'self'
```

Khi thêm `style-src-elem` hoặc `style-src-attr`, hãy đọc lại toàn bộ policy để chắc chắn fallback không mở rộng quyền ngoài dự kiến. Một directive không được khai báo không đồng nghĩa “không giới hạn” nếu có fallback; ngược lại, directive được khai báo nhưng có source rộng có thể cho phép nhiều hơn ý định của nhóm bảo mật.

## 6. Nonce cho inline `<style>` element

Nếu ứng dụng tạo một style block động ở server, có thể cho phép block cụ thể bằng nonce:

```http
Content-Security-Policy: default-src 'self'; style-src 'self' 'nonce-RANDOM_VALUE'
```

HTML response:

```html
<style nonce="RANDOM_VALUE">
  .theme-banner { color: #2457a7; }
</style>
```

Giá trị nonce trong header và attribute phải khớp chính xác. Nonce cần:

- Được tạo bằng nguồn ngẫu nhiên mật mã mạnh (CSPRNG).
- Khác nhau cho mỗi response HTML; không dùng một nonce cố định trong source code hoặc cấu hình lâu dài.
- Đủ khó đoán và không được tái sử dụng giữa người dùng/response.
- Được gắn chỉ vào style element mà server chủ động tin cậy.
- Không bị cache công khai theo cách khiến nonce của một response bị tái sử dụng cho người dùng khác.

Nonce **không áp dụng cho `style="..."` attribute**. Nếu cần cho phép style attribute, phải cân nhắc cách khác như hash với `'unsafe-hashes'`, hoặc thay đổi cách render để không cần inline attribute.

Ví dụ pseudocode server:

```js
const nonce = crypto.randomBytes(16).toString("base64");
response.setHeader(
  "Content-Security-Policy",
  `default-src 'self'; style-src 'self' 'nonce-${nonce}'`
);
renderPage({ nonce });
```

Đây là mã minh họa. Cách sinh nonce, gắn vào template và cấu hình cache phải theo framework/server thực tế. Nonce dùng cho CSP style và script có thể cùng một giá trị trong một response theo thiết kế, nhưng phải đảm bảo mỗi response có nonce mới và không rò rỉ qua cache hoặc log.

## 7. Hash cho inline style

Nếu một inline `<style>` block là nội dung tĩnh, không đổi giữa các response, có thể cho phép bằng hash:

```http
Content-Security-Policy: style-src 'self' 'sha256-BASE64_HASH'
```

Hash được tính trên nội dung chính xác của style block theo quy tắc CSP. Khi nội dung thay đổi, kể cả một số khác biệt về khoảng trắng hoặc xuống dòng, hash có thể không còn khớp. Đây là lý do hash phù hợp với block tĩnh, ổn định và được kiểm soát trong build pipeline.

Hash source cho inline style element khác với hash cho style attribute. Để cho phép một style attribute cụ thể bằng hash, CSP cần `'unsafe-hashes'` trong directive phù hợp, và hash phải khớp chính xác nội dung attribute. Hãy cân nhắc kỹ vì `'unsafe-hashes'` có thể làm một đoạn style trùng khớp được chấp nhận ở những vị trí attribute tương ứng; chỉ dùng khi đã hiểu phạm vi và đã kiểm thử.

Không tự tính hash bằng cách copy một đoạn CSS đã format lại trong editor. Hãy để build tooling tạo hash từ nội dung cuối cùng hoặc dùng công cụ tính hash đúng thuật toán/byte sequence, sau đó kiểm tra trên browser.

## 8. `'unsafe-inline'` và rủi ro của style inline

Ví dụ policy rộng:

```http
Content-Security-Policy: style-src 'self' 'unsafe-inline'
```

`'unsafe-inline'` cho phép inline style trong phạm vi directive, bao gồm các style block/attribute mà policy kiểm soát. Điều này có thể giúp ứng dụng cũ hoạt động nhanh, nhưng làm giảm khả năng CSP ngăn kẻ tấn công chèn CSS.

CSS injection không đồng nghĩa trực tiếp với JavaScript execution trong browser hiện đại. Tuy vậy, CSS không đáng tin có thể:

- Che, làm mờ hoặc thay đổi cách hiển thị nút, cảnh báo, trường nhập liệu và nội dung bảo mật.
- Tạo lớp phủ giao diện gây nhầm lẫn hoặc hỗ trợ UI redressing.
- Thay đổi trạng thái trình bày khiến người dùng hiểu sai nội dung hoặc thao tác.
- Kết hợp với các khả năng tải tài nguyên và side channel của browser để tạo rủi ro rò rỉ trong một số điều kiện.

Mức độ ảnh hưởng phụ thuộc DOM, browser, các directive khác và dữ liệu có thể quan sát. Không nên phóng đại CSS injection thành khả năng đánh cắp mọi dữ liệu; cũng không nên coi CSS chỉ là phần trang trí không có ý nghĩa bảo mật.

Khi ứng dụng cần inline style vì lý do kỹ thuật, hãy xác định cụ thể phần nào cần thiết. Chuyển style tĩnh sang file CSS, dùng class cố định hoặc nonce/hash cho `<style>` block có thể thu hẹp quyền hơn việc bật `'unsafe-inline'` toàn cục.

## 9. `'unsafe-hashes'` cho style attribute

Style attribute thường khó di chuyển ngay trong ứng dụng cũ. CSP có thể cho phép một số giá trị attribute cụ thể bằng hash và `'unsafe-hashes'`:

```http
Content-Security-Policy: style-src-attr 'unsafe-hashes' 'sha256-BASE64_HASH'
```

Hash phải khớp chính xác nội dung của attribute, ví dụ giá trị CSS trong `style="..."`. Không có nonce cho style attribute. `'unsafe-hashes'` không phải lời mời cho phép mọi attribute; nó thay đổi cách hash source được áp dụng cho inline attribute và cần được giới hạn bằng hash cụ thể.

Nếu có thể, refactor:

```html
<!-- Cách cũ -->
<div style="color: #2457a7">Thông báo</div>

<!-- Cách ưu tiên -->
<div class="notice notice--info">Thông báo</div>
```

```css
.notice--info { color: #2457a7; }
```

Class cố định giúp style được quản lý trong stylesheet, policy dễ hiểu và dữ liệu không điều khiển trực tiếp CSS declaration.

## 10. `style-src` không kiểm soát mọi URL trong CSS

Một stylesheet có thể tham chiếu tới các tài nguyên khác:

```css
@import url("/assets/extra.css");

@font-face {
  font-family: "ProductSans";
  src: url("/assets/product.woff2") format("woff2");
}

.hero {
  background-image: url("/assets/hero.webp");
}
```

Các loại tài nguyên này có thể chịu directive khác nhau:

| CSS construct | Directive CSP thường liên quan |
| --- | --- |
| Stylesheet `<link>` và `@import` | `style-src-elem` / `style-src` |
| Font qua `@font-face` | `font-src` |
| Ảnh nền qua `url(...)` | `img-src` |
| Nội dung tải bằng `fetch` từ JavaScript | `connect-src` |

Vì vậy, cho phép `style-src 'self'` không có nghĩa mọi URL mà CSS tham chiếu đều được phép. Ngược lại, mở rộng `img-src` hoặc `font-src` không cho phép tải stylesheet. Hãy thiết kế từng directive theo loại tài nguyên.

`style-src` cũng không thay thế `base-uri`, `object-src`, `script-src` hoặc các directive khác. CSP cần được đọc như một policy tổng thể, không chỉ một dòng style.

## 11. CSSOM và style được tạo bằng JavaScript

Ứng dụng có thể thay đổi giao diện qua CSSOM hoặc property `style`:

```js
const badge = document.querySelector(".badge");
badge.style.color = "#2457a7";
badge.classList.add("badge--active");
```

Đây là những cách thường dùng để thay đổi style khi runtime. Tuy nhiên, không nên suy luận rằng mọi thao tác CSSOM đều chịu cùng cách kiểm tra như `<style>` element hoặc `style` attribute được parse từ HTML. Việc enforcement có thể phụ thuộc API cụ thể, browser và phiên bản; một số thao tác gán style attribute qua DOM API có thể tạo violation trong khi cập nhật property CSSOM có hành vi khác.

Hãy kiểm tra trên browser mục tiêu bằng CSP Report-Only/enforcement. Về thiết kế, ưu tiên class cố định cho trạng thái UI; nếu cần giá trị động, validate theo kiểu dữ liệu và phạm vi hẹp (ví dụ enum màu), không đưa chuỗi CSS tùy ý từ người dùng vào CSSOM.

Ví dụ dùng mapping:

```js
const colors = {
  info: "#2457a7",
  success: "#18794e",
  warning: "#8a4b08",
};

badge.style.color = colors[status] ?? colors.info;
```

Giá trị CSS được chọn từ mapping do ứng dụng kiểm soát, không lấy nguyên CSS declaration từ input.

## 12. `style-src` và CSS injection

CSS injection xuất hiện khi dữ liệu không tin cậy có thể ảnh hưởng nội dung stylesheet, style element hoặc style attribute. Nguồn có thể là:

- Người dùng nhập màu, theme hoặc nội dung rich text.
- Giá trị từ URL được ghép vào thuộc tính `style`.
- Template server render một đoạn `<style>` từ cấu hình.
- Component tạo CSS động từ API hoặc storage.
- Thư viện bên thứ ba thêm style hoặc stylesheet vào trang.

Biện pháp phòng vệ:

1. Không cho người dùng cung cấp CSS tùy ý nếu sản phẩm không thật sự cần.
2. Với theme, dùng enum hoặc mapping các giá trị đã định nghĩa.
3. Chuyển style tĩnh sang stylesheet và class cố định.
4. Nếu cần style động, validate theo grammar hẹp và giới hạn giá trị.
5. Dùng CSP `style-src-attr`/`style-src-elem` để giảm bề mặt inline và nguồn tải.
6. Kiểm soát `img-src`, `font-src` và directive tài nguyên liên quan tới CSS URL.
7. Kiểm thử giao diện nhạy cảm như nút xác nhận, cảnh báo, thông báo lỗi và trạng thái thanh toán.

CSP là lớp giảm thiểu. Nếu ứng dụng tự tạo một stylesheet hợp lệ từ dữ liệu người dùng, policy có thể không ngăn được nội dung sai lệch được đưa vào nguồn đã được cho phép. Validation và thiết kế dữ liệu vẫn cần thiết.

## 13. Nhiều CSP policy được áp dụng như thế nào?

Nếu server gửi nhiều header `Content-Security-Policy`, browser thực thi tất cả policy; kết quả là các policy cùng hạn chế hành vi và policy sau không thể nới lỏng policy trước. Ví dụ, một policy cho phép CDN nhưng policy khác chỉ cho `'self'` thì stylesheet CDN vẫn có thể bị chặn.

Header từ reverse proxy/CDN và ứng dụng có thể vô tình tạo nhiều policy. Khi debug, hãy kiểm tra **tất cả** header CSP thực tế trong Network, không chỉ cấu hình ở source code. Một policy bổ sung thường dùng để thắt chặt, không phải để ghi đè policy cũ.

`Content-Security-Policy-Report-Only` dùng để quan sát vi phạm mà chưa chặn tài nguyên. Nó không phải một policy nới lỏng enforcement; nếu đồng thời có header enforce, policy enforce vẫn hoạt động.

## 14. Báo cáo vi phạm và triển khai dần

Khi CSP chặn style, browser có thể tạo violation report. Có thể cấu hình endpoint báo cáo bằng cơ chế CSP reporting phù hợp với browser/hạ tầng, ví dụ `report-to` cùng `Reporting-Endpoints`; `report-uri` là cơ chế cũ vẫn có thể gặp trong hệ thống hiện hữu.

Ví dụ policy theo dõi:

```http
Reporting-Endpoints: csp-endpoint="https://reports.example.com/csp"
Content-Security-Policy-Report-Only: default-src 'self'; style-src 'self'; report-to csp-endpoint
```

Khi nhận report, cần biết directive nào bị vi phạm (`style-src`, `style-src-elem` hay `style-src-attr`), nguồn bị chặn và URL trang. Không ghi hoặc xử lý report như dữ liệu đáng tin; report có thể chứa URL do người dùng kiểm soát, cần giới hạn kích thước, lọc và bảo vệ endpoint khỏi spam.

Quy trình rollout:

1. Thu thập stylesheet và inline style thực tế từ các luồng ứng dụng.
2. Bật Report-Only trên môi trường thử nghiệm hoặc một nhóm người dùng phù hợp.
3. Phân loại violation: CSS cần thiết, inline style cũ, extension/browser noise hoặc tài nguyên không mong muốn.
4. Refactor inline style sang class/CSS file; giới hạn CDN/host; thêm nonce/hash khi thật sự cần.
5. Chạy regression test cho trang chính, popup, widget, trang thanh toán và luồng đăng nhập.
6. Chuyển policy sang enforcement theo giai đoạn.
7. Theo dõi violation sau phát hành và rà soát ngoại lệ định kỳ.

Không thêm `'unsafe-inline'` chỉ để làm report biến mất. Hãy xác định nguồn style và chọn cách xử lý có phạm vi nhỏ nhất.

## 15. Ví dụ policy style-src theo nhu cầu

### 15.1 Ứng dụng chỉ dùng stylesheet cùng origin

```http
Content-Security-Policy: default-src 'self'; style-src 'self'
```

Phù hợp khi CSS được self-host và không cần inline style. Cần refactor style attribute/block hoặc thêm nonce/hash cho block cần thiết.

### 15.2 Ứng dụng dùng CDN CSS cụ thể

```http
Content-Security-Policy: default-src 'self'; style-src 'self' https://cdn.example.com
```

Chỉ cho phép host CDN cụ thể. Nếu CDN dùng nhiều hostname hoặc redirect, cần kiểm tra URL cuối và chính sách thực tế. Không mở `https:` tổng quát nếu chỉ có một CDN cần thiết.

### 15.3 Ứng dụng có một inline style block động

```http
Content-Security-Policy: default-src 'self'; style-src 'self' 'nonce-{RANDOM_PER_RESPONSE}'
```

Server gắn cùng nonce vào `<style nonce="...">` đã kiểm soát. Placeholder phải được thay bằng nonce mới cho từng response.

### 15.4 Cho phép stylesheet element nhưng chặn style attribute

```http
Content-Security-Policy: default-src 'self'; style-src 'self'; style-src-attr 'none'
```

Hữu ích khi ứng dụng đã chuyển inline style attribute sang class/CSSOM phù hợp nhưng vẫn dùng stylesheet bình thường.

Các ví dụ trên chỉ thể hiện phần style policy. Ứng dụng thực tế còn cần `script-src`, `img-src`, `font-src`, `connect-src`, `base-uri`, `object-src`, `frame-ancestors` và các directive phù hợp với chức năng.

## 16. Thực hành kiểm chứng trong môi trường lab

Thực hiện trên trang local hoặc ứng dụng lab bạn quản lý. Dùng CSS và dữ liệu giả; không thử thay đổi giao diện website bên ngoài.

### Bài thử A — Chặn stylesheet ngoài origin

1. Tạo trang lab ở `http://localhost:5173` và một stylesheet từ origin khác mà bạn kiểm soát.
2. Bắt đầu với policy `style-src 'self'`.
3. Mở trang, quan sát DevTools → Network và Console.
4. Thêm host stylesheet thử nghiệm vào policy rồi tải lại.

**Kỳ vọng:** Stylesheet khác origin bị chặn khi chưa được cho phép; sau khi thêm host cụ thể, browser có thể tải nó. Kiểm tra response header CSP thực tế.

### Bài thử B — Phân biệt style element và style attribute

Tạo trang có stylesheet `<link>`, một `<style>` block và một element có `style` attribute. Dùng policy:

```http
Content-Security-Policy: default-src 'self'; style-src-elem 'self'; style-src-attr 'none'
```

**Kỳ vọng:** Stylesheet cùng origin được cho phép; style attribute bị chặn. Inline `<style>` block không có nonce/hash cũng bị chặn theo `style-src-elem`.

### Bài thử C — Nonce cho `<style>` block

Server lab sinh nonce ngẫu nhiên cho mỗi response, đặt nonce vào CSP header và một `<style>` block. Thử xóa nonce khỏi element hoặc đổi một ký tự.

**Kỳ vọng:** Chỉ style element có nonce khớp policy được chấp nhận. Nonce không cấp quyền cho `style` attribute.

### Bài thử D — `'unsafe-inline'` và refactor class

Trong lab, bật/tắt `'unsafe-inline'` với một style block và style attribute. Sau đó chuyển style attribute sang class cố định trong stylesheet.

**Kỳ vọng:** `'unsafe-inline'` làm policy chấp nhận inline style rộng hơn; refactor sang class giúp bỏ nhu cầu mở quyền inline. Ghi lại violation trước/sau thay đổi.

### Bài thử E — CSS tham chiếu ảnh và font

Tạo CSS có `@import`, `@font-face` và `background-image` trỏ tới tài nguyên trên host lab khác. Giữ `style-src` chỉ cho phép origin hiện tại; thay đổi riêng `font-src` và `img-src` để quan sát.

**Kỳ vọng:** Stylesheet, font và ảnh được kiểm soát bởi các directive tương ứng. Cho phép stylesheet không tự động cho phép mọi tài nguyên được CSS tham chiếu.

## 17. Lỗi cấu hình và cách chẩn đoán

| Triệu chứng | Nguyên nhân có thể | Hướng xử lý |
| --- | --- | --- |
| CSS file cùng origin bị chặn | URL thực tế khác origin, redirect, hoặc policy/header khác | Kiểm tra URL cuối, tất cả CSP header và source list |
| `<style>` inline bị chặn | Thiếu nonce/hash hoặc policy không cho inline | Chuyển sang file CSS, thêm nonce/hash có kiểm soát |
| `style="..."` bị chặn | `style-src-attr` là `'none'` hoặc fallback không cho phép | Dùng class; nếu có lý do đặc biệt, đánh giá hash + `'unsafe-hashes'` |
| CDN CSS bị chặn | Host CDN không có trong `style-src-elem`/`style-src` | Thêm host chính xác sau khi xác minh nhu cầu |
| Font từ CSS không tải | Thiếu `font-src` | Cấu hình `font-src` riêng |
| Ảnh nền không tải | Thiếu `img-src` cho host ảnh | Cấu hình `img-src` riêng |
| Thêm nonce nhưng style attribute vẫn bị chặn | Nonce không áp dụng cho style attribute | Chuyển sang class hoặc hash/`unsafe-hashes` nếu phù hợp |
| Policy ở code cho phép nhưng browser vẫn chặn | Proxy/CDN thêm policy khác hoặc response khác môi trường | Kiểm tra tất cả CSP header trong Network |
| Report-Only không chặn CSS | Đây là chế độ chỉ báo cáo | Chuyển sang enforcement sau khi đã xử lý violation |

Khi debug, ghi lại URL trang, directive bị vi phạm, nguồn style, loại style (external/element/attribute), browser/version và tất cả response header CSP. Đừng sửa policy chỉ dựa trên thông báo rút gọn trong Console.

## 18. Checklist review `style-src`

- [ ] Đã xác định stylesheet bên ngoài, `<style>` block và style attribute đang dùng.
- [ ] `style-src` được khai báo rõ hoặc fallback `default-src` đã được hiểu và kiểm thử.
- [ ] Đã cân nhắc tách `style-src-elem` và `style-src-attr`.
- [ ] Chỉ cho phép `'self'` và host CSS thật sự cần thiết.
- [ ] Không dùng `https:` hoặc wildcard rộng nếu host cụ thể là đủ.
- [ ] Không bật `'unsafe-inline'` chỉ để tránh violation mà chưa đánh giá.
- [ ] Nonce được sinh ngẫu nhiên theo response và chỉ gắn cho style element tin cậy.
- [ ] Hash được tính trên nội dung chính xác và cập nhật trong build pipeline.
- [ ] Hiểu rằng nonce không áp dụng cho style attribute; hash attribute cần đánh giá `'unsafe-hashes'`.
- [ ] CSS URL tham chiếu ảnh/font được kiểm soát bởi `img-src`/`font-src` phù hợp.
- [ ] CSS động từ người dùng được validate bằng mapping/grammar hẹp.
- [ ] Đã kiểm tra CSSOM và API style trên browser mục tiêu.
- [ ] Report-Only được dùng để thu thập violation trước khi enforcement.
- [ ] Đã kiểm tra CSP header do proxy/CDN thêm và response trên production-like environment.
- [ ] Có regression test cho trang quan trọng và các luồng UI nhạy cảm.

## 19. Câu hỏi tự kiểm tra

1. `style-src` kiểm soát những loại style nào?
2. `style-src-elem` khác `style-src-attr` ra sao?
3. Nếu không khai báo `style-src`, browser có thể fallback về directive nào?
4. Vì sao nonce có thể cho phép `<style>` block nhưng không cấp quyền cho `style` attribute?
5. Khi nào hash phù hợp hơn nonce? `'unsafe-hashes'` có vai trò gì?
6. Vì sao `'unsafe-inline'` làm giảm khả năng phòng CSS injection?
7. `style-src` có tự cho phép font và ảnh mà CSS tham chiếu không?
8. Làm thế nào triển khai CSP Report-Only trước khi chuyển sang enforcement?
9. Nếu policy trong ứng dụng cho phép CSS nhưng browser vẫn chặn, cần kiểm tra những response header nào?
10. Vì sao CSS injection không đồng nghĩa trực tiếp với JavaScript execution nhưng vẫn có thể ảnh hưởng bảo mật?

## 20. Ghi nhớ

`style-src` giới hạn nguồn stylesheet và làm fallback cho hai directive chi tiết `style-src-elem` và `style-src-attr`. Stylesheet ngoài, `<style>` block và `style` attribute là những trường hợp khác nhau. Nonce/hash có thể cấp quyền cho style element cụ thể; nonce không áp dụng trực tiếp cho style attribute. `'unsafe-inline'` mở rộng quyền inline và làm giảm khả năng CSP hạn chế CSS injection.

Hãy ưu tiên stylesheet cùng origin, host CDN cụ thể, class cố định và nonce/hash cho inline style thật sự cần thiết. Kiểm soát `img-src`/`font-src` riêng cho tài nguyên CSS tham chiếu, dùng Report-Only để quan sát trước khi enforcement và kiểm tra header thực tế qua proxy/CDN. **CSP style policy thu hẹp nguồn CSS; validation, thiết kế DOM và các directive khác vẫn cần thiết để bảo vệ toàn bộ ứng dụng.**
