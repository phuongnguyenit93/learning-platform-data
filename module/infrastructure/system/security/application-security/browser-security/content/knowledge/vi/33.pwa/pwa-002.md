# Web App Manifest: khai báo danh tính và cách hiển thị PWA

## Mục tiêu học tập

Sau bài học, người học có thể:

1. Giải thích vai trò của Web App Manifest trong một Progressive Web App (PWA).
2. Liên kết manifest với tài liệu HTML và phục vụ file JSON qua HTTPS với content type phù hợp.
3. Cấu hình các member quan trọng như name, short_name, id, start_url, scope, display, icons, theme_color và background_color.
4. Phân biệt navigation scope của manifest với scope của service worker và ranh giới same-origin.
5. Hiểu manifest ảnh hưởng đến cài đặt, biểu tượng, cửa sổ khởi chạy và điều hướng trong app như thế nào.
6. Tránh các lỗi về URL, icon, MIME type, JSON, scope và cập nhật manifest.
7. Đánh giá các rủi ro quyền riêng tư và bảo mật liên quan đến start_url, scope, shortcuts, share_target và file_handlers.
8. Kiểm tra manifest bằng Chrome DevTools và thử cài đặt trên các browser mục tiêu.

> **Bối cảnh:** Module Browser Security phân tích ranh giới bảo mật giữa trình duyệt, origin, cookie và ứng dụng web để hiểu Same-Origin Policy, CORS và các cơ chế cách ly; đồng thời thực hành phòng vệ XSS, CSRF, clickjacking bằng CSP, Trusted Types và security headers. Manifest là metadata mô tả PWA với browser; nó ảnh hưởng tới danh tính, biểu tượng, URL khởi chạy và cách trình bày ứng dụng sau khi cài đặt.

## 1. Web App Manifest là gì?

Web App Manifest là một file JSON mô tả các thuộc tính của web application để browser có thể hiển thị và khởi chạy website theo cách gần với ứng dụng được cài đặt trên thiết bị.

Manifest thường khai báo:

- Tên ứng dụng và tên ngắn.
- URL browser nên mở khi người dùng khởi chạy app.
- Phạm vi điều hướng mà browser xem là nằm trong app.
- Biểu tượng dùng ở launcher, home screen hoặc danh sách ứng dụng.
- Chế độ hiển thị như browser, standalone hoặc fullscreen.
- Màu giao diện và màu nền khi khởi chạy.
- Shortcut và một số khả năng tích hợp với hệ điều hành nếu browser hỗ trợ.

Ví dụ một trang liên kết manifest:

    <!doctype html>
    <html lang="vi">
    <head>
      <meta charset="utf-8">
      <meta name="viewport" content="width=device-width, initial-scale=1">
      <title>Shop Portal</title>
      <link rel="manifest" href="/manifest.webmanifest">
    </head>
    <body>
      <main id="app"></main>
    </body>
    </html>

Browser đọc file được tham chiếu bởi link rel="manifest" và dùng các member được hỗ trợ để trình bày hoặc khởi chạy ứng dụng.

### Manifest không phải service worker

Hai thành phần thường đi cùng trong PWA nhưng có nhiệm vụ khác nhau:

| Thành phần | Vai trò |
| --- | --- |
| Web App Manifest | Mô tả tên, icon, URL khởi chạy, navigation scope và display mode |
| Service worker | Có thể xử lý fetch, cache, offline behavior, push và các sự kiện nền được browser hỗ trợ |

Chỉ thêm manifest không làm website tự hoạt động offline. Manifest không đăng ký service worker, không cache API response và không tạo cơ chế đồng bộ nền.

### Manifest không phải cơ chế cấp quyền

Manifest không tự cấp quyền camera, microphone, geolocation, notification hoặc clipboard. Các API này vẫn chịu Permissions Policy, secure context, quyền người dùng và điều kiện riêng của browser.

### Manifest không bảo đảm luôn có nút Install

Manifest là một đầu vào để browser nhận diện và trình bày web app. Cách cài đặt, điều kiện hiện nút Install và API như beforeinstallprompt khác nhau theo browser, hệ điều hành và phiên bản. Một số nền tảng có luồng Add to Home Screen riêng; một số browser cung cấp cài đặt từ menu mà không dùng cùng prompt.

Các hướng dẫn cũ có thể liệt kê một bộ tiêu chí installability cụ thể, chẳng hạn yêu cầu service worker. Không xem một checklist lịch sử là yêu cầu chung cho mọi browser hiện tại. Kiểm tra tài liệu của browser mục tiêu và thử luồng cài đặt thực tế. Dù có manifest hợp lệ, browser vẫn có thể không hiển thị prompt tự động.

## 2. Liên kết và phục vụ manifest

### Đặt link trong HTML

Thông thường, link manifest nằm trong head của trang:

    <link rel="manifest" href="/manifest.webmanifest">

Dùng URL tuyệt đối theo root path hoặc URL tương đối đã được kiểm tra. Nếu ứng dụng được triển khai dưới một subpath, phải tính đúng đường dẫn của file manifest.

Ví dụ ứng dụng chạy tại:

    https://example.test/shop/

thì:

    <link rel="manifest" href="/shop/manifest.webmanifest">

tham chiếu file ở /shop/manifest.webmanifest. Trong khi đó href="manifest.webmanifest" được resolve tương đối với URL document hiện tại; kết quả có thể khác theo path của trang.

### HTTPS và origin

Trong production, phục vụ PWA qua HTTPS. Secure context là điều kiện quan trọng cho nhiều tính năng PWA và browser API.

Nên đặt manifest cùng origin với website:

    https://shop.example.test/manifest.webmanifest

Manifest ở origin khác có thể cần CORS hợp lệ và cấu hình crossorigin tương ứng trên link element. Để giảm lỗi triển khai và tránh mở rộng trust boundary, ưu tiên phục vụ manifest cùng origin với ứng dụng.

### Content-Type

Nên phục vụ manifest với MIME type:

    Content-Type: application/manifest+json

Server có thể thêm charset UTF-8:

    Content-Type: application/manifest+json; charset=utf-8

Không phục vụ manifest dưới dạng HTML do fallback route trả về. Một response 200 với trang index.html không phải manifest JSON hợp lệ.

### CSP và manifest-src

Content Security Policy có directive manifest-src để giới hạn nguồn manifest mà document được phép tải:

    Content-Security-Policy: default-src 'self'; manifest-src 'self'

Nếu ứng dụng chỉ dùng manifest same-origin, 'self' là lựa chọn rõ ràng. Không mở wildcard nếu không có nhu cầu.

## 3. Một manifest hoàn chỉnh để bắt đầu

Ví dụ dưới đây mô tả một ứng dụng bán hàng chạy trong subpath /shop/:

    {
      "id": "/shop/",
      "name": "Shop Portal",
      "short_name": "Shop",
      "description": "Ứng dụng quản lý và mua sắm trực tuyến",
      "lang": "vi",
      "dir": "ltr",
      "start_url": "/shop/?source=pwa",
      "scope": "/shop/",
      "display": "standalone",
      "display_override": [
        "window-controls-overlay",
        "standalone"
      ],
      "orientation": "any",
      "theme_color": "#17324d",
      "background_color": "#ffffff",
      "icons": [
        {
          "src": "/shop/icons/icon-192.png",
          "sizes": "192x192",
          "type": "image/png",
          "purpose": "any"
        },
        {
          "src": "/shop/icons/icon-512.png",
          "sizes": "512x512",
          "type": "image/png",
          "purpose": "any"
        },
        {
          "src": "/shop/icons/icon-maskable-512.png",
          "sizes": "512x512",
          "type": "image/png",
          "purpose": "maskable"
        }
      ],
      "categories": [
        "shopping",
        "business"
      ],
      "shortcuts": [
        {
          "name": "Đơn hàng",
          "short_name": "Đơn hàng",
          "url": "/shop/orders/",
          "icons": [
            {
              "src": "/shop/icons/orders-96.png",
              "sizes": "96x96",
              "type": "image/png"
            }
          ]
        },
        {
          "name": "Giỏ hàng",
          "short_name": "Giỏ hàng",
          "url": "/shop/cart/"
        }
      ]
    }

Đây là ví dụ cấu hình, không phải bộ member bắt buộc cho mọi browser. Hãy thay tên, URL và asset bằng tài nguyên thật của ứng dụng.

## 4. Các member nhận diện ứng dụng

### name

name là tên đầy đủ của ứng dụng. Browser có thể dùng tên này trong giao diện cài đặt, launcher hoặc danh sách ứng dụng.

    "name": "Shop Portal - Quản lý cửa hàng"

Chọn tên dễ nhận diện, không dùng tên gây nhầm với ứng dụng khác hoặc thương hiệu mà tổ chức không sở hữu.

### short_name

short_name là tên ngắn khi không gian hiển thị hạn chế:

    "short_name": "Shop"

Nên giữ tên ngắn, dễ đọc và vẫn phân biệt được ứng dụng.

### description

description mô tả ngắn mục đích ứng dụng. Đây là metadata cho browser hoặc hệ thống cài đặt sử dụng ở nơi phù hợp; không phải nội dung thay thế title và nội dung accessible của trang.

### id

id xác định danh tính ứng dụng đã cài đặt. Browser dùng giá trị này để nhận biết manifest mới có phải là bản cập nhật của cùng một ứng dụng hay mô tả một ứng dụng khác.

Ví dụ:

    "id": "/shop/"

Nên khai báo id ổn định ngay từ đầu. Khi đổi URL manifest hoặc start_url, giữ id ổn định nếu vẫn là cùng một sản phẩm. Nếu thay id, một số browser có thể xem đó là ứng dụng khác thay vì bản cập nhật.

id phải cùng origin với start_url theo quy tắc của manifest. Đừng dùng id chứa mã định danh người dùng hoặc dữ liệu riêng tư.

Nếu bỏ id, browser có quy tắc fallback để xác định identity. Dựa vào fallback có thể làm identity thay đổi ngoài dự kiến khi URL khởi chạy thay đổi; vì vậy ứng dụng production nên khai báo id rõ ràng.

## 5. start_url: URL browser mở khi khởi chạy

start_url là URL mà developer đề xuất browser mở khi người dùng khởi chạy ứng dụng đã cài đặt:

    "start_url": "/shop/"

Giá trị này là đề xuất cho user agent; browser có thể bỏ qua hoặc cho người dùng tùy chỉnh. URL được resolve tương đối với URL của manifest, phải cùng origin với document cài đặt theo quy tắc xử lý manifest.

### start_url nên ổn định và không chứa bí mật

Không đưa các giá trị sau vào start_url:

- Access token hoặc refresh token.
- Session identifier.
- Password hoặc mã xác thực.
- User ID riêng tư hoặc mã định danh duy nhất.
- Thông tin thanh toán hoặc dữ liệu cá nhân.

URL có thể xuất hiện trong browser history, server log, analytics, screenshot hoặc các hệ thống quan sát khác. Một mã định danh người dùng trong start_url còn có thể tồn tại cùng thông tin cài đặt sau khi site data bị xóa.

Nếu cần đánh dấu nguồn khởi chạy cho analytics, chỉ dùng giá trị chung không nhận diện người dùng, ví dụ:

    "start_url": "/shop/?source=pwa"

Ngay cả tham số chung cũng cần được ứng dụng xử lý như input không tin cậy và không dùng làm bằng chứng xác thực.

### start_url phải trỏ tới route hoạt động

Kiểm tra:

- Server trả đúng trang ứng dụng khi truy cập trực tiếp.
- Route hoạt động sau khi reload.
- Nếu yêu cầu đăng nhập, luồng redirect/login được thiết kế rõ ràng.
- Không phụ thuộc state chỉ có trong memory của tab trước.
- URL nằm trong navigation scope đã khai báo.

Không dùng start_url trỏ tới trang tạm thời, endpoint redirect không ổn định hoặc URL chứa state dùng một lần.

## 6. scope: navigation scope của ứng dụng

scope xác định những URL mà browser xem là nằm trong phạm vi điều hướng của ứng dụng:

    "scope": "/shop/"

Với ví dụ trên, các URL cùng origin bắt đầu bằng path /shop/ thuộc scope, chẳng hạn:

    https://example.test/shop/
    https://example.test/shop/orders/
    https://example.test/shop/cart/

Các URL sau nằm ngoài scope:

    https://example.test/
    https://example.test/help/
    https://accounts.example.test/shop/

Khác origin thì không nằm trong scope, kể cả path giống nhau.

### Nên khai báo scope tường minh

Nếu bỏ scope, browser tính scope mặc định từ start_url. Quy tắc mặc định dựa trên parent path của start_url sau khi bỏ filename, query và fragment. Điều này có thể tạo phạm vi khác với điều nhóm phát triển nghĩ.

Ví dụ:

    "start_url": "/shop/index.html"

Nếu không khai báo scope, phạm vi mặc định có thể là /shop/. Nếu start_url là /shop/ thì scope mặc định là /shop/.

Hãy khai báo rõ:

    "start_url": "/shop/"
    "scope": "/shop/"

Dùng dấu slash cuối để tránh prefix ngoài ý muốn. Scope được so sánh theo prefix path; scope là /shop không phải cách diễn đạt rõ ràng bằng /shop/ vì prefix /shop có thể khớp cả /shopping.

start_url phải nằm trong scope được xử lý. Nếu start_url ở ngoài scope, browser có thể bỏ qua scope không hợp lệ hoặc dùng giá trị mặc định theo thuật toán của manifest. Giữ start_url và scope cùng origin, đồng thời kiểm tra URL sau khi resolve từ vị trí file manifest.

### Khi điều hướng ra ngoài scope

Navigation ra ngoài scope vẫn có thể xảy ra. Browser có thể chuyển sang giao diện browser thông thường hoặc hiển thị dấu hiệu cho biết người dùng đã rời khỏi phạm vi ứng dụng.

scope không phải firewall và không chặn request:

- Không ngăn JavaScript gọi fetch tới URL ngoài scope.
- Không giới hạn API mà backend cung cấp.
- Không thay Same-Origin Policy hoặc CORS.
- Không kiểm soát quyền truy cập tài khoản.
- Không ngăn người dùng nhập trực tiếp URL ngoài scope.

Backend vẫn phải xác thực session và authorization cho mọi route/API.

### Manifest scope khác service worker scope

Hai khái niệm cùng dùng từ scope nhưng mục đích khác nhau:

| Phạm vi | Được khai báo ở đâu | Kiểm soát điều gì |
| --- | --- | --- |
| Manifest scope | Member scope trong manifest | Navigation được xem là nằm trong app khi áp dụng presentation của manifest |
| Service worker scope | Đăng ký service worker, tùy chọn scope | Các client/navigation mà service worker có thể kiểm soát |

Ví dụ manifest:

    "scope": "/shop/"

Service worker:

    navigator.serviceWorker.register("/shop/sw.js", {
      scope: "/shop/"
    });

Hai giá trị có thể giống nhau nhưng không tự động liên kết. Một app có manifest scope /shop/ không có nghĩa service worker đã được đăng ký hoặc có quyền kiểm soát /shop/.

## 7. display và display_override

display mô tả cách browser nên trình bày ứng dụng đã cài đặt:

| Giá trị | Ý nghĩa |
| --- | --- |
| browser | Hiển thị trong browser thông thường |
| minimal-ui | Giao diện browser tối giản nếu được hỗ trợ |
| standalone | Giao diện giống ứng dụng riêng, thường không có thanh địa chỉ đầy đủ |
| fullscreen | Yêu cầu hiển thị toàn màn hình |

Ví dụ:

    "display": "standalone"

Browser có thể không hỗ trợ mọi mode hoặc áp dụng fallback. display không thay đổi origin, sandbox hay quyền JavaScript của trang.

### display_override

display_override cho phép liệt kê các mode ưu tiên theo thứ tự, browser chọn mode đầu tiên hỗ trợ rồi fallback về display:

    "display_override": [
      "window-controls-overlay",
      "standalone"
    ],
    "display": "standalone"

Đây là tính năng nâng cao; chỉ dùng khi giao diện ứng dụng có thể thích nghi với mode được chọn. Kiểm tra hỗ trợ trên browser/OS mục tiêu.

### Fullscreen không phải bảo đảm

Không giả định manifest display fullscreen sẽ buộc mọi browser hoặc mọi lần khởi chạy luôn vào fullscreen. Browser và hệ điều hành có thể áp dụng quy tắc riêng; người dùng vẫn kiểm soát thiết bị và có thể rời ứng dụng.

## 8. theme_color, background_color và orientation

### theme_color

theme_color gợi ý màu giao diện browser hoặc hệ điều hành sử dụng khi trình bày app:

    "theme_color": "#17324d"

Giá trị này cũng có thể được khai báo qua meta theme-color trong HTML để hỗ trợ các browser không đọc hoặc không cập nhật manifest theo cùng cách:

    <meta name="theme-color" content="#17324d">

Hãy giữ màu có độ tương phản phù hợp với các thành phần giao diện.

### background_color

background_color là màu nền browser có thể dùng trong quá trình khởi chạy trước khi stylesheet tải xong:

    "background_color": "#ffffff"

Chọn màu gần với nền ban đầu của ứng dụng để giảm hiện tượng nháy màu khi launch.

### orientation

orientation là hướng màn hình mặc định mà ứng dụng đề xuất:

    "orientation": "any"

Một số giá trị thường gặp gồm any, natural, portrait, portrait-primary, landscape và landscape-primary. Browser/hệ điều hành có thể không áp dụng hoặc hạn chế theo thiết bị.

Không khóa orientation nếu giao diện có thể thích nghi responsive. Chỉ yêu cầu hướng cụ thể khi chức năng thật sự cần, ví dụ một trò chơi hoặc ứng dụng hiển thị chuyên dụng.

## 9. icons: biểu tượng ứng dụng

icons là danh sách hình ảnh browser có thể dùng ở launcher, home screen, task switcher hoặc giao diện cài đặt.

Ví dụ:

    "icons": [
      {
        "src": "/shop/icons/icon-192.png",
        "sizes": "192x192",
        "type": "image/png",
        "purpose": "any"
      },
      {
        "src": "/shop/icons/icon-512.png",
        "sizes": "512x512",
        "type": "image/png",
        "purpose": "any"
      }
    ]

### src

src là URL của icon, thường nên dùng asset cùng origin và path ổn định. URL tương đối được resolve theo URL manifest, không phải luôn theo URL HTML.

Nếu manifest ở /shop/manifest.webmanifest và icon src là icons/icon-192.png, URL kết quả là /shop/icons/icon-192.png.

### sizes

sizes khai báo kích thước ảnh, ví dụ 192x192 hoặc 512x512. Cung cấp nhiều kích thước giúp browser chọn icon phù hợp với launcher và thiết bị.

Các kích thước 192x192 và 512x512 thường được dùng trong triển khai thực tế, nhưng yêu cầu cài đặt cụ thể khác nhau theo browser và nền tảng.

### type

type khai báo MIME type, ví dụ image/png hoặc image/webp. Khai báo đúng định dạng của file.

### purpose: any, maskable và monochrome

purpose mô tả cách icon có thể được sử dụng:

| Giá trị | Ý nghĩa |
| --- | --- |
| any | Icon thông thường, browser có thể crop/mask theo giao diện |
| maskable | Icon được thiết kế để browser áp dụng mask theo hình dạng launcher |
| monochrome | Icon đơn sắc cho các giao diện hỗ trợ |

Maskable icon cần đặt nội dung quan trọng trong safe zone để không bị cắt khi browser dùng mask hình tròn, vuông bo góc hoặc hình dạng khác.

Không chỉ đổi purpose thành maskable cho một icon đã thiết kế sát mép. Hãy tạo asset riêng, kiểm tra vùng an toàn và xem trước trên nhiều hình mask.

### Fallback icon

Không phải browser nào cũng hỗ trợ cùng bộ icon format và purpose. Có thể cung cấp PNG phổ biến để tăng tương thích, đồng thời thử nghiệm SVG/WebP nếu nền tảng mục tiêu hỗ trợ.

Icon không phải bằng chứng danh tính hay chữ ký của ứng dụng. Kẻ tấn công kiểm soát website có thể thay icon; browser vẫn phải xác định origin và TLS như bình thường.

## 10. Shortcuts và các member mở rộng

### shortcuts

shortcuts cho phép browser hiển thị lối tắt tới một số tác vụ trong menu ứng dụng:

    "shortcuts": [
      {
        "name": "Đơn hàng",
        "short_name": "Đơn hàng",
        "url": "/shop/orders/",
        "icons": [
          {
            "src": "/shop/icons/orders-96.png",
            "sizes": "96x96",
            "type": "image/png"
          }
        ]
      }
    ]

URL shortcut nên cùng origin và nằm trong manifest scope. Khi route mở, backend vẫn xác thực session; shortcut không tạo quyền truy cập đặc biệt.

### screenshots

screenshots có thể cung cấp ảnh xem trước cho một số giao diện cài đặt hoặc catalog. Chỉ dùng ảnh đúng với trải nghiệm thật và không để lộ dữ liệu tài khoản, thông tin cá nhân hoặc nội dung nội bộ.

### categories

categories mô tả nhóm ứng dụng như shopping, business, education hoặc productivity. Đây là metadata phân loại, không ảnh hưởng authorization.

### share_target

share_target cho phép ứng dụng nhận nội dung được chia sẻ từ hệ điều hành/browser nếu nền tảng hỗ trợ:

    "share_target": {
      "action": "/shop/share/",
      "method": "POST",
      "enctype": "multipart/form-data",
      "params": {
        "title": "title",
        "text": "text",
        "url": "url",
        "files": [
          {
            "name": "files",
            "accept": ["image/*", "text/plain"]
          }
        ]
      }
    }

Dữ liệu nhận từ share target là input không tin cậy. Server cần kiểm tra MIME type thực tế, kích thước, nội dung file, CSRF/session và quyền người dùng. Không tin filename hoặc accept filter như bằng chứng file an toàn.

Đặt action cùng origin và trong phạm vi route mà ứng dụng kiểm soát. Endpoint nhận share phải xử lý cả request POST và file upload như một endpoint web thông thường: xác thực, chống CSRF, giới hạn kích thước và kiểm tra nội dung.

### file_handlers và protocol_handlers

Một số browser hỗ trợ member đăng ký khả năng mở loại file hoặc protocol từ ứng dụng. Đây là tích hợp mạnh với hệ điều hành và có thể làm ứng dụng nhận dữ liệu từ nguồn bên ngoài.

Nếu dùng:

- Chỉ khai báo file type thực sự cần.
- Kiểm tra nội dung file ở server hoặc parser an toàn.
- Không thực thi nội dung file chỉ vì extension phù hợp.
- Xác thực URL/protocol và chống open redirect.
- Kiểm tra browser support và yêu cầu user consent.

Các member mở rộng không được hỗ trợ đồng đều. Đừng làm luồng cốt lõi phụ thuộc vào một capability chỉ có ở một browser.

## 11. Manifest và ranh giới bảo mật

Manifest là metadata công khai được browser tải. Không đưa bí mật hoặc cấu hình nội bộ vào file này.

### start_url không phải cơ chế xác thực

Một URL như:

    "start_url": "/shop/?user=123"

có thể tiết lộ định danh trong lịch sử, log và hệ thống analytics. Nếu backend dựa vào tham số này để quyết định người dùng nào được đăng nhập, thiết kế đó không an toàn.

Xác thực bằng session/token được quản lý theo kiến trúc phù hợp; backend kiểm tra quyền trên mỗi request. start_url chỉ chọn trang mở đầu.

### scope không phải ranh giới quyền truy cập

Manifest scope quyết định navigation nào được trình bày như nằm trong app. Nó không chặn người dùng truy cập URL khác và không giới hạn fetch/API.

Không đặt authorization dựa trên việc URL nằm trong scope hay ngoài scope.

### standalone không tạo sandbox

Ứng dụng hiển thị standalone vẫn chạy với origin và quyền của website. display không cô lập JavaScript, không ngăn XSS và không làm cookie/localStorage an toàn hơn.

### Manifest không thay CSP hoặc Permissions Policy

CSP manifest-src kiểm soát nguồn manifest; CSP script-src kiểm soát nguồn script; Permissions Policy kiểm soát browser feature. Manifest không thay thế các header bảo mật đó.

### Bảo vệ manifest và asset

- Phục vụ manifest qua HTTPS.
- Dùng same-origin nếu có thể.
- Trả đúng content type và JSON hợp lệ.
- Chỉ đưa icon, shortcut và URL thuộc ứng dụng đã kiểm soát.
- Không đưa token, API key hoặc user identifier vào manifest.
- Hạn chế manifest-src về self nếu chỉ dùng manifest cùng origin.
- Kiểm tra quyền publish file manifest trong deployment pipeline.

## 12. Cập nhật manifest và cache

Manifest có thể thay đổi theo phiên bản ứng dụng:

- Tên hoặc short_name được cập nhật.
- Icon được thay.
- start_url hoặc shortcuts được điều chỉnh.
- display hoặc theme_color thay đổi.

Browser không nhất thiết tải và áp dụng mọi thay đổi ngay sau mỗi lần reload. Cách phát hiện, thời điểm fetch lại và thời điểm cập nhật giao diện cài đặt khác nhau theo browser và nền tảng.

### Cache header cho manifest

Nếu muốn browser revalidate manifest thường xuyên:

    Cache-Control: no-cache
    ETag: "manifest-v12"

no-cache cho phép lưu response nhưng yêu cầu revalidate trước khi dùng lại khi cần. Nó không có nghĩa là không lưu.

Nếu manifest được version hóa trong URL, có thể dùng cache policy dài hơn và cập nhật link rel="manifest" khi phát hành. Chọn chiến lược thống nhất với quy trình deploy.

### Manifest và service worker cache

Nếu service worker chủ động cache file manifest, ứng dụng cần quản lý version và invalidation. Không giả định browser luôn nhận manifest mới ngay khi server đã deploy.

Với manifest thay đổi thường xuyên, cân nhắc không đưa manifest vào cache-first của service worker; dùng network/revalidation hoặc chiến lược có version rõ ràng.

### Giữ id ổn định khi cập nhật

Khi đổi tên, icon, theme hoặc start_url, giữ id nếu vẫn là cùng một ứng dụng. Chỉ đổi id khi thực sự muốn browser nhận diện một ứng dụng khác.

## 13. Kiểm tra manifest bằng Chrome DevTools

Thực hiện trên HTTPS staging hoặc localhost và dùng tên/icon thử nghiệm.

### Bước 1 — Xác nhận link manifest

1. Mở trang ứng dụng.
2. DevTools → Elements.
3. Tìm link rel="manifest" trong head.
4. Kiểm tra href đã resolve đúng URL.

### Bước 2 — Kiểm tra response

1. DevTools → Network.
2. Lọc request manifest.
3. Kiểm tra status 200.
4. Kiểm tra Content-Type là application/manifest+json.
5. Kiểm tra response body là JSON hợp lệ, không phải HTML fallback.
6. Kiểm tra redirect và origin của manifest.

### Bước 3 — Application panel

Trong Chrome DevTools:

1. Mở tab Application.
2. Chọn Manifest.
3. Kiểm tra name, short_name, id, start_url, scope và display.
4. Xem icon browser đã nhận.
5. Đọc cảnh báo về member thiếu, URL lỗi hoặc icon không hợp lệ.
6. Dùng tùy chọn cài đặt thử nếu browser cung cấp.

Giao diện DevTools thay đổi theo phiên bản; nếu mục Manifest không xuất hiện, kiểm tra link và Network trước.

### Bước 4 — Kiểm tra scope

1. Mở một URL nằm trong scope, ví dụ /shop/orders/.
2. Quan sát app được browser trình bày như ứng dụng.
3. Mở URL ngoài scope, ví dụ /help/.
4. Quan sát browser UI hoặc cách điều hướng thay đổi.
5. Xác nhận backend vẫn áp dụng authorization cho cả hai route.

### Bước 5 — Kiểm tra cài đặt và cập nhật

1. Cài app trên browser/OS mục tiêu.
2. Khởi chạy từ launcher và xác nhận start_url.
3. Cập nhật name/icon trong manifest ở staging.
4. Revalidate hoặc reload theo hướng dẫn browser.
5. Ghi nhận thời gian và cách browser áp dụng thay đổi.

## 16. Câu hỏi củng cố

**Câu 1.** Web App Manifest có nhiệm vụ chính gì?

**Giải đáp:** Mô tả metadata cho browser như tên, icon, URL khởi chạy, navigation scope và display mode của ứng dụng web.

**Câu 2.** Thêm manifest có làm website tự hoạt động offline không?

**Giải đáp:** Không. Offline behavior thường cần service worker và chiến lược cache/network riêng.

**Câu 3.** id khác start_url như thế nào?

**Giải đáp:** id xác định identity của ứng dụng đã cài; start_url là URL browser được đề xuất mở khi khởi chạy.

**Câu 4.** scope có chặn người dùng truy cập URL ngoài phạm vi không?

**Giải đáp:** Không. Scope chỉ xác định navigation được browser trình bày như nằm trong app. Backend vẫn phải xác thực và authorization.

**Câu 5.** Manifest scope và service worker scope có tự động giống nhau không?

**Giải đáp:** Không. Một cái điều khiển navigation presentation của app; cái còn lại điều khiển phạm vi client mà service worker có thể kiểm soát.

**Câu 6.** Có nên đưa user ID vào start_url không?

**Giải đáp:** Không. URL có thể được lưu trong history, log và thông tin cài đặt, tạo dấu vết định danh lâu dài.

**Câu 7.** display standalone có tạo sandbox cho JavaScript không?

**Giải đáp:** Không. Ứng dụng vẫn chạy trong origin của website và chịu các cơ chế bảo mật web thông thường.

**Câu 8.** Vì sao cần icon purpose maskable riêng?

**Giải đáp:** Launcher có thể áp dụng mask với hình dạng khác nhau. Icon maskable cần safe zone để logo không bị cắt.

## 17. Tổng kết

Web App Manifest là file JSON mô tả danh tính và cách browser trình bày một PWA. Các member quan trọng gồm name, short_name, id, start_url, scope, display, icons, theme_color và background_color. Hãy khai báo id ổn định, start_url cùng origin, scope tường minh có dấu slash cuối và icon đúng kích thước/purpose.

Manifest không đăng ký service worker, không tự tạo offline mode, không cấp quyền API và không tạo ranh giới authorization. Manifest scope chỉ ảnh hưởng navigation presentation; service worker scope là cơ chế riêng. Không đưa token hoặc định danh cá nhân vào start_url, validate dữ liệu từ share_target/file handlers và kiểm thử install/update trên từng browser/OS.

Phục vụ manifest qua HTTPS với MIME type application/manifest+json, giới hạn nguồn bằng CSP manifest-src, quản lý cache/update có chủ đích và giữ manifest cùng origin khi có thể. Dùng DevTools để xác minh response, JSON, URL, icon, scope và hành vi cài đặt trước khi phát hành.
