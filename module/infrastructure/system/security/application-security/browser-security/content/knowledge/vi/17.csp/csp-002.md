# script-src — kiểm soát nguồn và cách thực thi JavaScript bằng CSP

> **Chương:** CSP  
> **Mục tiêu:** Hiểu directive `script-src` trong Content Security Policy, phân biệt script cùng origin, script bên ngoài và inline script; cấu hình nonce/hash, `strict-dynamic`, kiểm soát event handler và dynamic code; triển khai Report-Only, xử lý cache và kiểm chứng chính sách trên browser.

## 1. script-src bảo vệ điều gì?

Một trang web có thể chạy JavaScript từ nhiều nơi: file ứng dụng cùng origin, CDN, thư viện phân tích, widget đối tác, đoạn script inline trong HTML hoặc script được tạo động khi trang chạy. Nếu kẻ tấn công chèn được một thẻ script hoặc một event handler, mã đó có thể thực thi trong origin của ứng dụng và sử dụng quyền mà trang đang có.

**Content Security Policy (CSP)** cho phép server khai báo những nguồn và cách thực thi nội dung mà browser được phép chấp nhận. Directive `script-src` kiểm soát các nguồn JavaScript chính, gồm:

- Script bên ngoài được tải qua phần tử `<script src="...">`.
- Script inline nằm trực tiếp trong HTML.
- Một số dạng thực thi code động như `eval()` hoặc `new Function()`.
- Một số ngữ cảnh script đặc biệt như event handler và URL dạng `javascript:`, tùy directive và chính sách cụ thể.

Ví dụ policy đơn giản:

```http
Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'self'
```

Với policy này, browser chỉ cho phép script từ cùng origin theo `'self'`. Inline script không có cơ chế cho phép riêng sẽ bị chặn; script từ CDN khác origin cũng bị chặn.

**CSP là lớp phòng vệ bổ sung.** Nó giúp giảm tác động của XSS và hạn chế nguồn script, nhưng không thay thế output encoding, xử lý DOM an toàn, kiểm soát quyền hoặc sửa lỗ hổng injection tại nguồn.

## 2. CSP được gửi và áp dụng ở đâu?

Với ứng dụng web, nên gửi CSP bằng HTTP response header:

```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Security-Policy: default-src 'self'; script-src 'self'
```

Browser áp dụng policy cho tài liệu nhận response. Reverse proxy, CDN hoặc ứng dụng có thể là nơi thêm header; cần kiểm tra **response cuối cùng** mà browser nhận được, không chỉ file cấu hình ở một tầng.

CSP cũng có thể khai báo bằng meta element:

```html
<meta
  http-equiv="Content-Security-Policy"
  content="default-src 'self'; script-src 'self'"
>
```

Tuy nhiên, meta CSP chỉ bắt đầu có hiệu lực khi parser gặp thẻ meta. Nội dung được tải hoặc thực thi trước đó có thể không chịu policy. Một số directive không được hỗ trợ qua meta, chẳng hạn `frame-ancestors` và chế độ `Content-Security-Policy-Report-Only`. Vì vậy, **response header là lựa chọn phù hợp cho policy bảo mật chính**.

### Nhiều CSP cùng lúc

Một tài liệu có thể nhận nhiều CSP header hoặc có thêm meta policy. Các policy thực thi được áp dụng đồng thời; browser phải thỏa **tất cả** chính sách, nên kết quả thường là giao của các quyền được cho phép. Một header CSP rộng hơn không thể mở lại script mà một policy thực thi khác đã chặn.

`Content-Security-Policy-Report-Only` chỉ báo cáo vi phạm và không chặn; nó không nới lỏng một CSP enforcement đang có.

## 3. script-src và các directive liên quan

Các directive có phạm vi khác nhau:

| Directive | Kiểm soát |
| --- | --- |
| `default-src` | Nguồn mặc định cho nhiều loại tài nguyên nếu không có directive chuyên biệt |
| `script-src` | Chính sách script tổng quát; đồng thời là fallback cho các directive script chuyên biệt khi chúng không được khai báo |
| `script-src-elem` | Script được tải hoặc nhúng qua phần tử `<script>` |
| `script-src-attr` | Inline event handler trong thuộc tính như `onclick`, `onerror` |

Quan hệ fallback:

1. Với phần tử `<script>`, browser ưu tiên `script-src-elem`; nếu không có, dùng `script-src`; nếu cũng không có, dùng `default-src`.
2. Với event handler attribute, browser ưu tiên `script-src-attr`; nếu không có, dùng `script-src`; nếu không có nữa, dùng `default-src`.
3. `script-src` không ghi đè một cách tự động các directive chuyên biệt đã được khai báo.

Ví dụ:

```http
Content-Security-Policy: default-src 'self'; script-src 'self'; script-src-attr 'none'
```

Policy trên cho phép script phần tử từ cùng origin, đồng thời chặn inline event handler. Nếu muốn kiểm soát riêng script element, có thể khai báo `script-src-elem`.

## 4. Source expression: browser cho phép script từ đâu?

`script-src` có thể chứa nhiều source expression:

| Source expression | Ý nghĩa | Ví dụ |
| --- | --- | --- |
| `'self'` | Cùng origin với tài liệu | `script-src 'self'` |
| `'none'` | Không cho phép nguồn nào | `script-src 'none'` |
| Host source | Cho phép host/nguồn cụ thể theo cú pháp CSP | `https://cdn.example.com` |
| Scheme source | Cho phép nguồn dùng scheme tương ứng | `https:` |
| `'nonce-...'` | Cho phép script có nonce khớp với giá trị trong policy | `'nonce-RANDOM_VALUE'` |
| `'sha256-...'` | Cho phép inline script có hash khớp | `'sha256-BASE64_DIGEST'` |
| `'strict-dynamic'` | Mở rộng niềm tin từ script được xác thực bằng nonce/hash sang script do nó nạp động, trong browser hỗ trợ | `'strict-dynamic'` |
| `'unsafe-inline'` | Cho phép inline script/event handler theo phạm vi directive | Cần tránh trong policy nghiêm ngặt |
| `'unsafe-eval'` | Cho phép các API đánh giá chuỗi như code | Chỉ dùng khi thật sự cần và đã đánh giá |

Các keyword CSP như `'self'`, `'none'`, `'nonce-...'` phải có dấu nháy đơn. Host source và scheme source không đặt trong dấu nháy.

Không nên dùng wildcard hoặc scheme source rộng chỉ để làm lỗi CSP biến mất. Một host được cho phép có thể chứa endpoint JSONP, script do người dùng kiểm soát hoặc thư viện có lỗ hổng; cho phép tải script từ host đó đồng nghĩa mở rộng ranh giới tin cậy.

## 5. 'self' và host allowlist: tiện lợi nhưng có giới hạn

Policy:

```http
Content-Security-Policy: script-src 'self' https://cdn.example.com
```

cho phép script từ origin ứng dụng và CDN đã nêu. Cách này dễ triển khai với ứng dụng cũ, nhưng cần kiểm tra:

- CDN có phục vụ file script cố định và được kiểm soát không?
- Host có endpoint JSONP hoặc nội dung do người dùng tải lên không?
- Có subdomain nào cùng origin trust boundary nhưng do tenant khác quản lý không?
- Có redirect hoặc cấu hình hosting khiến host được phép phục vụ script ngoài dự kiến không?

`'self'` cũng không bảo đảm mọi file cùng origin đều an toàn. Nếu ứng dụng phục vụ nội dung người dùng tải lên trên cùng origin, một đường dẫn có thể trở thành nguồn script không mong muốn nếu MIME type, nosniff và cách nhúng không được cấu hình đúng.

Host allowlist thường là bước cải thiện so với không có CSP, nhưng policy dựa trên nonce/hash và `strict-dynamic` có thể tạo ranh giới rõ hơn cho ứng dụng hiện đại.

## 6. Nonce: cho phép đúng script được server tin cậy

**Nonce** là một giá trị ngẫu nhiên, khó đoán, do server tạo cho mỗi response HTML. CSP chứa nonce đó; chỉ script element có thuộc tính `nonce` khớp mới được phép chạy theo cơ chế nonce.

Response header:

```http
Content-Security-Policy: script-src 'nonce-RANDOM_NONCE_PER_RESPONSE'; object-src 'none'; base-uri 'self'
```

HTML:

```html
<script nonce="RANDOM_NONCE_PER_RESPONSE">
  initializeApplication();
</script>
<script nonce="RANDOM_NONCE_PER_RESPONSE" src="/assets/app.js"></script>
```

`RANDOM_NONCE_PER_RESPONSE` là placeholder minh họa, không phải giá trị để dùng trong production. Server phải:

1. Sinh nonce bằng CSPRNG.
2. Tạo nonce mới cho mỗi response HTML.
3. Đặt cùng giá trị vào CSP header và các script element được phép.
4. Không để người dùng hoặc dữ liệu không tin cậy điều khiển thuộc tính nonce.
5. Không ghi nonce vào log công khai hoặc tái sử dụng lâu dài.

Nonce không phải token đăng nhập và không dùng để xác thực người dùng. Nó chỉ là bằng chứng cho browser rằng script element cụ thể được server đánh dấu là đáng tin cậy trong response đó.

### Nonce và cache

Nếu CDN cache nguyên HTML cùng CSP header rồi phát lại cho nhiều người dùng, nonce có thể bị tái sử dụng ngoài ý muốn. Điều này làm giảm lợi ích của nonce và có thể khiến response không còn được ràng buộc với một lần render riêng.

Các hướng xử lý thường gặp:

- Không cache HTML có nonce ở shared cache, hoặc cấu hình cache để nonce được tạo mới ở tầng edge cho từng response.
- Dùng hash cho inline script tĩnh không thay đổi nếu phù hợp.
- Kiểm tra CSP header và HTML được cache như một cặp; không để proxy thay một bên mà quên bên còn lại.

Không tạo nonce cố định trong source code, file template hoặc biến môi trường dài hạn. Nonce phải được sinh cho response theo thiết kế.

## 7. Hash: cho phép inline script có nội dung cố định

Thay vì nonce, CSP có thể cho phép một inline script dựa trên hash của **nội dung script chính xác**:

```html
<script>
  initializeApplication();
</script>
```

Server hoặc build pipeline tính SHA-256, SHA-384 hoặc SHA-512 trên nội dung inline script theo quy tắc CSP, sau đó khai báo:

```http
Content-Security-Policy: script-src 'sha256-BASE64_DIGEST'
```

`BASE64_DIGEST` là placeholder; cần thay bằng digest thực được tính từ đúng bytes nội dung script. Dấu cách, xuống dòng và thay đổi ký tự trong inline block có thể làm hash không còn khớp.

Hash phù hợp với inline script tĩnh, ít thay đổi. Nếu script được render với dữ liệu động hoặc thay đổi theo template, hash phải được tính lại theo nội dung cuối cùng; nonce thường thuận tiện hơn.

### Hash không tự cho phép event handler

Hash của inline `<script>` không mặc nhiên cho phép thuộc tính `onclick` hoặc URL `javascript:`. Muốn cho phép event handler dựa trên hash, CSP có cơ chế `'unsafe-hashes'` cùng hash phù hợp, nhưng đây là lựa chọn cần cân nhắc kỹ.

Thiết kế tốt hơn thường là bỏ inline handler:

```html
<button id="save">Lưu</button>
```

```js
document.querySelector("#save").addEventListener("click", saveForm);
```

Điều này tách hành vi khỏi markup, dễ kiểm thử và tránh phải cấp quyền cho từng chuỗi event handler.

## 8. 'strict-dynamic': mở rộng niềm tin từ script gốc

Ứng dụng hiện đại thường có một script bootstrap đáng tin cậy, sau đó script này tải module hoặc chunk động. Nếu chỉ dùng nonce/hash, mỗi script tải động có thể cần được cấp quyền riêng.

`'strict-dynamic'` cho phép browser hỗ trợ CSP3 mở rộng niềm tin từ script được cho phép bằng nonce hoặc hash sang script mà script đáng tin cậy đó nạp động thông qua các thao tác phù hợp.

Ví dụ:

```http
Content-Security-Policy: script-src 'nonce-RANDOM_NONCE' 'strict-dynamic'; object-src 'none'; base-uri 'self'
```

HTML bootstrap:

```html
<script nonce="RANDOM_NONCE" src="/assets/bootstrap.js"></script>
```

Bootstrap có thể nạp chunk ứng dụng:

```js
const script = document.createElement("script");
script.src = "/assets/dashboard.chunk.js";
document.head.append(script);
```

Trong browser hỗ trợ `strict-dynamic`, script được tin cậy có thể truyền niềm tin cho script nó nạp động. Vì vậy, script bootstrap trở thành một **root of trust**: nếu bootstrap có thể bị kiểm soát bởi dữ liệu không tin cậy, policy có thể cho phép mã độc đi theo chuỗi tải script.

Không dùng `strict-dynamic` như cách bỏ qua việc kiểm soát loader. Hãy kiểm tra mọi đường mà script gốc dùng để chọn URL, tên module, plugin hoặc chunk. URL script động cần được xây dựng từ manifest/allowlist do ứng dụng kiểm soát, không nối trực tiếp dữ liệu người dùng.

### Tương thích với browser cũ

Trong CSP3, khi `'strict-dynamic'` được hỗ trợ cùng nonce/hash, browser hiện đại bỏ qua một số host source, scheme source và `'self'` trong `script-src` để dựa vào chuỗi tin cậy. Các browser cũ không hiểu `strict-dynamic` có thể tiếp tục dùng host allowlist làm fallback.

Ví dụ policy tương thích:

```http
Content-Security-Policy: script-src 'nonce-RANDOM_NONCE' 'strict-dynamic' 'self' https://cdn.example.com
```

Trong browser CSP3 hiện đại, nonce/strict-dynamic là cơ chế chính; trong browser cũ, `'self'` và CDN host có thể là fallback. Hãy thử nghiệm trên browser mục tiêu và giữ allowlist fallback ở mức tối thiểu cần thiết.

## 9. Inline event handler và javascript: URL

Các thuộc tính như:

```html
<button onclick="saveForm()">Lưu</button>
<img src="/avatar.png" onerror="showFallback()">
```

là inline event handler. Một policy nghiêm ngặt như:

```http
Content-Security-Policy: script-src 'self'; script-src-attr 'none'
```

sẽ chặn inline event handler trong browser hỗ trợ directive chuyên biệt. Nếu không có `script-src-attr`, `script-src` điều khiển theo fallback.

Thay bằng event listener:

```js
document.querySelector("#save").addEventListener("click", saveForm);
```

URL dạng `javascript:...` cũng là một đường thực thi script và bị kiểm soát bởi chính sách script. Không cho dữ liệu người dùng tạo ra javascript URL; nếu thuộc tính cần một liên kết, parse URL và allowlist scheme như `https:`.

Không thêm `'unsafe-inline'` chỉ để giữ lại handler cũ. Hãy chuyển handler sang JavaScript module hoặc file được kiểm soát, rồi bật CSP theo từng giai đoạn.

## 10. 'unsafe-inline': vì sao làm yếu script-src?

`'unsafe-inline'` cho phép inline script và event handler trong phạm vi directive tương ứng. Khi có nó, các payload được chèn vào HTML có thể có thêm cơ hội thực thi.

Ví dụ policy yếu:

```http
Content-Security-Policy: script-src 'self' 'unsafe-inline'
```

Policy này cho phép script cùng origin và inline script. Nếu ứng dụng có DOM XSS hoặc HTML injection, CSP có thể không còn chặn được nhiều đường thực thi inline.

Trong CSP3, nếu `script-src` có nonce-source hoặc hash-source hợp lệ, `'unsafe-inline'` bị bỏ qua bởi browser hỗ trợ cơ chế mới. Tuy nhiên, không nên dựa vào quy tắc này để giữ policy khó hiểu; hãy bỏ `'unsafe-inline'` khi đã chuyển sang nonce/hash.

Nếu legacy code bắt buộc cần inline script, hãy đánh giá nonce hoặc hash thay vì cho phép mọi inline script. Đối với inline event handler, ưu tiên chuyển sang `addEventListener`.

## 11. 'unsafe-eval' và dynamic code

`'unsafe-eval'` cho phép các API chuyển chuỗi thành mã được thực thi, chẳng hạn:

- `eval("...")`.
- `new Function("...")`.
- `setTimeout("code", delay)` và `setInterval("code", delay)` dạng chuỗi.

Ví dụ:

```js
// Tránh: chuỗi được diễn giải như code.
setTimeout("refreshDashboard()", 1000);

// Nên dùng: truyền function.
setTimeout(() => refreshDashboard(), 1000);
```

Một số thư viện hoặc build tool cũ có thể yêu cầu `unsafe-eval` trong môi trường development. Không mang ngoại lệ đó sang production nếu không cần. Hãy tìm thư viện gây ra yêu cầu, bật build production phù hợp hoặc thay thế cách thực thi chuỗi.

WebAssembly có keyword riêng `'wasm-unsafe-eval'` trong CSP hiện đại để kiểm soát biên dịch/khởi tạo một số luồng WebAssembly. Đừng thêm keyword này hoặc `'unsafe-eval'` chỉ vì một lỗi console mà chưa xác định API và browser đang sử dụng.

## 12. script-src và Subresource Integrity (SRI)

CSP trả lời câu hỏi **nguồn nào được phép cung cấp script**. Nó không tự xác minh nội dung file tại một URL có đúng phiên bản mà ứng dụng mong đợi hay không.

Với thư viện CDN có nội dung tĩnh, có thể dùng **Subresource Integrity (SRI)**:

```html
<script
  src="https://cdn.example.com/library-1.2.3.min.js"
  integrity="sha384-BASE64_DIGEST"
  crossorigin="anonymous"
></script>
```

`BASE64_DIGEST` là placeholder; phải lấy hash chính xác từ artifact đã kiểm chứng. SRI giúp browser kiểm tra nội dung tải về có khớp hash khai báo không.

Đối với tài nguyên cross-origin, server CDN cần hỗ trợ CORS phù hợp để browser thực hiện kiểm tra SRI; thuộc tính `crossorigin` thường được dùng với `anonymous`. SRI không thay CSP: CSP giới hạn nguồn, SRI kiểm tra nội dung của tài nguyên cụ thể.

Nếu CDN thay nội dung mà không đổi URL, SRI sẽ làm tải script thất bại khi hash không còn khớp. Đây là hành vi mong muốn để phát hiện thay đổi ngoài dự kiến, nhưng quy trình nâng cấp thư viện cần cập nhật hash có kiểm soát.

## 13. Report-Only: quan sát trước khi chặn

Khi ứng dụng lớn, áp dụng CSP enforcement ngay có thể làm hỏng tính năng hợp lệ như analytics, module loader hoặc widget. Có thể triển khai một policy thử nghiệm bằng:

```http
Content-Security-Policy-Report-Only: default-src 'self'; script-src 'self' 'nonce-RANDOM_NONCE'
```

Browser sẽ ghi nhận vi phạm theo cơ chế báo cáo đã cấu hình nhưng **không chặn** tài nguyên vì policy Report-Only đó. Nếu tài liệu đã có CSP enforcement, policy enforcement vẫn tiếp tục chặn theo quy tắc của nó.

Quy trình triển khai:

1. Thu thập các script hợp lệ đang chạy và nguồn tải chúng.
2. Đưa policy dự kiến vào Report-Only.
3. Kiểm tra Console và báo cáo CSP; phân loại vi phạm thật, extension noise và tài nguyên hợp lệ.
4. Chuyển inline script sang nonce/hash, bỏ event handler và dynamic eval khi có thể.
5. Kiểm thử các luồng đăng nhập, thanh toán, lazy-load, analytics và module chunk.
6. Chuyển sang `Content-Security-Policy` enforcement, sau đó tiếp tục theo dõi.

Không coi số lượng report bằng 0 là bằng chứng tuyệt đối rằng không còn XSS. Báo cáo có thể thiếu do browser, cấu hình endpoint, mạng hoặc nội dung chưa được kích hoạt trong kiểm thử.

## 14. Policy mẫu theo mức độ

### Mức 1 — ứng dụng chỉ tải script cùng origin

```http
Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'self'; frame-ancestors 'none'
```

Phù hợp khi không có inline script và không cần CDN. Cần kiểm tra framework/build output thực tế.

### Mức 2 — dùng nonce cho script được server đánh dấu

```http
Content-Security-Policy: default-src 'self'; script-src 'nonce-RANDOM_NONCE_PER_RESPONSE'; script-src-attr 'none'; object-src 'none'; base-uri 'self'; frame-ancestors 'none'
```

Dùng nonce mới cho mỗi response và gắn cho đúng script. Nếu ứng dụng cần file script cùng origin không có nonce, phải quyết định rõ có thêm `'self'` hay chuyển file script sang nonce/SRI/loader đã kiểm soát.

### Mức 3 — bootstrap nonce với strict-dynamic

```http
Content-Security-Policy: default-src 'self'; script-src 'nonce-RANDOM_NONCE_PER_RESPONSE' 'strict-dynamic' 'self' https://cdn.example.com; script-src-attr 'none'; object-src 'none'; base-uri 'self'; frame-ancestors 'none'
```

Đây là mẫu tương thích có fallback; browser CSP3 hiện đại dựa vào nonce/strict-dynamic khi hỗ trợ, trong khi browser cũ có thể dùng host source. Kiểm tra loader và nguồn script được tải động trước khi áp dụng.

**Không sao chép nguyên mẫu vào production.** Mỗi ứng dụng có tập script, module, iframe, worker và yêu cầu tích hợp khác nhau. Policy phải được thiết kế từ tài nguyên thực tế, kiểm thử và phát hành theo giai đoạn.

## 15. Chẩn đoán lỗi script bị CSP chặn

| Thông báo/hiện tượng | Nguyên nhân thường gặp | Hướng kiểm tra |
| --- | --- | --- |
| Inline script bị blocked | Thiếu nonce/hash hoặc policy không cho inline | Kiểm tra header và nonce/hash của đúng script block |
| File CDN bị blocked | Host không nằm trong source list hoặc strict-dynamic đang thay đổi cách đánh giá | Kiểm tra CSP đầy đủ, nonce/hash và browser CSP3 |
| Event handler không chạy | `script-src-attr 'none'` hoặc fallback script-src chặn inline handler | Chuyển sang addEventListener |
| `eval` bị blocked | Không có `'unsafe-eval'` | Loại bỏ dynamic code hoặc thay thư viện |
| Nonce không khớp | Header và HTML dùng hai giá trị khác nhau, hoặc cache làm lệch cặp | Kiểm tra cùng response và cache layer |
| Script hash không khớp | Nội dung, whitespace hoặc line ending đã thay đổi | Tính lại hash từ nội dung inline cuối cùng |
| Script được nạp động bị chặn | Loader không được tin cậy hoặc strict-dynamic không áp dụng như dự kiến | Kiểm tra nonce/hash root, browser support và chuỗi loader |
| Chỉ lỗi sau deploy | CDN/proxy thêm CSP khác hoặc cache HTML cũ | Kiểm tra response cuối, nhiều CSP header và cache |

DevTools Console thường nêu directive và nguồn bị chặn. Network cho biết response header thực tế. Hãy kiểm tra cả HTML cuối cùng và header tương ứng; đừng chỉ sửa policy theo một thông báo lỗi đơn lẻ.

## 16. Thực hành: triển khai script-src trong ứng dụng lab

Thực hiện trên một trang thử nghiệm do bạn kiểm soát. Dùng nội dung script vô hại và không thử khai thác website bên ngoài.

### Bước 1 — Tạo trang có các loại script khác nhau

```html
<!doctype html>
<html lang="vi">
  <meta charset="utf-8">
  <title>CSP script-src lab</title>
  <button id="run">Chạy script ngoài</button>
  <p id="status">Chưa chạy</p>

  <script>
    document.querySelector("#status").textContent = "Inline script chạy";
  </script>

  <script src="/assets/app.js"></script>
</html>
```

Trong `/assets/app.js`, cập nhật một thông báo text đơn giản. Không thêm event handler inline vào markup.

### Bước 2 — Bật policy nghiêm ngặt

Server trả:

```http
Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'self'
```

Kỳ vọng file `/assets/app.js` được phép nếu cùng origin, còn inline script không có nonce/hash bị chặn. Quan sát Console.

### Bước 3 — Thêm nonce

Server sinh nonce ngẫu nhiên cho response, thêm `'nonce-...'` vào `script-src` và gắn cùng nonce vào inline script được phép. Tải lại trang và xác nhận chỉ script có nonce hợp lệ chạy.

Không dùng nonce cố định trong lab khi chuyển thành ví dụ production; mỗi response phải có nonce mới.

### Bước 4 — Thử event handler và eval

Thêm một event handler inline trong trang lab và thử `eval` với chuỗi vô hại. Quan sát policy chặn. Sau đó chuyển handler sang `addEventListener` và thay code động bằng function được định nghĩa trong file script.

### Bước 5 — Report-Only

Đưa policy dự kiến sang `Content-Security-Policy-Report-Only`. So sánh Console và hành vi: vi phạm được báo cáo nhưng không bị policy Report-Only chặn. Giữ lại enforcement header hiện có nếu cần.

### Bước 6 — Kiểm tra cache

Tải cùng trang qua các tầng cache nếu lab có CDN/proxy. Xác nhận nonce trong HTML khớp nonce trong CSP header của **cùng response** và không bị tái sử dụng ngoài ý muốn.

## 17. Những ngộ nhận thường gặp

| Ngộ nhận | Cách hiểu đúng |
| --- | --- |
| “Có script-src là đã chống được mọi XSS.” | CSP giảm một số đường thực thi; source-to-sink, output encoding và safe DOM vẫn cần thiết. |
| “'self' chỉ cho phép code do team viết.” | Mọi script phục vụ cùng origin có thể nằm trong phạm vi; cần kiểm tra nội dung người dùng và endpoint động. |
| “Nonce có thể dùng cố định.” | Nonce cần ngẫu nhiên và mới cho mỗi response HTML. |
| “Hash script không quan tâm whitespace.” | Hash phụ thuộc nội dung chính xác của inline block. |
| “Nonce cho phép event handler inline.” | Nonce trên script element không tự cấp quyền cho `onclick`; dùng event listener. |
| “strict-dynamic cho phép mọi script.” | Nó mở rộng niềm tin từ script nonce/hash được tin cậy sang script do nó nạp; loader phải được kiểm soát. |
| “Thêm unsafe-inline là cách sửa CSP nhanh.” | Nó làm yếu policy và có thể mở lại nhiều đường injection. |
| “unsafe-eval chỉ ảnh hưởng eval.” | Nó còn liên quan Function constructor và timer dạng chuỗi; WebAssembly có keyword riêng trong CSP hiện đại. |
| “CSP host allowlist kiểm tra nội dung script.” | Nó cho phép nguồn; SRI mới kiểm tra nội dung tài nguyên theo hash đã khai báo. |
| “Report-Only đang chặn thử.” | Report-Only báo cáo, không chặn; enforcement policy vẫn có hiệu lực độc lập. |

## 18. Checklist triển khai script-src

- Gửi CSP bằng response header và kiểm tra header cuối cùng ở browser.
- Bắt đầu với nguồn script tối thiểu; tránh wildcard và scheme source rộng.
- Ưu tiên nonce mới cho mỗi response hoặc hash cho inline script tĩnh.
- Không dùng nonce cố định; đồng bộ nonce giữa HTML và CSP qua cache/proxy.
- Dùng `strict-dynamic` chỉ khi hiểu và kiểm soát root script/loader.
- Chuyển inline event handler sang `addEventListener`.
- Tránh `'unsafe-inline'` và `'unsafe-eval'` trong production.
- Chỉ thêm host CDN đã xác minh; cân nhắc SRI cho script tĩnh bên thứ ba.
- Dùng `script-src-attr` để kiểm soát event handler và `script-src-elem` khi cần phân tách.
- Dùng Report-Only để quan sát trước khi enforcement, nhưng không coi report là bằng chứng đầy đủ.
- Kiểm tra các framework escape hatch, module loader, analytics và script được tải động.
- Kiểm thử luồng đăng nhập, thanh toán, lazy load và browser mục tiêu sau khi bật policy.

## 19. Câu hỏi tự kiểm tra

1. `script-src` kiểm soát những loại script nào và fallback với `default-src` ra sao?
2. Khác biệt giữa `script-src-elem` và `script-src-attr` là gì?
3. Vì sao nonce cần được tạo mới cho từng response HTML?
4. Hash CSP được tính trên phần nào của inline script và vì sao whitespace có thể làm thay đổi hash?
5. Vì sao nonce/hash trên script element không mặc nhiên cho phép inline event handler?
6. `strict-dynamic` truyền niềm tin theo cơ chế nào và vì sao loader trở thành root of trust?
7. Vì sao host allowlist có thể yếu hơn nonce/hash?
8. `unsafe-inline` và `unsafe-eval` mở rộng bề mặt thực thi ra sao?
9. CSP và SRI giải quyết hai câu hỏi bảo mật nào khác nhau?
10. Report-Only khác enforcement như thế nào và vì sao cần kiểm tra response qua cache?

**Ghi nhớ:** `script-src` là trung tâm kiểm soát JavaScript trong CSP. Hãy giới hạn nguồn script, ưu tiên nonce hoặc hash thay cho cho phép inline rộng, dùng `strict-dynamic` chỉ khi root loader đáng tin, loại bỏ event handler và dynamic eval khi có thể, và kiểm tra cache/response thực tế. CSP giảm tác động XSS nhưng hiệu quả phụ thuộc vào cách ứng dụng kiểm soát dữ liệu và sink; output encoding, safe DOM, sanitizer và authorization vẫn là những lớp bắt buộc.
