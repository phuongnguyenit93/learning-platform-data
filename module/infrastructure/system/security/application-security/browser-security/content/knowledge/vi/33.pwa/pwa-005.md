# Push notification

> **Chương:** PWA  
> **Học phần:** Application Security — Browser Security (SECURITY_APPLICATION_SECURITY_BROWSER_SECURITY)

Push notification cho phép server thông báo cho người dùng ngay cả khi trang web không đang mở ở foreground. Trong Progressive Web App (PWA), Web Push thường kết hợp Push API, Service Worker và Notifications API: người dùng chủ động đồng ý nhận thông báo, browser tạo một subscription, server gửi thông điệp qua push service của browser, Service Worker nhận sự kiện push và hiển thị notification.

Luồng này tạo ra một ranh giới bảo mật giữa ứng dụng, browser và push service. Subscription chứa endpoint cùng các key dùng để mã hóa payload; endpoint cần được bảo vệ như một capability nhạy cảm. Server phải xác thực người dùng khi đăng ký/hủy subscription, bảo vệ VAPID private key, mã hóa payload theo Web Push protocol và giới hạn nội dung nhạy cảm. Push notification cũng cần tôn trọng quyền người dùng, tránh prompt bất ngờ và xử lý việc permission hoặc subscription bị thu hồi.

Push service không phải hàng đợi nghiệp vụ bảo đảm giao nhận chính xác một lần. Thông báo có thể bị trễ, hết TTL, bị thay thế hoặc không đến thiết bị. Ứng dụng nên gửi tín hiệu ngắn gọn để Service Worker đồng bộ trạng thái có thẩm quyền từ server khi cần.

## 1. Mục tiêu học tập

Sau bài học, bạn có thể:

1. Phân biệt Push API, Notifications API và Service Worker.
2. Mô tả vòng đời từ permission đến subscription, gửi push và hiển thị notification.
3. Xin quyền notification đúng thời điểm sau hành động có ý nghĩa của người dùng.
4. Đăng ký Service Worker và tạo PushSubscription với VAPID public key.
5. Gửi subscription về server an toàn và gắn với đúng tài khoản/thiết bị.
6. Giải thích vai trò của VAPID, subscription keys và mã hóa payload Web Push.
7. Xử lý sự kiện push, notificationclick và điều hướng an toàn.
8. Quản lý TTL, retry, subscription hết hạn và rotation key.
9. Bảo vệ endpoint đăng ký, endpoint push và dữ liệu notification khỏi lạm dụng.
10. Kiểm thử permission, subscription, delivery và các tình huống thu hồi trong browser.

## 2. Push notification gồm những thành phần nào?

Ba API phía browser có vai trò khác nhau:

| Thành phần | Vai trò |
| --- | --- |
| Push API | Cho phép ứng dụng tạo subscription và nhận sự kiện push qua Service Worker |
| Service Worker | Chạy ngoài vòng đời trang đang mở, nhận push event và thực hiện công việc nền được browser cho phép |
| Notifications API | Hiển thị notification cho người dùng, thường qua ServiceWorkerRegistration.showNotification() trong PWA |

Ở phía server, ứng dụng cần một Web Push sender, VAPID key pair và kho lưu subscription. Giữa server ứng dụng và browser còn có push service do browser/vendor hoặc nhà cung cấp nền tảng vận hành.

Push notification không đồng nghĩa với một WebSocket luôn mở. Browser có thể đánh thức Service Worker khi có push mà không cần giữ tab hoạt động. Tuy vậy, browser và hệ điều hành vẫn kiểm soát tài nguyên, lịch giao nhận và quyền hiển thị.

## 3. Kiến trúc và luồng tổng thể

~~~mermaid
sequenceDiagram
    participant U as Người dùng
    participant P as PWA / Browser
    participant SW as Service Worker
    participant APP as Application Server
    participant PS as Push Service

    U->>P: Bấm bật thông báo
    P->>P: Xin Notification permission
    P->>SW: Đăng ký Service Worker
    P->>PS: PushManager.subscribe(VAPID public key)
    PS-->>P: PushSubscription (endpoint + keys)
    P->>APP: Gửi subscription qua HTTPS
    APP->>APP: Xác thực user, lưu subscription
    APP->>PS: Gửi Web Push đã mã hóa + VAPID
    PS-->>SW: Phát sự kiện push
    SW->>SW: Giải mã payload do browser xử lý
    SW->>P: showNotification()
    U->>SW: Bấm notification
    SW->>P: Focus tab hoặc mở route an toàn
~~~

Các bước trên có thể diễn ra cách nhau nhiều phút hoặc nhiều giờ. Người dùng có thể đóng tab, browser có thể ngủ, subscription có thể thay đổi và push service có thể trì hoãn thông điệp. Server cần coi subscription là trạng thái có thể thay đổi, không phải một địa chỉ giao hàng tồn tại vĩnh viễn.

## 4. Secure context và khả năng hỗ trợ

Web Push và Service Worker yêu cầu secure context trong browser hiện đại. Production nên dùng HTTPS với certificate hợp lệ; localhost thường được browser xem là môi trường đáng tin cậy cho phát triển.

Trước khi bật chức năng, kiểm tra API:

~~~js
function supportsWebPush() {
  return (
    "serviceWorker" in navigator &&
    "PushManager" in window &&
    "Notification" in window
  );
}

if (!supportsWebPush()) {
  showPushUnavailableMessage();
}
~~~

Sự tồn tại của các API không bảo đảm push hoạt động giống nhau trên mọi browser, hệ điều hành hoặc chế độ cài đặt. Hãy kiểm tra browser/version mục tiêu, secure context, quyền thông báo, khả năng chạy Service Worker và các giới hạn nền tảng. Nếu không hỗ trợ, cung cấp trải nghiệm thay thế như badge trong ứng dụng hoặc cập nhật khi người dùng mở lại trang.

## 5. Permission của notification

Notification permission có ba trạng thái phổ biến:

| Trạng thái | Ý nghĩa | Ứng xử của ứng dụng |
| --- | --- | --- |
| default | Người dùng chưa đưa ra quyết định rõ ràng | Giải thích lợi ích và chỉ hỏi sau hành động chủ động |
| granted | Browser cho phép origin hiển thị notification | Có thể đăng ký push nếu API và các điều kiện khác đáp ứng |
| denied | Người dùng hoặc browser đã từ chối | Không lặp prompt; giải thích cách người dùng tự thay đổi trong cài đặt nếu họ muốn |

Permission gắn với origin và được browser quản lý. Người dùng có thể thu hồi quyền sau khi đã cấp; ứng dụng cần kiểm tra trạng thái hiện tại thay vì chỉ ghi nhớ một cờ trong localStorage.

Không tự động gọi requestPermission khi trang vừa tải, khi người dùng chưa hiểu chức năng hoặc sau mỗi lần refresh. Prompt bất ngờ làm giảm niềm tin và nhiều browser có thể hạn chế các lời gọi không gắn với user activation.

## 6. Thiết kế UX opt-in

Hãy giải thích loại thông báo, tần suất và cách tắt trước khi yêu cầu permission. Ví dụ, một nút có nhãn “Bật thông báo cập nhật đơn hàng” giúp người dùng hiểu họ đang đăng ký điều gì.

Luồng phù hợp:

1. Hiển thị lợi ích cụ thể ngay trong màn hình liên quan.
2. Người dùng bấm nút bật thông báo.
3. Ứng dụng kiểm tra API và trạng thái permission.
4. Chỉ khi cần, gọi Notification.requestPermission() trong handler của hành động đó.
5. Nếu được cấp quyền, tạo subscription và gửi về server.
6. Nếu bị từ chối hoặc browser không hỗ trợ, giữ chức năng cốt lõi của ứng dụng hoạt động.

Không dùng nội dung gây hiểu nhầm như “Bắt buộc bật để tiếp tục” nếu tính năng không thực sự bắt buộc. Cung cấp cách tắt thông báo và hủy đăng ký trong phần cài đặt tài khoản.

## 7. Xin quyền sau hành động người dùng

Ví dụ:

~~~js
async function requestNotificationPermission() {
  if (!("Notification" in window)) {
    return "unsupported";
  }

  if (Notification.permission === "granted") {
    return "granted";
  }

  if (Notification.permission === "denied") {
    return "denied";
  }

  return Notification.requestPermission();
}

enableNotificationsButton.addEventListener("click", async () => {
  const permission = await requestNotificationPermission();

  if (permission === "granted") {
    await enablePushSubscription();
  } else {
    showNotificationPermissionState(permission);
  }
});
~~~

Nút bật thông báo nên được bấm trực tiếp bởi người dùng. Không gọi requestNotificationPermission trong useEffect, khi app khởi động hoặc từ một tác vụ nền. Nếu trạng thái là denied, không có API web chuẩn nào cho phép ứng dụng tự bật lại quyền; người dùng phải thay đổi trong browser/OS settings.

## 8. Đăng ký Service Worker

Service Worker cần được đăng ký trước khi tạo subscription:

~~~js
async function registerAppServiceWorker() {
  if (!("serviceWorker" in navigator)) {
    throw new Error("Service Worker is not supported");
  }

  return navigator.serviceWorker.register("/sw.js", {
    scope: "/"
  });
}
~~~

File Service Worker phải nằm trong phạm vi URL/scope phù hợp và được phục vụ với JavaScript content type. Server không nên trả HTML fallback cho URL /sw.js khi file không tồn tại. Dùng HTTPS và kiểm tra registration trong DevTools → Application → Service Workers.

Không đăng ký nhiều Service Worker scope chồng lấn một cách tùy tiện. Xác định rõ scope của PWA và phối hợp push handler với các handler fetch, install, activate đã có trong worker.

## 9. VAPID là gì?

VAPID (Voluntary Application Server Identification) cho phép application server chứng minh danh tính với push service. Ứng dụng tạo một cặp khóa public/private:

- Public key được đưa cho browser khi gọi PushManager.subscribe().
- Private key chỉ lưu ở server và dùng ký JWT VAPID khi gửi push.
- Subject trong VAPID thường là địa chỉ liên hệ dạng mailto: hoặc URL HTTPS của nhà vận hành.

VAPID dùng chữ ký ECDSA trên đường cong P-256 (JWT algorithm ES256) để xác thực application server với push service. VAPID không mã hóa nội dung push. Payload encryption là cơ chế riêng của Web Push protocol và sử dụng key material gắn với subscription.

Không bao giờ đưa VAPID private key vào JavaScript bundle, HTML, source map, mobile client hoặc repository công khai. Public key không phải bí mật và có thể được browser tải xuống.

## 10. Tạo và quản lý VAPID key pair

Có thể dùng thư viện Web Push phía server để tạo key pair và cấu hình sender. Ví dụ với package web-push trong Node.js:

~~~js
const webpush = require("web-push");

const vapidKeys = webpush.generateVAPIDKeys();
console.log("Public key:", vapidKeys.publicKey);
console.log("Private key:", vapidKeys.privateKey);
~~~

Đây là thao tác tạo key cho môi trường development. Trong production:

- Tạo key trong quy trình quản lý secret được kiểm soát.
- Lưu private key trong secret manager hoặc kho bí mật tương đương.
- Phân tách key giữa development, staging và production.
- Giới hạn quyền đọc private key cho workload gửi push.
- Có kế hoạch backup, rotation và ứng phó khi key bị lộ.
- Không log key hoặc đưa nó vào telemetry.

Khi thay VAPID key, các subscription được tạo với public key cũ có thể cần quy trình chuyển đổi hoặc đăng ký lại tùy browser. Hãy kiểm thử chiến lược rotation trước khi thay key production và duy trì khả năng gửi tới subscription cũ trong giai đoạn chuyển tiếp nếu kiến trúc yêu cầu.

## 11. Tạo PushSubscription

PushManager.subscribe() cần Service Worker registration, user-visible behavior và VAPID public key:

~~~js
function urlBase64ToUint8Array(base64String) {
  const padding = "=".repeat((4 - base64String.length % 4) % 4);
  const base64 = (base64String + padding)
    .replace(/-/g, "+")
    .replace(/_/g, "/");
  const raw = atob(base64);
  return Uint8Array.from(raw, (character) => character.charCodeAt(0));
}

async function createPushSubscription(vapidPublicKey) {
  const registration = await navigator.serviceWorker.ready;
  const existing = await registration.pushManager.getSubscription();

  if (existing) {
    // Nếu VAPID key đã đổi, cần migration có chủ đích thay vì gửi
    // subscription cũ bằng private key mới.
    return existing;
  }

  return registration.pushManager.subscribe({
    userVisibleOnly: true,
    applicationServerKey: urlBase64ToUint8Array(vapidPublicKey)
  });
}
~~~

VAPID public key phải là public key tương ứng với private key mà server sử dụng để gửi. userVisibleOnly: true khai báo rằng push được dùng cho trải nghiệm thông báo hiển thị với người dùng; không dùng Push API như một kênh nền bí mật để chạy tác vụ không có thông báo.

Chỉ tạo subscription sau khi người dùng opt-in và permission đã granted. Nếu đã có subscription, lấy và đồng bộ subscription hiện tại thay vì tạo nhiều subscription không cần thiết.

Đoạn code trên giả định VAPID public key không đổi. Khi rotate key, kiểm tra applicationServerKey hiện có qua subscription.options.applicationServerKey nếu browser hỗ trợ; không gửi subscription được tạo bằng key cũ bằng private key mới. Lập kế hoạch migration riêng, có thể cần unsubscribe rồi subscribe lại sau khi người dùng đã opt-in, và duy trì khả năng xử lý subscription cũ trong giai đoạn chuyển tiếp.

## 12. Gửi subscription về application server

PushSubscription có endpoint và key material. Có thể serialize bằng toJSON():

~~~js
async function saveSubscription(subscription, csrfToken) {
  const response = await fetch("/api/push/subscriptions", {
    method: "POST",
    credentials: "same-origin",
    headers: {
      "Content-Type": "application/json",
      "X-CSRF-Token": csrfToken
    },
    body: JSON.stringify(subscription.toJSON())
  });

  if (!response.ok) {
    throw new Error("Could not save push subscription");
  }
}
~~~

Endpoint đăng ký subscription phải xác thực người dùng và bảo vệ CSRF nếu dùng cookie session. Server cần xác định subscription thuộc user/device nào từ session đã xác thực, không tin userId do client tự gửi trong body.

Subscription endpoint là URL do push service cấp và có thể hoạt động như một capability: ai có endpoint cùng key material phù hợp có thể thử gửi thông điệp tới subscription đó. Không đưa endpoint vào log công khai, analytics, URL điều hướng hoặc nội dung notification. Lưu trữ subscription với quyền truy cập giới hạn và bảo vệ dữ liệu ở trạng thái lưu.

## 13. Lưu trữ và liên kết subscription

Một người dùng có thể đăng nhập trên nhiều browser profile hoặc thiết bị. Server thường cần nhiều subscription cho một user:

| Trường dữ liệu | Mục đích |
| --- | --- |
| subscription_id | ID nội bộ do server tạo |
| user_id | Tài khoản sở hữu subscription hiện tại |
| endpoint | Push endpoint do browser cung cấp |
| p256dh | Public key của subscription dùng trong mã hóa payload |
| auth | Authentication secret của subscription |
| created_at / updated_at | Theo dõi vòng đời |
| last_success_at | Theo dõi lần gửi thành công gần nhất |
| user_agent/device_label (nếu cần) | Hiển thị thiết bị cho người dùng; không dùng làm danh tính bảo mật |

Không lấy user_id từ client làm căn cứ duy nhất để gắn subscription. Lấy user identity từ session đã xác thực. Đặt unique constraint phù hợp trên endpoint hoặc fingerprint nội bộ để tránh duplicate record; bảo vệ endpoint và key material ở database.

Khi người dùng đổi tài khoản trên cùng browser profile, phải gỡ liên kết subscription khỏi tài khoản cũ trước khi gắn cho tài khoản mới. Nếu không, người dùng tiếp theo có thể tiếp tục nhận thông báo riêng tư của tài khoản trước.

## 14. Payload encryption của Web Push

Web Push protocol mã hóa payload trước khi application server gửi tới push service. Browser tạo subscription key material; server dùng public key và auth secret trong subscription để mã hóa payload theo chuẩn Web Push (ví dụ content encoding aes128gcm). Browser giải mã trước khi phát sự kiện push cho Service Worker.

Các lớp bảo vệ có vai trò riêng:

- TLS bảo vệ kết nối application server tới push service.
- VAPID xác thực application server với push service.
- Web Push payload encryption bảo vệ nội dung payload khỏi push service và bên trung gian không có key giải mã.
- Authorization ở application server quyết định user nào được gửi thông báo nào.

VAPID không phải encryption key của payload. Không tự viết thuật toán mã hóa; dùng thư viện Web Push đã được duy trì và tuân theo chuẩn. Không gửi payload nhạy cảm chỉ vì payload được mã hóa: thiết bị người dùng vẫn hiển thị notification trên màn hình khóa và có thể bị người khác nhìn thấy.

## 15. Gửi Web Push từ server

Ví dụ Node.js dùng package web-push:

~~~js
const webpush = require("web-push");

webpush.setVapidDetails(
  "mailto:security@example.com",
  process.env.VAPID_PUBLIC_KEY,
  process.env.VAPID_PRIVATE_KEY
);

async function sendInboxUpdate(subscription, eventId) {
  const payload = {
    type: "INBOX_UPDATE",
    eventId
  };

  return webpush.sendNotification(
    subscription,
    JSON.stringify(payload),
    {
      TTL: 60,
      urgency: "normal"
    }
  );
}
~~~

Ví dụ chỉ minh họa cấu trúc. Subscription phải được lấy từ database theo user được phép nhận event; eventId phải là định danh không nhạy cảm và server cần xác minh quyền khi người dùng mở nội dung. Thư viện thực hiện VAPID signing và payload encryption theo cấu hình; không tự gửi payload plaintext.

Không gửi push tới mọi subscription chỉ vì chúng nằm trong database. Trước khi gửi, kiểm tra quyền nhận thông báo, trạng thái tài khoản, loại event, tùy chọn user và giới hạn tần suất.

## 16. TTL, urgency và topic

Push service có thể giữ thông điệp trong một khoảng thời gian nếu thiết bị chưa online. TTL (time to live) giới hạn thời gian thông điệp được giữ; sau TTL, thông điệp có thể bị loại bỏ.

| Thuộc tính | Ý nghĩa | Cách chọn |
| --- | --- | --- |
| TTL | Thời gian push service có thể giữ thông điệp | Ngắn cho sự kiện nhanh hết giá trị; dài hơn cho thông báo có thể đọc sau |
| Urgency | Mức ưu tiên tương đối của thông điệp | Chọn theo mức cần thiết, không đặt mọi thông báo thành high |
| Topic | Khóa thay thế thông điệp đang chờ theo quy tắc Web Push | Dùng khi chỉ cần trạng thái mới nhất, ví dụ nhiều lần cập nhật cùng một đơn hàng |

Push không phải giao nhận exactly-once hoặc bảo đảm thứ tự nghiệp vụ. Một thông điệp có thể đến trễ, hết TTL hoặc không được giao. Ứng dụng nên có eventId, xử lý idempotent và tải trạng thái mới nhất từ API đã xác thực khi người dùng mở notification.

Push service áp dụng giới hạn kích thước payload riêng; giới hạn có thể khác theo provider và thay đổi theo thời gian. Giữ payload nhỏ, tránh gửi bản ghi lớn hoặc dữ liệu nhạy cảm; nếu cần nhiều dữ liệu, gửi eventId rồi tải nội dung từ API sau khi xác thực.

## 17. Xử lý push event trong Service Worker

Service Worker có thể bị dừng sau khi event hoàn tất; hãy dùng event.waitUntil() để browser biết công việc bất đồng bộ cần được hoàn tất:

~~~js
self.addEventListener("push", (event) => {
  let payload = { type: "SYNC" };

  try {
    if (event.data) {
      const parsed = event.data.json();
      if (parsed && typeof parsed === "object" && !Array.isArray(parsed)) {
        payload = parsed;
      }
    }
  } catch {
    payload = { type: "SYNC" };
  }

  const title = "Bạn có cập nhật mới";
  const options = {
    body: "Mở ứng dụng để xem chi tiết.",
    icon: "/icons/icon-192.png",
    badge: "/icons/badge-72.png",
    tag: "account-updates",
    data: {
      eventId: typeof payload.eventId === "string"
        ? payload.eventId
        : null
    }
  };

  event.waitUntil(
    self.registration.showNotification(title, options)
  );
});
~~~

Payload là dữ liệu đầu vào không nên được tin mù quáng. Kiểm tra type, độ dài và schema; không chèn HTML từ payload vào notification hoặc DOM. Ví dụ trên dùng title/body cố định để tránh đưa nội dung riêng tư lên màn hình khóa.

Nếu push payload chỉ là tín hiệu “có cập nhật”, Service Worker có thể gọi API đồng bộ tối thiểu khi phù hợp, nhưng phải tính tới credential, network availability, thời gian chạy nền và việc Service Worker có thể bị dừng.

## 18. Hiển thị notification an toàn

Trong Service Worker, dùng registration.showNotification():

~~~js
await self.registration.showNotification("Bạn có cập nhật mới", {
  body: "Mở ứng dụng để xem chi tiết.",
  icon: "/icons/icon-192.png",
  badge: "/icons/badge-72.png",
  tag: "inbox-update",
  renotify: false,
  data: {
    route: "/inbox"
  }
});
~~~

Không đưa OTP, access token, refresh token, nội dung tin nhắn riêng tư hoặc thông tin tài chính vào title/body nếu chúng có thể hiện trên màn hình khóa. Notification có thể được hiển thị ngoài ứng dụng và nhìn thấy bởi người ở gần thiết bị.

Notification không phải nguồn dữ liệu có thẩm quyền. Khi người dùng bấm, ứng dụng phải tải lại dữ liệu từ server và kiểm tra session/authorization hiện tại. Không coi eventId trong payload là bằng chứng người dùng có quyền xem bản ghi tương ứng.

## 19. Xử lý notification click

Notification click thường được xử lý trong Service Worker:

~~~js
self.addEventListener("notificationclick", (event) => {
  event.notification.close();

  const targetUrl = new URL("/inbox", self.location.origin);

  event.waitUntil((async () => {
    const windows = await self.clients.matchAll({
      type: "window",
      includeUncontrolled: true
    });

    for (const client of windows) {
      if (new URL(client.url).origin === self.location.origin) {
        await client.focus();
        if ("navigate" in client) {
          return client.navigate(targetUrl.href);
        }
        return;
      }
    }

    return self.clients.openWindow(targetUrl.href);
  })());
});
~~~

Đường dẫn đích được cố định trong ứng dụng. Nếu payload cần chứa route, server và client phải validate route theo allowlist same-origin; không chuyển trực tiếp URL tùy ý từ push payload sang clients.openWindow(). Điều này tránh notification trở thành open redirect hoặc điều hướng người dùng tới trang lừa đảo.

Sau khi mở trang, frontend cần tải lại nội dung từ API và kiểm tra quyền. Nếu user đã logout hoặc tài khoản bị thu hồi, route phải yêu cầu đăng nhập lại.

## 20. Notification actions và dữ liệu tương tác

Notification có thể khai báo action để người dùng chọn thao tác:

~~~js
await self.registration.showNotification("Có yêu cầu mới", {
  body: "Mở ứng dụng để xử lý.",
  actions: [
    { action: "open", title: "Mở ứng dụng" },
    { action: "dismiss", title: "Để sau" }
  ],
  data: { eventId: "evt_123" }
});
~~~

Không thực hiện hành động nhạy cảm chỉ dựa trên action string hoặc payload. Nếu action dẫn tới phê duyệt giao dịch, thay đổi quyền hoặc xóa dữ liệu, mở ứng dụng để xác thực người dùng và yêu cầu xác nhận theo quy trình server-side. Browser/platform có thể hỗ trợ action khác nhau; cung cấp đường click mặc định có thể hoạt động rộng hơn.

## 21. Unsubscribe và thu hồi subscription

Người dùng cần có cách tắt thông báo trong cài đặt ứng dụng. Để hủy subscription phía browser:

~~~js
async function unsubscribePush() {
  const registration = await navigator.serviceWorker.ready;
  const subscription = await registration.pushManager.getSubscription();

  if (!subscription) {
    return false;
  }

  const endpoint = subscription.endpoint;
  const response = await fetch("/api/push/subscriptions/remove", {
    method: "POST",
    credentials: "same-origin",
    headers: {
      "Content-Type": "application/json",
      "X-CSRF-Token": getCsrfToken()
    },
    body: JSON.stringify({ endpoint })
  });

  if (!response.ok) {
    throw new Error("Could not unlink push subscription from account");
  }

  return subscription.unsubscribe();
}
~~~

Trong production, server nên hỗ trợ gỡ subscription theo ID nội bộ hoặc xác định endpoint thuộc user đang đăng nhập; không tin endpoint do client gửi mà không kiểm tra quyền sở hữu. Ví dụ unlink ở server trước khi unsubscribe tại browser để server ngừng gửi ngay cả khi bước local gặp lỗi. Nếu bước local thất bại, hiển thị trạng thái cần thử lại hoặc đồng bộ lại khi người dùng mở app.

Khi logout, tách subscription khỏi tài khoản cũ để thiết bị dùng chung không tiếp tục nhận thông báo của người trước. Việc có unsubscribe ở browser hay chỉ unlink khỏi user là quyết định sản phẩm; dù chọn cách nào, server phải ngăn gửi thông báo riêng tư tới tài khoản đã logout.

## 22. Subscription hết hạn và thay đổi

Subscription có thể hết hiệu lực do người dùng thu hồi permission, xóa dữ liệu site, reset browser, thay đổi push service hoặc các điều kiện khác. expirationTime có thể là null; không dùng trường này làm cơ chế duy nhất để phát hiện subscription hết hạn.

Một số browser có hỗ trợ sự kiện pushsubscriptionchange, nhưng mức hỗ trợ và khả năng tự khôi phục subscription khác nhau. Ứng dụng nên:

- Kiểm tra getSubscription() khi người dùng quay lại hoặc vào màn hình cài đặt.
- Đồng bộ subscription hiện tại với server khi user đã đăng nhập.
- Xử lý push send trả 404/410 bằng cách đánh dấu subscription không còn hợp lệ và xóa/unlink.
- Dùng backoff cho lỗi tạm thời như 429 hoặc 5xx.
- Có thể yêu cầu người dùng bật lại khi permission hoặc subscription không còn.
- Không gửi prompt liên tục chỉ vì một lần gửi push thất bại.

Không giả định subscription luôn được giữ qua lần cài lại browser hoặc thiết bị. Server cần trạng thái lifecycle rõ ràng.

## 23. Xử lý lỗi khi gửi push

Phân loại phản hồi từ push service:

| Kết quả | Diễn giải thường gặp | Hướng xử lý |
| --- | --- | --- |
| Thành công | Push service đã chấp nhận thông điệp | Không đồng nghĩa notification chắc chắn đã hiển thị |
| 404 hoặc 410 | Subscription endpoint không còn hợp lệ | Xóa hoặc đánh dấu subscription stale |
| 401 hoặc 403 | VAPID/authentication hoặc cấu hình gửi có vấn đề | Kiểm tra key, audience, subject và cấu hình |
| 413 | Payload vượt giới hạn dịch vụ | Giảm kích thước payload |
| 429 | Bị rate limit | Retry với exponential backoff và jitter |
| 5xx hoặc network timeout | Push service tạm thời lỗi | Retry có giới hạn, giữ idempotency |

Không retry vô hạn và không retry 404/410 như lỗi mạng thông thường. Ghi nhận mã lỗi, provider và subscription ID nội bộ; không log endpoint đầy đủ hoặc key material.

## 24. Bảo vệ endpoint subscription khỏi CSRF và lạm dụng

Nếu API đăng ký subscription dùng session cookie, request POST vẫn có thể bị CSRF. Bảo vệ endpoint bằng CSRF token, kiểm tra Origin/Fetch Metadata và xác thực session. Chỉ cho user đã đăng nhập hoặc đã qua quy trình opt-in phù hợp đăng ký subscription.

Server cần:

- Không tin userId trong request body; lấy user từ session đã xác thực.
- Rate limit tạo/xóa subscription.
- Giới hạn kích thước body và validate schema.
- Kiểm tra endpoint là HTTPS URL hợp lệ và áp dụng chính sách outbound phù hợp.
- Không cho phép client yêu cầu server gửi push tới URL tùy ý.
- Kiểm soát quyền truy cập và xóa subscription theo owner.
- Chống duplicate record và account-switch leakage.

Subscription endpoint do client gửi lên có thể bị giả mạo. Khi server gửi tới endpoint đó, nó tạo request outbound; nếu không kiểm tra, API có thể trở thành SSRF primitive. Hãy xác thực scheme/host theo danh sách push service được hỗ trợ, dùng egress firewall hoặc outbound proxy có policy, chặn địa chỉ loopback/private/link-local và không theo redirect tùy tiện. Danh sách host phải được duy trì theo browser/provider mà sản phẩm hỗ trợ.

## 25. Bảo vệ VAPID key và dữ liệu subscription

VAPID private key là secret của application server. Subscription endpoint cùng p256dh/auth key material là dữ liệu nhạy cảm cần giới hạn quyền truy cập.

Các biện pháp:

- Lưu private key trong secret manager; không commit vào source.
- Chỉ push worker/service được phép đọc key.
- Mã hóa database backup và giới hạn quyền đọc subscription.
- Redact endpoint và key material khỏi log, trace, analytics.
- Tách dữ liệu theo môi trường và tenant.
- Có audit log cho việc thêm, xóa, chuyển owner subscription.
- Rotate key theo kế hoạch đã kiểm thử và có quy trình đăng ký lại.

Không coi public VAPID key là secret. Tuy nhiên, không cần đưa thêm metadata nội bộ, subscription endpoint hoặc user mapping vào frontend.

## 26. Quyền riêng tư và nội dung notification

Notification có thể hiện trên màn hình khóa, màn hình desktop chia sẻ hoặc thiết bị đang được người khác sử dụng. Payload được mã hóa trong quá trình Web Push nhưng nội dung hiển thị sau khi browser giải mã vẫn có thể bị người xung quanh nhìn thấy.

Thiết kế privacy-first:

- Dùng nội dung chung như “Bạn có cập nhật mới” thay vì hiển thị chi tiết nhạy cảm.
- Không gửi password reset token, OTP, access token hoặc refresh token trong payload.
- Chỉ gửi eventId hoặc loại sự kiện tối thiểu.
- Tải nội dung thật sau khi user mở ứng dụng và server xác minh quyền.
- Cho phép tắt từng nhóm notification và tắt toàn bộ.
- Tôn trọng quiet hours, tần suất và tùy chọn người dùng.
- Không dùng push để theo dõi vị trí hoặc hoạt động không được người dùng mong đợi.

Push delivery metadata như thời điểm, kích thước và endpoint vẫn có thể tiết lộ một phần hoạt động. Chỉ gửi khi cần và giảm metadata không cần thiết.

## 27. Notification không phải nguồn sự thật

Push có thể bị trễ, mất, trùng hoặc đến sau khi trạng thái nghiệp vụ đã thay đổi. Ví dụ, một đơn hàng có thể đã được hủy trước khi notification “đơn hàng sẵn sàng” đến thiết bị.

Vì vậy:

- Payload nên mang eventId hoặc tín hiệu đồng bộ nhỏ.
- Khi app mở, tải trạng thái mới nhất từ API.
- Server kiểm tra quyền user tại thời điểm đọc dữ liệu.
- Xử lý event idempotent và không áp dụng side effect nhạy cảm chỉ từ notification.
- Dùng API hoặc hàng đợi server-side làm nguồn dữ liệu chuẩn.

Không dùng push để thay thế job queue có bảo đảm giao nhận, audit hoặc workflow cần exactly-once. Nếu nghiệp vụ cần bảo đảm xử lý, phải có cơ chế server-side riêng và push chỉ là thông báo đánh thức/gợi ý.

## 28. Tích hợp với PWA lifecycle

Push notification thường đi cùng manifest và Service Worker của PWA, nhưng Web Push không chỉ dành cho một kiểu giao diện đã cài đặt. Điều kiện hỗ trợ phụ thuộc browser và nền tảng.

Khi cập nhật Service Worker:

- Giữ push handler tương thích với payload version cũ trong thời gian chuyển tiếp.
- Không xóa cache/icon đang được notification cũ tham chiếu quá sớm.
- Đảm bảo file icon và route notification tồn tại sau deployment.
- Kiểm thử worker update, activation và tab đang mở.
- Nếu thay đổi schema payload, dùng version field và fallback an toàn.

Ví dụ payload version:

~~~json
{
  "version": 1,
  "type": "INBOX_UPDATE",
  "eventId": "evt_123"
}
~~~

Service Worker nên kiểm tra version và xử lý loại sự kiện đã biết; payload không hợp lệ nên chuyển sang thông báo chung hoặc bỏ qua theo policy, không làm worker crash.

## 29. Push và Notification API trong iframe

Không nên thiết kế trải nghiệm push dựa trên giả định iframe bên thứ ba có thể xin permission và đăng ký subscription giống top-level PWA. Browser có thể hạn chế permission request trong embedded context và yêu cầu top-level interaction.

Nếu sản phẩm có widget nhúng:

- Để top-level application quản lý opt-in và permission.
- Không delegate notification permission một cách tùy tiện cho frame.
- Không gửi VAPID private key hoặc subscription của parent vào iframe.
- Dùng postMessage có kiểm tra exact origin và schema nếu frame cần báo sự kiện cho parent.
- Parent quyết định có đăng ký push và hiển thị notification hay không.

Feature policy và browser permission có thể thay đổi theo nền tảng; kiểm thử trên browser mục tiêu. Không dùng iframe để né prompt hoặc ép người dùng cấp quyền.

Trong DevTools, kiểm tra:

2. Application → Manifest: manifest và các icon cần cho notification.
3. Application/Storage: site data và trạng thái cache.

| Không bảo vệ endpoint đăng ký bằng CSRF | Attacker có thể thao túng subscription của phiên | CSRF token, Origin và rate limit |
| Tin payload là dữ liệu có thẩm quyền | Notification cũ/sai có thể gây hành động sai | Tải trạng thái mới từ API và authorize server-side |
| Đưa PII/OTP vào notification | Lộ dữ liệu trên lock screen | Payload tối thiểu, nội dung chung |
| Mở URL tùy ý từ payload | Open redirect/phishing | Dùng route same-origin allowlist |
| Retry vô hạn | Tốn tài nguyên và bị provider rate limit | Backoff, jitter và giới hạn retry |
| Bỏ subscription khi đổi tài khoản không đúng | Rò notification giữa các user trên thiết bị chung | Unlink owner trước khi gắn user mới |
| Tin HTTP 2xx nghĩa là notification đã hiển thị | Đánh giá sai độ tin cậy delivery | Theo dõi trạng thái nghiệp vụ độc lập |
| Không kiểm tra endpoint do client gửi | API gửi push có thể thành SSRF | Validate URL, egress control và allowlist provider |

## 38. Checklist review Push notification

- [ ] Chỉ yêu cầu permission sau khi giải thích và người dùng chủ động bấm.
- [ ] Có fallback khi browser/platform không hỗ trợ Push API hoặc Notifications API.
- [ ] Service Worker chạy trên secure context, scope và lifecycle được kiểm soát.
- [ ] PushSubscription dùng VAPID public key đúng môi trường.
- [ ] VAPID private key nằm trong secret manager và không xuất hiện ở client/log.
- [ ] Subscription được gửi qua HTTPS và endpoint API có authentication/CSRF protection.
- [ ] Server lấy user identity từ session, không tin userId trong body.
- [ ] Endpoint và key material được bảo vệ ở database và telemetry.
- [ ] Server kiểm tra URL subscription và chống SSRF khi gửi outbound.
- [ ] Payload được mã hóa bằng thư viện Web Push chuẩn.
- [ ] Payload tối thiểu, không chứa token/OTP/PII nhạy cảm.
- [ ] Push event được xử lý bằng event.waitUntil() và validate schema.
- [ ] Notification title/body không làm lộ dữ liệu trên màn hình khóa.
- [ ] notificationclick chỉ điều hướng tới route same-origin đã kiểm soát.
- [ ] API tải dữ liệu khi mở notification kiểm tra authorization lại.
- [ ] TTL/urgency/topic được chọn theo giá trị nghiệp vụ.
- [ ] Có retry backoff và cleanup 404/410.
- [ ] Có unsubscribe, logout cleanup và account-switch handling.
- [ ] Đã kiểm thử permission revoke, site data clear và subscription stale.
- [ ] Có browser/platform matrix và giám sát lỗi sau triển khai.

## 40. Ghi nhớ

Push notification kết hợp permission của người dùng, Service Worker, Push API, PushSubscription, VAPID và Notifications API. Browser cấp subscription gồm endpoint cùng key material; application server lưu subscription theo tài khoản/thiết bị, mã hóa payload theo Web Push protocol và gửi qua push service. Service Worker nhận push event và hiển thị notification khi browser cho phép.

Xin quyền đúng lúc, bảo vệ VAPID private key và subscription endpoint, xác thực/CSRF-protect API đăng ký, chống SSRF khi gửi outbound, giữ payload tối thiểu và điều hướng click tới route same-origin. Subscription có thể hết hạn, permission có thể bị thu hồi và delivery không được bảo đảm exactly-once. **Push chỉ báo hiệu có sự kiện; server vẫn là nguồn dữ liệu có thẩm quyền và phải kiểm tra quyền khi người dùng mở nội dung.**
