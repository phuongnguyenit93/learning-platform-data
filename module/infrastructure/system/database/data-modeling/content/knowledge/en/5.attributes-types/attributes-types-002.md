# Base Attributes, Derived Attributes, and Aggregate Results

When modeling data, it is necessary to distinguish between information recorded directly, information calculated from other data, and information summarized across multiple records. These three groups are closely related yet have different origins, update rules, and verification methods. Confusing them can cause the system to store duplicate data, compute incorrect figures, lose lineage back to the source, or display inconsistent results across screens and reports.

Within the scope of **DATABASE_DATA_MODELING**, attribute classification is part of transforming business requirements into a clear data model. Designers must determine where each value comes from, who is responsible for it, what rules calculate it, whether it changes over time, and whether the result needs to be stored at the time the business event occurs. These decisions affect entities, relationships, constraints, normalization, and choices across relational, document, graph, or analytical storage structures.

After this lesson, learners can:

- Distinguish base attributes, derived attributes, and aggregate results.
- Identify the source of truth, owner, recording timestamp, and update rules for each attribute.
- Describe derivation formulas and identify the input data needed to verify results.
- Distinguish calculations on a single object from aggregations over a set of records.
- Handle missing values, units of measurement, currencies, rounding, and time-varying data.
- Decide when to compute on query, store the result, use a snapshot, or build aggregated data.
- Detect risks of duplicate storage, out-of-sync updates, and discrepancies between detailed data and aggregated figures.

## 1. Three groups of information in a data model

### 1.1. Base attributes

A **base/source attribute** is a value recorded directly from an event, user, device, document, or authoritative system. Its value is not computed from other business attributes in the model under consideration.

Examples:

- `order_placed_at`: timestamp when the order was received.
- `quantity`: quantity of product ordered by the customer.
- `unit_price_at_order`: unit price locked in for the order line.
- `payment_received_at`: timestamp when the system received payment confirmation.
- `birth_date`: date of birth provided by the user or verified from an authoritative source.
- `temperature_celsius`: direct measurement from a sensor.

A base attribute can be entered manually, received via API, read from a device, or generated by the system according to its own rule. For example, a system-generated order code is not an aggregate result of order lines; it is an identifying value assigned at creation time. “Base” refers to the origin of the value in the model, not that the value is always immutable, always accurate, or necessarily entered by a human.

A base attribute can still be modified. A contact phone number can change; a current address can be updated; an ordered quantity can be adjusted before a business cutoff. When edits are allowed, you must specify who can edit, under what conditions, when it takes effect, and whether the previous value must be retained.

### 1.2. Derived attributes

A **derived attribute** is a value determined by a formula or rule from one or more other values. It does not need to be entered as an independent event because it can be recomputed from source data and defined rules.

Examples:

- `line_subtotal = quantity × unit_price_at_order`.
- `age = current date − birth_date` according to the age-calculation rule.
- `duration_minutes = end_time − start_time`.
- `is_overdue = due_date < check timestamp` and the payable amount has not been paid in full.
- `full_name = given_name + family_name` according to name formatting rules.

A derived attribute depends on input data and rules. If an input changes, the result may change. If the rule changes, the same set of inputs may yield a different result. Therefore, you should document the formula, scope of application, rule version, and calculation timestamp if the result is stored.

Not every value that looks like a calculation result should be derived. For example, the actual selling price locked on an order may originate from a price list, promotions, taxes, and a salesperson's decision. Once the transaction is confirmed, that price is an occurred event and must be kept as base transaction data. Recalculating it from the current price list can distort history.

### 1.3. Aggregate results

An **aggregate result** is a value computed from multiple records or multiple objects according to a defined scope and aggregation function. It typically answers questions about totals, counts, averages, minimum/maximum values, or a metric by group.

Examples:

- Daily total revenue: sum of eligible transaction values within the day.
- Order count by status: count of orders in each status at a point in time.
- Total shipped quantity by product: sum of shipped quantities across shipment lines.
- Average grade of a course: computed from valid grades according to grading rules.
- Inventory balance: inbound quantity minus outbound quantity, adjustments, and movements accounted for.

An aggregate result is a type of derived value, but it has an important characteristic: it depends on a set of records, filter conditions, grouping, and data cutoff timestamp. The same `SUM` operation can produce different results if the time range, transaction statuses, or exclusion rules change.

### 1.4. Quick comparison

| Criterion | Base attribute | Derived attribute | Aggregate result |
|---|---|---|---|
| Source | Recorded directly from an authoritative source | Formula/rule from input data | Set of records by scope and grouping |
| Computation scope | A single value or event | Usually one object or relationship | Multiple records or multiple objects |
| Example | Ordered quantity, payment timestamp | Line amount | Monthly revenue |
| When inputs change | Base value is updated per business process | May need recalculation | May need re-aggregation |
| Need to store formula? | Need source definition and recording rules | Yes | Yes, including filter and grouping criteria |
| Main risks | Wrong source, bad input, lost history | Inconsistent or outdated formulas | Wrong aggregation scope, late data, or double counting |

## 2. Identifying the source of truth for base attributes

An attribute only has meaning when we know what it describes and who has authority to confirm its value. The same concept may appear in multiple systems, but not every system is the official source.

For example, a customer name may appear in CRM, the sales system, invoicing, and the support platform. You must determine which system manages the customer profile, which only stores a snapshot for transactions, and which receives synchronized data. Without clarifying this, teams may update the same attribute in multiple places and create conflicting values.

### 2.1. Questions to describe a base attribute

- From which action or event is the value created?
- Who or which system provides the value?
- Which system is the authoritative source?
- At what moment is the value recorded: when the event occurs or when the system receives the data?
- Are edits allowed? Who can edit and under what conditions?
- When edited, must the old value, reason, and actor be stored?
- Must the value be unique or reference a lookup catalog?
- If the source does not send a value, does that mean not applicable, unknown, or a transmission error?

### 2.2. Example attribute profiles

| Attribute | Origin | Owner | Update rule |
|---|---|---|---|
| `order_placed_at` | Order intake event | Order service | Recorded when the order is created per business definition; unchanged on order edits. |
| `quantity_ordered` | Customer order or staff entry | Order service | Editable before cutoff; afterward adjusted via audited business process. |
| `unit_price_at_order` | Price and policy at confirmation time | Sales service | Locked per transaction; not automatically recalculated from current price list. |
| `payment_confirmed_at` | Confirmation from payment gateway or cashier | Payment service | Recorded from confirming source; may distinguish partner time vs. receipt time. |
| `customer_current_address` | Customer profile | CRM or designated profile system | Updated via profile management workflow. |

The system names in the table are examples. In a real project, identify the exact sources according to your organization's architecture and data ownership.

### 2.3. Do not equate “base” with “trustworthy”

A directly entered value can still be wrong. For example, staff may mistype a quantity, a sensor may mismeasure, or an external system may send duplicate data. Thus, base attributes still require format checks, value domain validation, update permissions, source verification, and discrepancy handling.

Distinguish three questions:

1. **Origin:** where did the value come from?
2. **Validity:** does the value satisfy the rules?
3. **Authority:** does that source have authority to determine the official value?

Data can come from a clear origin yet be invalid; or be valid in format yet not come from the official source.

## 3. Identifying derived attributes and specifying formulas

### 3.1. Start from the business question

Do not start by seeing a calculation in a report and immediately adding a corresponding column. Determine what the user needs to know and what decision the result supports.

For example, the question “How much is still receivable on the order?” requires specifying:

- Which components make up the total amount due?
- By what rules are discounts and taxes calculated?
- Which successful payments are subtracted?
- Do refunds change the collected amount or are they tracked separately?
- Are shipping fees, service fees, or manual adjustments included?
- Is the result viewed as of the current time or at order confirmation time?

Only after clarifying the meaning should you define the formula. The same label “balance due” can mean the amount payable before delivery, the uncollected amount at the current time, or the remaining amount after refunds.

### 3.2. Writing verifiable formula specifications

A good definition should state:

- Name and business meaning of the result.
- Input attributes and their sources.
- Formula or calculation rule.
- Unit of measurement, currency, and rounding rules.
- Handling of missing or invalid values.
- Applicability conditions and exceptions.
- Calculation timestamp or effective timestamp of the result.
- Rule version if the formula may change.

Example:

```text
Name: line_net_amount
Meaning: Net amount of an order line at transaction confirmation time.
Inputs: quantity_ordered, unit_price_at_order, line_discount_amount.
Formula: quantity_ordered * unit_price_at_order - line_discount_amount.
Unit: currency of the order.
Rounding: per confirmed currency rules and sales policy.
Timing: computed when the order line is finalized; store transaction result if history must be preserved.
```

Do not leave formulas solely in source code or in a developer's head. When rules affect money, entitlements, inventory, or reporting, there must be a business definition confirmed by the owner.

### 3.3. Distinguishing stable vs. time-dependent derived attributes

Some derived attributes depend only on finalized data, such as order line net amount from confirmed quantity and unit price. Others depend on query time, such as current age, days overdue, or active status.

| Type | Example | Key consideration |
|---|---|---|
| Derived from finalized transaction data | Line net amount | Result must preserve the exact meaning at transaction time. |
| Derived from current data | Display full name combined from first and last name | Changing inputs changes the displayed result. |
| Time-dependent derivation | Age, days remaining, active contract | The same base data can yield different results depending on the check date. |
| Rule-version-dependent derivation | Customer tier classification by spending threshold | Need to know which threshold applied at which time. |

For example, age should not be stored as a fixed number if the goal is to display current age. You can store date of birth as a base attribute and compute age at display time. If the business needs a person's age on the contract signing date, that result must be tied to the signing date and the calculation rule in effect at that time.

## 4. Aggregate results: calculations across multiple records

### 4.1. Distinguishing single-object calculations from set aggregations

`line_net_amount` is calculated on one order line. `order_total` can be the sum of lines for one order. `monthly_revenue` is an aggregation of revenue across many transactions in a month. All three results may be monetary amounts, yet their data scopes differ.

| Result | Scope | Illustrative calculation |
|---|---|---|
| Line net amount | One order line | Quantity × unit price − line discount |
| Order merchandise total | Lines of one order | Sum of line net amounts |
| Daily order count | Eligible orders on the day | Count of orders by business date |
| Monthly revenue | Eligible transactions in the month | Sum of revenue values per definition |
| Refund rate | Group of transactions within defined scope | Total refunds / total eligible collected payments |

An aggregate result always requires a clear scope. “May revenue” must specify which timezone defines the month, which dates are included, which statuses are counted, whether refunds are subtracted, and whether revenue is recognized by order date, delivery date, or payment date.

### 4.2. Common aggregation functions

| Aggregation | Meaning | Example | Notes |
|---|---|---|---|
| `COUNT` | Count records or values | Order count, customers with email | Distinguish counting all rows vs. counting non-null values. |
| `SUM` | Add values together | Total shipped quantity | Must define filter criteria and units. |
| `AVG` | Compute average | Average score | Simple average differs from weighted average. |
| `MIN` / `MAX` | Minimum/maximum value | Earliest delivery date | Specify whether missing values are ignored. |
| `COUNT DISTINCT` | Count distinct objects | Unique customers | Need clear customer identity definition and scope. |
| Ratio | Compare two quantities | Cancellation rate over total orders | Numerator and denominator must share a compatible scope. |
| Percentile | Distribution threshold | 95th percentile processing time | Not synonymous with average. |

### 4.3. Grouping data before aggregation

Aggregate results are often grouped by one or more dimensions such as date, product, branch, sales channel, or status. Each dimension must be clearly defined:

- Where does the grouping value come from?
- Group by creation time, recognition time, or completion time?
- Can categories be renamed or hierarchically structured?
- Can one record belong to multiple groups?
- Into which group are records without a dimension value placed?

For example, revenue by branch can be grouped by selling branch, fulfilling warehouse branch, or revenue-recognizing branch. If an order is sold at store A but shipped from warehouse B, determine which dimension matches the reporting question.

### 4.4. Aggregate results are not always simple arithmetic sums

Some metrics require special formulas:

- **Conversion rate:** completed orders divided by eligible visits or sessions, not the average of daily rates if the rule requires a period-wide rate.
- **Average order value:** total revenue divided by the number of in-scope orders, not the sum of averages across all order lines.
- **Inventory:** inbound quantity minus outbound quantity, plus/minus adjustments and held stock statuses per rules.
- **Average grade:** may require weighting by credits, question count, or evaluation coefficients.

Write formulas in terms of numerator, denominator, filter conditions, and scope. A metric name does not replace its definition.

## 5. End-to-end example: orders, payments, and shipments

Suppose an order has multiple lines. Each line stores quantity, locked unit price, and line discount. An order may have shipping fees, taxes, and an order-level discount. A customer may pay in multiple installments; an order may be shipped in multiple batches and partially refunded.

### 5.1. Attribute classification

| Attribute | Group | Rationale |
|---|---|---|
| `order_placed_at` | Base | Records the timestamp when the order was received. |
| `quantity_ordered` | Base | Quantity requested by the customer at intake time. |
| `unit_price_at_order` | Transaction base | Price locked from policy at confirmation time. |
| `line_discount_amount` | Base or locked result | May be determined by promotion rules; must store the amount applied to the transaction. |
| `line_net_amount` | Derived | Computed from quantity, unit price, and line discount. |
| `order_merchandise_total` | Aggregate | Sum of net amounts of lines in the order. |
| `payment_received_total` | Aggregate | Sum of successful payment transactions in scope. |
| `refund_total` | Aggregate | Sum of successful refund transactions. |
| `outstanding_amount` | Derived/aggregate | Computed per receivable rules minus collected payments and relevant adjustments. |
| `shipped_quantity` | Aggregate | Total quantity recorded in valid shipments. |
| `is_fully_shipped` | Derived | Compares shipped quantity with required quantity per rules. |

Some cases depend on design and policy. For example, `line_discount_amount` may be calculated from a promotion percentage, yet the actual applied amount locked into the transaction should be kept as applied data. `outstanding_amount` can change with payment and refund statuses; clarify whether it is the current balance or the balance at a cutoff point.

### 5.2. Illustrative formulas and rules

```text
line_net_amount
    = quantity_ordered * unit_price_at_order
      - line_discount_amount

order_merchandise_total
    = SUM(line_net_amount of the lines belonging to the order)

payment_received_total
    = SUM(amount of successful payment collection transactions)

refund_total
    = SUM(amount of successful refund transactions)

net_cash_received
    = payment_received_total - refund_total
```

Do not automatically equate `order_merchandise_total`, `net_cash_received`, and `outstanding_amount`. Merchandise total may exclude tax or shipping; cash received may include deposits; outstanding balance may need to account for discounts, fees, adjustments, and refund obligations. Each quantity must have its own business definition.

### 5.3. Illustrative SQL for derived and aggregate attributes

Computing each line's net amount:

```sql
SELECT
    order_id,
    order_line_id,
    quantity_ordered,
    unit_price_at_order,
    line_discount_amount,
    quantity_ordered * unit_price_at_order
        - line_discount_amount AS line_net_amount
FROM order_lines;
```

Computing merchandise total per order:

```sql
SELECT
    order_id,
    SUM(quantity_ordered * unit_price_at_order
        - line_discount_amount) AS order_merchandise_total
FROM order_lines
GROUP BY order_id;
```

Computing shipped quantity per order line:

```sql
SELECT
    order_line_id,
    SUM(shipped_quantity) AS shipped_quantity
FROM shipment_lines
WHERE shipment_status IN ('DISPATCHED', 'DELIVERED')
GROUP BY order_line_id;
```

These queries are examples only. In a real system, explicitly define which statuses count, how failed deliveries or returns are handled, and whether `DISPATCHED` counts as shipped per business definition. Do not copy illustrative filters if your organization's rules differ.

### 5.4. Change scenarios and impact on results

If order quantity is adjusted before confirmation, `line_net_amount` and merchandise total may need recalculation. Once the order is confirmed, quantity changes may need to be recorded as adjustments or partial cancellations to preserve history. When a shipment is returned, net delivered quantity can differ from total quantity ever handed over. When a refund succeeds, total refunded amount increases, while the original payment amount is not overwritten.

These scenarios show that base attributes, derived attributes, and aggregates must be connected through temporal rules. You cannot look only at mathematical formulas while ignoring business events.

## 6. Missing values, zero, and calculation validity

### 6.1. Do not equate NULL with 0

`NULL` usually indicates unknown, not provided, or not applicable depending on context. The number `0` is a specific value. For example:

- `discount_amount = 0`: confirmed there is no discount.
- `discount_amount = NULL`: discount is unknown or not yet computed.
- `shipped_quantity = 0`: confirmed no quantity has been shipped yet.
- `shipped_quantity = NULL`: shipping data has not been recorded or does not apply.

If both cases are conflated, reports may misinterpret incomplete data as a zero result. Define the semantics of missing values for each attribute.

### 6.2. Defining handling for missing inputs

For every formula, ask:

- If an input is missing, is the result undefined, not applicable, or computable from remaining data?
- Can a missing value be replaced with 0? What is the business justification?
- If the denominator is 0, how should a ratio metric be displayed?
- Are ineligible records excluded from the aggregate set or placed in a separate group?
- Should a data quality issue be flagged instead of returning a seemingly valid number?

For example, refund rate when there are no payment collections in the period should not automatically show 0% if the denominator is 0. The result may be “undefined” or “not applicable” depending on reporting goals.

### 6.3. Units of measurement, currencies, and precision

Do not add values with different units or currencies without a conversion rule. Adding 10 kg and 5 g requires converting to a common unit. Adding 100 USD and 100 VND is meaningless without specifying the exchange rate and effective timestamp.

For currency, clarify:

- Transaction currency and reporting currency.
- Number of decimal places allowed.
- Timestamp and source of exchange rates if converting.
- Whether rounding occurs at line level, invoice level, or total level.
- How rounding differences are handled.

For example, rounding each line before summing can yield a different result than summing exact numbers and rounding once. Rules must be consistent and confirmed.

## 7. Time, rule versions, and reproducibility

### 7.1. Which point in time does a derived result depend on?

A derived attribute can depend on:

- Timestamp when the base event occurred.
- Timestamp when the system recorded the event.
- Query or display timestamp.
- Reporting period cutoff timestamp.
- Applied version of the calculation rule.

For example, the status “active contract” is calculated from start date, end date, and check date. The same contract may be active today but inactive next month. If a historical report needs to know whether the contract was active on June 15, it must compute against that date rather than using the current status.

### 7.2. Rules changing over time

Customer segmentation thresholds, discount policies, scoring formulas, or tax rules can change. If you only store input data without knowing the rule version, historical recalculation may yield results different from what was accepted at the time.

Determine:

- Does the rule have an effective date?
- Must the rule ID or version be stored?
- Are old results preserved or recalculated when rules change?
- Should historical reports reflect the rule at occurrence time or the current rule?
- Who approves formula changes?

A common solution is to store base data, rule version, and finalized results for critical transactions. For reproducible analytical metrics, the system can recompute from detailed data provided the logic version and data scope are known.

### 7.3. Snapshots and current data

A **snapshot** is a record of a value at a specific point in time. Snapshots are useful when the business needs to preserve what was agreed upon, such as selling price, shipping address, tax rate, or contract terms at signing time.

Taking a snapshot does not mean copying every attribute of an object into every transaction. Store only the values needed to explain, reconcile, or fulfill obligations. Identify the purpose and source of each snapshot value.

| Data | Current value | Transaction snapshot |
|---|---|---|
| Customer address | Address currently used in customer profile | Address confirmed for the order at placement time |
| Product price | Currently listed price | Price locked in on the order line |
| Tax rate | Currently effective tax rate | Tax rate used to calculate the occurred transaction |
| Product name | Current display name | Product name or description on the document if retention is needed |

## 8. Deciding between computing on query and storing results

A derived attribute can be computed on demand or pre-stored. There is no single right choice for every case. The decision depends on computation cost, query frequency, freshness requirements, reproducibility, and criticality of the result.

### 8.1. Compute on query (on-demand)

The system computes the value from source data on every read.

Advantages:

- Avoids storing copies that can become stale.
- The formula and source data remain the single place determining the result.
- When source data changes, subsequent queries reflect the new value under current rules.

Limitations:

- Queries can be expensive on large datasets.
- Complex formulas may be duplicated across multiple queries.
- Results across reads can differ if source data changes.

Suitable for fast calculations, infrequently accessed values, or results that must always reflect current data.

### 8.2. Store derived value

The system stores the result alongside the object or transaction.

Advantages:

- Fast to read and easy to display.
- Preserves finalized results at the time of the business event.
- Convenient for documents or workflows needing stable outputs.

Limitations:

- Risk of drifting from input data if updates are not synchronized.
- Increases data duplication and maintenance rules.
- Requires defining when to recalculate and when not to recalculate.

Suitable for finalized transaction values or results used as business evidence.

### 8.3. Store aggregate results or materialized views

Aggregate results can be precomputed and stored in summary tables, materialized views, or analytics-ready datasets. This reduces query cost when record counts are large, but requires managing latency and refresh processes.

Determine:

- Refresh per event, on a schedule, or in batches?
- What is the maximum acceptable data staleness?
- When late events arrive or past data is corrected, are prior periods recomputed?
- Can aggregated figures be reconciled back to detailed data?
- Who is responsible when aggregated figures diverge?

### 8.4. Selection matrix

| Criterion | Compute on query | Store derived result | Store aggregate result |
|---|---|---|---|
| Freshness | Usually fresh as of query snapshot | Depends on update mechanism | Depends on refresh schedule |
| Read speed | Can be slow for complex calculations | Fast | Fast for predefined aggregate queries |
| Write cost | Lower | Higher due to updating the result | Incurs sync/refresh cost |
| Drift risk | Low if source and formula are consistent | Present if not updated properly | Present if aggregates are stale or scope is wrong |
| Best suited for | Flexible, infrequently used results | Finalized values needing fast reads | Large reports, dashboards, dimensional analytics |

Do not store a derived attribute merely because adding a column is easy. State the business or performance reason, synchronization rules, and verification method before storing it.

## 9. Relationship to normalization and storage models

### 9.1. Relational model

In a relational model, base attributes are usually stored in the table owning the data. Derived attributes can be computed in queries or stored intentionally. Aggregate results can be produced via `GROUP BY`, views, materialized views, or summary tables.

Normalization helps reduce duplicate storage of data determinable from another relationship. For example, do not repeat the customer's name on every order line if you only need to reference the customer profile for current information. However, finalized historical values like name or address on a document may require a snapshot because their business meaning differs from the current profile.

The key is distinguishing unnecessary duplicate data from intentional snapshot data. Both may look like copies, but their purpose and update rules differ.

### 9.2. Document model

A document can store an object together with its child components in one document. For example, an order has an array of line items and finalized total values. This is convenient when reading the whole order together. However, if the total is a derived value from the lines, clarify how the total is updated when lines are added, modified, or deleted.

Do not embed aggregate results into a document without a clear source and refresh rule. If line items have independent lifecycles or queries, consider splitting collections or storing references.

### 9.3. Graph model

In a graph model, relationships between entities are central. Base attributes can live on nodes or edges; some metrics are derived from paths or connectivity structures. For example, the number of relationships between customers and products can be used for recommendations, but that result depends on data scope and computation time.

If aggregate results are stored on nodes or edges, specify how metrics are updated when relationships are added or removed. Network-wide metrics can be expensive to recompute and require an appropriate update strategy.

### 9.4. Analytical model

In a data warehouse, base attributes from operational systems are typically brought into fact and dimension tables. Aggregations are computed by time, product, region, channel, or customer segment. Keep metric definitions consistent across dashboards and reports.

For example, “revenue” might be calculated by order date, payment date, or delivery date. If each report chooses its own interpretation, the same metric name will produce different numbers. A metric dictionary must document the formula, filters, time dimension, timezone, and refund/cancellation rules.

## 10. Quality control and result verification

### 10.1. Testing formulas with sample data

For each derived attribute, create a test set containing:

- Normal values.
- Minimum/maximum boundary values.
- Missing values.
- Zero or negative values if they can occur.
- Data changing after the result was calculated.
- Cases with rule versions or exceptions.

Calculate results manually for a few samples and compare against queries or implementation logic. For aggregate results, pick a small set of records so you can inspect every row included or excluded.

### 10.2. Reconciling detailed data and aggregates

An aggregate result needs a way to reconcile back to its source. For example, daily total revenue must trace back to the transactions forming that number. When discrepancies arise, the team needs to determine:

- Which records were included in the aggregation?
- Which records were excluded and why?
- Which filters or statuses were applied?
- Did data arrive late or get updated after cutoff?
- Which calculation rule or formula version was used?

Do not compare only the grand total. Check record counts, subtotals by small groups, and exception cases.

### 10.3. Checking consistency of stored data

If derived results are stored, there must be rules to detect when they no longer match inputs. You can use periodic reconciliation queries, in-transaction checks, or partial data recomputation. Define acceptable tolerance thresholds, who handles discrepancies, and an audited correction process.

For example, if `order_total` is stored on the order, it can be recomputed from line items and compared. However, you must use the exact discount, tax, fee rules, and cutoff timing. If the reconciliation formula differs from the original formula, comparisons will generate false alerts.

## 11. Common mistakes

| Mistake | Consequence | Fix |
|---|---|---|
| Treating every attribute as direct input | Fails to recognize formulas and input dependencies. | Classify the origin of every value. |
| Treating every calculated value as recomputable | Alters historical transactions when source data changes. | Identify which values must be locked as evidence. |
| Storing derived results in multiple places | Screens or reports can diverge from one another. | Designate one authoritative definition and source. |
| Not documenting formulas and filters | Impossible to explain why numbers differ. | Maintain an attribute and metric dictionary. |
| Adding values with different units or currencies | Totals are meaningless or inaccurate. | Standardize units, currencies, and conversion rules. |
| Arbitrarily replacing NULL with 0 | Missing data is misinterpreted as an actual zero value. | Define clear semantics for missing values. |
| Aggregating by current status for historical reports | Past periods change when current statuses change. | Define business timestamps and snapshot/event data. |
| Updating totals while omitting refunds or returns | Balances and revenue are wrong. | List all event types and inclusion conditions completely. |
| Materializing without a refresh process | Aggregate results go stale. | Set freshness SLAs, refresh mechanisms, and reconciliation. |
| Not storing rule versions | Historical results cannot be reproduced. | Attach versions or effective dates to rules. |

## 14. Practice exercise

A food delivery platform stores orders, menu line items, restaurants, drivers, payments, and deliveries. An order can contain multiple items, receive discounts, and incur delivery fees and taxes. Customers may pay multiple times due to failed transactions, and an order may be partially delivered or partially refunded. Management wants to view daily total revenue, order count by restaurant, average order value, and refund rate.

Complete the following tasks:

1. List at least 15 attributes and classify them as base, derived, or aggregate.
2. Identify the source of truth and owner of the key base attributes.
3. Write formulas for item line amount, order total, collected amount, refunded amount, and remaining balance due.
4. Clearly define daily revenue: recognition timestamp, order statuses, cancellation handling, and refunds.
5. Write SQL queries to calculate merchandise total per order and order count per restaurant.
6. Analyze how to handle NULL, 0, currency, discounts, and rounding.
7. Propose which results should be computed on query, which need snapshots, and which can be materialized for reporting; explain why.
8. Build a reconciliation check between detailed data and aggregate results.

**Self-evaluation criteria:** every value has a clear source and meaning; formulas can be recomputed from defined inputs; aggregate results have explicit scope and filters; historical transaction data is not altered by current price lists; report metrics can trace back to source records and discrepancies can be explained.

## Conclusion

Base attributes record events or values from authoritative sources; derived attributes are computed by rule from input data; aggregate results summarize multiple records within a defined scope. Properly distinguishing these three groups keeps the data model traceable, consistent, and explainable. When formulas, timing, units, rule versions, and reconciliation methods are clearly documented, the team can make sound choices among computing on query, storing transaction results, and materializing aggregate data while keeping results verifiable.
