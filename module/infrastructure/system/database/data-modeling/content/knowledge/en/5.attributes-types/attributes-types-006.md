# Text, Technical Codes, Length, and Unicode Rules

Text data appears in nearly every data model: person names, product names, addresses, descriptions, notes, business codes, and technical identifiers. Although stored alike as strings, these values serve different purposes. Product names need to support natural language; SKU codes must follow a stable character rule; technical keys need to identify records independently of how display names are written.

Applying a single rule to every string type can cause search, comparison, and uniqueness bugs. Accented Vietnamese text can become garbled when passing through systems without full Unicode support. Visually identical strings can be encoded with different Unicode code-point sequences. A 50-character limit can also be misunderstood if the application counts displayed characters while the database limits bytes or code units.

This lesson helps classify text data, separate technical codes from display content, choose appropriate length limits, and design consistent Unicode rules from the application to the database.

**After this lesson, you will be able to:**

- Distinguish free-form text, display labels, business codes, and technical identifiers.
- Explain the differences among byte, code unit, code point, and grapheme cluster.
- Choose appropriate Unicode encoding, normalization, comparison, and validation rules.
- Determine length limits based on business requirements and storage capabilities.
- Design character rules and uniqueness scopes for technical codes.
- Avoid mojibake, broken string truncation, lookalike characters, and inconsistent comparisons.

## 1. Classify text data before choosing a type

Not all strings carry the same meaning. Before choosing data types and limits, determine what the string is used for, who creates it, and how the system needs to compare or search it.

| Value kind | Example | Design characteristics |
|---|---|---|
| Free-form text | Product description, order notes | Unicode support, potentially large length, avoid overly narrow character sets |
| Display name or label | Customer name, product name | May contain accents/diacritics, multiple languages, needs display and search rules |
| Business code | SKU, order code, warehouse code | Defined format and uniqueness scope |
| Technical identifier | UUID, internal code | Used for stable references; independent of display name |
| Classification value | Product category, status | Should use a value domain or governed lookup catalog |
| Structured content | JSON, XML, markup content | Needs its own syntax, versioning, and structural validation rules |

For example, the product name “Cà phê rang xay Đà Lạt” is display text. The SKU “CF-DL-250G” is a rule-bound technical code. Both are strings, yet they should not share the same validation policy.

Ask for each attribute:

- Is it entered freely by users or generated by the system?
- Can the value contain multiple languages or non-ASCII characters?
- Does search need accent-insensitive, case-insensitive, or locale-specific matching?
- Must it be unique, and within what scope?
- Can the value change after creation?
- Must the original spelling be preserved for display, auditing, or reconciliation?

## 2. Unicode: one visible character can consist of multiple code units

Unicode is a standard assigning code points to characters and symbols across many writing systems. Unicode is not synonymous with UTF-8. Unicode defines character sets and code points; UTF-8, UTF-16, and UTF-32 are encoding schemes that map code points into storage units.

To design lengths accurately, distinguish four concepts:

| Concept | Meaning | Usage example |
|---|---|---|
| Byte | 8-bit unit of data | Measuring storage size in UTF-8 encoding |
| Code unit | Basic unit of an encoding | UTF-16 uses 16-bit units; one code point may take two code units |
| Code point | A Unicode code value | A Unicode symbol such as a letter, combining mark, or emoji |
| Grapheme cluster | A unit approximating what a user perceives as a single character | A letter with combining diacritics or a composite emoji can consist of multiple code points |

### 2.1. Example with Vietnamese

The letter “ế” can be represented by a single precomposed code point or by a base letter combined with diacritical marks. Two strings can look identical yet have different code-point sequences.

Consequently, comparing two strings directly by bytes or code points may return different results even when a user sees the exact same character. This is why a Unicode normalization policy must be defined before performing comparisons or applying uniqueness constraints.

### 2.2. Example with emoji and composite characters

A displayed emoji can be built from multiple code points, such as a family symbol or a symbol with a skin-tone modifier. An accented character in some scripts can also consist of a base character and combining marks.

Therefore:

- Counting bytes does not equal counting characters.
- Counting code points does not always equal counting characters visible to the user.
- Truncating a string at an arbitrary byte offset can corrupt a UTF-8 sequence.
- Truncating at a code point can still split a grapheme cluster into unintended fragments.

If a limit is presented to users as “maximum 100 characters”, determine whether the application counts by grapheme clusters or another rule. If the limit is storage capacity, calculate bytes according to the actual encoding.

## 3. Character encoding and display errors

A Unicode string may pass through multiple components:

1. Input UI;
2. Application and string-processing libraries;
3. Database connection driver;
4. Connection encoding configuration;
5. Column type and character set;
6. Export tools, reporting, or integrations.

All components must agree on the same encoding. Setting a column to support Unicode is not enough if the application or connection converts the data incorrectly.

### 3.1. UTF-8 and compatibility

UTF-8 is the dominant Unicode encoding on the web and in modern systems. It uses one to four bytes per code point. ASCII characters have an ASCII-compatible representation, while other characters may require multiple bytes.

When designing, verify:

- Does the database have a character set supporting full Unicode?
- Does the driver send and receive strings in the correct encoding?
- Does the connection have a consistent encoding configuration?
- Do import/export tools preserve data intact?
- Do integrated systems support Vietnamese and non-ASCII characters?

Column type names differ across DBMSs. Some DBMSs provide dedicated Unicode string types, while others configure character sets at the database or column level. Verify the behavior of your specific platform before implementation.

### 3.2. What is mojibake?

Mojibake is text rendered as garbled characters because data is decoded with an encoding that does not match its original encoding.

For example, a Vietnamese string may render as strange characters like “CÃ  phÃª” instead of “Cà phê”. In that case, the data was likely converted improperly at some step in the transmission or storage pipeline.

Do not fix this by manually replacing the garbled characters visible in the UI. Identify where the encoding diverged, inspect raw bytes or source data, and fix it at the source or in the conversion pipeline. If bad data has already been stored, prepare a verified recovery plan and backup before running bulk updates.

## 4. Unicode normalization before comparison

Unicode provides normalization forms to represent equivalent strings in a consistent canonical representation.

Two commonly referenced forms are:

- **NFC:** Canonical Composition, typically combining sequences that can be composed into precomposed canonical forms.
- **NFD:** Canonical Decomposition, splitting certain characters into base characters and combining marks.

There are also NFKC and NFKD, which are compatibility normalization forms. They collapse formal differences that Unicode considers compatible. Thus, they can be useful for certain search or identifier-handling rules, yet should not be applied blindly to source text whose exact spelling must be preserved.

### 4.1. Choosing a normalization form

For many business systems, NFC can be chosen as the standard storage form or comparison form for ordinary text fields. However, this decision must align with the application, integrating systems, and data preservation requirements.

A common strategy:

- Preserve user-submitted text as-is if original content must be retained.
- Generate a normalized form for comparison or search if needed.
- Apply the same rule across all write paths.
- Never arbitrarily normalize content where byte-for-byte identity matters, such as digital signatures or raw payloads.

Do not treat NFC as a substitute for format validation, whitespace handling, or case-insensitive comparison. These are separate policies.

### 4.2. Normalization is not stripping accents

Unicode normalization preserves character semantics per Unicode rules; accent stripping is a transformation for search or approximate matching. For example, “Hòa” and “Hoa” might be considered close in a search feature, yet are not necessarily the same name or the same code.

If accent-insensitive search is needed, build a separate search mechanism. Do not overwrite the original name with an accent-stripped string, as that destroys display information.

### 4.3. Case and comparison rules

Lowercasing, case folding, and case-insensitive comparison are not always identical. Rules depend on language and collation. Certain letters have locale-specific case mappings.

Distinguish:

- **Original value:** string entered by the user or received by the system.
- **Normalized form:** string normalized to a Unicode form.
- **Comparison form:** string or rule used for searching and determining equivalence.
- **Display form:** string returned to the user.

Do not write a naive lowercase function and assume it handles all Unicode cases.

## 5. Collations and string comparison

A collation defines how strings are compared and sorted according to a rule set. It determines whether comparisons are sensitive to case, accents, language rules, or specific character differences.

For example, two strings may be treated as equal in a case-insensitive collation, yet distinct in a case-sensitive collation. An accent-insensitive collation may treat certain accented and unaccented letters as equivalent when searching.

No single collation suits every column. Person names, place names, product codes, and technical keys have different requirements.

| Attribute kind | Comparison rules typically considered |
|---|---|
| Display name | May need case-insensitive search; accent stripping depends on feature |
| Description | Natural-language search, potentially using full-text search |
| Technical code | Exact comparison per published character set and casing rules |
| Opaque identifier | Comparison against canonical representation of the identifier |
| Status or category | Comparison against canonical value set, avoiding free-form spelling variants |

A column with an inappropriate collation can cause a UNIQUE constraint to reject two distinct codes or accept two values the business considers duplicates. Test collation behavior alongside unique constraints, indexes, and real queries.

## 6. Designing technical codes separately from display text

A technical code is a value used for identification or exchange between systems. It needs to be stable, easy to validate, and governed by clear rules. Display text serves humans and can vary in language or phrasing.

Example:

| Attribute | Illustrative value | Purpose |
|---|---|---|
| product_id | A UUID or internal ID | Stable technical identifier |
| sku | CF-DL-250G | Item code per enterprise rules |
| product_name | Cà phê rang xay Đà Lạt 250 g | Display name |
| product_description | Origin description, roast profile, and brewing instructions | Free-form text |

Do not use display names as primary keys. Names can change, collide, be translated into other languages, or contain diacritics and spaces. Technical codes need their own lifecycle and rules.

### 6.1. Code formatting rules

A technical code should clearly specify:

- Allowed character set;
- Minimum and maximum length;
- Case sensitivity / casing rules;
- Allowed separator characters;
- Whether whitespace is permitted;
- Whether Vietnamese diacritics or Unicode characters are permitted;
- Uniqueness scope;
- Whether leading zeros are significant;
- Whether the code can be changed after creation;
- Who or which system is authorized to issue codes.

For codes exchanged broadly across systems, a restricted ASCII character set can reduce risks from collation differences and integration tools. This is a design choice, not a mandatory rule for all codes. If the business requires codes with native characters, explicitly define encoding, normalization, and comparison rules.

Illustrative SKU format example:

~~~text
CF-DL-250G
CF-HN-500G
TEA-GT-100G
~~~

The rule might specify uppercase Latin letters, digits, and hyphens, length from 3 to 24 characters, no spaces. The system must also specify whether an SKU is unique enterprise-wide or only within each organization or supplier.

### 6.2. Leading zeros and data types

A code can consist of digits yet still be a string. For example, area code “0012” is not the number 12. Storing it as a numeric type can strip leading zeros and invite meaningless arithmetic.

Use string types for identifiers with leading zeros, separators, or no arithmetic use. Use numeric types only if the value is genuinely an arithmetic quantity.

### 6.3. Do not auto-strip diacritics from codes

If a technical code is specified as ASCII-only, validate and reject characters outside the allowed set. Do not automatically convert “ĐÀ NẴNG” to “DA NANG” or strip invalid characters without explicit rules. Two distinct codes could collapse into the same string after conversion.

If generating codes from display names is required, treat it as a code-generation workflow with collision checks, deduplication rules, and stability after the display name changes.

## 7. Length: characters, code points, or bytes?

Length limits must align with both user expectations and storage mechanics. The phrase “maximum 100 characters” must be clarified before turning it into a column limit.

There are at least three common ways to measure length:

- **Grapheme cluster count:** closest to what users perceive as characters.
- **Code point or code unit count:** number of code units per implementation.
- **Byte count:** storage size after encoding.

For example, a Vietnamese string or emoji can have more bytes than visible characters. Therefore, a 100-byte limit is not equivalent to 100 characters.

### 7.1. Business length and storage limits

Document two separate limits:

1. **Business limit:** maximum visible characters a user may enter, or character count required by a code format.
2. **Storage limit:** maximum units the column and system can store given the encoding and data type.

For instance, a product name might be limited to 200 grapheme clusters by UI policy, while the column needs enough byte capacity to hold the corresponding UTF-8 string. Check limits end-to-end across APIs, drivers, databases, message queues, and integrated systems.

### 7.2. Choosing string types

DBMSs vary in string types and length semantics. Common types:

| Conceptual type | Characteristics | When to consider |
|---|---|---|
| CHAR(n) | Fixed length or space-padding rules depending on DBMS | Truly fixed-length codes |
| VARCHAR(n) | Length-bounded string | Names, codes, and short-to-medium text fields |
| TEXT or equivalent | Long text; limits or storage mechanics depend on platform | Descriptions, notes, and long content |

Do not pick CHAR solely to cap length. Understand how your DBMS handles padding, trailing spaces, comparisons, and indexes. For variable-length codes, VARCHAR is usually clearer to express.

TEXT does not mean truly unlimited. DBMSs, protocols, APIs, and applications still impose size, memory, processing time, and payload limits.

### 7.3. Avoiding broken string truncation

When slicing a string by bytes, never cut in the middle of a UTF-8 multi-byte sequence for a code point. When slicing by code points, check whether it splits a grapheme cluster. If users enter data under a visible-character limit, the UI should count by the appropriate rule and report errors before saving.

Do not rely on the database to truncate oversized strings automatically. Some DBMSs raise errors, while some modes or operations may truncate with a warning. Applications must validate explicitly and never silently lose data.

## 8. Whitespace, control characters, and invisible characters

Text strings can contain various whitespace and control characters. Two visually identical strings may differ due to:

- ASCII spaces vs. non-breaking spaces;
- Tabs or line breaks;
- Leading or trailing whitespace;
- Zero-width characters;
- Bidirectional text control characters;
- Replacement characters or invalid characters after transcoding.

Do not strip all invisible characters indiscriminately. In free-form text, line breaks may carry meaning. In technical codes, tabs, newlines, and spaces should usually be rejected.

### 8.1. Trimming policy

Define whether leading and trailing whitespace is stripped. For display names, trimming leading/trailing whitespace may prevent accidental typos. For original document content, verbatim preservation may be needed.

For technical codes, the policy should usually be strict: reject whitespace or strip it using one uniform rule before format validation. Never let the application and database apply two different trimming behaviors.

### 8.2. Control characters and bidirectional controls

Certain Unicode control characters influence left-to-right or right-to-left text rendering order. They may be necessary in multilingual content, yet can make codes or display names misleading during visual inspection.

For technical codes, reject control characters and unnecessary formatting characters. For free-form text, handle them according to content policy, safe rendering, and language context. Do not strip them with a single blanket filter across all fields.

### 8.3. Confusable characters

Confusables are characters from different scripts that look nearly identical. For example, a Latin letter and a Cyrillic letter can look virtually the same. This can cause confusion in login identifiers, product codes, domain names, or reference codes.

For critical identifiers and codes:

- Restrict the character set to business needs;
- Apply uniform normalization and comparison rules;
- Warn or reject confusable characters where appropriate;
- Never rely on human eyes to verify uniqueness;
- Use stable technical IDs to link records.

For person names and free-form content, do not impose ASCII-only restrictions solely to avoid confusables. Separate display-field policies from identifier policies.

## 9. Designing logical rules for each field

A text attribute specification should state more than a name and string type. Use the following template:

| Component | Questions to answer |
|---|---|
| Meaning | What content does the string represent? |
| Source | User-entered, system-generated, or received from external systems? |
| Encoding | Which Unicode and encoding does the system use? |
| Length | Measured in graphemes, code points, code units, or bytes? |
| Character domain | Is the character set restricted? |
| Normalization | Is NFC or another form applied? |
| Comparison | Case-sensitive, accent-sensitive, or locale-dependent? |
| Whitespace | Trimmed, forbidden, or preserved? |
| Uniqueness | Globally unique or within what scope? |
| Preservation | Must the original raw string be retained? |

Example specification for two fields:

| Attribute | product_name | sku |
|---|---|---|
| Purpose | Display name for users | Item code for reference and exchange |
| Characters | Unicode | Uppercase Latin letters, digits, and hyphens per rules |
| Length | Max 200 grapheme clusters per UI policy | 3–24 characters per code format |
| Normalization | NFC for comparison form; retain original if needed | Normalized per published code format |
| Casing | Searchable case-insensitively | Define code as case-insensitive or uppercase-only |
| Whitespace | Trim leading/trailing per policy; internal spaces allowed | Not allowed |
| Uniqueness | Usually not unique | Unique within defined enterprise or tenant scope |

Values in the table are examples. Projects must confirm actual limits, scopes, and rules before applying them.

## 10. Design example: product catalog

Suppose a system needs to store SKU code, product name, search name, and description.

### 10.1. Identify meanings

- SKU is a business reference code, not a display name.
- Product name may contain Vietnamese diacritics and multiple languages.
- Description can be long and contain punctuation and line breaks.
- Search name can be derived data to support accent-insensitive or case-insensitive search.

Do not store an accent-stripped search name in the display-name column. Also do not use product name as a unique key.

### 10.2. Illustrative logical model

~~~sql
PRODUCT
-------
product_id          : Identifier, primary key
sku                 : Code, required, unique in agreed scope
product_name        : Unicode text, required, max 200 grapheme clusters
product_description : Unicode long text, optional
search_name         : Derived/search text, optional
created_at          : Timestamp
~~~

This is illustrative logical notation, not DDL for a specific DBMS. Specify how `search_name` is generated, along with collation, indexes, and physical limits for your deployment platform.

### 10.3. SKU entry workflow

1. Receive user input.
2. Validate allowed characters and length.
3. Apply published casing and whitespace rules.
4. Check uniqueness within the proper scope.
5. Store the canonical code.
6. Return a clear error if the code has an invalid format or already exists.

Do not automatically strip invalid characters and save, as users may not realize their code was altered. If automatic normalization occurs, display the result and ensure no collisions are introduced.

### 10.4. Product name entry workflow

1. Receive Unicode text.
2. Validate encoding and valid string structure.
3. Check length against UI rules and storage limits.
4. Handle leading/trailing whitespace per policy.
5. Store display content.
6. Generate a separate search form if needed.
7. On read, display the string in the proper encoding without losing diacritics.

## 11. Uniqueness with Unicode

A UNIQUE constraint is not merely a yes/no decision. It depends on whether the system considers two strings equivalent.

For example, the business may consider two SKUs differing only by case to be the same code. In that case, if the database compares case-sensitively, a plain UNIQUE constraint may allow both. Conversely, an accent-insensitive collation may treat two differently accented names as equivalent even when the business wants to keep both.

Define normalization rules before creating unique indexes or checking duplicates.

One design pattern is storing:

- Original value for display;
- Normalized value used for comparison;
- Uniqueness constraint on the normalized value within the appropriate scope.

Conceptual example:

~~~text
sku_original = "cf-dl-250g"
sku_canonical = "CF-DL-250G"
UNIQUE(tenant_id, sku_canonical)
~~~

This is only an example. If a code is case-sensitive, do not uppercase everything. If codes are issued by suppliers with their own rules, preserve the source's rules.

For display names, global uniqueness should usually not be enforced. Two people or two products can share the same name. If near-duplicate detection is needed, that is a search feature or separate business check, not a unique key.

## 12. Text search and source data

Search requires rules separate from storage. A name field can be searched by:

- Exact string;
- Case-insensitive match;
- Accent-insensitive match;
- Prefix;
- Full-text keywords;
- Aliases or alternate names;
- Language-specific names.

Do not alter source data merely to make searching easier. You can create a normalized search column or search index, provided it is clearly documented as derived data with defined generation and update rules.

For example, a user searching “ca phe” may expect to find “cà phê”. Search functionality can use an accent-stripped search key. However, if two products “Hoa” and “Hòa” are distinct, accent stripping must never be used as an identifier or uniqueness rule.

If the system supports multiple languages, define which name is primary, which are translations, which language has priority, and whether switching languages affects identity. Product ID remains stable even when display names change.

## 13. Evolving text rules over time

Unicode rules, collations, string libraries, and business requirements can change. Changing rules can introduce collisions between values previously considered distinct.

Before making changes:

1. Identify affected fields.
2. Check existing data against the new rules.
3. Find values that become duplicates after normalization or collation changes.
4. Define conflict resolution and who has authority to decide.
5. Plan updates to data, indexes, and applications.
6. Test integrations and backward compatibility with historical data.
7. Roll out with versioning, backups, and a recovery plan.

Do not change collations or bulk-normalize data without checking impacts on unique indexes. Two previously distinct codes may become equivalent under the new rules, causing migrations to fail or creating reference confusion.

If technical codes have already been exchanged with external systems, changing code rules may constitute an integration contract change. Use versioning or a compatible transition process rather than silently altering values.

## 14. Common mistakes

1. **Using numeric types for codes:** strips leading zeros or invites meaningless arithmetic.
2. **Enforcing length in bytes while describing it as characters:** users entering fewer characters get rejected when using Vietnamese or emoji.
3. **Assuming one visible character equals one code point:** breaks string slicing and length counting.
4. **Inconsistent encoding across components:** Vietnamese text suffers mojibake through drivers or import/export tools.
5. **Skipping Unicode normalization:** visually identical strings fail to match on exact comparison.
6. **Applying NFKC or accent stripping to source data without evaluation:** alters potentially meaningful distinctions.
7. **Using one collation for all columns:** technical codes and display names have different comparison needs.
8. **Putting UNIQUE on display names:** blocks valid entities that happen to share a name.
9. **Silently deleting unfamiliar characters:** alters codes or content without user awareness.
10. **Ignoring whitespace and control characters:** visually identical codes fail to match.
11. **Treating TEXT as unlimited:** overlooks API, protocol, memory, and storage limits.
12. **Failing to test after changing collations or normalization:** unique indexes can suffer collisions.

## 15. Checklist for designing text attributes

- [ ] Determined whether the string is free-form text, display name, business code, or technical identifier.
- [ ] Identified who creates the value and whether it can change.
- [ ] System supports Unicode end-to-end from UI to database and integrations.
- [ ] Appropriate encoding chosen and import/export tested.
- [ ] Decided whether to normalize Unicode, which form to use, and at which step.
- [ ] Distinguished normalization, lowercasing, case folding, and accent stripping.
- [ ] Defined collation and comparison rules for each attribute group.
- [ ] Business length measured in an explicit unit.
- [ ] Storage limits accommodate the actual encoding and data type.
- [ ] Truncation rules do not break code points or grapheme clusters.
- [ ] Technical codes have clear character sets, lengths, casing rules, and uniqueness scopes.
- [ ] Codes with leading zeros are stored as strings.
- [ ] Whitespace, control characters, and formatting characters handled per field type.
- [ ] Source data retained when display content or history must be preserved.
- [ ] Accent-insensitive or case-insensitive search separated from identity.
- [ ] Normalization or collation changes checked for collisions with a migration plan.

## 16. Practice exercise

A product management system has the following requirements:

- Product names support Vietnamese and English.
- SKUs consist solely of Latin letters, digits, and hyphens.
- SKUs are case-insensitive.
- Product names are limited by the number of characters visible to users.
- Users can search products using accent-insensitive keywords.
- Product descriptions can contain line breaks.
- Product codes must be unique within each organization.

Propose logical specifications for the attributes:

1. `product_id`;
2. `sku`;
3. `product_name`;
4. `product_description`;
5. `search_name`;
6. `tenant_id`.

Specify conceptual type, encoding, length, normalization, collation, uniqueness, and whitespace handling.

**Suggested solution:**

| Attribute | Reference specification |
|---|---|
| product_id | Stable technical identifier, independent of product name; primary key |
| sku | ASCII string per published character set; normalized to uppercase; no whitespace; UNIQUE per `tenant_id` |
| product_name | Unicode text; supports Vietnamese and English; NFC for canonical comparison form; bounded by grapheme clusters |
| product_description | Long Unicode text; line breaks allowed; do not mechanically trim or strip content characters |
| search_name | Derived value for search; can be lowercased and accent-stripped per search rules; never used as a key |
| tenant_id | Organization identifier; participates in SKU uniqueness scope and references a valid tenant |

One implementation approach stores the original name and builds `search_name` separately. During accent-insensitive search, the application or search engine applies the same transformation rules. SKUs are normalized before duplicate checking and stored in a single canonical representation.

**Additional questions to confirm:** how many grapheme clusters is the product name limit; can an SKU change after transactions occur; can an SKU be reused after a product is discontinued; and can organizations share codes with other organizations.

The exercise meets expectations when the specification clearly separates display text from technical codes, measures length in the right unit, preserves Vietnamese diacritics, supports accent-insensitive search without losing the original name, and enforces SKU uniqueness within the proper organization scope.
