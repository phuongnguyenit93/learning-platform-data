# So sánh cùng bài toán trên hai hệ quản trị với cấu hình được ghi rõ

Một cách học transaction concurrency hiệu quả là giữ nguyên bài toán nghiệp vụ, dữ liệu ban đầu và lịch chạy đồng thời, sau đó thực hiện trên hai hệ quản trị với cấu hình được ghi rõ. Khi đó có thể phân biệt đâu là quy tắc chung của transaction, đâu là hành vi phụ thuộc isolation level, lock manager hoặc cách engine triển khai MVCC.

Bài học này dùng bài toán **đặt chỗ có giới hạn sức chứa** để so sánh PostgreSQL và MySQL/InnoDB. Một phòng có sức chứa 10 người, hiện đã có 6 người được đặt. Hai request đồng thời muốn thêm mỗi request 3 người. Chỉ một request được phép thành công vì tổng 12 sẽ vượt sức chứa.

Hai môi trường được cố định như sau:

| Thành phần | PostgreSQL | MySQL |
| --- | --- | --- |
| Phiên bản lab | PostgreSQL 16.x | MySQL 8.4 LTS |
| Storage engine | Heap table, B-tree index | InnoDB |
| Isolation level của bài test chính | `READ COMMITTED` | `REPEATABLE READ` |
| Transaction | Bắt đầu/kết thúc tường minh | `START TRANSACTION`/`COMMIT` tường minh |
| Autocommit của session | Có thể bật mặc định; test dùng `BEGIN` rõ ràng | `autocommit = 1`; `START TRANSACTION` mở transaction rõ ràng |
| Kiểu đọc thông thường | Snapshot mới theo từng statement ở READ COMMITTED | Consistent read theo snapshot của transaction ở REPEATABLE READ |
| Cơ chế ghi | Row lock, MVCC và WAL | Row/record lock, MVCC và undo/redo log |

Đây là cấu hình lab để so sánh, không phải tuyên bố rằng hai engine luôn có cùng mặc định. MySQL/InnoDB thường dùng `REPEATABLE READ` mặc định; PostgreSQL mặc định dùng `READ COMMITTED`. Các bài test tiếp theo sẽ đổi isolation level có chủ đích để quan sát khác biệt.

## 1. Bất biến nghiệp vụ cần bảo vệ

Một phòng có sức chứa 10 người. Bảng reservation lưu số khách của từng lần đặt. Quy tắc nghiệp vụ là:

```text
SUM(reservation.guest_count WHERE room_id = 7) <= room.capacity
```

Dữ liệu ban đầu:

| Phòng | Sức chứa | Đã đặt | Còn chỗ |
| --- | ---: | ---: | ---: |
| 7 | 10 | 6 | 4 |

Hai request cùng đến:

- T1 muốn đặt thêm 3 người.
- T2 muốn đặt thêm 3 người.

Nếu cả hai thành công, tổng sẽ là `6 + 3 + 3 = 12`, vượt sức chứa. Hệ thống phải chấp nhận tối đa một request.

Đây là bất biến nhiều hàng: tổng khách được tính từ nhiều reservation, còn sức chứa được lưu ở hàng phòng. Hai transaction có thể INSERT hai reservation với primary key khác nhau, vì vậy chúng không nhất thiết xung đột trên cùng hàng con.

## 2. Xác nhận cấu hình thật trước khi chạy lab

Không chỉ dựa vào tên database hoặc cấu hình trong file ứng dụng. Hãy truy vấn trực tiếp trên từng môi trường.

### PostgreSQL

```sql
SELECT version();
SHOW default_transaction_isolation;
SHOW synchronous_commit;
SHOW fsync;
```

Trong bài test chính, mỗi transaction sẽ khai báo rõ:

```sql
BEGIN;
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

`SET TRANSACTION` phải chạy trước câu lệnh truy cập dữ liệu đầu tiên trong transaction. Với durability lab, giữ `synchronous_commit = on` và `fsync = on` theo cấu hình máy thử nghiệm; mục tiêu chính của bài học vẫn là concurrency, không phải benchmark độ bền ghi.

### MySQL/InnoDB

```sql
SELECT VERSION();
SELECT @@transaction_isolation;
SELECT @@autocommit;
SELECT @@innodb_flush_log_at_trx_commit;
SHOW VARIABLES LIKE 'sync_binlog';
```

Trong bài test chính, mở transaction và khai báo isolation level rõ ràng:

```sql
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION;
```

`SET TRANSACTION` không có `SESSION` hoặc `GLOBAL` áp dụng cho transaction kế tiếp trên connection. Nếu dùng `SET SESSION`, hãy ghi rõ cấu hình session và reset nó sau lab. Với durability lab, `innodb_flush_log_at_trx_commit = 1` là cấu hình thường dùng để flush redo log theo commit; nếu binary log được bật và cần durability tương ứng, kiểm tra thêm `sync_binlog`. Các giá trị này có ảnh hưởng hiệu năng, nên không thay đổi giữa các lần so sánh mà không ghi lại.

## 3. Tạo schema tương đương

Hai hệ quản trị dùng cùng mô hình logic: một hàng capacity tổng hợp và nhiều hàng reservation. Trước tiên, ta tạo phiên bản schema chỉ có reservation để tái hiện lỗi; sau đó bổ sung `reserved_count` để sửa lỗi bằng cập nhật nguyên tử.

### PostgreSQL 16

```sql
CREATE TABLE room (
    room_id BIGINT PRIMARY KEY,
    capacity INTEGER NOT NULL CHECK (capacity > 0)
);

CREATE TABLE reservation (
    reservation_id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    room_id BIGINT NOT NULL REFERENCES room(room_id),
    guest_count INTEGER NOT NULL CHECK (guest_count > 0)
);

CREATE INDEX ix_reservation_room_id
    ON reservation(room_id);
```

### MySQL 8.4 / InnoDB

```sql
CREATE TABLE room (
    room_id BIGINT PRIMARY KEY,
    capacity INT NOT NULL,
    CONSTRAINT ck_room_capacity CHECK (capacity > 0)
) ENGINE = InnoDB;

CREATE TABLE reservation (
    reservation_id BIGINT NOT NULL AUTO_INCREMENT,
    room_id BIGINT NOT NULL,
    guest_count INT NOT NULL,
    PRIMARY KEY (reservation_id),
    KEY ix_reservation_room_id (room_id),
    CONSTRAINT fk_reservation_room
        FOREIGN KEY (room_id) REFERENCES room(room_id),
    CONSTRAINT ck_reservation_guest_count CHECK (guest_count > 0)
) ENGINE = InnoDB;
```

MySQL thực thi `CHECK` từ MySQL 8.0.16 trở lên; MySQL 8.4 đáp ứng điều kiện này. Cả hai bảng đều dùng InnoDB để có transaction và row-level locking. Không dùng MyISAM cho bài lab vì MyISAM không cung cấp transaction semantics tương đương.

### Dữ liệu ban đầu giống nhau

Chạy trên cả hai hệ quản trị:

```sql
INSERT INTO room(room_id, capacity)
VALUES (7, 10);

INSERT INTO reservation(room_id, guest_count)
VALUES (7, 4), (7, 2);
```

Kiểm tra:

```sql
SELECT r.room_id, r.capacity,
       COALESCE(SUM(x.guest_count), 0) AS reserved_count
FROM room r
LEFT JOIN reservation x ON x.room_id = r.room_id
WHERE r.room_id = 7
GROUP BY r.room_id, r.capacity;
```

Kết quả mong đợi ở cả hai là `capacity = 10`, `reserved_count = 6`. Nếu chạy lại lab, cần rollback/reset dữ liệu hoặc tạo room ID mới để hai phiên không dùng dữ liệu từ lần thử trước.

## 4. Bài test sai: đọc tổng rồi INSERT

Đây là cách triển khai dễ viết nhưng không bảo vệ bất biến dưới concurrency:

```text
BEGIN
  SELECT SUM(guest_count)
  Nếu tổng + số khách mới <= capacity:
      INSERT reservation
COMMIT
```

Hai transaction đọc cùng tổng 6. Mỗi transaction thấy `6 + 3 <= 10`, nên cả hai đều quyết định hợp lệ. Chúng INSERT hai hàng khác nhau và có thể cùng commit.

### Session A — PostgreSQL

```sql
BEGIN;
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

SELECT COALESCE(SUM(guest_count), 0) AS reserved_count
FROM reservation
WHERE room_id = 7;
-- Trả về 6.
-- Tạm dừng, chưa INSERT.
```

### Session B — PostgreSQL

```sql
BEGIN;
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

SELECT COALESCE(SUM(guest_count), 0) AS reserved_count
FROM reservation
WHERE room_id = 7;
-- Cũng trả về 6.

INSERT INTO reservation(room_id, guest_count)
VALUES (7, 3);

COMMIT;
```

### Quay lại Session A — PostgreSQL

```sql
INSERT INTO reservation(room_id, guest_count)
VALUES (7, 3);

COMMIT;
```

Ở `READ COMMITTED`, mỗi statement PostgreSQL nhận một snapshot tại thời điểm statement bắt đầu. Hai câu SELECT chạy trước khi transaction nào INSERT, nên đều có thể đọc tổng 6. Hai INSERT tạo hai hàng mới với ID khác nhau; không có constraint nào diễn đạt tổng khách của nhiều hàng phải nhỏ hơn capacity. Cả hai có thể commit.

### Session A — MySQL/InnoDB

```sql
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION;

SELECT COALESCE(SUM(guest_count), 0) AS reserved_count
FROM reservation
WHERE room_id = 7;
-- Trả về 6 và thiết lập consistent-read snapshot của transaction.
-- Tạm dừng, chưa INSERT.
```

### Session B — MySQL/InnoDB

```sql
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION;

SELECT COALESCE(SUM(guest_count), 0) AS reserved_count
FROM reservation
WHERE room_id = 7;
-- Cũng trả về 6.

INSERT INTO reservation(room_id, guest_count)
VALUES (7, 3);

COMMIT;
```

### Quay lại Session A — MySQL/InnoDB

```sql
INSERT INTO reservation(room_id, guest_count)
VALUES (7, 3);

COMMIT;
```

Trong InnoDB, SELECT thông thường ở `REPEATABLE READ` là consistent read theo read view của transaction; nó không khóa toàn bộ các hàng hoặc khoảng dữ liệu được đọc. Hai transaction có thể cùng đọc snapshot có tổng 6 rồi chèn các hàng mới khác nhau. Khóa kiểm tra foreign key trên hàng phòng không biến phép tính tổng reservation thành một kiểm tra sức chứa nguyên tử. Vì vậy cả hai INSERT vẫn có thể commit.

### Kiểm tra kết quả sai

```sql
SELECT COALESCE(SUM(guest_count), 0) AS reserved_count
FROM reservation
WHERE room_id = 7;
```

Kết quả có thể là 12 ở cả hai hệ quản trị. Đây là write skew/predicate anomaly: mỗi transaction kiểm tra điều kiện trên dữ liệu nó đọc, nhưng hợp của hai thay đổi làm bất biến bị phá vỡ.

## 5. Vì sao hai isolation level khác nhau vẫn cho cùng lỗi?

`READ COMMITTED` của PostgreSQL và `REPEATABLE READ` của InnoDB không có cùng semantics snapshot, nhưng cả hai đều cho phép lịch chạy vừa mô tả khi chỉ dùng consistent SELECT thông thường rồi INSERT các hàng riêng biệt.

| Khía cạnh | PostgreSQL 16 `READ COMMITTED` | MySQL 8.4 InnoDB `REPEATABLE READ` |
| --- | --- | --- |
| Snapshot của SELECT thông thường | Mỗi statement có snapshot mới | Các consistent read trong transaction dùng read view được tạo ở lần consistent read đầu tiên |
| SELECT thông thường có khóa hàng không? | Không | Không; đây là consistent read |
| INSERT hai hàng reservation khác nhau | Có thể cùng commit | Có thể cùng commit |
| Vì sao không phát hiện tổng vượt giới hạn? | Không có constraint/lock bảo vệ predicate tổng | Snapshot read không khóa predicate và không có constraint tổng |
| Có thể dùng SERIALIZABLE để bảo vệ không? | Có; PostgreSQL dùng Serializable Snapshot Isolation và có thể hủy transaction | Có; InnoDB dùng locking semantics mạnh hơn, có thể chờ hoặc deadlock |

Không nên kết luận rằng `REPEATABLE READ` luôn ngăn phantom hoặc write skew trên mọi hệ quản trị. Tên isolation level giống nhau không đảm bảo triển khai giống nhau. Hãy dựa vào semantics của engine và test trên đúng phiên bản.

## 6. Cách sửa dùng một hàng bộ đếm chung

Một giải pháp dễ chứng minh là lưu `reserved_count` trên hàng room. Mỗi transaction đặt chỗ phải tăng bộ đếm bằng một câu UPDATE có điều kiện trước khi INSERT reservation. Hàng room trở thành guard/counter chung cho mọi lần đặt của cùng phòng.

### Bổ sung cột trên PostgreSQL

```sql
ALTER TABLE room
ADD COLUMN reserved_count INTEGER NOT NULL DEFAULT 0;

ALTER TABLE room
ADD CONSTRAINT ck_room_reserved_count
CHECK (reserved_count >= 0 AND reserved_count <= capacity);

UPDATE room
SET reserved_count = 6
WHERE room_id = 7;
```

### Bổ sung cột trên MySQL/InnoDB

```sql
ALTER TABLE room
ADD COLUMN reserved_count INT NOT NULL DEFAULT 0,
ADD CONSTRAINT ck_room_reserved_count
    CHECK (reserved_count >= 0 AND reserved_count <= capacity);

UPDATE room
SET reserved_count = 6
WHERE room_id = 7;
```

Trong production, khi thêm bộ đếm vào bảng đã có dữ liệu, cần backfill từ reservation và kiểm tra tổng trước khi bật constraint/đổi luồng ghi. Ví dụ trên giả định dữ liệu lab đã biết và có đúng 6 khách.

### Quy tắc cập nhật

```text
BEGIN
  UPDATE room
    tăng reserved_count nếu reserved_count + request <= capacity
  Nếu đúng một hàng được cập nhật:
    INSERT reservation
  Nếu INSERT lỗi:
    ROLLBACK cả bộ đếm và reservation
COMMIT
```

Hai transaction đặt cùng phòng phải cập nhật cùng một hàng `room`. Database sẽ điều phối xung đột ghi trên hàng này. Điều kiện sức chứa được kiểm tra ngay trong câu UPDATE, không tách thành SELECT rồi UPDATE.

## 7. PostgreSQL: UPDATE có điều kiện và RETURNING

Chạy trong Session A hoặc B:

```sql
BEGIN;
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

UPDATE room
SET reserved_count = reserved_count + 3
WHERE room_id = 7
  AND reserved_count + 3 <= capacity
RETURNING room_id, capacity, reserved_count;
```

Nếu câu lệnh trả về một hàng, ứng dụng có thể tiếp tục INSERT:

```sql
INSERT INTO reservation(room_id, guest_count)
VALUES (7, 3);

COMMIT;
```

Nếu UPDATE trả về 0 hàng, phòng không tồn tại hoặc không còn đủ chỗ. Ứng dụng phải rollback/hoàn tất theo nhánh từ chối nghiệp vụ và không INSERT reservation.

PostgreSQL ở `READ COMMITTED` khi UPDATE gặp một hàng đang bị transaction khác cập nhật sẽ chờ. Sau khi transaction kia commit, PostgreSQL kiểm tra lại điều kiện `WHERE` trên phiên bản hàng mới theo cơ chế xử lý concurrent update. Nếu transaction trước đã đổi `reserved_count` từ 6 thành 9, điều kiện `9 + 3 <= 10` sai và transaction sau cập nhật 0 hàng.

## 8. MySQL/InnoDB: UPDATE có điều kiện và số hàng cập nhật

Chạy trong Session A hoặc B:

```sql
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION;

UPDATE room
SET reserved_count = reserved_count + 3
WHERE room_id = 7
  AND reserved_count + 3 <= capacity;
```

Trong JDBC, lấy số hàng được cập nhật từ `executeUpdate()`. Trong MySQL CLI có thể xem ngay:

```sql
SELECT ROW_COUNT();
```

Nếu số hàng cập nhật là 1, INSERT reservation rồi commit:

```sql
INSERT INTO reservation(room_id, guest_count)
VALUES (7, 3);

COMMIT;
```

Nếu số hàng cập nhật là 0, rollback và trả kết quả hết chỗ hoặc phòng không tồn tại. Không được INSERT khi UPDATE không thành công.

InnoDB thực hiện UPDATE bằng locking/current read và khóa hàng cần sửa. Khi T2 phải chờ T1, sau khi T1 commit, thao tác UPDATE của T2 đánh giá điều kiện trên phiên bản hiện hành của hàng. Nếu bộ đếm đã là 9, điều kiện không còn đúng nên T2 không tăng bộ đếm.

### Lịch chạy đúng trên cả hai engine

| Bước | T1 | T2 |
| --- | --- | --- |
| 1 | UPDATE guard: 6 → 9, thành công | |
| 2 | | UPDATE cùng hàng, phải chờ T1 |
| 3 | INSERT reservation 3 khách | Đang chờ |
| 4 | COMMIT | Đang chờ |
| 5 | | Tiếp tục UPDATE, kiểm tra giá trị hiện hành 9 |
| 6 | | Điều kiện `9 + 3 <= 10` sai; cập nhật 0 hàng |
| 7 | | Không INSERT; rollback/đóng transaction |

Kết quả cuối là 9 khách. Một request thành công, request còn lại bị từ chối. Nếu T1 rollback thay vì commit, bộ đếm quay lại 6 và T2 có thể tiếp tục tăng lên 9.

## 9. Vì sao cách counter-row không phụ thuộc snapshot cũ?

Giải pháp counter-row không quyết định dựa trên một phép `SELECT SUM` đã đọc trước đó. Câu UPDATE vừa khóa hàng vừa kiểm tra điều kiện trên phiên bản cần cập nhật.

Điều này đặc biệt hữu ích khi so sánh hai engine:

- PostgreSQL `READ COMMITTED` dùng snapshot theo statement; UPDATE xử lý concurrent row version và đánh giá lại điều kiện sau khi chờ.
- InnoDB `REPEATABLE READ` giữ read view cho consistent read, nhưng UPDATE là current/locking read và thao tác trên phiên bản hiện hành của hàng.

Không có yêu cầu phải làm mới một snapshot SELECT cũ để ra quyết định. Điều kiện và thay đổi bộ đếm nằm trong cùng statement nguyên tử.

## 10. Cách khác: khóa guard bằng SELECT FOR UPDATE

Có thể khóa hàng room trước rồi mới tính tổng reservation:

```sql
BEGIN;

SELECT room_id, capacity
FROM room
WHERE room_id = 7
FOR UPDATE;

SELECT COALESCE(SUM(guest_count), 0)
FROM reservation
WHERE room_id = 7;

-- Nếu tổng + số khách mới <= capacity thì INSERT.
```

Mọi transaction đặt chỗ phải khóa cùng hàng room trước khi tính tổng và ghi reservation. Hàng room tồn tại ngay cả khi chưa có reservation, vì vậy nó làm guard tốt hơn việc chỉ khóa các hàng con hiện có.

### Khác biệt snapshot cần chú ý

Ở PostgreSQL `READ COMMITTED`, câu SELECT tổng chạy sau khi transaction lấy được guard sẽ có snapshot statement mới. Nếu transaction đã phải chờ guard, nó có thể đọc reservation vừa commit bởi transaction trước.

Ở MySQL/InnoDB `REPEATABLE READ`, SELECT thông thường là consistent read theo snapshot đã được thiết lập ở lần consistent read đầu tiên. Nếu transaction đã thực hiện một consistent SELECT trước khi lấy guard và sau đó phải chờ, câu SELECT tổng tiếp theo có thể vẫn dùng snapshot cũ. Vì vậy:

- Lấy guard trước mọi consistent read có thể ảnh hưởng đến quyết định, hoặc
- Dùng một locking/current read phù hợp để đọc dữ liệu sau khi lấy guard, hoặc
- Dùng counter-row conditional UPDATE như giải pháp chính của bài lab.

Không trộn một SELECT snapshot cũ với giả định rằng `SELECT ... FOR UPDATE` tự làm mới toàn bộ read view của transaction. Locking read và consistent read có semantics khác nhau trong InnoDB.

## 11. SERIALIZABLE trên PostgreSQL và MySQL

Một cách khác là yêu cầu database bảo đảm transaction có kết quả tương đương một thứ tự chạy tuần tự.

### PostgreSQL 16: Serializable Snapshot Isolation

```sql
BEGIN;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

SELECT COALESCE(SUM(guest_count), 0)
FROM reservation
WHERE room_id = 7;

-- Nếu tổng + 3 <= 10:
INSERT INTO reservation(room_id, guest_count)
VALUES (7, 3);

COMMIT;
```

PostgreSQL dùng Serializable Snapshot Isolation (SSI) để theo dõi các phụ thuộc đọc/ghi. Predicate read được theo dõi bằng predicate lock kiểu `SIREAD`; chúng không đơn giản là row lock chặn writer. Nếu hai transaction tạo một cấu trúc phụ thuộc không thể tuần tự hóa, PostgreSQL có thể hủy một transaction với serialization failure, SQLSTATE `40001`.

Ứng dụng phải rollback và retry toàn bộ transaction từ đầu. Không chỉ retry INSERT, vì quyết định đặt chỗ đã dựa trên tổng cũ.

### MySQL 8.4/InnoDB: SERIALIZABLE với locking semantics

```sql
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
START TRANSACTION;

SELECT COALESCE(SUM(guest_count), 0)
FROM reservation
WHERE room_id = 7;

-- Nếu tổng + 3 <= 10:
INSERT INTO reservation(room_id, guest_count)
VALUES (7, 3);

COMMIT;
```

Trong InnoDB, khi transaction tường minh đang mở, `SERIALIZABLE` làm SELECT thông thường hoạt động như locking read chia sẻ (shared next-key lock) trong các điều kiện áp dụng. Với index theo `room_id`, engine có thể khóa các record/range liên quan để bảo vệ predicate. Hai transaction cùng đọc rồi cùng muốn chèn có thể phải chờ hoặc deadlock khi nâng cấp/xung đột khóa; InnoDB chọn một transaction làm deadlock victim khi phát hiện vòng chờ.

Không giả định PostgreSQL SSI và InnoDB SERIALIZABLE triển khai cùng một thuật toán hoặc báo lỗi ở cùng thời điểm. PostgreSQL có thể phát serialization failure do dependency graph; InnoDB thường thể hiện bằng lock wait/deadlock tùy lịch và index/range bị khóa. Cả hai đều yêu cầu ứng dụng xử lý retry transaction khi lỗi concurrency phù hợp.

### So sánh SERIALIZABLE

| Khía cạnh | PostgreSQL 16 | MySQL 8.4/InnoDB |
| --- | --- | --- |
| Cơ chế nổi bật | SSI và theo dõi dependency/predicate read | Locking read với shared next-key locks trong transaction tường minh |
| Writer có thể bị chặn bởi reader? | Predicate SIREAD không chặn writer theo kiểu row lock thông thường; có thể phát hiện xung đột và abort | Shared/next-key lock có thể làm writer chờ hoặc tạo deadlock |
| Lỗi concurrency | Serialization failure, SQLSTATE `40001` | Deadlock error hoặc lock wait timeout tùy tình huống |
| Phục hồi | Rollback và retry toàn bộ transaction | Rollback transaction bị chọn làm victim/timeout rồi retry toàn bộ nếu an toàn |
| Tác động hiệu năng | Có thể abort transaction khi dependency nguy hiểm | Có thể tăng lock wait và deadlock, phụ thuộc index và range |

## 12. So sánh các phương án bảo vệ cùng bất biến

| Phương án | PostgreSQL 16 READ COMMITTED | MySQL 8.4/InnoDB REPEATABLE READ | Đặc điểm chung |
| --- | --- | --- | --- |
| SELECT SUM rồi INSERT | Có thể write skew | Có thể write skew | Không bảo vệ tổng nhiều hàng |
| SELECT guard `FOR UPDATE`, rồi SELECT SUM | Có thể dùng snapshot statement mới sau khi lấy guard | Phải chú ý read view cũ của consistent read | Mọi writer phải tuân thủ guard |
| Conditional UPDATE trên counter row | UPDATE khóa hàng và điều kiện được đánh giá lại sau khi chờ | UPDATE là current read, khóa hàng và đánh giá điều kiện hiện hành | Dễ chứng minh; một điểm ghi cho mỗi phòng |
| Optimistic version/CAS trên counter row | UPDATE theo version, kiểm tra số hàng trả về | UPDATE theo version, kiểm tra affected rows | Conflict phải rollback và retry/tính lại |
| SERIALIZABLE | SSI có thể abort transaction | Locking/next-key behavior có thể block/deadlock | Bảo vệ predicate nhưng cần xử lý lỗi concurrency |
| CHECK trên counter row | Ngăn `reserved_count > capacity` trên chính hàng room | Tương tự, CHECK được enforce trong MySQL 8.4 | Lớp bảo vệ bổ sung, không tự tính SUM reservation |

## 13. Kiểm tra ràng buộc và tính nhất quán của counter

Counter-row là một dạng denormalization: cùng một thông tin tổng được lưu ở hàng room và có thể tính lại từ bảng reservation. Điều này tăng hiệu năng điều phối nhưng tạo thêm trách nhiệm duy trì đồng bộ.

Mọi thao tác ảnh hưởng đến tổng phải cập nhật counter trong cùng transaction:

- Tạo reservation: tăng `reserved_count`.
- Hủy reservation: giảm `reserved_count`.
- Sửa số khách: tăng hoặc giảm theo delta.
- Chuyển reservation sang phòng khác: giảm phòng cũ và tăng phòng mới trong cùng transaction.
- Xóa reservation do admin hoặc batch job: cũng phải cập nhật counter.

Ví dụ hủy 2 khách:

```sql
BEGIN;

UPDATE room
SET reserved_count = reserved_count - 2
WHERE room_id = 7
  AND reserved_count >= 2;

-- Chỉ tiếp tục nếu đúng một hàng được cập nhật.
DELETE FROM reservation
WHERE reservation_id = :reservation_id
  AND room_id = 7
  AND guest_count = 2;

-- Kiểm tra số hàng DELETE; nếu không đúng một hàng, rollback.
COMMIT;
```

Trong ứng dụng thực tế, cần lấy `guest_count` từ reservation đã khóa/đọc nhất quán và dùng đúng delta. Ví dụ trên minh họa transaction boundary; không nên tin một giá trị delta do client gửi lên mà không xác nhận từ database.

### Đối soát định kỳ

```sql
SELECT
    r.room_id,
    r.capacity,
    r.reserved_count,
    COALESCE(SUM(x.guest_count), 0) AS calculated_count
FROM room r
LEFT JOIN reservation x ON x.room_id = r.room_id
GROUP BY r.room_id, r.capacity, r.reserved_count
HAVING r.reserved_count <> COALESCE(SUM(x.guest_count), 0)
    OR r.reserved_count > r.capacity;
```

Truy vấn này giúp phát hiện bộ đếm bị lệch. Nó không tự sửa dữ liệu và cũng không thay thế cơ chế concurrency trong đường ghi. Nếu phát hiện lệch, hãy điều tra nguyên nhân trước khi backfill hoặc cập nhật lại counter.

## 14. JDBC: cùng logic ứng dụng, khác cách kiểm tra kết quả

Ở cả hai driver, ứng dụng có thể dùng `PreparedStatement.executeUpdate()` để biết conditional UPDATE tác động bao nhiêu hàng.

```java
public boolean reserve(
        DataSource dataSource,
        long roomId,
        int guests) throws SQLException {

    try (Connection connection = dataSource.getConnection()) {
        connection.setAutoCommit(false);

        try {
            int updated;
            try (PreparedStatement statement = connection.prepareStatement(
                    "UPDATE room " +
                    "SET reserved_count = reserved_count + ? " +
                    "WHERE room_id = ? " +
                    "AND reserved_count + ? <= capacity")) {
                statement.setInt(1, guests);
                statement.setLong(2, roomId);
                statement.setInt(3, guests);
                updated = statement.executeUpdate();
            }

            if (updated != 1) {
                connection.rollback();
                return false;
            }

            try (PreparedStatement statement = connection.prepareStatement(
                    "INSERT INTO reservation(room_id, guest_count) VALUES (?, ?)")) {
                statement.setLong(1, roomId);
                statement.setInt(2, guests);
                statement.executeUpdate();
            }

            connection.commit();
            return true;
        } catch (SQLException | RuntimeException ex) {
            try {
                connection.rollback();
            } catch (SQLException rollbackError) {
                ex.addSuppressed(rollbackError);
            }
            throw ex;
        }
    }
}
```

Đây là logic dùng được cho cả hai schema ở trên. Tên driver URL và pool config khác nhau, nhưng câu UPDATE có điều kiện và transaction boundary tương tự.

Nếu lỗi mạng xảy ra trong `commit()`, lời gọi `rollback()` tiếp theo có thể cũng thất bại và không chứng minh transaction đã rollback. Connection đó phải bị loại khỏi pool. Với thao tác đặt chỗ cần retry an toàn, hãy thêm `request_id` duy nhất vào reservation/operation record và lưu kết quả trong cùng transaction.

## 15. Retry: lỗi concurrency khác với hết chỗ

Ứng dụng cần phân biệt ít nhất ba kết quả:

1. **Không đủ chỗ:** conditional UPDATE tác động 0 hàng. Đây là kết quả nghiệp vụ, không phải lỗi cần retry ngay.
2. **Deadlock/serialization failure/lock timeout:** transaction không hoàn tất vì concurrency. Có thể rollback và retry toàn bộ transaction với giới hạn nếu thao tác an toàn.
3. **Mất kết nối khi COMMIT:** kết quả có thể chưa xác định. Tra cứu bằng request ID hoặc retry cùng idempotency key; không tạo request ID mới cho cùng một ý định.

Một policy retry có thể gồm exponential backoff, jitter, giới hạn số lần và metric theo mã lỗi. Không retry vô hạn vì có thể làm tải tăng thêm khi database đang contention.

Với PostgreSQL, serialization failure thường có SQLSTATE `40001`; deadlock thường có SQLSTATE `40P01`. Với MySQL, deadlock thường là error 1213 và lock wait timeout thường là 1205, nhưng ứng dụng nên phân loại bằng vendor code/SQLState của driver thay vì chỉ so sánh message text.

## 16. Bài thực hành hai session trên PostgreSQL

### Bài A: tái hiện lỗi

1. Reset room 7 về 6 khách và xóa các reservation thêm từ lần chạy trước.
2. Mở hai session psql.
3. Trong A, BEGIN và SELECT SUM; giữ transaction mở.
4. Trong B, BEGIN và SELECT SUM; xác nhận cùng trả 6.
5. B INSERT 3 và COMMIT.
6. A INSERT 3 và COMMIT.
7. Truy vấn tổng; xác nhận có thể bằng 12.

### Bài B: sửa bằng counter row

1. Reset reservation và đặt `room.reserved_count = 6`.
2. A chạy conditional UPDATE tăng 3 và giữ transaction mở.
3. B chạy cùng UPDATE; quan sát B chờ khóa.
4. A INSERT reservation và COMMIT.
5. B tiếp tục; xác nhận UPDATE trả 0 hàng.
6. B không INSERT và kết thúc transaction.
7. Kiểm tra tổng reservation và counter đều bằng 9.

### Bài C: SERIALIZABLE

1. Reset dữ liệu.
2. A và B cùng chạy transaction `SERIALIZABLE`, đọc tổng trước khi ghi.
3. Cho cả hai INSERT rồi commit theo lịch xen kẽ.
4. Xác nhận PostgreSQL có thể hủy một transaction với serialization failure.
5. Retry toàn bộ transaction bị hủy; lần đọc mới thấy tổng 9 và từ chối thêm 3.

## 17. Bài thực hành hai session trên MySQL/InnoDB

### Bài A: tái hiện lỗi ở REPEATABLE READ

1. Reset room 7 về 6 khách.
2. Mở hai connection mysql client.
3. A đặt isolation `REPEATABLE READ`, START TRANSACTION và SELECT SUM.
4. B làm tương tự; cả hai đọc 6.
5. B INSERT 3 và COMMIT.
6. A INSERT 3 và COMMIT.
7. Truy vấn tổng; xác nhận có thể bằng 12.

### Bài B: sửa bằng counter row

1. Reset reservation và đặt `reserved_count = 6`.
2. A START TRANSACTION, conditional UPDATE tăng 3.
3. B START TRANSACTION và chạy cùng UPDATE; quan sát B chờ.
4. A INSERT reservation và COMMIT.
5. B tiếp tục; kiểm tra affected rows bằng 0.
6. B không INSERT và rollback/kết thúc.
7. Kiểm tra tổng reservation và counter đều bằng 9.

### Bài C: SERIALIZABLE

1. Reset dữ liệu.
2. A và B dùng transaction `SERIALIZABLE`, SELECT tổng rồi thử INSERT.
3. Quan sát lock wait hoặc deadlock tùy lịch và index.

Không yêu cầu hai engine phải báo cùng loại lỗi hoặc cùng thời điểm. Mục tiêu là xác nhận bất biến cuối cùng không bị phá vỡ và ứng dụng xử lý đúng kết quả concurrency.

## 18. Những gì cần ghi lại khi so sánh

Để kết quả có thể tái lập, ghi lại:

- Phiên bản chính xác của PostgreSQL, MySQL và JDBC driver.
- MySQL storage engine (`InnoDB`) và PostgreSQL table/index definition.
- Isolation level ở session/transaction thực tế.
- Autocommit, transaction boundaries và số connection.
- Các index liên quan đến `room_id`.
- Durability setting như `synchronous_commit`, `fsync`, `innodb_flush_log_at_trx_commit` và `sync_binlog` nếu bật binlog.
- Thứ tự bắt đầu, đọc, cập nhật và commit của hai session.
- Kết quả từng câu lệnh, affected row count, SQLSTATE/vendor code và thời gian chờ.
- Tổng reservation, counter và kết quả nghiệp vụ sau khi cả hai transaction kết thúc.

Nếu thay đổi isolation level, index, schema, storage engine hoặc autocommit giữa các lần thử, hãy ghi thành một test case riêng. Không so sánh hai lần chạy với nhiều biến thay đổi cùng lúc rồi kết luận nguyên nhân.

## 19. Bảng tổng kết bài toán đặt chỗ

| Câu hỏi | PostgreSQL 16 READ COMMITTED | MySQL 8.4/InnoDB REPEATABLE READ |
| --- | --- | --- |
| Hai transaction cùng SELECT SUM = 6? | Có thể | Có thể |
| Hai transaction INSERT hai reservation riêng và cùng commit? | Có thể nếu không có cơ chế bảo vệ bổ sung | Có thể nếu không có cơ chế bảo vệ bổ sung |
| SELECT thông thường có tự khóa predicate tổng? | Không | Không; consistent read không khóa predicate |
| Conditional UPDATE trên cùng counter row có điều phối? | Có, row lock và kiểm tra điều kiện sau khi chờ | Có, current/locking update và row lock |
| CHECK trên counter row có bảo vệ `reserved_count <= capacity`? | Có | Có trên MySQL 8.4 |
| SERIALIZABLE triển khai giống nhau? | Không; SSI và predicate dependency tracking | Không; locking/next-key semantics |
| Ứng dụng cần retry lỗi concurrency? | Có, toàn bộ transaction khi serialization/deadlock phù hợp | Có, toàn bộ transaction khi deadlock/timeout phù hợp |

## 20. Những điểm cần ghi nhớ

- So sánh concurrency phải ghi rõ phiên bản, storage engine, isolation level, autocommit, transaction boundary và index.
- Cùng bài toán sức chứa 10, đã đặt 6, hai request cùng đặt 3 có thể làm tổng vượt 10 nếu chỉ SELECT SUM rồi INSERT.
- PostgreSQL `READ COMMITTED` dùng snapshot theo statement; InnoDB `REPEATABLE READ` dùng read view cho consistent read trong transaction. Cả hai vẫn có thể gặp write skew trong lịch đọc-tổng-rồi-chèn này.
- `SELECT` thông thường không tự khóa predicate tổng trong hai cấu hình chính của lab.
- Một hàng counter/guard theo room cho phép mọi request cùng phòng tranh chấp trên một hàng có thẩm quyền.
- Conditional UPDATE vừa kiểm tra `reserved_count + request <= capacity` vừa thay đổi counter nguyên tử; request sau phải đánh giá điều kiện trên giá trị hiện hành sau khi chờ.
- Counter update và INSERT reservation phải cùng transaction; INSERT lỗi thì counter cũng phải rollback.
- CHECK bảo vệ giá trị của hàng counter, nhưng không tự tính tổng các hàng reservation.
- `SELECT ... FOR UPDATE` guard có thể dùng được, nhưng phải chú ý snapshot của InnoDB REPEATABLE READ nếu transaction đã có consistent read trước khi lấy guard.
- PostgreSQL SERIALIZABLE dùng SSI và có thể trả SQLSTATE `40001`; InnoDB SERIALIZABLE dùng locking semantics mạnh hơn và có thể chờ/deadlock.
- Retry lỗi concurrency phải chạy lại toàn bộ transaction; không retry riêng INSERT hoặc UPDATE cuối.
- Mất kết nối trong COMMIT là kết quả chưa xác định; dùng request ID/idempotency key để tra cứu hoặc retry an toàn.
- Đối soát `reserved_count` với tổng reservation định kỳ để phát hiện mọi đường ghi đã bỏ qua quy tắc cập nhật counter.
