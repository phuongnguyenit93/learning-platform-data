# CTE trong câu lệnh thay đổi dữ liệu theo phương ngữ

**Common Table Expression (CTE)** là một biểu thức truy vấn được đặt tên bằng mệnh đề `WITH`, giúp chia một câu SQL phức tạp thành những bước dễ đọc. Người mới học thường gặp CTE trong `SELECT`, nhưng CTE cũng rất hữu ích khi **thêm, sửa hoặc xóa dữ liệu** bằng `INSERT`, `UPDATE` và `DELETE`. Chẳng hạn, trước khi cập nhật trạng thái đơn hàng, ta có thể dùng CTE để tính tổng thanh toán của từng đơn, chọn những đơn đạt điều kiện, rồi mới cập nhật những bản ghi tương ứng.

Tuy nhiên, đây là vùng SQL có **khác biệt phương ngữ đáng kể**. PostgreSQL cho phép `WITH` trước nhiều câu lệnh thay đổi dữ liệu và còn hỗ trợ **data-modifying CTE** (CTE chứa chính `INSERT`/`UPDATE`/`DELETE` có `RETURNING`). SQL Server có CTE đứng trước `UPDATE`/`DELETE`/`INSERT` nhưng cú pháp `UPDATE ... FROM`, `OUTPUT` và giới hạn CTE khác PostgreSQL. MySQL 8.0 có CTE trong `UPDATE`/`DELETE` và ở phần truy vấn của `INSERT ... SELECT`, nhưng cú pháp nối bảng và khả năng trả về hàng thay đổi khác. SQLite hỗ trợ `WITH` cho DML cùng một số hạn chế về `RETURNING`. Oracle Database thường dùng CTE trong phần truy vấn nguồn của `MERGE` hoặc các truy vấn con phục vụ DML.

Bài học tập trung vào **cách dùng CTE để thay đổi dữ liệu theo từng phương ngữ**, không chỉ cách viết một `SELECT` có `WITH`. Ví dụ chính dùng PostgreSQL; các phần sau giải thích cách chuyển ý tưởng sang SQL Server, MySQL, SQLite và Oracle, cùng những điểm cần kiểm tra về phiên bản và hành vi giao dịch.

## 1. Ôn lại: CTE là gì và liên quan thế nào đến DML?

Mẫu CTE đọc dữ liệu:

```sql
WITH ten_cte AS (
    SELECT ...
    FROM ...
    WHERE ...
)
SELECT ...
FROM ten_cte;
```

`ten_cte` là tên có hiệu lực trong phạm vi **một câu lệnh SQL**. Nó không phải một bảng được tạo vĩnh viễn và không tự tồn tại cho câu lệnh tiếp theo.

Khi kết hợp với thao tác thay đổi dữ liệu, dạng khái quát thường là:

```sql
WITH candidates AS (
    SELECT khoa_chinh
    FROM bang_nguon
    WHERE dieu_kien
)
UPDATE bang_dich
SET cot_can_sua = gia_tri_moi
WHERE khoa_chinh IN (
    SELECT khoa_chinh FROM candidates
);
```

Ý tưởng gồm hai bước logic:

1. **CTE `candidates`** mô tả tập khóa của các hàng đủ điều kiện.
2. **`UPDATE`** dùng tập khóa đó để xác định những hàng trong bảng đích cần sửa.

Nhưng **cú pháp đặt `WITH`, cú pháp `UPDATE` khi có `JOIN`, cú pháp lấy các hàng vừa thay đổi và quy tắc thực thi** có thể khác nhau theo DBMS. Không nên giả định một câu SQL DML chứa CTE chạy nguyên vẹn trên tất cả hệ quản trị.

### 1.1. Phân biệt CTE đọc dữ liệu và CTE thay đổi dữ liệu

Hai khái niệm cần tách bạch:

| Kiểu sử dụng | Mô tả | Ví dụ |
|---|---|---|
| **CTE SELECT phục vụ DML** | CTE chỉ đọc/tính dữ liệu; `INSERT`, `UPDATE` hoặc `DELETE` ở câu lệnh chính | `WITH totals AS (SELECT ...) UPDATE ...` |
| **Data-modifying CTE** | Bản thân biểu thức bên trong `WITH` chứa lệnh thay đổi dữ liệu; câu lệnh chính có thể đọc hàng do nó trả về | PostgreSQL: `WITH changed AS (UPDATE ... RETURNING ...) SELECT ...` |

Hai kiểu không đồng nghĩa. Việc DBMS hỗ trợ `WITH` trước `UPDATE` **không đảm bảo** nó cũng cho phép `UPDATE` nằm **bên trong CTE**. Khả năng data-modifying CTE của PostgreSQL là một đặc điểm cần được nhận diện riêng.

### 1.2. CTE không thay thế giao dịch

Một câu lệnh SQL thay đổi dữ liệu thường có tính nguyên tử theo quy tắc của DBMS: hoặc thay đổi của câu lệnh được thực hiện, hoặc bị hủy nếu câu lệnh lỗi. Nhưng nếu nghiệp vụ gồm **nhiều câu lệnh** — cập nhật đơn, ghi lịch sử và cập nhật tồn kho — một CTE xuất hiện ở câu lệnh đầu **không tự ràng buộc** các câu lệnh sau vào cùng một giao dịch.

Khi cần nhiều thao tác cùng thành công hoặc cùng thất bại, vẫn phải dùng **transaction** với cách mở, kết thúc và xử lý lỗi phù hợp hệ quản trị. Các ví dụ PostgreSQL bên dưới sử dụng `BEGIN` và `ROLLBACK` để bạn quan sát tác động mà không làm biến đổi vĩnh viễn dữ liệu mẫu.

## 2. Tạo dữ liệu mẫu để thực hành an toàn

Ví dụ dưới đây có ba bảng:

- `orders_demo`: **một hàng mỗi đơn**, có số tiền cần thu và trạng thái.
- `payments_demo`: **nhiều thanh toán mỗi đơn**, phân biệt tiền đã ghi nhận (`CAPTURED`), đang chờ (`PENDING`) và thất bại (`FAILED`).
- `review_queue_demo`: danh sách đơn cần kiểm tra thủ công.

Chạy trong **database học tập riêng** bằng PostgreSQL, không thực hiện trên bảng sản xuất.

### 2.1. Tạo bảng

```sql
CREATE TABLE orders_demo (
    order_id INTEGER PRIMARY KEY,
    customer_id INTEGER NOT NULL,
    ordered_on DATE NOT NULL,
    status VARCHAR(20) NOT NULL
        CHECK (status IN ('NEW', 'PAID', 'CANCELLED')),
    order_total NUMERIC(12, 2) NOT NULL
        CHECK (order_total >= 0)
);

CREATE TABLE payments_demo (
    payment_id INTEGER PRIMARY KEY,
    order_id INTEGER NOT NULL REFERENCES orders_demo(order_id),
    payment_status VARCHAR(20) NOT NULL
        CHECK (payment_status IN ('CAPTURED', 'PENDING', 'FAILED')),
    amount NUMERIC(12, 2) NOT NULL
        CHECK (amount >= 0)
);

CREATE TABLE review_queue_demo (
    order_id INTEGER PRIMARY KEY REFERENCES orders_demo(order_id),
    reason VARCHAR(60) NOT NULL
);
```

Mỗi bảng có một mức chi tiết (*grain*) khác nhau. Cột `payments_demo.order_id` **không duy nhất**, vì một đơn có thể có nhiều bản ghi thanh toán. Khi cập nhật `orders_demo` bằng thông tin từ `payments_demo`, phải tránh để một đơn có nhiều dòng nguồn khiến kết quả khó xác định.

### 2.2. Nạp dữ liệu

```sql
INSERT INTO orders_demo
    (order_id, customer_id, ordered_on, status, order_total)
VALUES
    (101, 1, DATE '2025-01-05', 'NEW',       200000.00),
    (102, 1, DATE '2025-01-06', 'NEW',       100000.00),
    (103, 2, DATE '2025-01-07', 'PAID',      120000.00),
    (104, 2, DATE '2025-01-08', 'NEW',            0.00),
    (105, 3, DATE '2025-01-09', 'CANCELLED',  50000.00),
    (106, 3, DATE '2025-02-01', 'NEW',       300000.00),
    (107, 4, DATE '2025-02-02', 'NEW',       100000.00);

INSERT INTO payments_demo
    (payment_id, order_id, payment_status, amount)
VALUES
    (1001, 101, 'CAPTURED', 200000.00),
    (1002, 101, 'FAILED',   200000.00),
    (1003, 102, 'PENDING',  100000.00),
    (1004, 103, 'CAPTURED', 120000.00),
    (1005, 106, 'CAPTURED', 300000.00),
    (1006, 107, 'CAPTURED',  50000.00);

INSERT INTO review_queue_demo (order_id, reason)
VALUES
    (105, 'LEGACY_CANCELLED'),
    (106, 'MANUAL_CHECK');
```

**Tập đơn hàng ban đầu:**

| order_id | ordered_on | status | order_total | Tình huống |
|---:|---|---|---:|---|
| 101 | 2025-01-05 | NEW | 200.000 | Đã ghi nhận đủ 200.000; có thêm một lần thanh toán thất bại |
| 102 | 2025-01-06 | NEW | 100.000 | Mới có thanh toán PENDING |
| 103 | 2025-01-07 | PAID | 120.000 | Đã PAID |
| 104 | 2025-01-08 | NEW | 0 | Không có thanh toán |
| 105 | 2025-01-09 | CANCELLED | 50.000 | Đã hủy |
| 106 | 2025-02-01 | NEW | 300.000 | Đã ghi nhận đủ 300.000 |
| 107 | 2025-02-02 | NEW | 100.000 | Mới ghi nhận 50.000 |

Với dữ liệu này, những đơn `NEW` **có tổng thanh toán `CAPTURED` ít nhất bằng số tiền cần thu và tổng tiền đơn dương** là **101 và 106**. Đó sẽ là kết quả kỳ vọng khi ta dùng CTE để cập nhật trạng thái.

### 2.3. Quy ước thực hành

Các đoạn thay đổi dữ liệu trong bài được thiết kế thành **những ví dụ độc lập**. Trong PostgreSQL, bạn có thể bao mỗi ví dụ bằng:

```sql
BEGIN;

-- Đặt lệnh thử nghiệm ở đây.
-- SELECT để quan sát dữ liệu ngay trong giao dịch.

ROLLBACK;
```

`ROLLBACK` hủy những thay đổi chưa `COMMIT` của giao dịch; sau đó dữ liệu trở về trạng thái trước khi thử. **Nếu bạn chạy `COMMIT` thay `ROLLBACK`, các ví dụ về sau có thể cho kết quả khác** vì trạng thái đã đổi hoặc dòng đã bị xóa. Không chạy lại các lệnh `CREATE TABLE`/`INSERT` khởi tạo trên bảng đã tồn tại nếu chưa có kế hoạch đặt lại dữ liệu.

## 3. PostgreSQL: WITH ... UPDATE ... FROM

Nhu cầu: **Đổi trạng thái từ `NEW` thành `PAID` cho các đơn có tổng tiền thanh toán đã ghi nhận đủ**, trong khi vẫn loại đơn đã hủy, đơn đã thanh toán và đơn có tổng tiền bằng 0.

Thay vì nối trực tiếp mọi dòng `payments_demo`, hãy tạo CTE tổng hợp về **một hàng cho mỗi đơn**:

```sql
WITH captured_by_order AS (
    SELECT
        p.order_id,
        SUM(p.amount) AS captured_amount
    FROM payments_demo AS p
    WHERE p.payment_status = 'CAPTURED'
    GROUP BY p.order_id
)
SELECT
    o.order_id,
    o.status,
    o.order_total,
    c.captured_amount
FROM orders_demo AS o
JOIN captured_by_order AS c
    ON c.order_id = o.order_id
WHERE o.status = 'NEW'
  AND o.order_total > 0
  AND c.captured_amount >= o.order_total
ORDER BY o.order_id;
```

Kết quả truy vấn xem trước:

| order_id | status | order_total | captured_amount |
|---:|---|---:|---:|
| 101 | NEW | 200000.00 | 200000.00 |
| 106 | NEW | 300000.00 | 300000.00 |

Khi đã xác nhận điều kiện, áp dụng cùng logic cho `UPDATE`:

```sql
BEGIN;

WITH captured_by_order AS (
    SELECT
        p.order_id,
        SUM(p.amount) AS captured_amount
    FROM payments_demo AS p
    WHERE p.payment_status = 'CAPTURED'
    GROUP BY p.order_id
)
UPDATE orders_demo AS o
SET status = 'PAID'
FROM captured_by_order AS c
WHERE c.order_id = o.order_id
  AND o.status = 'NEW'
  AND o.order_total > 0
  AND c.captured_amount >= o.order_total
RETURNING o.order_id, o.status, o.order_total;

-- Chỉ để xem kết quả trong giao dịch:
SELECT order_id, status
FROM orders_demo
ORDER BY order_id;

ROLLBACK;
```

Lệnh `UPDATE ... RETURNING` trả về **hai đơn 101 và 106** với trạng thái mới `PAID`. `ROLLBACK` ở cuối giữ lại dữ liệu mẫu ban đầu.

### 3.1. CTE mô tả nguồn, UPDATE xác định đích

Phân biệt vai trò từng phần:

```text
payments_demo
    |
    | lọc payment_status = 'CAPTURED'
    | GROUP BY order_id + SUM(amount)
    v
captured_by_order (một hàng mỗi đơn đã có thanh toán CAPTURED)
    |
    | ghép order_id và kiểm tra điều kiện
    v
UPDATE orders_demo (chỉ những đơn NEW đủ tiền)
    |
    v
RETURNING (các hàng đã được cập nhật)
```

CTE `captured_by_order` chỉ là truy vấn tạo nguồn tính toán. **Hành động sửa dữ liệu nằm ở `UPDATE orders_demo`**, không phải trong chính CTE.

### 3.2. Vì sao phải tổng hợp trước khi UPDATE FROM?

Nếu nối trực tiếp bảng thanh toán mà một đơn có nhiều dòng `CAPTURED`, một hàng đích có thể khớp **nhiều hàng nguồn**. Trong PostgreSQL, khi `UPDATE ... FROM` cho một hàng đích khớp nhiều hàng nguồn, việc chọn hàng nguồn để tính biểu thức `SET` có thể không dự đoán được. Tương tự, một số DBMS cũng cảnh báo hoặc có quy tắc riêng cho cập nhật không xác định.

Việc `GROUP BY p.order_id` bảo đảm CTE có **tối đa một hàng mỗi `order_id`**, giúp điều kiện ghép và các giá trị nguồn rõ ràng. Với bản ghi thanh toán thực tế, còn phải bảo đảm mỗi khoản `CAPTURED` được ghi nhận đúng một lần theo **mã giao dịch thanh toán duy nhất**; CTE không tự sửa lỗi trùng giao dịch trong dữ liệu nguồn.

### 3.3. Không chuyển CTE thành bảng tạm chỉ để sử dụng một lần

Một CTE thông thường có phạm vi **một câu lệnh**. Trong PostgreSQL, bộ tối ưu có thể gộp hoặc vật chất hóa (*materialize*) CTE đọc dữ liệu tùy thuộc cấu trúc và tình huống; không nên coi mọi CTE là bảng tạm đã được lưu sẵn.

Nếu cần dùng cùng tập `captured_by_order` cho **nhiều câu lệnh** hoặc cần một ảnh chụp dữ liệu được quản lý riêng, có thể cân nhắc bảng tạm, bảng staging hoặc một giao dịch có mức cô lập phù hợp. CTE bản thân nó **không giữ kết quả qua những câu SQL độc lập**.

## 4. PostgreSQL: WITH ... INSERT ... SELECT

CTE cũng có ích khi cần **chọn dữ liệu đủ điều kiện để chèn vào bảng khác**. Ví dụ, muốn đưa những đơn `NEW` đã tồn tại trước tháng 2/2025 vào hàng chờ kiểm tra thủ công.

CTE `old_new_orders` mô tả tập đơn nguồn; `INSERT ... SELECT` chèn mã đơn và lý do:

```sql
BEGIN;

WITH old_new_orders AS (
    SELECT o.order_id
    FROM orders_demo AS o
    WHERE o.status = 'NEW'
      AND o.ordered_on < DATE '2025-02-01'
)
INSERT INTO review_queue_demo (order_id, reason)
SELECT src.order_id, 'OLD_NEW'
FROM old_new_orders AS src
WHERE NOT EXISTS (
    SELECT 1
    FROM review_queue_demo AS q
    WHERE q.order_id = src.order_id
)
RETURNING order_id, reason;

SELECT order_id, reason
FROM review_queue_demo
ORDER BY order_id;

ROLLBACK;
```

Nếu chạy từ dữ liệu ban đầu, các hàng được chèn là **101, 102 và 104** với lý do `OLD_NEW`. Hàng 105 là `CANCELLED` nên không đủ điều kiện; hàng 106 và 107 ở tháng 2 nên không phải đơn cũ; hàng 103 đã `PAID`.

Điều kiện `NOT EXISTS` tránh chèn lại những đơn đã có trong `review_queue_demo` ở **trạng thái dữ liệu hiện tại**, nhưng nó **không thay thế** ràng buộc duy nhất khi có nhiều phiên ghi đồng thời. `review_queue_demo.order_id` là khóa chính; PostgreSQL còn có thể sử dụng `ON CONFLICT (order_id) DO NOTHING` khi nghiệp vụ cho phép bỏ qua bản ghi trùng. Trong ứng dụng thật cần xác định cách xử lý xung đột khóa một cách có chủ đích.

**Điểm cần phân biệt:** CTE ở đây là `SELECT`; lệnh `INSERT` chính tạo bản ghi mới. `RETURNING` trả các hàng thật sự được chèn vào bảng đích, không phải toàn bộ hàng mà CTE có thể tìm thấy.

## 5. PostgreSQL: WITH ... DELETE ... USING

Khi xóa dữ liệu, CTE có thể giúp **xác định chính xác tập khóa cần loại bỏ** trước khi thực hiện hành động. Giả sử `review_queue_demo` có một hàng cũ của đơn đã hủy; ta muốn xóa mục đó khỏi hàng chờ kiểm tra, nhưng **không xóa chính đơn hàng**.

Xem trước tập cần xóa:

```sql
WITH cancelled_orders AS (
    SELECT order_id
    FROM orders_demo
    WHERE status = 'CANCELLED'
)
SELECT q.order_id, q.reason
FROM review_queue_demo AS q
JOIN cancelled_orders AS c
    ON c.order_id = q.order_id
ORDER BY q.order_id;
-- order_id = 105, reason = LEGACY_CANCELLED
```

Xóa bằng `DELETE ... USING` của PostgreSQL:

```sql
BEGIN;

WITH cancelled_orders AS (
    SELECT o.order_id
    FROM orders_demo AS o
    WHERE o.status = 'CANCELLED'
)
DELETE FROM review_queue_demo AS q
USING cancelled_orders AS c
WHERE c.order_id = q.order_id
RETURNING q.order_id, q.reason;

SELECT order_id, reason
FROM review_queue_demo
ORDER BY order_id;

ROLLBACK;
```

`DELETE ... RETURNING` cho **mục hàng chờ 105**. Các đơn trong `orders_demo` vẫn còn; thao tác chỉ xóa **dòng ở bảng `review_queue_demo`**. Sau `ROLLBACK`, bản ghi 105 của hàng chờ trở lại.

Một cách ít phụ thuộc cú pháp nối của từng DBMS là dùng `WHERE EXISTS` hoặc `WHERE order_id IN (SELECT ...)` từ CTE:

```sql
WITH cancelled_orders AS (
    SELECT order_id
    FROM orders_demo
    WHERE status = 'CANCELLED'
)
DELETE FROM review_queue_demo
WHERE order_id IN (
    SELECT order_id FROM cancelled_orders
);
```

Ví dụ trên **thực sự xóa dữ liệu** nếu bạn chạy ngoài giao dịch rollback, vì vậy nên bao trong `BEGIN ... ROLLBACK` khi thử nghiệm. Cần dùng `DELETE` đúng bảng đích: thay nhầm tên bảng có thể gây mất dữ liệu quan trọng.

## 6. PostgreSQL nâng cao: CTE chứa chính DML với RETURNING

Cho đến đây, mỗi CTE đều chỉ có `SELECT`. PostgreSQL còn hỗ trợ **data-modifying CTE**: đặt một câu `INSERT`, `UPDATE` hoặc `DELETE` trong `WITH` và sử dụng những hàng mà lệnh đó trả về bằng `RETURNING`.

Ví dụ: cập nhật một đơn cụ thể, đồng thời trả về chính xác hàng đã cập nhật qua tên CTE:

```sql
BEGIN;

WITH changed_orders AS (
    UPDATE orders_demo
    SET status = 'PAID'
    WHERE order_id = 101
      AND status = 'NEW'
    RETURNING order_id, customer_id, status, order_total
)
SELECT order_id, customer_id, status, order_total
FROM changed_orders;
-- Một hàng: order_id 101, status PAID

ROLLBACK;
```

Khác với `WITH candidates AS (SELECT ...) UPDATE ...`:

1. `changed_orders` **thực hiện `UPDATE`**, không chỉ tính danh sách ứng viên.
2. `RETURNING` tạo một tập hàng từ thao tác vừa thực hiện.
3. `SELECT FROM changed_orders` dùng chính tập hàng đó như nguồn.

Nếu điều kiện cập nhật không khớp hàng nào, `changed_orders` không trả hàng nào, nhưng cú pháp vẫn hợp lệ.

### 6.1. Ví dụ ghi log sau khi UPDATE trong cùng câu lệnh

Giả sử hệ thống có bảng nhật ký dành cho bài thực hành:

```sql
CREATE TABLE status_change_log_demo (
    log_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_id INTEGER NOT NULL,
    new_status VARCHAR(20) NOT NULL,
    recorded_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

Ta có thể dùng kết quả `RETURNING` của CTE thay đổi dữ liệu làm nguồn cho một `INSERT` chính:

```sql
BEGIN;

WITH changed_orders AS (
    UPDATE orders_demo
    SET status = 'PAID'
    WHERE order_id = 101
      AND status = 'NEW'
    RETURNING order_id, status
)
INSERT INTO status_change_log_demo (order_id, new_status)
SELECT order_id, status
FROM changed_orders
RETURNING log_id, order_id, new_status, recorded_at;

ROLLBACK;
```

Trong PostgreSQL, câu lệnh trên có thể:

- Cập nhật trạng thái đơn 101.
- Lấy hàng vừa cập nhật từ `RETURNING`.
- Chèn một bản ghi log có `new_status = 'PAID'`.
- Trả về dòng log mới.

Các thao tác này nằm trong **một câu lệnh SQL** và giao dịch thực hành, nên `ROLLBACK` hủy cả thay đổi đơn lẫn dòng log chưa commit. Đây là một trường hợp PostgreSQL thực sự khác các DBMS chỉ hỗ trợ CTE đọc dữ liệu phục vụ DML.

### 6.2. Không dùng data-modifying CTE như cơ chế chạy tuần tự mọi thao tác

Data-modifying CTE của PostgreSQL có các quy tắc cần nhớ:

- CTE chứa lệnh thay đổi dữ liệu cần đặt trong ngữ cảnh được PostgreSQL cho phép, thường gắn với câu lệnh cấp cao nhất.
- Kênh truyền dữ liệu đáng tin cậy từ một lệnh thay đổi trong CTE sang lệnh chính là **kết quả `RETURNING`**.
- Các lệnh thay đổi dữ liệu bên trong một `WITH` có thể dùng **cùng snapshot**, và **thứ tự cập nhật giữa những tác vụ độc lập không được đảm bảo**. Không suy ra rằng CTE viết trước thì luôn “chạy xong hoàn toàn rồi câu sau mới nhìn thấy bảng đã đổi” qua một truy vấn trực tiếp đến bảng đích.
- **Không cố sửa cùng một hàng bằng hai thao tác khác nhau trong cùng một câu lệnh** rồi mong DBMS chọn thứ tự như một chương trình tuần tự; kết quả có thể không được hỗ trợ hoặc không dự đoán được.
- CTE DML **không đồng nghĩa với bảng tạm** và không tự làm các tác vụ bên ngoài câu lệnh trở nên nguyên tử.

Khi cần nhiều bước có thứ tự rõ ràng và phụ thuộc trạng thái bảng sau từng bước, một **giao dịch gồm nhiều câu lệnh** thường dễ kiểm soát hơn việc nhồi mọi thay đổi vào một `WITH` phức tạp.

## 7. SQL Server: CTE trước UPDATE, DELETE và INSERT

SQL Server dùng `WITH cte_name AS (...)`, nhưng có những khác biệt quan trọng:

- CTE thường áp dụng cho **câu lệnh ngay sau nó**, ví dụ một `SELECT`, `INSERT`, `UPDATE`, `DELETE` hoặc `MERGE`.
- Khi `WITH` không phải đầu tiên của một batch, **câu lệnh trước nó cần được kết thúc** bằng dấu chấm phẩy; vì thế nhiều ví dụ viết `;WITH`.
- SQL Server có `UPDATE ... FROM` với cú pháp khác PostgreSQL.
- Để lấy những hàng trước/sau thay đổi, SQL Server dùng **`OUTPUT deleted...` và `OUTPUT inserted...`** thay vì cú pháp PostgreSQL `RETURNING`.

### 7.1. SQL Server: cập nhật từ CTE tổng hợp

Ví dụ tương đương về ý tưởng với mục 3, giả sử ba bảng mẫu đã tồn tại trên SQL Server với các cột tương ứng:

```sql
-- SQL Server
;WITH captured_by_order AS (
    SELECT
        p.order_id,
        SUM(p.amount) AS captured_amount
    FROM dbo.payments_demo AS p
    WHERE p.payment_status = 'CAPTURED'
    GROUP BY p.order_id
)
UPDATE o
SET status = 'PAID'
OUTPUT
    inserted.order_id,
    deleted.status AS old_status,
    inserted.status AS new_status
FROM dbo.orders_demo AS o
JOIN captured_by_order AS c
    ON c.order_id = o.order_id
WHERE o.status = 'NEW'
  AND o.order_total > 0
  AND c.captured_amount >= o.order_total;
```

Ở SQL Server, `UPDATE o` chỉ định alias bảng cần sửa, còn `FROM dbo.orders_demo AS o JOIN ...` cung cấp tập nguồn nối. `OUTPUT inserted...`/`deleted...` có thể trả trạng thái mới và cũ của **hàng được cập nhật**.

Điểm chung với PostgreSQL: CTE chỉ còn **một hàng mỗi đơn** nhờ `GROUP BY`, nên việc nối và cập nhật dễ xác định.

### 7.2. SQL Server: DELETE với CTE

```sql
-- SQL Server: ví dụ xóa hàng chờ của đơn đã hủy
;WITH cancelled_orders AS (
    SELECT order_id
    FROM dbo.orders_demo
    WHERE status = 'CANCELLED'
)
DELETE q
OUTPUT deleted.order_id, deleted.reason
FROM dbo.review_queue_demo AS q
JOIN cancelled_orders AS c
    ON c.order_id = q.order_id;
```

Đây không phải `DELETE ... USING` như PostgreSQL. Alias `q` xác định bảng bị xóa; `OUTPUT deleted...` trả dữ liệu của dòng bị xóa.

### 7.3. SQL Server: INSERT từ CTE

```sql
-- SQL Server
;WITH old_new_orders AS (
    SELECT order_id
    FROM dbo.orders_demo
    WHERE status = 'NEW'
      AND ordered_on < '2025-02-01'
)
INSERT INTO dbo.review_queue_demo (order_id, reason)
OUTPUT inserted.order_id, inserted.reason
SELECT s.order_id, 'OLD_NEW'
FROM old_new_orders AS s
WHERE NOT EXISTS (
    SELECT 1
    FROM dbo.review_queue_demo AS q
    WHERE q.order_id = s.order_id
);
```

Ở SQL Server, `OUTPUT` của `INSERT` xuất hiện **sau danh sách cột đích và trước `SELECT` nguồn**. Câu trên dùng literal ngày `'2025-02-01'` trong ngữ cảnh cột `DATE`; khi viết ứng dụng nên truyền tham số ngày đúng kiểu, không dựa vào định dạng ngày mơ hồ.

### 7.4. Có thể cập nhật qua chính CTE không?

SQL Server cho phép một số CTE đơn giản, có thể cập nhật được, làm **đích trực tiếp** của `UPDATE`:

```sql
-- SQL Server: CTE đơn giản chọn hàng từ một bảng
;WITH to_update AS (
    SELECT order_id, status
    FROM dbo.orders_demo
    WHERE order_id = 101
      AND status = 'NEW'
)
UPDATE to_update
SET status = 'PAID';
```

Cách này phù hợp khi CTE có cấu trúc thỏa quy tắc **updatable view/CTE** của SQL Server. Không phải mọi CTE có `JOIN`, `GROUP BY`, phép tổng hợp hay `DISTINCT` đều có thể được cập nhật trực tiếp. Đặc biệt, `UPDATE to_update` không tương đương PostgreSQL cho phép đặt lệnh `UPDATE` **bên trong** `WITH` và dùng `RETURNING`.

**Ghi nhớ:** SQL Server có cách chọn CTE là đích của một lệnh UPDATE trong những trường hợp phù hợp, nhưng **không có cùng mô hình data-modifying CTE kiểu `WITH changed AS (UPDATE ... RETURNING ...)` của PostgreSQL**.

## 8. MySQL 8.0: WITH trong UPDATE/DELETE và INSERT ... SELECT

MySQL 8.0 hỗ trợ CTE, nhưng **phiên bản cụ thể** và vị trí `WITH` trong cấu trúc DML cần được kiểm tra. Đặc biệt, không thể chuyển thẳng mọi câu `UPDATE ... FROM` của PostgreSQL sang MySQL vì MySQL thường sử dụng cú pháp **`UPDATE ... JOIN ... SET`**.

### 8.1. MySQL: UPDATE ... JOIN với CTE

```sql
-- MySQL 8.0
WITH captured_by_order AS (
    SELECT
        p.order_id,
        SUM(p.amount) AS captured_amount
    FROM payments_demo AS p
    WHERE p.payment_status = 'CAPTURED'
    GROUP BY p.order_id
)
UPDATE orders_demo AS o
JOIN captured_by_order AS c
    ON c.order_id = o.order_id
SET o.status = 'PAID'
WHERE o.status = 'NEW'
  AND o.order_total > 0
  AND c.captured_amount >= o.order_total;
```

Điểm khác PostgreSQL: `JOIN` nằm ngay sau bảng đích `orders_demo`, và `SET` xuất hiện **sau phần nối**. Với dữ liệu mẫu, ý tưởng cập nhật vẫn chọn các đơn **101 và 106**.

MySQL còn có những giới hạn liên quan việc tham chiếu bảng đang được cập nhật trong truy vấn con hoặc CTE cùng câu lệnh; cách xử lý có thể phụ thuộc **hình thức truy vấn, việc vật chất hóa CTE/derived table và phiên bản**. Không giả định mọi cách viết `WITH ... UPDATE` trên một bảng cũng giải quyết tự động lỗi “không thể cập nhật và đọc cùng bảng trong subquery”. Ví dụ ở đây tính toán từ **bảng `payments_demo` riêng**, nên không dựa trên việc đọc lại chính bảng đích trong CTE.

### 8.2. MySQL: DELETE dùng CTE làm tập khóa

```sql
-- MySQL 8.0
WITH cancelled_orders AS (
    SELECT order_id
    FROM orders_demo
    WHERE status = 'CANCELLED'
)
DELETE q
FROM review_queue_demo AS q
JOIN cancelled_orders AS c
    ON c.order_id = q.order_id;
```

MySQL có dạng **multi-table DELETE** (xóa một hoặc nhiều bảng được chỉ định, dù nguồn nối nhiều bảng). `DELETE q FROM ... JOIN ...` ở ví dụ này chỉ xóa **bảng có alias `q`**, không xóa `orders_demo`. Không sao chép cú pháp `DELETE ... USING` của PostgreSQL sang MySQL.

### 8.3. MySQL: INSERT ... SELECT với CTE trong phần SELECT

Với `INSERT ... SELECT`, vị trí `WITH` trong MySQL thường nằm **ở phần nguồn `SELECT`**:

```sql
-- MySQL 8.0
INSERT INTO review_queue_demo (order_id, reason)
WITH old_new_orders AS (
    SELECT order_id
    FROM orders_demo
    WHERE status = 'NEW'
      AND ordered_on < '2025-02-01'
)
SELECT s.order_id, 'OLD_NEW'
FROM old_new_orders AS s
WHERE NOT EXISTS (
    SELECT 1
    FROM review_queue_demo AS q
    WHERE q.order_id = s.order_id
);
```

Đây là một khác biệt cần nhớ so với kiểu `WITH ... INSERT INTO ... SELECT` của PostgreSQL và SQL Server. MySQL không cung cấp cú pháp `RETURNING` tổng quát cho `INSERT`/`UPDATE`/`DELETE` như PostgreSQL; ứng dụng có thể cần đọc số hàng bị ảnh hưởng hoặc thực hiện truy vấn kiểm tra bổ sung trong giao dịch.

### 8.4. Lưu ý giao dịch MySQL

Với InnoDB, các lệnh DML thông thường có thể đặt trong giao dịch:

```sql
START TRANSACTION;

-- Một lệnh WITH ... UPDATE/DELETE hay INSERT ... SELECT.

ROLLBACK;
```

Đừng đồng nhất quy tắc transaction của MySQL với PostgreSQL: một số lệnh **DDL** như `CREATE TABLE` có cơ chế implicit commit, không nên đưa vào một khối thử nghiệm và cho rằng `ROLLBACK` sẽ hủy luôn thao tác tạo bảng. Hãy tạo bảng mẫu trước, rồi dùng transaction cho các ví dụ DML.

## 9. SQLite: WITH ... UPDATE/DELETE/INSERT và RETURNING

SQLite hỗ trợ CTE trong các câu lệnh thay đổi dữ liệu. Tuy nhiên, khi chuyển ví dụ, hãy chú ý:

- SQLite có thể dùng `WITH ... UPDATE`, `WITH ... DELETE`, `WITH ... INSERT`.
- SQLite hỗ trợ `UPDATE ... FROM` ở các phiên bản tương đối mới, nhưng cách viết dùng `WHERE EXISTS` thường minh bạch và dễ đối chiếu hơn.
- `RETURNING` xuất hiện ở SQLite từ **3.35.0**; ứng dụng dùng SQLite cũ hơn cần phương án khác.
- SQLite **không cho phép** dùng `INSERT`/`UPDATE`/`DELETE ... RETURNING` như một subquery hay **CTE chứa DML** theo kiểu PostgreSQL.

### 9.1. SQLite: cập nhật bằng EXISTS tham chiếu CTE

```sql
-- SQLite, cần phiên bản hỗ trợ RETURNING nếu giữ dòng cuối.
WITH captured_by_order AS (
    SELECT
        p.order_id,
        SUM(p.amount) AS captured_amount
    FROM payments_demo AS p
    WHERE p.payment_status = 'CAPTURED'
    GROUP BY p.order_id
)
UPDATE orders_demo
SET status = 'PAID'
WHERE status = 'NEW'
  AND order_total > 0
  AND EXISTS (
      SELECT 1
      FROM captured_by_order AS c
      WHERE c.order_id = orders_demo.order_id
        AND c.captured_amount >= orders_demo.order_total
  )
RETURNING order_id, status, order_total;
```

Ví dụ này chỉ cập nhật **101 và 106** khi dữ liệu ở trạng thái ban đầu. Thay vì `UPDATE ... JOIN`, điều kiện `EXISTS` xác định hàng đích có một bản ghi CTE phù hợp hay không.

### 9.2. SQLite: INSERT từ CTE

```sql
-- SQLite
WITH old_new_orders AS (
    SELECT order_id
    FROM orders_demo
    WHERE status = 'NEW'
      AND ordered_on < '2025-02-01'
)
INSERT INTO review_queue_demo (order_id, reason)
SELECT s.order_id, 'OLD_NEW'
FROM old_new_orders AS s
WHERE NOT EXISTS (
    SELECT 1
    FROM review_queue_demo AS q
    WHERE q.order_id = s.order_id
)
RETURNING order_id, reason;
```

Lệnh `RETURNING` ở trên chỉ dùng được trên các phiên bản SQLite hỗ trợ. Nếu phiên bản không hỗ trợ, bỏ phần `RETURNING` và dùng một `SELECT` riêng để quan sát kết quả. Dữ liệu mẫu SQLite cũng cần được tạo bằng những kiểu dữ liệu và ràng buộc phù hợp với SQLite; không sao chép nguyên từng đặc điểm kiểu của PostgreSQL rồi mặc định có cùng kiểm tra kiểu.

### 9.3. SQLite: DELETE từ CTE

```sql
-- SQLite
WITH cancelled_orders AS (
    SELECT order_id
    FROM orders_demo
    WHERE status = 'CANCELLED'
)
DELETE FROM review_queue_demo
WHERE order_id IN (
    SELECT order_id FROM cancelled_orders
)
RETURNING order_id, reason;
```

`WITH` giúp đặt tên tập khóa cần xóa; `DELETE` vẫn là câu lệnh chính. Không nhầm với PostgreSQL cho phép `WITH deleted_rows AS (DELETE ... RETURNING ...) SELECT ...`.

## 10. Oracle Database: CTE trong nguồn SELECT hoặc MERGE

Oracle có cú pháp và tính năng DML khác PostgreSQL. Một hướng thường gặp là đặt CTE **trong truy vấn nguồn** cho một câu `MERGE` hoặc trong một truy vấn con phục vụ `UPDATE`/`DELETE`. Không nên tự động đặt `WITH` ở trước mọi câu DML Oracle rồi giả định cú pháp tương thích với PostgreSQL, nhất là nếu phải hỗ trợ nhiều phiên bản Oracle.

### 10.1. MERGE dùng nguồn là truy vấn có CTE

Ví dụ ý tưởng cập nhật các đơn đã thanh toán đủ tiền:

```sql
-- Oracle: CTE trong truy vấn nguồn của MERGE
MERGE INTO orders_demo o
USING (
    WITH captured_by_order AS (
        SELECT
            p.order_id,
            SUM(p.amount) AS captured_amount
        FROM payments_demo p
        WHERE p.payment_status = 'CAPTURED'
        GROUP BY p.order_id
    )
    SELECT order_id, captured_amount
    FROM captured_by_order
) c
ON (c.order_id = o.order_id)
WHEN MATCHED THEN
    UPDATE SET o.status = 'PAID'
    WHERE o.status = 'NEW'
      AND o.order_total > 0
      AND c.captured_amount >= o.order_total;
```

Ở đây `MERGE` là **lệnh chính**; CTE tạo nguồn `captured_by_order` từ thanh toán đã ghi nhận. Vì dữ liệu nguồn được nhóm theo `order_id`, mỗi đơn đích có tối đa một hàng nguồn tương ứng.

Không mặc định mọi `MERGE` đều là “upsert”: ví dụ trên **chỉ có nhánh `WHEN MATCHED THEN UPDATE`**, không có `INSERT`. Các phiên bản và tính năng Oracle có thể khác nhau về cú pháp `MERGE`/`RETURNING`, nên kiểm tra tài liệu đúng phiên bản khi triển khai thật.

### 10.2. UPDATE dùng điều kiện EXISTS với CTE trong subquery

Một cách diễn đạt cùng ý tưởng là dùng truy vấn con có `WITH` để tính dữ liệu liên quan:

```sql
-- Oracle: WITH là phần của SELECT nằm trong EXISTS
UPDATE orders_demo o
SET status = 'PAID'
WHERE o.status = 'NEW'
  AND o.order_total > 0
  AND EXISTS (
      WITH captured_by_order AS (
          SELECT order_id, SUM(amount) AS captured_amount
          FROM payments_demo
          WHERE payment_status = 'CAPTURED'
          GROUP BY order_id
      )
      SELECT 1
      FROM captured_by_order c
      WHERE c.order_id = o.order_id
        AND c.captured_amount >= o.order_total
  );
```

Đây vẫn là một câu `UPDATE`; CTE chỉ thuộc **truy vấn `SELECT` bên trong `EXISTS`**. Đoạn này minh họa cấu trúc dành cho Oracle, không phải cú pháp `UPDATE ... FROM` của PostgreSQL hay `UPDATE ... JOIN` của MySQL.

### 10.3. Tránh suy diễn sai từ WITH của Oracle

Một số khác biệt cần ghi nhớ:

- Nhiều ví dụ Oracle đặt `WITH` trong một **truy vấn `SELECT`**, gồm nguồn `MERGE` hoặc truy vấn con dùng để lọc/update.
- `MERGE` có điều kiện ghép và các quy tắc riêng; một hàng đích được nhiều hàng nguồn khớp có thể gây lỗi hoặc kết quả không hợp lệ theo ràng buộc của DBMS. Tổng hợp hoặc khử trùng đúng khóa trước khi `MERGE` rất quan trọng.
- Khả năng trả về bản ghi bị thay đổi khác `RETURNING` của PostgreSQL; không sao chép mẫu **data-modifying CTE** của PostgreSQL như thể đó là SQL chung.
- Cần xét phiên bản Oracle, cấu trúc truy vấn con, điều kiện ghép và quy tắc transaction cụ thể.

Trong các hệ quản trị có cú pháp update-join khác nhau, **thay đổi nguồn tính toán bằng CTE** là ý tưởng chung; **lệnh DML bao quanh** phải viết lại đúng phương ngữ.

## 11. Bảng đối chiếu phương ngữ

| Nhu cầu | PostgreSQL | SQL Server | MySQL 8.0 | SQLite | Oracle |
|---|---|---|---|---|---|
| `WITH` phục vụ cập nhật | `WITH ... UPDATE ... FROM ...` | `;WITH ... UPDATE alias SET ... FROM ...` | `WITH ... UPDATE t JOIN ... SET ...` | `WITH ... UPDATE ... WHERE EXISTS (...)` | Thường dùng `WITH` trong nguồn `SELECT`/`MERGE` hoặc subquery |
| `WITH` phục vụ chèn | `WITH ... INSERT INTO ... SELECT ...` | `;WITH ... INSERT INTO ... SELECT ...` | `INSERT INTO ... WITH ... SELECT ...` | `WITH ... INSERT INTO ... SELECT ...` | Dùng nguồn `SELECT` với CTE theo cú pháp Oracle |
| `WITH` phục vụ xóa | `WITH ... DELETE FROM ... USING ...` | `;WITH ... DELETE alias FROM ... JOIN ...` | `WITH ... DELETE alias FROM ... JOIN ...` | `WITH ... DELETE ... WHERE IN/EXISTS (...)` | Thường dùng truy vấn con/nguồn SELECT có CTE |
| Trả hàng sau DML | `RETURNING` | `OUTPUT inserted/deleted` | Không có `RETURNING` tổng quát tương đương | `RETURNING` từ 3.35.0 | Tùy loại DML và phiên bản, cú pháp khác |
| CTE **chứa DML** rồi `SELECT` từ kết quả | Có, với `RETURNING` và quy tắc riêng | Không theo mẫu PostgreSQL | Không theo mẫu PostgreSQL | Không theo mẫu PostgreSQL | Không coi là cú pháp chung tương đương |
| CTE dùng lại trong câu lệnh tiếp theo | Không; phạm vi một câu lệnh | Không; phạm vi một câu lệnh | Không; phạm vi một câu lệnh | Không; phạm vi một câu lệnh | Phạm vi trong câu truy vấn chứa nó |

Bảng trên mô tả **mẫu thường gặp**, không phải danh sách hoàn chỉnh cho mọi phiên bản DBMS. `WITH` có thể được phép ở những vị trí khác tùy sản phẩm và phiên bản. Khi cần ứng dụng đa hệ quản trị, hãy kiểm tra cú pháp thực tế của từng hệ bằng tài liệu và môi trường triển khai tương ứng.

## 12. Những vấn đề an toàn khi CTE đi kèm lệnh ghi

CTE giúp tách logic thành các bước dễ đọc, nhưng **không tự bảo đảm lệnh thay đổi dữ liệu an toàn**. Khi chuyển một `SELECT` sang `UPDATE` hoặc `DELETE`, phải kiểm soát phạm vi tác động, các điều kiện đồng thời và lỗi vận hành.

### 12.1. Xem trước chính xác các hàng đích

Trước khi chạy:

```sql
WITH captured_by_order AS (...)
UPDATE orders_demo ...
```

hãy có một truy vấn xem trước **cùng điều kiện**:

```sql
WITH captured_by_order AS (
    SELECT order_id, SUM(amount) AS captured_amount
    FROM payments_demo
    WHERE payment_status = 'CAPTURED'
    GROUP BY order_id
)
SELECT o.order_id, o.status, o.order_total, c.captured_amount
FROM orders_demo AS o
JOIN captured_by_order AS c ON c.order_id = o.order_id
WHERE o.status = 'NEW'
  AND o.order_total > 0
  AND c.captured_amount >= o.order_total
ORDER BY o.order_id;
```

Việc xem trước giúp phát hiện điều kiện quên lọc trạng thái, tính cả khoản `FAILED` hay thiếu điều kiện ghép. **Nhưng xem trước và cập nhật là hai câu lệnh riêng**; dữ liệu có thể thay đổi ở giữa nếu có ghi đồng thời. Khi cần bảo đảm cùng một tập dữ liệu, phải lựa chọn chiến lược khóa, mức cô lập hoặc giao dịch phù hợp.

### 12.2. Bảo đảm một hàng đích có một tập giá trị nguồn xác định

Giả sử một đơn có ba khoản thanh toán. Nếu `UPDATE ... FROM` nối trực tiếp ba hàng và đặt:

```sql
-- Ví dụ ý tưởng sai nếu muốn tổng tất cả thanh toán:
-- SET paid_amount = p.amount
```

thì `p.amount` không phải **tổng tiền của đơn**; đó là số tiền của một hàng thanh toán. Trong một số dạng cập nhật có nhiều hàng nguồn khớp, kết quả có thể phụ thuộc lựa chọn hàng nguồn không xác định.

Giải pháp là CTE tổng hợp:

```sql
WITH captured_by_order AS (
    SELECT order_id, SUM(amount) AS captured_amount
    FROM payments_demo
    WHERE payment_status = 'CAPTURED'
    GROUP BY order_id
)
...
```

Grain của CTE lúc này là **một hàng cho một order_id**, đúng với khóa của bảng cần cập nhật.

### 12.3. Dùng khóa và trạng thái để tạo điều kiện idempotent

Một lệnh được thiết kế tốt nên tránh thay đổi cùng bản ghi nhiều lần nếu chạy lặp trong một tình huống có thể dự đoán:

```sql
UPDATE orders_demo
SET status = 'PAID'
WHERE order_id = 101
  AND status = 'NEW';
```

Sau lần cập nhật đầu tiên, trạng thái không còn `NEW`, nên lần chạy tiếp theo **không cập nhật lại**. Điều kiện trạng thái vừa mô tả nghiệp vụ vừa giúp kiểm soát lặp thao tác. Nhưng **idempotent ở trạng thái đơn** không tự giải quyết việc ghi log trùng, gửi thông báo trùng hoặc nhận lại cùng giao dịch thanh toán nhiều lần; những tác vụ đó có thể cần khóa nghiệp vụ, ràng buộc duy nhất và cơ chế xử lý sự kiện riêng.

### 12.4. Giao dịch, khóa và mức cô lập

Ví dụ PostgreSQL:

```sql
BEGIN;

WITH captured_by_order AS (
    SELECT order_id, SUM(amount) AS captured_amount
    FROM payments_demo
    WHERE payment_status = 'CAPTURED'
    GROUP BY order_id
)
UPDATE orders_demo AS o
SET status = 'PAID'
FROM captured_by_order AS c
WHERE c.order_id = o.order_id
  AND o.status = 'NEW'
  AND o.order_total > 0
  AND c.captured_amount >= o.order_total
RETURNING o.order_id;

-- Kiểm tra, sau đó lựa chọn một trong hai:
ROLLBACK;
-- Hoặc COMMIT (không chạy cả hai như hai lệnh có hiệu lực).
```

Trong sản xuất, `UPDATE` có thể giữ khóa trên những hàng bị thay đổi, khiến các giao dịch khác phải chờ hoặc phát sinh deadlock tùy tình huống. Một giao dịch kéo dài có thể làm tăng chi phí lưu trữ phiên bản hoặc chặn công việc khác. Việc xử lý batch lớn, khóa, mức cô lập và thời gian giao dịch phải được thiết kế phù hợp DBMS, không chỉ dựa vào cú pháp `WITH`.

### 12.5. Trả về hàng thay đổi không giống đếm hàng của CTE

Ví dụ CTE `captured_by_order` gồm bốn đơn đã có khoản `CAPTURED`: **101, 103, 106, 107**. Nhưng lệnh `UPDATE` ở mục 3 chỉ thay đổi **hai đơn 101 và 106**:

- 103 đã `PAID`, không thỏa `status = 'NEW'`.
- 107 mới có 50.000 trên tổng cần thu 100.000.

Do đó `RETURNING` (PostgreSQL), `OUTPUT` (SQL Server) hoặc số hàng bị ảnh hưởng của DBMS **không bằng số hàng của CTE**. Đừng dùng kích thước CTE làm bằng chứng đã cập nhật đúng số hàng; phải kiểm tra **điều kiện của câu DML chính**.

## 13. Một ứng dụng nâng cao: CTE chọn lô công việc trước khi UPDATE

Với bảng hàng đợi có nhiều công việc cần xử lý, đôi khi cần chọn **một lô giới hạn** rồi cập nhật chúng thành trạng thái `PROCESSING`. PostgreSQL có thể phối hợp CTE với `FOR UPDATE SKIP LOCKED` để các worker đồng thời tránh giành cùng hàng.

Ví dụ **minh họa trên một bảng giả định**, không chạy trực tiếp vì bài học không tạo `jobs_demo`:

```sql
-- PostgreSQL; giả sử jobs_demo(job_id PK, status, created_at).
WITH picked AS (
    SELECT job_id
    FROM jobs_demo
    WHERE status = 'PENDING'
    ORDER BY created_at, job_id
    FOR UPDATE SKIP LOCKED
    LIMIT 10
)
UPDATE jobs_demo AS j
SET status = 'PROCESSING'
FROM picked AS p
WHERE p.job_id = j.job_id
RETURNING j.job_id, j.status;
```

Ý tưởng:

1. Chọn tối đa 10 công việc đang chờ theo thứ tự xác định.
2. Khóa các hàng được chọn trong giao dịch của câu lệnh; `SKIP LOCKED` bỏ qua hàng đang bị giao dịch khác khóa.
3. Cập nhật những công việc đó sang `PROCESSING`.
4. Trả về ID thực sự được cập nhật.

Đây là một kỹ thuật hữu ích cho **bảng hàng đợi**, nhưng nó có giới hạn: `SKIP LOCKED` có thể nhìn thấy tập dữ liệu không nhất quán theo kiểu snapshot thông thường, thích hợp với tác vụ lấy việc chứ không phải báo cáo tài chính. Hệ thống còn cần xử lý **worker chết giữa chừng, lease/timeout, retry và idempotency**. Không dùng lại cú pháp khóa PostgreSQL cho MySQL, SQL Server, SQLite hoặc Oracle mà không đối chiếu khả năng và ngữ nghĩa riêng của từng hệ.

## 14. Những lỗi thường gặp khi dùng CTE với DML

### Lỗi 1 — Nghĩ CTE chỉ được sử dụng với SELECT

Không đúng. Nhiều DBMS cho phép CTE phục vụ `INSERT`, `UPDATE` và `DELETE`. Nhưng **vị trí `WITH` và dạng câu lệnh chính** không đồng nhất giữa các phương ngữ.

### Lỗi 2 — Sao chép UPDATE FROM của PostgreSQL sang MySQL

PostgreSQL dùng dạng `UPDATE ... SET ... FROM source WHERE ...`; MySQL thường dùng `UPDATE target JOIN source ... SET ... WHERE ...`. Hai câu có cùng ý tưởng nhưng **khác cú pháp**.

### Lỗi 3 — Sao chép RETURNING sang SQL Server

SQL Server dùng `OUTPUT inserted...`/`deleted...` để trả thông tin hàng thay đổi, không phải `RETURNING` kiểu PostgreSQL. SQLite có `RETURNING` ở phiên bản mới, nhưng không vì thế mà hỗ trợ data-modifying CTE hoàn toàn giống PostgreSQL.

### Lỗi 4 — Nghĩ CTE chứa UPDATE của PostgreSQL chạy được ở mọi DBMS

`WITH changed AS (UPDATE ... RETURNING ...) SELECT ...` là **data-modifying CTE** đặc trưng được PostgreSQL hỗ trợ. Việc SQL Server hoặc SQLite hỗ trợ CTE đọc dữ liệu trước `UPDATE` không có nghĩa chúng chấp nhận lệnh `UPDATE` nằm bên trong biểu thức `AS (...)`.

### Lỗi 5 — Quên dấu chấm phẩy trước WITH của SQL Server

Trong nhiều batch SQL Server, khi có một câu lệnh phía trước chưa được kết thúc đúng, `WITH` có thể bị phân tích sai. Dùng dấu chấm phẩy để **kết thúc lệnh trước**, vì vậy người ta thường viết `;WITH` khi ví dụ xuất hiện giữa một batch.

### Lỗi 6 — Dùng CTE một lần rồi gọi lại ở câu lệnh sau

CTE có phạm vi **một câu SQL**, không phải một biến/bảng tạm còn tồn tại ở lệnh kế tiếp. Nếu cần dùng nhiều lần qua nhiều lệnh độc lập, phải tính lại hoặc dùng cấu trúc lưu dữ liệu thích hợp.

### Lỗi 7 — JOIN trực tiếp nhiều dòng nguồn để UPDATE một hàng đích

Khi một đơn có nhiều thanh toán, việc ghép nhiều hàng nguồn vào một hàng đích làm biểu thức cập nhật có thể không xác định. Hãy tổng hợp nguồn về **một hàng trên khóa cập nhật** hoặc thiết kế quy tắc chọn duy nhất.

### Lỗi 8 — Nhầm WITH với cơ chế chạy tuần tự nhiều bước

CTE tạo phụ thuộc truy vấn, nhưng không phải một ngôn ngữ lập trình mệnh lệnh để đảm bảo mọi phép đọc/ghi diễn ra từ trên xuống dưới theo thứ tự văn bản. Đặc biệt với nhiều data-modifying CTE ở PostgreSQL, cần nắm rõ snapshot và quy tắc `RETURNING`.

### Lỗi 9 — Không phân biệt tập ứng viên và tập đã thay đổi

Một CTE có thể chọn 4 đơn, nhưng câu `UPDATE` chỉ thay đổi 2 đơn vì điều kiện bổ sung ở câu chính. Muốn biết chính xác những gì đã thay đổi, xem `RETURNING`, `OUTPUT` hoặc số hàng bị ảnh hưởng, không chỉ đếm kết quả của CTE.

### Lỗi 10 — Xóa nhầm bảng khi viết DELETE có JOIN

`DELETE q FROM review_queue_demo q JOIN ...` của MySQL/SQL Server chỉ xóa **alias `q`**; `DELETE FROM review_queue_demo USING ...` của PostgreSQL có cú pháp khác. Cần xác nhận bảng đích trước khi chạy, đặc biệt ở truy vấn nối nhiều bảng.

### Lỗi 11 — Dùng CTE để che bẫy NULL hoặc điều kiện thiếu

`WHERE id IN (SELECT id FROM cte)` và `WHERE EXISTS (...)` vẫn tuân theo logic SQL và ràng buộc khóa. CTE không tự xử lý `NULL`, trùng khóa hoặc một câu `UPDATE` thiếu điều kiện `WHERE`. Trong ví dụ, `order_id` là khóa chính và kết quả nhóm chỉ chứa giá trị đã biết; trên dữ liệu thật phải kiểm tra.

### Lỗi 12 — Tin rằng rollback luôn hủy cả DDL và DML trên mọi DBMS

PostgreSQL có transaction DDL cho nhiều thao tác thông thường; MySQL có các lệnh DDL gây commit ngầm; hệ khác có quy tắc riêng. Chỉ đưa ra giả định an toàn sau khi kiểm tra **đúng loại câu lệnh và DBMS**.

## 15. Bài tập thực hành

Các bài dưới đây dùng dữ liệu mẫu ở mục 2. **Mỗi bài là một kịch bản độc lập**. Nếu thực hiện thay đổi trên PostgreSQL, đặt lệnh thử trong `BEGIN ... ROLLBACK` để có thể thử lại từ trạng thái ban đầu.

### Bài 1 — Xem trước những đơn sẽ cập nhật

Hãy viết CTE tính tổng khoản thanh toán `CAPTURED` theo từng `order_id`, sau đó chọn đơn `NEW` đủ tiền và `order_total > 0`.

Gợi ý:

```sql
WITH captured_by_order AS (
    SELECT order_id, SUM(amount) AS captured_amount
    FROM payments_demo
    WHERE payment_status = 'CAPTURED'
    GROUP BY order_id
)
SELECT o.order_id, c.captured_amount, o.order_total
FROM orders_demo AS o
JOIN captured_by_order AS c
    ON c.order_id = o.order_id
WHERE o.status = 'NEW'
  AND o.order_total > 0
  AND c.captured_amount >= o.order_total
ORDER BY o.order_id;
```

**Kết quả mong đợi:** **101 và 106**. Giải thích vì sao không chọn 102, 103, 104, 105, 107.

### Bài 2 — Chuyển SELECT sang UPDATE trong PostgreSQL

Chuyển truy vấn bài 1 sang `WITH ... UPDATE ... FROM`, sử dụng `RETURNING` để chỉ trả ID và trạng thái mới. Không quên điều kiện `o.status = 'NEW'`.

**Đáp án định hướng:** dùng `WITH captured_by_order AS (...) UPDATE orders_demo AS o SET status = 'PAID' FROM captured_by_order AS c WHERE ... RETURNING o.order_id, o.status`. Kết quả là **101 và 106**; rollback để giữ dữ liệu.

### Bài 3 — Chọn và INSERT những đơn cũ vào hàng chờ

Với bảng `review_queue_demo`, hãy tạo CTE chọn những đơn `NEW` có `ordered_on < DATE '2025-02-01'`. Chèn các mã chưa có trong hàng chờ với lý do `OLD_NEW`.

**Đáp án:** các mã **101, 102, 104** được chèn trong kịch bản ban đầu. `NOT EXISTS` giúp tránh chèn lại mã đã tồn tại ở trạng thái đang xét, nhưng bảng vẫn cần khóa chính/ràng buộc duy nhất.

### Bài 4 — DELETE có CTE

Yêu cầu: **xóa khỏi `review_queue_demo` những hàng thuộc đơn `CANCELLED`**, không xóa bản ghi trong `orders_demo`.

```sql
WITH cancelled_orders AS (
    SELECT order_id
    FROM orders_demo
    WHERE status = 'CANCELLED'
)
DELETE FROM review_queue_demo AS q
USING cancelled_orders AS c
WHERE c.order_id = q.order_id
RETURNING q.order_id, q.reason;
```

**Đáp án:** một dòng hàng chờ **105** được xóa. Sau `ROLLBACK`, dòng hàng chờ 105 vẫn tồn tại.

### Bài 5 — Phân biệt hai loại CTE

So sánh:

```sql
-- Dạng A: CTE đọc dữ liệu, UPDATE chính.
WITH candidates AS (
    SELECT order_id
    FROM orders_demo
    WHERE status = 'NEW'
)
UPDATE orders_demo
SET status = 'PAID'
WHERE order_id IN (SELECT order_id FROM candidates);
```

```sql
-- Dạng B: PostgreSQL data-modifying CTE.
WITH changed AS (
    UPDATE orders_demo
    SET status = 'PAID'
    WHERE order_id = 101 AND status = 'NEW'
    RETURNING order_id
)
SELECT * FROM changed;
```

**Câu hỏi:** lệnh thay đổi dữ liệu nằm **ngoài hay trong CTE** ở từng dạng? Vì sao dạng B không được coi là cú pháp chung cho mọi SQL DBMS? **Đáp án:** A thay đổi ở câu lệnh chính; B thay đổi ngay trong CTE, dùng `RETURNING` làm nguồn cho `SELECT`.

### Bài 6 — Dịch sang phương ngữ SQL Server

Chuyển `UPDATE ... FROM` ở bài 2 thành:

- `;WITH captured_by_order AS (...)`.
- `UPDATE o SET status = 'PAID'`.
- `OUTPUT inserted.order_id, deleted.status, inserted.status`.
- `FROM dbo.orders_demo AS o JOIN captured_by_order AS c ...`.

**Câu hỏi:** vì sao SQL Server dùng `OUTPUT` thay vì `RETURNING`? Dấu chấm phẩy trước `WITH` có vai trò gì trong batch?

### Bài 7 — Dịch sang MySQL

Chuyển ý tưởng cập nhật đủ tiền thành mẫu:

```sql
-- MySQL 8.0
WITH captured_by_order AS (
    SELECT order_id, SUM(amount) AS captured_amount
    FROM payments_demo
    WHERE payment_status = 'CAPTURED'
    GROUP BY order_id
)
UPDATE orders_demo AS o
JOIN captured_by_order AS c
    ON c.order_id = o.order_id
SET o.status = 'PAID'
WHERE o.status = 'NEW'
  AND o.order_total > 0
  AND c.captured_amount >= o.order_total;
```

**Câu hỏi:** vị trí của `JOIN`, `SET` khác PostgreSQL thế nào? Khi viết `INSERT ... SELECT` có CTE ở MySQL, `WITH` nên đặt ở đâu? **Đáp án:** trước `UPDATE` có `WITH`, còn nguồn `INSERT ... SELECT` thường đặt `WITH` sau `INSERT INTO ...` và trước `SELECT`.

### Bài 8 — SQLite và kiểm tra tồn tại

Viết `WITH captured_by_order AS (...) UPDATE orders_demo SET status = 'PAID' WHERE EXISTS (SELECT 1 FROM captured_by_order ... )`.

**Đáp án định hướng:** cần liên hệ `c.order_id = orders_demo.order_id` và điều kiện đủ tiền; SQLite từ phiên bản hỗ trợ `RETURNING` có thể trả ID các hàng cập nhật. CTE chỉ có `SELECT`; `UPDATE` là câu lệnh chính.

### Bài 9 — Tìm nguy cơ nhân bản nguồn

Giả sử một đơn có **hai khoản CAPTURED**, mỗi khoản 100.000, và tổng tiền đơn là 200.000. Nếu cập nhật bằng điều kiện `p.amount >= o.order_total` trên **từng dòng thanh toán**, đơn có được đánh dấu đủ tiền không?

**Đáp án:** **không**, vì từng khoản 100.000 không đạt 200.000; phải tính **`SUM(amount) GROUP BY order_id`** để có tổng 200.000. Nếu dùng dòng thanh toán trực tiếp làm nguồn cho `SET`, còn có nguy cơ nhiều hàng nguồn khớp một hàng đích. CTE tổng hợp bảo đảm mức chi tiết mong muốn.

### Bài 10 — Ghi log dựa trên RETURNING

Với PostgreSQL, giả sử đã tạo `status_change_log_demo` như mục 6.1. Viết câu:

1. CTE `changed_orders` chạy `UPDATE orders_demo ... RETURNING order_id, status`.
2. `INSERT INTO status_change_log_demo ... SELECT ... FROM changed_orders`.
3. `RETURNING` dòng log được chèn.

**Đáp án:** xem mẫu `WITH changed_orders AS (UPDATE ... RETURNING ...) INSERT INTO ... SELECT ... FROM changed_orders RETURNING ...`. Kết quả có một log cho đơn 101 nếu dữ liệu ban đầu có `status = 'NEW'`. Thực hiện trong giao dịch rollback khi học.

## 16. Những nguyên tắc nên ghi nhớ

| Nguyên tắc | Lý do |
|---|---|
| Viết truy vấn `SELECT` xem trước hàng đích | Phát hiện sai bộ lọc trước khi ghi dữ liệu |
| Xác định grain của CTE nguồn | Tránh một hàng đích khớp nhiều hàng nguồn |
| Phân biệt CTE đọc và data-modifying CTE | Tránh áp cú pháp PostgreSQL sai sang DBMS khác |
| Không coi CTE là bảng tạm tồn tại qua nhiều lệnh | Phạm vi tên CTE thường chỉ một câu SQL |
| Đặt `WITH` đúng vị trí của từng phương ngữ | MySQL, SQL Server, PostgreSQL, Oracle, SQLite có cú pháp khác |
| Dùng `RETURNING` / `OUTPUT` khi được hỗ trợ | Quan sát chính xác các hàng đã thay đổi |
| Dùng khóa chính, điều kiện trạng thái và ràng buộc duy nhất | Hạn chế ghi nhầm hoặc ghi trùng |
| Cân nhắc transaction và thao tác đồng thời | CTE không tự bảo đảm nhất quán qua nhiều câu SQL |
| Không giả định mọi CTE đều được materialize | Bộ tối ưu có thể chọn kế hoạch khác |
| Thử dữ liệu biên trước khi triển khai | Bao gồm trạng thái đã đổi, tiền bằng 0, thanh toán một phần, dữ liệu nguồn lặp |

## Kết luận

CTE không chỉ làm `SELECT` dễ đọc; nó còn là công cụ tổ chức logic rất hữu ích cho **`INSERT`, `UPDATE` và `DELETE`**. Một CTE có thể tính tổng, chọn tập khóa và chuẩn bị dữ liệu nguồn để câu lệnh DML chính thao tác trên đúng hàng. Trong PostgreSQL, CTE còn có thể **chứa chính thao tác thay đổi dữ liệu** và đưa các hàng vừa sửa sang bước kế tiếp bằng `RETURNING`.

Tuy nhiên, **hình thức DML với CTE phụ thuộc phương ngữ**: PostgreSQL dùng `UPDATE ... FROM` và `RETURNING`; SQL Server có `UPDATE ... FROM`, `OUTPUT` và yêu cầu về dấu chấm phẩy trước `WITH`; MySQL thường dùng `UPDATE ... JOIN` và đặt `WITH` trong nguồn `INSERT ... SELECT`; SQLite có `WITH` với DML và `RETURNING` ở phiên bản phù hợp nhưng không có data-modifying CTE kiểu PostgreSQL; Oracle thường đặt CTE trong truy vấn nguồn của `MERGE` hoặc trong subquery.

Khi áp dụng vào hệ thống thật, hãy xác định **đúng bảng đích, đúng tập hàng nguồn, đúng khóa ghép, đúng số hàng bị ảnh hưởng và đúng hành vi giao dịch** trước khi chạy câu lệnh ghi. CTE giúp biểu diễn ý định rõ ràng; việc giữ dữ liệu an toàn vẫn đòi hỏi hiểu đầy đủ ngữ nghĩa SQL và khả năng của DBMS đang sử dụng.
