# Persisting Resume Tokens Durably and Handling Lost Oplog History in MongoDB

An application can use a MongoDB **Change Stream** to listen for `insert`, `update`, `replace`, `delete`, and other change events without repeatedly querying the entire collection. For instance, once an order transitions to `paid`, a service can update a search index, sync analytics data, refresh a cache, or emit an event to another system.

However, a Change Stream is a **long-lived stream**, whereas application processes, network links, and servers can all fail. Suppose a consumer processes 1,000 events and then restarts. How does it know where to resume? And if the consumer stays down long enough for the required **oplog** history to be overwritten, can MongoDB re-emit those lost events?

This lesson is part of the **Change stream** chapter in the **Database Engine Document MongoDB** module, focusing on two closely linked responsibilities:

1. **Persisting resume tokens durably** so a consumer can restart, continue from where it left off, and minimize unnecessary replays.
2. **Detecting and handling lost oplog history** when a token can no longer resume; in that case, you need a resynchronization policy (*rebuild/reconciliation*) with a safe cutover anchor instead of silently dropping events.

A solid design must also answer a harder question: **when is it safe to save a checkpoint?** Persisting a token too early risks losing events; persisting after processing risks duplicate delivery. Therefore, Change Streams must be paired with **idempotency**, durable checkpoint storage, lag monitoring, and recovery plans.

## 1. Where Does a Change Stream Get Its Events?

On a replica set, MongoDB records data modifications into the **oplog** so secondaries can replicate them. A Change Stream exposes an interface over eligible changes, generating events from change history maintained by the system.

Conceptual diagram:

```text
                 APPLICATION WRITES
                       |
                       v
                 Primary mongod
                       |
               data operations
                       |
                       v
                     Oplog
                       |
             committed events
                       |
                       v
                Change Stream
                       |
                 mongos/mongod
                       |
                       v
                   Consumer
                       |
          +------------+------------+
          |                         |
          v                         v
    Process event            Save checkpoint
    (sink/read model)        (resume token)
```

Change Streams are supported in MongoDB deployments with appropriate replication, such as **replica sets** and **sharded clusters**. A standalone `mongod` lacks the oplog and replication infrastructure required.

Key distinctions:

- **The oplog** is a replication log; it is **not an eternal event queue** designed to retain every event indefinitely for slow consumers.
- **Change Streams** deliver only eligible events according to watch scope, filter pipelines, and accessible history.
- **A resume token** is a MongoDB-issued continuation marker, not a backup copy of all events and not data that can reconstruct purged history.
- **A consumer checkpoint** is application-managed state; while a MongoDB driver can auto-resume across certain transient errors, that **does not mean** the token was durably saved across deployments or restarts.

Change Streams reflect **majority-committed** changes under server semantics. Transient data written on a primary that rolls back before meeting commit criteria must not be treated by applications as a durably emitted Change Stream event.

## 2. Three Pieces of Information You Must Keep Separate

Suppose an order document contains:

```javascript
{
  _id: "order-1001",
  customerId: "C01",
  status: "paid",
  total: 250
}
```

When updated, a change event may take the abridged shape:

```javascript
{
  _id: {
    _data: "825...."
  },
  operationType: "update",
  clusterTime: Timestamp(...),
  ns: {
    db: "change_stream_lab",
    coll: "orders"
  },
  documentKey: {
    _id: "order-1001"
  },
  updateDescription: {
    updatedFields: {
      status: "paid"
    },
    removedFields: []
  }
}
```

This is an **event schema illustration**, not copy-paste runnable output: real `_data` and `Timestamp` values are generated by MongoDB.

| Field | Role | Should It Be Used as Checkpoint? |
| --- | --- | --- |
| **Event `_id`** | Server-generated **resume token** for the change event | **Yes**, store intact as a BSON/document value |
| `documentKey._id` | `_id` of the modified application document | **No**, identifies only the business document |
| `clusterTime` | Logical cluster timestamp of the event | Diagnostics; not a default replacement for resume tokens |
| `operationType` | Operation type, e.g., `insert`, `update`, `delete` | Does not identify a unique stream position |
| `ns` | Database/collection namespace | Useful for multi-namespace consumers |
| `fullDocument` | Document image when supplied by options | Data payload; not a token |

**The #1 mistake:** when we say "save the change event's `_id`", we mean `event._id` (the resume token), **not** `event.documentKey._id`. A document ID can be updated dozens of times; saving it tells you nothing about **which update** you last processed.

Resume tokens are **opaque**: applications must treat them as MongoDB-managed data—never decode `_data` to infer business order, never substitute a self-generated timestamp, and never truncate strings or alter BSON element types.

## 3. What Is a Resume Token Used For?

Once a consumer processes a change event and saves token `T100`:

```text
Changes in the stream:

    E98 ---- E99 ---- E100 ---- E101 ---- E102 ---- E103
                       |
                       v
                 checkpoint T100
                       |
                     crash
                       |
                    restart
                       |
                       v
               resumeAfter(T100)
                       |
                       v
                    E101 ...
```

As long as sufficient history remains and the token is valid, **`resumeAfter`** opens the Change Stream **immediately after** the position pointed to by the token. Thus the consumer avoids replaying the entire collection from scratch.

Common scenarios:

- Consumer process redeployment.
- Container restart after a crash.
- Network drop followed by stream reopening.
- Consumer failover from one instance to another.
- Application maintenance shorter than **the retained resumable history window**.

A token does not guarantee resumption succeeds in every scenario. It depends on MongoDB **still retaining the required history** and matching Change Stream configuration/scope.

## 4. Environment Prerequisites for Change Streams

Before writing a consumer, verify:

1. **Deployment:** a replica set or sharded cluster supporting Change Streams; the cluster must be properly configured with healthy eligible members.
2. **Version:** MongoDB server and driver versions supporting the options you plan to use (`resumeAfter`, `startAfter`, `startAtOperationTime`, or newer event types).
3. **Privileges:** account permissions to read and watch Change Streams on the target namespace.
4. **Scope:** watching a **collection**, **database**, or **cluster**, each differing in permissions, event scope, `namespace`, and invalidation behavior.
5. **History size:** the oplog has finite capacity/retention; consumers must keep pace with change rates.
6. **Pipeline:** custom stages must never strip or alter the resume token `_id`; filters are allowed, but event transformations must obey Change Stream rules.

### Opening a Simple Stream in `mongosh`

In Terminal A, connect to your lab replica set or `mongos`:

```javascript
use change_stream_lab

const stream = db.orders.watch();

while (stream.hasNext()) {
  const change = stream.next();
  printjson(change);
}
```

In Terminal B, connected to the same lab cluster, run:

```javascript
use change_stream_lab

db.orders.insertOne({
  _id: "order-1001",
  customerId: "C01",
  status: "pending",
  total: NumberDecimal("250.00"),
  createdAt: new Date()
});

db.orders.updateOne(
  { _id: "order-1001" },
  { $set: { status: "paid" } }
);
```

Terminal A receives the corresponding change events once emitted by the server. `while (stream.hasNext())` is **intentionally long-running** and blocks waiting for new events; that is normal consumer behavior, not a quick query. Real applications need shutdown signals, cursor closure, and lifecycle-managed restarts.

If the collection does not exist yet or privileges/infrastructure are missing, prepare the lab collection and verify support; never run test inserts on databases holding production data.

## 5. Where Does the Resume Token Appear?

A valid change event carries its token in `_id`:

```javascript
const change = stream.next();
const token = change._id;

printjson(token);
```

Illustrative look:

```javascript
{
  _data: "82655..."
}
```

The real token is a **BSON document**, which may include additional fields depending on server version or event type. Never extract only `token._data` assuming you can rebuild the full resume token from that string.

### Preserve Exact BSON Structure

Persist:

```javascript
{
  _id: "orders-consumer-v1",
  resumeToken: {
    _data: "..."
  },
  updatedAt: ISODate("2026-11-14T00:00:00Z")
}
```

Here `resumeToken` is **the entire token document received from the stream**, not manually typed mock data. `updatedAt` is purely for operations and monitoring.

If you must store checkpoints in a system that does not natively store BSON, use **Extended JSON** with full BSON type fidelity or a driver-recommended serialization format; never rely on plain `JSON.stringify()` assuming lost BSON types won't matter. Above all, the token document is opaque—never add or remove fields inside it.

## 6. Where Should Resume Tokens Be Stored Durably?

Holding a `lastToken` variable in RAM is **not durable**:

```javascript
let lastToken = change._id;
```

When the process is killed, the variable vanishes. One common choice is storing checkpoints in a **dedicated collection**:

```text
Database: change_stream_lab

orders
  ├── order-1001
  ├── order-1002
  └── ...

consumerCheckpoints
  └── {
        _id: "orders-sync-v1",
        resumeToken: <opaque BSON document>,
        updatedAt: <Date>,
        streamScope: "change_stream_lab.orders",
        pipelineVersion: 1
      }
```

Benefits of a checkpoint collection:

- Updatable after every processed event or batch.
- Can use **`majority` write concern** for durability across replica set failovers.
- Readable when a consumer restarts on a different node.
- Easy to inspect which worker is active, when its last token was saved, its pipeline version, and its namespace.

There is no requirement that MongoDB itself store the checkpoint. An architecture can use another transactional database or durable key-value store—provided it **preserves exact token structure**, survives crashes, coordinates multiple consumers, and aligns commits with side effects.

### Designing the Checkpoint Document

A practical schema may include:

| Field | Role |
| --- | --- |
| `_id` | Unique name of the consumer or logical partition |
| `resumeToken` | Full BSON document of the last checkpointed token |
| `updatedAt` | Timestamp when checkpoint was written |
| `streamScope` | Collection/database/cluster the token belongs to |
| `pipelineVersion` | Version of the filter/transform pipeline |
| `consumerVersion` | Application code version affecting processing |
| `lastOperationType` | Diagnostic info for the last event; not a substitute for token |
| `lastClusterTime` | Helps measure lag when available |
| `state` | e.g., `RUNNING`, `NEEDS_REBUILD`, `RECONCILING` |

**Never attach a TTL index to delete checkpoints by `updatedAt` carelessly.** If a checkpoint gets purged after a few days, the consumer wakes up blind to its last position and must enter recovery.

### Saving Checkpoints with Write Concern

In `mongosh`:

```javascript
db.consumerCheckpoints.updateOne(
  { _id: "orders-sync-v1" },
  {
    $set: {
      resumeToken: change._id,
      updatedAt: new Date(),
      streamScope: "change_stream_lab.orders",
      pipelineVersion: 1,
      state: "RUNNING"
    }
  },
  {
    upsert: true,
    writeConcern: {
      w: "majority",
      wtimeout: 10000
    }
  }
);
```

This is a **standalone command template** assuming `change` has already been processed successfully. Never run it with a fake token or before event processing finishes.

Majority write concern makes checkpoints resilient to routine failovers, but **does not automatically make external side effects exactly-once**. We examine that next.

## 7. Golden Rule: Process the Event First, Checkpoint Afterward

Suppose a consumer processes event E101:

```text
E101 received
      |
      v
Process E101 successfully
      |
      v
Persist E101 token durably
      |
      v
Continue to E102
```

Why enforce this order?

### Case A: Checkpoint Before Processing

```text
Receive E101
    |
    v
Save token T101   <-- checkpoint goes first
    |
    v
Crash before processing E101
    |
    v
Restart -> resumeAfter(T101)
    |
    v
Starts at E102
```

Result: **E101 is permanently skipped by the consumer**. MongoDB obeyed `resumeAfter` accurately by emitting only events after the checkpointed position. The bug lies in the application's commit order.

### Case B: Process Before Checkpointing

```text
Receive E101
    |
    v
Process E101 successfully
    |
    v
Crash before saving T101
    |
    v
Restart -> resumeAfter(T100)
    |
    v
E101 is redelivered
```

Result: **E101 may be processed twice**. Provided processing is idempotent, redelivery causes no data corruption. This is the standard trade-off: **accept at-least-once delivery with safe duplicate handling** instead of premature checkpointing that drops events.

### Trade-Off Table

| Order | Mid-Flight Crash | Risk |
| --- | --- | --- |
| Token first → side effect second | After saving token, before processing | **Dropped events** |
| Side effect first → token second | After processing, before saving token | **Duplicate delivery/processing** |
| Side effect + token in one compatible sink transaction | Atomic transaction commit/abort | Can achieve **sink-level exactly-once** when properly designed |

Never claim Change Streams natively provide **end-to-end exactly-once**. Drivers can auto-resume, yet sending emails, calling REST APIs, or writing to external systems is outside the resume token's commit boundary.

## 8. Designing Idempotency When Events Can Replay

### 8.1. Using Token or Operation ID as a Deduplication Key

Suppose a consumer logs processed events:

```javascript
db.processedChanges.updateOne(
  { _id: change._id },
  {
    $setOnInsert: {
      documentKey: change.documentKey,
      operationType: change.operationType,
      processedAt: new Date()
    }
  },
  {
    upsert: true,
    writeConcern: { w: "majority" }
  }
);
```

Because `processedChanges._id` uses the resume token, a replayed event hits the exact same key. However, **recording a "processed" marker alone does not protect an external side effect**: if you mark it processed and crash before dispatching downstream, the next run might skip the side effect.

### 8.2. Updating State with Idempotent Assignments

Suppose an event reports current status `paid`. If a read model only stores current state:

```javascript
db.orderReadModel.updateOne(
  { _id: "order-1001" },
  {
    $set: {
      status: "paid"
    }
  },
  { upsert: true }
);
```

Running the same `$set` twice does not double-count payments. Yet **event ordering** still matters: if an older event replays after a newer event already ran, an unguarded `$set` overwrites newer state. Thus idempotency requires more than "repeating the operation yields the same result"; it must also **guard against version regression** under concurrency, replays, or multiple writers.

Designs can attach a **reliable application `version`/`sequence`**, or enforce sequential processing with conditional updates. Never compare token `_data` strings to infer versions; tokens are opaque.

### 8.3. Avoid Non-Idempotent Increments

If every event executes:

```javascript
db.counters.updateOne(
  { _id: "paidOrders" },
  { $inc: { count: 1 } },
  { upsert: true }
)
```

a replayed event increments `count` **twice**. Record an applied-event marker **atomically with the increment** in an appropriate transaction, recompute counters from source data, or use a reconcilable aggregation design.

### 8.4. Atomic Sink + Checkpoint

When **both the side effect and checkpoint live in the same MongoDB deployment** and writes support transactions, wrap them in a transaction:

```text
Receive event E101 from Change Stream
       |
       v
BEGIN sink transaction
       |
       +-- Check if E101 already processed
       +-- Update read model / ledger
       +-- Record processed event ID
       +-- Save checkpoint token T101
       |
       v
COMMIT transaction (appropriate writeConcern)
```

With atomic commits, sink state and checkpoint advance together or not at all. This is a strong pattern when strict correctness is needed, though you must still handle **transaction retries/unknown commit results**, unique constraints/operation IDs, and concurrency. Do not open the Change Stream *inside* the transaction like a normal read; consume the stream outside, and place **writing results + checkpoint** inside their own transaction.

For Kafka, email, HTTP, or external systems, you cannot simply include external side effects inside a MongoDB transaction. Use an **outbox, deduplication keys, idempotent consumers, or coordinated protocols**.

## 9. Three Mechanisms to Start or Resume a Stream

Change Streams offer positioning options for distinct purposes.

| Option | Input | Meaning | When to Use? |
| --- | --- | --- | --- |
| **`resumeAfter`** | Known resume token | Start **after** the token's position | Restarting after normal events while history remains |
| **`startAfter`** | Known resume token | Start after the token, supporting special cases like **`invalidate` events** | Opening a new stream after `invalidate` where supported |
| **`startAtOperationTime`** | BSON Timestamp | Start at/via an eligible cluster operation time | When holding a valid cluster operation time without a token, or time-based workflows |

These start-position options **must not be mixed arbitrarily in the same command**; pick the single option matching your recovery state.

### 9.1. `resumeAfter`

In `mongosh`:

```javascript
const checkpoint = db.consumerCheckpoints.findOne({
  _id: "orders-sync-v1"
});

const options = checkpoint && checkpoint.resumeToken
  ? { resumeAfter: checkpoint.resumeToken }
  : {};

const stream = db.orders.watch([], options);
```

If the checkpoint contains a valid resumable token, the stream continues **after that token**. If no checkpoint exists, the code opens a stream from "now" by Change Stream default; it **does not automatically replay older operations**. In systems needing complete consistency, a missing checkpoint must trigger **controlled initialization/rebuild**, never silently starting fresh and ignoring past history.

### 9.2. `startAfter` After `invalidate`

When a watched collection is dropped or renamed, a **collection-level change stream** can emit `invalidate` and close. This follows different rules from a mere network blip.

```javascript
// Illustrates opening a new stream after an invalidate token
const stream = db.orders.watch([], {
  startAfter: invalidateResumeToken
});
```

`startAfter` opens a new stream after a token, including after an **`invalidate` event** in supported scenarios. **`resumeAfter` cannot cross an `invalidate` event**.

However, opening a new stream after `invalidate` **does not resurrect dropped collection data** or guarantee a newly created collection with the same name shares old history. When schemas or namespaces change, applications must decide **whether to rebuild the read model**.

### 9.3. `startAtOperationTime`

Syntax example (the timestamp must come from a **real cluster** or valid coordination point, never fabricated):

```javascript
db.orders.watch([], {
  startAtOperationTime: knownClusterTimestamp
});
```

This option is no magic wand when **the oplog has already evicted old history**. If the timestamp predates retained history, MongoDB still cannot recover the stream.

**Never take `new Date()` from an application host and convert it into a resume token.** A BSON Timestamp used for operation time is distinct from a system-clock BSON Date; conversions and start positions must derive from supported cluster metadata.

### 9.4. Never Decode Tokens to Extract a Timestamp

```text
Wrong:
  token._data -> slice a few bytes -> guess timestamp -> startAtOperationTime

Right:
  preserve exact BSON token
  -> resumeAfter(token) when valid
  or startAfter(invalidateToken) when appropriate
  or use a legitimately sourced operation time
```

Internal resume token layouts can evolve across versions; application code must never depend on custom algorithms decoding token internals.

## 10. Post-Batch Resume Token: Should You Checkpoint When the Stream Is Idle?

Collections do not always receive steady traffic. A consumer can run for minutes without seeing an `insert`, `update`, or `delete`. If it checkpoints only **event tokens**, its persisted position can grow stale while the stream keeps polling empty batches.

MongoDB supports a **post-batch resume token (PBRT)** in applicable scenarios. This token represents a server-side progress point usable for resuming even when a batch yields zero events.

```text
Server processes Change Stream
   |
   +-- batch with E101, E102 --> event tokens
   |
   +-- empty batch ------------> may include postBatchResumeToken
   |
   v
Driver/cursor can maintain an up-to-date resume token
```

This prevents consumers from keeping an ancient checkpoint while server history moves forward.

**One crucial rule applies:** never checkpoint a PBRT **ahead of events the application received but has not finished processing**. Advance the token only once every prior event in stream scope has been durably handled.

### Event Tokens vs. PBRT

- **Event token:** read from `change._id` or `ChangeStreamDocument.getResumeToken()`.
- **PBRT:** obtained from server/driver batch/cursor metadata—never derived from a wall clock.
- **Persisted token:** must reflect **the safe processed frontier**, not necessarily the newest token cached in driver memory.

The MongoDB Java Sync Driver provides Change Stream cursor APIs to access the cursor's current resume token on supporting versions. Before checkpointing during idle periods, understand **cursor buffering, batch processing, and side-effect ordering**.

A simple, safe starting pattern for beginners is checkpointing **event tokens after successful processing**, and adopting PBRT only once batching and idle semantics are thoroughly controlled.

## 11. Reopening a Stream After Restart in `mongosh`

Assume `consumerCheckpoints` exists, the consumer processes events sequentially one by one, and processing is idempotent.

```javascript
use change_stream_lab

const consumerId = "orders-sync-v1";
const saved = db.consumerCheckpoints.findOne({
  _id: consumerId
});

const watchOptions = {
  fullDocument: "updateLookup",
  maxAwaitTimeMS: 2000
};

if (saved && saved.resumeToken) {
  watchOptions.resumeAfter = saved.resumeToken;
}

const cursor = db.orders.watch([], watchOptions);

try {
  while (cursor.hasNext()) {
    const change = cursor.next();

    // Simple read-model example: record event receipt keyed by token.
    // Illustrates an idempotent side effect inside MongoDB only.
    db.processedChanges.updateOne(
      { _id: change._id },
      {
        $setOnInsert: {
          operationType: change.operationType,
          documentKey: change.documentKey,
          processedAt: new Date()
        }
      },
      {
        upsert: true,
        writeConcern: { w: "majority" }
      }
    );

    // Checkpoint ONLY AFTER the side effect above succeeds.
    db.consumerCheckpoints.updateOne(
      { _id: consumerId },
      {
        $set: {
          resumeToken: change._id,
          updatedAt: new Date(),
          state: "RUNNING",
          streamScope: "change_stream_lab.orders",
          pipelineVersion: 1
        }
      },
      {
        upsert: true,
        writeConcern: { w: "majority" }
      }
    );

    print("Processed:", change.operationType);
  }
} finally {
  cursor.close();
}
```

With `maxAwaitTimeMS`, empty batches cause the cursor to wait for subsequent batches; the `hasNext()` loop runs indefinitely. This snippet **does not stop automatically after a fixed event count**. Real services require shutdown handling, error classification, and backoff/restart logic.

### Limitations of This Example

- `processedChanges` and `consumerCheckpoints` are **two separate writes**. A crash right after the first can replay the event; the `_id` key prevents duplicate receipt records.
- If the real side effect is sending email, this example **is not sufficient** to guarantee an email is sent only once.
- If **two consumer instances share the same `consumerId`**, both will process events and overwrite each other's checkpoints. You need leader election, leases/fencing tokens, or partitioned ownership—never run multiple uncoordinated consumers on one checkpoint.
- `fullDocument: "updateLookup"` retrieves the current document on updates, but `fullDocument` may differ from the snapshot "right after the update" if subsequent edits or deletes occurred. Never treat it as an exact historical snapshot.
- Without an existing checkpoint, this code starts from current time. Systems needing full historical accuracy must run bootstrap/reconciliation first; this snippet demonstrates the mechanics, **not a complete production initialization flow**.

## 12. When a Consumer Stops for Too Long: What Is the Oplog History Window?

In a standard replica set, the oplog is a **capped collection** (or size/retention-bounded log). As new writes arrive, older entries are overwritten to stay within capacity and retention limits. Consequently, the resumable window is **never infinite**.

```text
Past time -------------------------------------------> present

  E01  E02  E03  E04  E05  E06  E07  E08  E09  E10
                 |===============================|
                 |    history still retained     |
                 |         in the oplog          |

Consumer checkpoint: T02
                       |
                       v
                  E02 is gone
                  insufficient history

resumeAfter(T02) -> fails due to oplog history lost
```

Once the entry needed to locate the continuation point is gone, MongoDB cannot recover it from an opaque resume token alone.

### Oplog Window Duration Is Not Fixed

For a fixed-size oplog:

- During quiet write periods, history may span days.
- During traffic spikes, the same capacity fills rapidly, **shrinking the effective time window**.
- Bulk loads, migrations, mass updates, or backfills flood the oplog and sharply raise the risk of consumers falling behind.

Therefore, "24 hours of oplog" is **a workload-dependent estimate**, not a fixed SLA unless your deployment enforces time-based retention guarantees.

### Sharded Clusters Have Multiple Histories to Track

In a sharded cluster, each shard is an independent replica set with its own oplog. A Change Stream may watch changes across multiple shards; history loss on **even one shard** can break resumability for a multi-shard stream.

Never inspect oplog retention on just one busy shard and assume the whole cluster is safe. Monitor retention and replication health across **all participating shards** and account for topology changes or shard removals per version.

## 13. Detecting When History Is Lost and Resumption Fails

When resuming fails because needed history is gone, MongoDB returns an error indicating **Change Stream history lost**, such as `ChangeStreamHistoryLost`. Exact error codes, messages, and error labels vary across server and driver versions.

Other conditions can also make resuming fail:

- Token belongs to an incompatible scope, namespace, or configuration.
- Collection was dropped/renamed and the stream emitted `invalidate`.
- Token was stored missing fields, with altered BSON types, or manually edited.
- Pipeline changes broke the resume token `_id`.
- Access privileges were revoked, network failed, topology lost primary, or the server does not support a requested option.

**Do not lump every stream-open failure into "history lost."** Distinguish transient retryable errors, invalid token/pipeline errors, and genuine history loss requiring a **rebuild**.

### Why Infinitely Retrying Does Not Fix Oplog History Loss

```text
Checkpoint T1000
      |
      v
History containing T1000 was overwritten
      |
      v
resumeAfter(T1000) -> history lost
      |
      v
retry same token -> lost history still does not exist
```

Retrying thousands of times per minute only wastes CPU and floods logs—it will never bring back an evicted oplog entry. Once **non-resumable history loss** is confirmed, the consumer must **halt normal checkpoint progression** and transition to controlled recovery.

### Never Silently Delete the Checkpoint and Open a Fresh Watch

Wrong handling:

```javascript
// WRONG for any consumer that must not miss events
try {
  // watch({ resumeAfter: oldToken })
} catch (e) {
  db.consumerCheckpoints.deleteOne({ _id: "orders-sync-v1" });
  db.orders.watch(); // starts from "now", skipping the gap
}
```

If events between T1000 and "now" have not reached the read model, starting a fresh stream from "now" **permanently drops them**. The fact that the cursor stops throwing errors does not mean downstream data is consistent.

## 14. Classifying Errors Before Recovering

| Scenario | Symptoms | Appropriate Response |
| --- | --- | --- |
| Brief network drop | Socket errors, server selection errors, retryable | Backoff and reconnect using checkpointed token |
| Primary failover | No primary briefly or topology shift | Wait for topology stabilization and resume from token |
| Driver-labeled resumable error | Driver/server permits resume | Rely on auto-resume or reopen from durable token |
| `ChangeStreamHistoryLost` | Oplog lacks needed history | Mark `NEEDS_REBUILD`; run reconciliation/cutover |
| `invalidate` from drop/rename | `invalidate` event and closed stream | Evaluate `startAfter`, scope, and state rebuild if namespace changed |
| Corrupted/edited BSON token | Invalid resume token or parse error | Restore valid checkpoint backup or rebuild; never "patch" tokens by guessing |
| Token from mismatched scope/pipeline | Inconsistent resume or pipeline rule violation | Stop consumer, inspect version/scope, reinitialize deliberately |
| Permission error | Unauthorized / missing watch privilege | Fix roles/credentials; never delete checkpoints |
| Side-effect failure | Sink API/DB rejects write | **Do not** checkpoint event; retry processing with idempotency |

### A Simple State Machine

```text
              STARTING
                  |
        load valid checkpoint
                  |
                  v
               RUNNING
            /     |     \
           /      |      \
     network   sink err  history lost
        |         |          |
        v         v          v
    RETRYING  RETRY_EVENT  NEEDS_REBUILD
        |         |          |
        +---------+          v
            |           RECONCILING
            |                |
            v                v
          RUNNING <---- SAFE_CUTOVER
```

`NEEDS_REBUILD` must surface visibly in monitoring. Never log a single warning line and keep serving stale downstream data as if no gap existed.

## 15. When History Is Lost: Resynchronizing Data

When resuming from the old checkpoint is impossible, distinguish two classes of target systems:

1. **Read models/caches reconstructible from current MongoDB state**: e.g., a search index reflecting live documents. Run a full snapshot/reconciliation and resume change tracking from a safe cutover point.
2. **Systems requiring every exact historical transition**: e.g., compliance ledgers recording every status hop. A current snapshot **cannot reconstruct lost intermediate transitions**. You must restore from an independent historical source—such as a durable event log, audit ledger, archive, retained backup/oplog—if one exists.

**No general algorithm can turn a current snapshot into every past update and delete.** If a document changed from A to B and back to A, the final state A reveals nothing about the two intermediate transitions.

### Three Recovery Tiers

| Requirement | Recovery Approach | Limitation |
| --- | --- | --- |
| Need current state only | Full rebuild or reconciliation with a safe cutover anchor | Must avoid gaps between snapshot and new stream |
| Need near-real-time updates; history loss tolerable | Open fresh stream after explicitly signaling degraded/lost state | Must never claim full historical sync |
| Need zero lost events | Restore from independent durable history outside the oplog | Without such a source, lost history cannot be recovered |

Critical business systems must decide which recovery tier is acceptable **before** history loss happens.

## 16. Why "Snapshot First, Then Open a New Stream" Can Lose Events

This is a classic design bug:

```text
t0: start scanning collection
t1: read order-1001, status = pending
t2: user updates order-1001 -> paid
t3: snapshot completes
t4: open change stream starting from current time

Snapshot read pending at t1.
Update event occurred at t2.
Stream only starts at t4.

=> Read model can stay stuck at pending forever.
```

Running a full `find()` before calling `watch()` **is not safe** if writes continue during the scan. This is the **snapshot-to-stream gap**.

### You Need a Safe Transition Boundary

Two common solution families exist:

**A. Short-term write quiesce/fencing.**

Put the source into a controlled state with no concurrent writes, rebuild current state, capture a fresh stream checkpoint **before reopening writes**, and resume from that checkpoint. Fencing must block background jobs, other consumers, and writers across all relevant shards.

**B. Stream-first, durably buffer changes during the snapshot.**

Establish a valid watch starting point; while scanning the snapshot, **durably buffer incoming events**. Then apply the snapshot and replay buffered changes from a consistent boundary—handling duplicates and ordering—before switching to live processing. This is more complex, especially across multi-collection or sharded snapshots, requiring clear consistency and cutover rules.

Both approaches tackle the same problem: **every change occurring between the snapshot and live stream must be accounted for** without slipping through a gap.

## 17. Recovery with Write Quiescing: Controlled Workflow Illustration

Suppose the sink is an `orderReadModel` collection rebuildable from `orders`. A conceptual procedure:

1. **Mark the consumer `NEEDS_REBUILD`**, keeping the failing token for investigation. Block older consumers from writing new `RUNNING` checkpoints.
2. **Fence writers:** pause or coordinate all writers to the source namespace so no mutations enter during transition. Enforce this cleanly in app/infrastructure layers rather than killing one random instance.
3. **Rebuild the sink** from stable source data. Build into a new collection or generation to avoid serving a half-built read model.
4. **Establish a valid resume anchor while writes remain fenced.** Open a new Change Stream and obtain a persistable token, or write a **barrier event** inside the watched stream scope to capture a deterministic event token per server/driver capabilities.
5. **Durably persist the token and generation/cutover state** with appropriate write concern.
6. **Switch readers to the rebuilt sink**, start the consumer from the new token, and release the write fence in order.
7. **Monitor** event lag, sink consistency, and recovery errors.

```text
Writer:   -- active -- |== FENCE ==| ----- active ---->
                       |           |
Snapshot:              |== REBUILD |
                                   |
Resume anchor:                     Tnew
                                   |
Consumer:                          +-- resumeAfter(Tnew) -->
```

### What Is a Barrier Event?

A **barrier event** is an intentional mutation whose token the consumer can capture once all other application writers are fenced. For example, in a **lab** you can update a metadata document inside the watched collection, ensuring the watch pipeline **does not filter out the marker event before reading its token**.

```javascript
// LAB ILLUSTRATION OF A BARRIER MECHANISM ONLY,
// NOT AN AUTOMATED PRODUCTION COMMAND.
db.orders.updateOne(
  { _id: "__stream_barrier__" },
  {
    $set: {
      kind: "__stream_barrier__",
      barrierId: "rebuild-2026-11-14",
      createdAt: new Date()
    }
  },
  { upsert: true, writeConcern: { w: "majority" } }
);
```

The consumer observes the barrier event, confirms all changes prior to that boundary are covered by the snapshot/rebuild, and persists the barrier's resume token. In real systems, isolate markers from business data and prove the ordering of fence/snapshot/marker/consumer on your topology.

**Never lift the write fence before establishing a safe resume anchor.** If the consumer still points at the expired token, finishing a rebuild without a valid new checkpoint simply loops right back into history loss.

## 18. Recovery Without Stopping Writes: Stream-First + Snapshot + Replay

When writes cannot be paused, a common architecture is **capturing changes before scanning state**:

```text
t0: open new change stream, capture resume anchor
          |
t1: start durably buffering new events into a staging log
          |
t2: capture snapshot / scan source
          |
t3: snapshot completes
          |
t4: replay staged events using cutover rules
          |
t5: transition to live processing
```

Correctness requires:

- **Stream anchor remains valid and retained** throughout recovery.
- **Durable staging log**, not an in-RAM array; if recovery restarts mid-rebuild, staged events must still be replayable.
- **Consistent snapshot or sound reconciliation algorithm** deciding which events must replay and when duplicates can be dropped.
- **Proper event application ordering** matching business logic and source writes.
- **Preventing the staging consumer from lagging** so far behind that the new stream itself falls out of the oplog window.
- **Cutover fencing/epochs** so an older consumer cannot overwrite checkpoints once the new consumer starts.

### Never Blindly Replay Old Events Over a Newer Snapshot

Example:

```text
t0: stream opens
t1: order-1001 changes pending -> paid; event E1 buffered
t2: snapshot reads order-1001 as paid
t3: order-1001 changes paid -> refunded; event E2 buffered
t4: snapshot completes
```

If the sink loads the final snapshot and blindly overwrites with E1 then E2 without ordering checks, it might happen to survive in a trivial case—yet across multiple collections, deletes, partial field updates, interleaved events, and non-atomic snapshots, state corrupts.

To guarantee accuracy, use an **explicit snapshot/cutover boundary** or version/ID-based reconciliation rather than "read snapshot first, replay all buffered events afterward." For sharded clusters and multi-collection data, prefer a CDC bootstrap framework proven on that topology.

### When No Consistent Snapshot Is Available

If writes cannot be fenced, no consistent snapshot is available, and no sound reconciliation algorithm exists, no manual rebuild can claim to be **lossless**. Explicitly document the **consistency gap** or adopt infrastructure supporting reliable bootstrap workflows.

## 19. Oplog Retention: Monitor Before an Outage Strikes

History helps only if the consumer can still resume in time. Monitor:

- **Timestamp of the latest durable processed checkpoint**.
- **Lag between event creation and checkpointing** (consumer lag).
- **Age of the oldest oplog entry still retained** across relevant replica sets/shards.
- **Peak write rate and oplog volume** during busy hours.
- **Reconnect/resume counts**, non-resumable errors, and rebuild triggers.
- **Sink throughput**, backlog depth, and side-effect completion latency.
- **Rebuild duration and cost** if full resync becomes necessary.

### Inspecting the Oplog on a Lab Replica Set

With appropriate privileges:

```javascript
rs.printReplicationInfo();
```

This reports oplog size and the time span between oldest and newest entries currently present. In a sharded cluster, run and collect this from **every relevant shard replica set**, never from `mongos` alone and never assuming all shards share identical windows.

For deeper inspection on a **lab replica set**, if the account can read `local`:

```javascript
db.getSiblingDB("local")
  .getCollection("oplog.rs")
  .find({}, { ts: 1 })
  .sort({ $natural: 1 })
  .limit(1);
```

This is a **read-only** query to inspect the oldest visible oplog entry. Never directly modify or delete `local.oplog.rs`. Time comparisons must respect **BSON Timestamps**, cluster clocks, and host clock skew.

### Never Rely on One Rigid Time Threshold

Suppose monitoring shows:

```text
Current consumer lag:        45 minutes
Observed oplog window:       6 hours
```

You have headroom, yet **never guarantee 5 hours 15 minutes of safety**. A sudden write spike can shrink the oplog window before the consumer catches up.

Trigger alerts when lag reaches a **conservative percentage** of remaining history, alongside alerts for backlog growth and stalled checkpoints. Exact thresholds depend on SLAs, traffic spikes, and recovery time.

## 20. Role of Oplog Size and Retention Configuration

Some deployments let you configure oplog size or retention parameters depending on server version. Expanding history gives consumers more breathing room after outages, though you must evaluate:

1. Disk, I/O, and operational cost on the replica set.
2. Actual write byte rate (not just modified document count).
3. Secondary replication lag and sync capacity.
4. Number of consumers and each consumer's checkpoint pace.
5. Behavior when one shard sees a sudden traffic burst.

**Tuning oplog configuration does not replace durable checkpoints or idempotency.** It only widens the resumable window. If events are already lost or consumers require retention exceeding practical oplog capacity, use an independent durable event store.

In managed MongoDB deployments, oplog/retention tuning may be restricted or handled differently from self-managed clusters. Do not prescribe server config tweaks to mask a slow consumer without evaluating the full system.

## 21. `invalidate` Errors Are Not `history lost`

A Change Stream can be **invalidated** by namespace operations such as collection drop or rename within the watched scope.

```text
Collection orders active
        |
        v
   drop / rename
        |
        v
  invalidate event
        |
        v
   stream ends
```

This is not necessarily an oplog history-loss issue. The stream emitted a valid **`invalidate` event** and closed per specification.

Distinguish the two cases:

- **Oplog history lost:** `resumeAfter` with the old token cannot locate needed history. Evaluate rebuild/reconciliation.
- **Received `invalidate` event:** observed a scope-terminating event. You can open a new stream via `startAfter` with the **invalidate token** where supported, though you must reassess **namespace and source data**.

If `orders` was dropped and recreated, the old read model may hold orders absent from the new collection. Resuming past `invalidate` **does not automatically purge stale read-model entries**. You need a collection-lifecycle policy.

## 22. Pipelines Can Make Resume Tokens Invalid

Change Streams return events with `_id` as the resume token. Transformation pipelines can accidentally alter or drop this field.

Bad example:

```javascript
db.orders.watch([
  {
    $project: {
      _id: 0,
      operationType: 1,
      documentKey: 1
    }
  }
]);
```

This strips `_id`, removing the resume token. Change Streams require the token for resumption; the server rejects pipelines that drop or modify it. Likewise, never replace `_id` with `documentKey._id`.

### A Simple Filter

```javascript
db.orders.watch([
  {
    $match: {
      operationType: {
        $in: ["insert", "update", "replace", "delete"]
      }
    }
  }
]);
```

Filters cut unnecessary traffic to the application, yet **changing filters across consumer versions alters processing semantics**. If a checkpoint came from an old pipeline, the new pipeline may skip events handled differently before—or vice versa. Therefore, store `streamScope` and `pipelineVersion` alongside the token, and plan migration/cutover whenever filtering logic changes materially.

Changing namespaces or options like `fullDocument` also affects side effects; never assume deploying a new pipeline is automatically compatible with an old checkpoint.

## 23. Java MongoDB Sync Driver: Durable Token Consumer

The MongoDB Java Sync Driver provides:

- `ChangeStreamIterable<T>` to configure the stream.
- `ChangeStreamDocument<T>` to read events.
- `MongoChangeStreamCursor<T>` to iterate the cursor.
- `resumeAfter(BsonDocument)` and `startAfter(BsonDocument)` for positioning.
- `getResumeToken()` on events to obtain the BSON token.

The code below illustrates a **sequential consumer** storing event receipts and checkpoints as BSON documents without lossy string serialization. The sink simply marks seen events in a collection; production services should replace that with actual side effects and add ownership coordination.

### 23.1. Java Code

```java
import com.mongodb.WriteConcern;
import com.mongodb.client.ChangeStreamIterable;
import com.mongodb.client.MongoChangeStreamCursor;
import com.mongodb.client.MongoClient;
import com.mongodb.client.MongoClients;
import com.mongodb.client.MongoCollection;
import com.mongodb.client.MongoDatabase;
import com.mongodb.client.model.Filters;
import com.mongodb.client.model.ReplaceOptions;
import com.mongodb.client.model.UpdateOptions;
import com.mongodb.client.model.changestream.ChangeStreamDocument;
import org.bson.BsonDateTime;
import org.bson.BsonDocument;
import org.bson.BsonString;
import org.bson.Document;

import java.util.Date;
import java.util.concurrent.TimeUnit;

public class DurableChangeStreamConsumer {
    private static final String CONSUMER = "orders-sync-v1";

    public static void main(String[] args) {
        String uri = System.getenv("MONGODB_URI");
        if (uri == null || uri.isBlank()) {
            throw new IllegalStateException("Missing MONGODB_URI");
        }

        try (MongoClient client = MongoClients.create(uri)) {
            MongoDatabase db =
                client.getDatabase("change_stream_lab");

            MongoCollection<Document> orders =
                db.getCollection("orders");

            // Store checkpoint as intact BSON without slicing _data.
            MongoCollection<BsonDocument> checkpoints =
                db.getCollection(
                    "consumerCheckpoints",
                    BsonDocument.class
                ).withWriteConcern(WriteConcern.MAJORITY);

            MongoCollection<BsonDocument> receipts =
                db.getCollection(
                    "processedChanges",
                    BsonDocument.class
                ).withWriteConcern(WriteConcern.MAJORITY);

            BsonDocument saved = checkpoints.find(
                Filters.eq("_id", CONSUMER)
            ).first();

            ChangeStreamIterable<Document> stream =
                orders.watch().maxAwaitTime(2, TimeUnit.SECONDS);

            if (saved != null
                    && saved.containsKey("resumeToken")
                    && saved.isDocument("resumeToken")) {
                stream = stream.resumeAfter(
                    saved.getDocument("resumeToken")
                );
            }

            try (MongoChangeStreamCursor<
                    ChangeStreamDocument<Document>> cursor =
                    stream.cursor()) {

                while (!Thread.currentThread().isInterrupted()) {
                    ChangeStreamDocument<Document> event =
                        cursor.tryNext();

                    if (event == null) {
                        // No new event in this poll cycle.
                        // Never fabricate tokens with System.currentTimeMillis().
                        continue;
                    }

                    BsonDocument token = event.getResumeToken();
                    if (token == null) {
                        throw new IllegalStateException(
                            "Event has no resume token"
                        );
                    }

                    // Illustrates idempotent receipt:
                    // same event token produces at most one record.
                    BsonDocument receipt = new BsonDocument()
                        .append("operationType",
                            new BsonString(
                                event.getOperationType().toString()
                            ))
                        .append("processedAt",
                            new BsonDateTime(
                                System.currentTimeMillis()
                            ));

                    receipts.updateOne(
                        Filters.eq("_id", token),
                        new BsonDocument(
                            "$setOnInsert", receipt
                        ),
                        new UpdateOptions().upsert(true)
                    );

                    // Checkpoint ONLY AFTER processing succeeds.
                    BsonDocument newCheckpoint = new BsonDocument()
                        .append("_id", new BsonString(CONSUMER))
                        .append("resumeToken", token)
                        .append("updatedAt",
                            new BsonDateTime(
                                System.currentTimeMillis()
                            ))
                        .append("state", new BsonString("RUNNING"))
                        .append("streamScope",
                            new BsonString("change_stream_lab.orders"));

                    checkpoints.replaceOne(
                        Filters.eq("_id", CONSUMER),
                        newCheckpoint,
                        new ReplaceOptions().upsert(true)
                    );

                    System.out.println(
                        "Checkpointed event: "
                            + event.getOperationType()
                    );
                }
            }
        }
    }
}
```

This code requires a compatible `mongodb-driver-sync` dependency and `MONGODB_URI` pointing to a replica set or sharded cluster supporting Change Streams. It cannot demonstrate real streams against a standalone `mongod`.

### 23.2. Key Takeaways in the Java Example

1. **Checkpoint loaded on startup:** if a BSON token exists, `resumeAfter(token)` is applied before opening the cursor.
2. **Event token preserved as `BsonDocument`:** never substitute `event.getDocumentKey()`.
3. **Receipt keyed uniquely by token:** illustrates preventing duplicate receipt inserts on replay.
4. **Checkpoint after side effect:** if writing the receipt throws, execution never reaches checkpoint persistence.
5. **Majority write concern:** applied to both receipt and checkpoint collections to reduce rollback risk during failovers.
6. **Cursor closed via try-with-resources:** prevents resource leaks on consumer shutdown.

**Limitation to emphasize:** because receipt and checkpoint are two separate writes, a crash can leave a written receipt with an unadvanced checkpoint; on restart, the event replays and the receipt update behaves idempotently. If the real side effect increments money/counters or calls external APIs, add explicit deduplication or transactions/outbox patterns.

This example omits leader leases, health reporting, backoff, idle PBRT handling, and `history lost` classification. It is a **core persistence-order template**, not an unattended production daemon.

## 24. Java: Detecting History Loss and Halting Checkpoint Progression

Service error orchestration should distinguish these cases:

```text
watch/resumeAfter
      |
      +-- success -----------> process event
      |
      +-- transient error ---> retry/backoff and resume
      |
      +-- history lost ------> NEEDS_REBUILD
      |
      +-- invalid token -----> inspect checkpoint/scope
      |
      +-- invalidate --------> evaluate startAfter & rebuild
```

Pseudocode illustrating the policy:

```java
// PSEUDOCODE: methods represent application-defined contracts.
try {
    runConsumerFromDurableCheckpoint();
} catch (ChangeStreamHistoryLostSignal error) {
    markConsumerState("NEEDS_REBUILD");
    stopPublishingStaleReadModel();
    notifyOperations(error);
    // Never delete the token and treat lost history as normal.
    executeControlledRebuildAndCutover();
} catch (TransientStreamSignal error) {
    backoff();
    reopenFromLastDurableCheckpoint();
}
```

The exception names `ChangeStreamHistoryLostSignal` and `TransientStreamSignal` are **illustrative classes/predicates, not built-in MongoDB Java Driver exceptions**. In real code, inspect `MongoException` subclasses, error codes, names, and error labels provided by your driver/server version. Never write `catch (ChangeStreamHistoryLostSignal)` in production unless you defined it yourself.

### When Checkpoint Commit Outcome Is Unknown

A checkpoint write with `w:"majority"` can return a write-concern timeout. That **does not prove the checkpoint was not written**. Therefore:

- Do not blindly advance to subsequent events assuming "it probably saved."
- Re-read checkpoint state with an appropriate read concern or retry per application write policy.
- Keep side effects idempotent, since the consumer may replay the event if persistence state was ambiguous.

Never switch from `resumeAfter` to `startAfter` merely because of a network timeout: the two options serve different purposes.

## 25. Multi-Instance Consumers: Only One Owner May Advance the Checkpoint

Suppose two processes A and B both run consumer `orders-sync-v1`:

```text
Process A: receives E101 -------> saves token T101
Process B: receives E105 -------> saves token T105
Process A: receives E102 -------> saves token T102

Final checkpoint = T102  (regressed by A)
```

Both processes can also deliver duplicate events to the sink. That is why beyond resume tokens you need **consumer ownership**:

- Use **distributed leases** with expiration and contention handling.
- Use **fencing tokens/epochs** so a stale consumer cannot write checkpoints after leadership moves.
- Store a checkpoint version and update conditionally (*compare-and-swap*).
- When scaling by partition, design **independent streams and checkpoints**, never letting multiple workers write to one shared checkpoint uncoordinated.

### Example Checkpoint Format with Epoch

```javascript
{
  _id: "orders-sync-v1",
  resumeToken: { _data: "..." },
  ownerId: "instance-B",
  epoch: NumberLong(12),
  state: "RUNNING",
  updatedAt: ISODate("2026-11-14T00:00:00Z")
}
```

This is an **illustrative document**, not a server-generated checkpoint. With fencing enabled, token updates must assert both `ownerId` and `epoch` still match, not `_id` alone.

Never compare `resumeToken._data` strings using `>` or `<` to decide which checkpoint is newer. Tokens are opaque; enforce **write ownership and processing order** in application logic.

## 26. Latency and Backpressure: Keeping Tokens Alive Long-Term

Suppose events arrive at 5,000 events/sec while the consumer processes 3,000 events/sec. Backlog grows by 2,000 events every second. Even with zero network errors, the consumer eventually falls behind the oplog's retained history.

```text
Source rate:     5,000 events/s
Sink rate:       3,000 events/s
                 ---------------
Backlog growth:  2,000 events/s

Without throughput improvements or architectural changes,
consumer lag keeps climbing into the danger zone.
```

Mitigation levers:

1. **Measure processing lag and throughput** per stream.
2. **Reduce side-effect cost:** safe batched checkpoints, indexed sinks, avoiding unnecessary lookups.
3. **Trim event volume** with valid filters without dropping required business events.
4. **Optimize source and sink:** I/O, networking, connection pools, CPU resources.
5. **Add coordinated parallelism**, where ordering and ownership allow.
6. **Widen the history window** where supported, though never as a substitute for fixing unbounded backlog growth.
7. **Buffer into a durable queue** to decouple source speed from sink speed, checkpointing only after events are durably enqueued.

### Batch Checkpointing: Safety Conditions

You can persist a checkpoint every 100 processed events instead of every event:

```text
Receive 100 events
      |
      v
Process ALL events 1..100 successfully
      |
      v
Persist token of event 100
```

If any event in the batch fails, never checkpoint past it. If a crash occurs mid-batch, processed events before the failure will replay; the sink still requires idempotency.

### Parallel Processing Must Respect the Safe Commit Frontier

If E101 finished, E102 is pending, and E103 finished, **never checkpoint T103** merely because E103 finished first. A safe checkpoint may advance only to the end of the **contiguous completed prefix** in stream order:

```text
E101 [done] -- E102 [pending] -- E103 [done] -- E104 [done]
                 |
                 v
         safe checkpoint must still wait for E102
```

For an ordered stream, parallel processing makes checkpointing significantly harder. Beginners should favor sequential processing where correctness is straightforward to verify.

## 27. Relationship Between `fullDocument`, `delete`, and Rebuilding Read Models

An `update` change event normally carries `updateDescription` with modified fields; when configured with:

```javascript
db.orders.watch([], {
  fullDocument: "updateLookup"
})
```

the server looks up and attaches the current document image. However:

- `fullDocument` can be missing if the document was deleted before lookup or the event type does not supply one.
- Under concurrent updates, `fullDocument: "updateLookup"` must never be treated as the exact snapshot **at the moment of that update event** under all conditions.
- For `delete`, the event gives `documentKey` to identify the deleted record; there is no "current document" to look up as with an insert.
- If exact **pre-/post-images** are needed for auditing, evaluate support, configuration, and retention of change stream pre-/post-images for your version. Never assume the oplog keeps every document image forever.

### Latest-State Reconciliation

For a search index:

```text
insert/update/replace -> update search document
delete                -> remove search document
rebuild               -> scan current orders state
                         and swap index generation
```

This design **converges to current state** with a proper cutover workflow. However, if the sink acts as a **ledger of every balance delta**, a current snapshot cannot replace lost intermediate insert/update/delete events.

## 28. Checkpointing After Special Events and Namespace Changes

Change Streams can also emit namespace/topology events depending on watch scope and server version. Before checkpointing, define an explicit policy:

| Event Type | Decision Required |
| --- | --- |
| `insert` | Create read-model record or trigger business action? |
| `update` | Use `updateDescription` or look up document? |
| `replace` | Replace entire state or merge fields? |
| `delete` | How to remove the record from the sink? |
| `drop` / `rename` | How does collection/namespace lifecycle affect the sink? |
| `invalidate` | Close stream and decide on `startAfter` vs. rebuild? |
| Version-specific new events | Will the consumer explicitly accept, flag, or skip them? |

A consumer supporting **only insert/update** that blindly checkpoints past `delete` leaves "ghost" records in the sink. If business rules require reflecting deletes, that is silent data loss even though the resume token keeps advancing.

Updating `pipelineVersion` whenever filters or handlers change prevents resuming an old checkpoint with incompatible event semantics.

## 29. Alerts and Operations Playbook

In production, configure alerts for:

| Metric / Signal | Purpose |
| --- | --- |
| `lastDurableCheckpointAt` | Is the consumer advancing checkpoints? |
| `lastEventClusterTime` | Processing lag relative to source |
| `oplogWindowEstimate` | Remaining resumable history span |
| `consumerLag` | Risk of exceeding the oplog window? |
| `resumableErrorCount` | Recurring network drops or failovers? |
| `nonResumableErrorCount` | Detect history loss and invalid tokens |
| `rebuildState` | Is the consumer serving live data or resyncing? |
| `pendingSinkWrites` | Backpressure or side-effect bottlenecks? |
| `checkpointWriteConcernErrors` | Are durable checkpoints failing? |
| `ownershipEpoch` | Detect stale leaders overwriting state |

### Playbook on History Loss

1. **Confirm the error class**; preserve logs, token, namespace, and versions for diagnosis.
2. **Block invalid checkpoint progression**; stop any other consumer from opening a fresh stream from "now" and silently skipping history.
3. **Classify the sink**: can current state rebuild it, or must every historical event be preserved?
4. **Select recovery mode**: quiesce writers + cutover, or stream-first with durable staging and consistent snapshot.
5. **Rebuild into a new generation** where possible; never serve half-rebuilt data.
6. **Establish the new resume anchor**, ensuring zero gap between snapshot and live stream.
7. **Reconcile counts and business invariants** before marking the consumer healthy.
8. **Monitor post-recovery lag** so the new stream does not fall out of the oplog again.
9. **Investigate root cause**: prolonged consumer downtime, slow sink, undersized oplog window, traffic spike, or checkpoint failure.

These steps are not instructions to shut down clusters or wipe oplogs. Replica set reconfiguration and high-risk recovery operations must follow formal operational plans, never improvised straight from lesson examples onto production.

## 30. Common Mistakes When Persisting Tokens and Resuming

| Symptom | Likely Cause | Fix |
| --- | --- | --- |
| Restart always begins at newest events | Token kept only in RAM or checkpoint never read | Persist full token and load on startup |
| Consumer skips an event | Checkpointed before side effect completed | Process first, checkpoint afterward |
| One event double-charges or double-counts | Replay after crash with non-idempotent side effect | Deduplicate, use transactional sink or operation IDs |
| Resume fails to locate history | Required oplog entries overwritten | Halt, flag history lost, rebuild/reconcile |
| `resumeAfter` retries fail forever | Non-resumable error; old token lost history | Stop infinite retries; enter recovery |
| Resume token rejected | Token altered, lost BSON types, or scope mismatch | Store raw BSON; check scope/pipeline/version |
| Resume after `invalidate` fails | Passing `resumeAfter` across `invalidate` | Use `startAfter` and handle lifecycle/rebuild |
| Fresh stream runs but sink misses data | Snapshot-then-watch gap or discarded checkpoint | Use safe cutover and reconciliation |
| Token regresses backward | Two consumers writing one checkpoint uncoordinated | Enforce fencing, leases, epochs, CAS |
| `_id` missing in stream events | Pipeline `$project` stripped the token | Preserve `event._id` intact |
| Checkpoint stalls when no events occur | Saving only event tokens without PBRT | Consider safely persisting PBRT when idle |
| Checkpoint advances ahead of sink | Saving cursor's latest token while events remain pending | Checkpoint only the safe processed frontier |
| Update `fullDocument` shows unexpected state | Lookup fetched current document after newer edits | Use `updateDescription` or proper pre-/post-images |
| Querying `documentKey` fails to locate position | Saved document ID instead of resume token | Persist event `_id` |
| Missing events in compliance audit | Oplog is not a permanent archive | Maintain an independent durable ledger/event log |
| Consumer lag grows endlessly | Sink throughput slower than source writes | Measure backlog, optimize cost, scale with coordination |

## 31. Practice Exercises and Answers

### Exercise 1. Choosing the Right Resume Token

A change event contains:

```javascript
{
  _id: { _data: "opaque-token" },
  documentKey: { _id: "order-1001" },
  operationType: "update"
}
```

Which value must you persist so a restart continues from the next event?

**Answer:** Persist **the entire `event._id`** as a BSON document. `documentKey._id` is the business document ID, not a stream position.

### Exercise 2. Checkpointing After Processing

A consumer finishes E1 and E2, then crashes while processing E3. The last durably saved token is T2. What happens upon restart?

**Answer:** `resumeAfter(T2)` returns E3 onward if history remains. If E3 already applied partial side effects before crashing, the application must handle duplicates via idempotency. Never save T3 before E3 finishes.

### Exercise 3. Why Not Checkpoint First?

A consumer receives E10, saves T10, and crashes before sending E10 to the sink. On restart it calls `resumeAfter(T10)`. Why does the sink lose E10?

**Answer:** Resuming starts **after E10**, so E10 is never redelivered. That is an ordering bug between side effect and checkpoint.

### Exercise 4. Oplog History Lost

A consumer is down for three days; calling `resumeAfter(oldToken)` returns history lost. Can retrying `resumeAfter(oldToken)` 1,000 more times fix it?

**Answer:** No. The needed history is gone from the oplog. Transition to recovery, determine whether to rebuild from current state or restore events from another archive.

### Exercise 5. Snapshot-to-Stream Gap

You scan a collection to rebuild a read model from 10:00 to 10:05, then open a Change Stream at 10:06. An update occurs at 10:03 right after that document was scanned. What goes wrong?

**Answer:** The 10:03 update is absent from the snapshot and precedes the new stream's start point, leaving a **gap**. Secure the seam using a write fence/barrier or stream-first + durable staging with an appropriate snapshot/reconciliation algorithm.

### Exercise 6. `resumeAfter` vs. `startAfter`

A collection is dropped, and the stream receives `invalidate` and closes. Should you call `resumeAfter(invalidateToken)` to continue past the invalidation?

**Answer:** No. `resumeAfter` cannot cross `invalidate`. `startAfter` opens a new stream after `invalidate` where permitted, though you must still address collection lifecycle and data state.

### Exercise 7. PBRT and In-Flight Events

The cursor returns a PBRT past E20, yet the sink has only completed through E18; E19 is still pending. Can you save the PBRT immediately?

**Answer:** No. Checkpointing past E19 risks skipping E19 on a crash. Persist tokens only up to the **safe frontier** of fully completed events.

### Exercise 8. Two Consumers Sharing One Checkpoint

Worker A writes T100, Worker B writes T110, then A writes T101. What went wrong and how do you fix it?

**Answer:** The checkpoint regressed and side effects may duplicate. Enforce single ownership via leases/fencing epochs or partition consumers with independent checkpoints; never compare token strings to determine order.

### Exercise 9. Missing Events in an Audit

A system must record **every single time** a user edits an order. The consumer suffers history loss, though you can `find()` all current documents. Can you reconstruct every historical event solely from `find()` results?

**Answer:** No. A document can transition multiple times and revert to an older value. You need another durable history source; current snapshots rebuild **final state** only, not every historical transition.

### Exercise 10. Strengths and Weaknesses of `updateLookup`

A consumer enables `fullDocument: "updateLookup"` and receives an update event. Can it assume `fullDocument` is always the exact image right when that update occurred?

**Answer:** No. Lookup may observe a newer state if subsequent edits happened, or return `null` if the document was deleted. Use `updateDescription` or exact pre-/post-images as required by business rules.

### Exercise 11. Checkpoint Write Concern

An application durably updates a sink, then writes the token to a checkpoint collection using only `w:1`. After a failover, the checkpoint rolls back while the sink retains the update. What happens?

**Answer:** The consumer replays already-processed events because the checkpoint rolled back, requiring an idempotent sink. Using `majority` write concern for checkpoints reduces rollback risk across routine failovers, though it does not eliminate duplicate-handling requirements.

### Exercise 12. Idle Stream with Zero Events

A consumer runs cleanly, yet an entire day passes with zero writes. The last event token is from yesterday. How can checkpoints advance during idle periods?

**Answer:** Use **post-batch resume tokens** via the server/driver cursor API once you understand the semantics and confirm zero pending events remain. Never fabricate tokens from wall clocks or guessed `clusterTime`s.

### Exercise 13. Filter Changes in a New Deployment

Consumer v1 watched only `insert`/`update`, while v2 adds `delete`. Can you resume from the old token and assume all historical deletes were already processed?

**Answer:** No. Deletes filtered out by the old pipeline never produced sink side effects. Evaluate filter-change impact, version checkpoints, and run rebuild/reconciliation to ensure target consistency.

### Exercise 14. Reading Lag Alerts

The source produces 8,000 changes/sec while the consumer processes 6,000/sec. Under steady conditions, how much does the backlog grow after 10 minutes?

**Answer:** A deficit of 2,000 events/sec. Over 600 seconds, the backlog grows by **1,200,000 events**. Without scaling throughput or changing architecture, the consumer approaches the oplog window danger line.

## 32. Compact Runbook Template for Operations Teams

When a consumer reports a resume failure, instead of deleting tokens and restarting blindly, record:

```text
CONSUMER_ID:
STREAM_SCOPE:
PIPELINE_VERSION:
CHECKPOINT_UPDATED_AT:
LAST_DURABLE_RESUME_TOKEN:
LAST_EVENT_CLUSTER_TIME:
ERROR_NAME / ERROR_CODE / ERROR_LABELS:
OPLOG_WINDOW_OBSERVED:
SOURCE_REPLICA_SET / SHARDS:
SINK_CONSISTENCY_STATUS:
RECOVERY_MODE:
RECOVERY_GENERATION:
NEW_ANCHOR:
CUTOVER_APPROVED_BY:
```

These fields are not mandatory MongoDB parameters; they are **operational telemetry** ensuring you can explain why a consumer resumed or required a rebuild.

### Criteria to Close the Incident

- Root cause identified: transient error, invalid token, `invalidate`, or oplog history loss.
- New checkpoint **durably persisted** matching the exact stream scope and pipeline.
- Sink rebuilt/reconciled via a process **with zero gaps or explicitly documented data-loss boundaries**.
- Consumer is processing and advancing checkpoints in order.
- Lag has dropped safely within the observed oplog window.
- No stale owner continues overwriting checkpoints or duplicating side effects.
- Key business counts and invariants verified as needed.

## 33. Summary

A **resume token** anchors a Change Stream consumer across restarts, yet remains useful only while **required history stays in the oplog** and the token matches the stream configuration. Keep the **BSON event `_id`** intact, persist checkpoints durably with proper write concern, and store stream scope and pipeline version to avoid token mismatches.

The safe default order is **process event successfully → persist checkpoint**. Since this can trigger replays after crashes, sinks must be **idempotent**; if sink writes and checkpoints must be atomic, use a supporting transaction or sink protocol. With parallel consumers, advance checkpoints only to the **contiguous completed frontier** and enforce ownership/fencing to prevent regressions.

Once oplog history is lost, **retrying the same token cannot recover purged events**. Never silently delete checkpoints and open a stream from "now," as that hides silent data gaps. Instead, classify business requirements: **rebuild current state** with a safe cutover between snapshot and live stream, or **restore events from durable archives** if full transition history is mandatory. Combining lag/oplog-window monitoring, clear recovery workflows, and idempotent processing is the foundation of reliable Change Stream operations.
