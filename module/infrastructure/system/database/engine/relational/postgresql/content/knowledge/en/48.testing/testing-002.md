# Sample Data, Seeding, and Reproducibility in PostgreSQL

Database testing is only valuable when the input data is sufficiently representative, recreatable, and does not depend on leftover state from a previous run. In PostgreSQL, **test data** is data used for testing; a **fixture** is a small dataset with a known structure and expected results; **seed** is the process of loading initial data into an environment; and **reproducibility** is the ability to recreate the same conditions and the same test results when re-run.

A good seed set needs to answer these questions:

- Where was the data generated from, and is it permitted for use in tests?
- Does each run produce the same baseline?
- Is the script safe to re-run?
- Are foreign-key relationships and sequences consistent?
- Do tests running in parallel affect one another?
- Are time, timezone, locale, collation, and random values stable?
- When a test fails, can the exact data and state that caused the failure be recreated?

The lesson **"Sample Data, Seeding, and Reproducibility"**, belonging to the **Testing** chapter of the **Database Engine Relational PostgreSQL** module, covers how to design fixtures, repeatable seed scripts, synthetic data generation, controlling random values, managing identity/sequences, isolating tests, preparing CI data, and recording conditions to reproduce failures.

> **Principle:** a test must be able to create the input data it needs without relying on test execution order or leftover data. Seeds should be versioned, intentionally repeatable, and recreatable on a clean database.

---

## 1. Sample Data in Database Testing

Sample data is data generated or selected to verify the behavior of schemas, SQL queries, constraints, transactions, stored procedures, and applications.

For example, a sales system might need customers and addresses, products and categories, orders and order items, payments and shipments, order statuses, along with missing data, boundary data, and invalid data cases.

Test data does not have to be large. A small fixture can verify join logic, aggregations, and constraints more clearly than a multi-million-row production copy.

## 2. How Do Fixtures, Seeds, and Test Data Differ?

| Concept | Purpose | Example |
|---|---|---|
| Fixture | Describes a known dataset for a test | 3 customers and 4 orders |
| Seed | Loads initial data for an environment | Countries, roles, product catalog |
| Synthetic data | Fake data generated according to rules | 100,000 simulated orders |
| Anonymized data | Source data processed to reduce identifiability | Masked copy |
| Snapshot | Database state saved at a point in time | Database template or dump |

The concepts can overlap. A seed can load fixtures; a fixture can be created using synthetic data; a snapshot can be a way to distribute a baseline.

## 3. Why Is Reproducible Data Needed?

If every test run has different data, bugs can appear intermittently and become hard to reproduce.

Reproducibility helps compare results across runs, detect regressions, reproduce bugs from CI, run tests in parallel under control, determine whether a change came from code or data, debug query plans, and ensure migrations do not lose important data.

A bug that only occurs on a random dataset without saving the seed, generator version, and test parameters will be difficult to investigate.

## 4. Classifying Test Data

A test suite usually needs multiple types of data:

1. **Reference data:** countries, currencies, fixed statuses.
2. **Baseline fixtures:** small records to verify business logic.
3. **Boundary data:** min/max values, empty, NULL, and limits.
4. **Negative data:** data violating constraints to verify errors.
5. **Volume data:** large data to measure performance.
6. **Concurrency data:** multiple sessions reading/writing concurrently.
7. **Historical data:** timestamps and states across multiple periods.
8. **Migration data:** data representing older schemas/versions.

Do not use a single seed for every purpose if tests have different requirements.

## 5. Designing Fixtures Around Business Scenarios

Fixtures should describe business situations, not just be a list of rows. For example: a new customer with no orders; a customer with a paid order; an order with multiple items; an order canceled before payment; a payment that failed then succeeded on retry; an out-of-stock product; an order containing discount and tax; two transactions updating inventory concurrently.

A clearly named fixture helps readers understand why the data exists and which tests use it.

## 6. Small and Readable Fixtures

Example simple schema:

~~~sql
CREATE SCHEMA IF NOT EXISTS app;

CREATE TABLE IF NOT EXISTS app.customer (
    customer_id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_key text NOT NULL UNIQUE,
    display_name text NOT NULL,
    created_at timestamptz NOT NULL
);

CREATE TABLE IF NOT EXISTS app.orders (
    order_id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id bigint NOT NULL
        REFERENCES app.customer(customer_id),
    status text NOT NULL,
    total_amount numeric(12, 2) NOT NULL CHECK (total_amount >= 0),
    created_at timestamptz NOT NULL
);
~~~

A fixture can use fixed IDs:

~~~sql
INSERT INTO app.customer
    (customer_id, customer_key, display_name, created_at)
VALUES
    (101, 'cust-alice', 'Alice Test', '2025-01-10 09:00:00+00'),
    (102, 'cust-bob',   'Bob Test',   '2025-01-11 09:00:00+00');

INSERT INTO app.orders
    (order_id, customer_id, status, total_amount, created_at)
VALUES
    (1001, 101, 'paid',      125.50, '2025-01-12 10:00:00+00'),
    (1002, 101, 'cancelled',   0.00, '2025-01-13 10:00:00+00'),
    (1003, 102, 'pending',    49.99, '2025-01-14 10:00:00+00');
~~~

Using fixed IDs makes assertions easy to read and independent of sequence state. After inserting explicit identity values, synchronize the sequence if the test continues inserting rows using default identity generation.

## 7. Choosing Stable Keys for Fixtures

You can use a natural key with a unique constraint, a fixed UUID defined in the fixture, fixed integer IDs in an isolated test database, or a composite key reflecting business identity.

Avoid relying on insert order or assuming the first row always has ID 1. Sequence IDs can change due to prior tests, rollbacks, or parallel workers.

## 8. What Is an Idempotent Seed?

An idempotent seed can be re-run without creating duplicates or leaving the state nondeterministic.

Example using a unique natural key:

~~~sql
INSERT INTO app.customer
    (customer_key, display_name, created_at)
VALUES
    ('cust-alice', 'Alice Test', '2025-01-10 09:00:00+00')
ON CONFLICT (customer_key) DO NOTHING;
~~~

Re-running the script does not create another customer with the same key.

Idempotent does not necessarily mean re-running always resets data to its initial state. If a test modified a row, `DO NOTHING` preserves that modification. Choose the behavior that matches the seed's purpose.

## 9. DO NOTHING vs. DO UPDATE

The two conflict-handling approaches have different semantics.

| Approach | Result when key exists | Best suited when |
|---|---|---|
| DO NOTHING | Keeps existing row | Seeding reference data without overwriting |
| DO UPDATE | Resets specified columns to baseline | Keeping seed-owned fields synchronized |
| Delete then insert | Replaces row, can affect FKs | Used only in an isolated test database |
| TRUNCATE then seed | Deletes all data in scope | Resetting a dedicated environment |

Upsert example:

~~~sql
INSERT INTO app.customer
    (customer_key, display_name, created_at)
VALUES
    ('cust-alice', 'Alice Test', '2025-01-10 09:00:00+00')
ON CONFLICT (customer_key)
DO UPDATE SET
    display_name = EXCLUDED.display_name,
    created_at = EXCLUDED.created_at;
~~~

Only update columns owned by the seed. If you also overwrite business-state columns, you may accidentally erase traces that tests need to inspect.

## 10. Separating Baseline Data and Mutable Test Data

Reference data such as country codes or status definitions is usually stable. Business data in tests is frequently modified.

Separate baseline seeds, per-test fixtures, generated workloads, and test outputs. Do not share the same mutable row across multiple tests if they can run in parallel or alter each other's state.

## 11. Versioned Seeds

When seeds change over time, record a version or checksum to know which baseline the test database is using.

~~~sql
CREATE SCHEMA IF NOT EXISTS test_support;

CREATE TABLE IF NOT EXISTS test_support.seed_version (
    seed_name text PRIMARY KEY,
    version integer NOT NULL,
    applied_at timestamptz NOT NULL
);

INSERT INTO test_support.seed_version
    (seed_name, version, applied_at)
VALUES
    ('core-fixtures', 3, '2025-02-01 00:00:00+00')
ON CONFLICT (seed_name)
DO UPDATE SET
    version = EXCLUDED.version,
    applied_at = EXCLUDED.applied_at;
~~~

In a real project, seed versions should be managed by a migration/seed runner so a version is not accidentally marked applied when part of the script fails.

## 12. Running Seeds Inside a Transaction

A pure SQL seed should usually run inside a transaction so that if an error occurs, the seed data is not partially applied.

~~~sql
BEGIN;

INSERT INTO app.customer
    (customer_key, display_name, created_at)
VALUES
    ('cust-alice', 'Alice Test', '2025-01-10 09:00:00+00')
ON CONFLICT (customer_key) DO NOTHING;

INSERT INTO app.orders
    (order_id, customer_id, status, total_amount, created_at)
SELECT
    1001,
    customer_id,
    'paid',
    125.50,
    '2025-01-12 10:00:00+00'
FROM app.customer
WHERE customer_key = 'cust-alice'
ON CONFLICT (order_id) DO NOTHING;

COMMIT;
~~~

If a statement fails, the transaction can roll back all seed changes performed so far.

Some commands cannot run inside a transaction block, such as `CREATE DATABASE`, `VACUUM`, and `CREATE INDEX CONCURRENTLY`. Keep those operations in a separate setup step.

## 13. Loading Order According to Foreign Keys

If a child table references a parent table, load the parent before the child.

~~~text
country
   |
   v
customer
   |
   v
orders
   |
   v
order_item
   |
   v
payment
~~~

Seed order must respect the dependency graph. If circular relationships exist, consider designing deferrable constraints, creating records via an appropriate workflow, or splitting foreign-key updates into a post-insert step.

Do not disable constraints just to make seeding easier; doing so can hide data bugs.

## 14. Foreign Keys and Deferrable Constraints

Some schemas allow foreign key checks at the end of a transaction:

~~~sql
ALTER TABLE app.child
ADD CONSTRAINT child_parent_fk
FOREIGN KEY (parent_id)
REFERENCES app.parent(parent_id)
DEFERRABLE INITIALLY DEFERRED;
~~~

In that case, a transaction can insert rows in different orders as long as all references are valid at commit time.

Use `DEFERRABLE` only when business semantics allow it. It is not the default solution for every fixture.

## 15. Cleanup with TRUNCATE

In an isolated test database, tables can be reset:

~~~sql
TRUNCATE TABLE
    app.order_item,
    app.payment,
    app.orders,
    app.customer
RESTART IDENTITY;
~~~

`TRUNCATE` is faster than deleting many rows and can reset owned sequences with `RESTART IDENTITY`, but it acquires a strong lock and does not fire row-level `DELETE` triggers.

If `CASCADE` is used, PostgreSQL may also truncate referencing tables. Use it only when the entire scope is understood.

Never run this reset command on a shared or production database.

## 16. Cleanup with DELETE

`DELETE` is suitable when triggers need to run or when removing only records belonging to a fixture:

~~~sql
DELETE FROM app.orders
WHERE customer_id IN (
    SELECT customer_id
    FROM app.customer
    WHERE customer_key LIKE 'test-%'
);
~~~

Delete child rows before parent rows if foreign keys do not cascade. Cleanup must use an accurate predicate and must not delete another test's data.

## 17. Transaction Rollback for Test Isolation

A common pattern is running a test inside a transaction and rolling back:

~~~sql
BEGIN;

INSERT INTO app.customer
    (customer_key, display_name, created_at)
VALUES
    ('test-one', 'Test One', now());

-- Assertions and test operations.

ROLLBACK;
~~~

This works well for tests running sequentially on the same connection that do not need to observe results from another session.

However, not everything rolls back: sequence values from `nextval()` are not returned; certain external side effects and actions outside the database are also not undone. Tests needing multiple connections or real commits may require dedicated databases/schemas.

## 18. Sequences and Identity Columns

Identity columns use a sequence to generate values.

~~~sql
CREATE TABLE app.ticket (
    ticket_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title text NOT NULL
);
~~~

With `GENERATED ALWAYS`, explicit values are normally rejected unless `OVERRIDING SYSTEM VALUE` is specified. With `GENERATED BY DEFAULT`, the caller can supply an explicit value.

When seeding fixed IDs, ensure the sequence continues from an appropriate value so later inserts do not collide with the primary key.

## 19. Synchronizing Sequences After Explicit IDs

You can retrieve the sequence attached to a column using `pg_get_serial_sequence()`:

~~~sql
SELECT setval(
    pg_get_serial_sequence('app.customer', 'customer_id')::regclass,
    COALESCE((SELECT max(customer_id) FROM app.customer), 1),
    EXISTS (SELECT 1 FROM app.customer)
);
~~~

The third argument indicates whether the value has already been marked as called. If the table is empty, `is_called = false` so the next `nextval()` returns the set value. If the table has rows, `is_called = true` so the next call advances by the sequence increment.

`setval()` and `nextval()` have non-transactional semantics unlike ordinary table changes. Do not rely on transaction rollback to restore a sequence to its previous state.

## 20. Avoid Depending on Current Sequence Values

Tests should not assume a sequence's `last_value` is a fixed number. A sequence can advance due to other tests, rollbacks, caching, or concurrent sessions.

To locate a row, query by natural key or known fixture ID. To test sequence behavior, create a dedicated test with its own sequence and appropriate assertions.

## 21. Generating Data with generate_series

PostgreSQL provides `generate_series()` to create many rows without application loops.

~~~sql
INSERT INTO app.metric_sample
    (sample_id, metric_value, recorded_at)
SELECT
    n,
    (n::numeric * 7919 % 100000) / 100.0,
    timestamptz '2025-01-01 00:00:00+00'
        + n * interval '1 minute'
FROM generate_series(1, 10000) AS g(n);
~~~

The formula computing values from `n` should be deterministic: the same input range produces the same values. Choose data types and arithmetic carefully to avoid integer overflow.

Use `generate_series()` for volume tests, partitioning, index tests, and time-series workloads.

## 22. Creating Structured Synthetic Data

Volume data should not simply repeat a single value. Query planner and index behavior depend on data distribution.

You can generate uniform, skewed, sparse, time-correlated, high-cardinality, NULL-heavy, and boundary-heavy distributions.

Simple distribution example:

~~~sql
INSERT INTO app.event_log
    (event_id, tenant_id, event_type, occurred_at)
SELECT
    n,
    CASE
        WHEN n % 10 = 0 THEN 1
        ELSE 2 + (n % 500)
    END,
    CASE
        WHEN n % 20 = 0 THEN 'payment'
        WHEN n % 5 = 0 THEN 'login'
        ELSE 'view'
    END,
    timestamptz '2025-01-01 00:00:00+00'
        + n * interval '1 second'
FROM generate_series(1, 100000) AS g(n);
~~~

This dataset gives tenant 1 a higher share than other tenants to test skew.

## 23. Random Data and setseed()

PostgreSQL provides `random()` to generate pseudo-random values. You can set the session PRNG seed with `setseed()`:

~~~sql
SELECT setseed(0.42);

SELECT random()
FROM generate_series(1, 5);
~~~

With the same PostgreSQL implementation, the same seed, and the same call order in a single session, the resulting sequence can be reproduced.

However, do not treat the `random()` sequence as a stable contract across all major versions, implementations, or changes in query execution order. Parallelism and calling `random()` in different places can change the generated sequence.

## 24. When Should random() Not Be Used for Fixtures?

Do not use random values when a test needs fixed expected results—for example, a total amount must equal a specific number, a customer must have exactly three orders, a row must land in a specific partition, a query must return an exact set of records, or a bug needs exact reproduction.

In those cases, use explicitly defined values or a deterministic generator keyed by input.

Random data is better suited for fuzzing, property-based tests, or load tests when the seed and parameters are saved for reproduction.

## 25. Deterministic Pseudo-Random Values

You can generate variation from a key using a deterministic hash function such as `md5()` instead of relying on session PRNG state.

Example deriving a bucket from the first two hex characters of a hash:

~~~sql
SELECT
    n,
    get_byte(
        decode(substr(md5('tenant:' || n::text), 1, 2), 'hex'),
        0
    ) AS bucket
FROM generate_series(1, 10) AS g(n);
~~~

The same input key produces the same bucket. Use the bucket to select categories or distribution ratios.

Hashing here is not a cryptographic random source. Do not use this technique to generate passwords, tokens, or secrets.

## 26. Saving the Seed and Generator Version

If a test uses randomness or fuzzing, log at a minimum the seed value, generator version/commit, PostgreSQL version, test name, parameters and dataset size, worker count/parallelism, timezone and locale, and relevant environment variables.

A seed number alone may not suffice if the generator code or call order changes.

When a test fails, save the minimized failing input if the framework supports it.

## 27. UUIDs and Reproducibility

Random UUIDs like `gen_random_uuid()` generate a new ID on every call. That works well when uniqueness is required, but not when tests need fixed IDs to compare results.

For fixtures, you can use defined UUID literals:

~~~sql
INSERT INTO app.customer (customer_id, customer_key, display_name)
VALUES
(
    '11111111-1111-4111-8111-111111111111',
    'cust-alice',
    'Alice Test'
);
~~~

If deterministic UUIDs from a namespace and name are needed, UUID v5 can be used via a supporting extension, though package/version dependencies must be managed. Do not generate IDs randomly if assertions require stable values.

## 28. Timestamps and Timezones

Time-related data is a common source of flaky tests.

Use `timestamptz` for absolute points in time and write literals with an explicit timezone:

~~~sql
INSERT INTO app.audit_event (event_time)
VALUES ('2025-03-08 10:00:00+00');
~~~

Set the test timezone explicitly:

~~~sql
SET TIME ZONE 'UTC';
~~~

Avoid relying on `now()` if expected results depend on execution time. In PostgreSQL, `now()` / `CURRENT_TIMESTAMP` return the transaction start time, whereas `clock_timestamp()` changes with real time.

## 29. Freezing Time in Tests

You can pass a fixed timestamp into an application or function instead of letting the code read the system clock directly.

Example function accepting a reference timestamp:

~~~sql
CREATE OR REPLACE FUNCTION app.is_expired(
    p_expires_at timestamptz,
    p_as_of timestamptz
)
RETURNS boolean
LANGUAGE sql
IMMUTABLE
AS $$
    SELECT p_expires_at <= p_as_of;
$$;
~~~

Test:

~~~sql
SELECT app.is_expired(
    '2025-01-01 00:00:00+00',
    '2025-01-02 00:00:00+00'
);
~~~

Injecting a clock/reference time helps test boundary conditions and avoids depending on wall-clock time.

## 30. DateStyle, Timezone, and Locale

Session settings can affect parsing and formatting.

~~~sql
SET DateStyle = 'ISO, YMD';
SET TIME ZONE 'UTC';
~~~

Avoid ambiguous date formats like `01/02/2025`. Use ISO format and an explicit timezone.

Locale, collation, and ICU/libc versions can affect sort order, case conversion, and comparisons. A test relying on text ordering must specify the collation environment.

## 31. Collation and Result Ordering

SQL does not guarantee row order if a query has no `ORDER BY`.

Do not write a test like:

~~~sql
SELECT customer_key
FROM app.customer;
~~~

and assume the first row will always be Alice.

Write explicitly:

~~~sql
SELECT customer_key
FROM app.customer
ORDER BY customer_key;
~~~

If ordering depends on locale/collation, declare the appropriate collation or compare results as sets when order is not the behavior under test.

## 32. Numeric and Floating-Point

For money and values requiring exact comparisons, use `numeric(p,s)` instead of `real`/`double precision` if business semantics require decimal exactness.

Example:

~~~sql
CREATE TABLE app.invoice (
    invoice_id bigint PRIMARY KEY,
    amount numeric(12, 2) NOT NULL
);
~~~

Floating-point uses an approximate binary representation. Tests should use a tolerance when checking floating-point results, or use `numeric` for financial calculations.

## 33. NULL, Empty Strings, and Boundary Values

Fixtures should distinguish NULL, empty strings, whitespace-only strings, zero, boolean false, month/year boundary dates, values just below/at/above limits, Unicode and long strings, duplicate keys, and missing references.

Do not seed only "clean" data. Negative and boundary fixtures help test constraints, validation, and error handling.

## 34. Testing Constraints with Negative Fixtures

A test can verify that the database rejects invalid data:

~~~sql
INSERT INTO app.orders
    (customer_id, status, total_amount, created_at)
VALUES
    (999999, 'paid', 10.00, now());
~~~

If the customer does not exist, the foreign key must reject the insert.

You can use a PL/pgSQL exception block in a test:

~~~sql
DO $$
BEGIN
    BEGIN
        INSERT INTO app.orders
            (customer_id, status, total_amount, created_at)
        VALUES
            (999999, 'paid', 10.00, now());

        RAISE EXCEPTION 'Expected foreign key violation';
    EXCEPTION
        WHEN foreign_key_violation THEN
            RAISE NOTICE 'Expected error observed';
    END;
END;
$$;
~~~

Ensure the exception handler only catches the expected error; if the code can throw a different error, the test must catch that discrepancy.

## 35. Large Seeds and ANALYZE

After loading many rows, planner statistics may not yet reflect the new distribution.

Run:

~~~sql
ANALYZE app.event_log;
~~~

For multiple tables:

~~~sql
ANALYZE;
~~~

Then use `EXPLAIN` or `EXPLAIN (ANALYZE, BUFFERS)` on the test queries.

If performance tests depend on statistics, the seed process must clearly specify when `ANALYZE` runs and whether autovacuum is active.

## 36. Bulk Loading with COPY

For large fixtures, `COPY` is usually more efficient than many individual `INSERT` statements.

Client-side example with `psql`:

~~~text
psql meta-command: copy app.customer(customer_key, display_name, created_at) from customers.csv using CSV format with header
~~~

`psql`'s `copy` meta-command reads files from the machine running `psql`. SQL `COPY FROM` with a filename accesses files on the server and has different privilege requirements.

For test automation, control encoding, delimiter, header, NULL representation, and file path so seeding produces consistent results.

## 37. Data Dependent on Load Order

When using CSV or multiple seed files, document the dependency order and format contract.

For example: reference data, customers, products, orders, order items, payments.

If IDs are auto-generated, parent/child mapping needs to be resolved deterministically. Avoid relying on row order within a file without an explicit key.

## 38. Test Data and Migrations

Schema migrations and data seeds have different lifecycles.

- Migrations change schemas or data according to application versions.
- Seeds create baseline/reference/test data.
- Fixtures create data for a specific test case.
- Production reference data can be managed as migrations if versioning is required.

Do not put millions of benchmark rows into production migrations. Do not place test-only fixtures into the production schema without clear reason and controls.

## 39. Seeding After Migrations

A common workflow:

~~~text
Create empty test database
          |
          v
Apply schema migrations
          |
          v
Install required extensions
          |
          v
Load baseline seed
          |
          v
Create per-test fixtures
          |
          v
Run tests
          |
          v
Cleanup / discard database
~~~

Tests must run against the schema produced by current migrations, not against an old dump whose schema might have drifted.

## 40. Dedicated Test Databases

The safest and most reproducible approach is creating a dedicated database per test run or worker.

Example:

~~~bash
createdb app_test_001
psql -X -v ON_ERROR_STOP=1 -d app_test_001 -f schema.sql
psql -X -v ON_ERROR_STOP=1 -d app_test_001 -f seed.sql
~~~

The database name should include a build/run/worker identifier to prevent collisions. Drop the database after testing only when certain it belongs to that run.

Do not share a test database with other developers or services holding important data.

## 41. Using Separate Schemas for Tests

If creating a new database is too expensive, you can create a separate schema per test worker and configure `search_path`.

~~~sql
CREATE SCHEMA test_worker_01;
SET search_path TO test_worker_01, public;
~~~

However, schema isolation is not completely equivalent to database isolation: extensions, database-level objects, shared sequences, advisory locks, and some catalog/settings remain database-scoped.

Avoid letting test workers share mutable tables or objects.

## 42. Parallel Tests and Collisions

Tests running in parallel can collide if they share fixed primary keys, unique natural keys, shared rows, sequence resets, temporary object names, advisory lock keys, global configuration, or external service identifiers.

Solutions include a separate database/schema per worker, namespace prefixes for fixture keys, appropriate transaction isolation, deterministic per-worker ID spaces, ownership-scoped cleanup, and never resetting shared sequences while another worker is running.

## 43. Temporary Tables

A temporary table belongs to the current session:

~~~sql
CREATE TEMP TABLE test_result (
    item_id bigint,
    result text
) ON COMMIT DROP;
~~~

It is useful for intermediate test data and disappears automatically when the session ends.

However, temporary tables do not replace fixtures that must be accessed across multiple connections. If an application opens a connection pool, each connection has its own temporary tables.

## 44. Transaction Isolation and Concurrency Testing

PostgreSQL defaults to `READ COMMITTED`. Concurrency tests must specify the isolation level explicitly if testing snapshot- or serialization-dependent behavior.

Example:

~~~sql
BEGIN ISOLATION LEVEL REPEATABLE READ;

SELECT balance
FROM app.account
WHERE account_id = 1;

COMMIT;
~~~

For `SERIALIZABLE` tests, check both the possibility of a transaction aborting due to a serialization failure and the application's retry logic.

Seed data must establish the exact preconditions so two sessions contend on a row or resource.

## 45. Reproducible Race Condition Tests

To reproduce a concurrency bug:

1. Use two independent connections.
2. Load fixtures with fixed IDs and states.
3. Control statement ordering using test barriers.
4. Record the isolation level.
5. Record transaction boundaries.
6. Save SQL logs or traces.
7. Verify the final state.

Do not use `pg_sleep()` as the primary synchronization mechanism when a barrier in the test harness can be used; sleeps only approximate timing and cause flakiness.

## 46. Seeds for Performance Tests

Performance seeds must represent the workload: row counts, data skew, index selectivity, foreign-key relationships, NULL ratios, hot keys, time distribution, update/delete ratios, partition sizes, and concurrent clients.

A table with 10 million rows where every value is identical does not represent production if production has different cardinality and skew.

Document generator parameters and dataset checksums.

## 47. Synthetic Data and Privacy

Synthetic data is generated from rules or a generator without directly copying real personal information. It is usually a good choice for development and CI.

If production-derived data is used, obtain policy approval, mask/anonymize identifiers and quasi-identifiers, strip credentials/tokens/secrets, protect free-text fields that may contain PII, evaluate re-identification risk, restrict access/retention, and record the source and processing steps.

Hashing emails or phone numbers is not always enough to anonymize because the value space can be guessable.

## 48. Masking Must Preserve Relationships

When anonymizing relational data:

- The same source identifier must map to the same masked identifier.
- Foreign keys must continue to match.
- Unique constraints must still be satisfied.
- Referential integrity must not be broken.
- Important distributions and skew should be preserved as needed.
- Sensitive information must not remain in logs or auxiliary CSVs.

Use deterministic mapping with a secret key if consistency across multiple datasets is needed; manage the key separately and do not commit it to the repository.

## 49. Seeding in a CI Pipeline

A typical pipeline:

~~~text
Start PostgreSQL service
          |
          v
Create isolated test database
          |
          v
Apply migrations
          |
          v
Install extensions
          |
          v
Load deterministic baseline
          |
          v
Run unit/integration tests
          |
          v
Collect logs and artifacts
          |
          v
Drop test database
~~~

Pin the PostgreSQL image/tag, extension packages, and locale. Do not use `latest` if environment reproducibility across CI runs is required.

## 50. Docker and Testcontainers

Containers help control the PostgreSQL major version, configuration, and package set.

When using Docker/Testcontainers:

- Pin the image tag or digest.
- Install extension packages during the image/build step.
- Wait for health/readiness, not just the container process.
- Create dedicated databases and roles.
- Run migrations and seeds in order.
- Expose logs when tests fail.
- Use temporary volumes or disposable databases.
- Clean up containers and volumes with proper ownership.

If an extension requires `shared_preload_libraries`, configure it before PostgreSQL starts.

## 51. Snapshots and Template Databases

PostgreSQL allows creating a database from a template:

~~~sql
CREATE DATABASE app_test_worker_01
WITH TEMPLATE app_test_template;
~~~

A template can be pre-populated with schemas, extensions, and baseline fixtures to reduce setup time.

Notes:

- No active sessions may be connected to the template database during copying per PostgreSQL requirements.
- The template must be refreshed when migrations/seeds change.
- A cloned database is a baseline snapshot at creation time.
- Each test still needs its own data and cleanup.
- Templates do not replace the server's package inventory.

A stale template can cause tests to run against a schema or seed that no longer matches the source code.

## 52. pg_dump/pg_restore as a Baseline Snapshot

You can create a custom-format dump from a prepared test database:

~~~bash
pg_dump -Fc -f test_baseline.dump app_test_template
~~~

Each run restores into a new database:

~~~bash
createdb app_test_run
pg_restore --dbname=app_test_run --exit-on-error test_baseline.dump
~~~

This approach fits large baselines where setup is time-consuming. However, version the snapshot alongside the migration/seed commit and extension package inventory.

## 53. Verifying That a Seed Loaded Completely

Do not check only the exit code of the seed script. Add assertions:

~~~sql
DO $$
BEGIN
    IF (SELECT count(*) FROM app.customer) < 2 THEN
        RAISE EXCEPTION 'Customer fixture is incomplete';
    END IF;

    IF NOT EXISTS (
        SELECT 1
        FROM app.customer
        WHERE customer_key = 'cust-alice'
    ) THEN
        RAISE EXCEPTION 'Required customer fixture is missing';
    END IF;
END;
$$;
~~~

Assertions should check preconditions that the test suite actually needs, without hardcoding total row counts if the seed is allowed to grow.

## 54. Recording the Environment to Reproduce Bugs

When a test fails, save the Git commit or build identifier, PostgreSQL version and image digest, extension versions, schema migration version, seed version/checksum, random seed and generator version, relevant database settings, timezone/locale/collation, test name and worker ID, SQL parameters or minimized fixture, and sanitized logs and error details with secrets removed.

Saving only a stack trace without the data fixture and environment can cause reproduction attempts to fail.

## 55. Flaky Tests Caused by State Dependencies

Common causes:

- Tests depending on a previously run test.
- Seeds running only once on a shared database.
- Sequence states not reset.
- `now()` causing expected values to change.
- Queries missing `ORDER BY`.
- Random values not pinned.
- Parallel tests sharing rows.
- Cleanup leaving leftover data.
- External service state not reset.
- Locale/timezone differing between local and CI.

Solve these through isolation, explicit inputs, deterministic fixtures, and reproducible evidence.

## 56. Common Anti-Patterns

### 56.1. Using a production dump as default test data

May contain sensitive data and makes tests depend on an unversioned snapshot.

### 56.2. Using one shared database for all tests

Easily causes race conditions, collisions, and test order dependencies.

### 56.3. Using random() without saving the seed

Makes exact reproduction of failing cases impossible.

### 56.4. Using TRUNCATE CASCADE on a shared database

Can wipe data outside the test's scope.

### 56.5. Assuming sequences roll back

Sequence values are not undone like row changes.

### 56.6. Skipping ANALYZE after bulk seeding

The planner may use stale or missing statistics.

### 56.7. Relying on default row ordering

Without `ORDER BY`, ordering is not guaranteed.

### 56.8. Mixing migrations and seeds indiscriminately

Makes it hard to tell whether failures belong to schema evolution or test data setup.

### 56.9. Checking only the seed command exit code

The script can finish while missing fixtures that tests require.

### 56.10. Using fake data with unrealistic formats

Query performance and application validation may fail to represent production.

## 57. Example Seed Workflow with psql

A simple shell workflow:

~~~bash
createdb app_test

psql -X \
  -v ON_ERROR_STOP=1 \
  -d app_test \
  -f db/schema.sql

psql -X \
  -v ON_ERROR_STOP=1 \
  -d app_test \
  -f db/seed/reference_data.sql

psql -X \
  -v ON_ERROR_STOP=1 \
  -d app_test \
  -f db/seed/test_fixtures.sql
~~~

`-X` ignores user `psql` startup files so personal settings cannot alter results. `ON_ERROR_STOP` causes `psql` to stop on SQL errors.

You can use `psql --single-transaction` for a group of transaction-compatible scripts. Do not use it when scripts contain commands that cannot run inside a transaction block.

## 58. Complete Deterministic Seed Example

~~~sql
BEGIN;

CREATE SCHEMA IF NOT EXISTS test_data;

CREATE TABLE IF NOT EXISTS test_data.customer (
    customer_id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_key text NOT NULL UNIQUE,
    display_name text NOT NULL,
    created_at timestamptz NOT NULL
);

CREATE TABLE IF NOT EXISTS test_data.orders (
    order_id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id bigint NOT NULL
        REFERENCES test_data.customer(customer_id),
    status text NOT NULL,
    total_amount numeric(12, 2) NOT NULL
        CHECK (total_amount >= 0),
    created_at timestamptz NOT NULL
);

INSERT INTO test_data.customer
    (customer_id, customer_key, display_name, created_at)
VALUES
    (101, 'cust-alice', 'Alice Test', '2025-01-10 09:00:00+00'),
    (102, 'cust-bob', 'Bob Test', '2025-01-11 09:00:00+00')
ON CONFLICT (customer_key) DO NOTHING;

INSERT INTO test_data.orders
    (order_id, customer_id, status, total_amount, created_at)
VALUES
    (
        1001,
        (SELECT customer_id
         FROM test_data.customer
         WHERE customer_key = 'cust-alice'),
        'paid',
        125.50,
        '2025-01-12 10:00:00+00'
    ),
    (
        1002,
        (SELECT customer_id
         FROM test_data.customer
         WHERE customer_key = 'cust-bob'),
        'pending',
        49.99,
        '2025-01-13 10:00:00+00'
    )
ON CONFLICT (order_id) DO NOTHING;

-- Explicit IDs require sequence synchronization before later generated inserts.
SELECT setval(
    pg_get_serial_sequence(
        'test_data.customer',
        'customer_id'
    )::regclass,
    COALESCE(
        (SELECT max(customer_id) FROM test_data.customer),
        1
    ),
    EXISTS (SELECT 1 FROM test_data.customer)
);

SELECT setval(
    pg_get_serial_sequence(
        'test_data.orders',
        'order_id'
    )::regclass,
    COALESCE(
        (SELECT max(order_id) FROM test_data.orders),
        1
    ),
    EXISTS (SELECT 1 FROM test_data.orders)
);

COMMIT;
~~~

The example uses natural keys and explicit IDs to make fixtures easily recognizable. In a real system, a seed script must handle cases where a key already exists with a different ID, and explicitly decide between `DO NOTHING` and `DO UPDATE` per column.

## 62. Reproducible Test Data Checklist

**Source and structure**

- Dataset is classified as fixture, seed, synthetic, or anonymized.
- Business scenarios and edge cases are documented.
- Natural keys or IDs are stable.
- Foreign-key order is clear.
- Sensitive data is removed/masked appropriately.

**Seed lifecycle**

- Scripts are under version control.
- Policy exists for `DO NOTHING`/`DO UPDATE`.
- Transactions and error handling are in place.
- Safe cleanup/reset is available.
- Identity sequences are handled.
- Seed can run on a clean database.

**Reproducibility**

- Random seed/generator version is recorded.
- Timestamps have explicit timezones.
- Reference time is fixed when needed.
- Locale/collation and PostgreSQL image are pinned.
- Query assertions include `ORDER BY` when order matters.
- Failing fixtures and environments are saved.

**Isolation and CI**

- Dedicated database/schema/namespace per worker.
- Parallel tests do not share mutable state.
- Extension packages and migrations are prepared.
- CI logs contain sufficient evidence.
- Test databases are cleaned up according to ownership.
- Performance datasets have representative distributions.

## 63. Frequently Asked Questions

### Is a seed the same as a migration?

No. Migrations evolve schemas or data across application versions; seeds load baseline/reference/test data. Both processes can run in the same pipeline, but they should have separate purposes and versioning.

### Must a seed script always be idempotent?

For baseline automation, it should usually be safe to re-run. However, `DO NOTHING`, `DO UPDATE`, and reset strategies have different behaviors; choose based on the goal.

### Should fixed IDs be used in fixtures?

They can be used in an isolated test database for readability and stable assertions. Synchronize sequences after explicit identity values and avoid collisions across workers sharing a database.

### Why do sequences advance after ROLLBACK?

`nextval()` is not designed to undo along with a transaction. Gaps in sequences are normal, and sequence values cannot be used as exact transaction counters.

### Does setseed() guarantee identical results across all PostgreSQL versions?

Do not rely on such a guarantee. It reproduces the PRNG sequence within the same implementation and call order, but it is not a cross-version contract for test fixtures.

### Should random() be used for all test data?

No. Data requiring fixed expected results should be explicitly declared or deterministically derived from keys. Randomness is better suited for fuzzing/load tests when the seed and generator details are recorded.

### How does TRUNCATE differ from DELETE?

`TRUNCATE` is fast, acquires a strong lock, can reset identities, and does not run row-level `DELETE` triggers. `DELETE` processes rows individually, can fire triggers, and supports predicates.

### Why should parallel tests not share a database?

Workers can collide on keys, sequences, rows, and cleanup. Use dedicated databases/schemas or namespace isolation.

### Does transaction rollback clean up everything a test creates?

No. Sequence state does not roll back like row changes; external side effects and actions outside the transaction are also not undone.

### Why is ANALYZE needed after large seeds?

The planner needs statistics matching the new data distribution to pick meaningful query plans.

### Can a production dump be used as a test fixture?

Only when policy permits and the data has been appropriately protected. Synthetic data is usually safer and easier to reproduce. If using anonymized data, re-identification risk still must be assessed.

### How do I reproduce a bug from CI?

Save the commit, PostgreSQL/image version, extensions, migration/seed version, random seed, timezone/locale, test parameters, and minimal failing fixture.

### Is a template snapshot always up to date?

No. A template only reflects the schema and seed at creation time. Version snapshots alongside migration/seed commits and refresh them when the baseline changes.

### When should COPY be used instead of INSERT?

When bulk loading a large dataset. Control encoding, delimiter, NULL representation, file location, and server/client privileges.

### How do I verify a seed loaded completely?

Add assertions for required natural keys, row counts, or business invariants that tests depend on. Do not rely solely on the loader's exit code.

Key commands and patterns:

INSERT INTO app.metric_sample (sample_id, metric_value)
SELECT
    n,
    (n::numeric * 7919 % 100000) / 100.0
FROM generate_series(1, 10000) AS g(n);

ON CONFLICT (customer_key) DO NOTHING;

-- Set timezone explicitly in the session.
SET TIME ZONE 'UTC';

-- Set the pseudo-random seed for the session.
SELECT setseed(0.42);

-- Synchronize identity/serial sequence after explicit IDs.
SELECT setval(
    pg_get_serial_sequence('app.customer', 'customer_id')::regclass,
    COALESCE((SELECT max(customer_id) FROM app.customer), 1),
    EXISTS (SELECT 1 FROM app.customer)
);

-- Update planner statistics after bulk seeding.
ANALYZE app.metric_sample;
~~~

# Create an isolated test database.
createdb app_test

# Run schema and seed with stop-on-error.

Principles to remember:

1. Fixtures describe data for a specific test; seeds load baselines; synthetic data serves volume and distribution tests.
2. Each test must declare preconditions and not depend on previously run tests.
3. Use natural keys or stable IDs so assertions are easy to reproduce.
4. Idempotent seeds need clear policies for `DO NOTHING`, `DO UPDATE`, and resets.
5. Run seeds in transactions when scripts are compatible.
6. Load parent rows before child rows or intentionally use deferrable constraints.
7. Use `TRUNCATE` only in controlled databases/schemas; understand locks, cascades, and trigger behavior.
8. Sequence values do not roll back with transactions; synchronize sequences after explicit identity values.
9. `generate_series()` creates reproducible volume data; design distributions matching the workload under test.
10. `setseed()` is not a cross-version contract; save the generator version and call order.
11. Use deterministic mapping from input keys when expected values must remain stable.
12. Use timestamps with explicit timezones and inject reference times to avoid flaky tests.
13. Locale/collation and query ordering must be specified whenever they affect results.
14. Use `numeric` for decimal exactness; use tolerances for floating-point.
15. Test NULL, empty, boundary, and negative cases.
16. Run `ANALYZE` after bulk loading when tests depend on planner statistics.
17. Use separate databases/schemas/namespaces for parallel workers.
18. Distinguish migrations, seeds, fixtures, and performance datasets.
19. Pin the PostgreSQL image, extension packages, seed version, and generator.
20. Use production-derived data only when permitted and privacy-protected.
21. Save the seed, environment, and failing fixture to reproduce failures.
22. CI tests must have ownership-scoped cleanup and sufficient logs for investigation.
23. Snapshots/templates should be versioned alongside schema and seed commits.
24. A good test data setup must be runnable from a clean database and yield deterministic results.

When a test fails, the dataset together with the execution conditions must be sufficient to recreate the bug on a clean database.
