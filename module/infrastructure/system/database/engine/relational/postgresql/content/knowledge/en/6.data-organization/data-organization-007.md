# Sequence, GENERATED AS IDENTITY, and the limits of auto-incrementing numbers in PostgreSQL

When designing PostgreSQL tables, many developers want every new row to receive a distinct numeric ID without the application computing it manually. For instance, the first order gets ID 1, the next gets 2, then 3, 4... PostgreSQL supports this need with **sequences** and **`GENERATED ... AS IDENTITY`** columns. In legacy schemas, you may also encounter familiar declarations like `SERIAL` or `BIGSERIAL`.

However, the phrase "auto-incrementing number" easily creates three false expectations: **numbers are strictly contiguous without gaps**, **smaller numbers were definitely committed earlier**, and **being auto-incremented automatically guarantees uniqueness**. PostgreSQL sequences promise none of these. They are designed primarily to **issue values efficiently and safely when multiple sessions request numbers concurrently**, not to serve as gapless transaction counters or replace table constraints.

This lesson explains sequence structure, the two identity modes, differences from `SERIAL`, how PostgreSQL handles concurrency, rollbacks, and caching, along with workflows for safely using sequences across schemas, data imports, and operations.

## 1. Learning objectives

After this lesson, you will be able to:

- Explain a sequence as an **independent stateful database object**.
- Use `CREATE SEQUENCE`, `nextval()`, `currval()`, `setval()`, and related administrative commands.
- Create auto-incrementing keys with `GENERATED ALWAYS AS IDENTITY` and `GENERATED BY DEFAULT AS IDENTITY`.
- Distinguish identity from `SERIAL`/`BIGSERIAL` and from `PRIMARY KEY` and `UNIQUE` constraints.
- Understand why rollbacks, failed inserts, `ON CONFLICT`, sequence caches, and restarts can create **ID gaps**.
- Understand why ID order does not guarantee commit order or business event order.
- Inspect which sequence is bound to a column and how to synchronize it after importing existing IDs.
- Recognize risks of range exhaustion, `CYCLE`, resetting sequences, permissions, and logical replication.
- Choose appropriate identifiers when applications require idempotency, chronological ordering, or uniqueness across multiple databases.

Examples are written for modern PostgreSQL. They are intended for a practice database—**never run sequence reset/alter commands on production tables holding live data**.

## 2. What is a sequence?

A **sequence** is a PostgreSQL object that generates numeric values according to a rule, typically incrementing step by step. It can back a table column or be called directly by an application.

Example of a sequence starting at 1000 with an increment of 1:

```sql
CREATE SEQUENCE lab_invoice_number_seq
    AS BIGINT
    START WITH 1000
    INCREMENT BY 1
    MINVALUE 1000
    NO CYCLE
    CACHE 1;
```

When calling:

```sql
SELECT nextval('lab_invoice_number_seq');
SELECT nextval('lab_invoice_number_seq');
SELECT nextval('lab_invoice_number_seq');
```

for a newly created sequence not yet used by other sessions, you will receive 1000, 1001, and 1002 in turn.

A sequence is not:

- **A column**: a column stores values in each row; a sequence is a number-issuing object.
- **`COUNT(*)`**: the current row count can shrink on deletions; a sequence does not automatically decrement just because rows are deleted.
- **`MAX(id) + 1`**: computing from the table is unsafe when multiple sessions insert concurrently unless another synchronization mechanism exists.
- **A transaction log**: sequences do not guarantee gapless issuance, and normal calls do not roll back with transactions.
- **A unique key**: sequences generate numbers per configuration, while `UNIQUE` or `PRIMARY KEY` is the layer enforcing uniqueness on table data.

### 2.1. A sequence maintains its own state

Each time `nextval` executes successfully, PostgreSQL issues the next value according to the sequence state, using coordination suitable for concurrent connections.

```text
             PostgreSQL sequence
                  start = 1
                  step  = 1
                      |
        +-------------+-------------+
        |             |             |
        v             v             v
     Session A     Session B     Session C
      nextval()     nextval()     nextval()
        |             |             |
        v             v             v
       1             2             3
```

An issued number does not necessarily belong to a committed record. For instance, one transaction may draw 2 and roll back, while the transaction drawing 3 commits normally.

### 2.2. Sequence attributes

| Attribute | Meaning |
| --- | --- |
| `AS SMALLINT / INTEGER / BIGINT` | Numeric data type and value range of the sequence |
| `START WITH n` | Initial value of the sequence when starting or restarting per configuration |
| `INCREMENT BY n` | Step increment; can be negative for descending sequences |
| `MINVALUE n` | Lowest allowed value |
| `MAXVALUE n` | Highest allowed value |
| `CACHE n` | Number of values pre-allocated in a block for a session to reduce synchronization overhead |
| `CYCLE` | Wraps around when reaching the limit, risking reissuing previously generated values |
| `NO CYCLE` | Raises an error when exhausted instead of wrapping around |
| `OWNED BY table.column` | Ties the sequence's lifecycle to a schema column when properly configured |

Normally, for auto-incrementing primary keys, pay close attention to **data type**, **exhaustion risk**, **`NO CYCLE`**, and the sequence's relationship with its column.

## 3. Lab: creating a schema and standalone sequence

> **Use only in a lab database.** The `DROP TABLE`/`DROP SEQUENCE` commands in this section can delete prior experiment data. Never run them wholesale on a production database.

Use a PostgreSQL database where you have permissions to create schemas and tables. There, run:

```sql
CREATE SCHEMA IF NOT EXISTS identity_lab;

-- Clean up objects created in previous practice runs.
DROP TABLE IF EXISTS identity_lab.orders;
DROP TABLE IF EXISTS identity_lab.shipments;
DROP TABLE IF EXISTS identity_lab.legacy_orders;
DROP SEQUENCE IF EXISTS identity_lab.ticket_seq;

CREATE SEQUENCE identity_lab.ticket_seq
    AS BIGINT
    START WITH 1000
    INCREMENT BY 1
    MINVALUE 1000
    NO CYCLE
    CACHE 1;
```

Because the example uses schema-qualified names, subsequent calls do not depend on the session's `search_path`.

### 3.1. Drawing numbers with `nextval()`

```sql
SELECT nextval('identity_lab.ticket_seq'::regclass) AS first_ticket;

SELECT nextval('identity_lab.ticket_seq'::regclass) AS second_ticket;
```

If the sequence is newly created with no other sessions calling it, the results are 1000 and then 1001.

The `regclass` argument identifies the sequence object PostgreSQL will call. Writing a string literal with `::regclass` clearly expresses an object name in SQL.

### 3.2. What does `currval()` return?

```sql
SELECT currval('identity_lab.ticket_seq'::regclass) AS my_last_ticket;
```

`currval()` returns the most recent value obtained by **the current session** from that sequence via `nextval()`. It does not advance to a new number.

This has two consequences:

- Session A, having just received 1001, can call `currval` and see 1001, even if Session B has since drawn a newer number.
- If a session **has never obtained a value via `nextval` on that sequence**, `currval` raises an error: "currval ... is not yet defined in this session".

`currval` is not a query for "the latest globally committed value" — sequences do not even store such a concept.

### 3.3. How does `lastval()` differ from `currval()`?

```sql
SELECT lastval() AS last_sequence_value_in_this_session;
```

`lastval()` returns the value of **whichever sequence `nextval` most recently called in the session**, without specifying a sequence name. If a session uses multiple identity tables or multiple sequences, `lastval()` may reflect a different sequence than the one you intended.

Therefore, when inserting rows into a table, the clearer way to retrieve generated keys is **`INSERT ... RETURNING id`**, rather than relying on `lastval()` or `SELECT MAX(id)`.

## 4. Creating GENERATED AS IDENTITY columns

PostgreSQL supports identity columns declared directly in DDL. General forms:

```sql
column_name BIGINT GENERATED ALWAYS AS IDENTITY
```

or:

```sql
column_name BIGINT GENERATED BY DEFAULT AS IDENTITY
```

An underlying sequence is automatically managed by PostgreSQL for this identity column. When an `INSERT` omits the identity column value, the system draws a value from the sequence.

### 4.1. GENERATED ALWAYS example

```sql
CREATE TABLE identity_lab.orders (
    order_id BIGINT GENERATED ALWAYS AS IDENTITY (
        START WITH 100
        INCREMENT BY 1
        CACHE 1
    ) PRIMARY KEY,
    external_ref TEXT NOT NULL UNIQUE,
    total_amount NUMERIC(12,2) NOT NULL
        CHECK (total_amount >= 0),
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

Column `order_id`:

- Uses `BIGINT` for a large value range.
- Is an identity column in `ALWAYS` mode.
- Uses an underlying sequence starting at 100, incrementing by 1, cache 1 in this example.
- Has `PRIMARY KEY` to **actually enforce non-NULL and uniqueness in the table**.

Column `external_ref` also carries `UNIQUE` because an external transaction reference has business meaning separate from the internal numeric key.

Insert data:

```sql
INSERT INTO identity_lab.orders (external_ref, total_amount)
VALUES
    ('web-order-001', 125000.00),
    ('web-order-002',  99000.00)
RETURNING order_id, external_ref, total_amount;
```

If the table is newly created and no other transactions touched the sequence, the IDs will typically be 100 and 101.

**`RETURNING` is the right way to obtain IDs issued directly by an insert.** There is no need to guess new numbers from `MAX(order_id)` or prior insert counts.

### 4.2. Creating a GENERATED BY DEFAULT column

```sql
CREATE TABLE identity_lab.shipments (
    shipment_id BIGINT GENERATED BY DEFAULT AS IDENTITY
        (START WITH 1 INCREMENT BY 1),
    tracking_code TEXT NOT NULL UNIQUE,
    status TEXT NOT NULL DEFAULT 'CREATED',
    CONSTRAINT shipments_pkey PRIMARY KEY (shipment_id)
);
```

When `shipment_id` is omitted from `INSERT`, PostgreSQL generates the ID automatically:

```sql
INSERT INTO identity_lab.shipments (tracking_code)
VALUES ('PKG-001'), ('PKG-002')
RETURNING shipment_id, tracking_code;
```

With `BY DEFAULT`, you **can** also supply an explicit ID:

```sql
INSERT INTO identity_lab.shipments (
    shipment_id, tracking_code
)
VALUES (500, 'PKG-500')
RETURNING shipment_id, tracking_code;
```

Key 500 is stored exactly as supplied provided it violates no constraints. **Inserting an explicit ID does not automatically advance the underlying sequence to 501.** This is a crucial point when importing data and synchronizing sequences afterward.

## 5. How do ALWAYS and BY DEFAULT differ?

| Case | `GENERATED ALWAYS` | `GENERATED BY DEFAULT` |
| --- | --- | --- |
| `INSERT` omits identity column | PostgreSQL generates value | PostgreSQL generates value |
| `INSERT` uses `DEFAULT` for identity column | Generates value | Generates value |
| `INSERT` supplies an explicit ID value | Normally rejected unless overridden | Allowed, if constraints are satisfied |
| Suitable when | Applications should not arbitrarily assign numeric keys during normal operations | Importing IDs from another system or migrations is needed |
| Automatically creates `PRIMARY KEY`? | No | No |
| Backed by an underlying sequence? | Yes | Yes |

### 5.1. Inserting explicit IDs into ALWAYS with OVERRIDING SYSTEM VALUE

For `identity_lab.orders` declared `GENERATED ALWAYS`, the following is normally rejected:

```sql
-- Only to illustrate the error on a GENERATED ALWAYS column.
INSERT INTO identity_lab.orders (
    order_id, external_ref, total_amount
)
VALUES (1000, 'manual-order-1000', 100.00);
```

If a valid data import task **genuinely needs** to preserve legacy IDs, PostgreSQL provides an explicit override syntax:

```sql
INSERT INTO identity_lab.orders (
    order_id, external_ref, total_amount
)
OVERRIDING SYSTEM VALUE
VALUES (1000, 'manual-order-1000', 100.00)
RETURNING order_id, external_ref;
```

`OVERRIDING SYSTEM VALUE` explicitly signals the intent to supply IDs instead of system-generated values. Use it only in controlled processes such as migrations, restores, or reconciled data transfers.

Note: ID 1000 is inserted into the table, yet the underlying sequence of `orders` **is not automatically advanced to 1001**.

### 5.2. Ignoring input IDs with OVERRIDING USER VALUE

When you want to insert data while **forcing new key generation** instead of keeping source keys, use:

```sql
INSERT INTO identity_lab.shipments (
    shipment_id, tracking_code
)
OVERRIDING USER VALUE
VALUES (9999, 'PKG-NEW')
RETURNING shipment_id, tracking_code;
```

In this case, ID 9999 from the `INSERT` is ignored and the `shipments` sequence issues a new value from its current state.

This feature is useful when copying data from a source table to a similarly structured target table without colliding with existing identifiers. Still, consider foreign keys and related data: if IDs change, references must be remapped according to a clear plan.

### 5.3. Which mode should you choose?

Choose `ALWAYS` if you want standard application inserts prohibited from arbitrarily dictating IDs, leaving overrides strictly to intentional migration steps.

Choose `BY DEFAULT` if business workflows regularly import or assign explicit IDs from trusted sources. Whichever mode you pick, unique constraints and proper permissions are still required.

**Identity is not a standalone security mechanism.** SQL privileges, triggers, other DML, and business rules must still prevent tampering or misuse of ID values. Do not treat `GENERATED ALWAYS` as an absolute guarantee of immutable keys across all operations.

## 6. Identity does not equal PRIMARY KEY or UNIQUE

Consider:

```sql
CREATE TABLE identity_lab.temporary_labels (
    label_no BIGINT GENERATED BY DEFAULT AS IDENTITY,
    label_text TEXT NOT NULL
);
```

Column `label_no` receives auto-generated numbers when omitted. However, the DDL **declares neither `PRIMARY KEY` nor `UNIQUE`**, so the database enforces no uniqueness constraint on that column.

An example can intentionally insert duplicate IDs in `BY DEFAULT` mode when no unique constraint exists:

```sql
INSERT INTO identity_lab.temporary_labels (label_no, label_text)
VALUES
    (9, 'A'),
    (9, 'B');
```

Two rows sharing ID 9 are entirely possible without a unique constraint. Identity columns implicitly carry `NOT NULL`, but **`NOT NULL` is not `UNIQUE`**.

To make the ID a primary key:

```sql
CREATE TABLE identity_lab.labels (
    label_no BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    label_text TEXT NOT NULL
);
```

Usage:

```sql
INSERT INTO identity_lab.labels (label_text)
VALUES ('Sample A'), ('Sample B')
RETURNING label_no, label_text;
```

The accurate mental model is:

```text
Sequence / Identity
        |
        | supplies a candidate number
        v
Column label_no
        |
        | PRIMARY KEY / UNIQUE validates
        v
Row with a valid key stored in table
```

If a sequence is mis-reset or uses `CYCLE`, it can still emit a previously issued number; **constraints** decide whether that number is accepted into the table or rejected.

## 7. SERIAL and BIGSERIAL: legacy syntax still seen in practice

Before identity columns were natively supported, PostgreSQL popularized:

```sql
CREATE TABLE identity_lab.legacy_orders (
    id BIGSERIAL PRIMARY KEY,
    description TEXT NOT NULL
);
```

`SERIAL` and `BIGSERIAL` are **convenience pseudo-types**, not distinct stored numeric data types. Conceptually, `BIGSERIAL` expands roughly to:

```sql
CREATE SEQUENCE identity_lab.legacy_orders_id_seq;

CREATE TABLE identity_lab.legacy_orders (
    id BIGINT NOT NULL DEFAULT
        nextval('identity_lab.legacy_orders_id_seq'::regclass),
    description TEXT NOT NULL,
    PRIMARY KEY (id)
);

ALTER SEQUENCE identity_lab.legacy_orders_id_seq
OWNED BY identity_lab.legacy_orders.id;
```

The second block serves **only to explain the conceptual equivalent**. Do not run both blocks in the same schema, as the first already creates the table and its associated sequence.

### 7.1. Comparing SERIAL and IDENTITY

| Criterion | `SERIAL` / `BIGSERIAL` | `GENERATED AS IDENTITY` |
| --- | --- | --- |
| DDL form | Convenience pseudo-type | More SQL-standard syntax supported by PostgreSQL |
| Number generation | Default calling `nextval` on a sequence | Identity column bound to an underlying sequence |
| Automatic uniqueness constraint | No, unless PK/UNIQUE is added | No, unless PK/UNIQUE is added |
| Controlling explicit ID inserts | Usually allows direct insertion | `ALWAYS` enforces tighter control; `BY DEFAULT` permits |
| Stored column type | `SERIAL` → integer, `BIGSERIAL` → bigint | Explicitly specify `SMALLINT`, `INTEGER`, `BIGINT` |
| Metadata management | Default expression + linked sequence | Identity is an official column property |
| Legacy systems | Very common | Preferred for new schemas when requirements match |

Not every legacy table using `SERIAL` needs an urgent rewrite to identity. The difference matters when designing migrations, sequence permissions, imports, and schema standardization; assess impact before altering a live table.

### 7.2. SERIAL does not automatically create a primary key

Example:

```sql
CREATE TABLE identity_lab.loose_serial (
    id SERIAL,
    note TEXT
);
```

`id SERIAL` creates the number-generation default and a `NOT NULL` constraint, yet **does not automatically create a `PRIMARY KEY`**. If the column must be a unique key, explicitly declare `PRIMARY KEY` or `UNIQUE` as required.

## 8. Why do sequences have gaps?

A standard sequence **is not designed to guarantee a contiguous sequence without missing values**.

Suppose a new sequence issues:

```text
Transaction A gets ID 100
Transaction B gets ID 101
Transaction C gets ID 102

A COMMITs
B ROLLBACKs
C COMMITs
```

The table ends up with IDs 100 and 102, missing 101. This is not data corruption.

### 8.1. nextval does not roll back with transactions

Using the lab sequence:

```sql
BEGIN;

SELECT nextval('identity_lab.ticket_seq'::regclass)
    AS ticket_in_transaction;

ROLLBACK;

SELECT nextval('identity_lab.ticket_seq'::regclass)
    AS ticket_after_rollback;
```

Values issued inside a rolled-back transaction **are not returned to the sequence** for reuse. Subsequent calls continue advancing the sequence state.

Design rationale: a sequence must issue numbers efficiently to many concurrent sessions without forcing every transaction to lock a single counter until commit. Undoing individual allocations would complicate concurrency and easily bottleneck throughput.

### 8.2. Failed INSERTs can still consume IDs

Suppose `orders` has an identity column and `UNIQUE(external_ref)`. An `INSERT` may draw an identity value before PostgreSQL detects a unique key collision or another constraint violation.

Example:

```sql
-- external_ref = 'web-order-001' already exists
INSERT INTO identity_lab.orders (external_ref, total_amount)
VALUES ('web-order-001', 1000.00);
```

The `INSERT` is rejected due to the unique constraint, yet the underlying sequence may already have consumed a value. As a result, the next successful `INSERT` can jump by more than 1.

### 8.3. INSERT ... ON CONFLICT can also leave gaps

Example:

```sql
INSERT INTO identity_lab.orders (external_ref, total_amount)
VALUES ('web-order-001', 1000.00)
ON CONFLICT (external_ref) DO NOTHING
RETURNING order_id;
```

When `external_ref` already exists, no row is inserted, yet preparing the candidate tuple may have already invoked `nextval` for the identity column. **Never assume `ON CONFLICT DO NOTHING` consumes no sequence numbers.**

Similarly, an upsert via `ON CONFLICT DO UPDATE` can consume sequence values even when it ends up updating an existing row instead of inserting a new one.

### 8.4. Deleting rows does not rewind a sequence

If a table contains IDs 1, 2, 3 and you delete row 2:

```sql
DELETE FROM identity_lab.labels
WHERE label_no = 2;
```

The next `INSERT` does not default to reusing ID 2. It continues drawing from the sequence.

Not reusing IDs is **beneficial** when IDs are stored in logs, foreign keys, or external events. Reusing old IDs can cause identity confusion across records.

## 9. Sequence CACHE and skipped numbers on session end

The `CACHE n` parameter allows PostgreSQL to allocate a **block of numbers** to a session to reduce how often sequence state must be synchronized.

Suppose a sequence:

```sql
CREATE SEQUENCE identity_lab.cached_demo_seq
    START WITH 1
    INCREMENT BY 1
    CACHE 10
    NO CYCLE;
```

In a simplified illustration:

```text
Session A is allocated a block potentially holding 1..10
  |-- uses 1
  |-- uses 2
  |-- closes before exhausting the block

Session B requests the next block
  |-- may receive 11
```

When Session A disconnects, unused pre-allocated numbers may never appear in the table. Server crashes, cache alterations, or other operational events can likewise leave gaps larger than `INCREMENT BY 1`.

**`CACHE 10` does not mean each `nextval` increments by 10.** It still issues values by the declared increment for that session, while managing blocks for efficiency.

### 9.1. CACHE and number ordering across sessions

Suppose A gets block 1..10 and B gets block 11..20. While A is still on 2, B may already insert and commit a row with ID 11.

Therefore:

- You cannot look at ID 11 and claim it was created **after all rows with smaller IDs**.
- You cannot use `MAX(id)` as an absolute logical clock for all transactions.
- You cannot treat ID differences as exact inserted row counts.

Caching is one of the primary reasons a sequence appears to "skip" a large range without any data loss.

### 9.2. Should you set CACHE = 1?

`CACHE 1` makes allocation easier to observe in labs and reduces the effect of pre-allocating large blocks. However, it **does not eliminate gaps** caused by rollbacks, failed inserts, concurrency, or deletes.

On write-heavy systems, changing cache size should be benchmarked against workload characteristics. Never drop it to 1 merely because "gaps in IDs look ugly".

## 10. ID values do not guarantee COMMIT order

A sequence issues values in `nextval` call order, yet **transaction completion order does not necessarily match that order**.

Example with two PostgreSQL connections:

```text
Time            Session A                    Session B
----------------------------------------------------------------
T1              nextval() -> 10
T2                                           nextval() -> 11
T3                                           COMMIT row ID 11
T4              COMMIT row ID 10
```

ID 10 was allocated before ID 11, yet row ID 11 committed first.

Consequently, these inferences are unsafe:

- "The row with the highest ID is definitely the most recently committed row."
- "If ID 500 has been processed, all transactions with smaller IDs have already finished."
- "Increasing IDs mean events always occurred in exact business order."
- "IDs can serve as forensic proof of chronological order."

If the application needs creation timestamps, add an appropriate `created_at` column—while keeping in mind that `now()` in PostgreSQL reflects transaction start time rather than exact commit time.

If you need **stronger commit-order or event-order guarantees**, design a mechanism suited to that requirement, such as a coordinated event log sequence, streaming system offsets, or dedicated serialization/business numbering. Adding `ORDER BY id` alone is not enough to turn an ID into a commit sequence.

## 11. Using RETURNING to retrieve new keys properly

The most common pattern:

```sql
INSERT INTO identity_lab.orders (external_ref, total_amount)
VALUES ('web-order-003', 210000.00)
RETURNING order_id, external_ref;
```

`RETURNING` returns keys of the **exact rows affected by that statement**, which is ideal when inserting child rows right after creating a parent record.

Example transaction writing an order and capturing the generated ID:

```sql
BEGIN;

WITH created_order AS (
    INSERT INTO identity_lab.orders (external_ref, total_amount)
    VALUES ('web-order-004', 350000.00)
    RETURNING order_id, external_ref
)
SELECT order_id, external_ref
FROM created_order;

COMMIT;
```

This example uses one table, though in real applications you can use the returned ID to insert detail lines within **the same transaction**.

Avoid:

```sql
-- Do not use this to retrieve the ID of a newly inserted row:
SELECT MAX(order_id) FROM identity_lab.orders;
```

Another session may insert concurrently, and caching/rollbacks mean `MAX` has no reliable relationship to your insert. `RETURNING` is explicit and direct.

### 11.1. Multi-row INSERT

```sql
INSERT INTO identity_lab.shipments (tracking_code)
VALUES
    ('PKG-BATCH-001'),
    ('PKG-BATCH-002'),
    ('PKG-BATCH-003')
RETURNING shipment_id, tracking_code;
```

Each row receives an ID per the sequence state. Applications should use the returned `RETURNING` data and business keys to map IDs, never assuming the issued IDs must form a contiguous range.

## 12. Inspecting which sequence is bound to a column

### 12.1. pg_get_serial_sequence

Although its name contains `serial`, `pg_get_serial_sequence` also locates the sequence bound to an eligible identity column.

```sql
SELECT pg_get_serial_sequence(
    'identity_lab.orders',
    'order_id'
) AS order_sequence;

SELECT pg_get_serial_sequence(
    'identity_lab.shipments',
    'shipment_id'
) AS shipment_sequence;
```

The result is the schema-qualified name of the backing sequence, such as `identity_lab.orders_order_id_seq`, depending on naming and schema state.

If the column is not bound to a sequence in a relationship recognized by the function, the result can be `NULL`. Never guess sequence names simply by concatenating `ten_bang || '_id_seq'`, as DBAs can rename sequences.

### 12.2. Listing sequences via pg_sequences

```sql
SELECT
    schemaname,
    sequencename,
    sequenceowner,
    data_type,
    start_value,
    min_value,
    max_value,
    increment_by,
    cycle,
    cache_size,
    last_value
FROM pg_sequences
WHERE schemaname = 'identity_lab'
ORDER BY sequencename;
```

The `pg_sequences` view exposes metadata for sequences in the database. The `last_value` column can be `NULL` if read privileges are lacking, no stored state is visible yet, or the sequence has not been called; nor is it **"the last committed ID"**.

In `psql`, useful meta-commands include:

```text
\ds identity_lab.*
\d identity_lab.orders
\d identity_lab.shipments
```

`\ds` lists sequences; `\d` inspects table and column definitions. Commands starting with `\` run inside `psql`, not as plain SQL in every GUI editor.

### 12.3. Metadata differs from business state

Suppose `pg_sequences.last_value` is 2000 while `SELECT MAX(order_id)` is 1990. You cannot conclude "10 orders were lost": the sequence may have issued numbers to rolled-back transactions, reserved cache blocks, or failed inserts.

Likewise, a lower `MAX(order_id)` does not prove the sequence needs resetting. Adjusting a sequence improperly can trigger key collisions while other sessions remain active.

## 13. setval(): adjusting sequence state and its risks

`setval` alters a sequence's value during controlled administrative or import workflows.

Common syntax:

```sql
SELECT setval('identity_lab.ticket_seq'::regclass, 5000);
```

From there, on a sequence incrementing by 1, the next `nextval` call normally returns 5001.

Three-argument form:

```sql
SELECT setval(
    'identity_lab.ticket_seq'::regclass,
    5000,
    false
);
```

When `is_called = false`, the next `nextval` call returns **5000 itself**, rather than 5001.

| Call | Effect on a sequence incrementing by 1 |
| --- | --- |
| `setval(seq, 5000)` | Sets value as already called; next `nextval` normally returns 5001 |
| `setval(seq, 5000, true)` | Same meaning as above |
| `setval(seq, 5000, false)` | Next `nextval` returns 5000 |

**Warning:** `setval` mutates the sequence and does not roll back like an ordinary row update. Never run it inside a transaction assuming `ROLLBACK` will restore the prior state.

### 13.1. Why must sequences be synchronized after importing explicit IDs?

Suppose you import into `identity_lab.shipments`:

```sql
INSERT INTO identity_lab.shipments (
    shipment_id, tracking_code
)
VALUES (700, 'PKG-HISTORY-700');
```

With `BY DEFAULT`, PostgreSQL accepts the explicit ID. Yet the auto-generating sequence may still sit at a small value. Once inserts continue until the sequence emits 700, `PRIMARY KEY` will reject the collision.

Similarly, `OVERRIDING SYSTEM VALUE` on a `GENERATED ALWAYS` column can insert higher IDs without advancing the backing sequence accordingly.

### 13.2. Syncing a sequence to MAX(id) on a non-empty table

Once you have verified the table has rows and want the next generated ID to exceed the highest existing ID:

```sql
SELECT setval(
    pg_get_serial_sequence(
        'identity_lab.shipments',
        'shipment_id'
    ),
    (SELECT MAX(shipment_id) FROM identity_lab.shipments),
    true
);
```

With a step-1 sequence, subsequent `nextval` calls will attempt to issue `MAX(shipment_id) + 1`.

**This is a maintenance example for labs or import windows where writes are paused.** Never run it blindly on a production table with concurrent writers; sessions may already hold cached values or active transactions, and `MAX(id)` can change immediately after you read it.

### 13.3. Empty tables require special handling

If the table is empty, `MAX(id)` returns `NULL` and cannot be passed directly to `setval`.

For a table whose **sequence increments positively from 1**, you can use the pattern:

```sql
SELECT setval(
    pg_get_serial_sequence(
        'identity_lab.shipments',
        'shipment_id'
    ),
    COALESCE(
        (SELECT MAX(shipment_id)
         FROM identity_lab.shipments),
        1
    ),
    EXISTS(
        SELECT 1 FROM identity_lab.shipments
    )
);
```

Meaning:

- Non-empty table: `is_called = true`, last value set to MAX(id), so the next number will exceed MAX.
- Empty table: `is_called = false`, value set to 1 so the next `nextval` returns 1.

This pattern **only fits positive sequences incrementing by 1 with an intended starting value of 1**. If a sequence starts at 100, uses another step, or counts downward, adapt it accordingly. On tables with concurrent writers, safe synchronization requires dedicated maintenance/locking procedures and verification.

### 13.4. Why shouldn't you reset a sequence back to 1?

Suppose a table once held IDs 1..1000 and most rows were later deleted. Resetting the sequence to 1 just to "look clean" can:

- Collide with surviving IDs and cause primary key errors.
- Reissue IDs that already appeared in logs, messages, exports, or external services.
- Cause operators to confuse two distinct records as the same entity.
- Conflict with sessions that cached old value blocks.
- Disrupt replication, CDC, or data-migration pipelines.

Treat auto-incrementing IDs as **technical identifiers**, not user-facing display ordinal numbers.

## 14. ALTER SEQUENCE and ALTER TABLE ... IDENTITY

Sequences can be altered, provided you understand how changes affect future values and concurrency.

### 14.1. ALTER SEQUENCE

Standalone sequence example:

```sql
ALTER SEQUENCE identity_lab.ticket_seq
    INCREMENT BY 5
    CACHE 5;
```

From then on, the sequence increments by 5 and caches per the new setting on future allocations, subject to session/cached-value effects. Do not expect every active session that already cached numbers to produce identical simple progressions right away.

Adjustable properties include `INCREMENT`, `MINVALUE`, `MAXVALUE`, `CACHE`, `CYCLE`, and several other options.

### 14.2. Changing identity mode

For `shipments`, which originally used `BY DEFAULT`:

```sql
ALTER TABLE identity_lab.shipments
ALTER COLUMN shipment_id
SET GENERATED ALWAYS;
```

After this operation, explicit ID inserts are governed by `ALWAYS` rules unless overridden with the proper syntax.

To switch back to allowing explicit IDs:

```sql
ALTER TABLE identity_lab.shipments
ALTER COLUMN shipment_id
SET GENERATED BY DEFAULT;
```

Mode changes must account for import jobs, ORMs, or existing scripts that pass IDs explicitly. Never change it merely to "modernize the schema" without auditing consumers.

### 14.3. Restarting an identity sequence

For **controlled** data reset scenarios, PostgreSQL supports restarting the identity-bound sequence via DDL:

```sql
-- Illustrative only for a lab table:
ALTER TABLE identity_lab.shipments
ALTER COLUMN shipment_id
RESTART WITH 1;
```

If legacy IDs remain in the table, restarting can cause duplicate-key errors on new inserts. Treat this as a maintenance operation, never an automatic way to patch gaps.

### 14.4. TRUNCATE ... RESTART IDENTITY

In a lab, if you genuinely want to wipe all rows and reset sequences owned by the table's columns:

```sql
TRUNCATE TABLE identity_lab.shipments RESTART IDENTITY;
```

This command **deletes every row in the table** and restarts sequences owned by its columns. Never run it on tables holding real data.

Contrast with:

```sql
TRUNCATE TABLE identity_lab.shipments CONTINUE IDENTITY;
```

`CONTINUE IDENTITY` preserves sequence state rather than restarting it on truncate.

**Notable detail:** sequence restarts performed by `TRUNCATE ... RESTART IDENTITY` are managed transactionally with `TRUNCATE`, unlike ordinary `nextval`/`setval` calls which do not roll back with transactions. When rolling back a transaction containing `TRUNCATE RESTART IDENTITY`, understand the specific behavior of `currval` in the session and sequence state.

## 15. Range exhaustion and CYCLE

Every sequence has a data type and bounds. For example:

- `SMALLINT` has a very small finite range.
- `INTEGER` has a larger limit, yet can still be exhausted after years on write-heavy systems.
- `BIGINT` has a vastly wider range, typically suited for systems expecting high row or ID allocation volumes.

Signed integer limits in PostgreSQL are typically:

| Type | Bytes | Value range |
| --- | ---: | --- |
| `SMALLINT` | 2 | -32,768 to 32,767 |
| `INTEGER` | 4 | -2,147,483,648 to 2,147,483,647 |
| `BIGINT` | 8 | -9,223,372,036,854,775,808 to 9,223,372,036,854,775,807 |

An ascending sequence normally starts at 1 by default, so it does not utilize the negative half for positive generation.

### 15.1. NO CYCLE: errors when exhausted

Sequence:

```sql
CREATE SEQUENCE identity_lab.small_demo_seq
    AS SMALLINT
    START WITH 1
    MINVALUE 1
    MAXVALUE 3
    INCREMENT BY 1
    NO CYCLE
    CACHE 1;
```

Calls:

```sql
SELECT nextval('identity_lab.small_demo_seq'); -- 1
SELECT nextval('identity_lab.small_demo_seq'); -- 2
SELECT nextval('identity_lab.small_demo_seq'); -- 3
```

The next call fails because the maximum has been reached:

```sql
SELECT nextval('identity_lab.small_demo_seq');
```

Sequence exhaustion is an event **to monitor proactively before it happens**, never something to discover in production only when `INSERT` commands begin failing.

### 15.2. CYCLE does not make a safe primary key

If you use:

```sql
CREATE SEQUENCE identity_lab.cycle_demo_seq
    START WITH 1
    MINVALUE 1
    MAXVALUE 3
    CYCLE
    CACHE 1;
```

The sequence wraps around after hitting the limit:

```text
1 -> 2 -> 3 -> 1 -> 2 -> ...
```

Yet a table still holding keys 1, 2, 3 cannot accept another row with those keys under a `PRIMARY KEY` constraint.

Therefore, **never enable CYCLE just to avoid range-exhaustion errors on a primary key**. The proper fix is widening the data type/range or redesigning the identifier.

### 15.3. Why using BIGINT early helps

Changing a primary key from `INTEGER` to `BIGINT` once a table is large impacts:

- Primary key and foreign key indexes.
- Referencing tables.
- ORMs, APIs, and application data types.
- Migration duration, locking, and storage capacity.

If data is expected to grow over the long term, starting with `BIGINT GENERATED ... AS IDENTITY` avoids risky type upgrades once the system is complex.

Still, `BIGINT` is **not infinite**, and IDs can also be burned by failed inserts or session caches. Monitoring growth rate and remaining headroom remains worthwhile for large-scale systems.

## 16. Sequences in multi-connection environments

Sequences handle multiple concurrent sessions well because every allocation uses internal coordination in PostgreSQL. However, **thread-safe number allocation** differs from **business-level guarantees**.

Suppose two sessions insert concurrently:

```text
Session A                                  Session B

BEGIN;                                     BEGIN;
INSERT ... -> order_id = 100              INSERT ... -> order_id = 101
(not yet committed)                        COMMIT;
COMMIT;
```

The two IDs do not collide under normal sequence allocation. Yet their commit order is the reverse of their ID order.

With `CACHE > 1`, spacing between numbers across sessions can grow even wider. If a session closes before consuming its entire cached block, some IDs will never be persisted in the table.

### 16.1. Never use MAX(id) + 1 instead of a sequence

Risky pattern:

```sql
INSERT INTO some_table (id, payload)
SELECT COALESCE(MAX(id), 0) + 1, 'new row'
FROM some_table;
```

This is purely a **design anti-pattern illustration**; `some_table` was not created in the lab.

Two sessions can both read `MAX(id) = 100` and both attempt to insert ID 101. With a PK, one fails; without a PK, duplicate IDs are created.

Sequences solve concurrent allocation far more effectively. For business rules that truly require a **gapless** counter, synchronization requirements differ: you may need a dedicated counter row updated transactionally with appropriate serialization, trading off lower throughput and higher contention. Do not force a standard sequence to guarantee something it was never built to promise.

### 16.2. Sequences do not replace idempotency

Suppose a client sends an order-creation request, the server commits successfully, and the connection drops before the client receives the response. The client retries, and PostgreSQL issues a **new ID** for the duplicate request.

Without a unique business key, **two orders** can be created, both carrying valid numeric keys.

Better design:

```sql
-- external_ref has UNIQUE in the orders table created earlier:
INSERT INTO identity_lab.orders (external_ref, total_amount)
VALUES ('api-request-123', 50000.00)
ON CONFLICT (external_ref) DO NOTHING
RETURNING order_id;
```

When a conflict occurs, `RETURNING` returns no newly inserted row. The application must verify whether the existing request has a matching payload, appropriate state, and what response to return; never treat `DO NOTHING` alone as a complete idempotent API.

**Sequences protect number issuance; business keys and transaction design protect against duplicate intent.**

## 17. Using sequences when importing historical data

A common workflow:

1. Create a PostgreSQL table with an identity column.
2. Import data from a legacy system where IDs already exist.
3. Let the application continue writing new rows with auto-generated IDs.

If you import explicit IDs without adjusting the sequence, the data looks fine right after import, yet **unique violations appear later** when the sequence reissues an ID that already exists.

### 17.1. Safe import plan

| Phase | Actions required |
| --- | --- |
| Preparation | Pause/coordinate related write streams; back up and scope target tables |
| Import | Use explicit IDs with `BY DEFAULT`, or `OVERRIDING SYSTEM VALUE` with `ALWAYS` when needed |
| Verification | Reconcile row counts, duplicate IDs, foreign keys, and other constraints |
| Synchronization | Adjust sequences so future allocations do not collide with existing data |
| Re-enable writes | Resume traffic, verify new inserts, and monitor for unique violations |
| Traceability | Record batch, data source, ID range, and actions performed |

### 17.2. Never run an unconditional setval in production

The Section 13 example using `MAX(id)` to sync a sequence fits a lab table **with no concurrent writers**. In production:

- Other transactions may actively be inserting new rows.
- Sessions may have cached blocks based on pre-adjustment state.
- Logical replication/failover processes may require separate sequence handling.
- Imported ID sets may not be a simple positive sequence starting at 1.
- Unsynchronized resets across multiple nodes can trigger collisions.

Perform this inside a controlled cutover workflow and verify outcomes everywhere IDs continue to be generated.

### 17.3. Does restore carry over sequence state?

Depending on backup/restore tools and export scope, sequence state may be exported and restored alongside data or require explicit adjustment afterward.

Never assume "once table rows are copied, the sequence automatically knows MAX(id)". When importing CSV files with explicit IDs via `COPY`, sequences **are not automatically updated** merely because those values were loaded.

When restoring, verify:

- Table data is fully restored.
- Required sequences exist.
- Sequence dependencies and `OWNED BY` ownership are intact.
- Each sequence's next value will not collide with existing IDs.
- Necessary privileges are configured.

## 18. Sequences and access privileges

A sequence is a database object with its own privileges. Never assume an account with `INSERT` on a table automatically holds permission to call every sequence function in the schema.

Common privileges:

| Sequence privilege | Related capability |
| --- | --- |
| `USAGE` | Permits `nextval` and `currval` operations in appropriate contexts |
| `SELECT` | Permits `currval` and appropriate read access on the sequence |
| `UPDATE` | Permits `nextval` or `setval` per PostgreSQL privilege rules |

Example for a standalone sequence:

```sql
-- Assumes role app_writer was already created by an administrator.
GRANT USAGE ON SEQUENCE identity_lab.ticket_seq TO app_writer;
```

A role wishing to call `nextval('identity_lab.ticket_seq')` directly needs appropriate sequence privileges plus schema usage privileges as required.

### 18.1. Do SERIAL and identity differ in privileges?

With `SERIAL`, the column normally has a default expression calling `nextval` on a separate sequence; applications relying on that default may require `USAGE` on the sequence in addition to `INSERT` on the table.

With `GENERATED AS IDENTITY`, value generation is integrated into the table `INSERT` operation; do not infer from `SERIAL` behavior that every identity insert strictly requires granting `USAGE` on the underlying sequence in the exact same way. Still, if an account needs to **call nextval/currval/setval directly**, sequence privileges must be verified.

Exact privilege behavior can vary by version and operation, so verify during deployment using the real application account—never run services as superuser just to silence permission errors.

### 18.2. Do not grant setval to regular application accounts

Permission to alter sequence state allows creating new IDs that collide with existing rows. Operations such as `setval`, `ALTER SEQUENCE`, or `RESTART IDENTITY` should therefore belong to controlled migration/DBA accounts.

Runtime accounts only need to create normal records, not reset number generators.

## 19. Sequences and logical replication

A PostgreSQL system may use **logical replication** to replicate data changes between a publisher and a subscriber. Distinguish clearly between:

- **ID values stored in rows** are replicated as part of row data.
- **Sequence state** is not automatically kept continuously in sync merely because table `INSERT`/`UPDATE` changes flow through logical replication.

If a subscriber is promoted to a new primary or begins accepting direct writes, sequences on the subscriber may still sit at older states and issue values that collide with existing IDs.

Conceptual illustration:

```text
Publisher:
    row id=900 is written and replicated
    sequence has advanced to >900

Subscriber:
    receives row id=900
    but local sequence may not yet be synced to >900

If new writes occur on subscriber:
    nextval() may issue an already-existing ID
    -> PK/UNIQUE violation
```

Therefore, when designing migrations or failovers over logical replication, include a step to **sync sequence states and verify write readiness after cutover**. Exact mechanics depend on topology, version, and orchestration tools; never blindly run `setval(MAX(id))` on production while writers remain active.

**Terminology note:** a "sequence for generating IDs" differs from a table's **replica identity** property (which specifies which columns identify rows during logical replication). The two terms sound similar yet mean completely different things.

## 20. Multiple databases or regions: is a sequence still unique?

A PostgreSQL sequence coordinates values only within **that sequence object inside one database/instance**. If two independent databases both start sequences at 1, both will generate rows with IDs 1, 2, 3.

If data from multiple sources is later merged, collisions occur.

Example:

```text
Database A: order_id = 1, 2, 3
Database B: order_id = 1, 2, 3

Merged into a single table:
    order_id values collide
```

Options depending on requirements:

- Use a composite key `(source_id, local_id)` when merging.
- Allocate non-overlapping ID ranges or coordinate centralized sequences where appropriate.
- Use independently generatable identifiers such as UUIDs (understanding index and size costs).
- Design business keys separate from internal numeric keys.
- Maintain a mapping from source IDs to target IDs during migration.

No single approach fits every topology. Sequences excel as **internal keys** within one database, yet do not automatically produce globally collision-free identifiers across independent systems.

## 21. Can auto-incrementing keys leak business information?

Because IDs are easily guessable in sequence, users may try changing `/orders/100` to `/orders/101` in an API.

**Auto-incrementing IDs are not an authorization mechanism.** Whether IDs are random or sequential, the server must still verify that the user is authorized to view or modify that specific resource.

Practices to avoid:

- Returning rows via `WHERE id = :id` without checking owner/tenant.
- Treating ID magnitude as proof of creation timestamp or real customer counts.
- Assuming switching to UUIDs alone fixes unauthorized data access bugs.

SQL privileges, application authorization, and where appropriate Row-Level Security must still be designed explicitly.

### 21.1. Technical IDs and contiguous document numbers are separate problems

Orders can use a technical key `order_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY`. However, certain accounting vouchers or invoice numbers may require **strict business numbering rules**, cancellation tracking, audit trails, and gapless continuity per legal or business mandates.

If you must prove an unbroken sequence of document numbers, a standard PostgreSQL sequence **is insufficient** because rollbacks and failed inserts burn numbers.

Possible approaches include:

- Non-contiguous technical identifiers for transactional tables.
- A business numbering allocator coordinated inside transactions with locking and state tracking.
- Recorded cancellation or unused-number audit entries for reconciliation.
- Separating document issuance from technical record creation.

Exact designs must follow regulatory and audit requirements of the system, not merely a SQL syntax choice.

## 22. Common misconceptions

| Common misconception | Accurate understanding |
| --- | --- |
| "The sequence issues 1, 2, 3 so the table has no missing numbers." | Rollbacks, conflicts, insert errors, caching, and row deletions create gaps. |
| "Rolling back an INSERT returns the ID to the sequence." | Standard `nextval` does not roll back. |
| "ON CONFLICT DO NOTHING never consumes IDs." | The sequence may be called before the conflict is detected. |
| "With an identity column, you don't need PRIMARY KEY." | Identity generates values; PK/UNIQUE enforces uniqueness. |
| "BY DEFAULT automatically advances the sequence when inserting ID 1000." | Explicit values do not automatically advance the sequence. |
| "ALWAYS means manual IDs can never be inserted." | `OVERRIDING SYSTEM VALUE` exists for intentional cases. |
| "lastval is always the ID of the table I care about." | It returns the most recently called sequence in the session, which could be another object. |
| "MAX(id) is the ID of the row I just inserted." | Data is concurrent; use `INSERT ... RETURNING`. |
| "A larger ID definitely committed later." | Allocation order and commit order differ; caching widens this gap further. |
| "CACHE 10 means each ID jumps by 10." | Step size comes from `INCREMENT`; `CACHE` manages pre-allocated blocks. |
| "Deleting rows rewinds the sequence." | Sequences are independent of current row counts. |
| "Enabling CYCLE avoids exhaustion with zero risk." | `CYCLE` can reissue already-used values; PKs will reject them. |
| "Resetting to 1 fixes gaps." | Can collide with existing rows, logs, foreign keys, and active sessions. |
| "SERIAL is a real numeric storage type." | It is a convenience declaration creating integer/bigint, default `nextval`, and a sequence. |
| "Logical replication auto-syncs sequence state." | Replicating rows and syncing sequence state are separate concerns. |
| "Auto-incrementing IDs are secure if only someone knowing the ID can view it." | Every access needs proper authorization, never security through ID obscurity. |
| "BIGINT never runs out." | `BIGINT` has a finite limit, albeit a huge one. |

## 24. Design and operations checklist

When choosing auto-incrementing numbers for a PostgreSQL table, ask yourself:

| Question | Decision to make |
| --- | --- |
| Need a technical key or a business number? | Sequences fit internal keys; document numbers may require a separate mechanism. |
| Is the data type large enough long-term? | Consider `BIGINT` when high ID volume is expected. |
| Should the column auto-generate values? | Use `GENERATED ALWAYS/BY DEFAULT AS IDENTITY`. |
| Should the app be allowed to supply IDs? | Pick `ALWAYS` or `BY DEFAULT` per workflow. |
| Need to prevent duplicate IDs in the table? | Declare `PRIMARY KEY` or `UNIQUE`. |
| Need the ID of a newly inserted row? | Use `INSERT ... RETURNING`. |
| Importing explicit IDs? | Plan sequence synchronization after import. |
| Multiple sessions inserting concurrently? | Use a sequence, avoid `MAX(id)+1`; never assume commit order. |
| Strictly gapless IDs required? | Standard sequences will not satisfy this; design a dedicated issuance workflow. |
| Could the numeric range run out? | Monitor proximity to limits; avoid `CYCLE` for PKs. |
| Using logical replication/failover? | Check and sync sequence state during cutover. |
| What privileges does the app account need? | Grant minimal table/sequence privileges; restrict `setval`/ALTER. |
| Need cross-database identifiers? | Local sequences are not globally unique; redesign if needed. |
| Handling request retries? | Add business/idempotency keys rather than relying on auto-incrementing IDs. |

## Conclusion

A **sequence** is a stateful number generator in PostgreSQL, while **`GENERATED ... AS IDENTITY`** attaches number generation declaratively to a table column. `GENERATED ALWAYS` prioritizes system-generated values and permits only intentional overrides; `GENERATED BY DEFAULT` lets applications supply explicit IDs when needed. `SERIAL`/`BIGSERIAL` is legacy syntax built on a sequence and `DEFAULT nextval`, still commonly encountered in existing systems.

The key takeaway: **auto-incrementing numbers do not guarantee gapless continuity, commit order, or uniqueness without constraints**. Rollbacks, failed inserts, `ON CONFLICT`, caches, and row deletions all create gaps; importing explicit IDs can leave sequences out of sync with data; and replication requires separate attention to sequence state.

When sequences are used for their intended purpose—efficiently issuing technical identifiers—paired with `PRIMARY KEY`/`UNIQUE`, `INSERT ... RETURNING`, safe import procedures, and idempotent design, you gain durable record keys for your application without mistaking them for a transaction clock or an absolute business numbering engine.
