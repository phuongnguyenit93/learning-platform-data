# Định dạng kết quả, bộ đệm truy vấn, lịch sử và đo thời gian trong psql

Khi làm việc với PostgreSQL bằng dòng lệnh, một phần lớn hiệu quả không nằm ở việc nhớ nhiều câu `SELECT` hơn, mà nằm ở cách sử dụng **`psql`**: điều chỉnh bảng kết quả để đọc rõ trên terminal, soạn một câu SQL nhiều dòng trước khi thực thi, xem hoặc sửa bộ đệm truy vấn, tìm lại lệnh cũ và đo thời gian để so sánh các cách viết SQL.

Bài học này tập trung vào bốn nhóm công cụ của `psql`:

1. **Định dạng kết quả** — trình bày thành bảng, dạng mở rộng, CSV, HTML; điều khiển pager, giá trị `NULL`, tiêu đề và xuất ra tệp.
2. **Bộ đệm truy vấn (query buffer)** — nơi `psql` giữ câu SQL đang nhập nhưng chưa gửi tới PostgreSQL Server; xem, chỉnh sửa, xóa, lưu hoặc thực thi nội dung.
3. **Lịch sử lệnh (history)** — gọi lại các câu đã nhập, tìm kiếm lịch sử và kiểm soát những gì được lưu xuống máy làm việc.
4. **Đo thời gian** — dùng `\timing` để quan sát thời lượng từ client và `EXPLAIN (ANALYZE, BUFFERS)` để hiểu server đã dành công sức vào bước nào.

**Điểm phân biệt quan trọng:** bộ đệm truy vấn của `psql` không phải `shared_buffers` của PostgreSQL Server. Query buffer chứa **văn bản câu lệnh đang soạn ở phía client**; `shared_buffers` là vùng nhớ đệm các trang dữ liệu/chỉ mục ở phía server. Hai cơ chế khác nhau về mục đích và phạm vi.

Các ví dụ dựa trên PostgreSQL hiện đại và `psql` tương thích. Một số tính năng (như định dạng CSV trong `\pset`) yêu cầu phiên bản `psql` đủ mới; hãy xem `psql --version` và `\?` trên môi trường thực tế khi cần.

## 1. Chuẩn bị môi trường psql và cách đọc hai loại lệnh

Kiểm tra phiên bản từ terminal:

```bash
psql --version
```

Kết nối tới database thử nghiệm:

```bash
psql -h localhost -p 5432 -U postgres -d postgres
```

Các tùy chọn gồm:

| Tùy chọn | Ý nghĩa |
|---|---|
| `-h` | Địa chỉ máy PostgreSQL Server |
| `-p` | Cổng dịch vụ PostgreSQL |
| `-U` | Tên role dùng để kết nối |
| `-d` | Tên database |

Lệnh trên chỉ minh họa kết nối cục bộ. Trong hệ thống thật nên dùng role có quyền phù hợp, xác thực an toàn và TLS khi cần; không đưa mật khẩu vào script, history hoặc dòng lệnh ở dạng công khai.

Sau khi kết nối, bạn có thể thấy prompt tương tự:

```text
postgres=>
```

Hai kiểu lệnh hay gặp:

- **SQL**: do PostgreSQL Server thực thi, ví dụ `SELECT current_database();`. Lệnh SQL thường kết thúc bằng dấu `;`.
- **Meta-command** của `psql`: bắt đầu bằng dấu gạch chéo ngược `\`, ví dụ `\x`, `\timing`, `\pset`. Chúng được `psql` xử lý và **thường không cần dấu `;`**.

Ví dụ:

```text
postgres=> SELECT current_database();
 current_database
------------------
 postgres
(1 row)

postgres=> \timing on
Timing is on.

postgres=> SELECT 1;
 ?column?
----------
        1
(1 row)

Time: 0.XXX ms
```

Các số thời gian `0.XXX` chỉ minh họa; chúng phụ thuộc máy, mạng, cache và công việc server đang thực hiện.

### 1.1. Những lệnh trợ giúp nên biết

```text
\?                 -- Trợ giúp các meta-command của psql
\h                 -- Trợ giúp cú pháp câu lệnh SQL
\h SELECT          -- Cú pháp SELECT
\conninfo          -- Thông tin kết nối hiện tại
\l                 -- Liệt kê database
\dn                -- Liệt kê schema
\dt                -- Liệt kê bảng trong phạm vi tìm kiếm
\d ten_bang        -- Xem mô tả một bảng
\q                 -- Thoát psql
```

Các dòng có chú thích trên nhằm giải thích, không phải một script SQL cần gửi nguyên văn. Hãy thử từng lệnh trực tiếp trong `psql`.

## 2. Tạo bảng mẫu để luyện định dạng và đo thời gian

Để tránh phụ thuộc dữ liệu sẵn có, ta tạo một schema riêng trong database thực hành.

```sql
CREATE SCHEMA IF NOT EXISTS psql_lab;

CREATE TABLE IF NOT EXISTS psql_lab.san_pham (
    id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    ten TEXT NOT NULL,
    nhom TEXT NOT NULL,
    gia NUMERIC(12, 2) NOT NULL,
    ghi_chu TEXT,
    tao_luc TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

Nếu bảng mới tạo chưa có hàng, nhập dữ liệu:

```sql
INSERT INTO psql_lab.san_pham
    (id, ten, nhom, gia, ghi_chu)
VALUES
    (1, 'Bàn phím cơ', 'Phụ kiện', 1250000.00, 'Bố cục gọn, kết nối USB-C'),
    (2, 'Chuột không dây', 'Phụ kiện',  450000.00, NULL),
    (3, 'Màn hình 27 inch', 'Màn hình', 5890000.00, 'Độ phân giải cao; phù hợp công việc'),
    (4, 'Tai nghe', 'Âm thanh',  890000.00, 'Có microphone');
```

Nếu chạy ví dụ này lần thứ hai khi các ID đã tồn tại, PostgreSQL có thể báo lỗi khóa chính; bài thực hành giả định một schema/bảng mới và dữ liệu được nhập một lần. Vì cột `id` cho phép cung cấp ID tường minh, chuỗi identity có thể không tự tăng theo những ID đã chèn. Trong ứng dụng thật, ưu tiên để database sinh ID hoặc đồng bộ sequence khi nhập dữ liệu cố định.

Đọc thử:

```sql
SELECT id, ten, nhom, gia, ghi_chu
FROM psql_lab.san_pham
ORDER BY id;
```

Bảng này có cột văn bản dài, giá tiền và `NULL`, đủ để thấy những khác biệt giữa các kiểu trình bày.

## 3. Định dạng kết quả: dùng \pset

Lệnh nền tảng của `psql` là:

```text
\pset [tuy_chon [gia_tri]]
```

`\pset` thay đổi cách **client `psql` trình bày kết quả truy vấn**. Nó không thay đổi dữ liệu trong database và không sửa định nghĩa bảng.

Bạn có thể xem trạng thái thiết lập của `psql` bằng `\pset`, hoặc xem từng tùy chọn theo cú pháp mà phiên bản hỗ trợ. Những tùy chọn thường dùng:

| Tùy chọn `\pset` | Tác dụng |
|---|---|
| `format` | Chọn dạng `aligned`, `unaligned`, `wrapped`, `csv`, `html`... |
| `border` | Số mức viền cho kết quả dạng bảng |
| `expanded` | Hiển thị mỗi bản ghi theo chiều dọc; có thể đặt `auto` |
| `null` | Chuỗi dùng để hiển thị SQL `NULL` |
| `fieldsep` | Ký tự phân cách cột cho định dạng `unaligned` |
| `recordsep` | Ký tự phân cách bản ghi trong kết quả không căn cột |
| `tuples_only` | Ẩn tiêu đề và thông tin phụ, chỉ in dữ liệu |
| `pager` | Bật/tắt trình phân trang khi kết quả dài |
| `footer` | Hiển thị hoặc ẩn thông tin cuối kết quả như số hàng |
| `linestyle` | Kiểu vẽ đường như `ascii`, `old-ascii` hoặc `unicode` |
| `columns` | Độ rộng terminal mục tiêu cho một số kiểu kết quả |
| `csv_fieldsep` | Ký tự phân cách trường cho định dạng CSV nếu phiên bản hỗ trợ |

Một số tùy chọn có thể không có trên `psql` cũ hoặc có ngữ nghĩa khác biệt nhỏ. Hãy dùng `\?` để kiểm tra cú pháp mà client đang chạy.

### 3.1. Dạng aligned: bảng có cột được căn chỉnh

```text
\pset format aligned
\pset border 1
```

Chạy:

```sql
SELECT id, ten, gia
FROM psql_lab.san_pham
ORDER BY id;
```

`aligned` thích hợp với kết quả có số cột không quá nhiều và chiều dài văn bản vừa phải. Các cột được căn để người đọc so sánh số liệu trực quan.

Tuy nhiên, nếu một truy vấn có 30 cột hoặc một cột chứa JSON dài, bảng có thể rộng hơn màn hình. Thay vì tăng kích thước terminal vô hạn, có thể dùng **expanded display** ở phần tiếp theo.

### 3.2. Điều chỉnh đường viền và đường kẻ

```text
\pset border 0
\pset border 1
\pset border 2
\pset linestyle unicode
```

Mức `border` thường ảnh hưởng đường viền quanh các cột và khung bảng. `linestyle unicode` giúp một số terminal hiển thị các đường kẻ Unicode gọn hơn; nếu terminal hoặc font không phù hợp, dùng kiểu ASCII.

Các tùy chọn này chỉ để **tăng khả năng đọc**, không làm thay đổi kết quả SQL và không tối ưu thời gian thực thi truy vấn.

### 3.3. Dạng wrapped và độ rộng cột

Với câu trả lời dài:

```text
\pset format wrapped
\pset columns 80
```

`wrapped` cho phép xuống dòng trong ô khi cần để hạn chế độ rộng bảng, theo cách xử lý của `psql`. Việc bọc dòng có thể hữu ích khi xem mô tả sản phẩm hoặc nội dung JSON dài, nhưng không nên coi nó là cách biểu diễn dữ liệu để máy khác parse.

Khi xuất sang file để chương trình đọc, hãy dùng **CSV** hoặc một định dạng dữ liệu có quy tắc escaping rõ ràng, không dùng bảng wrapped.

## 4. \x: hiển thị một bản ghi theo chiều dọc

Lệnh rất hữu ích trong `psql`:

```text
\x on
```

Sau đó:

```sql
SELECT *
FROM psql_lab.san_pham
WHERE id = 3;
```

Thay vì một dòng rất rộng, kết quả sẽ trình bày mỗi cột trên một dòng, thường tương tự:

```text
-[ RECORD 1 ]------------------------------
id       | 3
ten      | Màn hình 27 inch
nhom     | Màn hình
gia      | 5890000.00
ghi_chu  | Độ phân giải cao; phù hợp công việc
tao_luc  | ...
```

Dạng này phù hợp để xem một hoặc vài bản ghi có nhiều cột, ví dụ kết quả `SELECT *`, metadata, JSON hoặc một hàng chứa các trạng thái vận hành.

Các lệnh liên quan:

```text
\x on       -- Luôn in dạng expanded
\x off      -- Trở về cách hiển thị thông thường
\x auto     -- Tự dùng expanded khi kết quả quá rộng
\x          -- Chuyển trạng thái bật/tắt theo thiết lập hiện tại
```

`\x auto` rất hữu ích khi bạn thường xuyên chạy cả truy vấn ngắn và truy vấn rộng: client chọn cách trình bày theo độ rộng thực tế. Tuy nhiên, ngưỡng và cách xử lý còn phụ thuộc terminal/pager.

**Phân biệt với SQL:** `\x` không phải cú pháp của PostgreSQL Server. Nếu đặt `\x on` trong một công cụ chỉ gửi SQL trực tiếp qua JDBC, nó sẽ không được xử lý như meta-command của `psql`.

## 5. \a và \t: chuyển nhanh giữa kết quả đẹp và kết quả gọn

### 5.1. \a bật/tắt aligned output

```text
\a
```

`\a` là lối tắt chuyển giữa chế độ căn cột và không căn cột của `psql`. Nếu muốn kết quả tái lập rõ ràng trong một script, dùng cách chỉ định tường minh:

```text
\pset format unaligned
```

Định dạng `unaligned` có thể hữu ích khi xuất dữ liệu theo ký tự phân cách, nhưng **không tự có đầy đủ quy tắc quote/escape của CSV**.

### 5.2. \t: ẩn tiêu đề và phần phụ

```text
\t on
```

Sau đó:

```sql
SELECT COUNT(*)
FROM psql_lab.san_pham;
```

Kết quả có thể chỉ còn:

```text
4
```

Lệnh tắt `\t` là công tắc cho `tuples_only`; có thể dùng:

```text
\pset tuples_only on
\pset tuples_only off
```

Khi muốn kết quả gọn để con người xem hoặc cho script shell đọc một scalar, tắt tiêu đề và footer có ích. Nhưng nếu đưa dữ liệu nhiều cột sang một hệ thống khác, nên dùng định dạng CSV có escaping chuẩn thay vì chỉ dựa vào `\t` và `\a`.

### 5.3. Hiển thị NULL rõ ràng

PostgreSQL phân biệt ba tình huống: `NULL`, chuỗi rỗng `''` và chuỗi chứa dấu cách. Trong bảng kết quả của `psql`, `NULL` mặc định có thể không hiển thị một ký hiệu nổi bật.

Đặt chuỗi thay thế:

```text
\pset null '[NULL]'
```

Thử:

```sql
SELECT id, ten, ghi_chu
FROM psql_lab.san_pham
ORDER BY id;
```

Ở sản phẩm `id = 2`, cột `ghi_chu` sẽ được biểu diễn bằng `[NULL]`; người xem sẽ dễ phân biệt với chuỗi rỗng.

**Chú ý:** đây là cách **hiển thị**, không làm phép SQL `COALESCE` hay thay đổi cột trong database. Khi xuất dữ liệu sang file, một chuỗi thay thế tự chọn có thể trở nên mơ hồ nếu dữ liệu thật cũng chứa đúng chuỗi đó; cần quy ước định dạng rõ ràng.

## 6. Xuất CSV, HTML và văn bản không căn cột

### 6.1. CSV qua \pset format csv

Trên các bản `psql` có hỗ trợ `format csv`:

```text
\pset format csv
```

Sau đó:

```sql
SELECT id, ten, nhom, gia
FROM psql_lab.san_pham
ORDER BY id;
```

`psql` sẽ trình bày theo định dạng CSV, có quy tắc quote/escape các trường theo kết quả client. Đây thường phù hợp hơn `unaligned` nếu dữ liệu chứa dấu phẩy, dấu nháy kép hoặc xuống dòng.

Sau khi dùng xong:

```text
\pset format aligned
```

Một sự khác biệt quan trọng: `\pset format csv` là **cách hiển thị kết quả truy vấn của psql**; còn `COPY ... CSV` / `\copy ... CSV` là các công cụ xuất dữ liệu có cú pháp và quy tắc riêng. Không mặc định hai phương thức có kết quả byte-for-byte giống nhau với mọi thiết lập như `NULL`, header hoặc encoding.

### 6.2. Unaligned và ký tự phân cách

```text
\pset format unaligned
\pset fieldsep '|'
\pset tuples_only on
```

Chạy:

```sql
SELECT id, ten, gia
FROM psql_lab.san_pham
ORDER BY id;
```

Kết quả có thể có dạng:

```text
1|Bàn phím cơ|1250000.00
2|Chuột không dây|450000.00
3|Màn hình 27 inch|5890000.00
4|Tai nghe|890000.00
```

Đây là văn bản phân cách dễ xem, nhưng **không phải một định dạng interchange an toàn nếu giá trị chứa `|` hoặc dấu xuống dòng**. Với dữ liệu tùy ý, hãy ưu tiên CSV do `COPY`/`\copy` tạo hoặc công cụ xử lý dữ liệu có escaping thích hợp.

Trở về cấu hình thường dùng:

```text
\pset format aligned
\pset tuples_only off
```

### 6.3. HTML và các kiểu khác

```text
\pset format html
```

Sau đó chạy `SELECT`, `psql` tạo biểu diễn HTML cho bảng kết quả. Một số phiên bản còn hỗ trợ các kiểu như `latex` và `troff-ms`. Chúng phục vụ nhu cầu trình bày hoặc tích hợp theo định dạng, không thay đổi nội dung dữ liệu server.

Nếu muốn xuất báo cáo HTML, vẫn cần chú ý character set, khả năng xử lý CSS và an toàn khi đưa dữ liệu người dùng lên trang web. Một kết quả `psql` ở dạng HTML không mặc nhiên là một trang web hoàn chỉnh.

## 7. Pager, độ rộng terminal và xuất kết quả ra file

### 7.1. Pager là gì?

Khi đầu ra nhiều dòng, `psql` có thể đưa nó qua một trình phân trang như `less`, tùy môi trường. Thao tác này giúp cuộn/xem từng màn hình mà không làm terminal tràn hàng nghìn dòng.

```text
\pset pager on
\pset pager off
\pset pager always
```

- `on`: dùng pager khi phù hợp với kết quả và môi trường.
- `off`: không phân trang, in trực tiếp.
- `always`: yêu cầu sử dụng pager cho những đầu ra phù hợp dù kết quả không dài.

Khi đang ở pager như `less`, nhấn `q` thường để thoát pager, **không phải thoát PostgreSQL**. Hãy phân biệt thao tác của pager với lệnh `\q` tại prompt `psql`.

Để xem kết quả dạng dài cho việc kiểm tra vận hành, `\x auto` kết hợp pager có thể dễ đọc hơn việc chụp màn hình của một bảng quá rộng.

### 7.2. \o chuyển hướng đầu ra của query

Lệnh:

```text
\o /duong-dan/bao_cao.txt
```

thay đổi đích của **query output** tới tệp chỉ định; những truy vấn tiếp theo sẽ được ghi tới tệp đó thay vì hiển thị bình thường trên terminal. Muốn trở lại stdout:

```text
\o
```

Ví dụ tương tác:

```text
\pset format aligned
\o bao_cao_san_pham.txt
```

Sau đó chạy:

```sql
SELECT id, ten, gia
FROM psql_lab.san_pham
ORDER BY gia DESC;
```

Và kết thúc chuyển hướng:

```text
\o
```

**Lưu ý:** nếu quên `\o` không có tham số, các truy vấn sau có thể tiếp tục ghi vào file khiến bạn tưởng `psql` không hiển thị kết quả. Cẩn thận với đường dẫn và quyền filesystem; một bản xuất có thể chứa dữ liệu nhạy cảm.

### 7.3. \g ghi kết quả của đúng truy vấn hiện tại

Trong `psql`, `\g` gửi bộ đệm SQL hiện tại để thực thi. Có thể chỉ định đích ghi kết quả cho lần thực thi đó:

```text
SELECT id, ten, gia
FROM psql_lab.san_pham
ORDER BY id
\g san_pham.txt
```

Đoạn trên là **một tương tác trong `psql`**: không có `;` ở cuối `ORDER BY id`, vì meta-command `\g` đóng vai trò gửi truy vấn và ghi kết quả vào file.

Khác biệt:

- `\o file`: đổi đích đầu ra cho các truy vấn kế tiếp đến khi được đặt lại.
- `\g file`: thực thi truy vấn trong query buffer và chuyển kết quả của **lần thực thi đó** tới file.

Cẩn thận: nếu bạn đã gửi câu SQL bằng dấu `;` rồi mới gõ `\g` riêng, `psql` có thể **thực thi lại câu truy vấn trước đó** theo cách hoạt động của bộ đệm. Với `SELECT` thì chỉ thêm một lần đọc, nhưng với `INSERT` hoặc `UPDATE` có thể gây tác dụng phụ lặp lại.

### 7.4. \copy khác \o và \g như thế nào?

Nếu mục tiêu là tạo file CSV cho chương trình khác đọc, một cách rõ ràng là dùng `\copy`:

```text
\copy (SELECT id, ten, nhom, gia FROM psql_lab.san_pham ORDER BY id) TO 'san_pham.csv' WITH (FORMAT csv, HEADER true)
```

`\copy` là meta-command của `psql` dùng cơ chế PostgreSQL `COPY` qua client. File `san_pham.csv` được ghi **trên máy chạy `psql`**, theo quyền của tiến trình client.

Ngược lại, SQL `COPY ... TO 'path'` dùng đường dẫn phía **PostgreSQL Server** và có quy định đặc quyền khác:

```sql
-- Minh họa cú pháp server-side; cần quyền filesystem phù hợp.
COPY psql_lab.san_pham TO '/srv/postgresql/export/san_pham.csv'
WITH (FORMAT csv, HEADER true);
```

Không dùng câu lệnh server-side đó trên server thật nếu chưa được phép ghi vào đường dẫn tương ứng.

Đối với việc trao đổi dữ liệu, nên phân biệt:

| Công cụ | Mục tiêu | Nơi ghi |
|---|---|---|
| `\pset` | Chọn cách trình bày trong `psql` | Không tự tạo file |
| `\o file` | Chuyển hướng query output nhiều lần | Máy chạy `psql` |
| `\g file` | Thực thi một query và ghi kết quả | Máy chạy `psql` |
| `\copy ... TO` | Xuất dữ liệu qua giao thức COPY | Máy chạy `psql` |
| `COPY ... TO '/path'` | Xuất ở phía server | Máy chạy PostgreSQL Server |

## 8. Bộ đệm truy vấn của psql là gì?

**Query buffer** là nơi `psql` giữ văn bản SQL người dùng đã nhập nhưng chưa gửi thành một statement hoàn chỉnh tới server. Trong tương tác thông thường, câu SQL được gửi khi gặp dấu kết thúc hợp lệ như `;` ngoài chuỗi/comment, hoặc khi dùng một meta-command gửi truy vấn như `\g`.

Ví dụ bắt đầu nhập một câu nhiều dòng:

```text
postgres=> SELECT
postgres->     id,
postgres->     ten,
postgres->     gia
postgres-> FROM psql_lab.san_pham
postgres-> WHERE gia > 500000
postgres-> ORDER BY gia DESC
postgres->
```

Dấu prompt thay đổi từ `=>` sang `->` cho biết `psql` còn đang tích lũy câu SQL, chưa kết thúc. Câu SQL chưa có dấu `;` nên chưa được gửi tới server.

Tại thời điểm này có thể:

- In nội dung query buffer bằng `\p`.
- Mở trình soạn thảo để sửa bằng `\e`.
- Xóa câu đang soạn bằng `\r`.
- Gửi câu SQL bằng `\g`.
- Hoặc gõ dấu `;` để kết thúc và thực thi.

**Bộ đệm này ở phía client.** PostgreSQL Server không nhìn thấy bản nháp SQL trước khi `psql` gửi một statement hoàn chỉnh. Vì vậy câu truy vấn chưa kết thúc trong buffer không tự có transaction chạy, không giữ row lock do chính câu SQL ấy và không tiêu thụ CPU xử lý truy vấn trên server.

Tuy nhiên, nếu trước đó bạn đã mở transaction bằng `BEGIN` hoặc đã chạy những statement khác, session vẫn có thể giữ transaction/khóa từ các lệnh đã thực thi; xóa query buffer **không hủy transaction đang mở**.

## 9. \p, \r, \e, \w và \g: vòng đời của một câu SQL đang soạn

### 9.1. \p: in nội dung trong buffer

Khi đang nhập một câu SQL chưa hoàn tất:

```text
SELECT id, ten, gia
FROM psql_lab.san_pham
WHERE nhom = 'Phụ kiện'
\p
```

`\p` in lại phần SQL đang có trong query buffer, hữu ích khi bạn đã nhập nhiều dòng và muốn kiểm tra xem có thiếu một điều kiện `WHERE`, `JOIN` hay dấu ngoặc không.

`\p` **không thực thi** câu SQL; nó chỉ hiển thị văn bản đã lưu trong buffer.

### 9.2. \r: reset/clear query buffer

```text
\r
```

`\r` loại bỏ câu SQL đang soạn trong buffer để bạn nhập lại từ đầu. Nó đặc biệt hữu ích khi:

- Dán nhầm một câu SQL có điều kiện nguy hiểm.
- Đang nhập dở câu nhiều dòng và muốn hủy trước khi thực thi.
- Quên đóng dấu ngoặc hoặc dấu nháy và muốn bắt đầu lại.
- Không muốn gửi câu SQL đang nằm trong query buffer.

Ví dụ trước khi bấm gửi một lệnh sửa dữ liệu:

```text
UPDATE psql_lab.san_pham
SET gia = gia * 2
\r
```

Sau `\r`, câu `UPDATE` chưa được thực thi và không còn nằm trong buffer.

**Nhớ rằng `\r` chỉ tác động tới query buffer của `psql`**, không phải `ROLLBACK`. Nếu một `UPDATE` đã được gửi và commit, `\r` không hoàn tác dữ liệu.

### 9.3. \e: mở editor để soạn SQL

```text
\e
```

Khi gọi `\e`, `psql` mở trình soạn thảo được cấu hình cho client. Query buffer hiện tại có thể được đưa vào editor để chỉnh sửa. Sau khi lưu và thoát editor, `psql` xử lý phần SQL được sửa theo quy tắc của `\e`; nếu câu đã hoàn chỉnh với dấu `;`, nó có thể được gửi thực thi khi trở lại.

Vì thế, **không dùng `\e` như một thao tác xem vô hại khi buffer chứa lệnh phá hủy dữ liệu**. Hãy biết rõ cách editor lưu file và tình trạng dấu kết thúc câu SQL.

Có thể kiểm soát editor qua biến môi trường phù hợp, chẳng hạn `PSQL_EDITOR`, `EDITOR` hoặc `VISUAL`, tùy nền tảng và cách `psql` chọn chương trình.

Ví dụ trên shell Unix:

```bash
export PSQL_EDITOR=vim
psql -d postgres
```

Trên Windows, tên chương trình và cơ chế khai báo biến môi trường có thể khác. Điều quan trọng là `\e` mở **editor ở máy client**, không phải editor bên trong PostgreSQL Server.

### 9.4. \w: ghi query buffer thành tệp SQL

```text
\w ban_nhap.sql
```

`\w` ghi nội dung **query buffer hiện tại** vào file chỉ định, có ích khi bạn muốn giữ lại một truy vấn dài để chạy sau, review với đồng nghiệp hoặc đưa vào một script có kiểm soát.

**Đừng nhầm `\w` với `\o`:**

- `\w file.sql` lưu **văn bản câu truy vấn** trong buffer.
- `\o ket_qua.txt` lưu **kết quả các câu truy vấn** được thực thi sau đó.

Một file `.sql` được tạo bằng `\w` không tự là migration an toàn. Trước khi dùng lại cần kiểm tra schema đích, transaction, quyền và tác động dữ liệu.

### 9.5. \g: gửi query buffer để thực thi

```text
SELECT id, ten
FROM psql_lab.san_pham
WHERE gia > 500000
\g
```

`\g` gửi câu SQL hiện có trong buffer tới server, tương tự vai trò dấu kết thúc statement của `;` trong trường hợp này.

Nếu buffer chứa:

```sql
DELETE FROM psql_lab.san_pham WHERE id = 1;
```

thì dấu `;` đã thực thi lệnh. Gõ thêm `\g` sau đó có thể thực thi lại câu cuối theo cách `psql` xử lý lịch sử query buffer. Vì vậy, khi thao tác với DML/DDL, **chỉ gửi một lần và quan sát kết quả trước khi gửi tiếp**.

### 9.6. Bảng so sánh nhanh

| Lệnh | Tác động lên query buffer hoặc kết quả | Có chạy SQL không? |
|---|---|---|
| `\p` | In câu SQL hiện đang soạn | Không |
| `\r` | Xóa query buffer | Không |
| `\e` | Sửa câu SQL trong editor và xử lý nội dung khi đóng editor | Có thể, tùy nội dung sau sửa |
| `\w file` | Ghi câu SQL đang soạn vào file | Không |
| `\g` | Gửi câu SQL trong buffer | Có |
| `\g file` | Gửi SQL và ghi kết quả một lần ra file | Có |
| `;` hợp lệ | Kết thúc SQL và gửi thực thi | Có |

Trong thao tác thực tế, nên ưu tiên `\p` hoặc `\r` để tránh vô tình gửi một câu chưa được kiểm tra.

## 10. Nhận biết prompt nhiều dòng và trạng thái còn thiếu

Prompt của `psql` không chỉ cho biết tên database. Nó còn gợi ý câu SQL hiện tại chưa hoàn chỉnh do dấu nháy, dấu ngoặc, dấu comment hoặc dấu kết thúc statement.

Các trạng thái thường gặp có thể trông như sau:

```text
postgres=>   -- Sẵn sàng nhập câu SQL mới

postgres->   -- Đang nhập câu SQL nhiều dòng, chưa kết thúc

postgres'>   -- Đang ở trong chuỗi được mở bởi dấu nháy đơn

postgres">   -- Đang ở trong tên định danh nháy kép

postgres(>   -- Đang ở trong biểu thức có dấu ngoặc mở chưa đóng
```

Hình thức prompt có thể bị tùy chỉnh bằng các biến `PROMPT1`, `PROMPT2` của `psql`; bảng trên dùng hình thức thông dụng để minh họa.

Ví dụ gõ nhầm:

```text
postgres=> SELECT * FROM psql_lab.san_pham
postgres-> WHERE ten = 'Bàn phím cơ
postgres'>
```

Do thiếu dấu nháy đóng, `psql` vẫn chờ nội dung tiếp theo. Nếu không muốn hoàn thiện câu này, hãy dùng `\r` để xóa query buffer. Không phải mất kết nối hay deadlock chỉ vì prompt biến thành dạng `'>`.

Một dòng lệnh dài nhiều dấu ngoặc nên được kiểm tra trước khi gửi để tránh vô ý `UPDATE` toàn bảng hoặc `DELETE` thiếu điều kiện.

## 11. Lịch sử trong psql: phân biệt history với query buffer

**Query buffer** là bản nháp hiện tại. **History** là tập các lệnh/câu SQL đã nhập trong quá trình tương tác trước đó, có thể được giữ trong bộ nhớ và lưu ra tệp lịch sử.

Ví dụ:

- Bạn vừa nhập `SELECT ... WHERE ...` chưa có `;`: nó thuộc query buffer hiện tại.
- Bạn đã thực hiện một loạt câu `SELECT`, `EXPLAIN` và `\dt`: chúng có thể xuất hiện trong lịch sử lệnh của `psql`.
- Bạn gõ mũi tên lên: `psql` có thể đưa một mục từ history trở lại dòng nhập để chỉnh sửa/chạy lại.

Lịch sử hỗ trợ làm việc tương tác nhanh, nhưng **không thay thế Git, migration file hay audit log**. Nó có thể bị giới hạn dung lượng, bị xóa hoặc chưa từng được lưu nếu chương trình được build/khởi chạy không hỗ trợ lịch sử tương tác.

### 11.1. Điều hướng bằng bàn phím

Trong terminal có hỗ trợ readline hoặc thư viện nhập dòng tương đương:

- **Mũi tên lên/xuống:** chọn các lệnh cũ hoặc mới trong history.
- **Ctrl+R:** tìm kiếm ngược theo chuỗi đã gõ.
- **Ctrl+C:** ngắt quá trình nhập/hoạt động theo tình huống; trong `psql` cũng có thể hủy nhập câu đang soạn, nhưng cần phân biệt với việc gửi một câu lệnh đã chạy.
- **Ctrl+A / Ctrl+E:** di chuyển về đầu/cuối dòng trong kiểu chỉnh sửa readline thường gặp.

Tổ hợp phím có thể thay đổi theo terminal, cấu hình readline, hệ điều hành và phần mềm remote session.

### 11.2. \s xem hoặc lưu lịch sử tương tác

Trên phiên bản `psql` có hỗ trợ lệnh này và được build với thư viện lịch sử phù hợp:

```text
\s
```

thường hiển thị lịch sử lệnh tương tác, có thể dùng pager nếu phù hợp.

Để ghi ra file:

```text
\s lich_su_psql.txt
```

**Lưu ý tính tương thích:** nếu lệnh `\s` không có trên bản `psql` đang dùng, kiểm tra `\?` và cấu hình build. Lịch sử vẫn có thể được quản lý bằng các cơ chế khác của terminal/readline hoặc qua tệp lịch sử; không mặc định mọi client đều hỗ trợ cùng meta-command.

`\s` xuất **lịch sử**, không phải query result và không phải nội dung hiện thời của query buffer. Để lưu bản nháp query hiện tại, dùng `\w`.

### 11.3. HISTFILE và HISTSIZE

`psql` có những biến liên quan đến history. Trong nhiều phiên bản:

- **`HISTFILE`:** vị trí file lịch sử được dùng khi lưu phiên tương tác.
- **`HISTSIZE`:** giới hạn số mục lịch sử giữ lại.
- **`HISTCONTROL`:** kiểm soát một số mục được bỏ qua khi lưu, ví dụ lệnh lặp hoặc lệnh bắt đầu bằng khoảng trắng.
- **`HISTIGNORE`:** có thể cung cấp các mẫu lệnh bị loại khỏi lịch sử trên những phiên bản hỗ trợ.

Để xem giá trị một biến đang đặt, dùng `\echo` với cú pháp tham chiếu `:ten_bien`:

```text
\echo :HISTFILE
\echo :HISTSIZE
\echo :HISTCONTROL
```

Trong `psql`, `\set` không tham số hiển thị danh sách biến hiện có. Không dùng `\set TEN_BIEN` chỉ để xem giá trị: cú pháp ấy có thể **đặt biến thành chuỗi rỗng**.

Ví dụ trong môi trường Linux:

```text
\set HISTFILE '/home/student/.psql_history_training'
\set HISTSIZE 2000
\set HISTCONTROL ignoreboth
```

`ignoreboth` thường kết hợp cơ chế bỏ lệnh bắt đầu bằng khoảng trắng và bỏ lệnh trùng mục gần nhất trong lịch sử, tùy phiên bản hỗ trợ. Không coi cơ chế này là giải pháp bảo mật chắc chắn vì có thể vẫn lộ dữ liệu ở log khác, terminal, shell history, monitoring hoặc câu truy vấn được gửi lên server.

Đường dẫn ví dụ cần thay bằng thư mục có quyền truy cập phù hợp với tài khoản máy client. History file **nằm ở phía máy chạy `psql`**, không phải trong database PostgreSQL.

### 11.4. Tránh lưu thông tin nhạy cảm trong history

Không nhập mật khẩu và token vào câu SQL hoặc lệnh client khi có cách truyền an toàn hơn.

Ví dụ có nguy cơ lộ thông tin:

```sql
-- Ví dụ KHÔNG nên làm với mật khẩu thật:
CREATE ROLE app_user LOGIN PASSWORD 'mat_khau_nhay_cam';
```

Nếu gõ trực tiếp trong `psql`, lệnh có thể được lưu vào history, được ghi trong audit/statement logs hoặc xuất hiện trong công cụ giám sát tùy cấu hình. Ngay cả khi xóa history ở máy client, các nguồn ghi khác có thể còn.

Các thực hành nên ưu tiên:

1. Tránh in/gõ secret nguyên văn trong câu lệnh lưu vào history.
2. Dùng cơ chế xác thực và cấp secret phù hợp của tổ chức.
3. Giới hạn quyền truy cập file history và backup của máy client.
4. Không gửi nguyên file `.psql_history` cho người khác nếu chưa kiểm tra thông tin nhạy cảm.
5. Dùng script SQL đã review và quản lý phiên bản cho thao tác có tác động lớn.

History hữu ích cho năng suất cá nhân, nhưng **không phải bản ghi kiểm toán có bảo đảm tính toàn vẹn, đầy đủ và bất biến**.

## 12. \timing: đo thời gian từ phía client

Bật đo thời gian:

```text
\timing on
```

Chạy:

```sql
SELECT COUNT(*)
FROM psql_lab.san_pham;
```

Sau phần kết quả, `psql` in thời gian tương tự:

```text
Time: 0.XXX ms
```

Tắt bằng:

```text
\timing off
```

Có thể dùng `\timing` không tham số để chuyển trạng thái theo cách hỗ trợ của `psql`, nhưng trong script nên dùng `on` hoặc `off` rõ ràng.

### 12.1. \timing đo những gì?

`\timing` đo thời gian thực hiện **theo góc nhìn của `psql`** cho lệnh được gửi qua client. Kết quả chịu ảnh hưởng của:

- Thời gian server thực thi truy vấn.
- Quá trình gửi câu SQL và nhận kết quả qua kết nối.
- Lượng dữ liệu trả về.
- Độ trễ mạng giữa client và database.
- Các yếu tố khác của hệ thống khi client đo thời gian.

Vì vậy, số đo `\timing` **không hoàn toàn đồng nhất** với thời gian executor ở PostgreSQL Server. Tùy phiên bản và đường xử lý của client, chi phí hiển thị/format cũng không nhất thiết được tính giống hoàn toàn với thời gian xử lý server.

Nếu muốn so sánh đường đọc 10 hàng với đường đọc 1 triệu hàng, cần lưu ý phần truyền dữ liệu qua mạng có thể chiếm tỷ trọng rất lớn. Một truy vấn có kế hoạch server tốt vẫn có thể chậm từ góc nhìn người dùng nếu trả một tập dữ liệu khổng lồ.

### 12.2. Ví dụ đo hai kiểu truy vấn

```text
\timing on
```

```sql
SELECT COUNT(*)
FROM psql_lab.san_pham;

SELECT *
FROM psql_lab.san_pham
ORDER BY gia DESC;
```

Truy vấn đầu trả một giá trị, truy vấn sau trả nhiều cột và hàng hơn. Với bốn hàng mẫu, cả hai thường rất nhanh; không dùng kết quả này để kết luận đường truy cập tối ưu cho bảng hàng triệu bản ghi.

### 12.3. Vì sao một lần đo chưa đủ?

Thời gian truy vấn có thể thay đổi giữa các lần chạy vì:

- Shared buffers và page cache của hệ điều hành đã/ chưa có dữ liệu.
- PostgreSQL đang thực hiện checkpoint, autovacuum hoặc workload khác.
- Planner có ước lượng thống kê và kế hoạch cụ thể.
- Khóa hoặc tài nguyên dùng chung đang bị tranh chấp.
- Network và client không có cùng mức tải.
- Kết quả truy vấn khác nhau do dữ liệu thay đổi.

Vì vậy, nên đo **nhiều lần**, xem phân phối thời gian, thống kê tài nguyên và kiểm tra kế hoạch. Không tối ưu chỉ từ một con số nhanh/chậm đo thủ công.

## 13. EXPLAIN và EXPLAIN ANALYZE: đo sâu hơn \timing

Khi một truy vấn chậm, `\timing` cho biết “mất bao lâu ở phía client”, nhưng không cho biết **bước nào tốn chi phí**. PostgreSQL cung cấp `EXPLAIN` để xem kế hoạch và `EXPLAIN (ANALYZE, BUFFERS)` để đo số hàng/thời gian thực thi.

### 13.1. EXPLAIN chỉ xem kế hoạch dự kiến

```sql
EXPLAIN
SELECT id, ten, gia
FROM psql_lab.san_pham
WHERE gia > 500000
ORDER BY gia DESC;
```

Kết quả có thể mô tả `Seq Scan`, `Sort` và các ước lượng về số hàng/cost. Với bảng nhỏ, PostgreSQL thường chọn quét tuần tự thay vì tạo/chọn index; điều này không phải dấu hiệu SQL sai.

### 13.2. EXPLAIN ANALYZE thực thi truy vấn

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, ten, gia
FROM psql_lab.san_pham
WHERE gia > 500000
ORDER BY gia DESC;
```

Những thông tin nên quan sát:

| Thông tin | Ý nghĩa |
|---|---|
| `cost=...` | Chi phí tương đối theo mô hình planner, không phải milliseconds |
| `rows=...` trong ước lượng | Số hàng planner dự kiến ở một bước |
| `actual time=...` | Thời gian thực tế của một bước theo kết quả instrument |
| `actual rows=...` | Số hàng thực tế được xử lý/trả theo bước |
| `loops=...` | Số lần một node được thực thi |
| `Buffers: shared hit/read/...` | Tình trạng đọc/ghi/đụng tới trang theo instrumentation |
| `Planning Time` | Thời gian lập kế hoạch |
| `Execution Time` | Thời gian thực thi kế hoạch trong server |

Không so sánh trực tiếp `cost` với milliseconds: `cost` là đơn vị tương đối của mô hình chi phí, còn thời gian thực tế là số đo thực hiện.

`\timing` và `EXPLAIN ANALYZE` giải quyết những câu hỏi khác nhau:

- **`\timing`:** client mất bao lâu để gửi truy vấn và nhận kết quả?
- **`EXPLAIN ANALYZE`:** PostgreSQL đã chọn kế hoạch nào, mỗi bước thực sự xử lý bao nhiêu hàng và tốn bao nhiêu thời gian?
- **`BUFFERS`:** kết quả có liên quan đến mức độ đọc/ghi trang bộ nhớ và I/O không?

Lưu ý `EXPLAIN ANALYZE` có **overhead do đo lường**, không phải cách đo tuyệt đối không tác động. Muốn so sánh hiệu năng đáng tin cậy cần xét cả cấu trúc truy vấn, quy mô dữ liệu và điều kiện chạy.

### 13.3. Cảnh báo với DML

```sql
EXPLAIN (ANALYZE, BUFFERS)
UPDATE psql_lab.san_pham
SET gia = gia * 1.05
WHERE id = 1;
```

Lệnh trên **sẽ thực sự cập nhật dữ liệu** nếu được thực thi trong transaction được commit/đang autocommit. Không chạy nó trên production chỉ để “xem thử kế hoạch”.

Nếu cần đo một cập nhật trên database thử nghiệm rồi hoàn tác:

```sql
BEGIN;

EXPLAIN (ANALYZE, BUFFERS)
UPDATE psql_lab.san_pham
SET gia = gia * 1.05
WHERE id = 1;

ROLLBACK;
```

`ROLLBACK` hoàn tác thay đổi giao dịch của ví dụ trên, nhưng việc thực thi vẫn tạo tải, lấy khóa và có các tác động vận hành như sinh WAL/buffer activity. Với trigger có side effect ngoài database hoặc các thao tác phi giao dịch, rollback cũng không nhất thiết hoàn tác mọi thứ. Vì vậy cần môi trường thử phù hợp.

## 14. Đo thời gian chính xác hơn: tách client, server và plan

Một quy trình quan sát nên đi từ ít tác động đến nhiều thông tin:

```text
Bắt đầu với một SELECT cụ thể
             │
             ▼
\timing on → tổng thời gian client nhìn thấy
             │
             ▼
EXPLAIN → kế hoạch và ước lượng, chưa chạy query dữ liệu
             │
             ▼
EXPLAIN (ANALYZE, BUFFERS) → số liệu thực thi server
             │
             ▼
Đối chiếu hàng thực tế, I/O, lock và network
             │
             ▼
Thử phương án index / SQL / cấu hình có kiểm soát
             │
             ▼
Đo lại trong điều kiện tương đương
```

Ví dụ một truy vấn trả nhiều dữ liệu:

```sql
SELECT *
FROM psql_lab.san_pham;
```

Trên bảng cực lớn, `\timing` có thể phản ánh cả chi phí truyền và nhận hàng, trong khi `EXPLAIN ANALYZE` phân tích công việc executor. Nếu mục tiêu là phân tích plan, đừng làm terminal in ra hàng triệu dòng; có thể kiểm tra `EXPLAIN` trước, dùng output redirection khi cần và giới hạn lượng dữ liệu hiển thị theo mục tiêu.

### 14.1. Cẩn trọng khi dùng LIMIT để đo

```sql
SELECT *
FROM psql_lab.san_pham
LIMIT 10;
```

`LIMIT 10` chỉ giới hạn số hàng được trả và có thể thay đổi kế hoạch, không phải kỹ thuật trung lập để đo toàn bộ truy vấn. Nếu câu cần `ORDER BY`, index, filter hoặc join phức tạp, PostgreSQL có thể phải xử lý nhiều hơn 10 hàng để tìm được 10 kết quả cuối cùng.

Muốn đánh giá truy vấn gốc, phải đo **đúng điều kiện và khối lượng thực tế**, không thay bằng một câu khác rồi kết luận server đã tối ưu.

### 14.2. Làm mới thống kê nếu dữ liệu thay đổi mạnh

Trên bảng thử nghiệm:

```sql
ANALYZE psql_lab.san_pham;
```

`ANALYZE` cập nhật thống kê phục vụ planner. Sau khi nhập/xóa lượng lớn dữ liệu, thống kê lỗi thời có thể làm ước lượng hàng và kế hoạch thiếu phù hợp.

Nhưng **`ANALYZE` không phải nút tăng tốc vạn năng**. Nếu nguyên nhân là SQL sai, thiếu index cần thiết, network hoặc lock, cập nhật thống kê đơn thuần chưa chắc giải quyết vấn đề.

## 15. \watch: theo dõi một truy vấn theo chu kỳ

Trong lúc chẩn đoán, có thể muốn xem số kết nối hoặc hàng trong một bảng thay đổi qua thời gian. `psql` hỗ trợ `\watch` để chạy lại truy vấn theo chu kỳ.

Ví dụ:

```text
SELECT now(), COUNT(*) AS so_san_pham
FROM psql_lab.san_pham
\watch 2
```

Trong nhiều phiên bản `psql`, `\watch 2` lặp truy vấn khoảng mỗi 2 giây và hiển thị kết quả theo từng vòng. Dùng Ctrl+C để dừng việc theo dõi theo môi trường terminal.

Đây là ví dụ phù hợp vì truy vấn `COUNT(*)` trên bảng nhỏ. Trên bảng rất lớn, lặp một truy vấn tốn I/O mỗi giây có thể tạo tải đáng kể.

`\watch` **không phải lịch chạy ở PostgreSQL Server**. Nó cần client `psql` còn hoạt động và không tạo một job bền vững để chạy sau khi bạn thoát terminal.

### 15.1. Đo thời gian trong vòng lặp

Nếu bật `\timing on` rồi chạy `\watch`, kết quả trình bày thời gian có thể phụ thuộc phiên bản và cách `psql` điều phối việc theo dõi. Đừng xem khoảng giữa hai lần hiển thị đúng bằng execution time: nó còn liên quan tới thời gian chờ chu kỳ và đầu ra terminal.

Với giám sát production, thay vì chạy `\watch` thủ công nhiều giờ, nên dùng hệ thống metrics/alerting được thiết kế cho workload, retention và quyền truy cập phù hợp.

## 16. Các biến và script psql phục vụ quy trình lặp lại

Một vài cấu hình hữu ích có thể đặt ngay trong phiên hoặc lưu trong file startup `.psqlrc` của người dùng, tùy nền tảng.

Ví dụ tương tác:

```text
\pset null '[NULL]'
\x auto
\timing on
\pset pager on
```

Trong `.psqlrc`, có thể ghi các dòng meta-command tương tự để thiết lập cách hiển thị mặc định mỗi lần mở `psql`. Nên tránh đặt các lệnh DML/DDL có tác dụng thật trong startup file.

### 16.1. Không để cấu hình cá nhân làm sai output script

Nếu một script dự kiến xuất dữ liệu để công cụ khác parse, cấu hình `.psqlrc` của người chạy có thể làm kết quả khác nhau (ví dụ tự bật expanded mode, thêm footer hoặc đổi cách biểu diễn `NULL`).

Có thể chạy `psql` với `-X` để bỏ qua startup file:

```bash
psql -X -d postgres -f bao_cao.sql
```

Trong script, chủ động đặt format/output/timing cần thiết thay vì phụ thuộc cấu hình tương tác của từng người.

### 16.2. Biến psql và cách chèn vào SQL

`psql` hỗ trợ biến client:

```text
\set gia_toi_thieu 500000
```

Sử dụng trong query:

```sql
SELECT id, ten, gia
FROM psql_lab.san_pham
WHERE gia > :gia_toi_thieu;
```

Biến được `psql` thay thế trước khi gửi SQL. Nó hữu ích cho script nhỏ, nhưng không đồng nghĩa với **bind parameters của prepared statement ở driver**. Nếu chèn chuỗi trực tiếp không đúng cách, có thể gây lỗi cú pháp hoặc rủi ro injection.

Đối với dữ liệu text, `psql` có các cú pháp trích dẫn biến phù hợp như `:'ten_bien'` để thay thế dưới dạng SQL literal được quote đúng, tùy công dụng. Dù vậy, ứng dụng chuyên nghiệp thường nên dùng parameter binding của driver/ORM thay vì tự ghép SQL trong terminal.

### 16.3. Dừng script khi có lỗi

Trong script tự động:

```text
\set ON_ERROR_STOP on
```

Biến `ON_ERROR_STOP` giúp `psql` dừng khi gặp lỗi SQL/meta-command trong các ngữ cảnh script, thay vì tiếp tục chạy những lệnh sau và làm kết quả cuối khó diễn giải. Ví dụ trên shell:

```bash
psql -X -v ON_ERROR_STOP=1 -d postgres -f bao_cao.sql
```

Khi chạy automation, cần kiểm tra exit status của `psql`. Đừng chỉ quan sát có tệp output rồi kết luận mọi câu SQL trong script đã thành công.

## 17. Một buổi làm việc mẫu: soạn → kiểm tra → thực thi → xuất → đo

Đây là kịch bản kết nối các công cụ trong một tác vụ thực tế: bạn muốn lấy danh sách sản phẩm giá trên 500.000, kiểm tra kết quả, xuất CSV, rồi đo kế hoạch của truy vấn.

### Bước 1: thiết lập cách xem kết quả

Trong `psql`:

```text
\pset null '[NULL]'
\x auto
\timing on
```

### Bước 2: soạn câu SQL chưa gửi

```text
SELECT id, ten, nhom, gia, ghi_chu
FROM psql_lab.san_pham
WHERE gia > 500000
ORDER BY gia DESC
```

Vì chưa có `;`, câu SQL vẫn nằm trong query buffer.

### Bước 3: xem lại nội dung

```text
\p
```

Nếu nhận ra điều kiện sai, dùng `\e` để chỉnh trong editor hoặc `\r` để xóa rồi nhập lại. Không gửi lệnh nguy hiểm trước khi kiểm tra.

### Bước 4: thực thi

```text
\g
```

`psql` gửi query tới PostgreSQL Server, hiển thị kết quả và (vì đã bật `\timing`) thông báo thời gian client quan sát được.

### Bước 5: xuất CSV bằng một câu truy vấn có chủ đích

```text
\copy (SELECT id, ten, nhom, gia, ghi_chu FROM psql_lab.san_pham WHERE gia > 500000 ORDER BY gia DESC) TO 'bao_cao_san_pham.csv' WITH (FORMAT csv, HEADER true)
```

Lệnh `\copy` ghi file trên máy client. Sau khi xuất, nên kiểm tra kích thước/file và vị trí, đặc biệt nếu thông tin sản phẩm là dữ liệu nội bộ không được chia sẻ công khai.

### Bước 6: kiểm tra kế hoạch server

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, ten, nhom, gia, ghi_chu
FROM psql_lab.san_pham
WHERE gia > 500000
ORDER BY gia DESC;
```

So sánh `Execution Time` với `\timing` để hiểu hai thước đo đang quan sát những phạm vi khác nhau. Bảng mẫu chỉ có vài hàng nên không dùng sự khác biệt nhỏ giữa các lần đo để rút ra kết luận tối ưu index.

### Bước 7: trả lại trạng thái hiển thị thuận tiện

```text
\x off
\pset format aligned
\pset tuples_only off
\o
\timing off
```

Việc đặt lại giúp các truy vấn sau không bất ngờ in theo format CSV, tiếp tục ghi vào file, hoặc hiển thị quá dài.

## 18. Những lỗi thường gặp khi dùng query buffer và output format

| Hiện tượng | Nguyên nhân hay gặp | Cách xử lý |
|---|---|---|
| Prompt chuyển từ `=>` sang `->`, query chưa chạy | Chưa có dấu `;` hoặc chưa dùng `\g` | Hoàn tất câu SQL, dùng `\g` hoặc `\r` nếu muốn hủy |
| Prompt chuyển sang `'>` | Chuỗi nháy đơn chưa đóng | Đóng chuỗi cho đúng hoặc `\r` |
| Gõ `\r` nhưng dữ liệu vẫn đã thay đổi | Lệnh DML đã chạy trước đó | `\r` chỉ xóa bản nháp; cần cơ chế transaction/rollback khi còn khả thi |
| Câu `UPDATE` bị chạy lần nữa | Dùng `\g` sau khi lệnh đã được gửi bằng `;` | Không gửi lại khi chưa kiểm tra; tránh chạy trùng DML |
| Kết quả quá rộng | Nhiều cột/giá trị dài | `\x auto` hoặc `\pset format wrapped` |
| Không thấy output trên terminal | Trước đó đã dùng `\o file` | Gõ `\o` để trả lại stdout |
| Cần CSV nhưng file phân cách bị hỏng | Dùng unaligned với dấu phân cách xuất hiện trong dữ liệu | Dùng `\copy ... WITH (FORMAT csv)` hoặc `\pset format csv` |
| Không phân biệt NULL với chuỗi rỗng | Cách hiển thị mặc định không rõ | `\pset null '[NULL]'` |
| `\s` không được nhận diện | Phiên bản/build psql không hỗ trợ cách xem history đó | Kiểm tra `\?` và cơ chế lịch sử của môi trường |
| Lịch sử chứa secret | Đã gõ mật khẩu/token vào SQL hoặc command | Bảo vệ history và log, thu hồi secret khi cần |
| `\timing` lệch `EXPLAIN ANALYZE` | Một cái từ góc nhìn client, một cái là thời gian server instrument | So đúng phạm vi và điều kiện, tránh kết luận từ một lần chạy |
| Một truy vấn SELECT nhỏ trên bảng thử cho `Seq Scan` | Planner thấy quét bảng rẻ hơn index | Đánh giá trên dữ liệu đại diện, không mặc định là lỗi |
| Script chạy với output khó parse | `.psqlrc` thay format hoặc bật pager | Dùng `psql -X` và cấu hình output tường minh |

## 19. Bài tập thực hành

### Bài 1: chuyển một hàng sang dạng dễ đọc

**Yêu cầu:** lấy tất cả thông tin sản phẩm `id = 3` theo chiều dọc, sau đó trở về dạng bảng.

```text
\x on
```

```sql
SELECT *
FROM psql_lab.san_pham
WHERE id = 3;
```

```text
\x off
```

**Giải thích:** `\x` thay đổi hiển thị; câu `SELECT` và dữ liệu không đổi.

### Bài 2: phân biệt NULL với chuỗi rỗng

**Yêu cầu:** làm nổi bật giá trị `NULL` trong cột `ghi_chu`.

```text
\pset null '[NULL]'
```

```sql
SELECT id, ten, ghi_chu
FROM psql_lab.san_pham
ORDER BY id;
```

**Đáp án:** hàng `id = 2` hiển thị `[NULL]`. Điều đó không làm cột `ghi_chu` được cập nhật thành chuỗi mới.

### Bài 3: hủy một UPDATE đang soạn

**Yêu cầu:** nhập một câu `UPDATE` nhưng không gửi tới server và không làm thay đổi dữ liệu.

```text
UPDATE psql_lab.san_pham
SET gia = gia + 999999
WHERE id = 4
\p
\r
```

**Giải thích:** `\p` in bản nháp, `\r` xóa bản nháp. Vì không có `;` hoặc `\g` trước đó, câu `UPDATE` chưa được thực thi. Đây không phải ví dụ về rollback một giao dịch đã chạy.

### Bài 4: lưu bản nháp truy vấn để review

**Yêu cầu:** soạn query báo cáo rồi ghi **câu SQL** vào tệp, không ghi kết quả.

```text
SELECT nhom, COUNT(*) AS so_mat_hang
FROM psql_lab.san_pham
GROUP BY nhom
ORDER BY nhom
\w bao_cao_theo_nhom.sql
\r
```

**Đáp án:** `\w` ghi query buffer vào `bao_cao_theo_nhom.sql`, còn `\r` xóa phần SQL đang soạn. Trong ví dụ này chưa có lệnh thực thi truy vấn.

### Bài 5: xuất CSV đúng quy tắc

**Yêu cầu:** lưu dữ liệu các sản phẩm với tiêu đề cột.

```text
\copy (SELECT id, ten, nhom, gia FROM psql_lab.san_pham ORDER BY id) TO 'san_pham.csv' WITH (FORMAT csv, HEADER true)
```

**Giải thích:** `\copy` ghi tại phía client và sử dụng cơ chế CSV có escaping thích hợp. Không thay bằng `\pset fieldsep ','` rồi tự cho đó là CSV chuẩn.

### Bài 6: đo thời gian và xem chi phí thực thi

```text
\timing on
```

```sql
SELECT COUNT(*)
FROM psql_lab.san_pham;

EXPLAIN (ANALYZE, BUFFERS)
SELECT COUNT(*)
FROM psql_lab.san_pham;
```

**Câu hỏi:** tại sao hai con số thời gian có thể khác?

**Đáp án:** `\timing` đo theo góc nhìn client đối với các câu lệnh được gửi, trong khi `EXPLAIN ANALYZE` đo công việc của server với instrumentation và không trả toàn bộ tập kết quả của truy vấn gốc theo cùng một cách. Ngoài ra hai lần thực thi có thể chịu ảnh hưởng cache và workload khác nhau.

### Bài 7: tìm lại lệnh cũ

**Yêu cầu:** dùng mũi tên lên và tìm kiếm ngược để gọi lại một câu `SELECT` đã thực thi, chỉnh sửa điều kiện `WHERE` rồi chạy.

**Gợi ý:** trong terminal hỗ trợ readline, dùng mũi tên lên hoặc Ctrl+R. Kiểm tra kỹ câu gọi lại trước khi bấm Enter vì lịch sử cũng có thể chứa `INSERT`, `UPDATE`, `DELETE` hoặc DDL.

## 20. Quy tắc ghi nhớ khi làm việc với psql

```text
GÕ CÂU SQL
     │
     ▼
Query buffer trong psql
     ├── \p  : xem nội dung đang soạn
     ├── \e  : sửa trong editor
     ├── \w  : lưu câu SQL ra file
     ├── \r  : xóa bản nháp
     └── ; / \g : GỬI CÂU SQL ĐỂ CHẠY
                       │
                       ▼
                 PostgreSQL Server
                       │
              Planner / Executor
                       │
                       ▼
                   Result set
                       │
                       ▼
                  psql output
            ┌──────────┼───────────┐
            │          │           │
            ▼          ▼           ▼
     \pset / \x      \o / \g     \timing
     trình bày       ghi file    đo thời gian
            │          │           │
            └──────────┴───────────┘
                       │
                       ▼
              Người dùng / script

History:
  Mũi tên / Ctrl+R / \s / HISTFILE
  → hỗ trợ gọi lại các lệnh đã nhập;
    không phải transaction log hay audit log.
```

Năm điểm cốt lõi:

1. **Định dạng kết quả là việc của client.** `\pset`, `\x`, `\a`, `\t`, pager và `\o` giúp xem hoặc xuất dữ liệu; chúng không thay đổi semantics của câu `SELECT`.
2. **Query buffer chỉ giữ câu SQL đang soạn.** `\p` để xem, `\e` để sửa, `\w` để lưu, `\r` để xóa; `;` và `\g` mới gửi lệnh thực thi.
3. **History không phải transaction history của server.** Nó hỗ trợ năng suất khi dùng terminal, nhưng có thể bị giới hạn, không đầy đủ và chứa thông tin nhạy cảm.
4. **`\timing` và `EXPLAIN ANALYZE` không thay thế nhau.** Một thước đo thời gian qua client; thước kia giải thích kế hoạch và chi phí thực thi của server.
5. **An toàn trước khi tiện lợi.** Lệnh lấy lại từ history, câu trong query buffer và script có thể gây thay đổi dữ liệu thật. Xác định đúng database/schema, kiểm tra điều kiện, transaction và phạm vi tác động trước khi gửi lệnh.

Nắm vững những công cụ này giúp việc học và vận hành PostgreSQL bớt phụ thuộc vào thao tác thử-sai: bạn có thể **soạn SQL có kiểm soát, đọc kết quả theo định dạng thích hợp, lưu dữ liệu rõ ràng và dùng phép đo phù hợp để tìm nguyên nhân khi truy vấn chậm**.
