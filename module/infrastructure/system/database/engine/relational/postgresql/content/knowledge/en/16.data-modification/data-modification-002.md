# Default Values, Identity Columns, and Generated Columns in PostgreSQL

When inserting a record, the application does not necessarily have to supply every value. PostgreSQL can automatically populate **initial statuses**, **creation timestamps**, **default quantities**, **numeric identifiers**, or **values computed from other columns**. Although they look similar in that "the database auto-populates a value," these are distinct mechanisms with different syntax, evaluation timing, updatability, and data-integrity rules.

For example, when creating an order:

- `status` can default to `'draft'`.
- `created_at` can receive the transaction start timestamp.
- `order_id` can take the next number from a sequence via an **identity** column.
- `line_total` can be computed from `quantity * unit_price` via a **generated column**.

The three core concepts of this lesson in the **Data Modification** chapter are:

1. **`DEFAULT`**: fills in a value when a write statement omits the column or explicitly requests `DEFAULT`.
2. **`GENERATED ... AS IDENTITY`**: generates identifier values via a sequence, with two modes for controlling explicit inputs: `ALWAYS` and `BY DEFAULT`.
3. **Generated/computed column**: a column whose value depends on an expression over other columns in the same row, such as `quantity * unit_price`.

This lesson thoroughly explains each mechanism, covering `INSERT`, `UPDATE`, `RETURNING`, `OVERRIDING`, `ALTER TABLE`, `ON CONFLICT`, `NULL` edge cases, sequence ordering, concurrency, and migrations, along with a PostgreSQL lab you can practice on a test database.

## 1. The Big Picture: Three Different Kinds of "Auto-Fill"

| Mechanism | Declaration Example | When Does PostgreSQL Evaluate It? | Can You Supply a Value Directly? |
|---|---|---|---|
| Default value | `status TEXT DEFAULT 'draft'` | When INSERT uses the default | Yes, supplied value overrides DEFAULT |
| Function-based default | `created_at TIMESTAMPTZ DEFAULT now()` | When the default value is used | Yes |
| Identity BY DEFAULT | `id BIGINT GENERATED BY DEFAULT AS IDENTITY` | When no ID is provided | Yes |
| Identity ALWAYS | `id BIGINT GENERATED ALWAYS AS IDENTITY` | When no ID is provided | Manual INSERT requires appropriate override syntax |
| Generated stored | `total NUMERIC GENERATED ALWAYS AS (qty * price) STORED` | When writing/updating the row | Cannot assign an arbitrary value |
| Generated virtual (supported versions) | `... GENERATED ALWAYS AS (...) VIRTUAL` | When reading the value | Cannot assign an arbitrary value |

A critical point: **identity columns and generated computed columns both contain the word `GENERATED`, but they do not mean the same thing**.

- Identity uses a sequence to generate values when needed.
- A generated computed column depends on an expression over the row's own data.
- DEFAULT is a fallback value or expression when the writer does not provide one.

### 1.1. Which Column Needs Which Mechanism?

Ask:

- "What is a sensible initial value if the application sends nothing?" → `DEFAULT`.
- "Does each row need a database-issued numeric identifier?" → `IDENTITY` combined with a unique/primary key constraint.
- "Is this value always calculated from other columns in the same row?" → **Generated column** if the expression is eligible and supported by PostgreSQL.
- "Does the value only change upon a service event or trigger?" → May require dedicated update logic, not just DEFAULT/generated columns.

## 2. What Is DEFAULT?

`DEFAULT` defines an expression PostgreSQL uses to produce a value when an `INSERT` operation does not supply one for that column.

~~~sql
CREATE TABLE customer_preferences (
    preference_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    newsletter_enabled BOOLEAN NOT NULL DEFAULT FALSE,
    preferred_language TEXT NOT NULL DEFAULT 'vi',
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
~~~

If you write:

~~~sql
INSERT INTO customer_preferences (preferred_language)
VALUES ('en')
RETURNING *;
~~~

PostgreSQL automatically fills in:

- `preference_id` from the identity sequence.
- `newsletter_enabled = false`.
- `preferred_language = 'en'` because it was explicitly provided.
- `created_at` from the default expression.

### 2.1. DEFAULT Does Not Imply Required

~~~sql
CREATE TABLE defaults_only (
    nickname TEXT DEFAULT 'Guest',
    status TEXT DEFAULT 'new'
);
~~~

Both columns still allow `NULL` if `NOT NULL` is absent.

If business rules forbid `NULL`:

~~~sql
CREATE TABLE defaults_not_null (
    nickname TEXT NOT NULL DEFAULT 'Guest',
    status TEXT NOT NULL DEFAULT 'new'
);
~~~

**DEFAULT** determines the value when input is missing. **NOT NULL** guards the column value once determined.

### 2.2. DEFAULT Can Be a Constant or an Expression

~~~sql
CREATE TABLE default_examples (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    active BOOLEAN NOT NULL DEFAULT TRUE,
    retry_count INTEGER NOT NULL DEFAULT 0,
    category TEXT NOT NULL DEFAULT 'general',
    created_on DATE NOT NULL DEFAULT CURRENT_DATE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
~~~

Do not treat `DEFAULT 'general'` as a kind of "immutable column." A writer can still provide a different value:

~~~sql
INSERT INTO default_examples (
    active,
    retry_count,
    category
)
VALUES (FALSE, 3, 'custom');
~~~

If only a fixed set of values is allowed, use `CHECK`, a foreign key, or an appropriate data model.

## 3. When Is a Default Value Applied?

Consider a table:

~~~sql
CREATE TABLE default_semantics (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    status TEXT DEFAULT 'draft',
    quantity INTEGER DEFAULT 1
);
~~~

### 3.1. Omitting the Column in INSERT

~~~sql
INSERT INTO default_semantics (quantity)
VALUES (5)
RETURNING id, status, quantity;
~~~

The `status` column receives `'draft'`.

### 3.2. Explicitly Writing DEFAULT

~~~sql
INSERT INTO default_semantics (status, quantity)
VALUES (DEFAULT, DEFAULT)
RETURNING id, status, quantity;
~~~

Both columns use their respective defaults.

### 3.3. Explicitly Sending NULL

~~~sql
INSERT INTO default_semantics (status, quantity)
VALUES (NULL, NULL)
RETURNING id, status, quantity;
~~~

When the columns lack `NOT NULL`, both stored values are `NULL`. **PostgreSQL does not automatically replace an explicit `NULL` with `DEFAULT`**.

| Input in INSERT | What Does `status DEFAULT 'draft'` Receive? |
|---|---|
| Omit `status` column | `'draft'` |
| Write `status = DEFAULT` | `'draft'` |
| Write `status = 'paid'` | `'paid'` |
| Write `status = NULL` | `NULL` if the column allows it |
| Write `status = ''` | Empty string, not the default |

This is especially important when an API sends JSON `null` for any omitted field. If the backend passes `NULL` into the `INSERT` statement, the database default will not be applied.

### 3.4. When There Is No DEFAULT

An ordinary column without a default value receives `NULL` if omitted from `INSERT`, unless a constraint such as `NOT NULL` rejects it.

Having no `DEFAULT` does not mean PostgreSQL automatically fills in 0, an empty string, or the current timestamp.

## 4. INSERT ... DEFAULT VALUES

When every column can be generated or take a default value:

~~~sql
CREATE TABLE empty_request_events (
    event_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    event_type TEXT NOT NULL DEFAULT 'created',
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);

INSERT INTO empty_request_events
DEFAULT VALUES
RETURNING *;
~~~

`DEFAULT VALUES` specifies no columns; the database uses the default value for every column. If any required column lacks a default, the `INSERT` is rejected.

### 4.1. DEFAULT VALUES Differs from VALUES(NULL)

~~~sql
-- Uses all defaults.
INSERT INTO empty_request_events DEFAULT VALUES;

-- Not the same: writes an explicit NULL into event_type.
INSERT INTO empty_request_events (event_type)
VALUES (NULL);
~~~

The second statement violates `NOT NULL`; it does not receive `'created'`.

### 4.2. DEFAULT in Multi-Row VALUES

~~~sql
INSERT INTO empty_request_events (event_type)
VALUES
    (DEFAULT),
    ('processed'),
    (DEFAULT)
RETURNING event_id, event_type;
~~~

Each row can use `DEFAULT` or an explicit value in the corresponding position.

## 5. DEFAULT Is Evaluated Per Row

A default value can be a function, not just a constant:

~~~sql
CREATE TABLE random_samples (
    sample_id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    sampled_value DOUBLE PRECISION NOT NULL DEFAULT random()
);

INSERT INTO random_samples DEFAULT VALUES;
INSERT INTO random_samples DEFAULT VALUES;
~~~

`random()` is evaluated each time the default value is used. Different rows can receive different values.

### 5.1. DEFAULT Cannot Directly Reference Other Columns in the Same Row

The following idea is invalid for an ordinary default:

~~~sql
-- Invalid syntax in principle:
-- CREATE TABLE line_items (
--     quantity INTEGER,
--     unit_price NUMERIC,
--     total NUMERIC DEFAULT (quantity * unit_price)
-- );
~~~

A column's `DEFAULT` expression cannot directly depend on other column values in the same row this way.

If you need `total = quantity * unit_price`, use a **generated column** when appropriate, or compute it in the application/transaction with a consistent design.

### 5.2. DEFAULT Does Not Recalculate When Other Columns Change

If `unit_price` is updated, an ordinary column that previously received a `DEFAULT` **does not automatically change** to reflect the new price. `DEFAULT` serves to produce a value when a write command asks for the default, not to maintain a continuous computed relationship.

## 6. DEFAULT for Timestamps: now(), CURRENT_TIMESTAMP, and clock_timestamp()

A familiar example:

~~~sql
CREATE TABLE activity_log (
    activity_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    action_name TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
~~~

### 6.1. CURRENT_TIMESTAMP and now()

In PostgreSQL, `CURRENT_TIMESTAMP`, `now()`, and `transaction_timestamp()` return the **start time of the current transaction**.

~~~sql
BEGIN;

SELECT now() AS first_read;
SELECT pg_sleep(1);
SELECT now() AS second_read,
       clock_timestamp() AS actual_clock;

COMMIT;
~~~

Both `now()` calls in the same transaction return the same instant. `clock_timestamp()` reads the wall-clock time at the moment of invocation and can change.

`pg_sleep()` is only for testing environments; never keep production transactions sleeping.

### 6.2. DEFAULT CURRENT_TIMESTAMP Does Not Mean COMMIT Time

If a transaction begins at 10:00 and the `INSERT` runs at 10:05, `CURRENT_TIMESTAMP` still reflects the transaction start time.

If business logic requires "statement execution time" or "real wall-clock time at invocation," consider `statement_timestamp()` or `clock_timestamp()` instead of blindly using `now()`.

### 6.3. Choose TIMESTAMPTZ for Instants

An event that actually occurred at a point in time should typically use:

~~~sql
created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
~~~

`TIMESTAMPTZ` represents an instant in time, displayed in the session's time zone. PostgreSQL does not separately store the original time zone offset the user passed in.

If a column represents a business calendar date in a specific time zone, you may need `DATE` with explicit date-resolution rules rather than relying on the session's `CURRENT_DATE` while ignoring the business time zone.

### 6.4. DEFAULT created_at Does Not Automatically Update updated_at

~~~sql
CREATE TABLE profiles_time (
    profile_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    display_name TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
~~~

When updating `display_name`, the `updated_at` column **does not change automatically** just because it has a `DEFAULT`.

The application can update it explicitly:

~~~sql
UPDATE profiles_time
SET display_name = 'New Name',
    updated_at = clock_timestamp()
WHERE profile_id = 1;
~~~

If every write path must refresh `updated_at`, consider a tested and well-managed trigger. Do not use a `now()` generated column for this purpose, because generated column expressions have other restrictions.

## 7. DEFAULT with UUIDs and Identifier Strings

A system may need UUIDs instead of sequential numeric IDs:

~~~sql
CREATE TABLE external_requests (
    request_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    status TEXT NOT NULL DEFAULT 'pending'
);
~~~

`gen_random_uuid()` is built into modern PostgreSQL; availability depends on version and installation environment, while older versions may require an appropriate extension.

### 7.1. UUID Default Differs from Identity

- UUIDs are produced by a UUID generation function.
- Identity is managed by PostgreSQL via a sequence, typically on an integer type.
- UUIDs do not guarantee sequential ordering like a counter.
- Identity does not automatically guarantee uniqueness without an appropriate constraint.
- Both require considering `PRIMARY KEY` or `UNIQUE`.

### 7.2. Why Not Generate IDs with "SELECT MAX(id)+1"?

~~~sql
-- Do not use as a concurrent ID allocation mechanism:
-- SELECT COALESCE(MAX(order_id), 0) + 1 FROM orders;
~~~

Two transactions can observe the same `MAX(id)` and pick the same ID. Identity/sequences are designed to allocate numbers safely under concurrency, though a primary key is still required to enforce uniqueness.

## 8. Default Values with ALTER TABLE

You can change a default without redefining the table:

~~~sql
CREATE TABLE shipping_jobs (
    job_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    priority INTEGER NOT NULL DEFAULT 1,
    status TEXT NOT NULL DEFAULT 'waiting'
);
~~~

Change the default priority:

~~~sql
ALTER TABLE shipping_jobs
ALTER COLUMN priority SET DEFAULT 3;
~~~

Drop the default:

~~~sql
ALTER TABLE shipping_jobs
ALTER COLUMN priority DROP DEFAULT;
~~~

### 8.1. SET DEFAULT Usually Affects Future Writes Only

Changing the default from 1 to 3 **does not automatically update existing rows that currently have priority=1**.

If you want to modify existing data, run a separate `UPDATE` with a clear condition:

~~~sql
UPDATE shipping_jobs
SET priority = 3
WHERE priority = 1;
~~~

This command is only an example; in a real system, you must distinguish rows whose value of 1 came from the old default from rows where a user intentionally chose 1. Without tracking the value's origin, you **cannot automatically tell** whether every 1 should be replaced.

### 8.2. Adding a Column with a DEFAULT to a Large Table

~~~sql
ALTER TABLE shipping_jobs
ADD COLUMN retry_count INTEGER NOT NULL DEFAULT 0;
~~~

Modern PostgreSQL versions optimize away full table rewrites for many non-volatile defaults, but not every default expression or `ALTER TABLE` operation has the same cost. For large tables, check server version, locks, storage impact, and migration planning.

### 8.3. Adding a Default Is Not Adding a Constraint

~~~sql
ALTER TABLE shipping_jobs
ALTER COLUMN status SET DEFAULT 'waiting';
~~~

This only specifies the default status. It **does not forbid** `'invalid'` unless a matching `CHECK` or FK constraint exists.

~~~sql
ALTER TABLE shipping_jobs
ADD CONSTRAINT chk_shipping_status
CHECK (status IN ('waiting', 'running', 'done', 'failed'));
~~~

Enforcing the valid status set is the job of constraints, not `DEFAULT`.

## 9. What Is an Identity Column?

An **identity** column uses a sequence bound to the column to generate identifier numbers through PostgreSQL's built-in mechanism.

~~~sql
CREATE TABLE departments_identity (
    department_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    department_name TEXT NOT NULL
);
~~~

When inserting a row:

~~~sql
INSERT INTO departments_identity (department_name)
VALUES ('Engineering')
RETURNING department_id, department_name;
~~~

PostgreSQL draws a number from the sequence to populate `department_id`. The application does not need to pick an ID manually.

### 9.1. Why Does Identity Usually Accompany PRIMARY KEY?

Identity generates numbers, but it **does not automatically replace a `PRIMARY KEY` or `UNIQUE` constraint**. The "no duplicate IDs" rule must still be enforced by the appropriate constraint.

Common pattern:

~~~sql
id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY
~~~

In this pattern:

- Identity supplies the value.
- `PRIMARY KEY` guarantees non-NULL and table-wide uniqueness.
- Application permissions and transactions manage the record lifecycle.

### 9.2. Identity Is Not a "Gapless Consecutive Counter"

Sequence values can be consumed when a transaction fails, when an `INSERT` hits a conflict, or when sequence caching allocates numbers. Thus the ID series can have gaps.

**Never use identity as a count of processed orders**, strict event ordering, or legally required gapless invoice numbers.

## 10. GENERATED ALWAYS AS IDENTITY

Syntax:

~~~sql
CREATE TABLE inventory_categories (
    category_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    category_name TEXT NOT NULL UNIQUE
);
~~~

Normal insertion:

~~~sql
INSERT INTO inventory_categories (category_name)
VALUES ('Books'), ('Office')
RETURNING category_id, category_name;
~~~

The database allocates `category_id`.

### 10.1. ALWAYS Restricts Writers from Supplying an ID

The following is invalid without appropriate override syntax:

~~~sql
-- Deliberately illustrating a rejected operation:
-- INSERT INTO inventory_categories (category_id, category_name)
-- VALUES (500, 'Special');
~~~

`GENERATED ALWAYS` indicates that the ID is normally determined by the database, not the client.

### 10.2. When You Need to Insert a Specific ID: OVERRIDING SYSTEM VALUE

A controlled migration or import may need to preserve legacy IDs:

~~~sql
INSERT INTO inventory_categories (
    category_id,
    category_name
)
OVERRIDING SYSTEM VALUE
VALUES (500, 'Imported category')
RETURNING category_id;
~~~

`OVERRIDING SYSTEM VALUE` allows supplying an explicit ID to an `ALWAYS` identity column in an `INSERT`.

**Do not use overrides as the application's default write path.** They are suited for intentional operations where key collisions, sequence state, auditing, and permissions are verified.

### 10.3. ALWAYS Does Not Mean the Value Can Never Change

Identity `ALWAYS` primarily governs value generation on `INSERT` and write rules for the identity column. It is **not** a mechanism that prevents all data edits or replaces access control. ID mutability rules, FK reference responsibilities, and role permissions must still be designed separately.

## 11. GENERATED BY DEFAULT AS IDENTITY

An identity column in `BY DEFAULT` mode is more flexible:

~~~sql
CREATE TABLE external_categories (
    category_id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    category_name TEXT NOT NULL UNIQUE
);
~~~

Without supplying an ID:

~~~sql
INSERT INTO external_categories (category_name)
VALUES ('Standard')
RETURNING category_id;
~~~

The database allocates the ID.

You can supply an explicit ID:

~~~sql
INSERT INTO external_categories (
    category_id,
    category_name
)
VALUES (900, 'Imported')
RETURNING category_id;
~~~

PostgreSQL accepts 900 if constraints are satisfied.

### 11.1. BY DEFAULT Still Does Not Automatically Track Manually Used IDs

After inserting `category_id=900` directly, the identity sequence **does not automatically jump to 901** just because that row exists.

If later auto-generation reaches an already-inserted number, the primary key detects a duplicate and the `INSERT` fails. When importing IDs, plan to synchronize the sequence with the current dataset.

### 11.2. Choosing ALWAYS or BY DEFAULT?

| Scenario | Typical Choice |
|---|---|
| Application creates all new records, ID managed by DB | `ALWAYS` |
| Data imports regularly need to preserve explicit IDs | `BY DEFAULT` or `ALWAYS` + controlled override |
| One-time migration from a legacy system | `ALWAYS` + `OVERRIDING SYSTEM VALUE` may fit well |
| Want to prevent clients from arbitrarily picking IDs | `ALWAYS` with proper permissions/write paths |

Neither mode replaces security design: if an application has elevated privileges or builds raw SQL from unvalidated client input, fix the privileges and boundaries.

## 12. OVERRIDING USER VALUE

`OVERRIDING USER VALUE` tells PostgreSQL to **ignore the identity value supplied by the writer** and use a sequence-generated value instead.

Example with `BY DEFAULT`:

~~~sql
INSERT INTO external_categories (
    category_id,
    category_name
)
OVERRIDING USER VALUE
VALUES (9999, 'New generated category')
RETURNING category_id;
~~~

The value 9999 in `VALUES` is ignored for the identity column; `category_id` is allocated from the sequence.

### 12.1. Common Use Case: Copying Data While Generating New IDs

Suppose a table has normal columns like name, address, status, and an identity column. When copying a row into a new record, you should not reuse the old identity if both rows coexist.

This override clause lets you keep the `SELECT`/`INSERT` column structure while asking the database to generate new IDs, instead of rewriting the entire import query.

### 12.2. Do Not Confuse the Two OVERRIDING Clauses

| Syntax | Effect |
|---|---|
| `OVERRIDING SYSTEM VALUE` | Allows an explicit ID value instead of ALWAYS mode |
| `OVERRIDING USER VALUE` | Ignores the explicit ID value and uses the sequence |

The two clauses have **opposite** meanings. One preserves IDs from source data; the other forces newly generated IDs.

## 13. The Sequence Behind Identity

Identity relies on a **sequence object** in PostgreSQL. A sequence supplies numbers according to settings such as start value, increment, min/max, cycle, and cache.

~~~sql
CREATE TABLE ticket_numbers (
    ticket_id BIGINT GENERATED ALWAYS AS IDENTITY (
        START WITH 1000
        INCREMENT BY 1
    ) PRIMARY KEY,
    title TEXT NOT NULL
);
~~~

Insert rows:

~~~sql
INSERT INTO ticket_numbers (title)
VALUES ('First'), ('Second')
RETURNING ticket_id, title;
~~~

In a fresh lab with no prior writes, the first values will typically be 1000 and 1001.

### 13.1. Sequences Can Have Other Options

Options such as `START WITH`, `INCREMENT BY`, `MINVALUE`, `MAXVALUE`, `CACHE`, and `CYCLE` are available depending on the definition.

Do not configure `CYCLE` on a primary key ID without understanding the risk of number wraparound collisions and uniqueness interactions.

### 13.2. Sequences Do Not Roll Back Allocated Numbers

Model:

~~~text
Transaction A:
    nextval -> 1000
    INSERT fails with error
    ROLLBACK

Transaction B:
    nextval -> 1001
    INSERT succeeds
~~~

ID 1000 is left unused as a gap. This is normal.

### 13.3. Sequences Do Not Guarantee COMMIT Order

Transaction A may obtain ID 1000 first but commit after Transaction B obtains ID 1001. Therefore, **a smaller ID does not prove a transaction finished earlier**.

If you must determine event order, design appropriate data and semantics; for timestamps, also distinguish transaction time vs. commit time.

### 13.4. A Sequence Is Not a Row Counter

When rows are deleted, the sequence does not decrement. When transactions roll back, numbers may have been consumed. After manual imports, the table may hold IDs unrelated to sequence order.

To count rows:

~~~sql
SELECT COUNT(*) FROM ticket_numbers;
~~~

Do not use `MAX(ticket_id)` or the sequence value as the actual count of stored tickets.

## 14. INSERT RETURNING: How to Get the Generated ID

A common application bug pattern is:

1. INSERT a record.
2. Read the "last ID" from a shared source.
3. Use that ID to create child records.

The reliable and clean way in PostgreSQL is **`RETURNING`**:

~~~sql
INSERT INTO ticket_numbers (title)
VALUES ('Issue from app')
RETURNING ticket_id;
~~~

### 14.1. RETURNING Returns Actual Values After INSERT

On a table with DEFAULT/identity/generated columns:

~~~sql
INSERT INTO ticket_numbers (title)
VALUES ('Another issue')
RETURNING *;
~~~

The client sees the actually assigned ID without guessing from the sequence or depending on other transactions.

### 14.2. RETURNING in JDBC

~~~java
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.ResultSet;

String sql = """
    INSERT INTO ticket_numbers (title)
    VALUES (?)
    RETURNING ticket_id
    """;

try (PreparedStatement ps = connection.prepareStatement(sql)) {
    ps.setString(1, "Issue from Java");

    try (ResultSet rs = ps.executeQuery()) {
        if (rs.next()) {
            long ticketId = rs.getLong("ticket_id");
            // Use ticketId for subsequent operations.
        }
    }
}
~~~

This is a Java/JDBC example; it assumes `connection` is a valid PostgreSQL connection. In real code, manage transactions and rollbacks appropriately.

### 14.3. Never Use SELECT MAX(id) to Find the Just-Inserted ID

~~~sql
-- Do not infer the ID of the current INSERT:
-- SELECT MAX(ticket_id) FROM ticket_numbers;
~~~

The row with the maximum ID could come from another transaction or an import. Use `RETURNING` on the specific `INSERT` statement.

## 15. currval(), lastval(), and nextval()

PostgreSQL provides sequence functions:

- `nextval(sequence)`: allocates the next value.
- `currval(sequence)`: reads the value most recently allocated by `nextval` **for that sequence in the current session**.
- `lastval()`: reads the most recently allocated value in the current session from any sequence.

### 15.1. currval Is Not "The Last ID Across the Entire Database"

If the current session has not called `nextval` on that sequence yet, `currval` raises an error. It does not query the row with the largest ID.

### 15.2. lastval Can Be Misleading When Multiple Sequences Are Used

An operation with triggers or secondary inserts can consume another sequence. In that case, `lastval()` is not necessarily the ID of the table you care about.

### 15.3. Prefer RETURNING

Whenever possible:

~~~sql
INSERT INTO ticket_numbers (title)
VALUES ('New ticket')
RETURNING ticket_id;
~~~

`RETURNING` makes clear which statement the returned ID belongs to and can return multiple columns after defaults/generated expressions.

## 16. SERIAL and IDENTITY: How Do They Differ?

Before SQL-standard identity columns existed, PostgreSQL commonly used `SERIAL`, `BIGSERIAL`, and `SMALLSERIAL`.

Legacy example:

~~~sql
CREATE TABLE legacy_serial_tickets (
    ticket_id BIGSERIAL PRIMARY KEY,
    title TEXT NOT NULL
);
~~~

`SERIAL` is a **shorthand declaration convenience**, not a standalone numeric data type with full semantics as the name might suggest. It creates an integer column, an associated sequence, and a default calling `nextval` accordingly.

### 16.1. Comparison

| Feature | SERIAL/BIGSERIAL | GENERATED AS IDENTITY |
|---|---|---|
| Allocates numbers via sequence | Yes | Yes |
| Declaration syntax | Pseudo-type | SQL-standard column property |
| ALWAYS/BY DEFAULT modes | Not the same mechanism | Yes |
| Default nextval shown as ordinary default | Yes | Dedicated identity metadata |
| Automatically acts as PK | No; requires PRIMARY KEY | No; requires PRIMARY KEY |
| Sequence gaps can occur | Yes | Yes |
| Use in legacy systems | Very common | Preferred for new schemas needing explicit identity management |

### 16.2. When Do You Still Encounter SERIAL?

Many older projects or ORM migrations use `SERIAL`. That is not a reason to replace everything immediately. When designing new tables, identity expresses intent more clearly and provides PostgreSQL-supported management syntax.

### 16.3. Do Not Mix SERIAL and IDENTITY on the Same Column

A column should have one clearly designed ID-allocation mechanism. Do not attach an extra `DEFAULT nextval` to a column that already has an identity property unless performing a specific migration with full awareness of syntax constraints.

## 17. Adjusting Sequences When Importing Data with IDs

Suppose a `BY DEFAULT` identity table receives a batch of legacy IDs from another system. The auto-allocation sequence may still sit below the highest imported ID.

### 17.1. Getting a Column's Sequence Name

PostgreSQL supports:

~~~sql
SELECT pg_get_serial_sequence(
    'public.external_categories',
    'category_id'
);
~~~

This example assumes the table is in the `public` schema. If the object is in another schema, qualify the name properly. The function identifies the sequence bound to a serial/identity column via metadata.

### 17.2. Syncing a Sequence with setval When Writers Are Controlled

A common pattern in migrations once the table is confirmed non-empty:

~~~sql
SELECT setval(
    pg_get_serial_sequence(
        'public.external_categories',
        'category_id'
    ),
    (SELECT MAX(category_id) FROM public.external_categories),
    TRUE
);
~~~

With `is_called = TRUE`, the next `nextval` advances by the configured increment past the set value. This pattern assumes a standard step-1 ascending sequence and a non-NULL `MAX`.

**Do not copy-paste and run this blindly on a system with concurrent writers.** If an `INSERT` happens between computing `MAX` and calling `setval`, the sequence could rewind to an already-issued number or cause conflicts. Migrations must control write paths/locks and verify actual sequence state.

### 17.3. Empty Tables, Negative INCREMENT, and Other Sequence Configurations

The `MAX(id)` pattern does not fit every case automatically:

- Empty table → `MAX` is `NULL`.
- Descending sequence with negative increment → "next value" logic differs.
- Sequence with `MIN`/`MAX`/`CYCLE`.
- Table containing very large manually inserted IDs.
- Sequence that already issued numbers not yet committed.

Write a `setval`/restart procedure tailored to the **specific configuration**, rather than treating a `MAX` expression as a universal formula.

### 17.4. Legal IDs and Gapless Sequence Numbers

If invoice numbers are legally required to have no gaps, do not rely on an ordinary sequence as proof of gaplessness. Use a dedicated numbering mechanism with appropriate legal rules, transactions, and auditing.

## 18. Modifying Identity with ALTER TABLE

On an existing integer column that meets the requirements:

~~~sql
CREATE TABLE imported_users (
    user_id BIGINT PRIMARY KEY,
    display_name TEXT NOT NULL
);
~~~

You can consider adding the identity property in a migration:

~~~sql
ALTER TABLE imported_users
ALTER COLUMN user_id
ADD GENERATED BY DEFAULT AS IDENTITY;
~~~

However, adding identity **does not automatically align the sequence with existing IDs**. If legacy data contains `user_id` 1..10000, the new sequence may start at a low number and cause collisions later.

### 18.1. Switching BY DEFAULT to ALWAYS

~~~sql
ALTER TABLE imported_users
ALTER COLUMN user_id
SET GENERATED ALWAYS;
~~~

And the reverse:

~~~sql
ALTER TABLE imported_users
ALTER COLUMN user_id
SET GENERATED BY DEFAULT;
~~~

These commands only apply when the column is already an identity column and the migration is properly planned.

### 18.2. Restarting an Identity Sequence

~~~sql
ALTER TABLE imported_users
ALTER COLUMN user_id
RESTART WITH 20000;
~~~

This illustrates changing the starting point for future allocated values. Only run this after analyzing existing data, sequence ordering, and concurrent writers.

### 18.3. Dropping Identity

~~~sql
ALTER TABLE imported_users
ALTER COLUMN user_id
DROP IDENTITY;
~~~

Dropping the identity property does not delete data in the column. However, subsequent `INSERT`s that omit the ID will be rejected if the column remains `NOT NULL` without a new default.

### 18.4. Migrations Must Account for Dependencies

Before altering identity:

- Check foreign keys and referencing tables.
- Check whether application code inserts explicit IDs.
- Check ETL/replication/imports.
- Check sequence state and privileges.
- Prepare a rollback plan and test on representative data.

## 19. Generated Columns: Columns Computed from Other Columns

In PostgreSQL, a **generated column** is typically used for a value computed from an expression over the same row.

Example:

~~~sql
CREATE TABLE sales_line_calculation (
    line_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    quantity INTEGER NOT NULL CHECK (quantity > 0),
    unit_price NUMERIC(12, 2) NOT NULL CHECK (unit_price >= 0),
    line_total NUMERIC(14, 2)
        GENERATED ALWAYS AS (quantity * unit_price) STORED
);
~~~

On `INSERT`:

~~~sql
INSERT INTO sales_line_calculation (
    quantity,
    unit_price
)
VALUES (3, 125000.00)
RETURNING line_id, quantity, unit_price, line_total;
~~~

Result: `line_total = 375000.00`.

### 19.1. Generated Columns Differ from DEFAULT

`DEFAULT` provides an initial value when the column is omitted. A generated column is **a function of data in the same row** defined by an expression.

| Question | DEFAULT | Generated Column |
|---|---|---|
| Can it directly depend on other columns in the same row? | No | Yes, within expression limits |
| Automatically recalculated on UPDATE of source columns? | No | Yes |
| Can it be overridden with a manual value? | Yes, if constraints permit | Cannot write arbitrary values |
| Can it use volatile time functions? | Yes, when valid as a default expression | No, expression must satisfy immutability rules |
| Can it compute `quantity * unit_price` total? | Not as a column-dependent default | Yes |

### 19.2. Recalculation When Source Columns Change

~~~sql
UPDATE sales_line_calculation
SET quantity = 4
WHERE line_id = 1
RETURNING quantity, unit_price, line_total;
~~~

If row `line_id=1` was created by the first `INSERT` in the test table, `line_total` becomes `4 * 125000 = 500000`.

The service does not need to send a new `line_total` value. This reduces the risk of a service forgetting to update the total when `quantity` changes.

### 19.3. Cannot Directly Assign Arbitrary Values to a Generated Column

~~~sql
-- Expected to be rejected by PostgreSQL:
-- INSERT INTO sales_line_calculation
--     (quantity, unit_price, line_total)
-- VALUES (3, 125000, 1);
~~~

PostgreSQL manages `line_total` according to its expression. If a total must be manually adjustable for discounts, taxes, or special rules, choose a different column design rather than forcing a generated column to accept arbitrary numbers.

## 20. STORED and VIRTUAL: Differences Across PostgreSQL Versions

The examples in this lesson use:

~~~sql
GENERATED ALWAYS AS (expression) STORED
~~~

This is the standard form compatible with PostgreSQL versions that support stored generated columns.

### 20.1. STORED

A **stored generated column** is evaluated when a row is `INSERT`ed or `UPDATE`d, and **its value is stored on disk** like an ordinary column.

Advantages:

- Read queries can retrieve the precomputed value directly.
- Helpful when the expression is read frequently.
- Supports creating appropriate indexes on the stored generated column.

Trade-offs:

- Consumes disk storage for the values.
- Incurs computation cost on inserts and updates.
- Migrations adding or changing the expression can be expensive on large tables.

### 20.2. VIRTUAL

Newer PostgreSQL versions add support for **virtual generated columns**: the value is computed on read rather than stored on disk. PostgreSQL 18 supports this column type; older versions without it only offer `STORED` for generated columns.

Syntax example only for supported versions:

~~~sql
-- PostgreSQL 18+:
CREATE TABLE generated_virtual_demo (
    quantity INTEGER NOT NULL,
    unit_price NUMERIC(12, 2) NOT NULL,
    line_total NUMERIC
        GENERATED ALWAYS AS (quantity * unit_price) VIRTUAL
);
~~~

Note: `VIRTUAL` has specific restrictions on expressions/functions and capabilities; consult the documentation for the exact **server version you are running** before deploying.

### 20.3. Choosing STORED or VIRTUAL?

| Criterion | STORED | VIRTUAL |
|---|---|---|
| Primary evaluation timing | On row write/update | On value read |
| Storage cost for result column | Yes | Does not store values like stored |
| Compute load | Write-heavy | Read-heavy |
| Version support | Broader | Requires a newer supported version |
| Examples in this lab | Uses STORED | Optional alternative only |

Do not assume virtual is always better for saving space, nor assume stored is always faster for precomputing. Measure your workload and verify version constraints.

## 21. Expression Restrictions for Generated Columns

Generated columns are not meant for arbitrary logic. PostgreSQL enforces restrictions so values can be computed deterministically from the row.

### 21.1. Expressions Must Satisfy Immutability

Valid example:

~~~sql
line_total NUMERIC
    GENERATED ALWAYS AS (quantity * unit_price) STORED
~~~

Invalid example:

~~~sql
-- Volatile time functions are not allowed like this:
-- calculated_at TIMESTAMPTZ
--     GENERATED ALWAYS AS (now()) STORED
~~~

`now()` is not immutable with respect to the row's inputs. Generated expressions require functions that satisfy PostgreSQL's immutability rules.

### 21.2. Cannot Query Other Tables from a Generated Expression

A flawed idea:

~~~sql
-- Not valid as a generated expression:
-- total_value GENERATED ALWAYS AS (
--     SELECT SUM(...) FROM order_items
-- ) STORED
~~~

A generated column can only reference eligible data in the same row per expression limits; it cannot replace multi-row aggregates or queries to other tables.

### 21.3. Cannot Reference Another Generated Column

In PostgreSQL, one generated column cannot directly depend on another generated column to form a chain of computed dependencies in the declaration. If multi-step calculation is needed, repeat/combine the expression on the base columns or consider another design.

### 21.4. Cannot Mix DEFAULT and GENERATED on the Same Column

A column with a generated expression cannot simultaneously have a user-overridable default value in the usual way. When a value must be computed from other columns, specify a generated expression; when you want a flexible initial value, use a default.

### 21.5. User-Defined Functions Require Strict Evaluation

A PostgreSQL function marked `IMMUTABLE` must genuinely return the same result for the same inputs under all required conditions. Never falsely mark a function that reads other tables or depends on time as `IMMUTABLE` just to bypass generated expression checks; doing so can corrupt data consistency.

## 22. Generated Columns and NULL

Suppose:

~~~sql
CREATE TABLE totals_nullable (
    quantity INTEGER,
    unit_price NUMERIC(12, 2),
    total NUMERIC(14, 2)
        GENERATED ALWAYS AS (quantity * unit_price) STORED
);
~~~

If `quantity` or `unit_price` is `NULL`, multiplication evaluates to `NULL`.

~~~sql
INSERT INTO totals_nullable (quantity, unit_price)
VALUES (NULL, 100000)
RETURNING quantity, unit_price, total;
~~~

The resulting `total` is `NULL`, not 0.

### 22.1. To Forbid NULL

~~~sql
CREATE TABLE totals_required (
    quantity INTEGER NOT NULL CHECK (quantity > 0),
    unit_price NUMERIC(12, 2) NOT NULL CHECK (unit_price >= 0),
    total NUMERIC(14, 2)
        GENERATED ALWAYS AS (quantity * unit_price) STORED
);
~~~

Here both source values are required and validated by constraints.

### 22.2. COALESCE Changes Semantics

~~~sql
-- Example idea treating NULL as 0, only if business rules require it:
-- GENERATED ALWAYS AS (COALESCE(quantity,0) * unit_price) STORED
~~~

If `NULL` quantity means "unknown," turning it into 0 hides missing data. Do not apply `COALESCE` solely to avoid `NULL` without understanding business meaning.

### 22.3. CHECK Constraints on Generated Columns

You can attach appropriate constraints to the computed result:

~~~sql
CREATE TABLE computed_limits (
    quantity INTEGER NOT NULL,
    unit_price NUMERIC(12,2) NOT NULL,
    total NUMERIC(14,2)
        GENERATED ALWAYS AS (quantity * unit_price) STORED,
    CONSTRAINT chk_total_nonnegative
        CHECK (total >= 0)
);
~~~

However, if you already require positive `quantity` and non-negative `unit_price`, guarding logic directly on the source columns is clearer. Additional checks on `total` should have a concrete reason.

## 23. Generated Columns Can Help Create Normalized Keys

Another use case beyond arithmetic is normalizing fields for lookup.

~~~sql
CREATE TABLE customer_emails_generated (
    customer_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email_raw TEXT NOT NULL,
    email_key TEXT
        GENERATED ALWAYS AS (lower(btrim(email_raw))) STORED,
    CONSTRAINT chk_email_nonblank
        CHECK (btrim(email_raw) <> ''),
    CONSTRAINT uq_email_key
        UNIQUE (email_key)
);
~~~

When inserting:

~~~sql
INSERT INTO customer_emails_generated (email_raw)
VALUES ('  Alice@Example.COM  ')
RETURNING customer_id, email_raw, email_key;
~~~

The comparison key becomes `alice@example.com` according to the chosen rule.

### 23.1. Uniqueness on the Comparison Key

If `'alice@example.com'` is inserted again, `UNIQUE(email_key)` rejects it because the normalization expression yields the same key.

### 23.2. Do Not Confuse a Normalized Key with Email Validation

`lower(btrim(email_raw))` only performs simple string transformation. It does not prove that the email exists, that the owner is verified, or that the canonicalization rule suits every mail provider.

Additionally, case conversion can depend on collation/locale. Define the canonicalization policy before using it as a unique key.

### 23.3. When to Use an Expression Index Instead of a Generated Column?

You can create an index directly on:

~~~sql
CREATE UNIQUE INDEX uq_customer_emails_expr
ON some_customer_table (lower(btrim(email_raw)));
~~~

The example above assumes the source table exists. If you only need comparison/indexing without exposing `email_key` as a separate column, an expression index can be simpler.

Generated columns are useful when you want to expose the computation explicitly as a column to queries or applications, with the corresponding storage/compute trade-offs.

## 24. Generated Columns Can Be Used in Queries and RETURNING

~~~sql
SELECT
    line_id,
    quantity,
    unit_price,
    line_total
FROM sales_line_calculation
ORDER BY line_id;
~~~

If `sales_line_calculation` was created and populated, PostgreSQL returns `line_total` just like any other column.

### 24.1. ORDER BY Computed Results

~~~sql
SELECT
    line_id,
    line_total
FROM sales_line_calculation
ORDER BY line_total DESC;
~~~

### 24.2. Indexing STORED Columns

~~~sql
CREATE INDEX idx_sales_line_total
ON sales_line_calculation (line_total);
~~~

With stored generated columns, an index on the computed result can help filter or sort queries depending on the workload.

### 24.3. Do Not Treat a Computed Column as an Immutable Copy of Source Data

A `STORED` generated value updates whenever the source row is rewritten per PostgreSQL's calculation rules. It reflects the current values in the row, **not a historical snapshot** if prices or quantities are later edited.

For issued invoices, you may need to store a fixed historical sale price and lock edits via workflow. A generated column does not automatically satisfy accounting/audit requirements on its own.

## 25. Comprehensive Lab: Schema for Products and Orders

This practice lab is designed for a **test PostgreSQL database** where you have `CREATE SCHEMA` privileges. Do not run on production. If the `generated_lab` schema already exists, choose another database or schema name to avoid conflicts; never drop real data.

### 25.1. Create Schema

~~~sql
CREATE SCHEMA generated_lab;
~~~

### 25.2. Products Table with Identity and Defaults

~~~sql
CREATE TABLE generated_lab.products (
    product_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    sku TEXT NOT NULL UNIQUE,
    product_name TEXT NOT NULL,
    price NUMERIC(12, 2) NOT NULL
        CHECK (price >= 0),
    stock INTEGER NOT NULL DEFAULT 0
        CHECK (stock >= 0),

Breakdown:

| Column | Mechanism |
|---|---|
| `product_id` | Identity ALWAYS, PK |

INSERT INTO generated_lab.products (

PostgreSQL assigns `product_id`, `stock = 0`, `is_active = TRUE`, and the timestamps.

INSERT INTO generated_lab.products (

    DEFAULT,
    DEFAULT
)
RETURNING product_id, stock, is_active;
~~~

### 25.5. Sending Explicit NULL to a NOT NULL Column

~~~sql
-- Expected to be rejected by PostgreSQL:
-- INSERT INTO generated_lab.products (

~~~

`DEFAULT 0` **does not replace** an explicit `NULL`. The result is a `NOT NULL` violation.

## 26. Lab: Orders Table and Generated STORED Line Items

### 26.1. Orders Table

~~~sql
CREATE TABLE generated_lab.orders (
    order_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_code TEXT NOT NULL,
    status TEXT NOT NULL DEFAULT 'draft'
        CHECK (status IN (
            'draft', 'submitted', 'paid', 'cancelled'
        )),
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
~~~

### 26.2. Order Items Table

~~~sql
CREATE TABLE generated_lab.order_items (
    order_item_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL
        REFERENCES generated_lab.orders(order_id),
    product_id BIGINT NOT NULL
        REFERENCES generated_lab.products(product_id),
    quantity INTEGER NOT NULL DEFAULT 1
        CHECK (quantity > 0),
    unit_price NUMERIC(12, 2) NOT NULL
        CHECK (unit_price >= 0),
    line_total NUMERIC(14, 2)
        GENERATED ALWAYS AS (quantity * unit_price) STORED,
    CONSTRAINT uq_order_product
        UNIQUE (order_id, product_id)
);
~~~

**The unit price on each order line** is stored separately rather than querying the current price in `products` for historical totals. If the product price changes after the order is placed, `line_total` for existing orders still uses the `unit_price` snapshot in `order_items`.

### 26.3. Create an Order and Retrieve ID via RETURNING

~~~sql
INSERT INTO generated_lab.orders (customer_code)
VALUES ('CUST-001')
RETURNING order_id, status, created_at;
~~~

In a fresh lab environment, the first `order_id` might be 1, but never build workflows assuming that.

### 26.4. Create an Order and Item in One Statement Using a CTE

~~~sql
WITH new_order AS (
    INSERT INTO generated_lab.orders (customer_code)
    VALUES ('CUST-002')
    RETURNING order_id
)
INSERT INTO generated_lab.order_items (
    order_id,
    product_id,
    quantity,
    unit_price
)
SELECT
    o.order_id,
    p.product_id,
    2,
    p.price
FROM new_order AS o
JOIN generated_lab.products AS p
    ON p.sku = 'BOOK-001'
RETURNING
    order_item_id,
    order_id,
    quantity,
    unit_price,
    line_total;
~~~

In the lab tables, this statement creates one order and one line item, returning the identity ID along with the auto-computed line total.

### 26.5. Testing Default Quantity by Omitting the Column

With `INSERT ... SELECT`, the clean way to use `DEFAULT` is to **omit the `quantity` column from the `INSERT` list** and omit an expression for it from `SELECT`. For example, using the order for `CUST-002` just created:

~~~sql
INSERT INTO generated_lab.order_items (
    order_id, product_id, unit_price
)
SELECT
    o.order_id,
    p.product_id,
    p.price
FROM generated_lab.orders AS o
JOIN generated_lab.products AS p
    ON p.sku = 'BOOK-002'
WHERE o.customer_code = 'CUST-002'
RETURNING quantity, unit_price, line_total;
~~~

The resulting `quantity` takes the default 1. Unlike `VALUES(DEFAULT, ...)`, the `DEFAULT` keyword cannot be placed as an expression inside a `SELECT` list. Distinguishing **`VALUES(... DEFAULT ...)`** from **`INSERT ... SELECT`** is an important detail when writing row-creation SQL.

### 26.6. Recalculating line_total When Updating quantity

~~~sql
UPDATE generated_lab.order_items
SET quantity = 3
WHERE order_id IN (
    SELECT order_id
    FROM generated_lab.orders
    WHERE customer_code = 'CUST-002'
)
AND product_id IN (
    SELECT product_id
    FROM generated_lab.products
    WHERE sku = 'BOOK-001'
)
RETURNING
    order_item_id,
    quantity,
    unit_price,
    line_total;
~~~

`line_total` is recalculated from the new `quantity`.

### 26.7. Order Total Is a Multi-Row Aggregate

If you want the total amount for an order:

~~~sql
SELECT
    order_id,
    SUM(line_total) AS order_total
FROM generated_lab.order_items
GROUP BY order_id
ORDER BY order_id;
~~~

Do not try to put `SUM(line_total)` across multiple rows into a generated column on `orders`: generated expressions are limited to a single row and cannot reference other rows.

If you must store `orders.total_amount` for audit or performance reasons, choose an appropriate transaction protocol, trigger, or derived-data maintenance mechanism with proper concurrency control.

## 27. Lab: UPDATE SET column = DEFAULT

PostgreSQL allows requesting the default during an `UPDATE` on an ordinary column.

Example resetting `stock` to its declared default:

~~~sql
UPDATE generated_lab.products
SET stock = DEFAULT
WHERE sku = 'BOOK-003'
RETURNING sku, stock;
~~~

If the default for `stock` is 0, the value is set to 0.

### 27.1. DEFAULT in UPDATE Can Overwrite Existing Data

`SET stock = DEFAULT` does not mean "keep stock as it currently is." It **writes the default value** into the row via `UPDATE`. Use with caution.

### 27.2. Resetting Status with DEFAULT

~~~sql
UPDATE generated_lab.orders
SET status = DEFAULT
WHERE customer_code = 'CUST-002'
RETURNING order_id, status;
~~~

If the default is `'draft'`, this resets matching orders to draft. However, if an order was already paid, that could violate business workflow even though the constraint permits it.

**DEFAULT does not replace business state-transition validation.**

### 27.3. Generated Columns Are Not Fields to Reset Arbitrarily

A generated column derives its value from an expression and cannot be updated to an arbitrary value like `line_total = 1`. If the value must change, update the source columns or change the data design.

## 28. Lab: INSERT ... ON CONFLICT and Auto-Generated Values

PostgreSQL supports upserts via `INSERT ... ON CONFLICT`.

~~~sql
INSERT INTO generated_lab.products (
    sku, product_name, price
)
VALUES ('BOOK-001', 'PostgreSQL Fundamentals', 155000.00)
ON CONFLICT (sku) DO UPDATE
SET
    product_name = EXCLUDED.product_name,
    price = EXCLUDED.price,
    updated_at = CURRENT_TIMESTAMP
RETURNING product_id, sku, price, updated_at;
~~~

### 28.1. DEFAULT Is Used in the INSERT Branch

If the SKU does not exist yet, columns like `stock`, `is_active`, and timestamps with defaults are populated according to `INSERT` rules.

### 28.2. The UPDATE Branch Does Not Automatically Re-Apply All Defaults

If the SKU already exists, the `DO UPDATE` branch performs only the listed assignments. In the example, `updated_at` is **explicitly assigned** because its `DEFAULT` does not automatically re-run on updates.

### 28.3. Sequences Can Advance Even When a Conflict Occurs

Sequence allocation for the candidate `INSERT` row can happen before PostgreSQL detects the conflict and switches to `DO UPDATE`. Thus an upsert can consume identity numbers even when no new row is created.

Never rely on consecutive identity IDs to infer that "each `INSERT` created exactly one row."

### 28.4. Unique Constraints Protect the SKU

Here `ON CONFLICT (sku)` relies on the SKU's unique constraint/index. Identity is not directly involved in detecting an existing product with the same SKU.

## 29. Identity and COPY/Import

PostgreSQL provides `COPY FROM` for bulk loading. When importing data with explicit identity columns, exercise extra care: `COPY FROM` behavior for provided identity values **differs from `INSERT ALWAYS` defaults** in key ways; `COPY` can write input ID values regardless of identity mode.

### 29.1. Two Import Strategies

**Strategy A: Preserve Legacy IDs**

- Only do this when references from the source system must remain intact.
- Ensure no primary key collisions.
- Synchronize the sequence in a controlled manner after import.
- Verify foreign keys across imported tables.

**Strategy B: Issue New IDs**

- Let the database issue new identities.
- Keep a mapping table from `old_id` → `new_id`.
- Remap foreign keys using that mapping.
- Never infer relationships from "import sequence order."

### 29.2. Imports Are Not a Free Pass to Bypass Constraints

Even with `COPY`, constraints and transactions still matter. Never disable constraints or safeguards solely for import speed without an integrity and recovery plan.

## 30. Identity, Concurrency, and Gaps

Suppose two concurrent requests insert:

~~~sql
INSERT INTO generated_lab.orders (customer_code)
VALUES ('CUST-A')
RETURNING order_id;
~~~

and:

~~~sql
INSERT INTO generated_lab.orders (customer_code)
VALUES ('CUST-B')
RETURNING order_id;
~~~

The sequence allocates values through its dedicated mechanism, avoiding both requests computing the same `MAX(id)+1`.

### 30.1. ID Numbers Do Not Necessarily Reflect Business Time

One request can obtain a lower number first and commit after a request with a higher number. If an operation fails, a number may also be abandoned.

### 30.2. Why Can't You Assume an ID Is an Invoice Number?

In many accounting workflows, invoice numbers have strict issuance, cancellation, audit, and continuity requirements. Identity sequences can have gaps, so use a dedicated legal numbering mechanism when regulations or processes demand it.

### 30.3. UUIDs Do Not Determine Order Either

Using `gen_random_uuid()` produces good identifiers, but does not inherently express chronological order. Choose an ID type based on requirements: uniqueness, size, distribution, index locality, importability, and API exposure.

## 31. Choosing a Data Type for Identity

Identity is declared on supported integer types, for example:

~~~sql
id SMALLINT GENERATED ALWAYS AS IDENTITY
id INTEGER GENERATED ALWAYS AS IDENTITY
id BIGINT GENERATED ALWAYS AS IDENTITY
~~~

These lines illustrate single-column definitions, not three standalone SQL statements.

### 31.1. SMALLINT, INTEGER, or BIGINT?

| Type | Signed Integer Range (Approx.) | Considerations |
|---|---|---|
| `SMALLINT` | ±32 thousand | Use only when row counts are strictly bounded |
| `INTEGER` | ±2.1 billion | Fits many medium-sized tables |
| `BIGINT` | ±9.22 × 10¹⁸ | Wide headroom for long-lived IDs |

Sequences allocate values within the configured range. High-write, multi-year systems often prefer `BIGINT` for numeric primary keys to minimize range exhaustion risk, based on capacity calculations.

### 31.2. BIGINT Is Not Optimal in Every Case

`BIGINT` takes more space than `INTEGER` in indexes and rows. Choose based on growth projections and resources. For a lookup catalog of a few hundred fixed statuses, `INTEGER` or a natural business key may be more suitable.

### 31.3. Identity Does Not Hide IDs

Sequential numeric IDs can let users guess other resources' IDs. If an API uses `/orders/123`, you must still enforce authorization checks. Using UUIDs does not replace access control either.

## 32. Metadata: How to Know Whether a Column Has a Default, Identity, or Generated Expression

PostgreSQL exposes column metadata in `information_schema.columns`.

~~~sql
SELECT
    table_schema,
    table_name,
    column_name,
    data_type,
    column_default,
    is_identity,
    identity_generation,
    is_generated,
    generation_expression
FROM information_schema.columns
WHERE table_schema = 'generated_lab'
  AND table_name IN ('products', 'orders', 'order_items')
ORDER BY table_name, ordinal_position;
~~~

Useful metadata columns:

- `column_default`: the default expression if declared as a normal default.
- `is_identity`: whether it is an identity column.
- `identity_generation`: `ALWAYS` or `BY DEFAULT` when it is an identity column.
- `is_generated`: information about generated columns per version.
- `generation_expression`: the computation expression when provided by metadata.

### 32.1. Do Not Infer Identity Only from column_default

Identity has its own metadata and does not appear as a `nextval(...)` default like legacy `SERIAL` columns. Use the identity metadata columns to identify it accurately.

### 32.2. Using psql \d

In `psql`, you can run:

~~~text
\d generated_lab.products
\d generated_lab.order_items
~~~

These are `psql` meta-commands, **not standard SQL sent directly over JDBC**.

### 32.3. Inspect Actual Definitions Before Migrations

A schema may have been generated by an ORM across versions. Do not guess whether a column is identity or generated solely from names like `id` or `total`. Read the metadata.

## 33. Constraints Are Still Needed Alongside DEFAULT and Generated Columns

Suppose:

~~~sql
CREATE TABLE stock_defaults (
    product_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    quantity INTEGER DEFAULT 0
);
~~~

This does not prevent:

~~~sql
INSERT INTO stock_defaults (quantity)
VALUES (-100);
~~~

To forbid negatives:

~~~sql
CREATE TABLE stock_safe (
    product_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    quantity INTEGER NOT NULL DEFAULT 0
        CHECK (quantity >= 0)
);
~~~

### 33.1. DEFAULT Expresses Initial Intent; CHECK Protects Valid Ranges

- `DEFAULT 0`: if quantity is omitted, start at 0.
- `NOT NULL`: do not store missing values.
- `CHECK (quantity >= 0)`: do not store negative numbers.
- `PRIMARY KEY`: `product_id` cannot duplicate.

No single mechanism replaces all the others.

### 33.2. Generated Results Must Still Match Business Rules

`line_total = quantity * unit_price` is only valid if the line total is truly defined as that exact product.

If discounts, coupons, taxes, and fees apply:

\[
\text{total} \ne \text{quantity} \times \text{unit\_price}
\]

unless those other components do not apply.

Do not turn a convenient formula into a generated column if real business rules require more complex logic.

## 34. DEFAULT and API Design

A product-creation API might receive:

~~~json
{
  "sku": "BOOK-010",
  "productName": "Data Handbook",
  "price": 75000
}
~~~

If the API contract allows omitting `stock` and `isActive`, the backend can **omit those two columns from the `INSERT`** so PostgreSQL applies `DEFAULT`.

### 34.1. JSON null Differs from an Omitted Field

Two requests:

~~~json
{"sku":"BOOK-010","stock":null}
~~~

and:

~~~json
{"sku":"BOOK-010"}
~~~

can be handled differently by the backend:

- Field `stock` present with `null` → if explicitly bound as `NULL`, the DB does not use the default.
- Field `stock` omitted → SQL can omit the column, and the DB uses the default.

This is an API contract and mapper design decision, not merely a SQL detail.

### 34.2. Do Not Let Clients Supply Arbitrary created_at Values Without Reason

If creation time must reflect a system event, the API should not trust a client-supplied `created_at`, even when the database has a default. Because a default **is not applied when the writer supplies an explicit value**.

You can:

- Omit `created_at` from request DTOs.
- Restrict privileges and write paths.
- Use database triggers/logic when integrity must hold across multiple writers.

### 34.3. Identity Also Needs API Controls

A record-creation request usually should not expose a user-selectable `id` field. Identity `ALWAYS` adds defense at the DB layer, but API authorization and mass-assignment protection must still be designed.

## 35. Timezone Risks When Defaulting Creation Timestamps

~~~sql
created_at TIMESTAMP WITHOUT TIME ZONE DEFAULT now()
~~~

This differs from:

~~~sql
created_at TIMESTAMPTZ DEFAULT now()
~~~

In the first case, the instant from `now()` must be converted to a timezone-less timestamp whose interpretation depends on the session time zone. When storing event instants, `TIMESTAMPTZ` is usually clearer.

### 35.1. CURRENT_DATE Depends on the Session Date

~~~sql
SELECT CURRENT_DATE;
~~~

The session's current date depends on its `TimeZone` setting. A reporting system needing "the business date in Vietnam" must specify the business time zone explicitly instead of assuming the database connection's date always matches the user's location.

### 35.2. A Default Does Not Mean Historical Immutability

`created_at` has a `DEFAULT`, yet it remains a normal column that can be `UPDATE`d if a writer has permission. If business rules require "immutable after creation," enforce appropriate privileges, write paths, or protective mechanisms.

## 36. Migrating Between SERIAL and IDENTITY

A legacy schema might have:

~~~sql
CREATE TABLE legacy_items (
    item_id BIGSERIAL PRIMARY KEY,
    title TEXT NOT NULL
);
~~~

To switch to identity, you cannot simply change the text `BIGSERIAL` to `BIGINT GENERATED ...` in a migration script and expect live objects to transform automatically.

Inspect:

- How the old sequence was created and owned.
- The `nextval(...)` default on the column.
- Privileges granted on the sequence.
- Existing data in the table.
- Whether the ORM expects JDBC generated keys in a specific way.
- History of explicit ID imports.
- Locking and transaction limits during `ALTER TABLE`.

### 36.1. Do Not Drop Old Sequences Without Checking Dependencies

Legacy sequences may be referenced directly by name in code. A migration that drops or renames a sequence without updating the application can cause runtime failures.

### 36.2. Test Application Behavior Before and After Migration

Test:

- `INSERT` omitting `id`.
- `INSERT ... RETURNING id`.
- Batch `INSERT`.
- Upsert.
- `COPY`/import.
- Writer role privileges.
- Sequence state after restore.
- ORM behavior.

This is part of data migration, not merely DDL editing.

## 37. Generated Columns and Large Schema Migrations

Adding a `STORED` generated column on a large table may require evaluating the expression across all existing rows and incur table-rewrite/locking costs depending on the operation and version.

~~~sql
ALTER TABLE existing_order_items
ADD COLUMN line_total NUMERIC(14,2)
    GENERATED ALWAYS AS (quantity * unit_price) STORED;
~~~

This statement is a structural example; run it only if the table and source columns exist. Never run directly in production without evaluation.

### 37.1. Check Existing Data First

If `quantity` or `unit_price` contains `NULL`, the generated result can be `NULL`. If values overflow `numeric(14,2)`, the migration can fail during evaluation.

Evaluate:

- Data types and result bounds.
- `NULL` semantics.
- Precision and rounding.
- Expression immutability.
- Read/write load and related indexes.
- Rollback plan if `ALTER TABLE` fails.

### 37.2. When Business Formulas Change

If totals later need to include discounts, the initial generated formula is no longer sufficient. Evaluate schema/expression changes, stored data types, and historical preservation.

Do not use generated columns for calculations that depend on multi-table state or period-varying tax rules unless modeled appropriately as source columns.

### 37.3. Generated Columns Are Not the Only Way to Avoid Redundancy

If an expression is very simple and rarely read, you can compute it directly in `SELECT`:

~~~sql
SELECT quantity * unit_price AS line_total
FROM generated_lab.order_items;
~~~

Even when the table already has a generated column, this illustrates the alternative. Weigh read vs. write calculation costs, indexing needs, and correctness before adding a generated column.

## 38. Generated Columns vs. Triggers: When to Use Which?

| Scenario | DEFAULT | Generated Column | Trigger/Service |
|---|---|---|---|
| Initial status is draft | Ideal | Unnecessary | Possible, usually overkill |
| `created_at` on row insert | Suitable | Incompatible with `now()` | Possible in special cases |
| `line_total = qty × price` | No, depends on row columns | Ideal | Possible, more complex |
| `updated_at` changes on every UPDATE | Insufficient alone | Incompatible with `now()` | Service or trigger |
| Order total across multiple `order_items` | No | Invalid across rows | Controlled transaction/service/trigger |
| Numeric ID generation | Identity/sequence over manual DEFAULT | No | Rarely needs custom mechanism |
| Writing audit log on status change | No | No | Trigger/service/eventing |
| Price from an external API | No | No | Service or workflow |

### 38.1. A Generated Expression Must Yield the Same Result for the Same Source Columns

If a value requires calling an API, reading another table, or depending on current time, it is not a simple local immutable expression. Use a service/transaction or an appropriately stored stateful data model.

### 38.2. Triggers Are Not Automatically Safer

Triggers can introduce hidden side effects, complicate debugging, and still require careful concurrency design. Do not replace every `DEFAULT` or generated column with triggers just to "centralize logic in the database."

## 39. Concurrent Operations on Computed Totals

Example:

~~~sql
UPDATE generated_lab.order_items
SET quantity = quantity + 1
WHERE order_item_id = 1
RETURNING quantity, line_total;
~~~

If the row exists, PostgreSQL updates `quantity` under its transaction/row-locking rules and recalculates the stored generated `line_total`.

### 39.1. Generated Totals Do Not Prevent Overselling

Even if `line_total` follows the formula accurately, two users can still purchase beyond available stock if the application does not control inventory allocation transactionally.

A safer inventory pattern is:

~~~sql
UPDATE generated_lab.products
SET stock = stock - 2,
    updated_at = clock_timestamp()
WHERE sku = 'BOOK-001'
  AND stock >= 2
RETURNING product_id, stock;
~~~

If 0 rows are returned, stock is insufficient or the SKU does not exist.

### 39.2. Generated Columns Do Not Replace Multi-Table Transactions

When placing an order, creating the order, inserting items, and deducting stock must happen inside an appropriate transaction. A computed total column only guarantees per-row multiplication, not completion of the entire workflow.

### 39.3. Do Not Assign IDs to "Reserve Transaction Order"

Identity serves ID allocation and uniqueness. To enforce business ordering, design an explicit, scalable mechanism; obtaining an ID earlier does not mean committing earlier.

## 40. Common Error Handling

PostgreSQL returns SQLSTATE codes so backends can distinguish errors when using defaults, identity, and generated columns.

| Common SQLSTATE | Situation | Resolution |
|---|---|---|
| `23502` | `NULL` in a `NOT NULL` column | Check input fields or missing `DEFAULT` |
| `23505` | Duplicate `PRIMARY KEY`/`UNIQUE` | Check imported IDs, sequence sync, business keys |
| `23514` | `CHECK` constraint failed | Validate input data/business logic |
| `23503` | `FOREIGN KEY` violation | Verify relationships and write ordering |
| `22003` | Numeric value out of range | ID or total column exceeded type range |
| `428C9` | Generated always column violation | Invalid write to a generated or identity `ALWAYS` column |

Exact error codes should be verified for your operation and PostgreSQL version. Do not map every `23505` to "sequence error"—it could be a duplicate SKU, email, order code, or another unique key.

### 40.1. Never Expose Raw DB Errors to End Users

Database errors can leak table/column names and sensitive values. APIs should translate errors into stable, user-friendly messages without exposing internal schema details.

### 40.2. Do Not Blindly Retry Infinitely on ID Import Conflicts

Inspect whether the import duplicates business keys, where the sequence currently sits, whether concurrent writers exist, and what ID mapping strategy is in place.

### 40.3. When a Computed Total Evaluates to NULL

Check whether source columns contain `NULL`, since multiplying by `NULL` yields `NULL`. Do not automatically apply `COALESCE(..., 0)` if "unknown price" means something different from "zero price."

## Conclusion

PostgreSQL has three mechanisms often grouped together as "auto-generated values," yet they **solve three distinct problems**:

- **`DEFAULT`** fills in an initial status, quantity, or timestamp when an `INSERT` omits a value. It **does not replace an explicit `NULL`**, does not auto-update when the row changes, and does not guarantee valid data without constraints.
- **`GENERATED ALWAYS/BY DEFAULT AS IDENTITY`** uses a sequence to issue numeric IDs. `ALWAYS` restricts explicit ID input on `INSERT`, while `BY DEFAULT` is more flexible. Sequences are safe for concurrent allocation, yet they **can have gaps, do not roll back allocated numbers, and do not guarantee `COMMIT` order**.
- **Generated columns** compute values from expressions over the same row, such as `quantity * unit_price`. With `STORED`, values are computed on write and persisted; newer PostgreSQL versions also support `VIRTUAL`. Expressions must obey restrictions such as immutability and cannot replace multi-row aggregate queries.

In data-modification workflows, prefer `INSERT ... RETURNING` to retrieve real IDs, use `DEFAULT` deliberately rather than passing `NULL` indiscriminately, control `OVERRIDING` and sequences during imports, and separate row-level calculations from multi-table workflows. Constraints, transactions, authorization, and migration planning remain essential even when the database populates values automatically.

Choosing the right mechanism keeps `INSERT` statements concise, reduces synchronization bugs between applications and PostgreSQL, and keeps data meaningful and scalable in production systems.
