# Change-History Auditing Applications and Correctness Verification

In business applications, knowing the **current state** is often not enough. When a credit limit changes, an order moves from `NEW` to `PAID`, or a record is deleted, operators may need to answer: **What was the previous value? What is the new value? Which operation happened? When? Who or what job requested it? Did the operation commit or roll back?**

A common PostgreSQL solution is using a **trigger** to write a history row into an audit table inside the same transaction as the source-table change. The trigger inspects `OLD`, `NEW`, and `TG_OP`, and can store `jsonb` snapshots. This centralizes history tracking instead of relying on every application endpoint to remember to write audit entries itself.

Yet a sound audit trail needs far more than an `INSERT INTO audit_log`: you must define **which events to capture**, **security boundaries**, **accuracy of before/after snapshots**, **transaction semantics**, **operations that can bypass triggers**, **reconciliation against source data**, and **traceability limits**. In particular, a transactional audit trigger is **not** an immutable history ledger immune to superuser tampering and does **not** retain rolled-back transactions.

## 2. The Problem: What Do We Need to Remember?

Suppose an `accounts` table contains:

| account_id | tenant_id | account_code | display_name | credit_limit | status |
|---:|---:|---|---|---:|---|
| 1001 | 10 | AC-001 | An Binh Company | 500000 | ACTIVE |
| 2001 | 20 | AC-002 | Minh Ha Company | 800000 | ACTIVE |

A user raises the credit limit for account 1001 from 500000 to 700000. The source table retains only the **new value**. Without a history mechanism, it is hard to tell what the prior limit was or when it changed.

A desired audit row looks like:

```text
audit_id      = 3
account_id    = 1001
tenant_id     = 10
operation     = UPDATE
actor_id      = editor-42
old_row       = {"credit_limit": 500000, ...}
new_row       = {"credit_limit": 700000, ...}
occurred_at   = 2026-...+00
transaction_id= ...
```

These values are purely **illustrative examples**; actual sequence IDs, timestamps, and transaction IDs are generated by the server.

### Questions to Decide Before Writing Code

- Record every change or only business columns?
- Should no-op `UPDATE`s that leave values unchanged be audited?
- Should `INSERT` and `DELETE` be recorded?
- Do we need application-level actors or only database roles?
- Does the data contain PII or secrets that must not be copied into history?
- Who is allowed to read, update, delete, or purge audit records?
- Do users query point-in-time history or reconstruct past state?
- Is independent evidence needed even if a transaction rolls back or a DB superuser alters traces?

Not every application needs the same level of auditing.

## 3. Audit Trails vs. History Tables and Event Sourcing

| Mechanism | Primary Purpose | Key Point to Remember |
|---|---|---|
| Row audit trigger | Record DML before/after table changes | Transactional, coupled to source DML |
| History / version table | Keep structured historical row versions | Can support temporal queries |
| Business event | Express domain events like `OrderPaid` | Not 1:1 with arbitrary SQL `UPDATE`s |
| Transactional outbox | Record intent to publish externally inside the same transaction | Requires idempotent publishers/consumers |
| Logical decoding / CDC | Stream WAL changes via replication protocol | Handles different workloads from triggers; requires slot/lag ops |
| PostgreSQL server logs / pgAudit | Track SQL activity at database/statement level | Different from queryable row snapshots |
| External tamper-evident audit | Persist/anchor evidence outside the source DB | Needed when guarding against high-privilege DB insiders |

Row auditing fits when you want to **query who changed which row, from which value to which value** across monitored DML operations.

Audit triggers are **not** event sourcing: in event sourcing, events are the authoritative source used to derive state; with row auditing, the business table typically remains the **source of truth**, while the audit table is derived data written inside the same transaction.

## 4. Triggers vs. `RULE`: Choosing the Right Mechanism

In PostgreSQL, a **trigger** fires when an event occurs on a table/view at the declared timing and level. A **`RULE`** belongs to the query rewrite system: it transforms the query tree prior to execution.

### Using Triggers for Auditing

- Provides `OLD`/`NEW` corresponding to the changed row.
- Provides `TG_OP` distinguishing `INSERT`, `UPDATE`, and `DELETE`.
- Can write one event per affected row.
- Can use `AFTER` to observe the final row state after any `BEFORE` triggers.
- Audit DML executes within the same transaction.

### Why Shouldn't `RULE` Usually Be Used to Audit Row Changes?

`RULE` operates at the query-rewrite layer, not as a post-row-change callback holding per-row `OLD`/`NEW` records like a row-level trigger. Rewrite rules introduce subtle semantics with multi-row statements, `RETURNING`, side effects, and views. PostgreSQL generally recommends triggers for per-row logging/validation tasks, reserving rules for specialized cases such as view rewriting.

**Conclusion:** When the goal is **recording history of changed rows**, choose triggers first — never pick `RULE` merely because this chapter is titled "Triggers and Rules."

## 5. `BEFORE` vs. `AFTER` for Auditing

| Timing | When It Runs | Used For |
|---|---|---|
| `BEFORE INSERT/UPDATE` | Before writing a row | Value normalization, validation, modifying `NEW` |
| `AFTER INSERT/UPDATE/DELETE` | After the row operation in the statement | Recording history of the values applied at statement level |
| `INSTEAD OF` on a view | Replaces the view operation | Translating writes through a view to base tables |
| `AFTER ... FOR EACH STATEMENT` | Once per statement | Batch summary logs or processing via transition tables |

### Why Prefer `AFTER ROW`?

If a `BEFORE UPDATE` trigger trims names or sets timestamps, an `AFTER UPDATE` audit trigger observes `NEW` after all `BEFORE` modifications. That closely matches **the row state the statement actually wrote**.

Still, `AFTER` does not guarantee **committed** persistence; if the transaction later rolls back, both source changes and transactional audit rows roll back together.

### `RETURN` in an `AFTER` Trigger

The return value of a row-level `AFTER` trigger is never used to alter the source row. In the examples below, `RETURN NULL` indicates no row replacement; it does **not** skip rows of the outer DML statement.

## 6. Row-Level vs. Statement-Level

An SQL statement:

```sql
UPDATE accounts
SET status = 'SUSPENDED'
WHERE tenant_id = 10;
```

might update 100 rows.

**`FOR EACH ROW`**: the trigger runs once per affected row with bound `OLD`/`NEW` records.

**`FOR EACH STATEMENT`**: the trigger runs once per statement, even if 0 rows matched; it does not normally receive per-row `OLD`/`NEW` records. With eligible `AFTER` statement triggers declaring `REFERENCING OLD TABLE/NEW TABLE`, you can query **transition relations** holding the sets of old/new rows.

### Choosing Between Them

- Need per-row snapshots: straightforward `AFTER ... FOR EACH ROW`.
- Need set-based processing: `AFTER ... FOR EACH STATEMENT` + transition tables.
- Need to record attempted statements even on 0 matched rows: statement-level logging behaves differently from row auditing.

Both approaches differ in cost, semantics, and limits; test 0-row statements explicitly too.

## 7. Preparing the Lab Schema

Run once on your practice database:

```sql
CREATE SCHEMA IF NOT EXISTS lesson_audit;

CREATE TABLE lesson_audit.accounts (
    account_id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id BIGINT NOT NULL,
    account_code TEXT NOT NULL,
    display_name TEXT NOT NULL,
    credit_limit NUMERIC(14,2) NOT NULL
        CHECK (credit_limit >= 0),
    status TEXT NOT NULL DEFAULT 'ACTIVE'
        CHECK (status IN ('ACTIVE', 'SUSPENDED', 'CLOSED')),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
    UNIQUE (tenant_id, account_code)
);
```

`GENERATED BY DEFAULT AS IDENTITY` lets examples supply deterministic IDs; production schemas may choose `GENERATED ALWAYS` or another appropriate key strategy.

### Why Include `tenant_id`?

To reinforce that audit history also needs **tenant scoping**, rather than letting everyone with `SELECT` on the audit table read across all tenants. Each source row carries `tenant_id`, and audit rows capture that tenant scope.

## 8. History Table Using JSONB Snapshots

```sql
CREATE TABLE lesson_audit.account_audit (
    audit_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    account_id BIGINT NOT NULL,
    tenant_id BIGINT NOT NULL,
    operation TEXT NOT NULL
        CHECK (operation IN ('INSERT', 'UPDATE', 'DELETE')),
    old_row JSONB,
    new_row JSONB,
    actor_id TEXT,
    transaction_id BIGINT NOT NULL,
    occurred_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
    CHECK (
        (operation = 'INSERT'
         AND old_row IS NULL AND new_row IS NOT NULL)
        OR
        (operation = 'UPDATE'
         AND old_row IS NOT NULL AND new_row IS NOT NULL)
        OR
        (operation = 'DELETE'
         AND old_row IS NOT NULL AND new_row IS NULL)
    )
);

CREATE INDEX ix_account_audit_tenant_account_event
ON lesson_audit.account_audit (
    tenant_id,
    account_id,
    audit_id DESC
);

CREATE INDEX ix_account_audit_occurred
ON lesson_audit.account_audit (occurred_at DESC);
```

### Why Separate `audit_id` and `account_id`?

`account_id` is the **business entity key** and repeats across many historical events.

`audit_id` is the **event's own surrogate key**, generated by an identity sequence to distinguish log rows rather than mirroring the source ID.

### Why Omit a Foreign Key `account_audit.account_id -> accounts`?

When a source row is deleted, the audit table must still keep its historical snapshot. A direct FK requiring the parent row to remain present would block `DELETE` or cascade-delete the audit history. Other referencing designs exist, but the entity lifecycle must not destroy its own history.

### Why Use JSONB?

`to_jsonb(OLD)` and `to_jsonb(NEW)` capture all columns present on the source row when the trigger fires. If columns are later added to the source table, new snapshots automatically include them without adding matching columns to the audit table every time.

In exchange, JSONB does not replace typed columns for every analytics use case, and audit storage grows quickly if source rows contain large blobs or sensitive columns.

## 9. Metadata Semantics: Timestamps and Transaction IDs

Key fields:

- `occurred_at`: uses `clock_timestamp()` when the trigger writes the event, reflecting wall-clock time at invocation.
- `transaction_id`: uses `txid_current()` for the PostgreSQL `bigint` transaction identifier.
- `actor_id`: demonstrates application context set via `current_setting('app.actor_id', true)`.

### Do Not Confuse the Three Timestamp Functions

```sql
SELECT
    transaction_timestamp() AS transaction_started,
    statement_timestamp() AS statement_started,
    clock_timestamp() AS wall_clock_now;
```

| Function | Meaning |
|---|---|
| `now()` / `transaction_timestamp()` | Constant timestamp when the current transaction started |
| `statement_timestamp()` | Start time of the current statement |
| `clock_timestamp()` | Current wall-clock time, advancing within a statement |

The history table uses `clock_timestamp()` so multiple events inside one transaction show distinct timestamps, **yet it is not a strictly authoritative commit timestamp**. `occurred_at` precedes commit, and clock skew/resolution cannot guarantee commit ordering across concurrent transactions.

### Sequence IDs Do Not Define Global Commit Order

Sequences allocate values outside normal transaction rollback; numbers can leave gaps or be allocated earlier by a long-running transaction that commits later. `audit_id DESC` helps browse history in many scenarios, yet it **does not prove global commit order** under concurrency.

## 10. Audit Trigger Function

```sql
CREATE OR REPLACE FUNCTION lesson_audit.capture_account_changes()
RETURNS trigger
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = pg_catalog, pg_temp
AS $$
DECLARE
    v_account_id BIGINT;
    v_tenant_id BIGINT;
    v_old JSONB;
    v_new JSONB;
    v_actor TEXT;
BEGIN
    IF TG_OP = 'INSERT' THEN
        v_account_id := NEW.account_id;
        v_tenant_id := NEW.tenant_id;
        v_old := NULL;
        v_new := to_jsonb(NEW);
    ELSIF TG_OP = 'UPDATE' THEN
        v_account_id := NEW.account_id;
        v_tenant_id := NEW.tenant_id;
        v_old := to_jsonb(OLD);
        v_new := to_jsonb(NEW);

        -- Avoid writing an audit row when no field value changed.
        IF v_old IS NOT DISTINCT FROM v_new THEN
            RETURN NULL;
        END IF;
    ELSIF TG_OP = 'DELETE' THEN
        v_account_id := OLD.account_id;
        v_tenant_id := OLD.tenant_id;
        v_old := to_jsonb(OLD);
        v_new := NULL;
    ELSE
        RAISE EXCEPTION 'Unsupported trigger operation: %', TG_OP;
    END IF;

    v_actor := NULLIF(
        current_setting('app.actor_id', true),
        ''
    );

    INSERT INTO lesson_audit.account_audit (
        account_id,
        tenant_id,
        operation,
        old_row,
        new_row,
        actor_id,
        transaction_id,
        occurred_at
    )
    VALUES (
        v_account_id,
        v_tenant_id,
        TG_OP,
        v_old,
        v_new,
        v_actor,
        txid_current(),
        clock_timestamp()
    );

    -- Return value of an AFTER ROW trigger is ignored.
    RETURN NULL;
END;
$$;
```

### Why `SECURITY DEFINER`?

The design lets application roles modify `accounts` without having **direct `INSERT` privilege** on `account_audit`. The trigger function runs with the trusted owner's privileges to append the audit row.

This is **not** automatic security: the owner must follow least privilege (no excess rights), `search_path` and object references must be pinned safely, and `EXECUTE`/DDL grants and schema ownership must be locked down. In the lab you use a role with creation rights; in production, explicitly govern the owner role and `GRANT`/`REVOKE` rules.

## 11. Attaching the Trigger to the Source Table

```sql
CREATE TRIGGER trg_accounts_audit
AFTER INSERT OR UPDATE OR DELETE
ON lesson_audit.accounts
FOR EACH ROW
EXECUTE FUNCTION lesson_audit.capture_account_changes();
```

### Breakdown

- `AFTER`: fires after the statement-level row operation.
- `INSERT OR UPDATE OR DELETE`: three audited DML events.
- `FOR EACH ROW`: invokes once per modified row.
- `EXECUTE FUNCTION`: calls the PL/pgSQL trigger function; `OLD` and `NEW` are passed implicitly rather than as regular parameters.

The trigger function accesses special variables:

```text
TG_OP            'INSERT' | 'UPDATE' | 'DELETE'
TG_TABLE_SCHEMA  schema name of the triggering table
TG_TABLE_NAME    name of the triggering table
OLD              row before UPDATE/DELETE
NEW              row after INSERT/UPDATE
```

Never reference `OLD.column` in the `INSERT` branch or `NEW.column` in the `DELETE` branch; those records do not represent valid rows in those operations.

## 12. Inserting Initial Data and Observing History

```sql
BEGIN;

SELECT set_config('app.actor_id', 'seed-job', true);

INSERT INTO lesson_audit.accounts (
    account_id,
    tenant_id,
    account_code,
    display_name,
    credit_limit,
    status
)
VALUES
    (
        1001, 10, 'AC-001',
        'An Binh Company',
        500000.00, 'ACTIVE'
    ),
    (
        2001, 20, 'AC-002',
        'Minh Ha Company',
        800000.00, 'ACTIVE'
    );

COMMIT;
```

`set_config(..., true)` sets the configuration locally to the current transaction; here `app.actor_id` supplies audit metadata.

Inspect:

```sql
SELECT
    audit_id,
    tenant_id,
    account_id,
    operation,
    actor_id,
    old_row,
    new_row
FROM lesson_audit.account_audit
ORDER BY audit_id;
```

Expect **two `INSERT` events**, each with `old_row IS NULL` and `new_row` holding the inserted row's JSONB snapshot.

### An Important Caveat About `actor_id`

`app.actor_id` is a **custom session setting controlled by applications**, not an unforgeable identity verified by PostgreSQL itself. If untrusted clients can execute SQL or `SET`, they can overwrite it. Never rely on an unguarded custom setting as **non-repudiable legal proof** of who executed an action.

## 13. `UPDATE`: Capturing Before and After Images

```sql
BEGIN;

SELECT set_config('app.actor_id', 'editor-42', true);

UPDATE lesson_audit.accounts
SET credit_limit = 700000.00,
    updated_at = clock_timestamp()
WHERE tenant_id = 10
  AND account_id = 1001;

COMMIT;
```

Query history:

```sql
SELECT
    audit_id,
    operation,
    actor_id,
    old_row ->> 'credit_limit' AS old_limit,
    new_row ->> 'credit_limit' AS new_limit,
    occurred_at
FROM lesson_audit.account_audit
WHERE tenant_id = 10
  AND account_id = 1001
ORDER BY audit_id;
```

The new event shows operation `UPDATE`, `old_row` holding 500000, and `new_row` holding 700000 alongside all other row fields.

### Why Store Both Snapshots?

Storing only `new_row` forces every history query to look up the previous version in an earlier event — which breaks down with missing baseline logs, schema shifts, or when the first recorded event is an `UPDATE`. Storing **old + new** simplifies audits and reconciliation at the cost of extra storage and WAL volume.

## 14. `DELETE` Still Preserves the Key and Old Snapshot

```sql
BEGIN;

SELECT set_config('app.actor_id', 'admin-17', true);

DELETE FROM lesson_audit.accounts
WHERE tenant_id = 20
  AND account_id = 2001;

COMMIT;
```

After `DELETE`, row 2001 disappears from `accounts`, yet `account_audit` records:

```text
operation = DELETE
old_row   = {... account_id: 2001, ...}
new_row   = NULL
```

Inspect:

```sql
SELECT
    audit_id,
    operation,
    old_row ->> 'display_name' AS deleted_name,
    new_row
FROM lesson_audit.account_audit
WHERE account_id = 2001
ORDER BY audit_id;
```

Because there is no `audit -> accounts` foreign key, deleting the source row never wipes or blocks its history. That is an **intentional schema decision** — not permission for arbitrary invalid `account_id` entries, since triggers and monitoring maintain alignment with source data.

## 15. Skipping No-Op `UPDATE`s

In the trigger:

```sql
IF v_old IS NOT DISTINCT FROM v_new THEN
    RETURN NULL;
END IF;
```

runs after converting `OLD` and `NEW` to JSONB. If all fields match identically, the trigger skips inserting an audit event.

Test it:

```sql
UPDATE lesson_audit.accounts
SET status = status
WHERE tenant_id = 10
  AND account_id = 1001;
```

Assuming no other trigger mutates timestamps or columns on `UPDATE`, the snapshots are identical and **no new audit event is written**.

### That Is a Business Policy Choice, Not a Universal Truth

Some systems must log **attempted updates** even when no column value changed; in that case, do not suppress equal-row `UPDATE`s. Conversely, when tracking **meaningful state changes**, dropping no-ops cuts audit noise.

Never write `OLD IS DISTINCT FROM NEW` blindly without accounting for technical columns that always change like `updated_at` or version counters — they will cause logically unchanged updates to generate audit noise anyway.

## 16. Enforcing Immutable Key Columns

Audit queries rely on `account_id` and `tenant_id` to trace an entity. If callers mutate them, an `UPDATE` could store the new key in metadata and disconnect from earlier history.

You can block key mutations:

```sql
CREATE OR REPLACE FUNCTION lesson_audit.guard_account_identity()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
    IF NEW.account_id IS DISTINCT FROM OLD.account_id
       OR NEW.tenant_id IS DISTINCT FROM OLD.tenant_id THEN
        RAISE EXCEPTION
            'account_id and tenant_id are immutable';
    END IF;

    RETURN NEW;
END;
$$;

CREATE TRIGGER trg_accounts_guard_identity
BEFORE UPDATE
ON lesson_audit.accounts
FOR EACH ROW
EXECUTE FUNCTION lesson_audit.guard_account_identity();
```

### Why `BEFORE`?

This is pre-write **validation**. Rejecting a primary/tenant-key change via exception before persistence prevents the `AFTER` audit trigger from having to reconcile an entity whose identity mutated mid-flight.

Not every business key must be immutable; if `account_code` is editable, before/after snapshots capture the rename. **Surrogate PKs and tenant keys**, however, should almost always remain immutable or use dedicated migration/merge workflows.

## 17. What Happens When a Transaction Rolls Back?

The audit row inserted by the trigger lives **inside the same transaction** as the source change. Try:

```sql
BEGIN;

SELECT set_config('app.actor_id', 'rollback-test', true);

UPDATE lesson_audit.accounts
SET credit_limit = credit_limit + 12345.00
WHERE tenant_id = 10
  AND account_id = 1001;

SELECT credit_limit
FROM lesson_audit.accounts
WHERE account_id = 1001;

SELECT
    audit_id,
    actor_id,
    operation
FROM lesson_audit.account_audit
WHERE actor_id = 'rollback-test';

ROLLBACK;
```

After `ROLLBACK`:

```sql
SELECT credit_limit
FROM lesson_audit.accounts
WHERE account_id = 1001;

SELECT count(*) AS audit_events_after_rollback
FROM lesson_audit.account_audit
WHERE actor_id = 'rollback-test';
```

**Expected:** The source credit limit returns to its previously committed value; `audit_events_after_rollback = 0` (assuming no other committed rows shared that test actor ID).

### Critical Consequence

Row audit triggers record **committed state changes**, not a log of failed or rolled-back attempts. If you must capture failed updates/deletes or rejected calls, you need an out-of-band logging layer independent of the source transaction, not just an in-DB table in the same transaction.

## 18. Trigger Failure Fails the Statement

Suppose the audit function cannot insert an audit row because of missing privileges or a constraint violation:

```text
UPDATE accounts
  └── AFTER UPDATE trigger
        └── INSERT account_audit -> ERROR
              └── statement/transaction fails
```

PostgreSQL does not ignore the trigger error and commit the source table anyway. Unless caught and handled, the DML fails and statement changes roll back cleanly under transaction rules.

### Benefit

When business rules require **"never commit a source change without an audit entry,"** in-transaction triggers enforce fail-closed atomicity cleanly.

### Trade-Off

If the audit table runs out of disk, hits lock contention, or fails in trigger code, business writes fail too. This is the classic consistency-vs.-availability trade-off — manage it with monitoring and capacity planning.

## 19. `BEFORE` Triggers Can Modify `NEW` Before Auditing

Suppose we add a trigger that trims `display_name`:

```sql
CREATE OR REPLACE FUNCTION lesson_audit.trim_display_name()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
    NEW.display_name := btrim(NEW.display_name);
    RETURN NEW;
END;
$$;

CREATE TRIGGER trg_accounts_trim_name
BEFORE INSERT OR UPDATE
ON lesson_audit.accounts
FOR EACH ROW
EXECUTE FUNCTION lesson_audit.trim_display_name();
```

Test it:

```sql
UPDATE lesson_audit.accounts
SET display_name = '  An Binh Company  '
WHERE tenant_id = 10
  AND account_id = 1001;
```

The `BEFORE` trigger trims the whitespace; the `AFTER` audit trigger observes the already-normalized `NEW.display_name`. Since the stored value was already `"An Binh Company"`, the final row is unchanged, so **the no-op check skips writing an audit row** if no other columns changed.

### Ordering Across Multiple Triggers

When multiple triggers share timing, event, and relation on the same table, PostgreSQL executes them alphabetically by **trigger name**. Still, never rely on clever trigger names to disguise tangled business dependencies; design and test normalization, validation, and auditing explicitly for the expected outcome.

## 20. Technical Changes vs. Business Changes

If `updated_at` is modified by an `UPDATE` even when every business field is unchanged:

```sql
UPDATE lesson_audit.accounts
SET updated_at = clock_timestamp()
WHERE account_id = 1001;
```

then `to_jsonb(OLD) IS DISTINCT FROM to_jsonb(NEW)` evaluates to true because `updated_at` changed, generating an audit event.

### Three Strategies

**Log every column change:** appropriate when full row state including `updated_at` must be tracked.

**Log only business-field changes:** compare an explicit list of business columns, ignoring technical columns like `updated_at` or internal counters.

**Log both with classification:** add `change_kind` or `changed_fields` for downstream analysis.

### Example Comparing Business Fields

```sql
IF (OLD.display_name,
    OLD.credit_limit,
    OLD.status,
    OLD.account_code)
   IS NOT DISTINCT FROM
   (NEW.display_name,
    NEW.credit_limit,
    NEW.status,
    NEW.account_code) THEN
    RETURN NULL;
END IF;
```

This snippet is meant **inside the trigger's `UPDATE` branch**, not standalone. Whenever the table schema changes, update the business column list accordingly.

## 21. From Audit Rows to Column-Level Diffs

Every `UPDATE` audit row stores before and after JSONB snapshots. You can list modified keys by expanding each JSONB object into `(key, value)` pairs and comparing with a `FULL JOIN` inside a `LATERAL` subquery:

```sql
SELECT
    a.audit_id,
    d.field_name,
    d.before_value,
    d.after_value
FROM lesson_audit.account_audit AS a
CROSS JOIN LATERAL (
    SELECT
        COALESCE(o.key, n.key) AS field_name,
        o.value AS before_value,
        n.value AS after_value
    FROM jsonb_each(a.old_row) AS o(key, value)
    FULL JOIN jsonb_each(a.new_row) AS n(key, value)
      USING (key)
    WHERE o.value IS DISTINCT FROM n.value
) AS d
WHERE a.operation = 'UPDATE'
  AND a.account_id = 1001
ORDER BY a.audit_id, d.field_name;
```

`field_name` is coalesced from both sides; if a key only exists in one snapshot, the missing side appears as SQL `NULL`.

### JSON `null` vs. Missing Key

In JSONB, an explicit `null` value inside an object differs from an absent key. `jsonb_each` emits JSON `null` as a non-NULL JSONB value, whereas a key missing from one side of the join produces SQL `NULL`. Diff reports should distinguish the two across schema migrations that add or remove columns.

## 22. Querying Audit History per Account

Query:

```sql
SELECT
    audit_id,
    operation,
    actor_id,
    transaction_id,
    occurred_at,
    old_row,
    new_row
FROM lesson_audit.account_audit
WHERE tenant_id = 10
  AND account_id = 1001
ORDER BY audit_id;
```

The index `(tenant_id, account_id, audit_id DESC)` efficiently serves tenant-scoped history lookups ordered by recent ID.

### Not an Absolute Legal Ordering Guarantee

`audit_id` is allocated by a sequence before commit, so it is not a cross-transaction commit clock. When business requirements demand exact **commit-time state reconstruction** under concurrency, add commit-aware sequencing, snapshots, or CDC.

In sequential lab testing, `ORDER BY audit_id` is typically sufficient to inspect the generated sequence of changes.

## 23. Invariants That Must Be Verified

Before writing tests, list the exact **invariants** your audit design must uphold:

| Code | Invariant | Verification Method |
|---|---|---|
| A1 | Every tracked `INSERT` emits an `INSERT` event | Count new events and check `new_row` |
| A2 | Every value-changing `UPDATE` emits an `UPDATE` event | Match `old_row`/`new_row` against before/after row images |
| A3 | No-op `UPDATE`s produce no event per lab policy | Compare audit counts before and after |
| A4 | Every tracked `DELETE` emits a `DELETE` event | `old_row` populated, `new_row` is SQL `NULL` |
| A5 | Audits never cross tenant boundaries | Key and tenant in metadata match snapshot |
| A6 | Rolled-back DML leaves zero committed audit rows | `ROLLBACK` and re-query |
| A7 | Failed DML leaves no partial source or audit state | Test constraint/exception inside transaction |
| A8 | Only authorized roles may read audits | Test `GRANT`/`REVOKE`/RLS |
| A9 | Every real write path fires required triggers | Test `INSERT`/`UPDATE`/`DELETE`, `COPY`, `UPSERT`, admin scripts |
| A10 | Source and history reconcile at a consistent boundary | Compare latest snapshot against live source table |

Saying "we added a trigger, so auditing is done" is never enough. Only after defining **what correctness looks like** and **how to detect drift** is the system reliable long-term.

## 24. Verifying Event Counts After `INSERT`

After creating the trigger and running the initial two `INSERT`s:

```sql
SELECT
    operation,
    count(*) AS event_count
FROM lesson_audit.account_audit
GROUP BY operation
ORDER BY operation;
```

If run immediately after the initial inserts, expect:

```text
INSERT | 2
```

After running the later `UPDATE`/`DELETE` examples, counts naturally rise. To write tests **independent of prior lab state**, filter by a dedicated test key or capture baseline counts right before the operation inside the test transaction.

### Avoid Assuming Identity Always Starts at 1

Both `audit_id` and `account_id` use identity sequences that retain gaps after rolled-back transactions or earlier runs. Never hard-code assertions like "the first event always has `audit_id = 1`" in real systems.

## 25. Transactional `INSERT` Assertion Test

A repeatable test scoped to a dedicated test ID and rolled back cleanly:

```sql
BEGIN;

DO $$
DECLARE
    v_before BIGINT;
    v_after BIGINT;
    v_account_id BIGINT := 900001;
BEGIN
    SELECT count(*)
    INTO v_before
    FROM lesson_audit.account_audit
    WHERE account_id = v_account_id;

    INSERT INTO lesson_audit.accounts (
        account_id, tenant_id, account_code,
        display_name, credit_limit, status
    )
    VALUES (
        v_account_id, 90, 'TEST-900001',
        'Test Account', 10000, 'ACTIVE'
    );

    SELECT count(*)
    INTO v_after
    FROM lesson_audit.account_audit
    WHERE account_id = v_account_id;

    IF v_after <> v_before + 1 THEN
        RAISE EXCEPTION
            'Expected one audit INSERT event, got %',
            v_after - v_before;
    END IF;
END;
$$;

ROLLBACK;
```

### Why `ROLLBACK`?

To test audit creation and inspect results without polluting the database with leftover test accounts. If an assertion raises, the transaction enters an aborted state and still requires rollback before issuing subsequent commands.

Note: if `account_id` 900001 already exists in the lab database, the `INSERT` hits a unique-key error; pick an unused ID or an isolated test fixture.

## 26. Snapshot-Based `UPDATE` Verification Test

Stronger than merely counting rows:

```sql
BEGIN;

DO $$
DECLARE
    v_before JSONB;
    v_after JSONB;
    v_event lesson_audit.account_audit%ROWTYPE;
BEGIN
    SELECT to_jsonb(a)
    INTO STRICT v_before
    FROM lesson_audit.accounts AS a
    WHERE a.tenant_id = 10
      AND a.account_id = 1001;

    UPDATE lesson_audit.accounts
    SET credit_limit = credit_limit + 5000,
        updated_at = clock_timestamp()
    WHERE tenant_id = 10
      AND account_id = 1001;

    SELECT to_jsonb(a)
    INTO STRICT v_after
    FROM lesson_audit.accounts AS a
    WHERE a.tenant_id = 10
      AND a.account_id = 1001;

    SELECT *
    INTO STRICT v_event
    FROM lesson_audit.account_audit
    WHERE tenant_id = 10
      AND account_id = 1001
      AND operation = 'UPDATE'
    ORDER BY audit_id DESC
    LIMIT 1;

    IF v_event.old_row IS DISTINCT FROM v_before
       OR v_event.new_row IS DISTINCT FROM v_after THEN
        RAISE EXCEPTION 'Audit snapshot mismatch';
    END IF;
END;
$$;

ROLLBACK;
```

### Significance

This verifies not only that an event appeared, but also that **`OLD` matches the exact pre-`UPDATE` snapshot** and **`NEW` matches the exact post-`UPDATE` snapshot** within the same transaction.

### Limitation

Using `ORDER BY audit_id DESC LIMIT 1` assumes no interference; under multiple concurrent writers touching the same account, isolate tests with dedicated fixtures. Because the `UPDATE` holds a row lock, other writers cannot commit an update on that same row between your `UPDATE` and your `SELECT`, though using a fresh fixture remains best practice.

## 27. Testing a No-Change `UPDATE`

```sql
BEGIN;

DO $$
DECLARE
    v_count_before BIGINT;
    v_count_after BIGINT;
BEGIN
    SELECT count(*)
    INTO v_count_before
    FROM lesson_audit.account_audit
    WHERE tenant_id = 10 AND account_id = 1001;

    UPDATE lesson_audit.accounts
    SET status = status
    WHERE tenant_id = 10 AND account_id = 1001;

    SELECT count(*)
    INTO v_count_after
    FROM lesson_audit.account_audit
    WHERE tenant_id = 10 AND account_id = 1001;

    IF v_count_after <> v_count_before THEN
        RAISE EXCEPTION 'No-op UPDATE unexpectedly audited';
    END IF;
END;
$$;

ROLLBACK;
```

### Test Precondition

No other trigger may mutate row columns during `UPDATE ... SET status = status`; if another mechanism auto-increments a version or updates `updated_at` on every `UPDATE`, no-op detection must compare **business columns** rather than full rows.

Never confuse "an `UPDATE` matched one row" with "a value changed." PostgreSQL writes a new tuple version even when all logical fields match; your audit policy decides whether to log that or skip it.

## 28. Testing That `DELETE` Preserves Old Data

```sql
BEGIN;

DO $$
DECLARE
    v_before JSONB;
    v_old_event JSONB;
    v_new_event JSONB;
BEGIN
    INSERT INTO lesson_audit.accounts (
        account_id, tenant_id, account_code,
        display_name, credit_limit
    )
    VALUES (
        900002, 90, 'TEST-900002',
        'Account to Delete', 2000
    );

    SELECT to_jsonb(a)
    INTO STRICT v_before
    FROM lesson_audit.accounts AS a
    WHERE a.account_id = 900002;

    DELETE FROM lesson_audit.accounts
    WHERE account_id = 900002;

    SELECT old_row, new_row
    INTO STRICT v_old_event, v_new_event
    FROM lesson_audit.account_audit
    WHERE account_id = 900002
      AND operation = 'DELETE';

    IF v_old_event IS DISTINCT FROM v_before
       OR v_new_event IS NOT NULL THEN
        RAISE EXCEPTION 'Invalid DELETE audit event';
    END IF;
END;
$$;

ROLLBACK;
```

After `DELETE`, account 900002 is gone inside the transaction while `old_row` preserves its snapshot. After `ROLLBACK`, both the test account and its `INSERT`/`DELETE` audit rows vanish cleanly.

## 29. Reconciling Source Rows with Latest Audit State

If **every row has been audited since its initial `INSERT`**, you can compare current table state against each account's latest audit event:

```sql
WITH latest AS (
    SELECT DISTINCT ON (tenant_id, account_id)
        tenant_id,
        account_id,
        operation,
        new_row
    FROM lesson_audit.account_audit
    ORDER BY tenant_id, account_id, audit_id DESC
)
SELECT
    a.tenant_id,
    a.account_id,
    to_jsonb(a) AS current_row,
    l.new_row AS last_audited_row
FROM lesson_audit.accounts AS a
LEFT JOIN latest AS l
  ON l.tenant_id = a.tenant_id
 AND l.account_id = a.account_id
WHERE l.account_id IS NULL
   OR l.operation = 'DELETE'
   OR l.new_row IS DISTINCT FROM to_jsonb(a);
```

### Expected Result

In a sequential lab where all writes go through triggers, this query returns **0 rows**.

### Assumptions Behind This Check

- No pre-existing source rows lacked a baseline audit entry.
- No trigger was disabled or bypassed.
- Historical JSONB keys still match the current table schema.
- No concurrent transaction committed mid-check causing snapshot skew.
- `audit_id` order matches the test timeline; **never** treat this query alone as proof of global commit order across concurrent writers.

For reliable production reconciliation under concurrency, run against a **consistent snapshot** and factor in locking, CDC, or commit sequencing.

## 30. Detecting Deleted Source Rows Lacking a `DELETE` Audit Event

The inverse check looks for entities whose **latest event indicates the row still exists** even though the source table lacks it:

```sql
WITH latest AS (
    SELECT DISTINCT ON (tenant_id, account_id)
        tenant_id,
        account_id,
        operation,
        new_row
    FROM lesson_audit.account_audit
    ORDER BY tenant_id, account_id, audit_id DESC
)
SELECT
    l.tenant_id,
    l.account_id,
    l.operation,
    l.new_row
FROM latest AS l
LEFT JOIN lesson_audit.accounts AS a
  ON a.tenant_id = l.tenant_id
 AND a.account_id = l.account_id
WHERE a.account_id IS NULL
  AND l.operation <> 'DELETE';
```

If rows appear, possible causes include:

- A `DELETE` ran without firing the audit trigger.
- An audit log entry was deleted or altered.
- Rows were wiped via `TRUNCATE` or untracked operations.
- Data was loaded or migrated outside the audit contract.
- Events were misordered relative to actual commit order.

Never "patch the log" by inserting a fake `DELETE` event before investigating. Any retrospective system entry must be clearly marked as **reconciliation/correction**, never disguised as a historical user `DELETE`.

## 31. Verifying Sequential Event Chains

A lifecycle sequence:

```text
INSERT limit 500000
UPDATE limit 700000
UPDATE status SUSPENDED
DELETE
```

creates four events under lab rules. Across a sequential chain for one entity:

- `INSERT.new_row` is the initial state.
- `UPDATE_1.old_row` equals state before the update; `UPDATE_1.new_row` equals state after.
- `UPDATE_2.old_row` equals `UPDATE_1.new_row` (assuming no intervening changes).
- `DELETE.old_row` equals the state right before deletion.

Use `LAG` across audit events to detect breaks in the chain:

```sql
WITH ordered AS (
    SELECT
        tenant_id,
        account_id,
        audit_id,
        operation,
        old_row,
        new_row,
        lag(new_row) OVER (
            PARTITION BY tenant_id, account_id
            ORDER BY audit_id
        ) AS previous_new
    FROM lesson_audit.account_audit
)
SELECT *
FROM ordered
WHERE operation IN ('UPDATE', 'DELETE')
  AND previous_new IS DISTINCT FROM old_row;
```

In a sequential lab, expect 0 rows.

### Limitation of This Check

If concurrent transactions allocated `audit_id`s out of commit order, or if rows existed before auditing was enabled, chains can show gaps or mismatches. Treat this query as an **anomaly detector**, not standalone global historical proof.

## 32. Testing Multi-Table Transaction Atomicity

Suppose the application updates an account and inserts a business event in the same transaction:

```text
BEGIN
  UPDATE accounts
    └── trigger INSERT account_audit
  INSERT business_event
COMMIT
```

If the second statement fails and the transaction rolls back, the `UPDATE`'s audit event rolls back too.

### Why This Helps

There is no "account changed, audit missing" state in any committed transaction, provided the trigger is active and errors are not swallowed.

### Clear Boundary Required

If an application splits the source `UPDATE` and event emission into **two separate transactions**, the audit trigger only guarantees history for the `UPDATE` transaction; it cannot ensure the second transaction or an external HTTP call succeeded.

For reliable external event delivery aligned with DB commits, use a **transactional outbox** — never fire messages or HTTP requests inside a row trigger expecting PostgreSQL to roll them back.

## 33. Source Constraints Are Part of Correctness

`accounts` enforces:

```sql
credit_limit NUMERIC(14,2) NOT NULL CHECK (credit_limit >= 0)
```

Try:

```sql
BEGIN;

UPDATE lesson_audit.accounts
SET credit_limit = -1
WHERE account_id = 1001;

-- This UPDATE fails with a check_constraint error.
ROLLBACK;
```

Because the constraint fails, no negative `credit_limit` ever commits. Audit triggers do not repair invalid data; **constraints** protect source invariants while triggers record valid transactional changes.

### Errors Can Happen at Multiple Points

Constraint checks can be immediate or deferred depending on constraint definition; even if an `AFTER ROW` trigger already inserted an audit entry during the transaction, a later constraint failure rolls back both the source row and the audit row.

Never treat "the trigger ran" as "the transaction committed."

## 34. Multi-Row Updates: How Many Events?

```sql
BEGIN;

SELECT set_config('app.actor_id', 'bulk-job', true);

UPDATE lesson_audit.accounts
SET status = 'SUSPENDED'
WHERE tenant_id = 10
  AND status = 'ACTIVE';

SELECT
    count(*) AS events_in_transaction
FROM lesson_audit.account_audit
WHERE actor_id = 'bulk-job'
  AND operation = 'UPDATE';

ROLLBACK;
```

With an **`AFTER ROW` trigger**, every modified row that passes the audit filter emits one event. If the `WHERE` clause matches 0 rows, zero row-level invocations run. One bulk statement can produce tens of thousands of audit entries.

### Cost Evaluation

- Per-row PL/pgSQL function overhead.
- JSONB snapshot construction.
- WAL generation for audit inserts and indexes.
- Transaction footprint.
- Lock duration and contention.

Never attach heavy full-row JSONB triggers to high-write-rate tables without benchmarking throughput and storage first.

## 35. Statement-Level Transition Tables for Set-Based Processing

PostgreSQL supports **transition relations** on eligible `AFTER` triggers. For `UPDATE`, you can declare:

```sql
REFERENCING OLD TABLE AS old_rows NEW TABLE AS new_rows
FOR EACH STATEMENT
```

The trigger function reads `old_rows` and `new_rows` as temporary statement-scoped tables instead of running per-row PL/pgSQL loops.

### When Is This Useful?

- Batch audit logging via a single `INSERT ... SELECT`.
- Computing set-based summaries of modified rows.
- Cutting per-row function call overhead in bulk workloads.

### Restrictions

- Applies only to eligible trigger timings/types.
- Cannot be combined with column lists like `UPDATE OF column_list` per PostgreSQL rules.
- Joining `OLD` and `NEW` requires a **key immutable across the statement**.
- With partitioned tables and special DML, verify exact version behavior.

## 36. Lab: Statement-Level Transition Tables

Create a separate table pair so we do not double-audit `accounts`:

```sql
CREATE TABLE lesson_audit.batch_items (
    item_id BIGINT PRIMARY KEY,
    tenant_id BIGINT NOT NULL,
    qty INTEGER NOT NULL CHECK (qty >= 0)
);

CREATE TABLE lesson_audit.batch_item_changes (
    event_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    item_id BIGINT NOT NULL,
    tenant_id BIGINT NOT NULL,
    old_qty INTEGER NOT NULL,
    new_qty INTEGER NOT NULL,
    recorded_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp()
);

CREATE OR REPLACE FUNCTION lesson_audit.capture_batch_item_updates()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
    INSERT INTO lesson_audit.batch_item_changes (
        item_id,
        tenant_id,
        old_qty,
        new_qty
    )
    SELECT
        n.item_id,
        n.tenant_id,
        o.qty,
        n.qty
    FROM old_rows AS o
    JOIN new_rows AS n
      ON n.item_id = o.item_id
    WHERE o.qty IS DISTINCT FROM n.qty;

    RETURN NULL;
END;
$$;

CREATE TRIGGER trg_batch_item_updates
AFTER UPDATE
ON lesson_audit.batch_items
REFERENCING OLD TABLE AS old_rows
            NEW TABLE AS new_rows
FOR EACH STATEMENT
EXECUTE FUNCTION lesson_audit.capture_batch_item_updates();
```

Run it:

```sql
INSERT INTO lesson_audit.batch_items (
    item_id, tenant_id, qty
)
VALUES
    (1, 10, 5),
    (2, 10, 8),
    (3, 20, 7);

UPDATE lesson_audit.batch_items
SET qty = qty + 2
WHERE tenant_id = 10;

SELECT *
FROM lesson_audit.batch_item_changes
ORDER BY event_id;
```

Expect **two events** for items 1 and 2, even though `capture_batch_item_updates` fired **only once for the `UPDATE` statement**.

### Exact Scope of This Pattern

Joining `OLD` and `NEW` on `item_id` works only while `item_id` itself stays unchanged. If an `UPDATE` can mutate the primary key, you need a surrogate immutable key or a different design. To audit more fields, include those columns or snapshots rather than `qty` alone.

## 37. Statement `UPDATE` Matching 0 Rows

```sql
UPDATE lesson_audit.batch_items
SET qty = qty + 1
WHERE tenant_id = -999;
```

With a statement-level trigger, the function still runs **once for the statement**, but `old_rows` and `new_rows` are empty so `INSERT ... SELECT` inserts zero event rows.

With row-level triggers on `accounts`, zero matched rows means zero row trigger invocations.

### Why Does This Matter?

If the requirement is logging "someone attempted an `UPDATE`" even when zero rows matched, that is different from recording **data state transitions**. You will need statement-level auditing or application request logs instead.

## 38. Operations That Differ from Simple `UPDATE`/`DELETE`

Applications rarely use only the three simplest DML forms. Audit coverage must account for:

- `INSERT ... ON CONFLICT DO UPDATE` (`UPSERT`).
- `MERGE` (on supported versions).
- `COPY FROM` bulk loads.
- Cascading updates/deletes via foreign keys.
- Bulk jobs, migrations, and admin tools.
- `TRUNCATE`.
- Replication apply and sessions with altered trigger-firing modes.

Never claim "we installed triggers so every data mutation is audited" until you test every write path your application and tooling actually use.

## 39. `UPSERT` Can Act as Either `INSERT` or `UPDATE`

Using the unique constraint `(tenant_id, account_code)`:

```sql
INSERT INTO lesson_audit.accounts (
    tenant_id, account_code, display_name, credit_limit
)
VALUES (
    10, 'AC-001', 'An Binh Company', 710000
)
ON CONFLICT (tenant_id, account_code)
DO UPDATE
SET credit_limit = EXCLUDED.credit_limit;
```

Because `AC-001` already exists, the row takes the `DO UPDATE` branch; row-level audit sees an `UPDATE` (unless skipped as a no-op). When no conflict occurs, it records an `INSERT`.

### Subtler Trigger Semantics in `UPSERT`

`INSERT ... ON CONFLICT DO UPDATE` has specific trigger firing rules; statement-level `INSERT` and `UPDATE` triggers can both fire regardless of intuitive "one action per row" assumptions. Test **both row-level and statement-level** triggers explicitly whenever `UPSERT` is used.

When `ON CONFLICT DO NOTHING` skips a row, row auditing must not fabricate an `INSERT` event for a row that was never inserted.

## 40. `MERGE` and Multi-Branch Actions

`MERGE` combines `INSERT`, `UPDATE`, and `DELETE` across matched and unmatched branches in supported PostgreSQL versions.

### Test Cases to Cover

- `WHEN MATCHED THEN UPDATE`.
- `WHEN MATCHED THEN DELETE`.
- `WHEN NOT MATCHED THEN INSERT`.
- Executions where a branch touches zero rows.
- Both statement-level and row-level firing per target PostgreSQL version.

Never treat `MERGE` as "a single event" or identical to a plain `UPDATE`. If audits track **row outcomes**, inspect the actual actions executed.

## 41. `COPY FROM` and Bulk Ingestion

`COPY table FROM ...` can fire `INSERT` row triggers per PostgreSQL semantics, yet enabling full JSONB snapshot triggers during bulk loads adds massive overhead.

### Design Considerations

- Does importing 10 million initial rows really need 10 million `INSERT` audit rows?
- Can data load into a staging table first and merge under audit policy?
- Should batch IDs and source filenames be recorded for provenance?
- If triggers are temporarily disabled for speed, how is the **audit gap** formally documented?

Never quietly disable triggers just for fast imports while still claiming full audit completeness. When bootstrap loads bypass per-row auditing, record a clear **baseline/migration record** with provenance.

## 42. `TRUNCATE` Is a Gap When Using Only Row Audits

`TRUNCATE lesson_audit.accounts` wipes rows fast without **firing per-row `DELETE` triggers**.

PostgreSQL supports **statement-level triggers on `TRUNCATE`**:

```sql
CREATE OR REPLACE FUNCTION lesson_audit.log_truncate_attempt()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
    RAISE EXCEPTION
        'TRUNCATE is not allowed on audited table %',
        TG_TABLE_NAME;
END;
$$;

CREATE TRIGGER trg_accounts_block_truncate
BEFORE TRUNCATE
ON lesson_audit.accounts
FOR EACH STATEMENT
EXECUTE FUNCTION lesson_audit.log_truncate_attempt();
```

### Why Block `TRUNCATE` in the Lab?

When policy requires preserving full per-row `OLD` snapshots, `TRUNCATE` provides none via row `DELETE` triggers. Blocking it prevents accidental erasure without row `DELETE` events.

### Limits

- Privileged roles able to modify schema or disable/drop triggers can still bypass it.
- `TRUNCATE` carries special locking and transaction semantics; trigger blocking never replaces revoking `TRUNCATE` privilege.
- If an application genuinely uses `TRUNCATE`, enforce **statement-level** auditing and explicit snapshots/baselines rather than faking per-row `DELETE` records.

## 43. Governing `TRUNCATE` Privileges

In production:

- Never grant `TRUNCATE` casually to application roles.
- Withhold table ownership and schema DDL rights where unneeded.
- Prevent ordinary roles from running `ALTER TABLE ... DISABLE TRIGGER`.
- Separate migration/admin roles from runtime roles.
- Monitor schema and trigger-state changes.

A `BEFORE TRUNCATE` trigger blocks accidental commands, yet it is **never an unbreakable barrier against high-privilege accounts**. Access governance and external monitoring remain essential.

## 44. Triggers Can Be Disabled or Bypassed

Scenarios you must understand:

- `ALTER TABLE ... DISABLE TRIGGER` executed by a sufficiently privileged role.
- `DROP TRIGGER` / `DROP FUNCTION` by an authorized role.
- `session_replication_role` altering trigger firing modes according to permissions.
- Logical replication apply interacting with `ENABLE REPLICA` / `ENABLE ALWAYS TRIGGER`.
- Writes hitting unattached tables or misconfigured partitions.
- Bulk migrations running outside normal pipelines.

### Why Is This Dangerous?

If source rows mutate while audit triggers are inactive, **current state advances without matching history**. Re-enabling triggers later **never backfills missed events**.

### Operational Response

Document the exact window and scope of the audit gap, reconcile using snapshots, WAL/CDC, or backups where available, and insert transparent correction/baseline records. Never fabricate backdated fake events claiming "this exact change happened then" without proof.

## 45. Checking Existing Triggers and Enabled State

Inspect via `pg_trigger`:

```sql
SELECT
    n.nspname AS table_schema,
    c.relname AS table_name,
    t.tgname AS trigger_name,
    t.tgenabled AS firing_mode,
    t.tgisinternal AS internal_trigger,
    pg_get_triggerdef(t.oid, true) AS definition
FROM pg_catalog.pg_trigger AS t
JOIN pg_catalog.pg_class AS c
  ON c.oid = t.tgrelid
JOIN pg_catalog.pg_namespace AS n
  ON n.oid = c.relnamespace
WHERE n.nspname = 'lesson_audit'
ORDER BY c.relname, t.tgname;
```

`tgenabled` encodes enabled/disabled and replication firing modes. Don't merely verify "a trigger with that name exists" — verify its firing mode matches the environment being protected.

### Monitoring Definition Drift

Compare live catalog DDL against checked-in migration manifests using a trusted configuration-management pipeline. Querying catalogs inside the same DB alone cannot offer **tamper-proof evidence** if high-privilege insiders can edit both DB objects and logs.

## 46. Trigger Recursion and Write Loops

Because our audit function inserts into a **separate table** (`account_audit`) rather than updating `accounts`, it does not re-trigger itself.

However, adding a trigger on `account_audit` that updates `accounts`, or a trigger on `accounts` that issues an `UPDATE accounts`, can trigger recursion, deadlocks, or infinite loops.

PostgreSQL provides:

```sql
SELECT pg_trigger_depth();
```

but never use `IF pg_trigger_depth() > 1 THEN RETURN ...` as a band-aid to hide recursive trigger architecture.

### Sound Design

- Normalization/validation triggers modify `NEW` in `BEFORE` when appropriate.
- `AFTER` audit triggers only append to audit tables.
- Audit tables never carry triggers updating source tables back unless strictly justified and proven safe.
- Design outbox/event hooks cleanly to avoid feedback loops.

## 47. Partitioned Tables and Auditing

On tables partitioned by tenant or time, row triggers created on the parent clone/fire onto partitions in modern PostgreSQL, though exact capabilities depend on version, trigger options, and DDL operations.

### Scenarios to Test

- `INSERT` on parent routing to leaf partitions.
- `UPDATE` causing cross-partition row movement.
- `DELETE` via parent vs. directly on a leaf partition.
- `ATTACH`/`DETACH` partition maintenance.
- Bulk `COPY` and partition maintenance scripts.
- Statement-level triggers on parent vs. partitions.

### Never Assume Every Event Looks Like a Single-Table `UPDATE`

Cross-partition row movement during an `UPDATE` can execute internal `DELETE` + `INSERT` steps and fire corresponding triggers. Test against your **exact PostgreSQL version and partition layout** so you never miscount or misclassify operations.

If the audit table itself is partitioned, plan retention, indexes, and primary keys carefully so DML latency stays within SLA.

## 48. DDL Changes Are Outside `AFTER INSERT/UPDATE/DELETE`

Schema alterations:

```sql
ALTER TABLE lesson_audit.accounts
ADD COLUMN IF NOT EXISTS external_ref TEXT;
```

are not data DML events; the row audit trigger emits no "schema changed" record.

### How to Audit DDL

Combine:

- Versioned migration repositories and approval logs.
- Database server logs / DDL audit extensions (`pgAudit`).
- PostgreSQL **event triggers** for supported database-level DDL events.

Event triggers are distinct from row triggers, require elevated privileges, and have specific coverage rules. Never claim event triggers catch every administrator action or prevent superusers from tampering with logs.

## 49. Audit Rows Do Not Automatically Store Schema Versions

Suppose `accounts` originally had 7 columns, and a migration adds `external_ref`.

Older JSONB events lack `external_ref`, while newer events include it.

### Consequences

- Comparing snapshots across schema versions requires explicit rules.
- A missing key differs from JSON `null`.
- Renaming a column looks like "key A disappeared, key B appeared."
- History viewers must not assume every historical event shares an identical JSON shape.

### Mitigation

Include a `schema_version` or `event_version` column on the audit table managed via migrations if needed. UIs can render based on each event's own fields, while long-lived analytics pipelines need formal schema-evolution handling.

## 50. Backfilling Baseline History When Enabling Triggers

If a table already holds millions of rows before audit triggers are created, those existing rows **lack historical `INSERT` events**.

Clean rollout sequence:

1. Define a cutover/baseline timestamp.
2. Deploy audit schema and verify permissions.
3. Take a consistent snapshot or run an online watermarked backfill.
4. Insert explicit **`BASELINE`** records with source provenance — never masquerade them as original `INSERT`s.
5. Enable/monitor triggers across the cutover window.
6. Reconcile rows modified during the cutover window.
7. Document clearly the timestamp from which full change history starts.

### Lab Schema Note

The lab `account_audit` table restricts `operation` to `INSERT`/`UPDATE`/`DELETE`. To add `BASELINE`, update the `CHECK` constraint and contract via migration, or store baselines in a separate table. Never fabricate `operation = 'INSERT'` for pre-existing rows and present it as real original history.

A trustworthy audit trail never pretends to know unrecorded past changes; it documents **exact coverage boundaries**.

## 51. Concurrency: Two Sessions Updating the Same Row

Suppose account 1001 has `credit_limit = 700000`. Two concurrent sessions run:

**Session A:**

```sql
BEGIN;

UPDATE lesson_audit.accounts
SET credit_limit = credit_limit + 10000
WHERE tenant_id = 10 AND account_id = 1001;

-- Not committed yet.
```

**Session B:**

```sql
BEGIN;

UPDATE lesson_audit.accounts
SET credit_limit = credit_limit + 20000
WHERE tenant_id = 10 AND account_id = 1001;

COMMIT;
```

Session B blocks on A's row lock. Once A commits, PostgreSQL applies standard isolation/locking semantics; under `READ COMMITTED`, `credit_limit = credit_limit + 20000` re-evaluates against the newly committed row rather than silently clobbering A's increment from an old client read.

**Session A eventually commits:**

```sql
COMMIT;
```

### What Audits Must Reflect

Each **committed** `UPDATE` that modifies the row records an audit row whose `OLD` and `NEW` match the actual tuple versions seen by that statement. If a transaction aborts due to serialization failure or deadlock and rolls back, its audit row rolls back too.

### Never Guarantee Commit Order from `audit_id`

`audit_id` values can be assigned before commit; an older transaction may commit after another transaction with a higher `audit_id`. Relying solely on `audit_id` or `occurred_at` to assert "which independent transaction committed first" is unsafe.

## 52. Application-Layer Lost Updates

Audit triggers **do not stop** application code from reading a number, computing a total in Java, and issuing a stale absolute overwrite.

Example:

```text
A reads credit_limit = 700000
B reads credit_limit = 700000
A computes 710000, runs UPDATE SET credit_limit = 710000
B computes 720000, runs UPDATE SET credit_limit = 720000
```

Without optimistic locking/version checks or proper locking, A's change is logically lost. Auditing faithfully records:

```text
700000 -> 710000
710000 -> 720000
```

yet has no way to know B intended "+20000" rather than overwriting 710000.

### Solutions

- Use atomic SQL updates like `SET credit_limit = credit_limit + $1` where appropriate.
- Add `row_version` checks in `WHERE` for optimistic locking.
- Use `SELECT FOR UPDATE` or stricter isolation levels for complex workflows.
- Maintain concurrency tests and clear retry policies.

Audits help **detect** anomalies after the fact; they do not replace lost-update prevention.

## 53. Per-Entity Version Counters

Some designs add `row_version BIGINT NOT NULL DEFAULT 1` to the source table and increment it on business changes.

### Benefits

- Applications can run `UPDATE ... WHERE row_version = expected`.
- Audit snapshots capture before/after version numbers.
- Consecutive versions per entity can be verified directly.
- Distinguishes older vs. newer states even when global event IDs aren't strictly commit-ordered.

### Limits

Version counters do not protect audits if a privileged role edits rows directly or disables triggers. If incremented by application code instead of triggers/constraints, every write path must enforce it.

Do not add version counters to every table blindly; add them where a real concurrency contract needs them.

## 54. Transaction IDs Group Related Events

One transaction updates multiple accounts:

```sql
BEGIN;

SELECT set_config('app.actor_id', 'bulk-editor', true);

UPDATE lesson_audit.accounts
SET status = 'SUSPENDED'
WHERE tenant_id = 10
  AND status = 'ACTIVE';

COMMIT;
```

All audit rows emitted within that transaction share the same `txid_current()`. You can group by it:

```sql
SELECT
    transaction_id,
    count(*) AS events,
    min(occurred_at) AS first_event_time,
    max(occurred_at) AS last_event_time
FROM lesson_audit.account_audit
GROUP BY transaction_id
ORDER BY events DESC, transaction_id;
```

### Limits

A database `transaction_id` is not a **business request ID**: one HTTP request may span multiple transactions, or one transaction might batch unrelated operations. When request-to-audit traceability is needed, pass a trusted `request_id`/correlation ID alongside appropriate privacy controls.

Likewise, `transaction_id` is not a timestamp and should not be treated as a strict global commit-order integer across transactions.

## 55. Setting `actor_id` Safely in Applications

In the lab:

```sql
BEGIN;
SELECT set_config('app.actor_id', 'editor-42', true);
UPDATE lesson_audit.accounts ...;
COMMIT;
```

Backends can do the exact same thing with `SET LOCAL` or `set_config(..., true)` inside the transaction.

### Why `SET LOCAL` / Transaction-Local Settings?

With connection pooling, session-level settings leak from one request to the next unless reset. `SET LOCAL` or `set_config(..., true)` scopes the setting strictly to the current transaction.

### Crucial Trust Boundary

Custom GUCs like `app.actor_id` **can be set by any session able to run SQL**; they are not cryptographically signed identities verified by PostgreSQL.

If users have direct SQL access, never treat `app.actor_id` as tamper-proof attribution. Supplement with:

- Trusted backend authentication and authorization.
- Distinct DB role identities (noting shared pool limitations).
- Independent application/API request logs.
- Separate audit-service credentials.
- External append-only storage or cryptographic signing when compliance demands it.

## 56. `current_user` and `session_user` Differ from Business Actors

```sql
SELECT
    current_user,
    session_user,
    current_setting('app.actor_id', true) AS app_actor;
```

- `session_user` is normally the role that authenticated the connection.
- `current_user` reflects the active privilege-checking role (which shifts inside `SECURITY DEFINER` functions).
- `app.actor_id` is the application-supplied context string.

If all HTTP requests connect via a single shared `app_service` DB role, `session_user` cannot tell which end user clicked the button. Inside a `SECURITY DEFINER` trigger, `current_user` reflects the function owner, not even the app role.

### Metadata Design

You can record all relevant fields together:

- `database_session_user`.
- `application_actor_id`.
- `request_id`.
- `service_name`.
- `transaction_id`.

Always document clearly which fields are **database-authenticated** vs. **application-supplied** and each field's trust level.

## 57. JDBC: Setting the Actor in the Same Transaction

Java JDBC example:

```java
import java.math.BigDecimal;
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.SQLException;

public final class AccountRepository {
    public static void changeLimit(
            Connection conn,
            long authorizedTenantId,
            long accountId,
            BigDecimal newLimit,
            String authenticatedActor
    ) throws SQLException {
        boolean previousAutoCommit = conn.getAutoCommit();
        conn.setAutoCommit(false);

        try {
            try (PreparedStatement ps = conn.prepareStatement(
                    "SELECT set_config('app.actor_id', ?, true)"
            )) {
                ps.setString(1, authenticatedActor);
                ps.execute();
            }

            String updateSql = """
                UPDATE lesson_audit.accounts
                SET credit_limit = ?,
                    updated_at = clock_timestamp()
                WHERE tenant_id = ?
                  AND account_id = ?
                """;

            try (PreparedStatement ps = conn.prepareStatement(updateSql)) {
                ps.setBigDecimal(1, newLimit);
                ps.setLong(2, authorizedTenantId);
                ps.setLong(3, accountId);

                int changed = ps.executeUpdate();
                if (changed != 1) {
                    throw new SQLException(
                        "Account not found or not authorized"
                    );
                }
            }

            conn.commit();
        } catch (SQLException | RuntimeException ex) {
            conn.rollback();
            throw ex;
        } finally {
            conn.setAutoCommit(previousAutoCommit);
        }
    }
}
```

### What This Guarantees

`set_config(..., true)` and the `UPDATE` run inside **the same transaction** on **the same connection**, so the trigger reliably reads the transaction-scoped actor setting.

### What It Does Not Guarantee by Itself

- `authenticatedActor` must come from a verified authentication context, never blindly from a request body.
- `authorizedTenantId` must be authorized by the backend.
- End users with direct SQL access under the same DB role could still forge `app.actor_id`.
- Production pools require robust connection/error hygiene on failed transactions.
- Optimistic locking / version checks and idempotency keys are still separate concerns.

## 58. Spring: Transaction Context and Triggers

In Spring, a service can:

1. Start a transaction with `@Transactional`.
2. Call `SELECT set_config('app.actor_id', ?, true)` via `JdbcTemplate`.
3. Execute the `UPDATE` on the same transaction manager/datasource.
4. Commit or roll back at method exit.

Skeleton example:

```java
@Transactional
public void changeLimit(
        long authorizedTenantId,
        long accountId,
        BigDecimal newLimit,
        String actorId
) {
    jdbcTemplate.queryForObject(
        "SELECT set_config('app.actor_id', ?, true)",
        String.class,
        actorId
    );

    int changed = jdbcTemplate.update(
        """
        UPDATE lesson_audit.accounts
        SET credit_limit = ?,
            updated_at = clock_timestamp()
        WHERE tenant_id = ? AND account_id = ?
        """,
        newLimit,
        authorizedTenantId,
        accountId
    );

    if (changed != 1) {
        throw new IllegalStateException("Account not found");
    }
}
```

### Notes

This skeleton assumes configured `JdbcTemplate`, imports, and transaction management. `@Transactional` works only if Spring binds the exact same connection/transaction across both calls without opening nested/independent transactions.

On an unhandled exception triggering rollback, the transactional audit event rolls back with the `UPDATE`.

## 59. Do Not Let Applications Write Directly to the Audit Table

Ideally in production, the application role:

- Holds only needed DML privileges on `accounts`.
- Has **no direct `INSERT`/`UPDATE`/`DELETE`/`TRUNCATE` privileges** on `account_audit`.
- Does not own the schema or audit table.
- Cannot alter trigger functions or disable triggers.

Example DCL (**illustrative once an `app_writer` role exists**):

```sql
-- REVOKE ALL ON lesson_audit.account_audit FROM PUBLIC;
-- REVOKE ALL ON lesson_audit.account_audit FROM app_writer;
--
-- GRANT USAGE ON SCHEMA lesson_audit TO app_writer;
-- GRANT SELECT, INSERT, UPDATE, DELETE
--   ON lesson_audit.accounts TO app_writer;
```

### Why Apply `SECURITY DEFINER` Carefully?

When `app_writer` cannot insert directly into `account_audit`, `SECURITY DEFINER` lets the trigger run under its owner's privileges. Yet granting the owner overly broad permissions or leaving untrusted schemas on `search_path` opens privilege-escalation paths.

Never grant runtime roles ownership, DDL, or `SET ROLE` powers and then assume revoking direct table access on `account_audit` protects anything.

## 60. RLS on Both Source Tables and History Tables

In multi-tenant systems, `accounts` may use Row-Level Security; `account_audit` needs matching read-access policies too.

### Common Mistakes

- Enabling RLS on source tables while leaving audit tables unprotected.
- Admin reporting endpoints accidentally querying across tenants.
- Running application traffic as table owner or `BYPASSRLS`.
- `SECURITY DEFINER` helpers reading with owner rights in ways that bypass intended RLS filters.
- Trusting unvalidated user-supplied tenant IDs stored in custom session GUCs.

### Rule

Every history-lookup API must filter explicitly:

```sql
WHERE tenant_id = :authorized_tenant_id
  AND account_id = :requested_account_id
```

Here `:name` denotes application bind parameters, **not literal `psql` syntax**.

### Never Confuse Actor Identity with Authorization

A user may carry a valid actor ID while still being forbidden to read another account's history. Actor metadata handles **attribution**, not **authorization**.

## 61. `SECURITY DEFINER` and `search_path`

Our lab trigger function specifies:

```sql
SECURITY DEFINER
SET search_path = pg_catalog, pg_temp
```

and uses fully qualified names:

```sql
INSERT INTO lesson_audit.account_audit (...)
```

### Why?

A privileged routine referencing unqualified objects when untrusted schemas exist on `search_path` is vulnerable to **name-resolution hijacking**.

### Additional Hardening

- Make the function owner a minimal-privilege role rather than superuser.
- Restrict `CREATE` privileges on schemas strictly.
- Prevent writer roles from mutating audit rows directly.
- Schema-qualify any helper calls or keep resolution unambiguous.
- Never interpolate untrusted identifiers into dynamic SQL.
- Lock down `EXECUTE` and trigger DDL permissions.

`SECURITY DEFINER` is a powerful privilege boundary, never an unexamined default for every trigger.

## 62. Sensitive Data Inside Snapshots

`to_jsonb(OLD)` and `to_jsonb(NEW)` copy **every column** of the row. If the source table stores:

- Phone numbers, emails, physical addresses.
- Payment instruments.
- Password hashes.
- Tokens or secrets.
- Sensitive personal records.

then audit history retains **both old and new values** even after the source row erases or masks them.

### Safeguards

- **Data minimization:** audit only the columns required.
- Mask or redact sensitive fields before saving per policy.
- Strictly limit `SELECT` privileges on audit tables.
- Apply encryption at rest and proper key management.
- Enforce legally compliant retention and deletion policies.
- Never leak raw audit JSONB directly to clients or logs.
- Reconcile "right to erasure" obligations carefully against audit retention rules.

Audit tables must never turn into an ungoverned historical vault of secrets.

## 63. Column-Level History Instead of Full JSONB

If only `credit_limit` and `status` matter, you can model explicit typed columns:

```text
audit_id
account_id
tenant_id
old_credit_limit
new_credit_limit
old_status
new_status
actor_id
occurred_at
```

### Benefits

- Explicit types, easy indexing and filtering.
- Naturally excludes unneeded PII.
- Much smaller storage footprint than full-row JSONB on wide tables.

### Trade-Offs

- Adding audited columns requires table and trigger migrations.
- Easy to miss newly added source columns without schema coverage tests.
- Harder to share one generic audit table across heterogeneous source tables.

A hybrid approach stores typed metadata alongside JSONB containing **only an explicit allowlist of columns** instead of full rows.

## 64. Large Audit Tables: Storage, WAL, and TOAST

Each `UPDATE` may write:

```text
old snapshot JSONB
new snapshot JSONB
metadata columns
index entries
WAL records
```

On wide tables or large documents, JSONB spills to TOAST storage and generates heavy I/O and WAL. A table with 1 million rows updated frequently can generate tens of millions of audit rows rapidly.

### Optimization Levers

- Narrow audited fields.
- Skip no-op updates per policy.
- Index only actual audit lookup paths — never blindly index every JSONB key.
- Partition audit tables by time once volume and retention justify it.
- Benchmark storage/compression settings before tuning.
- Monitor autovacuum, WAL rate, replication lag, and disk usage.
- Alert on abnormal audit growth.

**Never sacrifice audit correctness for speed by silently disabling triggers under load**, unless the business explicitly approves an audited-gap procedure with provenance.

## 65. Indexing Audit Tables: Do Not Index Full JSONB by Default

Most common lookup query:

```sql
SELECT audit_id, operation, actor_id, occurred_at
FROM lesson_audit.account_audit
WHERE tenant_id = 10
  AND account_id = 1001
ORDER BY audit_id DESC
LIMIT 50;
```

The B-tree `(tenant_id, account_id, audit_id DESC)` handles this cleanly.

If filtering all events by actor is required:

```sql
SELECT *
FROM lesson_audit.account_audit
WHERE actor_id = 'editor-42'
ORDER BY occurred_at DESC;
```

consider a B-tree on `(actor_id, occurred_at DESC)` after measuring workload impact.

### When Is GIN on JSONB Appropriate?

If queries genuinely filter by arbitrary nested containment keys inside `old_row`/`new_row`, a GIN index helps — at significant size and write-amplification cost. Never add GIN indexes to both JSONB columns merely because their type is `jsonb`.

Also avoid indexing plaintext PII unnecessarily without clear authorization and operational need.

## 66. Time-Based Partitioning for Audit Logs

When logs grow quickly and obey fixed retention windows, partitioning by `occurred_at` (or another operational key) helps manage lifecycle.

### Benefits

- Clean retention enforcement by detaching/dropping expired partitions per policy.
- Partition pruning on time-bounded investigations.
- More manageable vacuum and index maintenance.

### Trade-Offs

- Partition keys interact with **`UNIQUE` and `PRIMARY KEY` constraints** on partitioned tables.
- Global uniqueness of `audit_id` alone does not automatically translate across every partitioning scheme.
- Partitioning by `occurred_at` uses trigger clock time, not commit time.
- Automation must pre-create upcoming partitions before each period begins.
- Partitions must never be dropped prior to retention deadlines.

Do not convert the simple lab table to a partitioned table prematurely; this section covers the architectural trade-offs.

## 67. Retention and History Deletion Policies

Audit logs may be kept for 90 days, 1 year, or much longer depending on business and regulatory needs; no single retention rule fits all systems.

### What Policy Must Specify

- Which data categories are stored.
- Retention period per category.
- Who may request and approve purges.
- How purges are logged and verified.
- How backups follow separate retention from live audit tables.
- How legal holds preserve exempted records.
- Ensuring APIs stop exposing records past access windows.

### Risks

Giving an auditor raw `DELETE` rights risks tampering; conversely, infinite retention violates data minimization rules. Prefer automated purge workflows with independent logging and separation of duties.

## 68. Application-Level Append-Only Is Not Tamper-Proof

Revoking `UPDATE` and `DELETE` on `account_audit` from regular roles helps, yet:

- Table owners and superusers still hold broad powers.
- Administrators can disable or drop triggers.
- Restoring backups replaces entire DB state.
- Compromised privileged credentials can alter policies or rows.

**Append-only for application roles** is practical defense-in-depth, not cryptographic immutability.

### When Stronger Tamper-Evidence Is Required

Consider:

- Streaming audit events to an external system with separate ownership/credentials.
- WORM / immutable object storage as compliance dictates.
- Digital signatures or hash chains with **external anchoring** and proper key management.
- Offloading and protecting DB server/DDL logs externally.
- Auditing privilege grants and configuration changes.

Hash chains stored **solely inside the same DB** can be recomputed by anyone controlling the database, so they cannot stop a malicious DB owner.

## 69. Auditing and Event-Driven Systems

Row audits reflect source table state; never dispatch HTTP calls, webhooks, or broker messages directly inside a trigger assuming transaction rollback can take them back.

### Transactional Outbox

A more reliable pattern:

```text
BEGIN
  UPDATE business table
  INSERT audit table (trigger)
  INSERT outbox event
COMMIT

Outbox publisher reads committed events
  -> publishes to broker
  -> consumer handles idempotently
```

If the transaction rolls back, transactional audit and outbox rows roll back cleanly. If commit succeeds while the publisher temporarily fails, the outbox safely retries later.

### Audit Events Differ from Business Events

`UPDATE status = 'PAID'` does not automatically prove a valid financial `PaymentCaptured` domain event occurred. Domain events carry validated business meaning and dedicated payload contracts.

## 70. Supplementing Audits with Logical Decoding / CDC

WAL-based CDC tracks committed changes via replication streams, useful when you need to:

- Sync search indexes or analytics warehouses.
- Stream changes to independent external storage.
- Cross-check for audit gaps outside row triggers.
- Order events along the server's commit stream.

### Operational Trade-Offs of CDC

- Stalled consumers hold back replication slots and risk filling WAL disks.
- Not all DDL changes appear automatically in expected row payloads.
- Replication credentials carry high privilege sensitivity.
- Schema evolution requires coordination.
- `DELETE` old-row capture requires appropriate `REPLICA IDENTITY` settings.
- Consumers must handle idempotency, ordering, and failovers.

CDC also does not authenticate application actors automatically; shared DB service roles still require trusted upstream attribution.

## 71. How This Differs from `pgAudit` and Server Logs

Row triggers answer: "What were row 1001's before/after values?" Statement-level audit extensions (`pgAudit`) and server logs answer: "Which role executed which `UPDATE`/`DDL`/`SELECT` command?" depending on configuration.

### When to Combine Them

- Need **before/after row values**: row audit trigger.
- Need **`SELECT`/read tracking**: row triggers do not fire on `SELECT`; rely on audit logs/extensions or application access logs.
- Need **DDL and privilege changes**: server logs, event triggers, and migration logs.
- Need **external evidence**: external append-only logging.

Never pitch row audit triggers as a complete solution for "log every read of sensitive records," since `SELECT` fires no table DML triggers.

## 72. Prerequisites for Replaying History

With a **complete event chain starting from a clean baseline**, successive `new_row` images let you trace past values.

However, accurately reconstructing state at time $T$ requires answering:

- Are you slicing by **event time** or **commit time**?
- Is ordering guaranteed globally or only per entity?
- Can an entity be `DELETE`d and re-`INSERT`ed under the same ID?
- Were any events dropped during migrations or replication?
- Did JSONB schemas evolve over time?
- Must state stay consistent across multi-entity transactions?

### Audit History vs. Point-in-Time Recovery (PITR)

Audit tables never replace WAL archiving and backups. To restore an entire database cleanly to point $T$, use managed backups and WAL PITR. Row audits primarily serve investigations and business history queries.

## 73. Adding Business Revision Numbers and Expected State

For stricter temporal chains, you can record:

```text
entity_id
row_version
old_row
new_row
actor
recorded_at
transaction_id
```

Events for the same entity can be checked against:

```text
new_version = old_version + 1
previous.new_row = next.old_row
```

If source writes enforce optimistic locking, stale concurrent updates fail cleanly, leaving only valid committed transitions in the audit log.

### When Is Even That Insufficient?

Per-row `row_version` tracks order **within one entity**, not across multiple entities globally. Multi-table point-in-time reconstruction still requires transaction/commit-order modeling.

## 74. Fault Injection to Verify Fail-Closed Auditing

Any system treating auditing as mandatory for commit should test what happens when audit insertion fails:

1. In staging, introduce a failing constraint or permission block on the audit insert.
2. Attempt a source `UPDATE`.
3. Verify the `UPDATE` fails and source state remains unchanged after rollback.
4. Confirm the API returns an error rather than false success.
5. Restore audit configuration and verify normal writes succeed again.

### Never Break Production to Test

Never revoke trigger owner rights or drop audit tables in production just to verify fail-closed behavior. Use staging or isolated test databases with controlled fault injection.

### Principle

If application code catches an audit error and proceeds to commit the source change anyway, it silently converts **mandatory auditing** into **best-effort logging** — a policy decision requiring business and security sign-off, never accidental exception swallowing.

## 75. Testing Race Conditions and Isolation Levels

Scenarios to run across at least two concurrent connections:

- Two `UPDATE`s on the same row where one holds a row lock blocking the other.
- One `UPDATE` committing while a second hits a serialization failure under `REPEATABLE READ` / `SERIALIZABLE`.
- Concurrent `DELETE` colliding with `UPDATE`.
- `UPDATE`s on distinct rows within the same tenant.
- Long-running transactions holding older snapshots while others commit.
- Bulk `UPDATE`s interleaved with single-row DML.

### Assertions

- Audit tables contain events exclusively from committed transactions.
- `OLD`/`NEW` match the exact row versions processed by each statement.
- Rolled-back transactions leave zero audit events.
- No source write succeeds without an audit row while triggers and grants are active.
- No cross-tenant audit leakage occurs.

Load tests must measure deadlocks, lock waits, WAL rate, p95 write latency, and audit growth — not just sequential single-session runs.

## 76. Property-Based Testing

Rather than checking only "500000 -> 700000", a randomized test harness can generate sequences of:

- Multiple `INSERT`s across valid tenant IDs.
- `UPDATE`s to `display_name`, `status`, and `credit_limit`.
- Selective `DELETE`s.
- No-op `UPDATE`s.
- Explicit rollbacks at random points.
- Constraint-violating statements.

After each committed transaction, assert:

1. All source constraints remain satisfied.
2. Every audit event obeys its `operation` shape rules.
3. Zero events survive from rolled-back transactions.
4. Live source state matches the latest committed audit snapshot within test scope.
5. All events belong strictly to the active test tenants.
6. Every application DML path is exercised.

### Why Property-Based Testing Helps

It exposes subtle combinations hard to think up by hand: no-ops immediately after real edits, delete-then-reinsert cycles, multi-row mutations inside one transaction, `NULL` edge cases, and schema-evolution mismatches.

Never run randomized property-based stress tests against production; run them in isolated environments with reproducible seeds.

## 77. Testing Audit Event JSON Shapes

Inspect snapshot shapes:

```sql
SELECT
    audit_id,
    operation,
    jsonb_typeof(old_row) AS old_json_type,
    jsonb_typeof(new_row) AS new_json_type,
    old_row IS NULL AS old_is_sql_null,
    new_row IS NULL AS new_is_sql_null
FROM lesson_audit.account_audit
ORDER BY audit_id;
```

With `to_jsonb(record)`, populated snapshots have type `'object'`, while non-applicable slots remain **SQL `NULL`** as enforced by the `CHECK` constraint.

### Do Not Confuse JSON `null` with SQL `NULL`

`old_row IS NULL` tests for SQL `NULL` on the column itself.

`old_row = 'null'::jsonb` is a JSONB scalar `null` stored inside a non-NULL column. The lab schema avoids storing `'null'::jsonb` for missing snapshots precisely to keep that distinction unambiguous.

## 78. Verifying `tenant_id` Consistency Inside JSONB Snapshots

For `INSERT` and `UPDATE` events, the metadata `tenant_id` should match `new_row`:

```sql
SELECT
    audit_id,
    tenant_id,
    new_row ->> 'tenant_id' AS tenant_in_snapshot
FROM lesson_audit.account_audit
WHERE new_row IS NOT NULL
  AND (
      new_row ->> 'tenant_id'
  ) IS DISTINCT FROM tenant_id::text;
```

For `DELETE`, compare against `old_row`:

```sql
SELECT audit_id, tenant_id
FROM lesson_audit.account_audit
WHERE operation = 'DELETE'
  AND (old_row ->> 'tenant_id')
      IS DISTINCT FROM tenant_id::text;
```

### Note

This checks internal consistency between metadata columns and JSONB payloads; it does not prove actor authenticity or authorization. If a compromised privileged user falsifies both columns identically, this query won't flag it — use independent provenance where required by your threat model.

## 79. Asserting Non-Empty Diffs on `UPDATE` Events via SQL

A `DO` block verifying no no-op `UPDATE` rows slipped into the audit table:

```sql
DO $$
DECLARE
    v_mismatch_count BIGINT;
BEGIN
    SELECT count(*)
    INTO v_mismatch_count
    FROM lesson_audit.account_audit
    WHERE operation = 'UPDATE'
      AND old_row IS NOT DISTINCT FROM new_row;

    IF v_mismatch_count <> 0 THEN
        RAISE EXCEPTION
            'Found % audit UPDATE events with no value change',
            v_mismatch_count;
    END IF;
END;
$$;
```

Under the lab's skip-no-op policy, no `UPDATE` event should have identical `old_row` and `new_row`.

### Policy May Differ

If a system deliberately audits every attempted `UPDATE` even when values remain equal, this assertion does not apply. Tests must verify **your declared system contract**, not impose one preference everywhere.

## 80. Monitoring Trigger Coverage and Audit Gaps

Key metrics to track:

| Metric | Why Track It |
|---|---|
| Audit event counts per table and operation | Spot sudden drops or spikes |
| Audit insert failures | Ensure source writes aren't failing or silently losing logs |
| Trigger enabled state | Catch unauthorized disabling or DDL drift |
| Source vs. latest-audit mismatches | Flag potential audit gaps |
| DML volume vs. audit volume | Detect unexpected event-ratio anomalies |
| Disk and WAL growth | Capacity forecasting |
| p95/p99 write latency | Watch trigger overhead |
| Replication/CDC lag | Monitor external reconciliation pipelines |
| Audit query latency | Keep investigations responsive |
| Unauthorized access attempts | Enforce read/write access controls |

### Account for Expected Differences

Because the lab skips no-ops, the count of `UPDATE` SQL statements may exceed `UPDATE` audit rows; conversely, one multi-row `UPDATE` emits many audit rows. Never expect a 1:1 ratio between SQL statement count and audit row count — interpret metrics through your row-vs.-statement model and no-op policy.

## 81. Soft Delete vs. Hard Delete

A system might set `status = 'CLOSED'` instead of executing a physical `DELETE`:

```sql
UPDATE lesson_audit.accounts
SET status = 'CLOSED',
    updated_at = clock_timestamp()
WHERE tenant_id = 10
  AND account_id = 1001;
```

Under our trigger, this emits an **`UPDATE`** event, not a `DELETE`. The new snapshot shows `status = 'CLOSED'`, and the row remains in `accounts`.

### Why Shouldn't This Be Rewritten as a `DELETE` Audit Event?

`TG_OP` records the actual SQL operation executed. If you want to record domain milestones like `AccountClosed`, store an explicit `business_event_type` or domain event rather than pretending a physical `DELETE` happened.

If business rules later allow reopening a `CLOSED` account back to `ACTIVE`, the history shows a coherent chain of `UPDATE` transitions.

## 82. Using Views or `INSTEAD OF` Triggers

Applications may expose a restricted view:

```sql
CREATE OR REPLACE VIEW lesson_audit.public_accounts AS
SELECT
    account_id,
    tenant_id,
    display_name,
    status
FROM lesson_audit.accounts;
```

When writes through that view perform **`INSERT`/`UPDATE`/`DELETE` on the underlying base table**, the base table's row trigger captures those changes cleanly.

### Where Complexity Creeps In

Complex views may rely on `INSTEAD OF` triggers or rewrite rules to translate writes to underlying tables. In those cases, check:

- Can any write modify only auxiliary tables without touching `accounts`?
- Can one view command execute multiple base-table DML operations?
- Could one user request emit multiple audit events?
- How do `OLD`/`NEW` on the view differ from full base-table snapshots?

**Never attach audit triggers solely to a view** while direct writes to base tables remain possible. Always put row auditing on the **authoritative base tables** and inspect all entry points.

## 83. Temporal Query: "State at Point in Time T"

Illustrative query returning the latest snapshot with `occurred_at <= T`:

```sql
WITH candidates AS (
    SELECT
        audit_id,
        tenant_id,
        account_id,
        operation,
        new_row,
        occurred_at,
        row_number() OVER (
            PARTITION BY tenant_id, account_id
            ORDER BY occurred_at DESC, audit_id DESC
        ) AS rn
    FROM lesson_audit.account_audit
    WHERE occurred_at <=
        TIMESTAMPTZ '2026-11-01 00:00:00+07'
)
SELECT
    tenant_id,
    account_id,
    new_row,
    occurred_at
FROM candidates
WHERE rn = 1
  AND operation <> 'DELETE';
```

### Important: This Is Only an Approximation by Event Timestamp

`occurred_at` records trigger invocation time, not commit time. A long transaction can generate an audit row before $T$ yet commit **after $T$**, meaning this query does not reconstruct the exact transactionally visible database snapshot at commit time $T$.

For strict **system-time temporal queries** under concurrency, build a commit-aware temporal model, CDC pipeline, or PITR workflow. Never cite this simple timestamp query as legal proof of exact committed state at an instant.

## 84. Auditing and Idempotent Requests

Suppose an HTTP call times out and the client retries, executing:

```sql
UPDATE lesson_audit.accounts
SET credit_limit = credit_limit + 10000
WHERE account_id = 1001;
```

twice. Auditing records **two `UPDATE` events**, and the credit limit rises twice.

### Root Cause

The audit trigger worked properly: two committed changes occurred. The real gap is **lack of application-level idempotency** on the business command.

### Mitigation

- Require an HTTP request / idempotency key.
- Persist idempotency state atomically inside the same transaction.
- For versioned updates, enforce `WHERE row_version = expected`.
- Never merge two identical audit entries into one to hide an unguarded retry bug.

Auditing reveals duplicate retries; it does not prevent them.

## 85. Quick Diagnostic Query Toolkit

### A — Event Counts by Operation

```sql
SELECT
    tenant_id,
    operation,
    count(*) AS events
FROM lesson_audit.account_audit
GROUP BY tenant_id, operation
ORDER BY tenant_id, operation;
```

### B — Full Lifecycle of One Entity

```sql
SELECT
    audit_id,
    operation,
    actor_id,
    old_row ->> 'status' AS old_status,
    new_row ->> 'status' AS new_status,
    occurred_at
FROM lesson_audit.account_audit
WHERE tenant_id = 10
  AND account_id = 1001
ORDER BY audit_id;
```

### C — Any Malformed Event Shapes?

```sql
SELECT audit_id, operation, old_row, new_row
FROM lesson_audit.account_audit
WHERE
    (operation = 'INSERT'
     AND (old_row IS NOT NULL OR new_row IS NULL))
    OR
    (operation = 'UPDATE'
     AND (old_row IS NULL OR new_row IS NULL))
    OR
    (operation = 'DELETE'
     AND (old_row IS NULL OR new_row IS NOT NULL));
```

In the lab, the `CHECK` constraint already prevents malformed inserts during normal operation. Still, this check helps when validating imported/migrated audit tables — though it cannot prevent table-owner bypasses.

### D — Any No-Op `UPDATE` Audit Rows?

```sql
SELECT audit_id, account_id
FROM lesson_audit.account_audit
WHERE operation = 'UPDATE'
  AND old_row IS NOT DISTINCT FROM new_row;
```

Under lab policy, expect zero rows.

### E — Are Triggers Present and Enabled?

```sql
SELECT
    tgname,
    tgenabled,
    pg_get_triggerdef(oid, true) AS trigger_ddl
FROM pg_catalog.pg_trigger
WHERE tgrelid = 'lesson_audit.accounts'::regclass
  AND NOT tgisinternal
ORDER BY tgname;
```

### F — Activity History for One Actor

```sql
SELECT
    audit_id,
    tenant_id,
    account_id,
    operation,
    occurred_at
FROM lesson_audit.account_audit
WHERE actor_id = 'editor-42'
ORDER BY occurred_at DESC, audit_id DESC
LIMIT 100;
```

These queries are **investigative tools**, not unassailable completeness proofs if privileged roles could have modified or purged rows.

## 86. Runbook When Missing Audit Events Are Suspected

1. Record the affected table, entity ID, tenant, time range, and observed symptom.
2. Check `pg_trigger`: does the trigger exist, is it enabled, and does its definition match expectations?
3. Inspect all DML paths: `UPDATE`, `DELETE`, `TRUNCATE`, `UPSERT`, `MERGE`, `COPY`, partition maintenance, and direct admin scripts.
4. Verify audit rollout/baseline timestamps and migration history.
5. Check server logs, DDL logs, and CDC streams if available.
6. Check whether any role/owner could have disabled/dropped triggers or written around them.
7. Reconcile current source rows against latest audit events inside a consistent snapshot.
8. Separate intentional policy-skipped no-ops from genuinely missing changes.
9. Document the uncertain time window and impacted records.
10. Recover only from verified evidence; where prior values are unrecoverable, explicitly mark the gap and record a correction entry with clear provenance.

### Never "Repair History" by Fabricating Data

If you only know the current limit is 700000 without knowing its prior value, never fabricate a fake row `"500000 -> 700000 by editor-X"` to fill the hole. A credible audit trail supports marking state as **unknown** or **reconstructed from evidence** rather than presenting guesses as fact.

## 87. Runbook When Writes Slow Down After Enabling Auditing

1. Compare p50/p95/p99 `INSERT`/`UPDATE`/`DELETE` latency before vs. after rollout.
2. Check event frequency and average byte size of before/after snapshots.
3. Review index count and index write amplification on the audit table.
4. Measure WAL volume, disk throughput, checkpoints, and replication lag.
5. Inspect wide/TOAST columns, JSONB serialization overhead, and trigger execution time.
6. Check lock contention on indexes, partitions, or audit inserts.
7. Evaluate statement-level transition tables if bulk workloads and semantics allow.
8. Consider auditing fewer columns, skipping no-ops, batching strategies, or alternative projections.
9. Never drop production auditing without formal policy approval.
10. Re-test correctness and permissions after every performance optimization.

### Don't Optimize Only the Trigger Function Body

A five-line trigger function can still generate tens of megabytes of audit WAL per batch. The real bottlenecks live across **storage, indexing, transactions, and replication**, not just PL/pgSQL execution time.

## 88. Architecture Decision Matrix

| Requirement | Typical Best Fit | Limitations |
|---|---|---|
| Store `OLD`/`NEW` for committed DML | `AFTER ROW` audit trigger | Misses rollbacks and `SELECT` |
| Huge bulk `UPDATE`s needing set processing | `AFTER STATEMENT` + transition tables | Trigger type and key-join restrictions |
| Block invalid writes before persistence | `BEFORE` trigger + constraints | Does not replace post-write auditing |
| Emit business events to brokers | Transactional outbox | Needs publisher and idempotent consumers |
| Record SQL statements / DDL / reads | Server logs / `pgAudit` / event triggers | Lacks structured before/after row snapshots |
| Stream changes for external data pipelines | Logical decoding / CDC | Requires replication ops and slot monitoring |
| Track effective business validity periods | Versioned / temporal schema | Requires explicit valid-time and system-time semantics |
| Proof immune to DB admin tampering | Independent external signed/anchored log | Added security and operational cost |
| Track only current live state | Normal typed table | No historical trail |

No single tool fits every problem. Always start by asking: **"What must we prove, and to whom?"** before choosing an implementation.

## Conclusion

**Trigger-based history auditing in PostgreSQL is a practical way to capture before-and-after row data atomically inside the source transaction.** With `AFTER INSERT OR UPDATE OR DELETE FOR EACH ROW`, triggers use `TG_OP`, `OLD`, and `NEW` to log `jsonb` snapshots along with entity keys, tenant scope, actor context, transaction ID, and timestamps.

To **verify correctness**, checking that a trigger row exists is never enough. Define clear invariants and test `INSERT`/`UPDATE`/`DELETE`, no-ops, multi-row statements, rollbacks, constraint failures, and reconcile `old_row`/`new_row` against real source states. When analyzing event streams, keep **event time**, **transaction time**, **commit order**, and **identity sequence order** distinct — a higher `audit_id` never guarantees a later commit.

Trigger auditing also has explicit boundaries: **it does not preserve rolled-back transactions**, does not log `SELECT` reads, does not generate per-row `DELETE` rows for `TRUNCATE`, and can be bypassed via high privileges, replication modes, or DDL. When compliance demands protection against DBA tampering or tracking failed attempts, combine server logs, CDC, and a protected external audit store.

Finally, protect audit data like sensitive production data: minimize or redact PII, restrict delete/modify rights, harden `SECURITY DEFINER`/`search_path`/RLS, scope connection-pool context carefully, monitor WAL/latency impact, and enforce clean retention policies. A valuable audit trail is **semantically accurate, testable, transparent about its boundaries, and consistently operated** — never just a table holding a few JSONB logs.
