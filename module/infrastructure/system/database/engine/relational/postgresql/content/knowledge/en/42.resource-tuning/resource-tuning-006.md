# I/O Cost, Storage Devices, and Related Parameters in PostgreSQL

I/O (input/output) is one of the decisive factors in PostgreSQL performance. When a query is slow, the cause may lie in CPU, query plan, memory, locks, or storage. A server with spare CPU yet high storage latency can still be slow because backends must wait to read pages, write WAL, flush data, or create temporary files.

Optimizing I/O is not simply picking the disk with the highest IOPS or raising a cache parameter. You need to understand the actual workload, read/write operation types, sequential vs. random access patterns, latency, throughput, queue depth, durability, and how PostgreSQL uses memory/WAL.

Four hardware metrics to distinguish:

- **Latency**: time to complete a single I/O operation.
- **IOPS**: number of I/O operations per second.
- **Throughput**: amount of data transferred per second, typically measured in MB/s or GB/s.
- **Queue depth**: number of I/O requests pending or being processed concurrently.

PostgreSQL also has multiple buffering layers and write mechanisms: shared buffers, OS page cache, WAL buffers, background writer, checkpointer, vacuum, and temporary files. A configuration change may reduce I/O at one layer while increasing pressure at another.

~~~mermaid
flowchart TD
    A["SQL workload"] --> B["Planner: choose access path"]
    B --> C["PostgreSQL shared buffers"]
    C -->|"Cache hit"| D["Return data from memory"]
    C -->|"Cache miss"| E["OS / storage read"]
    F["INSERT / UPDATE / DELETE"] --> G["WAL buffers"]
    G --> H["WAL write + flush"]
    F --> I["Dirty data pages"]
    I --> J["Background writer / checkpointer"]
    J --> K["Data storage"]
    E --> K
    L["Sort / hash / temp objects"] --> M["Temporary files"]
    M --> K
~~~

This lesson belongs to the **Resource Tuning** chapter of the **Database Engine Relational PostgreSQL** module. We will explore storage device characteristics, the I/O cost model, caching, WAL/checkpoints, vacuum, temporary files, related parameters, and how to measure performance before changing configuration.

## 2. What Is Database I/O?

I/O is the exchange of data between PostgreSQL, memory, and storage devices. In practice, a single transaction can trigger multiple types of I/O:

- Reading data pages to locate rows.
- Reading index pages to identify row locations.
- Writing WAL records before corresponding data pages are written.
- Flushing WAL to satisfy durability.
- Writing dirty data pages via checkpoints/background writer.
- Reading or writing temporary files when sorts/hashes exceed memory.
- Reading metadata, catalogs, and relation files.
- Reading/writing archived WAL or backup files via external tools.

Not every SQL operation directly accesses disk. If a page is already in shared buffers or the OS page cache, the read can be served from memory. However, a cache hit in PostgreSQL and a cache hit in the OS are two different concepts.

### Simplified Read Path

~~~text
Query executor
     |
     v
Shared buffers
     |
     +-- Page hit --> use page in memory
     |
     +-- Page miss
            |
            v
        OS page cache
            |
            +-- OS cache hit --> return page
            |
            +-- OS cache miss --> storage device
~~~

### Simplified Write Path

~~~text
Transaction modifies data
          |
          +--> WAL record in WAL buffers
          |         |
          |         v
          |      WAL write/flush
          |
          +--> Dirty data page in shared buffers
                    |
                    v
             Background writer / checkpoint
                    |
                    v
               Data files
~~~

WAL must be durably written before the corresponding data page according to the write-ahead logging rule. This allows PostgreSQL to recover changes after a crash.

## 3. Four Storage Device Metrics

### Latency

Latency is the time from submitting an I/O request to receiving the result. For databases, low latency is often critical because many queries must wait on sequential small reads.

For example, an index lookup may need to read a root page, an internal page, then a leaf page, and finally a data page. If each read has to go down to storage, total latency can rise substantially.

Latency should be examined by percentile:

- p50: median.
- p95: 95% of operations have latency no higher than this value.
- p99: 99% of operations have latency no higher than this value.
- Maximum: highest observed value, often sensitive to outliers.

Average latency can hide spikes. A system with a low average yet very high p99 can still cause application timeouts.

### IOPS

IOPS measures I/O operations per second. IOPS depends on request size, read/write mix, random/sequential pattern, and device limits.

A volume advertised at 50,000 IOPS does not mean PostgreSQL will always achieve 50,000 IOPS. Bottlenecks may also exist in:

- Volume throughput.
- Queue depth.
- Host CPU.
- Network path to storage.
- Hypervisor or cloud throttling.
- Filesystem.
- Number of backends generating I/O.
- Block size and read/write mix.

### Throughput

Throughput measures the amount of data transferred per unit of time. A sequential scan workload may require high throughput, whereas OLTP index lookups are usually sensitive to latency and random IOPS.

IOPS and throughput are related via request size:

\[
Throughput \approx IOPS \times Average\ I/O\ size
\]

For example, 10,000 IOPS with an average 16 KiB request size corresponds to roughly 156 MiB/s before overhead. This is only a unit conversion, not a device performance guarantee.

### Queue Depth

Queue depth is the number of I/O requests waiting or in flight. Increasing queue depth can help devices leverage parallelism, but an overly deep queue can increase latency.

Do not optimize solely for maximum IOPS. For OLTP databases, consistent latency and low tail latency are usually more important than peak throughput.

## 4. Random I/O vs. Sequential I/O

**Random I/O** accesses blocks at non-contiguous locations. Index lookups, nested-loop joins, and many OLTP operations generate random reads/writes.

**Sequential I/O** accesses contiguous or nearly contiguous blocks. Sequential scans, backup streams, and certain bulk operations generate sequential access patterns.

| Characteristic | Random I/O | Sequential I/O |
| --- | --- | --- |
| Access | Scattered blocks | Contiguous blocks |
| Critical metric | Latency and IOPS | Throughput |
| Example | Index lookup, point lookup | Sequential scan, backup |
| HDD | Heavily impacted by seek | Can achieve better throughput than random |
| SSD/NVMe | Generally handles better than HDD | High bandwidth |

SSDs do not have mechanical seeks like HDDs, yet random I/O still carries controller, firmware, flash translation layer, and queueing overhead. Do not treat random I/O as free.

### A Single Query Can Use Both

For example, an index-filtered query may read index pages randomly and then access scattered heap pages. If the condition selects many rows, the planner may choose a bitmap heap scan to group heap blocks and improve locality.

A sequential scan is not inherently bad. If a query needs most of a table, sequential reading can be faster and less expensive than thousands of index lookups.

## 5. Types of Storage Devices

### HDD

HDDs use spinning platters and mechanical read/write heads. Characteristics:

- Cost per GB is usually low.
- Sequential throughput can suit archiving or backups.
- Random I/O latency is higher than SSD due to seek/rotation.
- Performance depends on rotational speed, cache, controller, and workload.

HDDs are usually not a good choice for OLTP workloads with heavy random reads/writes requiring low latency.

### SATA SSD

SATA SSDs eliminate mechanical seeks and usually improve random I/O dramatically over HDDs. The SATA interface has a lower throughput ceiling than modern NVMe.

Can be suitable for moderate workloads or budget-constrained environments.

### NVMe SSD

NVMe uses PCIe and a protocol optimized for flash devices. Common characteristics:

- Low latency.
- Multiple queues and deep queue depths.
- High IOPS and throughput.
- Well-suited for database workloads with heavy random I/O.

Evaluate endurance, power-loss protection, firmware, thermal throttling, and sustained write performance.

### SAN and Network Block Storage

SAN or network block storage can provide shared or centrally managed volumes. Performance depends on:

- Network bandwidth and latency.
- Storage controller.
- Multipathing.
- QoS/throttling.
- Cache policy.
- Shared contention.
- Failure domain.

A powerful storage array can still be slow if multiple tenants or volumes compete for resources.

### Cloud Block Storage

Cloud volumes typically have separate IOPS and throughput limits, sometimes tied to volume size or instance type. Check:

- Baseline and burst performance.
- Provisioned IOPS.
- Throughput cap.
- Instance-level bandwidth.
- Queue length and burst credits.
- Availability zone latency.
- Snapshot/backup impact.
- Durability guarantees.

Do not take maximum marketing numbers as real-world expectations. Benchmark on the exact instance, volume type, filesystem, and workload.

## 6. Choosing Storage by Workload

| Workload | Primary Need | Notes |
| --- | --- | --- |
| OLTP with many point lookups | Low latency, random IOPS | NVMe or consistent-performance SSD |
| Data warehouse | Throughput, parallel reads | Sequential bandwidth and concurrency |
| Batch ETL | Throughput and temporary I/O | Temp storage, memory, parallelism |
| WAL-heavy workload | Low-latency durable writes | WAL device, fsync latency, power-loss protection |
| Backup/archive | Capacity and sequential throughput | Cheaper storage if restore time meets SLA |
| Mixed workload | Balanced read/write/latency | Benchmark against real workload |

Do not pick storage solely by capacity. Two 1 TB volumes can differ vastly in IOPS, throughput, latency, durability, and sustained performance.

## 7. PostgreSQL Storage Layout

A PostgreSQL cluster typically includes:

- Data directory: relation files, catalogs, control files, and configuration.
- WAL directory: defaults to the `pg_wal` directory inside the data directory.
- Temporary files: typically in the data directory or configured tablespaces.
- Tablespaces: map relations to other storage locations.
- Archive destination: where archived WAL is stored, typically managed by `archive_command` or an archive module.
- Backup destination: where base backups and backup artifacts are stored.

### Should You Separate WAL and Data onto Different Devices?

Separating WAL and data can be beneficial when:

- WAL write latency is a clear bottleneck.
- Data workloads generate heavy random I/O concurrently with WAL flushes.
- A dedicated device with appropriate durability and performance is available.
- The storage path is genuinely independent.

However, if both volumes share the same controller, network, or physical storage pool, the benefit may be small. Separating volumes also increases operational, capacity planning, and recovery complexity.

### Should You Separate Temporary Files?

A dedicated tablespace for temporary objects can isolate temp I/O from data files. However, if the temp workload is huge, the separate device can still saturate. Measure temp bytes and latency before deciding.

### Tablespaces

You can create a tablespace on a path accessible to the PostgreSQL service account:

~~~sql
CREATE TABLESPACE fast_data
LOCATION '/srv/postgresql/fast_data';
~~~

Then create a table/index in the tablespace:

~~~sql
CREATE TABLE orders_archive (
    order_id bigint,
    created_at timestamptz,
    total_amount numeric(12,2)
) TABLESPACE fast_data;
~~~

A tablespace only changes where a relation is stored. It does not automatically stripe a single table across multiple devices and does not guarantee performance on its own. The path must be prepared with proper permissions and included in the backup/restore plan.

## 8. Durability and Storage Devices

PostgreSQL relies on the OS and storage to execute writes/flushes/syncs. If a device or controller reports a flush complete when data is not actually persisted, the database can lose data on power loss.

Factors to evaluate:

- Power-loss protection on SSDs/controllers.
- Battery-backed or flash-backed write cache.
- Write-through vs. write-back cache policy.
- Filesystem and mount options.
- Virtualization/storage layer.
- Cloud volume durability guarantees.
- Actual `fsync`/flush behavior.
- Backup and recovery tests.

Do not disable durability settings to improve benchmark scores. A faster benchmark that fails to protect data after a crash is not a valid production optimization.

## 9. fsync and full_page_writes

Two core settings:

~~~conf
fsync = on
full_page_writes = on
~~~

### fsync

When enabled, PostgreSQL instructs the OS/storage to flush data as needed to ensure durability via supported mechanisms. Disabling `fsync` can cause data loss or corruption after a crash/power loss.

### full_page_writes

When enabled, PostgreSQL writes a full-page image to WAL under necessary conditions after a checkpoint, enabling recovery from torn pages.

Disabling `full_page_writes` can increase corruption risk after a crash if storage does not guarantee atomic page writes.

### synchronous_commit

~~~conf
synchronous_commit = on
~~~

This setting controls when COMMIT returns relative to WAL flush. It affects durability of committed transactions, not directly whether data pages have been written to heap files yet.

With asynchronous replication, `synchronous_commit=on` still ensures local WAL flush per configuration, without waiting for remote standby confirmation. With synchronous replication, it can wait for standbys per `synchronous_standby_names`.

Do not confuse `synchronous_commit` with synchronous replication or with `fsync`.

## 10. WAL and I/O

Every data-modifying transaction generates WAL records. WAL is a write-ahead log: WAL must be written before the corresponding data pages.

WAL workload typically includes:

- Writing WAL buffers to WAL segments.
- Flushing WAL on commit or as needed.
- Writing full-page images.
- WAL writes from bulk loads/index builds.
- Archiving WAL.
- Streaming replication.
- Reading WAL during recovery/standby replay.

### wal_buffers

~~~conf
wal_buffers = -1
~~~

A value of `-1` lets PostgreSQL auto-size WAL buffers based on version/configuration. Manual tuning is usually unnecessary without evidence of WAL buffer pressure.

### wal_compression

~~~conf
wal_compression = on
~~~

Can compress full-page images in WAL on supported versions. Compression reduces WAL bytes written/read at the cost of extra CPU. Benchmark against your CPU vs. storage bottleneck balance.

### wal_sync_method

This parameter selects the WAL synchronization method among choices supported on the platform. The right value depends on OS/filesystem/storage. Do not change it solely based on a blog benchmark; check OS-specific documentation and measure `fsync` latency.

### WAL and Dedicated Storage

WAL has a write pattern distinct from data files: append-oriented and sensitive to flush latency. A dedicated device can help if data I/O causes contention, but only when that device is genuinely independent and has proper durability.

## 11. Checkpoints and Write I/O

Checkpoints write dirty buffers to data files and record a checkpoint record in WAL. Checkpoints that occur too frequently can create write pressure; checkpoints that are too infrequent can increase WAL replay time during crash recovery.

Commonly tuned parameters:

~~~conf
checkpoint_timeout = '15min'
max_wal_size = '4GB'
min_wal_size = '1GB'
checkpoint_completion_target = 0.9
log_checkpoints = on
~~~

These values are examples only. Size them based on WAL generation rate, disk capacity, replication slots, archiving, and recovery objectives.

### checkpoint_timeout

Maximum time between timed checkpoints. Increasing it can reduce timed checkpoints while potentially increasing the amount of WAL to replay after a crash.

### max_wal_size

Soft threshold controlling when PostgreSQL triggers a checkpoint due to WAL growth. This is not a hard cap on the `pg_wal` directory. Replication slots or archive failures can push WAL well past this threshold.

### checkpoint_completion_target

Controls the target fraction of the checkpoint interval over which checkpoint writes are spread. Higher values smooth burst I/O, provided storage has enough throughput to finish on time.

### log_checkpoints

Enable to log checkpoint reason, duration, buffers written, and related statistics. Use this log to tell whether checkpoints are timed or requested.

## 12. Background Writer

The background writer writes out some dirty buffers before backends need to reuse them. Its goal is to reduce how often backends must write pages themselves during query execution.

Some parameters:

~~~conf
bgwriter_delay = '200ms'
bgwriter_lru_maxpages = 100
bgwriter_lru_multiplier = 2.0
~~~

General meaning:

- `bgwriter_delay`: pause between activity rounds.
- `bgwriter_lru_maxpages`: maximum pages the background writer attempts to write per round.
- `bgwriter_lru_multiplier`: multiplier adjusting pages cleaned based on recent demand.

The background writer does not replace the checkpointer. It helps keep clean buffers available; checkpoints are still responsible for writing required dirty buffers per the checkpoint process.

Raising `bgwriter_lru_maxpages` can increase background write I/O. If storage is already saturated, raising it can worsen contention.

## 13. Cache: shared_buffers

`shared_buffers` is the shared memory region PostgreSQL uses to cache data pages.

Example:

~~~conf
shared_buffers = '8GB'
~~~

This is an illustrative value only. A common starting point mentioned in PostgreSQL documentation is roughly 25% of RAM for a dedicated database server, though workload, RAM, OS cache, connection count, and other memory consumers can make the optimal value quite different.

### Is Raising shared_buffers Always Better?

No. When raising `shared_buffers`:

- PostgreSQL can retain more data pages.
- Hit ratio in shared buffers may rise.
- Memory left for the OS page cache decreases.
- Checkpoints/background writer may manage more dirty buffers.
- Shared memory footprint grows.
- Other workloads may run short of memory.

Measure buffer hits/reads, OS cache behavior, memory pressure, and latency. Do not optimize a single cache hit ratio number in isolation.

### shared_buffers Is Not Total PostgreSQL Memory

PostgreSQL also consumes memory for:

- `work_mem` for sort/hash operations.
- `maintenance_work_mem`.
- `temp_buffers`.
- Backend process overhead.
- `wal_buffers`.
- Parallel workers.
- Extensions and shared memory structures.

Calculate total memory under peak concurrency rather than looking only at `shared_buffers`.

## 14. OS Page Cache

PostgreSQL normally relies on the operating system's filesystem cache alongside shared buffers. When PostgreSQL reads a page from a file, that page may already sit in the OS page cache even if absent from shared buffers.

Therefore:

- `pg_stat_database.blks_read` does not necessarily represent physical disk reads.
- `EXPLAIN BUFFERS` `read` means the page was read into shared buffers, not proof that the physical device was hit.
- OS metrics are needed to confirm physical storage I/O.

Do not conclude that a cache miss in PostgreSQL equals a physical disk read.

### Memory Pressure

If the OS constantly reclaims page cache or swaps, query latency can rise. Production database servers should control swap behavior, memory overcommit, and co-located processes per OS policy.

## 15. effective_cache_size

~~~conf
effective_cache_size = '24GB'
~~~

`effective_cache_size` estimates how much cache is available to a query, including what PostgreSQL expects to utilize from shared buffers and the OS page cache. It **does not allocate memory** and is not a memory limit.

The planner uses this estimate when evaluating how likely an index access is to find pages in cache.

If set too low, the planner may cost index scans as more expensive than reality. If set too high, the planner may assume more cache hits than reality and pick an unsuitable index plan.

Set it according to real RAM, `shared_buffers`, remaining OS page cache, and competing workloads. It is a planner hint, not a measured cache size.

## 16. Planner Cost: seq_page_cost and random_page_cost

The planner uses cost units to compare plans. Two important parameters:

~~~conf
seq_page_cost = 1.0
random_page_cost = 4.0
~~~

These are common example defaults; actual defaults can vary by version/distribution or configuration.

- `seq_page_cost`: relative cost of a sequential page read.
- `random_page_cost`: relative cost of a random page read.

These are relative cost units in the planner model, not milliseconds or actual IOPS.

### When to Tune random_page_cost?

SSDs/NVMe can make random reads relatively cheaper compared to sequential reads because there is no mechanical seek. You can consider lowering `random_page_cost` if benchmarks show the planner overestimating random index access cost.

However, lowering it too far can cause the planner to pick an index scan for a query reading most of a table, generating excessive random I/O and performing worse than a sequential scan.

### Do Not Tune Just One Parameter

The planner also uses:

- `cpu_tuple_cost`.
- `cpu_index_tuple_cost`.
- `cpu_operator_cost`.
- Parallel setup/tuple costs.
- `effective_cache_size`.
- Selectivity/cardinality statistics.
- Correlation and index properties.

If a plan is wrong, check statistics, indexes, data distribution, and `EXPLAIN` before changing cost constants.

## 17. effective_io_concurrency

Parameter:

~~~conf
effective_io_concurrency = 100
~~~

It tells PostgreSQL the level of I/O concurrency useful for certain operations, notably bitmap heap scans and prefetching on storage systems supporting suitable asynchronous I/O.

The right value depends on storage and platform. Single HDDs, SSDs, RAID arrays, SANs, and cloud volumes behave differently.

Raising it can improve throughput when the device handles parallelism well, but can also increase queueing or contention. Benchmark using query plans containing bitmap heap scans and realistic workloads.

### maintenance_io_concurrency

On supported versions, `maintenance_io_concurrency` controls concurrency for certain maintenance operations such as vacuum. It can help leverage parallel storage during maintenance, subject to version and device type.

Do not assume both parameters should have the same value; query and maintenance workloads can differ.

## 18. work_mem and Temporary Files

`work_mem` is the base amount of memory a query operation such as sort or hash can use before spilling to temporary files.

Example:

~~~conf
work_mem = '16MB'
hash_mem_multiplier = 2.0
temp_file_limit = '10GB'
~~~

Values are illustrative only.

### work_mem Is Not a Per-Connection Memory Limit

A single query can have multiple sort/hash nodes, multiple parallel workers, and many concurrent sessions. Actual total memory can be a large multiple of `work_mem`.

Increasing `work_mem` can reduce temporary I/O yet cause memory exhaustion under high concurrency.

### Signs of Spilling

- `EXPLAIN ANALYZE` shows sort method `external merge` using disk.
- A Hash node reports `Batches` greater than 1, indicating spilling.
- `pg_stat_database.temp_files` and `temp_bytes` increase.
- Logs record temporary files if `log_temp_files` is enabled.

### temp_file_limit

Limits total temporary file space a process can use per PostgreSQL semantics. Exceeding the limit can abort the query. This is a disk-protection guardrail, not a substitute for query/memory tuning.

### log_temp_files

Example:

~~~conf
log_temp_files = '64MB'
~~~

Logs temporary files reaching the threshold size. Set an appropriate threshold to catch large spills without flooding logs.

## 19. maintenance_work_mem and Vacuum

`maintenance_work_mem` is memory allocated to maintenance operations like VACUUM and CREATE INDEX within operation/version limits.

Example:

~~~conf
maintenance_work_mem = '1GB'
autovacuum_work_mem = '256MB'
~~~

Actual capacity planning must count concurrent maintenance workers. Autovacuum can run multiple workers; total memory can be much larger when multiplied by concurrency.

Raising `maintenance_work_mem` can help certain operations finish faster and reduce temp I/O, yet does not replace storage bandwidth or vacuum strategy.

## 20. How Does Autovacuum Generate I/O?

Autovacuum reads heap/index pages to locate dead tuples, updates visibility/free space metadata, and may write modified pages. It competes for I/O with application workloads.

Related settings:

~~~conf
autovacuum = on
autovacuum_max_workers = 3
autovacuum_vacuum_cost_limit = 200
autovacuum_vacuum_cost_delay = '2ms'
~~~

Values are examples; PostgreSQL applies cost limits across workers and sharing mechanisms depending on version.

### vacuum_cost_limit and vacuum_cost_delay

The vacuum cost model estimates page access cost. When reaching the cost limit, vacuum sleeps for the cost delay to reduce I/O pressure.

- A higher cost limit lets vacuum run faster while generating heavier I/O.
- A higher cost delay slows vacuum down, reducing pressure while allowing dead tuples to linger longer.
- Disabling throttling or raising worker count does not automatically improve overall system performance.

### When Autovacuum Falls Behind

Dead tuples accumulate, table/index bloat grows, and queries must read more pages. I/O increases not only because of autovacuum; insufficient vacuuming also degrades read/write efficiency across the workload.

Inspect vacuum frequency, dead tuples, table churn, and transaction age.

## 21. Coordinating Checkpoints, Background Writer, and Vacuum

The three mechanisms serve different purposes:

| Mechanism | Goal | Primary I/O |
| --- | --- | --- |
| Background writer | Prepare clean buffers so backends write less themselves | Writing dirty data pages |
| Checkpointer | Complete checkpoints and flush required dirty pages | Writing/syncing data files |
| Autovacuum | Clean dead tuples, update visibility/free space | Reading/writing heap and index |

Raising one parameter may shift I/O in time rather than reducing total I/O volume.

For example, an aggressive background writer can reduce write bursts on backends, yet the exact same dirty pages still have to be written to storage.

## 22. Tablespaces and I/O Distribution

Tablespaces can place groups of relations on different storage devices:

- Tablespace for hot OLTP tables.
- Tablespace for indexes.
- Tablespace for large historical partitions.
- Tablespace for temporary objects.

However, physical separation only helps when the underlying I/O paths are genuinely independent. Two mount points on the same underlying volume do not add IOPS.

### temp_tablespaces

Can be configured as:

~~~conf
temp_tablespaces = 'temp_fast'
~~~

Or set per session/role as needed. Temporary files for sorts/hashes can use the specified tablespaces. Verify exact version behavior and ensure proper permissions/paths.

### Operational Risks

- A full tablespace can cause queries/DDL to fail.
- Backup/restore must handle every tablespace location.
- Moving tablespaces requires proper shutdown or online move procedures.
- Storage failure on one tablespace can make relations stored there inaccessible.

Do not scatter relations just to make a storage diagram look neat; have metrics proving a bottleneck and a clear backup/recovery plan.

## 23. Indexes and I/O Cost

Indexes reduce pages read when predicates are highly selective. However, indexes also introduce write amplification:

- INSERT must update indexes.
- UPDATE may update multiple indexes.
- DELETE leaves dead index tuples requiring vacuum.
- Large indexes consume cache and storage.
- Index scans can trigger random heap reads.

An unused index still consumes storage, cache, and write I/O.

### Checking Index Usage

~~~sql
SELECT
    schemaname,
    relname AS table_name,
    indexrelname AS index_name,
    idx_scan,
    idx_tup_read,
    idx_tup_fetch
FROM pg_stat_user_indexes
ORDER BY idx_scan;
~~~

Statistics can reset, and an index may be used rarely by seasonal workloads. Do not drop an index based solely on a short observation window.

### Index-Only Scan

Index-only scans can reduce heap I/O if the query retrieves all needed columns from the index and the visibility map permits skipping heap fetches. Vacuum keeps the visibility map up to date.

An index-only scan does not always mean zero heap page reads; inspect `EXPLAIN` for `Heap Fetches`.

## 24. Sequential Scan and Bitmap Heap Scan

### Sequential Scan

Reads most or all table pages. Can be optimal when a predicate returns a large fraction of rows or the table is small.

### Index Scan

Uses an index to locate rows and then accesses the heap. Good when selectivity is high and few heap pages need to be read.

### Bitmap Heap Scan

Uses a bitmap to collect tuples/pages to read, improving access locality compared to many scattered heap fetches.

Do not force the planner to use indexes by setting `random_page_cost` arbitrarily low. Check cardinality estimates, statistics, and actual plans.

## 25. Reading EXPLAIN BUFFERS

Example:

~~~sql
EXPLAIN (ANALYZE, BUFFERS, WAL)
SELECT *
FROM orders
WHERE customer_id = 42;
~~~

Key details:

- `Shared hit`: page was already in PostgreSQL shared buffers.
- `Shared read`: page was read into shared buffers.
- `Shared dirtied`: page was marked dirty.
- `Shared written`: page was written during the query.
- `Local/temp buffers`: activity on local or temporary buffers.
- `I/O Timings`: read/write time if `track_io_timing` is enabled.
- `WAL`: WAL records/bytes/FPIs where supported by the version.

### Reading Carefully

- `Shared read` does not prove a physical disk read; the page may come from the OS page cache.
- Buffer counts are usually block counts, not bytes.
- Parent/child plan lines report cumulative buffer counts; do not sum every line mechanically.
- `EXPLAIN ANALYZE` actually executes the statement.
- DML modifies data; use transaction rollback or staging when testing.
- A single query does not represent concurrent workload behavior.

## 26. track_io_timing

~~~conf
track_io_timing = on
~~~

When enabled, PostgreSQL collects I/O timing in statistics views and `EXPLAIN` where supported. Timing measurement can add slight overhead depending on platform and clock implementation.

Use it to identify queries spending time on reads/writes, while cross-checking with OS metrics and workload context. Cumulative timing in statistics views must be differenced over time.

## 27. pg_stat_io

Starting in PostgreSQL 16, the `pg_stat_io` view provides I/O statistics by backend type, object, and context.

~~~sql
SELECT *
FROM pg_stat_io
ORDER BY backend_type, object, context;
~~~

Field groups depending on version may include:

- `reads` and `read_time`.
- `writes` and `write_time`.
- `writebacks` and `writeback_time`.
- `extends` and `extend_time`.
- `hits`.
- `evictions`.
- `reuses`.
- `fsyncs` and `fsync_time`.
- `backend_type`, `object`, and `context`.

This view helps identify which backend types generate I/O and which operations dominate cost. Do not assume each counter maps one-to-one to a physical device operation; PostgreSQL buffers and the OS cache sit in between.

### Computing Deltas

Counters are cumulative since the last reset. Take snapshots at t1 and t2 and compute deltas to measure activity over an interval. Record `stats_reset` and server restarts to avoid skewed deltas.

## 28. pg_stat_database and pg_statio

### pg_stat_database

~~~sql
SELECT
    datname,
    blks_read,
    blks_hit,
    temp_files,
    temp_bytes,
    blk_read_time,
    blk_write_time
FROM pg_stat_database
ORDER BY blks_read DESC;
~~~

Timing columns are meaningful when `track_io_timing` is enabled. `blks_read` represents blocks read into shared buffers by PostgreSQL, not necessarily physical disk reads.

### Cache Hit Ratio

You can compute the hit ratio in shared buffers:

\[
Hit\ ratio = \frac{blks\_hit}{blks\_hit + blks\_read}
\]

This metric does not fully capture physical cache behavior and should not be used as the sole SLO. A sequential scan workload with a low hit ratio can still perform well if storage throughput is high and query latency meets targets.

### pg_statio_user_tables

~~~sql
SELECT
    relname,
    heap_blks_read,
    heap_blks_hit,
    idx_blks_read,
    idx_blks_hit,
    toast_blks_read,
    toast_blks_hit
FROM pg_statio_user_tables
ORDER BY heap_blks_read DESC;
~~~

Used to inspect which relations show high block reads/hits in PostgreSQL statistics. Counters can reset; correlate with time windows and workloads.

## 29. pg_stat_wal and Checkpoint Statistics

### WAL

~~~sql
SELECT *
FROM pg_stat_wal;
~~~

Provides counters such as WAL records, full-page images, bytes, writes, syncs, and timings depending on version/configuration.

### Checkpoint

PostgreSQL 17 and later expose checkpoint statistics in `pg_stat_checkpointer`:

~~~sql
SELECT *
FROM pg_stat_checkpointer;
~~~

PostgreSQL 16 and earlier use `pg_stat_bgwriter` for checkpoint counters:

~~~sql
SELECT *
FROM pg_stat_bgwriter;
~~~

Do not run a query referencing columns from one major version on another without verifying the view schema.

### Putting It Together

If query latency rises alongside checkpoint write/sync time, storage may be experiencing write pressure. If WAL bytes surge while checkpoints look normal, check the write workload, full-page images, logical decoding, and archiving/replication slots.

## 30. Monitoring Temporary I/O

Temporary files typically appear when sorts/hashes or certain operations exceed their memory budget.

Query per database:

~~~sql
SELECT
    datname,
    temp_files,
    temp_bytes
FROM pg_stat_database
ORDER BY temp_bytes DESC;
~~~

Find queries generating temp I/O using `pg_stat_statements` if the extension is installed and permissions allow:

~~~sql
SELECT
    queryid,
    calls,
    temp_blks_read,
    temp_blks_written,
    shared_blks_read,
    shared_blks_hit,
    left(query, 160) AS query_sample
FROM pg_stat_statements
ORDER BY temp_blks_written DESC
LIMIT 20;
~~~

Column names can vary across extension versions. `pg_stat_statements` is not automatically active just because PostgreSQL is running; you must install the extension and configure `shared_preload_libraries` per the documentation.

Remediation options include:

- Optimizing queries to reduce sort/hash input.
- Creating appropriate indexes.
- Adjusting `work_mem` cautiously.
- Reducing concurrency causing memory pressure.
- Using adequately performing temp storage.
- Setting `temp_file_limit` to protect disk space.

## 31. WAL and fsync Latency

For workloads writing many small transactions, commit latency can be dominated by WAL flush/fsync rather than data page writes.

Monitor:

- WAL writes/syncs.
- WAL write/sync time.
- Commit latency.
- `synchronous_commit`.
- Storage fsync latency.
- Group commit behavior.
- Synchronous standby latency if using synchronous replication.

Group commit lets multiple transactions share a single WAL flush in some situations. Not every COMMIT always corresponds to an individual physical fsync.

### wal_sync_method

Options depend on the OS. Choose a method suited to your filesystem/storage and how the OS implements flushes. Do not change this setting without benchmarking and verifying durability semantics.

### synchronous_commit

Setting `synchronous_commit=off` can reduce commit latency in some workloads, but recently acknowledged transactions may be lost if the server crashes. The database stays consistent via WAL, yet the transaction durability window changes.

Only apply this to workloads that accept this risk with business approval. Do not use it to mask a faulty storage device.

## 32. Read/Write Separation and Storage Tiering

Some systems place workloads or data by tier:

- Hot data on NVMe.
- Warm data on SSD.
- Historical/archive data on high-capacity storage.
- Backups/WAL archives on object storage.

PostgreSQL does not automatically tier data by temperature. You must use partitioning, tablespaces, archival policies, or application architecture.

### Partitioning

Partitioning can separate data by time/tenant and allow dropping/detaching old partitions instead of deleting millions of rows. However, partitioning does not reduce I/O automatically if queries fail to prune partitions or still read most of the data.

### Storage Tiering Does Not Replace Retention Design

Archived data still needs backups, integrity verification, and recovery per requirements. Moving relations to slower storage can slow down historical queries; communicate with the application team and implement proper query routing.

## 33. Measuring Storage from the OS

PostgreSQL views show internal activity. OS/storage metrics confirm what the physical or virtual device is actually doing.

Common Linux tools:

~~~bash
iostat -xz 1
vmstat 1
sar -d 1
lsblk
df -h
~~~

Key fields depending on tool:

- Read/write IOPS.
- Read/write throughput.
- Average request size.
- Await/latency.
- Queue depth.
- Utilization.
- I/O wait.
- Device errors.
- Filesystem free space.

Do not interpret `%util` on a modern device as the sole measure of saturation; NVMe devices handle multiple queues and utilization semantics differ from HDDs. Read metrics according to tool/kernel version.

On Windows/cloud, use Performance Monitor, storage telemetry, or the provider's corresponding metrics.

## 34. Benchmarking Storage

Benchmarking should separate two questions:

1. What IOPS/throughput/latency is the device capable of?
2. What performance does an actual PostgreSQL workload achieve on that device?

### fio

`fio` can simulate random/sequential reads/writes, block sizes, and queue depths. The example below is strictly for a dedicated test file in a test environment:

~~~bash
fio --name=randread \
    --filename=/mnt/test-volume/fio-test.bin \
    --size=4G \
    --rw=randread \
    --bs=8k \
    --iodepth=16 \
    --numjobs=4 \
    --direct=1 \
    --runtime=60 \
    --time_based \
    --group_reporting
~~~

This command reads/writes a test file and generates heavy I/O load. Never run it against an active data directory or production volume without a change plan. `direct=1` bypasses part of the page cache on supported platforms; behavior depends on OS/filesystem.

### pgbench

`pgbench` generates a PostgreSQL workload and measures transaction throughput/latency. Use schema, scale, client count, and workload close to production for end-to-end benchmarking.

~~~bash
pgbench -i -s 50 testdb
pgbench -c 32 -j 8 -T 300 -P 10 testdb
~~~

This is a workload example. Initializing `pgbench` drops/recreates `pgbench` tables in the target database; use a dedicated benchmark database. Test multiple client counts and record p95/p99 latency, TPS, WAL, I/O, and CPU.

### Controlled Benchmarking

- Run the same workload and data size.
- Clearly document warm/cold cache state.
- Do not benchmark while backups or vacuums skew results.
- Repeat runs multiple times.
- Record both throughput and tail latency.
- Monitor CPU, memory, I/O, and network.
- Test with production durability settings.
- Keep a baseline to compare after changes.

## 35. I/O Tuning Workflow

A sound workflow:

1. Identify the symptom: query latency, commit latency, throughput, or storage saturation.
2. Pick a representative time window.
3. Gather PostgreSQL statistics and OS/storage metrics.
4. Identify whether reads, writes, WAL, temp files, or vacuum are the main driver.
5. Use `EXPLAIN` to check query plans and buffer usage.
6. Check cache/memory pressure.
7. Check storage limits and queueing.
8. Change a small group of settings.
9. Re-benchmark the same workload.
10. Compare p95/p99 latency, throughput, I/O, WAL, and error rate.
11. Keep or roll back per predefined criteria.

Avoid changing many parameters simultaneously, as it makes attributing improvements or regressions difficult.

## 36. Investigation Example: Slow Query Due to Random Reads

**Symptom:** an API query filtering by `customer_id` slows down as data grows.

Investigate:

- Use `EXPLAIN (ANALYZE, BUFFERS)` to check for Index Scan vs. Bitmap Heap Scan.
- Check `shared read` and I/O timings.
- Check index/table correlation and selectivity.
- Check cache hit rate and memory pressure.
- Measure storage read latency and IOPS.
- Check whether the index covers needed columns.

Possible fixes:

- Create/adjust indexes if the query pattern fits.
- Update statistics.
- Improve query selectivity.
- Increase cache reasonably if memory allows.
- Use storage with lower random-read latency.
- Tune planner costs after benchmarking.

Do not lower `random_page_cost` just to force an Index Scan. If the query reads many scattered heap pages, a sequential scan or bitmap scan may be faster.

## 37. Investigation Example: WAL Flush Making COMMIT Slow

**Symptom:** DML statements run quickly, yet `COMMIT` exhibits high latency.

Check:

- `pg_stat_wal` writes/syncs and timings.
- OS fsync/write latency.
- WAL volume and full-page images.
- Synchronous replication status/standby latency.
- Session/role/database `synchronous_commit`.
- Storage power-loss protection and write cache policy.

Possible solutions:

- Move to storage with lower flush latency.
- Reduce WAL volume via schema/index/workload tuning.
- Tune group commit/concurrency per benchmarks.
- Review synchronous standby network latency.
- Only use `synchronous_commit=off` for transactions with an approved durability window.

Do not weaken durability to hide a storage device with unreliable flush behavior.

## 38. Investigation Example: Rising Temporary Files

**Symptom:** `temp_bytes` grows rapidly and the filesystem nears full.

Check:

- `pg_stat_database.temp_files`/`temp_bytes`.
- `pg_stat_statements` `temp_blks_written`.
- `EXPLAIN` sort/hash nodes.
- `work_mem` and concurrency.
- Query join/sort cardinality.
- Temp tablespace capacity and I/O latency.

Solutions:

- Optimize queries and reduce rows before sorting.
- Create indexes supporting `ORDER BY`/`JOIN` when appropriate.
- Increase `work_mem` cautiously at role/query scope.
- Reduce concurrency or limit batch sizes.
- Use a sufficiently sized temp tablespace.
- Set `temp_file_limit` and alerts.

Do not raise `work_mem` globally based on a single spilling query.

## 39. Investigation Example: Checkpoints Causing I/O Bursts

**Symptom:** periodic latency spikes and bursts in storage write throughput.

Check:

- `log_checkpoints` and checkpoint reasons.
- `pg_stat_checkpointer` (PostgreSQL 17+) or `pg_stat_bgwriter` (PostgreSQL 16 and earlier).
- WAL bytes/second.
- `max_wal_size` and `checkpoint_timeout`.
- `checkpoint_completion_target`.
- Background writer statistics.
- Storage write latency/queue depth.
- Replication slots and WAL archive retention.

Solutions:

- Increase `max_wal_size` if requested checkpoints happen too often and disk space allows.
- Tune `checkpoint_completion_target` to spread out write workload.
- Inspect background writer behavior.
- Improve storage throughput/latency.
- Reduce WAL generation if unnecessary indexes/updates exist.
- Monitor crash recovery time after changes.

## 40. Investigation Example: Autovacuum Competing for I/O

**Symptom:** latency rises whenever autovacuum runs on a large table.

Check:

- Autovacuum logs.
- `pg_stat_progress_vacuum`.
- `pg_stat_user_tables` `n_dead_tup` and `last_autovacuum`.
- I/O metrics by backend type/context in `pg_stat_io` if supported.
- Vacuum cost delay/limit.
- Table churn and index bloat.

Solutions:

- Adjust per-table scale factor/threshold for table size.
- Increase maintenance capacity if storage has headroom.
- Reduce vacuum cost rate if application latency must take priority.
- Vacuum more frequently to avoid massive cleanup runs.
- Consider partitioning and index bloat management.

Do not disable autovacuum for short-term I/O relief; dead tuples will accumulate and worsen I/O later.

## 42. How to Change Parameters Safely

Before making changes:

1. Record current values and sources.
2. Check context: `postmaster`, `sighup`, `superuser-backend`, `user`, or `internal`.
3. Check `pending_restart`.
4. Determine impact on memory, disk, and durability.
5. Select a benchmark workload.
6. Define success and rollback criteria.
7. Change a small group of settings.
8. Reload or restart as required.
9. Verify effective values.
10. Compare before/after metrics.

Inspect:

~~~sql
SELECT
    name,
    setting,
    unit,
    source,
    context,
    pending_restart
FROM pg_settings
WHERE name IN (
    'shared_buffers',
    'effective_cache_size',
    'random_page_cost',
    'seq_page_cost',
    'effective_io_concurrency',
    'work_mem',
    'maintenance_work_mem',
    'wal_buffers',
    'checkpoint_timeout',
    'max_wal_size',
    'checkpoint_completion_target',
    'track_io_timing'
)
ORDER BY name;
~~~

Some parameters require a restart, some support reload, and some can be set per session/role. Do not assume a single `pg_reload_conf()` applies every change.

## 43. Common Mistakes

1. **Choosing storage solely by capacity or advertised IOPS**, ignoring latency, throughput, queue depth, and instance limits.
2. **Treating random I/O and sequential I/O the same**, picking devices unsuited to the workload.
3. **Assuming `shared read` in PostgreSQL is always a physical disk read**, ignoring the OS page cache.
4. **Increasing `shared_buffers` without budgeting total memory**, starving the OS and other backends of RAM.
5. **Treating `effective_cache_size` as a memory allocation**, causing wrong memory calculations.
6. **Setting `random_page_cost` too low**, causing the planner to pick index plans that trigger excessive random heap reads.
7. **Increasing `effective_io_concurrency` without benchmarking**, creating queueing and storage contention.
8. **Increasing `work_mem` globally**, causing memory exhaustion when many queries/workers run concurrently.
9. **Increasing `maintenance_work_mem` while forgetting autovacuum worker count**, creating memory pressure.
10. **Using `temp_file_limit` as a fix for query spills**, when it only caps temp disk usage.
11. **Disabling `fsync` or `full_page_writes` for faster benchmarks**, compromising durability.
12. **Confusing `synchronous_commit` with synchronous replication**, misjudging commit guarantees.
13. **Separating WAL/data onto two mounts on the same storage pool and expecting independent I/O**, which fails to eliminate contention.
14. **Increasing `max_wal_size` without accounting for disk space and replication slots**, risking a full filesystem.
15. **Tuning the background writer too aggressively**, pushing extra write I/O onto already saturated storage.
16. **Disabling autovacuum because it generates I/O**, causing bloat and worse long-term I/O.
17. **Looking only at cache hit ratio**, ignoring tail latency and OS/device metrics.
18. **Reading cumulative counters as instantaneous rates**, without computing deltas and checking `stats_reset`.
19. **Running PostgreSQL 16 stats queries on PostgreSQL 17+**, missing the `pg_stat_checkpointer` split.
20. **Summing buffer counts across all `EXPLAIN` nodes**, double-counting cumulative figures.
21. **Running `fio` directly on a production data directory**, risking data corruption or service disruption.
22. **Benchmarking with only a single query**, failing to reflect concurrency and workload mix.
23. **Optimizing throughput while ignoring p95/p99 latency**, degrading user experience.
24. **Failing to check cloud volume burst/throttling**, seeing good performance only initially.
25. **Omitting tablespaces from backup/recovery plans**, causing restores to miss relation files.
26. **Not monitoring temporary files and WAL retention**, allowing disks to fill unexpectedly.
27. **Changing many parameters at once**, making root cause attribution impossible.
28. **Failing to save a baseline and rollback plan**, making recovery of a stable configuration difficult.

## 44. Practice Exercises with Answers

### Exercise 1. What is latency?

**Answer:** The time required to complete an I/O request from submission to receiving the result.

### Exercise 2. What is IOPS?

**Answer:** The number of I/O operations per second.

### Exercise 3. What is throughput?

**Answer:** The amount of data transferred per second, typically measured in MB/s or GB/s.

### Exercise 4. What can an overly high queue depth cause?

**Answer:** Increased wait times and tail latency even though the device can process multiple I/Os in parallel.

### Exercise 5. What storage characteristics do OLTP random lookups require?

**Answer:** Low latency and strong random IOPS, along with consistent sustained performance.

### Exercise 6. What are sequential scans usually sensitive to?

**Answer:** Sequential read throughput and sustained multi-block I/O handling.

### Exercise 7. What is `shared_buffers`?

**Answer:** The shared memory cache for data pages managed by PostgreSQL.

### Exercise 8. Does `effective_cache_size` allocate memory?

**Answer:** No. It is a cache estimate for the planner.

### Exercise 9. What is `random_page_cost` used for?

**Answer:** The relative cost of random page reads in the planner cost model.

### Exercise 10. What is `seq_page_cost` used for?

**Answer:** The relative cost of sequential page reads.

### Exercise 11. What does `effective_io_concurrency` affect?

**Answer:** Certain operations that can leverage I/O concurrency/prefetching, especially bitmap heap scans.

### Exercise 12. Is `work_mem` memory per connection or per operation?

**Answer:** Primarily a memory budget per sort/hash operation; one query can have multiple operations and parallel workers.

### Exercise 13. When do queries create temporary files?

**Answer:** When operations such as sorts/hashes exceed their memory budget or require temporary storage.

### Exercise 14. What does `temp_file_limit` do?

**Answer:** Limits total temporary file space a process may use according to PostgreSQL semantics.

### Exercise 15. Why must WAL be written before data pages?

**Answer:** Write-ahead logging ensures PostgreSQL can redo changes after a crash.

### Exercise 16. What is the risk of `fsync=off`?

**Answer:** Potential data loss or corruption after a crash/power loss.

### Exercise 17. What does `full_page_writes` protect against?

**Answer:** Helps recover from torn pages using full-page images in WAL when needed.

### Exercise 18. Does `synchronous_commit` change data page flushing?

**Answer:** It controls commit acknowledgement relative to WAL flush/apply; it does not mean heap data pages are immediately written.

### Exercise 19. Is `max_wal_size` a hard cap?

**Answer:** No. It is a soft threshold; WAL can exceed it due to workload, slots, and archiving.

### Exercise 20. What does `log_checkpoints` help investigate?

**Answer:** The reason, duration, and buffer counts of checkpoints/restartpoints.

### Exercise 21. Which PostgreSQL version introduced `pg_stat_io`?

**Answer:** PostgreSQL 16.

### Exercise 22. Which view holds checkpoint statistics in PostgreSQL 17?

**Answer:** `pg_stat_checkpointer`.

### Exercise 23. Where are checkpoint counters located in PostgreSQL 16 and earlier?

**Answer:** `pg_stat_bgwriter`.

### Exercise 24. Does `EXPLAIN BUFFERS` `shared read` always mean a physical disk read?

**Answer:** No. The page may have been served by the OS page cache.

### Exercise 25. Why not increase `work_mem` globally to fix temp I/O?

**Answer:** Multiple operations, sessions, and parallel workers can consume memory concurrently, risking memory exhaustion.

### Exercise 26. Why should you not disable autovacuum to reduce I/O?

**Answer:** Dead tuples and bloat accumulate, making long-term I/O and performance worse.

### Exercise 27. When is separating WAL and data helpful?

**Answer:** When both workloads contend and the dedicated storage path is genuinely independent with proper durability.

### Exercise 28. Which OS tools are commonly used on Linux to inspect disk I/O?

**Answer:** `iostat`, `vmstat`, `sar`, and corresponding storage telemetry tools.

### Exercise 29. Should `fio` be run directly on a production PostgreSQL data directory?

**Answer:** No. Only run it on a dedicated test file/device in a controlled environment.

### Exercise 30. How should an I/O tuning workflow begin?

**Answer:** Measure the workload and identify the bottleneck using PostgreSQL statistics, `EXPLAIN`, and OS/storage metrics before changing parameters.

## 47. Summary

**I/O cost depends on both storage hardware and how PostgreSQL accesses, caches, writes WAL, and flushes data pages.** Sound optimization requires measuring from the query down to the OS and device, then making controlled configuration changes.

1. **Latency, IOPS, throughput, and queue depth are distinct metrics.** OLTP and analytics workloads have different I/O needs.
2. **Random I/O and sequential I/O must be evaluated separately.** SSD/NVMe improves random access but does not eliminate all storage bottlenecks.
3. **Both `shared_buffers` and OS page cache participate in the read path.** `shared read` does not necessarily mean a physical disk read.
4. **`effective_cache_size` is only a planner estimate.** It does not allocate memory.
5. **`random_page_cost` and `seq_page_cost` are planner cost units.** Tune them after inspecting plans and benchmarking.
6. **`work_mem` multiplies by operation, session, and worker.** Excessive increases can cause memory pressure.
7. **WAL flushes and data page writes are distinct activities.** `fsync`/`full_page_writes` must adhere to durability policy.
8. **Checkpoints, background writer, and vacuum all generate write I/O.** Tune them to match workload and storage capacity.
9. **Temporary files and replication/WAL retention can fill disks.** Monitor temp bytes, slots, and the archiver.
10. **`pg_stat_io`, `pg_stat_wal`, `pg_stat_database`, and `EXPLAIN BUFFERS` complement OS metrics.**
11. **Benchmarks must represent the workload and capture tail latency.** Never use a single IOPS figure to assume the database will be fast.
12. **Never run destructive benchmarks on production data.** Save a baseline, change small batches, and keep a rollback plan.
13. **Never trade durability for benchmark speed.** Correctness and recoverability are foundational requirements.

An effective I/O strategy starts by identifying exactly which query or background process generates the load, which storage path is constrained, and which PostgreSQL parameters genuinely apply. Only then can storage, cache, WAL, and checkpoints be tuned toward a unified operational goal.
