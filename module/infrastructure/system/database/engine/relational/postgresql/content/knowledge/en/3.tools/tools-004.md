# Output Formatting, Query Buffer, History, and Timing in psql

When working with PostgreSQL from the command line, much of your efficiency comes not from memorizing more `SELECT` statements, but from knowing how to use **`psql`**: formatting result tables so they read clearly in the terminal, composing a multi-line SQL statement before executing it, viewing or editing the query buffer, recalling past commands, and measuring execution time to compare SQL approaches.

This lesson focuses on four groups of `psql` tools:

1. **Output formatting** — presenting results as tables, expanded records, CSV, or HTML; controlling the pager, `NULL` display, headers, and writing output to files.
2. **Query buffer** — where `psql` holds the SQL statement you are typing before sending it to the PostgreSQL Server; viewing, editing, clearing, saving, or executing its contents.
3. **Command history** — recalling previously entered commands, searching history, and controlling what is saved on your workstation.
4. **Timing** — using `\timing` to observe client-side duration and `EXPLAIN (ANALYZE, BUFFERS)` to understand where the server spent effort.

**Important distinction:** the `psql` query buffer is not PostgreSQL Server's `shared_buffers`. The query buffer holds **the command text being composed on the client side**; `shared_buffers` is the server-side memory area caching data and index pages. These two mechanisms differ in both purpose and scope.

Examples are based on modern PostgreSQL and compatible `psql` versions. Some features (such as CSV format in `\pset`) require a sufficiently recent `psql` version; check `psql --version` and `\?` in your actual environment when needed.

## 1. Preparing the psql environment and reading the two command types

Check the version from the terminal:

```bash
psql --version
```

Connect to the test database:

```bash
psql -h localhost -p 5432 -U postgres -d postgres
```

Options include:

| Option | Meaning |
|---|---|
| `-h` | PostgreSQL Server host address |
| `-p` | PostgreSQL service port |
| `-U` | Role name used to connect |
| `-d` | Database name |

The command above only illustrates a local connection. In real systems, use a role with appropriate privileges, secure authentication, and TLS when needed; never put passwords in scripts, history, or plain command lines.

After connecting, you may see a prompt similar to:

```text
postgres=>
```

Two common command types:

- **SQL**: executed by PostgreSQL Server, e.g. `SELECT current_database();`. SQL statements typically end with `;`.
- **`psql` meta-command**: starts with a backslash `\`, e.g. `\x`, `\timing`, `\pset`. These are processed by `psql` and **normally do not need `;`**.

Example:

```text
postgres=> SELECT current_database();
 current_database
------------------
 postgres
(1 row)

postgres=> \timing on
Timing is on.

postgres=> SELECT 1;
 ?column?
----------
        1
(1 row)

Time: 0.XXX ms
```

The `0.XXX` timing figures are illustrative only; they depend on hardware, network, cache, and current server activity.

### 1.1. Essential help commands

```text
\?                 -- Help for psql meta-commands
\h                 -- Help for SQL statement syntax
\h SELECT          -- Syntax for SELECT
\conninfo          -- Current connection information
\l                 -- List databases
\dn                -- List schemas
\dt                -- List tables in search scope
\d table_name      -- Describe a table
\q                 -- Exit psql
```

The commented lines above are explanatory, not a SQL script to send verbatim. Try each command directly inside `psql`.

## 2. Creating a sample table to practice formatting and timing

To avoid relying on pre-existing data, create a separate schema in your practice database.

```sql
CREATE SCHEMA IF NOT EXISTS psql_lab;

CREATE TABLE IF NOT EXISTS psql_lab.san_pham (
    id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    ten TEXT NOT NULL,
    nhom TEXT NOT NULL,
    gia NUMERIC(12, 2) NOT NULL,
    ghi_chu TEXT,
    tao_luc TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

If the newly created table has no rows yet, insert sample data:

```sql
INSERT INTO psql_lab.san_pham
    (id, ten, nhom, gia, ghi_chu)
VALUES
    (1, 'Mechanical keyboard', 'Accessories', 1250000.00, 'Compact layout, USB-C connection'),
    (2, 'Wireless mouse', 'Accessories',  450000.00, NULL),
    (3, '27-inch monitor', 'Monitors', 5890000.00, 'High resolution; suitable for work'),
    (4, 'Headphones', 'Audio',  890000.00, 'With microphone');
```

If you run this example a second time when the IDs already exist, PostgreSQL may raise a primary key error; this exercise assumes a fresh schema/table and a one-time insert. Because the `id` column allows explicit IDs, the identity sequence may not advance past the inserted IDs automatically. In real applications, prefer letting the database generate IDs or synchronizing the sequence after loading fixed IDs.

Test reading the data:

```sql
SELECT id, ten, nhom, gia, ghi_chu
FROM psql_lab.san_pham
ORDER BY id;
```

This table includes a long text column, prices, and `NULL`, which is enough to demonstrate the differences between display formats.

## 3. Formatting output: using \pset

The foundational `psql` command is:

```text
\pset [option [value]]
```

`\pset` changes how **the `psql` client presents query results**. It does not change data in the database and does not alter table definitions.

You can inspect `psql`'s current settings with `\pset`, or set individual options as supported by your version. Common options include:

| `\pset` option | Effect |
|---|---|
| `format` | Choose `aligned`, `unaligned`, `wrapped`, `csv`, `html`, etc. |
| `border` | Border level for tabular output |
| `expanded` | Display each record vertically; can be set to `auto` |
| `null` | String used to display SQL `NULL` |
| `fieldsep` | Column delimiter for `unaligned` format |
| `recordsep` | Record separator in unaligned output |
| `tuples_only` | Hide headers and footers, printing only data rows |
| `pager` | Enable/disable the pager for long output |
| `footer` | Show or hide trailing info such as row counts |
| `linestyle` | Line-drawing style such as `ascii`, `old-ascii`, or `unicode` |
| `columns` | Target terminal width for certain output formats |
| `csv_fieldsep` | Field delimiter for CSV format if supported by your version |

Some options may be unavailable in older `psql` releases or have slight semantic differences. Use `\?` to check the exact syntax supported by your running client.

### 3.1. Aligned format: column-aligned tables

```text
\pset format aligned
\pset border 1
```

Run:

```sql
SELECT id, ten, gia
FROM psql_lab.san_pham
ORDER BY id;
```

`aligned` works well when the result has a moderate number of columns and moderate text lengths. Columns are aligned so readers can compare numbers visually.

However, if a query returns 30 columns or a column contains long JSON, the table can exceed screen width. Instead of endlessly widening your terminal, use **expanded display** in the next section.

### 3.2. Adjusting borders and line styles

```text
\pset border 0
\pset border 1
\pset border 2
\pset linestyle unicode
```

The `border` level affects lines around columns and the table frame. `linestyle unicode` helps supported terminals render cleaner Unicode box-drawing lines; if your terminal or font does not render them well, use ASCII style.

These options only **improve readability**; they do not alter SQL results and do not optimize query execution time.

### 3.3. Wrapped format and column width

For long values:

```text
\pset format wrapped
\pset columns 80
```

`wrapped` wraps text inside cells when needed to limit table width, according to `psql` rules. Wrapping is handy when reading product descriptions or long JSON strings, but should not be treated as a machine-parseable data representation.

When exporting to a file for another program to read, use **CSV** or a format with explicit escaping rules, not a wrapped table.

## 4. \x: displaying a record vertically

A very useful command in `psql`:

```text
\x on
```

Then:

```sql
SELECT *
FROM psql_lab.san_pham
WHERE id = 3;
```

Instead of one very wide line, the result presents each column on its own line, typically like this:

```text
-[ RECORD 1 ]------------------------------
id       | 3
ten      | 27-inch monitor
nhom     | Monitors
gia      | 5890000.00
ghi_chu  | High resolution; suitable for work
tao_luc  | ...
```

This layout works well for inspecting one or a few records with many columns, such as `SELECT *`, metadata, JSON, or a row of operational statuses.

Related commands:

```text
\x on       -- Always print in expanded format
\x off      -- Return to normal display
\x auto     -- Automatically use expanded when output is too wide
\x          -- Toggle on/off based on current setting
```

`\x auto` is very practical when you routinely run both narrow and wide queries: the client chooses the layout based on actual width. However, thresholds and behavior still depend on your terminal and pager.

**Distinction from SQL:** `\x` is not PostgreSQL Server syntax. Placing `\x on` in a tool that sends SQL directly over JDBC will not be processed as a `psql` meta-command.

## 5. \a and \t: switching quickly between formatted and compact output

### 5.1. \a toggles aligned output

```text
\a
```

`\a` is a shortcut toggling `psql` between aligned and unaligned mode. If you want clear, reproducible output in a script, specify it explicitly:

```text
\pset format unaligned
```

`unaligned` format can be handy when outputting delimiter-separated data, but **does not automatically provide full CSV quoting/escaping rules**.

### 5.2. \t: hiding headers and footers

```text
\t on
```

Then:

```sql
SELECT COUNT(*)
FROM psql_lab.san_pham;
```

The output may be just:

```text
4
```

The `\t` command is a shortcut for `tuples_only`; you can use:

```text
\pset tuples_only on
\pset tuples_only off
```

When you want compact output for human reading or for a shell script reading a scalar value, hiding headers and footers is useful. However, when passing multi-column data to another system, use proper CSV with standard escaping instead of relying solely on `\t` and `\a`.

### 5.3. Displaying NULL clearly

PostgreSQL distinguishes three cases: `NULL`, the empty string `''`, and a string containing spaces. In `psql` result tables, `NULL` by default may not show a distinct marker.

Set a display string:

```text
\pset null '[NULL]'
```

Test:

```sql
SELECT id, ten, ghi_chu
FROM psql_lab.san_pham
ORDER BY id;
```

For product `id = 2`, the `ghi_chu` column renders as `[NULL]`, making it easy to tell apart from an empty string.

**Caution:** this is purely a **display setting**; it does not perform SQL `COALESCE` or modify columns in the database. When exporting to a file, a custom null marker can become ambiguous if real data contains that exact string; establish clear formatting conventions.

## 6. Exporting CSV, HTML, and unaligned text

### 6.1. CSV via \pset format csv

On `psql` versions supporting `format csv`:

```text
\pset format csv
```

Then:

```sql
SELECT id, ten, nhom, gia
FROM psql_lab.san_pham
ORDER BY id;
```

`psql` formats the query output as CSV, quoting/escaping fields per client rules. This is generally safer than `unaligned` when values contain commas, double quotes, or newlines.

After finishing:

```text
\pset format aligned
```

An important distinction: `\pset format csv` is a **`psql` query-result display mode**, whereas `COPY ... CSV` / `\copy ... CSV` are data-export tools with their own syntax and rules. Do not assume both produce byte-for-byte identical output across all settings such as `NULL`, headers, or encoding.

### 6.2. Unaligned and custom field delimiters

```text
\pset format unaligned
\pset fieldsep '|'
\pset tuples_only on
```

Run:

```sql
SELECT id, ten, gia
FROM psql_lab.san_pham
ORDER BY id;
```

The output may look like:

```text
1|Mechanical keyboard|1250000.00
2|Wireless mouse|450000.00
3|27-inch monitor|5890000.00
4|Headphones|890000.00
```

This is easy-to-read delimited text, but **not a safe interchange format if values contain `|` or newlines**. For arbitrary data, prefer CSV generated by `COPY`/`\copy` or a tool with proper escaping.

Return to standard settings:

```text
\pset format aligned
\pset tuples_only off
```

### 6.3. HTML and other formats

```text
\pset format html
```

Running `SELECT` afterward causes `psql` to output an HTML table representation. Some versions also support formats like `latex` and `troff-ms`. These serve presentation or format integration needs without modifying server data.

If you want to publish an HTML report, still pay attention to character encoding, CSS styling, and web-safety escaping when displaying user data. HTML output from `psql` is not automatically a complete web page.

## 7. Pager, terminal width, and writing results to files

### 7.1. What is the pager?

When output spans many lines, `psql` can pipe it through a pager such as `less`, depending on the environment. This lets you scroll page by page without flooding the terminal with thousands of lines.

```text
\pset pager on
\pset pager off
\pset pager always
```

- `on`: use the pager when appropriate for the output and environment.
- `off`: disable paging and print directly.
- `always`: force paging for eligible output even if it is short.

When inside a pager like `less`, pressing `q` normally exits the pager, **not PostgreSQL**. Distinguish pager controls from the `\q` command at the `psql` prompt.

For reviewing long operational outputs, `\x auto` combined with the pager can be much easier to read than screenshots of an overly wide table.

### 7.2. \o redirects query output

Command:

```text
\o /duong-dan/bao_cao.txt
```

changes the destination of **query output** to the specified file; subsequent queries write to that file instead of displaying normally in the terminal. To restore stdout:

```text
\o
```

Interactive example:

```text
\pset format aligned
\o bao_cao_san_pham.txt
```

Then run:

```sql
SELECT id, ten, gia
FROM psql_lab.san_pham
ORDER BY gia DESC;
```

And end redirection:

```text
\o
```

**Note:** if you forget to run `\o` with no arguments, later queries keep writing to the file, making it look like `psql` stopped showing output. Be careful with file paths and filesystem permissions; exports may contain sensitive data.

### 7.3. \g writes the output of just the current query

In `psql`, `\g` sends the current SQL buffer for execution. You can specify an output destination for that single execution:

```text
SELECT id, ten, gia
FROM psql_lab.san_pham
ORDER BY id
\g san_pham.txt
```

The snippet above is **a single `psql` interaction**: there is no `;` after `ORDER BY id`, because the `\g` meta-command submits the query and writes the result to the file.

Difference:

- `\o file`: redirects output for all subsequent queries until reset.
- `\g file`: executes the query in the query buffer and sends **that execution's output** to the file.

Be careful: if you already submitted a SQL statement with `;` and then type `\g` separately, `psql` may **re-execute the previous query** per its buffer behavior. For `SELECT` that only adds an extra read, but for `INSERT` or `UPDATE` it can repeat side effects.

### 7.4. How does \copy differ from \o and \g?

If the goal is generating a CSV file for another program to read, a clean approach is `\copy`:

```text
\copy (SELECT id, ten, nhom, gia FROM psql_lab.san_pham ORDER BY id) TO 'san_pham.csv' WITH (FORMAT csv, HEADER true)
```

`\copy` is a `psql` meta-command using PostgreSQL's `COPY` protocol via the client. The file `san_pham.csv` is written **on the machine running `psql`**, under the client process's permissions.

By contrast, SQL `COPY ... TO 'path'` uses a path on the **PostgreSQL Server** and has different privilege rules:

```sql
-- Server-side syntax illustration; requires appropriate filesystem privileges.
COPY psql_lab.san_pham TO '/srv/postgresql/export/san_pham.csv'
WITH (FORMAT csv, HEADER true);
```

Do not run that server-side statement on a real server unless you are explicitly authorized to write to that path.

For data exchange, distinguish clearly:

| Tool | Goal | Where it writes |
|---|---|---|
| `\pset` | Choose display formatting inside `psql` | Does not create files on its own |
| `\o file` | Redirect query output across multiple queries | Machine running `psql` |
| `\g file` | Execute one query and write its result | Machine running `psql` |
| `\copy ... TO` | Export data via the COPY protocol | Machine running `psql` |
| `COPY ... TO '/path'` | Export on the server side | Machine running PostgreSQL Server |

## 8. What is the psql query buffer?

The **query buffer** is where `psql` holds SQL text you have typed that has not yet been sent as a complete statement to the server. In normal interactive mode, SQL is sent when a valid terminator such as `;` appears outside strings/comments, or when you invoke a query-sending meta-command like `\g`.

Example starting a multi-line statement:

```text
postgres=> SELECT
postgres->     id,
postgres->     ten,
postgres->     gia
postgres-> FROM psql_lab.san_pham
postgres-> WHERE gia > 500000
postgres-> ORDER BY gia DESC
postgres->
```

The prompt changes from `=>` to `->`, indicating `psql` is still accumulating an unfinished SQL statement. Because there is no `;` yet, it has not been sent to the server.

At this point you can:

- Print the query buffer contents with `\p`.
- Open an editor to modify it with `\e`.
- Clear the draft statement with `\r`.
- Submit the SQL statement with `\g`.
- Or type `;` to terminate and execute it.

**This buffer lives on the client side.** PostgreSQL Server does not see the draft SQL until `psql` sends a complete statement. Therefore, an unfinished query sitting in the buffer does not start a transaction on its own, does not hold row locks from that statement, and does not consume query-processing CPU on the server.

However, if you previously started a transaction with `BEGIN` or executed other statements, the session may still hold transactions or locks from those executed commands; clearing the query buffer **does not roll back an open transaction**.

## 9. \p, \r, \e, \w, and \g: lifecycle of a drafted SQL statement

### 9.1. \p: print buffer contents

While typing an unfinished SQL statement:

```text
SELECT id, ten, gia
FROM psql_lab.san_pham
WHERE nhom = 'Accessories'
\p
```

`\p` prints the SQL currently in the query buffer, useful when you have typed many lines and want to verify you did not miss a `WHERE`, `JOIN`, or parenthesis.

`\p` **does not execute** the SQL statement; it only displays the text stored in the buffer.

### 9.2. \r: reset/clear the query buffer

```text
\r
```

`\r` discards the SQL statement currently being composed in the buffer so you can start over. It is especially useful when:

- You accidentally pasted a SQL statement with a dangerous condition.
- You are partway through a multi-line query and want to cancel before executing it.
- You forgot to close a parenthesis or quote and want a clean start.
- You decide not to send whatever SQL is in the query buffer.

Example before accidentally submitting a data-modifying command:

```text
UPDATE psql_lab.san_pham
SET gia = gia * 2
\r
```

After `\r`, the `UPDATE` was never executed and is no longer in the buffer.

**Remember that `\r` only affects `psql`'s query buffer**, not `ROLLBACK`. If an `UPDATE` was already sent and committed, `\r` does not undo the data change.

### 9.3. \e: open an editor to compose SQL

```text
\e
```

When you invoke `\e`, `psql` opens the configured external editor. The current query buffer is loaded into the editor for modification. After you save and exit the editor, `psql` processes the edited SQL according to `\e` rules; if the statement ends cleanly with `;`, it may be sent for execution upon returning.

Therefore, **do not treat `\e` as a harmless read-only preview when the buffer holds a destructive command**. Know how your editor saves files and check the statement terminator status.

You can control which editor is used via environment variables such as `PSQL_EDITOR`, `EDITOR`, or `VISUAL`, depending on your platform and how `psql` selects the program.

Example in a Unix shell:

```bash
export PSQL_EDITOR=vim
psql -d postgres
```

On Windows, program names and environment variable syntax may differ. The key point is that `\e` opens **an editor on the client machine**, not an editor inside PostgreSQL Server.

### 9.4. \w: write the query buffer to a SQL file

```text
\w ban_nhap.sql
```

`\w` writes the contents of the **current query buffer** to the specified file, which is helpful when you want to save a long query to run later, review with teammates, or incorporate into a controlled script.

**Do not confuse `\w` with `\o`:**

- `\w file.sql` saves **the query text** in the buffer.
- `\o ket_qua.txt` saves **the results of queries** executed afterward.

A `.sql` file created with `\w` is not automatically a safe migration. Before reusing it, verify the target schema, transactions, privileges, and data impact.

### 9.5. \g: submit the query buffer for execution

```text
SELECT id, ten
FROM psql_lab.san_pham
WHERE gia > 500000
\g
```

`\g` sends the SQL currently in the buffer to the server, serving the same statement-terminating role as `;` in this case.

If the buffer contained:

```sql
DELETE FROM psql_lab.san_pham WHERE id = 1;
```

then `;` already executed the statement. Typing `\g` right after can re-execute the last statement due to how `psql` retains the previous buffer. When running DML/DDL, **send once and inspect the outcome before sending again**.

### 9.6. Quick comparison table

| Command | Effect on query buffer or output | Executes SQL? |
|---|---|---|
| `\p` | Prints the SQL currently in the buffer | No |
| `\r` | Clears the query buffer | No |
| `\e` | Edits the SQL in an editor and processes it on exit | Possibly, depending on edited content |
| `\w file` | Writes drafted SQL to a file | No |
| `\g` | Submits the SQL in the buffer | Yes |
| `\g file` | Submits SQL and writes one-time output to a file | Yes |
| Valid `;` | Terminates SQL and submits for execution | Yes |

In daily practice, prefer `\p` or `\r` to avoid accidentally submitting an unchecked statement.

## 10. Recognizing multi-line prompts and incomplete states

The `psql` prompt does more than display the database name. It also hints when the current SQL statement is incomplete due to open quotes, parentheses, comments, or a missing statement terminator.

Common prompt states look like:

```text
postgres=>   -- Ready for a new SQL statement

postgres->   -- Composing a multi-line SQL statement, not yet terminated

postgres'>   -- Inside a string opened by a single quote

postgres">   -- Inside a double-quoted identifier

postgres(>   -- Inside an expression with an unclosed opening parenthesis
```

Prompt formatting can be customized using `psql`'s `PROMPT1` and `PROMPT2` variables; the list above uses the standard defaults for illustration.

Example of a typo:

```text
postgres=> SELECT * FROM psql_lab.san_pham
postgres-> WHERE ten = 'Mechanical keyboard
postgres'>
```

Because the closing single quote is missing, `psql` waits for more input. If you do not want to finish this statement, type `\r` to clear the query buffer. The prompt turning into `'>` does not mean a lost connection or a deadlock.

Long statements with nested parentheses should always be checked before submitting to avoid accidentally running an unfiltered `UPDATE` or `DELETE` across an entire table.

## 11. History in psql: distinguishing history from the query buffer

The **query buffer** is your current draft. **History** is the collection of previously entered commands and SQL statements from earlier interactions, kept in memory and optionally saved to a history file.

For example:

- You just typed `SELECT ... WHERE ...` without `;`: it sits in the current query buffer.
- You already executed a series of `SELECT`, `EXPLAIN`, and `\dt` commands: they appear in `psql`'s command history.
- You press the Up Arrow: `psql` recalls an item from history onto the input line to edit or re-run.

History speeds up interactive work, but **does not replace Git, migration files, or audit logs**. It can be size-limited, cleared, or never saved if the client was built or started without interactive history support.

### 11.1. Keyboard navigation

In terminals with readline or an equivalent line-editing library:

- **Up/Down arrows:** cycle through older or newer commands in history.
- **Ctrl+R:** reverse-search by typed substring.
- **Ctrl+C:** interrupt current input or active command depending on context; in `psql` it can also cancel composing the current draft, though you must distinguish cancelling input from cancelling an already-running statement.
- **Ctrl+A / Ctrl+E:** jump to start/end of line in standard readline editing mode.

Keybindings may vary by terminal, readline configuration, operating system, and remote session software.

### 11.2. \s to view or save interactive history

On `psql` builds that support this command with a compatible history library:

```text
\s
```

typically displays interactive command history, using the pager if appropriate.

To write history to a file:

```text
\s lich_su_psql.txt
```

**Compatibility note:** if `\s` is unavailable in your `psql` build, check `\?` and build options. History may still be handled by terminal/readline mechanisms or the history file; do not assume every client supports identical meta-commands.

`\s` outputs **history**, not query results and not the current query buffer contents. To save your current query draft, use `\w`.

### 11.3. HISTFILE and HISTSIZE

`psql` has history-related variables. In many versions:

- **`HISTFILE`:** path of the history file used to save interactive sessions.
- **`HISTSIZE`:** maximum number of history entries retained.
- **`HISTCONTROL`:** controls skipping certain entries when saving, such as duplicates or commands starting with a space.
- **`HISTIGNORE`:** can provide command patterns to exclude from history on supported versions.

To inspect a variable's current value, use `\echo` with `:var_name` syntax:

```text
\echo :HISTFILE
\echo :HISTSIZE
\echo :HISTCONTROL
```

In `psql`, `\set` with no arguments lists existing variables. Do not run `\set VAR_NAME` just to view a value: that syntax **sets the variable to an empty string**.

Example in a Linux environment:

```text
\set HISTFILE '/home/student/.psql_history_training'
\set HISTSIZE 2000
\set HISTCONTROL ignoreboth
```

`ignoreboth` typically combines ignoring commands starting with a space and ignoring commands identical to the most recent history entry, depending on version support. Do not rely on this as a rock-solid security measure, since data may still be recorded in other logs, terminal scrollback, shell history, monitoring tools, or server query logs.

Replace the example path with a directory accessible to your client OS account. The history file **lives on the machine running `psql`**, not inside the PostgreSQL database.

### 11.4. Avoiding sensitive information in history

Never type passwords or tokens into SQL statements or client commands when safer mechanisms exist.

Example with exposure risk:

```sql
-- Example of what NOT to do with a real password:
CREATE ROLE app_user LOGIN PASSWORD 'mat_khau_nhay_cam';
```

If typed directly in `psql`, the statement may be saved in history, written to audit/statement logs, or captured by monitoring tools depending on configuration. Even if you delete the client history file, other logs may still retain it.

Preferred practices:

1. Avoid typing or printing raw secrets in commands saved to history.
2. Use your organization's proper authentication and secret-provisioning mechanisms.
3. Restrict permissions on client history files and backups.
4. Never share a raw `.psql_history` file without scrubbing sensitive entries.
5. Use reviewed, version-controlled SQL scripts for high-impact operations.

History is helpful for personal productivity, but **it is not a tamper-evident, complete, immutable audit trail**.

## 12. \timing: measuring client-side execution time

Enable timing:

```text
\timing on
```

Run:

```sql
SELECT COUNT(*)
FROM psql_lab.san_pham;
```

After the results, `psql` prints timing similar to:

```text
Time: 0.XXX ms
```

Disable with:

```text
\timing off
```

You can run `\timing` without arguments to toggle per `psql` support, but in scripts use explicit `on` or `off`.

### 12.1. What does \timing measure?

`\timing` measures execution duration **from `psql`'s perspective** for the command sent by the client. The figure is influenced by:

- Server query execution time.
- Sending the SQL statement and receiving results over the connection.
- Result data volume.
- Network latency between client and database.
- Other client-side timing factors.

Thus, `\timing` measurements **are not identical** to server-side PostgreSQL executor time. Depending on client version and processing path, formatting/display overhead is not necessarily accounted for identically to server processing time.

When comparing reading 10 rows versus 1 million rows, remember that network transfer can dominate total time. A query with an efficient server plan can still feel slow to the user if it returns a massive result set.

### 12.2. Example timing two query shapes

```text
\timing on
```

```sql
SELECT COUNT(*)
FROM psql_lab.san_pham;

SELECT *
FROM psql_lab.san_pham
ORDER BY gia DESC;
```

The first query returns a single value; the second returns more columns and rows. With four sample rows, both are very fast; never use such results to conclude optimal access paths for tables with millions of rows.

### 12.3. Why a single measurement is not enough

Query duration can vary between runs because:

- Shared buffers and OS page cache may or may not already hold the data.
- PostgreSQL may be running checkpoints, autovacuum, or concurrent workloads.
- The planner uses statistics estimates and specific chosen plans.
- Locks or shared resources may face contention.
- Network and client load may vary.
- Query results change as underlying data changes.

Therefore, measure **multiple times**, inspect timing distributions, resource statistics, and execution plans. Never optimize based on a single manual fast/slow timing reading.

## 13. EXPLAIN and EXPLAIN ANALYZE: measuring deeper than \timing

When a query is slow, `\timing` tells you "how long it took on the client," but not **which step was expensive**. PostgreSQL provides `EXPLAIN` to view the plan and `EXPLAIN (ANALYZE, BUFFERS)` to measure actual rows and execution times.

### 13.1. EXPLAIN shows only the estimated plan

```sql
EXPLAIN
SELECT id, ten, gia
FROM psql_lab.san_pham
WHERE gia > 500000
ORDER BY gia DESC;
```

Output may show `Seq Scan`, `Sort`, and row/cost estimates. On small tables, PostgreSQL often chooses a sequential scan over creating/using an index; that is not a sign of bad SQL.

### 13.2. EXPLAIN ANALYZE executes the query

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, ten, gia
FROM psql_lab.san_pham
WHERE gia > 500000
ORDER BY gia DESC;
```

Metrics to observe:

| Metric | Meaning |
|---|---|
| `cost=...` | Relative cost in planner model units, not milliseconds |
| `rows=...` in estimate | Estimated number of rows at a plan step |
| `actual time=...` | Actual time of a step from instrumentation |
| `actual rows=...` | Actual rows processed/returned per step |
| `loops=...` | Number of times a plan node executed |
| `Buffers: shared hit/read/...` | Buffer hits, disk reads, and page accesses from instrumentation |
| `Planning Time` | Time spent planning the query |
| `Execution Time` | Time spent executing the plan on the server |

Do not compare `cost` directly with milliseconds: `cost` is a relative cost-model unit, whereas actual time is a real execution measurement.

`\timing` and `EXPLAIN ANALYZE` answer different questions:

- **`\timing`:** how long did the client wait to send the query and receive results?
- **`EXPLAIN ANALYZE`:** which plan did PostgreSQL choose, how many rows did each step actually process, and how long did each step take?
- **`BUFFERS`:** does the work involve heavy memory buffer hits or disk I/O?

Note that `EXPLAIN ANALYZE` incurs **instrumentation overhead** and is not a zero-impact measurement. Reliable performance comparisons require examining query structure, data scale, and execution conditions.

### 13.3. Warning for DML statements

```sql
EXPLAIN (ANALYZE, BUFFERS)
UPDATE psql_lab.san_pham
SET gia = gia * 1.05
WHERE id = 1;
```

This command **actually updates data** if executed in autocommit mode or a committed transaction. Never run it in production just to "preview a plan."

If you need to measure an update in a test database and undo it:

```sql
BEGIN;

EXPLAIN (ANALYZE, BUFFERS)
UPDATE psql_lab.san_pham
SET gia = gia * 1.05
WHERE id = 1;

ROLLBACK;
```

`ROLLBACK` reverts the transactional data change in this example, yet execution still generates load, acquires locks, and produces operational side effects such as WAL and buffer activity. With triggers having external side effects or non-transactional operations, rollback may not undo everything. Always use a proper test environment.

## 14. Measuring more accurately: separating client, server, and plan

An observation workflow should progress from lowest impact to richest detail:

```text
Start with a specific SELECT
             │
             ▼
\timing on → total client-observed time
             │
             ▼
EXPLAIN → plan and estimates, without running the data query
             │
             ▼
EXPLAIN (ANALYZE, BUFFERS) → server execution metrics
             │
             ▼
Compare actual rows, I/O, locks, and network
             │
             ▼
Test index / SQL / config changes in a controlled way
             │
             ▼
Re-measure under equivalent conditions
```

Example of a query returning lots of data:

```sql
SELECT *
FROM psql_lab.san_pham;
```

On a huge table, `\timing` can reflect the cost of transmitting and receiving rows, while `EXPLAIN ANALYZE` isolates executor work. If your goal is analyzing the plan, avoid flooding the terminal with millions of rows; inspect `EXPLAIN` first, redirect output if needed, and keep display volume aligned with your analysis goal.

### 14.1. Be careful when using LIMIT to benchmark

```sql
SELECT *
FROM psql_lab.san_pham
LIMIT 10;
```

`LIMIT 10` restricts the number of returned rows and can change the chosen plan; it is not a neutral proxy for measuring the full query. If the query involves `ORDER BY`, indexes, filters, or complex joins, PostgreSQL may still have to process far more than 10 rows to find those final 10 results.

To evaluate the original query, measure under **the real conditions and data volume**, rather than substituting a different query and assuming the server is already optimal.

### 14.2. Refreshing statistics after major data changes

On the test table:

```sql
ANALYZE psql_lab.san_pham;
```

`ANALYZE` updates planner statistics. After bulk inserts or deletes, stale statistics can cause inaccurate row estimates and suboptimal plans.

However, **`ANALYZE` is not a universal speed-up button**. If the root cause is poorly written SQL, a missing index, network latency, or lock contention, refreshing statistics alone will not solve the problem.

## 15. \watch: polling a query periodically

During diagnostics, you may want to watch connection counts or table row counts change over time. `psql` supports `\watch` to re-run a query at intervals.

Example:

```text
SELECT now(), COUNT(*) AS so_san_pham
FROM psql_lab.san_pham
\watch 2
```

In many `psql` versions, `\watch 2` repeats the query roughly every 2 seconds and displays each iteration's output. Use Ctrl+C to stop watching per your terminal environment.

This example is safe because `COUNT(*)` runs on a small table. On a very large table, repeating an I/O-heavy query every second can impose significant load.

`\watch` **is not a scheduled job on PostgreSQL Server**. It requires the `psql` client to stay open and does not persist as a background job after you exit the terminal.

### 15.1. Timing inside a watch loop

If `\timing on` is active when running `\watch`, how timing displays depends on your `psql` version and watch handling. Do not treat the interval between two prints as pure execution time: it also includes the sleep interval and terminal output.

For production monitoring, rather than leaving manual `\watch` running for hours, use proper metrics and alerting systems designed for workload safety, retention, and access control.

## 16. psql variables and scripts for repeatable workflows

Useful settings can be applied in-session or saved in a user's `.psqlrc` startup file, depending on platform.

Interactive example:

```text
\pset null '[NULL]'
\x auto
\timing on
\pset pager on
```

In `.psqlrc`, you can add similar meta-commands to set default display preferences whenever `psql` starts. Avoid placing DML/DDL statements with real side effects in a startup file.

### 16.1. Preventing personal settings from breaking script output

If a script outputs data for another tool to parse, a user's `.psqlrc` settings can alter the output (such as enabling expanded mode, adding footers, or changing how `NULL` renders).

Run `psql` with `-X` to skip the startup file:

```bash
psql -X -d postgres -f bao_cao.sql
```

Inside scripts, explicitly configure the needed format, output, and timing settings instead of relying on each operator's interactive preferences.

### 16.2. psql variables and inserting them into SQL

`psql` supports client-side variables:

```text
\set gia_toi_thieu 500000
```

Use in a query:

```sql
SELECT id, ten, gia
FROM psql_lab.san_pham
WHERE gia > :gia_toi_thieu;
```

`psql` substitutes the variable before sending SQL. This is convenient for small scripts, though it is not the same as **prepared statement bind parameters in a driver**. Improper raw string interpolation can cause syntax errors or injection risks.

For text values, `psql` provides quoting syntax such as `:'var_name'` to substitute as a properly quoted SQL literal, as appropriate. Even so, production applications should use driver/ORM parameter binding rather than assembling SQL in the terminal.

### 16.3. Stopping a script on error

In automated scripts:

```text
\set ON_ERROR_STOP on
```

`ON_ERROR_STOP` tells `psql` to stop when encountering a SQL or meta-command error in script contexts, instead of continuing through remaining statements and leaving ambiguous partial results. Shell example:

```bash
psql -X -v ON_ERROR_STOP=1 -d postgres -f bao_cao.sql
```

When running automation, always check `psql`'s exit status. Never assume every SQL statement in a script succeeded merely because an output file was created.

## 17. Sample workflow: compose → inspect → execute → export → measure

Here is a realistic end-to-end scenario: retrieve products priced over 500,000, inspect the output, export CSV, and check the query's execution plan.

### Step 1: configure display settings

In `psql`:

```text
\pset null '[NULL]'
\x auto
\timing on
```

### Step 2: compose the SQL without sending it yet

```text
SELECT id, ten, nhom, gia, ghi_chu
FROM psql_lab.san_pham
WHERE gia > 500000
ORDER BY gia DESC
```

Because there is no `;`, the statement stays in the query buffer.

### Step 3: review the buffer contents

```text
\p
```

If you spot an incorrect condition, use `\e` to edit in your editor or `\r` to clear and retype. Never submit a risky statement before reviewing it.

### Step 4: execute

```text
\g
```

`psql` sends the query to PostgreSQL Server, displays the results, and (with `\timing` enabled) reports client-observed elapsed time.

### Step 5: export CSV with an explicit query

```text
\copy (SELECT id, ten, nhom, gia, ghi_chu FROM psql_lab.san_pham WHERE gia > 500000 ORDER BY gia DESC) TO 'bao_cao_san_pham.csv' WITH (FORMAT csv, HEADER true)
```

`\copy` writes the file on the client machine. After exporting, verify file size and location, especially if product data is confidential and must not be shared publicly.

### Step 6: inspect the server plan

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, ten, nhom, gia, ghi_chu
FROM psql_lab.san_pham
WHERE gia > 500000
ORDER BY gia DESC;
```

Compare `Execution Time` with `\timing` to understand the different scopes each metric observes. Because the sample table has only a few rows, do not draw index-tuning conclusions from tiny timing differences.

### Step 7: restore convenient display state

```text
\x off
\pset format aligned
\pset tuples_only off
\o
\timing off
```

Resetting prevents later queries from unexpectedly printing in CSV format, continuing to write to a file, or rendering overly long expanded output.

## 18. Common mistakes with the query buffer and output formatting

| Symptom | Common cause | How to handle |
|---|---|---|
| Prompt changes from `=>` to `->`, query hasn't run | Missing `;` or `\g` | Finish the SQL statement, use `\g`, or `\r` to cancel |
| Prompt changes to `'>` | Unclosed single-quoted string | Close the quote properly or `\r` |
| Typed `\r` yet data still changed | DML already executed earlier | `\r` only clears drafts; use transaction/rollback while still possible |
| `UPDATE` ran a second time | Typed `\g` after `;` already submitted it | Don't re-submit without checking; avoid duplicate DML |
| Output too wide | Many columns or long values | `\x auto` or `\pset format wrapped` |
| No output appearing in terminal | Earlier `\o file` is still active | Type `\o` to restore stdout |
| Needed CSV but delimited file broke | Used unaligned when data contains delimiter | Use `\copy ... WITH (FORMAT csv)` or `\pset format csv` |
| Cannot distinguish NULL from empty string | Default display is unclear | `\pset null '[NULL]'` |
| `\s` not recognized | psql version/build lacks that history support | Check `\?` and environment history setup |
| History contains secrets | Typed password/token into SQL or command | Protect history/logs and rotate secrets if needed |
| `\timing` differs from `EXPLAIN ANALYZE` | One is client-side, one is server-instrumented | Compare appropriate scopes/conditions; avoid single-run conclusions |
| Small test SELECT shows `Seq Scan` | Planner finds table scan cheaper than index | Evaluate on representative data; don't assume it's a bug |
| Script produces hard-to-parse output | `.psqlrc` changed formatting or enabled pager | Use `psql -X` and set output options explicitly |

## 20. Rules of thumb when working with psql

```text
TYPE SQL STATEMENT
     │
     ▼
Query buffer in psql
     ├── \p  : preview drafted content
     ├── \e  : edit in external editor
     ├── \w  : save SQL statement to file
     ├── \r  : clear draft
     └── ; / \g : SUBMIT SQL TO EXECUTE
                       │
                       ▼
                 PostgreSQL Server
                       │
              Planner / Executor
                       │
                       ▼
                   Result set
                       │
                       ▼
                  psql output
            ┌──────────┼───────────┐
            │          │           │
            ▼          ▼           ▼
     \pset / \x      \o / \g     \timing
     formatting      write file  timing
            │          │           │
            └──────────┴───────────┘
                       │
                       ▼
               User / script

History:
  Arrows / Ctrl+R / \s / HISTFILE
  → helps recall entered commands;
    not a transaction log or audit log.
```

Five core takeaways:

1. **Output formatting is client-side work.** `\pset`, `\x`, `\a`, `\t`, the pager, and `\o` help view or export data; they never change the semantics of a `SELECT`.
2. **The query buffer only holds the SQL currently being composed.** `\p` views it, `\e` edits it, `\w` saves it, `\r` clears it; `;` and `\g` submit it for execution.
3. **History is not server transaction history.** It boosts terminal productivity, but can be truncated, incomplete, and contain sensitive information.
4. **`\timing` and `EXPLAIN ANALYZE` do not replace each other.** One measures client-side elapsed time; the other explains the server's execution plan and costs.
5. **Safety before convenience.** Commands recalled from history, statements in the query buffer, and scripts can modify real data. Confirm the right database/schema, check conditions, transactions, and blast radius before submitting.

Mastering these tools makes learning and operating PostgreSQL less reliant on trial and error: you can **compose SQL deliberately, inspect results in the right format, export data cleanly, and use the right measurements to diagnose slow queries**.
