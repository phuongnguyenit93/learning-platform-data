# Data-Modifying CTEs and Data Flow via RETURNING in PostgreSQL

A PostgreSQL query does not only use `WITH` to create temporary result tables for `SELECT`. Inside a *common table expression* (CTE), PostgreSQL also allows running **`INSERT`, `UPDATE`, `DELETE`**, and in supported versions, other data-modifying statements. When combined with **`RETURNING`**, the output of an earlier modification step can be passed directly to the next step **within the same SQL statement**.

Common real-world use cases:

- Create a customer and immediately use the generated `customer_id` to create an order.
- Transition orders from `pending` to `paid` and record history for **only those orders whose status actually changed**.
- Delete eligible records and move the deleted rows into an archive table.
- Safely decrement inventory with a guard condition, then record an inventory movement row.
- Mutate business data and emit a **transactional outbox** event in a single atomic operation.

However, data-modifying CTEs follow crucial rules: **data-modifying steps always run to completion**, **execution order across peer branches is not guaranteed**, steps share **the same statement snapshot**, and **you must not attempt to modify the same row twice within one statement**. Understanding these rules is essential for writing SQL that is both concise and transactionally sound.

## 1. Reviewing CTEs and RETURNING

A CTE is declared using `WITH`:

~~~sql
WITH active_customers AS (
    SELECT customer_id, full_name
    FROM customers
    WHERE is_active = true
)
SELECT *
FROM active_customers;
~~~

In this example, the CTE `active_customers` is a temporary row source read by the outer query. It **does not modify data**.

With a data-modifying CTE, the CTE body is a data-modification statement:

~~~sql
WITH changed AS (
    UPDATE orders
    SET status = 'paid'
    WHERE order_id = 101
    RETURNING order_id, status
)
SELECT order_id, status
FROM changed;
~~~

Here:

1. `UPDATE` locates order 101 and updates its status if a matching row exists.
2. `RETURNING` emits values from the row that was actually updated.
3. The CTE name `changed` becomes a **table-like row source** for the outer `SELECT`.
4. If no row was updated, `changed` produces **0 rows**.

The key distinction is that `changed` is **not a copy of the `orders` table**. It contains only the columns and rows emitted by `RETURNING`.

### Statements supporting RETURNING

PostgreSQL supports `RETURNING` on data-modifying statements such as:

| Statement | Meaning of returned data |
| --- | --- |
| `INSERT ... RETURNING` | Values of inserted rows, including generated IDs and defaults |
| `UPDATE ... RETURNING` | Post-update row values for the requested expressions |
| `DELETE ... RETURNING` | Values of deleted rows, useful for archiving/auditing |
| `MERGE ... RETURNING` | Availability varies by PostgreSQL version; verify server and docs syntax |

This lesson uses `INSERT`, `UPDATE`, and `DELETE` to avoid relying on `MERGE` differences across major versions.

## 2. Diagram of Data Flow via RETURNING

~~~mermaid
flowchart TD
    A["Current business table"] --> B["UPDATE / INSERT / DELETE"]
    B --> C["RETURNING modified rows"]
    C --> D["CTE: changed_rows"]
    D --> E["INSERT into audit / archive / outbox"]
    D --> F["SELECT returning results to application"]
    E --> G["One atomic statement"]
    F --> G
~~~

The critical insight is that the arrow from `changed_rows` to subsequent steps **flows through `RETURNING` data**, not by re-reading the base table in the same SQL statement.

Example:

~~~sql
WITH newly_inserted AS (
    INSERT INTO customers (full_name)
    VALUES ('An')
    RETURNING customer_id, full_name
)
SELECT customer_id, full_name
FROM newly_inserted;
~~~

If `customer_id` is auto-generated, the CTE returns the new ID directly. There is no need to run `SELECT MAX(customer_id)` or guess which row was "just created".

## 3. Setting Up the Practice Dataset

The remaining examples use a dedicated schema `dml_cte_lab` in a **PostgreSQL database dedicated to learning**. The script recreates the schema and drops existing data via `DROP SCHEMA ... CASCADE`, so **only run it after confirming you are in a lab database with no data you need to keep**.

### 3.1. Creating the schema and tables

~~~sql
-- RUN ONLY IN A DEDICATED LAB DATABASE.
DROP SCHEMA IF EXISTS dml_cte_lab CASCADE;
CREATE SCHEMA dml_cte_lab;

CREATE TABLE dml_cte_lab.customers (
    customer_id bigint GENERATED BY DEFAULT
        AS IDENTITY (START WITH 1000) PRIMARY KEY,
    email text NOT NULL UNIQUE,
    full_name text NOT NULL
);

CREATE TABLE dml_cte_lab.orders (
    order_id bigint GENERATED BY DEFAULT
        AS IDENTITY (START WITH 2000) PRIMARY KEY,
    customer_id bigint NOT NULL
        REFERENCES dml_cte_lab.customers(customer_id),
    status text NOT NULL
        CHECK (status IN ('pending', 'paid', 'cancelled')),
    total numeric(12, 2) NOT NULL
        CHECK (total >= 0),
    created_at timestamptz NOT NULL DEFAULT now(),
    paid_at timestamptz
);

-- Intentionally NO FK from audit.order_id to orders:
-- audit records must persist even if the order is deleted.
CREATE TABLE dml_cte_lab.order_audit (
    audit_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_id bigint NOT NULL,
    action text NOT NULL,
    previous_status text,
    new_status text,
    amount numeric(12, 2),
    recorded_at timestamptz NOT NULL DEFAULT now()
);

-- Transactional outbox: events written together with business data.
CREATE TABLE dml_cte_lab.outbox_events (
    event_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    aggregate_type text NOT NULL,
    aggregate_id bigint NOT NULL,
    event_name text NOT NULL,
    payload jsonb NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now(),
    published_at timestamptz
);

-- Archive table storing deleted/moved orders.
CREATE TABLE dml_cte_lab.orders_archive (
    order_id bigint PRIMARY KEY,
    customer_id bigint NOT NULL,
    status text NOT NULL,
    total numeric(12, 2) NOT NULL,
    created_at timestamptz NOT NULL,
    paid_at timestamptz,
    archived_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE dml_cte_lab.inventory (
    product_id integer PRIMARY KEY,
    quantity integer NOT NULL CHECK (quantity >= 0)
);

CREATE TABLE dml_cte_lab.inventory_movements (
    movement_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    product_id integer NOT NULL
        REFERENCES dml_cte_lab.inventory(product_id),
    delta integer NOT NULL CHECK (delta <> 0),
    quantity_after integer NOT NULL CHECK (quantity_after >= 0),
    recorded_at timestamptz NOT NULL DEFAULT now()
);
~~~

This design supports multiple independent examples:

- `customers` and `orders`: creating parent–child rows and updating statuses.
- `order_audit`: recording evidence of status transitions.
- `outbox_events`: storing events for a separate worker to publish after transaction commit.
- `orders_archive`: receiving rows deleted from the active table.
- `inventory` and `inventory_movements`: decrementing stock while logging movements.

The ID columns use `GENERATED BY DEFAULT AS IDENTITY` so we can seed fixed IDs while subsequent auto-generated IDs start in a separate range for predictable examples. In production systems, manage sequences carefully and avoid ad-hoc manual ID inserts without an explicit policy.

    (103, 2, 'pending',   200.00, '2026-11-03 08:00:00+00', NULL),

INSERT INTO dml_cte_lab.inventory

~~~

Initial state:

| order_id | customer_id | status | total |
| ---: | ---: | --- | ---: |
| 101 | 1 | pending | 120.00 |
| 102 | 1 | paid | 75.00 |
| 103 | 2 | pending | 200.00 |

When you intentionally want to keep changes in the lab, replace `ROLLBACK` with `COMMIT` deliberately—never do that on production data.

## 4. INSERT ... RETURNING: Getting Newly Generated IDs

The most basic step is inserting a row and receiving its primary key in the same SQL statement.

~~~sql
INSERT INTO dml_cte_lab.customers
    (email, full_name)
VALUES
    ('dung@example.test', 'Dung')
RETURNING customer_id, email, full_name;
~~~

PostgreSQL returns the identity-generated ID along with email and name. **The exact ID value may vary across runs** because sequences normally do not roll back alongside table rows.

To test without persisting:

~~~sql
BEGIN;

INSERT INTO dml_cte_lab.customers
    (email, full_name)
VALUES
    ('dung@example.test', 'Dung')
RETURNING customer_id, email;

ROLLBACK;
~~~

After rollback, the customer row is undone, yet the allocated sequence value remains consumed. Do not expect the next INSERT to reuse that exact number.

### Why not use MAX(id) to find the newly created row?

This approach is unreliable in multi-session systems:

~~~sql
-- DO NOT use to infer a newly generated ID.
SELECT MAX(customer_id)
FROM dml_cte_lab.customers;
~~~

Another transaction might just have inserted a row with a higher ID, or allocated IDs may not match commit order. `RETURNING` retrieves the ID **from your exact INSERT operation**, guaranteeing accuracy for the rows your statement inserted.

## 5. First Data-Modifying CTE: Create Customer Then Create Order

Combine both steps in **one SQL statement**:

~~~sql
BEGIN;

WITH new_customer AS (
    INSERT INTO dml_cte_lab.customers
        (email, full_name)
    VALUES
        ('dung@example.test', 'Dung')
    RETURNING customer_id
)
INSERT INTO dml_cte_lab.orders
    (customer_id, status, total)
SELECT
    customer_id,
    'pending',
    0.00
FROM new_customer
RETURNING order_id, customer_id, status, total;

ROLLBACK;
~~~

Explanation:

1. The `new_customer` CTE executes `INSERT` into `customers`.
2. `RETURNING customer_id` produces a stream with the ID of the newly inserted customer.
3. `INSERT INTO orders ... SELECT ... FROM new_customer` uses that ID to create the order.
4. `RETURNING` on the **main INSERT** returns the order ID and related fields.
5. If any constraint or step fails, the statement is never half-committed.
6. `ROLLBACK` restores the lab data to its pre-test state.

### Explicit data flow without re-reading the base table

~~~mermaid
flowchart LR
    A["INSERT customers"] --> B["RETURNING customer_id"]
    B --> C["CTE new_customer"]
    C --> D["INSERT orders ... SELECT FROM new_customer"]
    D --> E["RETURNING order_id"]
~~~

The new key passes directly through `RETURNING`. This is crucial whenever the first command generates data needed by the next command.

Never write:

~~~sql
-- Do not re-read to guess the newly created customer.
SELECT customer_id
FROM dml_cte_lab.customers
ORDER BY customer_id DESC
LIMIT 1;
~~~

That can pick up another user's customer and fails to express the causal link between the two operations.

## 6. UPDATE ... RETURNING: Receiving Only Actually Updated Rows

When transitioning order status, we often want to know **which orders actually passed the allowed status precondition**.

~~~sql
BEGIN;

UPDATE dml_cte_lab.orders
SET
    status = 'paid',
    paid_at = now()
WHERE order_id = 101
  AND status = 'pending'
RETURNING
    order_id,
    customer_id,
    status,
    total,
    paid_at;

ROLLBACK;
~~~

With the seed data, order 101 qualifies and `RETURNING` emits **one row**.

In contrast:

~~~sql
UPDATE dml_cte_lab.orders
SET status = 'paid'
WHERE order_id = 102
  AND status = 'pending'
RETURNING order_id;
~~~

returns **0 rows**, because order 102 is already `paid`. Filtering by current status prevents emitting a "transitioned to paid" history record when no valid transition actually occurred.

### RETURNING does not automatically prove "a value changed"

If you write:

~~~sql
UPDATE dml_cte_lab.orders
SET status = 'paid'
WHERE order_id = 102
RETURNING order_id, status;
~~~

the statement still updates one row, even though `status` was `paid` both before and after. `RETURNING` emits **rows touched by UPDATE**, which does not mean every column changed value.

If business logic requires emitting events only upon actual state transitions, include the transition guard in `WHERE` (such as `status = 'pending'`) paired with appropriate concurrency handling.

## 7. UPDATE CTE Followed by INSERT into an Audit Table

Problem: when order 101 transitions from `pending` to `paid`, insert an audit row for **the exact order that was updated**.

~~~sql
BEGIN;

WITH changed_orders AS (
    UPDATE dml_cte_lab.orders AS o
    SET
        status = 'paid',
        paid_at = now()
    WHERE o.order_id = 101
      AND o.status = 'pending'
    RETURNING
        o.order_id,
        o.customer_id,
        o.status,
        o.total
)
INSERT INTO dml_cte_lab.order_audit
    (order_id, action, previous_status, new_status, amount)
SELECT
    c.order_id,
    'status_changed',
    'pending',
    c.status,
    c.total
FROM changed_orders AS c
RETURNING
    audit_id,
    order_id,
    previous_status,
    new_status,
    amount;

SELECT order_id, status
FROM dml_cte_lab.orders
WHERE order_id = 101;

SELECT audit_id, order_id, action, new_status
FROM dml_cte_lab.order_audit
ORDER BY audit_id;

ROLLBACK;
~~~

**Result inside the transaction before rollback:**

- Order 101 has `status = 'paid'`.
- One new row in `order_audit` has `order_id = 101`, `previous_status = 'pending'`, and `new_status = 'paid'`.
- `INSERT INTO order_audit` inserts **0 rows** if `changed_orders` returns zero rows.

### Why did the example write previous_status = 'pending'?

`WHERE o.status = 'pending'` guarantees every updated row was in `pending` immediately prior to this valid transition, so we can record that value as a deterministic business rule.

When transitioning from **multiple possible initial statuses**, never hardcode `'pending'` for every row. Use a mechanism to capture the pre-update value appropriate to your PostgreSQL version and concurrency design, or handle auditing in a properly designed trigger. Ordinary `UPDATE ... RETURNING o.status` gives the **post-update** value and does not expose an `old_status` column by that name.

### Linkage guaranteed by returned rows

A two-statement design in application code:

~~~text
UPDATE orders ...
INSERT INTO order_audit ...
~~~

can also be correct inside a transaction with proper row-count/`RETURNING` checks. However, if the application updates and then **unconditionally inserts an audit row**, it can record false history for records already in the target state or missing altogether.

A data-modifying CTE expresses this cleanly: **audit only the rows actually emitted by `UPDATE ... RETURNING`**.

## 8. Combining Two INSERTs Depending on One UPDATE

A realistic scenario: when an order transitions to `paid`, simultaneously:

- Write history to `order_audit`.
- Write an event to `outbox_events` for an external worker to process later.
- Return both the audit ID and event ID to the application.

~~~sql
BEGIN;

WITH transitioned AS (
    UPDATE dml_cte_lab.orders AS o
    SET
        status = 'paid',
        paid_at = now()
    WHERE o.order_id = 103
      AND o.status = 'pending'
    RETURNING
        o.order_id,
        o.customer_id,
        o.status,
        o.total
),
audit_written AS (
    INSERT INTO dml_cte_lab.order_audit
        (order_id, action, previous_status, new_status, amount)
    SELECT
        t.order_id,
        'status_changed',
        'pending',
        t.status,
        t.total
    FROM transitioned AS t
    RETURNING audit_id, order_id
),
event_written AS (
    INSERT INTO dml_cte_lab.outbox_events
        (aggregate_type, aggregate_id, event_name, payload)
    SELECT
        'order',
        t.order_id,
        'order.paid',
        jsonb_build_object(
            'order_id', t.order_id,
            'customer_id', t.customer_id,
            'status', t.status,
            'total', t.total
        )
    FROM transitioned AS t
    RETURNING event_id, aggregate_id
)
SELECT
    a.order_id,
    a.audit_id,
    e.event_id
FROM audit_written AS a
JOIN event_written AS e
    ON e.aggregate_id = a.order_id;

ROLLBACK;
~~~

In the seed data, order 103 qualifies:

1. `transitioned` returns one row for order 103.
2. `audit_written` consumes it and inserts one audit row.
3. `event_written` consumes **the same `transitioned` RETURNING stream** and inserts one outbox row.
4. The final `SELECT` joins both newly created IDs on `order_id`.
5. If either write fails, no partial state of the statement is committed.

**Subtle point:** `audit_written` and `event_written` do not have to run linearly as "audit first, event second"; both read the same `transitioned` stream and write to **two different tables**. Never rely on physical execution order between two independent branches. If a later branch needs data generated only after writing the audit (such as `audit_id`), have it **read directly from `audit_written` via `RETURNING`** to establish an explicit dependency.

### Multi-stage dependency example

~~~sql
WITH inserted_audit AS (
    INSERT INTO dml_cte_lab.order_audit
        (order_id, action)
    VALUES
        (101, 'manual_review')
    RETURNING audit_id, order_id
),
inserted_event AS (
    INSERT INTO dml_cte_lab.outbox_events
        (aggregate_type, aggregate_id, event_name, payload)
    SELECT
        'order',
        a.order_id,
        'audit.created',
        jsonb_build_object('audit_id', a.audit_id)
    FROM inserted_audit AS a
    RETURNING event_id, payload
)
SELECT event_id, payload
FROM inserted_event;
~~~

Here `inserted_event` receives the newly generated `audit_id` **through `inserted_audit`'s `RETURNING`**, rather than guessing IDs with `MAX(audit_id)`. When running in the lab, wrap this statement in `BEGIN ... ROLLBACK` to preserve the seed data.

## 9. DELETE ... RETURNING: Capturing the Exact Deleted Rows

`DELETE ... RETURNING` returns data from **the rows deleted**. This is the foundation for moving rows from an active table to an archive table.

Simple example:

~~~sql
BEGIN;

DELETE FROM dml_cte_lab.orders
WHERE order_id = 104
  AND status = 'cancelled'
RETURNING
    order_id,
    customer_id,
    status,
    total,
    created_at,
    paid_at;

ROLLBACK;
~~~

Inside the transaction, order 104 is gone from `orders` and its columns appear in `RETURNING` output. After rollback, the row exists again.

**Do not confuse `RETURNING` with a `SELECT` reading after deletion.** `DELETE` is the mutating operation; `RETURNING` is that operation's own output.

## 10. Archiving Data in a Single Statement

Example: move `cancelled` orders into `orders_archive` while deleting them from the active table.

~~~sql
BEGIN;

WITH moved AS (
    DELETE FROM dml_cte_lab.orders
    WHERE status = 'cancelled'
    RETURNING
        order_id,
        customer_id,
        status,
        total,
        created_at,
        paid_at
)
INSERT INTO dml_cte_lab.orders_archive
    (order_id, customer_id, status, total, created_at, paid_at)
SELECT
    order_id,
    customer_id,
    status,
    total,
    created_at,
    paid_at
FROM moved
RETURNING order_id, status, archived_at;

-- Inspect after the move statement completes:
SELECT order_id
FROM dml_cte_lab.orders
WHERE order_id = 104;

SELECT order_id, status, total
FROM dml_cte_lab.orders_archive
WHERE order_id = 104;

ROLLBACK;
~~~

On the seed data, `moved` produces one row (order 104). The main `INSERT` consumes `moved` and writes it to the archive.

### Why use DELETE ... RETURNING instead of SELECT then DELETE?

A naive workflow:

~~~text
SELECT * FROM orders WHERE status = 'cancelled';
INSERT INTO orders_archive ...;
DELETE FROM orders WHERE status = 'cancelled';
~~~

can suffer several bugs if executed as separate uncoordinated statements:

- A row's status could change between `SELECT` and `DELETE`.
- The archive `INSERT` could succeed while `DELETE` fails, or vice versa, without a transaction.
- Conditions in the separate SQL statements could drift, leaving archived rows out of sync with deleted rows.
- It could read rows that no longer qualify by the time `DELETE` executes.

With `DELETE ... RETURNING`, **the moved rows are strictly the exact rows `DELETE` removed**. If the archive `INSERT` violates a unique or other constraint, the whole statement errors and `DELETE` is never committed on its own.

### Watch out for foreign keys and data lifecycle

The lab example has no child tables referencing `orders.order_id`. In real systems, deleting an order may be blocked by `order_items` FKs or cascade-delete dependent rows. An archival workflow must account for **all referencing relationships**, retention policies, and compliance requirements. Never treat CTEs as a way to bypass foreign keys.

## 11. Conditional Updates for Safe Inventory Decrement

Suppose product 501 has `quantity = 8`, and we need to ship 3 units.

An unsafe approach is:

~~~text
SELECT quantity FROM inventory WHERE product_id = 501;
-- Application sees 8 and decides to subtract 3.
UPDATE inventory SET quantity = 5 WHERE product_id = 501;
~~~

Between those two statements, another transaction may have modified inventory. Without proper synchronization, the application can overwrite changes or act on stale values.

Replace it with an **inline conditional update on the row**:

~~~sql
BEGIN;

UPDATE dml_cte_lab.inventory
SET quantity = quantity - 3
WHERE product_id = 501
  AND quantity >= 3
RETURNING product_id, quantity AS quantity_after;

ROLLBACK;
~~~

On the initial dataset, `quantity_after = 5`.

If remaining stock is less than 3, `WHERE quantity >= 3` does not match and `RETURNING` emits 0 rows. Together with `CHECK(quantity >= 0)`, this cleanly enforces no negative inventory.

### Why does this work under concurrent writes?

PostgreSQL manages row locks and `UPDATE` consistency. Under standard isolation levels, when two transactions attempt to update the same row concurrently, PostgreSQL coordinates lock waiting and predicate re-evaluation per MVCC rules. Checking `quantity >= 3` inside `UPDATE` itself is far more reliable than **reading quantity and overwriting it with a value computed from a stale read**.

Do not assume a single `UPDATE` solves every concurrency scenario: isolation levels, deadlocks, serialization failures, multi-product orders, and cross-row invariants still require explicit design.

## 12. Updating Inventory and Logging Movements via RETURNING

Extending the stock-decrement step: log a movement row only when the inventory update succeeds.

~~~sql
BEGIN;

WITH stock_changed AS (
    UPDATE dml_cte_lab.inventory AS i
    SET quantity = i.quantity - 3
    WHERE i.product_id = 501
      AND i.quantity >= 3
    RETURNING
        i.product_id,
        i.quantity AS quantity_after
)
INSERT INTO dml_cte_lab.inventory_movements
    (product_id, delta, quantity_after)
SELECT
    s.product_id,
    -3,
    s.quantity_after
FROM stock_changed AS s
RETURNING
    movement_id,
    product_id,
    delta,
    quantity_after;

ROLLBACK;
~~~

Result inside the transaction: one movement row with `product_id = 501`, `delta = -3`, and `quantity_after = 5`.

If tested on product 502, which has `quantity = 0`:

~~~sql
WITH stock_changed AS (
    UPDATE dml_cte_lab.inventory AS i
    SET quantity = i.quantity - 3
    WHERE i.product_id = 502
      AND i.quantity >= 3
    RETURNING i.product_id, i.quantity
)
INSERT INTO dml_cte_lab.inventory_movements
    (product_id, delta, quantity_after)
SELECT product_id, -3, quantity
FROM stock_changed
RETURNING movement_id;
~~~

`stock_changed` returns zero rows, so the movement `INSERT` **also inserts zero rows**.

Still, this only covers **processing a request once**. If the same request is retried twice, stock could be deducted twice. Add an idempotency key and unique constraint per business design to prevent duplicate processing—never assume `WITH` or `RETURNING` provides idempotency automatically.

## 13. RETURNING Can Return Expressions, Not Just Columns

`RETURNING` accepts an expression list much like `SELECT`.

~~~sql
BEGIN;

UPDATE dml_cte_lab.orders
SET
    total = total + 10.00
WHERE order_id = 101
RETURNING
    order_id,
    total,
    total * 0.10 AS ten_percent_reference,
    status,
    now() AS statement_time;

ROLLBACK;
~~~

In `UPDATE ... RETURNING`, `total` is the **post-update** value, which becomes 130.00 on the seed data. `total * 0.10` is computed from 130.00. The `ten_percent_reference` column merely illustrates an expression, not a universal tax/fee formula.

You can also construct JSON:

~~~sql
BEGIN;

UPDATE dml_cte_lab.orders AS o
SET status = 'paid', paid_at = now()
WHERE o.order_id = 101
  AND o.status = 'pending'
RETURNING
    o.order_id,
    jsonb_build_object(
        'order_id', o.order_id,
        'customer_id', o.customer_id,
        'status', o.status,
        'total', o.total
    ) AS event_payload;

ROLLBACK;
~~~

When output feeds an application or another CTE, building JSON directly can avoid inconsistent payload assembly in application code. Still, JSON payloads should follow proper event schemas and versioning rules.

## 14. Core Rule: Data-Modifying CTEs Always Run to Completion

This is a critical difference from many `SELECT` CTEs.

Example:

~~~sql
BEGIN;

WITH inserted AS (
    INSERT INTO dml_cte_lab.order_audit (order_id, action)
    VALUES
        (101, 'sample_a'),
        (102, 'sample_b')
    RETURNING audit_id, order_id
)
SELECT audit_id
FROM inserted
LIMIT 1;

SELECT COUNT(*) AS audit_rows
FROM dml_cte_lab.order_audit;

ROLLBACK;
~~~

The outer `SELECT ... LIMIT 1` **returns only one row**, yet the `INSERT` CTE still inserts **both rows**. Inside the transaction, the audit row count increases by 2, not 1.

This differs from some `SELECT` CTEs where PostgreSQL may evaluate only as many rows as the parent query pulls.

**Never use an outer `LIMIT` to control how many rows a CTE updates, deletes, or inserts.** To cap mutated rows, build an explicit row-selection predicate **in the DML source itself** with deterministic ordering and concurrency controls.

### Data-modifying CTE without RETURNING

PostgreSQL allows a data-modifying CTE without `RETURNING`:

~~~sql
BEGIN;

WITH touched AS (
    UPDATE dml_cte_lab.orders
    SET total = total + 1.00
    WHERE order_id = 101
)
SELECT 'executed' AS result;

ROLLBACK;
~~~

The `UPDATE` still executes even though the outer `SELECT` never reads from `touched`. However, without `RETURNING`, `touched` **produces no result table for downstream steps to reference**.

Therefore, whenever passing data between steps, `RETURNING` is essential—not decorative.

## 15. Snapshot Rule: CTEs in the Same Statement Do Not See Each Other's Edits via Base Tables

This is the easiest point to misunderstand when starting with data-modifying CTEs.

Data-modifying parts of a `WITH` statement and the main query share **the same statement-level snapshot**. Never expect another `SELECT` in the same statement to re-read the base table and see edits performed by a sibling DML CTE.

Look at this:

~~~sql
BEGIN;

WITH changed AS (
    UPDATE dml_cte_lab.orders AS o
    SET status = 'paid'
    WHERE o.order_id = 101
      AND o.status = 'pending'
    RETURNING o.order_id, o.status
)
SELECT
    changed.order_id,
    changed.status AS status_from_returning,
    (
        SELECT original.status
        FROM dml_cte_lab.orders AS original
        WHERE original.order_id = changed.order_id
    ) AS status_from_base_table
FROM changed;

ROLLBACK;
~~~

Under PostgreSQL's snapshot rules, this returns:

| order_id | status_from_returning | status_from_base_table |
| ---: | --- | --- |
| 101 | paid | pending |

- `status_from_returning` is the post-UPDATE value returned directly by DML.
- `status_from_base_table` comes from the base table's snapshot within **the same statement**, which does not see edits made by the DML CTE when scanning that base table.

If you run **a separate SELECT statement after the UPDATE statement finishes**, within the same transaction, your session sees its own committed/uncommitted transaction edits under normal transaction visibility:

~~~sql
BEGIN;

WITH changed AS (
    UPDATE dml_cte_lab.orders
    SET status = 'paid'
    WHERE order_id = 101
      AND status = 'pending'
    RETURNING order_id
)
SELECT COUNT(*) AS rows_changed
FROM changed;

-- This is a DIFFERENT statement, after the UPDATE statement.
SELECT order_id, status
FROM dml_cte_lab.orders
WHERE order_id = 101;

ROLLBACK;
~~~

The second `SELECT` sees `paid` inside the transaction because the prior update statement has completed.

### Design rule

**Within the same statement: if a later step needs freshly modified data, read `RETURNING` from the earlier step.** Never design a pipeline that mutates a table and expects another branch in the same statement to re-read the table and see the new state.

## 16. Execution Order Across Peer Data-Modifying CTEs Is Not Guaranteed

If you write two sibling branches:

~~~sql
WITH first_change AS (
    UPDATE dml_cte_lab.orders
    SET status = 'paid'
    WHERE order_id = 101
    RETURNING order_id
),
second_change AS (
    INSERT INTO dml_cte_lab.order_audit (order_id, action)
    VALUES (101, 'logged')
    RETURNING audit_id
)
SELECT ...
~~~

writing one branch **before** another does not mean PostgreSQL promises to run the first before the second in the effect order you expect. Data-modifying CTEs in the same statement execute under shared-snapshot rules; **actual execution order must not be relied upon**.

Moreover, `second_change` in the snippet inserts an audit row **unconditionally**; even if `first_change` updated 0 rows, the audit row would still be inserted. That is a business-logic bug.

### Right way when a later branch depends on an earlier branch

~~~sql
WITH first_change AS (
    UPDATE dml_cte_lab.orders
    SET status = 'paid'
    WHERE order_id = 101
      AND status = 'pending'
    RETURNING order_id, status
),
second_change AS (
    INSERT INTO dml_cte_lab.order_audit
        (order_id, action, new_status)
    SELECT
        order_id,
        'status_changed',
        status
    FROM first_change
    RETURNING audit_id, order_id
)
SELECT audit_id, order_id
FROM second_change;
~~~

Because `second_change` reads **`first_change`'s `RETURNING`**, data flows explicitly. You never depend on physical execution order between two unrelated branches.

## 17. Do Not Modify the Same Row Twice in One Statement

PostgreSQL warns clearly: **attempting to update the same row twice within a single statement is not supported with reliably predictable outcomes**. This includes updating and deleting the same row across data-modifying CTE branches.

Example **never to write or run**:

~~~sql
-- ANTI-EXAMPLE: two branches updating the same order_id=101.
WITH a AS (
    UPDATE dml_cte_lab.orders
    SET total = total + 10
    WHERE order_id = 101
    RETURNING order_id
),
b AS (
    UPDATE dml_cte_lab.orders
    SET status = 'paid'
    WHERE order_id = 101
    RETURNING order_id
)
SELECT * FROM a;
~~~

You cannot rely on `a` followed by `b` in text order to produce a final row reflecting both edits. **Avoid touching the same row twice**, even when the two CTEs appear to edit disjoint columns.

### Merge into a single UPDATE

~~~sql
BEGIN;

WITH changed AS (
    UPDATE dml_cte_lab.orders
    SET
        total = total + 10,
        status = 'paid',
        paid_at = now()
    WHERE order_id = 101
      AND status = 'pending'
    RETURNING order_id, status, total
)
SELECT * FROM changed;

ROLLBACK;
~~~

Each row is updated once; `RETURNING` emits both the updated status and updated total.

If two mutations genuinely must happen **sequentially**, use **two separate statements inside one transaction**, checking the first statement's output before running the next. Using a transaction does not require cramming everything into one statement.

## 18. Data-Modifying CTEs Must Be Attached to a Top-Level WITH

An important syntactic/semantic restriction: data-modifying statements inside `WITH` are supported in PostgreSQL when `WITH` is attached to a **top-level statement**.

Valid:

~~~sql
WITH changed AS (
    DELETE FROM dml_cte_lab.orders
    WHERE order_id = 9999
    RETURNING order_id
)
SELECT order_id
FROM changed;
~~~

Or:

~~~sql
WITH created AS (
    INSERT INTO dml_cte_lab.order_audit
        (order_id, action)
    VALUES
        (101, 'sample')
    RETURNING audit_id
)
SELECT audit_id
FROM created;
~~~

Do not assume you can bury a data-modifying CTE inside an arbitrary **nested subquery** like a regular read-only CTE. PostgreSQL's placement rules for data-modifying CTEs differ from `SELECT` CTEs, and DML in `WITH` must live at the supported top-level statement level.

If you only need temporary tables for filtering or aggregation, use `SELECT` CTEs. If modifying data, place `WITH` at the appropriate outer statement level.

## 19. Atomicity: One Statement, One Commit Outcome

In PostgreSQL, a data-modifying SQL statement runs inside a transaction. When a data-modifying CTE combines an `UPDATE` with an audit `INSERT`:

~~~text
UPDATE orders
  → RETURNING
  → INSERT order_audit
~~~

the operations form a single **atomic statement**. If any step fails a constraint check, you can never end up with "UPDATE committed while audit INSERT failed" merely because they live in two CTEs of the same statement.

Example:

~~~sql
BEGIN;

WITH changed AS (
    UPDATE dml_cte_lab.orders
    SET status = 'paid'
    WHERE order_id = 101
      AND status = 'pending'
    RETURNING order_id, status
)
INSERT INTO dml_cte_lab.order_audit
    (order_id, action, new_status)
SELECT order_id, 'status_changed', status
FROM changed;

ROLLBACK;
~~~

The whole example rolls back to preserve lab data. In a real application, commit the transaction appropriately to persist changes.

### Atomicity does not guarantee business logic is right

A statement can be transactionally atomic yet logically wrong:

- An `UPDATE` missing `status = 'pending'` emits bogus events.
- An `INSERT` into the outbox builds a payload with the wrong key/tenant.
- An `INSERT` branch ignores `RETURNING` and writes history even when `UPDATE` touched 0 rows.
- An audit table lacks constraints preventing duplicate events on retries.
- A cascading delete affects far more tables than intended.

**Atomicity ensures a failing statement is never half-committed; it does not substitute for expressing business rules accurately.**

## 20. Data-Modifying CTEs Do Not Replace Multi-Statement Transactions

Sometimes a pipeline needs to:

1. Check user permissions.
2. Lock business rows.
3. Update multiple tables under complex conditions.
4. Re-read/return results or invoke application logic.
5. Commit or roll back together.

When expressing everything cleanly in one statement is awkward, multiple SQL statements inside a single transaction remain a completely valid design:

~~~sql
BEGIN;

-- 1. Select or lock the rows to process.
SELECT order_id, status
FROM dml_cte_lab.orders
WHERE order_id = 101
FOR UPDATE;

-- 2. Update with business guards.
UPDATE dml_cte_lab.orders
SET status = 'paid', paid_at = now()
WHERE order_id = 101 AND status = 'pending'
RETURNING order_id, status;

-- 3. Application or stored procedure checks row count,
-- then inserts audit/outbox rows if the transition succeeded.

COMMIT;
~~~

This is a **workflow sketch**, not a complete implementation since the audit/outbox writes and error handling must still be implemented.

The strength of a multi-statement transaction is that statements **execute sequentially in program order** and later statements see earlier changes within the same transaction. Conversely, data-modifying CTEs within one statement share a snapshot and must not be thought of as sequential DML steps ordered by text position.

## 21. Handling Zero RETURNING Rows in Applications

A predicate such as:

~~~sql
UPDATE dml_cte_lab.orders
SET status = 'paid'
WHERE order_id = 101
  AND status = 'pending'
RETURNING order_id;
~~~

can yield:

- **1 row:** status transition succeeded for order 101.
- **0 rows:** order does not exist, or its current status is not `pending`.
- **Error:** constraint violation, lock timeout, deadlock, permission error, serialization failure, connection drop, etc.

Never treat every zero-row result as a database error. It can be a completely normal outcome of the `WHERE` predicate.

An API may need to distinguish:

- Order not found (`404` per API design).
- Order already paid (`409` or idempotent success, depending on business rules).
- Order cancelled and ineligible for payment.
- Another transaction just processed the order, requiring a state refresh or conflict response.

Distinguishing these cases typically requires an **additional query** or application-level state handling; never infer from 0 rows that every case means "not found".

## 22. Combining RETURNING with JDBC

With PostgreSQL JDBC, rows returned by a `RETURNING` statement can be read via a `ResultSet`. Java example:

~~~java
import java.math.BigDecimal;
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;

public static boolean markPaid(
    Connection connection,
    long orderId
) throws SQLException {
    String sql = """
        WITH changed AS (
            UPDATE dml_cte_lab.orders
            SET status = 'paid', paid_at = now()
            WHERE order_id = ?
              AND status = 'pending'
            RETURNING order_id, total
        )
        INSERT INTO dml_cte_lab.order_audit
            (order_id, action, previous_status, new_status, amount)
        SELECT
            order_id, 'status_changed', 'pending', 'paid', total
        FROM changed
        RETURNING order_id, amount
        """;

    try (PreparedStatement ps =
             connection.prepareStatement(sql)) {
        ps.setLong(1, orderId);

        try (ResultSet rs = ps.executeQuery()) {
            if (!rs.next()) {
                return false;
            }

            long updatedOrderId = rs.getLong("order_id");
            BigDecimal amount = rs.getBigDecimal("amount");

            // In practice, return a DTO/business result instead of printing to console.
            System.out.println(
                "Paid order " + updatedOrderId +
                " amount=" + amount
            );

            return true;
        }
    }
}
~~~

This method illustrates **one order** and does not manage `commit`/`rollback` on the connection itself. In real applications, transaction boundaries should be managed consistently by the service layer; never toggle autocommit randomly on a shared connection.

### Why executeQuery()?

Even though the SQL performs both an `UPDATE` and an `INSERT`, the top-level command is `INSERT ... RETURNING`, which produces a result set. With standard pgJDBC, `executeQuery()` reads those returned rows. For top-level commands without a result set, use `executeUpdate()` or `execute()` per the JDBC contract.

### Use parameter binding

Never concatenate `orderId` or request inputs directly into the SQL string. `PreparedStatement` binds values via `?` placeholders, preventing SQL injection from user-supplied inputs. However, binding does not replace authorization: the SQL must still be scoped to the authenticated user/tenant at the appropriate layer.

## 23. Transactional Outbox: Mutating Data and Recording Events Together

A common problem in event-driven architectures: an order is marked paid in PostgreSQL, and a service wants to notify a message broker.

If the application does:

~~~text
1. UPDATE orders then COMMIT
2. Publish event to message broker
~~~

it can hit a failure where **the order committed yet the event was never sent**.

If reversed:

~~~text
1. Publish event
2. UPDATE orders then COMMIT
~~~

it can hit a failure where **the event was sent yet the database transaction rolled back**.

The **transactional outbox** pattern stores the event in a table inside the same database and transaction as the business mutation:

~~~mermaid
flowchart TD
    A["UPDATE orders"] --> B["RETURNING order_id/status"]
    B --> C["INSERT outbox_events"]
    C --> D{"COMMIT transaction"}
    D -->|"Success"| E["Worker reads outbox after commit"]
    E --> F["Publish to broker"]
    F --> G["Mark published_at"]
    D -->|"Rollback"| H["Neither order change nor event is committed"]
~~~

Data-modifying CTE example:

~~~sql
BEGIN;

WITH paid_orders AS (
    UPDATE dml_cte_lab.orders AS o
    SET
        status = 'paid',
        paid_at = now()
    WHERE o.order_id = 101
      AND o.status = 'pending'
    RETURNING
        o.order_id,
        o.customer_id,
        o.status,
        o.total
)
INSERT INTO dml_cte_lab.outbox_events
    (aggregate_type, aggregate_id, event_name, payload)
SELECT
    'order',
    p.order_id,
    'order.paid',
    jsonb_build_object(
        'order_id', p.order_id,
        'customer_id', p.customer_id,
        'total', p.total,
        'status', p.status
    )
FROM paid_orders AS p
RETURNING event_id, aggregate_id, event_name;

ROLLBACK;
~~~

To publish events in production, a separate worker reads **committed** events, publishes them to the broker, and manages retries and marking them published.

### Does an outbox guarantee exactly-once delivery?

**Not by default.** A worker can publish an event successfully and crash before updating `published_at`; on restart, it may publish the event again. Downstream consumers therefore typically need **idempotency/deduplication** and *at-least-once* processing design.

What the CTE guarantees is that **the business change and the outbox record share one atomic statement/transaction**, not that external messaging delivery is automatically exactly-once.

## 24. Multi-Row UPDATE and RETURNING as a Dataset

`RETURNING` is not restricted to one row. It returns **every row** affected by the DML statement.

Example transitioning all `pending` orders to `cancelled` in the lab:

~~~sql
BEGIN;

WITH cancelled AS (
    UPDATE dml_cte_lab.orders AS o
    SET status = 'cancelled'
    WHERE o.status = 'pending'
    RETURNING o.order_id, o.customer_id, o.status, o.total
)
INSERT INTO dml_cte_lab.order_audit
    (order_id, action, previous_status, new_status, amount)
SELECT
    order_id,
    'status_changed',
    'pending',
    status,
    total
FROM cancelled
RETURNING audit_id, order_id, new_status;

ROLLBACK;
~~~

In the seed data, two orders are `pending` (101 and 103). The `cancelled` CTE emits **two rows**, and `order_audit` receives **two rows**.

Do not assume row order in `RETURNING` matches primary-key order or physical update/insert order. If stable output ordering is needed for inspection, wrap it in an outer `SELECT` with `ORDER BY`.

Example:

~~~sql
WITH changed AS (
    UPDATE dml_cte_lab.orders
    SET status = 'cancelled'
    WHERE status = 'pending'
    RETURNING order_id, status
)
SELECT order_id, status
FROM changed
ORDER BY order_id;
~~~

The outer `SELECT` sorts the `RETURNING` rows without altering the physical order PostgreSQL used to update rows.

## 25. How Do DML CTEs Differ from SELECT CTEs?

| Property | SELECT CTE | Data-modifying CTE |
| --- | --- | --- |
| CTE body | `SELECT` | `INSERT` / `UPDATE` / `DELETE` |
| Modifies data | Not directly | Yes |
| Produces result set | SELECT result | Only via `RETURNING`, if present |
| Runs if output is unread | Depends on optimization/parent pull | **Always runs to completion** |
| Partial pull via outer LIMIT | May limit computed rows in some plans | Does not limit DML rows modified |
| Passing data between branches | Via SELECT rows | Via `RETURNING` rows |
| Nesting in subqueries | More flexible | Top-level restriction for data-modifying WITH |
| Order across sibling DML branches | Irrelevant if read-only | **Must not rely on textual order** |

A common misconception is treating `WITH a AS (UPDATE ...)` as "finish the UPDATE, then later CTEs can SELECT the updated table". More accurately, it produces **one DML action and one `RETURNING` stream** within a shared-snapshot statement.

## 26. Locks, Concurrency, and Limits to Understand

Data-modifying CTEs do not bypass PostgreSQL's transaction engine. Updated/deleted rows are still subject to locks, MVCC, foreign keys, triggers, unique constraints, RLS, and isolation rules.

### Two sessions paying the same order concurrently

Suppose two sessions simultaneously run:

~~~sql
WITH paid AS (
    UPDATE dml_cte_lab.orders
    SET status = 'paid', paid_at = now()
    WHERE order_id = 101
      AND status = 'pending'
    RETURNING order_id
)
INSERT INTO dml_cte_lab.order_audit
    (order_id, action, new_status)
SELECT order_id, 'paid', 'paid'
FROM paid;
~~~

Normally under `READ COMMITTED`, one session performs the update first; the second waits on the row lock, re-evaluates the condition against the updated row version, gets **0 rows**, and therefore inserts no duplicate audit record.

That is the strength of binding business logic into **`UPDATE` predicates** and **`RETURNING` rows**. However, under higher isolation levels, the system may need to handle serialization failures and retries. For complex multi-table workflows, design transactions, locking, and idempotency explicitly.

### Not automatically deadlock-free

If one workflow updates two tables in one order while another updates them in reverse order, deadlocks can still occur. Putting everything in one statement does not make it immune to deadlocks. Applications must detect and safely retry transient failures per policy.

### RETURNING does not bypass permissions

The role running the DML needs the corresponding INSERT/UPDATE/DELETE privilege, and using `RETURNING` on specific columns generally also requires `SELECT` privilege on those columns. Row-level security can restrict which rows DML may modify or return. Never treat `RETURNING *` as a way to read columns the role is not permitted to see.

## 27. Multi-Row DELETE Can Cascade

When a CTE uses:

~~~sql
WITH removed AS (
    DELETE FROM some_parent_table
    WHERE ...
    RETURNING parent_id
)
INSERT INTO audit_table (...)
SELECT ...
FROM removed;
~~~

it returns only rows deleted by `DELETE` from **the target table** `some_parent_table`. If `ON DELETE CASCADE` deletes child rows in another table, the parent's `RETURNING` **does not automatically include those deleted child rows**.

If child rows must also be audited/archived, design that workflow explicitly: whether cascades should be allowed, whether child audit triggers are needed, or whether child rows should be archived by parent key first. Never assume "parent `RETURNING` backed up the whole data tree".

### Do not confuse with TRUNCATE

`TRUNCATE` does not offer a row-by-row `DELETE ... RETURNING` stream. `TRUNCATE ... CASCADE` is a different mechanism that wipes **entire dependent tables**, unsuitable as a substitute for controlled row-level archiving.

## 28. Common Mistakes

### 28.1. Using WITH and forgetting RETURNING

~~~sql
WITH updated AS (
    UPDATE dml_cte_lab.orders
    SET status = 'paid'
    WHERE order_id = 101
)
SELECT * FROM updated;
~~~

There is no `updated` row set to reference. A data-modifying CTE can still execute without `RETURNING`, yet cannot pass rows forward like a table.

### 28.2. Thinking LIMIT 1 makes DML touch only one row

`LIMIT` in the outer query limits rows **returned**, not rows modified by the data-modifying CTE. Put row limits inside the DML source deliberately.

### 28.3. Re-reading the base table in the same statement to see new state

DML branches and the main query share a snapshot. To read freshly modified values, use **`RETURNING`**—never a `SELECT` re-scanning the base table in the same statement.

### 28.4. Assuming textual CTE order equals DML execution order

Sibling DML branches have no guaranteed execution order. Express dependencies via `RETURNING`; if the same row needs two sequential edits, use **two separate statements in a transaction**.

### 28.5. Attempting to update the same row in two CTEs

PostgreSQL does not guarantee intended outcomes when the same row is mutated twice in one statement. Combine column edits into one `UPDATE` or split into separate statements.

### 28.6. Unconditional audit inserts

If `INSERT audit` uses static `VALUES`, it runs even when `UPDATE` touches 0 rows. Use `INSERT ... SELECT FROM changed RETURNING` so audit rows match updated rows.

### 28.7. Treating RETURNING as pre-UPDATE row values

`UPDATE ... RETURNING` returns post-update values. When both before and after values are needed, use a version-appropriate and semantically valid approach rather than aliasing the new column as `old_status`.

### 28.8. Assuming data-modifying CTEs provide idempotency

An `UPDATE inventory SET quantity=quantity-3` will deduct again if a request is replayed. Use idempotency keys and unique constraints/transactions.

### 28.9. Using SELECT MAX(id) after INSERT

Unreliable under concurrent sessions and identity sequences. Use `INSERT ... RETURNING id`.

### 28.10. Assuming audit INSERT always succeeds if UPDATE succeeds

If the audit table hits a constraint violation or disk full, **the entire statement fails**. Applications must handle transactions and errors rather than ignoring them.

### 28.11. Treating an outbox as exactly-once publication

An outbox makes database state and event persistence atomic, not broker/consumer delivery deduplicated. Build idempotency and retries.

### 28.12. Archiving with DELETE while ignoring foreign keys

Deleting parent rows can be blocked by `RESTRICT` or silently wipe child rows via `CASCADE`. Account for the full data model and retention policy.

### 28.13. Failing to distinguish 0 rows from SQL errors

Empty `RETURNING` normally comes from `WHERE` matching zero rows; constraint, permission, deadlock, or serialization errors are failures requiring separate handling.

### 28.14. Ignoring that EXPLAIN ANALYZE executes DML

`EXPLAIN (ANALYZE)` actually runs the statement, including `UPDATE`/`DELETE`/`INSERT`. Never run it on live data just to "peek at the plan" without safety wrappers. Use plain `EXPLAIN` without `ANALYZE` for estimated plans.

## 29. Observing Execution Plans and Results

A statement with a DML CTE can still be inspected with `EXPLAIN`:

~~~sql
EXPLAIN
WITH changed AS (
    UPDATE dml_cte_lab.orders
    SET status = 'paid'
    WHERE order_id = 101
      AND status = 'pending'
    RETURNING order_id
)
SELECT order_id
FROM changed;
~~~

`EXPLAIN` without `ANALYZE` produces only the estimated plan without executing DML.

To measure execution timing in a lab database:

~~~sql
BEGIN;

EXPLAIN (ANALYZE, BUFFERS)
WITH changed AS (
    UPDATE dml_cte_lab.orders
    SET status = 'paid'
    WHERE order_id = 101
      AND status = 'pending'
    RETURNING order_id
)
SELECT order_id
FROM changed;

ROLLBACK;
~~~

Here `EXPLAIN ANALYZE` **actually runs the UPDATE**, so roll back afterward in the lab. Sequences, external side effects, or non-transactional state are not rolled back like table rows, so never treat rollback as a universal "time machine" for all side effects.

### Metrics to measure

- Actual rows updated, deleted, or inserted.
- Index usage on `WHERE` predicates, such as `orders.order_id`.
- Foreign key, trigger, and index maintenance overhead on target tables.
- Lock wait time under concurrent sessions.
- Row counts emitted in `RETURNING`.
- WAL volume, throughput, and transaction duration during bulk operations.

For large batches, process in chunks using stable keys/predicates, bounded batch sizes, and retry logic. Never put `LIMIT` on an outer `SELECT` thinking the DML is batched.

RETURNING movement_id, quantity_after;
~~~

**Answer:** Stock for 501 drops from 8 to 5; movement logs `delta = -3` and `quantity_after = 5`.

### Exercise 7. What if stock is 0?

Change `product_id = 501` to `502` in Exercise 6's query.

**Answer:** `quantity >= 3` does not match; UPDATE touches 0 rows and movement INSERT adds 0 rows.

### Exercise 8. Does an outer LIMIT 1 limit how many rows INSERT writes?

~~~sql
WITH a AS (
    INSERT INTO dml_cte_lab.order_audit (order_id, action)
    VALUES (101, 'A'), (102, 'B'), (103, 'C')
    RETURNING audit_id
)
SELECT audit_id
FROM a
LIMIT 1;
~~~

**Answer:** No. `INSERT` still inserts all three rows; `SELECT` merely returns one row. Use a transaction and rollback in the lab.

### Exercise 9. Why are two UPDATEs on the same order_id in two CTEs wrong?

**Answer:** PostgreSQL does not support modifying the same row twice in one statement with guaranteed ordering or intended cumulative outcomes. Combine into one `UPDATE` or use multiple statements in a transaction.

### Exercise 10. Emitting an outbox event on payment

~~~sql
WITH transitioned AS (
    UPDATE dml_cte_lab.orders
    SET status = 'paid', paid_at = now()
    WHERE order_id = 103
      AND status = 'pending'
    RETURNING order_id, customer_id, status, total
)
INSERT INTO dml_cte_lab.outbox_events
    (aggregate_type, aggregate_id, event_name, payload)
SELECT
    'order',
    order_id,
    'order.paid',
    jsonb_build_object(
        'order_id', order_id,
        'status', status,
        'total', total
    )
FROM transitioned
RETURNING event_id, event_name;
~~~

**Answer:** One event is inserted when order 103 updates; no event is inserted if the UPDATE predicate fails to match. An external worker dispatches events after commit and must handle retries/duplicates.

### Exercise 11. When do you need multiple statements instead of one DML CTE?

**Suggested answer:** When steps need strict sequential ordering, reading updated tables in a subsequent statement, running application logic between steps, or updating the same row across sequential phases. A transaction preserves atomicity without forcing everything into one statement.

### Exercise 12. Does a DML CTE without RETURNING still run?

**Answer:** Yes, a data-modifying CTE still runs to completion. However, without `RETURNING`, it produces no result set for another CTE or the main SELECT to read by name.

### Exercise 13. Why isn't auditing only the parent order enough for cascades?

**Answer:** `DELETE ... RETURNING` on the parent table returns only rows deleted from the parent table. If an FK cascade deletes child rows, preserving child history requires its own audit/archive mechanism.

### Exercise 14. Distinguishing 0 RETURNING rows from errors

**Answer:** 0 rows can come from `WHERE` matching nothing; errors indicate PostgreSQL could not execute the statement (constraints, permissions, deadlocks, serialization failures, etc.). Applications must distinguish the two.

## 31. Project Checklist When Using Data-Modifying CTEs

1. **Define the business mutation:** INSERT, UPDATE, or DELETE, and on which keys/conditions?
2. **Scope target rows tightly:** write explicit `WHERE` predicates to avoid overly broad updates/deletes.
3. **Select only needed returned fields:** list explicit columns in `RETURNING` instead of defaulting to `RETURNING *`.
4. **Pass data explicitly via RETURNING:** downstream branches read via `SELECT FROM cte_name`.
5. **Do not expect base-table re-reads in the same statement to see edits:** respect the shared snapshot.
6. **Do not rely on textual order of DML branches:** wire explicit data dependencies where needed.
7. **Never update/delete the same row twice:** merge edits or split into separate statements.
8. **Handle 0 rows cleanly:** distinguish predicate non-match from SQL errors.
9. **Verify FKs, triggers, constraints, and RLS:** DML obeys all database rules.
10. **Design transaction boundaries:** statements are atomic, yet multi-step workflows may need a broader transaction.
11. **Design for concurrency:** row locks, isolation, retries, and idempotency when multiple writers exist.
12. **Verify audit/outbox pipelines:** events follow mutated rows; outbox workers handle retries.
13. **Inspect execution plans safely:** `EXPLAIN` for plans; `EXPLAIN ANALYZE` only in controlled environments.
14. **Test edge cases:** 0 rows, 1 row, many rows, invalid statuses, duplicate keys, and FK cascades.
15. **Use a dedicated lab database while learning:** never run reset/archive/delete scripts on live data.

## 32. Summary

**Data-modifying CTEs** let PostgreSQL turn `RETURNING` into a row stream consumed by the rest of the SQL statement:

~~~sql
WITH changed_rows AS (
    UPDATE some_table
    SET some_column = some_value
    WHERE some_condition
    RETURNING id, some_column
)
INSERT INTO audit_table (entity_id, new_value)
SELECT id, some_column
FROM changed_rows;
~~~

This pattern is valuable because **the audit table receives data directly from the exact rows `UPDATE` modified**, rather than from a guessed or re-queried row set.

Key rules to remember:

- `INSERT/UPDATE/DELETE ... RETURNING` is the channel for retrieving inserted, modified, or deleted rows.
- Data-modifying CTEs **run to completion**, unaffected by an outer `LIMIT`.
- Branches within the same statement share a snapshot; **never re-SELECT the base table** to pass new state between branches.
- Execution order across peer DML CTEs **is not guaranteed**; express dependencies via `RETURNING`.
- Avoid mutating **the same row more than once in a single statement**.
- All operations remain governed by transactions, locks, FKs, triggers, RLS, and constraints.
- Auditing, archiving, and transactional outboxes are practical applications; atomicity does not replace authorization or idempotency.

When you model data flow cleanly through `RETURNING`, you can write complex PostgreSQL mutations that stay crystal clear: **only the rows that actually changed generate history, derived records, or downstream events**.
