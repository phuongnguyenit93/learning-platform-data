# Implementing Permissions and RLS for Multi-Tenant Data

In a multi-tenant model, a single application serves multiple organizations or tenants on the same system. Data may reside together in one PostgreSQL database, yet each tenant may only read and modify data within its own scope. A single query missing a tenant filter predicate can leak data across customers, so access control must be enforced across multiple layers.

PostgreSQL provides **Row-Level Security (RLS)** to restrict which rows a role may read or modify. Combining RLS with schema/table grants, tenant-scoped foreign keys, transaction-scoped tenant context, and tests executed under the actual application role establishes a strong defense-in-depth boundary for shared tables.

RLS does not replace user authentication or business-level authorization. The application must still authenticate the logged-in user, verify which tenants they belong to, and permit selecting only authorized tenants. RLS ensures the database enforces row-level isolation even if an application query forgets a tenant filter.

## 1. Multi-Tenant Data Models

Three common multi-tenant architectures exist:

| Model | Organization | Strengths | Considerations |
|---|---|---|---|
| Shared tables | Multiple tenants share tables; each row has `tenant_id` | Easy schema and resource management | Tenant boundary must be tightly enforced |
| Schema per tenant | Each tenant gets its own schema | Separates object names and schema-level privileges | Migrations, connection routing, and schema counts grow complex |
| Database per tenant | Each tenant gets its own database | Clearer data isolation and per-tenant backup/restore | Higher operational overhead for resources, connections, and migrations |

This lesson focuses on the shared-tables model, where RLS provides its clearest value. In this model, business tables carry a `tenant_id` column identifying row ownership.

Example customers and orders tables:

~~~sql
CREATE SCHEMA app;

CREATE TABLE app.customers (
    tenant_id uuid NOT NULL,
    customer_id bigint GENERATED BY DEFAULT AS IDENTITY,
    name text NOT NULL,
    email text,
    PRIMARY KEY (tenant_id, customer_id),
    UNIQUE (tenant_id, email)
);

CREATE TABLE app.orders (
    tenant_id uuid NOT NULL,
    order_id bigint GENERATED BY DEFAULT AS IDENTITY,
    customer_id bigint NOT NULL,
    external_id text NOT NULL,
    total_amount numeric(14, 2) NOT NULL CHECK (total_amount >= 0),
    status text NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (tenant_id, order_id),
    UNIQUE (tenant_id, external_id),
    FOREIGN KEY (tenant_id, customer_id)
        REFERENCES app.customers (tenant_id, customer_id)
);

~~~

Including `tenant_id` in primary keys and foreign keys is critical. If you use `customer_id` alone as a foreign key, an order row could accidentally reference another tenant's customer if IDs are generated or imported without global uniqueness. A composite foreign key forces the order's `tenant_id` and customer's `tenant_id` to match.

Similarly, unique constraints typically must include `tenant_id`. For example, two tenants may both use order code `INV-100`; `UNIQUE(tenant_id, external_id)` permits that while preventing duplicate codes within the same tenant.

RLS controls row accessibility. It does not replace primary key design, unique constraints, foreign keys, or data validation.

## 2. What Does RLS Protect?

When RLS is enabled on a table, PostgreSQL applies policies to decide which rows a role can see or mutate. Policies can be defined separately for `SELECT`, `INSERT`, `UPDATE`, `DELETE`, or for `ALL` commands.

For instance, users of tenant A can only read rows with a matching `tenant_id`. If a query omits `WHERE tenant_id = ...`, the policy still restricts the returned rows.

Key properties of RLS:

- RLS is a row-level control layer; table-level `SELECT`, `INSERT`, `UPDATE`, and `DELETE` privileges must still be granted separately.
- When RLS is enabled with no matching policy, PostgreSQL defaults to denying all rows.
- Policies govern which existing rows are visible and which new rows may be written.
- Table owners bypass RLS by default unless `FORCE ROW LEVEL SECURITY` is enabled.
- Superusers and roles with the `BYPASSRLS` attribute always bypass RLS.
- RLS does not authenticate tenant identity; the application must establish a trustworthy tenant context.

RLS does not automatically restrict columns. If a role has `SELECT` on a table, RLS filters rows; restricting sensitive columns requires column privileges, dedicated views, or table splitting.

## 3. Separating Database Roles and Privileges

A secure design separates the schema migration role from runtime application roles.

Examples:

- **`migration_owner`:** owns schemas, tables, indexes, and functions, and executes migrations.
- **`app_runtime`:** application role used to read/write data within granted scope.
- **`report_reader`:** read-only role for a scoped reporting pipeline.
- **`support_operator`:** controlled, audited support role if business workflows require cross-tenant access.

Applications should never connect as a superuser or table owner. If the application connects as the table owner, RLS does not apply to its queries by default. `FORCE ROW LEVEL SECURITY` enforces policies even on table owners, though superusers and `BYPASSRLS` roles still bypass them.

Create roles and grant schema/table privileges:

~~~sql
CREATE ROLE migration_owner NOLOGIN;
CREATE ROLE app_runtime LOGIN PASSWORD 'replace-with-secret';

ALTER SCHEMA app OWNER TO migration_owner;
ALTER TABLE app.customers OWNER TO migration_owner;
ALTER TABLE app.orders OWNER TO migration_owner;

GRANT USAGE ON SCHEMA app TO app_runtime;

GRANT SELECT, INSERT, UPDATE, DELETE
ON ALL TABLES IN SCHEMA app
TO app_runtime;
~~~

If tables rely on standalone sequences, grant the required sequence privileges:

~~~sql
GRANT USAGE, SELECT
ON ALL SEQUENCES IN SCHEMA app
TO app_runtime;
~~~

For identity columns, PostgreSQL manages internal sequences; required privileges depend on how the application inserts values and table structure/version. Explicitly granting sequence usage for sequences accessed directly is common practice when using `serial` or calling `nextval`.

So future tables automatically inherit appropriate grants, configure default privileges under the object-owning role:

~~~sql
ALTER DEFAULT PRIVILEGES FOR ROLE migration_owner
IN SCHEMA app
GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_runtime;

ALTER DEFAULT PRIVILEGES FOR ROLE migration_owner
IN SCHEMA app
GRANT USAGE, SELECT ON SEQUENCES TO app_runtime;
~~~

Default privileges are bound to the role that creates the object. If migrations execute under a different role, privileges configured for `migration_owner` will not apply to objects created by that other role. Standardize object ownership in your migration workflow.

Verify the application role holds no excessive privileges:

~~~sql
SELECT
    rolname,
    rolsuper,
    rolbypassrls,
    rolcreaterole,
    rolcreatedb
FROM pg_roles
WHERE rolname IN ('migration_owner', 'app_runtime');
~~~

`app_runtime` must be non-superuser, without `BYPASSRLS`, and must not own business tables. Runtime roles should also lack `CREATE` on application schemas unless explicitly needed.

## 4. Enabling Row-Level Security on Tables

Enable RLS on every table requiring tenant isolation:

~~~sql
ALTER TABLE app.customers ENABLE ROW LEVEL SECURITY;
ALTER TABLE app.orders ENABLE ROW LEVEL SECURITY;
~~~

To enforce policies even when queries run as the table owner:

~~~sql
ALTER TABLE app.customers FORCE ROW LEVEL SECURITY;
ALTER TABLE app.orders FORCE ROW LEVEL SECURITY;
~~~

`FORCE ROW LEVEL SECURITY` reduces the risk of an owner accidentally bypassing policies during routine queries. However, migrations and administrative jobs may need full-table access. Use a dedicated administrative role with strict controls and auditing for those tasks. Superusers and `BYPASSRLS` roles still bypass policies.

Once RLS is enabled, if no policy matches the command and role being used, PostgreSQL blocks all row access. Create policies for every legitimate operation immediately after enabling RLS before serving application traffic.

## 5. Setting Tenant Context per Transaction

Policies need to know the active tenant. A widespread pattern in shared-table applications stores the tenant ID in a custom PostgreSQL configuration parameter, which policies read via `current_setting`.

For example, policies use:

~~~sql
NULLIF(current_setting('app.tenant_id', true), '')::uuid
~~~

The second parameter `true` tells `current_setting` to return `NULL` instead of raising an error if the setting is unset. `NULLIF` handles empty strings. When context is unset, `tenant_id = NULL` never evaluates to `TRUE`, so the policy blocks all rows.

The application must set the tenant context inside the same transaction as its business queries:

~~~sql
BEGIN;

SELECT set_config('app.tenant_id', '11111111-1111-1111-1111-111111111111', true);

SELECT order_id, customer_id, total_amount, status
FROM app.orders
ORDER BY created_at DESC;

COMMIT;
~~~

The third parameter `true` scopes `set_config` strictly to the current transaction. Once the transaction ends, PostgreSQL restores the prior value. This works safely with connection pools where a physical connection is reused across requests for different tenants.

**Never set tenant context with session-level `SET` on pooled connections.** If stale tenant context lingers, the next request can execute under the previous tenant's scope. With transaction pooling or application connection pools, use transaction-local settings and guarantee tenant queries run on that exact transaction and connection.

An important caveat: `set_config(..., true)` preserves the value only for the current transaction. If you run `SELECT set_config` in autocommit mode and then run your query in the next statement, the first transaction has already ended and the context has reset. The application must open an explicit transaction, set the context, and then query.

### 5.1. Setting Context in Java/JDBC

Illustrative example using a single connection and transaction:

~~~java
try (Connection connection = dataSource.getConnection()) {
    connection.setAutoCommit(false);

    try {
        try (PreparedStatement context = connection.prepareStatement(
                "SELECT set_config('app.tenant_id', ?, true)")) {
            context.setString(1, authenticatedTenantId.toString());
            context.execute();
        }

        // Repository calls must use this same connection/transaction.
        Order order = orderRepository.findById(connection, orderId);

        connection.commit();
        return order;
    } catch (Exception exception) {
        connection.rollback();
        throw exception;
    }
}
~~~

`authenticatedTenantId` must come from authenticated identity and verified tenant membership in the application tier. Never take a tenant ID from a client-supplied query parameter or header and apply it without verifying the user belongs to that tenant.

In Spring applications, place context initialization at the transaction boundary or inside a component hooked into the transaction manager. The key requirement is setting context after the transaction begins and before repositories execute, on the exact same connection used by that transaction. If an ORM opens a secondary connection, policies will not see the configured context.

### 5.2. Trust Boundary of Custom Settings

Custom settings like `app.tenant_id` are highly effective against application bugs that forget tenant filters. However, PostgreSQL allows any client able to execute SQL in a session to modify that custom parameter. Thus, if an attacker can execute arbitrary SQL using `app_runtime` credentials, they could set `app.tenant_id` to another tenant.

Therefore, this model strongly guards against routine coding mistakes, but is not by itself a boundary against a compromised application or SQL injection executing arbitrary statements under the same database role.

To strengthen trust boundaries:

- Use parameterized queries; never concatenate raw input into SQL.
- Never expose database credentials directly to end users.
- Authenticate users and verify tenant membership before setting context.
- Minimize `app_runtime` privileges and permit access only via trusted services.
- When isolation must withstand a compromised application role, consider per-tenant database roles/credentials or separate schemas/databases with corresponding authentication.
- Audit support or admin flows authorized to access multiple tenants.

Never treat a client-provided tenant ID as proof of authorization. It is merely a requested tenant selection; the server must validate it against the authenticated principal.

## 6. Creating `SELECT`, `INSERT`, `UPDATE`, and `DELETE` Policies

An RLS policy has two primary expressions:

- **`USING`:** determines which existing rows the role may see or target.
- **`WITH CHECK`:** determines whether new rows or post-`INSERT`/`UPDATE` row states are allowed to exist.

Create dedicated policies on `orders`:

~~~sql
CREATE POLICY orders_tenant_select
ON app.orders
FOR SELECT
TO app_runtime
USING (
    tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid
);

CREATE POLICY orders_tenant_insert
ON app.orders
FOR INSERT
TO app_runtime
WITH CHECK (
    tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid
);

CREATE POLICY orders_tenant_update
ON app.orders
FOR UPDATE
TO app_runtime
USING (
    tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid
)
WITH CHECK (
    tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid
);

CREATE POLICY orders_tenant_delete
ON app.orders
FOR DELETE
TO app_runtime
USING (
    tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid
);
~~~

You can create a unified policy for `customers`:

~~~sql
CREATE POLICY customers_tenant_access
ON app.customers
FOR ALL
TO app_runtime
USING (
    tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid
)
WITH CHECK (
    tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid
);
~~~

For a `FOR ALL` policy, `USING` filters existing rows for `SELECT`, `UPDATE`, and `DELETE`, while `WITH CHECK` validates newly inserted or updated rows. The role still needs matching SQL privileges granted via `GRANT`.

### 6.1. How `USING` and `WITH CHECK` Differ

| Command | `USING` Checks | `WITH CHECK` Checks |
|---|---|---|
| `SELECT` | Rows allowed to be read | Unused |
| `INSERT` | Unused | New rows allowed to be inserted |
| `UPDATE` | Existing rows allowed to be located and modified | Resulting row values after update |
| `DELETE` | Rows allowed to be deleted | Unused |
| `ALL` | Existing rows | Newly created or updated rows |

The sharpest distinction lies in `UPDATE`. If a policy only checks old rows via `USING`, an application could locate a row owned by the current tenant and change its `tenant_id` to another tenant. `WITH CHECK` blocks transferring row ownership across tenants.

Example `UPDATE` attempting to switch tenants:

~~~sql
UPDATE app.orders
SET tenant_id = '22222222-2222-2222-2222-222222222222'
WHERE order_id = 1001;
~~~

If the current context is tenant `1111...`, `WITH CHECK` rejects the post-update row because `tenant_id` no longer matches the context.

For `INSERT`, if the application tries to write a `tenant_id` differing from the tenant context, PostgreSQL rejects the operation as a policy violation. Have the server-side data access layer assign `tenant_id` from the verified context rather than trusting client-supplied values.

### 6.2. Default Policy Mode and Multiple Policies

Policies default to **permissive**. When multiple permissive policies apply to the same command and role, satisfying any single policy permits access (OR logic). Restrictive policies combine via AND with applicable permissive policies.

This can cause dangerous misconfigurations if a team adds a broad policy such as:

~~~sql
CREATE POLICY orders_support_read
ON app.orders
FOR SELECT
TO app_runtime
USING (true);
~~~

That policy allows `app_runtime` to read every row across all tenants because it is OR'd with the tenant policy. Never add a permissive blanket policy for the same runtime role just to handle an edge case.

When support workflows require cross-tenant access, use a separate role or a tightly scoped conditional policy paired with auditing. `AS RESTRICTIVE` can enforce mandatory conditions alongside permissive policies, provided you clearly understand how PostgreSQL combines policies per role and command before deploying.

Inspect existing policies with:

~~~sql
SELECT
    schemaname,
    tablename,
    policyname,
    permissive,
    roles,
    cmd,
    qual,
    with_check
FROM pg_policies
WHERE schemaname = 'app'
ORDER BY tablename, policyname;
~~~

## 7. Pairing RLS with Schema Design and Indexes

RLS filters rows using policy expressions. For tenant queries to perform well, design indexes and constraints around common access patterns.

If queries frequently fetch orders by tenant and time:

~~~sql
CREATE INDEX orders_tenant_created_at_idx
ON app.orders (tenant_id, created_at DESC);
~~~

If queries frequently filter by tenant and status:

~~~sql
CREATE INDEX orders_tenant_status_idx
ON app.orders (tenant_id, status);
~~~

Index column order must align with filters, joins, and sorts. An index leading with `tenant_id` generally helps tenant-scoped queries, though no single index layout fits every workload. Verify with `EXPLAIN` on real data.

Important constraints:

- Primary keys and unique keys should include `tenant_id` when uniqueness is scoped per tenant.
- Foreign keys should include `tenant_id` to prevent cross-tenant references.
- `tenant_id` must be `NOT NULL` on tenant-scoped tables.
- Defaults or triggers may populate `tenant_id`, provided the value always matches the verified context.
- Child tables, audit tables, attachments, and metadata tables must also carry explicit tenant rules.

Never rely on RLS as a substitute for foreign keys. Referential integrity checks have distinct behavior and can sometimes leak existence via constraint errors. Composite tenant-scoped foreign keys preserve consistency independently of row-read policies.

## 8. RLS with Views, Functions, and Special Objects

RLS protects queries passing through relations with active policies. Objects executing under different privileges or tables accessible directly require separate review.

### 8.1. Views

By default, PostgreSQL views check permissions on underlying tables using the view owner's privileges. If the view owner bypasses RLS, the view can inadvertently expose data outside the caller's scope.

Starting in PostgreSQL 15, views can be created with `security_invoker` so privileges and RLS policies evaluate as the caller:

~~~sql
CREATE VIEW app.visible_orders
WITH (security_invoker = true)
AS
SELECT order_id, customer_id, total_amount, status, created_at
FROM app.orders;
~~~

On earlier versions, design views and grants carefully, auditing view owners, policies, and underlying table privileges. Never assume a view preserves tenant isolation automatically merely because the base table has RLS.

### 8.2. `SECURITY DEFINER` Functions

Functions declared `SECURITY DEFINER` execute with the privileges of the function's owner. If that owner bypasses RLS or owns the tables, the function can read beyond the caller's scope.

Use `SECURITY DEFINER` only when genuinely necessary. When using it:

- Choose an owner with minimal privileges.
- Set a safe `search_path` containing only trusted schemas.
- Schema-qualify table and function names inside the function body.
- Validate tenant identity and parameters inside the function.
- Revoke `EXECUTE` from `PUBLIC` when unnecessary.
- Audit invocations and test using the actual runtime role.

Example setting `search_path` on a function:

~~~sql
ALTER FUNCTION app.some_admin_operation(uuid)
SET search_path = pg_catalog, app;
~~~

This snippet illustrates `search_path` hardening only; production functions must still verify caller authorization and tenant scope. Never let a definer function accept an arbitrary tenant ID and return that tenant's rows without independent authorization checks.

### 8.3. Partitions and Child Tables

If tenant tables are partitioned, define which access paths the application is allowed to use. Querying through the partitioned parent applies policies defined on the parent relation. If a role can query child partitions directly, verify that privileges and policies on each partition match as well.

A clean strategy is granting privileges solely on the parent table and withholding direct partition access from `app_runtime`. If business needs require direct partition queries, inspect policies, grants, and query paths on every partition.

### 8.4. Temporary and Non-Tenant-Scoped Tables

Not every table stores tenant-owned rows. Global configuration tables, shared catalogs, or technical scratch tables may have different scopes. Explicitly classify which tables are tenant-scoped, which are shared, and which roles may access each.

Do not let temporary or staging tables become a backdoor around tenant isolation. If data from RLS-protected tables is copied into staging tables accessible to broader roles, tightly govern permissions and data lifecycle.

## 9. Administrative Roles and Support Access

Certain workflows require cross-tenant visibility: customer support, consolidated reporting, auditing, operations, or incident response. Never grant `BYPASSRLS` to the standard application role to serve these workflows.

Instead, design dedicated paths:

- Read-only support roles granted strictly during controlled sessions.
- Admin functions or services verifying a ticket ID, justification, and tenant scope before running.
- Comprehensive audit logging of cross-tenant access recording actor, tenant, action, timestamp, and purpose.
- Protected break-glass accounts with short lifetimes and internal approval workflows.
- Dedicated reporting pipelines or roles with bounded data scopes.

If an administrative role holds `BYPASSRLS`, policies no longer constrain rows for that role. Treat those credentials like database admin privileges and never place them in general application connection pools.

Also note that backup, restore, replication, and maintenance tasks may require privileges that bypass RLS or operate at table/database level. Separate operational credentials from application credentials and validate export/restore outputs against organizational security policies.

## 10. Testing RLS and Tenant Isolation

Tests must run under the real application role, using connection and transaction patterns matching production. Running tests as a superuser or table owner bypasses RLS and creates false confidence.

### 10.1. Testing Cross-Tenant Reads

Seed data for two tenants using an authorized migration/seed role:

~~~sql
INSERT INTO app.customers (tenant_id, customer_id, name)
VALUES
  ('11111111-1111-1111-1111-111111111111', 101, 'Tenant A customer'),
  ('22222222-2222-2222-2222-222222222222', 201, 'Tenant B customer');

INSERT INTO app.orders (
    tenant_id, order_id, customer_id, external_id, total_amount, status
)
VALUES
  ('11111111-1111-1111-1111-111111111111', 1001, 101, 'A-1001', 150, 'paid'),
  ('22222222-2222-2222-2222-222222222222', 2001, 201, 'B-2001', 250, 'paid');
~~~

Then connect as `app_runtime` and set tenant A's context:

~~~sql
BEGIN;
SELECT set_config('app.tenant_id', '11111111-1111-1111-1111-111111111111', true);

SELECT order_id, external_id
FROM app.orders;
COMMIT;
~~~

The result must contain only order `A-1001`. Repeat for tenant B and verify only `B-2001` appears.

### 10.2. Testing Missing Context

Open a transaction as `app_runtime` without setting `app.tenant_id`:

~~~sql
BEGIN;

SELECT order_id
FROM app.orders;

COMMIT;
~~~

`SELECT` must return zero rows. `INSERT` or `UPDATE` attempting to write rows without a valid tenant context must be rejected by policies. This test is vital because connection pools may hand out fresh connections or a request path may omit the context-setup step.

### 10.3. Testing Writes and Tenant Transfers

Scenarios to verify:

- `INSERT` with `tenant_id` matching context succeeds.
- `INSERT` with `tenant_id` differing from context is rejected.
- `UPDATE` targeting another tenant's row cannot modify it.
- `UPDATE` on a current-tenant row attempting to change `tenant_id` is rejected by `WITH CHECK`.
- `DELETE` removes only rows belonging to the current tenant.
- Tenant A cannot reference a customer owned by tenant B due to the composite foreign key.
- The runtime role cannot read via views or functions outside policy scope.

An `UPDATE` or `DELETE` targeting a row hidden by a policy may affect 0 rows rather than throwing an error. Tests must assert affected row counts and resulting database state, not merely check for exceptions.

### 10.4. Testing Connection Pools

A particularly important test reuses the exact same physical connection across two tenants:

1. Borrow a connection and start a transaction for tenant A.
2. Set context A, query, and commit.
3. Borrow that same physical connection for tenant B.
4. Start a new transaction, set context B, and query.
5. Verify results belong strictly to tenant B.
6. Run a transaction without setting context and verify zero rows are returned.

This catches session-level `SET` bugs or improperly reset connection state. Test commit, rollback, and exception paths alike.

## 11. Rolling Out RLS Safely via Migrations

Enabling RLS on an actively used table can cause queries to return zero rows or writes to fail if policies and tenant contexts are not yet ready. Roll out in controlled stages.

A safe sequence:

1. Add `tenant_id` and backfill existing rows using verified tenant mappings.
2. Verify zero tenant-scoped rows lack `tenant_id`.
3. Add `NOT NULL`, composite keys, and required foreign keys.
4. Create indexes matching query patterns.
5. Deploy application changes that set tenant context inside transactions.
6. Grant least-privilege runtime permissions and test under the runtime role.
7. Create policies for every required operation.
8. Enable `ENABLE ROW LEVEL SECURITY`.
9. Enable `FORCE ROW LEVEL SECURITY` if table-owner protection is desired.
10. Monitor policy violations, unexpected zero-row queries, and application metrics after rollout.

During transition, a compatibility window may be needed so old and new application versions run side by side. If RLS is enabled before all code paths set context, legacy requests will fail. Conversely, deploying overly broad temporary policies risks exposing data. Prioritize data protection and include explicit verification gates at each step.

Migrations must have tested rollback or recovery procedures. Disabling RLS can expose data if the application already relies on policies; never treat `DISABLE ROW LEVEL SECURITY` as a default production rollback plan.

## 12. Monitoring and Auditing

RLS can cause queries to return fewer rows or silently affect zero rows without necessarily raising an error in every case. Monitor behavior in both the database and application layers.

Signals to track:

- Row-level security policy violation errors.
- Abnormal spikes in tenant queries returning 0 rows.
- Rejected `INSERT`/`UPDATE` rates.
- Missing or malformed tenant contexts.
- Cross-tenant queries from support/admin workflows.
- Roles with `BYPASSRLS`, or changes to table ownership/policies.
- Migrations introducing new tables without RLS enabled or without policies.
- Privilege (`GRANT`) changes on tenant-scoped schemas and tables.

Avoid logging sensitive tenant payloads, access tokens, or customer data into uncontrolled logs. Log normalized internal tenant identifiers alongside request IDs, actors, and outcomes to aid troubleshooting.

RLS policies do not automatically produce a complete audit log of every row read. If compliance requires knowing who viewed or modified specific records, implement application-level auditing, triggers, or tamper-resistant logging mechanisms, evaluating performance impact carefully.

## 13. Common Mistakes When Deploying RLS

| Symptom | Possible Cause | Resolution |
|---|---|---|
| RLS is enabled, yet the app still reads all tenants | App connects as table owner, superuser, or `BYPASSRLS` | Use a non-owning runtime role, inspect `FORCE` and role attributes |
| Queries always return 0 rows | Tenant context unset, reset, or malformed UUID | Set transaction-local context on the same transaction/connection |
| Tenant B requests see Tenant A data | Session-level setting used on pooled connections | Switch to transaction-local `set_config` and test pooling |
| `INSERT` is rejected | `WITH CHECK` fails against tenant context | Assign `tenant_id` from verified server-side context |
| `UPDATE` changing tenant fails | `WITH CHECK` blocks moving row to another tenant | Expected protective behavior—keep it |
| Adding a new policy leaks data | Permissive policies combine with OR | Audit all policies per role and command |
| View bypasses expected limits | View executes with owner privileges | Use `security_invoker` where appropriate and check PG version |
| Function accesses too broadly | `SECURITY DEFINER` runs with owner privileges | Restrict owner, `search_path`, `EXECUTE`, and verify tenant in function |
| Tenant references another tenant's data | Foreign key omits `tenant_id` | Use composite foreign keys |
| RLS tests pass falsely | Tests run as superuser or table owner | Execute tests with real `app_runtime` credentials |

Key rules to uphold:

- Never grant `BYPASSRLS` or superuser to application accounts.
- Never let `app_runtime` own tenant-scoped tables.
- Never trust client-supplied tenant IDs without verifying membership.
- Never use session-level tenant context with connection pools.
- Never assume RLS replaces `GRANT`, constraints, or authentication.
- Never add a broad permissive policy to patch an isolated access issue.
- Never leave views or `SECURITY DEFINER` functions as unguarded bypass paths.

## 14. Recommended Implementation and Operations Workflow

A checklist you can apply to every tenant-scoped table:

**Data design:** add `tenant_id NOT NULL`, composite primary/unique keys, and composite tenant foreign keys. Separate shared tables from tenant-scoped tables.

**Role design:** separate migration owner, runtime roles, and admin roles. Verify runtime roles lack superuser/`BYPASSRLS` and do not own tables.

**Context setup:** post-authentication, the server verifies tenant membership, opens a transaction, and sets transaction-local context via `set_config`. All repository queries share that connection.

**Policy creation:** define explicit `SELECT`, `INSERT`, `UPDATE`, `DELETE` policies—or `ALL` policies—with proper `USING` and `WITH CHECK` clauses. Audit how multiple policies combine.

**Enable RLS:** run `ENABLE` and evaluate `FORCE`. Audit owners, views, functions, partitions, and alternative access paths.

**Testing:** confirm tenant A cannot read, modify, delete, or insert tenant B data; missing context is denied; pooled connections never leak context; composite foreign keys block cross-tenant references.

**Deployment:** roll out migrations in phases, watch policy errors and metrics, and keep a tested recovery plan.

**Operations:** audit privileged access, monitor role and policy drift, verify new tables, drill backup/restore, and revisit policies whenever business rules change.

## 15. Maintaining Tenant Boundaries Over Time

RLS remains effective when treated as an ongoing part of data design and operations—not a one-off `ALTER TABLE`. Every new tenant-scoped table needs `tenant_id`, scoped grants, policies, and isolation tests. Every change to views, functions, partitions, or roles must be reviewed for its impact on tenant boundaries.

Periodically audit tables with RLS enabled, active policies, roles holding `BYPASSRLS`, table owners, schema grants, and `SECURITY DEFINER` functions. Integrating these checks into migration reviews or CI catches newly added tables missing policies before deployment.

When tenant context is bound cleanly to each transaction, runtime roles hold least privilege, and policies govern both reads and writes, PostgreSQL becomes a dependable enforcement layer for tenant boundaries. Combined with application authentication, composite tenant constraints, auditing, and isolation testing, a shared-table architecture can safely serve many tenants with verifiable access controls.
