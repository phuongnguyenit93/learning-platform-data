# Rules, the Query Rewrite System, and Usage Boundaries in PostgreSQL

## 1. An SQL Statement May Not Be What PostgreSQL Executes Directly

When an application sends:

```sql
SELECT *
FROM sales.active_products;
```

you might assume PostgreSQL simply reads a table named `active_products`. However, if `active_products` is a **view**, PostgreSQL expands the view definition into a query over one or more underlying base tables. A core part of that mechanism relies on **query rewrite rules**.

Similarly, PostgreSQL lets you declare:

```sql
CREATE RULE ... AS ON INSERT TO ...
DO ALSO ...;
```

or:

```sql
CREATE RULE ... AS ON DELETE TO ...
DO INSTEAD NOTHING;
```

Both constructs can **augment, replace, or suppress** an incoming statement before it reaches the planner and executor.

Keep one fundamental point clear from the start:

> **A rule is not a trigger that fires once per row.** A rule belongs to PostgreSQL's **query tree rewrite** system. When you need per-row `OLD`/`NEW` handling, constraint-like checks, exact row-level auditing, or business event emission, triggers and constraints are usually the better choice.

This lesson focuses on three questions:

1. What is a rule in reality, and at what stage does PostgreSQL rewrite queries?
2. How do `DO ALSO`, `DO INSTEAD`, `DO INSTEAD NOTHING`, `OLD`, and `NEW` work?
3. Where are the boundaries where you should choose **views, triggers, constraints, RLS, transactions, or an outbox** instead of writing custom rules?

### Learning Outcomes

After completing this lesson, you will be able to:

- Explain the `parser/analyzer -> rewriter -> planner -> executor` pipeline.
- Read `CREATE RULE` syntax and distinguish `SELECT`, `INSERT`, `UPDATE`, and `DELETE` rule events.
- Describe how views are implemented via the `_RETURN` rule.
- Distinguish `DO ALSO`, `DO INSTEAD`, and `DO INSTEAD NOTHING`.
- Understand that `OLD`/`NEW` in rules are **pseudo-relations during query rewrite**, unlike record variables in row-level triggers.
- Read an original SQL statement and deduce which actions are produced after rewriting.
- Build a safe lab for rules that augment, redirect, or suppress commands.
- Understand why rules with multi-row operations, volatile expressions, and `RETURNING` require careful handling.
- Recognize limitations involving `INSERT ... ON CONFLICT`, `COPY FROM`, and `TRUNCATE`.
- Distinguish automatically updatable views, `INSTEAD OF` triggers, and `INSTEAD` rules.
- Inspect rules through `pg_rewrite`, `pg_rules`, and `pg_get_ruledef`.
- Evaluate implications for concurrency, performance, security, auditing, and migrations.
- Pick the right tool for common real-world scenarios.

## 2. What Is a Rule in PostgreSQL?

A **rule**, within the scope of this lesson, is a rule belonging to PostgreSQL's **Query Rewrite System**, declared with `CREATE RULE`.

It is bound to a **target relation** and an **SQL event type**. When PostgreSQL analyzes a statement referencing that relation, the rewrite system transforms the query tree before the planner and executor run.

Simple mental model:

```text
Incoming SQL statement
       |
       v
Parsed query tree
       |
       v
Applicable rewrite rules
       |
       v
One or more rewritten query trees
       |
       v
Planner optimizes those query trees
       |
       v
Executor executes the plans
```

Conceptual examples:

```text
DELETE FROM protected_rows WHERE id = 10
       |
       v
Rule: ON DELETE DO INSTEAD NOTHING
       |
       v
No corresponding DELETE action remains to execute
```

Or:

```text
INSERT INTO orders ...
       |
       v
Rule: ON INSERT DO ALSO INSERT INTO audit ...
       |
       v
Original command + audit command generated by the rewriter
```

Neither mechanism is equivalent to invoking a procedural trigger each time a row changes.

### 2.1. Are Rules Part of Universal Standard SQL?

The `CREATE RULE` mechanism covered here is PostgreSQL-specific. Never assume another database engine supports an equivalent feature or shares the same semantics.

### 2.2. Is a Rule a Business Rule?

The word "rule" easily misleads newcomers into thinking of "business rules" or "validation rules."

In PostgreSQL:

- `CREATE RULE`: **transforms SQL statements**.
- `CHECK`, `NOT NULL`, `UNIQUE`, `FOREIGN KEY`: **data integrity constraints**.
- `CREATE TRIGGER`: **invokes behavior** at defined moments around table/view operations.
- Row Level Security: **controls which rows a role may access or modify**.
- Service-layer business rules: **domain logic and application protocols**.

They can work together, but they should never be conflated.

## 3. What Stages Does PostgreSQL Use to Process SQL?

A practical mental model:

<escape>1.</escape> **Parse:** accepts SQL text and builds a parse tree.

<escape>2.</escape> **Analyze:** resolves table/column names, data types, expressions, privileges, and semantics to build the initial query tree.

<escape>3.</escape> **Rewrite:** applies query rewrite rules; view expansion is the most important special case.

<escape>4.</escape> **Plan/Optimize:** chooses execution strategies, join order, index scans, sequential scans, sorts, aggregates, and physical plan nodes.

<escape>5.</escape> **Execute:** runs the plan, reads/writes tuples, manages MVCC visibility, and returns results.

Diagram:

```text
SQL text
   |
   v
Parser
   |
   v
Analyzer / Query Tree
   |
   v
Rewriter <------ pg_rewrite
   |
   +---- SELECT view -> query over base tables
   |
   +---- DML rule -> add/replace query
   |
   v
Planner
   |
   v
Execution Plan
   |
   v
Executor
   |
   v
Results / data modifications
```

### 3.1. Rewrite vs. Optimization

The rewriter transforms **the logical structure/meaning of queries according to rules**. The planner chooses **an efficient way to execute** the rewritten queries.

A rule is not a planner hint telling PostgreSQL "use index A," "join table B first," or "run faster."

### 3.2. Rewriting Is Not a Per-Row Loop

Given:

```sql
UPDATE some_table
SET status = 'ARCHIVED'
WHERE created_at < DATE '2025-01-01';
```

rules operate on **the statement and query tree**. You cannot reason as:

```text
For each updated row
    -> execute the rule block once
```

That describes certain **row-level triggers**, not the fundamental behavior of query rewrite rules.

### 3.3. Why Does This Distinction Matter?

If an application needs to audit **exactly each row that was truly INSERTed/UPDATEd/DELETEd**, statement-level query rewriting can break expectations in cases such as:

- Multi-row DML.
- `INSERT ... SELECT`.
- `DEFAULT` values or volatile expressions.
- Statements rejected by constraints.
- `RETURNING` and upserts.
- Rows filtered via joins or predicates introduced during rewrite.

Therefore, never choose `CREATE RULE` for per-row auditing merely because it accepts `OLD` and `NEW`.

## 4. `CREATE RULE` Syntax

General syntax:

```sql
CREATE [ OR REPLACE ] RULE rule_name AS
ON event TO table_name
[ WHERE condition ]
DO [ ALSO | INSTEAD ]
{
    NOTHING
    | command
    | ( command; command; ... )
};
```

Where:

- `rule_name`: name of the rule on the target relation.
- `event`: `SELECT`, `INSERT`, `UPDATE`, or `DELETE`.
- `table_name`: target relation of the rule.
- `WHERE condition`: optional predicate determining when the rule applies.
- `DO ALSO`: keep the original command and add the rule action(s).
- `DO INSTEAD`: replace the original command with the rule action(s) when applicable.
- `DO INSTEAD NOTHING`: replace the original command with no action.
- `command`: SQL command(s) permitted by the rewrite system.

### 4.1. Naming Conventions

Rule names should reflect intent:

```text
audit_order_insert
prevent_delete
route_insert
_RETURN
```

The name `_RETURN` has special meaning for view `SELECT` rules. Do not invent arbitrary names instead of `_RETURN` when dealing with view `SELECT` rules.

### 4.2. `DO ALSO` Is Implicit When Neither `ALSO` Nor `INSTEAD` Is Specified

If you omit `ALSO`/`INSTEAD`, the default falls into the `ALSO` branch in this syntax. Still, **always write `DO ALSO` explicitly** so readers never mistakenly assume the original command is replaced.

### 4.3. Ownership Scope of a Rule

A rule is defined on a specific relation. Permission to create a rule depends on object ownership / DDL privileges. A user cannot attach rules to someone else's table merely because they hold `SELECT`/`UPDATE` privileges on its data.

## 5. Four Event Types: `SELECT`, `INSERT`, `UPDATE`, `DELETE`

| Event | Common Role | Notes |
|---|---|---|
| `ON SELECT` | Defines view reads | Has strict requirements: `_RETURN` name, unconditional `INSTEAD` |
| `ON INSERT` | Rewrites row insertions | Prone to subtle interactions with defaults, `RETURNING`, `ON CONFLICT` |
| `ON UPDATE` | Rewrites row updates | `OLD`/`NEW` must be understood at query level |
| `ON DELETE` | Rewrites row deletions | Can suppress via `DO INSTEAD NOTHING`, but does not replace privileges/constraints |

### 5.1. There Is No `ON TRUNCATE` Rule

You cannot treat `TRUNCATE` as a form of `DELETE` rewritten by an `ON DELETE` rule.

To govern `TRUNCATE`:

- Revoke `TRUNCATE` privilege from unauthorized roles.
- Enforce administrative/DDL policies.
- Use `TRUNCATE` triggers if trigger behavior on `TRUNCATE` is needed.
- Consider withholding destructive bulk-operation privileges from application roles.

### 5.2. There Is No Dedicated `SELECT FOR UPDATE` Rule Event

A query can carry row-locking clauses, yet rule events remain only the four supported event types. Do not imagine an arbitrary `ON SELECT FOR UPDATE DO ...` rule event.

## 6. `DO ALSO`, `DO INSTEAD`, and `NOTHING`

Comparison table:

| Syntax | Original Command | Added / Replacement Action |
|---|---|---|
| `DO ALSO command` | Retained | Adds `command` |
| `DO INSTEAD command` | Replaced per rule semantics | Executes replacement `command` |
| `DO INSTEAD NOTHING` | Replaced | Adds no command |
| `DO ALSO NOTHING` | Retained | Adds no useful action |

### 6.1. `DO ALSO` Does Not Mean "Run Action After Original Command Succeeds"

A rule generates **additional query trees at rewrite time**. It is not an `AFTER INSERT/UPDATE/DELETE` callback receiving per-row `OLD`/`NEW` records after the row has settled in its final state.

When an action writes audit logs or sends notifications, you must account for execution order, which rows truly changed, duplicate invocations, and rewrite-system limits. Usually an **AFTER trigger** is far more appropriate.

### 6.2. `DO INSTEAD` Does Not Mean "Block Every Possible Data Change"

For instance, a rule blocking `DELETE` cannot stop:

- Roles with sufficient privileges to alter or drop the rule.
- A permitted `TRUNCATE` command.
- Writes via alternate paths or DDL changes.
- Other modification paths the rule was not designed to cover.

For critical data protection, combine privileges, constraints, RLS, triggers, and operational controls.

## 8. Views: The Most Common Use of Query Rewriting

Create a view showing only active products:

```sql
CREATE VIEW rule375.active_products AS
SELECT
    product_id,
    product_name,
    category,
    unit_price,
    is_active
FROM rule375.products
WHERE is_active;
```

Query it:

```sql
SELECT
    product_id,
    product_name,
    unit_price
FROM rule375.active_products
WHERE unit_price >= 80000
ORDER BY product_id;
```

Expected output:

| product_id | product_name | unit_price |
|---:|---|---:|
| 101 | Whole-bean roasted coffee | 120000.00 |
| 102 | Stainless steel coffee filter | 85000.00 |

### 8.1. Where Does View Data Live?

An ordinary view **does not store its own copy of rows**. PostgreSQL stores the query definition and expands the view through the rewrite system.

Conceptual expansion:

```sql
SELECT product_id, product_name, unit_price
FROM (
    SELECT
        product_id,
        product_name,
        category,
        unit_price,
        is_active
    FROM rule375.products
    WHERE is_active
) AS active_products
WHERE unit_price >= 80000
ORDER BY product_id;
```

This is a **logical interpretation model**, not a guarantee that PostgreSQL always materializes that subquery verbatim as a temporary table.

The planner may flatten subqueries, push down predicates, and apply other optimizations depending on view semantics.

### 8.2. Regular Views vs. Materialized Views

- Regular view: reads underlying data on each query and does not store result rows itself.
- Materialized view: physically stores results when created or refreshed, requiring explicit refresh management.

Never assume from `SELECT * FROM view` that results are cached on disk.

## 9. The `_RETURN` Rule Attached to Views

When you run `CREATE VIEW` for a regular view, PostgreSQL stores its definition via a special **`ON SELECT DO INSTEAD`** rewrite rule named `_RETURN`.

Conceptually:

```text
SELECT FROM rule375.active_products
          |
          v
_RETURN rule of active_products
          |
          v
View-defining query tree:
  SELECT ... FROM rule375.products
  WHERE is_active
          |
          v
Planner optimizes the entire rewritten query
```

### 9.1. Why Use `CREATE VIEW` Instead of Manually Creating `_RETURN`?

`CREATE VIEW` directly expresses the intent to define a read interface:

- Clean and readable.
- Supports column aliases, security options, and `CHECK OPTION` where applicable.
- Object dependencies are tracked properly in catalogs.
- Eliminates manually constructing special `SELECT` rules.
- Enables automatic updatability for eligible simple views.

**Best practice:** whenever the goal is defining a view, always use `CREATE VIEW` / `CREATE OR REPLACE VIEW` instead of manually crafting a `_RETURN` rule.

### 9.2. Do Not Create Custom `ON SELECT` Rules Arbitrarily

PostgreSQL imposes strict requirements on `ON SELECT` rules: they must follow the form required for view rewriting, including the special `_RETURN` name and restricted action/qualification rules. They are not meant for attaching arbitrary "SELECT audit rules" whenever a table is read.

## 10. Inspecting View Definitions and Rewrite Metadata

You can inspect a view definition with:

```sql
SELECT pg_get_viewdef(
    'rule375.active_products'::regclass,
    true
);
```

Or query the catalog view:

```sql
SELECT
    schemaname,
    viewname,
    definition
FROM pg_views
WHERE schemaname = 'rule375'
  AND viewname = 'active_products';
```

### 10.1. Querying `pg_rewrite`

`pg_rewrite` is the system catalog storing query rewrite rules.

```sql
SELECT
    n.nspname AS schema_name,
    c.relname AS relation_name,
    r.rulename,
    r.ev_type,
    r.is_instead,
    pg_get_ruledef(r.oid, true) AS rule_definition
FROM pg_rewrite AS r
JOIN pg_class AS c
    ON c.oid = r.ev_class
JOIN pg_namespace AS n
    ON n.oid = c.relnamespace
WHERE n.nspname = 'rule375'
ORDER BY c.relname, r.rulename;
```

You should see `_RETURN` on `active_products` along with any other rules created in the lab.

### 10.2. `pg_rules` Is a More Readable View

```sql
SELECT
    schemaname,
    tablename,
    rulename,
    definition
FROM pg_rules
WHERE schemaname = 'rule375'
ORDER BY tablename, rulename;
```

**Note:** `pg_rules` is a convenience view and may not show every view `_RETURN` rule the way you might expect. To inspect raw view-rule metadata, check `pg_rewrite` and `pg_get_viewdef`.

### 10.3. Useful Catalog Columns

| Catalog Field | Purpose |
|---|---|
| `ev_class` | OID of the relation owning the rule |
| `rulename` | Name of the rule |
| `ev_type` | Event type |
| `is_instead` | Whether it is an `INSTEAD` rule |
| `ev_qual` | Qualification condition in internal node representation |
| `ev_action` | Query action in internal node representation |
| `ev_enabled` | Enabled status under the rule firing mechanism |

To read human-readable SQL, use `pg_get_ruledef` instead of trying to decode `pg_node_tree` manually.

## 11. `EXPLAIN` for Queries Against a View

Query:

```sql
EXPLAIN (VERBOSE, COSTS OFF)
SELECT
    product_id,
    product_name
FROM rule375.active_products
WHERE unit_price >= 80000;
```

In the execution plan, you will typically see a scan over the underlying base table `rule375.products` with the combined filters.

### 11.1. Should `_RETURN` Appear by Name in `EXPLAIN`?

No. `EXPLAIN` shows the **post-rewrite, optimized execution plan**, not a step-by-step rewrite trace naming individual rules.

Seeing `products` scanned is expected because the view expands onto `products`. Use catalogs to inspect rule definitions.

### 11.2. Views Do Not Inherently Make Queries Slower

A simple view is usually merged and optimized together with the outer query by the planner. Never claim that views always cause an extra full scan or temporary table.

However, complex view constructs, security barriers, aggregates, `LIMIT`, `DISTINCT`, or window functions can restrict predicate pushdown or subquery flattening. Always inspect the actual plan.

## 12. Automatically Updatable Views: No Custom Rules Needed

Certain PostgreSQL views are **automatically updatable** when they satisfy eligibility criteria — for example, a simple view over a single base table without constructs that make DML mapping ambiguous.

Consider:

```sql
CREATE VIEW rule375.editable_active_products AS
SELECT
    product_id,
    product_name,
    category,
    unit_price,
    is_active
FROM rule375.products
WHERE is_active;
```

Through this view, PostgreSQL can automatically translate valid `INSERT`/`UPDATE`/`DELETE` commands to the base table without requiring a manual `ON UPDATE DO INSTEAD` rule.

### 12.1. What Happens If an `UPDATE` Makes a Row No Longer Match the View?

Without `CHECK OPTION`:

```sql
UPDATE rule375.editable_active_products
SET is_active = false
WHERE product_id = 104;
```

The command updates underlying row 104, and that row then **disappears from the view's results** because `is_active = false`.

This is not a PostgreSQL bug: a view is a read filter, not an implicit post-update constraint unless configured otherwise.

### 12.2. Isolate Tests or Restore Fixture State

If you ran that UPDATE and want later examples to see the original fixture data:

```sql
UPDATE rule375.products
SET is_active = true
WHERE product_id = 104;
```

Avoid running mutating DML repeatedly on lab fixtures and assuming sample outputs remain unchanged.

## 13. `WITH CHECK OPTION` on Updatable Views

To ensure rows created or updated through a view still satisfy the view's predicate:

```sql
CREATE VIEW rule375.checked_active_products AS
SELECT
    product_id,
    product_name,
    category,
    unit_price,
    is_active
FROM rule375.products
WHERE is_active
WITH LOCAL CHECK OPTION;
```

Now try:

```sql
-- Intentional error: row after UPDATE no longer satisfies the view.
UPDATE rule375.checked_active_products
SET is_active = false
WHERE product_id = 101;
```

PostgreSQL is expected to reject the statement because the modified row would fall outside the view's `CHECK OPTION` condition.

### 13.1. `LOCAL` vs. `CASCADED`

- `LOCAL CHECK OPTION`: checks the current view's own condition under PostgreSQL's defined semantics.
- `CASCADED CHECK OPTION`: across stacked updatable views, also checks conditions of underlying views appropriately.

Pay attention to limitations when a view in the stack uses rules or triggers. Never assume `CHECK OPTION` applies identically across `INSTEAD` rules or `INSTEAD OF` triggers as it does on pure automatically updatable views.

### 13.2. `CHECK OPTION` Does Not Replace a Table `CHECK` Constraint

Direct writes to `rule375.products` bypass `checked_active_products`. If "every product must be active" is a table-wide invariant, a view `CHECK OPTION` is insufficient; enforce it with a table constraint or data-model invariant.

### 13.3. Automatically Updatable Views Do Not Cover Every `SELECT`

Views with joins, aggregates, `DISTINCT`, or complex expressions are not automatically updatable. When writes through such views are genuinely needed, an `INSTEAD OF` trigger is usually far easier to control than custom DML rules.

## 14. Creating a `DO ALSO` Rule for a Simple `INSERT`

To observe how a rule appends an extra action, use separate tables apart from `products`.

```sql
CREATE TABLE rule375.requests (
    request_id integer PRIMARY KEY,
    request_title text NOT NULL
);

CREATE TABLE rule375.request_rule_log (
    log_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    request_id integer NOT NULL,
    event_name text NOT NULL,
    logged_at timestamptz NOT NULL DEFAULT now()
);
```

Create the rule:

```sql
CREATE RULE requests_insert_log AS
ON INSERT TO rule375.requests
DO ALSO
    INSERT INTO rule375.request_rule_log(
        request_id,
        event_name
    )
    VALUES (
        NEW.request_id,
        'INSERT'
    );
```

Run a simple INSERT:

```sql
INSERT INTO rule375.requests(request_id, request_title)
VALUES (1, 'First request');
```

Inspect:

```sql
SELECT *
FROM rule375.requests
ORDER BY request_id;

SELECT
    request_id,
    event_name
FROM rule375.request_rule_log
ORDER BY log_id;
```

In this simple case, both the request row and its log entry appear if the transaction commits.

### 14.1. This Is Not a Recommendation for Production Auditing

The lab's purpose is solely to demonstrate **`DO ALSO` appending a query**.

Never copy this rule into a required per-row audit system without understanding:

- Multi-row INSERTs.
- `INSERT ... SELECT`.
- Expressions with side effects.
- `RETURNING` and upserts.
- How `NEW` expressions are substituted during rewriting.
- Error behavior and alternate write paths.
- DML operations other than `INSERT`.

For auditing each row that **actually changed**, triggers are normally the right tool.

## 15. What Are `OLD` and `NEW` Inside Rules?

Rules can reference pseudo-relations:

```sql
OLD.column_name
NEW.column_name
```

Availability depends on event:

- `INSERT`: `NEW` can be referenced for inserted values.
- `UPDATE`: both `OLD` and `NEW` can be referenced.
- `DELETE`: `OLD` can be referenced for deleted values.

Example:

```sql
VALUES (NEW.request_id, 'INSERT')
```

from the INSERT rule above.

### 15.1. Rule `OLD`/`NEW` Are Not PL/pgSQL Record Variables

In a row-level trigger:

```sql
NEW.request_id
```

is a field on the current row's record variable, accessed inside the trigger function at row execution time.

In a rule:

```sql
NEW.request_id
```

is syntax processed by the **query rewriter** inside an SQL query tree. It does not create a PL/pgSQL per-row loop, nor does it provide trigger metadata variables like `TG_OP`, `TG_TABLE_NAME`, or `TG_WHEN`.

### 15.2. Why Do Both Mechanisms Share the Names `OLD` and `NEW`?

Because both refer to before/after data images of an operation. Yet their **scope, timing, and evaluation model** are fundamentally different.

Confusing the two is one of the biggest sources of design bugs when developers move from triggers to rules.

## 16. Rules Operate per Statement, Not as Per-Row Callbacks

Suppose an UPDATE modifies 1,000 rows:

```sql
UPDATE rule375.products
SET unit_price = unit_price * 1.05
WHERE category = 'coffee';
```

A row-level UPDATE trigger is invoked once per updated row under trigger rules.

An `ON UPDATE` rewrite rule transforms the **query tree** of that UPDATE. In nontrivial cases, the rewriter generates queries/actions executed as set-based operations by the planner and executor.

So never reason as:

```text
ON UPDATE rule
   = 1000 invocations of a row-handling procedure
```

That mental model is wrong.

### 16.1. Multi-Row Operations Must Be Tested Explicitly

A rule that looks intuitive with:

```sql
INSERT INTO rule375.requests VALUES (2, 'A');
```

may behave quite differently from intuition for:

```sql
INSERT INTO rule375.requests
SELECT ...
FROM another_table;
```

or:

```sql
INSERT INTO rule375.requests
VALUES (3, 'B'), (4, 'C'), (5, 'D');
```

SQL writes are **set-based**; expression substitution and generated rule actions can diverge sharply from "invoke once per row."

### 16.2. Never Use Rules to Call External APIs per Row

If the goal is sending an email, making an HTTP request, or publishing to Kafka per committed row, a rule is not a stable hook for external side effects.

A cleaner design:

- Trigger writes an outbox row in the same transaction.
- Independent worker reads committed outbox rows after commit.
- Consumer handles idempotency, retries, and errors.

## 17. `DO INSTEAD NOTHING`: Suppressing a DML Type in the Lab

Create a dedicated table:

```sql
CREATE TABLE rule375.protected_notes (
    note_id integer PRIMARY KEY,
    note_text text NOT NULL
);

INSERT INTO rule375.protected_notes(note_id, note_text)
VALUES
    (1, 'Keep document A'),
    (2, 'Keep document B');
```

Create the rule:

```sql
CREATE RULE protected_notes_no_delete AS
ON DELETE TO rule375.protected_notes
DO INSTEAD NOTHING;
```

Test it:

```sql
DELETE FROM rule375.protected_notes
WHERE note_id = 1;
```

Then inspect:

```sql
SELECT note_id, note_text
FROM rule375.protected_notes
ORDER BY note_id;
```

With the rule active as defined, both rows remain intact.

### 17.1. A `DELETE` May Report 0 Affected Rows

When a rule replaces `DELETE` with `NOTHING`, the executor performs no delete. Never assume a row was deleted merely because the client sent `DELETE` and received no exception.

Inspect affected row counts / command tags or issue follow-up checks depending on client interfaces and task requirements.

### 17.2. Why Doesn't This Rule Guarantee Absolute Delete Protection?

It only intercepts **`DELETE` events** under rule mechanics. Gaps remain:

- A role holding `TRUNCATE` privilege can wipe the table via a different command.
- Owners/DBAs can alter or drop the rule.
- Other DDL commands can destroy data.
- An `UPDATE` path might alter or blank out content contrary to policy.
- It never replaces backups, retention policies, legal holds, or audits.

If the goal is privilege-level delete prevention, revoking `DELETE` privilege is more direct and understandable.

### 17.3. When Suppression Requires a Clear Error

`DO INSTEAD NOTHING` **silently skips** the action rather than raising a descriptive business error.

If unauthorized deletions must fail loudly with an SQLSTATE and diagnostic details, use privileges or a trigger raising an exception. Never silently drop requests when callers expect explicit rejection.

## 18. `DO INSTEAD`: Redirecting Commands to Another Table

Create a target table for redirected inserts:

```sql
CREATE TABLE rule375.inbox (
    request_id integer PRIMARY KEY,
    request_title text NOT NULL,
    accepted_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE rule375.submission_endpoint (
    request_id integer PRIMARY KEY,
    request_title text NOT NULL
);
```

Create the replacement INSERT rule:

```sql
CREATE RULE redirect_submission_insert AS
ON INSERT TO rule375.submission_endpoint
DO INSTEAD
    INSERT INTO rule375.inbox(
        request_id,
        request_title
    )
    VALUES (
        NEW.request_id,
        NEW.request_title
    );
```

Execute:

```sql
INSERT INTO rule375.submission_endpoint(
    request_id,
    request_title
)
VALUES (501, 'Redirected request');
```

Inspect both tables:

```sql
SELECT *
FROM rule375.submission_endpoint;

SELECT request_id, request_title
FROM rule375.inbox
ORDER BY request_id;
```

**Expected under the lab rule:**

- `submission_endpoint` does not store row 501 from that call.
- `inbox` receives row 501.

### 18.1. Still Not a Complete Business Router

Production systems require:

- Constraint alignment between the endpoint and destination table.
- Write privileges and input validation.
- Proper `RETURNING` handling.
- Multi-row INSERT support.
- Upsert and duplicate-ID semantics.
- Migrations and error reporting.
- Observability, retries, and idempotency.

In most cases, a **view with an `INSTEAD OF` trigger** or an explicit write function/API is far clearer than DML rules.

### 18.2. Be Careful Returning Results to Callers

A client might expect:

```sql
INSERT ... RETURNING request_id;
```

while a `DO INSTEAD` rule lacks a compatible `RETURNING` clause in the rule action. Never assume rewriting automatically pulls generated rows from `inbox` back through `RETURNING`.

## 19. Conditional Rules: Rule `WHERE` Differs from Action `WHERE`

General form:

```sql
CREATE RULE some_rule AS
ON UPDATE TO some_table
WHERE OLD.some_column = 'A'
DO INSTEAD
    ...;
```

This is a **rule qualification condition**, not simply a `WHERE` filter inside a row-level trigger function.

PostgreSQL combines the rule condition with the query tree, `OLD`/`NEW` relations, and the original query's `WHERE` clause under rewrite semantics.

### 19.1. The "Suppress Part of the Rows" Trap

Suppose one `UPDATE` touches both rows matching and rows not matching a conditional `INSTEAD` rule. Never assume PostgreSQL runs the rule for row A and then executes the original `UPDATE` for row B like a procedural per-row `IF/ELSE`.

Conditional `INSTEAD` rules follow intricate rewrite rules. When you need **per-row** conditional modification or blocking, a `BEFORE ROW` trigger or an `UPDATE` with explicit predicates/constraints is much easier to reason about.

### 19.2. Conditional `DO INSTEAD NOTHING` Is Easy to Misinterpret

Never ship a rule like:

```sql
ON UPDATE
WHERE OLD.status = 'LOCKED'
DO INSTEAD NOTHING;
```

to production assuming it automatically serves as a bulletproof row-locking policy. You must verify exact behavior with multi-row `UPDATE`s, outer `WHERE` predicates, `RETURNING`, and all write paths.

### 19.3. Usage Boundary

**Rules fit structural query transformation. Triggers fit row-level or statement-level behavior at execution time.**

## 20. `SELECT` Rules Differ Fundamentally from DML Rules

On views or tables, `ON SELECT` cannot be used as a generic "log an audit row before `SELECT`" hook.

Reasons:

- `SELECT` rules have strict structural requirements: name `_RETURN`, unconditional `INSTEAD`, single corresponding `SELECT` action.
- Query rewriting is not a per-read side-effect hook.
- View expansion may be transformed or evaluated repeatedly across complex queries, subqueries, and optimizations.
- Access permissions, logging integrity, and statistical accuracy would be compromised.

When you need **read access auditing**:

- Use database audit/logging facilities suited to the requirement.
- Evaluate the capabilities and limits of a dedicated audit extension.
- Log read events at trusted application/API boundaries.
- Protect privileges and log privacy.
- Never treat an `ON SELECT` rule as a per-row `BEFORE SELECT` trigger.

## 21. Automatically Updatable Views, `INSTEAD OF` Triggers, and `INSTEAD` Rules

Three options exist for writing through views:

### 21.1. Automatically Updatable View

```sql
CREATE VIEW v AS
SELECT id, name, is_active
FROM base_table
WHERE is_active;
```

When eligible, PostgreSQL translates DML to the base table automatically.

Prefer this when the view is simple and write mapping is unambiguous.

### 21.2. `INSTEAD OF` Trigger on a View

For complex views, you can attach:

```sql
CREATE TRIGGER ...
INSTEAD OF INSERT OR UPDATE OR DELETE
ON some_view
FOR EACH ROW
EXECUTE FUNCTION ...;
```

The trigger function decides where and how each row writes to underlying tables and returns `NEW` or `NULL` under `INSTEAD OF` trigger semantics.

This fits cases where DML mapping requires explicit per-row logic.

### 21.3. DML Rewrite Rule on a View

An `ON INSERT/UPDATE/DELETE DO INSTEAD ...` rule lets a view or relation respond to DML via query rewriting. However:

- `RETURNING` handling is awkward.
- Multi-row statements diverge easily from row-by-row intuition.
- Combining with certain SQL features hits strict restrictions.
- Procedural error handling and side effects are harder to control.

**Best practice:** prefer automatically updatable views; when complex write mapping is required, use `INSTEAD OF` triggers. Use DML rules only for clear technical reasons after understanding all limitations.

## 22. How Should `INSERT ... RETURNING` Be Handled?

Applications frequently write:

```sql
INSERT INTO rule375.requests(request_id, request_title)
VALUES (99, 'Demo')
RETURNING request_id;
```

On an ordinary table, `RETURNING` outputs values from the inserted rows.

When the relation has rewrite rules on `INSERT`, complications arise:

- Which action(s) actually execute?
- Does the rule action include `RETURNING` or not?
- Are multiple rules attached to the same event?
- Do the returned result shapes match?
- Is the rule `DO ALSO` or `DO INSTEAD`?

### 22.1. `RETURNING` Does Not Work Automatically Like in Triggers

PostgreSQL enforces **specific restrictions** on `RETURNING` with rule actions, notably across `DO ALSO`, `DO INSTEAD`, and caller DML requesting `RETURNING`.

With a redirect rule:

```sql
CREATE RULE redirect AS
ON INSERT TO endpoint
DO INSTEAD
    INSERT INTO real_table(...)
    VALUES (...);
```

never assume:

```sql
INSERT INTO endpoint(...)
VALUES (...)
RETURNING id;
```

will automatically return the `id` from `real_table`.

### 22.2. When `RETURNING` Is a Core Application Contract

Simpler designs:

- Run DML directly against the base table with `RETURNING`.
- Use an explicit write function/procedure that returns the needed values.
- Use an automatically updatable view where eligible.
- Use a properly designed `INSTEAD OF` trigger on a view.

If you still choose a rule, design and test every caller `RETURNING` variation on your exact PostgreSQL version.

## 23. Rules and `INSERT ... ON CONFLICT`

A very common PostgreSQL idiom:

```sql
INSERT INTO some_table(id, value)
VALUES (1, 'A')
ON CONFLICT (id)
DO UPDATE SET value = EXCLUDED.value;
```

When a target relation has `ON INSERT` or `ON UPDATE` rules, PostgreSQL imposes **restrictions** on using it with `INSERT ... ON CONFLICT`.

Never assume upserts combine with rules seamlessly the way triggers do.

### 23.1. Why Does This Matter?

An upsert has two semantic paths:

1. Insert a new row.
2. On a matching conflict, execute `DO UPDATE` or `DO NOTHING`.

If the target relation also applies query rewrite actions, reasoning about which records get written and what queries get generated becomes ambiguous or unsupported. PostgreSQL rejects restricted combinations rather than promising fragile semantics.

### 23.2. Practical Design Guideline

If the system relies heavily on upserts:

- Prefer plain base tables with clear constraints and unique indexes.
- Use row-level triggers when checks or audits are needed.
- Avoid custom `INSERT`/`UPDATE` rules on upsert targets.
- Test `ON CONFLICT DO UPDATE`, `DO NOTHING`, and `RETURNING` explicitly.

Never replace `ON CONFLICT` with a naive "if exists then UPDATE else INSERT" rule lacking concurrency control. Unique constraints and native `ON CONFLICT` provide concurrency guarantees that manual query rewriting cannot replicate safely.

## 24. `COPY FROM` Does Not Fire Rules Like Regular `INSERT`

PostgreSQL provides bulk loading via:

```sql
COPY some_table (...) FROM ...;
```

**`COPY FROM` does not apply query rewrite rules per row the way an `INSERT` statement does.**

This matters hugely if you planned to rely on an `ON INSERT DO ALSO` rule to:

- Audit every loaded row.
- Enforce creation of companion records.
- Redirect data to another table.
- Perform validation logic.

A bulk ingestion pipeline using `COPY` **bypasses rule-based logic**.

### 24.1. Triggers and Constraints Behave Differently

In PostgreSQL, `COPY FROM` fires eligible triggers and checks table constraints under their standard rules. That makes triggers and constraints far more dependable than rules for invariants that must hold during bulk loads as well.

### 24.2. Do Not Say "`COPY` Bypasses All PostgreSQL Protections"

False. The point is specifically that **`COPY FROM` does not apply query rewrite rules** the way you might expect from `INSERT` SQL. It still operates within PostgreSQL's transaction, permission, and constraint systems.

## 25. `TRUNCATE` Is Not `DELETE`

Suppose you declared:

```sql
CREATE RULE protected_notes_no_delete AS
ON DELETE TO rule375.protected_notes
DO INSTEAD NOTHING;
```

You still cannot claim the table is protected against all row removal.

```sql
TRUNCATE TABLE rule375.protected_notes;
```

is a distinct command. It does not turn into `DELETE` row events for an `ON DELETE` rule to intercept.

### 25.1. Why Protecting Data via a `DELETE` Rule Is Incomplete

- Roles holding `TRUNCATE` privilege bypass the `DELETE` rule entirely.
- Other DDL commands (`DROP`, `ALTER`) can wipe data.
- Owners/DBAs can drop or alter the rule.
- Regulatory/retention policies require strict privilege governance and logging.

### 25.2. Enforce Protection Through Privileges

If only administrators may delete data:

- Revoke `DELETE` and `TRUNCATE` from non-privileged application roles.
- Ensure application roles lack unnecessary schema privileges or table ownership.
- Maintain proper backups and auditing.
- Use error-raising triggers or soft-delete workflows where domain validation is needed.

Never rely on a rule as the primary shield for critical data.

## 26. `VOLATILE` Expressions and Multiple Evaluation Risk

Expressions with side effects or values that change on every invocation:

```sql
nextval('some_sequence')
random()
clock_timestamp()
```

are classified as volatile in PostgreSQL.

When a statement contains volatile expressions and a rewrite rule generates extra queries or substitutes `NEW` expressions in multiple places, evaluation counts can diverge from the intuition "evaluate `NEW` once and pass that value to both actions."

### 26.1. Thought Experiment

The developer imagines:

```text
Main table INSERT evaluates nextval -> id N
DO ALSO action logs id N
```

Because rule rewriting substitutes the expression tree rather than binding a materialized tuple, a volatile expression can end up evaluated more times or differently than expected.

### 26.2. How to Avoid This

When logs must capture **the exact ID persisted in the inserted row**, an `AFTER ROW INSERT` trigger reading `NEW.id` gives the right contract.

When events must go outside the DB after commit:

- Trigger writes to an outbox table in the transaction.
- Worker publishes externally after commit.
- Never fire emails/HTTP directly from a rule action.

### 26.3. Do Not Use `statement_timestamp()` or `now()` as Proof of Single Evaluation

`now()` returns a constant transaction timestamp, so two evaluations produce equal values — that proves nothing about how many times an expression ran. Understand volatility and rewrite structure rather than trusting matching timestamps.

## 27. Rules Do Not Guarantee "Once-Only Side Effects"

A `DO ALSO INSERT INTO log...` rule merely adds a rewritten query action for matching statements.

It does not automatically guarantee:

- Exactly one log row per truly modified row.
- Coverage of every write path (`COPY`, direct writes, etc.).
- No duplicates when callers retry.
- Once-only post-commit external delivery.
- Strict consumer delivery order.
- Resilience if downstream tables or constraints change.

### 27.1. End-to-End Exactly-Once Is a Larger Problem

Even `AFTER` triggers paired with an outbox usually still need:

- Unique event IDs.
- Idempotent consumers.
- Retry policies.
- Deduplication.
- Out-of-order handling.
- Monitoring and replay tooling.

Rules solve none of these distributed-systems concerns.

## 28. `UPDATE` Rules with `OLD`/`NEW` Are Hard to Reason About

An `ON UPDATE` rule can reference:

```sql
OLD.unit_price
NEW.unit_price
```

Looking superficially like trigger code:

```sql
IF NEW.unit_price <> OLD.unit_price THEN ...
```

Yet the underlying mechanism is completely different.

### 28.1. Inside Triggers

A `BEFORE`/`AFTER ROW UPDATE` trigger runs per row with bound `OLD` and `NEW` record images matching its timing.

### 28.2. Inside Rules

`OLD` and `NEW` are pseudo-relations used to rewrite query trees; they are not PL/pgSQL record variables updated across a per-row loop.

### 28.3. When You Need to Block Steep Price Drops

Business rule:

```text
If new unit_price is under 50% of old unit_price,
reject the UPDATE with a clear error.
```

This is a **per-row comparison** of `OLD` and `NEW`. Write a `BEFORE ROW` trigger:

```sql
CREATE OR REPLACE FUNCTION rule375.guard_price_drop()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
    IF NEW.unit_price < OLD.unit_price * 0.5 THEN
        RAISE EXCEPTION
            'New price is less than half the old price'
            USING ERRCODE = '23514';
    END IF;

    RETURN NEW;
END;
$$;
```

Attach this function to the table via a trigger; the takeaway is that this belongs in row-by-row PL/pgSQL trigger code, not a rewrite rule.

## 29. Triggers: Key Differences from Rules

| Criterion | Rewrite Rule | Trigger |
|---|---|---|
| Primary stage | Rewriter, before planner/executor | Executor, when the DML event occurs |
| Processing unit | Query / query tree | Statement or row (`FOR EACH`) |
| Accessing `OLD`/`NEW` | Pseudo-relations during rewrite | `OLD`/`NEW` row records in row triggers; transition tables in supported statement triggers |
| Emitting actions | Generates or replaces query trees | Invokes trigger function |
| Per-row value validation | Error-prone, not the primary tool | `BEFORE ROW` trigger fits well |
| Auditing truly modified rows | Not recommended as primary choice | `AFTER ROW` trigger fits far better |
| Complex view DML | Possible via `INSTEAD` rules | `INSTEAD OF` trigger is usually clearer |
| View `SELECT` expansion | Foundational mechanism (`_RETURN`) | Regular triggers do not expand `SELECT` views |
| Bulk load with `COPY FROM` | `COPY` does not fire rules | `COPY FROM` can fire triggers |
| `ON CONFLICT` | Significant restrictions with DML rules | Defined PostgreSQL trigger semantics |
| `RETURNING` | Rule-specific restrictions | Interacts more directly via base DML |
| Per-row predictability | Unintuitive for most developers | Much clearer with well-defined row triggers |

### 29.1. Triggers Also Have Trade-Offs

Triggers can cause deadlocks, unexpected cascades, retry issues, overhead, and special interactions with multi-row statements and partitioning.

Not every business rule belongs in a trigger. If an invariant can be expressed as `CHECK` or `UNIQUE`, a constraint is simpler and more reliable.

### 29.2. Prefer the Tool at the Right Layer

- Domain/value checks -> `CHECK` / `NOT NULL`.
- Uniqueness -> `UNIQUE`.
- Referential integrity -> `FOREIGN KEY`.
- Row-level authorization -> RLS.
- Per-row operational logic -> triggers.
- Logical read projections -> `CREATE VIEW`.
- Specialized query-tree rewriting -> rules, only when genuinely needed.

## 30. Example: Replacing an Audit Rule with an `AFTER ROW` Trigger

`rule375.requests` already has an audit rule attached. To demonstrate the trigger alternative without double-logging into the same table, create a **separate practice table**.

```sql
CREATE TABLE rule375.trigger_requests (
    request_id integer PRIMARY KEY,
    request_title text NOT NULL
);

CREATE TABLE rule375.trigger_request_log (
    log_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    request_id integer NOT NULL,
    event_name text NOT NULL,
    logged_at timestamptz NOT NULL DEFAULT now()
);
```

Trigger function:

```sql
CREATE OR REPLACE FUNCTION rule375.log_trigger_request_insert()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
    INSERT INTO rule375.trigger_request_log(
        request_id,
        event_name
    )
    VALUES (
        NEW.request_id,
        'INSERT'
    );

    RETURN NEW;
END;
$$;
```

Create the trigger:

```sql
CREATE TRIGGER trg_trigger_requests_insert
AFTER INSERT ON rule375.trigger_requests
FOR EACH ROW
EXECUTE FUNCTION rule375.log_trigger_request_insert();
```

Insert multiple rows:

```sql
INSERT INTO rule375.trigger_requests(
    request_id, request_title
)
VALUES
    (201, 'Request A'),
    (202, 'Request B'),
    (203, 'Request C');
```

Inspect:

```sql
SELECT
    request_id,
    event_name
FROM rule375.trigger_request_log
ORDER BY request_id;
```

Expect three audit rows corresponding cleanly to the three inserted rows in the statement/transaction.

### 30.1. Why Does `AFTER ROW` Fit Here?

The trigger executes once per row actually inserted for that event. `NEW.request_id` holds the value of the processed row, not a substituted rewrite expression.

### 30.2. Should Committed Transaction Logs Be Written Inside the Trigger?

The log row is inserted in the same transaction. If the transaction rolls back, both the business row and the audit row roll back together. That is usually desirable for transactional audits and outboxes.

If you must retain **failed/rolled-back attempts** too, you need an auditing/logging mechanism outside the failing transaction; regular triggers cannot persist changes from rolled-back transactions.

### 30.3. `RETURN NEW` in an `AFTER` Trigger

In an `AFTER ROW` trigger, the return value does not control tuple persistence as it does in `BEFORE ROW`, though `RETURN NEW;` is valid, readable, and consistent. Never assume assigning `NEW` and returning `NEW` in an `AFTER` trigger alters the stored tuple.

## 31. Data Invariants: Use Constraints Instead of Rules

Suppose every product must have a non-negative price. We declared:

```sql
unit_price numeric(12, 2) NOT NULL
    CHECK (unit_price >= 0)
```

This is a **data-state invariant** enforced regardless of which SQL path modifies the table.

### 31.1. `CHECK` Fits Single-Row Valid Expressions

For example:

```sql
CHECK (unit_price >= 0)
```

applies automatically on `INSERT` and `UPDATE`. No query rewrite rule is needed.

### 31.2. `UNIQUE` Prevents Duplicates Safely

```sql
CREATE TABLE rule375.external_ids (
    external_id text PRIMARY KEY,
    description text NOT NULL
);
```

Never write a rule like:

```text
If duplicate ID exists, DO INSTEAD NOTHING
```

to replace a unique constraint; concurrency causes race conditions, and callers receive no clear signal of whether the write occurred.

### 31.3. `FOREIGN KEY` Enforces Referential Integrity

An order referencing a valid product belongs in a `FOREIGN KEY` constraint, not an `ON INSERT` rule issuing subqueries to decide whether to insert.

### 31.4. What If a Rule Spans Multiple Rows?

That may require transactions, explicit locking protocols, unique/exclusion constraints, or carefully designed triggers. A `CHECK` constraint alone cannot enforce every cross-row/cross-table invariant, yet a rule is rarely the right default either.

## 32. RLS: Controlling Who Can Read and Write Which Rows

Suppose each request belongs to a tenant.

A rule:

```sql
CREATE RULE ...
```

is not a general row-level access-control layer equivalent to **Row Level Security**.

### 32.1. Why Aren't Rules a Substitute for RLS?

- Rewritten queries interact subtly with different statement forms and bulk load paths.
- Rules do not authenticate callers.
- Rules do not enforce per-row/per-tenant authorization consistently across access paths.
- Interactions with views, joins, `RETURNING`, and DML grow complex.
- Administrative privileges require separate governance.

### 32.2. Mental Model

```text
Role / authenticated identity
           |
           v
PostgreSQL privileges
           |
           v
Row Level Security policies (when enabled and applicable)
           |
           v
Authorized query execution
```

### 32.3. Never Trust Unvalidated Client-Supplied Tenant IDs

A service accepting a client-supplied `tenant_id` parameter and appending `WHERE tenant_id = p_tenant_id` does not verify that the caller actually belongs to that tenant.

Bind tenant scope to verified authentication/authorization state and lock down direct permissions on tables, views, and routines.

## 33. Views and Security Boundaries: Avoid Oversimplification

Views are often used to expose a subset of columns and rows:

```sql
CREATE VIEW rule375.public_product_catalog AS
SELECT
    product_id,
    product_name,
    category,
    unit_price
FROM rule375.products
WHERE is_active;
```

Users granted `SELECT` on the view may not need direct privileges on the underlying table depending on owner/permission configuration and PostgreSQL version.

However, privilege checks, RLS, and view access follow specific PostgreSQL rules and configuration options.

### 33.1. `security_barrier`

Some views restrict sensitive rows/columns that callers must not see. When callers can pass untrusted user expressions, predicate evaluation order / pushdown matters.

PostgreSQL provides the `security_barrier` view option to support those boundaries.

Example syntax:

```sql
CREATE VIEW rule375.public_product_catalog_barrier
WITH (security_barrier = true)
AS
SELECT
    product_id,
    product_name,
    unit_price
FROM rule375.products
WHERE is_active;
```

However, `security_barrier` alone does not perform tenant authentication or seal every leak channel; evaluate RLS, grants, `LEAKPROOF` functions, and your threat model.

### 33.2. `security_invoker`

Modern PostgreSQL versions support the `security_invoker` view option, changing how permissions on underlying relations are checked according to documented semantics.

Usage example:

```sql
-- Syntax example for PostgreSQL versions supporting this option:
CREATE VIEW rule375.invoker_catalog
WITH (security_invoker = true)
AS
SELECT product_id, product_name
FROM rule375.products
WHERE is_active;
```

Verify your server version and privilege setup. Never assume views always run as owner or always as invoker across all setups.

### 33.3. Never Implement Security via `DO INSTEAD NOTHING`

A `DELETE` rule that silently does nothing is not an authorization policy. If a role must not delete rows, **revoke `DELETE` privilege**, or apply RLS and triggers as appropriate.

## 34. Rules and Concurrency: Think About Transactions, Not Just Syntax

Query rewriting finishes before the executor runs. Any generated actions execute within the caller's transaction context and obey MVCC, locking, and constraints.

### 34.1. Rule Actions Do Not Run in Separate Independent Transactions

If a `DO ALSO` action writes to a secondary table and one of the rewritten actions fails, PostgreSQL does not half-commit "log succeeded, main table failed" like two separate transactions.

All actions share PostgreSQL's transaction and rollback boundaries.

### 34.2. Atomicity Does Not Equal Business Correctness

Having both the original command and the rule action roll back together on failure **does not prove** you recorded accurate per-row logs, preserved ordering, or stayed consistent with external systems.

Distinguish clearly between:

- **Atomicity**: changes commit or roll back together in one transaction.
- **Correctness**: rows and event semantics accurately reflect domain rules.
- **Delivery**: events ship reliably after commit with retry handling.
- **Idempotency**: repeated invocation causes no duplicate side effects.
- **Isolation**: concurrent transactions preserve invariants.

Rules solve none of these five concerns by themselves.

## 35. Multi-Row `UPDATE`/`DELETE`: Surprising Effects

A statement:

```sql
UPDATE rule375.products
SET unit_price = unit_price * 1.10
WHERE category = 'coffee';
```

can affect many rows.

When DML rules generate extra queries:

- The rewriter treats the SQL statement as a whole query tree.
- `OLD`/`NEW` expand according to query relations and expressions.
- Generated actions can carry joins and predicates referencing affected sets.
- Callers may attach `RETURNING`.
- DML still encounters constraints and concurrent write conflicts.

### 35.1. Common Wrong Assumption

```text
Each row increased by 10%
  -> invoke rule
     -> INSERT one log record
```

Do not build mental models of rules around this.

### 35.2. Proper Design

If you need to audit every row whose price changed:

```sql
CREATE TRIGGER trg_price_audit
AFTER UPDATE OF unit_price ON rule375.products
FOR EACH ROW
WHEN (OLD.unit_price IS DISTINCT FROM NEW.unit_price)
EXECUTE FUNCTION rule375.some_audit_trigger_function();
```

This is a **template pattern**; `some_audit_trigger_function()` must exist before creating the trigger. The point is using a trigger with `OLD`/`NEW` records and `IS DISTINCT FROM` for NULL-safe comparison.

### 35.3. Trigger `WHEN` Differs from Rule `WHERE`

A trigger `WHEN` clause decides whether to fire the trigger for an event/row under trigger semantics.

A rule `WHERE` clause controls query rewriting. You cannot rename one to the other and expect identical behavior without proof.

## 36. Rules and Complex SQL Constructs

Statements that interact subtly with rules include:

- `INSERT ... ON CONFLICT`.
- `INSERT ... RETURNING`.
- `UPDATE ... FROM`.
- `DELETE ... USING`.
- `WITH` and data-modifying CTEs.
- `MERGE`, subject to version-specific rule-target restrictions.
- Multi-row `VALUES` and `INSERT ... SELECT`.
- Automatically updatable views or `INSTEAD OF` triggers.
- Writes targeting partitioned tables.

### 36.1. Never Assume a Rule Behaves Identically Across All DML Forms

A rule tested on `INSERT VALUES (1, 'A')` proves nothing about `INSERT ... ON CONFLICT DO UPDATE RETURNING ...`.

When applications use diverse DML forms, test every form on the exact PostgreSQL version with real privileges and schemas.

### 36.2. `MERGE` and Rule Targets

`MERGE` has specific restrictions and semantics regarding target relations with rules in PostgreSQL versions supporting `MERGE`. Never assume `ON INSERT`/`UPDATE`/`DELETE` rules on a table compose transparently with `MERGE`.

Consult the `MERGE` and `CREATE RULE` documentation for your **exact server version** before designing around it.

### 36.3. Partitions Do Not Turn Rules into Row Triggers

Partitioning changes tuple routing and partition-level execution, not rule rewrite semantics. On partitioned tables, rely on native partitioning, indexes/constraints, and supported triggers rather than ad-hoc rewrite rules per partition.

## 37. Recursive Rules and Rewrite Loops

A rule can produce an action targeting a relation/event that triggers another rule, forming useless or illegal rewrite cycles.

Dangerous setup:

```text
ON INSERT TO A
   DO INSTEAD INSERT INTO B ...

ON INSERT TO B
   DO INSTEAD INSERT INTO A ...
```

Without a proper stopping condition, the rewrite system detects the loop and raises an error rather than running as the author hoped.

### 37.1. Avoid Self-Referencing Rules

A rule on table A that generates the same DML operation back onto A risks infinite/recursive rewriting. Never use rules to implement loops.

### 37.2. When You Need Controlled Iteration

- For in-database iterative logic, use a PL/pgSQL function/procedure with explicit exit conditions.
- For set-based updates, write direct SQL.
- For asynchronous workflows, use a queue/outbox.
- For hierarchical data, use recursive CTEs (`WITH RECURSIVE`) for **querying**, not self-triggering rules.

## 38. Multiple Rules on the Same Relation and Event

A relation can hold multiple rules. When several rules apply to one DML event, verify:

- Whether any rules are conditional (`WHERE`).
- Whether they use `DO ALSO` or `INSTEAD`.
- Whether actions modify overlapping tables/rows.
- Whether `DEFAULT` or volatile expressions appear.
- Whether callers use `RETURNING`.
- Whether actions could cause recursive rewrites.

### 38.1. Never Rely on Coincidental Ordering

PostgreSQL has deterministic internal ordering rules for rule application, yet you must not structure business workflows as "rule A logs, rule B updates, rule C notifies" assuming procedural callback order just because names sort nicely.

### 38.2. When Clear Business Sequencing Matters

An explicit function/procedure or carefully designed trigger workflow is far easier to maintain:

```text
validate
  -> write data
  -> insert outbox
  -> commit
  -> async delivery
```

Define transaction boundaries and error handling cleanly for every step.

## 39. Rules and Auditing: Choosing Triggers, Logs, or Outboxes

Auditing comes in several forms:

| Need | Suitable Mechanism |
|---|---|
| Knowing which SQL text clients submitted | Database or application statement logging/auditing |
| Knowing which rows were truly INSERTed/UPDATEd/DELETEd | `AFTER ROW` trigger or proper change data capture |
| Storing old/new column history | Trigger with `OLD`/`NEW` records + history table |
| Emitting durable sync events | Transactional outbox / CDC |
| Tracking `SELECT` data access | Statement/API-level logging/auditing; never arbitrary `SELECT` rewrite rules |
| Blocking changes to immutable fields | `BEFORE ROW` trigger / privileges / constraints |
| Restricting which rows a user sees | RLS and grants |

### 39.1. Auditing via `DO ALSO` Is a Demo, Not a Production Default

Newcomers often write:

```sql
CREATE RULE log_change AS
ON UPDATE TO orders
DO ALSO INSERT INTO log ...;
```

and believe tracking is solved. Multi-row DML, `OLD`/`NEW` query binding, volatile expressions, and bulk write paths make rules a poor foundation for critical auditing.

### 39.2. When Before/After Values Are Needed

An `AFTER UPDATE` row-level trigger provides `OLD` and `NEW` directly inside the function, letting you check:

```sql
IF OLD.status IS DISTINCT FROM NEW.status THEN
    ...
END IF;
```

You still must handle types, permissions, privacy, and transactions, yet per-row behavior is far easier to verify.

## 40. Source of Truth and Transactional Outbox

Suppose an application creates orders and syncs them to a search index, analytics pipeline, or message broker.

Structurally sound architecture:

```text
Application
   |
   v
PostgreSQL transaction
   |
   +-- INSERT order
   |
   +-- INSERT outbox event
   |
   v
COMMIT
   |
   v
Worker reads outbox
   |
   +-- publish to search / queue
   +-- retry / deduplicate
   +-- mark processed
```

### 40.1. Why Aren't Rules the Main Tool Here?

Rules do not provide external transaction boundaries, downstream delivery guarantees, retries, or idempotency.

Using an `AFTER` trigger to write the outbox in the same transaction, or having the application write both order and outbox explicitly in one transaction, are standard approaches.

### 40.2. Never Make External HTTP Calls Directly Inside Triggers by Default

Although triggers beat rules for per-row changes, calling external APIs while a DB transaction is open:

- Increases latency and holds locks longer.
- Lets network hiccups fail database transactions.
- Creates non-rollbackable external side effects if the DB rolls back.
- Complicates retries and idempotency.

An outbox decouples durable data commits from external delivery.

## 41. Performance: Rules Are Not a Query Acceleration Shortcut

A rewrite rule can:

- Generate additional queries/actions.
- Complicate the query tree.
- Add scans or joins.
- Shift execution cost onto other tables.
- Interact with planning and plan caching.
- Multiply logical statements optimized and executed.

### 41.1. Views via `_RETURN` Optimize Well

Simple views often optimize much like inlined SQL, which is why clean view abstractions rarely add meaningful overhead by themselves.

### 41.2. DML Rules Can Add Hidden Overhead

A seemingly simple:

```sql
INSERT INTO endpoint ...
```

can expand into multiple queries, so benchmarking a simple `INSERT` on a bare table misrepresents workloads running through rules.

### 41.3. Measure Full Impact

- Run `EXPLAIN` on view `SELECT` queries.
- Monitor application query latency and p95/p99.
- Measure buffer/page reads and writes.
- Check WAL generation volume.
- Count modified/logged rows.
- Watch lock waits and deadlocks.
- Inspect plan cost and structure.
- Benchmark multi-row `INSERT`/`UPDATE`/`DELETE`.

Never assume rules are "free" simply because rewriting happens before the planner.

## 42. Materialized Views: When Results Should Be Stored

Regular views via `_RETURN` query live source data on demand. When an expensive aggregate report tolerates slightly stale data, consider a `MATERIALIZED VIEW`:

```sql
CREATE MATERIALIZED VIEW rule375.category_totals AS
SELECT
    category,
    count(*) AS product_count,
    sum(unit_price) AS total_price
FROM rule375.products
GROUP BY category;
```

Query it:

```sql
SELECT *
FROM rule375.category_totals
ORDER BY category;
```

### 42.1. Materialized Views Do Not Auto-Update on Every `INSERT`

After underlying data changes, a normal materialized view must be refreshed:

```sql
REFRESH MATERIALIZED VIEW rule375.category_totals;
```

### 42.2. `REFRESH CONCURRENTLY` Has Prerequisites

You cannot slap `CONCURRENTLY` onto any materialized view without meeting prerequisites such as a qualifying unique index and populated state. Check PostgreSQL docs before deploying.

### 42.3. When Should You Choose a Materialized View?

- Repeated heavy aggregate reports.
- High recomputation cost.
- Staleness within a refresh schedule is acceptable.
- Monitoring covers data freshness and refresh failures.

Never attach a `DO ALSO` rule that runs `REFRESH MATERIALIZED VIEW` on every insert: it destroys OLTP throughput and introduces severe lock contention.

## 43. Managing Rules: `DROP` and Altering Definitions

To remove the delete-blocking rule in the lab:

```sql
DROP RULE protected_notes_no_delete
ON rule375.protected_notes;
```

Normal `DELETE` statements now behave according to table privileges and constraints.

### 43.1. `DROP RULE` vs. `DROP TABLE`

`DROP RULE ... ON relation` drops only the named rule on that relation; it does not drop the table.

### 43.2. `CREATE OR REPLACE RULE`

PostgreSQL supports replacing a rule definition with:

```sql
CREATE OR REPLACE RULE rule_name AS
ON ...
DO ...;
```

In migrations, however, changing a rule alters the semantics of existing SQL statements sent by callers without changing caller code. Never treat it as a harmless internal tweak.

### 43.3. Rule Names Are Scoped to Each Relation

Rule names live per relation, so `DROP RULE` requires `ON relation` to avoid ambiguity across tables sharing a rule name.

### 43.4. Never Edit `pg_rewrite` Directly

System catalogs are not meant for raw DML updates to "toggle rules off." Always use supported DDL through controlled migrations.

## 44. Inspecting Rule Status and Dependencies

Beyond rule SQL text, inspect rule metadata:

```sql
SELECT
    r.oid,
    n.nspname,
    c.relname,
    r.rulename,
    r.ev_type,
    r.ev_enabled,
    r.is_instead
FROM pg_rewrite AS r
JOIN pg_class AS c
    ON c.oid = r.ev_class
JOIN pg_namespace AS n
    ON n.oid = c.relnamespace
WHERE n.nspname = 'rule375'
ORDER BY c.relname, r.rulename;
```

### 44.1. Enabled State and Replication Roles

PostgreSQL tracks enabled state for rules under session/replication roles. Seeing a rule in catalogs does not automatically mean it fires in every session configuration.

When troubleshooting unexpected behavior, verify:

- Whether the rule is enabled (`ev_enabled`).
- `session_replication_role` if relevant and accessible.
- Actual statement type (`INSERT`, `COPY`, `MERGE`, `TRUNCATE`, or view DML).
- Privileges and transaction state.
- Any `WHERE` condition on the rule.
- Interactions with triggers and constraints.

### 44.2. Never Toggle Rules Off as a Production "Hotfix"

Disabling or altering rule states mid-flight can route concurrent writes down inconsistent paths, corrupting derived state. Require explicit approval, migration planning, and a clear rollback path.

## 45. Example: Refactoring a DML Rule to a Trigger Safely

Suppose a project currently has:

```sql
CREATE RULE audit_orders_update AS
ON UPDATE TO orders
DO ALSO INSERT INTO orders_audit ...;
```

(This is an **illustrative sketch**, not complete runnable SQL.)

### 45.1. Refactoring Goals

- Accurately audit rows that actually updated.
- Record old/new values per policy.
- Support multi-row DML cleanly.
- Preserve compatibility with `ON CONFLICT` and `RETURNING` APIs.
- Minimize duplicate-log risk.
- Maintain a clean rollback path if the new trigger malfunctions.

### 45.2. Controlled Migration Steps

1. Inspect the exact existing definition with `pg_get_ruledef`.
2. Identify every DML caller touching `orders`.
3. Assess current audit coverage and existing duplicates.
4. Design the audit/outbox schema with event IDs, timestamps, and actor context.
5. Implement the trigger function with clear `OLD`/`NEW` handling.
6. Test `INSERT`/`UPDATE`/`DELETE`, multi-row batches, `COPY`, upserts, and `RETURNING`.
7. Structure the migration so the old rule and new trigger **never double-write** simultaneously.
8. Cut over cleanly within a coordinated migration/transaction, verifying permissions.
9. Reconcile logs and base data.
10. Monitor errors and keep a tested rollback procedure ready.

Never "add the new trigger while keeping the old rule for a few days to be safe" if both insert into the same audit table — that causes duplicate records.

### 45.3. Never Use `TRUNCATE` to Wipe Duplicate Audit Logs

If audit logs are regulated or required history, never wipe them to hide a migration mistake. Follow formal reconciliation, retention, and audit-trail policies.

## 46. Decision Matrix: Choosing the Right Mechanism

| Requirement | Preferred Choice | Why |
|---|---|---|
| Expose a fixed `SELECT` projection | `CREATE VIEW` | View rewriting via `_RETURN` |
| Simple view needing `INSERT`/`UPDATE` | Automatically updatable view | Avoids custom DML rules |
| Prevent view edits from leaving the view's filter | `WITH CHECK OPTION` (where supported) | Clear view contract |
| Complex view needing row-by-row DML mapping | `INSTEAD OF` trigger | Explicit per-row semantics |
| Price must be non-negative | `CHECK` | Table-level data invariant |
| Prevent duplicate codes | `UNIQUE` | Race-free compared to pre-checks |
| Enforce valid parent-child links | `FOREIGN KEY` | Native referential integrity |
| Restrict visible/writable rows per role/tenant | Grants + RLS | Enforced access control |
| Audit every row INSERTed/UPDATEd/DELETEd | `AFTER ROW` trigger | Actual per-row `OLD`/`NEW` state |
| Mutate/normalize row values before write | `BEFORE ROW` trigger | Modifies `NEW` cleanly |
| Sync events to search / message brokers | Outbox / CDC | Durable delivery and replay |
| Serve precomputed aggregate datasets | Materialized view | Fast reads with scheduled refreshes |
| Transform query tree at rewrite stage for rare special cases | Rule | Only when limits are fully understood |
| Block `DELETE` for application roles | `REVOKE DELETE` or RLS/triggers | Never `DO INSTEAD NOTHING` alone |
| Bulk import with validation rules | Constraints/triggers + staging | `COPY` skips rules |
| Upsert rows by unique key | `INSERT ... ON CONFLICT` | Never emulate with rules |

**Rule of thumb:** never choose `CREATE RULE` merely because the word "rule" sounds like "business rule." Choose it only when you specifically want **query rewriting**.

## 47. Misconceptions to Avoid

### Misconception 1 — Rules Work Like Triggers

No. Rules rewrite SQL query trees; triggers run in response to DML execution events.

### Misconception 2 — `OLD` and `NEW` Are Always PL/pgSQL Variables

No. In rules, `OLD`/`NEW` are pseudo-relations in query rewriting. In trigger functions, they are row records within trigger execution context.

### Misconception 3 — `DO ALSO` Guarantees Execution "After" the Original Command

Do not design around an `AFTER` callback model. Rules generate additional rewritten queries at rewrite time.

### Misconception 4 — `DO INSTEAD NOTHING` Is Complete Data Protection

No. It does not replace privileges, constraints, backups, RLS, or block `TRUNCATE`.

### Misconception 5 — An `ON INSERT` Rule Also Fires on `COPY`

No. `COPY FROM` follows bulk-load semantics and does not invoke query rewrite rules like SQL `INSERT`.

### Misconception 6 — Rules Compose Naturally with `ON CONFLICT`

Significant restrictions apply. Avoid DML rules on upsert targets unless explicitly verified and supported.

### Misconception 7 — `INSERT ... RETURNING` Always Returns Rows from a Redirected Table

Not automatically. `RETURNING` with rewrite rules has strict rules and limitations.

### Misconception 8 — Creating a View Always Slows Queries Down

Simple views often optimize very cleanly once expanded by the rewriter.

### Misconception 9 — Creating a View Materializes Data Separately

Regular views store no rows; materialized views store physical snapshots separately.

### Misconception 10 — Every View Is Automatically Updatable

No. Automatic updatability requires strict structural conditions.

### Misconception 11 — View `CHECK OPTION` Always Applies Through Custom `INSTEAD` Rules

Do not assume that. Interactions between `CHECK OPTION` and custom `INSTEAD` rules or triggers have specific rules and limits.

### Misconception 12 — Rule `WHERE` Equals Row-Level `IF`

No. It is a rewrite qualification condition, not a per-row procedural branch.

### Misconception 13 — Rules Are the Best Tool for Auditing

Not by default. Triggers, database audit logs, or CDC fit most auditing requirements much better.

### Misconception 14 — `DO ALSO` Logging Gives Exactly-Once Event Delivery

No. Distributed delivery, retries, and deduplication must be engineered explicitly.

### Misconception 15 — Rules Can Loop Indefinitely Like While Loops

Self-referencing rules risk recursive rewrite errors; never use rules to build loops.

### Misconception 16 — Not Seeing `_RETURN` in `pg_rules` Means a View Has No Rewrite Rule

Not necessarily. Inspect `pg_rewrite` and `pg_get_viewdef`.

### Misconception 17 — `EXPLAIN` Must List Every Applied Rule

`EXPLAIN` shows the post-rewrite, optimized execution plan, not a rewrite log.

### Misconception 18 — Rules Speed Up Queries Automatically

They can add extra queries, scans, and execution overhead.

### Misconception 19 — Rules Can Replace Privileges

No. Proper grants and RLS must be configured explicitly.

### Misconception 20 — Modifying a Rule Is Harmless

No. It changes how existing caller SQL executes without touching caller code.

### Misconception 21 — Running Both an Audit Rule and an Audit Trigger Gives "Double Protection"

It causes duplicate audit rows and reconciliation headaches.

### Misconception 22 — SQL in a Rule Action Runs Row-by-Row

No. Rules generate query-level SQL trees; multi-row behavior must be analyzed as set operations.

### Misconception 23 — Checking `now()` Proves an Action Evaluated Only Once

`now()` returns transaction start time, not an evaluation counter.

### Misconception 24 — Rules Can Implement a Business State Machine

Prefer constraints, triggers, transactional functions/procedures, or controlled service workflows.

### Misconception 25 — A View Is an Absolute Security Boundary

Owner/invoker privileges, RLS, `security_barrier`/`security_invoker`, and leakproof considerations must all be evaluated.

## 48. Practice Exercises with Solutions

Exercises relate to the `rule375` lab. Intentional-error commands or data-modifying queries should run in an isolated practice environment.

### Exercise 1. Which Pipeline Stage Owns Rules?

**Question:** Does `CREATE RULE` operate in the parser, rewriter, planner, or executor?

**Answer:** Primarily in the **query rewriter**, after analysis builds the query tree and before planning and execution.

### Exercise 2. Why Does a Rule Differ from a Row Trigger?

**Answer:** A rule rewrites query trees for matching events; a row trigger executes per affected row inside the executor according to its trigger definition.

### Exercise 3. Standard View Creation Syntax

```sql
CREATE VIEW rule375.only_coffee AS
SELECT product_id, product_name, unit_price
FROM rule375.products
WHERE category = 'coffee';
```

**Answer:** `CREATE VIEW` is the standard way to define a view; PostgreSQL creates and uses the `_RETURN` rule under the hood for view expansion.

### Exercise 4. Do Views Store Data Separately?

**Answer:** Regular views do not materialize rows. They evaluate the query definition against underlying base tables.

### Exercise 5. Inspecting a View Definition

```sql
SELECT pg_get_viewdef(
    'rule375.active_products'::regclass,
    true
);
```

**Answer:** Use `pg_get_viewdef`.

### Exercise 6. Inspecting Raw Rewrite Metadata

**Answer:** Query `pg_rewrite`, join `pg_class` and `pg_namespace`, and call `pg_get_ruledef(r.oid, true)`.

### Exercise 7. Does `DO ALSO` Keep the Original Command?

**Answer:** Yes, and appends the rule action according to rewrite semantics.

### Exercise 8. Does `DO INSTEAD` Keep the Original Command?

**Answer:** No; it replaces the original action according to rule semantics.

### Exercise 9. What Is `DO INSTEAD NOTHING`?

**Answer:** It replaces the original command within the rule's scope with no action at all.

### Exercise 10. Does `DELETE` on `protected_notes` Remove Rows?

```sql
DELETE FROM rule375.protected_notes
WHERE note_id = 1;
```

**Answer:** While `protected_notes_no_delete` is active, the `DELETE` is rewritten into nothing, so no deletion occurs.

### Exercise 11. Does a `DELETE` Rule Block `TRUNCATE`?

**Answer:** No. `TRUNCATE` is a distinct event and does not invoke `ON DELETE` rewrite rules.

### Exercise 12. Does `COPY FROM` Fire `INSERT` Rules?

**Answer:** No. `COPY FROM` bypasses query rewrite rules; rely on constraints and triggers instead.

### Exercise 13. Are Rule `OLD`/`NEW` PL/pgSQL Records?

**Answer:** No. They are pseudo-relations within the query rewrite system.

### Exercise 14. What Are `OLD`/`NEW` Used for in an `AFTER ROW` Trigger?

**Answer:** Reading fields from the old/new row records in a row-level trigger context — for example, recording change history.

### Exercise 15. Does Multi-Row `INSERT` Run a Rule Once per Row Like a Trigger?

**Answer:** No; rules operate at the query level.

### Exercise 16. What Should Be Preferred for Accurate Row-Change Auditing?

**Answer:** An `AFTER ROW` trigger or proper CDC/audit mechanism rather than a `DO ALSO` rule.

### Exercise 17. Why Shouldn't `CREATE RULE` Send HTTP Requests?

**Answer:** Rules lack commit-aware delivery, rollback safety, retries, deduplication, and ordering guarantees. Use an outbox and worker instead.

### Exercise 18. Can Simple Views Be Updated Directly?

**Answer:** Yes, when they satisfy PostgreSQL's requirements for automatically updatable views.

### Exercise 19. When Is `WITH CHECK OPTION` Used?

**Answer:** On eligible updatable views, to reject inserts/updates through the view that would produce rows outside the view's predicate.

### Exercise 20. Writing Per-Row Logic for Complex View `INSERT`s?

**Answer:** Prefer an `INSTEAD OF` trigger or an explicit API/function rather than crafting custom DML rules.

### Exercise 21. Does `ON INSERT DO INSTEAD` Redirect Automatically Support `RETURNING` from the Destination Table?

**Answer:** Not automatically. `RETURNING` support must be explicitly designed within rule limits or handled via triggers/APIs.

### Exercise 22. Why Avoid DML Rules on Tables Using `ON CONFLICT`?

**Answer:** PostgreSQL restricts `ON CONFLICT` when `INSERT`/`UPDATE` rules exist because rewrite actions conflict with upsert semantics. Use plain unique constraints and triggers instead.

### Exercise 23. Why Is `CHECK (unit_price >= 0)` Better Than a Rule?

**Answer:** A `CHECK` constraint enforces a data invariant consistently across all `INSERT`/`UPDATE` paths without relying on query rewrites.

### Exercise 24. How Do You Prevent Duplicate `external_id` Values?

**Answer:** Use `PRIMARY KEY` / `UNIQUE`, never a racy rule checking existence before inserting.

### Exercise 25. How Do You Stop Tenant 7 from Reading Tenant 8's Rows?

**Answer:** Proper privileges and RLS tied to trusted authentication context; rules are not a security substitute.

### Exercise 26. Can `EXPLAIN` on a View Query Show the Underlying Base Table?

**Answer:** Yes. Because view expansion happens before planning, the plan typically scans/joins the base tables.

### Exercise 27. Why Doesn't a `Seq Scan` Prove a View Is Slow?

**Answer:** The planner chooses plans by cost; on small tables, a sequential scan is cheaper than an index scan.

### Exercise 28. Does a Materialized View Update Immediately After Base-Table `INSERT`?

**Answer:** No. It requires an explicit `REFRESH MATERIALIZED VIEW`.

### Exercise 29. Does a `DO ALSO` Log Rule Guarantee Broker Delivery After Commit?

**Answer:** No. You need an outbox/CDC pipeline and a retry-capable worker.

### Exercise 30. Should an `UPDATE` Rule Block Steep per-Row Price Drops?

**Answer:** No; a `BEFORE ROW` trigger comparing `OLD` and `NEW` and raising an exception has far clearer semantics.

### Exercise 31. Is `WHERE` in `CREATE RULE` Equivalent to a Row Trigger's `WHERE`/Filter?

**Answer:** No. It operates under query rewrite semantics.

### Exercise 32. What Is the Risk of a Rule Inserting Back into Its Own Target Table?

**Answer:** Recursive rewriting / infinite expansion errors; replace with proper SQL, triggers, or procedures.

### Exercise 33. Should Multiple `DO ALSO` Rules Be Chained Like an Ordered Pipeline?

**Answer:** No, whenever strict per-row sequencing is required. Use transactions, functions, or triggers explicitly.

### Exercise 34. Can Rules Be Replaced in Production Without Checking Callers?

**Answer:** No. `CREATE OR REPLACE RULE` changes SQL semantics for existing callers; plan migrations, testing, and rollbacks carefully.

### Exercise 35. What Must `DROP RULE` Specify?

```sql
DROP RULE protected_notes_no_delete
ON rule375.protected_notes;
```

**Answer:** Both the rule name and the owning relation after `ON`.

### Exercise 36. How Do You Check Whether a Rule Is Enabled?

**Answer:** Query `pg_rewrite.ev_enabled` and account for session/replication role settings if relevant.

### Exercise 37. Why Might `security_barrier` Be Needed on a View?

**Answer:** To protect sensitive data in views against untrusted caller expressions / unsafe predicate pushdown, alongside grants, RLS, and threat-model analysis.

### Exercise 38. What Effect Does `security_invoker` Have?

**Answer:** On supporting versions, it causes underlying relation privileges to be checked under the invoking user rather than the view owner. Verify exact version and grants.

### Exercise 39. Does a Trigger Outbox Guarantee Exactly-Once External Delivery?

**Answer:** Not by itself. It guarantees atomic persistence inside the DB transaction; consumers still need retries, idempotency, and duplicate/out-of-order handling.

### Exercise 40. When Is Choosing a Rewrite Rule Justified?

**Answer:** Only when the problem genuinely requires **rewrite-level query transformation**, all limitations are understood, and every DML path is thoroughly tested — rather than row-level validation/auditing better served by triggers or constraints.

## 52. Summary

**PostgreSQL rules are a query-rewriting mechanism, not another name for triggers.**

Core picture:

```text
Incoming SQL
    |
    v
Parse + Analyze
    |
    v
Rewrite rules
    |
    +-- _RETURN expands views
    +-- DO ALSO appends actions
    +-- DO INSTEAD replaces actions
    +-- DO INSTEAD NOTHING drops actions
    |
    v
Planner
    |
    v
Executor
```

Principles to remember:

1. **`CREATE RULE` operates at the rewrite layer**, not as a per-row callback.
2. **Views are the primary use of the `_RETURN` `SELECT` rule**; use `CREATE VIEW` to create views.
3. **`DO ALSO` keeps the original action and adds another**; `DO INSTEAD` replaces it; `DO INSTEAD NOTHING` suppresses it within rule scope.
4. **`OLD`/`NEW` in rules are query-rewrite pseudo-relations**, distinct from trigger row records.
5. **DML rules have sharp limits** with multi-row statements, volatile expressions, `RETURNING`, `ON CONFLICT`, and similar features.
6. **`COPY FROM` does not fire `INSERT` rules like normal `INSERT` statements**, and `TRUNCATE` does not fire `DELETE` rules.
7. **Constraints protect data integrity**, **triggers handle row/statement events**, and **RLS enforces access** — never substitute `DO INSTEAD NOTHING`.
8. **Exact auditing and outbox publishing** belong in mechanisms with proper row/transaction semantics, not `DO ALSO` rules.
9. **Automatically updatable views and `INSTEAD OF` triggers** are far easier to reason about than custom DML rules on views.
10. **Rules do not inherently accelerate queries**; measure post-rewrite plans and the cost of all generated actions.
11. **Inspect rules via `pg_rewrite`/`pg_get_ruledef`**, checking server version and enabled state.
12. **Rule migrations are SQL behavior migrations**: they can alter outcomes for every caller even when application SQL stays untouched.

### One Sentence to Remember

> **A rule changes the statement PostgreSQL will execute; a trigger reacts to the operation PostgreSQL is executing.** Use **views** for logical read projections, **constraints/RLS** for invariants and access control, **triggers** for row-level behavior, and **query rewrite rules** only when query rewriting is truly the layer you need.
