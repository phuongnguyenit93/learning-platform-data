# Simulating Concurrent Ordering and Protecting Inventory Stock in PostgreSQL

A sales system can receive multiple purchase requests for the same product at the exact same moment. If two transactions both read the inventory count before updating it, both may believe stock is sufficient and confirm their orders. The result is overselling beyond actual stock, negative inventory, or an order state that mismatches the reserved quantity.

This is a database-level concurrency problem. Checking inventory in the application before sending an `INSERT` is insufficient, because another transaction can modify the data between the read and the write. PostgreSQL must execute the check and update as a single atomic operation, or lock the appropriate rows for the duration of the transaction.

The lesson **"Simulating Concurrent Ordering and Protecting Inventory Stock in PostgreSQL"**, part of the **End-to-End Practice** chapter of the **Database Engine Relational PostgreSQL** module, builds a small sales model and practices:

- Reproducing the race condition when two customers simultaneously purchase quantities close to available stock.
- Distinguishing between lost updates and overselling.
- Using conditional `UPDATE`s and `CHECK` constraints to protect invariants.
- Using `SELECT FOR UPDATE` to lock inventory when processing multi-product orders.
- Designing all-or-nothing transactions, idempotency, and a reservation lifecycle.
- Understanding `READ COMMITTED`, `REPEATABLE READ`, `SERIALIZABLE`, deadlocks, and retries.
- Simulating concurrency with multiple `psql` sessions, inspecting locks, and verifying final outcomes.

> **Principle:** inventory condition checks and stock modifications must be coordinated on the database side within the same transaction. The application must never make decisions based on a previously read value and overwrite newer state.

## 2. The Problem and Invariants

Suppose a store manages products and stock per warehouse.

We need to uphold the following invariants:

- Physical on-hand quantity is non-negative.
- Reserved quantity is non-negative.
- Reserved quantity never exceeds on-hand quantity.
- An order is confirmed only if all line items can be fulfilled.
- A retried request never creates a duplicate order or deducts stock a second time.
- Every inventory change is explainable and reconcilable.

In a simple model without reservations, the primary invariant is:

\[
available \geq 0
\]

When separating physical on-hand stock and reserved stock:

\[
available = on\_hand - reserved
\]

and:

\[
0 \leq reserved \leq on\_hand
\]

Invariants must be enforced by database constraints and transactional logic, not solely by application-layer validation.

## 3. Data Model

The practice model consists of:

- `products`: product catalog.
- `inventory`: stock counts per warehouse and product.
- `orders`: orders and idempotency keys.
- `order_items`: product line items within an order.
- `inventory_reservations`: stock held for an order, when using a reservation workflow.
- `inventory_movements`: audit history of inventory changes.

An order can contain multiple products; the same product can be stocked across multiple warehouses.

## 4. Creating the Lab Schema

Create the schema and tables:

~~~sql
CREATE SCHEMA IF NOT EXISTS shop;

CREATE TABLE shop.products (
    product_id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    sku text NOT NULL UNIQUE,
    product_name text NOT NULL,
    active boolean NOT NULL DEFAULT true
);

CREATE TABLE shop.inventory (
    warehouse_id bigint NOT NULL,
    product_id bigint NOT NULL
        REFERENCES shop.products(product_id),
    on_hand integer NOT NULL,
    reserved integer NOT NULL DEFAULT 0,
    updated_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (warehouse_id, product_id),
    CONSTRAINT inventory_nonnegative
        CHECK (on_hand >= 0 AND reserved >= 0),
    CONSTRAINT inventory_reserved_within_on_hand
        CHECK (reserved <= on_hand)
);

CREATE TABLE shop.orders (
    order_id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    idempotency_key text NOT NULL UNIQUE,
    status text NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT orders_status_valid
        CHECK (status IN (
            'pending', 'reserved', 'confirmed',
            'cancelled', 'rejected'
        ))
);

CREATE TABLE shop.order_items (
    order_id bigint NOT NULL REFERENCES shop.orders(order_id),
    product_id bigint NOT NULL REFERENCES shop.products(product_id),
    quantity integer NOT NULL CHECK (quantity > 0),
    unit_price numeric(12, 2) NOT NULL CHECK (unit_price >= 0),
    PRIMARY KEY (order_id, product_id)
);
~~~

The primary key of `inventory` is the `(warehouse_id, product_id)` pair. This allows a product to have distinct stock counts across different warehouses.

## 7. Why Application-Level Inventory Checks Are Insufficient

A naive flow typically does:

1. `SELECT available`.
2. Application checks whether `available` is sufficient.
3. If sufficient, application `INSERT`s the order.
4. Application `UPDATE`s `inventory`.

Between step 1 and step 4, another transaction can modify the same row.

For example, both customers read `available = 5`. Each wants to buy 4. Both see `4 <= 5` and proceed.

This is a race condition: the outcome depends on how transactions interleave.

Open two independent terminals and connect to the same database:

~~~

## 9. Experiment A: Two Sessions Reading Inventory Simultaneously

In Session A:

~~~sql
BEGIN;

SELECT on_hand - reserved AS available
FROM shop.inventory
WHERE warehouse_id = 10
  AND product_id = 1;
~~~

In Session B, before A updates:

~~~sql
BEGIN;

SELECT on_hand - reserved AS available
FROM shop.inventory
WHERE warehouse_id = 10
  AND product_id = 1;
~~~

Both sessions can read the value 5 because a plain `SELECT` does not lock the row to prevent another transaction from updating it.

This is the starting point of a race condition.

## 10. Experiment B: Overwriting with Stale Values

Suppose the application reads `available = 5` and calculates the new balance as 1 on the client side.

In Session A:

~~~sql
UPDATE shop.inventory
SET on_hand = 1,
    updated_at = now()
WHERE warehouse_id = 10
  AND product_id = 1;
~~~

In Session B, the application also uses the previously read value:

~~~sql
UPDATE shop.inventory
SET on_hand = 1,
    updated_at = now()
WHERE warehouse_id = 10
  AND product_id = 1;
~~~

After both transactions commit, `on_hand` ends up as 1 even though two orders were accepted for a combined quantity sold of 8.

This is a lost update: the later transaction writes a value computed from a stale snapshot and erases the logical effect of the earlier transaction.

In the lab, roll back and reload the baseline before the next experiment.

## 11. Distinguishing Lost Updates from Overselling

These two issues are related but not identical:

- **Lost update:** an update computed from an old value overwrites the result of another update.
- **Overselling:** the system accepts a total sold quantity greater than the supply available.

For instance, if two transactions both subtract 4 from 5 using separate read-then-write expressions, they can write 1 instead of -3. The database shows 1, yet the system confirmed sales totaling 8.

If you use atomic subtraction without a constraint, the result can become -3. With a `CHECK` constraint, an update driving stock negative is rejected. You need both the right update pattern and database invariants.

## 12. Atomic Conditional Subtraction

A simple and effective approach combines the check and the update in a single statement:

~~~sql
UPDATE shop.inventory
SET on_hand = on_hand - 4,
    updated_at = now()
WHERE warehouse_id = 10
  AND product_id = 1
  AND on_hand - reserved >= 4
RETURNING on_hand, reserved;
~~~

Outcomes:

- One row returned: stock was successfully deducted.
- Zero rows returned: either the inventory row is missing or available stock is insufficient.

The application does not need to read the count beforehand and compute the new balance. Both the condition and subtraction are executed by PostgreSQL on the updated row.

## 13. Why Conditional `UPDATE` Is Safe Under `READ COMMITTED`

When two transactions concurrently `UPDATE` the same row, PostgreSQL uses a row-level lock to serialize modifications to that row.

If the second transaction has to wait for the first transaction, PostgreSQL re-evaluates the `WHERE` predicate against the latest committed row version under `READ COMMITTED` semantics before updating.

Thus, if A subtracts 4 from 5 and commits, B re-evaluates `available >= 4`. Since only 1 remains, B does not update the row.

The critical point is that the predicate must live inside the `UPDATE` itself, not merely in an earlier `SELECT`.

## 16. `CHECK` Constraints as the Last Line of Defense

The `inventory` table already has:

~~~sql
CHECK (on_hand >= 0 AND reserved >= 0)
~~~

and:

~~~sql
CHECK (reserved <= on_hand)
~~~

If buggy code attempts to write negative `on_hand` or `reserved` greater than `on_hand`, PostgreSQL rejects the statement.

A constraint does not replace insufficient-stock business handling. It protects data integrity if another code path forgets the condition.

Never catch a constraint violation and still confirm the order. If the inventory update fails, the order-creation transaction must roll back.

## 17. Encapsulating Stock Deduction in a Function

You can create a function so all callers follow the exact same rule:

~~~sql
CREATE OR REPLACE FUNCTION shop.take_stock(
    p_warehouse_id bigint,
    p_product_id bigint,
    p_quantity integer
)
RETURNS integer
LANGUAGE plpgsql
AS $$
DECLARE
    v_on_hand integer;
BEGIN
    IF p_quantity <= 0 THEN
        RAISE EXCEPTION 'quantity must be positive';
    END IF;

    UPDATE shop.inventory
    SET on_hand = on_hand - p_quantity,
        updated_at = now()
    WHERE warehouse_id = p_warehouse_id
      AND product_id = p_product_id
      AND on_hand - reserved >= p_quantity
    RETURNING on_hand INTO v_on_hand;

    IF NOT FOUND THEN
        RAISE EXCEPTION USING
            ERRCODE = 'P0001',
            MESSAGE = 'insufficient stock or inventory row missing';
    END IF;

    RETURN v_on_hand;
END;
$$;
~~~

This function raises an exception when stock is insufficient. The caller must handle transaction failure and avoid creating a successful order.

The function runs inside the caller's transaction; it does not commit the transaction itself.

## 18. Creating the Order and Deducting Stock in the Same Transaction

Never commit stock deduction first and create the order in a separate transaction. If inserting the order fails after the first transaction committed the stock deduction, inventory is missing without any corresponding order.

A simple flow:

~~~sql
BEGIN;

SELECT shop.take_stock(10, 1, 2);

INSERT INTO shop.orders (idempotency_key, status)
VALUES ('checkout-2025-0001', 'confirmed')
RETURNING order_id;

-- Insert order_items using the returned order_id.

COMMIT;
~~~

In the application, capture `order_id` and insert `order_items` within the same transaction. If any step fails, roll back both the order and the inventory change.

## 19. Ensuring Valid Quantities

Never accept quantities of 0 or negative numbers.

Validate at two layers:

- Application validation to return clear errors early.
- Database `CHECK` constraints/function validation to protect all code paths.

Example constraint:

~~~sql
ALTER TABLE shop.order_items
ADD CONSTRAINT order_items_quantity_positive
CHECK (quantity > 0);
~~~

Do not use negative quantities to represent returns. Returns/refunds should be a distinct workflow with explicit movement types and audit records.

## 20. Multi-Product Orders

An order can include multiple line items:

| Product | Requested quantity |
|---|---:|
| Coffee | 2 |
| Tea | 3 |
| Mug | 1 |

All-or-nothing requirement: either every line is reserved/deducted, or no inventory changes at all.

If you process line by line and commit after each line, an order could end up only partially deducted. All operations must reside inside a single transaction.

## 21. Consolidating Duplicate Product Lines

A request might include the same product multiple times. For example, Coffee appears on two lines with quantities 2 and 3.

Before locking or updating inventory, aggregate them into a single Coffee line with quantity 5. Otherwise, the same transaction may touch the same inventory row multiple times in an unpredictable order.

Example request staging table:

~~~sql
CREATE TEMP TABLE requested_items (
    product_id bigint NOT NULL,
    quantity bigint NOT NULL CHECK (quantity > 0)
) ON COMMIT DROP;

INSERT INTO requested_items (product_id, quantity)
VALUES (1, 2), (2, 3), (1, 3);
~~~

Total requested is 5 Coffee and 3 Tea.

## 22. Locking Multiple Inventory Rows in a Consistent Order

When a transaction touches multiple products, other transactions might lock the same rows in a different order and trigger deadlocks.

Lock in ascending `product_id` order:

~~~sql
WITH requested AS (
    SELECT product_id, sum(quantity) AS required_qty
    FROM requested_items
    GROUP BY product_id
)
SELECT
    i.product_id,
    i.on_hand,
    i.reserved,
    r.required_qty
FROM shop.inventory AS i
JOIN requested AS r USING (product_id)
WHERE i.warehouse_id = 10
ORDER BY i.product_id
FOR UPDATE OF i;
~~~

The rows remain locked until the transaction ends. The application must verify that the number of rows returned matches the count of distinct requested product IDs and that `available` on each row is sufficient.

If an inventory row is missing or any product lacks sufficient stock, roll back the transaction before creating the order.

## 23. Why Does Lock Ordering Matter?

Suppose transaction A needs product 1 then product 2, while transaction B needs product 2 then product 1.

- A locks product 1.
- B locks product 2.
- A waits for product 2.
- B waits for product 1.

The two transactions wait on each other, forming a deadlock. PostgreSQL detects this and aborts one transaction.

If all code paths lock in the same ascending `product_id` order, this circular-wait scenario is significantly reduced.

Apply consistent ordering across inventory rows, account rows, and any other resources a transaction may lock.

## 24. Updating Multiple Products After Locking

Once all rows are locked and verified, you can update inventory:

~~~sql
WITH requested AS (
    SELECT product_id, sum(quantity) AS required_qty
    FROM requested_items
    GROUP BY product_id
)
UPDATE shop.inventory AS i
SET on_hand = i.on_hand - r.required_qty::integer,
    updated_at = now()
FROM requested AS r
WHERE i.warehouse_id = 10
  AND i.product_id = r.product_id
  AND i.on_hand - i.reserved >= r.required_qty
RETURNING i.product_id, i.on_hand;
~~~

The application must verify that the count of updated rows equals the count of distinct product IDs. If they do not match, roll back the entire transaction.

Because the rows were previously locked and checked, the transaction retains control until commit. Never ignore the `RETURNING` result.

## 25. Creating the Order After Verifying Inventory

Sequence inside a single transaction:

1. Receive request and validate quantities.
2. Aggregate duplicate product lines.
3. Lock inventory rows in a consistent order.
4. Verify every product exists and has sufficient `available` stock.
5. Update inventory.
6. Create the order.
7. Create `order_items`.
8. Write inventory movement/audit rows.
9. Commit.

If any step fails, roll back everything. Never send emails, call payment providers, or trigger external side effects before the transaction commits; use the outbox pattern for post-commit work.

## 26. Idempotency on Client Retries

A client may send a request, the server processes it successfully, and the response is lost. The client retries and submits the same order again.

If treated as a fresh request, the system could create a second order and deduct stock a second time.

Use a unique idempotency key for each checkout intent:

~~~sql
CREATE UNIQUE INDEX orders_idempotency_key_uq
ON shop.orders (idempotency_key);
~~~

The `orders` table in this lab already has the corresponding `UNIQUE` constraint. The same key must return the outcome of the processed operation without re-running side effects.

## 27. Handling Idempotency Keys Inside a Transaction

One pattern:

1. Attempt to insert the order with the idempotency key.
2. If the insert succeeds, this transaction owns the request and proceeds to reserve stock.
3. If the key already exists, read the existing order and return its stored state.
4. Never deduct stock again for an already-processed request.
5. If processing fails, roll back both the idempotency record and inventory changes, or store an explicit failure state per policy.

Example:

~~~sql
INSERT INTO shop.orders (idempotency_key, status)
VALUES ('checkout-2025-0002', 'pending')
ON CONFLICT (idempotency_key) DO NOTHING
RETURNING order_id;
~~~

If no row is returned, the application must fetch the existing order and determine the response based on `status`. Do not continue creating `order_items` or deducting stock as if it were a new request.

## 28. Reservations vs. Immediate Deduction

Many systems prefer not to decrement `on_hand` immediately at checkout. Instead, they hold stock for a window while awaiting payment.

In this model:

- `on_hand`: physical quantity in the warehouse.
- `reserved`: quantity held for incomplete orders.
- `available = on_hand - reserved`.

When creating a reservation, increment `reserved`. When payment succeeds, decrement both `on_hand` and `reserved`. When an order expires or is cancelled, decrement only `reserved`.

## 29. Creating the `reservations` Table

~~~sql
CREATE TABLE shop.inventory_reservations (
    reservation_id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id bigint NOT NULL REFERENCES shop.orders(order_id),
    warehouse_id bigint NOT NULL,
    product_id bigint NOT NULL,
    quantity integer NOT NULL CHECK (quantity > 0),
    status text NOT NULL
        CHECK (status IN ('reserved', 'consumed', 'released', 'expired')),
    expires_at timestamptz NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now(),
    FOREIGN KEY (warehouse_id, product_id)
        REFERENCES shop.inventory(warehouse_id, product_id),
    UNIQUE (order_id, warehouse_id, product_id)
);
~~~

The unique constraint prevents the same order from creating multiple reservations for the same product in the same warehouse.

## 30. Creating Reservations Atomically

~~~sql
UPDATE shop.inventory
SET reserved = reserved + 2,
    updated_at = now()
WHERE warehouse_id = 10
  AND product_id = 1
  AND on_hand - reserved >= 2
RETURNING on_hand, reserved;
~~~

If one row is returned, create the reservation record in the same transaction.

If no row is returned, stock is insufficient. Roll back the order/reservation transaction.

The `CHECK` constraint `reserved <= on_hand` provides an additional safety layer.

## 31. Confirming Reservations After Payment

When the payment provider confirms success, transition the reservation to `consumed` and decrement physical stock.

Within the same transaction:

1. Lock the reservation row.
2. Transition `status` strictly from `reserved` to `consumed`.
3. Decrement both `on_hand` and `reserved` by the same quantity.
4. Record the inventory movement.
5. Update order `status` to `confirmed`.
6. Commit.

Example inventory update:

~~~sql
UPDATE shop.inventory
SET on_hand = on_hand - 2,
    reserved = reserved - 2,
    updated_at = now()
WHERE warehouse_id = 10
  AND product_id = 1
  AND on_hand >= 2
  AND reserved >= 2;
~~~

Execute this only after the transaction has verified and transitioned the reservation state. If the reservation was already `consumed`, retries must not deduct stock again.

## 32. Releasing Reservations on Cancellation

When a customer cancels or payment fails:

~~~sql
UPDATE shop.inventory
SET reserved = reserved - 2,
    updated_at = now()
WHERE warehouse_id = 10
  AND product_id = 1
  AND reserved >= 2;
~~~

In practice, do not rely solely on quantity checks. First lock the reservation row and transition status from `reserved` to `released`/`expired` exactly once. Only the transaction that wins the status transition may decrement `reserved`.

This prevents two workers from simultaneously releasing the same reservation and decrementing `reserved` twice.

## 33. Expiring Reservations

A worker can find expired reservations:

~~~sql
SELECT reservation_id
FROM shop.inventory_reservations
WHERE status = 'reserved'
  AND expires_at <= now()
ORDER BY expires_at, reservation_id
FOR UPDATE SKIP LOCKED
LIMIT 100;
~~~

`SKIP LOCKED` allows multiple workers to process distinct rows without blocking on each other over the same reservation.

Inside a transaction, the worker locks a batch, transitions status to `expired`, decrements `reserved` accordingly, and commits. If processing fails, it rolls back so another worker can retry.

## 34. Do Not Hold Row Locks While Calling Payment Providers

Calling an external payment service can take several seconds or time out. Never hold database transactions and row locks open across network calls.

A better flow:

1. A short transaction creates the order and reservation.
2. Commit.
3. A worker calls the payment provider.
4. A separate transaction confirms or releases the reservation based on the result.
5. Timeouts and retries are handled via state transitions and idempotency.

Use an outbox to write outbound events in the same transaction as the order/reservation; a worker reads the outbox after commit.

## 35. State Machine for Orders

Define valid state transitions:

~~~text
pending
   |
   v
reserved
   |
   +------> confirmed
   |
   +------> cancelled
   |
   +------> expired
~~~

Do not permit arbitrary state transitions. For example, `confirmed` must never transition back to `pending` just because a client retried.

Use a conditional `UPDATE` matching the expected current status:

~~~sql
UPDATE shop.orders
SET status = 'confirmed'
WHERE order_id = 100
  AND status = 'reserved'
RETURNING order_id;
~~~

If no row is returned, the status has already changed or the order does not exist. The application must re-read the record and handle it idempotently.

## 36. `READ COMMITTED`

`READ COMMITTED` is PostgreSQL's default isolation level.

Each statement sees a fresh snapshot taken at the start of that statement. A transaction can see newly committed changes in subsequent statements.

A conditional `UPDATE` on a single inventory row is usually a simple and sufficient way to protect stock deductions under `READ COMMITTED`.

Never replace it with a `SELECT` followed by application logic, as subsequent statements may operate on changed state.

## 37. `REPEATABLE READ`

`REPEATABLE READ` holds a consistent snapshot throughout the transaction. If a transaction attempts to update a row already modified by another transaction after its snapshot started, PostgreSQL can abort it with a serialization failure.

The application must retry the entire transaction when encountering SQLSTATE `40001` if the operation is safe to retry.

Never retry only the final statement, because earlier decisions were based on the stale snapshot.

## 38. `SERIALIZABLE`

`SERIALIZABLE` requires transactions to behave as if executed in some serial order. PostgreSQL uses Serializable Snapshot Isolation to detect dependency patterns that could produce anomalies.

A transaction can be aborted with a serialization failure even when no deadlock exists.

Use `SERIALIZABLE` when business invariants span multiple rows or predicates that are hard to protect with explicit locks or atomic updates. Always implement a retry loop and monitor abort rates.

## 39. Retrying Serialization Failures

Key SQLSTATE codes:

| SQLSTATE | Meaning | Handling |
|---|---|---|
| `40001` | `serialization_failure` | Retry entire transaction |
| `40P01` | `deadlock_detected` | Retry entire transaction if operation is idempotent |
| `55P03` | `lock_not_available` | Consider retry/backoff or return busy |
| `23514` | `check_violation` | Invariant/validation error; do not blindly retry |
| `23505` | `unique_violation` | Handle duplicate/idempotency per constraint |

Retries must have a bounded attempt limit, exponential backoff with jitter, and a correlation ID in logs. Never retry indefinitely.

## 40. What Is a Deadlock?

A deadlock occurs when transactions hold locks that other transactions need, forming a wait cycle.

Example:

~~~text
Transaction A                Transaction B
-------------                -------------
Lock inventory row 1         Lock inventory row 2
Wait for row 2               Wait for row 1
       |                            |
       +---------- cycle -----------+
~~~

PostgreSQL detects the deadlock and aborts one transaction to break the cycle.

## 41. Preventing Deadlocks

- Lock rows in a consistent order.
- Keep transactions short.
- Never make network calls while holding locks.
- Avoid locking extra rows unnecessarily.
- Use appropriate indexes to narrow scan and lock scope.
- Use the exact same lock order across all code paths.
- Handle deadlocks with full-transaction retries when safe.

Lock order must be consistent across checkout, cancellation, payment confirmation, and inventory adjustment.

## 42. Lock Timeout and Statement Timeout

You can bound lock wait times inside a transaction:

~~~sql
SET LOCAL lock_timeout = '2s';
SET LOCAL statement_timeout = '10s';
~~~

`SET LOCAL` applies only to the current transaction.

`lock_timeout` prevents requests from waiting indefinitely on locks. `statement_timeout` bounds statement execution duration. Choose values based on your latency budget and workload rather than copying a single number across all systems.

Upon timeout, the transaction must generally roll back before returning the connection to the pool.

## 43. Optimistic Locking with a Version Column

If contention is rare and the application needs to detect stale reads, you can add a `version` column:

~~~sql
ALTER TABLE shop.inventory
ADD COLUMN version bigint NOT NULL DEFAULT 0;
~~~

Update:

~~~sql
UPDATE shop.inventory
SET on_hand = on_hand - 1,
    version = version + 1,
    updated_at = now()
WHERE warehouse_id = 10
  AND product_id = 1
  AND version = 7
  AND on_hand - reserved >= 1
RETURNING version, on_hand;
~~~

If no row is returned, either the version changed or stock is insufficient. The application re-reads and decides whether to retry or return a conflict.

Optimistic locking does not replace `CHECK` constraints.

## 44. Advisory Locks

PostgreSQL provides transaction-level advisory locks to serialize a logical resource that does not map directly to a table row.

Example:

~~~sql
SELECT pg_advisory_xact_lock(9001, 10);
~~~

The lock is held until the end of the transaction.

Advisory locks are helpful when serializing a workflow by a business key, but every related code path must obey the same lock protocol. They do not protect inventory if another code path skips the advisory lock.

Prefer row locks and constraints whenever a resource has a clear row representation.

## 45. Queue Workers and `SKIP LOCKED`

When multiple workers process orders or reservations, they can claim work using `SKIP LOCKED`:

~~~sql
WITH next_jobs AS (
    SELECT order_id
    FROM shop.orders
    WHERE status = 'pending'
    ORDER BY created_at, order_id
    FOR UPDATE SKIP LOCKED
    LIMIT 20
)
UPDATE shop.orders AS o
SET status = 'reserved'
FROM next_jobs AS j
WHERE o.order_id = j.order_id
RETURNING o.order_id;
~~~


Each worker receives a disjoint set of rows. `SKIP LOCKED` works well for queue-like processing, though it does not guarantee strict fairness; a row that happens to be repeatedly locked could be delayed.

## 46. Inventory Movement Ledger

Storing only the current balance makes investigating discrepancies difficult. You can record every change in a movement ledger:

~~~sql
CREATE TABLE shop.inventory_movements (
    movement_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    warehouse_id bigint NOT NULL,
    product_id bigint NOT NULL,
    order_id bigint,
    movement_type text NOT NULL,
    quantity_delta integer NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now(),
    reference_key text
);
~~~

Example movement types: `receipt`, `reservation`, `release`, `sale`, `return`, `adjustment`.

Write movement rows in the same transaction as the inventory update. Never write ledger entries post-commit via a separate request that could fail independently.

## 47. Reconciling Inventory and the Ledger

You can check for negative balances or reservations exceeding `on_hand`:

~~~sql
SELECT
    warehouse_id,
    product_id,
    on_hand,
    reserved
FROM shop.inventory
WHERE on_hand < 0
   OR reserved < 0
   OR reserved > on_hand;
~~~

Movement reconciliation requires an opening balance and clear rules specifying which movement types affect `on_hand` or `reserved`. A ledger is not automatically accurate if application code writes incorrect entries; reconciliation jobs and an audit trail are still required.

## 48. Multi-Warehouse Inventory

A product may be stocked in multiple warehouses. Checkout must select a warehouse according to business rules:

- Warehouse closest to the shipping address.
- Warehouse able to fulfill the entire quantity.
- Warehouse with the lowest shipping cost.
- Prefer a single warehouse to avoid split shipments.

When an order draws from multiple warehouses, the transaction must lock inventory rows in a global order—for instance, `warehouse_id` then `product_id`—to minimize deadlocks.

Do not sort only by `product_id` if the same product spans multiple warehouses.

## 49. Backorder and Overselling Policy

Not every system prohibits selling beyond available stock. Some businesses support backorders or preorders.

If backorders are allowed, model states explicitly:

- Available stock.
- Reserved stock.
- Backordered quantity.
- Expected replenishment date.

Do not use negative numbers to implicitly represent backorders if your inventory invariant requires non-negative values. Separate customer promises from physical stock counts.

## 50. Handling Cancellations and Refunds

Cancelling an order requires verifying state transitions and inventory movements.

- If the order is only `reserved`, release the reservation.
- If the order is `confirmed` and not yet shipped, restock per policy.
- If goods have already shipped, a return/receipt workflow must record stock only when physical goods arrive back at the warehouse.
- Payment refunds are a separate workflow with their own idempotency key.

Never automatically add stock back simply because a payment refund succeeded; the physical items may not have returned to the warehouse yet.

## 51. Verifying with Multiple Sessions

After each experiment, query:

SELECT
    i.warehouse_id,
    p.sku,
    i.on_hand,
    i.reserved,
    i.on_hand - i.reserved AS available
FROM shop.inventory AS i

Check order counts, `order_items`, and reservation statuses:

ORDER BY status;

Do not rely solely on application responses. Database state is the ultimate proof of transaction outcomes.

## 52. Observing Lock Waits

View sessions waiting on locks:

~~~sql
SELECT
    pid,
    usename,
    state,
    wait_event_type,
    wait_event,
    now() - query_start AS query_age,
    left(query, 160) AS query_text
FROM pg_stat_activity
WHERE wait_event_type = 'Lock'
ORDER BY query_start;
~~~

View locks and sessions:

~~~sql
SELECT
    a.pid,
    a.application_name,
    a.state,
    l.locktype,
    l.mode,
    l.granted,
    l.relation::regclass AS relation_name
FROM pg_locks AS l
JOIN pg_stat_activity AS a USING (pid)
ORDER BY a.pid, l.granted;
~~~

These views help identify blocking sessions. To find direct blockers, use `pg_blocking_pids(pid)`.

## 53. Finding Blocking Relationships

~~~sql
SELECT
    blocked.pid AS blocked_pid,
    blocker.pid AS blocker_pid,
    blocked.query AS blocked_query,
    blocker.query AS blocker_query
FROM pg_stat_activity AS blocked
JOIN LATERAL unnest(pg_blocking_pids(blocked.pid)) AS b(pid)
  ON true
JOIN pg_stat_activity AS blocker
  ON blocker.pid = b.pid;
~~~

Appropriate privileges are required to view session details. In production, protect query text as it may contain sensitive data.

## 54. Periodic Invariant Checks

An anomaly-detection query:

~~~sql
SELECT *
FROM shop.inventory
WHERE on_hand < 0
   OR reserved < 0
   OR reserved > on_hand;
~~~

If `CHECK` constraints are always enabled and unbypassed, this query should return zero rows. It remains valuable for operational monitoring and post-migration/import verification.

You can add checks for reservations mismatched with order statuses, orders missing `order_items`, or duplicate external references.

## 56. Mandatory Test Cases

A concurrency test suite should cover:

2. Two buyers concurrently purchasing 2 from stock 5: both can succeed, leaving 1.

11. Transaction timeout: no partial order left behind.
12. Client loses response after commit and retries: returns existing result.
13. Two warehouses both holding stock: selects the right warehouse per policy.
14. Reservation expires at the same moment a payment callback arrives: only one state transition wins.

## 57. Common Pitfalls

### 57.1. `SELECT` Followed by `UPDATE` Using Application-Held Values

Creates stale writes and race conditions. Move the predicate into the `UPDATE` or lock the row before deciding.

### 57.2. Missing `CHECK` Constraints

Another code path could write negative stock. Use constraints to enforce invariants.

### 57.3. Committing Per Order Item

Can produce orders with only partial stock deducted. Process all lines inside one transaction.

### 57.4. Locking Rows in Inconsistent Orders

Increases deadlock risk. Use a consistent lock order across all code paths.

### 57.5. Omitting Idempotency Keys

Client retries can create duplicate orders and deduct stock a second time.

### 57.6. Holding Transactions Open While Calling Payment APIs

Causes long lock waits and connection exhaustion. Commit the reservation first, call external services outside the transaction, and finalize in a new transaction.

### 57.7. Retrying Every Error

Constraint violations and insufficient stock are not serialization failures. Only retry identified transient errors, and always retry the entire transaction.

### 57.8. Using `SKIP LOCKED` Without Monitoring Backlog

Some jobs may be starved or delayed. Monitor oldest pending age and implement retry/dead-letter policies.

### 57.9. Relying Solely on Application Cache

Caches can go stale. Final inventory decisions must be confirmed by a database transaction.

### 57.10. Not Reconciling the Movement Ledger

Inventory balances can drift due to code bugs or manual receiving/shipping discrepancies. Regular reconciliation is necessary.

## 61. Production Deployment Checklist

**Data and Invariants**

- Inventory is keyed by `(warehouse_id, product_id)`.
- Quantities are validated to be positive.
- `CHECK` constraints protect balances.
- A movement/audit trail exists.
- Reconciliation queries exist.

**Concurrency**

- Conditional `UPDATE`s or row locking are used for all stock changes.
- Multi-row locks follow a consistent order.
- Transactions are short.
- Appropriate lock/statement timeouts are configured.
- Deadlock and serialization retries are bounded.

**Order Workflow**

- Inventory and order changes share the same transaction.
- Multi-item orders are all-or-nothing.
- Idempotency keys have a unique constraint.
- Order state transitions are validated.
- Reservation consume/release runs at most once.
- External calls stay outside long-running transactions.

**Operations**

- Lock waits and hot rows are monitored.
- Insufficient stock is tracked separately from database failures.
- Retries and backoffs emit metrics.
- Load tests use representative data.
- Restore and reconciliation runbooks exist.
- Alerts do not leak sensitive data.

## 62. Frequently Asked Questions

### Why is an application `SELECT available` followed by `UPDATE` unsafe?

Because another transaction can modify inventory after the `SELECT` and before the `UPDATE`. The value held by the application may already be stale.

### Is an arithmetic `UPDATE` safe on its own?

Subtracting like `on_hand = on_hand - quantity` avoids overwriting an old value, but you still need a sufficient-stock predicate and `CHECK` constraints to prevent negative numbers.

### Why do we need both conditional `UPDATE` and `CHECK`?

Conditional `UPDATE` answers the business question of whether enough stock exists. `CHECK` serves as a final safety net against any code path writing an invariant-violating state.

### Is `READ COMMITTED` sufficient for ordering?

For a single inventory row, a conditional `UPDATE` is usually sufficient. Multi-row workflows require transactions and lock ordering; more complex invariants may require explicit locks or `SERIALIZABLE`.

### What does `SELECT FOR UPDATE` do?

It locks the selected rows so other transactions cannot update or delete them until the transaction ends.

### When should I use `SKIP LOCKED`?

When multiple workers claim jobs from a queue and can skip rows currently being processed by another worker.

### Does a deadlock mean data is corrupted?

Not necessarily. PostgreSQL aborts one transaction to break the cycle. The application should handle it and retry the full transaction when the operation is safe to retry.

### Should I retry on insufficient stock?

Do not immediately retry it like a database error. It is a business outcome; return an out-of-stock response or re-run per policy once stock is replenished.

### Why are idempotency keys necessary?

So that request retries after timeouts or lost responses do not create a second order or duplicate inventory movement.

### Should I keep a transaction open while calling a payment provider?

No. Network calls have unpredictable latency and failure modes. Commit the reservation first, call the provider outside the transaction, then finalize in a new transaction.

### When should I use reservations instead of deducting `on_hand` immediately?

When stock must be held while waiting for payment or order confirmation. Reservations require explicit expiration, consume, and release transitions.

### Can two orders purchase the remaining stock simultaneously?

Yes, if their combined quantity does not exceed `available`. Row locking serializes the updates; the conditional predicate determines which transactions qualify.

### Why lock `product_id` in ascending order?

So all transactions acquire locks in the same order, reducing the chance of deadlock cycles.

### Does `SERIALIZABLE` eliminate all business logic bugs?

No. It detects serialization anomalies and may abort transactions. Applications still need constraints, validation, retries, and proper state machines.

### How can I tell which session is waiting?

Use `pg_stat_activity` where `wait_event_type = 'Lock'`, `pg_locks`, and `pg_blocking_pids()`.

### Does an inventory ledger replace the `inventory` table?

A ledger stores movement history; the `inventory` table typically stores current balances for fast lookups. Atomic writes within the same transaction and reconciliation keep both sources consistent.

### Are backorders represented as negative inventory?

Not necessarily. A backorder is a promise for future fulfillment and should be represented separately from physical `on_hand`/`reserved` counts.

### How do I know the concurrency problem is solved properly?

When concurrent tests prove sold quantities never exceed stock policy, every order is all-or-nothing, retries never duplicate side effects, and database invariants always hold.

## 63. Summary

Core SQL statements:

~~~sql
-- Atomic stock deduction, only when sufficient stock remains.
UPDATE shop.inventory
SET on_hand = on_hand - 4,
    updated_at = now()
WHERE warehouse_id = 10
  AND product_id = 1
  AND on_hand - reserved >= 4
RETURNING on_hand, reserved;

-- Hold stock while awaiting payment.
UPDATE shop.inventory
SET reserved = reserved + 2,
    updated_at = now()
WHERE warehouse_id = 10
  AND product_id = 1
  AND on_hand - reserved >= 2
RETURNING on_hand, reserved;

-- Lock inventory rows in a consistent order.
SELECT product_id, on_hand, reserved
FROM shop.inventory
WHERE warehouse_id = 10
  AND product_id IN (1, 2, 3)
ORDER BY product_id
FOR UPDATE;

-- Set timeouts inside a transaction.
SET LOCAL lock_timeout = '2s';
SET LOCAL statement_timeout = '10s';

-- Check invariants.
SELECT *
FROM shop.inventory
WHERE on_hand < 0
   OR reserved < 0
   OR reserved > on_hand;

-- Observe sessions waiting on locks.
SELECT
    pid,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE wait_event_type = 'Lock';
~~~

Key principles to remember:

1. Race conditions happen when multiple transactions read and decide on the same stale state.
2. Lost updates can cause recorded values to miss the cumulative effect of business operations.
3. Place sufficient-stock predicates inside the same conditional `UPDATE` as the subtraction.
4. Use `CHECK` constraints to protect `on_hand` and `reserved`.
5. Create `orders`, `order_items`, and inventory changes in the same transaction.
6. Multi-item orders must be all-or-nothing.
7. Aggregate duplicate product lines before locking or updating.
8. Lock multiple inventory rows in a consistent order.
9. Use idempotency keys so retries do not trigger duplicate side effects.
10. Reservations separate physical on-hand stock from held stock.
11. Reservation consume/release must be once-only state transitions.
12. Never hold transaction locks while calling payment or network services.
13. `READ COMMITTED` paired with conditional `UPDATE` suits many inventory operations.
14. `REPEATABLE READ`/`SERIALIZABLE` can abort transactions and require full-transaction retries.
15. Reduce deadlocks via lock ordering and handle them with bounded retries.
16. `SKIP LOCKED` helps queue workers, though backlogs must be monitored.
17. An inventory ledger helps explain changes and reconcile balances.
18. Monitoring locks and wait events helps pinpoint contention.
19. Multi-session testing is how concurrency behavior is proven.
20. Final state must satisfy both inventory invariants and the order state machine.
