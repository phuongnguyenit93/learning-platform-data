# Load Testing with Representative Data, Warm-Up, and Percentile Latency

A MySQL benchmark is only meaningful when its data, queries, read/write mix, and concurrency match how the system actually operates. Running a few `SELECT` statements on a tiny table and taking the average latency reveals nothing about how the database behaves with millions of rows, concurrent updates hitting hot rows, or a buffer pool that can no longer hold the full working set.

Load testing requires preparing data with realistic distributions, generating workload traffic at controlled rates, separating warm-up from steady-state measurement, and analyzing throughput, errors, and latency percentiles such as p50, p95, and p99. Metrics must be correlated with CPU, I/O, buffer pool, lock waits, and replication to determine whether bottlenecks reside in the application, network, or MySQL.

## 1. Define the Questions Before Benchmarking

Before picking a tool, decide what you are trying to measure. Benchmarks answer different questions:

- How many transactions per second can a MySQL instance sustain under the current workload?
- As concurrent clients increase, at what level does latency begin climbing sharply?
- Does a new index improve p95 of critical queries or merely slow down inserts?
- Is the buffer pool large enough to hold the hot working set?
- Does a schema, configuration, or version change increase lock waits or replication lag?
- Does the application meet latency SLOs during traffic spikes?

Express criteria as measurable metrics:

| Metric | Meaning |
|---|---|
| Offered load | Requests/transactions per second generated by the load tool |
| Throughput | Requests/transactions completed successfully per second |
| Latency | Elapsed time from sending a request to receiving the response at the defined boundary |
| Error rate | Percentage of SQL errors, HTTP errors, timeouts, retries, or rejected requests |
| Concurrency | Number of simultaneously active clients/sessions or in-flight requests |
| Resource utilization | CPU, RAM, disk IOPS/latency, network, and connection resources |
| Replication lag | Delay applying transactions on replicas when topology uses replication |

Define measurement boundaries clearly. Measuring at the HTTP API includes queueing, application code, connection pooling, network, and MySQL; measuring statement duration inside MySQL reflects only database processing. Both are useful, yet neither replaces the other.

## 2. Creating Representative Data

The dataset is a core part of the benchmark, not throwaway filler just to make tests run. A table with a few hundred rows fits entirely in the buffer pool and can be served via scans without exposing index issues. As data grows, cardinality, value distributions, and working set size can dramatically alter execution plans and latency.

### Characteristics to Reproduce

| Characteristic | Questions to answer | Why it matters |
|---|---|---|
| Row count and size | How many rows and how many GB of data/indexes? | Affects I/O, caching, scan times, and backups |
| Cardinality | How many distinct values exist in a column? | Affects selectivity and index choice |
| Skew/hot keys | Do a few customers or products receive most requests? | Creates hot pages, lock contention, and cache locality |
| Temporal distribution | Is recent data accessed much more often than older data? | Models time-window queries and retention patterns |
| Row size | Are there large JSON/text or nullable columns? | Affects page count, I/O, and memory usage |
| Table relationships | Parent/child ratios, items per order, events per user? | Affects joins, foreign keys, and cascades |
| Indexes | Are production-like secondary indexes present? | Affects reads, writes, and storage footprint |
| Validity | Are constraints, `NULL`s, duplicates, and boundary values similar? | Avoids benchmarking on unrealistically clean data |

Do not generate purely sequential IDs and uniform distributions if production data is skewed. For instance, top customers may drive 30% of queries; some statuses may account for only 1% of rows; recent orders are typically read far more often than older orders. These distributions directly shape caching and query plans.

### Working Set and Buffer Pool

Know whether your benchmark targets cache-friendly or disk-bound conditions:

- **Cache-friendly:** frequently accessed data and indexes are much smaller than `innodb_buffer_pool_size`. Goal is measuring throughput and latency when data sits mostly in RAM.
- **Disk-bound:** working set exceeds the buffer pool or access patterns are widely scattered. Goal is measuring read I/O, cache misses, and storage capacity under load.
- **Mixed:** a hot subset resides in RAM while colder data lives on disk. This is the typical reality for transactional workloads.

Never conclude the database can handle production load merely because a small-dataset benchmark showed low latency. Conversely, do not artificially force the working set larger than RAM if production genuinely maintains a high cache hit rate. Document the exact scenario under test.

### Generating Reproducible Data

Seeding should be deterministic so repeated runs share the same distribution. Record scripts, seeds, row counts, table/index sizes, and summary checksums or stats. If using a production snapshot, strip or anonymize sensitive data while preserving the needed distribution properties.

Example `orders` table:

```sql
CREATE TABLE orders (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  customer_id BIGINT UNSIGNED NOT NULL,
  status VARCHAR(24) NOT NULL,
  total_amount DECIMAL(14,2) NOT NULL,
  created_at DATETIME(6) NOT NULL,
  PRIMARY KEY (id),
  KEY idx_orders_customer_created (customer_id, created_at),
  KEY idx_orders_status_created (status, created_at)
) ENGINE=InnoDB;
```

The dataset needs realistic variety across customers, statuses, and timestamps so queries filtering by customer, status, and date ranges exhibit production-like selectivity. If every row shares the same `status`, the benchmark fails to represent production.

## 3. Modeling the Workload

A real workload is usually a mix of operations, not an endless loop of a single `SELECT`. Categorize operations by transaction or use case:

| Category | Example | Cost components |
|---|---|---|
| Point read | Fetch order by primary key | B-tree lookup, buffer pool, network round trip |
| Range read | Fetch customer orders in a time range | Index range scan, sort, rows examined |
| Join/report | Aggregate orders and order items | Join order, cardinality, temporary tables, aggregation |
| Insert | Create an order and line items | Primary/secondary indexes, redo, binlog, commit |
| Update | Change status or decrement inventory | Row locks, index maintenance, contention |
| Delete/cleanup | Batch-purge expired rows | Undo, purge, locking, replication |
| Mixed transaction | Read inventory, insert order, decrement stock | Multiple statements in one transaction plus atomicity |

Base operation ratios on observed production telemetry or documented assumptions. An illustrative workload might mix 65% reads, 25% inserts, 8% updates, and 2% deletes. These percentages are only examples; reporting, order-processing, and telemetry workloads differ widely.

Each transaction should mirror application boundaries: statement count, read/write sequence, isolation level, transaction duration, and commit pattern. Benchmarking isolated autocommit statements does not simulate a transaction performing five reads and two writes.

### Parameter Distributions Must Also Be Representative

Never send the same `customer_id` on every query if production accesses millions of customers. Conversely, do not pick uniformly at random when hot keys exist. Use realistic parameter distributions to reproduce true cache locality and lock contention.

For range queries, test multiple window sizes: queries touching 10 rows, 100 rows, and 10,000 rows. For status filters, reflect common vs. rare ratios. For updates, test both workers updating disjoint rows and multiple workers contending on hot rows.

## 4. Preparing the Benchmark Environment

Run benchmarks on a dedicated MySQL instance or clone reserved for testing. Never generate heavy load on production without operational approval and strict safety guardrails.

Record at minimum:

- MySQL version, edition, storage engine, and server configuration.
- CPU, RAM, core count, volume/storage type, IOPS, and filesystem.
- `innodb_buffer_pool_size`, redo capacity, connection limits, SQL mode, and isolation level.
- Schema, indexes, collation, charset, row counts, and size of each table.
- Binary logs, replication topology, durability settings, and backup activity.
- Client/driver/tool versions, load generator count, and network setup.
- Application version, JVM version, connection pool, and thread configuration.

Inspect MySQL configuration:

```sql
SELECT VERSION(), @@version_comment;

SHOW VARIABLES WHERE Variable_name IN (
  'innodb_buffer_pool_size',
  'innodb_redo_log_capacity',
  'max_connections',
  'transaction_isolation',
  'sql_mode',
  'binlog_format',
  'sync_binlog',
  'innodb_flush_log_at_trx_commit'
);
```

Ensure comparison runs share equivalent conditions. If one run overlaps with a backup or replica catch-up and another does not, results cannot be compared directly. Log every configuration change and never vary multiple parameters at once while isolating root causes.

### Separating Load Generators from the Database

Benchmark clients also consume CPU, RAM, sockets, and network bandwidth. If the load generator saturates its CPU, measured throughput reflects the generator's bottleneck rather than MySQL's limit.

Monitor CPU and network on both clients and server. For high load, scale out load generators or upgrade client resources. Verify the tool actually sustains its scheduled request rate; if it cannot, do not claim MySQL reached saturation.

## 5. Choosing Load-Testing Tools

Select tools suited to the layer under test:

| Tool | Appropriate scope | Notes |
|---|---|---|
| `sysbench` | Direct MySQL benchmarking, OLTP read/write, thread/concurrency tests | Handy built-in workloads; customize Lua scripts to match real queries |
| JMeter | HTTP, JDBC, and integrated flows | JDBC samplers can add overhead; configure pooling and transactions carefully |
| k6 | API/HTTP with arrival-rate models and thresholds | Measures end-to-end experience, not MySQL time alone |
| Gatling | HTTP/API and user journeys | Good for request flows; carefully manage feeders and injection profiles |
| Custom harnesses | App-specific business transactions | Requires accurate timestamps/histograms and low measurement overhead |

For direct MySQL benchmarking, `sysbench` is a solid starting point. Example OLTP data preparation:

```bash
sysbench oltp_read_write \
  --db-driver=mysql \
  --mysql-host=127.0.0.1 \
  --mysql-port=3306 \
  --mysql-user=bench_user \
  --mysql-password='REPLACE_WITH_SECRET' \
  --mysql-db=bench \
  --tables=8 \
  --table-size=1000000 \
  prepare
```

After preparing, run the workload with fixed concurrency and duration:

```bash
sysbench oltp_read_write \
  --db-driver=mysql \
  --mysql-host=127.0.0.1 \
  --mysql-port=3306 \
  --mysql-user=bench_user \
  --mysql-password='REPLACE_WITH_SECRET' \
  --mysql-db=bench \
  --tables=8 \
  --table-size=1000000 \
  --threads=64 \
  --time=300 \
  --report-interval=10 \
  --percentile=95 \
  run
```

These flags are illustrative only. Replace the sample password with a securely managed secret; avoid exposing secrets in shell history or CI logs. Run `cleanup` only after confirming you are targeting the benchmark database and data can be deleted. Default `sysbench` workloads do not automatically represent your business queries; write custom Lua scripts when queries, operation ratios, or key distributions differ.

## 6. Warm-Up: Why Not Measure Immediately After Startup?

Initial runs right after startup are slower because multiple layers are cold:

- InnoDB buffer pool does not yet hold frequently accessed pages.
- OS page cache and storage cache lack the working set.
- Connection pools have not yet opened target connections.
- JVM JIT has not compiled hot code paths.
- Prepared statement and metadata caches are not populated.
- DNS, TLS sessions, and connection initialization incur startup costs.

When measuring steady state, run a dedicated warm-up phase before recording primary metrics. However, warm-up must not hide cold-start behavior if the system must serve traffic immediately after restarts. In that case, measure cold-start and warm steady-state as two separate scenarios.

### Warm-Up Procedure

1. Start MySQL and the application with the exact benchmark configuration.
2. Initialize connection pools and run health checks just like production.
3. Apply representative traffic at low load, ramping gradually to the target level.
4. Continue running until latency, throughput, and cache metrics stabilize over a sufficient observation window.
5. Mark the exact end of warm-up; exclude warm-up samples from steady-state statistics.
6. Begin the primary measurement window without unscheduled config changes or data resets.

Never use a fixed warm-up duration for every system. A small table may warm up in seconds; a multi-gigabyte working set may take much longer or never fit fully in the buffer pool. A better criterion is observing stabilization of metrics and workload behavior.

### Warm Cache vs. Cold Cache Are Separate Scenarios

To measure cold-cache performance, use a controlled startup/restart procedure or controlled cache state. Never assume `FLUSH TABLES` empties the InnoDB buffer pool or OS page cache. Dropping OS caches or restarting production to test cold-cache behavior causes disruption and should never be done casually.

For cold-start tests, record whether MySQL restarted or only the application restarted, whether the buffer pool loaded from a dump, and the state of the OS page cache. For warm-cache tests, warm up using the exact expected key distribution.

## 7. Ramp-Up, Steady-State, Spike, and Soak Tests

Structure a load-test run into distinct phases with clear goals:

| Phase | Purpose | What to observe |
|---|---|---|
| Baseline | Measure latency and throughput at very low load | Base cost of queries and connections |
| Warm-up | Prime caches, pools, and runtime | Stabilization time, buffer pool reads, JIT |
| Ramp-up | Gradually raise offered load or concurrency | Inflection point where latency rises and resources saturate |
| Steady-state | Sustain target load long enough | p50/p95/p99, throughput, errors, and resource usage |
| Spike | Rapidly surge load for a short burst | Burst absorption, queueing, and recovery |
| Soak | Sustain moderate/high load over long duration | Memory leaks, connection leaks, purge lag, disk growth |
| Cool-down | Reduce load and monitor recovery | Queue drain, replica catch-up, and latency recovery |

Do not collapse all phases into one number. A system may achieve great p95 in steady state yet time out during a spike, or run fine for 5 minutes yet degrade after 2 hours due to queues, history list growth, or temp disk usage.

## 8. Closed-Loop vs. Open-Loop Load

The load-generation model shapes how results are interpreted.

### Closed-Loop: Fixed Concurrent Users

In a closed-loop model, each virtual user sends the next request only after the previous one completes. When latency rises, the rate of outgoing requests naturally drops. This mirrors users waiting for responses before clicking again, yet it can mask overload when the system cannot keep up.

### Open-Loop: Arrival Rate Independent of Responses

In an open-loop model, the load generator dispatches requests on a fixed schedule—such as 500 requests/second—regardless of whether earlier responses finished. This tests the system under steady offered load and exposes queue buildup as the server saturates.

| Model | Advantage | Interpretation risk |
|---|---|---|
| Closed-loop | Easy to model concurrent users | When the server slows, offered load drops too, masking saturation |
| Open-loop | Controls request rate independent of latency | Queues can grow rapidly; cap queues and track dropped requests |

Coordinated omission occurs when a load generator only measures requests sent after prior requests finish, ignoring all the time intervals where new requests should have been dispatched while the server stalled. Latency can look artificially healthy right when the system is choked. Choose tools supporting arrival-rate models or coordinated-omission-corrected histograms; record dropped iterations and queueing delays.

Do not look only at virtual user counts. 100 virtual users can generate vastly different request rates depending on think time and response time. Report concurrency, offered rate, and completed rate together.

## 9. Understanding p50, p95, and p99

Latency typically follows a skewed distribution: most requests are fast, while a small fraction are very slow due to lock waits, disk reads, checkpoints, GC, network hiccups, or plan flips. Averages obscure the tail of the distribution.

- **p50 (median):** 50% of requests finish within this time or faster. Represents typical user experience.
- **p95:** 95% of requests finish within this time or faster; 5% are slower.
- **p99:** 99% of requests finish within this time or faster; 1% are slower.
- **p99.9:** valuable for high-volume systems with strict tail SLOs, provided enough samples exist for stable estimation.

Example:

| Metric | Latency |
|---|---:|
| p50 | 18 ms |
| p95 | 95 ms |
| p99 | 420 ms |
| max | 2.8 s |

In this example, typical requests are fast, yet 1% take longer than 420 ms. Reporting only an average of 35 ms hides a real tail-latency problem.

### Computing Percentiles Correctly

Record per-request latencies or high-resolution histograms. Sort samples in ascending order; p95 is the threshold not exceeded by at least 95% of samples. At scale, tools rely on HDR histograms or streaming quantile estimators.

Never average per-worker p95 values to compute an overall p95. Suppose worker A handled 1,000 requests and worker B handled 10 requests; averaging their two p95s does not equal the p95 of all 1,010 requests. Merge raw samples or histograms as supported by your tool and compute global percentiles.

Percentiles require adequate sample counts. A p99 computed from a few hundred requests has low statistical stability because only a handful of samples sit in the tail. Report sample count, window duration, and calculation method alongside percentiles.

### Which Components Belong in Latency?

At the application layer, latency breaks down as:

```text
Request latency
  = client scheduling/queue
  + network to application
  + application processing
  + connection-pool wait
  + network to MySQL
  + database execution/lock/commit
  + response serialization/network
```

This is a conceptual decomposition; phases can overlap depending on architecture. Use distributed tracing or instrumentation to separate pool wait from query execution. If API p99 rises while MySQL statement latency stays flat, investigate pools, threads, GC, or networking.

## 10. Throughput, Error Rate, and Saturation Point

Throughput is the number of operations completed per unit time. Distinguish:

- **Offered throughput:** rate the load generator attempts to send.
- **Completed throughput:** rate the system finishes requests.
- **Successful throughput:** rate of error-free completions.

As load grows, completed throughput generally rises until hitting the saturation zone. Beyond that point, throughput plateaus or drops while latency and error rates climb sharply. That signals a resource or contention limit.

Illustrative curve:

```text
Throughput
  ^
  |                         _________
  |                    ____/
  |               ____/
  |          ____/
  |     ____/
  |____/________________________________> Offered load
      scaling zone     saturation zone
```

Never pick an operating point right on the saturation cliff if the system must absorb bursts or growth. Identify an operating point with enough headroom to keep latency and error rates inside SLOs.

Track both errors and retries. A request retried three times can generate three MySQL transactions even though the client sees a single business action. Unbounded retries amplify load precisely when the database is already overloaded.

Little's Law provides a steady-state sanity check:

\[
L = \lambda W
\]

Where `L` is the average number of requests inside the system, `λ` is average throughput, and `W` is average time spent in the system. This holds for stable systems with consistent measurement; do not apply it when queues are growing unboundedly.

## 11. Measuring API Latency and Throughput with k6

When measuring the end-to-end experience of a Spring Boot API backed by MySQL, use an HTTP tool such as k6. The following example generates a fixed arrival rate:

```javascript
import http from 'k6/http';
import { check } from 'k6';

export const options = {
  scenarios: {
    steady_api_load: {
      executor: 'constant-arrival-rate',
      rate: 200,
      timeUnit: '1s',
      duration: '10m',
      preAllocatedVUs: 50,
      maxVUs: 300,
    },
  },
  thresholds: {
    http_req_duration: ['p(95)<250', 'p(99)<500'],
    http_req_failed: ['rate<0.01'],
  },
};

export default function () {
  const response = http.get(
    'https://test.example.internal/api/orders?status=PAID'
  );

  check(response, {
    'status is 200': (r) => r.status === 200,
  });
}
```

These rates, URLs, and thresholds are examples only. The endpoint should hit a representative dataset under a least-privilege test account. Run a separate warm-up before the steady-state measurement; if `preAllocatedVUs` is too low, k6 may allocate extra VUs dynamically and incur dropped iterations. Monitor `dropped_iterations`, active VUs, and load-generator CPU.

`http_req_duration` measures client-side HTTP time, not SQL time alone. Pair it with APM/tracing or server metrics to separate connection-pool waits from statement times. To benchmark MySQL directly, use `sysbench` or a dedicated JDBC harness targeting the transactions under study.

## 12. Instrumenting MySQL Under Load

Capture state before, during, and after each run. Use aligned time windows to correlate DB changes with client latency.

### Connections and Concurrency

```sql
SHOW GLOBAL STATUS WHERE Variable_name IN (
  'Threads_connected',
  'Threads_running',
  'Connections',
  'Max_used_connections',
  'Aborted_connects'
);
```

`Threads_connected` is the count of open connections; `Threads_running` is threads not sleeping. When `Threads_running` spikes alongside latency, inspect CPU, lock waits, and query concurrency. Never blindly raise `max_connections`: more connections can worsen contention and memory pressure.

### Buffer Pool

```sql
SHOW GLOBAL STATUS WHERE Variable_name IN (
  'Innodb_buffer_pool_read_requests',
  'Innodb_buffer_pool_reads',
  'Innodb_buffer_pool_pages_data',
  'Innodb_buffer_pool_pages_free',
  'Innodb_buffer_pool_wait_free'
);
```

`Innodb_buffer_pool_read_requests` counts logical read requests; `Innodb_buffer_pool_reads` reflects physical page reads from disk due to buffer pool misses. Over a sampling interval, the approximate miss ratio is:

\[
\text{miss ratio} = \frac{\Delta \text{physical reads}}{\Delta \text{logical read requests}}
\]

This is a high-level indicator, not the sole performance metric. Even a low miss ratio can generate heavy absolute disk I/O at high QPS; inspect disk latency and bytes read concurrently.

### Statement Digests

Performance Schema aggregates statements by digest:

```sql
SELECT
  DIGEST_TEXT,
  COUNT_STAR,
  ROUND(AVG_TIMER_WAIT / 1000000000000, 3) AS avg_seconds,
  ROUND(MAX_TIMER_WAIT / 1000000000000, 3) AS max_seconds,
  SUM_ROWS_EXAMINED,
  SUM_ROWS_SENT,
  SUM_CREATED_TMP_DISK_TABLES
FROM performance_schema.events_statements_summary_by_digest
WHERE DIGEST_TEXT IS NOT NULL
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 20;
```

Performance Schema timers are in picoseconds; the division in the example converts to seconds. Digest summaries report execution counts, total/avg/max time, and rows examined/sent, though they do not replace client latency histograms. Enabling instrumentation adds some overhead; keep observability settings consistent across benchmark runs.

### Locks and Deadlocks

```sql
SHOW GLOBAL STATUS WHERE Variable_name IN (
  'Innodb_row_lock_current_waits',
  'Innodb_row_lock_time',
  'Innodb_row_lock_waits',
  'Innodb_deadlocks'
);

SHOW ENGINE INNODB STATUS\G
```

Compare before/after deltas to count lock waits and deadlocks during the benchmark window. Occasional deadlocks handled cleanly by retries can be normal, whereas rapidly climbing deadlock rates under higher concurrency require reviewing update ordering, transaction duration, and indexes.

### I/O and Operating System

Correlate MySQL status with host metrics: CPU utilization, run queue, memory pressure, swap, disk read/write IOPS, throughput, `fsync` latency, and network. A slow query is not always caused by SQL; IOPS-throttled storage or VM CPU steal can also be responsible.

## 13. Reading Execution Plans in Load Context

When a digest dominates total time, grab a representative query and inspect its plan:

```sql
EXPLAIN
SELECT id, created_at, total_amount
FROM orders
WHERE customer_id = 501
  AND created_at >= '2026-11-01'
ORDER BY created_at DESC
LIMIT 50;
```

On supported MySQL versions, `EXPLAIN ANALYZE` executes the query and reports actual iterator timings and row counts:

```sql
EXPLAIN ANALYZE
SELECT id, created_at, total_amount
FROM orders
WHERE customer_id = 501
  AND created_at >= '2026-11-01'
ORDER BY created_at DESC
LIMIT 50;
```

`EXPLAIN ANALYZE` actually runs the query. Use it only with well-understood `SELECT`s in benchmark environments; never run heavy queries casually on production. Compare estimated vs. actual rows, loop counts, temporary tables, filesorts, and chosen indexes.

An index can lower read latency while slowing inserts/updates due to extra B-tree maintenance. Benchmarks must measure the full mixed workload before and after an index change, not just re-run the optimized `SELECT`.

## 14. Organizing a Benchmark Matrix

Instead of ad-hoc runs, structure a controlled matrix:

| Run | Dataset | Concurrency/arrival rate | Goal |
|---|---|---|---|
| A | Working set smaller than buffer pool | Low | Cache-friendly baseline |
| B | Representative dataset | Low | Realistic workload baseline |
| C | Representative dataset | Stepped 1x, 2x, 4x | Find latency inflection point |
| D | Representative dataset, skewed keys | Target load | Measure hot-key contention |
| E | Dataset larger than buffer pool | Target load | Measure disk-bound behavior |
| F | Representative dataset | Short spike | Measure burst absorption and recovery |
| G | Representative dataset | Sustained steady load | Soak test and detect time-based degradation |

Change only one variable per comparison—such as index A vs. B or `innodb_buffer_pool_size`. Changing indexes, worker counts, and buffer pool size simultaneously obscures which factor drove the difference.

Repeat runs multiple times after restoring identical data and cache states per scenario. Report the median across runs alongside per-run percentiles, while retaining run-to-run variance. One lucky run is never enough to lock in production sizing.

## 15. Interpreting Results and Finding Bottlenecks

| Observation | Likely area to investigate |
|---|---|
| Throughput rises, p95 stays flat | System still has headroom in the current load band |
| Throughput flattens, p95/p99 spike | CPU, I/O, locks, or queues have saturated |
| High CPU, low disk, high rows examined | Query plan, scans, joins, sorts, or CPU-bound concurrency |
| High I/O latency and rising buffer pool physical reads | Large working set, cache misses, or slow storage |
| Rising lock waits/deadlocks | Hot rows, long transactions, update order, or suboptimal indexes |
| Rising pool wait while MySQL statement time stays low | Connection pool too small or connections held too long |
| Rising client dropped iterations | Load generator under-provisioned or server rejecting offered load |
| Rising replica lag despite healthy primary throughput | Applier, network, or replica resource bottleneck |
| Latency drifts upward during soak test | Leaks, queue buildup, purge/checkpoint backlog, memory or disk pressure |

Never draw conclusions from one metric alone. High CPU, for example, can stem from table scans, compression, encryption, or excessive thread contention; cross-check digests, execution plans, and OS metrics to confirm.

## 16. Mistakes That Invalidate Benchmarks

- **Dataset too small:** all pages fit in cache, failing to reflect production scale.
- **Artificially uniform data:** misses hot keys and skew present in real traffic.
- **Testing only one query:** ignores mixed read/write contention and index maintenance cost.
- **Measuring immediately:** warm-up, connection setup, and JIT distort steady-state numbers.
- **Reporting only averages:** hides tail latency and slow outliers.
- **Omitting offered load:** hides what load the server actually handled or whether the generator backed off.
- **Coordinated omission:** ignores intervals where requests should have arrived while the system stalled.
- **Underpowered load generator:** client CPU/network saturates before the database.
- **Changing multiple variables at once:** prevents attributing causality.
- **Ignoring errors and retries:** throughput looks inflated while requests fail or repeat.
- **Omitting cache state:** treats cold runs and warm runs as comparable.
- **Uncontrolled benchmarking on production:** impacts live users and yields non-reproducible results.

## 17. Reproducible Benchmark Reporting

A report should contain enough detail for someone else to reproduce the test and understand its boundaries:

1. Goals, SLOs, and benchmark questions.
2. Topology, MySQL version, hardware, storage, and server settings.
3. Dataset: row counts, storage size, indexes, cardinality, skew, and generation method.
4. Workload: transaction mix, read/write ratio, parameter distributions, and isolation level.
5. Load model: closed-loop vs. open-loop, offered rate, concurrency, and generator count.
6. Phases: baseline, warm-up, ramp-up, steady-state, spike/soak, and cool-down.
7. p50, p95, p99, max, successful throughput, error rate, and dropped iterations.
8. CPU, RAM, disk IOPS/latency, buffer pool, lock waits, redo, and replication lag.
9. Key execution plans/digests and evaluated changes.
10. Repetition count, variance, limitations, and operational conclusions.

Example summary table:

| Scenario | Offered req/s | Completed req/s | p50 | p95 | p99 | Error rate |
|---|---:|---:|---:|---:|---:|---:|
| Baseline | 100 | 100 | 12 ms | 28 ms | 45 ms | 0.00% |
| Target load | 300 | 298 | 20 ms | 85 ms | 190 ms | 0.05% |
| Near saturation | 600 | 430 | 34 ms | 620 ms | 1.8 s | 2.4% |

These numbers merely illustrate formatting. Whenever completed throughput lags offered load, inspect queues, dropped iterations, timeouts, and resources to see whether requests were delayed or dropped.

## 18. Practice Scenario

A Spring Boot API serves order history. Production holds 20 million orders and 2 million customers; most requests read the latest 50 orders; 20% of customers generate 70% of traffic. Order creation writes one order and several order items. The requirement is sustaining p95 below 250 ms at 300 requests/second with error rate under 0.5%.

**Step 1 — Build the dataset.** Generate 20 million orders with production-like customer skew, varied statuses, and varied timestamps. Generate order items matching the items-per-order distribution while keeping production indexes and foreign keys. Record data/index sizes and seeds.

**Step 2 — Construct the workload.** Create transactions reading the latest 50 orders per customer, creating orders with items, and updating statuses at target ratios. Apply skewed customer selection so hot keys receive the bulk of traffic.

**Step 3 — Baseline and warm-up.** Run low load to warm connection pools and the working set. Monitor buffer pool physical reads, throughput, and latency until stable. Capture cold-start results separately if required.

**Step 4 — Ramp-up.** Step the arrival rate through 100, 200, 300, 400, and 500 requests/second. Hold each step long enough for queues and caches to reach observable equilibrium. Record offered/completed rates, p50/p95/p99, errors, and dropped iterations.

**Step 5 — Locate bottlenecks.** If p99 climbs and digests show the history query examining too many rows, inspect `EXPLAIN ANALYZE` and indexes. If lock waits rise during order creation, check hot customers, write ordering, and transaction duration. If pool waits are high while DB statements are fast, inspect pool size and connection hold times.

**Step 6 — Re-measure after changes.** Change one variable, such as an index or batch insert, and re-run with the exact same dataset, seed, load profile, and warm-up. Compare read latency, write latency, throughput, and index footprint.

**Step 7 — Soak test.** Hold 300 requests/second for an extended period while monitoring p95/p99, errors, memory, redo, purge, disk, and replica lag. Declare SLO compliance only when metrics hold steady with adequate headroom.

## 19. Checklist Before Publishing Benchmark Results

- [ ] Defined goals, SLOs, and latency measurement boundaries.
- [ ] Dataset has representative scale, cardinality, skew, hot keys, and working set.
- [ ] Schema, indexes, constraints, SQL mode, and MySQL version match the target environment.
- [ ] Workload mirrors real read/write ratios, transaction boundaries, and parameter distributions.
- [ ] Load generator has ample resources and sustains the planned offered load.
- [ ] Documented closed-loop vs. open-loop model and checked for coordinated omission.
- [ ] Warm-up separated from steady-state; cold-start measured separately if needed.
- [ ] Executed baseline, ramp-up, steady-state, and spike/soak phases as required.
- [ ] Reported p50, p95, p99, throughput, error rate, timeouts, and dropped iterations.
- [ ] Percentiles calculated from merged samples/histograms, not averaged across workers.
- [ ] Sufficient sample counts and duration for meaningful tail-latency estimates.
- [ ] Monitored CPU, RAM, I/O, buffer pool, locks, redo, connections, and replication.
- [ ] Archived execution plans, statement digests, and configuration changes.
- [ ] Repeated runs with the same seed and controlled cache state.
- [ ] Report states limitations, variance, and untested conditions.

A trustworthy MySQL benchmark simulates real data and access patterns rather than simply spawning massive numbers of connections. Separating warm-up from the measurement window, controlling offered load, reporting p50/p95/p99 alongside throughput and error rates, and correlating with InnoDB metrics pinpoint true saturation limits. Only when data, workload, configuration, and measurement methodology are fully documented can results be compared across optimizations and guide operational decisions.
