# Impact of Identifier Generation Strategies on Batch Inserts

## Objectives

After this lesson, you will be able to:

- Explain why primary key generation strategy affects the ability to group multiple INSERTs into a JDBC batch.
- Distinguish IDENTITY, SEQUENCE, TABLE, and application-assigned identifiers in JPA/Hibernate.
- Understand the limitation of GenerationType.IDENTITY when Hibernate needs the primary key immediately after each INSERT.
- Configure batch inserts in Spring Boot and distinguish Hibernate batching settings from MySQL Connector/J rewrite capabilities.
- Design bulk write loops using flush() and clear() to control persistence context memory.
- Measure batch insert effectiveness and select an identifier strategy suited for MySQL.

## 1. What Is a Batch Insert?

Batch inserting sends multiple INSERT statements to the database as a group to reduce round-trips between the application and MySQL. Instead of sending one request per row, JDBC adds multiple parameter sets to the same PreparedStatement and invokes executeBatch().

Example of an unbatched flow:

~~~sql
INSERT INTO audit_log(message) VALUES ('created');
INSERT INTO audit_log(message) VALUES ('updated');
INSERT INTO audit_log(message) VALUES ('deleted');
~~~

When batching, the driver accepts multiple parameter sets for the same prepared statement and submits them as a batch:

~~~java
PreparedStatement statement =
    connection.prepareStatement(
        "INSERT INTO audit_log(message) VALUES (?)");

statement.setString(1, "created");
statement.addBatch();

statement.setString(1, "updated");
statement.addBatch();

statement.setString(1, "deleted");
statement.addBatch();

statement.executeBatch();
~~~

JPA/Hibernate can perform a similar optimization at the ORM layer. When the application calls persist() on multiple entities, Hibernate can defer SQL INSERTs, group matching statements, and flush them as batches.

Batch inserts typically help:

- Reduce network round-trips between the application and MySQL.
- Reduce per-statement preparation and dispatch overhead.
- Improve throughput for imports, ETL jobs, audit logging, and bulk entity creation.

Batching does not eliminate per-row database work. MySQL still validates constraints, updates indexes, writes redo/undo logs, and logs binary log events per transaction. Oversized batches can inflate memory consumption, lock hold times, transaction sizes, and replication lag.

## 2. JPA, Hibernate, and Primary Key Generation

In JPA, primary keys are declared with @Id. If the application or provider generates values automatically, @GeneratedValue uses one of these strategies:

| Strategy | How the Identifier Is Obtained |
|---|---|
| IDENTITY | Database generates the value on INSERT, e.g., MySQL AUTO_INCREMENT |
| SEQUENCE | Database allocates values from a sequence object |
| TABLE | Provider uses a dedicated table to allocate identifier values |
| AUTO | Provider selects a strategy based on dialect, key type, and provider version |

Another approach is an **application-assigned identifier**: the application assigns the ID before calling persist(), such as a UUID or an ID from a dedicated allocator service. This is not a JPA GenerationType constant; the entity simply declares @Id and the application sets the value.

The identifier strategy dictates when Hibernate knows the primary key—which is pivotal for batch inserts:

- If the ID is known before INSERT, Hibernate can queue the statement into a batch.
- If the ID is only created by MySQL after INSERT, Hibernate normally executes the INSERT immediately to retrieve the key.
- If the provider must query the database for each individual ID beforehand, ID-fetch overhead can erase batching gains; block allocation reduces those round-trips.

## 3. Why Does IDENTITY Hinder JDBC Insert Batching?

MySQL commonly uses AUTO_INCREMENT for integer primary keys. In JPA, the typical mapping is:

~~~java
@Entity
@Table(name = "orders")
public class Order {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    // Other properties
}
~~~

The id value is generated by MySQL only when the INSERT executes. Hibernate needs that key to populate the managed entity and maintain the identity map inside the persistence context. Consequently, with IDENTITY, Hibernate normally executes the INSERT immediately upon persisting the entity rather than deferring it for a JDBC batch.

Consequences:

- Even with hibernate.jdbc.batch_size configured, INSERTs for IDENTITY entities are still not batched through Hibernate's standard batching path.
- Calling saveAll() with thousands of entities does not automatically turn them into a multi-row INSERT.
- Enabling rewriteBatchedStatements=true in Connector/J will not create batches if Hibernate already dispatches individual INSERTs one by one.
- MySQL still generates AUTO_INCREMENT keys normally; the limitation stems from the ORM needing the generated key immediately after each INSERT.

IDENTITY offers simplicity, native MySQL integration, and easy compatibility with existing schemas. For ordinary CRUD workloads, it remains a solid choice. When bulk inserts dominate and throughput is critical, measure IDENTITY's impact and evaluate pre-INSERT ID allocation strategies.

Do not conclude that MySQL lacks support for multi-row INSERTs or JDBC batches with auto-increment. MySQL and the JDBC driver can handle batched INSERTs, yet Hibernate cannot defer and batch them along the standard IDENTITY path when it must fetch the generated key right after every entity.

## 4. SEQUENCE and MySQL Characteristics

GenerationType.SEQUENCE uses a sequence object to obtain IDs prior to INSERT. On databases with native sequences, the provider can pre-allocate an ID range and batch multiple inserts.

MySQL has no native sequence object like PostgreSQL or Oracle. Therefore, never assume the following declaration behaves identically across every Hibernate/MySQL version:

~~~java
@Id
@GeneratedValue(strategy = GenerationType.SEQUENCE)
private Long id;
~~~

Behavior depends on the JPA provider, dialect, and version. The provider may reject it or fall back to a table-backed sequence emulation. Inspect the actual DDL and SQL generated by Hibernate.

When pre-INSERT IDs are needed on MySQL, consider a TABLE generator, application-generated UUIDs, or an ID service. Do not pick SEQUENCE solely because it is commonly recommended for batch inserts on databases with native sequences.

## 5. TABLE Generator: Allocating IDs Before INSERT

GenerationType.TABLE uses a table to manage identifier values. Hibernate reads and updates counters in that table to assign IDs to entities.

Example:

~~~java
@Entity
@Table(name = "orders")
public class Order {
    @Id
    @TableGenerator(
        name = "order_id_generator",
        table = "id_generator",
        pkColumnName = "generator_name",
        valueColumnName = "next_value",
        pkColumnValue = "orders",
        allocationSize = 50
    )
    @GeneratedValue(
        strategy = GenerationType.TABLE,
        generator = "order_id_generator"
    )
    private Long id;
}
~~~

Hibernate uses the id_generator table to pre-allocate blocks of IDs. allocationSize=50 tells the provider it may allocate blocks of 50 values according to its supported generator/optimizer mechanism, avoiding querying the generator table for every single entity.

Conceptual generator table structure:

~~~sql
CREATE TABLE id_generator (
    generator_name VARCHAR(100) NOT NULL PRIMARY KEY,
    next_value BIGINT NOT NULL
) ENGINE=InnoDB;
~~~

Exact DDL may be generated by Hibernate and vary by dialect/version. Do not create the table manually using the schema above without verifying the DDL Hibernate expects.

### 5.1. Advantages

- IDs exist prior to INSERT, letting Hibernate defer and batch INSERTs.
- Works on MySQL without native sequence objects.
- Allocates in blocks to reduce generator table accesses.
- Keeps integer keys more compact than UUIDs inside InnoDB's clustered index.

### 5.2. Costs and Caveats

- The generator table adds extra writes and can become a contention point when many transactions allocate IDs simultaneously.
- A large allocationSize reduces generator hits at the expense of larger ID gaps on application restarts or unused blocks.
- All application instances must share compatible generator configurations. Never let nodes arbitrarily use mismatched allocation sizes or optimizers.
- Verify the generator table, unique segments, and transaction behavior across multiple instances.
- IDs are not guaranteed to be gap-free; never use generated IDs as gap-free business document numbers.

TABLE generators enable batch inserts, but require benchmarking under real load. In multi-node, high-throughput systems, measure generator table contention before committing to it.

## 6. UUIDs or Application-Assigned IDs

If the application generates IDs before writing, Hibernate does not wait for MySQL to return a generated key after each INSERT. This preserves the ability to group INSERTs into JDBC batches.

Example entity using UUID:

~~~java
import jakarta.persistence.*;
import java.util.UUID;

@Entity
@Table(name = "customers")
public class Customer {
    @Id
    private UUID id;

    @Column(nullable = false)
    private String name;

    protected Customer() {
    }

    public Customer(String name) {
        this.id = UUID.randomUUID();
        this.name = name;
    }
}
~~~

The ID is already populated before persist:

~~~java
Customer customer = new Customer("An");
entityManager.persist(customer);
~~~

With UUID keys, the application creates IDs without a database round-trip. This helps batch inserts, offline record creation, and independent ID generation across services.

### 6.1. Impact on InnoDB Primary Keys

InnoDB organizes table data in a clustered index, typically the primary key. Every secondary index also embeds the primary key value to point back to the row. Thus, primary key width and ordering affect every secondary index.

Random UUIDs carry specific costs:

- Larger keys than BIGINT, inflating clustered and secondary index sizes.
- Random values insert across scattered B-tree pages, causing page splits and hurting locality.
- Cache efficiency can drop as indexes grow larger and more fragmented.

UUIDs still excel for distributed ID generation without round-trips. When using UUIDs, prefer a compact storage representation like BINARY(16) over 36-character strings whenever mappings and tooling permit.

### 6.2. Time-Ordered IDs

Time-ordered UUIDs or roughly monotonic distributed IDs improve locality over random UUIDs. For instance, UUIDv7 embeds a leading timestamp so values tend to sort chronologically.

However:

- Not every JPA/Hibernate version ships identical built-in UUIDv7 support.
- Verify ID generation, JDBC mapping, and MySQL column types.
- Do not assume time-ordered IDs reflect exact commit order or replace business timestamps.
- When multiple nodes generate IDs, ensure uniqueness and ordering guarantees match your chosen library.

Never switch to UUIDs solely for batch inserts if your system heavily relies on BIGINT AUTO_INCREMENT and existing indexes. Measure index footprint, insert speed, buffer pool hit rate, and join cost first.

### 6.3. Snowflake or ULID Identifiers

Some systems construct IDs from timestamp, node identifier, and local sequence (e.g., Snowflake) or use ULIDs. These can also be generated prior to INSERT and support batching.

Requirements to evaluate:

- Zero ID collisions across instances, even across node restarts or configuration changes.
- System clocks must be managed if the algorithm relies on timestamps.
- Both Java types and MySQL column types must accommodate the full range.
- ID ordering reflects approximate time, not necessarily transaction commit order.
- Operational procedures for assigning node IDs and resolving duplicate node identifier incidents.

## 7. Comparing Identifier Strategies for Batch Inserts

| Strategy | ID Known Before INSERT? | Hibernate Batch INSERT Support | MySQL Characteristics |
|---|---:|---|---|
| IDENTITY / AUTO_INCREMENT | No | Normally cannot batch via Hibernate identity path | Simple, native, generated key retrieved after INSERT |
| Native SEQUENCE | Yes | Typically batchable | MySQL lacks native sequence objects; provider/dialect may reject or emulate |
| TABLE | Yes, after allocation from generator | Batchable | Uses an allocation table; requires managing contention and block sizes |
| Application-generated UUID | Yes | Batchable | Great for distribution; weigh primary key size and locality |
| Snowflake/ULID/custom ID | Yes | Batchable | Requires uniqueness, node/clock management, and type mapping |

No strategy wins in every scenario. For high insert throughput on MySQL, pre-INSERT ID strategies offer an advantage with Hibernate batching. When simplicity takes priority, IDENTITY remains sensible despite bypassing Hibernate's standard batching path.

## 8. Configuring JDBC Batching in Spring Boot

Hibernate does not enable large batch inserts merely because the application calls saveAll(). You must configure batch sizing.

In Spring Boot, configure in application.yml:

~~~yaml
spring:
  jpa:
    properties:
      hibernate.jdbc.batch_size: 50
      hibernate.order_inserts: true
      hibernate.order_updates: true
~~~

Properties:

- hibernate.jdbc.batch_size: number of statements Hibernate tries to group into a single JDBC batch. Typical starting values are a few dozen, tuned via benchmarks.
- hibernate.order_inserts: sorts INSERTs by entity type and dependency order to maximize grouping of identical statements.
- hibernate.order_updates: sorts UPDATEs to improve batching and in some cases reduce deadlocks.

These are Hibernate-specific properties, not standard JPA settings. Spring Boot forwards them to Hibernate via spring.jpa.properties.

Using properties format:

~~~properties
spring.jpa.properties.hibernate.jdbc.batch_size=50
spring.jpa.properties.hibernate.order_inserts=true
spring.jpa.properties.hibernate.order_updates=true
~~~

### 8.1. Batch Size Is Not Transaction Size

Two distinct concepts are frequently confused:

- **Batch size:** number of statements grouped into one JDBC executeBatch() call.
- **Transaction size:** number of operations committed or rolled back together.

For example, with a batch size of 50 and a transaction inserting 5,000 rows, Hibernate sends roughly 100 batches within that single transaction. The transaction holds all changes until commit.

Oversized transactions bloat undo/redo logs, lock hold durations, rollback times, and replication lag. Tune batch size and transaction size independently for your workload.

### 8.2. Ordering INSERTs

order_inserts=true lets Hibernate reorder INSERTs so statements for the same entity type group together. If a transaction interleaves persisting multiple entity types, ordering increases consecutive batches sharing one prepared statement.

However, reordering changes SQL execution order relative to persist() call order. Never rely on INSERT order to encode business ordering; use foreign keys, transactions, and entity relationships properly.

## 9. Configuring MySQL Connector/J for Batching

Hibernate builds JDBC batches via addBatch() and executeBatch(). MySQL Connector/J offers rewriteBatchedStatements to rewrite eligible batched INSERT/REPLACE statements into multi-value statements, reducing server round-trips.

Example URL:

~~~text
jdbc:mysql://db.internal.example:3306/sales_app?rewriteBatchedStatements=true
~~~

Or in Spring Boot configuration:

~~~yaml
spring:
  datasource:
    url: jdbc:mysql://db.internal.example:3306/sales_app?rewriteBatchedStatements=true
~~~

This property only optimizes batches actually submitted to JDBC by the application/ORM. It cannot turn individual immediate INSERTs sent by Hibernate into ORM batches.

Accordingly, if an entity uses GenerationType.IDENTITY, enabling rewriteBatchedStatements=true alone normally does not bypass the batching limitation caused by Hibernate retrieving keys after each INSERT.

Caveats:

- The driver rewrites batched INSERTs into multi-value INSERTs when statement structure and conditions qualify.
- Verify generated-key retrieval and update-count reporting against your exact Connector/J version.
- Large batches produce large network packets; watch max_allowed_packet, payload sizes, and memory.
- Benchmark with rewrite both enabled and disabled to confirm gains on your actual workload.

Do not confuse rewriteBatchedStatements with useServerPrepStmts. These two properties govern separate aspects of how the driver sends statements; their combination affects the execution path and must be tested.

## 10. Entity Configuration Example with TABLE Generator

Example entity using pre-allocated IDs:

~~~java
import jakarta.persistence.*;

@Entity
@Table(name = "import_item")
public class ImportItem {
    @Id
    @TableGenerator(
        name = "import_item_gen",
        table = "id_generator",
        pkColumnName = "generator_name",
        valueColumnName = "next_value",
        pkColumnValue = "import_item",
        allocationSize = 50
    )
    @GeneratedValue(
        strategy = GenerationType.TABLE,
        generator = "import_item_gen"
    )
    private Long id;

    @Column(nullable = false)
    private String payload;

    protected ImportItem() {
    }

    public ImportItem(String payload) {
        this.payload = payload;
    }
}
~~~

With Hibernate batching configured, INSERTs for ImportItem can be deferred and batched. Block allocation reduces hits to the generator table compared to allocating one ID at a time.

To verify Hibernate is actually batching, inspect SQL logs or JDBC/Hibernate statistics in a test environment. Having a pre-INSERT ID is a necessary condition, though not sufficient on its own: batch size must be positive, INSERTs must be batch-compatible, the transaction must flush appropriately, and nothing else may force immediate execution.

## 11. Bulk Persisting and Managing the Persistence Context

A naive loop:

~~~java
@Transactional
public void importItems(List<String> payloads) {
    for (String payload : payloads) {
        entityManager.persist(new ImportItem(payload));
    }
}
~~~

For small counts, this suffices. For hundreds of thousands of entities, the persistence context retains references to every persisted entity until detached or until the transaction ends, causing heap usage to climb sharply.

Flush and clear per batch:

~~~java
@Transactional
public void importItems(List<String> payloads) {
    int batchSize = 50;
    int count = 0;

    for (String payload : payloads) {
        entityManager.persist(new ImportItem(payload));
        count++;

        if (count % batchSize == 0) {
            entityManager.flush();
            entityManager.clear();
        }
    }

    entityManager.flush();
    entityManager.clear();
}
~~~

- flush() synchronizes pending changes in the persistence context to the database. This is when Hibernate dispatches the JDBC batch.
- clear() detaches all entities from the persistence context, freeing memory retained by the context.
- clear() does not commit the transaction. Flushed INSERTs remain inside the active transaction until commit.

The code above still uses a single transaction for the entire list. For massive datasets, split into multiple independent transactions to bound transaction duration and rollback scope. When splitting transactions, give each chunk a clear commit boundary and retry/idempotency strategy.

Never call clear() before flush() while changes remain unsynchronized, as managed entities would be detached before Hibernate emits the intended SQL.

### 11.1. Chunked Transactions

One clean structure separates a coordinator service from a bean processing each chunk in its own transaction:

~~~java
@Service
public class ImportCoordinator {
    private final ImportChunkWriter chunkWriter;

    public ImportCoordinator(ImportChunkWriter chunkWriter) {
        this.chunkWriter = chunkWriter;
    }

    public void importAll(List<String> values) {
        int chunkSize = 1000;

        for (int start = 0; start < values.size(); start += chunkSize) {
            int end = Math.min(start + chunkSize, values.size());
            chunkWriter.writeChunk(values.subList(start, end));
        }
    }
}

@Service
public class ImportChunkWriter {
    @PersistenceContext
    private EntityManager entityManager;

    @Transactional
    public void writeChunk(List<String> values) {
        int batchSize = 50;
        int count = 0;

        for (String value : values) {
            entityManager.persist(new ImportItem(value));
            count++;

            if (count % batchSize == 0) {
                entityManager.flush();
                entityManager.clear();
            }
        }

        entityManager.flush();
        entityManager.clear();
    }
}
~~~

Two separate beans ensure calls pass through the Spring proxy so @Transactional applies to each chunk. Calling another @Transactional method on the same object via self-invocation bypasses Spring's default transaction proxy.

Chunk size 1,000 and batch size 50 are illustrative values only. Choose them based on commit latency, transaction footprint, replication lag, packet limits, and retry granularity.

## 12. Does saveAll() Guarantee Batch Inserts?

Spring Data JPA provides saveAll() to save an iterable of entities. However, saveAll() does not promise that all INSERTs go out in one JDBC batch.

The outcome depends on:

- Whether each entity is considered new or already existing.
- The entity's identifier strategy.
- Hibernate batch size.
- How transactions and flushes are managed.
- Callbacks, cascades, relationships, and extra SQL triggered.
- Whether the driver supports batch optimizations.

With IDENTITY, Hibernate normally must INSERT immediately to fetch the ID, so saveAll() can still incur one INSERT round-trip per entity.

### 12.1. Note on Self-Assigned IDs with Spring Data JPA

Spring Data JPA must distinguish new entities from existing ones to choose between persist() and merge(). When an entity uses a UUID assigned before save(), the id field is non-null. Under default ID-based newness detection, the entity is treated as existing and routed through merge()—triggering an extra SELECT before INSERT.

You can use a nullable @Version property so Spring Data detects newness by version, or implement Persistable<ID> and supply an appropriate isNew(). Example:

~~~java
import jakarta.persistence.*;
import org.springframework.data.domain.Persistable;
import java.util.UUID;

@Entity
public class ExternalEvent implements Persistable<UUID> {
    @Id
    private UUID id;

    @Version
    private Long version;

    @Transient
    private boolean newEntity = true;

    protected ExternalEvent() {
    }

    public ExternalEvent(UUID id) {
        this.id = id;
    }

    @Override
    public UUID getId() {
        return id;
    }

    @Override
    public boolean isNew() {
        return newEntity;
    }

    @PostPersist
    void markNotNewAfterPersist() {
        newEntity = false;
    }

    @PostLoad
    void markNotNewAfterLoad() {
        newEntity = false;
    }
}
~~~

This is an illustrative pattern; ensure lifecycle callbacks and entity deserialization fit your application. Another option is calling EntityManager.persist() directly when you know the entity is new. Do not let every new entity fall back to merge() merely because an ID was pre-assigned.

## 13. Entity Relationships and INSERT Ordering

When one entity references another via foreign key, Hibernate must preserve SQL ordering compatible with database constraints. For example, creating an Order and its OrderItems:

~~~java
Order order = new Order();
order.addItem(new OrderItem("Keyboard"));
order.addItem(new OrderItem("Mouse"));

entityManager.persist(order);
~~~

Hibernate may have to INSERT the parent before children depending on mappings and cascades. order_inserts=true groups INSERTs by entity type while respecting foreign key dependencies.

A transaction persisting multiple entity types forms multiple batch groups. A batch size of 50 does not mean every 50 consecutive entities in a loop land in a single batch.

Contributing factors:

- Entity types and their respective SQL INSERT statements.
- Generated identifiers and when IDs become available.
- Cascade mappings and dependency order.
- Flush mode and queries that force Hibernate to flush.
- Callbacks or listeners performing extra queries or writes.

Design relationships cleanly and measure actual SQL instead of guessing batch counts solely from collection sizes.

## 14. Batch Inserts with @Version Entities

Optimistic locking uses @Version to detect concurrent updates:

~~~java
@Entity
public class InventoryItem {
    @Id
    private Long id;

    @Version
    private Long version;

    private Integer quantity;
}
~~~

Hibernate can batch UPDATEs on versioned entities if the driver/provider reports accurate update counts. The Hibernate property hibernate.jdbc.batch_versioned_data controls batching of versioned DML in certain configurations/versions. Check defaults and behavior for your Hibernate version before setting it explicitly.

@Version does not replace transactions or constraints. For new inserts, version is normally initialized by the provider; it is not a primary key strategy. During batch updates, Hibernate needs per-statement affected row counts to detect optimistic lock failures.

## 15. Choosing Batch Size and Transaction Size

No single batch size is optimal across all systems. Key factors:

- Network latency between application and MySQL.
- Row width and column count.
- Number of indexes, foreign keys, and triggers on the table.
- max_allowed_packet and batch size after driver rewriting.
- JVM memory and persistence context lifetime.
- Undo/redo, binary logs, and replication topology.
- Lock contention with concurrent transactional workloads.

Start benchmarking with batch sizes of 20, 50, and 100, and measure:

| Metric | What to Observe |
|---|---|
| Rows/second | Effective throughput |
| Batch execution time | Time to send and execute one batch |
| Commit latency | Time to commit the transaction |
| JVM heap | Memory growth with entity count |
| DB CPU and I/O | MySQL load during import |
| Lock waits/deadlocks | Contention with other workloads |
| Replication lag | Delay applying binary logs on replicas |
| Packet/statement size | Whether driver/server limits are approached |

Increasing batch size does not always increase throughput. Oversized batches raise execution and commit durations while making failed transaction retries far costlier.

## 16. Verifying Whether Hibernate Actually Batches

### 16.1. Enable Hibernate Statistics in Test Environments

Enable statistics with:

~~~yaml
spring:
  jpa:
    properties:
      hibernate.generate_statistics: true
~~~

Hibernate Statistics report entity inserts, flushes, prepared statements, and batch metrics depending on version. Never leave verbose SQL logging or heavy statistics enabled continuously in production if it creates log volume or exposes data.

### 16.2. Inspect SQL and JDBC Execution

In a lab environment, enable appropriate logging to verify:

- Whether SQL INSERTs are deferred until flush.
- Whether Hibernate logs batch execution.
- How many statements enter each batch.
- Whether generated keys are fetched after each INSERT or known beforehand.
- Whether the driver rewrites batches into multi-value INSERTs.

Seeing multiple INSERT lines in logs does not automatically prove batching failed: drivers can transmit batches differently at the wire protocol level. Combine Hibernate statistics, driver logs, lab MySQL general logs, or tracing to confirm.

### 16.3. Comparing Two Mappings

Create two comparable entities:

- IdentityItem using GenerationType.IDENTITY.
- TableGeneratedItem using GenerationType.TABLE with block allocation.

Run the exact same data volume, batch size, and transaction size. Record elapsed time, execution counts, ID fetch calls, and MySQL resource usage. Keep schemas and configurations identical aside from the ID strategy so the benchmark remains fair.

## 17. Common Pitfalls and Misconceptions

| Misconception or Error | Reality | Resolution |
|---|---|---|
| Calling saveAll() batches automatically | saveAll() does not guarantee JDBC batching | Configure Hibernate and check ID strategy/SQL |
| Setting batch_size alone is enough | IDENTITY still forces immediate Hibernate INSERTs | Choose pre-INSERT IDs if batching is required |
| rewriteBatchedStatements=true fixes everything | Driver only rewrites JDBC batches actually sent to it | Ensure Hibernate builds JDBC batches first |
| SEQUENCE is always best | MySQL has no native sequence object | Check dialect/provider; consider TABLE or app-assigned IDs |
| UUID is always faster than AUTO_INCREMENT | Random UUIDs bloat and fragment indexes | Measure index size, locality, and throughput |
| flush() means commit | Flush only pushes SQL within the active transaction | Commit according to transaction boundaries |
| clear() rolls back data | Clear detaches entities from persistence context | Clear only after flush when changes must persist |
| Batch size equals transaction size | They are two independent limits | Configure and benchmark separately |
| IDs must be gap-free | Rollbacks, pre-allocation, and concurrency create gaps | Never use primary keys as gap-free business numbers |
| Larger batches always go faster | Packets, memory, locks, and transactions bottleneck | Benchmark incrementally and monitor the server |

## 18. Selection Workflow for MySQL

A practical decision path:

1. For standard CRUD prioritizing simplicity without high-speed import needs, IDENTITY with AUTO_INCREMENT is appropriate.
2. When bulk inserts dominate, evaluate pre-allocated IDs so Hibernate can batch.
3. If integer keys are required, test a TABLE generator with block allocation and measure generator table contention.
4. For distributed ID generation, weigh UUIDs or time-ordered/Snowflake IDs; measure InnoDB index overhead.
5. Tune Hibernate jdbc.batch_size, order_inserts, and Connector/J rewriteBatchedStatements via benchmarks.
6. Separate batch size from transaction size; use flush/clear to bound the persistence context.
7. Test against production-like schemas, indexes, triggers, constraints, and replication.
8. Verify retry and idempotency before running interruptible bulk imports.

## 19. Pre-Deployment Batch Insert Checklist

### ID Strategy

- [ ] Identify whether the entity uses IDENTITY, TABLE, UUID, or application-assigned IDs.
- [ ] Confirm whether IDs are available before INSERT or fetched from MySQL afterward.
- [ ] On MySQL, never assume native SEQUENCE support.
- [ ] If using UUIDs, evaluate column type, index footprint, and locality.
- [ ] If using a TABLE generator, verify allocationSize and cross-instance contention.
- [ ] If using Spring Data JPA with self-assigned IDs, verify new-entity detection.

### Hibernate and JDBC

- [ ] Configure hibernate.jdbc.batch_size.
- [ ] Evaluate hibernate.order_inserts and hibernate.order_updates.
- [ ] Test Connector/J rewriteBatchedStatements where appropriate.
- [ ] Verify whether generated-key retrieval forces immediate INSERT execution.
- [ ] Measure actual batching using statistics/logs in test environments.

### Memory and Transactions

- [ ] Use flush() and clear() per batch when the persistence context grows large.
- [ ] Choose transaction size independently from JDBC batch size.
- [ ] Monitor heap usage, undo/redo, lock waits, and replication lag.
- [ ] Implement checkpoints and idempotency for resumable imports.
- [ ] Never hold transactions or connections open unnecessarily.

## Conclusion

Identifier strategies determine when Hibernate learns the primary key, directly governing whether INSERTs can be deferred and grouped into JDBC batches. On MySQL, IDENTITY/AUTO_INCREMENT is straightforward yet typically prevents Hibernate from batching INSERTs because generated keys arrive only after execution. TABLE generators, UUIDs, or application-assigned IDs supply keys before INSERT to enable batching, trading off generator synchronization overhead or index size and locality. Achieving high throughput requires pairing the right ID strategy with Hibernate and Connector/J tuning, persistence context management, sensible transaction sizing, and benchmarks on production-like workloads.
