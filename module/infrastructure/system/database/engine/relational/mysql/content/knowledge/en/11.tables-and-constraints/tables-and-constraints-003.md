# PRIMARY KEY, UNIQUE, and Row Identification Requirements in InnoDB

Every row in a table needs a clear way to be identified so applications can read, update, delete, and reference it accurately. In MySQL, both `PRIMARY KEY` and `UNIQUE` enforce non-duplication rules, but they carry different semantics and behavior. For InnoDB, the primary key also determines the physical storage organization: it is the clustered index, meaning the index according to which rows are arranged.

Therefore, choosing a primary key is not just picking an ID column name. A wide or frequently changing primary key increases the cost of every secondary index; a table without a primary key still gets an internal identifier generated by InnoDB, but applications cannot rely on that identifier stably. This lesson explains how to choose keys, how InnoDB organizes rows, and how to use `UNIQUE` to enforce business identification rules.

## Learning Objectives

After this lesson, you will be able to:

- Distinguish `PRIMARY KEY`, `UNIQUE`, candidate keys, and surrogate keys.
- Explain the role of the primary key in InnoDB's clustered index.
- Describe how InnoDB selects a clustered index when a table declares no primary key.
- Understand why secondary indexes store primary key information and why wide primary keys increase storage overhead.
- Design single-column keys, composite keys, and scoped unique keys aligned with business rules.
- Handle `NULL` properly in unique indexes and understand how collation affects uniqueness.
- Evaluate `AUTO_INCREMENT`, UUIDs, and natural keys when designing row identifiers.
- Audit existing tables and plan how to add keys to legacy tables.

## 1. Row Identifiers and Key Types

A row identifier is a value or set of values that uniquely identifies a single row. A customer table might use `customer_id`; an order detail table might use the pair `(order_id, line_no)`; a multi-tenant user table might require email to be unique within each tenant.

Terms to distinguish:

| Concept | Meaning |
|---|---|
| Candidate key | Minimal set of columns capable of uniquely identifying a row per business rules |
| Primary key | The candidate key chosen as the table's primary identifier; at most one primary key per table |
| Alternate key | Another candidate key not chosen as the primary key; typically protected with `UNIQUE` |
| Natural key | A key using data with business meaning, such as a country code or SKU |
| Surrogate key | An artificial key carrying no business meaning, such as `BIGINT AUTO_INCREMENT` |
| Composite key | A key composed of multiple columns, such as `(order_id, line_no)` |

A table can have multiple candidate keys, but only one of them is chosen as the primary key. The remaining candidate keys still need protection via unique constraints if business rules forbid duplicates.

For example, a user in a multi-tenant system might be identified internally by `user_id`, while email must be unique per tenant. `user_id` is the primary key, and `(tenant_id, email)` is an alternate key protected by `UNIQUE`.

## 2. How Do PRIMARY KEY and UNIQUE Differ?

`PRIMARY KEY` ensures all key values are unique and cannot be `NULL`. `UNIQUE` also ensures key values do not duplicate according to the index's comparison rules, but MySQL permits `NULL` in a unique column unless the column is declared `NOT NULL`.

| Characteristic | PRIMARY KEY | UNIQUE |
|---|---|---|
| Number per table | At most one | Can have multiple |
| Duplicate values | Disallowed | Disallowed for non-NULL keys per unique index rules |
| NULL | Disallowed | Allowed if the column permits NULL |
| Purpose | Primary row identifier | Enforce additional uniqueness rules |
| Index in InnoDB | Clustered index | Secondary unique index, unless chosen as clustered index when no PK exists |

Example:

```sql
CREATE TABLE app_user (
    user_id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    username VARCHAR(60) NOT NULL,
    email VARCHAR(254) NOT NULL,
    phone VARCHAR(30) NULL,
    PRIMARY KEY (user_id),
    UNIQUE KEY uq_app_user_username (username),
    UNIQUE KEY uq_app_user_email (email),
    UNIQUE KEY uq_app_user_phone (phone)
) ENGINE = InnoDB;
```

In this example, `user_id` is the primary identifier. Username, email, and phone number are guarded by independent unique indexes. `phone` allows `NULL`, so multiple rows can lack a phone number without violating the unique constraint. If the business requires every user to have a unique phone number, declare `phone NOT NULL` after defining the data rule.

### 2.1. UNIQUE Allows Multiple NULLs

In MySQL, `NULL` represents an unknown or missing value. Two `NULL` values are not considered equal in standard comparisons; therefore, a unique index can contain multiple `NULL`s.

```sql
INSERT INTO app_user (username, email, phone)
VALUES
    ('linh01', 'linh01@example.test', NULL),
    ('minh02', 'minh02@example.test', NULL);
```

These two rows are valid despite both having `phone = NULL`. However, attempting to insert the same non-null phone number twice is rejected:

```sql
INSERT INTO app_user (username, email, phone)
VALUES ('hoa03', 'hoa03@example.test', '0901234567');

INSERT INTO app_user (username, email, phone)
VALUES ('nam04', 'nam04@example.test', '0901234567');
```

Assuming `0901234567` was inserted in the first test row, the second insert violates `uq_app_user_phone`.

With a composite unique index, if one or more key components are `NULL`, MySQL can also allow multiple rows sharing that combination containing `NULL`. For example, `UNIQUE (tenant_id, external_code)` does not guarantee only one row per tenant if `external_code` is nullable. If the business rule requires an external code to exist and be unique, declare that column `NOT NULL`.

### 2.2. Composite UNIQUE Scoped by Business Boundaries

A value might not need to be globally unique across the entire system, only unique within a boundary. For example, two different tenants can both use customer code `C001`, but one tenant cannot have two customers with that same code.

```sql
CREATE TABLE tenant_customer (
    customer_id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    tenant_id BIGINT UNSIGNED NOT NULL,
    customer_code VARCHAR(40) NOT NULL,
    customer_name VARCHAR(150) NOT NULL,
    PRIMARY KEY (customer_id),
    UNIQUE KEY uq_tenant_customer_code (tenant_id, customer_code)
) ENGINE = InnoDB;
```

The composite unique index enforces the exact scope: `(tenant_id, customer_code)`. Do not create `UNIQUE(customer_code)` if the code is only unique per tenant, because a global constraint will reject valid codes belonging to other tenants.

### 2.3. Collation Affects String Uniqueness

A unique index on a string column uses the collation's comparison rules. Under a case-insensitive collation, `Admin` and `admin` may be treated as the same value. Under an accent-insensitive collation, differently accented strings can compare equal according to that collation's rules.

```sql
CREATE TABLE login_name_demo (
    login_name VARCHAR(80)
        CHARACTER SET utf8mb4
        COLLATE utf8mb4_0900_ai_ci
        NOT NULL,
    UNIQUE KEY uq_login_name (login_name)
) ENGINE = InnoDB;
```

In MySQL 8.0, the `utf8mb4_0900_ai_ci` collation is accent-insensitive and case-insensitive. Therefore, verify comparison rules before choosing a collation for emails, usernames, identifiers, or SKUs. Collation does not only affect `ORDER BY`; it also determines whether two values are considered duplicates in a unique index.

## 3. InnoDB Uses PRIMARY KEY as the Clustered Index

InnoDB stores row data inside the B-tree structure of the clustered index. When a table has a primary key, the primary key is the clustered index: entries in the B-tree's leaf pages contain the row data and are organized by the primary key.

This differs from the mental model some people hold where a table is a separate data heap and all indexes merely point to fixed physical slots. In InnoDB, a secondary index locates the secondary key value along with the primary key information needed to locate the corresponding row in the clustered index.

```text
                  PRIMARY KEY B-tree
              (InnoDB's clustered index)
                         |
             +-----------+-----------+
             |                       |
          Leaf page               Leaf page
         [PK + data]             [PK + data]

        SECONDARY INDEX: uq_email
             [email, PK]
                   |
                   +------> look up row by PK
```

Table example:

```sql
CREATE TABLE customer_account (
    account_id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    email VARCHAR(254) NOT NULL,
    display_name VARCHAR(120) NOT NULL,
    created_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    PRIMARY KEY (account_id),
    UNIQUE KEY uq_customer_account_email (email),
    KEY idx_customer_account_created_at (created_at)
) ENGINE = InnoDB;
```

`PRIMARY KEY(account_id)` is the clustered index. `uq_customer_account_email` and `idx_customer_account_created_at` are secondary indexes. When looking up an email via the unique index, InnoDB finds the email entry and then uses the `account_id` stored in that entry to read the row from the clustered index.

## 4. What Does InnoDB Do When a Table Has No PRIMARY KEY?

InnoDB still needs a clustered index to organize rows. When a table is created without declaring a primary key, InnoDB searches for a unique index where all component columns are `NOT NULL` to serve as the clustered index. If no suitable unique index exists, InnoDB automatically generates a hidden clustered index with an internal 6-byte row ID; this index is commonly referred to as `GEN_CLUST_INDEX`.

This means a table without a primary key does not lack an internal identifier. However, the hidden row ID generated by InnoDB is not an SQL column that applications can query, store in other tables, or use as a stable identification contract. Applications cannot issue `SELECT hidden_row_id ...` to identify rows.

Example of a table without a primary key or suitable unique key:

```sql
CREATE TABLE raw_import_row (
    source_name VARCHAR(80) NOT NULL,
    source_record_code VARCHAR(80) NULL,
    payload JSON NOT NULL,
    imported_at DATETIME(6) NOT NULL
) ENGINE = InnoDB;
```

This table has no primary key and no unique index whose columns are all `NOT NULL`. InnoDB creates a hidden clustered index to organize the data. Yet if two rows share the same `source_name`, `source_record_code`, and `payload`, the application has no declared key to distinguish them reliably.

### 4.1. Clustered Index Selection Order

In principle, InnoDB chooses in this order:

1. Use `PRIMARY KEY` if the table declares one.
2. If there is no primary key, use the first unique index in which every component column is `NOT NULL`.
3. If no suitable key exists, create a hidden clustered index on an internal 6-byte row ID.

If InnoDB uses a unique key as the clustered index, that key must satisfy the `NOT NULL` condition on all its columns. A unique index allowing `NULL` is ineligible under this rule.

## 5. Secondary Indexes Store Primary Key Information

A critical characteristic of InnoDB is that every entry in a secondary index stores the secondary key columns plus the row's primary key. The primary key is used to locate the row in the clustered index. Consequently, the width of the primary key affects every secondary index on the table.

Example of a table with a `BIGINT` primary key and three secondary indexes:

```sql
CREATE TABLE support_ticket (
    ticket_id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    tenant_id BIGINT UNSIGNED NOT NULL,
    ticket_code VARCHAR(40) NOT NULL,
    status VARCHAR(20) NOT NULL,
    created_at DATETIME(6) NOT NULL,
    PRIMARY KEY (ticket_id),
    UNIQUE KEY uq_ticket_tenant_code (tenant_id, ticket_code),
    KEY idx_ticket_tenant_status (tenant_id, status),
    KEY idx_ticket_created_at (created_at)
) ENGINE = InnoDB;
```

The secondary indexes must carry enough `ticket_id` primary key data to identify the row. If the primary key is a long string or spans many columns, the appended primary key makes indexes larger, reduces the number of entries per page, and increases read/write I/O.

Therefore, an InnoDB primary key should generally be:

- Compact, to keep secondary index sizes small.
- Stable, rarely or never changing after row creation.
- Always present (`NOT NULL`).
- Generated under a uniqueness rule and suitable for foreign key references from other tables.
- Typed appropriately for expected scale, avoiding overly narrow types that risk value exhaustion.

This is why `BIGINT` or `INT` surrogate keys are commonly used as primary keys for transactional tables with multiple secondary indexes. That does not mean every table must use `AUTO_INCREMENT`; composite or natural keys remain appropriate when they accurately reflect the data model.

## 6. Choosing a Natural Key or a Surrogate Key?

A natural key is data that already carries business meaning, such as a passport number, SKU, or country code. A surrogate key is a system-generated technical identifier, such as `BIGINT AUTO_INCREMENT`.

| Criterion | Natural Key | Surrogate Key |
|---|---|---|
| Meaning | Carries business meaning | Carries no business meaning |
| Stability | May change with business rules | Typically stable if designed properly |
| Width | Can be a long string or multi-column | Typically small and fixed-width |
| Uniqueness | Requires constraints per business rules | Requires an ID generator and primary key |
| Integration | Convenient when external sources have standard codes | Convenient for internal references |

A common design uses a surrogate key as the primary key while enforcing the natural key with a unique constraint:

```sql
CREATE TABLE product_catalog (
    product_id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    sku VARCHAR(40) NOT NULL,
    product_name VARCHAR(160) NOT NULL,
    PRIMARY KEY (product_id),
    UNIQUE KEY uq_product_catalog_sku (sku)
) ENGINE = InnoDB;
```

`product_id` is the stable internal identifier. `sku` remains unique per catalog rules, but if the business changes an SKU code, foreign keys across all tables referencing `product_id` do not need updating.

A surrogate key is not always better. For a junction table representing a many-to-many relationship, the pair of foreign keys can itself be the row's natural identifier:

```sql
CREATE TABLE student_course (
    student_id BIGINT UNSIGNED NOT NULL,
    course_id BIGINT UNSIGNED NOT NULL,
    enrolled_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    PRIMARY KEY (student_id, course_id),
    KEY idx_student_course_course (course_id)
) ENGINE = InnoDB;
```

Each row represents a single enrollment of one student in one course, so `(student_id, course_id)` is the natural composite key. If the business allows multiple enrollments or stores history across terms, add a component such as `enrollment_no` or use a surrogate key alongside a unique constraint reflecting the exact rule.

## 7. Designing Composite Keys and Column Order

A primary key can consist of multiple columns. With composite keys, column order affects the clustered index ordering and which queries can leverage the index's leftmost prefix.

Order detail example:

```sql
CREATE TABLE order_line (
    order_id BIGINT UNSIGNED NOT NULL,
    line_no SMALLINT UNSIGNED NOT NULL,
    product_id BIGINT UNSIGNED NOT NULL,
    quantity INT UNSIGNED NOT NULL,
    unit_price DECIMAL(12,2) NOT NULL,
    PRIMARY KEY (order_id, line_no),
    KEY idx_order_line_product (product_id)
) ENGINE = InnoDB;
```

The key `(order_id, line_no)` identifies which line number within the order. This index serves well for:

```sql
SELECT *
FROM order_line
WHERE order_id = 9001;

SELECT *
FROM order_line
WHERE order_id = 9001
  AND line_no = 2;
```

However, it is not equivalent to an index starting with `line_no` for queries filtering solely by `line_no`. With a clustered index, primary key order is also the physical data organization order; choosing column order to match common access patterns can improve locality and range scan efficiency.

If a child table references a composite key, declare the foreign key in the exact same column order and with compatible data types:

```sql
CREATE TABLE order_line_note (
    order_id BIGINT UNSIGNED NOT NULL,
    line_no SMALLINT UNSIGNED NOT NULL,
    note_text VARCHAR(500) NOT NULL,
    PRIMARY KEY (order_id, line_no),
    CONSTRAINT fk_order_line_note_line
        FOREIGN KEY (order_id, line_no)
        REFERENCES order_line (order_id, line_no)
) ENGINE = InnoDB;
```

Referencing columns must match in type and signedness (`SIGNED`/`UNSIGNED`); for strings, check charset/collation compatibility. InnoDB requires a suitable index for foreign keys. MySQL can auto-create an index on the child table if a suitable one does not exist, though explicitly declaring and naming indexes makes schema administration easier.

## 8. AUTO_INCREMENT: Convenient, Not a Gapless Sequence

`AUTO_INCREMENT` is a common way to generate integer surrogate keys:

```sql
CREATE TABLE payment_attempt (
    attempt_id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    order_id BIGINT UNSIGNED NOT NULL,
    attempted_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    PRIMARY KEY (attempt_id),
    KEY idx_payment_attempt_order (order_id)
) ENGINE = InnoDB;
```

When inserting, you can omit `attempt_id` so MySQL assigns a value:

```sql
INSERT INTO payment_attempt (order_id)
VALUES (9001), (9002), (9003);
```

Never treat `AUTO_INCREMENT` as a gapless sequential counter. Gaps can occur due to transaction rollbacks, failed inserts, deletions, concurrent allocations, or how the server manages counters. Do not use IDs to infer row counts, contiguous invoice numbers, or exact commit order.

If you need to read by time or creation order, use `ORDER BY attempted_at, attempt_id`. Without `ORDER BY`, SQL does not guarantee result order; clustered index order is not a query sorting contract.

`AUTO_INCREMENT` also has numeric type limits. Choose `INT` or `BIGINT` based on growth rate and table lifespan. For high-scale transactional systems, `BIGINT UNSIGNED` offers a far larger value range, though referencing foreign keys must match that type consistently.

## 9. UUIDs and Distributed Keys

In multi-service systems or when IDs must be generated across multiple nodes without waiting for a central database allocator, UUIDs can be an option. A 36-character text UUID is considerably wider than `BIGINT`; storing long strings as primary keys enlarges both the clustered index and all secondary indexes.

If using UUIDs, consider:

- Storing them in 16-byte binary form (`BINARY(16)`) instead of 36-character text strings if your application and tooling handle it cleanly.
- Standardizing the UUID version and byte ordering across services.
- Evaluating time-ordered locality of the UUID; random UUIDs scatter inserts across many pages, increasing page splits and reducing locality compared to monotonically increasing keys.
- Not sacrificing uniqueness or stability solely for index optimization; measure the real workload.

MySQL provides `UUID_TO_BIN()` and `BIN_TO_UUID()` to convert UUIDs. The swap flag parameter of `UUID_TO_BIN()` must be used consistently between writes and reads; never mix UUIDs converted in two different ways.

```sql
CREATE TABLE distributed_event (
    event_id BINARY(16) NOT NULL,
    event_type VARCHAR(60) NOT NULL,
    occurred_at DATETIME(6) NOT NULL,
    PRIMARY KEY (event_id),
    KEY idx_distributed_event_time (occurred_at)
) ENGINE = InnoDB;

INSERT INTO distributed_event (event_id, event_type, occurred_at)
VALUES (UUID_TO_BIN(UUID()), 'ORDER_CREATED', CURRENT_TIMESTAMP(6));
```

The snippet above illustrates storing UUIDs in binary form. Before choosing random UUIDs as a clustered key for a write-heavy table, compare against sequential ID strategies or time-ordered UUIDs.

## 10. Inspecting Existing Keys and Indexes

To view the full table definition:

```sql
SHOW CREATE TABLE customer_account;
```

To view indexes and their component columns:

```sql
SHOW INDEX FROM customer_account;
```

Columns commonly inspected in `SHOW INDEX` output:

| Column | Meaning |
|---|---|
| `Key_name` | Index name; `PRIMARY` indicates the primary key |
| `Non_unique` | `0` if unique, `1` if non-unique |
| `Seq_in_index` | Column position in a composite index |
| `Column_name` | Column participating in the index |
| `Sub_part` | Prefix length if only a column prefix is indexed |
| `Index_type` | Index type, usually `BTREE` for standard InnoDB indexes |

You can inventory indexes via `INFORMATION_SCHEMA.STATISTICS`:

```sql
SELECT
    TABLE_NAME,
    INDEX_NAME,
    NON_UNIQUE,
    SEQ_IN_INDEX,
    COLUMN_NAME,
    SUB_PART,
    INDEX_TYPE
FROM information_schema.statistics
WHERE TABLE_SCHEMA = DATABASE()
  AND TABLE_NAME = 'customer_account'
ORDER BY INDEX_NAME, SEQ_IN_INDEX;
```

To verify storage engine and estimate sizes:

```sql
SELECT
    TABLE_NAME,
    ENGINE,
    ROW_FORMAT,
    TABLE_ROWS,
    DATA_LENGTH,
    INDEX_LENGTH
FROM information_schema.tables
WHERE TABLE_SCHEMA = DATABASE()
  AND TABLE_NAME = 'customer_account';
```

`TABLE_ROWS` in InnoDB is normally an estimate. When an exact row count is needed, use `COUNT(*)` and evaluate the cost on large tables.

## 11. Handling Duplicate Key Errors and Upserts

When inserting a value that already exists in a primary key or unique index, MySQL returns a duplicate key error. This is the database-level safeguard for uniqueness, even under concurrent writes from multiple requests.

Do not rely on checking first with `SELECT` and then running `INSERT`, assuming duplicates cannot happen. Two transactions can both see no existing row before either inserts; the unique index is the final line of defense.

If business logic permits updating when a key already exists, use `INSERT ... ON DUPLICATE KEY UPDATE`:

```sql
INSERT INTO product_catalog (sku, product_name)
VALUES ('KB-001', 'Mechanical Keyboard')
ON DUPLICATE KEY UPDATE
    product_name = VALUES(product_name);
```

In MySQL 8.0.20 and later, using `VALUES(column)` in the update clause is deprecated; the row alias syntax is recommended for modern versions:

```sql
INSERT INTO product_catalog (sku, product_name)
VALUES ('KB-001', 'Mechanical Keyboard') AS new
ON DUPLICATE KEY UPDATE
    product_name = new.product_name;
```

Choose the right semantics: an upsert can update a row whenever any primary or unique key collides. If a table has multiple unique constraints, understand which keys can trigger the update branch and avoid letting two business rules accidentally update the wrong row.

`INSERT IGNORE` can downgrade certain errors to warnings and skip violating rows, but it can also mask invalid data. Only use it when ingestion policy clearly defines how duplicate records should be handled and the application checks the skipped row count.

## 12. Adding Keys to Legacy Tables

An older table might lack a primary key because it originated from file imports, logs, or legacy applications. Before adding keys, identify the business identifier and inspect existing data.

### 12.1. Finding Duplicate Rows for a Planned Key

Suppose you plan to use `source_name` and `source_record_code` as a unique key:

```sql
SELECT
    source_name,
    source_record_code,
    COUNT(*) AS duplicate_count
FROM legacy_import
WHERE source_name IS NOT NULL
  AND source_record_code IS NOT NULL
GROUP BY source_name, source_record_code
HAVING COUNT(*) > 1;
```

Check for null values:

```sql
SELECT COUNT(*) AS rows_with_missing_key
FROM legacy_import
WHERE source_name IS NULL
   OR source_record_code IS NULL;
```

If the planned key is a mandatory identifier, resolve duplicate and missing rows before creating the unique constraint. Do not blindly delete duplicate rows just to make DDL succeed; determine which row is canonical, whether records can be merged, or whether history must be preserved.

### 12.2. Adding a Surrogate Key

If no stable natural key exists, you can add a surrogate column:

```sql
ALTER TABLE legacy_import
    ADD COLUMN import_row_id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    ADD PRIMARY KEY (import_row_id);
```

Before running it, verify that the table has no existing primary key, the new column does not already exist, and the server version/engine supports the planned alteration. On large tables, this operation may rebuild the clustered index, consume I/O, and acquire locks; test on a replica/copy and schedule a maintenance window.

Once a primary key is in place, consider adding a unique constraint for the source key if business rules require it:

```sql
ALTER TABLE legacy_import
    ADD UNIQUE KEY uq_legacy_import_source_record
        (source_name, source_record_code);
```

Only add the unique constraint after cleaning duplicates and nulls according to business rules.

## 13. Key Design Principles for InnoDB

When creating new tables, evaluate the following principles:

**Choose an explicit primary key.** Never leave InnoDB to fall back on a hidden row ID if applications need to update, delete, reference, or sync individual rows.

**Prefer short and stable keys.** The primary key is carried inside every secondary index. The wider the key, the higher the storage and I/O cost of secondary indexes.

**Separate technical identifiers from business rules when needed.** Use a surrogate key as the primary key and unique constraints for emails, SKUs, or external codes if they must be unique.

**Set NOT NULL on mandatory identifier components.** Especially in composite unique keys, `NULL` can permit duplicate-looking combinations that the designer assumed were prevented.

**Order columns in composite keys based on queries and relationships.** Column order governs leftmost prefix matching, clustered data order, and how child tables reference the key.

**Synchronize data types across foreign keys.** Referencing columns need compatible types, including numeric signedness and string attributes.

**Do not infer order from IDs without ORDER BY.** When ordering is required, sort explicitly by timestamp and a unique key as a tie-breaker.

**Do not treat AUTO_INCREMENT as a contiguous sequence.** If the business requires gapless document numbers, that requires a dedicated numbering process with concurrency control and audit rules.

## 14. Checklist Before Finalizing PRIMARY KEY and UNIQUE

- Identified candidate keys and uniqueness rules within their business scope.
- Selected a non-null, unique, and stable primary key.
- Considered primary key width because InnoDB includes the primary key in secondary indexes.
- Decided whether a natural key or surrogate key fits the data lifecycle.
- Verified whether unique keys should allow `NULL` or require `NOT NULL`.
- Checked string column collations to understand exact duplicate comparison rules.
- Ordered composite key columns according to queries and referencing relationships.
- Matched data types between primary and foreign keys.
- Verified the table has a true primary key via `SHOW CREATE TABLE`.
- Understood that InnoDB falls back to an eligible unique key or hidden row ID if a primary key is missing.
- Audited duplicates and nulls before adding unique constraints to existing data.
- Assessed locking, disk space, and duration impacts when altering clustered indexes on large tables.

In InnoDB, the primary key serves as both the logical row identifier and the clustered index organizing data. Secondary indexes rely on the primary key to locate rows, so a compact, stable, and intentionally chosen primary key reduces storage and access overhead. `UNIQUE` protects additional candidate keys, though you must understand how MySQL handles `NULL` and collations. When both key types are designed around business rules and workload, tables gain clear identification, reliable relationships, and easier optimization.
