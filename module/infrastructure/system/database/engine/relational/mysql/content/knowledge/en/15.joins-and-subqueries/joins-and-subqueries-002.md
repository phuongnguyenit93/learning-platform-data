# LEFT/RIGHT OUTER JOIN and Unmatched Rows

In a relational database, a row in one table may have no corresponding row in another table. A department might not have any employees yet; an employee might not be assigned to a department yet; or a foreign key reference might hold a value whose parent record is missing due to bad data imports. If you use `INNER JOIN`, those unmatched rows vanish from the result. `LEFT OUTER JOIN` and `RIGHT OUTER JOIN` allow you to preserve rows on one side and represent the missing match with `NULL` on the other side.

In MySQL, the `OUTER` keyword is optional: `LEFT JOIN` is equivalent to `LEFT OUTER JOIN`, and `RIGHT JOIN` is equivalent to `RIGHT OUTER JOIN`. `LEFT JOIN` preserves all rows from the left table; `RIGHT JOIN` preserves all rows from the right table. Knowing precisely which table is preserved, which conditions belong in `ON` versus `WHERE`, and how to detect unmatched rows is foundational for writing reports, finding orphaned data, and auditing data quality.

This lesson belongs to the `DATABASE_MYSQL` module, where you practice table design, data types, keys, SQL queries, indexes, transactions, concurrency control, reading execution plans, and query optimization. The goal is to write semantically accurate outer joins when relationships may be missing, while avoiding accidentally turning an outer join into an inner join or multiplying rows through one-to-many relationships.

After this lesson, you will be able to:

- Explain the difference between `INNER JOIN`, `LEFT JOIN`, and `RIGHT JOIN`.
- Identify the preserved side and the side that can be `NULL`-extended.
- Place conditions in `ON` or `WHERE` according to business requirements.
- Find records without a matching entity using `LEFT JOIN ... IS NULL` and `NOT EXISTS`.
- Distinguish a `NULL` foreign key from a non-existent referenced key.
- Count rows accurately after an outer join and handle one-to-many relationships.
- Write `RIGHT JOIN` queries, convert them to equivalent `LEFT JOIN` queries, and understand how to simulate `FULL OUTER JOIN` in MySQL.
- Inspect indexes and execution plans for outer joins.

## 1. What Problem Does Outer Join Solve?

Suppose a system has `departments` and `employees` tables. Some departments have multiple employees, while others have none. In addition, an employee may not be assigned to any department yet, or may have a `department_id` pointing to a non-existent department ID.

If the question is "List all departments and the employees belonging to each department," `INNER JOIN` returns only departments with matching employees. Departments without employees are excluded from the result. `LEFT JOIN` keeps every department and sets the employee columns to `NULL` when there is no matching employee.

If the question is "List all employees and their departments if any," you need to preserve every employee. You can use `RIGHT JOIN` with `departments` on the left and `employees` on the right, or swap the table order to use `LEFT JOIN`.

| JOIN Type | Fully Preserved Rows | When No Matching Row Exists |
| --- | --- | --- |
| `INNER JOIN` | Only matching row pairs | Unmatched rows are discarded |
| `LEFT JOIN` | Left table | Right-side columns are set to `NULL` |
| `RIGHT JOIN` | Right table | Left-side columns are set to `NULL` |

An outer join does not create a real record in the missing table. The `NULL` values in the result are synthetic extension columns generated by the join operation to preserve rows on the retained side.

## 2. Creating a Fixture to Observe Matched and Unmatched Rows

Run this example within the same MySQL session. We do not declare a foreign key in this fixture because we intentionally want to insert an employee with a non-existent `department_id` to inspect orphaned data.

```sql
DROP TEMPORARY TABLE IF EXISTS employees;
DROP TEMPORARY TABLE IF EXISTS departments;

CREATE TEMPORARY TABLE departments (
    department_id INT UNSIGNED NOT NULL,
    department_name VARCHAR(100) NOT NULL,
    PRIMARY KEY (department_id)
) ENGINE = InnoDB;

CREATE TEMPORARY TABLE employees (
    employee_id INT UNSIGNED NOT NULL,
    employee_name VARCHAR(100) NOT NULL,
    department_id INT UNSIGNED NULL,
    is_active TINYINT(1) NOT NULL DEFAULT 1,
    PRIMARY KEY (employee_id),
    KEY idx_employees_department (department_id)
) ENGINE = InnoDB;

INSERT INTO departments (department_id, department_name) VALUES
(10, 'Engineering'),
(20, 'Sales'),
(30, 'Legal'),
(40, 'Operations');

INSERT INTO employees (employee_id, employee_name, department_id, is_active) VALUES
(1, 'An',     10, 1),
(2, 'Binh',   10, 1),
(3, 'Chi',    20, 1),
(4, 'Dung', NULL, 1),
(5, 'Em',     99, 1),
(6, 'Giang',  20, 0);
```

Cases represented in the fixture:

| Record | Meaning |
| --- | --- |
| Department 10 | Has two active employees |
| Department 20 | Has one active employee and one inactive employee |
| Departments 30 and 40 | Have no employees |
| Employee 4 | `department_id IS NULL`, not yet assigned to a department |
| Employee 5 | `department_id = 99`, but department 99 does not exist |
| Employee 6 | Valid department, but `is_active = 0` |

The fixture distinguishes three states that are often conflated: no reference key (`NULL`), a reference key whose parent record is missing (orphan key), and a valid relationship.

## 3. LEFT JOIN — Preserving All Rows on the Left

Syntax:

```sql
SELECT select_list
FROM left_table AS l
LEFT [OUTER] JOIN right_table AS r
    ON join_condition;
```

With `LEFT JOIN`, every row from `left_table` appears at least once. If a left-side row has one or more right-side rows satisfying `ON`, the result contains one row per matching pair. If there is no matching right-side row, MySQL emits a result row with all right-side columns set to `NULL`.

Example listing all departments and their employees:

```sql
SELECT
    d.department_id,
    d.department_name,
    e.employee_id,
    e.employee_name
FROM departments AS d
LEFT JOIN employees AS e
    ON e.department_id = d.department_id
ORDER BY d.department_id, e.employee_id;
```

Expected result:

| department_id | department_name | employee_id | employee_name |
| ---: | --- | ---: | --- |
| 10 | Engineering | 1 | An |
| 10 | Engineering | 2 | Binh |
| 20 | Sales | 3 | Chi |
| 20 | Sales | 6 | Giang |
| 30 | Legal | `NULL` | `NULL` |
| 40 | Operations | `NULL` | `NULL` |

Employees 4 and 5 do not appear because the query preserves all departments, not all employees. This is the first thing to decide before choosing which table goes on the left or right.

### 3.1. One Left Row Matching Multiple Right Rows

Department 10 appears twice because it has two employees. `LEFT JOIN` does not collapse child rows into a single row. If you want one row per department, use an appropriate aggregate or subquery:

```sql
SELECT
    d.department_id,
    d.department_name,
    COUNT(e.employee_id) AS employee_count
FROM departments AS d
LEFT JOIN employees AS e
    ON e.department_id = d.department_id
GROUP BY d.department_id, d.department_name
ORDER BY d.department_id;
```

The result has four departments, with employee counts of 2, 2, 0, and 0 respectively. Here `COUNT(e.employee_id)` counts the primary key of the right-side row. For departments with no employees, the padded `employee_id` column is `NULL`, so the count is 0.

## 4. RIGHT JOIN — Preserving All Rows on the Right

Syntax:

```sql
SELECT select_list
FROM left_table AS l
RIGHT [OUTER] JOIN right_table AS r
    ON join_condition;
```

With `RIGHT JOIN`, every row of the right table is preserved. If no left-side row matches, columns from the left table receive `NULL`.

Example: listing every employee and their department if any:

```sql
SELECT
    d.department_id,
    d.department_name,
    e.employee_id,
    e.employee_name,
    e.department_id AS employee_department_id
FROM departments AS d
RIGHT JOIN employees AS e
    ON e.department_id = d.department_id
ORDER BY e.employee_id;
```

Expected result:

| department_id | department_name | employee_id | employee_name | employee_department_id |
| ---: | --- | ---: | --- | ---: |
| 10 | Engineering | 1 | An | 10 |
| 10 | Engineering | 2 | Binh | 10 |
| 20 | Sales | 3 | Chi | 20 |
| `NULL` | `NULL` | 4 | Dung | `NULL` |
| `NULL` | `NULL` | 5 | Em | 99 |
| 20 | Sales | 6 | Giang | 20 |

Employees 4 and 5 still appear because `employees` is on the preserved right side. Employee 4 has no department ID yet; employee 5 has ID 99 but no matching department row.

### 4.1. Rewriting RIGHT JOIN as LEFT JOIN

The query above can be rewritten by swapping the order of the two tables:

```sql
SELECT
    d.department_id,
    d.department_name,
    e.employee_id,
    e.employee_name,
    e.department_id AS employee_department_id
FROM employees AS e
LEFT JOIN departments AS d
    ON d.department_id = e.department_id
ORDER BY e.employee_id;
```

Both queries have the exact same meaning and result set. Many engineering teams prefer `LEFT JOIN` because it reads naturally from the table being fully preserved to the supplemental table. However, `RIGHT JOIN` remains valid MySQL syntax; what matters is accurately understanding which side is preserved.

## 5. Distinguishing ON vs. WHERE in Outer Joins

This is the most error-prone part of using outer joins. Conditions in `ON` determine which rows are considered a match. Conditions in `WHERE` filter the result after the join has already generated `NULL`-padded rows for the unmatched side.

### 5.1. Keeping All Departments While Matching Only Active Employees

Requirement: list all departments; match only employees where `is_active = 1`.

```sql
SELECT
    d.department_id,
    d.department_name,
    e.employee_id,
    e.employee_name
FROM departments AS d
LEFT JOIN employees AS e
    ON e.department_id = d.department_id
   AND e.is_active = 1
ORDER BY d.department_id, e.employee_id;
```

The result still includes all four departments. Department 20 only matches employee 3; employee 6 fails the condition in `ON` and is not matched. Departments 30 and 40 have no active employees, so their employee columns are `NULL`.

### 5.2. Moving the Condition to WHERE Drops Unmatched Rows

```sql
SELECT
    d.department_id,
    d.department_name,
    e.employee_id,
    e.employee_name
FROM departments AS d
LEFT JOIN employees AS e
    ON e.department_id = d.department_id
WHERE e.is_active = 1
ORDER BY d.department_id, e.employee_id;
```

For departments 30 and 40, `e.is_active` is `NULL`; the condition `NULL = 1` does not evaluate to `TRUE`, so those rows are filtered out. The result no longer preserves all departments. This `WHERE` condition makes the query behave like an inner join with respect to the active-status filter.

Rule of thumb:

- To keep all rows from the preserved side and only restrict which rows match on the other side: place the matching condition in `ON`.
- To eliminate preserved-side rows as well when a condition is not met: place the condition in `WHERE`.
- Never move conditions between `ON` and `WHERE` without re-verifying the expected result.

### 5.3. WHERE Conditions on the Preserved Side

A `WHERE` condition on the left table of a `LEFT JOIN` filters left-side rows normally:

```sql
SELECT d.department_id, d.department_name, e.employee_name
FROM departments AS d
LEFT JOIN employees AS e
    ON e.department_id = d.department_id
WHERE d.department_id IN (10, 20);
```

The result keeps only departments 10 and 20. That does not undermine outer join semantics for the two remaining departments in the selected set; the left table is still preserved after its filter is applied.

With `RIGHT JOIN`, the same principle applies, except the preserved side is the right table. To preserve all employees, place optional department-filtering conditions in `ON`; putting department-column conditions in `WHERE` can discard employees without a matching department.

## 6. Finding Records Without a Matching Row

A common use of outer joins is finding rows in one table that have no related row in another table. This is commonly called an anti-join.

### 6.1. Departments with No Employees

```sql
SELECT
    d.department_id,
    d.department_name
FROM departments AS d
LEFT JOIN employees AS e
    ON e.department_id = d.department_id
WHERE e.employee_id IS NULL
ORDER BY d.department_id;
```

Expected result: departments 30 and 40. `employee_id` is a primary key and cannot be `NULL` in a real row. Therefore, when it is `NULL` in the outer join result, we know no employee row matched.

### 6.2. Using NOT EXISTS

The same requirement can be written using `NOT EXISTS`:

```sql
SELECT d.department_id, d.department_name
FROM departments AS d
WHERE NOT EXISTS (
    SELECT 1
    FROM employees AS e
    WHERE e.department_id = d.department_id
)
ORDER BY d.department_id;
```

`NOT EXISTS` directly states that no corresponding child row exists. It does not need to construct `NULL`-padded rows only to filter them away afterward. The MySQL optimizer can transform certain queries of this shape into an anti-join; verify with `EXPLAIN` on your actual query and MySQL version.

`NOT EXISTS` is generally safer than `NOT IN` when the subquery set may contain `NULL`, because a single `NULL` value in the subquery can cause `NOT IN` to evaluate to `UNKNOWN`.

### 6.3. Choosing the Right Column for the IS NULL Check

When using `LEFT JOIN ... WHERE right_column IS NULL`, the checked column must be guaranteed `NOT NULL` in any real row—typically the primary key or a `NOT NULL` unique key.

Avoid writing:

```sql
SELECT e.employee_id, e.employee_name
FROM employees AS e
LEFT JOIN departments AS d
    ON d.department_id = e.department_id
WHERE d.department_name IS NULL;
```

This query could pick up both unmatched rows and rows matching a department where `department_name` happens to allow `NULL` in another schema. In the current fixture `department_name` is `NOT NULL`, yet checking the primary key still expresses the anti-join intent more cleanly:

```sql
WHERE d.department_id IS NULL
```

## 7. Distinguishing NULL Foreign Keys from Orphan Keys

In the `employees` table, there are two distinct cases:

- Employee 4 has `department_id IS NULL`: no department has been assigned yet.
- Employee 5 has `department_id = 99`: a reference code exists, but department 99 does not.

To find all employees not matched to a valid department:

```sql
SELECT e.employee_id, e.employee_name, e.department_id
FROM employees AS e
LEFT JOIN departments AS d
    ON d.department_id = e.department_id
WHERE d.department_id IS NULL
ORDER BY e.employee_id;
```

The result includes employees 4 and 5.

To classify the two cases explicitly:

```sql
SELECT
    e.employee_id,
    e.employee_name,
    e.department_id,
    CASE
        WHEN e.department_id IS NULL THEN 'NOT_ASSIGNED'
        WHEN d.department_id IS NULL THEN 'ORPHAN_REFERENCE'
        ELSE 'MATCHED'
    END AS relation_status
FROM employees AS e
LEFT JOIN departments AS d
    ON d.department_id = e.department_id
ORDER BY e.employee_id;
```

Classification result:

| employee_id | relation_status |
| ---: | --- |
| 1 | MATCHED |
| 2 | MATCHED |
| 3 | MATCHED |
| 4 | NOT_ASSIGNED |
| 5 | ORPHAN_REFERENCE |
| 6 | MATCHED |

In production schemas, foreign keys can prevent new orphan keys from being created. However, a nullable foreign key column can still hold `NULL` unless declared `NOT NULL`; `NULL` usually indicates no relationship is specified. Outer joins are useful for auditing legacy data, imported datasets, or schemas lacking referential constraints.

## 8. COUNT and Aggregates After Outer Joins

An outer join creates padded rows for the unmatched side. Choosing the right counting expression is therefore critical.

```sql
SELECT
    d.department_id,
    d.department_name,
    COUNT(*) AS joined_rows,
    COUNT(e.employee_id) AS employee_count,
    COUNT(e.department_id) AS non_null_department_values
FROM departments AS d
LEFT JOIN employees AS e
    ON e.department_id = d.department_id
GROUP BY d.department_id, d.department_name
ORDER BY d.department_id;
```

For departments 30 and 40:

- `COUNT(*) = 1` because the department row still appears in the join result.
- `COUNT(e.employee_id) = 0` because no real employee matched.
- `COUNT(e.department_id) = 0` because the right-side column in the padded row is `NULL`.

When counting employees, use `COUNT(e.employee_id)` because `employee_id` is a non-nullable primary key. If you use `COUNT(*)`, every department with zero employees gets counted as one row.

### 8.1. SUM and AVG After LEFT JOIN

`SUM(e.salary)` or `AVG(e.salary)` on a group with no employees returns `NULL`. If a report needs to display 0, you can use `COALESCE(SUM(e.salary), 0)`. Decide that based on the reporting semantics.

Do not wrap each row in `COALESCE()` before aggregating if doing so alters the denominator of an average:

```sql
-- Average of salary values that have data
AVG(e.salary)

-- Each NULL row is converted to 0 before calculating the average
AVG(COALESCE(e.salary, 0))
```

These two expressions mean different things. For a department with no employees, the second expression evaluates over the `NULL`-padded outer join row and returns 0 instead of `NULL`. For a group with employees where some salaries are `NULL`, the second expression treats missing salaries as 0, lowering the average. Only use this pattern when business rules explicitly define missing values as 0.

## 9. One-to-Many JOINs and Row Multiplication Risk

An outer join does not guarantee that each row on the preserved side appears only once. If a department has multiple employees, the department repeats for each employee. If you join yet another one-to-many child table, the row count can grow as the product of child row counts across relationships.

For example, if a department has 2 employees and each employee has 3 skills, joining `departments -> employees -> employee_skills` can produce 6 rows for that department. In that case, `COUNT(e.employee_id)` would count each employee multiple times.

If you need to count distinct employees in a multi-table join, you can use `COUNT(DISTINCT e.employee_id)`, but first understand the cardinality and purpose of the count. When aggregating multiple child tables, it is usually better to aggregate each child table down to one row per parent key before joining.

Example aggregating active employees per department:

```sql
SELECT
    d.department_id,
    d.department_name,
    COALESCE(employee_totals.active_employee_count, 0) AS active_employee_count
FROM departments AS d
LEFT JOIN (
    SELECT department_id, COUNT(*) AS active_employee_count
    FROM employees
    WHERE is_active = 1
    GROUP BY department_id
) AS employee_totals
    ON employee_totals.department_id = d.department_id
ORDER BY d.department_id;
```

The derived table has at most one row per `department_id`, guaranteeing exactly one row per department in the result.

## 10. RIGHT JOIN and Reading Conditions

With `RIGHT JOIN`, the right table is the preserved side. In this query:

```sql
SELECT d.department_name, e.employee_name
FROM departments AS d
RIGHT JOIN employees AS e
    ON e.department_id = d.department_id
WHERE d.department_name = 'Sales';
```

`WHERE d.department_name = 'Sales'` excludes employees without a matching department, because `d.department_name` is `NULL` for those rows. If you want to keep every employee and only display the department name when the department is named Sales, the condition must go in `ON`:

```sql
SELECT d.department_name, e.employee_name
FROM departments AS d
RIGHT JOIN employees AS e
    ON e.department_id = d.department_id
   AND d.department_name = 'Sales';
```

The second query keeps all employees; those not in Sales get `NULL` for the department column. However, if the goal is to list only Sales employees, then the `WHERE` condition is the right one. Choose condition placement based on the business question, not a mechanical rule that every condition belongs in `ON`.

## 11. No Direct FULL OUTER JOIN Syntax in MySQL

MySQL does not provide direct `FULL OUTER JOIN` syntax. If you need to preserve all rows from both sides, you can combine:

1. A `LEFT JOIN` to fetch all departments together with matching employees or `NULL`.
2. A query fetching employees that do not have a matching department.
3. `UNION ALL` to combine the two result sets.

Example:

```sql
SELECT
    d.department_id,
    d.department_name,
    e.employee_id,
    e.employee_name
FROM departments AS d
LEFT JOIN employees AS e
    ON e.department_id = d.department_id

UNION ALL

SELECT
    d.department_id,
    d.department_name,
    e.employee_id,
    e.employee_name
FROM employees AS e
LEFT JOIN departments AS d
    ON d.department_id = e.department_id
WHERE d.department_id IS NULL
ORDER BY department_id, employee_id;
```

The first branch retrieves all departments, including those without employees. The second branch retrieves only employees without a matching department, avoiding repeating pairs already included in the first branch. `UNION ALL` preserves all rows as-is; using `UNION` could deduplicate rows across all result columns and change semantics if two valid rows happen to have identical projected values.

This simulates a full outer join on the declared join key. If the join condition is complex or involves multiple nullable columns, carefully verify the key used to identify unmatched rows and check cardinality.

## 12. NULL in JOIN Conditions

With standard equality comparison:

```sql
ON e.department_id = d.department_id
```

If `e.department_id` is `NULL`, the comparison expression does not return `TRUE`, so that employee matches no department. This is usually the desired behavior when `NULL` means unassigned.

MySQL provides the null-safe equality operator `<=>`:

```sql
ON e.department_id <=> d.department_id
```

`<=>` treats `NULL <=> NULL` as `TRUE`. Only use it when business logic defines two `NULL` values as belonging to the same relational group. If there are many `NULL` rows on both sides, they can cross-match with each other and generate unexpected row multiplication. With nullable foreign keys, you should normally not treat all `NULL` values as the same parent entity.

Do not confuse a `NULL` produced by no matching row with a `NULL` stored natively in a real row. When you need to distinguish them, inspect the non-nullable primary key of the joined side, or include an explicit flag/metadata column in the query.

## 13. Indexes and Outer Join Performance

Outer joins frequently need to look up matching rows by key. An index on the join column of the probed table can reduce the number of rows scanned.

In the fixture:

- `departments.department_id` is the primary key.
- `employees.department_id` has index `idx_employees_department`.

This is a standard layout: the parent table has a primary/unique key, and the child table has an index on the foreign key. In InnoDB, declaring a foreign key generally requires an appropriate index on the child table; if none exists yet, MySQL can create the needed index.

Inspecting the execution plan:

```sql
EXPLAIN
SELECT
    d.department_id,
    d.department_name,
    e.employee_id,
    e.employee_name
FROM departments AS d
LEFT JOIN employees AS e
    ON e.department_id = d.department_id
ORDER BY d.department_id, e.employee_id;
```

Observe:

- Which table is read first and the join order chosen by the optimizer.
- `type`, `possible_keys`, `key`, `rows`, and `Extra`.
- Whether the join condition uses an index or scans many rows.
- Actual rows compared to estimates if using `EXPLAIN ANALYZE`.

Key guidelines:

- Data types of the two joined columns should be compatible, including integer signedness as well as string charset and collation.
- Indexes on join columns are often important, though not every outer join requires a brand-new index; evaluate existing indexes and overall workload.
- Do not wrap join columns in functions without a good reason and supporting index, as that can prevent the condition from using an index.
- Filter rows on the non-preserved side inside `ON` when you want to keep all rows from the preserved side.
- Do not draw performance conclusions from a tiny fixture of a few rows; evaluate on data with realistic scale and distribution.

`EXPLAIN ANALYZE` executes the real query. Only run it on queries and environments that can tolerate the resulting load.

## 14. Common Mistakes

| Mistake | Consequence | Fix |
| --- | --- | --- |
| Switching `LEFT JOIN` to `INNER JOIN` without considering missing rows | Parent rows without child rows disappear | Keep outer join if business logic needs unmatched rows |
| Placing a right-table filter in `WHERE` | Can eliminate `NULL`-padded rows | Place it in `ON` if you only want to restrict matched rows |
| Using `COUNT(*)` to count child rows after `LEFT JOIN` | Parent rows with no children get counted as 1 | Use `COUNT(child.primary_key)` |
| Checking `IS NULL` on a nullable column of a real row | Confuses matched rows with `NULL` values with unmatched rows | Check the primary key or a `NOT NULL` column |
| Using `NOT IN` with a subquery containing `NULL` | Condition can evaluate to `UNKNOWN` and return no expected rows | Use `NOT EXISTS` or explicitly exclude `NULL`s |
| Assuming `LEFT JOIN` returns only one row per left row | Misses one-to-many multiplication | Verify cardinality and aggregate when needed |
| Using `<=>` on nullable keys without understanding the effect | `NULL` rows can cross-match | Use `=` for standard key relationships |
| Using `UNION` when simulating `FULL OUTER JOIN` | Drops legitimate duplicate rows | Use `UNION ALL` with an anti-join branch |
| Omitting `ORDER BY` | Result order is not guaranteed | Add explicit ordering and a unique tie-breaker if needed |

## 15. Process for Choosing a JOIN by Question

Before writing SQL, determine which table must appear in full:

| Question | Typically Appropriate Structure |
| --- | --- |
| Need only rows with relationships in both tables | `INNER JOIN` |
| Keep all departments, include employees if any | `departments LEFT JOIN employees` |
| Keep all employees, include departments if any | `employees LEFT JOIN departments` or `departments RIGHT JOIN employees` |
| Find departments with no employees | `LEFT JOIN ... WHERE employee_pk IS NULL` or `NOT EXISTS` |
| Find employees without a valid department | `employees LEFT JOIN departments ... WHERE department_pk IS NULL` |
| Keep all rows from both sides | Simulate using `LEFT JOIN UNION ALL` with an anti-join branch |

After choosing the join type:

1. Write the key matching condition and identify columns that may be `NULL`.
2. Determine which conditions define a "match" and place them in `ON`.
3. Determine which conditions filter the final result and place them in `WHERE`.
4. Verify expected row counts for one-to-one, one-to-many, and unmatched cases.
5. Choose a non-nullable key column to detect unmatched rows.
6. Verify the result and `EXPLAIN` plan on representative data.

## 17. Pre-Production Checklist for Outer Joins

- [ ] Clearly identified which table must be preserved in full.
- [ ] The `ON` condition accurately reflects the matching rule between the two tables.
- [ ] `WHERE` conditions do not inadvertently discard preserved rows.
- [ ] Tested unmatched relationships, `NULL` foreign keys, and orphan keys.
- [ ] The column used to detect unmatched rows is a key or `NOT NULL` column.
- [ ] Used `COUNT(child_pk)` when counting child rows after an outer join.
- [ ] Checked one-to-many cardinality and multiplication risks when joining multiple child tables.
- [ ] Considered `NOT EXISTS` for anti-join queries.
- [ ] Confirmed whether `<=>` for NULL-safe equality is truly needed.
- [ ] Data types and indexes on join columns are compatible.
- [ ] Included an explicit `ORDER BY` if ordering is part of the business output.
- [ ] Inspected the execution plan with `EXPLAIN` on representative data.

## 18. Completion Criteria

You have completed this lesson when you can choose `LEFT JOIN` or `RIGHT JOIN` accurately based on the side to preserve, explain the `NULL` columns generated when no row matches, place conditions in `ON`/`WHERE` with the right semantics, find unrelated records via anti-joins, distinguish `NULL` foreign keys from orphan keys, and avoid miscounting after outer joins. You should also be able to write equivalent `RIGHT` and `LEFT` joins, understand MySQL's `FULL OUTER JOIN` limitation, and inspect relevant indexes and execution plans.
