# GTID, server_uuid, server_id, and uniqueness requirements

## Objectives

After this lesson, you will be able to:

- Explain GTID structure and the role of the source UUID in identifying transactions.
- Distinguish `server_id` from `server_uuid`, and know where to configure and how to check each value.
- Ensure every server in a replication topology has a unique and stable identity.
- Recognize errors caused by copying a datadir, snapshot, or server configuration that duplicates identities.
- Check `gtid_executed`, `gtid_purged`, compare GTID sets, and use auto-position for replication.
- Plan safely for enabling GTID, adding replicas, cloning servers, and resolving identity incidents.

## 1. Why does replication require unique identities?

In a MySQL topology, multiple servers may exchange binary logs, apply transactions from one another, and participate in failover. Servers must know where each transaction originated, which transactions have executed, and which transactions still need to be transferred. If two servers share an identity, the system can misattribute transaction origins, skip events, or detect duplicate GTIDs.

MySQL uses two distinct types of identifiers with different roles:

- **`server_id`:** an integer identifying a server in the replication topology. It is recorded in binary log metadata and used by the replication mechanism.
- **`server_uuid`:** a unique UUID generated by MySQL for the server and stored in the datadir. In GTID, this UUID serves as the SID (source identifier) identifying the server that originally created the transaction.

GTID (Global Transaction Identifier) identifies transactions across the entire topology. For GTID to work properly, `server_id` must be unique, `server_uuid` must be unique, and each server must maintain a stable identity throughout its lifecycle.

For example, a topology with one source and two replicas:

| Server | Role | `server_id` | `server_uuid` |
|---|---|---:|---|
| `mysql-source-01` | Source | 101 | `a1a1...` |
| `mysql-replica-01` | Replica | 102 | `b2b2...` |
| `mysql-replica-02` | Replica | 103 | `c3c3...` |

The UUID values in the table are abbreviated for illustration. In MySQL, a full UUID has the form `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`.

Hostnames, IP addresses, or DNS records do not replace these two identifiers. Changing a hostname or IP does not automatically generate a new `server_id`/`server_uuid`.

## 2. GTID structure

With MySQL GTID, a transaction has the general format:

```text
source_uuid:transaction_number
```

Where:

- `source_uuid` is the SID, typically the `server_uuid` of the server that originally created the transaction.
- `transaction_number` is the sequence number (GNO), incrementing within that SID's GTID sequence.

Example:

```text
a1a1a1a1-1111-2222-3333-444444444444:57
```

This GTID identifies transaction number 57 created on the server with SID `a1a1a1a1-1111-2222-3333-444444444444`.

A server may have executed transactions originating from multiple servers. Therefore, a GTID set is a collection of multiple SIDs along with their corresponding sequence number intervals. Example:

```text
a1a1a1a1-1111-2222-3333-444444444444:1-57:60-62,
b2b2b2b2-1111-2222-3333-444444444444:1-14
```

For the first SID, this set contains transactions 1 through 57 and 60 through 62; numbers 58 and 59 are not in the set. The second SID has transactions 1 through 14. A GTID set can contain multiple disjoint intervals and does not have to be a single contiguous range.

A GTID is attached to a committed transaction and recorded by MySQL's GTID mechanism. When a replica applies a transaction from the source, it preserves that original GTID; the replica does not generate a new GTID with its own UUID for the replicated transaction. Locally created transactions on a replica (if writes are permitted) can carry the replica's SID and create separate history.

## 3. Distinguishing `server_id` and `server_uuid`

These two values complement each other and cannot substitute for one another.

| Attribute | `server_id` | `server_uuid` |
|---|---|---|
| Data type | 32-bit unsigned integer | 128-bit UUID, represented as a 36-character string with hyphens |
| Purpose | Identifies the server in metadata and the replication stream | SID used in GTID to identify the origin that created a transaction |
| Where configured/stored | MySQL configuration such as `my.cnf`/`my.ini`; also exposed as a system variable | `auto.cnf` file in the datadir, auto-generated by MySQL |
| How to change | Configure `server_id` on each server; persist in deployment config | Cannot be set via `SET`; MySQL generates it when no valid UUID exists in `auto.cnf` |
| Requirement | Unique within the topology | Unique within the topology and stable across restarts |

### 3.1. `server_id`

`server_id` is a 32-bit unsigned integer. Valid values for participating in replication range from `1` to `4294967295` (`2^32 - 1`). A value of `0` is not suitable for a server that needs to participate in replication. The default value may be `1`, so you should never leave all servers on the default.

Set a distinct value for each server in its configuration:

```ini
[mysqld]
server_id=101
log_bin=mysql-bin
```

On another replica, use a different value, such as `server_id=102`. Save the setting in the configuration file deployed with the server so the value does not revert to the default after a restart.

You can check the running value:

```sql
SELECT @@GLOBAL.server_id AS server_id;
```

`server_id` is recorded in replication events and helps MySQL identify an event's source. If two servers share the same `server_id`, a replica may mishandle events, skip events it believes it created itself, or raise replication errors. In multi-tier replication, ensure every member has a unique ID, not just directly connected sources and replicas.

### 3.2. `server_uuid`

When MySQL starts for the first time with a datadir that lacks `auto.cnf`, the server generates a UUID and stores it in this file. The file typically resides in the data directory with contents such as:

```ini
[auto]
server-uuid=a1a1a1a1-1111-2222-3333-444444444444
```

Check the UUID via SQL:

```sql
SELECT @@GLOBAL.server_uuid AS server_uuid;
```

`server_uuid` is a read-only variable. Do not set it with `SET GLOBAL`, do not manually edit `auto.cnf`, and do not manufacture a UUID by copying the string from another server.

MySQL must preserve a stable UUID across restarts so that GTIDs from the same server continue to belong to the same SID. If the UUID changed on every restart, transaction history would fragment across multiple SIDs and GTID management would become difficult.

## 4. Uniqueness rules in a topology

Every server participating in the same replication topology must have:

1. A distinct `server_id`.
2. A distinct `server_uuid`.
3. Identities persisted across restarts.
4. An identity record logged alongside hostname, IP, role, version, and replication status.

Example inventory table storing complete details:

| Hostname | IP / endpoint | Role | `server_id` | `server_uuid` | GTID mode |
|---|---|---|---:|---|---|
| `mysql-source-01` | `10.20.0.11` | Source | 101 | Full UUID | ON |
| `mysql-replica-01` | `10.20.0.12` | Replica | 102 | Full UUID | ON |
| `mysql-replica-02` | `10.20.0.13` | Replica | 103 | Full UUID | ON |

In practice, do not record abbreviated UUIDs in an official inventory table. Store the full string so duplicates can be detected.

### 4.1. Checking on each server

Run on the source and every replica:

```sql
SELECT
  @@hostname AS hostname,
  @@port AS port,
  @@GLOBAL.server_id AS server_id,
  @@GLOBAL.server_uuid AS server_uuid,
  @@GLOBAL.gtid_mode AS gtid_mode,
  @@GLOBAL.enforce_gtid_consistency AS enforce_gtid_consistency;
```

Record the results and compare across the whole topology. SQL run on one server only displays that server's own identity; MySQL does not provide a single built-in statement to list the UUIDs of all unconnected hosts. Use your inventory, configuration management tooling, or query each endpoint individually to reconcile.

### 4.2. Do not reuse the same identities across environments

Staging, QA, or disaster recovery servers may be created from a copy of production. If they ever connect to the same replication topology or could send binlogs to one another, they also need distinct identities. Ideally, each environment has a planned `server_id` range and a centrally managed UUID catalog.

If a test environment is completely isolated, sharing identities will not immediately damage production, but it creates risk if that environment is later connected to the topology, used as a failover source, or promoted into a live server. Handle identity properly right from the server provisioning workflow.

## 5. Risks when cloning or copying a datadir

A common mistake occurs when creating a replica by copying an entire datadir, volume snapshot, or VM image from a running server. The copy can carry over `auto.cnf` and the source server's `server_id` configuration.

The result can be two servers sharing the same:

- `server_id` from the copied `my.cnf`/`my.ini` configuration.
- `server_uuid` from the copied `auto.cnf` file.

If both servers participate in replication, they can generate GTIDs with the same SID and sequence numbers, leading to identity conflicts or preventing replication from operating properly.

### 5.1. Procedure for a physical datadir copy

When creating a new server from a physical copy of a datadir, handle identity before joining it to the topology:

1. Stop MySQL on the new server and verify the process has fully stopped.
2. Inspect the copied configuration and set a unique `server_id` for the new server.
3. If this is a new member needing its own identity, remove the `auto.cnf` file on the **new server** while MySQL is stopped so MySQL generates a new UUID on the next startup.
4. Start the new server and verify `@@server_uuid` and `@@server_id`.
5. Compare both values against all existing members before configuring replication or allowing writes.
6. Verify GTID history and configure replication using the chosen method.

Never delete `auto.cnf` on the original server or a running server. Do not delete this file if the goal is to restore the old server itself with its old identity. Generating a new UUID applies only to a new member that needs a distinct identity.

### 5.2. When using MySQL Clone Plugin or backup tools

Cloning, physical backup, and snapshot tools each have their own rules regarding identity, replication metadata, and GTIDs. Never assume every tool copies or regenerates `server_uuid` the same way. Read the instructions for your exact tool/version, and always verify the actual values on the target machine before connecting replication.

If two servers with duplicate UUIDs have already been running together, do not simply delete `auto.cnf` and restart to fix it. The servers may already have generated transactions with colliding SIDs; changing the UUID does not rewrite old GTID history. Stop unintended writes on the servers, collect GTID sets and logs, determine which server is canonical, and plan a controlled rebuild or history synchronization.

## 6. GTID mode and consistency requirements

GTID is controlled by two key variables:

- `gtid_mode`: determines whether the server generates and processes GTIDs.
- `enforce_gtid_consistency`: prevents operations incompatible with GTID consistency.

To use GTID fully, enable binary logging and set `enforce_gtid_consistency=ON` and `gtid_mode=ON` on the participating servers. Verify:

```sql
SHOW GLOBAL VARIABLES LIKE 'log_bin';
SHOW GLOBAL VARIABLES LIKE 'gtid_mode';
SHOW GLOBAL VARIABLES LIKE 'enforce_gtid_consistency';
```

When `gtid_mode=ON`, transactions written to the binary log must have a GTID. To guarantee history can be replayed safely, MySQL enforces consistency restrictions. For example, creating or dropping temporary tables inside a transaction or stored program, or mixing updates to transactional and non-transactional tables in the same transaction, may be rejected. Rules around `CREATE TABLE ... SELECT` have changed across versions, so check the documentation for your exact running MySQL version before including that SQL pattern in workflows.

Resolve warnings from `enforce_gtid_consistency=WARN` before switching to `ON`. Do not disable consistency just to let an old batch script run; fix the SQL workflow or split transactions in a compatible way.

### 6.1. GTID transition states

MySQL supports the following `gtid_mode` states:

| State | Meaning |
|---|---|
| `OFF` | Transactions are logged as anonymous, without GTIDs |
| `OFF_PERMISSIVE` | New transactions may be anonymous; GTID transactions are still accepted |
| `ON_PERMISSIVE` | New transactions use GTIDs; existing anonymous transactions in the replication stream are still accepted |
| `ON` | New transactions must have GTIDs; anonymous transactions are not accepted |

The supported transition order is:

```text
OFF
  -> OFF_PERMISSIVE
  -> ON_PERMISSIVE
  -> ON
```

These are sequential transition steps, not a single configuration setting. When migrating a running topology, coordinate all sources and replicas in the exact order specified by the MySQL documentation. Avoid switching one server to `ON` while another is still emitting anonymous transactions.

Before transitioning:

1. Enable `enforce_gtid_consistency=WARN` and resolve all warnings.
2. Ensure `log_bin=ON`, unique `server_id`, and unique `server_uuid` on all servers.
3. Transition sequentially through `OFF_PERMISSIVE`, then `ON_PERMISSIVE` across the topology.
4. Wait for in-flight anonymous transactions to finish applying.
5. Verify `ONGOING_ANONYMOUS_TRANSACTION_COUNT` equals 0 on the relevant servers.
6. Transition to `gtid_mode=ON` in the supported order, then verify replication and GTID sets.

Check ongoing anonymous transactions:

```sql
SHOW GLOBAL STATUS LIKE 'ONGOING_ANONYMOUS_TRANSACTION_COUNT';
```

Enabling GTID on a system with existing data and replication requires a planned change window, backups, and a rollback plan. For a new topology, configure the GTID settings from the start rather than running the transition procedure.

## 7. Inspecting GTID history

MySQL provides important status variables:

- `gtid_executed`: set of GTIDs executed on the server, including locally executed transactions and transactions applied from a source.
- `gtid_purged`: set of GTIDs that have been executed, whose binary logs containing those transactions have been purged from the server.
- `gtid_owned`: GTIDs currently owned by transactions during execution; typically used for advanced diagnostics.

Check:

```sql
SELECT @@GLOBAL.gtid_executed AS gtid_executed;
SELECT @@GLOBAL.gtid_purged AS gtid_purged;
```

`gtid_purged` is a subset of executed history. When a replica needs transactions already purged from the source's binlogs, the source cannot resend those transactions from its current logs. The replica must be reseeded from an appropriate backup, or the source must restore logs from archival storage if a copy still exists.

### 7.1. Comparing GTID sets

GTID functions help compare history:

```sql
-- Check whether the first set is a subset of the second set.
SELECT GTID_SUBSET(
  'a1a1a1a1-1111-2222-3333-444444444444:1-50',
  'a1a1a1a1-1111-2222-3333-444444444444:1-60'
);

-- Find GTIDs present in the first set but missing from the second set.
SELECT GTID_SUBTRACT(
  'a1a1a1a1-1111-2222-3333-444444444444:1-60',
  'a1a1a1a1-1111-2222-3333-444444444444:1-50'
);
```

In the example, `1-50` is a subset of `1-60`; subtraction returns the range `51-60`. When comparing source and replica, use full GTID sets retrieved from both servers and record the results along with the inspection timestamp.

You can wait for a server to apply up to a GTID set:

```sql
SELECT WAIT_FOR_EXECUTED_GTID_SET(
  'a1a1a1a1-1111-2222-3333-444444444444:1-60',
  30
);
```

A return value of `0` means the wait succeeded and the GTID set was executed; `1` means the timeout expired. This function is useful in failover testing or synchronizing before running a read-after-write query.

## 8. GTID auto-positioning

With file/position replication, the operator must track the binary log file name and byte offset on the source. GTID auto-position lets the replica and source exchange GTID sets so the source sends only the transactions the replica is missing.

On MySQL 8.0.23 and later, configure the replica using source/replica syntax:

```sql
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST = 'mysql-source-01.example.internal',
  SOURCE_PORT = 3306,
  SOURCE_AUTO_POSITION = 1;

START REPLICA;
```

This example assumes replication account credentials are already configured per security procedures. If you need to specify `SOURCE_USER`, `SOURCE_PASSWORD`, or TLS, use your organization's secret and certificate management process; never put real passwords in committed scripts or logs.

On MySQL versions before 8.0.23, the legacy syntax is `CHANGE MASTER TO ... MASTER_AUTO_POSITION=1` and `START SLAVE`. Use the exact command names matching your server version.

### 8.1. Prerequisites for auto-position to work

- GTID must be enabled and consistently configured on both the source and replica.
- The source must retain binary logs containing the transactions the replica is missing.
- The replica must have a GTID history matching the backup or initial seed state.
- Every member's `server_id` and `server_uuid` must be unique.
- There must be no unintended transactions appearing only on the replica (errant transactions) that diverge from the expected history.
- Do not configure auto-position and manual file/position coordinates simultaneously for the same channel; `SOURCE_AUTO_POSITION=1` replaces specifying binlog file and position.

If the source has already purged GTIDs that the replica lacks, auto-position cannot recreate those transactions. You must restore the replica from a newer backup or supply the missing binary logs from archival storage.

### 8.2. Checking replica status

```sql
SHOW REPLICA STATUS\G
```

Fields to inspect:

| Field | Meaning |
|---|---|
| `Source_UUID` | UUID of the source the replica is connecting to |
| `Auto_Position` | `1` if the channel uses GTID auto-position |
| `Retrieved_Gtid_Set` | GTIDs received from the source |
| `Executed_Gtid_Set` | GTIDs executed on the replica |
| `Last_IO_Error` | Error in the binlog receiver thread |
| `Last_SQL_Error` | Error when applying transactions |
| `Seconds_Behind_Source` | Estimated lag; not a complete measure of every form of lag |

If there are multiple replication channels, `SHOW REPLICA STATUS` displays status per channel; inspect the correct channel. You can use Performance Schema to observe connection errors and received GTID sets:

```sql
SELECT
  CHANNEL_NAME,
  SOURCE_UUID,
  SERVICE_STATE,
  LAST_ERROR_NUMBER,
  LAST_ERROR_MESSAGE
FROM performance_schema.replication_connection_status;
```

## 9. Errant transactions and the impact of local writes on a replica

An errant transaction is a transaction created directly on a replica that does not exist on the canonical source or other members. That transaction carries a GTID with the replica's SID. When the replica is promoted or when members exchange GTID sets, this divergent history can prevent the system from selecting a new source as expected.

For example, an application accidentally connects to a replica with `super_read_only=OFF` and executes:

```sql
INSERT INTO maintenance_note(note)
VALUES ('created on replica');
```

This transaction is created locally on the replica and can carry a SID from the replica's `server_uuid`. The primary source lacks that GTID. When switching roles or configuring auto-position, this extra transaction can push the replica's GTID set beyond the source's history.

To prevent this:

- Enable `read_only=ON` and `super_read_only=ON` on read replicas when the architecture forbids local writes.
- Use read-only application accounts on replicas.
- Do not give broad administrative accounts to applications.
- Monitor GTID sets on both source and replicas, especially before failover.
- Only create local transactions on a replica when explicitly designed for multi-source or special operational procedures.

Never delete a GTID from history by directly modifying system tables. If an errant transaction is detected, halt role-switching operations, identify the transaction's content and origin, and handle it according to an appropriate runbook. Rebuilding the replica from the canonical source may be required to bring history back to the desired state.

## 10. Failover and identity recovery

When promoting a replica to become the new source, the promoted server's identity remains its own identity. Do not change `server_uuid` simply because its role changed. The GTID set received from the old source remains in its executed history; new transactions created on the new source will use the new source's `server_uuid` as their SID.

Before promoting:

1. Confirm the old source has stopped accepting writes or is isolated to prevent split-brain.
2. Compare `gtid_executed` across replicas and select the server with the most complete, appropriate history.
3. Verify there are no unexpected errant transactions.
4. Wait for the selected replica to apply all required GTIDs per the RPO target.
5. Promote per the runbook, and configure the remaining replicas to point to the new source using GTID auto-position.
6. Verify `server_id`, `server_uuid`, GTID sets, replication channels, and write permissions.

Never reuse the same `server_id` or `server_uuid` for two running mysqld processes in the topology. If the old server is recovered to act as a new replica, determine whether it is the same logical server or a new member. If it is a new member created from a physical copy, handle its identity as in the cloning procedure before connecting.

## 11. Diagnosing identity and GTID errors

| Symptom | Possible cause | Remediation |
|---|---|---|
| Error reports source and replica have the same UUID | `auto.cnf` was copied from another machine or two instances share the same cloned datadir | Stop replication connections; identify the new node; generate a distinct UUID properly while mysqld is stopped; verify before reconnecting |
| Two servers have the same `server_id` | Server configuration was copied or left at default | Assign distinct IDs, save in config files, and verify across the topology |
| Auto-position reports source lacks required transactions | Source purged binlogs containing GTIDs the replica is missing | Restore logs from archive or reseed the replica from a newer backup |
| Replica's GTID set contains an unknown SID | Replica has local transactions, or was seeded from a different history | Use `GTID_SUBTRACT` to find the difference; determine the origin before modifying the topology |
| Replication stops when enabling GTID | Remaining anonymous transactions, non-GTID-consistent statements, or inconsistent config | Check `gtid_mode`, `enforce_gtid_consistency`, anonymous count, and error log; complete the transition step by step |
| Replica reports duplicate GTID error | Duplicate transaction history or invalid identity/seed history | Halt automated changes; collect GTID sets and binlogs, identify the canonical source, and rebuild the replica if needed |
| GTID set stops advancing despite active connection | I/O thread, SQL applier, filters, event error, or source lacks required logs | Check `SHOW REPLICA STATUS`, Performance Schema, error log, and relay log |

Do not use `RESET MASTER`, `RESET BINARY LOGS AND GTIDS`, or adjust `gtid_purged` as a routine troubleshooting step. Reset commands can delete binary logs or alter GTID history, breaking recoverability. Use them only with a verified plan, backups, and a clear understanding of their impact on your exact MySQL version.

## 12. Checklist before adding a server to the topology

Before adding a new source or replica, confirm:

- [ ] `server_id` is non-zero, within valid range, and not assigned to another server.
- [ ] `server_uuid` was generated uniquely by MySQL and differs from every other member's UUID.
- [ ] `auto.cnf` is not an identity copy of another server.
- [ ] `log_bin=ON` if the server needs to emit binlogs.
- [ ] `gtid_mode` and `enforce_gtid_consistency` align with the topology.
- [ ] The backup/seed GTID history is understood; no unexpected foreign transactions exist.
- [ ] MySQL version and replication settings are compatible with the source.
- [ ] The replica has `read_only`/`super_read_only` enabled per policy.
- [ ] Replication account, TLS, and access permissions are securely configured.
- [ ] `SHOW REPLICA STATUS` shows no errors and GTID sets advance properly.

## 13. Hands-on exercise

An operations team created `mysql-replica-03` by copying the datadir of `mysql-source-01`. After starting up, both machines return the same `server_uuid` and the same `server_id`. The replica has not yet been added to the topology.

Perform these steps in a lab environment:

1. Collect `@@hostname`, `@@server_id`, `@@server_uuid`, `@@gtid_mode`, and `@@gtid_executed` on both servers.
2. Identify the config file supplying `server_id` and the datadir path containing `auto.cnf` on the new replica.
3. Stop mysqld on the new replica; assign an unused `server_id` and handle `auto.cnf` so MySQL generates a new UUID on startup.
4. Restart the replica, verify the new UUID differs from the source, and confirm the source's UUID remains untouched.
5. Compare GTID history and verify the backup/seed matches before setting up auto-position.
6. Configure replication with `SOURCE_AUTO_POSITION=1`, start the replica, and monitor `Retrieved_Gtid_Set`, `Executed_Gtid_Set`, I/O errors, and SQL errors.
7. Prove the replica does not create local transactions by verifying application privileges and `super_read_only` status.

Never perform this exercise on production servers or the sole datadir serving a live system. The goal is to understand how identities are generated, stored, and verified before connecting replication.

**Self-check questions:**

1. In the GTID `a1a1...:57`, what do the UUID part and the number `57` represent?
2. Why must both `server_id` and `server_uuid` be unique?
3. Which file stores `server_uuid`, and why must it not be manually edited?
4. What happens if an entire datadir including `auto.cnf` is copied to a new member?
5. How does `gtid_executed` differ from `gtid_purged`?
6. What information does GTID auto-position use to select transactions to transmit?
7. Why can a locally created transaction on a replica become an errant transaction?
8. When promoting a replica to source, do you need to generate a new `server_uuid`? Explain.

## Conclusion

`server_id` identifies a server within the replication stream; `server_uuid` provides the SID identifying the origin that created a GTID. Every member requires both values to be unique and stable. GTID sets track which transactions have executed, and auto-position uses these sets to automatically determine which transactions a replica is missing. Check identities before connecting, handle datadir clones carefully, protect GTID history, and verify the entire topology before failover or recovery.
