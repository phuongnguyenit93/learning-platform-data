# Declared Primary Key, Qualifying Unique Key, and Hidden Row ID

InnoDB stores data in a **clustered index**: the leaf pages of the clustered index hold the full row data and are organized by that index's key. Which key is used as the clustered index directly affects how InnoDB locates rows, the size of secondary indexes, and INSERT/UPDATE costs.

InnoDB's selection rules are very important:

1. If the table has a `PRIMARY KEY`, InnoDB uses the primary key as the clustered index.
2. If there is no primary key, InnoDB selects the first unique index where all key columns are declared `NOT NULL`.
3. If there is no primary key and no qualifying unique index, InnoDB creates a hidden clustered index on an internal 6-byte row ID, commonly known as `GEN_CLUST_INDEX`.

Therefore, a table without a declared primary key does not necessarily use a hidden row ID: a qualifying unique index can become the clustered index. Conversely, a unique index with a nullable column does not qualify, because MySQL allows multiple rows to have `NULL` values in a unique index. This lesson helps you choose a stable primary key, understand the role of unique keys, and recognize when InnoDB must use a hidden row ID.

## 1. How Does the Clustered Index Store Rows?

InnoDB uses a B+ tree for indexes. For a clustered index, leaf pages contain the full row data rather than just keys and pointers to another storage location. Therefore, searching by the clustered key leads directly to the page containing the row.

Example of a table with primary key `id`:

```sql
CREATE TABLE customers (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    email VARCHAR(254) NOT NULL,
    full_name VARCHAR(120) NOT NULL,
    created_at DATETIME NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uq_customers_email (email)
) ENGINE=InnoDB;
```

`PRIMARY KEY (id)` is the clustered index. Rows are organized by `id` value; leaf pages of the clustered index hold `email`, `full_name`, `created_at`, and the remaining columns.

The unique index `uq_customers_email` is a secondary index. It stores the email value along with the primary key so InnoDB can locate the corresponding row. When querying by email, InnoDB can look up the entry in the secondary index and then use `id` to access the clustered index.

### Clustered Index Does Not Guarantee SELECT Result Order

Data is organized by the clustered key, but SQL does not guarantee row ordering if a SELECT query lacks `ORDER BY`. Do not rely on insert order, page order, or the primary key to infer result order. If the application needs deterministic ordering, write `ORDER BY` explicitly.

## 2. InnoDB's Clustered Index Selection Rules

InnoDB chooses the clustered index in the following order:

| Priority | Table structure | Clustered index used |
|---:|---|---|
| 1 | `PRIMARY KEY` declared | Primary key. |
| 2 | No primary key; one or more unique indexes with all key columns `NOT NULL` | First qualifying unique index. |
| 3 | No primary key and no qualifying unique index | 6-byte hidden row ID generated by InnoDB. |

This rule means:

- The primary key is always preferred, even when the table also has other unique indexes.
- A unique index is only a fallback candidate when every column participating in the index is `NOT NULL`.
- If there are multiple qualifying unique indexes and no primary key, InnoDB picks the first qualifying unique index.
- A unique index with a nullable column is not used as a fallback clustered index.
- The hidden row ID is the last resort when no suitable unique key exists.

## 3. A Declared Primary Key Always Takes Priority

When a table has a primary key, InnoDB uses it as the clustered index. Any remaining unique indexes are secondary indexes, regardless of whether those unique indexes were created before or after the primary key.

Example:

```sql
CREATE TABLE products (
    product_id BIGINT UNSIGNED NOT NULL,
    sku VARCHAR(40) NOT NULL,
    product_name VARCHAR(160) NOT NULL,
    PRIMARY KEY (product_id),
    UNIQUE KEY uq_products_sku (sku)
) ENGINE=InnoDB;
```

In this table:

- `product_id` is the clustered key.
- `sku` is enforced by a unique secondary index.
- InnoDB uses `product_id` as the row locator in the secondary index `uq_products_sku`.

Even when `sku` is a stable, unique business code, the declared primary key remains the clustered key. The unique constraint on `sku` still holds independent value: it prevents two products from sharing the same SKU.

### Primary Key Must Be Unique and Not NULL

MySQL requires primary key columns to be non-NULL. For a composite primary key, every key component must be non-NULL. The primary key is also the only unique constraint with the special name `PRIMARY`; a table can have only one primary key, though it can have multiple unique indexes.

Do not confuse `PRIMARY KEY` with `UNIQUE KEY`: both enforce uniqueness, but the primary key is also preferred by InnoDB as the clustered index and does not allow NULL.

## 4. Without a Primary Key, Which Unique Index Is Chosen?

If a table does not declare a primary key, InnoDB looks for a unique index in which all key columns are `NOT NULL`. That unique index can become the clustered index.

Example:

```sql
CREATE TABLE country_codes (
    country_code CHAR(2) NOT NULL,
    country_name VARCHAR(100) NOT NULL,
    currency_code CHAR(3) NOT NULL,
    UNIQUE KEY uq_country_codes_code (country_code)
) ENGINE=InnoDB;
```

The table has no `PRIMARY KEY`, but `uq_country_codes_code` is a unique index and `country_code` is `NOT NULL`. InnoDB can use this unique index as the clustered index. No hidden row ID is needed in this case.

Composite key example:

```sql
CREATE TABLE tenant_external_objects (
    tenant_id BIGINT UNSIGNED NOT NULL,
    external_id VARCHAR(80) NOT NULL,
    object_type VARCHAR(30) NOT NULL,
    payload JSON NOT NULL,
    UNIQUE KEY uq_tenant_external (tenant_id, external_id)
) ENGINE=InnoDB;
```

There is no separate primary key, but both `tenant_id` and `external_id` are `NOT NULL`; the composite unique index is a clustered index candidate. Uniqueness is evaluated across the pair `(tenant_id, external_id)`, not each column individually.

### If Multiple Qualifying Unique Indexes Exist

When there is no primary key and multiple unique indexes exist whose columns are all `NOT NULL`, InnoDB chooses the first qualifying unique index. You should not design around this implicit ordering if an explicit primary key can be declared. An explicitly declared primary key lets the schema communicate row identity accurately and avoids relying on the engine's fallback choice.

## 5. Unique Indexes with Nullable Columns Do Not Qualify

MySQL allows multiple rows to contain `NULL` values in a unique index. `NULL` is not treated as an equal value under standard unique checking rules, so a unique index with a nullable column does not guarantee every row has a complete unique key.

Example:

```sql
CREATE TABLE imported_contacts (
    email VARCHAR(254) NULL,
    display_name VARCHAR(120) NOT NULL,
    UNIQUE KEY uq_imported_contacts_email (email)
) ENGINE=InnoDB;
```

You can insert multiple rows with `email = NULL`:

```sql
INSERT INTO imported_contacts (email, display_name)
VALUES
    (NULL, 'Contact A'),
    (NULL, 'Contact B'),
    ('a@example.test', 'Contact C');
```

The unique index still prevents two rows from having the same non-NULL email, but allows multiple NULLs. Because the key column is nullable, `uq_imported_contacts_email` does not qualify as a fallback clustered index. If the table has no primary key or other qualifying unique index, InnoDB uses a hidden row ID.

The same applies to a composite unique index:

```sql
CREATE TABLE tenant_contacts (
    tenant_id BIGINT UNSIGNED NOT NULL,
    email VARCHAR(254) NULL,
    display_name VARCHAR(120) NOT NULL,
    UNIQUE KEY uq_tenant_email (tenant_id, email)
) ENGINE=InnoDB;
```

Even though `tenant_id` is non-NULL, the nullable `email` disqualifies the composite unique index from serving as the clustered index. Multiple rows can exist within the same tenant with a NULL email.

If the business requires email to be present and unique, declare `email NOT NULL`. If email is genuinely optional, choose a dedicated primary key or another unique key whose columns are all `NOT NULL`.

## 6. What Is the 6-Byte Hidden Row ID?

When an InnoDB table has neither a primary key nor a qualifying unique index, the engine automatically creates a hidden clustered index on an internal row ID column. This index is commonly called `GEN_CLUST_INDEX`.

Characteristics of the hidden row ID:

- The row ID is 6 bytes long.
- InnoDB automatically generates and manages the value; the row ID increases monotonically as new rows are added.
- The application does not declare this column.
- The row ID serves as the key of the hidden clustered index.
- It does not appear as a SQL column that SELECT can read or JOIN on.
- Applications cannot use the hidden row ID as a primary key, foreign key, or API key.
- The hidden row ID is not a user-declared `AUTO_INCREMENT` column.

The hidden row ID allows InnoDB to still have a clustered index even when the schema does not provide a suitable unique key. However, it does not replace the role of an explicit row identifier in the application data model.

### The Hidden Row ID Is Not a Key Design Solution

If a table lacks a primary key or suitable unique key:

- The application struggles to reference a row stably using an explicit business key.
- Updating or deleting a specific duplicate record accurately becomes difficult.
- Other tables cannot reference the hidden row ID with a foreign key.
- Sync tools, CDC, or reconciliation jobs may struggle to uniquely identify each row if source data lacks an identifier.
- InnoDB still has to store an internal row ID, yet secondary indexes cannot use a meaningful application key.

When designing new tables, declare an explicit primary key. For legacy tables without a primary key, evaluate duplicate data and choose an appropriate key before adding the constraint.

## 7. The Hidden Row ID Is Not Visible in SQL Queries

Suppose a table is created as follows:

```sql
CREATE TABLE raw_import_rows (
    source_name VARCHAR(40) NOT NULL,
    source_ref VARCHAR(100) NULL,
    imported_at DATETIME NOT NULL,
    raw_payload JSON NOT NULL,
    KEY idx_raw_import_source (source_name)
) ENGINE=InnoDB;
```

The table has no primary key. There is no unique index either; `idx_raw_import_source` is nonunique. InnoDB needs a clustered index and will use the hidden row ID.

You can run:

```sql
SHOW CREATE TABLE raw_import_rows;
SHOW INDEX FROM raw_import_rows;

SELECT *
FROM raw_import_rows;
```

These statements display the schema, user-declared indexes, and SQL-visible data. The hidden row ID is not displayed as a column in `SELECT *` and is not a SQL-visible index that applications can query.

Therefore, you cannot write `WHERE DB_ROW_ID = ...` or create a foreign key referencing `GEN_CLUST_INDEX`. To give every row an explicit identifier, add a schema-managed primary key.

## 8. The Primary Key Affects Every Secondary Index

In InnoDB, each secondary index entry contains the secondary key columns along with the primary key to locate the row in the clustered index. If the primary key consists of many columns or has long values, those columns increase the size of every secondary index.

More generally, a secondary index needs to carry the **clustered key** to locate the row. When the table has a primary key, the clustered key is the primary key. If there is no primary key and InnoDB selects a qualifying unique index, that unique index's columns serve as the clustered key. If the engine must use the hidden row ID, secondary indexes use the internal row ID as the locator.

Example:

```sql
CREATE TABLE order_items_wide_pk (
    tenant_code VARCHAR(40) NOT NULL,
    order_code VARCHAR(60) NOT NULL,
    line_number INT NOT NULL,
    product_id BIGINT UNSIGNED NOT NULL,
    quantity INT NOT NULL,
    PRIMARY KEY (tenant_code, order_code, line_number),
    KEY idx_order_items_product (product_id)
) ENGINE=InnoDB;
```

The secondary index `idx_order_items_product` needs to store `product_id` and the primary key columns to locate the row. A long composite primary key makes secondary index entries larger than a short numeric primary key does.

When the PK is wide:

- Secondary indexes consume more storage space.
- Each page fits fewer entries, which can increase page counts and I/O.
- The buffer pool must hold more index data for the same number of rows.
- INSERT/UPDATE operations can generate more index write and maintenance work.
- Child tables referencing the composite key must also carry the corresponding key components.

This is why a short surrogate primary key is often advantageous for OLTP tables with many secondary indexes. However, if a natural key is short, stable, and fits the workload, using it as the primary key can also be a good choice.

## 9. Choosing a Natural Key or a Surrogate Key?

A **natural key** is a key derived from business data, such as a country code, product code, or identifier assigned by a business system. A **surrogate key** is a technical key created solely to identify rows, such as `BIGINT AUTO_INCREMENT`.

| Criterion | Natural key | Surrogate key |
|---|---|---|
| Business meaning | Has direct meaning | Carries no business meaning. |
| Stability | Can change when business rules change | Usually immutable over the row's lifecycle. |
| Size | Can be long or composite across multiple columns | Usually short, e.g., BIGINT. |
| Uniqueness | Must be enforced via constraints | Enforced by the primary key. |
| References from other tables | May require composite keys or long strings | Usually simple via a single column. |
| Readability | Easy to understand during business lookups | Requires a JOIN to retrieve business details. |

A natural key is suitable as a primary key when it is:

- Unique across the entire data scope.
- Always populated, never NULL.
- Short and space-efficient.
- Stable, changing rarely or never.
- Governed by clear normalization rules.

If the business key is long, mutable, or scoped by tenant/context, a surrogate key is usually easier to manage. Keep a unique constraint on the natural key to protect business uniqueness.

## 10. Surrogate Primary Key and Business Unique Key Design Pattern

A common pattern is using a short numeric primary key for the clustered index while placing a unique index on the business code:

```sql
CREATE TABLE inventory_items (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    tenant_id BIGINT UNSIGNED NOT NULL,
    item_code VARCHAR(80) NOT NULL,
    item_name VARCHAR(160) NOT NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uq_inventory_tenant_item (tenant_id, item_code),
    KEY idx_inventory_created_at (created_at)
) ENGINE=InnoDB;
```

In this design:

- `id` is a short and stable clustered primary key.
- `(tenant_id, item_code)` ensures item codes are unique within each tenant.
- `created_at` has a secondary index for time-based queries.
- Secondary indexes include `id` to locate rows in the clustered index.

Do not drop the business unique constraint just because a surrogate primary key was added. The two keys solve different problems: the surrogate key identifies the row; the business unique key prevents duplicate business data.

## 11. Composite Primary Keys: When Should You Use Them?

A primary key can consist of multiple columns:

```sql
CREATE TABLE order_lines (
    order_id BIGINT UNSIGNED NOT NULL,
    line_number INT UNSIGNED NOT NULL,
    product_id BIGINT UNSIGNED NOT NULL,
    quantity INT UNSIGNED NOT NULL,
    PRIMARY KEY (order_id, line_number),
    KEY idx_order_lines_product (product_id)
) ENGINE=InnoDB;
```

The key `(order_id, line_number)` clearly expresses that a line item is identified within the scope of an order. This is a reasonable choice if line items do not have independent identifiers and queries frequently access data by `order_id`.

However, composite primary keys have implications:

- Every component is `NOT NULL`.
- Column order affects leftmost-prefix lookups.
- Secondary indexes store the primary key components.
- Foreign keys referencing the primary key must use the exact matching components and order.
- If the composite key is long, every secondary index can grow larger.

Choose a composite primary key when the columns form a natural, stable identifier that benefits queries. If the composite key is long or frequently carried across many tables, consider a surrogate key plus a unique constraint on the business pair.

## 12. Nullable Unique Keys and Fallback Key Choices

If business data has optional values, do not force `NOT NULL` solely to make a unique index qualify as the clustered key. Instead, separate row identity from optional attributes.

Example:

```sql
CREATE TABLE external_accounts (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    provider VARCHAR(40) NOT NULL,
    external_account_id VARCHAR(120) NULL,
    display_name VARCHAR(120) NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uq_provider_external_account (
        provider,
        external_account_id
    )
) ENGINE=InnoDB;
```

`id` always identifies a row. The composite unique key protects populated external account IDs per provider; multiple rows with `external_account_id = NULL` remain permitted under MySQL's unique semantics. This is a clean way to model cases where an external ID may not yet be assigned.

If the business rule requires each provider to have at most one row without an external ID, a nullable composite unique index does not enforce that rule automatically. Model the unassigned state appropriately or use other constraints/logic; do not rely on clustered-key selection to solve business uniqueness.

## 13. Why Should a Primary Key Be Short and Stable?

Because the primary key is embedded into secondary indexes, its size and stability affect the entire index structure.

Generally suitable criteria:

- Choose a data type large enough for the expected row count without being overly wide.
- Use `BIGINT UNSIGNED` when a large value range is needed; `INT UNSIGNED` may suffice for smaller tables.
- Avoid long strings as primary keys unless there is a clear business benefit.
- Avoid changing the primary key after a row is created.
- Choose composite key column order based on identity and access patterns.
- Evaluate the key's impact on secondary indexes, foreign keys, and storage size.

`AUTO_INCREMENT` is a common way to generate monotonically increasing surrogate keys, though not the only option. Application-generated IDs or a natural key can be used if they meet requirements. If using UUIDs, consider a `BINARY(16)` representation instead of `CHAR(36)` strings to reduce size; random UUIDs can still scatter inserts more than monotonically increasing keys.

Do not use timestamps or email addresses as primary keys simply because they appear unique at the moment. Emails can change; timestamps can collide; business strings can change rules or uniqueness scope.

## 14. Changing a Primary Key After a Table Already Has Data

The primary key determines the clustered index. When adding, dropping, or altering a primary key, InnoDB may have to rebuild the clustered index and related secondary indexes. This can be expensive in terms of I/O, CPU, temporary space, and impact on the table's write availability.

Example of altering a key on a test table:

```sql
ALTER TABLE imported_contacts
    ADD COLUMN id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY;
```

Before running on a large table, check the MySQL version, applicable DDL algorithms, metadata locks, rebuild duration, free disk space, replica lag, and deployment window. Do not assume every primary key change is instant or non-blocking.

If a table already contains duplicate data, adding a new primary key must ensure newly generated values are unique. For large tables, create a dedicated migration plan, test on a copy of the data, and have a rollback plan ready.

## 15. Inspecting Primary Keys and Unique Indexes in the Schema

### Viewing Table Definitions

```sql
SHOW CREATE TABLE customers;
SHOW INDEX FROM customers;
```

`SHOW CREATE TABLE` shows the primary key, unique keys, nullability, and columns. `SHOW INDEX` displays SQL-visible indexes, including `PRIMARY`, unique secondary indexes, and nonunique secondary indexes.

### Viewing Indexes in INFORMATION_SCHEMA

```sql
SELECT
    INDEX_NAME,
    NON_UNIQUE,
    SEQ_IN_INDEX,
    COLUMN_NAME,
    SUB_PART,
    INDEX_TYPE
FROM information_schema.statistics
WHERE TABLE_SCHEMA = DATABASE()
  AND TABLE_NAME = 'customers'
ORDER BY INDEX_NAME, SEQ_IN_INDEX;
```

`NON_UNIQUE = 0` indicates a unique index. `SEQ_IN_INDEX` indicates the column order within the index; `SUB_PART` indicates whether the index uses a prefix.

### Checking Nullability of Key Columns

```sql
SELECT
    COLUMN_NAME,
    COLUMN_TYPE,
    IS_NULLABLE,
    COLUMN_KEY
FROM information_schema.columns
WHERE TABLE_SCHEMA = DATABASE()
  AND TABLE_NAME = 'customers'
ORDER BY ORDINAL_POSITION;
```

Combine index metadata and column metadata to determine which unique index has all components `NOT NULL`. Simply seeing `Non_unique = 0` in `SHOW INDEX` is insufficient to conclude that an index can serve as a fallback clustered index.

### Listing Unique Indexes Where All Columns Are NOT NULL

```sql
SELECT
    s.INDEX_NAME,
    COUNT(*) AS key_parts,
    SUM(c.IS_NULLABLE = 'YES') AS nullable_parts
FROM information_schema.statistics AS s
JOIN information_schema.columns AS c
  ON c.TABLE_SCHEMA = s.TABLE_SCHEMA
 AND c.TABLE_NAME = s.TABLE_NAME
 AND c.COLUMN_NAME = s.COLUMN_NAME
WHERE s.TABLE_SCHEMA = DATABASE()
  AND s.TABLE_NAME = 'tenant_external_objects'
  AND s.NON_UNIQUE = 0
  AND s.INDEX_NAME <> 'PRIMARY'
GROUP BY s.INDEX_NAME
HAVING SUM(c.IS_NULLABLE = 'YES') = 0;
```

This query helps find candidate unique indexes on tables without a primary key. Review the results alongside index creation order and actual DDL. If multiple candidates exist, InnoDB selects the first qualifying unique index; declaring an explicit primary key remains easier to maintain.

## 16. How Can the Hidden Row ID Be Observed?

The hidden row ID is an internal InnoDB detail, not a column exposed in the SQL schema. You cannot SELECT the row ID value directly or reference it from an application.

You can infer that a table requires the hidden row ID when:

1. The table uses InnoDB.
2. `SHOW CREATE TABLE` has no primary key.
3. There is no unique index in which all participating columns are `NOT NULL`.
4. All remaining indexes are nonunique or unique indexes with nullable columns.

Example:

```sql
SHOW CREATE TABLE raw_import_rows;
SHOW INDEX FROM raw_import_rows;
```

If the schema matches the conditions above, InnoDB uses the hidden clustered index. `SHOW INDEX` does not expose a `row_id` column for applications to query; `GEN_CLUST_INDEX` is an internal structure, not a user-declared index.

Do not attempt to access the hidden row ID via internal names, assume SELECT order reflects row ID, or treat row position as an identifier. If you need to reference individual rows, create an explicit key.

## 17. Workflow for Choosing Keys When Designing a New Table

When designing an InnoDB table, you can follow this sequence:

1. Define the grain: what entity or event does one row represent?
2. Determine which business attributes must be unique and within what scope.
3. Check whether a natural key always exists, is stable, and is compact.
4. If a natural key fits, consider using it as the primary key.
5. If the natural key is long, nullable, mutable, or requires many columns, use a surrogate primary key and keep the business unique constraint.
6. If using a composite key, choose column order according to identity and access patterns.
7. Ensure every primary key column is `NOT NULL`.
8. Evaluate primary key size since it is stored in secondary indexes.
9. Check foreign keys and child tables referencing the key.
10. Use `SHOW CREATE TABLE`, `SHOW INDEX`, and metadata to verify the structure after creation.

The goal is not merely to avoid the hidden row ID. The goal is to establish an identifier that is clear, stable, business-unique, and efficient for clustered and secondary indexes.

## 18. Common Mistakes

| Mistake | Consequence | How to handle |
|---|---|---|
| Thinking a table without a primary key has no clustered index | Misunderstands InnoDB storage structure | InnoDB uses a qualifying unique NOT NULL index or a hidden row ID. |
| Thinking every unique index is a clustered key candidate | Overlooks unique indexes with nullable columns | Check `IS_NULLABLE` for all key parts. |
| Thinking nullable unique indexes disallow multiple NULLs | Import data fails or schema is misdesigned | Understand MySQL unique semantics; use a separate PK if NULL is valid. |
| Thinking a unique index replaces a primary key in every respect | Lacks an explicit identifier named PRIMARY | Declare a primary key when the model needs explicit identity. |
| Choosing a long string or overly wide composite primary key | Large secondary indexes consuming buffer pool memory | Prefer short, stable keys; keep separate business unique keys when needed. |
| Using email or a mutable attribute as PK | Key changes trigger index and reference updates | Use a surrogate key or a more stable natural key. |
| Relying on the hidden row ID in the application | Cannot query or reference rows stably | Create a SQL-visible primary key. |
| Thinking `AUTO_INCREMENT` is always contiguous without gaps | Application logic wrongly depends on ID sequence | Use IDs for identity, not as a continuous business counter. |
| Adding a primary key to a large table without planning | Resource-intensive rebuild and DDL impact | Evaluate online DDL, metadata locks, space, and duration beforehand. |
| Dropping the business unique constraint after adding a surrogate PK | Duplicate business data is permitted | Keep unique indexes matching the business scope. |

## 20. Key Takeaways to Remember

- InnoDB stores full rows in the leaf pages of the clustered index.
- A declared primary key is always the clustered index.
- Without a primary key, InnoDB picks the first unique index where all key columns are `NOT NULL`.
- A unique index with nullable columns does not qualify to replace the primary key because MySQL allows multiple NULLs.
- Without a primary key or qualifying unique index, InnoDB creates the hidden clustered index `GEN_CLUST_INDEX` on an internal 6-byte row ID.
- The hidden row ID is not a SQL-visible column and cannot be used in SELECT, JOIN, or as a foreign key.
- Secondary index entries carry primary key columns to locate rows; wide primary keys make every secondary index larger.
- Choose a primary key that is short, stable, unique, and non-NULL.
- A natural key fits if it is short, stable, and unique; otherwise, use a surrogate key alongside a business unique constraint.
- A composite primary key makes sense when its components form a natural identifier, though ordering and size must be weighed.
- Altering a primary key can rebuild the clustered index and secondary indexes; plan carefully for large tables.
- Use `SHOW CREATE TABLE`, `SHOW INDEX`, and `INFORMATION_SCHEMA` to verify structure and nullability.

By choosing an explicit primary key or qualifying unique key, you control which clustered index InnoDB uses and avoid relying on the hidden row ID. A short, stable, business-aligned key also keeps secondary indexes compact, makes row access more efficient, and keeps the schema easier to maintain.
