# GTID Divergence, Duplicate Server UUIDs, and Improper Environment Clones

This lesson belongs to the **DATABASE_MYSQL** module. When building replicas, restoring from backups, copying data directories, or creating staging environments from production, MySQL must clearly distinguish each server and its transaction history. Common errors include GTID mismatches between source and replica, errant transactions on a replica, purged binary logs still needed by a replica, two servers sharing the same server UUID, or a clone accidentally rejoining the production topology.

These scenarios directly impact data consistency. Never fix them by deleting files, setting GTIDs, or resetting binary logs on guesswork. First identify which server is the authoritative data source, compare GTID sets, inspect each node's identity, and clarify the clone's purpose: building a new replica or creating an isolated environment.

## 1. GTIDs and Server Identity in MySQL

A GTID (Global Transaction Identifier) uniquely identifies a transaction written to the binary log. A GTID has the form:

~~~text
source_uuid:transaction_number
~~~

Example:

~~~text
24bc7850-2c16-11ef-a1c4-0242ac120002:125
~~~

The UUID identifies the originating server that created the transaction; the number is the transaction's sequence number in that origin's GTID stream. GTIDs help MySQL track which transactions have executed, which remain to be transmitted, and prevent applying the same GTID twice in replication.

A MySQL server has two distinct identifiers:

- **server_id:** an integer configured in the configuration file or at startup. It must be unique across a replication topology.
- **server_uuid:** a UUID generated by MySQL and persisted in `auto.cnf` inside the data directory. It serves as the source component of GTIDs and must be unique across instances participating in a topology.

`server_id` and `server_uuid` do not substitute for one another. Changing `server_id` does not change `server_uuid`; conversely, generating a new UUID does not make `server_id` unique.

### 1.1. Key GTID Sets

MySQL exposes several variables and status fields:

| Name | Meaning |
|---|---|
| `GTID_EXECUTED` | Set of GTIDs executed on the instance |
| `GTID_PURGED` | Set of executed GTIDs whose binary logs have been purged from the instance |
| `Retrieved_Gtid_Set` | On a replica, set of GTIDs fetched from the source by the receiver thread |
| `Executed_Gtid_Set` | On a replica, set of GTIDs executed by the applier |
| `GTID_SUBSET(set1, set2)` | Returns 1 if `set1` is a subset of `set2` |
| `GTID_SUBTRACT(set1, set2)` | Returns GTIDs present in `set1` that are not in `set2` |

Check variables on each instance:

~~~sql
SELECT
    @@GLOBAL.server_id AS server_id,
    @@GLOBAL.server_uuid AS server_uuid,
    @@GLOBAL.gtid_mode AS gtid_mode,
    @@GLOBAL.enforce_gtid_consistency AS enforce_gtid_consistency,
    @@GLOBAL.log_bin AS log_bin,
    @@GLOBAL.gtid_executed AS gtid_executed,
    @@GLOBAL.gtid_purged AS gtid_purged;
~~~

`GTID_EXECUTED` is the executed transaction history. `GTID_PURGED` is a subset of that history, not an arbitrary flag you can set to pretend a replica already has data. Assigning GTIDs that do not correspond to real data causes replication to skip transactions the instance never actually applied.

## 2. Identifying GTID Divergence

In a simple topology, suppose the source has GTID set S and the replica has GTID set R. Three cases must be distinguished:

1. **Replica missing transactions:** some GTIDs exist on the source but are not yet in the replica's `GTID_EXECUTED`.
2. **Replica has extra transactions (errant transactions):** some GTIDs exist on the replica that do not exist on the source.
3. **Both sides have diverged histories:** each side holds distinct GTIDs, so neither set is a full subset of the other.

Example:

~~~text
Source:
  uuid-A:1-120

Replica:
  uuid-A:1-100
~~~

The replica is missing transactions 101 through 120. If the source still retains binary logs containing those GTIDs and replication is healthy, the replica can fetch and apply the missing range.

Another example:

~~~text
Source:
  uuid-A:1-120

Replica:
  uuid-A:1-120
  uuid-B:1
~~~

The replica has an extra GTID `uuid-B:1`. This could be a transaction written directly on the replica when it should not have accepted writes, or introduced from a different data history. This is an errant transaction requiring investigation.

### 2.1. Checking Asynchronous Replication Status

On MySQL 8.0.22 and later, run:

~~~sql
SHOW REPLICA STATUS\G
~~~

Older versions use:

~~~sql
SHOW SLAVE STATUS\G
~~~

Fields to read:

- `Replica_IO_Running` and `Replica_SQL_Running`: status of receiver and applier threads.
- `Last_IO_Errno`, `Last_IO_Error`: errors connecting or receiving binary logs.
- `Last_SQL_Errno`, `Last_SQL_Error`: errors applying transactions.
- `Retrieved_Gtid_Set`: GTIDs received from source.
- `Executed_Gtid_Set`: GTIDs executed on replica.
- `Auto_Position`: whether GTID auto-position is enabled.
- `Seconds_Behind_Source`: estimated lag; `NULL` does not mean the replica is synced.

Field names differ in older versions, such as `Slave_IO_Running` or `Seconds_Behind_Master`. Use the names matching your running version.

Never conclude a replica is in sync just because both threads show `Yes`. Compare GTID sets, inspect recent errors, and confirm transactions were executed.

### 2.2. Comparing GTID Sets Using MySQL Functions

Example hypothetical source and replica GTID sets:

~~~sql
SET @source_gtids =
  '24bc7850-2c16-11ef-a1c4-0242ac120002:1-120';

SET @replica_gtids =
  '24bc7850-2c16-11ef-a1c4-0242ac120002:1-100';

SELECT
    GTID_SUBSET(@replica_gtids, @source_gtids)
        AS replica_is_subset_of_source,
    GTID_SUBTRACT(@source_gtids, @replica_gtids)
        AS missing_on_replica,
    GTID_SUBTRACT(@replica_gtids, @source_gtids)
        AS extra_on_replica;
~~~

Expected results:

- `replica_is_subset_of_source` equals 1.
- `missing_on_replica` contains GTID range 101-120.
- `extra_on_replica` is empty.

In production, capture actual GTID sets from each server and run the comparison. Never substitute example strings for real server data.

If GTID sets are huge, output can be long. Save inspection results into a controlled incident record and avoid leaking unnecessary sensitive metadata.

### 2.3. Retrieved Differs from Executed

A replica may have received GTIDs from the source without executing all of them yet. Then `Retrieved_Gtid_Set` exceeds `Executed_Gtid_Set`. This occurs normally while the applier drains a backlog.

Never use `Retrieved_Gtid_Set` as proof that transactions were applied to tables. To confirm completion, wait for the applier to finish and check `Executed_Gtid_Set`.

You can use the wait function:

~~~sql
SELECT WAIT_FOR_EXECUTED_GTID_SET(
    '24bc7850-2c16-11ef-a1c4-0242ac120002:1-120',
    30
) AS wait_result;
~~~

The function returns 0 when the requested GTID set has executed, 1 on timeout, and `NULL` on error. Timeout is in seconds. Pass the real target GTID set rather than copying the example string.

## 3. Common Causes of GTID Divergence

### 3.1. Direct Writes on a Replica

A replica is meant to be read-only, yet an application, admin account, or background job writes data to it. That transaction generates a GTID stamped with the replica's own UUID. When compared with the source, that GTID becomes an errant transaction.

Check:

- Did an application connect to the replica endpoint by mistake?
- Did an admin account or job execute DML directly on the replica?
- Did any session temporarily disable `read_only`/`super_read_only`?
- Was a migration or maintenance task run on a standalone node?

Related variables:

~~~sql
SELECT
    @@GLOBAL.read_only,
    @@GLOBAL.super_read_only,
    @@GLOBAL.server_uuid,
    @@GLOBAL.gtid_executed;
~~~

`read_only` and `super_read_only` help curb unintended writes, yet do not replace privilege separation and operational controls. Certain privileged accounts can bypass `read_only` depending on version and grants. Restrict write accounts and monitor configuration changes.

### 3.2. Initializing a Replica from a Misaligned Backup

A replica is restored from backup, yet GTID metadata does not match the data inside the backup. For example, the backup holds data up to a point, while `GTID_PURGED` was set wrongly or `GTID_EXECUTED` was manually edited without reflecting actual rows in the data.

With auto-position enabled, source and replica exchange GTID sets to compute missing transactions. If metadata claims the replica already executed a GTID while the data lacks that transaction, the source will not resend it and data goes missing silently.

Therefore, backups must preserve exact GTID metadata and corresponding binary log coordinates. Use backup tools supporting consistent GTID capture; never construct GTID sets from guesses.

### 3.3. Source Purged Binary Logs Still Needed by the Replica

If the source deleted binary logs containing GTIDs the replica has not fetched yet, the source cannot resend those transactions. The replica fails stating the source already purged binary logs containing required GTIDs.

Inspect `GTID_PURGED` on the source and the missing set on the replica. If required GTIDs are absent from the source's binary logs, the standard recovery path is rebuilding the replica from a fresh backup/clone with matching GTID history, then reconnecting via auto-position.

Never fake `GTID_PURGED` on the replica to bypass the error. That alters transaction history metadata without restoring missing data.

### 3.4. Multiple Sources or Improper Promote/Failover

In topologies with multiple sources, multi-source replication, or post-failover states, each writer contributes GTIDs under its own UUID. Promoting a replica with diverged history and continuing writes on two branches causes GTID divergence.

Before failover:

- Designate exactly one authoritative writer.
- Ensure the promoted node has applied all required transactions.
- Fence off the old writer to prevent split-brain.
- Define clearly how remaining replicas repoint to the new source.
- Check GTID sets before and after role switches.

Never let both old and new sources accept writes simultaneously without a deliberately designed and verified multi-writer architecture.

## 4. Analyzing GTID Sets for Missing or Extra Transactions

During investigation, collect these values from both source and replica:

~~~sql
SELECT @@GLOBAL.server_uuid,
       @@GLOBAL.server_id,
       @@GLOBAL.gtid_executed,
       @@GLOBAL.gtid_purged;
~~~

On the replica, also save `SHOW REPLICA STATUS`. Then compare:

- GTIDs on source missing on replica: replica has not received/applied them or required binlogs were lost.
- GTIDs on replica absent from source: suspect errant transactions or the source was replaced by another branch.
- Unique GTIDs on both sides: determine divergence history and which node is authoritative.
- Identical GTID sets yet differing table data: GTID metadata alone does not prove data equality; verify data via checksums/row comparisons or dedicated verification tools.

### 4.1. Example Checking Errant GTIDs

Suppose source and replica have:

~~~sql
SET @source_gtids =
  '24bc7850-2c16-11ef-a1c4-0242ac120002:1-120';

SET @replica_gtids =
  '24bc7850-2c16-11ef-a1c4-0242ac120002:1-120,
   6c7b1b60-2c16-11ef-a1c4-0242ac120002:1';

SELECT GTID_SUBTRACT(@replica_gtids, @source_gtids)
       AS errant_gtids;
~~~

If the result contains the second UUID, the replica executed at least one GTID absent from the compared source's history. Investigate which session created that transaction, when, and what data changed.

You can check transaction history in Performance Schema if instrumentation and history still retain records, though history may be bounded or lost across restarts. Never assume Performance Schema preserves complete history forever.

## 5. Fixing a Replica Missing GTIDs

If the replica is simply behind and the source still retains all binary logs:

1. Check receiver connectivity and applier state.
2. Read `Last_IO_Error` and `Last_SQL_Error`.
3. Confirm the source has not purged required GTIDs.
4. Confirm no errant GTIDs complicate history.
5. Fix connectivity, replication privileges, or specific apply errors.
6. Let the replica resume fetching and applying transactions.
7. Wait for target GTIDs using `WAIT_FOR_EXECUTED_GTID_SET`.
8. Re-compare GTID sets after completion.

If the applier stopped due to a failing transaction, never skip the transaction just to flip the thread back to `Yes`. Understand the data or schema discrepancy on the replica, compare with the source, and repair consistently. Skipping events can permanently diverge replica data from the source.

### 5.1. Configuring GTID Auto-Position

In MySQL 8.0.23 and later, source configuration uses updated statement names:

If the replica has a running channel, stop replication before changing settings:

~~~sql
STOP REPLICA;
~~~

~~~sql
CHANGE REPLICATION SOURCE TO
    SOURCE_HOST = 'source.example.net',
    SOURCE_PORT = 3306,
    SOURCE_USER = 'repl_user',
    SOURCE_AUTO_POSITION = 1;
~~~

Credentials must be supplied via your organization's secret workflow; never embed real passwords in docs, logs, or shell history. On older versions, the command is `CHANGE MASTER TO` and the option is `MASTER_AUTO_POSITION = 1`.

Then:

~~~sql
START REPLICA;
SHOW REPLICA STATUS\G
~~~

This only configures connection settings and auto-positioning. It does not automatically repair missing data, errant GTIDs, duplicate UUIDs, or purged binary logs.

## 6. Recovering When the Source Purged Needed GTIDs

If the source no longer holds required binary logs, the replica cannot catch up merely by restarting threads.

Standard workflow:

1. Stop replication on the broken replica to stop futile retries.
2. Record `GTID_EXECUTED`, `GTID_PURGED`, `Retrieved_Gtid_Set`, `Executed_Gtid_Set`, and errors.
3. Confirm the current source is the authoritative data source.
4. Create a fresh backup/clone from the source or a fully synchronized healthy node.
5. Ensure the backup captures accurate GTID state.
6. Restore onto the target replica with its own `server_id` and `server_uuid`.
7. Verify `GTID_PURGED`/`GTID_EXECUTED` on the restored instance.
8. Configure replication using auto-position.
9. Wait for the replica to catch up and verify data.

Binary log retention must be long enough to cover incidents, detection, repair, and replica catch-up. Check:

~~~sql
SHOW VARIABLES LIKE 'binlog_expire_logs_seconds';
SHOW BINARY LOGS;
~~~

Verify variable names and binlog display commands against your version. Older versions may use `expire_logs_days`. Never manually purge logs before verifying every replica and backup dependency.

## 7. Errant Transactions: Why You Must Not Arbitrarily Erase GTIDs

An errant transaction is a transaction executed on a node that does not belong to the history of the source it is supposed to follow. It signals that data history may have branched.

For example, an admin runs an `UPDATE` directly on a replica. A new GTID gets recorded in the replica's `GTID_EXECUTED`. When replication resumes, auto-position tells the source not to resend already-present GTIDs—yet the local transaction mutated data in a way the source lacks.

Avoid:

- Manually deleting `auto.cnf` to "erase" a transaction's GTID.
- Resetting `GTID_PURGED` to force two sets to look alike.
- Running `RESET MASTER` or binary log resets on a node holding data that must be preserved.
- Skipping failing transactions without reconciling data.
- Returning a replica with errant GTIDs to production merely because replication threads show running.

Resolution depends on data validity:

- If the node holds no independent data worth keeping, rebuilding the node from the authoritative source is cleaner and safer.
- If the errant transaction contains legitimate business changes that must be kept, reconcile and apply those changes onto the source via controlled migration/DML, then rebuild the replica or resync per plan.
- If a source was promoted and older history must be reconciled, execute a topology-aware failover/rejoin plan instead of hand-editing GTID metadata.

GTIDs track transaction history, not a tool to merge two diverged datasets.

## 8. Duplicate Server UUID After Cloning a Data Directory

MySQL stores its server UUID in `auto.cnf` inside the data directory. Copying an entire data directory at the filesystem level copies `auto.cnf` too. When both source and clone boot with the same UUID, replication stops because two instances share a server UUID.

A typical error message reads:

~~~text
The slave I/O thread stops because master and slave have equal
MySQL server UUIDs; these UUIDs must be different for replication to work.
~~~

Thread names in older messages may use legacy terminology. The meaning remains identical: source and replica share the same `server_uuid`.

### 8.1. Checking UUID and `server_id`

On each instance:

~~~sql
SELECT
    @@hostname AS hostname,
    @@port AS port,
    @@server_id AS server_id,
    @@server_uuid AS server_uuid;
~~~

Two nodes in the same replication topology need distinct `server_id`s and distinct `server_uuid`s. Never check only hostnames or IPs: two machines with different hostnames still share an identical UUID if cloned from the same data directory copy.

### 8.2. Why Changing `server_id` Alone Is Not Enough

GTIDs embed the originating UUID, not `server_id`. When two nodes share the same `server_uuid`, changing `server_id` alone does not make their GTID identities distinct.

For clones created by copying a data directory, inspect `auto.cnf`. If UUIDs collide, stop the clone instance and follow the procedure to generate a new UUID on the clone only. Never delete or edit `auto.cnf` on a running instance.

### 8.3. Generating a New UUID for a Manual Clone

For a standalone data directory copy, the general procedure is:

1. Isolate the clone from production networks and stop MySQL on the clone.
2. Confirm the clone's exact data directory; never touch the source by mistake.
3. Back up the current `auto.cnf` file for auditability.
4. Remove `auto.cnf` on the clone after `mysqld` has completely stopped.
5. Configure a new, topology-unique `server_id` in the clone's configuration.
6. Start the clone; MySQL generates a fresh server UUID when no valid `auto.cnf` exists.
7. Read back `server_uuid` and `server_id` via SQL.
8. Connect the clone into the topology only after verifying its fresh identity and valid GTID state.

Example post-start check:

~~~sql
SELECT @@GLOBAL.server_id, @@GLOBAL.server_uuid;
~~~

Never invent a UUID by hand-editing `auto.cnf` while the server runs. Also never delete `auto.cnf` on the source to fix a replica error; operations must target the clone instance exclusively.

When using specialized clone/backup tools, read the tool and MySQL version docs to understand how instance identity is handled. Even when a tool updates metadata automatically, always verify `server_uuid` and `server_id` after cloning.

## 9. Cloning to Build a Replica vs. Cloning an Independent Environment

These two cloning goals carry different requirements.

| Aspect | Clone to Build a Replica | Clone for Independent Dev/Test |
|---|---|---|
| Data | Must stay consistent with source | Can use a masked/redacted snapshot |
| GTID history | Must preserve exact backup GTID metadata | Decide whether to keep history or detach into an independent environment |
| `server_uuid` | Must differ from source and other replicas | Must be distinct; never reuse production UUID |
| `server_id` | Unique in the replication topology | Distinct ID; avoid collisions if any replication connects |
| Replication channel | Configured to connect to target source | Must not auto-connect to production |
| Network | Allowed to reach source and required endpoints | Isolated or strictly allowlisted |
| Credentials | Uses restricted replication account | Replace/remove production secrets |
| Group Replication | Joins group only with valid identity and topology config | Never joins production cluster |

### 9.1. Cloning to Build a New Replica

When cloning to replace a replica or scale out topology:

- Preserve GTID metadata accompanying the backup.
- Assign a unique `server_uuid` and `server_id` to the recipient.
- Ensure GTID mode and `enforce_gtid_consistency` match the topology.
- Configure the source with GTID auto-position once all prerequisites are met.
- Confirm the source retains required binary logs if not restoring from the latest backup.
- Never reset GTID history merely to strip an old UUID; doing so breaks auto-position.
- Verify the replica catches up before serving read traffic.

A clone from the source holds data up to a specific GTID point. Upon restore, GTID state must reflect that exact point so the source sends only missing transactions.

### 9.2. Cloning into an Independent Dev/Test Environment

A production clone brought into dev/test must be isolated before opening applications or permitting network traffic:

1. Block network access to production source, replicas, and Group Replication.
2. Disable automatic replication startup on initial boot if copied config contains production channels.
3. Set a unique `server_id` and generate a fresh `server_uuid` if UUID was copied.
4. Inspect replication channels and drop channel configs only after confirming this environment will not act as a replica.
5. Check `group_replication_start_on_boot` and Group Replication settings; never let a clone join the production cluster.
6. Replace hostnames, ports, endpoints, application accounts, and secrets.
7. Mask personal/sensitive data per environment policy.
8. Check event scheduler, cron/jobs, webhooks, email/SMS, queue consumers, and external integrations so the clone never triggers real side effects.
9. Verify applications connect solely to dev/test databases.

You can use startup option `skip_replica_start` to prevent replica threads from auto-starting during isolation. Verify exact option name and behavior for your MySQL version. This is a startup safeguard, not a substitute for auditing channels and network rules.

If the independent clone no longer needs replication metadata, consider `STOP REPLICA` followed by `RESET REPLICA ALL` on that instance after recording configuration and confirming no channel reuse is needed. This removes replica connection/relay log metadata without erasing `GTID_EXECUTED` or converting data into a clean new GTID history. On older versions, commands are `STOP SLAVE` and `RESET SLAVE ALL`. Never confuse this with resetting GTIDs or binary logs.

## 10. Group Replication and Duplicate UUIDs

Group Replication relies on member identities and transaction exchange across nodes. Duplicate UUIDs or non-unique `server_id`s prevent members from joining the group or cause identity collisions.

Check:

~~~sql
SELECT MEMBER_ID, MEMBER_HOST, MEMBER_PORT,
       MEMBER_STATE, MEMBER_ROLE
FROM performance_schema.replication_group_members;
~~~

On each node, inspect:

~~~sql
SELECT @@GLOBAL.server_id,
       @@GLOBAL.server_uuid,
       @@GLOBAL.group_replication_group_name,
       @@GLOBAL.group_replication_local_address,
       @@GLOBAL.group_replication_start_on_boot;
~~~

Before adding a cloned node to a group:

- Assign a unique `server_uuid` and `server_id`.
- Set a unique `group_replication_local_address` that does not collide with any existing member.
- Verify `group_replication_group_name` matches the intended group.
- Check seed lists and network endpoints.
- Verify recovery credentials and TLS.
- Use MySQL Shell / AdminAPI or an approved cluster procedure to add the member.
- Wait for the member to reach `ONLINE` and confirm quorum before proceeding.

Never copy Group Replication configuration verbatim from a source to a clone and start both simultaneously. The clone could accidentally join the production group with a colliding identity or address.

## 11. Dangerous Reset Commands and Common Misconceptions

Certain commands heavily impact replication metadata or binary logs:

| Command | General Effect | What to Remember |
|---|---|---|
| `RESET REPLICA` | Clears relay logs and corresponding relay/replica state | Does not erase `GTID_EXECUTED` |
| `RESET REPLICA ALL` | Resets state and also deletes connection/channel config | Not a GTID history reset; older versions use `RESET SLAVE ALL` |
| `RESET MASTER` on older versions | Deletes binary logs and resets parts of GTID/binlog state | Can destroy history needed by replicas and backups |
| `RESET BINARY LOGS AND GTIDS` on MySQL 8.4 | Newer version's binary log and GTID reset command | Destructive operation; never use as routine troubleshooting |
| `SET GLOBAL gtid_purged` | Alters purged GTID metadata under strict preconditions | Does not materialize actual table data on the server |

Never run reset commands simply because GTID sets differ. Before using any reset, establish clear intent, MySQL version, backups, state of all replicas, and recoverability impact. For GTID divergence, rebuilding the replica from an authoritative source is almost always safer than hand-tweaking metadata to make sets appear alike.

## 12. End-to-End Investigation and Recovery Procedure

When detecting GTID mismatch, duplicate UUIDs, or bad clones:

### Step 1 — Isolate and Preserve Evidence

- Identify which node may be accepting unintended writes.
- If a clone risks connecting to production, isolate its network first.
- Never delete files, reset GTIDs, or flip source/replica roles before recording current state.
- Save error logs, `SHOW REPLICA STATUS`, `server_id`, `server_uuid`, and GTID sets.

### Step 2 — Identify the Authoritative Data Source

- Identify the legitimate writer at incident time.
- Check for failover, split-brain, or direct writes on replicas.
- Compare GTIDs and data across involved nodes.
- Never pick the authoritative node solely by larger GTID count; a higher GTID count does not guarantee more accurate data.

### Step 3 — Classify the Incident

- Replica merely missing GTIDs while source retains binlogs.
- Source purged GTIDs needed by replica.
- Replica has errant GTIDs.
- GTID metadata mismatches backup data.
- Duplicate `server_uuid` from copying a data directory.
- Duplicate `server_id` or clone auto-joining replication/cluster.
- Identical GTIDs yet differing actual data.

### Step 4 — Choose Recovery Path

- Replica missing GTIDs: fix receiver/applier and wait for catch-up.
- Purged binlogs: rebuild replica from fresh backup/clone.
- Errant transactions: reconcile and fix data, then rebuild node if needed.
- Duplicate UUID: isolate clone, assign fresh identity, and verify GTID state.
- Dev/test clone: sever production connections, audit channels/cluster, credentials, and external jobs.
- Group Replication: use proper member recovery and quorum procedures rather than arbitrarily bootstrapping a new group.

### Step 5 — Verify Post-Recovery

- Unique `server_id` and `server_uuid`.
- Matching GTID mode and consistency settings.
- GTID sets align in the expected direction.
- Receiver/applier or Group Replication member runs stably.
- Zero `Last_IO_Error`/`Last_SQL_Error`.
- Replica executed up to target GTIDs.
- Critical data reconciled.
- Dev/test clones cannot write or emit messages toward production.
- Backups and binary log retention meet future recovery goals.

## 13. Example: Rebuilding a Replica After Binary Logs Were Purged

Suppose replica R stayed offline too long. Source S purged binary logs R still needed. R can no longer catch up.

Sound workflow:

1. On R, record `server_uuid`, `server_id`, `GTID_EXECUTED`, and replication errors.
2. On S, verify `GTID_PURGED` and determine which transactions are gone from binary logs.
3. Stop replication on R and mark the node out of traffic rotation.
4. Take a fresh consistent backup from S or a fully synced healthy node.
5. Restore the backup onto R via a supported procedure.
6. Assign a new `server_id` if replacing the node; verify `server_uuid` differs from S and every other replica.
7. Verify `GTID_EXECUTED`/`GTID_PURGED` from the backup without tampering.
8. Configure `SOURCE_AUTO_POSITION = 1` and run `START REPLICA`.
9. Wait until R's `GTID_EXECUTED` covers target GTIDs.
10. Run data verification checks and return R to the read pool only once stable.

If restoring from a backup older than the current source, the source must still hold binary logs for every transaction since that backup coordinate. Otherwise, take a newer backup. This is why sufficient retention and backups with accurate GTID metadata are essential.

GTIDs reflect transaction history; `server_uuid` and `server_id` establish instance identity within a topology. When these values diverge or collide, preserve state, identify the authoritative data source, and classify the failure before acting. Rebuilding a replica from a backup with accurate GTID metadata is generally safer than manually editing GTID history; independent clones must be isolated and given distinct identities before connecting to any network near production.
