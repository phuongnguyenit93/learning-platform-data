# InnoDB Persistent Statistics, Sampling, and Auto-Recalculation

## Objectives

After this lesson, you will be able to:

- Explain why MySQL needs data statistics so the optimizer can estimate row counts and select an execution plan.
- Distinguish InnoDB persistent statistics from non-persistent statistics.
- Identify the roles of `innodb_stats_persistent`, `innodb_stats_auto_recalc`, and `innodb_stats_persistent_sample_pages`.
- Configure statistics at the instance level or per-table using `STATS_*` options.
- Read statistical data in `mysql.innodb_table_stats` and `mysql.innodb_index_stats`.
- Understand page sampling, cardinality, and the trade-off between accuracy and I/O cost.
- Proactively update statistics with `ANALYZE TABLE` after bulk data loads or major changes.
- Evaluate automatic statistics recalculation and handle cases where the optimizer uses stale estimates.
- Compare estimates against actual data using `EXPLAIN` and `EXPLAIN ANALYZE`.

Examples target MySQL 8.0/8.4 with InnoDB. Defaults and certain details may vary by version; verify on your target server before applying.

## 1. Why Does the Optimizer Need Statistics?

The MySQL optimizer must decide how to execute a SQL statement. For a multi-table `JOIN` query, it needs to estimate:

- How many rows each table has.
- Approximately how many rows the `WHERE` clause will retain.
- Whether a value in an index occurs frequently or rarely.
- Which index to use and in what order to read tables.
- Whether to use a nested-loop join or another suitable execution strategy.
- The expected costs of reading indexes, reading rows, and sorting.

The optimizer cannot read all data from every table just to decide the execution plan for each query. It relies on statistics to estimate cardinality and cost.

For example, an `orders` table with an index on `status`:

```sql
SELECT order_id, customer_id, created_at
FROM orders
WHERE status = 'PENDING';
```

If the optimizer estimates only 1% of orders are `PENDING`, using the index may make sense. If in reality 90% of rows are `PENDING`, a full table scan may be cheaper. Inaccurate statistics can lead the optimizer to choose an unsuitable plan.

### 1.1. Statistics Are Estimates, Not Exact Query Results

InnoDB statistics are generated by sampling index pages and estimating key distributions. Values such as table row count or index cardinality do not necessarily equal exact counts at query time.

This is by design: statistics need to be good enough to support plan selection at low cost. Sampling avoids scanning the entire index every time statistics are recalculated.

### 1.2. Statistics Directly Influence Execution Plans

Suppose a table has index `(status, created_at)`. If the optimizer evaluates `status = 'PENDING'` as highly selective, it may use the index to read a small subset. If the estimate is wrong and this status actually dominates the table, that plan may perform more index and clustered record accesses than a sequential scan.

Good statistics do not guarantee every plan is optimal, but stale or inaccurate statistics make it difficult for the optimizer to make good decisions.

## 2. What Are Persistent Statistics?

Persistent optimizer statistics are InnoDB index statistics stored on disk, allowing them to survive MySQL restarts. In MySQL 8.0/8.4, persistent statistics are enabled by default via `innodb_stats_persistent=ON`.

The system tables storing persistent statistics are:

- `mysql.innodb_table_stats`: table-level statistics.
- `mysql.innodb_index_stats`: index-level and index-prefix statistics.

Without persistent statistics, InnoDB uses in-memory non-persistent statistics. These statistics can be lost on server shutdown and recalculated when a table is opened or when certain operations require them. Because sampling can yield different estimates, execution plans may shift after a restart.

### 2.1. Benefits of Persistent Statistics

- Statistics persist across server restarts.
- Reduces the chance of execution plans changing solely because the server restarted and re-sampled statistics.
- Update timestamps can be inspected via `last_update`.
- Can be configured to recalculate automatically when data changes substantially.
- Sample page count can be tuned at the instance or table level.
- Helps investigate why the optimizer chose an unsuitable index or join order.

Persistent statistics improve stability, but they do not freeze execution plans. Plans can still change when statistics are updated, data changes, indexes/schemas change, or optimizer settings or MySQL versions change.

### 2.2. Checking Persistent Statistics Configuration

```sql
SHOW VARIABLES LIKE 'innodb_stats_persistent';
SHOW VARIABLES LIKE 'innodb_stats_auto_recalc';
SHOW VARIABLES LIKE 'innodb_stats_persistent_sample_pages';
```

In MySQL 8.0/8.4, typical defaults are:

| Variable | Default Value | Meaning |
|---|---:|---|
| `innodb_stats_persistent` | `ON` | Persist InnoDB index statistics to disk |
| `innodb_stats_auto_recalc` | `ON` | Automatically recalculate persistent statistics when a table changes significantly |
| `innodb_stats_persistent_sample_pages` | `20` | Number of index pages sampled when computing persistent statistics |

Always check actual values with `SHOW VARIABLES`; the instance configuration may have been changed by a DBA.

## 3. Configuring Persistent Statistics at the Instance Level

### 3.1. Enabling or Disabling Persistent Statistics

`innodb_stats_persistent` is a `GLOBAL` variable. It can be changed at runtime:

```sql
SET GLOBAL innodb_stats_persistent = ON;
```

This setting is stored per table at table creation time. It can be overridden per table with `STATS_PERSISTENT` in `CREATE TABLE` or `ALTER TABLE`.

Consequently, changing the `GLOBAL` variable does not automatically switch all existing tables from one mode to another. To change an existing table, use the table-level option and recalculate statistics as needed.

### 3.2. Enabling Automatic Recalculation

```sql
SET GLOBAL innodb_stats_auto_recalc = ON;
```

When enabled, InnoDB automatically recalculates persistent statistics if a table's data changes significantly. The default threshold is described as roughly 10% of the table's rows having changed.

Recalculation runs asynchronously in the background. Therefore, after a bulk `UPDATE`/`DELETE`/`INSERT` modifies more than the threshold, statistics are not necessarily updated immediately. There can be a delay of several seconds or longer depending on server load and state.

If you need fresh statistics immediately to evaluate or run an important query, run explicitly:

```sql
ANALYZE TABLE orders;
```

### 3.3. Adjusting Sample Page Count

```sql
SET GLOBAL innodb_stats_persistent_sample_pages = 64;
```

Increasing sample pages can improve cardinality estimate accuracy, but increases I/O and statistics computation time. Decreasing sample pages can make `ANALYZE TABLE` faster, but estimates become noisier.

A `GLOBAL` change applies to tables using the table-level default when statistics are recalculated. For a specific table, consider `STATS_SAMPLE_PAGES` instead of raising overhead across every table.

### 3.4. Changing Variables Does Not Refresh Statistics Automatically

After changing `innodb_stats_persistent_sample_pages`, do not assume existing statistics have been re-sampled. Run `ANALYZE TABLE` on the target tables to recalculate statistics using the new page count.

Similarly, enabling `innodb_stats_persistent` does not mean every existing table immediately gets fresh persistent statistics. Check table options and proactively analyze tables when needed.

## 4. Per-Table Configuration Using STATS_* Options

InnoDB allows tuning persistent statistics per table via table options:

| Option | Values | Meaning |
|---|---|---|
| `STATS_PERSISTENT` | `DEFAULT`, `0`, `1` | Choose persistent or non-persistent statistics for the table |
| `STATS_AUTO_RECALC` | `DEFAULT`, `0`, `1` | Enable/disable automatic recalculation of the table's persistent statistics |
| `STATS_SAMPLE_PAGES` | Positive integer | Number of index pages sampled when computing cardinality/statistics for the table |

### 4.1. Specifying at CREATE TABLE

```sql
CREATE TABLE orders (
    order_id BIGINT UNSIGNED NOT NULL,
    customer_id BIGINT UNSIGNED NOT NULL,
    status VARCHAR(20) NOT NULL,
    created_at DATETIME NOT NULL,
    total_amount DECIMAL(19,2) NOT NULL,
    PRIMARY KEY (order_id),
    KEY idx_orders_customer_created (customer_id, created_at),
    KEY idx_orders_status_created (status, created_at)
) ENGINE = InnoDB
  STATS_PERSISTENT = 1
  STATS_AUTO_RECALC = 1
  STATS_SAMPLE_PAGES = 64;
```

In this example, `orders` uses persistent statistics, enables automatic recalculation on significant data changes, and samples 64 index pages when estimating statistics.

### 4.2. Changing Options on an Existing Table

```sql
ALTER TABLE orders
    STATS_PERSISTENT = 1,
    STATS_AUTO_RECALC = 0,
    STATS_SAMPLE_PAGES = 64;
```

This example keeps persistent statistics enabled while disabling automatic recalculation specifically for `orders`. The DBA needs an explicit workflow to run `ANALYZE TABLE` after bulk loads or major distribution changes.

Changing table options does not replace recalculating statistics. After changing sample pages or enabling persistent statistics on a table, you can run:

```sql
ANALYZE TABLE orders;
```

### 4.3. Meaning of DEFAULT

`DEFAULT` lets the table inherit the corresponding `GLOBAL` configuration value:

```sql
ALTER TABLE orders
    STATS_PERSISTENT = DEFAULT,
    STATS_AUTO_RECALC = DEFAULT;
```

This is useful when returning a table to the instance-wide policy. `STATS_SAMPLE_PAGES` can be set explicitly so an important table uses a larger sample while other tables continue using the global value.

## 5. How Does InnoDB Sample Index Pages?

InnoDB does not need to scan every index record to estimate cardinality. When computing statistics, the engine samples index pages and uses the key distribution in the sample to estimate the number of distinct values.

This sampling method is commonly described as random dives: InnoDB reads randomly selected pages in the index, observes keys, and estimates the distribution across the entire index.

### 5.1. What Is Cardinality?

The cardinality of an index/prefix is the estimated number of distinct values in that key set. For instance, an index on `status` may have low cardinality if there are only `NEW`, `PAID`, and `CANCELLED` values; an index on `order_id` has high cardinality because every row has a distinct ID.

Cardinality helps the optimizer gauge selectivity. A predicate on an index with many distinct values generally filters a dataset better, though actual selectivity also depends on the specific value and data distribution.

### 5.2. How Does Sample Page Count Affect Results?

- Too small a sample: easily misses rare data regions or skewed distributions, causing cardinality estimates to fluctuate.
- Larger sample: provides more information for estimation, but requires reading more pages and increases `ANALYZE TABLE` duration.
- Large indexes or uneven distributions: generally more sensitive to sample size.
- Tables with many indexes and wide primary keys: statistics calculation cost can rise because InnoDB must analyze multiple index structures.

There is no single optimal sample count for every table. Adjust thoughtfully and compare both execution plan quality and analysis duration.

### 5.3. innodb_stats_persistent_sample_pages

This variable is `GLOBAL`, dynamic, and defaults to 20 in MySQL 8.0/8.4:

```sql
SHOW VARIABLES LIKE 'innodb_stats_persistent_sample_pages';
```

Example increasing the sample:

```sql
SET GLOBAL innodb_stats_persistent_sample_pages = 100;
ANALYZE TABLE orders;
```

Increasing the sample to 100 can stabilize estimates, though bigger is not always better. If `ANALYZE TABLE` becomes too slow, lower it or set a per-table value via `STATS_SAMPLE_PAGES`.

### 5.4. Per-Table STATS_SAMPLE_PAGES

```sql
ALTER TABLE orders
    STATS_SAMPLE_PAGES = 100;

ANALYZE TABLE orders;
```

This targets a single table with important indexes or hard-to-estimate distributions without increasing sample pages for all other tables.

## 6. Where Are Persistent Statistics Stored?

InnoDB stores persistent statistics in two system tables in the `mysql` schema.

### 6.1. mysql.innodb_table_stats

This table stores table-level statistics. Important columns:

| Column | Meaning |
|---|---|
| `database_name` | Schema containing the table |
| `table_name` | Table name |
| `last_update` | Timestamp when statistics were updated |
| `n_rows` | Estimated row count of the table |
| `clustered_index_size` | Clustered index page count per statistics |
| `sum_of_other_index_sizes` | Estimated total pages across secondary indexes |

Read statistics for a table:

```sql
SELECT
    database_name,
    table_name,
    last_update,
    n_rows,
    clustered_index_size,
    sum_of_other_index_sizes
FROM mysql.innodb_table_stats
WHERE database_name = DATABASE()
  AND table_name = 'orders';
```

`n_rows` is an estimate, not the exact result of `SELECT COUNT(*)`. Do not use this value for business logic requiring exact counts.

### 6.2. mysql.innodb_index_stats

This table stores statistics for each index and index prefix:

| Column | Meaning |
|---|---|
| `database_name`, `table_name` | Identifies the table |
| `index_name` | Index name |
| `last_update` | Timestamp when statistics were updated |
| `stat_name` | Statistic type, e.g., `n_diff_pfx01`, `n_leaf_pages`, `size` |
| `stat_value` | Estimated value |
| `sample_size` | Number of pages sampled for this estimate, if applicable |
| `stat_description` | Description of the prefix/structure being measured |

View index statistics:

```sql
SELECT
    index_name,
    stat_name,
    stat_value,
    sample_size,
    stat_description,
    last_update
FROM mysql.innodb_index_stats
WHERE database_name = DATABASE()
  AND table_name = 'orders'
ORDER BY index_name, stat_name;
```

### 6.3. Meaning of Common stat_name Values

- `n_diff_pfx01`: estimated distinct values for the prefix consisting of the first index column.
- `n_diff_pfx02`: estimated distinct values for the prefix consisting of the first two index columns.
- `n_diff_pfxNN`: continues for prefixes of the first NN index columns.
- `n_leaf_pages`: estimated number of leaf pages for the index.
- `size`: estimated total number of pages for the index.

For composite index `(customer_id, created_at)`, `n_diff_pfx01` reflects the estimated cardinality of `customer_id`; `n_diff_pfx02` reflects the distinct combinations of `(customer_id, created_at)`.

### 6.4. Do Not Edit Statistics Tables Directly in Normal Operations

`mysql.innodb_table_stats` and `mysql.innodb_index_stats` are InnoDB internal data. Manually modifying statistical values can cause the optimizer to use estimates that do not reflect actual data and complicate troubleshooting.

In normal operations, use `ANALYZE TABLE`, table options, and supported system variables. If experimenting with modified statistics in a research environment, keep backups, record original values, and understand how InnoDB loads and applies them; do not turn direct edits into a standard production practice.

## 7. Automatic Recalculation: Recalculating When Data Changes

Persistent statistics can be automatically recalculated by InnoDB when a table changes enough. The controlling variable is `innodb_stats_auto_recalc`, `ON` by default in MySQL 8.0/8.4.

### 7.1. The ~10% Row Threshold

When table data changes significantly—commonly described as more than 10% of rows—InnoDB marks statistics for update and performs recalculation in the background.

For example, a table with roughly 1,000,000 rows: if modified rows exceed the tracked threshold, InnoDB may trigger automatic recalculation. This is not a guarantee that after exactly 100,000 changes, analysis finishes instantaneously on the final DML statement.

The 10% threshold is a default trigger mechanism, not a business rule, and it does not guarantee statistics immediately reflect every distribution shift.

### 7.2. Automatic Recalculation Is Asynchronous

After a bulk load or large `UPDATE`, there may be a period during which statistics have not yet been recalculated. During that window, the optimizer may continue using old statistics.

If synchronization is needed before running the next workload, execute:

```sql
ANALYZE TABLE orders;
```

`ANALYZE TABLE` runs recalculation in the foreground, so the client receives a result once the operation finishes or fails. On large tables, this command can generate I/O and should be accounted for in operational planning.

### 7.3. Disabling Automatic Recalculation for a Table

```sql
ALTER TABLE orders
    STATS_AUTO_RECALC = 0;
```

When disabled, the DBA is responsible for refreshing statistics after significant changes. This can be useful if you need tight control over when statistics update to avoid unexpected plan changes during peak hours.

However, forgetting to run `ANALYZE TABLE` can leave the optimizer using stale statistics for a long time. Disable it only when an explicit schedule or operational trigger exists to refresh statistics.

### 7.4. Re-enabling via Default

```sql
ALTER TABLE orders
    STATS_AUTO_RECALC = DEFAULT;
```

Or explicitly set `1` if you want it enabled for that table:

```sql
ALTER TABLE orders
    STATS_AUTO_RECALC = 1;
```

### 7.5. Adding Indexes or Altering Columns

When adding an index to an existing table or adding/dropping columns, InnoDB computes and inserts index statistics into `mysql.innodb_index_stats` regardless of whether `innodb_stats_auto_recalc` is on or off. Even so, after bulk-loading data into a table or heavily altering key distributions, evaluate and proactively run `ANALYZE TABLE`.

## 8. ANALYZE TABLE: Proactively Updating Statistics

`ANALYZE TABLE` instructs the storage engine to analyze a table and update optimizer statistics. With InnoDB persistent statistics, this command recalculates the statistics stored in `mysql.innodb_*_stats`.

### 8.1. Basic Syntax

```sql
ANALYZE TABLE orders;
```

Multiple tables can be analyzed:

```sql
ANALYZE TABLE orders, order_items, customers;
```

### 8.2. When Should You Run ANALYZE TABLE?

- After loading large amounts of data via bulk load.
- After deleting or updating a large fraction of rows.
- After the value distribution of an indexed column shifts sharply.
- When `EXPLAIN` shows estimated rows diverging substantially from actual row counts.
- When the optimizer selects a poor index or join order following a batch of data changes.
- After changing `STATS_SAMPLE_PAGES` and needing recalculation at the new sample size.
- In test/benchmark data setup scripts to ensure statistics are populated.

### 8.3. ANALYZE TABLE Does Not Modify Business Data

This command updates metadata/statistics for the optimizer; it does not alter row values like `UPDATE` or `DELETE`. However, it still reads index pages and can generate I/O load, so avoid running it repeatedly without reason.

### 8.4. Distinguishing ANALYZE TABLE from OPTIMIZE TABLE

| Command | Purpose |
|---|---|
| `ANALYZE TABLE` | Compute/update statistics so the optimizer estimates better |
| `OPTIMIZE TABLE` | Reorganize/rebuild an InnoDB table where appropriate, potentially reclaiming space and defragmenting data/indexes |

If an execution plan is poor due to stale statistics, start with `ANALYZE TABLE`. Do not run `OPTIMIZE TABLE` solely to refresh cardinality, as it carries far heavier DDL/rebuild cost.

## 9. Persistent vs. Non-Persistent Statistics

If persistent statistics are disabled at the instance level or a table specifies `STATS_PERSISTENT=0`, InnoDB uses non-persistent statistics.

### 9.1. How Do Non-Persistent Statistics Work?

- Statistics are stored in memory instead of persisted in `mysql.innodb_*_stats`.
- They can be lost on server shutdown.
- InnoDB recalculates them when a table is opened or under certain update conditions/operations.
- Estimates after a restart may differ from before due to different samples.

This can cause execution plans to change after a restart even if business data has not changed substantially.

### 9.2. innodb_stats_transient_sample_pages

When a table uses non-persistent statistics, the relevant sampling variable is:

```sql
SHOW VARIABLES LIKE 'innodb_stats_transient_sample_pages';
```

In MySQL 8.0/8.4, the default value is 8. Increasing pages can improve estimates but increases I/O when opening tables or recalculating statistics. This variable only applies when persistent statistics are disabled for the table; when persistent stats are enabled, `innodb_stats_persistent_sample_pages` is used.

### 9.3. Do Not Confuse Sampling Variables

| Table State | Sampling Variable |
|---|---|
| `STATS_PERSISTENT=1` or persistent enabled via DEFAULT | `innodb_stats_persistent_sample_pages` |
| `STATS_PERSISTENT=0` | `innodb_stats_transient_sample_pages` |

MySQL 8.0 removed the legacy `innodb_stats_sample_pages` variable; use the corresponding persistent or transient variable rather than the old name.

## 10. Reading Statistics and Verifying Estimate Quality

Statistics are only useful when cross-checked against query behavior. You can combine statistics tables, `EXPLAIN`, and actual data.

### 10.1. Checking Last Update Time

```sql
SELECT
    database_name,
    table_name,
    last_update,
    n_rows
FROM mysql.innodb_table_stats
WHERE database_name = DATABASE()
  AND table_name = 'orders';
```

If `last_update` is too old relative to the most recent bulk load or major data change, check `STATS_AUTO_RECALC` and consider `ANALYZE TABLE`.

### 10.2. Checking Index Cardinality

```sql
SELECT
    index_name,
    stat_name,
    stat_value,
    sample_size,
    last_update
FROM mysql.innodb_index_stats
WHERE database_name = DATABASE()
  AND table_name = 'orders'
  AND stat_name LIKE 'n_diff_pfx%'
ORDER BY index_name, stat_name;
```

For composite indexes, prefix statistics indicate the estimated distinct values at each prefix length. If the leading prefix has low cardinality, a condition filtering only on the leading column may not be very selective.

### 10.3. Comparing with Actual Distinct Counts

To check a small index or test table, you can count distinct values:

```sql
SELECT
    COUNT(DISTINCT status) AS distinct_statuses
FROM orders;
```

For composite index `(customer_id, created_at)`, you can check:

```sql
SELECT COUNT(*) AS distinct_customer_created_pairs
FROM (
    SELECT customer_id, created_at
    FROM orders
    GROUP BY customer_id, created_at
) AS distinct_pairs;
```

This is a scan/aggregation over real data and can be expensive on large tables. Run it only in an appropriate environment or on a bounded dataset; do not turn this verification query into expensive periodic monitoring.

### 10.4. Cross-Checking EXPLAIN

```sql
EXPLAIN
SELECT order_id, customer_id, created_at
FROM orders
WHERE status = 'PENDING'
  AND created_at >= '2026-01-01'
  AND created_at < '2026-02-01';
```

Observe:

- `key`: index selected by the optimizer.
- `rows`: estimated rows to read.
- `filtered`: estimated percentage of rows remaining after filter conditions.
- `type`: access method such as `range`, `ref`, or `ALL`.
- `possible_keys`: indexes considered as candidates.

If `rows`/`filtered` estimates diverge widely from reality, statistics may be a contributing factor. Also check predicates, data types, collations, index design, and histograms.

### 10.5. Using EXPLAIN ANALYZE to See Actual Row Counts

MySQL 8.0.18 and later support `EXPLAIN ANALYZE` for eligible `SELECT` statements:

```sql
EXPLAIN ANALYZE
SELECT order_id, customer_id, created_at
FROM orders
WHERE status = 'PENDING'
  AND created_at >= '2026-01-01'
  AND created_at < '2026-02-01';
```

`EXPLAIN ANALYZE` actually executes the query and reports real row counts and timings across iterators. Comparing actual rows with estimated rows quantifies optimizer estimation error.

Do not run `EXPLAIN ANALYZE` casually on heavy production queries because it generates real load. Choose an appropriate window and data scope.

## 11. Statistics, Histograms, and Index Design

Persistent index statistics and histograms are related, yet they are distinct mechanisms.

- InnoDB persistent statistics primarily supply cardinality and index-size estimates derived from index page sampling.
- Histograms supply column value distribution information, helpful when the optimizer needs to estimate filter conditions on columns not well covered by index statistics.
- Index design determines which access paths the optimizer can choose; statistics only help estimate the costs of those paths.

Example updating a histogram for `status`:

```sql
ANALYZE TABLE orders
    UPDATE HISTOGRAM ON status WITH 32 BUCKETS;
```

Check histograms:

```sql
SELECT
    SCHEMA_NAME,
    TABLE_NAME,
    COLUMN_NAME,
    HISTOGRAM
FROM information_schema.COLUMN_STATISTICS
WHERE SCHEMA_NAME = DATABASE()
  AND TABLE_NAME = 'orders';
```

Histograms do not replace `mysql.innodb_index_stats`; they add column-level distribution detail. Creating histograms, choosing bucket counts, and setting refresh policies must be evaluated against the workload. An unsuitable or stale histogram can also skew estimates.

## 12. Workflow After a Bulk Load or Large Data Change

An operational workflow may include:

1. Load data or execute batch DML.
2. Confirm data loading is complete and no concurrent batch is still modifying the same table.
3. Verify `STATS_PERSISTENT`, `STATS_AUTO_RECALC`, and `STATS_SAMPLE_PAGES` settings.
4. If fresh statistics are needed immediately, run `ANALYZE TABLE`.
5. Check `last_update`, `n_rows`, and prefix cardinalities in `mysql.innodb_*_stats`.
6. Run `EXPLAIN` on critical queries.
7. On representative queries in a suitable environment, run `EXPLAIN ANALYZE` to compare estimated rows with actual rows.
8. If estimates remain inaccurate, consider raising sample pages for the specific table, checking histograms, indexes, and data distribution.
9. Record execution plans and latencies to catch shifts after future statistics updates.

Avoid running `ANALYZE TABLE` after every small `INSERT`/`UPDATE`. Frequency should balance statistics freshness against I/O and CPU overhead.

## 13. Configuration Examples by Table Type

### 13.1. Frequently Modified OLTP Table

```sql
ALTER TABLE orders
    STATS_PERSISTENT = 1,
    STATS_AUTO_RECALC = 1,
    STATS_SAMPLE_PAGES = 20;
```

Keep persistent statistics and automatic recalculation enabled. A sample size of 20 is the common default; monitor execution plans to determine if an increase is warranted.

### 13.2. Large Table with Skewed Index Distributions

```sql
ALTER TABLE event_logs
    STATS_PERSISTENT = 1,
    STATS_AUTO_RECALC = 1,
    STATS_SAMPLE_PAGES = 100;

ANALYZE TABLE event_logs;
```

A larger sample can improve estimates but increases analysis time. Keep the setting only if real benefits are measured.

### 13.3. Archive Table Updated in Scheduled Batches

```sql
ALTER TABLE monthly_archive
    STATS_PERSISTENT = 1,
    STATS_AUTO_RECALC = 0,
    STATS_SAMPLE_PAGES = 64;
```

After each archive batch completes, an operational job runs:

```sql
ANALYZE TABLE monthly_archive;
```

With this approach, the DBA controls when statistics refresh. Monitoring is required so the job is not missed; otherwise, the optimizer may rely on stale estimates.

### 13.4. Small Table with Simple Workload

Do not raise sample pages just because you can. For small tables and simple indexes, defaults are usually sufficient. Increasing the sample adds no value when current estimates are already accurate and queries have no issues.

## 14. Common Mistakes

| Situation | Cause | Fix |
|---|---|---|
| Execution plan changes after restart | Table uses non-persistent statistics or statistics were recalculated from a different sample | Enable appropriate persistent statistics and re-analyze the table |
| Optimizer still picks old index after bulk load | Background automatic recalculation hasn't finished yet, or is disabled | Run `ANALYZE TABLE` when immediate update is needed |
| `ANALYZE TABLE` is too slow | Sample pages too high, many indexes/partitions, or huge table | Reduce sample carefully, analyze on schedule, review index structure |
| Inaccurate cardinality estimates | Sample too small or skewed data distribution | Raise `STATS_SAMPLE_PAGES` for that table and run ANALYZE |
| Raising sample pages doesn't change the plan | Statistics aren't the root cause, or the optimizer still scores another index cheaper | Check actual rows, histograms, predicates, and index design |
| Auto recalc disabled and manual refresh forgotten | Statistics become stale after batch DML | Schedule an ANALYZE job and monitor `last_update` |
| Treating `n_rows` as exact COUNT | It is an estimated value | Use `COUNT(*)` when exact counts are required |
| Confusing persistent index stats with histograms | Two statistics sources with different purposes and update mechanisms | Inspect `innodb_index_stats` and `COLUMN_STATISTICS` separately |
| Editing `mysql.innodb_*_stats` directly | Interferes with internal data and corrupts estimates | Use `ANALYZE TABLE` and supported table options |

## 16. Conclusion

Persistent statistics allow InnoDB to store index statistics on disk to keep estimates more stable across server restarts. `innodb_stats_persistent` controls this mode; `innodb_stats_auto_recalc` enables background recalculation when a table changes significantly; and `innodb_stats_persistent_sample_pages` and `STATS_SAMPLE_PAGES` control how many index pages are sampled.

Statistics remain estimates. Too small a sample can skew cardinality, whereas too large a sample makes `ANALYZE TABLE` costly in I/O and time. Automatic recalculation does not update instantaneously, so after bulk loads or major distribution shifts, proactively analyze tables if you need updated plans immediately. Reading `mysql.innodb_table_stats` and `mysql.innodb_index_stats`, comparing estimates with actual rows, and tuning per table gives the optimizer better inputs without unnecessary statistical overhead.
