# The Cost-Based Optimizer and Plan Selection Inputs

MySQL does not execute a `SELECT` statement in the exact order that tables and conditions appear in the SQL text. Before running, the optimizer analyzes the query, examines the schema and data statistics, generates feasible execution alternatives, and then estimates their cost to choose a plan. This approach is called cost-based optimization.

A plan may use a table scan, index lookup, range scan, index merge, join reordering, subquery materialization, or an index for sorting. Each choice has a different cost. The optimizer estimates the number of rows to read, the rows remaining after filtering, the number of nested-loop iterations, data page access costs, and processing costs. It does not know the exact future runtime; the outcome depends on statistics quality and the cost model.

Understanding the optimizer's inputs helps explain why the same SQL statement can get a different plan after data grows, value distributions shift, indexes are added, or statistics are updated. This lesson covers the primary inputs, how to read estimates, and how to verify plans using `EXPLAIN`, `EXPLAIN ANALYZE`, and optimizer trace.

## Learning Objectives

After this lesson, you will be able to:

- Explain the cost-based optimizer and distinguish estimated cost from actual runtime.
- Identify the impact of SQL syntax, schema, indexes, constraints, and storage engine on the plan.
- Understand cardinality, selectivity, fanout, and estimated row counts.
- Explain the roles of table statistics, index statistics, and histograms.
- Update statistics with `ANALYZE TABLE` and manage histograms.
- Understand persistent statistics and the limitations of statistics sampling.
- Analyze choices among table scans, index access, range scans, join order, and join algorithms.
- Read the `rows`, `filtered`, `key`, `type`, `Extra`, and cost fields in `EXPLAIN`.
- Compare estimates against actual rows and timing using `EXPLAIN ANALYZE`.
- Use optimizer trace to inspect candidate alternatives and the reasons behind plan choices.
- Recognize the limitations of single-column statistics, skewed data, and column correlation.
- Troubleshoot poor plans by checking root causes before forcing indexes or using optimizer hints.

## 1. What Does the Cost-Based Optimizer Do?

The optimizer receives the SQL statement and relevant metadata, then determines valid transformations and data access paths. It estimates the cost of each alternative it considers and chooses a plan according to its cost model.

Example query:

    SELECT
        order_id,
        customer_id,
        order_date,
        total_amount
    FROM sales_order
    WHERE customer_id = 1001
      AND order_date >= '2025-01-01'
    ORDER BY order_date DESC
    LIMIT 20;

The optimizer may consider:

- Scanning the entire table and then filtering `customer_id` and `order_date`.
- Using an index on `customer_id`, then filtering `order_date`.
- Using a composite index starting with `customer_id` followed by `order_date`.
- Using an index that can cover all columns required in the result.
- Choosing an index scan direction aligned with `ORDER BY` and `LIMIT`.

If the table is very small, a table scan can be cheaper than an index lookup. If the table has millions of rows and the conditions select very few rows, an index range scan is usually advantageous. There is no rule that "having an index means always using the index"; the optimizer compares the costs of alternatives based on statistics and the cost model.

### 1.1. Cost Is Not Milliseconds

The cost value in `EXPLAIN` is the optimizer's internal cost unit. It is not an exact predicted millisecond count, nor can it be directly compared against the runtime of another query if the environment, configuration, or cost model differs.

Cost helps the optimizer compare alternatives within the same context. Actual runtime also depends on:

- Whether the data resides in the buffer pool or OS cache.
- I/O, CPU, memory, and concurrent load.
- Lock waits, metadata locks, and network latency.
- Result set size and how fast the client consumes data.
- Server configuration, storage engine, and MySQL version.

Therefore, a plan with a lower estimated cost is not guaranteed to have a lower runtime in every situation. Use `EXPLAIN` to understand the choice and measure actual runtime on a representative workload.

### 1.2. Cost-Based Does Not Mean Trying Every Possible Plan

The number of ways to join tables grows very rapidly with the number of tables. The optimizer uses search strategies and pruning to bound the plan space. It evaluates the alternatives generated by the optimization process; it does not guarantee checking every conceivable order and execution method.

Consequently, the chosen plan is the best alternative according to the information, model, and search space used by the optimizer. If cardinality estimates are wrong or a good alternative is never considered, the final plan can still be poor.

## 2. Three Main Groups of Inputs

Plan selection inputs can be divided into three groups:

| Group | Examples | Impact |
|---|---|---|
| SQL statement and semantics | JOIN, WHERE, ORDER BY, GROUP BY, LIMIT, subqueries, expressions | Determines operations and valid alternatives |
| Schema and storage structure | Data types, NULL, primary/unique keys, indexes, partitions, storage engine | Determines access paths and data constraints |
| Statistics and cost model | Row count, index cardinality, histograms, page count, cost constants | Estimates row counts and cost of each alternative |

The optimizer is also influenced by the MySQL version, optimizer switches, optimizer hints, session variables, and compatibility settings. These settings can enable, disable, or guide a strategy, but they do not replace proper SQL, index, and statistics design.

## 3. Inputs from the SQL Statement

### 3.1. Filter Predicates

The optimizer analyzes `WHERE` and `JOIN` predicates to determine how effectively it can use indexes or eliminate rows early.

Example equality predicate:

    WHERE customer_id = 1001

Range predicate:

    WHERE order_date >= '2025-01-01'
      AND order_date < '2025-02-01'

Multi-column predicate:

    WHERE customer_id = 1001
      AND order_status = 'PAID'

Equality predicates usually allow targeting a narrow index range. Range predicates can read an index interval. Multi-column predicates can leverage a composite index if the column order matches.

### 3.2. Sargability and Expressions on Columns

A predicate is sargable when the optimizer can use it to efficiently locate an index range. For example:

    WHERE created_at >= '2025-01-01'
      AND created_at <  '2025-02-01'

is typically much friendlier to a B-tree index on `created_at` than:

    WHERE DATE(created_at) = '2025-01-15'

Function expressions applied directly to a column can prevent a regular index from being used for range positioning. If you need to search repeatedly by an expression, consider an indexed generated column or a functional index when supported by your MySQL version.

Several other predicate forms also affect index usability:

- Comparing two different data types may require conversion.
- `LIKE 'abc%'` can leverage a range on a string index under suitable conditions; `LIKE '%abc'` usually cannot locate rows via a regular B-tree prefix.
- `OR` across different columns may lead the optimizer to consider index merge or a table scan.
- `NOT`, complex expressions, and unsuitable functions can reduce index usability.
- Collation and comparison rules affect the matching value set.

Not every expression renders an index unusable. Check `EXPLAIN` against the actual query and schema.

### 3.3. JOINs and Join Order

In multi-table queries, the optimizer can change the join order compared to the order written in the `FROM` clause. It estimates row counts after each join step to decide which table should be accessed first.

Example:

    SELECT
        c.customer_name,
        o.order_id,
        o.total_amount
    FROM customer AS c
    JOIN sales_order AS o
        ON o.customer_id = c.customer_id
    WHERE c.country_code = 'VN'
      AND o.order_status = 'PAID';

If `country_code = 'VN'` selects only a small fraction of customers, starting from `customer` may be good. If `order_status = 'PAID'` selects very few orders, starting from `sales_order` may be better. The outcome depends on statistics and indexes on both sides.

### 3.4. ORDER BY, GROUP BY, and LIMIT

`ORDER BY` can use an index if the column order and sort direction are compatible with the index and filter predicates. Otherwise, MySQL may have to sort the result.

`GROUP BY` may use an index or require a temporary table/sort depending on the structure and plan. `LIMIT` can allow an access path to stop early once enough rows are retrieved, making an index that supports both filtering and sorting advantageous.

Example:

    SELECT order_id, order_date
    FROM sales_order
    WHERE customer_id = 1001
    ORDER BY order_date DESC
    LIMIT 20;

An index `(customer_id, order_date)` can help locate the customer's orders and read them in date order without a separate sort. The optimizer must still weigh selectivity, scan direction, and lookup cost.

### 3.5. Subqueries and Derived Tables

The optimizer can transform some subqueries into semijoins, materialize intermediate results, or merge derived tables into the outer query block. Whether a transformation applies depends on query structure, `NULL` semantics, `DISTINCT`, `GROUP BY`, `LIMIT`, and other constraints.

Example:

    SELECT c.customer_id, c.customer_name
    FROM customer AS c
    WHERE EXISTS (
        SELECT 1
        FROM sales_order AS o
        WHERE o.customer_id = c.customer_id
          AND o.order_status = 'PAID'
    );

The optimizer can apply an appropriate semijoin strategy instead of executing the subquery independently in a naive way. Use `EXPLAIN FORMAT=TREE` or `JSON` to inspect the chosen execution structure.

## 4. Inputs from Schema and Data Structure

### 4.1. Data Types and Lengths

Data types affect comparison semantics, index size, read cost, and implicit conversions. For instance, join keys between two tables should have compatible types; avoid joining a `BIGINT` with a `VARCHAR` containing digits if the schema can be normalized.

Row and index sizes affect how many pages must be read. Indexes with smaller keys typically fit more entries per page, though the data type must still cover the value domain and fit business requirements.

### 4.2. NULL and Constraints

`NOT NULL`, `UNIQUE`, `PRIMARY KEY`, and constraints provide information about the data and its semantics. A unique key lets the optimizer know that an equality predicate can return at most one row under matching conditions. The primary key defines the unique row identifier.

Proper constraints support both data integrity and query optimization. Do not declare `UNIQUE` just as a "hint" to the optimizer if business data actually allows duplicates; constraints must reflect real rules.

### 4.3. Indexes and Column Order

Indexes are among the optimizer's most important inputs. They provide access paths as alternatives to table scans while also carrying key distribution statistics.

With a composite index:

    CREATE INDEX idx_order_customer_date
    ON sales_order (customer_id, order_date);

This index can support:

    WHERE customer_id = 1001

and:

    WHERE customer_id = 1001
      AND order_date >= '2025-01-01'

However, you cannot assume this index is always effective for a query filtering only on `order_date` without `customer_id`. A B-tree composite index primarily supports leftmost prefixes.

### 4.4. Covering Indexes

If an index contains all columns needed by a query, MySQL can read the result directly from the index without looking up rows in the clustered index. This is a covering index.

Example:

    CREATE INDEX idx_order_customer_date_amount
    ON sales_order (customer_id, order_date, total_amount);

    SELECT order_date, total_amount
    FROM sales_order
    WHERE customer_id = 1001
    ORDER BY order_date DESC
    LIMIT 20;

The index can cover the queried columns. However, wider indexes consume more space and increase `INSERT`/`UPDATE`/`DELETE` overhead. Do not add every column to an index solely to avoid table lookups; measure the read/write workload and data size.

### 4.5. Storage Engine

Each storage engine provides its own metadata and access costs. InnoDB has a clustered primary key, secondary indexes pointing to the primary key, a buffer pool, and its own index statistics. The optimizer combines server-layer costs with storage-engine information and costs to compare plans.

Two tables with the same row count but different engines, index sizes, cache residency, and storage layouts can yield different costs.

## 5. Cardinality, Selectivity, and Fanout

These are the core concepts for understanding optimizer estimates.

### 5.1. Cardinality

The cardinality of a column or index key generally refers to the estimated number of distinct values in statistics. For composite indexes, statistics can include cardinality for each index prefix.

For example, in a table with 1,000,000 orders:

- `order_status` has only 4 distinct values.
- `customer_id` has 100,000 distinct customers.
- `order_id` is the primary key with 1,000,000 distinct values.

An equality condition on `order_id` is usually highly selective. A condition like `order_status = 'PAID'` may match a large fraction of the table.

Cardinality shown in `SHOW INDEX` is an estimate, not necessarily an exact count.

### 5.2. Selectivity

Selectivity describes the fraction of rows satisfying a condition. Low-selectivity predicates in some conventions select few rows while high-selectivity predicates retain many rows (and documentation or tools may use different phrasing conventions), so focus on the estimated row count and remaining percentage when reading plans.

For example, in a table with 1,000,000 rows:

- `customer_id = 1001` may match only 12 rows.
- `order_status = 'PAID'` may match 700,000 rows.

The `customer_id` condition is much more selective. Using an index to fetch 12 rows can be cheaper than scanning the whole table; however, using an index to fetch 700,000 rows and performing row-by-row lookups can be more expensive than a table scan.

### 5.3. Fanout

Fanout is the average number of rows produced by a join step per input row, or the row multiplication factor through a join. If a customer averages 20 orders, joining `customer` with `sales_order` may produce around 20 rows per matching customer.

A bad fanout estimate in an early step propagates to subsequent join steps. Small errors across multiple steps can cause the optimizer to misjudge the entire plan.

### 5.4. Column Correlation

Suppose `order_status = 'CANCELLED'` frequently occurs in specific regions. If the optimizer only has independent statistics for `order_status` and `region_id`, it may assume approximate independence between the two predicates and misestimate when they are strongly correlated.

MySQL histograms are single-column statistics; they do not capture the full joint distribution of multiple columns. Composite indexes have prefix statistics that help certain multi-column queries, but they do not replace general multivariate statistics.

When predicates are strongly correlated, compare estimated rows against actual rows and evaluate composite indexes or appropriate data modeling.

## 6. InnoDB Table Statistics and Index Statistics

The optimizer needs to estimate table size and key distributions. For InnoDB, statistics are derived from metadata and index page sampling.

Typically available information includes:

- Estimated number of rows in the table.
- Number of data and index pages.
- Number of distinct values per index key/prefix.
- Average number of records per key.
- Statistics supporting range and lookup estimates.

Because InnoDB typically uses sampling rather than scanning all data for every statistic, estimated values can differ from `COUNT(*)` or exact data counts. Sampling outcomes can also vary with sample size and data state.

### 6.1. Viewing Index Statistics

    SHOW INDEX FROM sales_order;

Key columns:

| Column | Meaning |
|---|---|
| Key_name | Index name |
| Seq_in_index | Column position in a composite index |
| Column_name | Column belonging to the index |
| Non_unique | Whether the index allows duplicate keys |
| Cardinality | Estimated number of distinct values for the prefix |
| Sub_part | Prefix length if partially indexed |
| Index_type | Index type, usually BTREE for standard indexes |

`Cardinality` is an estimate and can be `NULL` when statistics are unavailable or inapplicable. Do not treat this number as an exact count.

### 6.2. Viewing Persistent InnoDB Statistics

In MySQL, persistent InnoDB statistics can be stored in system tables:

    SELECT *
    FROM mysql.innodb_table_stats
    WHERE database_name = DATABASE()
      AND table_name = 'sales_order';

    SELECT *
    FROM mysql.innodb_index_stats
    WHERE database_name = DATABASE()
      AND table_name = 'sales_order';

These tables provide information such as estimated row counts, page counts, cardinality per index prefix, and the timestamp of the last statistics update. Appropriate privileges are required to read the `mysql` schema.

Persistent statistics allow statistics to survive server restarts rather than relying solely on transient statistics. Related settings include `innodb_stats_persistent`, `innodb_stats_auto_recalc`, and `innodb_stats_persistent_sample_pages`. Defaults and behavior can vary by version and configuration; inspect the actual variables:

    SHOW VARIABLES LIKE 'innodb_stats_persistent';
    SHOW VARIABLES LIKE 'innodb_stats_auto_recalc';
    SHOW VARIABLES LIKE 'innodb_stats_persistent_sample_pages';

Do not change global sample pages just because one query has a bad plan. First identify which statistics are wrong, which tables are affected, and the cost of additional sampling.

### 6.3. Updating Statistics with ANALYZE TABLE

After bulk data loads, large deletions, or significant distribution shifts, you can update statistics:

    ANALYZE TABLE sales_order;

`ANALYZE TABLE` instructs the storage engine to update table and index statistics. With InnoDB using persistent stats, re-analyzing can give the optimizer fresher estimates.

Notes:

- `ANALYZE TABLE` does not modify business data.
- Statistics remain estimates, not exact counts of all values.
- Updating statistics can cause query plans to change.
- Running on production requires checking load, metadata locks, and execution duration.
- Do not schedule overly frequent runs without justification and impact assessment.

After `ANALYZE`, re-check `SHOW INDEX` and `EXPLAIN`. Do not assume every query will become faster; plans may change in another direction.

## 7. Histograms: Single-Column Distribution Statistics

Index cardinality indicates the estimated number of distinct values, but it does not fully describe the distribution. For example, a column might have 4 statuses where `PAID` accounts for 70%, `PENDING` 20%, `CANCELLED` 9%, and `REFUNDED` 1%. Knowing only that there are 4 values is insufficient to estimate a specific predicate.

Histograms add value distribution information for a column. MySQL can use histograms to improve selectivity estimates, especially for columns without a suitable index or for predicates where index statistics do not provide enough detail.

MySQL supports two main histogram types:

- Singleton histogram: stores individual values and their corresponding frequencies.
- Equi-height histogram: divides data into buckets with roughly equal observation counts, describing boundaries and intra-bucket distribution.

The maximum number of buckets and creation behavior depend on the version; MySQL 8.0 allows requesting up to 1024 buckets.

### 7.1. Creating Histograms

Example creating a histogram on `order_status`:

    ANALYZE TABLE sales_order
    UPDATE HISTOGRAM ON order_status
    WITH 32 BUCKETS;

You can request histograms for multiple columns in the same statement:

    ANALYZE TABLE sales_order
    UPDATE HISTOGRAM ON order_status, sales_channel
    WITH 64 BUCKETS;

Histograms are created individually per column. This does not create a multi-dimensional histogram for the combination of `order_status` and `sales_channel`.

### 7.2. Viewing Histograms

MySQL stores histogram data in `INFORMATION_SCHEMA.COLUMN_STATISTICS`:

    SELECT
        SCHEMA_NAME,
        TABLE_NAME,
        COLUMN_NAME,
        HISTOGRAM
    FROM information_schema.column_statistics
    WHERE SCHEMA_NAME = DATABASE()
      AND TABLE_NAME = 'sales_order';

`HISTOGRAM` is a JSON document containing the histogram type, bucket count, null fraction, distinct value estimation, and corresponding distribution details.

### 7.3. Dropping Histograms

If a histogram is no longer suitable or you want the optimizer to fall back to other statistics:

    ANALYZE TABLE sales_order
    DROP HISTOGRAM ON order_status;

Dropping a histogram does not drop any index on the column or delete data. It only removes the stored histogram statistics for the column.

### 7.4. Updating Histograms When Distributions Change

A histogram reflects the data at the time it was created or updated. If the data changes significantly, an outdated histogram may no longer represent the current distribution. Define an update policy based on data churn and workload.

Do not assume a plain `ANALYZE TABLE` always refreshes every existing histogram automatically in the way you expect; when histograms need updating, use the explicit `UPDATE HISTOGRAM` syntax and verify metadata afterward.

### 7.5. Limitations of Histograms

- Histograms are single-column statistics and do not fully describe correlations across multiple columns.
- Histograms do not create access paths like indexes do; they improve estimation, not page-access mechanics directly.
- Histograms do not guarantee the optimizer will choose an index or a specific plan.
- Histograms can be unrepresentative if the bucket count is small relative to diversity or if data changes rapidly.
- When a column is indexed, the optimizer also has index statistics and dedicated estimation methods; do not treat histograms as the sole source.

## 8. The MySQL Cost Model

After estimating row counts and operations, the optimizer needs a cost model to compare alternatives. The cost model can account for:

- Cost of reading data or index pages.
- Cost of searching and accessing records.
- CPU cost for evaluating conditions and expressions.
- Cost of creating or reading temporary tables.
- Cost of sorting, joining, and materialization.
- Costs reported by the storage engine.

MySQL splits certain costs into two groups:

- Server cost: costs at the SQL/server layer.
- Engine cost: costs provided by the storage engine.

In MySQL 8.0, the `mysql.server_cost` and `mysql.engine_cost` tables contain the cost constants used by the optimizer. You can inspect them to understand the configuration:

    SELECT *
    FROM mysql.server_cost;

    SELECT *
    FROM mysql.engine_cost;

Some rows may show `default_value` when a cost constant has not been customized. Cost values are model parameters, not millisecond benchmarks.

### 8.1. Do Not Arbitrarily Tweak Cost Constants

Cost constants can be customized in some environments, but doing so has broad effects on plan selection. A value tuned to improve one workload can cause another workload to choose worse plans.

Before changing them:

1. Identify multiple representative queries and specific issues.
2. Record baseline plans and actual execution times before making changes.
3. Verify indexes, statistics, and buffer pool configuration first.
4. Test in a staging environment with a production-like workload.
5. Apply controlled changes, monitor multiple query digests, and prepare a rollback path.

Do not update cost constants directly as a quick fix for a single query. In most cases, fixing the SQL, indexes, or statistics is the lower-risk path.

## 9. How the Optimizer Chooses an Access Path

An access path is how MySQL retrieves rows from a table or index.

### 9.1. Table Scan

A table scan reads the rows of a table to evaluate conditions. It can be reasonable when:

- The table is small.
- The condition selects a large percentage of rows.
- Index lookups would require many random accesses.
- The query needs many columns and the index is not covering.
- Statistics indicate a table scan has lower cost.

Do not treat `ALL` in `EXPLAIN` as an automatic error. For small tables or queries returning most of the table, a table scan can be the right plan.

### 9.2. Index Lookup and Range Scan

An index lookup locates matching keys and fetches rows. A range scan reads a contiguous range of keys matching a condition.

Example:

    SELECT order_id, order_date
    FROM sales_order
    WHERE customer_id = 1001
      AND order_date >= '2025-01-01'
      AND order_date < '2025-02-01';

The index `(customer_id, order_date)` can locate the exact customer and date range.

### 9.3. Index Merge

When multiple single-column indexes match `OR`/`AND` predicates, the optimizer may consider combining results from multiple indexes. `EXPLAIN` may show `type = index_merge`.

Index merge is not always better than a composite index. If a query frequently filters on the same combination of columns, an appropriate composite index can reduce work. Compare row counts, cost, and actual time.

### 9.4. Covering Index

When all required columns are present in the index, MySQL can avoid reading rows from the clustered index. In traditional `EXPLAIN`, `Extra` may display `Using index`.

A covering index reduces lookups but increases index size and write overhead. Choose columns based on the actual workload.

### 9.5. Index Condition Pushdown

Index Condition Pushdown (ICP) allows the storage engine to evaluate certain predicates on index entries before reading the full row. `EXPLAIN` may show `Using index condition`.

ICP can reduce full-row reads, though it does not mean every predicate is resolved using the index alone. Read `key`, `key_len`, `Extra`, and the full execution plan.

## 10. How the Optimizer Chooses Join Order and Join Algorithm

With multiple tables, the optimizer estimates row counts at each join step. If an early step produces too many rows, subsequent steps may have to process a massive volume.

Example:

    SELECT
        c.customer_name,
        o.order_id,
        p.payment_status
    FROM customer AS c
    JOIN sales_order AS o
        ON o.customer_id = c.customer_id
    JOIN payment AS p
        ON p.order_id = o.order_id
    WHERE c.country_code = 'VN'
      AND p.payment_status = 'SETTLED';

The optimizer considers:

- Which table has the more selective filter condition.
- Which indexes support lookups into the next table.
- Estimated orders per customer.
- Estimated payments per order.
- The cost of each join order and join algorithm.

MySQL can use the nested-loop family and hash joins in supported scenarios. Hash join was added in MySQL 8.0.18; algorithm details and optimizer switches vary across versions. Use `EXPLAIN FORMAT=TREE` to view the actual plan structure rather than guessing the algorithm from SQL syntax alone.

### 10.1. Estimated Rows Across Steps

If a step is estimated to return 100 rows and the next step has a fanout of 10, the optimizer may estimate roughly 1,000 rows after the join. If an input estimate is off by 100x, the total plan cost can be significantly distorted.

When reading multi-table plans, identify the first step with a large discrepancy between estimated rows and actual rows. That is usually where the skew starts; later steps merely amplify the error.

## 11. Practice: Creating a Schema to Observe Plan Selection

Create customer and order tables in a sandbox database:

    CREATE TABLE optimizer_customer_demo (
        customer_id BIGINT UNSIGNED NOT NULL,
        customer_name VARCHAR(100) NOT NULL,
        country_code CHAR(2) NOT NULL,
        PRIMARY KEY (customer_id),
        KEY idx_optimizer_customer_country (country_code)
    ) ENGINE = InnoDB;

    CREATE TABLE optimizer_order_demo (
        order_id BIGINT UNSIGNED NOT NULL,
        customer_id BIGINT UNSIGNED NOT NULL,
        order_date DATETIME NOT NULL,
        order_status VARCHAR(20) NOT NULL,
        total_amount DECIMAL(12,2) NOT NULL,
        PRIMARY KEY (order_id),
        KEY idx_optimizer_order_customer (customer_id),
        KEY idx_optimizer_order_date (order_date),
        KEY idx_optimizer_order_status (order_status)
    ) ENGINE = InnoDB;

    INSERT INTO optimizer_customer_demo
        (customer_id, customer_name, country_code)
    VALUES
        (1001, 'An', 'VN'),
        (1002, 'Binh', 'VN'),
        (1003, 'Chi', 'SG'),
        (1004, 'Dung', 'US');

    INSERT INTO optimizer_order_demo
        (order_id, customer_id, order_date, order_status, total_amount)
    VALUES
        (5001, 1001, '2025-01-02 10:00:00', 'PAID',      120.00),
        (5002, 1001, '2025-01-05 11:00:00', 'PENDING',    80.00),
        (5003, 1002, '2025-01-08 12:00:00', 'PAID',      250.00),
        (5004, 1003, '2025-01-10 13:00:00', 'CANCELLED',  40.00),
        (5005, 1004, '2025-02-01 14:00:00', 'PAID',      500.00);

On very small tables, the optimizer may choose a table scan even when indexes exist. This is normal: the cost of reading a few rows sequentially can be lower than initializing an index lookup and reading individual rows. Do not use results from tiny sample tables to conclude that an index is useless on large datasets.

## 12. ANALYZE TABLE and Comparing Plans Before/After

Run:

    ANALYZE TABLE optimizer_customer_demo;
    ANALYZE TABLE optimizer_order_demo;

Then inspect indexes:

    SHOW INDEX FROM optimizer_order_demo;

Run `EXPLAIN`:

    EXPLAIN
    SELECT
        order_id,
        order_date,
        total_amount
    FROM optimizer_order_demo
    WHERE customer_id = 1001
      AND order_date >= '2025-01-01'
      AND order_date < '2025-02-01'
    ORDER BY order_date DESC
    LIMIT 20;

The optimizer may choose the customer index, date index, or table scan depending on row counts and statistics. With larger, realistic data, try a composite index:

    CREATE INDEX idx_optimizer_order_customer_date
    ON optimizer_order_demo (customer_id, order_date);

After creating the index, run `EXPLAIN` again. The composite index can support equality on `customer_id` and range on `order_date`; however, on a tiny table, the optimizer may still pick a table scan. Evaluate against datasets with production-like scale and distribution.

## 13. Reading Traditional EXPLAIN

Example:

    EXPLAIN
    SELECT *
    FROM optimizer_order_demo
    WHERE customer_id = 1001;

Key columns:

| Column | Meaning |
|---|---|
| id | Query block identifier in the EXPLAIN output |
| select_type | SELECT type such as SIMPLE, PRIMARY, SUBQUERY, DERIVED |
| table | Table or derived object accessed |
| partitions | Partitions used if the table is partitioned |
| type | Access type, e.g., const, eq_ref, ref, range, index, ALL |
| possible_keys | Indexes considered as candidates |
| key | Chosen index |
| key_len | Used key length |
| ref | Values/columns compared against the index |
| rows | Estimated number of rows to read |
| filtered | Estimated percentage of rows remaining after additional filtering |
| Extra | Additional details such as Using where, Using index, Using filesort |

### 13.1. Access Type Is Not an Absolute Ranking

Common `type` values:

- `system`/`const`: table or query narrowed very tightly, typically at most one row under matching conditions.
- `eq_ref`: unique key lookup for each preceding row combination.
- `ref`: non-unique index lookup.
- `range`: reading an index interval.
- `index`: scanning the entire index.
- `ALL`: scanning the entire table.
- `index_merge`: combining multiple indexes.

These types are generally considered good when a query selects few rows, but no single type is always optimal across every workload. A `range` scan returning 90% of a table can be more expensive than a table scan; `ALL` on a table with a few rows can be completely reasonable.

### 13.2. rows and filtered

`rows` is the estimated number of rows the access method needs to read at that step. `filtered` is the estimated percentage of rows remaining after filter conditions described by `EXPLAIN`. The product of `rows` and `filtered/100` helps illustrate how many rows pass forward to the next step, though it must be interpreted within the context of join order and query blocks.

For example, if `rows = 10,000` and `filtered = 5.0`, the optimizer estimates roughly 500 rows remain after filtering at that step.

These are estimates, not actual counts.

### 13.3. Common Extra Values

| Extra | General Meaning |
|---|---|
| Using where | Row-level filtering is applied |
| Using index | Required columns can be returned from the index (covering access) |
| Using index condition | ICP filters via index predicates before reading the full row |
| Using filesort | A separate sort step is needed; does not guarantee disk spill |
| Using temporary | An internal temporary table is needed for part of processing |
| Using join buffer | A join buffer is used for an eligible join strategy |

`Using filesort` does not automatically indicate a performance bug. Sorting a small set can have negligible cost. `Using temporary` must also be evaluated against data size and operation type.

## 14. EXPLAIN FORMAT=JSON and FORMAT=TREE

`FORMAT=JSON` provides more detailed structure, including nested query blocks, access paths, `cost_info`, `rows_produced_per_join`, and index details.

    EXPLAIN FORMAT=JSON
    SELECT
        c.customer_name,
        o.order_id
    FROM optimizer_customer_demo AS c
    JOIN optimizer_order_demo AS o
        ON o.customer_id = c.customer_id
    WHERE c.country_code = 'VN';

`FORMAT=TREE` represents the plan as a tree, making it useful to inspect iterator order, filters, joins, and access methods:

    EXPLAIN FORMAT=TREE
    SELECT
        c.customer_name,
        o.order_id
    FROM optimizer_customer_demo AS c
    JOIN optimizer_order_demo AS o
        ON o.customer_id = c.customer_id
    WHERE c.country_code = 'VN';

Do not look only at the last line. Read from the input iterators upward to understand how data flows through each step.

## 15. EXPLAIN ANALYZE: Comparing Estimates with Actuals

Regular `EXPLAIN` shows optimizer estimates. MySQL 8.0.18 and later support `EXPLAIN ANALYZE` for `SELECT`; the query is executed and the output shows actual timing, actual rows, and iterator loop counts (`loops`).

Example:

    EXPLAIN ANALYZE
    SELECT
        order_id,
        order_date,
        total_amount
    FROM optimizer_order_demo
    WHERE customer_id = 1001
      AND order_date >= '2025-01-01'
      AND order_date < '2025-02-01';

Output may look like:

    -> Index range scan on optimizer_order_demo
       (cost=... rows=...)
       (actual time=... rows=... loops=...)

This is an illustrative shape only; actual figures depend on the server, data, and plan.

### 15.1. Reading Actual Rows and Loops

- Estimated `rows` indicates how many rows the optimizer predicted.
- Actual `rows` indicates how many rows the iterator actually returned per loop.
- `loops` indicates how many times the iterator was executed.
- `actual time` indicates the measured execution time for the iterator as formatted by MySQL.

An iterator with `actual rows = 5` and `loops = 100` may have processed around 500 rows across iterations, depending on output context. In nested loops, inner `loops` generally reflect how many times the inner side was invoked per outer row.

### 15.2. Finding the First Point of Divergence

Suppose the optimizer estimates a predicate returns 100 rows, but in reality it returns 50,000 rows. A subsequent join may iterate far more times than expected, making the initial plan expensive.

When analyzing:

1. Compare estimated rows and actual rows at the earliest iterator.
2. Identify predicates or columns whose distribution is poorly represented in statistics.
3. Check index cardinality and histograms.
4. Check whether data has skew or correlation across multiple columns.
5. Update statistics if needed and re-measure.
6. If statistics are reasonable yet the plan remains poor, examine indexes, SQL expressions, or optimizer trace.

### 15.3. EXPLAIN ANALYZE Executes the Query

`EXPLAIN ANALYZE` does not merely "inspect the plan." It executes the `SELECT` to collect actual timings and row counts. Expensive queries can consume CPU, I/O, and memory and impose load comparable to running the real query.

Do not run `EXPLAIN ANALYZE` casually on very heavy queries in production. Scope it carefully, use staging or a data replica, bound execution time, and ensure the `SELECT` causes no unintended operational impact.

## 16. Optimizer Trace: Inspecting the Selection Process

`EXPLAIN` shows the final plan. Optimizer trace lets you see candidates considered, estimates, and reasons behind selections.

Enable trace in the session:

    SET optimizer_trace = 'enabled=on';

Run the query to analyze:

    SELECT
        order_id,
        total_amount
    FROM optimizer_order_demo
    WHERE customer_id = 1001
      AND order_status = 'PAID';

Read the trace:

    SELECT TRACE
    FROM information_schema.optimizer_trace;

Disable trace when finished:

    SET optimizer_trace = 'enabled=off';

The trace is JSON and can be verbose. It can reveal:

- Query blocks and transformation steps.
- Candidate access methods.
- Range and row count estimates.
- Table scan cost versus index access cost.
- Join orders considered.
- Reasons certain alternatives were rejected.

Not every internal detail is displayed for every query. Use trace as a supplementary diagnostic tool, not as a stable output contract for applications to parse.

## 17. Why Can Plans Change?

Plans are not fixed forever. They can change whenever any of the inputs change:

- Row counts grow or shrink.
- Value distributions change (e.g., `PAID` status grows from 20% to 90%).
- Indexes are added, dropped, or have their column order changed.
- `ANALYZE TABLE` updates cardinality.
- Histograms are created, updated, or dropped.
- Cost model settings or optimizer switches change.
- A MySQL version upgrade introduces different optimizer transformations or cost models.
- Schema, data types, collations, or constraints change.

A query that was fast on a 10,000-row table can become slow when the table reaches 100 million rows. An index that was once helpful can become less selective as data distributions shift.

### 17.1. Stale Statistics and Skewed Data

Suppose a table has 10 million orders:

- 8 million `PAID` orders.
- 1.5 million `PENDING` orders.
- 400 thousand `CANCELLED` orders.
- 100 thousand `REFUNDED` orders.

If statistics only know the number of distinct values without knowing frequencies, the optimizer may estimate a rare status using an inappropriate assumption. Histograms help describe the distribution more clearly.

However, if the distribution changes rapidly after a histogram is created, a stale histogram can lead to bad estimates. Monitor data changes and update deliberately.

### 17.2. Version Changes

Upgrading MySQL can change:

- Supported query transformations.
- Cost or statistics calculations.
- Join algorithms.
- Rules for expressions, collations, and data types.
- Optimizer switches and optimizer hints.

After an upgrade, compare plans and performance of critical queries on staging. Do not assume old plans will stay identical simply because SQL text and indexes did not change.

## 18. When to Use Histograms vs. When You Need an Index

Histograms and indexes solve two different problems:

| Tool | Primary Goal | Creates a New Access Path? |
|---|---|---|
| Index | Locate and read rows efficiently by key | Yes |
| Index statistics | Describe cardinality and key/prefix distribution | No, but supports estimation |
| Histogram | Describe a column's value distribution | No |
| ANALYZE TABLE | Update table/index statistics | Not directly |
| EXPLAIN ANALYZE | Measure actual rows/timing of a plan | No |

Examples:

- Need fast range filtering on `order_date` in a large table: usually needs a suitable index.
- Need the optimizer to know `status = 'REFUNDED'` is only 1% when `status` lacks a suitable index: a histogram can help estimation.
- Need to know why the estimate is 100 while actual is 50,000: `EXPLAIN ANALYZE`.
- Need to see which indexes the optimizer considered and why some were rejected: optimizer trace.

Histograms do not replace indexes. Conversely, adding an index does not automatically resolve every statistical inaccuracy, especially with skewed distributions or multi-column correlations.

## 19. Optimizer Switches and Hints

MySQL provides `optimizer_switch` to toggle certain optimization strategies. You can view the current settings:

    SELECT @@optimizer_switch;

Some flags relate to strategies like `index_merge`, `derived_merge`, `materialization`, `semijoin`, `mrr`, or index condition pushdown. The list and defaults vary by version.

Optimizer hints can guide a query block or table to use or avoid a specific strategy or index. Example:

    SELECT /*+ INDEX(o idx_optimizer_order_customer_date) */
        o.order_id,
        o.order_date
    FROM optimizer_order_demo AS o
    WHERE o.customer_id = 1001;

Hints are an advanced tool. If you use a hint to force a plan, document the rationale, target workload, version, data characteristics, and post-deployment monitoring. Hints can become harmful as data or schema evolves.

Do not reach for `FORCE INDEX` or hints as the first step when a query is slow. First inspect estimated rows, actual rows, indexes, statistics, and query predicates.

## 20. Diagnostic Workflow When the Optimizer Picks a Poor Plan

When a query is slow or chooses a suspicious access path, follow this sequence:

1. Record the exact SQL statement, parameters, session variables, and MySQL version.
2. Run `EXPLAIN` to inspect access paths, join order, and estimated rows.
3. Run `EXPLAIN FORMAT=JSON` or `TREE` to see detailed structure.
4. If safe, run `EXPLAIN ANALYZE` on representative data to capture actual rows, loops, and timing.
5. Find the earliest iterator with a large gap between estimated and actual rows.
6. Check `SHOW INDEX`, cardinality, and relevant index prefixes.
7. Check `ANALYZE TABLE`, persistent statistics, and histograms.
8. Check whether the data has skew or correlation across predicates.
9. Check data types, implicit conversions, collations, and expressions on columns.
10. Evaluate composite indexes, covering indexes, or rewriting predicates.
11. Use optimizer trace if it is unclear why an alternative was rejected.
12. Re-measure on the same data, parameters, and load conditions; compare both latency and resource usage.

Do not change multiple factors at once. If you simultaneously alter indexes, histograms, and optimizer hints, it becomes hard to tell which change helped or hurt the plan.

## 21. Example of Diagnosing a Bad Estimate

Suppose the query is:

    SELECT order_id, total_amount
    FROM sales_order
    WHERE order_status = 'REFUNDED';

`EXPLAIN` estimates 500,000 rows, while `EXPLAIN ANALYZE` shows only 10,000 rows. Some possibilities:

- Index statistics are stale after data changes.
- A histogram is missing or no longer representative.
- Status distribution is heavily skewed relative to optimizer assumptions.
- Predicates involve conversions or collations causing unexpected estimates.

Workflow:

    ANALYZE TABLE sales_order;

    ANALYZE TABLE sales_order
    UPDATE HISTOGRAM ON order_status
    WITH 32 BUCKETS;

Then re-run `EXPLAIN` and `EXPLAIN ANALYZE`. Compare estimates and actuals. If the query still reads too many rows and lacks a suitable index, consider indexing `order_status` or creating a composite index matching common predicates.

Do not create an index merely because a query has a high estimated row count. If `REFUNDED` is rare, an index may be helpful; if `PAID` is 90% and the query fetches nearly all `PAID` rows, a table scan may be cheaper. Base decisions on the workload, not a single number.

## 22. Common Mistakes

- Thinking `cost` in `EXPLAIN` is time in milliseconds.
- Thinking the optimizer tests every possible plan and always finds the global optimum.
- Thinking that having an index forces the optimizer to use it.
- Treating `type = ALL` as a bug even when the table is tiny or the query needs most of the data.
- Reading cardinality as an exact count.
- Confusing cardinality with selectivity.
- Ignoring fanout and estimation errors propagating across multiple JOIN steps.
- Thinking histograms create indexes or directly make queries read fewer pages.
- Thinking a single-column histogram captures multi-column correlation.
- Assuming `ANALYZE TABLE` guarantees queries will run faster.
- Failing to update histograms after data distributions shift significantly.
- Looking only at `key` while ignoring `rows`, `filtered`, `Extra`, and join order.
- Thinking `Using filesort` always means sorting spills to disk.
- Thinking `EXPLAIN ANALYZE` only displays the plan without executing the query.
- Running `EXPLAIN ANALYZE` on very heavy queries in production without safeguards.
- Using `FORCE INDEX` or optimizer hints before understanding the root cause.
- Changing multiple factors simultaneously so the source of improvement is unknown.
- Judging performance on tiny sample tables and extrapolating to production data.

## 23. Checklist for Reading and Improving Plans

- Recorded the SQL, parameters, version, and session settings.
- Reviewed the schema, data types, constraints, and storage engine.
- Identified existing indexes and leftmost prefixes of composite indexes.
- Read access type, `key`, `key_len`, `rows`, `filtered`, and `Extra`.
- Checked join order and estimated fanout across each step.
- Distinguished estimated cost from actual execution time.
- Checked table/index statistics and when they were last updated.
- Assessed data skew and whether histograms are needed.
- Understood the limits of single-column statistics and multi-column correlation.
- Used `EXPLAIN ANALYZE` safely to compare estimates with actuals.
- Identified the first point of divergence rather than looking only at the final iterator.
- Used optimizer trace when needed to see why alternatives were chosen or rejected.
- Evaluated composite/covering indexes against both read and write workloads.
- Re-measured after each individual change on representative data and parameters.
- Documented the impact on other queries before rolling out broadly.

The cost-based optimizer selects plans based on SQL semantics, schema structure, indexes, data statistics, and the server/storage engine cost model. Cardinality, selectivity, and fanout drive most estimate quality; index statistics and histograms supply distribution details, while the cost model enables comparing access paths and join orders. When a plan is poor, compare estimated rows against actual rows with `EXPLAIN ANALYZE`, locate the first point of divergence, inspect statistics and indexes, and only then consider hints. A good plan must be validated against real data and workloads, not just a cost figure or whether the optimizer uses an index.
