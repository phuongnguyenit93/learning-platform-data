# SIGNAL, RESIGNAL, and Preserving Error Information

Stored programs need a clear error contract so the application knows which operation failed, why it failed, and whether it can continue or must stop. MySQL provides SIGNAL to proactively raise a condition, RESIGNAL to forward the condition currently being handled by a handler, and GET DIAGNOSTICS to read diagnostic information such as SQLSTATE, error code, and message text.

SIGNAL is commonly used to reject invalid data or report business errors. RESIGNAL allows a handler to perform cleanup, collect information, or add context while still returning the original error to the caller. GET STACKED DIAGNOSTICS is especially important inside handlers: it reads the condition that triggered the handler even if statements executed inside the handler have already modified the current diagnostics area.

A common mistake is catching SQLEXCEPTION and only logging or returning a generic message, losing the original SQLSTATE and error code. Another mistake is using GET DIAGNOSTICS CONDITION 1 assuming the first condition is always the primary error; MySQL does not guarantee that. This lesson teaches how to design SQLSTATE values, raise errors, choose handlers, retrieve the right diagnostics, and preserve errors across multiple stored program layers.

The examples focus on server-side SQL statements. When creating routines using the `mysql` command-line client, use DELIMITER so the client does not terminate the CREATE statement at the first semicolon. DELIMITER is a client command, not an SQL statement sent to the server.

## Learning Objectives

After this lesson, you will be able to:

- Distinguish condition, warning, not found, and exception.
- Explain SQLSTATE structure and select an appropriate SQLSTATE.
- Proactively raise errors using SIGNAL.
- Define named conditions using `DECLARE ... CONDITION`.
- Choose CONTINUE or EXIT handlers according to control flow.
- Understand condition handler precedence and scope.
- Use GET DIAGNOSTICS and GET STACKED DIAGNOSTICS.
- Retrieve the exact primary condition when the diagnostics area holds multiple conditions.
- Use RESIGNAL to forward the original error without losing SQLSTATE and MYSQL_ERRNO.
- Replace only MESSAGE_TEXT or intentionally translate errors into a new business error code.
- Distinguish cursor NOT FOUND errors from regular SQL errors.
- Design handlers with clear cleanup and transaction ownership.
- Test errors using CALL, SHOW WARNINGS, SHOW ERRORS, and application code.

## 1. Conditions and Errors in MySQL

In stored programs, a condition is information generated by the server when a statement produces a state requiring attention. A condition can be:

- Success.
- Warning.
- Not found.
- Error/exception.

A condition typically contains the following components:

| Component | Meaning |
|---|---|
| SQLSTATE | 5-character status code per SQL/ODBC standard |
| MYSQL_ERRNO | MySQL-specific numeric error code |
| MESSAGE_TEXT | Descriptive message for the condition |
| Other diagnostics items | Constraint, schema, table, column, or cursor context if available |

SQLSTATE is standardized and usually suitable for applications classifying errors at a general level. MYSQL_ERRNO is MySQL-specific and useful when identifying a specific error within the MySQL ecosystem. MESSAGE_TEXT is meant for diagnostics; applications should not parse message strings to drive business logic because the text can change by version, locale, or context.

### 1.1. Common SQLSTATE Classes

SQLSTATE consists of 5 characters. The first two characters determine the condition class:

| Class | Meaning | General MySQL Handling |
|---|---|---|
| 00 | Success | Must not be used to SIGNAL errors |
| 01 | Warning | Raises warning; SQLWARNING handler can catch |
| 02 | Not found | NOT FOUND handler can catch |
| Other than 00, 01, 02 | Exception | SQLEXCEPTION handler can catch |

Examples:

- 02000: no data found.
- 23000: integrity constraint violation, commonly encountered with duplicate keys or foreign keys.
- 22012: division by zero.
- 45000: user-defined exception, commonly used for general business errors.

For application-raised business errors, SQLSTATE 45000 is the standard general choice. Do not use class 00 to report errors. Do not use class 02 for validation errors because it is treated as NOT FOUND and could unintentionally trigger a handler terminating a cursor loop.

### 1.2. SQLSTATE and MYSQL_ERRNO Do Not Replace Each Other

For example, a validation error can use:

    SIGNAL SQLSTATE '45000'
        SET MYSQL_ERRNO = 30001,
            MESSAGE_TEXT = 'amount must be positive';

Here:

- SQLSTATE 45000 identifies this as an exception raised by the stored program.
- MYSQL_ERRNO 30001 is an application-chosen numeric code to identify the specific case.
- MESSAGE_TEXT helps operators understand the cause.

Maintain your custom code ranges in project documentation to avoid colliding with internal conventions or MySQL error codes used by the application. MYSQL_ERRNO is a 16-bit unsigned integer; MESSAGE_TEXT is limited to 128 characters.

## 2. SIGNAL: Proactively Raising a Condition

SIGNAL is used to raise a new condition. General syntax:

    SIGNAL condition_value
        [SET signal_information_item = value [, ...]];

`condition_value` can be:

- `SQLSTATE [VALUE] 'xxxxx'`.
- A condition name declared with `DECLARE ... CONDITION` and defined with a SQLSTATE.

Common signal information items:

| Item | Purpose |
|---|---|
| SQLSTATE | Specified in `condition_value` |
| MYSQL_ERRNO | Numeric MySQL error code |
| MESSAGE_TEXT | Error message |
| CONSTRAINT_SCHEMA / CONSTRAINT_NAME | Constraint context |
| SCHEMA_NAME / TABLE_NAME / COLUMN_NAME | Object context |
| CURSOR_NAME | Related cursor name if applicable |

You cannot assign NULL to a signal information item. Each item may appear only once in SET. RETURNED_SQLSTATE is determined by `condition_value` and is not assigned directly inside SET.

### 2.1. Raising a Validation Error

Example procedure rejecting an invalid amount:

    CREATE PROCEDURE validate_payment(
        IN p_amount DECIMAL(12,2)
    )
    BEGIN
        IF p_amount IS NULL OR p_amount <= 0 THEN
            SIGNAL SQLSTATE '45000'
                SET MYSQL_ERRNO = 30001,
                    MESSAGE_TEXT = 'amount must be greater than zero';
        END IF;

        SELECT 'payment amount accepted' AS result;
    END;

If `p_amount` is invalid, SIGNAL raises an exception and the CALL statement terminates with the error unless a matching handler catches it. The trailing SELECT is not executed.

SIGNAL requires no special privileges. It can be used in stored procedures, functions, triggers, and events. MySQL also permits SIGNAL outside stored programs as an extension.

### 2.2. Raising an Intentional Warning

SQLSTATE class 01 indicates a warning:

    SIGNAL SQLSTATE '01000'
        SET MESSAGE_TEXT = 'optional field was ignored',
            MYSQL_ERRNO = 30010;

Warnings do not automatically terminate stored programs. An SQLWARNING handler can catch this condition. Applications can inspect warnings via SHOW WARNINGS or an appropriate diagnostics API.

Do not use a warning instead of an exception when an operation must stop. Conversely, do not raise an exception for a situation that only needs a warning and should continue.

### 2.3. Class 02 SIGNAL and NOT FOUND

SQLSTATE class 02 indicates NOT FOUND:

    SIGNAL SQLSTATE '02000'
        SET MESSAGE_TEXT = 'requested row was not found';

This condition can trigger a NOT FOUND handler. With cursors, NOT FOUND is normally used to signal that FETCH has run out of rows. A `SELECT ... INTO` returning no rows can also raise NOT FOUND.

Therefore, do not use SQLSTATE 02000 for validation or ordinary business errors. If a NOT FOUND handler exists to terminate a cursor loop, a SIGNAL 02000 elsewhere can cause control flow to exit the loop or block unexpectedly.

If NOT FOUND is raised directly via SIGNAL/RESIGNAL and no matching handler exists, MySQL handles it like EXIT. This differs from a NOT FOUND raised naturally by certain read operations, whose default behavior is to continue.

### 2.4. Rules MySQL Enforces for SIGNAL

- SQLSTATE must be a valid 5-character string.
- SQLSTATE starting with `00` is invalid for SIGNAL.
- SQLSTATE 45000 is the generic user-defined exception.
- SQLSTATE class 01 creates a warning.
- SQLSTATE class 02 creates a not found condition.
- Other classes create exceptions; class 40 is also handled by MySQL as a regular exception.
- SIGNAL is not ignored by IGNORE and does not depend on strict SQL mode.
- Statements after SIGNAL run only if the condition is handled by a matching CONTINUE handler.

## 3. DECLARE ... CONDITION: Naming a Condition

Condition names make code easier to read and avoid repeating SQLSTATE literals.

Example:

    CREATE PROCEDURE create_invoice(
        IN p_total DECIMAL(12,2)
    )
    BEGIN
        DECLARE invalid_total CONDITION
            FOR SQLSTATE '45000';

        IF p_total IS NULL OR p_total <= 0 THEN
            SIGNAL invalid_total
                SET MYSQL_ERRNO = 30021,
                    MESSAGE_TEXT = 'invoice total is invalid';
        END IF;

        SELECT 'invoice accepted' AS result;
    END;

A condition declared with a SQLSTATE can be used with SIGNAL and RESIGNAL.

### 3.1. Conditions Bound to MySQL Error Codes

`DECLARE ... CONDITION` can also name a MySQL error number:

    DECLARE duplicate_key CONDITION FOR 1062;

This name can be used in `DECLARE ... HANDLER`:

    DECLARE EXIT HANDLER FOR duplicate_key
    BEGIN
        -- handle duplicate entry error
    END;

However, a condition name bound to a MySQL error number cannot be used directly in SIGNAL or RESIGNAL. SIGNAL/RESIGNAL only accepts condition names defined with a SQLSTATE.

To raise a named application error, define the condition with a SQLSTATE rather than a MySQL error number:

    DECLARE invalid_state CONDITION FOR SQLSTATE '45000';

### 3.2. Condition Name Scope

A condition name is scoped to the `BEGIN ... END` block where it is declared and any child blocks within that scope. If a condition name with the same name is declared in nested blocks, the declaration closest to the statement applies.

Choose business-meaningful names:

- `invalid_amount`
- `customer_not_found`
- `duplicate_order`
- `insufficient_balance`

Avoid generic names like `error1` or `condition_a` because they make handlers and SIGNAL calls hard to read.

## 4. DECLARE ... HANDLER: Handling Conditions

A handler defines the action taken when a condition occurs within the block's scope.

General syntax:

    DECLARE handler_action HANDLER
    FOR condition_value [, condition_value] ...
    statement;

`handler_action` can be:

- CONTINUE: runs the handler and then resumes after the statement that raised the condition.
- EXIT: runs the handler and then exits the `BEGIN ... END` block where the handler is declared.

MySQL does not support the UNDO handler action.

Common `condition_value` options:

- MySQL error code, e.g. 1062.
- `SQLSTATE 'xxxxx'`.
- Declared condition name.
- SQLWARNING.
- NOT FOUND.
- SQLEXCEPTION.

### 4.1. CONTINUE Handler

A CONTINUE handler handles the condition and then resumes execution at the statement immediately after the one that caused the condition.

Example:

    CREATE PROCEDURE demo_continue_handler()
    BEGIN
        DECLARE v_warning_seen BOOLEAN DEFAULT FALSE;

        DECLARE CONTINUE HANDLER FOR SQLWARNING
            SET v_warning_seen = TRUE;

        SIGNAL SQLSTATE '01000'
            SET MESSAGE_TEXT = 'non-fatal warning';

        SELECT
            v_warning_seen AS warning_was_handled,
            'procedure continued' AS execution_state;
    END;

After the handler runs, the SELECT executes. CONTINUE fits recoverable or intentionally ignored situations, such as marking cursor exhaustion.

Do not use CONTINUE for every SQLEXCEPTION and keep running as if nothing happened. If the preceding statement failed, variables or intermediate data may not be in the state subsequent statements expect.

### 4.2. EXIT Handler

An EXIT handler handles the condition and then exits the block where the handler is declared.

Example:

    CREATE PROCEDURE demo_exit_handler()
    BEGIN
        DECLARE EXIT HANDLER FOR SQLEXCEPTION
        BEGIN
            SELECT 'error handled; leaving this block' AS state;
        END;

        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'operation rejected';

        SELECT 'this statement is not reached' AS state;
    END;

An EXIT handler declared in the outermost block terminates the procedure block after handling. If the handler is declared in an inner block, EXIT leaves only that inner block; code in the parent block may continue depending on control flow.

### 4.3. Declaration Placement in a Block

In MySQL, local variable and named condition declarations must precede cursor declarations; cursor declarations must precede handler declarations. All declarations must appear at the top of the block before executable statements.

Standard order:

    BEGIN
        DECLARE v_done BOOLEAN DEFAULT FALSE;
        DECLARE v_order_id BIGINT;
        DECLARE c_no_order CONDITION FOR SQLSTATE '02000';
        DECLARE cur_orders CURSOR FOR
            SELECT order_id FROM orders;
        DECLARE CONTINUE HANDLER FOR NOT FOUND
            SET v_done = TRUE;

        -- executable statements start here
    END;

Declaring a handler before a cursor causes MySQL to report a syntax or invalid declaration order error.

## 5. Precedence Order When MySQL Selects a Handler

When a condition occurs, MySQL searches for a handler in the current block. If none matches, the server searches outward through enclosing blocks. When multiple handlers match in the same scope, MySQL applies this precedence order:

1. A handler for a specific MySQL error code has the highest precedence.
2. A handler for a specific SQLSTATE has the next highest precedence.
3. General category handlers such as SQLWARNING, NOT FOUND, or SQLEXCEPTION have lower precedence.

Among general handlers, SQLEXCEPTION has higher precedence than SQLWARNING. Do not rely on declaration order to resolve ties among handlers of the same precedence.

Example:

    DECLARE EXIT HANDLER FOR 1062
        SET v_duplicate = TRUE;

    DECLARE EXIT HANDLER FOR SQLSTATE '23000'
        SET v_integrity_error = TRUE;

    DECLARE EXIT HANDLER FOR SQLEXCEPTION
        SET v_general_error = TRUE;

If an INSERT raises error 1062, the handler for error code 1062 is selected over the SQLSTATE 23000 or SQLEXCEPTION handlers.

### 5.1. Local Scope Takes Precedence Over Outer Scope

If both an inner block and an outer block have matching handlers, the handler in the block closer to the statement raising the condition is selected first. The local scope rule is evaluated before specificity among handlers in different scopes.

Example:

    BEGIN
        DECLARE EXIT HANDLER FOR 1062
            SET v_outer_duplicate = TRUE;

        BEGIN
            DECLARE EXIT HANDLER FOR SQLEXCEPTION
                SET v_inner_error = TRUE;

            -- error 1062 occurs here
        END;
    END;

The SQLEXCEPTION handler in the inner block can be selected because it resides in the closest scope, even though the outer block's handler specifies code 1062.

### 5.2. Avoid Multiple Handlers at the Same Precedence Level

If a statement raises multiple conditions and multiple handlers of equal precedence match, handler selection can be indeterminate. The outcome may vary depending on the circumstances of the condition.

Good design:

- Avoid declaring multiple handlers of the same precedence that can match the same statement.
- Prefer a single general handler and branch via diagnostics when needed.
- Isolate a statement into a child block if it needs a dedicated handling policy.
- Do not rely on the order of `DECLARE HANDLER` lines expecting MySQL to choose a particular handler.

## 6. GET DIAGNOSTICS: Reading Error Information

GET DIAGNOSTICS reads the diagnostics area created by MySQL after executing a statement.

General syntax:

    GET [CURRENT | STACKED] DIAGNOSTICS
        statement_information_item [, ...]

    GET [CURRENT | STACKED] DIAGNOSTICS
        CONDITION condition_number
        condition_information_item [, ...];

Two common statement information items:

- NUMBER: number of conditions currently in the diagnostics area.
- ROW_COUNT: number of rows affected according to the statement's diagnostics.

Common condition information items:

- RETURNED_SQLSTATE
- MYSQL_ERRNO
- MESSAGE_TEXT
- TABLE_NAME
- COLUMN_NAME
- SCHEMA_NAME
- CONSTRAINT_NAME
- CURSOR_NAME
- CLASS_ORIGIN
- SUBCLASS_ORIGIN

Some items may be empty or not populated by the server for a particular condition. Do not build business logic assuming TABLE_NAME or COLUMN_NAME will always have a value.

### 6.1. CURRENT Diagnostics Area

`GET CURRENT DIAGNOSTICS` reads the current diagnostics area. If the CURRENT keyword is omitted, this is the default.

Example after a failing statement in the `mysql` client:

    GET DIAGNOSTICS CONDITION 1
        @sqlstate = RETURNED_SQLSTATE,
        @errno = MYSQL_ERRNO,
        @message = MESSAGE_TEXT;

    SELECT @sqlstate, @errno, @message;

Inside a stored program, you can assign into local variables:

    GET CURRENT DIAGNOSTICS
        v_condition_count = NUMBER;

### 6.2. STACKED Diagnostics Area

When a handler is activated, MySQL pushes the diagnostics area from before entering the handler onto the stacked diagnostics area and creates a new current diagnostics area for the handler.

Initially both areas have identical contents. However, statements executed inside the handler can modify the current diagnostics area. The stacked diagnostics area preserves the condition that triggered the handler and is not overwritten by ordinary statements inside the handler; RESIGNAL is the exception that can affect it.

Therefore, when preserving the original error, use:

    GET STACKED DIAGNOSTICS ...

Do not execute SET, INSERT, ROLLBACK, or other SQL statements first and then try to fetch the original error from the CURRENT diagnostics area. By then the current area may have changed.

### 6.3. Do Not Assume CONDITION 1 Is the Primary Error

MySQL can record multiple conditions in the diagnostics area and does not guarantee that condition number 1 is always the primary condition of the preceding statement.

To obtain the primary condition, first read NUMBER and then use that condition number:

    GET STACKED DIAGNOSTICS
        v_condition_count = NUMBER;

    IF v_condition_count > 0 THEN
        GET STACKED DIAGNOSTICS CONDITION v_condition_count
            v_sqlstate = RETURNED_SQLSTATE,
            v_mysql_errno = MYSQL_ERRNO,
            v_message_text = MESSAGE_TEXT;
    END IF;

In this example, the last condition is selected per MySQL guidance to obtain the primary condition when multiple conditions exist. This is more reliable than assuming CONDITION 1 is always the error to report.

### 6.4. Complete Example Inside an EXIT Handler

    CREATE PROCEDURE capture_error_context()
    BEGIN
        DECLARE v_condition_count INT DEFAULT 0;
        DECLARE v_sqlstate CHAR(5) DEFAULT '00000';
        DECLARE v_mysql_errno INT DEFAULT 0;
        DECLARE v_message_text VARCHAR(128) DEFAULT '';

        DECLARE EXIT HANDLER FOR SQLEXCEPTION
        BEGIN
            GET STACKED DIAGNOSTICS
                v_condition_count = NUMBER;

            IF v_condition_count > 0 THEN
                GET STACKED DIAGNOSTICS CONDITION v_condition_count
                    v_sqlstate = RETURNED_SQLSTATE,
                    v_mysql_errno = MYSQL_ERRNO,
                    v_message_text = MESSAGE_TEXT;
            END IF;

            SELECT
                v_sqlstate AS original_sqlstate,
                v_mysql_errno AS original_errno,
                v_message_text AS original_message;

            RESIGNAL;
        END;

        SIGNAL SQLSTATE '45000'
            SET MYSQL_ERRNO = 30031,
                MESSAGE_TEXT = 'demo failure for diagnostics';
    END;

The handler reads information from the stacked area before running statements that may alter the current area. The SELECT only illustrates observation; in real applications, do not return sensitive content or turn handler output into a result set outside the API contract. RESIGNAL forwards the original condition to the caller.

## 7. RESIGNAL: Forwarding the Handled Condition

RESIGNAL is only valid when the current execution context is a condition handler. Calling RESIGNAL outside a handler raises the error `RESIGNAL when handler not active`.

General syntax:

    RESIGNAL;

    RESIGNAL SET signal_information_item = value [, ...];

    RESIGNAL condition_value
        [SET signal_information_item = value [, ...]];

RESIGNAL vs. SIGNAL:

| SIGNAL | RESIGNAL |
|---|---|
| Creates a new condition | Forwards the existing condition inside a handler |
| Can be used in stored programs and outside handlers | Can only be used while executing a handler |
| Used for validation or raising business errors | Used for cleanup, adding context, or forwarding errors to the caller |
| Does not require a prior condition | Relies on the condition that activated the handler |

### 7.1. RESIGNAL Without Arguments: Preserving the Original Error

This is the simplest way to preserve an error:

    DECLARE EXIT HANDLER FOR SQLEXCEPTION
    BEGIN
        -- Can collect diagnostics or perform cleanup.
        RESIGNAL;
    END;

RESIGNAL without arguments forwards the condition currently being handled by the handler without altering the original SQLSTATE, MYSQL_ERRNO, and MESSAGE_TEXT.

This is the preferred choice when the handler only needs to clean up or perform a side task and let the caller decide how to handle it.

### 7.2. RESIGNAL SET: Modifying Only What Is Needed

If you need to add context to the message while keeping the SQLSTATE and error code:

    DECLARE EXIT HANDLER FOR SQLEXCEPTION
    BEGIN
        RESIGNAL
            SET MESSAGE_TEXT = 'order operation failed';
    END;

In this form, MESSAGE_TEXT is replaced. Other unspecified signal information items retain the original condition's details.

MESSAGE_TEXT is limited to 128 characters. Use short messages that do not contain passwords, tokens, personal data, or full SQL statements.

### 7.3. RESIGNAL with a New SQLSTATE: Intentionally Translating an Error

Sometimes you want to map an infrastructure error to a business error understood by the API:

    DECLARE EXIT HANDLER FOR 1062
    BEGIN
        RESIGNAL SQLSTATE '45000'
            SET MYSQL_ERRNO = 30042,
                MESSAGE_TEXT = 'order number already exists';
    END;

Here the handler turns a duplicate key error into business error code 30042. The caller sees the new condition as the raised error; the diagnostics area may retain additional conditions related to the original error. This translation is an intentional API decision, not preserving the original error verbatim.

If you need full original error details for investigation, read diagnostics from STACKED before RESIGNAL, then write them to an appropriate log channel. Do not alter SQLSTATE or MYSQL_ERRNO if the application needs to distinguish the exact original MySQL error.

### 7.4. RESIGNAL Does Not Replace SIGNAL

Do not use RESIGNAL to raise a new validation error outside a handler:

    -- Invalid context if this statement runs outside a handler:
    -- RESIGNAL SQLSTATE '45000';

Use SIGNAL for a new condition:

    SIGNAL SQLSTATE '45000'
        SET MESSAGE_TEXT = 'customer is inactive';

Only use RESIGNAL inside an active handler to forward the condition that the handler received.

## 8. Handler Pattern for Preserving the Original Error

A general handler typically has three steps:

1. Read condition details from STACKED diagnostics.
2. Perform required cleanup per the transaction contract.
3. RESIGNAL so the caller receives the original error.

Pattern:

    DECLARE v_condition_count INT DEFAULT 0;
    DECLARE v_sqlstate CHAR(5);
    DECLARE v_mysql_errno INT;
    DECLARE v_message_text VARCHAR(128);

    DECLARE EXIT HANDLER FOR SQLEXCEPTION
    BEGIN
        GET STACKED DIAGNOSTICS
            v_condition_count = NUMBER;

        IF v_condition_count > 0 THEN
            GET STACKED DIAGNOSTICS CONDITION v_condition_count
                v_sqlstate = RETURNED_SQLSTATE,
                v_mysql_errno = MYSQL_ERRNO,
                v_message_text = MESSAGE_TEXT;
        END IF;

        -- Perform cleanup consistent with transaction ownership.
        RESIGNAL;
    END;

Do not catch SQLEXCEPTION and exit the handler without RESIGNAL if the intent is to report an error to the caller. If an EXIT handler ends the procedure normally, the caller may mistakenly believe the operation succeeded even though a statement inside failed.

## 9. Combining RESIGNAL with Transactions

A handler may need to roll back when the stored procedure owns the transaction itself. However, MySQL does not have true nested transactions. Executing START TRANSACTION while another transaction is active can commit the current transaction before starting a new one.

Therefore, every procedure must clearly define its transaction contract:

- **Procedure-owned transaction**: the procedure itself executes START TRANSACTION, COMMIT, and ROLLBACK. The caller must invoke it under the required contract, typically with no active transaction open.
- **Caller-owned transaction**: the caller opens the transaction and decides COMMIT/ROLLBACK. The procedure does not run START TRANSACTION, COMMIT, or ROLLBACK itself.

### 9.1. Procedure-Owned Transaction

Example skeleton:

    CREATE PROCEDURE create_order_atomic(
        IN p_customer_id BIGINT UNSIGNED,
        IN p_amount DECIMAL(12,2)
    )
    BEGIN
        DECLARE v_transaction_started BOOLEAN DEFAULT FALSE;
        DECLARE v_condition_count INT DEFAULT 0;
        DECLARE v_sqlstate CHAR(5);
        DECLARE v_mysql_errno INT;
        DECLARE v_message_text VARCHAR(128);

        DECLARE EXIT HANDLER FOR SQLEXCEPTION
        BEGIN
            GET STACKED DIAGNOSTICS
                v_condition_count = NUMBER;

            IF v_condition_count > 0 THEN
                GET STACKED DIAGNOSTICS CONDITION v_condition_count
                    v_sqlstate = RETURNED_SQLSTATE,
                    v_mysql_errno = MYSQL_ERRNO,
                    v_message_text = MESSAGE_TEXT;
            END IF;

            IF v_transaction_started THEN
                ROLLBACK;
            END IF;

            RESIGNAL;
        END;

        IF p_amount IS NULL OR p_amount <= 0 THEN
            SIGNAL SQLSTATE '45000'
                SET MYSQL_ERRNO = 30051,
                    MESSAGE_TEXT = 'order amount must be positive';
        END IF;

        START TRANSACTION;
        SET v_transaction_started = TRUE;

        INSERT INTO orders(customer_id, total_amount)
        VALUES (p_customer_id, p_amount);

        COMMIT;
        SET v_transaction_started = FALSE;
    END;

This example illustrates structure only. In real code, set the transaction flag to accurately reflect state after START TRANSACTION and COMMIT succeed; define clear behavior if START or COMMIT itself fails. Most importantly, the caller must have no active transaction if the procedure is designed to own its transaction.

The handler retrieves diagnostics before ROLLBACK. RESIGNAL after ROLLBACK still forwards the original condition from the stacked diagnostics area.

### 9.2. Caller-Owned Transaction

If the application manages transactions, the procedure should leave that decision to the caller:

    CREATE PROCEDURE reserve_inventory(
        IN p_product_id BIGINT UNSIGNED,
        IN p_quantity INT
    )
    BEGIN
        DECLARE EXIT HANDLER FOR SQLEXCEPTION
        BEGIN
            RESIGNAL;
        END;

        IF p_quantity <= 0 THEN
            SIGNAL SQLSTATE '45000'
                SET MYSQL_ERRNO = 30052,
                    MESSAGE_TEXT = 'quantity must be positive';
        END IF;

        UPDATE inventory
        SET available_quantity = available_quantity - p_quantity
        WHERE product_id = p_product_id
          AND available_quantity >= p_quantity;

        IF ROW_COUNT() <> 1 THEN
            SIGNAL SQLSTATE '45000'
                SET MYSQL_ERRNO = 30053,
                    MESSAGE_TEXT = 'insufficient inventory';
        END IF;
    END;

The caller can execute:

    START TRANSACTION;

    CALL reserve_inventory(1001, 2);

    -- Other related business operations.

    COMMIT;

If CALL fails, the application receives the exception and decides to ROLLBACK per the transaction contract. The procedure does not unilaterally roll back the caller's transaction.

### 9.3. Error Logging and Rollback

If a handler inserts a record into `error_log` and then executes ROLLBACK on the transaction, the log record in that same transaction may also be rolled back. MySQL does not provide autonomous transactions like some other DBMSs.

To preserve error logs:

- Log at the application layer after receiving the error.
- Use an independent connection/transaction for auditing if architecture allows.
- Emit events to an external logging system.
- If logging inside the same transaction, understand that rollback can erase that record.

Do not claim durable auditing if the log INSERT can be rolled back alongside business operations.

## 10. Cursors and NOT FOUND: Separating EOF from Exceptions

In a cursor loop, NOT FOUND normally signals that FETCH has no more rows. Common handler:

    DECLARE v_done BOOLEAN DEFAULT FALSE;
    DECLARE cur_orders CURSOR FOR
        SELECT order_id
        FROM orders
        ORDER BY order_id;
    DECLARE CONTINUE HANDLER FOR NOT FOUND
        SET v_done = TRUE;

    OPEN cur_orders;

    read_loop: LOOP
        FETCH cur_orders INTO v_order_id;

        IF v_done THEN
            LEAVE read_loop;
        END IF;

        -- Process the current row.
    END LOOP;

    CLOSE cur_orders;

This NOT FOUND handler can also catch conditions from a `SELECT ... INTO` returning no rows if that SELECT runs in the same scope. This easily causes the cursor loop to terminate prematurely by mistake.

### 10.1. Isolating SELECT ... INTO with a Child Block

If the loop contains a secondary query that might find no rows, place it in its own block with a dedicated handler:

    read_loop: LOOP
        FETCH cur_orders INTO v_order_id;

        IF v_done THEN
            LEAVE read_loop;
        END IF;

        BEGIN
            DECLARE v_related_found BOOLEAN DEFAULT TRUE;
            DECLARE v_related_value VARCHAR(100);

            DECLARE CONTINUE HANDLER FOR NOT FOUND
                SET v_related_found = FALSE;

            SELECT related_value
            INTO v_related_value
            FROM order_metadata
            WHERE order_id = v_order_id;

            IF NOT v_related_found THEN
                SET v_related_value = 'no metadata';
            END IF;
        END;

        -- Outer cursor handler is not triggered by the secondary SELECT.
    END LOOP;

The inner block limits the scope of the NOT FOUND handler for `SELECT ... INTO`. FETCH still uses the NOT FOUND handler in the block enclosing the cursor loop.

### 10.2. Do Not Use SQLSTATE 02000 for Business Errors

If a routine executes `SIGNAL SQLSTATE '02000'` to report an invalid customer, a cursor's NOT FOUND handler could treat it as EOF. Use SQLSTATE 45000 for business errors and reserve SQLSTATE 02000 for genuine no-data semantics.

## 11. Catching Specific Errors and Translating to Business Errors

Some MySQL errors can be translated into error codes better understood by the application. For example, duplicate key 1062:

    CREATE PROCEDURE register_external_order(
        IN p_external_ref VARCHAR(100)
    )
    BEGIN
        DECLARE duplicate_key CONDITION FOR 1062;

        DECLARE EXIT HANDLER FOR duplicate_key
        BEGIN
            RESIGNAL SQLSTATE '45000'
                SET MYSQL_ERRNO = 30061,
                    MESSAGE_TEXT = 'external reference already exists';
        END;

        INSERT INTO external_order(external_ref)
        VALUES (p_external_ref);
    END;

The caller receives business error 30061 instead of depending directly on code 1062. This is an API design choice; if operations need the original error, capture diagnostics before translating.

To preserve the error verbatim, use RESIGNAL without arguments:

    DECLARE EXIT HANDLER FOR 1062
    BEGIN
        RESIGNAL;
    END;

Do not map all SQLEXCEPTIONs to the same SQLSTATE if the application or operators need to distinguish deadlocks, timeouts, duplicate keys, foreign keys, and configuration errors.

## 12. Propagating Errors Across Multiple Stored Program Layers

Procedure A can call procedure B. If B encounters an error:

- B may declare no handler; the condition propagates to the caller according to handler scope rules.
- B has an EXIT handler and RESIGNAL; the original condition is forwarded to A.
- A may have a specific handler to translate errors or perform cleanup.
- If A also calls RESIGNAL, the condition continues propagating up to the application.

Flow diagram:

    Application
        |
        | CALL procedure_A()
        v
    procedure_A
        |
        | CALL procedure_B()
        v
    procedure_B
        |
        | statement raises SQLSTATE / MySQL error
        v
    handler in procedure_B
        |
        | GET STACKED DIAGNOSTICS
        | optional cleanup
        | RESIGNAL
        v
    handler in procedure_A (if applicable)
        |
        | RESIGNAL or deliberate translation
        v
    Application receives condition

Each layer should translate an error only when there is a clear business reason. If every layer replaces MESSAGE_TEXT or SQLSTATE, finding the root cause becomes harder.

## 13. The Diagnostics Area Can Hold Multiple Conditions

A single statement can generate multiple warnings or conditions. The diagnostics area includes:

- Statement information: NUMBER, ROW_COUNT.
- Condition information: SQLSTATE, MYSQL_ERRNO, MESSAGE_TEXT, and related items.

When a handler is activated, MySQL creates a stacked diagnostics area holding the information from before the handler started. The CURRENT diagnostics area belongs to statements inside the handler. Use GET STACKED DIAGNOSTICS to read the initial condition after the handler runs other statements.

Example retrieving the total condition count:

    GET STACKED DIAGNOSTICS
        v_condition_count = NUMBER;

If you need to inspect multiple conditions, you can loop from 1 to NUMBER and read each condition. However, to obtain the statement's primary error in MySQL, do not assume condition 1 is the primary error; read the condition count via NUMBER and retrieve the condition at that position.

GET DIAGNOSTICS is a diagnostic statement and is allowed in stored programs. SIGNAL, RESIGNAL, and GET DIAGNOSTICS cannot be used as dynamic SQL statements via PREPARE/EXECUTE.

## 14. Building an Error Contract for Applications

Stored programs should raise structured errors so applications do not have to parse message strings.

An error contract may include:

| Component | Recommended Convention |
|---|---|
| SQLSTATE | General error group, e.g., 45000 for custom business errors |
| MYSQL_ERRNO | Specific project-managed numeric code |
| MESSAGE_TEXT | Short, safe message, max 128 characters |
| Logging context | Request ID, tenant ID, procedure name, and permitted diagnostic info |
| Retry policy | Retry only identified transient errors such as deadlock/lock timeout per policy |

Example convention:

| MYSQL_ERRNO | Meaning |
|---:|---|
| 30001 | Invalid amount value |
| 30021 | Invalid invoice total |
| 30042 | External order reference already exists |
| 30053 | Insufficient inventory |

The numbers above are examples only. Projects must maintain an error code registry so services do not assign conflicting meanings.

### 14.1. Do Not Parse MESSAGE_TEXT to Drive Business Logic

Do not write logic like:

    IF error_message LIKE '%duplicate%' THEN
        -- handle duplicate
    END IF;

Messages can change. Use SQLSTATE and MYSQL_ERRNO:

- SQLSTATE for general classification.
- MYSQL_ERRNO for specific error codes.
- MESSAGE_TEXT for operators or logs.

### 14.2. Do Not Leak Sensitive Information

Error messages returned to clients must not contain:

- Passwords, tokens, or secrets.
- SQL statements containing sensitive literals.
- Unnecessary personal data.
- Internal file paths or infrastructure details unnecessary for the caller.
- Full diagnostics contents if they include sensitive data.

Keep client messages short and safe; store detailed information in controlled log channels.

## 15. Testing SIGNAL and RESIGNAL

Testing should not merely confirm that a routine raises an error. Verify SQLSTATE, MYSQL_ERRNO, MESSAGE_TEXT, and control-flow behavior.

### 15.1. Testing SIGNAL

    CALL validate_payment(0);

Expectations:

- CALL returns an error.
- SQLSTATE is 45000.
- MYSQL_ERRNO is 30001.
- Message indicates amount must be greater than 0.
- Statements after SIGNAL do not run unless handled by a CONTINUE handler.

### 15.2. Testing RESIGNAL Preserving the Original Error

Create a procedure that intentionally raises an error inside a general handler:

    CREATE PROCEDURE test_preserve_original_error()
    BEGIN
        DECLARE v_condition_count INT DEFAULT 0;
        DECLARE v_sqlstate CHAR(5);
        DECLARE v_errno INT;
        DECLARE v_message VARCHAR(128);

        DECLARE EXIT HANDLER FOR SQLEXCEPTION
        BEGIN
            GET STACKED DIAGNOSTICS
                v_condition_count = NUMBER;

            IF v_condition_count > 0 THEN
                GET STACKED DIAGNOSTICS CONDITION v_condition_count
                    v_sqlstate = RETURNED_SQLSTATE,
                    v_errno = MYSQL_ERRNO,
                    v_message = MESSAGE_TEXT;
            END IF;

            RESIGNAL;
        END;

        SIGNAL SQLSTATE '45000'
            SET MYSQL_ERRNO = 30071,
                MESSAGE_TEXT = 'original test condition';
    END;

    CALL test_preserve_original_error();

Expect the caller to receive SQLSTATE 45000, MYSQL_ERRNO 30071, and the original message. The handler can read the information before forwarding.

### 15.3. Testing RESIGNAL Replacing the Message

    DECLARE EXIT HANDLER FOR SQLEXCEPTION
    BEGIN
        RESIGNAL SET
            MESSAGE_TEXT = 'order service could not complete request';
    END;

Expect the original condition's SQLSTATE and MYSQL_ERRNO to be preserved while MESSAGE_TEXT is replaced with the new message.

### 15.4. Testing Error Translation

Trigger a duplicate key and check whether the handler translates the error code into the defined business code. Also confirm internal logs still retain the original error details if operations require them.

### 15.5. Testing Handler Scope

Create a child block with a NOT FOUND handler and a parent block with another NOT FOUND handler. Verify that a `SELECT ... INTO` returning no rows does not cause the outer cursor loop to terminate early.

## 16. Common Mistakes

- Using `SIGNAL SQLSTATE '00000'` even though it is the success class.
- Using SQLSTATE 02000 for validation errors and accidentally triggering a NOT FOUND handler.
- Using a warning when a transaction or operation must stop.
- Calling RESIGNAL outside a handler.
- Using a condition name bound to a MySQL error number inside SIGNAL.
- Assuming RESIGNAL and SIGNAL serve the same purpose.
- Catching SQLEXCEPTION and swallowing the error without returning a failure state to the caller.
- Using GET DIAGNOSTICS CURRENT after the handler already ran SET/ROLLBACK and losing the original condition details.
- Assuming CONDITION 1 is always the primary error.
- Forgetting to read NUMBER before selecting which condition to inspect.
- Storing only MESSAGE_TEXT while discarding SQLSTATE and MYSQL_ERRNO.
- Changing SQLSTATE or MYSQL_ERRNO with no API translation reason.
- Declaring a handler before a cursor.
- Failing to realize an EXIT handler exits the block where it is declared.
- Sharing one NOT FOUND handler for both a cursor and `SELECT ... INTO` in the same scope.
- Inserting into `error_log` inside a transaction, then calling ROLLBACK and expecting the log row to persist.
- Having a procedure unilaterally ROLLBACK a transaction owned by the caller.
- Using message text in application code to branch business logic.
- Returning diagnostics containing sensitive data to the client.
- Failing to test SQLSTATE, MYSQL_ERRNO, and control flow together.

## 17. Error Handling Design Checklist

- Distinguished warning, not found, and exception.
- Selected SQLSTATE matching the condition semantics.
- Used 45000 for custom business errors where appropriate.
- Assigned MYSQL_ERRNO according to the project's error code registry.
- Kept MESSAGE_TEXT short, non-sensitive, and within the 128-character limit.
- Declared condition names with the proper type (SQLSTATE or MySQL error number).
- Placed variables, conditions, cursors, and handlers in exact declaration order.
- Selected CONTINUE or EXIT matching desired control flow.
- Understood handler precedence and scope.
- Used GET STACKED DIAGNOSTICS inside handlers when original error preservation is needed.
- Retrieved NUMBER before selecting the primary condition.
- Used RESIGNAL without arguments when preserving the error verbatim.
- Replaced MESSAGE_TEXT or SQLSTATE only with clear API intent.
- Separated cursor NOT FOUND from `SELECT ... INTO` returning no rows.
- Determined whether transactions are procedure-owned or caller-owned.
- Verified whether logging can be rolled back with the transaction.
- Tested using the actual application account and client driver.
- Confirmed the caller receives the expected SQLSTATE, MYSQL_ERRNO, and message.
