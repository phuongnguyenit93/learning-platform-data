# LAST_INSERT_ID, CONNECTION_ID, and Session-Scoped Values

In a retail application, right after creating an order, the application typically needs the ID just assigned by MySQL to insert order line items. When a statement fails or a transaction rolls back, the application must know whether that ID can be trusted. When investigating a long-running query, a DBA needs to identify which connection is executing the statement and which database, user, or SQL mode that connection is using.

MySQL provides `LAST_INSERT_ID()` to retrieve the most recent `AUTO_INCREMENT` value generated on the current connection and `CONNECTION_ID()` to identify the connection attached to the server. In addition, each connection maintains session variables, user-defined variables, and other connection-specific state. Understanding connection scope accurately prevents fetching the wrong ID, leaking state across a connection pool, and misdiagnosing sessions.

## 1. Connections and Sessions in MySQL

A client connecting to MySQL Server establishes a connection. Throughout that connection's lifetime, the server maintains session state tied to it. This state can include:

- The server-assigned Connection ID.
- The default database, login account, and session identity values.
- SQL mode, timezone, character set, collation, and other session system variables.
- User-defined variables such as `@current_order_id`.
- The value remembered by `LAST_INSERT_ID()`.
- Any active open transaction, isolation level, and locks held by that transaction.
- Temporary tables, prepared statements, and other session-bound resources.

Two distinct connections have separate session states. If connection A just inserted a row with ID `101`, calling `LAST_INSERT_ID()` on connection B will not return `101`. Likewise, `SET @x = 10` in A does not make `@x` visible in B.

A session is not synonymous with an HTTP request or a single transaction. One connection can run many sequential transactions; with a connection pool, the same physical connection can be reused by many different requests at different times.

## 2. LAST_INSERT_ID(): Retrieving the Newly Generated AUTO_INCREMENT ID

`LAST_INSERT_ID()` with no arguments returns the first `AUTO_INCREMENT` value successfully generated by the most recent `INSERT` statement that produced an auto-increment value on the current connection.

Example creating an orders table:

```sql
CREATE TABLE orders (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    customer_id BIGINT UNSIGNED NOT NULL,
    order_note VARCHAR(255) NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id)
) ENGINE=InnoDB;
```

Inserting an order and reading its ID:

```sql
INSERT INTO orders (customer_id, order_note)
VALUES (120, 'Deliver during business hours');

SELECT LAST_INSERT_ID() AS new_order_id;
```

Both statements must execute on the same connection. If `INSERT` generates ID `101`, `SELECT LAST_INSERT_ID()` immediately afterward on that connection returns `101`.

### 2.1. Values Belong to the Current Connection

Suppose two sessions A and B are connected to the server:

| Action | Session A | Session B |
|---|---|---|
| Initial state | `LAST_INSERT_ID()` holds A's own value | `LAST_INSERT_ID()` holds B's own value |
| A inserts an order | Generates ID `101` | Unchanged |
| B inserts an order | Still retains A's last value | Generates ID `102` |
| A calls `LAST_INSERT_ID()` | Returns `101` | Unaffected |
| B calls `LAST_INSERT_ID()` | Unaffected | Returns `102` |

This is why `LAST_INSERT_ID()` is safer than `SELECT MAX(id)` for obtaining a newly inserted ID. `MAX(id)` can return the ID inserted concurrently by another transaction; `LAST_INSERT_ID()` returns the value generated by this specific connection.

### 2.2. Do Not Retrieve the ID via MAX(id)

Avoid doing this:

```sql
INSERT INTO orders (customer_id)
VALUES (120);

SELECT MAX(id) FROM orders;
```

If another connection inserts an order before `SELECT MAX(id)` executes, the query can return the other connection's ID. Use `LAST_INSERT_ID()` to retrieve the ID assigned to the current connection.

### 2.3. First ID of a Multi-Row INSERT

When a single statement inserts multiple rows, `LAST_INSERT_ID()` returns only the first auto-increment value generated by that statement:

```sql
INSERT INTO orders (customer_id, order_note)
VALUES
    (120, 'Order A'),
    (121, 'Order B'),
    (122, 'Order C');

SELECT LAST_INSERT_ID() AS first_generated_id;
```

The result is the first ID allocated in the multi-row insert, not a list of all generated IDs. Never compute the remaining IDs by simply adding `1`, because `auto_increment_increment`, `auto_increment_offset`, ID allocation mechanisms, errors, or concurrent inserts can produce non-contiguous ID sequences.

If the application needs all generated keys, use the driver's generated-keys API if supported for that statement type, or re-query by a known unique business key. Never rely on `AUTO_INCREMENT` sequences always being gapless or contiguous.

## 3. LAST_INSERT_ID(expr): Setting the Connection's Return Value

MySQL also supports the form:

```sql
LAST_INSERT_ID(expr)
```

This form returns `expr` and remembers that value so the next argumentless `LAST_INSERT_ID()` call on the same connection returns it.

Example:

```sql
SELECT LAST_INSERT_ID(9001) AS assigned_value;
SELECT LAST_INSERT_ID() AS remembered_value;
```

Both outputs return `9001`. This is purely session-local state; it does not allocate a new `AUTO_INCREMENT` value and does not write rows to any table.

Do not use `LAST_INSERT_ID(expr)` as a substitute for durable sequences or application-managed ID generators. The value is scoped solely to the current connection and may be overwritten by the next operation.

### 3.1. Using with INSERT ... ON DUPLICATE KEY UPDATE

A common pattern retrieves a record's ID regardless of whether the statement inserted a new row or hit the update branch on an existing unique key.

Create a table with a unique business key:

```sql
CREATE TABLE external_orders (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    external_key VARCHAR(80) NOT NULL,
    status VARCHAR(20) NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uq_external_key (external_key)
) ENGINE=InnoDB;
```

Run:

```sql
INSERT INTO external_orders (external_key, status)
VALUES ('EXT-2026-0001', 'NEW')
ON DUPLICATE KEY UPDATE
    id = LAST_INSERT_ID(id);

SELECT LAST_INSERT_ID() AS order_id;
```

- If `external_key` did not exist, MySQL inserts a new row and `LAST_INSERT_ID()` returns the newly generated ID.
- If `external_key` already existed, the `UPDATE` branch assigns `id` to its existing value via `LAST_INSERT_ID(id)`. The function remembers that ID for the connection, so the following `SELECT` returns the existing row's ID.

This pattern is helpful for upserts that need the primary key back. Ensure `external_key` uniquely identifies the exact same entity and that conflicts occur only on the expected key. If the table has multiple unique keys, the duplicate branch could be triggered by a different key; understand all constraints before adopting this pattern.

## 4. LAST_INSERT_ID, Transactions, and Rollback

`LAST_INSERT_ID()` does not prove that data has been committed. With InnoDB, an insert can succeed inside a transaction and later be rolled back:

```sql
START TRANSACTION;

INSERT INTO orders (customer_id, order_note)
VALUES (120, 'Test order');

SELECT LAST_INSERT_ID() AS generated_id;

ROLLBACK;
```

Within that session, `LAST_INSERT_ID()` can still retain the generated ID even after the row was rolled back. A rollback does not revert `LAST_INSERT_ID()` to its pre-transaction value.

Therefore:

- Having an assigned ID does not prove the row still exists.
- After a rollback, treat the rolled-back row's ID as business-invalid.
- Never emit external order confirmations before the transaction commits successfully.
- When verification is needed, re-query the row after commit on the same or another appropriate connection.

InnoDB's `AUTO_INCREMENT` also does not guarantee gap-free sequences. Rollbacks, failed inserts, `INSERT IGNORE`, concurrent contention, and allocation mechanisms can leave gaps. Never use auto-increment IDs as contiguous business serial numbers or as proof of record counts.

### 4.1. When an INSERT Fails

If an insert statement fails or inserts zero rows, `LAST_INSERT_ID()` is considered undefined with respect to that statement's outcome. Never rely on a stale session value to assume the failed insert created a row.

Check the execution outcome of the statement itself. If the driver throws an exception, handle the error first; never call `LAST_INSERT_ID()` and assume it belongs to the failed insert.

### 4.2. Stored Procedures, Functions, and Triggers

Changes to `LAST_INSERT_ID()` inside a stored procedure remain visible to the caller after the procedure finishes. For stored functions and triggers, the value is restored to what it was before the function/trigger started once it exits. This prevents internal changes inside a function or trigger from mutating the caller's `LAST_INSERT_ID()` state.

When a procedure returns an ID, clarify which insert produced it and whether subsequent statements inside the procedure could overwrite it. Returning the ID via an `OUT` parameter often makes the procedure's contract clearer.

## 5. Retrieving Generated Keys in Applications

In applications, prefer the driver's generated-keys API because it binds the result directly to the specific executed statement.

Java JDBC example:

```java
String sql = "INSERT INTO orders (customer_id, order_note) VALUES (?, ?)";

try (PreparedStatement statement = connection.prepareStatement(
        sql, Statement.RETURN_GENERATED_KEYS)) {
    statement.setLong(1, customerId);
    statement.setString(2, note);

    int affected = statement.executeUpdate();
    if (affected != 1) {
        throw new SQLException("Expected one inserted order");
    }

    try (ResultSet keys = statement.getGeneratedKeys()) {
        if (!keys.next()) {
            throw new SQLException("MySQL did not return a generated key");
        }
        long orderId = keys.getLong(1);
        // Use orderId within the same transaction/business flow.
    }
}
```

If using `SELECT LAST_INSERT_ID()` instead of `getGeneratedKeys()`, run the query on the exact same physical `Connection` that executed the insert. Never check out a separate connection from the pool to run `LAST_INSERT_ID()`; a different session will hold a different value.

## 6. CONNECTION_ID(): Identifying the Current Connection

`CONNECTION_ID()` returns the connection ID assigned by MySQL Server to the active client connection.

```sql
SELECT CONNECTION_ID() AS connection_id;
```

This value helps DBAs correlate the current session with process lists, logs, or Performance Schema activity.

### 6.1. Inspecting Running Connections

```sql
SHOW PROCESSLIST;
```

In the output, the `Id` column corresponds to the connection ID. You can filter for the current connection in Performance Schema:

```sql
SELECT
    THREAD_ID,
    PROCESSLIST_ID AS connection_id,
    PROCESSLIST_USER,
    PROCESSLIST_HOST,
    PROCESSLIST_DB,
    PROCESSLIST_COMMAND,
    PROCESSLIST_TIME,
    PROCESSLIST_STATE
FROM performance_schema.threads
WHERE PROCESSLIST_ID = CONNECTION_ID();
```

`PROCESSLIST_ID` is the connection ID displayed by commands such as `SHOW PROCESSLIST`. `THREAD_ID` is an internal Performance Schema identifier; the two are different types of IDs and are not interchangeable.

Visibility into full process lists or other users' sessions depends on account privileges and MySQL version. If sessions appear missing, check privileges and Performance Schema configuration before concluding a connection does not exist.

### 6.2. CONNECTION_ID Is Not a User ID or Request ID

A connection ID identifies a MySQL Server connection during that connection's lifetime. It does not identify:

- An end user logged into the application.
- A specific HTTP request or background job.
- A business transaction.
- A long-lived connection whose identity persists across reconnects.

When a connection closes and the client reconnects, the new connection receives a different ID. The old ID is not a permanent key to store in business tables either. Never use `CONNECTION_ID()` as a user ID, order ID, or cross-reconnect correlation ID.

In applications using connection pools, many unrelated requests share the same physical connection over time. Logging `CONNECTION_ID()` helps diagnose MySQL sessions, yet you should use application-generated request IDs/trace IDs to trace a request across services.

## 7. Common Session Identification Functions and Values

Beyond those two core functions, MySQL exposes several functions and system variables describing the connection's active context.

| Function/Variable | Value Provided | Notes |
|---|---|---|
| `CONNECTION_ID()` | ID of the current connection | Meaningful only for the connection's lifetime |
| `LAST_INSERT_ID()` | Most recent auto-increment ID on the connection | Does not prove the row committed |
| `DATABASE()` | Current default database | Returns `NULL` if no database is selected |
| `USER()` | User and host the client connected with | Can differ from the actual account checked for privileges |
| `CURRENT_USER()` | MySQL account used for privilege checks in the current context | Can differ from `USER()`, especially inside `DEFINER` routines |
| `CURRENT_ROLE()` | Active roles in the session | Depends on role setup and MySQL version |
| `@@SESSION.sql_mode` | Connection's SQL mode | Distinct from `@@GLOBAL.sql_mode` |
| `@@SESSION.time_zone` | Session timezone | Affects certain date/time operations and timestamp conversions |
| `@@SESSION.autocommit` | Autocommit state | Affects how transactions start and commit |
| `@@SESSION.transaction_isolation` | Default transaction isolation level for the session | Can be changed per session |
| `@@SESSION.character_set_client` | Charset used by the client when sending statements | Must match application encoding |
| `@@SESSION.collation_connection` | Collation used for string expressions on the connection | Can affect string literal comparisons |

Quick inspection query:

```sql
SELECT
    CONNECTION_ID() AS connection_id,
    DATABASE() AS current_database,
    USER() AS login_identity,
    CURRENT_USER() AS privilege_identity,
    CURRENT_ROLE() AS active_roles,
    @@SESSION.sql_mode AS session_sql_mode,
    @@SESSION.time_zone AS session_time_zone,
    @@SESSION.autocommit AS autocommit_mode;
```

`USER()` normally reflects the client-supplied username and source host; `CURRENT_USER()` reflects the MySQL account evaluated for privilege checks. Inside a stored routine executing with `SQL SECURITY DEFINER`, `CURRENT_USER()` can be the definer while `USER()` remains the original connecting user. This distinction is very helpful when troubleshooting privilege errors.

## 8. User-Defined Session Variables

MySQL lets you create user-defined variables prefixed with `@`. They live inside the current session without requiring prior declaration:

```sql
SET @current_customer_id = 120;
SET @display_name = 'Nguyễn An';

SELECT
    @current_customer_id,
    @display_name;
```

Other sessions cannot see these variables. When the connection closes, the variables disappear.

### 8.1. Assigning and Using Variables

Assign values with `SET`:

```sql
SET @tax_rate = 0.08;
SET @subtotal = 1250000;

SELECT @subtotal * (1 + @tax_rate) AS total_amount;
```

Or assign from a scalar query result:

```sql
SELECT COUNT(*)
INTO @open_order_count
FROM orders
WHERE status = 'OPEN';

SELECT @open_order_count;
```

User-defined variables are dynamically typed based on the assigned value; they lack static type declarations like local variables in stored procedures. When exact arithmetic is needed, `CAST` values to the desired type and never use variables as substitutes for schema type constraints.

### 8.2. Session Variables Are Not Transactional

`COMMIT` and `ROLLBACK` do not clear or revert user-defined variable values:

```sql
SET @step_marker = 'before';

START TRANSACTION;
SET @step_marker = 'inside';
ROLLBACK;

SELECT @step_marker;
```

The output remains `inside`. Session variables belong to connection state, not transactional data in InnoDB tables. Never rely on `@variable` for business rollback semantics.

### 8.3. Avoid Reading and Assigning the Same User Variable in One Expression

Do not rely on evaluation order when both reading and assigning the same user-defined variable inside a single statement:

```sql
-- Do not rely on this evaluation order.
SELECT @row_num := @row_num + 1, id
FROM orders;
```

Evaluation order is not guaranteed to match author expectations. In MySQL 8.0, use window functions such as `ROW_NUMBER()` for row numbering:

```sql
SELECT
    ROW_NUMBER() OVER (ORDER BY id) AS row_num,
    id
FROM orders;
```

## 9. SESSION and GLOBAL System Variables

System variables can be read by scope:

- `@@SESSION.variable_name` or `@@LOCAL.variable_name`: value for the current connection.
- `@@GLOBAL.variable_name`: server-wide default for new sessions, if the variable supports global scope.
- `@@variable_name`: typically resolves to the session value when the variable is session-scoped.

Example:

```sql
SELECT
    @@SESSION.sql_mode AS session_mode,
    @@GLOBAL.sql_mode AS global_default,
    @@SESSION.time_zone AS session_zone,
    @@GLOBAL.time_zone AS global_zone;
```

Changing session settings:

```sql
SET SESSION time_zone = '+07:00';
SET SESSION sql_mode = 'STRICT_TRANS_TABLES,NO_ENGINE_SUBSTITUTION';
```

Assigning `sql_mode` replaces the entire active list. Do not append a mode by assigning a shortened string if you intend to keep existing modes; read the current value first and construct the updated list intentionally.

Some system variables are read-only, some allow session or global changes, and some require administrative privileges. Check the documentation for the specific variable and server version before modifying it.

## 10. Connection Pools and Residual Session State

Connection pools maintain a pool of physical connections for reuse. When request A alters session state and returns the connection to the pool, request B may later check out that exact same connection.

For example, request A runs:

```sql
SET @current_order_id = 7001;
SET SESSION time_zone = '+00:00';
SET SESSION foreign_key_checks = 0;
```

If the pool does not reset session state, request B may observe:

- `@current_order_id` still set to `7001`.
- `time_zone` no longer matching the application's default.
- `foreign_key_checks` still disabled on that connection.

This is a cross-request state leak bug. With `LAST_INSERT_ID()`, a new request could also read a leftover ID from a previous request if it calls the function without first executing a successful insert of its own.

### 10.1. Connection Pool Management Principles

- Never rely on residual session variables from prior requests.
- Initialize required session settings when creating or borrowing a connection.
- If temporarily altering session state, save the previous value and restore it in a `finally` block.
- Ensure transactions are either `COMMIT`ted or `ROLLBACK`ed before returning connections.
- Use driver/pool connection-reset features where supported, and verify reset behavior for temporary tables, prepared statements, and user variables.
- Never return a connection to the pool with an open transaction or dirty session state.
- Use application request IDs/trace IDs to correlate logs; use connection IDs only for point-in-time query diagnostics.

### 10.2. Inspecting State Before Use

A diagnostic query can capture:

```sql
SELECT
    CONNECTION_ID() AS connection_id,
    LAST_INSERT_ID() AS last_insert_id,
    DATABASE() AS current_database,
    USER() AS client_identity,
    CURRENT_USER() AS privilege_identity,
    @@SESSION.autocommit AS autocommit_mode,
    @@SESSION.sql_mode AS sql_mode,
    @@SESSION.time_zone AS time_zone,
    @@SESSION.foreign_key_checks AS foreign_key_checks;
```

Do not log all of this on every request if overhead and log volume are unnecessary. Use it for diagnostics, health checks, or targeted logging, while avoiding logging sensitive connection credentials.

## 11. Diagnosing Connections with PROCESSLIST and Performance Schema

When a query runs long or a session holds locks, DBAs often need the connection ID to inspect it:

```sql
SHOW FULL PROCESSLIST;
```

Helpful columns include `Id`, `User`, `Host`, `db`, `Command`, `Time`, `State`, and `Info`. `SHOW FULL PROCESSLIST` displays the full query text instead of truncating it, though the text can contain sensitive data; restrict access to authorized personnel.

You can filter waiting or running connections via Performance Schema:

```sql
SELECT
    PROCESSLIST_ID AS connection_id,
    THREAD_ID,
    PROCESSLIST_USER,
    PROCESSLIST_DB,
    PROCESSLIST_TIME,
    PROCESSLIST_STATE,
    PROCESSLIST_INFO
FROM performance_schema.threads
WHERE TYPE = 'FOREGROUND'
  AND PROCESSLIST_ID IS NOT NULL
ORDER BY PROCESSLIST_TIME DESC;
```

`PROCESSLIST_TIME` reports seconds spent in the current command state, not necessarily the total connection age. For deeper statement and wait-event analysis, join `events_statements_current`, `events_waits_current`, and `sys` views if Performance Schema is enabled and privileges permit.

### 11.1. KILL QUERY and KILL CONNECTION

Once the target connection is confirmed, MySQL supports:

```sql
KILL QUERY 12345;
KILL CONNECTION 12345;
```

- `KILL QUERY` terminates the connection's currently executing statement while keeping the connection open.
- `KILL CONNECTION` terminates the connection itself.

These are high-impact administrative operations. Before killing, verify connection ID, user, host, SQL text, open transaction, and application impact. Terminating a connection can roll back an active transaction and leave the client uncertain about final commit status if disconnected mid-commit. Required privileges depend on server version and granted administrative privileges.

Never store a connection ID and reuse it much later to kill a session; the old connection may have closed and the ID may no longer represent the original session. Always re-query the process list right before acting.

## 12. Common Misconceptions

| Misconception | Reality | How to Avoid |
|---|---|---|
| `LAST_INSERT_ID()` is the table's maximum ID | It is the value remembered by the current connection from a qualifying insert | Never use `MAX(id)` to fetch a newly inserted ID |
| Returned ID proves the transaction committed | The ID can remain remembered after rollback | Confirm business success only after commit succeeds |
| `AUTO_INCREMENT` IDs are continuous without gaps | Rollbacks and concurrency can leave gaps | Never use IDs as contiguous business sequence numbers |
| Multi-row insert returns a list via `LAST_INSERT_ID()` | It returns only the first generated ID from the statement | Use the driver's generated-keys API or unique business keys |
| `LAST_INSERT_ID()` is shared across all clients | Values are isolated per connection | Run the query on the exact same physical connection |
| `CONNECTION_ID()` is a request ID | It only identifies a MySQL connection | Use application-level request IDs/trace IDs |
| Connection pools open a fresh connection per request | Pools reuse physical connections | Reset session state on checkout/return |
| `ROLLBACK` reverts user variables | User variables are session state, not transactional data | Reset explicitly or avoid relying on variables across requests |
| `USER()` and `CURRENT_USER()` are always identical | They serve different purposes | Use the right function when diagnosing privilege issues |
| `THREAD_ID` equals `CONNECTION_ID()` | Performance Schema thread ID differs from processlist connection ID | Match `PROCESSLIST_ID` with `CONNECTION_ID()` |

## 13. Safe Workflow for Creating Records and Retrieving IDs

In an order-creation workflow, the typical sequence is:

1. Borrow a connection from the pool and ensure clean session state.
2. Start a transaction when writing across multiple tables.
3. Execute `INSERT` into `orders` via a prepared statement.
4. Retrieve the generated key from that statement or call `LAST_INSERT_ID()` on the same connection.
5. Use that ID to insert `order_items` inside the same transaction.
6. Commit only after all required operations succeed.
7. If any error occurs, roll back and never expose the ID as a completed order.
8. Before returning the connection to the pool, ensure the transaction and session state are cleaned up.

Illustrative SQL example:

```sql
START TRANSACTION;

INSERT INTO orders (customer_id, order_note)
VALUES (120, 'New order');

SET @new_order_id = LAST_INSERT_ID();

INSERT INTO order_items (order_id, product_id, quantity)
VALUES (@new_order_id, 42, 2);

COMMIT;

SELECT @new_order_id AS committed_order_id;
```

This example assumes `order_items` has the matching columns and the detail insert succeeds. `@new_order_id` is a session variable and therefore valid only on the same connection. In application code, hold the ID in a local language variable rather than relying on user-defined SQL variables whenever the driver returns generated keys.

If any step prior to commit fails, the application must roll back and must not treat the retrieved ID as an existing record. If the client loses connectivity while sending `COMMIT`, commit outcome may be ambiguous on the client side; reconcile using an idempotency key or unique business key before retrying the request.

## 14. Checklist for Working with Session-Scoped Values

- Was `LAST_INSERT_ID()` called on the exact connection that performed the insert?
- Did the insert genuinely succeed and generate an `AUTO_INCREMENT` value?
- For multi-row inserts, does the application account for the function returning only the first ID?
- Have you avoided using `MAX(id)` or incrementing IDs manually instead of generated keys?
- Did the transaction commit without rollback or statement errors?
- Does the driver support `getGeneratedKeys()`, and is the application invoking it on the right statement?
- Is `CONNECTION_ID()` used strictly for connection diagnostics rather than as a business ID or request ID?
- Are `PROCESSLIST_ID` and `THREAD_ID` kept clearly distinct?
- Are session variables, SQL mode, timezone, and transaction state reset in the connection pool?
- Have you avoided assuming user variables are transactional or shared across connections?
- Before killing a connection, did you verify the current session and rollback impact?
- For disconnects around commit time, is there an idempotency or reconciliation mechanism?

## Conclusion

`LAST_INSERT_ID()` supplies the `AUTO_INCREMENT` ID generated by the most recent qualifying statement on the current connection; the `LAST_INSERT_ID(expr)` form sets the value returned by the next call, which is useful in upsert patterns. This value does not prove a transaction committed and is not reverted by rollback. `CONNECTION_ID()` identifies the connection for diagnostics, not a user or request. User-defined variables and session system variables are likewise connection-bound, persist across transactions, and can leak across connection pools unless reset. Always retrieve generated keys on the same connection, verify commit, manage session state cleanly, and use dedicated request IDs in the application layer.
