# Undo Purge, History List Length, and Long-Running Transactions

In MySQL, InnoDB performance depends not only on currently running queries, but also on the amount of old row versions that must be retained for open transactions. When a transaction holds a snapshot for too long, InnoDB cannot clean up certain undo logs and delete-marked records. History list length grows as a result, purging gets blocked at an old watermark, undo tablespaces can bloat, and read/write operations have to traverse additional accumulated history.

This lesson explains the lifecycle of undo logs, read views, and purge; how to interpret history list length; how to locate transactions holding snapshots; how to distinguish purge pinned by a transaction from purge falling behind write load; and how to handle it safely in production. This is part of mastering MySQL from transactions and concurrency control to relational database optimization and operations.

## 1. Why Must InnoDB Retain Old Data Versions?

### 1.1. MVCC and Consistent Reads

InnoDB uses Multi-Version Concurrency Control (MVCC) to allow concurrent reads and writes across transactions. An ordinary `SELECT` under `REPEATABLE READ` or `READ COMMITTED` is typically a consistent nonlocking read: it reads data as of a snapshot and does not lock the rows it reads.

If another transaction updates a row after the snapshot was established, the reading transaction may still need to see the older value. InnoDB reconstructs that version from the undo log. Thus, reading transactions do not have to wait for every writing transaction to finish just to get a consistent result.

Each InnoDB record contains internal versioning fields. Among them:

- **DB_TRX_ID** records the transaction that most recently created or updated the row version.
- **DB_ROLL_PTR** points to the undo record used to reconstruct the previous version.
- **DB_ROW_ID** is an internal row identifier used when InnoDB must auto-generate a clustered index.

When a row is `DELETE`d, InnoDB first marks the row as deleted (delete-mark). The row and its corresponding index records do not necessarily disappear physically right away. A transaction with an older snapshot may still need to read the pre-deletion version.

### 1.2. Undo Logs Serve Two Purposes

Undo logs record the information needed to reverse changes on `ROLLBACK` and to reconstruct older versions when consistent reads need them.

InnoDB distinguishes insert undo and update undo:

- **Insert undo** supports rolling back rows inserted by a transaction. Once the transaction commits, insert undo is no longer needed for consistent reads and can be discarded.
- **Update undo** supports both rollback and reconstructing old versions for consistent reads. After commit, this undo may still be needed until no active read view can see the old version.

Undo logs live in undo log segments, which belong to rollback segments. Rollback segments are stored in undo tablespaces or the global temporary tablespace depending on operation type. In MySQL 8.0 and later, regular undo logs are stored in separate undo tablespaces created at instance initialization; exact layout depends on version and deployment.

### 1.3. Why Can a Read-Only Transaction Slow Down Purge?

A read-only transaction generates little or no undo of its own, yet its read view can force InnoDB to retain undo generated by other transactions.

For example:

1. Transaction A opens a snapshot at time T1 and reads the `orders` table.
2. Transaction B updates a row in `orders` and `COMMIT`s at time T2.
3. Transaction C continues updating or deleting data and `COMMIT`s.
4. Transaction A still needs to see the state as of T1.
5. InnoDB must retain old versions that A's snapshot might need. Purge cannot clean past the safe watermark of that read view.
6. When A ends via `COMMIT` or `ROLLBACK`, the snapshot is released and purge can resume cleaning history no longer referenced.

Therefore, a connection in the `Sleep` state can still be the reason history list length grows if its transaction and read view remain open. The fact that a `SELECT` finished executing does not mean the transaction has ended.

## 2. Read Views and Snapshot Lifetimes

### 2.1. `REPEATABLE READ`

`REPEATABLE READ` is InnoDB's default isolation level. Consistent reads within the same transaction use the snapshot established by the first consistent read. You can also create the snapshot immediately when starting a transaction using:

~~~sql
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;

START TRANSACTION WITH CONSISTENT SNAPSHOT;

SELECT COUNT(*) FROM orders;

-- Subsequent SELECT statements continue reading the same snapshot.
-- End the transaction to release the read view.
COMMIT;
~~~

If an application opens a transaction, executes a `SELECT`, and then keeps the connection open while waiting for user input or calling another service, the read view can persist throughout that wait time. A transaction does not have to be actively executing a SQL statement to hold an old snapshot.

If a transaction begins with `START TRANSACTION` but has not yet performed a consistent read, the time the read view is created may not coincide with the transaction start time. Thus, transaction age is a key indicator for finding candidates, though not always identical to snapshot age.

### 2.2. `READ COMMITTED`

Under `READ COMMITTED`, each consistent read within a transaction creates a fresh snapshot. This typically shortens how long an old read view is held compared to `REPEATABLE READ` when an application runs multiple `SELECT`s in a long transaction.

However, `READ COMMITTED` does not automatically solve all undo issues:

- A long-running `SELECT` still holds a snapshot for the duration the statement needs to read.
- A long writing transaction still retains the undo required for rollback until it finishes.
- A transaction can still hold row locks or other resources.
- Results between two `SELECT`s in the same transaction may differ because the snapshot is refreshed.

Only change the isolation level when business semantics allow it. Do not switch the entire system to `READ COMMITTED` solely to lower history list length without evaluating the consistency guarantees the application relies on.

### 2.3. Locking Reads Differ from Consistent Reads

`SELECT ... FOR UPDATE` and `SELECT ... FOR SHARE` are locking reads. They read state consistent with current locking mechanics, not simply as a consistent nonlocking read like an ordinary `SELECT`.

Locking reads can hold row locks until the transaction ends. A long writing or locking-read transaction can cause lock waits, block other DML, and retain its own undo until commit/rollback.

Distinguish two separate problems:

- **Old read views** can pin purge even without holding row locks.
- **Long-held locks** can block other transactions even if they are not the direct cause of history list length growth.

One transaction can cause both problems if it both creates an old read view and performs locking/writing operations.

### 2.4. Common Situations That Hold Snapshots Too Long

- Applications disable autocommit or use a transaction wrapper without calling `COMMIT`/`ROLLBACK` on every code path.
- Connection pools return a connection to the pool while a transaction is still open.
- A `SELECT` finishes, but the application holds the transaction open waiting on user interaction.
- A streaming or cursor-based reader runs slowly while the client processes rows chunk by chunk.
- Reporting jobs run inside a large transaction.
- Logical backups run `mysqldump --single-transaction` for a long time while the system executes heavy DML.
- A batch process performs many updates in a single transaction before committing.
- An application hits an exception or timeout and the error-handling path fails to close the transaction.

In particular, a read-only transaction under `REPEATABLE READ` can still pin the history list. Do not look only for transactions with large `trx_rows_modified`.

## 3. How Does Purge Work?

### 3.1. Purge Is Background Cleanup

Purge is InnoDB's background work to process undo log pages in the history list once old versions are no longer needed for MVCC or rollback. This includes removing delete-marked records from the clustered index and secondary indexes, and then freeing the processed undo log pages.

A `DELETE` does not mean the row and all index records are physically erased the instant the statement finishes. Distinguish these steps:

1. `DELETE` marks the row as deleted and writes the required undo.
2. The transaction commits.
3. Existing old read views may still need the pre-deletion version.
4. Once no read view needs that version, purge can process the undo and remove the delete-marked records.
5. Data page space is freed or becomes reusable within the tablespace.

`UPDATE` can also create old versions and delete-mark old secondary index records whenever indexed column values change. Thus, heavy `UPDATE`/`DELETE` loads can generate substantial work for purge.

### 3.2. Purge Threads and the History List

Purge runs on a background schedule using one or more purge threads. These threads process undo log pages in the history list. The thread count is governed by **`innodb_purge_threads`**; this sets the maximum number of purge threads allowed, and the system may adjust the actual active threads.

DML concentrated on a single table can bottleneck purging on that table to a single thread, even if more threads are configured. Increasing purge threads does not always boost throughput: threads may contend on the same table and compete with application threads for CPU/I/O.

If DML is spread across many tables, raising purge capacity may help after measuring and testing. If DML is concentrated on a few hot tables, observe contention and actual effectiveness before making changes.

### 3.3. When Can Purge Not Keep Up?

There are two main categories of causes:

**An old read view is pinning the purge watermark**

InnoDB must retain versions that an old snapshot might need. Even if purge threads have spare CPU and storage capacity, they are not allowed to clean history past that safe watermark. Adding purge threads will not fix the root cause; you must end the transaction holding the snapshot.

**Purge throughput is lower than the history generation rate**

No overly old read view exists, yet the `UPDATE`/`DELETE` workload still generates history faster than purge can process it. Causes may include massive DML, heavy operations on the same table, slow storage, insufficient CPU, or suboptimal purge settings for the workload.

Both categories can occur simultaneously. Before tuning variables, determine whether purge is pinned by a read view or simply lacks processing capacity.

## 4. What Is History List Length?

### 4.1. Interpreting the Metric Correctly

History list length is the length metric of the history list maintained by InnoDB and displayed in the `TRANSACTIONS` section of `SHOW ENGINE INNODB STATUS`. The history list holds undo log pages from committed transactions awaiting purge processing.

This metric:

- Indicates the backlog of history purge still has to process.
- Can grow under heavy write activity or when a transaction holds an old read view.
- Is not a count of deleted rows.
- Is not a count of open transactions.
- Is not undo size in bytes or megabytes.
- Has no fixed mapping from one history list unit to a specific row count or file size.

Two systems with the same history list length can have vastly different undo byte volumes, affected rows, and purge costs. Therefore, use the metric to track trends and pair it with transaction, DML, I/O, and undo tablespace size metrics.

### 4.2. Viewing History List Length via `SHOW ENGINE INNODB STATUS`

Run in a MySQL client:

~~~sql
SHOW ENGINE INNODB STATUS;
~~~

In the `mysql` CLI you can use vertical format:

~~~sql
SHOW ENGINE INNODB STATUS\G
~~~

Look for the `TRANSACTIONS` section, for example:

~~~text
------------
TRANSACTIONS
------------
Trx id counter 0 290328385
Purge done for trx's n:o < 0 290315608 undo n:o < 0 17
History list length 20
~~~

Output lines may vary by version. Pay attention to:

- **Trx id counter**: current transaction ID counter.
- **Purge done for trx's n:o**: transaction watermark up to which purge has processed based on displayed internal info.
- **History list length**: currently reported length of the history list.

If history list length rises across multiple samples, look for old transactions and check whether purge is pinned at the same watermark. A single snapshot is insufficient to conclude purge is stalled.

### 4.3. Tracking via `INNODB_METRICS`

You can query the corresponding metric in `INFORMATION_SCHEMA.INNODB_METRICS`:

~~~sql
SELECT
    NAME,
    COUNT,
    TYPE,
    STATUS,
    COMMENT
FROM INFORMATION_SCHEMA.INNODB_METRICS
WHERE NAME = 'trx_rseg_history_len';
~~~

The **`trx_rseg_history_len`** metric reflects history list length. Inspect the `TYPE` and `STATUS` columns to see how it is collected on your running version. If the metric is disabled in the metrics table, you can enable just this counter:

~~~sql
SET GLOBAL innodb_monitor_enable = trx_rseg_history_len;
~~~

There is no need to enable all InnoDB metrics just to monitor history list length. Counters can be enabled/disabled/reset and their state may not persist across restarts; re-verify after upgrades or restarts.

### 4.4. Evaluating Trends Instead of a Fixed Threshold

Sample periodically, e.g., every 30–60 seconds, and record:

| Timestamp | History list length | Oldest transaction | Load notes |
|---|---:|---|---|
| T0 | 12,000 | 2 minutes | Normal write load |
| T1 | 18,000 | 15 minutes | Reporting job started |
| T2 | 31,000 | 16 minutes | DML still rising |
| T3 | 32,000 | 16 minutes | History barely dropping |
| T4 | 4,000 | No old transaction | Purge caught up |

The numbers above only illustrate how to read trends, not universal alert thresholds.

A history list of several thousand may be normal for a given workload; a low value that climbs steadily can still signal an unhealthy trend. Establish baselines per MySQL version, DML rate, data type, undo capacity, and application SLA.

Observe at least three factors:

- **Current level**: how large the history list is relative to baseline.
- **Rate of change**: whether the metric continues climbing or is being driven down by purge.
- **Duration**: how long the backlog persists and whether it coincides with an old transaction.

Never set an alert on a single generic threshold and automatically kill transactions when that threshold is crossed.

## 5. Finding Long-Running Transactions

### 5.1. Listing Active InnoDB Transactions

`INFORMATION_SCHEMA.INNODB_TRX` provides information about currently active transactions in InnoDB, including start time, state, isolation level, current query, and rows locked/modified.

~~~sql
SELECT
    trx_id,
    trx_state,
    trx_started,
    TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS age_seconds,
    trx_isolation_level,
    trx_is_read_only,
    trx_autocommit_non_locking,
    trx_rows_locked,
    trx_rows_modified,
    trx_mysql_thread_id,
    trx_query
FROM information_schema.innodb_trx
ORDER BY trx_started;
~~~

How to read the columns:

- **trx_started**: timestamp when the transaction began.
- **age_seconds**: transaction age as of query execution time.
- **trx_state**: `RUNNING`, `LOCK WAIT`, `ROLLING BACK`, or `COMMITTING`.
- **trx_isolation_level**: transaction isolation level.
- **trx_is_read_only**: whether the transaction is marked read-only.
- **trx_autocommit_non_locking**: information on nonlocking read-only autocommit transactions.
- **trx_rows_locked**: approximate number of rows currently locked.
- **trx_rows_modified**: number of rows modified/inserted.
- **trx_mysql_thread_id**: MySQL connection ID.
- **trx_query**: currently executing statement; may be `NULL` if no statement is currently running.

Do not filter only for transactions with large `trx_rows_modified`. A read-only transaction can have `trx_rows_modified = 0` and still hold an old read view.

Some read-only and nonlocking transactions are not assigned an InnoDB transaction ID in the same way as write transactions. Therefore, do not filter out rows just because `trx_id` does not look like a normal write ID. Inspect age, isolation level, read-only status, and connection ID.

The `PROCESS` privilege is required to query `INFORMATION_SCHEMA.INNODB_TRX`. If the monitoring account lacks this privilege, coordinate with an operational account that has proper permissions.

### 5.2. Joining Transactions with Connections

To see the user, host, and connection state, join `INNODB_TRX` with Performance Schema `threads`:

~~~sql
SELECT
    it.trx_mysql_thread_id AS connection_id,
    th.processlist_user,
    th.processlist_host,
    th.processlist_db,
    th.processlist_command,
    th.processlist_time,
    it.trx_started,
    TIMESTAMPDIFF(SECOND, it.trx_started, NOW()) AS trx_age_seconds,
    it.trx_state,
    it.trx_isolation_level,
    it.trx_is_read_only,
    it.trx_autocommit_non_locking,
    it.trx_rows_locked,
    it.trx_rows_modified,
    it.trx_query
FROM information_schema.innodb_trx AS it
LEFT JOIN performance_schema.threads AS th
    ON th.processlist_id = it.trx_mysql_thread_id
ORDER BY it.trx_started;
~~~

Pay special attention to this combination:

- **processlist_command = Sleep**
- Large **trx_age_seconds**
- **trx_query IS NULL**
- **trx_isolation_level = REPEATABLE READ**
- **trx_rows_modified = 0** or very low

This is a prime candidate for a transaction that ran a `SELECT`, kept its snapshot, and left the connection idle. Still, verify the actual application and transaction before concluding. `Sleep` only describes the connection's current state; it does not by itself prove the transaction is pinning purge.

### 5.3. Checking `PROCESSLIST` and Statement History

You can quickly view connections:

~~~sql
SHOW FULL PROCESSLIST;
~~~

Or use Performance Schema:

~~~sql
SELECT
    PROCESSLIST_ID,
    PROCESSLIST_USER,
    PROCESSLIST_HOST,
    PROCESSLIST_DB,
    PROCESSLIST_COMMAND,
    PROCESSLIST_TIME,
    PROCESSLIST_STATE,
    PROCESSLIST_INFO
FROM performance_schema.threads
WHERE TYPE = 'FOREGROUND'
ORDER BY PROCESSLIST_TIME DESC;
~~~

`PROCESSLIST_INFO` usually shows only the current statement. If the connection is in `Sleep`, it may be `NULL` even while a transaction remains open. You can check `events_statements_history` or application logs if Performance Schema is configured to retain sufficient history, though in-memory history is bounded and older statements may have been evicted.

When correlating `INNODB_TRX` and Performance Schema `threads`, remember these are views of continuously changing internal state. The two sources may not be strictly synchronized at an exact instant; a transaction or connection may finish between reading the tables.

### 5.4. Distinguishing Snapshot-Holding Transactions from Lock Blockers

A read-only transaction can pin the history list without holding any row locks. Therefore, lock wait queries will not necessarily identify the transaction pinning purge.

Conversely, a transaction holding many row locks or in `LOCK WAIT` may block the application, yet may not be the transaction holding the oldest read view.

To check lock waits, read Performance Schema `data_locks` and `data_lock_waits`, or `sys.innodb_lock_waits` if available. Lock analysis is a separate diagnostic branch; do not use a list of lock blockers in place of checking transaction age and history list length.

## 6. Classifying Causes of History List Growth

### 6.1. Old Transaction Holding a Read View

Common signs:

- History list grows while an old transaction remains open.
- The transaction uses `REPEATABLE READ` and may have executed a consistent read.
- The connection may be `Sleep` with `trx_query` set to `NULL`.
- Once the transaction ends, the history list begins declining after purge processes the backlog.
- Increasing `innodb_purge_threads` does not let purge advance past the pinned read view.

The fix is to identify the transaction owner, verify business context, and end the transaction appropriately.

### 6.2. No Old Read View, Yet DML Generates History Too Fast

Common signs:

- No obvious old transaction appears in `INNODB_TRX`.
- History list still climbs during peak hours with heavy `UPDATE`/`DELETE`.
- CPU, I/O, or purge threads are heavily loaded.
- When DML load drops, the history list starts shrinking.
- DML concentrated on one hot table limits parallel purge scaling.

Check DML rate, transaction size, number of updated indexes, storage latency, and CPU capacity. Do not assume purge is broken merely because history list length is high.

### 6.3. Large Write Transactions and Rollback Segment Bloat

A large write transaction can generate huge amounts of undo before committing. While it stays open, undo required for rollback cannot be freed. If the transaction is rolled back, InnoDB must reverse the modifications; this process can take a long time depending on row count and modified data volume.

Inspect:

- `trx_rows_modified` and `trx_rows_locked`.
- Whether `trx_state` is `ROLLING BACK`.
- Transaction duration.
- Undo tablespace size.
- CPU/I/O and rollback completion speed.

Do not kill a massive write transaction expecting resources to be freed immediately. Rollback can continue running and create additional load for quite some time.

### 6.4. DML Concentrated on a Single Table

Purging on a single hot table may not scale linearly with the number of purge threads. Hot indexes, records, and pages can increase contention. If one table receives heavy `UPDATE`/`DELETE` traffic, examine index design, key distribution, and data batching.

Reducing unnecessary DML, using indexed filters, and batching can be far more effective than mechanically raising purge thread counts.

## 7. System Impact of Purge Lag

Prolonged history list growth can cause several consequences:

- Undo tablespaces grow in size because undo logs cannot yet be freed.
- More old versions must be retained to serve consistent reads.
- Delete-marked secondary index records persist longer before purge cleans them.
- Queries may have to traverse more old versions when reconstructing rows for snapshots.
- The buffer pool and I/O must serve extra old data or index pages containing unpurged records.
- Tables can retain many delete-marked records, increasing size and access cost.
- When backlogs persist, DML and query performance can degrade, especially if purge competes for resources with the main workload.

Still, a high history list does not automatically prove a specific SQL query is slow because of MVCC. Compare query latency, rows examined, buffer pool metrics, I/O, transaction waits, and DML history within the same window.

Also distinguish logical space from file size:

- Purge frees undo log pages and cleans old records so pages can be reused.
- Table data tablespace files do not necessarily shrink on the filesystem after purge.
- Undo tablespaces have a separate truncation mechanism; a drop in HLL does not mean undo files immediately shrink.

## 8. Investigation Workflow When History List Grows

### Step 1: Confirm Metrics and Trends

Capture multiple snapshots of:

~~~sql
SHOW ENGINE INNODB STATUS\G

SELECT NAME, COUNT, TYPE, STATUS, COMMENT
FROM information_schema.innodb_metrics
WHERE NAME = 'trx_rseg_history_len';
~~~

Record timestamps, HLL, purge watermark, and metric status. Determine whether the metric is climbing, flat, or declining.

### Step 2: Find the Oldest Transactions

~~~sql
SELECT
    trx_mysql_thread_id,
    trx_started,
    TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS age_seconds,
    trx_state,
    trx_isolation_level,
    trx_is_read_only,
    trx_rows_locked,
    trx_rows_modified,
    trx_query
FROM information_schema.innodb_trx
ORDER BY trx_started;
~~~

Look for old transactions, including read-only ones and those with no currently executing statement.

### Step 3: Identify the Owner

Join connection ID with Performance Schema `threads`, host, user, database, and command. Cross-reference with application logs, request IDs, job schedulers, backup processes, and connection pools.

### Step 4: Classify the Transaction

Ask these questions:

- Is this a read-only or write transaction?
- Might it have already created a consistent read view?
- Is it `REPEATABLE READ` or `START TRANSACTION WITH CONSISTENT SNAPSHOT`?
- Is the connection running a query, in `Sleep`, or waiting on locks?
- Is it running a backup, report, or data stream?
- Does the transaction have many modified rows that would take a long time to roll back?

### Step 5: Assess Purge Capacity

If there is no obvious old read view, inspect CPU, storage latency, DML workload, hot table count, and purge settings. Compare when history list climbed against `UPDATE`/`DELETE` throughput and when load subsided.

### Step 6: Pick the Lowest-Risk Action

- If the application still controls the session, have the session finish the transaction with `COMMIT` or `ROLLBACK` per business logic.
- If the transaction is orphaned or invalid, coordinate with the application owner to cancel the job or close the connection.
- If purge cannot keep up with load, reduce/batch DML and inspect indexes and resources before tuning purge settings.
- Monitor HLL afterward to confirm the backlog actually begins shrinking.

### Step 7: Verify Recovery

Continue sampling HLL, old transactions, undo tablespace size, CPU/I/O, and application latency. Consider the incident stabilized only when HLL trends down or returns to baseline, no abnormal old transactions remain, and the workload is not regenerating the backlog.

## 9. Handling Long-Running Transactions Safely

### 9.1. Prefer Ending Transactions from the Application

If the session is still controlled by the application, the best approach is to let the session execute `COMMIT` or `ROLLBACK` according to business logic. This gives the application an explicit completion status and prevents a connection pool from reusing a session carrying an old transaction.

If the transaction is read-only with no changes to commit, `COMMIT` typically closes the read view cleanly. If the transaction wrote data without finishing business logic, determine accurately whether to commit or roll back.

### 9.2. `KILL QUERY` Is Not the Same as Ending a Transaction

`KILL QUERY` cancels only the statement currently executing on the connection. If the statement is aborted while the connection still has an open transaction, the read view and transaction resources can remain alive.

When the goal is to terminate an abandoned connection, `KILL CONNECTION` disconnects the session and InnoDB rolls back any uncommitted transaction. However, rolling back a large transaction can take a long time; the transaction state may transition to `ROLLING BACK`.

Use the following action only after confirming the exact connection and obtaining approval from an authorized operator:

~~~sql
-- Re-verify the connection ID and owner before executing.
KILL CONNECTION 12345;
~~~

Never copy an ID from a stale snapshot and kill it minutes later. The connection ID might no longer belong to the original session. Re-query `INNODB_TRX` and `threads` immediately before acting.

### 9.3. Avoid Bulk-Killing by Transaction Age

Do not automatically kill every transaction exceeding a fixed number of minutes. Some long transactions may be backups, reports, or intentionally long-running business jobs. Killing the wrong transaction can trigger a massive rollback, disrupt work, or create extra load.

A better policy is:

- Identify owners and workload types.
- Set transaction timeouts appropriate to SLAs.
- Log when transactions open and close.
- Implement cleanup on application failures.
- Alert on transaction age and HLL trends.
- Automatically abort only job types governed by clear safety rules.

## 10. Reducing Excessive History Generation from the Application

### 10.1. Keep Transactions Short

Open transactions right before operations requiring consistency and end them immediately afterward. Never hold a transaction open while waiting on users, making HTTP calls, downloading files, or doing heavy CPU work.

Handling pattern:

~~~sql
START TRANSACTION;

UPDATE inventory
SET quantity = quantity - 1
WHERE product_id = 1001
  AND quantity > 0;

-- Perform DB operations that belong in the same transaction.

COMMIT;
~~~

In application code, ensure every success path commits and every error path rolls back or safely closes the connection.

### 10.2. Batching `DELETE` and `UPDATE`

A single transaction deleting millions of rows can create massive undo and hold resources for a long time. Split the work into small batches, committing after each batch:

~~~sql
DELETE FROM audit_log
WHERE created_at < '2024-01-01'
ORDER BY created_at
LIMIT 5000;
~~~

If autocommit is enabled, each statement is its own transaction. If inside an explicit transaction, `COMMIT` after each batch per job design.

For stable batching:

- Have appropriate indexes for filter conditions and processing order.
- Use a key marker or timestamp boundary to resume from the previous batch.
- Size each batch according to actual latency and undo impact.
- Pause or throttle pace when production load increases.
- Monitor HLL, replica lag, lock waits, and I/O between batches.

Do not use `LIMIT` arbitrarily without well-defined filter predicates; without an index, each batch may still scan substantial data and add load.

### 10.3. Timeout and Connection Pool Design

Applications should implement:

- Transaction timeouts tailored to business operation type.
- Clear query timeouts and request deadlines.
- Transaction state checks before returning connections to the pool.
- Rollbacks on exceptions or cancelled requests.
- No sharing of a single connection across concurrent threads.
- Logging of connection ID, transaction start time, and correlation/request ID.
- Alerts when `Sleep` connections hold open transactions for too long.

Application-tier timeouts do not always automatically terminate MySQL-side transactions. Verify whether the driver and framework send a cancel/rollback or merely stop waiting on the client side.

### 10.4. Long Backups and Reports

`mysqldump --single-transaction` creates a consistent snapshot to dump consistent data without locking all InnoDB tables throughout the run. If the dump takes a long time while the application continues heavy writes, the backup's read view can retain old undo and raise HLL.

During long backups:

- Schedule during low-write windows when feasible.
- Monitor the backup transaction and HLL throughout the process.
- Estimate dump duration from data size and actual read speed.
- Consider running backups on a replica when consistent with topology and consistency needs.
- Ensure the backup process closes its transaction upon completion or cancellation.
- Prevent job retries from opening multiple concurrent snapshots.

Running backups on a replica reduces impact on the primary, though it does not eliminate purge overhead on that replica. Monitor each instance separately.

## 11. Tuning Purge Configuration

Tune only after confirming old transactions are no longer the root cause and metrics show purge genuinely lacks processing capacity.

### 11.1. Inspecting Current Configuration

~~~sql
SELECT
    @@GLOBAL.innodb_purge_threads AS innodb_purge_threads,
    @@GLOBAL.innodb_max_purge_lag AS innodb_max_purge_lag,
    @@GLOBAL.innodb_max_purge_lag_delay AS innodb_max_purge_lag_delay,
    @@GLOBAL.innodb_purge_batch_size AS innodb_purge_batch_size,
    @@GLOBAL.innodb_undo_log_truncate AS innodb_undo_log_truncate,
    @@GLOBAL.innodb_max_undo_log_size AS innodb_max_undo_log_size;
~~~

Verify that the variables exist and share the same scope/semantics in your MySQL version. Do not copy settings verbatim across versions or onto managed databases with restricted admin privileges.

### 11.2. `innodb_purge_threads`

This variable sets the maximum number of purge threads permitted. Raising it can improve throughput when DML is spread across many tables and purge can parallelize.

Be cautious when:

- DML is concentrated on a single hot table.
- Purge threads compete with application threads for CPU/I/O.
- Storage is already saturated.
- The history list is pinned by an old read view.

Changing thread count cannot free undo still needed by a snapshot. After adjusting, compare HLL drain rate, CPU, I/O, and workload latency.

### 11.3. `innodb_max_purge_lag` and `innodb_max_purge_lag_delay`

**`innodb_max_purge_lag`** sets the desired purge lag threshold. When exceeded, InnoDB introduces delays on `INSERT`, `UPDATE`, and `DELETE` operations to give purge time to catch up. The default value `0` disables purge lag limits and delays under this mechanism.

**`innodb_max_purge_lag_delay`** caps the maximum delay in microseconds. It bounds the delay calculated when the purge lag threshold is exceeded.

This is a DML throttling mechanism when backlogs grow large. It is not a switch for purge to bypass a read view held by an active transaction. Choose thresholds based on transaction size, data characteristics, latency tolerance, and SLAs. A value suited to a small workload may not fit a heavy write workload.

### 11.4. `innodb_purge_batch_size`

This variable controls how many undo log pages purge analyzes/processes in one batch. It is an advanced tuning parameter; most systems do not need to change the default.

Test only with reproducible benchmarks, while monitoring CPU/I/O and knowing purge limits. Do not change multiple purge variables simultaneously, as it becomes difficult to tell which setting caused the difference.

## 12. Undo Tablespaces and Space Reclamation

### 12.1. Purge and Truncation Are Two Different Steps

Purge processes undo logs that are no longer needed and frees rollback segments/pages. Truncating an undo tablespace shrinks the undo tablespace file to return space to the filesystem.

An undo tablespace file can remain large after the history list drops because space is reused internally inside the tablespace. Thus:

- A drop in HLL does not mean the undo file shrinks immediately.
- A large undo file does not prove a transaction is still holding a snapshot.
- Inspect both rollback segment state and truncation behavior.

### 12.2. Automatic Undo Tablespace Truncation

In MySQL 8.4, automatic truncation is controlled by:

- **`innodb_undo_log_truncate`**: enables/disables automatic undo tablespace truncation.
- **`innodb_max_undo_log_size`**: size threshold at which an undo tablespace is marked for truncation.
- **`innodb_purge_rseg_truncate_frequency`**: frequency with which purge checks for undo tablespaces eligible to truncate.

Automatic truncation requires at least two active undo tablespaces. The process marks one tablespace's rollback segments inactive for new transactions, waits for active transactions using them to finish, lets purge free the undo logs, truncates the file, and reactivates the rollback segments.

Truncation can be delayed if transactions are still using rollback segments in that tablespace. Never manually delete or move undo files while MySQL is running.

You can inspect undo files via `INFORMATION_SCHEMA.FILES`:

~~~sql
SELECT
    TABLESPACE_NAME,
    FILE_NAME
FROM information_schema.files
WHERE FILE_TYPE = 'UNDO LOG';
~~~

Check tablespace status:

~~~sql
SELECT
    NAME,
    STATE
FROM information_schema.innodb_tablespaces
WHERE NAME LIKE 'innodb_undo_%';
~~~

Specific names and states depend on version and configuration. Consult documentation for your running version before using `ALTER UNDO TABLESPACE` or `DROP UNDO TABLESPACE`.

### 12.3. Avoid Confusing Undo Tablespaces with Table Data Files

Undo tablespaces hold undo logs. Table tablespace files hold clustered indexes, secondary indexes, and table data. Purge makes data pages reusable, but does not necessarily shrink `.ibd` files on the filesystem.

Reclaiming physical disk space from a table file is a separate tablespace reorganization/rebuild task requiring evaluation of temporary disk space, locking duration, I/O, and production impact. Do not run `OPTIMIZE TABLE` merely because history list length is high.

## 13. Two-Session Hands-On Example

### 13.1. Preparing the Test Table

Perform only in a lab environment:

~~~sql
CREATE TABLE purge_lab (
    id BIGINT NOT NULL PRIMARY KEY,
    status VARCHAR(20) NOT NULL,
    updated_at DATETIME NOT NULL,
    KEY idx_status_updated (status, updated_at)
) ENGINE=InnoDB;

INSERT INTO purge_lab (id, status, updated_at)
VALUES
    (1, 'new', NOW()),
    (2, 'new', NOW()),
    (3, 'new', NOW());
~~~

### 13.2. Session A Holds a Snapshot

~~~sql
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;

START TRANSACTION;

SELECT id, status
FROM purge_lab
ORDER BY id;

-- Keep the transaction open while switching to Session B.
~~~

The first `SELECT` establishes a read view for transaction A.

### 13.3. Session B Updates and Commits

~~~sql
START TRANSACTION;

UPDATE purge_lab
SET status = 'processed',
    updated_at = NOW()
WHERE id IN (1, 2, 3);

COMMIT;
~~~

Session B has committed, yet Session A can still see the old version per its snapshot. The undo generated by `UPDATE` may still be needed for Session A's consistent read.

You can repeat updates in Session B and observe HLL in a suitably loaded lab environment. Do not generate heavy DML loads in production just to test this example.

### 13.4. Releasing the Read View

Return to Session A:

~~~sql
COMMIT;
~~~

When transaction A ends, the read view is released. Purge can process history that is no longer needed. Observe the history list across multiple snapshots to watch the downward trend; do not expect every undo page to vanish in the very same millisecond.

### 13.5. Observing Open Transactions

In another administrative session:

~~~sql
SELECT
    trx_mysql_thread_id,
    trx_started,
    TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS age_seconds,
    trx_isolation_level,
    trx_is_read_only,
    trx_rows_modified,
    trx_query
FROM information_schema.innodb_trx
ORDER BY trx_started;
~~~

Locate Session A's connection, verify its transaction age and isolation level. Then finish with `COMMIT` in Session A and observe HLL afterward.

## 14. Operational Scenarios and Interpretation

### Scenario A: HLL Rises with a `REPEATABLE READ` Transaction in `Sleep`

**Observations**

- HLL climbs steadily.
- `INNODB_TRX` shows a transaction started long ago.
- The corresponding connection has `PROCESSLIST_COMMAND` equal to `Sleep`.
- `trx_query` is `NULL`, `trx_rows_modified` is 0.
- The application may have returned the connection to the pool without committing.

**Analysis**

The transaction may be holding a read view from an earlier `SELECT`. Having no active statement does not mean the snapshot was released.

**Action**

Identify the request/job owning the connection, have the application end the transaction, then monitor HLL and purge. If `KILL CONNECTION` is necessary, verify the connection ID and accept that a write transaction may require rollback.

### Scenario B: HLL Rises Alongside a Large `DELETE` Job

**Observations**

- HLL climbs during a data cleanup job.
- The transaction has very large `trx_rows_modified`.
- Undo tablespace size grows.
- CPU and I/O increase during the batch.

**Analysis**

The job generates undo rapidly, and a large transaction holds its undo until completion. After commit, purge still must process the history, and another old read view could continue pinning that undo.

**Action**

Split `DELETE` into batches, commit between batches, use appropriate indexes, and throttle the rate. Monitor HLL between batches to find a sustainable batch size.

### Scenario C: No Old Transaction Visible, Yet HLL Still Rises

**Observations**

- `INNODB_TRX` shows no clearly old transactions.
- HLL climbs during peak hours.
- DML is high and concentrated on a few tables.
- Storage latency or purge CPU increases.

**Analysis**

Purge may lack throughput relative to history generation speed. Confirm using multiple samples and metrics rather than a single transaction snapshot.

**Action**

Reduce unnecessary DML, batch operations, and check indexes and storage. Then test adjusting `innodb_purge_threads` in a controlled environment while measuring both HLL and application latency.

### Scenario D: HLL Drops, Yet the Undo File Remains Large

**Observations**

- History list returns near baseline.
- No abnormal old transactions remain.
- Undo tablespace files still occupy substantial disk space.

**Analysis**

Purge has processed the history, but returning undo file space to the filesystem is a separate truncation process. Tablespaces may retain space for internal reuse.

**Action**

Check `innodb_undo_log_truncate`, `innodb_max_undo_log_size`, active undo tablespace count, and rollback segment status. Wait for truncation to finish under version rules; never delete files manually.

## 15. Production Monitoring Checklist

- [ ] Collect history list length periodically with timestamps.
- [ ] Track HLL rate of increase/decrease against workload baselines.
- [ ] Alert on abnormally old transactions by application class.
- [ ] Monitor `Sleep` connections that still hold open InnoDB transactions.
- [ ] Record isolation level, `trx_rows_modified`, and `trx_rows_locked`.
- [ ] Track DML throughput and bulk `DELETE`/`UPDATE` jobs.
- [ ] Monitor CPU, I/O latency, and undo tablespace size.
- [ ] Distinguish old read views from insufficient purge throughput.
- [ ] Follow an owner-identification procedure before closing connections.
- [ ] Do not auto-`KILL` based on a single age threshold.
- [ ] Verify rollback completion after aborting a write transaction.
- [ ] Evaluate purge and undo tablespace truncation separately.
- [ ] Re-verify purge settings after MySQL upgrades.
- [ ] Rehearse the runbook in lab or staging environments.

## 17. Completion Criteria

You have completed this lesson when you can explain MVCC, undo logs, read views, and purge; distinguish insert undo from update undo; interpret history list length accurately; find old transactions including `Sleep` connections and read-only transactions; distinguish a transaction pinning a read view from purge lacking throughput; and build an evidence-based, safe remediation approach.
