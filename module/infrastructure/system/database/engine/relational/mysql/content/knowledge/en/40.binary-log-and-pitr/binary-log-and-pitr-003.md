# Row Image, Transaction Events, and Binary Log Volume

The binary log (binlog) records changes that MySQL needs for replication, point-in-time recovery (PITR), and change data capture (CDC) systems. When using row-based logging, MySQL writes row events describing the changed rows. The `binlog_row_image` option determines how many columns of the row before and after the change each event contains.

Binlog volume depends on the number of transactions, the number of affected rows, the size of data recorded in the row image, event overhead, and log retention duration. Large transactions also use a transaction cache before being written to the binlog file. Understanding these components helps choose appropriate settings, forecast capacity, and retain enough logs for both replicas and PITR.

This lesson belongs to the **Binary Log and PITR** chapter of the `DATABASE_MYSQL` module. The module covers table design, SQL, indexes, transactions, privileges, backups, and MySQL operations. The examples below target MySQL 8.0 and later; always verify the documentation for your exact server and client versions before changing production configurations.

After this lesson, you will be able to:

- Distinguish statement-based, row-based, and mixed binary logging.
- Explain `FULL`, `MINIMAL`, and `NOBLOB` in `binlog_row_image`.
- Read the basic structure of a transaction event group.
- Understand the role of the transaction cache and disk cache metrics.
- Estimate, monitor, and control binlog volume.
- Set log retention appropriate for replication and PITR.

## 1. What Does the Binary Log Store?

The binary log is a sequence of files generated by MySQL to record events that modify data or structure. When `log_bin` is enabled, the server writes the required changes into the binlog according to `binlog_format`.

The three primary modes are:

| Mode | Recorded content | Characteristics |
|---|---|---|
| `STATEMENT` | Executed SQL statements | Files can be smaller for a statement affecting many rows, but results depend on statement determinism and the replica environment. |
| `ROW` | Row-level changes | Replicas apply row changes; the row image determines which columns are recorded. |
| `MIXED` | Combination of statement and row events | MySQL selects the logging form per server rules; certain statements switch to row-based to ensure replication safety. |

In modern MySQL systems, `ROW` is the standard choice for replication and CDC. However, you should review replica compatibility, binlog reading tools, and capacity requirements before switching modes.

Checking status:

```sql
SHOW VARIABLES LIKE 'log_bin';
SHOW VARIABLES LIKE 'binlog_format';
SHOW VARIABLES LIKE 'binlog_row_image';
```

`binlog_row_image` affects row events only. If the server logs a statement as a statement event, the row image option does not change the recorded SQL text. With `MIXED`, the row image applies only when an operation is logged as a row event.

## 2. Row Events and Before Image / After Image

In row-based logging, MySQL records information about rows before and after an operation. Two key concepts:

- **Before image**: column values of the row prior to the change. Typically used to identify the row to update or delete.
- **After image**: column values of the row after the change. Used to reconstruct the new state on a replica or CDC consumer.

The operation type determines which images appear:

| Operation | Images typically recorded |
|---|---|
| `INSERT` | After image of the new row. |
| `UPDATE` | Before image and after image. |
| `DELETE` | Before image of the deleted row. |

For example, table `sales.orders` has columns `order_id`, `customer_id`, `status`, `note`, and `total`. A statement changing the status:

```sql
UPDATE sales.orders
SET status = 'shipped'
WHERE order_id = 105;
```

With `FULL`, the row event can contain all column values before and after the update. With `MINIMAL`, the before image may only need the identifying key `order_id`, and the after image may only need the changed `status` value. This is why row image significantly impacts volume when tables have many columns or large fields.

## 3. Three `binlog_row_image` Modes

`binlog_row_image` has three main values: `FULL`, `MINIMAL`, and `NOBLOB`. MySQL's default is `FULL` in commonly used current versions. This option can be set at global or session scope depending on version; always verify the effective value for the connection performing changes.

### 3.1. FULL

`FULL` records all columns in the before image and after image of row events.

```ini
[mysqld]
binlog_format=ROW
binlog_row_image=FULL
```

Advantages:

- Row events carry rich context about the row before and after the change.
- Easier to inspect changes, aiding incident investigation and CDC systems that require old values.
- Less reliance on downstream consumers reconstructing prior values from schemas or previous state.

In return, `FULL` can produce large logs when tables have many columns, multiple `BLOB`/`TEXT` fields, or transactions updating huge numbers of rows. Both old and new values of sensitive data can also appear in the binlog, so log files must be protected just like production data.

### 3.2. MINIMAL

`MINIMAL` records only the columns needed to identify the row in the before image and the required columns in the after image. For `UPDATE`, the after image usually contains only changed columns. For `DELETE`, the before image must suffice to identify the row to delete. For `INSERT`, the after image must suffice to construct the new row per row-event rules.

```ini
[mysqld]
binlog_format=ROW
binlog_row_image=MINIMAL
```

To identify a row, MySQL prioritizes a primary key or suitable unique key. If a table lacks a primary key or unique key capable of uniquely identifying rows, the before image may have to include all columns. Therefore, `MINIMAL` does not guarantee equal volume reduction for every table.

The advantage is reducing redundant data in events, especially on wide tables where each update modifies only a few columns. The drawback is that CDC tools or audit processes might not receive sufficient old values or unchanged columns. Consumers must understand partial row images and merge state properly.

### 3.3. NOBLOB

`NOBLOB` is similar to `FULL`, except it omits `BLOB` and `TEXT` columns that are unnecessary for identifying the row. BLOB/TEXT columns can still be recorded if needed to identify the row or required by the change itself.

```ini
[mysqld]
binlog_format=ROW
binlog_row_image=NOBLOB
```

This mode can reduce volume when tables store documents, images, long text, or large payloads in `BLOB`/`TEXT` columns. However, if a CDC system needs the full values of those fields, omitting them from the row image removes information that the consumer expects.

### 3.4. Quick Comparison

| Criterion | `FULL` | `MINIMAL` | `NOBLOB` |
|---|---|---|---|
| Before image | All columns | Columns needed to identify the row | Nearly all, except unnecessary BLOB/TEXT |
| After image | All columns | Columns needed for the new row or changed columns | Nearly all, except unnecessary BLOB/TEXT |
| Volume | Usually largest | Usually smallest if the table has a suitable key | Can decrease significantly with large columns |
| Analyzing old values | More complete | May lack unchanged columns | May lack BLOB/TEXT |
| CDC | Suits consumers needing full images | Consumers must support partial images | Consumers must tolerate missing unnecessary BLOB/TEXT fields |

No single mode is optimal for every system. Choose based on the requirements of replicas, CDC tools, auditing, incident investigation, and storage budget.

## 4. How Does a Primary Key Affect the Row Image?

Under `MINIMAL`, MySQL needs to identify the exact row before updating or deleting. A primary key is the clearest option. A unique key can also be used if it satisfies unique identification requirements, including having the required columns and disallowing `NULL` values under the applicable rules.

Example table with a primary key:

```sql
CREATE TABLE sales.orders (
  order_id BIGINT NOT NULL PRIMARY KEY,
  customer_id BIGINT NOT NULL,
  status VARCHAR(24) NOT NULL,
  note TEXT,
  total DECIMAL(12,2) NOT NULL
) ENGINE=InnoDB;
```

When updating `status`, the minimal before image may need only `order_id`; the after image may need only `status`. If the table lacks a suitable identifying key, MySQL may have to log many or all columns in the before image so the replica can pinpoint the right row.

A primary key has benefits beyond the binlog: it establishes row identity, supports InnoDB's clustered index, and helps replication/CDC process updates/deletes reliably. When designing schemas, favor a stable, unique primary key that does not need frequent modification.

## 5. Inspecting Row Images with `mysqlbinlog`

`mysqlbinlog` is the tool for reading and decoding binary logs. With row-based logging, use `--base64-output=DECODE-ROWS -vv` to display row events as readable comments.

```bash
mysqlbinlog --base64-output=DECODE-ROWS -vv mysql-bin.000123
```

The output may look like this illustration:

```text
### UPDATE `sales`.`orders`
### WHERE
###   @1=105
### SET
###   @3='shipped'
```

`@1`, `@3` are column positions in the event's table map, not guaranteed column names. Use the corresponding table metadata and schema to interpret them accurately. With `FULL`, many columns may appear in the `WHERE` and `SET` sections; with `MINIMAL`, only the required subset may appear.

Other inspection commands:

```sql
SHOW BINARY LOGS;
SHOW BINLOG EVENTS IN 'mysql-bin.000123' LIMIT 20;
```

`SHOW BINLOG EVENTS` shows event types, start/end positions, and summary info. For row events, `mysqlbinlog -vv` is generally more useful for viewing detailed contents. The decoded output is an interpretive representation for inspection; `###` lines are not directly executable SQL statements.

When reading logs, pay attention to the schema at the time the event was generated. If the table structure changed later, mapping column positions in old row events against the current schema can be incorrect.

## 6. Transaction Event Groups

Events for a transaction are written as a logical group. With InnoDB and row-based logging, a group typically has the general shape:

```text
GTID_LOG_EVENT (if GTID is enabled)
QUERY_EVENT: BEGIN
TABLE_MAP_EVENT
WRITE_ROWS_EVENT / UPDATE_ROWS_EVENT / DELETE_ROWS_EVENT
XID_EVENT (commit)
```

This is an illustrative diagram, not a fixed event list for every version or configuration. Additional events may appear such as metadata, annotations, checksums, or GTID-related events. With statement-based logging, changes are normally recorded via `QUERY_EVENT` containing the SQL statement. DDL is also typically logged as statement events even when `binlog_format=ROW`.

Key events:

- `GTID_LOG_EVENT`: tags the transaction with a GTID when GTID mode applies.
- `QUERY_EVENT`: records SQL statements such as `BEGIN` or DDL; under statement-based logging, can contain data-modifying SQL.
- `TABLE_MAP_EVENT`: maps the table ID in row events to the database, table, and column metadata.
- `WRITE_ROWS_EVENT`: records inserted rows.
- `UPDATE_ROWS_EVENT`: records the before image and after image of updated rows.
- `DELETE_ROWS_EVENT`: records the before image of deleted rows.
- `XID_EVENT`: marks the commit of a transactional transaction, typically InnoDB.

### 6.1. Why Are Transactions Logged in Groups?

For InnoDB transactions, MySQL holds binlog changes in a transaction cache while the transaction is running. On commit, the transaction's events are flushed into the binary log as a group. On rollback, uncommitted transactional changes are not recorded as a committed transaction in the binlog.

Thanks to event groups and commit markers, replicas can apply transactions along commit boundaries. When reading logs for PITR, avoid stopping mid-event-group if the goal is to reconstruct a consistent state. Choose a stop position at an appropriate transaction boundary.

### 6.2. Large Transactions and Non-Transactional Engines

Large InnoDB transactions can generate substantial row-event volume. If a transaction rolls back, its transactional changes do not become a committed transaction in the binlog, yet the cache resources and work consumed during execution can still be significant.

Changes to non-transactional tables such as MyISAM cannot roll back like InnoDB. MySQL uses a statement cache for certain non-transactional changes. When an operation mixes transactional and non-transactional tables, do not assume the entire change is atomic like an InnoDB-only transaction. For systems requiring reliable replication and PITR, prefer transactional engines and avoid mixing engines without a clear reason.

## 7. Transaction Cache and Memory Limits

Before a transaction is written to the binlog file, MySQL uses per-connection in-memory caches. Key variables:

| Variable | Role |
|---|---|
| `binlog_cache_size` | Initial cache size for a transaction's changes. |
| `max_binlog_cache_size` | Upper limit for the transaction cache; transactions exceeding the limit may fail. |
| `binlog_stmt_cache_size` | Cache size for statements needing the statement cache, typically involving non-transactional changes. |
| `max_binlog_stmt_cache_size` | Upper limit for the statement cache. |

When the transaction cache exceeds its allocated memory size, MySQL can spill the overflow to temporary files on disk. This allows large transactions without keeping everything in RAM, at the cost of temporary I/O. Setting `binlog_cache_size` too high can increase memory usage across many concurrent connections; do not raise it merely because you observed one large transaction.

Inspect current variables:

```sql
SHOW VARIABLES LIKE 'binlog_cache_size';
SHOW VARIABLES LIKE 'max_binlog_cache_size';
SHOW VARIABLES LIKE 'binlog_stmt_cache_size';
SHOW VARIABLES LIKE 'max_binlog_stmt_cache_size';
```

Monitor counters:

```sql
SHOW GLOBAL STATUS LIKE 'Binlog_cache_use';
SHOW GLOBAL STATUS LIKE 'Binlog_cache_disk_use';
SHOW GLOBAL STATUS LIKE 'Binlog_stmt_cache_use';
SHOW GLOBAL STATUS LIKE 'Binlog_stmt_cache_disk_use';
```

- `Binlog_cache_use`: number of times the transaction cache was used.
- `Binlog_cache_disk_use`: number of times the transaction cache had to use temporary disk files.
- `Binlog_stmt_cache_use`: number of times the statement cache was used.
- `Binlog_stmt_cache_disk_use`: number of times the statement cache had to use temporary disk files.

Status values are generally cumulative counters since server startup. Compare deltas over a time window alongside transaction counts and actual workload. Occasional disk spills are not automatically an incident; evaluate frequency, latency, and I/O load.

## 8. What Determines Binary Log Volume?

Binlog volume is the sum of changed data and event overhead. Roughly:

\[
\text{Binlog volume} \approx
\text{row images} + \text{event overhead} + \text{transaction metadata}
\]

Key factors:

1. **Number of transactions and affected rows.** A statement updating millions of records can generate huge logs even if the SQL text is very short.
2. **Row size and data types.** `BLOB`, `TEXT`, large JSON, or long string columns can inflate row images substantially.
3. **Row image.** `FULL` generally logs more values than `MINIMAL`; `NOBLOB` can reduce logs when unnecessary BLOB/TEXT fields exist.
4. **Update frequency.** A wide table updated frequently can produce large binlogs even if row count stays flat.
5. **Transaction and metadata overhead.** GTIDs, table maps, row event headers, checksums, and commit markers all add overhead.
6. **Logging style.** Statement-based can be compact for bulk operations, whereas row-based reflects changed row data and is usually more predictable for replication.

Qualitative example: a table has many descriptive columns, a long notes field, and a primary key. If each update only modifies `status`, `FULL` may repeatedly log many unchanged values; `MINIMAL` may need only the identifying key and the new status value. Conversely, if most columns are updated or there is no unique key, the volume reduction will be smaller.

To estimate real volume, measure binlog growth rates during normal and peak load windows. Do not rely solely on schema size or SQL statement counts, because two systems with the same number of statements can generate vastly different row-event volumes.

## 9. File Rotation and Size Limits

`max_binlog_size` sets the target size threshold for each binary log file. When a file reaches the threshold, MySQL rotates to the next file at an appropriate boundary.

```ini
[mysqld]
max_binlog_size=512M
```

The default in many MySQL 8.0 releases is 1 GiB; confirm on your running version. `max_binlog_size` is a rotation threshold, not a hard cap for every file. A transaction is never split across binlog files; if a single transaction exceeds the threshold, the file can grow past `max_binlog_size` before rotating once the transaction finishes.

Avoid setting the file size too small just to create many log files. Too many files increase management and inspection overhead. Also avoid setting it too large if copying, uploading, or archiving workflows need to process each file within a short window. Pick a size aligned with write rate, log transport, and operational handling.

Check existing files:

```sql
SHOW BINARY LOGS;
```

The output lists filenames and sizes. The total size of unexpired files indicates how much disk space binlogs currently occupy on the server.

## 10. Log Retention and Disk Capacity

`binlog_expire_logs_seconds` controls how long MySQL keeps binary logs before automatically deleting expired logs. This is a critical setting for replication and PITR.

```sql
SHOW VARIABLES LIKE 'binlog_expire_logs_seconds';
```

It can be set in the server configuration file:

```ini
[mysqld]
binlog_expire_logs_seconds=1209600
```

The example above sets retention to 14 days. This is an illustrative value only; appropriate retention must be based on backup schedules, recovery time, replica lag, and PITR objectives. Older versions may still support `expire_logs_days`; prefer the recommended setting for your MySQL version and avoid configuring two variables with ambiguous precedence.

### 10.1. Estimating Required Capacity

A practical estimate:

\[
\text{Estimated capacity} \approx
\text{Average daily binlog} \times
\text{Retention days} \times
\text{Safety buffer factor}
\]

For instance, if you measure an average of 18 GiB of binlog per day and need 14 days of retention, the baseline capacity is 252 GiB. Add a safety margin for peak days, large transactions, replica lag, and other files sharing the volume. Measure days with batch jobs, imports, or large migrations as well, since they can drive log growth far above normal days.

Monitor filesystem free space alongside `SHOW BINARY LOGS`. Do not wait until the disk is nearly full to adjust retention; binlogs can grow rapidly during heavy write loads.

### 10.2. Retention Must Satisfy Replication

Replicas need to read binary logs they have not yet received or applied. If the source deletes a file a replica still needs, replication can stop and require resynchronization from a backup or another recovery procedure.

Before reducing retention or purging logs manually, check replica status:

```sql
SHOW REPLICA STATUS\G
```

Check the file/position the replica is currently reading, I/O and SQL thread states, lag, and recent errors. If multiple replicas or replication channels exist, check all relevant consumers.

### 10.3. Retention Must Satisfy PITR

PITR requires a baseline full backup and a continuous binary log sequence from the backup point up to the target recovery time. If a file is missing from the chain, changes after the gap cannot be replayed normally.

Binlog retention should cover at least:

- The interval between full backups.
- Incident detection and investigation time.
- Time needed to download, prepare, and restore the backup.
- The window required to recover back to a pre-incident point.
- A safety margin for replication lag and storage disruptions.

For example, if full backups run weekly but the organization needs the ability to recover to any point within the last 10 days, keeping logs for 7 days is insufficient. Set retention according to actual recovery objectives and verify that backups and all required binlogs have been copied to safe storage.

## 11. Safely Purging Binary Logs

MySQL can automatically remove expired logs based on retention. Administrators can also delete logs manually with `PURGE BINARY LOGS`, but must verify replicas and PITR requirements before doing so.

Delete files older than a specified file:

```sql
PURGE BINARY LOGS TO 'mysql-bin.000250';
```

This command deletes files preceding `mysql-bin.000250`; the named file itself is kept. Or delete files before a timestamp:

```sql
PURGE BINARY LOGS BEFORE '2026-11-01 00:00:00';
```

Never run purge merely to free disk space without knowing whether replicas or PITR plans still need those files. Deleting the wrong logs can force rebuilding replicas or accepting loss of PITR capability across the deleted window.

A purge procedure should include: identifying the oldest file/position still needed by every replica; identifying the earliest PITR anchor still required; confirming associated backups have been verified; selecting a purge boundary after all retained anchors; recording the operation; and re-checking replication afterward.

## 12. Large Transactions, Large Events, and Operations

Large transactions can simultaneously increase binlog volume, transaction cache usage, commit latency, and replication lag. Helpful operational practices include:

- Splitting very large batch updates into smaller transactions when business logic allows.
- Avoiding redundant updates to the exact same value when unnecessary.
- Designing stable primary keys so `MINIMAL` can identify rows efficiently.
- Evaluating large BLOB/TEXT columns and choosing `NOBLOB` only when replicas/CDC do not need those fields.
- Monitoring `Binlog_cache_disk_use` to detect transaction cache spills to disk.
- Ensuring the binlog filesystem has headroom and alerts well before critical thresholds.
- Checking replica apply speed after large batches, imports, or migrations.

`binlog_row_event_max_size` is the target threshold for row event size. A single oversized row can still cause an event to exceed the threshold; this variable does not limit total transaction size or binlog file size. Do not confuse it with `max_binlog_size` or `max_binlog_cache_size`.

## 13. PITR and Transaction Boundaries

When recovering to a specific point in time, the usual process restores a full backup and replays binary logs from the backup anchor up to immediately before the incident-causing operation. With row-based logging, `mysqlbinlog` can decode row events to help pinpoint the transaction and changes where replay should stop.

Example reading logs by time range:

```bash
mysqlbinlog \
  --start-datetime='2026-11-18 09:00:00' \
  --stop-datetime='2026-11-18 10:30:00' \
  mysql-bin.000250 mysql-bin.000251
```

You can use `--start-position` and `--stop-position` once exact event positions are identified. In production recovery, verify transaction boundaries: stopping partway through a transaction's row events can leave an inconsistent state. Determine the stop point at an appropriate commit boundary and test the procedure on a copy before running it on the actual recovery target.

`FULL` makes reading old and new values clearer in many investigations. However, row images do not automatically produce a safe rollback operation. Reversing a transaction requires understanding business logic, dependency order, and side effects outside the database. Never modify original binlog files; work on copies and preserve the intact log chain for recovery.

## 14. Goal-Oriented Configuration Examples

### 14.1. System Prioritizing CDC and Investigation

```ini
[mysqld]
log_bin=mysql-bin
binlog_format=ROW
binlog_row_image=FULL
binlog_expire_logs_seconds=1209600
max_binlog_size=512M
```

This configuration prioritizes full row images so consumers can read old/new values conveniently. In exchange, log volume can be high. Verify whether consumers truly require full images and measure volume before finalizing retention.

### 14.2. Wide-Table Updates with Partial-Image CDC Support

```ini
[mysqld]
log_bin=mysql-bin
binlog_format=ROW
binlog_row_image=MINIMAL
binlog_expire_logs_seconds=1209600
max_binlog_size=512M
```

`MINIMAL` can significantly reduce data volume if tables have suitable unique keys and each update changes only a few columns. Before adopting it, test replicas and CDC consumers with both `UPDATE` and `DELETE`, especially on tables without primary keys.

### 14.3. Runtime Changes and Session Scope

Some variables can be changed dynamically. For example:

```sql
SET GLOBAL binlog_row_image = 'MINIMAL';
```

The global value typically acts as the default for new connections; existing sessions may retain their own session values. If the application uses a connection pool, check the value in sessions actually performing DML. Set it in the server configuration file or an appropriate persistence mechanism so the value survives restarts.

Do not change row image or binlog format mid-stream without testing all replicas, CDC, backup tools, and audit processes. Configuration changes can alter the shape of events received by consumers.

## 15. Binary Log Monitoring Checklist

The following commands provide an initial view of log and cache status:

```sql
-- Files and sizes
SHOW BINARY LOGS;

-- Relevant configuration
SHOW VARIABLES LIKE 'log_bin';
SHOW VARIABLES LIKE 'binlog_format';
SHOW VARIABLES LIKE 'binlog_row_image';
SHOW VARIABLES LIKE 'max_binlog_size';
SHOW VARIABLES LIKE 'binlog_expire_logs_seconds';

-- Transaction and statement caches
SHOW GLOBAL STATUS LIKE 'Binlog_cache_use';
SHOW GLOBAL STATUS LIKE 'Binlog_cache_disk_use';
SHOW GLOBAL STATUS LIKE 'Binlog_stmt_cache_use';
SHOW GLOBAL STATUS LIKE 'Binlog_stmt_cache_disk_use';

-- Replica status on a replica server
SHOW REPLICA STATUS\G
```

When building dashboards or alerts, track:

| Metric | Operational question |
|---|---|
| Total binlog size | Is log growth exceeding forecasts or volume capacity? |
| New log size per minute/hour | Is an unusual batch or transaction causing a log spike? |
| Age of the oldest log file | How much of the PITR window remains guaranteed? |
| Replica lag and file/position | Can replicas read logs before they expire? |
| `Binlog_cache_disk_use` | Are transactions frequently spilling cache to disk? |
| Log write errors and filesystem space | Is the server at risk of failing to write binlogs or halting writes? |

Set alerts on both absolute space used and growth rate. A volume with plenty of free space can still fill quickly if an import job produces abnormally large binlogs.

### Exercise 1: Comparing Row Images

In a test environment, create a table with a primary key, multiple columns, and a `TEXT` column. Enable row-based logging and run the same `UPDATE` under `FULL`, `MINIMAL`, and `NOBLOB` settings.

```sql
CREATE TABLE lab_orders (
  order_id BIGINT NOT NULL PRIMARY KEY,
  customer_id BIGINT NOT NULL,
  status VARCHAR(24) NOT NULL,
  note TEXT,
  total DECIMAL(12,2) NOT NULL
) ENGINE=InnoDB;

INSERT INTO lab_orders
  (order_id, customer_id, status, note, total)
VALUES
  (1, 1001, 'new', REPEAT('x', 10000), 125.00);

UPDATE lab_orders
SET status = 'shipped'
WHERE order_id = 1;
```

Inspect the binlog with `mysqlbinlog --base64-output=DECODE-ROWS -vv`. Record which columns appear in the before/after images and compare file sizes. Repeat with a table lacking a primary key to observe the difference in the before image.

Open a transaction, update two tables, and commit:

```sql
START TRANSACTION;
UPDATE sales.orders
SET status = 'processing'
WHERE order_id = 105;

UPDATE sales.order_items
SET quantity = quantity + 1
WHERE order_id = 105 AND product_id = 7;
COMMIT;
```

Use `SHOW BINLOG EVENTS` or `mysqlbinlog -vv` to locate the GTID, `BEGIN`, table maps, row events, and commit marker. Then run a similar transaction with `ROLLBACK` and compare the binlog contents.

### Exercise 3: Monitoring the Transaction Cache

Create a transaction updating many rows in a test environment. Record `Binlog_cache_use` and `Binlog_cache_disk_use` before and after. Increase the transaction volume to observe when the cache spills to temporary files. Do not use production to generate large transactions solely for testing.

Determine that retention must exceed the 7-day PITR window and include a safety margin for recovery time, replica lag, and operational disruptions. Measure average daily binlog output, calculate required storage capacity, and define volume alert thresholds.

## 17. Common Errors and Troubleshooting

| Symptom | Possible cause | What to check |
|---|---|---|
| Binlog grows rapidly after switching to `ROW` | Many rows updated or large row images | Check write rate, table types, `binlog_row_image`, and batch jobs. |
| `MINIMAL` does not reduce volume much | Table lacks a suitable primary/unique key or many columns change | Inspect schema and actual row events with `mysqlbinlog -vv`. |
| CDC misses old values | Consumer is reading partial images | Check `binlog_row_image`, connector settings, and old/new data requirements. |
| Binlog file exceeds `max_binlog_size` | A single transaction is larger than the threshold | Check large transactions; remember transactions are not split across files. |
| `Binlog_cache_disk_use` increases | Transaction cache exceeds memory buffer and spills to disk | Check transaction size, I/O, and cache; tune only after measuring. |
| Replica stops due to missing binlog | Needed file was purged or expired | Compare replica file/position against log list; may need to rebuild replica. |
| Cannot PITR to target point | Missing file in binlog chain or retention too short | Check full backup, stored log sequence, and archiving workflow. |
| Disk full despite per-file limit | `max_binlog_size` only controls individual file size, not total logs | Check retention, total size, growth rate, and purge policy. |

## 18. Workflow for Selecting Row Image and Managing Volume

1. **Identify consumers.** List replicas, CDC, auditing, backup tools, and investigation needs that read the binlog.
2. **Inventory schemas.** Identify tables with primary/unique keys, large columns, and update frequencies.
3. **Select the row image.** Use `FULL` if full images are needed; consider `MINIMAL` if consumers support partial images; use `NOBLOB` when BLOB/TEXT fields are unnecessary.
4. **Measure real data.** Compare binlog growth rates under normal and peak load before rolling out broadly.
5. **Configure caches sensibly.** Monitor cache spills, transaction sizes, and I/O before tuning cache variables.
6. **Configure file rotation and retention.** Choose `max_binlog_size`, `binlog_expire_logs_seconds`, and volume capacity based on write rate and PITR requirements.
7. **Protect the log chain.** Archive logs to appropriate storage, verify continuity, and restrict access permissions.
8. **Test recovery.** Restore a full backup and replay logs to a test target point; verify results and recovery duration.

The binary log is part of data recovery architecture. The row image determines change granularity, transaction event groups define commit boundaries, and cache and retention determine how long the server can write and keep logs. Configure these three aspects based on replication, CDC, PITR requirements, and real workload metrics; then verify by reading logs and running periodic recovery drills.
