# GROUPING, GROUPING_ID, and Distinguishing Summary Rows from Data NULLs in Oracle

When building summary reports, Oracle can generate additional subtotal and grand total rows using GROUP BY extensions such as ROLLUP, CUBE, and GROUPING SETS. In these summary rows, any dimension excluded from the grouping level is displayed as NULL. However, source data itself can also contain real NULLs, such as a transaction with an unknown region or an uncategorized product.

Therefore, seeing NULL in an output column is not enough to conclude whether it means "unknown data" or "all values." Oracle provides two functions to tell them apart:

- GROUPING(expression) indicates whether NULL in a grouping expression was generated by Oracle during aggregation.
- GROUPING_ID(expression, ...) encodes the GROUPING status of multiple expressions into a single integer, making it easy to identify the aggregation level.

This lesson explains how both functions work, how to read the GROUPING_ID bitmask, how to assign labels with CASE, how to filter summary rows with HAVING, and how to organize output for reports. The examples use a small sales table that includes real NULLs in the source data.

## 1. The problem: data NULLs vs. aggregation NULLs

Suppose you have a SALES table with columns REGION, PRODUCT, and AMOUNT. Some source rows may be missing a region or product name:

| REGION | PRODUCT | AMOUNT |
|---|---|---:|
| North | Laptop | 100 |
| North | Phone | 50 |
| South | Laptop | 80 |
| NULL | Laptop | 30 |
| North | NULL | 20 |

In this table:

- The NULL REGION in the fourth row is source data: the transaction has revenue, but the region is unknown or unrecorded.
- The NULL PRODUCT in the fifth row is source data: the item has not been identified.

Now generate a summary report:

~~~sql
SELECT region,
       product,
       SUM(amount) AS total_amount
FROM sales
GROUP BY ROLLUP(region, product);
~~~

ROLLUP produces multiple grouping levels, including detail groups by REGION and PRODUCT, subtotals by REGION, and the grand total. Oracle places NULL in any column omitted from the grouping level. The output can contain rows like:

| REGION | PRODUCT | TOTAL_AMOUNT | Meaning |
|---|---|---:|---|
| NULL | Laptop | 30 | Detail row, NULL REGION in source data |
| North | NULL | 20 | Detail row, NULL PRODUCT in source data |
| North | NULL | 170 | Subtotal for North, PRODUCT aggregated away |
| South | NULL | 80 | Subtotal for South, PRODUCT aggregated away |
| NULL | NULL | 30 | Subtotal for NULL REGION, PRODUCT aggregated away |
| NULL | NULL | 280 | Grand total, both dimensions aggregated away |

Two pairs of NULL values reveal the problem:

- North / NULL / 20 is a detail row whose PRODUCT is genuinely NULL.
- North / NULL / 170 is North's subtotal, where PRODUCT was dropped from the grouping level.
- NULL / NULL / 30 is the subtotal for the unknown region.
- NULL / NULL / 280 is the grand total.

Relying solely on REGION and PRODUCT, an application cannot reliably tell these rows apart. If you display every NULL as "All," the report turns unknown data into an aggregate. If you display every NULL as "Unknown," the grand total and subtotals are mislabeled.

This is the exact purpose of GROUPING and GROUPING_ID.

## 2. GROUPING: determining whether NULL comes from aggregation

### 2.1 Syntax

~~~sql
GROUPING(expression)
~~~

GROUPING takes an expression from the extended GROUP BY list and returns:

- 0 if the expression's value in the result row is an ordinary grouping value, including a real NULL present in the source data.
- 1 if Oracle generated NULL for that expression because it was omitted from the current grouping level in ROLLUP, CUBE, or GROUPING SETS.

GROUPING returns NUMBER 0 or 1. It does not alter column values; it provides metadata about the origin of NULL in summary rows.

### 2.2 Example with ROLLUP

~~~sql
SELECT region,
       product,
       SUM(amount) AS total_amount,
       GROUPING(region) AS g_region,
       GROUPING(product) AS g_product
FROM sales
GROUP BY ROLLUP(region, product)
ORDER BY GROUPING_ID(region, product), region, product;
~~~

Reading the two GROUPING columns:

| G_REGION | G_PRODUCT | Meaning |
|---:|---:|---|
| 0 | 0 | Detail row; both REGION and PRODUCT are grouping values, possibly real NULLs |
| 0 | 1 | REGION remains a grouping dimension; PRODUCT was aggregated to NULL |
| 1 | 1 | Both REGION and PRODUCT were aggregated; this is the grand total |

With ROLLUP(region, product), there is no grouping level by PRODUCT alone, so the 1 / 0 state is not generated by this ROLLUP structure.

Key point: GROUPING(region) does not ask "Is REGION NULL?". It asks "Was the NULL in REGION generated by the aggregation operation?".

### 2.3 Source NULLs return GROUPING equal to 0

A detail row with a NULL REGION in the source table still belongs to the detail group by REGION and PRODUCT. Therefore:

~~~sql
GROUPING(region) = 0
~~~

When Oracle generates a subtotal by dropping REGION from the grouping set, GROUPING(region) returns 1. Both rows display NULL, yet their GROUPING flags differ.

### 2.4 Using GROUPING to assign labels

You can combine it with CASE:

~~~sql
SELECT CASE
         WHEN GROUPING(region) = 1 THEN 'ALL REGIONS'
         WHEN region IS NULL THEN 'UNKNOWN REGION'
         ELSE region
       END AS region_label,
       CASE
         WHEN GROUPING(product) = 1 THEN 'ALL PRODUCTS'
         WHEN product IS NULL THEN 'UNKNOWN PRODUCT'
         ELSE product
       END AS product_label,
       SUM(amount) AS total_amount
FROM sales
GROUP BY ROLLUP(region, product)
ORDER BY GROUPING_ID(region, product), region, product;
~~~

The WHEN order is intentional:

1. Check GROUPING first to catch NULLs caused by aggregation.
2. Only when GROUPING equals 0, check whether the source value is genuinely NULL.
3. Otherwise, display the dimension value.

If you reverse the two conditions, subtotal rows containing NULL would also be mislabeled as "UNKNOWN REGION" or "UNKNOWN PRODUCT."

In a multilingual report, you can localize the labels (for example, into Vietnamese):

~~~sql
CASE
  WHEN GROUPING(region) = 1 THEN 'Tất cả khu vực'
  WHEN region IS NULL THEN 'Chưa xác định khu vực'
  ELSE region
END
~~~

Display labels do not modify the original NULLs in the table, nor do they write summary data back to the source table.

## 3. GROUPING_ID: encoding multiple GROUPING flags

### 3.1 Syntax and meaning

~~~sql
GROUPING_ID(expr [, expr] ...)
~~~

GROUPING_ID accepts one or more grouping expressions and returns an integer representing the vector of corresponding GROUPING values. You can think of it as a bitmask:

- Bit 0 corresponds to the last expression in the argument list.
- Earlier expressions carry higher bit weights.
- GROUPING equal to 1 means that dimension is aggregated out at the current grouping level.
- GROUPING equal to 0 means that dimension still participates in the current grouping level.

With two expressions:

~~~sql
GROUPING_ID(region, product)
~~~

bit states are interpreted in the order REGION then PRODUCT:

| GROUPING(region) | GROUPING(product) | Bit vector | GROUPING_ID(region, product) |
|---:|---:|---|---:|
| 0 | 0 | 00 | 0 |
| 0 | 1 | 01 | 1 |
| 1 | 0 | 10 | 2 |
| 1 | 1 | 11 | 3 |

With ROLLUP(region, product), the generated grouping levels are:

- (region, product): GROUPING_ID equals 0.
- (region): GROUPING_ID equals 1.
- (): GROUPING_ID equals 3.

The value 2 does not appear in this ROLLUP because there is no grouping set consisting solely of PRODUCT.

### 3.2 ROLLUP example with GROUPING_ID

~~~sql
SELECT region,
       product,
       SUM(amount) AS total_amount,
       GROUPING(region) AS g_region,
       GROUPING(product) AS g_product,
       GROUPING_ID(region, product) AS grouping_level
FROM sales
GROUP BY ROLLUP(region, product)
ORDER BY grouping_level, region, product;
~~~

GROUPING_ID gives the report a single grouping-level code column:

| GROUPING_LEVEL | Grouping level in ROLLUP(region, product) |
|---:|---|
| 0 | Detail by region and product |
| 1 | Subtotal by region |
| 3 | Grand total |

Multiple rows can share the same GROUPING_ID. For example, every REGION/PRODUCT combination at the detail level has ID 0. Thus GROUPING_ID is an **aggregation-level code**, not a unique row key.

### 3.3 Argument order affects the value

These two expressions do not necessarily produce the same code:

~~~sql
GROUPING_ID(region, product)
GROUPING_ID(product, region)
~~~

When GROUPING(region)=1 and GROUPING(product)=0:

- GROUPING_ID(region, product) has vector 10, value 2.
- GROUPING_ID(product, region) has vector 01, value 1.

Consequently, argument order is part of the reporting contract. Whenever you persist aggregation-level codes, document the expression order so application code does not misinterpret them.

### 3.4 GROUPING_ID for three dimensions

With REGION, PRODUCT, and CHANNEL:

~~~sql
GROUPING_ID(region, product, channel)
~~~

there are three bits, so states can range from 0 to 7:

| GROUPING(region) | GROUPING(product) | GROUPING(channel) | Vector | GROUPING_ID |
|---:|---:|---:|---|---:|
| 0 | 0 | 0 | 000 | 0 |
| 0 | 0 | 1 | 001 | 1 |
| 0 | 1 | 0 | 010 | 2 |
| 0 | 1 | 1 | 011 | 3 |
| 1 | 0 | 0 | 100 | 4 |
| 1 | 0 | 1 | 101 | 5 |
| 1 | 1 | 0 | 110 | 6 |
| 1 | 1 | 1 | 111 | 7 |

Not every extended GROUP BY generates all eight states. The actual grouping sets determine which levels appear; the table above describes the encoding capacity of three flags.

### 3.5 Labeling report levels with GROUPING_ID

With a two-dimensional ROLLUP:

~~~sql
SELECT region,
       product,
       SUM(amount) AS total_amount,
       GROUPING_ID(region, product) AS gid,
       CASE GROUPING_ID(region, product)
         WHEN 0 THEN 'DETAIL'
         WHEN 1 THEN 'REGION SUBTOTAL'
         WHEN 3 THEN 'GRAND TOTAL'
         ELSE 'OTHER GROUPING LEVEL'
       END AS row_type
FROM sales
GROUP BY ROLLUP(region, product)
ORDER BY gid, region, product;
~~~

With a two-dimensional CUBE, code 2 can also appear:

- 0: detail REGION + PRODUCT.
- 1: subtotal by REGION.
- 2: subtotal by PRODUCT.
- 3: grand total.

Do not reuse a ROLLUP CASE that omits code 2 for a CUBE if the query might switch from ROLLUP to CUBE.

## 4. Which grouping levels do ROLLUP, CUBE, and GROUPING SETS create?

GROUPING and GROUPING_ID are commonly used alongside GROUP BY extensions. To read results accurately, you need to understand where grouping sets come from.

### 4.1 GROUP BY ROLLUP

~~~sql
GROUP BY ROLLUP(region, product)
~~~

Generates the equivalent grouping sets:

~~~sql
GROUP BY GROUPING SETS (
    (region, product),
    (region),
    ()
)
~~~

This is an aggregation chain from detail to grand total:

~~~text
(REGION, PRODUCT)  detail
        |
        v
(REGION)           subtotal by region
        |
        v
()                 grand total
~~~

With three dimensions:

~~~sql
GROUP BY ROLLUP(region, product, channel)
~~~

the levels are (region, product, channel), (region, product), (region), and (). ROLLUP progressively drops expressions from right to left.

### 4.2 GROUP BY CUBE

~~~sql
GROUP BY CUBE(region, product)
~~~

Generates every grouping set combination:

~~~sql
GROUP BY GROUPING SETS (
    (region, product),
    (region),
    (product),
    ()
)
~~~

With two dimensions, CUBE has four levels:

| Grouping set | GROUPING(region) | GROUPING(product) | GROUPING_ID(region, product) |
|---|---:|---:|---:|
| (region, product) | 0 | 0 | 0 |
| (region) | 0 | 1 | 1 |
| (product) | 1 | 0 | 2 |
| () | 1 | 1 | 3 |

CUBE is useful when a report needs subtotals along every dimension as well as the grand total. The number of grouping sets grows exponentially with the number of dimensions: with n expressions, CUBE can generate 2^n grouping sets. Therefore, consider both dimensionality and data volume.

### 4.3 GROUP BY GROUPING SETS

GROUPING SETS lets you specify the exact grouping levels required:

~~~sql
SELECT region,
       product,
       SUM(amount) AS total_amount,
       GROUPING_ID(region, product) AS gid
FROM sales
GROUP BY GROUPING SETS (
    (region, product),
    (region),
    ()
);
~~~

This query generates detail, subtotal by REGION, and grand total, matching the levels of a two-dimensional ROLLUP. To get subtotals by PRODUCT instead of REGION:

~~~sql
GROUP BY GROUPING SETS (
    (region, product),
    (product),
    ()
)
~~~

GROUPING_ID still distinguishes the grouping level, though its code depends on the argument order of GROUPING_ID itself, not the order of result rows.

### 4.4 Why is GROUPING_ID needed with many grouping sets?

When a report has many dimensions, inspecting individual NULL columns makes identifying the grouping level error-prone. GROUPING_ID compresses multiple dimension states into a single code that can be used to:

- Label row levels.
- Select formatting or styling for subtotals and grand totals at the reporting layer.
- Filter a specific aggregation level in HAVING.
- Sort grouping levels by an explicit rule.
- Pass grouping-level metadata to an application without inferring it from NULLs.

It does not replace dimension columns, nor does it replace the grouping key of detail rows.

## 5. Distinguishing source NULLs from aggregation NULLs with a complete example

### 5.1 Creating the demonstration table

In a dedicated lab schema, create the table:

~~~sql
CREATE TABLE lab_sales_grouping (
    sale_id  NUMBER PRIMARY KEY,
    region   VARCHAR2(30),
    product  VARCHAR2(30),
    amount   NUMBER(12,2) NOT NULL
);
~~~

Load data:

~~~sql
INSERT INTO lab_sales_grouping VALUES (1, 'North', 'Laptop', 100);
INSERT INTO lab_sales_grouping VALUES (2, 'North', 'Phone', 50);
INSERT INTO lab_sales_grouping VALUES (3, 'South', 'Laptop', 80);
INSERT INTO lab_sales_grouping VALUES (4, NULL, 'Laptop', 30);
INSERT INTO lab_sales_grouping VALUES (5, 'North', NULL, 20);
COMMIT;
~~~

Two source NULLs are intentionally included:

- SALE_ID 4 has a NULL REGION.
- SALE_ID 5 has a NULL PRODUCT.

### 5.2 ROLLUP query with both GROUPING and GROUPING_ID

~~~sql
SELECT region,
       product,
       SUM(amount) AS total_amount,
       GROUPING(region) AS g_region,
       GROUPING(product) AS g_product,
       GROUPING_ID(region, product) AS gid
FROM lab_sales_grouping
GROUP BY ROLLUP(region, product)
ORDER BY gid, region, product;
~~~

Result in terms of groups (exact row order is determined by ORDER BY):

| REGION | PRODUCT | TOTAL_AMOUNT | G_REGION | G_PRODUCT | GID | Explanation |
|---|---|---:|---:|---:|---:|---|
| NULL | Laptop | 30 | 0 | 0 | 0 | Detail, source region NULL |
| North | NULL | 20 | 0 | 0 | 0 | Detail, source product NULL |
| North | Laptop | 100 | 0 | 0 | 0 | Detail |
| North | Phone | 50 | 0 | 0 | 0 | Detail |
| South | Laptop | 80 | 0 | 0 | 0 | Detail |
| NULL | NULL | 30 | 0 | 1 | 1 | Subtotal of source NULL REGION group |
| North | NULL | 170 | 0 | 1 | 1 | Subtotal of North |
| South | NULL | 80 | 0 | 1 | 1 | Subtotal of South |
| NULL | NULL | 280 | 1 | 1 | 3 | Grand total |

The two NULL / NULL rows are distinguished by GID and the flags:

- NULL region subtotal: G_REGION=0, G_PRODUCT=1, GID=1.
- Grand total: G_REGION=1, G_PRODUCT=1, GID=3.

The two North / NULL rows can also be distinguished:

- Detail row with source NULL PRODUCT: G_PRODUCT=0, GID=0.
- North subtotal: G_PRODUCT=1, GID=1.

This is why you should never write reports that rely solely on REGION IS NULL or PRODUCT IS NULL to guess summary rows.

### 5.3 Unambiguous labeling

~~~sql
SELECT CASE
         WHEN GROUPING(region) = 1 THEN 'ALL REGIONS'
         WHEN region IS NULL THEN 'UNKNOWN REGION'
         ELSE region
       END AS region_label,
       CASE
         WHEN GROUPING(product) = 1 THEN 'ALL PRODUCTS'
         WHEN product IS NULL THEN 'UNKNOWN PRODUCT'
         ELSE product
       END AS product_label,
       SUM(amount) AS total_amount,
       GROUPING_ID(region, product) AS gid
FROM lab_sales_grouping
GROUP BY ROLLUP(region, product)
ORDER BY gid, region, product;
~~~

Displayed result:

| REGION_LABEL | PRODUCT_LABEL | TOTAL_AMOUNT | GID |
|---|---|---:|---:|
| UNKNOWN REGION | Laptop | 30 | 0 |
| North | UNKNOWN PRODUCT | 20 | 0 |
| North | Laptop | 100 | 0 |
| North | Phone | 50 | 0 |
| South | Laptop | 80 | 0 |
| UNKNOWN REGION | ALL PRODUCTS | 30 | 1 |
| North | ALL PRODUCTS | 170 | 1 |
| South | ALL PRODUCTS | 80 | 1 |
| ALL REGIONS | ALL PRODUCTS | 280 | 3 |

UNKNOWN labels appear only for source NULLs. ALL labels appear only when GROUPING confirms the dimension was rolled up.

### 5.4 Why not use NVL to tell them apart?

A common attempt:

~~~sql
NVL(region, 'ALL REGIONS')
~~~

is not accurate. It turns both source NULLs and subtotal NULLs into the same string. To assign labels properly, check GROUPING first:

~~~sql
CASE
  WHEN GROUPING(region) = 1 THEN 'ALL REGIONS'
  WHEN region IS NULL THEN 'UNKNOWN REGION'
  ELSE region
END
~~~

NVL remains useful for source NULLs when business rules want a fallback value, but it is not a tool for identifying the origin of NULLs generated by ROLLUP/CUBE.

## 6. GROUPING_ID with CUBE

### 6.1 CUBE query

~~~sql
SELECT region,
       product,
       SUM(amount) AS total_amount,
       GROUPING(region) AS g_region,
       GROUPING(product) AS g_product,
       GROUPING_ID(region, product) AS gid
FROM lab_sales_grouping
GROUP BY CUBE(region, product)
ORDER BY gid, region, product;
~~~

With CUBE(region, product), in addition to detail groups, Oracle generates:

- Subtotals by REGION (PRODUCT aggregated away), GID 1.
- Subtotals by PRODUCT (REGION aggregated away), GID 2.
- Grand total, GID 3.

For instance, PRODUCT subtotal rows have NULL REGION and GROUPING(region)=1, while PRODUCT remains a grouping value with GROUPING(product)=0. If a source PRODUCT is NULL, it still has GROUPING(product)=0.

### 6.2 Labeling four levels

~~~sql
SELECT region,
       product,
       SUM(amount) AS total_amount,
       CASE GROUPING_ID(region, product)
         WHEN 0 THEN 'DETAIL'
         WHEN 1 THEN 'REGION SUBTOTAL'
         WHEN 2 THEN 'PRODUCT SUBTOTAL'
         WHEN 3 THEN 'GRAND TOTAL'
       END AS grouping_level
FROM lab_sales_grouping
GROUP BY CUBE(region, product)
ORDER BY GROUPING_ID(region, product), region, product;
~~~

This CASE matches a two-dimensional CUBE. If switched to ROLLUP, code 2 does not occur; if the dimension list or argument order changes, the code mapping must be updated.

### 6.3 CUBE can significantly increase row count

With n dimensions, CUBE can create 2^n grouping sets. For example, 5 dimensions yield 32 grouping sets, and 8 dimensions yield 256. Actual result row count also depends on the value combinations at each level, so the number of groups to aggregate can grow substantially.

Only use CUBE when the report genuinely needs all those subtotal combinations. If only a few specific levels are needed, GROUPING SETS can be clearer and more economical.

## 7. GROUPING SETS and level encoding

### 7.1 Requesting only the needed levels

~~~sql
SELECT region,
       product,
       SUM(amount) AS total_amount,
       GROUPING(region) AS g_region,
       GROUPING(product) AS g_product,
       GROUPING_ID(region, product) AS gid
FROM lab_sales_grouping
GROUP BY GROUPING SETS (
    (region, product),
    (region),
    ()
)
ORDER BY gid, region, product;
~~~

The codes match a two-dimensional ROLLUP: 0, 1, and 3. However, GROUPING SETS lets you specify exact grouping sets without forcing ROLLUP's prefix sequence.

For example, needing only detail and subtotals by PRODUCT without REGION subtotals:

~~~sql
GROUP BY GROUPING SETS (
    (region, product),
    (product),
    ()
)
~~~

GROUPING_ID still distinguishes the grouping levels, but the code depends on the argument order of GROUPING_ID itself, not the order of result rows.

### 7.2 GROUPING_ID for custom grouping levels

Suppose a query has dimensions REGION, PRODUCT, and CHANNEL:

~~~sql
SELECT region,
       product,
       channel,
       SUM(amount) AS total_amount,
       GROUPING_ID(region, product, channel) AS gid
FROM sales_by_channel
GROUP BY GROUPING SETS (
    (region, product, channel),
    (region, product),
    (region),
    (channel),
    ()
);
~~~

GROUPING_ID encodes the flags of all three expressions, even though the grouping sets do not include every combination. When writing a CASE for gid, list the exact grouping sets the query actually produces.

### 7.3 Avoiding unnecessary repeated grouping sets

If GROUPING SETS specifies the same grouping set multiple times, the result can contain duplicate groups with respect to the grouping structure. When you need to handle repeated grouping sets, understand the requirement and group-distinguishing mechanisms clearly. GROUPING_ID only encodes the grouping status of expressions; it is not a unique identifier per result record and does not replace mechanisms for handling duplicate groups.

## 8. Filtering and sorting by aggregation level

### 8.1 HAVING to keep subtotals or the grand total

GROUPING can be used in HAVING to select grouping levels:

~~~sql
SELECT region,
       product,
       SUM(amount) AS total_amount
FROM lab_sales_grouping
GROUP BY ROLLUP(region, product)
HAVING GROUPING(product) = 1;
~~~

This condition retains rows where PRODUCT was aggregated away—that is, subtotals by REGION and the grand total in a two-dimensional ROLLUP. It does not retain detail rows merely because the source PRODUCT is NULL, since GROUPING(product) is 0 on those rows.

Retrieving only the grand total:

~~~sql
SELECT region,
       product,
       SUM(amount) AS total_amount
FROM lab_sales_grouping
GROUP BY ROLLUP(region, product)
HAVING GROUPING_ID(region, product) = 3;
~~~

Retrieving only detail rows:

~~~sql
HAVING GROUPING_ID(region, product) = 0
~~~

### 8.2 Filtering a specific subtotal level

With CUBE:

~~~sql
SELECT region,
       product,
       SUM(amount) AS total_amount
FROM lab_sales_grouping
GROUP BY CUBE(region, product)
HAVING GROUPING_ID(region, product) = 2;
~~~

GID 2 corresponds to GROUPING(region)=1 and GROUPING(product)=0—that is, totals by PRODUCT without breaking down by REGION.

### 8.3 ORDER BY using GROUPING_ID

~~~sql
SELECT region,
       product,
       SUM(amount) AS total_amount,
       GROUPING_ID(region, product) AS gid
FROM lab_sales_grouping
GROUP BY ROLLUP(region, product)
ORDER BY gid, region, product;
~~~

Sorting by gid groups detail rows (0), subtotals (1), and the grand total (3) into blocks. Within each level, region/product continue to be sorted. Exact NULL placement depends on NULLS FIRST/LAST and ORDER BY rules; you can specify it explicitly:

~~~sql
ORDER BY gid,
         region NULLS LAST,
         product NULLS LAST;
~~~

ORDER BY is required to sort results. Never rely on incidental order returned by GROUP BY or an execution plan.

### 8.4 Filtering in WHERE vs. filtering grouping levels in HAVING

WHERE filters source rows before aggregation:

~~~sql
WHERE amount > 0
~~~

HAVING filters groups after aggregation and can reference GROUPING:

~~~sql
HAVING GROUPING_ID(region, product) IN (0, 3)
~~~

If you want to exclude REGION subtotals while keeping detail rows and the grand total, HAVING is appropriate. You cannot use WHERE to inspect GROUPING of summary rows before those rows are even generated.

## 9. GROUPING and GROUPING_ID are not counting functions

### 9.1 GROUPING does not count NULLs

GROUPING(region) returns 0 or 1 depending on whether REGION was aggregated out of the grouping set. It does not return the count of source NULLs, does not count rows, and does not test whether a column is NULL.

To count source NULLs in the base table, use:

~~~sql
SELECT COUNT(*) AS total_rows,
       COUNT(region) AS known_region_rows,
       COUNT(*) - COUNT(region) AS null_region_rows
FROM lab_sales_grouping;
~~~

This queries source data without subtotals. COUNT(region) skips NULL, while COUNT(*) counts every row.

### 9.2 GROUPING_ID is not a row key

For example, many detail combinations all have GID 0. Therefore, you cannot use GROUPING_ID alone as a primary key or unique identifier for result rows.

To uniquely identify a report row, combine:

- Dimension values.
- GROUPING_ID or GROUPING flags.
- Optionally a grouping/source key if the report requires detail-level identification.

### 9.3 GROUPING_ID is not GROUP_ID

Oracle also provides the GROUP_ID function in extended GROUP BY contexts. GROUP_ID and GROUPING_ID are two different functions:

- GROUPING_ID encodes the aggregation state of grouping expressions.
- GROUP_ID distinguishes duplicate groups produced by repeated grouping sets.

Do not swap them. In ordinary reports that need to distinguish source NULLs from subtotals, GROUPING/GROUPING_ID are the appropriate functions.

## 10. Combining with multiple dimensions and grouping expressions

### 10.1 Three dimensions

Example table with REGION, PRODUCT, and CHANNEL:

~~~sql
SELECT region,
       product,
       channel,
       SUM(amount) AS total_amount,
       GROUPING(region) AS g_region,
       GROUPING(product) AS g_product,
       GROUPING(channel) AS g_channel,
       GROUPING_ID(region, product, channel) AS gid
FROM sales_by_channel
GROUP BY ROLLUP(region, product, channel)
ORDER BY gid, region, product, channel;
~~~

ROLLUP produces these levels:

1. Detail by REGION, PRODUCT, CHANNEL: GID 0.
2. Subtotal by REGION, PRODUCT: CHANNEL aggregated away, GID 1.
3. Subtotal by REGION: PRODUCT and CHANNEL aggregated away, GID 3.
4. Grand total: all three aggregated away, GID 7.

### 10.2 Grouping expressions

If GROUP BY uses an expression, GROUPING/GROUPING_ID must reference that matching grouping expression:

~~~sql
SELECT TRUNC(sold_at, 'MM') AS sales_month,
       region,
       SUM(amount) AS total_amount,
       GROUPING(TRUNC(sold_at, 'MM')) AS g_month,
       GROUPING(region) AS g_region,
       GROUPING_ID(TRUNC(sold_at, 'MM'), region) AS gid
FROM sales
GROUP BY ROLLUP(TRUNC(sold_at, 'MM'), region);
~~~

Here the time dimension is the month-start expression, not the full SOLD_AT timestamp. Summary rows can still be distinguished from source NULLs in REGION via GROUPING(region).

For complex expressions, keep syntax consistent across SELECT, GROUP BY, and GROUPING functions. A select-list alias cannot arbitrarily substitute for the original expression everywhere.

### 10.3 GROUPING on a non-grouping expression

GROUPING is only meaningful for expressions participating in an extended GROUP BY. Do not pass a column that is not part of the grouping key to GROUPING expecting Oracle to deduce the origin of NULL. If you need to flag a dimension, include it in the appropriate GROUP BY and pass that exact grouping expression as the argument.

## 11. Safe report label design

### 11.1 Distinguishing three states

A dimension can have at least three display states:

1. A specific value, e.g., North.
2. NULL in source data, e.g., region unknown.
3. NULL from aggregation, meaning all regions at a summary level.

CASE should represent all three states:

~~~sql
CASE
  WHEN GROUPING(region) = 1 THEN 'ALL REGIONS'
  WHEN region IS NULL THEN 'UNKNOWN REGION'
  ELSE region
END
~~~

If the business also distinguishes "not applicable" from "not entered," a separate status code or source column is needed. GROUPING only distinguishes aggregation NULLs from NULLs in source data; it does not explain why source data is NULL.

### 11.2 Do not replace NULLs with sentinel strings in the source table

Some designs use dummy values like 'ALL' or 'UNKNOWN' instead of NULL. This can collide with valid data, skew aggregations, and make changing display languages difficult.

It is better to keep NULLs according to data semantics and use GROUPING/CASE in the query layer for presentation:

- Source NULL: UNKNOWN REGION.
- Aggregation NULL: ALL REGIONS.

If the business requires finer classification of source NULLs, store an explicit status or dimension key.

### 11.3 Do not drive logic purely from label strings

Applications can use GID as grouping-level metadata and keep labels strictly for display. Avoid sending the string 'GRAND TOTAL' and later using text comparison to detect total rows, because display wording or language may change.

Example result set:

~~~sql
SELECT region,
       product,
       SUM(amount) AS total_amount,
       GROUPING_ID(region, product) AS grouping_level,
       CASE GROUPING_ID(region, product)
         WHEN 0 THEN 'DETAIL'
         WHEN 1 THEN 'REGION_SUBTOTAL'
         WHEN 3 THEN 'GRAND_TOTAL'
       END AS row_label
FROM lab_sales_grouping
GROUP BY ROLLUP(region, product);
~~~

The application can format based on GROUPING_LEVEL while ROW_LABEL serves human readers.

## 12. Result and performance considerations

### 12.1 ROLLUP/CUBE increase the number of groups

Each grouping set produces an aggregation level. CUBE can generate 2^n grouping sets for n dimensions; many dimensions can rapidly increase group counts and computation cost. Generate only the reporting levels actually needed.

### 12.2 GROUPING_ID has low evaluation overhead, but the overall query is not free

Evaluating GROUPING_ID is a lightweight representation of grouping state. The main cost usually comes from reading data, forming groups, sorting/hashing, and the requested grouping sets. Tuning requires looking at the entire query and plan, not merely counting GROUPING_ID calls.

### 12.3 Put source filters in WHERE and group filters in HAVING

Example aggregating only positive-amount data:

~~~sql
SELECT region,
       product,
       SUM(amount) AS total_amount,
       GROUPING_ID(region, product) AS gid
FROM lab_sales_grouping
WHERE amount > 0
GROUP BY ROLLUP(region, product)
HAVING GROUPING_ID(region, product) IN (0, 1, 3);
~~~

WHERE shrinks the source row set before aggregation; HAVING selects grouping levels after aggregation. The HAVING above keeps all three ROLLUP levels mainly to illustrate placement; adjust the code list to retain only the levels needed in the report.

### 12.4 Inspecting the execution plan

~~~sql
EXPLAIN PLAN FOR
SELECT region,
       product,
       SUM(amount) AS total_amount,
       GROUPING_ID(region, product) AS gid
FROM lab_sales_grouping
GROUP BY ROLLUP(region, product);

SELECT *
FROM TABLE(DBMS_XPLAN.DISPLAY);
~~~

EXPLAIN PLAN shows the estimated plan, not runtime metrics. For large datasets, examine the actual execution plan, cardinality, sort/hash operations, I/O, memory, and grouping set counts.

## 13. Common mistakes

| Mistake/Misconception | Why it is wrong | Resolution |
|---|---|---|
| Assuming NULL REGION means grand total row | NULL can come from source data or aggregation | Use GROUPING(region) |
| Using NVL(region, 'ALL') for labeling | Merges source NULL and subtotal NULL into one label | Check GROUPING in CASE first, then region IS NULL |
| Thinking GROUPING(region)=1 means source region is NULL | It reports that the dimension was aggregated out of the level | Read GROUPING as grouping metadata |
| Treating GROUPING_ID as a unique row ID | Many detail groups share code 0 | Combine dimension values and metadata |
| Reordering GROUPING_ID arguments without updating CASE | Bit weights change | Document expression order |
| Using a CASE with only 0, 1, 3 for CUBE | Two-dimensional CUBE also has PRODUCT-only subtotals (code 2) | List every actual grouping set |
| Passing a non-GROUP BY column to GROUPING | There is no valid grouping metadata for that expression | Pass the exact grouping expression |
| Filtering subtotals in WHERE | WHERE runs before groups are formed | Use HAVING |
| Using CUBE on many dimensions without counting levels | Grouping sets grow as 2^n | Use GROUPING SETS when only a few levels are needed |
| Assuming GID 3 is always grand total in every query | Codes depend on argument count and order | Read the query's bitmask and grouping sets |
| Storing ALL/UNKNOWN labels in source columns | Mixes data with presentation | Keep source NULLs and build labels in SELECT |

## 16. Process for reading a summary row

When an application receives a row from a ROLLUP/CUBE report, read it in order:

1. Check GROUPING_ID and the expression order used to understand the aggregation level.
2. Use each GROUPING(expression) to identify which dimensions were dropped from the grouping set.
3. For a dimension with GROUPING equal to 0, if the value is NULL, it is a source NULL within that group.
4. For a dimension with GROUPING equal to 1, NULL is a marker for an aggregated-out dimension.
5. Build display labels with CASE without overwriting source data.
6. When filtering or sorting by level, use GROUPING_ID in HAVING/ORDER BY following the documented code contract.

Example of a row with REGION=NULL, PRODUCT=NULL:

| G_REGION | G_PRODUCT | GID | Interpretation |
|---:|---:|---:|---|
| 0 | 0 | 0 | Detail row where both source dimensions are NULL |
| 0 | 1 | 1 | Subtotal of the source NULL REGION group |
| 1 | 0 | 2 | Subtotal of the source NULL PRODUCT group |
| 1 | 1 | 3 | Grand total |

Not all of the rows above necessarily appear in the same query. They illustrate the four encodable grouping states for two dimensions when the corresponding grouping sets are requested.

## 17. Summary

In Oracle reports using ROLLUP, CUBE, or GROUPING SETS, NULL can come from two sources: original data genuinely missing a value, or Oracle generating NULL to represent a dimension aggregated out of a grouping level. **GROUPING(expression)** distinguishes the two cases: 0 is an ordinary grouping value, including source NULLs; 1 is an aggregation NULL. **GROUPING_ID(expr, ...)** encodes multiple GROUPING flags into a bitmask integer, useful for identifying and handling grouping levels.

Remember:

- Always check GROUPING before checking IS NULL in labeling CASE expressions.
- Read GROUPING_ID according to exact argument order; the last expression corresponds to the lowest-order bit.
- GID identifies the grouping level, not a unique row key.
- ROLLUP generates prefix levels; CUBE generates every combination; GROUPING SETS lets you specify exact levels.
- Use HAVING to filter grouping levels, ORDER BY to sort output, and preserve source NULLs in data according to proper semantics.

Once you understand the origin of NULLs, subtotal and grand total rows will no longer be confused with missing data, and applications can accurately display "Unknown," "All," and "Grand Total" labels.
