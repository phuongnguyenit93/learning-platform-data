# SQL BOOLEAN, giới hạn định danh và cú pháp mới theo bản hỗ trợ

Oracle Database bổ sung nhiều khả năng SQL theo từng release. Một thay đổi đáng chú ý ở dòng Oracle Database 23c/23ai là kiểu dữ liệu **BOOLEAN trong SQL**: trước đó PL/SQL đã có BOOLEAN từ lâu, nhưng SQL table column không thể khai báo kiểu này như một kiểu dữ liệu thông thường. Các release mới cũng bổ sung một số cú pháp DDL và truy vấn giúp câu lệnh ngắn gọn hơn.

Song song với cú pháp mới, Oracle có quy tắc giới hạn độ dài identifier phụ thuộc phiên bản và tham số **COMPATIBLE**. Hệ thống cũ thường bị giới hạn 30 byte; từ Oracle Database 12.2 trở lên, phần lớn identifier có thể dài tối đa 128 byte khi mức tương thích phù hợp. Đây là thay đổi ảnh hưởng trực tiếp đến tên bảng, cột, index, constraint, sequence, package và tên do ORM tự sinh.

Khi phát triển ứng dụng hoặc viết migration, cần kiểm tra đồng thời:

- Database release thực tế.
- Giá trị COMPATIBLE.
- Kiểu dữ liệu và cú pháp được release đó hỗ trợ.
- JDBC driver và ORM dialect của ứng dụng.
- Các database/version khác mà schema hoặc SQL cần tương thích.

Một câu SQL chạy được trên database development mới không có nghĩa nó chạy được trên production cũ. Không nên bật cú pháp mới chỉ dựa trên tên phiên bản nhìn thấy trong banner; hãy xác nhận cấu hình tương thích và toàn bộ stack client.

## 1. SQL BOOLEAN và PL/SQL BOOLEAN

Boolean biểu diễn một giá trị logic. Trong SQL, các trạng thái thường cần hiểu là:

- TRUE: điều kiện đúng.
- FALSE: điều kiện sai.
- UNKNOWN: chưa xác định, thường do giá trị NULL.

Trước Oracle Database 23c, PL/SQL đã hỗ trợ biến BOOLEAN:

~~~sql
DECLARE
  l_enabled BOOLEAN := TRUE;
BEGIN
  IF l_enabled THEN
    DBMS_OUTPUT.PUT_LINE('Enabled');
  END IF;
END;
/
~~~

Tuy nhiên, trên các Oracle release cũ, không thể khai báo một cột bảng thông thường bằng kiểu SQL BOOLEAN:

~~~sql
-- Không dùng được như một cột SQL trên các release cũ
CREATE TABLE feature_flag (
  flag_id NUMBER PRIMARY KEY,
  enabled BOOLEAN
);
~~~

Đây là khác biệt quan trọng: PL/SQL BOOLEAN là kiểu dữ liệu trong ngôn ngữ PL/SQL; nó không đồng nghĩa với việc SQL engine có kiểu BOOLEAN để lưu trong table, truy vấn hoặc bind như một SQL datatype.

Oracle Database 23c đưa BOOLEAN vào SQL. Oracle Database 23ai tiếp tục dòng release có hỗ trợ SQL BOOLEAN. Khi dùng tính năng này, phải xác nhận đúng release, mức COMPATIBLE, JDBC driver và Hibernate version đang triển khai.

## 2. Khai báo cột BOOLEAN trên Oracle hỗ trợ

Trên Oracle Database 23c/23ai có hỗ trợ SQL BOOLEAN, có thể khai báo:

~~~sql
CREATE TABLE feature_flag (
  flag_id   NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  flag_name VARCHAR2(100) NOT NULL,
  enabled   BOOLEAN DEFAULT FALSE NOT NULL
);
~~~

Insert:

~~~sql
INSERT INTO feature_flag(flag_name, enabled)
VALUES ('new-checkout', TRUE);

INSERT INTO feature_flag(flag_name, enabled)
VALUES ('legacy-report', FALSE);
~~~

Truy vấn:

~~~sql
SELECT flag_id,
       flag_name,
       enabled
  FROM feature_flag
 WHERE enabled = TRUE;
~~~

Cập nhật:

~~~sql
UPDATE feature_flag
   SET enabled = FALSE
 WHERE flag_name = 'legacy-report';
~~~

SQL BOOLEAN là kiểu logic thực sự. Không cần chuyển mọi giá trị thành chuỗi Y/N hoặc số 1/0 khi database đã hỗ trợ kiểu này. Tuy nhiên, ứng dụng vẫn phải thống nhất mapping và cách bind giữa JDBC, JPA/Hibernate và schema.

### BOOLEAN có thể NULL

Nếu không khai báo NOT NULL, một cột BOOLEAN có thể nhận NULL. Khi đó nó có ba trạng thái logic:

| Giá trị | Ý nghĩa |
|---|---|
| TRUE | Đúng |
| FALSE | Sai |
| NULL / UNKNOWN | Chưa biết hoặc chưa được thiết lập |

Nếu nghiệp vụ chỉ có hai trạng thái, nên khai báo NOT NULL và một default phù hợp. Nếu NULL có ý nghĩa riêng, cần giữ trạng thái thứ ba trong model và kiểm thử rõ.

## 3. Logic ba giá trị: TRUE, FALSE và UNKNOWN

SQL dùng logic ba giá trị cho biểu thức có thể nhận NULL. Kết quả của điều kiện không phải lúc nào cũng TRUE hoặc FALSE.

Một số quy tắc:

| A | B | A AND B | A OR B |
|---|---|---|---|
| TRUE | TRUE | TRUE | TRUE |
| TRUE | FALSE | FALSE | TRUE |
| TRUE | UNKNOWN | UNKNOWN | TRUE |
| FALSE | UNKNOWN | FALSE | UNKNOWN |
| FALSE | FALSE | FALSE | FALSE |
| UNKNOWN | UNKNOWN | UNKNOWN | UNKNOWN |

Với phép NOT:

| A | NOT A |
|---|---|
| TRUE | FALSE |
| FALSE | TRUE |
| UNKNOWN | UNKNOWN |

Ví dụ:

~~~sql
SELECT flag_name
  FROM feature_flag
 WHERE enabled = TRUE;
~~~

Điều kiện chỉ chọn hàng có enabled là TRUE. Hàng FALSE hoặc NULL không được chọn. Vì vậy, nếu ứng dụng cần phân biệt “đã tắt” và “chưa được quyết định”, không nên gộp NULL thành FALSE một cách âm thầm.

### IS NULL và kiểm tra trạng thái

~~~sql
SELECT flag_name
  FROM feature_flag
 WHERE enabled IS NULL;
~~~

Kiểm tra trạng thái chưa xác định bằng IS NULL, không dùng enabled = NULL, vì so sánh bằng NULL trả về UNKNOWN.

Khi xử lý logic nghiệp vụ, viết rõ điều kiện:

~~~sql
SELECT flag_name,
       CASE
         WHEN enabled = TRUE THEN 'ON'
         WHEN enabled = FALSE THEN 'OFF'
         ELSE 'UNSET'
       END AS enabled_state
  FROM feature_flag;
~~~

### BOOLEAN và WHERE

Trong các release hỗ trợ, biểu thức Boolean có thể dùng làm điều kiện SQL. Cách viết tường minh enabled = TRUE thường dễ đọc trong ví dụ và tránh nhầm lẫn khi đội ngũ chưa quen cú pháp mới.

Không dùng = 1 hoặc = 'Y' cho cột BOOLEAN. Những giá trị đó thuộc các mô hình lưu Boolean cũ bằng NUMBER hoặc CHAR.

## 4. CHECK constraint và default cho BOOLEAN

Với cột BOOLEAN, miền giá trị đã được giới hạn bởi datatype. Có thể khai báo default và NOT NULL:

~~~sql
CREATE TABLE notification_setting (
  setting_id NUMBER PRIMARY KEY,
  is_enabled BOOLEAN DEFAULT TRUE NOT NULL
);
~~~

NOT NULL quan trọng hơn một CHECK constraint bổ sung nếu nghiệp vụ yêu cầu hai trạng thái. Một CHECK expression thường không loại bỏ NULL vì kết quả UNKNOWN không bị xem là FALSE trong quy tắc kiểm tra constraint.

Ví dụ:

~~~sql
CREATE TABLE notification_setting (
  setting_id NUMBER PRIMARY KEY,
  is_enabled BOOLEAN,
  CONSTRAINT ck_notification_enabled
    CHECK (is_enabled IN (TRUE, FALSE))
);
~~~

Constraint trên không thay thế NOT NULL nếu cần cấm trạng thái chưa xác định. Hãy dùng:

~~~sql
is_enabled BOOLEAN DEFAULT TRUE NOT NULL
~~~

Khi đọc schema hoặc viết migration, đừng giả định một CHECK constraint tự động cấm NULL.

## 5. BOOLEAN trong PL/SQL và SQL trên release mới

Trước khi SQL BOOLEAN được hỗ trợ, PL/SQL có thể nhận Boolean từ logic trong procedure nhưng không thể lưu trực tiếp vào cột SQL BOOLEAN vì datatype đó chưa tồn tại trong SQL.

Một thủ tục cũ có thể dùng NUMBER hoặc CHAR để trao đổi trạng thái với SQL:

~~~sql
DECLARE
  l_enabled BOOLEAN := TRUE;
  l_flag_number NUMBER;
BEGIN
  IF l_enabled THEN
    l_flag_number := 1;
  ELSE
    l_flag_number := 0;
  END IF;

  UPDATE feature_flag_legacy
     SET enabled_number = l_flag_number
   WHERE flag_id = 10;
END;
/
~~~

Trên release hỗ trợ SQL BOOLEAN, SQL và PL/SQL có thể dùng datatype này trực tiếp trong các ngữ cảnh được tài liệu phiên bản cho phép. Tuy nhiên, cần phân biệt:

- Kiểu dữ liệu trong PL/SQL language.
- SQL datatype trong table/column.
- Kiểu JDBC dùng để bind và đọc.
- Kiểu Java mà ORM ánh xạ.

Một tính năng có trong database chưa có nghĩa mọi version JDBC/Hibernate đều tự động map chính xác. Kiểm tra toàn bộ chuỗi driver và framework.

## 6. JDBC: bind và đọc SQL BOOLEAN

Với Oracle JDBC driver hỗ trợ SQL BOOLEAN, có thể dùng JDBC Boolean API theo khả năng của driver:

~~~java
String sql =
    "insert into feature_flag(flag_id, flag_name, enabled) " +
    "values (?, ?, ?)";

try (PreparedStatement statement =
         connection.prepareStatement(sql)) {
    statement.setLong(1, 100L);
    statement.setString(2, "new-checkout");
    statement.setBoolean(3, true);
    statement.executeUpdate();
}
~~~

Đọc:

~~~java
String sql =
    "select enabled from feature_flag where flag_id = ?";

try (PreparedStatement statement =
         connection.prepareStatement(sql)) {
    statement.setLong(1, 100L);

    try (ResultSet resultSet = statement.executeQuery()) {
        if (resultSet.next()) {
            boolean enabled = resultSet.getBoolean("enabled");
            boolean wasNull = resultSet.wasNull();
        }
    }
}
~~~

ResultSet.getBoolean() trả về false khi SQL value là NULL; gọi wasNull() ngay sau lần đọc đó để phân biệt NULL với FALSE. Nếu nghiệp vụ cần ba trạng thái, không bỏ qua bước này.

API và SQL type support phụ thuộc Oracle JDBC driver version. Hãy dùng driver được hỗ trợ cho database release và JDK của ứng dụng, sau đó test setBoolean, getBoolean, NULL và prepared statement trên Oracle thật.

## 7. BOOLEAN trong Spring Data JPA và Hibernate

Trong Java, kiểu thường dùng là Boolean hoặc boolean:

- boolean chỉ có TRUE/FALSE.
- Boolean có thể là TRUE/FALSE/NULL.

Nếu cột SQL BOOLEAN có thể NULL, dùng Boolean để giữ trạng thái thứ ba. Nếu schema khai báo NOT NULL, có thể dùng boolean hoặc Boolean với validation phù hợp.

Ví dụ entity minh họa:

~~~java
@Entity
@Table(name = "FEATURE_FLAG")
public class FeatureFlag {

    @Id
    @Column(name = "FLAG_ID")
    private Long id;

    @Column(name = "FLAG_NAME", nullable = false)
    private String flagName;

    @Column(name = "ENABLED", nullable = false)
    private Boolean enabled;
}
~~~

Việc Hibernate map Java Boolean thành Oracle SQL BOOLEAN hay một kiểu tương thích khác phụ thuộc:

- Hibernate version.
- Oracle dialect.
- Oracle JDBC driver.
- Database release và COMPATIBLE.
- DDL do migration tạo ra.

Không tự giả định annotation Boolean sẽ luôn tạo ra cột SQL BOOLEAN trên mọi Oracle version. Nếu production schema dùng kiểu BOOLEAN mới, integration test cần chạy trên Oracle hỗ trợ và kiểm tra DDL/mapping thực tế.

### Tránh để Hibernate tự tạo schema khác migration

Nếu Flyway hoặc Liquibase quản lý schema, hãy để migration định nghĩa datatype chính xác và dùng:

~~~yaml
spring:
  jpa:
    hibernate:
      ddl-auto: validate
~~~

Không dùng create hoặc update trên production để framework tự quyết định kiểu cột Boolean khi ứng dụng cần hỗ trợ nhiều Oracle release.

## 8. Các release cũ: NUMBER(1) hoặc CHAR(1)

Trước Oracle Database 23c, cách phổ biến là biểu diễn Boolean bằng một kiểu SQL khác. Hai lựa chọn thường gặp:

**NUMBER(1):**

~~~sql
CREATE TABLE feature_flag_legacy (
  flag_id NUMBER PRIMARY KEY,
  enabled NUMBER(1) DEFAULT 0 NOT NULL,
  CONSTRAINT ck_feature_flag_enabled
    CHECK (enabled IN (0, 1))
);
~~~

- 1 biểu diễn TRUE.
- 0 biểu diễn FALSE.
- NOT NULL loại bỏ trạng thái thứ ba nếu nghiệp vụ chỉ cần hai trạng thái.
- CHECK constraint ngăn giá trị khác 0/1.

**CHAR(1):**

~~~sql
CREATE TABLE feature_flag_legacy (
  flag_id NUMBER PRIMARY KEY,
  enabled CHAR(1) DEFAULT 'N' NOT NULL,
  CONSTRAINT ck_feature_flag_enabled
    CHECK (enabled IN ('Y', 'N'))
);
~~~

- Y biểu diễn TRUE.
- N biểu diễn FALSE.
- Có thể dễ đọc trong SQL và báo cáo.
- Cần thống nhất quy ước giữa ứng dụng, ETL và hệ thống ngoài.

Không dùng đồng thời nhiều quy ước như 1, Y, T, TRUE cho cùng một cột. Chọn một representation và ràng buộc bằng constraint.

## 9. JPA AttributeConverter cho Boolean lưu bằng NUMBER

Nếu schema cũ dùng NUMBER(1), có thể dùng AttributeConverter để ánh xạ Java Boolean sang Integer:

~~~java
import jakarta.persistence.AttributeConverter;
import jakarta.persistence.Converter;

@Converter
public class BooleanNumberConverter
        implements AttributeConverter<Boolean, Integer> {

    @Override
    public Integer convertToDatabaseColumn(Boolean value) {
        if (value == null) {
            return null;
        }
        return value ? 1 : 0;
    }

    @Override
    public Boolean convertToEntityAttribute(Integer value) {
        if (value == null) {
            return null;
        }
        if (value == 1) {
            return Boolean.TRUE;
        }
        if (value == 0) {
            return Boolean.FALSE;
        }
        throw new IllegalArgumentException(
            "Unexpected Boolean representation: " + value
        );
    }
}
~~~

Áp dụng trên field:

~~~java
@Convert(converter = BooleanNumberConverter.class)
@Column(name = "ENABLED", precision = 1, scale = 0, nullable = false)
private Boolean enabled;
~~~

Converter cần xử lý NULL theo đúng nullability của cột. Nếu cột NOT NULL, validation ở entity và constraint ở database nên cùng bảo vệ invariant.

Nếu dùng autoApply = true, converter sẽ áp dụng cho mọi thuộc tính Boolean phù hợp trong persistence unit. Chỉ bật khi tất cả các cột Boolean đều dùng cùng representation. Với hệ thống có cả SQL BOOLEAN và NUMBER(1), nên gắn converter tường minh trên field cần chuyển đổi.

## 10. JPA AttributeConverter cho Boolean lưu bằng CHAR(1)

Nếu schema legacy dùng Y/N:

~~~java
import jakarta.persistence.AttributeConverter;
import jakarta.persistence.Converter;

@Converter
public class BooleanYnConverter
        implements AttributeConverter<Boolean, String> {

    @Override
    public String convertToDatabaseColumn(Boolean value) {
        if (value == null) {
            return null;
        }
        return value ? "Y" : "N";
    }

    @Override
    public Boolean convertToEntityAttribute(String value) {
        if (value == null) {
            return null;
        }
        return switch (value) {
            case "Y" -> Boolean.TRUE;
            case "N" -> Boolean.FALSE;
            default -> throw new IllegalArgumentException(
                "Unexpected Y/N value: " + value
            );
        };
    }
}
~~~

Đoạn switch trên cần Java version hỗ trợ switch expression. Nếu dự án dùng Java cũ hơn, viết bằng if/else.

Converter không thay thế CHECK constraint. Dữ liệu có thể được ghi từ SQL script, ETL hoặc ứng dụng khác; database vẫn cần bảo vệ miền giá trị.

## 11. Chọn representation khi hỗ trợ nhiều Oracle release

Nếu cùng một ứng dụng phải chạy trên Oracle 19c và Oracle 23ai, không thể giả định mọi database đều hiểu SQL BOOLEAN. Có hai hướng:

1. Dùng representation tương thích như NUMBER(1) hoặc CHAR(1) trên toàn bộ môi trường.
2. Dùng SQL BOOLEAN chỉ trên môi trường đã nâng cấp và quản lý migration/ORM mapping theo version.

Hướng thứ nhất thường dễ vận hành hơn khi cần một schema dùng chung giữa nhiều release. Hướng thứ hai tận dụng datatype mới nhưng làm tăng yêu cầu về migration, driver, ORM và compatibility.

Trước khi quyết định, trả lời:

- Có phải hỗ trợ Oracle 19c hoặc release cũ hơn không?
- Có database DR/test chưa được nâng cấp không?
- Có ETL, BI, CDC hoặc ứng dụng ngoài đọc schema không?
- JDBC driver thấp nhất đang dùng có hỗ trợ SQL BOOLEAN không?
- Hibernate dialect version có hiểu datatype và DDL mới không?
- Các migration cũ có cần rollback hoặc chạy lại không?

Không nên đổi cột NUMBER(1) sang BOOLEAN chỉ vì release mới hỗ trợ. Cân nhắc lợi ích thực tế và chi phí tương thích.

## 12. Giới hạn độ dài identifier trong Oracle

Identifier là tên của object hoặc thành phần SQL, ví dụ:

- Table và view.
- Column.
- Index.
- Constraint.
- Sequence.
- Schema/user.
- Package, procedure và function.
- Trigger.
- Synonym.
- Database link.

Oracle có giới hạn độ dài identifier theo release và tham số COMPATIBLE.

| Mức tương thích | Giới hạn phổ biến cho phần lớn identifier |
|---|---:|
| COMPATIBLE thấp hơn 12.2 | 30 byte |
| COMPATIBLE từ 12.2 trở lên | 128 byte |

Đây là giới hạn phổ biến cho phần lớn identifier SQL. Một số tên hoặc loại object có quy tắc riêng theo release; luôn xem SQL Language Reference của đúng phiên bản nếu đang dùng tên đặc biệt.

### Vì sao có giới hạn 30 byte?

Các Oracle release cũ sử dụng giới hạn 30 byte cho phần lớn tên object. Nhiều schema legacy, migration tool và ứng dụng được xây dựng quanh quy tắc này. Khi database được nâng cấp và COMPATIBLE cho phép, giới hạn phần lớn identifier tăng lên 128 byte.

Không phải chỉ nâng binary Oracle là mọi database lập tức dùng giới hạn mới. Giá trị COMPATIBLE phải cho phép feature tương ứng.

## 13. Byte khác ký tự

Giới hạn identifier của Oracle được tính bằng **byte**, không phải số ký tự hiển thị.

Với database character set đa byte, một tên có 20 ký tự Unicode có thể chiếm nhiều hơn 20 byte. Vì vậy:

- Không chỉ đếm số ký tự trong IDE.
- Không giả định 30 ký tự luôn vừa giới hạn 30 byte.
- Kiểm tra encoding/database character set.
- Ưu tiên tên ASCII ngắn, rõ ràng cho object cần tương thích nhiều môi trường.

Có thể minh họa sự khác biệt giữa số ký tự và số byte bằng SQL:

~~~sql
SELECT LENGTH('ABC') AS char_length,
       LENGTHB('ABC') AS byte_length
  FROM dual;
~~~

LENGTH đếm ký tự theo semantics của Oracle; LENGTHB trả số byte. Với identifier thật, có thể xem tên object và kiểm tra byte length:

~~~sql
SELECT object_name,
       LENGTH(object_name) AS char_length,
       LENGTHB(object_name) AS byte_length
  FROM user_objects
 ORDER BY byte_length DESC;
~~~

Các view dictionary lưu tên object theo metadata của database; quyền và view cụ thể tùy phạm vi cần kiểm tra.

## 14. Cách Oracle xử lý identifier không quote và có quote

Identifier không đặt trong dấu nháy kép được chuẩn hóa thành uppercase:

~~~sql
CREATE TABLE order_header (
  order_id NUMBER
);
~~~

Các cách tham chiếu sau tương đương về tên không quote:

~~~sql
SELECT order_id FROM order_header;
SELECT ORDER_ID FROM ORDER_HEADER;
SELECT Order_Id FROM Order_Header;
~~~

Identifier đặt trong dấu nháy kép giữ nguyên case:

~~~sql
CREATE TABLE "OrderHeader" (
  "orderId" NUMBER
);
~~~

Sau đó phải tham chiếu đúng:

~~~sql
SELECT "orderId"
  FROM "OrderHeader";
~~~

Nếu viết:

~~~sql
SELECT orderId
  FROM OrderHeader;
~~~

Oracle hiểu identifier không quote theo quy tắc uppercase và có thể không tìm thấy object đã tạo với quoted mixed-case name.

### Có nên dùng quoted identifier?

Thông thường nên tránh quoted identifier cho tên bảng/cột:

- Khó viết SQL và migration.
- Dễ sai case giữa Java, ORM và database.
- Công cụ quản trị có thể hiển thị/quote khác nhau.
- Tăng nguy cơ lỗi khi tích hợp BI, ETL hoặc ứng dụng khác.
- Làm naming strategy khó đoán.

Chỉ dùng quoted identifier khi có yêu cầu tương thích đặc biệt và đã kiểm soát mọi client.

## 15. Quy tắc tên identifier

Với nonquoted identifier, Oracle có quy tắc ký tự và từ khóa. Một số nguyên tắc thực hành:

- Bắt đầu bằng chữ cái theo database character set.
- Dùng chữ, số, underscore và các ký tự đặc biệt được Oracle cho phép như $ hoặc # theo quy tắc identifier.
- Không chứa dấu cách.
- Không dùng reserved word làm tên không quote.
- Không vượt giới hạn byte của release/COMPATIBLE.
- Giữ tên nhất quán và dễ đọc.

Quoted identifier có quy tắc khác và có thể chứa nhiều ký tự hơn, nhưng không nên dùng để né mọi vấn đề đặt tên.

### Reserved words

Tên như SELECT, TABLE, DATE, USER hoặc từ khóa SQL khác có thể gây xung đột. Dù một số từ có thể dùng dưới dạng quoted identifier, cách tốt hơn là đặt tên rõ ràng:

~~~sql
-- Tránh
CREATE TABLE "ORDER" (
  "DATE" DATE
);

-- Nên dùng tên mô tả
CREATE TABLE sales_order (
  ordered_at DATE
);
~~~

Danh sách reserved words thay đổi theo release. Một tên hợp lệ ở database cũ có thể trở thành từ khóa hoặc tên đặc biệt trong release mới. Khi nâng cấp, kiểm tra schema và SQL sinh ra.

## 16. Ảnh hưởng của giới hạn identifier đến Hibernate/JPA

Hibernate có thể sinh tên cho:

- Join table.
- Foreign key.
- Unique constraint.
- Index.
- Sequence.
- Collection table.
- Secondary table.
- Discriminator column.

Nếu naming strategy tạo tên dài hơn giới hạn của database cũ, migration hoặc schema generation có thể lỗi:

~~~text
ORA-00972: identifier is too long
~~~

Ví dụ một tên constraint sinh tự động:

~~~text
FK_CUSTOMER_ORDER_HISTORY_CUSTOMER_REFERENCE_ID
~~~

Tên này có thể vượt giới hạn 30 byte trên database cũ. Cách xử lý là dùng naming strategy có quy tắc rút gọn ổn định, hoặc khai báo tên ngắn tường minh trong mapping/migration.

Ví dụ:

~~~java
@Table(
    name = "CUSTOMER_ORDER",
    uniqueConstraints = {
        @UniqueConstraint(
            name = "UK_CUST_ORDER_CODE",
            columnNames = {"ORDER_CODE"}
        )
    }
)
~~~

Tên constraint cần nằm trong giới hạn của mọi Oracle release mà ứng dụng hỗ trợ.

## 17. Đặt tên tương thích nhiều phiên bản

Nếu schema phải chạy trên cả Oracle 11g/12.1 và Oracle 19c/23ai, cách an toàn là giữ phần lớn tên object trong giới hạn 30 byte. Điều này giảm nguy cơ migration mới chạy được trên database mới nhưng thất bại ở database cũ.

Một quy ước thực tế:

| Loại object | Prefix gợi ý | Ví dụ |
|---|---|---|
| Table | Không bắt buộc hoặc domain prefix | ORDER_HEADER |
| Primary key | PK_ | PK_ORDER_HEADER |
| Foreign key | FK_ | FK_ORDER_CUST |
| Unique constraint | UK_ | UK_ORDER_CODE |
| Check constraint | CK_ | CK_ORDER_STATUS |
| Index | IX_ | IX_ORDER_CREATED |
| Sequence | SEQ_ | SEQ_ORDER_ID |
| Trigger | TRG_ | TRG_ORDER_AUDIT |
| View | V_ hoặc VW_ | VW_ORDER_SUMMARY |

Prefix là quy ước nội bộ, không phải yêu cầu của Oracle. Tên phải có ý nghĩa, ổn định và không bị trùng.

### Rút gọn tên tự động

Nếu ORM hoặc migration tool sinh tên từ nhiều thành phần, không cắt chuỗi một cách ngẫu nhiên vì có thể tạo collision. Một chiến lược ổn định:

1. Chuẩn hóa tên nguồn.
2. Giữ prefix thể hiện loại object.
3. Giữ một phần tên domain quan trọng.
4. Thêm hash ngắn từ tên đầy đủ nếu cần tránh trùng.
5. Giới hạn theo byte, không theo số ký tự.
6. Dùng cùng một thuật toán trong mọi môi trường.

Ví dụ tên dài có thể thành:

~~~text
FK_ORDER_ITEM_PRODUCT_8A31
~~~

Không thay đổi thuật toán naming giữa các lần build nếu migration đã được tạo và áp dụng ở môi trường chia sẻ.

## 18. Kiểm tra COMPATIBLE

Tham số COMPATIBLE điều khiển mức tương thích của database với các khả năng và cấu trúc được giới thiệu ở release mới. Đây không phải tham số chỉ để thay đổi parser hoặc tăng giới hạn identifier.

Kiểm tra:

~~~sql
SHOW PARAMETER compatible;
~~~

Hoặc:

~~~sql
SELECT name,
       value
  FROM v$parameter
 WHERE name = 'compatible';
~~~

Đọc release:

~~~sql
SELECT banner
  FROM v$version;
~~~

Thông tin component:

~~~sql
SELECT product,
       version,
       status
  FROM product_component_version;
~~~

COMPATIBLE ảnh hưởng đến nhiều khả năng và cấu trúc database, không chỉ SQL BOOLEAN hoặc identifier. Không tự nâng giá trị tham số trong production chỉ để chạy một câu DDL mới.

Việc thay đổi COMPATIBLE phải nằm trong kế hoạch nâng cấp Oracle, có kiểm tra đường nâng cấp, backup, recovery và hướng dẫn chính thức. Một số thay đổi compatibility có thể không dễ đảo ngược sau khi database đã sử dụng feature mới.

## 19. Cú pháp mới: IF NOT EXISTS và IF EXISTS

Oracle Database 23c/23ai bổ sung cú pháp tồn tại/không tồn tại cho một số lệnh DDL. Ví dụ:

~~~sql
CREATE TABLE IF NOT EXISTS feature_flag (
  flag_id NUMBER PRIMARY KEY,
  enabled BOOLEAN DEFAULT FALSE NOT NULL
);
~~~

Xóa bảng nếu tồn tại:

~~~sql
DROP TABLE IF EXISTS feature_flag;
~~~

Các dạng IF [NOT] EXISTS được hỗ trợ tùy loại object và release. Không suy luận rằng mọi câu CREATE, ALTER hoặc DROP đều có thể thêm mệnh đề này. Kiểm tra SQL Language Reference của đúng database version trước khi dùng trong migration.

### IF NOT EXISTS không xác minh schema

CREATE TABLE IF NOT EXISTS có thể không tạo bảng nếu tên đã tồn tại. Điều đó không chứng minh bảng hiện có có đúng column, datatype, constraint hoặc index như migration mong muốn.

Trong migration production, cần phân biệt:

- Object đã tồn tại và đúng cấu trúc.
- Object đã tồn tại nhưng cấu trúc cũ/sai.
- Object tồn tại dưới loại khác hoặc schema khác.
- Migration history cho biết script đã chạy hay chưa.

IF NOT EXISTS là cú pháp tiện lợi, không thay thế schema migration tracking và kiểm tra drift.

### Trên release cũ

Với Oracle cũ không hỗ trợ DROP TABLE IF EXISTS, có thể dùng PL/SQL exception handling nhưng chỉ bỏ qua lỗi table or view does not exist:

~~~sql
BEGIN
  EXECUTE IMMEDIATE 'DROP TABLE feature_flag_legacy PURGE';
EXCEPTION
  WHEN OTHERS THEN
    IF SQLCODE <> -942 THEN
      RAISE;
    END IF;
END;
/
~~~

Không viết WHEN OTHERS THEN NULL cho DDL. Cách đó có thể che lỗi quyền, tablespace, dependency hoặc cú pháp.

Với CREATE TABLE, một migration tool có version history thường tốt hơn việc tự nuốt lỗi object already exists. Nếu cần xử lý idempotent bằng PL/SQL, chỉ bỏ qua đúng lỗi đã dự kiến và kiểm tra object hiện có.

## 20. Cú pháp mới: SELECT không cần FROM DUAL

Trong Oracle release truyền thống, truy vấn biểu thức hằng thường dùng DUAL:

~~~sql
SELECT 1 + 1 AS result
  FROM dual;
~~~

Oracle Database 23c/23ai hỗ trợ một số truy vấn SELECT không có FROM:

~~~sql
SELECT 1 + 1 AS result;
~~~

Điều này giúp SQL ngắn gọn hơn khi chỉ cần tính toán hoặc lấy biểu thức hằng. Tuy nhiên, nếu ứng dụng phải chạy trên Oracle release cũ, vẫn dùng FROM DUAL để tương thích:

~~~sql
SELECT SYSTIMESTAMP
  FROM dual;
~~~

Không tự động xóa DUAL khỏi mọi query trong một codebase cần hỗ trợ nhiều version. Một số query có DUAL vẫn hợp lệ trên release mới và giữ được khả năng chạy trên release cũ.

## 21. Cú pháp SQL mới và cách viết portable

Một số cú pháp mới làm SQL ngắn hơn, nhưng có thể tạo yêu cầu version tối thiểu. Ví dụ:

| Khả năng | Cách viết trên release mới | Cách viết tương thích hơn |
|---|---|---|
| Boolean column | BOOLEAN | NUMBER(1) hoặc CHAR(1) kèm constraint |
| DDL có điều kiện | CREATE TABLE IF NOT EXISTS | Migration versioned; hoặc PL/SQL xử lý lỗi cụ thể |
| Drop có điều kiện | DROP TABLE IF EXISTS | PL/SQL bắt riêng ORA-00942 |
| SELECT expression | SELECT 1 + 1 | SELECT 1 + 1 FROM dual |
| Tên object dài | Tối đa 128 byte trong điều kiện hỗ trợ | Giữ tên không quá 30 byte |

Nếu phải hỗ trợ nhiều Oracle release, hãy chọn cú pháp chung thấp nhất mà toàn bộ môi trường hỗ trợ hoặc tách migration/SQL theo release một cách có kiểm soát.

Không dùng IF NOT EXISTS để thay thế Flyway/Liquibase versioning, và không dùng kiểu BOOLEAN mới nếu database đích cũ không hiểu datatype.

## 22. Kiểm tra phiên bản và khả năng hỗ trợ từ ứng dụng

Có thể lấy database version từ JDBC metadata:

~~~java
try (Connection connection = dataSource.getConnection()) {
    DatabaseMetaData metadata = connection.getMetaData();

    String productName = metadata.getDatabaseProductName();
    String productVersion = metadata.getDatabaseProductVersion();
    int major = metadata.getDatabaseMajorVersion();
    int minor = metadata.getDatabaseMinorVersion();

    log.info("Database: {} {} ({}. {})",
        productName, productVersion, major, minor);
}
~~~

Có thể ghi nhận driver:

~~~java
DatabaseMetaData metadata = connection.getMetaData();
String driverName = metadata.getDriverName();
String driverVersion = metadata.getDriverVersion();
~~~

Ở phía database, DBA có thể xem V$VERSION, PRODUCT_COMPONENT_VERSION và V$PARAMETER. Ứng dụng không nhất thiết được cấp quyền đọc các view này; nếu cần version telemetry, expose thông tin qua một endpoint hoặc deployment configuration an toàn.

### Không chỉ kiểm tra major version

Một feature có thể phụ thuộc:

- Database release và Release Update.
- Giá trị COMPATIBLE.
- Container/PDB và service đang kết nối.
- Edition hoặc option.
- JDBC driver.
- Hibernate/JPA provider.
- Công cụ migration và SQL client.

Chỉ kiểm tra DatabaseMetaData.getDatabaseMajorVersion() là chưa đủ để kết luận mọi cú pháp mới được phép.

## 23. Feature gate trong ứng dụng

Nếu ứng dụng hỗ trợ nhiều Oracle version, tránh rải điều kiện version khắp repository. Nên quản lý khả năng database tại một nơi:

~~~java
public record OracleCapabilities(
    boolean sqlBooleanSupported,
    boolean ddlIfExistsSupported,
    boolean selectWithoutFromSupported,
    int identifierByteLimit
) {}
~~~

Một component khởi tạo có thể nhận capabilities từ cấu hình deployment hoặc kiểm tra metadata/compatibility bằng quyền được cấp. Không nên cố chạy mọi cú pháp rồi bắt exception để suy luận feature trong mỗi request.

Ví dụ chiến lược:

- Profile 19c dùng NUMBER(1), tên object <= 30 byte và DUAL.
- Profile 23ai dùng SQL BOOLEAN khi driver/ORM hỗ trợ; vẫn có thể giữ DUAL và tên ngắn nếu cần chung schema.
- Migration chọn đúng script theo release đã xác nhận.

Nếu cùng một schema được chia sẻ giữa database phiên bản khác nhau, chọn kiểu dữ liệu và identifier tương thích với database thấp nhất.

## 24. Migration từ NUMBER(1) sang BOOLEAN

Giả sử bảng cũ:

~~~sql
CREATE TABLE feature_flag (
  flag_id NUMBER PRIMARY KEY,
  enabled NUMBER(1) DEFAULT 0 NOT NULL,
  CONSTRAINT ck_feature_enabled CHECK (enabled IN (0, 1))
);
~~~

Khi chuyển sang release hỗ trợ SQL BOOLEAN, cần lập kế hoạch:

1. Xác định ứng dụng nào đọc/ghi cột.
2. Xác định integration/ETL/reporting phụ thuộc NUMBER(1).
3. Kiểm tra JDBC driver và Hibernate mapping.
4. Xác định có cần giữ khả năng rollback về release cũ không.
5. Chọn migration tạo cột mới hoặc chuyển kiểu theo khả năng được hỗ trợ.
6. Chuyển dữ liệu và kiểm tra NULL/0/1.
7. Triển khai ứng dụng tương thích với schema mới.
8. Xác nhận mọi client đã được nâng cấp trước khi loại bỏ representation cũ.

Không nên giả định ALTER TABLE MODIFY enabled BOOLEAN có thể chạy an toàn cho mọi release hoặc mọi trạng thái dữ liệu. Dùng SQL Language Reference đúng phiên bản và thử migration trên bản sao dữ liệu.

### Chiến lược cột song song

Với hệ thống cần cutover an toàn, có thể cân nhắc:

- Thêm cột mới có kiểu đích.
- Backfill từ NUMBER(1) sang BOOLEAN.
- Dual-write tạm thời hoặc dùng trigger/logic chuyển đổi được kiểm soát.
- Đọc đối chiếu giữa hai cột.
- Chuyển ứng dụng sang cột mới.
- Sau cửa sổ rollback, loại bỏ cột cũ bằng migration riêng.

Đây là mẫu migration tổng quát; trigger và dual-write làm tăng độ phức tạp, cần tránh nếu có thể triển khai downtime ngắn và migration đơn giản hơn.

## 25. Identifier dài khi nâng cấp database

Giả sử database cũ dùng tên tối đa 30 byte. Một migration mới được viết trên database 23ai và tạo constraint dài 60 byte. Migration chạy tốt ở dev nhưng thất bại khi triển khai lên một PDB cũ có COMPATIBLE thấp hơn.

Hướng xử lý:

- Kiểm tra COMPATIBLE ở tất cả môi trường.
- Kiểm tra độ dài byte của tên table, column, index, constraint và sequence.
- Kiểm tra tên Hibernate tự sinh.
- Dùng naming convention chung.
- Không để tool tự tạo tên khác nhau giữa build.
- Kiểm thử migration trên database có mức tương thích thấp nhất được hỗ trợ.

Nếu đã có object với tên dài trên database mới, không tự đổi tên ở production mà chưa xem xét dependency, view, package, grants và ứng dụng ngoài.

## 26. Các lỗi thường gặp liên quan BOOLEAN và identifier

| Lỗi | Nguyên nhân thường gặp | Hướng kiểm tra |
|---|---|---|
| ORA-00902: invalid datatype | Database không hỗ trợ SQL BOOLEAN ở release/compatibility hiện tại | Xem release, COMPATIBLE và DDL |
| ORA-00972: identifier is too long | Identifier vượt giới hạn byte | Kiểm tra 30/128 byte, quoted name và naming strategy |
| ORA-00904: invalid identifier | Sai tên, case, quote hoặc cột chưa tồn tại | Xem dictionary và SQL thực tế |
| ORA-00933: SQL command not properly ended | Cú pháp mới chạy trên release cũ hoặc SQL sai | Xác nhận release và SQL Language Reference |
| ORA-00955: name is already used by an existing object | DDL tạo object đã tồn tại | Kiểm tra object và migration history |
| ORA-00942: table or view does not exist | Sai schema, thiếu grant hoặc object không tồn tại | Kiểm tra owner, synonym và container |
| Lỗi bind Boolean | JDBC driver/ORM mapping không tương thích | Kiểm tra driver, Hibernate dialect và SQL type |
| TRUE/FALSE bị đọc thành cùng một giá trị | Dùng getBoolean nhưng bỏ qua wasNull | Phân biệt NULL và FALSE |

Không chữa ORA-00972 bằng cách đổi COMPATIBLE ngay. Trước hết xác định database thực sự có hỗ trợ identifier dài không và tên nào cần rút gọn.

## 27. Test BOOLEAN trên Oracle thật

Một integration test nên kiểm tra insert, update, NULL và đọc lại:

~~~java
@Test
void persistsTrueFalseAndNullOnOracle() {
    FeatureFlag enabled = new FeatureFlag("flag-on", true);
    FeatureFlag disabled = new FeatureFlag("flag-off", false);

    repository.saveAndFlush(enabled);
    repository.saveAndFlush(disabled);
    entityManager.clear();

    assertThat(repository.findById(enabled.getId())
        .orElseThrow().getEnabled()).isTrue();
    assertThat(repository.findById(disabled.getId())
        .orElseThrow().getEnabled()).isFalse();
}
~~~

Nếu column cho phép NULL, bổ sung test NULL và kiểm tra wasNull ở JDBC hoặc entity Boolean. Nếu column NOT NULL, kiểm tra database từ chối NULL và default hoạt động như thiết kế.

Với database cũ dùng NUMBER(1), test thêm giá trị ngoài 0/1 phải bị CHECK constraint từ chối.

## 28. Test identifier và migration

Kiểm thử migration trên đúng Oracle release/compatibility:

- Tạo table và constraint bằng migration thật.
- Xác nhận object được tạo đúng owner.
- Kiểm tra tên có vượt giới hạn byte không.
- Chạy Hibernate ddl-auto=validate.
- Kiểm tra SQL sinh ra và native query.
- Chạy migration từ schema cũ lên schema mới.
- Chạy migration trên môi trường có COMPATIBLE thấp nhất được hỗ trợ.

Không chỉ kiểm tra migration chạy trên một database mới nhất. Môi trường thấp nhất trong ma trận hỗ trợ thường phát hiện lỗi version gate sớm nhất.

## 29. Quy tắc chọn cú pháp theo release

Trước khi dùng một cú pháp mới, xác định:

1. Release đầu tiên hỗ trợ cú pháp.
2. Có yêu cầu COMPATIBLE tối thiểu không.
3. Cú pháp có khác theo patch/Release Update không.
4. JDBC driver và ORM có hỗ trợ datatype/metadata tương ứng không.
5. Migration có cần chạy trên database cũ không.
6. Công cụ ETL, BI, backup, replication và ứng dụng ngoài có hiểu kiểu dữ liệu mới không.
7. Có kế hoạch rollback hoặc compatibility window không.

Một release mới có thể hỗ trợ cú pháp ở SQL engine nhưng driver hoặc ORM đang dùng vẫn chưa map đúng. Vì vậy, version support là một ma trận, không phải một con số.

## 31. Kết luận

Oracle Database 23c/23ai đưa SQL BOOLEAN vào SQL engine, trong khi các release cũ chỉ có BOOLEAN trong PL/SQL và thường phải biểu diễn trạng thái bằng NUMBER(1) hoặc CHAR(1). SQL BOOLEAN có TRUE, FALSE và UNKNOWN khi NULL được cho phép; ứng dụng JDBC/JPA phải giữ đúng khác biệt giữa FALSE và NULL.

Giới hạn identifier phổ biến là 30 byte ở mức tương thích cũ và 128 byte khi COMPATIBLE cho phép từ 12.2 trở lên. Độ dài tính theo byte, quoted identifier giữ case và có thể làm SQL khó bảo trì. Hibernate naming strategy và migration cần được kiểm tra để tránh ORA-00972.

Các cú pháp mới như IF [NOT] EXISTS trong DDL và SELECT không cần FROM DUAL giúp SQL gọn hơn trên release hỗ trợ. Khi ứng dụng cần chạy trên nhiều Oracle version, hãy chọn cú pháp chung, dùng migration theo release có kiểm soát và kiểm tra database version, COMPATIBLE, JDBC driver, Hibernate dialect cùng các client tích hợp. Không suy luận khả năng hỗ trợ chỉ từ banner hoặc việc câu lệnh chạy trên một môi trường development.
