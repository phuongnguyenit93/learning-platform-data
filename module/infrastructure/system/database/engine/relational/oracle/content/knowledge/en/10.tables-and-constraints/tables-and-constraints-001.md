# Translating Data Domains and Business Relationships into Oracle Tables

Designing Oracle tables does not start with the question "how many columns do we need?", but with **understanding which business domain the data belongs to, what a single row represents, how entities relate to one another, and which rules must remain valid as data changes**. If business requirements are translated into tables mechanically, it is easy to end up with an all-in-one table, repeat customer information on every order, store a list of products in a text column, or check foreign keys only in Java code. Those decisions make data hard to maintain, prone to inconsistency, and difficult to scale.

In Oracle Database, the relational model is implemented through **tables, columns, data types, primary keys, foreign keys, unique constraints, check constraints, not null**, and supporting structures. This lesson walks through a small sales example end-to-end: from a business requirement statement, entity and relationship design, writing Oracle DDL, inserting sample data, and querying across tables, to identifying rules that must be handled through transactions or business logic.

## 1. From Business Language to the Relational Model

Suppose the product owner gives this requirement:

> "The system stores customers and products. A customer can create multiple orders; each order belongs to exactly one customer. An order has multiple line items; each line item points to one product, recording quantity and unit price at the time of ordering. An order can have one finalized shipping address. A product can also be sold in multiple orders. An order has a status of draft, confirmed, or cancelled."

We should not write `CREATE TABLE` right away. First, we need to break it down:

| Element in Description | Question to Clarify | Potential Design Outcome |
|---|---|---|
| Customer | Which attributes identify a customer? | `CUSTOMER` entity |
| Product | What are the SKU, name, current price, and active sales status? | `PRODUCT` entity |
| Order | Which transaction does one order row represent? | `SALES_ORDER` entity |
| Order line item | Where do quantity and price of **each product in each order** belong? | Associative entity `ORDER_ITEM` |
| Finalized shipping address | Is this order-specific data that does not change when the customer profile changes? | `ORDER_SHIPPING` or a snapshot column group on the order |
| Order status | What are the valid values? Which status transitions are allowed? | `ORDER_STATUS` column, `CHECK`, and state-transition rules |

Not **every noun** is a table. For example, "address" can be a **value object** composed of multiple attributes; if the business only uses a single shipping address at the time the order is finalized, we can store snapshot columns in `SALES_ORDER` or extract `ORDER_SHIPPING` when there are lifecycle or access-control reasons. Meanwhile, "unit price at the time of ordering" is an attribute of the **order line item**, not merely a current attribute of the product.

A table should have a **clear purpose and grain**: *what does one row in the table represent?*

- `CUSTOMER`: one row = one customer.
- `PRODUCT`: one row = one product with its own SKU.
- `SALES_ORDER`: one row = one order.
- `ORDER_ITEM`: one row = one product line item in an order.
- `ORDER_SHIPPING`: one row = finalized shipping information for at most one order.

Without clearly stating the grain, it is very easy to double-count totals after a `JOIN` or mix data from different levels of detail.

## 2. Identifying Entities, Attributes, and Business Values

### 2.1. How Do Entities and Value Objects Differ?

An **entity** has an identity that persists over time: a customer remains the same customer even if their name changes; an order remains the same order even if its status changes. In a database, an entity usually requires a stable key.

A **value object** is identified primarily by its **value**: money with amount and currency unit, an address with its components, a date range with two endpoints. A value object does not necessarily require its own table. The decision to extract a table depends on independence, query requirements, cardinality, relationships, access permissions, history tracking requirements, and change cost.

For instance, if the system allows each customer to register multiple addresses and mark a default address, that can be a `CUSTOMER_ADDRESS` entity linked to `CUSTOMER` in a 1:N relationship. However, the **shipping address of an already placed order** usually needs to remain unchanged even if the customer updates their profile address. Therefore, an order can store an address **snapshot**, rather than only referencing the current profile address.

### 2.2. Distinguishing Technical Keys and Business Keys

In our example:

- `CUSTOMER_ID`: technical key, generated by the database, used for foreign keys.
- `CUSTOMER_CODE`: business code, must be unique within the defined scope.
- `PRODUCT_ID`: technical key of the product.
- `SKU`: business-defined product code, needs to be unique per catalog rules.
- `ORDER_ID`: technical key of the order.
- `ORDER_NUMBER`: order code used in the UI, lookup, and integrations.

A **natural key** is an attribute or group of attributes with business meaning, such as SKU. A **surrogate key** is a technical key carrying no business meaning, such as the identity column `PRODUCT_ID`.

A technical key is suitable when a business key might change or is long/complex. However, using a surrogate key **does not exempt** you from applying `UNIQUE` to the business key if the business requires uniqueness. If only `CUSTOMER_ID` is the primary key, Oracle can still allow two rows with the same `CUSTOMER_CODE` unless there is a unique constraint or another enforcement mechanism.

## 3. Reading Cardinality and Optionality Before Writing Foreign Keys

**Cardinality** describes how many records can be related; **optionality** indicates whether a relationship is mandatory or not. Notations such as `1`, `0..1`, `0..N`, `1..N` must be stated from **both sides**, because "a customer has orders" is not enough to determine whether a customer is required to have at least one order.

| Relationship | Business Interpretation | Common Modeling Approach |
|---|---|---|
| **1:N** | Each order belongs to exactly one customer; a customer can have 0..N orders | `SALES_ORDER.CUSTOMER_ID NOT NULL` referencing `CUSTOMER` |
| **0..1:1** | An order has at most one shipping record; it may not exist while in draft | `ORDER_SHIPPING.ORDER_ID` as both `PRIMARY KEY` and `FOREIGN KEY` |
| **N:M** | An order has multiple products; a product can belong to multiple orders | Associative table `ORDER_ITEM` with two foreign keys and relationship attributes |
| **1:N with nullable FK** | An employee may not have a manager yet | `EMPLOYEE.MANAGER_ID NULL` referencing `EMPLOYEE` |
| **Pure N:M** | A student enrolls in many courses; a course has many students | `ENROLLMENT(STUDENT_ID, COURSE_ID)` with a composite key |

Sales domain diagram:

~~~text
      CUSTOMER                           PRODUCT
   [CUSTOMER_ID]                       [PRODUCT_ID]
        │                                    │
        │ 1                                  │ 1
        │                                    │
        │ 0..N                               │ 0..N
        ▼                                    ▼
    SALES_ORDER 1 ─────── 0..N ORDER_ITEM N..0 ──── PRODUCT
     [ORDER_ID]              [ORDER_ID, LINE_NO]
        │                     [PRODUCT_ID]
        │ 1                   [QUANTITY]
        │                     [UNIT_PRICE_AT_ORDER]
        │ 0..1
        ▼
   ORDER_SHIPPING
   [ORDER_ID = PK + FK]
~~~

Reading the diagram in business terms: an order must have a customer; a customer may never have made a purchase. A newly created order may not yet have line items or a shipping address, but when transitioning to the confirmed status, the business may require at least one line item and one address. **Minimum conditions that depend on status like this cannot be solved with FK and NOT NULL alone.**

## 4. Mapping Relationship Types to Oracle Tables

### 4.1. One-to-Many Relationship (1:N)

Place the **foreign key on the many side**. For customers and orders:

~~~text
CUSTOMER.CUSTOMER_ID          PK
           ▲
           │ FK
SALES_ORDER.CUSTOMER_ID       NOT NULL
~~~

`NOT NULL` forces every order to point to a customer. The foreign key forces that value to exist in the customer table while the constraint is enforced. Conversely, **you should not store a list of `ORDER_ID` values inside a column of `CUSTOMER`**.

For the relationship to allow 0..N orders per customer, do not add a unique constraint on `SALES_ORDER.CUSTOMER_ID`. If you put `UNIQUE(CUSTOMER_ID)` on the order table, each customer can have at most one order and the model diverges from the requirement.

### 4.2. Many-to-Many Relationship (N:M)

A `PRODUCT_IDS = '11,17,25'` column in `SALES_ORDER` makes it hard to constrain that each product exists, hard to update quantities, hard to build standard indexes, and hard to write joins. Instead, we use an **associative (junction) table**:

~~~text
SALES_ORDER ───< ORDER_ITEM >─── PRODUCT
                ORDER_ID       (FK)
                LINE_NO        (line position in the order)
                PRODUCT_ID     (FK)
                QUANTITY
                UNIT_PRICE_AT_ORDER_VND
~~~

`ORDER_ITEM` does not merely link two tables: it represents an **event/relationship with its own attributes**, including quantity and price at the time of ordering. This data cannot live solely on `PRODUCT`, because the same product can be ordered with different quantities, unit prices, and discounts across different orders.

There are two common ways to choose a key for an associative table:

- **Composite key**: `PRIMARY KEY(ORDER_ID, LINE_NO)` if each order numbers its lines 1, 2, 3...
- **Surrogate key**: `ORDER_ITEM_ID` as the primary key, plus a unique constraint on the business combination if needed.

In our example, we use the composite key `(ORDER_ID, LINE_NO)`. If the business specifies that *each product may appear only once per order*, you can add `UNIQUE(ORDER_ID, PRODUCT_ID)`. If the same SKU is allowed to appear on two lines with different promotions or warehouse allocations, **do not** add that unique constraint. This is a business decision; there is no one-size-fits-all answer.

### 4.3. One-to-One Relationship (1:1)

If `ORDER_SHIPPING` holds shipping information at the single-order level, you can use:

~~~text
SALES_ORDER.ORDER_ID                 PRIMARY KEY
               ▲
               │
ORDER_SHIPPING.ORDER_ID              PRIMARY KEY + FOREIGN KEY
~~~

The primary key of `ORDER_SHIPPING` ensures that **each order_id appears at most once**. The FK ensures the corresponding order exists. However, having no row in `ORDER_SHIPPING` is still valid: this is a **0..1 shipping record per order** relationship.

If the business requires **every order** to always have an address, consider placing the mandatory address columns directly in `SALES_ORDER`, or using transaction logic to ensure that confirming an order requires a shipping row. Splitting into a 1:1 table is only worthwhile if there are lifecycle, access-control, optional-attribute, or operational reasons.

### 4.4. Self-Referencing Relationship

An employee may report to another employee. Model:

~~~sql
CREATE TABLE lab_employee (
  employee_id NUMBER GENERATED ALWAYS AS IDENTITY,
  display_name VARCHAR2(100 CHAR) NOT NULL,
  manager_id NUMBER,
  CONSTRAINT pk_lab_employee PRIMARY KEY (employee_id),
  CONSTRAINT fk_lab_employee_manager
    FOREIGN KEY (manager_id) REFERENCES lab_employee (employee_id),
  CONSTRAINT ck_lab_employee_not_self
    CHECK (manager_id IS NULL OR manager_id <> employee_id)
);
~~~

A nullable `MANAGER_ID` expresses that an employee may have no manager. `CHECK` prevents an employee from directly managing themselves, but **does not prevent longer cycles**, such as A managing B and B managing A. If the business requires an acyclic management tree, additional controls are needed, typically placed in transaction-managed update logic.

## 5. From Business Rules to Oracle Constraints

Each constraint should map to a specific rule statement. Do not just create columns and rely on developers remembering to check them.

| Business Rule | Appropriate Oracle Mechanism | Distinction to Keep in Mind |
|---|---|---|
| Each order has a unique identifier | `PRIMARY KEY` | PK is always unique and not null |
| Customer code cannot duplicate | `UNIQUE(CUSTOMER_CODE)` plus `NOT NULL` if required | Unique on nullable columns has NULL behavior to understand carefully |
| Every order belongs to a real customer | `FOREIGN KEY(CUSTOMER_ID) REFERENCES CUSTOMER` | Must reference a PK or unique key on the target |
| An order must have a customer | `CUSTOMER_ID NOT NULL` | FK alone does not make a column mandatory |
| Quantity must be greater than 0 | `CHECK(QUANTITY > 0)` plus `NOT NULL` | CHECK alone does not reject NULL |
| Unit price is non-negative | `CHECK(UNIT_PRICE_AT_ORDER_VND >= 0)` | Also need to choose appropriate numeric precision |
| Status must belong to a fixed set | `CHECK(ORDER_STATUS IN (...))` | Does not enforce state-transition ordering |
| Name/address must contain meaningful data | `NOT NULL` and appropriate content validation | Empty strings are treated as NULL by Oracle; whitespace-only strings can still be stored |
| A confirmed order must have at least one line item | Usually requires transaction/business logic or advanced mechanisms | A standard FK cannot count child rows |
| Order total equals sum of line items | Computed/queried or controlled synchronization mechanism | CHECK cannot query multiple rows or other tables |

### 5.1. Oracle Characteristics to Remember

**NOT NULL and CHECK are different.** In SQL, a CHECK condition generally rejects rows when the expression evaluates to **FALSE**, whereas an **UNKNOWN result caused by NULL** may be accepted. Therefore, `CHECK(quantity > 0)` does not by itself forbid `NULL`; add `NOT NULL` whenever the data is mandatory.

**UNIQUE and NULL.** With a unique constraint on **a single nullable column**, Oracle allows multiple rows to contain `NULL`. If a business key is mandatory, also use `NOT NULL`. For multi-column unique constraints, Oracle has specific rules for how combinations containing NULL are handled; do not assume "any NULL is completely unconstrained."

**CHECK is not a procedural program.** Do not try to put subqueries or logic referencing other rows into CHECK as a substitute for cross-table constraints. Rules depending on multi-row state require additional design.

**DEFAULT is not pre-existing data.** A default applies during corresponding insert contexts; it does not retroactively fix old data and does not replace `NOT NULL`. A default status of `DRAFT` helps when creating new orders, but that status must still be within the domain allowed by CHECK.

**Constraints are part of data protection.** Even if a Java application performs pre-checks, database constraints are still needed to prevent two concurrent transactions from writing invalid data. Checking "code does not exist yet" and then inserting in Java cannot completely avoid race conditions without a unique constraint.

## 6. Choosing Data Types Before Creating Tables

In the sales example, we apply clear choices:

| Attribute | Illustrative Oracle Type | Rationale |
|---|---|---|
| Technical ID | `NUMBER GENERATED ALWAYS AS IDENTITY` | Oracle generates the key, independent of business codes |
| Customer code / SKU / order number | `VARCHAR2(n CHAR)` | Can contain letters and hyphens; preserves leading zeros |
| Display name | `VARCHAR2(n CHAR)` | Character-based length, suitable for multilingual names |
| Quantity | `NUMBER(9,0)` | Integer quantity domain with bounded range |
| Price in VND | `NUMBER(15,0)` | Illustrative convention for integer Vietnamese Dong; validate input before writing |
| Status | `VARCHAR2(20 CHAR)` with CHECK | Stable, human-readable code set |
| Active sales flag | `CHAR(1 CHAR)`, `Y/N` with CHECK | Portable across Oracle versions, controlled values |
| Creation timestamp | `TIMESTAMP(6) WITH TIME ZONE` | Records instant with timezone/offset information |

Here, **all prices are in VND and stored as integers** under an intentional assumption. If a system must support multiple currencies or decimal places, the model must add `CURRENCY_CODE`, choose appropriate precision/scale, and clearly define conversion/rounding rules. Do not define an ambiguous `NUMBER` and leave each application to guess the unit.

**Note:** `NUMBER(9,0)` or `NUMBER(15,0)` can **round** source values if the input has a fractional part. Even though the column only stores integers, preventing an input like `1.5` from becoming `2` must be handled in parsing/validation if the business forbids rounding.

## 7. Complete Oracle DDL: From Model to Tables

The statements below use Oracle Database syntax supporting **identity columns** (Oracle 12c and later) and are executed in a **practice PDB schema**. You need table creation privileges and appropriate tablespace quota. Run in a clean schema where the `LAB_*` names do not yet exist.

### 7.1. Customer Table

~~~sql
CREATE TABLE lab_customer (
  customer_id   NUMBER GENERATED ALWAYS AS IDENTITY,
  customer_code VARCHAR2(30 CHAR) NOT NULL,
  display_name  VARCHAR2(150 CHAR) NOT NULL,
  email         VARCHAR2(200 CHAR),
  created_at    TIMESTAMP(6) WITH TIME ZONE
                  DEFAULT SYSTIMESTAMP NOT NULL,

  CONSTRAINT pk_lab_customer PRIMARY KEY (customer_id),
  CONSTRAINT uq_lab_customer_code UNIQUE (customer_code)
);
~~~

`CUSTOMER_ID` is the surrogate key; `CUSTOMER_CODE` is the mandatory and unique business key. `EMAIL` is nullable because our example does not require every customer to provide an email. **Do not arbitrarily place unique(email)** before confirming with the business: an email might be a shared address, and case-insensitive comparison requires explicit rules.

### 7.2. Product Table

~~~sql
CREATE TABLE lab_product (
  product_id     NUMBER GENERATED ALWAYS AS IDENTITY,
  sku            VARCHAR2(40 CHAR) NOT NULL,
  product_name   VARCHAR2(200 CHAR) NOT NULL,
  unit_price_vnd NUMBER(15,0) NOT NULL,
  active_flag    CHAR(1 CHAR) DEFAULT 'Y' NOT NULL,

  CONSTRAINT pk_lab_product PRIMARY KEY (product_id),
  CONSTRAINT uq_lab_product_sku UNIQUE (sku),
  CONSTRAINT ck_lab_product_price CHECK (unit_price_vnd >= 0),
  CONSTRAINT ck_lab_product_active CHECK (active_flag IN ('Y', 'N'))
);
~~~

`UNIT_PRICE_VND` here is the **current product price**. Past orders must keep the price finalized in `ORDER_ITEM.UNIT_PRICE_AT_ORDER_VND`; if they only referenced the current price, updating the product table would corrupt historical totals. `ACTIVE_FLAG = 'N'` can be used to discontinue selling a product while preserving foreign keys from historical orders.

### 7.3. Sales Order Table: Many Orders per Customer

~~~sql
CREATE TABLE lab_sales_order (
  order_id      NUMBER GENERATED ALWAYS AS IDENTITY,
  order_number  VARCHAR2(40 CHAR) NOT NULL,
  customer_id   NUMBER NOT NULL,
  order_status  VARCHAR2(20 CHAR) DEFAULT 'DRAFT' NOT NULL,
  created_at    TIMESTAMP(6) WITH TIME ZONE
                  DEFAULT SYSTIMESTAMP NOT NULL,

  CONSTRAINT pk_lab_sales_order PRIMARY KEY (order_id),
  CONSTRAINT uq_lab_sales_order_number UNIQUE (order_number),
  CONSTRAINT fk_lab_sales_order_customer
    FOREIGN KEY (customer_id)
    REFERENCES lab_customer (customer_id),
  CONSTRAINT ck_lab_sales_order_status
    CHECK (order_status IN ('DRAFT', 'CONFIRMED', 'CANCELLED'))
);
~~~

`SALES_ORDER.CUSTOMER_ID NOT NULL` combined with the foreign key ensures each order points to a valid customer. `ORDER_NUMBER` is unique to avoid two orders having the same business code. Oracle cannot enforce transition sequences—such as whether moving from `CANCELLED` back to `CONFIRMED` is allowed—using `CHECK IN` alone; that rule belongs to transaction/service handling.

### 7.4. Order Item Table: Turning N:M into an Associative Entity

~~~sql
CREATE TABLE lab_order_item (
  order_id                NUMBER NOT NULL,
  line_no                 NUMBER(5,0) NOT NULL,
  product_id              NUMBER NOT NULL,
  quantity                NUMBER(9,0) NOT NULL,
  unit_price_at_order_vnd NUMBER(15,0) NOT NULL,

  CONSTRAINT pk_lab_order_item
    PRIMARY KEY (order_id, line_no),

  CONSTRAINT fk_lab_order_item_order
    FOREIGN KEY (order_id)
    REFERENCES lab_sales_order (order_id),

  CONSTRAINT fk_lab_order_item_product
    FOREIGN KEY (product_id)
    REFERENCES lab_product (product_id),

  CONSTRAINT ck_lab_order_item_line_no
    CHECK (line_no >= 1),

  CONSTRAINT ck_lab_order_item_quantity
    CHECK (quantity > 0),

  CONSTRAINT ck_lab_order_item_price
    CHECK (unit_price_at_order_vnd >= 0)
);
~~~

The composite key `(ORDER_ID, LINE_NO)` requires line items within the same order to have distinct sequence numbers. `PRODUCT_ID` is not part of the PK, because the same product **can be ordered across multiple orders**. If each product may appear on only one line per order, add:

~~~sql
-- Add only if the business forbids the same SKU appearing on multiple lines of the same order.
ALTER TABLE lab_order_item
  ADD CONSTRAINT uq_lab_order_item_product
  UNIQUE (order_id, product_id);
~~~

That constraint is **optional**. The main example does not apply it yet, because some systems split the same product across multiple lines due to different discounts, delivery batches, or fulfillment warehouses.

### 7.5. Order Shipping Table: 0..1:1

~~~sql
CREATE TABLE lab_order_shipping (
  order_id       NUMBER NOT NULL,
  recipient_name VARCHAR2(150 CHAR) NOT NULL,
  address_text   VARCHAR2(500 CHAR) NOT NULL,

  CONSTRAINT pk_lab_order_shipping PRIMARY KEY (order_id),
  CONSTRAINT fk_lab_order_shipping_order
    FOREIGN KEY (order_id)
    REFERENCES lab_sales_order (order_id)
);
~~~

A shipping row can only exist if a corresponding order exists. Because `ORDER_ID` is the PK of `LAB_ORDER_SHIPPING`, you cannot create two separate shipping addresses for the same order in this table. However, an order **may have no shipping row yet**; when confirming the order, the application must verify the corresponding business condition.

### 7.6. Indexes Supporting Key Foreign Keys

PK and unique constraints are normally backed by an appropriate index in Oracle. **A foreign key does not automatically get its own separate index simply because an FK exists.** For frequent join queries and parent key delete/update operations, consider:

~~~sql
CREATE INDEX ix_lab_sales_order_customer
  ON lab_sales_order (customer_id);

CREATE INDEX ix_lab_order_item_product
  ON lab_order_item (product_id);
~~~

The composite primary key `(ORDER_ID, LINE_NO)` already has an index structure leading with `ORDER_ID`, so creating a separate `ORDER_ID` index on `LAB_ORDER_ITEM` is unnecessary. Whether to add an index depends on data volume, execution plans, and workload characteristics; every index also increases write and storage overhead.

## 8. Inserting Sample Data in Relationship Order

Because FKs require the parent record to exist, the insertion flow in this example is **customer/product → order → order items/shipping address**. Oracle identity columns generate the technical IDs; when linking rows, we can look up records by their unique business keys or use JDBC/PLSQL mechanisms to retrieve the generated ID after insert.

~~~sql
-- 1. Master/catalog data.
INSERT INTO lab_customer (customer_code, display_name, email)
VALUES ('CUS-001', 'Sample Customer', 'customer@example.invalid');

INSERT INTO lab_product (sku, product_name, unit_price_vnd)
VALUES ('SKU-KEYBOARD', 'Sample Keyboard', 450000);

INSERT INTO lab_product (sku, product_name, unit_price_vnd)
VALUES ('SKU-MOUSE', 'Sample Mouse', 200000);

-- 2. Order pointing to a valid CUSTOMER_ID.
INSERT INTO lab_sales_order (order_number, customer_id)
SELECT 'SO-0001', customer_id
FROM lab_customer
WHERE customer_code = 'CUS-001';

-- 3. Add products to the order, capturing current price as a snapshot.
INSERT INTO lab_order_item (
  order_id, line_no, product_id, quantity, unit_price_at_order_vnd
)
SELECT o.order_id, 1, p.product_id, 2, p.unit_price_vnd
FROM lab_sales_order o
CROSS JOIN lab_product p
WHERE o.order_number = 'SO-0001'
  AND p.sku = 'SKU-KEYBOARD';

INSERT INTO lab_order_item (
  order_id, line_no, product_id, quantity, unit_price_at_order_vnd
)
SELECT o.order_id, 2, p.product_id, 1, p.unit_price_vnd
FROM lab_sales_order o
CROSS JOIN lab_product p
WHERE o.order_number = 'SO-0001'
  AND p.sku = 'SKU-MOUSE';

-- 4. Record the order's shipping snapshot.
INSERT INTO lab_order_shipping (
  order_id, recipient_name, address_text
)
SELECT order_id, 'Sample Recipient', 'Sample shipping address'
FROM lab_sales_order
WHERE order_number = 'SO-0001';

COMMIT;
~~~

The email `example.invalid`, names, and address above are **dummy data only**. Never put real customer data in a lab exercise. These `INSERT ... SELECT` statements rely on business keys with unique constraints. When re-running the entire script, you may hit unique errors because the data already exists; in real systems, use versioned migrations/seeds, idempotent scripts, or reset the dedicated lab schema.

### 8.1. Viewing the Order and Line Item Values

~~~sql
SELECT
  o.order_number,
  c.customer_code,
  o.order_status,
  i.line_no,
  p.sku,
  i.quantity,
  i.unit_price_at_order_vnd,
  i.quantity * i.unit_price_at_order_vnd AS line_amount_vnd
FROM lab_sales_order o
JOIN lab_customer c
  ON c.customer_id = o.customer_id
JOIN lab_order_item i
  ON i.order_id = o.order_id
JOIN lab_product p
  ON p.product_id = i.product_id
WHERE o.order_number = 'SO-0001'
ORDER BY i.line_no;
~~~

Logical result:

| ORDER_NUMBER | SKU | QUANTITY | UNIT_PRICE_AT_ORDER_VND | LINE_AMOUNT_VND |
|---|---|---:|---:|---:|
| `SO-0001` | `SKU-KEYBOARD` | 2 | 450000 | 900000 |
| `SO-0001` | `SKU-MOUSE` | 1 | 200000 | 200000 |

The order total across the two lines is **1,100,000 VND**, assuming no taxes, discounts, or shipping fees. If the business requires those components, appropriate data fields, calculation rules, and snapshots must be added; never assume every total is a simple price × quantity multiplication.

### 8.2. Computing Order Total from Line Items

~~~sql
SELECT
  o.order_number,
  NVL(SUM(i.quantity * i.unit_price_at_order_vnd), 0)
    AS item_total_vnd
FROM lab_sales_order o
LEFT JOIN lab_order_item i
  ON i.order_id = o.order_id
WHERE o.order_number = 'SO-0001'
GROUP BY o.order_number;
~~~

`LEFT JOIN` still shows an order that has no line items yet; `SUM` over an empty set returns `NULL`, so `NVL(..., 0)` converts it to 0 for display/calculation per this example's convention. If the application requires a confirmed order to have line items, check that condition separately.

### 8.3. Why Store Price at Order Time?

Suppose after the order is created, the price of `SKU-KEYBOARD` changes from 450000 to 500000:

~~~sql
UPDATE lab_product
SET unit_price_vnd = 500000
WHERE sku = 'SKU-KEYBOARD';

COMMIT;
~~~

The **current** price in `LAB_PRODUCT` has changed. However, `LAB_ORDER_ITEM.UNIT_PRICE_AT_ORDER_VND` on the old order remains **450000**, so historical reports remain accurate. This is a case of **intentional snapshot storage**: although there are technically two price columns, they carry two different temporal semantics, not useless duplication.

## 9. Observing Constraints Protecting Data Directly

In an isolated lab schema, you can run **deliberately invalid** statements to observe how the different constraints behave. Run each example separately; each failing statement will not insert a row.

### 9.1. Foreign Key: No Matching Customer

~~~sql
-- CUSTOMER_ID = -99999 is assumed not to exist in the lab.
INSERT INTO lab_sales_order (order_number, customer_id)
VALUES ('SO-ORPHAN', -99999);
~~~

Oracle rejects this when the FK is enabled/enforced; the typical error is `ORA-02291: integrity constraint violated - parent key not found`. If you only check "does the customer exist" in Java and omit the FK, another client can still insert an orphan order.

### 9.2. Duplicate Business Key

~~~sql
INSERT INTO lab_customer (customer_code, display_name)
VALUES ('CUS-001', 'Duplicate code customer');
~~~

The unique constraint `UQ_LAB_CUSTOMER_CODE` rejects existing codes, typically raising `ORA-00001`. Oracle enforces uniqueness under concurrency; a `SELECT` "check if absent" before `INSERT` in the application cannot replace a unique constraint.

### 9.3. Out-of-Domain Value

~~~sql
INSERT INTO lab_product (
  sku, product_name, unit_price_vnd, active_flag
)
VALUES ('SKU-NEGATIVE', 'Invalid product', -100, 'Y');
~~~

`CHECK(unit_price_vnd >= 0)` rejects negative prices, typically raising `ORA-02290`. Similarly, `ACTIVE_FLAG = 'Z'` is rejected by `CHECK(active_flag IN ('Y','N'))`.

### 9.4. Missing Mandatory Data

~~~sql
INSERT INTO lab_product (sku, product_name, unit_price_vnd)
VALUES ('SKU-NONAME', NULL, 100000);
~~~

`PRODUCT_NAME NOT NULL` rejects null values, typically raising `ORA-01400`. Oracle also treats an empty character string `''` as NULL in standard string contexts; however, a string consisting only of spaces is still a non-null value and requires business validation if disallowed.

### 9.5. Violating the Order Item Composite Key

Inserting another row with an existing `(ORDER_ID, LINE_NO)` violates `PK_LAB_ORDER_ITEM`, even if `PRODUCT_ID` differs. This confirms that **line numbers are unique within each order**, rather than globally unique across the entire database.

## 10. Model Normalization and Permitted Redundancy

### 10.1. What Is Wrong with an "All-in-One" Table?

A common initial design looks like:

~~~text
ORDER_FLAT(
  ORDER_NUMBER,
  CUSTOMER_CODE,
  CUSTOMER_NAME,
  PRODUCT_1,
  QTY_1,
  PRODUCT_2,
  QTY_2,
  PRODUCT_3,
  QTY_3,
  ...
)
~~~

Problems:

- Supports only a fixed number of products, or requires continually adding columns.
- Customer data is duplicated across every order; renaming a customer requires updating many rows.
- Hard to add foreign keys for each `PRODUCT_n` and hard to aggregate sales by product.
- Insert/update/delete operations can cause **anomalies**: updating one copy while missing others.

A relational model splitting `CUSTOMER`, `PRODUCT`, `SALES_ORDER`, and `ORDER_ITEM`, with foreign keys enforcing references, solves a large share of these issues.

### 10.2. Understanding Normalization Properly

- **1NF:** organize values and rows relationally; avoid repeating column groups like `PRODUCT_1, PRODUCT_2` or comma-separated ID lists in a single column in place of relationships.
- **2NF:** when a table has a composite key, non-key attributes should not depend on **only part** of the key if they truly belong to another entity. For example, product name belongs to `PRODUCT_ID`, not to the entire `(ORDER_ID, LINE_NO)` key in the order item table.
- **3NF:** non-key attributes should not depend transitively on the key through another non-key attribute when that belongs to a different entity. For example, `CUSTOMER_NAME` originates in `CUSTOMER` and should not be repeated as current profile info in every `SALES_ORDER`.

This is a practical understanding; when formal normalization proofs are required, all **functional dependencies** and candidate keys of the table must be thoroughly identified.

### 10.3. Intentional Denormalization: Historical Snapshots

`ORDER_ITEM.UNIT_PRICE_AT_ORDER_VND` and `PRODUCT.UNIT_PRICE_VND` are both prices, yet one represents the **locked transaction price** and the other represents the **current catalog price**. They cannot replace each other.

Similarly, order shipping info must reflect the **address finalized for that order**, avoiding changes when the customer edits their profile address. This is not an argument for arbitrarily copying all customer fields into every table. Store a snapshot only when the business truly requires **history to remain unaffected by changes to current source data**, and clearly define who updates the snapshot and when.

## 11. Relationships and Business Rules Beyond Simple Constraints

### 11.1. Valid Statuses vs. Valid Status Transitions

`CHECK(ORDER_STATUS IN ('DRAFT','CONFIRMED','CANCELLED'))` only checks whether **a value belongs to a set**. It cannot enforce the rule:

~~~text
DRAFT ─────────▶ CONFIRMED
  │                   │
  └────────▶ CANCELLED ◀────────┘

CANCELLED cannot return to CONFIRMED.
CONFIRMED must have at least one ORDER_ITEM.
~~~

The confirmation flow typically requires a transaction:

1. Lock or apply concurrency control on the order to be updated.
2. Verify the current status permits the transition.
3. Verify at least one product line item and a shipping address if required by the business.
4. Validate price, quantity, inventory/payment when covered by business rules.
5. Update the status and commit all related changes together; roll back if any check fails.

Multi-table checks must consider **concurrency**: two requests modifying the same order concurrently can observe different data if they only execute separate SELECT statements. Business logic and transaction isolation/locking must be designed for this scenario. Never treat a simple trigger running `SELECT COUNT` at an arbitrary moment as an automatic solution for every cross-table invariant.

### 11.2. Requiring at Least One Child Row

The FK `ORDER_ITEM.ORDER_ID → SALES_ORDER.ORDER_ID` ensures *no orphan order items*. It does **not** ensure every order has items. A row-level constraint on `SALES_ORDER` also cannot simply check "item count > 0" using a subquery.

If the rule only applies to `CONFIRMED` orders, keep `DRAFT` orders valid without items and perform the check inside the status-transition transaction. If the system has multiple write paths (API, import, batch, direct SQL), unify the enforcement boundary rather than placing it in only a single Java screen.

### 11.3. Conditional Uniqueness

For example, "email only needs to be unique among active accounts" does not equate to a simple unique constraint on the `EMAIL` column. A **function-based unique index** or an alternative data organization can be considered if the Oracle version and domain permit it. This is an advanced design requiring clear rules for NULL handling, case sensitivity, whitespace normalization, and concurrent inserts/updates.

Do not add a unique constraint merely based on observing that current sample data has no duplicates. You must ask **whether the business allows duplicates in the future**, and whether the uniqueness scope is a PDB, a tenant, an organization, or the entire system.

### 11.4. Time-Dependent Rules

A customer may have multiple addresses over effective periods. Beyond an FK, you must decide whether two time intervals are allowed to overlap, how interval endpoints are represented, and how concurrent transactions are handled. Oracle provides temporal data types and supporting features, but modeling effective-date boundaries does not happen automatically just by adding `VALID_FROM` and `VALID_TO` columns.

## 12. Delete and Update Strategies for Relationships

Once a customer has orders, deleting the customer can destroy historical context. By default, Oracle FKs block deleting a parent key while referencing child rows still exist, unless another behavior is configured or the constraint is no longer active.

| Approach | Effect | When to Consider |
|---|---|---|
| **Keep default FK behavior** | Blocks deleting a parent referenced by children; typically raises `ORA-02292` | Historical data is important; cascading deletes are unwanted |
| **`ON DELETE CASCADE`** | Deleting parent also deletes related child rows | Child depends completely on parent and has no independent existence, e.g., temporary auxiliary tables |
| **`ON DELETE SET NULL`** | When parent is deleted, child FK becomes NULL | Relationship must be **nullable** and business allows a child without a parent |
| **Soft delete / inactive flag** | Keeps the record and key, changes active status | Catalogs/customers with transaction history that must be retained |

Illustrative Oracle syntax for an optional relationship:

~~~sql
-- Conceptual example for a supporting table; manager_id must be nullable.
FOREIGN KEY (manager_id)
REFERENCES lab_employee (employee_id)
ON DELETE SET NULL
~~~

Oracle supports `ON DELETE CASCADE` and `ON DELETE SET NULL` for FKs with appropriate syntax, but **does not have a built-in `ON UPDATE CASCADE` FK clause common in some other RDBMSs**. Using stable technical keys and avoiding PK updates is the standard strategy. If a business key changes, handle it as a business attribute without having to update foreign keys across many tables.

**Do not enable cascade out of habit.** Deleting a `PRODUCT` should not erase historical order line items; deleting a `CUSTOMER` should not automatically wipe out all orders when audit/accounting records must be retained. Deletion policy is a business, legal, and operational decision—not merely a syntax choice.

## 13. Inspecting the Actual Model via the Oracle Data Dictionary

After creating tables in the target schema/PDB, you can query metadata to see **what the database model is actually enforcing**. First, verify the session context:

~~~sql
SELECT
  SYS_CONTEXT('USERENV', 'DB_NAME') AS database_name,
  SYS_CONTEXT('USERENV', 'CON_NAME') AS container_name,
  SYS_CONTEXT('USERENV', 'SESSION_USER') AS session_user,
  SYS_CONTEXT('USERENV', 'CURRENT_SCHEMA') AS current_schema
FROM dual;
~~~

In a CDB/PDB architecture, relationships and application data are scoped to the selected PDB/schema. Identical table names across two PDBs do not automatically imply an FK or shared data between them.

### 13.1. Viewing Tables and Columns

~~~sql
SELECT table_name
FROM user_tables
WHERE table_name LIKE 'LAB_%'
ORDER BY table_name;

SELECT
  table_name, column_id, column_name,
  data_type, nullable
FROM user_tab_columns
WHERE table_name IN (
  'LAB_CUSTOMER', 'LAB_PRODUCT',
  'LAB_SALES_ORDER', 'LAB_ORDER_ITEM', 'LAB_ORDER_SHIPPING'
)
ORDER BY table_name, column_id;
~~~

`USER_*` reflects objects owned by the current user. To inspect tables in another schema you are permitted to see, use the `ALL_*` views filtered by `OWNER`; the `DBA_*` views require appropriate catalog privileges.

### 13.2. Viewing PK, FK, UNIQUE, and CHECK Constraints

~~~sql
SELECT
  c.table_name,
  c.constraint_name,
  c.constraint_type,
  c.status,
  c.validated,
  cc.column_name,
  cc.position
FROM user_constraints c
JOIN user_cons_columns cc
  ON cc.constraint_name = c.constraint_name
 AND cc.table_name = c.table_name
WHERE c.table_name IN (
  'LAB_CUSTOMER', 'LAB_PRODUCT',
  'LAB_SALES_ORDER', 'LAB_ORDER_ITEM', 'LAB_ORDER_SHIPPING'
)
ORDER BY c.table_name, c.constraint_name, cc.position;
~~~

`CONSTRAINT_TYPE` typically uses `P` for primary key, `R` for referential/foreign key, `U` for unique, and `C` for check (including NOT NULL representations in the catalog). `STATUS` and `VALIDATED` indicate whether the constraint is currently enabled and whether existing data has been validated according to administrative state. A `DISABLED` or `NOVALIDATED` constraint does not provide the same guarantee as an `ENABLED VALIDATED` constraint.

### 13.3. Retrieving FK Relationships and Target Tables

~~~sql
SELECT
  child.table_name AS child_table,
  child.constraint_name AS fk_name,
  parent.table_name AS parent_table,
  parent.constraint_name AS parent_key_name
FROM user_constraints child
JOIN user_constraints parent
  ON parent.constraint_name = child.r_constraint_name
 AND parent.owner = child.r_owner
WHERE child.constraint_type = 'R'
  AND child.table_name LIKE 'LAB_%'
ORDER BY child.table_name, child.constraint_name;
~~~

This query maps relationships from the child table's constraint to the parent table's PK/unique constraint. When you need an ERD accurate down to **columns**, join `USER_CONS_COLUMNS` for both the FK and the referenced key ordered by `POSITION`, especially for composite keys. **Matching column names do not prove an FK exists**; only constraint metadata or DDL proves that the database enforces the relationship.

## 14. From Model to Java/JPA Applications and Migrations

A Java system may use JPA/Hibernate to map entities, but you must distinguish **relationships in the Java object graph** from **constraints in Oracle**.

Example:

~~~java
@Entity
@Table(name = "LAB_SALES_ORDER")
public class SalesOrder {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @Column(name = "ORDER_ID")
    private Long id;

    @ManyToOne(optional = false, fetch = FetchType.LAZY)
    @JoinColumn(name = "CUSTOMER_ID", nullable = false)
    private Customer customer;
}
~~~

This snippet illustrates the mapping; running it in practice requires a `Customer` class and corresponding Jakarta Persistence/driver configuration. `@ManyToOne` describes object relationships and how the ORM accesses them; **an FK created and enforced in Oracle** is what also protects changes coming from SQL scripts, batch jobs, ETL tools, or other applications. Cascade options in JPA do not map one-to-one with database `ON DELETE CASCADE` either.

### 14.1. Managing Schema with Migrations

A repository can be organized as:

~~~text
database/
├── migrations/
│   ├── V001__create_customer_and_product.sql
│   ├── V002__create_sales_order.sql
│   ├── V003__create_order_item_and_shipping.sql
│   ├── V004__add_indexes.sql
│   └── V005__add_business_rule_changes.sql
└── docs/
    ├── domain-rules.md
    └── erd.md
~~~

The migration filenames here illustrate the convention of a tool like Flyway. Table creation order must respect FK dependencies: create parent tables first, then child tables, or add FKs afterward with `ALTER TABLE`. When modifying relationships, pay attention to **existing data**, not just the new DDL: a new FK may fail validation due to orphan records; a new unique constraint may fail due to duplicate business keys.

**Oracle DDL generally performs an implicit commit.** Do not assume a sequence of `CREATE TABLE`/`ALTER TABLE` statements can simply be undone with `ROLLBACK` like a DML transaction. Migrations need a rollout plan, dry runs, backups, and a forward-fix plan if errors occur.

### 14.2. Business Changes Require a Data Plan

Suppose initially an order has only one shipping address, and later needs multiple partial shipments. Changing the model from 1:1 `ORDER_SHIPPING` to 1:N `SHIPMENT` is not just changing the `PRIMARY KEY`:

1. Define whether **one shipment row** represents a delivery trip or a package.
2. Add `SHIPMENT_ID` if each shipment needs an independent identity.
3. Add FK `SHIPMENT.ORDER_ID`; drop the one-order-one-shipment uniqueness constraint as appropriate.
4. Migrate legacy shipping/address data into shipment records consistently.
5. Update APIs, JPA mappings, reports, status rules, and historical data.
6. Verify no relationships are lost and prepare the application cutover plan.

This is why relational modeling must originate from **business rules**, not merely from the forms currently displayed on screen.

## 15. Graded Practice Exercises

### Exercise 1 — Identifying Entities and Grain

Requirement: "A library has readers, book titles, multiple physical copies of each book title, and loan records. A reader can borrow multiple copies at different times."

Identify the entities and grain for `READER`, `BOOK_TITLE`, `BOOK_COPY`, and `LOAN`. Why should we not have only a `BOOK` table with an `IS_BORROWED` flag when the same title has five physical copies?

**Guidance:** `BOOK_TITLE` represents the work/edition at the title level, while `BOOK_COPY` represents each physical copy. `LOAN` is the event of borrowing a specific copy over a time period. One title can have many copies, and one copy can appear in many loans over its history.

### Exercise 2 — From Description to PK/FK

Requirement: "A class has many students; a student can join many classes. Each enrollment must record the date and status."

Draw the relationship and propose the `STUDENT`, `CLASS`, and `ENROLLMENT` tables. If a student may have only **one enrollment** in the same class, choose the appropriate primary key or unique constraint.

**Guidance:**

~~~text
STUDENT 1 ───< ENROLLMENT >─── 1 CLASS
                STUDENT_ID (FK)
                CLASS_ID   (FK)
                ENROLLED_AT
                STATUS
~~~

`PRIMARY KEY(STUDENT_ID, CLASS_ID)` fits if repeat enrollments are not allowed in history. If a student can re-enroll multiple times after withdrawing, a new grain is needed: each **enrollment attempt** is its own entity, potentially needing `ENROLLMENT_ID` and a conditional uniqueness rule for active enrollments.

### Exercise 3 — 1:N Optionality

Given the relationship `CUSTOMER 1 — 0..N SALES_ORDER`, answer:

1. Which column holds the FK?
2. Why is that FK `NOT NULL`?
3. Does a customer with no orders violate the constraint?
4. If we want to require every customer to have at least one order, are the current constraints sufficient?

**Answer:** The FK is `SALES_ORDER.CUSTOMER_ID`; it is NOT NULL because every order must belong to exactly one customer. A customer without orders is still valid. This FK cannot guarantee that every customer has at least one order.

### Exercise 4 — Order Lines and Historical Prices

After inserting the sample data, update `LAB_PRODUCT.UNIT_PRICE_VND` for `SKU-KEYBOARD` to 500000. Use the query in Section 8.1 to inspect the locked price in `LAB_ORDER_ITEM`.

**Question:** Why shouldn't old order prices be recalculated using the current price from `LAB_PRODUCT`?

**Guidance:** The transaction price is an attribute of the **order line item at the time of ordering**, distinct from the current catalog price. Not storing a snapshot would alter historical reports whenever the product table is updated.

### Exercise 5 — Distinguishing Enforceable vs. Non-Enforceable Rules

Classify the following:

| Rule | Is a Single Table Constraint Enough? |
|---|---|
| Unique SKU | Yes: `UNIQUE`, plus `NOT NULL` if mandatory |
| Every order line points to an existing product | Yes: `FOREIGN KEY` |
| Quantity greater than 0 | Yes: `CHECK` + `NOT NULL` |
| A `CONFIRMED` order has at least one line item | No, not with a simple row-level CHECK/FK |
| Cannot transition from `CANCELLED` to `CONFIRMED` | No, not with a CHECK that only validates allowed status values |
| An order has at most one shipping snapshot | Yes: `ORDER_SHIPPING.ORDER_ID` as PK |

Also write down how to manage **transactions and concurrency** for the two rules not protected by simple constraints.

### Exercise 6 — Verifying via the Data Dictionary

Run the `USER_CONSTRAINTS` and `USER_CONS_COLUMNS` queries from Section 13. Find:

- Which columns make up the PK of `LAB_ORDER_ITEM`?
- Which key does `LAB_ORDER_ITEM.PRODUCT_ID` reference?
- Can `LAB_ORDER_SHIPPING` have two rows with the same `ORDER_ID`?
- Does every FK already have its own separate index?

**Guidance:** The order item PK is `(ORDER_ID, LINE_NO)`; the product FK references `LAB_PRODUCT.PRODUCT_ID`; shipping cannot have two rows with the same PK; FK indexes must be evaluated individually—Oracle does not automatically create a separate index for every FK.

## 16. Decision Flow When Adding a New Relationship

When a new requirement arises, you can walk through this sequence of questions:

~~~text
BUSINESS DESCRIPTION
      |
      v
What does one row of data represent?
      |
      v
Entity, value object, or status/attribute?
      |
      v
What is the identifying key? Is there a unique business key?
      |
      v
1:1, 1:N, or N:M relationship? Mandatory or optional?
      |
      v
Choose PK, FK, UNIQUE, NOT NULL, CHECK, and data types
      |
      v
Need historical snapshots, soft delete, or temporal rules?
      |
      v
Which rules exceed simple constraints?
      |
      v
Design transactions / services / additional enforcement
      |
      v
Create migrations and sample data, run JOIN queries
      |
      v
Cross-check data dictionary against business requirements
~~~

**Key takeaway:** Relationships in Oracle are not just lines connecting two boxes on an ERD. **Primary keys** clarify identity; **foreign keys** protect references; **NOT NULL, UNIQUE, and CHECK** push local rules down into the database; **associative tables** turn N:M into queryable and controllable data; and **transactions together with business logic** protect invariants spanning beyond a single row. When every table has a clear grain and every constraint maps to a specific rule, an Oracle schema becomes easier to understand, easier to extend, and far more reliable across both SQL and Java applications.
