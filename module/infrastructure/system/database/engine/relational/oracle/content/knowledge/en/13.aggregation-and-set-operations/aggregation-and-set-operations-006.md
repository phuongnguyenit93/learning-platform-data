# ROLLUP, CUBE, and GROUPING SETS

In Oracle Database, a standard GROUP BY creates one result row for each data group. However, business reports often need multiple aggregation levels at the same time: revenue by region and product, total revenue per region, total per product, and company-wide grand total. Writing a separate GROUP BY query for each level and combining them with UNION ALL makes SQL verbose and duplicates logic.

Oracle provides three key extensions to GROUP BY:

- **ROLLUP**: generates subtotals along a hierarchical order, from detail rows through progressively shorter grouping prefixes up to the grand total.
- **CUBE**: generates aggregate combinations for every subset of the selected dimensions.
- **GROUPING SETS**: specifies the exact groups to compute.

Two functions commonly used alongside them are **GROUPING** and **GROUPING_ID**. They distinguish real NULLs in the data from NULLs generated by Oracle to represent a subtotal level. **GROUP_ID** identifies duplicate groups created when a grouping sets list includes the same group multiple times.

This lesson focuses on syntax, output of each type, sorting and filtering aggregation levels, reporting usage, and SQL examples you can run in a practice schema.

## 1. From standard GROUP BY to multi-level aggregation

Suppose a sales table has these dimensions:

- **REGION**: sales region.
- **PRODUCT**: product category.
- **CHANNEL**: sales channel.
- **AMOUNT**: revenue.

Standard GROUP BY:

~~~sql
SELECT region,
       product,
       SUM(amount) AS revenue
FROM sales
GROUP BY region, product;
~~~

returns revenue for each region-and-product pair. If you also want subtotals by region, subtotals by product, and a company grand total, you need different groups:

~~~text
Detail:
  North / Laptop
  North / Phone
  South / Laptop
  South / Phone

Subtotal by region:
  North / all products
  South / all products

Subtotal by product:
  All regions / Laptop
  All regions / Phone

Grand total:
  All regions / all products
~~~

The three GROUP BY extensions express all these levels in a single query. In terms of results, each aggregation level is a **grouping set**: the set of expressions used to form groups.

Example:

| Grouping set | Meaning |
| --- | --- |
| (REGION, PRODUCT) | Detail revenue by region and product |
| (REGION) | Subtotal by region |
| (PRODUCT) | Subtotal by product |
| () | Grand total across all data |

Empty parentheses **()** represent the grouping set with no grouping dimensions; it forms one summary group over all rows remaining after WHERE.

## 2. ROLLUP: hierarchical aggregation

Syntax:

~~~sql
GROUP BY ROLLUP (expr1, expr2, ..., exprN)
~~~

ROLLUP produces grouping sets ordered from the full set down through progressively shorter prefixes, ending with the grand total.

With two expressions:

~~~sql
GROUP BY ROLLUP (region, product)
~~~

is equivalent in generated groups to:

~~~sql
GROUP BY GROUPING SETS (
    (region, product),
    (region),
    ()
)
~~~

With three expressions:

~~~sql
GROUP BY ROLLUP (region, product, channel)
~~~

the grouping sets are:

1. (REGION, PRODUCT, CHANNEL)
2. (REGION, PRODUCT)
3. (REGION)
4. ()

The number of grouping sets produced by a ROLLUP with N expressions is **N + 1**.

### 2.1. When is ROLLUP appropriate?

ROLLUP fits when dimensions form a hierarchy and the report aggregates step by step from detail up to higher levels. For example:

~~~text
Year
  └── Quarter
       └── Month
            └── Day
~~~

Query:

~~~sql
SELECT nam,
       quy,
       thang,
       SUM(doanh_thu) AS tong_doanh_thu
FROM doanh_thu_thang
GROUP BY ROLLUP (nam, quy, thang);
~~~

produces revenue by year/quarter/month, totals by year/quarter, and the grand total. Note that expression order matters: ROLLUP(NAM, QUY, THANG) is not the same as ROLLUP(THANG, QUY, NAM).

### 2.2. Two-dimensional ROLLUP

~~~sql
SELECT region,
       product,
       SUM(amount) AS revenue
FROM sales
GROUP BY ROLLUP (region, product);
~~~

The result includes:
- Pairs of REGION and PRODUCT.
- Sum of PRODUCT within each REGION, i.e. subtotal by REGION.
- Grand total.

ROLLUP does not automatically produce a subtotal by PRODUCT across all REGIONs, because PRODUCT is not an independent prefix in the order (REGION, PRODUCT). If you need that level too, use CUBE or GROUPING SETS.

### 2.3. Three-dimensional ROLLUP

~~~sql
SELECT region,
       product,
       channel,
       SUM(amount) AS revenue
FROM sales
GROUP BY ROLLUP (region, product, channel);
~~~

Generated levels:

| Level | Grouping columns | Meaning |
| --- | --- | --- |
| Detail | REGION, PRODUCT, CHANNEL | Per region, product, and channel |
| Channel subtotal | REGION, PRODUCT | Combines all channels within each region/product pair |
| Product subtotal | REGION | Combines all products and channels within each region |
| Grand total | None | Entire dataset |

ROLLUP creates prefixes strictly along the list order. It does not generate a separate subtotal by CHANNEL across all REGIONs and PRODUCTs.

## 3. CUBE: all combinations of dimensions

Syntax:

~~~sql
GROUP BY CUBE (expr1, expr2, ..., exprN)
~~~

CUBE generates a grouping set for **every subset** of the supplied expressions, including the full set and the empty set.

With two expressions:

~~~sql
GROUP BY CUBE (region, product)
~~~

the grouping sets are:

- (REGION, PRODUCT)
- (REGION)
- (PRODUCT)
- ()

These are four combinations, corresponding to 2².

With three expressions:

~~~sql
GROUP BY CUBE (region, product, channel)
~~~

there are 2³ = **8 grouping sets**:

| Grouping set | Meaning |
| --- | --- |
| (REGION, PRODUCT, CHANNEL) | Detail across all three dimensions |
| (REGION, PRODUCT) | Subtotal by region and product |
| (REGION, CHANNEL) | Subtotal by region and channel |
| (PRODUCT, CHANNEL) | Subtotal by product and channel |
| (REGION) | Subtotal by region |
| (PRODUCT) | Subtotal by product |
| (CHANNEL) | Subtotal by channel |
| () | Grand total |

With N expressions, CUBE can generate **2^N grouping sets**. The number of combinations grows rapidly: 5 dimensions yield 32 structural grouping sets, 10 dimensions yield 1,024. Each grouping set can produce many actual data groups, so CUBE over many high-cardinality dimensions can consume substantial resources.

### 3.1. When is CUBE appropriate?

CUBE fits multidimensional analysis when users need to view summaries across multiple angles:

- Revenue by region.
- Revenue by product.
- Revenue by channel.
- Revenue by region and product.
- Revenue by product and channel.
- Grand total revenue.

Example:

~~~sql
SELECT region,
       product,
       SUM(amount) AS revenue
FROM sales
GROUP BY CUBE (region, product);
~~~

The query generates subtotals by REGION as well as subtotals by PRODUCT. This is what distinguishes it from ROLLUP(REGION, PRODUCT).

### 3.2. CUBE does not imply sorting by dimension order

CUBE generates grouping sets, but **makes no guarantee about returned row order**. The ordering of groups in the result must be specified separately with ORDER BY. Nor should you rely on whatever order a SQL tool displays during a test run.

## 4. GROUPING SETS: specifying exact aggregation levels

Syntax:

~~~sql
GROUP BY GROUPING SETS (
    (expr_a, expr_b),
    (expr_a),
    (expr_b),
    ()
)
~~~

GROUPING SETS lets you explicitly specify the sets of expressions to aggregate. It does not automatically add intermediate levels outside the list.

Example:

~~~sql
SELECT region,
       product,
       SUM(amount) AS revenue
FROM sales
GROUP BY GROUPING SETS (
    (region, product),
    (region),
    ()
);
~~~

The query produces only:
- Detail by REGION and PRODUCT.
- Subtotal by REGION.
- Grand total.

It **does not produce a subtotal by PRODUCT** because (PRODUCT) is not in the list.

### 4.1. GROUPING SETS avoids generating unneeded totals

If a report only needs:
- Revenue by month and region.
- Revenue by region.
- Grand total.

you can write:

~~~sql
SELECT thang,
       region,
       SUM(amount) AS revenue
FROM sales_by_month
GROUP BY GROUPING SETS (
    (thang, region),
    (region),
    ()
);
~~~

There is no need for CUBE(THANG, REGION), because CUBE would also add the (THANG) grouping set, which may not serve the report.

### 4.2. Grouping set order is not display order

Even if you list grouping sets in a specific order, the final result still has no guaranteed order without ORDER BY. The GROUPING SETS list describes **which groups to form**, not a contract for sorting output rows.

### 4.3. Comparing the three constructs

| Criterion | ROLLUP | CUBE | GROUPING SETS |
| --- | --- | --- | --- |
| How groups are formed | Prefixes from full down to empty | Every subset of dimensions | Exactly the listed sets |
| Best suited for | Hierarchies | Multidimensional analysis | Reports with specific requirements |
| Structural group count | N + 1 | 2^N | Number of declared grouping sets |
| Includes grand total by default | Yes | Yes | Only when () is listed |
| Includes single-dimension subtotals | Only matching prefixes | Yes | Only when listed |
| Output control | By dimension order | Covers all combinations | Most precise |

## 5. GROUPING: distinguishing data NULLs from subtotal NULLs

A subtotal row typically displays NULL in columns that were rolled up. However, source data can also contain real NULLs. Looking at the column value alone cannot tell you which kind of NULL it is.

For example, a transaction's REGION might be NULL because the region is unknown. Meanwhile, the grand total row produced by ROLLUP also has REGION = NULL because it does not group by REGION. Two rows display the exact same value yet carry different meanings.

The **GROUPING(expr)** function solves this problem:

- Returns **0** if the expression is part of the current grouping set, even if its actual data value is NULL.
- Returns **1** if the expression was aggregated out of the grouping set and NULL was generated to represent an aggregation level.

Syntax:

~~~sql
GROUPING(expr)
~~~

Example:

~~~sql
SELECT region,
       product,
       GROUPING(region) AS g_region,
       GROUPING(product) AS g_product,
       SUM(amount) AS revenue
FROM sales
GROUP BY ROLLUP (region, product);
~~~

Interpretation:
- Detail by REGION/PRODUCT: G_REGION = 0, G_PRODUCT = 0.
- Subtotal by REGION: G_REGION = 0, G_PRODUCT = 1.
- Grand total: G_REGION = 1, G_PRODUCT = 1.
- A transaction with a NULL REGION that is still a detail group: G_REGION = 0, not 1.

**GROUPING does not check whether the column's data is NULL.** It checks whether the column was rolled up out of the current grouping set.

### 5.1. Why IS NULL is not enough to identify total rows

Suppose the output is:

| REGION | PRODUCT | REVENUE |
| --- | --- | ---: |
| NULL | TABLET | 25 |
| NULL | NULL | 25 |
| NULL | NULL | 425 |

Both of the last two rows display NULL for REGION and PRODUCT, yet one may be the subtotal for the NULL REGION, while the other is the grand total. If the data also contains a group where both REGION and PRODUCT are genuinely NULL, even more rows would display NULL.

Use GROUPING to identify them:

~~~sql
SELECT region,
       product,
       GROUPING(region) AS g_region,
       GROUPING(product) AS g_product,
       SUM(amount) AS revenue
FROM sales
GROUP BY ROLLUP (region, product);
~~~

You can display labels:

~~~sql
SELECT
    CASE
        WHEN GROUPING(region) = 1 THEN 'ALL REGIONS'
        WHEN region IS NULL THEN 'UNKNOWN REGION'
        ELSE region
    END AS region_label,
    CASE
        WHEN GROUPING(product) = 1 THEN 'ALL PRODUCTS'
        WHEN product IS NULL THEN 'UNKNOWN PRODUCT'
        ELSE product
    END AS product_label,
    SUM(amount) AS revenue
FROM sales
GROUP BY ROLLUP (region, product);
~~~

Here you must check GROUPING first, and only then check for real NULLs. If you reverse the order, summary rows with Oracle-generated NULLs would be mislabeled as "unknown."

## 6. GROUPING_ID: encoding multiple GROUPING flags

When there are many dimensions, outputting individual GROUPING flags can be verbose. **GROUPING_ID(expr1, expr2, ...)** returns a number representing the bit combination of the expressions' GROUPING flags.

Syntax:

~~~sql
GROUPING_ID(expr1 [, expr2 ...])
~~~

Each expression has a GROUPING flag:
- 0: the expression participates in the current grouping set.
- 1: the expression has been rolled up.

GROUPING_ID concatenates the flags in argument order into a bit vector and returns the corresponding integer. With two arguments REGION, PRODUCT, it works as follows:

| GROUPING(REGION) | GROUPING(PRODUCT) | Bits | GROUPING_ID(REGION, PRODUCT) |
| ---: | ---: | --- | ---: |
| 0 | 0 | 00 | 0 |
| 0 | 1 | 01 | 1 |
| 1 | 0 | 10 | 2 |
| 1 | 1 | 11 | 3 |

Example:

~~~sql
SELECT region,
       product,
       GROUPING_ID(region, product) AS grouping_level,
       SUM(amount) AS revenue
FROM sales
GROUP BY CUBE (region, product)
ORDER BY grouping_level, region, product;
~~~

GROUPING_ID helps you:
- Identify the aggregation level with a single numeric value.
- Filter the exact subtotal type in HAVING or an outer query block.
- Attach an aggregation-level code to report/API data.
- Sort aggregation levels as desired.

### 6.1. Argument order affects the code

GROUPING_ID(REGION, PRODUCT) is not the same as GROUPING_ID(PRODUCT, REGION), because bit positions correspond to the order of passed expressions. When an application persists grouping level codes or uses them in CASE, keep the argument order consistent.

With many expressions, do not guess the numeric codes. List the GROUPING flags, build the corresponding bit table, and verify with a small query.

### 6.2. GROUPING_ID must use expressions from GROUP BY

If grouping by an expression:

~~~sql
SELECT TRUNC(order_date, 'MM') AS month_start,
       GROUPING(TRUNC(order_date, 'MM')) AS g_month,
       SUM(amount) AS revenue
FROM orders
GROUP BY ROLLUP (TRUNC(order_date, 'MM'));
~~~

The expression in GROUPING must match the expression used in GROUP BY. Do not substitute GROUPING(ORDER_DATE) just because ORDER_DATE is the source column; grouping is being performed on the result of TRUNC(ORDER_DATE,'MM').

## 7. GROUP_ID: identifying repeated grouping sets

GROUPING SETS allows declaring the same grouping set multiple times. This can create result groups with identical grouping keys and aggregates.

**GROUP_ID()** returns a number identifying duplicate occurrences of a group generated by repeated grouping sets:
- The first group among duplicates receives 0.
- Subsequent copies receive 1, 2, ...

Example intentionally declaring the detail grouping set twice:

~~~sql
SELECT region,
       product,
       GROUP_ID() AS duplicate_group,
       SUM(amount) AS revenue
FROM sales
GROUP BY GROUPING SETS (
    (region, product),
    (region),
    (region, product),
    ()
)
ORDER BY duplicate_group, region, product;
~~~

Detail groups by REGION/PRODUCT are generated from two identical grouping sets. GROUP_ID distinguishes the occurrence number. If the goal is to remove duplicates, you can use:

~~~sql
SELECT region,
       product,
       SUM(amount) AS revenue
FROM sales
GROUP BY GROUPING SETS (
    (region, product),
    (region),
    (region, product),
    ()
)
HAVING GROUP_ID() = 0;
~~~

However, the better solution is usually **not declaring duplicate grouping sets in the first place**. GROUP_ID is useful when grouping structures are generated dynamically or when diagnosing a complex grouping list. It is not a general replacement for DISTINCT across arbitrary outputs.

## 8. Combining ROLLUP, CUBE, and GROUPING SETS with composite columns

Oracle supports **composite columns**: a group of multiple expressions enclosed in parentheses to be treated as a single unit in certain grouping operations.

Example:

~~~sql
SELECT region,
       product,
       channel,
       SUM(amount) AS revenue
FROM sales
GROUP BY ROLLUP ((region, product), channel);
~~~

Here (REGION, PRODUCT) is treated as one aggregation unit; ROLLUP produces:
- (REGION, PRODUCT, CHANNEL)
- (REGION, PRODUCT)
- ()

It does not generate (REGION) or (PRODUCT) separately. This is useful when a report treats the REGION/PRODUCT pair as an indivisible level.

An example with CUBE:

~~~sql
SELECT region,
       product,
       channel,
       SUM(amount) AS revenue
FROM sales
GROUP BY CUBE ((region, product), channel);
~~~

The two grouping units are the pair (REGION, PRODUCT) and CHANNEL, so CUBE produces four combinations:
- (REGION, PRODUCT, CHANNEL)
- (REGION, PRODUCT)
- (CHANNEL)
- ()

When using composite columns, identify the **grouping units** before counting grouping sets. CUBE over two units creates 2² = 4 structural sets, even though the first unit contains two columns.

## 9. WHERE, HAVING, and filtering aggregation levels

WHERE and HAVING operate at different stages:

- **WHERE** filters source rows before GROUP BY forms groups.
- **HAVING** filters groups after aggregation.
- GROUPING and GROUPING_ID help HAVING conditions recognize subtotal/grand-total levels.

Example:

~~~sql
SELECT region,
       product,
       SUM(amount) AS revenue
FROM sales
WHERE amount > 0
GROUP BY ROLLUP (region, product)
HAVING SUM(amount) >= 100;
~~~

WHERE removes non-positive transactions before aggregating. HAVING keeps groups with total revenue of at least 100, including subtotal levels if they meet the threshold.

### 9.1. Retrieving only regional totals, excluding detail and grand total

With ROLLUP(REGION, PRODUCT), GROUPING(PRODUCT)=1 holds on regional subtotal rows and on the grand total. To retrieve only regional subtotals:

~~~sql
SELECT region,
       SUM(amount) AS revenue
FROM sales
GROUP BY ROLLUP (region, product)
HAVING GROUPING(region) = 0
   AND GROUPING(product) = 1;
~~~

Conditions:
- REGION is not rolled up: it represents a specific region or a real NULL value.
- PRODUCT is rolled up: the row is a subtotal by region.

### 9.2. Retrieving only the grand total

~~~sql
SELECT SUM(amount) AS total_revenue
FROM sales
GROUP BY ROLLUP (region, product)
HAVING GROUPING_ID(region, product) = 3;
~~~

With the two expressions in the exact order REGION, PRODUCT, code 3 indicates both expressions have been rolled up.

You can use GROUPING(region)=1 and GROUPING(product)=1 instead of the numeric code if you want a more self-explanatory condition.

### 9.3. WHERE can change the grand total as well

~~~sql
SELECT region,
       product,
       SUM(amount) AS revenue
FROM sales
WHERE region = 'NORTH'
GROUP BY ROLLUP (region, product);
~~~

This query computes all aggregation levels solely from NORTH transactions. The grand total in the output is also only NORTH revenue, not total company revenue.

If a report needs NORTH details alongside a company-wide grand total, you cannot simply write WHERE REGION='NORTH' and expect ROLLUP to keep filtered-out data. You must design separate grouping sets/conditional expressions or separate query blocks to make each level's dataset explicit.

### 9.4. HAVING filters each aggregated group

~~~sql
SELECT region,
       product,
       GROUPING_ID(region, product) AS gid,
       SUM(amount) AS revenue
FROM sales
GROUP BY CUBE (region, product)
HAVING SUM(amount) >= 100;
~~~

HAVING applies to each group generated by CUBE. A subtotal by REGION may pass the condition while smaller detail groups are dropped. To always keep the grand total regardless of revenue, combine the condition with GROUPING_ID:

~~~sql
HAVING SUM(amount) >= 100
    OR GROUPING_ID(region, product) = 3
~~~

## 10. ORDER BY for results with multiple aggregation levels

ROLLUP, CUBE, and GROUPING SETS do not guarantee return order. Furthermore, NULL columns in subtotals can be confused with real NULLs if you sort only by dimension values.

Example:

~~~sql
SELECT region,
       product,
       GROUPING(region) AS g_region,
       GROUPING(product) AS g_product,
       SUM(amount) AS revenue
FROM sales
GROUP BY ROLLUP (region, product)
ORDER BY GROUPING(region),
         region NULLS LAST,
         GROUPING(product),
         product NULLS LAST;
~~~

Order:
1. Groups where REGION is not rolled up come before the grand total row.
2. Within each REGION, detail PRODUCT groups come before the REGION subtotal.
3. Real NULL values are handled via NULLS LAST.
4. The grand total row is identified by GROUPING(REGION)=1 and placed last.

If you need a custom report order, use CASE on GROUPING_ID or GROUPING:

~~~sql
ORDER BY
    CASE GROUPING_ID(region, product)
        WHEN 0 THEN 1
        WHEN 1 THEN 2
        WHEN 3 THEN 3
        ELSE 4
    END,
    region NULLS LAST,
    product NULLS LAST;
~~~

With CUBE, which also includes PRODUCT subtotals (GROUPING_ID=2), CASE should define that level too. Never use a GROUPING_ID code derived from a different expression order than the one declared.

The following examples use a separate sandbox table. Run them in a schema with CREATE TABLE, INSERT, and SELECT privileges. The dataset includes one row with a real NULL REGION so you can observe how GROUPING distinguishes source values from subtotal rows.

The last three rows show REGION as NULL in two different situations. The pair of GROUPING flags clarifies:

- (1,1): grand total.

### 11.5. CUBE by region and product

~~~sql
SELECT region,
       product,
       GROUPING_ID(region, product) AS gid,

GROUP BY CUBE (region, product)
ORDER BY gid,
         region NULLS LAST,

~~~

CUBE generates detail groups, subtotals by REGION, subtotals by PRODUCT, and the grand total. The PRODUCT subtotals:

| REGION | PRODUCT | GID | REVENUE | Meaning |
| --- | --- | ---: | ---: | --- |
| NULL | LAPTOP | 2 | 220 | LAPTOP total across all regions |

The NULL REGION rows with GID=2 are subtotals by PRODUCT, not the NULL REGION data group. The NULL REGION/TABLET detail group has GID=0. GROUPING_ID makes the distinction explicit.

### 11.6. GROUPING SETS selecting only three levels

~~~sql
SELECT region,
       product,
       GROUPING_ID(region, product) AS gid,
       SUM(amount) AS revenue
FROM sales_group_demo
GROUP BY GROUPING SETS (
    (region, product),
    (product),
    ()
)
ORDER BY gid,
         region NULLS LAST,
         product NULLS LAST;
~~~

The result contains:
- Detail by REGION/PRODUCT.
- Subtotal by PRODUCT across all regions.
- Grand total.

There is no subtotal by REGION because the (REGION) grouping set is not listed.

### 11.7. Three-dimensional ROLLUP

~~~sql
SELECT region,
       product,
       channel,
       GROUPING_ID(region, product, channel) AS gid,
       SUM(amount) AS revenue
FROM sales_group_demo
GROUP BY ROLLUP (region, product, channel)
ORDER BY gid,
         region NULLS LAST,
         product NULLS LAST,
         channel NULLS LAST;
~~~

The generated levels are:
- REGION/PRODUCT/CHANNEL.
- REGION/PRODUCT.
- REGION.
- Grand total.

GROUPING_ID distinguishes the aggregation level. With three arguments, each GROUPING flag contributes one bit; the exact numeric value depends on the order REGION, PRODUCT, CHANNEL.

### 11.8. Filtering only regional totals

~~~sql
SELECT region,
       SUM(amount) AS revenue
FROM sales_group_demo
GROUP BY ROLLUP (region, product)
HAVING GROUPING(region) = 0
   AND GROUPING(product) = 1
ORDER BY region NULLS LAST;
~~~

The result includes:
- NORTH: 230.
- SOUTH: 170.
- REGION NULL: 25.

The grand total is excluded because GROUPING(REGION)=1. Detail groups are excluded because GROUPING(PRODUCT)=0.

### 11.9. Cleaning up the practice table

~~~sql
DROP TABLE sales_group_demo PURGE;
~~~

Only drop the lesson's sandbox table when you are certain the data is no longer needed. DROP TABLE is DDL with implicit commit rules; PURGE bypasses the recycle bin per standard behavior.

## 12. ROLLUP/CUBE/GROUPING SETS vs. UNION ALL

Multiple aggregation levels can be written as multiple SELECT statements combined with UNION ALL:

~~~sql
SELECT region, product, SUM(amount) AS revenue
FROM sales
GROUP BY region, product

UNION ALL

SELECT region, CAST(NULL AS VARCHAR2(30)) AS product,
       SUM(amount) AS revenue
FROM sales
GROUP BY region

UNION ALL

SELECT CAST(NULL AS VARCHAR2(30)) AS region,
       CAST(NULL AS VARCHAR2(30)) AS product,
       SUM(amount) AS revenue
FROM sales;
~~~

This is one way to express the grouping sets (REGION, PRODUCT), (REGION), (). However, keep several points in mind:

- Each branch may repeat FROM/WHERE logic and cause source data to be accessed multiple times.
- NULLs must be CAST to compatible types across UNION branches.
- UNION ALL preserves duplicate rows, matching grouping sets semantics; UNION removes duplicates and can alter results.
- Subtotal NULL rows still need an identifying flag if source data contains real NULLs.
- The optimizer may optimize different query forms differently; do not claim ROLLUP is always faster than UNION ALL or always scans the table only once.

When the logic is multiple aggregation levels over the same dataset, GROUPING SETS is usually more direct. When different levels have different source conditions, UNION ALL or separate query blocks can be clearer.

## 13. Performance and choosing dimensionality

ROLLUP, CUBE, and GROUPING SETS are not free. Each grouping set can generate many actual groups; large datasets and high-cardinality dimensions can increase CPU, PGA, TEMP usage, and aggregation time.

### 13.1. ROLLUP usually generates fewer structural sets than CUBE

With 5 expressions:
- ROLLUP generates 6 grouping sets.
- CUBE generates 32 grouping sets.

With 10 expressions:
- ROLLUP generates 11 grouping sets.
- CUBE generates 1,024 grouping sets.

If a report only needs details, subtotals by region, and a grand total, GROUPING SETS or ROLLUP is much more appropriate than CUBE over all dimensions.

### 13.2. Cardinality of each dimension matters

A grouping set on REGION might produce a few dozen groups; a grouping set on CUSTOMER_ID might produce millions of groups. When CUBE is applied over multiple high-cardinality identifier dimensions, output group counts and memory demands can surge.

Before using CUBE:
- Identify which dimensions truly need analysis.
- Evaluate the distinct value count of each dimension.
- Avoid including fine-grained keys like transaction ID in CUBE without a clear reason.
- Generate only the grouping sets needed by the report.
- Measure the execution plan and runtime on representative data.

### 13.3. WHERE reduces data before aggregation

If reporting only on a specific time range, filter first:

~~~sql
SELECT region,
       product,
       SUM(amount) AS revenue
FROM sales
WHERE sale_date >= DATE '2024-01-01'
  AND sale_date <  DATE '2025-01-01'
GROUP BY ROLLUP (region, product);
~~~

WHERE limits the input row set for every aggregation level. Using a half-open range ensures all timestamps in 2024 are included when SALE_DATE has a time component.

However, if you want an all-time grand total alongside 2024-only details, a simple WHERE as above cannot be used; you must express the separate conditions explicitly per aggregation level.

### 13.4. HAVING reduces output groups, and does not replace WHERE

~~~sql
HAVING SUM(amount) >= 100
~~~

filters after aggregation. If a condition applies purely to source data, put it in WHERE to shrink the input. If a condition depends on aggregate results, use HAVING.

### 13.5. Viewing the execution plan

~~~sql
EXPLAIN PLAN FOR
SELECT region,
       product,
       GROUPING_ID(region, product) AS gid,
       SUM(amount) AS revenue
FROM sales_group_demo
GROUP BY CUBE (region, product);

SELECT *
FROM TABLE(DBMS_XPLAN.DISPLAY);
~~~

The plan may show operations such as SORT GROUP BY, HASH GROUP BY, or grouping generation steps depending on the version and optimizer. EXPLAIN PLAN is an estimate; on production-like systems, inspect the cursor plan and runtime statistics when authorized.

Do not create an index solely because a query uses ROLLUP or CUBE. Indexes help filter conditions, data access, or specific execution paths; aggregates may still need to process many rows. Base decisions on workload and measurement.

## 14. Notes on expressions, aliases, and data types

### 14.1. GROUP BY on expressions

You can group by expressions:

~~~sql
SELECT TRUNC(sale_date, 'MM') AS month_start,
       SUM(amount) AS revenue
FROM sales
GROUP BY ROLLUP (TRUNC(sale_date, 'MM'));
~~~

If you want to identify subtotals:

~~~sql
SELECT TRUNC(sale_date, 'MM') AS month_start,
       GROUPING(TRUNC(sale_date, 'MM')) AS g_month,
       SUM(amount) AS revenue
FROM sales
GROUP BY ROLLUP (TRUNC(sale_date, 'MM'));
~~~

GROUPING must reference the corresponding expression used in GROUP BY.

### 14.2. Do not arbitrarily select ungrouped or unaggregated columns

~~~sql
-- Invalid if product_name is neither grouped nor aggregated.
SELECT region,
       product,
       product_name,
       SUM(amount)
FROM sales
GROUP BY ROLLUP (region, product);
~~~

Oracle requires select-list expressions to conform to GROUP BY rules. Even if PRODUCT_NAME functionally depends on PRODUCT by data key, SQL still must express the relationship in Oracle-accepted syntax, such as adding PRODUCT_NAME to the appropriate grouping set or joining the dimension table after aggregation.

### 14.3. Aliases do not substitute for expressions in GROUPING

Aliases in SELECT name output columns, while GROUPING/GROUPING_ID require the corresponding grouping expression and should not be replaced with an alias as if it were a source column:

~~~sql
SELECT TRUNC(sale_date, 'MM') AS month_start,
       GROUPING(TRUNC(sale_date, 'MM')) AS g_month,
       SUM(amount)
FROM sales
GROUP BY ROLLUP (TRUNC(sale_date, 'MM'));
~~~

This is the clear way for Oracle to identify the exact expression being rolled up.

### 14.4. NULL type of summary rows

The NULL generated by ROLLUP/CUBE/GROUPING SETS is a marker representing an aggregation level, not a new data value written into the table. Never UPDATE the source table to "fill subtotal NULLs." If display labels are needed, use CASE combined with GROUPING/GROUPING_ID in SELECT.

## 15. Java applications and reporting

An Oracle report can return both detail rows and summary rows. The Java layer needs to recognize the row type rather than merely checking whether REGION or PRODUCT is NULL.

Example API/report query:

~~~sql
SELECT region,
       product,
       GROUPING_ID(region, product) AS grouping_level,
       SUM(amount) AS revenue
FROM sales
GROUP BY ROLLUP (region, product)
ORDER BY GROUPING_ID(region, product),
         region NULLS LAST,
         product NULLS LAST;
~~~

In Java/JDBC, you can read:
- REGION and PRODUCT as String, which may be null.
- GROUPING_LEVEL as an integer.
- REVENUE as BigDecimal.

Example:

~~~java
int groupingLevel = rs.getInt("GROUPING_LEVEL");
String region = rs.getString("REGION");
String product = rs.getString("PRODUCT");
BigDecimal revenue = rs.getBigDecimal("REVENUE");

switch (groupingLevel) {
    case 0 -> {
        // Detail by region and product.
    }
    case 1 -> {
        // Subtotal by region.
    }
    case 3 -> {
        // Grand total.
    }
    default -> {
        // Handle other aggregation levels if the query is extended.
    }
}
~~~

With a two-dimensional CUBE, GID=2 represents the subtotal by PRODUCT; GID=1 represents the subtotal by REGION. With a two-dimensional ROLLUP, only codes 0, 1, and 3 appear. **Do not reuse the same GID interpretation across queries if the expression order or grouping sets structure differs.**

When reading primitive `getInt`, SQL NULL can also be mapped to 0; GROUPING_ID is non-NULL in normal result rows, but for dimension columns, use `getString`/`getObject` to preserve NULL state. If the API needs to distinguish real NULLs from subtotals, return GROUPING/GROUPING_ID or an explicit row-type field.

### 15.1. Do not build dynamic SQL from unchecked dimension names

If a report lets users choose dimensions like REGION, PRODUCT, or CHANNEL, never concatenate client-supplied strings directly into GROUP BY CUBE or ORDER BY. Column names cannot be passed via bind variables. Map selections through a fixed whitelist of SQL expressions, and cap the number of dimensions to prevent CUBE from generating too many grouping sets.

## 16. Process for choosing a construct

When designing a multi-level report, proceed in this order:

1. List every output data level needed: detail, regional total, product total, grand total.
2. Identify which dimensions form a natural hierarchy.
3. If you need totals along hierarchical prefixes, use ROLLUP.
4. If you need every combination of a small set of dimensions, use CUBE.
5. If you need only specific combinations, use GROUPING SETS.
6. If source data has real NULLs, add GROUPING or GROUPING_ID to distinguish subtotals.
7. If grouping sets could repeat, eliminate duplicates in the definition or check GROUP_ID.
8. Add an explicit ORDER BY for report ordering.
9. Use WHERE for source-row conditions and HAVING for group conditions.
10. Check grouping set counts, cardinality, execution plan, and TEMP usage on representative data.
11. In JDBC, return an aggregation-level code so the application layer can distinguish detail/summary rows.
12. If subtotal business rules require different datasets, consider separate query blocks instead of a single shared WHERE.

## 17. Common misconceptions

**ROLLUP and CUBE are the same.** False. ROLLUP generates prefixes according to expression order; CUBE generates every subset.

**ROLLUP(A,B) generates totals by A and totals by B.** False. It generates (A,B), (A), and (). To get a separate total by B, use CUBE or GROUPING SETS.

**GROUPING SETS automatically adds intermediate subtotals.** False. It generates only the exact grouping sets listed.

**GROUPING(expr)=1 means the source column is NULL.** False. It means the expression was rolled up out of the current grouping set.

**WHERE col IS NULL retrieves all total rows.** False. It can retrieve both real NULLs and subtotals; use GROUPING to distinguish them.

**A three-dimensional CUBE creates only three totals.** False. Three dimensions generate 2³ = 8 grouping sets.

**The order in GROUPING SETS is also the display order.** False. ORDER BY is required.

**GROUPING_ID always has the same code for the same level in every query.** False. The code depends on the argument list and order as well as the grouping sets structure.

**GROUP_ID is the same as GROUPING_ID.** False. GROUPING_ID encodes roll-up flags; GROUP_ID identifies duplicate groups generated by repeated grouping sets.

**CUBE is always better than UNION ALL.** False. CUBE can produce many unnecessary groups; UNION ALL can be cleaner when branches have different source logic. Choose by requirements and inspect the plan.

**GROUP BY ROLLUP guarantees row order.** False. Only a final ORDER BY determines return order.

**NULL in a subtotal row is data written into the table.** False. It is how rolled-up columns are represented in the query output.

**Simply adding GROUPING_ID is enough for an API.** Not necessarily. The application layer still needs to know the code convention, dimension order, real NULL types, and which aggregation levels exist in the query.
