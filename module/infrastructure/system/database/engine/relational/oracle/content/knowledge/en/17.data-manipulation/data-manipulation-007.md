# RETURNING INTO to Retrieve Values After INSERT, UPDATE, or DELETE in Oracle

In many data modification operations, the application immediately needs the values of the row just inserted, updated, or deleted. For example:

- After inserting an order, retrieve the ORDER_ID generated by a sequence or identity column.
- After updating a balance, retrieve the new balance to return to the application.
- After deleting a record, retrieve the ID and details of the deleted row for logging or returning a response.
- When updating multiple rows, collect all changed values for further processing in PL/SQL.

Oracle SQL provides the **RETURNING INTO** clause to return expressions from rows affected by a DML statement into PL/SQL variables or bind variables. As a result, when appropriate, the application does not need to run an extra SELECT just to read back the values it wrote.

RETURNING INTO can be used with INSERT, UPDATE, and DELETE. Usage depends on how many rows the DML affects:

- Single row: use scalar variables in INTO.
- Multiple rows: in PL/SQL, use BULK COLLECT INTO to gather results into collections.
- Zero rows: do not assume target variables were set to NULL or preserved according to a business rule; check SQL%ROWCOUNT.

This lesson covers syntax, examples per DML type, identity/sequence, bulk collect, SQL%ROWCOUNT, transactions, common limitations, and application patterns.

## 1. What Is RETURNING INTO?

RETURNING INTO is part of a DML statement allowing you to retrieve expressions from the rows the statement just affected.

General pattern:

~~~sql
INSERT INTO table_name (...)
VALUES (...)
RETURNING expression [, expression ...]
INTO variable [, variable ...];
~~~

~~~sql
UPDATE table_name
SET ...
WHERE ...
RETURNING expression [, expression ...]
INTO variable [, variable ...];
~~~

~~~sql
DELETE FROM table_name
WHERE ...
RETURNING expression [, expression ...]
INTO variable [, variable ...];
~~~

Expressions after RETURNING are placed into variables in exact positional order after INTO. The count of expressions and target variables must match; data types must be compatible.

RETURNING does not auto-COMMIT, does not replace transaction control, and does not mean data is committed for other sessions to see. It simply returns values of affected rows within the current transaction.

## 2. INSERT ... RETURNING INTO

### 2.1 Retrieving the Newly Generated Primary Key

Suppose we have an orders table:

~~~sql
CREATE TABLE orders (
    order_id      NUMBER PRIMARY KEY,
    customer_id   NUMBER NOT NULL,
    order_date    DATE DEFAULT SYSDATE NOT NULL,
    total_amount  NUMBER(12,2) NOT NULL,
    status        VARCHAR2(20) DEFAULT 'NEW' NOT NULL
);
~~~

If ORDER_ID is allocated from a sequence:

~~~sql
CREATE SEQUENCE orders_seq START WITH 1000 INCREMENT BY 1;
~~~

In PL/SQL:

~~~sql
DECLARE
    l_order_id orders.order_id%TYPE;
BEGIN
    INSERT INTO orders (
        order_id,
        customer_id,
        total_amount
    )
    VALUES (
        orders_seq.NEXTVAL,
        42,
        1250000
    )
    RETURNING order_id INTO l_order_id;

    DBMS_OUTPUT.PUT_LINE('New order id = ' || l_order_id);
END;
/
~~~

After INSERT, the ORDER_ID of the exact row inserted is placed into L_ORDER_ID. This is a reliable way to capture the key assigned to that row, instead of guessing sequence values or querying for the latest row.

### 2.2 Retrieving Multiple Columns After INSERT

~~~sql
DECLARE
    l_order_id    orders.order_id%TYPE;
    l_order_date  orders.order_date%TYPE;
    l_status      orders.status%TYPE;
BEGIN
    INSERT INTO orders (
        order_id,
        customer_id,
        total_amount
    )
    VALUES (
        orders_seq.NEXTVAL,
        42,
        1250000
    )
    RETURNING order_id, order_date, status
    INTO l_order_id, l_order_date, l_status;

    DBMS_OUTPUT.PUT_LINE(
        'Order=' || l_order_id ||
        ', date=' || TO_CHAR(l_order_date, 'YYYY-MM-DD HH24:MI:SS') ||
        ', status=' || l_status
    );
END;
/
~~~

ORDER_DATE and STATUS were omitted from INSERT, so the database applies DEFAULT. RETURNING retrieves the inserted row's values, including defaults generated by the statement.

### 2.3 Retrieving Values from an Identity Column

Oracle supports identity columns:

~~~sql
CREATE TABLE customers (
    customer_id NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_name VARCHAR2(100) NOT NULL,
    created_at TIMESTAMP DEFAULT SYSTIMESTAMP NOT NULL
);
~~~

When omitting CUSTOMER_ID from the INSERT list:

~~~sql
DECLARE
    l_customer_id customers.customer_id%TYPE;
    l_created_at  customers.created_at%TYPE;
BEGIN
    INSERT INTO customers (customer_name)
    VALUES ('Nguyen An')
    RETURNING customer_id, created_at
    INTO l_customer_id, l_created_at;

    DBMS_OUTPUT.PUT_LINE('Customer id = ' || l_customer_id);
END;
/
~~~

RETURNING captures the identity allocated for the inserted row. This avoids running a separate SELECT to look up the new row's key.

### 2.4 DEFAULT and Expressions in RETURNING

RETURNING can fetch multiple columns or valid expressions from the affected row:

~~~sql
DECLARE
    l_order_id orders.order_id%TYPE;
    l_amount   orders.total_amount%TYPE;
BEGIN
    INSERT INTO orders (
        order_id,
        customer_id,
        total_amount
    )
    VALUES (
        orders_seq.NEXTVAL,
        42,
        250000
    )
    RETURNING order_id, total_amount * 1.1
    INTO l_order_id, l_amount;

    DBMS_OUTPUT.PUT_LINE(
        'Id=' || l_order_id || ', amount with factor=' || l_amount
    );
END;
/
~~~

The second expression is a calculation on the inserted row's value. If you only need the raw column, return the column name directly for readability.

### 2.5 No Need for SELECT MAX(id) to Find the Newly Inserted Row

A common anti-pattern:

~~~sql
INSERT INTO customers (customer_name)
VALUES ('Nguyen An');

SELECT MAX(customer_id)
INTO l_customer_id
FROM customers;
~~~

MAX(customer_id) could belong to another session that inserted afterward, or an older row with a higher key under data rules. It does not identify the row created by the current INSERT.

RETURNING INTO binds the return value directly to the current DML:

~~~sql
INSERT INTO customers (customer_name)
VALUES ('Nguyen An')
RETURNING customer_id INTO l_customer_id;
~~~

When you need the sequence, identity, or default value of the exact row inserted, RETURNING is usually the clearest option.

## 3. UPDATE ... RETURNING INTO

### 3.1 Retrieving New Values After UPDATE

~~~sql
DECLARE
    l_new_salary employees.salary%TYPE;
BEGIN
    UPDATE employees
    SET salary = salary * 1.10
    WHERE employee_id = 100
    RETURNING salary INTO l_new_salary;

    IF SQL%ROWCOUNT = 1 THEN
        DBMS_OUTPUT.PUT_LINE('New salary = ' || l_new_salary);
    ELSE
        DBMS_OUTPUT.PUT_LINE('No employee updated');
    END IF;
END;
/
~~~

In this example, L_NEW_SALARY receives the row's SALARY after UPDATE. SQL%ROWCOUNT reports how many rows were affected by UPDATE.

### 3.2 Retrieving Multiple Columns After UPDATE

~~~sql
DECLARE
    l_salary    employees.salary%TYPE;
    l_updated_at employees.updated_at%TYPE;
BEGIN
    UPDATE employees
    SET salary = salary + 500000,
        updated_at = SYSTIMESTAMP
    WHERE employee_id = 100
    RETURNING salary, updated_at
    INTO l_salary, l_updated_at;

    IF SQL%ROWCOUNT = 1 THEN
        DBMS_OUTPUT.PUT_LINE(
            'Salary=' || l_salary ||
            ', updated=' || TO_CHAR(l_updated_at, 'YYYY-MM-DD HH24:MI:SS')
        );
    END IF;
END;
/
~~~

Each RETURNING expression is assigned to the variable at the matching position. Using `%TYPE` keeps PL/SQL variables aligned with table column types.

### 3.3 RETURNING Expressions Computed from New Values

~~~sql
DECLARE
    l_new_total NUMBER;
    l_adjusted  NUMBER;
BEGIN
    UPDATE orders
    SET total_amount = total_amount * 1.05
    WHERE order_id = 1001
    RETURNING total_amount, total_amount - 100
    INTO l_new_total, l_adjusted;
END;
/
~~~

Each expression has its own target variable in the same order as the RETURNING list. For UPDATE and DELETE, RETURNING supports simple expressions and certain single aggregate expressions; do not mix regular expressions with aggregates in the same list. For INSERT, RETURNING expressions must be simple expressions.

If you only need the raw column, return the column name directly for readability.

### 3.4 Old Values vs. New Values

In an UPDATE example:

~~~sql
UPDATE employees
SET salary = salary * 1.10
WHERE employee_id = 100
RETURNING salary INTO l_new_salary;
~~~

RETURNING retrieves the column's value in the row after UPDATE. If business logic needs both before and after values for auditing or calculating deltas, save the old value before modifying in a controlled workflow, use an appropriate audit table/trigger, or design a separate query per transaction requirements. Do not assume a single simple RETURNING variable captures both versions automatically.

PL/SQL example reading the old value first, then updating:

~~~sql
DECLARE
    l_old_salary employees.salary%TYPE;
    l_new_salary employees.salary%TYPE;
BEGIN
    SELECT salary
    INTO l_old_salary
    FROM employees
    WHERE employee_id = 100
    FOR UPDATE;

    UPDATE employees
    SET salary = salary * 1.10
    WHERE employee_id = 100
    RETURNING salary INTO l_new_salary;

    DBMS_OUTPUT.PUT_LINE(
        'Old=' || l_old_salary || ', new=' || l_new_salary
    );
END;
/
~~~

SELECT FOR UPDATE locks the read row until the transaction ends, coordinating the read-write workflow across concurrent sessions. Consider lock hold duration and exception handling in real applications.

## 4. DELETE ... RETURNING INTO

### 4.1 Retrieving Information from the Deleted Row

~~~sql
DECLARE
    l_order_id orders.order_id%TYPE;
    l_customer_id orders.customer_id%TYPE;
    l_amount orders.total_amount%TYPE;
BEGIN
    DELETE FROM orders
    WHERE order_id = 1001
    RETURNING order_id, customer_id, total_amount
    INTO l_order_id, l_customer_id, l_amount;

    IF SQL%ROWCOUNT = 1 THEN
        DBMS_OUTPUT.PUT_LINE(
            'Deleted order=' || l_order_id ||
            ', customer=' || l_customer_id ||
            ', amount=' || l_amount
        );
    ELSE
        DBMS_OUTPUT.PUT_LINE('No order deleted');
    END IF;
END;
/
~~~

DELETE removes the row from the table in the current transaction, yet RETURNING still supplies the deleted row's values to the target variables. This is useful when you need to record details before committing.

### 4.2 Logging After DELETE

You can capture keys and values to log, then insert into an audit table:

~~~sql
DECLARE
    l_order_id orders.order_id%TYPE;
    l_amount   orders.total_amount%TYPE;
BEGIN
    DELETE FROM orders
    WHERE order_id = 1001
    RETURNING order_id, total_amount
    INTO l_order_id, l_amount;

    IF SQL%ROWCOUNT = 1 THEN
        INSERT INTO order_delete_log (
            order_id,
            deleted_amount,
            logged_at
        )
        VALUES (
            l_order_id,
            l_amount,
            SYSTIMESTAMP
        );
    END IF;
END;
/
~~~

Both DML statements belong to the same transaction. If the transaction rolls back, both DELETE and the log INSERT roll back, unless the system intentionally uses an autonomous transaction for auditing by specific design. Do not arbitrarily put COMMIT inside a procedure sharing the application's transaction.

### 4.3 RETURNING Does Not Restore Deleted Rows

RETURNING only copies the deleted row's values into variables. It does not retain a permanent copy and does not replace backups, flashback, auditing, or data recovery mechanisms. If a row must be restored, use transaction rollback before commit or an appropriate recovery mechanism afterward.

## 5. Single Row vs. Multiple Rows: INTO or BULK COLLECT INTO?

This is the most important distinction when using RETURNING in PL/SQL.

### 5.1 DML Expected to Affect Exactly One Row

With a primary key:

~~~sql
UPDATE employees
SET salary = salary + 100
WHERE employee_id = 100
RETURNING salary INTO l_salary;
~~~

If the predicate guarantees at most one row, a scalar variable is suitable. Still check SQL%ROWCOUNT to handle the zero-row case.

### 5.2 DML Affecting Multiple Rows

If UPDATE can modify multiple rows, use BULK COLLECT INTO to receive all returned values into collections:

~~~sql
DECLARE
    TYPE t_employee_ids IS TABLE OF employees.employee_id%TYPE;
    TYPE t_salaries IS TABLE OF employees.salary%TYPE;

    l_employee_ids t_employee_ids;
    l_salaries     t_salaries;
BEGIN
    UPDATE employees
    SET salary = salary * 1.05
    WHERE department_id = 10
    RETURNING employee_id, salary
    BULK COLLECT INTO l_employee_ids, l_salaries;

    DBMS_OUTPUT.PUT_LINE('Updated rows = ' || SQL%ROWCOUNT);

    FOR i IN 1 .. l_employee_ids.COUNT LOOP
        DBMS_OUTPUT.PUT_LINE(
            'Employee=' || l_employee_ids(i) ||
            ', new salary=' || l_salaries(i)
        );
    END LOOP;
END;
/
~~~

Each collection receives one RETURNING column. Collections correspond by index; the i-th element of L_EMPLOYEE_IDS and L_SALARIES belong to the same returned DML row.

### 5.3 Multi-Row DELETE with BULK COLLECT

~~~sql
DECLARE
    TYPE t_order_ids IS TABLE OF orders.order_id%TYPE;
    TYPE t_customer_ids IS TABLE OF orders.customer_id%TYPE;

    l_order_ids    t_order_ids;
    l_customer_ids t_customer_ids;
BEGIN
    DELETE FROM orders
    WHERE status = 'CANCELLED'
      AND order_date < DATE '2025-01-01'
    RETURNING order_id, customer_id
    BULK COLLECT INTO l_order_ids, l_customer_ids;

    DBMS_OUTPUT.PUT_LINE('Deleted rows = ' || SQL%ROWCOUNT);

    FOR i IN 1 .. l_order_ids.COUNT LOOP
        DBMS_OUTPUT.PUT_LINE(
            'Deleted order=' || l_order_ids(i) ||
            ', customer=' || l_customer_ids(i)
        );
    END LOOP;
END;
/
~~~

This is a multi-row DML example. Ensure the DELETE predicate has the exact scope and understand foreign key, trigger, and retention impacts before running on live data.

### 5.4 Single-Row INSERT vs. Multi-Row INSERT

INSERT ... VALUES is the simple case for scalar RETURNING INTO:

~~~sql
INSERT INTO customers (customer_name)
VALUES ('Lan')
RETURNING customer_id INTO l_customer_id;
~~~

For multi-row inserts, RETURNING availability depends on the INSERT form and Oracle version restrictions. Never assume an INSERT ... SELECT or multitable INSERT can use RETURNING like INSERT ... VALUES. With PL/SQL bulk DML, FORALL combined with RETURNING BULK COLLECT INTO is a pattern to review for your exact statement type and Oracle version. If a specific syntax does not support RETURNING, use staging/correlated keys or query by known keys rather than guessing newly inserted rows with MAX(id).

### 5.5 FORALL and RETURNING BULK COLLECT INTO

FORALL dispatches a DML operation across a collection's index range, reducing context switches between the PL/SQL engine and SQL engine. Example illustrating updating multiple employees by ID list:

~~~sql
DECLARE
    TYPE t_ids IS TABLE OF employees.employee_id%TYPE;
    TYPE t_new_salaries IS TABLE OF employees.salary%TYPE;

    l_ids          t_ids := t_ids(101, 102, 103);
    l_new_salaries t_new_salaries;
BEGIN
    FORALL i IN 1 .. l_ids.COUNT
        UPDATE employees
        SET salary = salary + 100
        WHERE employee_id = l_ids(i)
        RETURNING salary BULK COLLECT INTO l_new_salaries;

    FOR i IN 1 .. l_new_salaries.COUNT LOOP
        DBMS_OUTPUT.PUT_LINE('New salary=' || l_new_salaries(i));
    END LOOP;
END;
/
~~~

With FORALL and DML RETURNING, carefully review the collection and result-mapping rules of your Oracle/PLSQL version, especially when an iteration affects zero rows or multiple rows. If each result must map back to its exact input key, design result structures and test zero-row and multi-row cases rather than assuming output indices always match input indices.

## 6. SQL%ROWCOUNT and Zero-Row Cases

### 6.1 Checking How Many Rows DML Affected

In PL/SQL, SQL%ROWCOUNT is an implicit cursor attribute reporting how many rows the most recent DML statement affected:

~~~sql
UPDATE employees
SET salary = salary + 100
WHERE employee_id = -1
RETURNING salary INTO l_salary;

IF SQL%ROWCOUNT = 0 THEN
    DBMS_OUTPUT.PUT_LINE('No row was updated');
END IF;
~~~

If no row satisfies WHERE, no new value is returned. Do not read the RETURNING variable as if it were guaranteed to be set to NULL. The safe approach is checking SQL%ROWCOUNT immediately after DML and only using results per actual row count.

### 6.2 Do Not Use SQL%ROWCOUNT After Another SQL Statement

SQL%ROWCOUNT describes the most recent SQL statement. Running another SELECT or DML before checking overwrites the attribute for the new statement.

Save it immediately:

~~~sql
UPDATE employees
SET salary = salary + 100
WHERE department_id = 10
RETURNING employee_id BULK COLLECT INTO l_employee_ids;

l_updated_count := SQL%ROWCOUNT;
~~~

Then use L_UPDATED_COUNT in subsequent processing.

### 6.3 SELECT INTO and RETURNING INTO Do Not Behave Identically

SELECT ... INTO scalar variables normally raises NO_DATA_FOUND on zero rows and TOO_MANY_ROWS on multiple rows. DML RETURNING follows its own rules; do not mechanically apply SELECT INTO expectations to RETURNING variables when DML affects zero or multiple rows.

Design around key cardinality:

- Single row: check SQL%ROWCOUNT = 1.
- Zero rows: handle not found.
- Multiple rows: use BULK COLLECT where supported.

## 7. RETURNING with SQL*Plus and Bind Variables

In SQL*Plus or compatible environments, you can declare a bind variable and use a colon in RETURNING INTO:

~~~sql
VARIABLE b_customer_id NUMBER

INSERT INTO customers (customer_name)
VALUES ('Mai')
RETURNING customer_id INTO :b_customer_id;

PRINT b_customer_id
~~~

Bind variables belong to the client session. The colon distinguishes a SQL bind variable from a PL/SQL variable name.

UPDATE example:

~~~sql
VARIABLE b_salary NUMBER

UPDATE employees
SET salary = salary + 500
WHERE employee_id = 101
RETURNING salary INTO :b_salary;

PRINT b_salary
~~~

Bind variable display and syntax support can differ across SQL*Plus, SQLcl, SQL Developer, and application drivers. If the environment does not support direct bind invocation, wrap DML in a PL/SQL block or use the appropriate output-bind API.

## 8. Using RETURNING in Applications

### 8.1 Purpose of Output Binds

In applications, RETURNING INTO corresponds to sending input binds and receiving output binds from DML. Example creating a customer:

~~~sql
INSERT INTO customers (customer_name)
VALUES (:customer_name)
RETURNING customer_id INTO :new_customer_id
~~~

CUSTOMER_NAME is an input bind; NEW_CUSTOMER_ID is an output bind. How output binds are registered depends on the driver and framework. With Oracle JDBC, use Oracle driver support for RETURNING or wrap the DML in a PL/SQL procedure returning an OUT parameter; do not assume every standard JDBC PreparedStatement automatically understands Oracle output-bind syntax via the same API.

### 8.2 Wrapping in a Stored Procedure

A clean interface is creating a procedure with an OUT parameter:

~~~sql
CREATE OR REPLACE PROCEDURE create_customer (
    p_customer_name IN customers.customer_name%TYPE,
    p_customer_id OUT customers.customer_id%TYPE
)
AS
BEGIN
    INSERT INTO customers (customer_name)
    VALUES (p_customer_name)
    RETURNING customer_id INTO p_customer_id;
END;
/
~~~

The application calls the procedure and reads P_CUSTOMER_ID via the OUT parameter per driver API. The procedure does not auto-COMMIT; the transaction remains under caller control unless designed otherwise.

### 8.3 Do Not Re-Query by Non-Unique Data

After INSERT, do not SELECT by CUSTOMER_NAME if names are not UNIQUE:

~~~sql
SELECT customer_id
FROM customers
WHERE customer_name = :customer_name;
~~~

The query can return multiple rows or pick the wrong record. RETURNING retrieves the key of the exact row the DML just created.

## 9. RETURNING and Transactions

### 9.1 RETURNING Does Not COMMIT

~~~sql
INSERT INTO customers (customer_name)
VALUES ('Hoa')
RETURNING customer_id INTO l_customer_id;
~~~

Immediately after the statement, the current transaction sees the inserted row and the variable holds the key. Other sessions do not see uncommitted data by default.

COMMIT is controlled separately:

~~~sql
COMMIT;
~~~

Or roll back:

~~~sql
ROLLBACK;
~~~

On rollback, the inserted row is gone from the rolled-back transaction, even though the PL/SQL variable still holds the key value returned earlier by RETURNING. The variable preserves the value it received; it does not prove the row still exists or was committed.

### 9.2 Do Not Arbitrarily Commit Inside Procedures

Procedures shared across multiple application flows should normally let the caller decide COMMIT/ROLLBACK, unless transaction boundaries are explicitly designed otherwise. A COMMIT inside a procedure can commit other caller changes in the same transaction.

### 9.3 RETURNING Does Not Guarantee Values Will Not Change Later

The returned value reflects the DML operation just executed. Another transaction can update the row once locks are released/the transaction ends. If you need the latest state at a later point, re-query by key under appropriate transaction semantics.

## 10. Triggers, Defaults, and Generated Columns

RETURNING is useful when a table has defaults or identity columns:

~~~sql
INSERT INTO customers (customer_name)
VALUES ('Hoa')
RETURNING customer_id, created_at
INTO l_customer_id, l_created_at;
~~~

Columns omitted from INSERT receive defaults or identity values per table definition. RETURNING lets you retrieve those columns directly from the affected row.

If the table has triggers that modify column values or execute secondary DML, check the exact semantics of the trigger and your Oracle version. Do not assume RETURNING is a snapshot of all trigger side effects or related tables. Only retrieve DML row columns supported by RETURNING; if complex audit data is required, design a dedicated audit/trigger mechanism.

## 11. Limitations and Edge Cases to Watch

RETURNING INTO is convenient, but it does not apply unconditionally to every DML form.

Limitations to verify per Oracle version:

- RETURNING cannot be used with certain remote DML (remote objects) or parallel DML.
- Do not use RETURNING as if a multitable INSERT could return a normal result set.
- DML on views with INSTEAD OF triggers has specific restrictions with RETURNING.
- Oracle does not support RETURNING on INSERT with a subquery (such as INSERT ... SELECT); INSERT ... VALUES is the pattern used in identity-retrieval examples in this lesson. If you need to insert from a query and collect keys, design an alternative workflow with explicit correlated keys.
- Multi-row DML requires appropriate collection/bulk patterns; never use scalar targets as if only one row existed.
- Arbitrary aggregate expressions or subqueries cannot be mixed freely in the RETURNING list; the list must obey RETURNING clause rules.
- Per the SQL Language Reference: do not use RETURNING with remote objects or parallel DML; cannot return LONG types; cannot be used on views with INSTEAD OF triggers. In certain cases, an UPDATE with a BEFORE UPDATE trigger may reject a RETURNING list containing primary key or NOT NULL columns depending on version rules.

If a statement reports a syntax error or unsupported RETURNING construct, do not work around it by picking MAX(id) or guessing the modified row. Identify the version, DML type, and object type, and choose an alternative with explicit correlated keys.

## 12. Comparing RETURNING INTO vs. Re-Querying After DML

| Criterion | RETURNING INTO | SELECT after DML |
|---|---|---|
| Retrieving newly inserted key | Directly from the inserted row | Requires knowing key or unique lookup condition |
| Retrieving values after UPDATE | Returns values of updated row | Re-query by key |
| Retrieving deleted row data | Can return deleted row values | Cannot SELECT deleted row under normal transaction state |
| Round trips | Combines DML and output | Typically requires an extra statement |
| Multi-row data | Use BULK COLLECT where supported | SELECT by key / key list |
| Scope of support | Restricted by DML form/object type | More flexible, though requires explicit keys and semantics |

RETURNING is ideal when you need values from the exact row modified by DML. SELECT after DML fits when you need data from other tables, values computed by complex queries, or when the specific DML form does not support RETURNING.

## 13. Complete Example: Create Order and Return Key

~~~sql
CREATE TABLE lab_orders_returning (
    order_id      NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id   NUMBER NOT NULL,
    total_amount  NUMBER(12,2) NOT NULL,
    status        VARCHAR2(20) DEFAULT 'NEW' NOT NULL,
    created_at    TIMESTAMP DEFAULT SYSTIMESTAMP NOT NULL
);
~~~

PL/SQL block:

~~~sql
DECLARE
    l_order_id    lab_orders_returning.order_id%TYPE;
    l_status      lab_orders_returning.status%TYPE;
    l_created_at  lab_orders_returning.created_at%TYPE;
BEGIN
    INSERT INTO lab_orders_returning (
        customer_id,
        total_amount
    )
    VALUES (
        42,
        875000
    )
    RETURNING order_id, status, created_at
    INTO l_order_id, l_status, l_created_at;

    DBMS_OUTPUT.PUT_LINE(
        'Created order ' || l_order_id ||
        ', status=' || l_status ||
        ', at=' || TO_CHAR(l_created_at, 'YYYY-MM-DD HH24:MI:SS')
    );
END;
/
~~~

Points to observe:

1. ORDER_ID is allocated by the identity column.
2. STATUS and CREATED_AT receive DEFAULT values.
3. RETURNING brings all three values into variables in the same block.
4. There is no COMMIT in the block; the caller decides when the transaction ends.

## 14. Complete Example: Update and Return Multiple Rows

~~~sql
DECLARE
    TYPE t_ids IS TABLE OF employees.employee_id%TYPE;
    TYPE t_salaries IS TABLE OF employees.salary%TYPE;

    l_ids t_ids;
    l_salaries t_salaries;
    l_count PLS_INTEGER;
BEGIN
    UPDATE employees
    SET salary = salary + 250
    WHERE department_id = 20
    RETURNING employee_id, salary
    BULK COLLECT INTO l_ids, l_salaries;

    l_count := SQL%ROWCOUNT;
    DBMS_OUTPUT.PUT_LINE('Rows updated = ' || l_count);

    FOR i IN 1 .. l_ids.COUNT LOOP
        DBMS_OUTPUT.PUT_LINE(
            'Employee ' || l_ids(i) ||
            ' now has salary ' || l_salaries(i)
        );
    END LOOP;
END;
/
~~~

This is the pattern when UPDATE can affect multiple rows. BULK COLLECT gathers returned values into collections; SQL%ROWCOUNT reports total affected rows. If row count can be very large, consider PGA memory and appropriate batching.

## 15. Complete Example: Delete and Log Row Details

~~~sql
DECLARE
    l_order_id orders.order_id%TYPE;
    l_amount   orders.total_amount%TYPE;
BEGIN
    DELETE FROM orders
    WHERE order_id = 2001
    RETURNING order_id, total_amount
    INTO l_order_id, l_amount;

    IF SQL%ROWCOUNT = 1 THEN
        INSERT INTO order_delete_log (
            order_id,
            deleted_amount,
            logged_at
        )
        VALUES (
            l_order_id,
            l_amount,
            SYSTIMESTAMP
        );
    ELSE
        DBMS_OUTPUT.PUT_LINE('Order not found');
    END IF;
END;
/
~~~

DELETE and the log INSERT belong to the current transaction. If you need to ensure the log is not rolled back along with the main data, that is a separate audit requirement needing an intentionally designed transaction boundary.

## 16. Self-Practice Lab

Lab tables in this section should be created in a dedicated practice schema with appropriate privileges. Never run experimental DDL/DML on production schemas. Oracle DDL performs an implicit commit.

### 16.1 Create Table

~~~sql
CREATE TABLE lab_returning_demo (
    item_id     NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    item_name   VARCHAR2(80) NOT NULL,
    quantity    NUMBER(10) NOT NULL,
    unit_price  NUMBER(12,2) NOT NULL,
    updated_at  TIMESTAMP DEFAULT SYSTIMESTAMP NOT NULL
);
~~~

### 16.2 INSERT and Retrieve Identity/Default

~~~sql
DECLARE
    l_item_id lab_returning_demo.item_id%TYPE;
    l_updated_at lab_returning_demo.updated_at%TYPE;
BEGIN
    INSERT INTO lab_returning_demo (
        item_name,
        quantity,
        unit_price
    )
    VALUES (
        'Keyboard',
        5,
        450000
    )
    RETURNING item_id, updated_at
    INTO l_item_id, l_updated_at;

    DBMS_OUTPUT.PUT_LINE(
        'Item id=' || l_item_id ||
        ', created at=' || TO_CHAR(l_updated_at, 'YYYY-MM-DD HH24:MI:SS')
    );
END;
/
~~~

### 16.3 UPDATE and Retrieve New Values

~~~sql
DECLARE
    l_quantity lab_returning_demo.quantity%TYPE;
    l_price lab_returning_demo.unit_price%TYPE;
BEGIN
    UPDATE lab_returning_demo
    SET quantity = quantity + 2,
        unit_price = unit_price * 1.05,
        updated_at = SYSTIMESTAMP
    WHERE item_name = 'Keyboard'
    RETURNING quantity, unit_price
    INTO l_quantity, l_price;

    IF SQL%ROWCOUNT = 1 THEN
        DBMS_OUTPUT.PUT_LINE(
            'Quantity=' || l_quantity || ', price=' || l_price
        );
    END IF;
END;
/
~~~

### 16.4 DELETE and Retrieve Deleted Values

~~~sql
DECLARE
    l_item_id lab_returning_demo.item_id%TYPE;
    l_item_name lab_returning_demo.item_name%TYPE;
BEGIN
    DELETE FROM lab_returning_demo
    WHERE item_name = 'Keyboard'
    RETURNING item_id, item_name
    INTO l_item_id, l_item_name;

    IF SQL%ROWCOUNT = 1 THEN
        DBMS_OUTPUT.PUT_LINE(
            'Deleted item ' || l_item_id || ': ' || l_item_name
        );
    ELSE
        DBMS_OUTPUT.PUT_LINE('No matching item');
    END IF;
END;
/
~~~

### 16.5 DML Affecting Zero Rows

~~~sql
DECLARE
    l_quantity lab_returning_demo.quantity%TYPE;
BEGIN
    UPDATE lab_returning_demo
    SET quantity = quantity + 1
    WHERE item_id = -999
    RETURNING quantity INTO l_quantity;

    IF SQL%ROWCOUNT = 0 THEN
        DBMS_OUTPUT.PUT_LINE('No row updated');
    END IF;
END;
/
~~~

Notice that the zero-row branch relies on SQL%ROWCOUNT, not on a particular value of L_QUANTITY.

## 17. Common Errors

| Error / Misconception | Reality | How to handle |
|---|---|---|
| RETURNING auto-COMMITs | It only returns values inside the current transaction | Manage COMMIT/ROLLBACK separately |
| RETURNING only works with INSERT | Works with INSERT, UPDATE, and DELETE within supported scope | Choose the right DML and syntax |
| SELECT MAX(id) is how to get the new key | May capture another session's or another row's key | Use RETURNING on the inserted row |
| DEFAULT cannot be retrieved after INSERT | You can return columns receiving defaults/identity | List columns in RETURNING |
| A scalar variable can receive multiple rows | Multi-row DML requires appropriate bulk collections | Use BULK COLLECT INTO |
| Zero-row RETURNING assigns NULL | Do not rely on target variable state | Check SQL%ROWCOUNT |
| SQL%ROWCOUNT can be read after several statements | It describes the most recent SQL statement | Save it immediately after DML |
| RETURNING proves rows are committed | Data may still be uncommitted or later rolled back | Distinguish returned values from transaction state |
| DELETE cannot return deleted columns | RETURNING can return values of the deleted row | Specify needed columns in RETURNING |
| RETURNING automatically fetches both OLD and NEW in every version | Check syntax/version; basic pattern returns supported DML expressions | Save old values separately if needed |
| Every INSERT form supports RETURNING | Certain INSERT forms have restrictions | Check SQL Language Reference for your version |
| NOT FOUND can be handled via TOO_MANY_ROWS like SELECT INTO | DML RETURNING has its own semantics | Use SQL%ROWCOUNT and bulk patterns |
| RETURNING replaces auditing | It only returns values to the caller | Design audits/triggers per requirements |
| RETURNING prevents duplicate inserts | It does not lock a nonexistent condition | Use UNIQUE constraints and handle duplicates |

## 18. Checklist Before Using RETURNING INTO

Before adding DML into an application or procedure, check:

1. Is the DML an INSERT, UPDATE, or DELETE?
2. Is the statement expected to affect at most one row or multiple rows?
3. Are RETURNING expressions in the exact order and type-compatible with target variables?
4. If INSERT uses identity/defaults, are the needed columns listed?
5. If UPDATE needs old and new values, is capturing old values designed clearly?
6. If DELETE needs auditing, does the log share the same transaction or use a separate one?
7. Is SQL%ROWCOUNT checked immediately after DML?
8. On zero rows, does code avoid reading unassigned RETURNING variables?
9. On multiple rows, is BULK COLLECT used with appropriate memory management?
10. Do the INSERT/DML form and target object fall within your Oracle version's RETURNING limits?
11. How does the caller control COMMIT/ROLLBACK?
12. For uniqueness, is a proper constraint in place rather than relying only on NOT EXISTS/RETURNING?

## 19. Summary

RETURNING INTO is an Oracle SQL mechanism that retrieves values from rows affected by INSERT, UPDATE, or DELETE into PL/SQL or bind variables:

- INSERT commonly uses RETURNING to capture identity, sequence keys, or default values of the inserted row.
- UPDATE uses RETURNING to capture post-update values of affected rows.
- DELETE uses RETURNING to capture details of deleted rows, useful for logging or further processing within the transaction.
- Single-row DML uses scalar INTO; multi-row DML in PL/SQL uses BULK COLLECT INTO where statement structure permits.
- SQL%ROWCOUNT reports affected row count; check it immediately after DML and do not assume target variables hold valid values when zero rows matched.
- RETURNING does not auto-COMMIT and does not replace transaction control, auditing, or constraints.
- Certain DML forms and object types have support restrictions; verify syntax against your deployed Oracle version.

When you need values from the exact row just modified, RETURNING INTO keeps statements concise and avoids re-querying on non-unique predicates. Combine it with appropriate keys/constraints, explicit zero-row and multi-row handling, and intentional transaction boundaries.
