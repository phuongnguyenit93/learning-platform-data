# SQL BOOLEAN, Identifier Limits, and New Syntax by Supported Release

Oracle Database adds many SQL capabilities with each release. A notable change in the Oracle Database 23c/23ai line is the **BOOLEAN data type in SQL**: previously PL/SQL had BOOLEAN for a long time, but SQL table columns could not be declared with this type as a regular data type. Newer releases also add several DDL and query syntaxes that make statements more concise.

Alongside new syntax, Oracle enforces identifier length limits that depend on the version and the **COMPATIBLE** parameter. Older systems were typically limited to 30 bytes; from Oracle Database 12.2 onward, most identifiers can be up to 128 bytes long when the compatibility level permits. This change directly affects table, column, index, constraint, sequence, package, and ORM-generated names.

When developing applications or writing migrations, simultaneously verify:

- The actual database release.
- The COMPATIBLE value.
- Data types and syntax supported by that release.
- The application's JDBC driver and ORM dialect.
- Other databases/versions with which the schema or SQL must remain compatible.

A SQL statement that runs on a new development database does not mean it will run on an older production system. Do not enable new syntax solely based on the version name seen in a banner; confirm compatibility settings and the entire client stack.

## 1. SQL BOOLEAN and PL/SQL BOOLEAN

A Boolean represents a logical value. In SQL, the states you typically need to understand are:

- TRUE: condition is true.
- FALSE: condition is false.
- UNKNOWN: undetermined, usually due to a NULL value.

Before Oracle Database 23c, PL/SQL already supported BOOLEAN variables:

~~~sql
DECLARE
  l_enabled BOOLEAN := TRUE;
BEGIN
  IF l_enabled THEN
    DBMS_OUTPUT.PUT_LINE('Enabled');
  END IF;
END;
/
~~~

However, on older Oracle releases, you could not declare a regular table column with the SQL BOOLEAN type:

~~~sql
-- Cannot be used as a SQL column on older releases
CREATE TABLE feature_flag (
  flag_id NUMBER PRIMARY KEY,
  enabled BOOLEAN
);
~~~

This is an important distinction: PL/SQL BOOLEAN is a data type within the PL/SQL language; it does not mean the SQL engine has a BOOLEAN type to store in tables, query, or bind as a SQL datatype.

Oracle Database 23c brings BOOLEAN into SQL. Oracle Database 23ai continues the release line supporting SQL BOOLEAN. When using this feature, verify the exact release, COMPATIBLE level, JDBC driver, and Hibernate version being deployed.

## 2. Declaring a BOOLEAN Column on Supported Oracle Releases

On Oracle Database 23c/23ai supporting SQL BOOLEAN, you can declare:

~~~sql
CREATE TABLE feature_flag (
  flag_id   NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  flag_name VARCHAR2(100) NOT NULL,
  enabled   BOOLEAN DEFAULT FALSE NOT NULL
);
~~~

Insert:

~~~sql
INSERT INTO feature_flag(flag_name, enabled)
VALUES ('new-checkout', TRUE);

INSERT INTO feature_flag(flag_name, enabled)
VALUES ('legacy-report', FALSE);
~~~

Query:

~~~sql
SELECT flag_id,
       flag_name,
       enabled
  FROM feature_flag
 WHERE enabled = TRUE;
~~~

Update:

~~~sql
UPDATE feature_flag
   SET enabled = FALSE
 WHERE flag_name = 'legacy-report';
~~~

SQL BOOLEAN is a true logical type. You do not need to convert every value to Y/N strings or 1/0 numbers once the database supports this type. However, applications must still standardize mapping and binding across JDBC, JPA/Hibernate, and the schema.

### BOOLEAN Can Be NULL

If NOT NULL is not declared, a BOOLEAN column can accept NULL. In that case, it has three logical states:

| Value | Meaning |
|---|---|
| TRUE | True |
| FALSE | False |
| NULL / UNKNOWN | Unknown or not yet set |

If the business logic only has two states, declare NOT NULL with an appropriate default. If NULL has its own meaning, preserve the third state in the model and test it explicitly.

## 3. Three-Valued Logic: TRUE, FALSE, and UNKNOWN

SQL uses three-valued logic for expressions that can evaluate to NULL. A condition's result is not always TRUE or FALSE.

Some rules:

| A | B | A AND B | A OR B |
|---|---|---|---|
| TRUE | TRUE | TRUE | TRUE |
| TRUE | FALSE | FALSE | TRUE |
| TRUE | UNKNOWN | UNKNOWN | TRUE |
| FALSE | UNKNOWN | FALSE | UNKNOWN |
| FALSE | FALSE | FALSE | FALSE |
| UNKNOWN | UNKNOWN | UNKNOWN | UNKNOWN |

For NOT:

| A | NOT A |
|---|---|
| TRUE | FALSE |
| FALSE | TRUE |
| UNKNOWN | UNKNOWN |

Example:

~~~sql
SELECT flag_name
  FROM feature_flag
 WHERE enabled = TRUE;
~~~

The condition selects only rows where enabled is TRUE. Rows with FALSE or NULL are not selected. Therefore, if the application needs to distinguish "disabled" from "undecided," do not silently merge NULL into FALSE.

### IS NULL and Checking State

~~~sql
SELECT flag_name
  FROM feature_flag
 WHERE enabled IS NULL;
~~~

Check the undetermined state with IS NULL; do not use enabled = NULL, because comparing against NULL returns UNKNOWN.

When handling business logic, write conditions explicitly:

~~~sql
SELECT flag_name,
       CASE
         WHEN enabled = TRUE THEN 'ON'
         WHEN enabled = FALSE THEN 'OFF'
         ELSE 'UNSET'
       END AS enabled_state
  FROM feature_flag;
~~~

### BOOLEAN and WHERE

In supported releases, Boolean expressions can be used as SQL conditions. Writing `enabled = TRUE` explicitly is often easier to read in examples and avoids confusion when a team is unfamiliar with the new syntax.

Do not use `= 1` or `= 'Y'` for a BOOLEAN column. Those values belong to legacy models storing Booleans as NUMBER or CHAR.

## 4. CHECK Constraints and Defaults for BOOLEAN

With a BOOLEAN column, the value domain is already constrained by the datatype. You can declare a default and NOT NULL:

~~~sql
CREATE TABLE notification_setting (
  setting_id NUMBER PRIMARY KEY,
  is_enabled BOOLEAN DEFAULT TRUE NOT NULL
);
~~~

NOT NULL is more important than an additional CHECK constraint when the business requires two states. A CHECK expression generally does not reject NULL because UNKNOWN is not treated as FALSE under constraint checking rules.

Example:

~~~sql
CREATE TABLE notification_setting (
  setting_id NUMBER PRIMARY KEY,
  is_enabled BOOLEAN,
  CONSTRAINT ck_notification_enabled
    CHECK (is_enabled IN (TRUE, FALSE))
);
~~~

The constraint above does not replace NOT NULL if the undetermined state must be forbidden. Use:

~~~sql
is_enabled BOOLEAN DEFAULT TRUE NOT NULL
~~~

When reading schemas or writing migrations, do not assume a CHECK constraint automatically forbids NULL.

## 5. BOOLEAN in PL/SQL and SQL on Newer Releases

Before SQL BOOLEAN was supported, PL/SQL could derive Booleans from logic inside a procedure but could not store them directly into a SQL BOOLEAN column because that datatype did not exist in SQL.

A legacy procedure might use NUMBER or CHAR to exchange states with SQL:

~~~sql
DECLARE
  l_enabled BOOLEAN := TRUE;
  l_flag_number NUMBER;
BEGIN
  IF l_enabled THEN
    l_flag_number := 1;
  ELSE
    l_flag_number := 0;
  END IF;

  UPDATE feature_flag_legacy
     SET enabled_number = l_flag_number
   WHERE flag_id = 10;
END;
/
~~~

On releases supporting SQL BOOLEAN, SQL and PL/SQL can use this datatype directly in contexts permitted by the release documentation. However, distinguish between:

- The data type in the PL/SQL language.
- The SQL datatype in a table/column.
- The JDBC type used to bind and read.
- The Java type mapped by the ORM.

A feature existing in the database does not mean every JDBC/Hibernate version automatically maps it correctly. Verify the full driver and framework chain.

## 6. JDBC: Binding and Reading SQL BOOLEAN

With an Oracle JDBC driver that supports SQL BOOLEAN, you can use the JDBC Boolean APIs as supported by the driver:

~~~java
String sql =
    "insert into feature_flag(flag_id, flag_name, enabled) " +
    "values (?, ?, ?)";

try (PreparedStatement statement =
         connection.prepareStatement(sql)) {
    statement.setLong(1, 100L);
    statement.setString(2, "new-checkout");
    statement.setBoolean(3, true);
    statement.executeUpdate();
}
~~~

Reading:

~~~java
String sql =
    "select enabled from feature_flag where flag_id = ?";

try (PreparedStatement statement =
         connection.prepareStatement(sql)) {
    statement.setLong(1, 100L);

    try (ResultSet resultSet = statement.executeQuery()) {
        if (resultSet.next()) {
            boolean enabled = resultSet.getBoolean("enabled");
            boolean wasNull = resultSet.wasNull();
        }
    }
}
~~~

ResultSet.getBoolean() returns false when the SQL value is NULL; call wasNull() immediately after that read to distinguish NULL from FALSE. If the business logic needs three states, do not skip this step.

API and SQL type support depend on the Oracle JDBC driver version. Use a driver supported for your database release and application JDK, then test setBoolean, getBoolean, NULL, and prepared statements against a real Oracle instance.

## 7. BOOLEAN in Spring Data JPA and Hibernate

In Java, the types commonly used are Boolean or boolean:

- boolean only has TRUE/FALSE.
- Boolean can be TRUE/FALSE/NULL.

If the SQL BOOLEAN column is nullable, use Boolean to preserve the third state. If the schema declares NOT NULL, you can use boolean or Boolean with appropriate validation.

Illustrative entity example:

~~~java
@Entity
@Table(name = "FEATURE_FLAG")
public class FeatureFlag {

    @Id
    @Column(name = "FLAG_ID")
    private Long id;

    @Column(name = "FLAG_NAME", nullable = false)
    private String flagName;

    @Column(name = "ENABLED", nullable = false)
    private Boolean enabled;
}
~~~

Whether Hibernate maps Java Boolean to Oracle SQL BOOLEAN or another compatible type depends on:

- Hibernate version.
- Oracle dialect.
- Oracle JDBC driver.
- Database release and COMPATIBLE.
- DDL generated by migrations.

Do not assume a Boolean annotation will always produce a SQL BOOLEAN column across all Oracle versions. If the production schema uses the new BOOLEAN type, integration tests must run on a supported Oracle release and verify the actual DDL/mapping.

### Avoid Letting Hibernate Auto-Generate a Schema Differing from Migrations

If Flyway or Liquibase manages the schema, let migrations define the exact datatype and use:

~~~yaml
spring:
  jpa:
    hibernate:
      ddl-auto: validate
~~~

Do not use create or update in production to let the framework decide Boolean column types when the application must support multiple Oracle releases.

## 8. Older Releases: NUMBER(1) or CHAR(1)

Before Oracle Database 23c, the common approach was representing Booleans using another SQL type. Two common choices:

**NUMBER(1):**

~~~sql
CREATE TABLE feature_flag_legacy (
  flag_id NUMBER PRIMARY KEY,
  enabled NUMBER(1) DEFAULT 0 NOT NULL,
  CONSTRAINT ck_feature_flag_enabled
    CHECK (enabled IN (0, 1))
);
~~~

- 1 represents TRUE.
- 0 represents FALSE.
- NOT NULL eliminates the third state if the business only needs two states.
- CHECK constraint prevents values other than 0/1.

**CHAR(1):**

~~~sql
CREATE TABLE feature_flag_legacy (
  flag_id NUMBER PRIMARY KEY,
  enabled CHAR(1) DEFAULT 'N' NOT NULL,
  CONSTRAINT ck_feature_flag_enabled
    CHECK (enabled IN ('Y', 'N'))
);
~~~

- Y represents TRUE.
- N represents FALSE.
- Can be easy to read in SQL and reports.
- Requires agreeing on the convention across applications, ETL, and external systems.

Do not mix multiple conventions such as 1, Y, T, TRUE for the same column. Choose one representation and enforce it with a constraint.

## 9. JPA AttributeConverter for Booleans Stored as NUMBER

If a legacy schema uses NUMBER(1), you can use an AttributeConverter to map Java Boolean to Integer:

~~~java
import jakarta.persistence.AttributeConverter;
import jakarta.persistence.Converter;

@Converter
public class BooleanNumberConverter
        implements AttributeConverter<Boolean, Integer> {

    @Override
    public Integer convertToDatabaseColumn(Boolean value) {
        if (value == null) {
            return null;
        }
        return value ? 1 : 0;
    }

    @Override
    public Boolean convertToEntityAttribute(Integer value) {
        if (value == null) {
            return null;
        }
        if (value == 1) {
            return Boolean.TRUE;
        }
        if (value == 0) {
            return Boolean.FALSE;
        }
        throw new IllegalArgumentException(
            "Unexpected Boolean representation: " + value
        );
    }
}
~~~

Apply on the field:

~~~java
@Convert(converter = BooleanNumberConverter.class)
@Column(name = "ENABLED", precision = 1, scale = 0, nullable = false)
private Boolean enabled;
~~~

The converter must handle NULL consistently with column nullability. If the column is NOT NULL, both entity validation and the database constraint should protect the invariant.

If using autoApply = true, the converter applies to all matching Boolean attributes in the persistence unit. Only enable it when all Boolean columns use the same representation. In systems having both SQL BOOLEAN and NUMBER(1), attach the converter explicitly on fields requiring conversion.

## 10. JPA AttributeConverter for Booleans Stored as CHAR(1)

If a legacy schema uses Y/N:

~~~java
import jakarta.persistence.AttributeConverter;
import jakarta.persistence.Converter;

@Converter
public class BooleanYnConverter
        implements AttributeConverter<Boolean, String> {

    @Override
    public String convertToDatabaseColumn(Boolean value) {
        if (value == null) {
            return null;
        }
        return value ? "Y" : "N";
    }

    @Override
    public Boolean convertToEntityAttribute(String value) {
        if (value == null) {
            return null;
        }
        return switch (value) {
            case "Y" -> Boolean.TRUE;
            case "N" -> Boolean.FALSE;
            default -> throw new IllegalArgumentException(
                "Unexpected Y/N value: " + value
            );
        };
    }
}
~~~

The switch above requires a Java version supporting switch expressions. If the project uses an older Java version, write it with if/else.

A converter does not replace a CHECK constraint. Data can be written by SQL scripts, ETL, or other applications; the database still needs to enforce the value domain.

## 11. Choosing a Representation When Supporting Multiple Oracle Releases

If the same application must run on both Oracle 19c and Oracle 23ai, you cannot assume every database understands SQL BOOLEAN. There are two approaches:

1. Use a compatible representation such as NUMBER(1) or CHAR(1) across all environments.
2. Use SQL BOOLEAN only on upgraded environments and manage migrations/ORM mappings by version.

The first approach is usually easier to operate when a shared schema is needed across multiple releases. The second leverages the new datatype but increases requirements on migrations, drivers, ORM, and compatibility.

Before deciding, answer:

- Must Oracle 19c or older releases be supported?
- Are there DR/test databases that have not been upgraded?
- Do ETL, BI, CDC, or external applications read the schema?
- Does the lowest JDBC driver in use support SQL BOOLEAN?
- Does the Hibernate dialect version understand the new datatype and DDL?
- Do old migrations need to be rolled back or re-run?

Do not switch a NUMBER(1) column to BOOLEAN solely because a newer release supports it. Weigh practical benefits against compatibility costs.

## 12. Identifier Length Limits in Oracle

An identifier is the name of a SQL object or element, for example:

- Table and view.
- Column.
- Index.
- Constraint.
- Sequence.
- Schema/user.
- Package, procedure, and function.
- Trigger.
- Synonym.
- Database link.

Oracle enforces identifier length limits based on the release and the COMPATIBLE parameter.

| Compatibility Level | Common Limit for Most Identifiers |
|---|---:|
| COMPATIBLE below 12.2 | 30 bytes |
| COMPATIBLE 12.2 or higher | 128 bytes |

This is the common limit for most SQL identifiers. Certain names or object types have release-specific rules; always check the SQL Language Reference for the exact version if using special names.

### Why Was There a 30-Byte Limit?

Older Oracle releases used a 30-byte limit for most object names. Many legacy schemas, migration tools, and applications were built around this rule. When a database is upgraded and COMPATIBLE allows it, the limit for most identifiers increases to 128 bytes.

Merely upgrading Oracle binaries does not make every database immediately use the new limit. The COMPATIBLE value must enable the corresponding feature.

## 13. Bytes vs. Characters

Oracle's identifier limit is measured in **bytes**, not display character count.

With a multi-byte database character set, a 20-character Unicode name can occupy more than 20 bytes. Therefore:

- Do not just count characters in an IDE.
- Do not assume 30 characters always fit within a 30-byte limit.
- Check the encoding/database character set.
- Prefer short, clear ASCII names for objects that must remain compatible across multiple environments.

You can illustrate the difference between character count and byte count with SQL:

~~~sql
SELECT LENGTH('ABC') AS char_length,
       LENGTHB('ABC') AS byte_length
  FROM dual;
~~~

LENGTH counts characters per Oracle semantics; LENGTHB returns the number of bytes. For real identifiers, you can inspect object names and check byte lengths:

~~~sql
SELECT object_name,
       LENGTH(object_name) AS char_length,
       LENGTHB(object_name) AS byte_length
  FROM user_objects
 ORDER BY byte_length DESC;
~~~

Dictionary views store object names according to database metadata; exact privileges and views depend on the scope being checked.

## 14. How Oracle Handles Unquoted and Quoted Identifiers

Identifiers not enclosed in double quotes are normalized to uppercase:

~~~sql
CREATE TABLE order_header (
  order_id NUMBER
);
~~~

The following unquoted references are equivalent:

~~~sql
SELECT order_id FROM order_header;
SELECT ORDER_ID FROM ORDER_HEADER;
SELECT Order_Id FROM Order_Header;
~~~

Identifiers enclosed in double quotes preserve exact case:

~~~sql
CREATE TABLE "OrderHeader" (
  "orderId" NUMBER
);
~~~

Afterward, you must reference them identically:

~~~sql
SELECT "orderId"
  FROM "OrderHeader";
~~~

If you write:

~~~sql
SELECT orderId
  FROM OrderHeader;
~~~

Oracle interprets unquoted identifiers as uppercase and may fail to find objects created with quoted mixed-case names.

### Should You Use Quoted Identifiers?

Generally, avoid quoted identifiers for table/column names:

- Harder to write SQL and migrations.
- Easy to introduce case mismatches between Java, ORM, and the database.
- Administration tools may display/quote them differently.
- Increases error risk when integrating BI, ETL, or other applications.
- Makes naming strategies unpredictable.

Only use quoted identifiers when there is a specific compatibility requirement and all clients are under control.

## 15. Identifier Naming Rules

For unquoted identifiers, Oracle has character and keyword rules. Some practical guidelines:

- Start with a letter in the database character set.
- Use letters, digits, underscores, and special characters allowed by Oracle such as $ or # per identifier rules.
- Do not include spaces.
- Do not use reserved words as unquoted names.
- Do not exceed the byte limit of the release/COMPATIBLE level.
- Keep names consistent and readable.

Quoted identifiers have different rules and can contain more characters, but should not be used to work around all naming issues.

### Reserved Words

Names like SELECT, TABLE, DATE, USER, or other SQL keywords can cause conflicts. Although some words can be used as quoted identifiers, the better approach is choosing clear names:

~~~sql
-- Avoid
CREATE TABLE "ORDER" (
  "DATE" DATE
);

-- Prefer descriptive names
CREATE TABLE sales_order (
  ordered_at DATE
);
~~~

The reserved word list changes across releases. A name valid on an older database can become a keyword or special identifier in a newer release. When upgrading, check schemas and generated SQL.

## 16. Impact of Identifier Limits on Hibernate/JPA

Hibernate can generate names for:

- Join tables.
- Foreign keys.
- Unique constraints.
- Indexes.
- Sequences.
- Collection tables.
- Secondary tables.
- Discriminator columns.

If a naming strategy generates a name longer than an older database's limit, migrations or schema generation can fail:

~~~text
ORA-00972: identifier is too long
~~~

Example of an auto-generated constraint name:

~~~text
FK_CUSTOMER_ORDER_HISTORY_CUSTOMER_REFERENCE_ID
~~~

This name can exceed the 30-byte limit on older databases. The fix is to use a naming strategy with a deterministic shortening rule, or declare short explicit names in mappings/migrations.

Example:

~~~java
@Table(
    name = "CUSTOMER_ORDER",
    uniqueConstraints = {
        @UniqueConstraint(
            name = "UK_CUST_ORDER_CODE",
            columnNames = {"ORDER_CODE"}
        )
    }
)
~~~

Constraint names should stay within the limit of every Oracle release the application supports.

## 17. Multi-Version Compatible Naming

If a schema must run on both Oracle 11g/12.1 and Oracle 19c/23ai, the safest approach is keeping most object names within the 30-byte limit. This reduces the risk of a new migration working on a new database but failing on an older one.

A practical convention:

| Object Type | Suggested Prefix | Example |
|---|---|---|
| Table | Optional or domain prefix | ORDER_HEADER |
| Primary key | PK_ | PK_ORDER_HEADER |
| Foreign key | FK_ | FK_ORDER_CUST |
| Unique constraint | UK_ | UK_ORDER_CODE |
| Check constraint | CK_ | CK_ORDER_STATUS |
| Index | IX_ | IX_ORDER_CREATED |
| Sequence | SEQ_ | SEQ_ORDER_ID |
| Trigger | TRG_ | TRG_ORDER_AUDIT |
| View | V_ or VW_ | VW_ORDER_SUMMARY |

Prefixes are internal conventions, not Oracle requirements. Names must be meaningful, stable, and collision-free.

### Automated Name Shortening

If an ORM or migration tool generates names from multiple components, do not truncate strings arbitrarily because that can cause collisions. A stable strategy:

1. Normalize source names.
2. Keep the prefix indicating object type.
3. Retain a significant portion of the domain name.
4. Append a short hash of the full name if needed to avoid collisions.
5. Enforce the limit by bytes, not by character count.
6. Use the exact same algorithm across all environments.

For example, a long name can become:

~~~text
FK_ORDER_ITEM_PRODUCT_8A31
~~~

Do not change the naming algorithm between builds once migrations have been generated and applied to shared environments.

## 18. Checking COMPATIBLE

The COMPATIBLE parameter controls the database's compatibility level with capabilities and structures introduced in newer releases. It is not a parameter meant solely to alter the parser or increase identifier limits.

Check:

~~~sql
SHOW PARAMETER compatible;
~~~

Or:

~~~sql
SELECT name,
       value
  FROM v$parameter
 WHERE name = 'compatible';
~~~

Read the release:

~~~sql
SELECT banner
  FROM v$version;
~~~

Component details:

~~~sql
SELECT product,
       version,
       status
  FROM product_component_version;
~~~

COMPATIBLE affects many database capabilities and structures, not just SQL BOOLEAN or identifiers. Do not unilaterally raise the parameter value in production just to run a single new DDL statement.

Changing COMPATIBLE must be part of an Oracle upgrade plan, with verified upgrade paths, backups, recovery, and official documentation. Some compatibility changes may not be easily reversible once the database has used new features.

## 19. New Syntax: IF NOT EXISTS and IF EXISTS

Oracle Database 23c/23ai adds existence/non-existence clauses for certain DDL commands. Example:

~~~sql
CREATE TABLE IF NOT EXISTS feature_flag (
  flag_id NUMBER PRIMARY KEY,
  enabled BOOLEAN DEFAULT FALSE NOT NULL
);
~~~

Drop table if it exists:

~~~sql
DROP TABLE IF EXISTS feature_flag;
~~~

IF [NOT] EXISTS forms are supported depending on object type and release. Do not assume every CREATE, ALTER, or DROP command accepts this clause. Check the SQL Language Reference for the exact database version before using it in migrations.

### IF NOT EXISTS Does Not Validate Schema

CREATE TABLE IF NOT EXISTS may skip creating the table if the name already exists. That does not prove the existing table has the exact columns, datatypes, constraints, or indexes expected by the migration.

In production migrations, distinguish between:

- Object already exists and has the right structure.
- Object already exists but has an outdated/wrong structure.
- Object exists as a different type or in a different schema.
- Migration history indicating whether the script has already run.

IF NOT EXISTS is syntactic convenience; it does not replace schema migration tracking and drift detection.

### On Older Releases

On older Oracle releases that do not support DROP TABLE IF EXISTS, you can use PL/SQL exception handling while ignoring only the table-or-view-does-not-exist error:

~~~sql
BEGIN
  EXECUTE IMMEDIATE 'DROP TABLE feature_flag_legacy PURGE';
EXCEPTION
  WHEN OTHERS THEN
    IF SQLCODE <> -942 THEN
      RAISE;
    END IF;
END;
/
~~~

Do not write WHEN OTHERS THEN NULL for DDL. That can mask permission, tablespace, dependency, or syntax errors.

For CREATE TABLE, a version-tracked migration tool is usually better than swallowing object-already-exists errors. If idempotent PL/SQL handling is necessary, ignore only the exact expected error and verify the existing object.

## 20. New Syntax: SELECT Without FROM DUAL

In traditional Oracle releases, querying constant expressions typically uses DUAL:

~~~sql
SELECT 1 + 1 AS result
  FROM dual;
~~~

Oracle Database 23c/23ai supports certain SELECT queries without FROM:

~~~sql
SELECT 1 + 1 AS result;
~~~

This makes SQL more concise when only evaluating or returning constant expressions. However, if the application must run on older Oracle releases, continue using FROM DUAL for compatibility:

~~~sql
SELECT SYSTIMESTAMP
  FROM dual;
~~~

Do not automatically remove DUAL from every query in a codebase that must support multiple versions. Queries with DUAL remain valid on newer releases while preserving compatibility with older ones.

## 21. New SQL Syntax and Writing Portable SQL

Some new syntaxes make SQL shorter, yet introduce minimum version requirements. Examples:

| Capability | New Release Syntax | More Compatible Syntax |
|---|---|---|
| Boolean column | BOOLEAN | NUMBER(1) or CHAR(1) with constraint |
| Conditional DDL | CREATE TABLE IF NOT EXISTS | Versioned migrations; or PL/SQL handling specific errors |
| Conditional Drop | DROP TABLE IF EXISTS | PL/SQL catching specifically ORA-00942 |
| SELECT expression | SELECT 1 + 1 | SELECT 1 + 1 FROM dual |
| Long object names | Up to 128 bytes when supported | Keep names at or below 30 bytes |

If multiple Oracle releases must be supported, choose the lowest common syntax supported across all environments or separate migrations/SQL by release in a controlled manner.

Do not use IF NOT EXISTS to replace Flyway/Liquibase versioning, and do not use the new BOOLEAN type if older target databases do not understand the datatype.

## 22. Checking Version and Capabilities from the Application

You can retrieve the database version from JDBC metadata:

~~~java
try (Connection connection = dataSource.getConnection()) {
    DatabaseMetaData metadata = connection.getMetaData();

    String productName = metadata.getDatabaseProductName();
    String productVersion = metadata.getDatabaseProductVersion();
    int major = metadata.getDatabaseMajorVersion();
    int minor = metadata.getDatabaseMinorVersion();

    log.info("Database: {} {} ({}. {})",
        productName, productVersion, major, minor);
}
~~~

You can record driver details:

~~~java
DatabaseMetaData metadata = connection.getMetaData();
String driverName = metadata.getDriverName();
String driverVersion = metadata.getDriverVersion();
~~~

On the database side, DBAs can query V$VERSION, PRODUCT_COMPONENT_VERSION, and V$PARAMETER. The application is not necessarily granted access to read these views; if version telemetry is needed, expose it via a safe endpoint or deployment configuration.

### Do Not Check Only the Major Version

A feature can depend on:

- Database release and Release Update.
- COMPATIBLE value.
- Container/PDB and connected service.
- Edition or option.
- JDBC driver.
- Hibernate/JPA provider.
- Migration tools and SQL clients.

Checking only DatabaseMetaData.getDatabaseMajorVersion() is insufficient to conclude all new syntax is permitted.

## 23. Feature Gates in the Application

If the application supports multiple Oracle versions, avoid scattering version checks across repositories. Centralize database capabilities in one place:

~~~java
public record OracleCapabilities(
    boolean sqlBooleanSupported,
    boolean ddlIfExistsSupported,
    boolean selectWithoutFromSupported,
    int identifierByteLimit
) {}
~~~

An initialization component can receive capabilities from deployment configuration or inspect metadata/compatibility with granted privileges. Do not attempt every syntax and catch exceptions to infer features on every request.

Example strategy:

- 19c profile uses NUMBER(1), object names <= 30 bytes, and DUAL.
- 23ai profile uses SQL BOOLEAN when driver/ORM supports it; can still keep DUAL and short names if sharing a schema.
- Migrations select the proper script based on the confirmed release.

If the same schema is shared across databases of different versions, choose data types and identifiers compatible with the lowest database version.

## 24. Migrating from NUMBER(1) to BOOLEAN

Suppose the legacy table is:

~~~sql
CREATE TABLE feature_flag (
  flag_id NUMBER PRIMARY KEY,
  enabled NUMBER(1) DEFAULT 0 NOT NULL,
  CONSTRAINT ck_feature_enabled CHECK (enabled IN (0, 1))
);
~~~

When moving to a release supporting SQL BOOLEAN, plan:

1. Identify which applications read/write the column.
2. Identify integrations/ETL/reporting depending on NUMBER(1).
3. Verify the JDBC driver and Hibernate mapping.
4. Determine whether rollback capability to an older release must be retained.
5. Choose a migration that creates a new column or converts the type per supported capabilities.
6. Migrate data and verify NULL/0/1 values.
7. Deploy applications compatible with the new schema.
8. Confirm all clients have been upgraded before dropping the legacy representation.

Do not assume ALTER TABLE MODIFY enabled BOOLEAN can run safely on every release or every data state. Consult the SQL Language Reference for the exact version and test the migration on a copy of the data.

### Parallel Column Strategy

For systems requiring a safe cutover, you can consider:

- Add a new column with the target type.
- Backfill from NUMBER(1) to BOOLEAN.
- Temporarily dual-write or use controlled conversion triggers/logic.
- Cross-check reads between both columns.
- Switch applications to the new column.
- After the rollback window, drop the old column in a separate migration.

This is a general migration pattern; triggers and dual-writes add complexity and should be avoided if a brief downtime and simpler migration are feasible.

## 25. Long Identifiers During Database Upgrades

Suppose an older database uses names up to 30 bytes. A new migration is written on a 23ai database and creates a 60-byte constraint. The migration runs fine in dev but fails when deployed to an older PDB with a lower COMPATIBLE setting.

How to handle:

- Check COMPATIBLE across all environments.
- Check byte lengths of table, column, index, constraint, and sequence names.
- Check Hibernate auto-generated names.
- Use a shared naming convention.
- Prevent tools from generating different names across builds.
- Test migrations on a database with the lowest supported compatibility level.

If objects with long names already exist on a newer database, do not rename them in production without reviewing dependencies, views, packages, grants, and external applications.

## 26. Common Errors Related to BOOLEAN and Identifiers

| Error | Common Cause | What to Check |
|---|---|---|
| ORA-00902: invalid datatype | Database does not support SQL BOOLEAN at current release/compatibility | Check release, COMPATIBLE, and DDL |
| ORA-00972: identifier is too long | Identifier exceeds byte limit | Check 30/128 bytes, quoted names, and naming strategy |
| ORA-00904: invalid identifier | Wrong name, case, quotes, or column does not exist | Check dictionary and actual SQL |
| ORA-00933: SQL command not properly ended | New syntax executed on older release or invalid SQL | Confirm release and SQL Language Reference |
| ORA-00955: name is already used by an existing object | DDL creating an object that already exists | Check objects and migration history |
| ORA-00942: table or view does not exist | Wrong schema, missing grant, or object does not exist | Check owner, synonyms, and container |
| Boolean bind error | Incompatible JDBC driver/ORM mapping | Check driver, Hibernate dialect, and SQL type |
| TRUE/FALSE read as the same value | Using getBoolean while ignoring wasNull | Distinguish NULL from FALSE |

Do not fix ORA-00972 by immediately changing COMPATIBLE. First verify whether the database truly supports long identifiers and which names should be shortened.

## 27. Testing BOOLEAN on a Real Oracle Database

An integration test should verify insert, update, NULL, and read-back:

~~~java
@Test
void persistsTrueFalseAndNullOnOracle() {
    FeatureFlag enabled = new FeatureFlag("flag-on", true);
    FeatureFlag disabled = new FeatureFlag("flag-off", false);

    repository.saveAndFlush(enabled);
    repository.saveAndFlush(disabled);
    entityManager.clear();

    assertThat(repository.findById(enabled.getId())
        .orElseThrow().getEnabled()).isTrue();
    assertThat(repository.findById(disabled.getId())
        .orElseThrow().getEnabled()).isFalse();
}
~~~

If the column allows NULL, add a NULL test and verify wasNull in JDBC or Boolean on the entity. If the column is NOT NULL, verify the database rejects NULL and defaults behave as designed.

On older databases using NUMBER(1), also test that values outside 0/1 are rejected by the CHECK constraint.

## 28. Testing Identifiers and Migrations

Test migrations on the exact Oracle release/compatibility:

- Create tables and constraints using actual migrations.
- Confirm objects are created under the right owner.
- Check whether names exceed byte limits.
- Run Hibernate ddl-auto=validate.
- Check generated SQL and native queries.
- Run migrations from the old schema to the new schema.
- Run migrations on an environment with the lowest supported COMPATIBLE setting.

Do not test migrations only on the newest database. The lowest environment in the support matrix usually catches version-gate failures earliest.

## 29. Rules for Choosing Syntax by Release

Before using a new syntax, determine:

1. The first release supporting the syntax.
2. Whether a minimum COMPATIBLE level is required.
3. Whether syntax differs by patch/Release Update.
4. Whether the JDBC driver and ORM support the corresponding datatype/metadata.
5. Whether migrations must run on older databases.
6. Whether ETL, BI, backup, replication, and external applications understand the new data type.
7. Whether a rollback plan or compatibility window is required.

A newer release may support syntax in the SQL engine while the driver or ORM in use does not yet map it properly. Therefore, version support is a matrix, not a single number.

## 31. Conclusion

Oracle Database 23c/23ai introduces SQL BOOLEAN into the SQL engine, whereas older releases only had BOOLEAN in PL/SQL and commonly represented states using NUMBER(1) or CHAR(1). SQL BOOLEAN has TRUE, FALSE, and UNKNOWN when NULL is allowed; JDBC/JPA applications must preserve the distinction between FALSE and NULL.

The common identifier limit is 30 bytes at older compatibility levels and 128 bytes when COMPATIBLE permits from 12.2 onward. Length is measured in bytes, and quoted identifiers preserve case and can make SQL harder to maintain. Hibernate naming strategies and migrations must be checked to prevent ORA-00972.

New syntaxes such as IF [NOT] EXISTS in DDL and SELECT without FROM DUAL make SQL cleaner on supported releases. When an application must run across multiple Oracle versions, choose shared syntax, use controlled release-specific migrations, and verify database version, COMPATIBLE, JDBC driver, Hibernate dialect, and integrated clients. Do not infer support solely from a banner or from a statement running in a development environment.
