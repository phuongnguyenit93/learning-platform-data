# EXPLAIN PLAN and Differences from the Executed Plan

Oracle provides several ways to view an execution plan. Two commonly compared methods are **EXPLAIN PLAN** and **DBMS_XPLAN.DISPLAY_CURSOR**. They are related but answer two different questions:

- **EXPLAIN PLAN** asks the optimizer to analyze a SQL statement and store the estimated plan in PLAN_TABLE. The explained SQL statement is not executed.
- **DBMS_XPLAN.DISPLAY_CURSOR** reads the plan of a SQL cursor that has already been parsed/executed and is still in the library cache. When runtime row-source statistics are gathered, this plan can show actual row counts, operation start counts, timing, and observed I/O.

Therefore, EXPLAIN PLAN is useful when you want a quick look at a projected plan, whereas the cursor plan is stronger evidence when investigating a SQL statement that actually ran in the application. The two plans can differ due to bind values, child cursors, optimizer environment, statistics, schema resolution, adaptive behavior, and many other runtime factors.

A reliable diagnostic workflow is typically: identify the exact SQL_ID and child cursor, collect the actual plan along with runtime statistics, compare estimated rows against actual rows, and then use EXPLAIN PLAN as a complementary tool to test a SQL variant or a different parse environment.

## 1. Execution Plans in Oracle

### 1.1. What Is a Plan?

An execution plan describes how Oracle intends to execute, or has executed, a SQL statement. A plan is represented as operations/row sources with parent-child relationships. Common operations include:

- TABLE ACCESS FULL: reads a table via a full scan.
- TABLE ACCESS BY INDEX ROWID: fetches rows from a table using ROWIDs obtained from an index.
- INDEX RANGE SCAN, INDEX UNIQUE SCAN, INDEX FULL SCAN: index access types.
- NESTED LOOPS, HASH JOIN, MERGE JOIN: join methods.
- SORT ORDER BY, SORT GROUP BY, HASH GROUP BY: sorting or grouping.
- FILTER: applies filtering conditions.
- PARTITION RANGE ITERATOR: coordinates partition access.

A plan can also display predicates, projections, partition pruning, parallel execution, temporary space, and memory information depending on the operation type and format.

### 1.2. Plans Are Organized as a Tree

Example:

```sql
SELECT e.employee_id, d.department_name
FROM employees e
JOIN departments d
  ON d.department_id = e.department_id
WHERE d.location_id = 1700;
```

An illustrative plan:

```text
SELECT STATEMENT
  HASH JOIN
    TABLE ACCESS FULL DEPARTMENTS
    TABLE ACCESS FULL EMPLOYEES
```

Child operations produce input row sources for parent operations. Reading a plan requires examining parent-child relationships and processing order, rather than simply reading lines top-to-bottom as a sequential list of commands.

### 1.3. A Plan Can Be Projected or Executed

A plan generated by EXPLAIN PLAN is the optimization result for the SQL statement in the environment of the explain operation. A cursor plan is the plan attached to an actual cursor in the shared pool/library cache. When the cursor has executed and runtime statistics have been gathered, you gain actual execution data for evaluation.

A cached plan may have been parsed without finishing execution, executed multiple times, or split into multiple child cursors. Always identify the exact cursor and child number during an investigation.

## 2. How EXPLAIN PLAN Works

### 2.1. Basic Syntax

```sql
EXPLAIN PLAN FOR
SELECT employee_id, last_name
FROM employees
WHERE department_id = 50;

SELECT *
FROM TABLE(DBMS_XPLAN.DISPLAY);
```

The EXPLAIN PLAN FOR command instructs Oracle to parse/optimize the SQL statement and save the plan into PLAN_TABLE. The explained SELECT statement does not execute to return data. Afterward, DBMS_XPLAN.DISPLAY formats the stored plan content.

### 2.2. Assigning a STATEMENT_ID

If you need to keep multiple plans in PLAN_TABLE, set a statement identifier:

```sql
EXPLAIN PLAN
    SET STATEMENT_ID = 'EMP_DEPT_50'
FOR
SELECT employee_id, last_name
FROM employees
WHERE department_id = 50;

SELECT *
FROM TABLE(
    DBMS_XPLAN.DISPLAY(
        table_name   => 'PLAN_TABLE',
        statement_id => 'EMP_DEPT_50',
        format       => 'TYPICAL'
    )
);
```

STATEMENT_ID helps distinguish between explain runs. You can include a timestamp or test name in the identifier within the length limits and conventions of PLAN_TABLE.

### 2.3. PLAN_TABLE

PLAN_TABLE stores the rows describing plans generated by EXPLAIN PLAN. Oracle provides scripts/resources to create this structure; in modern releases, users can typically use PLAN_TABLE and its corresponding synonym depending on the database setup.

Common columns include:

- STATEMENT_ID: identifier of the explain run.
- PLAN_ID: plan identifier.
- OPERATION, OPTIONS: operation type and variant.
- OBJECT_OWNER, OBJECT_NAME, OBJECT_TYPE: involved object.
- ID, PARENT_ID: plan tree structure.
- COST, CARDINALITY, BYTES: optimizer estimates.
- ACCESS_PREDICATES, FILTER_PREDICATES: access/filter conditions.
- TEMP_SPACE: estimated temporary space in applicable operations.

Do not rely on manually reading raw PLAN_TABLE rows if DBMS_XPLAN can present them more clearly. The structure of PLAN_TABLE can vary across releases.

### 2.4. Viewing a Plan in SQL*Plus or SQLcl

After EXPLAIN PLAN:

```sql
SELECT *
FROM TABLE(DBMS_XPLAN.DISPLAY);
```

Or display a specific statement:

```sql
SELECT *
FROM TABLE(
    DBMS_XPLAN.DISPLAY(
        'PLAN_TABLE',
        'EMP_DEPT_50',
        'BASIC +PREDICATE'
    )
);
```

BASIC shows the core information; +PREDICATE adds access/filter conditions. You can use TYPICAL or ALL when more detail is needed.

### 2.5. Cleaning Up Test Plans

PLAN_TABLE can accumulate many statements if different STATEMENT_IDs are used. Delete only the rows belonging to your own test:

```sql
DELETE FROM plan_table
WHERE statement_id = 'EMP_DEPT_50';
COMMIT;
```

Only delete rows created by your own session and matching the exact statement identifier. In a multi-user environment, do not arbitrarily truncate or delete the entire PLAN_TABLE.

## 3. EXPLAIN PLAN Does Not Execute the SQL Statement

### 3.1. No A-Rows from an Actual Run

EXPLAIN PLAN provides estimates such as cardinality, cost, and bytes. Because the target SQL statement is not executed, it cannot provide the actual number of rows returned, actual elapsed time, or buffer gets for that run.

A typical explain plan has E-Rows/estimates but no runtime A-Rows for the target SQL statement.

### 3.2. Does Not Measure Query Execution Time

The runtime of the EXPLAIN PLAN command only reflects the work of parsing/optimizing and storing the plan, not the execution time of the explained SQL statement. Do not use the elapsed time of EXPLAIN PLAN to conclude whether a query is fast or slow.

### 3.3. Does Not Produce DML Side Effects for the Explained Statement

Example:

```sql
EXPLAIN PLAN FOR
UPDATE orders
SET status_code = 'CLOSED'
WHERE order_date < DATE '2025-01-01';
```

This command does not update rows in ORDERS. It only explains the projected plan for the UPDATE. However, EXPLAIN PLAN is itself an operation that writes plan rows into PLAN_TABLE; explaining does not replace testing DML against safe data.

### 3.4. The Statement Still Requires Parsing and Privileges

Not executing the SQL statement does not mean Oracle skips syntax checks, object resolution, and required privileges to explain it. A SQL statement with syntax errors or invalid object references can still fail during the parse/optimization step.

### 3.5. Do Not Use EXPLAIN PLAN to Verify Business Results

EXPLAIN PLAN does not tell you which rows a SELECT returns, how many rows a DML statement affects, or whether constraints would be violated at runtime. Those questions require controlled execution and observing actual results.

## 4. DBMS_XPLAN.DISPLAY and DISPLAY_CURSOR

### 4.1. DISPLAY

DBMS_XPLAN.DISPLAY reads a plan stored in PLAN_TABLE:

```sql
SELECT *
FROM TABLE(
    DBMS_XPLAN.DISPLAY(
        table_name   => 'PLAN_TABLE',
        statement_id => 'EMP_DEPT_50',
        format       => 'TYPICAL'
    )
);
```

The data source for DISPLAY is a plan table. It does not look up cursors that have executed in the library cache.

### 4.2. DISPLAY_CURSOR

DBMS_XPLAN.DISPLAY_CURSOR displays the plan of a cursor in the library cache:

```sql
SELECT *
FROM TABLE(
    DBMS_XPLAN.DISPLAY_CURSOR(
        sql_id          => '0123456789abc',
        cursor_child_no => 0,
        format          => 'TYPICAL'
    )
);
```

The SQL_ID and child number above are illustrative placeholders only. Replace them with values obtained from an actual cursor.

### 4.3. Most Recent Cursor in the Session

In a simple lab, you can run the target query and immediately call:

```sql
SELECT *
FROM TABLE(
    DBMS_XPLAN.DISPLAY_CURSOR(
        NULL,
        NULL,
        'TYPICAL'
    )
);
```

The two NULL parameters instruct Oracle to select the appropriate most recent cursor in the session according to the API semantics. In environments with multiple interleaved SQL statements, the safer approach is to explicitly retrieve SQL_ID/child number from V$SQL or instrumentation to avoid picking the wrong cursor.

### 4.4. DISPLAY_AWR

DBMS_XPLAN.DISPLAY_AWR can display plans stored in the Automatic Workload Repository when appropriate licensing/privileges and AWR data are available. AWR plan history is useful for viewing historical plans, though it does not necessarily contain full runtime row-source statistics for every execution.

Do not confuse an AWR plan with the plan currently being executed in the library cache.

### 4.5. Access Privileges

Reading cursor plans may require privileges to query dynamic performance views and related catalog metadata. DBMS_XPLAN.DISPLAY from PLAN_TABLE and DISPLAY_CURSOR from the shared pool have different privilege scopes. DBAs should grant the minimum required privileges to investigators rather than unnecessarily granting broad administrative privileges.

## 5. Executed Plans and Runtime Statistics

### 5.1. Why Are Runtime Statistics Needed?

A cursor plan shows the operations and estimates, but to know whether the estimates are accurate, you need actual row-source statistics. Oracle can collect runtime information such as:

- Operation start count (Starts).
- Actual row count (A-Rows).
- Operation time (A-Time) when collected.
- Logical I/O (Buffers).
- Physical reads (Reads).
- Work area memory (OMem, 1Mem, Used-Mem) for applicable operations.

Available information depends on the collection method, cursor type, and DBMS_XPLAN format.

### 5.2. GATHER_PLAN_STATISTICS

You can add a hint to collect row-source statistics for a SQL statement:

```sql
SELECT /*+ GATHER_PLAN_STATISTICS */
       employee_id, last_name
FROM employees
WHERE department_id = 50;
```

After the SQL executes, view the plan:

```sql
SELECT *
FROM TABLE(
    DBMS_XPLAN.DISPLAY_CURSOR(
        NULL,
        NULL,
        'ALLSTATS LAST'
    )
);
```

ALLSTATS LAST requests displaying I/O/memory/row-source statistics for the last recorded execution, if corresponding data is available. If runtime stats were not gathered, the A-Rows column may be missing or uninformative.

### 5.3. STATISTICS_LEVEL = ALL

In a lab session, you can enable:

```sql
ALTER SESSION SET STATISTICS_LEVEL = ALL;
```

This setting instructs Oracle to collect additional runtime statistics for eligible statements in the session. It can increase overhead, so enable it only within the required scope and duration. After testing, restore the original setting:

```sql
ALTER SESSION SET STATISTICS_LEVEL = TYPICAL;
```

If the session originally had a different setting, read and restore that exact previous value instead of defaulting to TYPICAL.

### 5.4. A-Rows Does Not Mean the Final Row Count of the Query

A-Rows appears per operation. A scan operation may read many rows, a filter discards some, a join produces a different row count, and an aggregation further reduces the count. You must read A-Rows at the right row source and within the proper parent-child context.

### 5.5. Starts Affects How You Compare

An operation on the inner side of nested loops can be executed multiple times. E-Rows is typically an estimate per start, whereas A-Rows in the plan output can be the cumulative total across starts. When comparing, you must consider Starts and how the format/version presents the figures. Do not conclude a misestimate simply by dividing A-Rows by E-Rows while ignoring Starts.

For example, an inner operation expecting 1 row per execution, with Starts = 1,000 and total A-Rows = 1,000, can be completely accurate. Comparing 1,000 directly against 1 would falsely suggest a 1,000x error.

## 6. Key Columns in DBMS_XPLAN

| Column | Meaning | Usage |
|---|---|---|
| Id | Operation ID in the plan | Identifies the row source |
| Operation | Type of operation | Understand access/join method |
| Name | Object or index | Identifies the object used |
| Starts | Number of times the operation started | Critical for nested loops |
| E-Rows | Optimizer-estimated rows | Compare against actuals |
| A-Rows | Actual rows recorded | Detect estimate skew |
| A-Time | Runtime duration per operation | Find time-consuming areas; read carefully |
| Buffers | Logical I/O | Evaluate buffer read work |
| Reads | Physical reads | Evaluate storage I/O |
| OMem / 1Mem | Estimated memory for work area | Analyze sort/hash memory |
| Used-Mem | Memory used during the operation | Inspect runtime work area usage |
| Cost | Optimizer-estimated cost | Compare optimizer alternatives |
| Bytes | Estimated data volume | Understand intermediate volume |

Not every format or every operation includes all columns. A-Time can be rounded and does not simply sum up to the total statement elapsed time.

## 7. Why Does EXPLAIN PLAN Differ from the Executed Plan?

### 7.1. Bind Values and Bind Peeking

A SQL statement may use binds:

```sql
SELECT *
FROM orders
WHERE customer_id = :customer_id;
```

Customer 100 might have only 1 order, whereas customer 200 might have 50,000 orders. Different selectivity can cause the optimizer to choose index access for one value and a full scan/hash strategy for another.

EXPLAIN PLAN often does not fully reproduce the actual bind scenario and child cursor created when the application ran. Bind peeking during hard parse, adaptive cursor sharing, and bind sensitivity can cause the cursor plan to differ from the explain plan.

### 7.2. Bind Datatypes

Binding NUMBER, VARCHAR2, DATE, or TIMESTAMP differently can affect implicit conversion and access predicates. An application binding a type different from the column type can cause the actual plan to differ from a plan explained with literals or another bind type.

Always record the bind datatype from the driver/application, not just the displayed value.

### 7.3. Different Child Cursors

A SQL_ID can have multiple child cursors due to differences in bind behavior, optimizer environment, object metadata, authorization context, or other cursor sharing reasons. Each child can have its own plan.

If you only inspect child 0 while the application runs child 3, your conclusion will be wrong. Identify the exact SQL_ID and child number of the execution under investigation.

### 7.4. Different Optimizer Environments

Settings such as OPTIMIZER_MODE, optimizer feature enablement, NLS, parallel settings, statistics level, and certain other parameters can affect the plan. The application session and the session running EXPLAIN PLAN may not share the same environment.

Compare the cursor's optimizer environment with the explain session when needed.

### 7.5. Statistics Changes

Between the time of EXPLAIN PLAN and the time the application parsed/executed:

- Table/column/index statistics may have been regathered.
- Histograms may have been created or changed.
- Partition/global stats may have been updated.
- Data may have changed significantly enough for stats to become stale or yield a different plan.

A fresh explain plan does not necessarily reflect a plan created earlier in the shared pool.

### 7.6. Schema Resolution, Synonyms, and Current Schema

Two sessions with different CURRENT_SCHEMA, different synonyms, or different privileges can resolve the same object name to different objects. This is especially easy to overlook when SQL omits explicit schema owners.

When investigating, verify the actual objects in the plan: OBJECT_OWNER, OBJECT_NAME, and object type.

### 7.7. VPD, Application Context, and Security Policies

Virtual Private Database (VPD) or row-level security can append predicates to SQL based on user/context. An application session may have a client identifier or application context different from the explain session. Thus, the SQL parsed by the application can differ from what the optimizer sees in the explain session.

You must reproduce the proper security context when investigating, without spoofing or bypassing policies in production to force a plan.

### 7.8. Global Temporary Tables and Session-Specific Data

Global temporary tables share metadata, but their data belongs to a session or transaction as declared. The statistics and data in the application session may differ from those in the explain session. A plan explained in a session without the same temporary dataset may not be representative.

### 7.9. Dynamic Statistics and Feedback

The optimizer may use dynamic statistics, cardinality/statistics feedback, or adaptive mechanisms. Such information can appear in subsequent parses/cursors or lead to a different child/plan than a standalone EXPLAIN PLAN.

### 7.10. Adaptive Plans

Some releases/configurations support adaptive plans. A plan can contain runtime choices, and the branch actually used can depend on information observed at runtime. An explain plan does not tell you for certain which branch was selected in a specific execution.

### 7.11. SQL Profile, SQL Patch, and SQL Plan Baseline

The actual cursor may be influenced by a SQL Profile, SQL Patch, or SQL Plan Baseline applied to the statement. EXPLAIN PLAN in another session or environment may not reflect the same plan management configuration.

When comparing, check the SQL Management Base, related profiles/patches, and the plan hash of the actual cursor.

### 7.12. Parallel Execution

A plan can execute in parallel with specific PX servers, DOP, and distribution methods. Explain plan may show the projected parallel plan, while runtime DOP, downgrade, PX allocation, and actual execution behavior can differ when resources change.

### 7.13. Oracle Version and Optimizer Features

Different database releases or OPTIMIZER_FEATURES_ENABLE settings can alter transformations, costing, and plans. Do not compare plans across two releases while ignoring optimizer version differences.

## 8. Identifying the Exact SQL_ID and Child Cursor

### 8.1. Finding the SQL Statement in V$SQL

Example:

```sql
SELECT sql_id,
       child_number,
       plan_hash_value,
       executions,
       parsing_schema_name,
       module,
       action,
       last_active_time,
       sql_text
FROM v$sql
WHERE sql_text LIKE '%FROM orders%'
ORDER BY last_active_time DESC;
```

V$SQL holds cursor information in the shared pool. A LIKE filter may return multiple similar statements; use the SQL_ID recorded by application tracing/APM if available.

### 8.2. Inspecting Child Cursors

```sql
SELECT sql_id,
       child_number,
       plan_hash_value,
       executions,
       is_bind_sensitive,
       is_bind_aware,
       optimizer_env_hash_value,
       parsing_schema_name
FROM v$sql
WHERE sql_id = :sql_id
ORDER BY child_number;
```

Available columns may vary by release. IS_BIND_SENSITIVE and IS_BIND_AWARE are helpful when investigating adaptive cursor sharing.

### 8.3. Viewing the Plan for a Specific Child

```sql
SELECT *
FROM TABLE(
    DBMS_XPLAN.DISPLAY_CURSOR(
        sql_id          => :sql_id,
        cursor_child_no => :child_number,
        format          => 'TYPICAL +PREDICATE'
    )
);
```

Make sure to bind the exact SQL_ID and child number matching the cursor under analysis. A single SQL_ID does not imply only one execution plan.

### 8.4. Inspecting the Optimizer Environment

```sql
SELECT name, value
FROM v$sql_optimizer_env
WHERE sql_id = :sql_id
  AND child_number = :child_number
ORDER BY name;
```

Compare key settings against the session running EXPLAIN PLAN. You do not need to compare every row mechanically; focus on differing parameters that can affect the optimizer.

### 8.5. Retrieving Full SQL Text

SQL_TEXT in V$SQL may contain only part of the statement. Use V$SQL.SQL_FULLTEXT or DBMS_LOB.SUBSTR depending on privileges and release to retrieve the complete SQL text. Cross-check whitespace, comment hints, literals, and bind names.

## 9. Viewing Plans with DBMS_XPLAN by Purpose

### 9.1. Projected Plan from PLAN_TABLE

```sql
EXPLAIN PLAN
    SET STATEMENT_ID = 'TEST_EXPLAIN'
FOR
SELECT *
FROM orders
WHERE customer_id = 1001;

SELECT *
FROM TABLE(
    DBMS_XPLAN.DISPLAY(
        'PLAN_TABLE',
        'TEST_EXPLAIN',
        'TYPICAL +PREDICATE'
    )
);
```

### 9.2. Executed Cursor Plan

```sql
SELECT /*+ GATHER_PLAN_STATISTICS */
       *
FROM orders
WHERE customer_id = 1001;

SELECT *
FROM TABLE(
    DBMS_XPLAN.DISPLAY_CURSOR(
        NULL,
        NULL,
        'ALLSTATS LAST +PREDICATE'
    )
);
```

In real environments, use explicit SQL_ID/child instead of NULL if the session runs multiple interleaved statements.

### 9.3. Common Formats

| Format | Purpose |
|---|---|
| BASIC | Core operations |
| TYPICAL | Information normally needed to read a plan |
| ALL | More detailed output |
| +PREDICATE | Predicate information |
| +ALIAS | Alias/query block |
| +OUTLINE | Plan outline hints |
| +PEEKED_BINDS | Peeked bind values if present |
| +NOTE | Optimizer notes |
| +IOSTATS | Runtime I/O statistics if available |
| +MEMSTATS | Memory statistics if available |
| ALLSTATS LAST | Runtime statistics of the last collected execution |

Options can be combined in the format string, for example ALLSTATS LAST +PEEKED_BINDS +PREDICATE. Availability and output detail depend on the Oracle release.

### 9.4. Predicate Information

Access Predicates are typically conditions used to locate rows in an index/row source. Filter Predicates are conditions applied after or within an operation. Distinguishing them helps explain why an operation reads many rows only to discard most of them.

### 9.5. Outline Data

+OUTLINE can display outline hints used to reproduce a plan. This is useful data when studying a plan or using SQL Plan Management. Do not copy an outline into permanent hints without understanding its dependencies and environment.

## 10. EXPLAIN PLAN and Bind Variables

### 10.1. Literals and Binds Can Lead to Different Estimates

Compare:

```sql
SELECT *
FROM orders
WHERE customer_id = 1001;
```

with:

```sql
SELECT *
FROM orders
WHERE customer_id = :customer_id;
```

A literal gives the optimizer specific value information at parse time. A bind may be handled via bind peeking/ACS and child cursor behavior. You cannot assume a literal plan from EXPLAIN PLAN reliably represents every bind execution.

### 10.2. Bind Datatypes and Implicit Conversion

If CUSTOMER_ID is NUMBER but the application binds VARCHAR2, Oracle may perform conversion. Conversion can affect access paths and estimates. Bind the correct datatype and inspect Predicate Information/the plan.

### 10.3. Peeked Binds Are Not All Binds

+PEEKED_BINDS displays the bind information peeked during the relevant parse if available. It is not a history of all bind values ever executed. Use V$SQL_BIND_CAPTURE when appropriate, while remembering that bind capture does not record every execution and has limitations.

### 10.4. Child Cursors and ACS

Adaptive Cursor Sharing can create child cursors suited for different selectivity ranges. When a query runs slowly, identify the actual child cursor, bind-aware status, and plan hash instead of only running EXPLAIN PLAN with a literal.

## 11. Adaptive Plans and Executed Plans

### 11.1. Adaptive Plans

An adaptive plan can contain multiple plan choices at optimization time. At runtime, Oracle can use runtime information to choose the appropriate branch when adaptive conditions are met.

### 11.2. Displayed Plans May Contain Unused Branches

Plan output may show inactive operations or alternative branches. You need to read the format and adaptive information to distinguish the selected branch from unused branches.

### 11.3. ALLSTATS LAST

Runtime statistics show which operations actually produced rows/starts and which branch was executed. EXPLAIN PLAN only shows the projected plan and has no runtime evidence of which branch was chosen.

### 11.4. Plan Hash Value

PLAN_HASH_VALUE is a fingerprint used to identify plan structure according to Oracle's algorithm. Two cursors with different plan hashes typically have different plan structures; matching plan hashes do not guarantee that all runtime details, predicates, binds, or environments are identical.

Some releases also include a full plan hash or other plan hash metadata. Do not use plan hash as sole proof that two executions are completely equivalent.

## 12. SQL Monitor and Other Runtime Sources

### 12.1. Real-Time SQL Monitoring

SQL Monitoring can provide information per execution, operation, elapsed time, CPU, I/O, parallel servers, and progress over time. It is especially useful for long-running SQL or parallel execution.

Real-Time SQL Monitoring depends on edition, licensing/management packs, and configuration. Verify privileges and licensing terms in your environment before using it.

### 12.2. DBMS_SQLTUNE.REPORT_SQL_MONITOR

In environments with appropriate privileges and licensing, you can generate a report:

```sql
SELECT DBMS_SQLTUNE.REPORT_SQL_MONITOR(
           sql_id       => :sql_id,
           type         => 'TEXT',
           report_level => 'ALL'
       )
FROM dual;
```

A SQL Monitor report adds runtime detail; it does not replace identifying the exact execution/child cursor. You may need SQL_EXEC_ID and SQL_EXEC_START when the same SQL_ID has multiple executions.

### 12.3. SQL Trace and TKPROF

SQL trace records parse/execute/fetch details, waits, and related statistics. TKPROF formats the trace for investigation. Tracing helps separate parse, execute, and fetch time as well as waits; plans inside trace output can provide additional execution evidence.

Enabling trace incurs overhead and can capture sensitive binds/data. Use it within controlled scope/duration and protect trace files.

### 12.4. AWR and ASH

AWR/ASH help observe workload and SQL/plan history over time in environments with appropriate privileges/licensing. Aggregated historical data does not necessarily replace full runtime statistics for a specific execution.

### 12.5. Application Tracing

Applications should log SQL_ID, module/action, request ID, execution timing, and appropriately sanitized bind metadata. This helps correlate slow requests with the exact cursor in the database. Do not write secrets or raw sensitive data to logs.

## 13. Which Environment Factors Cause EXPLAIN PLAN to Differ?

| Factor | EXPLAIN PLAN | Executed Cursor Plan |
|---|---|---|
| Bind values | May not reproduce bind peek/child behavior | Bound to the actual cursor/child |
| Bind datatype | Depends on how explain/parse is invoked | Datatype bound by the application |
| Optimizer environment | Current explain session | Environment at cursor parse |
| Statistics | Stats at explain time | Stats/metadata when the cursor was parsed |
| Schema/synonyms | Per explain session | Per actual parsing schema and context |
| VPD/context | Context of the explain session | Context when the application parsed |
| Child cursor | Does not represent a specific runtime child | Has SQL_ID and child number |
| Adaptive behavior | Projected plan | Can observe runtime branch |
| Runtime rows/time/I/O | Not available for target SQL | Available if gathered |
| SQL Profile/Baseline/Patch | Depends on explain environment | Can affect actual cursor |

## 14. Workflow for Investigating a Slow SQL Statement

### Step 1 — Identify the Exact Execution

Collect SQL_ID, child number, SQL_EXEC_ID/SQL_EXEC_START if available, module/action, user/schema, request ID, and execution timestamp.

### Step 2 — Retrieve Full SQL Text

Compare the SQL text from the cursor with the SQL generated by the application. Check bind placeholders, literals, comments/hints, and query blocks.

### Step 3 — Retrieve the Cursor Plan

Call DBMS_XPLAN.DISPLAY_CURSOR with the specific SQL_ID/child number. Do not assume child 0 is the child the application is using.

### Step 4 — Gather Runtime Statistics

If safely reproducible, run with GATHER_PLAN_STATISTICS or an appropriate STATISTICS_LEVEL and retrieve ALLSTATS LAST. For past production executions, check SQL Monitor/AWR/trace if data is available.

### Step 5 — Compare E-Rows and A-Rows

Find the first operation with a large discrepancy, accounting for Starts. Record the predicates and input row sources.

### Step 6 — Check Binds and Child Cursors

Inspect bind datatypes, peeked binds, bind sensitivity/awareness, and optimizer environment. Determine whether the query serves multiple selectivity groups.

### Step 7 — Check Objects and Statistics

Verify owner/object, table/column/index stats, histograms, extended stats, partition stats, stale status, and gather timestamps.

### Step 8 — Check Runtime Factors

Inspect concurrency, DOP, workarea memory, TEMP spill, I/O, locks, waits, session context, and schema changes near the incident time.

### Step 9 — Form Hypotheses and Test Under Control

Use EXPLAIN PLAN to explore an alternative rewrite or setting, then validate with cursor plan/runtime in a representative environment. Do not change system-wide optimizer parameters for quick tests.

### Step 10 — Protect the Good Plan

Once a stable plan is identified, evaluate a SQL Plan Baseline or appropriate SQL Tuning tool. Document the conditions, SQL text, bind profile, plan hash, and before/after measurements.

## 15. Example Comparing EXPLAIN PLAN and Cursor Plan

### 15.1. Create Lab Data

Run in a dedicated lab schema:

```sql
CREATE TABLE plan_lab (
    id NUMBER NOT NULL,
    category VARCHAR2(20),
    payload VARCHAR2(100)
);

INSERT INTO plan_lab(id, category, payload)
SELECT level,
       CASE
           WHEN MOD(level, 100) = 0 THEN 'RARE'
           ELSE 'COMMON'
       END,
       RPAD('X', 50, 'X')
FROM dual
CONNECT BY level <= 100000;

CREATE INDEX plan_lab_cat_ix
    ON plan_lab(category);

COMMIT;
```

### 15.2. Gather Statistics

BEGIN

## 16. Common Mistakes and Misconceptions

### 16.1. Using EXPLAIN PLAN to Conclude Query Runtime

EXPLAIN PLAN does not execute the target SQL and does not measure actual elapsed time. Use cursor runtime statistics, SQL Monitor, or trace.

### 16.2. Comparing Plans Without Keeping the Same Binds

A common literal and a rare literal can have vastly different selectivity. Record bind values/types and child cursors.

### 16.3. Looking at the Wrong Child Cursor

A SQL_ID can have multiple children. Calling DISPLAY_CURSOR with the wrong child number can lead to misdiagnosis. Identify the child from V$SQL, trace, or APM.

### 16.4. Not Collecting A-Rows

Without GATHER_PLAN_STATISTICS or appropriate runtime statistics, ALLSTATS LAST cannot retroactively produce actual rows for a past execution. Gather them when reproducing or use available historical sources.

### 16.5. Reading E-Rows and A-Rows While Ignoring Starts

An operation executed multiple times can have cumulative A-Rows. Account for Starts before concluding an estimate error.

### 16.6. Confusing Cost with Elapsed Time

Cost is an optimizer metric, not seconds. A lower-cost plan does not guarantee lower runtime when estimates are skewed or workloads differ.

### 16.7. Assuming EXPLAIN PLAN Always Matches Production

Session, schema, context, statistics, binds, version, profiles/baselines, and runtime adaptive behavior can differ. Reproduce the production environment as closely as possible.

### 16.8. Looking Only at the Topmost Operation

A plan is a row-source tree. Trace parent-child relationships, predicates, and cardinalities from the child operations.

### 16.9. Using Before/After EXPLAIN PLAN to Prove Runtime Improvement

An explain plan only shows what is projected. After changing SQL/stats/indexes, run a representative workload and measure runtime, buffers, reads, CPU, and latency.

### 16.10. Enabling Runtime Statistics System-Wide Without Control

STATISTICS_LEVEL=ALL can increase overhead. Prefer the GATHER_PLAN_STATISTICS hint for lab queries or enable the setting in an investigation session and restore it afterward.

## 17. Rules for Using Each Tool

| Tool | When to Use | Key Limitations |
|---|---|---|
| EXPLAIN PLAN | Inspect projected plan, test SQL rewrites | Does not execute target SQL; no actual rows/time |
| DBMS_XPLAN.DISPLAY | Format a plan in PLAN_TABLE | Only reflects the stored explain run |
| DBMS_XPLAN.DISPLAY_CURSOR | Inspect an actual cursor plan in the shared pool | Requires exact SQL_ID/child; runtime stats may not be collected |
| DBMS_XPLAN.DISPLAY_AWR | Inspect historical plans in AWR | Depends on AWR/licensing/privileges; not all executions have actual rows |
| SQL Monitor | Analyze long/parallel executions at runtime | Depends on licensing, privileges, and monitoring thresholds |
| SQL Trace/TKPROF | Analyze parse/execute/fetch, waits, and I/O | Incurs overhead; requires managing trace files |
| AWR/ASH | Investigate workload and history | Aggregated data; depends on licensing/privileges |

**Principle to remember:** EXPLAIN PLAN shows how the optimizer projects executing SQL in the explain environment; it does not execute the target SQL and does not provide runtime rows/time. DBMS_XPLAN.DISPLAY reads PLAN_TABLE, whereas DISPLAY_CURSOR reads actual cursors in the library cache. When investigating production, identify the SQL_ID/child cursor, bind datatypes/values, optimizer environment, and session context; gather runtime statistics to compare E-Rows with A-Rows while accounting for Starts. Use EXPLAIN PLAN to explore, then validate every change with actual execution and representative measurements.
