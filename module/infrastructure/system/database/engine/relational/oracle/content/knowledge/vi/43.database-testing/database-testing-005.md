# Kiểm thử SQL với NULL, chuỗi rỗng, dữ liệu trùng và Unicode

Kiểm thử SQL trong Oracle cần chú ý đến khác biệt giữa cách ứng dụng Java biểu diễn dữ liệu và cách Oracle lưu, so sánh, ràng buộc, sắp xếp và trả dữ liệu. Bốn nhóm tình huống dễ tạo lỗi là:

- **NULL:** biểu diễn giá trị không xác định hoặc không có. SQL dùng logic ba giá trị nên phép so sánh với NULL không hoạt động như so sánh thông thường.
- **Chuỗi rỗng:** Oracle xử lý chuỗi ký tự có độ dài bằng 0 như NULL đối với các kiểu ký tự thông thường. Một chuỗi chỉ chứa dấu cách vẫn là dữ liệu khác NULL.
- **Dữ liệu trùng:** trùng có thể là trùng toàn bộ dòng, trùng khóa nghiệp vụ, trùng sau chuẩn hóa hoặc trùng theo collation. UNIQUE constraint, GROUP BY và logic ứng dụng có vai trò khác nhau.
- **Unicode:** một ký tự có thể cần nhiều byte, một ký tự hiển thị có thể gồm nhiều code point, và hai chuỗi nhìn giống nhau có thể có biểu diễn Unicode khác nhau. Character set, length semantics, JDBC binding và collation đều ảnh hưởng kết quả.

Mục tiêu của bài học là xây dựng bộ kiểm thử có thể tái lập, xác định chính xác Oracle đang lưu gì và hiểu vì sao một predicate, constraint hoặc phép so sánh cho ra kết quả cụ thể. Các ví dụ sử dụng Oracle SQL và Java JDBC; tên bảng, dữ liệu và giá trị cấu hình chỉ mang tính minh họa.

## 1. Vì sao phải kiểm thử các trường hợp biên?

Một câu SQL có thể chạy đúng với dữ liệu thông thường nhưng sai khi một cột chứa NULL, chuỗi rỗng, dấu cách, giá trị Unicode hoặc khóa nghiệp vụ bị lặp.

Ví dụ, ứng dụng có thể gửi chuỗi rỗng cho trường ghi chú. Java phân biệt null với chuỗi rỗng, nhưng khi bind vào cột VARCHAR2 của Oracle, chuỗi rỗng được xử lý như NULL. Nếu truy vấn dùng phép so sánh với chuỗi rỗng, kết quả không phải là tìm các dòng có chuỗi rỗng như ở một số database khác.

Tương tự, hệ thống có thể kiểm tra trước rằng email chưa tồn tại rồi mới INSERT. Hai request đồng thời có thể cùng vượt qua bước SELECT và cùng INSERT. Chỉ UNIQUE constraint mới là hàng rào cuối cùng bảo vệ tính duy nhất ở database.

Với Unicode, chuỗi "é" có thể được biểu diễn bằng một code point dựng sẵn hoặc bằng chữ "e" kết hợp dấu sắc. Hai chuỗi nhìn giống nhau nhưng byte sequence khác nhau. So sánh nhị phân, chuẩn hóa và collation có thể cho kết quả khác nhau.

### 1.1 Các lớp cần kiểm thử

| Lớp | Câu hỏi cần trả lời |
|---|---|
| Java input | Phân biệt null, empty, blank và whitespace như thế nào? |
| JDBC binding | setString, setNull, setNString có gửi đúng kiểu dữ liệu không? |
| Oracle storage | Giá trị được lưu là NULL, empty LOB hay chuỗi có dấu cách? |
| SQL semantics | Predicate, JOIN, GROUP BY và aggregate xử lý NULL ra sao? |
| Constraint | UNIQUE, CHECK, NOT NULL và foreign key cho phép trường hợp nào? |
| Character set | Ký tự có được lưu đầy đủ trong database character set không? |
| Length | Giới hạn tính theo byte hay character? |
| Collation | Chữ hoa/thường, dấu và Unicode-equivalent được so sánh thế nào? |
| Concurrency | Hai transaction cùng ghi một khóa có tạo duplicate không? |
| Regression | Kết quả có ổn định giữa môi trường và phiên bản không? |

### 1.2 Nguyên tắc tạo test

Một test tốt phải chỉ rõ:

- Input gốc được gửi từ ứng dụng.
- Kiểu cột đích.
- Kiểu bind parameter.
- NLS/session settings có liên quan.
- Dữ liệu sau khi lưu.
- SQL dùng để đọc lại.
- Kết quả mong đợi.
- Transaction có commit hay rollback.

Không nên chỉ nhìn chuỗi hiển thị trên màn hình. NULL, chuỗi rỗng và một chuỗi có dấu cách có thể được UI render giống nhau. Hãy kiểm tra thêm IS NULL, LENGTH, LENGTHB, DUMP hoặc mã byte khi cần.

## 2. Tạo môi trường kiểm thử có thể tái lập

Dùng schema riêng hoặc bảng test có tên rõ ràng. Không thử INSERT, DELETE hoặc thay đổi NLS trên bảng nghiệp vụ production chỉ để kiểm tra một giả thuyết.

Ví dụ bảng test:

~~~sql
CREATE TABLE sql_edge_case_test (
    test_id       NUMBER GENERATED BY DEFAULT AS IDENTITY,
    case_name     VARCHAR2(100 CHAR),
    varchar_value VARCHAR2(100 CHAR),
    char_value    CHAR(10 CHAR),
    number_value  NUMBER,
    created_at    TIMESTAMP WITH TIME ZONE DEFAULT SYSTIMESTAMP,
    CONSTRAINT sql_edge_case_test_pk PRIMARY KEY (test_id)
);
~~~

Định nghĩa CHAR/VARCHAR2 với CHAR semantics tường minh giúp test không phụ thuộc NLS_LENGTH_SEMANTICS của session tạo bảng.

Nếu phiên bản Oracle hoặc chính sách schema không cho phép identity column, dùng sequence và trigger hoặc cấp test_id từ ứng dụng.

### 2.1 Dùng transaction và rollback

Có thể chạy test trong transaction riêng:

~~~sql
SAVEPOINT before_edge_case_test;

INSERT INTO sql_edge_case_test (
    case_name,
    varchar_value,
    char_value,
    number_value
)
VALUES (
    'null-case',
    NULL,
    'A',
    10
);

-- Chạy các truy vấn kiểm tra tại đây.

ROLLBACK TO before_edge_case_test;
~~~

Nếu test cần xác nhận dữ liệu từ session khác hoặc qua connection pool, cần commit trong schema test và có bước cleanup riêng. ROLLBACK chỉ hoàn tác transaction hiện tại; nó không xóa dữ liệu đã commit từ session khác.

### 2.2 Ghi nhận môi trường

Kết quả test có thể phụ thuộc database version, character set, NLS và JDBC driver. Thu thập các thông tin sau trước khi chạy:

~~~sql
SELECT * FROM v$version;

SELECT parameter, value
FROM nls_database_parameters
WHERE parameter IN (
    'NLS_CHARACTERSET',
    'NLS_NCHAR_CHARACTERSET'
);

SELECT parameter, value
FROM nls_session_parameters
WHERE parameter IN (
    'NLS_COMP',
    'NLS_SORT',
    'NLS_LENGTH_SEMANTICS',
    'NLS_LANGUAGE',
    'NLS_TERRITORY',
    'NLS_DATE_LANGUAGE'
)
ORDER BY parameter;
~~~

Quyền đọc V$VERSION có thể cần được cấp. Nếu không có quyền, ghi nhận version qua công cụ quản trị hoặc DBA.

NLS_LENGTH_SEMANTICS là mặc định khi tạo một số cột ký tự nếu DDL không ghi rõ BYTE hoặc CHAR. Nó không tự thay đổi semantics của cột đã tồn tại. Nên khai báo độ dài rõ trong DDL và không dựa vào giá trị session ngầm định.

## 3. NULL trong Oracle và logic ba giá trị

Trong SQL, NULL biểu thị giá trị không xác định hoặc không có. NULL không phải số 0, không phải chuỗi rỗng, không phải FALSE và cũng không phải một giá trị có thể so sánh bằng dấu bằng thông thường.

SQL sử dụng logic ba giá trị:

- TRUE
- FALSE
- UNKNOWN

Khi một biểu thức so sánh với NULL, kết quả thường là UNKNOWN. Trong mệnh đề WHERE, chỉ dòng có điều kiện TRUE mới được giữ lại; FALSE và UNKNOWN đều bị loại.

### 3.1 So sánh đúng với NULL

Không dùng:

~~~sql
SELECT *
FROM employees
WHERE commission_pct = NULL;
~~~

Biểu thức này không tìm được các dòng có commission_pct là NULL, vì phép so sánh cho kết quả UNKNOWN.

Dùng:

~~~sql
SELECT *
FROM employees
WHERE commission_pct IS NULL;
~~~

Và:

~~~sql
SELECT *
FROM employees
WHERE commission_pct IS NOT NULL;
~~~

Đây là cú pháp kiểm tra NULL chuẩn.

### 3.2 Bảng chân trị cơ bản

| Biểu thức | Kết quả |
|---|---|
| 5 = 5 | TRUE |
| 5 = 6 | FALSE |
| 5 = NULL | UNKNOWN |
| NULL = NULL | UNKNOWN |
| 5 <> NULL | UNKNOWN |
| NULL IS NULL | TRUE |
| NULL IS NOT NULL | FALSE |
| NOT UNKNOWN | UNKNOWN |

Điểm quan trọng: NULL không bằng NULL trong phép so sánh bằng. Nếu cần kiểm tra hai giá trị có cùng trạng thái NULL hoặc bằng nhau, phải viết logic rõ ràng.

### 3.3 AND, OR và NOT

Logic ba giá trị ảnh hưởng đến điều kiện kết hợp:

| A | B | A AND B | A OR B |
|---|---|---|---|
| TRUE | TRUE | TRUE | TRUE |
| TRUE | FALSE | FALSE | TRUE |
| TRUE | UNKNOWN | UNKNOWN | TRUE |
| FALSE | UNKNOWN | FALSE | UNKNOWN |
| UNKNOWN | UNKNOWN | UNKNOWN | UNKNOWN |

Ví dụ:

~~~sql
SELECT *
FROM employees
WHERE department_id = 10
   OR commission_pct IS NULL;
~~~

Một dòng có department_id = 10 vẫn được chọn dù commission_pct NULL, vì TRUE OR UNKNOWN là TRUE.

Ngược lại:

~~~sql
SELECT *
FROM employees
WHERE department_id = 10
  AND commission_pct > 0;
~~~

Nếu commission_pct NULL, điều kiện thứ hai UNKNOWN; TRUE AND UNKNOWN là UNKNOWN nên dòng bị loại.

### 3.4 NOT không biến UNKNOWN thành TRUE

Ví dụ:

~~~sql
SELECT *
FROM employees
WHERE NOT (commission_pct = 0);
~~~

Dòng có commission_pct NULL không được trả về. Bởi vì NULL = 0 là UNKNOWN và NOT UNKNOWN vẫn là UNKNOWN.

Nếu nghiệp vụ muốn lấy mọi dòng có commission khác 0 hoặc chưa có commission, phải viết:

~~~sql
SELECT *
FROM employees
WHERE commission_pct <> 0
   OR commission_pct IS NULL;
~~~

Đừng suy luận rằng NOT trước một biểu thức sẽ tự động bao gồm các giá trị NULL.

## 4. Các phép toán với NULL

### 4.1 Phép toán số học

Phép toán số học có toán hạng NULL thường trả về NULL:

~~~sql
SELECT
    100 + NULL AS add_result,
    100 - NULL AS subtract_result,
    100 * NULL AS multiply_result,
    100 / NULL AS divide_result
FROM dual;
~~~

Các cột kết quả đều là NULL.

Nếu cần thay NULL bằng một giá trị nghiệp vụ, phải dùng quy tắc rõ ràng:

~~~sql
SELECT salary + NVL(commission, 0) AS total_compensation
FROM employee_pay;
~~~

Chỉ thay NULL bằng 0 khi nghiệp vụ xác định "không có commission" tương đương số tiền 0. Không tự động thay mọi NULL bằng 0, vì NULL có thể mang nghĩa chưa biết hoặc chưa được nhập.

### 4.2 Nối chuỗi trong Oracle

Oracle có hành vi nối chuỗi đặc thù: nối một chuỗi ký tự với NULL hoặc chuỗi có độ dài bằng 0 thường trả về chuỗi còn lại; nối hai giá trị NULL cho kết quả NULL. Đây là quy tắc của Oracle đối với phép nối ký tự và cần được kiểm thử theo phiên bản.

Ví dụ:

~~~sql
SELECT
    'Oracle' || NULL AS result_one,
    NULL || 'JDBC' AS result_two,
    NULL || NULL AS result_three
FROM dual;
~~~

Không suy rộng hành vi nối chuỗi này sang phép so sánh hoặc phép toán số học. Oracle có thể thay đổi cách xử lý chuỗi rỗng trong tương lai; ứng dụng không nên dựa vào việc coi NULL và empty là hai trạng thái riêng đối với VARCHAR2.

### 4.3 Hàm aggregate

Các hàm aggregate thường bỏ qua NULL trong biểu thức đầu vào:

~~~sql
SELECT
    COUNT(*) AS all_rows,
    COUNT(commission_pct) AS rows_with_commission,
    SUM(commission_pct) AS commission_sum,
    AVG(commission_pct) AS commission_average,
    MIN(commission_pct) AS minimum_commission,
    MAX(commission_pct) AS maximum_commission
FROM employees;
~~~

- COUNT(*) đếm tất cả dòng.
- COUNT(column) chỉ đếm giá trị không NULL.
- SUM, AVG, MIN và MAX bỏ qua NULL.
- Nếu không có giá trị không NULL, nhiều aggregate trả NULL; COUNT trả 0.

Nếu muốn AVG xem NULL như 0, phải viết AVG(NVL(column, 0)), nhưng kết quả nghiệp vụ sẽ khác vì các dòng NULL được đưa vào mẫu số.

### 4.4 GROUP BY và DISTINCT

GROUP BY gom các giá trị NULL của cùng một nhóm vào một nhóm:

~~~sql
SELECT department_id, COUNT(*)
FROM employees
GROUP BY department_id;
~~~

Các dòng có department_id NULL được gom chung trong một group.

DISTINCT cũng chỉ trả một kết quả NULL:

~~~sql
SELECT DISTINCT department_id
FROM employees;
~~~

Điều này khác cách UNIQUE constraint xử lý NULL. GROUP BY/DISTINCT là phép gom kết quả truy vấn; UNIQUE là quy tắc kiểm soát dữ liệu khi ghi.

### 4.5 ORDER BY

Oracle mặc định thường đặt NULLS LAST với ASC và NULLS FIRST với DESC. Để kết quả kiểm thử rõ ràng và ổn định, nên ghi rõ:

~~~sql
SELECT employee_id, commission_pct
FROM employees
ORDER BY commission_pct ASC NULLS FIRST;
~~~

Hoặc:

~~~sql
ORDER BY commission_pct DESC NULLS LAST;
~~~

Kết quả có thể thay đổi nếu không chỉ định NULLS FIRST/LAST hoặc không có tie-breaker cho các giá trị bằng nhau.

## 5. NOT IN, NOT EXISTS và NULL

Một lỗi phổ biến là dùng NOT IN với tập con có chứa NULL.

Ví dụ:

~~~sql
SELECT customer_id
FROM customers
WHERE customer_id NOT IN (
    SELECT customer_id
    FROM blocked_customers
);
~~~

Nếu subquery trả về một NULL, điều kiện NOT IN có thể trở thành UNKNOWN đối với các giá trị không khớp, khiến query trả về ít dòng hoặc không có dòng nào.

### 5.1 Ví dụ minh họa

Giả sử blocked_customers có các giá trị:

| customer_id |
|---:|
| 10 |
| 20 |
| NULL |

Điều kiện tương đương:

~~~sql
customer_id <> 10
AND customer_id <> 20
AND customer_id <> NULL
~~~

Với customer_id = 30, hai điều kiện đầu TRUE nhưng điều kiện cuối UNKNOWN. TRUE AND TRUE AND UNKNOWN là UNKNOWN nên dòng bị loại.

### 5.2 Dùng NOT EXISTS

Nếu muốn lấy customer không có bản ghi blocked tương ứng:

~~~sql
SELECT c.customer_id
FROM customers c
WHERE NOT EXISTS (
    SELECT 1
    FROM blocked_customers b
    WHERE b.customer_id = c.customer_id
);
~~~

NOT EXISTS kiểm tra có dòng tương ứng hay không, tránh tác động của một NULL không liên quan trong tập con.

Nếu c.customer_id có thể NULL, biểu thức bằng nhau trong subquery không match NULL với NULL. Hãy quyết định rõ khách hàng có ID NULL có được xem là không bị block hay dữ liệu đó phải bị loại bằng IS NOT NULL.

### 5.3 Khi nào NOT IN vẫn dùng được?

Có thể dùng NOT IN nếu subquery được bảo đảm không trả NULL, ví dụ cột có NOT NULL constraint hoặc query lọc rõ:

~~~sql
SELECT c.customer_id
FROM customers c
WHERE c.customer_id NOT IN (
    SELECT b.customer_id
    FROM blocked_customers b
    WHERE b.customer_id IS NOT NULL
);
~~~

Dù vậy, NOT EXISTS thường diễn đạt anti-join rõ ràng hơn khi có quan hệ giữa hai bảng.

## 6. NVL, COALESCE, NULLIF và CASE

Các hàm xử lý NULL có mục đích khác nhau. Chọn hàm theo semantics, không chỉ theo cú pháp ngắn.

### 6.1 NVL

NVL trả biểu thức thứ hai nếu biểu thức đầu tiên NULL:

~~~sql
SELECT NVL(commission_pct, 0)
FROM employees;
~~~

Lưu ý NVL có quy tắc chuyển đổi kiểu dữ liệu. Oracle có thể chuyển expr2 sang kiểu expr1 hoặc áp dụng quy tắc numeric precedence. Hãy dùng các kiểu tương thích và kiểm thử khi kết hợp VARCHAR2, NUMBER hoặc DATE.

Vì chuỗi rỗng là NULL đối với VARCHAR2, biểu thức sau không tạo chuỗi rỗng thay thế:

~~~sql
SELECT NVL(varchar_value, '')
FROM sql_edge_case_test;
~~~

Nếu varchar_value NULL, giá trị thay thế cũng là NULL. Hãy dùng một giá trị thực sự không rỗng nếu nghiệp vụ cần hiển thị placeholder.

### 6.2 COALESCE

COALESCE trả về biểu thức đầu tiên khác NULL:

~~~sql
SELECT COALESCE(mobile_phone, work_phone, home_phone, 'Chưa có số')
FROM contacts;
~~~

COALESCE hỗ trợ nhiều đối số và có short-circuit evaluation. Các biểu thức cần tương thích kiểu dữ liệu.

### 6.3 NULLIF

NULLIF trả NULL khi hai biểu thức bằng nhau, nếu không trả biểu thức đầu:

~~~sql
SELECT numerator / NULLIF(denominator, 0)
FROM calculations;
~~~

Ví dụ giúp tránh chia cho 0. Nếu denominator bằng 0, NULLIF trả NULL và phép chia trả NULL thay vì lỗi chia cho 0. Nếu nghiệp vụ muốn báo lỗi hoặc dùng một giá trị thay thế, cần xử lý riêng.

### 6.4 CASE

CASE giúp viết quy tắc rõ ràng:

~~~sql
SELECT
    CASE
        WHEN commission_pct IS NULL THEN 'NOT_SET'
        WHEN commission_pct = 0 THEN 'ZERO'
        ELSE 'HAS_VALUE'
    END AS commission_state
FROM employees;
~~~

Thứ tự WHEN quan trọng. Nhánh IS NULL phải được viết riêng; không viết commission_pct = NULL.

### 6.5 DECODE và NULL

Oracle DECODE có hành vi đặc biệt: hai giá trị NULL trong các biểu thức so sánh của DECODE được xem là bằng nhau. Điều này khác toán tử bằng thông thường.

~~~sql
SELECT DECODE(NULL, NULL, 'MATCH', 'NO_MATCH')
FROM dual;
~~~

Kết quả là MATCH.

Không nên thay DECODE bằng biểu thức bằng một cách máy móc hoặc ngược lại. Khi viết logic mới, CASE thường dễ đọc và chuẩn SQL hơn; nếu cần NULL-safe comparison, viết rõ IS NULL/IS NOT NULL.

## 7. Chuỗi rỗng trong Oracle

Với kiểu ký tự thông thường, Oracle hiện xử lý chuỗi có độ dài bằng 0 như NULL. Ví dụ:

~~~sql
INSERT INTO sql_edge_case_test (case_name, varchar_value)
VALUES ('empty-varchar', '');
~~~

Khi đọc lại:

~~~sql
SELECT
    varchar_value,
    CASE WHEN varchar_value IS NULL THEN 'IS_NULL'
         ELSE 'NOT_NULL'
    END AS null_state,
    LENGTH(varchar_value) AS char_length
FROM sql_edge_case_test
WHERE case_name = 'empty-varchar';
~~~

varchar_value được xem là NULL, và LENGTH trả NULL.

### 7.1 NULL, empty và blank

Cần phân biệt các input sau:

| Input từ ứng dụng | Ví dụ | Hành vi thường thấy với VARCHAR2 |
|---|---|---|
| Java null | null | SQL NULL nếu bind null đúng cách |
| Chuỗi rỗng | "" | Oracle xử lý như NULL |
| Một dấu cách | " " | Chuỗi có một ký tự space |
| Nhiều dấu cách | "   " | Chuỗi có các ký tự space |
| Tab | ký tự TAB | Chuỗi không rỗng nếu được lưu |
| Non-breaking space | U+00A0 | Ký tự Unicode khác space ASCII |
| Chuỗi có chữ | "Oracle" | Giá trị ký tự thông thường |

Không dùng trim hoặc kiểm tra length để thay thế mọi khái niệm. Ví dụ, một chuỗi gồm tab hoặc non-breaking space có thể không bị xử lý giống dấu cách ASCII.

### 7.2 Kiểm tra bằng LENGTH và DUMP

Ví dụ:

~~~sql
SELECT
    case_name,
    CASE WHEN varchar_value IS NULL THEN 'NULL'
         ELSE 'NOT NULL'
    END AS null_state,
    LENGTH(varchar_value) AS char_len,
    LENGTHB(varchar_value) AS byte_len,
    DUMP(varchar_value, 1016) AS dump_value
FROM sql_edge_case_test
ORDER BY test_id;
~~~

- IS NULL xác nhận NULL.
- LENGTH đếm độ dài theo character semantics của Oracle.
- LENGTHB trả độ dài tính theo byte.
- DUMP hiển thị kiểu dữ liệu và biểu diễn byte ở định dạng được chọn.

DUMP(NULL) cũng trả NULL; không dùng DUMP một mình để phân biệt chuỗi rỗng với NULL trong VARCHAR2 vì Oracle đã chuẩn hóa chuỗi rỗng thành NULL.

### 7.3 CHAR có blank padding

CHAR(n) là kiểu fixed-length. Oracle đệm dấu cách ở cuối để đạt độ dài khai báo. Ví dụ CHAR(10) lưu giá trị 'A' như một giá trị được blank-pad.

~~~sql
INSERT INTO sql_edge_case_test (case_name, char_value)
VALUES ('char-one-letter', 'A');
~~~

Đọc lại:

~~~sql
SELECT
    char_value,
    LENGTH(char_value) AS char_len,
    LENGTHB(char_value) AS byte_len,
    DUMP(char_value, 1016) AS dump_value
FROM sql_edge_case_test
WHERE case_name = 'char-one-letter';
~~~

CHAR có thể trả độ dài bao gồm các dấu cách đệm theo semantics của kiểu. VARCHAR2 không tự đệm độ dài cố định.

### 7.4 Chuỗi chỉ có dấu cách không phải NULL

Ví dụ:

~~~sql
INSERT INTO sql_edge_case_test (case_name, varchar_value)
VALUES ('one-space', ' ');
~~~

Dòng này có varchar_value khác NULL. LENGTH thường trả 1 cho một dấu cách ASCII; LENGTHB cũng thường trả 1 với AL32UTF8.

Nếu ứng dụng gọi trim() trước khi bind, một chuỗi chỉ có dấu cách có thể biến thành chuỗi rỗng và sau đó được Oracle lưu như NULL. Đây là thay đổi nghiệp vụ cần được quyết định rõ.

### 7.5 EMPTY_CLOB khác NULL

CLOB là LOB locator, có cách biểu diễn empty LOB riêng. EMPTY_CLOB() tạo một empty LOB có locator, khác với NULL.

Ví dụ:

~~~sql
CREATE TABLE lob_edge_case_test (
    id NUMBER PRIMARY KEY,
    note_clob CLOB
);

INSERT INTO lob_edge_case_test (id, note_clob)
VALUES (1, NULL);

INSERT INTO lob_edge_case_test (id, note_clob)
VALUES (2, EMPTY_CLOB());

SELECT
    id,
    CASE WHEN note_clob IS NULL THEN 'NULL'
         ELSE 'NOT_NULL'
    END AS lob_state,
    CASE WHEN note_clob IS NOT NULL
         THEN DBMS_LOB.GETLENGTH(note_clob)
    END AS lob_length
FROM lob_edge_case_test
ORDER BY id;
~~~

Dòng 1 có NULL locator; dòng 2 có empty LOB locator với độ dài 0. Đây là trường hợp không nên áp dụng quy tắc chuỗi rỗng VARCHAR2 một cách máy móc.

## 8. Kiểm thử NULL và chuỗi rỗng qua JDBC

Java phân biệt null và empty string. Oracle JDBC binding cần được kiểm thử để biết database nhận được gì.

### 8.1 Bind Java null

Dùng setNull với JDBC type rõ ràng:

~~~java
String sql =
    "INSERT INTO sql_edge_case_test (case_name, varchar_value) " +
    "VALUES (?, ?)";

try (Connection connection = dataSource.getConnection();
     PreparedStatement statement = connection.prepareStatement(sql)) {

    statement.setString(1, "java-null");
    statement.setNull(2, java.sql.Types.VARCHAR);
    statement.executeUpdate();
}
~~~

Có thể dùng setString(index, null) trong nhiều trường hợp, nhưng setNull với SQL type rõ ràng giúp code dễ hiểu và tránh vấn đề suy luận kiểu ở một số API/framework.

### 8.2 Bind chuỗi rỗng

~~~java
statement.setString(2, "");
~~~

Với VARCHAR2, Oracle xử lý chuỗi rỗng như NULL. Nếu ứng dụng cần phân biệt "người dùng không nhập" và "người dùng chủ động xóa nội dung", cần lưu thêm trạng thái riêng hoặc dùng một mô hình dữ liệu khác. Không thể dựa vào VARCHAR2 để phân biệt hai giá trị này chỉ bằng null và empty.

### 8.3 Bind chuỗi chỉ có dấu cách

~~~java
statement.setString(2, "   ");
~~~

Đây là chuỗi có dữ liệu, không phải NULL. Nếu business rule muốn coi blank là không có giá trị, chuẩn hóa ở một tầng được quy định rõ và test cả space, tab, line break và Unicode whitespace.

### 8.4 Kiểu NCHAR/NVARCHAR2

Với cột NCHAR/NVARCHAR2, JDBC có các API N-string như setNString và getNString:

~~~java
String sql =
    "INSERT INTO unicode_test (national_text) VALUES (?)";

try (PreparedStatement statement = connection.prepareStatement(sql)) {
    statement.setNString(1, "Tiếng Việt 日本語");
    statement.executeUpdate();
}
~~~

Dùng setNString cho national character type khi phù hợp với driver. Với VARCHAR2, setString thường là lựa chọn tự nhiên vì dữ liệu được lưu theo database character set.

Không chuyển qua lại VARCHAR2 và NVARCHAR2 chỉ để "sửa Unicode" mà chưa hiểu database character set, national character set và implicit conversion.

## 9. UNIQUE constraint và NULL

UNIQUE constraint kiểm soát tính duy nhất của một hoặc nhiều cột. Trong Oracle, NULL có semantics đặc biệt:

- Một UNIQUE constraint trên một cột cho phép nhiều dòng có giá trị NULL.
- Với unique key ghép, các trường hợp có thành phần NULL có semantics riêng; cần kiểm thử đúng tổ hợp cột và phiên bản đang dùng thay vì suy luận từ phép so sánh bằng.
- PRIMARY KEY không cho phép NULL và yêu cầu duy nhất.
- Nếu nghiệp vụ bắt buộc giá trị phải có, cần NOT NULL cùng UNIQUE.

Ví dụ:

~~~sql
CREATE TABLE user_alias_test (
    id NUMBER PRIMARY KEY,
    alias VARCHAR2(100),
    CONSTRAINT user_alias_test_uk UNIQUE (alias)
);
~~~

Có thể thêm nhiều dòng alias NULL:

~~~sql
INSERT INTO user_alias_test (id, alias) VALUES (1, NULL);
INSERT INTO user_alias_test (id, alias) VALUES (2, NULL);
~~~

Hai INSERT này được phép bởi unique constraint một cột vì NULL không được xem như một giá trị bằng nhau để vi phạm uniqueness.

### 9.1 UNIQUE không đồng nghĩa NOT NULL

Nếu cột email phải luôn có giá trị và không trùng:

~~~sql
CREATE TABLE app_user_test (
    user_id NUMBER PRIMARY KEY,
    email VARCHAR2(320 CHAR) NOT NULL,
    CONSTRAINT app_user_test_email_uk UNIQUE (email)
);
~~~

NOT NULL đảm bảo có giá trị; UNIQUE đảm bảo không trùng. Hai constraint giải quyết hai yêu cầu khác nhau.

### 9.2 Composite unique key

Ví dụ:

~~~sql
CREATE TABLE external_reference_test (
    tenant_id NUMBER,
    external_code VARCHAR2(100),
    CONSTRAINT external_reference_test_uk
        UNIQUE (tenant_id, external_code)
);
~~~

Cần kiểm thử các tổ hợp:

- (1, 'A')
- (1, 'A') lần hai
- (1, NULL)
- (1, NULL) lần hai
- (NULL, 'A')
- (NULL, 'A') lần hai
- (NULL, NULL) nhiều lần

Với composite key, Oracle cho phép các tổ hợp chứa NULL theo semantics của unique constraint; do đó không nên giả định rằng mọi dòng có cùng phần non-NULL sẽ luôn bị từ chối. Tạo test trong schema riêng và ghi rõ kết quả theo Oracle version. Nếu business rule muốn coi NULL là một giá trị chung trong composite key, hãy mã hóa rule đó bằng constraint/index có biểu thức chuẩn hóa rõ ràng thay vì dựa vào cách người đọc diễn giải UNIQUE mặc định.

### 9.3 CHECK constraint và NULL

CHECK constraint chỉ loại dòng khi biểu thức cho kết quả FALSE. Nếu biểu thức cho UNKNOWN vì một cột NULL, dòng có thể vẫn được chấp nhận.

Ví dụ:

~~~sql
CREATE TABLE quantity_test (
    id NUMBER PRIMARY KEY,
    quantity NUMBER CHECK (quantity > 0)
);
~~~

INSERT quantity NULL có thể được chấp nhận vì NULL > 0 là UNKNOWN, không phải FALSE.

Nếu quantity bắt buộc phải có và lớn hơn 0:

~~~sql
CREATE TABLE quantity_required_test (
    id NUMBER PRIMARY KEY,
    quantity NUMBER NOT NULL CHECK (quantity > 0)
);
~~~

Luôn tách yêu cầu presence (NOT NULL) và miền giá trị (CHECK).

### 9.4 Foreign key và NULL

Một foreign key nullable có thể chứa NULL mà không cần dòng cha tương ứng. Nếu quan hệ bắt buộc phải tồn tại, thêm NOT NULL cho cột foreign key.

Với composite foreign key, cần hiểu cách Oracle xử lý các thành phần NULL và kiểm thử đầy đủ. Nếu business rule yêu cầu tất cả thành phần cùng có hoặc cùng không có, có thể thêm CHECK constraint để ngăn trạng thái chỉ có một phần khóa.

## 10. Kiểm thử dữ liệu trùng bằng SQL

Trước khi tạo UNIQUE constraint hoặc xử lý migration, cần xác định "trùng" theo định nghĩa nghiệp vụ.

Các dạng trùng thường gặp:

1. Trùng toàn bộ các cột.
2. Trùng primary/business key.
3. Trùng một phần khóa ghép.
4. Trùng sau khi trim khoảng trắng.
5. Trùng không phân biệt chữ hoa/thường.
6. Trùng không phân biệt dấu.
7. Trùng sau Unicode normalization.
8. Trùng theo quy tắc collation cụ thể.

### 10.1 Tìm duplicate theo business key

Ví dụ tìm email trùng:

~~~sql
SELECT email, COUNT(*) AS duplicate_count
FROM app_users
WHERE email IS NOT NULL
GROUP BY email
HAVING COUNT(*) > 1
ORDER BY duplicate_count DESC, email;
~~~

GROUP BY gom các giá trị NULL vào một nhóm, vì vậy thêm WHERE email IS NOT NULL nếu mục tiêu là tìm duplicate của giá trị đã nhập. Nếu muốn đếm nhóm NULL riêng, bỏ điều kiện đó và xem nhóm NULL như một trạng thái dữ liệu cần xử lý.

### 10.2 Tìm duplicate theo khóa ghép

~~~sql
SELECT tenant_id,
       external_code,
       COUNT(*) AS duplicate_count
FROM external_reference
GROUP BY tenant_id, external_code
HAVING COUNT(*) > 1
ORDER BY duplicate_count DESC;
~~~

Kết quả cần được diễn giải theo business key. Nếu một phần key có NULL, hãy quyết định liệu các dòng đó có được coi là cùng một thực thể hay là các giá trị chưa xác định riêng biệt.

### 10.3 Tìm duplicate toàn bộ dòng

~~~sql
SELECT customer_id,
       full_name,
       phone_number,
       COUNT(*) AS duplicate_count
FROM customer_import_stage
GROUP BY customer_id, full_name, phone_number
HAVING COUNT(*) > 1;
~~~

Không nhất thiết phải đưa surrogate ID vào GROUP BY nếu muốn tìm các dòng trùng về mặt dữ liệu. Nếu thêm primary key duy nhất, sẽ không còn phát hiện được duplicate nghiệp vụ.

### 10.4 Dùng ROW_NUMBER để chọn dòng giữ lại

Nếu đã xác định duplicate và có quy tắc giữ lại một dòng:

~~~sql
SELECT *
FROM (
    SELECT s.*,
           ROW_NUMBER() OVER (
               PARTITION BY email
               ORDER BY created_at, import_id
           ) AS rn
    FROM customer_import_stage s
    WHERE email IS NOT NULL
)
WHERE rn > 1;
~~~

ROW_NUMBER giúp xác định các dòng dư theo partition. ORDER BY phải có tie-breaker ổn định, ví dụ import_id duy nhất. Không xóa dữ liệu chỉ dựa trên truy vấn mẫu; trước khi DELETE cần xác nhận bản ghi giữ lại, foreign key phụ thuộc và audit requirements.

### 10.5 Tìm duplicate sau chuẩn hóa

Ví dụ business rule bỏ qua khoảng trắng ở hai đầu và không phân biệt chữ hoa/thường:

~~~sql
SELECT UPPER(TRIM(email)) AS normalized_email,
       COUNT(*) AS duplicate_count
FROM customer_import_stage
WHERE email IS NOT NULL
GROUP BY UPPER(TRIM(email))
HAVING COUNT(*) > 1;
~~~

Đây mới chỉ là chuẩn hóa case theo môi trường; không giải quyết đầy đủ Unicode normalization hoặc mọi quy tắc ngôn ngữ. Nếu chuẩn hóa được dùng trong constraint, phải áp dụng cùng một quy tắc khi insert, search, update và migration.

## 11. Chống duplicate khi nhiều transaction đồng thời

Một pattern sai phổ biến:

~~~text
1. SELECT xem email đã tồn tại chưa.
2. Nếu chưa, INSERT.
~~~

Hai request có thể chạy cùng lúc:

~~~text
Transaction A                  Transaction B
-------------                  -------------
SELECT email -> no row
                               SELECT email -> no row
INSERT email
                               INSERT same email
COMMIT
                               COMMIT
~~~

Cả hai SELECT đều thấy chưa có dòng. Chỉ UNIQUE constraint mới đảm bảo không có hai dòng cùng khóa khi transaction cạnh tranh.

### 11.1 Dùng UNIQUE constraint làm hàng rào cuối

~~~sql
ALTER TABLE app_users
ADD CONSTRAINT app_users_email_uk UNIQUE (email);
~~~

Ứng dụng cần bắt lỗi unique violation, thường là ORA-00001, rồi đọc lại trạng thái hoặc trả conflict phù hợp.

Không coi lỗi ORA-00001 luôn là lỗi hệ thống. Trong một thao tác create-if-absent, đó có thể là kết quả hợp lệ cho biết request khác đã tạo trước.

### 11.2 MERGE không tự loại bỏ race condition

MERGE hữu ích cho upsert:

~~~sql
MERGE INTO customer_target t
USING (
    SELECT :customer_code AS customer_code,
           :customer_name AS customer_name
    FROM dual
) s
ON (t.customer_code = s.customer_code)
WHEN MATCHED THEN
    UPDATE SET t.customer_name = s.customer_name
WHEN NOT MATCHED THEN
    INSERT (customer_code, customer_name)
    VALUES (s.customer_code, s.customer_name);
~~~

Tuy nhiên, hai transaction đồng thời có thể cùng đánh giá NOT MATCHED và cạnh tranh INSERT. Unique constraint vẫn cần thiết; ứng dụng phải xử lý ORA-00001 hoặc retry theo logic phù hợp.

### 11.3 Idempotent insert

Với import hoặc API retry, nên có một request key/import key duy nhất:

~~~sql
CREATE TABLE import_request (
    request_id VARCHAR2(100) PRIMARY KEY,
    payload_hash RAW(32) NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT SYSTIMESTAMP
);
~~~

Nếu request được gửi lại với cùng request_id và cùng payload_hash, trả kết quả cũ hoặc trạng thái đã xử lý. Nếu cùng key nhưng payload khác, từ chối vì idempotency key bị tái sử dụng sai.

## 12. Unicode trong Oracle

Unicode là chuẩn mã hóa ký tự, không phải một encoding duy nhất. Một ký tự có thể được biểu diễn bằng một hoặc nhiều code point. Encoding chuyển các code point thành byte.

Trong Oracle cần phân biệt:

- Database character set: dùng cho CHAR, VARCHAR2, CLOB và nhiều metadata.
- National character set: dùng cho NCHAR, NVARCHAR2, NCLOB.
- Client character set và driver conversion.
- Unicode normalization.
- Collation và quy tắc so sánh/sắp xếp.

### 12.1 AL32UTF8

AL32UTF8 là database character set UTF-8 chuẩn của Oracle và thường là lựa chọn khuyến nghị cho database mới cần hỗ trợ đa ngôn ngữ. Nó mã hóa Unicode code point bằng 1 đến 4 byte.

Không nhầm AL32UTF8 với character set Oracle cũ tên UTF8, vốn sử dụng cách mã hóa CESU-8 cho supplementary characters. Với hệ thống mới, hãy kiểm tra và chọn AL32UTF8 theo hướng dẫn Oracle cho release đang triển khai.

Kiểm tra:

~~~sql
SELECT parameter, value
FROM nls_database_parameters
WHERE parameter IN (
    'NLS_CHARACTERSET',
    'NLS_NCHAR_CHARACTERSET'
);
~~~

Không thể đổi database character set một cách tùy tiện sau khi database đã có dữ liệu. Migration character set cần đánh giá dữ liệu, khả năng chuyển đổi, tool và kế hoạch backup/rollback.

### 12.2 NCHAR và NVARCHAR2

NCHAR/NVARCHAR2 sử dụng national character set của database. National character set thường là AL16UTF16 hoặc UTF8 tùy cấu hình Oracle.

- CHAR/VARCHAR2 lưu theo database character set.
- NCHAR/NVARCHAR2 lưu theo national character set.
- CLOB dùng database character set.
- NCLOB dùng national character set.

Không phải cứ dữ liệu có tiếng Việt hoặc tiếng Nhật thì bắt buộc dùng NVARCHAR2. Nếu database character set là AL32UTF8, VARCHAR2 có thể lưu đa ngôn ngữ. Chọn loại cột dựa trên kiến trúc và yêu cầu tương thích.

### 12.3 Kiểm tra charset và khả năng biểu diễn

Một bộ test Unicode nên có:

- Tiếng Việt có dấu: Tiếng Việt.
- Tiếng Nhật: 日本語.
- Tiếng Hàn: 한국어.
- Tiếng Trung: 中文.
- Ký tự supplementary/emoji: 😀.
- Ký tự kết hợp: chữ cái và combining mark.
- Ký tự khoảng trắng Unicode như non-breaking space.
- Ký tự dấu nháy, dấu gạch và ký hiệu tiền tệ.

Không chỉ test SELECT hiển thị trên SQL client. Cần INSERT bằng JDBC, đọc lại bằng JDBC, kiểm tra code point/byte và so sánh với input ban đầu.

## 13. BYTE semantics và CHAR semantics

Khai báo VARCHAR2(20) có thể dùng BYTE hoặc CHAR semantics tùy NLS_LENGTH_SEMANTICS tại thời điểm tạo cột.

- BYTE semantics giới hạn theo số byte.
- CHAR semantics giới hạn theo số character theo semantics Oracle.

Với AL32UTF8, một character có thể cần nhiều byte. Vì vậy VARCHAR2(20 BYTE) không chắc chứa được 20 ký tự tiếng Việt, Nhật hoặc emoji.

### 13.1 Khai báo rõ semantics

Ví dụ:

~~~sql
CREATE TABLE unicode_length_test (
    code_byte VARCHAR2(20 BYTE),
    code_char VARCHAR2(20 CHAR)
);
~~~

Với code_byte, giới hạn là 20 byte. Với code_char, giới hạn là 20 character theo semantics của Oracle; vẫn phải tuân theo giới hạn byte tối đa của datatype và phiên bản.

### 13.2 LENGTH và LENGTHB

~~~sql
SELECT
    LENGTH('A') AS ascii_chars,
    LENGTHB('A') AS ascii_bytes,
    LENGTH('Tiếng Việt') AS viet_chars,
    LENGTHB('Tiếng Việt') AS viet_bytes
FROM dual;
~~~

LENGTH trả độ dài theo character semantics; LENGTHB trả độ dài theo byte trong character set đang dùng.

Với AL32UTF8, dữ liệu ASCII thường dùng một byte mỗi ký tự; ký tự có dấu hoặc ký tự ngoài ASCII thường cần nhiều byte.

### 13.3 Các hàm độ dài liên quan

Oracle cung cấp các hàm:

- LENGTH: số character theo character set của input.
- LENGTHB: số byte.
- LENGTHC: số Unicode complete characters.
- LENGTH2: số UCS2 code points.
- LENGTH4: số UCS4 code points.

Các hàm này không nhất thiết bằng số ký tự người dùng nhìn thấy trên màn hình. Một grapheme có thể gồm base character và combining mark; nó có thể được đếm thành nhiều đơn vị tùy hàm.

Ví dụ một chữ có dấu có thể được biểu diễn bằng ký tự dựng sẵn hoặc ký tự cơ sở cộng combining mark. Độ dài có thể khác nhau dù hiển thị gần như giống nhau.

### 13.4 ORA-12899

Nếu giá trị vượt giới hạn cột, Oracle có thể trả ORA-12899: value too large for column.

Khi điều tra:

1. Xem DDL cột là BYTE hay CHAR.
2. Xem database character set.
3. Đo LENGTH và LENGTHB của input trong môi trường tương ứng.
4. Kiểm tra kiểu bind và conversion.
5. Kiểm tra giá trị có bị truncate ở Java/UI trước khi gửi không.
6. Xác định nghiệp vụ muốn giới hạn theo ký tự, byte hay số grapheme.

Không tăng độ dài cột một cách tự động trước khi xác định hợp đồng dữ liệu.

## 14. Unicode normalization

Hai chuỗi có thể nhìn giống nhau nhưng dùng code point khác nhau.

Ví dụ chữ é có thể được biểu diễn:

- NFC: một code point dựng sẵn U+00E9.
- NFD: U+0065 (e) theo sau U+0301 (combining acute accent).

Hai chuỗi có thể khác byte và khác độ dài dù người dùng nhìn thấy giống nhau.

Oracle không tự động chuẩn hóa mọi dữ liệu văn bản thành NFC/NFD khi INSERT. Nếu nghiệp vụ cần so sánh canonical-equivalent strings, hãy chuẩn hóa ở tầng ứng dụng hoặc dùng một chiến lược database được thiết kế và kiểm thử rõ.

### 14.1 Chuẩn hóa trong Java

Java cung cấp Normalizer:

~~~java
import java.text.Normalizer;

String normalized =
    Normalizer.normalize(input, Normalizer.Form.NFC);
~~~

Có thể chọn NFC để lưu một dạng canonical phổ biến. Tuy nhiên, quyết định phải nhất quán giữa tất cả producer, import, API và batch job.

Không chuẩn hóa âm thầm nếu dữ liệu cần bảo toàn nguyên văn cho mục đích pháp lý, tìm kiếm hoặc audit. Có thể lưu raw input và normalized key riêng nếu nghiệp vụ cần cả hai.

### 14.2 Tạo test cho hai dạng Unicode

~~~java
String composed = "\u00E9";
String decomposed = "e\u0301";

System.out.println(composed.equals(decomposed)); // false

String nfcA = Normalizer.normalize(
    composed, Normalizer.Form.NFC
);
String nfcB = Normalizer.normalize(
    decomposed, Normalizer.Form.NFC
);

System.out.println(nfcA.equals(nfcB)); // true
~~~

Sau khi normalize, bind cả hai giá trị vào cột test và kiểm tra byte/length. Nếu database cần unique theo normalized value, hãy lưu normalized key hoặc dùng cơ chế index được thiết kế rõ ràng.

### 14.3 Unicode normalization khác case folding

NFC/NFD giải quyết biểu diễn canonical; nó không tự biến chữ hoa thành chữ thường hoặc bỏ dấu. Case folding và accent-insensitive comparison là quy tắc riêng.

Ví dụ, A, a và á có quan hệ khác nhau tùy collation. Đừng gộp normalize, lowercase và remove diacritics thành một thao tác chung nếu nghiệp vụ chưa định nghĩa.

## 15. Collation, so sánh và sắp xếp Unicode

So sánh chuỗi có thể dựa trên binary representation hoặc linguistic rules. Oracle hỗ trợ NLS_SORT và NLS_COMP ở mức session trong các cấu hình liên quan; các phiên bản mới còn có collation ở mức column/expression với cú pháp và khả năng phụ thuộc release.

### 15.1 Binary comparison và linguistic comparison

Binary comparison so sánh theo biểu diễn ký tự/byte theo character set. Linguistic comparison dùng quy tắc ngôn ngữ để xử lý thứ tự, case hoặc accent.

Ví dụ một truy vấn có thể cần không phân biệt chữ hoa/thường:

~~~sql
SELECT *
FROM app_users
WHERE NLSSORT(username, 'NLS_SORT=BINARY_CI')
    = NLSSORT(:username, 'NLS_SORT=BINARY_CI');
~~~

BINARY_CI là một ví dụ case-insensitive sort. Quy tắc accent-insensitive và các sort khác phụ thuộc Oracle version và NLS support.

### 15.2 NLS_COMP và NLS_SORT

Có thể thiết lập session để kiểm thử:

~~~sql
ALTER SESSION SET NLS_COMP = LINGUISTIC;
ALTER SESSION SET NLS_SORT = BINARY_CI;
~~~

Các thiết lập này ảnh hưởng cách một số phép so sánh và sắp xếp được xử lý trong session. Không nên thay đổi toàn cục hoặc giả định tất cả connection pool session có cùng state.

Trong connection pool, session state có thể tồn tại sau khi logical connection được trả về. Nếu ứng dụng dùng ALTER SESSION, cần reset state hoặc cấu hình session initialization để request sau không bị ảnh hưởng.

### 15.3 Collation và UNIQUE

Nếu business rule không phân biệt hoa/thường, UNIQUE constraint binary mặc định có thể cho phép Alice và alice cùng tồn tại. Có thể cần function-based unique index hoặc collation-aware unique design tùy release.

Ví dụ minh họa:

~~~sql
CREATE UNIQUE INDEX app_users_username_ci_uk
ON app_users (NLSSORT(username, 'NLS_SORT=BINARY_CI'));
~~~

Trước khi tạo index, phải kiểm tra dữ liệu hiện tại có duplicate theo quy tắc mới hay không. Nếu có, tạo unique index sẽ thất bại. Cần xác định cách xử lý bản ghi xung đột và đảm bảo truy vấn lookup dùng cùng semantics.

### 15.4 ORDER BY và tính ổn định

Khi sort theo collation, nhiều chuỗi có thể được xem là tương đương. Thêm một khóa phụ duy nhất để thứ tự ổn định:

~~~sql
SELECT user_id, username
FROM app_users
ORDER BY NLSSORT(username, 'NLS_SORT=BINARY_CI'),
         user_id;
~~~

Điều này quan trọng cho pagination và test snapshot. Nếu không có tie-breaker, thứ tự các dòng bằng nhau có thể thay đổi giữa execution.

## 16. Unicode trong Java và JDBC

Java String lưu chuỗi dưới dạng UTF-16 code units. Một số Unicode code point ngoài Basic Multilingual Plane được biểu diễn bằng surrogate pair, tức hai code unit.

Do đó:

- String.length() đếm UTF-16 code units.
- String.codePointCount() đếm Unicode code points.
- Cả hai không nhất thiết bằng số grapheme cluster người dùng nhìn thấy.

Ví dụ:

~~~java
String emoji = "😀";

System.out.println(emoji.length()); // 2 UTF-16 code units
System.out.println(
    emoji.codePointCount(0, emoji.length())
); // 1 Unicode code point
~~~

Nếu ứng dụng giới hạn input theo String.length(), emoji có thể được tính là hai đơn vị. Nếu nghiệp vụ muốn giới hạn ký tự người dùng nhìn thấy, cần một grapheme-aware library hoặc quy tắc riêng.

### 16.1 setString và getString

Với VARCHAR2:

~~~java
statement.setString(1, "Tiếng Việt 日本語 😀");
String value = resultSet.getString(1);
~~~

Driver chuyển đổi giữa Java UTF-16 và database character set. Với AL32UTF8, các code point Unicode được hỗ trợ có thể được lưu đầy đủ. Nếu database character set không biểu diễn được ký tự, conversion có thể gây lỗi hoặc thay thế tùy đường đi và cấu hình; cần test thực tế, không giả định.

### 16.2 setNString và getNString

Với NVARCHAR2/NCHAR:

~~~java
statement.setNString(1, "Tiếng Việt 日本語 😀");
String value = resultSet.getNString(1);
~~~

Dùng API N-string khi cột là national character type và driver yêu cầu/khuyến nghị. Đọc DDL để biết cột là VARCHAR2 hay NVARCHAR2.

### 16.3 Không cắt chuỗi bằng byte tùy tiện

Không dùng substring theo byte UTF-8 nếu chưa kiểm tra ranh giới code point. Cắt giữa các byte của một ký tự đa byte có thể tạo dữ liệu không hợp lệ.

Nếu cần giới hạn theo Oracle byte capacity, encode chuỗi theo UTF-8 trong Java rồi tính số byte, nhưng vẫn phải tính đến database conversion, national charset và collation. Tốt nhất là kiểm tra tại tầng validation bằng cùng semantics với cột đích và xử lý ORA-12899 có kiểm soát.

### 16.4 Kiểm tra round-trip

Một test JDBC nên:

1. Tạo chuỗi test trong Java.
2. Ghi nhận code points và UTF-16 length.
3. Bind vào cột đích.
4. Đọc lại bằng getString/getNString.
5. So sánh chuỗi gốc với chuỗi đọc lại.
6. So sánh NFC-normalized form nếu nghiệp vụ cần.
7. Đo LENGTH/LENGTHB phía Oracle.
8. Kiểm tra không bị thay thế ký tự hoặc truncate.

## 17. Dữ liệu Unicode nhìn giống nhau nhưng không bằng nhau

Một số tình huống cần đưa vào test:

- Chữ dựng sẵn so với base + combining mark.
- Latin có dấu so với không dấu.
- Chữ hoa so với chữ thường.
- Space U+0020 so với non-breaking space U+00A0.
- Hyphen-minus U+002D so với en dash U+2013 hoặc em dash U+2014.
- ASCII apostrophe so với curly apostrophe.
- Emoji có variation selector.
- Emoji có skin-tone modifier.
- Emoji family dùng zero-width joiner.
- Ký tự supplementary ngoài BMP.

Hai chuỗi có thể hiển thị gần giống nhau nhưng khác code point, byte, collation weight hoặc normalization. Một test chỉ nhìn UI là không đủ.

### 17.1 Kiểm tra code point trong Java

~~~java
input.codePoints().forEach(cp ->
    System.out.printf("U+%04X%n", cp)
);
~~~

Với dữ liệu đọc từ database, chạy cùng đoạn code trên để xác định ký tự có thay đổi trong quá trình lưu/đọc hay không.

### 17.2 Kiểm tra byte trong Oracle

~~~sql
SELECT
    LENGTH(text_value) AS char_length,
    LENGTHB(text_value) AS byte_length,
    DUMP(text_value, 1016) AS hex_dump
FROM unicode_test
WHERE id = :id;
~~~

DUMP hữu ích khi cần xem byte/code representation theo Oracle. Nó không thay thế một công cụ Unicode inspector, nhưng giúp xác định dữ liệu trong database có đúng như mong đợi không.

## 18. Kiểm thử trim, whitespace và chuẩn hóa

TRIM trong Oracle thường xử lý dấu cách theo quy tắc mặc định; không nên giả định nó xóa mọi Unicode whitespace. Tab, newline và non-breaking space có thể cần xử lý riêng.

### 18.1 Test space ASCII

~~~sql
SELECT
    LENGTH(' ') AS one_space_length,
    LENGTH(TRIM(' ')) AS trimmed_length
FROM dual;
~~~

Sau TRIM, kết quả chuỗi rỗng được Oracle xem như NULL, vì vậy LENGTH trả NULL.

### 18.2 Kiểm tra bằng DUMP

~~~sql
SELECT
    DUMP(' ', 1016) AS ascii_space,
    DUMP(UNISTR('\00A0'), 1016) AS no_break_space,
    DUMP(CHR(9), 1016) AS tab_character
FROM dual;
~~~

UNISTR hỗ trợ biểu diễn ký tự Unicode bằng escape trong SQL. Cách viết escape và byte output cần được kiểm tra theo database/national character set.

### 18.3 Định nghĩa blank theo nghiệp vụ

Nếu một trường bắt buộc không được chứa whitespace-only, không chỉ dùng IS NOT NULL. Có thể kiểm tra sau khi chuẩn hóa khoảng trắng theo tập ký tự được nghiệp vụ chấp nhận.

Ví dụ đơn giản cho space ASCII:

~~~sql
CHECK (TRIM(display_name) IS NOT NULL)
~~~

Nhưng CHECK với NULL/UNKNOWN cần được hiểu đúng và TRIM mặc định không xử lý toàn bộ Unicode whitespace. Một giải pháp robust hơn là chuẩn hóa input ở application service và lưu normalized key riêng, kèm constraint để bảo vệ quy tắc đã chọn.

## 20. Ví dụ tạo dữ liệu kiểm thử tổng hợp

Bảng test đơn giản:

~~~sql
CREATE TABLE customer_edge_test (
    id NUMBER PRIMARY KEY,
    customer_code VARCHAR2(40 CHAR),
    display_name VARCHAR2(100 CHAR),
    note_text VARCHAR2(200 CHAR),
    amount NUMBER,
    CONSTRAINT customer_edge_code_uk UNIQUE (customer_code)
);
~~~

Chèn dữ liệu:

~~~sql
INSERT INTO customer_edge_test
    (id, customer_code, display_name, note_text, amount)
VALUES
    (1, 'C001', 'Nguyễn An', 'Ghi chú', 100);

INSERT INTO customer_edge_test
    (id, customer_code, display_name, note_text, amount)
VALUES
    (2, 'C002', '日本語', '', NULL);

INSERT INTO customer_edge_test
    (id, customer_code, display_name, note_text, amount)
VALUES
    (3, 'C003', '😀', ' ', 0);

INSERT INTO customer_edge_test
    (id, customer_code, display_name, note_text, amount)
VALUES
    (4, NULL, '한국어', NULL, 50);

INSERT INTO customer_edge_test
    (id, customer_code, display_name, note_text, amount)
VALUES
    (5, NULL, '中文', 'NBSP test', 75);
~~~

Có thể chèn hai NULL vào customer_code vì unique constraint một cột cho phép nhiều NULL. note_text của dòng 2 được lưu như NULL; note_text của dòng 3 là một dấu cách.

Kiểm tra:

~~~sql
SELECT
    id,
    customer_code,
    CASE WHEN note_text IS NULL THEN 'NULL'
         ELSE 'NOT_NULL'
    END AS note_state,
    LENGTH(note_text) AS note_length,
    LENGTHB(note_text) AS note_bytes,
    display_name,
    LENGTH(display_name) AS name_length,
    LENGTHB(display_name) AS name_bytes,
    amount
FROM customer_edge_test
ORDER BY id;
~~~

Dùng test này để so sánh kết quả trên các database environment. Nếu character set hoặc column length semantics khác nhau, ghi lại sự khác biệt thay vì giả định môi trường giống nhau.

## 21. Kiểm thử duplicate sau chuẩn hóa và tạo unique index

Giả sử username không phân biệt hoa/thường theo business rule. Trước khi tạo index, tìm duplicate:

~~~sql
SELECT UPPER(TRIM(username)) AS normalized_username,
       COUNT(*) AS duplicate_count
FROM app_users
WHERE username IS NOT NULL
GROUP BY UPPER(TRIM(username))
HAVING COUNT(*) > 1;
~~~

Sau khi xử lý dữ liệu xung đột, có thể tạo function-based unique index:

~~~sql
CREATE UNIQUE INDEX app_users_username_norm_uk
ON app_users (UPPER(TRIM(username)));
~~~

Index này chỉ thể hiện một quy tắc cụ thể: UPPER và TRIM theo semantics Oracle/session phù hợp. Nó không tự xử lý NFC/NFD, mọi Unicode whitespace hoặc mọi ngôn ngữ.

Nếu muốn NULL không được phép, thêm NOT NULL. Nếu muốn cho phép nhiều NULL, cần kiểm tra behavior của expression/index với NULL và test theo release. Function-based index có thể có quy tắc lưu key khác nhau với toàn bộ expression NULL; hãy xác nhận bằng test insert trước khi áp dụng production.

### 21.1 Không để normalization khác nhau giữa write và read

Nếu insert chuẩn hóa bằng NFC nhưng search không chuẩn hóa, người dùng có thể không tìm thấy bản ghi vừa tạo. Tất cả đường ghi, đọc, update, import, dedupe và unique enforcement phải dùng cùng quy tắc.

Nên đóng gói normalization trong một thư viện hoặc API dùng chung, có version và test vectors. Khi thay đổi quy tắc, cần migration và kiểm tra collision trước.

## 22. Test session state và NLS trong connection pool

Connection pool giữ physical session qua nhiều request. Session state như NLS_COMP, NLS_SORT, timezone, current schema và module/action có thể tồn tại sau khi logical connection được trả về pool.

Nếu request A chạy:

~~~sql
ALTER SESSION SET NLS_SORT = BINARY_CI;
~~~

và request B dùng lại physical connection mà không reset, request B có thể nhận semantics khác với dự kiến.

### 22.1 Kiểm tra state trước và sau checkout

Có thể chạy:

~~~sql
SELECT
    SYS_CONTEXT('USERENV', 'SID') AS sid,
    SYS_CONTEXT('USERENV', 'CURRENT_SCHEMA') AS current_schema
FROM dual;

SELECT parameter, value
FROM nls_session_parameters
WHERE parameter IN ('NLS_COMP', 'NLS_SORT');
~~~

Ghi lại SID để biết logical connection có quay lại cùng physical session hay không.

### 22.2 Reset session state

Cấu hình connection pool nên có hook initialization/reset nếu ứng dụng thay đổi session state. Tránh để mỗi DAO tự ALTER SESSION mà không khôi phục.

Các thay đổi NLS chỉ dùng cho một truy vấn có thể được thể hiện qua biểu thức NLSSORT/NLS parameters khi phù hợp, hoặc qua collation expression ở release hỗ trợ. Điều này làm semantics gần với câu SQL hơn và giảm phụ thuộc session state.

### 22.3 Test song song

Chạy nhiều request trên cùng pool:

- Request A cần case-insensitive comparison.
- Request B cần binary comparison.
- Request C đọc Unicode và sắp xếp.
- Request D chạy import.

Xác nhận kết quả không phụ thuộc request nào đã dùng physical connection trước đó.

## 23. Đọc dữ liệu và so sánh trong Java

Không nên dùng Java String.equals() để mô phỏng mọi quy tắc Oracle collation. String.equals() so sánh chuỗi theo code unit sequence; Oracle có thể dùng binary hoặc linguistic collation.

### 23.1 So sánh raw

~~~java
boolean sameRaw = left.equals(right);
~~~

Phù hợp khi muốn kiểm tra hai chuỗi Java có cùng sequence hay không.

### 23.2 So sánh sau NFC

~~~java
String leftNfc =
    Normalizer.normalize(left, Normalizer.Form.NFC);
String rightNfc =
    Normalizer.normalize(right, Normalizer.Form.NFC);

boolean sameCanonical = leftNfc.equals(rightNfc);
~~~

Phù hợp khi nghiệp vụ muốn coi canonical-equivalent strings là giống nhau.

### 23.3 So sánh không phân biệt hoa/thường

Có thể dùng Locale.ROOT cho một số quy tắc ứng dụng:

~~~java
boolean sameCaseInsensitive =
    left.toLowerCase(Locale.ROOT)
        .equals(right.toLowerCase(Locale.ROOT));
~~~

Đây không nhất thiết giống Oracle linguistic collation hoặc Unicode full case folding. Nếu ứng dụng và database cùng thực thi một unique/search rule, hãy chọn một semantics chuẩn và kiểm thử hai phía bằng cùng bộ test vectors.

### 23.4 Không dùng locale mặc định tùy tiện

String.toLowerCase() không truyền Locale dùng default locale của JVM. Kết quả có thể khác giữa môi trường chạy. Với key kỹ thuật, Locale.ROOT thường dễ dự đoán hơn; với ngôn ngữ người dùng, cần quy tắc locale-aware được xác định rõ.

## 24. Những lỗi thường gặp và cách tránh

| Lỗi | Vì sao sai | Cách làm đúng |
|---|---|---|
| Dùng column = NULL | So sánh trả UNKNOWN | Dùng IS NULL |
| Dùng column = empty string để tìm empty | Oracle xem empty VARCHAR2 như NULL | Dùng IS NULL; lưu trạng thái riêng nếu cần phân biệt |
| Coi dấu cách là NULL | Space là ký tự có dữ liệu | Test TRIM/whitespace theo business rule |
| Dùng NOT IN với subquery có NULL | UNKNOWN có thể loại mọi dòng | Dùng NOT EXISTS hoặc lọc NULL |
| Dùng UNIQUE để bắt buộc có giá trị | UNIQUE cho phép NULL | Thêm NOT NULL |
| Nghĩ CHECK(column > 0) loại NULL | UNKNOWN không phải FALSE | Thêm NOT NULL |
| SELECT trước INSERT để chống trùng | Race condition giữa transaction | UNIQUE constraint và xử lý ORA-00001 |
| Tin MERGE không có race | Concurrent insert vẫn có thể xung đột | Giữ unique constraint và retry/handle |
| So sánh Unicode bằng mắt | Chuỗi nhìn giống có thể khác code point | Kiểm tra normalization, code point và collation |
| Dùng LENGTHB như số ký tự | Unicode có độ dài byte biến thiên | Dùng LENGTH/CHAR semantics theo yêu cầu |
| Cắt chuỗi theo byte tùy tiện | Có thể cắt giữa UTF-8 sequence | Cắt theo code point/grapheme và kiểm tra byte limit |
| Dùng VARCHAR2(n) mà không rõ semantics | Phụ thuộc BYTE/CHAR mặc định khi tạo | Ghi rõ n BYTE hoặc n CHAR |
| Giả định setString("") lưu empty | Oracle xem empty VARCHAR2 như NULL | Thiết kế trạng thái riêng nếu cần |
| ALTER SESSION trong pool mà không reset | Request sau nhận session state cũ | Khởi tạo/reset session nhất quán |
| Dùng UPPER để chuẩn hóa mọi Unicode | Không xử lý mọi normalization/accent/locale | Định nghĩa normalization và collation đầy đủ |

## 25. Quy trình kiểm thử SQL có hệ thống

Một quy trình phù hợp cho feature mới hoặc regression:

### Bước 1: Viết quy tắc nghiệp vụ

Ví dụ:

- Email bắt buộc.
- Email không phân biệt chữ hoa/thường.
- Username được chuẩn hóa NFC.
- Ghi chú rỗng được xem là chưa có.
- Một tenant không có hai external reference giống nhau.
- Tên hiển thị phải giữ nguyên dấu và Unicode.

Không bắt đầu bằng câu SQL trước khi định nghĩa dữ liệu nào được chấp nhận.

### Bước 2: Xác định schema và semantics

Ghi rõ:

- Data type.
- BYTE/CHAR semantics.
- NOT NULL/UNIQUE/CHECK/FK.
- Database character set.
- National character set nếu dùng.
- Collation.
- Default và DEFAULT ON NULL nếu có.
- Trigger/function-based index ảnh hưởng dữ liệu.

### Bước 3: Xây test vector

Tạo input cho NULL, empty, blank, duplicate, NFC/NFD, case, accent, supplementary character và biên độ dài.

### Bước 4: Test SQL trực tiếp

Chạy INSERT/SELECT/UPDATE trong schema test. Dùng IS NULL, LENGTH, LENGTHB, DUMP, GROUP BY và constraint để quan sát.

### Bước 5: Test qua JDBC

Dùng cùng input qua setString, setNull, setNString và đọc bằng getString/getNString. Kiểm tra round-trip.

### Bước 6: Test concurrency

Chạy hai hoặc nhiều transaction cùng ghi natural key. Xác nhận unique constraint giữ invariant và ứng dụng xử lý ORA-00001 theo hợp đồng.

### Bước 7: Test NLS và pool reuse

Chạy test với session settings khác nhau và tái sử dụng physical connection. Xác nhận semantics được reset hoặc được thể hiện rõ trong SQL.

### Bước 8: Test migration và dữ liệu cũ

Trước khi thêm unique index hoặc thay đổi normalization, tìm duplicate hiện có, phân loại NULL, xác định record giữ lại và kiểm tra foreign key.

### Bước 9: Ghi lại expected result

Mỗi test nên ghi input, DDL, SQL, expected result và actual result. Không chỉ lưu screenshot của SQL client.

## 26. Checklist kiểm thử

### NULL và chuỗi rỗng

- [ ] Kiểm tra IS NULL và IS NOT NULL.
- [ ] Kiểm tra phép so sánh bằng NULL không được dùng trong predicate.
- [ ] Kiểm tra AND/OR/NOT với UNKNOWN.
- [ ] Kiểm tra NOT IN khi subquery có NULL.
- [ ] Kiểm tra NOT EXISTS với khóa nullable.
- [ ] Kiểm tra NVL, COALESCE, NULLIF và CASE.
- [ ] Kiểm tra COUNT(*), COUNT(column), SUM và AVG.
- [ ] Kiểm tra GROUP BY/DISTINCT với NULL.
- [ ] Kiểm tra empty VARCHAR2 được xử lý như NULL.
- [ ] Kiểm tra space, tab, newline và NBSP riêng.
- [ ] Kiểm tra EMPTY_CLOB khác NULL nếu có LOB.

### Duplicate và constraint

- [ ] Tìm duplicate theo natural key.
- [ ] Tìm duplicate toàn bộ business columns.
- [ ] Kiểm tra composite key có NULL.
- [ ] Kiểm tra UNIQUE và NOT NULL riêng biệt.
- [ ] Kiểm tra CHECK với NULL.
- [ ] Kiểm tra foreign key nullable.
- [ ] Kiểm tra race condition hai transaction cùng INSERT.
- [ ] Xử lý ORA-00001 trong ứng dụng.
- [ ] Kiểm tra MERGE khi có concurrency.
- [ ] Kiểm tra duplicate sau trim/case/normalization.

### Unicode

- [ ] Xác nhận NLS_CHARACTERSET là charset mong muốn.
- [ ] Xác nhận NLS_NCHAR_CHARACTERSET nếu dùng NCHAR types.
- [ ] Kiểm tra VARCHAR2 BYTE và CHAR semantics.
- [ ] Kiểm tra LENGTH và LENGTHB.
- [ ] Kiểm tra supplementary characters/emoji.
- [ ] Kiểm tra NFC và NFD.
- [ ] Kiểm tra case/accent collation.
- [ ] Kiểm tra setString/getString.
- [ ] Kiểm tra setNString/getNString cho national types.
- [ ] Kiểm tra ORA-12899 tại giới hạn byte/character.
- [ ] Kiểm tra round-trip từ UI/API tới Oracle và ngược lại.

### Tính lặp lại và vận hành

- [ ] Test dùng schema/bảng riêng.
- [ ] Có rollback hoặc cleanup có kiểm soát.
- [ ] Ghi nhận Oracle version, JDBC driver và NLS settings.

- [ ] Ghi expected/actual result và lỗi Oracle đầy đủ.

## 27. Kết luận

NULL, chuỗi rỗng, duplicate và Unicode không phải các trường hợp biên có thể xử lý bằng một vài câu IF đơn giản. Oracle dùng logic ba giá trị; chuỗi rỗng VARCHAR2 được xử lý như NULL; UNIQUE, CHECK và foreign key có semantics riêng với NULL; duplicate phải được định nghĩa theo business key; Unicode phụ thuộc character set, byte/character length, normalization và collation.

Bộ kiểm thử đáng tin cậy cần chạy cả SQL trực tiếp lẫn JDBC round-trip, quan sát dữ liệu bằng IS NULL, LENGTH, LENGTHB và DUMP, kiểm tra constraint trong tình huống đồng thời, và giữ cố định database/NLS/driver settings. Khi quy tắc dữ liệu được định nghĩa rõ, các test vector có thể được dùng lại cho migration, API validation, import, regression và kiểm thử nhiều môi trường Oracle.
