# Local/Global Indexes and Partition Maintenance Impact in Oracle

When an Oracle table is partitioned, indexes on the table must also be designed around how data is partitioned and around maintenance operations such as ADD, DROP, TRUNCATE, MOVE, SPLIT, MERGE, or EXCHANGE PARTITION. An index can be organized per table partition (local index), or have a scope independent of the table's partitions (global index).

Local indexes are usually easier to maintain alongside data partitions: when a partition is added, dropped, or exchanged, the corresponding index part can be handled locally. Global indexes can access keys across multiple table partitions, making them suited for queries searching by keys that do not include the partition key, though certain partition maintenance operations may require updating the index or render it unusable if the proper options are not used.

Choosing local versus global is not solely a SELECT performance decision. It affects key uniqueness, ETL cost, lock duration, availability, rebuild procedures, and DDL deployment complexity.

After this lesson, you will be able to:

- Distinguish between local indexes, global nonpartitioned indexes, and global partitioned indexes.
- Understand how local index partitions align with table partitions.
- Distinguish between local prefixed and local nonprefixed indexes.
- Choose local/global based on queries, partition keys, unique constraints, and workloads.
- Understand partition pruning and index partition pruning.
- Predict the impact of ADD, DROP, TRUNCATE, MOVE, SPLIT, MERGE, and EXCHANGE PARTITION.
- Use UPDATE INDEXES/UPDATE GLOBAL INDEXES and understand differences across Oracle versions.
- Check for indexes or index partitions in the UNUSABLE state.
- Rebuild index partitions at the proper scope and manage maintenance costs.
- Plan ETL, partition exchange, and post-migration verification.

> Partition maintenance syntax and index maintenance capabilities vary by Oracle version, partition type, index type, and DDL options. Examples in this lesson are common patterns; verify syntax on your running version and inspect index status after every operation. Do not test DROP/TRUNCATE/MOVE on production tables to learn syntax.

## 1. Foundation: Partitioned Tables and Indexes

### 1.1. What is a partitioned table?

Partitioning divides a large table into smaller physical/logical parts based on a partition key. Applications still query a single table name; Oracle identifies which partitions to read or modify based on predicates and metadata.

Example of a SALES table partitioned monthly by SALE_DATE:

| Partition | Data range |
| --- | --- |
| P2026_01 | January 2026 |
| P2026_02 | February 2026 |
| P2026_03 | March 2026 |
| P2026_04 | April 2026 |

A query:

```sql
SELECT SUM(amount)
FROM sales
WHERE sale_date >= DATE '2026-03-01'
  AND sale_date <  DATE '2026-04-01';
```

may only need to read partition P2026_03. Eliminating irrelevant partitions is called partition pruning. Partitioning helps manage data by time, archive, purge, load, and query; it does not automatically create indexes.

### 1.2. Table partitions and index partitions are separate structures

A partitioned table can have:

- No indexes.
- One or more local indexes.
- One or more global indexes.
- Both local and global indexes on different columns.

Each index has its own partitioning and lifecycle. When a table partition changes, determine which indexes Oracle maintains automatically, which require update options, and which index partitions can transition to UNUSABLE.

### 1.3. Local and global describe the relationship to table partitions

- **Local index:** an index partitioned to match the table; each index partition is paired with one table partition.
- **Global index:** an index spanning multiple table partitions; the index's partitioning does not have to match the table's partitioning.

A global index can be a nonpartitioned index (a single global index structure) or a global partitioned index with its own partitioning scheme.

## 2. Local Indexes

### 2.1. Concept

A local index is partitioned using the same partitioning key and corresponding boundaries as the table. Each partition of a local index references only data belonging to the corresponding table partition.

Example:

```sql
CREATE INDEX ix_sales_customer_local
ON sales (customer_id)
LOCAL;
```

If SALES has 12 monthly table partitions, the local index normally has 12 corresponding index partitions. Index partition names may be generated by Oracle from metadata or specified in the index creation statement depending on syntax.

### 2.2. Local index model

```text
TABLE SALES
  P2026_01 ───── LOCAL INDEX PARTITION P2026_01
  P2026_02 ───── LOCAL INDEX PARTITION P2026_02
  P2026_03 ───── LOCAL INDEX PARTITION P2026_03
  P2026_04 ───── LOCAL INDEX PARTITION P2026_04

Each index partition indexes only the rows
in the corresponding table partition.
```

Local indexes are equipartitioned: the index structure mirrors the table's partition structure. This generally keeps maintenance operations isolated to the corresponding index partition rather than adjusting a table-wide index.

### 2.3. Advantages

- **Local maintenance:** dropping/truncating a table partition typically only affects the corresponding local index partition.
- **Data lifecycle management:** archiving or purging by partition keeps remaining index partitions active.
- **Recoverability:** if a local index partition needs rebuilding, that partition can be rebuilt independently.
- **ETL friendly:** new partitions can be loaded and indexed using per-partition workflows.
- **Partition-wise access:** the optimizer can exploit the relationship between table partitions and local index partitions.
- **Independent of global keyspace:** index partitions can be maintained alongside their corresponding table partitions.

### 2.4. Limitations

- Queries without a predicate on the partition key may have to probe many local index partitions.
- A local index is not necessarily the best access path for a table-wide lookup on a key that excludes the partition key.
- Local unique indexes have key restrictions: to guarantee table-wide uniqueness, the unique key must normally contain the full table partitioning key.
- The number of index partitions scales with the number of table partitions, increasing metadata and maintenance work.

### 2.5. Adding partitions and local indexes

When adding a table partition, Oracle can create the corresponding local index partition automatically from metadata. With range partitioning, for example:

```sql
ALTER TABLE sales
ADD PARTITION p2026_05
VALUES LESS THAN (DATE '2026-06-01');
```

Local indexes are maintained in step with the table's partition structure. After DDL, it is still good practice to check USER_IND_PARTITIONS/ALL_IND_PARTITIONS to confirm the new index partition is usable.

## 3. Global Indexes

### 3.1. Global nonpartitioned index

A global nonpartitioned index is a single index that can hold entries pointing to rows in any table partition. The index is not split into partitions matching the table.

For example, on a SALES table partitioned by SALE_DATE, an application needs to look up transactions by SALE_ID without knowing the date:

```sql
CREATE INDEX ix_sales_sale_id_global
ON sales (sale_id);
```

Because this index neither declares LOCAL nor specifies its own partitioning clause, it is a global nonpartitioned index on a partitioned table.

### 3.2. Global partitioned index

A global partitioned index has its own partitioning scheme, independent of the table's partitioning. Illustrative example of a global index hash-partitioned on CUSTOMER_ID:

```sql
CREATE INDEX ix_sales_customer_g
ON sales (customer_id)
GLOBAL PARTITION BY HASH (customer_id)
PARTITIONS 8;
```

These index partitions distribute keys from the entire table by hashing CUSTOMER_ID; they do not correspond one-to-one with monthly table partitions.

A global partitioned index can also be partitioned by range/list/hash depending on syntax and Oracle version limits. Choose the scheme based on how the index is queried and managed, rather than blindly copying the table's scheme.

### 3.3. Global index model

```text
TABLE SALES (partitioned by SALE_DATE)
  P2026_01 ─┐
  P2026_02 ─┼────> GLOBAL INDEX
  P2026_03 ─┤       Contains keys pointing to ROWIDs
  P2026_04 ─┘       across multiple table partitions

Global partitioned index:
  G1, G2, G3 ... are index partitions
  under an independent scheme, not matching table partitions.
```

### 3.4. Advantages

- Lookups by a key excluding the partition key can access one global index instead of probing every local index partition.
- Can support unique constraints on keys that omit the partition key, depending on constraint/index types and partitioned table rules.
- Global partitioned indexes can distribute storage and I/O across multiple index partitions.
- Suitable for applications requiring table-wide access by ID or business key.

### 3.5. Limitations

- DROP/TRUNCATE/SPLIT/MERGE/EXCHANGE operations on a table partition may require maintaining global indexes because the index references rows across many table partitions.
- If the global index is not updated appropriately, the index or index partitions can become UNUSABLE.
- Maintaining a single table partition can generate work on the global index, increasing I/O, redo, DDL duration, or availability impact.
- Global partitioned indexes have their own scheme, so index partition maintenance also requires independent planning.

## 4. Comparing Local and Global Indexes

| Criterion | Local index | Global index |
| --- | --- | --- |
| Relationship to table partitions | Aligned with table partitions | Spans multiple table partitions |
| Index partitioning | Matches the table | Independent or nonpartitioned |
| Drop/truncate a table partition | Usually affects only the matching index partition | May need to update the global index |
| Lookup without partition key | May need to probe many index partitions | Usually more convenient via global index |
| Unique key excluding partition key | Cannot enforce table-wide uniqueness with local unique index | Can use global unique index/constraint when supported |
| Partition administration | Usually simple and localized | More complex when table partitions change |
| Best suited for | DW, partition lifecycle, queries with partition key | Table-wide lookups, unique keys independent of partition key |

There is no rule that every index on a partitioned table must be local or must be global. Designs often combine:

- Local indexes for queries filtering on the partition key or workloads with frequent partition maintenance.
- Global indexes for table-wide ID/key lookups that omit the partition key.
- Avoiding redundant indexes if queries can effectively use partition pruning and local indexes.

## 5. Local Prefixed and Local Nonprefixed Indexes

### 5.1. Prefixed local index

A local index is called prefixed if the table's partition key columns appear at the leading edge (leftmost prefix) of the index key in the appropriate order.

Example on a SALES table partitioned by SALE_DATE:

```sql
CREATE INDEX ix_sales_date_customer_l
ON sales (sale_date, customer_id)
LOCAL;
```

SALE_DATE is the partition key column and leads the index key, so this is a local prefixed index.

### 5.2. Nonprefixed local index

If a local index does not begin with the full partition key, it is a local nonprefixed index:

```sql
CREATE INDEX ix_sales_customer_date_l
ON sales (customer_id, sale_date)
LOCAL;
```

CUSTOMER_ID leads and SALE_DATE follows. The index is still local, but its key does not have the partition key in the prefix position.

### 5.3. Impact on queries

Suppose the query is:

```sql
SELECT *
FROM sales
WHERE sale_date = DATE '2026-03-15'
  AND customer_id = 1001;
```

Oracle can partition-prune by SALE_DATE and then use the matching local index partition. A prefixed index can support access by partition key and customer.

If the query only has:

```sql
SELECT *
FROM sales
WHERE customer_id = 1001;
```

Oracle does not know which monthly partition holds rows for CUSTOMER_ID. With a local nonprefixed index, it may need to probe relevant local index partitions; a global index is usually more convenient if customer lookups run frequently across the entire dataset. However, if the partition count is small or queries have other narrowing conditions, a local index can still be reasonable.

### 5.4. Prefixed does not always mean faster

Prefixed/nonprefixed describes the position of the partition key in the index key, not an absolute performance label. Consider:

- Does the query have a partition key predicate?
- How many partitions must be probed?
- Selectivity of the leading index column?
- Index clustering and number of ROWIDs to fetch?
- Maintenance and uniqueness costs?

Choose column order based on predicates and business goals, not merely to make an index prefixed.

## 6. Unique Indexes and the Partition Key

A critical design question is: how do you guarantee an ID cannot appear in two different partitions?

### 6.1. Local unique indexes must include the partition key

Suppose SALES is partitioned by SALE_DATE. If you create a local unique index on SALE_ID alone:

```sql
CREATE UNIQUE INDEX ux_sales_id_l
ON sales (sale_id)
LOCAL;
```

Oracle cannot guarantee SALE_ID is unique across the entire table using only local index partitions, because each index partition checks uniqueness only within its own partition. Two rows with the same SALE_ID could exist in two different table partitions.

Therefore, a local unique index on a partitioned table must include the full table partitioning key in the index key so uniqueness can be enforced per partition. Example:

```sql
CREATE UNIQUE INDEX ux_sales_date_id_l
ON sales (sale_date, sale_id)
LOCAL;
```

This index enforces uniqueness for the combination of SALE_DATE and SALE_ID. It does not guarantee SALE_ID alone is unique if the same SALE_ID appears on two different dates.

### 6.2. When a unique key must exclude the partition key

If business rules require SALE_ID to be unique table-wide, even if the same ID could fall into different date partitions, a suitable global unique index/constraint is needed:

```sql
CREATE UNIQUE INDEX ux_sales_id_g
ON sales (sale_id);
```

Then a constraint can be added using that index:

```sql
ALTER TABLE sales
ADD CONSTRAINT uq_sales_id
UNIQUE (sale_id)
USING INDEX ux_sales_id_g;
```

A global unique index can make partition maintenance operations heavier because the index must continue representing uniqueness across the entire table. This is a trade-off that must be factored into the design.

### 6.3. Global unique indexes and NULLs

Standard UNIQUE constraint NULL rules still apply. If an ID is mandatory, declare NOT NULL separately. Do not rely on uniqueness to enforce data presence.

### 6.4. Choosing a partition key affects constraints

When designing partitioning, weigh:

- Is the partition key part of the business key?
- Is table-wide uniqueness required on a column that excludes the partition key?
- Can a composite key of partition key and ID legitimately match business semantics?
- Is a global unique index acceptable for maintenance and availability?

Do not add the partition key to UNIQUE just to make a local unique index valid if doing so alters business meaning. If SALE_ID must be globally unique, UNIQUE(SALE_DATE, SALE_ID) is not a substitute for UNIQUE(SALE_ID).

## 7. Partition Pruning and Index Access

### 7.1. Partition pruning

Partition pruning is Oracle's elimination of unnecessary table partitions based on predicates and partition metadata. Example:

```sql
SELECT SUM(amount)
FROM sales
WHERE sale_date >= DATE '2026-03-01'
  AND sale_date <  DATE '2026-04-01';
```

If SALES is range-partitioned by SALE_DATE, Oracle can read only the March partition. Partition pruning operates independently of whether the table has local or global indexes.

### 7.2. Index partition pruning

With a local index, index partitions align with table partitions. When Oracle prunes table partitions, it can likewise access only the corresponding local index partitions.

With a global index, the index partitioning scheme is independent of table partitioning. Global index access can locate ROWIDs belonging to multiple table partitions; Oracle then accesses the table partitions containing those rows. Table partition pruning and global index partition pruning are two distinct mechanisms.

### 7.3. Queries without the partition key

```sql
SELECT sale_date, amount
FROM sales
WHERE sale_id = :sale_id;
```

If there is only a local index on SALE_ID, Oracle may need to access many local index partitions because it does not know the date partition. A global index on SALE_ID can locate the table-wide ROWID more directly.

If the query has both SALE_DATE and SALE_ID, a local index may need only one index partition:

```sql
SELECT sale_date, amount
FROM sales
WHERE sale_date = :sale_date
  AND sale_id = :sale_id;
```

### 7.4. Do not confuse partition pruning with index skip scan

Partition pruning eliminates table/index partitions based on the partition key. Index skip scan is a technique for accessing a composite B-tree index when the predicate omits the leading column in certain cases. The two techniques are different; do not assume skip scan substitutes for local/global design.

### 7.5. Reading the plan

In execution plans, you may encounter:

| Operation | Meaning |
| --- | --- |
| PARTITION RANGE SINGLE | Only one range partition is selected |
| PARTITION RANGE ITERATOR | Iterates over a selected set of partitions |
| PARTITION RANGE ALL | No pruning; accesses all range partitions |
| PARTITION LIST SINGLE | Selects one list partition |
| PARTITION HASH SINGLE | Selects one hash partition when conditions suffice |
| INDEX RANGE SCAN | Scans a range of index keys |
| INDEX UNIQUE SCAN | Looks up one unique key |
| TABLE ACCESS BY LOCAL INDEX ROWID | Accesses table via local index ROWID |

Specific operations depend on partition type, version, and optimizer transformations. Use DBMS_XPLAN to inspect PSTART/PSTOP and accessed partitions; with dynamic pruning, values may display as KEY or other runtime notations.

## 8. Creating Local and Global Indexes

### 8.1. Creating a local nonunique index

```sql
CREATE INDEX ix_sales_customer_l
ON sales (customer_id)
LOCAL;
```

Oracle creates index partitions corresponding to the table partitions.

### 8.2. Creating a local index with named index partitions

You can specify names and tablespaces for individual index partitions using CREATE INDEX PARTITION syntax:

```sql
CREATE INDEX ix_sales_date_customer_l
ON sales (sale_date, customer_id)
LOCAL (
    PARTITION pidx_2026_01 TABLESPACE idx_2026_01,
    PARTITION pidx_2026_02 TABLESPACE idx_2026_02,
    PARTITION pidx_2026_03 TABLESPACE idx_2026_03
);
```

The list of index partitions must match the table partition structure at creation time. Syntax and management for partitions added afterward must be verified against DDL and your running version. If separate naming/tablespaces are not needed, letting Oracle manage index partitions is usually simpler.

### 8.3. Creating a global nonpartitioned index

```sql
CREATE INDEX ix_sales_sale_id_g
ON sales (sale_id);
```

On a partitioned table, an index declaring neither LOCAL nor a global partitioning clause is a global nonpartitioned index.

### 8.4. Creating a global partitioned index

Hash-partitioned example:

```sql
CREATE INDEX ix_sales_customer_g
ON sales (customer_id)
GLOBAL PARTITION BY HASH (customer_id)
PARTITIONS 8;
```

Range-partitioned example:

```sql
CREATE INDEX ix_sales_id_range_g
ON sales (sale_id)
GLOBAL PARTITION BY RANGE (sale_id) (
    PARTITION gip_1 VALUES LESS THAN (1000000),
    PARTITION gip_2 VALUES LESS THAN (2000000),
    PARTITION gip_max VALUES LESS THAN (MAXVALUE)
);
```

The index partitioning key and boundaries here belong to the index, not the table's partitioning key SALE_DATE. Choose a scheme matching the index key distribution and queries.

### 8.5. Checking locality

```sql
SELECT
    index_name,
    locality,
    alignment,
    partitioning_type,
    partition_count
FROM user_part_indexes
WHERE table_name = 'SALES'
ORDER BY index_name;
```

USER_PART_INDEXES/ALL_PART_INDEXES/DBA_PART_INDEXES describe partitioned indexes and locality. Global nonpartitioned indexes lack index partition metadata like local/global partitioned indexes; also inspect USER_INDEXES.

## 9. Impact of Partition Maintenance Operations

After every DDL statement, determine:

1. Which table partitions were added, dropped, emptied, moved, or had boundaries changed?
2. How were the corresponding local index partitions maintained?
3. Do global indexes need entry/ROWID updates?
4. Could any index or index partition become UNUSABLE?
5. Are UPDATE INDEXES/UPDATE GLOBAL INDEXES, rebuilds, or statistics gathering required?

### 9.1. Overview table

| Operation | Local index | Global index |
| --- | --- | --- |
| ADD PARTITION | Creates/maintains corresponding index partition | Usually needs no changes to existing keys; verify per specific DDL |
| DROP PARTITION | Drops corresponding index partition | Must maintain global entries or handle index status |
| TRUNCATE PARTITION | Empties corresponding index partition | Must maintain global entries or handle index status |
| MOVE PARTITION | Can make local index partition UNUSABLE if index is not maintained | May need global index update/rebuild |
| SPLIT PARTITION | Local index partitions are split/maintained with the table | Global index requires maintenance depending on DDL options |
| MERGE PARTITIONS | Local index partitions are merged accordingly | Global index requires maintenance depending on DDL options |
| EXCHANGE PARTITION | Must handle staging table index and local index | Global index may need updating; check INCLUDING/UPDATE INDEXES |

This table is a guide, not a substitute for version-specific syntax documentation. Some operations feature asynchronous global index maintenance or differences between online and offline DDL. After running DDL, verify index status rather than assuming from DDL success alone.

## 10. DROP PARTITION and Global Indexes

### 10.1. DROP PARTITION

Example of dropping an old partition:

```sql
ALTER TABLE sales
DROP PARTITION p2025_01;
```

The table partition is removed. The corresponding local index partition is also removed/maintained under the local structure. Global indexes may need updating to remove ROWIDs pointing to the dropped partition.

### 10.2. Maintaining global indexes

In supported versions and cases, you can specify:

```sql
ALTER TABLE sales
DROP PARTITION p2025_01
UPDATE INDEXES;
```

Some documentation/versions or specific syntaxes use UPDATE GLOBAL INDEXES. Verify in the Oracle SQL Language Reference for your exact release. Index update options may perform global index maintenance synchronously during DDL or leverage the release's asynchronous maintenance mechanism.

If an index maintenance option is omitted in a case where Oracle does not auto-maintain it, global indexes or index partitions can transition to UNUSABLE. Queries using that index can no longer use that access path; depending on status and settings, subsequent DML may fail or require rebuilding first.

### 10.3. Asynchronous global index maintenance

Oracle Database 12c and later support asynchronous global index maintenance for certain DROP/TRUNCATE partition operations. Instead of deleting all index entries immediately, Oracle can mark metadata and defer cleanup of stale entries until an appropriate time. This shortens DDL duration, though it does not mean old index entries disappear instantly or never need cleanup.

Exact behavior depends on release, index type, operation, and clauses used. Do not assume every DROP PARTITION on every version automatically maintains global indexes. Check release documentation, post-DDL index status, and appropriate cleanup jobs.

### 10.4. When to use DROP PARTITION?

DROP PARTITION fits when removing an entire data range permanently, such as purging a month past retention. Compared to DELETEing millions of rows, partition DDL can be faster and generate less undo/redo for the removed data, while still requiring evaluation of:

- Foreign key constraints and dependencies.
- Global indexes.
- Materialized views and statistics.
- Backups/archiving/retention.
- DDL locking and operational windows.

DROP PARTITION is DDL with an implicit commit; it cannot be rolled back like an uncommitted DELETE.

## 11. TRUNCATE PARTITION

### 11.1. TRUNCATE vs. DROP

- DROP PARTITION removes the partition and its metadata from the table.
- TRUNCATE PARTITION keeps the partition in the table while deleting all rows inside it.

Example:

```sql
ALTER TABLE sales
TRUNCATE PARTITION p2026_01;
```

The corresponding local index partition is emptied along with the table partition. Global indexes must be maintained so entries pointing to truncated rows do not produce invalid results.

### 11.2. Maintaining indexes

Common syntax example:

```sql
ALTER TABLE sales
TRUNCATE PARTITION p2026_01
UPDATE INDEXES;
```

In other releases/syntaxes, documentation may specify UPDATE GLOBAL INDEXES. Oracle 12c and later support asynchronous global index maintenance for certain truncate/drop operations; options and behavior must be confirmed per release. If a global index is not maintained and becomes UNUSABLE, handle the index before relying on it.

### 11.3. When to use it?

TRUNCATE PARTITION is useful when you need to preserve the monthly/quarterly partition frame while emptying data, such as reloading a partition after a failed ETL run. Because it is DDL, the operation performs an implicit commit and cannot be rolled back like DELETE. Confirm data has been archived or can be reloaded before running.

## 12. MOVE PARTITION

### 12.1. Purpose

MOVE PARTITION relocates a table partition's segment, typically to change tablespaces, compress data, alter storage attributes, or reorganize the segment.

Example:

```sql
ALTER TABLE sales
MOVE PARTITION p2026_03
TABLESPACE sales_data_2026;
```

Moving a partition can change row ROWIDs. Indexes containing ROWIDs must be maintained or rebuilt; both the corresponding local index partition and global indexes must be considered.

### 12.2. Maintaining indexes during MOVE

A common syntax form:

```sql
ALTER TABLE sales
MOVE PARTITION p2026_03
TABLESPACE sales_data_2026
UPDATE INDEXES;
```

If an index maintenance option supported in your release is omitted, the corresponding local index partition or global indexes may become UNUSABLE. Exact impact depends on index type, version, and MOVE mode (online/offline, compression, tablespace, partition/subpartition).

### 12.3. Rebuilding a local index partition after MOVE

If an index partition becomes UNUSABLE, look up the index partition name and rebuild it:

```sql
ALTER INDEX ix_sales_customer_l
REBUILD PARTITION pidx_2026_03;
```

The index partition name can differ from the table partition name. Query USER_IND_PARTITIONS instead of assuming the names match.

### 12.4. MOVE and availability

MOVE PARTITION is DDL that may require metadata locks or impact access depending on the mode and release. When high availability is required, review supported ONLINE syntax, check restrictions with partition/index types, and test in a comparable environment. ONLINE does not mean zero locks or zero extra resource usage.

## 13. SPLIT PARTITION

### 13.1. Purpose

SPLIT PARTITION divides one partition into two new partitions. Commonly used when a MAXVALUE partition or large partition must be split along a new boundary.

For example, partition P_FUTURE currently holds dates from May onward. Splitting May out of the future partition:

```sql
ALTER TABLE sales
SPLIT PARTITION p_future
AT (DATE '2026-06-01')
INTO (
    PARTITION p2026_05,
    PARTITION p_future
);
```

Oracle distributes rows according to the partition bound. Local index partitions must also be split/maintained across the two new partitions.

### 13.2. Global indexes

SPLIT changes ROWIDs/partition placement for affected rows and may require global index maintenance. Example using the clause:

```sql
ALTER TABLE sales
SPLIT PARTITION p_future
AT (DATE '2026-06-01')
INTO (
    PARTITION p2026_05,
    PARTITION p_future
)
UPDATE INDEXES;
```

Clause availability and syntax depend on release and index types. Check global index status after splitting. On large tables, index maintenance work can be substantial and must be accounted for in the maintenance window.

### 13.3. Splitting partitions can be resource-intensive

Splitting may require reading/moving data within the partition, updating local index partitions, and maintaining global indexes. Do not treat split as a metadata-only operation in all cases. Check partition size, compression, tablespace, undo/redo, parallelism, and lock duration.

## 14. MERGE PARTITIONS

### 14.1. Purpose

MERGE PARTITIONS combines adjacent partitions into one new partition. Commonly used when many small partitions need consolidation or when changing data management granularity.

Example:

```sql
ALTER TABLE sales
MERGE PARTITIONS p2026_01, p2026_02
INTO PARTITION p2026_q1;
```

The two source partitions are replaced by the target partition. Corresponding local index partitions are merged alongside the table.

### 14.2. Maintaining global indexes

Example:

```sql
ALTER TABLE sales
MERGE PARTITIONS p2026_01, p2026_02
INTO PARTITION p2026_q1
UPDATE INDEXES;
```

Global indexes must be maintained according to the operation's and release's rules. Otherwise, global indexes or index partitions can become UNUSABLE. After MERGE, check index status and verify query plans.

### 14.3. Notes

- Partitions being merged must follow the partitioning method's rules; for range partitions, they must usually be adjacent.
- Confirm the target partition name does not already exist.
- Check tablespace, compression, and storage attributes of the new partition.
- Assess impact on local/global indexes and statistics.
- Verify data remains within valid bounds after merging.

## 15. EXCHANGE PARTITION

### 15.1. Concept

EXCHANGE PARTITION swaps the data segment of a table partition with a structurally compatible nonpartitioned table. This is a popular technique for loading large datasets into a data warehouse: load and validate data in staging first, then exchange into the target partition.

Example:

```sql
ALTER TABLE sales
EXCHANGE PARTITION p2026_04
WITH TABLE sales_stage;
```

After exchanging, the partition's prior data resides in the staging table, while the staging data resides in the partition. This metadata/segment swap is faster than row-by-row INSERTs in many scenarios, though compatibility rules and indexes still require handling.

### 15.2. Compatibility conditions

The staging table must have compatible column definitions, data types, and attributes matching the exchanged partition. Constraints, partition key values, and indexes must also be checked. With validation enabled, Oracle verifies staging rows satisfy the partition bound; with `WITHOUT VALIDATION`, ensuring data belongs to the partition falls on the ETL pipeline.

Do not use `WITHOUT VALIDATION` purely for speed unless an equivalent data check has already run. A row whose SALE_DATE lies outside the partition bound can corrupt logical integrity if exchanged without validation.

### 15.3. INCLUDING INDEXES

If you want to swap the local index partition with a corresponding index on the staging table, use `INCLUDING INDEXES` when index structures match:

```sql
ALTER TABLE sales
EXCHANGE PARTITION p2026_04
WITH TABLE sales_stage
INCLUDING INDEXES;
```

If corresponding indexes are not exchanged, the local index partition may require rebuilding or become UNUSABLE depending on conditions and clauses. The staging table must have structurally matching indexes for `INCLUDING INDEXES`.

### 15.4. UPDATE GLOBAL INDEXES

Global indexes reference rows across multiple table partitions. When exchanging a partition, global indexes must be updated to point to the correct ROWIDs. Example:

```sql
ALTER TABLE sales
EXCHANGE PARTITION p2026_04
WITH TABLE sales_stage
INCLUDING INDEXES
WITHOUT VALIDATION
UPDATE GLOBAL INDEXES;
```

This is a common pattern; syntax, asynchronous maintenance capabilities, and online support depend on release. Confirm in the Oracle SQL Language Reference before use.

### 15.5. ETL partition exchange workflow

A safe workflow typically follows:

1. Create/prepare a staging table compatible with the target partition.
2. Load data into staging.
3. Validate row counts, duplicates, NULLs, domains, and partition-key bounds.
4. Gather statistics on staging if required by the workflow.
5. Prepare matching indexes if using `INCLUDING INDEXES`.
6. Exchange the partition with appropriate validation/index options.
7. Check local/global index status.
8. Verify row counts and representative queries on the new partition.
9. Archive old data now in staging per retention policy, or truncate staging after confirmation.

EXCHANGE PARTITION is DDL and performs an implicit commit. Have a rollback/reverse-exchange plan in case verification fails; standard `ROLLBACK` cannot undo DDL.

## 16. Checking and Recovering UNUSABLE Indexes

### 16.1. Why can an index become UNUSABLE?

Certain partition maintenance operations can mark an index or index partition as UNUSABLE if Oracle does not maintain the index in the requested/supported manner. Common scenarios include:

- MOVE PARTITION without an appropriate index maintenance option.
- SPLIT/MERGE or EXCHANGE changing ROWIDs/partition contents without updating global indexes.
- Loads or partition operations run with options that leave index partitions unusable.
- An index partition manually marked unusable or a DDL failure mid-maintenance.

An UNUSABLE index is no longer a valid access path for the optimizer. Certain DML operations may raise errors if they must maintain an unusable index, depending on index type and settings. Do not ignore this state just because SELECT queries can still fall back to full table scans.

### 16.2. Checking USER_INDEXES

```sql
SELECT
    index_name,
    table_name,
    status,
    visibility,
    partitioned,
    uniqueness
FROM user_indexes
WHERE table_name = 'SALES'
ORDER BY index_name;
```

`USER_INDEXES` gives the overall status for indexes. For partitioned indexes, check individual index partitions; the overall status may not reveal exactly which partition needs rebuilding.

### 16.3. Checking USER_IND_PARTITIONS

```sql
SELECT
    index_name,
    partition_name,
    status,
    tablespace_name
FROM user_ind_partitions
WHERE index_name IN (
    SELECT index_name
    FROM user_indexes
    WHERE table_name = 'SALES'
)
ORDER BY index_name, partition_position;
```

For subpartitioned indexes, inspect `USER_IND_SUBPARTITIONS`/`ALL_IND_SUBPARTITIONS` to check each subpartition. Use `ALL_` or `DBA_` views when broader scope is needed and privileges allow.

### 16.4. Rebuilding a local index partition

```sql
ALTER INDEX ix_sales_customer_l
REBUILD PARTITION pidx_2026_03;
```

Rebuilds only the specified partition. `pidx_2026_03` is an example; retrieve the exact name from `USER_IND_PARTITIONS`.

### 16.5. Rebuilding a global index partition

For a global partitioned index:

```sql
ALTER INDEX ix_sales_customer_g
REBUILD PARTITION sys_p123;
```

Retrieve the partition name from the dictionary. Global partitioned index partitions do not necessarily share names with table partitions.

### 16.6. Rebuilding a global nonpartitioned index

```sql
ALTER INDEX ix_sales_sale_id_g
REBUILD;
```

This rebuilds the entire global nonpartitioned index. For large indexes, the operation can require substantial I/O and temporary space; schedule accordingly.

### 16.7. Rebuilding does not replace root-cause investigation

Before rebuilding, determine:

- Which index is unusable: local, global partitioned, or global nonpartitioned?
- Which partitions/subpartitions are affected?
- Which DDL rendered the index unusable?
- Can the index be maintained via clauses on the next run?
- How much tablespace, TEMP, redo, and time will the rebuild need?
- Must statistics be gathered after rebuilding?

If the next partition operation renders the index unusable again, merely rebuilding treats only the symptom. Fix the DDL/ETL process.

## 17. Statistics and Execution Plans After Partition Maintenance

### 17.1. Why are statistics needed?

Partition maintenance can alter row counts, data distribution, and skew within partitions. The optimizer needs accurate statistics to estimate cardinality and select access paths.

After a load, exchange, split, merge, truncate, or drop, determine which statistics need updating:

- Table-level statistics.
- Partition-level statistics.
- Index statistics.
- Global statistics or synopses when using incremental statistics.

Not every DDL operation requires an immediate full-table gather. For very large tables, use incremental statistics and partition-level gathering per DBA design.

### 17.2. Gathering statistics for a single partition

Example:

```sql
BEGIN
    DBMS_STATS.GATHER_TABLE_STATS(
        ownname          => USER,
        tabname          => 'SALES',
        partname         => 'P2026_03',
        estimate_percent => DBMS_STATS.AUTO_SAMPLE_SIZE,
        cascade          => TRUE
    );
END;
/
```

`CASCADE` can gather statistics on related indexes as supported by `DBMS_STATS`. In production, follow existing stats policies; do not trigger a full-table re-gather when only one partition changed if incremental statistics are configured.

### 17.3. Checking the execution plan

```sql
EXPLAIN PLAN FOR
SELECT SUM(amount)
FROM sales
WHERE sale_date >= DATE '2026-03-01'
  AND sale_date <  DATE '2026-04-01'
  AND customer_id = 1001;

SELECT *
FROM TABLE(DBMS_XPLAN.DISPLAY);
```

Check:

- Whether PSTART/PSTOP indicate selected partitions or all partitions.
- Whether the access path uses a local or global index.
- Whether E-Rows match actual distribution.
- Whether there is a full scan or table access by ROWID.
- Whether the plan changed after maintenance/statistics.

### 17.4. Inspecting actual rows

In a test environment:

```sql
SELECT /*+ GATHER_PLAN_STATISTICS */
       SUM(amount)
FROM sales
WHERE sale_date >= DATE '2026-03-01'
  AND sale_date <  DATE '2026-04-01'
  AND customer_id = 1001;

SELECT *
FROM TABLE(
    DBMS_XPLAN.DISPLAY_CURSOR(
        NULL,
        NULL,
        'ALLSTATS LAST +PARTITION'
    )
);
```

Actual row-source statistics allow comparing E-Rows against A-Rows. If estimates diverge sharply, examine histograms, column correlations, partition stats, and bind peeking/adaptive behavior per version. Do not draw conclusions for an entire workload from a single run.

To keep the example simple, the table does not declare a primary key. If you want `SALE_ID` unique table-wide, add a global unique index/constraint after loading data; if uniqueness is only per date, use a composite key per business rules.

### 18.2. Load data

```sql
INSERT INTO lab_sales_part (
    sale_id, sale_date, customer_id, channel, amount

SELECT
    LEVEL,
    DATE '2026-01-01' + MOD(LEVEL, 90),
    MOD(LEVEL, 1000) + 1,
    CASE MOD(LEVEL, 3)
        WHEN 0 THEN 'WEB'
        WHEN 1 THEN 'STORE'
        ELSE 'PARTNER'
    END,
    MOD(LEVEL * 19, 50000) / 100
FROM dual
CONNECT BY LEVEL <= 100000;

COMMIT;
```

Data is distributed across the January–March partitions. Partition `P_FUTURE` may remain empty.

### 18.3. Create a local index

```sql
CREATE INDEX ix_lsp_customer_local
```

The index is local prefixed because `SALE_DATE` is the partition key and leads the index key.

```sql
CREATE INDEX ix_lsp_sale_global
```

### 18.5. Check locality and partition status

## 19. Common Errors and Pitfalls

| Symptom | Possible Cause | Resolution |
| --- | --- | --- |
| Local unique index rejected | Unique key lacks partition key | Include full partition key in local unique key or use global unique index |
| Lookup by ID scans many index partitions | Query lacks partition key and index is local | Consider global index or add partition key predicate |
| Index partition UNUSABLE after MOVE | MOVE did not maintain indexes or used unsuitable options | Rebuild partition or rerun DDL with release-appropriate clause |
| Global index UNUSABLE after DROP/TRUNCATE | Global index not maintained per release mechanism | Use `UPDATE INDEXES`/`UPDATE GLOBAL INDEXES` or rebuild |
| EXCHANGE makes local index partition unusable | Staging index does not match or lacks `INCLUDING INDEXES` | Prepare staging index and verify exchange clauses |
| Query reads too many partitions | Predicate prevents pruning or applies function on partition key | Write sargable predicates, check implicit conversion and plan |
| Plan does not use local index | Full scan is cheaper or stats/selectivity differ from expectations | Compare cost, E-Rows/A-Rows, clustering, and workload |
| Global index maintenance prolongs DDL | Large index with many entries to update | Schedule, use async mechanism if release supports it, benchmark, and monitor cleanup |
| Local index partition name mismatches table partition | Index partition names managed independently by Oracle/DDL | Query `USER_IND_PARTITIONS` |
| Overall index status is misleading | Partitioned index tracks status per partition | Check `USER_IND_PARTITIONS`/`USER_IND_SUBPARTITIONS` |
| Query plan changes after ETL | Stale statistics or new data distribution | Gather partition/global stats per policy |
| Global unique constraint complicates purging | Table-wide uniqueness requires global index | Factor maintenance cost into partition key and constraint design |

## 20. Best Practices

1. **Design partitions and indexes together.** The partition key affects pruning, local uniqueness, and maintenance cost.
2. **Use local indexes for partition-based data lifecycles.** They generally keep DROP/TRUNCATE/EXCHANGE localized.
3. **Use global indexes when table-wide lookups are genuinely required.** Especially when queries omit the partition key.
4. **Do not use local unique indexes to fake global uniqueness.** A local key must contain the partition key; if a business key is globally unique, use an appropriate solution.
5. **Distinguish local prefixed and nonprefixed.** Column order affects access paths and how many index partitions must be probed.
6. **Check the impact of each DDL operation.** DROP, TRUNCATE, MOVE, SPLIT, MERGE, and EXCHANGE do not have identical index impacts.
7. **Use UPDATE INDEXES/UPDATE GLOBAL INDEXES for your exact release.** Do not rely on syntax from another version.
8. **Verify index status after maintenance.** Inspect both index-level and partition/subpartition-level status.
9. **Rebuild at the right scope.** Rebuild only affected partitions if sufficient; avoid unnecessary full-index rebuilds.
10. **Manage global index maintenance as part of ETL.** Account for I/O, redo, DDL duration, and availability.
11. **Validate staging before EXCHANGE.** Never skip validation without an equivalent partition-bound check step.
12. **Update statistics per partition.** Use incremental stats if your architecture and version support them.
13. **Check PSTART/PSTOP and actual rows.** Confirm partition pruning is actually taking place.
14. **Test DDL in a comparable environment.** DDL performs an implicit commit and can affect data/availability.

## 22. Mental Model

```text
PARTITIONED TABLE
       |
       +-----------------------------+
       |                             |
       v                             v
   LOCAL INDEX                   GLOBAL INDEX
   Aligned with table partitions Spans multiple table partitions
       |                             |
       v                             v
   Each table partition          Nonpartitioned or
   has a matching index part     partitioned with its own scheme
       |                             |
       v                             v
   Easy local maintenance        Convenient table-wide lookups
   Fits partition lifecycle      But partition DDL must maintain
                                 global entries

PARTITION MAINTENANCE
  ADD / DROP / TRUNCATE / MOVE
  SPLIT / MERGE / EXCHANGE
       |
       v
  Check local index partitions
  Check global index status
  UPDATE INDEXES where appropriate
  REBUILD if UNUSABLE
  GATHER STATS and verify plan
```

**Key takeaway:** local indexes follow the lifecycle of individual table partitions; global indexes serve queries across multiple partitions but cause certain partition maintenance operations to require extra update or rebuild work. Choose the index type based on predicates, partition key, and uniqueness requirements; after every DDL operation, check index status, partition pruning, and execution plans before concluding the system is ready.
