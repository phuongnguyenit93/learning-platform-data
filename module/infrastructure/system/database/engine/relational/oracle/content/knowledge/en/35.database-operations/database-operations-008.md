# ADR, Alert Logs, Trace Files, and Using ADRCI

Oracle Database stores diagnostic information in the **Automatic Diagnostic Repository (ADR)**. ADR is a directory-based storage structure that centralizes alert logs, trace files, incidents, dumps, health-check outputs, and data used for incident analysis. DBAs can use SQL views to query certain details, use OS tools to read files when appropriate, or use **ADRCI (ADR Command Interpreter)** to manage and package diagnostic data.

Three components to distinguish:

- **Alert log:** a chronological log of significant database or instance events, such as startup/shutdown, critical errors, checkpoints, archive logs, and operational warnings.
- **Trace file:** detailed files generated by an Oracle process, session, or diagnostic component; may contain call stacks, error stacks, waits, SQL traces, binds, and internal information depending on the trace type.
- **ADRCI:** a command-line utility for exploring ADR homes, viewing alerts, listing problems/incidents, creating incident packages, and managing retention/purging.

When a database encounters an error, the workflow usually begins by identifying the right instance and incident time, reading the alert log to locate landmarks, pulling the corresponding trace files, and then using ADRCI/IPS to generate a diagnostic package if needed for Oracle Support. Collection must be controlled because traces and dumps can contain SQL text, bind values, usernames, paths, and sensitive data.

## 1. What Is ADR?

### 1.1. Purpose

The Automatic Diagnostic Repository is where Oracle stores diagnostic data in a unified structure. ADR was introduced to replace earlier scattered storage methods and supports:

- Recording critical events and errors.
- Storing trace files by database, instance, listener, and other components.
- Managing incidents and problems.
- Running Health Monitor/diagnostic workflows.
- Packaging incident-related data for analysis.
- Applying retention policies and purging old data.

ADR is not a database backup repository and does not replace RMAN. Traces, alert logs, dumps, and incident packages support diagnostics; they do not restore datafiles or redo.

### 1.2. ADR Base and ADR Home

- **ADR base:** the root directory containing one or more ADR homes.
- **ADR home:** the diagnostic area for a specific database instance or Oracle component.

Example structure on Linux:

§§§text
/u01/app/oracle/diag/
    rdbms/
        orcl/
            orcl/
                alert/
                trace/
                incident/
                cdump/
                hm/
                metadata/
    tnslsnr/
        dbhost01/
            listener/
                alert/
                trace/
                incident/
§§§

Actual paths depend on ADR base, DB_UNIQUE_NAME, instance name, Oracle Home, and platform. Do not assume the database home always resides under /u01/app/oracle or that all systems use the same directory names.

### 1.3. Common Directories

| Directory | Contents |
|---|---|
| alert | Alert log, typically in XML and corresponding text formats |
| trace | Trace files, process traces, and certain diagnostic files |
| incident | Incident dumps and metadata |
| cdump | Core dumps if any |
| hm | Health Monitor output |
| metadata | Metadata supporting ADR |
| sweep | Internal management/diagnostic data depending on version |

Do not manually delete files directly inside ADR directories to free disk space. Use ADRCI purge or Oracle-supported management mechanisms to avoid deleting referenced data by mistake.

### 1.4. ADR Homes for Multiple Components

A host can have multiple ADR homes:

- Database instance.
- Listener.
- ASM instance.
- Oracle Clusterware.
- Certain clients or other Oracle components depending on configuration.

Connection errors may reside in the listener ADR home rather than the database ADR home. When investigating, select the right component and home.

## 2. Identifying ADR Base, ADR Home, and Diagnostic Paths

### 2.1. V$DIAG_INFO

Inside the database, the V$DIAG_INFO view is the starting point for locating diagnostic paths:

§§§sql
SELECT name, value
FROM v$diag_info
ORDER BY name;
§§§

Common names:

| NAME | Meaning |
|---|---|
| Diag Enabled | Whether ADR is enabled |
| ADR Base | ADR root directory |
| ADR Home | ADR home of the current instance |
| Diag Trace | Trace directory |
| Diag Alert | Alert log location |
| Diag Incident | Incident directory |
| Diag Cdump | Core dump location |
| Health Monitor | Health Monitor data location |
| Default Trace File | Default trace file of the current session |

Specific names and values may vary by version or instance type.

### 2.2. Getting the Current Trace File Path

§§§sql
SELECT value
FROM v$diag_info
WHERE name = 'Default Trace File';
§§§

This path is useful when identifying the default trace file for the session running the SQL query. Not all traces are written to the default trace file; process traces, incident dumps, and SQL traces may create separate files.

### 2.3. Viewing the ADR Home

§§§sql
SELECT value
FROM v$diag_info
WHERE name = 'ADR Home';
§§§

This path serves as the reference when running ADRCI and selecting the right home. In RAC, each instance has its own ADR home named after the instance.

### 2.4. Checking via Parameters

Related parameters:

§§§sql
SHOW PARAMETER diagnostic_dest;
SHOW PARAMETER db_unique_name;
SHOW PARAMETER instance_name;
§§§

DIAGNOSTIC_DEST sets the root location for diagnostic data in corresponding ADR configurations. Oracle can derive ADR base using platform rules if the parameter is not explicitly set.

### 2.5. Database and Listener Have Different ADR Homes

If a client cannot connect, check the listener log. The database alert log only records events once requests reach the database or involve a database process. The listener has its own ADR home and can be accessed via ADRCI:

§§§text
diag/tnslsnr/<host_name>/<listener_name>
§§§

Replace host_name and listener_name with actual host values.

## 3. Alert Log

### 3.1. Role

The alert log is the single most important log for tracking database/instance-level events. It typically records:

- Startup, mount, open, and shutdown.
- Database state changes.
- Checkpoints and redo/archive activity.
- Datafile, control file, and tablespace events.
- Critical ORA errors.
- Created incidents/problems.
- Warnings regarding memory, processes, recovery, and background processes.

The alert log is not a SQL audit log. It does not record every SQL statement executed by users.

### 3.2. XML and Text Alert Logs

In ADR, Oracle stores the alert log in XML format; many versions also maintain a text-formatted alert log for convenient DBA reading. Filenames and paths typically live under the alert directory inside the ADR home.

The XML format includes structured timestamps, components, message types/levels, and message text. The text alert log is easy to skim quickly with an editor or tail command. When structured querying or filtering is needed, use diagnostic views or ADRCI.

### 3.3. Viewing the Alert Log with ADRCI

Launch the tool:

§§§text
adrci
§§§

List ADR homes:

§§§text
adrci> show homes
§§§

Select the database home:

§§§text
adrci> set home diag/rdbms/orcl/orcl
§§§

View alerts:

§§§text
adrci> show alert
§§§

The home name above is only an example. Use the exact path shown by show homes.

### 3.4. Viewing the Most Recent Lines

§§§text
adrci> show alert -tail 100
§§§

Continuous monitoring:

§§§text
adrci> show alert -tail -f
§§§

Depending on the ADRCI release, option syntax may differ slightly; use help show alert to see the syntax supported by your installed version.

### 3.5. Querying the XML Alert Log via View

Some releases provide V$DIAG_ALERT_EXT for querying the alert log:

§§§sql
SELECT originating_timestamp,
       message_type,
       message_level,
       message_text,
       problem_key
FROM v$diag_alert_ext
WHERE originating_timestamp >=
      SYSTIMESTAMP - INTERVAL '1' DAY
ORDER BY originating_timestamp DESC;
§§§

This view is useful for filtering by time, message type, problem key, or text. Exact columns may vary by release; run DESC V$DIAG_ALERT_EXT in your database.

### 3.6. Searching for ORA Errors

Example searching for messages containing ORA codes:

§§§sql
SELECT originating_timestamp,
       message_text
FROM v$diag_alert_ext
WHERE originating_timestamp >=
      SYSTIMESTAMP - INTERVAL '6' HOUR
  AND message_text LIKE '%ORA-%'
ORDER BY originating_timestamp;
§§§

Do not search solely for the ORA string. Check surrounding messages before and after to identify the root cause, as the final ORA may only be a downstream symptom.

### 3.7. Reading Chronologically

During an incident, establish:

1. When user impact began.
2. The first abnormal event in the alert log.
3. Subsequent warnings/errors.
4. How instance/database state changed.
5. Whether any incident or trace file was generated at that time.

Align timezones across the alert log, application logs, OS logs, and monitoring before comparing. Some timestamps are displayed in different timezones.

## 4. Trace Files

### 4.1. What Is a Trace File?

A trace file contains diagnostic details generated by an Oracle process, session, or component. Traces can include:

- Error stacks and call stacks.
- Process/session state.
- Wait events and timing information.
- SQL text and execution details.
- Bind values if the trace level collects them.
- Heap dumps, system state dumps, or process state dumps.
- Details on deadlocks, latches, enqueues, or internal errors.

Traces do not have a single uniform format across all types. Some traces are readable in a text editor; large dumps require specialized tools or Oracle Support for interpretation.

### 4.2. Session Trace Files

Path to a session's default trace file:

§§§sql
SELECT value
FROM v$diag_info
WHERE name = 'Default Trace File';
§§§

You can set a tracefile identifier to make subsequently generated files easy to spot:

§§§sql
ALTER SESSION SET tracefile_identifier = 'ORDER_API_DEBUG';
§§§

The identifier is appended to the trace filename per Oracle naming rules. Keep the name short and free of sensitive data.

### 4.3. Background Process Trace Files

Background processes such as DBWn, LGWR, SMON, PMON, or others may write dedicated traces when errors or diagnostic events occur. Not every background process generates traces continuously.

When the alert log points to a process name and trace file path, open that exact file rather than looking only at the DBA session's default trace.

### 4.4. Trace Files and Incident Dumps

Incidents usually have dedicated dumps inside the ADR incident directory. Trace files may reference the incident or dump. Do not delete files inside the incident directory via filesystem commands, as doing so can break package integrity or destroy evidence.

### 4.5. Oversized Trace Files

SQL traces or event traces can grow very rapidly under heavy workloads. Before enabling tracing:

- Limit scope to a specific session/user/module and time window.
- Verify the output location and available free space.
- Establish a clear stop time to disable tracing.
- Avoid enabling high trace levels instance-wide unless necessary.
- Protect files because they may contain SQL/bind data.

## 5. SQL Tracing for Sessions and Workloads

### 5.1. Purpose of SQL Trace

SQL trace records parse, execute, fetch calls, and related waits. When formatted with TKPROF, DBAs can inspect:

- Parse/execute/fetch counts.
- CPU and elapsed time.
- Logical reads and physical reads.
- Rows processed.
- Wait events and wait time.
- Execution plans depending on configuration and trace data.

SQL trace helps distinguish CPU-bound queries from I/O waits, lock waits, or excessive parse/fetch calls.

### 5.2. Enabling Trace for the Current Session

You can use DBMS_SESSION:

§§§sql
BEGIN
    DBMS_SESSION.SESSION_TRACE_ENABLE(
        waits     => TRUE,
        binds     => FALSE,
        plan_stat => 'ALL_EXECUTIONS'
    );
END;
/
§§§

Supported signatures depend on the Oracle release. If an overload lacks plan_stat, use the overload provided in the package specification. Enable binds only when necessary and after assessing data exposure risk.

Disable trace:

§§§sql
BEGIN
    DBMS_SESSION.SESSION_TRACE_DISABLE;
END;
/
§§§

Always include an explicit step to disable trace; closing the session is not deliberate trace management.

### 5.3. Using ALTER SESSION

In some environments, SQL trace can be enabled with:

§§§sql
ALTER SESSION SET sql_trace = TRUE;
§§§

Disable:

§§§sql
ALTER SESSION SET sql_trace = FALSE;
§§§

DBMS_SESSION or DBMS_MONITOR is usually more flexible when controlling waits/binds and tracing other sessions.

### 5.4. Tracing Another Session by SID/SERIAL#

DBAs can enable trace for another session using DBMS_MONITOR:

§§§sql
BEGIN
    DBMS_MONITOR.SESSION_TRACE_ENABLE(
        session_id => 123,
        serial_num => 456,
        waits      => TRUE,
        binds      => FALSE
    );
END;
/
§§§

SID and SERIAL# must be retrieved from V$SESSION when enabling trace. Combine both to avoid targeting the wrong session, since SIDs can be reused. In RAC, identify the corresponding instance/session and use cluster-appropriate APIs/views.

Disable trace:

§§§sql
BEGIN
    DBMS_MONITOR.SESSION_TRACE_DISABLE(
        session_id => 123,
        serial_num => 456
    );
END;
/
§§§

### 5.5. Tracing by Client Identifier

Applications can set CLIENT_IDENTIFIER using DBMS_SESSION.SET_IDENTIFIER. DBAs can enable trace by client ID:

§§§sql
BEGIN
    DBMS_MONITOR.CLIENT_ID_TRACE_ENABLE(
        client_id => 'APP_USER_1001',
        waits     => TRUE,
        binds     => FALSE
    );
END;
/
§§§

Disable:

§§§sql
BEGIN
    DBMS_MONITOR.CLIENT_ID_TRACE_DISABLE(
        client_id => 'APP_USER_1001'
    );
END;
/
§§§

This method is useful with connection pools because one end user may be served by multiple database sessions. CLIENT_IDENTIFIER must be set accurately by the application and cleared when connections are returned to the pool.

### 5.6. Tracing by Service/Module/Action

DBMS_MONITOR can enable trace by service, module, and action:

§§§sql
BEGIN
    DBMS_MONITOR.SERV_MOD_ACT_TRACE_ENABLE(
        service_name => 'ORDER_SERVICE',
        module_name  => 'ORDER_API',
        action_name  => 'CREATE_ORDER',
        waits        => TRUE,
        binds        => FALSE
    );
END;
/
§§§

Disable:

§§§sql
BEGIN
    DBMS_MONITOR.SERV_MOD_ACT_TRACE_DISABLE(
        service_name => 'ORDER_SERVICE',
        module_name  => 'ORDER_API',
        action_name  => 'CREATE_ORDER'
    );
END;
/
§§§

Module/action values are typically set by the application via DBMS_APPLICATION_INFO.SET_MODULE. Verify exact runtime service/module/action names before enabling trace.

### 5.7. Tracing Broad Database Clients

Tracing by service/module/action or client ID can affect many sessions. Estimate the number of matching sessions and trace volume before enabling in production.

## 6. TKPROF and SQL Trace Analysis

### 6.1. What Is TKPROF?

TKPROF is an Oracle-provided utility that formats raw SQL trace files into readable reports. It aggregates parse/execute/fetch counts, CPU, elapsed time, logical/physical I/O, rows, and wait statistics per cursor.

### 6.2. Example Running TKPROF

On a host with Oracle client/database tools:

§§§text
tkprof input.trc output.prf sys=no sort=exeela,fchela
§§§

Replace trace and output paths with actual filenames. Depending on version, available sort and report options may vary.

### 6.3. Reading Report Sections

- Parse: parse overhead and parse count.
- Execute: time/CPU/I/O during execution.
- Fetch: cost of retrieving rows back to the client.
- Rows: number of rows processed at each phase.
- Misses/library cache: indicators of hard parsing or cursor reuse.
- Waits: wait time per event if wait tracing was enabled.

A SELECT statement may have a fast execute phase but a very slow fetch phase because the client retrieves many rows or consumes them slowly. Never look solely at execute time.

### 6.4. EXPLAIN in TKPROF

TKPROF accepts an EXPLAIN option to generate plans under a given account/schema. Those plans are re-explained in the explain environment and may differ from the actual cursor plan used during the trace. When actual runtime plans are needed, check SQL_ID/child cursor using DBMS_XPLAN.DISPLAY_CURSOR.

### 6.5. Traces with Bind Values

Bind traces can capture user values, tokens, emails, account numbers, or business data. Enable binds only when truly needed, restrict duration, and safeguard files/reports. Before sharing traces, verify security policies and redaction procedures.

## 7. Incidents and Problems in ADR

### 7.1. Problem

A problem is a class of error or critical issue identified by Oracle using a problem key/signature. Multiple occurrences of the same error type can be linked to the same problem.

### 7.2. Incident

An incident is a specific occurrence of a problem. A single problem can have multiple incidents, each with its own timestamp and associated dumps/traces.

For example, a recurring internal ORA error may generate one problem key and multiple incidents. Grouping them prevents DBAs from treating every dump as an unrelated issue.

### 7.3. Incident Flood Control

Oracle may cap the number of incident dumps created for a single problem within a time window to avoid filling disk when an error repeats continuously. Consequently, not every error occurrence creates a new incident dump.

### 7.4. ADRCI show problem

§§§text
adrci> show problem
§§§

Lists problems in the current ADR home. Select the right home before running.

### 7.5. ADRCI show incident

§§§text
adrci> show incident
§§§

Output can be filtered by problem or time range using options supported by your ADRCI release. Run help show incident to inspect syntax.

### 7.6. Incident Details

Incident details may include:

- Incident ID.
- Problem ID/key.
- Creation time.
- Incident status.
- File paths for dumps/traces.
- Related component and process.

Use the incident ID to build packages and reference diagnostic data with Oracle Support.

## 8. ADRCI Basics

### 8.1. Starting ADRCI

From the operating system shell:

§§§text
adrci
§§§

ADRCI is a command-line interpreter. It is not SQL*Plus and does not accept raw SQL syntax directly. Commands use prefixes like show, set, ips, purge, or help.

### 8.2. Listing Homes

§§§text
adrci> show homes
§§§

Output may list multiple homes for databases, listeners, ASM, or other components.

### 8.3. Selecting a Home

§§§text
adrci> set home diag/rdbms/orcl/orcl
§§§

If multiple homes exist, select the exact database/instance or listener under investigation. Subsequent show commands operate within the selected home.

### 8.4. Viewing Alerts

§§§text
adrci> show alert
adrci> show alert -tail 100
adrci> show alert -tail -f
§§§

show alert -tail -f is useful when watching startup or reproducing errors. Stop tailing using your terminal's standard interrupt key sequence.

### 8.5. Viewing Trace Files

§§§text
adrci> show tracefile
§§§

Lists trace files inside the ADR home. Use filter/sort options if supported by your release, or check help show tracefile.

### 8.6. Viewing Problems and Incidents

§§§text
adrci> show problem
adrci> show incident
§§§

Once an incident is found, record its ID and timestamp to correlate with the alert log, trace files, and monitoring.

### 8.7. Help

§§§text
adrci> help
adrci> help show alert
adrci> help ips
adrci> help purge
§§§

ADRCI syntax can vary slightly across Oracle Homes/versions. Running help on the target host itself is the closest authoritative syntax reference.

## 9. Incident Packaging Service (IPS)

### 9.1. Why Package Incidents?

When opening a service request with Oracle Support, you typically need to supply traces, dumps, alert logs, and relevant metadata. IPS bundles the required files into a structured incident package, reducing manual searching and copying.

### 9.2. Creating a Package by Problem

Example in ADRCI:

§§§text
adrci> ips create package problem 1
§§§

The number 1 is an illustrative problem ID. Replace it with the actual problem ID from show problem.

### 9.3. Creating a Package by Incident

§§§text
adrci> ips create package incident 12345
§§§

Replace 12345 with the actual incident ID. Packaging by incident focuses on one specific occurrence; packaging by problem can bundle multiple related incidents as required.

### 9.4. Viewing Packages

§§§text
adrci> ips show package
§§§

Note the returned package ID. You can update the package, add incidents, or attach additional files using IPS commands per your needs and release syntax.

### 9.5. Generating a Package

§§§text
adrci> ips generate package 7 in /u01/support
§§§

The number 7 is an example package ID. The target directory must exist and be writable. ADRCI generates a package/archive file ready to transfer to support.

### 9.6. Packaging by Time Range

When no clear incident ID exists, you can create a package by time interval or by file/problem depending on supported IPS commands. Check help ips create package and help ips add in your running version.

### 9.7. Inspecting Contents Before Sending

Packages may contain SQL text, bind values, schema/object names, hostnames, paths, usernames, or sensitive data. Before transferring externally:

- Verify the exact scope of files included in the package.
- Check organizational data-handling and security policies.
- Use approved Oracle Support upload channels.
- Do not send packages via public email/chat without authorization.
- Retain the package ID, creation timestamp, and service request reference.

## 10. ADRCI Purge and Retention Policy

### 10.1. Why Is Retention Needed?

Traces, incident dumps, and alert logs grow over time. ADR uses retention policies to determine how long diagnostic data is kept before becoming eligible for purging.

Purging too early can destroy forensic evidence; keeping data indefinitely can fill filesystems and disrupt the database/Oracle Home.

### 10.2. Viewing Retention Policy

In ADRCI:

§§§text
adrci> show control
§§§

Output contains ADR control and retention attributes. Field names, units, and contents may vary by release.

### 10.3. Purging by Data Age

ADRCI purge typically accepts age in minutes and a data type:

§§§text
adrci> purge -age 10080 -type TRACE
§§§

For example, 10080 minutes equals 7 days. Execute only after verifying the data type, home, and retention policy. Do not treat this example as a default production command.

### 10.4. Purging Different Data Types

Depending on version, ADRCI supports purging types such as TRACE, ALERT, INCIDENT, CDUMP, or HM. Run help purge to confirm valid types for the current home.

### 10.5. Do Not Purge with Filesystem Wildcards

Do not run recursive OS delete commands directly against trace/incident directories to clean ADR. Manual deletion can corrupt metadata, break incident/package links, or remove files held open by active processes.

### 10.6. Retention and Incidents

Incidents may need to be kept longer than routine traces while under investigation or awaiting Oracle Support. Before purging, confirm the service request has received the package and the data is no longer needed. Consider exporting/packaging prior to cleanup.

### 10.7. Monitoring Disk Space

Monitor ADR base and individual ADR home disk usage, trace growth rate, incident floods, and free filesystem space. Alert early before the filesystem fills up; do not wait until the database cannot write traces or the alert log.

## 11. Health Monitor and Diagnostic Data

### 11.1. Health Monitor

Oracle Health Monitor can run checks to diagnose database/file/component issues. Results are stored in ADR and can be viewed through appropriate views/packages.

### 11.2. When to Use It?

Health Monitor is helpful when investigating corruption, block/datafile issues, or certain database structural problems. Select checks suited to the symptoms and Oracle documentation; do not run arbitrary checks on production without understanding their impact.

### 11.3. ADRCI and HM

ADRCI can display Health Monitor details in supported releases. Run help show hm_run or the corresponding command to view runs and results.

### 11.4. Health Monitor Does Not Replace Backup Validation

Health checks help detect issues, but they do not replace RMAN backup validation, restore tests, or disaster recovery procedures. Diagnostic output does not repair corruption on its own.

## 12. Structured Incident Investigation Workflow

### Step 1 — Define Scope

Record the database, DB_UNIQUE_NAME, instance, host, container/PDB, service, and incident timestamp. If connections fail to reach the database, inspect the listener ADR home.

### Step 2 — Locate the ADR Home

Inside the database, query V$DIAG_INFO. If the database cannot open, determine ADR base/home from Oracle Home, configuration, and ADRCI show homes.

### Step 3 — Read the Alert Log

Inspect around the incident start time. Look for ORA errors, process names, incident IDs, file paths, startup/shutdown events, and preceding/subsequent messages.

### Step 4 — Retrieve the Right Trace

If the alert log points to a trace path, open that exact file. If session tracing is required, capture SID/SERIAL# or client/module/action and enable scoped tracing.

### Step 5 — Correlate Incidents/Problems

Use ADRCI show problem and show incident. Cross-reference problem keys, incident IDs, and timestamps with the alert log.

### Step 6 — Analyze SQL Trace If Needed

Run TKPROF on raw SQL traces to inspect parse/execute/fetch, CPU, I/O, and waits. Cross-check with DBMS_XPLAN or SQL Monitor if actual plan/runtime details are needed.

### Step 7 — Build an Incident Package

Use IPS to create a package by incident/problem or appropriate time window. Generate the package into a protected directory.

### Step 8 — Protect and Share

Inspect the package for sensitive data, store hashes/metadata if required by process, and transfer via approved support channels.

### Step 9 — Recover and Monitor

After resolving the incident, verify database status, fresh alert log entries, application health, and resource metrics. Do not purge diagnostic data until the investigation is confirmed complete.

## 13. Diagnostic Query Examples

### 13.1. Listing ADR Locations

§§§sql
SELECT name, value
FROM v$diag_info
ORDER BY name;
§§§

### 13.2. Alert Log in the Last 30 Minutes

§§§sql
SELECT originating_timestamp,
       message_type,
       message_level,
       message_text
FROM v$diag_alert_ext
WHERE originating_timestamp >=
      SYSTIMESTAMP - INTERVAL '30' MINUTE
ORDER BY originating_timestamp;
§§§

### 13.3. Filtering ORA Errors

§§§sql
SELECT originating_timestamp,
       message_text,
       problem_key
FROM v$diag_alert_ext
WHERE message_text LIKE '%ORA-%'
  AND originating_timestamp >=
      SYSTIMESTAMP - INTERVAL '1' DAY
ORDER BY originating_timestamp DESC;
§§§

### 13.4. Sessions and Processes

§§§sql
SELECT s.sid,
       s.serial#,
       s.username,
       s.module,
       s.action,
       s.client_identifier,
       p.spid,
       p.tracefile
FROM v$session s
JOIN v$process p
  ON p.addr = s.paddr
WHERE s.type = 'USER'
ORDER BY s.sid;
§§§

V$PROCESS columns can differ by release. If TRACEFILE is absent in your version's view, use V$DIAG_INFO or ADRCI to locate trace paths.

### 13.5. Sessions with SQL Trace Enabled

§§§sql
SELECT sid,
       serial#,
       username,
       sql_trace,
       sql_trace_waits,
       sql_trace_binds,
       module,
       action
FROM v$session
WHERE sql_trace = 'ENABLED';
§§§

Column names/values may vary by release. You may need to consult V$SESSION or other monitor views to verify session trace state.

### 13.6. Incident Metadata

Incident details can be viewed via ADRCI or suitable diagnostic views such as V$DIAG_INCIDENT. Columns and access privileges depend on release; run DESC on available views and cross-check incident IDs with ADRCI.

## 14. Listener Alert Log and Connection Errors

### 14.1. When to Check Listener ADR?

If clients report ORA-12514, ORA-12541, ORA-12505, or ORA-12170, inspect the listener log alongside the client connect descriptor, service registration, and network status.

### 14.2. Selecting the Listener Home

In ADRCI:

§§§text
adrci> show homes
adrci> set home diag/tnslsnr/dbhost01/listener
adrci> show alert -tail 100
§§§

Host/listener names are illustrative only. A host may run multiple listeners, each with its own ADR home.

### 14.3. Database Alert Log Still Needs Checking

The listener may accept a connection and hand it off to the database. If an error occurs after the request reaches the instance, the database alert log or session trace may contain additional details. Read both along the timeline.

### 14.4. Listener Log and Database Alert Log Serve Different Roles

The listener log records connection requests, service registration, and network-level events. The database alert log records events inside the database/instance. Never substitute one log for the other.

| No connection errors in alert log | Listener ADR home | Check listener/service/network |
| Trace file location unclear | Default Trace File, V$PROCESS, ADRCI | Identify the right session/process |
| Trace file growing too large | SQL trace scope and duration | Disable trace, restrict module/session |
| ORA error appearing repeatedly | Alert log/problem/incident | Find the first event and problem key |
| Incident not created on every error | Flood control/incident policy | Inspect problem and incident history |
| ADR base full | ADR retention/trace data | Use ADRCI purge by age/type |
| IPS package missing files | Wrong home/incident/problem selected | Verify package contents and incident ID |
| Cannot see ADRCI home | ADR base/home discovery | Check Oracle Home, ADR base, and OS permissions |
| TKPROF report lacks accurate plan | Explained in a different environment | Cross-check with actual cursor plan |
| Trace binds contain sensitive data | Binds enabled too broadly | Disable trace and secure packages/reports |
| Cannot locate session trace | SID/SERIAL# changed | Identify current session and instance |

## 16. Security and Access Control for Diagnostic Data

### 16.1. Traces Can Contain Sensitive Data

Traces may contain SQL text, bind values, schema names, user identifiers, file paths, hostnames, and application data. Some dumps may contain memory contents. Treat traces as sensitive operational data.

### 16.2. Restricting Read Permissions

Only DBAs, support staff, or authorized personnel should have read access to the entire ADR. OS permissions on ADR directories must align with the Oracle owner/group and organizational policy.

### 16.3. Scoping Traces Narrowly

Prefer tracing by SID/SERIAL#, client ID, service/module/action, or a specific session. Avoid enabling binds or instance-wide event traces without assessing space and data exposure.

### 16.4. Protecting Incident Packages

Packages can include more files than expected. Before uploading:

- Inspect the package contents and scope.
- Use channels approved by your organization.
- Do not place packages in public directories.
- Do not commit them to source control.
- Delete temporary copies once internal retention expires.

### 16.5. Auditing Actions

Record who enabled tracing, the scope, start/stop times, ADRCI purges, and package IDs. This keeps diagnostic collection accountable and explains disk usage changes.

## 18. Incident Investigation Checklist

- [ ] Identify database, DB_UNIQUE_NAME, instance, and host.
- [ ] Identify incident start time and timezone.
- [ ] Retrieve ADR Base and ADR Home from V$DIAG_INFO or ADRCI.
- [ ] Select the right database/listener/ASM ADR home.
- [ ] Read the alert log before, during, and after the error timestamp.
- [ ] Locate the first ORA error, process name, and incident/problem key.
- [ ] Identify the exact trace file from the alert log, V$PROCESS, or ADRCI.
- [ ] If SQL trace is needed, limit by session/client/module and duration.
- [ ] Disable trace once data is collected.
- [ ] Use TKPROF when analyzing parse/execute/fetch/waits.
- [ ] Correlate problem ID and incident ID.
- [ ] Create an IPS package for the exact incident/problem if support is needed.
- [ ] Inspect the package for sensitive data before sharing.
- [ ] Check ADR retention and filesystem capacity.
- [ ] Purge only via ADRCI by verified age/type.
- [ ] Record timeline, package ID, and resolution outcome.
