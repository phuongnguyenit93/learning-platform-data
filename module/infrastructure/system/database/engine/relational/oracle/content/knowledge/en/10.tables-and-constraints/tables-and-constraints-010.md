# Virtual Columns, Identity Columns, and Value-Generation Modes

> **Topic:** Database Engine Relational Oracle  
> **Chapter:** Tables and Constraints  
> **Goal:** Design **virtual columns**, **identity columns**, and default value-generation mechanisms in Oracle; clearly distinguish `GENERATED ALWAYS`, `GENERATED BY DEFAULT`, and `GENERATED BY DEFAULT ON NULL`; and understand their impact on `INSERT`, `UPDATE`, constraints, indexes, concurrency, and data loading.

## 1. The Problem: Which Columns Does the App Supply vs. the Database Generate?

A sales system may handle data like this:

```text
Order line item
├── line_id       : unique identifier, generated by the database
├── quantity      : quantity, supplied by the application
├── unit_price    : unit price, supplied by the application
├── line_total    : quantity × unit_price, derived from the two columns above
├── created_at    : creation timestamp, defaulted by the database
└── status        : status, defaulting to 'NEW' when omitted
```

Although all five appear to be "automatically populated," they do not share the same mechanism:

- **Identity column** generates a new identifier using Oracle's internal generator. Values are normally assigned during `INSERT` and do not compute expressions over other columns.
- **Virtual column** has a value **derived from an expression** over columns in the same row. Applications never write data directly to a virtual column.
- **Default column** receives a default expression when `INSERT` omits the column, or under `DEFAULT ON NULL` rules.
- **Sequence** is a standalone number-generation object usable across multiple statements and multiple tables.
- **Trigger** executes PL/SQL logic on DML events; sometimes used to assign IDs in legacy systems.

Crucially, **derived values**, **write-time generated values**, and **default values** carry distinct semantics. Picking the wrong mechanism can cause duplicate IDs, inconsistent computed values, or unintended overwrites.

### Quick Comparison Table

| Characteristic | Virtual column | Identity column | `DEFAULT` / `DEFAULT ON NULL` |
|---|---|---|---|
| Purpose | Represent a value computed from same-row data | Generate an identifier on insert | Populate an initial value |
| Value source | SQL expression referencing source columns | Oracle-managed sequence for the identity | Literal or supported default expression/function |
| Stored per row like a normal column? | Not stored as a regular column; expression keys can be stored in an index | Yes, as a normal numeric value | Yes, as a normal column value |
| Direct value on `INSERT`? | No | Depends on `ALWAYS` / `BY DEFAULT` mode | Explicit values allowed |
| Updates automatically when other columns `UPDATE`? | Yes, because the value is derived | Does not change with other columns | Does not recompute when other columns update |
| Usable in `SELECT` / `WHERE`? | Yes | Yes | Yes |
| Indexable? | Yes, subject to expression rules | Yes, commonly the primary key | Yes, depending on type and design |

## 2. Virtual Columns: Data Defined by an Expression

A **virtual column** is an Oracle column whose value is defined by a SQL expression, typically based on regular columns in **the same row**. Oracle stores the expression definition in metadata; the virtual values themselves are not stored independently per row inside the table segment.

Example:

```sql
CREATE TABLE lab_order_lines (
    line_id NUMBER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    quantity NUMBER(10,0) NOT NULL,
    unit_price NUMBER(14,2) NOT NULL,
    line_total GENERATED ALWAYS AS (quantity * unit_price) VIRTUAL,
    CONSTRAINT ck_lab_lines_qty CHECK (quantity > 0),
    CONSTRAINT ck_lab_lines_price CHECK (unit_price >= 0)
);
```

Here:

- `QUANTITY` and `UNIT_PRICE` are regular stored columns.
- `LINE_TOTAL` is a **virtual column**; `quantity * unit_price` is its defining expression.
- `LINE_ID` is an **identity column**; explained in depth below.
- `CHECK` constraints enforce domain rules; `NUMBER` alone does not prevent negative numbers.

Insert data:

```sql
INSERT INTO lab_order_lines (quantity, unit_price)
VALUES (3, 125000.00);

COMMIT;

SELECT line_id, quantity, unit_price, line_total
FROM lab_order_lines;
```

Output looks like:

```text
LINE_ID  QUANTITY  UNIT_PRICE  LINE_TOTAL
-------  --------  ----------  ----------
1        3         125000.00   375000.00
```

`LINE_ID = 1` is only an example assuming the generator starts at 1 and has not been used yet; never assume the first ID is always 1 in every environment.

### 2.1. Virtual Values Change Automatically with Source Columns

```sql
UPDATE lab_order_lines
SET quantity = 4
WHERE quantity = 3;

SELECT quantity, unit_price, line_total
FROM lab_order_lines;
```

The logical value of `LINE_TOTAL` becomes `500000.00` when quantity is 4 and unit price is `125000.00`. Do not run:

```sql
UPDATE lab_order_lines
SET line_total = 500000;
```

In fact, **virtual columns cannot be updated directly**. To change the result, update the input columns or alter the expression definition.

### 2.2. Virtual Columns Differ from Regular Columns with DEFAULT

Consider a regular column:

```sql
created_at TIMESTAMP(6) WITH TIME ZONE
    DEFAULT SYSTIMESTAMP NOT NULL
```

`DEFAULT SYSTIMESTAMP` applies during insert per declaration rules; the value is persisted at row creation and **does not change on subsequent reads**.

By contrast, `LINE_TOTAL` is always derived from the current `QUANTITY` and `UNIT_PRICE`. A virtual column is not a "populated once and frozen" column.

## 3. Virtual Column Syntax and Examples

### 3.1. Basic Syntax

```sql
column_name [datatype]
    GENERATED ALWAYS AS (expression) VIRTUAL
```

In supported Oracle syntax, the `VIRTUAL` keyword may be omitted in certain forms, but **writing it explicitly** makes it immediately clear to readers that the column is computed.

Oracle infers the data type from the expression if omitted. For arithmetic, control input precision/scale intentionally or use `CAST` when a strict contract is needed.

Adding a virtual column to an existing table:

```sql
ALTER TABLE lab_order_lines
ADD (
    amount_group GENERATED ALWAYS AS (
        CASE
            WHEN quantity * unit_price >= 1000000
                THEN 'LARGE'
            ELSE 'NORMAL'
        END
    ) VIRTUAL
);
```

Then:

```sql
SELECT line_id, line_total, amount_group
FROM lab_order_lines;
```

`AMOUNT_GROUP` reflects the `CASE` expression result. Because it is derived, application code never needs to store redundant classification labels.

### 3.2. Normalizing Codes or Strings for Querying

Suppose emails may be entered with mixed case and extra whitespace. A virtual column exposes the normalized key:

```sql
CREATE TABLE lab_customers (
    customer_id NUMBER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email VARCHAR2(254 CHAR) NOT NULL,
    email_key GENERATED ALWAYS AS (
        LOWER(TRIM(email))
    ) VIRTUAL
);
```

Query:

```sql
SELECT customer_id, email, email_key
FROM lab_customers;
```

You can create an index on the virtual column:

```sql
CREATE INDEX ix_lab_customers_email_key
ON lab_customers (email_key);
```

Now:

```sql
SELECT customer_id, email
FROM lab_customers
WHERE email_key = 'user@example.com';
```

can use the index when the optimizer judges it beneficial. **An index on a virtual column stores computed key values inside the index structure**, even though the virtual column itself is not stored in the table row.

**Domain warning:** `LOWER(TRIM(email))` is only a string-normalization example. Email identity rules, case sensitivity, Unicode handling, collation, and uniqueness policies must be defined by the application; never assume simple lowercasing fits every email system.

### 3.3. Computing Dates from Another Date

A deadline defined as a fixed number of days from creation date:

```sql
CREATE TABLE lab_due_dates (
    task_id NUMBER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    opened_on DATE NOT NULL,
    due_on GENERATED ALWAYS AS (opened_on + 7) VIRTUAL
);
```

On a `DATE`, `opened_on + 7` adds seven **calendar days (24-hour units in `DATE` arithmetic)**. If the business rule is "7 business days" or depends on DST/timezones, this expression is insufficient.

Use virtual columns for fixed, deterministic rules that depend solely on row values. Rules involving holiday calendars, lookup tables, or service states belong elsewhere.

### 3.4. Virtual Columns for JSON Queries

In Oracle versions with appropriate SQL/JSON support, a frequently queried JSON attribute can be exposed as a virtual column:

```sql
CREATE TABLE lab_json_events (
    event_id NUMBER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    payload CLOB CHECK (payload IS JSON),
    event_type GENERATED ALWAYS AS (
        JSON_VALUE(
            payload,
            '$.eventType' RETURNING VARCHAR2(30)
        )
    ) VIRTUAL
);
```

This is useful when querying a JSON property by column name and considering an index on it. Before wide adoption, verify JSON type handling, string normalization, JSON path errors, missing values, and indexing behavior on your exact Oracle release.

## 4. Virtual Column Restrictions and Design Rules

### 4.1. Expressions Must Fit the Single-Row Model

A virtual column is not a "mini SQL view that runs arbitrary queries." Its expression must be a **scalar expression** built from columns of the same row and supported Oracle functions.

Avoid defining virtual columns that:

- Reference other tables via **subqueries**.
- Use aggregate functions like `SUM` or `COUNT`.
- Call sequences such as `my_seq.NEXTVAL` on read.
- Depend on current wall-clock time such as `SYSDATE` or `SYSTIMESTAMP` expecting "live updates over time."
- Call non-deterministic functions whose results vary across calls for identical inputs, especially if indexed or constrained.
- Form circular dependencies or reference other virtual columns in unsupported ways.

Example of a desired "age as of today" column:

```sql
-- Unsuitable for a row-invariant virtual column:
age_today AS (
    TRUNC(MONTHS_BETWEEN(SYSDATE, birth_date) / 12)
)
```

Age changes with the calendar even when the row never changes, so compute it in **queries** or the application layer using an explicit reference date:

```sql
SELECT birth_date,
       TRUNC(
           MONTHS_BETWEEN(DATE '2026-11-14', birth_date) / 12
       ) AS age_on_reference_date
FROM people;
```

This illustrates calculating age against a reference date; legal age rules, leap years, and data edge cases must be defined separately by the business.

### 4.2. Virtual Columns Cannot Be Directly INSERTed or UPDATEd

On `LAB_ORDER_LINES`:

```sql
-- Valid:
INSERT INTO lab_order_lines (quantity, unit_price)
VALUES (2, 45000.00);

-- Invalid: LINE_TOTAL is virtual; cannot insert a value directly.
INSERT INTO lab_order_lines (quantity, unit_price, line_total)
VALUES (2, 45000.00, 90000.00);

-- Invalid: cannot modify LINE_TOTAL via direct UPDATE.
UPDATE lab_order_lines
SET line_total = 1;
```

The two statements labeled "Invalid" are **error illustrations**, not meant to be run in the main lab script. Oracle raises errors in the `ORA-540xx` family for illegal operations on virtual columns.

To refresh a virtual column's value, modify its source columns or update the expression via controlled DDL.

### 4.3. Virtual Columns Can Participate in Indexes and Constraints

When deterministic and supported, Oracle allows virtual columns in:

- B-tree indexes.
- `CHECK` constraints and, where appropriate, uniqueness constraints/indexes.
- Certain partitioning strategies in supporting releases.
- Optimizer statistics and query predicates.

Example enforcing unique normalized `email_key`:

```sql
CREATE UNIQUE INDEX ux_lab_customers_email_key
ON lab_customers (email_key);
```

When two rows yield the same `email_key`, DML is rejected by the unique index. This is a business design choice: define email normalization rules carefully first so you do not enforce uniqueness on the wrong expression.

**Note:** Not every expression or datatype is indexable, and maintaining an index adds overhead whenever source columns change.

### 4.4. Performance and Physical Storage Considerations

Virtual columns avoid storing redundant derived data, yet **do not automatically make queries faster**:

- When reading an unindexed virtual column, Oracle evaluates the expression dynamically.
- If an index exists on the virtual column, the index stores the computed keys and must be maintained on `INSERT`/`UPDATE`.
- Complex expressions, especially PL/SQL functions or JSON parsing, consume CPU.
- On large tables, altering expressions or building indexes consumes significant resources and affects active queries.
- Statistics and selectivity determine whether the optimizer uses the index.

Thus, virtual columns primarily enforce **a single, consistent derivation rule**. Evaluate performance using real execution plans and workloads.

### 4.5. When Should You Avoid Virtual Columns?

Do not use a virtual column when:

1. You need to store a **point-in-time transaction snapshot** even if inputs or formulas later change.
2. The formula depends on another table, external service, current time, or mutable external state.
3. The value must be editable independently of source columns.
4. Calculation results depend on a versioned business algorithm that must be preserved for audit.
5. Calculation is CPU-heavy and read-heavy without a suitable indexing/materialization plan.

For instance, a finalized order must persist its **billed amount at transaction time**. If unit prices or rounding policies change after an invoice is issued, a virtual column recomputing from current price tables destroys historical accuracy. Persist immutable transaction snapshots instead.

## 5. Identity Columns: Numeric Keys Generated by Oracle on INSERT

An **identity column** is Oracle's built-in mechanism for generating numeric column values using a database-managed internal generator. Introduced in Oracle Database **12c**, the core options are:

```sql
column_name NUMBER
    GENERATED ALWAYS AS IDENTITY

column_name NUMBER
    GENERATED BY DEFAULT AS IDENTITY

column_name NUMBER
    GENERATED BY DEFAULT ON NULL AS IDENTITY
```

It fits **surrogate keys** especially well when the application does not choose IDs manually. Oracle manages the underlying sequence automatically; no manual `BEFORE INSERT` trigger is required.

Example:

```sql
CREATE TABLE lab_tickets (
    ticket_id NUMBER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title VARCHAR2(200 CHAR) NOT NULL
);
```

Insert a row:

```sql
INSERT INTO lab_tickets (title)
VALUES ('Report access error');

COMMIT;

SELECT ticket_id, title
FROM lab_tickets;
```

Oracle generates `TICKET_ID` when the insert omits it. The generated ID is **physically stored in the row**, unlike a virtual column computed from an expression.

### 5.1. Identity Is Not Synonymous with Primary Key

`GENERATED ... AS IDENTITY` specifies **value generation**, whereas `PRIMARY KEY` specifies **uniqueness and non-NULL identity constraints**.

Write both clearly:

```sql
ticket_id NUMBER GENERATED ALWAYS AS IDENTITY PRIMARY KEY
```

Never assume an identity column automatically covers every key requirement:

- `BY DEFAULT` permits manual ID entry, introducing collision risks if misused.
- Generators can produce gaps.
- Generated surrogate IDs do not replace business keys like `order_code`.
- Always declare `PRIMARY KEY` or `UNIQUE` when uniqueness is required.

Identity columns carry `NOT NULL` behavior under Oracle rules, yet `PRIMARY KEY` remains the explicit declaration for the table's row identifier.

### 5.2. Should You Have Both an Internal ID and a Business Code?

An orders table commonly includes:

```sql
CREATE TABLE lab_orders (
    order_id NUMBER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_code VARCHAR2(40 CHAR) NOT NULL UNIQUE,
    created_at TIMESTAMP(6) WITH TIME ZONE
        DEFAULT SYSTIMESTAMP NOT NULL
);
```

- `ORDER_ID` is the system-generated numeric key for joins and foreign keys.
- `ORDER_CODE` is the business identifier that may require formatting, prefixes, or leading zeros under its own rules.
- `CREATED_AT` records the insertion timestamp by default.

Never rely on ID order to guarantee chronological order or exact valid record counts. Generated IDs **are not a clock**, and gaps arise from rollbacks and sequence pre-allocation.

## 6. The Three Identity Modes: ALWAYS, BY DEFAULT, BY DEFAULT ON NULL

This is the core distinction of the lesson.

### 6.1. GENERATED ALWAYS AS IDENTITY

In **ALWAYS** mode, Oracle owns ID generation; the application **cannot supply an explicit value** for the column in standard `INSERT` statements.

```sql
CREATE TABLE lab_id_always (
    id NUMBER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    note_text VARCHAR2(100 CHAR)
);

INSERT INTO lab_id_always (note_text)
VALUES ('Row A');

INSERT INTO lab_id_always (note_text)
VALUES ('Row B');
```

Attempting to provide an ID fails under this mode:

```sql
-- Error illustration; do not run in the main flow:
INSERT INTO lab_id_always (id, note_text)
VALUES (500, 'Application assigned ID');
```

Oracle raises `ORA-32795` when attempting to insert an explicit value into a `GENERATED ALWAYS` column. Passing explicit `NULL` does not trigger generation in ALWAYS mode either; simply **omit the ID column from the INSERT list**.

**Choose ALWAYS when:** the database strictly owns ID generation and applications must be blocked from manual ID entry via normal DML.

### 6.2. GENERATED BY DEFAULT AS IDENTITY

In **BY DEFAULT** mode, Oracle generates an ID when the column is omitted; if the application passes an explicit valid ID, Oracle uses that supplied value.

```sql
CREATE TABLE lab_id_default (
    id NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    note_text VARCHAR2(100 CHAR)
);

-- Oracle generates ID:
INSERT INTO lab_id_default (note_text)
VALUES ('Auto-generated ID');

-- Application provides explicit ID:
INSERT INTO lab_id_default (id, note_text)
VALUES (8000, 'Imported data with legacy ID');
```

Watch out for **explicit `NULL`**:

```sql
-- Error illustration; do not run in the main flow:
INSERT INTO lab_id_default (id, note_text)
VALUES (NULL, 'Client passed NULL');
```

With standard `BY DEFAULT`, passing explicit `NULL` **is not the same as omitting the column**: Oracle does not generate an ID here and raises a `NOT NULL` violation, typically `ORA-01400`.

**Choose BY DEFAULT when:** IDs should be auto-generated normally, yet imports or special workflows must supply pre-existing IDs.

### 6.3. GENERATED BY DEFAULT ON NULL AS IDENTITY

**BY DEFAULT ON NULL** mode supports all three cases:

1. Omit ID column from `INSERT` → Oracle generates ID.
2. Pass explicit `NULL` → Oracle generates ID.
3. Pass explicit number → Oracle uses that number.

```sql
CREATE TABLE lab_id_default_null (
    id NUMBER GENERATED BY DEFAULT ON NULL AS IDENTITY PRIMARY KEY,
    note_text VARCHAR2(100 CHAR)
);

-- Omit ID:
INSERT INTO lab_id_default_null (note_text)
VALUES ('ID omitted');

-- Pass explicit NULL:
INSERT INTO lab_id_default_null (id, note_text)
VALUES (NULL, 'ID sent as NULL');

-- Pass explicit ID:
INSERT INTO lab_id_default_null (id, note_text)
VALUES (9000, 'ID supplied by import');
```

This mode works well when frameworks, ORMs, ETL jobs, or clients routinely bind `NULL` for uninitialized IDs while imports still need to supply explicit IDs when required.

### 6.4. Behavior Comparison Matrix

| INSERT Pattern | ALWAYS | BY DEFAULT | BY DEFAULT ON NULL |
|---|---|---|---|
| Omit ID column | **Oracle generates** | **Oracle generates** | **Oracle generates** |
| Pass `ID = 123` | **Error** | Accepted if valid/unique | Accepted if valid/unique |
| Pass `ID = NULL` | **Error** | **NOT NULL error** | **Oracle generates** |
| Use `DEFAULT` keyword | Version/syntax-dependent; safest is omitting ID column | Generally requests generated default | Generally requests generated default |
| Best suited for | Database exclusively owns IDs | Supporting explicit ID imports | Supporting explicit IDs and clients passing NULL |

In all three modes, enforce uniqueness with a primary key or unique constraint. In modes allowing manual ID entry, inserting a large explicit ID **does not automatically advance** the identity sequence past that value.

### 6.5. INSERT, UPDATE, and Identity Ownership

Identity is a **row-insertion value generator**, not a continuous update formula. Updating another column never regenerates the ID:

```sql
UPDATE lab_id_always
SET note_text = 'Updated content'
WHERE note_text = 'Row A';
```

With `GENERATED ALWAYS`, applications should also treat the identity column as non-updatable. In other modes, explicit DML capabilities and restrictions follow your Oracle release rules. **Treat primary keys as immutable identifiers**, even when SQL technically allows updates.

## 7. Identity Generation Options

Identity generators accept options similar to sequences. Example:

```sql
CREATE TABLE lab_ids_options (
    id NUMBER GENERATED ALWAYS AS IDENTITY (
        START WITH 1000
        INCREMENT BY 5
        CACHE 20
        NOCYCLE
    ) PRIMARY KEY,
    label VARCHAR2(100 CHAR) NOT NULL
);
```

Here:

- `START WITH 1000`: initial value for the generator.
- `INCREMENT BY 5`: step size between generated values, per sequence rules.
- `CACHE 20`: pre-allocates sequence numbers in memory for better throughput.
- `NOCYCLE`: stops rather than wrapping around at the limit.

In a fresh table, generated values run `1000`, `1005`, `1010`, ...; **gaps** can still occur due to rollbacks, errors, cache eviction, and concurrency.

### 7.1. START WITH and INCREMENT BY

`START WITH` and `INCREMENT BY` help when specific numeric ranges are needed. Never encode year, branch, or order type inside identity IDs if those attributes can change or follow business rules.

Encode business meaning in `ORDER_CODE`, rather than relying on gapless identity sequences.

### 7.2. CACHE and NOCACHE

Caching avoids disk/dictionary overhead for every single number allocation. Oracle pre-allocates a batch; after instance restarts or crashes, unused cached numbers are discarded.

| Option | Primary Effect | Key Consideration |
|---|---|---|
| `CACHE n` | Improves allocation throughput across many workloads | Unused cached values leave gaps on restart/failure |
| `NOCACHE` | Does not pre-cache ranges as `CACHE` does | **Does not** guarantee gapless IDs |
| `INCREMENT BY` | Sets step interval | Does not protect uniqueness if manual inserts collide |
| `CYCLE` | Allows wrapping at bounds | Risks colliding with still-existing IDs |
| `NOCYCLE` | Does not wrap at bounds | Appropriate for most surrogate keys |

**Never choose `NOCACHE` expecting "gapless IDs."** Transaction rollbacks, failed inserts, and concurrent sessions still consume numbers without creating committed rows.

### 7.3. CYCLE and ORDER

Sequence options like `CYCLE` and `ORDER` may appear in identity options depending on release/configuration.

- `CYCLE` is unsuitable for long-lived surrogate primary keys because wrapping collides with existing rows.
- `ORDER` ensures allocation ordering across multi-instance environments per sequence rules, yet **never turns an ID into proof of commit order** or completion time.
- In Real Application Clusters (RAC), concurrency and allocation behavior can cause visible IDs to differ from commit order.

For chronological auditing, use dedicated timestamp columns with clear contracts rather than inferring order from identity IDs.

### 7.4. Do Identity Columns Guarantee Gapless Numbers?

**No.** Consider two transactions:

```text
Session A: INSERT → gets ID 101 → ROLLBACK
Session B: INSERT → gets ID 102 → COMMIT
```

The table ends up containing `102` without `101`. Oracle never reclaims ID `101` from the rolled-back transaction.

Common causes of gaps:

1. Transaction rollbacks.
2. Failed `INSERT` statements after the generator already allocated a number.
3. Cached values lost upon instance restart or failure.
4. Deleted rows after commit.
5. Concurrent sessions and RAC instances.

Therefore, use identity/sequence values as **identifiers**, not as exact row counters or legally gapless document numbers. If strictly gapless numbering is legally required, build a dedicated serialized business numbering workflow accepting the associated locking and accounting trade-offs.

## 8. Standalone Sequences vs. Identity Columns

Before identity columns existed, Oracle commonly used a `SEQUENCE` plus a trigger to assign IDs. Standalone sequences remain useful when a generator must span multiple statements, multiple tables, or custom application logic.

### 8.1. Creating a Standalone Sequence

```sql
CREATE SEQUENCE lab_order_seq
    START WITH 1
    INCREMENT BY 1
    CACHE 20
    NOCYCLE;
```

Direct usage:

```sql
SELECT lab_order_seq.NEXTVAL AS new_value
FROM dual;
```

`NEXTVAL` advances and returns the next value; `CURRVAL` retrieves the last `NEXTVAL` obtained in the current session per sequence rules.

Defaulting a table column from a sequence (supported from Oracle 12c onward):

```sql
CREATE TABLE lab_sequence_orders (
    order_id NUMBER DEFAULT lab_order_seq.NEXTVAL PRIMARY KEY,
    order_label VARCHAR2(100 CHAR) NOT NULL
);
```

Insert a row:

```sql
INSERT INTO lab_sequence_orders (order_label)
VALUES ('Order using sequence default');
```

This behaves similarly to identity for default generation, except `LAB_ORDER_SEQ` is an **independent, explicitly named sequence object** managed separately.

### 8.2. When to Choose Identity vs. Standalone Sequence?

Choose an identity column when:

- Each table owns its own Oracle-generated numeric surrogate key.
- You want metadata to explicitly declare the column as an identity column.
- You want `ALWAYS` / `BY DEFAULT` / `BY DEFAULT ON NULL` insert controls.
- Multiple tables do not need to share one sequence.
- You want to avoid maintaining boilerplate ID triggers.

Choose a standalone sequence when:

- Multiple tables share a single number space or allocation rule.
- Applications must fetch IDs prior to inserting rows in explicit flows.
- Multiple statements or objects must call `NEXTVAL` directly.
- Integrating with legacy designs built around named sequences.
- Generator administration must remain independent of one table column's lifecycle.

**Do not share one global sequence just to make IDs "increase uniformly across the whole database"** without a clear business benefit; it couples unrelated objects unnecessarily.

### 8.3. Legacy Trigger-Based ID Generation

Legacy pattern example:

```sql
CREATE TABLE lab_trigger_orders (
    order_id NUMBER PRIMARY KEY,
    order_label VARCHAR2(100 CHAR)
);
```

```sql
CREATE OR REPLACE TRIGGER trg_lab_trigger_orders_bi
BEFORE INSERT ON lab_trigger_orders
FOR EACH ROW
WHEN (NEW.order_id IS NULL)
BEGIN
    :NEW.order_id := lab_order_seq.NEXTVAL;
END;
/
```

When an insert omits `order_id` or passes NULL, the trigger assigns the sequence value. While valid in legacy code, it adds PL/SQL maintenance outside the table declaration.

For **pure key generation**, identity columns or sequence defaults are simpler. Triggers remain appropriate for DML rules that cannot be expressed via constraints, defaults, or identity columns.

## 9. DEFAULT, DEFAULT ON NULL, and Other Default Sources

Identity covers numeric surrogate IDs; Oracle provides **`DEFAULT`** for regular columns.

### 9.1. DEFAULT: Applied When No Value Is Supplied

```sql
CREATE TABLE lab_order_defaults (
    order_id NUMBER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    status VARCHAR2(20 CHAR) DEFAULT 'NEW' NOT NULL,
    created_at TIMESTAMP(6) WITH TIME ZONE
        DEFAULT SYSTIMESTAMP NOT NULL,
    quantity NUMBER(10,0) DEFAULT 1 NOT NULL
);
```

Insert:

```sql
INSERT INTO lab_order_defaults DEFAULT VALUES;
```

Support for `INSERT ... DEFAULT VALUES` depends on Oracle version and column setup; for portable illustration, pass one regular column and let the remaining columns use their defaults:

```sql
INSERT INTO lab_order_defaults (status)
VALUES ('PROCESSING');
```

`CREATED_AT` and `QUANTITY` receive their defaults; `STATUS` keeps the supplied value.

Passing explicit `NULL` to `QUANTITY` defined with standard `DEFAULT 1 NOT NULL`:

```sql
-- Raises NOT NULL error (does NOT substitute 1):
INSERT INTO lab_order_defaults (status, quantity)
VALUES ('NEW', NULL);
```

Standard `DEFAULT` **does not automatically replace explicit NULLs**.

### 9.2. DEFAULT ON NULL: Populating Even When NULL Is Passed

```sql
CREATE TABLE lab_on_null_defaults (
    event_id NUMBER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    event_type VARCHAR2(30 CHAR)
        DEFAULT ON NULL 'UNKNOWN' NOT NULL,
    created_at TIMESTAMP(6) WITH TIME ZONE
        DEFAULT ON NULL SYSTIMESTAMP NOT NULL
);
```

Insert:

```sql
INSERT INTO lab_on_null_defaults (event_type, created_at)
VALUES (NULL, NULL);
```

Oracle substitutes the defaults for NULL inputs under `DEFAULT ON NULL` semantics. In Oracle, `DEFAULT ON NULL` implies `NOT NULL` behavior on the column; do not design assuming you can simultaneously use `DEFAULT ON NULL` and store `NULL` as a distinct valid state.

**Distinction:** `DEFAULT ON NULL` on regular columns accepts literals, timestamps, or supported expressions. `GENERATED BY DEFAULT ON NULL AS IDENTITY` is an **identity mode** backed by a numeric generator.

### 9.3. DEFAULT ON NULL Is Not a Virtual Column

Suppose:

```sql
quantity NUMBER(10,0) DEFAULT ON NULL 1 NOT NULL
```

`QUANTITY` receives `1` on insert and **stores `1`**. If later updated to `5`, it holds `5`—there is no formula recomputing it from other columns.

A virtual column:

```sql
line_total GENERATED ALWAYS AS (quantity * unit_price) VIRTUAL
```

is always derived from both source columns, never populated once and frozen.

### 9.4. Common Default Expressions

| Goal | Typical Declaration | Notes |
|---|---|---|
| Initial status | `DEFAULT 'NEW'` | Pair with CHECK/FK to protect allowed statuses |
| Default quantity | `DEFAULT 1` | Pair with NOT NULL/CHECK for non-negative domain |
| Server timestamp on insert | `DEFAULT SYSTIMESTAMP` | Choose timezone-appropriate column type |
| Server date/time | `DEFAULT SYSDATE` | Oracle `DATE` stores seconds, without timezone |
| Binary UUID | `DEFAULT SYS_GUID()` | 16-byte identifier; align with app UUID rules |
| Sequence value | `DEFAULT lab_seq.NEXTVAL` | Requires supporting Oracle syntax/version |
| Replace NULL with default | `DEFAULT ON NULL ...` | Cannot treat NULL as a separate stored value |

Note: defaults apply at `INSERT` time and **do not auto-update** later. For example, `updated_at DEFAULT SYSTIMESTAMP` does not refresh automatically on `UPDATE`; maintain last-modified timestamps via controlled DML or appropriate triggers/auditing.

## 10. Comparing Generation Modes Across INSERT Patterns

Put all five column kinds side by side:

```sql
CREATE TABLE lab_generation_mix (
    id NUMBER GENERATED BY DEFAULT ON NULL AS IDENTITY PRIMARY KEY,
    input_a NUMBER(10,0) DEFAULT 1 NOT NULL,
    input_b NUMBER(10,0) DEFAULT ON NULL 2 NOT NULL,
    total_value GENERATED ALWAYS AS (input_a + input_b) VIRTUAL,
    created_at TIMESTAMP(6) WITH TIME ZONE
        DEFAULT SYSTIMESTAMP NOT NULL
);
```

Case 1: supply only `INPUT_A`:

```sql
INSERT INTO lab_generation_mix (input_a)
VALUES (10);
```

Logical row result:

- `ID`: auto-generated.
- `INPUT_A = 10`.
- `INPUT_B = 2` (omitted on insert).
- `TOTAL_VALUE = 12` from the virtual expression.
- `CREATED_AT` receives the insert timestamp.

Case 2: client passes NULL for `ID` and `INPUT_B`:

```sql
INSERT INTO lab_generation_mix (id, input_a, input_b)
VALUES (NULL, 20, NULL);
```

Logical result:

- `ID` is still generated because of `BY DEFAULT ON NULL AS IDENTITY`.
- `INPUT_B` receives `2` because of `DEFAULT ON NULL 2`.
- `TOTAL_VALUE = 22`.

Case 3: client supplies an explicit ID:

```sql
INSERT INTO lab_generation_mix (id, input_a, input_b)
VALUES (9000, 7, 8);
```

Logical result:

- `ID = 9000` (assuming no key collision).
- `TOTAL_VALUE = 15`.
- The internal identity sequence **is not automatically bumped past 9000** just because this row was inserted.

Case 4: client tries to supply `TOTAL_VALUE`:

```sql
-- Invalid: virtual columns cannot be written directly.
INSERT INTO lab_generation_mix (
    input_a, input_b, total_value
) VALUES (3, 4, 7);
```

Oracle rejects writing to the virtual column. Instead, query `total_value` via `SELECT` after inserting source columns.

### Comparison Table for INSERT Behavior with NULL

| Mechanism | Column Omitted on INSERT | Explicit NULL Passed | Explicit Value Passed |
|---|---|---|---|
| Regular column `DEFAULT x` | Uses `x` | Keeps NULL if nullable; error if NOT NULL | Stores supplied value |
| Regular column `DEFAULT ON NULL x` | Uses `x` | Uses `x` | Stores supplied value |
| Identity `ALWAYS` | Generates ID | Explicit write forbidden | Explicit write forbidden |
| Identity `BY DEFAULT` | Generates ID | NOT NULL error | Stores supplied value |
| Identity `BY DEFAULT ON NULL` | Generates ID | Generates ID | Stores supplied value |
| Virtual `GENERATED ALWAYS AS (...)` | Derived from expression | Direct write forbidden | Direct write forbidden |

## 11. Retrieving Newly Generated IDs in SQL and JDBC

### 11.1. Never Use MAX(id) to Find the Just-Inserted ID

A common anti-pattern:

```sql
-- Unreliable under concurrent sessions:
SELECT MAX(order_id)
FROM lab_orders;
```

Between session A's insert and its `MAX` query, session B may insert another row with a larger ID. That query **does not reliably identify session A's row**.

Always capture the generated ID directly from the insert operation or the driver's generated-keys API.

### 11.2. RETURNING ... INTO in SQL*Plus/SQLcl

```sql
VARIABLE new_ticket_id NUMBER

INSERT INTO lab_tickets (title)
VALUES ('Verification request')
RETURNING ticket_id INTO :new_ticket_id;

PRINT new_ticket_id;

COMMIT;
```

`RETURNING` returns the ID of the **exact row just inserted by that statement**. This is ideal when immediately inserting child rows with a foreign key.

Syntax for bind/return variables varies across clients and frameworks; the snippet above targets SQL*Plus or SQLcl supporting `VARIABLE` and `PRINT`.

### 11.3. JDBC PreparedStatement and Generated Keys

In Java JDBC, ask the driver for generated keys via `getGeneratedKeys()` or Oracle `RETURNING INTO` where supported by your framework.

Conceptual JDBC example:

```java
String sql = "INSERT INTO lab_tickets (title) VALUES (?)";

try (PreparedStatement ps = connection.prepareStatement(
        sql, new String[] { "TICKET_ID" })) {
    ps.setString(1, "List display error");
    ps.executeUpdate();

    try (ResultSet keys = ps.getGeneratedKeys()) {
        if (keys.next()) {
            long ticketId = keys.getLong(1);
            System.out.println("Generated ID: " + ticketId);
        }
    }
}
```

Different Oracle JDBC driver versions and frameworks vary in column-name arrays vs. generated key return types; test on your actual driver. The snippet assumes a valid `Connection` and application-managed transaction.

### 11.4. Sequence CURRVAL Is Not the Standard Way to Read Identity IDs

When using a **standalone sequence** after calling `NEXTVAL` in the same session, `CURRVAL` works:

```sql
SELECT lab_order_seq.CURRVAL
FROM dual;
```

However, never inspect the internal sequence name backing an identity column and call `CURRVAL` on it in application code. For identity columns, use `RETURNING` or `getGeneratedKeys()`. **Internal sequence names are not a stable public API.**

## 12. Importing Legacy Data and Resyncing Generators

### 12.1. The Problem with Explicit ID Imports

Suppose a table uses:

```sql
id NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
```

A migration imports 50,000 rows with `ID`s from 1 to 50,000. The internal identity generator remains at a low value, because explicit inserts do not force the sequence past imported values.

Post-migration, an `INSERT` omitting ID generates an ID **that already exists**, causing primary key violations such as `ORA-00001`.

### 12.2. Planning the Migration

1. Decide explicitly whether to **preserve legacy IDs** or generate new IDs with a mapping table.
2. If preserving legacy IDs, use a mode permitting explicit IDs such as `BY DEFAULT` or `BY DEFAULT ON NULL`.
3. After importing, query `MAX(id)` on the loaded data.
4. Reset the identity generator's starting point using syntax **supported by your Oracle version** so future generated IDs never collide.
5. Test an auto-generated insert in a lab/staging pass after migration.
6. Verify foreign keys, consistency, and ID history across related tables.

Some Oracle releases support `START WITH LIMIT VALUE` when altering an identity column via `ALTER TABLE`; exact syntax and restrictions vary by release. Consult the **SQL Language Reference for your exact version** rather than manually altering internal `ISEQ$$_...` sequences guessed from the dictionary.

### 12.3. ALWAYS Mode During Migrations

If the target table uses `GENERATED ALWAYS`, standard `INSERT`s cannot supply explicit IDs. To preserve legacy IDs, either use `BY DEFAULT` during migration (or an Oracle-supported import mechanism) and switch management mode afterward if appropriate.

Never toggle production schemas from `ALWAYS` to `BY DEFAULT` carelessly just to make one import script pass without checking how other applications write IDs and planning the cutover.

## 13. Identity Columns Under Concurrency and Oracle RAC

### 13.1. Uniqueness vs. Commit Order

Identity generators allocate numbers using sequence mechanics. Under concurrent sessions:

```text
Session A: gets ID 1001, runs longer, COMMITs later.
Session B: gets ID 1002, COMMITs immediately.
```

If queries filter by commit time, row 1002 appears before row 1001. Hence:

- A larger ID **does not guarantee** the row committed later.
- IDs are not guaranteed to be contiguous.
- Rolled-back transactions still consume IDs.
- `ORDER BY id` orders by ID value, not exact business event chronology.

For chronological ordering, store explicit `created_at` / `event_occurred_at` timestamps or dedicated event sequence mechanisms matching real ordering needs.

### 13.2. Caching and Multiple Instances

In Oracle RAC, multiple instances share the same database. Sequence caching and allocation are tuned for concurrency; depending on configuration, ID ranges issued by two instances may not align with application-observed wall-clock order.

Never treat IDs as a "global clock." If strict global ordering is a business requirement, design a **linearization point** and understand its transaction and synchronization cost.

### 13.3. When Are UUIDs a Better Fit?

When distributed systems create records **offline** or need IDs before reaching Oracle, UUIDs/GUIDs may fit better. Oracle provides `SYS_GUID()` returning a 16-byte binary value:

```sql
CREATE TABLE lab_guid_records (
    record_id RAW(16) DEFAULT SYS_GUID() PRIMARY KEY,
    payload VARCHAR2(100 CHAR)
);
```

`RAW(16)` with `SYS_GUID()` is an alternative to numeric identity columns. Weigh Java ID generation, API representation, index locality/performance, batch inserts, and uniqueness guarantees.

Numeric identity columns are very convenient when the database centrally issues keys; GUIDs shine when distributed nodes generate keys independently. Neither is universally optimal.

## 14. Indexes, Statistics, and Constraints on Generated Columns

### 14.1. Identity and Primary Key Indexes

Declaring:

```sql
id NUMBER GENERATED ALWAYS AS IDENTITY PRIMARY KEY
```

enforces `PRIMARY KEY`, typically backed by an index. Choosing an appropriately sized numeric type keeps keys compact and foreign keys consistent.

Child table:

```sql
CREATE TABLE lab_ticket_comments (
    comment_id NUMBER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    ticket_id NUMBER NOT NULL,
    content VARCHAR2(1000 CHAR) NOT NULL,
    CONSTRAINT fk_lab_comment_ticket
        FOREIGN KEY (ticket_id) REFERENCES lab_tickets(ticket_id)
);
```

`TICKET_ID` in the child table uses a compatible type matching the referenced column; it **must not be an identity column**, because it is a foreign key rather than the comment's own ID.

### 14.2. Virtual Columns and Index Queries

Virtual columns give frequently queried expressions a clean name and index:

```sql
CREATE INDEX ix_lab_lines_total
ON lab_order_lines (line_total);

SELECT line_id, line_total
FROM lab_order_lines
WHERE line_total >= 1000000;
```

The optimizer **may** use the index when the predicate is selective and statistics support it. Queries returning a large fraction of the table may still prefer a full table scan.

Check the execution plan:

```sql
EXPLAIN PLAN FOR
SELECT line_id, line_total
FROM lab_order_lines
WHERE line_total >= 1000000;

SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY);
```

`EXPLAIN PLAN` shows an estimated plan. For real tuning, also measure executions, buffer gets, physical reads, and elapsed time.

### 14.3. CHECK Constraints on Virtual Columns

Example:

```sql
ALTER TABLE lab_order_lines
ADD CONSTRAINT ck_lab_line_total_nonnegative
CHECK (line_total >= 0);
```

Remember that `CHECK` obeys three-valued logic: if the expression yields `NULL`, `UNKNOWN` passes `CHECK`. In this example, `QUANTITY` and `UNIT_PRICE` are `NOT NULL`, so their product never yields `NULL` from missing inputs.

Add constraints matching the business domain. Never assume a numeric virtual column is always valid if inputs can be missing or unconstrained.

### 14.4. When Virtual Column Expressions Change

Modifying a total or classification formula affects dependent queries, virtual-column indexes, and constraints. Crucially, if historical reports or invoices read that column, changing the expression alters historical query results.

For **immutable history**, store finalized values or formula versions explicitly rather than relying on virtual columns as historical snapshots.

## 15. Inspecting Virtual and Identity Metadata

Oracle stores metadata in the data dictionary. Querying it distinguishes defaulted, virtual, and identity columns reliably without guessing by name.

### 15.1. Viewing Table Columns

```sql
SELECT column_id,
       column_name,
       data_type,
       virtual_column,
       identity_column,
       nullable
FROM user_tab_columns
WHERE table_name = 'LAB_ORDER_LINES'
ORDER BY column_id;
```

Key attributes:

- `VIRTUAL_COLUMN`: whether the column is virtual (`YES`/`NO`).
- `IDENTITY_COLUMN`: whether it is an identity column (on releases exposing this column).
- `DATA_TYPE`: Oracle data type.
- `NULLABLE`: nullability metadata.
- `COLUMN_ID`: column position in table metadata.

Depending on release, system-generated/hidden columns may differ between `USER_TAB_COLUMNS` and `USER_TAB_COLS`.

### 15.2. Viewing Identity Configuration

On supporting Oracle releases:

```sql
SELECT table_name,
       column_name,
       generation_type,
       sequence_name,
       identity_options
FROM user_tab_identity_cols
WHERE table_name IN (
    'LAB_TICKETS',
    'LAB_ID_ALWAYS',
    'LAB_ID_DEFAULT',
    'LAB_ID_DEFAULT_NULL'
)
ORDER BY table_name;
```

This view shows each identity column, generation mode, and backing sequence. System sequence names look like `ISEQ$$_...`; treat them as **administrative metadata** and never hard-code them in Java or application SQL.

### 15.3. Viewing a Virtual Column's Expression

In many Oracle releases, the column expression resides in `USER_TAB_COLUMNS.DATA_DEFAULT` or equivalent dictionary fields. `DATA_DEFAULT` is typed as `LONG` in several views, limiting string querying and formatting.

With appropriate privileges, use client describe tools or `DBMS_METADATA.GET_DDL`:

```sql
SELECT DBMS_METADATA.GET_DDL(
           'TABLE', 'LAB_ORDER_LINES'
       ) AS table_ddl
FROM dual;
```

The returned DDL shows exact `GENERATED ALWAYS AS (...) VIRTUAL` and `GENERATED ... AS IDENTITY` definitions. For long DDL output in SQL*Plus/SQLcl, adjust `LONG`, `LINESIZE`, and `PAGESIZE` to view the full text.

### 15.4. Distinguishing Legacy Sequences and Triggers

```sql
SELECT sequence_name, increment_by, cache_size
FROM user_sequences
WHERE sequence_name = 'LAB_ORDER_SEQ';

SELECT trigger_name, table_name, status
FROM user_triggers
WHERE table_name = 'LAB_TRIGGER_ORDERS';
```

A single table might have column defaults, an identity column, and triggers interacting. When debugging unexpected values, inspect both DDL and triggers to see every active mechanism.

## 16. Comprehensive Hands-On Lab in a Separate Schema

This exercise creates standalone objects in a **lab schema**. Run it only with `CREATE TABLE`, index, sequence privileges, and sufficient quota—never in a production schema.

### 16.1. Create a Sample Invoice Lines Table

```sql
CREATE TABLE lab_invoice_lines (
    line_id NUMBER GENERATED BY DEFAULT ON NULL AS IDENTITY (
        START WITH 100
        INCREMENT BY 1
        CACHE 20
        NOCYCLE
    ) PRIMARY KEY,

    item_code VARCHAR2(30 CHAR) NOT NULL,
    quantity NUMBER(10,0) DEFAULT ON NULL 1 NOT NULL,
    unit_price NUMBER(14,2) NOT NULL,
    line_total GENERATED ALWAYS AS (
        quantity * unit_price
    ) VIRTUAL,

    status VARCHAR2(20 CHAR) DEFAULT 'DRAFT' NOT NULL,
    created_at TIMESTAMP(6) WITH TIME ZONE
        DEFAULT SYSTIMESTAMP NOT NULL,

    CONSTRAINT ck_lab_invoice_qty CHECK (quantity > 0),
    CONSTRAINT ck_lab_invoice_price CHECK (unit_price >= 0),
    CONSTRAINT ck_lab_invoice_status
        CHECK (status IN ('DRAFT', 'APPROVED', 'VOID'))
);
```

Design notes:

- `LINE_ID` is generated when omitted or passed as NULL.
- `QUANTITY` defaults to 1 when omitted or passed as NULL.
- `LINE_TOTAL` is derived from quantity and unit price.
- `STATUS` defaults to `DRAFT` when omitted, constrained to the allowed set.
- `CREATED_AT` captures creation time and is not virtual.
- Constraints protect domains across SQL Developer, JDBC, and ETL writes.

### 16.2. Insert Three Rows Using Three Patterns

```sql
-- Row 1: database generates ID; quantity uses default.
INSERT INTO lab_invoice_lines (
    item_code, unit_price
)
VALUES (
    'BOOK-001', 50000.00
);

-- Row 2: client passes NULL for ID and quantity.

    line_id, item_code, quantity, unit_price
)
VALUES (
    NULL, 'PEN-002', NULL, 12000.00
);

-- Row 3: explicit ID and explicit quantity supplied.

)
```

Query:

```sql
       unit_price,

       status,
```

Logical output:

| ITEM_CODE | LINE_ID | QUANTITY | UNIT_PRICE | LINE_TOTAL | STATUS |
|---|---|---:|---:|---:|---|
| BOOK-001 | Oracle-generated, e.g. 100 | 1 | 50000.00 | 50000.00 | DRAFT |
| PEN-002 | Oracle-generated, e.g. 101 | 1 | 12000.00 | 12000.00 | DRAFT |
| BAG-003 | 9000 | 2 | 150000.00 | 300000.00 | APPROVED |

Generated values 100/101 assume the generator had not previously issued values; do not treat sample IDs as guaranteed fixed outputs.

`LINE_TOTAL` becomes `48000.00` without any direct update to it.

## 17. Common Error Scenarios

| Symptom | Why It Happens | Resolution |
|---|---|---|
| `ORA-32795` when inserting into identity | Supplying an explicit value to `GENERATED ALWAYS` | Omit ID column from `INSERT` or choose the right identity mode |
| `ORA-01400` inserting NULL into `BY DEFAULT` identity | `BY DEFAULT` does not convert explicit NULL into a generated ID | Omit ID column or use `BY DEFAULT ON NULL` if intended |
| `ORA-00001` on identity primary key | Manual ID collision, unsynced generator after import, or duplicate data | Inspect data, generator state, and import process |
| `ORA-540xx` writing to virtual column | Attempting to insert/update virtual column or invalid expression | Write only source columns; check virtual expression restrictions |
| Virtual column value changes after UPDATE | Expression depends on source columns | Expected behavior; store a real column if a snapshot is required |
| Default ignored when client sends NULL | Standard `DEFAULT` applies only when column is omitted | Use `DEFAULT ON NULL` or fix client behavior |
| `UPDATED_AT` unchanged after UPDATE | `DEFAULT SYSTIMESTAMP` applies only at creation | Maintain update timestamps via DML/triggers |
| Gaps in IDs | Rollbacks, caching, concurrency, failed inserts | Normal behavior for sequences/identities |
| Index on virtual column not chosen | Optimizer favors full scan, or stats/selectivity differ | Inspect execution plans, statistics, and workload |
| Need to change a widely used virtual formula | Expression is part of the data contract | Analyze indexes, constraints, reports, and historical data |
| Using ID as creation timestamp | Sequences are not clocks | Store `CREATED_AT` with an explicit time contract |
| Importing large IDs then auto-inserts collide | Internal sequence does not auto-advance to `MAX(id)` on explicit inserts | Resync generator per Oracle version guidance |

Never diagnose from the error code alone: inspect the full Oracle message, live DDL, and executed SQL.

## 18. Design Principles for Java/JDBC Applications

### 18.1. Agree on "Who Owns" the Value

If Oracle declares an ID as `GENERATED ALWAYS`, the application must never generate IDs for that table. Configure ORMs to retrieve generated keys and exclude the ID column from `INSERT`s.

If an application needs both normal inserts and legacy ID imports:

- Consider `BY DEFAULT` or `BY DEFAULT ON NULL`.
- Restrict explicit ID inserts to controlled import workflows.
- Resync the identity generator after imports.
- Enforce primary key uniqueness and foreign keys.

### 18.2. Never Send Values for Virtual Columns

In DTOs/APIs, expose `line_total` as **read-only**; requests only supply `quantity` and `unit_price`. The database computes `line_total` per its definition, and the app reads it back via `SELECT` or `RETURNING` where available.

Even if a client sends `line_total`, never pass it into an `INSERT`/`UPDATE` on the virtual column. If business validation compares a client-submitted total against the server calculation, treat the client figure strictly as an assertion to validate, not a persisted source column.

### 18.3. Use PreparedStatement and Generated Keys

Example:

```java
String sql = """
    INSERT INTO lab_tickets (title)
    VALUES (?)
    """;

try (PreparedStatement ps =
         connection.prepareStatement(
             sql, new String[] {"TICKET_ID"}
         )) {
    ps.setString(1, "Support request");
    ps.executeUpdate();

    try (ResultSet keys = ps.getGeneratedKeys()) {
        if (keys.next()) {
            long ticketId = keys.getLong(1);
            System.out.println(ticketId);
        }
    }
}
```

Ensure a compatible Java/JDBC driver for the generated-keys syntax and manage connection/transaction boundaries in the outer layer.

### 18.4. Distinguish Missing Keys from Explicit NULL

In JSON APIs, there is a meaningful difference between:

```json
{}
```

and:

```json
{"id": null}
```

When an ORM builds an `INSERT`, those inputs can produce different SQL:

- Omitting the `ID` column from the insert.
- Binding `ID = NULL`.

With `BY DEFAULT`, the second fails; with `BY DEFAULT ON NULL`, it generates an ID. Define explicitly in your API/framework contract what sending `null` means.

### 18.5. Do Not Let Pre-COMMIT Generated IDs Mislead the App

An `INSERT` may generate and return an ID to Java, yet the transaction later rolls back. The application "saw" that ID, even though no row exists in the database afterward.

That is normal sequence/identity behavior. Therefore:

- Never report transaction completion merely because a generated ID was obtained.
- Distinguish "ID allocated" from "transaction committed."
- Use clean transaction boundaries and outbox/event-publishing patterns before emitting external notifications.

## 20. Decision Flow for Designing Oracle Table Columns

```text
Where does the column's value come from?
|
+-- Is it an expression over columns in the same row?
|      |
|      +-- Valid expression, recomputable on read,
|      |   no historical snapshot needed?
|      |        └── VIRTUAL COLUMN
|      |
|      +-- Must preserve finalized value or depends on
|          external sources?
|               └── Regular column + calculation in
|                   appropriate transaction/service
|
+-- Need a new numeric key on row insertion?
|      |
|      +-- Database generates exclusively?
|      |        └── GENERATED ALWAYS AS IDENTITY
|      |
|      +-- Explicit IDs allowed?
|      |        └── GENERATED BY DEFAULT AS IDENTITY
|      |
|      +-- Explicit IDs allowed, and NULL also requests a new ID?
|               └── GENERATED BY DEFAULT ON NULL AS IDENTITY
|
+-- Need an initial value for a regular column?
|      |
|      +-- Only when column is omitted?
|      |        └── DEFAULT
|      |
|      +-- When column is omitted or NULL is passed?
|               └── DEFAULT ON NULL
|
+-- Need a number generator shared beyond a single identity?
|               └── Standalone SEQUENCE
|
+-- Rule needs special DML logic not expressible
    via constraints/defaults/identity?
                └── Consider TRIGGER or application layer
```

Once chosen, also specify **data types, NULL semantics, unique/primary keys, transaction rules, and how JDBC retrieves generated values**. That ensures predictable behavior across concurrent sessions and applications.

## 21. Operational Takeaways

- **Virtual columns** represent derived data; no independent value is written directly into the table row like a regular column.
- **Identity columns** generate and **persist a numeric value** on insert, with three modes governing manual ID entry.
- **`GENERATED ALWAYS`** fits when the database has sole ownership of IDs.
- **`GENERATED BY DEFAULT`** allows client-supplied IDs, yet explicit NULL does not trigger generation.
- **`GENERATED BY DEFAULT ON NULL`** generates values both when the ID is omitted and when NULL is passed.
- **`DEFAULT`** initializes regular columns when omitted; **`DEFAULT ON NULL`** also handles NULL on insert.
- **Identity/sequence values do not guarantee gapless numbering, commit ordering, or row counts.**
- **Virtual columns can be indexed**, yet indexes carry storage/write overhead and the optimizer may choose another access path.
- **Never use virtual columns to replace immutable business snapshots** when formulas or source values can change.
- **Retrieve newly inserted IDs with `RETURNING` or `getGeneratedKeys()`**, never with `MAX(id)`.
- **After importing explicit IDs**, resync the generator to prevent collisions on subsequent auto-generated inserts.
- **Oracle version and JDBC driver differences affect syntax and metadata**, especially around identity adjustment options and complex virtual columns.
