# Recycle Bin, FLASHBACK DROP, and PURGE Behavior in Oracle

## 1. What is the recycle bin?

Oracle Database includes a **recycle bin** to retain certain DROPped tables, giving users the opportunity to recover a table with Flashback Drop without restoring the entire database from backups.

When an eligible table is DROPped while the recycle bin is enabled, Oracle renames the object to a system-generated name of the form BIN$..., while keeping its metadata and associated dependent objects. The table no longer appears under its old name in the schema, so users can create a new table with the same name. The old table's data continues to occupy space in the tablespace until it is purged or automatically purged by Oracle when space is needed.

Key concepts:

- **Recycle bin:** Storage for eligible DROPped tables and their dependent objects.
- **Flashback Drop:** Ability to recover a table from the recycle bin using the FLASHBACK TABLE ... TO BEFORE DROP statement.
- **PURGE:** Permanently removes an object from the recycle bin; Flashback Drop can no longer restore it.

The recycle bin is a rapid recovery convenience for accidental DROP operations. It is not a backup, does not protect against storage/database loss, and does not replace RMAN, Data Guard, or independent backups.

## 2. Lifecycle of a table after DROP

When a standard DROP TABLE is executed, Oracle checks the recycle bin and applicable conditions. If the table is eligible and the recycle bin is enabled, the object moves into the recycle bin instead of being physically deleted immediately.

~~~text
Active table
        |
        | DROP TABLE table_name
        v
Oracle checks recycle bin and eligibility conditions
        |
        +---- Recycle bin enabled, object eligible
        |                |
        |                v
        |        Renamed to BIN$...
        |                |
        |                v
        |        Eligible for FLASHBACK DROP
        |                |
        |        +-------+--------+
        |        |                |
        |        v                v
        |     Recover           PURGE
        |        |                |
        |        v                v
        |   Active table    Permanently deleted
        |
        +---- PURGE / recycle bin OFF / unsupported object
                         |
                         v
                  Removed bypassing recycle bin
~~~

Three states must be distinguished:

1. **Active table:** An object with its normal name in the schema.
2. **Table in recycle bin:** A DROPped object that can still be recovered if not yet purged and still meeting conditions.
3. **Purged table:** An object removed from the recycle bin; Flashback Drop cannot recover it.

### 2.1. DROP does not immediately free all space

When a table enters the recycle bin, its segments still exist and continue to occupy space in the tablespace. Therefore, dropping a large table does not necessarily increase free space immediately.

This is why a schema may report quota exhaustion even after dropping many tables. Check the recycle bin and purge objects that no longer need recovery.

### 2.2. Object names in the recycle bin

Object names in the recycle bin typically have the form:

~~~text
BIN$xxxxxxxxxxxxxxxxxxxxxxxx==$0
~~~

This is an internal name generated by Oracle. It is not the original business table name. The recycle bin also records the original name so users can look up and restore it.

A dropped table can be replaced by a new table with the same name. Consequently, the original name is not necessarily unique in the recycle bin: the same name may have multiple dropped versions from different points in time.

## 3. Enabling, disabling, and checking the recycle bin

### 3.1. Checking configuration

In SQL*Plus:

~~~sql
SHOW PARAMETER recyclebin;
~~~

Or:

~~~sql
SELECT name,
       value,
       isses_modifiable,
       issys_modifiable
FROM v$parameter
WHERE name = 'recyclebin';
~~~

The recycle bin is enabled by default in common Oracle Database configurations. However, always check the actual value in the running database/session.

### 3.2. Disabling the recycle bin for a session

~~~sql
ALTER SESSION SET recyclebin = OFF;
~~~

When the recycle bin is disabled in a session, tables dropped during that session are not retained in the recycle bin. Session-level disabling has a narrower scope than changing the database-wide configuration.

### 3.3. Disabling the recycle bin at system level

A DBA can modify the system parameter according to the modifiability supported by the release and environment:

~~~sql
ALTER SYSTEM SET recyclebin = OFF SCOPE = BOTH;
~~~

If the environment does not allow the chosen SCOPE, check parameter modifiability and SPFILE/PFILE configuration per administrative procedure. Do not make system-wide changes merely to handle a single accidental DROP.

### 3.4. Re-enabling the recycle bin

~~~sql
ALTER SESSION SET recyclebin = ON;
~~~

Or the DBA re-enables it at system level with the appropriate configuration. Re-enabling does not restore objects that were purged while the recycle bin was disabled.

### 3.5. Disabling the recycle bin is not PURGE

Disabling the recycle bin affects how objects dropped after the change are handled. It does not automatically purge objects that were already in the recycle bin beforehand.

To remove existing objects from the recycle bin, use the PURGE command with the appropriate scope.

## 4. Viewing objects in the recycle bin

### 4.1. SHOW RECYCLEBIN

In SQL*Plus:

~~~sql
SHOW RECYCLEBIN;
~~~

This command displays objects in the current user's recycle bin, typically showing the system name, original name, object type, and drop time.

### 4.2. USER_RECYCLEBIN

To query with SQL:

~~~sql
SELECT object_name,
       original_name,
       operation,
       type,
       ts_name,
       droptime,
       can_undrop,
       can_purge
FROM user_recyclebin
ORDER BY droptime DESC;
~~~

Commonly used columns:

| Column | Meaning |
| --- | --- |
| OBJECT_NAME | System name in the recycle bin, typically starting with BIN$ |
| ORIGINAL_NAME | Object name prior to DROP |
| OPERATION | Operation that placed the object into the recycle bin |
| TYPE | Object type |
| TS_NAME | Tablespace containing the object |
| DROPTIME | Timestamp of DROP |
| CAN_UNDROP | Whether the object can be restored |
| CAN_PURGE | Whether the object can be purged |
| BASE_OBJECT | Identifier of the associated base object |
| RELATED | Relationship to dependent objects |

Column names and availability can vary by view/release. Consult the data dictionary reference for your exact release when full verification is needed.

### 4.3. RECYCLEBIN synonym

RECYCLEBIN is a convenient synonym for viewing the current user's recycle bin in supported SQL tools:

~~~sql
SELECT object_name,
       original_name,
       type,
       droptime
FROM recyclebin
ORDER BY droptime DESC;
~~~

### 4.4. DBA_RECYCLEBIN

A DBA can inspect the recycle bin across multiple schemas using DBA_RECYCLEBIN with appropriate dictionary privileges:

~~~sql
SELECT owner,
       object_name,
       original_name,
       type,
       ts_name,
       droptime,
       can_undrop,
       can_purge
FROM dba_recyclebin
ORDER BY owner, droptime DESC;
~~~

This view is useful when investigating database-wide space usage or identifying which objects hold segments in a tablespace.

### 4.5. Distinguishing main objects from dependent objects

When dropping a table, Oracle may place associated dependent objects into the recycle bin as well, such as indexes and certain table-bound objects. As a result, a single table can generate multiple rows in USER_RECYCLEBIN.

Do not treat every row in the recycle bin as a separate business table. Use TYPE, ORIGINAL_NAME, RELATED, and BASE_OBJECT to distinguish base objects from dependent objects.

## 5. FLASHBACK DROP: recovering a DROPped table

### 5.1. Basic syntax

~~~sql
FLASHBACK TABLE table_name
TO BEFORE DROP;
~~~

Example:

~~~sql
FLASHBACK TABLE employees
TO BEFORE DROP;
~~~

Oracle locates the matching table version in the recycle bin and restores it to the schema under its original name if that name is still available.

### 5.2. Recovering with a new name

If a new table was already created with the same name, or if you want to keep both the new and old versions, use RENAME TO:

~~~sql
FLASHBACK TABLE employees
TO BEFORE DROP
RENAME TO employees_recovered;
~~~

The old table is restored as EMPLOYEES_RECOVERED. The new name must be valid and must not conflict with existing objects in the schema.

### 5.3. Recovering a specific version by recycle bin name

If a table with the same name was dropped multiple times, the recycle bin may hold multiple versions. You can specify the exact system name of the object to recover:

~~~sql
SELECT object_name,
       original_name,
       droptime
FROM user_recyclebin
WHERE original_name = 'EMPLOYEES'
ORDER BY droptime DESC;
~~~

After identifying the right BIN$ name:

~~~sql
FLASHBACK TABLE "BIN$xxxxxxxxxxxxxxxx==$0"
TO BEFORE DROP
RENAME TO employees_older;
~~~

The BIN$ name must be enclosed in double quotes because of special characters and Oracle-generated casing. Never guess system names; retrieve the exact string from USER_RECYCLEBIN or DBA_RECYCLEBIN.

### 5.4. When multiple versions share the same original name

If you do not specify a recycle bin name, Oracle selects the matching object according to default rules—typically the most recent recoverable version. To avoid restoring the wrong version:

1. Query USER_RECYCLEBIN.
2. Compare ORIGINAL_NAME and DROPTIME.
3. Check TYPE and related objects.
4. Use the specific OBJECT_NAME in FLASHBACK TABLE.
5. Specify RENAME TO if the original name is already taken or if both versions must be kept.

### 5.5. Restoring dependent objects

When a table is restored, Oracle also restores dependent objects retained with the table in the recycle bin, such as related indexes and triggers. However, dependent object names may need to be checked if their old names were reused by new objects or collide.

After Flashback Drop, verify:

~~~sql
SELECT index_name,
       index_type,
       status
FROM user_indexes
WHERE table_name = 'EMPLOYEES_RECOVERED';

SELECT trigger_name,
       status
FROM user_triggers
WHERE table_name = 'EMPLOYEES_RECOVERED';

SELECT constraint_name,
       constraint_type,
       status
FROM user_constraints
WHERE table_name = 'EMPLOYEES_RECOVERED';
~~~

The table name in these queries must match the restored name. If the table was restored under its original name, replace EMPLOYEES_RECOVERED with EMPLOYEES.

### 5.6. Privileges on the restored table

Grants attached to the table are stored with the object in the recycle bin and can be restored by the Flashback Drop mechanism. After restoring, check object privileges via USER_TAB_PRIVS or DBA_TAB_PRIVS to verify actual state.

Do not assume every dependency outside the table is automatically rebuilt. Specifically, if DROP used CASCADE CONSTRAINTS and removed foreign key constraints on other tables, inspect and handle those related constraints under a separate plan.

## 6. Prerequisites and limitations of FLASHBACK DROP

Flashback Drop only works while the object still exists in the recycle bin and Oracle can still restore it.

Cases where Flashback Drop cannot be relied upon:

- The table has been purged.
- The table was dropped with PURGE.
- The recycle bin was disabled at the time of DROP.
- The object is not in a category supported by the recycle bin.
- The object in the recycle bin was automatically purged by Oracle to free space.
- The tablespace containing the object was dropped or is no longer available.
- The object falls under special exclusions from the recycle bin per Oracle rules, such as SYS-owned objects or tables in the SYSTEM tablespace.

The recycle bin primarily supports tables and dependent objects. Not every schema object type—such as packages, procedures, sequences, or users—can be recovered via FLASHBACK TABLE ... TO BEFORE DROP.

### 6.1. SYS objects and the SYSTEM tablespace

Do not rely on the recycle bin as a recovery mechanism for SYS system objects. Tables in the SYSTEM tablespace and Oracle-excluded objects are not protected in the standard way.

Place application tables in appropriate application tablespaces rather than SYSTEM.

### 6.2. Clustered tables

Tables belonging to a cluster have specific limitations regarding the recycle bin/Flashback Drop. Do not assume a clustered table can be recovered like a standard heap table.

### 6.3. Objects that were purged or auto-purged

Once an object has been purged, recycle bin metadata can no longer support Flashback Drop. Switch to an appropriate recovery method such as RMAN restore/recover, an auxiliary database, or another backup.

### 6.4. Original name already taken

If a new object has already been created with the original name, Flashback Drop cannot simply overwrite the new object. Use RENAME TO to restore the old object under a different name, then compare data and decide on merging/renaming.

### 6.5. Quota and tablespaces

A restored table requires an available tablespace and sufficient space/quota. Verify the owner's quota and tablespace status before restoring, especially when an object has stayed in the recycle bin for a long time or storage has changed.

### 6.6. Flashback Drop does not recover TRUNCATEd data

TRUNCATE TABLE does not move the table into the recycle bin. It keeps the object while removing data according to DDL semantics. FLASHBACK TABLE ... TO BEFORE DROP is not a tool for recovering truncated rows.

If a table was truncated by mistake, evaluate backup/recovery, Flashback Database, or another recovery solution suited to the database state.

## 7. PURGE: permanently deleting objects in the recycle bin

PURGE removes objects from the recycle bin and frees their corresponding segments once Oracle completes processing. After a purge, Flashback Drop cannot restore that object.

### 7.1. Purging a single table

~~~sql
PURGE TABLE employees;
~~~

This command purges the object in the recycle bin matching the original name in the current schema. If multiple versions share the same name, inspect the recycle bin and specify the system name to target the exact object.

### 7.2. Purging by system name

~~~sql
PURGE TABLE "BIN$xxxxxxxxxxxxxxxx==$0";
~~~

Use this when multiple dropped versions share the same original name or when you want to purge one exact object.

### 7.3. Purging an index

~~~sql
PURGE INDEX old_employee_idx;
~~~

This applies to an index currently in the recycle bin. If an index is a dependent object of a table in the recycle bin, purging the table may also purge its dependent objects.

### 7.4. Purging the current user's recycle bin

~~~sql
PURGE RECYCLEBIN;
~~~

This command purges objects in the current user's recycle bin. Use it only when the user confirms Flashback Drop is no longer needed for any retained object.

### 7.5. Purging by tablespace

~~~sql
PURGE TABLESPACE users;
~~~

You can specify a user to restrict the scope within the tablespace:

~~~sql
PURGE TABLESPACE users USER app_owner;
~~~

This is a tablespace-scoped operation and may delete more objects than a single specific table. Check DBA_RECYCLEBIN before running.

### 7.6. Purging the database-wide recycle bin

~~~sql
PURGE DBA_RECYCLEBIN;
~~~

This is a database-wide administrative operation requiring special administrative privileges per Oracle rules. It can delete objects from the recycle bins of multiple schemas. Do not use it in place of a single user's PURGE RECYCLEBIN.

### 7.7. DROP TABLE ... PURGE

When you are certain Flashback Drop will not be needed:

~~~sql
DROP TABLE employees PURGE;
~~~

The table is dropped and purged directly rather than placed into the recycle bin. This decision cannot be reversed using Flashback Drop.

## 8. Comparing DROP, FLASHBACK DROP, PURGE, and TRUNCATE

| Operation | Does the table still exist under its old name? | Does data remain in the table? | Recycle bin | Recoverable via Flashback Drop? |
| --- | --- | --- | --- | --- |
| DROP TABLE | No | Table is retained if eligible | May be present | Yes, while object remains in recycle bin |
| DROP TABLE ... PURGE | No | No | No | No |
| FLASHBACK TABLE ... TO BEFORE DROP | Yes, under original or new name | Table data is restored | Object is removed from recycle bin | No longer an object in recycle bin |
| PURGE TABLE | No | No | Object removed from recycle bin | No |
| TRUNCATE TABLE | Yes | Rows are removed | Does not place table in recycle bin | Cannot use Flashback Drop |
| DELETE FROM table | Yes | Rows deleted transactionally | No | Can ROLLBACK before COMMIT; Flashback Query/Table options may apply depending on retention |

### 8.1. DROP TABLE

~~~sql
DROP TABLE employees;
~~~

If the table is eligible and the recycle bin is enabled, Oracle retains the object in the recycle bin.

### 8.2. DROP TABLE PURGE

~~~sql
DROP TABLE employees PURGE;
~~~

Bypasses the recycle bin for the dropped table. Cannot be recovered using FLASHBACK TABLE ... TO BEFORE DROP.

### 8.3. TRUNCATE TABLE

~~~sql
TRUNCATE TABLE employees;
~~~

TRUNCATE is DDL; it does not place the table into the recycle bin and cannot be rolled back like DELETE. The table remains, but the data is removed. Do not confuse TRUNCATE with DROP.

### 8.4. DELETE FROM

~~~sql
DELETE FROM employees
WHERE department_id = 50;

ROLLBACK;
~~~

DELETE is DML and can be rolled back before COMMIT. After COMMIT, Flashback Query/Flashback Table or media recovery may be options depending on configuration and retention; the recycle bin is not involved.

## 9. Automatic purge under space pressure

The recycle bin does not guarantee indefinite retention. When a tablespace needs space for new allocations, Oracle can automatically purge objects in that tablespace's recycle bin to free extents.

This means:

- A table dropped yesterday might no longer be in the recycle bin today if the tablespace needed space.
- A large table in the recycle bin can be auto-purged before users have a chance to restore it.
- The recycle bin cannot be treated as long-term storage.
- Long-term recoverability requires a proper backup/recovery strategy.

### 9.1. Space pressure and quota

Objects in the recycle bin continue to occupy tablespace space. When a schema is near its quota limit, dropping a table does not necessarily free enough quota to create a new object. Controlled purging of eligible objects can release extents.

### 9.2. Monitoring tablespace capacity

Example checking datafiles:

~~~sql
SELECT tablespace_name,
       ROUND(SUM(bytes) / 1024 / 1024, 2) AS allocated_mb
FROM dba_data_files
GROUP BY tablespace_name
ORDER BY tablespace_name;
~~~

Checking free extents:

~~~sql
SELECT tablespace_name,
       ROUND(SUM(bytes) / 1024 / 1024, 2) AS free_mb
FROM dba_free_space
GROUP BY tablespace_name
ORDER BY tablespace_name;
~~~

Both queries require appropriate dictionary privileges. With bigfile tablespaces, autoextend, ASM, and quotas, inspect additional datafile/storage metrics rather than relying solely on total allocated/free space.

### 9.3. Finding recycle bin objects consuming space

Recycle bin views provide object metadata; to investigate space usage in detail, you can join DBA_RECYCLEBIN with segment metadata by object name where privileges and views allow:

~~~sql
SELECT r.owner,
       r.object_name,
       r.original_name,
       r.type,
       r.ts_name,
       r.droptime,
       s.bytes
FROM dba_recyclebin r
LEFT JOIN dba_segments s
  ON s.owner = r.owner
 AND s.segment_name = r.object_name
ORDER BY s.bytes DESC NULLS LAST;
~~~

Segment naming and how dependent objects are stored may prevent this simple join from capturing 100% of a table's space usage. Inspect related objects and aggregate by base object when accurate reporting is required.

### 9.4. Do not rely on a fixed retention period

The recycle bin does not have a fixed-day retention window. How long an object survives depends on space pressure, allocation activity, and DBA purges. If business rules require retaining dropped tables for 30 days, implement a dedicated backup/export workflow rather than relying on the recycle bin.

## 10. Workflow for recovering an accidentally DROPped table

When an accidental DROP TABLE is discovered, avoid creating new objects or purging until you have assessed the situation.

### Step 1. Identify schema and table name

~~~sql
SHOW USER;

SELECT object_name,
       original_name,
       type,
       droptime,
       can_undrop,
       can_purge
FROM user_recyclebin
WHERE original_name = 'EMPLOYEES'
ORDER BY droptime DESC;
~~~

If the table belongs to another schema, the DBA checks DBA_RECYCLEBIN.

### Step 2. Identify the right version

Compare DROPTIME, OBJECT_NAME, and dependent objects. If multiple versions share the same name, select the exact BIN$ name rather than referencing the original name ambiguously.

### Step 3. Check target name availability

~~~sql
SELECT object_name,
       object_type
FROM user_objects
WHERE object_name IN ('EMPLOYEES', 'EMPLOYEES_RECOVERED');
~~~

If the original name is already in use, pick another recovery name.

### Step 4. Check tablespace and quota

Verify the owner still has privileges/quota and the tablespace remains available. If the object to recover resides in an unavailable tablespace, follow storage/DBA recovery procedures.

### Step 5. Execute Flashback Drop

~~~sql
FLASHBACK TABLE employees
TO BEFORE DROP
RENAME TO employees_recovered;
~~~

If there is no name collision and you want to restore under the original name, omit RENAME TO.

### Step 6. Verify the data

~~~sql
SELECT COUNT(*)
FROM employees_recovered;

SELECT *
FROM employees_recovered
FETCH FIRST 10 ROWS ONLY;
~~~

Check row counts, keys, sample data, and business requirements. If the table was restored under a different name, inspect views/procedures/application references expecting the original name.

### Step 7. Check dependent objects and grants

~~~sql
SELECT index_name, status
FROM user_indexes
WHERE table_name = 'EMPLOYEES_RECOVERED';

SELECT constraint_name, constraint_type, status
FROM user_constraints
WHERE table_name = 'EMPLOYEES_RECOVERED';

SELECT trigger_name, status
FROM user_triggers
WHERE table_name = 'EMPLOYEES_RECOVERED';
~~~

Inspect object privileges, synonyms, views, procedures, and foreign keys from other tables. Rebuild/recreate dependencies that were not automatically restored or were altered by the DROP operation.

### Step 8. Purge unneeded versions only after verification

Only after confirming the table is properly restored and dependencies work, purge remaining dropped versions if they are no longer needed. Avoid running PURGE RECYCLEBIN at the start of the workflow.

## 11. Complete hands-on example

The lab below creates a table, DROPps it, inspects the recycle bin, restores it, handles a name collision, and PURGEs. Run in a test schema.

### 11.1. Create the table

~~~sql
CREATE TABLE recycle_lab_orders (
    order_id NUMBER PRIMARY KEY,
    customer_name VARCHAR2(100) NOT NULL,
    amount NUMBER(12,2)
);

INSERT INTO recycle_lab_orders
VALUES (1, 'Customer A', 120);

INSERT INTO recycle_lab_orders
VALUES (2, 'Customer B', 250);

COMMIT;
~~~

### 11.2. DROP the table

~~~sql
DROP TABLE recycle_lab_orders;
~~~

If the recycle bin is enabled and the table is eligible, it will appear in the recycle bin.

### 11.3. Inspect the recycle bin

~~~sql
SELECT object_name,
       original_name,
       type,
       droptime,
       can_undrop
FROM user_recyclebin
WHERE original_name = 'RECYCLE_LAB_ORDERS'
ORDER BY droptime DESC;
~~~

Record the Oracle-generated OBJECT_NAME.

### 11.4. Restore using the original name

~~~sql
FLASHBACK TABLE recycle_lab_orders
TO BEFORE DROP;
~~~

Check:

~~~sql
SELECT *
FROM recycle_lab_orders
ORDER BY order_id;
~~~

### 11.5. DROP again and create a new table with the same name

~~~sql
DROP TABLE recycle_lab_orders;

CREATE TABLE recycle_lab_orders (
    order_id NUMBER PRIMARY KEY,
    note VARCHAR2(100)
);
~~~

The new table now occupies the original name. The older version can still reside in the recycle bin.

### 11.6. Restore the old version under another name

~~~sql
FLASHBACK TABLE recycle_lab_orders
TO BEFORE DROP
RENAME TO recycle_lab_orders_old;
~~~

Inspect both tables:

~~~sql
SELECT * FROM recycle_lab_orders;
SELECT * FROM recycle_lab_orders_old ORDER BY order_id;
~~~

The new table and restored table coexist under two different names.

### 11.7. Purge the old object

~~~sql
PURGE TABLE recycle_lab_orders_old;
~~~

If the object to purge still sits in the recycle bin under its system name, query USER_RECYCLEBIN and specify the exact BIN$ name.

### 11.8. Clean up the lab

~~~sql
DROP TABLE recycle_lab_orders PURGE;
DROP TABLE recycle_lab_orders_old PURGE;
~~~

If a table was already purged in the previous step, its corresponding DROP may no longer be needed. Run cleanup only for identified lab objects—never on business objects.

## 12. Privileges and administrative scope

### 12.1. User restoring their own table

Typically, an owner can view their own recycle bin, restore tables in their own schema, and purge their own objects by ownership privilege.

### 12.2. DBA restoring another schema's object

To act on another schema's objects, appropriate administrative privileges are needed, such as FLASHBACK ANY TABLE and dictionary privileges to inspect the database-wide recycle bin. Do not grant such broad privileges to an application user just to recover one table.

### 12.3. DBA_RECYCLEBIN and PURGE DBA_RECYCLEBIN

DBA_RECYCLEBIN lets administrators inspect recycle bin objects across owners. PURGE DBA_RECYCLEBIN is a database-wide operation requiring special administrative privilege. Evaluate impact across all schemas before executing.

### 12.4. Privileges on restored objects

After recovery, re-verify:

- Object owner and table name.
- Indexes, triggers, constraints.
- Object privilege grants.
- Synonyms and dependencies.
- Views/procedures/packages referencing the table.
- Related application accounts and roles.

Do not assume the application works properly just because FLASHBACK TABLE succeeded.

## 13. Security and data lifecycle governance

The recycle bin can retain data after users think a table was deleted. This matters for sensitive data and retention policies:

- DROP TABLE does not mean data has been permanently erased from database storage.
- Users with appropriate privileges can restore the table from the recycle bin.
- Objects in the recycle bin continue to occupy storage.
- Oracle may auto-purge under space demand, so long-term retention is not guaranteed.
- PURGE eliminates Flashback Drop recoverability and must be governed by policy.

For sensitive data, enforce data retention, encryption, access control, and purge procedures aligned with legal/business requirements. Do not treat a standard DROP as a secure erase.

### 13.1. Distinguishing purge from backup retention

PURGE removes an object from the recycle bin in the current database. It does not automatically delete RMAN backups or exports stored elsewhere. If data deletion is required across all copies, establish a dedicated process covering backups, replicas, standbys, exports, and storage lifecycles.

### 13.2. Controlling PURGE

In production:

1. Only the responsible data owner approves purges.
2. Identify owner, original name, object name, and tablespace.
3. Verify the object is not being held for recovery.
4. Check dependent objects and applications.
5. Verify command scope: single table, tablespace, user, or entire database.
6. Record the change per audit/change management.
7. Verify space usage after purging.

## 14. Common errors and troubleshooting

| Symptom/error | Possible cause | Resolution |
| --- | --- | --- |
| FLASHBACK TABLE cannot find object | Table not in recycle bin, recycle bin OFF at DROP, or object already purged | Check USER_RECYCLEBIN/DBA_RECYCLEBIN and alerts/history |
| ORA-38305: object not in RECYCLE BIN | Object is no longer in recycle bin or wrong name | Re-query recycle bin and identify exact object |
| ORA-38312: original name is used by an existing object | Original name already taken by another table/object | Use RENAME TO with an unused target name |
| ORA-38301: can not perform DDL/DML over objects in Recycle Bin | Attempting unsupported direct DDL/DML on a recycle bin object | Restore first using FLASHBACK TABLE |
| FLASHBACK DROP cannot restore table | Unsupported object, already purged, or tablespace unavailable | Check recycle bin limits and RMAN options |
| Table dropped but space did not decrease | Segments still reside in recycle bin | Inspect recycle bin and purge unneeded objects |
| Cannot create new table due to quota | Dropped objects still consume quota/tablespace | Check quota and purge under control |
| Table restored but application fails | Dependencies, grants, synonyms, or object name changed | Verify indexes/constraints/triggers/grants and recompile dependencies |
| Object missing from SHOW RECYCLEBIN | Logged in as wrong owner or object was not recycled | Check SHOW USER and DBA_RECYCLEBIN |
| Object disappeared from recycle bin | Likely auto-purged due to tablespace pressure or manually purged | Switch to backup/recovery if needed |

Error messages and behavior depend on release, object type, and recycle bin state. Read the full Oracle error message rather than relying solely on the error code in the table.

## 15. Checklist before FLASHBACK DROP or PURGE

1. **Right database/PDB/schema?** Confirm environment and owner.
2. **Was the recycle bin enabled during DROP?** Check parameters and operation history.
3. **Is the object still in the recycle bin?** Query USER_RECYCLEBIN or DBA_RECYCLEBIN.
4. **Was the right version selected?** Compare ORIGINAL_NAME, OBJECT_NAME, and DROPTIME.
5. **Is the target name already taken?** Use RENAME TO if needed.
6. **Are tablespace and quota still available?** Confirm restore feasibility.
7. **Which dependent objects must be checked?** Indexes, triggers, constraints, and grants.
8. **Are there foreign keys on other tables?** Especially if DROP used CASCADE CONSTRAINTS.
9. **Could auto-purge happen?** The recycle bin is not long-term retention.
10. **Is the PURGE scope right?** Single object, user recycle bin, tablespace, or entire database.
11. **Do backups need to be kept?** The recycle bin does not replace RMAN.
12. **Was data verified after restore?** Check row counts and business records.
13. **Were application dependencies checked?** Views, synonyms, stored code, and grants.
14. **Is the purge approved?** Purge cannot be undone via Flashback Drop.
15. **Was the action documented?** Record operator, timestamp, object, and reason.

**Principle to remember:** DROP TABLE can place a table in the recycle bin; FLASHBACK TABLE ... TO BEFORE DROP restores retained objects; PURGE permanently removes them so Flashback Drop can no longer restore them. The recycle bin can be auto-purged by Oracle when a tablespace needs space, so it is not a long-term backup archive. Before restoring, identify the exact version and check dependencies; before purging, verify scope and recovery requirements.
