# Limitations of Cost and Avoiding Conclusions from a Single Plan Snapshot

An execution plan is vital evidence when analyzing SQL performance, yet a single plan snapshot tells only part of the story. It shows how Oracle intended or chose to organize operations in one specific context. It does not by itself prove whether a SQL statement runs fast or slow, does not capture overall system load at runtime, and does not represent every execution across different bind values.

Likewise, cost in an execution plan is an internal estimate used by the optimizer to compare candidate plans. Cost is not milliseconds, not actual blocks read, and not a performance score you can arbitrarily compare across different systems, points in time, or SQL statements.

To reach reliable conclusions, combine the plan with runtime statistics, bind values, cursor identity, data statistics, session environment, and workload context. Observe multiple representative executions, identify what changed, and measure impact before modifying SQL, indexes, or optimizer settings.

## 1. What Does Cost Represent?

Cost is a value computed by Oracle's cost model during optimization. The optimizer uses cost to compare feasible plans against the active optimization goal. The model may factor in blocks to read, I/O type, CPU, cardinality, row width, memory eligibility, parallel execution, and system statistics.

Cost has important properties:

- It is an estimate, not a post-execution measurement.
- It depends on statistics, optimizer parameters, and the environment used at parse time.
- It is meaningful primarily for comparing alternatives within the same optimization problem.
- It can change when statistics, database version, parameters, binds, or metadata change.
- It does not directly express elapsed time, CPU seconds, logical reads, or physical reads.

For example, a cost of 500 does not mean the SQL takes 500 ms. Nor is a SQL statement with cost 500 in Environment A inherently slower than a SQL statement with cost 200 in Environment B. Two systems have different CPUs, storage, caches, system statistics, parallel policies, and workloads.

### 1.1 Why Doesn't Low Cost Guarantee Low Execution Time?

Cost is calculated from assumptions and information available at optimization time. Actual execution can be affected by:

- Whether the buffer cache is warm or cold.
- Other sessions contending for CPU, I/O, latches, locks, or memory.
- Storage latency fluctuating over time.
- Actual row counts differing from estimated cardinality.
- Actual bind values differing from the bind value used at parse time.
- Hash joins or sorts spilling to TEMP.
- Parallel workers lacking resources or experiencing data skew.
- Slow client fetching or fetching only partial results.
- Network latency between the application and the database.

A low-cost plan can take a long time when blocked on I/O or locks. Conversely, a higher-cost plan can finish quickly on a specific run thanks to cached data and an idle system.

### 1.2 Cost Can Change Without Much Change in Actual Performance

After gathering statistics, the optimizer may produce different cardinality or cost estimates than before. The plan may still keep the same operations and join order. If actual runtime and buffer gets remain nearly unchanged, a mere shift in cost does not prove a problem.

On the other hand, a small shift in cost can tip the optimizer into a different access path or join order. In that case, measure the actual impact of the new plan rather than looking only at whether cost went up or down.

### 1.3 Cost Is Not a Metric for Ranking All SQL Statements

Do not sort every SQL statement in a system by cost and label the highest-cost queries as the slowest ones. One SQL statement might run once a day, whereas a low-cost SQL statement might execute tens of thousands of times per minute.

To identify heavy-load SQL, evaluate execution count, total CPU, total elapsed time, logical reads, physical reads, wait time, rows processed, and business criticality to users.

## 2. What Does an Execution Plan Tell You?

An execution plan depicts the operation tree Oracle intends to use or used for a cursor. Depending on how the plan is retrieved, it may be:

- **Estimated plan:** a plan generated by running EXPLAIN PLAN; that action does not execute the SQL.
- **Cursor plan:** a plan attached to a child cursor in the shared pool.
- **Adaptive plan:** a plan containing alternative branches that Oracle resolves at runtime.
- **Runtime plan statistics:** row counts, operation start counts, buffer gets, reads, and elapsed time collected during execution, if appropriate collection was enabled.

A typical plan can reveal:

- The access path for each table/index.
- Join order and join methods.
- Predicates used for access or filtering.
- Estimated cardinality.
- Estimated cost.
- Partition pruning and parallel operations if present.
- Notes on dynamic statistics, adaptive behavior, or optimizer environment.

It does not necessarily reveal:

- Time spent waiting on locks, network, or clients.
- Bind values for every execution.
- Resource contention at runtime.
- Actual row counts if row-source statistics were not collected.
- Complete history of prior executions.
- Why another cursor for the same SQL text received a different plan.
- End-to-end application cost, including processing time outside the database.

Therefore, a plan snapshot is a cross-section of one cursor at one moment, not a complete profile of the SQL over its entire lifecycle.

## 3. Distinguishing EXPLAIN PLAN from the Actual Cursor Plan

EXPLAIN PLAN asks Oracle to generate an estimated plan and write it into a plan table. It does not execute the explained SQL statement.

Example:

~~~sql
EXPLAIN PLAN FOR
SELECT order_id, order_date
FROM orders
WHERE status = 'RETURNED';

SELECT *
FROM TABLE(DBMS_XPLAN.DISPLAY);
~~~

The output helps show which access path the optimizer might choose in the EXPLAIN PLAN command's context. However, it can differ from the application's plan because of:

- Different bind datatypes and bind values.
- Different session parameters.
- Different current schema, synonyms, or object resolution.
- Different optimizer environment.
- The application cursor having been parsed earlier with a different bind value.
- Multiple child cursors.
- Statistics or metadata changing between the two parses.
- Adaptive plans or runtime feedback not yet reflected.

When analyzing SQL that has already run, inspect the actual cursor via `DBMS_XPLAN.DISPLAY_CURSOR`. Identify the exact `SQL_ID` and child number when multiple child cursors exist.

~~~sql
SELECT *
FROM TABLE(
  DBMS_XPLAN.DISPLAY_CURSOR(
    sql_id          => 'SQL_ID_HERE',
    cursor_child_no => 0,
    format          => 'TYPICAL +PREDICATE +ALIAS +NOTE'
  )
);
~~~

Replace the placeholder `SQL_ID` and child number with real values. If you pass `NULL` for `SQL_ID` and child number, `DBMS_XPLAN` typically picks the most recent cursor in the current session; that approach is unsuitable for investigating a cursor executed from a separate application session.

### 3.1 SQL_ID Does Not Mean a Single Plan

`SQL_ID` identifies a normalized SQL statement under Oracle's mechanism. One `SQL_ID` can have multiple child cursors. Each child cursor can have its own plan hash value and execution plan.

Reasons multiple child cursors can exist include:

- Different bind metadata or bind sensitivity.
- Different optimizer environments.
- Different object or privilege metadata.
- Certain differences in NLS, schema, or session settings.
- Cursor sharing incompatibilities.
- Adaptive cursor sharing creating plans suited to different bind value ranges.

When a report lists only `SQL_ID` without child number, plan hash value, and observation timestamp, conclusions about the plan can be inaccurate.

### 3.2 PLAN_HASH_VALUE Also Has Limitations

`PLAN_HASH_VALUE` is a hash value helpful for identifying and comparing plan structure in many situations. It is useful for spotting plan changes, yet it is not a complete signature of every execution characteristic.

Do not rely on plan hash as sole proof that two runs have identical or different performance. Certain details, runtime conditions, bind values, adaptive choices, or execution environments can differ even when plan hashes match. Conversely, a different plan hash does not automatically prove the new plan is worse.

## 4. Cardinality Estimates Can Be Wrong

The optimizer must predict how many rows pass through each operation before the SQL statement executes. Wrong cardinality can skew both cost and plan selection.

Common causes include:

- Stale or missing table/column statistics.
- Skewed data without appropriate histograms.
- Filter predicates across correlated columns.
- Expressions or functions that complicate estimation models.
- Bind values with widely varying selectivity.
- Newly inserted data falling outside recorded statistics bounds.
- Non-uniform distribution on join keys.
- Partition/global statistics not reflecting actual data.
- Dynamic statistics or feedback not applying to that case.

For instance, suppose `ORDERS` has 10 million rows. Status `NEW` accounts for 70%, while `RETURNED` accounts for 0.1%. If the optimizer estimates both statuses as uniformly distributed, the ideal access path for each bind value can differ dramatically from reality.

An `EXPLAIN PLAN` using literal `RETURNED` does not represent an application run binding `NEW`. Even with identical SQL text, bind peeking and adaptive cursor sharing can produce different child cursors.

### 4.1 E-Rows and A-Rows

When runtime row-source statistics are available, `DBMS_XPLAN` can show:

- **E-Rows:** estimated row count.
- **A-Rows:** actual rows returned by the operation in the profiled run.
- **Starts:** number of times the operation started.
- **Buffers:** logical reads / buffer gets.
- **Reads:** recorded physical reads.
- **A-Time:** actual time per collected metrics and format.

To collect metrics for a test run:

~~~sql
SELECT /*+ gather_plan_statistics */
       order_id, order_date
FROM orders
WHERE status = :status;
~~~

After running and fetching results, inspect in the same session:

~~~sql
SELECT *
FROM TABLE(
  DBMS_XPLAN.DISPLAY_CURSOR(
    NULL,
    NULL,
    'ALLSTATS LAST +PEEKED_BINDS +PREDICATE +ALIAS +NOTE'
  )
);
~~~

`ALLSTATS LAST` is meaningful only when row-source statistics were collected for the target execution. The `gather_plan_statistics` hint provides controlled collection for a test query; other statistics settings can be used per environment policy.

### 4.2 Reading Discrepancies Properly

If `E-Rows` is 10 while `A-Rows` is 100,000, the operation returned far more rows than estimated. This can force upper operations to process much more data than projected.

However, on the inner side of nested loops, an operation can start many times. Read `A-Rows` alongside `Starts` and the plan structure, avoiding comparing two raw numbers without understanding how counts accumulate.

Locate the first operation with a major discrepancy from bottom to top. Skew at a lower operation can propagate up the entire branch. Simply forcing a join method at the top operation can mask symptoms without fixing the root cause.

### 4.3 A-Rows Still Does Not Tell the Whole Story

`A-Rows` describes how many rows flowed through an operation during the measured run. It does not replace metrics for wait time, network, locks, CPU contention, or client processing time after fetching.

An operation with low `A-Rows` can still take a long time due to slow I/O or resource waits. An operation with high `A-Rows` can run quickly if data is cached and processing is lightweight.

## 5. A Plan Snapshot Is Bounded by Time

A plan belongs to a cursor created in a specific context. Afterward, the environment can change:

- Statistics are gathered or published.
- Indexes are created, rebuilt, made invisible, or dropped.
- Tables are partitioned, exchanged, or experience bulk data changes.
- Optimizer parameters change.
- New bind values trigger a new child cursor.
- Cursors are invalidated and hard-parsed again.
- The database is upgraded or optimizer feature levels change.
- A SQL Profile, SQL Patch, or SQL Plan Baseline is applied.
- Sessions switch to a different service/module/action.
- Adaptive cursor sharing or statistics feedback changes optimization on subsequent runs.

Therefore, a screenshot taken yesterday does not prove the current plan is unchanged. Likewise, a snapshot taken right after a single test run does not represent every bind value or every peak-load period.

When archiving evidence, record the timestamp, database/PDB, `SQL_ID`, child number, plan hash, instance, module/action, bind group, optimizer environment, and how runtime statistics were collected.

## 6. Bind Variables Give One SQL Multiple Behaviors

Bind variables reduce hard parses and improve cursor reuse. However, bind selectivity can vary enormously.

Example:

~~~sql
SELECT order_id, order_date
FROM orders
WHERE status = :status;
~~~

If `NEW` makes up most of the table while `RETURNED` is rare, a plan optimal for `NEW` may perform poorly for `RETURNED`.

### 6.1 Bind Peeking

During a hard parse, the optimizer can peek at the current bind value to estimate selectivity. The initial plan can reflect that peeked value. If subsequent runs supply bind values with vastly different selectivity, performance can shift.

### 6.2 Adaptive Cursor Sharing

Oracle can mark a cursor as bind-sensitive or bind-aware and create separate child cursors for distinct bind-value buckets when criteria are met. This helps handle skewed workloads.

Do not assume Oracle always creates a separate plan for every bind value or automatically resolves every case. Check child cursors, bind capture/peeked binds, plan hashes, and runtime metrics for each group.

### 6.3 One Snapshot Covers Only One Bind Group

If a report omits bind values or selectivity groups, it is hard to know which case the plan applies to. You do not need to record sensitive raw bind values in analysis documents; you can categorize them into groups such as common, medium, rare, or non-sensitive value ranges.

For sensitive data, avoid broad bind tracing. When testing bind datatypes or selectivity, use synthetic test data or approved controls to protect sensitive information.

## 7. Execution Time Is More Than Operation Time

A SQL statement can spend time across many areas:

- CPU processing row sources.
- I/O reading blocks.
- Waiting on locks or enqueues.
- Waiting on latches, mutexes, or internal resources.
- Waiting on TEMP due to sort/hash spills.
- Waiting on PX workers or parallel coordination.
- Waiting on client fetches or the network.
- Parsing/hard parsing and library cache activity.
- Triggers, PL/SQL, nested SQL calls, or recursive SQL.

Elapsed time is wall-clock duration observed by the caller. CPU time is actual CPU consumed. These two figures can diverge widely.

If elapsed time far exceeds CPU time, check wait events and wait causes. If CPU time accounts for most of elapsed time, inspect row counts, calculations, joins, sorts, parses, and CPU utilization. Operation names alone cannot distinguish these two situations.

### 7.1 Logical Reads vs. Physical Reads

- **Logical reads / buffer gets:** number of block accesses through the buffer cache.
- **Physical reads:** number of blocks read from storage within the reported scope.

A query with high logical reads can drive heavy CPU and buffer contention even when physical reads are low. A query with high physical reads depends heavily on storage latency and cache state.

Do not conclude that zero physical reads means a query has no I/O cost or is healthy. Nor should you compare two runs with different cache states and concurrency without noting those conditions.

### 7.2 A Run May Fetch Only Partial Results

An application may open a cursor and fetch only a few rows, or a user may close a screen before reading the full result set. Execution metrics then reflect work completed up to the stop point rather than a full fetch.

When benchmarking, specify explicitly whether the application fetches all rows, paginates, or stops early. When comparing against SQL*Plus or another tool, ensure equivalent fetch behavior.

## 8. Adaptive Plans and Runtime Choices

Some plans contain adaptive branches. The optimizer writes alternative choices into the plan and selects the appropriate branch at runtime once enough execution feedback is observed.

Consequently, reading a plan at parse time alone may not reveal which final branch ran. `DBMS_XPLAN` can show adaptive details and inactive/active operations depending on format and release.

When inspecting an adaptive plan:

1. Retrieve the plan of the exact child cursor.
2. Read the notes on adaptive plans.
3. Use a format supporting adaptive information if the version permits.
4. Collect runtime row-source statistics.
5. Compare executions across representative binds and data.

Do not assume every operation printed in an adaptive plan actually executed. Check operation status and runtime statistics.

## 9. Cache and System State Alter Results

Two executions of the exact same plan can have different runtimes due to system state differences.

Examples:

- The first run reads blocks from storage; the second finds them in the buffer cache.
- The first run performs a hard parse; the second reuses the cursor.
- The first run executes on an idle system; the second contends for CPU with a batch job.
- Storage latency varies under concurrent load.
- TEMP or PGA experiences different pressure.
- Parallel server process availability differs.
- Results are cached by the application or fetched differently by clients.

This is why a single fast or slow run cannot prove a plan is good or bad. Measure multiple runs using representative workloads, record cache state and concurrency, and avoid intentionally warming caches if your goal is measuring cold-start behavior.

No single benchmark procedure fits every system. Define the question up front: user latency, throughput, total CPU, I/O, or first-run behavior.

## 10. How to Collect Reliable Evidence

A plan analysis report should capture at minimum:

| Category | Information to Record |
|---|---|
| SQL identity | `SQL_ID`, SQL text, or sanitized version hiding sensitive data |
| Cursor | Child number, plan hash, parsing schema |
| Timestamp | Timestamp, database, PDB, instance |
| Application | Service, module, action, client identifier |
| Binds | Datatype and selectivity group; store raw values only when permitted |
| Optimizer | Optimizer mode, relevant parameters, plan notes |
| Statistics | Table/column/index/partition statistics, last analyzed |
| Plan | `DBMS_XPLAN` output and predicate information |
| Runtime | E-Rows, A-Rows, Starts, buffers, reads, CPU, elapsed |
| Waits | Wait class/event, total wait time, and wait counts |
| Workload | Execution count, concurrency, fetch pattern, representative data |

You do not always need every field for every SQL statement. For a targeted incident, start with `SQL_ID`, child cursor, actual plan, bind group, runtime statistics, and wait profile; expand when evidence points to additional needs.

### 10.1 Using DBMS_XPLAN for Plans

Example retrieving a specific cursor's plan:

~~~sql
SELECT *
FROM TABLE(
  DBMS_XPLAN.DISPLAY_CURSOR(
    sql_id          => 'SQL_ID_HERE',
    cursor_child_no => 0,
    format          => 'ALLSTATS LAST +PEEKED_BINDS +PREDICATE +ALIAS +NOTE'
  )
);
~~~

Without row-source statistics, `ALLSTATS LAST` may omit `A-Rows` and expected runtime metrics. Use `gather_plan_statistics` in a test query or an appropriate test configuration.

### 10.2 Using V$SQL and V$SQL_PLAN_STATISTICS_ALL

`V$SQL` holds cursor-level statistics such as executions, elapsed time, CPU time, buffer gets, disk reads, and rows processed. Stat columns are typically totals or averages per cursor, so account for execution count and snapshot timing.

Example cursor summary query:

~~~sql
SELECT sql_id,
       child_number,
       plan_hash_value,
       executions,
       ROUND(elapsed_time / 1e6, 3) AS elapsed_seconds,
       ROUND(cpu_time / 1e6, 3) AS cpu_seconds,
       buffer_gets,
       disk_reads,
       rows_processed,
       last_active_time
FROM v$sql
WHERE sql_id = 'SQL_ID_HERE'
ORDER BY child_number;
~~~

`V$SQL_PLAN_STATISTICS_ALL` combines plan structure with per-operation execution statistics when collected. Access to `V$` views depends on granted privileges and CDB/PDB context.

### 10.3 Using SQL Monitor When Appropriate

Real-Time SQL Monitoring provides live execution progress for eligible SQL statements, including timing, CPU, I/O, waits, parallel workers, and operation-level metrics. Feature availability and privileges depend on Oracle Database version, edition, configuration, and licensing.

SQL Monitor is valuable for long-running, parallel, or multi-operation SQL. It does not replace identifying the exact SQL execution, and not every SQL statement automatically gets a monitor report.

## 11. Comparing Plans Across Points in Time

When a SQL statement suddenly slows down, compare before and after the event rather than looking solely at the current plan.

Cross-check:

- `SQL_ID` and child cursor.
- Plan hash value and plan operations.
- Bind group.
- Statistics `last_analyzed` and data changes.
- Optimizer environment.
- SQL Profile, SQL Patch, SQL Plan Baseline.
- Timing of DDL, deployments, or database upgrades.
- Elapsed time, CPU, buffer gets, physical reads, and wait events.
- Execution count and concurrency level.

AWR/ASH can aid historical analysis where licensed and configured. AWR stores periodic statistics snapshots; ASH samples active session activity over time. These are historical datasets bounded by sampling intervals and retention, not complete operation-by-operation logs of every session.

When using historical data, verify snapshot interval, retention, instance, startup time, and SQL execution identity. Never compare raw totals across two windows of differing duration or workload without normalization.

## 12. Avoiding Common False Conclusions

| Hasty Conclusion | Why Evidence Is Insufficient |
|---|---|
| High cost means slow SQL | Cost is an internal estimate, not wall-clock time |
| Lower cost means performance improved | Runtime may be governed by cache, waits, and concurrency |
| Full scan is always a bug | A full scan can be optimal when many rows are needed |
| An index in the plan means the query is efficient | Index access may still read many leaf/table blocks |
| One SQL_ID has only one plan | One SQL_ID can have multiple child cursors |
| Matching plan hashes mean identical runtime | Runtime conditions and bind values can differ |
| EXPLAIN PLAN is what the application ran | Binds and session environment may differ |
| E-Rows matching A-Rows means the SQL is healthy | Waits, CPU, I/O, fetching, and contention can still be high |
| High A-Rows means an operation is slow | Must measure actual time and resource cost |
| One slow run proves a regression | Could be system load, cold cache, or transient waits |
| One fast run proves the fix worked | Must repeat across representative workloads and binds |
| Written hints are guaranteed to apply | Must verify Hint Report and actual plan |

## 13. Workflow When Given Only One Screenshot

If a colleague or monitoring alert hands you a single execution plan screenshot, treat it only as a starting point.

### Step 1: Identify Source and Timestamp

Ask whether the screenshot came from `EXPLAIN PLAN`, `DISPLAY_CURSOR`, SQL Monitor, or another tool. Record timestamp, database, PDB, instance, and session.

### Step 2: Identify the Cursor

Obtain `SQL_ID`, child number, and plan hash. If missing, retrieve them from the database if possible. Never guess the child cursor solely from SQL text.

### Step 3: Identify Binds and Environment

Record bind datatypes, selectivity group, optimizer mode, relevant session parameters, parsing schema, and application module/action.

### Step 4: Retrieve the Full Plan

Request complete text output, including predicate information, aliases, notes, partition information, and adaptive details if relevant. Screenshots often truncate vital columns, operations, or notes.

### Step 5: Gather Runtime Statistics

If reproducible, run the query with row-source statistics in an appropriate environment. Compare E-Rows/A-Rows, Starts, Buffers, Reads, and A-Time.

### Step 6: Gather Waits and Workload Context

If elapsed time is high while CPU is low, inspect wait events. If CPU is high, examine row counts, joins, sorts, parses, and concurrency. Record fetch patterns and execution counts.

### Step 7: Repeat Across Representative Scenarios

Test common, rare, and boundary bind values. Repeat enough times to separate trends from transient noise. Keep test conditions consistent across comparisons.

### Step 8: Propose Changes Only After Finding the Root Cause

Fixes might involve gathering statistics, adding extended statistics, fixing predicates, tuning indexes, addressing bind-sensitive cursors, or managing plans. Tie every proposal to measured evidence and evaluate impact on related workloads.

## 14. Example: Low Cost Yet Slow Application Response

Suppose a plan shows:

- `INDEX RANGE SCAN` on `ORDERS_STATUS_IX`.
- `TABLE ACCESS BY INDEX ROWID`.
- Low `E-Rows`.
- Low `Cost`.

Yet the application still reports the query is slow.

Multiple hypotheses must be checked:

1. The index range scan actually returns far more rows than `E-Rows`.
2. A high clustering factor causes scattered table block visits.
3. Physical reads are slow due to storage latency.
4. The session is waiting on I/O or another resource.
5. The application fetches many rows over a slow network.
6. The SQL executes repeatedly in a loop, creating high total time despite each call being fast.
7. The cursor ran for a different bind value than the one in the screenshot.

How to check:

- Retrieve the exact child cursor and plan.
- Compare E-Rows/A-Rows, Starts, Buffers, and Reads.
- Inspect wait events and CPU usage.
- Check bind groups and child cursors.
- Measure database time vs. application time.
- Compare multiple runs under identical conditions.

Only after pinpointing the bottleneck should you decide whether to modify indexes, statistics, or SQL.

## 15. Example: Cost Increases Yet SQL Is Not Slower

After gathering statistics, cost climbs from 80 to 140 while the plan hash stays identical. Elapsed time and buffer gets across multiple runs remain comparable.

This happens because the optimizer updated cardinality or system inputs while still selecting the same plan. Higher cost alone is not a valid reason to roll back statistics.

If the plan hash changes, still measure runtime. The new plan could be faster, equivalent, or slower. Compare across representative bind values and workloads rather than trusting a single cost number.

## 16. Writing a Verifiable Regression Report

A strong regression report separates **observations**, **hypotheses**, and **conclusions**.

Example structure:

| Section | Content |
|---|---|
| Observation | Elapsed time rose from 0.4 s to 3.2 s under the same workload type |
| Identity | `SQL_ID`, child number, plan hash, timestamp |
| Difference | New child cursor uses hash join instead of nested loops |
| Runtime evidence | A-Rows, Buffers, Reads, CPU, waits |
| Hypothesized cause | Cardinality of the `REGION` predicate was underestimated |
| Verification evidence | Histograms/extended stats and actual data counts |
| Trial change | Pending statistics or SQL rewrite in a test environment |
| Result | Comparison across multiple runs with the same bind group |
| Risk | Other SQL sharing the same stats/indexes could be affected |

If runtime statistics are not yet available, explicitly label the cause as a hypothesis. Never turn a screenshot-based guess into a definitive conclusion.

## 17. Checklist Before Concluding from an Execution Plan

- [ ] Know whether the plan comes from `EXPLAIN PLAN` or an actual cursor.
- [ ] Captured timestamp, database/PDB, instance, and session context.
- [ ] Captured `SQL_ID`, child number, and plan hash value.
- [ ] Inspected the complete plan text and Predicate Information.
- [ ] Identified bind datatypes and selectivity groups.
- [ ] Checked optimizer environment and relevant plan notes.
- [ ] Obtained E-Rows/A-Rows/Starts when evaluating cardinality.
- [ ] Checked Buffers, Reads, CPU, elapsed time, and wait events.
- [ ] Understood whether the application fetches partial or full results.
- [ ] Accounted for concurrency, cache state, and system state.
- [ ] Compared multiple representative executions.
- [ ] Separated observations from hypotheses.
- [ ] Measured before/after impact on equivalent workloads.
- [ ] Evaluated impact on other SQL before rolling out broad changes.

## 18. Conclusion

Cost is an estimation tool for the optimizer to compare plans, not a stopwatch. An execution plan shows how Oracle organizes a query in one specific context, yet a single snapshot cannot fully describe runtime behavior, bind values, child cursors, waits, concurrency, or change history.

When investigating performance, identify the exact cursor, retrieve the actual plan, compare estimated cardinality against actual rows, examine buffer/physical reads and wait events, and repeat across representative bind values and workloads. Draw conclusions only when the evidence explains both the plan structure and the observed runtime behavior.
