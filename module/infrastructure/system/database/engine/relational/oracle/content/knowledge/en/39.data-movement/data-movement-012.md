# Character Sets, Timezone Files, VERSION, and Source/Target Compatibility

When migrating an Oracle Database using Data Pump, transportable tablespaces, RMAN, or upgrade tools, compatibility between source and target databases does not depend solely on the Oracle version number. DBAs must verify at least four configuration layers:

1. **Character set:** whether the database character set and national character set can represent the source data.
2. **Time zone file version:** whether the timezone rule set Oracle uses for timezone-aware timestamp types is compatible.
3. **Database release and COMPATIBLE:** the software version, metadata structure, and feature level the database is permitted to use.
4. **Data Pump VERSION:** the metadata version Export generates to support importing into a target database.

These concepts are independent yet can combine to cause failures in a single migration. For example, Data Pump may read a dump file yet fail import because the target has a lower timezone file version than the source; or metadata exported at a compatible level fails because the target character set cannot represent certain source characters.

Therefore, before running export/import, build a source-to-target compatibility matrix, inventory actual data, identify used features, and test the migration on a representative clone. Never treat a successful expdp run as proof that import will succeed or that converted data will be lossless.

## 1. Four Types of "Version" to Distinguish

In Oracle, the word "version" can refer to several distinct concepts:

| Concept | What does it indicate? | Primary impact |
|---|---|---|
| Oracle Database release | Software/database release, e.g., 19c or 21c | Ability to read metadata, features, and dump formats |
| COMPATIBLE | Configured database feature compatibility level | Database structures/features usable and downgrade eligibility |
| Data Pump VERSION | Metadata level generated by Export | Ability to import into older releases within supported scope |
| Time zone file version | Timezone region rule set used by Oracle | Timezone-aware timestamp conversion and Data Pump TSTZ compatibility |

Character set is a different attribute altogether, not a version. Source and target can share the exact same Oracle release and COMPATIBLE yet differ in character set or timezone file version.

### 1.1. Oracle release does not equal COMPATIBLE

An Oracle Home can be 19c while database COMPATIBLE remains set lower to maintain compatibility with an older feature set. Conversely, once COMPATIBLE is raised, the database can use structures or features incompatible with older releases.

### 1.2. Data Pump VERSION does not upgrade a database

The expdp VERSION parameter controls the metadata version written to the dump file within Oracle-supported bounds. It does not change the source database, convert character sets, upgrade timezone files, or make every new feature work on an older database.

### 1.3. Time zone file version is not DBTIMEZONE

The time zone file version is the version of the timezone region dataset. DBTIMEZONE is the database's timezone, whereas SESSIONTIMEZONE is the current session's timezone. These three values serve different purposes.

## 2. Oracle Database Character Sets

### 2.1. What is a character set?

A character set defines how characters are encoded into bytes. In Oracle, the character set governs how character data is stored, compared, converted, and exchanged between clients and the database.

Examples:

- AL32UTF8: modern standard Unicode UTF-8, supporting supplementary characters.
- WE8MSWIN1252: Windows Western European character set.
- WE8ISO8859P1: ISO-8859-1 character set.
- JA16SJIS: Japanese Shift-JIS character set.
- AL16UTF16: Unicode UTF-16, commonly used as the national character set.

Character set names carry technical meaning; never infer them solely from language names or server locale.

### 2.2. NLS_CHARACTERSET

NLS_CHARACTERSET is the database character set. It is used for standard character data types:

- CHAR
- VARCHAR2
- CLOB
- Certain database metadata and other character data

Check:

```sql
SELECT parameter, value
FROM nls_database_parameters
WHERE parameter = 'NLS_CHARACTERSET';
```

Or:

```sql
SELECT value
FROM nls_database_parameters
WHERE parameter = 'NLS_CHARACTERSET';
```

### 2.3. NLS_NCHAR_CHARACTERSET

NLS_NCHAR_CHARACTERSET is the national character set, used for:

- NCHAR
- NVARCHAR2
- NCLOB

Common values are AL16UTF16 or legacy UTF8. Check:

```sql
SELECT parameter, value
FROM nls_database_parameters
WHERE parameter IN (
    'NLS_CHARACTERSET',
    'NLS_NCHAR_CHARACTERSET'
)
ORDER BY parameter;
```

The national character set is separate from the database character set. A database using AL32UTF8 does not automatically have NLS_NCHAR_CHARACTERSET set to AL32UTF8.

### 2.4. Oracle's AL32UTF8 vs. UTF8

These two names are easily confused:

- **AL32UTF8** is Oracle's character set implementing standard Unicode UTF-8, supporting characters outside the Basic Multilingual Plane.
- **UTF8** is Oracle's legacy character set name, using CESU-8 to represent supplementary characters; it is not equivalent to modern standard UTF-8.

For new databases needing Unicode, AL32UTF8 is usually the recommended choice. Never pick UTF8 merely because its name contains "UTF".

### 2.5. Character set supersets and subsets

A character set capable of representing every character of another character set is considered a superset within that conversion context. If the target cannot represent a source character, conversion can cause:

- Replacement characters.
- Conversion errors.
- Lost or altered values.
- Import failures on certain rows/columns.
- Data exceeding byte limits after conversion.

You cannot determine compatibility merely by comparing charset names. Check superset/subset relationships, actual data, data types, and the conversion path.

## 3. Client Character Set and NLS_LANG

### 3.1. What is NLS_LANG?

NLS_LANG is an Oracle OCI client-side environment variable structured as:

```text
NLS_LANG=LANGUAGE_TERRITORY.CHARACTERSET
```

Illustrative example:

```text
NLS_LANG=AMERICAN_AMERICA.AL32UTF8
```

The CHARACTERSET portion describes the encoding the client uses. The Oracle client can convert between the client character set and database character set during data transmission.

### 3.2. NLS_LANG does not change the database character set

Setting NLS_LANG does not change the database's NLS_CHARACTERSET. Nor does it convert already-stored data. NLS_LANG only affects character exchange at the OCI client and how the client renders/receives data.

If a client terminal uses UTF-8 encoding yet NLS_LANG declares a different charset, input/output data can suffer mojibake or corrupted characters. This can be a client conversion bug even while data inside the database remains intact.

### 3.3. Checking NLS session parameters

```sql
SELECT parameter, value
FROM nls_session_parameters
ORDER BY parameter;
```

NLS_SESSION_PARAMETERS shows the session's NLS settings. It is not the sole source for determining client OS encoding.

### 3.4. NLS_LANG and Data Pump

Data Pump converts data based on database and dump file character set metadata. Do not use NLS_LANG as a way to fix a dump whose source charset is incompatible with the target. For conversion errors, inspect database character sets, national character sets, actual data, and Data Pump logs.

### 3.5. Diagnosing display issues

When Vietnamese or Unicode data displays incorrectly:

1. Check NLS_CHARACTERSET and NLS_NCHAR_CHARACTERSET.
2. Check the encoding of the terminal, application driver, and client.
3. Check NLS_LANG if using an OCI client.
4. Read the same value through multiple clients with known encodings.
5. Distinguish corrupted stored data from data merely displayed incorrectly.

Never run bulk updates to "fix encoding" before determining whether the fault lies in storage or client conversion.

## 4. Unicode and Character Set Conversion

### 4.1. Why do migrations require checking Unicode?

An older database may use a region/language-restricted character set. When moving to a new system with multilingual data, emojis, or supplementary characters, the legacy charset may not represent all data.

Moving to Unicode is often part of modernization, but requires evaluating storage capacity, indexes, column length semantics, applications, and external interfaces.

### 4.2. Conversion during export/import

Data Pump can convert character data from the source character set to the target character set during import. The outcome depends on whether the target can represent the source data and the converted data types.

Examples:

- Source WE8MSWIN1252 to target AL32UTF8: the target can represent the source character repertoire and supports many more characters.
- Source AL32UTF8 to target WE8MSWIN1252: characters outside the target repertoire cannot be represented; conversion may error out or lose data depending on conversion path.

Verify with real data and import logs, not merely charset names.

### 4.3. Character set conversion is not a byte copy

During conversion, Oracle interprets bytes according to the source character set and re-encodes them into the target character set. Byte counts can grow or shrink. A VARCHAR2 column declared with BYTE semantics can exceed its byte limit after conversion even though the character count stays unchanged.

### 4.4. BYTE and CHAR length semantics

VARCHAR2(100 BYTE) caps by bytes; VARCHAR2(100 CHAR) caps by character count under supported semantics. In AL32UTF8, a single character can occupy 1 to 4 bytes.

Check metadata:

```sql
SELECT owner,
       table_name,
       column_name,
       data_type,
       data_length,
       char_length,
       char_used
FROM dba_tab_columns
WHERE data_type IN ('CHAR', 'VARCHAR2', 'NCHAR', 'NVARCHAR2')
ORDER BY owner, table_name, column_id;
```

CHAR_USED typically distinguishes BYTE from CHAR semantics. Inspect columns near their limits before moving to a charset with larger byte widths.

### 4.5. MAX_STRING_SIZE

MAX_STRING_SIZE controls size limits for SQL data types such as VARCHAR2, NVARCHAR2, and RAW in SQL. This is a different parameter/feature from character sets. When source and target differ in MAX_STRING_SIZE configuration, check columns or expressions using extended sizes and corresponding upgrade requirements.

### 4.6. CLOB and NCLOB

CLOB uses the database character set; NCLOB uses the national character set. Converting CLOB/NCLOB can differ from converting VARCHAR2/NVARCHAR2 in size limits and processing behavior. Inventory LOB columns and test multilingual content.

### 4.7. NLS_NCHAR_CONV_EXCP

NLS_NCHAR_CONV_EXCP can be enabled to force Oracle to raise an exception when converting NCHAR/NVARCHAR2 data causes character loss in scenarios governed by the parameter. It helps during conversion testing but does not replace a full database assessment.

### 4.8. Database character set migration and DMU

When changing a database character set, Oracle provides the Database Migration Assistant for Unicode (DMU) to analyze data, locate at-risk columns, assist cleansing, and convert. This is the recommended method to evaluate for migrating a database to Unicode.

Never run ALTER DATABASE CHARACTER SET as a quick fix. It carries strict prerequisites and does not replace a supported migration workflow. On legacy databases, CSSCAN/CSALTER tools were used in certain older releases; use the tool supported by Oracle for your current release.

## 5. Time Zone Files in Oracle

### 5.1. What is a time zone file?

Oracle uses timezone files containing timezone region names and offset rules over time, including historical timezone and daylight saving time changes per region. These rules change when governments update policies, so Oracle ships new timezone file versions.

The time zone file version governs how Oracle interprets timestamps with timezone regions. When source and target databases have different versions, Data Pump may need compatibility handling before importing TSTZ data.

### 5.2. Location of timezone files

Inside Oracle Home, timezone files typically reside under:

```text
$ORACLE_HOME/oracore/zoneinfo
```

Small and large files may exist per release naming conventions, such as `timezlrg_n.dat`. Never copy timezone files from another Oracle Home into a running database as a manual version upgrade.

### 5.3. Checking the timezone file version

```sql
SELECT * FROM v$timezone_file;
```

The view typically shows the filename and version currently used by the database. Check both source and target; record results alongside Oracle Home/release.

### 5.4. Viewing supported timezone names

```sql
SELECT tzname
FROM v$timezone_names
WHERE tzname IN (
    'UTC',
    'Asia/Ho_Chi_Minh',
    'America/New_York',
    'Europe/London'
)
ORDER BY tzname;
```

Supported region names depend on the timezone file. Avoid storing ambiguous timezone abbreviations like CST when business logic requires a specific region; prefer region names.

## 6. DBTIMEZONE, SESSIONTIMEZONE, and Timestamps

### 6.1. DBTIMEZONE

DBTIMEZONE is the database's timezone. It is not the timezone file version and does not necessarily equal the operating system's timezone.

Check:

```sql
SELECT dbtimezone FROM dual;
```

### 6.2. SESSIONTIMEZONE

SESSIONTIMEZONE is the current session's timezone:

```sql
SELECT sessiontimezone FROM dual;
```

Applications can set session timezone via ALTER SESSION or connection initialization. Different sessions can display timestamps in different timezones.

### 6.3. SYSTIMESTAMP and CURRENT_TIMESTAMP

- SYSTIMESTAMP returns the database host system timestamp with timezone/offset.
- CURRENT_TIMESTAMP returns the current timestamp in the session timezone.
- LOCALTIMESTAMP returns a timestamp without timezone in the session timezone.

Example:

```sql
SELECT systimestamp,
       current_timestamp,
       localtimestamp,
       dbtimezone,
       sessiontimezone
FROM dual;
```

### 6.4. TIMESTAMP WITH TIME ZONE

TIMESTAMP WITH TIME ZONE (TSTZ) stores a timestamp along with a timezone displacement or region information as managed by Oracle. Use region names when business logic must preserve timezone identity, because fixed offsets do not capture historical/future DST rules.

### 6.5. TIMESTAMP WITH LOCAL TIME ZONE

TIMESTAMP WITH LOCAL TIME ZONE (TSLTZ) is normalized to DBTIMEZONE upon storage and displayed in SESSIONTIMEZONE upon query. Values do not retain the original timezone region like TSTZ.

### 6.6. TIMESTAMP without timezone

Standard TIMESTAMP carries no timezone. If an application stores UTC instants in TIMESTAMP without documenting the convention, readers may misinterpret them as local time. Standardize conventions in both schema and application contracts.

### 6.7. Distinction example

```sql
CREATE TABLE timezone_lab (
    event_id NUMBER,
    event_tstz TIMESTAMP WITH TIME ZONE,
    event_tsltz TIMESTAMP WITH LOCAL TIME ZONE,
    event_ts TIMESTAMP
);

INSERT INTO timezone_lab
VALUES (
    1,
    TO_TIMESTAMP_TZ(
        '2026-11-14 09:00:00 Asia/Ho_Chi_Minh',
        'YYYY-MM-DD HH24:MI:SS TZR'
    ),
    TO_TIMESTAMP_TZ(
        '2026-11-14 09:00:00 Asia/Ho_Chi_Minh',
        'YYYY-MM-DD HH24:MI:SS TZR'
    ),
    TIMESTAMP '2026-11-14 09:00:00'
);
COMMIT;
```

After changing SESSIONTIMEZONE and re-querying, TSTZ and TSLTZ display differently. TSTZ retains the value's timezone information; TSLTZ displays in the session timezone.

## 7. Time Zone File Version and TSTZ Data

### 7.1. Why can versions differ?

Oracle updates timezone rules when local time policies or DST rules change. Two Oracle Homes at different release/patch levels can ship with different timezone file versions.

Source may store TSTZ values under an older version while target runs a newer version; or source may have a newer version than target. The latter case is especially critical when Data Pump imports timezone-aware timestamp data.

### 7.2. ORA-39405

A common Data Pump import error is ORA-39405: the source database has a higher TSTZ version than the target database. Data Pump does not support importing TSTZ data in that direction when the target timezone file is lower than the source in restricted cases.

The exact message depends on release, but the typical resolution is preparing the target timezone file version to match or exceed the source before importing, following the supported DBMS_DST procedure.

### 7.3. Why not just change DBTIMEZONE?

DBTIMEZONE does not replace the timezone file. Changing DBTIMEZONE does not upgrade the timezone rules version and does not resolve TSTZ data compatibility. Check V$TIMEZONE_FILE and the DBMS_DST procedure.

### 7.4. TSTZ and TSLTZ in migrations

Inventory timestamp columns with timezone:

```sql
SELECT owner,
       table_name,
       column_name,
       data_type,
       data_length
FROM dba_tab_columns
WHERE data_type LIKE 'TIMESTAMP%TIME ZONE%'
ORDER BY owner, table_name, column_id;
```

Check tables containing TSTZ/TSLTZ data via related data dictionary views such as DBA_TSTZ_TABLES and DBA_TSTZ_TAB_COLS if provided by your release. Do not search only for columns named DATE, because DATE stores no timezone.

### 7.5. Impact of timezone rule changes

When timezone rules change, the same local timestamp/region can map to a different UTC instant than in an earlier version. Oracle provides a timezone data upgrade procedure to handle affected data. Evaluate affected rows, ambiguous/nonexistent local times, and downstream applications.

## 8. Upgrading the Timezone File with DBMS_DST

### 8.1. What is DBMS_DST?

DBMS_DST is a package supporting timezone data upgrades inside the database. The process features a prepare window and an upgrade window, allowing assessment of affected tables/columns and conversion per Oracle procedures.

### 8.2. Checking current and available versions

```sql
SELECT * FROM v$timezone_file;
```

Available timezone files depend on Oracle Home and patch level. Installing a new Oracle Home does not automatically switch a database to the newer timezone file version; the database must run the corresponding upgrade procedure.

### 8.3. Pre-upgrade checks

Oracle supplies timezone upgrade check scripts in the Oracle Home admin directory on corresponding releases, typically named:

```text
utltz_upg_check.sql
```

The check script helps identify the target version, affected data volume, and issues requiring attention. Verify the exact script in your running release's Oracle Home.

### 8.4. Prepare window

During the prepare phase, the DBA identifies the target version, opens the prepare window, and locates affected tables/columns. APIs such as DBMS_DST.BEGIN_PREPARE, DBMS_DST.FIND_AFFECTED_TABLES, and DBMS_DST.END_PREPARE can be used per version procedure.

Save the findings to evaluate before entering the upgrade window. Pay special attention to large tables, TSTZ columns, error rows, and required time.

### 8.5. Upgrade window

The upgrade phase upgrades the timezone version and updates necessary data. Oracle provides a matching apply script, typically:

```text
utltz_upg_apply.sql
```

In some releases, the process includes opening the upgrade window, running UPGRADE_DATABASE, handling errors, and closing the upgrade window via DBMS_DST. Database state, open mode, CDB/PDB, and downtime requirements depend on release.

### 8.6. Do not copy API snippets into a generic runbook

DBMS_DST signatures and startup mode requirements have changed across releases. Use the official scripts and instructions shipped with your exact Oracle Home, inspect the package specification, and execute inside a maintenance window with backups/rollback. Never run BEGIN_UPGRADE or UPGRADE_DATABASE on production based solely on an abbreviated snippet.

### 8.7. Post-upgrade verification

After completion:

```sql
SELECT * FROM v$timezone_file;
```

Check upgrade status, error tables/logs created by scripts, DBA_TSTZ_TABLES, and applications using timezone regions. Test timestamp conversions around DST boundaries if used by the business.

### 8.8. CDB/PDB

In multitenant environments, timezone file versions and upgrade steps may have specific rules for CDB root and PDBs. Execute in the right container, check each PDB's status, and follow release documentation. Do not assume running a script once in root automatically handles every container identically.

## 9. Data Pump VERSION

### 9.1. What is VERSION?

The Data Pump Export VERSION parameter specifies the metadata version Export generates. It supports exporting data/metadata for import into an older release within Oracle's supported compatibility matrix.

Example:

```text
expdp system@SRCDB schemas=APP directory=DP_DIR dumpfile=app_%U.dmp logfile=app_exp.log parallel=4 version=12.2
```

The VERSION value must be a supported target release compatible with the source. The example above illustrates syntax only; consult the compatibility matrix for your exact source/target releases before running.

### 9.2. VERSION=COMPATIBLE

If VERSION is omitted, Export normally uses the source database's COMPATIBLE value to determine the corresponding metadata level. You can specify it explicitly:

```text
expdp system@SRCDB schemas=APP directory=DP_DIR dumpfile=app.dmp logfile=app.log version=COMPATIBLE
```

### 9.3. VERSION controls metadata only

VERSION does not:

- Change NLS_CHARACTERSET.
- Upgrade or downgrade timezone files.
- Lower the source's COMPATIBLE.
- Convert every new data type into an older data type.
- Guarantee source-specific features have an equivalent representation on the target.
- Make every older release able to read every newer dump file.

If an object uses a feature absent in the target release, the object may be omitted, metadata may be transformed, or export/import may raise errors depending on the feature.

### 9.4. VERSION is an Export parameter

VERSION is an expdp parameter. Do not confuse it with the database COMPATIBLE parameter or a target upgrade option. When building import commands, review impdp parameters separately along with dump file compatibility.

### 9.5. Example exporting for import into an older release

```text
expdp system@SRCDB \
  schemas=APP \
  directory=DP_DIR \
  dumpfile=app_legacy_%U.dmp \
  logfile=app_legacy_exp.log \
  parallel=4 \
  version=12.2
```

Command illustrated in a Unix-style shell. In Windows CMD/PowerShell, line continuation differs; it can be written on one line. Replace 12.2 with the actual supported target release.

### 9.6. Data Pump client/server versions

Data Pump is a server-based tool. The expdp/impdp client binary, source/target database servers, and dump file version can all affect execution. Use a Data Pump client matching the database server and follow Oracle's interoperability rules. Do not infer compatibility simply because an expdp command prints a newer version banner.

## 10. COMPATIBLE Parameter

### 10.1. Purpose

COMPATIBLE is an initialization parameter defining the feature compatibility level a database is allowed to use. It helps Oracle maintain structural and feature compatibility across certain upgrade phases.

Check:

```sql
SELECT name, value, isdefault, issys_modifiable
FROM v$parameter
WHERE name = 'compatible';
```

### 10.2. COMPATIBLE differs from Oracle release

For instance, a database can run on an Oracle 19c Home while COMPATIBLE remains set lower. The database does not necessarily adopt all new release features until the parameter is raised and other conditions are satisfied.

### 10.3. Not easily reversible

Raising COMPATIBLE can allow Oracle to use structures/features incompatible with earlier releases. Once raised and new features have been used, lowering the parameter back cannot be treated as a supported downgrade.

Therefore, raise COMPATIBLE only after:

- Completing software/database upgrade.
- Testing applications and database components.
- Confirming no rollback to an older release is needed.
- Having backups and a recovery plan.
- Reviewing feature/upgrade path requirements.

### 10.4. COMPATIBLE and Data Pump VERSION

The two parameters serve two goals:

- COMPATIBLE governs feature compatibility of the running database.
- Data Pump VERSION governs the metadata level written inside an export dump.

Setting a lower VERSION does not lower the source's COMPATIBLE. Keeping COMPATIBLE low also does not guarantee every exported object has target-compatible metadata.

### 10.5. COMPATIBLE and source/target

When migrating to a newer target release, the target can usually adopt a release-appropriate COMPATIBLE after completing upgrade and validation. When moving data from a newer source back to an older target, inspect source COMPATIBLE, feature usage, and export VERSION; you cannot simply alter COMPATIBLE to produce a compatible dump.

## 11. Source and Target Compatibility Matrix

Before migration, build a table covering at least these items:

| Item | Source | Target | What to verify |
|---|---|---|---|
| Oracle release | | | Supported migration/upgrade path |
| COMPATIBLE | | | Feature and downgrade implications |
| NLS_CHARACTERSET | | | Target can represent source data |
| NLS_NCHAR_CHARACTERSET | | | NCHAR/NVARCHAR2/NCLOB compatibility |
| Time zone file version | | | Target not lower than needed for TSTZ import |
| MAX_STRING_SIZE | | | Columns/metadata using extended strings |
| Database role/architecture | | | CDB/PDB, RAC, non-CDB |
| Platform/endianness | | | Whether transportable tablespaces need conversion |
| Data Pump VERSION | | | Export metadata matches target |
| Encryption/TDE | | | Wallet/keystore and decryption privileges |
| Options/components | | | Spatial, XML DB, Java, Text, Partitioning... |
| Timezone semantics | | | Session/database/application timezone |
| Storage/LOB | | | SecureFiles, tablespaces, and capacity |

Do not leave unknown items blank. Mark them explicitly as "unverified" and verify them before scheduling the migration.

## 12. Source Inventory Workflow

### 12.1. Oracle release

```sql
SELECT banner
FROM v$version
ORDER BY banner;
```

You can also check:

```sql
SELECT version, version_full, instance_name
FROM v$instance;
```

The `version_full` column may not exist in some older releases.

### 12.2. Character sets

```sql
SELECT parameter, value
FROM nls_database_parameters
WHERE parameter IN (
    'NLS_CHARACTERSET',
    'NLS_NCHAR_CHARACTERSET'
)
ORDER BY parameter;
```

### 12.3. Timezone

```sql
SELECT * FROM v$timezone_file;

SELECT dbtimezone, sessiontimezone
FROM dual;
```

### 12.4. COMPATIBLE and MAX_STRING_SIZE

```sql
SELECT name, value
FROM v$parameter
WHERE name IN ('compatible', 'max_string_size');
```

### 12.5. Inventorying TSTZ/TSLTZ columns

```sql
SELECT owner,
       table_name,
       column_name,
       data_type
FROM dba_tab_columns
WHERE data_type LIKE 'TIMESTAMP%TIME ZONE%'
ORDER BY owner, table_name, column_id;
```

### 12.6. Inventorying character columns

```sql
SELECT owner,
       table_name,
       column_name,
       data_type,
       data_length,
       char_length,
       char_used
FROM dba_tab_columns
WHERE data_type IN ('CHAR', 'VARCHAR2', 'NCHAR', 'NVARCHAR2')
ORDER BY owner, table_name, column_id;
```

### 12.7. Checking database components

```sql
SELECT comp_id,
       comp_name,
       version,
       status
FROM dba_registry
ORDER BY comp_id;
```

The target must have the required components/options for imported objects. INVALID status or missing components can cause object compilation failures.

## 13. Preflight Character Set Conversion

### 13.1. Identify unrepresentable characters

Do not inspect only a few sample rows. Use DMU or an appropriate assessment tool to detect data unrepresentable in the target charset, byte expansion, and column length issues.

### 13.2. Check data near length limits

BYTE-semantics columns risk overflowing limits after converting to a multi-byte charset. Find columns whose DATA_LENGTH is near the limit and measure post-conversion byte lengths in a test environment.

### 13.3. Application testing

Test:

- Inserting/updating Unicode from the application.
- Reading back data via JDBC/OCI/ODP.NET and SQL*Plus.
- Searching, sorting, comparing, and indexing multilingual data.
- Exporting/importing LOB data.
- Connecting through clients with different NLS_LANG/encoding settings.

### 13.4. Data cleansing

If source data contains invalid byte sequences or characters stored under the wrong encoding, conversion cannot guess the original intent. Cleanse data before migration and document conversion rules.

### 13.5. Never use NLS_LANG to fix corrupted data

NLS_LANG affects only client conversion. If bytes stored inside the database are already in the wrong charset, changing NLS_LANG will not restore original characters. Controlled data assessment and repair are required.

## 14. Preflight Timezone Compatibility

### 14.1. Compare source and target

Run on both databases:

```sql
SELECT filename, version
FROM v$timezone_file;
```

Record the versions. If the source version is higher than the target, especially when the dump contains TSTZ data, upgrade the target timezone file before importing per Oracle guidelines.

### 14.2. Inspect TSTZ data

List TSTZ/TSLTZ columns and assess row counts, table sizes, and applications relying on timezone regions. Estimate upgrade duration and plan post-conversion validation.

### 14.3. Upgrade the timezone file before import

In many ORA-39405 cases, the resolution is upgrading the target timezone file version to match or exceed the source before running impdp. Execute using DBMS_DST/scripts for your exact release and test beforehand.

### 14.4. Do not downgrade timezone files to match source

Do not treat a lower timezone file version as an arbitrarily swappable configuration setting. Downgrading may be unsupported and can misinterpret timestamps. Prefer upgrading the target to a compatible version.

### 14.5. Application timezone rules

Even when Data Pump import succeeds, applications may display different times if session timezone, DBTIMEZONE, or timezone region assumptions changed. Test dates around DST transitions, midnight, month-end, and business cutoffs.

## 15. Data Pump Migration Across Releases

### 15.1. Basic export and import

Example schema export:

```text
expdp system@SRCDB \
  schemas=APP \
  directory=DP_DIR \
  dumpfile=app_%U.dmp \
  logfile=app_export.log \
  parallel=4
```

Example import to target:

```text
impdp system@TGTDB \
  schemas=APP \
  directory=DP_DIR \
  dumpfile=app_%U.dmp \
  logfile=app_import.log \
  parallel=4
```

Directory objects and file locations must be configured on the respective database servers. When source/target sit on different hosts, transfer dump files securely or use an appropriate Data Pump method.

### 15.2. Exporting with VERSION

```text
expdp system@SRCDB \
  schemas=APP \
  directory=DP_DIR \
  dumpfile=app_for_target.dmp \
  logfile=app_for_target.log \
  version=12.2
```

Set VERSION to an Oracle-supported target release. Read the export log to spot incompatible objects/features.

### 15.3. SQLFILE to inspect DDL

Before running the actual import, use impdp's SQLFILE to write DDL to a file:

```text
impdp system@TGTDB \
  schemas=APP \
  directory=DP_DIR \
  dumpfile=app_for_target.dmp \
  sqlfile=app_preview.sql \
  logfile=app_preview.log
```

SQLFILE lets you review DDL without executing standard import statements. It does not prove data will import successfully; test import on a target clone.

### 15.4. Test import into another schema

REMAP_SCHEMA and REMAP_TABLESPACE help test importing into an isolated schema/tablespace:

```text
impdp system@TGTDB \
  schemas=APP \
  remap_schema=APP:APP_TEST \
  remap_tablespace=APP_DATA:APP_TEST_DATA \
  directory=DP_DIR \
  dumpfile=app_for_target.dmp \
  logfile=app_test_import.log
```

This is an example; inspect dependencies, grants, synonyms, directories, external tables, and object references before use.

### 15.5. VERSION does not handle every new feature

If the source uses data types, object metadata, or database features absent in the target release, export/import may skip, transform, or error on them. Review Data Pump logs, SQLFILE, invalid objects, and application tests.

## 16. Compatibility by Migration Direction

### 16.1. Older source to newer target

This is the common upgrade direction:

- The target usually supports older source metadata, though upgrade paths and Data Pump compatibility still require verification.
- The target character set may be a broader Unicode set; check conversion and column byte limits.
- The target timezone file may be newer; check TSTZ data and version compatibility.
- Check components/options, data types, MAX_STRING_SIZE, TDE, and platform.

### 16.2. Newer source to older target

This direction carries more restrictions:

- Use Data Pump VERSION within supported bounds.
- Not every new feature can be represented on the target.
- Source COMPATIBLE/feature usage may block downgrade.
- Higher source timezone file than target can cause ORA-39405.
- Unicode source character set to legacy target risks character loss.
- Explicitly check Oracle's downgrade/migration matrix.

### 16.3. Same release yet different timezone file

Two databases on the same release may be patched differently and use different timezone file versions. Never assume timezone compatibility just from 19c/21c; always query V$TIMEZONE_FILE.

### 16.4. Same release yet different character set

Two databases on the same release can still have lossy data conversion. Compare NLS_CHARACTERSET and NLS_NCHAR_CHARACTERSET, then inspect actual data.

### 16.5. Same charset yet different NLS settings

NLS_DATE_FORMAT, NLS_TIMESTAMP_FORMAT, NLS_SORT, NLS_COMP, and session timezone can affect applications or processing results even when database charsets match. Standardize formats and bind data types in application code rather than relying on NLS defaults.

## 17. Migration Methods and Compatibility Limits

### 17.1. Data Pump logical migration

Data Pump export/import moves object metadata and logical rows. It can convert character data across database character sets and lets you choose VERSION for metadata within supported bounds.

Data Pump does not automatically upgrade the target timezone file, raise COMPATIBLE, or install missing database options.

### 17.2. Transportable tablespaces

Transportable tablespaces move datafiles along with metadata instead of unloading/reloading all rows. Check:

- Source/target endian format.
- Character set compatibility per transportable rules.
- Database release and COMPATIBLE.
- Tablespace self-containment.
- TDE/encryption and wallets.
- Datafile version and platform support.

If cross-platform endianness differs, RMAN CONVERT or a supported datafile conversion workflow may be needed. Do not treat Data Pump VERSION as an endian-conversion tool.

### 17.3. RMAN duplicate/restore

RMAN physical migration/duplicate has its own release, platform, endian, storage, and backup format compatibility rules. The database's character set and timezone file are preserved as part of the physical database; this is not logical character-set conversion.

### 17.4. Database upgrade

In-place database upgrades have separate paths and requirements from Data Pump. Check upgrade paths, preupgrade checks, component statuses, COMPATIBLE, and timezone files. Never use Data Pump VERSION as a substitute for a database upgrade.

### 17.5. Heterogeneous migration

When moving from non-Oracle to Oracle or vice versa, character mapping, data type mapping, timezone semantics, and collation can differ. Require a mapping specification, conversion tests, and business-key reconciliation.

## 18. Common Errors

| Error/symptom | Possible cause | Resolution |
|---|---|---|
| ORA-39405 | Source TSTZ version higher than target | Check V$TIMEZONE_FILE, upgrade target timezone file via DBMS_DST |
| ORA-02374 | Conversion error while loading data | Check import log, charset, row/column, and source data |
| ORA-12899 after conversion | Value exceeds column limit after encoding change | Check BYTE/CHAR semantics and column definitions |
| Characters turn into question marks or wrong glyphs | Target charset cannot represent them or wrong client encoding | Separate database conversion from NLS_LANG |
| Import does not support object metadata | Target release lower than source feature | Check Data Pump VERSION and feature compatibility |
| Dump file unreadable | Incompatible Data Pump dump format/client/server version | Use a supported Data Pump version/path |
| TSTZ displays differently after migration | Different timezone rules/session timezone | Compare timezone files, DBTIMEZONE, SESSIONTIMEZONE |
| DATE/TIMESTAMP values shifted by hours | Application assumed an unstored timezone | Clarify storage convention and application conversion |
| Objects INVALID after import | Missing component/feature/privilege | Check DBA_REGISTRY, grants, and compilation errors |
| Transportable import fails | Endian, self-containment, tablespace, or version mismatch | Check transportable compatibility and RMAN CONVERT if needed |

## 19. Sample Migration Scenario

Suppose an Oracle 19c source uses AL32UTF8 and timezone file version 42; a freshly installed Oracle 19c target has database character set AL32UTF8 yet timezone file version 32. Schema APP contains many TSTZ columns.

### Step 1 — Inventory source and target

Run queries for Oracle release, COMPATIBLE, character sets, timezone file, MAX_STRING_SIZE, and DBA_REGISTRY on both databases.

### Step 2 — Identify incompatibilities

Source and target character sets match, but the target timezone file is lower than the source. Data Pump import may fail with ORA-39405 when encountering TSTZ data.

### Step 3 — Plan the timezone upgrade

Verify the newer timezone file is available in the target Oracle Home. Run prechecks with the corresponding script, evaluate affected tables, prepare backups, and schedule a maintenance window.

### Step 4 — Upgrade the target timezone file

Follow the DBMS_DST/scripts procedure for your exact release. Verify V$TIMEZONE_FILE and TSTZ data after upgrade.

### Step 5 — Export schema

Run expdp with an appropriate VERSION if the target requires release-specific metadata compatibility. Retain dumps/logs and checksums.

### Step 6 — Test import

Run impdp on a target clone. Review SQLFILE, import logs, conversion warnings, and invalid objects.

### Step 7 — Reconciliation

Compare row counts, business totals, LOB counts, character samples, timestamp samples, and sequence/identity behavior.

### Step 8 — Cutover

Lock in the source freeze time, export delta/final, import, validate the application, update connections/services, and keep the rollback plan for the agreed duration.

This example illustrates processing order only. Specific versions and timezone scripts must match the actual Oracle Home.

## 20. Post-Import Verification

### 20.1. Character set

Confirm target NLS_CHARACTERSET and NLS_NCHAR_CHARACTERSET match design. Verify multilingual strings through the real application.

### 20.2. Timezone file

```sql
SELECT * FROM v$timezone_file;
SELECT dbtimezone, sessiontimezone FROM dual;
```

Verify timestamp samples around DST/offset transitions if business logic uses timezone regions.

### 20.3. Objects and components

```sql
SELECT owner, object_type, status, COUNT(*)
FROM dba_objects
WHERE owner = 'APP'
GROUP BY owner, object_type, status
ORDER BY object_type, status;

SELECT comp_id, comp_name, version, status
FROM dba_registry
ORDER BY comp_id;
```

### 20.4. Data validation

Compare row counts per table, monetary/quantity totals by business key, LOB data, null counts, and critical columns. Matching row counts alone do not prove characters or timestamps converted accurately.

### 20.5. Application validation

Test:

- Login/session timezone.
- Unicode inserts/updates.
- Searching/sorting/collation.
- Timestamp conversion across timezones.
- Batch jobs, Scheduler, and Data Guard if present.
- Business date and cutoff reports.
- API/client encoding.

### 20.6. Post-migration performance

Character sets, indexes, collations, data lengths, and storage can affect table/index sizes. After cutover, monitor SQL plans, buffer gets, I/O, CPU, and latency.
