# Impact of NULL and Empty Sets on Aggregate Functions

When writing reports in Oracle SQL, a seemingly simple question like "what is the total salary of this department?" can produce **0**, **NULL**, or **no result rows**. Those results are not synonymous. They depend on whether the query has input rows, whether the aggregated values contain NULLs, and whether you are computing over the entire dataset or per group.

For example:

- No employees belong to department 999: the input set to the aggregation is **empty**.
- Two employees belong to department 30, but neither has a recorded salary yet: the input set has **two rows**, but the salary column contains two NULL values.
- Three employees belong to department 10, with salaries of 1,000, NULL, and 2,000 respectively: there are **three rows**, with two known salary values.

Oracle handles these three cases differently:

- `COUNT(*)` counts rows.
- `COUNT(expression)` counts non-NULL values of the expression.
- `SUM`, `AVG`, `MIN`, `MAX`, and many other aggregate functions ignore NULL values.
- When the input set has no qualifying values, many aggregates return NULL; `COUNT` specifically returns 0.
- An aggregate without `GROUP BY` still returns one result row; a query with `GROUP BY` on an empty input set usually forms no groups and returns 0 rows.

This lesson focuses on distinguishing **empty sets**, **groups with rows where all values are NULL**, **an aggregated value of 0**, and **NULL rows generated by an OUTER JOIN**. This is foundational for writing accurate reports, KPIs, statistics, and data quality check queries.

## 1. Three input states to distinguish

Suppose you are summing the `AMOUNT` column. There are three typical input states:

| State | Input rows | Row count | Non-NULL AMOUNT count |
| --- | --- | ---: | ---: |
| **Empty set** | No rows | 0 | 0 |
| **Rows exist, all AMOUNTs NULL** | NULL, NULL, ... | Greater than 0 | 0 |
| **Known values exist** | 1000, NULL, 2000, ... | Greater than 0 | Greater than 0 |

For basic aggregates:

| Aggregate | Empty set | Rows exist, all expressions NULL | Non-NULL values exist |
| --- | --- | --- | --- |
| `COUNT(*)` | 0 | Counts rows | Counts all rows |
| `COUNT(expr)` | 0 | 0 | Counts non-NULL expr values |
| `COUNT(DISTINCT expr)` | 0 | 0 | Counts distinct values, ignoring NULL |
| `SUM(expr)` | NULL | NULL | Sum of non-NULL values |
| `AVG(expr)` | NULL | NULL | Average of non-NULL values |
| `MIN(expr)` | NULL | NULL | Minimum among non-NULL values |
| `MAX(expr)` | NULL | NULL | Maximum among non-NULL values |

Common pitfall: **SUM returns NULL both for an empty set and when rows exist with all NULL values.** Looking at the SUM result alone is not enough to tell the two situations apart. Also check `COUNT(*)` and `COUNT(expr)`.

## 2. Lab data for testing

Create the department and employee tables in a **dedicated practice schema** with table creation privileges and tablespace quota. These examples do not require DBA privileges.

## 3. Aggregates over the entire input set

A SELECT statement containing only aggregate functions and **no GROUP BY** produces one summary result for the entire filtered row set.

### 3.1. No matching rows

```sql
SELECT
    COUNT(*) AS row_count,
    COUNT(salary) AS known_salary_count,
    COUNT(DISTINCT salary) AS distinct_salary_count,
    SUM(salary) AS salary_sum,
    AVG(salary) AS salary_avg,
    MIN(salary) AS salary_min,
    MAX(salary) AS salary_max
FROM lab_agg_employees
WHERE department_id = 20;
```

Department 20 has no employees. Nevertheless, an aggregate query without GROUP BY still returns **one result row**:

| ROW_COUNT | KNOWN_SALARY_COUNT | DISTINCT_SALARY_COUNT | SALARY_SUM | SALARY_AVG | SALARY_MIN | SALARY_MAX |
| ---: | ---: | ---: | --- | --- | --- | --- |
| 0 | 0 | 0 | NULL | NULL | NULL | NULL |

Key takeaways:

- `COUNT(*)` returns 0 because there are no rows.
- `COUNT(SALARY)` returns 0 because there are no non-NULL salary values.
- `SUM`, `AVG`, `MIN`, and `MAX` return NULL because there are no input values to compute.
- The client still receives **one row**, not an empty result set.

### 3.2. Rows exist, but all aggregated values are NULL

```sql
SELECT
    COUNT(*) AS row_count,
    COUNT(salary) AS known_salary_count,
    COUNT(DISTINCT salary) AS distinct_salary_count,
    SUM(salary) AS salary_sum,
    AVG(salary) AS salary_avg,
    MIN(salary) AS salary_min,
    MAX(salary) AS salary_max
FROM lab_agg_employees
WHERE department_id = 30;
```

Department 30 has two employees, both with `SALARY NULL`:

| ROW_COUNT | KNOWN_SALARY_COUNT | DISTINCT_SALARY_COUNT | SALARY_SUM | SALARY_AVG | SALARY_MIN | SALARY_MAX |
| ---: | ---: | ---: | --- | --- | --- | --- |
| 2 | 0 | 0 | NULL | NULL | NULL | NULL |

Compared to department 20:

- `ROW_COUNT` differs: 0 versus 2.
- The aggregates based on salary values are identical: salary count is 0, and sum/avg/min/max are all NULL.

Therefore, **a NULL SUM does not tell you whether rows exist**. To distinguish them, you must also inspect COUNT(*).

### 3.3. Partially NULL values

```sql
SELECT
    COUNT(*) AS row_count,
    COUNT(salary) AS known_salary_count,
    SUM(salary) AS salary_sum,
    AVG(salary) AS salary_avg,
    MIN(salary) AS salary_min,
    MAX(salary) AS salary_max
FROM lab_agg_employees
WHERE department_id = 10;
```

Department 10 has salaries 1000, NULL, and 2000:

| ROW_COUNT | KNOWN_SALARY_COUNT | SALARY_SUM | SALARY_AVG | SALARY_MIN | SALARY_MAX |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 3 | 2 | 3000 | 1500 | 1000 | 2000 |

SUM/AVG/MIN/MAX ignore rows with a NULL salary. Therefore:

\[
AVG(SALARY) = \frac{1000 + 2000}{2} = 1500
\]

Oracle does not divide by 3. The denominator of AVG is the number of non-NULL values, corresponding to `COUNT(SALARY)`.

### 3.4. Zero is a real value

```sql
SELECT
    COUNT(*) AS row_count,
    COUNT(salary) AS known_salary_count,
    SUM(salary) AS salary_sum,
    AVG(salary) AS salary_avg,
    MIN(salary) AS salary_min,
    MAX(salary) AS salary_max
FROM lab_agg_employees
WHERE department_id = 40;
```

Department 40 has one employee with a salary of 0:

| ROW_COUNT | KNOWN_SALARY_COUNT | SALARY_SUM | SALARY_AVG | SALARY_MIN | SALARY_MAX |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 1 | 0 | 0 | 0 | 0 |

This clearly proves that **NULL is different from 0**. If an application automatically replaces NULL with 0 when writing data, it can no longer distinguish "salary unknown" from "salary is 0."

## 4. COUNT(*), COUNT(expression), and COUNT(DISTINCT)

### 4.1. COUNT(*) counts rows

`COUNT(*)` counts all rows in the input set, even when some columns in a row are NULL:

```sql
SELECT COUNT(*) AS employee_rows
FROM lab_agg_employees
WHERE department_id = 10;
```

The result is 3. Bình's NULL `SALARY` column does not make that row disappear from the count.

### 4.2. COUNT(expression) counts only non-NULL values

```sql
SELECT
    COUNT(*) AS employee_rows,
    COUNT(salary) AS employees_with_known_salary,
    COUNT(department_id) AS employees_assigned_to_department
FROM lab_agg_employees;
```

General meaning:

- `COUNT(*)` counts rows.
- `COUNT(SALARY)` counts only rows with a non-NULL salary.
- `COUNT(DISTINCT SALARY)` counts distinct salary values and does not count NULL.

In a query with multiple JOINs, `COUNT(*)` counts **rows after the JOIN**. If one employee joins to three child rows, that employee contributes three to COUNT(*). Determine the grain of the result set before naming the result "employee_count."

### 4.3. COUNT(DISTINCT expression)

```sql
SELECT
    COUNT(*) AS employee_rows,
    COUNT(salary) AS known_values,
    COUNT(DISTINCT salary) AS distinct_known_salaries
FROM lab_agg_employees
WHERE department_id = 10;
```

Result:

- 3 employee rows.
- 2 non-NULL salary values.
- 2 distinct salary levels: 1000 and 2000.

If two employees both have a salary of 1000, `COUNT(SALARY)` counts both, whereas `COUNT(DISTINCT SALARY)` counts only one salary level.

**NULL is ignored in COUNT(expression), including COUNT(DISTINCT expression).** If you need to count rows with NULL, use `COUNT(*) - COUNT(expression)`:

```sql
SELECT
    COUNT(*) AS total_rows,
    COUNT(salary) AS known_salary_rows,
    COUNT(*) - COUNT(salary) AS null_salary_rows
FROM lab_agg_employees
WHERE department_id = 10;
```

The results are 3, 2, and 1.

## 5. How do SUM, AVG, MIN, and MAX ignore NULL?

### 5.1. SUM: adding known values

```sql
SELECT SUM(salary) AS salary_total
FROM lab_agg_employees
WHERE department_id = 10;
```

The result is 3000, because NULL does not contribute to the sum. If all salaries are NULL or there are no rows, SUM returns NULL.

Do not interpret a NULL `SUM` as "total equals 0" without confirming the business semantics. It could mean:

- There are no employees.
- Employees exist, but no salary values have been recorded yet.
- The filter condition found no non-NULL salary values.

### 5.2. AVG: denominator includes only non-NULL values

```sql
SELECT
    COUNT(*) AS employee_count,
    COUNT(salary) AS salary_count,
    SUM(salary) AS salary_sum,
    AVG(salary) AS salary_avg
FROM lab_agg_employees
WHERE department_id = 10;
```

For department 10:

\[
AVG(SALARY) = \frac{SUM(SALARY)}{COUNT(SALARY)}
= \frac{3000}{2} = 1500
\]

If you use `COUNT(*)` as the denominator, the manually computed result would be 1000 and would no longer match the semantics of `AVG(SALARY)` in Oracle.

### 5.3. MIN and MAX: NULL does not become the minimum/maximum value

```sql
SELECT
    MIN(salary) AS minimum_salary,
    MAX(salary) AS maximum_salary
FROM lab_agg_employees
WHERE department_id = 10;
```

Results are 1000 and 2000. Oracle ignores NULL salaries when computing MIN/MAX. If all values are NULL or there are no rows, both return NULL.

### 5.4. Other aggregates

Many other aggregate functions also ignore NULL arguments:

- `STDDEV` / `STDDEV_POP` / `STDDEV_SAMP`: standard deviation.
- `VARIANCE` / `VAR_POP` / `VAR_SAMP`: variance.
- `MEDIAN`: median.
- `LISTAGG`: ignores NULL measure values when concatenating strings.
- `COUNT(DISTINCT ...)`: does not count NULL.

Some statistical functions have specific rules when only one input value remains; for example, sample versus population calculations differ. When using them in official reports, read the documentation for the specific function and deployed Oracle release rather than assuming every function shares the same boundary behavior.

LISTAGG example:

```sql
SELECT
    department_id,
    LISTAGG(full_name, ', ')
        WITHIN GROUP (ORDER BY employee_id) AS employee_names
FROM lab_agg_employees
GROUP BY department_id
ORDER BY department_id NULLS LAST;
```

`LISTAGG` ignores NULL measure values. If there are no values to concatenate, the aggregate result is NULL. If the resulting string exceeds the limit, handle overflow options according to your release and application requirements.

## 6. Aggregates without GROUP BY vs. aggregates with GROUP BY

This is an important distinction when the input set is empty.

### 6.1. Aggregates without GROUP BY return one row

```sql
SELECT COUNT(*) AS row_count, SUM(salary) AS salary_sum
FROM lab_agg_employees
WHERE department_id = 999;
```

There are no employees in department 999, yet the SELECT statement still returns one row:

```text
ROW_COUNT | SALARY_SUM
----------+-----------
0         | NULL
```

Oracle computes the aggregate over the **entire input set**. COUNT returns 0; SUM returns NULL.

### 6.2. GROUP BY on an empty set returns 0 rows

```sql
SELECT
    department_id,
    COUNT(*) AS row_count,
    SUM(salary) AS salary_sum
FROM lab_agg_employees
WHERE department_id = 999
GROUP BY department_id;
```

The result has **0 rows**, because there are no input rows to form a `DEPARTMENT_ID` group. No group exists to return COUNT=0.

### 6.3. GROUP BY on a group with rows where all values are NULL

```sql
SELECT
    department_id,
    COUNT(*) AS row_count,
    COUNT(salary) AS known_salary_count,
    SUM(salary) AS salary_sum
FROM lab_agg_employees
WHERE department_id = 30
GROUP BY department_id;
```

The result has one row for department 30:

```text
DEPARTMENT_ID | ROW_COUNT | KNOWN_SALARY_COUNT | SALARY_SUM
--------------+-----------+--------------------+-----------
30            | 2         | 0                  | NULL
```

The group exists because there are two employees, even though no salary values are known.

### 6.4. NULL in GROUP BY forms a group

Oracle places rows with a NULL grouping key value into **one NULL group**:

```sql
SELECT
    department_id,
    COUNT(*) AS employee_count,
    COUNT(salary) AS known_salary_count,
    SUM(salary) AS salary_sum
FROM lab_agg_employees
GROUP BY department_id
ORDER BY department_id NULLS LAST;
```

Minh's row has `DEPARTMENT_ID NULL` and forms a separate group. In GROUP BY, NULLs are grouped together even though the comparison `NULL = NULL` in normal conditions does not return TRUE. These are two different SQL contexts.

## 7. Distinguishing empty sets from all-NULL sets using COUNT

SUM, AVG, MIN, and MAX can return NULL in both cases. Combine the count functions:

```sql
SELECT
    COUNT(*) AS input_rows,
    COUNT(salary) AS nonnull_salary_values,
    SUM(salary) AS salary_sum,
    CASE
        WHEN COUNT(*) = 0 THEN 'EMPTY INPUT'
        WHEN COUNT(salary) = 0 THEN 'ROWS EXIST, ALL SALARY NULL'
        ELSE 'HAS KNOWN SALARY'
    END AS input_state
FROM lab_agg_employees
WHERE department_id = :department_id;
```

If `:department_id` is bound to 20, 30, and 10 in turn:

| DEPARTMENT_ID | INPUT_ROWS | NONNULL_SALARY_VALUES | SALARY_SUM | INPUT_STATE |
| ---: | ---: | ---: | --- | --- |
| 20 | 0 | 0 | NULL | EMPTY INPUT |
| 30 | 2 | 0 | NULL | ROWS EXIST, ALL SALARY NULL |
| 10 | 3 | 2 | 3000 | HAS KNOWN SALARY |

This is a useful query pattern for reporting APIs. If you only return `SALARY_SUM`, the client cannot distinguish department 20 from department 30. If you also return the row count and known value count, the client has enough information to decide how to display it.

## 8. NVL and COALESCE: replacing NULL at the right moment

Where you place the NULL-replacement function changes the aggregate result.

### 8.1. NVL inside SUM

```sql
SELECT
    SUM(salary) AS sum_ignore_null,
    SUM(NVL(salary, 0)) AS sum_null_as_zero
FROM lab_agg_employees
WHERE department_id = 10;
```

For department 10, both equal 3000:

- `SUM(SALARY)` ignores NULL.
- `SUM(NVL(SALARY,0))` replaces Bình's NULL salary with 0 before summing.

The two expressions produce the same sum in this example, but they do not necessarily carry the same business meaning.

### 8.2. NVL outside SUM

```sql
SELECT
    NVL(SUM(salary), 0) AS display_salary_sum
FROM lab_agg_employees
WHERE department_id = 20;
```

Department 20 has no employees, so SUM returns NULL; the outer NVL turns the result into 0.

### 8.3. Comparison table of three cases

```sql
SELECT
    department_id,
    COUNT(*) AS row_count,
    COUNT(salary) AS known_count,
    SUM(salary) AS sum_original,
    SUM(NVL(salary, 0)) AS sum_nvl_inside,
    NVL(SUM(salary), 0) AS sum_nvl_outside
FROM lab_agg_employees
WHERE department_id IN (10, 20, 30, 40)
GROUP BY department_id
ORDER BY department_id;
```

Expected results:

| DEPARTMENT_ID | ROW_COUNT | KNOWN_COUNT | SUM_ORIGINAL | SUM_NVL_INSIDE | SUM_NVL_OUTSIDE |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 10 | 3 | 2 | 3000 | 3000 | 3000 |
| 30 | 2 | 0 | NULL | 0 | 0 |
| 40 | 1 | 1 | 0 | 0 | 0 |

Department 20 **does not appear** because this is a GROUP BY directly on the employees table: no rows means no group. Thus there is no row for either the inner or outer NVL to apply to.

If querying an aggregate over the whole set:

```sql
SELECT
    COUNT(*) AS row_count,
    SUM(salary) AS sum_original,
    SUM(NVL(salary, 0)) AS sum_nvl_inside,
    NVL(SUM(salary), 0) AS sum_nvl_outside
FROM lab_agg_employees
WHERE department_id = 20;
```

The result is `ROW_COUNT=0`, `SUM_ORIGINAL=NULL`, `SUM_NVL_INSIDE=NULL`, and `SUM_NVL_OUTSIDE=0`. Reason: SUM has no rows to add, even when the inner expression contains NVL.

**Rule:** `NVL(SUM(x),0)` turns a NULL sum result into 0, covering both the no-rows case and the all-NULL-x case. If you need to distinguish the two states, always return `COUNT(*)` and `COUNT(x)` as well.

### 8.4. AVG(NVL(x,0)) vs. NVL(AVG(x),0)

```sql
SELECT
    AVG(salary) AS avg_ignore_null,
    AVG(NVL(salary, 0)) AS avg_null_as_zero,
    NVL(AVG(salary), 0) AS avg_display_default
FROM lab_agg_employees
WHERE department_id = 10;
```

Department 10 has 1000, NULL, and 2000:

- `AVG(SALARY) = 1500`: the denominator is the two known values.
- `AVG(NVL(SALARY,0)) = 1000`: replaces NULL with 0, making the denominator three rows.
- `NVL(AVG(SALARY),0) = 1500`: computes the average over known values first, only replacing the final NULL result if there are no values to calculate.

This is a difference that can skew KPIs if NVL is accidentally placed inside AVG.

## 9. NULL in conditional aggregation

Conditional aggregation uses CASE inside COUNT/SUM/AVG to compute multiple metrics in a single query pass.

### 9.1. Counting qualifying rows with COUNT(CASE ...)

```sql
SELECT
    COUNT(*) AS all_employees,
    COUNT(CASE WHEN active_flag = 'Y' THEN 1 END) AS active_employees,
    COUNT(CASE WHEN active_flag = 'N' THEN 1 END) AS inactive_employees
FROM lab_agg_employees;
```

When the condition is not TRUE, CASE without ELSE returns NULL; `COUNT(expression)` ignores NULL. Therefore, the conditional count returns 0 if no rows match.

### 9.2. Counting using SUM of 0 and 1

```sql
SELECT
    SUM(CASE WHEN active_flag = 'Y' THEN 1 ELSE 0 END) AS active_employees,
    SUM(CASE WHEN active_flag = 'N' THEN 1 ELSE 0 END) AS inactive_employees
FROM lab_agg_employees;
```

On a set with rows, each row contributes 1 or 0. However, if the input set is empty, SUM of the expression is also NULL because there are no rows to sum. If you need a numeric 0 even on an empty set, you can use:

```sql
SELECT
    NVL(SUM(CASE WHEN active_flag = 'Y' THEN 1 ELSE 0 END), 0)
        AS active_employees
FROM lab_agg_employees
WHERE department_id = 20;
```

Or use `COUNT(CASE WHEN ... THEN 1 END)`, which returns 0 on an empty input set in an aggregate without GROUP BY.

### 9.3. Distinguishing no matching rows from NULL measure values

Example calculating total salary of active employees:

```sql
SELECT
    COUNT(CASE WHEN active_flag = 'Y' THEN 1 END) AS active_rows,
    COUNT(CASE WHEN active_flag = 'Y' THEN salary END) AS active_known_salaries,
    SUM(CASE WHEN active_flag = 'Y' THEN salary END) AS active_salary_sum
FROM lab_agg_employees
WHERE department_id = :department_id;
```

If a department has active employees but all salaries are NULL, `ACTIVE_ROWS` is greater than 0, `ACTIVE_KNOWN_SALARIES` equals 0, and `ACTIVE_SALARY_SUM` is NULL. If no employees match, both COUNTs are 0 and SUM is NULL. Combining these columns helps the client distinguish the cause.

### 9.4. ELSE 0 can change the meaning of the sum

These two expressions:

```sql
SUM(CASE WHEN active_flag = 'Y' THEN salary END)

SUM(CASE WHEN active_flag = 'Y' THEN salary ELSE 0 END)
```

behave differently:

- The first expression feeds only active rows' salaries into the aggregate; other rows return NULL and are ignored.
- The second expression feeds 0 for inactive rows. If rows exist but there are no active employees, the result may be 0 instead of NULL.
- If active rows have NULL salaries and there are no inactive rows contributing ELSE 0, the sum is still NULL.
- If the input set is empty, both SUMs are still NULL.

Clarify whether the KPI measures "the sum of known salaries of active employees" or "a sum under the convention that every inactive row equals 0." Do not use ELSE 0 just to avoid NULL on the screen.

## 10. OUTER JOIN generates NULLs: counting child rows properly

When joining departments to employees, `LEFT JOIN` retains departments without employees and adds a row where employee-side columns are NULL.

### 10.1. Comparing COUNT(*) and COUNT(employee_id)

```sql
SELECT
    d.department_id,
    d.department_name,
    COUNT(*) AS joined_rows,
    COUNT(e.employee_id) AS employee_count,
    COUNT(e.salary) AS known_salary_count,
    SUM(e.salary) AS salary_sum
FROM lab_agg_departments d
LEFT JOIN lab_agg_employees e
  ON e.department_id = d.department_id
GROUP BY d.department_id, d.department_name
ORDER BY d.department_id;
```

Logical result:

| DEPARTMENT_ID | DEPARTMENT_NAME | JOINED_ROWS | EMPLOYEE_COUNT | KNOWN_SALARY_COUNT | SALARY_SUM |
| ---: | --- | ---: | ---: | ---: | --- |
| 10 | Engineering | 3 | 3 | 2 | 3000 |
| 20 | Sales | 1 | 0 | 0 | NULL |
| 30 | Human Resources | 2 | 2 | 0 | NULL |
| 40 | Legal | 1 | 1 | 1 | 0 |

Department 20 has no employees:

- `COUNT(*) = 1` because LEFT JOIN creates one NULL-extended row for the department.
- `COUNT(e.employee_id) = 0` because the employee key in the padded row is NULL.
- `COUNT(e.salary) = 0` and `SUM(e.salary) = NULL`.

Department 30 has two real employees, both with NULL salaries:

- `COUNT(*) = 2` and `COUNT(e.employee_id) = 2`.
- `COUNT(e.salary) = 0` and `SUM(e.salary) = NULL`.

Therefore, combining `COUNT(e.employee_id)` and `COUNT(e.salary)` distinguishes **no employees** from **employees exist, but no salary yet**.

### 10.2. Condition in ON vs. WHERE

To keep all departments and join only active employees:

```sql
SELECT
    d.department_id,
    COUNT(e.employee_id) AS active_employee_count
FROM lab_agg_departments d
LEFT JOIN lab_agg_employees e
  ON e.department_id = d.department_id
 AND e.active_flag = 'Y'
GROUP BY d.department_id
ORDER BY d.department_id;
```

If you move `e.active_flag = 'Y'` to WHERE, the NULL-extended row for a department with no employees will be eliminated because the condition evaluates to UNKNOWN. The result will no longer retain every department.

This is why a query using LEFT JOIN can still return fewer departments than expected. Decide whether a filter restricts **which rows are matched** (usually in ON) or eliminates **results after the join** (WHERE).

### 10.3. NVL on SUM in an outer join

```sql
SELECT
    d.department_id,
    COUNT(e.employee_id) AS employee_count,
    COUNT(e.salary) AS known_salary_count,
    SUM(e.salary) AS salary_sum,
    NVL(SUM(e.salary), 0) AS salary_sum_display
FROM lab_agg_departments d
LEFT JOIN lab_agg_employees e
  ON e.department_id = d.department_id
GROUP BY d.department_id
ORDER BY d.department_id;
```

`SALARY_SUM_DISPLAY` equals 0 for both department 20 (no employees) and department 30 (employees exist, all salaries NULL). If the report needs to distinguish them, do not return only the NVL-wrapped column; also keep `EMPLOYEE_COUNT` and `KNOWN_SALARY_COUNT` or add a status label.

## 11. HAVING and groups with no aggregated values

`HAVING` filters groups after aggregates are computed. A condition like `HAVING SUM(salary) > 0` does not keep a group whose SUM is NULL, because `NULL > 0` evaluates to UNKNOWN.

### 11.1. Filtering groups with positive total salary

```sql
SELECT
    department_id,
    COUNT(*) AS employee_count,
    SUM(salary) AS salary_sum
FROM lab_agg_employees
GROUP BY department_id
HAVING SUM(salary) > 0
ORDER BY department_id NULLS LAST;
```

Department 30 is excluded because its SUM is NULL; department 40 with SUM 0 is also excluded; department 10 with SUM 3000 is kept. Minh's NULL department_id group has SUM 500, so it is also kept.

### 11.2. Filtering groups with employees but no salaries yet

```sql
SELECT
    department_id,
    COUNT(*) AS employee_count,
    COUNT(salary) AS known_salary_count,
    SUM(salary) AS salary_sum
FROM lab_agg_employees
GROUP BY department_id
HAVING COUNT(*) > 0
   AND COUNT(salary) = 0
ORDER BY department_id NULLS LAST;
```

In a direct GROUP BY query, every group already has at least one row; `COUNT(*) > 0` may be redundant, but writing it clarifies intent. The result is department 30: two employees and no known salaries.

### 11.3. HAVING SUM IS NULL is not enough to detect an all-NULL group

```sql
SELECT department_id, COUNT(*) AS employee_count, SUM(salary) AS salary_sum
FROM lab_agg_employees
GROUP BY department_id
HAVING SUM(salary) IS NULL;
```

In a direct GROUP BY, this query selects groups that have rows where all salaries are NULL (department 30). However, if the data comes from an OUTER JOIN, a department group with no employees also has a NULL SUM. In that case, you must also check `COUNT(employee_id)` to tell them apart.

## 12. Aggregates after JOIN can be multiplied

A common reporting bug is summing amounts after joining two independent child tables. Suppose an order has two payment rows and three note rows; if you join both child tables on `ORDER_ID`, each payment row appears three times.

Conceptual example:

```text
ORDERS (one order)
    |
    +---- PAYMENTS: 2 rows
    |
    +---- NOTES:    3 rows

JOIN both child tables on ORDER_ID:
    2 x 3 = 6 rows

SUM(payment_amount) after JOIN may be multiplied by 3.
```

The SUM function is not mishandling NULLs; **the input set to SUM simply contains more copies than expected**.

### 12.1. Aggregate each child table before joining

```sql
WITH payment_totals AS (
    SELECT order_id, SUM(payment_amount) AS paid_amount
    FROM order_payments
    GROUP BY order_id
),
note_counts AS (
    SELECT order_id, COUNT(*) AS note_count
    FROM order_notes
    GROUP BY order_id
)
SELECT
    o.order_id,
    NVL(p.paid_amount, 0) AS paid_amount,
    NVL(n.note_count, 0) AS note_count
FROM orders o
LEFT JOIN payment_totals p
  ON p.order_id = o.order_id
LEFT JOIN note_counts n
  ON n.order_id = o.order_id;
```

Each CTE has at most one row per order_id, so the join does not multiply payment rows by note rows. If you need to distinguish "no payments" from "payments exist but all payment_amounts are NULL," include `COUNT(*)` and `COUNT(payment_amount)` in the payment_totals CTE.

## 13. Scalar subqueries and empty sets

A scalar aggregate subquery without GROUP BY still returns one row:

```sql
SELECT
    (SELECT COUNT(*)
       FROM lab_agg_employees
      WHERE department_id = 999) AS employee_count,
    (SELECT SUM(salary)
       FROM lab_agg_employees
      WHERE department_id = 999) AS salary_sum
FROM dual;
```

Result of the outer SELECT:

```text
EMPLOYEE_COUNT | SALARY_SUM
---------------+-----------
0              | NULL
```

If a scalar subquery **without GROUP BY** uses SUM/COUNT, it returns one aggregated row as shown above. If a scalar subquery has GROUP BY and forms no groups, the subquery returns 0 rows; when used as a scalar expression, the corresponding value becomes NULL.

Example:

```sql
SELECT
    (SELECT COUNT(*)
       FROM lab_agg_employees
      WHERE department_id = 999
      GROUP BY department_id) AS grouped_count
FROM dual;
```

The subquery forms no groups because department 999 has no employees; the scalar expression in the outer query receives NULL. Difference:

- Aggregate without GROUP BY: `COUNT(*)` returns 0.
- Aggregate with GROUP BY and no groups: no row to fetch, so the scalar subquery becomes NULL.

This is why you must inspect the **query block structure**, not just the COUNT function name.

## 14. DISTINCT and NULL in aggregates

`COUNT(DISTINCT expr)` ignores NULL:

```sql
SELECT
    COUNT(*) AS total_rows,
    COUNT(salary) AS nonnull_rows,
    COUNT(DISTINCT salary) AS distinct_salaries
FROM lab_agg_employees
WHERE department_id = 10;
```

Results are 3, 2, 2.

Meanwhile, `SELECT DISTINCT salary` can return a NULL row if the data contains NULL:

```sql
SELECT DISTINCT salary
FROM lab_agg_employees
WHERE department_id = 10
ORDER BY salary NULLS LAST;
```

The result has 1000, 2000, and one NULL row. Do not confuse `SELECT DISTINCT` with `COUNT(DISTINCT ...)`: SELECT DISTINCT retains one NULL representative in the result set; COUNT DISTINCT does not count NULL.

## 15. Aggregate functions with CASE and NULL conditions

CASE lets you define precisely which values enter the aggregate.

### 15.1. Counting employees with known salaries by department

```sql
SELECT
    department_id,
    COUNT(CASE WHEN salary IS NOT NULL THEN 1 END) AS known_salary_count,
    COUNT(CASE WHEN salary IS NULL THEN 1 END) AS missing_salary_count
FROM lab_agg_employees
GROUP BY department_id
ORDER BY department_id NULLS LAST;
```

Unmatched branches have no ELSE and therefore return NULL; COUNT ignores them. The result for department 30 is 0 known and 2 missing.

### 15.2. Conditional SUM

```sql
SELECT
    department_id,
    SUM(CASE WHEN active_flag = 'Y' THEN salary END) AS active_salary_sum,
    COUNT(CASE WHEN active_flag = 'Y' THEN 1 END) AS active_count,
    COUNT(CASE WHEN active_flag = 'Y' THEN salary END) AS active_known_salary_count
FROM lab_agg_employees
GROUP BY department_id
ORDER BY department_id NULLS LAST;
```

For department 30, there are two active employees, but no known salaries. Result: `ACTIVE_COUNT=2`, `ACTIVE_KNOWN_SALARY_COUNT=0`, and `ACTIVE_SALARY_SUM=NULL`.

### 15.3. Distinguishing no active rows from active rows with NULL salary

If a department has employees but all are inactive, `ACTIVE_COUNT` is 0 and `ACTIVE_KNOWN_SALARY_COUNT` is also 0; the active salary sum is NULL. If a department has no employees, the same three aggregates can also yield 0/0/NULL in an ungrouped whole-set aggregate. To distinguish them, add `COUNT(*)` or `COUNT(e.employee_id)`.

This is a general rule: **an aggregate filtered by CASE only describes the subset of data passed into the function**; it does not on its own tell you how many rows existed in the source set before the CASE condition.

## 16. Choosing display values in reports

Reports should not always display NULL. However, if you convert NULL to 0, preserve status information so users do not misinterpret it.

### 16.1. A status-aware report design

```sql
SELECT
    d.department_id,
    d.department_name,
    COUNT(e.employee_id) AS employee_count,
    COUNT(e.salary) AS known_salary_count,
    SUM(e.salary) AS salary_sum,
    CASE
        WHEN COUNT(e.employee_id) = 0 THEN 'NO EMPLOYEES'
        WHEN COUNT(e.salary) = 0 THEN 'SALARY NOT RECORDED'
        ELSE 'HAS SALARY DATA'
    END AS salary_data_state,
    CASE
        WHEN COUNT(e.employee_id) = 0 THEN 0
        WHEN COUNT(e.salary) = 0 THEN NULL
        ELSE SUM(e.salary)
    END AS salary_total_for_report
FROM lab_agg_departments d
LEFT JOIN lab_agg_employees e
  ON e.department_id = d.department_id
GROUP BY d.department_id, d.department_name
ORDER BY d.department_id;
```

In this example:

- Department 20: has no employees; the report can display a total of 0 per the chosen policy.
- Department 30: has employees, but salaries are not yet recorded; keep NULL to indicate unknown.
- Department 40: actual salary is 0; status is HAS SALARY DATA and total is 0.

Thus, department 20 and department 40 both have a display value of 0, yet **different data states**. Department 30 is NULL because no salary values exist yet. This is a clearer report design than applying NVL to every case.

### 16.2. APIs should return both metrics and state

A report response might contain:

```json
{
  "departmentId": 30,
  "employeeCount": 2,
  "knownSalaryCount": 0,
  "salarySum": null,
  "salaryDataState": "SALARY_NOT_RECORDED"
}
```

For department 20, the response might be:

```json
{
  "departmentId": 20,
  "employeeCount": 0,
  "knownSalaryCount": 0,
  "salarySum": 0,
  "salaryDataState": "NO_EMPLOYEES"
}
```

This is just an illustrative API convention; what matters is that the backend does not erase the difference between **no employees**, **salary unknown**, and **salary equals 0** if the business needs to distinguish them.

## 17. Common mistakes

| Symptom | Common wrong conclusion | Correct understanding |
| --- | --- | --- |
| SUM returns NULL | "The total is 0" | Either there are no rows or every expression value is NULL |
| COUNT(*) returns 0, but client sees a row | "There is one row of NULL data" | An aggregate without GROUP BY returns one row with COUNT equal to 0 |
| GROUP BY returns no rows | "COUNT didn't run" | An empty set forms no groups; there are no aggregate rows to return |
| COUNT(*) differs from COUNT(column) | "Oracle undercounted" | COUNT(column) ignores NULL values; COUNT(*) counts rows |
| COUNT(DISTINCT column) is lower than COUNT(column) | "Data is missing rows" | COUNT DISTINCT collapses duplicates and ignores NULL |
| AVG is smaller than hand-calculated | Divided total by COUNT(*) | AVG divides by the number of non-NULL values |
| SUM(NVL(x,0)) is 0 while SUM(x) is NULL | "NVL only changes formatting" | Inner NVL replaces each value before aggregation |
| AVG(NVL(x,0)) is lower than AVG(x) | "Oracle miscalculated AVG" | NULL values are replaced with 0 and included in the denominator |
| LEFT JOIN gives COUNT(*) = 1 for childless parent | "There is one child" | The NULL-extended row is still counted by COUNT(*) |
| LEFT JOIN has NULL SUM | "There are no children" | Either no children exist or children exist with all NULL measures |
| Report SUM increases after adding a JOIN | "SUM is buggy" | A 1-to-many join can multiply rows before aggregation |
| HAVING SUM(x) > 0 drops all-NULL group | "The group vanished" | NULL > 0 is UNKNOWN; HAVING keeps only TRUE |
| SELECT DISTINCT includes a NULL row, but COUNT DISTINCT = 0 | "The two DISTINCTs contradict each other" | SELECT DISTINCT keeps one NULL; COUNT DISTINCT ignores NULL |
| Aggregate scalar subquery returns NULL | "Outer query has no rows" | A 0-row scalar subquery becomes NULL; the outer query can still return rows |

## Summary

When using aggregate functions in Oracle, always check **the number of input rows** and **the number of non-NULL values**. `COUNT(*)` counts rows, `COUNT(expression)` counts non-NULL values, and `SUM`/`AVG`/`MIN`/`MAX` ignore NULL. Aggregates without GROUP BY still return one row on an empty set; GROUP BY on an empty set forms no groups. Hence a NULL SUM can mean either no rows or rows exist with all NULL measure values.

OUTER JOIN adds NULL-extended rows, so `COUNT(*)` can be 1 even when no child rows exist; count the child-side key instead. When joining multiple 1-to-many relationships, check the grain and aggregate each source before joining to avoid multiplying totals. Use `NVL`/`COALESCE` only when replacement semantics are clearly defined, and retain counts/status if the report must distinguish **no data**, **data not yet recorded**, and **value equal to 0**.
