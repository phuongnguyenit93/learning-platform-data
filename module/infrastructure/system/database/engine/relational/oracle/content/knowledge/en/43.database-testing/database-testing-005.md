# Testing SQL with NULL, Empty Strings, Duplicates, and Unicode

Testing SQL in Oracle requires attention to the differences between how a Java application represents data and how Oracle stores, compares, constrains, sorts, and returns data. Four scenario groups are especially error-prone:

- **NULL:** represents an unknown or missing value. SQL uses three-valued logic, so comparisons with `NULL` do not behave like standard comparisons.
- **Empty strings:** Oracle treats zero-length character strings as `NULL` for standard character types. A string containing only spaces is still non-`NULL` data.
- **Duplicate data:** duplicates can mean full-row duplicates, business-key duplicates, duplicates after normalization, or collation-equivalent duplicates. `UNIQUE` constraints, `GROUP BY`, and application logic each play distinct roles.
- **Unicode:** one character may require multiple bytes, one displayed character may comprise multiple code points, and two visually identical strings may have different Unicode representations. Character sets, length semantics, JDBC binding, and collation all affect results.

The objective of this lesson is to build a reproducible test suite, determine precisely what Oracle is storing, and understand why a predicate, constraint, or comparison yields a specific outcome. Examples use Oracle SQL and Java JDBC; table names, data, and configuration values are illustrative only.

## 1. Why test edge cases?

A SQL query may pass with normal data yet fail when a column contains `NULL`, an empty string, spaces, Unicode values, or repeated business keys.

For example, an application might send an empty string for a notes field. Java distinguishes `null` from an empty string, but when bound to an Oracle `VARCHAR2` column, an empty string is treated as `NULL`. If a query compares against an empty string literal, the result will not match rows the way some other databases behave.

Similarly, a system might check beforehand whether an email exists before inserting. Two concurrent requests can both pass the `SELECT` check and both attempt `INSERT`. Only a `UNIQUE` constraint acts as the final safeguard guaranteeing uniqueness at the database layer.

With Unicode, the character "é" can be represented as a single precomposed code point or as the letter "e" followed by a combining acute accent. Two visually identical strings have different byte sequences. Binary comparison, normalization, and collation can produce different results.

### 1.1 Layers to test

| Layer | Question to answer |
|---|---|
| Java input | How are `null`, empty, blank, and whitespace distinguished? |
| JDBC binding | Do `setString`, `setNull`, and `setNString` send the expected data type? |
| Oracle storage | Is the stored value `NULL`, an empty LOB, or a string of spaces? |
| SQL semantics | How do predicates, `JOIN`, `GROUP BY`, and aggregates handle `NULL`? |
| Constraints | Which cases do `UNIQUE`, `CHECK`, `NOT NULL`, and foreign keys permit? |
| Character set | Can characters be represented fully in the database character set? |
| Length | Are limits measured in bytes or characters? |
| Collation | How are case, accents, and Unicode-equivalent strings compared? |
| Concurrency | Can two transactions writing the same key concurrently create duplicates? |
| Regression | Are results consistent across environments and versions? |

### 1.2 Principles for designing tests

A good test must specify:

- The original input sent from the application.
- The target column data type.
- The bind parameter type.
- Relevant NLS/session settings.
- The data after storage.
- The SQL used to read it back.
- The expected result.
- Whether the transaction commits or rolls back.

Do not rely solely on how a string looks on screen. `NULL`, an empty string, and a space-only string can render identically in a UI. Also inspect `IS NULL`, `LENGTH`, `LENGTHB`, `DUMP`, or byte sequences when necessary.

## 2. Creating a reproducible test environment

Use a dedicated schema or clearly named test tables. Never run test `INSERT`s, `DELETE`s, or NLS changes against production business tables just to verify a hypothesis.

Example test table:

~~~sql
CREATE TABLE sql_edge_case_test (
    test_id       NUMBER GENERATED BY DEFAULT AS IDENTITY,
    case_name     VARCHAR2(100 CHAR),
    varchar_value VARCHAR2(100 CHAR),
    char_value    CHAR(10 CHAR),
    number_value  NUMBER,
    created_at    TIMESTAMP WITH TIME ZONE DEFAULT SYSTIMESTAMP,
    CONSTRAINT sql_edge_case_test_pk PRIMARY KEY (test_id)
);
~~~

Defining `CHAR`/`VARCHAR2` with explicit `CHAR` semantics prevents tests from depending on the `NLS_LENGTH_SEMANTICS` of the session that created the table.

If the Oracle version or schema policy disallows identity columns, use a sequence and trigger or supply `test_id` from the application.

### 2.1 Using transactions and rollback

Tests can run inside an isolated transaction:

~~~sql
SAVEPOINT before_edge_case_test;

INSERT INTO sql_edge_case_test (
    case_name,
    varchar_value,
    char_value,
    number_value
)
VALUES (
    'null-case',
    NULL,
    'A',
    10
);

-- Run verification queries here.

ROLLBACK TO before_edge_case_test;
~~~

If a test must verify data from another session or through a connection pool, commit inside the test schema and include a dedicated cleanup step. `ROLLBACK` only undoes the current transaction; it does not remove data committed by another session.

### 2.2 Recording the environment

Test results can depend on database version, character set, NLS settings, and JDBC driver. Collect the following before running:

~~~sql
SELECT * FROM v$version;

SELECT parameter, value
FROM nls_database_parameters
WHERE parameter IN (
    'NLS_CHARACTERSET',
    'NLS_NCHAR_CHARACTERSET'
);

SELECT parameter, value
FROM nls_session_parameters
WHERE parameter IN (
    'NLS_COMP',
    'NLS_SORT',
    'NLS_LENGTH_SEMANTICS',
    'NLS_LANGUAGE',
    'NLS_TERRITORY',
    'NLS_DATE_LANGUAGE'
)
ORDER BY parameter;
~~~

Querying `V$VERSION` may require privileges. If unavailable, record the version via administrative tools or a DBA.

`NLS_LENGTH_SEMANTICS` provides the default when creating certain character columns if DDL omits `BYTE` or `CHAR`. It does not retroactively change the semantics of existing columns. Declare lengths explicitly in DDL and do not rely on implicit session defaults.

## 3. NULL in Oracle and three-valued logic

In SQL, `NULL` represents an unknown or absent value. `NULL` is not zero, not an empty string, not `FALSE`, and not a value that can be compared using a standard equality operator.

SQL uses three-valued logic:

- `TRUE`
- `FALSE`
- `UNKNOWN`

When an expression compares against `NULL`, the result is typically `UNKNOWN`. In a `WHERE` clause, only rows evaluating to `TRUE` are kept; both `FALSE` and `UNKNOWN` are filtered out.

### 3.1 Proper comparison with NULL

Do not use:

~~~sql
SELECT *
FROM employees
WHERE commission_pct = NULL;
~~~

This expression will not find rows where `commission_pct` is `NULL`, because the comparison evaluates to `UNKNOWN`.

Use:

~~~sql
SELECT *
FROM employees
WHERE commission_pct IS NULL;
~~~

And:

~~~sql
SELECT *
FROM employees
WHERE commission_pct IS NOT NULL;
~~~

This is the standard `NULL`-checking syntax.

### 3.2 Basic truth table

| Expression | Result |
|---|---|
| `5 = 5` | `TRUE` |
| `5 = 6` | `FALSE` |
| `5 = NULL` | `UNKNOWN` |
| `NULL = NULL` | `UNKNOWN` |
| `5 <> NULL` | `UNKNOWN` |
| `NULL IS NULL` | `TRUE` |
| `NULL IS NOT NULL` | `FALSE` |
| `NOT UNKNOWN` | `UNKNOWN` |

Key takeaway: `NULL` does not equal `NULL` under equality comparison. If you need to check whether two values share the same `NULL` state or are equal, write explicit logic.

### 3.3 AND, OR, and NOT

Three-valued logic affects compound conditions:

| A | B | A AND B | A OR B |
|---|---|---|---|
| `TRUE` | `TRUE` | `TRUE` | `TRUE` |
| `TRUE` | `FALSE` | `FALSE` | `TRUE` |
| `TRUE` | `UNKNOWN` | `UNKNOWN` | `TRUE` |
| `FALSE` | `UNKNOWN` | `FALSE` | `UNKNOWN` |
| `UNKNOWN` | `UNKNOWN` | `UNKNOWN` | `UNKNOWN` |

Example:

~~~sql
SELECT *
FROM employees
WHERE department_id = 10
   OR commission_pct IS NULL;
~~~

A row with `department_id = 10` is still selected even if `commission_pct` is `NULL`, because `TRUE OR UNKNOWN` evaluates to `TRUE`.

Conversely:

~~~sql
SELECT *
FROM employees
WHERE department_id = 10
  AND commission_pct > 0;
~~~

If `commission_pct` is `NULL`, the second condition is `UNKNOWN`; `TRUE AND UNKNOWN` is `UNKNOWN`, so the row is excluded.

### 3.4 NOT does not turn UNKNOWN into TRUE

Example:

~~~sql
SELECT *
FROM employees
WHERE NOT (commission_pct = 0);
~~~

Rows where `commission_pct` is `NULL` are not returned. Because `NULL = 0` is `UNKNOWN`, and `NOT UNKNOWN` remains `UNKNOWN`.

If business logic intends to fetch all rows with non-zero commission or no commission set, write:

~~~sql
SELECT *
FROM employees
WHERE commission_pct <> 0
   OR commission_pct IS NULL;
~~~

Never assume `NOT` in front of an expression automatically includes `NULL` values.

## 4. Operations with NULL

### 4.1 Arithmetic operations

Arithmetic operations with a `NULL` operand normally return `NULL`:

~~~sql
SELECT
    100 + NULL AS add_result,
    100 - NULL AS subtract_result,
    100 * NULL AS multiply_result,
    100 / NULL AS divide_result
FROM dual;
~~~

All resulting columns are `NULL`.

If `NULL` must be substituted with a business value, apply an explicit rule:

~~~sql
SELECT salary + NVL(commission, 0) AS total_compensation
FROM employee_pay;
~~~

Substitute `NULL` with `0` only when business rules define "no commission" as equivalent to `0`. Do not blindly replace every `NULL` with `0`, as `NULL` may mean unknown or unentered.

### 4.2 String concatenation in Oracle

Oracle has distinct string concatenation behavior: concatenating a character string with `NULL` or a zero-length string normally returns the other string; concatenating two `NULL` values yields `NULL`. This is Oracle's rule for character concatenation and should be tested per version.

Example:

~~~sql
SELECT
    'Oracle' || NULL AS result_one,
    NULL || 'JDBC' AS result_two,
    NULL || NULL AS result_three
FROM dual;
~~~

Do not generalize this concatenation behavior to comparisons or arithmetic operations. Oracle could change empty string handling in the future; applications should not rely on treating `NULL` and empty as two separate states for `VARCHAR2`.

### 4.3 Aggregate functions

Aggregate functions generally ignore `NULL` in input expressions:

~~~sql
SELECT
    COUNT(*) AS all_rows,
    COUNT(commission_pct) AS rows_with_commission,
    SUM(commission_pct) AS commission_sum,
    AVG(commission_pct) AS commission_average,
    MIN(commission_pct) AS minimum_commission,
    MAX(commission_pct) AS maximum_commission
FROM employees;
~~~

- `COUNT(*)` counts all rows.
- `COUNT(column)` counts only non-`NULL` values.
- `SUM`, `AVG`, `MIN`, and `MAX` ignore `NULL`.
- When there are no non-`NULL` values, many aggregates return `NULL`; `COUNT` returns `0`.

If `AVG` should treat `NULL` as `0`, write `AVG(NVL(column, 0))`, noting that the business result changes because `NULL` rows enter the denominator.

### 4.4 GROUP BY and DISTINCT

`GROUP BY` groups all `NULL` values together into a single group:

~~~sql
SELECT department_id, COUNT(*)
FROM employees
GROUP BY department_id;
~~~

Rows with `NULL` `department_id` are collected into one group.

`DISTINCT` also returns only one `NULL` result:

~~~sql
SELECT DISTINCT department_id
FROM employees;
~~~

This differs from how `UNIQUE` constraints treat `NULL`. `GROUP BY`/`DISTINCT` are query result grouping operations; `UNIQUE` is a write-time data integrity rule.

### 4.5 ORDER BY

Oracle defaults to `NULLS LAST` for `ASC` and `NULLS FIRST` for `DESC`. For clear, stable test results, specify this explicitly:

~~~sql
SELECT employee_id, commission_pct
FROM employees
ORDER BY commission_pct ASC NULLS FIRST;
~~~

Or:

~~~sql
ORDER BY commission_pct DESC NULLS LAST;
~~~

Results can vary if `NULLS FIRST`/`LAST` is omitted or no tie-breaker exists for equal values.

## 5. NOT IN, NOT EXISTS, and NULL

A common bug is using `NOT IN` with a subquery that can return `NULL`.

Example:

~~~sql
SELECT customer_id
FROM customers
WHERE customer_id NOT IN (
    SELECT customer_id
    FROM blocked_customers
);
~~~

If the subquery returns even a single `NULL`, the `NOT IN` condition evaluates to `UNKNOWN` for non-matching values, causing the query to return fewer rows or zero rows.

### 5.1 Illustrative example

Suppose `blocked_customers` contains:

| customer_id |
|---:|
| 10 |
| 20 |
| NULL |

The equivalent condition is:

~~~sql
customer_id <> 10
AND customer_id <> 20
AND customer_id <> NULL
~~~

For `customer_id = 30`, the first two conditions are `TRUE`, but the last condition is `UNKNOWN`. `TRUE AND TRUE AND UNKNOWN` is `UNKNOWN`, so the row is excluded.

### 5.2 Using NOT EXISTS

To retrieve customers without a matching blocked record:

~~~sql
SELECT c.customer_id
FROM customers c
WHERE NOT EXISTS (
    SELECT 1
    FROM blocked_customers b
    WHERE b.customer_id = c.customer_id
);
~~~

`NOT EXISTS` checks whether a matching row exists, avoiding the side effect of an unrelated `NULL` in the subset.

If `c.customer_id` can be `NULL`, the equality predicate in the subquery will not match `NULL` to `NULL`. Explicitly decide whether a customer with a `NULL` ID should be treated as unblocked or filtered out via `IS NOT NULL`.

### 5.3 When is NOT IN still usable?

`NOT IN` can be used if the subquery is guaranteed never to return `NULL`, such as a column with a `NOT NULL` constraint or an explicit filter:

~~~sql
SELECT c.customer_id
FROM customers c
WHERE c.customer_id NOT IN (
    SELECT b.customer_id
    FROM blocked_customers b
    WHERE b.customer_id IS NOT NULL
);
~~~

Even so, `NOT EXISTS` generally expresses an anti-join more clearly when relating two tables.

## 6. NVL, COALESCE, NULLIF, and CASE

Null-handling functions serve different purposes. Choose the function by semantics, not merely shorthand syntax.

### 6.1 NVL

`NVL` returns the second expression if the first expression is `NULL`:

~~~sql
SELECT NVL(commission_pct, 0)
FROM employees;
~~~

Note that `NVL` applies data type conversion rules. Oracle may convert `expr2` to `expr1`'s type or apply numeric precedence rules. Use compatible types and test when combining `VARCHAR2`, `NUMBER`, or `DATE`.

Because an empty string is `NULL` for `VARCHAR2`, the following expression does not produce an empty string fallback:

~~~sql
SELECT NVL(varchar_value, '')
FROM sql_edge_case_test;
~~~

If `varchar_value` is `NULL`, the fallback value is also `NULL`. Use a genuinely non-empty value if the business case requires displaying a placeholder.

### 6.2 COALESCE

`COALESCE` returns the first non-`NULL` expression:

~~~sql
SELECT COALESCE(mobile_phone, work_phone, home_phone, 'No phone number')
FROM contacts;
~~~

`COALESCE` supports multiple arguments and uses short-circuit evaluation. Expressions must have compatible data types.

### 6.3 NULLIF

`NULLIF` returns `NULL` when two expressions are equal; otherwise it returns the first expression:

~~~sql
SELECT numerator / NULLIF(denominator, 0)
FROM calculations;
~~~

This example prevents division by zero. If `denominator` is `0`, `NULLIF` returns `NULL`, and the division yields `NULL` instead of a divide-by-zero error. If the business case requires raising an error or returning a substitute value, handle it explicitly.

### 6.4 CASE

`CASE` expresses rules clearly:

~~~sql
SELECT
    CASE
        WHEN commission_pct IS NULL THEN 'NOT_SET'
        WHEN commission_pct = 0 THEN 'ZERO'
        ELSE 'HAS_VALUE'
    END AS commission_state
FROM employees;
~~~

`WHEN` branch ordering matters. The `IS NULL` branch must be written explicitly; never write `commission_pct = NULL`.

### 6.5 DECODE and NULL

Oracle `DECODE` has special behavior: two `NULL` values in `DECODE` comparison expressions are considered equal. This differs from the standard equality operator.

~~~sql
SELECT DECODE(NULL, NULL, 'MATCH', 'NO_MATCH')
FROM dual;
~~~

The result is `MATCH`.

Do not mechanically replace `DECODE` with equality expressions or vice versa. For new logic, `CASE` is usually more readable and ANSI-SQL compliant; when `NULL`-safe comparison is needed, write `IS NULL`/`IS NOT NULL` explicitly.

## 7. Empty strings in Oracle

For standard character types, Oracle currently treats a zero-length string as `NULL`. Example:

~~~sql
INSERT INTO sql_edge_case_test (case_name, varchar_value)
VALUES ('empty-varchar', '');
~~~

When reading back:

~~~sql
SELECT
    varchar_value,
    CASE WHEN varchar_value IS NULL THEN 'IS_NULL'
         ELSE 'NOT_NULL'
    END AS null_state,
    LENGTH(varchar_value) AS char_length
FROM sql_edge_case_test
WHERE case_name = 'empty-varchar';
~~~

`varchar_value` is treated as `NULL`, and `LENGTH` returns `NULL`.

### 7.1 NULL, empty, and blank

Distinguish the following inputs:

| Application input | Example | Typical behavior with `VARCHAR2` |
|---|---|---|
| Java `null` | `null` | SQL `NULL` if bound properly as null |
| Empty string | `""` | Oracle treats as `NULL` |
| Single space | `" "` | String containing one space character |
| Multiple spaces | `"   "` | String containing space characters |
| Tab | TAB character | Non-empty string if stored |
| Non-breaking space | `U+00A0` | Unicode character distinct from ASCII space |
| Text string | `"Oracle"` | Normal character value |

Do not use trimming or length checks as a one-size-fits-all substitute for all concepts. For instance, a string containing tabs or non-breaking spaces may not be handled identically to ASCII spaces.

### 7.2 Inspecting with LENGTH and DUMP

Example:

~~~sql
SELECT
    case_name,
    CASE WHEN varchar_value IS NULL THEN 'NULL'
         ELSE 'NOT NULL'
    END AS null_state,
    LENGTH(varchar_value) AS char_len,
    LENGTHB(varchar_value) AS byte_len,
    DUMP(varchar_value, 1016) AS dump_value
FROM sql_edge_case_test
ORDER BY test_id;
~~~

- `IS NULL` confirms `NULL`.
- `LENGTH` counts length according to Oracle character semantics.
- `LENGTHB` returns length in bytes.
- `DUMP` shows the data type and byte representation in the chosen format.

`DUMP(NULL)` also returns `NULL`; do not use `DUMP` alone to distinguish an empty string from `NULL` in `VARCHAR2`, as Oracle already normalizes empty strings to `NULL`.

### 7.3 CHAR has blank padding

`CHAR(n)` is a fixed-length type. Oracle pads trailing spaces up to the declared length. For example, `CHAR(10)` stores `'A'` as a blank-padded value.

~~~sql
INSERT INTO sql_edge_case_test (case_name, char_value)
VALUES ('char-one-letter', 'A');
~~~

Reading back:

~~~sql
SELECT
    char_value,
    LENGTH(char_value) AS char_len,
    LENGTHB(char_value) AS byte_len,
    DUMP(char_value, 1016) AS dump_value
FROM sql_edge_case_test
WHERE case_name = 'char-one-letter';
~~~

`CHAR` can return a length including trailing padding spaces per type semantics. `VARCHAR2` does not automatically pad to a fixed length.

### 7.4 Space-only strings are not NULL

Example:

~~~sql
INSERT INTO sql_edge_case_test (case_name, varchar_value)
VALUES ('one-space', ' ');
~~~

This row has a non-`NULL` `varchar_value`. `LENGTH` normally returns `1` for an ASCII space; `LENGTHB` also normally returns `1` under `AL32UTF8`.

If the application calls `trim()` before binding, a space-only string turns into an empty string and is subsequently stored by Oracle as `NULL`. This is a business behavior change that must be explicitly decided.

### 7.5 EMPTY_CLOB is different from NULL

`CLOB` uses a LOB locator and has a distinct empty LOB representation. `EMPTY_CLOB()` creates an empty LOB with a locator, which differs from `NULL`.

Example:

~~~sql
CREATE TABLE lob_edge_case_test (
    id NUMBER PRIMARY KEY,
    note_clob CLOB
);

INSERT INTO lob_edge_case_test (id, note_clob)
VALUES (1, NULL);

INSERT INTO lob_edge_case_test (id, note_clob)
VALUES (2, EMPTY_CLOB());

SELECT
    id,
    CASE WHEN note_clob IS NULL THEN 'NULL'
         ELSE 'NOT_NULL'
    END AS lob_state,
    CASE WHEN note_clob IS NOT NULL
         THEN DBMS_LOB.GETLENGTH(note_clob)
    END AS lob_length
FROM lob_edge_case_test
ORDER BY id;
~~~

Row 1 has a `NULL` locator; row 2 has an empty LOB locator of length `0`. This is a case where the `VARCHAR2` empty-string rule must not be applied mechanically.

## 8. Testing NULL and empty strings through JDBC

Java distinguishes `null` and empty strings. Oracle JDBC binding must be tested to verify what the database receives.

### 8.1 Binding Java null

Use `setNull` with an explicit JDBC type:

~~~java
String sql =
    "INSERT INTO sql_edge_case_test (case_name, varchar_value) " +
    "VALUES (?, ?)";

try (Connection connection = dataSource.getConnection();
     PreparedStatement statement = connection.prepareStatement(sql)) {

    statement.setString(1, "java-null");
    statement.setNull(2, java.sql.Types.VARCHAR);
    statement.executeUpdate();
}
~~~

`setString(index, null)` works in many cases, but `setNull` with an explicit SQL type makes intent clear and avoids type inference issues in certain APIs/frameworks.

### 8.2 Binding an empty string

~~~java
statement.setString(2, "");
~~~

With `VARCHAR2`, Oracle treats an empty string as `NULL`. If the application must distinguish between "user did not enter a value" and "user explicitly cleared the content", store a separate status flag or use a different data model. You cannot rely on `VARCHAR2` alone to distinguish these two states using `null` versus empty string.

### 8.3 Binding a space-only string

~~~java
statement.setString(2, "   ");
~~~

This is a non-`NULL` string containing data. If business rules consider blank strings equivalent to no value, normalize at one well-defined layer and test spaces, tabs, line breaks, and Unicode whitespace.

### 8.4 NCHAR/NVARCHAR2 types

For `NCHAR`/`NVARCHAR2` columns, JDBC provides N-string APIs such as `setNString` and `getNString`:

~~~java
String sql =
    "INSERT INTO unicode_test (national_text) VALUES (?)";

try (PreparedStatement statement = connection.prepareStatement(sql)) {
    statement.setNString(1, "Tiếng Việt 日本語");
    statement.executeUpdate();
}
~~~

Use `setNString` for national character types when appropriate for the driver. For `VARCHAR2`, `setString` is usually the natural choice because data is stored using the database character set.

Do not switch back and forth between `VARCHAR2` and `NVARCHAR2` merely to "fix Unicode" without understanding the database character set, national character set, and implicit conversions.

## 9. UNIQUE constraints and NULL

A `UNIQUE` constraint enforces uniqueness across one or more columns. In Oracle, `NULL` has special semantics:

- A single-column `UNIQUE` constraint permits multiple rows containing `NULL`.
- For composite unique keys, cases with `NULL` components have specific semantics; test the exact column combination and Oracle version in use rather than inferring from equality comparisons.
- `PRIMARY KEY` disallows `NULL` and enforces uniqueness.
- If business rules require a value to be present, combine `NOT NULL` with `UNIQUE`.

Example:

~~~sql
CREATE TABLE user_alias_test (
    id NUMBER PRIMARY KEY,
    alias VARCHAR2(100),
    CONSTRAINT user_alias_test_uk UNIQUE (alias)
);
~~~

Multiple rows with `NULL` alias can be inserted:

~~~sql
INSERT INTO user_alias_test (id, alias) VALUES (1, NULL);
INSERT INTO user_alias_test (id, alias) VALUES (2, NULL);
~~~

Both `INSERT`s are allowed by a single-column unique constraint because `NULL` values are not considered equal for uniqueness violations.

### 9.1 UNIQUE is not synonymous with NOT NULL

If an email column must always have a value and be unique:

~~~sql
CREATE TABLE app_user_test (
    user_id NUMBER PRIMARY KEY,
    email VARCHAR2(320 CHAR) NOT NULL,
    CONSTRAINT app_user_test_email_uk UNIQUE (email)
);
~~~

`NOT NULL` guarantees presence; `UNIQUE` guarantees uniqueness. The two constraints enforce two separate requirements.

### 9.2 Composite unique keys

Example:

~~~sql
CREATE TABLE external_reference_test (
    tenant_id NUMBER,
    external_code VARCHAR2(100),
    CONSTRAINT external_reference_test_uk
        UNIQUE (tenant_id, external_code)
);
~~~

Test these combinations:

- `(1, 'A')`
- `(1, 'A')` a second time
- `(1, NULL)`
- `(1, NULL)` a second time
- `(NULL, 'A')`
- `(NULL, 'A')` a second time
- `(NULL, NULL)` multiple times

With composite keys, Oracle allows combinations containing `NULL` per unique constraint semantics; therefore, do not assume rows sharing the same non-`NULL` portion will always be rejected. Write tests in a dedicated schema and document the behavior for your Oracle version. If business rules want `NULL` treated as a common sentinel value in a composite key, encode that rule with an explicitly normalized constraint/index expression rather than relying on assumptions about default `UNIQUE`.

### 9.3 CHECK constraints and NULL

A `CHECK` constraint only rejects a row when its expression evaluates to `FALSE`. If the expression evaluates to `UNKNOWN` because a column is `NULL`, the row may still be accepted.

Example:

~~~sql
CREATE TABLE quantity_test (
    id NUMBER PRIMARY KEY,
    quantity NUMBER CHECK (quantity > 0)
);
~~~

Inserting a `NULL` quantity can succeed because `NULL > 0` is `UNKNOWN`, not `FALSE`.

If quantity is mandatory and must be greater than zero:

~~~sql
CREATE TABLE quantity_required_test (
    id NUMBER PRIMARY KEY,
    quantity NUMBER NOT NULL CHECK (quantity > 0)
);
~~~

Always separate presence requirements (`NOT NULL`) from domain rules (`CHECK`).

### 9.4 Foreign keys and NULL

A nullable foreign key may contain `NULL` without requiring a matching parent row. If the relationship is mandatory, add `NOT NULL` to the foreign key column.

With composite foreign keys, understand how Oracle handles `NULL` components and test thoroughly. If business rules require all components to be present together or absent together, add a `CHECK` constraint to prevent partially populated keys.

## 10. Testing duplicate data with SQL

Before creating a `UNIQUE` constraint or running a migration, define "duplicate" according to business rules.

Common types of duplicates:

1. Exact full-row duplicates.
2. Primary/business key duplicates.
3. Partial composite key duplicates.
4. Duplicates after trimming whitespace.
5. Case-insensitive duplicates.
6. Accent-insensitive duplicates.
7. Duplicates after Unicode normalization.
8. Duplicates under specific collation rules.

### 10.1 Finding duplicates by business key

Example finding duplicate emails:

~~~sql
SELECT email, COUNT(*) AS duplicate_count
FROM app_users
WHERE email IS NOT NULL
GROUP BY email
HAVING COUNT(*) > 1
ORDER BY duplicate_count DESC, email;
~~~

`GROUP BY` groups `NULL` values into a single group, so add `WHERE email IS NOT NULL` when targeting duplicates among entered values. If you want to count the `NULL` group separately, remove that predicate and handle the `NULL` group as a distinct data condition.

### 10.2 Finding duplicates by composite key

~~~sql
SELECT tenant_id,
       external_code,
       COUNT(*) AS duplicate_count
FROM external_reference
GROUP BY tenant_id, external_code
HAVING COUNT(*) > 1
ORDER BY duplicate_count DESC;
~~~

Interpret results according to business key rules. If part of the key is `NULL`, decide whether those rows represent the same entity or distinct unknown values.

### 10.3 Finding full-row duplicates

~~~sql
SELECT customer_id,
       full_name,
       phone_number,
       COUNT(*) AS duplicate_count
FROM customer_import_stage
GROUP BY customer_id, full_name, phone_number
HAVING COUNT(*) > 1;
~~~

Omit surrogate IDs from `GROUP BY` when looking for data-level duplicates. Including a unique primary key will prevent detecting business duplicates.

### 10.4 Using ROW_NUMBER to select rows to keep

Once duplicates are identified and a retention rule is defined:

~~~sql
SELECT *
FROM (
    SELECT s.*,
           ROW_NUMBER() OVER (
               PARTITION BY email
               ORDER BY created_at, import_id
           ) AS rn
    FROM customer_import_stage s
    WHERE email IS NOT NULL
)
WHERE rn > 1;
~~~

`ROW_NUMBER` identifies surplus rows within each partition. `ORDER BY` must include a deterministic tie-breaker, such as a unique `import_id`. Never delete data based solely on a sample query; before running `DELETE`, verify the retained record, dependent foreign keys, and audit requirements.

### 10.5 Finding duplicates after normalization

Example business rule ignoring leading/trailing whitespace and case:

~~~sql
SELECT UPPER(TRIM(email)) AS normalized_email,
       COUNT(*) AS duplicate_count
FROM customer_import_stage
WHERE email IS NOT NULL
GROUP BY UPPER(TRIM(email))
HAVING COUNT(*) > 1;
~~~

This only performs environment-dependent case normalization; it does not fully resolve Unicode normalization or all linguistic rules. If normalization is enforced in a constraint, apply the exact same rule across insert, search, update, and migration paths.

## 11. Preventing duplicates across concurrent transactions

A common flawed pattern:

~~~text
1. SELECT to check whether email already exists.
2. If not, INSERT.
~~~

Two requests can run simultaneously:

~~~text
Transaction A                  Transaction B
-------------                  -------------
SELECT email -> no row
                               SELECT email -> no row
INSERT email
                               INSERT same email
COMMIT
                               COMMIT
~~~

Both `SELECT`s observe no existing row. Only a `UNIQUE` constraint guarantees two rows with the same key cannot exist under concurrent transactions.

### 11.1 Using a UNIQUE constraint as the final safeguard

~~~sql
ALTER TABLE app_users
ADD CONSTRAINT app_users_email_uk UNIQUE (email);
~~~

The application must catch the unique violation error—typically `ORA-00001`—then re-read state or return an appropriate conflict response.

Do not treat `ORA-00001` as always being a fatal system error. In a create-if-absent operation, it can be an expected outcome indicating another request created the record first.

### 11.2 MERGE does not automatically eliminate race conditions

`MERGE` is useful for upserts:

~~~sql
MERGE INTO customer_target t
USING (
    SELECT :customer_code AS customer_code,
           :customer_name AS customer_name
    FROM dual
) s
ON (t.customer_code = s.customer_code)
WHEN MATCHED THEN
    UPDATE SET t.customer_name = s.customer_name
WHEN NOT MATCHED THEN
    INSERT (customer_code, customer_name)
    VALUES (s.customer_code, s.customer_name);
~~~

However, two concurrent transactions can both evaluate `NOT MATCHED` and race to `INSERT`. A `UNIQUE` constraint is still required; the application must handle `ORA-00001` or retry using appropriate logic.

### 11.3 Idempotent inserts

For imports or API retries, maintain a unique request/import key:

~~~sql
CREATE TABLE import_request (
    request_id VARCHAR2(100) PRIMARY KEY,
    payload_hash RAW(32) NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT SYSTIMESTAMP
);
~~~

If a request is retried with the same `request_id` and same `payload_hash`, return the previous result or processed status. If the same key arrives with a different payload, reject it as an invalid reuse of the idempotency key.

## 12. Unicode in Oracle

Unicode is a character encoding standard, not a single byte encoding. One character can be represented by one or more code points. An encoding maps code points to bytes.

In Oracle, distinguish:

- Database character set: used for `CHAR`, `VARCHAR2`, `CLOB`, and much of metadata.
- National character set: used for `NCHAR`, `NVARCHAR2`, `NCLOB`.
- Client character set and driver conversion.
- Unicode normalization.
- Collation and comparison/sorting rules.

### 12.1 AL32UTF8

`AL32UTF8` is Oracle's standard UTF-8 database character set and is typically the recommended choice for new databases requiring multilingual support. It encodes Unicode code points in 1 to 4 bytes.

Do not confuse `AL32UTF8` with Oracle's legacy character set named `UTF8`, which uses CESU-8 encoding for supplementary characters. For new systems, verify and choose `AL32UTF8` according to Oracle documentation for your release.

Check:

~~~sql
SELECT parameter, value
FROM nls_database_parameters
WHERE parameter IN (
    'NLS_CHARACTERSET',
    'NLS_NCHAR_CHARACTERSET'
);
~~~

You cannot arbitrarily change the database character set once a database contains data. Character set migration requires evaluating data, convertibility, tooling, and backup/rollback plans.

### 12.2 NCHAR and NVARCHAR2

`NCHAR`/`NVARCHAR2` use the database's national character set. The national character set is typically `AL16UTF16` or `UTF8` depending on Oracle configuration.

- `CHAR`/`VARCHAR2` store using the database character set.
- `NCHAR`/`NVARCHAR2` store using the national character set.
- `CLOB` uses the database character set.
- `NCLOB` uses the national character set.

Having Vietnamese or Japanese data does not automatically mandate `NVARCHAR2`. If the database character set is `AL32UTF8`, `VARCHAR2` can store multilingual text. Choose column types based on architecture and compatibility requirements.

### 12.3 Testing charset and representation coverage

A Unicode test suite should include:

- Vietnamese with diacritics: `Tiếng Việt`.
- Japanese: `日本語`.
- Korean: `한국어`.
- Chinese: `中文`.
- Supplementary characters/emojis: `😀`.
- Combining characters: base letter plus combining mark.
- Unicode whitespace such as non-breaking space.
- Quotes, dashes, and currency symbols.

Do not only test `SELECT` display in a SQL client. `INSERT` via JDBC, read back via JDBC, inspect code points/bytes, and compare against the original input.

## 13. BYTE semantics and CHAR semantics

Declaring `VARCHAR2(20)` can use `BYTE` or `CHAR` semantics depending on `NLS_LENGTH_SEMANTICS` when the column was created.

- `BYTE` semantics limit by byte count.
- `CHAR` semantics limit by character count per Oracle semantics.

With `AL32UTF8`, one character can take multiple bytes. Hence `VARCHAR2(20 BYTE)` will not necessarily hold 20 Vietnamese, Japanese, or emoji characters.

### 13.1 Declaring semantics explicitly

Example:

~~~sql
CREATE TABLE unicode_length_test (
    code_byte VARCHAR2(20 BYTE),
    code_char VARCHAR2(20 CHAR)
);
~~~

For `code_byte`, the limit is 20 bytes. For `code_char`, the limit is 20 characters under Oracle semantics; it still remains subject to the maximum byte limit of the data type and Oracle version.

### 13.2 LENGTH and LENGTHB

~~~sql
SELECT
    LENGTH('A') AS ascii_chars,
    LENGTHB('A') AS ascii_bytes,
    LENGTH('Tiếng Việt') AS viet_chars,
    LENGTHB('Tiếng Việt') AS viet_bytes
FROM dual;
~~~

`LENGTH` returns length in character semantics; `LENGTHB` returns length in bytes under the active character set.

Under `AL32UTF8`, ASCII data typically uses one byte per character; accented or non-ASCII characters usually require multiple bytes.

### 13.3 Related length functions

Oracle provides:

- `LENGTH`: number of characters in the input's character set.
- `LENGTHB`: number of bytes.
- `LENGTHC`: number of Unicode complete characters.
- `LENGTH2`: number of UCS2 code points.
- `LENGTH4`: number of UCS4 code points.

These functions do not necessarily match the number of visible characters a user sees on screen. A grapheme may consist of a base character plus combining marks, which may be counted as multiple units depending on the function.

For example, an accented letter may be represented as a precomposed character or a base character plus combining mark. Lengths can differ even though visual rendering looks nearly identical.

### 13.4 ORA-12899

If a value exceeds the column limit, Oracle raises `ORA-12899: value too large for column`.

When investigating:

1. Check whether the column DDL specifies `BYTE` or `CHAR`.
2. Check the database character set.
3. Measure `LENGTH` and `LENGTHB` of the input in the corresponding environment.
4. Check bind types and conversions.
5. Check whether the value was truncated in Java/UI before sending.
6. Clarify whether business rules intend to limit by characters, bytes, or graphemes.

Do not blindly increase column length before clarifying the data contract.

## 14. Unicode normalization

Two strings can look identical while using different code points.

For example, the letter `é` can be represented as:

- NFC: a single precomposed code point `U+00E9`.
- NFD: `U+0065` (`e`) followed by `U+0301` (combining acute accent).

The two strings can have different byte sequences and lengths even though users see them identically.

Oracle does not automatically normalize all text data to NFC/NFD on `INSERT`. If business logic requires comparing canonical-equivalent strings, normalize at the application layer or adopt a well-designed, tested database strategy.

### 14.1 Normalizing in Java

Java provides `Normalizer`:

~~~java
import java.text.Normalizer;

String normalized =
    Normalizer.normalize(input, Normalizer.Form.NFC);
~~~

You can choose NFC to store a common canonical form. However, the decision must be consistent across all producers, imports, APIs, and batch jobs.

Do not normalize silently if data must be preserved verbatim for legal, search, or audit purposes. Store the raw input and a normalized key separately if business needs both.

### 14.2 Writing tests for both Unicode forms

~~~java
String composed = "\u00E9";
String decomposed = "e\u0301";

System.out.println(composed.equals(decomposed)); // false

String nfcA = Normalizer.normalize(
    composed, Normalizer.Form.NFC
);
String nfcB = Normalizer.normalize(
    decomposed, Normalizer.Form.NFC
);

System.out.println(nfcA.equals(nfcB)); // true
~~~

After normalizing, bind both values to the test column and verify bytes/lengths. If the database must enforce uniqueness on the normalized value, store a normalized key or use an explicitly designed indexing mechanism.

### 14.3 Unicode normalization differs from case folding

NFC/NFD handles canonical representation; it does not automatically convert uppercase to lowercase or strip accents. Case folding and accent-insensitive comparisons are separate rules.

For instance, `A`, `a`, and `á` relate differently depending on collation. Do not conflate normalization, lowercasing, and diacritic removal into one generic operation unless business rules explicitly define it.

## 15. Collation, comparison, and sorting Unicode

String comparison can rely on binary representation or linguistic rules. Oracle supports `NLS_SORT` and `NLS_COMP` at the session level in applicable configurations; newer releases also provide column/expression-level collation with release-dependent syntax and capabilities.

### 15.1 Binary comparison vs. linguistic comparison

Binary comparison compares character/byte representations per the character set. Linguistic comparison applies language rules for ordering, case, or accents.

Example query needing case-insensitive comparison:

~~~sql
SELECT *
FROM app_users
WHERE NLSSORT(username, 'NLS_SORT=BINARY_CI')
    = NLSSORT(:username, 'NLS_SORT=BINARY_CI');
~~~

`BINARY_CI` is an example of case-insensitive sorting. Accent-insensitive rules and other sorts depend on Oracle version and NLS support.

### 15.2 NLS_COMP and NLS_SORT

You can configure a session for testing:

~~~sql
ALTER SESSION SET NLS_COMP = LINGUISTIC;
ALTER SESSION SET NLS_SORT = BINARY_CI;
~~~

These settings affect how certain comparisons and sorts are evaluated within the session. Do not change them globally or assume all sessions in a connection pool share the same state.

In a connection pool, session state can persist after a logical connection is returned. If the application runs `ALTER SESSION`, reset state or configure session initialization so subsequent requests are unaffected.

### 15.3 Collation and UNIQUE

If business rules are case-insensitive, a default binary `UNIQUE` constraint will allow `Alice` and `alice` to coexist. A function-based unique index or collation-aware unique design may be needed depending on the release.

Illustrative example:

~~~sql
CREATE UNIQUE INDEX app_users_username_ci_uk
ON app_users (NLSSORT(username, 'NLS_SORT=BINARY_CI'));
~~~

Before creating the index, check existing data for duplicates under the new rule. If duplicates exist, creating the unique index will fail. Decide how to resolve conflicting records and ensure lookup queries use identical semantics.

### 15.4 ORDER BY and stability

When sorting by collation, multiple strings may be treated as equivalent. Add a unique secondary key for deterministic ordering:

~~~sql
SELECT user_id, username
FROM app_users
ORDER BY NLSSORT(username, 'NLS_SORT=BINARY_CI'),
         user_id;
~~~

This is vital for pagination and snapshot tests. Without a tie-breaker, the order of tied rows can change between executions.

## 16. Unicode in Java and JDBC

Java `String` stores text as UTF-16 code units. Unicode code points outside the Basic Multilingual Plane are represented using surrogate pairs—two code units.

Consequently:

- `String.length()` counts UTF-16 code units.
- `String.codePointCount()` counts Unicode code points.
- Neither necessarily equals the number of grapheme clusters a user sees.

Example:

~~~java
String emoji = "😀";

System.out.println(emoji.length()); // 2 UTF-16 code units
System.out.println(
    emoji.codePointCount(0, emoji.length())
); // 1 Unicode code point
~~~

If an application limits input by `String.length()`, an emoji counts as two units. If business rules limit visible characters, use a grapheme-aware library or explicit rule.

### 16.1 setString and getString

For `VARCHAR2`:

~~~java
statement.setString(1, "Tiếng Việt 日本語 😀");
String value = resultSet.getString(1);
~~~

The driver converts between Java UTF-16 and the database character set. With `AL32UTF8`, supported Unicode code points can be stored intact. If the database character set cannot represent a character, conversion may fail or substitute characters depending on the path and configuration; test empirically rather than assuming.

### 16.2 setNString and getNString

For `NVARCHAR2`/`NCHAR`:

~~~java
statement.setNString(1, "Tiếng Việt 日本語 😀");
String value = resultSet.getNString(1);
~~~

Use the N-string API when the column is a national character type and the driver requires/recommends it. Inspect DDL to know whether a column is `VARCHAR2` or `NVARCHAR2`.

### 16.3 Do not truncate strings arbitrarily by bytes

Never slice UTF-8 byte arrays without checking code point boundaries. Cutting in the middle of a multi-byte character sequence produces corrupt data.

If you must enforce an Oracle byte capacity limit, encode the string as UTF-8 in Java to count bytes, while still accounting for database conversion, national charsets, and collation. Ideally, validate at the validation layer using the same semantics as the target column and handle `ORA-12899` gracefully.

### 16.4 Round-trip verification

A JDBC test should:

1. Construct the test string in Java.
2. Record code points and UTF-16 length.
3. Bind to the target column.
4. Read back via `getString`/`getNString`.
5. Compare the original string with the retrieved string.
6. Compare NFC-normalized forms if required by business rules.
7. Measure `LENGTH`/`LENGTHB` on the Oracle side.
8. Verify no character replacement or truncation occurred.

## 17. Unicode strings that look alike but are unequal

Scenarios to include in tests:

- Precomposed letters vs. base + combining mark.
- Accented Latin vs. unaccented Latin.
- Uppercase vs. lowercase.
- Space `U+0020` vs. non-breaking space `U+00A0`.
- Hyphen-minus `U+002D` vs. en dash `U+2013` or em dash `U+2014`.
- ASCII apostrophe vs. curly apostrophe.
- Emoji with variation selector.
- Emoji with skin-tone modifier.
- Emoji family using zero-width joiners.
- Supplementary characters outside the BMP.

Two strings can render almost identically while differing in code points, bytes, collation weight, or normalization. Visual UI inspection alone is insufficient.

### 17.1 Inspecting code points in Java

~~~java
input.codePoints().forEach(cp ->
    System.out.printf("U+%04X%n", cp)
);
~~~

Run the same snippet on data read from the database to verify whether characters changed during storage/retrieval.

### 17.2 Inspecting bytes in Oracle

~~~sql
SELECT
    LENGTH(text_value) AS char_length,
    LENGTHB(text_value) AS byte_length,
    DUMP(text_value, 1016) AS hex_dump
FROM unicode_test
WHERE id = :id;
~~~

`DUMP` is useful for inspecting Oracle's internal byte/code representation. It does not replace a Unicode inspector tool, but verifies whether stored database data matches expectations.

## 18. Testing trim, whitespace, and normalization

Oracle `TRIM` normally handles spaces per default rules; do not assume it removes all Unicode whitespace. Tabs, newlines, and non-breaking spaces may require dedicated handling.

### 18.1 Testing ASCII spaces

~~~sql
SELECT
    LENGTH(' ') AS one_space_length,
    LENGTH(TRIM(' ')) AS trimmed_length
FROM dual;
~~~

After `TRIM`, the resulting empty string is treated as `NULL` by Oracle, so `LENGTH` returns `NULL`.

### 18.2 Inspecting with DUMP

~~~sql
SELECT
    DUMP(' ', 1016) AS ascii_space,
    DUMP(UNISTR('\00A0'), 1016) AS no_break_space,
    DUMP(CHR(9), 1016) AS tab_character
FROM dual;
~~~

`UNISTR` supports representing Unicode characters via escape sequences in SQL. Escape syntax and byte output should be verified against the database/national character set.

### 18.3 Defining blank per business rules

If a mandatory field must not contain whitespace-only text, `IS NOT NULL` alone is insufficient. Validate after normalizing whitespace across the character set accepted by business rules.

Simple example for ASCII spaces:

~~~sql
CHECK (TRIM(display_name) IS NOT NULL)
~~~

However, `CHECK` behavior with `NULL`/`UNKNOWN` must be properly understood, and default `TRIM` does not strip all Unicode whitespace. A more robust solution normalizes input in the application service and stores a separate normalized key alongside a constraint enforcing the chosen rule.

## 19. Test matrix for NULL, empty, duplicates, and Unicode

A test suite should include intentional cases:

| Group | Input | What to verify |
|---|---|---|
| Null | Java `null` / SQL `NULL` | `IS NULL`, aggregates, joins, and constraints |
| Empty | `""` | Oracle `VARCHAR2` treats as `NULL` |
| Blank | `" "` | Non-`NULL`; `TRIM` can produce `NULL` |
| Whitespace | tab/newline/NBSP | Distinct from ASCII space |
| Number null | `NULL` in `NUMBER` | Arithmetic and aggregates |
| Unique null | Multiple `NULL`s in unique column | Unique constraint behavior |
| Composite key | Each `NULL`/non-`NULL` combination | Unique/FK rules by key shape |
| Duplicate | Same natural key | `GROUP BY`/`HAVING` and unique indexes |
| Case | `Alice`/`alice` | Binary vs. case-insensitive comparison |
| Accent | `e`/`é` | Accent-sensitive vs. insensitive |
| Normalization | NFC/NFD | Code points and canonical equivalence |
| Multibyte | `Tiếng Việt`, `日本語` | `LENGTH` and `LENGTHB` |
| Supplementary | emoji | UTF-16 code units and Oracle character count |
| Over limit | Strings near column limit | `BYTE`/`CHAR` semantics and `ORA-12899` |
| Trailing spaces | `'A'`/`'A '` | `CHAR`/`VARCHAR2` comparison semantics |

### 19.1 Boundary testing

For a `VARCHAR2(20 BYTE)` column, test:

- Exact 20-byte value.
- 21-byte value.
- 10 ASCII characters.
- 10 multi-byte characters.
- String containing a 4-byte character.
- String mixing ASCII and Unicode.

For `VARCHAR2(20 CHAR)`, test boundary character counts and actual byte lengths. Never assume `20 CHAR` always equates to 20 displayed graphemes.

### 19.2 Multi-layer testing

An input should be verified across:

1. UI/browser.
2. JSON/API serialization.
3. Java `String`.
4. JDBC bind.
5. Oracle column.
6. SQL comparison/constraint.
7. JDBC fetch.
8. UI rendering.

Testing only directly in SQL Developer can miss encoding bugs in HTTP, JSON, drivers, or connection pools.

INSERT INTO customer_edge_test

SELECT

## 21. Testing duplicates after normalization and creating unique indexes

Suppose usernames are case-insensitive per business rules. Before creating the index, find duplicates:

~~~sql
SELECT UPPER(TRIM(username)) AS normalized_username,
       COUNT(*) AS duplicate_count
FROM app_users
WHERE username IS NOT NULL
GROUP BY UPPER(TRIM(username))
HAVING COUNT(*) > 1;
~~~

After resolving conflicting data, create a function-based unique index:

~~~sql
CREATE UNIQUE INDEX app_users_username_norm_uk
ON app_users (UPPER(TRIM(username)));
~~~

This index only expresses one specific rule: `UPPER` and `TRIM` under the applicable Oracle/session semantics. It does not automatically handle NFC/NFD, all Unicode whitespace, or all locales.

If `NULL` must be disallowed, add `NOT NULL`. If multiple `NULL`s should be allowed, verify expression/index behavior with `NULL` and test for your release. Function-based indexes may have distinct key-storage rules when the entire expression evaluates to `NULL`; confirm with insert tests before applying to production.

### 21.1 Do not let write and read normalization diverge

If inserts normalize using NFC while searches do not, users may fail to find records they just created. All write, read, update, import, deduplication, and unique enforcement paths must apply the exact same rule.

Package normalization in a shared library or API, versioned and backed by test vectors. When changing the rule, plan a migration and check for collisions first.

## 22. Testing session state and NLS in connection pools

Connection pools retain physical sessions across multiple requests. Session state such as `NLS_COMP`, `NLS_SORT`, timezone, current schema, and module/action can persist after a logical connection is returned to the pool.

If Request A executes:

~~~sql
ALTER SESSION SET NLS_SORT = BINARY_CI;
~~~

and Request B reuses that physical connection without resetting it, Request B may inherit unexpected semantics.

### 22.1 Checking state before and after checkout

You can run:

~~~sql
SELECT
    SYS_CONTEXT('USERENV', 'SID') AS sid,
    SYS_CONTEXT('USERENV', 'CURRENT_SCHEMA') AS current_schema
FROM dual;

SELECT parameter, value
FROM nls_session_parameters
WHERE parameter IN ('NLS_COMP', 'NLS_SORT');
~~~

Log the `SID` to see whether a logical connection returned to the same physical session.

### 22.2 Resetting session state

Connection pool configuration should include initialization/reset hooks if the application alters session state. Avoid letting individual DAOs run `ALTER SESSION` without restoring state.

Single-query NLS overrides can be expressed via `NLSSORT`/NLS parameter functions where appropriate, or via collation expressions in supporting releases. This keeps semantics close to the SQL statement and reduces session state coupling.

### 22.3 Parallel testing

Run concurrent requests on the same pool:

- Request A requires case-insensitive comparison.
- Request B requires binary comparison.
- Request C reads and sorts Unicode.
- Request D runs an import.

Verify that results never depend on which request previously held the physical connection.

## 23. Reading data and comparing in Java

Do not use Java `String.equals()` to emulate all Oracle collation rules. `String.equals()` compares strings by UTF-16 code unit sequence; Oracle may use binary or linguistic collation.

### 23.1 Raw comparison

~~~java
boolean sameRaw = left.equals(right);
~~~

Appropriate when verifying two Java strings have the exact same code unit sequence.

### 23.2 Comparison after NFC

~~~java
String leftNfc =
    Normalizer.normalize(left, Normalizer.Form.NFC);
String rightNfc =
    Normalizer.normalize(right, Normalizer.Form.NFC);

boolean sameCanonical = leftNfc.equals(rightNfc);
~~~

Appropriate when business rules consider canonical-equivalent strings identical.

### 23.3 Case-insensitive comparison

`Locale.ROOT` can be used for certain application rules:

~~~java
boolean sameCaseInsensitive =
    left.toLowerCase(Locale.ROOT)
        .equals(right.toLowerCase(Locale.ROOT));
~~~

This is not necessarily identical to Oracle linguistic collation or full Unicode case folding. If both the application and database enforce a uniqueness/search rule, select one canonical semantics and test both sides with identical test vectors.

### 23.4 Do not use the default locale arbitrarily

`String.toLowerCase()` without a `Locale` uses the JVM's default locale. Behavior can vary across runtime environments. For technical keys, `Locale.ROOT` is generally more predictable; for user-facing languages, apply clearly defined locale-aware rules.

## 24. Common mistakes and how to avoid them

| Mistake | Why it is wrong | Correct practice |
|---|---|---|
| Using `column = NULL` | Comparison evaluates to `UNKNOWN` | Use `IS NULL` |
| Using `column = ''` to find empty strings | Oracle treats empty `VARCHAR2` as `NULL` | Use `IS NULL`; store separate state if distinction is needed |
| Treating spaces as `NULL` | Spaces are non-null data characters | Test `TRIM`/whitespace per business rules |
| Using `NOT IN` with a subquery containing `NULL` | `UNKNOWN` can filter out every row | Use `NOT EXISTS` or filter out `NULL` |
| Using `UNIQUE` to require a value | `UNIQUE` permits `NULL` | Add `NOT NULL` |
| Assuming `CHECK(column > 0)` rejects `NULL` | `UNKNOWN` is not `FALSE` | Add `NOT NULL` |
| `SELECT` before `INSERT` to prevent duplicates | Race condition across transactions | Use `UNIQUE` constraint and handle `ORA-00001` |
| Trusting `MERGE` to be race-free | Concurrent inserts can still collide | Keep `UNIQUE` constraint and retry/handle |
| Comparing Unicode visually | Lookalike strings can differ in code points | Check normalization, code points, and collation |
| Treating `LENGTHB` as character count | Unicode has variable byte length | Use `LENGTH`/`CHAR` semantics as required |
| Truncating strings by arbitrary byte offset | Can split a multi-byte UTF-8 sequence | Slice by code point/grapheme and check byte limit |
| Using `VARCHAR2(n)` without explicit semantics | Depends on default `BYTE`/`CHAR` at creation | Explicitly write `n BYTE` or `n CHAR` |
| Assuming `setString("")` stores an empty string | Oracle treats empty `VARCHAR2` as `NULL` | Design separate status state if needed |
| Running `ALTER SESSION` in a pool without resetting | Subsequent requests inherit stale state | Initialize/reset sessions consistently |
| Using `UPPER` to normalize all Unicode | Misses normalization/accents/locales | Define full normalization and collation rules |

## 25. Systematic SQL testing workflow

A suitable workflow for new features or regressions:

### Step 1: Write down business rules

For example:

- Email is mandatory.
- Email is case-insensitive.
- Username is NFC-normalized.
- Empty notes are treated as absent.
- A tenant cannot have two identical external references.
- Display names must preserve diacritics and Unicode.

Do not start writing SQL before defining what data is valid.

### Step 2: Define schema and semantics

Specify:

- Data type.
- `BYTE`/`CHAR` semantics.
- `NOT NULL`/`UNIQUE`/`CHECK`/`FK`.
- Database character set.
- National character set if used.
- Collation.
- `DEFAULT` and `DEFAULT ON NULL` if applicable.
- Triggers/function-based indexes affecting data.

### Step 3: Build test vectors

Create inputs for `NULL`, empty, blank, duplicates, NFC/NFD, case, accents, supplementary characters, and length boundaries.

### Step 4: Test SQL directly

Run `INSERT`/`SELECT`/`UPDATE` in a test schema. Inspect with `IS NULL`, `LENGTH`, `LENGTHB`, `DUMP`, `GROUP BY`, and constraints.

### Step 5: Test through JDBC

Pass the same inputs through `setString`, `setNull`, and `setNString`, and read back via `getString`/`getNString`. Verify round-trip integrity.

### Step 6: Test concurrency

Run two or more transactions concurrently writing the same natural key. Verify the `UNIQUE` constraint preserves invariants and the application handles `ORA-00001` per contract.

### Step 7: Test NLS and pool reuse

Run tests with varying session settings while reusing physical connections. Confirm semantics are either reset or made explicit in SQL.

### Step 8: Test migrations and legacy data

Before adding a unique index or changing normalization, detect existing duplicates, classify `NULL`s, determine retained records, and verify foreign keys.

### Step 9: Document expected results

Each test should record inputs, DDL, SQL, expected results, and actual results. Do not just save screenshots of a SQL client.

## 26. Testing checklist

### NULL and empty strings

- [ ] Verified `IS NULL` and `IS NOT NULL`.
- [ ] Verified equality comparisons with `NULL` are not used in predicates.
- [ ] Tested `AND`/`OR`/`NOT` with `UNKNOWN`.
- [ ] Tested `NOT IN` when subqueries contain `NULL`.
- [ ] Tested `NOT EXISTS` with nullable keys.
- [ ] Tested `NVL`, `COALESCE`, `NULLIF`, and `CASE`.
- [ ] Tested `COUNT(*)`, `COUNT(column)`, `SUM`, and `AVG`.
- [ ] Tested `GROUP BY`/`DISTINCT` with `NULL`.
- [ ] Verified empty `VARCHAR2` is treated as `NULL`.
- [ ] Tested space, tab, newline, and NBSP separately.
- [ ] Verified `EMPTY_CLOB` differs from `NULL` when LOBs are used.

### Duplicates and constraints

- [ ] Searched for duplicates by natural key.
- [ ] Searched for duplicates across all business columns.
- [ ] Tested composite keys containing `NULL`.
- [ ] Verified `UNIQUE` and `NOT NULL` independently.
- [ ] Tested `CHECK` constraints with `NULL`.
- [ ] Tested nullable foreign keys.
- [ ] Tested race conditions with two transactions inserting concurrently.
- [ ] Handled `ORA-00001` in the application.
- [ ] Tested `MERGE` under concurrency.
- [ ] Checked duplicates after trimming/casing/normalization.

### Unicode

- [ ] Confirmed `NLS_CHARACTERSET` matches target charset.
- [ ] Confirmed `NLS_NCHAR_CHARACTERSET` if national types are used.
- [ ] Tested `VARCHAR2` `BYTE` and `CHAR` semantics.
- [ ] Checked `LENGTH` and `LENGTHB`.
- [ ] Tested supplementary characters/emojis.
- [ ] Tested NFC and NFD forms.
- [ ] Tested case/accent collations.

- [ ] Tested `setNString`/`getNString` for national types.

- [ ] Verified round-trip from UI/API to Oracle and back.

### Repeatability and operations

- [ ] Tests use dedicated schemas/tables.
- [ ] Controlled rollback or cleanup is in place.
- [ ] Oracle version, JDBC driver, and NLS settings recorded.
- [ ] Re-runnable with fixed test vectors.
- [ ] Session state verified across connection pool reuse.
- [ ] Migrations tested on a data copy before production.
- [ ] Expected/actual results and full Oracle errors logged.

## 27. Conclusion

`NULL`, empty strings, duplicates, and Unicode are not edge cases that can be solved with a few simple `IF` statements. Oracle uses three-valued logic; empty `VARCHAR2` strings are treated as `NULL`; `UNIQUE`, `CHECK`, and foreign keys have distinct semantics for `NULL`; duplicates must be defined by business keys; and Unicode depends on character sets, byte/character lengths, normalization, and collation.

A reliable test suite needs both direct SQL tests and JDBC round-trip tests, inspecting stored data with `IS NULL`, `LENGTH`, `LENGTHB`, and `DUMP`, testing constraints under concurrency, and pinning database/NLS/driver settings. Once data rules are clearly defined, test vectors can be reused across migrations, API validation, imports, regressions, and multi-environment Oracle testing.
