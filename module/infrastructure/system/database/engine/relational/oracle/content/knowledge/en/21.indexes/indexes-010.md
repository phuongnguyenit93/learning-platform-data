# Reverse Key Indexes, Monotonically Increasing Keys, and Range Query Capabilities in Oracle

In Oracle Database, B-tree indexes normally store keys in ascending order. When a table receives many new rows with keys generated by an ascending sequence, new values tend to be inserted into the trailing region of the index. If many sessions insert concurrently, they can focus access on a few leaf blocks at the right edge of the B-tree. In certain high-concurrency write workloads, this causes **right-hand index leaf block contention**.

A **reverse key index** is a B-tree index type that reverses the byte order of the key before storing it in the index. Reversing bytes scatters ascending keys across more leaf block regions, reducing insert concentration on the trailing leaf block. In return, the logical order of the index no longer matches the original value order. Therefore, a reverse key index supports suitable equality lookups, but does not support key-order index range scans like a standard B-tree.

This lesson explains the relationship between ascending keys and leaf block contention, how reverse key indexes work, their impact on equality and range queries, how to create/rebuild them, diagnostics, and alternative solutions.

## 1. B-tree Indexes and Leaf Block Structure

Oracle B-tree indexes are organized into levels:

- **Root block:** the starting point for searches.
- **Branch blocks:** intermediate blocks containing separator keys and pointers to lower levels.
- **Leaf blocks:** store index key values along with ROWIDs (or corresponding row info) to locate data in the table.

Simple diagram:

~~~text
                    ROOT
                      |
             +--------+--------+
             |                 |
          BRANCH A          BRANCH B
          /     \            /     \
         v       v          v       v
      LEAF 1  LEAF 2      LEAF 3  LEAF 4
       keys    keys        keys    keys
~~~

A B-tree keeps keys in sorted order so Oracle can navigate from the root down to the right branch and leaf blocks. When searching for a specific value, Oracle follows the matching branches. When searching for a value range, Oracle can start at the leaf block containing the start of the range and walk subsequent leaf blocks until the end of the range.

### 1.1. Leaf block splits

When a leaf block no longer has space for a new key, Oracle can perform a block split to distribute entries between blocks. Splitting is normal B-tree behavior, not always a performance bug.

With evenly distributed keys, inserts go into many leaf blocks. With continuously ascending keys, most new keys tend to go into the rightmost region of the index. When many sessions insert concurrently, that trailing region can become a hot spot.

### 1.2. What is a monotonically increasing key?

A monotonically increasing key is a key whose new values are generally larger than previous keys. Common examples:

- Primary keys drawn from an Oracle sequence.
- ID columns generated by an incrementing counter in the application.
- High-resolution timestamps or event sequence numbers with increasing order.
- Transaction codes containing a continuously incrementing numeric suffix.

Example:

| Insert # | ID |
|---:|---:|
| 1 | 1001 |
| 2 | 1002 |
| 3 | 1003 |
| 4 | 1004 |
| 5 | 1005 |

In a standard B-tree index on `ID`, new values are generally appended to the right edge of the index order.

### 1.3. Right-hand index hot blocks

When many sessions insert ascending keys simultaneously, they may all need to modify the rightmost leaf block or leaf blocks near the right edge of the index. Oracle must coordinate block and buffer access. This can lead to waits such as:

- `buffer busy waits` in certain buffer block contention scenarios.
- `enq: TX - index contention` in certain index/transaction contention scenarios.
- `gc buffer busy acquire` or `gc buffer busy release` in RAC environments when a hot block must move or be requested across instances.
- Other wait events depending on version, index type, and execution path.

Not every table using a sequence experiences contention. Whether it becomes an issue depends on concurrent writer count, insert rate, block size, cache configuration, index type, RAC workload, and block hold time. A low-concurrency sequential write application may never need a reverse key index.

## 2. Why Can Ascending Keys Cause Contention?

Suppose a regular B-tree index has leaf blocks containing keys:

~~~text
LEAF A: 1001, 1002, 1003
LEAF B: 1004, 1005, 1006
LEAF C: 1007, 1008, 1009  <-- trailing region
~~~

When many sessions simultaneously insert `1010, 1011, 1012...`, they all head to the trailing region of the index. If the leaf block fills up, splits occur; if many sessions need the same hot block simultaneously, they must wait for appropriate access.

~~~text
Session 1 ---- insert ID 1010 ----+
Session 2 ---- insert ID 1011 ----+----> Right-most leaf block
Session 3 ---- insert ID 1012 ----+
Session 4 ---- insert ID 1013 ----+
                                      |
                                      v
                             Hot block contention
~~~

This is **index leaf block contention**, which is not the same as row lock contention on the same row. Sessions may be inserting completely different rows yet still contend on the same index block because new keys sit adjacent in index order.

### 2.1. Why does sequence CACHE not solve hot leaf blocks by itself?

Sequence `CACHE` lets Oracle pre-allocate a batch of sequence values in memory, reducing dictionary accesses/writes and certain types of sequence allocation contention. However, allocated values still ascend and still land in the trailing region of a standard B-tree index.

Therefore, distinguish clearly:

| Issue | Mechanism involved | Possible approaches to consider |
|---|---|---|
| Sequence allocation contention | Sequence state/allocation, especially with RAC config/workload | `CACHE`, `NOORDER` where appropriate, scalable sequences depending on release |
| Index leaf block contention | Many inserts hitting the same B-tree trailing edge | Reverse key index, hash-partitioned index, alternative key/partition design |
| Same-row contention | Row lock / TX row lock contention | Adjust transaction boundaries and update logic |
| Other buffer/block contention | Buffer cache, ITL, or hot blocks | Identify block/segment and wait type before making changes |

Increasing `CACHE` can reduce sequence allocation cost, but does not scramble key ordering in the index. If the bottleneck is the right-hand leaf block, you must address index design or key distribution.

### 2.2. RAC and right-hand index contention

In Oracle RAC, each instance has its own buffer cache while sharing access to database files. When an index leaf block is modified by multiple instances, ownership of the block must be transferred or shipped across the interconnect via Cache Fusion. If a hot leaf block ping-pongs continuously between instances, global cache waits can appear.

A reverse key index can scatter ascending keys across multiple leaf blocks, reducing concentration on a single block at the right edge. However, it does not eliminate all RAC contention and does not replace actual AWR/ASH or wait event analysis.

## 3. How Does a Reverse Key Index Work?

A reverse key index is a B-tree index in which Oracle reverses the byte order of the key before sorting and storing the index entry. This is byte-level reversal, not reversing character digits as displayed to a user.

Conceptual byte illustration:

~~~text
Original numeric key:  [byte A] [byte B] [byte C]
Reversed key:          [byte C] [byte B] [byte A]
~~~

This is a conceptual model; actual internal representation depends on datatype and how Oracle encodes values. The key point is that reversing byte order keeps consecutive ascending values from sitting next to each other in ordinary numeric order in the B-tree.

With an ascending sequence, new keys get distributed across more leaf block positions rather than piling up at one end of the index.

### 3.1. Reverse key does not change table column values

Suppose a table has IDs `1001, 1002, 1003`. A reverse key index alters only how keys are organized inside the index. Values in the table remain `1001, 1002, 1003`.

Queries are still written with original values:

~~~sql
SELECT *
FROM orders
WHERE order_id = 1002;
~~~

Oracle can use the reverse key index to look up the key using the literal value `1002`. The application does not reverse IDs before querying.

### 3.2. Scattering inserts

A standard B-tree sorts by the original key. A reverse key index changes storage order, sending numerically adjacent ascending keys to different positions in the index.

~~~text
Normal B-tree index:
1001 -> 1002 -> 1003 -> 1004 -> 1005 -> trailing region
                                            ^
                                            |
                                   concentrated inserts

Reverse key B-tree:
Original key 1001 -> index position A
Original key 1002 -> index position B
Original key 1003 -> index position C
Original key 1004 -> index position D
Original key 1005 -> index position E

=> inserts scatter across multiple leaf blocks
~~~

This diagram illustrates the tendency only. Exact dispersion depends on byte representation, key type, value range, and real data; reverse keys do not guarantee perfectly uniform distribution.

### 3.3. A reverse key index is still a B-tree index

A reverse key index is not a hash index. It retains a B-tree structure and still supports equality lookups when conditions fit. The critical change is that key order inside the index no longer matches ascending/descending order of the original values.

## 4. Creating a Reverse Key Index

You can create a reverse key index with the `REVERSE` keyword:

~~~sql
CREATE INDEX ix_orders_order_id_rev
ON orders (order_id)
REVERSE;
~~~

Example with a unique key:

~~~sql
CREATE UNIQUE INDEX ux_orders_order_id_rev
ON orders (order_id)
REVERSE;
~~~

A reverse key index can still be unique and still enforces uniqueness on the key. Reversing bytes does not change the uniqueness of original values.

If a primary key or unique constraint is backed by a reverse key index, design explicitly because uniqueness enforcement continues to work, whereas range queries on that key cannot rely on index order like a regular B-tree.

### 4.1. Reverse key on composite keys

You can create a multi-column index:

~~~sql
CREATE INDEX ix_event_account_seq_rev
ON account_events (account_id, event_seq)
REVERSE;
~~~

This remains a composite index. However, because key byte order is reversed, do not expect standard composite B-tree range scan and prefix access rules to apply in original value order. Check execution plans for real predicates.

If the workload consists mainly of exact lookups on the full key or compatible columns, reverse key can help. If the workload needs ranges by account/time or reading adjacent events, reverse key can hurt query efficiency.

### 4.2. Converting an existing index to reverse or non-reverse

You can rebuild an index to change its reverse attribute:

~~~sql
ALTER INDEX ix_orders_order_id
REBUILD REVERSE;
~~~

To convert a reverse key index back to a standard B-tree index:

~~~sql
ALTER INDEX ix_orders_order_id_rev
REBUILD NOREVERSE;
~~~

Rebuild is an index maintenance operation requiring planning for time, temp space, I/O, locking/availability, and DML impact depending on options and configuration. Never run rebuild casually on large indexes during peak hours.

### 4.3. Inspecting index DDL

You can inspect DDL stored in the data dictionary:

~~~sql
SELECT DBMS_METADATA.GET_DDL(
           'INDEX',
           'IX_ORDERS_ORDER_ID_REV',
           USER
       )
FROM dual;
~~~

The DDL output confirms whether the index was created with `REVERSE`. Dictionary view `USER_INDEXES` provides index details like uniqueness, status, leaf blocks, and clustering factor; do not infer reverse behavior solely from application naming conventions.

## 5. Equality Lookups: Reverse Key Indexes Remain Useful

Reverse key indexes preserve exact-key lookup capability. Example:

~~~sql
SELECT order_id, customer_id, order_status
FROM orders
WHERE order_id = :order_id;
~~~

With an appropriate index, Oracle can perform `INDEX UNIQUE SCAN` or `INDEX RANGE SCAN` depending on uniqueness and query structure. After finding the entry, Oracle can use the ROWID to access the table row.

Common suitable cases:

- Finding an order by primary key.
- Finding an event by unique ID.
- Checking existence of an exact key.
- Joining with an equality condition on an indexed key.
- Updating/deleting a row by equality key.

Example:

~~~sql
UPDATE orders
SET order_status = 'SHIPPED'
WHERE order_id = :order_id;
~~~

If the workload combines heavy inserts with equality lookups by ID, a reverse key index can be a reasonable candidate once hot leaf block contention is proven to be the bottleneck.

### 5.1. Equality on a composite index

With the index:

~~~sql
CREATE INDEX ix_event_account_seq_rev
ON account_events (account_id, event_seq)
REVERSE;
~~~

An equality query on both columns:

~~~sql
SELECT event_id, account_id, event_seq
FROM account_events
WHERE account_id = :account_id
  AND event_seq = :event_seq;
~~~

can use the index if the optimizer finds it beneficial. Distinguish this query from fetching a range of `event_seq` values for an account.

## 6. Range Queries: The Biggest Trade-Off

Standard B-tree indexes store keys in sorted order, supporting range predicates such as:

~~~sql
SELECT order_id, order_date
FROM orders
WHERE order_id BETWEEN 100000 AND 101000;
~~~

Oracle can start at the leaf containing the lower bound and walk subsequent leaf entries until the upper bound.

In a reverse key index, byte order is reversed. Numerically adjacent original keys do not sit adjacent in the index. Therefore, a reverse key index **does not support index range scans in original key order**.

Predicates that generally cannot leverage a reverse key index like a standard B-tree:

~~~sql
WHERE order_id BETWEEN :low_id AND :high_id
~~~

~~~sql
WHERE order_id > :last_seen_id
~~~

~~~sql
WHERE order_id < :cutoff_id
~~~

~~~sql
ORDER BY order_id
~~~

Oracle may pick a full table scan, another index, or an alternative access path. Never expect a reverse key index to accelerate these queries merely because the index exists.

### 6.1. Comparing equality and range

| Predicate | Standard B-tree | Reverse key B-tree |
|---|---|---|
| `id = :id` | Can use index equality lookup | Can use index equality lookup |
| `id IN (:a, :b, :c)` | Can use multiple equality probes | Can use multiple equality probes |
| `id BETWEEN :a AND :b` | Can use index range scan | Does not support range scan in ID order |
| `id > :id` | Can use index range scan | Does not support range scan in ID order |
| `ORDER BY id` | Can read in index order if plan fits | Cannot rely on reverse index order for original ID order |
| Fetching consecutive IDs | Usually suitable | Usually unsuitable |

"Can use" does not mean the optimizer always selects the index. Oracle decides based on cost, statistics, selectivity, clustering factor, columns needed, and other factors.

### 6.2. Why are range scans impossible after byte reversal?

Suppose original values follow the order:

~~~text
1001 < 1002 < 1003 < 1004 < 1005
~~~

After byte reversal, index order no longer preserves numeric order. Entries satisfying `1002` through `1004` can be scattered across many leaf blocks. Oracle cannot simply walk from a starting leaf block to an ending leaf block in original order as with a regular B-tree.

To return results, the database would have to inspect many entries or choose another access path; the benefit of an index range scan is lost.

### 6.3. ORDER BY and MIN/MAX

Do not use a reverse key index when the primary goal is reading data in key order, for example:

~~~sql
SELECT order_id
FROM orders
ORDER BY order_id DESC
FETCH FIRST 100 ROWS ONLY;
~~~

A regular B-tree can support ordered index-reading plans. A reverse key index does not store original numeric order, so it cannot replace a standard B-tree for such queries.

`MIN`/`MAX` queries on the key require the same consideration. If finding min/max or top-N by original value is needed, a reverse key index is usually not appropriate.

## 7. Reverse Key Indexes and Composite Indexes

In a standard composite B-tree, column order and the leading column govern access capabilities. Example:

~~~sql
CREATE INDEX ix_orders_customer_date
ON orders (customer_id, order_date);
~~~

This index fits:

~~~sql
WHERE customer_id = :customer_id
  AND order_date >= :from_date
  AND order_date < :to_date
~~~

because Oracle can locate a customer's region and then range-scan by date.

If created with `REVERSE`:

~~~sql
CREATE INDEX ix_orders_customer_date_rev
ON orders (customer_id, order_date)
REVERSE;
~~~

byte reversal breaks original customer/date sorting. Do not assume an equality predicate on the leading column followed by a range on the second column will still work like a regular index.

### 7.1. Choosing indexes by access pattern

| Query pattern | Standard index | Reverse key |
|---|---|---|
| Equality on entire key | Suitable | Can be suitable |
| Equality on unique key | Suitable | Can be suitable |
| Equality leading key, range trailing key | Can be very suitable | Generally unsuitable for range |
| Range by timestamp/sequence | Suitable if key order matches | Unsuitable |
| Fetching N newest records | Can suit with appropriate `DESC`/order | Unsuitable to rely on original key order |
| Concurrent inserts with ascending IDs | May suffer right-hand contention | Can reduce leaf block concentration |

Do not convert every index on a table to `REVERSE`. A table can have multiple indexes serving different workloads; reverse key should be applied only to indexes where write concurrency benefits outweigh range scan loss.

## 8. Reverse Key Indexes, Sequences, and Ascending Keys

A common pattern:

~~~sql
CREATE SEQUENCE orders_seq
    START WITH 1
    INCREMENT BY 1
    CACHE 1000
    NOORDER;

CREATE TABLE orders (
    order_id NUMBER PRIMARY KEY,
    customer_id NUMBER NOT NULL,
    order_date DATE NOT NULL
);
~~~

When inserting:

~~~sql
INSERT INTO orders (order_id, customer_id, order_date)
VALUES (orders_seq.NEXTVAL, :customer_id, SYSDATE);
~~~

If the primary key is backed by a regular B-tree index, new keys trend toward the trailing edge of the index.

You can create a reverse key unique index to scatter inserts:

~~~sql
CREATE UNIQUE INDEX ux_orders_order_id_rev
ON orders (order_id)
REVERSE;
~~~

Then use this index to support the constraint or equality ID lookups depending on constraint/index design. When replacing an index backing an existing constraint, follow proper constraint and index management procedures rather than simply dropping an index in active use by a constraint.

### 8.1. Sequence CACHE

`CACHE` pre-allocates a range of sequence values in memory, reducing allocation overhead. Example:

~~~sql
CREATE SEQUENCE orders_seq
    START WITH 1
    INCREMENT BY 1
    CACHE 1000;
~~~

`CACHE` does not guarantee gap-free sequences. Instance restarts, rollbacks, or unused cached values can leave gaps. Sequences are not tools for generating strictly consecutive gap-free document numbers.

`CACHE` reduces sequence allocation overhead, but does not change key ordering in a B-tree. If the right-hand leaf block remains a bottleneck, increasing `CACHE` alone will not solve it.

### 8.2. ORDER and NOORDER in RAC

Sequences can be configured as `ORDER` or `NOORDER`. `ORDER` guarantees allocation order across requests in supported environments; `NOORDER` allows allocation without guaranteeing global ordering across RAC instances. For high-throughput RAC workloads, `NOORDER` is commonly considered when global ordering is unnecessary.

Even with `NOORDER`, sequence values still ascend within each instance's cache in their own range and can still create hot insert regions depending on design. Reverse key indexes address index placement dispersion, distinct from how sequences distribute numbers.

### 8.3. Scalable sequences

Some Oracle releases support scalable sequences, which prepend/embed instance and session identifiers into generated values to reduce sequence allocation contention under high concurrency/RAC. Exact syntax and availability depend on release.

Scalable sequences help reduce a different kind of contention, with considerations:
- Generated values no longer reflect simple chronological monotonicity.
- Number ranges and key lengths change.
- Applications must not assume sequences represent timestamps or commit order.
- Verify range queries, unique keys, and business expectations.

Scalable sequences and reverse key indexes are not two names for the same solution. One changes how values are generated and distributed; the other changes how keys are stored in the B-tree.

## 9. Reverse Key Indexes in RAC Workloads

In RAC, multiple instances can simultaneously insert into a table using an ascending primary key. With a regular B-tree, the trailing leaf block region can become a hot block repeatedly requested across Cache Fusion.

A reverse key index can scatter inserts across multiple leaf blocks and reduce cross-instance contention on a single block. However:

- It does not eliminate row locks if multiple sessions update the same row.
- It does not eliminate sequence allocation contention.
- It does not eliminate table block contention if the table itself has hot blocks.
- It does not resolve every global cache wait.
- It trades away range scans and original key ordering.

When a RAC workload needs both insert throughput and range queries, consider multiple indexes or a partitioning strategy rather than relying on reverse key as the sole index.

## 10. Alternatives and Complements

A reverse key index is a specialized tool. Other options may fit better depending on workload.

### 10.1. Hash-partitioned global indexes

A hash-partitioned global index distributes keys across multiple index partitions. This reduces write concentration on a single region while preserving standard B-tree ordering within each partition.

Concept:

~~~text
Key -> HASH(key) -> Index partition
                      |       |       |
                      v       v       v
                    Part 1  Part 2  Part 3
~~~

Illustrative syntax for a global hash-partitioned index:

~~~sql
CREATE INDEX ix_orders_id_hash
ON orders (order_id)
GLOBAL PARTITION BY HASH (order_id)
PARTITIONS 8;
~~~

Exact syntax and support depend on table type, Oracle version, and partitioning options. Hash partitioning distributes keys across partitions by hash, so ranges on original values may need to probe multiple partitions. Check execution plans and documentation for your release.

### 10.2. Table/index partitioning

If a table is partitioned by date or another business attribute, local indexes distribute data and index segments per partition. This helps when workloads filter by the partition key and follow partition-based data lifecycles.

Partitioning does not automatically eliminate right-hand contention if all inserts still land in the newest partition's trailing index leaf. Align partition keys and local/global index strategies with write patterns.

### 10.3. Distributed key design

A key embedding a shard/instance/tenant or hash prefix can distribute inserts better, though it alters key semantics and can impact ranges/ordering. For example, leading a composite key with a tenant prefix can spread load across tenants if tenant traffic is not overly skewed. Do not add random prefixes arbitrarily if the application relies on global ordering or simple keys.

### 10.4. Combining reverse key with other normal indexes on the same table

You can maintain a reverse key index for inserts/equality lookups alongside another index for range queries, if the storage and DML overhead of two indexes is acceptable. Every extra index increases `INSERT`/`UPDATE`/`DELETE` cost because Oracle must maintain an additional structure.

Illustrative example:
- Unique reverse index on `ORDER_ID` to reduce hot leaf contention on inserts and serve equality lookups.
- Standard index on `(ORDER_DATE, ORDER_ID)` to serve daily reporting and date-ordered pagination.

Do not create both a normal and a reverse index on the same column "just in case"; have concrete query workloads and measure the cost.

## 11. When Should You Use or Avoid a Reverse Key Index?

### 11.1. Signals to evaluate reverse key

- Very high concurrent insert rate on the table.
- Monotonically or near-monotonically increasing index keys.
- AWR/ASH or session monitoring shows index leaf/block contention.
- Inserts concentrate on the right-most leaf block.
- Read queries are predominantly equality lookups on the key.
- Range/ordered reports can use a different index or tolerate another access path.

### 11.2. Signals it is unsuitable

- Queries frequently use `BETWEEN`, `>`, `<` on the indexed key.
- Applications need the newest/oldest IDs using index order.
- Queries rely on `ORDER BY key FETCH FIRST N`.
- The index is the primary access path for range pagination.
- The real bottleneck is sequence allocation, row locks, table hot blocks, or another mechanism.
- Insert concurrency is low, making range-scan loss unjustified.

### 11.3. Quick decision table

| Workload | Direction |
|---|---|
| High concurrent inserts, ascending sequence keys, equality lookups | Evaluate reverse key index |
| High concurrent inserts, frequent key range queries | Evaluate hash partitioning, partition strategy, or distributed keys; keep normal B-tree if needed |
| Key-order range/top-N reads are critical | Standard B-tree |
| Only sequence waits, no index leaf contention | Investigate `CACHE`/`ORDER`/scalable sequences and sequence usage |
| Heavy updates to the same row | Investigate row locks; reverse key does not help |
| RAC hot index block | Measure global cache contention and evaluate reverse or hash-partitioned index |

## 12. Measuring and Diagnosing Index Contention

Do not create a reverse key index merely because an ID uses a sequence. Prove that the bottleneck resides at the index leaf block level.

### 12.1. Inspecting wait events

DBAs can observe waiting sessions:

~~~sql
SELECT sid,
       serial#,
       username,
       event,
       wait_class,
       seconds_in_wait,
       sql_id,
       blocking_session
FROM v$session
WHERE wait_class <> 'Idle'
ORDER BY seconds_in_wait DESC;
~~~

Events to watch depending on version and workload:
- `buffer busy waits`;
- `enq: TX - index contention`;
- `gc buffer busy acquire`;
- `gc buffer busy release`;
- Other global cache or index block wait events.

Exact event names and semantics vary across releases. Correlate wait events with target objects/segments, `SQL_ID`, module/action, and peak load windows.

### 12.2. Viewing segment statistics

`V$SEGMENT_STATISTICS` can expose metrics like logical reads, physical reads, buffer busy waits, or ITL waits per segment, depending on release and supported statistics.

~~~sql
SELECT owner,
       object_name,
       subobject_name,
       statistic_name,
       value
FROM v$segment_statistics
WHERE owner = USER
  AND object_name IN ('IX_ORDERS_ID', 'IX_ORDERS_ORDER_ID_REV')
  AND statistic_name IN (
      'logical reads',
      'physical reads',
      'buffer busy waits',
      'ITL waits'
  )
ORDER BY object_name, statistic_name;
~~~

These are cumulative statistics. When comparing, capture snapshots at the start and end of equivalent intervals/workloads and compute deltas. Never compare raw cumulative totals between segments of different ages or DML volumes.

### 12.3. Inspecting index metadata

~~~sql
SELECT index_name,
       table_name,
       uniqueness,
       status,
       blevel,
       leaf_blocks,
       distinct_keys,
       clustering_factor,
       num_rows,
       last_analyzed
FROM user_indexes
WHERE table_name = 'ORDERS'
ORDER BY index_name;
~~~

Attributes like `BLEVEL`, `LEAF_BLOCKS`, `DISTINCT_KEYS`, and `CLUSTERING_FACTOR` describe index structure and statistics, but do not prove contention on their own. Combine them with wait events, segment stats, and workload metrics.

### 12.4. Identifying SQL causing index inserts

Correlate `SQL_ID` with SQL text and session module/action to pinpoint `INSERT`/`UPDATE`/`DELETE` statements on the table. If authorized, AWR/ASH helps analyze over time and by object; AWR/ASH usage depends on licensing and environment policy.

Never enable system-wide tracing or query high-privilege administrative views just to locate a hot index without an appropriate investigation scope.

## 13. Comparing Execution Plans: Equality and Range

Create two independent lab tables to compare, avoiding maintaining both a normal and a reverse index on the same column during insert tests.

### 13.1. Create lab data

Practice only in an authorized DEV/TEST schema:

~~~sql
CREATE TABLE lab_normal_key (
    id      NUMBER NOT NULL,
    payload VARCHAR2(50)
);

CREATE TABLE lab_reverse_key (
    id      NUMBER NOT NULL,
    payload VARCHAR2(50)
);

INSERT INTO lab_normal_key (id, payload)
SELECT LEVEL, 'row-' || TO_CHAR(LEVEL)
FROM dual
CONNECT BY LEVEL <= 100000;

INSERT INTO lab_reverse_key (id, payload)
SELECT LEVEL, 'row-' || TO_CHAR(LEVEL)
FROM dual
CONNECT BY LEVEL <= 100000;

COMMIT;
~~~

Create indexes:

~~~sql
CREATE INDEX ix_lab_normal_key
ON lab_normal_key (id);

CREATE INDEX ix_lab_reverse_key
ON lab_reverse_key (id)
REVERSE;

BEGIN
    DBMS_STATS.GATHER_TABLE_STATS(USER, 'LAB_NORMAL_KEY');
    DBMS_STATS.GATHER_TABLE_STATS(USER, 'LAB_REVERSE_KEY');
END;
/
~~~

### 13.2. Equality lookup on a normal index

~~~sql
EXPLAIN PLAN FOR
SELECT payload
FROM lab_normal_key
WHERE id = 50000;

SELECT *
FROM TABLE(DBMS_XPLAN.DISPLAY);
~~~

### 13.3. Equality lookup on a reverse key index

~~~sql
EXPLAIN PLAN FOR
SELECT payload
FROM lab_reverse_key
WHERE id = 50000;

SELECT *
FROM TABLE(DBMS_XPLAN.DISPLAY);
~~~

Both queries can use an index equality lookup if the optimizer judges it beneficial. Exact operation names depend on index uniqueness, projection, and cost.

### 13.4. Range query on a normal index

~~~sql
EXPLAIN PLAN FOR
SELECT payload
FROM lab_normal_key
WHERE id BETWEEN 50000 AND 50100;

SELECT *
FROM TABLE(DBMS_XPLAN.DISPLAY);
~~~

The optimizer can choose `INDEX RANGE SCAN` on the standard B-tree.

### 13.5. Range query on a reverse key index

~~~sql
EXPLAIN PLAN FOR
SELECT payload
FROM lab_reverse_key
WHERE id BETWEEN 50000 AND 50100;

SELECT *
FROM TABLE(DBMS_XPLAN.DISPLAY);
~~~

A reverse key index does not support range scans in original ID order. The optimizer may pick a full table scan or another access path. Do not force an index hint to claim the reverse index can range scan; observe the natural operation.

### 13.6. Viewing predicates and execution statistics

When running actual queries in the lab, you can use:

~~~sql
SELECT /*+ GATHER_PLAN_STATISTICS */
       payload
FROM lab_normal_key
WHERE id BETWEEN 50000 AND 50100;

SELECT *
FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(NULL, NULL, 'ALLSTATS LAST +PREDICATE'));
~~~

Repeat for the reverse table. Ensure the statement just executed is the cursor displayed, and statistics collection was enabled for that statement. Compare actual rows, buffers, access predicates, and operations—not just estimated cost.

## 14. Concurrency Practice to Observe Right-Hand Contention

A single session inserting sequentially rarely shows hot leaf block contention. A multi-session concurrent workload is needed.

### 14.1. Create separate comparison tables

~~~sql
CREATE TABLE lab_insert_normal (
    id      NUMBER NOT NULL,
    payload VARCHAR2(100)
);

CREATE TABLE lab_insert_reverse (
    id      NUMBER NOT NULL,
    payload VARCHAR2(100)
);

CREATE UNIQUE INDEX ux_lab_insert_normal
ON lab_insert_normal (id);

CREATE UNIQUE INDEX ux_lab_insert_reverse
ON lab_insert_reverse (id)
REVERSE;
~~~

### 14.2. Use a sequence for each table

~~~sql
CREATE SEQUENCE lab_normal_seq START WITH 1 INCREMENT BY 1 CACHE 1000 NOORDER;
CREATE SEQUENCE lab_reverse_seq START WITH 1 INCREMENT BY 1 CACHE 1000 NOORDER;
~~~

Each worker/session inserts a large batch of rows into its corresponding table:

~~~sql
INSERT INTO lab_insert_normal (id, payload)
VALUES (lab_normal_seq.NEXTVAL, 'normal');

COMMIT;
~~~

~~~sql
INSERT INTO lab_insert_reverse (id, payload)
VALUES (lab_reverse_seq.NEXTVAL, 'reverse');

COMMIT;
~~~

Repeat many times from multiple sessions or use a controlled benchmark tool. Do not run both workloads simultaneously against the same resource if comparing independently; keep session counts, row counts, payloads, commit frequency, and run durations equivalent.

### 14.3. Compare results

Record:
- Total rows inserted.
- Rows/second or completion time.
- Wait events over time.
- Segment statistics before and after.
- CPU, I/O, redo, and commit latency.
- Impact on related equality and range queries.

A reverse key index can reduce certain types of leaf block contention, yet it does not guarantee throughput will always increase. If the bottleneck is redo, log file sync, sequence allocation, or storage I/O, results can differ.

### 14.4. Do not treat the lab as a production benchmark

This lab only illustrates the methodology. Real results depend on CPU, storage, cache, database release, concurrency, index size, RAC, and concurrent workloads. Before changing production indexes, benchmark with representative data and read/write ratios.

## 15. Index Conversion and Rollout Planning

Once you have confirmed a B-tree index suffers from right-hand contention and the workload is primarily equality-based, you can evaluate switching to reverse key.

A controlled rollout process:

1. Identify the index and SQL statements causing contention.
2. Classify read workloads: equality, range, `ORDER BY`, pagination, `MIN`/`MAX`.
3. Check constraints relying on the index.
4. Prototype the reverse index in a test environment.
5. Compare execution plans for critical SQL statements.
6. Benchmark insert concurrency and read workloads.
7. Plan rebuild/constraint handling, storage, availability, and rollback.
8. Deploy within an appropriate maintenance window.
9. Monitor wait events, segment stats, SQL latency, and application errors.
10. If trade-offs are unacceptable, rebuild `NOREVERSE` or revert the index strategy per plan.

### 15.1. Rebuilds can require additional resources

Index rebuilds can consume additional segment and `TEMP` space, I/O, CPU, and may impact DML depending on how they are run. Online rebuilds have specific restrictions and prerequisites by index type, release, and licensing. Do not assume every reverse key index can be rebuilt online in every environment.

### 15.2. Unique constraints and indexes

If the index backs a primary key or unique constraint, verify how the constraint is tied to the index. Never drop an index before understanding dependencies. You may need `ALTER TABLE ENABLE`/`DISABLE` or `USING INDEX` per a specific constraint plan, though those operations can affect integrity and concurrency. Test in a non-production environment first.

## 16. Common Misconceptions

| Misconception | Accurate understanding |
|---|---|
| Reverse key reverses ID digits | Oracle reverses key bytes inside the index without changing column values |
| Reverse key is a hash index | It is still a B-tree index |
| Reverse key makes inserts faster in every case | It reduces right-hand leaf block contention when that is the bottleneck |
| Reverse key does not support equality | Equality lookups can still use a reverse key index |
| Reverse key supports BETWEEN like a standard B-tree | It does not support range scans in original value order |
| A large CACHE solves every hot index block | `CACHE` reduces sequence allocation overhead, not index key order |
| Sequences have no gaps when ORDER is used | Sequences do not guarantee gap-free values; rollbacks/caches/restarts create gaps |
| Every table using a sequence needs reverse key | Consider it only with high concurrency and measured contention |
| Reverse key eliminates row locks | No; row locks are still required for DML on the same row |
| Reverse key always distributes perfectly uniformly | Dispersion depends on byte representation and key distribution |
| Having a reverse index guarantees the optimizer will use it | The optimizer still decides based on cost and predicates |
| A reverse index can serve as the sole index for all queries | Range, ordering, and top-N by original key usually require a normal index or another path |

## 17. Review Questions

**Question 1.** Why can ascending keys cause right-hand index contention?

**Answer:** New keys are generally inserted into the trailing edge of the B-tree index. Many sessions inserting concurrently can hit the same rightmost leaf block, causing buffer/block contention.

**Question 2.** What does a reverse key index change?

**Answer:** Oracle reverses the byte order of index keys before storage, altering their sorted position in the B-tree and scattering inserts with ascending keys.

**Question 3.** Is a reverse key index still a B-tree?

**Answer:** Yes. It is a B-tree index with byte-reversed keys.

**Question 4.** Does a reverse key index support `WHERE id = :id`?

**Answer:** Yes, it can. Equality lookups remain supported when the optimizer finds the index cost-effective.

**Question 5.** Why is a reverse key index unsuitable for `BETWEEN`?

**Answer:** Byte order is reversed, so numerically consecutive original values do not sit adjacent in the index; range scans in original key order are impossible.

**Question 6.** Does a reverse key index help `ORDER BY id`?

**Answer:** You cannot rely on reverse index order to return results in original ID order; queries may require a sort or another access path.

**Question 7.** Does sequence `CACHE` replace a reverse key index?

**Answer:** No. `CACHE` reduces sequence allocation overhead; reverse key changes key placement inside the index to relieve hot leaf blocks.

**Question 8.** Can a reverse key index be a unique index?

**Answer:** Yes. Oracle still enforces uniqueness on the original key values.

**Question 9.** When should a reverse key index be evaluated?

**Answer:** When high-concurrency inserts use ascending keys, right-hand leaf block contention is proven, and read workloads are mostly equality lookups.

**Question 10.** When should a standard B-tree index be kept?

**Answer:** When range queries, `ORDER BY`, top-N, or pagination in original key order are important.

**Question 11.** Does a reverse key index solve `TX` row lock contention?

**Answer:** No. Row lock contention is conflict over table rows/transactions; reverse key addresses insert placement in the index.

**Question 12.** How do you verify benefits before deploying?

**Answer:** Benchmark normal and reverse indexes under equivalent concurrent workloads, measuring wait events, segment statistics, throughput, and execution plans for both equality and range queries.

## Conclusion

**A reverse key index is a B-tree index in which Oracle reverses the byte order of keys to scatter ascending-key inserts away from the trailing leaf block.** It can reduce right-hand index leaf block contention in high-concurrency write workloads, especially when multiple sessions or RAC instances insert ascending sequence keys simultaneously.

In return, a reverse key index does not preserve original value order and therefore does not support index range scans on those keys. Equality lookups can still use the index, whereas `BETWEEN`, inequality ranges, `ORDER BY`, and top-N by key usually require a standard B-tree index or an alternative design. Sequence `CACHE`, `NOORDER`, and scalable sequences address different aspects of key allocation; they do not substitute for scattering insert placement in the index.

Before choosing reverse key, identify the contending wait events and segments, classify read queries by equality vs. range, test normal and reverse indexes on representative workloads, and weigh total read/write costs. Reverse key is an intentional choice for a specific workload pattern, not a default setting for every ascending primary key.
